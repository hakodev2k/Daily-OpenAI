# Ý tưởng hôm nay: Personal API Contract Guardian

## 1. Tóm tắt ý tưởng

Xây dựng một công cụ giúp developer theo dõi thay đổi API contract giữa backend và client, phát hiện breaking change trước khi deploy. Công cụ phù hợp với developer/team nhỏ dùng REST API nhưng chưa muốn triển khai hệ thống API governance phức tạp.

Quy mô: Medium. MVP dự kiến: 2-4 tuần.

## 2. Bài toán thực tế

Khi API thay đổi, nhiều lỗi phát sinh do đổi tên field, xóa property, thay đổi kiểu dữ liệu hoặc thay đổi validation nhưng không được phát hiện sớm. Developer thường kiểm tra thủ công bằng Swagger, test case hoặc chờ QA phát hiện.

Giả định: các team nhỏ chưa có quy trình quản lý contract API tự động sẽ gặp vấn đề này thường xuyên.

## 3. Người dùng mục tiêu

Primary user:
- Backend developer.
- Technical lead quản lý nhiều API.
- Solo developer xây dựng nhiều service.

Pain point: biết API đang chạy nhưng không biết thay đổi mới có phá vỡ client cũ hay không.

## 4. Giải pháp đề xuất

Workflow:

1. Import OpenAPI/Swagger document hiện tại.
2. Lưu version contract.
3. Developer upload version mới.
4. Hệ thống compare hai version.
5. Sinh báo cáo breaking change.

Ví dụ:

API cũ có `customerName`, API mới đổi thành `name`; hệ thống cảnh báo đây là breaking change.

Điểm khác biệt: tập trung vào workflow cá nhân và CI/CD đơn giản thay vì enterprise API management.

## 5. Tại sao ý tưởng này đáng làm

Giá trị:
- Giảm lỗi production do thay đổi API.
- Học sâu OpenAPI, testing và CI/CD.

Phù hợp solo developer vì có thể bắt đầu bằng một CLI/tool nhỏ.

Rủi ro thất bại: nếu người dùng chỉ có vài API đơn giản thì giá trị thấp.

Lý do không nên xây: nhiều team lớn đã có API governance riêng.

## 6. Phạm vi MVP

### Must have

- Upload OpenAPI JSON/YAML.
- Compare hai version.
- Phát hiện breaking change cơ bản.
- Xuất Markdown report.

### Should have

- GitHub Actions integration.
- Comment vào Pull Request.
- Lưu lịch sử version.

### Later

- AI giải thích impact.
- Multi-project dashboard.
- Team collaboration.

## 7. Luồng hoạt động

Developer push code
→ CI tạo OpenAPI file
→ tool nhận contract mới
→ validate
→ compare với version trước
→ lưu kết quả
→ trả report.

Failure:
- Không có baseline: tạo version đầu tiên.
- File lỗi: báo validation error.
- Không chắc breaking change: đánh dấu warning.

## 8. Kiến trúc đề xuất

Modular monolith:

- CLI hoặc Web UI.
- ASP.NET Core API nếu cần server mode.
- PostgreSQL lưu project/version.
- Background worker cho scan định kỳ.
- File storage cho OpenAPI documents.
- Serilog logging.

Không cần microservice vì workload nhỏ.

## 9. Công nghệ đề xuất

- .NET 8/9: phù hợp với kinh nghiệm C#.
- ASP.NET Core: xây API nhanh.
- PostgreSQL: lưu metadata.
- OpenAPI.NET/NSwag: parse contract.
- Docker: deploy dễ.
- GitHub Actions: CI integration.

Alternative đơn giản: .NET CLI + SQLite.

## 11. API và tích hợp

Tích hợp:
- GitHub Actions: chạy kiểm tra khi merge.
- OpenAPI specification: nguồn dữ liệu chính.

Không cần API bên ngoài trong MVP.

## 12. AI có thực sự cần thiết không?

AI hữu ích nhưng optional.

Có thể dùng AI để giải thích:
- Vì sao thay đổi nguy hiểm.
- Client nào có thể bị ảnh hưởng.

Fallback: rule engine deterministic.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

Tạo 10 thay đổi API mẫu và kiểm tra rule detection.

### Phase 1 — Core MVP

Build parser, comparer và report generator.

### Phase 2 — Reliability

Thêm test, logging, edge case handling.

### Phase 3 — Expansion

Thêm GitHub integration và dashboard.

### Phase 4 — Production readiness

Docker image, documentation, release pipeline.

## 14. Các bài toán kỹ thuật đáng học

1. OpenAPI parsing - hiểu API contract.
2. Semantic versioning - quản lý compatibility.
3. Diff algorithm - so sánh cấu trúc dữ liệu.
4. CI/CD integration - tự động hóa workflow.
5. Rule engine - thiết kế business rule.

## 15. Rủi ro và cách xử lý

- False positive: cho phép cấu hình rule.
- Scope lớn: chỉ hỗ trợ REST/OpenAPI trước.
- Adoption thấp: dùng chính dự án cá nhân trước.

## 16. Kiểm thử

5 scenario:

1. Thêm field không breaking.
2. Xóa required field bị cảnh báo.
3. Đổi type field bị phát hiện.
4. OpenAPI invalid bị từ chối.
5. CI pipeline trả đúng exit code.

## 17. Cách đo dự án hữu ích

- Thời gian review API giảm.
- Số lần tool được chạy trong CI.
- Tỷ lệ cảnh báo chính xác.

## 20. Việc cần làm ngay hôm nay

Trong 60-120 phút:

Objective: tạo CLI có thể compare hai OpenAPI file.

Tasks:

1. Tạo project:

```bash
dotnet new console -n ApiContractGuardian
```

2. Cài package OpenAPI parser.

3. Tạo:
- ContractLoader.cs
- ContractComparer.cs
- ChangeReport.cs

4. Load hai file swagger.json.
5. In danh sách breaking change ra console.

Kết quả:

Có thể chạy command và nhận report thay đổi API.

Verification:
- Parse được OpenAPI.
- Detect được xóa endpoint.
- Detect được thay đổi field type.

Stop condition:
Không thêm dashboard, AI hoặc authentication trước khi core compare hoạt động.
