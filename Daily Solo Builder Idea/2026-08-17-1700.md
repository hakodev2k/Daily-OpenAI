# Ý tưởng hôm nay: ExposureDiff — Self-hosted Attack Surface Drift Monitor

## 1. Tóm tắt ý tưởng

**ExposureDiff** là một công cụ self-hosted dành cho developer vận hành VPS, mini PC, homelab hoặc các ứng dụng Docker, có nhiệm vụ định kỳ kiểm tra **những cổng và dịch vụ đang thực sự lộ ra mạng**, so sánh với danh sách được phép, rồi cảnh báo khi xuất hiện thay đổi ngoài ý muốn. Thay vì chỉ hỏi “server có sống không?”, công cụ trả lời câu hỏi quan trọng hơn: **“Hôm nay bề mặt mạng của tôi có khác hôm qua không, và thay đổi đó có chủ ý không?”**

- **Người dùng chính:** solo developer/self-hoster có 1–20 máy chủ hoặc endpoint do chính họ quản lý.
- **Bài toán:** port/service vô tình bị expose sau khi đổi Docker Compose, firewall, reverse proxy hoặc cấu hình máy chủ.
- **Quy mô:** Medium.
- **Thời gian MVP ước tính:** 7–12 ngày làm ngoài giờ, hoặc khoảng 3–5 ngày tập trung.

## 2. Bài toán thực tế

Một developer tự vận hành dịch vụ thường thay đổi nhiều lớp cấu hình: Docker port publishing, reverse proxy, firewall, cloud security group, ứng dụng mới, database, dashboard quản trị hoặc agent nội bộ. Sau một thay đổi tưởng như nhỏ, một service có thể bắt đầu lắng nghe ở interface hoặc port không mong muốn.

**Fact đã xác nhận:** Docker Engine trên Linux tự tạo các firewall rule để hỗ trợ network isolation, port publishing và filtering cho bridge network. Điều đó có nghĩa là việc publish port trong Docker không chỉ là chi tiết cấu hình ứng dụng mà trực tiếp ảnh hưởng đường đi mạng trên host. Nguồn: Docker Docs — Packet filtering and firewalls: https://docs.docker.com/engine/network/packet-filtering-firewalls/

**Fact đã xác nhận:** Nmap phân loại port theo nhiều trạng thái như `open`, `closed`, `filtered`, và tài liệu chính thức nêu rõ open port là nơi ứng dụng đang chấp nhận kết nối. Nguồn: Nmap — Port Scanning Basics: https://nmap.org/book/man-port-scanning-basics.html

Người gặp vấn đề này thường là:

- developer chạy nhiều container trên VPS;
- người có homelab hoặc mini PC;
- solo builder có staging/prod nhỏ;
- developer thử công cụ mới rồi quên đóng port;
- người dùng reverse proxy nhưng vô tình publish cả port backend trực tiếp.

Tần suất không nhất thiết hàng ngày, nhưng vấn đề xuất hiện lặp lại mỗi khi:

- deploy service mới;
- sửa `docker-compose.yml`;
- đổi firewall;
- thêm database/cache/monitoring dashboard;
- migrate VPS;
- cài package hoặc daemon mới.

Cách xử lý hiện tại thường là:

- chạy `nmap` thủ công;
- xem `docker ps`;
- xem `ss -lntup` hoặc `netstat`;
- kiểm tra UFW/firewalld;
- nhớ bằng đầu “port nào đáng lẽ phải mở”.

Nhược điểm là mỗi nguồn chỉ cho một góc nhìn. `docker ps` cho biết port container được publish nhưng không cho biết một scanner ở vị trí mạng khác nhìn thấy gì. Ngược lại, một scan ngoài mạng cho biết bề mặt quan sát được nhưng không nói thay đổi đó đến từ container nào hoặc có được phê duyệt hay không.

**Analysis:** giá trị chính của ExposureDiff không nằm ở việc thay Nmap, mà nằm ở **lịch sử + baseline + diff + approval**.

**Assumption cần kiểm chứng:** solo self-hoster thực sự muốn một dashboard nhỏ và alert theo thay đổi thay vì tự chạy script. Điều này cần validation trước khi đầu tư nhiều UI.

## 3. Người dùng mục tiêu

### Primary user cho MVP

Một backend developer hoặc solo builder có:

- 1–5 VPS/mini PC;
- Docker hoặc systemd services;
- một vài domain/subdomain;
- reverse proxy như Nginx/Caddy/Traefik;
- không có team security riêng.

### Context sử dụng

Người dùng deploy thường xuyên bằng Docker Compose hoặc CI/CD, có thể publish port mới trong quá trình thử nghiệm rồi quên thu hồi.

### Pain point chính

Họ không có một câu trả lời nhanh cho:

> “Có port hoặc service nào đang expose mà tôi không hề chủ động cho phép không?”

### Workaround hiện tại

- ghi port trong README;
- chạy Nmap thủ công;
- nhớ cấu hình bằng kinh nghiệm;
- chỉ giám sát uptime của domain chính.

### Vì sao họ thử ExposureDiff

Vì setup ban đầu có thể rất nhỏ: khai báo host + expected ports, chạy scan định kỳ, nhận một diff rõ ràng khi trạng thái thay đổi.

## 4. Giải pháp đề xuất

Người dùng khai báo một **Asset** và một **Exposure Policy**.

Ví dụ:

- Host: `prod.example.com`
- Allowed TCP:
  - `22` — SSH
  - `80` — HTTP redirect
  - `443` — HTTPS
- Explicitly forbidden:
  - `5432` — PostgreSQL
  - `6379` — Redis
  - `3000` — internal web app

ExposureDiff định kỳ chạy một probe từ worker ở vị trí mạng đã chọn, lưu kết quả scan, normalize dữ liệu rồi so sánh với baseline trước đó.

### Input

- hostname/IP do người dùng sở hữu hoặc có quyền kiểm tra;
- danh sách port được phép;
- tần suất scan;
- tùy chọn TLS/HTTP probe cho port web.

### Processing

1. resolve DNS;
2. scan danh sách port cấu hình hoặc top ports;
3. normalize trạng thái;
4. nếu port mở, thử service fingerprint nhẹ;
5. với HTTP/HTTPS, đọc status, server header, TLS certificate metadata;
6. so với scan gần nhất và policy;
7. tạo findings.

### Output

Ví dụ:

```text
NEW EXPOSURE
Host: prod.example.com
Port: 5432/tcp
Observed: open
Expected: forbidden
First seen: 2026-08-17 16:58 ICT
Previous scan: closed
Severity: high
```

### Tự động hóa

- scan định kỳ;
- diff;
- classify finding;
- alert Telegram/email/webhook;
- mark finding resolved khi exposure biến mất.

### Người dùng vẫn kiểm soát

- asset nào được phép scan;
- port nào allowed/forbidden;
- cadence;
- acknowledgement;
- cập nhật baseline.

### Differentiator

Không cố trở thành vulnerability scanner đầy đủ. ExposureDiff chỉ tập trung vào một câu hỏi hẹp và dễ tin cậy:

> **“Attack surface đã thay đổi như thế nào so với trạng thái được phê duyệt?”**

### Ví dụ end-to-end

1. Hà deploy Grafana và tạm publish `3000:3000` để debug.
2. Sau khi xong, quên xóa mapping.
3. Worker scan buổi tối thấy `3000/tcp` chuyển từ `closed` sang `open`.
4. Policy không có port 3000 trong allow-list.
5. ExposureDiff gửi Telegram: “New unexpected exposure: 3000/tcp”.
6. Hà sửa Compose, deploy lại.
7. Scan tiếp theo thấy port closed và tự đóng finding.

## 5. Tại sao ý tưởng này đáng làm

### Giá trị thực tế

Nó bảo vệ chính các server cá nhân của developer ngay từ user đầu tiên. Không cần chờ có khách hàng mới tạo giá trị.

### Giá trị học kỹ thuật

Project buộc phải xử lý:

- networking;
- DNS;
- background jobs;
- subprocess execution;
- parsing structured command output;
- state diff;
- idempotent alerts;
- security boundaries;
- deployment self-hosted.

### Phù hợp solo developer

Core workflow rất nhỏ:

`asset -> scan -> normalized snapshot -> diff -> alert`

Không cần microservice, queue lớn hay data pipeline phức tạp.

### Vẫn hữu ích khi chỉ có một user

Một developer có 2–3 server vẫn có thể dùng ExposureDiff hàng tháng trong nhiều năm.

### Điều khiến ý tưởng thất bại

Nếu người dùng đã có external attack-surface monitoring hoặc SIEM đầy đủ, ExposureDiff có thể quá đơn giản.

### Lý do mạnh nhất để không build

Nếu chính bạn chỉ có một VPS rất ổn định, ít deploy, và một cron script `nmap + diff` đã giải quyết đủ tốt thì dashboard riêng có thể không đáng công bảo trì.

## 6. Phạm vi MVP

### Must have

- CRUD Asset: hostname/IP + label.
- TCP port policy: allowed/forbidden.
- chạy scan thủ công.
- scheduled scan.
- parse Nmap XML output.
- lưu `ScanRun` và `ObservedPort`.
- diff với scan trước.
- finding khi:
  - new open port;
  - forbidden port open;
  - allowed port unexpectedly closed.
- dashboard lịch sử 10–20 scan gần nhất.
- Telegram hoặc generic webhook alert.

### Should have

- HTTP probe cho port 80/443/custom.
- TLS certificate expiry.
- DNS resolution history.
- acknowledgement cho finding.
- suppression window trong thời gian maintenance.
- Docker label/import để generate expected exposure cho chính host chạy agent.

### Later

- nhiều probe locations;
- cloud security group reconciliation;
- IPv6;
- service/version fingerprint nâng cao;
- certificate transparency integration;
- mobile app;
- team workspace;
- vulnerability databases/CVE matching.

MVP không làm vulnerability scanner và không scan Internet diện rộng.

## 7. Luồng hoạt động

### Happy path

User tạo Asset
→ nhập hostname + policy
→ API validate hostname/IP
→ scheduler tạo ScanRun
→ worker gọi Nmap với target đã allow-list
→ parser đọc XML
→ lưu observed ports
→ compare với previous successful run
→ sinh findings
→ gửi alert một lần cho finding mới
→ dashboard hiển thị diff
→ scan sau xác nhận trạng thái bình thường
→ finding chuyển `Resolved`.

### Alternative flow: DNS đổi IP

- lưu cả hostname lẫn resolved IP;
- nếu IP thay đổi, ghi `DnsChange` event trong scan metadata;
- vẫn scan hostname theo policy;
- không tự coi IP change là security incident, chỉ là informational finding.

### Failure: target timeout

- ScanRun = `Failed` hoặc `Partial`;
- không dùng run thất bại làm baseline mới;
- retry có giới hạn;
- alert “scanner unavailable” tách khỏi exposure finding.

### Failure: Nmap missing

Worker health check báo dependency missing và không nhận scan jobs.

### Failure: notification provider lỗi

Finding vẫn được lưu; notification dùng retry và `NotificationAttempt` để không mất alert.

## 9. Công nghệ đề xuất

**Vì sao phù hợp:** LTS/current supported baseline hợp với project mới năm 2026; networking, background services, API và health checks đều tốt.

**Đơn giản hơn:** một console app .NET + SQLite trước khi có web.

**Khi outgrow:** không phải vấn đề chính; quy mô này ASP.NET Core có thể phục vụ lâu dài.

**Đơn giản hơn:** SQLite cho single-node prototype.

**Khi outgrow:** nếu scan hàng chục nghìn assets, có thể partition observations; chưa cần ở MVP.

### Nmap

**Vì sao:** công cụ trưởng thành, có XML output, mô hình port state rõ. Tài liệu chính thức mô tả Nmap là port scanner và phân loại các trạng thái `open`, `closed`, `filtered`, v.v. Nguồn: https://nmap.org/book/man-port-scanning-basics.html

**Đơn giản hơn:** `TcpClient.ConnectAsync` trên danh sách port nhỏ.

**Khi outgrow:** nếu cần distributed probing hoặc custom protocol fingerprint, có thể xây probe agent riêng.

### Vue 3 + Vite

**Vì sao:** dashboard nhỏ, tốc độ phát triển nhanh.

**Đơn giản hơn:** Razor Pages.

**Khi outgrow:** gần như không cần đổi framework chỉ vì scale.

### BackgroundService

**Vì sao:** recurring scan đơn giản, không cần thêm scheduler infrastructure.

**Đơn giản hơn:** cron gọi CLI.

**Khi outgrow:** chuyển Hangfire/Quartz.NET khi cần nhiều lịch, retry policy và operational UI.

### Docker Compose

**Vì sao:** self-hosted dễ triển khai.

Docker Docs xác nhận Docker sử dụng firewall rules cho network isolation và port publishing trên bridge network; đây cũng là một trong những lý do project này hữu ích với môi trường containerized. Nguồn: https://docs.docker.com/engine/network/packet-filtering-firewalls/

### Playwright

Dùng cho E2E dashboard và workflow acknowledge finding.

### GitHub Actions

Build, unit test, integration test, Docker image build.

## 10. Thiết kế dữ liệu ban đầu

### `Asset`

Purpose: đối tượng cần theo dõi.

Fields:

- `Id`
- `Name`
- `Target`
- `IsEnabled`
- `ScanIntervalMinutes`
- `CreatedAt`
- `LastSuccessfulScanAt`

Relationship:

- 1-N `PortPolicyRule`
- 1-N `ScanRun`
- 1-N `Finding`

Retention: giữ lâu dài.

### `PortPolicyRule`

Purpose: expected network exposure.

Fields:

- `Id`
- `AssetId`
- `Protocol`
- `PortFrom`
- `PortTo`
- `Expectation` (`Allowed`, `Forbidden`, `RequiredOpen`)
- `Description`

Retention: giữ history sau này; MVP có thể update trực tiếp.

### `ScanRun`

Purpose: một lần quan sát asset.

Fields:

- `Id`
- `AssetId`
- `StartedAt`
- `CompletedAt`
- `Status`
- `ResolvedIp`
- `ScannerVersion`
- `ErrorCode`

Retention: 90–180 ngày mặc định, configurable.

### `ObservedPort`

Purpose: kết quả normalized.

Fields:

- `ScanRunId`
- `Protocol`
- `Port`
- `State`
- `ServiceName`
- `ProductHint`

Retention: cùng ScanRun.

### `Finding`

Purpose: lifecycle của drift.

Fields:

- `Id`
- `AssetId`
- `Fingerprint`
- `Type`
- `Severity`
- `FirstSeenAt`
- `LastSeenAt`
- `Status`
- `AcknowledgedAt`
- `ResolvedAt`

Fingerprint giúp idempotency.

### `NotificationAttempt`

Purpose: track delivery.

Fields:

- `FindingId`
- `Channel`
- `AttemptedAt`
- `Status`
- `ProviderMessageId`

Retention: 30–90 ngày.

## 11. API và tích hợp

### Nmap CLI

- **Purpose:** TCP port scan và optional service detection nhẹ.
- **Auth:** không có.
- **Cost/rate limit:** miễn phí; giới hạn thực tế là CPU/network/time.
- **Privacy:** chỉ scan asset do user quản lý.
- **Fallback:** built-in TCP connect probe cho port list nhỏ.

### Telegram Bot API

- **Purpose:** alert nhanh.
- **Auth:** bot token.
- **Cost:** phù hợp MVP; cần tôn trọng provider limits.
- **Privacy:** message chứa hostname/port; cho phép user tắt hoặc dùng alias.
- **Fallback:** generic webhook hoặc email.

### DNS system resolver

- **Purpose:** resolve hostname trước scan.
- **Auth:** không.
- **Cost:** gần như không đáng kể ở quy mô nhỏ.
- **Privacy:** query DNS có thể đi qua resolver configured trên host.
- **Fallback:** IP target trực tiếp.

### ASP.NET Core Health Checks

- **Purpose:** app/db/scanner readiness.
- **Auth:** internal endpoint có thể hạn chế qua reverse proxy.
- **Cost:** không có.
- **Fallback:** custom `/healthz` implementation.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem hoàn toàn deterministic:

- port open hay không;
- state thay đổi hay không;
- có vi phạm policy hay không;
- alert đã gửi hay chưa.

Dùng LLM để quyết định một port có “nguy hiểm” hay không sẽ làm giảm độ tin cậy và khiến người dùng khó hiểu logic.

Nếu sau này muốn AI, chỉ nên dùng như **optional explanation layer**:

- input: finding + service metadata + policy;
- output structured: summary, likely cause, suggested checks;
- validation: không cho AI thay đổi severity hoặc tự remediate;
- deterministic fallback: hiển thị raw finding và checklist tĩnh.

MVP không cần AI.

## 14. Các bài toán kỹ thuật đáng học

### 1. State normalization và diff

Nmap có nhiều states, scan có thể partial. Bạn phải định nghĩa khi nào một change đủ chắc để tạo finding.

**Skill:** domain modeling và deterministic state machine.

### 2. Idempotency trong alert

Một port có thể mở qua 20 scan liên tiếp nhưng user chỉ nên nhận một alert ban đầu, rồi optional reminder.

**Skill:** fingerprinting, lifecycle state, retry-safe workflows.

### 3. Reliable background processing

Scan có thể timeout, DNS fail, worker restart giữa job.

**Skill:** retry, cancellation token, leases, failure recovery.

### 4. Network vantage point

Một port có thể `open` từ LAN nhưng `filtered` từ Internet. Nmap docs nhấn mạnh trạng thái phản ánh cách scanner nhìn target, không phải thuộc tính tuyệt đối của port.

**Skill:** hiểu networking thực tế và measurement semantics.

### 5. Security boundary của chính scanner

Tool security không được trở thành công cụ scan tùy ý Internet từ UI.

**Skill:** allow-list, authorization, SSRF-like target validation, safe subprocess execution.

## 15. Rủi ro và cách xử lý

### Rủi ro: biến project thành vulnerability scanner

**Mitigation:** scope statement rõ: exposure drift only. Không CVE DB ở MVP.

### Rủi ro: false positive do packet loss/firewall

**Mitigation:** yêu cầu 2 observations liên tiếp cho một số transition, hoặc severity thấp với ambiguous states.

### Rủi ro: scan asset không được phép

**Mitigation:** chỉ cho target do admin nhập; optional ownership verification; không có public multi-user scanning endpoint; rate limit chặt.

### Rủi ro: subprocess injection

**Mitigation:** không build shell command string; dùng `ProcessStartInfo.ArgumentList`; validate hostname/IP/port; không nhận raw Nmap flags từ user ở MVP.

### Rủi ro: scanner container cần quyền cao

**Mitigation:** ưu tiên TCP connect scan không yêu cầu raw packet capability; chỉ cấp capability cụ thể nếu thật sự cần.

### Rủi ro: privacy

Asset names/IPs là dữ liệu hạ tầng.

**Mitigation:** self-host, encrypt secrets, hạn chế log, alias trong notification.

### Rủi ro: maintenance burden

Nmap output/schema version thay đổi.

**Mitigation:** XML parser fixtures + pin supported versions + compatibility tests.

### Rủi ro: người dùng không cần UI

**Mitigation:** Phase 0 bằng CLI trước; nếu cron + diff đã đủ, có thể dừng ở personal CLI tool.

## 16. Kiểm thử

### Strategy

- **Unit tests:** policy evaluator, state transitions, fingerprinting.
- **Integration tests:** Postgres + parser + scheduler.
- **E2E tests:** Playwright cho asset → scan → finding → acknowledge.
- **Failure-path tests:** timeout, invalid XML, DNS failure, Telegram failure.
- **Security tests:** invalid target, argument injection, unauthorized endpoint.
- **Data-quality tests:** duplicate observations, partial scans, state mapping.

### 5 test scenario quan trọng nhất

1. Port 5432 từ closed → open và policy = forbidden → đúng một high finding.
2. Cùng port vẫn open ở 5 scan sau → không tạo 5 findings/alerts mới.
3. Scan timeout giữa chừng → run partial/failed, baseline cũ giữ nguyên.
4. User nhập target chứa shell metacharacters → request bị reject, không execute command ngoài ý muốn.
5. Port quay về closed → finding được resolve và lịch sử vẫn giữ first/last seen.

### First vertical slice

Endpoint:

```http
POST /api/scans/preview
Content-Type: application/json

{
  "target": "127.0.0.1",
  "ports": [22, 80, 443, 5432]
}
```

Backend:

1. validate target chỉ là localhost trong phiên đầu;
2. chạy Nmap XML output;
3. parse `<port>` và `<state>`;
4. map về:

```json
{
  "target": "127.0.0.1",
  "ports": [
    { "port": 22, "protocol": "tcp", "state": "closed" },
    { "port": 5432, "protocol": "tcp", "state": "open" }
  ]
}
```

### Unit test đầu tiên

Dùng một XML fixture nhỏ và assert parser map đúng:

- port number;
- protocol;
- state;
- service name nếu có.

### Expected result

Cuối phiên phải có một API chạy local và trả kết quả scan thật của localhost dưới dạng JSON normalized.

### Verification checklist

- [ ] `dotnet test` pass.
- [ ] `POST /api/scans/preview` hoạt động.
- [ ] input target không hợp lệ bị reject.
- [ ] không dùng shell command concatenation.
- [ ] XML Nmap được parse bằng test fixture.
- [ ] khi Nmap không tồn tại, API trả lỗi có kiểm soát.

### Stop condition

Dừng phiên ngay khi **một request HTTP có thể scan localhost và trả normalized JSON ổn định**. Chưa tạo database, scheduler, Telegram, authentication hoặc dashboard trong buổi đầu.

## Phân tách fact / analysis / assumption

- **Confirmed facts:** khả năng port-state scanning của Nmap; Docker firewall/port publishing behavior; ASP.NET Core health-check support.
- **Observation:** các primitive kỹ thuật cần thiết đều có sẵn, nên MVP không cần tự viết network scanner từ đầu.
- **Analysis:** giá trị khác biệt nằm ở baseline, diff, lifecycle và alert idempotency chứ không nằm ở scan engine.
- **Assumption:** solo developer/self-hoster sẵn sàng duy trì một service nhỏ để đổi lấy việc phát hiện exposure drift tự động.
- **Recommendation:** bắt đầu bằng localhost/VPS của chính mình, dùng TCP connect/Nmap scan hẹp và policy allow-list; tuyệt đối không xây public arbitrary-target scanner trong MVP.
