# Ý tưởng hôm nay: TimeZone Guard — Trình kiểm chứng lịch chạy Cron và Job theo múi giờ

## 1. Tóm tắt ý tưởng

**TimeZone Guard** là một công cụ web/CLI giúp developer nhập một lịch chạy dạng cron hoặc cấu hình scheduler, chọn múi giờ mong muốn, sau đó xem trước các lần chạy thực tế, phát hiện lệch UTC/local time, rủi ro DST, thời điểm không tồn tại hoặc bị lặp, và sinh ra cấu hình an toàn hơn cho GitHub Actions, Quartz.NET hoặc scheduler nội bộ. Công cụ nhắm tới developer và team nhỏ thường xuyên triển khai background jobs, scheduled workflows hoặc automation nhưng dễ cấu hình sai giờ khi môi trường chạy dùng UTC hoặc khi hệ thống liên quan nhiều múi giờ.

- **Bài toán chính:** job được cấu hình đúng cú pháp nhưng chạy sai giờ thực tế, đặc biệt khi nhầm UTC với local time hoặc gặp Daylight Saving Time.
- **Quy mô:** Medium.
- **MVP ước tính:** 5–10 ngày làm ngoài giờ cho một developer.

## 2. Bài toán thực tế

### Confirmed facts

GitHub Actions hỗ trợ `on.schedule` bằng POSIX cron. Theo tài liệu GitHub hiện tại, scheduled workflow mặc định chạy theo UTC, nhưng có thể khai báo thêm IANA timezone cho timezone-aware scheduling. GitHub cũng ghi rõ rằng timezone có DST có thể gặp trường hợp giờ bị bỏ qua khi spring-forward; một lịch nằm trong giờ bị bỏ qua sẽ được đẩy tới thời điểm hợp lệ tiếp theo.

Nguồn:

- GitHub Actions workflow syntax: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax
- Events that trigger workflows: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows

.NET cũng phân biệt hai tình huống khó khi xử lý DST:

- **Invalid time:** một local time không tồn tại do đồng hồ nhảy tới trước.
- **Ambiguous time:** một local time có thể ánh xạ sang hai UTC instant khác nhau khi đồng hồ quay lại.

`TimeZoneInfo` cung cấp API như `IsInvalidTime` và `IsAmbiguousTime` để phát hiện các trường hợp này.

Nguồn:

- .NET Time zone overview: https://learn.microsoft.com/en-us/dotnet/standard/datetime/time-zone-overview
- `TimeZoneInfo.IsInvalidTime`: https://learn.microsoft.com/en-us/dotnet/api/system.timezoneinfo.isinvalidtime?view=net-10.0
- `TimeZoneInfo.IsAmbiguousTime`: https://learn.microsoft.com/en-us/dotnet/api/system.timezoneinfo.isambiguoustime?view=net-10.0

### Vấn đề thực tế

Developer thường cấu hình cron bằng một chuỗi rất ngắn như:

```text
30 7 * * 1-5
```

Nhưng chuỗi đó không tự nói rõ:

- 07:30 theo UTC hay theo giờ Hà Nội?
- scheduler có hỗ trợ timezone hay không?
- sau khi deploy sang Linux container, timezone hệ điều hành có giống máy local không?
- nếu chạy cho khách hàng ở Mỹ hoặc châu Âu, lịch có giữ nguyên 07:30 local sau khi DST đổi không?
- nếu một job chạy lúc 02:30 ở timezone có DST, điều gì xảy ra vào ngày 02:30 không tồn tại?
- nếu local time xuất hiện hai lần, job chạy một hay hai lần?

Các lỗi kiểu này không phải lỗi syntax. Cron parser vẫn chấp nhận cấu hình, CI vẫn xanh, ứng dụng vẫn deploy thành công, nhưng hành vi production có thể sai.

### Ai gặp vấn đề

- Backend developer dùng Hangfire, Quartz.NET, `BackgroundService` hoặc cron Linux.
- Developer dùng GitHub Actions cho job định kỳ.
- Team nhỏ có hệ thống chạy ở UTC nhưng business schedule theo local time.
- SaaS nhỏ có khách hàng ở nhiều timezone.
- Người vận hành bot, crawler, notifier, report generator hoặc batch processing.

### Tần suất

**Quan sát:** không phải dự án nào cũng gặp lỗi timezone hàng ngày, nhưng schedule là loại cấu hình thường được tạo rồi để chạy hàng tháng hoặc hàng năm. Sai một lần có thể tồn tại lâu vì job vẫn “đang chạy”, chỉ là chạy sai giờ.

### Cách xử lý hiện nay

Developer thường:

- tự cộng/trừ UTC offset;
- dùng website cron expression viewer;
- chạy thử bằng cron tạm thời;
- đọc log sau khi deploy;
- dùng `crontab.guru` để kiểm tra cú pháp cron;
- thêm comment thủ công như `# 14:30 Vietnam = 07:30 UTC`;
- tìm Google mỗi lần DST thay đổi.

Các cách này hữu ích nhưng phân mảnh. Một cron viewer thường chỉ trả lời “lần chạy tiếp theo là khi nào”, không nhất thiết kiểm tra intent của người dùng, timezone semantics của từng platform hoặc DST anomalies.

### Assumption cần validation

Giả định sản phẩm: developer sẽ thấy giá trị nếu một công cụ không chỉ parse cron mà còn trả lời câu hỏi **“lịch này có thực sự chạy vào thời điểm business mà tôi mong muốn trên platform tôi sắp deploy không?”**. Giả định này cần được test bằng 5–10 người dùng trước khi đầu tư nhiều vào UI hoặc integration.

Người dùng mở TimeZone Guard trước khi:

- commit một cron mới;
- thay đổi lịch production;
- chuyển job từ server local sang cloud;

### Pain point chính

Họ có thể kiểm tra cú pháp cron nhưng vẫn không chắc runtime sẽ chạy đúng local time mong muốn.

- chạy thử thủ công;
- chờ job chạy thật;

### Lý do thử TimeZone Guard

Nó đưa cả **intent, platform, timezone và DST** vào cùng một màn hình và cho kết quả có thể kiểm chứng trước khi deploy.

## 4. Giải pháp đề xuất

### Main workflow

Người dùng nhập:

1. Platform:
   - Generic POSIX cron;
   - GitHub Actions;
   - Quartz.NET;
2. Cron expression;
3. Timezone mà người dùng **muốn business schedule tuân theo**, ví dụ `Asia/Bangkok`;
4. Tùy chọn “expected local time”, ví dụ 14:30;
5. Khoảng kiểm tra, ví dụ 12 tháng tiếp theo.

Hệ thống xử lý:

1. Parse cron theo dialect của platform.
2. Sinh các occurrence trong khoảng thời gian đã chọn.
3. Convert từng occurrence sang:
   - UTC;
   - timezone mục tiêu;
   - timezone runtime nếu user khai báo.
4. Dò:
   - offset thay đổi;
   - DST transition;
   - invalid local time;
   - ambiguous local time;
   - occurrence lệch expected local time;
   - cron chạy nhiều/ít hơn người dùng nghĩ.
5. Sinh verdict và recommendation.

Output:

- lịch 10 lần chạy tiếp theo;
- timeline 12 tháng;
- cảnh báo màu theo mức độ;
- explanation bằng ngôn ngữ đơn giản;
- cấu hình đề xuất phù hợp platform;
- đoạn test code C# để người dùng đưa vào test suite.

### Tự động hóa và quyền kiểm soát

**Tự động:**

- parse schedule;
- calculate occurrences;
- detect anomaly;
- compare intent với runtime behavior;
- generate safe examples.

**Người dùng vẫn kiểm soát:**

- timezone business;
- platform;
- policy cho ambiguous time;
- khoảng thời gian kiểm tra;
- quyết định sửa schedule.

MVP không tự động sửa repository hoặc deploy workflow.

### Key differentiator

Không chỉ là “cron parser”. TimeZone Guard hoạt động như một **schedule verifier**:

```text
Business intent
    ↓
Platform semantics
    ↓
Timezone rules
    ↓
Actual occurrences
    ↓
Mismatch / DST risk / recommendation
```

### Ví dụ end-to-end

Một developer muốn GitHub Action chạy **08:30 sáng giờ Việt Nam mỗi ngày làm việc**.

Người dùng nhập:

```text
Platform: GitHub Actions
Cron: 30 1 * * 1-5
Business timezone: Asia/Bangkok
Expected local time: 08:30
```

TimeZone Guard hiển thị:

```text
UTC       Asia/Bangkok
01:30     08:30
```

Kết quả:

```text
PASS
Next 20 occurrences match 08:30 Asia/Bangkok.
No DST transition exists in this timezone for the checked range.
```

Sau đó người dùng chọn `America/New_York`, expected time `08:30`, nhưng vẫn dùng fixed UTC cron. Timeline cho thấy local time thay đổi khi DST đổi. Tool trả về:

```text
WARNING: local execution time changes across DST.
Recommended: use timezone-aware scheduling when the selected platform supports it.
```

Nếu platform là GitHub Actions, tool có thể sinh ví dụ:

```yaml
on:
  schedule:
    - cron: '30 8 * * 1-5'
      timezone: 'America/New_York'
```

và ghi chú rằng timezone-aware schedule vẫn cần hiểu cách platform xử lý giờ bị skip trong DST transition.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Đây là loại tool nhỏ nhưng có thể được dùng mỗi khi tạo scheduled job mới. Nó đặc biệt hữu ích vì lỗi timezone thường nằm giữa config, infrastructure và business rule — nơi unit test thông thường dễ bỏ sót.

### Technical learning value

Project buộc developer hiểu sâu:

- `DateTimeOffset`;
- `TimeZoneInfo`;
- IANA vs Windows timezone IDs;
- cron semantics;
- DST;
- platform-specific scheduler behavior;
- deterministic simulation;
- property-based testing cho date/time.

### Phù hợp với solo developer

Core logic hoàn toàn deterministic. Không cần AI, GPU, crawler, queue phức tạp hay nguồn dữ liệu lớn. Phần khó chủ yếu là correctness, không phải scale.

### Vẫn hữu ích với rất ít user

Ngay cả khi chỉ chính developer sử dụng, nó có thể trở thành:

- tool cá nhân kiểm tra GitHub Actions;
- test helper cho các project có Hangfire/Quartz;
- CLI chạy trong CI;
- portfolio project về date/time correctness.

### Điều gì làm ý tưởng thất bại

Nếu tool chỉ trở thành một cron viewer khác mà không tạo ra verification rõ ràng, người dùng sẽ không có lý do quay lại.

### Lý do mạnh nhất để không build

Cron viewers đã tồn tại rất nhiều. Nếu không tập trung vào **intent verification + timezone + platform semantics + DST regression**, project dễ trở thành một clone không có giá trị riêng.

## 7. Luồng hoạt động

### Happy path

```text
User nhập cron + platform + timezone + intent
    ↓
Input validation
    ↓
Cron parser parse expression
    ↓
Occurrence engine sinh candidate instants
    ↓
Timezone engine convert UTC/local
    ↓
Risk analyzer kiểm tra mismatch và DST
    ↓
Result được trả về
    ↓
UI hiển thị timeline + verdict + recommendation
```

### Validation

Kiểm tra:

- cron có đúng số field cho dialect không;
- timezone có tồn tại không;
- interval kiểm tra có quá lớn không;
- expected local time có hợp lệ không;
- schedule có sinh occurrence nào trong range không.

### Storage

MVP có thể hoạt động **không cần database** cho chế độ anonymous.

Nếu muốn lưu history:

- chỉ lưu khi user bấm Save;
- không cần cho vertical slice đầu tiên.

### Alternative flow 1 — Cron không hợp lệ

Response:

```json
{
  "status": "invalid",
  "errors": [
    {
      "code": "CRON_PARSE_ERROR",
      "field": "cron",
      "message": "Expected 5 POSIX cron fields."
    }
  ]
}
```

### Alternative flow 2 — Timezone không tồn tại

Không fallback im lặng sang UTC. Trả lỗi rõ ràng.

### Alternative flow 3 — Invalid local time

Ví dụ một lịch business muốn chạy 02:30 trong ngày DST spring-forward.

Tool đánh dấu:

```text
INVALID LOCAL TIME
This wall-clock time does not exist on the transition date.
```

Recommendation phải phụ thuộc platform; không tự khẳng định hành vi khi adapter chưa được verify.

### Alternative flow 4 — Ambiguous local time

Nếu local time xuất hiện hai lần, tool hiển thị cả hai UTC offsets để người dùng thấy sự mơ hồ thay vì tự chọn một cách âm thầm.

### Failure case

Nếu timezone data trên host không đầy đủ hoặc platform adapter không support dialect:

- fail closed;
- trả `UNSUPPORTED_PLATFORM_SEMANTICS`;
- không đưa verdict giả tạo.

## 10. Thiết kế dữ liệu ban đầu

MVP anonymous có thể không cần DB. Core model nên là domain objects, không phải database entities.

### `ScheduleVerificationRequest`

Mục đích: mô tả intent cần kiểm tra.

Fields:

```text
Platform
Expression
BusinessTimeZone
ExpectedLocalTime?
StartInstant
CheckDuration
AmbiguousTimePolicy?
```

### `ScheduleOccurrence`

Mục đích: biểu diễn một lần chạy dự kiến.

Fields:

```text
Sequence
UtcInstant
LocalDateTime
UtcOffset
IsDst
IsAmbiguous
IsInvalid
MatchesExpectedLocalTime
```

Lưu ý: invalid local time không phải lúc nào cũng có một actual UTC occurrence. Có thể cần một model riêng cho expected wall-clock candidate thay vì ép mọi record thành actual occurrence.

### `VerificationIssue`

Fields:

```text
Code
Severity
Date
Description
Expected
Actual
RecommendationCode
```

Ví dụ issue codes:

```text
LOCAL_TIME_DRIFT
INVALID_WALL_CLOCK_TIME
AMBIGUOUS_WALL_CLOCK_TIME
PLATFORM_TIMEZONE_NOT_SET
NO_OCCURRENCE_IN_RANGE
UNSUPPORTED_CRON_DIALECT
```

### `VerificationReport`

Fields:

```text
Id
CreatedAt
Input
Verdict
Occurrences[]
Issues[]
Recommendation
EngineVersion
TimezoneDataFingerprint?
```

### 1. GitHub Actions semantics

**Purpose:** platform adapter cho `on.schedule`.

Confirmed behavior theo GitHub Docs:

- POSIX cron;

- có optional IANA timezone;
- minimum interval 5 phút;
- workflow chạy trên default branch;

**Authentication:** không cần để verify một snippet người dùng paste vào.

**Cost/rate limit:** không có vì MVP không gọi GitHub API.

**Privacy:** input xử lý local trong app.

**Fallback:** generic POSIX adapter nếu platform-specific metadata không có.

### 2. .NET `TimeZoneInfo`

**Purpose:** timezone calculations.

**Authentication:** không.

**Cost:** không.

**Privacy:** local computation.

**Fallback:** fail startup nếu host không có timezone support cần thiết; không dùng external timezone API chỉ để chữa deployment sai.

### 3. Quartz.NET — phase sau

Chỉ tích hợp semantics sau khi đọc official docs và viết compatibility tests. Không nên lấy cron syntax generic rồi gắn nhãn Quartz.NET nếu chưa verify số fields và behavior.

### 4. GitHub API — Later

Có thể dùng để scan `.github/workflows/*.yml`.

**Authentication:** GitHub token/OAuth/GitHub App.

**Rate limit:** phụ thuộc authentication và GitHub API policy tại thời điểm tích hợp; phải đọc docs chính thức lúc build.

**Privacy:** private repository là dữ liệu nhạy cảm; chỉ request permission tối thiểu.

**Fallback:** upload/paste YAML thủ công.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core task là bài toán deterministic:

```text
schedule + platform rules + timezone rules
→ exact occurrences
→ exact comparison
→ exact warnings
```

LLM sẽ làm hệ thống tệ hơn nếu dùng để quyết định thời gian chạy vì:

- có thể hallucinate cron semantics;
- không đảm bảo exact date arithmetic;
- khó regression test;
- tốn chi phí và latency vô ích.

### AI có thể xuất hiện sau này ở đâu?

Chỉ như optional explanation layer, ví dụ user nhập:

```text
"Chạy lúc 8:30 sáng giờ Hà Nội từ thứ 2 đến thứ 6"
```

AI có thể đề xuất structured intent:

```json
{
  "localTime": "08:30",
  "daysOfWeek": ["MON","TUE","WED","THU","FRI"],
  "timezone": "Asia/Bangkok"
}
```

Nhưng hệ thống phải:

1. validate JSON schema;
2. hiển thị intent cho user xác nhận;
3. dùng deterministic engine để generate/verify schedule;
4. không deploy AI-generated cron tự động.

MVP nên bỏ AI hoàn toàn.

## 15. Rủi ro và cách xử lý

### Rủi ro 1 — Tool đưa kết luận sai

Đây là risk lớn nhất. Một verifier sai còn nguy hiểm hơn không có verifier.

**Mitigation:**

- golden fixtures;
- official docs làm source of truth cho platform semantics;
- adapter versioning;
- fail closed khi behavior chưa verify;
- hiển thị assumptions rõ ràng.

### Rủi ro 2 — Platform thay đổi behavior

GitHub Actions hoặc scheduler khác có thể bổ sung/change features.

**Mitigation:**

- adapter có version metadata;
- lưu source URL và ngày review;
- test docs/examples định kỳ;
- không hardcode unsupported assumptions.

### Rủi ro 3 — Scope phình thành scheduler product

Dễ bị kéo sang:

- job runner;
- monitoring;
- alerting;
- distributed scheduler;
- workflow engine.

**Mitigation:**

Scope sentence:

> TimeZone Guard verifies schedule behavior; it does not execute business jobs.

### Rủi ro 4 — User nhầm prediction với guarantee

GitHub Actions scheduled workflow có thể bị ảnh hưởng bởi platform scheduling/load, nên calculated occurrence là intended schedule semantics, không phải SLA về exact execution instant.

**Mitigation:**

UI phân biệt:

```text
Scheduled occurrence
vs
Observed actual run time
```

MVP chỉ xác minh scheduled occurrence.

### Rủi ro 5 — Timezone database thay đổi

Governments có thể thay đổi timezone/DST rules.

**Mitigation:**

- report ghi engine version/runtime timezone data context;
- re-run verification trong CI;
- không xem report 3 năm trước là vĩnh viễn đúng.

### Rủi ro 6 — Public API bị abuse

**Mitigation:**

- max date range;
- max occurrences;
- request timeout;
- IP rate limit;
- không cho cron tạo hàng triệu candidate events.

### Rủi ro 7 — Adoption thấp

Có thể developer chỉ dùng cron viewer hiện có.

**Mitigation:**

MVP phải chứng minh một warning mà cron viewer thường không thể hiện: business intent mismatch across timezone/DST.

### Bước 4 — Implement vertical slice

Pseudo implementation:

```csharp
public sealed class ScheduleVerifier
{
    public IReadOnlyList<ScheduleOccurrence> GetNextOccurrences(
        ScheduleRequest request)
    {
        var timezone = TimeZoneInfo.FindSystemTimeZoneById(request.TimeZoneId);
        var expression = CronExpression.Parse(request.Cron);

        var results = new List<ScheduleOccurrence>();
        var cursor = request.Start.UtcDateTime;

        while (results.Count < request.OccurrenceCount)
        {
            var next = expression.GetNextOccurrence(cursor, TimeZoneInfo.Utc);

            if (next is null)
                break;

            var utc = new DateTimeOffset(next.Value, TimeSpan.Zero);
            var local = TimeZoneInfo.ConvertTime(utc, timezone);

            results.Add(new ScheduleOccurrence(
                utc,
                local,
                local.Offset));

            cursor = next.Value;
        }

        return results;
    }
}
```

Nếu API thực tế của cron package khác, điều chỉnh theo official package docs; mục tiêu của session là behavior, không phải copy nguyên pseudo code.
