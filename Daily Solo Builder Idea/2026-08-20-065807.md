# Ý tưởng hôm nay: CalendarMirror Guard — Calendar Event Reconciliation & Repair Tool

## 1. Tóm tắt ý tưởng

CalendarMirror Guard là một công cụ self-hosted giúp developer theo dõi các sự kiện lịch do ứng dụng của mình tạo trên Microsoft 365, phát hiện khi bản ghi trong database và event thực tế trong Outlook Calendar bị lệch, sau đó đưa ra hoặc thực hiện quy trình repair có kiểm soát. Công cụ nhắm tới các ứng dụng có logic kiểu “app tạo event cho user, sau đó app còn phải đổi giờ, hủy hoặc cập nhật event” nhưng hiện thiếu cơ chế reconciliation đáng tin cậy.

- Người dùng chính: backend developer/solo SaaS developer tích hợp Microsoft Graph Calendar.
- Bài toán chính: event trong database và event trên calendar của user có thể drift sau retry lỗi, user chỉnh tay, quyền hết hạn, missed notification hoặc sync job bị gián đoạn.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

### Confirmed facts

Microsoft Graph hỗ trợ `calendarView/delta` để lấy các event mới, bị cập nhật hoặc bị xóa trong một khoảng thời gian mà không cần đọc lại toàn bộ calendar ở mỗi lần đồng bộ. Một vòng delta sync trả `@odata.nextLink` cho các trang tiếp theo và cuối cùng trả `@odata.deltaLink` để client dùng cho vòng incremental sync kế tiếp.

Nguồn:

- https://learn.microsoft.com/en-us/graph/delta-query-events
- https://learn.microsoft.com/en-us/graph/api/event-delta?view=graph-rest-1.0

Microsoft cũng mô tả việc kết hợp change notifications với delta query: notification dùng push model để báo rằng resource đã thay đổi, còn delta query dùng pull model để lấy những thay đổi chưa xử lý. Tài liệu lifecycle notifications nêu rõ notification có thể bị missed, và khi xảy ra tình huống này ứng dụng nên resync dữ liệu, ví dụ bằng delta query.

Nguồn:

- https://learn.microsoft.com/en-us/graph/delta-query-overview
- https://learn.microsoft.com/en-us/graph/change-notifications-lifecycle-events

Microsoft Graph event hỗ trợ custom extensions, và khi tạo event có thể dùng `transactionId` để giảm khả năng tạo duplicate do retry không cần thiết.

Nguồn:

- https://learn.microsoft.com/en-us/graph/api/user-post-events?view=graph-rest-1.0
- https://learn.microsoft.com/en-us/graph/api/opentypeextension-post-opentypeextension?view=graph-rest-1.0

### Observation

Các API trên cung cấp primitives để sync, nhưng developer vẫn phải tự giải quyết một tầng quan trọng hơn:

> Khi hệ thống business coi database là source of truth nhưng Outlook Calendar thực tế đã lệch khỏi trạng thái mong muốn, chính xác event nào cần sửa và sửa như thế nào?

Đây là bài toán reconciliation, không chỉ là “gọi PATCH event”.

Ví dụ drift phổ biến:

- Database ghi meeting 14:00 nhưng calendar vẫn là 13:00 vì lần update trước fail.
- Event bị user xóa thủ công nhưng app vẫn coi là active.
- App retry create và sinh duplicate event.
- Subscription change notification hết hạn hoặc bị missed.
- Token/quyền user tạm thời không hợp lệ nên update không hoàn tất.
- Recurring event có exception khiến so sánh đơn giản theo `eventId` không đủ.
- App bị restart giữa lúc update DB và gọi Microsoft Graph.

### Assumption cần kiểm chứng

Developer có integration calendar thường tự viết từng sync job riêng, nhưng thiếu một lớp reusable có thể:

1. lưu expected state;
2. đọc actual state;
3. diff;
4. phân loại drift;
5. repair idempotently;
6. lưu audit trail.

MVP có thể kiểm chứng assumption này ngay trên một ứng dụng cá nhân dùng Microsoft Graph mà không cần người dùng bên ngoài.

## 3. Người dùng mục tiêu

**Primary user:** backend developer xây ứng dụng có chức năng tạo hoặc cập nhật Outlook Calendar event cho user thông qua Microsoft Graph delegated permissions.

### User profile

- Làm backend/API integration.
- Có database lưu business event, booking, appointment hoặc training session.
- Mỗi business record có event tương ứng trên Outlook Calendar.
- Không muốn xin application-wide calendar permission nếu use case có thể hoạt động bằng delegated access.

### Context of use

Một ứng dụng scheduling tạo event vào calendar của user. Sau đó admin thay đổi thời gian, location hoặc hủy lịch. Hệ thống cần đảm bảo calendar của user phản ánh đúng trạng thái business hiện tại.

### Main pain point

“API update đã chạy chưa?” không đồng nghĩa với “calendar hiện đang đúng”. Khi có lỗi giữa chừng, rất khó biết record nào đang drift.

### Current workaround

- Lưu `GraphEventId` trong DB.
- Gọi Graph PATCH khi business record thay đổi.
- Retry nếu API lỗi.
- Kiểm tra thủ công khi user báo lịch sai.
- Đôi khi set cờ `NeedToUpdate` và chờ user login lại.

### Vì sao họ sẽ thử tool này

Tool biến một integration dễ tạo lỗi âm thầm thành workflow có trạng thái rõ:

```text
Expected → Actual → Drift → Repair → Verified
```

## 4. Giải pháp đề xuất

CalendarMirror Guard giữ một **desired snapshot** cho mỗi calendar event mà ứng dụng quản lý và định kỳ hoặc theo trigger đọc **actual snapshot** từ Microsoft Graph.

### Main workflow

1. App đăng ký một managed event với CalendarMirror Guard.
2. Tool lưu business key, user, calendar/event identifiers và desired fields.
3. Sync worker gọi Graph delta query hoặc `GET event` để lấy actual state.
4. Diff engine so sánh các field được quản lý.
5. Nếu giống nhau → trạng thái `InSync`.
6. Nếu lệch → tạo `DriftCase`.
7. Rule engine phân loại:
   - time drift;
   - event deleted;
   - duplicate;
   - attendee drift;
   - location drift;
   - Graph object inaccessible;
   - uncertain conflict.
8. User xem proposed repair.
9. Repair worker PATCH/create/delete theo policy.
10. Tool đọc lại event và xác nhận trạng thái `Verified`.

### Input

Một managed event có thể được đăng ký bằng API:

```json
{
  "externalKey": "training-session-8124:user-42",
  "userId": "user-42",
  "graphEventId": "...",
  "desired": {
    "subject": "Technical Training",
    "start": "2026-08-25T14:00:00+07:00",
    "end": "2026-08-25T15:00:00+07:00",
    "location": "Meeting Room A",
    "isCancelled": false
  }
}
```

### Processing

Deterministic diff chỉ so sánh những property mà application sở hữu. Ví dụ app có thể quản lý `start`, `end`, `subject`, `location`, nhưng không ghi đè `body` nếu user tự thêm note.

### Output

```text
Managed Event: training-session-8124:user-42
Status: Drifted
Difference:
- start expected 14:00, actual 13:00
- end expected 15:00, actual 14:00
Recommended action: PATCH start/end
Confidence: deterministic
```

### What is automated

- Incremental Graph sync.
- Snapshot normalization.
- Drift detection.
- Retry/backoff.
- Repair execution cho case an toàn.
- Verification sau repair.
- Audit log.

### What remains under user control

- Field nào được app quản lý.
- Có cho auto-repair hay không.
- Có recreate event bị user xóa hay không.
- Environment/tenant nào được phép thay đổi.
- Conflict policy.

### Key differentiator

Đây không phải calendar app và cũng không phải generic two-way sync. Nó là **reconciliation engine cho calendar integrations do application quản lý**, tương tự cách infrastructure controller liên tục so desired state với actual state.

### Ví dụ end-to-end

Admin đổi training session từ 13:00 sang 14:00.

```text
Business DB updated
→ CalendarMirror receives desired-state revision 18
→ existing Graph PATCH fails due to transient error
→ reconciliation worker later reads calendar
→ detects actual start=13:00, desired start=14:00
→ creates TimeDrift case
→ repair policy permits start/end updates
→ PATCH event
→ GET event again
→ verifies 14:00
→ marks case Resolved
```

Người dùng không cần đăng nhập lại chỉ để hệ thống nhớ rằng có update chưa hoàn tất; nếu delegated token vẫn usable theo architecture của host app, reconciliation có thể tiếp tục theo policy.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Calendar integration có kiểu failure rất khó chịu: request ban đầu có thể “gần như thành công”, nhưng một subset user vẫn có calendar sai. Reconciliation giúp phát hiện sai lệch bằng state thực tế thay vì tin vào trạng thái job.

### Technical learning value

Project chạm vào nhiều bài toán Senior/Architect thực tế:

- distributed consistency;
- idempotency;
- delta synchronization;
- conflict resolution;
- retry/recovery;
- OAuth delegated permissions;
- webhook/change notification lifecycle;
- state machine;
- observability.

### Vì sao phù hợp solo developer

Core MVP chỉ cần một provider là Microsoft Graph và một resource là calendar event. Không cần microservices, Kafka hay enterprise infrastructure.

### Có ích ngay cả khi chỉ có một người dùng

Developer có thể gắn tool vào chính project calendar integration đang làm và dùng nó như operational dashboard để tìm sync drift.

### Điều gì làm ý tưởng thất bại

- Không định nghĩa rõ source of truth.
- So sánh quá nhiều field do user sở hữu và gây overwrite ngoài ý muốn.
- Token/permission model của host application không cho phép background reconciliation hợp lý.
- Recurrence scope được đưa vào MVP quá sớm.

### Lý do mạnh nhất để không build

Nếu ứng dụng chỉ tạo event một lần và không bao giờ cần update/hủy/sync lại, một reconciliation layer riêng có thể là overkill.

## 7. Luồng hoạt động

### Register flow

Application
→ POST desired event state
→ validate required fields
→ normalize time zone
→ persist `ManagedEvent`
→ optional initial Graph fetch
→ mark `PendingReconciliation`.

### Reconciliation flow

Scheduler/manual trigger
→ load managed event
→ obtain Graph access context
→ fetch actual event
→ normalize actual snapshot
→ compare desired/actual
→ store reconciliation run
→ return `InSync` hoặc create `DriftCase`.

### Repair flow

User selects drift
→ policy validation
→ compare latest desired revision
→ fetch current actual event again
→ ensure no newer conflicting state
→ PATCH Graph
→ fetch event again
→ verify fields
→ mark resolved.

### Event deleted

Graph returns not found / delta reports deletion
→ create `MissingRemoteEvent` drift
→ policy decides:

```text
Ignore
or
Recreate
or
Require manual approval
```

MVP mặc định **manual approval**.

### Token expired / permission unavailable

Graph request fails auth
→ classify `AccessUnavailable`
→ do not retry aggressively
→ preserve drift state
→ wait for host app to refresh/re-authorize according to its OAuth flow.

### Graph throttling

`429`
→ honor `Retry-After`
→ reschedule reconciliation
→ do not mark event as incorrect.

### App restart giữa repair

Repair operation có deterministic operation key:

```text
managedEventId + desiredRevision + repairType
```

Worker restart
→ lookup existing attempt
→ read actual state
→ if desired state already achieved, mark success without PATCH lần nữa.

## 11. API và tích hợp

### Microsoft Graph Calendar API

**Purpose:** đọc, tạo và cập nhật Outlook calendar event.

**Authentication:** OAuth 2.0 thông qua Microsoft identity platform.

**Permissions:** chọn least privilege theo use case. Tài liệu `event: delta` liệt kê `Calendars.Read` là least privileged read permission cho delta query; mutation sẽ cần quyền write phù hợp.

Nguồn:

- https://learn.microsoft.com/en-us/graph/api/event-delta?view=graph-rest-1.0

**Cost/rate limit concern:** Graph có throttling; client phải handle `429` và retry theo hướng dẫn response.

**Privacy:** calendar chứa title, attendee, location và potentially sensitive business information. Chỉ lưu field cần thiết.

**Fallback:** nếu Graph tạm unavailable, giữ desired state và retry/reconcile sau. Không dùng browser automation làm fallback.

### Microsoft Graph delta query

**Purpose:** lấy incremental changes thay vì repeatedly fetch toàn bộ calendar window.

**Authentication:** cùng Graph connection.

**Concern:** calendarView delta gắn với calendar + date range và token/link phải được lưu đúng.

**Fallback:** full reconcile một bounded date range khi delta state bị mất hoặc invalid.

### Microsoft Graph change notifications

**Purpose:** trigger reconciliation gần real-time.

**Authentication/permission:** tùy resource subscription.

**Concern:** subscription có lifecycle và notifications có thể bị missed; do đó đây không được là source of truth duy nhất.

**Fallback:** scheduled delta/full reconciliation.

### Open extensions

**Purpose:** optional correlation metadata trên event, ví dụ managed record ID.

**Authentication:** calendar write permission phù hợp.

**Privacy:** không lưu secret trong extension.

**Fallback:** giữ mapping trong DB bằng `GraphEventId` + business external key.

### `transactionId`

**Purpose:** giảm duplicate event khi retry create request.

**Fallback:** application-level idempotency + post-create reconciliation.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem là consistency và deterministic state comparison. AI không nên quyết định event nào cần overwrite.

Các operation cần chính xác tuyệt đối:

```text
ExpectedStart != ActualStart
ExpectedEnd != ActualEnd
ExpectedLocation != ActualLocation
```

đều giải quyết tốt hơn bằng code thường.

AI chỉ có thể là optional future feature để tóm tắt incident history cho developer, nhưng không nằm trong repair path.

**Expected output:** thay đổi Outlook được phát hiện incremental.

**Completion criteria:** sửa/xóa event trực tiếp trong Outlook xuất hiện thành drift case mà không cần manual reconcile.

**Goal:** chạy ổn định self-hosted.

**Main tasks:**

- CI/CD;
- DB backup;
- telemetry;

**Expected output:** một instance có thể vận hành nhiều ngày không cần can thiệp thủ công.

## 14. Các bài toán kỹ thuật đáng học

### 1. Desired-state reconciliation

Bạn phải tách rõ:

```text
Business state
Desired calendar state
Actual calendar state
```

và tránh đồng nhất ba thứ này.

**Skill cải thiện:** distributed systems thinking, controller/reconciliation pattern.

### 2. Idempotent repair

PATCH/create có thể timeout sau khi server đã xử lý request. Retry mù có thể gây duplicate hoặc mutation lặp.

**Skill cải thiện:** idempotency, operation keys, verify-before-retry.

### 3. Delta synchronization

Graph delta flow có paging, opaque state token và reset/resync scenarios.

**Skill cải thiện:** incremental sync, cursor persistence, failure recovery.

### 4. Conflict resolution

Không phải mọi field trên event đều thuộc sở hữu application.

Ví dụ user thêm note vào body không nên bị tool overwrite chỉ vì desired snapshot cũ không chứa note đó.

**Skill cải thiện:** ownership boundaries, merge policy, conflict classification.

### 5. OAuth lifecycle và least privilege

Background sync phụ thuộc auth context, permission type và token lifecycle.

**Skill cải thiện:** delegated/application permission trade-offs, reauthorization, least privilege.

## 15. Rủi ro và cách xử lý

### Scope expansion

**Risk:** biến thành full calendar synchronization engine.

**Mitigation:** MVP chỉ quản lý event do host application đăng ký.

### Overwrite user changes

**Risk:** app repair ghi đè note/location user cố tình sửa.

**Mitigation:** field ownership policy rõ ràng; default manual approval; không quản lý `body` ở MVP.

### Permission/privacy

**Risk:** calendar permission rất nhạy cảm.

**Mitigation:** least privilege, single test account trước, không lưu access token plaintext, redact event body/log.

### Event ID/mapping failure

**Risk:** mapping bị mất hoặc event bị recreate.

**Mitigation:** external business key + optional extension + reconciliation flow cho missing event.

### Recurring events

**Risk:** recurring master, occurrence và exception làm logic phức tạp mạnh.

**Mitigation:** explicitly exclude recurring events khỏi MVP hoặc chỉ mark `UnsupportedRecurringEvent`.

### Missed notifications

**Risk:** push notification không đến.

**Mitigation:** notification chỉ là trigger; delta/scheduled reconciliation vẫn là safety net.

### Throttling

**Risk:** nhiều user/calendar làm Graph requests tăng nhanh.

**Mitigation:** delta query, bounded windows, backoff, `Retry-After`, batching workload theo user.

### Time zone bugs

**Risk:** DST/time zone conversion tạo false drift.

**Mitigation:** lưu UTC instant + original time-zone identifier; normalize trước compare; có dedicated test matrix.

### Adoption

**Risk:** niche developer tool.

**Mitigation:** coi personal utility + reusable library/portfolio project là giá trị chính trước monetization.

### 5 test scenario quan trọng nhất

1. **Time drift:** DB 14:00, Outlook 13:00 → detect → PATCH → verify 14:00.
2. **Remote delete:** Outlook event bị xóa → `MissingRemoteEvent`, không tự recreate nếu chưa approved.
3. **Timeout after successful PATCH:** retry worker đọc actual state, thấy đã đúng và không PATCH lần hai.
4. **429 throttling:** worker honor retry delay và không đánh dấu drift thành failure business.
5. **User-owned field changed:** user sửa body, app chỉ quản lý start/end → event vẫn `InSync` nếu managed fields đúng.

- % worker restart không làm duplicate operation;
- delta cursor recovery rate;

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, tạo một console prototype có thể:

```text
Load desired event JSON
→ GET actual event qua Microsoft Graph
→ normalize
→ diff start/end/subject/location
→ in kết quả ra terminal
```

Chưa làm database, dashboard, delta query hoặc auto repair.

### Files/components cần tạo


### Setup commands

### Sample desired file

```json
{
  "graphEventId": "EVENT_ID_FROM_DEV_CALENDAR",
  "subject": "Calendar Mirror Test",
  "start": "2026-08-25T14:00:00+07:00",
  "end": "2026-08-25T15:00:00+07:00",
  "location": "Room A"
}
```

### First vertical slice

Implement:

```csharp
public sealed record EventDifference(
    string Field,
    string? Expected,
    string? Actual);
```

và:

```csharp
IReadOnlyList<EventDifference> Compare(
    DesiredEvent desired,
    ActualEvent actual);
```

Chỉ compare 4 field:

```text
Subject
Start
End
Location
```

Normalize start/end về UTC trước khi compare.

### Expected terminal result

Event đúng:

```text
Event: Calendar Mirror Test
Status: IN SYNC
Differences: 0
```

Sau khi tự chỉnh Outlook từ 14:00 thành 13:30:

```text
Event: Calendar Mirror Test
Status: DRIFTED
Differences: 2

Start
Expected: 2026-08-25T07:00:00Z
Actual:   2026-08-25T06:30:00Z

End
Expected: 2026-08-25T08:00:00Z
Actual:   2026-08-25T07:30:00Z
```

### Verification checklist

- [ ] Có một test event thật trong dev Outlook calendar.
- [ ] CLI đọc được event bằng Microsoft Graph.
- [ ] Event đúng trả `IN SYNC`.
- [ ] Chỉnh giờ event trực tiếp trong Outlook tạo `DRIFTED`.
- [ ] Start/end được compare theo instant thay vì raw display string.
- [ ] Thay đổi field không được quản lý không ảnh hưởng kết quả.
- [ ] Có ít nhất 3 unit tests cho diff engine.
- [ ] Không log access token.

### Stop condition

Kết thúc coding session ngay khi bạn có thể thực hiện chuỗi sau:

```text
1. Run CLI → IN SYNC
2. Edit event time manually in Outlook
3. Run CLI again → DRIFTED với expected/actual chính xác
```

Không làm repair, scheduler, webhook hoặc UI trong session đầu tiên. Vertical slice này đủ để chứng minh core value proposition: **application có thể phát hiện calendar state thực tế đã lệch khỏi desired business state**.
