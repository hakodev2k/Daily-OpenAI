# Ý tưởng hôm nay: Graph Subscription Sentinel

## 1. Tóm tắt ý tưởng

**Graph Subscription Sentinel** là một công cụ self-hosted giúp developer theo dõi, gia hạn và tự phục hồi các **Microsoft Graph change-notification subscriptions** trước khi chúng hết hạn hoặc bị mất thông báo. Công cụ đặc biệt hữu ích cho các hệ thống dùng Outlook mail/calendar, Teams hoặc Microsoft 365 webhook nhưng không muốn tự xây lại toàn bộ logic renewal, lifecycle handling, retry và delta-recovery trong từng project.

- Người dùng chính: .NET backend developer hoặc solo builder tích hợp Microsoft Graph.
- Vấn đề chính: subscription có vòng đời hữu hạn, có thể cần reauthorization, có thể bị remove hoặc miss notification; nếu không phát hiện kịp, ứng dụng âm thầm ngừng đồng bộ.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Microsoft Graph change notifications sử dụng mô hình subscription: ứng dụng tạo subscription tới một resource và Graph gửi webhook khi resource thay đổi. Subscription không tồn tại vĩnh viễn; ứng dụng cần theo dõi `expirationDateTime` và gia hạn định kỳ. Microsoft cũng có lifecycle notifications như `reauthorizationRequired`, `subscriptionRemoved` và `missed` để cảnh báo khi luồng notification gặp rủi ro.

**Confirmed facts:**

- Microsoft Graph yêu cầu webhook endpoint public qua HTTPS, thực hiện validation khi tạo subscription và ứng dụng phải renew subscription để tiếp tục nhận notification. Microsoft khuyến nghị phản hồi notification nhanh; tài liệu hiện tại nêu Graph xem notification là delivered khi endpoint trả 2xx trong vòng 3 giây và có retry cho một số failure.  
  Nguồn: https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks

- Microsoft Graph có lifecycle notifications cho các tình huống như `reauthorizationRequired`, `subscriptionRemoved` và `missed`; nếu không xử lý, change-notification flow có thể bị gián đoạn.  
  Nguồn: https://learn.microsoft.com/en-us/graph/change-notifications-lifecycle-events

- Delta query cho phép ứng dụng lấy các entity đã tạo, cập nhật hoặc xóa kể từ lần đồng bộ trước thay vì đọc lại toàn bộ resource. Microsoft mô tả delta query là pull model và change notifications là push model; hai cơ chế có thể kết hợp để xây đồng bộ tin cậy hơn.  
  Nguồn: https://learn.microsoft.com/en-us/graph/delta-query-overview

**Observation:** code để tạo subscription khá ngắn, nhưng vận hành production lại gồm nhiều concern tách biệt: secret validation, expiration tracking, renewal, retry, lifecycle events, duplicate notification, recovery khi missed events và monitoring.

**Assumption cần kiểm chứng:** team nhỏ hoặc developer cá nhân có nhiều Graph integrations sẽ thích tách phần “subscription reliability” khỏi business logic để tránh mỗi project tự viết một phiên bản khác nhau.

Hiện nay cách xử lý thường là:

- Tạo Hangfire/Azure Function riêng để renew subscription.
- Lưu expiration trong DB hoặc config.
- Gửi alert khi renewal job fail.
- Viết lifecycle endpoint riêng.
- Khi nghi ngờ mất dữ liệu thì chạy full sync hoặc delta query thủ công.

Các mảnh này không khó riêng lẻ, nhưng dễ bị quên, đặc biệt khi project chỉ có một vài subscription và lỗi chỉ xuất hiện sau nhiều ngày hoặc sau khi permission/token thay đổi.

## 3. Người dùng mục tiêu

**Primary user:** .NET backend developer làm các ứng dụng Microsoft 365 integration cho internal tools, SaaS nhỏ hoặc automation service.

### User profile

- Biết C#, ASP.NET Core và Microsoft Graph.
- Có từ một đến vài chục subscriptions.
- Không muốn vận hành enterprise event platform.

### Context of use

Ví dụ:

- Đồng bộ Outlook calendar vào database.
- Theo dõi mailbox để trigger workflow.
- Theo dõi Microsoft 365 resource changes.
- Đồng bộ contact hoặc event cho background service.

### Main pain point

Ứng dụng đang chạy bình thường nhưng subscription hết hạn hoặc bị removed, và developer chỉ phát hiện khi người dùng báo dữ liệu không còn cập nhật.

### Current workaround

Cron/Hangfire job tự renew + log + alert thủ công.

### Lý do họ thử giải pháp này

Một dashboard nhỏ cho biết rõ:

- Subscription nào khỏe.
- Subscription nào sắp hết hạn.
- Renewal lần cuối thành công hay thất bại.
- Lifecycle notification nào vừa xảy ra.
- Resource nào có dấu hiệu missing events.
- Có cần chạy delta recovery hay không.

## 4. Giải pháp đề xuất

Graph Subscription Sentinel đứng giữa **Graph subscription lifecycle** và application business logic.

### Main workflow

1. Developer đăng ký một Graph tenant/app vào Sentinel.
2. Sentinel tạo hoặc import subscription metadata.
3. Scheduler tính thời điểm renew an toàn trước expiration.
4. Background worker renew subscription.
5. Lifecycle endpoint nhận notification từ Graph.
6. Sentinel cập nhật health state.
7. Nếu nhận `missed` hoặc subscription bị mất:
   - đánh dấu resource `NeedsRecovery`;
   - chạy delta recovery nếu resource hỗ trợ và user bật chế độ này;
   - hoặc tạo action item rõ ràng cho developer.
8. Dashboard hiển thị health và lịch sử.

### Input

- Tenant/app credentials hoặc access-token provider.
- Resource URI Graph cần subscribe.
- Change types.
- Notification URL.
- Lifecycle notification URL.
- Renewal policy.
- Optional delta recovery configuration.

### Processing

- Create/renew/list/delete Graph subscription.
- Track `expirationDateTime`.
- Validate `clientState`.
- Store lifecycle events.
- Retry renewal theo policy.
- Deduplicate notification bằng delivery/resource metadata phù hợp.
- Trigger recovery workflow khi cần.

### Output

- Subscription health dashboard.
- Renewal history.
- Lifecycle alert.
- Recovery status.
- Structured logs.
- Optional Telegram/Teams/email notification sau MVP.

### User control

User quyết định:

- Subscription nào được Sentinel quản lý.
- Có auto-renew hay chỉ cảnh báo.
- Có auto-recreate khi subscription bị removed hay không.
- Có chạy delta recovery tự động hay chỉ tạo warning.
- Target resources và Graph permissions.

### Key differentiator

Không phải generic webhook monitor. Nó tập trung vào **Microsoft Graph subscription reliability**: expiration + lifecycle + reauthorization + delta-recovery trong một workflow thống nhất.

### Ví dụ cụ thể

Một app đang subscribe vào Outlook event changes.

- Subscription sẽ hết hạn trong vài giờ.
- Sentinel renew trước thời điểm đó.
- Renewal lần đầu bị `401` do token issue.
- Job retry sau khi token provider refresh credential.
- Nếu Graph gửi `reauthorizationRequired`, Sentinel đánh dấu subscription `AttentionRequired` và chạy reauthorize flow được cấu hình.
- Nếu nhận lifecycle event báo missed notifications, Sentinel chạy calendar delta query từ `deltaLink` gần nhất để lấy các thay đổi bị bỏ lỡ.
- App business không cần tự biết chi tiết toàn bộ lifecycle này.

## 7. Luồng hoạt động

### Create/import flow

User tạo subscription config
→ validate resource/change types
→ validate credentials
→ gọi Graph `/subscriptions`
→ lưu subscription ID + expiration
→ schedule renewal
→ hiển thị `Healthy`.

### Renewal flow

Scheduler tìm subscription đến renewal window
→ acquire token
→ PATCH subscription expiration
→ nếu success: lưu expiration mới + operation history
→ nếu transient failure: retry
→ nếu auth failure: chuyển `AttentionRequired`
→ gửi alert nếu vượt retry policy.

### Lifecycle flow

Graph gửi lifecycle POST
→ validate `clientState`/payload
→ persist lifecycle event
→ map event tới subscription
→ update health state
→ enqueue recovery action nếu policy cho phép
→ response nhanh cho Graph.

### Recovery flow

`missed` event
→ lấy stored delta checkpoint
→ gọi delta query
→ follow `@odata.nextLink` cho tới `@odata.deltaLink`
→ publish recovered changes cho handler/internal callback
→ update checkpoint
→ mark recovery complete.

### Failure cases quan trọng

- Subscription ID không còn tồn tại → manual/auto recreate.
- Secret sai → reject notification.
- Token acquisition fail → retry + alert.
- Delta token không còn usable → fallback full re-sync policy.
- Process restart giữa renewal → idempotent job state.
- Hai worker renew cùng subscription → distributed/database lock.

## 9. Công nghệ đề xuất

### .NET 10 + ASP.NET Core

Phù hợp với webhook endpoint, background processing, Graph SDK/HTTP client và dependency injection.

**Simpler alternative:** Minimal API + một HostedService.

**Outgrow point:** chỉ tách worker riêng khi có nhiều tenant/subscription và job throughput tăng rõ rệt.

### EF Core + PostgreSQL

Tốt cho subscription state, operation history và locks.

**Simpler alternative:** SQLite cho local single-user prototype.

**Outgrow point:** không cần đổi DB sớm; PostgreSQL đủ cho quy mô rất lớn so với MVP.

### Hangfire

Phù hợp cho persisted scheduled job, retry và manual trigger.

**Simpler alternative:** `BackgroundService` + periodic timer.

**Outgrow point:** nếu cần hàng chục nghìn job đa vùng, chuyển sang queue/broker riêng.

### Vue 3 + Vite

Dashboard nhỏ, nhanh phát triển.

**Simpler alternative:** Razor Pages nếu muốn giảm frontend complexity.

### Microsoft Graph SDK hoặc typed `HttpClient`

SDK giúp model/API request thuận tiện. Typed HTTP client cho phép kiểm soát endpoint và retry rõ ràng hơn. MVP có thể dùng SDK cho auth/request và bọc nó sau interface `IGraphSubscriptionClient`.

### Docker

Dễ self-host.

### Playwright

Dùng cho E2E dashboard và manual renewal/recreate flows.

### GitHub Actions

Build, test và publish Docker image.

## 11. API và tích hợp

### Microsoft Graph `/subscriptions`

**Purpose:** create, renew, inspect và delete subscription.

**Authentication:** OAuth2 access token với permission phù hợp resource.

**Cost/rate limit:** Graph có throttling; renewal cần retry theo `Retry-After` khi gặp throttling thay vì spam request.

**Privacy/permission concern:** Sentinel phải giữ credential hoặc tích hợp credential provider, nên áp dụng least privilege và secret storage an toàn.

**Fallback:** nếu Graph API tạm unavailable, giữ trạng thái và retry trước expiration; nếu không còn đủ thời gian thì alert.

Nguồn tổng quan change notifications:  
https://learn.microsoft.com/en-us/graph/change-notifications-overview

### Microsoft Graph lifecycle notification endpoint

**Purpose:** biết subscription/resource đang cần reauthorization, bị removed hoặc có missed notification.

**Authentication/validation:** validate payload/client state theo subscription configuration.

**Fallback:** periodic reconciliation job có thể list local subscriptions và so sánh health khi lifecycle notification không tới.

Nguồn:  
https://learn.microsoft.com/en-us/graph/change-notifications-lifecycle-events

### Microsoft Graph delta query

**Purpose:** recovery dữ liệu sau missed notification.

**Authentication:** cùng Graph permission phù hợp resource.

**Rate concern:** follow paging; không poll quá thường xuyên.

**Fallback:** nếu delta state không usable, chuyển subscription sang `FullResyncRequired` thay vì âm thầm bỏ qua.

Nguồn:  
https://learn.microsoft.com/en-us/graph/delta-query-overview

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Tất cả core operations đều deterministic:

- expiration calculation;
- renewal scheduling;
- lifecycle mapping;
- retry;
- delta pagination;
- health state transition.

AI không giúp tăng reliability và thậm chí làm hệ thống khó kiểm chứng hơn.

Nếu muốn mở rộng sau này, AI có thể optional để giải thích incident log bằng ngôn ngữ tự nhiên, nhưng không được quyết định renewal/recovery action.

## 14. Các bài toán kỹ thuật đáng học

### 1. Reliable background processing

Renew subscription đúng lúc nhưng không renew quá nhiều. Học durable scheduling, retry, timeout và job persistence.

### 2. Distributed/idempotent renewal

Hai worker không được PATCH cùng subscription vô kiểm soát. Học locking, idempotency và state transitions.

### 3. OAuth và permission boundaries

Học token lifecycle, least privilege, tenant isolation và safe secret handling.

### 4. Delta synchronization

Học incremental synchronization, paging, checkpoint và recovery sau missed events.

### 5. Webhook lifecycle design

Học cách phản hồi webhook nhanh, xử lý async và tách delivery acknowledgement khỏi business processing.

## 15. Rủi ro và cách xử lý

### Authentication complexity

**Risk:** nhiều auth mode/tenant làm MVP nặng.

**Mitigation:** chỉ hỗ trợ một tenant + client-credentials provider đầu tiên.

### Permission exposure

**Risk:** tool giữ credential có Graph permissions quan trọng.

**Mitigation:** least privilege, secret store, không log token, optional external credential provider.

### Auto-recovery gây sai dữ liệu

**Risk:** delta adapter bug có thể duplicate hoặc bỏ sót record.

**Mitigation:** immutable recovery operation log, idempotent consumer key, dry-run/manual approval trước khi bật automatic mode.

### API dependency

**Risk:** Graph outage/throttling lúc gần expiration.

**Mitigation:** renew sớm, retry with jitter, respect `Retry-After`, alert khi remaining lifetime xuống ngưỡng nguy hiểm.

### Scope creep

**Risk:** biến thành generic Microsoft 365 integration platform.

**Mitigation:** MVP chỉ quản lý subscription reliability và một delta adapter.

### User adoption

**Risk:** pain chưa đủ lớn cho team nhỏ.

**Mitigation:** bắt đầu như library/self-hosted tool dùng cho chính project trước; chỉ productize nếu usage lặp lại.

## 16. Kiểm thử

### Testing strategy

- Unit test cho renewal-time calculation và state transitions.
- Integration test với PostgreSQL/Hangfire.
- HTTP contract test cho Graph client bằng mock server.
- E2E test dashboard với Playwright.
- Failure-path test cho 401/404/429/5xx.
- Security test cho client-state validation và secret leakage.

### 5 scenario quan trọng nhất

1. Subscription còn 60 phút → scheduler enqueue đúng một renewal job.
2. Graph trả `429` + `Retry-After` → job retry đúng thời gian, không spam.
3. Nhận `subscriptionRemoved` → status chuyển `RecoveryRequired`/`AttentionRequired`, không giả vờ healthy.
4. Duplicate lifecycle payload → không tạo hai recovery workflow.
5. `missed` event → delta recovery lấy đủ create/update/delete changes và cập nhật checkpoint chỉ sau khi xử lý hoàn tất.

### Error rate

- Renewal failure rate.
- Duplicate recovery rate.
- Unhandled lifecycle-event rate.

### Repeated use

Tool có giá trị nếu vẫn đang quản lý subscription sau 30–60 ngày, không phải chỉ chạy demo một lần.

### Reliability metric

Mục tiêu cá nhân có thể đặt:

- 100% managed subscriptions được renew trước expiration trong test/production nhỏ.
- Không có subscription âm thầm expired mà dashboard vẫn báo healthy.

Không cần AI quality metric vì AI không dùng.

### First vertical slice

Tạo entity:

```csharp
public sealed class ManagedSubscription
{
    public Guid Id { get; init; }
    public string GraphSubscriptionId { get; init; } = "";
    public string Resource { get; init; } = "";
    public DateTimeOffset ExpirationDateTimeUtc { get; set; }
    public DateTimeOffset? LastRenewedAtUtc { get; set; }
    public SubscriptionStatus Status { get; set; }
}
```

Policy đầu tiên:

```text
NeedsRenewal = ExpirationDateTimeUtc <= UtcNow + 60 minutes
```

Tạo `FakeGraphSubscriptionClient`:

```text
RenewAsync(subscription)
→ trả expiration = UtcNow + 24 hours
```

Tạo endpoint debug:

```text
POST /dev/subscriptions/seed
POST /dev/renewals/run
GET  /dev/subscriptions
```

### Expected result

Seed subscription hết hạn sau 30 phút.

Trước renewal:

```json
{
  "status": "Healthy",
  "expiresInMinutes": 30
}
```

Run renewal.

Sau renewal:

```json
{
  "status": "Healthy",
  "expiresInMinutes": 1440,
  "lastRenewedAtUtc": "..."
}
```

### Verification checklist

- [ ] Subscription còn 30 phút được chọn để renew.
- [ ] Subscription còn 6 giờ không được renew.
- [ ] Mỗi subscription chỉ renew một lần trong một run.
- [ ] Fake client exception làm status chuyển `AttentionRequired` hoặc ghi failure rõ ràng.
- [ ] Có unit test cho boundary đúng 60 phút.
- [ ] Có integration test cho `POST /dev/renewals/run`.

### Stop condition

Kết thúc session khi command/test chứng minh được workflow:

```text
seed expiring subscription
→ renewal scan
→ fake Graph PATCH
→ expiration được cập nhật
→ test pass
```

Không làm OAuth, database thật, Vue, Hangfire hoặc delta recovery trong session đầu tiên. Vertical slice này đủ để chứng minh core domain của dự án trước khi thêm infrastructure.
