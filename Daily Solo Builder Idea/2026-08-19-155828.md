# Ý tưởng hôm nay: ConfigSentinel — Configuration Drift & Sensitive Reference Auditor

## 1. Tóm tắt ý tưởng

ConfigSentinel là một công cụ self-hosted giúp developer so sánh cấu hình giữa local, development, staging và production mà không cần lưu các giá trị nhạy cảm thực tế. Công cụ phát hiện key bị thiếu, key thừa, sai kiểu dữ liệu, feature flag lệch môi trường và reference tới kho cấu hình nhạy cảm không còn hợp lệ trước khi deploy.

- Người dùng chính: backend developer hoặc solo SaaS developer vận hành nhiều môi trường.
- Bài toán chính: configuration drift khiến deployment chạy ở môi trường này nhưng lỗi ở môi trường khác.
- Quy mô: **Medium**.
- Thời gian MVP: **2–3 tuần**.

## 2. Bài toán thực tế

Một ứng dụng thực tế thường có configuration phân tán ở nhiều nơi:

- `appsettings.json`
- `appsettings.Development.json`
- environment variables
- Docker Compose
- Azure App Service settings
- Azure App Configuration
- Azure Key Vault references
- GitHub Actions variables

Cùng một application nhưng staging có thể thiếu một key, production còn giữ key cũ hoặc một reference tới external configuration không còn truy cập được.

### Confirmed facts

Microsoft mô tả Azure App Configuration là dịch vụ dùng để centralize application settings và feature settings. App Configuration cũng hỗ trợ snapshot bất biến của một tập key-value để triển khai cấu hình an toàn hơn.

Nguồn:

- https://learn.microsoft.com/en-us/azure/azure-app-configuration/
- https://learn.microsoft.com/en-us/azure/azure-app-configuration/concept-snapshots

Microsoft cũng hỗ trợ Key Vault reference từ Azure App Configuration. Giá trị lưu trong App Configuration là URI tham chiếu tới Key Vault thay vì nội dung nhạy cảm thực tế; application phải có quyền truy cập các dịch vụ liên quan.

Nguồn:

- https://learn.microsoft.com/en-us/azure/azure-app-configuration/use-key-vault-references-dotnet-core
- https://learn.microsoft.com/en-us/azure/app-service/app-service-key-vault-references

### Observation

Các nền tảng cung cấp nơi lưu configuration tốt, nhưng việc so sánh “configuration contract” giữa nhiều môi trường thường vẫn do developer tự kiểm tra bằng portal, CLI hoặc script riêng.

### Assumption cần kiểm chứng

Một developer có từ 2–4 môi trường sẽ tiết kiệm thời gian nếu có tool trả về báo cáo kiểu:

```text
Production missing: Payments:WebhookCredentialRef
Staging extra: FeatureFlags:OldCheckout
Production type mismatch: Cache:TtlSeconds
Reference unavailable: Database:CredentialRef
```

## 3. Người dùng mục tiêu

Primary user là backend developer hoặc solo developer vận hành một ASP.NET Core application có nhiều environment.

Context sử dụng phổ biến:

```text
local → dev → staging → production
```

Pain point chính là không có một contract rõ ràng để biết môi trường nào đang thiếu, dư hoặc sai cấu hình.

Workaround hiện tại gồm mở portal để so sánh thủ công, export config rồi diff, grep environment variables hoặc chỉ phát hiện khi runtime lỗi.

Lý do thử ConfigSentinel: một command có thể trả lời nhanh “production configuration có đáp ứng contract của application hay không?”.

## 4. Giải pháp đề xuất

ConfigSentinel coi configuration như một **contract**.

Ví dụ schema:

```yaml
Database:
  CredentialRef:
    required: true
    sensitive: true

Cache:
  TtlSeconds:
    type: integer
    min: 1

FeatureFlags:
  NewCheckout:
    type: boolean
```

Sau đó cấu hình source:

```text
local.json
staging.env
Azure App Configuration: staging
Azure App Configuration: production
```

Workflow:

```text
collect metadata
→ normalize key names
→ redact sensitive values
→ validate schema
→ compare environments
→ classify drift
→ generate report
```

Output ví dụ:

```text
Environment: production

ERROR   Payments:WebhookCredentialRef  Missing required key
ERROR   Cache:TtlSeconds               Expected integer
WARN    FeatureFlags:OldCheckout       Unknown key
WARN    Search:Endpoint                Different from staging
OK      Database:CredentialRef         External reference reachable
```

Tool mặc định không persist sensitive values. Với key được đánh dấu nhạy cảm chỉ lưu metadata như key name, source, reference URI, trạng thái kiểm tra và optional version ID.

Ví dụ end-to-end: trước khi deploy, developer chạy:

```bash
configsentinel audit --environment production
```

Tool phát hiện một required configuration key bị thiếu và trả exit code khác `0`, nhờ đó deployment pipeline có thể dừng trước khi application nhận traffic.

**Key differentiator:** đây không phải generic text diff; tool hiểu required key, expected type, environment-specific override, sensitive reference và allowed difference.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Có thể dùng ngay cho project cá nhân hoặc application đang vận hành nhiều môi trường.

### Technical learning value

Dự án liên quan configuration systems, cloud authentication, schema validation, secure logging, CI/CD quality gates và configuration normalization.

### Phù hợp solo developer

Core engine nhỏ và rõ:

```text
source adapters
→ normalized model
→ validators
→ drift engine
→ report
```

Không cần microservices hay distributed infrastructure.

### Vẫn hữu ích với ít người dùng

Chỉ cần tool phát hiện được một lỗi cấu hình trước production thì đã có giá trị cá nhân thực tế.

### Điều gì khiến ý tưởng thất bại

- project chỉ có một environment;
- configuration rất ít và thay đổi hiếm;
- Infrastructure as Code hiện tại đã đảm bảo môi trường hoàn toàn deterministic;
- scope adapter phình quá nhanh.

### Lý do mạnh nhất để không build

Nếu toàn bộ configuration đã nằm trong một declarative source duy nhất, được validate chặt trong CI và recreate môi trường deterministic, một tool bổ sung có thể không đáng công bảo trì.

## 6. Phạm vi MVP

### Must have

- Đọc `appsettings*.json`.
- Đọc `.env` file.
- Configuration contract bằng YAML hoặc JSON.
- Detect missing required key.
- Detect unknown key.
- Validate primitive type: string, integer, boolean, URL.
- Mark sensitive key và không persist raw value.
- Compare hai environment.
- CLI output với severity `ERROR/WARN/INFO`.
- Exit code khác `0` khi có blocking error.

### Should have

- Azure App Configuration adapter.
- External reference existence check.
- Ignore rule theo environment.
- Baseline/snapshot.
- HTML report.
- GitHub Actions integration.

### Later

- Azure App Service settings.
- GitHub variables metadata.
- Kubernetes ConfigMap metadata.
- Docker Compose parser.
- Config change history.
- Slack/Telegram notification.
- Web dashboard.
- Pull request annotation.

## 7. Luồng hoạt động

```text
User selects environment
→ load contract
→ load configured sources
→ authenticate external source if needed
→ normalize keys
→ redact sensitive values
→ validate required/type rules
→ compare with reference environment
→ calculate severity
→ store audit metadata
→ return report
```

CI flow:

```text
git push
→ GitHub Actions
→ configsentinel audit
→ errors detected
→ exit code 1
→ deployment blocked
```

Failure cases:

- Cloud source unavailable → `AUDIT_INCOMPLETE`, không coi là pass.
- Permission denied → ghi resource và lỗi quyền nhưng không log credential.
- External reference không verify được → `NOT_VERIFIED`.
- Contract invalid → fail fast trước khi đọc external source.

## 8. Kiến trúc đề xuất

MVP dùng modular monolith/CLI solution:

```text
ConfigSentinel.Cli
ConfigSentinel.Core
ConfigSentinel.Sources
ConfigSentinel.Tests
```

Core chứa normalized configuration model, schema parser, validators, diff engine và severity rules; không phụ thuộc Azure.

Source adapter dùng interface:

```csharp
public interface IConfigurationSourceReader
{
    Task<ConfigurationSnapshot> ReadAsync(
        SourceDefinition source,
        CancellationToken cancellationToken);
}
```

Adapters MVP:

```text
JsonConfigurationSourceReader
EnvFileConfigurationSourceReader
```

Database, queue và cache đều **không cần** trong MVP. Audit history có thể ghi JSON metadata file; database chỉ cần khi có dashboard/history.

CLI local không cần authentication riêng. Azure adapter sau này dùng `DefaultAzureCredential`.

Logging dùng structured console output và optional JSON report.

Deployment dưới dạng standalone CLI executable hoặc Docker image.

## 11. API và tích hợp

### Local JSON / environment files

Purpose: core MVP.

Authentication: none.

Cost: none.

Privacy concern: file có thể chứa dữ liệu nhạy cảm.

Fallback: metadata-only mode và redaction.

### Azure App Configuration

Purpose: đọc key-value từ cloud environment.

Authentication: Azure identity/RBAC.

Official .NET provider: https://learn.microsoft.com/en-us/azure/azure-app-configuration/reference-dotnet-provider

Cost/rate limit: audit chạy trước deploy hoặc theo lịch thưa, không cần polling liên tục.

Fallback: export configuration thành JSON rồi audit offline.

### Azure Key Vault references

Purpose: verify external sensitive references.

Authentication: Azure identity/RBAC theo setup.

Privacy: không persist referenced value.

Fallback: validate reference syntax và đánh dấu `NOT_VERIFIED`.

### GitHub Actions

Purpose: chạy audit trước deployment.

Authentication: workflow identity do user quản lý.

Fallback: CLI local.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Các quyết định missing key, wrong type, invalid URL, unavailable reference và unexpected environment difference đều cần deterministic rule engine.

AI có thể được thêm sau để diễn giải report bằng ngôn ngữ tự nhiên, nhưng không nên quyết định deployment pass/fail.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác nhận drift tồn tại trong project thật.

**Tasks:** chọn một ASP.NET Core project, export config của local/dev/staging, diff key names và ghi lại inconsistency.

**Expected output:** 10–30 configuration keys với ít nhất một drift thực tế hoặc bằng chứng manual comparison mất thời gian.

**Completion criteria:** tìm được một inconsistency đáng chú ý hoặc chứng minh workflow hiện tại bất tiện.

### Phase 1 — Core MVP

**Goal:** audit JSON configuration bằng contract.

**Tasks:** CLI, YAML parser, JSON reader, normalized key format, required/type validators, console report, exit code.

**Expected output:**

```bash
configsentinel audit --source appsettings.Production.json
```

**Completion criteria:** phát hiện đúng missing/type errors trong fixture tests.

### Phase 2 — Reliability

**Goal:** xử lý sensitive data và failure paths an toàn.

**Tasks:** masking, `.env` adapter, schema validation, structured logging, timeout/cancellation và security tests.

**Completion criteria:** fixture sensitive values không xuất hiện trong logs hoặc reports.

### Phase 3 — Useful expansion

**Goal:** dùng được với cloud environment thật.

**Tasks:** Azure App Configuration adapter, external reference verifier, staging-vs-production diff, baseline ignore rules và GitHub Actions example.

**Completion criteria:** audit thành công một cloud-hosted project thực tế.

### Phase 4 — Production readiness

**Goal:** reusable lâu dài.

**Tasks:** publish executable, Docker image, semantic versioning, sample contracts, security docs và release pipeline.

**Completion criteria:** clean machine có thể cài và audit sample project chỉ dựa vào README.

## 14. Các bài toán kỹ thuật đáng học

### 1. Configuration normalization

Một logical key có thể xuất hiện dưới dạng:

```text
Cache:TtlSeconds
Cache__TtlSeconds
CACHE__TTLSECONDS
```

Cần canonical representation nhất quán.

### 2. Sensitive-data-safe processing

Tool cần inspect configuration mà không vô tình log dữ liệu bí mật. Kỹ năng học được: redaction, secure logging và data minimization.

### 3. Cloud identity

Azure adapter nên dùng managed/interactive identity thay vì credential hard-coded. Kỹ năng học được: Azure RBAC và `DefaultAzureCredential`.

### 4. Drift classification

Không phải mọi difference đều lỗi. Một số key như endpoint hoặc log level hợp lệ khi khác môi trường. Kỹ năng học được: policy/rule engine design.

### 5. CI/CD quality gate

CLI phải deterministic về exit code và report. Kỹ năng học được: deployment safeguards và developer tooling contract.

## 15. Rủi ro và cách xử lý

### Sensitive data leakage

Mitigation: masking, metadata-only persistence, never-log policy và tests quét output cho fixture markers.

### Permission quá rộng

Mitigation: least privilege; chỉ yêu cầu read/verify tối thiểu cho adapter.

### False positives

Mitigation: rule rõ ràng như:

```yaml
allowDifference: true
```

### Scope expansion

Mitigation: MVP chỉ JSON + `.env`; Azure là adapter đầu tiên sau core.

### Platform dependency

Mitigation: ports/adapters architecture để core không phụ thuộc cloud SDK.

### User adoption

Mitigation: command:

```bash
configsentinel init --from appsettings.json
```

để sinh starter contract tự động.

## 16. Kiểm thử

Strategy:

- Unit tests cho normalization và validators.
- Integration tests cho file readers.
- Adapter tests với mocked cloud clients.
- End-to-end CLI tests.
- Security tests đảm bảo sensitive fixtures không leak.

5 scenario quan trọng:

1. Required key thiếu → `ERROR`, exit code `1`.
2. Integer field chứa text → type validation fail.
3. Sensitive input không xuất hiện trong console/report.
4. Key khác giữa staging và production nhưng `allowDifference=true` → không blocking.
5. Cloud source timeout → audit trả `INCOMPLETE`, không trả `PASS`.

## 17. Cách đo dự án có hữu ích hay không

- **Usage:** số lần audit chạy trước deploy.
- **Prevention:** số configuration issue được phát hiện trước runtime.
- **Time saved:** thời gian manual comparison trước và sau khi dùng tool.
- **Completion rate:** % audit hoàn tất.
- **False-positive rate:** findings sai / tổng findings.
- **Repeated use:** số deployment liên tiếp có ConfigSentinel gate.
- **Reliability:** mục tiêu cá nhân >99% audit executions hoàn tất deterministic và 0 sensitive-data leakage incident.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, hoàn thành vertical slice:

```text
contract.yaml
+ appsettings.Production.json
→ audit
→ console findings
→ exit code
```

### Setup

```bash
dotnet new sln -n ConfigSentinel
dotnet new console -n ConfigSentinel.Cli -o src/ConfigSentinel.Cli
dotnet new classlib -n ConfigSentinel.Core -o src/ConfigSentinel.Core
dotnet new xunit -n ConfigSentinel.Tests -o tests/ConfigSentinel.Tests

dotnet sln add src/ConfigSentinel.Cli
dotnet sln add src/ConfigSentinel.Core
dotnet sln add tests/ConfigSentinel.Tests

dotnet add src/ConfigSentinel.Cli reference src/ConfigSentinel.Core
dotnet add tests/ConfigSentinel.Tests reference src/ConfigSentinel.Core

dotnet add src/ConfigSentinel.Cli package YamlDotNet
```

### Files cần tạo

```text
src/ConfigSentinel.Core/
  Models/ConfigurationRule.cs
  Models/ConfigurationFinding.cs
  Services/ConfigurationAuditor.cs

src/ConfigSentinel.Cli/
  Program.cs

samples/
  contract.yaml
  appsettings.Production.json
```

### Sample contract

```yaml
rules:
  - key: Database:CredentialRef
    required: true
    type: string
    sensitive: true

  - key: Cache:TtlSeconds
    required: true
    type: integer

  - key: FeatureFlags:NewCheckout
    required: true
    type: boolean
```

### Sample configuration

```json
{
  "Database": {
    "CredentialRef": "[REDACTED_REFERENCE]"
  },
  "Cache": {
    "TtlSeconds": "invalid-number"
  }
}
```

### First vertical slice

Flatten JSON thành canonical keys, sau đó audit rules.

Expected output:

```text
OK     Database:CredentialRef
ERROR  Cache:TtlSeconds             expected integer
ERROR  FeatureFlags:NewCheckout     required key missing

Audit failed: 2 errors
```

### Verification checklist

- [ ] Nested JSON key được flatten đúng.
- [ ] Required key missing được phát hiện.
- [ ] Integer type mismatch được phát hiện.
- [ ] Sensitive field không in raw value ra console.
- [ ] CLI trả exit code `1` khi có error.
- [ ] Ít nhất 3 unit tests pass.

### Stop condition

Kết thúc session khi command:

```bash
dotnet run --project src/ConfigSentinel.Cli -- samples/contract.yaml samples/appsettings.Production.json
```

trả đúng hai lỗi trong sample và không hiển thị raw sensitive value. Không làm Azure integration, dashboard, database hoặc AI trong session đầu tiên.
