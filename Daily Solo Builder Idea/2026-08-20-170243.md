# Ý tưởng hôm nay: RuntimeSunset — .NET Support & Upgrade Readiness Guard

## 1. Tóm tắt ý tưởng

RuntimeSunset là một developer tool self-hosted/CLI giúp quét repository .NET để tìm **runtime/SDK/framework version sắp hết hỗ trợ, version pin không nhất quán và các điểm có thể cản trở việc nâng cấp**. Công cụ đọc `TargetFramework`, `global.json`, Docker image, GitHub Actions workflow và metadata release chính thức của .NET, sau đó tạo một báo cáo actionable cho từng repository.

- Người dùng chính: .NET developer hoặc solo SaaS developer duy trì nhiều repository.
- Bài toán chính: project vẫn build bình thường nhưng đang tiến gần EOL hoặc dùng runtime không đồng nhất giữa local, CI và container.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Một project .NET thường khai báo version ở nhiều nơi:

- `TargetFramework` trong `.csproj`;
- SDK version trong `global.json`;
- Docker base image như `mcr.microsoft.com/dotnet/aspnet:8.0`;
- `actions/setup-dotnet` trong GitHub Actions;
- documentation hoặc deployment script;
- runtime đang cài trên host thực tế.

Khi một version tiến gần end-of-support, developer có thể biết thông tin này từ trang lifecycle nhưng vẫn phải tự tìm xem repository nào đang dùng version đó và phải sửa ở đâu.

**Confirmed facts từ nguồn chính thức:**

- Chính sách hỗ trợ .NET hiện liệt kê .NET 10 là LTS, end of support ngày **14/11/2028**; .NET 9 và .NET 8 đều kết thúc hỗ trợ ngày **10/11/2026**. Microsoft cũng nêu rằng ứng dụng phải duy trì patch hiện hành trong lifecycle để tiếp tục được hỗ trợ.
- Repository `dotnet/core` công bố `releases-index.json` chứa các trường machine-readable như `channel-version`, `support-phase`, `eol-date`, `latest-sdk`, `latest-runtime` và trạng thái security update.
- `actions/setup-dotnet` có thể lấy SDK từ `dotnet-version` hoặc `global.json`; nếu không pin version phù hợp, môi trường CI có thể phụ thuộc vào SDK đã cài sẵn trên runner.

Nguồn:

- https://dotnet.microsoft.com/en-us/platform/support/policy
- https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core
- https://github.com/dotnet/core/blob/main/release-notes/releases-index.json
- https://github.com/dotnet/core/blob/main/release-notes/schemas/README.md
- https://github.com/actions/setup-dotnet

**Observation:** Dependabot/Renovate rất hữu ích cho package update, nhưng lifecycle của runtime/framework là một lớp vấn đề khác: project có thể không có package outdated đáng kể nhưng vẫn chạy trên một framework sắp EOL.

**Assumption cần kiểm chứng:** developer có từ 5–20 repository sẽ thấy giá trị ở một báo cáo tập trung cho biết “repo nào phải nâng trước, còn bao nhiêu ngày hỗ trợ và file nào đang pin version cũ”.

## 3. Người dùng mục tiêu

**Primary user:** .NET backend developer hoặc solo developer vận hành nhiều API/worker/service.

- Context: có nhiều repository với tuổi đời khác nhau, build bằng GitHub Actions hoặc Azure DevOps và deploy qua Docker/VPS/Azure.
- Main pain point: không nhớ tất cả project đang target version nào và version đó còn được hỗ trợ bao lâu.
- Current workaround: mở từng `.csproj`, `global.json`, Dockerfile, CI YAML rồi đối chiếu thủ công với lifecycle page.
- Lý do thử tool: chạy một command và nhận được report có deadline + vị trí cần sửa.

MVP không phục vụ governance enterprise, không yêu cầu quyền admin cloud và không scan toàn organization ngay từ đầu.

## 4. Giải pháp đề xuất

Người dùng chạy:

```bash
runtimesunset scan ./MySolution
```

Tool sẽ:

1. Tìm `.csproj`, `.fsproj`, `global.json`, `Dockerfile`, `.github/workflows/*.yml`.
2. Extract các version liên quan tới .NET.
3. Normalize version thành channel, ví dụ `net8.0` → `.NET 8`.
4. Lấy metadata lifecycle chính thức.
5. So sánh các version giữa application, SDK, CI và container.
6. Sinh severity:
   - `OK`
   - `UPGRADE_SOON`
   - `EOL`
   - `VERSION_DRIFT`
   - `UNPINNED_CI`
7. Xuất console table + JSON/Markdown report.

### Ví dụ

Repository có:

```text
src/App/App.csproj           net8.0
src/Worker/Worker.csproj     net8.0
global.json                  8.0.416
Dockerfile build image       sdk:8.0
Dockerfile runtime image     aspnet:8.0
.github/workflows/ci.yml      dotnet-version: 8.0.x
```

RuntimeSunset trả:

```text
Framework: .NET 8
Support phase: Maintenance
End of support: 2026-11-10
Days remaining: 82
Status: UPGRADE_SOON

Upgrade surfaces:
- src/App/App.csproj
- src/Worker/Worker.csproj
- global.json
- Dockerfile
- .github/workflows/ci.yml

Recommended target: .NET 10 LTS
```

User vẫn quyết định khi nào upgrade và target nào; tool không tự sửa code trong MVP.

**Key differentiator:** tập trung vào **lifecycle + cross-file version consistency**, không chỉ package dependency update.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Ngay cả khi chỉ dùng cho project cá nhân, tool giúp tạo inventory rõ ràng về runtime support và tránh tình trạng “project cũ nhưng vẫn chạy nên chưa ai để ý”.

### Technical learning value

Dự án kết hợp:

- repository/static analysis;
- semantic parsing XML/YAML/JSON;
- external metadata synchronization;
- policy engine;
- CLI UX;
- CI integration;
- caching và graceful degradation.

### Vì sao phù hợp solo developer

Core workflow rất nhỏ: scan → normalize → compare → report. Không cần database trong phiên bản CLI đầu tiên, không cần AI và không cần cloud infrastructure.

### Vẫn hữu ích khi có rất ít user

Chỉ cần bản thân có vài repository .NET là đã có thể dùng hàng tháng hoặc trước mỗi planning cycle.

### Điều gì làm ý tưởng thất bại

- Report chỉ lặp lại thông tin có thể nhìn thấy nhanh trong `.csproj`.
- Scanner tạo nhiều false positive.
- Tool không phát hiện đủ các nơi version được pin.

### Lý do mạnh nhất để không build

Nếu chỉ duy trì một repository duy nhất và luôn nâng .NET ngay khi release, một script PowerShell nhỏ có thể đủ; dashboard/product hoàn chỉnh sẽ là overkill.

## 6. Phạm vi MVP

### Must have

- CLI scan một directory local.
- Parse `TargetFramework` và `TargetFrameworks` từ project files.

### Later

- GitHub App.

- Pull request auto-generated upgrade checklist.

- Node/Java/Python lifecycle adapters.

## 7. Luồng hoạt động

### Normal flow

User chạy CLI
→ validate path
→ discover files
→ parse version declarations
→ normalize thành runtime channels
→ load lifecycle metadata từ cache hoặc official source
→ evaluate policies
→ tạo findings
→ render console/JSON report
→ set process exit code.

### Failure cases

**Không có internet**

→ dùng cache metadata gần nhất
→ report `metadataAge`
→ warning nếu cache quá cũ.

**Không parse được YAML/XML**

→ không dừng toàn bộ scan
→ tạo finding `PARSE_ERROR` cho file đó.

**Version dùng variable**

Ví dụ Dockerfile dùng `ARG DOTNET_VERSION`.

→ cố resolve ARG local nếu có giá trị mặc định
→ nếu không resolve được, đánh dấu `UNKNOWN_VERSION` thay vì đoán.

**Multi-target project**

→ evaluate từng target framework riêng.

**Preview framework**

→ report preview/go-live status riêng, không áp lifecycle như stable release.

## 10. Thiết kế dữ liệu ban đầu

Không cần relational database. Dùng các model nhỏ.

### RuntimeDeclaration

**Purpose:** một nơi trong repository khai báo .NET version.

Fields:

- `SourceType`
- `FilePath`
- `LineNumber`
- `RawValue`
- `NormalizedChannel`
- `Component` (`Framework`, `SDK`, `RuntimeImage`, `BuildImage`, `CI`)

Relationship: nhiều declarations thuộc một scan.

Retention: chỉ tồn tại trong process hoặc JSON report.

### ReleaseChannel

**Purpose:** metadata lifecycle của một .NET major release.

Fields:

- `ChannelVersion`
- `ReleaseType`
- `SupportPhase`
- `EolDate`
- `LatestRuntime`
- `LatestSdk`
- `LatestReleaseDate`
- `Security`

Retention: cache 24 giờ hoặc configurable.

### Finding

**Purpose:** một vấn đề/action item.

Fields:

- `Code`
- `Severity`
- `Message`
- `FilePath`
- `DetectedVersion`
- `RecommendedVersion`
- `DaysUntilEol`

### ScanReport

Fields:

- `RepositoryPath`
- `ScannedAt`
- `MetadataUpdatedAt`
- `Declarations`
- `Findings`
- `Summary`

## 11. API và tích hợp

### Official .NET Release Metadata

Source:

```text
https://builds.dotnet.microsoft.com/dotnet/release-metadata/releases-index.json
```

GitHub mirror/documentation:

```text
https://github.com/dotnet/core/blob/main/release-notes/releases-index.json
```

- Purpose: latest version, lifecycle phase, EOL date, release type.
- Authentication: không cần.
- Cost/rate limit: public static metadata, nhưng vẫn cache để tránh request thừa.
- Privacy: không upload source code.
- Fallback: local cached JSON hoặc bundled minimal lifecycle table có timestamp.

### GitHub Actions `actions/setup-dotnet`

- Purpose: detect version CI đang install.
- Authentication: không cần API; parse YAML local.
- Cost: none.
- Privacy: none beyond local repository.
- Fallback: nếu workflow dùng custom action/script, report `UNRESOLVED_CI_RUNTIME`.

### Microsoft Artifact Registry Docker images

MVP chỉ parse image tag trong Dockerfile, không cần gọi registry API.

Fallback: nếu tag dynamic, report unknown.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Lifecycle evaluation là deterministic:

```text
declared version + official EOL metadata + current date → status
```

Dùng LLM để quyết định supported/EOL sẽ làm kết quả kém tin cậy hơn.

AI chỉ có thể là optional feature tương lai để giải thích migration plan từ diff/build errors, nhưng không nên tham gia core scanner hoặc policy decision.

## 14. Các bài toán kỹ thuật đáng học

### 1. Static repository analysis

Học cách discover và parse nhiều kiểu cấu hình mà không phụ thuộc regex mong manh.

### 2. Version normalization

`net8.0`, `8.0.x`, `8.0.416`, `aspnet:8.0` đều biểu diễn version khác nhau nhưng cần map về cùng lifecycle channel.

Kỹ năng: semantic versioning, canonicalization, ambiguity handling.

### 3. Policy engine

Tách detection khỏi policy để user có thể cấu hình:

```text
warnBeforeEolDays: 180
failOnEol: true
```

Kỹ năng: rule design, deterministic evaluation, explainable findings.

### 4. Reliable metadata synchronization

External metadata có thể timeout hoặc thay schema.

Kỹ năng: cache, schema validation, retry, fallback, freshness reporting.

### 5. CI-friendly CLI design

Kỹ năng: stable exit code, machine-readable output, actionable console UX và reproducible behavior.

## 15. Rủi ro và cách xử lý

### False positives

**Risk:** version được build động từ variable hoặc imported props.

**Mitigation:** chỉ tạo high-confidence finding khi resolve được rõ; unresolved value phải có status riêng.

### Scope expansion

**Risk:** biến thành full dependency/SBOM scanner.

**Mitigation:** MVP chỉ lifecycle/runtime version; package CVE để cho Dependabot/NuGet tooling hiện có.

### Metadata dependency

**Risk:** endpoint release metadata đổi format hoặc unavailable.

**Mitigation:** JSON schema validation, local cache, fallback source, expose metadata freshness.

### Recommendation quá đơn giản

**Risk:** `.NET 8 → .NET 10` không có nghĩa upgrade luôn trivial.

**Mitigation:** recommendation chỉ là target lifecycle; không tuyên bố migration compatibility cho source code.

### User adoption

**Risk:** developer không cần tool riêng nếu chỉ có một repo.

**Mitigation:** ưu tiên CLI cực nhẹ, chạy tốt trong CI và hỗ trợ multi-repo script sau này.

### Maintenance burden

**Risk:** syntax file/config mới xuất hiện.

**Mitigation:** parser adapters độc lập, fixture-based tests và chỉ support pattern phổ biến trước.

## 16. Kiểm thử

### Strategy

- Unit test cho version normalization và policy engine.
- Parser tests dùng fixture `.csproj`, JSON, Dockerfile, YAML.
- Integration test với local fake metadata server.
- Failure-path tests cho timeout/cache/schema error.
- CLI snapshot tests cho output/exit code.

### 5 test scenario quan trọng nhất

1. Repository target `net8.0` được map đúng lifecycle/EOL và cảnh báo theo threshold.
2. `.csproj` là .NET 10 nhưng Docker runtime vẫn 8.0 → `VERSION_DRIFT`.
3. `global.json` pin SDK khác channel với `TargetFramework` nhưng hợp lệ → report informational thay vì false fail.
4. Metadata endpoint unavailable → dùng cache và report metadata age.
5. GitHub Actions không pin .NET version rõ ràng → `UNPINNED_CI` hoặc `UNRESOLVED_CI_RUNTIME` theo rule.

### First vertical slice

`ProjectScanner` tìm `*.csproj` và parse:

```xml
<TargetFramework>net8.0</TargetFramework>
```

Normalize thành:

```text
8.0
```

Tạm dùng sample metadata:

```csharp
new ReleaseChannel(
    ChannelVersion: "8.0",
    SupportPhase: "maintenance",
    EolDate: new DateOnly(2026, 11, 10));
```

CLI output:

```text
samples/Net8Sample/Net8Sample.csproj
Framework: .NET 8
Support phase: maintenance
End of support: 2026-11-10
Days remaining: <calculated>
Status: UPGRADE_SOON
```

### Verification checklist

- [ ] Tìm được `.csproj` recursive.

### Expected result

Một command như:

```bash
dotnet run --project src/RuntimeSunset.Cli -- scan ./samples
```

in ra lifecycle status thật cho project sample.

### Stop condition

Dừng session ngay khi scanner đọc được một `.csproj`, map framework thành lifecycle channel, tính EOL status và có ít nhất ba test policy pass. Không thêm frontend, GitHub API, Docker parser hoặc AI trong session đầu tiên.
