# Ý tưởng hôm nay: RuleSentry — Outlook Inbox Rule Drift & Forwarding Watcher

## 1. Tóm tắt ý tưởng

RuleSentry là một công cụ self-hosted giúp người dùng Microsoft 365 theo dõi **Inbox rules và các hành vi forwarding đáng chú ý**, lưu snapshot theo thời gian, phát hiện rule mới hoặc rule bị thay đổi và cảnh báo khi xuất hiện hành vi rủi ro như tự động forward email ra ngoài hoặc di chuyển thư vào folder khó thấy.

- Người dùng chính: developer, admin nhỏ hoặc power user dùng Microsoft 365 và muốn tự giám sát mailbox của mình.
- Bài toán chính: một mailbox có thể bị thay đổi rule mà người dùng không nhận ra ngay.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

### Confirmed facts

Microsoft Graph v1.0 có API để lấy toàn bộ `messageRule` trong Inbox bằng:

```http
GET /me/mailFolders/inbox/messageRules
```

Quyền delegated tối thiểu để chỉ đọc các rule là `MailboxSettings.Read`. Microsoft cũng cho phép sửa rule với `MailboxSettings.ReadWrite`.

Nguồn:

- https://learn.microsoft.com/en-us/graph/api/mailfolder-list-messagerules?view=graph-rest-1.0
- https://learn.microsoft.com/en-us/graph/api/messagerule-update?view=graph-rest-1.0

Microsoft Defender documentation liệt kê suspicious Inbox rules và external forwarding là dấu hiệu có thể liên quan tới compromised mailbox. Các rule có thể forward email tới địa chỉ lạ, move email sang folder ít được chú ý hoặc xóa/ẩn dấu vết.

Nguồn:

- https://learn.microsoft.com/en-us/defender-office-365/responding-to-a-compromised-email-account
- https://learn.microsoft.com/en-us/defender-xdr/alert-grading-playbook-inbox-manipulation-rules

Microsoft cũng cảnh báo automatic external forwarding có thể tạo rủi ro disclosure dữ liệu.

Nguồn:

- https://learn.microsoft.com/en-us/defender-office-365/outbound-spam-policies-external-email-forwarding

### Observation

Enterprise tenant có thể dùng Defender XDR, Purview Audit và Exchange Online tooling để điều tra rule changes, nhưng các công cụ đó hướng nhiều tới security/admin workflow hơn là một personal/self-hosted timeline đơn giản.

### Assumption cần kiểm chứng

Solo developer, consultant hoặc admin nhỏ sẽ thấy hữu ích ở một dashboard đơn giản chỉ cần delegated login, tự snapshot rule định kỳ và cảnh báo khi cấu hình lệch khỏi baseline.

### Cách người dùng thường xử lý hiện nay

- Mở Outlook Rules UI để kiểm tra thủ công.
- Chạy Exchange Online PowerShell như `Get-InboxRule`.
- Dùng Microsoft 365 admin/security portal nếu có quyền và license phù hợp.
- Chỉ phát hiện khi email biến mất, bị forward hoặc có incident.

Điểm bất tiện là các cách trên mang tính point-in-time; người dùng khó trả lời nhanh: **“Rule này xuất hiện từ lúc nào và khác gì so với hôm qua?”**

## 3. Người dùng mục tiêu

### Primary user

Developer hoặc technical user đang dùng một tài khoản Microsoft 365 work/school và có nhiều automation/mail rules.

- Bối cảnh: mailbox dùng cho công việc, GitHub notifications, alerts, Azure, invoices, support và automation.
- Pain point: không nhớ chính xác rule hiện có và khó nhận biết thay đổi ngoài dự kiến.
- Workaround: vào Outlook hoặc chạy PowerShell thủ công.
- Lý do thử RuleSentry: có baseline, diff history và cảnh báo có ngữ cảnh.

MVP chỉ cần hỗ trợ **một mailbox của chính user**, tránh mở rộng ngay sang tenant-wide monitoring.

## 4. Giải pháp đề xuất

### Main workflow

User đăng nhập Microsoft bằng OAuth
→ RuleSentry gọi Microsoft Graph để lấy Inbox rules
→ normalize dữ liệu thành snapshot
→ tính fingerprint
→ so sánh snapshot trước
→ phân loại thay đổi
→ lưu diff
→ hiển thị dashboard
→ gửi notification khi thay đổi đạt ngưỡng rủi ro.

### Input

Các thuộc tính như:

- `displayName`
- `sequence`
- `isEnabled`
- `conditions`
- `exceptions`
- `actions`
- `forwardTo`
- `redirectTo`
- `delete`
- `moveToFolder`
- `markAsRead`
- `stopProcessingRules`

### Processing

Deterministic rules đánh điểm rủi ro, ví dụ:

- external forwarding mới: High
- rule mới có `delete=true`: High
- move mail sang RSS/Junk/Notes-like location: Medium/High tùy rule
- đổi sequence: Low
- rename rule: Low
- disable rule: Medium nếu rule thuộc allowlist quan trọng

### Output

Ví dụ:

```text
HIGH — New external forwarding detected
Rule: Invoice Processing
Action: forwardTo -> external-domain.example
Detected: 03:54
Previous snapshot: no forwarding action
```

### User control

User quyết định:

- rule nào được allowlist;
- domain nào được xem là trusted;
- mức độ cảnh báo;
- retention;
- có bật remediation hay chỉ read-only.

### Key differentiator

Không cố thay thế Defender. Điểm khác biệt là **personal mailbox configuration history + human-readable diff + self-hosted control**.

## 6. Phạm vi MVP

### Must have

- Microsoft sign-in bằng delegated OAuth.
- Quyền read-only `MailboxSettings.Read`.
- Lấy Inbox message rules từ Microsoft Graph.
- Normalize và hash snapshot.
- Detect added/removed/changed rule.
- Risk scoring deterministic.
- Dashboard timeline.
- Manual “Run scan now”.
- Scheduler scan mỗi 15–60 phút tùy cấu hình.
- Notification qua Telegram hoặc email webhook đơn giản.

### Should have

- Ignore known rule changes.
- Diff viewer theo field.
- Export JSON.
- Baseline pinning.
- Notification deduplication.

### Later

- Tenant-wide multi-mailbox mode.
- Exchange Online PowerShell adapter.
- Purview audit correlation.
- One-click disable suspicious rule.
- Hidden rule inspection qua Exchange tooling.
- Slack/Teams integration.
- Security incident workflow.

## 7. Luồng hoạt động

User login
→ obtain delegated token
→ Graph call
→ validate response
→ canonicalize rules
→ create snapshot
→ compare with previous snapshot
→ persist changes
→ score risk
→ notify if threshold crossed.

### Failure cases

**Graph returns 401/403**

→ refresh token hoặc mark connection as `NeedsReauth`.

**429 rate limit**

→ respect `Retry-After`, không retry dồn dập.

**No rule changes**

→ chỉ lưu heartbeat hoặc skip snapshot body mới để giảm storage.

**Notification provider down**

→ giữ notification pending và retry idempotently.

**Graph schema có field mới**

→ canonicalizer chỉ dùng field known, raw response có thể lưu riêng cho debugging.

## 11. API và tích hợp

### Microsoft Graph — Inbox message rules

Purpose: đọc Inbox rules.

Endpoint:

```http
GET /me/mailFolders/inbox/messageRules
```

Auth: OAuth 2.0 delegated.

Least privileged documented permission: `MailboxSettings.Read`.

Cost/rate limit: không giả định quota cố định; client phải xử lý throttling/`Retry-After`.

Privacy: rule metadata có thể chứa email address, keyword và folder destination.

Fallback: cho phép import JSON snapshot thủ công để test offline.

Nguồn:

https://learn.microsoft.com/en-us/graph/api/mailfolder-list-messagerules?view=graph-rest-1.0

### Microsoft identity platform

Purpose: sign-in và token acquisition.

Fallback: dev mode với sample Graph JSON.

### Notification provider

Telegram webhook/bot hoặc generic webhook.

Fallback: dashboard-only alerts.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem yêu cầu độ chính xác và reproducibility cao. Rule diff và risk scoring có thể làm deterministic.

Ví dụ:

```text
if newAction.forwardTo contains external domain
and destination not in allowlist
=> High
```

AI có thể thêm sau chỉ để viết explanation dễ đọc, nhưng không nên quyết định severity hoặc remediation.

## 14. Các bài toán kỹ thuật đáng học

### 1. Canonicalization và semantic diff

JSON property order hoặc array order không nên tạo false positive. Kỹ năng: normalized representation và stable hashing.

### 2. OAuth delegated token lifecycle

Kỹ năng: consent, refresh token, secure token persistence, revoked sessions.

### 3. Idempotent alerting

Một change không được spam notification qua nhiều scan. Kỹ năng: dedup key và delivery state machine.

### 4. Security scoring

Học cách biến raw configuration change thành risk signal nhưng vẫn tránh overclaim.

### 5. External API resilience

Kỹ năng: throttling, backoff, timeout, retry boundary và degraded mode.

## 15. Rủi ro và cách xử lý

### OAuth token security

**Risk:** token bị lộ có thể cho phép đọc mailbox settings.

**Mitigation:** encrypt at rest, least privilege, không log token, rotate secret, single-user deployment trước.

### False positive

**Risk:** user chủ động tạo forwarding rule hợp lệ nhưng bị báo High.

**Mitigation:** trusted destination allowlist và acknowledgement.

### Graph API dependency

**Risk:** API throttling hoặc temporary outage.

**Mitigation:** exponential backoff, heartbeat status và không đánh outage thành security incident.

### Scope creep

**Risk:** project biến thành Defender clone.

**Mitigation:** MVP chỉ theo dõi Inbox rule drift.

### Missing hidden/admin-level rules

**Risk:** Graph Inbox messageRules không thay thế toàn bộ Exchange/Purview investigation surface.

**Mitigation:** ghi rõ coverage boundary; Exchange PowerShell/Purview adapters chỉ là extension sau.

### Privacy

**Risk:** conditions có thể chứa keyword nhạy cảm.

**Mitigation:** local/self-hosted default, encryption, optional redaction, configurable retention.

## 16. Kiểm thử

### Strategy

- Unit tests cho canonicalizer, diff engine và risk scorer.
- Integration tests với mocked Graph HTTP responses.
- E2E Playwright cho dashboard.
- Failure-path tests cho 401, 429, 500 và notification outage.
- Security tests cho token leakage trong logs.

### 5 test scenario quan trọng nhất

1. Tạo rule mới → detect `Added` đúng một lần.
2. Thêm `forwardTo` external address → High alert.
3. Chỉ đổi sequence → Low severity, không High.
4. Graph trả 429 → retry theo `Retry-After`, không duplicate snapshot.
5. Restart app sau khi alert đã gửi → không gửi lại cùng alert.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, hoàn thành vertical slice:

**sample Graph JSON → normalize → hash → compare hai snapshot → in diff ra terminal.**

Chưa cần OAuth thật trong session đầu.

### Files/components

```text
RuleSentry.sln
src/
  RuleSentry.Core/
    Models/InboxRule.cs
    Normalization/RuleCanonicalizer.cs
    Diff/RuleDiffEngine.cs
  RuleSentry.Cli/
    Program.cs
tests/
  RuleSentry.Tests/
samples/
  rules-before.json
  rules-after.json
```

### Commands

```bash
dotnet new sln -n RuleSentry
dotnet new classlib -n RuleSentry.Core -o src/RuleSentry.Core
dotnet new console -n RuleSentry.Cli -o src/RuleSentry.Cli
dotnet new xunit -n RuleSentry.Tests -o tests/RuleSentry.Tests
dotnet sln add src/RuleSentry.Core src/RuleSentry.Cli tests/RuleSentry.Tests
dotnet add src/RuleSentry.Cli reference src/RuleSentry.Core
dotnet add tests/RuleSentry.Tests reference src/RuleSentry.Core
```

### First vertical slice

`rules-before.json`:

```json
{
  "value": [
    {
      "id": "rule-1",
      "displayName": "Alerts",
      "isEnabled": true,
      "actions": {
        "markAsRead": true
      }
    }
  ]
}
```

`rules-after.json` thêm một forwarding action với địa chỉ placeholder như `audit-recipient@external.example`.

CLI expected output:

```text
Rule changed: Alerts
Field: actions.forwardTo
Before: none
After: external destination
Risk: HIGH
Reason: new external forwarding destination
```

### Verification checklist

- [ ] JSON property order khác nhau không tạo diff giả.
- [ ] Rule added được detect.
- [ ] Rule removed được detect.
- [ ] External forwarding được đánh High.
- [ ] Có ít nhất 3 unit tests pass.
- [ ] `dotnet run` hiển thị diff rõ ràng.

### Stop condition

Dừng session ngay khi command:

```bash
dotnet run --project src/RuleSentry.Cli -- samples/rules-before.json samples/rules-after.json
```

trả về semantic diff đúng và test suite pass. Không làm dashboard, OAuth hoặc notification trong session đầu.
