# Ý tưởng hôm nay: ContractPulse — API Contract Drift Watcher cho các dự án .NET

## 1. Tóm tắt ý tưởng

ContractPulse là một công cụ self-hosted theo dõi OpenAPI contract của các API mà một developer hoặc team nhỏ đang phụ thuộc, phát hiện thay đổi giữa các snapshot và cảnh báo khi có khả năng gây breaking change cho consumer. Thay vì chỉ diff hai file OpenAPI thủ công trong CI của API owner, công cụ tập trung vào góc nhìn **consumer**: “API tôi đang gọi vừa thay đổi điều gì, endpoint nào của tôi có nguy cơ hỏng, và tôi đã xác nhận thay đổi đó chưa?”.

**Project size:** Medium. **MVP ước tính:** 7–12 ngày làm ngoài giờ, hoặc khoảng 30–45 giờ tập trung.

## 2. Bài toán thực tế

### Confirmed facts

ASP.NET Core có hỗ trợ sinh OpenAPI document trực tiếp từ ứng dụng; tài liệu Microsoft hiện tại cho biết .NET 10 hỗ trợ OpenAPI 3.1 và có thể sinh document cả runtime lẫn build-time. Điều này khiến OpenAPI trở thành nguồn contract khả dụng cho nhiều API .NET.

Nguồn: https://learn.microsoft.com/en-us/aspnet/core/fundamentals/openapi/aspnetcore-openapi

`oasdiff` là một dự án open-source chuyên diff OpenAPI và phát hiện breaking changes. Nó hỗ trợ CLI, CI, JSON/YAML/Markdown output và OpenAPI 3.1. Điều này xác nhận phần “phát hiện thay đổi contract” có thể dựa trên tooling hiện hữu thay vì tự viết parser/rule engine từ đầu.

Nguồn: https://github.com/oasdiff/oasdiff

### Observation

Tooling hiện có giải quyết rất tốt câu hỏi “spec A khác spec B ở đâu?”. Tuy nhiên consumer của nhiều API thường còn phải tự quản lý các việc khác: định kỳ lấy spec mới, giữ lịch sử, biết mình thực sự dùng endpoint nào, suppress thay đổi đã chấp nhận, và nhận cảnh báo chỉ khi thay đổi liên quan đến mình.

### Assumption cần validation

Developer làm integration với nhiều internal/third-party API có thể đang dùng Swagger UI, email/Teams/Slack hoặc release notes để phát hiện thay đổi. Khi provider không thông báo đầy đủ, regression thường chỉ lộ ra khi integration test hoặc production request bắt đầu lỗi.

ContractPulse nhắm vào khoảng trống này, nhưng cần phỏng vấn 3–5 developer trước khi đầu tư sâu để xác nhận họ thực sự gặp vấn đề đủ thường xuyên.

## 3. Người dùng mục tiêu

Người dùng MVP là **backend developer quản lý 3–20 REST API dependencies**, đặc biệt developer .NET làm integration với internal service hoặc API bên thứ ba.

Bối cảnh sử dụng: developer có URL OpenAPI/Swagger JSON hoặc file spec trong Git repository và muốn biết contract có thay đổi hay không mà không phải mở Swagger UI từng ngày.

Pain point chính là phát hiện muộn breaking change. Workaround hiện tại có thể là đọc release note, diff file thủ công, chạy integration test, hoặc chờ consumer lỗi. Họ sẽ thử ContractPulse nếu chỉ cần khai báo một URL/spec và sau đó nhận được cảnh báo có tín hiệu cao thay vì noise.

## 4. Giải pháp đề xuất

Người dùng thêm một `API Watch` gồm tên API, URL tới OpenAPI document, lịch kiểm tra và tùy chọn endpoint mình đang sử dụng. ContractPulse định kỳ tải spec, canonicalize nội dung, tính hash; nếu hash không đổi thì kết thúc ngay. Nếu thay đổi, hệ thống lưu snapshot mới và chạy `oasdiff` giữa snapshot trước/sau.

Kết quả được normalize thành các `ContractChange`: endpoint, HTTP method, loại thay đổi, severity, breaking/non-breaking và message. Dashboard hiển thị timeline. Chỉ thay đổi liên quan tới endpoint đã chọn mới được ưu tiên cảnh báo.

Ví dụ: developer theo dõi `Billing API`, chỉ dùng `POST /payments` và `GET /payments/{id}`. Provider đổi `POST /payments` bằng cách thêm request field bắt buộc `currency`. Job phát hiện spec hash mới, `oasdiff` đánh dấu breaking change, ContractPulse tạo incident và gửi Telegram webhook. Developer mở dashboard, xem old/new contract và chọn `Acknowledged` sau khi cập nhật consumer.

Phần tự động: polling, snapshot, diff, classification, notification, retry. Người dùng vẫn kiểm soát endpoint scope, severity threshold, acknowledgement và retention.

**Differentiator:** không cố cạnh tranh với diff engine; nó biến diff engine thành một **consumer-side monitoring workflow có state và lịch sử**.

## 5. Tại sao ý tưởng này đáng làm

Giá trị thực tế là giảm thời gian kiểm tra API thủ công và đưa contract drift thành tín hiệu chủ động. Giá trị học tập tốt vì dự án chạm vào background processing, idempotency, external HTTP reliability, subprocess/container integration, schema versioning, notification và observability.

Nó phù hợp solo developer vì MVP chỉ cần modular monolith, PostgreSQL và một worker. `oasdiff` xử lý phần khó nhất là semantic diff nên không cần xây rule engine riêng.

Ngay cả chỉ có một người dùng, công cụ vẫn hữu ích để theo dõi API trong các personal integration và side project.

Dự án sẽ thất bại nếu phần lớn API cần theo dõi không expose OpenAPI ổn định hoặc developer không coi contract drift là vấn đề đủ lớn. Lý do mạnh nhất **không nên build** là nếu nhu cầu thực tế chỉ là “block breaking changes trong CI của API do chính mình sở hữu”; trường hợp đó chạy `oasdiff` trực tiếp trong CI đơn giản hơn rất nhiều.

## 6. Phạm vi MVP

### Must have

- Tạo API Watch từ một public OpenAPI URL.
- Poll theo interval cố định.
- Download spec với timeout và giới hạn kích thước.
- Canonical hash để bỏ qua snapshot giống nhau.
- Lưu current/previous snapshot.
- Chạy `oasdiff breaking` và đọc machine-readable output.
- Lưu danh sách breaking changes.
- Dashboard: API status, last checked, last changed, change history.
- Một notification channel: Telegram Bot hoặc generic webhook.
- Retry có giới hạn và trạng thái lỗi rõ ràng.

### Should have

- Filter theo path + HTTP method.
- Acknowledge change.
- Non-breaking changelog.
- Manual “Check now”.
- Configurable severity.
- Conditional GET bằng `ETag` / `Last-Modified` khi server hỗ trợ.

### Later

- Private endpoints với OAuth/API key.
- GitHub repository spec source.
- Consumer code mapping endpoint → repository/file.
- GitHub PR/issue creation.
- Teams/Slack/Discord integrations.
- Multi-user/multi-tenant.
- AI explanation.

## 7. Luồng hoạt động

`User creates API Watch → validate URL/scheme → fetch spec → validate OpenAPI → canonicalize/hash → store initial snapshot → scheduler waits → fetch again → unchanged hash: record successful check and stop → changed hash: store candidate snapshot → run oasdiff → normalize findings → persist change set → apply endpoint/severity filters → notify → user reviews/acknowledges`.

Failure flows quan trọng:

- HTTP timeout/5xx: retry exponential backoff, không thay current snapshot.
- 401/403: đánh dấu `AuthenticationFailed`, không retry liên tục.
- Response không phải OpenAPI hợp lệ: giữ snapshot cũ và tạo health warning.
- Diff process timeout/crash: snapshot mới được giữ ở trạng thái `PendingDiff`; job có thể retry idempotently.
- Notification fail: diff vẫn được commit; notification có retry riêng.
- Provider trả cùng contract nhưng JSON formatting/order khác: canonicalization/hash phải tránh tạo false change nếu có thể.

## 8. Kiến trúc đề xuất

Dùng **modular monolith**.

- **Frontend:** Vue 3 SPA nhỏ cho Watch list, detail và change timeline.
- **Backend:** ASP.NET Core Web API chứa Watch, Snapshot, Diff và Notification modules.
- **Database:** PostgreSQL cho metadata và normalized findings.
- **Background worker:** `BackgroundService` cho MVP; polling theo `NextCheckAt`.
- **Scheduler:** chưa cần Hangfire nếu chỉ có một process và vài chục watches.
- **Queue:** chưa cần. Database đóng vai trò durable work state.
- **Cache:** chưa cần; workload nhỏ.
- **File storage:** MVP có thể lưu compressed spec trong PostgreSQL `bytea` hoặc text; khi snapshot tăng nhiều mới chuyển object storage.
- **Authentication:** MVP personal/self-hosted có thể dùng single-user auth hoặc reverse-proxy auth; không cần identity platform phức tạp.
- **Diff engine:** gọi `oasdiff` executable/container với timeout và output JSON.
- **Notification:** Telegram Bot hoặc generic webhook.
- **Logging:** structured logging + health endpoint.
- **Deployment:** Docker Compose gồm app + PostgreSQL.

## 9. Công nghệ đề xuất

**.NET 10 + ASP.NET Core:** phù hợp vì đây là phiên bản .NET LTS hiện hành trong 2026 và stack tự nhiên cho HTTP, hosted services và OpenAPI. Alternative đơn giản hơn là một .NET console worker trước khi có UI. Chỉ cần tách worker thành service riêng khi số watch/job tăng đến mức ảnh hưởng web process.

**EF Core + PostgreSQL:** schema nhỏ, migration thuận tiện, JSONB hữu ích nếu muốn giữ raw normalized diff. SQLite đơn giản hơn cho single-user local MVP; chuyển PostgreSQL khi deploy lâu dài hoặc cần concurrency.

**Vue 3 + Vite:** đủ nhẹ cho dashboard. Alternative nhanh nhất là Razor Pages, thậm chí nên dùng Razor Pages nếu mục tiêu là ship MVP sớm hơn học frontend.

**`oasdiff`:** reuse semantic diff engine đã hỗ trợ OpenAPI 3.1 và machine-readable output. Alternative là tự dùng OpenAPI.NET rồi viết rules, nhưng đó là scope trap. Chỉ thay engine nếu cần rule semantics đặc thù.

**Docker Compose:** tái lập deployment dễ dàng trên VPS/mini PC. Không cần Kubernetes.

**xUnit + Testcontainers:** integration test PostgreSQL và HTTP flows sát production hơn.

**Playwright:** chỉ cần vài E2E smoke tests cho create watch → change visible.

## 10. Thiết kế dữ liệu ban đầu

### `ApiWatch`

Mục đích: cấu hình một API cần theo dõi.

Fields chính: `Id`, `Name`, `SpecUrl`, `IntervalMinutes`, `Enabled`, `NextCheckAt`, `LastCheckedAt`, `LastSuccessAt`, `CurrentSnapshotId`, `CreatedAt`.

Quan hệ: 1-N với `ApiSnapshot`, 1-N với `ChangeSet`.

### `ApiSnapshot`

Mục đích: immutable copy của contract tại một thời điểm.

Fields: `Id`, `ApiWatchId`, `ContentHash`, `OpenApiVersion`, `Content`, `FetchedAt`, `ETag`, `LastModified`.

Retention: giữ snapshot đầu tiên, snapshot hiện tại và snapshot có change; có thể xóa intermediate duplicate/old snapshots sau 30–90 ngày.

### `ChangeSet`

Mục đích: kết quả so sánh hai snapshot.

Fields: `Id`, `ApiWatchId`, `BaseSnapshotId`, `RevisionSnapshotId`, `Status`, `BreakingCount`, `CreatedAt`, `AcknowledgedAt`.

### `ContractChange`

Mục đích: một finding có thể query/filter.

Fields: `Id`, `ChangeSetId`, `RuleId`, `Severity`, `Path`, `HttpMethod`, `Message`, `RawJson`.

Không cần schema lớn hơn cho MVP.

## 11. API và tích hợp

### OpenAPI endpoint của provider

Purpose: nguồn contract. Authentication MVP: public/no-auth. Cost: thường không tính tiền nhưng phải poll có trách nhiệm. Privacy: spec có thể tiết lộ API surface; self-hosted giúp giữ dữ liệu trong hệ thống của người dùng. Fallback: upload file/manual check nếu URL unavailable — để Phase 2.

### oasdiff

Purpose: semantic diff và breaking-change detection. Không cần authentication. Open-source Apache-2.0 theo repository hiện tại. Tool hỗ trợ JSON/YAML/Markdown và OpenAPI 3.1; release gần đây vẫn đang bổ sung rule detection, nên cần pin version để kết quả không tự thay đổi sau upgrade.

Nguồn: https://github.com/oasdiff/oasdiff và https://github.com/oasdiff/oasdiff/releases

Fallback: nếu binary fail, giữ snapshot ở trạng thái chờ và retry; không tự kết luận “safe”.

### Telegram Bot API / generic webhook

Purpose: cảnh báo. Token là secret và phải mã hóa/đưa qua environment variable. Notification không được quyết định transaction thành công của diff. Nếu unavailable, giữ `NotificationPending` và hiển thị alert trên dashboard.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem là deterministic: fetch spec, hash, semantic diff, filter và notify. Dùng LLM để quyết định breaking/non-breaking sẽ kém tin cậy hơn rule engine.

AI có thể là tính năng Later để giải thích một change bằng ngôn ngữ dễ hiểu hoặc đề xuất migration checklist, nhưng kết quả phải được coi là advisory và không được override severity từ deterministic engine.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác nhận pain point. **Tasks:** hỏi 3–5 backend developer họ theo dõi API changes thế nào; lấy 3 public/internal OpenAPI specs dùng thử; chạy `oasdiff` thủ công trên version history. **Output:** danh sách workflow thật và 2–3 sample drift cases. **Done khi:** ít nhất hai người nói họ sẽ dùng watcher hoặc bạn tự chứng minh nó tiết kiệm công việc lặp lại hàng tuần.

### Phase 1 — Core MVP

**Goal:** một URL chạy end-to-end. **Tasks:** CRUD Watch, fetch, hash, snapshot, scheduled polling, invoke oasdiff, persist findings, simple dashboard. **Output:** thay spec fixture sẽ tạo visible change. **Done khi:** demo local từ URL A → update fixture → dashboard thấy breaking change mà không thao tác DB.

### Phase 2 — Reliability

**Goal:** chạy nhiều ngày không cần babysit. **Tasks:** timeout, retry, idempotency, validation, conditional requests, notification retry, tests, SSRF protection. **Output:** worker chịu được network/provider failure. **Done khi:** failure-path test suite pass và restart process không tạo duplicate change set.

### Phase 3 — Useful expansion

**Goal:** giảm noise. **Tasks:** path/method subscription, acknowledgement, non-breaking changelog, generic webhook, retention cleanup. **Output:** notification chỉ chứa contract changes liên quan consumer. **Done khi:** theo dõi 5 API trong một tuần với alert có thể hành động.

### Phase 4 — Production readiness

**Goal:** self-host ổn định. **Tasks:** Docker image, Compose, health checks, backup, metrics, upgrade docs, pinned diff engine version, secret handling. **Output:** deploy được lên VPS bằng một documented flow. **Done khi:** restore database + restart container khôi phục đầy đủ state.

## 14. Các bài toán kỹ thuật đáng học

1. **Reliable background processing:** học cách claim due jobs, tránh hai worker xử lý cùng watch và thiết kế cancellation/timeout đúng.
2. **Idempotency:** cùng một pair snapshot không được sinh nhiều `ChangeSet` khi process restart.
3. **External HTTP resilience:** conditional request, timeout, retry classification, response-size limits và circuit-like behavior.
4. **Secure URL fetching / SSRF:** URL do user nhập có thể trỏ vào localhost/cloud metadata/private network; đây là bài học security rất thực tế.
5. **Tool process isolation:** gọi `oasdiff` an toàn, giới hạn execution time, parse output có version và xử lý tool upgrade.

## 15. Rủi ro và cách xử lý

**Scope expansion:** rất dễ biến thành API management platform. Mitigation: MVP chỉ watcher + history + one notification channel.

**False/noisy alerts:** provider có thể regenerate spec với thay đổi không ảnh hưởng consumer. Mitigation: semantic diff thay raw text diff, endpoint filter và acknowledgement.

**SSRF:** fetch arbitrary URL là rủi ro lớn nhất nếu public SaaS. Mitigation: MVP self-hosted; chỉ `https`; resolve DNS và block loopback/link-local/private CIDR nếu expose multi-user; giới hạn redirect.

**Sensitive specs:** internal API contract có thể chứa thông tin không muốn gửi ra ngoài. Mitigation: local processing, không upload spec sang third party, encryption-at-rest nếu cần.

**Diff engine dependency:** behavior thay đổi giữa releases. Mitigation: pin version và lưu `DiffEngineVersion` trong ChangeSet.

**Provider không có OpenAPI:** không giải quyết được. Không dùng browser scraping để bù trong MVP.

**Adoption:** developer có thể thấy CI đã đủ. Mitigation: validate consumer-side use case trước; nếu không có demand, giữ nó làm personal utility thay vì SaaS.

## 16. Kiểm thử

Unit test cho canonical hashing, scheduling, filter và state transitions. Integration test dùng `WebApplicationFactory`, PostgreSQL/Testcontainers và fake HTTP server. E2E Playwright chỉ cover critical UI flow. Failure-path test đặc biệt quan trọng hơn số lượng UI test.

Năm scenario quan trọng nhất:

1. Initial fetch tạo snapshot nhưng không tạo breaking alert.
2. Spec thay đổi bằng một known breaking fixture → đúng một ChangeSet và đúng finding.
3. Cùng revision được xử lý lại sau simulated crash → không duplicate ChangeSet/notification.
4. Provider timeout/500 → current snapshot không bị thay và job được retry đúng policy.
5. URL trỏ vào blocked private/loopback destination → request bị từ chối trước khi fetch.

## 17. Cách đo dự án có hữu ích hay không

- **Usage:** số API Watch active được kiểm tra liên tục ít nhất 14 ngày.
- **Useful signal:** số change alerts thực sự được mở/acknowledge.
- **Time saved:** số lần người dùng không còn phải mở Swagger/release note thủ công; có thể hỏi self-report theo tuần.
- **Task completion:** ≥95% scheduled checks hoàn thành hoặc được phân loại lỗi rõ ràng trong cửa sổ dự kiến.
- **Noise:** tỷ lệ alert bị đánh dấu irrelevant; mục tiêu ban đầu <30%, sau endpoint filtering <15%.
- **Reliability:** không duplicate ChangeSet/notification qua restart/retry.
- **Retention:** người dùng vẫn giữ watcher enabled sau 30 ngày quan trọng hơn page views.

Không có AI quality metric vì MVP không dùng AI.

## 20. Việc cần làm ngay hôm nay

**Coding session: 90–120 phút.** Mục tiêu duy nhất: tạo vertical slice có thể nhập hai OpenAPI fixture và nhận được breaking-change result qua API.

### Setup

```bash
mkdir ContractPulse
cd ContractPulse
dotnet new sln -n ContractPulse
dotnet new webapi -n ContractPulse.Api -o src/ContractPulse.Api
dotnet new xunit -n ContractPulse.Tests -o tests/ContractPulse.Tests
dotnet sln add src/ContractPulse.Api/ContractPulse.Api.csproj
dotnet sln add tests/ContractPulse.Tests/ContractPulse.Tests.csproj
dotnet add tests/ContractPulse.Tests/ContractPulse.Tests.csproj reference src/ContractPulse.Api/ContractPulse.Api.csproj
mkdir fixtures
```

Cài `oasdiff` theo hướng dẫn chính thức hoặc chạy bằng Docker để tránh phụ thuộc local installation:

```bash
docker run --rm tufin/oasdiff --help
```

### Files/components cần tạo

- `fixtures/base.yaml`
- `fixtures/revision.yaml` — cố ý thêm một required request property.
- `src/ContractPulse.Api/Contracts/BreakingChange.cs`
- `src/ContractPulse.Api/Services/IOpenApiDiffService.cs`
- `src/ContractPulse.Api/Services/OasDiffService.cs`
- `src/ContractPulse.Api/Endpoints/DiffEndpoints.cs`
- `tests/ContractPulse.Tests/OasDiffServiceTests.cs`

### First vertical slice

Implement `POST /api/diff` nhận hai local fixture names trong development mode. Service gọi `oasdiff breaking ... --format json`, capture stdout/stderr + exit code, deserialize findings tối thiểu thành JSON response. Chưa database, chưa scheduler, chưa frontend.

### Expected result

```bash
curl -X POST http://localhost:5000/api/diff \
  -H "Content-Type: application/json" \
  -d '{"base":"base.yaml","revision":"revision.yaml"}'
```

Response phải cho thấy ít nhất một breaking change từ fixture revision.

### Verification checklist

- [ ] Solution build thành công.
- [ ] `oasdiff` chạy được từ execution environment đã chọn.
- [ ] Endpoint trả structured JSON, không chỉ raw stdout.
- [ ] Breaking fixture tạo ít nhất một finding.
- [ ] Hai spec giống nhau trả zero findings.
- [ ] Tool timeout/error được map thành HTTP error có message rõ ràng.
- [ ] Có ít nhất một automated test pass.

### Stop condition

**Dừng session ngay khi** một automated test và một `curl` call đều chứng minh được `base spec → changed spec → structured breaking-change result`. Không thêm PostgreSQL, scheduler, authentication, Telegram, Vue hay AI trong buổi đầu. Vertical slice này đủ để xác nhận technical core trước khi mở rộng.
