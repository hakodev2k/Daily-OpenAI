# Ý tưởng hôm nay: LicenseDelta — NuGet License Change & Dependency Policy Guard

## 1. Tóm tắt ý tưởng

LicenseDelta là một developer tool dành cho dự án .NET giúp **snapshot toàn bộ dependency graph cùng license metadata, phát hiện license thay đổi giữa hai lần restore/upgrade và chặn những thay đổi vi phạm policy trước khi merge**. Công cụ tập trung vào bài toán mà vulnerability scanner không giải quyết đầy đủ: package hoặc transitive dependency có thể đổi license, xuất hiện license chưa được phê duyệt, hoặc chuyển từ SPDX expression sang custom license file mà developer không để ý.

- Người dùng chính: solo developer hoặc team nhỏ xây sản phẩm .NET có nhiều NuGet dependencies.
- Bài toán chính: license/compliance drift âm thầm xảy ra khi dependency graph thay đổi.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

### Confirmed facts

NuGet hỗ trợ khai báo license bằng SPDX expression hoặc license file trong package metadata. NuGet Registration API cũng expose `licenseExpression`, package version, dependency groups và các metadata liên quan, nên việc thu thập license information bằng code là khả thi mà không cần scrape giao diện web.

Nguồn:

- Microsoft Learn — `.nuspec` license metadata: https://learn.microsoft.com/en-us/nuget/reference/nuspec
- Microsoft Learn — NuGet Registration API: https://learn.microsoft.com/en-us/nuget/api/registration-base-url-resource

.NET CLI hiện hỗ trợ liệt kê cả top-level và transitive dependencies bằng `dotnet package list --include-transitive` trên .NET 10; với SDK cũ hơn dùng dạng `dotnet list package`.

Nguồn:

- Microsoft Learn — `dotnet package list`: https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-list

GitHub Dependency Review Action đã có khả năng allow/deny SPDX licenses khi dependency thay đổi trong pull request. Điều này xác nhận license policy là một use case thực tế trong software supply-chain review.

Nguồn:

- GitHub Docs — Configuring dependency review action: https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/manage-your-dependency-security/configure-dependency-review-action

### Observation

Developer thường quan tâm nhiều hơn đến CVE, outdated package và breaking API changes. License metadata ít được nhìn thấy trong workflow hàng ngày, đặc biệt với transitive dependencies.

Một upgrade tưởng như đơn giản:

```text
Package A 4.2 -> 4.3
```

có thể làm dependency tree đổi thành:

```text
Package A 4.3
  -> Package B 2.1
  -> Package C 5.0
```

Nếu `Package C` mang license mà dự án không muốn sử dụng, developer có thể chỉ phát hiện muộn khi audit release hoặc review legal/compliance.

### Current workaround

Người dùng hiện có thể:

- kiểm tra license thủ công trên NuGet.org;
- dùng GitHub Dependency Review;
- dùng SBOM/license scanners;
- chạy `dotnet package list --include-transitive` rồi tự đối chiếu;
- duy trì allowlist bằng spreadsheet hoặc documentation.

Các phương pháp này có ích nhưng workflow vẫn bị phân mảnh nếu developer muốn một tool nhỏ, local-first và .NET-first để trả lời ba câu hỏi rất cụ thể:

1. Dependency graph vừa thay đổi ở đâu?
2. License nào vừa xuất hiện hoặc thay đổi?
3. Thay đổi đó có vi phạm policy của project không?

### Assumption cần validation

Team nhỏ và solo developer sẽ thấy đủ giá trị nếu công cụ chạy được cả local CLI lẫn CI mà không cần SaaS account hoặc upload source/dependency data ra ngoài.

## 3. Người dùng mục tiêu

**Primary user:** backend .NET developer vận hành một hoặc nhiều repository thương mại/personal product có NuGet dependencies.

### Context of use

- Upgrade package định kỳ.
- Merge Dependabot/Renovate PR.
- Chuẩn bị release.
- Kiểm tra dependency mới trước khi thêm vào project.

### Main pain point

Developer biết package version thay đổi nhưng không có một diff rõ ràng về license impact của toàn dependency graph.

### Current workaround

Mở NuGet package page, đọc license từng package, chạy scanner khác hoặc bỏ qua nếu thay đổi có vẻ nhỏ.

### Reason they would try LicenseDelta

Một command duy nhất:

```bash
licensedelta check MySolution.sln
```

trả về:

```text
+ New dependency: Foo.Bar 3.1.0
  License: LGPL-3.0-only
  Policy: DENIED
  Introduced by: Example.Client 8.2.0

~ License changed:
  Acme.Parser 4.0.0: MIT
  Acme.Parser 5.0.0: Apache-2.0
  Policy: ALLOWED

Result: FAIL
```

## 4. Giải pháp đề xuất

LicenseDelta gồm một CLI và optional web dashboard nhỏ.

### Main workflow

User chạy:

```bash
licensedelta snapshot MySolution.sln
```

Tool:

1. Restore solution.
2. Lấy dependency graph gồm direct + transitive dependencies.
3. Query NuGet metadata cho từng package/version.
4. Normalize license expression.
5. Lưu snapshot vào `.licensedelta/lock.json`.

Sau khi upgrade package, user chạy:

```bash
licensedelta check MySolution.sln
```

Tool tạo dependency graph mới, so với baseline và trả về:

- package mới;
- package bị remove;
- version thay đổi;
- license expression thay đổi;
- custom/unknown license;
- policy violation;
- dependency path đã introduce package đó.

### Input

- `.sln` hoặc `.csproj`.
- Policy file:

```yaml
allowed:
  - MIT
  - Apache-2.0
  - BSD-2-Clause
  - BSD-3-Clause

denied:
  - GPL-3.0-only
  - AGPL-3.0-only

unknownLicense: warn
customLicenseFile: review
```

### Processing

Deterministic pipeline:

```text
Resolve packages
→ collect NuGet metadata
→ normalize SPDX expressions
→ build dependency graph
→ compare baseline/current
→ evaluate policy
→ render report
```

### Output

- terminal report;
- JSON report cho CI;
- Markdown report cho PR/comment integration về sau;
- exit code `0` nếu pass và khác `0` nếu policy fail.

### User control

Tool không tự quyết định package nào “tốt” hoặc “xấu”. User sở hữu policy và có thể approve exception cụ thể theo package/version.

### Key differentiator

Không cố thay thế SBOM scanner hay GitHub Dependency Review. Điểm khác biệt là **license-diff history cho NuGet dependency graph**, chạy local-first, giải thích package nào đã kéo transitive license mới vào và tạo baseline version-controlled giống lockfile.

### Ví dụ end-to-end

Developer có project dùng:

```text
Some.Client 6.0
```

Baseline không có `Helper.Native`.

Sau khi upgrade lên `Some.Client 7.0`, LicenseDelta phát hiện:

```text
Some.Client 7.0
└── Helper.Native 2.0
```

`Helper.Native` có license ngoài allowlist.

CI fail và chỉ rõ dependency path. Developer có ba lựa chọn:

- rollback upgrade;
- evaluate license rồi thêm exception;
- tìm package alternative.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Tool có thể dùng ngay trên bất kỳ .NET repository cá nhân nào có NuGet dependencies. Giá trị không phụ thuộc vào việc có nhiều user.

### Technical learning value

Dự án chạm vào:

- NuGet protocol/API;
- dependency graph resolution;
- SPDX expression parsing;
- deterministic snapshots;
- CI exit semantics;
- caching và rate limiting;
- supply-chain tooling.

### Vì sao phù hợp solo developer

Core MVP chỉ cần CLI + file snapshot + NuGet metadata. Không cần account system, payment, mobile app hoặc microservices.

### Điều gì khiến dự án thất bại

Nếu GitHub Dependency Review hoặc existing SBOM tools đã đáp ứng hoàn toàn workflow của target user, tool mới không đủ khác biệt.

### Lý do mạnh nhất để không build

License compliance là domain có yếu tố pháp lý. Công cụ phải được định vị rõ là **engineering policy checker**, không phải legal advice. Nếu cố đưa ra kết luận pháp lý tự động, maintenance và risk tăng mạnh.

## 6. Phạm vi MVP

### Must have

- CLI nhận `.sln` hoặc `.csproj`.
- Resolve direct + transitive NuGet dependencies.
- Đọc `licenseExpression` từ NuGet metadata.
- Nhận diện package dùng custom license file hoặc không có license expression.

- Diff baseline với current dependency graph.
- Policy allow/deny/warn.

### Should have

- Cache NuGet metadata local.
- Exception theo package/version.
- Markdown report.
- `--no-restore` mode.
- Detect deprecated packages và basic vulnerability metadata nếu API đã có sẵn, nhưng không biến đây thành vulnerability scanner.

### Later

- GitHub PR comment.
- SBOM import/export CycloneDX/SPDX.
- Dashboard history.
- Multi-repository view.
- License text hash diff.
- Support npm/pnpm/Maven.
- Central organization policy server.

## 7. Luồng hoạt động

### Baseline flow

User chọn solution
→ validate path
→ restore project
→ resolve dependency graph
→ query package metadata
→ normalize licenses
→ save baseline snapshot
→ show summary.

### Check flow

User/CI chạy check
→ build current dependency graph
→ load baseline
→ calculate dependency + license diff
→ apply policy
→ render terminal/JSON report
→ return exit code.

### Important alternative flows

**NuGet API unavailable:** dùng metadata cache nếu còn; đánh dấu package `unverified` thay vì giả định license.

**Private NuGet feed:** metadata resolver cần dùng authenticated package source hoặc đọc `.nupkg` local cache khi có thể.

**Custom license file:** không tự kết luận loại license; status là `manual-review-required`.

**SPDX compound expression:** parser giữ nguyên semantics của `AND`, `OR`, `WITH`; policy evaluator không được treat chuỗi như simple substring.

**Multi-targeting:** deduplicate package/version nhưng giữ framework origins để giải thích package chỉ xuất hiện ở `net10.0` hay target khác.

## 11. API và tích hợp

### NuGet Registration API

**Purpose:** lấy package version, dependency groups, `licenseExpression`, vulnerability metadata và package URL metadata.

**Authentication:** không cần với nuget.org public feed.

**Cost/rate concern:** API public nên vẫn cần cache, timeout và retry hợp lý; không giả định unlimited throughput.

**Privacy:** chỉ gửi package ID/version, không gửi source code.

**Fallback:** local NuGet package/cache hoặc status `metadata-unavailable`.

Nguồn: https://learn.microsoft.com/en-us/nuget/api/registration-base-url-resource

### NuGet CLI/.NET CLI

**Purpose:** resolve package graph theo project thực tế, bao gồm transitive packages.

**Authentication:** private source có thể cần credentials do NuGet config quản lý.

**Fallback:** parse `project.assets.json` sau restore để có resolved graph.

### GitHub Actions

**Purpose:** CI enforcement.

Không cần GitHub API trong MVP; command chỉ cần trả exit code.

### GitHub Dependency Review

Không phải dependency bắt buộc. Có thể document cách dùng song song: GitHub Dependency Review kiểm tra PR dependency changes, LicenseDelta giữ baseline/diff local và .NET-specific explainability.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Dependency resolution, SPDX expression evaluation, policy matching và diff đều deterministic.

AI có thể được thêm sau để viết explanation thân thiện hơn, nhưng không nên quyết định policy.

Nếu có optional AI sau này:

- input: deterministic diff + package metadata;
- output: explanation text;
- validation: chỉ cho phép AI diễn giải facts đã có;
- fallback: template-based explanation;
- risk: hallucination về legal implications là lý do mạnh để giữ AI ngoài core workflow.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** chứng minh license-diff thật sự xuất hiện trong repository thực tế.

**Tasks:**

- Chọn 2–3 .NET projects cá nhân.
- Resolve full transitive dependency list.

**Expected output:** một JSON prototype chứa package graph + license.

**Completion criteria:** ít nhất một upgrade tạo graph diff mà không dễ nhìn thấy chỉ từ `.csproj`.

### Phase 1 — Core MVP

**Goal:** `snapshot` và `check` chạy end-to-end.

**Tasks:** CLI, resolver, NuGet metadata client, snapshot serializer, diff engine, policy evaluator.

**Expected output:** CI có thể fail khi dependency mới mang denied license.

**Completion criteria:** demo project pass baseline, sau khi thêm test package vi phạm thì command fail với dependency path đúng.

### Phase 2 — Reliability

**Goal:** tool đáng tin khi chạy CI.

**Tasks:** retry, timeout, local cache, corrupted cache handling, deterministic serialization, multi-target framework tests, private-feed error reporting.

**Expected output:** network failure không tạo false pass.

**Completion criteria:** failure scenarios có explicit status và exit code ổn định.

### Phase 3 — Useful expansion

**Goal:** giảm friction cho developer.

**Tasks:** Markdown report, exception workflow, package-path visualization, `--format json|markdown|text`, baseline schema migration.

**Expected output:** report đủ rõ để paste thẳng vào PR.

### Phase 4 — Production readiness

**Goal:** public/open-source usable release.

**Tasks:** GitHub Actions CI, NuGet package/global tool publish, docs, sample policy, telemetry-off-by-default, changelog và compatibility tests.

**Completion criteria:** người khác có thể cài tool và chạy trên repo mới trong dưới 10 phút.

## 14. Các bài toán kỹ thuật đáng học

### 1. Dependency graph resolution

Không chỉ list package; cần giữ edge để trả lời “package nào kéo dependency này vào”. Kỹ năng: graph modeling, cycle handling, multi-target frameworks.

### 2. SPDX expression parsing

`MIT OR Apache-2.0` khác hoàn toàn `MIT AND Apache-2.0`. Kỹ năng: parser/evaluator, domain modeling, deterministic policy semantics.

### 3. Reproducible snapshots

Hai runs cùng input cần tạo output ổn định để Git diff không nhiễu. Kỹ năng: canonical ordering, schema versioning, reproducible tooling.

### 4. NuGet protocol + caching

Metadata cho hàng trăm transitive dependencies dễ tạo nhiều requests. Kỹ năng: HTTP caching, batching, rate-awareness, retry và offline behavior.

### 5. Fail-safe CI design

Metadata unavailable không được biến thành green build một cách im lặng. Kỹ năng: fail-open vs fail-closed trade-offs, exit codes, error classification.

## 15. Rủi ro và cách xử lý

### Legal interpretation risk

**Risk:** user hiểu report là kết luận pháp lý.

**Mitigation:** tool chỉ evaluate user-defined policy; luôn ghi rõ “not legal advice”; custom license luôn manual review.

### Missing/inaccurate metadata

**Risk:** package thiếu `licenseExpression` hoặc dùng license file.

**Mitigation:** trạng thái `UNKNOWN`/`CUSTOM`, không đoán license bằng AI.

### False positives từ compound licenses

**Risk:** parser policy xử lý `AND/OR` sai.

**Mitigation:** dùng parser chuẩn, test matrix lớn và preserve original expression.

### Private feed complexity

**Risk:** credentials và metadata format khác nhau.

**Mitigation:** MVP ưu tiên nuget.org; private feed support chỉ sử dụng standard NuGet credential/config behavior.

### Scope expansion

**Risk:** biến thành full SCA/security platform.

**Mitigation:** core scope là license drift + dependency policy; vulnerability/SBOM chỉ là integrations phụ.

### Maintenance burden

**Risk:** NuGet API/SDK behavior thay đổi.

**Mitigation:** abstraction `IPackageMetadataSource`, contract tests và pin SDK compatibility matrix.

## 16. Kiểm thử

### Testing strategy

- Unit tests: SPDX policy, graph diff, exception rules.
- Integration tests: NuGet registration metadata và `project.assets.json` parser.
- E2E tests: sample solution snapshot → package change → check.
- Failure-path tests: timeout, missing metadata, malformed policy, corrupted baseline.
- Security tests: path traversal trong output/cache path, unsafe secret logging từ private feeds.
- Data-quality tests: package/version/license mapping đúng với known fixture set.

### 5 test scenarios quan trọng nhất

1. Direct package mới có allowed license → PASS.
2. Transitive package mới có denied license → FAIL và dependency path đúng.
3. Package version đổi nhưng license không đổi → report version diff, không false policy alert.
4. License expression đổi từ `MIT` sang `GPL-3.0-only` → FAIL rõ ràng.
5. NuGet metadata unavailable → không silently PASS; trả `UNKNOWN` theo configured policy.

### First vertical slice

Chọn một sample `.csproj`, chạy restore và đọc `obj/project.assets.json`.

Extract tối thiểu:

```text
PackageId
Version
DirectOrTransitive
```

Sau đó query NuGet Registration API cho từng package/version và lấy:

```text
licenseExpression
```

Terminal output kỳ vọng:

```text
PACKAGE                         VERSION      TYPE         LICENSE
Microsoft.Extensions.Http       10.0.0       Direct       MIT
Polly                            8.x.x        Transitive   BSD-3-Clause
Example.Package                  1.x.x        Transitive   UNKNOWN
```

### Verification checklist

- [ ] Đọc được package list từ một real `.csproj` sau restore.
- [ ] Có cả direct và ít nhất một transitive dependency.
- [ ] Query được `licenseExpression` cho package public trên nuget.org.
- [ ] Package không có expression được hiển thị `UNKNOWN`, không crash.
- [ ] Output được sort deterministic theo package ID + version.
- [ ] Có ít nhất một unit test cho metadata mapping hoặc package asset parsing.

### Stop condition

Dừng session khi command kiểu:

```bash
dotnet run --project src/LicenseDelta.Cli -- ./SampleApp/SampleApp.csproj
```

in ra được dependency table có license metadata cho một project thật. Không làm UI, database, GitHub integration, SBOM hoặc AI trong session đầu tiên.
