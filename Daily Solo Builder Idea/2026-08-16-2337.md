# Ý tưởng hôm nay: API Contract Drift Guard

## 1. Tóm tắt ý tưởng

**API Contract Drift Guard** là một công cụ self-hosted theo dõi OpenAPI contract của các API nội bộ hoặc public, so sánh phiên bản mới với baseline gần nhất, phát hiện breaking changes và tạo báo cáo tập trung vào **consumer impact** thay vì chỉ hiển thị diff kỹ thuật. Người dùng chính là developer hoặc team nhỏ có nhiều API/client nhưng chưa có API governance phức tạp.

- **Project size:** Medium
- **Estimated MVP time:** 2–3 tuần làm ngoài giờ
- **Giá trị cốt lõi:** phát hiện sớm thay đổi API có khả năng làm hỏng frontend, mobile app, integration hoặc service downstream trước khi deploy.

## 2. Bài toán thực tế

### Confirmed facts

ASP.NET Core từ .NET 9 có built-in OpenAPI support; `Microsoft.AspNetCore.OpenApi` hỗ trợ sinh OpenAPI ở runtime và `Microsoft.Extensions.ApiDescription.Server` hỗ trợ sinh tài liệu OpenAPI ở build time. Microsoft cũng nêu rõ build-time OpenAPI có thể dùng cho spec-based integration testing hoặc commit vào source control.

Nguồn: [Microsoft Learn — Generate OpenAPI documents](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/openapi/aspnetcore-openapi?view=aspnetcore-10.0)

`oasdiff` là một dự án open-source chuyên so sánh OpenAPI và phát hiện breaking changes. Công cụ hỗ trợ các mức `ERR`, `WARN`, `INFO`, có thể chạy trong CI và trả exit code lỗi để chặn pipeline khi phát hiện thay đổi nguy hiểm.

Nguồn: [oasdiff — Breaking Changes](https://github.com/oasdiff/oasdiff/blob/main/docs/BREAKING-CHANGES.md)

### Observation

Việc một công cụ như `oasdiff` tồn tại và tập trung vào CI cho thấy API contract compatibility là một vấn đề đủ phổ biến để có tooling riêng. Tuy nhiên output dạng diff vẫn chủ yếu trả lời câu hỏi **“spec thay đổi gì?”**, trong khi developer thường cần thêm câu hỏi thực dụng hơn:

- Client nào có thể bị ảnh hưởng?
- Endpoint nào có consumer đang sử dụng?
- Breaking change có thực sự đáng chặn release không?
- Team nào cần được báo?
- Có thay đổi nào đã xảy ra ngoài CI do một environment đang chạy contract khác với source control không?

### Bài toán cụ thể

Trong hệ thống có backend API cùng frontend, mobile, integration hoặc nhiều service downstream, API contract có thể thay đổi qua:

- đổi field từ optional sang required;
- xóa hoặc rename property;
- đổi enum;
- thay response status;
- xóa endpoint;
- đổi parameter;
- thay schema type;
- thay contract trực tiếp ở environment mà không có baseline rõ ràng.

Hiện tại developer thường xử lý bằng review code, Swagger UI, integration test hoặc phản ứng sau khi client lỗi. Những cách này phân tán và phụ thuộc nhiều vào việc reviewer nhớ được contract cũ.

### Assumption cần validation

MVP giả định rằng team nhỏ có 2–10 API hoặc client integration sẽ thấy hữu ích nếu có một dashboard đơn giản lưu contract history và gửi cảnh báo khi breaking change xuất hiện. Giả định này cần kiểm chứng bằng 3–5 developer/team thực tế trước khi đầu tư sâu.

## 3. Người dùng mục tiêu

### Primary user

Backend developer hoặc Tech Lead trong team 3–15 người đang vận hành ASP.NET Core API và có ít nhất một consumer độc lập như frontend, mobile app, external integration hoặc service khác.

### Context of use

- API deploy nhiều lần mỗi tuần.
- OpenAPI/Swagger đã tồn tại.
- Team chưa có dedicated API platform hoặc API governance tooling.
- Breaking changes chủ yếu được bắt qua code review, QA hoặc bug sau deploy.

### Main pain point

Developer không có một nơi trả lời nhanh: **“Contract mới có làm hỏng consumer hiện tại không?”**

### Current workaround

- review Swagger thủ công;
- chạy regression test;
- đọc PR diff;
- giữ file OpenAPI trong repo;
- dùng CLI diff riêng lẻ;
- chờ consumer báo lỗi.

### Lý do họ sẽ thử giải pháp

MVP chỉ yêu cầu cung cấp OpenAPI URL hoặc upload spec, không cần thay đổi kiến trúc hệ thống. Giá trị có thể nhìn thấy ngay sau lần contract thứ hai được scan.

## 4. Giải pháp đề xuất

API Contract Drift Guard hoạt động như một **contract history + compatibility monitor**.

### Workflow chính

1. User tạo một API project.
2. Nhập OpenAPI URL, ví dụ `https://api.example.com/openapi/v1.json`, hoặc upload file JSON/YAML.
3. Hệ thống lấy contract và canonicalize nội dung để loại bỏ noise.
4. Contract đầu tiên trở thành baseline.
5. Lần scan tiếp theo, hệ thống chạy diff bằng `oasdiff`.
6. Kết quả được normalize thành danh sách change có severity.
7. Dashboard hiển thị:
   - breaking changes;
   - warnings;
   - affected endpoint/schema;
   - version trước/sau;
   - thời điểm phát hiện.
8. Nếu có `ERR` hoặc `WARN`, gửi Telegram/Slack/email tùy cấu hình.
9. User có thể đánh dấu change là `Acknowledged`, `Accepted` hoặc `Needs Fix`.

### Input

- OpenAPI URL hoặc file OpenAPI.
- Optional authentication header/token.
- Scan schedule.
- Severity threshold.

### Processing

- fetch spec;
- validate;
- normalize/canonicalize;
- hash;
- skip nếu không thay đổi;
- compare với baseline;
- parse diff;
- persist report;
- evaluate notification policy.

### Output

- contract snapshot;
- structured change report;
- severity;
- endpoint/schema affected;
- notification.

### Phần tự động hóa

- scheduled contract retrieval;
- hash comparison;
- breaking-change detection;
- report generation;
- notification.

### Phần user vẫn kiểm soát

- baseline nào được coi là approved;
- severity threshold;
- acknowledgement;
- scan interval;
- credentials;
- API nào được theo dõi.

### Key differentiator

Không xây lại engine diff. MVP tận dụng `oasdiff` làm detection engine và tập trung vào **history, monitoring, approval state, notification và consumer context**.

### Ví dụ end-to-end

Một developer theo dõi `Employee API`.

- Baseline có response `EmployeeDto.middleName` là nullable.
- Build mới đổi field này thành required.
- Scheduler fetch OpenAPI mới lúc 12:00.
- Hash thay đổi nên hệ thống chạy `oasdiff breaking`.
- Change được phân loại là breaking.
- Dashboard hiển thị endpoint `/employees/{id}` và schema `EmployeeDto` bị ảnh hưởng.
- Telegram gửi: `Employee API: 1 breaking change detected — middleName became required`.
- Developer mở report, kiểm tra frontend và quyết định revert hoặc accept breaking change.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Công cụ giải quyết một lỗi có chi phí cao nhưng thường chỉ được phát hiện muộn: backend vẫn build/deploy thành công nhưng consumer không còn tương thích.

### Technical learning value

Dự án buộc người làm phải xử lý:

- OpenAPI parsing;
- deterministic hashing;
- external process execution;
- scheduled jobs;
- idempotency;
- diff normalization;
- secrets;
- notification delivery;
- observability;
- integration testing.

### Phù hợp solo developer

Engine breaking-change detection đã có thể tái sử dụng từ `oasdiff`, nên phạm vi sản phẩm tập trung vào orchestration và UX thay vì nghiên cứu compatibility rules từ đầu.

### Vẫn hữu ích nếu chỉ có một user

Ngay cả chỉ dùng cho các API cá nhân, công cụ vẫn có giá trị như một safety net trước deploy và một lịch sử contract tự động.

### Điều làm dự án thất bại

Nếu người dùng đã có API governance mạnh trong CI hoặc client integration test đủ tốt, dashboard riêng có thể không mang thêm nhiều giá trị.

### Lý do mạnh nhất để không build

`oasdiff` và các GitHub Action đã giải quyết tốt use case CI. Nếu validation cho thấy người dùng chỉ muốn “fail PR khi breaking” thì nên dùng trực tiếp `oasdiff` thay vì xây sản phẩm mới.

## 6. Phạm vi MVP

### Must have

- Tạo API monitor bằng OpenAPI URL.
- Manual scan.
- Scheduled scan bằng background job.
- Validate OpenAPI document.
- Snapshot contract.
- SHA-256 hash để bỏ qua spec không đổi.
- Compare current spec với previous approved snapshot bằng `oasdiff`.
- Parse kết quả JSON/YAML thành structured changes.
- Dashboard lịch sử scan.
- Trang chi tiết breaking changes.
- Severity `ERR/WARN/INFO`.
- Telegram notification khi vượt threshold.
- Mark snapshot là approved baseline.

### Should have

- Upload OpenAPI file thủ công.
- Bearer token/API key cho protected OpenAPI endpoint.
- Ignore rule cho known change.
- Webhook notification.
- Export Markdown report.
- GitHub commit/PR metadata nếu scan được trigger từ CI.

### Later

- Consumer registry.
- Mapping endpoint → client/service.
- GitHub App.
- Pull request comment.
- Multi-user/team workspace.
- Semantic behavior analysis bằng AI.
- Automatic SDK regeneration.
- GraphQL/protobuf support.

## 7. Luồng hoạt động

```text
User registers OpenAPI source
        ↓
Validate URL / credentials
        ↓
Fetch OpenAPI document
        ↓
Validate + canonicalize
        ↓
Calculate SHA-256
        ↓
Hash unchanged? ── yes ──> Save scan as NoChange
        ↓ no
Persist ContractSnapshot
        ↓
Find approved baseline
        ↓
Run oasdiff
        ↓
Parse structured result
        ↓
Persist ContractChanges
        ↓
Evaluate severity policy
        ↓
Create notification if threshold reached
        ↓
Dashboard + Telegram
```

### Alternative flows

**OpenAPI URL timeout**

- Retry tối đa 3 lần với exponential backoff.
- Không tạo snapshot mới.
- Scan status = `FetchFailed`.

**Invalid OpenAPI**

- Lưu validation error.
- Không cập nhật baseline.

**Không có baseline**

- Snapshot đầu tiên trở thành candidate baseline.
- User approve hoặc auto-approve lần đầu.

**Spec không đổi nhưng formatting thay đổi**

- Canonicalize JSON trước khi hash để hạn chế false positive.

**oasdiff process lỗi**

- Scan status `DiffFailed`.
- Giữ snapshot để retry.
- Không gửi breaking-change notification giả.

### Frontend

Vue 3 + TypeScript.

Cần vì dashboard và report history là phần tạo khác biệt so với CLI thuần.

### Backend

ASP.NET Core 10 modular monolith.

Phụ trách API, orchestration, validation, storage và notification.

### Database

PostgreSQL.

Lưu metadata monitor, scan, snapshot, structured change và notification state.

### Background worker / scheduler

Hangfire.

Cần cho scheduled fetch, retry và notification. MVP không cần queue riêng.

### Queue

**Không cần ở MVP.** Hangfire storage đã đủ để quản lý background jobs.

### Cache

**Không cần.** Workload thấp và phần lớn dữ liệu là historical read.

### File storage

Ban đầu lưu compressed OpenAPI snapshot trong database nếu mỗi spec nhỏ. Khi kích thước hoặc số snapshot tăng mới chuyển sang object storage.

### Authentication

MVP self-hosted single-user có thể dùng local admin account hoặc reverse-proxy auth. Không cần OAuth phức tạp ngay.

### AI model

Không cần cho core MVP.

### Notification

Telegram Bot API vì setup đơn giản và phù hợp cho personal/small-team tool.

### Logging / monitoring

Structured logging bằng Serilog + ASP.NET Core health checks.

### Deployment

Docker Compose trên VPS hoặc mini PC.

### .NET 10 LTS

Nguồn: [.NET Support Policy](https://dotnet.microsoft.com/en-us/platform/support/policy)

**Tại sao phù hợp:** stable platform, background processing tốt, phù hợp stack hiện có.

**Simpler alternative:** .NET 8 nếu môi trường hiện tại chưa nâng cấp, nhưng vòng support ngắn hơn tại thời điểm hiện tại.

**Outgrow:** gần như không phải bottleneck; scale issue sẽ đến từ storage/worker trước runtime.

### ASP.NET Core

REST API + web host + health check + dependency injection.

**Simpler alternative:** Minimal API thay controller nếu số endpoint nhỏ.

### Entity Framework Core + PostgreSQL

EF Core giúp migration và persistence nhanh; PostgreSQL phù hợp self-hosting.

**Simpler alternative:** SQLite cho single-user MVP local.

**Outgrow:** khi có nhiều tenant, vẫn có thể giữ PostgreSQL và tối ưu index/partition trước khi đổi kiến trúc.

### Hangfire

Thích hợp cho scheduled jobs, retry, dashboard vận hành.

**Simpler alternative:** `BackgroundService` + cron library.

**Outgrow:** khi cần throughput lớn hoặc distributed workflow phức tạp mới cân nhắc queue riêng.

### oasdiff

Dùng như external CLI process hoặc container sidecar trong giai đoạn đầu.

**Tại sao:** đã có engine breaking-change detection, output JSON/YAML/Markdown và hỗ trợ CI.

Nguồn: [oasdiff repository](https://github.com/oasdiff/oasdiff)

**Simpler alternative:** gọi binary local trực tiếp.

**Outgrow:** nếu cần custom rule sâu, có thể xây adapter hoặc tích hợp library/service riêng.

### Vue 3 + TypeScript

Dashboard đủ đơn giản để Vue phù hợp và giữ tốc độ phát triển cao.

### Docker Compose

Một container app + PostgreSQL là đủ.

### Playwright

Dùng cho E2E flow: tạo monitor → scan → xem report → approve baseline.

### GitHub Actions

Build, test và publish Docker image.

## 11. API và tích hợp

### OpenAPI endpoint

**Purpose:** nguồn contract.

**Authentication:** none, bearer token hoặc API key tùy API.

**Cost/rate limit:** thường không đáng kể nếu scan vài lần/ngày.

**Privacy:** spec có thể chứa internal endpoint/schema, nên không log raw credential và hạn chế gửi spec ra ngoài.

**Fallback:** upload JSON/YAML file hoặc đọc spec từ Git repository.

### oasdiff

**Purpose:** validation/diff/breaking-change detection.

**Authentication:** không cần khi chạy local CLI.

**Cost:** open-source CLI; chi phí là compute nhỏ.

**Privacy:** chạy local để contract không rời khỏi host.

**Fallback:** nếu process unavailable, đánh dấu scan `DiffFailed`; không tự đoán kết quả.

### Telegram Bot API

**Purpose:** notification.

**Authentication:** bot token.

**Cost/rate limit:** phù hợp lượng notification thấp; cần retry cho transient error.

**Privacy:** chỉ gửi summary, không gửi toàn bộ internal schema.

**Fallback:** dashboard-only notification hoặc generic webhook.

### ASP.NET Core build-time OpenAPI

Nếu monitor chính repo .NET, contract có thể được sinh ngay lúc build. Microsoft xác nhận `Microsoft.Extensions.ApiDescription.Server` hỗ trợ build-time OpenAPI generation và tài liệu tạo ra có thể dùng cho spec-based integration testing.

Nguồn: [Microsoft Learn — Generate OpenAPI documents](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/openapi/aspnetcore-openapi?view=aspnetcore-10.0)

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

Core breaking-change detection không cần AI vì deterministic rules đáng tin cậy hơn.

### AI task có thể thêm sau

AI chỉ nên dùng để biến structured diff thành phần giải thích dễ đọc, ví dụ:

> `customerType` changed from optional to required. Existing clients that omit this property may fail validation.

### Required context

- structured diff;
- endpoint;
- schema;
- severity rule;
- optional consumer metadata.

### Expected structured output

```json
{
  "summary": "string",
  "likelyImpact": "low|medium|high",
  "recommendedChecks": ["string"]
}
```

### Validation

- JSON Schema validation;
- AI không được thay đổi severity do `oasdiff` quyết định;
- user-facing report luôn hiển thị deterministic source change.

### Deterministic fallback

Template-based explanation từ `RuleId`, `Path`, `SchemaName`, `Message`.

### Risks

- hallucination về impact;
- tăng latency;
- chi phí API;
- nguy cơ gửi internal API schema ra external model.

Do đó AI **không nằm trong MVP**.

## 14. Các bài toán kỹ thuật đáng học

### 1. Deterministic normalization và hashing

Hai OpenAPI file có thể khác formatting nhưng semantically giống nhau. Cần canonicalization trước hash.

**Skill cải thiện:** deterministic processing, serialization, content-addressable storage.

### 2. Reliable background processing

Scheduler phải chịu được timeout, restart và temporary network errors.

**Skill cải thiện:** Hangfire, retry, idempotency, recovery.

### 3. External process orchestration

Backend gọi `oasdiff`, capture stdout/stderr, timeout và exit code.

**Skill cải thiện:** process isolation, cancellation, resource limits.

### 4. Secrets và protected endpoints

Một số OpenAPI endpoint yêu cầu auth.

**Skill cải thiện:** encryption-at-rest, secret handling, permission boundaries.

### 5. Change lifecycle

Một change có thể `Detected → Acknowledged → Accepted → BaselineApproved`.

**Skill cải thiện:** state modeling và auditability mà không cần event sourcing.

## 15. Rủi ro và cách xử lý

### Technical complexity

**Risk:** parsing output từ `oasdiff` thay đổi theo version.

**Mitigation:** pin phiên bản binary và viết adapter contract test.

### Scope expansion

**Risk:** biến dự án thành full API management platform.

**Mitigation:** MVP chỉ OpenAPI monitor + diff + notification.

### Data privacy

**Risk:** internal OpenAPI spec chứa tên endpoint/schema nhạy cảm.

**Mitigation:** local processing, no external AI mặc định, encrypt secrets, configurable snapshot retention.

### Security

**Risk:** user cung cấp URL có thể tạo SSRF.

**Mitigation:** block localhost/private network theo mode cloud; self-hosted mode cho phép allowlist; validate scheme; timeout; response-size limit.

### API dependency

**Risk:** monitored endpoint tạm thời down.

**Mitigation:** retry và phân biệt `FetchFailed` với breaking change.

### Unreliable external data

**Risk:** OpenAPI endpoint trả spec khác nhau do deployment rolling.

**Mitigation:** require cùng hash xuất hiện N lần hoặc cho phép stabilization delay trước khi alert.

### Cost

**Risk:** gần như thấp ở MVP.

**Mitigation:** scan interval tối thiểu, deduplicate bằng hash, không dùng AI mặc định.

### Legal/platform restrictions

Không crawl website; monitor endpoint do user cấu hình. Cần đảm bảo user có quyền truy cập contract đó.

### User adoption

**Risk:** developer thấy CLI đủ dùng.

**Mitigation:** validation trước build và tập trung vào use case continuous monitoring/history thay vì copy tính năng CLI.

### Maintenance burden

**Risk:** OpenAPI/oasdiff version thay đổi.

**Mitigation:** pin versions, automated compatibility tests và release cadence chậm.

## 16. Kiểm thử

### Strategy

- **Unit tests:** canonicalization, hashing, severity policy, state transitions.
- **Integration tests:** PostgreSQL, Hangfire, `oasdiff` adapter.
- **E2E tests:** Playwright cho monitor/report flow.
- **Failure-path tests:** timeout, invalid spec, binary error, Telegram failure.
- **Security tests:** SSRF protection, secret redaction, oversized response.
- **Data-quality tests:** cùng semantic spec phải cho hash/diff ổn định theo rule đã chọn.

### 5 test scenario quan trọng nhất

1. **Optional → required property** phải tạo breaking change đúng endpoint/schema.
2. **Spec chỉ đổi whitespace/order** không tạo snapshot/change mới sau canonicalization.
3. **OpenAPI endpoint timeout** không làm baseline bị thay đổi.
4. **Cùng scheduled job bị chạy hai lần** không tạo duplicate report/notification.
5. **Telegram gửi thất bại rồi retry** chỉ tạo một logical notification khi thành công.

## 20. Việc cần làm ngay hôm nay

### Development objective — 60–120 phút

> nhập hai OpenAPI files → backend chạy `oasdiff` → API trả về danh sách breaking changes → hiển thị JSON result.

### Setup commands

```bash

dotnet new sln -n ApiContractGuard

dotnet new webapi -n ApiContractGuard.Api -o src/ApiContractGuard.Api
dotnet new xunit -n ApiContractGuard.Api.Tests -o tests/ApiContractGuard.Api.Tests

dotnet sln add tests/ApiContractGuard.Api.Tests/ApiContractGuard.Api.Tests.csproj

dotnet add tests/ApiContractGuard.Api.Tests/ApiContractGuard.Api.Tests.csproj reference src/ApiContractGuard.Api/ApiContractGuard.Api.csproj

mkdir samples
```

Cài `oasdiff` bằng phương thức phù hợp với OS hoặc chạy qua Docker. Dự án chính thức cung cấp CLI và Docker usage.

Nguồn: [oasdiff repository](https://github.com/oasdiff/oasdiff)

### First vertical slice

API endpoint:

```http
POST /api/contracts/compare
Content-Type: application/json
```

Request:

```json
{
  "baselinePath": "samples/baseline.json",
  "candidatePath": "samples/candidate.json"
}
```

Backend chạy tương đương:

```bash
oasdiff breaking samples/baseline.json samples/candidate.json --format json
```

Response tối thiểu:

```json
{
  "hasBreakingChanges": true,
  "exitCode": 0,
  "rawResult": {}
}
```

Trong session đầu **chưa cần database, scheduler, Vue, auth hay Telegram**.

### Expected result

Tạo `baseline.json` và `candidate.json` trong đó candidate xóa một response property hoặc biến property thành required. Gọi endpoint và thấy breaking change trả về từ backend.

### Verification checklist

- [ ] `dotnet build` thành công.
- [ ] API chạy local.
- [ ] `oasdiff` được gọi bằng `ProcessStartInfo.ArgumentList`, không ghép shell string nguy hiểm.
- [ ] Cancellation token/timeout được truyền vào process runner.
- [ ] Candidate không đổi → không có breaking change.
- [ ] Candidate có breaking change → endpoint trả kết quả tương ứng.
- [ ] Có ít nhất một integration test cho `OasDiffRunner`.

### Stop condition

Dừng session ngay khi endpoint có thể so sánh hai sample OpenAPI documents và trả về breaking-change result ổn định. Không thêm UI, database hoặc scheduler trong buổi đầu.
