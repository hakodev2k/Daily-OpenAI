# Ý tưởng hôm nay: TabBudget — Trình quản lý “ngân sách tab” giúp giảm tab overload mà không biến thành bookmark manager

## 1. Tóm tắt ý tưởng

**TabBudget** là một browser extension cho Chrome/Chromium giúp người dùng đặt “ngân sách tab” theo domain hoặc theo nhóm công việc, ví dụ tối đa 8 tab GitHub, 5 tab tài liệu, 3 tab mạng xã hội đang mở cùng lúc. Khi vượt ngưỡng, extension không đóng tab ngay mà chuyển tab dư vào một **parking queue** có thể khôi phục, kèm thời điểm mở, tiêu đề, URL và lý do bị park.

Dự án nhắm tới developer và knowledge worker thường xuyên mở hàng chục tab rồi mất kiểm soát. Vấn đề cốt lõi không phải “lưu bookmark”, mà là **giới hạn working set đang hoạt động** và tạo một cơ chế dọn tab có thể đảo ngược.

- **Project size:** Small → Medium
- **Estimated MVP time:** 5–8 ngày làm ngoài giờ, hoặc 2–3 ngày nếu chỉ làm bản local-first rất gọn.

## 2. Bài toán thực tế

### Vấn đề hiện tại

Một browser session của developer rất dễ phình thành hàng chục tab: tài liệu API, GitHub issues, Stack Overflow, dashboard cloud, PR, ticket, video, mail, AI tool, tài liệu vendor. Người dùng thường giữ tab mở vì sợ “đóng rồi quên”, nhưng chính việc giữ quá nhiều tab làm tăng chi phí nhận thức khi tìm lại thứ đang cần.

Tab groups và bookmarks giải quyết một phần bài toán tổ chức, nhưng không trực tiếp áp dụng một quy tắc kiểu: “tôi chỉ muốn tối đa 8 tab của domain X đang active, tab dư thì chuyển sang hàng chờ có thể restore”.

### Confirmed facts

- Chrome cung cấp `chrome.tabs` API để extension tạo, cập nhật, di chuyển, reload và truy vấn tab. Việc truy cập các thuộc tính nhạy cảm như `url`, `title`, `favIconUrl` cần permission phù hợp. Nguồn: [Chrome Tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs).
- Chrome cung cấp `chrome.tabGroups` API để thao tác nhóm tab; API này hỗ trợ Manifest V3 và có thể query/update group. Nguồn: [Chrome Tab Groups API](https://developer.chrome.com/docs/extensions/reference/api/tabGroups).
- Chrome có `chrome.storage` dành riêng cho extension, hỗ trợ `local`, `sync`, `session`; `storage.local` có quota và dữ liệu tồn tại đến khi extension bị gỡ. Nguồn: [Chrome Storage API](https://developer.chrome.com/docs/extensions/reference/api/storage).
- Manifest V3 sử dụng extension service worker thay cho background page dài hạn; trạng thái quan trọng không nên chỉ giữ trong biến global của service worker. Nguồn: [Manifest V3 overview](https://developer.chrome.com/docs/extensions/develop/migrate/what-is-mv3) và [Migrate to a service worker](https://developer.chrome.com/docs/extensions/develop/migrate/to-service-workers).
- `chrome.alarms` có thể chạy logic theo thời gian, nhưng alarm có thể bị delay và thiết bị đang sleep sẽ không bị đánh thức chỉ để chạy alarm. Nguồn: [Chrome Alarms API](https://developer.chrome.com/docs/extensions/reference/api/alarms).

### Observation

Chrome đã có primitive kỹ thuật để đọc danh sách tab, nhóm tab, persist dữ liệu và xử lý background event. Vì vậy phần khó của TabBudget không nằm ở “có API hay không”, mà nằm ở UX, luật park/restore và tránh làm người dùng mất tab.

### Assumption

- Có một nhóm người dùng thực sự muốn **giới hạn active tabs**, thay vì chỉ group chúng.
- Người dùng chấp nhận extension đọc URL/title của tab nếu permission được giải thích rõ.
- “Park thay vì close vĩnh viễn” tạo cảm giác an toàn đủ lớn để người dùng bật automation.

### Vì sao workaround hiện tại chưa tối ưu

Các cách phổ biến:

- tự đóng tab thủ công;
- dùng tab groups;
- bookmark tab “để đọc sau”;
- dùng browser history;
- giữ toàn bộ tab mở vì sợ mất context.

Những cách này hoặc đòi hỏi thao tác thủ công, hoặc không enforce giới hạn working set. TabBudget tạo ra một rule engine nhỏ, có khả năng đảo ngược, tập trung đúng một mục tiêu: **giữ số tab đang mở ở mức kiểm soát được**.

## 3. Người dùng mục tiêu

### Primary user

Developer hoặc technical knowledge worker dùng Chrome/Edge cả ngày, thường có 20–80 tab mở và liên tục mở thêm tab mới trong lúc đọc docs, debug hoặc review code.

### Context of use

- Khi debug một issue và mở hàng loạt tài liệu liên quan.
- Khi research API/library mới.
- Khi xử lý nhiều GitHub issues/PR.
- Khi sử dụng nhiều app web song song.

### Main pain point

Người dùng biết rằng có quá nhiều tab nhưng không muốn đóng vì mỗi tab chứa context hoặc một thứ “có thể cần lại”. Kết quả là tab bar mất khả năng định hướng.

### Current workaround

- Group tabs thủ công.
- Pin tab quan trọng.
- Search tab bằng browser UI.
- Save bookmark hoặc “read later”.

### Lý do thử TabBudget

Extension không bắt người dùng tổ chức mọi thứ. Chỉ cần đặt vài rule, ví dụ:

- `github.com` → max 8 active tabs
- `learn.microsoft.com` → max 6
- `youtube.com` → max 3
- default window budget → max 25

Từ đó extension hỗ trợ dọn phần vượt ngưỡng mà vẫn giữ khả năng restore.

## 4. Giải pháp đề xuất

### Main workflow

1. Người dùng cài extension.
2. Tạo một hoặc vài budget rule.
3. Extension lắng nghe các event tab được tạo/cập nhật/đóng.
4. Khi một rule bị vượt ngưỡng:
   - xác định các tab candidate;
   - loại tab pinned, active, audio-playing hoặc được user lock;
   - xếp hạng tab ít ưu tiên hơn;
   - park tab phù hợp vào local queue;
   - đóng tab gốc sau khi đã persist record thành công.
5. Người dùng mở popup/side panel để xem parking queue.
6. Click Restore để mở lại tab.

### Input

- URL và title tab.
- Rule do user cấu hình.
- Tab metadata: active/pinned/groupId/audible/last-accessed khi API cung cấp và logic cho phép.
- User action như lock, restore, exclude domain.

### Processing

Rule engine:

```text
open tab
→ normalize URL/domain
→ find matching budget rule
→ count active tabs in scope
→ if count <= limit: no-op
→ else select park candidate
→ persist candidate
→ verify persist
→ close tab
```

### Output

- Số tab active giảm về ngưỡng mong muốn.
- Parking queue hiển thị tab đã park.
- User restore được bằng một click.
- Audit nhỏ: “parked because github.com exceeded budget 8”.

### Tự động hóa

Có thể tự động:

- detect vượt budget;
- chọn candidate;
- park;
- dọn queue cũ sau N ngày nếu user bật retention policy;
- nhắc review queue định kỳ.

### User vẫn kiểm soát

- rule nào được bật;
- domain nào exempt;
- tab nào locked;
- tab active/pinned có được phép park hay không;
- có auto-park hay chỉ cảnh báo;
- retention của parking queue.

### Key differentiator

**Không phải bookmark manager.** TabBudget tập trung vào “working-set control”: giới hạn số tab đang sống trong browser ngay lúc này, với khả năng rollback.

### Ví dụ concrete

Hà đang debug một integration và đã mở 12 tab `learn.microsoft.com`, trong khi rule giới hạn là 6.

- TabBudget thấy 12 > 6.
- Nó bỏ qua tab đang active và 1 tab pinned.
- Nó chọn 5 tab cũ hơn để park trước.
- Mỗi tab được lưu thành `ParkedTab`.
- Sau khi lưu thành công, extension đóng 5 tab đó.
- Popup hiển thị nhóm “learn.microsoft.com — 5 parked”.
- Một giờ sau, Hà cần lại một bài docs, search title trong queue và Restore.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Ngay cả khi chỉ có một user, extension vẫn hữu ích nếu người đó thực sự thường xuyên bị tab overload. Đây là loại project có thể được dùng hằng ngày bởi chính developer tạo ra nó.

### Technical learning value

Dự án chạm vào:

- Chrome Extension Manifest V3;
- event-driven state management;
- persistence an toàn;
- permissions/privacy;
- UX cho automation có khả năng destructive;
- scoring/rule engine;
- browser APIs.

### Vì sao phù hợp solo developer

MVP không cần backend, account, database server, AI API hay cloud deployment. Một extension local-only là đủ để validate core value.

### Vì sao vẫn hữu ích với rất ít users

Đây là personal productivity tool. Chỉ cần bản thân developer dùng hằng ngày là project đã có giá trị.

### Điều gì khiến idea thất bại

- User không tin extension có quyền đọc tab URL/title.
- Auto-parking gây khó chịu hơn lợi ích.
- Browser tab groups có sẵn đã đủ dùng đối với phần lớn người dùng.
- Candidate selection chọn nhầm tab quan trọng.

### Strongest reason not to build

Nếu core behavior cuối cùng chỉ trở thành “một tab manager khác”, idea mất sự khác biệt. Project chỉ đáng làm nếu **budget-based working set + reversible parking** thực sự khiến workflow tốt hơn tab groups/bookmarks thông thường.

## 6. Phạm vi MVP

### Must have

1. Manifest V3 extension chạy trên Chrome/Edge Chromium.
2. Query tab hiện tại.
3. Tạo budget rule theo hostname.
4. Chế độ **Warn only**.
5. Chế độ **Auto park**.
6. Không park:
   - active tab;
   - pinned tab;
   - tab được lock thủ công.
7. Persist parked tabs bằng `chrome.storage.local`.
8. Restore một tab.
9. Restore toàn bộ tab của một domain.
10. Hiển thị lý do bị park.
11. Safe write-before-close: chỉ đóng tab sau khi record đã persist thành công.

### Should have

- Window-level total tab budget.
- Exclusion patterns.
- Group parking queue theo hostname.
- Search parked tabs theo title/URL.
- Undo ngay sau auto-park.
- Badge hiển thị số tab vượt budget.
- Export/import rules JSON.

### Later

- Tab group-aware rules.
- Cross-device sync settings.
- “Project workspace” rules.
- Time-based resurfacing.
- Usage analytics local-only.
- Firefox support.
- Optional self-hosted sync service.

Không đưa AI, cloud account, team sharing hoặc recommendation engine vào MVP.

## 7. Luồng hoạt động

### Happy path

User mở tab
→ `chrome.tabs` event kích hoạt
→ normalize hostname
→ match rule
→ count tabs
→ vượt limit
→ candidate selector chạy
→ persist `ParkedTab`
→ verify storage write
→ close tab
→ popup cập nhật queue
→ user restore khi cần.

### Alternative flow: Warn only

Vượt budget
→ badge/popup cảnh báo
→ user chọn “Park 3 tabs”
→ extension mới thực hiện.

### Failure: storage write thất bại

Không đóng tab.

Đây là rule bắt buộc. Dữ liệu park phải tồn tại trước khi tab bị đóng.

### Failure: tab thay đổi URL giữa lúc đánh giá

Re-query tab ngay trước khi đóng và verify `tab.id`, URL hoặc state phù hợp. Nếu khác kỳ vọng, bỏ candidate và recalculate.

### Failure: tab đang phát audio

Mặc định skip. Có option riêng nếu user muốn override.

### Failure: candidate là browser internal page

Các URL như `chrome://`, extension pages hoặc scheme không restore được ổn định phải được exclude.

### Failure: user restore khiến budget vượt lại

Restore action được coi là explicit user intent. Extension tạo grace period, ví dụ 10 phút, không auto-park tab vừa restore ngay lập tức.

### Queue

Không cần RabbitMQ/Kafka. “Parking queue” chỉ là data structure persist local, không phải message queue.

### Cache

Không cần.

### File storage

Không cần.

### Authentication

Không cần cho local-only MVP.

### External APIs

Không cần.

### AI model

Không cần.

### Notification channel

Chrome badge hoặc browser notification là đủ nếu user bật.

### Logging/monitoring

## 9. Công nghệ đề xuất

### TypeScript + Chrome Extension Manifest V3

**Vì sao phù hợp:** browser extension native environment dùng JavaScript/TypeScript trực tiếp; dùng .NET ở đây sẽ thêm complexity không cần thiết.

**Simpler alternative:** JavaScript thuần.

**Khi outgrow:** gần như không cần đổi stack; chỉ cần build tooling tốt hơn khi codebase lớn.

### Vite

Dùng cho build popup/options UI và TypeScript bundling.

**Simpler alternative:** không bundler, chỉ `tsc`.

### Vue 3 — optional

Nếu UI popup/options bắt đầu nhiều state và component, Vue phù hợp với kinh nghiệm web hiện có.

**Simpler alternative:** plain DOM + TypeScript.

### chrome.storage.local

**Vì sao phù hợp:** official extension storage, không cần backend.

**Simpler alternative:** không có lựa chọn đơn giản hơn mà vẫn phù hợp Manifest V3; `localStorage` không nên là core storage cho service worker.

**Khi outgrow:** nếu cần search hàng chục nghìn record hoặc cross-device history lớn, chuyển parked records sang IndexedDB hoặc backend optional.

### Playwright

Dùng cho E2E phần options/popup nếu có thể load extension trong Chromium test context.

**Simpler alternative:** manual smoke test + unit test cho rule engine.

### Vitest

Unit test pure functions như hostname matching, candidate scoring, exclusion logic.

### GitHub Actions

Build, lint, test và tạo zip artifact.

Không cần .NET, PostgreSQL, Docker, Azure hay Kubernetes cho MVP vì những thành phần này không giải quyết thêm giá trị cốt lõi.

## 10. Thiết kế dữ liệu ban đầu

### `BudgetRule`

**Purpose:** định nghĩa giới hạn tab.

Fields:

```ts
interface BudgetRule {
  id: string;
  scopeType: 'hostname' | 'window';
  pattern: string;
  maxActiveTabs: number;
  mode: 'warn' | 'autoPark';
  enabled: boolean;
  createdAt: number;
  updatedAt: number;
}
```

### `ParkedTab`

**Purpose:** restore một tab đã bị park.

Fields:

```ts
interface ParkedTab {
  id: string;
  originalTabId?: number;
  url: string;
  title: string;
  faviconUrl?: string;
  hostname: string;
  parkedAt: number;
  reason: string;
  sourceWindowId?: number;
  sourceGroupTitle?: string;
  restoredAt?: number;
}
```

### `TabLock`

**Purpose:** bảo vệ tab user không muốn auto-park.

```ts
interface TabLock {
  tabId: number;
  lockedAt: number;
}
```

`tabId` chỉ hợp lệ trong browser session, vì vậy record này có thể nằm ở `storage.session` thay vì permanent storage.

### `Settings`

Fields:

- defaultMode;
- skipPinned;
- skipAudible;
- restoreGraceMinutes;
- retentionDays;
- notificationsEnabled.

### `ActionLog`

Optional, bounded retention.

- action: parked/restored/skipped/error;
- timestamp;
- tab metadata tối thiểu;
- reason.

### Relationships

Không cần relational DB. Data có thể lưu theo key collections.

### Data retention

- Parked tab giữ đến khi restore/delete hoặc hết retention.
- Action log giữ số lượng giới hạn.
- Không lưu page body, cookies, form data hoặc browsing content.

## 11. API và tích hợp

### Chrome Tabs API

**Purpose:** đọc và thao tác tab.

**Authentication:** không cần OAuth.

**Permission concern:** truy cập URL/title cần khai báo permission phù hợp.

**Cost/rate limit:** không có chi phí API SaaS; vẫn nên tránh query toàn bộ tab quá mức không cần thiết.

**Privacy:** URL có thể chứa dữ liệu nhạy cảm, nên chỉ lưu local.

**Fallback:** không có fallback thực sự; đây là dependency nền tảng.

Nguồn: [Chrome Tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs).

### Chrome Tab Groups API

**Purpose:** future enhancement cho group-aware rules.

**Authentication:** không cần.

**Permission:** `tabGroups`.

**Fallback:** MVP bỏ integration này hoàn toàn nếu muốn giảm permission surface.

Nguồn: [Chrome Tab Groups API](https://developer.chrome.com/docs/extensions/reference/api/tabGroups).

### Chrome Storage API

**Purpose:** persist rule và parked tabs.

**Authentication:** không cần.

**Concern:** quota và write performance.

**Privacy:** local storage không phải encrypted secret vault; không lưu token hoặc secret.

**Fallback:** IndexedDB nếu dataset lớn hơn.

Nguồn: [Chrome Storage API](https://developer.chrome.com/docs/extensions/reference/api/storage).

### Chrome Alarms API

**Purpose:** periodic retention cleanup hoặc review reminder.

**Authentication:** không cần.

**Reliability concern:** alarm có thể bị delay; không dùng cho logic đòi timing chính xác.

**Fallback:** cleanup lazy khi popup mở hoặc khi service worker được wake bởi event khác.

Nguồn: [Chrome Alarms API](https://developer.chrome.com/docs/extensions/reference/api/alarms).

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem có thể giải quyết tốt bằng deterministic rules:

- hostname matching;
- count tabs;
- candidate scoring;
- exclusion rules;
- park/restore.

Dùng AI để “đoán tab nào quan trọng” sẽ tạo rủi ro không đáng có vì:

- hallucination/uncertainty không phù hợp với thao tác đóng tab;
- phải gửi URL/title ra ngoài;
- tăng latency và cost;
- privacy risk cao hơn;
- khó giải thích tại sao tab bị chọn.

Nếu sau này muốn experiment với AI, AI chỉ nên **gợi ý rule hoặc group**, không được tự quyết destructive action mà không có deterministic validation.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác định có thật sự cần “budget-based tab control”.

**Main tasks:**

- Trong 3 ngày tự ghi số tab peak mỗi ngày.
- Chọn 3 domain thường phình tab nhất.
- Dùng một script prototype chỉ thống kê tab count theo hostname.
- Tự hỏi: nếu extension nhắc “GitHub 14/8 tabs”, hành động đó có hữu ích không?

**Expected output:** bảng 3 ngày với tab count và các domain phổ biến.

**Completion criteria:** ít nhất một domain thường xuyên vượt mức mà user tự đánh giá là hợp lý.

### Phase 1 — Core MVP

**Goal:** chạy được end-to-end warn → park → restore.

**Main tasks:**

- scaffold MV3 extension;
- query tabs;
- rule CRUD tối thiểu;
- candidate selector;
- storage write-before-close;
- parking queue;
- restore action.

**Expected output:** extension unpacked dùng được thật.

**Completion criteria:** mở 10 tab GitHub với budget 5 → park 5 → restore lại được chính xác.

### Phase 2 — Reliability

**Goal:** không làm mất tab hoặc park nhầm dễ dàng.

**Main tasks:**

- skip pinned/active/audible;
- re-query trước close;
- grace period sau restore;
- duplicate protection;
- error handling;
- unit tests;
- bounded audit log.

**Expected output:** core workflow chịu được browser state thay đổi.

**Completion criteria:** failure test không tạo tình huống tab bị đóng nhưng parking record bị mất.

### Phase 3 — Useful expansion

**Goal:** làm extension thực sự tiện dùng hằng ngày.

**Main tasks:**

- window budget;
- exclusion pattern;
- bulk restore;
- search parked tabs;

## 14. Các bài toán kỹ thuật đáng học

### 1. Event-driven state management trong Manifest V3

Service worker không sống mãi, vì vậy state phải được persist đúng chỗ. Đây là bài tập tốt để học cách thiết kế background logic không phụ thuộc process lifetime.

### 2. Safe destructive workflow

Pattern quan trọng:

```text
prepare record
→ persist
→ verify
→ destructive action
```

Kỹ năng này áp dụng được cho file operations, migration, offboarding, queue processing và automation nói chung.

### 3. Candidate selection có thể giải thích

Thay vì ML, dùng scoring:

```text
pinned      => never
active      => never
audible     => skip
locked      => never
recent      => low park priority
old inactive=> high park priority
```

Học cách xây rule engine đơn giản, predictable và testable.

### 4. Browser permission minimization

Phải hiểu permission nào thật sự cần, giảm host permission không cần thiết, và giải thích privacy rõ ràng.

### 5. Recovery và idempotency

Event tab có thể đến nhiều lần; restore có thể double-click; tab có thể biến mất giữa các bước. Đây là môi trường tốt để luyện idempotent operations và stale-state handling.

## 15. Rủi ro và cách xử lý

### Rủi ro: park nhầm tab quan trọng

**Mitigation:**

- skip active/pinned/audible;
- lock button;
- default Warn mode;
- Undo;
- explain reason;
- auto-park chỉ bật per-rule.

### Rủi ro: mất tab do storage lỗi

**Mitigation:** tuyệt đối write-before-close. Storage failure = no close.

### Rủi ro: URL chứa dữ liệu nhạy cảm

Một số URL chứa query parameters hoặc identifiers.

**Mitigation:** local-only MVP, không telemetry, không gửi cloud, có option strip common tracking parameters khi lưu nếu user muốn.

### Rủi ro: permission làm user e ngại

**Mitigation:** permission tối thiểu, docs rõ ràng về lý do cần `tabs`.

### Rủi ro: extension biến thành tab manager khổng lồ

**Mitigation:** giữ product boundary: budget, park, restore. Không thêm notes, bookmarks, task management, knowledge base vào core.

### Rủi ro: service worker bị terminate

**Mitigation:** không giữ critical state trong global memory; persist settings/queue; event handler có thể chạy lại an toàn.

### Rủi ro: API/browser behavior thay đổi

**Mitigation:** dựa chủ yếu vào official stable extension APIs, có integration tests trên Chromium channel chính.

### Rủi ro: user adoption thấp

**Mitigation:** validate cá nhân trước, open-source early, không xây backend hoặc billing trước khi có evidence.

### Rủi ro maintenance burden

Extension platform thay đổi theo thời gian.

**Mitigation:** codebase nhỏ, ít dependencies, test core logic pure functions.

## Research notes

### Confirmed facts

- Chrome Tabs API cho phép extension tương tác với tab, gồm query/create/update/move/reload và các thao tác liên quan. [Chrome Tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs)
- Chrome Tab Groups API có thể query và update tab groups trên Manifest V3. [Chrome Tab Groups API](https://developer.chrome.com/docs/extensions/reference/api/tabGroups)
- Chrome Storage API cung cấp extension-specific persistent storage; `storage.local` phù hợp cho local state và có quota. [Chrome Storage API](https://developer.chrome.com/docs/extensions/reference/api/storage)
- Manifest V3 dùng service worker thay cho long-lived background page; state quan trọng cần được persist vì worker có thể terminate. [Manifest V3](https://developer.chrome.com/docs/extensions/develop/migrate/what-is-mv3), [Service worker migration](https://developer.chrome.com/docs/extensions/develop/migrate/to-service-workers)
- Chrome Alarms API hỗ trợ scheduled background behavior nhưng không đảm bảo exact timing khi máy sleep hoặc runtime bị trì hoãn. [Chrome Alarms API](https://developer.chrome.com/docs/extensions/reference/api/alarms)

### Observations

Các browser API cần cho MVP đều tồn tại và không yêu cầu third-party service. Vì vậy feasibility kỹ thuật của extension là tốt; rủi ro lớn hơn nằm ở UX và độ tin cậy của auto-parking.

### Analysis

Một extension chỉ “quản lý tab” sẽ khó khác biệt. Boundary hợp lý nhất là **active-tab budget + reversible parking + safety-first selection**. Đây là khác biệt đủ cụ thể để có thể đo được: active tab count có giảm không và user có restore thành công khi cần không.

### Assumptions

- Tab overload là vấn đề đủ thường xuyên với nhóm developer/knowledge worker mục tiêu.
- Local-only privacy là lợi thế đáng kể.
- Người dùng thích cơ chế park hơn cơ chế đóng tab vĩnh viễn.

### Recommendation

Build bản **Warn-only first** trước khi bật auto-park. Chỉ khi chính developer dùng vài ngày và thấy cảnh báo budget thực sự hữu ích mới triển khai destructive automation.
