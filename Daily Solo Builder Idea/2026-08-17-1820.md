# Ý tưởng hôm nay: Impact Ledger — Nhật ký thành tựu kỹ thuật có bằng chứng cho developer

## 1. Tóm tắt ý tưởng

**Impact Ledger** là một ứng dụng cá nhân giúp developer tự động thu thập các dấu vết công việc có thể kiểm chứng như pull request, issue, commit, release note và mốc dự án, sau đó biến chúng thành một “nhật ký tác động” dùng cho self-review, performance review, CV và phỏng vấn. Điểm khác biệt là mọi thành tựu đều giữ liên kết về bằng chứng gốc thay vì chỉ là ghi chú chủ quan.

- **Người dùng chính:** software developer làm việc lâu dài trên GitHub hoặc GitHub Enterprise.
- **Bài toán:** sau vài tháng, developer thường nhớ mình “đã làm nhiều việc” nhưng khó nhớ chính xác thay đổi nào tạo ra giá trị, ở repo nào, khi nào, và bằng chứng nằm ở đâu.
- **Quy mô:** Medium.
- **Thời gian MVP ước tính:** 10–14 ngày làm ngoài giờ.

## 2. Bài toán thực tế

### Confirmed facts

GitHub cung cấp REST API chính thức để đọc pull request, issue và commit. Pull request có thể truy cập các quan hệ như commits, comments, review comments và trạng thái liên quan; API commit hỗ trợ lấy commit, so sánh commit và tìm pull request liên quan đến commit. Điều này làm cho việc xây dựng một lớp thu thập bằng chứng kỹ thuật từ GitHub là khả thi mà không cần scraping giao diện web.

Nguồn chính thức:

- GitHub Pull Requests REST API: https://docs.github.com/en/rest/pulls/pulls
- GitHub Commits REST API: https://docs.github.com/en/rest/commits
- GitHub Issues REST API: https://docs.github.com/en/rest/issues/issues
- GitHub REST API overview: https://docs.github.com/en/rest

Microsoft Graph cũng có API chính thức cho calendar events. Điều này có thể trở thành integration mở rộng để liên kết các mốc như architecture review, incident review hoặc project kickoff, nhưng không cần cho MVP.

Nguồn:

- Microsoft Graph calendar overview: https://learn.microsoft.com/en-us/graph/api/resources/calendar-overview?view=graph-rest-1.0
- Microsoft Graph list events: https://learn.microsoft.com/en-us/graph/api/calendar-list-events?view=graph-rest-1.0

### Observation

Developer thường có dữ liệu công việc rải rác giữa pull request, issue, commit, release, calendar, chat và ticket system. Khi đến kỳ đánh giá hiệu suất hoặc cập nhật CV, họ phải quay lại tìm thủ công từng bằng chứng rồi cố nhớ “việc này giải quyết vấn đề gì”.

### Assumption cần kiểm chứng

Giả định quan trọng của dự án là developer thực sự thấy đau ở bước **reconstruct impact** chứ không chỉ ở bước “liệt kê activity”. Nếu người dùng chỉ cần danh sách pull request gần đây thì GitHub UI đã đủ và sản phẩm không có giá trị riêng.

### Cách xử lý hiện tại

- Ghi achievement bằng Notion, Obsidian hoặc Markdown thủ công.
- Tìm lại pull request khi cần viết self-review.
- Dựa vào lịch sử commit hoặc Jira để nhớ dự án.
- Copy link vào một document riêng.
- Cuối quý mới ngồi tổng hợp nên dễ bỏ sót việc đã làm từ đầu quý.

### Vì sao chưa tốt

- Dữ liệu bị phân mảnh.
- Activity không đồng nghĩa với impact.
- Tìm lại bằng chứng tốn thời gian.
- Thành tựu được viết quá muộn nên mất context.
- Dễ tạo “CV bullet” nghe hay nhưng thiếu evidence cụ thể.

## 3. Người dùng mục tiêu

### Primary user cho MVP

Một **backend developer hoặc full-stack developer có từ 2–10 năm kinh nghiệm**, làm việc thường xuyên trên GitHub, có nhiều pull request mỗi tháng và cần định kỳ chuẩn bị self-review, promotion case hoặc CV.

### Context sử dụng

- Công ty dùng GitHub hoặc developer có repository cá nhân.
- Mỗi tuần có nhiều PR/issue.
- Sau 1–3 tháng, developer khó nhớ chi tiết tác động của từng thay đổi.

### Main pain point

Không phải thiếu activity, mà là thiếu một nơi trả lời nhanh:

- Tôi đã giải quyết vấn đề quan trọng nào?
- Có bằng chứng cụ thể ở đâu?
- Thay đổi đó liên quan performance, reliability, security, delivery hay architecture?
- Có thể dùng việc này cho promotion/CV không?

### Workaround hiện tại

Notion/Markdown thủ công, bookmark link, search GitHub, xem lại Jira hoặc hỏi đồng nghiệp.

### Lý do thử Impact Ledger

Nếu app có thể tự động thu thập activity rồi chỉ yêu cầu user bổ sung 1–2 dòng context cho những item đáng giữ, effort ghi chép sẽ thấp hơn nhiều so với duy trì một achievement log hoàn toàn thủ công.

## 4. Giải pháp đề xuất

### Main workflow

1. User kết nối GitHub bằng Personal Access Token hoặc GitHub OAuth.
2. Chọn repository cần theo dõi.
3. Background worker lấy pull request, issue và commit của user trong một khoảng thời gian.
4. Hệ thống chuẩn hóa chúng thành `WorkEvidence`.
5. Rule engine gắn các tín hiệu sơ bộ:
   - merged PR
   - bug fix
   - performance
   - security
   - reliability
   - dependency/runtime upgrade
   - test coverage
   - architecture/refactor
6. Dashboard hiển thị danh sách evidence theo tuần/tháng.
7. User chọn những item đáng giữ và thêm:
   - Problem
   - Action
   - Result
   - Scope
   - Evidence link
8. App tạo “Impact Entry” có thể dùng trong self-review hoặc CV draft.

### Input

- GitHub account/repositories.
- Pull request, issue, commit metadata.
- User annotation ngắn.

### Processing

- Deduplicate activity.
- Liên kết commit → PR nếu có.
- Liên kết PR → issue nếu metadata cho phép.
- Nhóm evidence theo repository/time window.
- Rule-based tagging dựa trên title, labels, changed files và metadata.

### Output

Một impact entry dạng:

```text
Category: Reliability
Problem: Background job thỉnh thoảng xử lý trùng notification.
Action: Thiết kế idempotency key và unique constraint cho delivery record.
Result: Loại bỏ duplicate trong test/replay scenario và đơn giản hóa retry logic.
Evidence:
- PR #482
- Issue #451
- Commit abc123
```

### Phần được tự động hóa

- Sync GitHub data.
- Deduplicate.
- Group activity.
- Rule-based tags.
- Suggest candidates đáng review.

### Phần user kiểm soát

- Xác nhận một activity có thực sự tạo impact hay không.
- Viết result thật, không cho hệ thống tự suy diễn metric.
- Chọn item nào xuất sang review/CV.

### Key differentiator

Không phải “GitHub activity dashboard”, mà là **evidence-backed impact ledger**. Mọi bullet quan trọng phải dẫn về bằng chứng gốc.

### Ví dụ end-to-end

Hà merge một PR sửa timeout của Selenium runner.

- Impact Ledger sync PR và issue liên quan.
- Rule engine phát hiện title có `timeout`, `retry`, `stale element` nên gợi ý tag `Reliability`.
- App hỏi hai field bắt buộc:
  - “Trước thay đổi này, failure mode là gì?”
  - “Sau thay đổi này, bạn xác nhận điều gì đã tốt hơn?”
- Hà nhập rằng workflow giảm flakiness trong các run lặp lại và thêm link PR.
- Cuối tháng, app có thể xuất entry này vào nhóm “Reliability & Automation”.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

- Giảm thời gian tìm lại công việc cũ.
- Tạo habit ghi impact khi context còn mới.
- Tăng chất lượng self-review và CV vì có evidence.
- Có thể dùng cho cá nhân ngay cả khi không có user khác.

### Technical learning value

Dự án có nhiều bài toán phù hợp để nâng cấp kỹ năng senior/backend:

- OAuth/token security.
- Incremental synchronization.
- API pagination/rate limiting.
- Deduplication.
- Background processing.
- Search/indexing.
- Structured AI output nếu thêm AI sau này.

### Solo feasibility

Core workflow chỉ cần một modular monolith, PostgreSQL và một worker. Không cần realtime, queue phân tán hay hệ thống dữ liệu lớn.

### Giá trị khi chỉ có một người dùng

Rất cao: đây là personal career tool. Không cần network effect.

### Điều làm idea thất bại

Nếu user phải annotate quá nhiều thì họ sẽ bỏ dùng sau vài tuần.

### Strongest reason not to build

Nếu GitHub activity của user vốn ít hoặc team dùng công cụ khác hoàn toàn, automation không tiết kiệm đủ effort so với một file Markdown đơn giản.

## 6. Phạm vi MVP

### Must have

- Kết nối GitHub bằng token.
- Chọn 1–5 repositories.
- Sync pull requests của user trong 90 ngày gần nhất.
- Lưu title, status, merge date, repo, URL, labels.
- Tạo `ImpactEntry` thủ công từ PR đã sync.
- Form theo cấu trúc Problem / Action / Result.
- Dashboard filter theo month/category/repository.
- Export Markdown.

### Should have

- Sync issues và commits.
- Auto-link PR với issue.
- Background sync hàng ngày.
- Rule-based tagging.
- Search full-text.
- CSV/JSON export.

### Later

- GitHub OAuth App.
- GitLab/Azure DevOps integration.
- Microsoft Graph calendar integration.
- AI-assisted draft.
- CV mode.
- Promotion packet mode.
- Weekly reminder email.
- Browser extension để capture evidence nhanh.

## 7. Luồng hoạt động

```text
User connects GitHub
→ token validation
→ select repositories
→ sync request created
→ GitHub API calls with pagination
→ normalize PR/issue/commit
→ deduplicate by provider + repository + external id
→ store WorkEvidence
→ user reviews candidates
→ create ImpactEntry
→ save evidence links
→ export Markdown
```

### Alternative flow: API rate limit

- Worker lưu sync cursor.
- Dừng gracefully.
- Record `NextRetryAt`.
- Resume từ cursor thay vì sync lại toàn bộ.

### Alternative flow: token revoked

- Mark connection `NeedsReauth`.
- Không xóa dữ liệu local.
- Dashboard hiển thị integration degraded.

### Alternative flow: PR deleted/private repository mất quyền

- Giữ local metadata tối thiểu đã sync.
- Mark evidence là `SourceUnavailable`.

### Failure case: duplicate data

Unique key:

```text
Provider + RepositoryId + EvidenceType + ExternalId
```

## 11. API và tích hợp

### GitHub REST API

**Purpose:** lấy pull request, issue, commit metadata.

**Authentication:** fine-grained personal access token hoặc OAuth/App trong phase sau.

**Rate-limit concern:** phải xử lý pagination, conditional sync và backoff thay vì full sync liên tục.

**Privacy:** private repositories có thể chứa tên project/client nhạy cảm; chỉ lưu metadata thực sự cần.

**Fallback:** manual import bằng JSON/CSV hoặc paste GitHub URL.

Nguồn:

- https://docs.github.com/en/rest
- https://docs.github.com/en/rest/pulls/pulls
- https://docs.github.com/en/rest/commits
- https://docs.github.com/en/rest/issues/issues

### Microsoft Graph Calendar — Later

**Purpose:** liên kết mốc meeting/incident/review với impact entry.

**Authentication:** delegated OAuth.

**Privacy:** calendar có thể chứa thông tin cá nhân hoặc meeting title nhạy cảm.

**Fallback:** user thêm milestone date thủ công.

Nguồn:

- https://learn.microsoft.com/en-us/graph/api/resources/calendar-overview?view=graph-rest-1.0
- https://learn.microsoft.com/en-us/graph/api/calendar-list-events?view=graph-rest-1.0

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

MVP không cần AI.

### Task phù hợp cho AI ở phase sau

Chuyển một impact entry đã được user xác nhận thành 2–3 dạng wording:

- self-review bullet
- CV bullet
- interview STAR talking point

### Context gửi cho model

Chỉ gửi:

- Problem
- Action
- Result
- category
- sanitized evidence title

Không gửi code/private diff mặc định.

### Structured output mong đợi

```json
{
  "selfReview": "...",
  "cvBullet": "...",
  "star": {
    "situation": "...",
    "task": "...",
    "action": "...",
    "result": "..."
  },
  "unsupportedClaims": []
}
```

### Validation

Rule bắt buộc:

- Không được tạo metric mới.
- Nếu source không có con số thì AI không được tự thêm `%`, số user, latency hoặc revenue.
- Any statement không map được về field gốc phải flag.

### Deterministic fallback

Template:

```text
Improved {category} by addressing {problem}. Implemented {action}. Result: {result}.
```

### Risks

- Hallucination.
- Privacy leak.
- Cost.
- Wording nghe quá marketing.

Vì vậy AI không được phép là source of truth.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác nhận người dùng thực sự đau ở khâu nhớ và chứng minh impact.

**Tasks:**

- Chọn 3 tháng GitHub history của chính mình.
- Manual spreadsheet 20 PR gần đây.
- Thử phân loại PR nào thực sự đáng cho self-review.
- Đo thời gian tìm evidence và viết 5 impact entries.

**Expected output:** một sample ledger 5 entries.

**Completion criteria:** ít nhất 3/5 entry cần quay lại GitHub để tìm context/bằng chứng; nếu không, automation có thể chưa đáng làm.

### Phase 1 — Core MVP

**Goal:** hoàn thiện vertical slice GitHub PR → Impact Entry → Markdown export.

**Tasks:**

- Setup solution.
- PostgreSQL + EF migrations.
- GitHub token config.
- Sync PR endpoint.
- Evidence dashboard.
- Create/edit impact entry.
- Markdown export.

**Expected output:** chạy được với repo cá nhân thật.

**Completion criteria:** tạo một impact entry có evidence link từ PR sync tự động.

### Phase 2 — Reliability

**Goal:** sync ổn định.

**Tasks:**

- Idempotency.
- Pagination.
- Retry/backoff.
- Token encryption.
- Integration tests với mocked GitHub API.
- Observability.

**Expected output:** sync lặp lại không tạo duplicate.

**Completion criteria:** chạy 20 sync liên tiếp trên cùng dataset và row count đúng.

### Phase 3 — Useful expansion

**Goal:** giảm effort review hàng tuần.

**Tasks:**

- Issues + commits.
- Rule tagging.
- Search.
- Weekly digest page.
- Candidate scoring deterministic.

**Expected output:** user chỉ cần review candidate thay vì đọc tất cả activity.

**Completion criteria:** trong một tuần có thể chọn 1–3 candidate trong dưới 5 phút.

### Phase 4 — Production readiness

**Goal:** self-host ổn định dài hạn.

**Tasks:**

- Docker image.
- Backup/restore PostgreSQL.
- Health checks.
- Secret management docs.
- Data export/delete.
- GitHub Actions pipeline.

**Expected output:** deploy mới bằng Docker Compose trong một command flow rõ ràng.

**Completion criteria:** restore backup trên môi trường sạch và xác nhận impact entries còn nguyên.

## 14. Các bài toán kỹ thuật đáng học

### 1. Incremental synchronization

Không sync toàn bộ lịch sử mỗi lần. Cần checkpoint, updated timestamps và resume logic.

**Skill:** thiết kế synchronization pipeline thực tế.

### 2. Idempotency và deduplication

Provider API có thể trả lại cùng object nhiều lần.

**Skill:** unique constraints, upsert, repeatable jobs.

### 3. Rate-limit aware background processing

Không retry mù khi API hạn chế request.

**Skill:** backoff, scheduling, API budget.

### 4. Privacy-preserving data handling

Career evidence từ private repo có thể chứa project/customer names.

**Skill:** data minimization, encryption, retention design.

### 5. Evidence-to-impact modeling

Một PR không mặc định là một achievement. Cần model cho nhiều evidence liên kết một impact entry.

**Skill:** domain modeling và semantic boundaries.

## 15. Rủi ro và cách xử lý

### Scope expansion

Rất dễ biến thành GitHub/Jira/Slack/Calendar data warehouse.

**Mitigation:** MVP chỉ GitHub PR.

### Privacy

Private repository metadata nhạy cảm.

**Mitigation:**

- single-user self-host option.
- token encryption.
- không lưu diff/code mặc định.
- configurable field retention.

### GitHub API dependency

API thay đổi hoặc token thiếu quyền.

**Mitigation:** provider adapter + graceful degraded mode + manual evidence URL.

### User adoption

Nếu mỗi PR yêu cầu annotate thì quá nặng.

**Mitigation:** chỉ review candidate đáng chú ý; không bắt user xử lý toàn bộ activity.

### AI hallucination

Nếu thêm AI, có thể tạo achievement vượt quá evidence.

**Mitigation:** AI chỉ paraphrase structured verified fields; không sinh metric.

### Maintenance burden

Nhiều integration sẽ tăng mạnh maintenance.

**Mitigation:** một provider stable trước; extension theo demand thật.

## 16. Kiểm thử

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong 60–120 phút, tạo vertical slice đầu tiên:

**Nhập GitHub username + repository → gọi GitHub API → hiển thị 10 pull request gần nhất trong một trang web local.**

Chưa cần database, auth hoặc AI.

### Files/components cần tạo

```text
ImpactLedger.sln
src/ImpactLedger.Api/
src/ImpactLedger.Web/
src/ImpactLedger.Api/Integrations/GitHub/GitHubClient.cs
src/ImpactLedger.Api/Integrations/GitHub/GitHubPullRequestDto.cs
src/ImpactLedger.Api/Endpoints/GitHubEndpoints.cs
```

### Setup commands

```bash
dotnet new sln -n ImpactLedger
dotnet new webapi -n ImpactLedger.Api -o src/ImpactLedger.Api
dotnet sln add src/ImpactLedger.Api/ImpactLedger.Api.csproj

npm create vite@latest src/ImpactLedger.Web -- --template vue-ts
cd src/ImpactLedger.Web
npm install
```

### First backend endpoint

```text
GET /api/github/repos/{owner}/{repo}/pulls
```

```json

    "title": "Fix background job retry",
    "state": "closed",
    "url": "https://github.com/...",
    "createdAt": "...",
    "mergedAt": "..."
  }
]
```

### Expected result

Trong browser local, nhập một public repository và thấy danh sách PR lấy từ GitHub thật.

### Verification checklist

- [ ] API trả 200 cho repository public hợp lệ.
- [ ] Repository sai trả error rõ ràng.
- [ ] UI hiển thị loading state.
- [ ] UI hiển thị empty state.
- [ ] Click PR mở đúng GitHub URL.
- [ ] Không hard-code repository trong code.
- [ ] Không cần database để hoàn thành session này.

### Stop condition

Dừng ngay khi vertical slice **Browser → ASP.NET Core → GitHub API → Vue table** chạy thành công.

Không thêm authentication, PostgreSQL, background worker, AI hoặc architecture abstraction trong session đầu tiên. Mục tiêu hôm nay là chứng minh đường dữ liệu chính hoạt động end-to-end.
