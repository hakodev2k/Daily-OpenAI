# Ý tưởng hôm nay: RepoPolicy Lab — Mô phỏng chính sách GitHub trước khi push hoặc merge

## 1. Tóm tắt ý tưởng

**RepoPolicy Lab** là một developer tool chạy local để kiểm tra trước xem một branch, commit hoặc tập thay đổi có khả năng vi phạm GitHub repository rulesets trước khi developer push hoặc mở Pull Request hay không. Công cụ giúp cá nhân và nhóm nhỏ phát hiện sớm các vấn đề như branch name không hợp lệ, commit chưa được ký, file path bị cấm, file quá lớn, thiếu required checks trong cấu hình dự kiến hoặc thay đổi không phù hợp với policy của repository.

- **Project size:** Medium
- **Estimated MVP time:** 10–14 ngày làm ngoài giờ
- **Người dùng chính:** developer làm việc với nhiều repository có quy tắc merge/push khác nhau
- **Vấn đề chính:** policy thường chỉ “đánh” khi push hoặc merge, làm gián đoạn flow và buộc developer quay lại sửa lịch sử commit, branch hoặc file structure.

## 2. Bài toán thực tế

GitHub cung cấp **repository rulesets** để kiểm soát cách developer tương tác với branch và tag. Theo GitHub Docs, rulesets có thể yêu cầu Pull Request, required status checks, signed commits, linear history, chặn force push, hạn chế file path, extension, file size và nhiều điều kiện khác. Nguồn: [GitHub Docs — Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

GitHub cũng cho phép **push rulesets** để chặn push theo file path, path length, extension và file size. Nguồn: [GitHub Docs — Creating rulesets for a repository](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository).

### Fact đã xác nhận

GitHub mô tả rằng required status checks phải pass trước khi thay đổi được merge vào branch/tag bị ruleset bảo vệ. Rulesets cũng có thể yêu cầu commit được ký và xác minh, hoặc buộc mọi thay đổi vào target branch phải đi qua Pull Request. Nguồn: [GitHub Docs — Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

GitHub troubleshooting docs cũng ghi nhận rằng nếu commit metadata hoặc signing không thỏa rule, push có thể bị reject và developer đôi khi phải rebase hoặc rewrite history để sửa. Nguồn: [GitHub Docs — Troubleshooting rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/troubleshooting-rules).

### Quan sát

Trong workflow thực tế, developer thường chỉ nhận feedback đầy đủ ở một trong các thời điểm sau:

- khi push lên remote;
- khi tạo PR;
- khi merge;
- khi branch protection/ruleset reject;
- khi CI chạy xong.

Các lỗi này đôi khi rất rẻ nếu phát hiện trước push, ví dụ:

- branch name sai convention;
- commit message thiếu ticket ID;
- file `.pem`, `.pfx`, `.zip` hoặc artifact lớn nằm trong diff;
- commit chưa signed;
- chỉnh file ở path mà policy không cho phép;
- merge strategy không phù hợp;
- repository yêu cầu PR nhưng developer định push trực tiếp.

### Giả định cần kiểm chứng

MVP giả định rằng developer sẽ chấp nhận chạy một command như:

```bash
repopolicy check
```

trước khi push, hoặc cài Git hook để chạy tự động.

Nếu tool quá chậm, tạo quá nhiều false positive hoặc yêu cầu đồng bộ policy phức tạp, developer sẽ tắt nó. Đây là rủi ro adoption chính.

## 3. Người dùng mục tiêu

### Primary user

Developer làm việc cá nhân hoặc trong team nhỏ, thường xuyên sử dụng GitHub và có repository policy không giống nhau giữa các project.

### Context of use

- trước `git push`;
- trước khi mở PR;
- khi checkout một repository mới;
- khi repository admin vừa thay đổi policy;
- trong pre-push hook;
- trong CI như một check độc lập.

### Pain point chính

Developer không biết chắc local changes hiện tại có đáp ứng repository policy cho đến khi tương tác với GitHub remote.

### Current workaround

- đọc CONTRIBUTING.md;
- nhớ convention bằng kinh nghiệm;
- thử push rồi sửa;
- nhìn GitHub UI;
- dùng pre-commit hooks riêng lẻ;
- dùng script nội bộ không thống nhất giữa repo.

### Lý do họ thử RepoPolicy Lab

Một command thống nhất có thể trả lời:

> “Nếu push/merge trạng thái hiện tại, những policy nào có khả năng fail và cần sửa gì trước?”

## 4. Giải pháp đề xuất

RepoPolicy Lab gồm một CLI local với file policy declarative trong repository, ví dụ:

```yaml
version: 1
branch:
  allowedPatterns:
    - "feature/*"
    - "bugfix/*"
    - "hotfix/*"

commits:
  requireSigned: true
  messageRegex: "^(PROJ-[0-9]+|chore:|docs:)"

files:
  denyExtensions:
    - ".pfx"
    - ".pem"
  denyPaths:
    - "secrets/**"
    - "artifacts/**"
  maxFileSizeMb: 10

merge:
  requirePullRequest: true
  requiredChecks:
    - build
    - test
```

### Workflow chính

Developer chạy:

```bash
repopolicy check --base origin/main
```

Tool sẽ:

1. đọc `.repopolicy.yml`;
2. xác định current branch;
3. lấy commit range giữa `origin/main` và HEAD;
4. đọc commit metadata;
5. đọc danh sách changed files;
6. áp dụng local policy engine;
7. trả kết quả từng rule;
8. exit code `0` nếu pass, `1` nếu có blocking violations.

### Input

- local Git repository;
- `.repopolicy.yml`;
- base branch;
- optional fetched GitHub ruleset snapshot về sau.

### Processing

Rule engine deterministic kiểm tra:

- branch naming;
- signed commit metadata;
- commit message pattern;
- changed file path;
- extension;
- file size;
- protected path ownership rule đơn giản;
- whether direct push to protected branch is disallowed;
- required check names trong policy config.

### Output

Ví dụ:

```text
RepoPolicy Lab
Target: main
Base: origin/main

PASS branch-name        feature/PROJ-221-ruleset-check
FAIL commit-signature   2 commits are unsigned
PASS commit-message     4/4 commits match policy
FAIL file-path          artifacts/test-video.mp4 matches artifacts/**
WARN file-size          logs/debug.zip = 8.6 MB, threshold warning = 8 MB

Blocking violations: 2
Suggested actions:
- Sign or rewrite commits: 8ac21f1, 32f9aa4
- Remove artifacts/test-video.mp4 from the commit
```

### Điều gì được tự động

- diff inspection;
- Git metadata parsing;
- matching rules;
- severity classification;
- machine-readable JSON output;
- optional Git hook installation.

### Điều gì user kiểm soát

- policy file;
- severity của rule;
- base branch;
- warning threshold;
- whether a rule blocks push;
- whether hook is enabled.

### Key differentiator

Không cố thay GitHub rulesets. RepoPolicy Lab là **shift-left simulator**: đưa một subset quan trọng của repository policy về local machine để developer biết lỗi trước khi GitHub reject.

### Ví dụ end-to-end

Một developer đang làm branch `feature/payment-fix`, commit 3 file và chạy `repopolicy check`. Tool phát hiện một commit chưa signed và một file `debug-output.zip` vượt rule local. Developer sửa ngay, chạy lại đến khi pass rồi mới push. GitHub vẫn là nguồn enforcement cuối cùng; RepoPolicy Lab chỉ giảm số vòng push-fail-fix.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

- giảm push/merge failure có thể tránh được;
- giảm số lần rewrite Git history sau khi remote reject;
- giúp onboarding repo mới nhanh hơn;
- làm policy trở nên executable thay vì chỉ nằm trong documentation.

### Technical learning value

Dự án chạm nhiều kỹ năng senior-level nhưng scope vẫn rõ:

- Git internals;
- CLI design;
- deterministic policy engines;
- YAML config validation;
- pattern matching;
- process execution;
- exit codes;
- Git hooks;
- GitHub API integration về sau;
- config drift detection.

### Vì sao phù hợp solo developer

Core MVP không cần database, backend hay frontend. Chỉ cần một CLI cross-platform, một config format và rule engine.

### Hữu ích dù chỉ có một user

Developer có thể dùng ngay trên các repo cá nhân, đặc biệt khi có nhiều repository với convention khác nhau.

### Điều gì khiến dự án thất bại

Nếu tool cố mô phỏng 100% behavior của GitHub rulesets, scope sẽ bùng nổ và dễ sai khác với server-side enforcement.

### Lý do mạnh nhất để không build

GitHub đã có server-side enforcement rất mạnh. Nếu team hiếm khi bị reject hoặc policy rất đơn giản, giá trị của một local simulator có thể không đủ lớn.

## 7. Luồng hoạt động

### Main flow

Developer chạy command
→ tool tìm Git root
→ đọc config
→ validate config
→ xác định base ref
→ chạy Git commands lấy branch/commits/files
→ normalize metadata
→ chạy từng rule evaluator
→ aggregate findings
→ render terminal output
→ trả exit code.

### Alternative flow: repo chưa fetch remote

Nếu `origin/main` không tồn tại local:

→ tool không tự ý fetch trong MVP
→ trả lỗi rõ:

```text
Base ref origin/main not found locally.
Run: git fetch origin main
```

### Alternative flow: config không tồn tại

→ suggest:

```bash
repopolicy init
```

### Failure case: malformed YAML

→ hiển thị line/column nếu parser hỗ trợ
→ exit code riêng cho config error.

### Failure case: Git command fail

→ không biến thành policy violation
→ trả technical error riêng để CI phân biệt.

### Failure case: shallow clone

Nếu commit range không đủ:

→ cảnh báo `history incomplete`
→ không claim pass tuyệt đối cho commit rules.

### Failure case: merge commit phức tạp

MVP dùng `git diff --name-only base...HEAD` và commit range rõ ràng. Không cố mô phỏng merge queue hoặc server-generated merge commit.

## 11. API và tích hợp

### 1. Git executable

**Purpose:** đọc repository state.

**Authentication:** không cần cho local operations.

**Cost/rate limit:** không có.

**Privacy:** data không rời máy.

**Fallback:** nếu Git không tồn tại, fail fast với installation guidance.

### 2. GitHub REST API — Later

Có thể dùng để đọc rulesets của repository nếu user có quyền phù hợp.

MVP không nên phụ thuộc GitHub API vì mục tiêu đầu tiên là local policy-as-code.

**Authentication:** GitHub token / device flow hoặc GitHub CLI token về sau.

**Rate limit:** phải tôn trọng GitHub API limits.

**Privacy:** repo metadata gửi tới GitHub vốn đã là remote metadata; token phải lưu an toàn.

**Fallback:** `.repopolicy.yml` local.

### 3. GitHub rulesets format — Reference only trong MVP

RepoPolicy Lab không tuyên bố tái hiện toàn bộ semantics của GitHub. Policy local chỉ lấy cảm hứng từ các rule có giá trị shift-left rõ ràng.

GitHub xác nhận rulesets có thể yêu cầu signed commits, pull requests, status checks, block force push, file path/extension/size restrictions. Nguồn: [GitHub Docs — Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Đây là bài toán validation deterministic.

Các operation chính đều có rule rõ ràng:

- regex;
- glob;
- boolean flags;
- signature status;
- file size;
- branch identity;
- commit metadata.

Dùng AI để quyết định một push có vi phạm policy hay không sẽ làm kết quả khó giải thích và kém ổn định hơn.

### AI có thể hữu ích về sau ở đâu?

Một use case phụ là biến policy text tự nhiên từ CONTRIBUTING.md thành **draft config**, ví dụ:

> “Branches must start with feature/, commits need PROJ ticket, do not commit certificate files.”

AI có thể đề xuất YAML nhưng user phải review. Đây không thuộc MVP.

## 15. Rủi ro và cách xử lý

### Rủi ro 1: cố mô phỏng GitHub quá nhiều

**Mitigation:** chỉ claim support cho subset rõ ràng. Mỗi rule phải có documentation “local approximation” hay “exact deterministic local check”.

### Rủi ro 2: false positive

**Mitigation:**

- explicit config;
- warning/error levels;
- explain command;
- tests bằng fixture repositories;
- no heuristic trong blocking rule.

### Rủi ro 3: performance trong repo lớn

**Mitigation:**

- chỉ inspect commit range cần thiết;
- không scan toàn working tree;
- limit expensive file operations;
- measure runtime;
- cache không cần ở MVP.

### Rủi ro 4: signed commit detection khác GitHub

GitHub có semantics verification riêng. RepoPolicy Lab chỉ nên detect local signature existence/status mà Git cung cấp, không tuyên bố match 100% GitHub verified state.

### Rủi ro 5: config trở thành policy duplicate

Nếu GitHub và `.repopolicy.yml` khác nhau, user có thể hiểu sai.

**Mitigation:**

- tài liệu nói GitHub là enforcement source of truth;
- về sau thêm drift check hoặc generated config;
- MVP không tự claim sync.

### Rủi ro 6: hook bị bypass

Local hook luôn có thể bypass. Tool không phải security boundary.

**Mitigation:** GitHub server-side ruleset vẫn là enforcement cuối cùng.

### Rủi ro 7: scope creep thành full DevSecOps platform

**Mitigation:** MVP chỉ check local Git policy. Không dashboard, no agent, no org management, no SaaS.

4. Commit unsigned khi `requireSigned=true` → fail.

## Kết luận lựa chọn

**Confirmed fact:** GitHub có hệ thống rulesets mạnh với nhiều rule có thể reject push/merge hoặc buộc workflow cụ thể.

**Observation:** một subset đáng kể của các rule này có thể kiểm tra hoàn toàn local trước khi tương tác với GitHub.

**Analysis:** một local preflight tool có giá trị nếu nó giới hạn scope vào deterministic checks và không tuyên bố thay thế GitHub enforcement.

**Assumption:** developer sẵn sàng chạy một command nhanh hoặc cài pre-push hook nếu feedback rõ và ít false positive.

**Recommendation:** MVP chỉ tập trung `branch + commit metadata + changed file policy`. Không sync GitHub rulesets, không SaaS, không AI và không plugin framework trước khi chứng minh local preflight thực sự giảm push-fail-fix loops.
