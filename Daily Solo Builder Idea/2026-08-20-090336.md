# Ý tưởng hôm nay: NuGet Upgrade Rehearsal Lab

## 1. Tóm tắt ý tưởng

NuGet Upgrade Rehearsal Lab là một developer tool self-hosted giúp developer **thử nâng cấp NuGet package trong một môi trường cô lập trước khi áp dụng vào branch thật**. Công cụ tạo bản sao tạm của repository, nâng package theo policy, chạy restore/build/test, phát hiện vulnerability/deprecation còn lại và trả về một báo cáo upgrade có thể hành động.

- Người dùng chính: .NET developer hoặc team nhỏ duy trì nhiều project/package.
- Bài toán chính: biết package cần nâng cấp là một chuyện; biết nâng cấp phiên bản nào sẽ phá build, test hay dependency graph lại là chuyện khác.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

### Confirmed facts

NuGet hiện đã có nhiều tín hiệu native để phát hiện dependency có vấn đề:

- `dotnet package list --outdated` có thể liệt kê package có phiên bản mới.
- `dotnet package list --deprecated` phát hiện package đã bị deprecate.
- `dotnet package list --vulnerable` phát hiện package có known vulnerability.
- .NET 10 thay đổi audit để các project target .NET 10 mặc định kiểm tra cả transitive packages với `NuGetAuditMode=all`.
- .NET 10 có `dotnet package update`, bao gồm `--vulnerable`, để nâng package có vulnerability lên bản không còn vulnerability đã biết.

Nguồn chính thức:

- Microsoft Learn — Auditing package dependencies: https://learn.microsoft.com/en-us/nuget/concepts/auditing-packages
- Microsoft Learn — `dotnet package list`: https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-list
- Microsoft Learn — `dotnet package update`: https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-update
- Microsoft Learn — transitive audit behavior in .NET 10: https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/10.0/nugetaudit-transitive-packages
- Microsoft Learn — package deprecation: https://learn.microsoft.com/en-us/nuget/nuget-org/deprecate-packages

### Observation

Các lệnh trên giúp trả lời **“package nào có vấn đề?”**, nhưng developer vẫn thường phải tự trả lời câu hỏi khó hơn:

- Nâng từ `8.x` lên `9.x` có build được không?
- Nếu package A nâng lên thì transitive package B có thay đổi gì?
- Test nào fail sau upgrade?
- Cần nâng một package hay cả một nhóm package cùng lúc?
- Một major upgrade có đáng làm ngay hay nên giữ phiên bản hiện tại?

### Assumption cần kiểm chứng

Developer duy trì solution có nhiều project sẽ thấy giá trị ở một tool tự động chạy các “upgrade rehearsal” theo policy thay vì tự tạo branch, sửa version, build, test và rollback thủ công cho từng dependency.

### Cách xử lý hiện tại

- Chạy Dependabot/Renovate rồi xem PR có pass CI không.
- Tự sửa version trong `.csproj` hoặc `Directory.Packages.props`.
- Chạy `dotnet restore`, `dotnet build`, `dotnet test`.
- Rollback nếu lỗi.
- Với major upgrade, thử từng package hoặc nhiều tổ hợp bằng tay.

Điểm bất tiện là quá trình này lặp lại, tốn thời gian và thiếu một báo cáo thống nhất về **impact**.

## 3. Người dùng mục tiêu

**Primary user:** backend developer .NET duy trì solution có từ 5–30 NuGet dependencies và có CI/test cơ bản.

- Bối cảnh sử dụng: trước sprint dependency cleanup, khi audit báo vulnerability, hoặc khi chuẩn bị nâng .NET SDK/framework.
- Main pain point: không biết dependency update nào an toàn, update nào kéo theo breaking change thực tế.
- Workaround: tạo branch tạm và chạy build/test thủ công.
- Lý do thử tool: nhận được kết quả kiểu “safe patch/minor”, “requires coordinated update”, “breaks compile”, “tests regress” trước khi đụng vào branch làm việc.

MVP chỉ phục vụ repository local/self-hosted, chưa cần multi-tenant SaaS.

## 4. Giải pháp đề xuất

Người dùng trỏ tool tới một repository local hoặc Git URL và chọn policy:

```text
Mode: PatchMinorOnly
Target: MySolution.sln
Tests: dotnet test
Timeout: 20m
```

Tool sẽ:

1. Clone hoặc copy repository vào workspace tạm.
2. Chạy baseline restore/build/test.
3. Quét package outdated/deprecated/vulnerable.
4. Chọn candidate update theo policy.
5. Tạo từng rehearsal độc lập.
6. Update package trong workspace.
7. Chạy restore/build/test lại.
8. So sánh dependency graph và test result với baseline.
9. Lưu kết quả.
10. Xuất Markdown/JSON report.

### Ví dụ end-to-end

Solution có:

```text
Serilog.AspNetCore 8.0.1
Npgsql 8.0.3
FluentValidation 11.9.0
```

Tool phát hiện:

- `Serilog.AspNetCore` có minor update.
- `Npgsql` có major version mới.
- một transitive dependency có vulnerability.

Policy `PatchMinorOnly` sẽ rehearsal các update patch/minor trước.

Kết quả:

```text
Serilog.AspNetCore 8.0.1 -> 8.0.3
Restore: PASS
Build: PASS
Tests: 142/142 PASS
Risk: LOW
Recommendation: Safe candidate
```

Một rehearsal khác:

```text
Package X 4.2.0 -> 5.0.0
Restore: PASS
Build: FAIL
Compiler errors: 7
Affected projects: Api, Infrastructure
Risk: HIGH
Recommendation: Manual migration required
```

**Điểm khác biệt:** công cụ không chỉ báo “có bản mới”, mà **chứng minh mức impact bằng build/test thực tế trong sandbox**.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Developer có thể dùng cho chính repository của mình ngay từ MVP. Nếu chỉ tránh được vài lần tạo branch tạm hoặc một dependency upgrade gây lỗi CI thì tool đã có giá trị.

### Technical learning value

Dự án chứa các bài toán đáng học:

- process orchestration;
- sandbox workspace;
- parsing CLI JSON;
- package graph analysis;
- timeout/cancellation;
- reproducible execution;
- CI integration.

### Vì sao phù hợp solo developer

Core flow nhỏ và deterministic. Không cần AI, không cần big data, không cần distributed system. Có thể bắt đầu bằng CLI rồi mới thêm dashboard.

### Vì sao vẫn hữu ích với rất ít user

Một developer duy trì vài repository .NET đã có thể dùng nó định kỳ để giảm dependency debt.

### Điều gì làm ý tưởng thất bại

Nếu repository có test coverage thấp thì “build/test pass” không đồng nghĩa upgrade an toàn về behavior.

### Lý do mạnh nhất để không build

Dependabot/Renovate + CI đã giải quyết một phần đáng kể nhu cầu này. Nếu workflow hiện tại đã tự động tạo PR và CI rất nhanh, lợi ích bổ sung của tool phải đến từ **local rehearsal, batch comparison và richer impact report**.

## 6. Phạm vi MVP

### Must have

- Nhận path tới repository local.
- Phát hiện `.sln`, `.csproj`, `Directory.Packages.props`.
- Chạy baseline `restore`, `build`, `test`.
- Đọc package bằng `dotnet package list --format json`.
- Hỗ trợ policy patch/minor only.
- Tạo workspace riêng cho mỗi rehearsal.
- Update một package mỗi rehearsal.
- Capture exit code, duration, stdout/stderr.
- So sánh baseline với rehearsal.
- Sinh Markdown report.
- Cleanup workspace an toàn.

### Should have

- `--vulnerable` mode.
- `--deprecated` report.
- Grouped package updates.
- Timeout/cancellation.
- Ignore list.
- Config file YAML/JSON.
- Git diff sau update.

### Later

- GitHub PR comment.
- Scheduled scan.
- Docker executor.
- Multi-repository dashboard.
- Major-version migration hints.
- Historical reliability score theo package.
- GitHub App/SaaS.

## 7. Luồng hoạt động

Repository
→ validate repo/SDK
→ detect solution/projects
→ baseline restore/build/test
→ package scan
→ build candidate list
→ create isolated workspace
→ update candidate package
→ restore
→ build
→ test
→ collect dependency graph/result
→ compare with baseline
→ persist report
→ cleanup.

### Failure cases

- Baseline đã fail: dừng rehearsal và báo `BaselineInvalid`.
- Package source yêu cầu auth: báo rõ source nào fail, không log credential.
- Update gây restore conflict: classify `DependencyConflict`.
- Build timeout: terminate process tree và classify `Timeout`.
- Test flaky: cho phép retry sau MVP, nhưng MVP phải đánh dấu kết quả không chắc chắn thay vì giả định package gây lỗi.
- Workspace cleanup fail: giữ path trong report để user dọn thủ công.

### xUnit

Unit + integration tests.

## 11. API và tích hợp

### .NET CLI

**Purpose:** package discovery, restore, build, test và update.

- Authentication: dùng NuGet config/source auth hiện có trên máy.
- Cost: miễn phí.
- Rate limit: phụ thuộc package source.
- Privacy: không log credential hoặc full authenticated source URL.
- Fallback: nếu JSON output unsupported, báo SDK không tương thích thay vì parse console text mong manh.

### NuGet.org / configured NuGet sources

**Purpose:** lấy package metadata/version/vulnerability data thông qua NuGet tooling.

- Authentication: nuget.org public không cần auth; private feed có thể cần credential.
- Rate limit: không giả định unlimited; nên cache metadata theo run sau MVP.
- Privacy: private feed URL có thể chứa thông tin tổ chức.
- Fallback: dùng restore/package list kết quả hiện có nếu network tạm lỗi.

### Git

**Purpose:** xác định commit và tạo isolated workspace/worktree.

- Authentication: chỉ cần nếu clone remote.
- MVP fallback: chỉ support local repo.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core bài toán có thể giải quyết tốt hơn bằng deterministic tooling:

- package discovery;
- semantic version comparison;
- update;
- restore/build/test;
- diff;
- risk classification.

AI có thể được thêm sau này để tóm tắt compiler error hoặc migration guide, nhưng không nên quyết định package có “safe” hay không.

Fallback luôn là raw evidence từ build/test/log.

## 14. Các bài toán kỹ thuật đáng học

### 1. Reliable process orchestration

Phải chạy command dài, capture output, timeout và kill process tree đúng cách. Kỹ năng: robust tooling/background execution.

### 2. Reproducible workspace isolation

Không được sửa repo thật khi rehearsal. Kỹ năng: Git worktree, temp filesystem, cleanup và isolation.

### 3. Dependency graph reasoning

Một direct package có thể kéo nhiều transitive package. Kỹ năng: đọc package graph và xác định nguyên nhân dependency.

### 4. Result classification

Phân biệt restore conflict, compile break, test regression, infrastructure failure và timeout. Kỹ năng: error taxonomy/diagnostics.

### 5. Flaky-test handling

Một test fail sau upgrade chưa chắc do dependency. Kỹ năng: retry policy, baseline comparison và confidence scoring.

## 15. Rủi ro và cách xử lý

### False confidence

**Risk:** build/test pass nhưng production behavior vẫn lỗi.

**Mitigation:** report phải dùng từ “candidate” thay vì “guaranteed safe”; hiển thị test count và coverage nếu user cung cấp.

### Flaky tests

**Risk:** package bị đánh dấu unsafe do test vốn đã flaky.

**Mitigation:** baseline test trước; sau MVP cho phép retry và lịch sử flaky.

### Private package source

**Risk:** credential bị ghi vào logs.

**Mitigation:** không serialize NuGet credentials; redact URL query/userinfo và known secret patterns.

### Runtime cost

**Risk:** 20 candidates × full test suite có thể rất chậm.

**Mitigation:** giới hạn concurrency, policy patch/minor, configurable test command và stop-after-N-failures.

### Scope expansion

**Risk:** biến thành full dependency-management platform.

**Mitigation:** MVP chỉ rehearsal + report; không tự merge PR.

### Tooling version differences

**Risk:** CLI output/behavior khác theo SDK.

**Mitigation:** detect SDK version, ưu tiên JSON output và test matrix .NET 8/9/10.

## 16. Kiểm thử

### Strategy

- Unit test cho version policy và risk classification.
- Integration test chạy với fixture solution thật.
- End-to-end test CLI trên temporary Git repo.
- Failure-path test cho restore/build/test timeout.
- Security test cho log redaction và path traversal.
- Data-quality test đảm bảo baseline/rehearsal mapping đúng package/project.

### 5 test scenario quan trọng nhất

1. Patch update restore/build/test đều pass → `LOW`.
2. Update gây compile error → `HIGH`, giữ compiler evidence.
3. Baseline test fail trước update → dừng và trả `BaselineInvalid`.
4. Private source error không làm lộ credential trong report/log.
5. Cancel run giữa `dotnet test` → process bị terminate, workspace được cleanup.

## 17. Cách đo dự án có hữu ích hay không

Metrics thực tế:

- **Rehearsal completion rate:** % candidate chạy tới kết quả rõ ràng.
- **Manual time saved:** thời gian dependency maintenance trước/sau khi dùng tool.
- **Actionable result rate:** % result dẫn tới update accepted, deferred hoặc rejected có lý do.
- **False classification rate:** package được báo PASS nhưng PR thật fail CI vì nguyên nhân tool đáng lẽ phát hiện được.
- **Repeated use:** số tuần có ít nhất một run.
- **Reliability:** % run không fail do chính tool.

Mục tiêu cá nhân hợp lý trong 30 ngày:

- chạy trên ít nhất 3 repository;
- rehearsal 20+ dependency updates;
- giảm ít nhất 50% thao tác branch/build/test thủ công trong dependency maintenance.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, tạo vertical slice đầu tiên:

**scan package outdated → chọn một candidate → tạo temp copy → update → build → in PASS/FAIL**.

### Files/components cần tạo

```text
NuGetUpgradeLab.sln
src/
  NuGetUpgradeLab.Cli/
    Program.cs
    PackageScanner.cs
    WorkspaceManager.cs
    CommandRunner.cs
    RehearsalRunner.cs
    Models.cs
tests/
  NuGetUpgradeLab.Tests/
```

### Setup commands

```bash
dotnet new sln -n NuGetUpgradeLab
dotnet new console -n NuGetUpgradeLab.Cli -o src/NuGetUpgradeLab.Cli
dotnet new xunit -n NuGetUpgradeLab.Tests -o tests/NuGetUpgradeLab.Tests
dotnet sln add src/NuGetUpgradeLab.Cli
dotnet sln add tests/NuGetUpgradeLab.Tests
dotnet add tests/NuGetUpgradeLab.Tests reference src/NuGetUpgradeLab.Cli
```

### First vertical slice

Command dự kiến:

```bash
dotnet run --project src/NuGetUpgradeLab.Cli -- scan /path/to/sample-repo
```

Flow đầu tiên:

1. Chạy:

```bash
dotnet package list --outdated --format json
```

2. Parse candidate đầu tiên.
3. Copy repo vào temp directory.
4. Trong temp directory, chạy package update cho candidate.
5. Chạy:

```bash
dotnet restore
dotnet build --no-restore
dotnet test --no-build
```

6. In kết quả:

```text
Package: Example.Package
From: 1.2.0
To: 1.2.3
Restore: PASS
Build: PASS
Tests: PASS
Workspace: <temp-path>
```

### Expected result

Tool chứng minh được giá trị cốt lõi: một package update được thử nghiệm mà **repo gốc không bị thay đổi**.

### Verification checklist

- [ ] Repo gốc không có Git diff sau run.
- [ ] Candidate package được parse từ JSON output.
- [ ] Temp workspace có version mới.
- [ ] Exit code restore/build/test được capture đúng.
- [ ] Build failure trả non-zero result rõ ràng.
- [ ] Có ít nhất một integration test với fixture project.

### Stop condition

Dừng session khi bạn có thể chạy một command lên sample repository và nhận được kết quả PASS/FAIL cho một package update trong temp workspace, đồng thời `git status` của repository gốc vẫn sạch.
