# Ý tưởng hôm nay: Dependency Upgrade Rehearsal Lab

## 1. Tóm tắt ý tưởng

Dependency Upgrade Rehearsal Lab là một developer tool giúp tự động **thử nâng cấp dependency trong môi trường tạm**, build/test project, ghi lại lỗi phát sinh và tạo báo cáo “upgrade nào an toàn, upgrade nào phá vỡ hệ thống” trước khi developer sửa file project thật. Người dùng chính là .NET developer có nhiều package NuGet, thường trì hoãn upgrade vì sợ breaking change và mất thời gian thử từng version.

- Project size: **Medium**.
- Estimated MVP time: **2–3 tuần**.

## 2. Bài toán thực tế

Dependency update là công việc lặp lại nhưng có chi phí nhận thức cao. Một package mới có thể build được nhưng làm integration test lỗi, thay đổi transitive dependency, yêu cầu migration, hoặc tạo warning mới. Khi có nhiều dependency, việc nâng từng package rồi revert thủ công rất mất thời gian.

**Confirmed facts từ nguồn hiện tại:**

- GitHub Dependabot có thể tự động tạo pull request cho version update và security update; GitHub mô tả workflow chuẩn là review changelog, chạy test rồi merge. Dependabot cũng hỗ trợ grouping để giảm số lượng PR cần review. [GitHub Docs — Dependabot version updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-version-updates) và [Optimizing Dependabot PR creation](https://docs.github.com/en/code-security/tutorials/secure-your-dependencies/optimizing-pr-creation-version-updates)
- Với .NET 10, `dotnet package list --outdated` có thể liệt kê package có version mới; command hỗ trợ output JSON, `--include-transitive`, `--vulnerable` và các filter version. [Microsoft Learn — dotnet package list](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-list)
- .NET 10 hiện là LTS và đang trong active support theo policy Microsoft cập nhật tháng 7/2026. [Official .NET Support Policy](https://dotnet.microsoft.com/en-us/platform/support/policy)

**Observation:** Dependabot rất tốt ở bước phát hiện + tạo PR, nhưng developer vẫn phải chờ CI hoặc tự checkout từng PR để hiểu package nào thực sự phá vỡ solution.

**Assumption cần validate:** solo developer và team nhỏ sẽ thấy có giá trị ở một tool local/self-hosted có thể chạy một “upgrade rehearsal matrix” trước khi tạo PR hoặc trước khi chấp nhận Dependabot PR.

Workaround hiện tại thường là:

- `dotnet add package ...` rồi `dotnet test`.
- Checkout Dependabot PR và debug thủ công.
- Update nhiều package cùng lúc rồi khó xác định package nào gây lỗi.
- Trì hoãn upgrade cho đến khi có security issue hoặc framework migration.

Điểm bất tiện chính là thiếu một workflow lặp lại, có lịch sử và có khả năng cô lập lỗi theo từng dependency/version.

## 3. Người dùng mục tiêu

Primary user: **.NET backend developer hoặc solo builder** có một hoặc nhiều solution dùng NuGet.

- Context of use: trước sprint maintenance, trước migration .NET mới, hoặc sau khi Dependabot báo nhiều package outdated.
- Main pain point: không biết package nào nâng cấp được an toàn mà không phải thử thủ công từng package.
- Current workaround: update package → build → test → revert → lặp lại.
- Reason to try: chạy một command và nhận bảng kết quả rõ ràng package nào PASS, package nào FAIL, lỗi ở build hay test nào.

MVP chỉ tối ưu cho NuGet/.NET; không cố hỗ trợ npm, pip, Maven ngay từ đầu.

## 4. Giải pháp đề xuất

Tool nhận một repository hoặc solution path, đọc danh sách package outdated, sau đó tạo các **upgrade experiment** tách biệt.

### Workflow chính

Input:

- Repository path.
- `.sln` hoặc `.slnx`.
- Upgrade policy, ví dụ `patch-only`, `minor`, `major` hoặc danh sách package cụ thể.
- Commands cần verify, ví dụ `dotnet build`, `dotnet test`.

Processing:

1. Snapshot trạng thái repository hiện tại.
2. Lấy danh sách dependency outdated.
3. Với từng candidate, tạo temporary Git worktree hoặc working copy.
4. Update đúng một package/version.
5. Restore.
6. Build.
7. Test.
8. Ghi duration, warnings, failed tests và diff package graph.
9. Cleanup sandbox.

Output:

Một report như:

```text
Package                         From     To       Result
---------------------------------------------------------
Serilog.AspNetCore              9.0.0    10.0.0   PASS
FluentValidation.AspNetCore     11.3.0   12.0.0   BUILD_FAIL
Npgsql.EntityFrameworkCore...   9.0.4    10.0.1   TEST_FAIL
Polly                           8.5.0    8.6.2    PASS
```

Developer có thể chọn một PASS experiment và yêu cầu tool tạo patch/branch tương ứng.

### Concrete example

Một ASP.NET Core API có 18 package outdated. Developer chạy:

```bash
upgrade-lab scan MyApp.sln --policy minor --run "dotnet test"
```

Tool tìm thấy 7 candidate phù hợp. Sau 12 phút:

- 4 package PASS.
- 1 package build fail vì API bị rename.
- 2 package test fail.

Developer có thể upgrade ngay 4 package an toàn, sau đó tập trung review 3 package còn lại.

**Key differentiator:** không phải chỉ “package update bot”; sản phẩm tập trung vào **rehearsal + isolation + evidence** trước khi thay đổi main working tree.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Ngay cả một người dùng duy nhất cũng có thể dùng tool hàng tháng cho repository cá nhân. Nó giảm thao tác lặp lại và làm dependency maintenance ít rủi ro hơn.

### Technical learning value

Dự án giúp học sâu:

- Process orchestration.
- Git worktree.
- CLI design.
- NuGet dependency graph.
- Test result parsing.
- Cancellation/timeouts.
- Isolation và reproducibility.

### Vì sao phù hợp solo developer

MVP có thể là CLI thuần local. Không cần frontend, auth, cloud hay database server. Core value nằm ở orchestration engine.

### Vì sao vẫn hữu ích khi ít user

Nó là personal developer utility thực sự, không cần network effect.

### Điều gì làm ý tưởng thất bại

- Experiment chạy quá chậm.
- False confidence: PASS nhưng production vẫn lỗi.
- Tool không xử lý tốt Central Package Management hoặc multi-targeting.
- Developer đã hài lòng với Dependabot + CI hiện có.

### Lý do mạnh nhất để không build

Nếu các repository của bạn có test suite rất tốt và Dependabot PR chạy CI nhanh, phần lớn giá trị của tool đã được pipeline hiện tại cung cấp.

## 6. Phạm vi MVP

### Must have

- Detect `.sln`/`.slnx` và project files.
- Chạy `dotnet package list --outdated --format json`.
- Parse top-level NuGet package candidates.
- Tạo isolated temporary workspace bằng Git worktree.
- Upgrade đúng một package trong mỗi experiment.
- Chạy restore/build/test command.
- Capture exit code, duration, stdout/stderr.
- Report PASS / RESTORE_FAIL / BUILD_FAIL / TEST_FAIL / TIMEOUT.
- Cleanup worktree an toàn.
- Export Markdown + JSON report.

### Should have

- Patch-only/minor/major policy.
- Parallelism giới hạn, ví dụ 2–4 experiment đồng thời.
- Filter package.
- Baseline test trước experiment.
- Parse `.trx` để liệt kê failed tests.
- Compare warnings.
- Resume failed/interrupted run.

### Later

- GitHub PR integration.
- Dependabot PR ingestion.
- Group upgrade experiment.
- Docker sandbox.
- Multi-framework support.
- Changelog/release-note aggregation.
- AI-assisted failure explanation.

## 7. Luồng hoạt động

User command
→ validate Git repository/solution
→ verify working tree policy
→ run baseline restore/build/test
→ query outdated packages
→ generate candidate experiments
→ create isolated worktree
→ apply package update
→ restore
→ build
→ test
→ capture artifacts
→ persist result
→ cleanup
→ aggregate report.

### Failure cases quan trọng

- Baseline đã fail: dừng scan hoặc đánh dấu results không đáng tin.
- Package restore cần private feed auth: reuse NuGet config hoặc báo explicit authentication error.
- Update gây project file invalid: experiment = `UPDATE_FAIL`.
- Test treo: timeout + kill process tree.
- User stop bằng Ctrl+C: cancellation token cleanup worktree.
- Disk đầy: stop scheduling new experiments.
- Repository có uncommitted changes: MVP chỉ rehearsal trên `HEAD`, không âm thầm copy dirty changes.

## 8. Kiến trúc đề xuất

MVP nên là **modular CLI monolith**.

### CLI

Commands:

```text
upgrade-lab scan
upgrade-lab run
upgrade-lab report
upgrade-lab clean
```

### Core modules

- `RepositoryInspector`
- `PackageDiscovery`
- `ExperimentPlanner`
- `WorkspaceManager`
- `CommandRunner`
- `ResultCollector`
- `ReportGenerator`

### Database

Không cần PostgreSQL ở MVP. Dùng JSON files trong:

```text
.upgrade-lab/runs/{run-id}/
```

### Background worker

Không cần service background lâu dài. CLI orchestration bằng async tasks là đủ.

### Queue

Không cần broker. Dùng `Channel<T>` hoặc `SemaphoreSlim` để giới hạn concurrency.

### Cache

Không cần Redis. Có thể tận dụng NuGet global package cache mặc định.

### File storage

Local filesystem để lưu logs, report, TRX và metadata.

### Authentication

Không cần account/auth ở local MVP. Private NuGet feeds dùng credential mechanism hiện có của `dotnet restore`.

### External APIs

Không cần API ngoài cho core workflow.

### AI model

Không cần.

### Logging

Structured console logging + log file cho mỗi experiment.

### Deployment

`dotnet tool` hoặc single-file executable cho Windows/Linux.

## 9. Công nghệ đề xuất

### .NET 10

Lựa chọn tốt nhất cho MVP vì đây là LTS hiện hành và phù hợp trực tiếp với ecosystem cần thao tác. Microsoft hiện liệt kê .NET 10 là LTS active support. [Official .NET Support Policy](https://dotnet.microsoft.com/en-us/platform/support/policy)

**Simpler alternative:** .NET 8 nếu cần chạy trên môi trường cũ.

**Outgrow point:** không phải vấn đề scale; CLI có thể tiếp tục ở .NET lâu dài.

### System.CommandLine

Phù hợp để xây CLI có subcommands/options rõ ràng.

**Simpler alternative:** parse `args` thủ công cho prototype.

### Git CLI

Gọi `git worktree` trực tiếp thay vì dùng full Git library.

**Why:** behavior tương thích với repository thật và giảm code.

**Alternative:** LibGit2Sharp nếu cần API thuần managed về sau.

### `System.Diagnostics.Process`

Dùng chạy `dotnet`, `git`, capture stdout/stderr, timeout và cancellation.

### JSON persistence

`System.Text.Json` đủ cho MVP.

**Outgrow point:** khi cần lịch sử hàng nghìn run và query dashboard thì chuyển SQLite/PostgreSQL.

### xUnit

Test planner, parser và process orchestration.

### Docker

Không bắt buộc trong MVP. Chỉ thêm khi muốn isolation mạnh hơn.

### GitHub Actions

Dùng build/test/release CLI binary; không cần tích hợp GitHub API ở MVP.

## 11. API và tích hợp

### .NET CLI

Purpose: discovery, package update, restore/build/test.

Authentication: kế thừa NuGet credential/config của môi trường người dùng.

Cost/rate limit: không có SaaS cost; NuGet source có thể có rate policy riêng.

Privacy: command có thể truy cập private package source.

Fallback: nếu JSON output không khả dụng, MVP nên báo unsupported SDK thay vì parse human-readable text không ổn định.

### Git

Purpose: worktree isolation, commit SHA, patch generation.

Authentication: core local flow không cần remote auth.

Fallback: nếu không phải Git repo, có thể thêm copy-directory sandbox sau; MVP nên yêu cầu Git.

### GitHub Dependabot — Later

GitHub xác nhận Dependabot có thể tạo PR để giữ dependency up-to-date và hỗ trợ configuration/grouping. [GitHub Docs](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-version-updates)

Purpose tương lai: import danh sách Dependabot PR và rehearsal từng PR.

Authentication: GitHub token/GitHub App khi feature này được thêm.

Fallback: local NuGet discovery vẫn là core workflow.

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

AI không nên quyết định PASS/FAIL. Core evaluation phải hoàn toàn deterministic dựa trên command exit code và test result.

Nếu thêm về sau, AI chỉ làm task:

- Tóm tắt compiler errors dài.
- Group repeated errors.
- Giải thích khả năng breaking API dựa trên logs + diff.
- Tạo “next investigation steps”.

Expected structured output:

```json
{
  "summary": "Build fails after package update",
  "likelyCause": "Removed extension method",
  "evidence": ["CS1061 in OrderService.cs:84"],
  "suggestedChecks": ["Review package migration guide"]
}
```

Validation:

- Không được đổi experiment result.
- Evidence phải map tới log line thực tế.
- Nếu evidence không tồn tại, bỏ AI summary.

Deterministic fallback: raw logs + failed-test list.

Risks: hallucination, source-code privacy, token cost và latency. Vì vậy AI không nằm trong MVP.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** chứng minh workflow có tiết kiệm thời gian.

Main tasks:

- Chọn một .NET repo thật có ít nhất 5 outdated package.
- Manually thử 3 package theo đúng workflow dự kiến.
- Ghi thời gian cho update/build/test/revert.

Expected output: danh sách metadata cần report và estimate thời gian tiết kiệm.

Completion criteria: ít nhất một package PASS và một package FAIL được cô lập rõ ràng.

### Phase 1 — Core MVP

**Goal:** chạy một experiment end-to-end.

Main tasks:

- CLI skeleton.
- Outdated package discovery.
- Worktree manager.
- Single-package updater.
- Build/test runner.
- Markdown report.

Expected output: command scan một solution và test lần lượt dependency.

Completion criteria: chạy ổn định trên một repo cá nhân có ít nhất 5 package candidate.

### Phase 2 — Reliability

**Goal:** xử lý failure và interruption an toàn.

Main tasks:

- Baseline verification.
- Timeout/cancellation.
- Worktree cleanup.
- Retry restore có giới hạn.
- TRX parsing.
- Integration tests.

Expected output: Ctrl+C hoặc test timeout không để lại repository bẩn.

Completion criteria: 10 failure-path tests pass.

### Phase 3 — Useful expansion

**Goal:** làm tool đủ tiện để dùng thường xuyên.

Main tasks:

- Concurrency limit.
- Version policy.
- Filter package.
- JSON report.
- Historical run comparison.
- Generate patch cho PASS experiment.

Expected output: dependency maintenance session thực tế có thể hoàn thành chủ yếu bằng tool.

### Phase 4 — Production readiness

**Goal:** distribution ổn định.

Main tasks:

- `dotnet tool` packaging.
- Windows/Linux CI matrix.
- Documentation.
- Semantic versioning.
- Telemetry opt-in hoặc không telemetry.
- Release artifacts.

Completion criteria: install từ package feed, chạy trên repo mới từ clean machine và có deterministic cleanup.

## 14. Các bài toán kỹ thuật đáng học

### 1. Process orchestration

Phải quản lý nhiều child process, output streams, timeout và cancellation. Đây là kỹ năng hữu ích cho CLI, CI runner và agent tooling.

### 2. Reproducible workspace isolation

Git worktree cho phép chạy experiment mà không làm bẩn working directory chính. Bài toán này giúp hiểu Git internals và reproducible automation.

### 3. Failure classification

Không chỉ biết “command failed”, mà phải phân biệt update/restore/build/test/timeout. Kỹ năng này rất gần production observability.

### 4. Concurrency control

Chạy nhiều experiment song song có thể tiết kiệm thời gian nhưng gây CPU/RAM/disk contention. Học bounded concurrency và backpressure.

### 5. Dependency graph reasoning

Một direct package update có thể kéo theo transitive dependency changes. Đây là cơ hội học sâu NuGet resolution và package compatibility.

## 15. Rủi ro và cách xử lý

### False confidence

Risk: build/test PASS nhưng production vẫn có runtime issue.

Mitigation: report phải gọi kết quả là “verification passed”, không gọi “production safe”; cho phép custom verification commands.

### Long runtime

Risk: 30 packages × full integration test suite quá lâu.

Mitigation: patch/minor filters, package whitelist, concurrency limit, fast verification profile trước full test.

### Dirty repository

Risk: tool làm mất uncommitted work.

Mitigation: MVP luôn chạy từ committed `HEAD` trong worktree mới; không sửa working tree chính.

### Private NuGet feeds

Risk: restore fail vì authentication.

Mitigation: reuse `NuGet.Config`; phân loại `RESTORE_AUTH_FAIL`; không log credentials.

### Disk growth

Risk: worktree/log artifacts chiếm dung lượng.

Mitigation: cleanup cuối run + `upgrade-lab clean`; retention policy.

### Scope creep

Risk: biến tool thành Dependabot/Renovate clone.

Mitigation: giữ core promise là “rehearse and verify upgrades”, không xây scheduler/PR bot trước.

### Platform differences

Risk: test chạy khác giữa Windows/Linux.

Mitigation: MVP ghi rõ execution environment; Docker mode để sau.

## 16. Kiểm thử

Testing strategy:

- Unit tests cho package/version policy và report generation.
- Integration tests với fixture Git repo thật được tạo trong temp directory.
- Process tests cho timeout/cancellation.
- End-to-end CLI tests trên sample solution.
- Security/privacy tests đảm bảo secret trong NuGet config không bị ghi log.

### 5 test scenario quan trọng nhất

1. Package upgrade thành công, build/test đều pass → `PASS`.
2. Package update làm compiler error → `BUILD_FAIL` với đúng log artifact.
3. Baseline test fail trước upgrade → scan dừng và không gán lỗi cho package.
4. Test command treo → timeout, kill child process và cleanup worktree.
5. Ctrl+C giữa experiment → run được đánh dấu cancelled và repository chính không thay đổi.

- 0 dirty working tree incidents.

### AI quality metric

Không áp dụng ở MVP.

Success signal tốt nhất: sau 4 tuần, tool được dùng ít nhất 3 lần và giúp xác định nhanh package nào có thể update mà không cần manual update/revert từng package.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, hoàn thành vertical slice:

**discover outdated packages → chọn một package → tạo Git worktree → build solution → cleanup.**

Chưa cần update package tự động nếu hết thời gian; nhưng session phải chứng minh sandbox orchestration hoạt động.

### Files/components cần tạo

```text
DependencyUpgradeLab.sln
src/
  UpgradeLab.Cli/
```

### First vertical slice

Implement `ProcessRunner` để chạy:

```bash
dotnet package list --outdated --format json
```

Parse ít nhất:

```text
PackageId
ResolvedVersion
LatestVersion
ProjectPath
```

Sau đó implement:

```bash
git worktree add <temp-path> HEAD
```

Trong worktree:

```bash
dotnet build <solution>
```

Cuối cùng:

```bash
git worktree remove <temp-path> --force
```

### Expected result

CLI output tối thiểu:

```text

Commit: abc1234

[1] Serilog.AspNetCore 9.0.0 -> 10.0.0

Creating sandbox...
Build: PASS (8.4s)
Cleanup: PASS
```

### Verification checklist

- [ ] `dotnet package list --outdated --format json` được parse bằng code, không regex console text.
- [ ] Temporary worktree nằm ngoài repo chính.
- [ ] `dotnet build` chạy thành công trong worktree.
- [ ] Working tree chính không thay đổi.
- [ ] Temp worktree được xóa sau success.
- [ ] Temp worktree cũng được cleanup khi build throw exception.
- [ ] Có ít nhất một automated test cho `ProcessRunner` hoặc parser.

### Stop condition

Dừng session khi CLI có thể chạy trên một repository .NET thật, hiển thị ít nhất một outdated package, tạo sandbox worktree, build trong sandbox và cleanup hoàn toàn mà `git status` ở repository chính vẫn sạch.
