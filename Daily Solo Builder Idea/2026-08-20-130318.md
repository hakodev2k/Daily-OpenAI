# Ý tưởng hôm nay: LicenseDrift Watcher — Dependency License Change Monitor

## 1. Tóm tắt ý tưởng

LicenseDrift Watcher là một developer tool self-hosted giúp theo dõi license của các dependency trong project .NET theo từng version, phát hiện khi package mới đổi license, mất metadata license, chuyển sang license có điều kiện chặt hơn hoặc xuất hiện dependency mới chưa được review. Công cụ phù hợp với solo developer, indie SaaS và team nhỏ muốn tránh việc update package “vẫn build được” nhưng vô tình làm thay đổi nghĩa vụ phân phối hoặc compliance.

- Người dùng chính: backend developer hoặc solo SaaS developer dùng nhiều NuGet packages.
- Bài toán chính: dependency update có thể thay đổi license/compliance nhưng pipeline thường chỉ kiểm tra build, test và vulnerability.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Một project .NET có thể phụ thuộc trực tiếp và gián tiếp vào hàng chục hoặc hàng trăm NuGet packages. Developer thường chú ý đến version, security advisory và breaking API, nhưng license dễ bị xem như metadata tĩnh.

**Confirmed facts:**

- NuGet hỗ trợ khai báo license bằng `PackageLicenseExpression` sử dụng SPDX identifier hoặc bằng `PackageLicenseFile` nếu license tùy chỉnh. Microsoft khuyến nghị package author khai báo license rõ ràng và lưu ý rằng package không có license mặc định vẫn thuộc exclusive copyright. Nguồn: Microsoft Learn — NuGet library guidance: https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/nuget
- File `.nuspec` có thể chứa SPDX license expression như `MIT`, `BSD-2-Clause OR MIT`, hoặc một license file đóng gói bên trong package. Nguồn: Microsoft Learn — `.nuspec` reference: https://learn.microsoft.com/en-us/nuget/reference/nuspec
- Microsoft khuyến nghị không dùng `LicenseUrl` cũ vì một URL thay đổi có thể tạo ambiguity đối với các version package trước; license expression/file giúp metadata license gắn chặt với package version hơn. Nguồn: Microsoft Learn — package authoring best practices: https://learn.microsoft.com/en-us/nuget/create-packages/package-authoring-best-practices
- SPDX định nghĩa chuẩn license identifiers và license expressions như `AND`, `OR`, `WITH`, giúp công cụ có thể parse license theo cách machine-readable thay vì chỉ so sánh chuỗi. Nguồn: SPDX — Handling License Info: https://spdx.dev/learn/handling-license-info/

**Observation:** tooling dependency phổ biến thường tập trung vào version update và vulnerability trước; license review vẫn thường là bước thủ công hoặc chỉ được chạy khi phát hành sản phẩm.

**Assumption cần kiểm chứng:** với project nhỏ, giá trị lớn nhất không phải “legal advice”, mà là cảnh báo sớm khi dependency tree thay đổi theo cách khiến developer cần review lại license trước khi merge hoặc release.

### Ai gặp vấn đề này?

- Solo developer phát hành SaaS, desktop app hoặc CLI.
- Developer tạo package/library để phân phối công khai.
- Team nhỏ không có Open Source Program Office riêng.
- Consultant bàn giao source/binary cho khách hàng.

### Vấn đề xuất hiện khi nào?

- Sau `dotnet restore` khi version package thay đổi.
- Khi Dependabot/Renovate tạo PR update dependency.
- Khi thêm một package mới.
- Khi transitive dependency thay đổi dù direct dependency không đổi.
- Trước release hoặc bàn giao binary/source.

### Cách hiện tại thường xử lý

- Mở trang NuGet từng package để xem license.
- Export dependency list rồi kiểm tra bằng spreadsheet.
- Chỉ review direct dependency mà bỏ sót transitive dependency.
- Dùng scanner lớn phục vụ enterprise nhưng khó cấu hình cho project cá nhân.
- Không kiểm tra cho tới khi có yêu cầu compliance.

Điểm bất tiện là developer cần biết **license nào đã thay đổi so với trạng thái đã chấp nhận trước đây**, không chỉ cần một danh sách license hiện tại.

## 3. Người dùng mục tiêu

**Primary user:** solo .NET developer hoặc backend developer trong team nhỏ đang duy trì một sản phẩm có nhiều NuGet dependencies.

- **Context:** thường xuyên update package bằng CLI, Dependabot hoặc Renovate.
- **Pain point:** không biết một dependency update có làm thay đổi license/compliance hay không.
- **Current workaround:** review thủ công trang package hoặc bỏ qua license khi update.
- **Reason to try:** tool có thể trả lời nhanh “dependency tree hiện tại khác baseline đã approve ở đâu?”.

MVP chỉ tập trung vào project .NET/NuGet để giữ scope nhỏ và tận dụng ecosystem có metadata license tương đối rõ.

## 4. Giải pháp đề xuất

Người dùng trỏ LicenseDrift Watcher vào một `.sln`, `.csproj` hoặc repository.

Tool thực hiện workflow:

1. Chạy hoặc đọc kết quả dependency graph.
2. Xác định direct và transitive NuGet package/version.
3. Lấy package metadata và license expression/file.
4. Chuẩn hóa license expression theo SPDX.
5. So sánh với baseline snapshot đã được user approve.
6. Sinh report gồm:
   - package mới;
   - package bị xóa;
   - version thay đổi;
   - license thay đổi;
   - license metadata biến mất;
   - package cần manual review.
7. Trả exit code khác 0 nếu rule policy bị vi phạm.

### Input

- `.sln` hoặc `.csproj`.
- Optional `license-policy.yml`.
- Baseline JSON đã approve.

### Processing

- Resolve dependency graph.
- Parse NuGet package metadata.
- Normalize license expression.
- Apply deterministic policy rules.
- Compare current snapshot với baseline.

### Output

- Console report.
- JSON report cho CI.
- Markdown report cho PR artifact.
- Exit code cho pipeline.

### Những gì tự động hóa

- Dependency discovery.
- License metadata extraction.
- Diff giữa baseline và current state.
- Policy validation.

### Những gì user vẫn quyết định

- License nào được phép.
- License nào cần review.
- Có chấp nhận package custom-license hay không.
- Một license có phù hợp với mô hình phân phối thực tế hay không.

### Key differentiator

Không cố đóng vai luật sư hoặc “đánh giá license tự động 100%”. Tool tập trung vào **license drift detection**: chỉ đưa developer tới đúng dependency vừa thay đổi so với trạng thái đã được chấp nhận trước đó.

### Ví dụ end-to-end

Project đang có:

```text
PackageA 4.2.0 -> MIT
PackageB 2.1.0 -> Apache-2.0
```

Developer merge một PR update dependency. Snapshot mới cho thấy:

```text
PackageA 4.3.0 -> MIT
PackageB 3.0.0 -> custom license file
PackageC 1.0.0 -> GPL-3.0-only (transitive)
```

Report:

```text
PASS PackageA: version changed, license unchanged
REVIEW PackageB: license expression replaced by custom license file
BLOCK PackageC: new transitive dependency violates configured policy
```

Developer chỉ cần review hai thay đổi thực sự có ý nghĩa thay vì kiểm tra toàn bộ dependency tree mỗi lần.

## 7. Luồng hoạt động

### Baseline flow

User chạy scan
→ validate project path
→ resolve dependency graph
→ collect package metadata
→ normalize licenses
→ user review unknown/custom cases
→ save approved baseline.

### CI flow

PR thay đổi package
→ CI restore project
→ LicenseDrift scan
→ current snapshot được tạo trong memory
→ compare với baseline
→ apply policy
→ sinh report
→ exit `0` nếu pass hoặc configured review-only
→ exit khác `0` nếu policy violation.

### Alternative flows

**NuGet metadata không có SPDX expression:** lưu trạng thái `custom-license-file` hoặc `missing-license`, không tự suy diễn license.

**Package source offline:** dùng cache nếu có; nếu không, đánh dấu `metadata-unavailable` thay vì giả định an toàn.

**Package version giống baseline:** không cần fetch lại nếu cache key package/version còn hợp lệ.

**Transitive graph thay đổi:** report package mới/xóa ngay cả khi direct package không đổi.

**SPDX expression phức tạp:** parse AST thay vì so chuỗi raw.

## 10. Thiết kế dữ liệu ban đầu

### PackageSnapshot

**Purpose:** snapshot một dependency tại một thời điểm.

Fields:

- `PackageId`
- `Version`
- `IsDirect`
- `ParentPackages[]`
- `LicenseKind`
- `LicenseExpression`
- `LicenseFileHash`
- `Source`
- `CapturedAt`

Relationship: thuộc một `ProjectSnapshot`.

Retention: baseline giữ trong Git; current snapshot có thể ephemeral.

### ProjectSnapshot

**Purpose:** trạng thái dependency tree của project.

Fields:

- `SchemaVersion`
- `ProjectPath`
- `TargetFrameworks[]`
- `Packages[]`
- `CreatedAt`

Retention: chỉ cần baseline mới nhất cho MVP; history optional.

### LicensePolicy

**Purpose:** rule user-defined.

Fields:

- `AllowedExpressions[]`
- `ReviewExpressions[]`
- `DeniedExpressions[]`
- `AllowMissingMetadata`
- `PackageExceptions[]`

Retention: version-controlled trong repo.

### PackageException

**Purpose:** exception có chủ đích.

Fields:

- `PackageId`
- `VersionRange`
- `Reason`
- `ApprovedAt`
- `ExpiresAt?`

Retention: giữ trong policy để audit lý do.

### ScanFinding

**Purpose:** kết quả diff/policy evaluation.

Fields:

- `PackageId`
- `OldVersion`

- `OldLicense`
- `NewLicense`

## 11. API và tích hợp

### NuGet package metadata

**Purpose:** lấy package metadata/license cho version cụ thể.

**Authentication:** public NuGet không cần auth; private feed support có thể cần credential provider/token.

**Cost/rate-limit concern:** public feed có network latency và service limits; tool nên cache theo `{PackageId, Version, Source}`.

**Privacy:** package ID/version có thể tiết lộ stack nếu gửi tới external feeds; với private project nên chỉ query source đã cấu hình.

**Fallback:** đọc `.nupkg` từ local NuGet cache nếu package đã restore.

### Local NuGet global-packages folder

**Purpose:** ưu tiên metadata local, giảm network calls.

**Authentication:** không cần.

**Cost:** gần như bằng 0.

**Privacy:** dữ liệu ở máy local.

**Fallback:** package source metadata.

### SPDX License List

**Purpose:** validate identifiers/expression.

**Authentication:** không cần cho static data.

**Cost:** thấp; có thể bundle versioned license list hoặc dùng library parser.

**Privacy:** không có package data phải gửi đi.

**Fallback:** dùng embedded SPDX identifier set đi kèm release của tool.

### GitHub Actions

**Purpose:** chạy scan trong PR pipeline.

**Authentication:** core scan không cần GitHub token nếu chỉ chạy CLI; PR comment integration về sau mới cần permission.

**Cost/rate limit:** phụ thuộc Actions minutes và GitHub API nếu dùng comment integration.

**Privacy:** JSON report có thể chứa tên private package, nên không upload public artifact nếu repo/log public.

**Fallback:** chỉ fail/pass bằng exit code.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem cần deterministic behavior:

- dependency nào thay đổi;
- metadata license nào thay đổi;
- SPDX expression parse ra sao;
- policy rule có pass hay fail.

AI không nên quyết định một license có “an toàn pháp lý” hay không.

Nếu mở rộng về sau, AI chỉ nên là optional assistant để:

- tóm tắt report dài;
- giải thích sự khác nhau giữa hai license cho developer đọc nhanh;
- gợi ý câu hỏi cần hỏi legal/compliance.

Nhưng output AI phải được gắn nhãn informational, không phải legal advice, và không ảnh hưởng deterministic exit code.

## 14. Các bài toán kỹ thuật đáng học

### 1. Dependency graph resolution

Transitive dependencies khác nhau theo target framework và package graph. Bài toán này cải thiện hiểu biết về NuGet restore, assets file và graph traversal.

### 2. SPDX expression parsing

`MIT OR Apache-2.0`, `GPL-3.0-only WITH ...` không thể xử lý đúng bằng string contains. Đây là cơ hội học tokenizer, parser/AST và canonicalization.

### 3. Deterministic policy engine

Tool phải cho cùng input → cùng output. Kỹ năng học được: rule precedence, explicit exceptions, stable severity model và testability.

### 4. Cache và failure recovery

Feed có thể chậm/offline. Cần local cache, retry giới hạn và fallback. Kỹ năng học được: resilient external dependency design.

### 5. Baseline drift detection

Phân biệt “toàn bộ trạng thái hiện tại” với “điều gì thay đổi từ trạng thái đã approve”. Kỹ năng học được: immutable snapshot, diff algorithm và audit-friendly workflows.

## 15. Rủi ro và cách xử lý

### Legal interpretation risk

**Risk:** user hiểu output như legal advice.

**Mitigation:** tool chỉ báo metadata/rule match, không kết luận legal compatibility; documentation phải nêu rõ cần review chuyên môn khi cần.

### Missing/inaccurate package metadata

**Risk:** package khai báo license sai hoặc thiếu.

**Mitigation:** phân loại `unknown`/`manual-review`, không tự đoán từ repository README nếu MVP chưa hỗ trợ evidence chain.

### Custom license files

**Risk:** không thể map deterministic sang SPDX.

**Mitigation:** hash license file và phát hiện file thay đổi; bắt manual review thay vì auto-classify.

### Scope expansion

**Risk:** nhanh chóng biến thành full SCA/compliance platform.

**Mitigation:** MVP chỉ NuGet + license drift, không vulnerability scanner, không policy pháp lý phức tạp.

### Private feed credentials

**Risk:** secret exposure trong logs/config.

**Mitigation:** dùng existing NuGet credential mechanism; tool không tự lưu raw credential.

### Performance

**Risk:** repo lớn gây nhiều metadata lookup.

**Mitigation:** local package cache trước, parallel bounded concurrency và persistent metadata cache.

### False blocking CI

**Risk:** một package metadata unavailable làm toàn bộ pipeline fail.

**Mitigation:** configurable severity: `warn`, `review`, `block`; network failure khác policy violation.

## 16. Kiểm thử

### Strategy

- **Unit tests:** SPDX normalization, policy matching, snapshot diff.
- **Integration tests:** scan project fixture với restored NuGet packages.
- **End-to-end tests:** CLI baseline rồi đổi package version và chạy check.
- **Failure-path tests:** feed unavailable, missing metadata, corrupt package cache.
- **Security tests:** đảm bảo logs không in credentials/private feed tokens.
- **Data-quality tests:** fixture cho expression, custom file và missing license.

### 5 test scenario quan trọng nhất

1. Package version đổi nhưng license không đổi → `PASS/INFO`, không block.
2. Package version đổi từ một allowed SPDX expression sang denied expression → `BLOCK`.
3. Transitive dependency mới xuất hiện → report phải hiển thị parent chain.
4. Custom license file thay đổi hash giữa hai version → `REVIEW`.
5. NuGet feed unavailable nhưng metadata có trong local cache → scan vẫn hoàn thành deterministic.

## 17. Cách đo dự án có hữu ích hay không

### Product usage metric

- Số repository thực sự chạy `licensedrift check` trên PR hoặc trước release mỗi tuần.

### Time saved

- So sánh thời gian review dependency update thủ công với thời gian đọc drift report.

### Task completion rate

- % dependency update PR có license check hoàn tất trước merge.

### Error rate

- % finding bị user đánh dấu false positive.

### Repeated use

- Số tuần liên tiếp tool chạy trên cùng repository.

### Technical reliability

- % scan hoàn tất thành công khi dependency graph không đổi.
- Cache hit rate.
- Median scan duration.

### Success criteria MVP

Trong 30 ngày dùng cho 2–3 repo cá nhân:

- tool phát hiện được ít nhất một dependency/license state cần review;
- một scan cached hoàn thành trong thời gian đủ ngắn để chạy trên PR;
- false-positive rate cho deterministic rules dưới 5%;
- không cần manual reconfiguration cho mỗi lần package version update.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, tạo vertical slice đầu tiên:

**`.csproj` → lấy dependency list → đọc license metadata từ package local → in report console.**

Chưa cần policy, database hoặc web UI.

### Files/components cần tạo

```text
LicenseDrift.sln
src/
  LicenseDrift.Cli/
    Program.cs
    Models/PackageLicenseInfo.cs
    Services/DependencyReader.cs
    Services/NuGetLicenseReader.cs
tests/
  LicenseDrift.Tests/
    NuGetLicenseReaderTests.cs
fixtures/
  SampleApp/
    SampleApp.csproj
```

### Setup commands

```bash
dotnet new sln -n LicenseDrift
dotnet new console -n LicenseDrift.Cli -o src/LicenseDrift.Cli
dotnet new xunit -n LicenseDrift.Tests -o tests/LicenseDrift.Tests
dotnet new console -n SampleApp -o fixtures/SampleApp

dotnet sln add src/LicenseDrift.Cli
dotnet sln add tests/LicenseDrift.Tests
dotnet add tests/LicenseDrift.Tests reference src/LicenseDrift.Cli

dotnet add fixtures/SampleApp package Newtonsoft.Json
dotnet restore fixtures/SampleApp
```

### First vertical slice

Prototype có thể bắt đầu bằng:

```bash
dotnet list fixtures/SampleApp/SampleApp.csproj package --include-transitive
```

Sau đó code:

1. Nhận path `.csproj` từ CLI argument.
2. Đọc `obj/project.assets.json` sau restore.
3. Lấy package ID/version cho một target framework.
4. Tìm package trong NuGet global packages folder.
5. Mở `.nuspec` tương ứng.
6. Đọc `<license type="expression">` hoặc `<license type="file">`.
7. In table:

```text
PACKAGE              VERSION     TYPE        LICENSE
Newtonsoft.Json      x.y.z       Direct      MIT
Some.Dependency      a.b.c       Transitive  Apache-2.0
```

Nếu không có metadata:

```text
Unknown.Package      a.b.c       Transitive  REVIEW: missing-license
```

### Expected result

Một command:

```bash
dotnet run --project src/LicenseDrift.Cli -- fixtures/SampleApp/SampleApp.csproj
```

trả về dependency list kèm license metadata thực tế từ package đã restore.

### Verification checklist

- [ ] Đọc được ít nhất một direct dependency.
- [ ] Đọc được ít nhất một transitive dependency nếu fixture có.
- [ ] Không hard-code license.
- [ ] License được lấy từ package metadata thực tế.
- [ ] Package thiếu license không làm process crash.
- [ ] Có ít nhất một test fixture cho SPDX expression.
- [ ] Output ổn định giữa hai lần chạy với cùng dependency state.

### Stop condition

Dừng session ngay khi tool có thể quét một sample `.csproj` đã restore và in chính xác package ID, version, direct/transitive status và license metadata cho từng dependency. Không xây policy engine, GitHub integration, UI hoặc AI trong session đầu tiên.
