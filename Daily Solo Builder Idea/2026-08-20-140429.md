# Ý tưởng hôm nay: TraceBudget Lab — OpenTelemetry Sampling Policy Simulator

## 1. Tóm tắt ý tưởng

TraceBudget Lab là một developer tool self-hosted giúp developer **mô phỏng chính sách sampling cho distributed traces trước khi áp dụng lên OpenTelemetry Collector thật**. Tool nhận một tập trace mẫu, chạy nhiều chiến lược như probabilistic sampling, error/latency-based tail sampling hoặc policy kết hợp, rồi cho biết trace nào sẽ được giữ, trace nào bị bỏ, tỷ lệ dữ liệu còn lại và liệu các trace quan trọng có bị mất hay không.

- Người dùng chính: backend developer hoặc team nhỏ đang dùng OpenTelemetry cho .NET services.
- Bài toán chính: sampling giúp giảm telemetry volume nhưng cấu hình sai có thể vừa tốn chi phí vừa làm mất trace cần thiết để điều tra incident.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Distributed tracing tạo ra rất nhiều span. Với ứng dụng có nhiều HTTP request, database call, queue message và external API call, số trace có thể tăng nhanh hơn mức developer thực sự cần lưu lâu dài.

Developer thường giải quyết bằng sampling, nhưng đây không phải lựa chọn đơn giản kiểu “giữ 10% là xong”. Nếu dùng probabilistic sampling, lỗi hiếm có thể bị bỏ. Nếu dùng tail sampling để ưu tiên error hoặc latency cao, Collector phải giữ state đủ lâu để quan sát trace trước khi ra quyết định.

**Confirmed facts:**

- .NET có built-in distributed tracing dựa trên `Activity`, và Microsoft khuyến nghị OpenTelemetry như một lựa chọn vendor-neutral để thu thập trace. Nguồn: Microsoft Learn — Distributed tracing: https://learn.microsoft.com/en-us/dotnet/core/diagnostics/distributed-tracing
- OpenTelemetry Collector `tail_sampling` processor đưa ra quyết định sau khi nhóm span theo `trace_id`. Tài liệu chính thức nêu rõ tất cả span của cùng một trace phải tới cùng Collector instance để quyết định sampling chính xác. Nguồn: OpenTelemetry Collector Contrib: https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/tailsamplingprocessor
- Tài liệu của processor cũng lưu ý probabilistic sampling thường hiệu quả hơn tail sampling nếu không cần các quyết định dựa trên toàn bộ trace. Nguồn: OpenTelemetry Collector Contrib — tail sampling processor.
- Tail sampling processor hiện có telemetry riêng để theo dõi sampling-policy execution, late spans và trace bị drop do quá lớn; tail-storage support vẫn nằm sau feature gate và đang tiếp tục phát triển. Nguồn: https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/tailsamplingprocessor/documentation.md

**Observation:** công cụ chính thức tập trung vào việc thực thi pipeline thực tế, nhưng việc trả lời trước câu hỏi “policy này sẽ giữ lại đúng loại trace mình quan tâm hay không?” vẫn thường đòi hỏi developer dựng Collector, feed traffic rồi phân tích kết quả thủ công.

**Assumption cần validation:** developer/team nhỏ sẽ thấy hữu ích nếu có một sandbox nhỏ để chạy policy trên trace mẫu và so sánh kết quả trước khi sửa Collector production config.

Workaround phổ biến hiện nay:

- chỉnh YAML Collector rồi deploy staging;
- tăng sampling rate rồi xem telemetry dashboard;
- viết script ad-hoc để thống kê trace;
- dựa vào cảm giác để chọn tỷ lệ như 1%, 5%, 10%;
- chỉ giữ error trace nhưng không kiểm tra xem slow trace hoặc rare endpoint có bị mất.

Những cách này không sai, nhưng vòng feedback chậm và khó so sánh nhiều policy trên cùng một dataset.

## 3. Người dùng mục tiêu

**Primary user:** backend developer đang vận hành 1–20 service có OpenTelemetry tracing, đặc biệt là .NET/ASP.NET Core application.

- **Context:** chuẩn bị bật tracing rộng hơn, muốn giảm telemetry volume hoặc đang điều chỉnh Collector sampling policy.
- **Main pain point:** không biết policy mới sẽ ảnh hưởng thế nào tới error trace, slow trace, endpoint ít traffic và tổng volume.
- **Current workaround:** chỉnh Collector config rồi test trên staging hoặc production canary.
- **Reason to try:** có thể kiểm tra policy offline với cùng một tập trace trước khi rollout.

MVP không cố thay thế Jaeger, Grafana Tempo, Application Insights hay OpenTelemetry Collector. Nó chỉ là **policy simulator + regression checker**.

## 4. Giải pháp đề xuất

TraceBudget Lab có workflow đơn giản:

1. Import trace sample dưới dạng OTLP JSON hoặc JSON normalized format.
2. Tool chuẩn hóa dữ liệu thành `Trace → Spans → Attributes`.
3. User định nghĩa policy bằng UI đơn giản hoặc YAML subset.
4. Simulator chạy policy deterministic trên toàn bộ dataset.
5. Dashboard trả về:
   - số trace trước/sau sampling;
   - estimated data reduction;
   - error-trace retention;
   - slow-trace retention;
   - rare-endpoint retention;
   - trace bị drop theo từng policy rule;
   - danh sách trace quan trọng bị mất.
6. User so sánh Policy A với Policy B rồi export một Collector configuration draft.

### Ví dụ end-to-end

Một service có 50.000 trace mẫu trong 24 giờ. Developer đang cân nhắc:

```text
Policy A:
- keep all traces with ERROR
- keep traces >= 2s
- sample 5% remaining traces
```

TraceBudget Lab chạy policy và báo:

```text
Input traces:                50,000
Retained traces:              4,620
Estimated reduction:          90.8%
Error traces retained:       100.0%
Slow traces retained:        100.0%
Rare endpoint retention:      36.0%
```

Sau đó developer thử Policy B với 10% fallback sampling và thấy rare-endpoint retention tăng đáng kể nhưng telemetry volume cũng tăng. Người dùng tự quyết định trade-off.

### Input

- OTLP JSON export;
- normalized trace JSON;
- sau MVP: OTLP HTTP receiver local.

### Processing

- group span by `trace_id`;
- derive trace-level metrics như duration, status, span count, service count;
- evaluate policy;
- calculate retention metrics.

### Output

- comparison report;
- dropped-trace examples;
- policy regression status;
- Collector YAML draft.

### Automated

- grouping;
- policy execution;
- metrics calculation;
- regression checks.

### User-controlled

- dataset;
- budget target;
- important trace criteria;
- final production config.

### Key differentiator

Không phải telemetry backend. Điểm khác biệt là **sampling policy testing giống unit/integration testing cho observability configuration**.

## 7. Luồng hoạt động

### Normal flow

User upload trace dataset
→ validate schema
→ normalize spans
→ group by trace ID
→ calculate derived trace metadata
→ load sampling policy
→ evaluate each trace
→ store simulation result
→ calculate retention metrics
→ render comparison dashboard/report.

### Regression flow

User chọn baseline policy
→ chạy candidate policy
→ evaluate assertions
→ kết quả PASS/FAIL.

Ví dụ assertion:

```text
error_retention >= 100%
slow_trace_retention >= 95%
overall_retention <= 10%
```

### Failure cases

- File invalid JSON → reject với line/error detail.
- Missing `trace_id` → mark invalid span, không silently merge.
- Duplicate spans → deduplicate theo span ID nếu có.
- Dataset quá lớn → streaming parse hoặc hard limit trong MVP.
- Policy invalid → validation error trước simulation.
- Attribute không tồn tại → rule trả false, không crash.
- Probability rule cần reproducible result → hash `trace_id`, không dùng random mới mỗi lần chạy.

Không cần.

Không cần ở MVP.

## 9. Công nghệ đề xuất

### .NET 10 + ASP.NET Core

**Why:** phù hợp với domain observability/.NET, performance tốt và có sẵn `Activity`/OpenTelemetry ecosystem.

**Simpler alternative:** console app trước khi có web UI.

**Outgrow point:** chỉ cần worker riêng khi simulation trở thành CPU-heavy multi-user workload.

### EF Core + PostgreSQL

**Why:** đủ cho policy, dataset metadata và result summary.

**Simpler alternative:** SQLite cho local-only version.

**Outgrow point:** raw trace analytics lớn không nên ép vào relational DB; khi đó dùng columnar/telemetry backend thay vì scale PostgreSQL vô hạn.

### Vue 3 + Vite

**Why:** nhẹ, phù hợp dashboard và policy comparison.

**Simpler alternative:** Razor Pages.

### System.Text.Json streaming APIs

**Why:** tránh load toàn bộ dataset lớn vào memory.

**Simpler alternative:** deserialize whole file trong Phase 1.

### Docker

**Why:** reproducible self-hosted deployment.

### Playwright

**Why:** E2E cho import → simulate → compare.

### GitHub Actions

**Why:** build/test/package image.

## 10. Thiết kế dữ liệu ban đầu

### Dataset

**Purpose:** đại diện cho một trace sample.

Fields:

- `Id`
- `Name`
- `FilePath`
- `ImportedAt`
- `TraceCount`
- `SpanCount`
- `FileSizeBytes`
- `SchemaVersion`
- `Status`

Relationship: Dataset có nhiều Simulation.

Retention: user-configurable; mặc định 30 ngày cho raw dataset.

### SamplingPolicy

**Purpose:** policy có thể chạy lại nhiều lần.

Fields:

- `Id`
- `Name`
- `DefinitionJson`
- `CreatedAt`
- `UpdatedAt`

Relationship: một policy dùng trong nhiều Simulation.

Retention: giữ lâu dài vì nhỏ.

### Simulation

**Purpose:** một execution của policy trên dataset.

Fields:

- `Id`
- `DatasetId`
- `PolicyId`
- `StartedAt`
- `CompletedAt`
- `Status`
- `InputTraceCount`
- `RetainedTraceCount`
- `InputSpanCount`
- `RetainedSpanCount`
- `ErrorRetentionRate`
- `SlowTraceRetentionRate`
- `ExecutionMs`

### TraceDecision

**Purpose:** giải thích vì sao trace được keep/drop.

Fields:

- `SimulationId`
- `TraceIdHash`
- `Decision`
- `MatchedRule`
- `DurationMs`
- `HasError`
- `SpanCount`

Không nhất thiết lưu decision cho mọi trace trong dataset rất lớn; MVP có thể lưu toàn bộ dưới giới hạn và sau đó chỉ lưu sample/aggregate.

## 11. API và tích hợp

### OpenTelemetry data model / OTLP

**Purpose:** source format tiêu chuẩn cho trace.

**Authentication:** không cần khi import file local.

**Cost/rate-limit:** không có external rate limit.

**Privacy:** trace attributes có thể chứa URL, user identifier, SQL metadata hoặc business data. Tool phải coi dataset là sensitive.

**Fallback:** normalized JSON format riêng, documented rõ.

Nguồn: https://opentelemetry.io/docs/specs/otlp/

### OpenTelemetry Collector configuration

**Purpose:** export draft config sau simulation.

**Authentication:** không cần.

**Concern:** Collector processor configuration có thể thay đổi theo release và một số feature ở trạng thái beta/alpha.

**Fallback:** chỉ export generic policy report thay vì hứa config chạy được trên mọi version.

Nguồn: https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/tailsamplingprocessor

### Optional future: Jaeger/Tempo

Không đưa vào MVP. Import trực tiếp từ backend sẽ tạo thêm authentication, pagination và version compatibility không cần thiết để chứng minh core value.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Sampling simulation cần reproducible và explainable. Deterministic policy engine phù hợp hơn AI.

Các bài toán chính đều giải quyết tốt bằng code thường:

- group trace;
- check error status;
- duration threshold;
- attribute rules;
- deterministic probability;
- metrics calculation.

AI có thể được thêm sau để giải thích report bằng natural language, nhưng không nên quyết định trace nào được giữ.

Việc không dùng AI giúp:

- kết quả repeatable;
- không có hallucination;
- không phát sinh token cost;
- không gửi telemetry nhạy cảm ra bên ngoài;
- dễ chạy offline/self-hosted.

## 14. Các bài toán kỹ thuật đáng học

### 1. Deterministic probabilistic sampling

Thay vì `Random.NextDouble()`, dùng hash của `trace_id` để cùng một trace luôn có cùng quyết định ở cùng sampling rate.

**Skill cải thiện:** hashing, deterministic distributed decisions, reproducible testing.

### 2. Trace aggregation

Span có thể tới không theo thứ tự. Simulator phải group và derive trace-level metadata đúng.

**Skill cải thiện:** correlation, aggregation, distributed telemetry semantics.

### 3. Large dataset processing

Dataset hàng trăm MB không nên deserialize toàn bộ vào memory.

**Skill cải thiện:** streaming JSON, bounded memory, profiling và backpressure.

### 4. Policy engine design

Rule phải composable nhưng không biến thành một DSL quá phức tạp.

**Skill cải thiện:** interpreter/policy pattern, validation, explainability.

### 5. Regression metrics

Không chỉ đo overall retention mà phải bảo vệ important cohorts như error/slow/rare endpoints.

**Skill cải thiện:** observability engineering và quality gates.

## 15. Rủi ro và cách xử lý

### Simulator khác behavior của Collector

**Risk:** user tin kết quả nhưng production Collector xử lý khác.

**Mitigation:** MVP chỉ hỗ trợ một subset policy đã document; test bằng golden datasets; tránh tuyên bố 100% compatibility.

### Scope expansion thành telemetry backend

**Risk:** bắt đầu thêm search, dashboards, alerts, retention storage.

**Mitigation:** product boundary rõ: simulator không phải APM.

### Data privacy

**Risk:** trace chứa dữ liệu nhạy cảm.

**Mitigation:** self-hosted default; không upload external; redact known sensitive attributes trong UI/log; retention configurable.

### Dataset không đại diện production

**Risk:** policy tối ưu trên sample nhưng fail khi traffic pattern đổi.

**Mitigation:** report dataset composition; khuyến nghị nhiều time windows; không gọi kết quả là production guarantee.

### Performance

**Risk:** hàng triệu spans gây memory pressure.

**Mitigation:** hard limit MVP, streaming parser, cancellation, benchmark trước khi support dataset lớn.

### Maintenance burden

**Risk:** OpenTelemetry Collector policy options thay đổi.

**Mitigation:** versioned compatibility matrix và support subset ổn định thay vì clone toàn bộ config schema.

## 16. Kiểm thử

### Strategy

- **Unit tests:** policy rules, duration/error derivation, deterministic sampling.
- **Integration tests:** import file → simulation → persisted summary.
- **E2E tests:** browser import → create policy → compare result.
- **Failure-path tests:** malformed JSON, missing IDs, huge file, cancellation.
- **Security tests:** path traversal, unsafe upload filename, stored attribute rendering/XSS.
- **Data-quality tests:** duplicate spans, incomplete trace, late/missing spans.

### 5 test scenario quan trọng nhất

1. Policy `keep errors` giữ 100% trace có error status trong golden dataset.
2. Cùng `trace_id` và 5% probability cho cùng decision qua 1.000 lần chạy.
3. Candidate policy vượt budget nhưng vẫn giữ error → report đúng cả PASS/FAIL từng assertion.
4. Dataset có duplicate/missing span không làm crash và warning được ghi rõ.
5. Dataset lớn hơn configured limit bị reject hoặc streaming xử lý mà memory không tăng mất kiểm soát.

## 17. Cách đo dự án có hữu ích hay không

### Product usage metric

- số policy comparison thực sự chạy mỗi tháng;
- số lần simulation được dùng trước config change.

### Time saved

Đo thời gian từ “có policy candidate” đến “biết ảnh hưởng lên dataset”. So sánh với deploy staging + quan sát thủ công.

### Task completion rate

Tỷ lệ simulation hoàn thành thành công trên dataset hợp lệ.

Mục tiêu MVP: > 98% với dataset trong supported limits.

### Error rate

- parser failures;
- simulation failures;
- non-deterministic output phải bằng 0.

### Repeated use

Developer quay lại dùng tool cho ít nhất 3 lần thay sampling policy trong 60–90 ngày.

### Technical reliability

Cùng dataset + policy version phải tạo cùng result hash.

### Quality metric

Quan trọng nhất không phải số trace drop được, mà là:

```text
Important Trace Retention
```

Ví dụ:

- Error retention = 100%.
- Slow trace retention >= 95%.
- Overall retention <= budget target.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, hoàn thành vertical slice đầu tiên:

```text
trace JSON → policy engine → console report
```

Chưa làm database, frontend hoặc Docker.

### Files/components cần tạo

```text
TraceBudgetLab.sln
src/
  TraceBudgetLab.Cli/
    Program.cs
    Models/SpanRecord.cs
    Models/TraceRecord.cs
    Policies/ISamplingPolicy.cs
    Policies/ErrorPolicy.cs
    Policies/DurationPolicy.cs
    Policies/ProbabilisticPolicy.cs
    Simulation/SimulationEngine.cs
tests/
  TraceBudgetLab.Tests/
    SimulationEngineTests.cs
samples/
  traces.json
```

### Setup commands

```bash
dotnet new sln -n TraceBudgetLab
dotnet new console -n TraceBudgetLab.Cli -o src/TraceBudgetLab.Cli
dotnet new xunit -n TraceBudgetLab.Tests -o tests/TraceBudgetLab.Tests
dotnet sln add src/TraceBudgetLab.Cli
dotnet sln add tests/TraceBudgetLab.Tests
dotnet add tests/TraceBudgetLab.Tests reference src/TraceBudgetLab.Cli
```

### Sample schema

Tạo `samples/traces.json` với khoảng 20 trace synthetic, mỗi trace có:

```json
{
  "traceId": "trace-001",
  "durationMs": 2450,
  "hasError": true,
  "endpoint": "/api/orders",
  "spanCount": 8
}
```

Không cần OTLP schema trong session đầu.

### First vertical slice

Implement policy:

```text
KEEP if hasError == true
KEEP if durationMs >= 2000
ELSE keep 10% by deterministic traceId hash
```

CLI:

```bash
dotnet run --project src/TraceBudgetLab.Cli -- samples/traces.json
```

Expected output:

```text
Input traces:            20
Retained traces:          7
Retention rate:       35.0%
Error retention:     100.0%
Slow retention:      100.0%
Dropped traces:          13
```

### Verification checklist

- [ ] JSON sample load thành công.
- [ ] Error trace luôn được giữ.
- [ ] Trace >= 2 giây luôn được giữ.
- [ ] Probabilistic rule dựa trên hash, không dùng random runtime.
- [ ] Chạy lặp lại 10 lần cho cùng kết quả.
- [ ] Có ít nhất 3 unit test pass.
- [ ] Console hiển thị retained ratio và error retention.

### Stop condition

Dừng session khi command line có thể đọc sample dataset, chạy policy và in một report deterministic. Không làm UI, PostgreSQL, OTLP importer hay Collector YAML generator trong buổi đầu.
