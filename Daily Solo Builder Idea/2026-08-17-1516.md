# Ý tưởng hôm nay: A11yRoute — Accessibility Regression Guard cho web app

## 1. Tóm tắt ý tưởng

**A11yRoute** là một công cụ QA/developer tự động duyệt các route quan trọng của web app, chạy accessibility scan bằng Playwright + axe-core, lưu baseline theo route và báo chính xác violation nào là **mới xuất hiện sau một thay đổi code**. Thay vì chỉ tạo một báo cáo accessibility tĩnh, công cụ tập trung vào regression: “PR này vừa làm accessibility tệ đi ở đâu?”.

- **Project size:** Medium
- **Estimated MVP time:** 2–3 tuần làm ngoài giờ
- **Người hưởng lợi chính:** developer/QA của web app nhỏ và vừa
- **Bài toán chính:** accessibility issue thường chỉ được phát hiện muộn, khó biết issue nào đã tồn tại từ trước và issue nào vừa bị introduce

## 2. Bài toán thực tế

### Confirmed facts

Playwright có tài liệu chính thức hướng dẫn tích hợp `@axe-core/playwright` để tìm các accessibility issue tự động phát hiện được như contrast kém, form control thiếu label hoặc duplicate ID. Chính Playwright cũng nhấn mạnh rằng automated accessibility testing **không phát hiện được mọi vấn đề**, vì vậy vẫn cần manual assessment và inclusive user testing. Nguồn: [Playwright — Accessibility testing](https://playwright.dev/docs/accessibility-testing).

WCAG 2.2 là W3C Recommendation và định nghĩa các success criteria có thể kiểm thử cho khả năng tiếp cận web. W3C khuyến nghị dùng phiên bản WCAG hiện hành khi phát triển hoặc cập nhật accessibility policy. Nguồn: [W3C — WCAG 2.2](https://www.w3.org/TR/WCAG22/), [WAI — What’s New in WCAG 2.2](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/).

### Observation

Tooling đã có khả năng scan một page khá tốt, nhưng workflow phổ biến vẫn thường là:

1. Developer chạy audit thủ công trên vài màn hình.
2. QA tạo ticket cho từng issue.
3. CI có thể fail ngay khi bất kỳ violation nào tồn tại.
4. Với hệ thống cũ đã có nhiều violation, team dễ bỏ luôn accessibility gate vì số lượng lỗi ban đầu quá lớn.

Điểm khó không chỉ là “scan được hay không”, mà là **quản lý technical debt accessibility theo thời gian mà không chặn toàn bộ development**.

### Assumption cần validate

Một team có legacy accessibility debt sẽ sẵn sàng dùng tool nếu nó cho phép:

- baseline lỗi cũ,
- chỉ fail CI khi có regression mới,
- hiển thị route + selector + rule + evidence,
- cho phép ignore có lý do và thời hạn.

### Vì sao cách hiện tại bất tiện

Nếu chỉ dùng một assertion kiểu `expect(violations).toEqual([])`, project legacy có thể fail hàng loạt ngay ngày đầu. Ngược lại, nếu bỏ gate hoàn toàn thì regression mới không bị chặn. Một lớp quản lý baseline và diff nằm giữa hai cực này là khoảng trống thực dụng mà một solo developer có thể xây được.

## 3. Người dùng mục tiêu

### Primary user

Developer hoặc QA Automation Engineer đang duy trì web application có khoảng 10–100 route quan trọng.

### Context of use

- SPA hoặc server-rendered web app.
- Có CI/CD.
- Có Playwright hoặc sẵn sàng thêm Playwright.
- Chưa có accessibility process chặt chẽ.
- Có thể đã tồn tại accessibility debt từ trước.

### Main pain point

Họ muốn chặn accessibility regression mà không phải sửa toàn bộ lỗi cũ trước khi bật CI gate.

### Current workaround

- Lighthouse chạy thủ công.
- axe DevTools chạy từng page.
- Script Playwright tự viết.
- Spreadsheet/ticket để track lỗi.
- Hoặc bỏ hẳn accessibility khỏi CI vì quá noisy.

### Reason họ sẽ thử A11yRoute

Họ chỉ cần khai báo route + login setup, chạy một command, rồi nhận report dạng:

> `/checkout`: 2 violations mới, 0 resolved, 5 baseline.

Đây là feedback có tính hành động hơn một audit report tổng hợp.

## 4. Giải pháp đề xuất

### Main workflow

User tạo file cấu hình:

```yaml
baseUrl: https://staging.example.com
routes:
  - path: /login
    name: Login
  - path: /products
    name: Product List
  - path: /checkout
    name: Checkout
```

Sau đó chạy:

```bash
a11yroute scan
```

A11yRoute sẽ:

1. Mở browser bằng Playwright.
2. Login nếu có setup script.
3. Đi từng route.
4. Chờ page ổn định.
5. Chạy `axe-core`.
6. Chuẩn hóa violation thành fingerprint ổn định.
7. So sánh với baseline trước đó.
8. Phân loại `new`, `existing`, `resolved`, `ignored`.
9. Xuất Markdown/HTML/JSON report.
10. Trả exit code khác 0 nếu có regression vượt policy.

### Input

- Base URL.
- Route list.
- Optional Playwright auth state.
- Include/exclude selectors.
- Rule policy.
- Baseline JSON.

### Processing

Core engine normalize mỗi violation theo:

- axe rule id,
- route,
- selector/node target,
- impact,
- một phần failure summary.

Sau đó tạo fingerprint để so sánh giữa các lần scan.

### Output

- Console summary.
- `a11y-report.json` cho machine processing.
- `a11y-report.md` cho PR comment/artifact.
- Optional screenshot cho violation mới.

### What is automated

- Route scanning.
- axe execution.
- Diff với baseline.
- Severity filtering.
- CI exit code.
- Evidence collection.

### What remains under user control

- Route nào quan trọng.
- Khi nào chấp nhận baseline.
- Violation nào được ignore.
- Ignore đến khi nào.
- Manual accessibility testing.

### Key differentiator

**A11yRoute không cố chứng minh một website “đạt WCAG hoàn toàn”. Nó chỉ bảo đảm accessibility không âm thầm tệ đi qua từng thay đổi code.**

### Ví dụ end-to-end

PR đổi component `Button.vue` làm icon-only button mất `aria-label`.

CI chạy A11yRoute:

- `/dashboard`: 1 violation mới `button-name`.
- `/settings`: 2 violation mới cùng rule.
- `/login`: không đổi.

Report gom cả ba occurrence về cùng component pattern, hiển thị selector và screenshot. PR fail vì policy đặt `new serious/critical violations = 0`.

Developer sửa component một lần, chạy lại, tất cả regression biến mất.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Tool giải quyết một workflow rất cụ thể: đưa accessibility vào CI ngay cả khi project chưa sạch accessibility debt.

### Technical learning value

Project giúp học sâu về:

- browser automation,
- DOM stability,
- CI tooling,
- fingerprint/diff algorithm,
- structured reporting,
- accessibility fundamentals,
- flaky test mitigation.

### Vì sao phù hợp solo developer

Core MVP chỉ cần CLI + Playwright + axe + JSON baseline. Không cần multi-tenant SaaS, queue, payment hay distributed architecture.

### Vẫn hữu ích với rất ít user

Ngay cả chỉ dùng cho project cá nhân, A11yRoute có thể trở thành reusable CI tool cho mọi web app sau này.

### Điều gì khiến idea thất bại

- Fingerprint quá không ổn định khiến cùng một lỗi bị nhận diện thành lỗi mới liên tục.
- Scan flaky vì page chưa load xong.
- Report quá noisy.
- Tool bị hiểu nhầm là thay thế manual accessibility testing.

### Lý do mạnh nhất để không build

Nếu mục tiêu chỉ là scan vài page greenfield và team đã enforce `axe` trực tiếp trong Playwright tests rất tốt, một wrapper riêng có thể không mang thêm đủ giá trị.

## 7. Luồng hoạt động

### Happy path

User chạy command
→ load config
→ validate URL/routes
→ start Playwright browser
→ restore auth state
→ navigate route
→ wait strategy
→ run axe
→ normalize results
→ compare baseline
→ persist report
→ evaluate policy
→ exit `0` hoặc `1`.

### Alternative flow — chưa có baseline

Scan lần đầu
→ toàn bộ violations được đánh dấu `unbaselined`
→ user review
→ chạy `a11yroute baseline accept`
→ snapshot được lưu vào repo.

Không nên tự động chấp nhận baseline ngay trong scan vì có thể vô tình hợp thức hóa regression.

### Failure — route 500

Navigation thất bại
→ mark route `scan_failed`
→ report HTTP/status error
→ policy mặc định fail scan để tránh false green.

### Failure — selector thay đổi

Fingerprint dựa hoàn toàn vào selector có thể false-positive.

Mitigation MVP:

- normalize dynamic IDs,
- combine rule + normalized target,
- báo `possibly_changed` khi confidence thấp.

### Failure — login expired

Nếu storage state không còn hợp lệ:

- detect redirect về login,
- fail với message rõ ràng,
- không coi page login là target page.

## 9. Công nghệ đề xuất

### .NET 10

**Why it fits:** current LTS line, phù hợp để viết CLI, file processing, policy engine và packaging.

**Simpler alternative:** Node.js/TypeScript vì Playwright + axe ecosystem native JS thuận tiện hơn.

**Khi outgrow:** không phải bottleneck; lựa chọn chủ yếu là developer ergonomics.

### Playwright for .NET

Dùng cho navigation, authentication, screenshot, browser lifecycle.

**Simpler alternative:** Playwright Test + TypeScript toàn bộ project. Đây thực tế có thể là lựa chọn đơn giản nhất nếu mục tiêu chỉ là tool accessibility.

### axe-core

Playwright docs chính thức dùng `@axe-core/playwright`; với implementation .NET có hai hướng:

1. chạy axe script trong page context,
2. tạo một Node sidecar package nhỏ chỉ cho scan engine.

**Recommendation:** nếu integration .NET trực tiếp trở nên rườm rà, dùng **TypeScript cho scan engine** và .NET chỉ khi thực sự cần. Không nên ép .NET vào nơi ecosystem JS rõ ràng thuận lợi hơn.

### Spectre.Console

Dùng cho CLI table/progress/report summary.

**Simpler alternative:** `System.CommandLine` + Console.WriteLine.

### System.Text.Json

Baseline/report serialization, đủ cho MVP.

### Docker

Optional để chạy CI reproducibly.

### GitHub Actions

Cung cấp sample action chạy tool trên PR.

### Playwright E2E cho chính A11yRoute

Dogfood: test tool bằng những fixture pages cố tình chứa accessibility violations.

Fields:

## 11. API và tích hợp

### Playwright

**Purpose:** browser automation.

**Authentication:** không cần external auth; website target có thể cần session.

**Cost/rate limit:** không có API cost, nhưng scan làm tăng traffic vào target environment.

**Privacy:** screenshot có thể chứa user/test data.

**Fallback:** allow disable screenshot và chỉ scan staging/local.

Source: [Playwright Accessibility Testing](https://playwright.dev/docs/accessibility-testing).

### axe-core / @axe-core/playwright

**Purpose:** automated accessibility rules.

**Authentication:** không.

**Cost:** open-source package; cần kiểm tra license version cụ thể trước khi redistribute binary/package.

**Privacy:** chạy trong browser context; không cần gửi DOM lên cloud nếu implementation local.

**Fallback:** scan disabled rule-by-rule; manual checklist vẫn cần.

### WCAG 2.2

Không phải API mà là tiêu chuẩn tham chiếu để giải thích mục tiêu accessibility.

Nguồn chính thức: [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/).

### GitHub Actions

**Purpose:** chạy scan trên PR.

**Authentication:** `GITHUB_TOKEN` chỉ cần nếu Later muốn comment vào PR; core scan không cần.

**Cost:** phụ thuộc Actions minutes của repo/account; tool không nên giả định quota miễn phí cụ thể.

**Fallback:** Jenkins/Azure DevOps/local command.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem là deterministic:

- run browser,
- collect violations,
- normalize,
- compare baseline,
- apply policy.

LLM có thể Later dùng để gợi ý cách sửa dựa trên violation + HTML snippet, nhưng không nên tham gia quyết định CI pass/fail.

Nếu thêm AI sau này:

- **Task:** giải thích violation bằng ngôn ngữ dễ hiểu và đề xuất fix mẫu.
- **Context:** axe rule metadata + sanitized HTML snippet.
- **Structured output:** `{summary, whyItMatters, suggestedFix, confidence}`.
- **Validation:** rule id/help URL vẫn là source of truth.
- **Fallback:** hiển thị axe help text/documentation.
- **Risks:** hallucination, gửi source code ra ngoài, latency và cost.

Không phải violation nào cũng cần fail build.

Skill:

- severity gates,
- error budgets,

- developer experience.

### 5. Accessibility engineering

Tool buộc developer hiểu limitation của automated tests và cách mapping technical rule sang user impact.

## 15. Rủi ro và cách xử lý

### Technical complexity — unstable fingerprints

**Mitigation:** bắt đầu exact match rule+normalized selector; không thêm fuzzy algorithm cho đến khi có fixture chứng minh cần thiết.

### Scope expansion

Rất dễ trượt thành full accessibility platform.

**Mitigation:** MVP chỉ giải quyết regression scan; không dashboard, không crawler, không AI, không compliance certification.

### Data privacy

Screenshot/HTML có thể chứa thông tin nhạy cảm.

**Mitigation:** default không lưu full DOM; screenshot optional; recommend staging/test users; redact known selectors.

### Security

CLI chạy browser và potentially login credentials.

**Mitigation:** đọc secrets từ environment; không persist password; support pre-generated storage state; mask logs.

### API/tool dependency

Playwright/axe thay đổi version có thể làm result đổi.

**Mitigation:** lưu `axeVersion` + `toolVersion` trong report/baseline; version lock package.

### Unreliable external data

Không phụ thuộc external dataset.

### Cost

Browser CI có compute cost.

**Mitigation:** chỉ scan critical routes trên PR; full route scan nightly.

### Legal/platform restrictions

Không tuyên bố tool chứng nhận WCAG compliance. Automated scan chỉ là một phần của accessibility testing, phù hợp với chính cảnh báo của Playwright docs.

### User adoption

Nếu setup route/auth quá khó, team sẽ bỏ.

**Mitigation:** sample configs, init wizard, Playwright storage-state integration.

### Maintenance burden

Browser tooling update liên tục.

**Mitigation:** giữ adapter layer nhỏ quanh Playwright/axe và có compatibility matrix.

### Unit tests

- config validation.

### Integration tests

Fixture HTML pages chứa known axe violations.

### End-to-end tests

CLI chạy vào demo ASP.NET/Vue hoặc static fixture server, tạo report và exit code.

### Failure-path tests

- route timeout,
- 500 response,
- unauthenticated redirect,
- browser crash,
- malformed baseline.

### Security tests

Bảo đảm secret từ config/env không xuất hiện trong logs/report.

### Data-quality tests

Snapshot expected violations cho fixture pages; khi axe version đổi, review deliberate diff.

### Năm test scenario quan trọng nhất

1. **No regression:** baseline có 3 lỗi, scan mới vẫn đúng 3 lỗi → exit 0.
2. **New serious violation:** thêm button không accessible name → `new=1`, exit 1.
3. **Resolved violation:** sửa label → report `resolved=1`, exit 0.
4. **Expired ignore:** lỗi từng được ignore nhưng `expiresAt` đã qua → trở thành actionable.
5. **Navigation failure:** `/checkout` trả 500 → scan không được green giả; route state = failed và CI fail.

## 17. Cách đo dự án có hữu ích hay không

### Product usage metric

- Số repo thực sự chạy tool trong CI ít nhất 4 tuần.

### Time saved

- Median time từ regression introduction đến detection.
- Target cá nhân: phát hiện ngay PR thay vì chờ manual QA.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong 60–120 phút, tạo được vertical slice chứng minh concept:

> scan một page cố tình có accessibility violation, ghi baseline, sửa page, rồi thấy diff `resolved`.

### Files/components cần tạo

```text
A11yRoute/
  package.json
  playwright.config.ts
  src/
    scan.ts
    fingerprint.ts
    diff.ts
  fixtures/
    bad.html
    good.html
  baseline.json
```

Dùng TypeScript cho session đầu tiên vì đây là đường ngắn nhất đến `@axe-core/playwright`; quyết định .NET wrapper có thể để sau khi concept đã chứng minh.

### Commands

```bash
mkdir A11yRoute
cd A11yRoute
npm init -y
npm install -D typescript tsx @playwright/test @axe-core/playwright
npx playwright install chromium
```

Tạo `fixtures/bad.html`:

```html
<!doctype html>
<html lang="en">
<body>
  <button><img src="icon.png"></button>
</body>
</html>
```

Tạo một local static server đơn giản hoặc dùng Playwright `page.setContent()` để tránh mất thời gian setup server.

### First vertical slice

`scan.ts`:

1. launch Chromium,
2. load `bad.html`,
3. chạy `new AxeBuilder({ page }).analyze()`,
4. lấy `violations`,
5. tạo fingerprint từ `rule.id + target`,
6. serialize JSON.

`diff.ts`:

- đọc baseline cũ,
- tạo sets,
- output `new/existing/resolved`.

### Expected result

Lần 1:

```text
New: 1+
Existing: 0
Resolved: 0
```

Accept baseline.

Sau đó sửa HTML thêm accessible name phù hợp và scan lại:

```text
New: 0
Existing: 0
Resolved: 1+
```

Con số exact phụ thuộc axe rule output, nên mục tiêu là chứng minh diff pipeline chứ không hard-code rule count trước khi chạy thực tế.

### Verification checklist

- [ ] Playwright mở fixture thành công.
- [ ] axe trả ít nhất một violation cho fixture xấu.
- [ ] Result được serialize JSON.
- [ ] Fingerprint ổn định khi scan cùng fixture hai lần.
- [ ] Baseline diff phân biệt được existing/new/resolved.
- [ ] Sau khi sửa fixture, ít nhất một baseline entry chuyển thành resolved.
- [ ] Không có AI, database hoặc web dashboard nào được thêm vào session đầu.

### Stop condition

**Dừng session ngay khi pipeline `page → axe result → fingerprint → baseline diff → console summary` chạy được end-to-end.**

Không tiếp tục làm UI, GitHub integration, Docker hay architecture refactor trong ngày đầu.

## Research notes

### Confirmed facts

- Playwright có hướng dẫn accessibility testing bằng `@axe-core/playwright`, đồng thời cảnh báo automated tests chỉ bắt được một phần accessibility issues: https://playwright.dev/docs/accessibility-testing
- WCAG 2.2 là W3C Recommendation và chứa các success criteria cho web accessibility: https://www.w3.org/TR/WCAG22/
- W3C liệt kê các success criteria mới của WCAG 2.2 như Focus Not Obscured, Dragging Movements, Target Size, Consistent Help và Accessible Authentication: https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/

### Analysis

Khoảng trống đáng khai thác không phải viết thêm một accessibility scanner, mà là tạo một **regression-control workflow** dễ bật cho project đang có legacy debt.

### Assumption

Developer/QA sẽ chấp nhận baseline debt nếu tool giúp họ ngăn lỗi mới và làm debt giảm dần thay vì đòi project phải sạch ngay từ đầu.

### Recommendation

Bắt đầu bằng CLI open-source + CI workflow. Chỉ xem xét dashboard hoặc SaaS khi đã chứng minh rằng baseline diff và fingerprint thực sự ổn định trên nhiều project.
