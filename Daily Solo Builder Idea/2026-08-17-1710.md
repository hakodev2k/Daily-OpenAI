# Ý tưởng hôm nay: A11y Regression Guard — Accessibility Diff cho Web App

## 1. Tóm tắt ý tưởng

**A11y Regression Guard** là một công cụ self-hosted giúp developer chạy accessibility scan trên các luồng web quan trọng, lưu baseline và chỉ báo những accessibility violations mới xuất hiện sau mỗi thay đổi. Công cụ phù hợp cho developer hoặc team nhỏ đã có Playwright nhưng chưa có quy trình accessibility regression rõ ràng, tránh tình trạng mỗi lần chạy axe-core lại nhận một danh sách lỗi dài mà không biết lỗi nào vừa bị code mới gây ra.

- **Kích thước dự án:** Medium
- **Thời gian MVP ước tính:** 2–3 tuần làm ngoài giờ
- **Người dùng chính:** web developer hoặc QA automation engineer trong team nhỏ
- **Vấn đề chính:** accessibility issues dễ được phát hiện quá muộn và kết quả scan khó đưa vào quy trình regression nếu project đã tồn tại nhiều lỗi cũ.

## 2. Bài toán thực tế

### Confirmed facts

Playwright có tài liệu chính thức hướng dẫn accessibility testing bằng `@axe-core/playwright`. Các ví dụ gồm những lỗi như contrast kém, form control thiếu label hoặc duplicate IDs. Tuy nhiên Playwright cũng nhấn mạnh rằng automated accessibility testing chỉ phát hiện được một phần vấn đề và cần kết hợp với manual assessment và inclusive user testing. Nguồn: **Playwright — Accessibility testing**.

`axe-core` là accessibility engine mã nguồn mở có thể tích hợp vào automated tests. Deque cho biết axe-core hỗ trợ các rules liên quan WCAG 2.0, 2.1 và 2.2, và chính dự án cũng nêu rằng automated checks không bao phủ toàn bộ accessibility issues. Nguồn: **Deque — axe-core README và API documentation**.

### Observation

Vấn đề thực tế với một project đã phát triển lâu không chỉ là “có accessibility violations hay không”. Nếu hiện tại ứng dụng có 40 lỗi và CI fail ngay khi số lỗi lớn hơn 0, team thường có hai lựa chọn không hấp dẫn:

1. sửa toàn bộ backlog trước khi bật CI gate; hoặc
2. bỏ qua automated accessibility gate vì quá ồn.

### Analysis

Một công cụ tập trung vào **regression** thay vì yêu cầu “zero issue ngay lập tức” có thể hữu ích hơn:

- snapshot trạng thái hiện tại làm baseline;
- chạy lại các route/flow sau thay đổi;
- fingerprint violations ổn định;
- phân loại `new`, `existing`, `resolved`;
- chỉ fail CI khi có lỗi mới vượt policy.

### Assumption

Giả định chính của MVP: một developer/team nhỏ sẵn sàng bổ sung 5–20 route hoặc flow quan trọng vào test manifest nếu việc đó giúp họ ngăn accessibility regressions mà không phải xử lý toàn bộ legacy backlog ngay lập tức.

## 3. Người dùng mục tiêu

### Primary user

Developer hoặc QA automation engineer đang duy trì một web application có:

- Playwright hoặc khả năng chạy Chromium tự động;
- nhiều màn hình đã tồn tại;
- accessibility chưa phải tiêu chí bắt buộc từ ngày đầu;
- CI/CD trên GitHub Actions, Azure DevOps hoặc tương tự.

### Context sử dụng

Người dùng thường phát triển feature, sửa UI, refactor component hoặc đổi design system. Những thay đổi này có thể vô tình làm:

- mất accessible name;
- phá heading hierarchy;
- tạo duplicate IDs;
- thêm màu có contrast không phù hợp;
- render button/link sai semantic;
- thêm ARIA attribute không hợp lệ.

### Pain point

Một raw axe report có thể quá dài và không trả lời được câu hỏi quan trọng nhất khi review PR:

> “Code trong PR này có tạo accessibility regression mới không?”

### Current workaround

- chạy browser extension bằng tay;
- chạy axe trong từng test rồi fail nếu có violation;
- lưu JSON report nhưng tự so sánh bằng mắt;
- chỉ accessibility test trước release;
- hoặc không gate regression vì legacy issues quá nhiều.

### Vì sao họ có thể thử giải pháp

A11y Regression Guard không bắt team phải đạt accessibility hoàn hảo ngay. Nó tạo quy tắc đơn giản hơn:

> “Không làm accessibility tệ hơn hôm qua, và dần giảm backlog.”

## 4. Giải pháp đề xuất

Người dùng khai báo một manifest nhỏ:

```yaml
project: etm-portal
baseUrl: https://qa.example.com
scenarios:
  - name: login-page
    path: /login
  - name: timesheet-list
    path: /timesheets
    authState: auth/admin.json
  - name: create-timesheet-dialog
    flow: flows/create-timesheet.spec.ts
```

Runner sẽ:

1. mở route hoặc chạy flow bằng Playwright;
2. chạy `@axe-core/playwright` ở state cần kiểm tra;
3. normalize kết quả;
4. tạo fingerprint cho từng violation/node;
5. so với baseline gần nhất;
6. sinh report gồm `new`, `existing`, `resolved`;
7. trả exit code khác 0 nếu policy bị vi phạm.

### Input

- URL/route hoặc Playwright flow;
- optional authentication state;
- rule tags như `wcag2a`, `wcag2aa`, `wcag21aa`, `wcag22aa`;
- baseline JSON.

### Processing

Mỗi finding được normalize theo các thành phần ổn định, ví dụ:

```text
ruleId
+ scenario
+ normalized target selector
+ selected HTML/semantic signature
```

Không nên fingerprint toàn bộ HTML vì class động hoặc generated IDs có thể làm baseline thay đổi giả.

### Output

- console summary;
- machine-readable JSON;
- HTML report;
- exit code cho CI.

Ví dụ:

```text
Accessibility Regression Report

New       : 2
Existing  : 14
Resolved  : 3

NEW serious: button-name
Scenario: create-timesheet-dialog
Target: button.save-entry

NEW moderate: label
Scenario: login-page
Target: input[name="username"]
```

### Automated

- browser execution;
- axe scan;
- result normalization;
- baseline diff;
- report generation;
- CI gate.

### User control

Người dùng vẫn quyết định:

- route/flow nào quan trọng;
- severity nào được phép;
- finding nào chấp nhận vào baseline;
- khi nào baseline được cập nhật;
- manual accessibility checks nào cần thực hiện.

### Key differentiator

Không phải một accessibility scanner mới. Scanner dùng axe-core đã được kiểm chứng; sản phẩm tập trung vào **versioned regression workflow**:

```text
scan → fingerprint → baseline → diff → policy → evidence
```

### Ví dụ end-to-end

Một developer sửa component `DialogButton`.

1. PR pipeline dựng app.
2. Guard chạy scenario `create-timesheet-dialog`.
3. axe-core phát hiện `button-name` trên nút Save mới bị mất text/aria-label.
4. Baseline cũ không chứa finding này.
5. Report đánh dấu `NEW / serious`.
6. CI fail.
7. Developer sửa component.
8. Chạy lại: finding biến mất, pipeline pass.

Một lỗi contrast cũ đã có trong baseline vẫn được report là `existing`, nhưng không làm PR fail nếu policy chỉ chặn regression mới.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Có giá trị ngay trên personal project hoặc web app đang làm việc. Không cần có customer bên ngoài mới sử dụng được.

### Technical learning value

Project buộc developer xử lý nhiều bài toán tốt cho Middle → Senior:

- browser automation;
- deterministic fingerprints;
- snapshot/baseline testing;
- CI exit policies;
- flaky-result reduction;
- artifact/report generation;
- accessibility fundamentals.

### Phù hợp cho solo developer

Core engine khá hẹp:

```text
Playwright + axe-core + JSON baseline + diff engine + CLI
```

Không cần multi-tenant SaaS, billing, Kubernetes hay queue ở MVP.

### Vẫn hữu ích với một người dùng

Ngay cả chỉ sử dụng cho project cá nhân, nó vẫn giúp:

- học accessibility theo case thực tế;
- tránh regression;
- tạo portfolio project có chiều sâu;
- tạo reusable QA tool cho các repo sau.

### Điều gì khiến dự án thất bại

Nếu fingerprint quá bất ổn khiến mỗi DOM thay đổi nhỏ tạo hàng chục “new findings”, công cụ sẽ trở nên noisy và mất giá trị.

### Lý do mạnh nhất để không build

Nếu bạn chỉ có một web app nhỏ với vài trang và có thể duy trì policy “zero axe violations” trực tiếp trong Playwright, thì abstraction này có thể không đáng công. Project chỉ thực sự nổi bật khi giải quyết legacy baseline, nhiều scenario và regression history.

## 7. Luồng hoạt động

```text
Developer defines scenario
        ↓
CLI validates manifest
        ↓
Launch Playwright browser
        ↓
Navigate / execute scenario
        ↓
Run axe-core
        ↓
Normalize findings
        ↓
Generate fingerprints
        ↓
Load baseline
        ↓
Diff results
        ↓
Apply policy
        ↓
Write JSON + HTML report
        ↓
Exit 0 / Exit 1
```

### Alternative flow — chưa có baseline

Lần đầu:

```bash
a11yguard scan --create-baseline
```

Tool scan và yêu cầu explicit flag để tạo baseline, tránh âm thầm coi mọi violation là hợp lệ.

### Alternative flow — finding đã được sửa

Nếu fingerprint tồn tại trong baseline nhưng không còn xuất hiện:

```text
status = RESOLVED
```

Report phải highlight để user có thể prune baseline.

### Failure case — route không load

Không được coi “không scan được” là pass.

```text
Scenario status: ERROR
Reason: Navigation timeout
Exit: non-zero
```

### Failure case — axe injection lỗi

Đánh dấu infrastructure error riêng với accessibility failure.

### Failure case — selector động

Fingerprint engine cần normalize attributes/configurable ignore patterns để giảm false diffs.

## 9. Công nghệ đề xuất

### .NET 10

Tại thời điểm tháng 8/2026, .NET 10 là một release được hỗ trợ và phù hợp để xây CLI mới.

**Vì sao phù hợp:**

- đúng stack hiện tại;
- strong typing cho model/report;
- cross-platform;
- dễ publish single-file binary;
- thuận tiện viết CLI orchestration.

**Simpler alternative:** TypeScript CLI thuần vì Playwright và axe đều thuộc ecosystem Node.

**Khi nào chọn TypeScript thay .NET:** nếu mục tiêu là đóng góp/open-source cho cộng đồng frontend nhanh nhất và muốn loại bỏ IPC giữa .NET với Node.

### Playwright for .NET hoặc Node worker

Hai lựa chọn:

**Option A — Microsoft.Playwright:** giữ toàn bộ orchestration bằng C#.

**Option B — Node runner nhỏ:** dùng package `@axe-core/playwright` trực tiếp và giao tiếp JSON với .NET CLI.

Khuyến nghị MVP: **Node/TypeScript runner + .NET CLI chỉ khi muốn luyện kiến trúc tool đa-runtime**. Còn để ship nhanh nhất, TypeScript toàn bộ thậm chí còn đơn giản hơn.

Nếu ưu tiên stack cá nhân, dùng .NET CLI + Node runner là bài tập integration thú vị nhưng không bắt buộc.

### `@axe-core/playwright`

Official Playwright documentation sử dụng package này cho accessibility testing. Nó cho phép chạy axe engine ngay trong Playwright flow. Nguồn: **Playwright — Accessibility testing; Deque axe-core-npm**.

### YAML parser

Ví dụ `YamlDotNet` nếu CLI là C#.

**Alternative:** JSON config để giảm dependency.

### Spectre.Console hoặc System.CommandLine

Để tạo UX CLI rõ ràng.

**Simpler:** tự parse args ở prototype.

### HTML report

RazorLight hoặc template HTML đơn giản.

MVP không cần Vue.

### Playwright

Dùng thêm chính Playwright để E2E test tool against sample sites.

### GitHub Actions

Dùng cho CI, release binary và dogfood accessibility guard chính nó nếu sau này có dashboard.

### Docker

Optional. Chỉ cần khi muốn cố định browser/runtime cho CI.

## 11. API và tích hợp

### Playwright

**Purpose:** điều khiển browser và dựng UI state cần scan.

**Authentication:** không cần với Playwright itself; target web app có thể cần auth.

**Cost/rate limit:** open-source tooling, không phải paid API.

**Privacy:** browser session có thể chứa cookie/token; không đưa chúng vào report.

**Fallback:** scan public route hoặc setup custom flow.

### axe-core / `@axe-core/playwright`

**Purpose:** accessibility rules engine.

**Authentication:** không.

**Cost:** axe-core là open-source; package chạy local. Nguồn: **Deque axe-core repository**.

**Privacy:** kết quả được xử lý local; axe API có thể chạy mà không cần gửi page content tới third-party server. Nguồn: **Deque axe-core API documentation**.

**Fallback:** không nên tự viết accessibility engine. Nếu axe integration unavailable, scenario phải fail rõ ràng.

### GitHub Actions

**Purpose:** chạy regression trên PR.

**Authentication:** `GITHUB_TOKEN` chỉ cần nếu sau này muốn comment PR/upload qua API; basic workflow artifact không cần tool tự quản token.

**Cost:** phụ thuộc plan/minutes của repository; không nên hard-code claim về pricing.

**Fallback:** local CLI hoặc Azure DevOps.

### SARIF — Later

Có thể export để dùng với code scanning UI nếu phù hợp. Không đưa vào core MVP trước khi CLI diff hoạt động ổn định.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem cần deterministic behavior:

```text
same scan result + same baseline → same diff
```

AI không nên quyết định một accessibility violation có phải regression hay không.

Nếu sau này thêm AI, nó chỉ nên làm optional explanation:

```text
Finding → giải thích bằng ngôn ngữ dễ hiểu → gợi ý khu vực code cần kiểm tra
```

Nhưng output phải được gắn nhãn advisory, không tham gia pass/fail.

Deterministic fallback luôn là:

- rule documentation;
- affected node;
- impact;
- axe help text;
- baseline status.

Điều này loại bỏ cost, latency, privacy risk và hallucination khỏi MVP.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác nhận baseline-diff thực sự giảm noise.

**Main tasks:**

1. chọn một web app có sẵn;
2. chạy axe trên 5 route;
3. lưu raw JSON;
4. sửa cố ý một button để tạo accessibility regression;
5. viết script nhỏ so raw result cũ/mới;
6. đánh giá xem fingerprint nào đủ ổn định.

**Expected output:** 2 JSON scan + prototype diff.

**Completion criteria:** tool nhận ra regression cố ý mà không đánh dấu hàng loạt findings không đổi là mới.

### Phase 1 — Core MVP

**Goal:** có CLI chạy end-to-end.

**Main tasks:**

- config loader;
- scenario runner;
- axe adapter;
- finding normalizer;
- fingerprint engine;
- baseline loader;
- diff engine;
- console output;
- exit policy.

**Expected output:**

```bash
a11yguard scan
```

chạy được trên sample app và trả exit code đúng.

**Completion criteria:** 3 scenario, ít nhất 1 baseline violation và 1 injected regression được phân loại chính xác.

### Phase 2 — Reliability

**Goal:** giảm flaky result và failure ambiguity.

**Main tasks:**

- navigation retry hợp lý;

- distinguish scan error vs accessibility failure;

- unit tests cho fingerprints;
- integration tests;

**Expected output:** cùng một commit chạy liên tiếp cho cùng diff.

### Phase 3 — Useful expansion

**Goal:** làm tool thực sự dễ dùng trong PR workflow.

**Main tasks:**

- HTML report;
- screenshot cho finding mới;

**Expected output:** report có đủ evidence để developer sửa issue mà không phải rerun thủ công.

**Completion criteria:** dogfood trên một repository thật trong ít nhất 1 tuần.

### Phase 4 — Production readiness

**Goal:** package ổn định và dễ vận hành.

**Main tasks:**

- semantic versioning;
- migration/version của baseline schema;
- release binaries;
- Docker image optional;
- structured logs;
- troubleshooting guide;
- security notes;
- documentation về limits của automated accessibility testing.

**Expected output:** developer mới có thể add tool vào repo trong khoảng 15–30 phút.

**Completion criteria:** fresh repo setup từ README chạy thành công mà không cần sửa source tool.

## 14. Các bài toán kỹ thuật đáng học

### 1. Stable fingerprinting

DOM là dữ liệu động. Nếu fingerprint dùng full selector hoặc full HTML, UI refactor vô hại có thể bị coi là finding mới.

Cần học cách cân bằng:

- stability;
- uniqueness;
- explainability.

Đây là bài toán giống log/event deduplication và regression identity.

### 2. Snapshot/baseline evolution

Baseline không được trở thành “sọt rác chấp nhận mọi lỗi”. Tool cần phân biệt:

- baseline creation;
- explicit approval;
- resolved issue cleanup;
- schema versioning.

Skill cải thiện: configuration governance và test architecture.

### 3. Browser automation reliability

Page readiness, animation, lazy-rendered controls và authenticated state đều ảnh hưởng scan.

Skill cải thiện:

- Playwright synchronization;
- deterministic E2E design;
- fixture isolation;
- failure diagnostics.

### 4. CI policy design

Không phải mọi issue đều nên block build giống nhau.

Ví dụ:

```yaml
policy:
  new:
    critical: fail
    serious: fail
    moderate: warn
    minor: warn
```

Skill cải thiện: quality gates và risk-based engineering.

### 5. Privacy-preserving test evidence

Screenshot, DOM snippet và authenticated page có thể chứa PII.

Skill cải thiện:

- redaction;
- minimum evidence collection;
- artifact retention;
- secure CI practices.

## 15. Rủi ro và cách xử lý

### Risk: automated scan bị hiểu nhầm là accessibility compliance đầy đủ

**Mitigation:** documentation và report luôn hiển thị rõ automated testing không thay thế manual testing. Điều này phù hợp với hướng dẫn chính thức của Playwright. Nguồn: **Playwright — Accessibility testing**.

### Risk: fingerprint instability

**Mitigation:**

- canonicalize target selectors;
- bỏ dynamic IDs bằng config;
- dùng rule + scenario + semantic target;
- tạo test fixtures chuyên cho fingerprint engine.

### Risk: baseline che giấu technical debt

**Mitigation:** report luôn hiển thị số `existing`; thêm `resolved` và trend sau MVP. Baseline update phải explicit.

### Risk: scope expansion

Tool rất dễ biến thành full QA platform.

**Mitigation:** MVP chỉ giải quyết accessibility diff. Không thêm generic visual regression, performance, API testing hay test management.

### Risk: authenticated app secrets

**Mitigation:** không commit storage-state có token; allow env path; mask sensitive values; document CI secret practices.

### Risk: browser/runtime maintenance

**Mitigation:** pin Playwright version; cung cấp install command; optional Docker image sau MVP.

### Risk: axe behavior thay đổi khi nâng version

Một rule update có thể tạo findings mới dù app không thay đổi.

**Mitigation:** lưu `axeVersion` trong baseline/report. Khi engine version thay đổi, report phải flag `engine_changed=true`; có migration/rescan workflow rõ ràng.

### Risk: user adoption thấp

Nếu setup scenario quá phức tạp, người dùng sẽ quay lại browser extension.

**Mitigation:** support URL-only scenario trước; advanced flow là optional.

Tạo `scan.mjs` với flow:

```javascript
import { chromium } from 'playwright';
import AxeBuilder from '@axe-core/playwright';
import path from 'node:path';
import { pathToFileURL } from 'node:url';

const browser = await chromium.launch();
const page = await browser.newPage();
const file = pathToFileURL(path.resolve('fixtures/bad-form.html')).href;

await page.goto(file);

const results = await new AxeBuilder({ page }).analyze();

for (const violation of results.violations) {
  console.log(`${violation.impact ?? 'unknown'} | ${violation.id}`);
  for (const node of violation.nodes) {
    console.log(`  ${node.target.join(' ')}`);
  }
}

await browser.close();
```

## Research notes

### Confirmed facts

- Playwright chính thức hướng dẫn accessibility testing sử dụng `@axe-core/playwright` và cảnh báo automated testing không thể phát hiện mọi accessibility issue. Nguồn: **Playwright documentation — Accessibility testing**.
- axe-core là accessibility testing engine cho web UI, hỗ trợ các rule sets liên quan WCAG 2.0/2.1/2.2 và có package Playwright integration. Nguồn: **Deque axe-core** và **axe-core-npm** repositories.
- axe-core API có thể chạy local trong testing infrastructure và trả structured violation results để lưu hoặc xử lý tiếp. Nguồn: **Deque axe-core API documentation**.

### Observation

Những công cụ này đã giải tốt phần “scan”. Khoảng trống mà project này nhắm tới không phải viết accessibility rules mới, mà là xây workflow baseline/diff đủ ổn định để legacy project có thể áp dụng nguyên tắc “không tạo regression mới”.

### Recommendation

MVP nên reuse axe-core hoàn toàn và đầu tư phần lớn engineering effort vào fingerprint stability, baseline governance, CI semantics và actionable evidence. Đó là nơi project có khác biệt rõ nhất và cũng là phần mang lại giá trị học tập lớn nhất cho một solo developer.
