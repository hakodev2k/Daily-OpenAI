# Ý tưởng hôm nay: Webhook Replay Lab

## 1. Tóm tắt ý tưởng

Webhook Replay Lab là một công cụ self-hosted dành cho developer để **nhận, lưu, kiểm tra, chỉnh sửa an toàn và replay webhook** từ các dịch vụ như GitHub, Stripe hoặc hệ thống nội bộ vào local/staging endpoint. Nó giải quyết bài toán debug integration khi webhook chỉ xuất hiện ở một thời điểm cụ thể, payload khó tái tạo, hoặc hệ thống đích đang tạm thời lỗi.

- Người dùng chính: backend developer, QA automation engineer, solo builder làm việc với API/webhook.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Webhook là cơ chế phổ biến để hệ thống bên ngoài chủ động gửi sự kiện tới backend. Khi integration lỗi, developer thường cần tái hiện chính xác request đã nhận: method, headers, body, signature, timestamp và response của endpoint.

**Confirmed facts:**

- GitHub cho phép redeliver webhook, nhưng tài liệu hiện tại chỉ cho phép redeliver các delivery gần đây trong một cửa sổ giới hạn; GitHub cũng không tự động redeliver mọi failed delivery. [GitHub Docs — Redelivering webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks)
- GitHub khuyến nghị xử lý webhook nhanh, có thể đưa payload vào queue để xử lý async, và dùng delivery ID để chống xử lý trùng/replay ngoài ý muốn. [GitHub Docs — Webhook best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)
- Stripe CLI hỗ trợ trigger event, forward webhook vào local và resend event, cho thấy workflow “capture → inspect → replay” là một nhu cầu thực tế trong phát triển integration. [Stripe Docs — Stripe CLI](https://docs.stripe.com/stripe-cli/use-cli)

**Observation:** mỗi provider có tooling riêng, nhưng developer làm với nhiều provider vẫn phải đổi qua lại giữa dashboard, CLI, logs và local tunnel.

**Assumption cần kiểm chứng:** developer/team nhỏ sẽ thấy có giá trị ở một công cụ provider-agnostic, self-hosted, giữ lịch sử lâu hơn và cho phép replay có kiểm soát.

Hiện tại workaround phổ biến là:

- Copy JSON từ log rồi dùng Postman/cURL gửi lại.
- Dùng provider-specific CLI.
- Lưu payload thủ công vào file.
- Dùng request bin/tunnel để xem request.
- Viết script tạm cho từng integration.

Các cách này hoạt động nhưng dễ mất headers, signature context, query string, response status hoặc metadata cần thiết để tái hiện lỗi.

## 3. Người dùng mục tiêu

**Primary user:** backend developer làm việc với nhiều webhook integration trong dự án cá nhân, SaaS nhỏ hoặc hệ thống nội bộ.

- Bối cảnh sử dụng: phát triển hoặc debug GitHub App, payment callback, notification service, CRM integration, CI/CD webhook, automation bot.
- Main pain point: nhận được một webhook lỗi nhưng không tái hiện chính xác request sau đó.
- Workaround: copy payload từ logs rồi dựng lại request bằng Postman/cURL.
- Lý do thử công cụ: có một inbox thống nhất, lưu request đầy đủ và replay bằng một click/CLI command.

MVP chỉ phục vụ developer cá nhân hoặc team nhỏ, không cố trở thành enterprise event platform.

## 4. Giải pháp đề xuất

Người dùng tạo một **capture endpoint** trong Webhook Replay Lab, ví dụ:

```text
https://hooks.example.com/inbox/github-orders
```

Sau đó cấu hình provider gửi webhook tới endpoint này. Tool sẽ:

1. Nhận request.
2. Lưu method, path, query, headers, body, thời gian, source IP và content type.
3. Trả response mặc định hoặc forward ngay tới target endpoint thật.
4. Ghi lại response của target.
5. Hiển thị request trong dashboard.
6. Cho phép replay request tới local/staging/prod target được whitelist.

### Ví dụ end-to-end

Một GitHub webhook `pull_request.closed` tới production worker nhưng worker đang lỗi DB.

Developer mở Webhook Replay Lab:

- Chọn delivery đã fail.
- Xem raw headers/body.
- Chọn target `http://host.docker.internal:5000/webhooks/github`.
- Replay.
- Backend trả `500`.
- Developer sửa code.
- Replay lại cùng request.
- Backend trả `200`.

**Điểm khác biệt:** không chỉ là request bin; tool lưu lịch sử, forward, replay, diff response, hỗ trợ redaction và deterministic reproduction.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Có thể dùng ngay cho các project cá nhân dùng GitHub webhook, payment webhook, bot hoặc automation service. Giá trị xuất hiện từ ngày đầu ngay cả khi chỉ có một người dùng.

### Technical learning value

Dự án buộc developer xử lý nhiều bài toán production thực tế:

- HTTP request fidelity.
- Signature verification.
- Idempotency.
- Retry.
- Background processing.
- Sensitive-data redaction.
- Local networking và Docker.
- Observability.

### Vì sao phù hợp solo developer

Core domain nhỏ và rõ: capture, store, forward, replay. Không cần ML, không cần dữ liệu lớn, không cần mobile app hay distributed architecture ở MVP.

### Điều gì làm ý tưởng thất bại

- Developer thấy cURL/Postman/provider CLI đã đủ.
- Tool lưu payload nhạy cảm không tạo được niềm tin.
- Replay không giữ đủ fidelity khiến debug không đáng tin.

### Lý do mạnh nhất để không build

Nếu mục tiêu chỉ là debug một provider duy nhất như Stripe, provider-native tooling có thể đơn giản hơn và không cần thêm service phải vận hành.

## 6. Phạm vi MVP

### Must have

- Tạo webhook inbox với random secret URL.
- Capture `method`, `path`, `query`, `headers`, `body`, `receivedAt`.
- Hiển thị danh sách delivery và request detail.
- Cấu hình một target endpoint cho mỗi inbox.
- Forward request tới target.
- Replay delivery thủ công.
- Lưu response status, headers, duration và body giới hạn kích thước.
- Secret header redaction mặc định.
- Payload-size limit.

### Should have

- Retry với exponential backoff.
- Delivery tags: success / failed / replayed.
- Compare original response với replay response.
- Export cURL.
- Search theo header/event type/status.
- CLI replay command.

### Later

- Team accounts.
- GitHub/Stripe adapters.
- Signature regeneration plugin.
- Replay batch.
- Mock response mode.
- Contract assertions.
- Time-travel test scenario.
- Cloud-hosted SaaS.

## 7. Luồng hoạt động

### Normal flow

Provider gửi webhook
→ endpoint kiểm tra inbox token
→ validate payload size/content type
→ redact headers nhạy cảm
→ lưu delivery
→ enqueue forward operation
→ forward tới target
→ lưu response
→ dashboard cập nhật trạng thái.

### Replay flow

User chọn delivery
→ kiểm tra quyền và target whitelist
→ clone request snapshot
→ thêm replay metadata nội bộ
→ gửi tới target
→ lưu replay attempt riêng
→ hiển thị diff status/body/duration.

### Alternative / failure cases

- Target timeout → đánh dấu failed, không mất original payload.
- Target DNS lỗi → retry theo policy.
- Payload quá lớn → trả `413 Payload Too Large`.
- Invalid inbox token → `404` thay vì tiết lộ endpoint tồn tại.
- Sensitive header → không hiển thị raw trừ khi người dùng bật explicit capture rule.
- Replay vào production → mặc định disable; phải whitelist target trước.

## 8. Kiến trúc đề xuất

### Frontend

Vue 3 SPA nhỏ để xem inbox, deliveries và replay attempts.

### Backend

ASP.NET Core modular monolith gồm các module:

- `Inboxes`
- `Deliveries`
- `Forwarding`
- `Replay`
- `Redaction`

### Database

PostgreSQL lưu metadata và body nhỏ. Với MVP chưa cần object storage nếu giới hạn payload ở khoảng 1 MB.

### Background worker

Dùng `BackgroundService` hoặc Hangfire để forward/retry mà không giữ HTTP request của provider quá lâu.

### Queue

MVP có thể dùng database-backed Hangfire queue. Không cần RabbitMQ ban đầu.

### Cache

Không cần cache ở MVP.

### Authentication

Có thể bắt đầu bằng single-user admin secret/session nếu self-hosted cá nhân. OAuth để sau.

### External APIs

Không cần external API cho core workflow. Tool chỉ nhận và gửi HTTP request.

### AI

Không cần ở MVP.

### Logging

Structured logging với request ID, delivery ID, target ID và attempt number.

### Deployment

Docker Compose gồm API + PostgreSQL. Có thể chạy trên VPS, mini PC hoặc Azure Container Apps/App Service.

## 9. Công nghệ đề xuất

### .NET 10 + ASP.NET Core

Phù hợp cho HTTP-heavy backend, middleware, background services và dependency injection.

**Simpler alternative:** Minimal API project duy nhất.

**Outgrow point:** chỉ cần tách worker riêng khi traffic lớn hoặc replay job nặng.

### EF Core + PostgreSQL

Đủ tốt cho delivery history, filtering và retry state.

**Simpler alternative:** SQLite cho single-user local MVP.

**Outgrow point:** nếu payload volume lớn, chuyển body sang S3-compatible object storage.

### Hangfire

Phù hợp cho retry, delayed job, dashboard debug và persistence đơn giản.

**Simpler alternative:** `BackgroundService` + database polling.

**Outgrow point:** nếu throughput cao hoặc multi-region, chuyển sang broker như RabbitMQ/Azure Service Bus.

### Vue 3 + Vite

Nhanh để build dashboard delivery inspector.

**Simpler alternative:** Razor Pages để giảm số project.

### Docker Compose

Phù hợp self-hosted và local development.

### Playwright

Dùng E2E test cho capture → inspect → replay workflow.

### GitHub Actions

Build, test và publish Docker image.

## 10. Thiết kế dữ liệu ban đầu

### Inbox

**Purpose:** cấu hình một webhook receiver.

Fields:

- `Id`
- `Name`
- `PublicTokenHash`
- `TargetUrl`
- `IsForwardingEnabled`
- `CreatedAt`

Relationship: một Inbox có nhiều Delivery.

Retention: giữ cho tới khi user xóa; token chỉ lưu hash.

### Delivery

**Purpose:** immutable snapshot của incoming webhook.

Fields:

- `Id`
- `InboxId`
- `Method`
- `Path`
- `QueryString`
- `HeadersJson`
- `Body`
- `BodySha256`
- `ContentType`
- `ReceivedAt`
- `SourceIp`

Retention: configurable, ví dụ 7/30/90 ngày.

### DeliveryAttempt

**Purpose:** ghi mỗi lần forward hoặc replay.

Fields:

- `Id`
- `DeliveryId`
- `AttemptType`
- `TargetUrl`
- `StartedAt`
- `CompletedAt`
- `StatusCode`
- `DurationMs`
- `ResponseHeadersJson`
- `ResponseBody`
- `Error`

Relationship: một Delivery có nhiều attempts.

### RedactionRule

**Purpose:** che dữ liệu nhạy cảm.

Fields:

- `Id`
- `InboxId`
- `Location` (`Header`, `JsonPath`, `Query`)
- `Pattern`
- `Action`

Retention: giữ theo inbox.

## 11. API và tích hợp

### Generic HTTP webhook

- Purpose: core input/output.
- Authentication: inbox secret/token riêng.
- Cost/rate limit: do chính server kiểm soát.
- Privacy: payload có thể chứa PII/token.
- Fallback: disable persistence và dùng passthrough-only mode trong tương lai.

### GitHub Webhooks

- Purpose: một integration thực tế để validation MVP.
- Authentication: GitHub webhook secret có thể verify bằng signature.
- Rate/cost: GitHub không tính phí riêng cho webhook; REST API chỉ cần nếu muốn import/redeliver provider-side delivery.
- Permission concern: API redelivery cần quyền webhook phù hợp. [GitHub REST API — Repository webhooks](https://docs.github.com/en/rest/repos/webhooks)
- Fallback: dùng capture endpoint trực tiếp, không gọi GitHub REST API.

### Stripe CLI / webhook

- Purpose: test local forwarding và replay concept.
- Authentication: provider-managed credentials nếu dùng Stripe CLI; Webhook Replay Lab core không cần Stripe credential.
- Privacy: payment event có thể chứa thông tin nhạy cảm, nên redaction phải ưu tiên.
- Fallback: generic webhook capture.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Capture, compare và replay đều là deterministic HTTP operations. AI sẽ làm core workflow kém tin cậy hơn mà không tạo nhiều giá trị.

Nếu mở rộng về sau, AI chỉ nên dùng optional để:

- Tóm tắt payload lớn.
- Giải thích khác biệt giữa hai attempts.
- Gợi ý nguyên nhân dựa trên response/log snippets.

Nhưng replay engine tuyệt đối không phụ thuộc AI.

## 14. Các bài toán kỹ thuật đáng học

### 1. HTTP request fidelity

Phải quyết định metadata nào cần lưu để replay đủ giống original. Kỹ năng học được: HTTP semantics, headers, encoding, content types, redirects.

### 2. Idempotency và replay safety

Replay có thể tạo side effect lần hai. Kỹ năng học được: idempotency key, duplicate detection, safe retry design.

### 3. Reliable background processing

Provider không nên chờ backend target xử lý lâu. Kỹ năng học được: queue, timeout, retry, dead-letter behavior.

### 4. Sensitive-data handling

Webhook có thể chứa token, email, customer data. Kỹ năng học được: redaction, encryption, retention policy, least privilege.

### 5. Signature verification

Provider thường ký payload dựa trên raw bytes. Kỹ năng học được: HMAC verification, canonical raw body handling, timing-safe compare.

## 15. Rủi ro và cách xử lý

### Data privacy

**Risk:** lưu raw webhook chứa PII/secrets.

**Mitigation:** redaction mặc định, retention ngắn, encryption at rest, body-size limit, optional “metadata-only” mode.

### Replay gây side effect trùng

**Risk:** tạo duplicate order/payment/action.

**Mitigation:** production target disabled mặc định; warning rõ; whitelist; replay header; user-confirmed target; sandbox first.

### SSRF

**Risk:** user nhập target URL nội bộ nguy hiểm.

**Mitigation:** allowlist scheme/host, chặn metadata IP ranges, DNS re-resolution checks, single-user mode trước.

### Scope expansion

**Risk:** biến thành full event platform.

**Mitigation:** MVP chỉ capture/forward/replay HTTP.

### Storage growth

**Risk:** payload lịch sử chiếm nhiều disk.

**Mitigation:** retention cleanup + hard size limit.

### Provider-specific signature

**Risk:** signature cũ có timestamp expired hoặc target từ chối replay.

**Mitigation:** giữ raw request; không hứa regenerate mọi signature; provider adapter là feature sau MVP.

## 16. Kiểm thử

### Strategy

- Unit tests cho redaction, URL validation, retry decision.
- Integration tests với PostgreSQL + local fake target.
- E2E Playwright cho capture → UI → replay.
- Failure-path tests cho timeout/DNS/5xx.
- Security tests cho SSRF và secret exposure.

### 5 test scenario quan trọng nhất

1. Nhận JSON webhook và forward nguyên body tới target.
2. Target trả `500`, attempt được lưu và retry đúng policy.
3. Replay một delivery tạo attempt mới nhưng không sửa original snapshot.
4. Header `Authorization`/secret được redact khỏi UI/log.
5. Target URL trỏ tới loopback/metadata network bị policy chặn khi production mode bật.

## 17. Cách đo dự án có hữu ích hay không

Không dùng page view hay số request tổng làm vanity metric.

Metrics có ý nghĩa:

- **Replay success rate:** % replay tái hiện hoặc xác nhận fix thành công.
- **Debug time saved:** thời gian từ lỗi webhook → reproduction trước và sau khi dùng tool.
- **Capture completeness:** % delivery có đủ body + headers + response để debug.
- **Failure visibility:** % failed forward có error reason rõ ràng.
- **Repeated use:** số ngày/tuần có ít nhất một delivery được inspect hoặc replay.
- **Reliability:** % delivery được persistence thành công trước khi forward.

Mục tiêu validation cá nhân hợp lý: trong 30 ngày, tool được dùng để debug ít nhất 3 incident và tiết kiệm rõ rệt thao tác dựng lại request thủ công.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, tạo vertical slice đầu tiên:

**POST webhook → lưu memory → forward tới fake target → xem response trong terminal.**

### Files/components cần tạo

```text
WebhookReplayLab.sln
src/
  WebhookReplayLab.Api/
    Program.cs
    Models/Delivery.cs
    Services/WebhookForwarder.cs
tests/
  WebhookReplayLab.Tests/
```

### Setup commands

```bash
dotnet new sln -n WebhookReplayLab
dotnet new webapi -n WebhookReplayLab.Api -o src/WebhookReplayLab.Api
dotnet new xunit -n WebhookReplayLab.Tests -o tests/WebhookReplayLab.Tests
dotnet sln add src/WebhookReplayLab.Api
dotnet sln add tests/WebhookReplayLab.Tests
dotnet add tests/WebhookReplayLab.Tests reference src/WebhookReplayLab.Api
```

### First vertical slice

Implement endpoint:

```text
POST /hooks/{token}
```

Behavior:

1. Read raw body.
2. Capture request headers.
3. Create `Delivery` in an in-memory list.
4. Forward body + content type tới configurable `TargetUrl`.
5. Print:

```text
Delivery: <id>
Received: 2026-...
Forwarded: http://localhost:6001/test
Status: 200
Duration: 42ms
```

Tạo fake target ngay trong test hoặc một minimal API thứ hai:

```text
POST /test → 200 OK
```

### Verification checklist

- [ ] `curl` gửi JSON vào `/hooks/dev` nhận `202` hoặc `200`.
- [ ] Raw JSON đến fake target không bị thay đổi.
- [ ] `Content-Type` được forward đúng.
- [ ] Delivery có unique ID.
- [ ] Target trả `500` thì original request vẫn còn trong memory.
- [ ] Có ít nhất một integration test chạy pass.

### Stop condition

Kết thúc session ngay khi có thể chạy:

```bash
curl -X POST http://localhost:5000/hooks/dev \
  -H "Content-Type: application/json" \
  -d '{"event":"order.created","id":123}'
```

và quan sát được request đã được capture, forward sang fake target, status/duration được ghi lại. Không làm dashboard, database, auth hoặc AI trong session đầu tiên.
