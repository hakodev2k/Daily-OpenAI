# Ý tưởng hôm nay: TraceCapsule — Incident Reproduction Bundle từ OpenTelemetry

## 1. Tóm tắt ý tưởng

TraceCapsule là một developer tool self-hosted giúp developer **đóng gói một khoảng thời gian sự cố thành một “incident capsule” có thể mang đi debug**: traces, structured logs, metrics snapshot, request metadata, service map và các correlation ID liên quan. Thay vì gửi hàng loạt screenshot/log rời rạc cho đồng đội hoặc tự mò lại dữ liệu vài giờ sau, người dùng tạo một bundle chuẩn hóa để tái hiện và phân tích sự cố nhanh hơn.

- Người dùng chính: backend developer hoặc solo developer vận hành ứng dụng .NET có OpenTelemetry.
- Bài toán chính: dữ liệu debug bị phân tán giữa logs, traces, metrics và nhiều service, khiến việc tái hiện lỗi sau khi sự cố xảy ra tốn thời gian.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Khi một lỗi production hoặc staging xảy ra, developer thường phải ghép nhiều mảnh thông tin:

- log của API;
- trace của request;
- downstream HTTP call;
- database span;
- metric spike;
- exception stack;
- correlation ID;
- deployment/version metadata.

**Confirmed facts:** OpenTelemetry .NET hiện hỗ trợ ổn định cả traces, metrics và logs. Aspire Dashboard có thể nhận telemetry qua OTLP và cung cấp giao diện/query cho logs, traces và spans. Microsoft cũng cảnh báo telemetry có thể chứa dữ liệu nhạy cảm và cần bảo vệ quyền truy cập. Nguồn: OpenTelemetry .NET docs và Microsoft Aspire docs.

**Observation:** observability tools giúp xem dữ liệu tốt, nhưng workflow “chọn một incident → gom đúng evidence → chia sẻ/tái phân tích” vẫn thường mang tính thủ công.

**Assumption cần kiểm chứng:** developer sẽ thấy hữu ích nếu có thể tạo một bundle nhỏ, có cấu trúc và tự redaction, thay vì chia sẻ toàn bộ dashboard hoặc copy nhiều log riêng lẻ.

Workaround hiện tại thường là:

- copy logs vào ticket;
- gửi trace ID qua chat;
- chụp screenshot dashboard;
- export JSON thủ công;
- viết script riêng để lấy dữ liệu theo khoảng thời gian.

Các cách này dễ thiếu context, khó tái sử dụng và có nguy cơ vô tình đưa dữ liệu nhạy cảm vào ticket/chat.

## 3. Người dùng mục tiêu

**Primary user:** backend developer vận hành 1–10 service nhỏ hoặc một modular monolith có OpenTelemetry.

- Bối cảnh: debug lỗi staging/production sau alert, customer report hoặc failed background job.
- Main pain point: mất 15–60 phút chỉ để gom đủ dữ liệu trước khi bắt đầu phân tích nguyên nhân.
- Workaround: mở Grafana/Application Insights/Aspire Dashboard rồi copy thủ công nhiều nơi.
- Lý do thử TraceCapsule: tạo một bundle bằng một lệnh hoặc một click, có correlation và redaction sẵn.

MVP không nhắm tới enterprise observability platform; chỉ tập trung vào workflow incident handoff/reproduction cho developer cá nhân hoặc team nhỏ.

## 4. Giải pháp đề xuất

Người dùng chọn một trong ba input:

1. `traceId`;
2. khoảng thời gian + service name;
3. request/correlation ID.

TraceCapsule sẽ:

1. Query telemetry backend.
2. Tìm root trace và các span liên quan.
3. Lấy structured logs cùng trace/span ID.
4. Lấy metric snapshot trong khoảng thời gian ngắn quanh incident.
5. Redact field nhạy cảm theo rule.
6. Sinh một bundle dạng thư mục/ZIP:

```text
incident-2026-08-20-001/
  manifest.json
  traces.json
  logs.jsonl
  metrics.json
  service-map.json
  summary.md
```

7. Tạo `summary.md` deterministic chứa timeline, services bị ảnh hưởng, errors, slow spans và links/reference IDs.

### Ví dụ end-to-end

Một background job xử lý đơn hàng trả lỗi `500` lúc 14:07.

Developer chạy:

```bash
tracecapsule capture --service orders-api --from 14:06 --to 14:08
```

Tool tìm thấy một trace có exception, một downstream call timeout và một log warning ngay trước đó. Bundle được tạo local. Developer mở `summary.md`, thấy request timeline và span chậm nhất, sau đó gửi bundle cho đồng đội hoặc attach vào issue nội bộ.

**Điểm khác biệt:** không cố thay observability UI; nó tạo artifact chuẩn hóa, nhỏ gọn và có thể lưu/version/share để phục vụ điều tra.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Có thể dùng ngay cho chính các project .NET cá nhân đang có logging/tracing. Giá trị xuất hiện ngay cả khi chỉ có một người dùng vì nó rút ngắn bước thu thập evidence.

### Technical learning value

Dự án buộc developer hiểu sâu hơn về:

- OpenTelemetry data model;
- trace/log correlation;
- OTLP;
- query APIs;
- redaction;
- incident timeline;
- CLI UX;
- serialization hiệu quả.

### Phù hợp solo developer

Core workflow nhỏ: query → correlate → redact → export. Không cần ML, không cần distributed system, không cần ingest telemetry riêng ở MVP.

### Có thể hữu ích với rất ít user

Một mình developer vẫn dùng nó như “debug snapshot generator” cho các app cá nhân.

### Điều gì làm ý tưởng thất bại

- Existing observability backend đã export incident đủ tiện.
- Query API khác nhau giữa backend khiến integration tốn công.
- Bundle không đủ context để debug.

### Lý do mạnh nhất để không build

Nếu toàn bộ workload chỉ dùng Aspire Dashboard local và lỗi dễ tái hiện trực tiếp, việc export bundle có thể không tiết kiệm đủ thời gian để đáng duy trì thêm tool.

## 6. Phạm vi MVP

### Must have

- CLI `capture` theo time range + service.
- Adapter đầu tiên cho Aspire Dashboard hoặc một OTLP-compatible/queryable source đơn giản.
- Thu thập traces + logs liên quan.
- Correlate bằng trace ID/span ID.
- Redact các key phổ biến như authorization, cookie, password, token.
- Sinh `manifest.json` + `summary.md` + raw JSON.
- Giới hạn kích thước bundle.

### Should have

- Metric snapshot.
- Capture trực tiếp bằng trace ID.
- Service dependency map.
- Rule redaction bằng config file.
- ZIP export.
- Diff hai incident capsule.

### Later

- Grafana Tempo/Loki adapter.
- Application Insights adapter.
- Jaeger adapter.
- Web UI.
- GitHub issue attachment workflow.
- AI-assisted incident summary.
- MCP server cho coding agent đọc capsule.

## 7. Luồng hoạt động

User chạy `tracecapsule capture`
→ validate input/time range
→ query telemetry source
→ normalize traces/logs
→ correlate records
→ apply redaction rules
→ compute derived facts
→ ghi bundle local
→ in summary path và statistics.

### Failure cases

- Không tìm thấy trace → tạo bundle rỗng có diagnostic reason.
- Backend timeout → retry giới hạn.
- Quá nhiều logs → truncate theo budget và ghi rõ dropped count.
- Field nhạy cảm → redact trước khi ghi disk.
- Query API unavailable → giữ config, trả lỗi rõ và không tạo bundle giả.

Không cần ở MVP.

## 11. API và tích hợp

### Aspire Dashboard

**Purpose:** nguồn telemetry đầu tiên cho local/dev workflow.

**Confirmed fact:** Aspire Dashboard nhận telemetry qua OTLP và hiện có CLI/API để truy vấn logs, traces và spans. Microsoft docs mô tả `aspire otel logs`, `aspire otel traces` và `aspire otel spans`, bao gồm structured JSON output.

- Authentication: tùy deployment; dashboard có browser token/API security options.
- Cost: local, không có API cost riêng.
- Privacy: telemetry có thể chứa secrets/runtime data.
- Fallback: import từ JSON file export nếu query trực tiếp không khả dụng.

### OpenTelemetry

**Purpose:** common data model.

- Authentication: phụ thuộc backend.
- Rate limit: phụ thuộc backend.
- Privacy: cần redaction trước persist/share.
- Fallback: file-based import.

### Future adapters

Tempo/Loki, Jaeger, Application Insights chỉ làm sau khi MVP chứng minh utility.

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

MVP không cần AI vì correlation, timeline và error extraction đều deterministic.

Later AI có thể dùng để:

- tóm tắt incident;
- nhóm các error message;
- đề xuất câu hỏi điều tra tiếp theo.

Nếu dùng AI:

- Input: capsule đã redacted.
- Output: JSON structured gồm `summary`, `suspectedAreas`, `questions`.
- Validation: mọi claim phải reference trace/span/log ID có thật trong capsule.
- Fallback: deterministic summary.
- Risks: hallucination, privacy, token cost, latency.

Không cho AI quyết định bỏ/redact dữ liệu.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** chứng minh bundle giúp debug nhanh hơn.

**Tasks:** lấy một app .NET có OpenTelemetry, tạo một incident test, export trace/log thủ công rồi định nghĩa tối thiểu những field thật sự cần.

**Expected output:** sample capsule bằng tay.

**Completion criteria:** có thể nhìn capsule và hiểu timeline lỗi mà không mở dashboard.

### Phase 1 — Core MVP

**Goal:** capture tự động từ một source.

**Tasks:** CLI, adapter, normalization, correlation, export.

**Expected output:** `tracecapsule capture` sinh folder hoàn chỉnh.

**Completion criteria:** một lỗi integration test tạo được capsule có trace + logs liên quan.

### Phase 2 — Reliability

**Goal:** bundle an toàn và predictable.

**Tasks:** redaction, limits, retry, schema version, tests, error handling.

**Expected output:** bundle không chứa field nhạy cảm đã định nghĩa.

**Completion criteria:** test suite cover timeout, empty result, oversize, redaction.

### Phase 3 — Useful expansion

**Goal:** tăng giá trị điều tra.

**Tasks:** metrics snapshot, service map, diff capsules, trace-ID capture.

**Expected output:** incident comparison hữu ích giữa before/after fix.

### Phase 4 — Production readiness

**Goal:** dùng ổn định như dev tool.

**Tasks:** cross-platform release, docs, sample config, telemetry-source compatibility matrix, release automation.

**Completion criteria:** fresh machine có thể install và capture sample incident trong dưới 10 phút.

## 14. Các bài toán kỹ thuật đáng học

### 1. Trace-log correlation

Học cách nối telemetry records bằng trace ID, span ID và resource attributes.

### 2. Schema normalization

Các backend biểu diễn dữ liệu khác nhau; cần đưa về model chung mà không mất evidence quan trọng.

### 3. Privacy-preserving export

Học redaction pipeline, allowlist/denylist và xử lý nested attributes.

### 4. Bounded data collection

Phải kiểm soát time range, record count và bundle size để tránh export khổng lồ.

### 5. Incident timeline generation

Biến telemetry raw thành timeline deterministic có thể đọc nhanh mà không suy diễn quá mức.

## 15. Rủi ro và cách xử lý

### Dữ liệu nhạy cảm

**Risk:** logs/traces chứa email, token hoặc payload cá nhân.

**Mitigation:** redact trước disk, default denylist, custom rules, dry-run report.

### Backend-specific API

**Risk:** mỗi observability product có query API khác nhau.

**Mitigation:** chỉ support một source ở MVP; adapter interface rõ.

### Bundle quá lớn

**Risk:** time range rộng kéo quá nhiều logs.

**Mitigation:** hard limit, sampling/truncation và manifest ghi dropped count.

### False confidence

**Risk:** developer nghĩ capsule là toàn bộ incident evidence.

**Mitigation:** manifest ghi rõ query window, source, dropped records và limitations.

### Scope expansion

**Risk:** biến thành full observability platform.

**Mitigation:** không ingest telemetry liên tục; chỉ query/export theo yêu cầu.

## 16. Kiểm thử

### Strategy

- Unit tests cho correlation/redaction/timeline.
- Integration tests với fake telemetry source.
- Contract tests cho adapter.
- Failure-path tests cho timeout/empty/oversize.
- Security tests đảm bảo credential không lọt vào bundle.

### 5 scenario quan trọng nhất

1. Một trace có spans từ 3 services được gom đúng vào capsule.
2. Logs có cùng trace ID được correlate đúng.
3. Field nhạy cảm nested bị redact trước khi ghi file.
4. Query trả 100.000 logs nhưng bundle tuân thủ size/record budget và ghi dropped count.
5. Source timeout không tạo bundle “success” giả.

## 17. Cách đo dự án có hữu ích hay không

- **Time-to-evidence:** thời gian từ lúc biết incident đến khi có đủ dữ liệu bắt đầu debug.
- **Capsule completeness:** % incident có đủ trace + logs liên quan.
- **Repeated usage:** số incident thực tế được capture mỗi tháng.
- **Shareability:** % capsule có thể đưa cho người khác và họ hiểu timeline mà không mở dashboard gốc.
- **Redaction reliability:** số secret/sensitive-value leak trong test corpus phải bằng 0.
- **Technical reliability:** capture success rate trên source được support.

Validation cá nhân hợp lý: dùng tool cho ít nhất 5 incident/test failures và giảm rõ thời gian thu thập evidence so với workflow thủ công.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong 60–120 phút, build vertical slice đầu tiên:

**đọc một file telemetry JSON mẫu → correlate logs theo trace ID → sinh `summary.md`.**

### Files/components cần tạo

```text
TraceCapsule.sln
src/
  TraceCapsule.Cli/
    Program.cs
    Models/NormalizedTrace.cs
    Models/NormalizedLog.cs
    Services/CorrelationService.cs
    Services/SummaryWriter.cs
samples/
  traces.json
  logs.jsonl
tests/
  TraceCapsule.Tests/
```

### Setup commands

```bash
dotnet new sln -n TraceCapsule
dotnet new console -n TraceCapsule.Cli -o src/TraceCapsule.Cli
dotnet new xunit -n TraceCapsule.Tests -o tests/TraceCapsule.Tests
dotnet sln add src/TraceCapsule.Cli
dotnet sln add tests/TraceCapsule.Tests
dotnet add tests/TraceCapsule.Tests reference src/TraceCapsule.Cli
```

### First vertical slice

Tạo sample trace:

```json
{
  "traceId": "trace-001",
  "service": "orders-api",
  "durationMs": 1830,
  "status": "Error"
}
```

Tạo `logs.jsonl` với 3 log, trong đó 2 log có `traceId=trace-001` và 1 log không liên quan.

CLI:

```bash
dotnet run --project src/TraceCapsule.Cli -- capture-file samples/traces.json samples/logs.jsonl
```

Expected output:

```text
capsule/
  manifest.json
  logs.jsonl
  summary.md
```

`summary.md` phải hiển thị:

- Trace ID
- Service
- Duration
- Status
- 2 correlated logs
- 1 ignored log count

### Verification checklist

- [ ] CLI chạy được trên Windows.
- [ ] Chỉ log đúng trace ID được đưa vào summary.
- [ ] Output deterministic khi chạy hai lần với cùng input.
- [ ] Có ít nhất một unit test cho correlation.
- [ ] Không có database hoặc web UI trong session đầu.

### Stop condition

Kết thúc session khi command trên tạo được `summary.md` chính xác từ sample telemetry và test correlation chạy pass.
