# Ý tưởng hôm nay: SafeClone — Privacy-Safe Database Snapshot Builder

## 1. Tóm tắt ý tưởng

SafeClone là một công cụ self-hosted giúp developer tạo **bản sao database dành cho local/dev/test từ dữ liệu thật nhưng đã được biến đổi an toàn**, thay vì copy nguyên production database hoặc tự viết script masking rời rạc cho từng project. Công cụ tập trung vào deterministic pseudonymization, giữ quan hệ dữ liệu hợp lệ, kiểm tra constraint sau khi clone và tạo audit report để biết cột nào đã được xử lý.

- Người dùng chính: backend developer hoặc solo SaaS developer cần dữ liệu thực tế để debug/test nhưng không muốn mang nguyên dữ liệu nhạy cảm về môi trường non-production.
- Vấn đề chính: test bằng fake data thường không tái hiện được bug thật, còn copy production data nguyên trạng tạo rủi ro privacy/security và khó quản lý.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–4 tuần**.

## 2. Bài toán thực tế

### Confirmed facts

PostgreSQL cung cấp `pg_dump` để xuất database thành SQL script hoặc các format dump khác, và tài liệu chính thức mô tả SQL dump là một trong các phương pháp chuẩn để backup/restore database. PostgreSQL cũng cung cấp `information_schema`, bao gồm metadata về tables, columns và constraints, nên một công cụ có thể introspect schema mà không cần hard-code cấu trúc database.

Nguồn:

- PostgreSQL — Backup and Restore: https://www.postgresql.org/docs/current/backup.html
- PostgreSQL — Reference / pg_dump: https://www.postgresql.org/docs/current/reference.html
- PostgreSQL — Information Schema: https://www.postgresql.org/docs/current/information-schema.html

Microsoft SQL Server có Dynamic Data Masking để giảm mức độ lộ dữ liệu trong query result cho user không có quyền `UNMASK`, nhưng tài liệu Microsoft lưu ý rằng dữ liệu gốc trong database **không bị thay đổi**. Điều này khác với nhu cầu tạo một database non-production đã được transform thực sự.

Nguồn:

- Microsoft Learn — Dynamic Data Masking: https://learn.microsoft.com/en-us/sql/relational-databases/security/dynamic-data-masking

Microsoft hiện liệt kê .NET 10 là bản **Long Term Support**, được hỗ trợ đến tháng 11/2028, phù hợp để bắt đầu một tool mới vào thời điểm hiện tại.

Nguồn:

- Microsoft Learn — .NET releases and support: https://learn.microsoft.com/en-us/dotnet/core/releases-and-support

### Observation

Developer thường gặp hai lựa chọn không lý tưởng:

1. Tạo seed data thủ công: an toàn hơn nhưng thường không đủ độ phức tạp để tái hiện lỗi production.
2. Copy production DB về local/staging: dữ liệu thực tế hơn nhưng có thể chứa email, số điện thoại, tên, địa chỉ, token reference, internal note hoặc business data không nên xuất hiện ở môi trường non-production.

Ngoài ra, các script masking viết thủ công thường có các vấn đề:

- mỗi project một script khác nhau;
- khó biết đã xử lý đủ cột chưa;
- thay email bằng random string có thể làm hỏng unique constraint;
- random hóa foreign key có thể phá referential integrity;
- cùng một customer xuất hiện ở nhiều bảng nhưng bị transform thành nhiều giá trị khác nhau;
- sau vài tháng schema thay đổi nhưng masking rule không được cập nhật.

### Assumption cần kiểm chứng

Một developer sẽ thấy SafeClone hữu ích nếu tool giảm đáng kể thời gian tạo dataset test thực tế, đồng thời có thể chứng minh rằng các cột nhạy cảm đã được transform trước khi database clone được sử dụng.

## 3. Người dùng mục tiêu

**Primary user:** backend developer làm việc với PostgreSQL và cần tạo database local/staging từ snapshot production hoặc database gần production.

### User profile

- Làm backend API, background jobs hoặc integration service.
- Có quyền đọc một database nguồn hoặc file dump.
- Cần debug bug khó tái hiện bằng seed data nhỏ.
- Không muốn developer workstation chứa nguyên dữ liệu nhạy cảm.

### Context of use

Ví dụ:

- một bug chỉ xảy ra với customer có nhiều order, subscription và notification history;
- query performance chỉ chậm khi distribution dữ liệu đủ lớn;
- QA cần dataset có quan hệ thật nhưng không cần biết danh tính thật của customer;
- staging cần refresh dữ liệu định kỳ nhưng không được giữ raw PII.

### Main pain point

Tạo dataset có hình dạng giống production nhưng an toàn thường cần nhiều script SQL thủ công và kiểm tra bằng mắt.

### Current workaround

- `pg_dump` rồi restore nguyên bản;
- seed data bằng EF Core/Faker;
- chạy vài câu `UPDATE` thủ công sau khi restore;
- tự viết script masking per-project.

### Vì sao họ sẽ thử SafeClone

Một config khai báo rule một lần, sau đó có thể chạy lại mỗi lần cần refresh database và nhận report machine-readable về những gì đã được transform.

## 4. Giải pháp đề xuất

SafeClone nhận:

- connection tới source database **hoặc** database tạm đã restore từ dump;
- connection tới target database;
- file policy mô tả cách xử lý từng cột nhạy cảm.

Ví dụ policy:

```yaml
tables:
  users:
    email:
      strategy: deterministic-email
    full_name:
      strategy: fake-name
    phone:
      strategy: null
  orders:
    customer_email:
      strategy: deterministic-email
```

### Main workflow

1. User chạy `safeclone inspect`.
2. Tool đọc schema và sinh inventory tables/columns/constraints.
3. User xác nhận rule cho các cột cần transform.
4. User chạy `safeclone clone`.
5. Tool copy schema/data sang target hoặc transform database clone hiện có.
6. Các transformer chạy theo dependency order.
7. Tool validate NOT NULL, UNIQUE, FK và row counts.
8. Tool sinh report:
   - bảng nào đã xử lý;
   - cột nào có rule;
   - cột nghi ngờ nhạy cảm nhưng chưa có rule;
   - constraint nào fail;
   - checksum/count trước và sau.

### Input

- database connection;
- YAML/JSON policy;
- optional deterministic seed;
- include/exclude table patterns.

### Processing

- schema introspection;
- sensitive-column rule matching;
- deterministic tokenization/hash-based mapping;
- batched updates hoặc transform-on-copy;
- constraint validation.

### Output

- sanitized target database;
- Markdown/JSON report;
- non-zero CLI exit code nếu validation không đạt.

### Tự động hóa

Tool tự động:

- đọc schema;
- sắp thứ tự xử lý;
- batch update;
- retry transaction hợp lý;
- kiểm tra rule coverage;
- validate database sau transform.

### User vẫn kiểm soát

User quyết định:

- cột nào được coi là sensitive;
- strategy nào dùng;
- có giữ deterministic mapping giữa các bảng hay không;
- database nào được phép làm source/target;
- có được phép overwrite target hay không.

### Điểm khác biệt

SafeClone không cố trở thành data-generation platform hoàn chỉnh. Điểm trọng tâm là:

> **Lấy dataset có hình dạng thực tế → biến đổi reproducible → chứng minh bằng validation report rằng clone đã sẵn sàng dùng cho dev/test.**

### Ví dụ end-to-end

Production có:

```text
Users
- Id
- Email
- FullName

Orders
- Id
- UserId
- BillingEmail
```

Customer thật:

```text
Email        = customer@example.com
BillingEmail = customer@example.com
```

SafeClone dùng deterministic transformer dựa trên secret seed nội bộ của clone run:

```text
Email        = user-81f3@example.invalid
BillingEmail = user-81f3@example.invalid
```

Hai field vẫn match nhau nên business logic liên quan tới email correlation còn hoạt động, nhưng clone không giữ email thật.

## 7. Luồng hoạt động

### Flow chính

User tạo policy
→ `safeclone inspect`
→ schema được đọc
→ tool kiểm tra rule có trỏ đúng table/column hay không
→ `safeclone plan`
→ hiển thị tables, row estimates và transformations
→ user chạy `safeclone clone`
→ copy hoặc transform target
→ chạy post-transform verification
→ sinh report
→ exit `0` nếu pass.

### Flow khi rule sai

Policy tham chiếu `users.phone_number` nhưng schema mới đã đổi thành `phone`:

→ validation fail trước khi clone
→ report `UnknownColumn`
→ không thực hiện mutation.

### Flow khi UNIQUE collision

Hai giá trị khác nhau transform thành cùng output:

→ batch transaction rollback
→ transformer trả collision error
→ run fail
→ report chỉ rõ table/column và strategy.

### Flow khi target đang chứa data

→ mặc định refuse
→ user phải dùng explicit `--allow-recreate-target` hoặc target database rỗng.

### Flow khi database lớn

→ đọc theo primary-key/keyset batch
→ transform theo chunk
→ commit theo batch có checkpoint
→ log progress.

### Failure cases quan trọng

- network disconnect;
- source connection mất giữa run;
- schema đổi sau khi inspect;
- disk target hết chỗ;
- transformer exception;
- target constraint fail;
- deterministic seed thay đổi ngoài ý muốn.

MVP nên fail-safe: nếu không chắc clone hợp lệ, không đánh dấu run là successful.

## 11. API và tích hợp

### PostgreSQL protocol qua Npgsql

**Purpose:** schema inspection và data transformation.

**Authentication:** PostgreSQL credentials; ưu tiên environment variables hoặc secret store ngoài tool.

**Cost/rate limit:** không có external API rate limit; giới hạn chính là database resource và connection pool.

**Privacy:** tool đọc raw source data trong process memory nên máy chạy tool phải là trusted environment.

**Fallback:** chạy SafeClone gần database trong private network/container thay vì download dump về workstation.

### PostgreSQL `information_schema`

**Purpose:** đọc metadata tables/columns và một phần constraint metadata.

**Authentication:** database account cần quyền đọc metadata/schema tương ứng.

**Cost:** query metadata thấp so với copy data.

**Fallback:** dùng PostgreSQL system catalogs cho metadata PostgreSQL-specific khi `information_schema` không đủ.

### `pg_dump` / `pg_restore`

**Purpose:** optional strategy để clone schema hoặc tạo intermediate dump.

**Authentication:** giống PostgreSQL client tooling.

**Cost:** local compute/storage.

**Fallback:** direct-copy qua Npgsql cho MVP nếu tích hợp process `pg_dump` làm workflow phức tạp hơn.

### SQL Server Dynamic Data Masking

Không phải dependency của MVP. Nó chỉ là bằng chứng rằng masking là một problem domain có support chính thức ở SQL Server, nhưng SafeClone cần **static transformation của clone**, không chỉ masking query result.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem cần tính deterministic, reproducible và audit-friendly. Normal code phù hợp hơn AI cho:

- schema detection;
- transformation;
- FK ordering;
- constraint validation;
- uniqueness checks.

AI có thể được thêm sau để **gợi ý** cột nào có vẻ sensitive dựa trên tên/schema context, nhưng không nên tự động quyết định hoặc transform dữ liệu mà không có policy xác nhận.

Nếu sau này có AI:

- Input: table/column names + types, không gửi raw row data.
- Output: structured suggestions `{column, category, confidence}`.
- Validation: user review bắt buộc.
- Fallback: regex/rule engine.
- Risk: false negative nguy hiểm hơn false positive; vì vậy AI không được là safety boundary.

## 14. Các bài toán kỹ thuật đáng học

### 1. Schema introspection

Tool phải hiểu database mà không có EF entity model.

Kỹ năng học được:

- `information_schema`;
- system catalogs;
- dynamic SQL;
- quoting identifiers;
- type mapping.

### 2. Deterministic pseudonymization

Cùng một input cần tạo cùng một output trong phạm vi clone để giữ correlation.

Kỹ năng học được:

- keyed hashing;
- canonicalization;
- collision handling;
- format-preserving transformation.

### 3. Constraint-preserving transformation

Một transformer có thể vô tình phá:

- `UNIQUE`;
- `NOT NULL`;
- FK;
- length constraint;
- check constraint.

Kỹ năng học được: database integrity và safe migration patterns.

### 4. Large-data batching

Không thể load vài triệu row vào RAM.

Kỹ năng học được:

- keyset pagination;
- server-side streaming;
- batch commit;
- progress checkpoints;
- backpressure.

### 5. Privacy-preserving observability

Tool cần log đủ để debug nhưng không được log chính dữ liệu đang cố bảo vệ.

Kỹ năng học được:

- structured logging;
- metadata-only diagnostics;
- redaction;
- security boundary design.

## 15. Rủi ro và cách xử lý

### Rủi ro: bỏ sót sensitive column

**Mitigation:**

- `inspect` report;
- regex heuristic;
- explicit allowlist/denylist;
- fail CI nếu policy coverage giảm so với schema trước.

### Rủi ro: deterministic transformation vẫn có thể bị reverse-engineer nếu thiết kế yếu

**Mitigation:**

- dùng keyed cryptographic transform thay vì plain unsalted hash;
- không commit seed/key vào repo;
- rotation cho clone environment;
- không quảng cáo pseudonymization là anonymization tuyệt đối.

### Rủi ro: tool phá business semantics

Ví dụ date-shift làm `EndDate < StartDate`.

**Mitigation:** hỗ trợ grouped transformer cho related fields và custom invariant validation.

### Rủi ro: performance quá chậm

**Mitigation:** batch updates, COPY/direct transfer ở phase sau, benchmark trên dataset lớn trước khi thêm feature.

### Rủi ro: schema thay đổi giữa inspect và clone

**Mitigation:** capture schema hash và re-check trước mutation.

### Rủi ro: source/target nhầm lẫn

**Mitigation:** hard guardrail không mutate source; source connection read-only nếu có thể; target phải explicit.

### Rủi ro: scope expansion

Dự án dễ biến thành ETL/data platform.

**Mitigation:** MVP chỉ PostgreSQL + masking + verification. Không orchestration, warehouse, CDC hoặc analytics.

### Rủi ro: compliance expectations

Tool không nên tự tuyên bố clone “compliant”.

**Mitigation:** output chỉ mô tả technical transformations và verification, không đưa legal certification.

### Database fixture

Tạo table đơn giản:

```sql
CREATE TABLE users (
    id uuid PRIMARY KEY,
    email varchar(255) NOT NULL UNIQUE,
    full_name varchar(255) NOT NULL
);
```

Insert 3 rows sample.

### First vertical slice

CLI command tạm:

```bash
dotnet run --project src/SafeClone.Cli -- mask-email \
  --table users \
  --column email
```

Flow:

1. Connect database demo.
2. Query metadata để xác nhận `users.email` tồn tại.
3. Select email theo batch nhỏ.
4. Transform bằng deterministic HMAC-based function với development-only seed.
5. Update values.
6. Query lại.
7. Print:

```text
Table: users
Column: email
Rows processed: 3
Original values remaining: 0
Unique constraint: PASS
Result: PASS
```

### Expected result

Nếu chạy hai database fixture giống nhau với cùng seed, email transformed phải giống nhau. Chạy với seed khác phải cho output khác.

### Verification checklist

- [ ] PostgreSQL Testcontainer start được.
- [ ] Tool đọc được metadata `users.email`.
- [ ] 3 rows được transform.
- [ ] Output giữ format email hợp lệ cho application test.
- [ ] `UNIQUE` constraint không fail.
- [ ] Cùng input + cùng seed → cùng output.
- [ ] Different seed → different output.
- [ ] Console không print original email.
- [ ] Có ít nhất một integration test pass end-to-end.

### Stop condition

Dừng session ngay khi command có thể transform `users.email` trong PostgreSQL Testcontainer và integration test xác nhận:

```text
original email absent
+ deterministic output
+ UNIQUE constraint valid
```

Không làm YAML policy, web UI, SQL Server, row subsetting, scheduler hoặc AI trong buổi đầu tiên.
