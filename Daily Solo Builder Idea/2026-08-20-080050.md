# Ý tưởng hôm nay: CachePulse — GitHub Actions Cache Waste Analyzer

## 1. Tóm tắt ý tưởng

CachePulse là một developer tool self-hosted giúp phân tích cache của GitHub Actions để phát hiện repository đang bị **cache thrashing, cache key sinh quá nhiều biến thể, cache gần như không bao giờ hit hoặc cache chiếm dung lượng nhưng mang lại rất ít lợi ích**. Công cụ đọc metadata cache qua GitHub API, đối chiếu với workflow YAML, rồi tạo báo cáo cụ thể về cache nào nên giữ, cache nào nên xóa và key nào nên thiết kế lại.

- Người dùng chính: developer hoặc team nhỏ dùng GitHub Actions thường xuyên.
- Bài toán chính: cache CI có thể làm build nhanh hơn nhưng cũng dễ tạo hàng loạt cache ít dùng, bị eviction liên tục và khó biết cache strategy hiện tại có thực sự hiệu quả hay không.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

GitHub Actions cho phép cache dependencies và intermediate files giữa các workflow run. Theo tài liệu GitHub, GitHub-hosted runner bắt đầu từ môi trường sạch nên dependency caching có thể giảm download lại và rút ngắn thời gian chạy workflow. GitHub cũng phân biệt rõ cache với artifacts: cache dành cho dữ liệu có thể tái tạo, còn artifacts dùng để lưu output của job sau khi workflow kết thúc.

GitHub hiện áp dụng giới hạn cache repository và eviction policy. Theo tài liệu hiện tại, cache mặc định không được truy cập trong hơn 7 ngày có thể bị xóa; repository mặc định có giới hạn tổng cache 10 GB, và khi vượt giới hạn, cache cũ sẽ bị eviction để tạo chỗ cho cache mới. GitHub cảnh báo tình trạng này có thể dẫn tới **cache thrashing**, tức cache liên tục được tạo rồi bị xóa trước khi kịp được tái sử dụng.

Nguồn chính thức:

- GitHub Docs — Dependency caching: https://docs.github.com/en/actions/concepts/workflows-and-actions/dependency-caching
- GitHub Docs — Dependency caching reference: https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching
- GitHub Docs — Managing caches: https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manage-caches
- GitHub Docs — REST API endpoints for Actions cache: https://docs.github.com/en/rest/actions/cache

### Confirmed facts

- Cache key có thể exact-match hoặc fallback qua `restore-keys`.
- Nội dung của cache đã tồn tại không được sửa; muốn thay đổi phải tạo cache mới với key khác.
- GitHub có REST API để query và quản lý GitHub Actions cache.
- GitHub ghi nhận cache thrashing là một tình trạng thực tế khi cache storage bị eviction thường xuyên.
- Cache không nên chứa secrets hoặc credentials vì cache có thể được restore bởi workflow có quyền đọc phù hợp.

### Observation

Trong nhiều repository, developer chỉ nhìn thấy build “có cache” hay “không có cache” ở từng run, nhưng không có một góc nhìn dài hạn kiểu:

- cache key nào tạo 200 biến thể/tháng;
- cache nào chiếm nhiều GB nhưng chỉ hit một lần;
- branch nào đang tạo cache không bao giờ được dùng lại;
- restore key nào quá rộng;
- cache nào đang bị eviction rồi tái tạo lặp đi lặp lại;
- workflow nào cache dữ liệu tốn nhiều thời gian upload hơn lượng thời gian tiết kiệm được.

### Assumption cần kiểm chứng

Developer/team nhỏ sẽ thấy có giá trị ở một công cụ chỉ tập trung vào **cache efficiency và cache hygiene**, thay vì dùng dashboard GitHub thủ công hoặc đọc từng workflow log.

Hiện tại workaround phổ biến là:

- vào GitHub Actions UI để xem cache;
- dùng `gh cache` để list/delete;
- đọc workflow YAML bằng mắt;
- xem log từng run để biết hit/miss;
- xóa cache thủ công khi repository đầy.

Các cách này đủ cho repository nhỏ nhưng nhanh chóng trở nên thủ công khi có nhiều branch, matrix build, SDK version hoặc dependency lock file.

## 3. Người dùng mục tiêu

### Primary user

Backend developer hoặc solo SaaS developer có 3–20 repository dùng GitHub Actions cho build/test/publish.

### Context of use

Repository thường có:

- .NET restore cache;
- NuGet packages;
- npm/pnpm/yarn dependencies;
- Playwright browser binaries;
- Docker layer related caches;
- matrix build theo OS hoặc SDK version.

### Main pain point

CI chậm hoặc cache storage liên tục đầy nhưng developer không biết cache nào thực sự có giá trị.

### Current workaround

Mở GitHub UI, chạy `gh cache list`, đọc workflow YAML và xóa cache thủ công.

### Lý do họ sẽ thử CachePulse

Một lệnh hoặc một dashboard cho biết ngay:

- cache đang dùng bao nhiêu dung lượng;
- nhóm cache nào có churn cao;
- key nào tạo quá nhiều biến thể;
- cache nào có dấu hiệu ít được tái sử dụng;
- đề xuất sửa workflow cụ thể.

MVP chỉ phục vụ GitHub Actions, không cố hỗ trợ GitLab CI, Azure DevOps hay Jenkins ngay từ đầu.

## 4. Giải pháp đề xuất

CachePulse hoạt động theo workflow:

1. User kết nối một repository GitHub.
2. Tool gọi GitHub Actions Cache REST API để lấy danh sách cache hiện tại.
3. Tool đọc `.github/workflows/*.yml` từ repository.
4. Parser tìm các bước `actions/cache`, `setup-dotnet`, `setup-node` hoặc các setup action có caching option.
5. Tool normalize cache key expression thành template.
6. Tool nhóm cache theo logical prefix/template.
7. Tool tính các chỉ số:
   - số lượng cache entries;
   - tổng size;
   - tuổi cache;
   - thời gian từ create tới last access nếu API cung cấp metadata tương ứng;
   - churn giữa các key gần nhau;
   - branch/ref distribution;
   - lock-file hash cardinality;
   - cache density trên từng workflow.
8. Tool sinh các finding như:
   - `High churn`;
   - `Likely low reuse`;
   - `Overly-specific key`;
   - `Broad restore-key`;
   - `Possible cache thrashing`;
   - `Large cache family`;
   - `Sensitive-path risk`.
9. User xem finding và quyết định sửa workflow hoặc xóa cache.

### Input

- GitHub repository.
- GitHub App hoặc fine-grained token có quyền đọc metadata cần thiết.
- Optional: workflow-run logs trong phase sau.

### Processing

Deterministic parsing + rule engine. Không cần AI ở core.

### Output

Ví dụ:

```text
Repository: sample-api
Total cache size: 8.6 GB
Cache families: 14

Finding: nuget-linux-main-*
Entries: 61
Size: 4.1 GB
Pattern: hashFiles('**/*.csproj')
Risk: High churn
Reason: key changes on many project-file edits even when package graph is unchanged
Recommendation: consider hashing package lock files instead
```

### Key differentiator

Không chỉ list cache. Tool cố trả lời câu hỏi thực tế hơn:

**“Cache strategy này có đang tiết kiệm CI time hay chỉ tạo thêm storage churn?”**

### Ví dụ end-to-end

Một repository .NET dùng:

```yaml
key: nuget-${{ runner.os }}-${{ hashFiles('**/*.csproj') }}
```

Mỗi thay đổi nhỏ trong `.csproj` tạo key mới. Sau vài tuần repository có nhiều cache tương tự.

CachePulse:

- phát hiện 40 cache cùng logical prefix;
- nhóm chúng thành một cache family;
- thấy tổng size 3.2 GB;
- phát hiện key phụ thuộc toàn bộ `.csproj`;
- đề xuất chuyển sang `packages.lock.json` nếu project đã dùng lock file;
- user sửa workflow;
- lần scan sau số lượng cache variants giảm rõ rệt.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

CachePulse có thể dùng ngay trên chính các repository cá nhân chạy GitHub Actions. Không cần có khách hàng mới tạo giá trị.

### Technical learning value

Dự án giúp học sâu về:

- GitHub REST API;
- CI caching semantics;
- YAML parsing;
- static workflow analysis;
- GitHub authentication;
- time-series metrics;
- rule engines;
- optimization measurement.

### Vì sao phù hợp solo developer

Core domain khá nhỏ:

- fetch cache metadata;
- parse workflow;
- group cache families;
- calculate findings;
- display report.

Không cần distributed architecture hay large-scale data pipeline.

### Vì sao vẫn hữu ích nếu chỉ có một user

Nếu bản thân có nhiều repository GitHub Actions, tool vẫn giúp:

- giảm build friction;
- tránh cache đầy;
- hiểu rõ CI performance;
- kiểm tra cache hygiene định kỳ.

### Điều gì làm ý tưởng thất bại

- Cache API metadata không đủ để suy ra hit rate chính xác.
- Developer thấy GitHub UI + `gh cache` đã đủ.
- Tool đưa recommendation quá generic.

### Lý do mạnh nhất để không build

GitHub không cung cấp trực tiếp một metric hoàn chỉnh kiểu “cache X đã giúp tiết kiệm Y phút”. Nếu muốn ROI chính xác, tool sẽ phải kết hợp workflow logs hoặc instrumentation bổ sung, khiến scope tăng đáng kể.

## 7. Luồng hoạt động

### Normal flow

User chọn repository
→ authenticate GitHub
→ fetch cache metadata
→ fetch workflow YAML
→ validate/parse YAML
→ normalize cache key expressions
→ group cache families
→ calculate metrics
→ evaluate rules
→ store scan
→ render findings.

### Rescan flow

User chạy lại scan
→ fetch latest state
→ compare với previous snapshot
→ update trends
→ mark findings new/resolved/persisting.

### Failure cases

#### GitHub API rate limit

- Không retry liên tục.
- Hiển thị thời gian scan gần nhất.
- Retry với backoff.

#### Workflow YAML không parse được

- Vẫn hiển thị cache inventory.
- Mark workflow analysis partial.

#### Cache API không trả đủ metadata

- Không suy diễn hit rate.
- Finding chỉ dựa trên dữ liệu xác nhận được.

#### Repository có workflow generated/dynamic

- Chỉ phân tích YAML thực tế trong repository.
- Mark unsupported expression nếu key quá động.

#### Permission thiếu

- Trả lỗi permission cụ thể.
- Không yêu cầu quyền write ở MVP.

## 11. API và tích hợp

### GitHub Actions Cache REST API

**Purpose:** lấy cache inventory và metadata.

**Authentication:** GitHub token/GitHub App theo quyền API yêu cầu.

**Cost/rate limit:** bị giới hạn bởi GitHub API rate limits; tool phải cache metadata nội bộ và tránh scan liên tục.

**Privacy:** cache key có thể chứa branch/version/file hash; coi là repository metadata.

**Fallback:** user có thể import output từ `gh cache list` ở local-only mode sau này.

Nguồn: https://docs.github.com/en/rest/actions/cache

### GitHub Repository Contents API

**Purpose:** đọc `.github/workflows/*.yml`.

**Authentication:** read repository content.

**Rate limit:** scan một lần rồi dùng conditional request/commit SHA để tránh tải lại workflow không đổi.

**Privacy:** workflow có thể chứa names/configuration; không log raw YAML không cần thiết.

**Fallback:** local directory scan qua CLI.

### `gh cache`

GitHub Docs xác nhận cache có thể được quản lý bằng GitHub CLI `gh cache`.

**Purpose:** có thể dùng làm optional local adapter hoặc tạo cleanup command cho user.

Nguồn: https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manage-caches

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem cần tính chính xác và evidence rõ ràng. Rule engine deterministic tốt hơn AI cho:

- grouping cache;
- cache size thresholds;
- age analysis;
- key cardinality;
- workflow parsing;
- recommendation mapping.

AI có thể là optional feature sau này để giải thích finding bằng ngôn ngữ dễ hiểu, nhưng không được quyết định cache nào nên xóa.

### Deterministic fallback

Toàn bộ sản phẩm MVP chính là deterministic implementation nên không có AI dependency.

## 14. Các bài toán kỹ thuật đáng học

### 1. Static analysis của GitHub workflow expressions

Cache keys thường chứa:

```text
${{ runner.os }}
${{ hashFiles(...) }}
${{ matrix.* }}
${{ github.ref }}
```

Không thể evaluate đầy đủ chỉ bằng YAML parser.

Skill cải thiện:

- parsing;
- AST/lightweight expression analysis;
- normalization;
- conservative inference.

### 2. Cache-family clustering

Tool phải nhận ra:

```text
nuget-Linux-AAA
nuget-Linux-BBB
nuget-Linux-CCC
```

thuộc cùng một logical family.

Skill:

- deterministic normalization;
- grouping heuristics;
- false-positive control.

### 3. API rate limiting

Organization có nhiều repositories dễ tạo nhiều request.

Skill:

- pagination;
- ETag/conditional requests;
- retry/backoff;
- rate-limit budgeting.

### 4. Evidence-based recommendations

Không nên nói “xóa cache này” chỉ vì cache cũ.

Finding cần evidence:

- size;
- age;
- count;
- key pattern;
- workflow source location.

Skill:

- rule-engine design;
- explainability;
- safe automation.

### 5. Longitudinal CI analysis

So sánh scan theo thời gian giúp phân biệt temporary spike với persistent waste.

Skill:

- time-series thinking;
- baseline;
- trend analysis;
- optimization measurement.

## 15. Rủi ro và cách xử lý

### API metadata không đủ để tính hit rate chính xác

**Risk:** tool suy diễn sai cache efficiency.

**Mitigation:** MVP không gọi metric là “hit rate” nếu không có dữ liệu trực tiếp. Dùng wording như `reuse likelihood`, `churn indicator`, `cache family size` và luôn hiển thị evidence.

### Recommendation làm build chậm hơn

**Risk:** user thay key theo đề xuất nhưng cache reuse tệ hơn.

**Mitigation:** recommendation chỉ là suggestion; yêu cầu đo trước/sau. Không auto-edit workflow MVP.

### Delete nhầm cache

**Risk:** cleanup automation gây cache miss hàng loạt.

**Mitigation:** read-only MVP. Auto-delete để Later và luôn có dry-run.

### GitHub API dependency

**Risk:** API schema/permissions thay đổi.

**Mitigation:** adapter boundary + local `gh` import fallback.

### Workflow expression complexity

**Risk:** parser hiểu sai dynamic key.

**Mitigation:** `Unknown/Partially analyzed` tốt hơn đoán.

### Scope expansion

**Risk:** trở thành full CI observability platform.

**Mitigation:** chỉ tập trung cache lifecycle và key design trong 3 phase đầu.

### User adoption

**Risk:** cache vấn đề không đủ đau với repo nhỏ.

**Mitigation:** dogfood trên nhiều repo cá nhân và target developer có matrix/monorepo/multi-language CI.

### 5 test scenario quan trọng nhất

1. 50 cache keys cùng logical prefix được group đúng thành một family.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, tạo vertical slice đầu tiên:

**GitHub cache API response fixture → parse cache entries → group theo key prefix → in report terminal.**

Không làm web UI, database hoặc GitHub OAuth trong session đầu.

### Files/components cần tạo

```text
CachePulse.sln
src/
  CachePulse.Cli/
    Program.cs
    Models/ActionCacheEntry.cs
    Analysis/CacheFamilyAnalyzer.cs
    Reporting/ConsoleReporter.cs
    samples/caches.json
tests/
  CachePulse.Tests/
    CacheFamilyAnalyzerTests.cs
```

### Commands

```bash
dotnet new sln -n CachePulse

dotnet new console \
  -n CachePulse.Cli \
  -o src/CachePulse.Cli

dotnet new xunit \
  -n CachePulse.Tests \
  -o tests/CachePulse.Tests

dotnet sln add src/CachePulse.Cli
dotnet sln add tests/CachePulse.Tests

dotnet add tests/CachePulse.Tests reference src/CachePulse.Cli
```

### Sample fixture

Tạo `samples/caches.json` với khoảng 8 entries mô phỏng:

```json
[
  {
    "key": "nuget-Linux-a1",
    "sizeInBytes": 120000000
  },
  {
    "key": "nuget-Linux-b2",
    "sizeInBytes": 125000000
  },
  {
    "key": "nuget-Linux-c3",
    "sizeInBytes": 118000000
  },
  {
    "key": "playwright-Linux-v1",
    "sizeInBytes": 650000000
  }
]
```

Không cần fixture giống GitHub API 100%; mục tiêu session đầu là validate analyzer.

### First vertical slice

Implement:

```csharp
CacheFamilyAnalyzer.Analyze(entries)
```

Output model:

```csharp
public sealed record CacheFamilySummary(
    string Family,
    int EntryCount,
    long TotalSizeBytes);
```

Simple normalization ban đầu:

```text
nuget-Linux-a1
nuget-Linux-b2
nuget-Linux-c3
```

→ family:

```text
nuget-Linux-*
```

Chưa cố generalize mọi cache key.

### Expected result

Chạy:

```bash
dotnet run --project src/CachePulse.Cli
```

Terminal hiển thị:

```text
CachePulse report

Family                Entries    Size
nuget-Linux-*          3          346 MB
playwright-Linux-*     1          650 MB

Finding:
nuget-Linux-* has multiple variants.
```

### Verification checklist

- [ ] JSON fixture parse thành model.
- [ ] Các key NuGet được group đúng.
- [ ] Total bytes được tính đúng.
- [ ] Report sort theo total size giảm dần.
- [ ] Có unit test cho grouping.
- [ ] Input rỗng không crash.
- [ ] Một key malformed không làm fail toàn bộ report.

### Stop condition

Kết thúc session khi command:

```bash
dotnet run --project src/CachePulse.Cli
```

đọc fixture và in ra ít nhất **2 cache families + entry count + total size + 1 finding** với test chạy pass:

```bash
dotnet test
```

Không làm GitHub authentication, database, scheduler, dashboard hoặc AI trước khi vertical slice này hoạt động.
