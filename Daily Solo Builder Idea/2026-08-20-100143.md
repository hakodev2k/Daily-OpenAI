# Ý tưởng hôm nay: InboxRule Guard — Microsoft 365 Inbox Rule Security Auditor

## 1. Tóm tắt ý tưởng

InboxRule Guard là một công cụ self-hosted giúp người dùng Microsoft 365 **kiểm kê, đánh giá rủi ro và theo dõi thay đổi của Outlook Inbox rules**, đặc biệt các rule có hành vi forward/redirect ra ngoài, xóa email, đánh dấu đã đọc hoặc chuyển thư vào folder ít được chú ý. Công cụ nhắm tới developer hoặc admin kỹ thuật muốn phát hiện sớm rule bất thường mà không cần triển khai một SIEM lớn.

- Người dùng chính: developer/admin kỹ thuật quản lý một hoặc vài Microsoft 365 mailbox.
- Bài toán chính: Inbox rule có thể bị cấu hình sai hoặc bị kẻ tấn công lợi dụng để ẩn/forward thư, nhưng việc kiểm tra thủ công thường không diễn ra đều đặn.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Inbox rules là một tính năng bình thường của Outlook: người dùng có thể tự động move, delete, forward, redirect hoặc xử lý email theo điều kiện. Vấn đề là cùng một cơ chế này cũng có thể tạo ra hành vi nguy hiểm nếu account bị compromise hoặc user vô tình cấu hình sai.

### Confirmed facts

Microsoft Defender hiện có playbook riêng cho **suspicious inbox manipulation rules**. Tài liệu mô tả attacker có thể tạo rule để:

- xóa email;
- chuyển email sang folder ít được chú ý;
- đánh dấu email đã đọc;
- forward email ra địa chỉ bên ngoài;
- lọc các email có keyword cụ thể để che giấu hoạt động.

Nguồn: Microsoft Defender XDR — Alert classification for suspicious inbox manipulation rules  
https://learn.microsoft.com/en-us/defender-xdr/alert-grading-playbook-inbox-manipulation-rules

Microsoft cũng coi automatic external forwarding là một security risk vì có thể làm rò rỉ dữ liệu ra ngoài tổ chức. Microsoft 365 có các outbound spam policy để kiểm soát automatic forwarding.

Nguồn: Microsoft Defender for Office 365 — Configuring and controlling external email forwarding  
https://learn.microsoft.com/en-us/defender-office-365/outbound-spam-policies-external-email-forwarding

Microsoft Graph v1.0 có API để lấy toàn bộ Inbox `messageRule` của user:

```http
GET /me/mailFolders/inbox/messageRules
```

Least-privileged delegated permission cho thao tác đọc là `MailboxSettings.Read`.

Nguồn: Microsoft Graph — List rules  
https://learn.microsoft.com/en-us/graph/api/mailfolder-list-messagerules?view=graph-rest-1.0

### Observation

Microsoft 365 đã có nhiều lớp security control dành cho tổ chức, nhưng với developer, homelab, tenant nhỏ hoặc người muốn kiểm tra mailbox của chính mình, vẫn có khoảng trống cho một tool nhẹ tập trung riêng vào:

**snapshot rule → classify risk → detect change → notify → explain exactly why the rule is suspicious.**

### Assumption cần kiểm chứng

Người dùng kỹ thuật sẽ thấy tool này hữu ích nếu nó giảm thao tác kiểm tra thủ công và phát hiện rule mới trong vài phút/giờ thay vì chỉ khi incident đã xảy ra.

### Workaround hiện tại

Người dùng thường:

- mở Outlook Rules UI và kiểm tra thủ công;
- dùng PowerShell/Exchange tooling;
- xem security alerts nếu tenant có Defender capability phù hợp;
- chỉ phát hiện rule lạ sau khi email đã bị mất/forward.

Nhược điểm của các cách này là fragmented và không tạo baseline lịch sử dễ hiểu cho một mailbox cụ thể.

## 3. Người dùng mục tiêu

### Primary user

Một developer hoặc technical admin đang quản lý Microsoft 365 mailbox của chính mình hoặc một tenant nhỏ.

### Context sử dụng

- Có account Microsoft 365 dùng hàng ngày.
- Có nhiều Inbox rules phục vụ lọc notification, CI/CD, billing, monitoring hoặc project mail.
- Muốn biết khi rule mới xuất hiện hoặc rule cũ thay đổi.

### Main pain point

Không có thói quen kiểm tra Inbox rules thường xuyên và khó nhớ trạng thái “bình thường” trước đây.

### Current workaround

Thỉnh thoảng mở Outlook để xem rules hoặc chạy PowerShell command thủ công.

### Vì sao họ sẽ thử giải pháp

Một dashboard nhỏ cho biết ngay:

- rule nào mới;
- rule nào vừa thay đổi;
- rule nào forward ra external address;
- rule nào delete/move/mark-read email;
- rule nào đáng kiểm tra ngay.

MVP không cố phục vụ toàn bộ enterprise SOC.

## 4. Giải pháp đề xuất

Người dùng đăng nhập bằng Microsoft identity và cấp quyền đọc Inbox rules. InboxRule Guard định kỳ gọi Microsoft Graph để lấy rule, chuẩn hóa chúng thành snapshot và đánh giá theo bộ rule deterministic.

### Main workflow

1. User đăng nhập Microsoft 365.
2. Tool gọi Microsoft Graph để lấy Inbox rules.
3. Chuẩn hóa rule về cấu trúc nội bộ.
4. Tính fingerprint cho từng rule.
5. So sánh với snapshot gần nhất.
6. Phân loại hành vi đáng chú ý.
7. Lưu change event.
8. Hiển thị dashboard và gửi notification nếu đạt threshold.

### Input

- Microsoft account authentication.
- Inbox `messageRule` metadata từ Microsoft Graph.
- User-defined allowlist, ví dụ domain hoặc rule name tin cậy.

### Processing

Mỗi rule được đánh điểm dựa trên các tín hiệu như:

- forward/redirect tới recipient ngoài domain;
- delete message;
- move vào folder bất thường;
- mark as read;
- stop processing more rules;
- rule mới xuất hiện;
- destination thay đổi;
- rule bị enable sau một thời gian disable;
- rule chứa condition hẹp vào billing/security/admin keywords.

Không cần AI để quyết định core risk score.

### Output

Ví dụ:

```text
HIGH RISK
Rule: Invoice Backup
Change: Newly created
Action: Redirects message to external recipient
Other actions: Mark as read
Detected: 2026-08-20 10:00 UTC+7
Reason: External redirect + mark-as-read combination
```

### Phần tự động

- Poll Graph.
- Snapshot rules.
- Diff rules.
- Risk scoring.
- Notification.

### Phần user kiểm soát

- Acknowledge finding.
- Allowlist trusted rule.
- Tự quyết định disable/delete rule.
- Cấu hình polling interval và retention.

MVP **không tự xóa rule** để tránh tool trở thành nguồn gây outage.

### Key differentiator

Không chỉ liệt kê rule hiện tại. Tool xây dựng **history + diff + deterministic security explanation** để user biết chính xác điều gì vừa thay đổi.

### Ví dụ end-to-end

Hôm qua mailbox có 8 rules hợp lệ. Hôm nay có rule thứ 9:

- condition: subject contains “invoice”;
- action: redirect to external recipient;
- action: mark as read.

Tool phát hiện fingerprint mới, chấm risk cao, hiển thị diff và gửi Telegram/email notification. User mở Outlook, xác nhận rule không hợp lệ và xóa nó.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Tool có thể bảo vệ chính mailbox cá nhân hoặc work tenant nhỏ ngay cả khi chỉ có một người dùng.

### Technical learning value

Dự án giúp luyện:

- OAuth/OIDC với Microsoft identity;
- Microsoft Graph permissions;
- periodic synchronization;
- change detection;
- secure token storage;
- deterministic rule engine;
- notification reliability;
- security UX.

### Phù hợp solo developer

Domain hẹp: một loại resource (`messageRule`), một integration chính (Microsoft Graph), một scheduler và dashboard đơn giản.

### Vẫn hữu ích nếu không có user khác

Nó có thể chạy như personal security utility cho mailbox của chính developer.

### Điều gì khiến idea fail

- User đã có Defender/SIEM workflow tốt và không cần tool riêng.
- Permission/login setup tạo quá nhiều friction.
- Risk rules tạo nhiều false positive.

### Lý do mạnh nhất để không build

Nếu mục tiêu là enterprise SOC với hàng nghìn mailbox, Microsoft security products và Exchange tooling sẽ phù hợp hơn một solo project tự host.

## 7. Luồng hoạt động

### Normal flow

User sign-in  
→ OAuth validation  
→ Graph token acquisition  
→ GET Inbox messageRules  
→ normalize  
→ fingerprint  
→ compare previous snapshot  
→ persist snapshot/change events  
→ calculate risk  
→ dashboard  
→ notification nếu threshold đạt.

### No-change flow

Graph sync thành công  
→ fingerprints giống snapshot trước  
→ lưu sync metadata  
→ không tạo notification.

### Rule changed

Rule ID/fingerprint khác  
→ compute field-level diff  
→ create `RuleChange`  
→ recalculate risk  
→ notify nếu cần.

### Graph unavailable

HTTP timeout/5xx  
→ retry có backoff  
→ không ghi snapshot rỗng  
→ giữ snapshot cũ  
→ đánh dấu sync failed.

### Token expired

MSAL refresh flow  
→ nếu refresh thất bại thì mark connection `NeedsReauthentication`  
→ không spam retry vô hạn.

### User removes rule intentionally

Detect removal  
→ lưu change event  
→ risk thấp hoặc informational.

## 11. API và tích hợp

### Microsoft Graph — Inbox message rules

**Purpose:** lấy rule hiện tại.

Endpoint:

```http
GET /me/mailFolders/inbox/messageRules
```

**Authentication:** OAuth 2.0.

**Least privileged delegated permission:** `MailboxSettings.Read`.

**Cost/rate limit:** Graph có throttling; tool phải tôn trọng `429` và `Retry-After` thay vì poll quá nhanh.

**Privacy:** rule có thể chứa email address hoặc keyword nội bộ. Chỉ lưu field cần thiết và hỗ trợ redaction.

**Fallback:** nếu Graph unavailable, giữ snapshot cũ và retry sau; tuyệt đối không coi response lỗi là “zero rules”.

Nguồn:  
https://learn.microsoft.com/en-us/graph/api/mailfolder-list-messagerules?view=graph-rest-1.0

### Microsoft identity platform

**Purpose:** sign-in và delegated access.

**Authentication:** Authorization Code Flow/OIDC.

**Privacy:** refresh token cần bảo vệ như credential.

**Fallback:** require reauthentication khi token không thể refresh.

### Telegram Bot API — optional

**Purpose:** notification nhanh.

**Authentication:** bot token.

**Cost/rate limit:** đủ nhẹ cho personal utility.

**Privacy:** không gửi full rule payload; chỉ gửi rule name + severity + reason.

**Fallback:** dashboard-only hoặc SMTP.

### Microsoft Defender documentation

Không phải runtime integration, nhưng dùng làm basis cho risk rule design.

Nguồn:  
https://learn.microsoft.com/en-us/defender-xdr/alert-grading-playbook-inbox-manipulation-rules

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem cần deterministic behavior hơn AI:

- rule changed hay chưa;
- destination có external hay không;
- action có delete/redirect/mark-read hay không;
- severity threshold.

Những thứ này nên dùng code và policy rõ ràng.

AI có thể là optional future feature để giải thích finding bằng ngôn ngữ tự nhiên, nhưng không nên tham gia quyết định security severity trong MVP.

Lợi ích của việc không dùng AI:

- zero inference cost;
- latency thấp;
- privacy tốt hơn;
- dễ audit;
- không hallucinate security action.

## 14. Các bài toán kỹ thuật đáng học

### 1. Secure OAuth token handling

Học cách phân biệt access token, refresh token, delegated permission và reauthentication. Đây là kỹ năng quan trọng khi tích hợp Microsoft Graph production-grade.

### 2. Snapshot + deterministic diff

Một rule có thể đổi sequence, recipient hoặc action. Cần normalize JSON để fingerprint ổn định, tránh báo thay đổi giả chỉ vì property order.

Kỹ năng cải thiện: canonicalization, hashing, change-data modeling.

### 3. Rate limiting và retry

Graph có throttling. Tool cần xử lý `429`, `Retry-After`, transient errors và không tạo retry storm.

Kỹ năng cải thiện: resilient API integration.

### 4. Security rule engine

Cần biến các tín hiệu thành explainable score, ví dụ:

```text
External redirect          +50
Mark as read               +20
Delete message             +30
New rule                   +20
Trusted domain             -30
```

Kỹ năng cải thiện: policy design, explainability, false-positive management.

### 5. Privacy-preserving storage

Không phải field nào cũng cần lưu raw. Có thể hash external recipients hoặc redact keyword condition tùy mode.

Kỹ năng cải thiện: data minimization và privacy-aware architecture.

## 15. Rủi ro và cách xử lý

### Permission friction

**Risk:** OAuth/Entra app registration làm user ngại setup.

**Mitigation:** MVP single-user với setup guide rõ ràng; chỉ yêu cầu delegated `MailboxSettings.Read`.

### False positives

**Risk:** nhiều rule legitimate cũng forward/move email.

**Mitigation:** risk score + allowlist + baseline; rule cũ không thay đổi không cần spam alert.

### Sensitive rule metadata

**Risk:** conditions/actions có email addresses hoặc internal keywords.

**Mitigation:** encryption at rest, optional hashing, configurable retention, no raw payload in notification.

### Graph dependency

**Risk:** throttling hoặc outage.

**Mitigation:** retry/backoff, stale snapshot marker, không overwrite snapshot bằng empty/error response.

### Scope creep

**Risk:** biến thành full Microsoft 365 security platform.

**Mitigation:** giữ MVP chỉ Inbox rules của một mailbox.

### Automated remediation

**Risk:** auto-disable/delete rule legitimate gây mất email flow.

**Mitigation:** MVP read-only; remediation chỉ là future feature với explicit confirmation.

### User adoption

**Risk:** personal users không muốn self-host một service cho một mailbox.

**Mitigation:** CLI/desktop mode có thể là extension sau MVP; trước tiên validate trên chính mailbox developer.

Số lần dashboard/finding được mở sau một real rule change.

### Time saved

Thời gian cần để trả lời câu hỏi:

> “Inbox rules hiện tại có gì khác tuần trước?”

Mục tiêu: từ kiểm tra thủ công vài phút xuống vài giây.

### Task completion rate

% sync run tạo được snapshot hợp lệ khi Graph available.

### Error rate

% sync thất bại do auth/throttle/network.

### Repeated use

Tool vẫn được giữ chạy sau 30 ngày và có ít nhất một change event hữu ích.

### Technical reliability

- >99% successful scheduled sync khi Graph hoạt động bình thường.
- zero snapshot loss do transient errors.

### Security quality

Quan trọng hơn số alert là:

- bao nhiêu finding cần action thật;
- bao nhiêu finding là false positive;
- có bỏ sót external forwarding rule trong test corpus hay không.

Không cần vanity metric như page views.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, hoàn thành vertical slice đầu tiên:

**Microsoft sign-in → gọi Graph → lấy Inbox rules → in normalized security summary ra console/API.**

Chưa cần database hoặc dashboard.

### Files/components cần tạo

```text
InboxRuleGuard.sln
src/
  InboxRuleGuard.Api/
    Program.cs
    Graph/
      GraphRuleClient.cs
    Models/
      InboxRuleDto.cs
      RuleSecuritySummary.cs
    Security/
      RuleClassifier.cs
tests/
  InboxRuleGuard.Tests/
    RuleClassifierTests.cs
```

### Setup commands

```bash
dotnet new sln -n InboxRuleGuard
dotnet new webapi -n InboxRuleGuard.Api -o src/InboxRuleGuard.Api
dotnet new xunit -n InboxRuleGuard.Tests -o tests/InboxRuleGuard.Tests
dotnet sln add src/InboxRuleGuard.Api
dotnet sln add tests/InboxRuleGuard.Tests
dotnet add tests/InboxRuleGuard.Tests reference src/InboxRuleGuard.Api
```

Thêm authentication package phù hợp với Microsoft identity/Graph SDK theo implementation đã chọn.

### Entra setup

Tạo test app registration và cấu hình delegated permission:

```text
MailboxSettings.Read
```

Không xin `Mail.Read` nếu MVP chỉ cần Inbox rule metadata.

### First vertical slice

Tạo endpoint:

```http
GET /api/rules/scan
```

Flow:

```text
Authenticated user
→ acquire Graph token
→ GET /me/mailFolders/inbox/messageRules
→ map rules
→ classify actions
→ return JSON summary
```

Example output:

```json
[
  {
    "name": "Build notifications",
    "enabled": true,
    "risk": "Low",
    "signals": ["MoveToFolder"]
  },
  {
    "name": "External copy",
    "enabled": true,
    "risk": "High",
    "signals": ["ExternalRedirect", "MarkAsRead"]
  }
]
```

### First classifier rules

Chỉ implement 4–5 tín hiệu đầu tiên:

```text
Redirect/forward action
Delete action
Mark-as-read action
Move action
Enabled/disabled state
```

Nếu recipient domain khác domain chính của user, thêm `ExternalDestination`.

### Expected result

Gọi endpoint sau khi sign-in và nhìn thấy danh sách real Inbox rules của mailbox test kèm classification đơn giản.

### Verification checklist

- [ ] Sign-in Microsoft thành công.
- [ ] App chỉ yêu cầu permission cần thiết cho rule reading.
- [ ] Graph trả real message rules.
- [ ] Rule mapping không làm mất action data quan trọng.
- [ ] Có ít nhất 3 unit tests cho classifier.
- [ ] Không log access token.
- [ ] Tạo một rule test trong Outlook và thấy nó trong kết quả scan.

### Stop condition

Kết thúc coding session ngay khi:

1. user đăng nhập được;
2. `/api/rules/scan` trả real Inbox rules;
3. ít nhất một rule được phân loại thành security signal;
4. unit test classifier pass.

Không thêm PostgreSQL, scheduler, Telegram, AI hoặc multi-tenant support trong session đầu tiên.
