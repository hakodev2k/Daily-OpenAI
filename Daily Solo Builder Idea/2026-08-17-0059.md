# Ý tưởng hôm nay: Webhook Replay Lab — Hộp đen ghi, kiểm tra và phát lại webhook

## 1. Tóm tắt ý tưởng

**Webhook Replay Lab** là một developer tool self-hosted nhận webhook từ GitHub, Stripe hoặc bất kỳ hệ thống HTTP nào, lưu lại request một cách an toàn, cho phép inspect headers/body/signature metadata và **replay chính xác hoặc có chỉnh sửa** vào localhost, staging hay một endpoint test. Nó giúp developer debug các lỗi webhook khó tái hiện, kiểm tra idempotency và failure handling mà không phải chờ sự kiện thật xảy ra lần nữa.

- **Project size:** Medium
- **Estimated MVP time:** 2–3 tuần làm ngoài giờ
- **Primary user:** backend developer xây integration dựa trên webhook
- **Vấn đề chính:** webhook là event-driven, payload thật thường khó tái tạo, retry behavior khác nhau giữa provider và lỗi production có thể biến mất trước khi developer kịp điều tra.

## 2. Bài toán thực tế

### Confirmed facts

GitHub mô tả webhook là cơ chế gửi HTTP request tới server khi một event xảy ra thay vì phải polling API. GitHub cũng khuyến nghị webhook receiver trả `2XX` trong vòng **10 giây**; nếu server phản hồi chậm hơn, delivery bị coi là failure. GitHub hiện không tự động redeliver failed deliveries. citeturn1search5turn1search2turn1search4

GitHub cho phép redeliver webhook deliveries trong **3 ngày gần nhất**, qua UI hoặc REST API, và tài liệu chính thức thậm chí cung cấp hướng dẫn viết scheduled script để tìm failed deliveries rồi redeliver chúng. citeturn1search0turn1search8

REST API của GitHub cho phép đọc delivery metadata/payload và yêu cầu redelivery; quyền ghi webhook là cần thiết cho redelivery. citeturn1search3turn1search9

### Observation

Các capability trên xác nhận hai nhu cầu thực tế: developer cần **quan sát payload đã giao** và cần **phát lại event** để test/recover. Tuy nhiên provider-specific redelivery chỉ giải quyết event của provider đó và thường phát lại vào URL webhook đã cấu hình, trong khi debugging thường cần replay cùng payload vào localhost/staging, thay header, mô phỏng timeout, hoặc chạy cùng event nhiều lần để kiểm tra idempotency.

### Analysis

Một tool nhỏ tập trung vào “capture once, replay anywhere” có thể hữu ích hơn một generic API client khi debug webhook vì nó giữ nguyên context của request gốc: method, content type, headers, timestamp, payload, delivery identifier và response từ receiver.

### Assumption cần validation

Giả định cần kiểm chứng: developer làm integration ít nhất vài lần mỗi tháng sẽ muốn lưu event history riêng thay vì chỉ dùng dashboard của từng provider. Validation nên hỏi 5 developer từng tích hợp GitHub/Stripe/payment/CRM webhook và quan sát họ debug một event thất bại như thế nào.

## 3. Người dùng mục tiêu

**Primary user:** backend developer hoặc solo builder tích hợp dịch vụ bên thứ ba bằng webhook.

- **Context:** đang phát triển hoặc vận hành ASP.NET Core API nhận webhook.
- **Pain point:** lỗi chỉ xảy ra với một payload thật, nhưng không dễ tạo lại chính xác event.
- **Current workaround:** copy JSON từ provider dashboard, dùng Postman/cURL, trigger event thật lại, hoặc dùng chức năng redelivery riêng của provider.
- **Reason to try:** một URL capture duy nhất + lịch sử request + nút Replay giúp rút workflow debug thành vài thao tác.

MVP không cố phục vụ enterprise event platform hoặc message broker.

## 4. Giải pháp đề xuất

Mỗi “Inbox” có một endpoint riêng:

```text
POST https://hooks.example.dev/i/7d5f...
```

Khi provider gửi webhook:

1. ASP.NET Core nhận raw request body.
2. Ghi lại method, headers được allowlist, content type, timestamp và body.
3. Tính SHA-256 fingerprint.
4. Trả `202 Accepted` nhanh.
5. UI hiển thị event ngay trong inbox.
6. User mở event, xem request và response metadata.
7. User chọn target `localhost`, `staging` hoặc custom URL.
8. Tool replay request và lưu replay attempt/result.

### Input

- HTTP webhook request.
- Replay target URL.
- Optional header overrides.
- Optional body edit cho test case mới.

### Processing

- body-size validation;
- safe header filtering;
- optional signature verification adapter;
- encrypted storage;
- fingerprinting;
- HTTP forwarding/replay;
- timeout/retry policy;
- response capture.

### Output

- searchable delivery history;
- raw/pretty JSON view;
- replay result: status, latency, response body truncated;
- diff giữa original và edited replay.

### Automated

Capture, persistence, retention cleanup và replay execution.

### User-controlled

Target URL, credentials, payload modification, retry count và retention.

### Key differentiator

Không phải webhook provider hay tunnel service đầy đủ. Sản phẩm tập trung vào **reproducible debugging**: một production event có thể biến thành regression fixture và được replay nhiều lần vào các build khác nhau.

### Ví dụ

Một GitHub webhook `issues.opened` làm API trả `500` do field optional bất ngờ null. Developer mở event trong Webhook Replay Lab, thấy raw payload, sửa code local, chọn target `http://host.docker.internal:5080/webhooks/github`, replay cùng event và thấy `200`. Sau đó bấm “Save as fixture” để event này trở thành regression test data.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Tool giảm thời gian tái hiện bug event-driven và tạo cầu nối trực tiếp từ production incident sang local debugging/regression testing.

### Technical learning value

Dự án có các bài toán thực tế: raw HTTP body capture, HMAC verification, idempotency, SSRF protection, encrypted storage, background delivery, retry/backoff, streaming UI và data retention.

### Suitable for solo developer

Core workflow nhỏ: receive → persist → inspect → replay. Không cần xây message broker hoặc tunneling protocol ở MVP.

### Useful with very few users

Chỉ riêng developer sở hữu tool đã có thể dùng nó cho GitHub Apps, payment sandbox, Telegram bot, CI integrations hoặc personal automations.

### What would make it fail

Nếu user chỉ debug một provider duy nhất và dashboard provider đã đủ tốt, họ không cần thêm tool.

### Strongest reason not to build

Thị trường webhook tooling đã có nhiều sản phẩm. Vì vậy dự án chỉ đáng tiếp tục nếu differentiator “event → reproducible regression fixture” thực sự được user đánh giá cao.

## 6. Phạm vi MVP

### Must have

- Tạo webhook inbox và random secret URL.
- Nhận `POST` request.
- Lưu raw body tối đa configurable size.
- Allowlist headers cần thiết.
- Event list + event detail.
- Pretty-print JSON.
- Manual replay tới một target URL.
- Override selected headers.
- Capture replay status code, latency và response snippet.
- Replay history.
- SHA-256 fingerprint.
- Configurable retention.
- SSRF protection cho replay target.

### Should have

- GitHub signature verification (`X-Hub-Signature-256`).
- Save event as named fixture.
- Search/filter theo header/event type/status.
- Payload editor trước replay.
- Compare two payloads.
- CLI command để replay fixture.

### Later

- Local tunnel agent.
- Stripe/provider adapters.
- Automatic retry simulator.
- Latency/failure injection.
- GitHub App integration để import recent deliveries.
- Test-code generator.
- Team workspaces.
- WebSocket/SSE live event stream.

## 7. Luồng hoạt động

```text
Provider
   ↓ POST
Public Inbox Endpoint
   ↓
Validate size + content type
   ↓
Read raw body once
   ↓
Filter sensitive headers
   ↓
Persist Delivery
   ↓
202 Accepted
   ↓
Developer opens UI
   ↓
Selects Replay Target
   ↓
Validate target / SSRF policy
   ↓
Background HTTP replay
   ↓
Capture response + latency
   ↓
Display result / save fixture
```

### Failure cases

**Payload quá lớn:** trả `413 Payload Too Large`, chỉ lưu metadata nếu policy cho phép.

**Database unavailable:** không trả success giả; trả `503` để provider biết delivery chưa được ghi nhận.

**Replay target timeout:** attempt = `TimedOut`; không tự retry vô hạn.

**Private IP target:** cloud mode block mặc định để chống SSRF; self-hosted mode cho phép explicit allowlist.

**Duplicate event:** vẫn có thể lưu delivery nhưng đánh dấu fingerprint duplicate; không tự suy luận rằng duplicate là lỗi.

**Invalid JSON:** lưu raw payload bình thường vì webhook không bắt buộc phải là JSON.

Admin UI cần local account hoặc reverse-proxy authentication. Public inbox endpoint xác định bằng unguessable token.

Không cần.

### Notification

Không cần cho core workflow; có thể thêm Telegram sau.

## 9. Công nghệ đề xuất

### .NET 10 + ASP.NET Core

Phù hợp cho raw HTTP handling, typed `HttpClient`, background jobs và self-hosting.

**Simpler alternative:** một ASP.NET Core project duy nhất với SQLite.

**Outgrow point:** nếu ingestion volume lên hàng nghìn request/giây mới cần tách capture path và durable queue.

### EF Core + PostgreSQL

Phù hợp metadata query, retention và JSON fields.

**Simpler alternative:** SQLite cho local-only MVP.

### Hangfire

Dùng cho replay và cleanup, tránh giữ request HTTP của UI trong suốt outbound delivery.

**Simpler alternative:** `BackgroundService` + `Channel<T>` nhưng mất durability khi restart.

### Vue 3

Request inspector cần UI tương tác; Vue đủ nhẹ và nhanh để build.

### Docker Compose

Giúp self-hosting đơn giản và giữ dữ liệu trong hạ tầng của user.

### Playwright

E2E capture → inspect → replay rất phù hợp để tự động hóa bằng Playwright.

## 11. API và tích hợp

### Generic HTTP webhook

**Purpose:** nhận event từ bất kỳ provider nào.

**Authentication:** URL token + provider signature nếu có.

**Cost/rate limit:** do chính host kiểm soát; cần body-size/rate limit.

**Privacy:** payload có thể chứa PII hoặc secrets.

**Fallback:** user có thể import fixture thủ công.

### GitHub webhook

GitHub cung cấp webhook delivery, signature và redelivery workflow; receiver phải xử lý delivery nhanh, và GitHub không tự động redeliver failed webhook. citeturn1search2turn1search4

**Authentication:** HMAC secret cho verification; GitHub API token chỉ cần nếu sau này import/redeliver qua API.

**Permission concern:** redelivery API cần webhook write permission. citeturn1search9

**Fallback:** core tool vẫn hoạt động hoàn toàn từ inbound webhook mà không cần GitHub API.

### Localhost replay

MVP self-hosted trên máy developer có thể gọi localhost trực tiếp. Nếu server nằm trên VPS, user phải cung cấp reachable target; **không xây tunnel trong MVP**.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Webhook capture, signature verification, replay và diff đều deterministic. Dùng LLM để “phân tích lỗi” ở MVP sẽ tăng chi phí và nguy cơ gửi payload nhạy cảm ra ngoài mà chưa tạo giá trị cốt lõi.

Nếu sau này thêm AI, nó chỉ nên là opt-in assistant đọc **redacted** payload + response để đề xuất hypotheses; kết quả không được quyết định retry hoặc thay đổi event tự động.

## 13. Kế hoạch triển khai

**Expected output:** top 3 debugging workflows.

**Completion criteria:** ít nhất 2 người muốn replay event thật vào local/staging hoặc lưu regression fixture.

**Goal:** capture và replay một generic webhook.

**Tasks:** Inbox endpoint, PostgreSQL persistence, event UI, replay target, `HttpClient` sender.

**Expected output:** cURL → inbox → UI → replay → test receiver.

**Completion criteria:** cùng payload được replay byte-for-byte và response được lưu.

### Phase 2 — Reliability

**Goal:** xử lý dữ liệu và failure an toàn.

**Tasks:** Hangfire, timeout, body limit, rate limit, SSRF guard, secret encryption, retention, structured logging.

**Expected output:** tool chịu được restart và target failure.

**Completion criteria:** failure-path integration tests pass; không duplicate replay do job retry ngoài policy.

### Phase 3 — Useful expansion

**Goal:** biến debugger thành regression workflow.

**Tasks:** named fixtures, payload edit, header override, GitHub signature verification, CLI replay.

**Expected output:** event production có thể lưu và chạy lại như fixture.

**Completion criteria:** developer có thể reproduce một bug từ saved fixture mà không cần provider gửi event lại.

### Phase 4 — Production readiness

**Goal:** self-host dễ và an toàn.

**Tasks:** Docker Compose, backup, health checks, HTTPS guidance, audit logs, README, GitHub Actions, Playwright E2E.

**Expected output:** deployment repeatable.

**Completion criteria:** restore DB trên host mới và replay fixture thành công.

## 14. Các bài toán kỹ thuật đáng học

### 1. Raw HTTP fidelity

Phải lưu body bytes trước khi deserialize để replay chính xác và verify HMAC đúng.

**Skill:** ASP.NET Core request pipeline, buffering, streaming.

### 2. Idempotency và duplicate delivery

Webhook có thể được gửi/replay nhiều lần; receiver downstream phải chịu duplicate.

**Skill:** idempotency keys, fingerprints, delivery semantics.

### 3. SSRF-safe replay

Một endpoint cho phép user nhập URL outbound là bề mặt SSRF rõ ràng.

**Skill:** DNS/IP validation, network policy, redirect handling, allowlist.

### 4. Secret/PII-safe storage

Payload và headers có thể chứa dữ liệu nhạy cảm.

**Skill:** encryption-at-rest, redaction, retention, least privilege.

### 5. Reliable background delivery

Timeout/retry phải có giới hạn và không biến một thao tác replay thành storm.

**Skill:** Hangfire, backoff, cancellation, auditability.

## 15. Rủi ro và cách xử lý

### Data privacy

**Risk:** webhook chứa customer data/token.

**Mitigation:** self-host first, encrypt payload, header allowlist, configurable retention, manual purge, không gửi AI bên ngoài.

### Security

**Risk:** SSRF qua replay URL.

**Mitigation:** cloud mode block loopback/link-local/private CIDR; resolve DNS rồi validate IP; không follow redirect mặc định; explicit target allowlist.

### Scope expansion

**Risk:** cố trở thành ngrok + Hookdeck + message broker.

**Mitigation:** MVP chỉ capture/inspect/replay/fixture.

### Cost

**Risk:** payload history làm DB tăng nhanh.

**Mitigation:** size limit, compression, retention cleanup, quota per inbox.

### Provider differences

**Risk:** signature/retry semantics khác nhau.

**Mitigation:** generic core; provider adapters là plugin optional.

### User adoption

**Risk:** Postman/cURL đã đủ.

**Mitigation:** validate “production event → reusable fixture” trước khi build advanced UI.

### Maintenance

**Risk:** public receiver bị spam.

**Mitigation:** unguessable token, rate limiting, optional IP/provider signature restrictions.

## 16. Kiểm thử

### Strategy

- **Unit:** fingerprint, header redaction, target validation, retention rules.
- **Integration:** real PostgreSQL + in-process test receiver.
- **E2E:** Playwright cho event list/detail/replay.
- **Failure-path:** timeout, DNS failure, `500`, oversized payload, DB unavailable.
- **Security:** SSRF, redirect-to-private-IP, malicious headers, XSS trong JSON/string payload.
- **Data quality:** replayed body bytes/hash phải khớp original khi không edit.

### 5 test scenario quan trọng

1. POST JSON được capture và raw SHA-256 khớp input.
2. Replay không chỉnh sửa gửi body byte-for-byte giống original.
3. Target `http://169.254.169.254` bị block.
4. Target timeout tạo `TimedOut` attempt nhưng không mất original delivery.
5. Payload chứa `<script>` hiển thị như text, không execute trong inspector.

## 17. Cách đo dự án có hữu ích hay không

- **Usage:** số event được replay mỗi tuần, không phải tổng event ingest.
- **Time saved:** thời gian từ bug report đến reproducible request.
- **Task completion:** % replay attempt có kết quả xác định (`2xx/4xx/5xx/timeout`) thay vì internal error.
- **Error rate:** internal capture/replay failures <1% với target reachable.
- **Repeated use:** ít nhất một inbox được dùng lại trong 4 tuần liên tiếp.
- **Reliability:** không mất acknowledged delivery sau restart; cleanup đúng retention.
- **Core validation metric:** số saved fixture thực sự được replay lại sau ngày tạo.

Không dùng page views hay số account đăng ký làm success metric chính.

```bash
curl -X POST http://localhost:5000/inbox/demo \

  -H "X-Test-Event: issue.created" \
  -d '{"id":123,"title":"Webhook bug"}'
```

Tạo một second local endpoint `/test-receiver` ghi body nhận được. Replay delivery vào endpoint đó.

### Implementation constraint quan trọng

Đọc raw body thành `byte[]`; không deserialize rồi serialize lại trước khi replay. Mục tiêu của session đầu là chứng minh **fidelity**.

### Expected result

Sau một `curl`, `GET /deliveries` thấy event. Gọi replay và `/test-receiver` nhận body có SHA-256 giống request gốc.

### Verification checklist

- [ ] `dotnet build` pass.
- [ ] Capture endpoint trả `202`.
- [ ] Raw body được lưu nguyên bytes.
- [ ] Content-Type được giữ lại.
- [ ] Replay target nhận body giống original.
- [ ] SHA-256 trước/sau replay giống nhau.
- [ ] Target timeout được cancel bằng `CancellationToken`.
- [ ] Có ít nhất một integration test capture → replay.

### Stop condition

Dừng session khi một request gửi bằng `curl` có thể được capture và replay sang local test receiver với **body hash giống hệt**. Không thêm database, UI, signature verification hoặc provider integration trong session đầu.
