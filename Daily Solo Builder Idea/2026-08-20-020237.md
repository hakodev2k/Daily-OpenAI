# Ý tưởng hôm nay: BatteryLedger — Cross-Device Battery Health Historian

## 1. Tóm tắt ý tưởng

BatteryLedger là một công cụ local-first/self-hosted giúp theo dõi **sức khỏe pin theo thời gian trên nhiều laptop Windows/Linux**, thay vì chỉ xem một battery report tại một thời điểm. Một collector nhỏ chạy định kỳ trên mỗi máy, chuẩn hóa các chỉ số như design capacity, full-charge capacity, remaining capacity, charge rate và trạng thái pin, sau đó lưu snapshot vào dashboard để người dùng thấy tốc độ chai pin, phát hiện thay đổi bất thường và quyết định khi nào cần kiểm tra hoặc thay pin.

- Người dùng chính: developer hoặc power user có 1–5 laptop/mini-PC chạy Windows/Linux.
- Bài toán chính: dữ liệu sức khỏe pin có sẵn trong hệ điều hành nhưng lịch sử dài hạn, so sánh nhiều thiết bị và cảnh báo xu hướng thường bị phân tán.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

### Confirmed facts

Windows đã có tooling chính thức cho battery diagnostics. `powercfg /batteryreport` tạo báo cáo về đặc tính sử dụng pin trong vòng đời hệ thống và hỗ trợ xuất HTML/XML. Microsoft cũng cung cấp `Windows.Devices.Power.BatteryReport`, trong đó có các trường như `DesignCapacityInMilliwattHours`, `FullChargeCapacityInMilliwattHours`, `RemainingCapacityInMilliwattHours`, `ChargeRateInMilliwatts` và `Status`.

Nguồn chính thức:

- Microsoft Learn — Powercfg command-line options: https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/powercfg-command-line-options
- Microsoft Learn — BatteryReport class: https://learn.microsoft.com/en-us/uwp/api/windows.devices.power.batteryreport
- Microsoft Learn — Get battery information: https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/get-battery-info

Linux có UPower, một abstraction chính thức trong desktop Linux để enumerate power devices, theo dõi device events và truy vấn history/statistics thông qua D-Bus. CLI `upower` cũng hỗ trợ dump thông tin battery và monitor thay đổi.

Nguồn chính thức:

- UPower project: https://upower.freedesktop.org/
- UPower D-Bus reference: https://upower.freedesktop.org/docs/UPower/
- UPower CLI manual: https://upower.freedesktop.org/docs/upower.1.html

### Observation

Dữ liệu cơ bản để theo dõi battery health đã tồn tại ở OS level. Tuy nhiên workflow thường là chạy `powercfg /batteryreport`, mở HTML, xem một vài con số rồi quên; hoặc trên Linux dùng `upower -i` cho trạng thái hiện tại. Việc quan sát xu hướng qua 3, 6 hoặc 12 tháng và so sánh nhiều máy không phải là luồng mặc định của các công cụ này.

### Assumption cần kiểm chứng

Power user và developer sở hữu nhiều laptop sẽ thấy hữu ích khi có một lịch sử riêng, local-first, không cần cloud account, trả lời được các câu hỏi như:

- Pin máy A mất bao nhiêu % full-charge capacity trong 90 ngày?
- Máy B giảm mạnh sau một giai đoạn nhiệt độ hoặc workload cao hay chỉ do một reading nhiễu?
- Thiết bị nào đang xuống cấp nhanh nhất?
- Sau khi thay pin, health baseline đã quay về mức nào?

### Vấn đề hiện tại

Người dùng thường xử lý bằng:

- mở Windows battery report khi thấy pin tụt nhanh;
- dùng tool OEM riêng của Dell/Lenovo/HP;
- xem `upower` hoặc desktop battery widget trên Linux;
- tự ghi lại capacity vào Excel/Notion;
- chỉ phản ứng khi thời lượng pin đã giảm rõ rệt.

Các cách này không sai, nhưng dữ liệu rời rạc và khó tạo trend dài hạn.

## 3. Người dùng mục tiêu

### Primary user

Developer hoặc power user có từ một đến vài laptop Windows/Linux và muốn theo dõi thiết bị cá nhân lâu dài.

### Context of use

- Laptop làm việc chính dùng hàng ngày.
- Máy cá nhân dùng coding/gaming.
- Laptop cũ chuyển thành home server hoặc lab machine.
- Máy dual-boot hoặc fleet nhỏ trong gia đình.

### Main pain point

Người dùng biết pin đang chai nhưng không biết **chai nhanh đến mức nào** hoặc thay đổi đó có thật sự bất thường so với baseline trước đó.

### Current workaround

Chạy battery report thủ công, mở vendor utility, hoặc chỉ nhìn phần trăm pin còn lại.

### Lý do họ sẽ thử BatteryLedger

Cài một agent nhẹ, để nó lưu snapshot mỗi vài giờ hoặc mỗi ngày, rồi xem chart health theo tuần/tháng mà không cần tự ghi chép.

## 4. Giải pháp đề xuất

### Main workflow

1. Người dùng cài `batteryledger-agent` lên máy.
2. Agent nhận diện OS và battery devices.
3. Collector đọc các chỉ số có sẵn từ OS API/CLI.
4. Dữ liệu được normalize về model chung.
5. Snapshot được lưu local hoặc POST về BatteryLedger server self-hosted.
6. Dashboard hiển thị health trend, capacity trend và recent anomalies.
7. Rule engine có thể cảnh báo khi health giảm quá nhanh trong một khoảng thời gian.

### Input

- Windows `BatteryReport` API hoặc `powercfg /batteryreport /xml`.
- Linux UPower/D-Bus hoặc `upower` CLI.
- Metadata máy: hostname alias, OS, battery manufacturer/model nếu OS expose.

### Processing

- Normalize capacity về mWh/Wh.
- Tính health ratio:

```text
FullChargeCapacity / DesignCapacity * 100
```

- Làm trơn dữ liệu bằng rolling median để tránh phản ứng với một reading bất thường.
- Tính delta theo 7/30/90 ngày.
- Phát hiện reset baseline khi battery identity thay đổi.

### Output

Dashboard ví dụ:

```text
ThinkPad T14
Battery health: 86.4%
30-day change: -1.8 pp
90-day change: -4.6 pp
Latest full-charge capacity: 43.2 Wh
Design capacity: 50.0 Wh
Trend: degrading faster than recent baseline
```

### Tự động hóa

- Capture snapshot.
- Normalize dữ liệu.
- Retention/aggregation.
- Trend calculation.
- Optional anomaly alert.

### User control

- Chọn sampling frequency.
- Chọn local-only hoặc self-hosted sync.
- Chọn alert threshold.
- Đặt alias và tag cho device.
- Xóa toàn bộ lịch sử của một device.

### Key differentiator

Không cố trở thành battery optimizer hay thay đổi power settings. BatteryLedger chỉ làm một việc rõ ràng: **xây dựng lịch sử health đáng tin cậy, lâu dài và cross-device từ dữ liệu OS-native**.

### Ví dụ end-to-end

Một developer có laptop Windows dùng hàng ngày và một laptop Linux cũ.

Sau khi cài agent hai máy:

- Windows collector đọc full-charge/design capacity.
- Linux collector đọc cùng nhóm dữ liệu qua UPower.
- Hai máy gửi snapshot về server Docker chạy trên mini PC.
- Sau 60 ngày, dashboard cho thấy laptop Windows giảm từ 91% xuống 86%, trong khi Linux ổn định quanh 78%.
- Người dùng nhìn trend và biết máy Windows đang xuống nhanh hơn, thay vì chỉ dựa vào cảm giác “pin dạo này yếu”.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Có giá trị ngay với chính developer sở hữu laptop, không cần chờ user khác. Chỉ cần một máy và 30 ngày dữ liệu đã tạo được insight hữu ích.

### Technical learning value

Dự án cho phép học sâu về:

- OS-specific APIs.
- D-Bus trên Linux.
- Background agent/service.
- Time-series data modeling.
- Data normalization.
- Trend/anomaly detection không cần AI.
- Local-first/self-hosted architecture.

### Vì sao phù hợp solo developer

Core domain nhỏ: collect → normalize → persist → chart → alert. Không cần scraping, không cần ML model, không cần large-scale infrastructure.

### Vì sao vẫn hữu ích nếu chỉ có một user

Battery history là dữ liệu cá nhân tích lũy theo thời gian. Một người dùng vẫn nhận giá trị sau vài tuần/tháng.

### Điều gì làm dự án thất bại

- OS/hardware không expose ổn định design/full-charge capacity.
- Dữ liệu quá nhiễu khiến trend không đáng tin.
- User chỉ quan tâm battery health một lần mỗi năm nên không muốn chạy agent.

### Lý do mạnh nhất để không build

Nếu nhu cầu chỉ là kiểm tra battery health tức thời trên một laptop Windows, `powercfg /batteryreport` đã đủ và một sản phẩm riêng là overkill.

## 7. Luồng hoạt động

### Normal flow

Agent timer chạy
→ xác định battery devices
→ đọc raw metrics
→ validate đơn vị/range
→ normalize snapshot
→ tạo deterministic snapshot key
→ lưu local spool
→ gửi tới server
→ server deduplicate
→ lưu PostgreSQL
→ recompute summary
→ dashboard hiển thị trend.

### Offline flow

Agent không kết nối server
→ snapshot vẫn được lưu local spool
→ lần chạy sau retry
→ server nhận dữ liệu cũ theo original timestamp
→ timeline không bị mất.

### Unsupported metric

OS trả `null` hoặc battery controller không report capacity
→ lưu metric availability
→ không tính health ratio từ dữ liệu thiếu
→ UI hiển thị `Not reported` thay vì tự suy đoán.

### Multiple batteries

Máy có nhiều battery
→ mỗi battery có identity riêng
→ server lưu snapshot theo `DeviceId + BatteryId`
→ UI có aggregate view và per-battery view.

### Battery replacement

Battery identity hoặc design capacity thay đổi đáng kể
→ tạo potential replacement event
→ không nối trend cũ vào trend mới một cách mù quáng
→ user xác nhận replacement.

## 10. Thiết kế dữ liệu ban đầu

### Device

**Purpose:** đại diện một máy vật lý.

Fields:

- `Id`
- `Name`
- `OsFamily`
- `OsVersion`
- `AgentVersion`
- `LastSeenAt`
- `CreatedAt`

Relationship: một Device có nhiều Battery.

Retention: giữ tới khi user xóa.

### Battery

**Purpose:** định danh một battery/controller trong device.

Fields:

- `Id`
- `DeviceId`
- `NativeIdentifierHash`
- `Manufacturer`
- `Model`
- `SerialHash`
- `DesignCapacityMwh`
- `FirstSeenAt`
- `LastSeenAt`
- `IsActive`

Không cần lưu serial raw nếu không cần; hash đủ cho replacement detection.

### BatterySnapshot

**Purpose:** một reading tại thời điểm cụ thể.

Fields:

- `Id`
- `BatteryId`
- `CapturedAt`
- `FullChargeCapacityMwh`
- `RemainingCapacityMwh`
- `ChargeRateMw`
- `Status`
- `HealthPercent`
- `Source`
- `QualityFlags`

Relationship: Battery có nhiều Snapshot.

Retention: giữ raw snapshots 12 tháng; có thể downsample sau đó.

### DailyBatteryAggregate

**Purpose:** giảm dữ liệu chart dài hạn.

Fields:

- `BatteryId`
- `Date`
- `MedianHealthPercent`
- `MedianFullChargeCapacityMwh`
- `MinHealthPercent`
- `MaxHealthPercent`
- `SampleCount`

### AlertRule

**Purpose:** rule deterministic.

Fields:

- `BatteryId`
- `WindowDays`
- `DropThresholdPercentagePoints`
- `MinimumSamples`
- `Enabled`

## 11. API và tích hợp

### Windows `powercfg`

**Purpose:** bootstrap/prototype hoặc fallback collector.

**Authentication:** local OS command; không cần external credential.

**Cost/rate limit:** không có API cost.

**Privacy:** report chứa machine/battery usage metadata, vì vậy parser chỉ nên trích fields cần thiết.

**Fallback:** dùng `Windows.Devices.Power.BatteryReport` khi phù hợp.

Nguồn: https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/powercfg-command-line-options

### Windows.Devices.Power

**Purpose:** đọc charge/capacity/status trực tiếp từ Windows API.

**Authentication:** local app access; không cần cloud account.

**Limitation:** Microsoft ghi rõ các property có thể trả `null` khi battery không tồn tại hoặc controller không report giá trị.

**Fallback:** `powercfg /batteryreport` hoặc mark metric unavailable.

Nguồn: https://learn.microsoft.com/en-us/uwp/api/windows.devices.power.batteryreport

### Linux UPower

**Purpose:** enumerate battery device, đọc property và theo dõi change event.

**Authentication:** D-Bus system service local.

**Cost/rate limit:** không có external API cost.

**Privacy:** dữ liệu chỉ ở máy nếu user không bật sync.

**Fallback:** gọi `upower --battery`/`--show-info` nếu D-Bus binding gặp vấn đề.

Nguồn:

- https://upower.freedesktop.org/docs/UPower/
- https://upower.freedesktop.org/docs/upower.1.html

### Notification webhook

Optional, generic HTTP POST. Không cần provider-specific integration ở MVP.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem là time-series collection và deterministic trend analysis. AI không làm collection chính xác hơn.

Các tác vụ nên dùng normal code:

- health ratio;
- rolling median;
- percentage-point delta;
- missing-data handling;
- anomaly threshold;
- device/battery identity matching.

Nếu sau này thêm AI, chỉ nên là một optional explanation layer như:

> “Health giảm 4.6 percentage points trong 90 ngày, nhanh hơn median 90 ngày trước.”

Nhưng ngay cả phần này deterministic template cũng đủ tốt.

## 14. Các bài toán kỹ thuật đáng học

### 1. OS-specific hardware telemetry

Windows và Linux expose battery data qua cơ chế khác nhau.

**Skill cải thiện:** platform abstraction, native API integration, defensive programming.

### 2. Data normalization

Không phải mọi controller đều report cùng fields hoặc cùng chất lượng dữ liệu.

**Skill cải thiện:** nullable domain modeling, quality flags, normalization pipeline.

### 3. Reliable background sync

Laptop thường offline, sleep hoặc đổi mạng.

**Skill cải thiện:** local spool, retry, idempotency, eventual synchronization.

### 4. Time-series analysis

Battery readings có noise và missing samples.

**Skill cải thiện:** aggregation, rolling median, downsampling, trend calculation.

### 5. Device identity và replacement detection

Cùng một laptop có thể thay pin.

**Skill cải thiện:** entity identity, change detection, conflict handling.

## 15. Rủi ro và cách xử lý

### Hardware không report đủ dữ liệu

**Risk:** `DesignCapacity` hoặc `FullChargeCapacity` null.

**Mitigation:** metric availability flags; không suy đoán; hỗ trợ nhiều collector path.

### Reading nhiễu

**Risk:** một sample bất thường làm alert sai.

**Mitigation:** rolling median, minimum sample count, alert theo sustained change chứ không theo một reading.

### Battery identity không ổn định

**Risk:** OS identifier thay đổi sau update/reboot.

**Mitigation:** composite fingerprint từ stable metadata, nhưng không phụ thuộc duy nhất serial.

### Privacy

**Risk:** telemetry gửi máy chủ ngoài ý muốn.

**Mitigation:** local-first default, rõ field nào được sync, không gửi process/application data.

### Security

**Risk:** device ingest token bị lộ.

**Mitigation:** token per device, hash at rest, rotation, revoke, TLS nếu chạy qua Internet.

### Scope expansion

**Risk:** biến thành hardware monitoring suite.

**Mitigation:** chỉ battery health trong MVP; CPU/GPU/SMART không thuộc core scope.

### User adoption

**Risk:** cần chờ nhiều tuần mới thấy trend.

**Mitigation:** import một Windows battery report ban đầu để bootstrap historical context nếu parser có thể làm đáng tin.

### Maintenance burden

**Risk:** OS API behavior thay đổi.

**Mitigation:** collector interface tách biệt, fixture-based parser tests và capability detection.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, tạo vertical slice đầu tiên:

**Windows collector → normalized JSON → console history file.**

Không làm backend/dashboard trong session đầu.

### Files/components cần tạo

```text

    Collectors/IBatteryCollector.cs
    Collectors/WindowsBatteryCollector.cs
    Storage/JsonLineSnapshotStore.cs
tests/
  BatteryLedger.Agent.Tests/
    BatteryHealthTests.cs
```

### Commands

```bash
dotnet new sln -n BatteryLedger
dotnet new console -n BatteryLedger.Agent -o src/BatteryLedger.Agent
dotnet new xunit -n BatteryLedger.Agent.Tests -o tests/BatteryLedger.Agent.Tests

dotnet add tests/BatteryLedger.Agent.Tests reference src/BatteryLedger.Agent
```

### First vertical slice

1. Chạy:

```powershell
powercfg /batteryreport /output battery-report.xml /xml
```

2. Parse các field cần thiết từ XML nếu có.
3. Normalize về object:

```json
{
  "capturedAt": "<runtime timestamp>",
  "designCapacityMwh": 50000,
  "fullChargeCapacityMwh": 45000,
  "healthPercent": 90.0,
  "source": "windows-powercfg"
}
```

4. Append JSON vào:

```text
data/battery-snapshots.jsonl
```

5. In console:

```text
Battery health: 90.0%
Full charge: 45.0 Wh
Design: 50.0 Wh
Snapshot saved.
```

### Test đầu tiên

```csharp
[Fact]
public void CalculatesHealthPercent()
{
    var health = BatteryHealth.Calculate(45000, 50000);
    Assert.Equal(90.0, health);
}
```

### Expected result

Sau khi chạy agent hai lần, file JSONL có hai timestamped snapshots thật từ laptop.

### Verification checklist

- [ ] `powercfg /batteryreport /xml` chạy thành công trên máy Windows có pin.
- [ ] Parser không hard-code machine-specific path.
- [ ] Capacity được normalize về mWh.
- [ ] Health ratio chỉ tính khi cả design/full-charge capacity hợp lệ.
- [ ] Missing field không làm process crash.
- [ ] Một unit test health calculation pass.
- [ ] Chạy agent lần hai tạo sample mới.

### Stop condition

Dừng session khi lệnh:

```bash
dotnet run --project src/BatteryLedger.Agent
```

đọc được battery metrics thật, in health ra console và append một normalized snapshot vào JSONL. Không dựng database, API, Docker hoặc Vue trước khi vertical slice này hoạt động ổn định.
