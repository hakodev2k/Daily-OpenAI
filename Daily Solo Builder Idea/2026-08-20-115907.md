# Ý tưởng hôm nay: RateGuard — Outbound API Rate-Limit Governor

## 1. Tóm tắt ý tưởng

RateGuard là một developer tool self-hosted giúp ứng dụng có nhiều background job hoặc integration bên thứ ba **kiểm soát outbound API request theo quota, rate-limit header và retry policy**, thay vì để từng service tự retry theo cách riêng rồi cùng nhau gây ra 429 hoặc thundering herd. Công cụ phù hợp với solo developer hoặc team nhỏ đang tích hợp GitHub, Microsoft Graph, AI API, CRM, payment API hoặc các dịch vụ SaaS có giới hạn request.

- Người dùng chính: backend developer xây automation, scheduled job và integration API.
- Bài toán chính: nhiều job dùng chung một API nhưng không có request budget tập trung, dẫn đến 429, retry chồng retry, job trễ hoặc thất bại khó chẩn đoán.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Một ứng dụng tích hợp API bên ngoài thường bắt đầu đơn giản: mỗi job dùng `HttpClient`, gặp lỗi thì retry. Khi số job tăng, cách này dễ phát sinh vấn đề:

- nhiều job cùng gọi một provider trong cùng thời điểm;
- mỗi job tự retry độc lập;
- retry có thể xảy ra đúng lúc provider vẫn đang giới hạn;
- một endpoint tốn quota nhưng job khác không biết;
- request ít quan trọng có thể chiếm budget của request quan trọng;
- lỗi 429 bị ghi log nhưng không có lịch sử budget để giải thích nguyên nhân.

### Confirmed facts

GitHub REST API áp dụng cả **primary rate limits** và **secondary rate limits**. Tài liệu hiện tại ghi rõ unauthenticated request thường bị giới hạn ở 60 request/giờ, authenticated user thường có 5.000 request/giờ, và GitHub có thêm secondary limits để bảo vệ hệ thống. Khi vượt giới hạn, API có thể trả `403` hoặc `429`. GitHub khuyến nghị tôn trọng `retry-after`, `x-ratelimit-remaining` và `x-ratelimit-reset`, đồng thời tránh retry liên tục khi đang bị giới hạn.

Nguồn: GitHub Docs — Rate limits for the REST API  
https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api

GitHub cũng khuyến nghị giảm polling, dùng webhook khi có thể, thực hiện request tuần tự thay vì tạo concurrency quá cao, và sử dụng conditional request với `ETag`/`If-None-Match`. Với authenticated conditional GET, response `304 Not Modified` có thể không tính vào primary rate limit.

Nguồn: GitHub Docs — Best practices for using the REST API  
https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api

.NET có sẵn `System.Threading.RateLimiting` và Microsoft có tài liệu minh họa việc tạo client-side HTTP rate-limiting handler cho `HttpClient`, vì vậy phần enforcement cốt lõi của RateGuard có thể triển khai bằng primitive có sẵn thay vì tự viết thuật toán concurrency từ đầu.

Nguồn: Microsoft Learn — Rate limiting an HTTP handler in .NET  
https://learn.microsoft.com/en-us/dotnet/core/extensions/http-ratelimiter

### Observation

Các SDK/provider thường có retry hoặc rate-limit handling riêng, nhưng khi một hệ thống có nhiều worker/job khác nhau sử dụng cùng credential hoặc cùng quota, policy bị phân tán ở nhiều nơi. Vấn đề không chỉ là “retry request”, mà là **điều phối toàn bộ outbound traffic cùng chia sẻ một budget**.

### Assumption cần kiểm chứng

Developer vận hành nhiều integration sẽ chấp nhận thêm một lightweight governor nếu nó giúp giảm 429, giảm request dư thừa và trả lời được câu hỏi: “job nào đang tiêu quota, khi nào budget hồi phục, request nào đang chờ?”.

## 3. Người dùng mục tiêu

### Primary user

Backend developer hoặc solo SaaS developer có từ 3–10 background job/integration cùng gọi API bên thứ ba.

### Context of use

Ví dụ hệ thống có:

- job đồng bộ repository GitHub;
- job đọc issue/PR;
- scheduled report;
- polling một API không có webhook;
- retry job khi provider tạm lỗi;
- một số request interactive cần ưu tiên hơn scheduled sync.

### Main pain point

Không biết tổng outbound request rate hiện tại, không có request budget tập trung và khó kiểm soát retry xuyên suốt nhiều job.

### Current workaround

- `Polly`/retry riêng trong từng service;
- `Task.Delay` thủ công;
- semaphore cục bộ;
- giảm cron frequency;
- xem log khi bị 429 rồi sửa từng chỗ;
- hard-code delay theo từng provider.

### Vì sao họ sẽ thử RateGuard

Vì họ có thể giữ nguyên phần lớn business code nhưng đưa outbound call qua một gateway/library thống nhất để có queue, quota state, retry scheduling và observability chung.

## 4. Giải pháp đề xuất

RateGuard có hai mode:

1. **In-process SDK** cho ứng dụng .NET nhỏ.
2. **Local HTTP gateway** cho nhiều process/service cùng chia sẻ budget.

MVP chỉ cần triển khai mode gateway để chứng minh bài toán cross-process.

### Main workflow

Application gửi một outbound job tới RateGuard với:

- provider;
- HTTP method;
- target URL đã whitelist;
- request metadata;
- priority;
- idempotency classification;
- optional deadline.

RateGuard:

1. xác định policy của provider;
2. kiểm tra budget hiện tại;
3. queue request nếu chưa được phép chạy;
4. gửi request khi có permit;
5. đọc response headers;
6. cập nhật rate-limit state;
7. nếu gặp 429/403 rate-limit thì schedule retry theo `Retry-After` hoặc reset timestamp;
8. trả kết quả hoặc callback status cho caller.

### Input

```json
{
  "provider": "github",
  "priority": "normal",
  "method": "GET",
  "url": "https://api.github.com/repos/example/project/issues",
  "deadlineSeconds": 60
}
```

Không lưu plaintext credential trong payload. Credential được cấu hình riêng theo provider profile.

### Processing

- per-provider queue;
- token bucket/concurrency limiter;
- adaptive cooldown từ response headers;
- retry classification;
- priority scheduling;
- request deduplication cho safe GET nếu phù hợp.

### Output

```json
{
  "status": "completed",
  "httpStatus": 200,
  "attemptCount": 1,
  "queueWaitMs": 182,
  "providerRemaining": 4321
}
```

### Tự động hóa

RateGuard tự động:

- giữ request trong queue;
- áp dụng pacing;
- tôn trọng cooldown;
- retry safe request;
- cập nhật quota state;
- ghi metrics.

### User vẫn kiểm soát

User quyết định:

- endpoint nào được phép gọi;
- request nào được retry;
- priority;
- deadline;
- max attempts;
- credential profile;
- provider policy.

### Key differentiator

Không phải generic API proxy. Điểm khác biệt là **budget-aware scheduling cho background jobs**: nhìn toàn bộ request của một provider như một tài nguyên hữu hạn cần phân phối, thay vì chỉ retry từng HTTP call độc lập.

### Ví dụ end-to-end

Một hệ thống có ba job GitHub chạy cùng lúc 12:00:

- `RepoSync`: 200 request tiềm năng;
- `IssueRadar`: 50 request;
- `InteractiveRefresh`: 3 request do user vừa click.

RateGuard nhận tất cả request.

`InteractiveRefresh` có priority cao nên được thực hiện trước. `RepoSync` bị pace xuống. Khi một response cho biết quota còn thấp, RateGuard giảm tốc tất cả GitHub jobs thay vì chỉ service vừa nhận response đó. Nếu nhận `Retry-After`, queue GitHub chuyển sang cooldown và tự resume sau thời điểm phù hợp.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Công cụ có thể dùng ngay cho project cá nhân có scheduled jobs, GitHub integration, Microsoft Graph hoặc AI API. Giá trị không phụ thuộc vào việc có nhiều user bên ngoài.

### Technical learning value

Dự án giúp thực hành:

- rate limiting;
- queue scheduling;
- concurrency control;
- retry/recovery;
- HTTP semantics;
- idempotency;
- observability;
- multi-process coordination.

### Vì sao phù hợp solo developer

Core domain khá nhỏ: request queue + provider policy + execution engine + dashboard. Không cần Kubernetes, distributed consensus hay data platform ở MVP.

### Vì sao vẫn hữu ích với rất ít user

Chỉ cần dùng trong các automation cá nhân đã có thể:

- giảm 429;
- gom retry logic;
- nhìn request budget tập trung;
- giảm polling dư thừa;
- debug background job dễ hơn.

### Điều gì khiến ý tưởng thất bại

Nếu phần lớn integration người dùng chỉ có một job/API hoặc SDK provider đã xử lý quota rất tốt, lợi ích của governor riêng có thể không đủ lớn.

### Lý do mạnh nhất để không build

Nhiều ứng dụng nhỏ chỉ cần `Polly` + `System.Threading.RateLimiting` trong cùng process. Nếu không có nhu cầu chia sẻ quota giữa nhiều worker/process thì RateGuard dễ trở thành abstraction thừa.

## 7. Luồng hoạt động

### Normal flow

Caller tạo outbound request
→ validate provider + target whitelist
→ classify retry safety
→ enqueue
→ scheduler kiểm tra permit
→ execute HTTP request
→ parse provider headers
→ update budget state
→ persist attempt
→ trả result.

### Rate-limited flow

Request chạy
→ provider trả 429/403 rate-limit
→ parser kiểm tra `Retry-After`/reset header
→ set provider cooldown
→ request retry-safe được đưa lại queue với `NotBefore`
→ request unsafe trả failure để caller quyết định
→ scheduler resume sau cooldown.

### Timeout flow

Queue wait vượt deadline
→ không gửi request ra ngoài
→ trả `expired-in-queue`.

### Provider unavailable

Nhiều request trả 5xx/network failure
→ retry với exponential backoff có jitter
→ vượt max attempts thì fail
→ không block queue vô hạn.

### Invalid target

Target URL không thuộc allowlist
→ reject trước khi queue
→ không thực hiện HTTP request.

### Shutdown

Application nhận SIGTERM
→ dừng nhận request mới
→ hoàn tất request đang chạy hoặc timeout
→ queued item vẫn nằm trong DB
→ resume sau restart.

## 10. Thiết kế dữ liệu ban đầu

### ProviderProfile

**Purpose:** định nghĩa một API provider và policy cơ bản.

Fields:

- `Id`
- `Name`
- `BaseUrl`
- `MaxConcurrency`
- `RequestsPerWindow`
- `WindowSeconds`
- `RetryAfterHeader`
- `RemainingHeader`
- `ResetHeader`
- `IsEnabled`
- `CreatedAt`

Relationships:

- một provider có nhiều `OutboundRequest`;
- một provider có một current `ProviderState`.

Retention: lâu dài cho tới khi user xóa.

### ProviderState

**Purpose:** lưu trạng thái runtime phục hồi được sau restart.

Fields:

- `ProviderId`
- `Remaining`
- `ResetAt`
- `CooldownUntil`
- `LastResponseAt`
- `Version`

Retention: cập nhật in-place, không cần lịch sử dài.

### OutboundRequest

**Purpose:** durable queue item.

Fields:

- `Id`
- `ProviderId`
- `Method`
- `RelativeUrl`
- `HeadersJson` với dữ liệu nhạy cảm đã loại bỏ
- `BodyReference` hoặc body nhỏ
- `Priority`
- `RetrySafe`
- `Status`
- `NotBefore`
- `DeadlineAt`
- `CreatedAt`
- `CompletedAt`

Retention: 7–30 ngày sau completion.

### RequestAttempt

**Purpose:** audit từng lần gửi.

Fields:

- `Id`
- `OutboundRequestId`
- `AttemptNumber`
- `StartedAt`
- `FinishedAt`
- `StatusCode`
- `DurationMs`
- `ErrorType`
- `RetryAfterSeconds`
- `RemainingObserved`

Retention: 14–30 ngày hoặc aggregate rồi xóa.

### CredentialProfile

MVP có thể không lưu secret trong DB. Chỉ lưu:

- `ProviderId`
- `SecretReferenceName`

Secret thực tế lấy từ environment variable hoặc mounted secret.

## 11. API và tích hợp

### GitHub REST API

**Purpose:** provider đầu tiên để test thực tế.

**Authentication:** fine-grained token, GitHub App token hoặc token khác phù hợp use case.

**Rate-limit concern:** GitHub có primary và secondary rate limits; response headers cung cấp thông tin để theo dõi primary limit.

**Privacy/permission:** token chỉ cấp quyền tối thiểu cần thiết; RateGuard không hiển thị token trong UI/log.

**Fallback:** chạy RateGuard với fake provider local nếu không cấu hình GitHub credential.

Nguồn:  
https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api

### Generic HTTP provider

**Purpose:** hỗ trợ API không có adapter riêng.

**Authentication:** credential thông qua environment/config mapping.

**Rate-limit concern:** user tự khai báo request/window và header mapping.

**Fallback:** fixed local rate policy nếu provider không trả quota headers.

### `System.Threading.RateLimiting`

**Purpose:** local admission control.

**Authentication/cost:** không có.

**Privacy:** không ảnh hưởng.

Nguồn:  
https://learn.microsoft.com/en-us/dotnet/core/extensions/http-ratelimiter

### OpenTelemetry — Later

Có thể export request duration, queue wait và 429 count. Không cần cho MVP nếu structured logs đã đủ.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Các quyết định cốt lõi đều deterministic:

- request nào được chạy;
- bao nhiêu permit còn lại;
- khi nào retry;
- deadline;
- cooldown;
- priority;
- HTTP status classification.

AI không nên tham gia scheduling vì có thể làm hành vi khó dự đoán.

Nếu mở rộng sau này, AI chỉ có thể dùng optional để giải thích log hoặc tạo human-readable incident summary, nhưng không được quyền thay đổi execution policy tự động.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác nhận có vấn đề thật trong workflow cá nhân.

**Main tasks:**

- lấy một integration hiện có dùng GitHub API;
- log request count trong 1–3 ngày;

**Expected output:** bảng request rate, burst time và failure mode.

**Completion criteria:** chứng minh ít nhất một tình huống mà request governor tập trung tạo hành vi tốt hơn delay/retry độc lập.

### Phase 1 — Core MVP

**Goal:** enqueue → schedule → execute → record hoàn chỉnh.

**Main tasks:**

- provider config;
- `POST /requests`;
- DB queue;
- scheduler worker;
- concurrency limiter;
- GitHub adapter;
- basic queue dashboard.

**Expected output:** 100 fake requests được pace đúng giới hạn.

**Completion criteria:** không vượt configured concurrency/request window trong integration test.

### Phase 2 — Reliability

**Goal:** xử lý failure production-like.

**Main tasks:**

- graceful shutdown;
- retry-safe classification;

- allowlist;
- secret redaction;

**Completion criteria:** kill process giữa lúc chạy rồi restart, queue phục hồi chính xác và không duplicate unsafe request.

### Phase 3 — Useful expansion

**Goal:** giảm request không cần thiết và tăng visibility.

**Main tasks:**

**Expected output:** dashboard trả lời được request nào đang tiêu quota và tại sao request bị chờ.

**Goal:** chạy self-hosted ổn định.

**Main tasks:**

- Docker image;

- health checks;
- backup DB;
- retention cleanup;
- OpenTelemetry hoặc metrics endpoint;

## 14. Các bài toán kỹ thuật đáng học

### 1. Distributed-style rate limiting ngay cả trong monolith

Bạn phải quản lý permits, time windows và concurrency theo provider. Kỹ năng cải thiện: concurrency primitives, token bucket, fixed/sliding window và scheduling fairness.

### 2. Retry và idempotency

Retry `GET` thường đơn giản hơn retry `POST`. Tool phải phân biệt retry-safe thay vì coi mọi lỗi như nhau. Kỹ năng cải thiện: HTTP semantics, idempotency key, duplicate prevention.

### 3. Durable queue và lease recovery

Worker có thể crash sau khi claim request nhưng trước khi ghi kết quả. Kỹ năng cải thiện: database queue, lease timeout, optimistic concurrency, at-least-once processing.

### 4. Adaptive provider state

Configured rate có thể khác trạng thái provider quan sát được từ headers. Kỹ năng cải thiện: reconciliation giữa local policy và remote quota.

### 5. Fair scheduling

Nếu luôn ưu tiên high-priority, low-priority request có thể starvation. Kỹ năng cải thiện: weighted priority, aging và backpressure.

## 15. Rủi ro và cách xử lý

### Technical complexity

**Risk:** tự biến project thành distributed API gateway.

**Mitigation:** MVP chỉ một instance, một DB, một scheduler, một GitHub adapter.

### Duplicate side effects

**Risk:** retry request unsafe có thể tạo action hai lần.

**Mitigation:** mặc định chỉ auto-retry `GET`/`HEAD`; mutation cần `RetrySafe=true` và idempotency strategy rõ ràng.

### Secret exposure

**Risk:** gateway nhìn thấy authentication header.

**Mitigation:** secret lấy từ provider profile, không nhận credential qua request payload, redact log, encryption hoặc external secret store ở phase sau.

### SSRF

**Risk:** endpoint generic cho phép gọi URL nội bộ nguy hiểm.

**Mitigation:** base URL allowlist, reject arbitrary scheme/host, DNS/IP validation, không hỗ trợ user-supplied unrestricted URL ở MVP.

### Incorrect rate-limit interpretation

**Risk:** mỗi provider có semantics khác nhau.

**Mitigation:** generic policy dùng local configured limit; provider adapter mới được phép parse provider-specific headers.

### Queue latency

**Risk:** request interactive bị delayed sau batch lớn.

**Mitigation:** priority + deadline + reserved concurrency tùy provider ở phase sau.

### Database growth

**Risk:** attempt history lớn nhanh.

**Mitigation:** retention job, chỉ lưu metadata, không lưu full response body mặc định.

### User adoption

**Risk:** tool phức tạp hơn retry library.

**Mitigation:** tập trung use case rõ: nhiều job/process chia sẻ cùng API budget. Không quảng bá cho single-call app.

## 16. Kiểm thử

### Unit tests

Kiểm tra:

- priority ordering;
- retry decision;
- `Retry-After` parsing;
- deadline calculation;
- rate-limit state update.

### Integration tests

Dùng fake HTTP server trả tuần tự:

```text
200
200
429 + Retry-After
200
```

Xác minh scheduler pause và resume đúng.

### End-to-end tests

Playwright kiểm tra:

- tạo provider;
- enqueue requests;
- xem queue chuyển trạng thái;
- xem metrics.

### Failure-path tests

- process crash giữa attempt;
- DB unavailable;
- provider timeout;
- 429 không có `Retry-After`;
- malformed headers.

### Security tests

- SSRF attempt;
- path escaping;
- header injection;
- secret xuất hiện trong logs.

### 5 test scenario quan trọng nhất

1. 50 request đồng thời với limit 5 concurrency không bao giờ vượt 5 active request.
2. Provider trả `429 + Retry-After: 10`; không request nào của provider được gửi trong cooldown window.
3. High-priority request vào sau một batch low-priority vẫn được xử lý sớm nhưng low-priority không starvation vĩnh viễn.
4. Worker crash sau khi claim request; request được reclaim sau lease timeout mà không mất dữ liệu.
5. Mutation không được đánh dấu retry-safe nhận network uncertainty thì không tự động gửi lần hai.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, tạo vertical slice đầu tiên chứng minh:

> 20 request được gửi vào cùng lúc nhưng fake provider chỉ nhận tối đa 2 request đồng thời.

### Files/components cần tạo

```text
RateGuard.sln
src/
  RateGuard.Api/
    Program.cs
    Models/OutboundRequest.cs
    Services/RequestScheduler.cs
    Services/RateLimitedHttpClient.cs
    Configuration/ProviderOptions.cs
tests/
  RateGuard.Tests/
    RateLimiterIntegrationTests.cs
```

### Setup commands

```bash
dotnet new sln -n RateGuard
dotnet new webapi -n RateGuard.Api -o src/RateGuard.Api
dotnet new xunit -n RateGuard.Tests -o tests/RateGuard.Tests
dotnet sln add src/RateGuard.Api
dotnet sln add tests/RateGuard.Tests
dotnet add tests/RateGuard.Tests reference src/RateGuard.Api
```

Không thêm PostgreSQL trong session đầu tiên. Dùng in-memory queue để thấy vertical slice chạy được trước.

### First vertical slice

Tạo endpoint:

```text
POST /requests
```

Payload đơn giản:

```json
{
  "path": "/demo",
  "priority": "normal"
}
```

Tạo một fake provider endpoint ngay trong app:

```text
GET /fake-provider/demo
```

Fake provider:

- tăng `activeRequestCount`;
- delay 500 ms;
- ghi `maxObservedConcurrency`;
- giảm counter;
- trả 200.

`RateLimitedHttpClient` dùng `ConcurrencyLimiter` với:

```text
PermitLimit = 2
```

Gửi 20 request vào queue gần như đồng thời.

### Expected result

Console/log hiển thị tương tự:

```text
queued=20
running=2
completed=0
...
queued=0
running=0
completed=20
maxObservedConcurrency=2
```

### Verification checklist

- [ ] 20 request đều hoàn tất.
- [ ] `maxObservedConcurrency` không bao giờ > 2.
- [ ] Queue không block HTTP thread bằng `.Wait()`/`.Result`.
- [ ] CancellationToken được truyền xuyên suốt.
- [ ] Có ít nhất một integration test xác minh concurrency limit.
- [ ] Log có request ID và queue wait time.

### Stop condition

Kết thúc session ngay khi test sau pass:

```text
Given 20 queued requests
And provider concurrency limit = 2
When scheduler processes all requests
Then all 20 complete successfully
And max provider concurrency observed = 2
```

Không làm database, dashboard, GitHub authentication, Redis, AI hoặc distributed mode trong buổi đầu tiên.
