# Ý tưởng hôm nay: SourcePulse — Citation Freshness & Link Drift Guard

## 1. Tóm tắt ý tưởng

SourcePulse là một developer tool self-hosted giúp quét các file Markdown có chứa link/citation, lưu snapshot metadata của từng nguồn và phát hiện khi nguồn **chết, redirect, đổi domain, đổi tiêu đề, thay đổi nội dung đáng kể hoặc trở nên không còn khớp với citation ban đầu**. Công cụ đặc biệt hữu ích cho repository chứa nhiều báo cáo AI-generated, research notes, technical docs hoặc knowledge base được cập nhật liên tục.

- Người dùng chính: developer/solo builder duy trì nhiều tài liệu Markdown có external citations.
- Bài toán chính: link vẫn trả `200 OK` nhưng nội dung nguồn đã thay đổi, redirect hoặc mất tính liên quan mà người viết không biết.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

### Confirmed facts

Các link checker phổ biến đã giải quyết khá tốt bài toán broken link. Ví dụ, lychee hỗ trợ kiểm tra URL trong Markdown/HTML, chạy dưới dạng CLI, library hoặc GitHub Action và có thể fail CI khi URL không hợp lệ.

Nguồn:

- https://github.com/lycheeverse/lychee
- https://github.com/lycheeverse/lychee-action

HTTP còn có các validator/metadata như `Last-Modified` và `ETag` giúp client xác định representation đã thay đổi hay chưa. RFC 9110 mô tả `Last-Modified` là timestamp mà origin server tin rằng representation được sửa lần cuối; các validator này có thể dùng với conditional requests để giảm việc tải lại nội dung không đổi.

Nguồn:

- https://www.rfc-editor.org/rfc/rfc9110.html

Nghiên cứu về broken external links trên Stack Overflow cũng cho thấy link rot là vấn đề thực tế trong knowledge base kỹ thuật, đặc biệt khi tài liệu phụ thuộc vào nguồn bên ngoài.

Nguồn:

- https://arxiv.org/abs/2010.04892

### Observation

Broken-link detection chỉ trả lời một câu hỏi:

> URL còn truy cập được không?

Nhưng với report/research note, các failure thực tế còn gồm:

- URL trả `200` nhưng article đã được rewrite.
- URL redirect sang homepage hoặc trang generic.
- Documentation page giữ URL cũ nhưng nội dung API đã thay đổi.
- GitHub README thay đổi đáng kể sau khi report được viết.
- Trang product pricing thay đổi nhưng note vẫn trích thông tin cũ.
- Source đổi title hoặc canonical URL.
- Một citation từng hỗ trợ claim A nhưng nội dung mới không còn chứa evidence đó.

Một link checker bình thường thường không lưu historical fingerprint đủ để nhận biết loại drift này.

### Assumption cần kiểm chứng

Developer duy trì nhiều Markdown report hoặc AI-generated research files sẽ thấy giá trị trong việc biết:

> “Nguồn này vẫn online, nhưng đã thay đổi đủ nhiều để cần review lại citation.”

Đây là assumption cần validate bằng cách chạy SourcePulse trên một repository thật trong 2–4 tuần.

### Cách xử lý hiện tại

Người dùng thường:

- chạy broken-link checker;
- mở link thủ công;
- rely vào cached browser history;
- không kiểm tra lại source cũ;
- hoặc chỉ phát hiện citation lỗi khi cần đọc lại tài liệu nhiều tháng sau.

Vấn đề là việc review thủ công không scale khi repository có hàng trăm hoặc hàng nghìn URLs.

## 3. Người dùng mục tiêu

**Primary user:** developer duy trì một repository Markdown chứa technical research, AI-generated reports hoặc long-lived documentation.

### Context of use

Ví dụ repository có cấu trúc:

```text
reports/
  2026-08-18-ai-security.md
  2026-08-19-dotnet-news.md
  2026-08-20-market-notes.md
notes/
  azure-graph.md
  postgres-performance.md
```

Mỗi file có nhiều nguồn external.

### Main pain point

Không biết citation nào đã trở nên stale hoặc thay đổi sau khi tài liệu được tạo.

### Current workaround

Chạy link checker để bắt `404/500`, sau đó kiểm tra thủ công một số URL quan trọng.

### Lý do họ thử SourcePulse

Một command như:

```bash
sourcepulse scan .
```

có thể trả về:

```text
37 sources unchanged
4 sources redirected
2 sources changed significantly
1 source unavailable

REVIEW REQUIRED
reports/2026-08-18-ai-security.md:74
https://vendor.example/docs/security
Content similarity: 61%
Title changed: yes
Last reviewed: 12 days ago
```

## 4. Giải pháp đề xuất

SourcePulse hoạt động theo mô hình **extract → fetch → normalize → fingerprint → compare → classify → report**.

### Input

- Markdown files hoặc directory.
- Optional config `.sourcepulse.yml`.
- Baseline snapshot lưu từ lần scan trước.

### Processing

1. Parse Markdown và extract external URLs.
2. Map URL tới file/line/citation context.
3. Fetch URL với timeout, redirect limit và user-agent rõ ràng.
4. Lưu HTTP metadata:
   - status code;
   - final URL;
   - content type;
   - ETag;
   - Last-Modified;
   - title;
   - canonical URL nếu có.
5. Với HTML/text response:
   - strip script/style/navigation cơ bản;
   - normalize whitespace;
   - hash normalized text;
   - tạo secondary fingerprint cho title + headings + visible text.
6. So sánh với baseline.
7. Classify drift.
8. Xuất Markdown/JSON report.

### Output

Mỗi URL có trạng thái:

```text
UNCHANGED
MINOR_CHANGE
MAJOR_CHANGE
REDIRECTED
BROKEN
BLOCKED
CONTENT_TYPE_CHANGED
REVIEW_REQUIRED
```

### What is automated

- URL extraction.
- HTTP fetching.
- Conditional request.
- Redirect tracking.
- Content fingerprinting.
- Change scoring.
- Historical snapshot.
- CI exit code.

### User control

User quyết định:

- domain nào được scan;
- threshold major/minor change;
- URL nào ignore;
- source nào critical;
- retention period;
- có fail CI hay chỉ warning.

### Key differentiator

SourcePulse **không cố cạnh tranh với broken-link checker**. Điểm khác biệt là:

> Theo dõi citation/source drift theo thời gian, không chỉ availability tại thời điểm hiện tại.

### Ví dụ end-to-end

Ngày 1, report chứa:

```markdown
Theo tài liệu Vendor X, API hỗ trợ tối đa 100 requests/minute.
Nguồn: https://vendor.example/api/limits
```

SourcePulse snapshot:

```text
Status: 200
Title: API Limits
TextHash: A1...
ETag: xyz
```

Ba tuần sau, cùng URL vẫn `200`, nhưng page đổi thành:

```text
Default limit: 60 requests/minute
```

SourcePulse phát hiện visible-text fingerprint thay đổi lớn và report:

```text
MAJOR_CHANGE
Source appears to have changed significantly.
Review citation context at reports/api-research.md:52.
```

Tool không tự kết luận claim sai; nó chỉ đưa evidence để người dùng review.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Tool có giá trị ngay cho một repository cá nhân có nhiều research Markdown. Không cần có user bên ngoài mới hữu ích.

Nếu một developer tạo report tự động mỗi ngày, số URL tích lũy tăng nhanh và việc review thủ công trở nên không thực tế.

### Technical learning value

Dự án có nhiều bài toán thú vị:

- HTTP conditional requests;
- caching semantics;
- content normalization;
- similarity/fingerprint algorithms;
- retry/rate limiting;
- deterministic diff;
- CLI design;
- CI integration;
- SQLite indexing.

### Vì sao phù hợp solo developer

Core workflow hoàn toàn deterministic, không cần account system, payment, cloud data pipeline hoặc heavy infrastructure.

MVP chỉ cần:

- CLI;
- SQLite;
- HTTP client;
- Markdown parser;
- report generator.

### Useful even with very few users

Một người dùng duy nhất vẫn có thể dùng tool hàng ngày để bảo vệ quality của docs/research repository.

### Điều gì làm dự án thất bại

- HTML thay đổi quá nhiễu khiến false positive cao.
- Website chống bot quá nhiều khiến scan thất bại.
- User chỉ quan tâm broken links chứ không quan tâm source drift.
- Existing tools cộng thêm custom script đã đủ tốt.

### Lý do mạnh nhất để không build

Nếu repository chủ yếu link tới immutable resources như RFC, versioned docs hoặc commit-pinned GitHub files, source drift có thể quá hiếm để justify một tool riêng.

## 7. Luồng hoạt động

### First scan

User chạy:

```bash
sourcepulse scan ./docs
```

→ discover Markdown files
→ extract URLs
→ normalize/deduplicate URLs
→ fetch URLs
→ build source snapshot
→ store SQLite
→ generate baseline report.

Output:

```text
Scanned: 216 URLs
Healthy: 209
Redirected: 4
Broken: 3
Baseline created: yes
```

### Subsequent scan

User chạy lại:

```bash
sourcepulse scan ./docs --compare-latest
```

→ load previous snapshot
→ conditional fetch where possible
→ compare metadata/content
→ classify drift
→ generate change report.

### URL unchanged via validator

Server trả `304 Not Modified`
→ reuse previous content fingerprint
→ mark `UNCHANGED`
→ không download full body.

### URL redirects

Original:

```text
/docs/v1/auth
```

Final:

```text
/docs/authentication
```

→ store redirect chain
→ classify `REDIRECTED`
→ warn nếu redirect sang khác host hoặc homepage.

### Rate limit

Server trả `429`
→ đọc `Retry-After` nếu có
→ schedule bounded retry trong current scan
→ nếu vẫn fail, mark `RATE_LIMITED`, không mark `BROKEN`.

### Bot protection

Server trả `403`
→ mark `BLOCKED`
→ không retry aggressive.

### Large response

Content-Length vượt threshold
→ chỉ lưu metadata hoặc skip body
→ mark `BODY_SKIPPED_TOO_LARGE`.

### Binary content

PDF/image/zip
→ MVP chỉ kiểm tra HTTP metadata/status
→ không cố extract text.

## 11. API và tích hợp

### Generic HTTP/HTTPS

**Purpose:** fetch public citations.

**Authentication:** không cần cho public URLs.

**Cost/rate-limit concern:** mỗi domain có policy khác nhau; phải dùng bounded concurrency, delay và respect `429`/`Retry-After`.

**Privacy:** URL có thể chứa query parameters nhạy cảm.

Mitigation:

- không log query value mặc định;
- cho phép redact query parameters;
- không gửi URL sang third-party service.

**Fallback:** nếu blocked/rate-limited, mark trạng thái chính xác thay vì coi link broken.

### HTTP conditional requests

**Purpose:** giảm bandwidth.

Use:

- `If-None-Match` với stored ETag;
- `If-Modified-Since` với stored Last-Modified.

RFC 9110 là reference chính cho HTTP semantics.

Nguồn:

https://www.rfc-editor.org/rfc/rfc9110.html

### GitHub URLs

MVP xử lý như HTTP thông thường.

Later có thể dùng GitHub API để fingerprint:

- repository default branch;
- file blob SHA;
- release/tag;
- commit-pinned links.

Authentication: optional token để tránh public API rate limit.

Fallback: raw HTTPS fetch.

### Wayback Machine

Không đưa vào MVP.

Later có thể dùng để giúp user tìm archived source khi URL chết, nhưng phải kiểm tra API/rate-limit tại thời điểm implementation.

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

MVP không cần AI.

### Deterministic core

Các việc sau nên dùng normal code:

- URL parsing;
- HTTP status;
- redirects;
- ETag/Last-Modified;
- normalized hash;
- text similarity;
- threshold classification.

### AI task tiềm năng sau MVP

AI chỉ hữu ích ở bước:

> “Source đã thay đổi; thay đổi này có làm citation context trở nên không còn được support không?”

Input có thể gồm:

```json
{
  "citation_context": "...",
  "old_summary": "...",
  "new_relevant_excerpt": "..."
}
```

Expected structured output:

```json
{
  "status": "still_supported | weakened | contradicted | unclear",
  "confidence": 0.0,
  "reason": "..."
}
```

### Validation

AI output chỉ là recommendation; không tự edit report hay claim.

User phải review source.

### Deterministic fallback

Nếu không có AI:

```text
MAJOR_CHANGE → REVIEW_REQUIRED
```

workflow vẫn hoạt động hoàn chỉnh.

### Risks

- token cost;
- latency;
- sending source text to external provider;
- hallucination;
- false confidence.

Vì vậy AI tuyệt đối không phải dependency của MVP.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác nhận source drift thực sự xuất hiện đủ thường xuyên.

**Main tasks:**

1. Chọn một repository Markdown thật có ít nhất 100 URLs.
2. Chạy một script thô lấy:
   - URL;
   - status;
   - final URL;
   - title;
   - SHA-256 visible text.
3. Lưu snapshot.
4. Chạy lại sau vài ngày.
5. Review manual các URL đổi hash.

**Expected output:** một CSV/JSON với change examples thực tế.

**Completion criteria:** tìm được ít nhất một trong các case:

- meaningful content change;
- redirect drift;
- broken source;
- title/canonical change;
- noisy source cần ignore rule.

Nếu mọi thay đổi đều noise, cần reconsider product trước khi build tiếp.

### Phase 1 — Core MVP

**Goal:** vertical workflow hoàn chỉnh.

**Main tasks:**

- CLI project.
- Markdown URL extraction.
- HTTP fetcher.
- HTML title/text normalizer.
- SHA-256 fingerprint.
- SQLite snapshot.
- compare latest vs previous.
- Markdown report.

**Expected output:**

```bash
sourcepulse scan ./reports
```

trả report có changed URLs.

**Completion criteria:** scan 100+ URLs, restart process và vẫn compare được với historical baseline.

### Phase 2 — Reliability

**Goal:** giảm false positives và network failures.

**Main tasks:**

- per-domain concurrency;
- timeout;
- retry;
- `429` handling;
- redirect chain;
- ETag/Last-Modified;
- conditional requests;
- size limits;
- ignore rules;
- integration tests.

**Expected output:** scan ổn định với mixed public sites.

**Completion criteria:** transient network failures không bị báo thành broken link ngay lập tức.

### Phase 3 — Useful expansion

**Goal:** biến raw changes thành actionable review list.

**Main tasks:**

- text similarity;
- heading diff;
- critical-source tags;
- only-changed snapshots;
- history command;
- source reference context;
- CI exit policies.

**Expected output:** report ưu tiên source nào đáng review trước.

**Completion criteria:** user có thể xử lý report trong vài phút thay vì mở toàn bộ URLs.

### Phase 4 — Production readiness

**Goal:** chạy lâu dài trong repo cá nhân/team nhỏ.

**Main tasks:**

- global-tool packaging;
- Docker image;
- GitHub Actions example;
- database migrations;
- backup/export;
- structured logs;
- retention cleanup;
- docs;
- security review.

**Expected output:** reproducible installation và unattended scans.

**Completion criteria:** chạy nhiều tuần mà DB không tăng mất kiểm soát và không spam target domains.

## 14. Các bài toán kỹ thuật đáng học

### 1. HTTP caching và conditional requests

Bạn sẽ phải hiểu rõ:

- ETag;
- weak/strong validators;
- Last-Modified;
- `304 Not Modified`;
- redirect semantics;
- timeout và retry.

Skill cải thiện: **HTTP protocol engineering**.

### 2. Content normalization

Raw HTML hash rất dễ thay đổi vì:

- timestamp;
- navigation;
- ads;
- analytics IDs;
- dynamic widgets.

Bạn phải xây normalization strategy đủ đơn giản nhưng giảm noise.

Skill cải thiện: **data normalization và deterministic processing**.

### 3. Change classification

Hash equality chỉ trả lời changed/not changed.

Một tool hữu ích cần phân biệt:

- tiny cosmetic change;
- title change;
- major visible-text change;
- redirect;
- domain migration.

Skill cải thiện: **diff algorithms và signal/noise judgment**.

### 4. Responsible crawling

Tool phải scan hàng trăm URLs mà không trở thành abusive crawler.

Cần:

- host-based concurrency;
- rate limiting;
- cache;
- backoff;
- sensible user-agent.

Skill cải thiện: **network resource management**.

### 5. Historical data modeling

Không cần lưu full response mọi lần nhưng vẫn cần đủ evidence để compare.

Skill cải thiện: **storage trade-offs, retention và auditability**.

## 15. Rủi ro và cách xử lý

### Rủi ro 1 — False positive quá nhiều

Dynamic pages đổi hash mỗi lần scan.

**Mitigation:**

- strip script/style;
- ignore common dynamic blocks;
- compare visible-text similarity;
- per-domain rules;
- minor/major thresholds;
- allow ignore URL/domain.

### Rủi ro 2 — Website block crawler

Một số site trả 403 hoặc CAPTCHA.

**Mitigation:**

- không bypass anti-bot;
- identify user-agent rõ ràng;
- rate-limit;
- mark `BLOCKED`;
- user có thể exclude domain.

### Rủi ro 3 — Gây load cho website

Hourly scans của hàng nghìn URLs có thể không phù hợp.

**Mitigation:**

- cache;
- conditional GET;
- configurable minimum recheck interval;
- per-host limits;
- skip immutable/versioned URLs lâu hơn.

### Rủi ro 4 — URL chứa dữ liệu nhạy cảm

Query string có thể chứa token/session identifiers.

**Mitigation:**

- redact query values trong logs/report;
- warn khi URL có suspicious parameters;
- không persist credentials;
- optional query-parameter denylist.

### Rủi ro 5 — Scope expansion thành crawler lớn

Dễ thêm screenshot, archive, search engine, semantic validation.

**Mitigation:**

MVP giữ đúng boundary:

> Markdown external citation freshness.

### Rủi ro 6 — Storage growth

Nếu lưu full HTML mỗi lần thì DB tăng nhanh.

**Mitigation:**

- không lưu full body mặc định;
- chỉ lưu fingerprint + metadata;
- retain changed snapshots;
- cleanup job.

### Rủi ro 7 — User adoption thấp

Có thể người dùng hài lòng với lychee.

**Mitigation:**

Validation phải đo source drift khác broken links, không định vị sản phẩm như “link checker khác”.

### Data-quality tests

Đảm bảo cùng một normalized page tạo cùng fingerprint.

### 5 test scenario quan trọng nhất

1. **ETag unchanged**
   - first response `200 + ETag`;
   - second response `304`;
   - result phải `UNCHANGED`.

2. **Meaningful content change**
   - cùng URL;
   - title giữ nguyên;
   - visible text đổi lớn;
   - result `MAJOR_CHANGE`.

3. **Redirect migration**
   - URL cũ `301` sang URL mới;
   - lưu final URL và redirect chain;
   - result `REDIRECTED`.

4. **Rate-limited source**
   - server trả `429`;
   - tool không mark `BROKEN`;
   - respect bounded retry.

5. **Dynamic noise**
   - page chỉ đổi timestamp/footer;
   - normalized fingerprint/similarity không tạo major alert.

manual citation review

SourcePulse changed-only review

- ignored với reason;
- citation updated;
- confirmed unchanged-in-meaning.

Theo dõi:

- false broken rate;
- false major-change rate;
- network failure rate.

### Repeated use

Một signal mạnh:

> user tiếp tục chạy tool sau 4 tuần mà không phải ép buộc.

### Technical reliability

Target cá nhân hợp lý:

- >98% eligible URLs được classified mỗi scan;
- no unbounded retries;
- scan restart không corrupt DB.

### Meaningful finding rate

Metric quan trọng nhất:

```text
meaningful findings / total alerts reviewed
```

Nếu chỉ 2% alerts hữu ích, normalization/classification chưa đủ tốt.

Không áp dụng cho MVP vì AI không được sử dụng.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, hoàn thành vertical slice:

> Markdown file → extract URLs → fetch → tạo fingerprint → lưu snapshot JSON → chạy lần hai và phát hiện source thay đổi.

Chưa dùng SQLite, EF Core, dashboard hoặc AI.

### Files/components cần tạo

```text
SourcePulse.sln
src/
  SourcePulse.Cli/
    Program.cs
    UrlExtractor.cs
    SourceFetcher.cs
    SourceSnapshot.cs
    Fingerprint.cs
    SnapshotStore.cs
samples/
  sources.md
  snapshots/
tests/
  SourcePulse.Tests/
```

### Setup commands

```bash
dotnet new sln -n SourcePulse

dotnet new console \
  -n SourcePulse.Cli \
  -o src/SourcePulse.Cli

dotnet new xunit \
  -n SourcePulse.Tests \
  -o tests/SourcePulse.Tests

dotnet sln add src/SourcePulse.Cli
dotnet sln add tests/SourcePulse.Tests

dotnet add tests/SourcePulse.Tests reference src/SourcePulse.Cli
```

Optional package cho prototype:

```bash
dotnet add src/SourcePulse.Cli package AngleSharp
```

### Sample Markdown

Tạo `samples/sources.md`:

```markdown
# Sources

- RFC 9110: https://www.rfc-editor.org/rfc/rfc9110.html
- lychee: https://github.com/lycheeverse/lychee
```

### First vertical slice

Implement:

```text
sourcepulse <markdown-file>
```

Prototype logic:

1. Read Markdown file.
2. Regex extract `https://...` URLs.
3. Deduplicate.
4. `HttpClient.GetAsync` từng URL với concurrency tối đa 4.
5. Đọc body nếu content type là HTML/text và body < 2 MB.
6. Normalize cực đơn giản:

```text
HTML → visible-ish text
collapse whitespace
trim
```

7. SHA-256 normalized text.
8. Save:

```json
[
  {
    "url": "https://...",
    "status": 200,
    "finalUrl": "https://...",
    "title": "...",
    "hash": "..."
  }
]
```

vào:

```text
samples/snapshots/latest.json
```

9. Nếu file snapshot cũ tồn tại, compare hash/status/final URL.

### Expected console result

Lần đầu:

```text
2 URLs discovered
2 healthy
Baseline created
```

Lần hai:

```text
2 URLs discovered
1 unchanged
1 changed

CHANGED
https://example...
Old hash: ...
New hash: ...
```

### Integration test local không phụ thuộc internet

Trong cùng session, tạo một fake `HttpMessageHandler` hoặc local test server.

Test flow:

```text
Response 1: "API limit = 100"
Response 2: "API limit = 60"
```

Expected:

```text
hash1 != hash2
status = CHANGED
```

### Verification checklist

- [ ] CLI đọc được một Markdown file.
- [ ] Extract được ít nhất 2 unique URLs.
- [ ] HTTP fetch có timeout.
- [ ] Redirect final URL được lưu.
- [ ] HTML/text tạo được deterministic SHA-256 fingerprint.
- [ ] Snapshot được ghi xuống disk.
- [ ] Lần chạy thứ hai compare với snapshot trước.
- [ ] Có ít nhất một test chứng minh content change được detect.
- [ ] Không cần database.
- [ ] Không cần AI.

### Stop condition

Kết thúc coding session ngay khi có thể chứng minh:

```text
Markdown
  ↓
URL extraction
  ↓
HTTP fetch
  ↓
fingerprint
  ↓
snapshot
  ↓
second-run diff
```

với ít nhất một automated test pass.

Không thêm dashboard, scheduler, GitHub API, semantic AI validation hoặc advanced HTML normalization trong session đầu tiên.
