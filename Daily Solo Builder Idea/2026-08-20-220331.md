# Ý tưởng hôm nay: ActionJanitor — GitHub Actions Artifact & Run Hygiene Auditor

## 1. Tóm tắt ý tưởng

**ActionJanitor** là một web/CLI nhỏ kết nối với GitHub để phát hiện repository đang giữ workflow artifacts/logs lâu hơn cần thiết, workflow runs thất bại lặp lại, artifact quá lớn hoặc retention policy không phù hợp, rồi đưa ra danh sách hành động dọn dẹp có thể kiểm tra trước khi thực thi. Sản phẩm giúp solo developer và nhóm nhỏ giảm việc kiểm tra thủ công trong GitHub Actions và tránh tích lũy dữ liệu CI không cần thiết.

**Quy mô:** Medium. **MVP ước tính:** 5–8 ngày làm ngoài giờ.

## 2. Bài toán thực tế

### Confirmed facts

GitHub cho phép cấu hình thời gian lưu Actions artifacts/logs; mặc định là 90 ngày. Với public repository, retention có thể đặt từ 1–90 ngày; private repository có thể lên tới 400 ngày. GitHub cũng cho phép đặt `retention-days` riêng cho artifact khi dùng `actions/upload-artifact`, và artifact có thể bị xóa trước khi hết hạn để thu hồi storage. Nguồn chính thức: [GitHub Actions retention settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository), [Removing workflow artifacts](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/remove-workflow-artifacts), [Store and share data with workflow artifacts](https://docs.github.com/en/actions/tutorials/store-and-share-data).

GitHub REST API có rate limits; authenticated user thường có primary limit 5,000 requests/hour, đồng thời có secondary limits. GitHub khuyến nghị dùng response headers và conditional requests khi phù hợp. Nguồn: [REST API rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [REST API best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api).

### Observation

GitHub cung cấp từng cơ chế riêng lẻ để xem runs, artifacts, retention và xóa dữ liệu, nhưng một developer quản lý nhiều repository vẫn phải tự tổng hợp câu trả lời cho các câu hỏi như: repo nào đang tích lũy artifact, workflow nào tạo artifact lớn, run thất bại nào đã cũ và có thể dọn, policy nào đang quá rộng.

### Assumption cần kiểm chứng

Solo developer có từ khoảng 5 repository hoạt động trở lên sẽ thấy dashboard tổng hợp và cleanup plan hữu ích hơn việc mở từng repository. Đây là giả định sản phẩm, không phải số liệu thị trường đã xác nhận.

## 3. Người dùng mục tiêu

MVP tập trung vào **developer cá nhân hoặc maintainer quản lý nhiều GitHub repositories có GitHub Actions**.

Họ thường kiểm tra CI trong GitHub UI, đôi khi xóa artifacts/runs bằng tay hoặc đơn giản để mặc định. Pain point chính là không có một góc nhìn nhỏ gọn theo kiểu “cái gì đang tốn chỗ hoặc đáng dọn trước”. Họ sẽ thử ActionJanitor nếu công cụ chỉ cần token quyền tối thiểu, chạy read-only mặc định và đưa ra cleanup plan rõ ràng trước khi xóa.

## 4. Giải pháp đề xuất

Workflow chính:

`GitHub token / GitHub App → chọn repositories → lấy workflow runs + artifacts → chuẩn hóa metadata → áp policy → tạo findings → người dùng review → tùy chọn cleanup`

Input gồm repository, tuổi tối đa của failed runs/artifacts, ngưỡng kích thước artifact và allowlist workflow. Output là dashboard/CLI report gồm `Keep`, `Review`, `Cleanup candidate` cùng lý do cụ thể.

Ví dụ: người dùng scan 12 repo. ActionJanitor phát hiện repo A có 38 artifacts cũ hơn 30 ngày, workflow B tạo artifact 420 MB mỗi lần chạy, repo C vẫn dùng retention mặc định dù artifact chỉ phục vụ debugging ngắn hạn. Công cụ tạo plan; người dùng tick 15 artifacts và xác nhận xóa. Không có auto-delete trong MVP.

**Khác biệt chính:** không cố thay GitHub Actions; nó là lớp “hygiene + policy audit” cross-repository, ưu tiên explain-before-delete.

## 5. Tại sao ý tưởng này đáng làm

Giá trị thực tế xuất hiện ngay với chính developer xây nó: audit các repo cá nhân, workflow thử nghiệm và artifact CI. Về kỹ thuật, dự án luyện GitHub REST API, pagination, rate limiting, idempotency, background jobs, permission minimization và safe destructive operations.

Nó phù hợp solo developer vì domain nhỏ, không cần dataset lớn, không cần scraping và có thể triển khai như CLI trước rồi mới thêm web UI.

Dự án thất bại nếu scan không tạo ra insight tốt hơn GitHub UI hoặc cleanup tiết kiệm quá ít công sức/storage. **Lý do mạnh nhất để không build:** nếu bạn chỉ có 1–2 repo dùng Actions nhẹ, công cụ có thể không mang đủ giá trị so với thao tác thủ công.

## 6. Phạm vi MVP

### Must have

- Authenticate bằng fine-grained PAT nhập qua environment variable.
- Chọn danh sách repository cụ thể.
- Lấy workflow runs và artifacts qua GitHub REST API.
- Hiển thị artifact: repo, workflow/run, size, created/expires time, age.
- Rule engine đơn giản: age, size, run conclusion.
- Sinh cleanup candidates nhưng mặc định read-only.
- Cho phép xóa từng artifact sau explicit confirmation.
- Lưu lịch sử scan và action.

### Should have

- Dashboard tổng hợp theo repo/workflow.
- Dry-run export Markdown/JSON.
- Rate-limit awareness.
- Ignore rules trong `actionjanitor.yml`.
- Scheduled scan.

### Later

- GitHub App multi-user.
- Organization-wide scanning.
- Pull request đề xuất thay `retention-days` trong workflow YAML.
- Cost/storage trend estimation khi có dữ liệu lịch sử đủ tốt.
- Slack/Teams/email notifications.

## 7. Luồng hoạt động

Người dùng cấu hình token và repos → API validate quyền → scan metadata theo pagination → lưu snapshot → rule engine tạo findings → UI/CLI hiển thị plan → user chọn action → backend re-fetch artifact để tránh thao tác trên state cũ → delete → ghi audit log → refresh kết quả.

Failure cases quan trọng: token hết hạn thì dừng scan và báo repository bị ảnh hưởng; rate limit thấp thì checkpoint rồi retry sau; artifact đã bị GitHub xóa thì coi delete là idempotent success; repo mất quyền thì đánh dấu inaccessible thay vì fail toàn batch; GitHub API lỗi tạm thời thì retry có backoff.

## 8. Kiến trúc đề xuất

Dùng **modular monolith**.

- **Frontend:** Vue 3, chỉ cần dashboard + scan detail + confirmation dialog.
- **Backend:** ASP.NET Core Web API, chứa GitHub integration, policy engine và cleanup service.
- **Database:** PostgreSQL lưu repo config, scan snapshots, findings và audit actions.
- **Background worker:** `BackgroundService` cho scan; MVP chưa cần queue riêng.
- **Scheduler:** timer đơn giản hoặc Hangfire khi thêm scheduled scan.
- **Cache:** chưa cần; tận dụng DB và conditional requests sau này.
- **File storage:** không cần vì chỉ lưu metadata, không tải artifact content.
- **Authentication:** MVP single-user/self-hosted; secret/token từ environment/secret store.
- **External API:** GitHub REST API.
- **AI:** không cần.
- **Logging:** OpenTelemetry/structured logging ở mức tối thiểu.
- **Deployment:** Docker Compose gồm app + PostgreSQL trên VPS/mini PC.

Không cần microservices, Kubernetes hay message broker cho MVP.

## 9. Công nghệ đề xuất

**.NET 10 + ASP.NET Core:** .NET 10 là bản LTS hiện hành trong năm 2026 và phù hợp cho API/background processing. Nếu môi trường hiện tại ưu tiên .NET 8 thì MVP vẫn chạy tốt; chỉ nên nâng khi dependency/tooling sẵn sàng.

**EF Core + PostgreSQL:** schema nhỏ, query/reporting thuận tiện. SQLite là lựa chọn đơn giản hơn cho CLI/single-user; chuyển PostgreSQL khi cần concurrent web + worker.

**Vue 3 + Vite:** dashboard nhỏ, nhanh xây. Có thể bỏ frontend hoàn toàn ở tuần đầu và dùng CLI/Swagger.

**HttpClientFactory + System.Text.Json:** đủ cho GitHub REST integration, không cần SDK nặng nếu chỉ dùng vài endpoint.

**Docker Compose:** phù hợp self-host. Nếu số người dùng tăng đáng kể, có thể chuyển app sang Azure Container Apps/App Service và managed PostgreSQL.

**Playwright:** kiểm tra flow scan → review → confirm delete bằng fake GitHub API.

## 10. Thiết kế dữ liệu ban đầu

### RepositoryTarget

Mục đích: repository được audit. Fields: `Id`, `Owner`, `Name`, `IsEnabled`, `LastScanAt`. Một repository có nhiều scan. Không cần lưu token trong entity.

### ScanRun

Fields: `Id`, `StartedAt`, `CompletedAt`, `Status`, `RepositoryCount`, `ErrorCount`. Giữ 90–180 ngày rồi aggregate/xóa tùy nhu cầu.

### ArtifactSnapshot

Fields: `Id`, `ScanRunId`, `RepositoryTargetId`, `GitHubArtifactId`, `Name`, `SizeBytes`, `CreatedAt`, `ExpiresAt`, `WorkflowRunId`, `Expired`. Snapshot cũ có thể purge sau khi tạo trend summary.

### Finding

Fields: `Id`, `ScanRunId`, `Type`, `Severity`, `ArtifactId`, `Reason`, `SuggestedAction`, `Status`.

### CleanupAction

Audit trail cho destructive operation: `Id`, `GitHubArtifactId`, `RequestedAt`, `CompletedAt`, `Result`, `ErrorCode`. Giữ lâu hơn snapshot để truy vết.

## 11. API và tích hợp

### GitHub REST API

Mục đích: đọc repositories/workflow runs/artifacts và xóa artifact khi được xác nhận. Authentication bằng fine-grained PAT ở MVP; cần cấp đúng repository permissions cho endpoint sử dụng. Concern chính là rate limits và quyền destructive. Fallback khi API unavailable: giữ scan trước đó, đánh dấu stale và không cho cleanup dựa trên dữ liệu quá cũ.

GitHub khuyến nghị xử lý `retry-after`, `x-ratelimit-*` headers và exponential backoff khi gặp secondary rate limits. Conditional requests với ETag có thể giảm request tính vào primary rate limit khi nhận `304 Not Modified` trong điều kiện phù hợp. Nguồn: [GitHub REST API best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api).

### GitHub Webhooks — Later

Webhooks có thể gửi event tới server thay vì polling liên tục; GitHub mô tả đây là cơ chế nhận dữ liệu khi event xảy ra. Repository webhook yêu cầu quyền owner/admin để tạo. Vì MVP scan theo yêu cầu nên chưa cần webhook. Nguồn: [About webhooks](https://docs.github.com/en/webhooks/about-webhooks), [Creating webhooks](https://docs.github.com/en/webhooks/using-webhooks/creating-webhooks).

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Các quyết định MVP đều dựa trên metadata và policy deterministic: tuổi artifact, kích thước, trạng thái run, retention, allowlist. Dùng LLM để quyết định xóa artifact sẽ làm tăng rủi ro, latency và khó kiểm chứng mà không đem lại lợi thế tương xứng.

Nếu sau này muốn AI, chỉ nên dùng để giải thích findings hoặc gợi ý policy; mọi destructive action vẫn phải được rule engine + user confirmation kiểm soát.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** chứng minh có dữ liệu đáng dọn. **Tasks:** dùng `gh api` hoặc script nhỏ scan 5–10 repo của chính mình, ghi lại artifact count/size/age và thời gian kiểm tra thủ công. **Output:** sample JSON + 5 findings thật. **Done:** ít nhất một rule tạo insight có thể hành động.

### Phase 1 — Core MVP

**Goal:** vertical slice read-only. **Tasks:** API GitHub client, repo config, artifact scan, rule engine, CLI/API report. **Output:** `scan` trả cleanup candidates. **Done:** scan nhiều repo không cần mở GitHub UI.

### Phase 2 — Reliability

**Goal:** destructive action an toàn. **Tasks:** retry/backoff, rate-limit handling, re-validation, confirmation token, audit log, integration tests. **Output:** xóa artifact có kiểm soát. **Done:** retry/re-run không gây action ngoài ý muốn.

### Phase 3 — Useful expansion

**Goal:** dùng hàng tuần. **Tasks:** Vue dashboard, scheduled scan, Markdown report, ignore policy. **Output:** dashboard cross-repo. **Done:** một scan định kỳ tạo report hữu ích mà không cần thao tác thủ công.

### Phase 4 — Production readiness

**Goal:** self-host ổn định. **Tasks:** Docker, health checks, backup DB, secret management, telemetry, README, restore test. **Output:** deploy reproducible. **Done:** rebuild server từ repo + backup thành công.

## 14. Các bài toán kỹ thuật đáng học

1. **Rate-limit-aware API client:** học pagination, throttling, retry và conditional requests.
2. **Idempotent destructive operations:** xử lý trường hợp artifact đã biến mất hoặc request bị retry.
3. **Policy engine:** tách rule deterministic khỏi orchestration để dễ test và mở rộng.
4. **Long-running scan:** checkpoint theo repository để một lỗi không làm mất toàn bộ tiến trình.
5. **Least-privilege security:** thiết kế read-only mặc định và chỉ mở quyền delete khi người dùng thực sự cần.

## 15. Rủi ro và cách xử lý

**Xóa nhầm artifact:** nguy hiểm nhất. Mitigation: read-only mặc định, preview, re-fetch trước delete, explicit confirmation, allowlist protected workflows; không auto-delete trong MVP.

**Token quá mạnh:** dùng fine-grained token và document quyền tối thiểu; không log token; inject qua secret/environment.

**Rate limit/API dependency:** pagination có kiểm soát, backoff, checkpoint, cache snapshot và scan incremental.

**Scope creep:** không thêm workflow editor, billing analytics, organization governance hay AI vào MVP.

**Insight không đủ giá trị:** validation trước bằng dữ liệu repo thật; nếu chỉ tìm được vài MB artifact không đáng quan tâm thì dừng dự án sớm.

**Maintenance:** GitHub API versioned; cô lập toàn bộ integration sau interface và contract tests.

## 16. Kiểm thử

Unit tests cho rule engine và state transitions; integration tests với fake GitHub HTTP server; E2E bằng Playwright cho dashboard; failure-path tests cho 401/403/404/429/5xx; security tests đảm bảo token không xuất hiện trong log/response.

Năm scenario quan trọng nhất:

1. Artifact cũ + lớn được đánh dấu cleanup candidate đúng rule.
2. Artifact thuộc protected workflow không bao giờ được đề xuất xóa.
3. API trả rate-limit response → scan checkpoint và retry đúng thời điểm/backoff.
4. Artifact bị xóa bên ngoài giữa preview và confirm → action kết thúc idempotently, không crash batch.
5. User chưa confirm → không có DELETE request nào được gửi.

## 17. Cách đo dự án có hữu ích hay không

- **Usage:** số repo được scan ít nhất mỗi tuần.
- **Time saved:** thời gian audit 10 repo trước/sau ActionJanitor.
- **Task completion:** tỷ lệ scan hoàn tất trên tổng scan bắt đầu.
- **Error rate:** tỷ lệ repo scan lỗi và cleanup action lỗi.
- **Repeated use:** có tiếp tục dùng sau 4 tuần hay không.
- **Reliability:** >99% findings có thể trace về metadata/rule cụ thể; mục tiêu này đo bằng test + audit, không phải AI score.
- **Value metric:** số bytes/artifacts được người dùng chủ động cleanup sau review, nhưng không coi “xóa càng nhiều càng tốt” là mục tiêu.

## 18. Khả năng mở rộng

**Realistic:** organization dashboard, GitHub App auth, webhook-assisted incremental updates, policy-as-code, PR tự động đề xuất `retention-days`, trend theo workflow, Slack/Teams digest, CLI standalone, cloud-hosted và self-hosted editions.

**Speculative:** anomaly detection dự báo workflow nào sắp tạo storage spike hoặc benchmark retention policy giữa nhiều organization. Chỉ làm khi đã có dataset sử dụng thực tế.

Open-source core khá hợp lý vì policy engine và GitHub integration có giá trị học tập; hosted multi-user version có thể là lớp thương mại sau này.

## 19. Mô hình giá trị hoặc kiếm tiền

Phù hợp nhất với **Personal utility + Open-source project + Portfolio project**. Với solo developer, giá trị ban đầu nằm ở việc tự quản lý CI hygiene và thể hiện năng lực API integration, background processing, reliability và safe automation.

SaaS chỉ thực tế nếu validation cho thấy nhóm nhỏ thực sự muốn cross-repository governance. Khi đó có thể bán hosted organization dashboard hoặc policy reporting; chưa nên thiết kế billing/multi-tenancy trong MVP.

## 20. Việc cần làm ngay hôm nay

**Phiên đầu: 60–120 phút. Mục tiêu:** tạo CLI scan một repository và in artifacts theo size/age.

### Setup

```bash
mkdir ActionJanitor
cd ActionJanitor
dotnet new sln -n ActionJanitor
dotnet new console -n ActionJanitor.Cli -o src/ActionJanitor.Cli
dotnet new xunit -n ActionJanitor.Tests -o tests/ActionJanitor.Tests
dotnet sln add src/ActionJanitor.Cli tests/ActionJanitor.Tests
dotnet add tests/ActionJanitor.Tests reference src/ActionJanitor.Cli
```

Tạo:

- `GitHubOptions.cs`
- `GitHubArtifactsClient.cs`
- `ArtifactInfo.cs`
- `ArtifactPolicy.cs`
- `Program.cs`
- `ArtifactPolicyTests.cs`

Đọc token từ `GITHUB_TOKEN`, owner/repo từ command-line args. Implement một GET tới GitHub Actions artifacts endpoint, map tối thiểu `id`, `name`, `size_in_bytes`, `created_at`, `expires_at`, sau đó tính `AgeDays` và in bảng text. Thêm rule đầu tiên: `AgeDays >= 30 && SizeBytes >= 50 MB => Review`.

### Expected result

Chạy:

```bash
GITHUB_TOKEN=... dotnet run --project src/ActionJanitor.Cli -- hakodev2k Daily-OpenAI
```

CLI phải hiển thị artifact metadata thật hoặc thông báo rõ repository không có artifact; unit test phải chứng minh rule 30 ngày/50 MB hoạt động.

### Verification checklist

- [ ] Token không hard-code và không xuất hiện trong log.
- [ ] HTTP non-success được hiển thị rõ, không swallow exception.
- [ ] Pagination metadata được nhận diện dù phiên đầu chỉ cần xử lý page đầu.
- [ ] Có ít nhất 2 unit tests cho `ArtifactPolicy`.
- [ ] Output có `Name`, `SizeMB`, `AgeDays`, `Decision`.
- [ ] Không có DELETE endpoint trong code phiên đầu.

**Stop condition:** dừng ngay khi một repository thật có thể được scan end-to-end và CLI tạo quyết định `Keep/Review` deterministic. Không làm dashboard, database hay scheduler trong phiên đầu.
