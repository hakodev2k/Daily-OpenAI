# Ý tưởng hôm nay: LinkVault Sentinel — Kho lưu trữ bookmark chống “link rot” cho tài liệu kỹ thuật

## 1. Tóm tắt ý tưởng

**LinkVault Sentinel** là một ứng dụng self-hosted giúp developer lưu các đường link quan trọng, theo dõi xem nội dung còn tồn tại hay đã thay đổi, và tự động tạo snapshot cục bộ để tài liệu vẫn đọc được ngay cả khi website bị xóa, đổi URL hoặc sửa nội dung. Sản phẩm tập trung vào **knowledge preservation** cho các tài liệu kỹ thuật, bài blog, issue, hướng dẫn triển khai và tài liệu tham khảo mà developer thường bookmark nhưng hiếm khi kiểm tra lại cho đến lúc cần dùng.

- **Project size:** Medium
- **Estimated MVP time:** 2–3 tuần làm ngoài giờ
- **Giá trị cốt lõi:** biến bookmark từ một danh sách URL mong manh thành một kho kiến thức có trạng thái, lịch sử thay đổi và bản lưu offline.

## 2. Bài toán thực tế

### Confirmed facts

HTTP hỗ trợ các cơ chế conditional request như `ETag`, `If-None-Match`, `Last-Modified` và `If-Modified-Since`, cho phép client kiểm tra tài nguyên có thay đổi hay không mà không nhất thiết tải lại toàn bộ nội dung. Đây là nền tảng phù hợp để xây một hệ thống kiểm tra link tiết kiệm bandwidth. Nguồn: [MDN — HTTP conditional requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Conditional_requests).

SingleFile là một dự án open-source có browser extension và CLI, có thể lưu một trang web hoàn chỉnh thành một file HTML duy nhất. Bản CLI có thể chạy headless qua Chrome/Chromium và hỗ trợ Docker. Nguồn: [SingleFile CLI](https://github.com/gildas-lormeau/single-file-cli), [SingleFile](https://github.com/gildas-lormeau/SingleFile).

SingleFile cũng lưu ý rằng một số thành phần tương tác như dynamic map, carousel hoặc JavaScript-driven UI có thể không hoạt động đầy đủ trong bản lưu offline, vì mặc định tool có thể loại bỏ script để giữ snapshot ổn định hơn. Nguồn: [SingleFile FAQ](https://github.com/gildas-lormeau/SingleFile/blob/master/faq.md).

### Observation

Bookmark manager truyền thống thường chỉ lưu URL, title và folder/tag. Nếu nội dung nguồn biến mất hoặc thay đổi mạnh, bookmark vẫn tồn tại nhưng giá trị kiến thức thực tế đã mất.

Công cụ web archiving như SingleFile đã giải quyết tốt bài toán “lưu một trang”. Tuy nhiên, nó không tự đóng vai trò như một **monitoring workflow** cho hàng trăm bookmark: kiểm tra định kỳ, phân loại trạng thái, xác định trang đã thay đổi đáng kể hay chưa, và ưu tiên link nào cần xem lại.

### Analysis

Đây là một khoảng trống phù hợp cho solo project: không cần phát minh lại browser engine hay archive format. MVP có thể orchestration các primitive sẵn có:

1. HTTP conditional requests cho link đơn giản.
2. HTML text extraction + content hashing cho thay đổi.
3. SingleFile CLI cho snapshot đầy đủ.
4. PostgreSQL cho metadata.
5. Background job cho lịch kiểm tra.

### Assumption cần validate

- Một developer có khoảng 100–500 bookmark kỹ thuật quan trọng sẽ thấy giá trị nếu tool tự báo “12 link đã chết, 7 tài liệu thay đổi đáng kể, 3 bài đã được lưu offline trước khi biến mất”.
- Người dùng chấp nhận self-host tool nếu snapshot nằm hoàn toàn trong máy/VPS của họ.
- Giá trị cao nhất không nằm ở việc “lưu mọi website”, mà ở nhóm link người dùng **chủ động đánh dấu là đáng bảo tồn**.

## 3. Người dùng mục tiêu

### Primary user

Developer hoặc technical lead thường xuyên lưu tài liệu kỹ thuật từ:

- Microsoft Learn
- GitHub issues/discussions
- engineering blogs
- Stack Overflow
- vendor documentation
- migration guides
- architecture articles
- release notes
- personal technical blogs

### Context of use

Người dùng có nhiều bookmark được tích lũy trong vài năm. Một số tài liệu chỉ được mở lại sau vài tháng, ví dụ khi gặp lại lỗi cũ hoặc cần migrate một hệ thống legacy.

### Main pain point

Đến lúc cần dùng lại thì:

- URL trả `404`, `410` hoặc redirect sang trang khác.
- Blog bị xóa.
- Documentation đã update khiến nội dung cũ không còn.
- Page vẫn tồn tại nhưng đoạn hướng dẫn đã bị chỉnh sửa.
- Người dùng không nhớ phiên bản nào đã từng đọc.

### Current workaround

- Browser bookmark.
- Copy link vào Notion/Obsidian.
- Save PDF thủ công.
- Screenshot.
- Copy/paste đoạn quan trọng vào note.
- Dùng SingleFile thủ công.

Các cách này đều có một vấn đề: người dùng phải nhớ **lưu trước khi nguồn biến mất**.

### Vì sao họ sẽ thử LinkVault Sentinel

Tool tự chuyển từ mô hình:

> “Tôi hy vọng link này còn sống khi cần dùng.”

sang:

> “Tôi biết link này đang ở trạng thái nào và đã có bản offline nếu nguồn biến mất.”

## 4. Giải pháp đề xuất

Người dùng thêm URL vào LinkVault Sentinel bằng UI hoặc API.

Hệ thống sẽ:

1. Normalize URL.
2. Fetch metadata.
3. Lưu `ETag`, `Last-Modified`, status code và content hash nếu có.
4. Extract readable text.
5. Tạo snapshot HTML bằng SingleFile CLI.
6. Định kỳ kiểm tra lại.
7. Phân loại thay đổi:
   - unchanged
   - minor change
   - major content change
   - redirected
   - unavailable
   - permanently gone
8. Khi link biến mất, UI vẫn cho mở bản archived snapshot gần nhất.

### Input

- URL
- optional title
- tags
- importance level: Normal / Important / Critical
- check frequency

### Processing

- HTTP HEAD/GET có conditional headers.
- DOM/text normalization.
- SHA-256 hash.
- Optional text similarity để tránh báo thay đổi do timestamp/banner.
- Snapshot qua SingleFile CLI.

### Output

Mỗi bookmark có:

- current status
- last checked
- last changed
- latest snapshot
- snapshot history
- diff summary
- source URL
- offline open button

### What is automated

- link health check
- change detection
- retry
- snapshot creation
- retention cleanup
- notification

### What remains under user control

- URL nào đáng monitor
- tần suất check
- snapshot nào được pin giữ vĩnh viễn
- domain nào được phép snapshot
- có theo redirect mới hay không

### Key differentiator

Không cạnh tranh trực tiếp với bookmark manager hoặc web clipper.

**LinkVault Sentinel = bookmark monitor + personal web archive + change history.**

### Ví dụ end-to-end

Hà bookmark một blog:

`https://example.com/dotnet-migration-guide`

Ngày đầu:

- HTTP 200
- title: “Migrating ASP.NET Core 8 to 10”
- content hash `A1...`
- snapshot `snapshot-001.html`

Ba tháng sau:

- server trả HTTP 301 sang `/new-guide`
- tool ghi nhận redirect
- follow redirect theo policy
- snapshot mới được tạo

Sáu tháng sau:

- URL mới trả 404

Dashboard hiển thị:

```text
Status: Source unavailable
Last live: 2027-01-12
Latest archive: 2027-01-12
Snapshots: 4
Open archived copy
```

Tài liệu vẫn đọc được offline.

## 7. Luồng hoạt động

### Main flow

User adds URL
→ URL validation
→ DNS/IP safety validation
→ HTTP request
→ redirect policy
→ retrieve headers/body
→ normalize readable content
→ calculate content hash
→ store metadata
→ run SingleFile snapshot
→ persist snapshot record
→ display result
→ schedule next check

### Subsequent check

Scheduler selects due bookmark
→ sends conditional request using `If-None-Match` or `If-Modified-Since`
→ server returns `304 Not Modified`
→ update `LastCheckedAt`
→ no snapshot required

Nếu server trả `200`:

→ parse content
→ hash normalized text
→ compare previous hash
→ if unchanged: no new snapshot
→ if changed: create new snapshot
→ record change event

### Failure flow: timeout

Timeout
→ retry với exponential backoff
→ nếu vẫn lỗi: `TemporarilyUnavailable`
→ giữ nguyên snapshot cũ
→ không đánh dấu link dead ngay lập tức

### Failure flow: 404

Lần đầu 404
→ status `SuspectedGone`
→ retry sau 24 giờ

Nhiều lần liên tiếp 404
→ `Unavailable`
→ notify user
→ archive vẫn giữ nguyên

### Redirect flow

301/308
→ record redirect
→ follow redirect nếu domain policy cho phép
→ user có thể chọn update canonical URL

### Login-required page

401/403
→ không cố bypass authentication
→ trạng thái `AuthRequired`
→ MVP không snapshot trang private cần session.

## 9. Công nghệ đề xuất

### .NET 10

Dùng .NET 10 LTS cho API và worker.

**Vì sao phù hợp:** supported LTS, HttpClient ecosystem tốt, background services ổn định.

**Simpler alternative:** .NET 8 nếu môi trường hiện tại đã chuẩn hóa ở version này.

**Outgrow:** hầu như không phải vấn đề; scale chủ yếu đến từ worker/storage.

### ASP.NET Core

Cho REST API + static SPA hosting + health checks.

### EF Core + PostgreSQL

Metadata quan hệ nhỏ và rõ ràng.

**Alternative:** SQLite cho bản personal-only.

Thực tế, SQLite là lựa chọn rất hợp lý cho prototype đầu tiên. PostgreSQL chỉ nên dùng nếu muốn chạy multi-container và chuẩn bị multi-user.

### Hangfire

Cho recurring job và retry.

**Alternative đơn giản hơn:** `BackgroundService` + DB query theo `NextCheckAt`.

Nếu muốn MVP cực nhỏ, chọn `BackgroundService` trước.

### HttpClientFactory

Cần kiểm soát:

- timeout
- redirect
- headers
- retry
- user agent

### AngleSharp hoặc HtmlAgilityPack

Parse HTML và normalize DOM/text.

### Mozilla Readability port / custom extraction

Có thể dùng readability-style extraction hoặc rule đơn giản để bỏ:

- nav
- script
- footer
- ads

MVP không cần hoàn hảo.

SingleFile CLI có thể lưu complete web page thành single HTML file và hỗ trợ chạy qua Chromium/headless. Nguồn: [SingleFile CLI](https://github.com/gildas-lormeau/single-file-cli).

### Docker

## 11. API và tích hợp

### HTTP websites

Purpose: nguồn dữ liệu chính.

Authentication: public URL only ở MVP.

Rate limit concern:

Tool phải tự rate-limit theo domain, ví dụ không gửi hàng trăm request đồng thời.

Privacy concern:

URL bookmark có thể tiết lộ interest hoặc thông tin dự án nội bộ. Không gửi URL cho third-party service mặc định.

Fallback:

Nếu HEAD không hoạt động, dùng GET.

### HTTP Conditional Requests

Dùng:

```http
If-None-Match: "etag-value"
If-Modified-Since: Sat, 15 Aug 2026 10:00:00 GMT
```

MDN xác nhận `ETag` và `Last-Modified` là validator chuẩn cho conditional requests. Nguồn: [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Conditional_requests).

Fallback:

Nếu server không trả validator thì dùng content hash.

### SingleFile CLI

Purpose: archive page thành một HTML file.

Authentication: none cho public page.

Cost: free/open-source; local CPU/storage cost.

Privacy: chạy local.

Fallback:

Nếu SingleFile fail:

- lưu raw HTML
- screenshot optional
- status snapshot `Partial`

### Telegram Bot API

Purpose: báo link chết hoặc changed.

Authentication: bot token.

Cost: thông thường không phải cost chính cho quy mô personal.

Privacy: chỉ gửi title + URL + status, không gửi archived content.

Fallback: notification trong dashboard.

### Browser bookmark import

Netscape Bookmark HTML format có thể parse local, không cần cloud API.

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

MVP không cần AI.

### Deterministic responsibilities

Normal code xử lý tốt hơn cho:

- HTTP status
- redirect
- ETag
- Last-Modified
- content hash
- HTML diff
- snapshot
- scheduling
- retention

### AI task có thể thêm sau

Khi một trang thay đổi mạnh, AI có thể tạo:

```json
{
  "changeType": "technical-update",
  "summary": "The article now recommends .NET 10 instead of .NET 8.",
  "importantChanges": [
    "Target framework changed",
    "Deployment command updated"
  ]
}
```

### Context

Chỉ gửi:

- extracted old text
- extracted new text
- diff chunks

Không gửi cookie hoặc raw headers chứa credential.

### Validation

AI summary chỉ là explanatory metadata.

Source of truth vẫn là deterministic diff.

### Fallback

Nếu AI lỗi:

show raw text diff.

### Risks

- token cost với bài dài
- latency
- privacy
- hallucinated interpretation

Do đó không nên đưa vào Phase 1.

## 14. Các bài toán kỹ thuật đáng học

### 1. HTTP caching semantics

Không chỉ biết `GET`, mà hiểu:

- ETag
- weak/strong validators
- Last-Modified
- 304
- redirect
- cache headers

Skill nâng cấp: HTTP protocol reasoning.

### 2. Reliable background processing

Hundreds of bookmarks không thể scan bằng một vòng `foreach` ngây thơ.

Cần học:

- retries
- backoff
- timeouts
- concurrency limits
- job idempotency

Skill nâng cấp: production background workers.

### 3. Content normalization

Trang có thể thay đổi mỗi request vì:

- timestamp
- ads
- recommendation widgets
- analytics markup

Nếu hash raw HTML, false positive sẽ rất cao.

Cần normalize readable content trước hash.

Skill nâng cấp: data canonicalization và signal/noise separation.

### 4. Safe URL fetching / SSRF prevention

Self-host service nhận URL từ user có nguy cơ bị lợi dụng để fetch:

```text
http://localhost
http://169.254.169.254
private network services
```

Cần validate DNS/IP và redirect destination.

Skill nâng cấp: server-side URL security.

### 5. Storage lifecycle

Snapshot sẽ tăng dần theo thời gian.

Cần retention policy, deduplication và quota.

Skill nâng cấp: operational storage design.

## 15. Rủi ro và cách xử lý

### Technical complexity: Dynamic websites

Risk:

Single-page apps hoặc content lazy-loaded có thể snapshot không đầy đủ.

Mitigation:

- classify snapshot quality
- cho user manual recapture
- timeout configurable
- không hứa archive hoàn hảo mọi website

### Scope expansion

Risk:

Dễ biến thành:

- Pocket clone
- Notion clone
- search engine
- crawler
- Wayback Machine

Mitigation:

MVP chỉ trả lời ba câu hỏi:

1. Link còn sống không?
2. Nội dung có thay đổi đáng kể không?
3. Tôi có bản offline không?

### Data privacy

Risk:

Snapshot có thể chứa nội dung nhạy cảm.

Mitigation:

MVP chỉ public URLs.

Không archive authenticated pages.

### Security / SSRF

Risk cao vì server fetch arbitrary URL.

Mitigation:

Block:

- localhost
- RFC1918 ranges
- link-local
- metadata endpoints
- non-http schemes

Revalidate IP sau redirect.

### API dependency

Không phụ thuộc API chính ngoài website nguồn.

SingleFile là local dependency nhưng có thể được adapter hóa.

### Unreliable external data

Website đôi khi timeout.

Không đánh dấu `Gone` chỉ từ một lần lỗi.

### Cost

Chi phí chính:

- disk
- bandwidth
- CPU Chromium

Mitigation:

- snapshot only on change
- retention
- max file size
- daily job budget

### Legal / platform restrictions

Không phải mọi website đều cho phép redistributing content.

Mitigation:

- product mặc định là private personal archive
- không public-share snapshot
- tôn trọng authentication/paywall
- optional robots/site policy review trước commercial SaaS

### Licensing

SingleFile CLI là AGPL-3.0.

Nếu sản phẩm thương mại tích hợp sâu hoặc modify/distribute code, cần legal/license review.

Architecture nên có interface:

```csharp
IPageArchiver
```

để thay implementation nếu cần.

### User adoption

Risk:

Người dùng không muốn maintain thêm một self-hosted service.

Mitigation:

Docker Compose one-command install.

### Maintenance burden

Chromium/SingleFile thay đổi theo thời gian.

Mitigation:

pin version và upgrade có kiểm thử.

```text

```

### Data-quality tests

Hai HTML khác nhau chỉ ở timestamp phải normalize thành cùng meaningful hash nếu rule hỗ trợ.

### 5 test quan trọng nhất

1. **Conditional request:** server trả ETag; check thứ hai trả 304; hệ thống không tạo snapshot mới.
2. **Real content change:** body thay đổi; hash khác; ChangeEvent + snapshot mới được tạo.
3. **Temporary failure:** timeout 2 lần rồi success; bookmark không bị đánh dấu Gone.
4. **SSRF:** URL redirect từ public domain sang `127.0.0.1`; request bị chặn.
5. **Archive fallback:** source trả 404 nhưng snapshot cũ vẫn mở được.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong 60–120 phút, tạo một vertical slice chứng minh core technical hypothesis:

> Một URL có thể được fetch, normalized, hashed, lưu metadata, rồi check lần hai để biết nội dung đã thay đổi hay chưa.

Chưa cần SingleFile, UI, scheduler hoặc database thật.

### Files/components cần tạo

```text
LinkVault.sln
src/LinkVault.Api/
tests/LinkVault.Tests/

src/LinkVault.Api/Monitoring/UrlMonitor.cs
src/LinkVault.Api/Monitoring/UrlCheckResult.cs
src/LinkVault.Api/Monitoring/ContentNormalizer.cs
src/LinkVault.Api/Program.cs
```

### Setup commands

```bash
mkdir LinkVault
cd LinkVault

dotnet new sln -n LinkVault

dotnet new webapi -n LinkVault.Api -o src/LinkVault.Api
dotnet new xunit -n LinkVault.Tests -o tests/LinkVault.Tests

dotnet sln add src/LinkVault.Api/LinkVault.Api.csproj
dotnet sln add tests/LinkVault.Tests/LinkVault.Tests.csproj

dotnet add tests/LinkVault.Tests/LinkVault.Tests.csproj reference src/LinkVault.Api/LinkVault.Api.csproj
```

Optional HTML parser:

```bash
dotnet add src/LinkVault.Api package AngleSharp
```

### First vertical slice

Endpoint:

```http
POST /api/check
Content-Type: application/json

{
  "url": "https://example.com"
}
```

Response:

```json
{
  "url": "https://example.com",
  "statusCode": 200,
  "finalUrl": "https://example.com/",
  "etag": null,
  "lastModified": null,
  "contentLength": 1256,
  "contentHash": "...",
  "checkedAt": "2026-08-17T07:01:00Z"
}
```

### Minimal `UrlMonitor` behavior

1. Parse URL.
2. Allow only `http`/`https`.
3. Send GET.
4. Read final URL.
5. Read ETag/Last-Modified.
6. Parse visible-ish text.
7. Normalize whitespace.
8. SHA-256 normalized text.
9. Return result.

### Content hash snippet

```csharp
var bytes = Encoding.UTF8.GetBytes(normalizedText);
var hash = Convert.ToHexString(SHA256.HashData(bytes));
```

### Test đầu tiên

Dùng custom `HttpMessageHandler` hoặc local `TestServer`.

Case:

```text
HTML A:
<h1>.NET Guide</h1>
<p>Hello world</p>

HTML B:
<h1>.NET Guide</h1>
<p>Hello world</p>
```

Expected:

```text
Hash A == Hash B
```

Sau đó thay body:

```text
Hello .NET 10
```

Expected:

```text
Hash A != Hash B
```

### Expected visible result

Chạy:

```bash
dotnet run --project src/LinkVault.Api
```

Gọi endpoint với một URL public và nhận JSON có content hash.

Gọi lại cùng URL và thấy hash ổn định nếu content không đổi.

### Verification checklist

- [ ] Project build thành công.
- [ ] Endpoint từ chối scheme ngoài HTTP/HTTPS.
- [ ] URL hợp lệ trả status code.
- [ ] Response có final URL.
- [ ] Response có SHA-256 hash.
- [ ] Hai nội dung giống nhau cho cùng hash.
- [ ] Nội dung thay đổi cho hash khác.
- [ ] Timeout có `CancellationToken`.
- [ ] Không log full HTML body.

### Stop condition

Dừng coding session khi:

> Có thể chứng minh bằng test rằng hệ thống phân biệt được “same meaningful content” và “changed content” cho một URL.

Không thêm database, scheduler, SingleFile, Docker, Vue hoặc AI trước khi vertical slice này chạy ổn.
