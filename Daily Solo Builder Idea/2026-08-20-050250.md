# Ý tưởng hôm nay: LicenseLens — Dependency License & Compliance Drift Guard

## 1. Tóm tắt ý tưởng

LicenseLens là một developer tool self-hosted giúp quét dependency của dự án .NET, tạo snapshot license theo từng phiên bản package, phát hiện khi dependency mới hoặc dependency transitively introduced làm thay đổi risk profile, rồi xuất báo cáo rõ ràng trước khi merge/deploy. Công cụ nhắm tới solo developer và team nhỏ muốn kiểm soát license drift mà không cần mua một nền tảng software-composition-analysis lớn.

- Người dùng chính: backend developer hoặc solo SaaS developer dùng NuGet và có nhiều dependency trực tiếp/transitive.
- Bài toán chính: package update có thể kéo theo license mới hoặc dependency transitively changed nhưng developer chỉ nhìn version/vulnerability mà bỏ sót license implication.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

### Confirmed facts

NuGet package metadata có trường `licenseExpression`; giá trị này theo cú pháp license expression của NuGet/SPDX. NuGet cũng hỗ trợ package dùng license file thay vì expression.

Nguồn chính thức:

- https://learn.microsoft.com/en-us/nuget/api/registration-base-url-resource
- https://learn.microsoft.com/en-us/nuget/reference/nuspec
- https://learn.microsoft.com/en-us/nuget/nuget-org/licenses.nuget.org

GitHub Dependency Graph có thể hiển thị version, license, manifest và vulnerability information của dependency; GitHub Dependency Review có thể phân tích dependency thay đổi trong pull request. Dependency Review Action cũng hỗ trợ policy kiểu `allow-licenses` hoặc `deny-licenses`.

Nguồn chính thức:

- https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-graph
- https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-dependency-changes-in-a-pull-request
- https://docs.github.com/en/code-security/tutorials/secure-your-dependencies/customize-dependency-review-action

### Observation

Tooling hiện có đã giải quyết khá tốt bài toán “dependency mới có vulnerability/license gì?”, đặc biệt khi dùng GitHub. Khoảng trống phù hợp cho một solo project là workflow local/self-hosted tập trung vào:

- snapshot dependency graph theo thời gian;
- diff license giữa hai lần restore;
- giải thích dependency nào kéo dependency transitively vào;
- policy riêng cho từng project;
- xử lý package không có SPDX expression rõ ràng;
- xuất evidence để developer review thay vì chỉ pass/fail CI.

### Assumption cần kiểm chứng

Developer của project nhỏ có nhu cầu “biết dependency update này đã thay đổi license surface như thế nào?” nhưng không muốn triển khai platform SCA phức tạp hoặc phụ thuộc hoàn toàn vào GitHub-hosted workflow.

### Cách xử lý hiện tại

Developer thường:

- đọc license trên NuGet.org thủ công;
- xem `dotnet list package --include-transitive`;
- dựa vào GitHub Dependency Review;
- grep package metadata;
- dùng spreadsheet/checklist khi chuẩn bị release;
- hoặc chỉ kiểm tra vulnerability mà bỏ qua license.

Vấn đề là việc review thủ công trở nên chậm khi có nhiều dependency transitively introduced, và rất khó biết “license surface đã thay đổi từ release trước ở điểm nào”.

## 3. Người dùng mục tiêu

**Primary user:** một .NET developer duy trì ứng dụng SaaS nhỏ, API thương mại hoặc sản phẩm cá nhân có nhiều NuGet packages.

### Context of use

Người dùng thường update package hàng tuần/tháng bằng Dependabot, Renovate hoặc thủ công, sau đó cần biết update đó có kéo dependency/license mới vào hay không.

### Main pain point

Không có một diff đơn giản theo kiểu:

```text
Before
MIT: 42 packages
Apache-2.0: 8 packages
UNKNOWN: 1 package

After
MIT: 43 packages
Apache-2.0: 8 packages
GPL-3.0-only: 1 package   <-- NEW
UNKNOWN: 1 package
```

và quan trọng hơn là biết package trực tiếp nào tạo ra thay đổi đó.

### Current workaround

Mở NuGet pages, dependency tree, GitHub dependency review hoặc file lock rồi tự đối chiếu.

### Lý do họ thử LicenseLens

Chạy một command local:

```bash
licenselens scan
```

rồi nhận được report deterministic trước khi commit hoặc merge.

## 4. Giải pháp đề xuất

LicenseLens hoạt động như một dependency snapshot/diff engine.

### Main workflow

User chọn solution/project
→ tool đọc dependency graph sau restore
→ resolve direct + transitive packages
→ lấy license metadata
→ normalize SPDX/license state
→ áp policy
→ lưu snapshot
→ so với baseline trước
→ xuất diff + violation report.

### Input

- `.sln` hoặc `.csproj`.
- `project.assets.json` sau restore.
- Optional policy file `licenselens.yml`.
- Optional baseline snapshot.

### Processing

1. Parse resolved dependency graph từ `obj/project.assets.json`.
2. Xác định direct/transitive dependency.
3. Query NuGet registration metadata khi local cache chưa có metadata.
4. Normalize:
   - SPDX expression;
   - embedded license file;
   - legacy URL;
   - unknown/missing.
5. Build dependency paths.
6. So sánh snapshot hiện tại với baseline.
7. Evaluate policy.

### Output

- Console summary.
- Markdown report.
- JSON report cho CI.
- Exit code khác `0` khi có policy violation.

### User control

Tool **không tự quyết định license nào “tốt/xấu”**. User định nghĩa policy theo project.

Ví dụ:

```yaml
allowed:
  - MIT
  - Apache-2.0
  - BSD-2-Clause

review_required:
  - LGPL-2.1-only
  - UNKNOWN

blocked:
  - GPL-3.0-only
```

### Key differentiator

Không chỉ scan trạng thái hiện tại. Core value là:

> **License drift between dependency snapshots + dependency path evidence.**

### Ví dụ end-to-end

Developer update `Some.Client` từ 4.2 lên 5.0.

LicenseLens chạy và thấy:

```text
NEW REVIEW REQUIRED
Package: Some.Native.Helper 2.0.0
License: LGPL-2.1-only
Type: Transitive
Introduced by:
MyApp -> Some.Client 5.0.0 -> Some.Native.Helper 2.0.0

Baseline: absent
Current: present
```

Developer có thể review trước khi package update được merge.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Có thể dùng cho mọi .NET project cá nhân ngay cả khi chỉ có một người dùng. Mỗi lần update package, tool tạo thêm safety net bên cạnh vulnerability scan.

### Technical learning value

Dự án có các bài toán thú vị:

- dependency graph resolution;
- NuGet metadata API;
- SPDX expression parsing;
- caching;
- deterministic snapshot/diff;
- CLI design;
- CI exit codes;
- policy engine.

### Phù hợp solo developer

MVP không cần account, payment, cloud infrastructure hay frontend. Một CLI + local SQLite/cache đã đủ để chứng minh value.

### Useful even with few users

Ngay cả chỉ dùng trong các repository cá nhân, nó vẫn tạo release evidence và tránh việc phải kiểm tra license thủ công.

### Điều gì làm dự án thất bại

- GitHub Dependency Review đã đủ cho target user.
- License metadata thực tế quá thiếu hoặc ambiguous để report đáng tin.
- User không quan tâm license compliance ở project nhỏ.

### Lý do mạnh nhất để không build

Nếu workflow của user đã hoàn toàn nằm trên GitHub và Dependency Review Action đáp ứng đủ policy, LicenseLens có thể chỉ tạo thêm một lớp tooling không cần thiết.

## 7. Luồng hoạt động

### Normal flow

User chạy:

```bash
dotnet restore
licenselens scan MyApp.csproj --baseline baseline.json
```

→ validate `project.assets.json`
→ parse graph
→ metadata cache lookup
→ fetch metadata còn thiếu
→ normalize license
→ evaluate policy
→ diff baseline
→ write report
→ return exit code.

### First-run flow

Không có baseline
→ scan current graph
→ tạo report
→ user review
→ chạy `licenselens baseline save`
→ snapshot trở thành baseline.

### Metadata unavailable

NuGet API timeout
→ dùng cache nếu có
→ nếu không có cache, mark `METADATA_UNAVAILABLE`
→ không silently coi là allowed.

### License missing

Package không có expression rõ ràng
→ mark `UNKNOWN` hoặc `LICENSE_FILE`
→ đưa vào manual review theo policy.

### Multi-target framework

Package graph khác giữa `net10.0` và target khác
→ MVP report theo từng target framework, không merge mù hai graph.

## 11. API và tích hợp

### NuGet V3 Registration API

**Purpose:** đọc package metadata, bao gồm `licenseExpression` khi có.

**Authentication:** public NuGet.org metadata không yêu cầu credential cho basic lookup.

**Cost/rate-limit concern:** không giả định unlimited throughput; dùng local cache, bounded concurrency và retry có backoff.

**Privacy:** package IDs/versions của private project có thể tiết lộ dependency choices nếu gửi ra ngoài. MVP chỉ query package identifiers cần thiết.

**Fallback:** dùng local NuGet package metadata/cache; nếu không xác định được thì mark unknown thay vì đoán.

Nguồn:

https://learn.microsoft.com/en-us/nuget/api/registration-base-url-resource

### Local NuGet assets

**Purpose:** lấy graph đã resolve chính xác cho project.

**Authentication:** không cần.

**Cost:** local only.

**Fallback:** yêu cầu user chạy `dotnet restore` trước.

### GitHub Dependency Review — optional later

**Purpose:** so sánh kết quả LicenseLens với GitHub-native dependency workflow hoặc dùng như CI complement.

**Authentication:** tùy GitHub environment.

**Fallback:** CLI vẫn hoạt động độc lập.

Nguồn:

https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-dependency-changes-in-a-pull-request

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem cần deterministic evidence:

- package nào;
- version nào;
- license expression nào;
- dependency path nào;
- policy nào bị vi phạm.

AI không nên quyết định license compliance vì đây là domain có legal implication và hallucination không chấp nhận được.

Nếu mở rộng sau này, AI chỉ có thể optional cho việc **tóm tắt human-readable report**, nhưng quyết định pass/fail phải do policy engine deterministic thực hiện.

## 14. Các bài toán kỹ thuật đáng học

### 1. Dependency graph reconstruction

Học cách chuyển NuGet restore artifacts thành graph đáng tin, bao gồm transitive edges và target-framework-specific resolution.

### 2. Deterministic diff

Snapshot phải stable để cùng graph không tạo noise do ordering/timestamp. Kỹ năng này hữu ích cho config diff, schema diff và infrastructure tooling.

### 3. Policy engine

Tách evidence khỏi decision. Scanner chỉ thu facts; policy quyết định allowed/review/blocked.

### 4. API rate limiting & caching

Metadata lookup cho hàng trăm package cần bounded concurrency, retry và cache hợp lý.

### 5. Ambiguous metadata handling

Tool phải biết khi nào **không biết**, thay vì biến missing metadata thành một kết luận giả.

## 15. Rủi ro và cách xử lý

### Legal interpretation risk

**Risk:** user hiểu tool như tư vấn pháp lý.

**Mitigation:** LicenseLens chỉ cung cấp metadata/policy automation; không tuyên bố license tương thích pháp lý. Documentation phải ghi rõ cần legal review khi cần.

### Incomplete metadata

**Risk:** package dùng custom license file hoặc metadata cũ.

**Mitigation:** `UNKNOWN`/`LICENSE_FILE` là first-class state; không tự map bằng phỏng đoán.

### False confidence

**Risk:** report xanh nhưng package có điều khoản ngoài SPDX metadata.

**Mitigation:** report rõ source và confidence; policy có `review_required`.

### Scope creep

**Risk:** biến thành full SCA platform.

**Mitigation:** MVP chỉ .NET + NuGet + license drift.

### NuGet dependency

**Risk:** external metadata unavailable.

**Mitigation:** local cache, restore assets, graceful unknown state.

### User adoption

**Risk:** developer thấy GitHub Dependency Review đã đủ.

**Mitigation:** validate differentiator “local baseline drift + evidence + offline-ish workflow” trước khi xây dashboard.

## 16. Kiểm thử

### Strategy

- Unit tests: SPDX state normalization, policy evaluation, snapshot diff.
- Integration tests: sample `project.assets.json` fixtures.
- End-to-end tests: restore sample project rồi chạy CLI.
- Failure-path tests: network timeout, invalid metadata, missing assets.
- Security tests: path traversal trong output path, malformed package metadata.
- Data-quality tests: cùng graph phải tạo normalized output giống nhau.

### 5 test scenario quan trọng nhất

1. Direct package update nhưng license không đổi → không tạo false violation.
2. Update direct package kéo thêm transitive blocked license → report dependency path chính xác.
3. Package không có `licenseExpression` → `UNKNOWN`, không tự allowed.
4. NuGet metadata endpoint timeout → dùng cache hoặc mark unavailable.
5. Multi-target project resolve package khác nhau → report đúng theo từng target framework.
