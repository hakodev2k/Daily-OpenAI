# Ý tưởng hôm nay: Personal API Contract Guardian

## 1. Tóm tắt ý tưởng

Xây dựng công cụ giúp developer theo dõi thay đổi của REST API contract giữa các phiên bản, tự động phát hiện breaking changes và tạo báo cáo trước khi deploy. Người dùng chính là backend developer hoặc team nhỏ muốn giảm lỗi khi API thay đổi.

Quy mô: Medium. MVP dự kiến 2-4 tuần.

## 2. Bài toán thực tế

Developer thường thay đổi DTO, endpoint, validation hoặc response format nhưng không nhận ra ảnh hưởng tới client cũ. Hiện nay nhiều đội dùng review thủ công, Swagger diff hoặc chạy test rời rạc.

Giả định phổ biến: team nhỏ chưa có hệ thống quản lý API compatibility hoàn chỉnh.

## 3. Người dùng mục tiêu

Backend developer, technical lead trong team nhỏ.

Bối cảnh: trước mỗi lần release API cần biết thay đổi nào có nguy cơ gây lỗi.

Pain point: mất thời gian review thủ công và phát hiện lỗi sau khi mobile/frontend đã cập nhật.

## 4. Giải pháp đề xuất

Workflow:

- Import OpenAPI/Swagger document hiện tại.
- Lưu snapshot từng phiên bản API.
- So sánh version mới với version cũ.
- Phân loại thay đổi: breaking, warning, safe.
- Tạo báo cáo Markdown hoặc comment vào pull request.

Điểm khác biệt: tập trung cho solo developer và .NET API, có rule tùy chỉnh theo nghiệp vụ.

Ví dụ: Developer đổi field `customerId` thành `id`. Tool cảnh báo đây là breaking change trước khi merge.

## 5. Tại sao ý tưởng này đáng làm

Giá trị thực tế: giảm lỗi integration giữa backend và client.

Giá trị kỹ thuật: học API governance, OpenAPI parsing, CI/CD integration.

Phù hợp solo developer vì MVP chỉ cần một modular monolith.

Lý do thất bại: nhiều team đã có công cụ tương tự và không muốn thêm workflow mới.

## 6. Phạm vi MVP

### Must have

- Upload OpenAPI JSON/YAML.
- Lưu API snapshot.
- So sánh hai phiên bản.
- Xuất báo cáo breaking changes.

### Should have

- GitHub Actions integration.
- Slack/Teams notification.
- Rule configuration.

### Later

- Marketplace rules.
- Multi-project dashboard.
- Enterprise authentication.

## 7. Luồng hoạt động

Developer upload API spec → validate schema → parse endpoints/models → compare snapshot → lưu kết quả → tạo report → gửi notification.

Failure cases:

- File OpenAPI lỗi.
- Schema không tương thích.
- Không đủ permission khi tích hợp GitHub.

## 8. Kiến trúc đề xuất

- Frontend: Vue hoặc React dashboard.
- Backend: ASP.NET Core modular monolith.
- Database: PostgreSQL lưu projects, snapshots, changes.
- Background worker: xử lý diff lớn.
- Storage: local/S3-compatible storage cho spec files.
- Authentication: JWT hoặc GitHub OAuth.
- Logging: Serilog + OpenTelemetry.

Không cần microservices ở MVP.

## 9. Công nghệ đề xuất

- .NET 10 / ASP.NET Core: phù hợp với backend API.
- EF Core + PostgreSQL: đơn giản và đủ khả năng mở rộng.
- OpenAPI.NET: đọc specification.
- Vue 3: nhanh cho dashboard.
- Docker + GitHub Actions: deployment đơn giản.

## 11. API và tích hợp

- GitHub API: tạo PR comment. Cần OAuth token.
- OpenAPI documents: nguồn dữ liệu chính.
- Webhook CI/CD: kích hoạt kiểm tra tự động.

Fallback: chạy CLI local nếu không dùng cloud.

## 12. AI có thực sự cần thiết không?

AI hữu ích nhưng không bắt buộc.

Có thể dùng AI để giải thích breaking change bằng ngôn ngữ tự nhiên hoặc đề xuất migration plan.

Không dùng AI cho việc detect diff vì rule-based chính xác hơn.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

Tạo CLI đọc hai file OpenAPI và kiểm tra diff.

Hoàn thành khi có thể phát hiện 5 loại breaking change.

### Phase 1 — Core MVP

Xây backend, database, dashboard và report.

### Phase 2 — Reliability

Thêm test, logging, retry, validation.

### Phase 3 — Useful expansion

Thêm GitHub Actions và notification.

### Phase 4 — Production readiness

Deploy cloud, backup, monitoring, documentation.

## 14. Các bài toán kỹ thuật đáng học

1. OpenAPI parsing - hiểu API contract.
2. Version comparison - xử lý diff phức tạp.
3. CI/CD integration - automation workflow.
4. Rule engine - thiết kế business rules mở rộng.

## 15. Rủi ro và cách xử lý

- Scope lớn: bắt đầu chỉ với REST/OpenAPI.
- False positive: cho phép custom rules.
- API format khác nhau: chuẩn hóa parser.
- Adoption thấp: ưu tiên CLI trước dashboard.

## 20. Việc cần làm ngay hôm nay

Mục tiêu 90 phút: tạo CLI prototype kiểm tra breaking change.

Files:

- src/ApiGuardian.Cli/Program.cs
- src/ApiGuardian.Core/OpenApiDiffService.cs
- tests/OpenApiDiffTests.cs

Commands:

```bash
dotnet new console -n ApiGuardian.Cli
dotnet new xunit -n ApiGuardian.Tests
```

Vertical slice:

Input: old.json + new.json

Output: danh sách breaking changes dạng Markdown.

Verification:

- Test xóa endpoint.
- Test đổi required property.
- Test thêm field không breaking.

Stop condition: CLI chạy được từ terminal và trả kết quả diff chính xác.
