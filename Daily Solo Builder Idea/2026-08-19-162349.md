# Ý tưởng hôm nay: WorkProof — Daily Work Evidence Journal

## 1. Tóm tắt ý tưởng

WorkProof là một công cụ cá nhân giúp developer tự động gom bằng chứng công việc từ GitHub commits, pull requests, calendar events và ghi chú thủ công thành một timeline theo ngày, sau đó tạo bản nháp daily update, weekly summary và achievement log để dùng khi báo cáo tiến độ hoặc review hiệu suất.

- Người dùng chính: software developer làm nhiều task song song và thường quên mình đã làm gì sau vài ngày hoặc vài tuần.
- Vấn đề chính: bằng chứng công việc nằm rải rác ở GitHub, calendar, ticket, chat và trí nhớ cá nhân.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Developer thường tạo ra rất nhiều “dấu vết công việc” nhưng chúng phân tán:

- commit và pull request trong GitHub;
- meeting, refinement, support call trong calendar;
- bug fix nhỏ không có ticket riêng;
- research, debugging hoặc hỗ trợ đồng nghiệp không tạo ra commit;
- task kéo dài nhiều ngày nhưng mỗi ngày chỉ có một phần tiến triển.

Khi đến daily standup, weekly report, sprint review hoặc performance review, developer thường phải nhớ lại công việc bằng cách mở Git history, calendar, Jira/board, chat và email rồi tổng hợp thủ công.

**Confirmed facts:** GitHub REST API hỗ trợ liệt kê commits của repository; với public repository endpoint có thể dùng không cần authentication, còn private repository có thể dùng fine-grained token với quyền `Contents: read`. Nguồn: GitHub Docs — REST API endpoints for commits: https://docs.github.com/en/rest/commits/commits

Microsoft Graph v1.0 hỗ trợ lấy danh sách event của user qua các endpoint như `GET /me/events` hoặc `GET /me/calendar/events`; delegated permission tối thiểu có thể là `Calendars.ReadBasic` tùy dữ liệu cần đọc. Nguồn: Microsoft Learn — List events: https://learn.microsoft.com/en-us/graph/api/user-list-events?view=graph-rest-1.0

**Observation:** GitHub và calendar đã có API chính thức, nên phần lớn dữ liệu đầu vào của MVP có thể lấy ổn định mà không cần scraping browser.

**Assumption cần kiểm chứng:** một developer cá nhân sẽ thấy giá trị nếu việc tạo daily/weekly summary mất dưới 30 giây thay vì phải tự rà nhiều nguồn.

Workaround hiện tại thường là:

- ghi note thủ công cuối ngày;
- xem `git log` trước standup;
- copy title PR vào OneNote/Notion;
- mở calendar để nhớ các cuộc họp;
- đến cuối tháng mới cố nhớ lại thành tích.

Những cách này đơn giản nhưng phụ thuộc nhiều vào thói quen ghi nhớ và dễ bỏ sót các công việc “vô hình” như debugging, incident support, review code hoặc research.

## 3. Người dùng mục tiêu

**Primary user:** backend developer làm việc trên nhiều repository và tham gia meeting/support trong ngày.

- **Bối cảnh sử dụng:** trước daily standup, cuối ngày, cuối tuần hoặc khi chuẩn bị self-review.
- **Main pain point:** không có một timeline đáng tin cậy cho biết mình thực sự đã làm gì.
- **Current workaround:** mở GitHub, calendar và note rồi tổng hợp thủ công.
- **Lý do thử WorkProof:** có một bản timeline tự động nhưng vẫn cho phép người dùng xác nhận/chỉnh sửa trước khi tạo báo cáo.

MVP chỉ tập trung vào **một người dùng**, không cố trở thành employee monitoring system hay analytics platform cho manager.

## 4. Giải pháp đề xuất

Người dùng kết nối một hoặc vài GitHub repository và tùy chọn Microsoft 365 calendar. WorkProof định kỳ lấy metadata, chuẩn hóa thành các `WorkEvidenceItem`, gom theo ngày rồi cho người dùng review nhanh.

### Main workflow

Input:

- GitHub commit metadata;
- pull request metadata nếu bật integration;
- calendar event metadata;
- manual note ngắn.

Processing:

1. Chuẩn hóa timestamp về timezone người dùng.
2. Loại bỏ duplicate activity.
3. Gom activity theo project/category.
4. Cho phép user đánh dấu `Meaningful`, `Noise`, `Private`.
5. Tạo deterministic daily timeline.
6. Tùy chọn dùng AI để viết lại timeline thành status update ngắn.

Output:

- Daily timeline.
- Daily standup draft.
- Weekly achievement summary.
- Searchable historical evidence.

### Concrete example

Trong một ngày, user có:

- 3 commits ở repository backend;
- 1 PR merged;
- 2 meeting calendar events;
- một note thủ công: “Investigated Graph calendar sync issue, root cause was missing update path.”

WorkProof hiển thị:

```text
09:15  Commit  Add retry policy for Graph call
10:30  Meeting  Sprint refinement
11:42  PR      #184 Fix calendar update flow — merged
14:05  Note    Investigated Graph calendar sync issue
15:30  Meeting  QA bug triage
16:18  Commit  Add integration tests
```

User bỏ một meeting không liên quan khỏi report rồi bấm `Generate Daily Update`.

Output:

```text
Today:
- Fixed the calendar update flow and merged PR #184.
- Added retry handling and integration tests for Graph calls.
- Investigated the remaining calendar sync issue with QA.

Next:
- Validate the fix in staging.
```

### Key differentiator

WorkProof không cố “đo năng suất” bằng số commit. Nó chỉ xây **personal evidence ledger** giúp user nhớ lại và tự diễn giải công việc của chính mình.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Ngay cả khi chỉ có một người dùng, tool vẫn có giá trị vì giảm thời gian chuẩn bị daily update, weekly summary và self-review.

### Technical learning value

Dự án cho phép học sâu về:

- API synchronization;
- OAuth/delegated permissions;
- incremental sync;
- deduplication;
- time-zone handling;
- privacy-aware data processing;
- AI summarization có validation.

### Phù hợp solo developer

Core domain rất nhỏ: ingest evidence → normalize → review → summarize. Không cần distributed system hay big data ở MVP.

### Vì sao vẫn hữu ích với ít user

Đây là personal utility. Không cần network effect, marketplace hay lượng người dùng lớn mới tạo giá trị.

### Điều gì khiến ý tưởng thất bại

- User vẫn phải chỉnh sửa quá nhiều sau mỗi lần import.
- Metadata từ commit/calendar không đủ để phản ánh công việc thật.
- Việc kết nối các provider tạo friction lớn hơn lợi ích.

### Lý do mạnh nhất để không build

Nếu developer đã có thói quen ghi journal đều đặn mỗi ngày và không thấy việc tổng hợp thủ công tốn thời gian, WorkProof có thể chỉ tạo thêm một công cụ phải duy trì.

## 7. Luồng hoạt động

### Initial setup

User mở WorkProof
→ tạo local profile
→ thêm GitHub repositories
→ cấu hình authentication nếu repository private
→ chọn timezone
→ chạy first sync
→ review imported items.

### Daily sync

Scheduler chạy
→ gọi provider API
→ lấy activity từ checkpoint gần nhất
→ normalize metadata
→ tạo hash/idempotency key
→ bỏ duplicate
→ lưu evidence item
→ cập nhật last sync cursor.

### Daily review

User mở timeline
→ exclude noise
→ thêm manual note nếu cần
→ chọn items cần đưa vào report
→ generate summary
→ copy Markdown/text.

### Failure cases

**GitHub API unavailable:** giữ cursor hiện tại, retry sau; không đánh dấu sync thành công.

**Token expired:** hiển thị integration health = `Needs attention` và dừng sync provider đó.

**Duplicate commit:** unique key theo provider + repository + external ID ngăn insert trùng.

**Calendar event thay đổi:** update bản ghi theo provider event ID thay vì tạo duplicate.

**Timezone mismatch:** lưu timestamp UTC, convert sang timezone user khi group theo ngày.

## 8. Kiến trúc đề xuất

### Frontend

Vue 3 SPA nhỏ gồm:

- Today Timeline;
- History;
- Integrations;
- Daily Summary editor.

Không cần SSR.

### Backend

ASP.NET Core modular monolith gồm các module:

- `Evidence`
- `Integrations`
- `Sync`
- `Summaries`
- `Settings`

Một process là đủ cho MVP.

### Database

PostgreSQL lưu metadata, sync cursor và summary. SQLite là lựa chọn còn đơn giản hơn nếu chạy local single-user.

### Background worker

Dùng `BackgroundService` để chạy sync mỗi 15–60 phút hoặc on-demand.

Không cần message broker ở MVP.

### Cache

Không cần cache ban đầu vì lượng dữ liệu cá nhân nhỏ.

### Authentication

Self-hosted single-user có thể dùng local password hoặc reverse-proxy auth. Provider OAuth/token được lưu encrypted.

### External APIs

- GitHub REST API.
- Microsoft Graph calendar optional.

### AI

Optional, chỉ dùng ở bước rewrite summary.

### Logging

Structured log gồm:

- provider;
- sync start/end;
- item count;
- error code;
- correlation ID.

Không log token hoặc raw private calendar body.

### Deployment

Docker Compose trên VPS, mini PC hoặc local workstation.

## 9. Công nghệ đề xuất

### .NET 10 + ASP.NET Core

Tại thời điểm chạy này, .NET 10 là LTS đang active và là lựa chọn production hợp lý. Nguồn: .NET support policy: https://dotnet.microsoft.com/en-us/platform/support/policy

**Why it fits:** HTTP API, OAuth integration, worker và typed configuration đều phù hợp với ASP.NET Core.

**Simpler alternative:** một ASP.NET Core app với Razor Pages thay vì tách Vue.

**Outgrow point:** gần như chưa cần thay đổi cho personal-scale use.

### EF Core + PostgreSQL

Phù hợp để lưu structured evidence và query timeline.

**Simpler alternative:** SQLite.

**Outgrow point:** chỉ cần PostgreSQL khi chạy server hoặc nhiều thiết bị truy cập.

### BackgroundService

Đủ cho scheduled sync đơn giản.

**Simpler alternative:** chỉ sync khi user mở app/bấm nút.

**Outgrow point:** nếu có nhiều provider/job retry phức tạp thì chuyển Hangfire hoặc Quartz.NET.

### Vue 3

Phù hợp dashboard tương tác nhẹ và timeline.

**Simpler alternative:** Razor Pages.

### Docker

Giúp self-hosted reproducible.

### Playwright

Dùng E2E test cho flow sync mock data → review → export summary.

### GitHub Actions

Build, test và publish Docker image.

## 11. API và tích hợp

### GitHub REST API

**Purpose:** lấy commit metadata và sau MVP có thể lấy PR metadata.

**Authentication:** public repository có thể gọi endpoint commits không authentication; private repository cần credential có quyền phù hợp, ví dụ fine-grained token `Contents: read`. Nguồn: https://docs.github.com/en/rest/commits/commits

**Rate limit:** phải tôn trọng rate-limit headers và tránh full resync không cần thiết.

**Privacy:** commit message và repository name có thể chứa thông tin nội bộ; chỉ lưu dữ liệu cần thiết.

**Fallback:** cho phép manual import hoặc local `git log` adapter ở phiên bản sau.

### Microsoft Graph Calendar

**Purpose:** lấy meeting metadata để bổ sung context ngày làm việc.

**Authentication:** delegated OAuth; Microsoft Graph hỗ trợ các permission như `Calendars.ReadBasic`, `Calendars.Read`, `Calendars.ReadWrite`, tùy dữ liệu cần đọc. MVP nên xin quyền nhỏ nhất có thể. Nguồn: https://learn.microsoft.com/en-us/graph/api/user-list-events?view=graph-rest-1.0

**Cost/rate limit:** không giả định unlimited; worker phải xử lý throttling và retry.

**Privacy:** subject/location có thể nhạy cảm; mặc định chỉ lấy metadata cần thiết và cho phép tắt calendar integration.

**Fallback:** manual note hoặc ICS import trong tương lai.

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

Core evidence ledger hoàn toàn deterministic và không cần AI.

### Exact AI task

Rewrite selected evidence items thành:

```json
{
  "done": ["..."],
  "next": ["..."],
  "blockers": ["..."]
}
```

### Required context

Chỉ gửi selected item title + user note, không gửi toàn bộ repository/calendar content.

### Validation

- output phải parse được theo JSON schema;
- mọi bullet phải trace về ít nhất một evidence item;
- model không được tự thêm achievement không tồn tại.

### Deterministic fallback

Template engine:

```text
Completed:
- {selected items}
```

### Risks

- hallucination;
- privacy;
- cost;
- latency.

Do đó AI không nằm trên critical path.

## 14. Các bài toán kỹ thuật đáng học

### 1. Incremental synchronization

Không nên tải lại toàn bộ lịch sử mỗi lần. Cần cursor, timestamp window và safe overlap để tránh missed event.

**Skill improved:** data synchronization và eventual consistency.

### 2. Idempotency và deduplication

Một commit/event có thể xuất hiện lại ở nhiều lần sync.

**Skill improved:** stable external IDs, fingerprinting và upsert design.

### 3. OAuth và least privilege

Calendar integration yêu cầu xử lý token, consent và refresh flow đúng cách.

**Skill improved:** secure third-party integration.

### 4. Time-zone correctness

Activity ở UTC nhưng report lại theo ngày local; meeting qua nửa đêm càng dễ sai.

**Skill improved:** temporal data modeling.

### 5. AI grounding

Nếu dùng AI, summary phải chỉ dựa trên evidence thực tế.

**Skill improved:** structured output, provenance và hallucination control.

## 15. Rủi ro và cách xử lý

### Privacy

**Risk:** calendar và commit metadata chứa thông tin nội bộ.

**Mitigation:** self-hosted-first, metadata-minimal, encryption cho credential, user-controlled retention, no telemetry mặc định.

### Scope expansion

**Risk:** biến thành Jira/Notion replacement.

**Mitigation:** domain boundary rõ: WorkProof chỉ lưu evidence và summary, không quản lý task lifecycle.

### “Commit count = productivity” misuse

**Risk:** product bị hiểu thành monitoring tool.

**Mitigation:** không có productivity score; không ranking; không đo số dòng code; single-user focus.

### API dependency

**Risk:** throttling, token hết hạn hoặc provider thay đổi.

**Mitigation:** adapter abstraction, retry policy, integration health, manual note fallback.

### Data noise

**Risk:** quá nhiều commit nhỏ khiến timeline khó đọc.

**Mitigation:** filter merge commits, grouping configurable, include/exclude review.

### User adoption

**Risk:** user không mở app đều.

**Mitigation:** timeline tự sync; workflow review dưới 30 giây; export clipboard một click.

## 16. Kiểm thử

### Strategy

- Unit test normalization, grouping, timezone và fingerprint.
- Integration test GitHub adapter bằng recorded/mock HTTP response.
- Database integration test cho upsert/idempotency.
- Playwright E2E cho timeline → select → summary.
- Security test đảm bảo token không xuất hiện trong log/API response.

### 5 scenario quan trọng nhất

1. Sync cùng một commit hai lần chỉ tạo một EvidenceItem.
2. Commit lúc `23:30 UTC` được group đúng ngày theo timezone user.
3. GitHub trả rate-limit/throttle thì sync không mất cursor.
4. Item marked `Private/Exclude` không xuất hiện trong exported summary.
5. AI hoặc deterministic summary không tạo bullet không có source evidence.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, hoàn thành vertical slice:

**GitHub repository → lấy commit hôm nay → normalize → in timeline ra console.**

### Files/components cần tạo

```text
WorkProof.sln
src/
  WorkProof.Api/
    Program.cs
    GitHub/GitHubCommitClient.cs
    Evidence/WorkEvidenceItem.cs
    Evidence/EvidenceNormalizer.cs
tests/
  WorkProof.Tests/
```

### Setup commands

```bash
dotnet new sln -n WorkProof
dotnet new webapi -n WorkProof.Api -o src/WorkProof.Api
dotnet new xunit -n WorkProof.Tests -o tests/WorkProof.Tests
dotnet sln add src/WorkProof.Api
dotnet sln add tests/WorkProof.Tests
dotnet add tests/WorkProof.Tests reference src/WorkProof.Api
```

### First vertical slice

Tạo endpoint:

```text
GET /api/evidence/github?owner={owner}&repo={repo}
```

Flow:

1. Gọi GitHub commits REST endpoint.
2. Lọc commits trong ngày theo UTC window đơn giản.
3. Map mỗi commit thành:

```json
{
  "type": "Commit",
  "externalId": "sha",
  "title": "commit message first line",
  "occurredAtUtc": "...",
  "sourceUrl": "..."
}
```

4. Sort theo thời gian.
5. Return JSON.

### Integration test

Mock GitHub HTTP response gồm ba commits và xác nhận:

- đúng số item;
- đúng external ID;
- đúng thứ tự thời gian;
- commit message multiline chỉ lấy first line làm title.

### Expected result

Chạy:

```bash
dotnet run --project src/WorkProof.Api
```

Sau đó gọi endpoint với một public repository và nhận timeline JSON thực tế.

### Verification checklist

- [ ] API project chạy local.
- [ ] Đọc được commits từ một public GitHub repository.
- [ ] Không cần database trong session đầu tiên.
- [ ] Mỗi commit được normalize thành `WorkEvidenceItem`.
- [ ] Sort timestamp đúng.
- [ ] Có ít nhất một automated test pass.
- [ ] Không log authorization header nếu sau đó thêm token.

### Stop condition

Dừng session ngay khi một GitHub repository thật có thể đi qua flow:

```text
GitHub API
→ GitHubCommitClient
→ EvidenceNormalizer
→ JSON timeline
```

Không làm Vue, PostgreSQL, Microsoft Graph, OAuth hoặc AI trong buổi đầu tiên.
