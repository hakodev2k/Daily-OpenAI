# Ý tưởng hôm nay: Personal API Contract Guardian

## 1. Tóm tắt ý tưởng

Một công cụ dành cho developer giúp theo dõi sự thay đổi của API contract giữa các phiên bản backend, tự động phát hiện breaking change trước khi deploy. Dự án giúp backend developer và team nhỏ tránh lỗi do API thay đổi nhưng frontend, mobile app hoặc integration chưa kịp cập nhật.

- Người dùng: Solo developer, freelancer, team backend nhỏ.
- Quy mô: Medium.
- MVP: 2–4 tuần.

## 2. Bài toán thực tế

Khi phát triển REST API, thay đổi DTO, validation rule, enum, response structure hoặc authentication flow có thể vô tình phá vỡ client đang sử dụng.

Hiện nay nhiều developer xử lý bằng:

- Review code thủ công.
- Kiểm tra Swagger bằng mắt.
- Chờ QA phát hiện lỗi.
- Viết test integration nhưng không luôn bao phủ contract.

Giả định: với dự án có nhiều client hoặc nhiều version API, việc phát hiện sớm contract drift có thể tiết kiệm thời gian debug.

## 3. Người dùng mục tiêu

Primary user:

- .NET backend developer làm việc với ASP.NET Core Web API.
- Có nhiều endpoint, nhiều client hoặc nhiều môi trường deploy.

Pain point:

- Không biết thay đổi nào là breaking change.
- Khó review ảnh hưởng của API change.

Workaround hiện tại:

- Manual review Swagger/OpenAPI.
- Trao đổi qua chat giữa backend và frontend.

## 4. Giải pháp đề xuất

Sản phẩm đọc OpenAPI specification của API ở các thời điểm khác nhau, so sánh contract và tạo báo cáo thay đổi.

Workflow:

1. Developer upload hoặc kết nối OpenAPI JSON.
2. Hệ thống lưu snapshot version.
3. Engine phân tích khác biệt.
4. Sinh report:
   - Endpoint bị xóa.
   - Field bị rename.
   - Type thay đổi.
   - Required field mới.
   - Breaking change.
5. Gửi cảnh báo qua GitHub PR comment hoặc notification.

Ví dụ:

Developer đổi `CustomerResponse.Name` thành `FullName`. Tool phát hiện client cũ có nguy cơ lỗi và cảnh báo trước merge.

Điểm khác biệt: tập trung vào workflow cá nhân/team nhỏ, không phải API management platform doanh nghiệp.

## 5. Tại sao ý tưởng này đáng làm

Giá trị thực tế:

- Có thể dùng ngay cho chính dự án .NET cá nhân.
- Giúp hiểu sâu API design và backward compatibility.

Giá trị kỹ thuật:

- OpenAPI parsing.
- Version comparison.
- CI/CD integration.
- Developer tooling.

Phù hợp solo developer vì MVP không cần user management phức tạp.

Lý do thất bại:

- Developer không thấy đau đủ lớn để cài thêm tool.
- Các công cụ API testing hiện có đã đáp ứng nhu cầu cơ bản.

## 6. Phạm vi MVP

### Must have

- Import OpenAPI JSON/YAML.
- Lưu snapshot.
- Compare hai version.
- Phân loại breaking/non-breaking change.
- Export Markdown report.

### Should have

- GitHub Action.
- Pull request comment.
- Slack/Telegram notification.
- Rule configuration.

### Later

- AI giải thích impact.
- Auto migration suggestion.
- Multi repository dashboard.

## 7. Luồng hoạt động

Developer push code
→ CI generate OpenAPI
→ Tool nhận specification
→ Validate format
→ Compare với version trước
→ Lưu kết quả
→ Generate report
→ Fail pipeline nếu có breaking change nghiêm trọng.

Failure cases:

- OpenAPI không hợp lệ.
- Missing previous version.
- False positive do custom rule.

## 8. Kiến trúc đề xuất

Modular monolith:

- Frontend: Vue/React dashboard đơn giản.
- Backend: ASP.NET Core Web API.
- Database: PostgreSQL.
- Worker: BackgroundService xử lý scan.
- Storage: Local/S3 compatible storage cho spec file.
- Authentication: GitHub OAuth nếu cần.
- Notification: GitHub API.
- Logging: Serilog.

Không cần queue hoặc microservice ở MVP.

## 9. Công nghệ đề xuất

- .NET 10 + ASP.NET Core: phù hợp với kinh nghiệm backend.
- PostgreSQL + EF Core: lưu version và metadata.
- OpenAPI.NET: parse specification.
- Vue 3: dashboard nhẹ.
- Docker: dễ chạy local.
- GitHub Actions: integration tự nhiên.

Alternative:

- CLI .NET console nếu chỉ muốn dùng cá nhân.

Khi mở rộng lớn hơn có thể cần message queue và distributed processing.

## 10. Thiết kế dữ liệu ban đầu

### Project

Purpose: nhóm API cần theo dõi.

Fields:
- Id
- Name
- RepositoryUrl
- CreatedAt

### ApiSnapshot

Purpose: lưu từng OpenAPI version.

Fields:
- Id
- ProjectId
- Version
- ContentHash
- FilePath
- CreatedAt

### ApiChangeReport

Purpose: lưu kết quả compare.

Fields:
- Id
- SnapshotFrom
- SnapshotTo
- Severity
- ChangesJson
- CreatedAt

## 11. API và tích hợp

GitHub API:

- Purpose: comment vào pull request.
- Authentication: GitHub App/token.
- Concern: permission repository.
- Fallback: export Markdown.

OpenAPI document:

- Purpose: input chính.
- Không cần external API.

## 12. AI có thực sự cần thiết không?

AI useful but optional.

AI có thể dùng để:

- Giải thích impact của breaking change bằng ngôn ngữ tự nhiên.
- Gợi ý migration note.

Output:

```json
{
  "risk":"high",
  "reason":"Field removal affects existing mobile clients",
  "suggestion":"Create new field and keep old field temporarily"
}
```

Validation:
- Rule engine vẫn quyết định severity.
- AI chỉ giải thích.

Rủi ro:
- Chi phí API.
- Hallucination.

## 15. Rủi ro và cách xử lý

Scope creep:
- Chỉ tập trung REST API trước.

False positive:
- Cho phép custom rule.

API format khác nhau:
- Hỗ trợ OpenAPI chuẩn trước.

Maintenance:
- Giữ architecture đơn giản.

## 16. Kiểm thử

Chiến lược:

- Unit test diff engine.
- Integration test API.
- E2E dashboard.

5 scenario quan trọng:

1. Endpoint bị xóa.
2. Required field thêm mới.
3. Response type thay đổi.
4. Không có snapshot cũ.
5. Invalid OpenAPI file.

## 17. Cách đo dự án có hữu ích hay không

## 20. Việc cần làm ngay hôm nay

Mục tiêu 60–120 phút: tạo phiên bản CLI đầu tiên có thể compare hai OpenAPI file.

Tasks:

1. Tạo solution:

```bash
dotnet new console -n ApiContractGuardian
```

2. Thêm package OpenAPI parser.

3. Tạo:

```
/src
  /DiffEngine
  /Models
  /Commands
```

4. Implement:

- Load old.json.
- Load new.json.
- Detect endpoint added/removed.
- Print Markdown report.

Verification:

- Chạy command với hai file mẫu.
- Nhận được danh sách thay đổi.

Stop condition:

CLI phát hiện chính xác endpoint bị xóa và field response thay đổi.
