# Ý tưởng hôm nay: RepoPolicy Radar — GitHub Repository Governance Drift Auditor

## 1. Tóm tắt ý tưởng

RepoPolicy Radar là một developer tool self-hosted giúp developer **kiểm tra nhiều GitHub repository theo cùng một baseline bảo vệ** và phát hiện repository nào bị lệch cấu hình: thiếu ruleset, thiếu required status checks, cho phép force-push, thiếu signed commits, thiếu production environment protection hoặc có workflow deploy không qua environment gate.

- Người dùng chính: solo developer hoặc tech lead quản lý nhiều repository GitHub.
- Bài toán chính: các repository được tạo ở thời điểm khác nhau thường có policy khác nhau và dễ bị “configuration drift”.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Khi chỉ có một repository, developer có thể kiểm tra branch protection thủ công. Nhưng khi có nhiều project, template, demo, internal tool và production service, các cài đặt bảo vệ thường bị lệch dần theo thời gian.

Một repository có thể yêu cầu pull request và status check, repository khác lại cho push trực tiếp vào `main`; một repo production có environment approval, repo khác deploy thẳng từ workflow.

### Confirmed facts

- GitHub rulesets có thể áp dụng nhiều lớp rule lên branch/tag và hỗ trợ các rule như require pull request, require status checks, block force push, require signed commits, require deployments to succeed before merging và code scanning requirements. Nguồn: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets
- GitHub REST API có endpoint để đọc repository rulesets và các active rules áp dụng cho branch. Nguồn: https://docs.github.com/en/rest/repos/rules
- GitHub environments có thể yêu cầu approval, giới hạn branch deployment và chỉ cấp environment secrets sau khi protection rules được thỏa mãn. Nguồn: https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments
- GitHub rule suites cho phép xem kết quả evaluation của ruleset ở mức repository. Nguồn: https://docs.github.com/en/rest/repos/rule-suites

### Observation

GitHub cung cấp primitive rất mạnh để bảo vệ repository, nhưng developer quản lý nhiều repo vẫn phải tự quyết định baseline và tự kiểm tra repo nào đang lệch baseline đó.

### Assumption cần validation

Solo developer có từ khoảng 5–20 repository hoạt động sẽ thấy hữu ích nếu có một dashboard hoặc CLI trả lời ngay:

> “Repo nào đang yếu hơn baseline của tôi và chính xác rule nào bị thiếu?”

### Workaround hiện tại

- Mở Settings của từng repository.
- Copy ruleset thủ công.
- Dùng organization-level policy nếu đang có plan/phạm vi phù hợp.
- Viết script GitHub CLI ad-hoc.
- Dựa vào repository template nhưng không kiểm tra drift sau khi repo đã tồn tại lâu.

Vấn đề là các cách này hoặc tốn thời gian, hoặc không lưu lịch sử thay đổi, hoặc không cho thấy mức độ rủi ro một cách thống nhất.

## 3. Người dùng mục tiêu

### Primary user

Developer cá nhân hoặc tech lead nhỏ đang có nhiều repository GitHub cho API, automation, background worker, CLI, frontend và production service.

### Context of use

- Có 5–30 repository.
- Một số repository deploy production bằng GitHub Actions.
- Có baseline mong muốn cho `main` nhưng chưa có central governance tooling.

### Main pain point

Không biết repository nào đã bị lệch cấu hình bảo vệ so với repository chuẩn.

### Current workaround

Mở từng repo để kiểm tra settings hoặc nhớ cấu hình bằng kinh nghiệm.

### Vì sao họ thử tool này

Chỉ cần khai báo baseline một lần, sau đó chạy scan và nhận report deterministic.

## 4. Giải pháp đề xuất

Người dùng tạo một policy file, ví dụ:

```yaml
policyVersion: 1
branches:
  main:
    requirePullRequest: true
    blockForcePush: true
    requireStatusChecks:
      - build
      - test
production:
  requireEnvironment: true
  environmentName: production
```

RepoPolicy Radar sẽ:

1. Lấy danh sách repository được chọn.
2. Đọc repository rulesets/branch rules.
3. Đọc workflow YAML để xác định workflow deploy có reference tới `environment` hay không.
4. Đọc environment metadata nếu token có quyền.
5. Chuẩn hóa dữ liệu thành một `RepositorySecuritySnapshot`.
6. So sánh snapshot với baseline.
7. Xuất `Pass`, `Warning`, `Fail`, kèm bằng chứng và remediation.

### Ví dụ end-to-end

Người dùng scan ba repo:

```text
api-orders
worker-mail
personal-dashboard
```

Kết quả:

```text
api-orders          PASS
worker-mail         FAIL  main allows force push
personal-dashboard  WARN  deploy workflow does not reference production environment
```

Người dùng click `worker-mail` và thấy:

```text
Expected: blockForcePush = true
Actual:   no active rule found
Evidence: branch main / active rules
Fix: add block force pushes to the matching ruleset
```

### Key differentiator

Tool không cố thay GitHub policy engine. Nó đóng vai trò **policy-as-code auditor** độc lập, tập trung vào drift detection, lịch sử và bằng chứng.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Có thể dùng trực tiếp cho repository cá nhân ngay cả khi không có người dùng bên ngoài.

### Technical learning value

Dự án giúp học sâu:

- GitHub REST API.
- Fine-grained permissions.
- Policy evaluation engine.
- YAML parsing.
- GitHub Actions workflow semantics.
- Background scanning.
- Drift history.

### Vì sao phù hợp solo developer

Core logic nhỏ và deterministic:

```text
Fetch → Normalize → Evaluate → Report
```

Không cần AI, message broker hoặc infrastructure lớn.

### Dự án vẫn hữu ích nếu chỉ có một user

Nếu tool giúp phát hiện một production repository bị thiếu protection rule thì đã có giá trị thực tế.

### Điều gì làm ý tưởng thất bại

- User chỉ có 1–2 repo và kiểm tra thủ công đủ nhanh.
- GitHub organization-level governance hiện tại đã đáp ứng toàn bộ nhu cầu.
- Policy engine quá generic khiến cấu hình khó dùng hơn chính GitHub UI.

### Lý do mạnh nhất để không build

Nếu toàn bộ repository đều nằm trong một organization có governance chuẩn, ruleset cấp organization có thể giải quyết nhiều phần của bài toán trực tiếp trong GitHub.

## 6. Phạm vi MVP

### Must have

- Kết nối GitHub bằng fine-grained token hoặc GitHub App.
- Chọn repository cần scan.
- Baseline YAML versioned trong Git.
- Scan default branch.
- Kiểm tra:
  - require pull request;
  - block force push;
  - required status checks;
  - signed commit requirement;
  - production workflow có dùng GitHub environment hay không.
- Report Pass/Warning/Fail.
- Lưu scan history.
- CLI command để chạy CI.

### Should have

- Detect required deployment-before-merge rule.
- Environment protection audit.
- Compare hai lần scan.
- Markdown/JSON output.
- Allow per-repository exception có expiry date.
- GitHub Actions reusable workflow để chạy auditor.

### Later

- Auto-remediation PR hoặc ruleset update.
- Organization-wide baseline.
- Multiple policy profiles.
- Slack/Teams notifications.
- GitHub Check Run annotation.
- Policy pack cho public repo, internal service, production service.

## 7. Luồng hoạt động

```text
User chọn repo
→ validate GitHub permission
→ fetch repository metadata
→ fetch active branch rules/rulesets
→ fetch workflow files
→ fetch environment metadata khi khả dụng
→ normalize snapshot
→ evaluate baseline
→ lưu scan + findings
→ render report
→ optional CI exit code
```

### Alternative flows

**Không đủ permission:** đánh dấu `Unknown`, không coi là `Pass`.

**API rate limit:** cache metadata, retry với backoff, dừng scan còn lại nếu quota thấp.

**Ruleset kế thừa từ organization:** giữ `source_type/source` trong evidence để tránh báo false positive.

**Repository archived:** có thể skip theo policy.

**Workflow deploy không rõ:** đánh dấu `Needs Review` thay vì suy đoán chắc chắn.

MVP self-hosted có thể single-user login hoặc local-only mode.

### AI

Không cần.

### Logging

Structured logs với `repository`, `scanId`, `ruleId`, `githubRequestId`.

## 10. Thiết kế dữ liệu ban đầu

### RepositoryTarget

**Purpose:** repository được quản lý.

Fields:

- `Id`
- `Owner`
- `Name`
- `DefaultBranch`
- `IsArchived`
- `PolicyProfile`
- `LastScannedAt`

Relationship: có nhiều Scan.

### PolicyProfile

**Purpose:** baseline mong muốn.

Fields:

- `Id`
- `Name`
- `Version`
- `YamlContent`
- `CreatedAt`

Retention: giữ version cũ để biết scan trước dùng policy nào.

### Scan

**Purpose:** một lần kiểm tra repository.

Fields:

- `Id`
- `RepositoryTargetId`
- `PolicyProfileId`
- `StartedAt`
- `CompletedAt`
- `Status`
- `SnapshotJson`

Retention: giữ 90–180 ngày ban đầu.

### Finding

**Purpose:** một rule mismatch.

Fields:

- `Id`
- `ScanId`
- `RuleCode`
- `Severity`
- `ExpectedJson`
- `ActualJson`
- `EvidenceJson`
- `Remediation`

### PolicyException

**Purpose:** suppress finding có kiểm soát.

Fields:

- `RepositoryTargetId`
- `RuleCode`
- `Reason`
- `ExpiresAt`

Exception bắt buộc có expiry để tránh suppress vĩnh viễn.

## 11. API và tích hợp

### GitHub REST API — rulesets/rules

**Purpose:** đọc active protections.

**Authentication:** fine-grained PAT hoặc GitHub App token.

**Permission concern:** chỉ yêu cầu read permission cần thiết; không xin write ở MVP.

**Rate limit concern:** scan batch cần cache và concurrency thấp.

**Fallback:** nếu endpoint không truy cập được, kết quả phải là `Unknown`, không suy luận.

Nguồn: https://docs.github.com/en/rest/repos/rules

### GitHub repository contents API

**Purpose:** đọc `.github/workflows/*.yml`.

**Authentication:** read repository contents.

**Privacy:** workflow có thể chứa naming/configuration nội bộ; không log raw file mặc định.

**Fallback:** chỉ audit branch rules nếu workflow không đọc được.

### GitHub environments

**Purpose:** kiểm tra environment dùng cho production.

**Authentication:** tùy repository/plan/permission.

**Plan concern:** một số protection capabilities khác nhau theo repository visibility và GitHub plan.

**Fallback:** đánh dấu capability là `Not available / Unknown` thay vì fail policy sai.

Nguồn: https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Policy evaluation cần deterministic behavior và evidence rõ ràng. AI không nên quyết định repository có compliant hay không.

Có thể thêm AI sau này như optional helper để giải thích finding bằng ngôn ngữ tự nhiên, nhưng:

- rule result vẫn do deterministic engine sinh ra;
- AI không được thay severity;
- AI không được tự động sửa repository.

MVP hoàn toàn không cần model API.

## 15. Rủi ro và cách xử lý

### False positive

**Risk:** ruleset inherited hoặc workflow reusable làm scanner hiểu sai.

**Mitigation:** evidence-first design, `Unknown/Needs Review`, không ép binary Pass/Fail khi thiếu dữ liệu.

### Token security

**Risk:** tool giữ GitHub credential.

**Mitigation:** ưu tiên GitHub App, encrypt token at rest, minimum read permissions, không log credential.

### GitHub API changes

**Risk:** endpoint/schema thay đổi.

**Mitigation:** typed adapter layer + contract tests + pin API version header.

### Scope expansion

**Risk:** biến thành full GitHub security platform.

**Mitigation:** MVP chỉ audit repository governance baseline.

### Plan-specific capabilities

**Risk:** một rule không có ở plan hiện tại.

**Mitigation:** capability detection và policy rule `requiredIfSupported`.

### User adoption

**Risk:** người dùng thấy GitHub UI đã đủ.

**Mitigation:** validation tập trung vào người có nhiều repo và drift history, không cạnh tranh với GitHub UI cho single-repo setup.

## 16. Kiểm thử

### Strategy

- Unit tests cho từng evaluator.
- Integration tests với recorded/synthetic GitHub responses.
- Contract tests cho normalization.
- E2E test CLI và dashboard.
- Security tests cho credential/log redaction.

### 5 test scenario quan trọng nhất

1. `main` có đủ PR + status checks + force-push block → Pass.
2. Rule đến từ organization-level ruleset → không báo missing.
3. GitHub trả `403` do thiếu permission → `Unknown`, không Pass.
4. Workflow deploy production không reference environment → Warning/Fail theo policy.
5. Exception hết hạn → finding tự xuất hiện lại ở scan tiếp theo.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, xây vertical slice đầu tiên:

```text
GitHub repo → fetch active rules for main → evaluate 3 rules → print report
```

### Files/components tạo

```text
RepoPolicyRadar.sln
src/
  RepoPolicyRadar.Cli/
    Program.cs
    GitHub/GitHubRulesClient.cs
    Policy/RepositoryPolicy.cs
    Policy/PolicyEvaluator.cs
    Models/BranchRuleSnapshot.cs
tests/
  RepoPolicyRadar.Tests/
    PolicyEvaluatorTests.cs
policy.example.json
```

### Setup commands

```bash
dotnet new sln -n RepoPolicyRadar
dotnet new console -n RepoPolicyRadar.Cli -o src/RepoPolicyRadar.Cli
dotnet new xunit -n RepoPolicyRadar.Tests -o tests/RepoPolicyRadar.Tests
dotnet sln add src/RepoPolicyRadar.Cli
dotnet sln add tests/RepoPolicyRadar.Tests
dotnet add tests/RepoPolicyRadar.Tests reference src/RepoPolicyRadar.Cli
```

### First vertical slice

Policy đầu tiên chỉ có ba rule:

```json
{
  "requirePullRequest": true,
  "blockForcePush": true,
  "requiredStatusChecks": ["build"]
}
```

CLI:

```bash
dotnet run --project src/RepoPolicyRadar.Cli -- owner/repository main
```

Expected output:

```text
Repository: owner/repository
Branch: main

[PASS] Require pull request
[FAIL] Block force push
[WARN] Required status check 'build' not found

Result: FAIL
```

### Implementation order

1. Đọc `GITHUB_TOKEN` từ environment variable.
2. Gọi endpoint active rules cho branch `main`.
3. Map response thành ba boolean/list đơn giản.
4. Viết `PolicyEvaluator` thuần C#.
5. In report ra console.
6. Viết unit test cho Pass/Fail/Unknown.

### Expected result

Cuối session, tool phải audit được ít nhất một repository thật và trả kết quả nhìn thấy ngay trong terminal.

### Verification checklist

- [ ] Không hard-code token.
- [ ] API `200` được parse thành snapshot.
- [ ] API `403/404` không bị coi là Pass.
- [ ] Ba evaluator có unit test.
- [ ] CLI exit code `0` khi compliant, khác `0` khi Fail.
- [ ] Output chứa evidence ngắn cho mỗi failed rule.

### Stop condition

Dừng session khi một repository thật có thể được scan end-to-end và ít nhất một unit test chứng minh evaluator trả kết quả deterministic. Không làm dashboard, database, scheduler hoặc auto-remediation trong buổi đầu.
