# Ý tưởng hôm nay: RestoreProof — Automated Backup Restore Drill

## 1. Tóm tắt ý tưởng

**RestoreProof** là một công cụ self-hosted dành cho developer, homelab owner và team nhỏ, tự động lấy một backup gần nhất, restore nó vào môi trường tạm, chạy các health/data checks rồi xóa môi trường test sau khi hoàn tất. Mục tiêu không phải tạo thêm một hệ thống backup, mà trả lời câu hỏi khó hơn: **“Backup này có thực sự restore được, mất bao lâu, và ứng dụng sau restore có chạy đúng không?”**

- **Project size:** Medium
- **Estimated MVP time:** 2–4 tuần làm ngoài giờ
- **Primary category:** Self-hosting / reliability / backup verification

## 2. Bài toán thực tế

### Confirmed facts

AWS Well-Architected khuyến nghị định kỳ restore backup sang một vị trí mới và chạy test để xác minh integrity; tài liệu cũng chỉ ra các anti-pattern như chỉ giả định backup tồn tại, giả định backup có thể recover, hoặc không biết restore có đáp ứng RTO/RPO hay không.

Nguồn: [AWS Well-Architected — REL09-BP04 Perform periodic recovery of the data](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_backing_up_data_periodic_recovery_testing_data.html)

AWS Backup còn có một sản phẩm riêng tên **Restore testing**, cho phép tạo restore-testing plan theo lịch, tự restore recovery point, theo dõi thời gian restore, chạy validation và xóa resource sau test. Điều này là bằng chứng mạnh rằng “backup validation bằng restore thực tế” là một bài toán riêng, khác với việc chỉ kiểm tra backup job thành công.

Nguồn: [AWS Backup — Restore testing](https://docs.aws.amazon.com/aws-backup/latest/devguide/restore-testing.html)

`restic` hỗ trợ restore snapshot bằng lệnh `restic restore ... --target ...` và có `restic check` / `restic check --read-data` để kiểm tra repository metadata hoặc toàn bộ dữ liệu.

Nguồn: [restic documentation — Introduction](https://restic.readthedocs.io/en/stable/010_introduction.html), [restic — Restoring from backup](https://restic.readthedocs.io/en/v0.19.1/050_restore.html)

Docker Compose hỗ trợ `healthcheck` và `depends_on.condition: service_healthy`, đủ để dựng một application stack tạm và chỉ bắt đầu dependent service khi database/service dependency đã healthy.

Nguồn: [Docker Docs — Compose services / healthcheck](https://docs.docker.com/reference/compose-file/services/), [Docker Docs — Control startup order](https://docs.docker.com/compose/how-tos/startup-order/)

### Observation

Nhiều backup tool tập trung vào việc:

- tạo backup;
- giữ nhiều snapshot;
- encrypt data;
- upload sang remote storage;
- verify repository structure.

Nhưng developer nhỏ hoặc homelab thường không có một pipeline tự động thực hiện toàn bộ chuỗi:

```text
backup
→ restore vào sandbox
→ boot database/app
→ kiểm tra dữ liệu quan trọng
→ đo restore duration
→ ghi bằng chứng
→ cleanup
```

Điểm quan trọng là **repository check thành công không đồng nghĩa application recovery thành công**. Một PostgreSQL dump có thể restore được nhưng thiếu extension; một volume có thể tồn tại nhưng app không boot; một backup có thể đúng dữ liệu nhưng restore quá lâu so với kỳ vọng.

### Bài toán hiện tại

Developer có thể đang backup:

- PostgreSQL dump;
- SQL Server `.bak`;
- Docker volumes;
- application files;
- config files;
- personal documents;
- self-hosted services như Gitea, Vaultwarden, Immich, Paperless, Home Assistant.

Họ thường thấy backup job báo `Success`, nhưng ít khi thực hiện recovery drill vì quy trình thủ công tốn thời gian và dễ phá environment đang chạy.

### Assumption cần validation

Giả định của MVP là một nhóm người dùng cụ thể — developer/self-hoster có 1–10 service Docker — sẵn sàng dùng một tool nếu chỉ cần khai báo:

- backup source;
- restore command;
- validation command;
- schedule;

sau đó nhận được bằng chứng PASS/FAIL rõ ràng.

Giả định này cần được kiểm tra bằng phỏng vấn 3–5 người đang thực sự vận hành backup cá nhân/team nhỏ.

## 3. Người dùng mục tiêu

### Primary user

Một developer hoặc self-hoster đang chạy 2–10 ứng dụng trên VPS, mini PC hoặc NAS bằng Docker Compose và đã có backup bằng `restic`, script, `pg_dump`, SQL Server backup hoặc snapshot volume.

### Context of use

- Backup chạy hằng ngày/tuần.
- Restore thực tế chỉ được làm khi migrate hoặc có sự cố.
- Không có dedicated SRE/infra team.
- Muốn biết backup có usable trước khi cần tới nó.

### Main pain point

Không biết backup có thực sự recover được cho đến lúc có sự cố.

### Current workaround

- chạy `restic check`;
- nhìn log backup job;
- restore thủ công vài tháng một lần;
- copy dump sang máy test;
- tin rằng `pg_dump`/volume backup thành công nghĩa là recovery thành công.

### Lý do user thử RestoreProof

Tool không yêu cầu thay hệ thống backup hiện tại. Nó đứng **sau backup** như một lớp verification.

## 4. Giải pháp đề xuất

RestoreProof định nghĩa mỗi workload bằng một **Restore Drill Plan**.

Ví dụ:

```yaml
name: personal-gitea
schedule: "0 3 * * 0"
backup:
  provider: restic
  repository: s3:s3.amazonaws.com/my-backups/gitea
  snapshot: latest
restore:
  target: ./workspaces/gitea
  command: restic restore latest --target ${RESTORE_DIR}
validation:
  - type: file_exists
    path: data/gitea/gitea.db
  - type: docker_compose
    file: restore-compose.yml
  - type: http
    url: http://restore-gitea:3000/api/healthz
  - type: sqlite_query
    database: data/gitea/gitea.db
    query: "select count(*) from user"
    min: 1
cleanup:
  ttl_minutes: 30
```

### Main workflow

1. User tạo Restore Drill Plan.
2. Scheduler bắt đầu drill.
3. Hệ thống tạo isolated working directory.
4. Fetch/restore backup gần nhất.
5. Chạy pre-validation trên files/checksum.
6. Nếu workload cần runtime, chạy Docker Compose sandbox.
7. Chờ health checks.
8. Chạy validation rules:
   - HTTP status;
   - database query;
   - row count;
   - file existence;
   - checksum;
   - custom script.
9. Đo:
   - restore duration;
   - startup duration;
   - validation duration;
   - total recovery duration.
10. Lưu report.
11. Gửi notification.
12. Cleanup containers/files/network.

### Input

- backup provider/config;
- credentials reference;
- restore command hoặc adapter;
- optional Docker Compose file;
- validation rules;
- schedule;
- max runtime;
- retention policy cho reports.

### Processing

- resolve latest backup;
- restore;
- launch sandbox;
- validate;
- capture logs;
- calculate timing/metrics;
- cleanup.

### Output

Một report ví dụ:

```text
Restore Drill: personal-gitea
Result: PASS
Backup snapshot: 2026-08-17 02:00 UTC
Restore duration: 02m14s
App startup: 00m23s
Validation: 5/5 passed
Total recovery time: 02m51s
Recovered data age: 11h52m
Cleanup: Success
```

### User control

Tool **không tự promote restored environment vào production**. User quyết định:

- validation rules;
- schedule;
- backup snapshot selection;
- resource limits;
- acceptable recovery duration;
- RPO/RTO thresholds.

### Key differentiator

RestoreProof không cạnh tranh với `restic`, Borg, cloud backup hay NAS backup. Nó là **proof-of-recovery orchestration layer**.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Một backup chỉ có giá trị khi restore được. Tool tạo bằng chứng định kỳ thay vì sự tự tin dựa trên log backup job.

### Technical learning value

Dự án cho phép học sâu:

- process orchestration;
- container lifecycle;
- isolation;
- reliable background jobs;
- timeouts;
- resource cleanup;
- database restore;
- backup semantics;
- secret handling;
- RPO/RTO measurement;
- observability.

### Phù hợp solo developer

MVP chỉ cần hỗ trợ:

1. local/restic backup;
2. restore folder;
3. Docker Compose sandbox;
4. HTTP/file/custom-script validation.

Không cần xây backup engine.

### Vẫn hữu ích nếu chỉ có một user

Có thể dùng ngay cho các project cá nhân, VPS, database test hoặc self-hosted services. Giá trị không phụ thuộc network effect.

### Điều có thể làm project thất bại

Nếu target audience thấy restore drill quá tốn storage/CPU hoặc backup workload quá đa dạng để cấu hình đơn giản, tool sẽ khó được dùng định kỳ.

### Strongest reason not to build

Nếu chỉ có một PostgreSQL database nhỏ và người dùng đã có CI script restore + test rất đơn giản, một Bash/PowerShell script có thể đủ. RestoreProof chỉ đáng build khi cần quản lý nhiều workload, lịch chạy, history, timing, cleanup và notification.

## 7. Luồng hoạt động

```text
Scheduler / Manual trigger
        ↓
Load DrillPlan
        ↓
Acquire per-plan lock
        ↓
Create isolated workspace
        ↓
Resolve backup snapshot
        ↓
Check RPO / snapshot age
        ↓
Restore data
        ↓
Restore failed? ─── yes ──> Report FAIL → Cleanup
        ↓ no
Run pre-start validations
        ↓
Start sandbox if configured
        ↓
Wait for health / readiness
        ↓
Run validation rules
        ↓
Calculate timings + result
        ↓
Persist report
        ↓
Notify
        ↓
Cleanup workspace/container/network
```

### Failure cases quan trọng

#### Backup source unavailable

- Retry có giới hạn.
- Không fallback sang snapshot không rõ nguồn.
- Result = `BackupUnavailable`.

#### Backup quá cũ

Restore vẫn có thể chạy nhưng report = `FailRpo` hoặc `Warning`, tùy policy.

#### Restore process timeout

Kill process tree và đánh dấu `RestoreTimeout`.

#### Docker container không healthy

Capture logs trước khi cleanup.

#### Validation command treo

Mỗi rule có timeout riêng.

#### Cleanup lỗi

Drill result có thể PASS về data nhưng `CleanupStatus = Failed`; tool phải retry cleanup và báo riêng vì leaked containers/storage có thể tích tụ.

#### Scheduler chạy duplicate

Per-plan distributed/advisory lock để không chạy hai restore drill cùng workload cùng lúc.

## 9. Công nghệ đề xuất

### .NET 10 + ASP.NET Core

Phù hợp với long-running orchestration, process handling, background workers và REST API.

**Simpler alternative:** một .NET console app trước khi thêm web UI.

**Khi outgrow:** không phải vấn đề chính; bottleneck sẽ là Docker/IO/concurrent restores.

### EF Core + PostgreSQL

Lưu history và metrics dễ dàng.

**Simpler alternative:** SQLite trong MVP local-only.

**Khi outgrow:** PostgreSQL đủ cho rất lâu; volume data thấp.

### Hangfire

Phù hợp lịch định kỳ, retry và visibility.

**Simpler alternative:** Quartz.NET hoặc `BackgroundService`.

**Khi outgrow:** nếu có hàng trăm remote agents mới cần queue/distributed orchestration.

### restic 0.19.x

Restic cung cấp snapshot, restore, check và scripting-friendly command line. Documentation chính thức chỉ rõ có thể restore snapshot vào target directory và chạy repository check.

Nguồn: [restic documentation](https://restic.readthedocs.io/en/stable/)

**Simpler alternative:** local tar/zip backup adapter để phát triển MVP.

### Docker Compose

Dùng để boot restored application stack trong môi trường ephemeral.

Docker Compose hỗ trợ healthcheck và startup dependency conditions, rất phù hợp với validation sandbox.

Nguồn: [Docker Docs — healthcheck](https://docs.docker.com/reference/compose-file/services/)

**Simpler alternative:** chỉ chạy database container bằng `docker run`.

### Vue 3

Dashboard lịch sử PASS/FAIL, recovery time và drill details.

### Playwright

Chỉ cần khi UI ổn định, dùng E2E test cho plan → run → report.

### GitHub Actions

Build/test/publish container image.

### Deployment target

VPS hoặc mini PC/Linux host.

Cloud deployment cần cân nhắc vì worker cần truy cập backup repository và Docker engine.

## 11. API và tích hợp

### restic CLI

**Purpose:** list snapshot, restore, check.

**Authentication:** repository password + backend credentials nếu dùng S3/B2/etc.

**Cost/rate limit:** phụ thuộc storage provider, download full backup có thể tạo egress cost.

**Privacy:** restored data rất nhạy cảm; workspace phải nằm trên trusted host và cleanup sau run.

**Fallback:** local folder/tar adapter.

### Docker Engine / Docker Compose

**Purpose:** dựng sandbox runtime.

**Authentication:** local Unix socket hoặc remote TLS endpoint.

**Cost:** local compute/storage.

**Privacy:** restored service chỉ nên bind internal network, không expose public port mặc định.

**Fallback:** validation trực tiếp trên files/database dump nếu app boot không cần thiết.

### Telegram Bot API

**Purpose:** thông báo PASS/FAIL.

**Authentication:** bot token.

**Cost/rate limit:** không đáng kể cho personal usage.

**Privacy:** chỉ gửi metadata, không gửi backup content/log chứa secret.

**Fallback:** email hoặc dashboard.

### PostgreSQL / SQL Server adapters — Phase 2

Có thể dùng native CLI:

- `pg_restore`, `psql`;
- `sqlcmd` hoặc restore qua SQL API/command.

Không nên giả định mọi dump đều cùng format; adapter phải explicit.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem cần deterministic proof:

- restore command exit code;
- container health;
- HTTP status;
- database query;
- row count;
- checksum;
- timing.

AI không nên quyết định “backup hợp lệ hay không”.

### Có thể thêm sau nhưng không cần

Một model có thể tóm tắt failed logs thành explanation, nhưng chỉ là convenience.

Nếu thêm:

- input phải redact secrets;
- output không được thay PASS/FAIL deterministic;
- user phải thấy raw validation result;
- có template fallback.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác nhận người dùng có backup nhưng không test restore định kỳ.

**Main tasks:**

- hỏi 3–5 developer/self-hoster:
  - backup gì?
  - lần cuối restore thử khi nào?

**Expected output:** 3–5 interview notes + quyết định continue/stop.

**Completion criteria:** ít nhất 2 người nói họ muốn tự động hóa restore verification hoặc bản thân bạn có ít nhất 2 workload thực tế để dùng.

**Goal:** manual restore drill hoạt động end-to-end.

**Main tasks:**

- console/API project;
- plan YAML parser;
- workspace manager;
- local backup adapter;
- restic adapter;
- command validator;
- HTTP validator;
- report JSON/Markdown;

**Expected output:** chạy một command và nhận PASS/FAIL.

**Completion criteria:** một restic snapshot được restore vào temp folder, validate file và cleanup thành công.

**Goal:** dễ deploy và vận hành lâu dài.

**Main tasks:**

**Expected output:** documented self-hosted release.

**Completion criteria:** cài mới trên host khác và chạy một drill thành công chỉ dựa trên docs.

## 14. Các bài toán kỹ thuật đáng học

### 1. Reliable long-running orchestration

Restore có thể kéo dài vài phút đến hàng giờ và không thể giả định process luôn thành công.

Cần:

- step state;
- timeout;
- cancellation;
- retry;
- crash recovery.

**Skill:** workflow orchestration và background processing thực tế.

### 2. Cleanup/idempotency

Một run crash giữa chừng vẫn phải dọn:

- container;
- network;
- volumes;
- workspace.

**Skill:** idempotent cleanup, compensation logic, failure recovery.

### 3. Isolation và security

Restored data có thể chứa production secrets và personal data.

Sandbox không được tự động expose public network.

**Skill:** Docker security, secret handling, least privilege.

### 4. Recovery validation design

“File tồn tại” chưa đủ. User phải định nghĩa application-specific proof.

Ví dụ:

```sql
select count(*) from users where is_deleted = false;
```

hoặc:

```http
GET /health/ready → 200
```

**Skill:** testability, invariants, data-quality assertions.

### 5. RPO/RTO measurement

RPO và RTO không chỉ là khái niệm architecture; tool đo trực tiếp:

- backup age;
- total recovery time.

**Skill:** reliability engineering và operational metrics.

## 15. Rủi ro và cách xử lý

### Technical complexity

**Risk:** mỗi backup format cần cách restore khác nhau.

**Mitigation:** adapter interface nhỏ; MVP chỉ local/restic.

### Scope expansion

**Risk:** biến thành full backup platform.

**Mitigation:** nguyên tắc project: **never own backup creation in MVP**. Chỉ verify restore.

### Data privacy

**Risk:** restored production data tồn tại tạm trên disk.

**Mitigation:**

- configurable encrypted disk/workspace;
- cleanup luôn chạy;
- no public port;
- artifacts không chứa raw data;
- retention mặc định ngắn.

### Security

**Risk:** arbitrary command execution từ plan.

**Mitigation:** MVP single-admin/self-hosted; về sau dùng allowlisted validation types thay generic shell cho multi-user mode.

### Docker socket privilege

**Risk:** app có Docker socket gần như có quyền root trên host.

**Mitigation:** tách privileged worker, Unix user riêng, remote Docker socket qua TLS hoặc document single-host trust boundary rõ ràng.

### API dependency

Không đáng kể ở core MVP vì phần lớn local tools.

### Storage/egress cost

**Risk:** weekly full restore từ S3/B2 có thể tốn bandwidth/egress.

**Mitigation:**

- run monthly;
- chọn subset workload;
- local mirror;
- estimate restored bytes trước run;
- configure max download size.

### Unreliable external data

Backup repository có thể bị temporary unavailable.

**Mitigation:** phân biệt infrastructure failure với invalid backup.

### Legal/platform restrictions

Không có scraping; user phải có quyền với backup data. Nếu dữ liệu chứa customer information, restore test environment vẫn phải tuân thủ chính sách privacy của tổ chức.

### User adoption

**Risk:** setup validation rules mất công.

**Mitigation:** cung cấp templates cho PostgreSQL, Docker Compose, Gitea, Vaultwarden, generic HTTP app.

### Maintenance burden

**Risk:** Docker/restic CLI output thay đổi.

**Mitigation:** pin versions trong CI fixtures, ưu tiên JSON output khi tool hỗ trợ, adapter contract tests.

### 5 test scenarios quan trọng nhất

1. **Valid snapshot:** restore thành công, 4/4 checks PASS, workspace bị xóa.
2. **Corrupted/missing restore data:** restore hoặc validation FAIL, report giữ đúng failure evidence.
3. **App never becomes healthy:** timeout, capture container logs, cleanup vẫn chạy.
4. **Process bị crash giữa drill:** worker restart không tạo duplicate restore; orphan resource được cleanup.
5. **Backup quá cũ:** restore có thể thành công nhưng RPO policy phải báo FAIL/WARN đúng cấu hình.

## 20. Việc cần làm ngay hôm nay

### Development objective — 60–120 phút

Tạo vertical slice nhỏ nhất chứng minh concept:

> Tạo một restic repo local → backup sample data → RestoreProof console app restore snapshot mới nhất vào temp directory → kiểm tra một file expected → in PASS/FAIL + duration → cleanup.

Không có database, UI, Docker hay scheduler trong session đầu.

### First vertical slice

`ResticRestorer` chạy:

```bash
restic restore latest --target <temp-path>
```

Restic official docs xác nhận `latest` có thể dùng để restore snapshot mới nhất vào target directory.

Nguồn: [restic — Restoring from backup](https://restic.readthedocs.io/en/v0.19.1/050_restore.html)

Sau restore:

1. locate `health.txt`;
2. đọc content;
3. assert bằng `restore-proof-ok`;
4. in result.

Expected output:

```text
RestoreProof Drill
Snapshot: latest
Restore: PASS
Validation: PASS
Restore duration: 00:00:01.842
Recovered file: health.txt
Cleanup: PASS
Overall: PASS
```

### ProcessRunner requirements

Ngay session đầu nên làm đúng:

- dùng `ProcessStartInfo.ArgumentList` thay vì build shell string;
- capture stdout/stderr;
- có `CancellationToken`;
- có timeout;
- kill entire process tree khi timeout;
- không log password.

### Verification checklist

- [ ] `dotnet build` thành công.
- [ ] restic local repository được init.
- [ ] sample snapshot tồn tại.
- [ ] CLI restore snapshot vào temp folder.
- [ ] `health.txt` được tìm thấy.
- [ ] content đúng → `Overall: PASS`.
- [ ] đổi expected content sai → `Overall: FAIL`.
- [ ] restore directory bị cleanup sau run.
- [ ] stdout/stderr được capture nếu restic lỗi.
- [ ] có ít nhất 1 unit test cho `FileExistsRule` hoặc content validation.

### Stop condition

Dừng session ngay khi **một backup thật được restore bằng restic, một validation deterministic chạy thành công và workspace được cleanup tự động**.

Không thêm:

- PostgreSQL;
- Docker Compose;
- Hangfire;
- Vue;
- Telegram;
- database persistence.

Những phần đó chỉ bắt đầu sau khi vertical slice đầu tiên chứng minh rằng orchestration restore → validate → cleanup hoạt động.
