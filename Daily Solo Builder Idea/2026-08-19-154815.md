# Ý tưởng hôm nay: UpgradeProof — Dependency Upgrade Canary

## 1. Tóm tắt ý tưởng

UpgradeProof là một công cụ self-hosted giúp developer **thử nâng cấp dependency trong môi trường cô lập trước khi chạm vào branch làm việc chính**, sau đó tự động chạy restore, build, test và tạo báo cáo rủi ro cho từng package upgrade. Sản phẩm phù hợp với developer .NET hoặc team nhỏ có nhiều repository và thường xuyên trì hoãn nâng NuGet package vì sợ breaking change hoặc mất thời gian kiểm tra thủ công.

- Người dùng chính: backend developer .NET duy trì một hoặc nhiều repository có dependency cập nhật thường xuyên.
- Vấn đề chính: biết package đã cũ là dễ, nhưng xác định bản nâng cấp nào thực sự an toàn mới tốn thời gian.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Dependency update là công việc lặp lại trong hầu hết project sống lâu hơn vài tháng. Developer có thể biết package nào outdated khá dễ, nhưng mỗi upgrade lại kéo theo một chuỗi câu hỏi:

- Project còn restore được không?
- Có compile error mới không?
- Unit/integration test có fail không?
- API public nào đã đổi?
- Có package transitive nào thay đổi bất thường không?
- Upgrade major version có phá behavior runtime không?

**Confirmed facts:**

- .NET CLI hiện hỗ trợ `dotnet package list --outdated` và output JSON, cho phép lấy danh sách package outdated theo cách machine-readable. Microsoft Learn cũng ghi nhận từ .NET 10, noun-first command `dotnet package list` được dùng thay cho form cũ `dotnet list package`. Nguồn: Microsoft Learn — `dotnet package list`: https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-list
- .NET 10 có `dotnet package update`, có thể cập nhật package trực tiếp và hỗ trợ mode `--vulnerable` cho package có security advisory. Nguồn: Microsoft Learn — `dotnet package update`: https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-update
- GitHub Dependabot có thể tự động tạo pull request cho version update hoặc security update. Nguồn: GitHub Docs — Dependabot version updates: https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-version-updates
- Renovate cung cấp Dependency Dashboard và approval workflow cho dependency updates. Nguồn: Renovate Docs — Dependency Dashboard: https://docs.renovatebot.com/key-concepts/dashboard/

**Observation:** tooling hiện tại giải quyết tốt bài toán “phát hiện update” và “tạo PR”, nhưng developer vẫn phải dựa vào CI để biết update đó có thực sự an toàn với codebase của mình hay không.

**Assumption cần kiểm chứng:** với solo developer có nhiều repository, một tool chạy local/self-hosted, đánh giá upgrade theo kiểu “canary experiment” trước khi tạo PR sẽ giảm đáng kể thời gian và số PR dependency bị fail.

Workaround phổ biến hiện nay:

- Chạy `dotnet package list --outdated` rồi update thủ công từng package.
- Để Dependabot/Renovate tạo PR hàng loạt rồi xử lý PR nào đỏ CI.
- Chờ vài tháng rồi nâng nhiều package cùng lúc.
- Upgrade trực tiếp trên branch hiện tại rồi revert nếu lỗi.

Điểm bất tiện là developer thường biết “package nào cần update” nhưng không có một lịch sử tập trung cho biết **upgrade nào từng được thử, kết quả ra sao, fail ở bước nào và package nào đang liên tục bị block**.

## 3. Người dùng mục tiêu

### Primary user

.NET backend developer duy trì 3–20 repository cá nhân, internal tool hoặc SaaS nhỏ.

### Context of use

- Có nhiều project dùng ASP.NET Core, EF Core, Microsoft.Extensions, Azure SDK, Microsoft Graph SDK hoặc third-party packages.
- CI chạy build/test nhưng dependency updates thường được xử lý ad hoc.
- Không muốn Dependabot tạo quá nhiều PR noise.

### Main pain point

Developer muốn biết nhanh:

> “Nếu nâng package A từ 8.0.3 lên 9.0.0 thì project của tôi có còn build và test pass không?”

### Current workaround

Tạo branch tạm, sửa `.csproj`, restore, build, test rồi xóa branch.

### Reason they would try UpgradeProof

Tool biến quy trình trên thành một thao tác repeatable:

```text
scan → choose upgrade → isolated run → build/test → report
```

và lưu lịch sử để không phải thử lại cùng một upgrade nhiều lần.

## 4. Giải pháp đề xuất

Người dùng đăng ký một local repository hoặc Git repository vào UpgradeProof.

Ví dụ:

```text
C:\src\OrderService
```

Tool scan solution bằng:

```bash
dotnet package list --outdated --format json
```

Sau đó hiển thị:

```text
Microsoft.EntityFrameworkCore
Current: 9.0.4
Latest: 10.0.1
Risk: Major
Status: Not tested
```

Người dùng chọn `Test upgrade`.

UpgradeProof sẽ:

1. Tạo working copy tạm bằng `git worktree` hoặc clone vào workspace riêng.
2. Áp dụng đúng một upgrade.
3. Chạy restore.
4. Chạy build.
5. Chạy test.
6. Ghi lại elapsed time, exit code và log summary.
7. So sánh dependency graph trước/sau.
8. Trả về verdict.

Ví dụ output:

```text
Upgrade
Microsoft.EntityFrameworkCore 9.0.4 → 10.0.1

Restore: PASS
Build: FAIL
Tests: NOT RUN

3 compile errors
- UseSqlServer(...): overload changed
- RelationalEventId.X no longer available

Verdict: BLOCKED
```

### What is automated

- Package discovery.
- Workspace isolation.
- Package update.
- Restore/build/test pipeline.
- Log collection.
- Cleanup workspace.
- Persist experiment result.

### What remains under user control

- Package nào được test.
- Có test major update hay không.
- Command test custom.
- Có tạo branch/PR sau khi pass hay không.

### Key differentiator

UpgradeProof không cạnh tranh trực tiếp với Dependabot/Renovate ở việc tạo update PR. Nó tập trung vào câu hỏi:

> “Upgrade này có pass trên codebase của tôi trước khi tôi quyết định nhận nó hay không?”

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Ngay cả chỉ dùng cá nhân, tool giúp xử lý backlog NuGet update có hệ thống hơn và giảm thao tác branch/revert thủ công.

### Technical learning value

Project có nhiều bài toán đáng học:

- Process orchestration.
- Git worktree management.
- Long-running jobs.
- Structured command output parsing.
- Workspace isolation.
- Retry và cancellation.
- Log summarization.
- Dependency graph analysis.

### Vì sao phù hợp solo developer

Core workflow rất rõ và giới hạn:

```text
repository → package candidate → isolated experiment → verdict
```

Không cần distributed system, ML model, data lake hay enterprise identity ở MVP.

### Có giá trị ngay cả khi chỉ có một user

Developer có thể chạy tool trên chính các repository cá nhân và dùng lịch sử experiments như một “dependency maintenance ledger”.

### Điều gì làm ý tưởng thất bại

- Developer thấy Dependabot + CI đã đủ.
- Test suite hiện tại quá yếu nên “PASS” không phản ánh runtime safety.
- Workspace setup quá phức tạp với repo có private feeds hoặc secret-dependent tests.

### Lý do mạnh nhất để không build

Nếu chỉ duy trì một repository nhỏ với ít dependency và CI rất nhanh, việc để Dependabot tạo PR rồi nhìn CI có thể đơn giản hơn đáng kể.

## 6. Phạm vi MVP

### Must have

- Add một local Git repository.
- Detect `.sln` hoặc `.csproj`.
- Chạy `dotnet package list --outdated --format json`.
- Hiển thị top-level outdated packages.
- Chọn một package/version để test.
- Tạo isolated workspace.
- Update package.
- Chạy `dotnet restore`.
- Chạy `dotnet build`.
- Chạy `dotnet test`.
- Persist experiment result.
- Cleanup workspace.
- UI hoặc CLI hiển thị PASS/FAIL.

### Should have

- Custom build/test command per repository.
- Timeout/cancellation.
- Log viewer.
- Dependency graph diff.
- Filter patch/minor/major.
- Skip package/version đã test gần đây.
- Security/vulnerable package scan.

### Later

- GitHub PR creation.
- Renovate/Dependabot integration.
- Test multiple related packages as a group.
- Containerized test environment.
- Runtime smoke tests.
- Database migration compatibility check.
- AI-assisted failure explanation.
- Multi-user/team dashboard.

## 7. Luồng hoạt động

### Normal flow

User add repository
→ validate Git repo và .NET project
→ scan package list
→ parse outdated package JSON
→ user chọn candidate
→ create experiment
→ create isolated worktree
→ capture baseline dependency graph
→ apply package update
→ restore
→ build
→ test
→ capture updated graph
→ save result
→ cleanup workspace
→ show verdict.

### Failure flows

#### Restore fail

- Experiment dừng.
- Lưu restore log.
- Verdict = `RestoreFailed`.

#### Build fail

- Không chạy test.
- Lưu compiler errors.
- Verdict = `BuildFailed`.

#### Test fail

- Lưu failed test list.
- Verdict = `TestsFailed`.

#### Command timeout

- Kill child process tree.
- Verdict = `TimedOut`.

#### Workspace cleanup fail

- Đánh dấu workspace orphaned.
- Cleanup job xử lý lại sau.

#### Private NuGet feed không auth

- Hiển thị rõ lỗi source/auth.
- Không ghi package là incompatible.

## 8. Kiến trúc đề xuất

### Architecture style

**Modular monolith**.

Các module logic:

- `Repositories`
- `PackageScanning`
- `Experiments`
- `ProcessRunner`
- `Workspaces`
- `Reports`

### Frontend

Vue 3 dashboard nhỏ.

Cần vì xem experiment history và log dễ hơn CLI thuần.

**Simpler MVP alternative:** bắt đầu CLI, web UI ở Phase 3.

### Backend

ASP.NET Core API.

Nhiệm vụ:

- Manage repositories.
- Queue experiments.
- Persist results.
- Serve logs/results.

### Database

SQLite cho MVP local-first.

Lý do:

- Single-user.
- Zero infrastructure.
- Backup đơn giản.

PostgreSQL chỉ cần khi deploy multi-user/server mode.

### Background worker

`BackgroundService` xử lý experiment queue.

Không cần Hangfire ban đầu vì workflow đơn giản và số job nhỏ.

### Queue

In-process bounded channel hoặc DB job table.

Khuyến nghị DB job table nếu muốn recover sau restart.

### Cache

Không cần ở MVP.

### File storage

Filesystem cho raw logs.

Database chỉ giữ metadata và log summary.

### Authentication

Không cần nếu app chỉ bind localhost.

Nếu deploy VPS thì thêm single-user login hoặc reverse proxy auth.

### External APIs

Không bắt buộc cho core MVP.

NuGet data được lấy qua .NET CLI và configured package sources.

### AI model

Không cần cho core workflow.

### Notification

Không cần ban đầu. Có thể thêm Telegram/email khi batch experiment chạy lâu.

### Logging

Serilog/OpenTelemetry-compatible structured logs.

### Deployment

Primary deployment nên là local desktop-adjacent service hoặc Docker trên developer machine.

Không nên chạy remote server nếu source repository/private credentials chỉ tồn tại local.

## 11. API và tích hợp

### .NET CLI

**Purpose:** package discovery, restore, build, test và package update.

**Authentication:** kế thừa NuGet configuration của máy chạy.

**Cost:** miễn phí.

**Concern:** private package source có thể cần credential provider hoặc `NuGet.config`.

**Fallback:** cho phép custom shell command.

### Git CLI

**Purpose:** validate clean tree và tạo/remove worktree.

**Authentication:** không cần nếu xử lý local repository.

**Cost:** miễn phí.

**Concern:** repo có submodule/LFS cần xử lý riêng.

**Fallback:** isolated copy mode.

### GitHub API — later only

**Purpose:** tạo branch/PR khi experiment pass.

**Authentication:** PAT hoặc GitHub App.

**Rate limit:** phụ thuộc authentication mode.

**Privacy:** source repo permission phải tối thiểu cần thiết.

**Fallback:** chỉ output patch/commands cho user tự commit.

### Dependabot/Renovate

Không cần integration trong MVP.

Confirmed fact: cả hai đã có workflow dependency update riêng; UpgradeProof nên bổ sung chứ không clone chúng.

Sources:

- GitHub Dependabot: https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-version-updates
- Renovate Dashboard: https://docs.renovatebot.com/key-concepts/dashboard/

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

Core verdict phải deterministic:

```text
restore exit code
build exit code
test exit code
```

AI không được quyết định PASS/FAIL.

### Optional AI task

AI có thể tóm tắt compiler/test failures thành:

```json
{
  "summary": "EF Core upgrade removed API used by 3 files",
  "likelyCause": "Breaking API change",
  "affectedFiles": ["..."],
  "suggestedNextStep": "..."
}
```

### Required context

- Package from/to version.
- Compiler error lines.
- Failed test names.
- Tối đa một đoạn code context nhỏ quanh lỗi nếu user cho phép.

### Validation

AI output chỉ là explanation.

Deterministic status luôn dựa vào process exit codes.

### Fallback

Hiển thị raw compiler/test logs.

### Risks

- Hallucination về nguyên nhân.
- Source code privacy.
- API cost.
- Latency.

Vì vậy AI không nằm trong MVP.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác nhận dependency upgrade experiment thực sự tiết kiệm thao tác.

**Main tasks:**

- Chọn 3 repository .NET thật.
- Chạy `dotnet package list --outdated --format json`.
- Chọn 5 package updates.
- Thử thủ công bằng git worktree + build/test.
- Ghi thời gian mỗi experiment.

**Expected output:** bảng 5 upgrades với PASS/FAIL và thời gian xử lý.

**Completion criteria:** quy trình lặp đủ giống nhau để automation có giá trị rõ ràng.

### Phase 1 — Core MVP

**Goal:** một command có thể test một package upgrade end-to-end.

**Main tasks:**

- CLI project.
- Detect solution.
- Parse package JSON.
- Create worktree.
- Apply update.
- Restore/build/test.
- Print verdict.
- Cleanup worktree.

**Expected output:**

```bash
upgradeproof test Microsoft.EntityFrameworkCore --to 10.0.1
```

**Completion criteria:** command trả đúng PASS/FAIL trên ít nhất 3 repository.

### Phase 2 — Reliability

**Goal:** experiment không phá repo và recover được khi lỗi.

**Main tasks:**

- Timeout.
- Cancellation token.
- Process tree kill.
- Dirty repo validation.
- Workspace cleanup recovery.
- SQLite persistence.
- Structured logs.
- Unit/integration tests.

**Expected output:** experiment history đáng tin cậy.

**Completion criteria:** kill app giữa experiment rồi restart không làm mất trạng thái hoặc để workspace vô hạn.

### Phase 3 — Useful expansion

**Goal:** biến tool thành dependency maintenance dashboard.

**Main tasks:**

- Vue dashboard.
- Scan all outdated packages.
- Risk categorization patch/minor/major.
- History filter.
- Dependency graph diff.
- Batch queue.

**Expected output:** nhìn một màn hình biết package nào safe, blocked, chưa test.

### Phase 4 — Production readiness

**Goal:** dùng ổn định hàng tuần.

**Main tasks:**

- Installer/Docker option.
- Backup SQLite.
- Config docs.
- Health endpoint.
- Metrics.
- Log retention.
- GitHub Actions release pipeline.

**Completion criteria:** tool chạy ổn định trên repository thật trong ít nhất vài tuần mà không làm hỏng working tree.

## 14. Các bài toán kỹ thuật đáng học

### 1. Process orchestration

Chạy nhiều child process nối tiếp nhau, capture stdout/stderr, cancellation và timeout.

**Skill improved:** production-grade CLI/process management.

### 2. Workspace isolation

Đảm bảo experiment không thay đổi repository đang làm việc.

**Skill improved:** Git internals, worktree, filesystem lifecycle.

### 3. Long-running workflow state

Experiment có nhiều stage và có thể fail giữa chừng.

**Skill improved:** workflow state machine, recovery và persistence.

### 4. Dependency graph comparison

Một direct package update có thể làm nhiều transitive package đổi theo.

**Skill improved:** graph analysis và change attribution.

### 5. Reliable cleanup

Workspace/temp files không được tích tụ khi process crash.

**Skill improved:** resource lifecycle, idempotent cleanup.

## 15. Rủi ro và cách xử lý

### False sense of safety

**Risk:** build/test pass nhưng runtime vẫn lỗi.

**Mitigation:** verdict phải ghi rõ `Build/Test validated`, không gọi là “fully safe”. Cho phép custom smoke-test command sau này.

### Repo setup phức tạp

**Risk:** project cần Docker, DB, secrets hoặc external services.

**Mitigation:** per-repository custom test command; cho phép chỉ chạy restore/build ở MVP.

### Private NuGet feed

**Risk:** experiment fail vì auth thay vì compatibility.

**Mitigation:** classify infrastructure/auth errors khác với package incompatibility.

### Git worktree edge cases

**Risk:** submodule, Git LFS hoặc custom hooks.

**Mitigation:** detect unsupported repo features và fallback clone/copy mode.

### Scope expansion

**Risk:** biến thành Renovate clone.

**Mitigation:** giữ product boundary là “test upgrade”, không tự động dependency policy engine trong MVP.

### Security

**Risk:** tool chạy commands từ repository không tin cậy.

**Mitigation:** MVP chỉ cho local trusted repository; không nhận arbitrary public repo từ internet trong server mode.

### Maintenance burden

**Risk:** .NET CLI output/version behavior có thể đổi.

**Mitigation:** dùng JSON format có explicit output version khi phù hợp và integration-test parser với fixtures.

## 16. Kiểm thử

### Unit tests

- Package JSON parser.
- Version/risk classification.
- Experiment state transitions.
- Command result mapping.

### Integration tests

Tạo fixture repositories nhỏ để test restore/build/test.

### End-to-end tests

CLI hoặc UI:

```text
scan → select update → experiment → verdict
```

### Failure-path tests

- Restore fail.
- Build fail.
- Test fail.
- Timeout.
- App crash/restart.

### Security tests

- Path traversal.
- Arbitrary command injection từ package ID/version.
- Repository outside allowed root.

### 5 test scenario quan trọng nhất

1. Patch upgrade build/test pass → verdict `Passed`.
2. Major upgrade gây compile error → `BuildFailed`, test không chạy.
3. Package source auth fail → classify `InfrastructureFailed`, không đánh dấu incompatible.
4. Cancel experiment giữa test → process con bị terminate và workspace cleanup thành công.
5. Repo chính không có file nào thay đổi sau experiment.

### Technical reliability

- Không làm dirty repository chính.
- Không để orphan workspace.

Không áp dụng cho MVP vì AI chưa dùng.

- Auto-detect package families cần upgrade cùng nhau.
- Docker sandbox.

- Benchmark before/after.
- Generate patch hoặc branch sau khi pass.

- Small SaaS team.

- GitHub.
- Azure DevOps repos.
- Renovate.
- Dependabot PRs.
- NuGet security audit data qua .NET CLI.

### Desktop client

Tauri hoặc .NET MAUI tray app có thể hợp lý nếu muốn local-first UX mạnh hơn.

### Self-hosted/cloud

Self-hosted/local là natural fit.

### Open-source

Core engine rất phù hợp open-source vì developer có thể tự host và đóng góp adapters.

### Speculative

Cross-language support cho npm, Maven, pip, Cargo có thể mở rộng sau, nhưng không nên thiết kế abstraction đa ecosystem từ ngày đầu.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, xây vertical slice đầu tiên:

```text
scan một .NET repo
→ chọn một outdated NuGet package
→ tạo git worktree
→ update package
→ build
→ in PASS/FAIL
→ xóa worktree
```

Chưa cần database, UI hoặc AI.

### Files/components cần tạo

```text
UpgradeProof.sln
src/
  UpgradeProof.Cli/
    Program.cs
    PackageScanner.cs
    WorktreeManager.cs
    ProcessRunner.cs
    UpgradeExperimentRunner.cs
tests/
  UpgradeProof.Tests/
```

### Setup commands

```bash
dotnet new sln -n UpgradeProof
dotnet new console -n UpgradeProof.Cli -o src/UpgradeProof.Cli
dotnet new xunit -n UpgradeProof.Tests -o tests/UpgradeProof.Tests
dotnet sln add src/UpgradeProof.Cli
dotnet sln add tests/UpgradeProof.Tests
dotnet add tests/UpgradeProof.Tests reference src/UpgradeProof.Cli
```

### First vertical slice

#### 1. PackageScanner

Chạy:

```bash
dotnet package list --outdated --format json
```

Parse và in:

```text
Outdated packages
1. Microsoft.Extensions.Http 9.0.4 → 9.0.8
2. Npgsql 9.0.2 → 9.0.4
```

#### 2. WorktreeManager

Tạo temp folder:

```bash
git worktree add <temp-path> HEAD
```

#### 3. Apply one upgrade

Trong temp worktree:

```bash
dotnet package update PACKAGE@VERSION --project path/to/project.csproj
```

Nếu command này không phù hợp với repo fixture đang dùng, fallback session đầu tiên bằng:

```bash
dotnet add path/to/project.csproj package PACKAGE --version VERSION
```

#### 4. Build

```bash
dotnet build --no-restore
```

Nếu restore chưa chạy explicit thì dùng:

```bash
dotnet restore
dotnet build --no-restore
```

#### 5. Output

```text
Experiment
Package: Npgsql
9.0.2 → 9.0.4

Restore: PASS
Build: PASS
Duration: 12.4s

Verdict: PASS
```

#### 6. Cleanup

```bash
git worktree remove <temp-path> --force
```

### Expected result

Có thể chạy một command tương tự:

```bash
dotnet run --project src/UpgradeProof.Cli -- C:\src\MyApi
```

và ít nhất:

- đọc được outdated package,
- chạy một upgrade trong workspace riêng,
- build được workspace,
- in verdict,
- không sửa repository gốc.

### Verification checklist

- [ ] `dotnet package list --outdated --format json` được parse thành object.
- [ ] Tool tạo được temp worktree.
- [ ] Upgrade chỉ xảy ra trong temp worktree.
- [ ] Build exit code được capture chính xác.
- [ ] stdout/stderr được capture.
- [ ] Temp worktree được remove sau khi hoàn tất.
- [ ] `git status` của repository gốc vẫn clean.
- [ ] Có ít nhất một test cho JSON parser hoặc ProcessRunner.

### Stop condition

Dừng session ngay khi một package upgrade thật có thể được test trong isolated worktree và terminal in rõ:

```text
PASS
```

hoặc:

```text
BUILD FAILED
```

trong khi repository gốc vẫn hoàn toàn không thay đổi.
