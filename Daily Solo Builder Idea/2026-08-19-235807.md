# Ý tưởng hôm nay: ReplyLedger — Personal Email Follow-up Tracker

## 1. Tóm tắt ý tưởng

ReplyLedger là một công cụ cá nhân giúp developer hoặc knowledge worker theo dõi các email đã gửi mà **cần chờ phản hồi**, tự phát hiện khi thread có reply mới và nhắc lại khi quá hạn. Thay vì biến toàn bộ inbox thành task manager, người dùng chỉ đánh dấu những email thực sự cần theo dõi và hệ thống duy trì một “follow-up ledger” nhỏ, rõ ràng.

- Người dùng chính: developer, consultant hoặc người thường xuyên phải gửi email chờ phản hồi từ đồng nghiệp/khách hàng.
- Bài toán chính: quên follow-up email quan trọng sau vài ngày vì thread bị chìm trong inbox.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **1–2 tuần**.

## 2. Bài toán thực tế

### Confirmed facts

Microsoft Graph hiện hỗ trợ đọc message trong mailbox, truy cập các thuộc tính như `conversationId`, `internetMessageId`, `sentDateTime`, `receivedDateTime`, `subject` và sender/recipients. Điều này đủ để xây một lớp theo dõi thread mà không cần tải toàn bộ nội dung email nếu MVP chỉ cần metadata. Nguồn: [Microsoft Graph message resource](https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0).

Microsoft Graph cũng hỗ trợ `message: delta` theo từng mail folder, trả về message được thêm, cập nhật hoặc xóa cùng `@odata.nextLink` / `@odata.deltaLink`. Delta query giúp client đồng bộ thay đổi incremental thay vì tải toàn bộ folder mỗi lần. Nguồn: [Microsoft Graph message delta](https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0) và [Delta query overview](https://learn.microsoft.com/en-us/graph/delta-query-overview).

### Observation

Email client thường cung cấp search, flag hoặc reminder, nhưng workflow “email này đang chờ ai trả lời, đã chờ bao lâu, lần cuối mình follow-up khi nào?” thường vẫn phụ thuộc vào trí nhớ hoặc task app riêng.

### Assumption cần kiểm chứng

Người dùng có đủ email “đang chờ phản hồi” để một dashboard chuyên biệt tạo giá trị; nếu chỉ có 1–2 thread mỗi tháng thì Outlook flag hoặc task app có thể đã đủ.

### Cách người dùng thường xử lý hiện tại

- Flag email trong Outlook.
- Tạo task thủ công trong Todoist/Microsoft To Do.
- Đặt calendar reminder.
- Search `Sent Items` vài ngày sau.
- Ghi chú trong Notion hoặc spreadsheet.

Điểm bất tiện là trạng thái task và trạng thái email tách rời. Khi đối phương reply, task vẫn tồn tại cho tới khi người dùng tự đóng.

## 3. Người dùng mục tiêu

**Primary user:** một developer hoặc technical lead xử lý 5–20 email công việc cần follow-up mỗi tuần.

- **Context:** gửi email hỏi QA, PM, khách hàng, vendor, HR hoặc team khác rồi phải chờ phản hồi.
- **Main pain point:** không nhớ thread nào đang chờ, đặc biệt khi có nhiều công việc song song.
- **Current workaround:** flag email, tạo reminder hoặc giữ email unread.
- **Lý do thử công cụ:** muốn một danh sách duy nhất gồm “waiting”, “replied”, “overdue” mà không phải quản lý thủ công hai hệ thống.

MVP chỉ phục vụ **một tài khoản Microsoft 365/Outlook cá nhân**, không cố giải quyết shared mailbox hay team collaboration.

## 4. Giải pháp đề xuất

Người dùng mở ReplyLedger và đánh dấu một sent email là **Needs reply**.

### Main workflow

1. Người dùng chọn email từ danh sách Sent Items gần đây.
2. Chọn deadline, ví dụ `3 ngày làm việc`.
3. ReplyLedger lưu metadata thread và trạng thái `Waiting`.
4. Background worker dùng Microsoft Graph delta query để theo dõi message mới trong Inbox.
5. Khi có message cùng `conversationId`, item chuyển sang `Replied`.
6. Nếu deadline tới mà chưa có reply, item chuyển `Overdue` và gửi notification.
7. Người dùng có thể snooze, close hoặc tạo follow-up mới.

### Input

- Sent email metadata.
- Deadline hoặc số ngày chờ.
- Optional note như `Waiting for API approval`.

### Processing

- Match reply bằng `conversationId` trước.
- Kiểm tra sender/recipients để giảm false positive.
- Track incremental mailbox changes qua delta token.
- Tính trạng thái dựa trên thời gian và reply metadata.

### Output

Dashboard nhỏ gồm:

```text
Waiting     4
Overdue     2
Replied     3

[Overdue] QA sign-off                 4d
[Waiting]  Azure access approval      2d
[Replied]  Contract clarification     1d
```

### Tự động hóa

- Đồng bộ reply mới.
- Cập nhật trạng thái.
- Nhắc overdue.

### User control

- Chọn email nào cần track.
- Chọn deadline.
- Snooze/close.
- Không tự gửi follow-up ở MVP.

### Key differentiator

Không cố biến inbox thành task manager. Tool chỉ quản lý **outbound dependency**: “Tôi đã hỏi ai đó và đang chờ câu trả lời”.

### Ví dụ end-to-end

Thứ Hai, developer gửi email cho QA: `Please confirm the regression result for release 2.4`.

Người dùng mở ReplyLedger → chọn email → `Needs reply in 2 business days`.

- Thứ Ba: chưa có reply → `Waiting`.
- Thứ Tư 16:00: chưa reply → `Overdue` + notification.
- 16:20 QA trả lời trong cùng conversation → worker sync message → status tự chuyển `Replied`.
- User mở item, đọc context và bấm `Close`.

Không cần tự nhớ hoặc update task riêng.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Có thể dùng ngay cho email công việc thật. Dự án vẫn hữu ích với chỉ một user vì giá trị nằm ở giảm missed follow-up, không phụ thuộc network effect.

### Technical learning value

Dự án bao gồm:

- Microsoft Graph delegated auth.
- Delta synchronization.
- Background processing.
- Idempotency.
- Thread matching.
- Timezone/business-day calculation.
- Privacy-preserving metadata storage.

### Phù hợp solo developer

Domain model nhỏ, chỉ vài entity và một integration chính. Không cần microservices, search engine, queue broker hoặc AI trong MVP.

### Điều gì làm dự án thất bại

- Matching reply không đủ chính xác.
- Người dùng phải thao tác quá nhiều để add item.
- Outlook/To Do workflow hiện tại đã đủ tiện.
- Quyền `Mail.Read` khiến người dùng không muốn cấp access.

### Lý do mạnh nhất để không build

Nếu nhu cầu cá nhân chỉ là 2–3 follow-up mỗi tháng, dùng Outlook flag + reminder sẽ đơn giản hơn rất nhiều.

## 7. Luồng hoạt động

### Normal flow

User login
→ consent delegated permission
→ load Sent Items
→ chọn message
→ validate metadata
→ tạo FollowUpItem
→ lưu DB
→ scheduler chạy sync
→ Graph delta trả message mới
→ match `conversationId`
→ cập nhật `Replied`
→ user close.

### Overdue flow

Scheduler
→ query `Waiting` item có `DueAt <= now`
→ đổi `Overdue`
→ tạo NotificationAttempt
→ gửi notification
→ lưu delivery result.

### Alternative flows

**Reply đến từ thread mới:** conversation không match → item vẫn `Waiting`; user có thể manually mark replied.

**Delta token invalid/expired:** reset sync state và bootstrap lại Inbox trong bounded window, ví dụ 30 ngày.

**Graph throttling:** tôn trọng retry delay và retry sau.

**User revoke permission:** đánh dấu integration disconnected, không mất local follow-up data.

**Email bị xóa:** vẫn giữ follow-up metadata nếu user đã track, nhưng deep link có thể unavailable.

## 9. Công nghệ đề xuất

### .NET 10 + ASP.NET Core

**Vì sao phù hợp:** current supported .NET stack, mạnh cho Graph integration, background services và web API.

**Simpler alternative:** một ASP.NET Core Razor Pages project duy nhất.

**Outgrow point:** gần như không cần tách service cho đến khi có nhiều user hoặc nhiều providers.

### Microsoft Graph SDK for .NET

**Vì sao:** typed client, auth integration tốt, giảm boilerplate request handling.

**Simpler alternative:** `HttpClient` gọi Graph REST trực tiếp; cách này thậm chí hữu ích để hiểu delta URLs rõ hơn.

**Outgrow point:** không có vấn đề đáng kể cho quy mô cá nhân.

### PostgreSQL + EF Core

**Vì sao:** reliable persistence cho sync tokens, unique constraints và query deadline.

**Simpler alternative:** SQLite.

**Khi outgrow:** multi-instance deployment hoặc nhiều user thì PostgreSQL vẫn đủ lâu dài.

### BackgroundService

**Vì sao:** chỉ có 2 recurring jobs nhỏ.

**Simpler alternative:** timer trong app, nhưng `BackgroundService` rõ lifecycle hơn.

**Khi outgrow:** nếu cần retry dashboard, persistent jobs và delayed jobs phức tạp, chuyển sang Hangfire.

### Vue 3

**Vì sao:** dashboard interaction đơn giản, quen thuộc.

**Simpler alternative:** Razor Pages.

### Docker

Self-hosted deployment reproducible.

### Playwright

E2E test cho login-mocked flow, create follow-up và status transition.

### GitHub Actions

Build, test và publish Docker image.

## 11. API và tích hợp

### Microsoft Graph — Messages

**Purpose:** lấy Sent Items và metadata reply.

**Authentication:** OAuth delegated permission.

Microsoft Graph documentation hiện liệt kê `Mail.ReadBasic` là delegated least-privileged permission cho một số read scenarios của message delta, trong khi `Mail.Read` cung cấp nội dung đầy đủ hơn. MVP nên thử dùng scope thấp nhất đủ cho các property cần thiết thay vì mặc định xin `Mail.Read`. Nguồn: [message: delta permissions](https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0).

**Rate-limit concern:** Graph có throttling; delta sync giúp giảm lượng dữ liệu đọc so với full polling.

**Privacy:** đây là rủi ro lớn nhất. MVP chỉ lưu metadata cần thiết, không lưu body/attachments.

**Fallback:** nếu sync lỗi, manual `Mark as replied` vẫn cho phép workflow tiếp tục.

### Microsoft Graph Delta Query

**Purpose:** lấy changes incremental trong Inbox.

**Authentication:** cùng Graph delegated token.

**Cost:** không có infrastructure cost riêng ngoài API throttling/usage policy.

**Concern:** phải lưu và xử lý `@odata.nextLink` / `@odata.deltaLink` đúng cách.

**Fallback:** bounded re-sync một khoảng thời gian khi delta state không còn hợp lệ.

### Telegram Bot API — optional

**Purpose:** overdue notification.

**Authentication:** bot token lưu trong secret store/env var.

**Cost:** phù hợp personal use với volume rất thấp.

**Privacy:** notification chỉ gửi subject hoặc alias, không gửi email body.

**Fallback:** in-app overdue badge.

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

AI không cần cho việc xác định deadline, sync hoặc conversation matching.

Một extension hợp lý về sau là **gợi ý sent email nào có khả năng cần follow-up**.

### Exact AI task

Input:

- subject;
- recipient roles/domains;
- một đoạn text cuối email nếu user opt-in;
- metadata thread.

Output structured:

```json
{
  "needsFollowUp": true,
  "confidence": 0.87,
  "suggestedDays": 3,
  "reason": "Explicit request for confirmation"
}
```

### Validation

AI chỉ đưa suggestion; user phải confirm trước khi tạo FollowUpItem.

### Deterministic fallback

Manual `Track` luôn là workflow chính.

### Risks

- Hallucination về intent.
- Privacy khi gửi email text sang model API.
- Latency và cost.

Vì vậy **AI không thuộc MVP**.

## 14. Các bài toán kỹ thuật đáng học

### 1. Incremental synchronization

Phải hiểu `nextLink`, `deltaLink`, cursor persistence và recovery.

**Skill:** xây sync engine hiệu quả thay vì brute-force polling.

### 2. Idempotency

Một message có thể xuất hiện lại trong sync flow; status transition không được duplicate.

**Skill:** unique constraints, idempotent handlers, replay-safe processing.

### 3. Conversation matching

Không phải mọi reply thực tế đều luôn xuất hiện theo cách mong đợi.

**Skill:** deterministic matching + fallback design thay vì cố đạt “AI magic”.

### 4. OAuth token lifecycle

Delegated auth cần xử lý consent, refresh và revoked access.

**Skill:** secure identity integration production-grade.

### 5. Time-based workflow

Deadlines, timezone và business day dễ có edge cases.

**Skill:** temporal modeling, scheduler correctness và deterministic tests.

## 15. Rủi ro và cách xử lý

### Privacy

**Risk:** email metadata là dữ liệu nhạy cảm.

**Mitigation:** chỉ lưu metadata tối thiểu, không lưu body, encryption at rest, configurable retention.

### Permission scope

**Risk:** user không muốn cấp mailbox permission.

**Mitigation:** dùng least-privilege scope đủ cho MVP; giải thích rõ dữ liệu nào được đọc/lưu.

### False reply detection

**Risk:** cùng conversation nhưng reply không giải quyết yêu cầu.

**Mitigation:** trạng thái `Replied` chỉ có nghĩa “có reply mới”, không tự kết luận vấn đề resolved; user vẫn bấm Close.

### Delta sync complexity

**Risk:** pagination/token recovery có bug.

**Mitigation:** isolate MailSync module, test với recorded fixtures và luôn giữ bounded full-resync fallback.

### Notification fatigue

**Risk:** quá nhiều reminder.

**Mitigation:** một reminder khi overdue + optional daily digest; không spam hourly.

### Scope creep

**Risk:** biến thành CRM/task manager.

**Mitigation:** product rule rõ: chỉ track sent email đang chờ reply.

### API dependency

**Risk:** Graph outage/throttling.

**Mitigation:** retry, local state, last-sync indicator và manual status update.

### Adoption

**Risk:** add follow-up thủ công vẫn quá phiền.

**Mitigation:** mục tiêu interaction dưới 5 giây; Outlook add-in chỉ phát triển nếu core MVP chứng minh useful.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, tạo vertical slice đầu tiên:

**Mock sent email → create follow-up → simulate reply → status tự chuyển từ Waiting sang Replied.**

Chưa kết nối Microsoft Graph trong session đầu để tập trung chứng minh domain workflow.

### Domain model đầu tiên

```csharp
public enum FollowUpStatus
{
    Waiting,
    Overdue,
    Replied,
    Closed
}

public sealed class FollowUpItem
{
    public Guid Id { get; init; }
    public required string ConversationId { get; init; }
    public required string Subject { get; init; }
    public DateTimeOffset SentAt { get; init; }
    public DateTimeOffset DueAt { get; init; }
    public FollowUpStatus Status { get; private set; }

    public void MarkReplied()
    {
        if (Status is FollowUpStatus.Waiting or FollowUpStatus.Overdue)
            Status = FollowUpStatus.Replied;
    }
}
```

### First vertical slice

Implement ba endpoint in-memory:

```text
POST /api/followups
GET  /api/followups
POST /api/inbox-events
```

Ví dụ tạo follow-up:

```json
{
  "conversationId": "conv-001",
  "subject": "QA sign-off for release 2.4",
  "dueAt": "2026-08-22T09:00:00+07:00"
}
```

Sau đó simulate reply:

```json
{
  "conversationId": "conv-001",
  "receivedAt": "2026-08-20T10:30:00+07:00"
}
```

`ReplyMatcher` tìm item cùng conversation và gọi `MarkReplied()`.

### Expected result

Trước event:

```json
{
  "status": "Waiting"
}
```

Sau event:

```json
{
  "status": "Replied"
}
```

### Verification checklist

- [ ] Solution build thành công.
- [ ] Tạo được một follow-up qua HTTP.
- [ ] GET trả trạng thái `Waiting`.
- [ ] Inbox event cùng conversation chuyển trạng thái thành `Replied`.
- [ ] Event conversation khác không ảnh hưởng item.
- [ ] Gửi cùng event hai lần vẫn giữ `Replied`, không tạo duplicate transition.
- [ ] Có ít nhất 3 unit tests pass.

### Stop condition

Dừng session ngay khi có thể chạy một script/cURL tạo follow-up, giả lập reply và quan sát status đổi từ `Waiting` sang `Replied` với test pass.

**Không** thêm PostgreSQL, Microsoft login, Graph SDK, Vue, Docker, Telegram hay AI trong session đầu tiên.
