# Ý tưởng hôm nay: SupportHorizon — .NET Runtime End-of-Support Radar

## 1. Tóm tắt ý tưởng

SupportHorizon là một developer tool self-hosted giúp quét repository .NET để xác định **runtime/SDK nào đang được dùng, còn bao lâu tới ngày hết hỗ trợ, patch hiện tại có bị tụt lại không, và project nào cần được ưu tiên nâng cấp trước**. Thay vì chỉ phát hiện package vulnerability, công cụ tập trung vào một rủi ro khác: ứng dụng vẫn build và chạy bình thường nhưng nền tảng runtime đã hoặc sắp ra khỏi vòng đời hỗ trợ.

- Người dùng chính: backend developer hoặc solo developer duy trì nhiều repository .NET.
- Bài toán chính: khó theo dõi lifecycle của nhiều runtime/version xuyên suốt nhiều project.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

### Confirmed facts

Microsoft duy trì lifecycle rõ ràng cho .NET. Tại thời điểm nghiên cứu ngày 20/08/2026, các version đang được hỗ trợ gồm .NET 10 LTS, .NET 9 STS và .NET 8 LTS. .NET 8 và .NET 9 đều có ngày end-of-support là **10/11/2026**, trong khi .NET 10 LTS được hỗ trợ tới **14/11/2028**.

Nguồn chính thức:

- Microsoft Learn — .NET releases and support: https://learn.microsoft.com/en-us/dotnet/core/releases-and-support
- .NET release metadata repository: https://github.com/dotnet/core/blob/main/release-notes/releases-index.json
- .NET release notes: https://github.com/dotnet/core/blob/main/release-notes/README.md

Microsoft cũng công bố machine-readable release metadata trong `releases-index.json`. Metadata này bao gồm các trường như `channel-version`, `latest-release`, `latest-sdk`, `support-phase`, `eol-date` và `release-type`, vì vậy lifecycle có thể được kiểm tra bằng code thay vì hard-code thủ công.

GitHub Dependency Graph và SBOM có thể cung cấp dependency information của repository, nhưng chúng chủ yếu giải quyết software supply chain/dependency visibility. GitHub cho phép export dependency graph dưới dạng SPDX-compatible SBOM qua REST API.

Nguồn chính thức:

- GitHub Docs — Dependency graph: https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-graph
- GitHub Docs — SBOM REST API: https://docs.github.com/en/rest/dependency-graph/sboms

### Observation

Một repository .NET có thể khai báo version ở nhiều nơi:

- `<TargetFramework>net8.0</TargetFramework>` trong `.csproj`;
- `global.json` để pin SDK;
- `FROM mcr.microsoft.com/dotnet/aspnet:8.0` trong `Dockerfile`;
- CI image hoặc setup step trong GitHub Actions/Azure DevOps;
- documentation hoặc deployment manifest.

Do đó một project có thể nâng `TargetFramework` nhưng vẫn deploy bằng container runtime cũ, hoặc ngược lại.

### Assumption cần kiểm chứng

Developer duy trì từ 5 repository trở lên sẽ thấy giá trị nếu có một dashboard trả lời ngay:

- Repo nào đang dùng runtime sắp hết support?
- Còn bao nhiêu ngày?
- Project file và Docker image có đang lệch major version không?
- SDK patch hiện tại có tụt đáng kể so với latest servicing release không?
- Repo nào nên được nâng cấp trước?

### Cách xử lý hiện tại

Developer thường:

- nhớ lifecycle bằng kinh nghiệm;
- kiểm tra Microsoft Learn khi cần upgrade;
- search từng `csproj`;
- chạy script grep trong nhiều repository;
- chờ tới lúc CI/image/runtime báo warning;
- chỉ nâng version khi có ticket hoặc vulnerability cụ thể.

Các cách này hoạt động với một repository nhưng nhanh chóng trở nên thủ công khi số lượng project tăng.

## 3. Người dùng mục tiêu

### Primary user

Backend developer hoặc solo SaaS developer duy trì khoảng 5–30 repository .NET trên máy local hoặc GitHub.

### Context of use

- Có nhiều API/background worker chạy .NET 8/9/10.
- Một số repo ít được chạm tới trong nhiều tháng.
- Có Dockerfile và CI/CD riêng cho từng project.
- Muốn lên kế hoạch upgrade trước khi runtime hết support.

### Main pain point

Không có một inventory đáng tin cậy cho biết mỗi repo đang chạy runtime nào và lifecycle risk ra sao.

### Current workaround

Search repository thủ công, mở Microsoft lifecycle page, tạo spreadsheet hoặc dựa vào trí nhớ.

### Lý do họ sẽ thử SupportHorizon

Chỉ cần trỏ tool vào một folder chứa nhiều repository hoặc nhập danh sách GitHub repo, sau đó nhận một bảng ưu tiên upgrade có bằng chứng cụ thể từ source file.

## 4. Giải pháp đề xuất

### Main workflow

Người dùng cấu hình một workspace:

```text
D:/repos
```

SupportHorizon sẽ:

1. Tìm repository có `.csproj`, `global.json`, `Dockerfile`.
2. Parse target framework và SDK/runtime references.
3. Tải .NET release metadata chính thức.
4. Chuẩn hóa version về major channel như `8.0`, `9.0`, `10.0`.
5. Tính số ngày tới `eol-date`.
6. Phân loại risk.
7. Phát hiện mismatch giữa source, SDK và Docker runtime.
8. Lưu snapshot để theo dõi thay đổi qua thời gian.
9. Hiển thị dashboard hoặc xuất Markdown/JSON report.

### Input

- Local folder hoặc một repository cụ thể.
- Optional GitHub repository URL ở phase sau.
- Risk thresholds, ví dụ 180/90/30 ngày.

### Processing

Deterministic parser đọc XML, JSON, Dockerfile text và đối chiếu với official release metadata.

### Output

Ví dụ:

```text
Repository        TFM      Docker     EOL         Days Left   Risk
orders-api        net8.0   aspnet:8   2026-11-10  82          HIGH
invoice-worker    net10.0  aspnet:10  2028-11-14  817         OK
legacy-sync       net8.0   aspnet:9   2026-11-10  82          HIGH + MISMATCH
```

### Automated

- Repo discovery.
- Version extraction.
- Lifecycle lookup.
- Risk scoring.
- Snapshot/history.
- Optional scheduled rescan.

### User control

- Repo nào được scan.
- Risk thresholds.
- Repo nào được ignore/archive.
- Có cho phép network lookup hay chạy offline với cache.

### Key differentiator

SupportHorizon không cố thay Dependabot. Nó trả lời câu hỏi **“platform/runtime của project còn được support bao lâu và các lớp build/deploy có đồng nhất không?”**, thay vì chỉ tập trung package vulnerability.

### Ví dụ end-to-end

Developer có 12 repo trong `D:/repos`.

Tool phát hiện:

```text
customer-api/src/Customer.Api.csproj -> net8.0
customer-api/global.json              -> 8.0.4xx
customer-api/Dockerfile               -> aspnet:8.0
```

Sau khi tải release metadata, tool thấy channel 8.0 đang ở maintenance và có EOL 10/11/2026. Dashboard đánh dấu HIGH vì chỉ còn dưới 90 ngày theo threshold đã cấu hình.

Developer tạo ticket nâng `customer-api` lên .NET 10 và mark repository là `UpgradePlanned`. Lần scan sau vẫn giữ warning nhưng hiển thị trạng thái kế hoạch.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Một developer có thể dùng ngay cho chính repository cá nhân hoặc công việc để xây inventory runtime mà trước đây phải tự nhớ hoặc ghi chép.

### Technical learning value

Project giúp luyện:

- static source analysis;
- lifecycle/version normalization;
- reliable background refresh;
- GitHub API integration;
- caching external metadata;
- policy/risk engine;
- deterministic report generation.

### Phù hợp solo developer

Core domain khá nhỏ: scan → normalize → compare → score → report. Không cần ML, không cần big data và không cần distributed system.

### Vẫn hữu ích khi có rất ít user

Chỉ cần một user có nhiều repo là tool đã có giá trị thực tế. Không phụ thuộc network effect.

### Điều gì khiến project thất bại

- Developer chỉ có 1–2 repo và dễ nhớ lifecycle.
- Parser quá dễ false positive.
- Tool cố hỗ trợ quá nhiều ecosystem từ đầu.
- Report chỉ lặp lại thông tin có thể grep bằng một command.

### Lý do mạnh nhất để không build

Nếu chỉ cần kiểm tra một repository .NET duy nhất, một script PowerShell khoảng vài chục dòng có thể đủ. Project chỉ đáng làm khi mục tiêu là inventory nhiều repo, history, policy và CI integration.

## 6. Phạm vi MVP

### Must have

- Scan local workspace recursively.
- Parse `.csproj` TargetFramework/TargetFrameworks.
- Parse `global.json` SDK version nếu có.
- Parse official .NET Docker base images từ Dockerfile theo pattern phổ biến.
- Download và cache .NET `releases-index.json`.
- Match repo version với support phase/EOL.
- Tính days-to-EOL.
- Risk levels: `OK`, `WATCH`, `HIGH`, `EOL`.
- Detect TFM/Docker major mismatch.
- CLI report dạng table + JSON.
- Lưu latest scan snapshot.

### Should have

- Web dashboard.
- Repository tags/owner.
- Ignore rules.
- Markdown report.
- GitHub Actions mode trả non-zero exit code khi policy fail.
- Alert khi EOL threshold bị vượt.
- Scan `global.json` patch drift so với latest SDK metadata.

### Later

- GitHub organization discovery.
- GitHub SBOM import.
- Azure DevOps repositories.
- PostgreSQL/Node/Python/Java runtime lifecycle providers.
- Docker base image digest freshness.
- Auto-create upgrade issue.
- Pull request helper.
- Slack/Teams/Telegram notifications.

## 7. Luồng hoạt động

```text
User chọn workspace
→ validate folder
→ discover repositories
→ parse project metadata
→ normalize versions
→ load cached lifecycle metadata
→ refresh metadata nếu stale
→ calculate lifecycle status
→ apply risk policy
→ persist scan
→ render CLI/dashboard report
→ optional notification
```

### Alternative flows

**Không có internet:** dùng cached metadata và hiển thị `MetadataAge`.

**Repo multi-target:** lưu tất cả TFM và đánh giá version rủi ro nhất.

**Không có Dockerfile:** không coi là lỗi; chỉ report source runtime.

**Dockerfile dùng ARG:** parser đánh dấu `Unresolved` thay vì đoán.

**Unknown framework:** lưu evidence và không tự gán lifecycle.

### Failure cases

- Metadata endpoint timeout → dùng cache.
- Invalid XML → repo status `ParseFailed` nhưng scan các repo khác tiếp tục.
- Symlink loop → tránh recursive traversal vô hạn.
- Permission denied → ghi warning, không crash toàn scan.

## 9. Công nghệ đề xuất

### .NET 10

**Vì sao phù hợp:** đây là current LTS và chính project cũng nên chạy trên runtime có support horizon dài.

**Simpler alternative:** .NET 8 nếu môi trường hiện tại chưa có .NET 10.

**Khi outgrow:** không phải bottleneck kiến trúc; chỉ nâng runtime theo lifecycle.

### C# + `System.Xml.Linq`

Dùng parse `.csproj` mà không cần Roslyn ở MVP.

**Simpler alternative:** regex nhưng dễ sai với XML/multi-target.

**Outgrow:** khi cần hiểu evaluated MSBuild properties, chuyển sang Microsoft.Build APIs.

### Dockerfile parser đơn giản

MVP chỉ hỗ trợ các dòng `FROM` phổ biến.

**Simpler alternative:** regex có test fixtures.

**Outgrow:** khi cần ARG/stage variable resolution, dùng parser chuyên dụng hoặc own tokenizer.

### SQLite + EF Core

Phù hợp scan history local.

**Simpler alternative:** JSON file cho prototype đầu.

**Outgrow:** team mode/multi-user chuyển PostgreSQL.

### ASP.NET Core + Vue 3

Chỉ thêm sau khi CLI chứng minh utility.

### Docker

Hữu ích để self-host mà không cài SDK vào host, nhưng cần mount repo read-only.

### GitHub Actions

Dùng cho CI build/test/release tool. Sau này chính SupportHorizon có thể chạy như CI check.

## 10. Thiết kế dữ liệu ban đầu

### Repository

**Purpose:** đại diện source repository được theo dõi.

Fields:

```text
Id
Name
LocalPath
RemoteUrl?
IsIgnored
LastScannedAt
```

Relationship: một Repository có nhiều Scan.

Retention: giữ lâu dài; path có thể được cập nhật.

### Scan

**Purpose:** snapshot một lần quét.

Fields:

```text
Id
RepositoryId
StartedAt
CompletedAt
Status
RiskLevel
DaysToEol?
MetadataVersion
```

Retention: có thể giữ 90–365 ngày; aggregate older scans sau này.

### RuntimeEvidence

**Purpose:** bằng chứng version tìm được trong source.

Fields:

```text
Id
ScanId
SourceType        // Csproj, GlobalJson, Dockerfile
FilePath
RawValue
NormalizedChannel
LineNumber?
```

Relationship: một Scan có nhiều evidence.

Retention: theo Scan.

### LifecycleEntry

**Purpose:** normalized official runtime lifecycle.

Fields:

```text
ChannelVersion
LatestRelease
LatestSdk
SupportPhase
ReleaseType
EolDate
SourceUrl
FetchedAt
```

Retention: overwrite latest cache; optional history nếu muốn audit metadata changes.

### Finding

**Purpose:** actionable issue.

Fields:

```text
Id
ScanId
Code
Severity
Message
EvidenceJson
```

Ví dụ code:

```text
RUNTIME_EOL_SOON
RUNTIME_EOL
TFM_DOCKER_MISMATCH
SDK_PATCH_BEHIND
UNKNOWN_RUNTIME
```

## 11. API và tích hợp

### .NET Release Metadata

**Purpose:** source of truth cho .NET lifecycle và latest patch.

**Authentication:** không cần.

**Cost/rate limit:** dữ liệu nhỏ; fetch vài lần mỗi ngày là đủ.

**Privacy:** không gửi source code lên external service.

**Fallback:** cached metadata local.

Nguồn:

- https://github.com/dotnet/core/blob/main/release-notes/releases-index.json
- Microsoft Learn lifecycle page.

### GitHub REST API — optional phase

**Purpose:** discover repositories, lấy files hoặc SBOM trong team/cloud mode.

**Authentication:** fine-grained token/GitHub App tùy private repo.

**Cost/rate limit:** cần tôn trọng GitHub API rate limits.

**Privacy:** repository metadata/source có thể là private.

**Fallback:** local filesystem scan.

GitHub có endpoint export dependency graph dưới SPDX SBOM; endpoint này yêu cầu repository read access với private resource, còn public resource có thể dùng không authentication theo tài liệu hiện tại.

Nguồn:

- https://docs.github.com/en/rest/dependency-graph/sboms

### Git

**Purpose:** xác định repo root/remote URL/last commit.

**Authentication:** không cần cho local repository.

**Fallback:** filesystem-only mode.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem hoàn toàn deterministic:

```text
version evidence
+ official lifecycle metadata
+ risk thresholds
= finding
```

AI không nên quyết định một runtime có EOL hay không vì đây là factual policy data có cấu trúc.

AI có thể là optional future feature để giải thích upgrade impact từ release notes, nhưng không nên nằm trong MVP.

Nếu thêm sau này:

- Task: summarize breaking-change/release-note context.
- Context: selected repo version + official migration docs.
- Output: structured JSON gồm `summary`, `possibleRisks`, `checklist`.
- Validation: mọi factual lifecycle date vẫn lấy deterministic source.
- Fallback: hiển thị official links.
- Risks: hallucination, cost, latency, private-code leakage.

## 14. Các bài toán kỹ thuật đáng học

### 1. Static configuration/source analysis

Phải tìm version đúng trong XML, JSON và Dockerfile thay vì grep mù.

**Skill cải thiện:** parser design, evidence extraction, conservative analysis.

### 2. Version normalization

`net8.0`, SDK `8.0.4xx`, runtime image `8.0` đều cần map về lifecycle channel `8.0` nhưng vẫn giữ raw value.

**Skill cải thiện:** semantic version reasoning và canonical models.

### 3. Reliable external metadata caching

Tool phải hoạt động ngay cả khi GitHub/Microsoft metadata temporarily unavailable.

**Skill cải thiện:** cache freshness, retry, stale-but-valid fallback.

### 4. Policy engine

Ví dụ:

```text
EOL             => CRITICAL
<= 30 days      => CRITICAL
<= 90 days      => HIGH
<= 180 days     => WATCH
otherwise       => OK
```

**Skill cải thiện:** rule modeling, explainability và deterministic decisions.

### 5. CI integration

Project có thể fail build khi runtime đã EOL hoặc còn dưới threshold policy.

**Skill cải thiện:** CLI exit codes, machine-readable output và developer-experience design.

## 15. Rủi ro và cách xử lý

### False positive

**Risk:** parser hiểu sai version được tính động.

**Mitigation:** lưu raw evidence, đánh `Unresolved` khi không chắc chắn, không tự đoán.

### Scope expansion

**Risk:** cố hỗ trợ mọi runtime/package manager.

**Mitigation:** MVP chỉ `.NET + local repos + common Dockerfile patterns`.

### Lifecycle metadata thay đổi

**Risk:** hard-coded data nhanh lỗi thời.

**Mitigation:** dùng official machine-readable metadata và lưu source URL/fetched time.

### API dependency

**Risk:** metadata fetch bị lỗi.

**Mitigation:** local cache + stale warning.

### Privacy

**Risk:** source repo có code nhạy cảm.

**Mitigation:** local-first; chỉ gửi request lấy lifecycle metadata, không upload source.

### Security

**Risk:** scanning untrusted repo có file path tricks/symlink loops.

**Mitigation:** không execute repo code, không chạy MSBuild trong MVP, canonicalize path, limit recursion.

### User adoption

**Risk:** report không có hành động cụ thể.

**Mitigation:** mỗi finding phải có evidence, EOL date, days left và recommended next channel.

### Maintenance burden

**Risk:** parser ecosystem quá rộng.

**Mitigation:** provider interface nhưng chỉ ship provider thực sự maintainable.

## 17. Cách đo dự án có hữu ích hay không

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, tạo vertical slice đầu tiên:

```text
scan một folder
→ tìm .csproj
→ đọc TargetFramework
→ tải releases-index.json
→ in lifecycle/EOL ra console
```

Không làm database, dashboard hay GitHub integration.

### Files/components cần tạo

```text
SupportHorizon.sln
src/
  SupportHorizon.Cli/
    Program.cs
    Scanning/ProjectScanner.cs
    Lifecycle/DotNetLifecycleClient.cs
    Lifecycle/DotNetReleaseEntry.cs
    Models/ProjectRuntime.cs
tests/
  SupportHorizon.Tests/
    ProjectScannerTests.cs
    Fixtures/
      Net8App/Sample.csproj
      Net10App/Sample.csproj
```

### Setup commands

```bash
dotnet new sln -n SupportHorizon
dotnet new console -n SupportHorizon.Cli -o src/SupportHorizon.Cli
dotnet new xunit -n SupportHorizon.Tests -o tests/SupportHorizon.Tests
dotnet sln add src/SupportHorizon.Cli
dotnet sln add tests/SupportHorizon.Tests
dotnet add tests/SupportHorizon.Tests reference src/SupportHorizon.Cli
```

### First vertical slice

`ProjectScanner`:

1. `Directory.EnumerateFiles(root, "*.csproj", SearchOption.AllDirectories)`.
2. Parse XML bằng `XDocument`.
3. Đọc `TargetFramework` hoặc `TargetFrameworks`.
4. Chuẩn hóa `net8.0` → `8.0`, `net10.0` → `10.0`.

`DotNetLifecycleClient`:

1. Download official `releases-index.json`.
2. Deserialize `releases-index`.
3. Match `channel-version`.
4. Return `support-phase`, `eol-date`, `latest-release`, `latest-sdk`.

CLI output:

```text
Repo          Framework   Support       EOL          Days Left
Sample.Net8   net8.0      maintenance   2026-11-10   82
Sample.Net10  net10.0     active        2028-11-14   817
```

Số `Days Left` phải được tính runtime, không hard-code.

### Expected result

Một command thực tế:

```bash
dotnet run --project src/SupportHorizon.Cli -- D:/repos
```

in được ít nhất:

- project path;
- detected target framework;
- support phase;
- EOL date;
- days remaining.

### Verification checklist

- [ ] `net8.0` được normalize thành channel `8.0`.
- [ ] `net10.0` được normalize thành channel `10.0`.
- [ ] EOL lấy từ downloaded metadata, không hard-code.
- [ ] Project không có `TargetFramework` không crash scanner.
- [ ] Một invalid `.csproj` không làm stop toàn batch.
- [ ] Có ít nhất 2 unit tests pass.
- [ ] Chạy trên một repository thật và output nhìn đúng.

### Stop condition

Dừng session ngay khi command có thể scan một folder thật và tạo table lifecycle chính xác cho ít nhất hai target framework khác nhau.

Không thêm Vue, SQLite, Docker parser, scheduler hoặc GitHub API trong buổi đầu tiên.
