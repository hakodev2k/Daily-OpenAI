# Ý tưởng hôm nay: Config Drift Radar

## 1. Tóm tắt ý tưởng

**Config Drift Radar** là một công cụ self-hosted giúp developer so sánh cấu hình giữa local, development, staging và production để phát hiện **missing key, extra key, type mismatch, stale secret metadata và configuration drift** trước khi deploy. Công cụ tập trung vào việc so sánh **cấu trúc và metadata**, không cần đọc hoặc lưu giá trị secret thật, nên phù hợp cho developer/team nhỏ muốn giảm lỗi kiểu “chạy ở máy tôi nhưng fail ở staging/prod”.

- Người dùng chính: backend developer .NET, solo builder, technical lead của team nhỏ.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Ứng dụng hiện đại thường lấy cấu hình từ nhiều nguồn: `appsettings.json`, `appsettings.{Environment}.json`, environment variables, user secrets, Azure App Configuration, Azure Key Vault hoặc biến của CI/CD. Cấu hình cuối cùng được tạo từ nhiều lớp override, nên rất dễ xuất hiện drift giữa môi trường.

**Confirmed facts:**

- ASP.NET Core mặc định có nhiều configuration providers; environment variables được đọc sau `appsettings.json`, `appsettings.{ENVIRONMENT}.json` và user secrets nên có thể override các giá trị trước đó. Microsoft cũng lưu ý hierarchical key syntax khác nhau giữa platform, ví dụ Bash không hỗ trợ dấu `:` trực tiếp trong tên environment variable. Nguồn: Microsoft Learn — Configuration in ASP.NET Core: https://learn.microsoft.com/en-us/aspnet/core/fundamentals/configuration/?view=aspnetcore-10.0
- Azure App Configuration có .NET configuration provider chính thức, hỗ trợ chọn key, refresh động và tích hợp với `IConfiguration`. Nguồn: Microsoft Learn — Azure App Configuration .NET provider: https://learn.microsoft.com/en-us/azure/azure-app-configuration/reference-dotnet-provider
- Azure Key Vault SDK cho .NET có thể liệt kê `SecretProperties` mà **không trả về secret value**; metadata bao gồm tên, version, created/updated time, enabled state và expiration. Điều này cho phép kiểm tra sự tồn tại hoặc metadata của secret mà không cần đọc nội dung secret. Nguồn: Microsoft Learn — `SecretClient.GetPropertiesOfSecrets`: https://learn.microsoft.com/en-us/dotnet/api/azure.security.keyvault.secrets.secretclient.getpropertiesofsecrets?view=azure-dotnet

**Observation:** tooling hiện có thường giải quyết từng nguồn riêng lẻ — IDE/user secrets, Azure Portal, deployment variables, Key Vault, App Configuration — trong khi câu hỏi developer thực sự cần trước deploy thường đơn giản hơn: “staging có đủ các key mà app cần không, production có key thừa/cũ nào không, và schema giữa các môi trường có lệch nhau không?”.

**Assumption cần kiểm chứng:** developer/team nhỏ sẵn sàng dùng một CLI/check trong CI nếu tool không yêu cầu gửi secret lên SaaS và có thể chạy read-only.

Workaround phổ biến hiện nay:

- Mở từng `appsettings.*.json` để so sánh bằng mắt.
- Check Azure Portal thủ công.
- Copy danh sách environment variables.
- Đợi deployment fail vì missing configuration.
- Viết script PowerShell/Bash tạm thời.

Các cách này rời rạc, khó tái sử dụng và dễ bỏ sót khi số key tăng lên.

## 3. Người dùng mục tiêu

**Primary user:** backend developer .NET đang duy trì một hoặc vài ứng dụng có từ 2–4 môi trường deploy.

- Context: trước release, migration hoặc thay đổi integration.
- Main pain point: không biết môi trường đích có đủ cấu hình mà phiên bản mới yêu cầu hay không.
- Current workaround: manual compare file/portal/env vars hoặc phát hiện sau khi deploy.
- Lý do thử sản phẩm: chạy một lệnh và nhận report cụ thể, không lộ secret value.

MVP chỉ cần phục vụ một developer hoặc một repository. Không cần multi-tenant enterprise governance.

## 4. Giải pháp đề xuất

Người dùng định nghĩa các **configuration sources** và một **baseline schema**.

Ví dụ:

```yaml
project: orders-api
baseline: local
sources:
  local:
    type: appsettings
    path: ./src/Orders.Api/appsettings.json
  staging:
    type: azure-app-configuration
    endpoint: https://orders-stg.azconfig.io
  production-secrets:
    type: azure-key-vault-metadata
    vaultUri: https://orders-prod-kv.vault.azure.net
```

Tool thực hiện:

1. Đọc key từ từng source.
2. Normalize key về canonical form, ví dụ `Database:ConnectionString`.
3. Không lưu secret value; với Key Vault chỉ lấy metadata/name.
4. Infer hoặc đọc expected type/schema nếu có.
5. Compare các environment.
6. Phân loại drift:
   - Missing.
   - Extra.
   - Type mismatch.
   - Disabled secret.
   - Secret sắp hết hạn.
   - Key tồn tại nhưng không được reference bởi schema/code scan tùy chọn.
7. Xuất Markdown/JSON và exit code cho CI.

### Ví dụ end-to-end

Developer thêm cấu hình mới:

```json
"Email": {
  "RetryCount": 5,
  "SenderAddress": "..."
}
```

Local có đủ hai key, staging chỉ có `Email:SenderAddress`.

Trước deploy, developer chạy:

```bash
configdrift scan --project configdrift.yml
```

Kết quả:

```text
[ERROR] staging: missing Email:RetryCount
[WARN ] production-keyvault: SMTP-Password expires in 12 days
[INFO ] staging: extra LegacyApi:BaseUrl

Exit code: 2
```

CI fail trước khi application được deploy.

**Key differentiator:** kiểm tra **presence/schema/metadata across environments** theo hướng privacy-first, thay vì trở thành secret manager mới.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Tool có thể dùng ngay cho chính các project .NET có `appsettings`, Azure App Configuration hoặc Key Vault. Chỉ một người dùng cũng đủ tạo giá trị nếu mỗi release giảm được vài lần kiểm tra portal thủ công hoặc tránh một deployment fail.

### Technical learning value

Dự án giúp học sâu:

- .NET configuration pipeline.
- Environment normalization.
- Azure SDK authentication.
- Secret metadata handling.
- CLI design.
- CI/CD quality gates.
- Schema inference và validation.

### Phù hợp solo developer

Core engine nhỏ: load source → normalize → compare → report. Các integration có thể thêm dần bằng adapter mà không cần microservices.

### Điều gì làm ý tưởng thất bại

- Config của user quá đơn giản nên script Bash/PowerShell đã đủ.
- Azure permissions khiến setup phức tạp.
- Tool tạo quá nhiều warning gây alert fatigue.
- Việc infer type từ string environment variables không đáng tin nếu không có schema.

### Lý do mạnh nhất để không build

Nếu phần lớn project chỉ có một `appsettings.json` cộng vài env vars và ít thay đổi, lợi ích có thể không đủ lớn để duy trì thêm một tool CI.

## 6. Phạm vi MVP

### Must have

- CLI chạy local.
- Đọc `appsettings.json` / `appsettings.{Environment}.json`.
- Đọc `.env` hoặc danh sách environment variables từ file export.
- Normalize hierarchical keys.
- Compare hai hoặc nhiều source theo key presence.
- Detect missing/extra keys.
- Optional schema file mô tả expected type + required/optional.
- Markdown + JSON output.
- Exit code theo severity.
- Redact values trong toàn bộ output/log.

### Should have

- Azure App Configuration adapter.
- Azure Key Vault metadata-only adapter.
- Secret expiration warning.
- Ignore rules/globs.
- Baseline snapshots trong Git.
- GitHub Actions example.

### Later

- Code scan tìm `IOptions<T>` / strongly typed options.
- Auto-generate config schema từ C# options classes.
- GitHub PR comment.
- Azure DevOps extension.
- Config history timeline.
- Web dashboard.
- Team policy packs.

MVP không cần UI web, database hoặc SaaS.

## 7. Luồng hoạt động

### Normal flow

User chạy CLI
→ load project config
→ validate source definitions
→ authenticate source nếu cần
→ fetch key names/metadata
→ normalize keys
→ apply ignore rules
→ compare với schema/baseline
→ classify findings
→ render report
→ trả exit code.

### Alternative flows

**Local-only:** chỉ compare `appsettings.json`, staging export và production export, không cần Azure credential.

**Azure read-only:** dùng `DefaultAzureCredential`, chỉ đọc App Configuration và Key Vault metadata.

**Schema-first:** schema quy định key bắt buộc; không cần chọn một environment làm baseline.

### Failure cases

- Azure credential không có quyền → report `SourceUnavailable`, không giả vờ môi trường “empty”.
- File JSON invalid → fail scan rõ ràng.
- Duplicate key sau normalization → cảnh báo conflict.
- Key Vault throttling/network error → retry giới hạn, sau đó trả trạng thái unknown.
- Environment variable value không parse được type → chỉ đánh dấu unknown nếu schema yêu cầu type.

## 8. Kiến trúc đề xuất

### Client

**CLI-first**. Không cần frontend ở MVP vì use case phù hợp terminal và CI.

### Core engine

Một .NET solution gồm:

- `ConfigDrift.Core` — models, normalization, comparison.
- `ConfigDrift.Sources` — adapters.
- `ConfigDrift.Cli` — commands/reporting.

Đây là modular monolith ở mức codebase, không phải distributed system.

### Database

Không cần database ở MVP. Snapshot có thể xuất JSON vào artifact hoặc Git nếu user muốn.

### Background worker

Không cần. Scan chạy theo command invocation.

### Queue/cache

Không cần.

### Authentication

Azure adapters dùng `DefaultAzureCredential`. Local source không cần auth.

### External APIs

- Azure App Configuration.
- Azure Key Vault metadata.

### AI

Không cần.

### Logging

`Microsoft.Extensions.Logging` với default redaction policy: không log config value.

### Deployment

Publish thành .NET tool hoặc self-contained executable. Có thể phát hành container nhỏ cho CI runner nếu cần.

## 9. Công nghệ đề xuất

### .NET 10

Rất phù hợp vì sản phẩm là CLI/developer tool và cần tương tác sâu với .NET configuration APIs.

**Simpler alternative:** PowerShell script cho prototype đầu tiên.

**Outgrow point:** không có lý do kỹ thuật để đổi stack ngay cả khi tool lớn hơn.

### `System.CommandLine`

Dùng xây command hierarchy như:

```text
configdrift scan
configdrift snapshot
configdrift validate
```

**Simpler alternative:** parse `args[]` trực tiếp cho prototype.

### `Microsoft.Extensions.Configuration`

Tận dụng đúng semantics configuration của .NET thay vì tự invent parser.

### Azure App Configuration SDK/provider

Provider chính thức có thể đọc key-value vào .NET configuration pipeline. Microsoft hỗ trợ integration trực tiếp qua `AddAzureAppConfiguration`. Nguồn: https://learn.microsoft.com/en-us/azure/azure-app-configuration/reference-dotnet-provider

### `Azure.Security.KeyVault.Secrets`

Dùng `SecretClient.GetPropertiesOfSecrets()` để lấy **properties mà không lấy secret value**. Đây là điểm quan trọng cho privacy-first design. Nguồn: https://learn.microsoft.com/en-us/dotnet/api/azure.security.keyvault.secrets.secretclient.getpropertiesofsecrets?view=azure-dotnet

### `Azure.Identity`

`DefaultAzureCredential` giúp chạy local bằng developer identity và chạy CI/cloud bằng workload/managed identity phù hợp.

### Tests

- xUnit.
- Testcontainers cho integration tests nếu sau này cần Azurite-like substitute hoặc fake HTTP service.

### CI

GitHub Actions hoặc Azure DevOps đều phù hợp. MVP chỉ cần sample workflow YAML.

## 10. Thiết kế dữ liệu ban đầu

Không cần relational database. Core model có thể nhỏ.

### `ConfigSourceDefinition`

**Purpose:** mô tả nguồn cấu hình.

Fields:

- `Name`
- `Type`
- `Location`
- `LabelOrEnvironment`
- `Options`

Relationship: thuộc một project config file.

Retention: source definition nằm trong YAML; không chứa secret value.

### `ConfigEntryMetadata`

**Purpose:** normalized representation của một key.

Fields:

- `CanonicalKey`
- `SourceName`
- `DeclaredType`
- `IsSecret`
- `IsEnabled`
- `ExpiresOn`
- `Version`
- `ValueFingerprint` — chỉ optional, không dùng ở MVP nếu nguồn là secret.

Retention: in-memory trong scan; chỉ persistence khi user export snapshot.

### `ConfigRule`

**Purpose:** expected contract.

Fields:

- `Key`
- `Required`
- `ExpectedType`
- `Sensitive`
- `SeverityIfMissing`

### `DriftFinding`

**Purpose:** report item.

Fields:

- `Code`
- `Source`
- `Key`
- `Severity`
- `Message`
- `Metadata`

Không lưu raw secret value trong bất kỳ model persistent nào.

## 11. API và tích hợp

### ASP.NET Core configuration files

- Purpose: baseline/local source.
- Authentication: none.
- Cost/rate limit: none.
- Privacy: file có thể chứa secret nếu project đang làm sai practice; loader phải ignore value output.
- Fallback: user export key list thủ công.

### Environment variable export

- Purpose: compare runtime-style config.
- Authentication: none nếu file local.
- Privacy: tuyệt đối không render value mặc định.
- Fallback: chỉ import key names.

### Azure App Configuration

- Purpose: đọc centralized config keys.
- Authentication: Azure identity/RBAC.
- Cost/rate limit: có service request limits và Azure pricing tùy tier; scanner phải tránh poll liên tục.
- Privacy: App Configuration có thể chứa non-secret values và Key Vault references; report chỉ cần key metadata.
- Fallback: user export snapshot JSON rồi scan offline.
- Official docs: https://learn.microsoft.com/en-us/azure/azure-app-configuration/reference-dotnet-provider

### Azure Key Vault

- Purpose: verify secret presence, enabled/expiry/version metadata.
- Authentication: Azure identity và permission list secrets.
- Cost/rate limit: API có throttling; không scan theo giây.
- Privacy: dùng listing properties thay vì `GetSecret` khi chỉ cần metadata.
- Fallback: import metadata export.
- Official docs: https://learn.microsoft.com/en-us/dotnet/api/azure.security.keyvault.secrets.secretclient.getpropertiesofsecrets?view=azure-dotnet

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Config comparison là bài toán deterministic. Rule engine sẽ chính xác, dễ test và không phát sinh chi phí/token/hallucination.

Nếu sau này muốn thêm AI, use case hợp lý nhất chỉ là optional:

- Giải thích một report dài bằng ngôn ngữ tự nhiên.
- Gợi ý tên key mapping khi migration từ legacy naming.
- Sinh migration checklist.

Nhưng AI không được quyết định key nào missing, secret nào expired hoặc pipeline có pass hay không.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** chứng minh drift thực sự xuất hiện trong project cá nhân.

**Main tasks:**

- Chọn 1 API .NET có ít nhất local + staging config.
- Export key names từ hai môi trường.
- Compare thủ công và ghi lại mismatches.
- Hỏi thêm 2–3 developer xem họ đang kiểm config trước deploy bằng cách nào.

**Expected output:** danh sách 5–10 drift case thật.

**Completion criteria:** tìm thấy ít nhất 2 loại lỗi mà tool có thể phát hiện tự động và người dùng thấy đáng kiểm tra trước deploy.

### Phase 1 — Core MVP

**Goal:** CLI local compare được file-based sources.

**Main tasks:**

- `appsettings.json` loader.
- `.env` key loader.
- key normalization.
- compare engine.
- Markdown/JSON report.
- exit code.

**Expected output:** `configdrift scan` chạy được trên một repo thật.

**Completion criteria:** detect chính xác missing/extra key giữa ít nhất 3 sources.

### Phase 2 — Reliability

**Goal:** output đủ tin cậy để chạy CI.

**Main tasks:**

- Schema validation.
- Ignore rules.
- invalid/unknown source state.
- sensitive-value redaction tests.
- unit/integration tests.
- stable finding codes.

**Expected output:** tool không leak value và failure source không bị hiểu nhầm là empty config.

**Completion criteria:** test suite bao phủ core rules và CLI trả deterministic exit code.

### Phase 3 — Useful expansion

**Goal:** thêm cloud integrations có giá trị cao nhất.

**Main tasks:**

- Azure App Configuration source.
- Azure Key Vault metadata source.
- expiration policy.
- baseline snapshot.

**Expected output:** một command scan local + staging Azure + production metadata.

**Completion criteria:** chạy được bằng read-only identity và không gọi `GetSecret` trong metadata-only mode.

### Phase 4 — Production readiness

**Goal:** dễ cài và vận hành lâu dài.

**Main tasks:**

- package thành .NET global tool.
- GitHub Actions sample.
- Azure DevOps sample.
- changelog/versioning.
- telemetry opt-out hoặc không telemetry mặc định.
- docs về RBAC tối thiểu.

**Expected output:** developer mới có thể setup trong khoảng 15 phút.

**Completion criteria:** clean install → configure → scan → CI fail/pass chạy end-to-end theo documentation.

## 14. Các bài toán kỹ thuật đáng học

### 1. Configuration precedence và normalization

Cần hiểu thật sự cách .NET merge nhiều provider, cách `:` và `__` được biểu diễn, cũng như case sensitivity theo platform.

**Skill cải thiện:** configuration architecture và cross-platform behavior.

### 2. Schema inference và strongly typed options

Nếu mở rộng scan C# `IOptions<T>`, tool phải map property tree sang config keys và nullable/required semantics.

**Skill cải thiện:** reflection, Roslyn, source analysis, configuration binding.

### 3. Read-only cloud authentication

Dùng Azure identity sao cho đủ quyền list metadata nhưng không cấp quyền rộng hơn cần thiết.

**Skill cải thiện:** RBAC, least privilege, managed identity/workload identity.

### 4. Privacy-preserving diagnostics

Report phải hữu ích mà không log value.

**Skill cải thiện:** secure logging, redaction, secret lifecycle thinking.

### 5. Deterministic CI quality gate

Warning/error rules phải ổn định, versioned và không tạo false failure liên tục.

**Skill cải thiện:** developer tooling, exit-code contracts, CI ergonomics.

## 15. Rủi ro và cách xử lý

### False positive do optional configuration

**Risk:** key chỉ cần trong một số environment.

**Mitigation:** schema hỗ trợ environment scope và `required: false`.

### Type inference yếu với environment variables

**Risk:** mọi env var đều là string ở transport layer.

**Mitigation:** không infer type nếu không có schema; schema hoặc strongly typed options mới là source of truth.

### Secret exposure

**Risk:** tool vô tình log raw config values.

**Mitigation:** architecture metadata-first; adapters trả `ConfigEntryMetadata`, không trả value trừ provider thực sự cần; snapshot mặc định không chứa value; redaction tests bắt buộc.

### Azure permission complexity

**Risk:** setup RBAC làm user bỏ cuộc.

**Mitigation:** MVP hoạt động offline/file-first; cloud adapters optional; cung cấp `configdrift doctor` kiểm quyền.

### API throttling/network dependency

**Risk:** pipeline fail chỉ vì Azure tạm thời unavailable.

**Mitigation:** phân biệt `drift detected` với `source unavailable`; policy cho phép fail-open/fail-closed tùy project; retry ngắn.

### Scope creep

**Risk:** biến thành secret manager/config deployment platform.

**Mitigation:** sản phẩm chỉ **observe + compare + report** trong MVP; không edit production config.

### Adoption

**Risk:** developer không muốn thêm config file nữa.

**Mitigation:** auto-discover `appsettings*.json`, support zero-config compare command và generate starter schema.

## 16. Kiểm thử

### Strategy

- Unit tests cho normalization/comparison/rules.
- Integration tests cho file providers và Azure adapter abstraction.
- CLI end-to-end tests dùng fixture repositories.
- Failure-path tests cho invalid JSON, inaccessible source, timeout.
- Security tests xác nhận report/log không chứa values được đánh dấu sensitive.
- Data-quality tests kiểm canonical key mapping.

### 5 test scenario quan trọng nhất

1. `appsettings.json` có `Email:RetryCount`, staging thiếu key → finding `CFG001 MissingRequiredKey`.
2. Env var `Email__RetryCount` normalize thành `Email:RetryCount` và không bị báo missing sai.
3. Key Vault trả secret `ApiKey` enabled nhưng sắp hết hạn → warning đúng threshold, không gọi API lấy secret value.
4. Azure source unauthorized → `SourceUnavailable`, không sinh hàng trăm false missing findings.
5. Report/log được scan và không chứa giá trị sample secret `super-secret-123`.

## 17. Cách đo dự án có hữu ích hay không

### Product usage metric

- Số lần scan thực sự chạy trước deploy/release.

### Time saved

- Thời gian check config thủ công trước release so với `configdrift scan`.

### Task completion rate

- % scan hoàn tất và cho report actionable, không rơi vào unknown state.

### Error rate

- False positive rate trên các finding severity Error.

### Repeated use

- Số tuần liên tiếp project vẫn giữ check trong CI.

### Technical reliability

- % scan cloud source thành công.
- Median scan duration.
- Số lần report làm lộ value nhạy cảm phải bằng **0**.

### Validation target ban đầu

Trong 30 ngày, tool nên phát hiện ít nhất một real drift trước deployment hoặc giảm đáng kể thao tác manual compare. Nếu không đạt, không nên mở rộng sang dashboard/SaaS.

### Open-source

Core engine và adapters phù hợp open-source. Hosted dashboard hoặc enterprise policy packs có thể là commercial layer nếu có demand.

## 19. Mô hình giá trị hoặc kiếm tiền

Phù hợp với:

- **Personal utility**
- **Open-source project**
- **Portfolio project**
- **Developer tool**
- **Consulting accelerator**

Monetization ở MVP chưa cần thiết. Giá trị mạnh nhất là công cụ dùng thật cho workflow release và portfolio thể hiện tư duy reliability/security.

Nếu sau này có usage thật từ team nhỏ, commercial options hợp lý hơn là:

- Hosted scan history/dashboard.
- Team policies.
- GitHub/Azure DevOps integration nâng cao.
- One-time paid desktop/enterprise package.

Không nên xây SaaS trước khi CLI có người dùng lặp lại.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, tạo vertical slice đầu tiên:

**Compare hai file cấu hình → normalize keys → in missing/extra keys → trả exit code khác 0 khi có drift.**

### Files/components cần tạo

```text
ConfigDriftRadar.sln
src/
  ConfigDrift.Cli/
    Program.cs
  ConfigDrift.Core/
    ConfigFlattener.cs
    ConfigComparer.cs
    Models/DriftFinding.cs
tests/
  ConfigDrift.Core.Tests/
    ConfigComparerTests.cs
samples/
  appsettings.local.json
  appsettings.staging.json
```

### Setup commands

```bash
dotnet new sln -n ConfigDriftRadar

dotnet new console -n ConfigDrift.Cli -o src/ConfigDrift.Cli
dotnet new classlib -n ConfigDrift.Core -o src/ConfigDrift.Core
dotnet new xunit -n ConfigDrift.Core.Tests -o tests/ConfigDrift.Core.Tests

dotnet sln add src/ConfigDrift.Cli
dotnet sln add src/ConfigDrift.Core
dotnet sln add tests/ConfigDrift.Core.Tests

dotnet add src/ConfigDrift.Cli reference src/ConfigDrift.Core
dotnet add tests/ConfigDrift.Core.Tests reference src/ConfigDrift.Core
```

### First vertical slice

Tạo sample baseline:

```json
{
  "Database": {
    "ConnectionString": "LOCAL_ONLY",
    "CommandTimeout": 30
  },
  "Email": {
    "SenderAddress": "dev@example.com",
    "RetryCount": 3
  }
}
```

Staging:

```json
{
  "Database": {
    "ConnectionString": "REDACTED",
    "CommandTimeout": 30
  },
  "Email": {
    "SenderAddress": "staging@example.com"
  },
  "LegacyApi": {
    "BaseUrl": "https://legacy.example.com"
  }
}
```

Implement command:

```bash
dotnet run --project src/ConfigDrift.Cli -- \
  samples/appsettings.local.json \
  samples/appsettings.staging.json
```

Expected output:

```text
Config Drift Report

MISSING  Email:RetryCount
EXTRA    LegacyApi:BaseUrl

Summary: 1 missing, 1 extra
Exit code: 2
```

### Implementation detail quan trọng

`ConfigFlattener` phải chuyển nested JSON thành canonical keys:

```text
Database:ConnectionString
Database:CommandTimeout
Email:SenderAddress
Email:RetryCount
```

Ở session đầu tiên chỉ compare **keys**, tuyệt đối không print values.

### Verification checklist

- [ ] Nested JSON được flatten đúng.
- [ ] Key tồn tại cả hai source không bị report.
- [ ] `Email:RetryCount` được báo missing ở staging.
- [ ] `LegacyApi:BaseUrl` được báo extra.
- [ ] Console output không chứa `LOCAL_ONLY`, `REDACTED` hoặc email value.
- [ ] Ít nhất 3 unit tests pass.
- [ ] Process exit code khác `0` khi có missing required key.

### Stop condition

Dừng session ngay khi command trên tạo report đúng và test pass. Không thêm Azure, Key Vault, UI, database, authentication hoặc AI trong phiên đầu tiên.
