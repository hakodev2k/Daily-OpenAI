# Ý tưởng hôm nay: ShareScope — Trình giám sát quyền chia sẻ OneDrive/SharePoint cá nhân

## 1. Tóm tắt ý tưởng

**ShareScope** là một ứng dụng self-hosted nhỏ giúp một cá nhân hoặc một nhóm kỹ thuật nhỏ theo dõi các file/folder trên OneDrive hoặc SharePoint đang được chia sẻ cho ai, bằng loại quyền nào, và quyền đó thay đổi theo thời gian ra sao. Nó giải quyết tình trạng “đã từng share file cho ai đó nhưng vài tuần sau không còn nhớ”, đặc biệt với tài liệu nội bộ, file kỹ thuật, tài chính, hồ sơ nhân sự hoặc tài liệu dự án.

- **Project size:** Medium
- **MVP ước tính:** 2–3 tuần làm ngoài giờ
- **Giá trị cốt lõi:** tạo một lịch sử quyền chia sẻ dễ hiểu, phát hiện link public/anonymous hoặc quyền mới xuất hiện, và nhắc người dùng review các chia sẻ cũ.

## 2. Bài toán thực tế

### Confirmed facts

Microsoft Graph biểu diễn file/folder trên OneDrive và SharePoint dưới dạng `driveItem`, có API để đọc permission của item. Microsoft Graph cũng hỗ trợ delta query cho `driveItem` để ứng dụng chỉ lấy các thay đổi kể từ lần đồng bộ trước, thay vì phải đọc lại toàn bộ cây file mỗi lần. Microsoft nêu rõ delta query dùng state token và trả về `@odata.deltaLink` để ứng dụng tiếp tục theo dõi các thay đổi sau đó.

Ngoài ra, change notifications có thể báo khi nội dung trong hierarchy thay đổi; với OneDrive for Business và SharePoint, Graph còn hỗ trợ security-event notifications cho driveItem khi subscription được tạo với header phù hợp. Tuy nhiên, phạm vi subscription có giới hạn: OneDrive for Business chỉ cho subscribe ở root folder, không phải từng file riêng lẻ.

Nguồn:

- Microsoft Graph — driveItem resource: https://learn.microsoft.com/en-us/graph/api/resources/driveitem?view=graph-rest-1.0
- Microsoft Graph — delta query overview: https://learn.microsoft.com/en-us/graph/delta-query-overview
- Microsoft Graph — create subscription: https://learn.microsoft.com/en-us/graph/api/subscription-post-subscriptions?view=graph-rest-1.0

### Observation

Trong công việc thực tế, người dùng thường chia sẻ file qua:

- link “Anyone with the link”;
- share trực tiếp cho email;
- share cho nhóm;
- quyền inherited từ folder hoặc SharePoint site;
- quyền edit tạm thời nhưng không có quy trình thu hồi rõ ràng.

Giao diện OneDrive/SharePoint cho phép xem sharing theo từng item, nhưng nếu muốn trả lời các câu hỏi như “file nào đang có anonymous link?”, “tuần này permission nào mới xuất hiện?”, “link nào đã tồn tại 90 ngày?”, người dùng thường phải kiểm tra rời rạc từng vị trí.

### Assumption

Giả định MVP nhắm tới developer/technical lead hoặc chủ doanh nghiệp nhỏ dùng Microsoft 365 và có quyền truy cập chính các drive/site của mình. Không giả định có quyền tenant-wide hay quyền admin toàn tổ chức.

### Vì sao cách hiện tại bất tiện

- Permission phân tán ở nhiều file/folder.
- Không có lịch sử thay đổi dạng timeline riêng cho người dùng.
- Khó review định kỳ các link cũ.
- Một file bị move/rename vẫn có thể giữ sharing mà người dùng quên.
- Kiểm tra thủ công theo từng item rất tốn thời gian.
- Xuất inventory một lần không giúp phát hiện drift sau đó.

## 3. Người dùng mục tiêu

### Primary user

**Developer hoặc technical lead dùng Microsoft 365 cho công việc cá nhân/nhóm nhỏ.**

### Context of use

- Có nhiều tài liệu kỹ thuật, file proposal, export dữ liệu, tài liệu QA, checklist hoặc tài liệu nội bộ nằm trong OneDrive/SharePoint.
- Thỉnh thoảng phải share file cho đồng nghiệp, QA, PM, khách hàng hoặc vendor.
- Có nhu cầu tự kiểm tra quyền chia sẻ mà không chờ tenant admin hay security team.

### Main pain point

Người dùng không biết chính xác những file nào vẫn đang được share sau nhiều tuần/tháng và permission nào mới phát sinh.

### Current workaround

- Mở OneDrive/SharePoint rồi kiểm tra từng file.
- Ghi note thủ công khi share.
- Nhờ admin kiểm tra nếu có incident.
- Không kiểm tra gì cho tới khi phát sinh vấn đề.

### Lý do họ sẽ thử ShareScope

Chỉ cần đăng nhập Microsoft, chọn drive/site cần theo dõi, rồi có một trang “Exposure Review” liệt kê các chia sẻ đáng chú ý và lịch sử thay đổi.

## 4. Giải pháp đề xuất

### Main workflow

1. Người dùng đăng nhập bằng Microsoft Entra ID.
2. Chọn OneDrive hoặc SharePoint drive cần theo dõi.
3. ShareScope chạy initial inventory:
   - duyệt drive items;
   - đọc permission của item quan trọng;
   - chuẩn hóa permission thành snapshot.
4. Hệ thống lưu snapshot và `deltaLink`.
5. Background job chạy định kỳ bằng delta query để tìm item thay đổi.
6. Với item thay đổi, hệ thống đọc lại permission và so với snapshot trước.
7. Nếu phát hiện quyền mới, quyền bị mở rộng hoặc anonymous link mới, tạo finding.
8. Dashboard cho phép người dùng review, acknowledge hoặc mark as expected.

### Input

- Microsoft account/tenant identity.
- Drive hoặc site được phép truy cập.
- Policy đơn giản do user cấu hình, ví dụ:
  - cảnh báo anonymous link;
  - cảnh báo quyền `write` mới;
  - cảnh báo sharing tồn tại hơn 60 ngày;
  - bỏ qua một số folder.

### Processing

- Delta synchronization.
- Permission normalization.
- Diff hai snapshot.
- Rule-based risk scoring.
- Lưu lịch sử immutable ở mức application record.

### Output

- Danh sách sharing hiện tại.
- Timeline permission changes.
- Findings cần review.
- Daily/weekly summary tùy chọn.

### Tự động hóa

Tự động:

- polling delta link;
- refresh permission khi item thay đổi;
- so sánh snapshot;
- tạo finding;
- gửi notification.

Người dùng kiểm soát:

- drive/site được scan;
- policy;
- các item bị ignore;
- việc revoke permission.

**MVP không tự động revoke permission.** Đây là quyết định có thể gây gián đoạn nên phải để user review và xử lý thủ công trước.

### Key differentiator

ShareScope không cố làm một hệ thống DLP/SIEM doanh nghiệp. Nó là **permission drift tracker cấp cá nhân/nhóm nhỏ**, tập trung vào câu hỏi rất cụ thể: “quyền chia sẻ file của tôi đã thay đổi thế nào và cái gì cần review hôm nay?”.

### Ví dụ end-to-end

Một developer share file `Migration-Plan.xlsx` cho vendor với quyền edit trong tuần triển khai.

- Ngày 1: ShareScope thấy một permission mới và ghi snapshot.
- Ngày 30: quyền vẫn còn tồn tại.
- Policy đặt `external edit > 14 days` → finding mới xuất hiện.
- Dashboard hiển thị:
  - file;
  - email bên ngoài;
  - quyền edit;
  - thời điểm first seen;
  - last seen;
  - link mở trực tiếp trong Microsoft 365.
- User xác minh task đã xong rồi revoke quyền thủ công.
- Lần sync tiếp theo, ShareScope ghi nhận permission đã bị remove và đóng finding.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Ngay cả chỉ dùng cho chính developer, tool vẫn hữu ích vì file sharing là việc lặp lại thường xuyên nhưng review permission thường không được làm đều đặn.

### Technical learning value

Dự án chạm vào nhiều kỹ năng tốt cho Senior .NET Developer:

- delegated OAuth và Microsoft Graph;
- incremental synchronization;
- state token management;
- permission normalization;
- change detection;
- retry/throttling;
- rule engine;
- security-by-design.

### Vì sao phù hợp solo developer

Core workflow tương đối hẹp:

`Graph → snapshot → diff → finding → dashboard`

Không cần ML, queue phân tán, Kubernetes hay big data.

### Vẫn hữu ích khi chỉ có vài user

Tool có thể là personal utility self-hosted và đem lại giá trị ngay khi chỉ theo dõi một drive.

### Điều khiến ý tưởng thất bại

- Graph permission model quá phức tạp khiến kết quả dễ gây false positive.
- Người dùng không tin risk classification.
- Scope bị mở rộng thành một full security platform.
- Permission enumeration quá chậm trên drive lớn.

### Lý do mạnh nhất để không build

Nếu user chỉ lưu rất ít tài liệu và hiếm khi share externally, lợi ích không đủ lớn so với công sức duy trì OAuth, permission model và Graph throttling.

## 7. Luồng hoạt động

### Happy path

User connect Microsoft account
→ OAuth consent validation
→ discover drive
→ initial delta traversal
→ store item metadata
→ fetch permissions
→ normalize permissions
→ store snapshot
→ save `deltaLink`
→ scheduler chạy tiếp delta
→ detect changed items
→ refresh permissions
→ diff snapshot
→ create/update findings
→ dashboard + notification.

### Alternative flow: Graph trả nhiều trang

- Follow `@odata.nextLink` cho tới khi nhận `@odata.deltaLink`.
- Không đánh dấu sync complete trước khi lấy hết page.

### Alternative flow: item bị delete

Delta API có thể trả item với deleted facet.

Ứng dụng:

- mark item deleted;
- close active findings;
- giữ lịch sử snapshot trong retention period.

### Failure: delta token không còn dùng được

- Mark sync state `NeedsFullResync`.
- Chạy lại initial traversal.
- Không xóa lịch sử trước đó.

### Failure: 429/throttling

- Respect `Retry-After` nếu response có.
- exponential backoff;
- giới hạn số request song song.

### Failure: permission API bị denied

- Log item + error code;
- mark incomplete scan;
- không kết luận “safe” nếu dữ liệu permission chưa đọc được.

## 9. Công nghệ đề xuất

### .NET 10 + ASP.NET Core

**Vì sao phù hợp:** LTS, current supported runtime, background processing và OAuth integration mạnh.

**Đơn giản hơn:** Minimal API single project.

**Outgrow khi:** cần tách worker độc lập vì scan load tăng mạnh.

### Entity Framework Core 10

**Vì sao phù hợp:** schema nhỏ, relational model rõ, migration đơn giản.

**Đơn giản hơn:** Dapper.

**Outgrow khi:** bulk snapshot lớn tới mức insert hàng trăm nghìn record thường xuyên; khi đó có thể dùng COPY/bulk insert.

### PostgreSQL 17/18 tùy hosting

**Vì sao phù hợp:** JSONB hữu ích cho raw normalized permission metadata và SQL mạnh.

**Đơn giản hơn:** SQLite cho local-only prototype.

**Outgrow khi:** gần như không cần thay DB cho quy mô solo/small team.

### Microsoft Graph SDK cho .NET

**Vì sao phù hợp:** typed request model, auth integration thuận tiện.

**Đơn giản hơn:** raw `HttpClient` cho vài endpoint.

**Khi nên chuyển raw HTTP:** delta URL thường là opaque URL returned by Graph; đôi khi raw HTTP giúp xử lý state link rõ và ít phụ thuộc SDK abstraction hơn.

### BackgroundService

**Vì sao phù hợp:** một process, schedule đơn giản, không thêm infrastructure.

**Đơn giản hơn:** manual sync endpoint trong Phase 0.

**Outgrow khi:** hàng trăm connection hoặc cần durable distributed jobs.

### Vue 3 + Vite

**Vì sao phù hợp:** dashboard nhẹ, table/filter tốt, dev experience nhanh.

**Đơn giản hơn:** Razor Pages.

**Outgrow khi:** không có giới hạn đáng kể ở quy mô này.

### Docker Compose

**Vì sao phù hợp:** self-hosting một lệnh.

**Đơn giản hơn:** chạy trực tiếp `dotnet run` + local PostgreSQL.

**Outgrow khi:** SaaS multi-tenant lớn mới cân nhắc managed container/orchestrator.

## 11. API và tích hợp

### Microsoft Graph — driveItem delta

**Purpose:** incremental sync.

**Authentication:** OAuth access token, delegated permission phù hợp với drive user có quyền truy cập.

**Cost/rate limit:** Graph có throttling; app phải xử lý 429 và backoff.

**Privacy:** metadata file có thể nhạy cảm; không log full path nếu deployment multi-user.

**Fallback:** manual/full resync.

Docs:

- https://learn.microsoft.com/en-us/graph/delta-query-overview
- https://learn.microsoft.com/en-us/graph/api/resources/driveitem?view=graph-rest-1.0

### Microsoft Graph — driveItem permissions

**Purpose:** lấy sharing state thực tế.

**Authentication:** delegated Graph permissions phù hợp.

**Cost/rate limit:** request theo item có thể trở thành N+1; MVP chỉ refresh permission cho item thay đổi hoặc item được policy theo dõi.

**Privacy:** recipient identity là dữ liệu nhạy cảm.

**Fallback:** đánh dấu item `PermissionStateUnknown`; không giả định safe.

### Microsoft Graph change notifications

**Purpose:** later phase để giảm polling latency.

**Confirmed limitation:** OneDrive for Business subscribe ở root; không subscribe individual files.

Docs:

https://learn.microsoft.com/en-us/graph/api/subscription-post-subscriptions?view=graph-rest-1.0

**Fallback:** periodic delta polling.

### Telegram Bot API hoặc SMTP

Chỉ dùng cho notification sau MVP.

Nếu unavailable, finding vẫn tồn tại trên dashboard.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem là permission state, diff và policy evaluation — tất cả nên deterministic.

Không nên dùng LLM để quyết định một permission có “an toàn” hay không vì:

- không cần natural-language reasoning;
- output phải repeatable;
- risk scoring phải giải thích được;
- không nên gửi metadata tài liệu cho model ngoài hệ thống nếu không cần.

### AI có thể hữu ích sau này nhưng không phải MVP

Một optional feature tương lai có thể dùng AI để tạo weekly summary tự nhiên từ structured findings, ví dụ:

> “Tuần này xuất hiện 2 external edit permissions và 1 anonymous link.”

Ngay cả phần này cũng có deterministic template fallback nên AI không phải dependency.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác nhận Graph permission data đủ để tạo useful diff.

**Tasks:**

- Tạo test Entra app.
- Login delegated.
- Gọi Graph lấy drive root.
- Liệt kê 20–50 items.
- Đọc permissions cho 5–10 file đã share theo các kiểu khác nhau.
- Tạo bảng thủ công so sánh API response với UI Microsoft 365.

**Expected output:** một console prototype dump normalized permission JSON.

**Completion criteria:** ít nhất 3 loại sharing được nhận dạng chính xác và stable key cho permission diff được xác định.

### Phase 1 — Core MVP

**Goal:** complete vertical workflow.

**Tasks:**

- ASP.NET API.
- EF Core schema.
- OAuth connection.
- Initial delta sync.
- Permission normalization.
- Snapshot + diff.
- 3 risk rules.
- Vue dashboard.

**Expected output:** thay đổi sharing trên một test file xuất hiện trên dashboard sau sync.

**Completion criteria:** user tạo permission → sync → finding xuất hiện → user remove permission → next sync đóng finding.

### Phase 2 — Reliability

**Goal:** không mất state khi Graph/API fail.

**Tasks:**

- checkpoint transaction.
- retry 429/5xx.
- token refresh handling.
- idempotent snapshot updates.
- incomplete-state flag.
- structured logs.
- unit/integration tests.

**Expected output:** sync có thể retry mà không tạo duplicate changes.

**Completion criteria:** fault injection 429/timeout/restart không làm mất delta state hoặc nhân đôi finding.

### Phase 3 — Useful expansion

## 14. Các bài toán kỹ thuật đáng học

### 1. Incremental synchronization

Phải quản lý `nextLink`, `deltaLink`, pagination và re-sync.

**Skill cải thiện:** thiết kế sync engine và checkpoint bền vững.

### 2. Permission normalization

Graph permission object có nhiều dạng identity/link/inheritance.

**Skill cải thiện:** domain modeling từ external API phức tạp.

### 3. Idempotency

Một item có thể xuất hiện nhiều lần trong change stream hoặc sync retry.

**Skill cải thiện:** durable processing, deterministic diff và unique-key design.

### 4. API throttling

Permission lookup trên nhiều item dễ tạo burst request.

**Skill cải thiện:** concurrency control, backoff, rate-limit-aware architecture.

### 5. Privacy-preserving metadata

Không cần lưu file content nhưng vẫn phải bảo vệ filename, path, email recipient và token.

**Skill cải thiện:** data minimization, encryption, safe logging.

## 15. Rủi ro và cách xử lý

### Risk: Graph permission semantics phức tạp

**Mitigation:**

- lưu raw JSON song song normalized data;
- chỉ classify các case đã verify;
- trạng thái `Unknown` thay vì đoán.

### Risk: request quá nhiều

**Mitigation:**

- delta sync;
- chỉ refresh permission cho changed item;
- bounded concurrency 2–5 workers;
- exponential backoff;
- cache safe metadata ngắn hạn.

### Risk: false positive

**Mitigation:**

- rule-based finding rõ lý do;
- allow acknowledge/ignore;
- không có opaque AI scoring.

### Risk: sensitive metadata

**Mitigation:**

- không tải file content;
- encrypt OAuth tokens;
- hash recipient identity nếu full email không cần;
- redact logs;
- self-host option.

### Risk: token/consent hết hạn

**Mitigation:**

- connection health state;
- explicit reconnect flow;
- không spam retry khi consent bị revoke.

### Risk: scope creep thành DLP platform

**Mitigation:**

MVP chỉ có 3–4 rules và một drive. Không scan mail, Teams, endpoints, malware, content classification hay tenant-wide data.

### Risk: maintenance burden

**Mitigation:**

- dùng Graph v1.0;
- isolate Graph adapter;
- integration tests với recorded fixtures;
- pin SDK versions.

## 20. Việc cần làm ngay hôm nay

### Session 60–120 phút: chứng minh permission diff hoạt động

#### Development objective

Tạo console prototype kết nối Microsoft Graph, đọc permission của một file test hai lần và in ra diff sau khi user thay đổi sharing trong OneDrive.

#### Files/components cần tạo

```text
ShareScope/
  src/
    ShareScope.Spike/
      Program.cs
      GraphClientFactory.cs
      PermissionNormalizer.cs
      Models/
        NormalizedPermission.cs
      appsettings.json
```

#### Setup

```bash
dotnet new sln -n ShareScope
mkdir src
cd src
dotnet new console -n ShareScope.Spike -f net10.0
cd ..
dotnet sln add src/ShareScope.Spike/ShareScope.Spike.csproj
```

Thêm package Microsoft Graph/Auth phù hợp phiên bản hiện hành hoặc, để spike đơn giản hơn, dùng `HttpClient` + access token lấy bằng delegated flow.

#### First vertical slice

1. Authenticate Microsoft account.
2. Lấy `drive/root/children`.
3. Chọn một test file theo ID.
4. Gọi permission endpoint.
5. Normalize thành list:

```json
[
  {
    "permissionKey": "...",
    "role": "read",
    "recipientType": "external-user",
    "linkScope": null
  }
]
```

6. Save JSON thành `before.json`.
7. User mở OneDrive và share thêm file cho một test account hoặc tạo sharing link.
8. Run tool lần nữa → `after.json`.
9. Code in ra:

```text
ADDED  external-user  write  vendor@example.com
```

hoặc:

```text
ADDED  anonymous-link  read
```

#### Expected result

Một thay đổi permission thật trên OneDrive được detect bằng code deterministic.

#### Verification checklist

- [ ] Login thành công bằng delegated auth.
- [ ] Đọc được test drive item.
- [ ] Đọc được permissions.
- [ ] Không lưu file content.
- [ ] `PermissionNormalizer` cho output stable giữa hai lần chạy nếu permission không đổi.
- [ ] Add một sharing permission → diff báo `ADDED`.
- [ ] Remove permission → diff báo `REMOVED`.
- [ ] Access token không xuất hiện trong console/log file.

#### Stop condition

Dừng session ngay khi tool detect chính xác **một permission added và một permission removed** trên cùng test file. Không xây database, UI, scheduler hoặc Docker trong session đầu.

## Research notes

### Confirmed

- Microsoft Graph hỗ trợ `driveItem` cho file/folder OneDrive và SharePoint.
- `driveItem` có API permissions và khả năng track changes.
- Delta query hỗ trợ `driveItem` và dùng `@odata.nextLink`/`@odata.deltaLink` cho incremental sync.
- Change notifications hỗ trợ OneDrive/SharePoint drive hierarchy; OneDrive for Business có giới hạn subscription ở root.
- .NET 10 là LTS, Active support và theo support policy ngày 2026-07-14 được hỗ trợ đến 2028-11-14.

### Analysis

Những API hiện có đủ để xây một MVP permission drift tracker mà không cần application-wide tenant access hoặc lưu file content.

### Assumptions

- Primary user chấp nhận delegated sign-in và chỉ scan tài nguyên mà chính họ được phép truy cập.
- Drive quy mô cá nhân/nhóm nhỏ đủ để periodic delta sync và selective permission refresh hoạt động với chi phí thấp.

### Recommendation

Bắt đầu bằng console spike kiểm chứng permission object thật trước. Nếu API response không ổn định hoặc không đủ để phân biệt external/anonymous/write theo cách đáng tin, nên dừng dự án trước khi xây dashboard.
