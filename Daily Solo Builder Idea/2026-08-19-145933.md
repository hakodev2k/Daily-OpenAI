# Ý tưởng hôm nay: FlakeAtlas — Playwright Failure Fingerprint Hub

## 1. Tóm tắt ý tưởng

FlakeAtlas là một công cụ self-hosted giúp developer và QA engineer **thu thập artifact từ các lần chạy Playwright thất bại, tạo fingerprint cho lỗi, nhóm các failure giống nhau và theo dõi flaky test theo thời gian**. Thay vì mở từng `trace.zip`, screenshot và log riêng lẻ trong CI, người dùng có một dashboard cho biết lỗi nào đang lặp lại, lỗi nào mới xuất hiện và test nào “fail rồi pass khi retry”.

- Người dùng chính: developer/QA automation trong team nhỏ hoặc solo developer có test Playwright chạy trên CI.
- Bài toán chính: mất thời gian điều tra cùng một failure lặp lại ở nhiều workflow run.
- Quy mô: **Medium**.
- MVP dự kiến: **2–3 tuần**.

## 2. Bài toán thực tế

Playwright cung cấp Trace Viewer rất mạnh cho việc điều tra một test run cụ thể. Trace có thể chứa DOM snapshot, screenshot, network activity và source context; Playwright cũng hỗ trợ giữ trace khi failure hoặc khi retry. Đây là nền tảng tốt để debug một lỗi đơn lẻ. [Playwright — Tracing](https://playwright.dev/docs/api/class-tracing) [Playwright — Test trace options](https://playwright.dev/docs/api/class-testoptions)

Playwright HTML report còn phân biệt các test passed, failed, flaky và skipped; khi chạy CI, cấu hình phổ biến là retry test và capture trace ở retry đầu tiên. [Playwright — Trace Viewer](https://playwright.dev/docs/next/trace-viewer-intro)

**Vấn đề còn lại:** Trace Viewer chủ yếu giúp xem từng execution. Khi một suite có hàng trăm test chạy mỗi ngày, developer vẫn phải tự trả lời các câu hỏi mang tính lịch sử:

- Lỗi này có phải lỗi mới không?
- Failure tương tự đã xảy ra bao nhiêu lần tuần này?
- Test này thật sự flaky hay chỉ fail do một regression mới?
- Những failure khác nhau có cùng root cause như `Timeout waiting for selector` hay cùng request `500` không?
- Retry đang che giấu bao nhiêu test không ổn định?

Cách xử lý hiện tại thường là mở CI run → download artifact → mở trace → đọc log → tìm workflow run cũ → so sánh thủ công.

GitHub Actions cho phép upload/download workflow artifacts và cấu hình retention cho artifact trong giới hạn repository/organization. Điều này thuận tiện cho lưu trữ ngắn hạn nhưng không tự biến artifact thành lịch sử lỗi có thể query và nhóm theo fingerprint. [GitHub Docs — Store and share workflow data with artifacts](https://docs.github.com/en/actions/tutorials/store-and-share-data)

**Observation:** tooling hiện có giải quyết “debug execution” tốt hơn “failure intelligence theo thời gian”.

**Assumption cần validation:** một developer hoặc team nhỏ sẽ thấy đáng dùng nếu FlakeAtlas giảm đáng kể số lần phải mở lại trace của cùng một loại lỗi.

## 3. Người dùng mục tiêu

### Primary user

Developer hoặc QA automation engineer duy trì Playwright E2E suite khoảng vài chục đến vài trăm test và chạy trên GitHub Actions/Azure DevOps.

### Bối cảnh sử dụng

- Test chạy mỗi PR hoặc theo lịch.
- CI có retry để giảm false-negative.
- Failure artifacts gồm trace, screenshot, console log hoặc HTML report.
- Team nhỏ chưa muốn mua một test analytics platform lớn.

### Main pain point

Không biết failure hiện tại là “lỗi mới” hay “một flaky failure đã thấy nhiều lần”.

### Current workaround

- Xem HTML report từng run.
- Download `trace.zip`.
- Search logs thủ công.
- Ghi chú flaky test trong issue/Excel/Notion.
- Retry cho tới khi pipeline xanh.

### Lý do họ sẽ thử FlakeAtlas

Nếu chỉ cần upload một file JSON/artifact từ CI và nhận lại:

> “Failure này thuộc cluster #12, đã xảy ra 17 lần trong 14 ngày, 82% pass ở retry đầu tiên.”

thì việc triage sẽ nhanh và có căn cứ hơn.

## 4. Giải pháp đề xuất

FlakeAtlas không thay Trace Viewer. Nó đứng **trước Trace Viewer** như một lớp indexing và triage.

### Main workflow

1. Playwright test run kết thúc.
2. CI tạo một `flakeatlas-run.json` chứa metadata:
   - test name
   - project/browser
   - status từng attempt
   - duration
   - error message
   - stack trace
   - trace path
   - screenshot path
   - commit SHA
   - branch
   - workflow run ID
3. Một CLI nhỏ upload manifest + artifact cần thiết vào FlakeAtlas.
4. Backend normalize error.
5. Fingerprint engine tính `FailureFingerprint` bằng deterministic rules.
6. Failure được gắn vào cluster có fingerprint tương ứng.
7. Dashboard hiển thị:
   - New failure
   - Known flaky
   - Regression candidate
   - Frequency 7/30 ngày
   - Retry recovery rate
8. User click cluster để mở execution cụ thể hoặc link tới Playwright Trace Viewer.

### Input

- Metadata JSON do reporter/CLI sinh ra.
- Optional `trace.zip`.
- Optional screenshot và log excerpt.

### Processing

- Normalize error strings.
- Loại dynamic tokens như GUID, timestamp, port, test data ID.
- Extract exception type, call site, failing action, URL/path khi có.
- Hash thành fingerprint.
- Group failure.
- Tính statistics.

### Output

Ví dụ:

```text
Cluster FLK-018
Test: Checkout should create order
Fingerprint: TimeoutError|checkout.spec.ts:87|button[data-test=confirm]
Occurrences: 12 / 7 days
Retry recovery: 10/12
Browsers: chromium 12
First seen: 2026-08-14
Last seen: 2026-08-19
Classification: Likely flaky
```

### Automation

Hệ thống tự group và tính metrics. Người dùng vẫn quyết định:

- cluster có thật sự cùng root cause không;
- test có nên quarantine không;
- failure là app bug hay test bug;
- cluster nào đã resolved.

### Key differentiator

Không cố phân tích toàn bộ trace bằng AI. MVP tập trung vào **deterministic fingerprint + lịch sử occurrence + retry behavior**, sau đó link tới trace gốc để người dùng điều tra sâu.

### Ví dụ end-to-end

`Login should redirect to dashboard` fail ở CI với:

```text
TimeoutError: locator('[data-test=profile-avatar]') timed out after 10000ms
```

Một tuần trước lỗi tương tự có timeout `15000ms` và URL chứa test user khác. FlakeAtlas normalize các giá trị động, nhận ra cùng call site + locator + error type và đưa vào cùng cluster.

Developer thấy cluster này đã xảy ra 23 lần nhưng 20 lần pass ở retry. Thay vì mở 23 trace, họ mở 2–3 representative traces để tìm root cause.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Dự án hữu ích ngay cả khi chỉ dùng cho một repository cá nhân. Sau vài tuần chạy CI, lịch sử failure trở thành dữ liệu giúp quyết định test nào đáng sửa trước.

### Technical learning value

Dự án có các bài toán không phải CRUD đơn thuần:

- log normalization;
- deterministic fingerprinting;
- artifact ingestion;
- CI integration;
- reliability metrics;
- long-term time-series aggregation;
- safe handling of traces có thể chứa dữ liệu nhạy cảm.

### Phù hợp solo developer

Core workflow nhỏ: ingest → fingerprint → cluster → dashboard. Không cần microservices, distributed tracing hay data warehouse ở MVP.

### Có ích dù chỉ có vài user

Một repository với suite chạy vài chục lần mỗi tuần đã đủ tạo dữ liệu cho tool.

### Ý tưởng sẽ fail nếu

- fingerprint grouping có false positive quá cao;
- setup CI phức tạp hơn giá trị nhận được;
- dashboard chỉ lặp lại thông tin mà Playwright report đã có;
- người dùng không chạy E2E đủ thường xuyên để lịch sử có giá trị.

### Lý do mạnh nhất để không build

Nếu suite rất nhỏ và failure chỉ xảy ra vài lần mỗi tháng, mở Trace Viewer trực tiếp có thể nhanh hơn duy trì thêm một service.

## 7. Luồng hoạt động

### Happy path

CI test run
→ Playwright reporter sinh manifest
→ upload manifest
→ API validate schema
→ persist run metadata
→ normalize failure
→ calculate fingerprint
→ find/create cluster
→ update counters
→ dashboard hiển thị cluster mới/cũ
→ user mở trace khi cần.

### Retry flow

Attempt 1 fail
→ attempt 2 pass
→ run vẫn được ingest đầy đủ
→ test result được đánh dấu `RecoveredByRetry`
→ cluster nhận thêm occurrence
→ retry recovery rate được cập nhật.

### Failure cases

**Manifest invalid**

→ `400` với schema error chi tiết.

**Artifact upload fail nhưng metadata upload thành công**

→ giữ result; artifact status `Missing`; cho phép retry upload riêng.

**Fingerprint collision**

→ user có thể split occurrence khỏi cluster.

**CI gửi cùng run hai lần**

→ deduplicate bằng `(ProjectId, ProviderRunId, TestId, AttemptNumber)`.

**Trace quá lớn**

→ reject theo size limit hoặc chỉ lưu external artifact URL.

**Backend temporarily unavailable**

→ CLI retry với exponential backoff; nếu vẫn fail thì lưu bundle tại CI artifact để upload lại sau.

## 8. Kiến trúc đề xuất

### Kiến trúc tổng thể

**Modular monolith** là đủ cho MVP.

```text
Playwright CI
   |
   | flakeatlas upload
   v
ASP.NET Core API
   |
   +-- Ingestion
   +-- Fingerprinting
   +-- Clustering
   +-- Analytics
   +-- Artifact Metadata
   |
PostgreSQL
   |
Local/S3-compatible artifact storage (optional)
   |
Vue Dashboard
```

### Frontend

Vue 3 dashboard gồm 4 màn hình:

- Projects
- Runs
- Failure Clusters
- Cluster Detail

### Backend

ASP.NET Core Minimal API hoặc controllers, chia module theo domain.

### Database

PostgreSQL cho query lịch sử, unique constraints và aggregate đơn giản.

### Background worker

Không bắt buộc ở vertical slice đầu tiên. Khi upload trace/artifact, dùng `BackgroundService` hoặc Hangfire để xử lý cleanup và các job không cần trả ngay.

### Scheduler

Một daily retention cleanup job là đủ.

### Queue

Không cần RabbitMQ ở MVP. DB-backed job queue hoặc background worker đủ.

### Cache

Không cần.

### File storage

MVP có hai mode:

1. **Metadata-only:** giữ URL tới GitHub artifact.
2. **Self-hosted artifact:** lưu trace/screenshot vào local volume hoặc S3-compatible storage.

Metadata-only nên là mode đầu tiên vì giảm complexity và privacy risk.

### Authentication

Single-user API key cho MVP. Multi-user/OAuth để sau.

### External APIs

GitHub API chỉ cần khi muốn tự download artifacts hoặc comment PR. MVP có thể hoàn toàn không cần GitHub token nếu CI chủ động POST dữ liệu.

### AI model

Không cần ở MVP.

### Logging

Serilog hoặc built-in structured logging với:

- ProjectId
- RunId
- TestId
- ClusterId
- Fingerprint

### Deployment

Docker Compose trên VPS/mini PC hoặc Azure Container Apps. Không cần Kubernetes.

## 9. Công nghệ đề xuất

### .NET 10 LTS + ASP.NET Core

Microsoft hiện liệt kê .NET 10 là LTS, được support tới tháng 11/2028. Đây là lựa chọn hợp lý cho project mới trong năm 2026. [Microsoft Learn — .NET releases and support](https://learn.microsoft.com/en-us/dotnet/core/releases-and-support)

**Vì sao phù hợp:** HTTP ingestion, background jobs, hashing, JSON parsing và PostgreSQL đều rất tự nhiên trong .NET.

**Simpler alternative:** .NET 10 Minimal API một project duy nhất.

**Khi outgrow:** chỉ tách ingestion worker khi số artifact upload đồng thời tăng đáng kể.

### EF Core + PostgreSQL

**Vì sao phù hợp:** schema relational rõ, cần unique constraints và aggregate theo thời gian.

**Simpler alternative:** SQLite nếu chỉ dùng cho một repo trên máy cá nhân.

**Khi outgrow:** nếu occurrence tăng tới hàng chục triệu, có thể archive dữ liệu cũ hoặc thêm materialized aggregates trước khi nghĩ tới hệ thống khác.

### Vue 3 + Vite

**Vì sao phù hợp:** nhanh để làm filter/table/detail dashboard.

**Simpler alternative:** Razor Pages để giảm frontend toolchain.

### Playwright custom reporter hoặc CLI

MVP nên bắt đầu với CLI đọc JSON result để tránh coupling sâu vào Playwright internals.

Sau khi workflow chứng minh hữu ích, mới tạo reporter package.

### Docker

API + PostgreSQL chạy được local/self-hosted.

### GitHub Actions

Dùng để chạy test, tạo manifest và gọi upload CLI. GitHub Actions hỗ trợ workflow artifact và retention configuration. [GitHub Docs — Workflow artifacts](https://docs.github.com/en/actions/tutorials/store-and-share-data)

### Playwright

Playwright trace có thể lưu screenshot, DOM snapshot và network activity; Playwright Test còn có các trace mode như `on-first-retry`, `retain-on-failure` và `on-all-retries`. [Playwright — Tracing](https://playwright.dev/docs/api/class-tracing) [Playwright — TestOptions.trace](https://playwright.dev/docs/api/class-testoptions)

## 10. Thiết kế dữ liệu ban đầu

### Project

**Purpose:** một test suite/repository được theo dõi.

Fields:

- `Id`
- `Name`
- `RepositoryUrl`
- `ApiKeyHash`
- `RetentionDays`
- `CreatedAt`

Relationships:

- Project 1-N TestRun
- Project 1-N TestCase
- Project 1-N FailureCluster

Retention: cấu hình theo project.

### TestRun

**Purpose:** đại diện một CI run.

Fields:

- `Id`
- `ProjectId`
- `Provider`
- `ProviderRunId`
- `CommitSha`
- `Branch`
- `PullRequestNumber`
- `StartedAt`
- `CompletedAt`
- `CiUrl`

Unique:

```text
(ProjectId, Provider, ProviderRunId)
```

### TestCase

**Purpose:** identity ổn định của test.

Fields:

- `Id`
- `ProjectId`
- `Suite`
- `Title`
- `SourceFile`
- `SourceLine`
- `StableKey`

### TestAttempt

**Purpose:** từng execution kể cả retry.

Fields:

- `Id`
- `TestRunId`
- `TestCaseId`
- `AttemptNumber`
- `BrowserProject`
- `Status`
- `DurationMs`
- `ErrorType`
- `ErrorMessage`
- `StackTrace`
- `TraceLocation`
- `ScreenshotLocation`

### FailureCluster

**Purpose:** nhóm failure được coi là cùng signature.

Fields:

- `Id`
- `ProjectId`
- `Fingerprint`
- `NormalizedSignature`
- `FirstSeenAt`
- `LastSeenAt`
- `OccurrenceCount`
- `RetryRecoveredCount`
- `State` (`Open`, `Ignored`, `Resolved`)

### FailureOccurrence

**Purpose:** mapping attempt thất bại vào cluster.

Fields:

- `Id`
- `FailureClusterId`
- `TestAttemptId`
- `DetectedAt`
- `FingerprintVersion`

Retention: xóa occurrence cũ theo policy nhưng có thể giữ aggregate cluster lâu hơn.

## 11. API và tích hợp

### Playwright

**Purpose:** nguồn test metadata và trace.

**Authentication:** không cần với local result files.

**Cost/rate limit:** không có API cost cho việc đọc artifact local.

**Privacy concern:** trace có thể chứa DOM, request data và source context.

**Fallback:** metadata-only manifest; không upload trace.

### GitHub Actions artifacts

**Purpose:** giữ trace/screenshot ở CI và chỉ lưu link/reference trong FlakeAtlas.

**Authentication:** GitHub token cần nếu backend chủ động tải private artifact; không cần nếu chỉ lưu CI URL hoặc upload từ workflow.

**Rate/cost concern:** artifact retention chịu giới hạn cấu hình repository/organization. [GitHub Docs](https://docs.github.com/en/actions/tutorials/store-and-share-data)

**Privacy:** private repository artifact không nên copy sang public storage.

**Fallback:** workflow trực tiếp upload artifact tới FlakeAtlas hoặc chỉ lưu metadata.

### GitHub PR comment — Later

**Purpose:** comment “3 known flaky, 1 new failure” lên PR.

**Authentication:** GitHub App hoặc token với permission tối thiểu phù hợp.

**Fallback:** dashboard-only.

### S3-compatible storage — Optional

**Purpose:** lưu trace lâu dài.

**Authentication:** access key/managed identity tùy provider.

**Cost:** storage tăng theo số trace.

**Privacy:** cần encryption + retention.

**Fallback:** local volume hoặc GitHub artifact URL.

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

AI không nên quyết định core fingerprint vì grouping phải repeatable và testable.

### Nếu thêm AI sau MVP

AI có thể nhận:

- normalized error;
- 3 representative stack traces;
- console excerpt;
- network errors đã được redact;
- occurrence stats.

Task duy nhất:

> tạo summary ngắn giúp developer biết cluster có dấu hiệu gì chung.

Expected structured output:

```json
{
  "summary": "Most failures happen after the checkout POST returns 503.",
  "suspectedLayer": "backend",
  "evidence": [
    "11/13 attempts contain POST /api/orders 503",
    "all occur before confirmation locator timeout"
  ],
  "confidence": "medium"
}
```

### Validation

- AI không được thay đổi cluster membership.
- Evidence phải tham chiếu dữ liệu đã có.
- UI luôn hiển thị raw deterministic data cạnh AI summary.

### Deterministic fallback

Nếu AI unavailable, tool vẫn hoạt động đầy đủ bằng fingerprint + metrics.

### Risks

- Hallucination root cause.
- Chi phí API.
- Trace/log chứa dữ liệu nhạy cảm.
- Latency.

Vì vậy AI không thuộc Must Have.

## 14. Các bài toán kỹ thuật đáng học

### 1. Failure fingerprinting

Cần biến error không ổn định thành signature ổn định mà không group nhầm.

Kỹ năng cải thiện:

- text normalization;
- hashing;
- similarity boundaries;
- domain-driven heuristics.

### 2. Idempotent ingestion

CI có thể retry upload hoặc workflow được rerun.

Kỹ năng cải thiện:

- idempotency keys;
- unique constraints;
- upsert strategy;
- distributed workflow thinking.

### 3. Flaky-test metrics

Một test “fail rồi pass retry” không đồng nghĩa 100% với flaky; cần định nghĩa metric rõ.

Kỹ năng cải thiện:

- operational metrics;
- time-window aggregation;
- tránh kết luận sai từ retry data.

### 4. Artifact lifecycle

Trace có thể lớn và chứa thông tin nhạy cảm.

Kỹ năng cải thiện:

- retention;
- storage abstraction;
- encryption;
- access control;
- cost awareness.

### 5. CI integration

Tool chỉ hữu ích nếu integration gần như không tạo friction.

Kỹ năng cải thiện:

- custom reporter/CLI;
- GitHub Actions;
- resilient upload;
- artifact handling.

## 15. Rủi ro và cách xử lý

### False-positive cluster

**Risk:** hai root cause khác nhau bị group chung vì cùng `TimeoutError`.

**Mitigation:** fingerprint gồm error type + source call site + normalized locator/action; hỗ trợ manual split; version fingerprint algorithm.

### False-negative cluster

**Risk:** dynamic text khiến cùng lỗi sinh fingerprint khác nhau.

**Mitigation:** normalize GUID, timestamp, numeric IDs, ports, generated test names; viết fixture test cho normalization.

### Privacy

**Risk:** traces có DOM, URL, headers hoặc dữ liệu test.

**Mitigation:** metadata-only mặc định; trace upload opt-in; retention ngắn; private storage; redaction; không gửi trace sang AI theo default.

### Storage cost

**Risk:** giữ trace cho mọi failure làm disk tăng nhanh.

**Mitigation:** chỉ giữ trace representative hoặc external URL; retention 7/30 ngày; dedupe bằng SHA-256 nếu cần.

### Scope creep

**Risk:** biến thành full observability/test management platform.

**Mitigation:** MVP chỉ Playwright + failure clustering + retry metrics.

### User adoption

**Risk:** thêm bước upload khiến team bỏ dùng.

**Mitigation:** CLI một command và GitHub Actions snippet nhỏ; sau đó mới custom reporter.

### API dependency

**Risk:** backend tự kéo GitHub artifacts sẽ phụ thuộc permissions/rate limits.

**Mitigation:** MVP để CI push metadata sang backend, không cần backend gọi GitHub API.

## 16. Kiểm thử

### Strategy

- Unit test normalization và fingerprint.
- Integration test EF Core + PostgreSQL.
- API contract test cho manifest ingestion.
- E2E Playwright cho dashboard.
- Failure-path test cho duplicate upload, malformed manifest và storage missing.
- Security test cho API key và path traversal nếu upload file.

### 5 test scenario quan trọng nhất

1. Hai error chỉ khác GUID/timestamp phải vào cùng fingerprint.
2. Hai `TimeoutError` khác call site/locator phải tạo cluster khác nhau.
3. Upload cùng `ProviderRunId` hai lần không duplicate attempt.
4. Test fail attempt 1 và pass attempt 2 phải tăng `RetryRecoveredCount` đúng một lần.
5. Artifact không tồn tại nhưng metadata hợp lệ vẫn được ingest và cluster vẫn query được.

## 17. Cách đo dự án có hữu ích hay không

### Product usage metric

- Số failure cluster được mở/triage mỗi tuần.
- Tỷ lệ failure được nhận diện là “known cluster” thay vì “new”.

### Time saved

Đo median thời gian từ CI fail đến khi developer biết failure thuộc loại nào.

Baseline trước tool: ví dụ mở CI + download trace + search workflow cũ.

Sau tool: xem cluster detail trước, chỉ mở trace khi cần.

### Task completion rate

% failed CI runs được ingest thành công và gắn cluster.

### Error rate

- ingestion failure rate;
- duplicate occurrence rate;
- manual split rate — proxy cho false-positive grouping.

### Repeated use

Ít nhất 3–4 ngày/tuần có người mở dashboard trong các tuần có CI failure.

### Technical reliability

- >99% manifest hợp lệ được ingest thành công trong self-hosted environment mục tiêu.
- duplicate upload không thay đổi aggregate sai.

### AI quality metric

Không áp dụng cho MVP vì AI không cần thiết.

### Success criterion thực dụng

Sau 30 ngày, nếu tool giúp nhận ra ít nhất 3 recurring failure cluster mà không phải mở lại toàn bộ trace cũ và giảm đáng kể triage time, project đã chứng minh giá trị cá nhân.

## 20. Việc cần làm ngay hôm nay

### Mục tiêu session 60–120 phút

Tạo **fingerprint engine + CLI prototype** nhận file JSON chứa failure và in ra cluster fingerprint ổn định.

Không làm database, dashboard hoặc GitHub integration trong session đầu.

### Components/files cần tạo

```text
FlakeAtlas.sln
src/
  FlakeAtlas.Core/
    Failures/
      FailureInput.cs
      FailureNormalizer.cs
      FailureFingerprintService.cs
  FlakeAtlas.Cli/
    Program.cs
tests/
  FlakeAtlas.Core.Tests/
    FailureNormalizerTests.cs
samples/
  failures.json
```

### Commands

```bash
dotnet new sln -n FlakeAtlas

dotnet new classlib -n FlakeAtlas.Core -o src/FlakeAtlas.Core
dotnet new console -n FlakeAtlas.Cli -o src/FlakeAtlas.Cli
dotnet new xunit -n FlakeAtlas.Core.Tests -o tests/FlakeAtlas.Core.Tests

dotnet sln add src/FlakeAtlas.Core
dotnet sln add src/FlakeAtlas.Cli
dotnet sln add tests/FlakeAtlas.Core.Tests

dotnet add src/FlakeAtlas.Cli reference src/FlakeAtlas.Core
dotnet add tests/FlakeAtlas.Core.Tests reference src/FlakeAtlas.Core
```

### Sample input

```json
[
  {
    "test": "checkout creates order",
    "errorType": "TimeoutError",
    "message": "locator('[data-test=confirm]') timed out after 10000ms for order 18432",
    "sourceFile": "tests/checkout.spec.ts",
    "sourceLine": 87
  },
  {
    "test": "checkout creates order",
    "errorType": "TimeoutError",
    "message": "locator('[data-test=confirm]') timed out after 15000ms for order 99127",
    "sourceFile": "tests/checkout.spec.ts",
    "sourceLine": 87
  }
]
```

### Fingerprint rule v1

1. Lowercase message.
2. Normalize timeout duration:

```text
10000ms -> {duration}
```

3. Normalize large numeric IDs:

```text
18432 -> {number}
```

4. Normalize GUID nếu có.
5. Giữ error type.
6. Giữ source file + line.
7. SHA-256 signature canonical.

Canonical string ví dụ:

```text
timeouterror|tests/checkout.spec.ts:87|locator('[data-test=confirm]') timed out after {duration} for order {number}
```

### Expected result

Chạy:

```bash
dotnet run --project src/FlakeAtlas.Cli -- samples/failures.json
```

Output:

```text
Fingerprint: 7af2...
Occurrences: 2
Tests:
- checkout creates order
```

Hai sample failure phải có cùng fingerprint.

Sau đó thêm sample thứ ba:

```text
locator('[data-test=cancel]') timed out ...
```

Nó phải tạo fingerprint khác.

### Verification checklist

- [ ] Solution build thành công.
- [ ] CLI đọc JSON file.
- [ ] GUID/timestamp/dynamic ID được normalize.
- [ ] Hai failure cùng locator/call site tạo cùng fingerprint.
- [ ] Failure khác locator tạo fingerprint khác.
- [ ] Có ít nhất 5 unit tests cho normalizer.
- [ ] Output nhìn thấy ngay trên terminal.

### Stop condition

Dừng session khi CLI có thể nhận ít nhất 3 failure sample, group đúng thành 2 fingerprint và toàn bộ unit test pass. **Không** mở rộng sang PostgreSQL, Vue, CI uploader hoặc AI trong buổi đầu.
