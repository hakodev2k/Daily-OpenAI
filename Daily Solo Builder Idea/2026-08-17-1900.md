# Ý tưởng hôm nay: FlakyTest Ledger — Sổ theo dõi test không ổn định từ CI

## 1. Tóm tắt ý tưởng

**FlakyTest Ledger** là một công cụ self-hosted nhỏ dành cho developer và QA engineer, tự thu thập lịch sử test từ CI để phát hiện những test lúc pass lúc fail, xếp hạng mức độ bất ổn và lưu bằng chứng phục vụ việc sửa lỗi. Thay vì chỉ nhìn một lần chạy CI bị đỏ, người dùng có một “hồ sơ sức khỏe” cho từng test theo thời gian.

- **Bài toán chính:** flaky test làm CI mất độ tin cậy, gây rerun thủ công, tốn thời gian điều tra và dễ khiến team bỏ qua lỗi thật.
- **Quy mô:** Medium.
- **MVP ước tính:** 7–12 ngày làm việc part-time cho một developer.

## 2. Bài toán thực tế

### Confirmed facts

Playwright hỗ trợ retry và phân loại test thành `passed`, `flaky` và `failed`; một test được xem là flaky khi lần đầu fail nhưng retry sau đó pass. Playwright cũng có `failOnFlakyTests`, `repeatEach` và các tùy chọn retry để phục vụ phát hiện hoặc xử lý test không ổn định. [Playwright — Retries](https://playwright.dev/docs/test-retries) · [Playwright — TestConfig](https://playwright.dev/docs/api/class-testconfig)

GitHub Actions cho phép lấy workflow runs, jobs và workflow artifacts qua REST API. Artifact có thể chứa test results, failures, screenshots hoặc output khác được tạo trong CI. Điều này tạo nền tảng kỹ thuật đủ tốt để một công cụ bên ngoài thu thập dữ liệu lịch sử mà không cần scraping giao diện GitHub. [GitHub Docs — Workflow runs](https://docs.github.com/en/rest/actions/workflow-runs) · [GitHub Docs — Workflow jobs](https://docs.github.com/en/rest/actions/workflow-jobs) · [GitHub Docs — Workflow artifacts](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)

### Observation

CI thường chỉ cho thấy trạng thái của từng run. Khi một test fail ngắt quãng, developer phải tự nhớ hoặc tự tìm các run cũ để biết lỗi đó có phải lỗi mới, flaky lâu ngày, hay lỗi thật do regression.

### Assumption

Với team nhỏ hoặc project cá nhân có vài trăm E2E/integration tests, việc duy trì một dashboard chuyên biệt cho flakiness chưa đủ quan trọng để mua một nền tảng observability/testing lớn, nhưng đủ gây khó chịu để một công cụ self-hosted nhỏ tạo giá trị.

### Current workaround

Người dùng thường:

- rerun failed test hoặc rerun cả job;
- xem HTML report/traces của một lần chạy;
- search lịch sử Actions thủ công;
- thêm retry rồi quên quay lại sửa nguyên nhân;
- dùng spreadsheet hoặc issue tracker để ghi test hay fail;
- cuối cùng có nguy cơ “quen” với một nhóm test đỏ định kỳ.

Vấn đề là các cách trên **phân mảnh**, thiếu dữ liệu lịch sử chuẩn hóa và không trả lời nhanh các câu hỏi như:

- Test nào flaky nhiều nhất 30 ngày qua?
- Test nào mới bắt đầu flaky sau commit gần đây?
- Test nào fail 3 lần rồi pass khi retry?
- Test nào chỉ flaky trên Chromium hoặc chỉ trên CI?
- Test nào nên ưu tiên sửa trước?

## 3. Người dùng mục tiêu

### Primary user cho MVP

Developer hoặc QA automation engineer đang chạy Playwright trên GitHub Actions cho một repository nhỏ đến trung bình.

### Context of use

- Có CI chạy mỗi pull request hoặc mỗi ngày.
- Có retry hoặc rerun do test không ổn định.
- Có test report dạng JSON/JUnit hoặc artifact có thể parse.
- Không muốn đưa test telemetry sang dịch vụ SaaS bên thứ ba.

### Main pain point

Không có một nơi đơn giản để nhìn lịch sử flakiness theo test case.

### Current workaround

Mở từng workflow run, xem artifact/report, search bằng tên test và đoán mức độ nghiêm trọng.

### Lý do họ có thể thử công cụ này

Chỉ cần kết nối một repo, ingest vài chục run và ngay lập tức thấy danh sách “test hay fail nhất” là đã tạo giá trị mà không cần thay đổi kiến trúc test hiện tại.

## 4. Giải pháp đề xuất

FlakyTest Ledger hoạt động như một lớp phân tích lịch sử phía trên CI.

### Main workflow

1. Người dùng thêm GitHub repository.
2. Cấu hình workflow cần theo dõi và tên artifact chứa test result.
3. Hệ thống lấy các workflow run gần đây qua GitHub API.
4. Với mỗi run, hệ thống tải artifact test report.
5. Parser chuẩn hóa kết quả thành từng `TestExecution`.
6. Engine tính các chỉ số:
   - total executions;
   - first-attempt failures;
   - retry passes;
   - hard failures;
   - flaky rate;
   - consecutive flaky runs;
   - last flaky time.
7. Dashboard hiển thị ranking các test đáng xử lý.
8. Người dùng mở một test để xem timeline fail/pass, browser/project, error signature, commit SHA và link ngược về GitHub run.

### Input

- GitHub repository.
- Workflow name hoặc workflow ID.
- Artifact chứa JSON/JUnit test result.
- Optional: branch filter.

### Processing

- Fetch metadata từ GitHub Actions API.
- Parse test result.
- Chuẩn hóa test identity.
- Deduplicate run.
- Tính flakiness score bằng deterministic rules.

### Output

- Dashboard theo test.
- Flaky ranking.
- Timeline theo run.
- Error signature phổ biến.
- Link về source CI run/artifact.

### Automated

- Periodic sync.
- Parsing.
- Scoring.
- Detect new flaky tests.

### User control

- Repo/workflow nào được theo dõi.
- Ngưỡng flaky rate.
- Test nào bị mute/ignore có lý do.
- Thời gian retention.

### Key differentiator

Không phải “test dashboard” chung. Công cụ chỉ tập trung vào **lịch sử độ ổn định của từng test** và giúp trả lời “test nào đang làm CI mất niềm tin?”.

### Ví dụ end-to-end

Một project có test `Employee can submit leave request`.

Trong 20 lần chạy gần nhất:

- 16 lần pass ngay;
- 3 lần fail lần đầu nhưng retry pass;
- 1 lần fail toàn bộ retries.

Dashboard tính flaky rate riêng cho first-attempt failure, đánh dấu test “High attention”, hiển thị 3 error signatures đều liên quan đến timeout locator. Developer mở timeline, thấy lỗi chỉ xuất hiện trên Chromium CI và có thể tập trung sửa synchronization thay vì tiếp tục rerun ngẫu nhiên.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

- Giảm thời gian search lịch sử CI thủ công.
- Tách flaky failure khỏi regression thật rõ hơn.
- Tạo backlog sửa flaky test dựa trên dữ liệu.
- Giúp đo xem việc sửa test có thực sự cải thiện độ ổn định.

### Technical learning value

Dự án có nhiều bài toán thực tế nhưng vừa sức:

- GitHub REST API;
- artifact ingestion;
- background synchronization;
- idempotency;
- parsing test report;
- time-series aggregation;
- deterministic scoring;
- observability cho chính monitoring tool.

### Tại sao phù hợp solo developer

MVP có thể giới hạn cực hẹp:

- chỉ GitHub Actions;
- chỉ Playwright JSON reporter;
- chỉ một repo;
- chỉ dashboard read-only;
- không cần AI;
- không cần distributed architecture.

### Vẫn hữu ích khi chỉ có một user

Nếu developer tự chạy hàng trăm Playwright tests trong project cá nhân hoặc công việc, dashboard vẫn tiết kiệm thời gian và cung cấp lịch sử mà GitHub UI không tối ưu cho mục đích này.

### Điều gì khiến ý tưởng thất bại

- Parser không ổn định khi format test report thay đổi.
- Test identity không nhất quán khiến cùng một test bị tách thành nhiều bản ghi.
- Người dùng có quá ít test hoặc CI hiếm khi chạy, khiến dữ liệu không đủ giá trị.
- Dashboard chỉ đẹp nhưng không giúp quyết định test nào cần sửa.

### Strongest reason not to build

Nếu workflow hiện tại chỉ có vài chục test rất ổn định và CI hiếm khi flaky, project này sẽ trở thành infrastructure thừa.

## 6. Phạm vi MVP

### Must have

- Connect một GitHub repository bằng fine-grained token.
- Chọn workflow cần theo dõi.
- Fetch 30–100 workflow runs gần nhất.
- Download một artifact chứa Playwright JSON report.
- Parse test name, project/browser, status, retry, duration, error text.
- Idempotent import theo workflow run + test execution.
- Tính:
  - total runs;
  - first-attempt failure count;
  - flaky count;
  - hard failure count;
  - flaky rate;
  - last seen.
- Dashboard ranking flaky tests.
- Test detail timeline.
- Manual sync button.

### Should have

- Scheduled sync mỗi 15–60 phút.
- Filter theo branch/browser/project.
- Error signature grouping.
- Ignore/mute test với reason và expiry date.
- Deep link về GitHub Actions run.
- Simple trend 7/30 ngày.

### Later

- JUnit XML support.
- Azure DevOps/GitLab CI.
- PR comment.
- Slack/Telegram notification.
- Auto-create GitHub issue.
- Correlate flakiness với code ownership.
- Compare before/after một fix commit.
- Cross-repository dashboard.

## 7. Luồng hoạt động

### Happy path

User connects GitHub repo
→ backend validates token/repository access
→ user selects workflow + artifact pattern
→ sync worker fetches workflow runs
→ unseen runs được queued logically trong DB
→ worker fetches artifact metadata
→ downloads report
→ parser extracts test executions
→ normalized records stored
→ scoring service recomputes metrics
→ dashboard displays ranked flaky tests
→ user opens test timeline.

### Alternative flow — artifact chưa tồn tại

Run đã hoàn thành nhưng không có matching artifact:

- mark `NoArtifact`;
- không coi là system error;
- dashboard hiển thị coverage gap;
- sync sau có thể thử lại nếu run còn mới.

### Alternative flow — report parse fail

- lưu import status `ParseFailed`;
- giữ error message và artifact metadata;
- không insert partial execution trừ khi parser support transactional import;
- cho phép retry sau khi parser được sửa.

### Alternative flow — GitHub API rate limit hoặc network error

- exponential backoff;
- giữ cursor/last successful run;
- không reset toàn bộ sync;
- manual retry được phép.

### Failure safety

Mỗi workflow run có unique constraint nên retry sync không tạo duplicate.

## 8. Kiến trúc đề xuất

### Tổng thể

**Modular monolith** là đủ cho MVP.

```text
Vue UI
   ↓
ASP.NET Core API
   ├── GitHub Integration Module
   ├── Test Report Import Module
   ├── Flakiness Analysis Module
   └── Dashboard Module
          ↓
      PostgreSQL
          ↑
BackgroundService Sync Worker
```

### Frontend

Vue 3 SPA.

Lý do:

- dashboard/filter/timeline phù hợp SPA;
- dễ tận dụng kinh nghiệm Vue;
- frontend không cần SSR.

### Backend

ASP.NET Core modular monolith.

Một process chứa:

- API;
- sync orchestration;
- parser;
- aggregation.

Không cần microservice.

### Database

PostgreSQL.

Lưu:

- repository config;
- workflow run metadata;
- executions;
- aggregate metrics;
- sync status.

### Background worker

`BackgroundService` là đủ cho MVP.

Không cần Hangfire ngay vì:

- chỉ có vài scheduled sync;
- job model đơn giản;
- có thể lưu checkpoint trực tiếp trong DB.

Nếu sau này có nhiều repo/job/retry UI, Hangfire hoặc Quartz.NET mới đáng cân nhắc.

### Queue

Không cần external queue.

DB-backed sync state đủ cho một instance.

### Cache

Không cần cho MVP.

Dashboard query có thể aggregate trực tiếp hoặc dùng materialized summary table.

### File storage

MVP không cần giữ artifact gốc lâu dài.

Có thể:

- download vào temp storage;
- parse;
- giữ normalized fields;
- xóa file sau import.

Trace/screenshot chỉ lưu URL/reference ở phase sau.

### Authentication

MVP personal-use có thể dùng local account hoặc single-user config.

Nếu public deployment:

- ASP.NET Core Identity;
- encrypt GitHub token at rest.

### External API

GitHub REST API là integration chính.

### AI model

Không cần.

### Notification

Không cần trong MVP.

### Logging

Structured logs qua `ILogger` + console.

Later thêm OpenTelemetry nếu cần.

### Deployment

Docker Compose:

- app;
- PostgreSQL.

Chạy được trên VPS, mini PC hoặc Azure Container Apps/App Service tùy nhu cầu.

## 9. Công nghệ đề xuất

### .NET 10 LTS

Tại ngày 17/08/2026, .NET 10 đang ở trạng thái Active LTS và Microsoft công bố end of support vào 14/11/2028. [Microsoft .NET Support Policy](https://dotnet.microsoft.com/en-us/platform/support/policy)

**Why:** phù hợp project mới, thời gian support dài, tận dụng ASP.NET Core/EF Core.

**Simpler alternative:** .NET 8 nếu môi trường hiện hữu bắt buộc, nhưng với project greenfield không có lý do lớn để bắt đầu thấp hơn .NET 10.

**Outgrow:** không phải vấn đề scale; chỉ nâng major version theo lifecycle.

### ASP.NET Core Minimal API hoặc Controllers

**Why:** REST API đơn giản, integration/background worker trong cùng host.

**Simpler:** Minimal API cho MVP.

**Outgrow:** chuyển sang Controllers/module conventions khi endpoint nhiều hơn.

### Entity Framework Core + PostgreSQL

**Why:** dữ liệu relational và query aggregate rõ ràng.

**Simpler:** SQLite cho local-only prototype.

**Outgrow:** PostgreSQL vẫn đủ lâu; chỉ cần tối ưu index/partition nếu executions lên hàng chục triệu bản ghi.

### Vue 3 + Vite

**Why:** dashboard tương tác, filter nhanh, stack quen thuộc.

**Simpler:** Razor Pages nếu muốn giảm một project frontend.

**Outgrow:** không dễ outgrow ở scale này.

### BackgroundService

**Why:** sync định kỳ đơn giản.

**Simpler:** command `dotnet run -- sync` chạy thủ công cho phase đầu.

**Outgrow:** dùng Hangfire/Quartz khi cần nhiều jobs, retry UI, scheduling phức tạp.

### Docker Compose

**Why:** deploy app + DB nhất quán.

**Simpler:** chạy local `dotnet run` + local PostgreSQL.

**Outgrow:** Azure Container Apps hoặc managed hosting khi cần high availability.

### Playwright

Dùng Playwright để E2E test chính dashboard và luồng configuration. Ironically, project theo dõi flaky tests cũng nên tự có test suite ổn định.

### GitHub Actions

Dùng build/test/publish image.

Không cần self-hosted runner trong MVP.

## 10. Thiết kế dữ liệu ban đầu

### `TrackedRepository`

**Purpose:** repo được theo dõi.

Fields:

- `Id`
- `Owner`
- `Name`
- `DefaultBranch`
- `WorkflowId`
- `ArtifactPattern`
- `Enabled`
- `LastSyncAt`

Relations:

- 1 → many `WorkflowRunRecord`.

Retention:

- giữ lâu dài cho đến khi user xóa repo.

### `WorkflowRunRecord`

**Purpose:** checkpoint và metadata của một Actions run.

Fields:

- `Id`
- `TrackedRepositoryId`
- `ExternalRunId`
- `HeadSha`
- `Branch`
- `Conclusion`
- `StartedAt`
- `CompletedAt`
- `ImportStatus`
- `ImportedAt`

Unique:

- `(TrackedRepositoryId, ExternalRunId)`.

Retention:

- MVP giữ 90 ngày mặc định.

### `TestCase`

**Purpose:** canonical identity của một test.

Fields:

- `Id`
- `StableKey`
- `FilePath`
- `TitlePath`
- `ProjectName`
- `FirstSeenAt`
- `LastSeenAt`

`StableKey` có thể hash từ normalized `file + titlePath + project`.

### `TestExecution`

**Purpose:** một attempt của một test trong một run.

Fields:

- `Id`
- `WorkflowRunRecordId`
- `TestCaseId`
- `RetryIndex`
- `Status`
- `DurationMs`
- `ErrorSignature`
- `ErrorExcerpt`

Relations:

- many executions → one test;
- many executions → one run.

Retention:

- 90–180 ngày configurable.

### `TestHealthSnapshot`

**Purpose:** aggregate nhanh cho dashboard.

Fields:

- `TestCaseId`
- `WindowDays`
- `ExecutionCount`
- `FirstAttemptFailures`
- `FlakyRuns`
- `HardFailures`
- `FlakyRate`
- `LastFlakyAt`
- `Score`

Có thể recompute sau mỗi import thay vì dùng event streaming.

### `IgnoredTestRule`

**Purpose:** user tạm mute một test.

Fields:

- `TestCaseId`
- `Reason`
- `ExpiresAt`
- `CreatedAt`

## 11. API và tích hợp

### GitHub Actions REST API

**Purpose:** lấy workflow runs/jobs/artifacts.

Confirmed capabilities:

- GitHub REST API có endpoint list workflow runs.
- Có endpoint list jobs cho workflow run.
- Có endpoint list/download artifact.
- Fine-grained token với Actions read permission có thể dùng cho private repo phù hợp quyền truy cập. [GitHub Docs — Workflow jobs](https://docs.github.com/en/rest/actions/workflow-jobs) · [GitHub Docs — Artifacts](https://docs.github.com/en/rest/actions/artifacts)

**Authentication:** fine-grained personal access token hoặc GitHub App later.

**Cost:** GitHub API bản thân không yêu cầu trả tiền per request; cần quan tâm rate limits của token/account và GitHub plan hiện tại.

**Privacy:** token là secret quan trọng; chỉ xin quyền read tối thiểu.

**Fallback:** manual upload test result file để parser/dashboard vẫn hoạt động nếu API unavailable.

### Playwright JSON reporter

**Purpose:** nguồn dữ liệu test execution có retry/status/error.

**Authentication:** không cần.

**Cost:** không.

**Privacy:** test report có thể chứa URL/error text nhạy cảm; cần retention và redaction option.

**Fallback:** JUnit XML parser sau MVP.

### GitHub workflow artifacts

Artifact phù hợp để giữ test output sau job hoàn thành; GitHub docs liệt kê test results, failures và screenshots là các ví dụ artifact điển hình. [GitHub Docs — Workflow artifacts](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem hoàn toàn deterministic:

- parse report;
- count pass/fail/retry;
- group history;
- calculate flakiness score;
- rank tests.

Không nên đưa LLM vào MVP vì:

- error grouping có thể bắt đầu bằng normalized exception/message hash;
- scoring phải giải thích được;
- AI làm tăng cost, latency và privacy risk;
- hallucination không phù hợp khi phân loại quality signal.

Later AI có thể là optional feature để tóm tắt nhiều error logs thành “suspected cause”, nhưng kết quả phải được gắn nhãn suggestion và không ảnh hưởng score chính.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác nhận dữ liệu lịch sử thực sự hữu ích.

**Tasks:**

- Lấy 20–50 Playwright reports từ một repo thực tế.
- Viết script nhỏ parse test name/status/retry.
- Xuất CSV ranking flaky tests.
- Kiểm tra xem top 5 có khớp với cảm nhận thực tế của developer hay không.

**Expected output:** một bảng top flaky tests từ dữ liệu thật.

**Completion criteria:** ít nhất một test được phát hiện là thường xuyên flaky mà việc nhìn từng CI run khó nhận ra.

### Phase 1 — Core MVP

**Goal:** end-to-end từ GitHub → DB → dashboard.

**Tasks:**

- tạo ASP.NET Core API;
- GitHub client;
- report parser;
- entities + EF Core;
- sync command;
- dashboard ranking;
- test detail timeline.

**Expected output:** connect một repo và import history thành dashboard.

**Completion criteria:** chạy sync hai lần không duplicate dữ liệu và dashboard hiển thị cùng kết quả.

### Phase 2 — Reliability

**Goal:** sync đáng tin cậy.

**Tasks:**

- retry/backoff;
- transactional import;
- unique constraints;
- parser error handling;
- token encryption;
- structured logging;
- integration tests;
- test identity normalization.

**Expected output:** service có thể chạy vài ngày liên tục không cần sửa DB thủ công.

**Completion criteria:** network/API/parser failure không làm mất checkpoint hoặc duplicate execution.

### Phase 3 — Useful expansion

**Goal:** biến dữ liệu thành action.

**Tasks:**

- 7/30-day trend;
- error signature grouping;
- filter by browser/branch;
- mute with expiry;
- new-flaky notification;
- compare pre/post fix.

**Expected output:** dashboard hỗ trợ quyết định test nào sửa trước.

**Completion criteria:** user có thể tạo một backlog sửa flaky tests chỉ từ dashboard.

### Phase 4 — Production readiness

**Goal:** deploy self-hosted ổn định.

**Tasks:**

- Docker Compose;
- backup DB;
- retention job;
- health check;
- metrics;
- setup docs;
- secret handling;
- GitHub Actions CI/CD.

**Expected output:** một VPS/mini PC instance có thể tự chạy.

**Completion criteria:** restart/deploy không mất dữ liệu và có documented recovery path.

## 14. Các bài toán kỹ thuật đáng học

### 1. Stable test identity

Tên test có thể thay đổi hoặc được parameterize.

Cần thiết kế canonical key từ:

- file path;
- suite/title hierarchy;
- project/browser.

**Skill cải thiện:** data normalization và identity design.

### 2. Idempotent CI ingestion

Cùng một run có thể được sync nhiều lần.

Cần:

- external IDs;
- unique constraints;
- transactional import;
- safe retry.

**Skill cải thiện:** reliable integration processing.

### 3. Flakiness scoring

Một test có 1 flaky event trong 2 runs khác hẳn 1 event trong 100 runs.

Score nên xét:

- sample size;
- recent rate;
- hard failure rate;
- consecutive unstable runs;
- recency.

**Skill cải thiện:** practical metrics/statistical reasoning mà không cần ML.

### 4. Rate limit và incremental sync

Không nên fetch toàn bộ history mỗi lần.

Cần checkpoint và chỉ lấy runs mới.

**Skill cải thiện:** API synchronization và cost-aware polling.

### 5. Error signature normalization

Timeout messages thường chứa dynamic values.

Có thể normalize:

- timestamps;
- IDs;
- URLs;
- line numbers;
- numeric durations.

Sau đó hash normalized message.

**Skill cải thiện:** log processing và deterministic clustering.

## 15. Rủi ro và cách xử lý

### Risk: scope bùng nổ thành full test management platform

**Mitigation:** MVP chỉ trả lời một câu hỏi: “test nào flaky nhất và bằng chứng là gì?”. Không test case management, không manual QA, không requirement tracking.

### Risk: test report chứa dữ liệu nhạy cảm

**Mitigation:**

- giữ excerpt ngắn;
- optional regex redaction;
- không lưu raw artifact sau parse;
- configurable retention;
- encrypt secrets.

### Risk: GitHub API dependency

**Mitigation:** abstract integration và có manual-upload fallback.

### Risk: rate limits

**Mitigation:** incremental sync, ETag/cache metadata khi phù hợp, không poll quá thường xuyên.

### Risk: false flaky classification

Ví dụ test retry pass vì backend test environment vừa hồi phục, không phải lỗi test code.

**Mitigation:** gọi metric là “observed flakiness”, giữ raw evidence và environment dimensions; không tự khẳng định root cause.

### Risk: maintenance burden

Report format có thể thay đổi.

**Mitigation:** parser contract tests với fixture versions và adapter interface.

### Risk: user adoption thấp

**Mitigation:** validation bằng CLI/CSV trước khi xây dashboard đầy đủ.

- interrupted import;

### Security tests

- token không xuất hiện trong logs;
- unauthorized user không xem repo config;
- redact secret-like values trong error excerpt.

### 5 test scenarios quan trọng nhất

1. Một test fail attempt 0 nhưng pass retry 1 → phải tính là flaky, không phải hard failure.
2. Một test fail tất cả retries → hard failure, không được tính giống retry-pass.
3. Sync cùng run hai lần → execution count không tăng.
4. Artifact malformed → run chuyển `ParseFailed`, dữ liệu cũ vẫn nguyên vẹn.
5. GitHub API trả 429 → worker backoff và resume từ checkpoint sau đó.

## 17. Cách đo dự án có hữu ích hay không

### Product usage metric

- số CI runs được sync mỗi tuần;
- số lần người dùng mở test detail từ flaky ranking.

### Time saved

Đo một tác vụ cụ thể:

> Tìm top 5 test flaky nhất trong 30 ngày.

So sánh thời gian làm thủ công trên GitHub Actions với FlakyTest Ledger.

### Task completion rate

Tỷ lệ sync runs thành công có usable test data.

Target ban đầu: >95% với supported report format.

### Error rate

- parse failure rate;
- duplicate import count;
- API sync failure rate.

### Repeated use

Một tín hiệu tốt hơn page views là user quay lại dashboard ít nhất hàng tuần để kiểm tra test health.

### Reliability

- không duplicate data;
- sync delay nằm trong configured interval;
- recovery sau restart không cần thao tác thủ công.

### Outcome metric

Theo dõi số test có flaky rate giảm sau khi được đánh dấu “fixed”. Đây là metric hữu ích hơn số chart/dashboard views.

## 20. Việc cần làm ngay hôm nay

### Thời lượng

90–120 phút.

### Development objective

Tạo vertical slice nhỏ nhất chứng minh core idea:

> Đọc một Playwright JSON report và xuất top flaky tests ra HTTP endpoint.

Chưa kết nối GitHub API, chưa cần database thật.

### Files/components cần tạo

```text
FlakyTestLedger/
├── src/
│   └── FlakyTestLedger.Api/
│       ├── Program.cs
│       ├── Models/
│       │   ├── TestExecution.cs
│       │   └── TestHealth.cs
│       ├── Services/
│       │   ├── PlaywrightReportParser.cs
│       │   └── FlakinessCalculator.cs
│       └── fixtures/
│           └── sample-report.json
└── tests/
    └── FlakyTestLedger.Tests/
        └── FlakinessCalculatorTests.cs
```

### Setup commands

```bash
dotnet new sln -n FlakyTestLedger

dotnet new webapi -n FlakyTestLedger.Api -o src/FlakyTestLedger.Api --framework net10.0

dotnet new xunit -n FlakyTestLedger.Tests -o tests/FlakyTestLedger.Tests --framework net10.0

dotnet sln add src/FlakyTestLedger.Api/FlakyTestLedger.Api.csproj
dotnet sln add tests/FlakyTestLedger.Tests/FlakyTestLedger.Tests.csproj

dotnet add tests/FlakyTestLedger.Tests/FlakyTestLedger.Tests.csproj reference src/FlakyTestLedger.Api/FlakyTestLedger.Api.csproj
```

### First vertical slice

Tự tạo fixture với ba test:

- Test A: pass ngay 10 lần.
- Test B: fail attempt 0 và pass attempt 1 trong 3/10 runs.
- Test C: hard fail 2/10 runs.

Implement `FlakinessCalculator` để output:

```json
[
  {
    "test": "Test B",
    "runs": 10,
    "flakyRuns": 3,
    "hardFailures": 0,
    "flakyRate": 0.30
  }
]
```

Expose endpoint:

```http
GET /api/tests/flaky
```

Sort descending theo `flakyRate`.

### Expected result

Chạy:

```bash
dotnet test
dotnet run --project src/FlakyTestLedger.Api
```

Mở:

```text
http://localhost:xxxx/api/tests/flaky
```

và nhận được ranking test từ fixture.

### Verification checklist

- [ ] Test fail rồi retry pass được tính là flaky.
- [ ] Hard failure được tách khỏi flaky retry-pass.
- [ ] Test pass toàn bộ có flaky rate = 0.
- [ ] API sort đúng test flaky nhất lên đầu.
- [ ] Unit tests pass.
- [ ] Không có GitHub token, database hoặc frontend nào bị thêm sớm.

### Stop condition

Dừng session ngay khi endpoint trả đúng ranking từ fixture và unit test xác nhận classification logic. Không bắt đầu GitHub OAuth, Vue dashboard, Hangfire hay Docker trong buổi đầu.
