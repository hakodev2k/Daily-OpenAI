# Ý tưởng hôm nay: Personal API Change Impact Analyzer

## 1. Tóm tắt ý tưởng

Một công cụ dành cho developer giúp phân tích ảnh hưởng của thay đổi API trước khi merge hoặc deploy. Người dùng cung cấp OpenAPI specification cũ và mới, hệ thống phát hiện breaking changes, tạo báo cáo mức độ ảnh hưởng và gợi ý nơi cần cập nhật.

Quy mô: Medium. MVP dự kiến 2–4 tuần.

## 2. Bài toán thực tế

Khi backend thay đổi REST API, developer thường phải tự kiểm tra controller, client, mobile app, integration và tài liệu liên quan. Với hệ thống có nhiều service, việc bỏ sót breaking change có thể gây lỗi production.

Giả định phổ biến: nhiều team hiện dùng review thủ công, diff Swagger hoặc kiểm thử sau khi deploy. Cách này tốn thời gian và phụ thuộc kinh nghiệm cá nhân.

## 3. Người dùng mục tiêu

Primary user: Backend developer và technical lead.

Họ cần biết nhanh:
- API nào bị ảnh hưởng.
- Client nào có thể bị lỗi.
- Thay đổi có an toàn để release không.

Workaround hiện tại là review code thủ công, chạy test hoặc kiểm tra Swagger bằng tay.

## 4. Giải pháp đề xuất

Workflow:

1. Developer upload OpenAPI JSON/YAML phiên bản cũ và mới.
2. Hệ thống so sánh endpoint, schema, parameter, response.
3. Sinh báo cáo:
   - Breaking change.
   - Non-breaking change.
   - Risk level.
   - Recommendation.

Ví dụ: API đổi field `customerId` thành `id` trong response. Tool cảnh báo mobile client có thể bị lỗi mapping.

Điểm khác biệt: tập trung vào developer cá nhân và team nhỏ, chạy local/self-hosted thay vì phụ thuộc SaaS.

## 5. Tại sao ý tưởng này đáng làm

Giá trị thực tế:
- Giảm lỗi do thay đổi API.
- Tạo công cụ dùng được ngay trong dự án cá nhân.

Giá trị kỹ thuật:
- Học API contract testing.
- Học static analysis.
- Học CI/CD integration.

Phù hợp solo developer vì MVP chỉ cần một parser, engine so sánh và web UI đơn giản.

Lý do không nên làm: thị trường có nhiều API testing tools lớn; cần khác biệt bằng trải nghiệm đơn giản và developer workflow.

## 6. Phạm vi MVP

### Must have
- Upload OpenAPI files.
- Compare endpoints.
- Detect breaking changes cơ bản.
- Export Markdown report.

### Should have
- GitHub Action integration.
- Comment kết quả vào Pull Request.
- Rule configuration.

### Later
- AI explanation.
- Multi-service dependency graph.
- Team dashboard.

## 7. Luồng hoạt động

Upload spec
→ validate schema
→ parse API model
→ compare version
→ calculate risk
→ store result
→ show report
→ optional notification

Failure cases:
- OpenAPI invalid.
- Missing schema reference.
- Unsupported API format.

## 8. Kiến trúc đề xuất

Modular monolith:

- Frontend: Vue.
- Backend: ASP.NET Core Web API.
- Database: PostgreSQL.
- Worker: BackgroundService cho phân tích lớn.
- Storage: local file hoặc Azure Blob khi cần.
- Authentication: đơn giản bằng local account hoặc GitHub OAuth.
- Logging: Serilog.

Không cần queue hoặc microservice ở MVP.

## 9. Công nghệ đề xuất

- .NET 10 / ASP.NET Core: phù hợp với backend parsing và API.
- EF Core + PostgreSQL: lưu project, scan history.
- Vue: UI nhanh cho dashboard.
- Docker: dễ chạy local.
- GitHub Actions: tích hợp CI.

Alternative: CLI .NET tool nếu chỉ muốn developer workflow.

## 12. AI có thực sự cần thiết không?

AI hữu ích nhưng không bắt buộc.

Có thể dùng AI để giải thích:
- Vì sao change nguy hiểm.
- Cách migrate client.

Input: API diff.
Output: structured recommendation.

Fallback: rule engine truyền thống.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

Test với 10–20 API changes từ project thật.

Output: danh sách rule cần hỗ trợ.

### Phase 1 — Core MVP

Xây parser, comparer, report generator.

Hoàn thành khi có thể detect breaking change từ hai file Swagger.

### Phase 2 — Reliability

Thêm test, validation, logging.

### Phase 3 — Useful expansion

Thêm GitHub Action và PR integration.

### Phase 4 — Production readiness

Deploy Docker, backup, documentation.

## 14. Các bài toán kỹ thuật đáng học

1. API contract comparison — học static analysis.
2. Schema diffing — xử lý cấu trúc dữ liệu phức tạp.
3. CI integration — học developer tooling.
4. Rule engine design — học extensibility.

## 15. Rủi ro và cách xử lý

- Quá nhiều API format: bắt đầu với OpenAPI 3.x.
- False positive: cho phép ignore rule.
- Scope lớn: chỉ hỗ trợ REST API trước.
- Khó kiếm user: dùng chính dự án cá nhân để validate.

## 16. Kiểm thử

Năm scenario quan trọng:

1. Remove endpoint.
2. Change required field.
3. Add optional field.
4. Change response type.
5. Invalid OpenAPI document.

Dùng unit test cho rule engine và integration test cho API.

## 20. Việc cần làm ngay hôm nay

Mục tiêu 90 phút: tạo bản CLI đầu tiên có thể so sánh hai OpenAPI file.

Tasks:

1. Tạo solution:
```bash
dotnet new sln -n ApiImpactAnalyzer
dotnet new console -n ApiImpactAnalyzer.Cli
```

2. Cài thư viện OpenAPI parser.

3. Tạo:
- OpenApiLoader.cs
- ApiComparer.cs
- BreakingChangeRule.cs
- MarkdownReporter.cs

4. Chuẩn bị hai file swagger.json mẫu.

Kết quả mong đợi:
CLI chạy được:

```bash
dotnet run old.json new.json
```

và xuất ra report Markdown có danh sách thay đổi.

Stop condition: Không xây UI, authentication hoặc database trước khi engine phân tích hoạt động ổn định.
