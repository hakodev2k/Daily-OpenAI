# Ý tưởng hôm nay: MigrationSentry — EF Core Migration Dry-Run & Lock-Risk Analyzer

## 1. Tóm tắt ý tưởng

**MigrationSentry** là một developer tool chạy local/CI giúp developer lấy các EF Core migrations sắp deploy, áp chúng lên một PostgreSQL database disposable có schema gần production, đo thời gian thực thi, quan sát lock, phát hiện thao tác dễ gây downtime và tạo một report “deploy risk” trước khi migration chạm production. Tool tập trung vào một vấn đề rất cụ thể: migration chạy tốt trên database nhỏ ở local nhưng có thể lock bảng lớn, scan dữ liệu lâu hoặc thất bại khi deploy thật.

- Người dùng chính: .NET backend developer dùng EF Core + PostgreSQL.
- Bài toán chính: database migration có rủi ro performance/locking nhưng thường chỉ được review bằng code hoặc SQL tĩnh.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

EF Core migrations giúp cập nhật schema theo model và Microsoft hỗ trợ cả SQL scripts lẫn migration bundles để deploy. Microsoft cũng cảnh báo việc apply migration có thể dẫn tới data-loss scenarios và khuyến nghị kiểm soát quá trình deploy thay vì để production app tự migrate một cách thiếu kiểm soát. Migration bundles có thể được tạo trong CI và chạy sau đó như executable độc lập. Nguồn: [Applying Migrations — EF Core](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/applying), [EF Core CLI reference](https://learn.microsoft.com/en-us/ef/core/cli/dotnet).

Ở phía PostgreSQL, nhiều dạng `ALTER TABLE` mặc định cần `ACCESS EXCLUSIVE` lock nếu tài liệu không nói khác. `ACCESS EXCLUSIVE` xung đột với tất cả lock modes khác; do đó một migration tưởng như đơn giản có thể chặn cả đọc lẫn ghi trong thời gian lock được giữ. PostgreSQL cũng document rằng một số constraint có thể dùng `NOT VALID` rồi `VALIDATE CONSTRAINT` để tránh scan dài ở bước đầu và giảm mức lock khi validation. Nguồn: [PostgreSQL ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html), [PostgreSQL Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html).

### Vấn đề thực tế

Developer thường review migration bằng một trong các cách:

- đọc file migration C#;
- generate SQL script;
- chạy trên local database nhỏ;
- test trên staging có dữ liệu ít hơn production;
- deploy rồi theo dõi log.

Các cách này dễ bỏ sót:

- `ALTER TABLE` giữ lock quá lâu;
- thêm constraint buộc full-table scan;
- đổi column type dẫn tới table rewrite;
- index creation block write;
- migration có data backfill quá lớn;
- timeout chỉ xảy ra khi bảng có hàng triệu rows;
- hai migrations riêng lẻ an toàn nhưng chạy chung lại giữ transaction quá lâu.

### Confirmed facts

- EF Core có thể generate migration bundle bằng `dotnet ef migrations bundle` và bundle tương đương việc update database tới target migration. [Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/applying)
- PostgreSQL `ALTER TABLE` có lock level khác nhau theo subcommand; nếu không được ghi chú riêng, `ACCESS EXCLUSIVE` là mặc định. [PostgreSQL docs](https://www.postgresql.org/docs/current/sql-altertable.html)
- `ACCESS EXCLUSIVE` xung đột với mọi lock mode khác. [PostgreSQL locking docs](https://www.postgresql.org/docs/current/explicit-locking.html)
- Testcontainers for .NET có module PostgreSQL và có thể khởi động database container trực tiếp từ test/tooling code. [Testcontainers PostgreSQL module](https://dotnet.testcontainers.org/modules/postgres/)

### Observation

Các primitive để generate/apply migration và chạy disposable PostgreSQL đã tồn tại. Khoảng trống phù hợp cho một solo project là **orchestrate chúng thành migration rehearsal workflow có measurement + risk rules + reproducible report**, thay vì viết một migration engine mới.

### Assumption cần validate

Tool chỉ đáng làm nếu developer có bảng đủ lớn hoặc deployment đủ nhạy cảm để migration downtime thực sự là vấn đề. Với project nhỏ có vài nghìn rows, review migration thủ công có thể đã đủ.

## 3. Người dùng mục tiêu

### Primary user

.NET backend developer dùng EF Core với PostgreSQL và có CI/CD cho staging/production.

### Context sử dụng

Trước merge hoặc trước release, developer có một hoặc nhiều pending migrations và muốn biết:

- migration cần bao lâu trên dataset realistic;
- lock nào xuất hiện;
- có operation nguy hiểm nào không;
- migration có làm request giả lập bị block không;
- có cần đổi migration strategy trước deploy không.

### Main pain point

Migration review hiện thiên về static review trong khi rủi ro thật phụ thuộc vào data volume, table shape, query workload và lock interaction.

### Current workaround

- generate SQL rồi đọc bằng tay;
- restore bản backup staging;
- chạy migration thủ công;
- mở `pg_stat_activity`/`pg_locks` bằng query tay;
- dùng maintenance window để giảm rủi ro.

### Vì sao user thử MigrationSentry

Vì tool biến quy trình “tôi nghĩ migration này ổn” thành một report reproducible:

```text
Migration: AddCustomerStatusIndex
Elapsed: 18.4s
Max blocked request time: 4.8s
Lock: ShareLock / AccessExclusiveLock observed
Table rows: 4,120,381
Risk: HIGH
Reason: blocking > 2s threshold
```

## 4. Giải pháp đề xuất

### Main workflow

```text
Select project / migration range
→ generate migration SQL or bundle
→ start disposable PostgreSQL
→ restore schema/sample dataset
→ start workload probes
→ apply migration
→ observe pg_locks + pg_stat_activity
→ capture timings/errors
→ evaluate deterministic risk rules
→ generate Markdown/JSON report
→ fail/pass CI based on threshold
```

### Input

- path tới .NET project;
- DbContext name;
- migration range;
- PostgreSQL version;
- seed SQL / pg_dump / synthetic data generator;
- optional workload probes;
- risk thresholds.

### Processing

MigrationSentry sẽ:

1. dựng PostgreSQL container;
2. tạo baseline schema;
3. nạp sample dataset;
4. khởi động các probe query lặp lại;
5. apply migration bằng generated SQL hoặc migration bundle;
6. poll `pg_locks` và `pg_stat_activity`;
7. ghi elapsed time, blocked queries, failed probes;
8. detect SQL patterns có rủi ro;
9. sinh report.

### Output

Ví dụ:

```text
MigrationSentry Report

Target: PostgreSQL 18
Rows in Orders: 3,800,000
Migration duration: 42.6s

Findings
[HIGH] Orders ALTER COLUMN observed ACCESS EXCLUSIVE lock for 38.2s
[HIGH] SELECT probe blocked for 37.9s
[MEDIUM] Migration transaction duration > 30s
[INFO] Index created successfully

Verdict: BLOCK RELEASE
```

### Tự động hóa

- container lifecycle;
- migration execution;
- lock sampling;
- workload probe;
- risk rules;
- report generation;
- CI exit code.

### User vẫn kiểm soát

- dataset representative tới mức nào;
- probe query nào quan trọng;
- threshold bao nhiêu;
- migration strategy có thay đổi hay không;
- có cho release tiếp tục hay không.

### Key differentiator

**Dynamic rehearsal**, không chỉ SQL linting.

Một SQL statement nhìn “nguy hiểm” nhưng chạy 50 ms trên table thật có thể chấp nhận được. Ngược lại, một migration trông vô hại có thể block workload 20 giây trên vài triệu rows. Tool đo hành vi thực trong disposable environment.

### Ví dụ end-to-end

Developer tạo migration thêm foreign key cho bảng `TimesheetEntries` có vài triệu rows.

MigrationSentry dựng PostgreSQL container, restore schema và dataset representative khoảng 2 triệu rows, rồi chạy probe `SELECT`, `INSERT`, `UPDATE` mỗi 200 ms.

Khi migration chạy, tool thấy constraint creation giữ lock trong 23 giây và `INSERT` bị block gần toàn bộ thời gian. Report đánh `HIGH`.

Developer đổi migration thành flow `ADD CONSTRAINT ... NOT VALID` rồi một migration sau dùng `VALIDATE CONSTRAINT`. Chạy lại rehearsal cho thấy bước đầu nhanh hơn đáng kể và validation dùng mức lock ít disruptive hơn theo behavior quan sát được. Developer có evidence để review PR.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Một migration lỗi hoặc lock production có thể gây incident dù application code không thay đổi nhiều. Tool này dùng được ngay trên chính project của developer.

### Technical learning value

Dự án giúp học sâu:

- EF Core migrations internals;
- PostgreSQL locking;
- `pg_stat_activity`/`pg_locks`;
- Testcontainers;
- long-running orchestration;
- workload simulation;
- CI quality gates;
- database performance testing.

### Phù hợp solo developer

MVP chỉ support:

- EF Core;
- PostgreSQL;
- one DbContext;
- local/CI execution;
- Markdown report.

Không cần web app, cloud backend hoặc multi-user SaaS.

### Có giá trị khi chỉ một user

Nó có thể sống như CLI trong vài repositories và chạy ở CI trước release.

### Điều khiến project thất bại

- sample data không representative nên kết quả tạo false confidence;
- setup quá khó nên developer bỏ qua;
- rule engine quá generic;
- chạy rehearsal quá lâu trong CI;
- production schema/data khác quá nhiều.

### Lý do mạnh nhất để không build

**Không thể mô phỏng production hoàn hảo.** Nếu user coi report là chứng nhận “migration chắc chắn safe” thì tool có thể nguy hiểm. Product phải luôn trình bày đây là risk-reduction evidence, không phải guarantee.

## 6. Phạm vi MVP

### Must have

- CLI `migrationsentry run`.
- Detect EF Core project + DbContext.
- Chọn baseline migration và target migration.

- Compare two migration approaches.

- Multiple workload probes từ YAML.
- Table row-count summary.

## 7. Luồng hoạt động

### Happy path

```text
User runs CLI
→ validate Docker + project
→ resolve migrations
→ generate baseline DB
→ seed data
→ warm up probes
→ start lock sampler
→ apply target migration
→ continue probes
→ stop sampler
→ aggregate metrics
→ evaluate policies
→ write report
→ return exit code
```

### Failure: Docker unavailable

```text
validate environment
→ Docker connection failed
→ stop immediately
→ actionable error
```

Không fallback sang production connection string.

### Failure: migration fail

Tool giữ container sống trong configurable debug window hoặc export logs/schema state rồi terminate. Report verdict `FAILED`.

### Failure: probe query invalid

Một probe invalid không được biến migration thành pass. Report ghi `ProbeConfigurationError` và mặc định verdict `INCONCLUSIVE`.

### Failure: lock sampler missed short lock

Report phải ghi sampling interval và không tuyên bố “no lock occurred”; chỉ nói “no lock observed at configured sampling frequency”.

### Failure: dataset quá nhỏ

Cho rule minimum row counts. Nếu table mục tiêu có < configured threshold, verdict có thể là `LOW_CONFIDENCE`.

## 11. API và tích hợp

### Docker / Testcontainers

Purpose: disposable PostgreSQL.

Authentication: Docker daemon access local/CI.

Cost: local compute/CI minutes; không cần cloud API.

Privacy: seed dataset có thể chứa dữ liệu thật nếu user dùng production dump. Tool nên khuyến nghị sanitized/anonymized dump và không upload dữ liệu ra ngoài.

Fallback: nếu Docker không chạy, fail fast.

### EF Core tooling

Purpose: resolve/generate/apply migrations.

Authentication: none.

Version concern: tool phải ghi lại EF Core tooling version để report reproducible.

Fallback: cho phép user cung cấp `migration.sql` trực tiếp nếu project resolution fail.

### PostgreSQL system views

Purpose: quan sát active sessions/locks.

MVP chỉ query disposable DB mà tool tạo, nên không cần production permission model.

### Optional GitHub/Azure DevOps integration — Later

Chỉ upload report/annotation. Không cần cho core product.

- hallucination;
- migration SQL có business-sensitive names;
- cost/latency.

Vì vậy AI không nằm trong MVP.

## 14. Các bài toán kỹ thuật đáng học

### 1. PostgreSQL lock observation

Phải hiểu `pg_locks`, `pg_stat_activity`, lock modes và relation mapping.

Kỹ năng cải thiện: database concurrency và incident diagnosis.

### 2. Concurrent workload orchestration

Tool phải chạy migration, nhiều probe loops và lock sampler cùng lúc, rồi cancellation sạch khi một component fail.

Kỹ năng cải thiện: async orchestration, cancellation tokens và failure propagation trong .NET.

### 3. Reproducible database fixtures

Dataset phải đủ lớn nhưng CI runtime vẫn hợp lý.

Kỹ năng cải thiện: synthetic data generation, database snapshots và Testcontainers optimization.

### 4. Explainable risk scoring

Không dùng black-box score. Ví dụ:

```text
+50 ACCESS EXCLUSIVE observed > 2s
+40 write probe blocked > 2s
+20 migration > 30s
+15 ALTER COLUMN TYPE detected
```

Kỹ năng cải thiện: policy engines và measurable quality gates.

### 5. Confidence modeling

“No issue observed” không đồng nghĩa “safe”. Report phải gắn context:

- sample row count;
- PostgreSQL version;
- lock sampling interval;
- probe coverage;
- data source.

Kỹ năng cải thiện: engineering verification và communicating uncertainty.

## 15. Rủi ro và cách xử lý

### Sample data không giống production

**Risk:** false confidence.

**Mitigation:** luôn hiển thị dataset profile; hỗ trợ sanitized dump; verdict có `Confidence`; không dùng chữ “production safe”.

### CI quá chậm

**Risk:** developer disable tool.

**Mitigation:** chỉ chạy khi `Migrations/**` thay đổi; cache baseline seed image sau MVP; giới hạn row count; có quick/full modes.

### Lock sampling miss short events

**Risk:** report bỏ sót lock.

**Mitigation:** configurable 10–100 ms sampling; static SQL risk rules bổ sung dynamic observation; report nói rõ sampling limits.

### Tool tự viết migration recommendations sai

**Risk:** developer làm theo recommendation không phù hợp.

**Mitigation:** MVP chỉ report observed behavior + link docs; recommendation phải descriptive, không auto-edit source.

### Docker dependency

**Risk:** một số CI environment không có Docker.

**Mitigation:** document supported runners; later cho external PostgreSQL connection ở test environment, nhưng không production.

### Scope expansion

**Risk:** thêm SQL Server/MySQL quá sớm.

**Mitigation:** chỉ PostgreSQL trong MVP.

### Data privacy

**Risk:** user dùng production dump có PII.

**Mitigation:** local-only, không telemetry payload, document sanitized dataset workflow, exclude dumps khỏi git mặc định.

## Research notes

### Confirmed facts

- EF Core hỗ trợ migration scripts và migration bundles cho deployment. Microsoft document rõ `dotnet ef migrations bundle` tạo executable áp migration tới target database.
- PostgreSQL document lock level của `ALTER TABLE`; nhiều forms mặc định lấy `ACCESS EXCLUSIVE` nếu không có ghi chú khác.
- `ACCESS EXCLUSIVE` xung đột với tất cả table-level lock modes.
- PostgreSQL hỗ trợ các pattern như `NOT VALID` + `VALIDATE CONSTRAINT` trong một số loại constraint để tránh scan dài ở bước add constraint và giảm disruption khi validate.
- Testcontainers for .NET có PostgreSQL module chính thức để dựng disposable database.

### Observations

Static SQL review quan trọng nhưng không thể hiện đầy đủ interaction với data volume và concurrent workload. Dynamic rehearsal bổ sung evidence mà không cần truy cập production.

### Assumptions

- Developer có migrations đủ rủi ro để đáng chạy rehearsal.
- Dataset synthetic/sanitized có thể gần production đủ để phát hiện lớp rủi ro lớn.
- CI runtime 2–10 phút cho migration-changing PR là chấp nhận được; cần validate bằng usage thật.

### Recommendation

Build **lock + probe experiment trước**, rồi mới nối EF Core migrations vào. Nếu experiment không tạo ra signal rõ ràng hoặc CI runtime quá đắt, dừng project trước khi xây thêm orchestration.
