# Ý tưởng hôm nay: ExposureMap — Docker Host Exposure Auditor

## 1. Tóm tắt ý tưởng

ExposureMap là một công cụ self-hosted giúp developer **nhìn thấy chính xác container/service nào đang được expose ra host, interface nào đang lắng nghe, mức độ rủi ro của từng port mapping và cấu hình nào cần sửa trước khi deploy**. Tool đặc biệt hữu ích cho người tự host ứng dụng bằng Docker Compose trên VPS, mini PC hoặc máy Linux nhưng khó trả lời nhanh câu hỏi: “Service nào hiện có thể truy cập từ bên ngoài và có đúng ý định không?”.

- Người dùng chính: solo developer, homelab user, maintainer của VPS nhỏ.
- Bài toán chính: Docker port publishing, host networking và firewall behavior dễ tạo ra exposure ngoài ý muốn.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **1–2 tuần**.

## 2. Bài toán thực tế

### Confirmed facts

Docker documentation hiện nêu rõ rằng khi publish port mà không chỉ định host IP, port mặc định được bind tới tất cả địa chỉ host (`0.0.0.0` và `[::]`). Docker cũng cảnh báo việc publish port có thể khiến service truy cập được từ bên ngoài; nếu bind explicit vào `127.0.0.1` hoặc `::1`, service chỉ được truy cập từ host trong cấu hình thông thường.

Docker trên Linux còn tự tạo firewall rules để hỗ trợ bridge networking, NAT và port publishing. Điều này khiến việc chỉ nhìn `ufw status`, Compose file hoặc application config riêng lẻ chưa chắc phản ánh đầy đủ trạng thái exposure thực tế.

Nguồn chính thức:

- Docker — Port publishing and mapping: https://docs.docker.com/engine/network/port-publishing/
- Docker — Networking overview: https://docs.docker.com/engine/network/
- Docker — Packet filtering and firewalls: https://docs.docker.com/engine/network/packet-filtering-firewalls/
- Docker — Host network driver: https://docs.docker.com/engine/network/drivers/host/

### Observation

Một developer self-host nhiều service thường phải ghép thông tin từ:

- `docker compose.yml`;
- `docker ps`;
- `docker inspect`;
- `ss -lntup`;
- reverse proxy config;
- firewall rules;
- cloud/VPS firewall;
- README hoặc trí nhớ cá nhân.

Vấn đề lặp lại mỗi khi thêm container, đổi reverse proxy, mở port debug hoặc copy một Compose example từ Internet.

### Assumption cần kiểm chứng

Developer cá nhân sẽ thấy giá trị nếu có một dashboard duy nhất cho biết **intended exposure vs actual exposure**, thay vì chỉ liệt kê port đang mở.

## 3. Người dùng mục tiêu

**Primary user:** developer tự host 3–30 Docker containers trên một VPS hoặc mini PC.

- Bối cảnh sử dụng: deploy ASP.NET Core API, PostgreSQL, Redis, Grafana, automation tools, reverse proxy hoặc side projects.
- Main pain point: không chắc port nào đang public ngoài Internet/LAN và port nào chỉ nên internal.
- Workaround hiện tại: chạy `docker ps`, `ss`, xem Compose file và kiểm tra firewall thủ công.
- Lý do thử tool: muốn nhận một câu trả lời rõ ràng kiểu “PostgreSQL đang bind mọi interface nhưng policy của bạn khai báo internal-only”.

MVP không nhắm tới enterprise Kubernetes hoặc cloud security posture management.

## 4. Giải pháp đề xuất

Người dùng chạy ExposureMap trên Docker host.

Tool đọc:

- Docker Engine metadata;
- Compose labels/config nếu có;
- socket/listening ports trên host;
- một policy file đơn giản do user định nghĩa.

Ví dụ policy:

```yaml
services:
  api:
    exposure: public-via-proxy
  postgres:
    exposure: internal-only
  redis:
    exposure: internal-only
  grafana:
    exposure: lan-only
```

ExposureMap tạo report:

```text
postgres
Expected: internal-only
Observed: 0.0.0.0:5432 -> 5432/tcp
Risk: HIGH
Reason: port is published on all host interfaces
Suggested change: bind to localhost or remove host publishing
```

### Main workflow

Input
→ collect Docker/network metadata
→ normalize service/port/interface information
→ compare với exposure policy
→ classify mismatch
→ lưu snapshot
→ hiển thị diff và cảnh báo.

### Điều được tự động hóa

- Inventory container/network/port.
- Detect wildcard bindings.
- Detect host networking.
- Detect database/cache services exposed ngoài policy.
- So sánh snapshot hiện tại với snapshot trước.
- Tạo remediation hint.

### Điều user vẫn kiểm soát

- Service nào thực sự được phép public.
- LAN subnet nào được tin cậy.
- Có cho phép active connectivity check hay không.
- Có áp dụng remediation tự động hay chỉ report.

### Key differentiator

Không chỉ là port scanner. ExposureMap biết **container nào sở hữu port**, **Compose service nào sinh mapping đó**, **policy mong muốn là gì**, và **exposure vừa thay đổi từ lần deploy nào**.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Ngay cả chỉ một người dùng, tool vẫn có thể bảo vệ các VPS và self-hosted service cá nhân khỏi lỗi cấu hình đơn giản nhưng nguy hiểm.

### Technical learning value

Dự án giúp học sâu:

- Docker networking;
- Linux socket inspection;
- network namespaces;
- host binding semantics;
- firewall interaction;
- policy evaluation;
- security-focused observability.

### Phù hợp solo developer

Core problem nhỏ và deterministic. Không cần AI, không cần dữ liệu lớn, không cần cloud infrastructure phức tạp.

### Điều khiến dự án thất bại

- Chỉ hiển thị dữ liệu giống `docker ps` mà không đưa ra insight mới.
- False positive quá nhiều.
- Cố hỗ trợ mọi OS/firewall/network driver ngay từ đầu.

### Lý do mạnh nhất để không build

Nếu chỉ có 1–2 container và tất cả chạy sau reverse proxy được cấu hình cố định, kiểm tra thủ công có thể đã đủ.

## 6. Phạm vi MVP

### Must have

- Chạy trên Linux Docker host.
- Đọc container, network và published port từ Docker Engine.
- Đọc listening TCP sockets từ host.
- Detect bindings trên `0.0.0.0`, `[::]`, loopback và specific interface.
- Policy file `exposuremap.yml`.
- Classification: `OK`, `WARNING`, `HIGH`.
- Detect mismatch giữa expected và observed exposure.
- Lưu snapshot sau mỗi scan.
- CLI report dễ đọc.
- Exit code khác 0 khi có violation để dùng trong CI/deploy script.

### Should have

- Web dashboard nhỏ.
- Snapshot diff.
- Docker Compose service mapping.
- JSON/SARIF output.
- Ignore rule có expiration date.
- Telegram/email notification optional.

### Later

- nftables/iptables rule correlation sâu.
- VPS/cloud firewall adapters.
- Reverse proxy route discovery.
- Remote agent.
- Multi-host inventory.
- GitHub PR comment.
- Automatic safe fix generation.

## 7. Luồng hoạt động

### Normal flow

User chạy scan
→ validate Docker socket access
→ enumerate running containers
→ read port bindings/network mode
→ enumerate host listeners
→ correlate container ↔ host socket
→ load policy
→ evaluate rules
→ persist snapshot
→ render report
→ return exit code.

### Alternative flows

**Docker socket unavailable**
→ report capability missing
→ vẫn có thể chạy host-listener-only mode.

**Container dùng `network_mode: host`**
→ không dựa vào Docker port mappings
→ flag rằng container chia sẻ host network namespace
→ correlate theo process/listening ports nếu khả thi.

**Service mới chưa có policy**
→ trạng thái `UNCLASSIFIED`, không mặc định coi là safe.

**Listener chỉ trên loopback**
→ classify local-only.

**IPv6 wildcard nhưng IPv4 không mở**
→ report IPv6 riêng; không gộp thành một kết luận mơ hồ.

## 8. Kiến trúc đề xuất

Dùng **modular monolith**.

### Core modules

- `DockerInventory`: lấy containers, networks, ports.
- `HostListeners`: lấy TCP/UDP listener metadata.
- `PolicyEngine`: expected exposure rules.
- `Correlation`: map service ↔ container ↔ host binding.
- `RiskEngine`: deterministic classification.
- `Snapshots`: lưu trạng thái lịch sử.
- `Reporting`: CLI/JSON/web output.

### Frontend

Không cần trong vertical slice đầu tiên. Có thể thêm Vue 3 dashboard sau khi CLI chứng minh có giá trị.

### Backend

ASP.NET Core có thể host API/dashboard và background scan trong cùng process.

### Database

SQLite đủ cho MVP vì dữ liệu nhỏ và single-host.

### Background worker

`BackgroundService` chạy scan định kỳ nếu web mode bật.

### Queue

Không cần.

### Cache

Không cần.

### File storage

Không cần ngoài SQLite và policy YAML.

### Authentication

CLI không cần. Web dashboard self-hosted có thể bắt đầu với single-user login hoặc reverse-proxy auth.

### AI model

Không cần.

### Logging/monitoring

Structured logs + health endpoint là đủ.

### Deployment

Có hai mode hợp lý:

1. Native binary chạy trực tiếp trên Linux host.
2. Privileged-light container chỉ mount Docker socket read-only và các host metadata cần thiết.

MVP nên ưu tiên native binary để tránh tạo thêm complexity về namespace visibility.

## 11. API và tích hợp

### Docker Engine

- Purpose: container/network/port inventory.
- Authentication: local Unix socket trong self-hosted mode.
- Cost: không có API usage cost.
- Privacy/security: Docker socket có quyền rất mạnh; MVP phải dùng read-only operations và documentation cảnh báo rõ.
- Fallback: `docker inspect` CLI.

Docker networking docs: https://docs.docker.com/engine/network/

### Linux `ss`

- Purpose: host listening sockets.
- Authentication: không cần cho phần lớn listener metadata; process metadata có thể cần quyền cao hơn.
- Cost: không có.
- Privacy: local-only.
- Fallback: `/proc/net/*` hoặc `netstat` trên hệ cũ.

### Optional notification channel

Telegram/webhook/email chỉ nên là phase sau.

MVP vẫn hữu ích hoàn toàn offline.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Exposure classification nên deterministic và explainable.

Ví dụ:

```text
expected = internal-only
observed hostIp = 0.0.0.0
=> HIGH
```

AI không nên quyết định một port có “an toàn” hay không vì:

- kết quả phải reproducible;
- false negative có hậu quả security;
- rule-based logic dễ test hơn;
- không cần gửi infrastructure metadata ra ngoài.

Nếu sau này thêm AI, chỉ nên dùng optional để giải thích remediation bằng ngôn ngữ tự nhiên, không dùng làm source of truth.

## 14. Các bài toán kỹ thuật đáng học

### 1. Docker networking semantics

Học cách bridge, host mode, published ports, IPv4/IPv6 và NAT thực sự hoạt động thay vì chỉ dùng Compose theo thói quen.

### 2. Correlation giữa container và host state

Mapping Docker metadata với host listener giúp rèn kỹ năng observability và system-level diagnostics.

### 3. Policy engine deterministic

Thiết kế rule có priority, exceptions và explainability giúp học policy-as-code mà không cần framework lớn.

### 4. Security-oriented false positives

Một auditor vô dụng nếu cảnh báo quá nhiều. Việc phân biệt `public`, `LAN`, `loopback`, `internal Docker network` là bài toán classification thực tế.

### 5. Snapshot diff

So sánh trạng thái deploy trước/sau giúp học stable identity, normalization và change detection.

## 15. Rủi ro và cách xử lý

### Docker socket privilege

**Risk:** process có quyền truy cập Docker socket thường có quyền rất mạnh trên host.

**Mitigation:** chỉ dùng read operations; ưu tiên native local binary; không expose Docker socket qua network; document threat model rõ.

### False sense of security

**Risk:** tool có thể nói container không public nhưng cloud firewall/reverse proxy vẫn tạo đường truy cập khác.

**Mitigation:** ghi rõ scope “host/container exposure auditor”, không tuyên bố là full network security scanner.

### Firewall complexity

**Risk:** iptables/nftables/UFW có interaction phức tạp.

**Mitigation:** MVP chỉ sử dụng observable binding + Docker metadata; firewall-deep analysis là later feature.

### IPv6 bị bỏ sót

**Risk:** user kiểm tra IPv4 nhưng service vẫn bind IPv6 wildcard.

**Mitigation:** model IPv4/IPv6 riêng ngay từ đầu.

### Scope expansion

**Risk:** biến thành cloud security platform.

**Mitigation:** single-host Linux + Docker là boundary của MVP.

### Maintenance burden

**Risk:** Docker networking behavior thay đổi qua version.

**Mitigation:** integration tests chạy với các Docker Engine version được support và tránh phụ thuộc output text nếu Engine API có metadata tương đương.

## 16. Kiểm thử

### Strategy

- Unit tests cho exposure classification.
- Integration tests với Docker containers thật trong CI nơi khả thi.
- Golden tests cho normalized scan snapshots.
- Failure-path tests khi Docker daemon/`ss` unavailable.
- Security tests cho web dashboard và permission handling nếu thêm UI.

### 5 test scenario quan trọng nhất

1. `127.0.0.1:8080 -> 80` được classify `local-only`.
2. `0.0.0.0:5432 -> 5432` trong service `internal-only` tạo `HIGH` violation.
3. IPv6 wildcard `[::]:6379` không bị bỏ sót dù IPv4 không có mapping.
4. Container `network_mode: host` được đánh dấu special-case và không kết luận sai từ port mapping rỗng.
5. Một container mới không có policy xuất hiện là `UNCLASSIFIED`, không tự động coi là safe.

## 17. Cách đo dự án có hữu ích hay không

Metrics nên đo insight và reliability:

- **Unintended exposure found:** số exposure thực sự được xác nhận là sai cấu hình.
- **Mean review time:** thời gian kiểm tra security exposure trước deploy giảm bao nhiêu so với thủ công.
- **Classification precision:** tỷ lệ alert được user xác nhận là hợp lệ.
- **Scan success rate:** tỷ lệ scan hoàn tất không mất collector quan trọng.
- **Change detection:** tỷ lệ exposure mới được phát hiện ngay trong scan đầu sau deploy.
- **Repeated use:** số tuần có scan được chạy ít nhất một lần.

Mục tiêu validation cá nhân: trong 30 ngày, tool phải phát hiện hoặc xác nhận được ít nhất 3 thay đổi exposure thực tế và mỗi lần review mất dưới 1 phút.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, tạo vertical slice đầu tiên:

**Docker container inventory → port normalization → console report wildcard vs loopback.**

### Files/components cần tạo

```text
ExposureMap.sln
src/
  ExposureMap.Cli/
    Program.cs
    Models/ObservedEndpoint.cs
    Services/DockerCollector.cs
    Services/ExposureClassifier.cs
tests/
  ExposureMap.Tests/
    ExposureClassifierTests.cs
```

### Setup commands

```bash
dotnet new sln -n ExposureMap
dotnet new console -n ExposureMap.Cli -o src/ExposureMap.Cli
dotnet new xunit -n ExposureMap.Tests -o tests/ExposureMap.Tests
dotnet sln add src/ExposureMap.Cli
dotnet sln add tests/ExposureMap.Tests
dotnet add tests/ExposureMap.Tests reference src/ExposureMap.Cli
```

Dùng Docker CLI cho prototype đầu để giảm setup:

```bash
docker ps --format '{{json .}}'
docker inspect <container>
```

### First vertical slice

1. Lấy danh sách running containers.
2. Parse `NetworkSettings.Ports` từ `docker inspect`.
3. Normalize thành:

```text
ContainerName
Protocol
ContainerPort
HostIp
HostPort
ExposureScope
```

4. Classification đầu tiên:

```text
127.0.0.1 / ::1   => LocalOnly
0.0.0.0 / ::      => AllInterfaces
specific host IP  => SpecificInterface
no published port => DockerInternal
```

5. In console table:

```text
SERVICE       HOST BIND          CONTAINER     EXPOSURE
api           0.0.0.0:8080       8080/tcp      ALL_INTERFACES
postgres      127.0.0.1:5432     5432/tcp      LOCAL_ONLY
redis         -                  6379/tcp      DOCKER_INTERNAL
```

### Expected result

Chạy:


### Verification checklist

- [ ] Tool thấy tất cả running containers.
- [ ] Parse được IPv4 wildcard.
- [ ] Parse được loopback binding.
- [ ] Không coi unpublished container port là public.
- [ ] Có unit test cho ít nhất 4 classification cases.
- [ ] Output đủ rõ để phát hiện một port đáng nghi bằng mắt trong dưới 10 giây.

### Stop condition

Dừng session ngay khi tool có thể phân biệt đúng **ALL_INTERFACES**, **LOCAL_ONLY** và **DOCKER_INTERNAL** trên ít nhất ba container test. Chưa làm database, dashboard, firewall parser, notifications hoặc AI trong session đầu tiên.
