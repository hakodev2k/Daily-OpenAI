# Ý tưởng hôm nay: RestoreProof — Backup Restore Verification Runner

## 1. Tóm tắt ý tưởng

RestoreProof là một công cụ self-hosted giúp developer **kiểm chứng backup có thực sự restore được hay không** bằng cách định kỳ lấy snapshot/dump, khôi phục vào môi trường cô lập, chạy health check và lưu bằng chứng kết quả. Nó phù hợp cho solo developer hoặc team nhỏ đang tự host PostgreSQL, file backup hoặc Docker-based services nhưng hiện mới chỉ kiểm tra rằng “backup đã tạo thành công”, chưa kiểm tra end-to-end rằng dữ liệu có thể phục hồi.

- Người dùng chính: developer tự vận hành ứng dụng nhỏ, homelab, VPS hoặc SaaS cá nhân.
- Vấn đề chính: backup tồn tại nhưng không chắc restore được khi thật sự xảy ra sự cố.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Một hệ thống backup thường có hai lớp vấn đề khác nhau:

1. File/snapshot backup có tồn tại và không bị corruption.
2. Backup có thể restore thành một hệ thống hoạt động với dữ liệu hợp lệ.

Hai việc này không hoàn toàn giống nhau.

**Confirmed facts:**

- PostgreSQL cung cấp `pg_dump`, `psql` và `pg_restore` để tạo và phục hồi logical backup. Tài liệu chính thức cũng lưu ý rằng restore có thể fail hoặc tạo trạng thái partial nếu lỗi không được xử lý đúng. Nguồn: PostgreSQL Documentation — SQL Dump / `pg_restore`: https://www.postgresql.org/docs/current/backup-dump.html
- Restic cung cấp `restic check` để kiểm tra repository và `restic restore` để phục hồi snapshot. Tài liệu restic khuyến nghị chạy `check` định kỳ để phát hiện repository hỏng trước khi cần restore. Nguồn: restic Documentation — Working with repositories / Restoring from backup: https://restic.readthedocs.io/en/stable/045_working_with_repos.html và https://restic.readthedocs.io/en/stable/050_restore.html

**Observation:** các công cụ trên giải quyết tốt thao tác backup/restore riêng lẻ nhưng không tự biến quy trình đó thành một bài kiểm thử định kỳ có pass/fail, evidence, history và cảnh báo.

**Assumption cần kiểm chứng:** với solo developer và ứng dụng nhỏ, việc tự động chạy restore drill mỗi tuần/tháng sẽ có giá trị hơn việc chỉ nhìn log “backup completed successfully”.

Hiện tại nhiều người xử lý bằng một trong các cách:

- Kiểm tra file backup có tồn tại.
- Kiểm tra dung lượng file.
- Chạy `restic check`.
- Thỉnh thoảng restore thủ công vào máy local.
- Chỉ thử restore khi thật sự có incident.

Điểm bất tiện là restore thủ công dễ bị bỏ qua vì mất thời gian, cần nhớ nhiều command, cần dựng database/container tạm và phải dọn môi trường sau khi test.

## 3. Người dùng mục tiêu

**Primary user:** developer đang tự vận hành 1–10 ứng dụng nhỏ trên VPS, mini PC, NAS hoặc cloud instance.

### User profile

- Có PostgreSQL database, file uploads hoặc config backup.
- Dùng Docker Compose hoặc container-based deployment.
- Có cron/Hangfire/script tạo backup định kỳ.
- Không có dedicated DevOps/SRE team.

### Context of use

Người dùng đã có backup nhưng muốn biết câu trả lời cho câu hỏi:

> “Nếu server chết tối nay, backup mới nhất có đủ để dựng hệ thống lên lại không?”

### Main pain point

Không có bằng chứng gần đây cho thấy backup restore được.

### Current workaround

Chạy command thủ công vài tháng một lần hoặc không test restore.

### Reason they would try RestoreProof

Tool biến restore thành một bài kiểm thử định kỳ, chạy tự động trong sandbox và trả kết quả đơn giản:

```text
orders-db / snapshot 2026-08-18
Restore: PASS
Schema check: PASS
Row sanity checks: PASS
App health check: PASS
Duration: 3m 42s
```

## 4. Giải pháp đề xuất

RestoreProof cho phép người dùng khai báo một **Restore Plan** bằng YAML hoặc UI.

Ví dụ:

```yaml
name: orders-postgres
schedule: weekly
source:
  type: pg_dump
  path: /backups/orders/latest.dump
restore:
  image: postgres:18
  database: restore_test
checks:
  - type: sql
    query: SELECT COUNT(*) FROM orders
    assertion: greater_than
    value: 0
  - type: sql
    query: SELECT MAX(created_at) FROM orders
    assertion: newer_than_days
    value: 7
cleanup: always
```

### Main workflow

Input:

- Backup file hoặc restic snapshot.
- Restore configuration.
- Một số assertions tối thiểu.

Processing:

- Tạo isolated PostgreSQL container.
- Restore backup.
- Chạy schema/data checks.
- Ghi log và duration.
- Xóa container/database test.

Output:

- `PASS`, `WARN`, `FAIL`.
- Restore duration.
- Check results.
- Error log rút gọn.
- Snapshot metadata.

### Automated

- Chọn backup mới nhất.
- Provision sandbox.
- Restore.
- Verify.
- Cleanup.
- Ghi history.
- Notification khi fail.

### User control

Người dùng tự xác định:

- Backup source.
- Restore image/version.
- SQL assertions.
- Retention.
- Notification channel.
- Có cho phép chạy test production-like hay không.

### Key differentiator

RestoreProof không phải backup engine. Nó là **automated restore drill runner** — kiểm tra khả năng khôi phục thay vì chỉ kiểm tra backup job có hoàn thành.

### Ví dụ end-to-end

Một developer có PostgreSQL chạy trong Docker và mỗi đêm tạo `pg_dump -Fc`.

Chủ nhật 03:00:

1. RestoreProof tìm file dump mới nhất.
2. Tạo container PostgreSQL tạm.
3. Tạo database `restoreproof_xxx`.
4. Chạy `pg_restore`.
5. Chạy assertions:
   - bảng `users` tồn tại;
   - có ít nhất một user;
   - `orders.created_at` có record trong 7 ngày gần đây;
   - migration version bằng production expected version.
6. Kết quả PASS.
7. Container bị xóa.
8. History được lưu.

Ba tuần sau, backup script tạo ra file lỗi. Restore fail và Telegram/email báo ngay thay vì vài tháng sau mới phát hiện.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Tool có giá trị ngay cả khi chỉ có một người dùng vì chính developer có thể dùng nó để kiểm tra backup các project cá nhân.

### Technical learning value

Dự án liên quan tới:

- Process execution.
- Docker lifecycle.
- Database restore.
- Health checking.
- Background scheduling.
- Timeout/cancellation.
- Secret handling.
- Failure isolation.
- Observability.

### Vì sao phù hợp solo developer

Domain nhỏ và rõ:

```text
backup → sandbox → restore → verify → cleanup → report
```

Không cần distributed system hay traffic lớn.

### Vì sao vẫn hữu ích với rất ít user

Một restore failure được phát hiện sớm có thể đã đủ để chứng minh utility của project.

### Điều gì làm ý tưởng thất bại

- Người dùng đã có managed database với automated restore verification tốt.
- Setup Restore Plan quá phức tạp.
- Tool cần nhiều quyền Docker/root khiến user ngại cài.
- Restore test quá tốn disk/CPU.

### Lý do mạnh nhất để không build

Nếu toàn bộ workload dùng managed database có built-in point-in-time restore và người dùng thường xuyên test recovery bằng quy trình khác, RestoreProof có thể trở thành infrastructure dư thừa.

## 7. Luồng hoạt động

### Happy path

User tạo Restore Plan
→ validate config
→ locate backup
→ validate file/hash/age
→ provision test database
→ restore
→ execute assertions
→ persist result
→ cleanup
→ send notification nếu cấu hình.

### Backup không tồn tại

Không tìm thấy file
→ `FAIL: BackupNotFound`
→ không tạo container
→ notification.

### Backup quá cũ

File tồn tại nhưng vượt `maxBackupAge`
→ `WARN` hoặc `FAIL` tùy policy.

### Restore fail

`pg_restore` exit code khác 0
→ capture stderr
→ mark failed
→ cleanup container
→ notification.

### Assertion fail

Restore thành công nhưng query sanity check fail
→ `FAIL: DataValidation`
→ lưu check nào fail.

### Cleanup fail

Restore check xong nhưng container không xóa được
→ run vẫn lưu primary result
→ thêm operational warning và retry cleanup.

### User cancel

CancellationToken
→ kill process/container
→ cleanup best-effort
→ trạng thái `Cancelled`.

- xem plans;
- chạy manual drill;
- xem history;
- mở logs.

MVP thậm chí có thể bắt đầu CLI-only.

### Database

### Background worker

`BackgroundService` chạy job queue nội bộ.

### Scheduler

Quartz.NET hoặc timer-based hosted service.

MVP manual-only trước; scheduler thêm ở Phase 2.

### Queue

Không cần message broker.

Một bounded `Channel<RestoreJob>` hoặc database polling là đủ.

### Cache

Không cần.

### File storage

Không copy backup vào RestoreProof nếu không cần. Tool đọc backup từ mounted path.

Chỉ giữ log và metadata nhỏ.

### Authentication

Single-user authentication hoặc reverse-proxy authentication.

Nếu chỉ chạy LAN/local, MVP có thể disable auth nhưng phải bind localhost mặc định.

### External APIs

Không bắt buộc.

### AI model

Không cần.

### Notification channel

Telegram Bot API hoặc SMTP có thể thêm sau.

### Logging

Structured logging với:

- `RunId`
- `PlanId`
- `BackupPath`
- `RestoreStage`
- `DurationMs`

Không log password/connection string.

### Deployment

Docker Compose hoặc standalone .NET binary trên Linux VPS/mini PC.

Tool cần quyền điều khiển container runtime nếu dùng Docker sandbox.

## 11. API và tích hợp

### PostgreSQL tools

**Purpose:** backup restore.

Utilities:

```text
pg_dump
pg_restore
psql
createdb
```

**Authentication:** database credentials khi backup source được lấy trực tiếp từ DB; restore sandbox dùng credential generated tạm.

**Cost:** miễn phí/open-source tooling.

**Privacy:** backup chứa toàn bộ dữ liệu production; tool không được upload ra ngoài mặc định.

**Fallback:** hỗ trợ file dump đã tồn tại mà không cần kết nối production DB.

### Docker Engine

**Purpose:** isolated temporary database.

**Authentication/permission:** user chạy RestoreProof cần quyền gọi Docker daemon.

**Security concern:** Docker socket là quyền rất mạnh.

**Fallback:** user cung cấp external disposable PostgreSQL instance thay vì Docker.

### restic

**Purpose:** lấy snapshot và kiểm tra repository nếu user đang dùng restic.

**Authentication:** repository password/access key tùy backend.

**Cost/rate limit:** phụ thuộc storage backend.

**Privacy:** credentials không được lưu plaintext trong DB.

**Fallback:** direct filesystem backup source.

### Telegram Bot API / SMTP

**Purpose:** failure notification.

**Authentication:** bot token hoặc SMTP credential.

**Fallback:** dashboard + local log.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Restore verification phải deterministic.

Các bước quan trọng đều có kết quả rõ ràng:

- process exit code;
- SQL query result;
- timeout;
- file age;
- hash;
- container health;
- HTTP status.

AI có thể được thêm optional sau này để giải thích log dài nhưng không nên quyết định PASS/FAIL.

Nếu dùng AI sau MVP:

- Input: sanitized restore log.
- Output: structured `possibleCause`, `suggestedChecks`, `confidence`.
- Validation: chỉ hiển thị suggestion, không thay đổi run status.
- Fallback: raw logs.
- Risk: log có dữ liệu nhạy cảm và AI có thể suy đoán sai.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** chứng minh restore drill đáng tự động hóa.

**Main tasks:**

- Chọn một PostgreSQL project cá nhân.
- Tạo một `pg_dump` thật.
- Viết shell/PowerShell script restore vào Docker container.
- Chạy 3 SQL sanity checks.
- Cố tình corrupt hoặc dùng dump sai để quan sát failure.

**Expected output:** một script manual cho kết quả PASS/FAIL.

**Completion criteria:** script tái tạo được quy trình restore từ đầu đến cuối mà không sửa tay giữa chừng.

### Phase 1 — Core MVP

**Goal:** product hóa script thành runner.

**Main tasks:**

- YAML Restore Plan.
- Backup discovery.
- Docker sandbox lifecycle.
- `pg_restore`/`psql` executor.
- SQL assertions.
- SQLite run history.
- CLI `restoreproof run <plan>`.

**Expected output:** một command chạy full drill.

**Completion criteria:** command trả exit code `0` khi pass và non-zero khi fail.

### Phase 2 — Reliability

**Goal:** đảm bảo runner không tự gây operational problem.

**Main tasks:**

- Timeout/cancellation.
- Cleanup `finally` path.
- Disk-space check.
- Secret redaction.
- Retry cleanup.
- Scheduler.
- Integration tests với Testcontainers.

**Expected output:** job fail giữa chừng vẫn không để lại container rác.

**Completion criteria:** 20 failure-path tests liên tiếp không để lại resource orphan.

### Phase 3 — Useful expansion

**Goal:** giảm công việc quan sát thủ công.

**Main tasks:**

- Web dashboard.
- Telegram/SMTP notification.
- Restic source.
- Trend restore duration.
- Backup-age policy.

**Expected output:** weekly restore drill chạy tự động và chỉ báo khi có vấn đề.

### Phase 4 — Production readiness

**Goal:** self-host ổn định lâu dài.

**Main tasks:**

- Docker image.
- Health endpoints.
- Structured logs.
- Metrics.
- Run retention cleanup.
- Backup RestoreProof metadata.
- Security documentation.
- Least-privilege deployment examples.

**Expected output:** deployment package rõ ràng.

**Completion criteria:** chạy liên tục 30 ngày, tất cả scheduled drills có trạng thái cuối cùng và không có orphan container.

## 14. Các bài toán kỹ thuật đáng học

### 1. Reliable process execution

Phải chạy `docker`, `pg_restore`, `psql` với timeout, cancellation, stdout/stderr capture và exit code.

Kỹ năng cải thiện: OS process management và production-grade command orchestration.

### 2. Resource lifecycle và cleanup

Container/database tạm phải luôn được xóa kể cả khi process crash.

Kỹ năng cải thiện: deterministic cleanup, compensating action và failure recovery.

### 3. Backup verification semantics

“Restore command exit code 0” chưa chắc nghĩa là dữ liệu đúng.

Kỹ năng cải thiện: thiết kế health assertions và data-quality checks.

### 4. Secret handling

Tool có thể cần DB password, restic password hoặc cloud storage credentials.

Kỹ năng cải thiện: secret injection, environment variables, redaction và least privilege.

### 5. Scheduler overlap control

Restore job có thể chạy lâu hơn schedule interval.

Kỹ năng cải thiện: distributed-lock thinking, concurrency limits và job state machine ngay trong modular monolith.

## 15. Rủi ro và cách xử lý

### Docker socket security

**Risk:** quyền Docker gần tương đương quyền root trên host trong nhiều deployment.

**Mitigation:** local-only default, documentation rõ, optional external runner, không expose API public nếu không auth.

### Backup privacy

**Risk:** dump chứa dữ liệu production.

**Mitigation:** không upload backup; sandbox local; log redaction; không lưu query rows đầy đủ.

### Disk exhaustion

**Risk:** restore database lớn làm đầy disk.

**Mitigation:** preflight free-space threshold, max backup size, concurrency = 1 mặc định.

### Scope expansion

**Risk:** cố hỗ trợ mọi database/storage từ đầu.

**Mitigation:** PostgreSQL + local file trước.

### Restore version mismatch

**Risk:** PostgreSQL tool/server version khác production.

**Mitigation:** Restore Plan pin major version; report version metadata.

### False confidence

**Risk:** vài SQL assertions pass nhưng application vẫn không recover được.

**Mitigation:** UI gọi đây là “restore verification”, không phải full disaster-recovery certification; thêm app smoke test sau MVP.

### Maintenance burden

**Risk:** Docker/PostgreSQL behavior thay đổi theo version.

**Mitigation:** pin/test supported versions, matrix integration tests.

## 16. Kiểm thử

### Strategy

- **Unit tests:** config validation, backup selection, assertion evaluation.
- **Integration tests:** Testcontainers PostgreSQL + real dump/restore.
- **E2E tests:** CLI hoặc dashboard thực sự tạo và dọn sandbox.
- **Failure-path tests:** corrupt dump, timeout, disk low, invalid password.
- **Security tests:** secret redaction, unsafe path, command injection.
- **Data-quality tests:** assertions trả đúng PASS/FAIL.

### 5 test scenario quan trọng nhất

1. Valid PostgreSQL dump restore thành công và tất cả assertions PASS.
2. Corrupted dump khiến run FAIL và container vẫn được cleanup.
3. Restore timeout bị cancel đúng và process con không còn chạy.
4. SQL assertion phát hiện backup hợp lệ về format nhưng dữ liệu business thiếu.
5. Password/connection string không xuất hiện trong stored logs hoặc API response.

## 17. Cách đo dự án có hữu ích hay không

### Product usage metric

Số restore drills hoàn thành mỗi tháng.

### Time saved

So sánh thời gian manual restore drill trước và sau tool.

### Task completion rate

```text
completed restore drills / scheduled restore drills
```

### Error rate

Tỷ lệ run fail vì chính RestoreProof bug thay vì backup problem.

### Repeated use

Có tiếp tục để scheduler chạy sau 4–8 tuần hay bị tắt sau thử nghiệm đầu tiên.

### Technical reliability

- orphan container count = 0;
- job status stuck = 0;
- cleanup success > 99% trong môi trường cá nhân.

### Outcome metric quan trọng nhất

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, tạo vertical slice đầu tiên:

```text
PostgreSQL dump file
→ temporary PostgreSQL container
→ restore
→ SELECT sanity check
→ PASS/FAIL
→ cleanup
```

### Files/components cần tạo

```text
RestoreProof.sln
src/
  RestoreProof.Cli/
    Program.cs
    RestoreRunner.cs
    ProcessRunner.cs
    Models/RestoreResult.cs
tests/
  RestoreProof.Tests/
```

### Setup commands

```bash
dotnet new sln -n RestoreProof
dotnet new console -n RestoreProof.Cli -o src/RestoreProof.Cli
dotnet new xunit -n RestoreProof.Tests -o tests/RestoreProof.Tests
dotnet sln add src/RestoreProof.Cli
dotnet sln add tests/RestoreProof.Tests
dotnet add tests/RestoreProof.Tests reference src/RestoreProof.Cli
```

Kiểm tra Docker:

```bash
docker version
```

Tạo database test ban đầu:

```bash
docker run --rm --name restoreproof-source \
  -e POSTGRES_PASSWORD=test \
  -e POSTGRES_DB=demo \
  -p 55432:5432 \
  -d postgres:18
```

Sau đó tạo sample table/data rồi dump:

```bash
pg_dump -h localhost -p 55432 -U postgres -Fc demo > demo.dump
```

### First vertical slice

`RestoreRunner` thực hiện:

1. Generate container name.
2. `docker run` PostgreSQL tạm trên random port.
3. Chờ database ready.
4. Create target DB.
5. Chạy:

```bash
pg_restore -d <connection> demo.dump
```

6. Chạy:

```sql
SELECT COUNT(*) FROM demo_items;
```

7. Nếu count > 0 → PASS.
8. Trong `finally`:

```bash
docker rm -f <container>
```

### Expected result

Terminal hiển thị dạng:

```text
RestoreProof Run
Backup: demo.dump
Container: restoreproof-7f2c
Restore: PASS
Check demo_items > 0: PASS
Duration: 8.4s
Cleanup: PASS
```

### Verification checklist

- [ ] `demo.dump` restore được vào container hoàn toàn mới.
- [ ] Query sanity check trả PASS.
- [ ] Đổi dump thành file invalid thì command trả FAIL.
- [ ] Sau cả success và failure, `docker ps -a` không còn restore container.
- [ ] Password không xuất hiện trong terminal log.
- [ ] Có ít nhất một integration test chạy qua real PostgreSQL container.

### Stop condition

Dừng session ngay khi command duy nhất có thể chứng minh:

```text
real dump → real restore → real SQL verification → automatic cleanup
```

Không làm dashboard, scheduler, restic integration, notification hoặc AI trong session đầu tiên.
