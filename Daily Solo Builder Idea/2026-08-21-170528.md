# Ý tưởng hôm nay: HarDiff — HAR-to-API Regression Reproducer

## 1. Tóm tắt ý tưởng

**HarDiff** là một developer tool giúp biến file HAR thu từ trình duyệt thành một bộ API regression checks có thể chạy lại trên local/QA/staging, tự động loại dữ liệu nhạy cảm, parameterize host/token/dynamic IDs và so sánh response theo quy tắc deterministic thay vì chỉ diff text thô. Công cụ phù hợp cho backend/QA developer thường phải tái hiện bug từ network traffic nhưng không muốn viết thủ công hàng chục request test.

- Người dùng chính: backend developer, QA automation engineer, solo developer debug web/API flows.
- Vấn đề chính: bug thực tế thường chỉ tái hiện được qua chuỗi request trong browser; HAR có dữ liệu nhưng chưa phải test suite có thể maintain.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Khi một bug chỉ xuất hiện trong UI, developer thường mở DevTools Network, tìm request lỗi, copy cURL hoặc export HAR rồi tái hiện thủ công. Nếu flow gồm 10–30 API calls, cách này nhanh chóng trở nên khó dùng lại: token hết hạn, host khác giữa QA/local, request chứa IDs động, response chứa timestamp/request ID và HAR có thể chứa dữ liệu nhạy cảm.

### Confirmed facts

Chrome DevTools hỗ trợ export network requests thành HAR. Chrome hiện mặc định cung cấp export HAR đã **sanitized**, loại các header nhạy cảm như `Cookie`, `Set-Cookie` và `Authorization`; người dùng vẫn có thể chọn export bản chứa sensitive data nếu bật tùy chọn tương ứng. Nguồn: https://developer.chrome.com/docs/devtools/network/reference

Playwright hỗ trợ record HAR và replay từ HAR thông qua `recordHar` và `page.routeFromHAR()`/`browserContext.routeFromHAR()`. Playwright cũng hỗ trợ `update`, `updateContent`, `updateMode`, URL filter và HAR replay; documentation lưu ý service-worker intercepted requests không được phục vụ từ HAR và khuyến nghị block service workers khi dùng request interception. Nguồn: https://playwright.dev/docs/mock và https://playwright.dev/docs/api/class-browsercontext

Playwright 1.60 còn bổ sung HAR recording như một phần first-class của tracing API qua `tracing.startHar()`/`stopHar()`. Nguồn: https://playwright.dev/docs/release-notes

W3C Web Performance work từng định nghĩa HAR là định dạng archival cho HTTP transactions mà browser có thể export để chứa dữ liệu performance/network. Nguồn: https://www.w3.org/2013/01/webperf

### Observation

HAR rất tốt để **capture** và Playwright rất tốt để **mock/replay network**, nhưng developer debugging backend thường cần một bước ở giữa:

- chọn chỉ API calls quan trọng;
- chuyển host/environment;
- inject auth mới;
- thay dynamic IDs;
- bỏ analytics/static assets;
- normalize nondeterministic response fields;
- rerun request thật;
- so sánh semantic result;
- lưu một regression case có thể commit vào Git.

### Assumption cần validate

Tool hữu ích nhất với team có bug/API flow thường được tái hiện từ browser network. Nếu project đã có contract/integration tests rất tốt và mọi bug đều có reproduction nhỏ, HarDiff có thể không đem nhiều giá trị.

## 3. Người dùng mục tiêu

Primary user của MVP là **backend developer hoặc QA automation engineer đang debug SPA/mobile-web frontend gọi REST APIs**.

### Context sử dụng

- QA gửi HAR từ một flow lỗi.
- Developer muốn chạy lại cùng request sequence trên QA/local.
- API có authentication, dynamic identifiers và response metadata thay đổi.
- Developer cần biến reproduction thành regression test sau khi sửa bug.

### Main pain point

HAR chứa “đủ dữ liệu để hiểu chuyện gì xảy ra”, nhưng chưa phải artifact dễ chạy lại và dễ review trong Git.

### Current workaround

- Copy as cURL từng request.
- Postman collection viết tay.
- Bruno/HTTP files tạo thủ công.
- Viết integration test C# riêng.
- Playwright test lại toàn UI flow.

### Vì sao user thử HarDiff

Vì họ muốn đi từ **HAR thực tế → test case có thể chạy lại** trong vài phút, nhưng vẫn kiểm soát token, redaction và assertion.

## 4. Giải pháp đề xuất

### Main workflow

```text
Import HAR
→ security scan/redaction
→ classify requests
→ keep only target APIs
→ detect variables
→ user confirms environment mapping
→ generate replay case
→ execute real HTTP requests
→ normalize responses
→ compare against baseline/rules
→ save regression result
```

### Input

- `.har` hoặc HAR `.zip`.
- Optional base URL patterns.
- Environment map, ví dụ:
  - `https://qa.example.com` → `http://localhost:5000`.
- Secret placeholders.
- Ignore rules:
  - analytics;
  - static assets;
  - telemetry;
  - OPTIONS/preflight.
- Normalization paths, ví dụ:
  - `$.requestId`;
  - `$.createdAt`;
  - `$.traceId`.

### Processing

Deterministic code:

1. Parse HAR.
2. Scan header/query/body cho sensitive patterns.
3. Build request dependency graph nhẹ dựa trên URL/path/body values.
4. Detect repeated literal values có thể là IDs.
5. Extract variables thành placeholders.
6. Replay bằng `HttpClient`.
7. Compare status code, content type, selected headers và JSON structure/value rules.
8. Persist run result.

### Output

Một generated case có thể trông như:

```yaml
name: create-booking-and-load-detail
baseUrl: ${API_BASE_URL}

variables:
  userId: ${USER_ID}

requests:
  - id: create-booking
    method: POST
    path: /api/bookings
    body: fixtures/create-booking.json
    capture:
      bookingId: $.id

  - id: get-booking
    method: GET
    path: /api/bookings/${bookingId}

assertions:
  - request: create-booking
    status: 201
  - request: get-booking
    status: 200
    jsonIgnore:
      - $.updatedAt
      - $.requestId
```

### What is automated

- HAR parsing.
- API request filtering.
- Sensitive-value detection.
- Common host replacement.
- Dynamic-value candidates.
- Response normalization.
- Regression diff report.

### User remains in control

User xác nhận:

- request nào được giữ;
- secret nào phải inject;
- dynamic value nào được capture/reuse;
- field nào được ignore;
- destructive requests có được replay hay không.

### Key differentiator

**Không chỉ replay HAR**, mà chuyển traffic thực tế thành **reviewable regression case** với redaction, environment mapping và semantic diff.

### Ví dụ end-to-end

QA gửi HAR từ bug: mở outlet list → chọn outlet → tạo booking → load booking detail trả sai timezone.

HarDiff import HAR và loại bỏ ảnh, JS bundle, Application Insights và OPTIONS. Nó giữ 4 API requests. Tool phát hiện booking ID ở response request #3 xuất hiện trong URL request #4 và đề xuất capture `$.id` thành `${bookingId}`. User xác nhận, map QA host sang localhost, inject local auth token và chạy case. Trước fix, response detail lệch ngày; sau fix, regression case pass và được commit vào repo.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Developer có thể dùng ngay cho bug reproduction cá nhân. Chỉ một case khó tái hiện đã đủ chứng minh utility.

### Technical learning value

Dự án có nhiều bài toán thú vị:

- HAR parsing;
- HTTP semantics;
- JSON diff;
- secret redaction;
- dynamic data extraction;
- dependency inference;
- deterministic replay;
- destructive-action guardrails.

### Suitable for solo developer

MVP có thể là CLI + local web UI, không cần cloud service, account system hay distributed workers.

### Useful with few users

Ngay cả một developer cũng có thể giữ các HAR-derived regression cases trong repository và chạy trong CI.

### What could make it fail

- auto-variable detection tạo nhiều false positives;
- flows phụ thuộc browser cookies/service workers/WebSockets;
- APIs có nhiều nondeterministic behavior;
- user lo HAR chứa secrets;
- generated format khó chỉnh hơn viết test tay.

### Strongest reason not to build

Nếu product cố “tự động hiểu toàn bộ browser flow”, scope sẽ nổ rất nhanh. HarDiff chỉ nên xử lý **HTTP API requests có thể replay bằng HttpClient**; UI state, WebSocket, SSE và browser behavior nằm ngoài MVP.

## 7. Luồng hoạt động

```text
User imports HAR
→ validate format
→ scan for sensitive data
→ classify requests
→ user selects API hosts
→ normalize/filter
→ detect variable candidates
→ user confirms transformations
→ generate case
→ validate target environment
→ replay sequentially
→ capture dynamic values
→ normalize responses
→ compare
→ result report
→ optional export/commit
```

### Failure: HAR contains Authorization/Cookie

Tool không persist raw value. Import phase phải detect và thay bằng `${AUTH_TOKEN}`/redacted marker trước khi lưu project data.

### Failure: target API unreachable

Run dừng hoặc skip dependent requests theo policy; report rõ `ConnectionFailed`, không coi là assertion mismatch.

### Failure: capture JSONPath không tồn tại

Dependent request không chạy và được đánh dấu `BlockedByMissingCapture`.

### Failure: DELETE/POST có side effect nguy hiểm

Default run mode chặn methods/configured paths được đánh dấu destructive. User phải enable rõ ở environment profile.

### Failure: response body không phải JSON

Fallback compare status/content-type/hash/text rules; không bắt JSON parser xử lý.

### Failure: rate limit 429

Không tự spam retry. Respect `Retry-After` nếu cấu hình cho phép và ghi rõ replay timing.

## 11. API và tích hợp

### HAR format

Purpose: input chuẩn từ browser/tool network captures.

Authentication: không có.

Privacy concern: HAR có thể chứa header, cookies, query strings và body nhạy cảm. Chrome sanitized export giảm một số nguy cơ nhưng tool vẫn phải tự scan vì body/query vẫn có thể chứa secrets/PII. Nguồn: https://developer.chrome.com/docs/devtools/network/reference

Fallback: nếu HAR có field/vendor extension chưa hiểu, preserve metadata cần thiết và bỏ qua phần không hỗ trợ; không fail toàn import nếu request cơ bản vẫn parse được.

### Playwright HAR

Purpose: tạo HAR test fixtures hoặc future capture workflow.

Playwright hỗ trợ HAR recording và replay; `routeFromHAR` có `notFound=abort|fallback`, update modes và URL filtering. Nguồn: https://playwright.dev/docs/mock

Concern: HarDiff không nên phụ thuộc Playwright-specific minimal HAR fields cho mọi chức năng; parser nên chịu được browser HAR và Playwright HAR.

### Target HTTP API

Purpose: replay thật.

Authentication: runtime secret injection.

Rate-limit concern: user cấu hình concurrency = 1 ở MVP; sequential replay là default an toàn.

Privacy: request/response raw data không được upload ra dịch vụ khác.

Fallback: offline/mock mode có thể dùng saved baseline sau này, nhưng MVP tập trung real API.

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

Core product không cần AI.

### AI có thể hỗ trợ sau này

- đặt tên variable từ context;
- đề xuất ignore fields;
- giải thích response diff;
- gợi ý request nào thuộc cùng business flow.

Ví dụ structured output:

```json
{
  "candidate": "bookingId",
  "source": "request:create-booking $.id",
  "consumers": ["request:get-booking path"],
  "confidence": 0.91
}
```

### Validation

AI suggestion không được tự động thay case. User phải confirm và deterministic engine phải xác minh value thật sự xuất hiện ở source/consumer.

### Deterministic fallback

- literal equality;
- GUID detection;
- repeated-value matching;
- JSON path captures;
- configured normalization.

### Risks

- gửi HAR data ra model;
- hallucinated dependency;
- cost/latency;
- làm format khó dự đoán.

Vì vậy AI không nằm trong MVP.

## 14. Các bài toán kỹ thuật đáng học

### 1. Secret detection và privacy-preserving capture

HAR có thể chứa token, session data hoặc PII trong nhiều vị trí. Cần pipeline:

```text
parse → classify sensitivity → redact → only then log/persist
```

Kỹ năng: secure logging, data minimization, secret scanning.

### 2. Dynamic value dependency detection

Response `id` của request A có thể đi vào path/body của request B.

Kỹ năng: value provenance, dependency graph, deterministic heuristics.

### 3. Semantic response diff

Text diff dễ fail vì timestamp/order/trace IDs.

Kỹ năng: canonical JSON, ignore paths, structural comparison, typed assertions.

### 4. Safe replay of side-effecting APIs

POST/DELETE có thể tạo dữ liệu thật.

Kỹ năng: environment guardrails, explicit confirmation, idempotency thinking, dry-run design.

### 5. Reproducibility

Một case tốt phải chạy lại sau nhiều tuần dù token/IDs thay đổi.

Kỹ năng: fixtures, variable injection, environment abstraction, deterministic execution.

## 15. Rủi ro và cách xử lý

### Sensitive data leak

**Risk:** HAR chứa credentials/PII.

**Mitigation:** never upload by default; sanitizer before persist/log; raw HAR marked temporary; generated cases reject known secret patterns; optional `hardiff scan` command.

### Destructive replay

**Risk:** replay POST/DELETE lên production.

**Mitigation:** production host denylist/default safety mode; non-GET methods require environment `allowMutations=true`; DELETE additionally requires explicit path allowlist.

### False regression

**Risk:** timestamps/order/request IDs gây fail.

**Mitigation:** semantic JSON diff + ignore rules + assertions trên fields quan trọng.

### Over-automation

**Risk:** variable detector biến mọi GUID thành dynamic capture.

**Mitigation:** suggestions only; user confirms; V1 chỉ auto-detect exact value reuse.

### Unsupported protocols

**Risk:** WebSockets/SSE/service-worker-heavy flows.

**Mitigation:** report `Unsupported` rõ ràng; không giả vờ replay được.

### Scope creep

**Risk:** biến thành Postman clone.

**Mitigation:** focus HAR import → sanitized replay case → regression diff. Không làm generic API designer/workspace trong MVP.

### Maintenance burden

**Risk:** HAR variants/tool-specific extensions.

**Mitigation:** tolerant parser + fixture corpus từ Chrome/Edge/Playwright; versioned internal model.

### 5 scenario quan trọng nhất

1. HAR có 200 entries nhưng chỉ 6 API requests đúng host → generated case chỉ chứa 6.
2. Response A trả GUID và request B dùng GUID trong path → capture/reuse chạy đúng.
3. Response chỉ khác `requestId` và `updatedAt` đã ignore → test pass.
4. HAR chứa Authorization header → generated case chỉ chứa `${AUTH_TOKEN}`, không raw value.
5. Case có DELETE và target host không nằm trong mutation allowlist → run bị block trước khi gửi request.

## 17. Cách đo dự án có hữu ích hay không

### Product usage metric

Số HAR được chuyển thành reusable regression cases.

### Time saved

Đo thời gian từ lúc nhận HAR tới lúc có reproducible API test trước và sau HarDiff.

Target validation cá nhân hợp lý: một flow 5–10 API calls có thể chuyển thành regression case trong **dưới 10 phút** sau khi tool trưởng thành. Đây là mục tiêu thử nghiệm, không phải claim thị trường.

### Task completion rate

Tỷ lệ import thành công → generated case chạy được trên target environment.

### Error rate

- parse failures;
- replay infrastructure failures;
- false regression do normalization;
- missing capture failures.

### Repeated use

Nếu sau 4 tuần developer tiếp tục dùng HarDiff cho bug mới, utility được chứng minh.

### Technical reliability

- 0 known secret raw value persisted/logged trong test corpus.
- 100% destructive requests đi qua safety policy.
- generated case schema backward compatible trong cùng major version.

### AI quality metric

Không áp dụng cho MVP.

## Research notes

### Confirmed facts

- Chrome DevTools hỗ trợ export HAR và mặc định có lựa chọn sanitized HAR loại `Cookie`, `Set-Cookie`, `Authorization` headers.
- HAR là định dạng archival cho HTTP transaction data và được nhiều browser/network tools sử dụng.
- Playwright hỗ trợ record HAR và replay bằng `routeFromHAR`.
- Playwright có URL filtering, update modes và HAR content options.
- Playwright documentation nêu limitation với requests intercepted bởi Service Workers khi HAR routing.

### Observations

Existing tooling đã giải quyết capture và mock rất tốt. Khoảng trống phù hợp cho HarDiff là **HAR → sanitized, parameterized, reviewable real-API regression case**.

### Assumptions

- Developer/QA thường có HAR hoặc có thể export HAR khi bug khó tái hiện.
- Việc giảm thời gian viết lại request sequence tạo đủ giá trị để duy trì tool.
- File-based test format dễ được chấp nhận hơn database-centric workspace cho MVP.

### Recommendation

Build **inspect + sanitize CLI trước**, sau đó mới thêm replay. Nếu sanitized request list không tạo giá trị từ 2–3 HAR thật, dừng project trước khi xây UI hoặc dependency inference.
