# Ý tưởng hôm nay: ConfigDrift Guard — Configuration Contract & Drift Detector cho .NET

## 1. Tóm tắt ý tưởng

ConfigDrift Guard là một công cụ developer/self-hosted giúp **định nghĩa “configuration contract” cho ứng dụng .NET, so sánh cấu hình giữa local/staging/production mà không cần lộ giá trị secret, phát hiện key bị thiếu/thừa/sai kiểu/sai nguồn và cảnh báo khi cấu hình drift khỏi baseline**. Nó phù hợp cho backend developer hoặc solo builder có nhiều `appsettings.*.json`, environment variables, Docker secrets, Azure App Configuration hoặc Key Vault và thường gặp lỗi kiểu “code đúng nhưng production fail vì config khác môi trường”.

- Người dùng chính: .NET backend developer, solo builder, team nhỏ vận hành nhiều môi trường.
- Bài toán chính: cấu hình phân tán, override theo thứ tự provider và drift giữa môi trường rất khó nhìn thấy trước khi deploy.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Ứng dụng ASP.NET Core có thể nhận configuration từ nhiều provider: JSON, environment variables, command line, user secrets, Azure Key Vault, Azure App Configuration và custom provider. Microsoft xác nhận các provider được đọc theo thứ tự cấu hình và provider sau có thể override provider trước, vì vậy giá trị cuối cùng tại runtime có thể khác đáng kể so với những gì developer nhìn thấy trong một file `appsettings.json`.

Nguồn chính thức:

- [Microsoft Learn — Configuration in ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/configuration/?view=aspnetcore-10.0)
- [Microsoft Learn — Azure Key Vault configuration provider in ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/security/key-vault-configuration?view=aspnetcore-10.0)

### Confirmed facts

1. ASP.NET Core hỗ trợ nhiều configuration provider và thứ tự provider ảnh hưởng đến giá trị cuối cùng.
2. Azure Key Vault có provider riêng cho ASP.NET Core và hỗ trợ polling/reload thông qua `ReloadInterval`.
3. GitHub secret scanning/push protection tập trung vào phát hiện credential bị hardcode hoặc bị push vào repository; nó không giải quyết bài toán semantic config drift giữa các môi trường runtime.

Nguồn:

- [GitHub Docs — Secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning)
- [GitHub Docs — Push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection)

### Observation

Trong nhiều project nhỏ, developer thường biết “những key nào đáng lẽ phải tồn tại” thông qua `IOptions<T>` class hoặc code truy cập `builder.Configuration[...]`, nhưng không có một artifact trung tâm mô tả:

- key bắt buộc;
- kiểu dữ liệu;
- có phải secret hay không;
- nguồn nào được phép cung cấp;
- môi trường nào cần key đó;
- giá trị có được giống nhau giữa environments hay không;
- key nào đã bị orphan sau khi code thay đổi.

### Assumption cần kiểm chứng

Developer/team nhỏ sẽ thấy hữu ích nếu có một tool chạy trong CI hoặc CLI để trả lời trước deploy:

> “Production đang thiếu 3 keys, staging có 2 keys không còn dùng, một secret đang xuất hiện trong file JSON thay vì secret store, và giá trị cấu hình feature flag giữa staging/prod khác baseline.”

Hiện workaround phổ biến là:

- đọc thủ công `appsettings.*.json`;
- kiểm tra Azure Portal hoặc environment variables;
- grep code để tìm config key;
- đợi application startup fail;
- viết script PowerShell/bash riêng cho từng project;
- dùng `ValidateOnStart` nhưng chỉ phát hiện lỗi tại runtime của một environment, không cho cái nhìn drift cross-environment.

Điểm yếu của cách hiện tại là các công cụ bị rời rạc và thường không tạo được một diff an toàn, repeatable giữa nhiều nguồn cấu hình.

## 3. Người dùng mục tiêu

**Primary user:** .NET backend developer sở hữu hoặc vận hành 2–5 service nhỏ trên local/staging/production.

### User profile

- Dùng ASP.NET Core và `IOptions<T>`.
- Có `appsettings.json`, environment variables và ít nhất một secret store hoặc CI secret.
- Deploy bằng Docker, Azure App Service, Azure Container Apps hoặc VPS.

### Context of use

Tool được chạy:

- trước deploy;
- trong CI;
- sau khi thay đổi config;
- khi debug lỗi chỉ xuất hiện ở staging/production;
- định kỳ để phát hiện orphaned hoặc unexpected config.

### Main pain point

Không biết chắc cấu hình runtime của các môi trường có cùng “shape” và đúng policy hay không mà không cần xem trực tiếp secret value.

### Current workaround

Spreadsheet, README, wiki, shell script, manual portal inspection hoặc chỉ dựa vào startup validation.

### Reason họ sẽ thử solution

Một lệnh duy nhất:

```bash
configdrift check --environment production
```

trả về kết quả có thể dùng ngay trong CI:

```text
FAIL: 3 blocking configuration issues

Missing:
  Payments:ApiKey              [required, secret]
  Storage:ContainerName        [required]

Wrong source:
  Jwt:SigningKey
  expected: secret-store
  actual: appsettings.Production.json

Unexpected:
  LegacyFeature:Endpoint
```

## 4. Giải pháp đề xuất

ConfigDrift Guard có hai thành phần logic chính:

1. **Configuration Contract** — mô tả schema và policy mong đợi.
2. **Environment Snapshot** — snapshot chỉ chứa metadata/fingerprint, không chứa plaintext secret.

### Main workflow

Developer tạo contract:

```yaml
app: Billing.Api
keys:
  Database:ConnectionString:
    required: true
    secret: true
    allowedSources:
      - environment
      - keyvault

  Features:EnableNewCheckout:
    type: boolean
    required: true
    secret: false

  Payments:TimeoutSeconds:
    type: integer
    min: 1
    max: 60
```

Tool sau đó đọc configuration của một environment thông qua adapter, normalize key và đánh giá:

- key tồn tại hay không;
- parse đúng type hay không;
- source provider có hợp lệ không;
- secret có xuất hiện trong nguồn không an toàn không;
- key có nằm ngoài contract không;
- fingerprint có thay đổi từ snapshot trước không.

### Input

- `config-contract.yml`.
- Một hoặc nhiều nguồn configuration:
  - appsettings JSON;
  - `.env`/environment variables;
  - Azure Key Vault metadata;
  - Azure App Configuration;
  - Docker Compose environment section;
  - CLI JSON export từ runtime agent.

### Processing

Tool normalize key về dạng canonical như:

```text
Logging:LogLevel:Default
Database:ConnectionString
Features:EnableNewCheckout
```

Sau đó apply rules.

### Output

- Console report.
- JSON report cho CI.
- Optional HTML dashboard.
- Exit code `0/1/2` theo severity.

### What is automated

- discovery;
- normalization;
- policy validation;
- drift detection;
- secret-source checks;
- snapshot comparison;
- report generation.

### What remains under user control

- contract definition;
- môi trường được phép query;
- source nào được coi là trusted;
- severity policy;
- việc approve intentional drift.

### Key differentiator

Tool không cố quản lý secrets hay thay thế Key Vault/App Configuration. Nó đóng vai trò **contract verifier** giữa code, configuration metadata và deployment environments.

### Ví dụ end-to-end

Developer thêm option:

```csharp
public sealed class MailOptions
{
    public required string Host { get; init; }
    public int Port { get; init; }
    public required string Username { get; init; }
    public required string Password { get; init; }
}
```

CI chạy ConfigDrift Guard trên staging và production.

Kết quả:

```text
staging: PASS
production: FAIL

Mail:Password missing
Mail:Port = "smtp" -> expected integer
Mail:Username source = appsettings.Production.json
policy warning: expected environment or secret-store
```

Developer sửa config trước khi release thay vì phát hiện sau deploy.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Đây là tool có thể dùng trực tiếp cho project cá nhân và work project có nhiều environments. Chỉ cần một integration bị fail do missing config là tool đã có giá trị thực tế.

### Technical learning value

Project cho cơ hội học sâu:

- ASP.NET Core configuration pipeline;
- options validation;
- secret hygiene;
- deterministic schema validation;
- config normalization;
- CI exit contracts;
- Azure identity và secret metadata access;
- diff/fingerprint design.

### Vì sao phù hợp solo developer

Core engine hoàn toàn deterministic và domain nhỏ. Không cần SaaS backend, không cần microservice, không cần data pipeline lớn.

### Vì sao vẫn hữu ích khi chỉ có một người dùng

Developer có thể dùng nó như CLI riêng cho toàn bộ project cá nhân. Giá trị không phụ thuộc network effect.

### Điều gì làm ý tưởng thất bại

- Contract phải viết tay quá nhiều.
- False positive cao.
- Tool vô tình log secret.
- Các adapter cloud yêu cầu permission quá rộng.
- Developer cảm thấy `ValidateOnStart` + shell script là đủ.

### Lý do mạnh nhất để không build

Nếu chỉ có một application với một môi trường và configuration rất nhỏ, complexity thêm của contract riêng có thể lớn hơn lợi ích.

## 7. Luồng hoạt động

### Normal flow

Developer chạy CLI
→ load contract
→ load source adapters
→ normalize keys
→ classify source
→ validate shape/type/policy
→ tạo snapshot redacted
→ compare baseline
→ tạo report
→ trả exit code.

### CI flow

PR/build
→ build app
→ generate/resolve config metadata
→ `configdrift check`
→ blocking violation → exit `1`
→ pipeline fail
→ developer sửa contract hoặc deployment config.

### Alternative flows

#### Key bị thiếu

- `required=true` → error.
- `required=false` → ignore hoặc warning.

#### Value là secret

Tool không render value. Output chỉ có:

```text
Database:ConnectionString = <redacted>
```

#### Source không truy cập được

Ví dụ Key Vault timeout:

```text
ENVIRONMENT_UNAVAILABLE
```

Không được coi nhầm thành “mọi key đều missing”.

#### Intentional drift

User approve fingerprint mới:

```bash
configdrift baseline approve production
```

Approval cần tạo commit change rõ ràng để audit.

#### Duplicate source

Nếu một key xuất hiện trong nhiều providers, report effective provider + shadowed providers:

```text
Feature:Enabled
effective: environment
shadowed: appsettings.Production.json
```

## 11. API và tích hợp

### ASP.NET Core configuration conventions

**Purpose:** normalize key structure và hiểu provider ordering.

- Authentication: không cần.
- Cost/rate limit: không có.
- Privacy: local config có thể chứa secret.
- Fallback: parse JSON/env snapshot thủ công.

Nguồn: [Microsoft Learn — Configuration in ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/configuration/?view=aspnetcore-10.0)

### Azure Key Vault — later

**Purpose:** chỉ lấy metadata/existence và optional fingerprint logic cho secret version.

- Authentication: `DefaultAzureCredential`/Managed Identity.
- Cost: Key Vault request có pricing và service limits; scan frequency phải có giới hạn.
- Privacy: không log secret value.
- Permission: chỉ cấp quyền tối thiểu cần thiết; nếu có thể chỉ dựa vào metadata/version thay vì value.
- Fallback: import một redacted environment snapshot do deployment pipeline tạo.

Nguồn: [Microsoft Learn — Key Vault configuration provider](https://learn.microsoft.com/en-us/aspnet/core/security/key-vault-configuration?view=aspnetcore-10.0)

### GitHub Secret Scanning

**Purpose:** không phải dependency của core; dùng như lớp bảo vệ bổ sung cho repository chứa contract/baseline.

- Authentication: tùy REST API usage.
- Cost/availability: phụ thuộc repository/account plan và feature.
- Privacy: không gửi secret vào tool chỉ để scan.
- Fallback: local regex scanner.

Nguồn:

- [GitHub Docs — Secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning)
- [GitHub Docs — REST API for secret scanning](https://docs.github.com/en/rest/secret-scanning/secret-scanning)

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem là deterministic validation. Required key, type mismatch, source mismatch, missing key và drift fingerprint đều nên được xử lý bằng code thông thường.

AI có thể trở thành optional feature về sau cho:

- giải thích report bằng ngôn ngữ tự nhiên;
- gợi ý contract từ codebase;
- nhóm finding tương tự.

Nhưng AI không được quyết định pass/fail CI.

### Nếu thêm AI sau này

Input chỉ nên gồm:

- key name;
- finding code;
- non-secret metadata;
- contract rule.

Không gửi raw secret.

Expected output:

```json
{
  "summary": "...",
  "recommendedAction": "..."
}
```

Output AI chỉ mang tính advisory.

## 14. Các bài toán kỹ thuật đáng học

### 1. Configuration provider precedence

Phải mô hình hóa effective value khi nhiều source định nghĩa cùng key.

**Skill improved:** hiểu sâu ASP.NET Core configuration pipeline và override behavior.

### 2. Secret-safe fingerprinting

Muốn biết “secret có đổi không” mà không lưu secret.

Có thể dùng HMAC:

```text
HMAC(environment-specific-key, secret-value)
```

thay vì plain SHA-256 để giảm rủi ro dictionary attack với secret có entropy thấp.

**Skill improved:** secure hashing, key management, privacy-preserving comparison.

### 3. Deterministic diff engine

Cùng input phải sinh cùng report/order để CI review ổn định.

**Skill improved:** canonicalization, immutable models, reproducible tooling.

### 4. Adapter abstraction

Mỗi source có semantics khác nhau nhưng cần đưa về cùng model.

**Skill improved:** ports/adapters design, boundary normalization.

### 5. Safe runtime discovery

Nếu sau này đọc effective config trực tiếp từ ASP.NET Core runtime, phải đảm bảo endpoint không biến thành đường leak config.

**Skill improved:** security boundary, least privilege, secure diagnostics.

## 15. Rủi ro và cách xử lý

### Secret leakage

**Risk:** report hoặc exception log vô tình chứa raw value.

**Mitigation:**

- `SecretValue` type riêng không override `ToString()` bằng raw value;
- centralized redaction;
- snapshot serializer không có field raw;
- security tests search known fixture secret trong toàn bộ output.

### False positives

**Risk:** environment intentionally khác nhau nhưng tool báo lỗi.

**Mitigation:** rule hỗ trợ `environments`, severity và explicit baseline approval.

### Contract maintenance burden

**Risk:** developer ngừng cập nhật contract.

**Mitigation:** generator + CI cảnh báo unused/new keys + contract versioning.

### Cloud permissions

**Risk:** adapter yêu cầu quyền quá rộng.

**Mitigation:** local snapshot mode là default; cloud direct-access chỉ optional và documented least privilege.

### Fingerprint security

**Risk:** SHA hash raw secret có thể tiết lộ thông tin cho secret yếu.

**Mitigation:** dùng HMAC với key riêng, hoặc chỉ dùng provider version metadata nếu có.

### Scope expansion

**Risk:** biến tool thành full secret manager/deployment platform.

**Mitigation:** core charter: **detect and validate, never become source of truth for secrets**.

### Provider incompatibility

**Risk:** generic model không biểu diễn đủ semantics của từng provider.

**Mitigation:** expose source-specific metadata nhưng giữ validation core nhỏ.

- run CLI process;
- kiểm tra console, JSON report và exit code.

### Failure-path tests

- malformed YAML;
- missing source;
- invalid environment variable;
- permission denied.

### Security tests

- fixture secret không xuất hiện trong any output.

### 5 scenario quan trọng nhất

1. Required key missing → exit code fail.
2. Boolean key có value `abc` → type violation.
3. Secret tồn tại trong `appsettings.Production.json` nhưng policy chỉ cho `keyvault/environment` → fail.
4. Secret thay đổi → fingerprint thay đổi nhưng report không chứa plaintext.
5. Key được intentional override bằng environment variable → tool hiển thị effective source đúng và không báo duplicate sai.

### Contract sample

```json
{
  "keys": [
    {
      "path": "Database:ConnectionString",
      "required": true,
      "secret": true,
      "type": "string"
    },
    {
      "path": "Features:EnableBeta",
      "required": true,
      "secret": false,
      "type": "boolean"
    },
    {
      "path": "Worker:MaxConcurrency",
      "required": true,
      "secret": false,
      "type": "integer"
    }
  ]
}
```

### Broken production sample

```json
{
  "Features": {
    "EnableBeta": "not-a-bool"
  },
  "Worker": {
    "MaxConcurrency": "8"
  }
}
```

Expected report:

```text
ConfigDriftGuard
Environment: Production

ERROR Database:ConnectionString
  Required configuration key is missing.

ERROR Features:EnableBeta
  Expected boolean but received "not-a-bool".

PASS Worker:MaxConcurrency
  integer = 8

Result: FAILED (2 errors)
```

### First vertical slice

Implement:

```bash
dotnet run --project src/ConfigDriftGuard.Cli -- \
  samples/config-contract.json \
  samples/appsettings.Production.json
```

Flow:

```text
load contract
→ flatten JSON keys
→ validate existence
→ validate primitive type
→ print findings
→ Environment.ExitCode = findings.Any(Error) ? 1 : 0
```

### Verification checklist

- [ ] Nested JSON được flatten đúng thành `A:B:C`.
- [ ] Missing required key tạo `ERROR`.
- [ ] `not-a-bool` bị phát hiện.
- [ ] String `"8"` được policy quyết định rõ: strict fail hoặc parse integer; MVP chọn một rule và test cố định.
- [ ] Output không in raw value cho key `secret=true`.
- [ ] Process trả exit code `1` khi có error.
- [ ] Sau khi sửa sample đúng contract, process trả exit code `0`.
- [ ] Có ít nhất 5 unit tests pass.

### Stop condition

Dừng session khi command này hoạt động end-to-end:

```bash
dotnet run --project src/ConfigDriftGuard.Cli -- \
  samples/config-contract.json \
  samples/appsettings.Production.json
```

và terminal hiển thị ít nhất một `missing key`, một `type mismatch`, đồng thời exit code phản ánh đúng trạng thái. Không làm YAML, Azure Key Vault, Roslyn, dashboard hay AI trong coding session đầu tiên.
