# Ý tưởng hôm nay: NetworkProof — Nhật ký bằng chứng chất lượng Internet tại nhà

## 1. Tóm tắt ý tưởng

**NetworkProof** là một ứng dụng self-hosted chạy nền để đo định kỳ khả năng truy cập Internet, DNS resolution, latency, packet loss và thời gian mất kết nối, sau đó biến dữ liệu thành một timeline dễ hiểu để người dùng biết sự cố nằm ở Wi-Fi/LAN, DNS hay đường Internet bên ngoài. Sản phẩm phù hợp với người làm việc từ xa, developer, streamer hoặc hộ gia đình thường gặp tình trạng mạng chập chờn nhưng không có bằng chứng lịch sử khi cần tự chẩn đoán hoặc làm việc với ISP.

- **Project size:** Medium
- **Estimated MVP time:** 10–14 ngày làm ngoài giờ
- **Core differentiator:** không phải speed-test đơn lẻ; trọng tâm là **continuous evidence + incident reconstruction**.

## 2. Bài toán thực tế

Một sự cố Internet phổ biến là “mạng lúc được lúc không”. Khi người dùng chạy speed test sau đó, kết quả có thể lại bình thường nên rất khó trả lời:

- Mất mạng bắt đầu lúc nào?
- Kéo dài bao lâu?
- Gateway nội bộ có còn reachable không?
- DNS hỏng hay toàn bộ Internet hỏng?
- Chỉ một dịch vụ không truy cập được hay nhiều endpoint cùng fail?
- Latency tăng trước khi mất kết nối hay không?

Người dùng hiện thường xử lý bằng ping thủ công, restart modem/router, chạy speed test tại thời điểm phát hiện, chụp ảnh lỗi hoặc gọi ISP và mô tả bằng trí nhớ. Các cách này thiếu lịch sử liên tục và khó phân biệt các lớp lỗi.

### Fact đã xác nhận

Cloudflare có tài liệu riêng về **Aggregated Internet Measurement** và mô tả mục tiêu là giúp hiểu chất lượng kết nối Internet để nhận biết khi nào kết nối tốt hoặc xấu. Nguồn: [Cloudflare Speed documentation](https://developers.cloudflare.com/speed/).

RIPE Atlas là một mạng lưới toàn cầu các probe dùng để đo **Internet connectivity and reachability** theo thời gian thực. Phần lớn dữ liệu RIPE Atlas được công khai; hệ thống cũng hỗ trợ measurement, result API, ping statistics và user-defined measurements. Nguồn: [RIPE Atlas — What is RIPE Atlas?](https://atlas.ripe.net/docs/getting-started/what-is-ripe-atlas/).

### Observation

Các công cụ như speed test rất hữu ích để đánh giá tại một thời điểm, còn monitoring platform chuyên nghiệp thường được thiết kế cho server/network engineer. Có khoảng trống cho một công cụ cá nhân đơn giản hơn, chạy trong nhà và trả lời câu hỏi thực tế: **“Trong 7 ngày qua mạng nhà tôi đã hỏng như thế nào?”**

### Assumption cần kiểm chứng

Người dùng sẽ thấy giá trị nếu dashboard giúp phân loại được tối thiểu ba loại sự cố: local gateway unreachable, DNS failure nhưng Internet IP vẫn reachable, và upstream Internet outage. Nếu chỉ thu thập ping nhưng không giải thích được sự cố, sản phẩm sẽ không khác đáng kể so với script shell đơn giản.

## 3. Người dùng mục tiêu

### Primary user

Người làm việc tại nhà sử dụng Internet cho meeting, remote desktop, coding, gaming hoặc streaming và thỉnh thoảng gặp sự cố mạng không ổn định.

### Context of use

NetworkProof chạy 24/7 trên mini PC, Raspberry Pi, NAS, máy Windows/Linux luôn bật hoặc Docker host trong mạng gia đình. Người dùng chỉ mở dashboard khi vừa gặp lag/mất mạng, muốn xem xu hướng 24h/7 ngày hoặc chuẩn bị báo sự cố cho ISP.

### Main pain point

Không có dữ liệu lịch sử đủ rõ để biết lỗi xảy ra ở đâu và khi nào.

### Current workaround

- `ping 8.8.8.8 -t`
- browser speed test
- ghi chú thủ công
- router logs khó đọc
- ứng dụng monitoring server quá nặng cho nhu cầu gia đình

### Reason to try

Cài một lần rồi gần như không cần thao tác; khi sự cố xảy ra đã có dữ liệu trước đó.

## 4. Giải pháp đề xuất

NetworkProof thực hiện nhiều probe nhẹ theo chu kỳ, ví dụ mỗi 15–30 giây: ping/default gateway, DNS resolve một hostname ổn định, TCP connect/HTTPS request đến một hoặc hai endpoint công khai, ping một IP Internet và optional traceroute chỉ khi incident bắt đầu.

### Input

- gateway IP
- DNS resolver(s)
- test hostname
- external IP targets
- HTTP endpoint
- interval
- timeout
- retention period

### Processing

Mỗi vòng đo tạo một `ProbeBatch` chứa kết quả từng probe. Rule engine phân loại tình trạng thành `Healthy`, `LocalNetworkFailure`, `DnsFailure`, `InternetReachabilityFailure`, `HighLatency`, `PartialServiceFailure` hoặc `Unknown`.

### Output

Dashboard hiển thị uptime theo ngày, số incident, longest outage, median/p95 latency, DNS failure count, timeline sự cố và incident detail với bằng chứng trước/trong/sau sự cố.

### Automated

- chạy probe
- phát hiện incident
- gộp các sample liên tiếp thành một outage
- tính metrics
- retention cleanup
- optional notification

### User control

Người dùng quyết định endpoint nào được đo, ngưỡng latency, có bật traceroute hay không, retention và export report.

### Key differentiator

Không cố đo “Internet speed” liên tục vì việc tải dữ liệu thường xuyên vừa tốn băng thông vừa dễ gây nhiễu. MVP tập trung vào **availability, latency, DNS và incident evidence**.

### Ví dụ end-to-end

20:14 người dùng đang họp thì Teams lag. Đến 20:16 mạng bình thường lại. Khi mở NetworkProof, timeline cho thấy gateway vẫn ping được toàn thời gian, DNS queries vẫn thành công, hai external IP cùng timeout 94 giây và HTTP probe fail cùng thời điểm. Ứng dụng phân loại incident là `Probable upstream Internet outage` thay vì lỗi Wi-Fi nội bộ.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Có giá trị cá nhân ngay từ ngày đầu vì dữ liệu lịch sử chỉ hữu ích nếu được thu thập **trước khi** sự cố xuất hiện.

### Technical learning value

Dự án chạm vào network diagnostics, background processing, time-series aggregation, incident state machine, retention, idempotency, Linux/Windows networking và observability.

### Suitable for solo developer

Core MVP chỉ cần một service, SQLite/PostgreSQL và dashboard đơn giản. Không cần Kafka, Prometheus cluster hay distributed tracing.

### Useful with few users

Ngay cả chỉ dùng tại nhà, project vẫn có giá trị lâu dài.

### What would make it fail

Nếu classification thường xuyên sai hoặc quá nhiều false positive do endpoint mục tiêu tạm lỗi, user sẽ mất niềm tin.

### Strongest reason not to build

Nếu mục tiêu chỉ là biết “mạng có đang up không”, một script ping hoặc công cụ uptime có thể đã đủ. NetworkProof chỉ đáng làm nếu incident reconstruction và multi-layer diagnosis thực sự tốt hơn.

## 7. Luồng hoạt động

Scheduler tick → load probe configuration → execute probes concurrently với bounded timeout → normalize result → store `ProbeSample` → incident classifier đọc current + recent samples → mở/cập nhật/đóng incident → update aggregate metrics → optional notification → retention job xóa raw samples quá hạn.

### Alternative flow: ICMP bị chặn

Một số endpoint không trả ICMP. Hệ thống đánh dấu probe capability, dùng TCP connect tới 443 hoặc HTTP probe và không coi riêng ICMP failure là Internet outage.

### DNS failure

Gateway success + external IP success + hostname resolution fail → classify `DnsFailure`.

### Local network failure

Gateway fail đồng thời nhiều external probe fail → classify `LocalNetworkFailure` hoặc `Local path unavailable`.

### Partial external failure

Một endpoint fail nhưng endpoint khác success → không mở global outage; classify `PartialServiceFailure`.

### Process restart

Khi app restart, incident đang mở phải được khôi phục từ DB thay vì tạo incident trùng.

## 8. Kiến trúc đề xuất

### Architecture style

**Modular Monolith** với các module `Monitoring`, `IncidentDetection`, `Metrics`, `Reporting` và `Notifications`.

### Frontend

Vue 3 + lightweight chart library.

### Backend

ASP.NET Core Web API + hosted worker.

### Database

SQLite cho single-node MVP. Chuyển PostgreSQL nếu có nhiều agent, raw sample volume lớn hoặc cần richer reporting.

### Background worker

`BackgroundService` chạy monitoring loop.

### Queue

Không cần. Một bounded `Channel<T>` trong process có thể dùng nếu muốn tách probe execution và persistence, nhưng không bắt buộc ở bản đầu.

### Cache

Không cần Redis.

### File storage

Chỉ cần export report; lưu local filesystem.

### Authentication

Single-user self-hosted có thể dùng local admin account. Nếu chỉ bind LAN thì prototype có thể trì hoãn auth, nhưng production nên có auth nếu expose ra Internet.

### External APIs

Không bắt buộc. RIPE Atlas chỉ là optional correlation source về sau.

### AI

Không cần.

### Logging

Structured `ILogger` với event ID cho probe/incident transition.

### Monitoring

App nên tự có `/healthz`, nhưng tránh monitoring chính nó bằng cùng một process duy nhất nếu cần reliability cao hơn.

### Deployment

Docker Compose hoặc systemd/Windows Service.

## 11. API và tích hợp

### 1. DNS/ICMP/HTTP chuẩn hệ điều hành

**Purpose:** core measurement.

**Auth:** không cần.

**Cost:** gần như zero.

**Privacy:** chỉ lưu target và metrics, không inspect traffic người dùng.

**Fallback:** TCP 443 nếu ICMP unavailable.

### 2. RIPE Atlas — optional later

RIPE Atlas cung cấp public measurement data và API; user-defined measurements dùng credit system. Nguồn: [RIPE Atlas docs](https://atlas.ripe.net/docs/getting-started/what-is-ripe-atlas/).

**Purpose:** so sánh outage tại nhà với measurement bên ngoài.

**Auth:** public data phần lớn không cần account; tạo custom measurement cần account/credits tùy use case.

**Rate/cost concern:** API rate limits và credit system phải được tôn trọng.

**Fallback:** bỏ correlation; core app vẫn hoạt động.

### 3. Telegram Bot API — optional

Purpose: báo outage/recovery. MVP có thể để notification là phase 2.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Classification của MVP nên hoàn toàn deterministic vì input nhỏ và có cấu trúc, rule dễ kiểm thử, cần explainability và không nên hallucinate nguyên nhân sự cố.

Ví dụ rule:

```text
GatewayFail && ExternalFail => LocalNetworkFailure
GatewayOk && ExternalIpOk && DnsFail => DnsFailure
GatewayOk && ExternalIpFailOnMultipleTargets => InternetReachabilityFailure
OnlyOneExternalTargetFail => PartialServiceFailure
```

AI có thể thêm về sau để viết report bằng ngôn ngữ tự nhiên, nhưng report phải dựa trên metrics đã tính sẵn và không được tự kết luận nguyên nhân vượt quá rule engine.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** chứng minh multi-probe timeline hữu ích hơn ping log.

**Main tasks:** chạy script 48–72 giờ trên mạng nhà; log gateway ping, public IP, DNS và HTTPS; cố tình tạo ba tình huống tắt gateway, đổi DNS sai và mô phỏng upstream outage; kiểm tra có phân biệt đúng không.

**Expected output:** CSV + chart đơn giản.

**Completion criteria:** ba loại fault cho pattern khác nhau rõ ràng.

### Phase 1 — Core MVP

**Goal:** monitoring end-to-end.

**Tasks:** probe engine, SQLite persistence, incident state machine, 24h dashboard, incident detail.

**Expected output:** self-hosted app chạy liên tục.

**Completion criteria:** một outage mô phỏng xuất hiện đúng trên timeline.

### Phase 2 — Reliability

**Goal:** monitoring không tạo dữ liệu sai khi restart/failure.

**Tasks:** retry policy, timeout, cancellation, idempotent incident transitions, retention, unit/integration tests và structured logs.

**Completion criteria:** restart app giữa incident không tạo duplicate incident.

### Phase 3 — Useful expansion

**Goal:** tạo report có ích khi troubleshooting.

**Tasks:** p95 latency, export incident report, traceroute on failure, notifications và weekly availability summary.

**Completion criteria:** xuất được report 7 ngày chứa outage duration và evidence.

### Phase 4 — Production readiness

**Goal:** chạy ổn định nhiều tháng.

**Tasks:** Docker image, backup/restore, resource limits, health checks, CI, documentation và data retention controls.

**Completion criteria:** deploy lại từ đầu và restore history thành công.

## 14. Các bài toán kỹ thuật đáng học

### 1. Multi-signal incident classification

Không dựa vào một ping đơn lẻ.

**Skill:** fault isolation, rule engine, confidence scoring.

### 2. Long-running background loop

Worker phải xử lý timeout, cancellation và restart sạch.

**Skill:** `BackgroundService`, async, cancellation tokens, graceful shutdown.

### 3. Incident state machine

Failure đầu tiên chưa chắc là outage. Cần rule như ba lần fail liên tiếp để mở incident và N success để đóng.

**Skill:** state machine, debounce, hysteresis.

### 4. Time-series retention

Raw sample tăng liên tục.

**Skill:** aggregation, retention, indexes, storage sizing.

### 5. Cross-platform network behavior

ICMP permissions và networking khác nhau giữa Windows/Linux/container.

**Skill:** capability detection, portable diagnostics.

## 15. Rủi ro và cách xử lý

### False positive do target chết

**Mitigation:** ít nhất hai external targets độc lập; không mở global incident vì một target duy nhất fail.

### ICMP bị chặn

**Mitigation:** TCP/HTTPS fallback.

### Monitoring tạo traffic quá nhiều

**Mitigation:** payload cực nhỏ, interval 15–60 giây, không chạy bandwidth test liên tục.

### Database tăng vô hạn

**Mitigation:** raw retention + daily aggregates.

### Classification bị hiểu như “ISP chắc chắn có lỗi”

**Mitigation:** dùng wording như `Probable upstream failure` và hiển thị evidence; tránh tuyên bố nguyên nhân tuyệt đối.

### Container network khác host network

**Mitigation:** document rõ host/network mode; test gateway reachability khi startup.

### Privacy

Không capture packet hoặc nội dung browsing. Chỉ lưu kết quả probe đã cấu hình.

### Maintenance burden

Giữ adapter ít, dựa vào protocol chuẩn thay vì scraping hay vendor API.

## 16. Kiểm thử

### Unit tests

Incident classifier, state transitions, aggregate metrics và retention cutoff.

### Integration tests

SQLite persistence, fake probe server và DNS/HTTP timeout behavior.

### End-to-end tests

Playwright cho dashboard load, date filter, incident detail và config edit.

### Failure-path tests

Target timeout, DNS NXDOMAIN, worker cancellation, database temporarily locked và restart during open incident.

### Security tests

Input validation cho hostname/IP; SSRF control nếu cloud edition sau này cho phép arbitrary HTTP target.

### Five most important scenarios

1. Gateway + external fail liên tiếp → mở local-path incident đúng.
2. Gateway OK + public IP OK + DNS fail → classify DNS failure.
3. Một external target fail nhưng target khác OK → không báo global outage.
4. Ba failures rồi ba successes → incident mở/đóng đúng duration.
5. Process restart khi incident đang mở → tiếp tục incident cũ, không duplicate.

## 20. Việc cần làm ngay hôm nay

### Thời lượng

**90–120 phút.**

### Development objective

Tạo vertical slice đầu tiên: một console worker chạy mỗi 10 giây, đo gateway + DNS + HTTPS, in ra một classification rõ ràng.

### Files/components to create

```text
NetworkProof/
  NetworkProof.sln
  src/
    NetworkProof.Worker/
      Program.cs
      MonitoringWorker.cs
    NetworkProof.Core/
      ProbeResult.cs
      ProbeBatch.cs
      IncidentClassifier.cs
      Probes/
        PingProbe.cs
        DnsProbe.cs
        HttpProbe.cs
  tests/
    NetworkProof.Core.Tests/
      IncidentClassifierTests.cs
```

### Setup commands

```bash
mkdir NetworkProof
cd NetworkProof

dotnet new sln -n NetworkProof
dotnet new worker -n NetworkProof.Worker -o src/NetworkProof.Worker -f net10.0
dotnet new classlib -n NetworkProof.Core -o src/NetworkProof.Core -f net10.0
dotnet new xunit -n NetworkProof.Core.Tests -o tests/NetworkProof.Core.Tests -f net10.0

dotnet sln add src/NetworkProof.Worker/NetworkProof.Worker.csproj
dotnet sln add src/NetworkProof.Core/NetworkProof.Core.csproj
dotnet sln add tests/NetworkProof.Core.Tests/NetworkProof.Core.Tests.csproj

dotnet add src/NetworkProof.Worker/NetworkProof.Worker.csproj reference src/NetworkProof.Core/NetworkProof.Core.csproj
dotnet add tests/NetworkProof.Core.Tests/NetworkProof.Core.Tests.csproj reference src/NetworkProof.Core/NetworkProof.Core.csproj
```

### First vertical slice

Cấu hình hard-code tạm:

```text
Gateway: 192.168.1.1
DNS hostname: example.com
HTTPS: https://example.com/
External IP: 1.1.1.1
Interval: 10 seconds
Timeout: 2 seconds
```

Output terminal mong muốn:

```text
20:58:10 Gateway=OK 2ms DNS=OK 21ms InternetPing=OK 34ms HTTP=OK 91ms => Healthy
20:58:20 Gateway=OK 2ms DNS=FAIL InternetPing=OK 31ms HTTP=FAIL => DnsFailure
```

### Tests cần viết ngay

1. Gateway fail + external fail → `LocalNetworkFailure`.
2. Gateway OK + external IP OK + DNS fail → `DnsFailure`.
3. Gateway OK + hai external fail → `InternetReachabilityFailure`.
4. Chỉ một target fail → `PartialServiceFailure`.
5. Tất cả OK → `Healthy`.

### Expected result

Sau buổi đầu, bạn có một agent thật chạy liên tục và phân loại được trạng thái mạng từ nhiều signal mà chưa cần database hay UI.
