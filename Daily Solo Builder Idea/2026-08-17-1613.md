# Ý tưởng hôm nay: A11y Smoke Test — Accessibility Regression Guard cho web app

## 1. Tóm tắt ý tưởng

**A11y Smoke Test** là một công cụ CLI + dashboard nhỏ giúp developer chạy các accessibility checks tự động trên những user flow quan trọng của web app, phát hiện regression như thiếu label, contrast kém, ARIA sai, focus bị che khuất hoặc component mới tạo ra vi phạm WCAG. Công cụ ưu tiên workflow thực tế cho team nhỏ: chọn 5–20 route hoặc flow quan trọng, chạy Playwright + axe-core, lưu baseline, chỉ cảnh báo khi xuất hiện lỗi mới hoặc mức độ nghiêm trọng tăng.

- **Project size:** Medium
- **Estimated MVP time:** 2–3 tuần làm ngoài giờ

Điểm khác biệt không phải là “thêm một axe wrapper”, mà là **biến accessibility thành regression gate dễ dùng cho developer**: scan theo user flow, baseline có chủ đích, diff theo lần chạy, evidence rõ ràng, và tách lỗi tự động phát hiện được khỏi các mục bắt buộc phải review thủ công.

## 2. Bài toán thực tế

### Confirmed facts

W3C khuyến nghị sử dụng phiên bản WCAG mới nhất khi xây dựng hoặc cập nhật chính sách accessibility; WCAG 2.2 hiện là W3C Recommendation và bổ sung các tiêu chí như Focus Not Obscured, Dragging Movements, Target Size và Accessible Authentication. Nguồn: https://www.w3.org/TR/wcag/ và https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/

Playwright có tài liệu chính thức cho accessibility testing bằng `@axe-core/playwright`, nhưng cũng cảnh báo rằng automated accessibility tests chỉ phát hiện được một phần vấn đề và cần kết hợp manual assessment. Nguồn: https://playwright.dev/docs/accessibility-testing

axe-core hỗ trợ nhiều rule liên quan WCAG 2.0, 2.1, 2.2 và best practices. Tài liệu dự án nêu rõ một phần các vấn đề chỉ có thể được đánh dấu `incomplete` để người dùng review thủ công. Nguồn: https://github.com/dequelabs/axe-core

### Observation

Developer thường đã có functional test hoặc Playwright test nhưng accessibility vẫn được xử lý như một audit riêng biệt. Khi component, modal, form hoặc design system thay đổi, regression accessibility có thể xuất hiện dù functional tests vẫn pass.

### Analysis

Vấn đề cần giải quyết không phải là “không có accessibility engine”, vì axe-core đã giải quyết phần đó khá tốt. Vấn đề thực tế hơn là:

- làm sao chạy accessibility checks đúng lúc UI ở trạng thái cần test;
- làm sao tránh team bỏ qua hàng trăm lỗi legacy;
- làm sao biết lỗi nào là **mới xuất hiện** sau một PR;
- làm sao lưu evidence đủ để developer sửa nhanh;
- làm sao phân biệt lỗi máy có thể kết luận với lỗi cần manual review.

### Assumption

Giả định MVP: primary user là developer hoặc QA engineer trong team web nhỏ đã có Playwright hoặc có thể chạy Chromium headless trong CI.

## 3. Người dùng mục tiêu

### Primary user

Web developer / QA automation engineer trong team nhỏ từ 1–10 người, đang phát triển SPA hoặc web app nội bộ bằng Vue, React, Angular hoặc Razor/Blazor.

### Context of use

- trước khi merge PR;
- chạy nightly regression;
- kiểm tra component mới như modal, form, menu, drawer, table;
- kiểm tra các route quan trọng như login, profile, checkout, search, admin form.

### Main pain point

Functional tests có thể pass nhưng UI vẫn có các lỗi accessibility như:

- input không có accessible label;
- button chỉ có icon mà screen reader không biết ý nghĩa;
- contrast không đủ;
- duplicate IDs;
- ARIA attribute sai;
- dialog thiếu accessible name;
- focus bị mất hoặc focus tới element không mong muốn.

### Current workaround

- chạy axe extension thủ công;
- audit định kỳ bằng Lighthouse/Accessibility Insights;
- thêm một vài test axe vào Playwright nhưng không có baseline/diff/report workflow;
- chỉ xử lý khi QA hoặc user báo lỗi.

### Reason to try this solution

Người dùng chỉ cần định nghĩa một số flow quan trọng, chạy một command, rồi nhận report “3 lỗi mới kể từ baseline” thay vì phải phân tích toàn bộ accessibility state của hệ thống mỗi lần.

## 4. Giải pháp đề xuất

A11y Smoke Test gồm một CLI chạy browser automation và một dashboard/report nhỏ.

### Main workflow

1. User tạo file `a11y-smoke.yml`.
2. Khai báo base URL và một số flow.
3. CLI dùng Playwright mở trang, thực hiện interaction.
4. Tại các checkpoint, axe-core scan DOM hiện tại.
5. Công cụ normalize kết quả thành fingerprint ổn định.
6. So sánh với baseline gần nhất.
7. Chỉ highlight:
   - violation mới;
   - violation biến mất;
   - impact tăng;
   - node count tăng đáng kể.
8. Xuất HTML/JSON report.
9. CI có thể fail theo policy.

### Input

Ví dụ:

```yaml
baseUrl: http://localhost:5173
ruleset: wcag-aa
flows:
  - name: login-page
    steps:
      - goto: /login
      - scan: initial
  - name: create-employee-modal
    steps:
      - goto: /employees
      - click: "role=button[name='Add employee']"
      - scan: modal-open
```

### Processing

- Playwright xử lý navigation/interactions.
- `@axe-core/playwright` chạy scan tại checkpoint.
- Normalizer loại bỏ dữ liệu thay đổi không quan trọng.
- Fingerprint dựa trên `ruleId + route + checkpoint + normalized selector/context`.
- Diff engine so baseline và current run.

### Output

Mỗi issue hiển thị:

- rule ID;
- impact;
- flow/checkpoint;
- affected element;
- HTML snippet đã rút gọn;
- help URL;
- trạng thái: New / Existing / Fixed / Needs review;
- screenshot optional;
- first seen / last seen.

### What is automated

- browser navigation;
- axe scan;
- normalization;
- regression diff;
- report generation;
- CI exit code.

### What remains under user control

- chọn flow quan trọng;
- xác định baseline hợp lệ;
- suppress issue có lý do;
- manual review cho vấn đề automation không thể kết luận;
- quyết định policy fail CI.

### Key differentiator

**Regression-first accessibility testing**, không phải absolute “0 violation or fail”. Điều này giúp một codebase legacy có thể bắt đầu ngay mà không phải sửa toàn bộ accessibility debt trước.

### Concrete example

Một developer sửa component `IconButton` để dùng lại ở nhiều nơi. Functional tests đều pass. PR pipeline chạy A11y Smoke Test và thấy `button-name` xuất hiện mới tại 7 nodes trong 3 flow. Report chỉ ra component và DOM snippet. Developer thêm `aria-label`, chạy lại, các regression biến mất và PR pass.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

- phát hiện regression trước khi merge;
- giảm reliance vào audit thủ công sau release;
- biến accessibility thành một phần của software quality thay vì checklist cuối dự án;
- phù hợp cho cả web app cá nhân và project công việc.

### Technical learning value

Project này luyện được:

- Playwright orchestration;
- accessibility concepts và WCAG;
- deterministic fingerprinting;
- baseline/diff design;
- CI quality gates;
- report generation;
- handling flaky browser state.

### Why suitable for a solo developer

Core engine chỉ cần:

- config parser;
- Playwright runner;
- axe adapter;
- normalization/diff;
- HTML report.

Không cần microservices, queue, ML pipeline hay hạ tầng lớn.

### Useful even with few users

Ngay cả chỉ có một người dùng, công cụ vẫn hữu ích như personal QA gate cho các side project và internal tools.

### What would make the idea fail

Nếu sản phẩm chỉ là `playwright + axe-core` với output JSON mặc định thì không đủ khác biệt.

### Strongest reason not to build it

Accessibility automation không thể chứng minh toàn bộ WCAG compliance. Playwright và axe-core đều nhấn mạnh rằng vẫn cần manual testing. Nếu sản phẩm marketing như “automatic WCAG compliance”, nó sẽ sai về mặt kỹ thuật và làm mất niềm tin. Nguồn: https://playwright.dev/docs/accessibility-testing

## 6. Phạm vi MVP

### Must have

1. CLI `a11y-smoke run`.
2. YAML config cho URL và flow đơn giản.
3. Steps: `goto`, `click`, `fill`, `waitFor`, `scan`.
4. Chromium Playwright runner.
5. `@axe-core/playwright` integration.
6. Rule profile tối thiểu: WCAG A/AA phổ biến.
7. JSON result persistence.
8. Stable fingerprint cho violations.
9. Baseline + current diff.
10. HTML report.
11. Exit code configurable:
    - fail on new critical;
    - fail on new serious;
    - never fail, report only.
12. Suppression file có reason và expiry date optional.

### Should have

- screenshot tại checkpoint;
- GitHub Actions summary;
- SARIF export;
- scan component/state cụ thể;
- trend report theo rule;
- `--update-baseline`;
- rule tags configurable;
- retries cho navigation flaky.

### Later

- authenticated reusable sessions;
- visual focus-order recording;
- keyboard-only scenario runner;
- GitHub PR comment bot;
- Azure DevOps integration;
- browser matrix;
- manual-review checklist;
- component ownership mapping;
- VS Code extension.

## 7. Luồng hoạt động

### Happy path

Developer chạy:

```bash
a11y-smoke run --config a11y-smoke.yml
```

→ config validation
→ start Playwright
→ execute flow
→ checkpoint scan
→ store raw result
→ normalize violations
→ compare baseline
→ generate report
→ calculate exit code
→ CI pass/fail.

### Alternative flow: chưa có baseline

First run:

- scan toàn bộ flow;
- report violations;
- user review;
- command `a11y-smoke baseline accept` lưu baseline.

Không auto-accept baseline vì có thể vô tình “hợp thức hóa” lỗi nghiêm trọng.

### Failure: target page unavailable

- đánh dấu flow là infrastructure failure;
- không coi là accessibility failure;
- retry có giới hạn;
- exit code riêng nếu user muốn.

### Failure: selector không tìm thấy

- capture screenshot;
- lưu step index;
- fail flow như automation error.

### Failure: axe scan trả `incomplete`

Không chuyển thành pass/fail cứng. Đưa vào section **Needs manual review**.

### Suppressed issue

Issue vẫn được lưu và hiển thị là Suppressed, kèm reason. Nếu suppression có expiry và đã hết hạn, issue trở lại trạng thái active.

## 8. Kiến trúc đề xuất

### Architecture style

**Modular monolith + CLI worker**, chưa cần service phân tán.

```text
CLI
 ├─ Config Module
 ├─ Flow Runner
 │   └─ Playwright
 ├─ Accessibility Scanner
 │   └─ axe-core
 ├─ Result Normalizer
 ├─ Baseline/Diff Engine
 ├─ Policy Engine
 └─ Report Generator
        ├─ HTML
        └─ JSON
```

### Frontend

MVP không cần SPA riêng. Static HTML report là đủ.

Sau khi có usage thực tế mới cân nhắc Vue dashboard.

### Backend

Không cần ASP.NET Core server cho first MVP. CLI local-first đơn giản hơn.

Nếu Phase 3 cần centralized history thì thêm ASP.NET Core API.

### Database

MVP dùng SQLite hoặc JSON files.

Khuyến nghị SQLite nếu muốn query trend/history dễ hơn.

### Background worker

Không cần. CI hoặc cron gọi CLI trực tiếp.

### Scheduler

Không cần tích hợp scheduler riêng. Dùng GitHub Actions cron, Azure DevOps schedule hoặc OS cron.

### Queue

Không cần.

### Cache

Không cần.

### File storage

Local directory:

```text
.a11y-smoke/
  baselines/
  runs/
  screenshots/
  reports/
```

### Authentication

MVP không cung cấp auth platform. Flow có thể dùng setup script để đăng nhập test account.

Không lưu production credentials trong config.

### External APIs

Không bắt buộc.

### AI model

Không cần cho core.

### Notification

CI output và report artifact đủ cho MVP.

### Logging

Structured console logs + JSON run metadata.

### Deployment

Primary execution target:

- developer workstation;
- GitHub Actions;
- Azure DevOps agent;
- Docker optional.

## 9. Công nghệ đề xuất

### .NET 10

Dùng **.NET 10 LTS** cho CLI/orchestrator nếu muốn giữ core logic bằng C#. Theo policy chính thức của Microsoft, .NET 10 đang ở Active support và end of support vào 14/11/2028. Nguồn: https://dotnet.microsoft.com/en-us/platform/support/policy

**Why it fits:**

- CLI mạnh;
- file/config processing tốt;
- dễ viết diff/policy engine;
- quen thuộc với stack C#.

**Simpler alternative:** viết toàn bộ bằng TypeScript/Node để Playwright integration trực tiếp hơn.

**When to outgrow:** không phải vấn đề performance; chỉ đổi kiến trúc nếu cần centralized SaaS.

### Playwright

Dùng Playwright cho browser automation. Tài liệu chính thức có ví dụ tích hợp `@axe-core/playwright` và scan tại các state UI khác nhau. Nguồn: https://playwright.dev/docs/accessibility-testing

**Simpler alternative:** chỉ scan URL tĩnh bằng axe CLI/browser driver, nhưng sẽ bỏ lỡ modal, menu, form state.

### axe-core

Accessibility engine chính.

axe-core có rule categories cho ARIA, color, forms, keyboard, language, structure, text alternatives và nhiều nhóm khác. Nguồn: https://github.com/dequelabs/axe-core/blob/develop/doc/API.md

**Simpler alternative:** Lighthouse accessibility audit.

**Why axe fits better:** dễ embed trực tiếp vào stateful Playwright flow.

### Node sidecar

Khuyến nghị ban đầu dùng một small Node runner cho `@axe-core/playwright`, gọi từ .NET CLI qua child process hoặc JSON stdin/stdout.

Lý do: giảm effort bridge Playwright .NET với axe JavaScript injection ở MVP.

Sau này có thể chuyển toàn bộ runner sang TypeScript nếu thấy C# orchestrator không đem lại giá trị đủ lớn.

### SQLite

Lưu runs, issue fingerprints, suppressions.

**Simpler alternative:** JSON files.

**Outgrow when:** cần multi-user centralized dashboard → PostgreSQL.

### GitHub Actions

Dùng CI để chạy regression gate.

**Alternative:** Azure DevOps pipeline.

### Docker

Optional. Chỉ dùng nếu cần reproducible CI environment.

## 11. API và tích hợp

### Playwright

**Purpose:** browser automation.

**Authentication:** không cần API auth; app under test có thể cần test credentials.

**Cost/rate limit:** không có API cost; cost nằm ở CI compute.

**Privacy:** browser session có thể chứa dữ liệu nhạy cảm nếu chạy against production — không khuyến nghị.

**Fallback:** local dev environment hoặc staging fixture site.

### axe-core / `@axe-core/playwright`

**Purpose:** accessibility scan.

**Authentication:** không cần.

**Cost:** open-source package.

**Privacy:** chạy trong browser context; report cần tránh lưu full DOM nếu chứa sensitive content.

**Fallback:** nếu axe fail, mark scanner failure, không coi là “no issue”.

Nguồn: https://github.com/dequelabs/axe-core và https://playwright.dev/docs/accessibility-testing

### GitHub Actions

**Purpose:** CI execution và artifact/report publishing.

**Authentication:** mặc định workflow context; MVP không cần GitHub App.

**Rate-limit concern:** hầu như không đáng kể nếu chỉ chạy test và upload artifact.

**Fallback:** local CLI / Azure DevOps.

### W3C WCAG 2.2

Không phải runtime API. Dùng như standards reference để giải thích rule mapping và manual checklist. W3C nêu WCAG 2.2 có success criteria ở ba level A, AA, AAA. Nguồn: https://www.w3.org/WAI/standards-guidelines/wcag/

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem hoàn toàn deterministic:

- browser flow;
- axe scan;
- fingerprint;
- diff;
- policy;
- report.

AI thậm chí có thể gây hại nếu tự kết luận một violation là false positive hoặc tự sửa ARIA không đúng semantics.

### AI có thể được thêm sau, nhưng chỉ optional

Possible task:

- giải thích violation bằng ngôn ngữ đơn giản;
- đề xuất candidate fix dựa trên DOM snippet;
- tạo PR comment dễ đọc.

Nhưng output phải luôn gắn nhãn suggestion và không thay thế rule engine.

Deterministic fallback: show axe help URL + raw evidence.

## 14. Các bài toán kỹ thuật đáng học

### 1. Stable fingerprinting cho dynamic DOM

Selector hoặc generated IDs có thể đổi giữa runs.

Cần học cách normalize DOM evidence thành identity đủ ổn định nhưng không merge nhầm issues khác nhau.

**Skill improved:** deterministic diffing, data normalization.

### 2. Stateful browser automation

Accessibility issue thường chỉ xuất hiện sau interaction như mở modal hoặc validation error.

**Skill improved:** robust Playwright flow design, waits, deterministic UI state.

### 3. Baseline management

Baseline không được trở thành “thùng rác ignore mọi lỗi”.

Cần explicit accept, history và suppression reason.

**Skill improved:** quality gate governance.

### 4. Failure classification

Phân biệt:

- app unavailable;
- test selector broken;
- scanner error;
- accessibility violation;
- manual review required.

**Skill improved:** production-grade automation reliability.

### 5. CI signal-to-noise

Nếu pipeline báo quá nhiều noise, developer sẽ ignore.

**Skill improved:** policy design, developer experience, actionable reporting.

## 15. Rủi ro và cách xử lý

### Automated testing coverage limitation

**Risk:** user tưởng tool chứng minh WCAG compliance.

**Mitigation:** UI/report luôn hiển thị “automated checks only”; section Needs manual review bắt buộc. Playwright chính thức cũng khuyến nghị kết hợp automation với manual và inclusive user testing. Nguồn: https://playwright.dev/docs/accessibility-testing

### Scope expansion

**Risk:** biến thành full accessibility platform.

**Mitigation:** MVP chỉ regression scan cho web apps; không làm screen reader simulator, legal compliance SaaS, mobile accessibility.

### Flaky browser tests

**Risk:** UI timing tạo false failures.

**Mitigation:** explicit waits, retry selective, failure classification, no blind sleep.

### Sensitive DOM content

**Risk:** report lưu email/token/text thật.

**Mitigation:** default chỉ lưu node snippet ngắn; redact common secret patterns; khuyến nghị chạy staging/test data.

### Baseline abuse

**Risk:** mọi issue được accept để CI xanh.

**Mitigation:** baseline update explicit; audit metadata; suppression reason; optional expiry.

### axe-core dependency

**Risk:** rule behavior thay đổi theo version.

**Mitigation:** pin tool version trong run metadata và baseline; upgrade cần explicit baseline review.

### Maintenance burden

**Risk:** browser/version compatibility.

**Mitigation:** support Chromium first; Firefox/WebKit later.

### Data-quality tests

Same input/run state phải tạo cùng fingerprint.

### Five most important scenarios

1. Baseline clean, thêm unlabeled icon button → report New serious violation.
2. Existing legacy issue trong baseline → current run không fail nếu không thay đổi.
3. Fix existing issue → report Fixed.
4. Selector của flow bị đổi → classification là Automation Failure, không phải accessibility pass/fail.
5. axe trả `incomplete` → issue nằm ở Needs Manual Review và không tự động đánh dấu compliant.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong 60–120 phút, tạo vertical slice đơn giản nhất:

**một command mở một local HTML page bằng Playwright, chạy axe-core, và in ra các violation gồm rule ID + impact + target.**

Chưa làm baseline, database hay dashboard.

### Files/components to create

```text
a11y-smoke/
  runner/
    package.json
    scan.mjs
  fixtures/
    bad-form.html
  README.md
```

### Setup commands

```bash
mkdir a11y-smoke
cd a11y-smoke
mkdir runner fixtures
cd runner
npm init -y
npm install @playwright/test @axe-core/playwright
npx playwright install chromium
```

### `fixtures/bad-form.html`

Tạo page cố tình có:

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8" />
  <title>A11y Fixture</title>
</head>
<body>
  <input type="text" />
  <button><svg aria-hidden="true"></svg></button>
  <img src="demo.png" />
</body>
</html>
```

### `runner/scan.mjs`

Vertical slice:

```javascript
import { chromium } from 'playwright';
import AxeBuilder from '@axe-core/playwright';

const browser = await chromium.launch();
const page = await browser.newPage();

await page.goto(process.argv[2]);

const result = await new AxeBuilder({ page }).analyze();

for (const violation of result.violations) {
  console.log(`\n[${violation.impact}] ${violation.id}`);
  for (const node of violation.nodes) {
    console.log(`  - ${node.target.join(' ')}`);
  }
}

await browser.close();
process.exit(result.violations.length > 0 ? 2 : 0);
```

### Run fixture

Terminal 1:

```bash
cd fixtures
python -m http.server 8080
```

Terminal 2:

```bash
cd runner
node scan.mjs http://localhost:8080/bad-form.html
```

### Expected result

Command phải phát hiện được ít nhất các lỗi liên quan missing accessible names/labels hoặc image alternative text tùy rule evaluation của axe version hiện tại, và trả exit code khác 0.

Playwright chính thức dùng `AxeBuilder.analyze()` theo cùng pattern để scan page hiện tại. Nguồn: https://playwright.dev/docs/accessibility-testing

### Verification checklist

- [ ] Chromium khởi chạy thành công.
- [ ] Fixture page load được.
- [ ] axe-core trả về `violations`.
- [ ] CLI in `ruleId`, `impact`, `target`.
- [ ] Process exit code là non-zero khi có violation.
- [ ] Sau khi sửa HTML cho có label/alt/accessible button name, số violation giảm.
- [ ] Không có database, API server hoặc UI thừa trong session đầu tiên.

### Stop condition

Dừng session ngay khi bạn chứng minh được vòng lặp:

**bad HTML → scan detects issue → fix HTML → issue disappears.**

Không xây baseline/diff trong buổi đầu. Baseline là vertical slice thứ hai.

### Observation

Tooling cho scan accessibility đã trưởng thành; cơ hội nằm ở developer workflow, regression detection và signal-to-noise hơn là phát minh thêm một rule engine.

### Analysis

Regression-first baseline phù hợp hơn cho codebase legacy vì team có thể khóa “không tạo thêm lỗi mới” trước khi xử lý dần accessibility debt cũ.

### Assumption

MVP nhắm tới web team nhỏ có khả năng chạy browser automation trong local/CI, không nhắm tới tổ chức cần formal legal compliance certification.

### Recommendation

Bắt đầu như open-source CLI, prove deterministic diff + useful PR signal trước khi thêm dashboard, SaaS hoặc AI.
