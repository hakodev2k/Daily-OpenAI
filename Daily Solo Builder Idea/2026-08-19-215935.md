# Ý tưởng hôm nay: ActionSweep — GitHub Actions Storage & Cache Janitor

## 1. Tóm tắt ý tưởng

ActionSweep là một công cụ self-hosted giúp developer nhìn thấy **artifact, cache và workflow-run storage nào đang chiếm chỗ trong GitHub Actions**, giải thích vì sao chúng tồn tại lâu, rồi đề xuất hoặc thực hiện cleanup theo policy an toàn. Nó tập trung vào một vấn đề rất thực tế: CI chạy lâu ngày tạo ra artifact/cache khó theo dõi, cache có thể bị churn/eviction, còn việc cleanup thủ công qua từng repository tốn thời gian.

- Người dùng chính: solo developer hoặc maintainer có nhiều repository dùng GitHub Actions.
- Quy mô: **Medium**.
- MVP: khoảng **1–2 tuần**.

## 2. Bài toán thực tế

**Confirmed facts:** GitHub Actions cho phép lưu build/test output dưới dạng workflow artifacts; artifact/log mặc định được giữ 90 ngày và retention có thể cấu hình. GitHub cũng cho phép xóa artifact để thu hồi storage. Dependency cache có quota theo repository và cơ chế eviction; tài liệu GitHub hiện nêu mặc định 10 GB/repository và cache không được truy cập quá thời hạn retention có thể bị loại bỏ. GitHub REST API cung cấp endpoint quản lý Actions cache và rate-limit information.

Nguồn chính thức:
- GitHub Workflow Artifacts: https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts
- Removing workflow artifacts: https://docs.github.com/en/actions/how-tos/manage-workflow-runs/remove-workflow-artifacts
- Dependency caching reference: https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching
- Actions cache REST API: https://docs.github.com/en/rest/actions/cache
- REST API rate limits: https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api

**Observation:** GitHub có UI/API cho từng phần, nhưng maintainer vẫn phải tự trả lời các câu hỏi vận hành như repository nào đang phình nhanh, cache key nào churn liên tục, artifact nào có retention quá dài, hoặc cleanup policy nào đủ an toàn.

**Assumption cần kiểm chứng:** với developer có nhiều repo CI/CD, việc kiểm tra thủ công đủ phiền để họ muốn một dashboard/policy engine nhỏ thay vì mở từng trang Actions.

## 3. Người dùng mục tiêu

MVP chỉ phục vụ **developer/maintainer cá nhân có 5–30 repository GitHub dùng Actions**.

Họ thường cần giữ test reports, Playwright screenshots, binaries hoặc dependency caches nhưng không muốn tự kiểm tra từng repo. Workaround hiện tại là GitHub UI, `gh`, REST API hoặc YAML retention riêng lẻ. Lý do thử ActionSweep: một nơi duy nhất để thấy storage inventory, candidate cleanup và estimated reclaim trước khi xóa.

## 4. Giải pháp đề xuất

Người dùng cài ActionSweep, kết nối GitHub bằng token/GitHub App với quyền tối thiểu, chọn repositories và chạy scan.

Luồng chính:

Repository list → lấy artifact/cache metadata → normalize → tính age/size/last-access → áp policy → tạo cleanup plan → người dùng approve → delete → lưu audit result.

Ví dụ: repo A có nhiều Playwright artifacts 200–500 MB từ các run cũ. Policy `failed-run artifacts: 14 days`, `successful-run artifacts: 5 days`, `never delete latest successful artifact` đánh dấu 18 artifact có thể xóa. Dashboard cho biết tổng dung lượng candidate; người dùng chọn 15 mục và bấm Execute.

Điểm khác biệt: **plan-before-delete + explainable policy + cross-repository inventory**, không phải một nút “delete old artifacts”.

## 5. Tại sao ý tưởng này đáng làm

Giá trị cá nhân xuất hiện ngay nếu bạn có nhiều GitHub Actions workflows. Dự án cũng luyện REST API pagination, rate limiting, background processing, policy evaluation, destructive-operation safety và observability.

Một người có thể xây MVP vì domain hẹp và GitHub cung cấp API chính thức. Dù chỉ có một user, nó vẫn là maintenance utility hữu ích.

Ý tưởng thất bại nếu inventory của GitHub UI/CLI đã đủ tiện với phần lớn target users. Lý do mạnh nhất để **không** build: nếu bản thân bạn chỉ có vài repo và Actions storage chưa từng gây phiền, ROI cá nhân sẽ thấp.

## 6. Phạm vi MVP

### Must have

- Kết nối GitHub bằng credential lưu ngoài database hoặc environment secret.
- Chọn repository cần theo dõi.
- Scan artifacts và Actions caches bằng REST API.
- Hiển thị size, age, expiration/last-used metadata khi API cung cấp.
- Policy đơn giản theo age + size + keep-latest-N.
- Dry-run cleanup plan.
- Explicit confirmation trước delete.
- Audit log cho từng deletion.

### Should have

- Scheduled scan hằng ngày.
- Trend storage theo ngày.
- Detect cache-key churn.
- Telegram/email notification khi vượt threshold.
- Export cleanup report Markdown/JSON.

### Later

- GitHub App multi-account.
- Organization-wide policies.
- Pull request gợi ý `retention-days` tối ưu cho workflow YAML.
- Cost/budget integration nếu API/account data phù hợp.
- Automatic cleanup với approval rules.

## 7. Luồng hoạt động

User chọn repo → backend kiểm tra quyền → enqueue scan → worker gọi GitHub API có pagination → lưu snapshot metadata → policy engine đánh giá → dashboard hiện candidate → user review → backend re-fetch item để tránh stale delete → delete → ghi audit.

Failure cases quan trọng:

- `401/403`: đánh dấu permission/auth failure, không retry vô hạn.
- `404`: resource có thể đã hết hạn/bị xóa; coi operation idempotent nếu mục tiêu là “resource absent”.
- `429`/rate limit: đọc `retry-after` hoặc rate-limit headers và defer job.
- Partial scan: snapshot mang trạng thái incomplete, không cho auto-delete dựa trên inventory thiếu.
- Delete thất bại giữa batch: lưu từng result; retry chỉ item chưa thành công.

## 8. Kiến trúc đề xuất

Dùng **modular monolith**.

- Frontend: Vue 3 dashboard.
- Backend: ASP.NET Core Web API.
- Database: PostgreSQL lưu repository config, snapshots, policy và audit.
- Background worker: Hangfire hoặc `BackgroundService` cho scan.
- Queue riêng: chưa cần; database-backed jobs đủ cho MVP.
- Cache: chưa cần Redis.
- Authentication: local single-user auth hoặc reverse-proxy auth cho self-hosted MVP.
- External API: GitHub REST API.
- AI: không cần.
- Logging: OpenTelemetry/structured logging.
- Deployment: một Docker Compose stack trên VPS/mini PC.

## 9. Công nghệ đề xuất

- **.NET 10 + ASP.NET Core**: phù hợp API/background jobs và là current LTS line trong 2026. Alternative đơn giản: console app trước khi có dashboard.
- **EF Core + PostgreSQL**: đủ cho snapshot/history. SQLite còn đơn giản hơn nếu single-user; chuyển PostgreSQL khi cần concurrent worker/web.
- **Vue 3 + Vite**: dashboard nhẹ, phù hợp CRUD + charts. Razor Pages là lựa chọn đơn giản hơn nếu muốn giảm frontend complexity.
- **Hangfire**: tiện retry/scheduling/dashboard job. `BackgroundService` đủ nếu chỉ một periodic scan.
- **Docker Compose**: deploy app + DB; chưa cần Kubernetes.
- **xUnit + Testcontainers**: integration tests với database thật.
- **GitHub Actions**: build/test chính project ActionSweep; dogfood chính CI platform đang quản lý.

## 10. Thiết kế dữ liệu ban đầu

**TrackedRepository** — repo được scan. Fields: `Id`, `Owner`, `Name`, `Enabled`, `LastScanAt`. Không lưu access token trực tiếp.

**StorageSnapshot** — tổng quan một lần scan. Fields: `RepositoryId`, `CapturedAt`, `ArtifactBytes`, `CacheBytes`, `Status`.

**StorageItem** — metadata artifact/cache. Fields: `ExternalId`, `Type`, `NameOrKey`, `SizeBytes`, `CreatedAt`, `LastAccessedAt`, `ExpiresAt`, `WorkflowRunId`, `SnapshotId`.

**CleanupPolicy** — rule declarative. Fields: `ItemType`, `MinAgeDays`, `MinSizeBytes`, `KeepLatestCount`, `Enabled`.

**CleanupExecution** — audit destructive action. Fields: `ItemExternalId`, `PlannedAt`, `ExecutedAt`, `Outcome`, `Reason`.

Raw snapshots có thể purge sau 90–180 ngày; aggregate daily metrics giữ lâu hơn.

## 11. API và tích hợp

### GitHub REST API

Purpose: repositories, Actions artifacts/caches và deletion operations. Authentication cần token/GitHub App phù hợp với repo và operation. Cần xử lý pagination, primary/secondary rate limits và least privilege. Fallback: scan thủ công qua imported JSON từ `gh api` nếu người dùng không muốn cấp credential cho service.

### Telegram Bot — optional

Purpose: threshold alerts. Bot token cần bảo vệ; không gửi repository-sensitive metadata nếu không cần. Fallback: dashboard-only alert.

Không cần scraping GitHub HTML.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Candidate cleanup phải được xác định bằng deterministic rules có thể giải thích và test. LLM sẽ làm tăng cost, latency và rủi ro khi quyết định destructive action mà không đem lại lợi ích đủ lớn.

Nếu sau này thêm AI, nó chỉ nên tóm tắt report bằng ngôn ngữ tự nhiên; AI không được trực tiếp quyết định/xóa resource.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** chứng minh pain point tồn tại trên chính repo của bạn.

Tasks: dùng GitHub API/`gh` lấy artifact/cache inventory của 5–10 repo; ghi lại tổng size, số item cũ và thời gian cần để kiểm tra thủ công.

Output: CSV/JSON inventory.

Done khi tìm được ít nhất một cleanup pattern lặp lại hoặc kết luận vấn đề không đủ lớn.

### Phase 1 — Core MVP

**Goal:** vertical slice scan → plan → delete.

Tasks: API client, repository config, artifact/cache scanner, policy engine, dry-run endpoint, confirmation delete.

Output: web page hiển thị candidate cleanup.

Done khi có thể scan một repo và xóa một test artifact/cache an toàn qua UI.

### Phase 2 — Reliability

Thêm pagination tests, rate-limit handling, idempotency, partial-scan state, retry, audit, secret handling và integration tests.

Done khi injected failures không tạo duplicate/destructive unintended operations.

### Phase 3 — Useful expansion

Thêm multi-repo dashboard, daily snapshot, churn detection, notifications và policy templates.

Done khi dashboard trả lời “repo nào cần attention?” trong vài giây.

### Phase 4 — Production readiness

Docker image, migrations, backup DB, health checks, OpenTelemetry, README, least-privilege deployment guide và restore test.

Done khi có thể redeploy trên máy sạch và phục hồi DB/config có kiểm chứng.

## 14. Các bài toán kỹ thuật đáng học

1. **Rate-limit-aware API client** — học adaptive retry, headers và backoff thay vì retry mù.
2. **Idempotent destructive workflow** — phân biệt absent resource, failed delete và duplicate execution.
3. **Snapshot consistency** — tránh ra quyết định cleanup từ scan chưa hoàn tất.
4. **Policy engine** — biến rule thành logic deterministic, explainable và testable.
5. **Least-privilege integration** — thiết kế credential scope, secret storage và audit trail.

## 15. Rủi ro và cách xử lý

- **Xóa nhầm artifact cần thiết:** dry-run mặc định, keep-latest-N, explicit approval, re-fetch trước delete.
- **API thay đổi/rate limit:** isolate GitHub client, version API headers, backoff theo response headers.
- **Credential compromise:** không log token; secret qua environment/secret store; document minimum permissions.
- **Scope creep sang full CI platform:** giữ boundary ở storage hygiene.
- **Storage data không phản ánh billing chính xác:** gọi nó là inventory/reclaim estimate, không tuyên bố billing savings nếu chưa có billing evidence.
- **Maintenance burden:** chỉ support GitHub Actions trong MVP.

## 16. Kiểm thử

Unit test policy engine; integration test EF Core/GitHub HTTP client bằng stub server; E2E test dashboard; failure-path test cho `403/404/429`; security test để chắc token không xuất hiện trong log.

Năm scenario quan trọng nhất:

1. Item mới hơn retention threshold không bao giờ thành candidate.
2. `keep latest 3` vẫn giữ đúng ba item mới nhất dù các item này lớn.
3. Scan bị lỗi giữa pagination → snapshot `Incomplete` và cleanup bị khóa.
4. Delete trả `404` sau khi item đã hết hạn → operation kết thúc idempotently.
5. Rate limit → job defer đúng thời điểm thay vì retry loop.

## 17. Cách đo dự án có hữu ích hay không

- Số repository được scan lặp lại mỗi tuần.
- Số MB/GB candidate được phát hiện và thực sự reclaimed.
- Thời gian review storage giảm so với kiểm tra thủ công.
- Tỷ lệ cleanup executions thành công.
- Số destructive false positives: mục tiêu **0**.
- Scan completion rate > 99% sau khi retry transient failures.
- Tỷ lệ user quay lại dashboard hoặc giữ scheduled scan sau 30 ngày.

## 18. Khả năng mở rộng

**Realistic:** organization view, cache-thrashing detector, workflow-level retention recommendations, Slack/Teams notification, GitHub App auth, CLI companion và self-hosted/cloud variants.

## 20. Việc cần làm ngay hôm nay

### Coding session 60–120 phút

**Objective:** tạo CLI đầu tiên nhận `owner/repo`, gọi GitHub API và in ra artifact inventory + tổng size; chưa xóa gì.

Tạo:

```text
ActionSweep.sln
src/ActionSweep.Cli/
src/ActionSweep.Core/
tests/ActionSweep.Tests/
```

Setup:

```bash
dotnet new sln -n ActionSweep
dotnet new console -n ActionSweep.Cli -o src/ActionSweep.Cli
dotnet new classlib -n ActionSweep.Core -o src/ActionSweep.Core
dotnet new xunit -n ActionSweep.Tests -o tests/ActionSweep.Tests
dotnet sln add src/ActionSweep.Cli src/ActionSweep.Core tests/ActionSweep.Tests
dotnet add src/ActionSweep.Cli reference src/ActionSweep.Core
dotnet add tests/ActionSweep.Tests reference src/ActionSweep.Core
```

Vertical slice:

1. `GitHubActionsClient` nhận `HttpClient`.
2. Implement list artifacts cho một repository với pagination tối thiểu.
3. Map response thành `ArtifactInfo`.
4. `ArtifactInventoryService` tính `Count`, `TotalBytes`, `OldestCreatedAt`.
5. CLI in table và summary.
6. Viết test bằng fake `HttpMessageHandler` cho hai trang API response.

**Expected result:** chạy CLI với một test repository và nhìn thấy danh sách artifact cùng tổng dung lượng; không có destructive endpoint nào trong code.

**Verification checklist:**

- [ ] `dotnet test` pass.
- [ ] Pagination test pass.
- [ ] Token không xuất hiện trong console/log.
- [ ] CLI xử lý repository không có artifact mà không crash.
- [ ] `403` tạo error message rõ ràng.
- [ ] Output có tổng bytes và artifact count.

**Stop condition:** dừng phiên đầu tiên ngay khi CLI có thể inventory một repository thật và tests pass. Chưa xây database, dashboard, scheduler hay delete operation trong session này.
