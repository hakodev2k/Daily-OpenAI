# Ý tưởng hôm nay: FlagJanitor — Stale Feature Flag Cleanup Assistant

## 1. Tóm tắt ý tưởng

FlagJanitor là một developer tool self-hosted giúp quét source code và metadata feature flag để tìm **flag đã hoàn tất rollout nhưng vẫn còn nằm trong code**, sau đó tạo một cleanup report có bằng chứng: flag xuất hiện ở đâu, nhánh cũ nào có thể bỏ, test nào cần sửa và mức độ an toàn để cleanup. Công cụ nhắm tới backend developer hoặc team nhỏ đang dùng feature flags nhưng không có quy trình cleanup đều đặn.

- Người dùng chính: developer vận hành codebase có nhiều feature flags.
- Bài toán chính: feature flags tạm thời biến thành technical debt vì thêm flag dễ hơn xóa flag.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Feature flags rất hữu ích cho progressive rollout, trunk-based development, kill switch và thử nghiệm. Tuy nhiên, sau khi một feature đã được rollout hoàn toàn, code thường vẫn giữ lại cả hai nhánh:

```csharp
if (featureManager.IsEnabledAsync("NewCheckout"))
{
    return NewCheckout();
}

return OldCheckout();
```

Khi `NewCheckout` đã bật 100% trong production nhiều tuần, nhánh `OldCheckout()` có thể trở thành dead code nhưng vẫn tồn tại vì cleanup không khẩn cấp bằng feature mới.

**Confirmed facts:**

- LaunchDarkly mô tả phần lớn temporary flags nên được remove sau khi hoàn tất và coi flag hygiene là một vấn đề code quality/technical debt. Tài liệu của họ có code references, stale flag health và archive checks để hỗ trợ cleanup. Nguồn: https://launchdarkly.com/docs/guides/flags/technical-debt và https://launchdarkly.com/docs/home/flags/code-references
- LaunchDarkly hiện xác định stale temporary flag dựa trên age/status và có tiêu chí “ready for code removal” hoặc “ready to archive” dựa trên trạng thái, code reference, prerequisite và evaluation. Nguồn: https://launchdarkly.com/docs/home/releases/flag-health và https://launchdarkly.com/docs/home/flags/flag-status
- Unleash cũng coi stale flags là technical debt và có lifecycle/cleanup state. Tài liệu chính thức nói rằng stale flag có thể trigger automated workflow như breaking builds hoặc mở pull request cleanup. Nguồn: https://docs.getunleash.io/concepts/technical-debt

**Observation:** các nền tảng feature management lớn đã đầu tư vào stale flag lifecycle, cho thấy việc cleanup là một nhu cầu engineering có thật, không chỉ là vấn đề lý thuyết.

**Khoảng trống mà MVP nhắm tới:** một tool local/provider-agnostic dành cho developer .NET hoặc team nhỏ, có thể chạy ngay trên repository mà không cần mua gói feature-management cao hơn và không cần gửi source code lên SaaS.

Cách xử lý hiện tại thường là:

- Search tên flag thủ công trong IDE.
- Xem dashboard provider để đoán flag nào đã stale.
- Tạo ticket cleanup rồi để backlog lâu ngày.
- Xóa branch condition thủ công và dựa vào reviewer để phát hiện lỗi.
- Chỉ cleanup khi code đã quá khó đọc.

Nhược điểm là developer khó trả lời đồng thời các câu hỏi: flag có còn được dùng không, nằm ở những file nào, nhánh nào là branch cuối cùng, có test nào còn cover branch cũ, và có thật sự đủ an toàn để bỏ không.

## 3. Người dùng mục tiêu

Primary user cho MVP là **backend developer làm việc với một hoặc vài repository .NET sử dụng feature flags**.

- User profile: Middle/Senior backend developer hoặc solo SaaS developer.
- Context: codebase có 10–100 temporary flags, deploy thường xuyên qua CI/CD.
- Main pain point: biết flag “có vẻ đã xong” nhưng cleanup mất nhiều bước và dễ bỏ sót reference.
- Current workaround: grep/search tên flag, xem dashboard provider, sửa code bằng tay.
- Reason to try: nhận được một report cụ thể “flag nào nên cleanup trước, nằm ở đâu, bằng chứng gì cho thấy có thể remove”.

MVP không cố quản lý toàn bộ rollout lifecycle. Nó chỉ tập trung vào **cleanup safety**.

## 4. Giải pháp đề xuất

Người dùng chạy:

```bash
dotnet flagjanitor scan ./src --config flagjanitor.yaml
```

Tool nhận input từ hai nhóm nguồn:

1. Source repository.
2. Optional metadata từ feature flag provider hoặc file manifest local.

Ví dụ manifest local:

```yaml
flags:
  - key: NewCheckout
    state: launched
    temporary: true
    createdAt: 2026-05-01
    lastEvaluationAt: 2026-08-01
    finalVariation: true
```

FlagJanitor sẽ:

1. Parse source code.
2. Tìm feature flag key và call sites.
3. Phân loại reference: evaluation, fallback, test, config, documentation.
4. Kết hợp metadata lifecycle.
5. Tính cleanup confidence bằng rule deterministic.
6. Tạo report Markdown/JSON.

Ví dụ output:

```text
Flag: NewCheckout
Status: Cleanup candidate
Confidence: High

Evidence:
- temporary flag
- age: 110 days
- provider state: launched
- final variation: true
- 6 code references found
- 2 test references found
- no prerequisite detected

Suggested cleanup:
1. Keep NewCheckout branch
2. Remove OldCheckout branch
3. Remove 2 obsolete tests
4. Remove flag evaluation wrapper
5. Archive flag after deployment verification
```

### Key differentiator

Tool không chỉ báo “flag stale”. Nó kết nối **flag lifecycle → source references → code cleanup plan** và chạy local.

### Ví dụ end-to-end

Developer thấy `EnableNewInvoiceFlow` đã bật 100% production từ lâu.

→ chạy FlagJanitor
→ tool phát hiện 4 `IsEnabledAsync` calls, 3 tests và 1 config reference
→ report đánh dấu “High cleanup confidence”
→ developer mở từng location
→ xóa branch cũ
→ chạy test
→ scan lại
→ tool báo `0 runtime references`
→ developer archive flag ở provider.

Automation dừng trước bước xóa code thật trong MVP; người dùng vẫn kiểm soát quyết định cuối cùng.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Ngay cả khi chỉ dùng cho repository cá nhân, tool giúp biến feature-flag cleanup từ một việc mơ hồ thành checklist có bằng chứng.

### Technical learning value

Dự án chạm tới:

- Roslyn syntax analysis.
- Static analysis.
- Git history metadata.
- Provider API integration.
- Rule engine.
- CI quality gate.
- Safe automated refactoring.

### Vì sao phù hợp solo developer

MVP có domain nhỏ: scan source, collect flag references, evaluate cleanup rules, generate report. Không cần distributed system, không cần ML, không cần dataset lớn.

### Có ích kể cả ít user

Một developer có nhiều repository vẫn có thể dùng tool định kỳ trước release hoặc code-health sprint.

### Điều gì làm ý tưởng thất bại

- Codebase dùng flag keys dynamic khiến scanner khó tìm.
- Team quá ít feature flags nên grep đã đủ.
- Provider đã cung cấp đầy đủ code references/cleanup workflow phù hợp nhu cầu.
- False positive quá nhiều làm developer mất niềm tin.

### Lý do mạnh nhất để không build

Nếu toàn bộ dự án chỉ dùng một provider thương mại có sẵn code references, flag health và cleanup workflow tốt, tool riêng có thể không tiết kiệm đủ thời gian để đáng duy trì.

## 6. Phạm vi MVP

## 7. Luồng hoạt động

### Normal flow

Developer chạy `scan`
→ validate config
→ enumerate source files
→ Roslyn parse C# syntax tree
→ identify configured feature-flag evaluation calls
→ extract literal flag keys
→ map references
→ load lifecycle metadata
→ execute cleanup rules
→ write report
→ return CI exit code.

### Example rule

```text
IF temporary = true
AND state in [launched, cleanup]
AND age >= 30 days
AND finalVariation is known
AND runtimeReferences > 0
THEN CleanupCandidate
```

Rule chỉ đưa ra recommendation, không tự xóa code.

### Alternative flows

**Dynamic key**

```csharp
await manager.IsEnabledAsync($"Tenant_{tenantId}");
```

→ scanner đánh dấu `Dynamic reference — manual review`.

**Unknown flag**

Code chứa key nhưng manifest không có.

→ báo `Unknown external state`, không kết luận safe cleanup.

**No code reference**

Manifest có flag nhưng source không còn dùng.

→ đánh dấu `Archive candidate`.

**Parser failure**

Một file syntax error.

→ report warning và tiếp tục scan các file khác; exit code tùy strict mode.

- `FlagKey`
- `Category`

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem cần tính lặp lại và độ tin cậy cao. Các việc như tìm call site, extract flag key, đánh giá age/status/reference và tạo cleanup score đều deterministic.

AI chỉ có thể là optional feature sau này để:

- giải thích một finding dài bằng ngôn ngữ tự nhiên;
- gợi ý refactor cho cấu trúc code phức tạp;
- tóm tắt cleanup PR.

Nhưng AI không nên quyết định một flag “safe to delete”. Quyết định safety phải dựa vào evidence deterministic và user approval.

## 14. Các bài toán kỹ thuật đáng học

### 1. Static analysis với Roslyn

Học cách đi từ text search sang syntax/semantic analysis, phân biệt method invocation, literal argument, helper wrapper và test reference.

### 2. Safe automation

Tool phải biết khi nào **không** nên kết luận. Kỹ năng quan trọng là thiết kế confidence/evidence thay vì auto-fix mù quáng.

### 3. Provider-agnostic domain model

LaunchDarkly, Unleash hoặc custom flags có lifecycle khác nhau. Cần normalize metadata mà không làm mất semantics quan trọng.

### 4. Incremental scanning

Repository lớn không nên parse toàn bộ mọi lần. Học content hashing, Git diff và cache invalidation.

### 5. CI quality gates

Thiết kế exit code/baseline để tool hữu ích mà không làm pipeline noisy.

## 15. Rủi ro và cách xử lý

### False positive

**Risk:** tool bảo cleanup nhưng flag vẫn cần.

**Mitigation:** không tự delete; yêu cầu nhiều evidence; confidence rõ; dynamic references luôn manual review.

### Dynamic flag keys

**Risk:** static scanner không biết runtime-generated key.

**Mitigation:** detect non-literal argument và downgrade confidence; cho phép ignore/pattern rule.

### Provider dependency

**Risk:** API thay đổi hoặc feature nằm ở paid plan.

**Mitigation:** local manifest là core source; provider connector chỉ optional.

### Scope expansion

**Risk:** biến thành feature-management platform đầy đủ.

**Mitigation:** không implement rollout/config evaluation; chỉ cleanup analysis.

### Security

**Risk:** provider token bị lộ trong logs/config.

**Mitigation:** environment variable/secret store; read-only permission; redact logs; không persist token.

### Adoption

**Risk:** team nhỏ thấy grep đủ tốt.

**Mitigation:** tập trung vào multi-evidence report + CI baseline, không cạnh tranh với simple grep ở repo 3 flags.

### Maintenance

**Risk:** nhiều SDK/helper patterns khác nhau.

**Mitigation:** pattern adapters cấu hình được, bắt đầu từ một .NET pattern rõ ràng.

## 16. Kiểm thử

### Strategy

- Unit tests cho rule engine.
- Parser tests cho nhiều C# syntax pattern.
- Integration tests scan fixture solution.
- Snapshot tests cho Markdown/JSON report.
- Failure-path tests cho malformed YAML và broken source file.
- Security tests đảm bảo token không xuất hiện trong output/log.

### 5 test scenario quan trọng nhất

1. Literal flag key trong `IsEnabledAsync` được map đúng file/line.
2. Dynamic flag expression được đánh dấu manual review, không kết luận cleanup.
3. Temporary launched flag lâu ngày + runtime references → `Cleanup candidate`.
4. Manifest flag không còn source reference → `Archive candidate`.
5. Unknown flag trong source → CI warning/error theo policy.

## 17. Cách đo dự án có hữu ích hay không

Các metric có ý nghĩa:

- **Cleanup candidates found:** số flag thực sự được xác nhận cần remove.
- **Cleanup completion rate:** % candidate được cleanup trong 30 ngày.
- **Flag debt trend:** số temporary flags có tuổi vượt threshold qua từng scan.
- **Manual investigation time:** thời gian trung bình để tìm toàn bộ references trước và sau khi dùng tool.
- **False-positive rate:** % finding developer đánh dấu không hợp lệ.
- **Scan reliability:** % scan hoàn thành không lỗi.
- **Scan duration:** thời gian trên repository thực tế.
- **Unknown reference count:** số code reference trỏ tới flag không tồn tại trong catalog.

Validation target cá nhân hợp lý: tool giúp cleanup được 3–5 stale flags và giảm ít nhất một nửa thời gian lập cleanup checklist so với search thủ công.

Monetization có thể thực tế nếu sau này cung cấp multi-repo SaaS/team analytics, nhưng giá trị mạnh nhất ban đầu là một tool dùng được ngay trong codebase cá nhân và portfolio.

Nó thể hiện các kỹ năng có giá trị với Senior .NET Developer/Architect: static analysis, developer tooling, CI integration, reliability, technical-debt management và safe automation.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong **60–120 phút**, build vertical slice:

> Scan một thư mục C# → tìm literal feature flag key → in `FlagKey / file / line` ra console.

Chưa cần YAML, provider API, Git history hay dashboard.

### Files/components cần tạo

```text
FlagJanitor.sln
src/
  FlagJanitor.Cli/
    Program.cs
    Scanning/
      CSharpFlagScanner.cs
      FlagReference.cs
tests/
  FlagJanitor.Tests/
    CSharpFlagScannerTests.cs
    Fixtures/
      SampleFeature.cs
```

### Setup commands

```bash
dotnet new sln -n FlagJanitor
dotnet new console -n FlagJanitor.Cli -o src/FlagJanitor.Cli
dotnet new xunit -n FlagJanitor.Tests -o tests/FlagJanitor.Tests
dotnet sln add src/FlagJanitor.Cli
dotnet sln add tests/FlagJanitor.Tests
dotnet add tests/FlagJanitor.Tests reference src/FlagJanitor.Cli
dotnet add src/FlagJanitor.Cli package Microsoft.CodeAnalysis.CSharp
dotnet add tests/FlagJanitor.Tests package Microsoft.CodeAnalysis.CSharp
```

### Fixture code

```csharp
public async Task Execute(IFeatureManager manager)
{
    if (await manager.IsEnabledAsync("NewCheckout"))
    {
        RunNewFlow();
    }
}
```

### First vertical slice

Implement scanner:

1. Load every `*.cs` file under supplied path.
2. Parse bằng `CSharpSyntaxTree.ParseText`.
3. Find `InvocationExpressionSyntax`.
4. Match method name `IsEnabledAsync`.
5. Read first argument nếu là `LiteralExpressionSyntax` string.
6. Get `Location.GetLineSpan()`.
7. Print:

```text
NewCheckout | Fixtures/SampleFeature.cs | line 3
```

CLI prototype:

```bash
dotnet run --project src/FlagJanitor.Cli -- ./tests/FlagJanitor.Tests/Fixtures
```

### Expected result

Console hiển thị chính xác mọi literal feature flag reference trong fixture.

### Verification checklist

- [ ] Detect được `"NewCheckout"`.
- [ ] File path đúng.
- [ ] Line number đúng.
- [ ] Một file có nhiều flags được report riêng.
- [ ] `IsEnabledAsync(variable)` không crash scanner.
- [ ] Method khác có string tương tự không bị nhận nhầm.
- [ ] Có ít nhất 3 unit tests pass.

### Stop condition

Kết thúc session ngay khi command scan một thư mục fixture và trả đúng danh sách flag key + file + line bằng Roslyn. Không làm provider API, YAML manifest, cleanup score, web UI hoặc AI trong session đầu tiên.
