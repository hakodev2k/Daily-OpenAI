# Ý tưởng hôm nay: IdempotencyLab — Retry & Duplicate Side-Effect Test Harness cho API

## 1. Tóm tắt ý tưởng

**IdempotencyLab** là một developer tool chạy local/CI giúp kiểm tra một API có thực sự an toàn trước retry, timeout và duplicate request hay không. Tool gửi cùng một business operation nhiều lần dưới các failure patterns có kiểm soát, sau đó kiểm tra database/outbox/response để phát hiện duplicate order, duplicate booking, duplicate notification hoặc các side effect bị thực hiện nhiều lần.

- Người dùng chính: backend developer xây REST APIs, background integrations hoặc payment/booking/order workflows.
- Bài toán chính: retry là cần thiết để tăng resilience nhưng có thể lặp side effect nếu endpoint không idempotent.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

Một hệ thống phân tán thường phải retry khi gặp network failure, timeout, HTTP 5xx hoặc dependency tạm thời unavailable. Vấn đề là client có thể không biết request đầu tiên đã được server xử lý hay chưa.

Ví dụ:

```text
Client → POST /orders
Server → insert order thành công
Network → response bị mất
Client → timeout
Client → retry POST /orders
Server → insert order lần thứ hai
```

### Confirmed facts

Microsoft hiện khuyến nghị dùng `Microsoft.Extensions.Resilience` và `Microsoft.Extensions.Http.Resilience` cho resilience trong .NET; các package này được xây trên Polly và hỗ trợ retry, timeout, circuit breaker, rate limiting và hedging. Nguồn: [Introduction to resilient app development — Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/core/resilience/).

Tài liệu hiện tại của Microsoft về HTTP resilience cảnh báo retry các unsafe methods có thể gây duplicate side effects. Ví dụ Microsoft nêu rõ retry một `POST` chèn record vào database có thể tạo duplicate; API cung cấp `DisableForUnsafeHttpMethods` để tắt retry cho `POST`, `PATCH`, `PUT`, `DELETE` và `CONNECT` khi phù hợp. Nguồn: [Build resilient HTTP apps — Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/core/resilience/http-resilience).

IETF HTTPAPI Working Group đã làm việc trên draft `Idempotency-Key` để hỗ trợ các phương thức không idempotent như `POST`/`PATCH` trở nên fault-tolerant. Draft mô tả key do client gửi và server dùng key/fingerprint để nhận diện retry của cùng operation. Đây vẫn là Internet-Draft/work in progress, không nên coi là một RFC hoàn tất. Nguồn: [The Idempotency-Key HTTP Header Field — IETF](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/).

ASP.NET Core hỗ trợ integration testing bằng `WebApplicationFactory<TEntryPoint>` và `TestServer`, cho phép gọi SUT bằng `HttpClient` trong test process. Nguồn: [Integration tests in ASP.NET Core — Microsoft Learn](https://learn.microsoft.com/en-us/aspnet/core/test/integration-tests?view=aspnetcore-10.0).

### Vấn đề thực tế

Developer thường test happy path:

```text
POST once
→ 201 Created
→ DB có một record
```

Nhưng ít test các tình huống:

- cùng request được gửi 2–10 lần gần như đồng thời;
- request đầu tiên commit DB nhưng response bị drop;
- client timeout rồi retry;
- retry dùng cùng `Idempotency-Key` nhưng payload khác;
- hai request cùng business key chạy race condition;
- endpoint tạo DB record đúng một lần nhưng publish message hai lần;
- endpoint trả cùng response nhưng downstream side effect vẫn bị duplicate.

### Current workaround

- viết integration test thủ công cho từng endpoint;
- Postman/Bruno gửi lại request bằng tay;
- dùng load-test tool nhưng tự viết assertion business state;
- nhìn DB/log sau khi retry;
- tin rằng unique constraint hoặc transaction đã đủ.

Các cách này giải quyết được từng case nhưng không tạo một workflow reusable để **mô phỏng ambiguity của network + kiểm chứng business side effect**.

### Assumption cần validate

Tool đáng làm nhất cho endpoint tạo giá trị thật: order, booking, payment request, user provisioning, notification request hoặc enqueue job. Với CRUD admin API ít critical, integration tests bình thường có thể đã đủ.

## 3. Người dùng mục tiêu

### Primary user

Backend developer dùng ASP.NET Core, EF Core và PostgreSQL/SQL Server, có endpoint `POST` hoặc background handler mà duplicate processing gây hậu quả.

### Context sử dụng

Trước merge hoặc release, developer muốn kiểm tra:

- retry có tạo duplicate row không;
- concurrent duplicate request có race không;
- idempotency key có được enforce đúng không;
- failed/timeout response có để lại side effect không;
- retry sau partial failure có trả lại kết quả cũ hay tạo operation mới.

### Main pain point

Khó nhất không phải gửi request hai lần, mà là **xác định tất cả side effects phải giữ invariant**.

Ví dụ một order endpoint có thể:

```text
Orders = 1
OrderItems = 3
OutboxMessages = 1
PaymentRequests = 1
EmailsQueued = 1
```

Nếu chỉ kiểm tra HTTP response, duplicate side effect dễ bị bỏ sót.

### Current workaround

Developer viết test riêng cho từng endpoint hoặc tái hiện incident bằng script. Việc này mất thời gian, khó chuẩn hóa và thường không cover các timing window khác nhau.

### Vì sao họ thử IdempotencyLab

Vì mỗi endpoint có thể khai báo một scenario nhỏ và tool tự chạy nhiều retry/fault patterns rồi kiểm tra invariant.

## 4. Giải pháp đề xuất

### Main workflow

```text
Define scenario
→ start SUT/test environment
→ prepare baseline state
→ send operation
→ inject duplicate/retry/timeout pattern
→ wait for eventual processing
→ query observers
→ assert invariants
→ generate report
```

### Input

Một YAML/JSON scenario:

```yaml
name: create-order-is-idempotent
request:
  method: POST
  url: /api/orders
  headers:
    Idempotency-Key: "{{operationId}}"
  body:
    customerId: customer-1
    productId: product-99

patterns:
  - sequential-duplicate
  - concurrent-duplicate
  - retry-after-client-timeout

invariants:
  - sql: "select count(*) from orders where external_id = @operationId"
    equals: 1
  - sql: "select count(*) from outbox_messages where correlation_id = @operationId"
    equals: 1
```

### Processing

Tool sẽ:

1. generate một logical operation ID;
2. gửi request theo pattern;
3. record status code, latency, body hash;
4. chạy observer queries sau mỗi phase;
5. chờ eventual consistency trong timeout giới hạn;
6. so sánh invariant;
7. lưu trace timeline.

### Output

```text
Scenario: create-order-is-idempotent
Pattern: concurrent-duplicate x5

HTTP responses: 201, 201, 201, 201, 201
Orders created: 1 ✅
Outbox messages: 1 ✅
Payment requests: 1 ✅
Response resource id stable: ✅

Verdict: PASS
```

Một failure report:

```text
Pattern: retry-after-timeout
Orders created: 1 ✅
Outbox messages: 2 ❌

Timeline:
00ms  request A started
82ms  DB order committed
91ms  outbox inserted
100ms simulated client timeout
180ms retry B started
244ms second outbox inserted

Verdict: FAIL — duplicate side effect
```

### Điều được tự động hóa

- duplicate request generation;
- concurrency;
- client-side timeout/cancellation;
- request correlation;
- response comparison;
- database observers;
- invariant evaluation;
- timeline/report.

### User vẫn kiểm soát

- endpoint và payload;
- business invariants;
- cleanup/seed strategy;
- idempotency key format;
- allowed status codes;
- eventual consistency window.

### Key differentiator

Không phải load testing và cũng không phải generic API testing. Tool tập trung vào câu hỏi:

> **“Một logical operation bị gửi nhiều lần dưới failure conditions thì business side effects có vẫn xảy ra đúng một lần không?”**

## 7. Luồng hoạt động

### Happy path

```text
load scenario
→ validate config
→ run setup SQL
→ generate operationId
→ send request pattern
→ collect responses
→ poll invariants
→ write report
→ run cleanup
→ exit 0
```

### Failure: endpoint unreachable

Tool phân biệt:

```text
SUTUnavailable
```

với:

```text
IdempotencyFailure
```

Không được báo duplicate fail khi test environment chưa chạy.

### Failure: SQL observer unavailable

Verdict là `INCONCLUSIVE`, không phải PASS.

### Failure: eventual invariant chưa đạt

Ví dụ outbox được xử lý async. Tool poll theo interval tới deadline. Nếu vượt deadline, report cả history:

```text
0ms count=0
200ms count=0
400ms count=2
```

### Failure: timeout simulation

Client cancellation không đảm bảo server dừng processing. Đây chính là behavior cần test. Tool phải ghi rõ client timeout xảy ra lúc nào nhưng không suy luận server transaction đã rollback.

### Failure: same idempotency key + different payload

Scenario có thể yêu cầu server trả `409`, `422` hoặc status khác do user cấu hình. Tool không ép một semantics duy nhất vì `Idempotency-Key` hiện chưa phải finalized RFC.

## 11. API và tích hợp

### Target HTTP API

Purpose: system under test.

Authentication: configurable Bearer/API key/header reference từ environment.

Rate-limit concern: test chỉ chạy ở local/staging/test environment. Tool phải có `allowed-hosts` guard để tránh vô tình bắn duplicate request vào production.

Privacy: request/response có thể chứa PII. Mặc định report lưu hash/selected paths thay vì full body.

Fallback: endpoint unavailable → test `INCONCLUSIVE`.

### PostgreSQL

Purpose: observer read business state.

Authentication: read-only user nếu có thể.

Cost: không đáng kể local/test.

Privacy: query chỉ trả metric/invariant cần thiết; không dump bảng.

Fallback: observer unavailable → không cho PASS nếu invariant phụ thuộc observer đó.

### Microsoft.Extensions.Http.Resilience — research/reference

Không phải dependency bắt buộc của MVP. Nó hữu ích để tạo sample SUT demonstrating retry behavior. Microsoft hiện cho phép disable retry cho unsafe methods vì retry có thể gây duplicate side effects. Nguồn: [HTTP resilience patterns](https://learn.microsoft.com/en-us/dotnet/core/resilience/http-resilience).

### IETF Idempotency-Key draft

Tool có thể hỗ trợ header tên `Idempotency-Key`, nhưng phải ghi rõ draft này vẫn là work in progress. Không hard-code semantics ngoài scenario config. Nguồn: [IETF draft](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/).

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem cần deterministic test và invariant rõ ràng. LLM không nên quyết định một endpoint có idempotent hay không.

AI có thể được thêm rất muộn để giải thích report hoặc gợi ý invariant từ OpenAPI/schema, nhưng mọi verdict phải đến từ executable assertions.

Các rủi ro khi thêm AI sớm:

- hallucinate side effects;
- bỏ sót business invariant;
- gửi payload nhạy cảm ra ngoài;
- làm test không reproducible;
- tăng cost/latency.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** chứng minh một endpoint thật có retry ambiguity đáng test.

**Tasks:** chọn một endpoint tạo side effect; viết script gửi cùng request 5 lần sequential/concurrent; query DB; ghi lại duplicate behavior hoặc chứng minh idempotency hiện tại.

**Expected output:** một test thủ công + timeline.

**Completion criteria:** xác định được ít nhất 2 business invariants đáng tái sử dụng.

**Goal:** scenario file chạy end-to-end.

**Tasks:** CLI, JSON/YAML parser, request template, sequential/concurrent patterns, PostgreSQL observer, invariant evaluator, Markdown report.

**Expected output:** một command kiểm tra endpoint idempotency.

**Completion criteria:** có scenario PASS và một deliberately-broken sample endpoint FAIL.

### Phase 2 — Reliability

**Goal:** giảm flaky/false positive.

**Tasks:** eventual polling, cancellation handling, isolated variables, cleanup, secret redaction, structured errors, database timeout, production-host guard.

**Expected output:** failure type rõ ràng: `FAIL`, `INCONCLUSIVE`, `SUT_ERROR`.

**Completion criteria:** rerun 20 lần local cho cùng scenario không có flaky result khi SUT ổn định.

**Goal:** mô phỏng ambiguity thực tế hơn.

**Tasks:** client-timeout-then-retry, payload mismatch with same key, Testcontainers hooks, WebApplicationFactory adapter, outbox preset.

**Expected output:** test được DB commit + lost response style scenario.

**Completion criteria:** bắt được ít nhất một intentionally injected duplicate-side-effect bug mà happy-path integration test không bắt.

### Phase 4 — Production readiness

**Goal:** dùng trong CI thật.

**Tasks:** NuGet/global tool packaging, JSON schema cho config, versioned DSL, CI examples, security docs, sample project, artifact retention, documentation.

## 14. Các bài toán kỹ thuật đáng học

### 1. At-least-once reality và idempotency

Retry không thể đảm bảo request đầu tiên chưa được xử lý. Học cách thiết kế operation key, business unique constraint và cached result.

### 2. Concurrency race conditions

Hai request cùng key có thể cùng pass `SELECT not exists` trước khi insert. Học database constraint, transaction isolation, atomic insert/upsert và lock semantics.

### 3. Fault timing

Một timeout ở 20 ms khác hoàn toàn timeout sau DB commit. Học cách phân biệt client cancellation, server completion và uncertain outcome.

### 4. Eventual invariant testing

Outbox/message processing thường async. Học polling có deadline, stable observation và tránh `Task.Delay` cứng gây flaky test.

### 5. Safe test tooling

Tool cố ý gửi duplicate request nên phải chống chạy nhầm production. Học host allowlist, environment guard, destructive-test safety và secret redaction.

## 15. Rủi ro và cách xử lý

### Gửi nhầm vào production

**Risk:** cực kỳ nghiêm trọng.

**Mitigation:** mặc định chỉ cho `localhost`, loopback và explicit allowlist; production-looking host cần `--allow-unsafe-target` + environment acknowledgement. CI config nên lock target host.

### False confidence

**Risk:** một scenario pass không chứng minh endpoint idempotent với mọi failure timing.

**Mitigation:** report rõ patterns đã chạy; không dùng chữ “certified safe”; bổ sung patterns dần từ incident thật.

### Test flaky

**Risk:** async side effects chưa hoàn tất.

**Mitigation:** eventual assertions với deadline + observation history; không sleep cố định.

### Observer thay đổi state

**Risk:** SQL observer vô tình write.

**Mitigation:** support/read-only DB credential; validate query bắt đầu bằng read-only operation cho MVP; docs khuyến nghị DB role chỉ SELECT.

### Scope expansion

**Risk:** biến thành chaos platform/load tester.

**Mitigation:** chỉ HTTP duplicate/retry + invariant observers trong MVP.

### API semantics khác nhau

**Risk:** một số endpoint hợp lệ khi mỗi retry trả status khác nhau.

**Mitigation:** response expectations configurable; core verdict dựa trên business invariant.

### Sensitive data

**Mitigation:** redact headers, không lưu auth token, payload body mặc định hash, opt-in selected response fields.

1. **5 concurrent requests, cùng key** → đúng 1 order + 1 outbox message.
2. **Client timeout rồi retry** → đúng 1 side effect dù response đầu không nhận được.
3. **Cùng key nhưng payload khác** → server không tạo operation thứ hai và trả behavior đã cấu hình.
4. **Endpoint deliberately broken** → tool phát hiện `Orders=1` nhưng `OutboxMessages=2`.
5. **Observer unavailable** → verdict `INCONCLUSIVE`, tuyệt đối không PASS.

## Research notes

### Confirmed facts

- .NET hiện có `Microsoft.Extensions.Resilience` và `Microsoft.Extensions.Http.Resilience` cho retry/timeout/circuit breaker và các resilience strategies.
- Microsoft cảnh báo retry unsafe HTTP methods có thể gây duplicate data; thư viện hỗ trợ tắt retry cho những methods này.
- ASP.NET Core cung cấp `WebApplicationFactory<TEntryPoint>`/TestServer cho integration testing.
- .NET 10 là LTS active tại thời điểm nghiên cứu và được support tới tháng 11/2028.
- IETF có draft về `Idempotency-Key`, nhưng tài liệu này vẫn là work in progress chứ chưa nên được mô tả như một chuẩn RFC hoàn tất.

### Observation

Các primitive để retry, integration test và implement idempotency đã tồn tại. Khoảng trống phù hợp cho một solo tool là **orchestrate failure patterns + business observers + executable invariants** để biến idempotency thành thứ có thể regression-test trong CI.

### Assumption

Developer sẽ chấp nhận viết 2–5 invariant cho operation critical nếu đổi lại họ không phải viết custom concurrency/retry orchestration cho mỗi endpoint.

### Recommendation

Build **concurrent duplicate runner + one invariant** trước. Chỉ xây scenario DSL sau khi cùng pattern được tái sử dụng ở ít nhất 2 endpoint khác nhau.
