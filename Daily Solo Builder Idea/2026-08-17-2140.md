# Ý tưởng hôm nay: NuGet License Gate — Kiểm tra giấy phép dependency trước khi merge hoặc release

## 1. Tóm tắt ý tưởng

**NuGet License Gate** là một CLI/tool CI dành cho dự án .NET, quét toàn bộ NuGet dependency trực tiếp và transitive, chuẩn hóa metadata giấy phép rồi đối chiếu với policy của repository để cảnh báo hoặc chặn build khi xuất hiện license chưa được phê duyệt. Công cụ giúp developer tránh tình trạng chỉ phát hiện vấn đề licensing sau khi package đã được đưa vào production hoặc sản phẩm thương mại.

- **Project size:** Medium
- **Estimated MVP time:** 7–10 ngày làm ngoài giờ
- **Người dùng chính:** .NET developer hoặc team nhỏ có nhiều NuGet packages và muốn kiểm soát license theo policy nội bộ.

## 2. Bài toán thực tế

Một dự án .NET có thể chỉ khai báo vài package trực tiếp nhưng thực tế kéo theo nhiều transitive dependencies. Developer thường review package mới theo chức năng, security hoặc compatibility, trong khi license metadata dễ bị bỏ qua.

### Fact đã xác nhận

- `dotnet package list --include-transitive` có thể liệt kê cả dependency trực tiếp và transitive; .NET 10 còn hỗ trợ output machine-readable JSON qua `--format json`. Nguồn: [Microsoft Learn — dotnet package list](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-list).
- NuGet V3 Registration API cung cấp package metadata, trong đó có `licenseExpression`, `licenseUrl`, dependency metadata và package content URL. Nguồn: [Microsoft Learn — Package metadata, NuGet API](https://learn.microsoft.com/en-us/nuget/api/registration-base-url-resource).
- NuGet hỗ trợ license theo SPDX expression, ví dụ `MIT`, `BSD-2-Clause OR MIT`; package cũng có thể dùng license file thay vì expression. Nguồn: [Microsoft Learn — .nuspec reference](https://learn.microsoft.com/en-us/nuget/reference/nuspec).
- SPDX License List cung cấp các identifier và expression chuẩn hóa, có thể dùng cho automation. Nguồn: [SPDX — Handling License Info](https://spdx.dev/learn/handling-license-info/).

### Quan sát

Security scanning hiện đã khá phổ biến trong CI, nhưng licensing thường vẫn được kiểm tra thủ công hoặc chỉ dựa trên UI của package registry. Điều này đặc biệt dễ sót khi transitive dependency thay đổi sau một package upgrade.

### Giả định cần kiểm chứng

MVP giả định developer/team nhỏ muốn policy đơn giản kiểu:

- allow: `MIT`, `Apache-2.0`, `BSD-2-Clause`, `BSD-3-Clause`;
- review-required: `MPL-2.0`, custom license;
- deny: một số license do team tự cấu hình.

Công cụ không nên tự tuyên bố một license là “an toàn pháp lý”; nó chỉ thực thi policy do user định nghĩa.

## 3. Người dùng mục tiêu

### Primary user

.NET backend developer hoặc maintainer của một repository có nhiều NuGet dependency và deploy định kỳ qua GitHub Actions/Azure DevOps.

### Context of use

- trước khi thêm package mới;
- trong pull request;
- trước release;
- sau dependency upgrade;
- khi kiểm kê dependency cho khách hàng hoặc nội bộ.

### Main pain point

Developer khó trả lời nhanh:

> “Dependency tree hiện tại có license nào mới xuất hiện, package nào thiếu license metadata, và thay đổi này có vi phạm policy repo không?”

### Current workaround

- mở từng package trên nuget.org;
- đọc `.nuspec`;
- chạy script custom;
- dựa vào spreadsheet;
- chỉ kiểm tra top-level package.

### Lý do thử tool

Một command deterministic có thể chạy local và CI, output rõ package nào gây violation và dependency đó đến từ đâu.

## 4. Giải pháp đề xuất

User thêm file policy vào repository:

```yaml
version: 1
allow:
  - MIT
  - Apache-2.0
  - BSD-2-Clause
  - BSD-3-Clause
review:
  - MPL-2.0
deny:
  - GPL-3.0-only
unknown: review
```

Sau đó chạy:

```bash
nuget-license-gate scan MySolution.sln
```

### Main workflow

1. Chạy `dotnet package list --include-transitive --format json`.
2. Parse package ID + resolved version.
3. Fetch NuGet metadata.
4. Lấy `licenseExpression`; nếu package dùng license file thì đánh dấu cần đọc package metadata bổ sung.
5. Normalize expression.
6. Evaluate theo policy.
7. In report và trả exit code khác 0 nếu có `deny` hoặc unresolved item theo cấu hình.

### Input

- solution/project path;
- policy YAML;
- optional package source;
- optional baseline file.

### Processing

- dependency discovery;
- metadata resolution;
- license expression parsing;
- policy evaluation;
- diff với baseline nếu có.

### Output

CLI report:

```text
PASS  Serilog 4.3.0                  Apache-2.0
PASS  Dapper 2.1.66                  Apache-2.0
REVIEW Some.Package 3.2.1            MPL-2.0
DENY  Another.Package 1.4.0          GPL-3.0-only
UNKNOWN Legacy.Package 2.0.0         license file / metadata incomplete
```

JSON/SARIF output có thể thêm sau.

### What is automated

- dependency enumeration;
- license metadata lookup;
- normalization;
- policy evaluation;
- CI exit status.

### What stays under user control

- allow/deny/review policy;
- exception list;
- legal interpretation;
- approval cho custom license.

### Key differentiator

Tool tập trung vào **.NET/NuGet workflow + transitive dependency + policy-as-code + diff**, không cố trở thành một enterprise software-composition-analysis platform.

### Concrete example

Một PR upgrade `PackageA` từ 2.x lên 3.x. Version mới kéo thêm `PackageB`. Developer không khai báo `PackageB` trực tiếp nên dễ bỏ sót. NuGet License Gate phát hiện `PackageB` xuất hiện lần đầu, license là `MPL-2.0`, policy repo yêu cầu review. PR CI chuyển sang trạng thái warning/fail tùy policy và chỉ ra dependency path gây ra package đó.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Có thể dùng ngay trong chính các repo .NET cá nhân để review dependency trước merge.

### Technical learning value

Dự án chạm vào:

- CLI engineering;
- NuGet V3 protocol;
- SPDX expression parsing;
- transitive dependency graph;
- cache + retry;
- deterministic policy engines;
- CI integration;
- reproducible reports.

### Phù hợp solo developer

Không cần frontend, database server hoặc cloud account cho MVP. CLI + local cache là đủ.

### Có ích dù chỉ có một user

Ngay cả khi không public, tool vẫn giúp kiểm tra các dự án cá nhân và tạo reusable CI guard.

### Điều khiến ý tưởng thất bại

Nếu metadata license của package quá thiếu hoặc tool tạo quá nhiều false positive, developer sẽ bypass nó.

### Lý do mạnh nhất để không build

Các platform SCA lớn đã có capability licensing. Nếu user đang dùng một hệ thống enterprise hoàn chỉnh thì standalone tool này có thể không tạo thêm nhiều giá trị.

## 6. Phạm vi MVP

### Must have

1. Input `.sln` hoặc `.csproj`.
2. Enumerate top-level + transitive NuGet packages.
3. Fetch `licenseExpression` qua NuGet V3 metadata.
4. Parse license expression cơ bản: single ID, `AND`, `OR`, parentheses.
5. YAML policy: allow/review/deny/unknown.
6. Console report.
7. Exit code CI-friendly.
8. Local metadata cache.
9. Exception theo `packageId@version`.
10. JSON report.

### Should have

- baseline/diff mode;
- dependency path;
- offline cache-only mode;
- multiple package sources;
- `--fail-on review`;
- ignore dev-only project/path;
- Markdown report cho PR artifact.

### Later

- SARIF;
- GitHub PR annotations;
- Azure DevOps task;
- CycloneDX/SPDX SBOM import/export;
- license file extraction từ `.nupkg`;
- package source auth;
- policy inheritance;
- repository-wide multi-language adapters.

## 7. Luồng hoạt động

User chạy scan
→ validate solution/project
→ invoke .NET CLI package listing
→ parse JSON
→ deduplicate package ID/version
→ resolve metadata từ cache hoặc NuGet source
→ parse license expression
→ evaluate policy
→ build findings
→ render console/JSON report
→ return exit code.

### Alternative flow: package không có `licenseExpression`

→ kiểm tra metadata khác như license file
→ đánh dấu `UNKNOWN` hoặc `REVIEW`
→ không tự đoán license từ README/project URL.

### Failure: NuGet API timeout

→ retry giới hạn
→ fallback cache nếu còn dữ liệu
→ nếu vẫn unavailable, report `MetadataUnavailable`
→ policy quyết định fail-open hay fail-closed.

### Failure: private feed

→ MVP cho phép user cấu hình source nhưng không tự implement mọi auth flow.
→ nếu metadata không truy cập được, report rõ ràng thay vì giả định license.

### Failure: malformed SPDX expression

→ classify `INVALID_METADATA`
→ không silently normalize một expression không parse được.

## 11. API và tích hợp

### 1. .NET CLI

Purpose: dependency discovery.

Command chính:

```bash
dotnet package list --include-transitive --format json
```

Authentication: phụ thuộc feed/package restore config.

Cost: free.

Fallback: parse `project.assets.json` trong future nếu cần kiểm soát graph sâu hơn.

### 2. NuGet V3 Service Index / Registration API

Purpose: package metadata/license.

Authentication: nuget.org public không cần; private feed có thể cần.

Rate limit/cost: không nên giả định unlimited; tool cần cache và bounded concurrency.

Privacy: gửi package IDs/version tới package source tương ứng.

Fallback: cache local hoặc mark metadata unavailable.

### 3. licenses.nuget.org

Microsoft cung cấp stable reference URLs cho license expressions trên nuget.org, nhưng service này hướng đến browser và không cung cấp machine-readable API. Nguồn: [Microsoft Learn — licenses.nuget.org](https://learn.microsoft.com/en-us/nuget/nuget-org/licenses.nuget.org).

Vì vậy MVP không nên scrape trang này; chỉ dùng làm human reference link trong report.

### 4. SPDX License List

Purpose: chuẩn identifier/expression semantics.

Authentication: không cần.

Fallback: bundle snapshot/versioned license IDs hoặc dùng NuGet expression data khi parser chỉ cần syntax.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

License policy là bài toán cần deterministic, explainable và reproducible behavior. AI không nên quyết định package “được phép” hay “không được phép”.

AI chỉ có thể xuất hiện rất muộn để tóm tắt custom license cho người review, nhưng không nên tác động vào exit code.

Deterministic code tốt hơn vì:

- cùng input phải ra cùng decision;
- dễ unit test;
- không hallucination;
- không gửi license text ra third-party;
- CI latency thấp;
- không có token cost.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** kiểm chứng vấn đề trên repo thật.

**Main tasks:**

1. Chọn 3 solution .NET cá nhân.
2. Chạy package list có transitive dependencies.
3. Lấy metadata license cho khoảng 20–50 package.
4. Ghi lại bao nhiêu package có expression, license file hoặc metadata khó xử lý.
5. Viết policy giả lập.

**Expected output:** một dependency-license inventory thủ công nhỏ.

**Completion criteria:** tool có thể thay thế một quy trình review thực tế, không chỉ demo parser.

### Phase 1 — Core MVP

**Goal:** `solution → dependencies → license metadata → decision → exit code`.

**Main tasks:**

- CLI skeleton;
- dependency discovery;
- NuGet registration client;
- YAML policy;
- single-license evaluator;
- console output;
- tests.

**Expected output:** scan một repo public .NET thành công.

**Completion criteria:** CI fail đúng khi policy deny package.

### Phase 2 — Reliability

**Goal:** chạy ổn định trong CI.

**Tasks:**

- retries;
- timeout;
- local cache;
- bounded concurrency;
- malformed metadata handling;
- `AND`/`OR` expression parser;
- JSON output;
- deterministic ordering.

**Completion criteria:** network glitch không gây duplicate/garbled report và kết quả cùng input ổn định.

### Phase 3 — Useful expansion

**Goal:** giảm noise cho PR review.

**Tasks:**

- baseline/diff;
- dependency path;
- exception expiry;
- Markdown output;
- `--new-only`.

**Completion criteria:** PR chỉ highlight license change mới thay vì toàn bộ dependency tree mỗi lần.

### Phase 4 — Production readiness

**Goal:** publish thành tool reusable.

**Tasks:**

- NuGet package/global tool;
- semantic versioning;

## 15. Rủi ro và cách xử lý

### Rủi ro 1: biến tool thành “legal advisor”

**Mitigation:**

- wording rõ: tool enforces user-defined policy;
- không kết luận “license này hợp pháp/không hợp pháp”;
- custom license luôn review nếu chưa có explicit exception.

### Rủi ro 2: metadata thiếu hoặc sai

**Mitigation:**

- report provenance/source;
- distinguish `unknown`, `missing`, `invalid`;
- không đoán từ package name hoặc README.

### Rủi ro 3: SPDX expression phức tạp

**Mitigation:**

- implement AST/parser có test;
- không split chuỗi bằng regex đơn giản;
- unsupported syntax → explicit failure/review.

### Rủi ro 4: private feed authentication

**Mitigation:**

Không cố hỗ trợ mọi feed ở MVP. Dựa vào existing NuGet config cho dependency resolution, còn metadata private feed là Phase 3+.

### Rủi ro 5: CI chậm

**Mitigation:**

- cache metadata;
- deduplicate ID/version;
- bounded parallel requests;
- baseline scan.

### Rủi ro 6: policy quá cứng làm developer bypass

**Mitigation:**

- allow/review/deny thay vì chỉ pass/fail;
- exception có reason + expiry;
- `--new-only`.

### Rủi ro 7: maintenance burden của license list

**Mitigation:**

Dựa vào SPDX/NuGet standardized expression thay vì hard-code knowledge pháp lý của từng license.

## 18. Khả năng mở rộng

## 20. Việc cần làm ngay hôm nay

### Thời lượng

Khoảng **90–120 phút**.

### Development objective

### First vertical slice

Hard-code policy ban đầu:

```csharp
var allowed = new HashSet<string>(StringComparer.Ordinal)
{
    "MIT",
    "Apache-2.0",
    "BSD-2-Clause",
    "BSD-3-Clause"
};
```

CLI usage tạm thời:

```bash
dotnet run --project NuGetLicenseGate.Cli -- Newtonsoft.Json 13.0.3
```

Expected output dạng:

```text
Package: Newtonsoft.Json
Version: 13.0.3
License: MIT
Decision: PASS
Source: NuGet V3 registration metadata
```

### Implementation steps

1. Fetch NuGet service index.
2. Resolve `RegistrationsBaseUrl`.
3. Fetch package registration metadata cho ID/version.
4. Extract `licenseExpression`.
5. Pass vào `LicensePolicyEvaluator`.
6. In decision.
7. Add tests cho MIT + unknown.

### Expected result

Một binary thật có thể query NuGet metadata và đưa ra policy decision deterministic cho một package cụ thể.

### Verification checklist

- [ ] `dotnet build` pass.
- [ ] `dotnet test` pass.
- [ ] Package có MIT trả `PASS`.
- [ ] Unknown/custom metadata không bị tự động allow.
- [ ] HTTP timeout được cấu hình.
- [ ] Không hard-code URL registration leaf theo pattern không được NuGet API đảm bảo; discover base/resource đúng protocol.
- [ ] Decision logic không nằm trong HTTP client.
- [ ] Chưa thêm DB, UI, AI hoặc microservice.

### Stop condition

Dừng khi command `package ID + version → NuGet metadata → license expression → policy decision` chạy ổn định và có unit tests. Session sau mới mở rộng sang `dotnet package list --include-transitive --format json` để scan toàn solution.

## Nguồn nghiên cứu

1. [Microsoft Learn — dotnet package list](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-list) — xác nhận .NET CLI có thể liệt kê transitive dependencies và xuất JSON; noun-first command được giới thiệu từ .NET 10.
2. [Microsoft Learn — Package metadata, NuGet API](https://learn.microsoft.com/en-us/nuget/api/registration-base-url-resource) — xác nhận NuGet V3 Registration API chứa metadata như `licenseExpression`, `licenseUrl`, dependency metadata và package content URL.
3. [Microsoft Learn — .nuspec reference](https://learn.microsoft.com/en-us/nuget/reference/nuspec) — xác nhận NuGet package có thể khai báo SPDX license expression hoặc embedded license file.
4. [Microsoft Learn — licenses.nuget.org](https://learn.microsoft.com/en-us/nuget/nuget-org/licenses.nuget.org) — xác nhận service cung cấp stable human-readable license reference nhưng không có machine-readable response, do đó không nên scrape làm core API.
5. [SPDX — Handling License Info](https://spdx.dev/learn/handling-license-info/) — mô tả SPDX identifiers và expression syntax dùng `AND`, `OR`, `WITH`.
6. [SPDX — Specifications](https://spdx.dev/use/specifications/) — SPDX là chuẩn quốc tế ISO/IEC 5962:2021 và SPDX 3.0 là current document version tại thời điểm nghiên cứu.
7. [.NET Support Policy](https://dotnet.microsoft.com/en-us/platform/support/policy) — tại 17/08/2026, .NET 10 là Active LTS, patch 10.0.10, support đến 14/11/2028.

## Kết luận lựa chọn

**Confirmed facts:** NuGet và .NET CLI đã cung cấp đủ primitive chính cho MVP: enumerate transitive packages, machine-readable package list và license metadata qua NuGet V3.

**Observation:** licensing là một phần của software supply chain nhưng dễ bị review thủ công, đặc biệt với transitive dependencies.

**Analysis:** một CLI nhỏ, deterministic và policy-as-code tạo giá trị rõ hơn việc xây dashboard lớn ngay từ đầu.

**Assumption:** team nhỏ chấp nhận maintain một allow/review/deny policy nếu tool tạo ít noise và hỗ trợ baseline/diff.

**Recommendation:** tập trung MVP vào `dependency discovery → metadata → SPDX parse → policy decision → CI exit code`; tuyệt đối không cố thay thế luật sư, enterprise SCA hoặc build multi-language platform trong phiên bản đầu.
