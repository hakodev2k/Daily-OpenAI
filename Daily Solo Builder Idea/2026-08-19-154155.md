# Ý tưởng hôm nay: ContractSentry — API Contract Change Watcher

## 1. Tóm tắt ý tưởng

ContractSentry là một công cụ self-hosted theo dõi OpenAPI/Swagger contract của các API mà developer đang tích hợp, tự động snapshot phiên bản mới, so sánh với phiên bản trước, phát hiện breaking change và cảnh báo khi thay đổi có thể làm client hiện tại bị lỗi. Người dùng chính là backend developer hoặc solo builder phụ thuộc vào nhiều REST API bên ngoài nhưng không muốn chỉ phát hiện thay đổi khi production bắt đầu trả `400`, `404` hoặc deserialize lỗi.

- **Project size:** Medium
- **Estimated MVP time:** 2–3 tuần

## 2. Bài toán thực tế

Một ứng dụng backend thường phụ thuộc vào nhiều API: payment, Microsoft Graph, CRM, email, AI provider, internal services hoặc API của đối tác. Vấn đề là contract của các API này có thể thay đổi theo thời gian: endpoint bị xóa, parameter trở thành required, response field đổi type, enum bị thu hẹp hoặc schema thay đổi theo cách khiến generated client hoặc code deserialize hiện tại không còn tương thích.

### Confirmed facts

- ASP.NET Core .NET 10 hỗ trợ tạo OpenAPI 3.1 document và OpenAPI 3.1 sử dụng JSON Schema 2020-12 sâu hơn so với OpenAPI 3.0. Microsoft cũng ghi nhận các thay đổi trong OpenAPI.NET 2.0 có thể ảnh hưởng code transformer và tooling dựa trên schema. Nguồn: Microsoft Learn — ASP.NET Core .NET 10 OpenAPI release notes. https://learn.microsoft.com/en-us/aspnet/core/release-notes/aspnetcore-10.0?view=aspnetcore-10.0
- `oasdiff` là dự án mã nguồn mở chuyên so sánh OpenAPI, có lệnh `breaking`, `changelog` và khả năng fail CI khi phát hiện breaking change. Tài liệu của dự án mô tả rõ việc thêm required request property hoặc xóa contract có thể làm client hợp lệ trước đó bị lỗi. Nguồn: https://github.com/oasdiff/oasdiff và https://github.com/oasdiff/oasdiff/blob/main/docs/BREAKING-CHANGES.md
- `oasdiff` hiện hỗ trợ OpenAPI 3.1 và các JSON Schema feature như nullable type arrays, `const`, `prefixItems`, conditional schema và webhook definitions. Nguồn: https://github.com/oasdiff/oasdiff/blob/main/docs/OPENAPI-31.md

### Observation

Tooling hiện tại mạnh ở use case “so sánh hai file contract trong CI của API mình sở hữu”. Nhưng khi developer là **consumer của API bên thứ ba**, vấn đề khác đi: họ cần định kỳ lấy contract từ nhiều nguồn, lưu lịch sử, biết thay đổi nào mới xuất hiện, nhận notification và đánh dấu API nào thực sự đang được code của họ sử dụng.

### Assumption cần kiểm chứng

Developer phụ thuộc vào nhiều REST API sẽ thấy giá trị nếu một service nhỏ có thể cảnh báo “API X vừa thêm required field ở endpoint bạn đang dùng” trước khi deployment hoặc background job của họ bắt đầu fail.

### Workaround hiện tại

Developer thường:

- Theo dõi changelog thủ công.
- Đọc release note của từng provider.
- Chỉ biết thay đổi sau khi integration test fail.
- Commit Swagger JSON vào repository rồi diff bằng Git.
- Viết script `curl` + `git diff` riêng cho từng API.
- Chạy `oasdiff` thủ công khi nghi ngờ có thay đổi.

Các cách trên có thể hiệu quả cho 1–2 API nhưng trở nên phân mảnh khi có nhiều integration hoặc khi provider không có changelog rõ ràng.

## 3. Người dùng mục tiêu

### Primary user

Backend developer hoặc solo SaaS builder đang duy trì ứng dụng phụ thuộc vào khoảng 3–20 REST API có OpenAPI document hoặc schema endpoint công khai/private.

### Context of use

Ví dụ một backend sử dụng:

- Microsoft Graph
- Internal company APIs
- Payment provider
- CRM API
- AI gateway
- Notification API

Developer muốn biết contract nào đã thay đổi kể từ lần kiểm tra trước mà không phải mở từng trang documentation.

### Main pain point

Breaking API change có thể xuất hiện âm thầm giữa hai lần release của chính ứng dụng consumer.

### Current workaround

Developer dựa vào provider changelog hoặc integration test.

### Reason to try ContractSentry

Một dashboard duy nhất có thể trả lời:

- API nào vừa thay đổi?
- Có breaking change không?
- Endpoint nào bị ảnh hưởng?
- Đây là lần đầu thay đổi xuất hiện hay đã biết?
- Client của mình có đang sử dụng endpoint đó không?

## 4. Giải pháp đề xuất

Người dùng đăng ký một API source bằng URL OpenAPI, ví dụ:

```text
https://api.example.com/openapi.json
```

ContractSentry định kỳ tải document, normalize nội dung, tính hash và chỉ tạo snapshot mới khi contract thay đổi.

Khi có thay đổi:

1. Lấy snapshot trước đó.
2. Chạy OpenAPI diff engine.
3. Phân loại change thành:
   - Breaking
   - Potentially breaking
   - Non-breaking
4. Lưu change set.
5. Hiển thị diff theo endpoint/schema.
6. Gửi notification nếu severity đạt threshold.

### Key differentiator

Không xây một diff engine mới từ đầu. ContractSentry tập trung vào **monitoring lifecycle của API consumer**:

```text
fetch → snapshot → diff → history → relevance → notify
```

### Concrete example

Developer thêm Microsoft-like internal API:

```text
https://partner-api.example.com/swagger/v1/swagger.json
```

Version hôm qua:

```json
{
  "paths": {
    "/orders": {
      "post": {
        "requestBody": {
          "required": false
        }
      }
    }
  }
}
```

Version hôm nay thay đổi request schema và thêm field bắt buộc:

```json
{
  "required": ["customerRegion"]
}
```

ContractSentry tạo event:

```text
Severity: BREAKING
API: Partner Orders API
Endpoint: POST /orders
Change: required request property added
Property: customerRegion
Detected: 2026-08-19 15:xx UTC+7
```

Developer nhận Telegram/email notification và có thể kiểm tra client trước khi job production chạy lần tiếp theo.

### User control

Tool tự động fetch/diff/notify, nhưng người dùng quyết định:

- Polling frequency
- Severity threshold
- Endpoint ignore list
- Retention
- Notification channel
- Credential storage
- API nào được phép truy cập

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Ngay cả chỉ có một người sử dụng, tool vẫn hữu ích vì có thể theo dõi các API mà chính developer phụ thuộc vào.

### Technical learning value

Project chạm tới nhiều kỹ năng backend thực tế:

- Scheduled jobs
- HTTP conditional requests
- Content hashing
- OpenAPI parsing
- External process execution
- Change detection
- Retry
- Notification delivery
- Secret storage
- Data retention

### Suitable for solo developer

Core domain nhỏ và dễ giới hạn. MVP không cần microservices, Kafka, Kubernetes hoặc AI.

Một modular monolith với worker định kỳ là đủ.

### Useful with few users

Đây là loại developer utility mà personal value không phụ thuộc network effect.

### What would make it fail

- Phần lớn API cần theo dõi không expose OpenAPI document ổn định.
- Provider version API rõ ràng đến mức monitoring không cần thiết.
- Diff tạo quá nhiều noise khiến developer bỏ notification.
- Authentication cho schema endpoint quá đa dạng gây scope tăng nhanh.

### Strongest reason not to build

Nếu chỉ phụ thuộc một vài API nổi tiếng có versioning và deprecation policy rất tốt, việc theo dõi changelog + integration test có thể đơn giản hơn việc vận hành thêm một service.

## 7. Luồng hoạt động

### Normal monitoring flow

User creates monitor
→ validate URL
→ fetch OpenAPI document
→ verify parseable OpenAPI
→ normalize content
→ compute hash
→ save first snapshot
→ schedule future check.

Next polling cycle:

Scheduler triggers
→ HTTP GET contract
→ `304 Not Modified` hoặc new document
→ compute hash
→ compare với last snapshot
→ nếu giống: record successful check only
→ nếu khác: save snapshot
→ run diff
→ persist change set
→ evaluate severity
→ send notification.

### Manual check flow

User clicks `Check now`
→ enqueue check job
→ fetch contract
→ process exactly như scheduled job
→ UI hiển thị result.

### Failure cases

#### API timeout

Không tạo snapshot mới. Check status = `Failed`. Retry với backoff.

#### HTTP 401/403

Mark authentication failure và không retry liên tục.

#### HTTP 404

Raise high-priority source-unavailable warning vì contract endpoint có thể đã đổi.

#### Invalid OpenAPI document

Lưu metadata lỗi, không thay last-known-good snapshot.

#### Diff process crashes

Snapshot vẫn được lưu, change set có status `DiffFailed`, cho phép rerun.

#### Notification fails

Change set không bị rollback. Notification delivery retry độc lập.

## 9. Công nghệ đề xuất

### .NET 10 + ASP.NET Core

**Why it fits:** phù hợp background processing, HTTP integrations, dependency injection và self-hosting.

**Simpler alternative:** .NET console worker + Razor Pages.

**Outgrow point:** không cần đổi framework; chỉ tách worker khi polling volume rất lớn.

### Entity Framework Core + PostgreSQL

**Why it fits:** data model relational và query lịch sử đơn giản.

**Simpler alternative:** SQLite cho personal deployment.

**Outgrow point:** PostgreSQL vẫn đủ cho hàng nghìn monitor; storage raw snapshots mới là phần có thể cần tách.

### Hangfire

**Why it fits:** recurring monitoring, retry và manual run.

**Simpler alternative:** `BackgroundService` + polling loop.

**Outgrow point:** chỉ cần broker riêng khi có nhiều worker hoặc workload lớn.

### oasdiff CLI

**Why it fits:** đã giải quyết bài toán khó nhất là semantic OpenAPI breaking-change detection và hỗ trợ machine-readable output.

**Simpler alternative:** shell out tới Docker image thay vì bundle binary.

**Outgrow point:** nếu cần tighter integration/performance, có thể viết adapter riêng hoặc dùng Go service/library sau này, nhưng không cần ở MVP.

### Vue 3

**Why it fits:** dashboard nhỏ, phù hợp developer tooling.

**Simpler alternative:** Razor Pages.

Nếu mục tiêu là ship nhanh nhất, Razor Pages thực ra có thể là lựa chọn tốt hơn.

### Docker Compose

**Why it fits:** dễ self-host.

### Playwright

Dùng cho E2E dashboard và manual check workflow.

### GitHub Actions

Build/test/publish Docker image.

## 11. API và tích hợp

### OpenAPI / Swagger endpoint

**Purpose:** data source chính.

**Authentication:** public, Basic Auth hoặc Bearer token trong MVP.

**Cost/rate limit:** phụ thuộc provider; default polling nên thận trọng, ví dụ 1–24 giờ.

**Privacy:** private API schema có thể tiết lộ endpoint/data model nội bộ.

**Fallback:** manual upload OpenAPI file có thể thêm sau.

### oasdiff

**Purpose:** semantic diff và breaking-change rules.

**Authentication:** không cần.

**Cost:** open-source local execution.

**Operational concern:** pin version để kết quả diff không thay đổi bất ngờ khi upgrade.

**Fallback:** raw text/hash diff nếu CLI unavailable, nhưng không nên gọi đó là breaking-change detection.

### Telegram Bot API

**Purpose:** notification.

**Authentication:** bot token.

**Cost:** phù hợp personal use.

**Privacy:** message nên chỉ chứa summary, không gửi full private schema.

**Fallback:** dashboard-only notification hoặc generic webhook.

### Generic webhook

**Purpose:** integrate với Slack/Discord/automation system thông qua webhook receiver phù hợp.

**Authentication:** configurable secret/header.

**Fallback:** no-op nếu delivery fail, retry background.

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

Core system không cần AI. Breaking-change detection phải deterministic.

AI chỉ có thể thêm sau cho task:

```text
Summarize a machine-readable change set into developer-friendly explanation.
```

### Exact AI input

- API name
- Endpoint
- Change type
- Old schema excerpt
- New schema excerpt

### Expected structured output

```json
{
  "summary": "...",
  "likelyImpact": "low|medium|high",
  "recommendedChecks": ["..."]
}
```

### Validation

AI không được quyết định breaking/non-breaking severity. Severity lấy từ deterministic diff engine.

### Fallback

Template-based message:

```text
POST /orders: required property 'customerRegion' added.
```

### Risks

- hallucination
- latency
- token cost
- private schema leakage

Vì vậy AI không thuộc MVP.

## 13. Kế hoạch triển khai

## 14. Các bài toán kỹ thuật đáng học

### 1. Semantic contract comparison

Text diff không đủ cho OpenAPI vì reorder JSON hoặc description change có thể không ảnh hưởng client.

Kỹ năng học được:

- OpenAPI semantics
- JSON Schema
- compatibility reasoning

### 2. Reliable scheduled polling

Mỗi API monitor có cadence riêng và source có thể timeout hoặc rate limit.

Kỹ năng học được:

- recurring jobs
- retry
- backoff
- timeout
- job idempotency

### 3. HTTP caching semantics

Dùng `ETag`, `If-None-Match`, `Last-Modified` giúp giảm request/download không cần thiết.

Kỹ năng học được:

- HTTP conditional requests
- caching headers
- network efficiency

### 4. Immutable snapshot history

Cần lưu contract theo content hash để audit mà không tạo duplicate data.

Kỹ năng học được:

- content-addressable storage concept
- deduplication
- retention design

### 5. Secret handling

Private schema endpoints có thể cần token.

Kỹ năng học được:

- encrypted configuration
- secret redaction
- least privilege

## 15. Rủi ro và cách xử lý

### API dependency

**Risk:** provider đổi URL hoặc ngừng expose OpenAPI.

**Mitigation:** last-known-good snapshot, source health status, manual file source sau MVP.

### False-positive/noisy alerts

**Risk:** developer tắt notification.

**Mitigation:** severity threshold, ignore rules, changelog grouping.

### Security

**Risk:** arbitrary URL monitor có thể tạo SSRF.

**Mitigation:**

- reject private IP ranges khi public multi-user mode
- restrict schemes to HTTP/HTTPS
- DNS/IP validation
- personal single-user mode trước

### Credential leakage

**Risk:** Bearer token xuất hiện trong logs.

**Mitigation:** secret storage + redaction + không serialize credential vào job payload/log.

### Storage growth

**Risk:** snapshot history tăng liên tục.

**Mitigation:** hash dedup + retention policy.

### Breaking-rule evolution

**Risk:** upgrade `oasdiff` làm rule behavior thay đổi.

**Mitigation:** pin exact version và lưu `DiffEngineVersion` cùng ChangeSet.

### User adoption

**Risk:** problem không đủ đau.

**Mitigation:** validate bằng chính integration của developer trước khi build SaaS/team features.

### Scope expansion

**Risk:** biến thành universal API governance platform.

**Mitigation:** MVP chỉ OpenAPI pull monitoring.

## 16. Kiểm thử

### Strategy

- Unit tests cho hash, normalization, severity evaluation và URL validation.
- Integration tests với PostgreSQL/Testcontainers.
- Integration tests với fake OpenAPI server.
- Process-level tests chạy pinned `oasdiff` fixture.
- Playwright E2E cho dashboard.
- Security tests cho SSRF và secret logging.

### 5 test scenario quan trọng nhất

1. Contract không đổi → không tạo snapshot duplicate và không tạo ChangeSet.
2. Thêm required request property → ChangeSet được đánh dấu breaking.
3. Source trả `500` → last-known-good snapshot vẫn nguyên, check được đánh dấu failed.
4. Source trả `304 Not Modified` → không chạy diff không cần thiết.
5. Notification thất bại → ChangeSet vẫn tồn tại và delivery được retry độc lập.

## 17. Cách đo dự án có hữu ích hay không

### Product usage metric

Số API monitors active và số ngày service thực sự chạy monitoring.

### Time saved

Thời gian từ khi provider contract thay đổi tới khi developer nhận biết.

Metric:

```text
Detection latency = DetectedAt - SourceChangeApproximation
```

Trong fixture/internal API có thể đo chính xác.

### Task completion rate

Tỷ lệ scheduled checks hoàn thành thành công.

Target cá nhân hợp lý:

```text
> 99% successful checks excluding upstream outages
```

### Error rate

- Fetch failure rate
- Diff failure rate
- Notification failure rate

### Repeated use

Một tín hiệu tốt hơn page views:

```text
Developer keeps at least 3 monitors enabled for 30 days.
```

### Usefulness validation

Trong 60 ngày, tool nên phát hiện ít nhất một thay đổi mà developer thực sự cần kiểm tra hoặc giúp xác nhận “không có breaking change” trước upgrade.

### Technical reliability

- No duplicate snapshot for identical content.
- No lost ChangeSet after restart.
- Retry state persisted.

## 20. Việc cần làm ngay hôm nay

### Development objective

Trong 60–120 phút, tạo vertical slice:

```text
2 OpenAPI files → oasdiff → parse JSON → print breaking changes
```

Không làm database hoặc UI trong session đầu tiên.

### Files/components cần tạo

```text
ContractSentry.sln
src/
  ContractSentry.Core/
    Models/ContractChange.cs
    Services/OasDiffRunner.cs
  ContractSentry.Cli/
    Program.cs
fixtures/
  api-v1.json
  api-v2.json
tests/
  ContractSentry.Tests/
```

### Setup commands

```bash
dotnet new sln -n ContractSentry

dotnet new classlib \
  -n ContractSentry.Core \
  -o src/ContractSentry.Core

dotnet new console \
  -n ContractSentry.Cli \
  -o src/ContractSentry.Cli

dotnet new xunit \
  -n ContractSentry.Tests \
  -o tests/ContractSentry.Tests

dotnet sln add src/ContractSentry.Core
dotnet sln add src/ContractSentry.Cli
dotnet sln add tests/ContractSentry.Tests

dotnet add src/ContractSentry.Cli reference src/ContractSentry.Core
dotnet add tests/ContractSentry.Tests reference src/ContractSentry.Core
```

### Prepare oasdiff

Nếu dùng Docker:

```bash
docker pull tufin/oasdiff
```

Tạo `api-v1.json` với endpoint:

```text
POST /users
```

request body:

```json
{
  "type": "object",
  "properties": {
    "name": {
      "type": "string"
    }
  }
}
```

Tạo `api-v2.json` và thêm:

```json
"required": ["email"]
```

với property mới:

```json
"email": {
  "type": "string"
}
```

### First vertical slice

`OasDiffRunner` chạy:

```bash
docker run --rm \
  -v <fixtures-folder>:/data:ro \
  tufin/oasdiff \
  breaking \
  --format json \
  /data/api-v1.json \
  /data/api-v2.json
```

Parse stdout thành model:

```csharp
public sealed record ContractChange(
    string Id,
    string Level,
    string Text,
    string? Path,
    string? Operation);
```

CLI output mong muốn:

```text
ContractSentry
==============
Base: api-v1.json
Revision: api-v2.json

Breaking changes: 1

[ERR] POST /users
Required request property added: email

Result: BREAKING
```

### Verification checklist

- [ ] Hai fixture OpenAPI đều parse được.
- [ ] `oasdiff` process exit được và stdout được capture.
- [ ] JSON output deserialize được trong C#.
- [ ] Fixture v2 tạo ít nhất một breaking-change result.
- [ ] Chạy v1 so với chính v1 trả zero breaking changes.
- [ ] Có một xUnit integration test cho hai fixture.
- [ ] CLI trả exit code khác `0` khi breaking change được phát hiện.

### Expected result

Sau session đầu tiên có thể chạy:

```bash
dotnet run --project src/ContractSentry.Cli -- \
  fixtures/api-v1.json \
  fixtures/api-v2.json
```

và nhận được một report breaking change có cấu trúc.

### Stop condition

Dừng session ngay khi CLI có thể phân biệt chính xác:

```text
UNCHANGED / COMPATIBLE / BREAKING
```

giữa hai OpenAPI fixtures và integration test pass. Không thêm PostgreSQL, Hangfire, Vue, authentication hoặc AI trước khi vertical slice này hoạt động.
