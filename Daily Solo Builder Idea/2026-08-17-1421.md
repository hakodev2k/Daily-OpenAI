# Ý tưởng hôm nay: DataForge — Relational Test Data Generator cho SQL Server/PostgreSQL

## 1. Tóm tắt ý tưởng

**DataForge** là một công cụ self-hosted/CLI dành cho developer và QA, đọc schema của SQL Server hoặc PostgreSQL rồi sinh dữ liệu test giả nhưng vẫn tôn trọng quan hệ PK/FK, nullable, unique, độ dài chuỗi và một số business rule do người dùng khai báo. Mục tiêu là tạo ra bộ dữ liệu đủ “giống thật để test” nhưng không cần copy dữ liệu production có PII hoặc chỉnh tay hàng trăm record.

- **Project size:** Medium
- **Estimated MVP time:** 2–4 tuần làm ngoài giờ

**Confirmed facts:**
- SQL Server expose metadata về foreign key thông qua `sys.foreign_key_columns`; mỗi row mô tả cột FK và cột được tham chiếu. Nguồn: Microsoft Learn — https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-foreign-key-columns-transact-sql?view=sql-server-ver17
- PostgreSQL expose foreign-key metadata thông qua `information_schema.referential_constraints`. Nguồn: PostgreSQL 18 docs — https://www.postgresql.org/docs/current/infoschema-referential-constraints.html
- EF Core model chứa entity types/properties và map chúng xuống relational columns, nên một adapter dựa trên EF Core metadata cũng khả thi khi tool chạy trong solution .NET. Nguồn: Microsoft Learn — https://learn.microsoft.com/en-us/ef/core/modeling/entity-types và https://learn.microsoft.com/en-us/ef/core/modeling/entity-properties
- Bogus là thư viện fake-data cho .NET, hỗ trợ deterministic seed và có locale `vi`. Nguồn: https://github.com/bchavez/Bogus
- Tính đến 17/08/2026, .NET 10 là LTS đang Active support đến 14/11/2028. Nguồn: https://dotnet.microsoft.com/en-us/platform/support/policy

**Phân tích:** các primitive để đọc schema và sinh fake-data đều đã có; phần đáng xây không phải một faker mới mà là engine hiểu dependency graph giữa các bảng và biến schema thành dataset có thể insert được ngay.

## 2. Bài toán thực tế

Developer và QA thường cần dữ liệu để test các tình huống như:

- một employee có nhiều timesheet entries;
- một order có customer, address, items và payment;
- một event có registrations và attendees;
- một workflow có nhiều status/history records;
- một API cần test pagination/filter/search trên vài nghìn row;
- một integration test cần database có dữ liệu hợp lệ ngay sau khi container khởi động.

Các cách xử lý phổ biến hiện nay thường là:

1. Seed cứng vài record trong migration hoặc test fixture.
2. Viết script SQL riêng cho từng module.
3. Clone/sanitize một phần dữ liệu production.
4. Tạo record thủ công qua UI/API.
5. Dùng faker để generate từng entity nhưng tự xử lý quan hệ.

Mỗi cách đều có giới hạn:

- Seed cứng nhanh lỗi thời khi schema thay đổi.
- Script SQL lớn khó bảo trì.
- Copy production kéo theo vấn đề PII, quyền truy cập và dữ liệu nhạy cảm.
- Tạo tay quá chậm.
- Faker thuần túy không tự hiểu FK graph, unique constraints, insertion order hoặc cyclic relations.

**Confirmed fact:** SQL Server và PostgreSQL đều cung cấp metadata về FK để tool có thể xây graph phụ thuộc thay vì yêu cầu user khai báo mọi relationship bằng tay.

**Observation:** Bogus đã giải quyết tốt việc tạo fake values, nhưng không tự biến một database schema bất kỳ thành bộ dữ liệu relational hoàn chỉnh.

**Assumption:** nhóm backend/QA làm việc với hệ thống nhiều bảng và thường xuyên reset môi trường test sẽ cảm nhận pain rõ nhất.

## 3. Người dùng mục tiêu

### Primary user

Backend developer hoặc QA automation engineer làm với SQL Server/PostgreSQL và cần dựng test database lặp lại nhiều lần.

### Context of use

- local development;
- integration test;
- QA environment;
- ephemeral database trong CI;
- demo environment;
- reproducing bug với một dataset có cấu trúc cụ thể.

### Main pain point

Dữ liệu test hiện tại hoặc quá ít, hoặc khó tái tạo, hoặc phụ thuộc vào production dump.

### Current workaround

- `INSERT` scripts;
- custom seeders;
- copy DB;
- manual API calls;
- test fixture riêng cho từng module.

### Vì sao họ có thể thử DataForge

Nếu họ có thể chạy một command như:

```bash
dataforge generate \
  --provider postgres \
  --connection "$TEST_DB" \
  --profile profiles/qa.yml \
  --seed 20260817
```

và nhận một database hợp lệ với 500 employees, 20 projects và 15.000 timesheet rows thì workflow test trở nên repeatable hơn nhiều.

## 4. Giải pháp đề xuất

DataForge gồm hai bước chính:

1. **Inspect** database schema.
2. **Generate** dataset theo schema + rule profile.

### Input

- connection string hoặc schema file export;
- provider: SQL Server/PostgreSQL;
- số lượng record mục tiêu;
- deterministic seed;
- optional profile YAML/JSON mô tả các rule semantic.

Ví dụ:

```yaml
entities:
  Employee:
    count: 200
    columns:
      FirstName: faker.name.first_name
      LastName: faker.name.last_name
      Email: faker.internet.email
      EmployeeCode: sequence:EMP-{0000}
      OfficeCode:
        pick: [HN, HCMC]

  TimesheetEntry:
    count_per_parent:
      Employee: [20, 80]
    columns:
      Hours:
        decimal_between: [0.5, 8]
```

### Processing

1. Đọc tables, columns, data types, nullability.
2. Đọc PK, FK, unique constraints.
3. Xây dependency graph.
4. Topological sort để xác định insertion order.
5. Map columns sang generator phù hợp.
6. Generate parent rows trước.
7. Generate child rows và chọn FK từ parent pool.
8. Validate uniqueness/range/nullability.
9. Insert transactionally hoặc export thành SQL/JSON/CSV.

### Output

- generated rows;
- insert report;
- seed/version của dataset;
- warnings về field chưa map được;
- optional generated SQL file.

### Tự động hóa

Tool tự động:

- discover schema;
- chọn insertion order;
- generate basic values;
- resolve foreign keys;
- enforce simple constraints;
- retry khi collision unique;
- báo field khó generate.

User vẫn kiểm soát:

- số lượng record;
- semantic rule;
- distribution;
- special business constraints;
- bảng được include/exclude;
- có insert trực tiếp hay export file.

### Key differentiator

Không chỉ là “fake values generator”; DataForge tạo **relational scenario data** có thể dùng ngay cho test database.

### Ví dụ end-to-end

Một developer có database:

```text
Employee
Project
ProjectMember
TimesheetEntry
LeaveRequest
```

Họ chạy:

```bash
dataforge inspect --connection "$DB" --out schema.json
```

DataForge nhận ra:

```text
Employee -> ProjectMember <- Project
Employee -> TimesheetEntry
Project  -> TimesheetEntry
Employee -> LeaveRequest
```

Sau đó:

```bash
dataforge generate \
  --schema schema.json \
  --profile etm-demo.yml \
  --seed 42 \
  --apply "$LOCAL_DB"
```

Kết quả:

```text
Generated
  Employee:       100
  Project:         12
  ProjectMember:  240
  TimesheetEntry: 6000
  LeaveRequest:   180

Validation
  PK violations:      0
  FK violations:      0
  Unique violations:  0
  Unmapped columns:    2

Seed: 42
```

User có thể chạy lại seed 42 để tái tạo dataset tương tự khi reproduce bug.

## 7. Luồng hoạt động

```text
User command
  -> Validate connection/profile
  -> Inspect schema
  -> Build normalized schema model
  -> Build FK dependency graph
  -> Detect unsupported/cyclic relationships
  -> Create generation plan
  -> Generate parent entities
  -> Generate dependent entities
  -> Validate constraints
  -> Export/insert
  -> Run post-generation validation
  -> Produce report + manifest
```

### Alternative flow: dry run

```text
generate
-> plan
-> generate first N rows in memory
-> display preview
-> no DB write
```

### Failure: unknown data type

Tool không đoán bừa.

```text
Unsupported column: Employee.Location geometry
Action: mark generator explicitly or exclude column
```

### Failure: circular FK

Ví dụ:

```text
Employee.ManagerId -> Employee.Id
```

MVP strategy:

1. Insert employees với `ManagerId = null` nếu nullable.
2. Generate mapping.
3. Update manager relationships ở pass 2.

Nếu non-nullable cycle phức tạp, fail với actionable diagnostic thay vì disable constraints âm thầm.

### Failure: unique collision

Retry generator với giới hạn, ví dụ 10 lần. Nếu vẫn collision:

```text
GenerationException:
Unable to satisfy UNIQUE constraint UX_Employee_Email
Generated: 93/100
```

### Failure: database insert

Mặc định transaction toàn batch:

```text
BEGIN
insert...
validate...
COMMIT
```

Nếu lỗi giữa chừng thì rollback.

## 11. API và tích hợp

### PostgreSQL Information Schema

Purpose:

- table metadata;
- column metadata;
- constraints;
- referential constraints.

**Confirmed:** `information_schema.referential_constraints` chứa các referential/foreign-key constraints của current database.

Nguồn: https://www.postgresql.org/docs/current/infoschema-referential-constraints.html

Authentication: DB credentials.

Cost: không có API charge.

Permission concern: metadata visibility phụ thuộc quyền user; docs PostgreSQL ghi rõ chỉ constraints mà current user có quyền phù hợp mới xuất hiện.

Fallback: cho phép schema JSON input offline.

### SQL Server catalog views

Purpose: metadata discovery.

**Confirmed:** `sys.foreign_key_columns` có row cho từng column hoặc nhóm columns thuộc FK và chứa source/referenced object/column IDs.

Nguồn: https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-foreign-key-columns-transact-sql?view=sql-server-ver17

Authentication: SQL/AAD/Windows tùy connection.

Permission concern: metadata visibility bị giới hạn theo securables mà user sở hữu hoặc được cấp quyền.

Fallback: schema export.

### Bogus

Purpose: semantic fake data.

Authentication: none.

Cost: core Bogus là open-source; repository cũng có commercial premium extensions nhưng MVP không cần chúng.

Privacy: all generation local.

Fallback: built-in primitive generators.

### EF Core model metadata — Later

Nếu chạy DataForge ngay trong một .NET solution, có thể đọc `IModel` để biết entity types/properties/navigation thay vì introspect database.

Microsoft docs xác nhận entity types/properties nằm trong EF Core model và relational properties map xuống columns.

Nguồn:

- https://learn.microsoft.com/en-us/ef/core/modeling/entity-types
- https://learn.microsoft.com/en-us/ef/core/modeling/entity-properties

Không nên bắt buộc EF Core vì DataForge cần dùng được cả với database không thuộc .NET app.

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

Core generation **không cần AI**.

Schema graph, FK resolution và constraint validation nên deterministic.

### AI task phù hợp ở phiên bản sau

AI chỉ nên hỗ trợ **suggest generation rules**.

Input:

```json
{
  "table": "Employee",
  "columns": [
    {"name":"FirstName","type":"nvarchar(100)"},
    {"name":"Email","type":"nvarchar(255)"},
    {"name":"EmployeeStatusCode","type":"varchar(20)"}
  ]
}
```

Expected output:

```json
{
  "FirstName": {"generator":"person.firstName"},
  "Email": {"generator":"internet.email"},
  "EmployeeStatusCode": {
    "generator":"manual_required",
    "reason":"Allowed values are unknown"
  }
}
```

### Validation

AI output phải validate against JSON Schema và generator registry.

AI không được invent allowed enum values rồi insert vào DB.

### Deterministic fallback

Column-name heuristics:

```text
*Email* -> email
*FirstName* -> first name
*Phone* -> phone
*CreatedAt* -> datetime
otherwise -> primitive generator
```

### Risks

- hallucinated semantic rules;
- gửi schema names ra provider bên ngoài;
- API cost;
- latency.

**Recommendation:** bỏ AI khỏi MVP hoàn toàn.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác minh relational generation có tiết kiệm effort thực sự.

Main tasks:

1. Chọn một database có 5–10 bảng.
2. Viết prototype query metadata.
3. Viết tay dependency graph.
4. Generate 100–1000 rows với Bogus.
5. Đo thời gian so với hand-written seed script.
6. Thử reset database rồi generate lại.

Expected output:

```text
schema.json
profile.yml
generated.sql
```

Completion criteria:

- generated dataset insert thành công;
- 0 FK violation;
- có thể chạy lại bằng cùng seed;
- ít nhất một workflow test thật sử dụng dataset đó.

### Phase 1 — Core MVP

**Goal:** CLI hoàn chỉnh cho một database provider.

Main tasks:

- `inspect` command;
- normalized schema model;
- graph builder;
- primitive generators;
- Bogus mappings;
- YAML profile;
- SQL export;
- validation report.

Expected output:

```bash
dataforge inspect
dataforge generate
dataforge validate
```

Completion criteria:

- 10+ table schema chạy được;
- parent-child data valid;
- deterministic seed;
- no manual insert ordering.

### Phase 2 — Reliability

**Goal:** không tạo data “có vẻ đúng” nhưng thực tế vi phạm constraint.

Main tasks:

- transaction handling;
- unique collision retry;
- cyclic FK handling;
- unsupported-type diagnostics;
- connection secret masking;
- structured logging;
- integration tests với Testcontainers;
- schema hash validation.

Expected output:

Tool fail-fast và actionable.

Completion criteria:

- failure không để DB half-seeded;
- tests cover common FK/unique/null scenarios;
- logs không chứa connection password.

### Phase 3 — Useful expansion

**Goal:** dùng tốt hơn cho QA/CI.

Main tasks:

- second DB provider;
- direct bulk insert;
- weighted distributions;
- reference tables;
- table/column heuristics;
- dataset manifest;
- scenario profiles.

Completion criteria:

- cùng profile chạy được trong local và CI;
- dataset vài chục nghìn rows generate trong thời gian chấp nhận được;

## 14. Các bài toán kỹ thuật đáng học

### 1. Graph algorithms cho database dependencies

Cần học:

- directed graph;
- topological sort;
- strongly connected components;
- cycle detection.

Skill cải thiện: biến relational schema thành executable generation plan.

### 2. Constraint-aware generation

Không chỉ random values.

Phải giải:

- unique;
- nullable;
- ranges;
- lengths;
- precision;
- composite keys;
- FK selection.

Skill cải thiện: data integrity và robust validation.

### 3. Reproducible randomness

Một bug hữu ích khi có thể nói:

```text
Reproduce with seed 87291
```

Cần hiểu random seed, generator ordering và nondeterminism.

Skill cải thiện: reproducible testing.

### 4. High-throughput database insertion

Ban đầu row-by-row được, nhưng dataset lớn cần:

- batching;
- PostgreSQL `COPY`;
- SQL Server bulk copy;
- transaction strategy.

Skill cải thiện: database performance.

### 5. Provider abstraction

SQL Server và PostgreSQL expose metadata khác nhau nhưng core không nên biết provider details.

Skill cải thiện:

- ports/adapters;
- canonical domain model;
- compatibility testing.

## 15. Rủi ro và cách xử lý

### Risk 1 — Business rules không nằm trong schema

Ví dụ:

```text
If Status = Inactive then EndDate must not be null
```

DB có thể không enforce rule này.

**Mitigation:** profile rule rõ ràng, không hứa zero-config perfection.

### Risk 2 — Circular foreign keys

Self-reference hoặc multi-table cycles có thể phá topological sort.

**Mitigation:** deferred relation pass; nếu không giải được thì diagnostic rõ ràng.

### Risk 3 — Trigger/stored procedure side effects

Insert fake data có thể trigger logic ngoài ý muốn.

**Mitigation:** nhấn mạnh chỉ chạy trên non-production database; optional `--confirm-target` guard.

### Risk 4 — User vô tình trỏ vào production

Đây là rủi ro nghiêm trọng nhất.

**Mitigation:**

- mặc định generate/export, không apply;
- `--apply` explicit;
- require allowlist DB name;
- block database names matching `prod|production` trừ khi override mạnh;
- preview target server/database trước insert.

### Risk 5 — Unique-space quá nhỏ

Ví dụ code chỉ có 5 giá trị nhưng user đòi 100 unique rows.

**Mitigation:** detect/retry limit và fail với explanation.

### Risk 6 — Scale

1 triệu rows sẽ chậm nếu dùng per-row insert.

**Mitigation:** MVP giới hạn scale; Phase 3 thêm bulk writer.

### Risk 7 — Privacy

Nếu tool chỉ generate synthetic data thì privacy risk thấp hơn clone production.

Nhưng profile hoặc schema names vẫn có thể nhạy cảm.

**Mitigation:** local-first; AI off by default; no telemetry mặc định.

### Risk 8 — Scope explosion

User có thể yêu cầu stored procedures, triggers, full DB cloning, anonymization, data masking, snapshots.

**Mitigation:** giữ product boundary:

> Generate synthetic relational data from schema + explicit rules.

## 20. Việc cần làm ngay hôm nay

### Thời lượng

Khoảng **90 phút**.

### Development objective

Tạo vertical slice nhỏ nhất chứng minh core idea:

> Đọc 3-table schema từ PostgreSQL, xây FK graph và in đúng generation order.

Chưa generate fake values, chưa UI, chưa AI.

### Sample schema

Dùng:

```sql
CREATE TABLE customer (
    id uuid PRIMARY KEY,
    name varchar(100) NOT NULL,
    email varchar(255) NOT NULL UNIQUE
);

CREATE TABLE orders (
    id uuid PRIMARY KEY,
    customer_id uuid NOT NULL REFERENCES customer(id),
    created_at timestamptz NOT NULL
);

CREATE TABLE order_item (
    id uuid PRIMARY KEY,
    order_id uuid NOT NULL REFERENCES orders(id),
    product_name varchar(200) NOT NULL,
    quantity int NOT NULL
);
```

Expected graph:

```text

  -> orders
      -> order_item
```

Expected generation order:

```text
1. customer
2. orders
3. order_item
```

### Test đầu tiên

```csharp
[Fact]
public void Should_order_parent_before_child()
{
    var schema = TestSchema.Create(
        "customer",
        "orders",
        "order_item",
        fk: new[]
        {
            ("orders", "customer"),
            ("order_item", "orders")
        });

    var order = new GenerationPlanner()
        .BuildInsertionOrder(schema);

    Assert.Equal(
        new[] { "customer", "orders", "order_item" },
        order);
}
```

### Expected result

Sau session đầu tiên phải có một command thật kết nối PostgreSQL và in được dependency order.

Đó là bằng chứng phần kỹ thuật khó nhất của idea — schema introspection → dependency graph — khả thi.

### Verification checklist

- [ ] PostgreSQL container chạy.
- [ ] 3 tables được tạo.
- [ ] CLI connect thành công.
- [ ] Discover đủ 3 tables.
- [ ] Discover đúng 2 foreign keys.
- [ ] Generation order = customer → orders → order_item.
- [ ] Unit test topological sort pass.
- [ ] `dotnet test` pass.
- [ ] Không hardcode table order trong planner.

### Stop condition

**Dừng session khi CLI in đúng generation order từ schema PostgreSQL thật.**

Không thêm Bogus, không tạo web UI, không sinh hàng nghìn records trong session đầu. Nếu phần graph chạy được, session sau mới thêm `ColumnSchema` và generate 10 customers + 50 orders với deterministic seed.

## Kết luận

DataForge giải quyết một vấn đề rất cụ thể: **test data hiện nay thường khó tái tạo, quá ít hoặc phụ thuộc vào production**, trong khi schema database đã chứa đủ metadata để tự động hóa phần lớn relational setup. MVP có thể bắt đầu cực nhỏ với một provider và CLI, nhưng vẫn mở ra các bài toán kỹ thuật đáng học như graph planning, deterministic generation, constraint validation và high-throughput insert.

Điểm quan trọng là giữ phạm vi rõ ràng: **synthetic relational test data từ schema + explicit rules**, không cố tự động hiểu toàn bộ business domain. Với boundary đó, đây là project một developer có thể hoàn thành, dùng được ngay cho chính workflow của mình và đủ chiều sâu để trở thành một open-source developer tool nghiêm túc.
