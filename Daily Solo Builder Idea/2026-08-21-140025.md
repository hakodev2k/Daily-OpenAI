# Ý tưởng hôm nay: RuleShadow — Outlook Inbox Rule Auditor & Replay Sandbox

## 1. Tóm tắt ý tưởng

**RuleShadow** là một công cụ self-hosted giúp người dùng Microsoft 365/Outlook kiểm tra các Inbox rules hiện có, phát hiện rule trùng lặp, rule bị “che” bởi thứ tự xử lý, rule lỗi/disabled, hành động forwarding hoặc delete đáng chú ý, rồi **mô phỏng một email sẽ đi qua chuỗi rule như thế nào trước khi người dùng sửa rule thật**. Sản phẩm nhắm tới developer hoặc power user có nhiều rule Outlook nhưng khó biết rule nào đang gây mất email, chuyển sai folder hoặc tạo hành vi khó dự đoán.

- Người dùng chính: developer/power user dùng Outlook hoặc Microsoft 365 với nhiều Inbox rules.
- Bài toán chính: rule tích lũy lâu ngày, thứ tự và điều kiện chồng chéo khiến email bị xử lý khác với kỳ vọng.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

### Confirmed facts

Microsoft Graph có API chính thức để làm việc với Outlook message rules. Microsoft mô tả Inbox rules là các rule áp dụng lên message đến dựa trên conditions, actions và exceptions; rule có thuộc tính như `sequence`, `isEnabled`, `hasError`, `isReadOnly`, và action có thể bao gồm move/copy, mark, forward, redirect hoặc stop processing các rule phía sau.

Nguồn chính thức:

- [Organize Outlook messages using the Outlook mail API — Microsoft Learn](https://learn.microsoft.com/en-us/graph/outlook-organize-messages)
- [messageRule resource type — Microsoft Learn](https://learn.microsoft.com/en-us/graph/api/resources/messagerule?view=graph-rest-1.0)
- [List rules — Microsoft Learn](https://learn.microsoft.com/en-us/graph/api/mailfolder-list-messagerules?view=graph-rest-1.0)

Microsoft Graph v1.0 hỗ trợ endpoint đọc Inbox rules qua `GET /me/mailFolders/inbox/messageRules`. Tài liệu hiện tại liệt kê `MailboxSettings.Read` là permission delegated read-only tối thiểu cho việc list rules. Đây là nền tảng đủ để xây một auditor read-only mà không cần quyền chỉnh sửa mailbox ngay từ MVP.

Microsoft cũng hỗ trợ delta query/change notifications cho mail nếu sau này cần theo dõi message changes thay vì polling toàn bộ mailbox, nhưng MVP không cần dùng các capability này. Nguồn: [Outlook mail API overview — Microsoft Learn](https://learn.microsoft.com/en-us/graph/outlook-mail-concept-overview).

### Vấn đề thực tế

Inbox rules thường được tạo rất nhanh để giải quyết một nhu cầu nhỏ:

- email từ hệ thống A → folder A;
- subject chứa `Invoice` → folder Finance;
- sender B → mark as read;
- notification C → delete;
- một loại email → forward sang địa chỉ khác.

Sau vài tháng hoặc vài năm, mailbox có thể tích lũy nhiều rule với condition tương tự nhưng khác thứ tự. Khi một email không xuất hiện ở Inbox, người dùng thường phải mở từng rule và tự suy luận xem rule nào đã match.

Các tình huống dễ xảy ra:

1. Rule đầu tiên match và bật `stopProcessingRules`, khiến rule phía dưới không bao giờ chạy với cùng nhóm email.
2. Hai rule cùng match nhưng move message sang hai folder khác nhau.
3. Rule cũ vẫn forward/redirect email dù business need đã thay đổi.
4. Rule bị disabled hoặc `hasError=true` nhưng người dùng không để ý.
5. Rule quá rộng, ví dụ chỉ dựa vào một keyword phổ biến trong subject.
6. Nhiều rule gần giống nhau làm người dùng không nhớ rule nào là rule “chính”.

### Observation

Outlook/Graph đã có UI và API để quản lý rule. Vì vậy RuleShadow không nên là “một màn hình khác để CRUD Inbox rules”. Giá trị riêng nên nằm ở:

- snapshot lịch sử rule;
- deterministic conflict detection;
- giải thích rule order;
- replay/simulation bằng message fixture;
- diff trước/sau thay đổi;
- read-only-by-default.

### Assumption cần validate

Ý tưởng chỉ đáng build nếu người dùng có đủ nhiều rule hoặc từng gặp sự cố email bị chuyển/xóa/forward sai. Nếu mailbox chỉ có 2–3 rule đơn giản, Outlook UI đã đủ.

## 3. Người dùng mục tiêu

### Primary user

Một developer hoặc power user dùng Microsoft 365/Outlook hàng ngày và có khoảng nhiều Inbox rules được tích lũy theo thời gian.

### Context sử dụng

Người dùng nhận nhiều loại email công việc:

- CI/CD notifications;
- GitHub/Azure alerts;
- ticket/QA notifications;
- billing/invoice;
- Microsoft 365 admin messages;
- vendor/system notifications;
- mailing lists;
- project-specific mail.

### Main pain point

Khi một email “biến mất”, người dùng không biết ngay:

- rule nào match;
- rule nào chạy trước;
- rule phía sau có còn cơ hội chạy không;
- message bị move, mark, forward hay delete;
- rule hiện tại có khác tuần trước không.

### Current workaround

- mở Outlook Settings và kiểm tra từng rule;
- disable rule từng cái rồi thử lại;
- search mailbox thủ công;
- ghi chú rule trong spreadsheet;
- xóa và tạo lại rule khi cấu hình quá rối.

### Vì sao họ thử RuleShadow

Vì tool không cần thay đổi mailbox trong MVP. Nó tạo một view kiểu “static analyzer + debugger cho Inbox rules”, an toàn hơn việc sửa thử trực tiếp trên mailbox thật.

## 4. Giải pháp đề xuất

### Main workflow

```text
Connect Microsoft account
→ load Inbox rules
→ normalize rules
→ compute findings
→ save snapshot
→ show ordered rule graph
→ select/create message fixture
→ simulate rule matching
→ show execution trace
→ user decides whether to change Outlook rule manually
→ re-scan
→ compare before/after
```

### Input

- Microsoft account/tenant authentication.
- Inbox rules từ Graph.
- Optional message fixture gồm:
  - sender;
  - recipients;
  - subject;
  - body preview/text optional;
  - importance;
  - categories;
  - attachment flag.
- Optional audit policies do user cấu hình.

### Processing

Deterministic engine thực hiện:

- parse rule conditions;
- parse exceptions;
- sort theo `sequence`;
- evaluate enabled/error state;
- simulate `stopProcessingRules`;
- map actions;
- detect overlaps/conflicts;
- compare snapshot changes.

### Output

Ví dụ finding:

```text
Potential shadowed rule

Rule #4: "Azure Alerts"
Condition: subject contains "Azure"
Action: move to /Alerts/Azure
Stop processing: true

Rule #8: "Azure Billing"
Condition: subject contains "Azure" AND "Invoice"
Action: move to /Finance/Azure

Why flagged:
Messages containing both "Azure" and "Invoice" may match Rule #4 first,
then Rule #8 may never execute because Rule #4 stops further processing.
```

Simulation trace:

```text
Fixture: "Azure Invoice August 2026"
From: billing@example.invalid

1. Rule #1 "GitHub"            → no match
2. Rule #4 "Azure Alerts"      → MATCH
   Action: move /Alerts/Azure
   stopProcessingRules = true
3. Rule #8 "Azure Billing"     → NOT EVALUATED

Final simulated result:
Folder: /Alerts/Azure
```

### Tự động hóa

RuleShadow tự động:

- lấy rule inventory;
- snapshot/diff;
- detect rule overlap;
- highlight risky action;
- simulate order;
- tạo execution trace.

### Người dùng vẫn kiểm soát

MVP không tự create/update/delete rule. Người dùng sửa rule trong Outlook/Entra-approved client rồi chạy scan lại.

### Key differentiator

**Replay sandbox + explainable rule trace**, không chỉ inventory.

### Ví dụ end-to-end

Người dùng nhận thấy invoice Azure không còn vào folder Finance. RuleShadow scan 34 rules và thấy rule `Azure Notifications` đứng trước `Azure Invoice`, condition rộng hơn và có `stopProcessingRules=true`.

Người dùng nhập fixture subject `Microsoft Azure Invoice #12345`. Simulator cho thấy message match rule đầu và rule Finance không được evaluate. Người dùng sửa thứ tự rule trong Outlook, scan lại và chạy cùng fixture. Trace mới cho thấy invoice vào đúng folder Finance.

Tool đã giải quyết vấn đề mà không cần quyền write mailbox.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Nếu chính developer có nhiều Outlook rules, sản phẩm có utility cá nhân ngay từ ngày đầu: tìm rule conflict và lưu lịch sử cấu hình mailbox.

### Technical learning value

Project có nhiều bài toán thú vị:

- Microsoft Graph auth;
- modeling một mini rule language;
- deterministic simulation;
- conflict analysis;
- privacy-preserving email fixtures;
- snapshot diff;
- permission minimization.

### Phù hợp solo developer

MVP chỉ cần một mailbox, Inbox rules, một web app/CLI và một deterministic rule evaluator. Không cần scrape Outlook UI, không cần ML, không cần microservices.

### Vẫn hữu ích với rất ít user

Một developer có thể dùng nó như personal mail configuration debugger. Không cần đạt network effect.

### Điều gì khiến ý tưởng thất bại

- Graph rule semantics có những edge case khó mô phỏng chính xác;
- người dùng ít rule nên không thấy giá trị;
- permission onboarding gây phiền;
- false positive quá nhiều;
- action/condition của Outlook phức tạp hơn scope MVP.

### Lý do mạnh nhất để không build

Nếu conflict detection không đủ chính xác để người dùng tin execution trace, tool sẽ trở thành dashboard “tham khảo” và không giúp debug thực sự. Vì vậy simulator cần bắt đầu bằng một subset rule rõ ràng, không giả vờ support toàn bộ semantics ngay từ đầu.

## 6. Phạm vi MVP

### Must have

- Login Microsoft account.
- List Inbox rules bằng Microsoft Graph v1.0.
- Lưu rule metadata:
  - id;
  - displayName;
  - sequence;
  - isEnabled;
  - hasError;
  - isReadOnly;
  - conditions;
  - exceptions;
  - actions.
- Snapshot mỗi lần scan.
- Diff rule added/removed/changed/reordered.
- Finding rules:
  - disabled;
  - has error;
  - duplicate/similar condition;
  - broad condition before narrow condition;
  - `stopProcessingRules` shadow candidate;
  - forward/redirect action requires review;
  - delete/permanent-delete action requires review nếu Graph action metadata thể hiện điều đó.
- Manual message fixture editor.
- Deterministic simulator cho subset condition phổ biến:
  - sender/from;
  - subject contains;
  - body/body-or-subject contains;
  - importance;
  - recipient contains;
  - attachment flag nếu rule API cung cấp predicate tương ứng.
- Simulation trace theo sequence.
- Export report Markdown/JSON.

### Should have

- Import một email sample bằng user-selected message ID với riêng permission read mail optional.
- Mask sender/recipient/domain trong persisted fixture.
- Saved fixtures.
- Rule coverage: fixture nào hit rule nào.
- Custom warning policies.
- “Compare before/after” simulation.

### Later

- Write mode create/update/delete rules.
- Shared mailbox support.
- Multiple mailboxes.
- Webhook/delta-based continuous monitoring.
- Policy-as-code.
- Automatic rule reorder proposal.
- AI explanation.
- Organization-wide auditing.

Không thêm các phần Later vào MVP.

## 7. Luồng hoạt động

### Normal flow

```text
User signs in
→ Graph auth validates MailboxSettings.Read
→ GET Inbox messageRules
→ normalize conditions/actions
→ validate supported semantics
→ persist snapshot
→ run analyzers
→ dashboard
→ user opens finding
→ creates/selects fixture
→ simulator evaluates rule #1..N
→ trace generated
→ user fixes Outlook manually
→ re-scan
→ diff + re-simulation
```

### Alternative flow: unsupported predicate

Một rule chứa condition chưa được simulator hỗ trợ.

```text
Rule loaded
→ condition recognized as unsupported
→ rule status = PartiallySimulatable
→ simulator does not guess
→ execution trace shows "unknown result"
```

Tool không được coi unknown là false.

### Failure flow: Graph permission missing

```text
GET rules → 403
→ connection status = MissingPermission
→ show required read-only permission
→ keep previous snapshots
```

### Failure flow: Graph unavailable/throttled

- retry với exponential backoff;
- respect `Retry-After` nếu có;
- không ghi empty snapshot thành “all rules deleted”.

### Failure flow: rule changed giữa scan và simulation

Simulation luôn gắn với một immutable `RuleSnapshotId`, vì vậy trace vẫn reproducible.

### Failure flow: fixture chứa dữ liệu nhạy cảm

MVP mặc định cho manual fixture và không cần body thật. Nếu import email sample sau này, raw body không persist mặc định; chỉ lưu normalized fields cần cho simulation.

## 11. API và tích hợp

### Microsoft Graph — Inbox rules

Endpoint chính:

```http
GET /me/mailFolders/inbox/messageRules
```

Purpose: lấy ordered Inbox rule definitions.

Microsoft document `MailboxSettings.Read` là least-privileged delegated permission cho list rules. Nguồn: [List rules](https://learn.microsoft.com/en-us/graph/api/mailfolder-list-messagerules?view=graph-rest-1.0).

**Privacy concern:** rule có thể chứa sender addresses, recipient addresses, forwarding targets và keywords. Đây vẫn là dữ liệu nhạy cảm dù không đọc mail body.

**Fallback:** nếu Graph lỗi, giữ snapshot cũ với trạng thái stale; không suy luận rules đã bị xóa.

### Microsoft Graph — Message API (optional Should Have)

Nếu user muốn import một email thật làm fixture, app cần permission đọc mail phù hợp theo endpoint message sử dụng. MVP nên **không yêu cầu permission này mặc định** để giữ principle of least privilege.

Fallback: manual fixture luôn hoạt động mà không cần đọc message thật.

### Change notifications / delta query — Later

Microsoft Graph hỗ trợ change notifications và delta synchronization cho mail. Chỉ cần nếu product tiến tới continuous monitoring; snapshot periodic/manual đủ cho MVP.

Nguồn: [Organize Outlook messages using Outlook mail API](https://learn.microsoft.com/en-us/graph/outlook-organize-messages) và [Outlook mail API overview](https://learn.microsoft.com/en-us/graph/outlook-mail-concept-overview).

### Cost / rate-limit concern

Một mailbox có ít rule nên request volume rất thấp. Không cần aggressive polling. Scan manual hoặc 1–4 lần/ngày là đủ.

### Permission concern

Điểm mạnh của MVP là auditor rules có thể hoạt động với permission read-only dành cho mailbox settings, không cần write access.

## 12. AI có thực sự cần thiết không?

**AI is not necessary.**

Core problem là một rule engine deterministic. LLM sẽ làm giảm khả năng kiểm chứng nếu dùng để quyết định rule có match hay không.

### AI có thể hỗ trợ sau MVP

AI chỉ nên dùng để biến trace kỹ thuật thành giải thích dễ đọc:

Input:

```json
{
  "finding": "shadow_candidate",
  "rule_a": "...normalized...",
  "rule_b": "...normalized...",
  "simulation_trace": "..."
}
```

Output:

```json
{
  "summary": "Rule A may prevent Rule B from running for Azure invoice emails.",
  "suggested_checks": [
    "Review stopProcessingRules on Rule A",
    "Test invoice fixture after changing sequence"
  ]
}
```

### Validation method

AI explanation phải tham chiếu finding/trace deterministic. Nó không được tự tạo kết luận mới không có evidence.

### Deterministic fallback

Không bật AI thì toàn bộ auditor/simulator vẫn hoạt động.

### Risks

- gửi rule/email metadata ra model;
- hallucination;
- cost;
- latency.

Do đó AI không thuộc MVP.

## 13. Kế hoạch triển khai

### Phase 0 — Validation

**Goal:** xác định Outlook rule conflict có thật trong mailbox test/personal được phép.

**Main tasks:**

- viết CLI login Graph;
- list Inbox rules;
- export tên/sequence/enabled/error/actions;
- manually inspect 10–30 rules;
- tìm duplicate/broad-vs-narrow candidates;
- thử tạo 5 manual fixtures và tự trace.

**Expected output:** Markdown report từ mailbox thật.

**Completion criteria:** tìm ít nhất một finding/actionable insight hoặc chứng minh trace giúp hiểu rule nhanh hơn Outlook UI.

### Phase 1 — Core MVP

**Goal:** read-only auditor + simulator end-to-end.

**Main tasks:**

- ASP.NET Core;
- Graph connector;
- rule normalization;
- PostgreSQL snapshot;
- analyzer;
- fixture editor;
- simulation engine;
- Vue trace UI.

**Expected output:** một fixture chạy qua rule snapshot và tạo trace reproducible.

**Completion criteria:** user debug được ít nhất một rule ordering problem mà không cần sửa rule thử-nghiệm trực tiếp.

### Phase 2 — Reliability

**Goal:** không tạo false confidence.

**Main tasks:**

- explicit support matrix cho predicates/actions;
- `Unknown` evaluation state;
- Graph throttling/error handling;
- immutable snapshot;
- PII masking;
- auth hardening;
- unit/integration/E2E tests;
- structured logs.

**Expected output:** unsupported rule không bao giờ bị silently coi là no-match.

**Completion criteria:** simulator có `Complete`, `Partial`, `Indeterminate` classification rõ ràng.

### Phase 3 — Useful expansion

**Goal:** biến thành tool sử dụng định kỳ.

## 14. Các bài toán kỹ thuật đáng học

### 1. Deterministic rule simulation

Phải chuyển Graph predicates/actions thành internal AST hoặc normalized model rồi evaluate theo order.

Kỹ năng cải thiện: interpreters, rule engines, domain modeling.

### 2. Three-valued evaluation: Match / NoMatch / Unknown

Nếu simulator chưa hỗ trợ một predicate, không thể giả định rule không match.

Ví dụ:

```text
Supported conditions → match
Unsupported condition → unknown
Rule result → indeterminate
```

Kỹ năng cải thiện: correctness modeling và safe static analysis.

### 3. Shadow/conflict detection

Hai conditions có quan hệ subset/superset không phải lúc nào cũng dễ xác định.

MVP chỉ nên detect các case explainable:

```text
subject contains [Azure]
vs
subject contains [Azure, Invoice]
```

Kỹ năng cải thiện: set reasoning và static analysis.

### 4. Permission minimization & privacy

Core tool chỉ cần rule settings, không cần đọc toàn bộ mailbox.

Kỹ năng cải thiện: OAuth scopes, Microsoft Graph permission design, data minimization.

### 5. Snapshot diff

Rule reorder có thể thay behavior dù condition/action không đổi.

Kỹ năng cải thiện: canonicalization, hashing, semantic diff và temporal data.

## 15. Rủi ro và cách xử lý

### Simulator khác semantics thật của Outlook

**Risk:** nguy hiểm nhất vì user có thể tin trace sai.

**Mitigation:** support subset rõ ràng; unknown state; test against mailbox fixtures; không claim full compatibility; expose normalized rule JSON/evidence.

### Rule data chứa PII

**Risk:** sender/forward address/keyword nhạy cảm.

**Mitigation:** self-host first; encrypt volume/DB; optional masking; không persist raw mail body mặc định.

### Permission onboarding

**Risk:** người dùng ngại consent app.

**Mitigation:** read-only `MailboxSettings.Read` core; mail-read permission tách optional.

### False positives

**Risk:** overlap không có nghĩa conflict business.

**Mitigation:** gọi là `Review`/`Candidate`, không gọi vulnerability; cho dismiss với reason.

### Write mode gây mất email

**Risk:** nếu tool chỉnh rule tự động, blast radius lớn.

**Mitigation:** không có write mode trong MVP.

### Scope creep

**Risk:** nhanh chóng muốn thành full Outlook client.

**Mitigation:** chỉ Inbox rule analysis + simulation + snapshots.

### API dependency

**Risk:** Graph behavior/schema thay đổi.

**Mitigation:** use v1.0, adapter layer, contract tests, normalized internal model.

### Failure-path tests

- token expired;
- Graph unavailable;
- unsupported action;

### Security tests

- no access token in logs;
- unauthenticated user cannot access rule snapshots;
- imported message body not persisted unless explicit opt-in;
- export respects masking policy.

### Data-quality tests

Canonical normalization phải giữ stable hash khi JSON property order thay đổi nhưng semantics không đổi.

### 5 scenario quan trọng nhất

1. **Broad rule trước narrow rule + stopProcessing=true** → narrow rule được flag shadow candidate.
2. **Cùng fixture nhưng rule order đổi** → final simulated folder thay đổi đúng trace.
3. **Unsupported predicate** → result `Indeterminate`, không phải `NoMatch`.
4. **Graph scan fail sau khi đã có snapshot cũ** → snapshot cũ giữ nguyên, không tạo mass deletion diff.
5. **Rule chỉ disabled** → xuất finding nhưng simulator bỏ qua rule theo enabled state.

### Research notes

**Confirmed facts:** Microsoft Graph v1.0 có API list Inbox rules; rule model bao gồm conditions/actions/exceptions và metadata về sequence/enabled/error; list-rules API hỗ trợ permission read-only cho mailbox settings. Microsoft Graph cũng có mail change notification/delta capabilities nếu sau này cần continuous monitoring.

**Observation:** Primitive quản lý rules đã có sẵn trong Outlook/Graph; phần có giá trị mới là explainable static analysis, snapshot diff và replay sandbox.

**Analysis:** Read-only-first làm MVP an toàn và giảm permission burden. Full Outlook semantics quá rộng, vì vậy simulator phải publish support matrix và dùng `Unknown/Indeterminate` thay vì đoán.

**Assumption:** người dùng có rule set đủ lớn sẽ đánh giá cao trace và conflict findings hơn việc tự kiểm tra Outlook Settings.

**Recommendation:** chỉ tiếp tục sang web dashboard/full simulator sau khi CLI V0 phát hiện hoặc giải thích được ít nhất một behavior thật trên mailbox được phép.
