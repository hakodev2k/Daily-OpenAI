# Ý tưởng hôm nay: ActionStorage Scout — GitHub Actions Artifact & Cache Cost Auditor

## 1. Tóm tắt ý tưởng

ActionStorage Scout là một developer tool self-hosted giúp developer **phân tích GitHub Actions artifact/cache đang chiếm bao nhiêu dung lượng, artifact nào đang bị giữ quá lâu, workflow nào tạo dữ liệu dư thừa và cleanup nào có thể thực hiện an toàn**. Công cụ tập trung vào một vấn đề rất thực tế: GitHub Actions có quota storage, retention, cache eviction và chi phí phát sinh, nhưng việc hiểu “repo nào/workflow nào đang làm đầy storage” thường bị phân tán giữa Actions UI, billing và workflow YAML.

- Người dùng chính: solo developer hoặc team nhỏ dùng GitHub Actions thường xuyên.
- Bài toán chính: artifact/cache tăng dần, khó xác định nguồn gây lãng phí và khó quyết định xóa gì mà không ảnh hưởng debug/release.
- Quy mô: **Medium**.
- Thời gian MVP ước tính: **2–3 tuần**.

## 2. Bài toán thực tế

GitHub Actions tạo ra nhiều loại dữ liệu tạm hoặc bán-tạm:

- build artifact;
- test report;
- Playwright screenshot/trace/video;
- code coverage;
- deployment package;
- cache NuGet/npm/pnpm;
- log của workflow;
- artifact được upload lại ở nhiều job hoặc nhiều run.

### Confirmed facts

GitHub hiện cho phép quản lý artifact thông qua REST API: có endpoint để **list**, **download** và **delete** Actions artifact. Metadata artifact bao gồm các trường như `size_in_bytes`, `created_at`, `expires_at`, `expired` và thông tin workflow run. Điều này đủ để xây dựng một inventory và cleanup engine mà không cần scraping UI.

Nguồn: GitHub Docs — REST API endpoints for GitHub Actions artifacts  
https://docs.github.com/en/rest/actions/artifacts

GitHub mặc định giữ workflow artifact/log trong **90 ngày**, và retention có thể tùy chỉnh trong giới hạn của repository/organization/enterprise. Artifact đã xóa thì không thể restore bằng GitHub UI.

Nguồn: GitHub Docs — Removing workflow artifacts  
https://docs.github.com/en/actions/how-tos/manage-workflow-runs/remove-workflow-artifacts

GitHub Actions storage là tài nguyên có quota theo plan. Tài liệu hiện tại ghi nhận ví dụ: GitHub Free có 500 MB Actions artifact storage, GitHub Pro có 1 GB, Team 2 GB và Enterprise Cloud 50 GB; storage vượt allowance có thể phát sinh chi phí. GitHub cũng ghi rõ storage charge được tích lũy theo thời gian trong billing cycle.

Nguồn: GitHub Docs — GitHub Actions billing  
https://docs.github.com/en/billing/concepts/product-billing/github-actions

Actions cache có lifecycle riêng. GitHub mô tả cache không được truy cập quá 7 ngày có thể bị xóa; cache storage repository mặc định có giới hạn và cache churn có thể dẫn tới tình trạng “cache thrashing”. GitHub cũng cung cấp REST API cho cache usage/storage limit.

Nguồn: GitHub Docs — Dependency caching reference  
https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching

Nguồn: GitHub Docs — REST API endpoints for GitHub Actions cache  
https://docs.github.com/en/rest/actions/cache

### Observation

GitHub cung cấp đủ primitive để xem artifact, cache và billing, nhưng developer vẫn phải tự ghép nhiều góc nhìn:

1. artifact nào lớn nhất;
2. workflow nào liên tục tạo artifact;
3. artifact nào ít giá trị nhưng retention dài;
4. artifact nào phục vụ release và không nên xóa;
5. cache nào đang churn;
6. thay đổi YAML nào sẽ giảm storage mà không làm mất khả năng debug.

### Assumption cần kiểm chứng

Solo developer hoặc team nhỏ có nhiều repository sẽ có nhu cầu một dashboard self-hosted cho câu hỏi:

> “Storage Actions của tôi đang đi đâu, và tôi có thể giảm nó như thế nào mà không phá workflow?”

Đây là giả định sản phẩm cần validation, không phải market fact đã được chứng minh.

### Cách xử lý hiện tại

Người dùng thường:

- mở từng repository → Actions → từng run → xem artifact;
- tự đặt `retention-days` trong từng workflow;
- dùng GitHub CLI/REST API để xóa thủ công;
- đợi artifact tự expire;
- xem billing tổng nhưng không có mental model rõ về workflow nào gây tăng storage;
- xóa cache khi gặp cache churn mà không biết nguyên nhân.

Điểm bất tiện là cleanup thường phản ứng sau khi storage đã thành vấn đề, thay vì dựa trên evidence và policy.

## 4. Giải pháp đề xuất

ActionStorage Scout hoạt động theo mô hình **inventory → classify → recommend → cleanup with approval**.

### Main workflow

1. User kết nối GitHub bằng fine-grained token hoặc GitHub App.
2. Chọn repository cần audit.
3. Tool gọi GitHub REST API để lấy artifact/cache metadata.
4. Tool lưu snapshot định kỳ.
5. Engine tính:
   - total bytes;
   - bytes theo workflow;
   - bytes theo artifact name;
   - artifact age;
   - duplicate pattern;
   - retention waste estimate;
   - cache churn indicator.
6. Dashboard hiển thị cleanup candidates.
7. User duyệt hoặc reject cleanup.
8. Tool xóa artifact qua GitHub API nếu được user xác nhận.

### Input

- repository list;
- GitHub credentials;
- policy:
  - protected artifact names;
  - minimum retention;
  - keep latest N runs;
  - release tag protection;
  - max artifact size;
  - max repository storage target.

### Processing

Deterministic rules trước:

- artifact đã quá X ngày;
- artifact thuộc failed run;
- artifact name giống debug output;
- artifact nằm ngoài latest N successful runs;
- artifact không gắn release/tag;
- artifact duplicate theo name + workflow + gần giống size;
- artifact retention cao hơn policy.

### Output

Ví dụ:

```text
Repository: hakodev2k/example
Estimated artifact storage: 3.8 GB

Top producers
1. playwright-report   1.6 GB
2. test-results        1.1 GB
3. publish-output      0.7 GB

Cleanup candidates
- 42 Playwright artifacts older than 14 days: 1.2 GB
- 16 duplicate publish artifacts: 410 MB
- 8 failed-run test bundles older than 7 days: 180 MB

Potential reclaim: 1.79 GB
Risk: Low/Medium
```

### What is automated

- inventory;
- snapshot;
- aggregation;
- candidate scoring;
- stale artifact detection;
- reporting;
- optional deletion sau approval.

### User control

User quyết định:

- repository nào được audit;
- retention policy;
- artifact nào được protect;
- cleanup có được execute hay không;
- tool có quyền read-only hay write.

### Key differentiator

Không chỉ là “delete old artifact script”. Công cụ giữ lịch sử và trả lời câu hỏi **artifact nào tạo ra storage theo thời gian, workflow nào gây ra nó, và cleanup nào ít rủi ro nhất**.

### Ví dụ end-to-end

Một repository chạy Playwright mỗi giờ và upload:

```text
playwright-report
trace.zip
screenshots
```

Sau 10 ngày, Scout phát hiện:

- artifact `playwright-report` chiếm 58% storage;
- 80% artifact thuộc successful run;
- user thực tế chỉ cần giữ failed run lâu;
- workflow hiện dùng `retention-days: 30` cho mọi run.

Scout đề xuất:

- successful run: giữ 3 ngày;
- failed run: giữ 14 ngày;
- release artifact: giữ 30 ngày;
- protect latest successful artifact.

User duyệt 70 artifact cũ → tool xóa → lưu audit log về số byte đã reclaim.

## 5. Tại sao ý tưởng này đáng làm

### Practical value

Đây là một tool có thể dùng ngay cho chính các repository cá nhân có GitHub Actions. Giá trị xuất hiện ngay cả khi chỉ có một user.

### Technical learning value

Project có nhiều bài toán thực tế:

- GitHub REST API;
- pagination;
- rate limiting;
- scheduled synchronization;
- idempotent cleanup;
- policy engine;
- cost/storage analytics;
- OAuth/GitHub App permissions;
- observability;
- safe destructive operations.

### Vì sao phù hợp solo developer

Core domain khá nhỏ:

```text
GitHub metadata
→ normalize
→ calculate usage
→ recommend
→ optional delete
```

Không cần machine learning, không cần distributed architecture, không cần large dataset.

### Vì sao vẫn hữu ích với rất ít user

Một người có nhiều repositories vẫn đủ tạo recurring value: tool giảm thao tác thủ công và giúp hiểu Actions storage tốt hơn.

### Điều gì làm dự án thất bại

- GitHub UI/billing đã đủ tốt đối với đa số target user.
- Savings quá nhỏ nên user không quan tâm.
- Cleanup recommendation thiếu trust.
- Authentication setup quá phiền.
- Tool chỉ hiển thị số liệu nhưng không đưa ra hành động cụ thể.

### Lý do mạnh nhất để không build

Nếu bạn chỉ có 1–2 repo nhỏ và không gần chạm quota, một script GitHub CLI 30 dòng có thể đủ. Khi đó dashboard/persistence sẽ là overengineering.

MVP tuyệt đối không tự động xóa artifact theo schedule nếu user chưa cấu hình explicit policy.

## 7. Luồng hoạt động

### Sync flow

User chọn repo
→ validate GitHub permission
→ list artifacts với pagination
→ normalize metadata
→ upsert artifact snapshot
→ aggregate usage
→ chạy policy evaluator
→ lưu recommendation
→ dashboard hiển thị kết quả.

### Cleanup flow

User chọn candidate
→ tool kiểm tra candidate vẫn tồn tại
→ re-fetch metadata hiện tại
→ kiểm tra protection rule
→ hiển thị artifact ID/name/size/age
→ user xác nhận
→ gọi GitHub DELETE artifact endpoint
→ GitHub trả success/failure
→ ghi audit log
→ update local state.

### Alternative flows

#### Artifact đã expire trước khi cleanup

- API trả không còn artifact.
- Mark `AlreadyExpired`.
- Không retry deletion.

#### Rate limit

- Tôn trọng response headers.
- Dừng batch.
- Retry sau với exponential backoff.

#### Permission thiếu

Read-only token:

- inventory được;
- delete button disable.

Write Actions permission:

- cho phép deletion.

GitHub tài liệu hiện tại yêu cầu Actions repository permission `read` để list artifact bằng fine-grained token và `write` để delete artifact.

Nguồn:  
https://docs.github.com/en/rest/actions/artifacts

#### Artifact protected

- không được đưa vào destructive candidate;
- vẫn hiển thị trong analytics.

#### GitHub API unavailable

- giữ snapshot gần nhất;
- dashboard đánh dấu dữ liệu stale;
- không cho cleanup trên stale state.

## 11. API và tích hợp

### GitHub Actions Artifacts REST API

**Purpose:** list/delete artifact.

**Authentication:** fine-grained PAT hoặc GitHub App token.

**Permissions:**

- list: Actions read;
- delete: Actions write.

**Cost/rate limit:** phải xử lý GitHub API rate limit và pagination.

**Privacy:** metadata có thể tiết lộ branch name, artifact name, commit SHA; không public dashboard.

**Fallback:** read-only CSV/JSON import từ GitHub CLI trong development mode.

Nguồn:  
https://docs.github.com/en/rest/actions/artifacts

### GitHub Actions Cache REST API

**Purpose:** cache usage/storage limit và cache inventory trong phase sau.

**Authentication:** GitHub token với permission phù hợp.

**Concern:** cache lifecycle khác artifact; không gộp hai loại thành cùng cleanup rule.

**Fallback:** bỏ cache analysis khỏi MVP.

Nguồn:  
https://docs.github.com/en/rest/actions/cache

### GitHub Billing data

**Purpose:** correlation giữa observed storage và account-level cost.

**MVP:** không bắt buộc.

GitHub hiện cung cấp tài liệu billing và SKU cho Actions, bao gồm artifact/cache storage. Tuy nhiên billing permissions và account context phức tạp hơn repository inventory.

Nguồn:  
https://docs.github.com/en/billing/concepts/product-billing/github-actions

Fallback:

- MVP chỉ tính bytes và potential reclaim;
- không claim dollar savings nếu chưa có billing data chính xác.

### GitHub workflow YAML

Không cần API đặc biệt ở MVP.

Phase sau có thể:

- fetch `.github/workflows/*.yml`;
- tìm `actions/upload-artifact`;
- đọc `retention-days`;
- tạo suggested patch.

## 12. AI có thực sự cần thiết không?

**AI is useful but optional.**

Core engine không cần AI.

### Những việc deterministic code làm tốt hơn

- cộng storage;
- group artifact;
- tính age;
- identify expiration;
- retention rule;
- duplicate naming pattern;
- cleanup candidate;
- GitHub deletion;
- permission validation.

### AI task có thể thêm sau

AI có thể đọc:

- workflow YAML;
- artifact history;
- policy;

và tạo explanation như:

```json
{
  "finding": "Playwright success artifacts retained too long",
  "evidence": {
    "workflow": "e2e.yml",
    "artifact": "playwright-report",
    "retentionDays": 30,
    "monthlyObservedBytes": 4123456789
  },
  "suggestion": "Reduce successful-run retention to 3 days while keeping failed runs for 14 days",
  "confidence": 0.84
}
```

### Validation

AI không được phép trực tiếp xóa artifact.

Mọi recommendation phải được map về deterministic evidence:

- artifact IDs;
- actual bytes;
- age;
- workflow name;
- policy rule.

### Deterministic fallback

Nếu không cấu hình AI:

- rule engine vẫn cung cấp toàn bộ core value.

### Risks

- hallucination về GitHub behavior;
- token cost;
- latency;
- workflow YAML có thể chứa thông tin nhạy cảm;
- recommendation nghe hợp lý nhưng sai context.

Vì vậy AI chỉ nên làm explanation layer, không phải decision engine.

## 14. Các bài toán kỹ thuật đáng học

### 1. API pagination và rate limiting

Artifact count có thể lớn, nên sync phải xử lý nhiều page và partial failure.

Kỹ năng học được:

- resilient HTTP client;
- pagination abstraction;
- backoff;
- rate-limit awareness.

### 2. Safe destructive operations

Delete artifact là irreversible theo GitHub documentation.

Kỹ năng học được:

- revalidation;
- approval workflow;
- immutable audit log;
- dry-run;
- idempotency.

### 3. Historical data modeling

Nếu chỉ lưu current state thì không biết workflow nào đang tăng storage theo thời gian.

Kỹ năng học được:

- snapshot vs current state;
- time-series aggregation;
- retention policy;
- storage-efficient analytics.

### 4. Policy engine

Cleanup không thể chỉ dựa vào tuổi artifact.

Ví dụ:

```text
keep release-* forever within GitHub retention limit
keep latest 3 successful publish artifacts
keep failed Playwright traces 14 days
delete successful Playwright reports after 3 days
```

Kỹ năng học được:

- policy modeling;
- rule evaluation;
- precedence;
- explainability.

### 5. Permission design

Read-only mode và cleanup mode nên tách rõ.

Kỹ năng học được:

- least privilege;
- GitHub fine-grained permissions;
- privilege escalation avoidance;
- token storage.

## 15. Rủi ro và cách xử lý

### Risk 1 — Xóa artifact còn cần thiết

**Impact:** mất release package hoặc debug evidence.

**Mitigation:**

- manual approval mặc định;
- protected pattern;
- keep-latest-N;
- revalidate trước delete;
- release/tag protection;
- dry-run;
- audit log.

### Risk 2 — API dependency

GitHub API có rate limit hoặc downtime.

**Mitigation:**

- incremental sync;
- exponential backoff;
- stale-data marker;
- không cleanup khi sync chưa fresh.

### Risk 3 — Credential leakage

PAT/GitHub App token rất nhạy cảm.

**Mitigation:**

- fine-grained token;
- encrypt at rest;
- không log token/header;
- read-only permission mặc định;
- write permission chỉ khi bật cleanup.

### Risk 4 — Savings nhỏ

Nhiều user có thể chưa bao giờ vượt quota.

**Mitigation:**

Validation trước với repository có nhiều CI artifact; position tool như visibility + hygiene, không chỉ “cost saving”.

### Risk 5 — Scope expansion thành GitHub FinOps

Dễ kéo thêm runner minute, packages, Codespaces, billing, container registry.

**Mitigation:**

Core product chỉ tập trung:

```text
Actions artifact + cache storage
```

trong ít nhất 3 phase đầu.

### Risk 6 — Estimate cost sai

Storage billing có thể phụ thuộc plan/account/current pricing.

**Mitigation:**

MVP không chuyển bytes thành USD nếu không có billing data đã verify. Hiển thị:

```text
Potential reclaim: 1.8 GB
```

thay vì claim:

```text
You save $X/month
```

### Risk 7 — Data volume local

Snapshot mỗi artifact mỗi giờ có thể phình DB.

**Mitigation:**

- current state + daily aggregate;
- snapshot dedup;
- raw snapshot retention 30 ngày;
- compact historical metrics.

### Security tests

- token không xuất hiện trong logs;
- read-only user không trigger delete;
- SSRF không áp dụng nhiều vì target API cố định GitHub, nhưng callback/config URL nếu thêm sau phải validate;
- CSRF protection cho destructive action nếu dùng cookie auth.

### Data-quality tests

- tổng group-by bằng tổng artifact size;
- artifact không double-count giữa page;
- expired artifact không tính active storage sau state refresh;
- historical aggregate không bị duplicate khi rerun sync.

### 5 test scenario quan trọng nhất

1. Repository có 250 artifact → pagination sync đủ 250, không duplicate.
2. Candidate được generate từ snapshot nhưng artifact bị xóa bên ngoài trước khi approve → tool mark missing, không lỗi batch.
3. Protected artifact `release-*` không bao giờ xuất hiện trong executable cleanup list.
4. GitHub trả rate-limit → worker backoff và resume mà không tạo duplicate snapshot.
5. User approve 10 artifact → chỉ 10 artifact được delete và audit log ghi đúng total reclaimed bytes.

```text
GitHub repository
```

### First vertical slice

Implement GitHub request:


```csharp
    DateTimeOffset? ExpiresAt,
    bool Expired,
    long? WorkflowRunId);
```

Analyzer:

```csharp
public sealed record ArtifactSummary(
    int Count,
    long TotalBytes,
    IReadOnlyList<ArtifactInfo> Largest,
    IReadOnlyList<ArtifactInfo> OlderThanThreshold);
```
