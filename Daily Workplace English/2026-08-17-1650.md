# Daily Workplace English — Ngày 14

- **Ngày:** 17/08/2026 (UTC+7)
- **Tình huống công việc:** Góp ý code review về một thay đổi có thể gây lỗi khi xử lý `null`
- **Kỹ năng giao tiếp chính:** Đưa ra code-review feedback rõ ràng, tập trung vào code thay vì người viết, và đề xuất cách sửa
- **Thời gian học:** 20 phút
- **Độ khó:** Lower-intermediate

## 1. Tình huống hôm nay

Bạn đang review một Pull Request của đồng nghiệp cho một ASP.NET Core API. Trong đoạn code mới, service gọi repository để lấy một entity rồi sử dụng ngay property của entity đó. Tuy nhiên, repository có thể trả về `null` nếu record không tồn tại.

Người liên quan gồm bạn và một backend developer khác. Bạn cần để lại comment trên Pull Request để chỉ ra rủi ro `NullReferenceException`, giải thích khi nào lỗi có thể xảy ra và gợi ý một cách xử lý an toàn hơn.

Khó khăn giao tiếp là feedback quá trực tiếp như “This code is wrong” dễ làm người nhận tập trung vào giọng điệu thay vì vấn đề kỹ thuật. Ngược lại, feedback quá mềm như “Maybe this could possibly be improved” lại không nói rõ mức độ rủi ro.

Mục tiêu là dùng cấu trúc:

**Observation → Risk → Scenario → Suggestion → Confirmation**

## 2. Bạn cần nói gì?

Trong một code-review comment tốt, bạn nên:

- Chỉ ra chính xác đoạn logic cần chú ý.
- Mô tả rủi ro kỹ thuật thay vì đánh giá người viết code.
- Nêu trường hợp cụ thể mà lỗi có thể xảy ra.
- Đề xuất một hướng sửa rõ ràng.
- Khi cần, đặt câu hỏi để xác nhận assumption thay vì khẳng định điều chưa chắc chắn.

Ví dụ, thay vì nói:

> “You forgot the null check.”

Bạn có thể nói:

> “This value can be null when the record doesn’t exist, so we may want to handle that case before accessing `Status`.”

Câu thứ hai tập trung vào **behavior của code**, không tập trung vào lỗi của người viết.

## 3. Đoạn hội thoại hoặc mẫu trình bày

**Reviewer:** “I noticed that `GetByIdAsync` can return null when the record doesn’t exist.”  
*Mình để ý rằng `GetByIdAsync` có thể trả về null khi record không tồn tại.*

**Reviewer:** “In that case, accessing `employee.Status` here could throw a `NullReferenceException`.”  
*Trong trường hợp đó, việc truy cập `employee.Status` ở đây có thể gây `NullReferenceException`.*

**Reviewer:** “Could we handle the null case before checking the status?”  
*Mình có thể xử lý trường hợp null trước khi kiểm tra status được không?*

**Developer:** “Good catch. I assumed the employee would always exist at this point.”  
*Đúng rồi, chỗ này mình đã giả định employee luôn tồn tại.*

**Reviewer:** “That assumption may be valid for the current flow, but the service can also be called from the background job.”  
*Giả định đó có thể đúng với flow hiện tại, nhưng service cũng có thể được gọi từ background job.*

**Reviewer:** “I’d suggest returning `NotFound` or handling the missing record explicitly here.”  
*Mình đề xuất trả về `NotFound` hoặc xử lý rõ ràng trường hợp không có record tại đây.*

**Developer:** “Makes sense. I’ll add the null handling and update the tests.”  
*Hợp lý. Mình sẽ thêm xử lý null và cập nhật tests.*

## 4. Các cụm từ quan trọng

### 1. “I noticed that…”

- **Nghĩa:** Tôi để ý rằng…
- **Khi dùng:** Mở đầu một observation trong code review mà không mang tính phán xét.
- **Ví dụ:** “I noticed that this query is executed twice in the same request.”

### 2. “In that case, … could …”

- **Nghĩa:** Trong trường hợp đó, … có thể…
- **Khi dùng:** Giải thích consequence hoặc risk của một scenario cụ thể.
- **Ví dụ:** “In that case, the retry could create a duplicate record.”

### 3. “Could we handle … before …?”

- **Nghĩa:** Chúng ta có thể xử lý … trước khi … được không?
- **Khi dùng:** Đề xuất thay đổi code dưới dạng câu hỏi cộng tác.
- **Ví dụ:** “Could we validate the input before calling the external API?”

### 4. “That assumption may be valid for…”

- **Nghĩa:** Giả định đó có thể đúng đối với…
- **Khi dùng:** Khi muốn công nhận logic hiện tại nhưng chỉ ra rằng nó không đúng trong mọi context.
- **Ví dụ:** “That assumption may be valid for the UI flow, but this endpoint is also used by integrations.”

### 5. “I’d suggest…”

- **Nghĩa:** Tôi đề xuất…
- **Khi dùng:** Đưa ra recommendation rõ ràng nhưng vẫn giữ tính hợp tác.
- **Ví dụ:** “I’d suggest moving this validation into the service layer.”

### 6. “Could this happen when…?”

- **Nghĩa:** Trường hợp này có thể xảy ra khi… không?
- **Khi dùng:** Khi bạn chưa chắc assumption của mình đúng và muốn xác nhận scenario.
- **Ví dụ:** “Could this happen when two jobs process the same record at the same time?”

### 7. “Good catch.”

- **Nghĩa:** Phát hiện hay / cảm ơn đã chỉ ra.
- **Khi dùng:** Phản hồi ngắn khi đồng ý với một review comment hữu ích.
- **Ví dụ:** “Good catch. I missed that edge case.”

## 6. Mẫu câu hoặc ngữ pháp cần nhớ

### Dùng `could` để nói về rủi ro kỹ thuật có khả năng xảy ra

**Cấu trúc:**

`Subject + could + base verb`

Ví dụ:

> “Accessing `employee.Status` here could throw a `NullReferenceException`.”

`could` rất hữu ích trong code review vì nó diễn tả một **khả năng/rủi ro**, không khẳng định chắc chắn rằng lỗi luôn xảy ra.

Các ví dụ khác:

- “This query could become slow when the table grows.”
- “The retry could create duplicate records.”
- “This change could break clients that still use the old response format.”

### Khi nào dùng

Dùng khi:

- Có một scenario có thể gây lỗi.
- Bạn muốn mô tả risk thay vì nói lỗi chắc chắn xảy ra.
- Bạn chưa có bằng chứng rằng behavior xảy ra trong mọi trường hợp.

### Lỗi thường gặp

Sai:

> “This code could throws an exception.”

Đúng:

> “This code could throw an exception.”

Sau modal verb như `could`, dùng **động từ nguyên mẫu không `to`**: `could throw`, không phải `could throws`.

## 7. Cách nói tự nhiên hơn

### Chưa tự nhiên hoặc quá trực tiếp

“You forgot the null check.”

### Tự nhiên và chuyên nghiệp hơn

“This value can be null, so we may want to add a null check before accessing the property.”

### Giải thích

Câu đầu tập trung vào việc người viết “quên”. Câu sau tập trung vào behavior của code và hành động cần làm. Trong code review, cách này thường giúp trao đổi khách quan hơn.

### Chưa tự nhiên hoặc quá trực tiếp

“This code is wrong.”

### Tự nhiên và chuyên nghiệp hơn

“This could fail when the record doesn’t exist.”

### Giải thích

`wrong` quá chung chung. Phiên bản thứ hai nói rõ **failure condition**, giúp người nhận hiểu và sửa nhanh hơn.

### Chưa tự nhiên hoặc quá trực tiếp

“Change this to return NotFound.”

### Tự nhiên và chuyên nghiệp hơn

“I’d suggest returning `NotFound` here, unless there’s a reason we need to continue when the record is missing.”

### Giải thích

Khi có nhiều thiết kế hợp lệ, `I’d suggest` phù hợp hơn mệnh lệnh trực tiếp. Tuy nhiên, nếu đây là security issue, production bug hoặc project convention bắt buộc, feedback trực tiếp như “This needs to be fixed before merge” hoàn toàn phù hợp.

## 8. Phát âm và luyện nói

### “I noticed that this can be null.”

Nhấn **NOTICED** và **NULL**. `that` thường nhẹ hơn. Có thể ngắt:

“I **NOTICED** that / this can be **NULL**.”

Không cần cố đọc mọi từ với cùng lực nhấn.

### “This could throw a NullReferenceException.”

Nhấn **THROW** và phần chính của **NullReferenceException**. `could` thường không cần nhấn mạnh trừ khi bạn muốn đối lập giữa khả năng và chắc chắn.

“This could **THROW** / a `NullReferenceException`.”

### “I’d suggest handling the null case here.”

Nhấn **SUGGEST**, **NULL CASE**, **HERE**. `I’d` là dạng rút gọn của `I would`; nói liền thay vì tách thành hai từ.

“I’d **SUGGEST** / handling the **NULL CASE** here.”

Các ghi chú trên chỉ giúp bạn chú ý nhịp và trọng âm; cách ghi bằng tiếng Việt không thể thay thế phát âm chuẩn từ audio.

### Shadowing script

> “I noticed that this value can be null when the record doesn’t exist. In that case, accessing the property could throw a `NullReferenceException`. Could we handle the null case before checking the status? I’d suggest returning `NotFound` or handling the missing record explicitly.”

Cách luyện:

1. Đọc chậm từng câu.
2. Nghe lại bằng Text-to-Speech nếu có.
3. Lặp lại từng câu, tập trung vào từ được nhấn.
4. Ghi âm và nghe lại giọng của bạn.
5. Nói toàn bộ review comment mà không nhìn văn bản.

## 9. Bài tập nhanh

### Bài 1 — Điền từ

“This line ______ throw a `NullReferenceException` when the entity is null.”

A. could  
B. coulds  
C. could to

### Bài 2 — Chọn feedback chuyên nghiệp hơn

A. “You wrote this wrong.”  
B. “This could fail when the record doesn’t exist.”  
C. “Bad code.”

### Bài 3 — Viết lại câu

Viết lại câu sau thành một code-review comment tập trung vào code thay vì người viết:

> “You forgot to validate the input.”

### Bài 4 — Hoàn thành câu

“I’d suggest ______ the null case before accessing `Status`.”

A. handle  
B. handling  
C. handled

### Bài 5 — Chọn câu phù hợp khi chưa chắc assumption

Bạn nghi ngờ hai background jobs có thể update cùng một record.

A. “Two jobs always update this record together.”  
B. “Could this happen when two jobs process the same record at the same time?”  
C. “Your concurrency logic is wrong.”

### Bài 6 — Sắp xếp comment theo thứ tự hợp lý

A. “I’d suggest handling the missing record explicitly.”  
B. “`GetByIdAsync` can return null.”  
C. “In that case, accessing `Status` could throw an exception.”

## 10. Bài tập thực hành chủ động

### Scenario

Bạn đang review một Pull Request. Đoạn code mới dùng `FirstAsync()` để lấy một record từ database. Theo flow hiện tại record thường tồn tại, nhưng nếu dữ liệu đã bị xóa trước đó thì query có thể throw exception. Bạn muốn đề xuất xử lý trường hợp không tìm thấy record một cách rõ ràng.

### Các ý bắt buộc

Viết một review comment 4–6 câu có:

- Observation: bạn thấy điều gì trong code.
- Risk: lỗi gì có thể xảy ra.
- Scenario: khi nào lỗi xảy ra.
- Suggestion: bạn đề xuất sửa thế nào.
- Question hoặc confirmation nếu có assumption chưa chắc chắn.

### Cấu trúc gợi ý

`Observation → Possible issue → Scenario → Suggestion → Question`

### Cụm từ có thể dùng

- “I noticed that…”
- “In that case, … could …”
- “Could this happen when…?”
- “Could we handle…?”
- “I’d suggest…”

### Tiêu chí hoàn thành

Comment của bạn đạt yêu cầu nếu người nhận có thể trả lời ba câu hỏi ngay lập tức:

1. Vấn đề nằm ở đâu?
2. Tại sao nó là một risk?
3. Bạn đề xuất thay đổi gì?

## 11. Đáp án và giải thích

### Bài 1

**Đáp án: A — could**

> “This line could throw a `NullReferenceException` when the entity is null.”

Sau `could` dùng động từ nguyên mẫu: `could throw`.

### Bài 2

**Đáp án: B**

> “This could fail when the record doesn’t exist.”

Câu này chỉ ra condition cụ thể và tập trung vào behavior của code. A và C đánh giá người viết hoặc code mà không giải thích vấn đề.

### Bài 3

Một đáp án tốt:

> “It looks like the input is used before validation. Could we validate it before calling the service?”

Hoặc:

> “This input can be invalid here, so we may want to validate it before processing the request.”

Cả hai đều chuyển trọng tâm từ **“you forgot”** sang **behavior + suggestion**.

### Bài 4

**Đáp án: B — handling**

> “I’d suggest handling the null case before accessing `Status`.”

Sau `suggest` có thể dùng gerund: `suggest doing something`.

### Bài 5

**Đáp án: B**

> “Could this happen when two jobs process the same record at the same time?”

Bạn chưa chắc scenario có thể xảy ra nên dùng câu hỏi để xác nhận assumption thay vì khẳng định.

### Bài 6

**Đáp án: B → C → A**

> “`GetByIdAsync` can return null. In that case, accessing `Status` could throw an exception. I’d suggest handling the missing record explicitly.”

Thứ tự này rõ ràng: **observation → consequence → suggestion**.

## 12. Mẫu trả lời tham khảo

> **“I noticed that `FirstAsync()` is used here, so this could throw if the record no longer exists. Could that happen if the record is deleted before this operation runs? If so, I’d suggest handling the missing-record case explicitly, for example by using `FirstOrDefaultAsync()` and checking the result. That would make the behavior clearer and avoid an unexpected exception.”**

Các mẫu câu có thể tái sử dụng:

- **“I noticed that…”**
- **“This could … when …”**
- **“Could that happen if…?”**
- **“I’d suggest…”**
- **“That would…”**

## 13. Thử nói lại theo cách của bạn

Chọn một review comment thật bạn từng viết hoặc từng nhận và nói lại theo template sau:

- **Context:** I’m reviewing…
- **Observation:** I noticed that…
- **Possible risk:** This could…
- **Scenario:** This may happen when…
- **My proposed action:** I’d suggest…
- **Confirmation:** Could this happen if…?

Bạn có thể thay `null`, `FirstAsync()`, `NotFound` bằng một vấn đề thật như:

- thiếu cancellation token,
- query N+1,
- retry gây duplicate data,
- transaction boundary chưa rõ,
- logging chứa sensitive information.

## 14. Tóm tắt cần ghi nhớ

### 3 câu nên nhớ

1. **“I noticed that this value can be null when the record doesn’t exist.”**
2. **“In that case, accessing this property could throw an exception.”**
3. **“I’d suggest handling the missing record explicitly.”**

### Lỗi cần tránh

- Tránh dùng feedback chung chung như **“This code is wrong.”**
- Sau `could`, không thêm `s`: dùng **`could throw`**, không phải **`could throws`**.
- Không biến assumption chưa xác nhận thành fact; hãy hỏi **“Could this happen when…?”** nếu cần.

### Thử thách hôm nay

Lấy một Pull Request thật hoặc một đoạn code bạn từng review. Viết lại **một review comment** theo cấu trúc:

**Observation → Risk → Scenario → Suggestion.**
