# Daily Workplace English — Ngày 25

- **Ngày:** 17/08/2026 (UTC+7)
- **Tình huống công việc:** Giải thích với QA vì sao một test case cần thay đổi sau khi requirement được cập nhật
- **Kỹ năng giao tiếp chính:** Phân biệt bug với expected behavior, giải thích requirement change và đề xuất cập nhật test case mà không làm QA cảm thấy bị bác bỏ
- **Thời gian học:** 20–25 phút
- **Độ khó:** Lower-intermediate

## 1. Tình huống hôm nay

QA báo một test case đang fail trên QA environment. Test case cũ kỳ vọng ASP.NET Core API trả về `400 Bad Request` khi client gửi lại cùng một request hai lần. Tuy nhiên, trong buổi refinement gần đây, Product Owner đã xác nhận behavior mới: request lặp lại hợp lệ phải được xử lý theo hướng idempotent và trả về `200 OK` nếu trạng thái cuối cùng đã đúng.

Những người liên quan gồm bạn và QA engineer. Bạn đã kiểm tra implementation và thấy behavior hiện tại phù hợp với requirement mới. Vì vậy, vấn đề không còn nằm ở code mà nằm ở expected result của test case.

Khó khăn giao tiếp là nếu bạn nói quá trực tiếp như:

> “Your test case is wrong.”

QA có thể hiểu rằng bạn đang đổ lỗi. Nhưng nếu bạn chỉ nói:

> “This is expected.”

thì lại thiếu bằng chứng và context.

Mục tiêu là dùng cấu trúc:

**Acknowledge → Explain the requirement change → Compare old vs new behavior → Clarify why the test fails → Suggest test update → Invite confirmation**

## 2. Bạn cần nói gì?

Trong tình huống này, bạn nên:

- Xác nhận rằng bạn đã xem test failure.
- Nói rõ behavior hiện tại đã thay đổi theo requirement mới.
- So sánh expected behavior cũ và mới.
- Giải thích rằng đây không phải regression của API.
- Đề xuất QA cập nhật expected result của test case.
- Mở đường cho QA phản hồi nếu họ có thông tin khác.

Điểm quan trọng là tập trung vào **sự thay đổi của requirement**, không tập trung vào việc ai đúng ai sai.

## 3. Đoạn hội thoại hoặc mẫu trình bày

**QA:** “This test is still failing. The API returns `200 OK`, but the expected result is `400 Bad Request`.”  
*Test này vẫn đang fail. API trả về `200 OK`, nhưng expected result là `400 Bad Request`.*

**You:** “I checked the implementation, and the current response matches the updated requirement.”  
*Mình đã kiểm tra implementation, và response hiện tại phù hợp với requirement đã được cập nhật.*

**QA:** “Was the behavior changed recently?”  
*Behavior này mới được thay đổi gần đây à?*

**You:** “Yes. Previously, we treated a duplicate request as an error, but the new behavior is to make the operation idempotent.”  
*Đúng vậy. Trước đây chúng ta coi duplicate request là lỗi, nhưng behavior mới là xử lý operation theo hướng idempotent.*

**You:** “If the requested state is already applied, the API should now return `200 OK` instead of `400 Bad Request`.”  
*Nếu trạng thái được yêu cầu đã được áp dụng rồi, API hiện tại nên trả về `200 OK` thay vì `400 Bad Request`.*

**QA:** “So this test case needs to be updated?”  
*Vậy test case này cần được cập nhật đúng không?*

**You:** “Yes. I think we should update the expected status code and keep a separate case for genuinely invalid requests.”  
*Đúng. Mình nghĩ chúng ta nên cập nhật expected status code và giữ một case riêng cho các request thực sự không hợp lệ.*

**You:** “Please let me know if you have a different acceptance criterion on your side.”  
*Nếu phía bạn có acceptance criterion khác thì cho mình biết nhé.*

## 4. Các cụm từ quan trọng

### 1. “I checked the implementation, and…”

- **Nghĩa:** Tôi đã kiểm tra implementation, và…
- **Khi dùng:** Khi muốn cho thấy nhận định của bạn dựa trên việc đã kiểm tra code hoặc behavior.
- **Ví dụ thêm:** “I checked the implementation, and the timeout is still configured as expected.”

### 2. “The current response matches the updated requirement.”

- **Nghĩa:** Response hiện tại phù hợp với requirement mới.
- **Khi dùng:** Khi behavior thay đổi do requirement, không phải do bug.
- **Ví dụ thêm:** “The current validation matches the updated acceptance criteria.”

### 3. “Previously, we treated … as …”

- **Nghĩa:** Trước đây chúng ta xử lý/coi … là …
- **Khi dùng:** Khi so sánh behavior cũ và mới.
- **Ví dụ thêm:** “Previously, we treated an empty value as invalid.”

### 4. “The new behavior is to…”

- **Nghĩa:** Behavior mới là…
- **Khi dùng:** Khi giải thích thay đổi rõ ràng và ngắn gọn.
- **Ví dụ thêm:** “The new behavior is to retry the request once before returning an error.”

### 5. “I think we should update…”

- **Nghĩa:** Tôi nghĩ chúng ta nên cập nhật…
- **Khi dùng:** Khi đề xuất thay đổi mà không áp đặt.
- **Ví dụ thêm:** “I think we should update the API documentation as well.”

### 6. “Keep a separate case for…”

- **Nghĩa:** Giữ một case riêng cho…
- **Khi dùng:** Khi muốn phân tách các test scenario khác nhau.
- **Ví dụ thêm:** “We should keep a separate case for authorization failures.”

### 7. “Please let me know if you have a different acceptance criterion.”

- **Nghĩa:** Hãy cho tôi biết nếu bạn có acceptance criterion khác.
- **Khi dùng:** Khi muốn xác nhận rằng hai bên đang dùng cùng một nguồn requirement.
- **Ví dụ thêm:** “Please let me know if you have a different expected result in the test specification.”

## 5. Từ vựng trong tình huống

### 1. `idempotent`

- **Loại từ:** adjective
- **IPA:** /ˌaɪdəmˈpoʊtənt/
- **Nghĩa:** có thể thực hiện lặp lại mà không làm thay đổi kết quả cuối ngoài lần đầu cần thiết
- **Ví dụ:** “The new behavior is to make the operation idempotent.”
- **Collocation:** `idempotent operation`, `idempotent API`

### 2. `expected result`

- **Loại từ:** noun phrase
- **IPA:** /ɪkˈspektɪd rɪˈzʌlt/
- **Nghĩa:** kết quả mong đợi
- **Ví dụ:** “The expected result is `400 Bad Request`.”
- **Collocation:** `verify the expected result`

### 3. `acceptance criterion`

- **Loại từ:** noun phrase
- **IPA:** /əkˈseptəns kraɪˈtɪriən/
- **Nghĩa:** tiêu chí chấp nhận
- **Ví dụ:** “Please let me know if you have a different acceptance criterion.”
- **Collocation:** `meet an acceptance criterion`

### 4. `duplicate request`

- **Loại từ:** noun phrase
- **IPA:** /ˈduːplɪkət rɪˈkwest/
- **Nghĩa:** request bị gửi lặp lại
- **Ví dụ:** “Previously, we treated a duplicate request as an error.”
- **Collocation:** `handle duplicate requests`

### 5. `invalid request`

- **Loại từ:** noun phrase
- **IPA:** /ɪnˈvælɪd rɪˈkwest/
- **Nghĩa:** request không hợp lệ
- **Ví dụ:** “We should keep a separate case for genuinely invalid requests.”
- **Collocation:** `reject an invalid request`

### 6. `regression`

- **Loại từ:** noun
- **IPA:** /rɪˈɡreʃən/
- **Nghĩa:** lỗi mới làm hỏng behavior từng hoạt động đúng
- **Ví dụ:** “This does not look like a regression.”
- **Collocation:** `regression issue`, `regression test`

## 6. Mẫu câu hoặc ngữ pháp cần nhớ

### Mẫu câu: “Previously…, but now…”

**Cấu trúc:**

`Previously, + past simple, but now + present simple.`

**Ý nghĩa:** Dùng để so sánh behavior cũ và behavior hiện tại sau khi requirement hoặc implementation thay đổi.

**Ví dụ trong bài:**

> “Previously, we treated a duplicate request as an error, but the new behavior is to make the operation idempotent.”

**Ví dụ thêm:**

- “Previously, the API returned `404`, but now it returns an empty result.”
- “Previously, we validated this field on the client, but now the backend validates it as well.”

**Khi dùng:**

- Giải thích requirement change.
- Giải thích API contract change.
- Làm rõ vì sao test cũ không còn đúng.

**Lỗi thường gặp:**

Sai: `Previously, we treat duplicate requests as errors.`  
Đúng: `Previously, we treated duplicate requests as errors.`

Sau `previously`, khi nói về behavior đã xảy ra trong quá khứ, thường cần dùng **past simple**.

## 7. Cách nói tự nhiên hơn

### Chưa tự nhiên hoặc quá trực tiếp

“Your test case is wrong.”

### Tự nhiên và chuyên nghiệp hơn

“The test case looks like it is still using the previous expected behavior.”

### Giải thích

Câu thứ hai tập trung vào test expectation, không đánh giá người viết test. Nó cũng mở khả năng rằng test case chỉ chưa được cập nhật.

### Chưa tự nhiên hoặc quá trực tiếp

“This is not a bug.”

### Tự nhiên và chuyên nghiệp hơn

“Based on the updated requirement, this looks like expected behavior rather than a regression.”

### Giải thích

Câu tốt hơn đưa ra căn cứ là updated requirement và tránh khẳng định thiếu context.

### Chưa tự nhiên hoặc quá trực tiếp

“Change the expected result to `200`.”

### Tự nhiên và chuyên nghiệp hơn

“I think we should update the expected status code to `200 OK` for this scenario.”

### Giải thích

Trong collaboration, dùng `I think we should…` giúp câu mang tính đề xuất hơn. Tuy nhiên, nếu bạn đang ghi rõ một action item đã được team thống nhất, câu trực tiếp như “Please update the expected status code to `200 OK`” cũng hoàn toàn phù hợp.

## 8. Phát âm và luyện nói

### 1. “matches the updated requirement”

- **Stress:** nhấn `MATCHES`, `UPDATED`, `REQUIREMENT`.
- **Connected speech:** `matches the` thường nối nhẹ, không tách quá rõ từng từ.
- **Gợi ý cho người Việt:** chú ý âm cuối `/tʃɪz/` trong `matches`, không bỏ âm cuối.
- **Pause:** “The current response / matches the updated requirement.”

### 2. “Previously, we treated…”

- **Stress:** nhấn `PREVIOUSLY` và `TREATED`.
- **Connected speech:** `we treated` nối khá liền trong tốc độ nói tự nhiên.
- **Gợi ý:** không đọc `treated` thành hai từ tách rời; âm cuối `/ɪd/` cần nhẹ nhưng có.
- **Pause:** “Previously, / we treated a duplicate request as an error.”

### 3. “I think we should update…”

- **Stress:** nhấn `THINK`, `SHOULD`, `UPDATE`.
- **Reduced sound:** `should` có thể được đọc nhẹ hơn khi không phải từ chính.
- **Gợi ý:** tránh nhấn đều mọi từ.
- **Pause:** “I think / we should update the expected status code.”

### Shadowing script

> “I checked the implementation, and the current response matches the updated requirement.”  
> “Previously, we treated a duplicate request as an error.”  
> “The new behavior is to make the operation idempotent.”  
> “I think we should update the expected status code for this scenario.”

Cách luyện:

1. Đọc chậm từng câu.
2. Nghe bằng Text-to-Speech nếu có.
3. Lặp lại từng câu một.
4. Ghi âm giọng của bạn.
5. Nói lại toàn bộ đoạn mà không nhìn text.

## 10. Bài tập thực hành chủ động

### Scenario

Một Playwright test đang fail vì test cũ kỳ vọng API trả về `404 Not Found`, nhưng requirement mới nói rằng khi không có dữ liệu phù hợp, endpoint phải trả về `200 OK` với một empty list.

### Nhiệm vụ

Viết một message 5–7 câu cho QA.

Message cần có:

- Xác nhận bạn đã xem failure.
- Nói behavior hiện tại phù hợp requirement mới.
- So sánh behavior cũ và mới.
- Giải thích đây không phải regression.
- Đề xuất cập nhật expected result.
- Mời QA phản hồi nếu acceptance criterion của họ khác.

### Suggested structure

`Acknowledge → Requirement change → Old vs new behavior → Conclusion → Suggested test update → Confirmation`

### Useful phrases

- “I checked the implementation, and…”
- “The current response matches the updated requirement.”
- “Previously, we treated…”
- “The new behavior is to…”
- “I think we should update…”
- “Please let me know if…”

### Completion criteria

Bài hoàn thành tốt khi:

- Có 5–7 câu.
- Không dùng “your test is wrong”.
- Có ít nhất một câu so sánh behavior cũ và mới.
- Có một đề xuất next action rõ ràng.

## 12. Mẫu trả lời tham khảo

> “I checked the failing Playwright test, and the API response matches the updated requirement. Previously, the endpoint returned `404 Not Found` when no records were found, but the new behavior is to return `200 OK` with an empty list. Based on that change, this looks like expected behavior rather than a regression. **I think we should update the expected result in this test case.** Please let me know if you have a different acceptance criterion on your side.”

Mẫu câu có thể tái sử dụng:

- **“Previously…, but the new behavior is to…”**
- **“Based on…, this looks like…”**
- **“I think we should update…”**

## 13. Thử nói lại theo cách của bạn

Hãy lấy một test case thật trong công việc và nói lại theo template sau:

- **Context:** What test or API is involved?
- **What happened:** What is failing?
- **My current understanding:** What behavior is expected now?
- **Missing information:** Is any requirement still unclear?
- **My proposed action:** What should be updated?
- **Expected next update:** What do you need from QA or PO next?

Hãy thay toàn bộ ví dụ trong bài bằng task, bug hoặc test thực tế bạn đang làm.
