# 1. `CancellationToken` propagation trong .NET: cancellation là cooperative contract, không phải nút “kill thread”

## 1. What is it?

`CancellationToken` là cơ chế cooperative cancellation của .NET. Nó không cưỡng bức dừng một thread. Nó truyền một tín hiệu rằng work hiện tại không còn cần thiết và code ở từng layer phải chủ động quan sát tín hiệu đó rồi dừng ở một điểm an toàn.

Mental model:

```text
Client disconnect / timeout / shutdown
            ↓
CancellationToken becomes cancelled
            ↓
API → application → EF Core / HTTP client / queue operation
            ↓
Each layer cooperatively stops work
```

Điểm quan trọng là **propagation**. Nếu token chỉ tồn tại ở controller nhưng không đi xuống database hoặc external API, application vẫn tiếp tục tiêu tốn tài nguyên sau khi caller đã bỏ request.

## 2. Why does it exist?

Trong server production, request có thể mất giá trị trước khi work hoàn thành vì:

* client đóng kết nối;
* upstream gateway timeout;
* deployment yêu cầu graceful shutdown;
* background job bị hủy;
* user bắt đầu request mới và kết quả cũ không còn cần thiết.

Nếu hệ thống không propagate cancellation, các operation vô ích vẫn chiếm database connection, ThreadPool capacity, HTTP socket và CPU. Dưới tải cao, work “mồ côi” này có thể làm latency tăng cho request còn hợp lệ.

## 3. How does it work?

`CancellationTokenSource` sở hữu trạng thái cancellation. `CancellationToken` là handle chỉ đọc được truyền qua call chain. Khi source gọi `Cancel()`, token chuyển sang trạng thái cancelled.

Một async API tốt thường:

1. nhận `CancellationToken`;
2. truyền tiếp xuống dependency;
3. gọi `ThrowIfCancellationRequested()` trong CPU loop hoặc custom code;
4. không nuốt `OperationCanceledException` như lỗi nghiệp vụ.

Trong ASP.NET Core, `HttpContext.RequestAborted` phản ánh request bị hủy. Minimal API/controller có thể bind trực tiếp `CancellationToken` từ request.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    OrderService service,
    CancellationToken cancellationToken) =>
{
    var order = await service.GetAsync(id, cancellationToken);
    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

```csharp
public async Task<OrderDto?> GetAsync(
    Guid id,
    CancellationToken cancellationToken)
{
    var order = await _db.Orders
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new OrderDto(x.Id, x.Number, x.Total))
        .SingleOrDefaultAsync(cancellationToken);

    if (order is null)
        return null;

    using var response = await _pricingClient.GetAsync(
        $"api/pricing/{id}",
        cancellationToken);

    response.EnsureSuccessStatusCode();
    return order;
}
```

Nếu business operation cần timeout riêng:

```csharp
using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(2));
using var linked = CancellationTokenSource.CreateLinkedTokenSource(
    requestToken,
    timeoutCts.Token);

await dependency.CallAsync(linked.Token);
```

## 5. Real production scenario

Một product API gọi SQL Server rồi gọi pricing service. Gateway timeout là 3 giây nhưng backend không propagate cancellation. Pricing service đôi khi mất 10 giây.

Client nhận timeout sau 3 giây nhưng backend tiếp tục giữ SQL/HTTP resources thêm nhiều giây. Khi traffic tăng, pool connection bị bão hòa mặc dù phần lớn caller đã bỏ request.

## 6. Failure scenario & troubleshooting

**Symptom** → gateway báo nhiều timeout, nhưng database và dependency vẫn có workload cao sau khi request đã kết thúc.

**Evidence** → traces cho thấy child dependency span tiếp tục chạy sau parent request timeout.

**Hypothesis** → cancellation không được truyền xuống dependency.

**Diagnosis** → tìm method async nhận `CancellationToken.None`, overload không có token, hoặc catch `OperationCanceledException` rồi tiếp tục xử lý.

**Fix** → truyền token xuyên suốt, thêm timeout phù hợp cho remote dependency, dừng CPU loop bằng token check.

**Verification** → load test với client abort; kiểm tra dependency concurrency và connection usage giảm nhanh sau cancellation.

## 7. Common mistakes

* Tạo `CancellationTokenSource` mới ở mỗi layer và làm mất token từ caller.
* Dùng `CancellationToken.None` trong EF Core hoặc `HttpClient`.
* Nghĩ cancellation sẽ tự động rollback mọi side effect đã xảy ra.
* Catch `Exception` rồi biến `OperationCanceledException` thành HTTP 500.
* Dùng cancellation thay cho transaction hoặc compensating logic.

## 8. Alternatives

Cancellation không thay thế timeout, Circuit Breaker hoặc idempotency. Timeout đặt deadline cho operation; cancellation truyền tín hiệu dừng; Circuit Breaker bảo vệ trước dependency đang lỗi; idempotency bảo vệ side effect khi retry.

## 9. Trade-offs

### Advantages

* Giảm wasted work.
* Giải phóng resource sớm.
* Hỗ trợ graceful shutdown.
* Cải thiện behavior dưới overload.

### Costs / Risks

* Contract phải xuyên qua nhiều layer.
* Side effect có thể đã xảy ra trước cancellation.
* Debugging phức tạp nếu mọi cancellation bị log như lỗi.
* Code custom phải xác định điểm dừng an toàn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu rằng `CancellationToken` là tín hiệu cooperative, không phải thread termination.

### Middle
Biết propagate token qua ASP.NET Core, EF Core, `HttpClient` và background processing.

### Senior
Đánh giá deadline, dependency timeout, resource leakage và side effect xảy ra trước cancellation.

### Technical Lead / Architect
Thiết kế end-to-end timeout budget, cancellation propagation convention và observability để cancellation không bị nhầm với lỗi hệ thống.

## 11. Key takeaway

* Cancellation chỉ có giá trị khi được propagate xuyên call chain.
* Nó giảm wasted work nhưng không hoàn tác side effect.
* Timeout, cancellation và idempotency giải quyết các vấn đề khác nhau.

# 2. ASP.NET Core streaming response

## 1. What is it?

Streaming response gửi dữ liệu theo từng chunk thay vì dựng toàn bộ payload trong memory.

```text
Traditional: source → load all → serialize all → response
Streaming:   source → read chunk → write chunk → repeat
```

## 2. Why does it exist?

Endpoint export hàng trăm MB nếu buffer toàn bộ payload sẽ làm memory tăng theo kích thước response. Streaming giữ working set gần kích thước buffer và cải thiện time-to-first-byte.

## 3. How does it work?

ASP.NET Core ghi trực tiếp vào `HttpResponse.Body`. Sau khi headers đã gửi, response đã “started”, nên không thể dễ dàng chuyển sang status code lỗi khác nếu failure xảy ra giữa stream.

## 4. Practical implementation

```csharp
app.MapGet("/exports/orders.csv", async (
    AppDbContext db,
    HttpResponse response,
    CancellationToken cancellationToken) =>
{
    response.ContentType = "text/csv; charset=utf-8";

    await using var writer = new StreamWriter(response.Body, leaveOpen: true);
    await writer.WriteLineAsync("Id,Number,Total");

    await foreach (var order in db.Orders
        .AsNoTracking()
        .OrderBy(x => x.Id)
        .Select(x => new { x.Id, x.Number, x.Total })
        .AsAsyncEnumerable()
        .WithCancellation(cancellationToken))
    {
        await writer.WriteLineAsync(
            $"{order.Id},{order.Number},{order.Total}");
    }

    await writer.FlushAsync(cancellationToken);
});
```

## 5. Real production scenario

Finance export 2 GB transaction data. Buffering có thể OOM App Service; streaming giữ memory tương đối ổn định.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận file bị cắt nhưng HTTP status vẫn 200.  
**Evidence** → exception xảy ra sau khi response started.  
**Hypothesis** → failure giữa stream.  
**Diagnosis** → kiểm tra `HttpResponse.HasStarted`, DB timeout, disconnect.  
**Fix** → validate trước khi stream; với export cực lớn dùng background job + Blob Storage.  
**Verification** → inject failure giữa stream.

## 7. Common mistakes

* Stream HTTP nhưng query vẫn `ToListAsync()`.
* Không propagate `RequestAborted`.
* Giữ transaction/database resource quá lâu.
* Dùng streaming khi cần retry/resume nhưng không có artifact persisted.

## 8. Alternatives

Buffering cho payload nhỏ; background export + Blob Storage cho file rất lớn; pagination cho interactive data.

## 9. Trade-offs

### Advantages
* Memory thấp hơn.
* TTFB tốt hơn.

### Costs / Risks
* Partial response khó biểu diễn lỗi.
* Connection sống lâu.
* Backpressure và disconnect phải xử lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt buffering và streaming.

### Middle
Biết stream end-to-end.

### Senior
Quan tâm cancellation, backpressure và partial response.

### Technical Lead / Architect
Chọn synchronous stream hay async export pipeline dựa trên size, reliability và UX.

## 11. Key takeaway

* Streaming giảm memory nhưng tăng lifecycle complexity.
* Phải stream xuyên pipeline.
* Export rất lớn thường nên tạo artifact bất đồng bộ.

# 3. EF Core split queries

## 1. What is it?

`AsSplitQuery()` tách query có nhiều collection `Include` thành nhiều SQL statements để tránh cartesian explosion.

## 2. Why does it exist?

Một Order có 20 Items và 5 Payments có thể tạo 100 joined rows dù logic chỉ có 26 objects. Payload lặp và materialization cost tăng mạnh.

## 3. How does it work?

```csharp
var orders = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .ToListAsync(cancellationToken);
```

EF query parent và collections riêng rồi ghép graph bằng key.

## 4. Practical implementation

Read API thường nên projection trước:

```csharp
var result = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummaryDto(
        x.Id,
        x.Number,
        x.Items.Count,
        x.Payments.Sum(p => p.Amount)))
    .ToListAsync(cancellationToken);
```

## 5. Real production scenario

Admin list load 100 orders với Items, Notes, Payments. Single join tạo hàng chục nghìn rows. Projection cho list và split query cho detail giảm payload đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → DB CPU giảm nhưng total latency tăng.  
**Evidence** → nhiều DB round-trips qua network latency cao.  
**Hypothesis** → split-query round-trip cost vượt lợi ích giảm duplication.  
**Fix** → projection hoặc single query nếu cardinality thấp.  
**Verification** → benchmark topology gần production.

## 7. Common mistakes

* Dùng `Include` khi chỉ cần vài fields.
* Nghĩ split luôn nhanh hơn.
* Bỏ qua consistency window giữa statements.
* Chỉ đo SQL time, không đo network/materialization.

## 8. Alternatives

Single query, projection, explicit queries, raw SQL/Dapper.

## 9. Trade-offs

### Advantages
* Tránh cartesian explosion.
* Giảm duplicated payload.

### Costs / Risks
* Nhiều round-trip.
* Consistency window.
* Có thể che access pattern quá lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `Include` có thể nhân rows.

### Middle
Biết projection và split query.

### Senior
Đánh giá cardinality, round-trip và materialization.

### Technical Lead / Architect
Thiết kế read model theo use case thay vì entity graph.

## 11. Key takeaway

* Split query chữa cartesian explosion, không chữa access pattern kém.
* Projection thường tốt hơn cho read API.
* Đo end-to-end latency.

# 4. SQL keyset pagination

## 1. What is it?

Keyset pagination dùng sort key cuối trang trước làm cursor, thay vì `OFFSET`.

## 2. Why does it exist?

`OFFSET 100000` vẫn khiến database phải tìm và bỏ qua rất nhiều rows. Dữ liệu thay đổi giữa các request còn dễ gây duplicate/missing rows.

## 3. How does it work?

```sql
SELECT TOP (@PageSize)
    Id, CreatedAt, Number, Total
FROM Orders
WHERE CreatedAt < @LastCreatedAt
   OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index:

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON Orders (CreatedAt DESC, Id DESC)
INCLUDE (Number, Total);
```

## 4. Practical implementation

```csharp
if (lastCreatedAt is not null && lastId is not null)
{
    query = query.Where(x =>
        x.CreatedAt < lastCreatedAt ||
        (x.CreatedAt == lastCreatedAt && x.Id < lastId));
}
```

Ordering phải deterministic.

## 5. Real production scenario

Admin có 50 triệu orders. Page sâu bằng OFFSET mất vài giây, nhưng UX chỉ cần Next/Previous. Keyset giữ latency gần ổn định hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate giữa pages.  
**Evidence** → sort chỉ theo `CreatedAt`.  
**Hypothesis** → sort key không unique.  
**Fix** → thêm `Id` làm tie-breaker.  
**Verification** → test rows cùng timestamp và concurrent inserts.

## 7. Common mistakes

* Cursor không deterministic.
* Predicate và `ORDER BY` không đồng nhất.
* Index không phù hợp.
* Vẫn yêu cầu arbitrary page number.

## 8. Alternatives

Offset cho dataset nhỏ; keyset cho feed/list lớn; Elasticsearch `search_after` cho search workload.

## 9. Trade-offs

### Advantages
* Page sâu ổn định hơn.
* Ít scan/discard.

### Costs / Risks
* Không phù hợp direct page jump.
* Cursor contract phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu OFFSET không miễn phí.

### Middle
Viết seek predicate đúng.

### Senior
Đọc execution plan và logical reads.

### Technical Lead / Architect
Chọn pagination contract theo UX, dataset và mutation rate.

## 11. Key takeaway

* Keyset tốt cho “next/previous” trên dataset lớn.
* Sort phải deterministic.
* Pagination là quyết định API + database.

# 5. Elasticsearch alias + reindex

## 1. What is it?

Alias là tên logic trỏ tới physical index. Reindex tạo index version mới khi mapping/analyzer cần thay đổi.

## 2. Why does it exist?

Application không nên phụ thuộc `products-v3` trực tiếp. Alias cho stable contract trong khi index lifecycle thay đổi.

## 3. How does it work?

```text
products-v2 → backfill → products-v3
                         ↑
              atomic alias switch
```

Live changes trong reindex window phải được reconcile.

## 4. Practical implementation

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v2", "alias": "products-read" } },
    { "add":    { "index": "products-v3", "alias": "products-read" } }
  ]
}
```

## 5. Real production scenario

Marketplace đổi analyzer cho product search. Reindex mất 40 phút; alias cho phép rebuild và cutover mà application không downtime.

## 6. Failure scenario & troubleshooting

**Symptom** → sản phẩm mới nhất biến mất sau cutover.  
**Evidence** → events trong backfill window chưa vào v3.  
**Hypothesis** → synchronization gap.  
**Fix** → high-water mark + replay hoặc controlled dual-write.  
**Verification** → compare source versions và index versions trước cutover.

## 7. Common mistakes

* App phụ thuộc physical index name.
* Không replay live changes.
* Xóa old index ngay.
* Chỉ so total document count.

## 8. Alternatives

In-place mapping update khi hỗ trợ; dual index write; rebuild từ primary DB/CMS.

## 9. Trade-offs

### Advantages
* Near-zero-downtime migration.
* Rollback nhanh.

### Costs / Risks
* Storage tạm thời tăng.
* Synchronization phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu alias là indirection.

### Middle
Biết reindex + alias switch.

### Senior
Thiết kế cutover/replay/rollback.

### Technical Lead / Architect
Xác định source of truth và index lifecycle ownership.

## 11. Key takeaway

* Alias tách app khỏi physical index lifecycle.
* Reindex phải xử lý live writes.
* Search migration là consistency problem.

# 6. Circuit Breaker và Bulkhead

## 1. What is it?

Circuit Breaker ngừng gọi dependency đang lỗi; Bulkhead giới hạn resource/concurrency mà dependency được phép chiếm.

## 2. Why does it exist?

Dependency chậm có thể giữ sockets/threads/connections lâu; retries làm load tăng đúng lúc dependency yếu, gây cascading failure.

## 3. How does it work?

```text
Closed → failure threshold → Open
Open → break duration → Half-Open
Half-Open → success → Closed
           → fail    → Open
```

Bulkhead giới hạn concurrent calls hoặc queue.

## 4. Practical implementation

```csharp
services.AddHttpClient<ReviewClient>(client =>
{
    client.BaseAddress = new Uri(configuration["Reviews:BaseUrl"]!);
})
.AddStandardResilienceHandler(options =>
{
    options.AttemptTimeout.Timeout = TimeSpan.FromSeconds(2);
    options.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(5);
});
```

Policy cụ thể phải dựa trên SLA, idempotency và traffic.

## 5. Real production scenario

Reviews API tăng từ 100 ms lên 8 giây. Product API chờ Reviews và dần cạn capacity. Timeout + bulkhead + circuit breaker + graceful fallback ngăn Reviews kéo sập product page.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency hồi phục nhưng caller vẫn fallback.  
**Evidence** → circuit Open/Half-Open.  
**Hypothesis** → break policy không khớp recovery behavior.  
**Diagnosis** → xem sampling window, break duration, trial latency.  
**Fix** → tune bằng telemetry.  
**Verification** → fault-injection slow/500/recovery.

## 7. Common mistakes

* Retry không timeout.
* Retry non-idempotent POST.
* Circuit scope quá rộng.
* Bulkhead limit tùy tiện.
* Fallback làm sai business semantics.

## 8. Alternatives

Timeout, rate limiting, queue/asynchronous processing, caching/fallback.

## 9. Trade-offs

### Advantages
* Giảm cascading failure.
* Fail fast.
* Bảo vệ capacity.

### Costs / Risks
* Policy tuning khó.
* Có thể reject khi dependency vừa recover.
* Thêm state cần monitor.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Biết remote dependency sẽ fail.

### Middle
Cấu hình timeout/retry/circuit cơ bản.

### Senior
Đánh giá idempotency và concurrency budget.

### Technical Lead / Architect
Quyết định dependency criticality, fallback semantics và resilience boundaries.

## 11. Key takeaway

* Circuit Breaker bảo vệ repeated failures.
* Bulkhead bảo vệ capacity.
* Retry sai có thể khuếch đại outage.

# 7. Azure Managed Identity + Key Vault

## 1. What is it?

Managed Identity cung cấp identity do Azure quản lý cho workload. Key Vault quản lý secrets/keys/certificates với access control và audit.

## 2. Why does it exist?

Client secrets tạo secret sprawl, rotation burden và leak risk. Identity-first giảm credential tĩnh; Key Vault giữ các secrets vẫn bắt buộc tồn tại.

## 3. How does it work?

```text
App Service
  ↓ managed identity
Entra ID
  ↓ token
Key Vault / Azure resource
```

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(configuration["KeyVault:Uri"]!),
    new DefaultAzureCredential());

var secret = await client.GetSecretAsync(
    "ThirdPartyApiKey",
    cancellationToken: cancellationToken);
```

Với Blob/Service Bus/SQL hỗ trợ Entra auth, ưu tiên Managed Identity trực tiếp thay vì lấy secret.

## 5. Real production scenario

App Service truy cập SQL/Blob bằng Managed Identity, chỉ external vendor API key nằm trong Key Vault.

## 6. Failure scenario & troubleshooting

**Symptom** → local chạy, Production 403.  
**Evidence** → token có nhưng Key Vault deny.  
**Hypothesis** → authorization/RBAC scope sai.  
**Diagnosis** → principal ID, role assignment, network restriction.  
**Fix** → least-privilege role đúng scope; kiểm tra Private Endpoint/DNS.  
**Verification** → audit log và test bằng workload identity.

## 7. Common mistakes

* Lưu client secret để “dùng Managed Identity”.
* Cấp admin role quá rộng.
* Log secret.
* Bỏ qua private DNS/network path.

## 8. Alternatives

Environment secrets, Kubernetes Secrets + external secret store, workload identity federation.

## 9. Trade-offs

### Advantages
* Giảm static secrets.
* Audit tốt hơn.
* Rotation dễ quản lý hơn.

### Costs / Risks
* IAM/networking phức tạp.
* Key Vault trở thành dependency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Không hard-code secret.

### Middle
Dùng `DefaultAzureCredential`.

### Senior
Debug token/RBAC/networking.

### Technical Lead / Architect
Chuẩn hóa identity-first credential strategy.

## 11. Key takeaway

* Identity trước, secret sau.
* Key Vault không thay thế least privilege.
* Tách authentication failure khỏi authorization failure.

# 8. Docker multi-stage build

## 1. What is it?

Multi-stage build dùng SDK stage để build/publish và runtime stage chỉ chạy artifact.

## 2. Why does it exist?

SDK image chứa compiler/tooling không cần trong production, làm image lớn và attack surface rộng.

## 3. How does it work?

```text
SDK image → restore/build/publish
                    ↓
Runtime image ← copy published files
```

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

COPY MyApp.csproj .
RUN dotnet restore MyApp.csproj

COPY . .
RUN dotnet publish MyApp.csproj -c Release -o /app/publish --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApp.dll"]
```

## 5. Real production scenario

Cluster scale-out thường xuyên. Runtime image nhỏ giảm registry transfer và pod startup time.

## 6. Failure scenario & troubleshooting

**Symptom** → build pass, runtime crash vì native lib thiếu.  
**Evidence** → lib chỉ có trong SDK stage.  
**Hypothesis** → runtime dependency không được mang sang final image.  
**Fix** → cài dependency tối thiểu hoặc chọn compatible base image.  
**Verification** → integration test trên final image.

## 7. Common mistakes

* Copy source vào runtime.
* Dùng `latest`.
* Chạy root không cần thiết.
* Không patch base image.
* Chỉ test source, không test image.

## 8. Alternatives

Single-stage SDK image, self-contained publish, Native AOT khi workload phù hợp.

## 9. Trade-offs

### Advantages
* Image nhỏ.
* Attack surface giảm.
* Pull/deploy nhanh.

### Costs / Risks
* Dockerfile phức tạp hơn.
* Runtime debugging có ít tools hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu build image khác runtime image.

### Middle
Viết multi-stage Dockerfile.

### Senior
Quan tâm provenance, native deps, base image security.

### Technical Lead / Architect
Chuẩn hóa base image governance và patch workflow.

## 11. Key takeaway

* Runtime image chỉ nên chứa thứ cần để chạy.
* Test final image như production artifact.
* Image size ảnh hưởng deploy behavior và security.

# 9. p95/p99 latency trong production

## 1. What is it?

Percentiles mô tả distribution latency: p50, p95, p99 cho biết tỷ lệ request nằm dưới một threshold. Average có thể che slow tail.

## 2. Why does it exist?

Người dùng cảm nhận slow requests. Với fan-out distributed calls, xác suất một request gặp slow dependency tăng. SLO dựa trên percentile phản ánh trải nghiệm tốt hơn average.

## 3. How does it work?

```text
p99 rises
 → segment by endpoint/version
 → inspect slow traces
 → locate dependency
 → correlate CPU/GC/DB/network
```

## 4. Practical implementation

```csharp
private static readonly Meter Meter = new("OrderService");
private static readonly Histogram<double> DurationMs =
    Meter.CreateHistogram<double>("order.processing.duration", "ms");

var sw = Stopwatch.StartNew();
try
{
    await ProcessOrderAsync(cancellationToken);
}
finally
{
    DurationMs.Record(sw.Elapsed.TotalMilliseconds);
}
```

## 5. Real production scenario

Average tăng 180→210 ms nhưng p99 tăng 700 ms→6 s. Slow traces cho thấy 1% cache misses chạy query plan xấu.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 tăng, average/CPU gần bình thường.  
**Evidence** → slow traces tập trung một path.  
**Hypothesis** → tail-specific dependency/query.  
**Diagnosis** → cache ratio, spans, SQL logical reads/plan.  
**Fix** → sửa bottleneck cụ thể.  
**Verification** → p95/p99 quay về baseline.

## 7. Common mistakes

* Chỉ xem average.
* Xem p99 với sample count quá nhỏ.
* Gộp mọi endpoint.
* Scale trước khi localize bottleneck.

## 8. Alternatives

Average cho aggregate view; max quá nhạy; histogram/percentile cho distribution.

## 9. Trade-offs

### Advantages
* Phản ánh tail user experience.
* Hữu ích cho SLO.

### Costs / Risks
* Cần volume đủ lớn.
* High-cardinality segmentation tăng telemetry cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu average khác percentile.

### Middle
Đọc p50/p95/p99.

### Senior
Phân đoạn tail theo dependency/workload.

### Technical Lead / Architect
Định nghĩa SLO và telemetry strategy.

## 11. Key takeaway

* Average có thể che tail rất xấu.
* Percentile cần sample count và segmentation đúng.
* Optimize slow path bằng evidence.

# 10. Optimizely CMS content modeling

## 1. What is it?

Content modeling xác định page type, block, fields và reuse boundary. Trong Optimizely CMS, page thường là route-level content; block là component/reusable content fragment.

## 2. Why does it exist?

Giant page type gây duplicate fields và khó reuse; quá nhiều shared blocks làm editor mất context. Content model cân bằng reuse, editorial usability, rendering và migration.

## 3. How does it work?

```text
Editor → publish → content repository
                 → application rendering
                 → CDN/browser
                 → optional search indexing
```

## 4. Practical implementation

```csharp
[ContentType(DisplayName = "Article Page")]
public class ArticlePage : PageData
{
    public virtual string Heading { get; set; } = string.Empty;
    public virtual XhtmlString Body { get; set; } = new();
    public virtual ContentArea RelatedContent { get; set; } = new();
}

[ContentType(DisplayName = "Promo Block")]
public class PromoBlock : BlockData
{
    public virtual string Title { get; set; } = string.Empty;
    public virtual string CtaText { get; set; } = string.Empty;
    public virtual Url CtaUrl { get; set; } = new();
}
```

Không nên biến mọi frontend component thành CMS content type.

## 5. Real production scenario

Hero campaign dùng trên 200 pages: shared block hợp lý. Legal disclaimer chỉ có meaning trong một page cụ thể có thể nên page-local để tránh hidden coupling.

## 6. Failure scenario & troubleshooting

**Symptom** → editor sửa một shared block và vô tình thay đổi 70 pages.  
**Evidence** → block reuse rộng hơn editor nghĩ.  
**Hypothesis** → technical reuse không khớp editorial ownership.  
**Fix** → tách global/shared với page-local content, conventions và reference awareness.  
**Verification** → content reference audit + editor acceptance test.

## 7. Common mistakes

* Modeling theo frontend component tree thay vì editorial domain.
* Giant page type.
* Mọi field group thành shared block.
* Thay property type/name không có migration plan.
* Bỏ qua search/cache invalidation.

## 8. Alternatives

Page-local properties, shared blocks, headless CMS, application configuration.

## 9. Trade-offs

### Advantages
* Reuse content có chủ đích.
* Editor workflow linh hoạt.

### Costs / Risks
* Shared content tạo hidden coupling.
* Schema evolution cần migration.
* Cache/search invalidation phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu page và block có ownership khác nhau.

### Middle
Model content theo use case.

### Senior
Đánh giá editor workflow, caching, indexing và migration.

### Technical Lead / Architect
Thiết kế content domain boundary và governance cho CMS enterprise.

## 11. Key takeaway

* Content model là architecture contract.
* Reuse chỉ tốt khi semantic ownership cũng được reuse.
* Model phải phục vụ editor, runtime, search, cache và migration.
