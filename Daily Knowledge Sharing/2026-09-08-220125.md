# 1. ASP.NET Core DI captive dependency: khi Singleton vô tình giữ Scoped service và tạo lifetime bug khó thấy

## 1. What is it?

Captive dependency xảy ra khi một service có lifetime dài hơn giữ reference tới dependency có lifetime ngắn hơn, điển hình nhất là `Singleton` giữ `Scoped` service.

Mental model:

```text
Singleton lives for application lifetime
        ↓ captures
Scoped service expected to live per request
        ↓
Scoped instance effectively becomes long-lived
```

Vấn đề không chỉ là “DI container không thích”. Lifetime là contract về ownership, thread-safety và resource boundary.

## 2. Why does it exist?

ASP.NET Core dùng DI để quản lý object graph. `Scoped` thường đại diện unit-of-work/request boundary, ví dụ `DbContext`. Nếu `Singleton` giữ scoped instance, request isolation bị phá vỡ.

Điều này có thể dẫn tới:

* cross-request state leakage;
* concurrent access vào object không thread-safe;
* connection/resource lifetime kéo dài;
* lỗi “A second operation was started on this context”.

## 3. How does it work?

DI container tạo Singleton một lần. Nếu constructor của Singleton nhận Scoped dependency và validation không bắt được, instance Scoped đó bị giữ theo Singleton.

```text
App starts
  ↓
Singleton created
  ↓
Scoped dependency resolved once
  ↓
Request A ─┐
Request B ─┼─> same captured instance
Request C ─┘
```

Đây là lý do `DbContext` gần như luôn phải ở request scope và không được giữ trong Singleton.

## 4. Practical implementation

Sai:

```csharp
public sealed class ReportCache
{
    private readonly AppDbContext _db;

    public ReportCache(AppDbContext db)
    {
        _db = db;
    }
}

services.AddSingleton<ReportCache>();
```

Tốt hơn: Singleton chỉ giữ `IServiceScopeFactory` nếu thực sự cần tạo scoped work độc lập.

```csharp
public sealed class ReportRefreshService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public ReportRefreshService(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    public async Task RefreshAsync(CancellationToken cancellationToken)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        var data = await db.Reports
            .AsNoTracking()
            .ToListAsync(cancellationToken);

        // update cache from detached DTO/data
    }
}
```

Nếu service không cần Singleton, đơn giản hơn là đổi lifetime đúng theo dependency graph.

## 5. Real production scenario

Một singleton cache refresher giữ `DbContext`. Khi traffic tăng, nhiều request và refresh job đồng thời chạm context đó. Production bắt đầu xuất hiện lỗi concurrency rải rác, local test lại khó tái hiện vì traffic thấp.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi EF Core concurrency hoặc dữ liệu cross-request bất thường.

**Evidence** → object identity của `DbContext` giống nhau giữa nhiều request.

**Hypothesis** → scoped dependency bị captive.

**Diagnosis** → kiểm tra service registration graph và bật scope validation ở môi trường phát triển.

**Fix** → sửa lifetime hoặc tạo explicit scope tại operation boundary.

**Verification** → log scope/context identifier trong load test và xác nhận mỗi request có context phù hợp.

## 7. Common mistakes

* Nghĩ Singleton chỉ là “tối ưu để đỡ new object”.
* Inject `DbContext`, `HttpContext`, request-specific service vào Singleton.
* Dùng Service Locator khắp nơi để né lifetime error.
* Tạo scope nhưng giữ scoped object ra ngoài scope.

## 8. Alternatives

* `Scoped`: phù hợp request/unit-of-work.
* `Transient`: phù hợp stateless lightweight service.
* Singleton + explicit scope: chỉ khi background/global component thực sự cần lifetime dài.

## 9. Trade-offs

### Advantages

Singleton giảm số lần khởi tạo và phù hợp state immutable/global.

### Costs / Risks

Nó yêu cầu thread-safety, lifecycle rõ ràng và không được nắm giữ state scoped.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Transient`, `Scoped`, `Singleton` là lifecycle contract.

### Middle

Biết chọn lifetime và phát hiện captive dependency.

### Senior

Đánh giá thread-safety, ownership và resource boundary.

### Technical Lead / Architect

Chuẩn hóa registration conventions và review dependency graph theo lifetime, không chỉ theo interface/class.

## 11. Key takeaway

* Lifetime mismatch là correctness problem, không chỉ configuration problem.
* Singleton không được vô tình giữ request-scoped state.
* Chọn lifetime dựa trên ownership và concurrency semantics.

# 2. EF Core global query filters cho multi-tenant: tiện nhưng dễ biến isolation thành “ẩn trong ORM”

## 1. What is it?

Global query filter là predicate EF Core tự động gắn vào query cho một entity type. Một use case phổ biến là multi-tenancy:

```csharp
modelBuilder.Entity<Order>()
    .HasQueryFilter(x => x.TenantId == _tenantContext.TenantId);
```

Mental model:

```text
App writes: db.Orders.Where(...)
EF executes: WHERE TenantId = currentTenant AND (...)
```

## 2. Why does it exist?

Nếu developer phải nhớ thêm `TenantId` vào mọi query, một lần quên có thể gây data leak giữa tenants. Global filter giảm repetition và tạo default-safe behavior ở ORM layer.

Nhưng đây không phải security boundary tuyệt đối. Database authorization, schema design và operational tooling vẫn phải được xem xét.

## 3. How does it work?

EF Core thêm expression vào query tree trước khi translate SQL. Filter áp dụng mặc định cho query entity đó, kể cả navigation load trong nhiều trường hợp.

Có thể bypass bằng `IgnoreQueryFilters()`, vì vậy code có quyền gọi method này phải được review cẩn thận.

## 4. Practical implementation

```csharp
public sealed class TenantContext
{
    public Guid TenantId { get; init; }
}

public sealed class AppDbContext : DbContext
{
    private readonly TenantContext _tenant;

    public AppDbContext(
        DbContextOptions<AppDbContext> options,
        TenantContext tenant) : base(options)
    {
        _tenant = tenant;
    }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Order>()
            .HasQueryFilter(x => x.TenantId == _tenant.TenantId);
    }
}
```

Write path vẫn phải gán đúng `TenantId` và validate aggregate ownership.

## 5. Real production scenario

Một SaaS B2B có hàng nghìn tenant chung database. Query filter giảm nguy cơ developer quên tenant predicate ở read path. Tuy nhiên admin/support workflow có quyền cross-tenant cần boundary riêng, explicit và audited.

## 6. Failure scenario & troubleshooting

**Symptom** → background job không thấy dữ liệu nào.

**Evidence** → job chạy ngoài HTTP request nên `TenantContext` chưa được set.

**Hypothesis** → global filter đang dùng tenant rỗng/default.

**Diagnosis** → inspect generated SQL và tenant value runtime.

**Fix** → background job phải iterate tenant explicit hoặc dùng administrative query path có kiểm soát.

**Verification** → integration test cả request path và background path.

## 7. Common mistakes

* Xem query filter như security layer duy nhất.
* Dùng `IgnoreQueryFilters()` tùy tiện.
* Không index `TenantId` trong access path phù hợp.
* Quên set tenant trong background worker.
* Cho client gửi `TenantId` rồi tin trực tiếp.

## 8. Alternatives

* Database-per-tenant: isolation mạnh hơn, operational cost cao hơn.
* Schema-per-tenant: trung gian nhưng migration phức tạp.
* Row-Level Security: enforce gần database hơn nhưng tăng platform-specific complexity.

## 9. Trade-offs

### Advantages

* Default-safe query behavior.
* Giảm repetitive predicates.
* Dễ áp dụng shared-schema multi-tenancy.

### Costs / Risks

* Behavior bị ẩn.
* Background/admin flows phức tạp.
* Không thay thế authorization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu filter được thêm tự động.

### Middle

Biết implement tenant context và integration test.

### Senior

Đánh giá bypass path, indexing và background execution.

### Technical Lead / Architect

Quyết định isolation model: shared table, RLS, schema-per-tenant hay database-per-tenant dựa trên risk, scale và operations.

## 11. Key takeaway

* Global query filter là guardrail, không phải security boundary hoàn chỉnh.
* Multi-tenancy phải được thiết kế cả read, write, admin và background paths.
* Isolation model là architecture decision, không chỉ EF Core feature.

# 3. SQL Server parameter sniffing: cùng một query nhưng execution plan tốt cho tenant này lại tệ cho tenant khác

## 1. What is it?

Parameter sniffing là behavior SQL Server dùng giá trị parameter tại thời điểm compile để ước lượng cardinality và chọn execution plan. Plan đó có thể được cache và reuse cho các giá trị khác.

## 2. Why does it exist?

Plan compilation có cost. Reuse plan giúp giảm CPU và tăng throughput. Nhưng data distribution lệch mạnh khiến một plan không tối ưu cho mọi parameter.

Ví dụ tenant A có 100 rows, tenant B có 50 triệu rows. Cùng query theo `TenantId` có thể cần chiến lược access khác nhau.

## 3. How does it work?

```text
First execution: TenantId = small tenant
        ↓
Optimizer estimates few rows
        ↓
Plan cached
        ↓
Later execution: huge tenant
        ↓
Same plan reused → poor I/O / joins / memory grant
```

Parameter sniffing không phải bug mặc định; nó là trade-off của plan reuse.

## 4. Practical implementation

Query:

```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE TenantId = @TenantId
  AND CreatedAt >= @FromDate;
```

Investigation:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

So sánh actual execution plan với nhiều parameter đại diện. Các mitigation có thể gồm:

* cải thiện index/data model;
* `OPTION (RECOMPILE)` cho query đặc thù;
* `OPTIMIZE FOR` trong trường hợp phù hợp;
* tách query path cho skewed workloads;
* dùng Query Store để quan sát/force plan khi có bằng chứng.

## 5. Real production scenario

SaaS invoice API nhanh cho 98% tenants nhưng p99 cực cao ở vài enterprise tenants. App code giống nhau; bottleneck nằm ở plan được tối ưu cho tenant nhỏ nhưng reused cho tenant lớn.

## 6. Failure scenario & troubleshooting

**Symptom** → query đôi khi 40 ms, đôi khi 8 giây với cùng SQL text.

**Evidence** → actual rows lệch xa estimated rows; Query Store cho thấy plan regressions.

**Hypothesis** → skew + parameter-sensitive plan.

**Diagnosis** → chạy query với representative values, xem estimated/actual cardinality và logical reads.

**Fix** → chọn mitigation dựa trên workload, không tự động `RECOMPILE` mọi nơi.

**Verification** → benchmark nhiều tenant classes và theo dõi p95/p99 sau deploy.

## 7. Common mistakes

* Đổ lỗi cho “SQL chậm” mà không xem plan.
* Clear plan cache ở production như giải pháp lâu dài.
* Dùng `RECOMPILE` đại trà làm tăng CPU compile.
* Chỉ test một tenant nhỏ.

## 8. Alternatives

Nếu data skew là đặc tính domain lâu dài, có thể cần partitioning, separate data stores hoặc workload-specific query path thay vì chỉ hint optimizer.

## 9. Trade-offs

### Advantages

Plan reuse giảm compile cost.

### Costs / Risks

Một cached plan có thể không phù hợp skewed parameters.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu parameterized query có execution plan được cache.

### Middle

Biết đọc actual plan, logical reads và Query Store.

### Senior

Phân biệt index problem, stale statistics và parameter-sensitive plan.

### Technical Lead / Architect

Đánh giá data distribution và tenant scale có yêu cầu query/data partitioning strategy riêng hay không.

## 11. Key takeaway

* Cùng SQL text không đồng nghĩa cùng cost cho mọi parameter.
* Diagnose bằng actual plan + representative values.
* Hint là công cụ cuối, không thay thế hiểu data distribution.

# 4. CQRS với một database: tách intent trước khi nghĩ tới separate read/write stores

## 1. What is it?

CQRS tách command và query theo intent.

* Command thay đổi state.
* Query đọc state.

CQRS **không bắt buộc** phải có hai database, Event Sourcing hoặc message broker.

Mental model đơn giản:

```text
HTTP POST → Command Handler → Domain/DB
HTTP GET  → Query Handler   → DB projection
```

## 2. Why does it exist?

Read và write thường có concern khác nhau. Write cần invariant, transaction và authorization. Read cần projection tối ưu cho UI/reporting.

Nếu ép cả hai qua cùng generic service/repository abstraction, API có thể trở nên khó tối ưu hoặc business rules bị trộn với read mapping.

## 3. How does it work?

Với một database:

```text
Command side ─┐
              ├─ SQL Server
Query side   ─┘
```

Sự tách biệt nằm ở code path và model, không nhất thiết ở infrastructure.

## 4. Practical implementation

```csharp
public sealed record ApproveInvoiceCommand(Guid InvoiceId);

public sealed class ApproveInvoiceHandler
{
    private readonly AppDbContext _db;

    public ApproveInvoiceHandler(AppDbContext db) => _db = db;

    public async Task Handle(
        ApproveInvoiceCommand command,
        CancellationToken cancellationToken)
    {
        var invoice = await _db.Invoices
            .SingleAsync(x => x.Id == command.InvoiceId, cancellationToken);

        invoice.Approve();
        await _db.SaveChangesAsync(cancellationToken);
    }
}
```

Query có thể projection trực tiếp:

```csharp
var dto = await db.Invoices
    .AsNoTracking()
    .Where(x => x.Id == id)
    .Select(x => new InvoiceDetailsDto(
        x.Id, x.Status, x.Total, x.Customer.Name))
    .SingleAsync(cancellationToken);
```

## 5. Real production scenario

Approval platform có write rules phức tạp nhưng dashboard đọc hàng nghìn records. Command path giữ domain invariants; query path projection trực tiếp DTO. Cả hai vẫn dùng một SQL database để giữ operations đơn giản.

## 6. Failure scenario & troubleshooting

**Symptom** → team áp CQRS rồi tạo hàng trăm handler chỉ forward sang service khác, không có khác biệt về responsibility.

**Evidence** → thêm ceremony nhưng không giảm coupling hay complexity.

**Hypothesis** → pattern được áp dụng theo template thay vì problem.

**Diagnosis** → xem command/query boundaries có thực sự khác behavior, model hoặc optimization không.

**Fix** → đơn giản hóa những use case CRUD thuần.

**Verification** → code path ngắn hơn, ownership rõ hơn và test tập trung vào behavior.

## 7. Common mistakes

* Đồng nhất CQRS với MediatR.
* Cho rằng CQRS bắt buộc separate DB.
* Tạo command cho mọi setter nhỏ.
* Tách architecture trước khi business complexity xuất hiện.

## 8. Alternatives

* Simple layered CRUD: tốt cho domain đơn giản.
* CQRS one database: complexity vừa phải.
* Separate read/write stores: chỉ khi scale/model/latency yêu cầu.
* Event Sourcing: một pattern khác, không bắt buộc đi với CQRS.

## 9. Trade-offs

### Advantages

* Intent rõ.
* Read model linh hoạt.
* Write path bảo vệ invariant tốt hơn.

### Costs / Risks

* Nhiều classes/conventions.
* Có thể overengineer CRUD.
* Separate stores tăng consistency và operations cost nếu tiến quá xa.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt read và state-changing operation.

### Middle

Biết xây command/query handler rõ responsibility.

### Senior

Đánh giá transaction, authorization và read optimization.

### Technical Lead / Architect

Quyết định CQRS có thực sự giải quyết complexity hay chỉ thêm ceremony; chỉ tách stores khi business/scale justify.

## 11. Key takeaway

* CQRS bắt đầu từ separation of intent.
* Một database thường đủ cho nhiều hệ thống.
* Không cần Event Sourcing hay Microservices để “được gọi là CQRS”.

# 5. Inbox Pattern cho message consumer: xử lý duplicate delivery mà không biến side effect thành double-charge

## 1. What is it?

Inbox Pattern lưu dấu message đã xử lý tại consumer để duplicate delivery không tạo side effect lần hai.

```text
Message arrives
   ↓
Check Inbox(MessageId)
   ├─ exists → acknowledge duplicate
   └─ absent → process + save Inbox record atomically
```

## 2. Why does it exist?

Message broker thường cung cấp at-least-once delivery. Nếu consumer xử lý xong nhưng crash trước khi acknowledge, broker có thể deliver lại message.

Vì vậy “message chỉ gửi một lần” không phải assumption an toàn.

## 3. How does it work?

Consumer dùng stable message identifier. Business side effect và inbox marker phải nằm trong cùng local transaction khi có thể.

```text
BEGIN TRANSACTION
  check Inbox
  update business state
  insert Inbox row
COMMIT
ACK broker message
```

Nếu ACK thất bại, redelivery sẽ thấy Inbox row và bỏ qua side effect.

## 4. Practical implementation

```csharp
public async Task HandleAsync(
    PaymentCaptured message,
    CancellationToken cancellationToken)
{
    await using var transaction =
        await _db.Database.BeginTransactionAsync(cancellationToken);

    var alreadyProcessed = await _db.InboxMessages
        .AnyAsync(x => x.MessageId == message.MessageId, cancellationToken);

    if (alreadyProcessed)
        return;

    var order = await _db.Orders
        .SingleAsync(x => x.Id == message.OrderId, cancellationToken);

    order.MarkPaid(message.Amount);

    _db.InboxMessages.Add(new InboxMessage
    {
        MessageId = message.MessageId,
        ProcessedAtUtc = DateTimeOffset.UtcNow
    });

    await _db.SaveChangesAsync(cancellationToken);
    await transaction.CommitAsync(cancellationToken);
}
```

Database cần unique constraint trên `MessageId` để race condition không tạo duplicate processing.

## 5. Real production scenario

Service Bus redeliver `PaymentCaptured` sau network interruption. Nếu consumer chỉ “process rồi Complete message”, order có thể bị ghi nhận payment hai lần. Inbox làm duplicate delivery trở thành no-op.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate business rows dù Inbox tồn tại.

**Evidence** → hai consumer đồng thời check “not exists” rồi cùng process.

**Hypothesis** → check và insert không có uniqueness/atomicity.

**Diagnosis** → xem transaction isolation và unique index.

**Fix** → unique constraint + transactional write; xử lý duplicate-key như already processed.

**Verification** → test concurrent duplicate delivery.

## 7. Common mistakes

* Tin broker sẽ exactly-once end-to-end.
* Dùng timestamp làm dedup key không ổn định.
* Check Inbox ngoài transaction.
* Không cleanup Inbox retention.
* Side effect gọi external API không idempotent nhưng vẫn coi local transaction là đủ.

## 8. Alternatives

* Natural idempotency bằng business key.
* Upsert/unique constraint trực tiếp trên business state.
* External idempotency key nếu downstream API hỗ trợ.

## 9. Trade-offs

### Advantages

* Chống duplicate delivery thực tế.
* Dễ audit message history.

### Costs / Risks

* Tăng storage/write cost.
* Cần cleanup strategy.
* External side effects vẫn cần idempotency riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu message có thể được giao nhiều lần.

### Middle

Biết dedup bằng message ID và unique constraint.

### Senior

Thiết kế transaction boundary và external side-effect idempotency.

### Technical Lead / Architect

Quy định message identity, retention, ownership và idempotency contract toàn integration landscape.

## 11. Key takeaway

* At-least-once delivery yêu cầu consumer idempotent.
* Inbox marker phải gắn với business transaction.
* Exactly-once business effect là thiết kế application, không phải lời hứa của broker.

# 6. Azure Private Endpoint + Private DNS: private connectivity chỉ đúng khi name resolution cũng đúng

## 1. What is it?

Private Endpoint tạo network interface với private IP trong VNet cho Azure PaaS resource như Key Vault, Storage hoặc SQL. Client kết nối tới private IP thay vì public endpoint.

Nhưng hostname vẫn thường là hostname chuẩn của service. Vì vậy DNS phải resolve đúng private address.

## 2. Why does it exist?

Public network access tăng exposure và phụ thuộc internet/public routing. Private Endpoint đưa data plane traffic vào private network boundary.

Tuy nhiên “đã tạo Private Endpoint” chưa có nghĩa application sẽ dùng nó nếu DNS vẫn trả public IP.

## 3. How does it work?

```text
App in VNet
   ↓ lookup myvault.vault.azure.net
Private DNS zone
   ↓ private IP
Private Endpoint NIC
   ↓
Key Vault
```

Nếu DNS sai:

```text
hostname → public IP
```

Application có thể timeout hoặc bị firewall chặn dù Private Endpoint vẫn “Healthy”.

## 4. Practical implementation

Operational check từ Linux container/VM:

```bash
nslookup myvault.vault.azure.net
```

Hoặc:

```bash
dig myvault.vault.azure.net
```

Kết quả phải dẫn tới private IP theo thiết kế. Với App Service VNet Integration, cần kiểm tra VNet link tới Private DNS zone và DNS forwarding nếu dùng custom DNS.

## 5. Real production scenario

App Service truy cập Key Vault qua Private Endpoint. Dev environment chạy tốt; Production timeout. Network team đã tạo endpoint nhưng quên link Private DNS zone với Production VNet.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout khi gọi Storage/Key Vault; Azure resource khỏe.

**Evidence** → `nslookup` từ workload trả public IP.

**Hypothesis** → name resolution bypass private endpoint.

**Diagnosis** → kiểm tra Private DNS zone, VNet link, custom DNS forwarder và split-horizon configuration.

**Fix** → sửa DNS path, không hard-code private IP.

**Verification** → resolve hostname và kiểm tra connection telemetry từ workload subnet.

## 7. Common mistakes

* Chỉ kiểm tra Private Endpoint status.
* Hard-code private IP.
* Quên DNS khi có hub-spoke/custom DNS.
* Disable public access trước khi validate private path.
* Không test từ đúng subnet/workload runtime.

## 8. Alternatives

* Service Endpoint: network restriction khác model, không tạo private NIC cho resource.
* Public endpoint + firewall/IP rules: đơn giản hơn nhưng exposure khác.

## 9. Trade-offs

### Advantages

* Private data-plane path.
* Giảm public exposure.
* Tích hợp tốt với enterprise network segmentation.

### Costs / Risks

* DNS/networking complexity tăng.
* Troubleshooting cross-team khó.
* Chi phí endpoint và operational governance tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hostname resolution quyết định traffic đi đâu.

### Middle

Biết kiểm tra DNS, private IP và VNet integration.

### Senior

Debug split DNS, hub-spoke và firewall path.

### Technical Lead / Architect

Thiết kế private connectivity pattern thống nhất, ownership giữa app/platform/network và rollout tránh self-inflicted outage.

## 11. Key takeaway

* Private Endpoint và Private DNS là một cặp thiết kế.
* Test từ runtime environment, không từ laptop.
* Network security đúng phải đi kèm observability và rollback path.

# 7. OAuth 2.0 refresh token rotation: giảm blast radius của token bị đánh cắp nhưng yêu cầu state và replay detection

## 1. What is it?

Refresh token rotation phát refresh token mới mỗi lần token cũ được dùng. Token cũ sau đó bị invalidated hoặc đánh dấu đã sử dụng.

```text
RT1 → token endpoint → AT2 + RT2
RT1 reused later → suspicious replay
```

## 2. Why does it exist?

Access token thường ngắn hạn. Refresh token sống lâu hơn nên nếu bị đánh cắp, attacker có thể duy trì access lâu. Rotation làm token bị đánh cắp có cửa sổ sử dụng nhỏ hơn và giúp phát hiện replay.

## 3. How does it work?

Authorization server giữ state/token family. Khi `RT1` được exchange, `RT2` được phát hành. Nếu `RT1` xuất hiện lại, server có thể revoke toàn token family vì có dấu hiệu theft/replay.

## 4. Practical implementation

Application không tự phát minh refresh-token protocol nếu dùng identity provider chuẩn. Nhưng client/backend phải xử lý token storage an toàn và refresh race.

Pseudo-flow thực tế:

```text
401 / token near expiry
   ↓
Acquire refresh lock
   ↓
Exchange refresh token once
   ↓
Persist new RT atomically
   ↓
Retry original call
```

Trong browser app, ưu tiên Authorization Code + PKCE và provider guidance thay vì lưu long-lived refresh token tùy tiện trong `localStorage`.

## 5. Real production scenario

Mobile app có session dài nhiều tuần. Rotation cho phép backend phát hiện refresh token cũ bị replay từ thiết bị khác và revoke session family.

## 6. Failure scenario & troubleshooting

**Symptom** → users thỉnh thoảng bị logout khi app mở nhiều tabs/devices.

**Evidence** → hai refresh requests gần đồng thời dùng cùng refresh token.

**Hypothesis** → client refresh race làm token cũ bị reuse hợp lệ nhưng trông giống replay.

**Diagnosis** → correlation logs tại token endpoint và client refresh timeline.

**Fix** → serialize refresh per session, atomic token persistence, provider-supported grace behavior nếu có.

**Verification** → concurrency test nhiều requests cùng lúc khi token hết hạn.

## 7. Common mistakes

* Lưu refresh token trong unsafe browser storage.
* Không revoke token family khi replay đáng ngờ.
* Log token value.
* Tự build OAuth server khi không cần.
* Dùng access token lifetime cực dài để né refresh complexity.

## 8. Alternatives

* Cookie session cho server-rendered web app.
* Short-lived access token không refresh cho machine jobs ngắn.
* Client credentials/Managed Identity cho service-to-service, không dùng user refresh token.

## 9. Trade-offs

### Advantages

* Giảm lifetime hữu dụng của stolen token.
* Phát hiện replay tốt hơn.

### Costs / Risks

* Cần server state/token family logic.
* Client concurrency phức tạp.
* Incorrect rotation dễ gây forced logout.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu access token và refresh token khác mục đích.

### Middle

Biết implement client flow theo provider SDK/protocol.

### Senior

Đánh giá token theft, storage, replay và concurrency.

### Technical Lead / Architect

Chọn authentication flow theo client type và threat model; không áp một token strategy cho mọi workload.

## 11. Key takeaway

* Refresh token là credential nhạy cảm dài hạn.
* Rotation giảm blast radius nhưng cần replay semantics đúng.
* Service-to-service và user authentication cần flow khác nhau.

# 8. SLO, error budget và burn rate: biến reliability thành engineering decision thay vì dashboard decoration

## 1. What is it?

SLI là metric đo reliability thực tế. SLO là target cho SLI. Error budget là phần failure được phép trong target window.

Ví dụ SLO 99.9% availability trong 30 ngày cho phép khoảng 0.1% requests thất bại theo định nghĩa SLI.

Burn rate đo tốc độ tiêu error budget so với tốc độ cho phép.

## 2. Why does it exist?

“Zero downtime” không phải target thực tế cho hầu hết hệ thống. Nếu không có reliability target, team không có framework để cân bằng feature velocity và stability work.

## 3. How does it work?

```text
SLI: successful requests / valid requests
        ↓
SLO: 99.9% over 30 days
        ↓
Error budget: allowed failure portion
        ↓
Burn rate: how fast budget is being consumed
```

High burn rate trong short window có thể báo incident nhanh hơn chỉ nhìn availability trung bình tháng.

## 4. Practical implementation

Prometheus-style conceptual query:

```text
error_ratio = 5xx_requests / total_valid_requests
```

Trong Application Insights/Azure Monitor, team có thể xây metric/filter tương tự, nhưng quan trọng là định nghĩa “valid requests” và loại trừ expected 4xx nếu phù hợp business semantics.

Alert strategy nên kết hợp short-window high burn và long-window sustained burn.

## 5. Real production scenario

Checkout API có SLO 99.95%. Sau deploy, error rate chỉ 1% trong 15 phút nên dashboard tháng trông vẫn “99.9x%”. Burn-rate alert phát hiện error budget đang bị tiêu nhanh bất thường và page on-call sớm.

## 6. Failure scenario & troubleshooting

**Symptom** → team có SLO đẹp nhưng users vẫn phàn nàn.

**Evidence** → SLI chỉ đo HTTP 200, trong khi API trả 200 với business failure payload.

**Hypothesis** → SLI không phản ánh user-visible success.

**Diagnosis** → map user journey với technical telemetry.

**Fix** → định nghĩa SLI theo success semantics thực tế, có thể gồm dependency/business outcome.

**Verification** → incident thực tế phải làm SLI xấu đi theo cách hợp lý.

## 7. Common mistakes

* Dùng SLA làm SLO nội bộ.
* Đặt 99.999% vì “nghe tốt”.
* Alert mọi single failure thay vì burn rate.
* SLI không phản ánh user experience.
* Có error budget nhưng không dùng vào release decision.

## 8. Alternatives

Traditional threshold alerts vẫn hữu ích cho CPU, queue depth, saturation nhưng không thay thế service-level reliability target.

## 9. Trade-offs

### Advantages

* Reliability có ngôn ngữ định lượng.
* Cân bằng feature vs stability.
* Alert gắn với user impact hơn.

### Costs / Risks

* Chọn SLI sai tạo false confidence.
* Telemetry pipeline cần đáng tin.
* Multi-service SLO decomposition phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu availability không chỉ là “server up”.

### Middle

Biết đọc error rate, latency và SLO dashboards.

### Senior

Thiết kế SLI gắn với user journey và burn-rate alert.

### Technical Lead / Architect

Dùng error budget để quyết định release risk, resilience investment và reliability ownership.

## 11. Key takeaway

* SLO phải đo điều user thực sự quan tâm.
* Error budget biến reliability thành trade-off định lượng.
* Burn rate giúp phát hiện budget đang bị tiêu quá nhanh.

# 9. Playwright E2E testing: test user-critical flow nhưng không biến test suite thành production clone chậm và flaky

## 1. What is it?

Playwright điều khiển browser thật để test hệ thống từ UI qua network/backend theo góc nhìn user.

Mental model:

```text
Browser action
  ↓
Frontend
  ↓
API
  ↓
Database / dependencies
```

Đây là test có fidelity cao nhưng cost cũng cao.

## 2. Why does it exist?

Unit test không phát hiện được mọi integration failure như route sai, auth redirect lỗi, broken JavaScript bundle, CORS issue hoặc API contract mismatch.

E2E test bảo vệ một số critical journeys mà lower-level tests không thể cover toàn chain.

## 3. How does it work?

Playwright launch browser, navigate, interact bằng locator và assert observable behavior. Auto-wait giúp giảm một số timing race nhưng không chữa test design kém.

## 4. Practical implementation

```typescript
import { test, expect } from '@playwright/test';

test('user can submit timesheet', async ({ page }) => {
  await page.goto('/timesheets/new');

  await page.getByLabel('Hours').fill('8');
  await page.getByRole('button', { name: 'Submit' }).click();

  await expect(page.getByText('Submitted')).toBeVisible();
});
```

Không nên dùng arbitrary `waitForTimeout(5000)` nếu có deterministic condition để chờ.

## 5. Real production scenario

Timesheet app có critical flow: login → create timesheet → submit → manager sees pending approval. Team giữ vài E2E flows quan trọng, còn validation/business rules chủ yếu test ở unit/integration layer.

## 6. Failure scenario & troubleshooting

**Symptom** → CI fail ngẫu nhiên, rerun lại pass.

**Evidence** → test dùng fixed sleeps và shared test account/data.

**Hypothesis** → race condition và test isolation kém.

**Diagnosis** → trace viewer, screenshots, network logs và parallel test behavior.

**Fix** → stable locators, deterministic waits, isolated test data, API setup/cleanup khi phù hợp.

**Verification** → chạy suite nhiều lần song song và đo flake rate.

## 7. Common mistakes

* Test mọi business rule bằng browser.
* CSS selector mong manh.
* Shared mutable data giữa tests.
* Fixed sleeps.
* E2E suite quá lớn làm pipeline chậm hàng chục phút.

## 8. Alternatives

* Unit tests: nhanh, cô lập logic.
* Integration tests: bảo vệ DB/API boundaries.
* Contract tests: bảo vệ service interfaces.
* E2E: dùng cho user-critical cross-system flows.

## 9. Trade-offs

### Advantages

* Fidelity cao.
* Bắt integration regression thực tế.

### Costs / Risks

* Chậm hơn.
* Flakiness risk cao hơn.
* Setup environment/data phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu E2E test mô phỏng user flow.

### Middle

Viết stable locator và deterministic wait.

### Senior

Thiết kế test pyramid theo risk và debug flakiness bằng trace/evidence.

### Technical Lead / Architect

Quy định flow nào xứng đáng E2E và kiểm soát pipeline cost, test data và environment ownership.

## 11. Key takeaway

* E2E test nên bảo vệ critical journeys, không thay thế lower-level tests.
* Flakiness thường là design signal.
* Test strategy là risk allocation, không phải coverage competition.

# 10. C# `record`, value equality và domain semantics: khi “hai object giống nhau” là yêu cầu nghiệp vụ chứ không chỉ syntax

## 1. What is it?

C# `record` cung cấp value-based equality mặc định: hai instances có cùng component values có thể được xem là equal.

```csharp
public sealed record Money(decimal Amount, string Currency);
```

```csharp
new Money(100, "USD") == new Money(100, "USD") // true
```

Điều quan trọng là semantics: value equality phù hợp với object được định nghĩa bởi giá trị, không phải identity.

## 2. Why does it exist?

Class thường dùng reference equality mặc định. Với Value Object như Money, Address hoặc DateRange, identity của instance không quan trọng; values mới là meaning.

Nếu equality semantics sai, deduplication, dictionary key, tests và domain rules có thể sai theo cách khó thấy.

## 3. How does it work?

Record compiler sinh equality members dựa trên positional/properties. `with` expression hỗ trợ non-destructive mutation:

```csharp
var updated = original with { Currency = "EUR" };
```

Nhưng record không tự biến nested mutable object thành immutable. Value semantics chỉ an toàn khi toàn object graph phù hợp.

## 4. Practical implementation

```csharp
public sealed record Money(decimal Amount, string Currency)
{
    public Money Add(Money other)
    {
        if (Currency != other.Currency)
            throw new InvalidOperationException("Currency mismatch");

        return this with { Amount = Amount + other.Amount };
    }
}
```

Entity lại thường cần identity semantics:

```csharp
public sealed class Order
{
    public Guid Id { get; init; }
}
```

Hai orders có cùng values nhưng khác `Id` vẫn là hai entities khác nhau.

## 5. Real production scenario

Pricing engine dùng `Money` làm Value Object. Value equality giúp test, caching key và dedup logic rõ ràng. Nhưng nếu dùng record cho mutable EF Core entity chỉ vì “syntax ngắn”, equality semantics có thể không phù hợp lifecycle của entity.

## 6. Failure scenario & troubleshooting

**Symptom** → object trong `HashSet` không được tìm thấy sau khi nested mutable property thay đổi.

**Evidence** → hash-relevant value thay đổi sau insertion.

**Hypothesis** → value object không thực sự immutable.

**Diagnosis** → inspect equality members và nested collections/references.

**Fix** → immutable value object; tránh mutable members trong hashed equality semantics.

**Verification** → unit tests cho equality, hash code và collection behavior.

## 7. Common mistakes

* Dùng record cho mọi DTO/entity vì ngắn.
* Cho mutable collection vào Value Object rồi tưởng immutable.
* Đồng nhất record với DDD Value Object hoàn chỉnh.
* Dùng entity values để equality thay vì identity.

## 8. Alternatives

* Class + explicit `IEquatable<T>` khi cần custom equality.
* `readonly record struct` cho small value type phù hợp.
* Regular class cho identity-based entity.

## 9. Trade-offs

### Advantages

* Value equality thuận tiện.
* Syntax concise.
* Phù hợp immutable data/value objects.

### Costs / Risks

* Equality semantics có thể bị dùng sai.
* Nested mutability vẫn tồn tại.
* EF/domain entity lifecycle có thể không phù hợp record semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu reference equality và value equality khác nhau.

### Middle

Biết dùng record cho DTO/value-centric models.

### Senior

Đánh giá hash/equality, immutability và ORM interaction.

### Technical Lead / Architect

Xác định domain type nào có identity, type nào được định nghĩa bởi values và giữ semantics nhất quán xuyên persistence/API/domain.

## 11. Key takeaway

* Chọn `record` vì equality semantics, không chỉ vì syntax đẹp.
* Value Object nên được định nghĩa bởi values và gần như immutable.
* Entity identity và Value Object equality là hai domain concepts khác nhau.
