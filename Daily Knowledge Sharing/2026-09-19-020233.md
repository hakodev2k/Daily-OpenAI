# 1. .NET `CancellationToken`: cancellation propagation như một end-to-end resource contract

## 1. What is it?

`CancellationToken` là cooperative cancellation mechanism của .NET. Mental model đúng không phải “ném `OperationCanceledException` để dừng code”, mà là **tín hiệu ownership rằng caller không còn cần work này nữa và các layer phía dưới nên ngừng tiêu thụ tài nguyên khi có thể**.

Một request bị client disconnect nhưng application vẫn query database, gọi HTTP dependency và serialize kết quả là work không còn giá trị.

## 2. Why does it exist?

Không thể an toàn “kill” arbitrary thread đang chạy managed code. Work có thể đang giữ lock, transaction hoặc unmanaged resource. Vì vậy cancellation phải cooperative: caller phát tín hiệu; operation quan sát token tại những điểm an toàn.

Trong backend, cancellation giúp giải phóng:

- database connection sớm hơn;
- HTTP connection và socket work;
- CPU loop không còn cần thiết;
- queue/worker shutdown đúng cách.

## 3. How does it work?

```text
Client disconnect / timeout
        │
        ▼
HttpContext.RequestAborted
        │
        ▼
Application service
        │
        ├── EF Core query
        └── HttpClient call
```

Token chỉ có tác dụng nếu được propagate. Một method nhận token nhưng gọi dependency mà không truyền token xuống dưới đã phá cancellation chain.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    OrderService service,
    CancellationToken ct) =>
{
    var order = await service.GetAsync(id, ct);
    return order is null ? Results.NotFound() : Results.Ok(order);
});

public async Task<OrderDto?> GetAsync(Guid id, CancellationToken ct)
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    if (order is null) return null;

    var risk = await riskClient.GetFromJsonAsync<RiskDto>(
        $"risk/{id}", ct);

    return Map(order, risk);
}
```

## 5. Real production scenario

Search API có p95 2 giây. User đổi filter liên tục, browser hủy request cũ. Nếu cancellation không xuống SQL và Elasticsearch client, server tiếp tục xử lý hàng loạt queries mà không response nào còn được dùng.

## 6. Failure scenario & troubleshooting

**Symptom** → request count giảm nhưng database CPU và active commands vẫn cao.  
**Evidence** → traces cho thấy HTTP span đã kết thúc nhưng dependency calls tiếp tục.  
**Hypothesis** → cancellation chain bị mất.  
**Diagnosis** → inspect method signatures và dependency calls; tìm `CancellationToken.None` hoặc overload không nhận token.  
**Fix** → propagate token đến I/O boundary; với cleanup bắt buộc, dùng lifecycle riêng thay vì token đã cancelled.  
**Verification** → cancel load test và quan sát dependency duration/active connections giảm nhanh.

## 7. Common mistakes

Nhận token nhưng không truyền xuống; tạo `new CancellationTokenSource()` vô cớ và tách khỏi caller; catch `OperationCanceledException` rồi log Error; dùng cancellation như rollback guarantee; check token quá thường xuyên trong trivial code nhưng bỏ quên expensive I/O.

## 8. Alternatives

Timeout giới hạn thời lượng; cancellation biểu diễn caller intent. Hai khái niệm thường phối hợp bằng linked token. Queue-based work có thể cần durable cancellation command thay vì request-scoped token.

## 9. Trade-offs

### Advantages

Giảm wasted work, cải thiện shutdown và bảo vệ downstream capacity.

### Costs / Risks

Propagation làm API signatures dài hơn; cancellation giữa side effects cần reasoning về partial completion.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cancellation là cooperative signal.

### Middle

Propagate token xuyên controller/service/EF Core/HttpClient.

### Senior

Phân biệt cancellation trước và sau side effect; thiết kế cleanup, timeout và telemetry đúng.

### Technical Lead / Architect

Định nghĩa cancellation boundary cho HTTP, workers và distributed workflows; không giả định in-process token có thể cancel work đã được publish sang service khác.

## 11. Key takeaway

- Cancellation là resource-management contract xuyên call chain.
- Timeout và cancellation liên quan nhưng không giống nhau.
- Sau một irreversible side effect, cancellation cần business reasoning chứ không chỉ `ThrowIfCancellationRequested()`.

# 2. ASP.NET Core `ProblemDetails`: error contract ổn định mà không làm lộ implementation

## 1. What is it?

`ProblemDetails` là machine-readable HTTP error representation dựa trên RFC problem details semantics. Giá trị chính của nó là tạo **public error contract** tách khỏi exception classes và stack trace nội bộ.

## 2. Why does it exist?

Nếu mỗi endpoint trả error shape khác nhau, frontend phải viết parsing logic theo từng API. Nếu serialize exception trực tiếp, application làm lộ implementation, stack trace hoặc sensitive data.

## 3. How does it work?

```text
Domain/Application failure
        │
        ▼
Exception / result mapping
        │
        ▼
HTTP status + ProblemDetails
        │
        ▼
Client handles stable error code
```

HTTP status biểu diễn protocol semantics; `type`, `title`, `detail` và extensions có thể bổ sung domain-specific information.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();
app.UseExceptionHandler();
app.UseStatusCodePages();

app.MapPost("/orders", async (CreateOrder request, OrderService service, CancellationToken ct) =>
{
    var result = await service.CreateAsync(request, ct);

    return result switch
    {
        CreateOrderResult.Duplicate => Results.Problem(
            statusCode: StatusCodes.Status409Conflict,
            title: "Order already exists",
            extensions: new Dictionary<string, object?>
            {
                ["code"] = "order_duplicate"
            }),
        _ => Results.Created($"/orders/{result.Id}", result)
    };
});
```

## 5. Real production scenario

Vue frontend cần phân biệt validation failure, concurrency conflict và dependency outage. Nó dựa trên stable `code`, không parse English `detail` string.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend behavior hỏng sau backend refactor dù status code không đổi.  
**Evidence** → client đang match exception message.  
**Hypothesis** → implementation detail đã trở thành accidental API contract.  
**Diagnosis** → inspect network payload và frontend branching.  
**Fix** → versioned/stable error codes và documented semantics.  
**Verification** → contract tests bảo vệ status + error code, không phụ thuộc stack trace/message nội bộ.

## 7. Common mistakes

Trả `200 OK` với `{ success:false }`; trả mọi lỗi thành 500; expose exception message; dùng `detail` như stable identifier; biến mọi domain failure thành exception.

## 8. Alternatives

Custom error envelope có thể hợp lý nếu organization đã có contract. `ValidationProblemDetails` phù hợp validation. gRPC dùng status/trailers thay HTTP JSON problem shape.

## 9. Trade-offs

### Advantages

Error handling nhất quán, dễ document và giảm coupling với implementation.

### Costs / Risks

Cần taxonomy/error-code governance; quá nhiều error codes tạo maintenance burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Map đúng HTTP status và hiểu 4xx khác 5xx.

### Middle

Implement centralized exception/problem mapping.

### Senior

Thiết kế stable error semantics, security redaction và observability correlation.

### Technical Lead / Architect

Quyết định organization-wide API error contract và backward compatibility policy.

## 11. Key takeaway

- Public error contract không nên là exception serialization.
- Client nên branch theo stable semantics, không parse human-readable message.
- `ProblemDetails` chuẩn hóa shape; domain taxonomy vẫn phải do team thiết kế.

# 3. PostgreSQL keyset pagination: stable ordering, composite cursor và index access path

## 1. What is it?

Keyset pagination lấy page tiếp theo dựa trên giá trị sort key cuối cùng đã thấy thay vì `OFFSET N`. Mental model: **tiếp tục scan từ một vị trí có thứ tự**, không yêu cầu database bỏ qua N rows trước đó.

## 2. Why does it exist?

`OFFSET 100000` vẫn buộc database tìm và discard rất nhiều rows. Với dataset thay đổi liên tục, offset còn có thể gây duplicate/missing items giữa pages.

## 3. How does it work?

Với ordering `(CreatedAt DESC, Id DESC)`, cursor phải chứa cả hai giá trị để tạo total order:

```sql
SELECT id, created_at, total
FROM orders
WHERE tenant_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Index phù hợp:

```sql
CREATE INDEX ix_orders_tenant_created_id
ON orders (tenant_id, created_at DESC, id DESC);
```

## 4. Practical implementation

```csharp
var query = db.Orders
    .Where(x => x.TenantId == tenantId);

if (cursor is not null)
{
    query = query.Where(x =>
        x.CreatedAt < cursor.CreatedAt ||
        (x.CreatedAt == cursor.CreatedAt && x.Id.CompareTo(cursor.Id) < 0));
}

var page = await query
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id)
    .Take(50)
    .AsNoTracking()
    .ToListAsync(ct);
```

Kiểm tra SQL translation thực tế thay vì giả định LINQ tạo đúng access path.

## 5. Real production scenario

Audit log có hàng trăm triệu rows. Admin UI chủ yếu Next/Previous, không cần nhảy tới “page 18,432”. Keyset giảm I/O đáng kể so với deep offset.

## 6. Failure scenario & troubleshooting

**Symptom** → một số records bị lặp giữa pages.  
**Evidence** → ordering chỉ dùng `CreatedAt`, nhiều rows cùng timestamp.  
**Hypothesis** → sort order không deterministic.  
**Diagnosis** → kiểm tra duplicate sort values và generated SQL.  
**Fix** → thêm unique tie-breaker vào ordering/cursor/index.  
**Verification** → insert concurrent records trong pagination test và kiểm tra không duplicate theo traversal semantics.

## 7. Common mistakes

Cursor chỉ chứa timestamp; sort expression không match index; encode cursor nhưng không validate tenant/filter context; quảng cáo keyset như hỗ trợ random page number tự nhiên.

## 8. Alternatives

Offset pagination đơn giản và phù hợp dataset nhỏ hoặc UX cần random page. Snapshot/export workflow phù hợp khi cần consistent traversal toàn dataset.

## 9. Trade-offs

### Advantages

Deep-page performance ổn định hơn và ít chịu row shifting.

### Costs / Risks

Cursor phức tạp hơn, khó jump arbitrary page, ordering phải deterministic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `OFFSET` và cursor khác nhau.

### Middle

Implement composite cursor và matching index.

### Senior

Đọc execution plan, I/O và concurrent-write semantics.

### Technical Lead / Architect

Chọn pagination contract theo UX, dataset size và consistency requirement thay vì mặc định một pattern.

## 11. Key takeaway

- Keyset pagination là ordered continuation, không phải offset được encode.
- Total order cần tie-breaker ổn định.
- Query, ordering và index phải được thiết kế cùng nhau.

# 4. Elasticsearch synchronization: Outbox, indexing lag và read-your-write expectation

## 1. What is it?

Khi SQL là source of truth và Elasticsearch phục vụ search, synchronization là pipeline đưa committed business changes sang search index. Đây là eventual-consistency boundary, không phải “save vào hai database”.

## 2. Why does it exist?

Dual write trực tiếp rất dễ rơi vào partial failure: SQL commit thành công nhưng Elasticsearch indexing thất bại, hoặc ngược lại. Distributed transaction thường không khả dụng và không đáng complexity.

## 3. How does it work?

```text
SQL transaction
 ├── Business row
 └── Outbox event
        │
        ▼
Publisher / Consumer
        │
        ▼
Elasticsearch index
        │
        ▼
Search API
```

Outbox đảm bảo business change và intent-to-publish được commit atomically trong cùng database transaction.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

product.ChangeName(request.Name);
db.OutboxMessages.Add(OutboxMessage.From(
    new ProductChanged(product.Id, product.Version)));

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Consumer nên index idempotently, thường dùng document ID ổn định và version/order strategy phù hợp.

## 5. Real production scenario

Editor publish CMS product content. Product detail page đọc primary store thấy dữ liệu mới ngay, nhưng search results cập nhật sau vài giây. Product team phải hiểu đây là expected consistency window.

## 6. Failure scenario & troubleshooting

**Symptom** → product tồn tại trong SQL nhưng mất khỏi search nhiều giờ.  
**Evidence** → outbox backlog tăng; Elasticsearch indexing errors xuất hiện.  
**Hypothesis** → synchronization pipeline stalled.  
**Diagnosis** → đo outbox age, consumer lag, failed document IDs và index health.  
**Fix** → retry bounded, DLQ/replay tooling, schema/mapping correction.  
**Verification** → backlog age trở về SLO và reconciliation không còn divergence.

## 7. Common mistakes

Dual write trong request; không có replay; dùng Elasticsearch làm transactional source of truth; không monitor lag; out-of-order event ghi đè version mới bằng version cũ.

## 8. Alternatives

CDC có thể phát changes từ database log. Scheduled rebuild đơn giản hơn cho low-frequency data. Direct synchronous indexing chỉ hợp lý nếu chấp nhận coupling/failure semantics rõ ràng.

## 9. Trade-offs

### Advantages

Tách transactional correctness khỏi search availability và cho phép replay.

### Costs / Risks

Eventual consistency, pipeline operations, schema evolution và reconciliation complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SQL và search index có vai trò khác nhau.

### Middle

Implement idempotent indexing consumer.

### Senior

Xử lý ordering, replay, lag metrics và mapping migration.

### Technical Lead / Architect

Định nghĩa source of truth, acceptable lag SLO và user experience trong consistency window.

## 11. Key takeaway

- Search synchronization là distributed consistency problem.
- Outbox loại một class dual-write failure nhưng không loại mọi failure.
- Indexing lag phải được đo và có recovery path.

# 5. DDD Aggregate: invariant boundary, transaction boundary và lý do Aggregate không phải object graph

## 1. What is it?

Aggregate là consistency boundary chứa một hoặc nhiều domain objects được thay đổi thông qua Aggregate Root. Nó không có nghĩa “load toàn bộ object graph liên quan”. Mental model: **những invariants nào phải đúng ngay sau một transaction?**

## 2. Why does it exist?

Nếu mọi entity có thể sửa trực tiếp từ mọi nơi, business invariants bị phân tán. Ngược lại, nếu gom cả domain vào một Aggregate khổng lồ, transaction contention và load cost tăng mạnh.

## 3. How does it work?

```text
Order (Aggregate Root)
 ├── OrderLine
 └── ShippingAddress value

Customer ── chỉ tham chiếu bằng CustomerId ──► Customer Aggregate
```

Aggregate boundary thường tương ứng transaction boundary. Cross-aggregate consistency thường cần eventual process hoặc application orchestration.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void AddLine(ProductId productId, int quantity, Money price)
    {
        if (quantity <= 0) throw new DomainException("Quantity must be positive");
        if (_lines.Count >= 50) throw new DomainException("Order line limit exceeded");

        _lines.Add(new OrderLine(productId, quantity, price));
    }
}
```

Invariant nằm ở domain behavior, không để controller tự sửa collection tùy ý.

## 5. Real production scenario

Timesheet Aggregate phải bảo đảm total submitted hours trong một ngày không vượt policy. Employee profile là Aggregate khác; timesheet chỉ giữ `EmployeeId`, không kéo toàn Employee graph vào transaction.

## 6. Failure scenario & troubleshooting

**Symptom** → update một Order cần load hàng nghìn child records và thường xuyên conflict.  
**Evidence** → Aggregate chứa lịch sử, payment, shipment, reviews và unrelated entities.  
**Hypothesis** → consistency boundary quá rộng.  
**Diagnosis** → hỏi invariant nào thực sự cần atomic transaction.  
**Fix** → tách boundaries và dùng events/workflows cho cross-boundary coordination.  
**Verification** → transaction nhỏ hơn nhưng business invariants vẫn được bảo vệ.

## 7. Common mistakes

DDD = Entities + Repository + MediatR; mỗi table là Aggregate; navigation property quyết định boundary; Aggregate Root chỉ là class có `Id`; cross-aggregate transaction ở mọi use case.

## 8. Alternatives

CRUD/anemic model có thể đủ cho domain đơn giản. Application-service validation hợp lý khi rule không phải invariant của một Aggregate. Không nên áp rich domain model chỉ để “đúng architecture”.

## 9. Trade-offs

### Advantages

Business invariants có ownership rõ, change isolation tốt hơn.

### Costs / Risks

Sai boundary tạo complexity, contention hoặc eventual-consistency burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt Entity, Value Object và Aggregate Root.

### Middle

Đặt invariant vào behavior và tránh bypass root.

### Senior

Reason về transaction boundary, concurrency và cross-aggregate workflow.

### Technical Lead / Architect

Xác định Bounded Context/Aggregate boundaries từ business invariants, ownership và operational constraints.

## 11. Key takeaway

- Aggregate là consistency boundary, không phải database relationship graph.
- Boundary càng lớn, transaction và contention cost càng cao.
- Domain đơn giản có thể không cần rich DDD model.

# 6. Azure Service Bus Sessions: ordered processing, stateful workflow và throughput trade-off

## 1. What is it?

Service Bus Sessions nhóm messages có cùng `SessionId` để một receiver giữ exclusive lock trên session và xử lý group đó theo thứ tự nhận. Mental model: **partitioned sequential stream theo business key**.

## 2. Why does it exist?

Competing consumers tăng throughput nhưng có thể xử lý messages của cùng Order song song hoặc lệch thứ tự. Một số workflows cần serialization theo entity/business process mà vẫn muốn parallelism giữa entities khác nhau.

## 3. How does it work?

```text
Order A: A1 → A2 → A3 ─► Session A ─► Consumer 1
Order B: B1 → B2 ──────► Session B ─► Consumer 2
```

Một session được lock bởi một receiver tại một thời điểm; sessions khác có thể xử lý song song.

## 4. Practical implementation

```csharp
var message = new ServiceBusMessage(BinaryData.FromObjectAsJson(evt))
{
    SessionId = evt.OrderId.ToString(),
    MessageId = evt.EventId.ToString()
};

await sender.SendMessageAsync(message, ct);
```

Consumer vẫn phải idempotent vì Service Bus có at-least-once delivery; session ordering không loại duplicate delivery.

## 5. Real production scenario

Order workflow nhận `Created`, `PaymentAuthorized`, `Packed`, `Shipped`. Dùng `OrderId` làm `SessionId` giúp một order được xử lý sequentially trong khi hàng nghìn orders khác chạy song song.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog lớn nhưng CPU consumers thấp.  
**Evidence** → phần lớn messages tập trung vào vài SessionId nóng.  
**Hypothesis** → hot sessions giới hạn parallelism.  
**Diagnosis** → đo active sessions, messages/session, processing duration và lock loss.  
**Fix** → xem lại partition key/business requirement; giảm work trong session handler; không phá ordering nếu invariant thực sự cần nó.  
**Verification** → backlog age giảm mà per-session ordering vẫn đúng.

## 7. Common mistakes

Nghĩ sessions cho exactly-once; dùng một `SessionId` cho toàn queue; handler quá lâu làm lock renewal phức tạp; không DLQ poison messages; dựa vào order nhưng producer phát events sai thứ tự từ đầu.

## 8. Alternatives

Không dùng sessions nếu operations idempotent/commutative. Partitioned stream platforms phù hợp event-stream workloads. Database optimistic concurrency đôi khi đơn giản hơn serialization ở broker.

## 9. Trade-offs

### Advantages

Ordering theo key và stateful workflow coordination rõ ràng.

### Costs / Risks

Hot session làm giảm throughput; session locks/state tăng operational complexity và cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue delivery và `SessionId` grouping.

### Middle

Implement session sender/processor và settlement.

### Senior

Thiết kế idempotency, lock handling, DLQ và hot-session diagnostics.

### Technical Lead / Architect

Quyết định ordering có phải business invariant hay chỉ là assumption có thể loại bỏ để tăng scalability.

## 11. Key takeaway

- Sessions serialize work theo key, không tạo exactly-once delivery.
- Ordering có throughput cost.
- Chỉ trả cost đó khi business invariant thực sự cần ordering.

# 7. Kubernetes readiness probe: traffic admission khác process liveness như thế nào

## 1. What is it?

Readiness probe trả lời: **Pod này có sẵn sàng nhận traffic ngay bây giờ không?** Nó khác liveness probe, vốn trả lời process có đang ở trạng thái cần restart hay không.

## 2. Why does it exist?

Process có thể đã chạy nhưng chưa load configuration, migration/check startup chưa xong hoặc dependency thiết yếu chưa sẵn sàng. Nếu Service route traffic quá sớm, deployment tạo 5xx dù container “Running”.

## 3. How does it work?

```text
Pod starts
   │
   ├─ liveness: alive?
   └─ readiness: ready for traffic?
                    │ yes
                    ▼
              Service endpoints
```

Readiness failure loại Pod khỏi traffic endpoints nhưng không nhất thiết restart container.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<StartupReadyCheck>("startup_ready", tags: ["ready"]);

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready")
});
```

Kubernetes:

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
  failureThreshold: 3
```

## 5. Real production scenario

Rolling deployment tạo Pod mới. App cần warm configuration/cache trong 20 giây. Readiness giữ Pod ngoài load balancer đến khi startup hoàn tất, trong khi Pods cũ vẫn phục vụ traffic.

## 6. Failure scenario & troubleshooting

**Symptom** → tất cả Pods chuyển NotReady khi Redis tạm lỗi, website mất toàn bộ capacity.  
**Evidence** → readiness endpoint phụ thuộc Redis dù application có fallback.  
**Hypothesis** → health semantics không match actual serving capability.  
**Diagnosis** → inspect probe dependencies và fallback behavior.  
**Fix** → chỉ fail readiness với dependency thực sự bắt buộc để serve; degraded dependencies đi vào telemetry/health khác.  
**Verification** → dependency outage không loại toàn fleet nếu app vẫn phục vụ degraded mode.

## 7. Common mistakes

Readiness và liveness dùng cùng endpoint; liveness check remote dependencies làm restart storm; probe quá aggressive; health endpoint thực hiện expensive query.

## 8. Alternatives

Startup probe hữu ích cho slow-start applications. App Service health check có semantics platform khác nhưng cùng nguyên tắc traffic admission. Không phải mọi dependency đều thuộc readiness.

## 9. Trade-offs

### Advantages

Safer rollout và tránh gửi traffic tới instance chưa sẵn sàng.

### Costs / Risks

Probe sai có thể tự tạo outage hoặc restart/traffic flapping.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt alive và ready.

### Middle

Implement health endpoints/probes.

### Senior

Thiết kế dependency semantics, thresholds và rollout diagnostics.

### Technical Lead / Architect

Định nghĩa service degradation model: dependency nào bắt buộc, dependency nào optional, và platform nên phản ứng ra sao.

## 11. Key takeaway

- Readiness điều khiển traffic; liveness điều khiển restart decision.
- Remote dependency không mặc nhiên thuộc liveness/readiness.
- Health check sai có thể gây outage lớn hơn failure ban đầu.

# 8. Contract Testing: bảo vệ API compatibility giữa services mà không biến CI thành distributed E2E

## 1. What is it?

Contract testing xác minh producer và consumer đồng ý về observable interface: endpoint, fields, types, required semantics hoặc message schema. Nó nằm giữa unit/integration tests và full E2E.

## 2. Why does it exist?

Service A có thể pass toàn bộ tests của nó nhưng deployment vẫn phá Service B vì rename field hoặc thay enum semantics. Full environment E2E cho mọi combination chậm và brittle.

## 3. How does it work?

```text
Consumer expectation
        │
        ▼
Contract artifact/spec
        │
        ▼
Producer verification
```

Contract chỉ nên mô tả behavior consumer thực sự phụ thuộc, không snapshot toàn response một cách vô thức.

## 4. Practical implementation

Một integration contract test đơn giản với ASP.NET Core:

```csharp
[Fact]
public async Task GetOrder_keeps_required_contract()
{
    var response = await client.GetAsync("/orders/123");
    response.EnsureSuccessStatusCode();

    var json = await response.Content.ReadFromJsonAsync<JsonElement>();
    Assert.True(json.TryGetProperty("id", out _));
    Assert.True(json.TryGetProperty("status", out var status));
    Assert.Contains(status.GetString(), new[] { "pending", "paid", "cancelled" });
}
```

Ở quy mô nhiều teams, consumer-driven contract tooling có thể publish/verify contracts trong CI.

## 5. Real production scenario

Checkout service phụ thuộc Product API field `currency`. Product team muốn đổi response model. Contract verification fail trước deployment vì consumer vẫn cần field đó.

## 6. Failure scenario & troubleshooting

**Symptom** → contract suite fail liên tục khi producer thêm harmless fields.  
**Evidence** → tests snapshot toàn JSON.  
**Hypothesis** → contract quá chặt, kiểm tra implementation shape thay vì consumer need.  
**Diagnosis** → map assertions về actual consumer behavior.  
**Fix** → tolerant reading và chỉ assert required semantics.  
**Verification** → additive compatible changes pass, breaking changes fail.

## 7. Common mistakes

Snapshot toàn payload; coi OpenAPI generation là đủ; contract test thay integration test; không version message schemas; mock producer behavior khác production.

## 8. Alternatives

OpenAPI/schema validation tốt cho structural compatibility. Integration tests tốt cho service + real dependencies. E2E cần cho critical journeys nhưng không nên là lớp duy nhất bắt breaking change.

## 9. Trade-offs

### Advantages

Feedback nhanh hơn distributed E2E và ownership breaking changes rõ hơn.

### Costs / Risks

Contract artifact/version management; false confidence nếu semantic expectations thiếu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu backward-compatible vs breaking API change.

### Middle

Viết contract assertions có ý nghĩa.

### Senior

Thiết kế consumer-driven verification và schema evolution.

### Technical Lead / Architect

Định nghĩa compatibility policy, ownership và release gates giữa teams/services.

## 11. Key takeaway

- Contract tests bảo vệ dependency assumptions, không thay mọi test layer.
- Chỉ contract hóa behavior consumer thật sự cần.
- Additive change nên dễ; breaking change phải có migration path rõ.

# 9. Third-party API resilience: timeout budget, retry, Circuit Breaker và failure amplification

## 1. What is it?

Resilience cho remote API là kiểm soát cách failure/latency của dependency lan vào hệ thống. Timeout, retry và Circuit Breaker giải quyết các failure modes khác nhau; ghép chúng sai có thể khuếch đại outage.

## 2. Why does it exist?

Network và remote services có partial failure. Nếu mỗi request chờ 100 giây và retry 5 lần, một dependency chậm có thể giữ hết sockets/requests và kéo chính application xuống.

## 3. How does it work?

```text
Incoming request budget: 3s
        │
        ├─ dependency timeout: 800ms
        ├─ bounded retry + jitter (chỉ transient + safe)
        └─ circuit opens khi failure vượt threshold
```

Retry tiêu thụ latency budget và tăng traffic. Circuit Breaker ngừng gọi tạm thời để tránh tiếp tục gây pressure khi dependency rõ ràng unhealthy.

## 4. Practical implementation

Với .NET resilience pipeline:

```csharp
builder.Services.AddHttpClient<ReviewClient>(client =>
{
    client.BaseAddress = new Uri(config["Reviews:BaseUrl"]!);
})
.AddStandardResilienceHandler(options =>
{
    options.AttemptTimeout.Timeout = TimeSpan.FromMilliseconds(800);
    options.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(2);
    options.Retry.MaxRetryAttempts = 2;
});
```

Retry policy phải xét HTTP method, idempotency và remote contract.

## 5. Real production scenario

Product page gọi review provider. Provider p99 tăng lên 8 giây. Nếu reviews là optional, page nên trả product data với reviews unavailable thay vì giữ toàn request đến timeout dài.

## 6. Failure scenario & troubleshooting

**Symptom** → provider outage làm outbound QPS tăng gấp ba.  
**Evidence** → retry count tăng cùng timeout/error rate.  
**Hypothesis** → retry amplification.  
**Diagnosis** → trace attempts, latency budget, status codes và concurrency.  
**Fix** → giảm attempts, exponential backoff+jitter, circuit/fallback và capacity isolation.  
**Verification** → dependency failure không làm application saturation; degraded behavior đúng contract.

## 7. Common mistakes

Retry mọi 4xx; retry non-idempotent POST không key; timeout từng attempt nhưng không có total budget; Circuit Breaker dùng như health check; fallback trả stale data mà business không cho phép.

## 8. Alternatives

Async queue phù hợp nếu caller không cần immediate result. Cache phù hợp dữ liệu có stale tolerance. Bulkhead/concurrency limiter bảo vệ capacity khi dependency chậm.

## 9. Trade-offs

### Advantages

Giảm failure propagation và tăng khả năng degraded operation.

### Costs / Risks

Policies thêm latency/complexity; retry sai làm outage nặng hơn; fallback có correctness cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu remote call luôn có thể timeout/fail.

### Middle

Configure timeout/retry có giới hạn và log attempts.

### Senior

Reason về idempotency, total budget, retry storm, circuit và fallback semantics.

### Technical Lead / Architect

Phân loại dependencies theo criticality và định nghĩa degradation/capacity isolation strategy.

## 11. Key takeaway

- Retry không phải reliability miễn phí; nó tiêu thụ budget và capacity.
- Timeout phải xuất phát từ end-to-end latency budget.
- Optional dependency nên có explicit degraded behavior nếu business cho phép.

# 10. Vue.js async state: race condition khi request cũ ghi đè request mới

## 1. What is it?

Frontend async race xảy ra khi nhiều requests cùng cập nhật một state nhưng completion order khác initiation order. User chọn filter B sau A, nhưng response A về muộn hơn và ghi đè dữ liệu B.

## 2. Why does it exist?

JavaScript execution là event-driven; `await` không đảm bảo các independent network requests hoàn tất theo thứ tự được gọi. UI nhanh và user interaction liên tục làm race dễ xuất hiện.

## 3. How does it work?

```text
User selects A ─► Request A ─────────────► response A (late)
User selects B ─────► Request B ─► response B
                              │            │
                              ▼            ▼
                           state=B      state=A ❌
```

## 4. Practical implementation

Dùng `AbortController` để cancel request cũ:

```ts
import { ref, watch } from 'vue'

const filter = ref('all')
const items = ref([])
let controller: AbortController | undefined

watch(filter, async value => {
  controller?.abort()
  controller = new AbortController()

  try {
    const response = await fetch(`/api/items?filter=${encodeURIComponent(value)}`, {
      signal: controller.signal
    })
    items.value = await response.json()
  } catch (error) {
    if (!(error instanceof DOMException && error.name === 'AbortError')) throw error
  }
})
```

Backend cũng nên propagate request cancellation để work cũ không tiếp tục vô ích.

## 5. Real production scenario

Automotive marketplace có make/model filters. User đổi Toyota → Ford nhanh. Ford response về trước nhưng Toyota response chậm hơn ghi đè list, khiến filter label và results không khớp.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị data không match selected filter.  
**Evidence** → DevTools Network cho thấy requests hoàn tất out of order.  
**Hypothesis** → stale response mutation.  
**Diagnosis** → throttle network và log request sequence/filter value.  
**Fix** → abort stale requests hoặc dùng monotonic request ID và chỉ accept latest response.  
**Verification** → automated UI test với delayed responses không còn stale overwrite.

## 7. Common mistakes

Giả định `await` serialize user actions; loading boolean dùng chung cho nhiều requests; abort request nhưng hiển thị AbortError như user-facing error; debounce được coi là race-condition guarantee.

## 8. Alternatives

Latest-request ID guard đơn giản khi transport không hỗ trợ cancellation. Data-fetching libraries có thể quản lý query keys/cancellation/cache. Debounce giảm request volume nhưng không thay stale-response protection.

## 9. Trade-offs

### Advantages

UI state nhất quán hơn và cancellation giảm wasted network/backend work.

### Costs / Risks

Cần lifecycle/error handling cẩn thận; cancellation không hoàn tác side effect đã xảy ra trên server.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu network completion order không deterministic.

### Middle

Implement cancellation/latest-response guard và loading/error state.

### Senior

Liên kết frontend cancellation với API semantics, caching và observability.

### Technical Lead / Architect

Chuẩn hóa async data-access pattern cho frontend để tránh mỗi component tự giải quyết race, retry và cache theo cách khác nhau.

## 11. Key takeaway

- Async UI phải bảo vệ state khỏi stale responses.
- Debounce giảm volume nhưng không đảm bảo ordering.
- Frontend cancellation có giá trị hơn khi backend cũng propagate cancellation.
