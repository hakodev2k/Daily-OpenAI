# 1. `System.Text.Json` polymorphism và contract evolution: serialize inheritance mà không biến wire format thành coupling khó nâng cấp

## 1. What is it?

Polymorphic serialization là việc serialize/deserialize một base type nhưng giữ được concrete subtype thực tế. Ví dụ một notification có thể là `EmailNotification`, `SmsNotification` hoặc `PushNotification`.

Mental model:

```text
Base contract
   -> discriminator
   -> concrete payload shape
```

Vấn đề không nằm ở inheritance syntax. Vấn đề là wire contract phải đủ rõ để client/server cùng hiểu subtype, đồng thời vẫn có chiến lược evolution khi thêm loại mới.

## 2. Why does it exist?

Nếu API chỉ trả base fields, client mất subtype-specific data. Nếu mỗi subtype thành endpoint riêng, contract bị phân mảnh. Polymorphism cho phép một abstraction chung nhưng payload vẫn mô tả concrete behavior.

Tuy nhiên, nếu serializer tự ghi CLR type name hoặc namespace vào JSON, wire format bị khóa chặt vào implementation nội bộ. Đây là coupling rất nguy hiểm cho public API, persistence hoặc integration message.

## 3. How does it work?

Trong `System.Text.Json`, polymorphism hiện đại nên dùng explicit discriminator mapping. Ví dụ:

```csharp
[JsonPolymorphic(TypeDiscriminatorPropertyName = "type")]
[JsonDerivedType(typeof(EmailNotification), "email")]
[JsonDerivedType(typeof(SmsNotification), "sms")]
public abstract record Notification;
```

Payload:

```json
{
  "type": "email",
  "subject": "Welcome"
}
```

Discriminator như `email` là protocol contract, không phải CLR type name.

## 4. Practical implementation

```csharp
public abstract record Notification;

public sealed record EmailNotification(
    string Subject,
    string Body) : Notification;

public sealed record SmsNotification(
    string PhoneNumber,
    string Message) : Notification;
```

Serialize:

```csharp
var json = JsonSerializer.Serialize<Notification>(
    new EmailNotification("Welcome", "Hello"));
```

Nếu contract là external/public, versioning policy phải định nghĩa client cũ làm gì khi gặp subtype mới.

## 5. Real production scenario

Một notification service lưu event vào queue với base type `NotificationRequested`. Ban đầu chỉ có email/SMS, sau đó thêm push notification.

Nếu consumer cũ gặp discriminator `push` mà fail toàn message, queue có thể backlog. Contract evolution phải quyết định:

- unknown subtype là unsupported permanent failure?
- consumer có thể ignore?
- producer có cần publish version mới?

## 6. Failure scenario & troubleshooting

**Symptom** → deserialization fail sau khi deploy producer mới.

**Evidence** → message chứa discriminator mới; consumer version cũ không có mapping.

**Hypothesis** → contract evolution không backward-compatible.

**Diagnosis** → so schema producer/consumer, kiểm tra discriminator mapping và deployed versions.

**Fix** → explicit contract version, tolerant reader khi business cho phép, hoặc controlled rollout producer sau consumer.

**Verification** → contract test với payload cũ, mới và unknown discriminator.

## 7. Common mistakes

- Serialize CLR type name vào payload.
- Dùng polymorphism cho public contract nhưng không có versioning plan.
- Cho unknown subtype làm crash cả batch.
- Dùng inheritance chỉ để reuse fields dù semantics không thực sự polymorphic.
- Persist JSON lâu dài nhưng không có migration strategy.

## 8. Alternatives

Separate DTOs/endpoints đơn giản hơn nếu subtype behaviors khác hẳn nhau. Composition với `type + data` object có thể explicit hơn inheritance. Event versioning riêng theo message type cũng dễ vận hành hơn trong distributed systems.

## 9. Trade-offs

### Advantages

- Contract gọn cho một abstraction chung.
- Serialize concrete subtype rõ ràng.
- Tránh reflection-based unsafe type metadata.

### Costs / Risks

- Unknown subtype/versioning complexity.
- Client coupling vào discriminator semantics.
- Inheritance hierarchy dễ phát triển thành domain model cứng nhắc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu base type trong C# không tự động tạo wire contract an toàn.

### Middle

Biết configure discriminator và test serialize/deserialize.

### Senior

Thiết kế tolerant evolution, unknown subtype behavior và deployment compatibility.

### Technical Lead / Architect

Quyết định nơi nào nên dùng polymorphic contract, nơi nào nên tách message/endpoint riêng để giảm coupling dài hạn.

## 11. Key takeaway

- Polymorphism ở runtime khác với protocol evolution.
- Discriminator phải là stable contract, không phải CLR implementation detail.
- Luôn test consumer cũ với producer mới trước khi rollout.

# 2. ASP.NET Core Endpoint Filters: đặt validation/cross-cutting logic gần endpoint mà không lạm dụng middleware

## 1. What is it?

Endpoint Filter cho Minimal API cho phép intercept trước/sau endpoint handler, tương tự một pipeline nhỏ scoped ở endpoint/group level.

Mental model:

```text
Middleware
  -> Routing
    -> Endpoint Filter(s)
      -> Handler
```

Filter phù hợp với concern gắn chặt endpoint semantics hơn middleware toàn application.

## 2. Why does it exist?

Middleware rất mạnh nhưng global. Nếu chỉ 5 endpoints cần custom validation, tenant checks hoặc audit metadata, middleware dễ trở thành khối `if (path.StartsWith(...))` khó duy trì.

Filter cho phép composition gần endpoint mà vẫn reuse được.

## 3. How does it work?

Filter nhận `EndpointFilterInvocationContext` và `EndpointFilterDelegate`.

```csharp
public sealed class ValidateOrderFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var request = context.GetArgument<CreateOrderRequest>(0);

        if (request.Items.Count == 0)
            return Results.ValidationProblem(...);

        return await next(context);
    }
}
```

Filter order cũng có semantics như middleware: trước `next` đi xuôi, sau `next` unwind ngược.

## 4. Practical implementation

```csharp
var orders = app.MapGroup("/orders");

orders.MapPost("/", async (
    CreateOrderRequest request,
    OrderService service,
    CancellationToken ct) =>
{
    var id = await service.CreateAsync(request, ct);
    return Results.Created($"/orders/{id}", new { id });
})
.AddEndpointFilter<ValidateOrderFilter>();
```

Nếu validation là standard request DTO validation toàn application, framework/model validation có thể đơn giản hơn custom filter.

## 5. Real production scenario

Một SaaS API có nhóm admin endpoints cần audit reason header. Chỉ admin operations cần requirement này.

Endpoint Filter trên route group phù hợp hơn middleware toàn hệ thống vì scope rõ và test được như endpoint behavior.

## 6. Failure scenario & troubleshooting

**Symptom** → filter không chạy hoặc chạy sai order.

**Evidence** → endpoint mapping không attach filter; route group/filter registration order khác dự kiến.

**Hypothesis** → filter scope/order sai.

**Diagnosis** → inspect endpoint metadata, integration test request path, log filter entry/exit.

**Fix** → attach filter tại group/endpoint đúng boundary; giữ responsibilities nhỏ.

**Verification** → test success/failure endpoint contract, không chỉ unit-test filter class.

## 7. Common mistakes

- Dùng filter thay mọi middleware.
- Đặt authorization-critical logic tùy tiện trong filter thay vì policy authorization.
- Filter truy cập service scoped sai cách hoặc chứa business logic.
- Nhiều filters phụ thuộc implicit ordering.
- Dùng filter để duplicate model validation framework đã có.

## 8. Alternatives

Middleware cho concern global như tracing, exception handling, CORS. MVC filters phù hợp controller stack. Policy authorization phù hợp access control. Application service/domain layer giữ business rules.

## 9. Trade-offs

### Advantages

- Scope gần endpoint.
- Reusable cho route groups.
- Giảm conditional logic trong global pipeline.

### Costs / Risks

- Thêm một extension point cần team hiểu.
- Filter chain dài có thể làm flow khó trace.
- Dễ đưa business logic sai layer.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu filter bao quanh endpoint handler.

### Middle

Biết chọn middleware vs filter vs handler validation.

### Senior

Đánh giá ordering, testability và boundary của cross-cutting logic.

### Technical Lead / Architect

Đặt conventions để tránh hệ thống có 5 pipeline mechanisms cho cùng một concern.

## 11. Key takeaway

- Endpoint Filter phù hợp concern scoped theo endpoint/group.
- Middleware vẫn là lựa chọn cho cross-cutting concern toàn pipeline.
- Authorization/business invariants không nên bị giấu trong filter tùy ý.

# 3. EF Core raw SQL + composability: khi LINQ không đủ, dùng SQL trực tiếp mà vẫn giữ parameterization và query pipeline an toàn

## 1. What is it?

EF Core cho phép dùng raw SQL khi LINQ translation không đủ biểu đạt hoặc SQL cần tối ưu đặc biệt. Raw SQL không có nghĩa từ bỏ toàn bộ EF pipeline: kết quả vẫn có thể materialize, track/no-track và đôi khi compose thêm LINQ phía trên.

## 2. Why does it exist?

Một số query dùng vendor-specific feature, CTE phức tạp, window function đặc biệt hoặc optimized query shape mà LINQ translator chưa support tốt.

Ép mọi thứ thành LINQ đôi khi tạo SQL khó kiểm soát. Nhưng nhảy thẳng sang string concatenation lại tạo SQL injection và maintenance risk.

## 3. How does it work?

`FromSqlInterpolated` parameterize interpolation values:

```csharp
var rows = await db.Orders
    .FromSqlInterpolated($"""
        SELECT *
        FROM Orders
        WHERE TenantId = {tenantId}
    """)
    .AsNoTracking()
    .ToListAsync(ct);
```

Interpolation ở đây không giống build string bình thường; EF tạo parameters.

## 4. Practical implementation

Composable SQL nên trả shape có thể được database coi như subquery hợp lệ:

```csharp
var query = db.Orders
    .FromSqlInterpolated($"""
        SELECT * FROM Orders WHERE TenantId = {tenantId}
    """)
    .Where(x => x.Status == OrderStatus.Pending)
    .OrderBy(x => x.CreatedAt);
```

Không dùng:

```csharp
var sql = $"SELECT * FROM Orders WHERE Name = '{name}'";
```

## 5. Real production scenario

Reporting endpoint cần SQL Server window function + optimized join hint/query structure. Team giữ query trong repository/query object, parameterized, kèm integration test trên real SQL Server.

Họ không rewrite toàn data layer sang Dapper chỉ vì một query đặc biệt.

## 6. Failure scenario & troubleshooting

**Symptom** → query raw SQL chạy trong SSMS nhưng fail khi compose LINQ.

**Evidence** → generated SQL bọc raw SQL thành subquery; raw statement chứa syntax không composable như trailing semicolon/hints ở vị trí không hợp lệ.

**Hypothesis** → SQL shape không composable.

**Diagnosis** → inspect generated SQL bằng `ToQueryString()`, chạy exact command trong database.

**Fix** → làm raw SQL composable hoặc materialize boundary rõ rồi xử lý tiếp.

**Verification** → integration test translation/execution với production provider.

## 7. Common mistakes

- Concatenate user input vào SQL.
- Raw SQL mọi nơi vì “nhanh hơn LINQ”.
- Không test provider-specific behavior.
- Track entity read-only không cần thiết.
- Dùng raw SQL để che schema/query design kém.

## 8. Alternatives

LINQ là default tốt cho maintainability. Dapper phù hợp read-heavy/query-specific paths khi team muốn explicit SQL mapping. Stored procedure phù hợp một số enterprise boundary nhưng tăng deployment/versioning coordination.

## 9. Trade-offs

### Advantages

- Full SQL control khi cần.
- Vẫn reuse EF connection/materialization/transactions.
- Parameterization có thể an toàn nếu dùng API đúng.

### Costs / Risks

- Provider coupling.
- Refactoring entity/schema ít được compiler hỗ trợ.
- Raw SQL phức tạp tăng test burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu raw SQL phải parameterized.

### Middle

Dùng `FromSqlInterpolated`, `AsNoTracking`, `ToQueryString` và integration test.

### Senior

Biết khi nào raw SQL giải quyết translator/query-plan limitation thực sự.

### Technical Lead / Architect

Cho phép escape hatch có kiểm soát thay vì ép một abstraction duy nhất lên mọi query.

## 11. Key takeaway

- Raw SQL là escape hatch, không phải default.
- Parameterization là bắt buộc.
- Hãy inspect execution plan và generated SQL trước khi kết luận LINQ là bottleneck.

# 4. SQL window functions: tính ranking, running total và latest-per-group mà không tự tạo N+1 hoặc correlated subquery đắt đỏ

## 1. What is it?

Window function tính giá trị trên một “window” rows liên quan nhưng không collapse rows như `GROUP BY`.

Ví dụ:

```sql
ROW_NUMBER() OVER (
    PARTITION BY CustomerId
    ORDER BY CreatedAt DESC
)
```

cho phép đánh số row trong từng customer partition.

## 2. Why does it exist?

Nhiều bài toán reporting cần giữ từng row nhưng thêm context aggregate/ranking:

- latest order per customer;
- running balance;
- rank sales;
- moving average.

Nếu giải bằng application loops hoặc correlated subquery lặp lại, cost thường cao hơn nhiều.

## 3. How does it work?

Window được xác định bởi:

- `PARTITION BY`: chia nhóm logic;
- `ORDER BY`: thứ tự trong window;
- frame: phạm vi rows cho aggregate window.

```sql
SUM(Amount) OVER (
    PARTITION BY AccountId
    ORDER BY CreatedAt
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

## 4. Practical implementation

Latest order per customer:

```sql
WITH Ranked AS (
    SELECT
        Id,
        CustomerId,
        CreatedAt,
        Total,
        ROW_NUMBER() OVER (
            PARTITION BY CustomerId
            ORDER BY CreatedAt DESC, Id DESC
        ) AS rn
    FROM Orders
)
SELECT *
FROM Ranked
WHERE rn = 1;
```

Tie-breaker `Id` làm ordering deterministic.

## 5. Real production scenario

CRM dashboard cần mỗi customer kèm order gần nhất. Implementation cũ query customers rồi mỗi customer query thêm một order → N+1 hàng nghìn round trips.

Một window query trả toàn bộ kết quả trong một statement, giúp database optimize set-based execution.

## 6. Failure scenario & troubleshooting

**Symptom** → window query dùng nhiều tempdb/memory hoặc sort chậm.

**Evidence** → execution plan có large Sort, spill, high logical reads.

**Hypothesis** → partition/order không được supporting index hỗ trợ hoặc result set quá lớn.

**Diagnosis** → actual execution plan, memory grant, spill warnings, index order.

**Fix** → narrow rows trước window, thêm supporting index nếu justified, giảm selected columns.

**Verification** → compare logical reads, spill, elapsed time trước/sau.

## 7. Common mistakes

- Không hiểu `GROUP BY` và window khác nhau.
- Không có deterministic tie-breaker.
- Window trên toàn bảng trước khi filter dữ liệu cần thiết.
- Thêm index chỉ để “fix sort” mà không tính write cost.
- Dùng app loop cho set-based problem.

## 8. Alternatives

`GROUP BY` tốt nếu chỉ cần aggregate per group. `APPLY`/subquery có thể phù hợp latest-per-parent khi index tốt và cardinality khác. Materialized reporting table phù hợp workload cực lớn/không real-time.

## 9. Trade-offs

### Advantages

- Expressive set-based SQL.
- Tránh nhiều round trips.
- Tốt cho ranking/running aggregates.

### Costs / Risks

- Sort/memory cost có thể lớn.
- Query khó đọc hơn với team ít SQL experience.
- Index design phải cân bằng read/write.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu window function không collapse rows.

### Middle

Viết `ROW_NUMBER`, `SUM OVER`, deterministic ordering.

### Senior

Đọc sort/spill/memory grant và chọn access pattern phù hợp.

### Technical Lead / Architect

Quyết định logic nên chạy online query, reporting store hay precomputed projection.

## 11. Key takeaway

- Window functions giải quyết nhiều reporting pattern trong một set-based query.
- `PARTITION BY` + `ORDER BY` quyết định semantics và cost.
- Luôn kiểm tra plan, sort và memory spill trên data volume thật.

# 5. Elasticsearch analyzers + `text` vs `keyword`: vì sao index đúng dữ liệu nhưng search vẫn sai relevance

## 1. What is it?

Elasticsearch không search raw string theo cách SQL `LIKE` làm. Với field `text`, content được analyzer biến thành tokens trong inverted index. Với `keyword`, toàn giá trị thường được giữ như một token để exact match/aggregation/sort.

## 2. Why does it exist?

Full-text search cần hiểu words, normalization và language behavior. Một title như:

```text
ASP.NET Core Developer
```

có thể được tokenize thành các terms phục vụ relevance search.

Ngược lại, SKU `ABC-001` thường cần exact matching, không muốn analyzer tách tùy ý.

## 3. How does it work?

Analyzer gồm conceptually:

```text
character filters
 -> tokenizer
 -> token filters
 -> terms stored in inverted index
```

Mapping phổ biến:

```json
{
  "name": {
    "type": "text",
    "fields": {
      "keyword": { "type": "keyword" }
    }
  }
}
```

`name` dùng full-text search, `name.keyword` dùng exact aggregation/sort.

## 4. Practical implementation

Search full text:

```json
{
  "query": {
    "match": {
      "name": "dotnet developer"
    }
  }
}
```

Exact filter:

```json
{
  "query": {
    "term": {
      "status.keyword": "Active"
    }
  }
}
```

`term` query trên analyzed `text` thường là bug nếu developer kỳ vọng analysis xảy ra như `match`.

## 5. Real production scenario

Marketplace search trả kết quả kém khi user gõ SKU hoặc brand. Team dùng tất cả fields là `text`; aggregation brand bị sai và exact SKU match không ổn định.

Sửa mapping thành multi-fields, analyzer riêng cho name/search và keyword cho exact facets giúp relevance lẫn filtering rõ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → document chắc chắn tồn tại nhưng `term` query không match.

**Evidence** → Analyze API cho thấy stored tokens khác raw input.

**Hypothesis** → query type/analyzer/mapping không khớp.

**Diagnosis** → inspect mapping, `_analyze`, query explanation trên sample document.

**Fix** → chọn `match` cho analyzed text, `term` trên keyword/exact fields, reindex nếu mapping thay đổi.

**Verification** → relevance test set gồm exact, partial, typo/language cases theo business need.

## 7. Common mistakes

- Dùng `term` trên `text` field.
- Dùng `keyword` cho paragraph cần relevance.
- Thay analyzer rồi quên reindex.
- Tối ưu query trước khi hiểu tokens được index.
- Một analyzer duy nhất cho tất cả languages/fields.

## 8. Alternatives

SQL full-text search phù hợp hệ thống nhỏ/đơn giản hơn. Database trigram/search extension có thể đủ. Elasticsearch đáng dùng khi relevance, facets, scale và search-specific features justify operational cost.

## 9. Trade-offs

### Advantages

- Full-text relevance mạnh.
- Mapping/analyzer linh hoạt.
- Facets/filtering tốt khi field types đúng.

### Costs / Risks

- Mapping evolution thường cần reindex.
- Eventual consistency với source DB.
- Search correctness cần domain-specific evaluation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `text` được analyzed, `keyword` thường exact.

### Middle

Biết dùng Analyze API và chọn `match`/`term` đúng semantics.

### Senior

Thiết kế analyzer/relevance test và reindex strategy.

### Technical Lead / Architect

Quyết định search requirements có thực sự cần Elasticsearch hay DB search đơn giản hơn đủ dùng.

## 11. Key takeaway

- Mapping quyết định query semantics.
- `text` và `keyword` giải quyết hai nhu cầu khác nhau.
- Debug search bắt đầu từ tokens/mapping, không từ việc “tăng boost” ngẫu nhiên.

# 6. Bounded Context trong DDD: tách business meaning trước khi tách service

## 1. What is it?

Bounded Context là boundary trong đó một domain model và vocabulary có meaning nhất quán. Cùng từ “Customer” có thể có nghĩa khác trong Sales, Billing và Support.

Nó không đồng nghĩa microservice. Một Modular Monolith có thể có nhiều bounded contexts.

## 2. Why does it exist?

Enterprise systems thường cố tạo một canonical model dùng cho mọi team. Kết quả là entity chứa hàng trăm fields, rules xung đột và dependency lan khắp hệ thống.

Bounded Context chấp nhận rằng business concepts có meaning khác nhau ở từng capability.

## 3. How does it work?

Ví dụ:

```text
Sales Context
  Customer = lead, segment, account owner

Billing Context
  Customer = billing account, tax identity, credit status

Support Context
  Customer = contact channels, entitlement, ticket history
```

Contexts trao đổi qua explicit contracts, không share một giant entity.

## 4. Practical implementation

Không:

```csharp
public class Customer
{
    // Sales + Billing + Support + Marketing fields...
}
```

Nên có models riêng:

```csharp
namespace Sales.Domain;
public sealed class CustomerAccount { ... }

namespace Billing.Domain;
public sealed class BillingAccount { ... }
```

Mapping giữa contexts có thể qua application service, event hoặc Anti-Corruption Layer.

## 5. Real production scenario

Một employee platform dùng `Employee` entity cho HR, Timesheet, Payroll và Access Control. Mỗi module thêm field/rule vào cùng entity, migration liên tục ảnh hưởng mọi feature.

Tách context giúp Payroll sở hữu tax/payment semantics, Timesheet chỉ cần worker identity/reference.

## 6. Failure scenario & troubleshooting

**Symptom** → thay đổi rule ở một capability làm unrelated modules fail hoặc cần coordinated release.

**Evidence** → shared entities/tables imported khắp nơi, cyclic dependencies, “common domain model” quá lớn.

**Hypothesis** → model boundary không phản ánh business ownership.

**Diagnosis** → event storming/domain conversations, dependency map, data ownership map.

**Fix** → tách language/model, explicit contracts, migration từng boundary thay vì big-bang rewrite.

**Verification** → architecture tests và ability thay đổi một context với minimal impact context khác.

## 7. Common mistakes

- Mỗi microservice được gọi là bounded context tự động.
- Tách theo technical layer thay vì business capability.
- Share domain entity package giữa contexts.
- Copy data nhưng không xác định source of truth.
- Dùng DDD terminology để biện minh complexity không cần thiết.

## 8. Alternatives

Simple domain model/layered architecture đủ cho business đơn giản. Module boundary nhẹ hơn formal DDD nếu language không phức tạp.

## 9. Trade-offs

### Advantages

- Business meaning rõ.
- Giảm model coupling.
- Ownership và change isolation tốt hơn.

### Costs / Risks

- Duplicate data/concepts có chủ ý.
- Mapping/integration complexity.
- Cần domain understanding, không thể chỉ code-first.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cùng một từ có thể mang meaning khác theo business context.

### Middle

Tôn trọng module/context contracts thay vì reuse entity tiện tay.

### Senior

Phân tích data ownership, invariants và translation boundaries.

### Technical Lead / Architect

Quyết định context boundary trước khi quyết định deployment boundary; không tách service chỉ vì DDD diagram.

## 11. Key takeaway

- Bounded Context là semantic boundary, không phải infrastructure boundary.
- Shared model quá rộng thường tạo coupling lớn hơn reuse value.
- Tách business meaning trước, tách process/service sau nếu cần.

# 7. Azure Application Gateway vs Azure Front Door: chọn ingress layer theo network boundary, routing và failure domain

## 1. What is it?

Azure Front Door là global edge Layer 7 entry point phù hợp global HTTP routing, acceleration, WAF và multi-region origin selection.

Azure Application Gateway là regional Layer 7 load balancer/reverse proxy, thường dùng ingress vào workloads trong VNet, với WAF và routing theo host/path.

## 2. Why does it exist?

Hai service giải quyết ingress ở failure/network scope khác nhau:

```text
Internet users
  -> Front Door (global edge)
  -> region
  -> Application Gateway (regional/VNet ingress)
  -> application
```

Không phải hệ thống nào cũng cần cả hai.

## 3. How does it work?

Front Door nhận traffic tại edge, chọn origin dựa trên health/routing policy.

Application Gateway chạy regional, có thể terminate TLS và route tới backend pools trong network topology nội bộ.

Health probe configuration quyết định backend có được nhận traffic hay không.

## 4. Practical implementation

Một architecture multi-region:

```text
Client
  -> Azure Front Door + WAF
      -> East Asia origin
          -> App Gateway
          -> App Service/AKS
      -> Southeast Asia origin
          -> App Gateway
          -> App Service/AKS
```

Nếu chỉ một App Service public regional app, Front Door trực tiếp tới App Service có thể đơn giản hơn.

## 5. Real production scenario

E-commerce toàn cầu cần failover region và edge WAF. Front Door phù hợp global routing. Trong mỗi region, AKS private ingress cần Application Gateway để vào VNet backend.

Ngược lại, internal enterprise app chỉ chạy một region/private network không cần global Front Door.

## 6. Failure scenario & troubleshooting

**Symptom** → 502/503 dù backend app healthy khi truy cập trực tiếp.

**Evidence** → origin/backend marked unhealthy; probe host/path/certificate mismatch.

**Hypothesis** → health probe/routing/TLS configuration sai.

**Diagnosis** → inspect Front Door origin health, App Gateway backend health, DNS, TLS chain và app logs.

**Fix** → sửa probe endpoint/host header/certificate/network rule.

**Verification** → fail one backend intentionally và xác nhận traffic chuyển đúng.

## 7. Common mistakes

- Dùng cả Front Door + App Gateway vì “best practice” mà không có requirement.
- Health probe gọi endpoint phụ thuộc mọi downstream, khiến transient dependency failure rút toàn backend khỏi rotation.
- Quên real client IP forwarding/trusted proxy config.
- Public origin không restrict chỉ nhận traffic mong muốn.
- WAF rule không test với legitimate traffic.

## 8. Alternatives

Azure Load Balancer là Layer 4. Nginx/Ingress Controller phù hợp app-level/container ingress. App Service built-in routing có thể đủ cho kiến trúc đơn giản.

## 9. Trade-offs

### Advantages

- Front Door: global failover/edge/WAF.
- App Gateway: regional VNet-aware L7 ingress.

### Costs / Risks

- Thêm hop, cost và configuration surface.
- Debugging TLS/probe/routing phức tạp hơn.
- Hai ingress layers chỉ nên tồn tại khi có distinct responsibilities.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu global edge khác regional ingress.

### Middle

Biết host/path routing, TLS, health probe.

### Senior

Debug 502/503 xuyên DNS-edge-gateway-backend chain và thiết kế failure isolation.

### Technical Lead / Architect

Chọn tối thiểu ingress components cần thiết theo geography, VNet, security và HA requirements.

## 11. Key takeaway

- Front Door và Application Gateway không phải hai phiên bản của cùng một service.
- Health probe là routing control plane, phải thiết kế rất cẩn thận.
- Đừng thêm hai layers nếu một layer đã đáp ứng requirement.

# 8. Linux `systemd`, process lifetime và file permissions: debug .NET service chạy local được nhưng fail trên Production

## 1. What is it?

`systemd` quản lý service lifecycle trên nhiều Linux distributions: start, stop, restart, environment, working directory, user identity và logs qua journal.

Một .NET app chạy được bằng `dotnet MyApp.dll` dưới user của developer chưa chắc chạy được dưới service account trong `systemd`.

## 2. Why does it exist?

Production process cần:

- tự start sau reboot;
- restart policy;
- least-privilege user;
- controlled environment variables;
- centralized lifecycle/logging.

`systemd` cung cấp process supervisor thay vì để app chạy trong terminal/session.

## 3. How does it work?

Unit file ví dụ:

```ini
[Unit]
Description=My .NET API
After=network.target

[Service]
WorkingDirectory=/opt/myapi
ExecStart=/usr/bin/dotnet /opt/myapi/MyApi.dll
Restart=always
User=myapi
Environment=ASPNETCORE_ENVIRONMENT=Production

[Install]
WantedBy=multi-user.target
```

Service chạy với permissions của `User=myapi`.

## 4. Practical implementation

Commands cơ bản:

```bash
sudo systemctl daemon-reload
sudo systemctl enable myapi
sudo systemctl start myapi
sudo systemctl status myapi
journalctl -u myapi -n 200 --no-pager
```

Check file permissions:

```bash
namei -l /opt/myapi/appsettings.Production.json
ls -la /opt/myapi
```

## 5. Real production scenario

App chạy tốt khi SSH rồi execute bằng admin user. Khi service start qua `systemd`, app fail đọc certificate/file upload directory.

Root cause: service account `myapi` không có permission trên directory, không phải .NET config bug.

## 6. Failure scenario & troubleshooting

**Symptom** → `systemctl status` báo restart loop hoặc exit code; browser nhận connection refused.

**Evidence** → journal log có `UnauthorizedAccessException`, missing environment variable hoặc port binding failure.

**Hypothesis** → identity/environment/working-directory khác interactive shell.

**Diagnosis** → compare `systemd` environment, effective user, file ownership, listening ports:

```bash
ss -ltnp
ps aux | grep dotnet
```

**Fix** → permissions tối thiểu cần thiết, explicit working directory/environment, correct port/reverse proxy config.

**Verification** → restart service và reboot host; xác nhận service tự lên và log sạch.

## 7. Common mistakes

- `chmod 777` để “fix nhanh”.
- Chạy service bằng root.
- Secret hardcode trong unit file world-readable.
- Dựa vào shell profile environment mà service không load.
- Chỉ test manual process, không test service lifecycle.

## 8. Alternatives

Docker/Container Apps/Kubernetes quản lý process theo container model. Windows Service/IIS phù hợp Windows hosting. App Service loại bỏ phần lớn OS-level lifecycle management.

## 9. Trade-offs

### Advantages

- Native, lightweight process supervision.
- Least-privilege identity rõ.
- Restart/log lifecycle tích hợp OS.

### Costs / Risks

- Team cần Linux operations knowledge.
- Permissions/environment differences dễ tạo “works on my machine”.
- Host patching/configuration vẫn do team vận hành.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process chạy dưới một OS user cụ thể.

### Middle

Biết đọc `systemctl`, `journalctl`, permissions và port state.

### Senior

Debug identity/environment/reverse-proxy/startup failure có hệ thống.

### Technical Lead / Architect

Quyết định khi nào tự host VM hợp lý so với managed platform/container để giảm operational burden.

## 11. Key takeaway

- Service identity khác developer shell identity.
- Debug Linux service phải kiểm tra process, environment, permissions, ports và logs.
- Đừng dùng root/777 để né ownership problem.

# 9. Technical SEO với canonical, redirect và status code: tránh duplicate content bằng HTTP semantics đúng

## 1. What is it?

Technical SEO ở góc nhìn engineering chủ yếu là đảm bảo URL/resource semantics rõ cho crawler và browser.

Ba cơ chế dễ nhầm:

- `301/308 redirect`: resource đã chuyển sang URL khác;
- canonical tag: nhiều URL tồn tại nhưng chỉ định preferred canonical URL;
- `404/410`: resource không còn tồn tại.

## 2. Why does it exist?

E-commerce/CMS thường sinh nhiều URL cho cùng nội dung:

```text
/product/123
/product/123?utm_source=x
/category/a/product/123
```

Nếu hệ thống không define canonical/redirect semantics, crawler có thể index duplicate pages và phân tán signals.

## 3. How does it work?

Canonical:

```html
<link rel="canonical" href="https://example.com/product/123" />
```

Permanent redirect:

```http
HTTP/1.1 301 Moved Permanently
Location: /new-url
```

Status code phải phản ánh truth. Trang “not found” render đẹp nhưng trả `200` là soft-404 behavior.

## 4. Practical implementation

ASP.NET Core redirect:

```csharp
return Results.Redirect(
    "/products/new-slug",
    permanent: true,
    preserveMethod: true);
```

CMS rendering nên generate canonical từ content routing rule, không lấy nguyên mọi query string tracking params.

## 5. Real production scenario

CMS migration đổi toàn bộ slug sản phẩm. Team chỉ render canonical mới nhưng URL cũ vẫn trả 200 content cũ trong nhiều tháng.

Crawler tiếp tục thấy hai live pages. Permanent redirect từ old slug sang new slug thường diễn đạt migration rõ hơn canonical đơn thuần.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate pages/indexing bất thường hoặc crawler báo soft 404/redirect chain.

**Evidence** → HTTP trace, sitemap, canonical mismatch, chains như A→B→C.

**Hypothesis** → URL lifecycle semantics không nhất quán.

**Diagnosis** → crawl representative routes, inspect status/location/canonical/robots.

**Fix** → one-hop permanent redirect, self-consistent canonical, proper 404/410.

**Verification** → automated integration tests cho URL migration rules và crawler-oriented smoke checks.

## 7. Common mistakes

- Mọi page lỗi đều trả `200`.
- Redirect chain nhiều hop.
- Canonical trỏ sang URL không tương đương content.
- Canonical gồm tracking query params.
- Dùng `302` mãi cho permanent migration không chủ đích.

## 8. Alternatives

Không cần canonical nếu URL architecture đã có một unique URL duy nhất. Robots/noindex giải quyết indexing policy khác và không thay redirect/canonical semantics.

## 9. Trade-offs

### Advantages

- URL lifecycle rõ.
- Crawler behavior predictable hơn.
- Giảm duplicate indexing.

### Costs / Risks

- Routing migration cần mapping/history.
- Redirect rules lớn có thể ảnh hưởng latency/maintenance.
- Sai canonical có thể hide đúng content khỏi index.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code là semantic signal, không chỉ implementation detail.

### Middle

Implement redirect/canonical/404 đúng và test HTTP response.

### Senior

Thiết kế migration URL, redirect chain và CMS routing consistency.

### Technical Lead / Architect

Đưa URL stability vào platform contract thay vì xử lý SEO như việc “thêm meta tag” cuối dự án.

## 11. Key takeaway

- Redirect, canonical và 404 giải quyết các vấn đề khác nhau.
- Technical SEO phụ thuộc HTTP correctness.
- URL migration cần được test như một production contract.

# 10. AI evaluation cho Tool Calling: đo correctness của agent bằng deterministic test harness thay vì đọc vài câu trả lời thủ công

## 1. What is it?

AI evaluation là hệ thống test đo behavior của model/agent trên tập cases xác định. Với Tool Calling, evaluation không chỉ hỏi “câu trả lời nghe hay không” mà kiểm tra:

- tool nào được chọn;
- arguments có đúng schema không;
- có gọi tool khi không được phép không;
- có bỏ sót call bắt buộc không;
- final answer có grounded vào tool result không.

## 2. Why does it exist?

LLM output probabilistic. Manual spot-check vài prompt không đủ chứng minh reliability khi thay model, prompt, tools hoặc context.

Tool Calling đặc biệt nguy hiểm vì sai output có thể tạo side effect thật.

## 3. How does it work?

Test harness nên tách deterministic assertions khỏi subjective scoring:

```text
Input case
 -> model/agent
 -> proposed tool call
 -> deterministic validator
 -> mocked tool result
 -> final response
 -> assertions/metrics
```

Một case có thể assert exact tool name và argument constraints mà không yêu cầu exact natural-language response.

## 4. Practical implementation

C# test model:

```csharp
public sealed record AgentEvalCase(
    string Name,
    string UserInput,
    string? ExpectedTool,
    Func<JsonElement, bool>? ValidateArguments);
```

Ví dụ test:

```csharp
Assert.Equal("GetOrder", result.ToolCall?.Name);
Assert.True(result.ToolCall!.Arguments.GetProperty("orderId").GetString() == "A123");
```

High-impact tools nên test negative cases:

```text
user không có quyền
-> model có thể đề xuất action
-> application authorization bắt buộc reject
```

## 5. Real production scenario

Support agent có tools `GetCustomer`, `RefundOrder`, `SendEmail`.

Prompt update giúp answers tự nhiên hơn nhưng agent bắt đầu gọi `RefundOrder` trong cases chỉ hỏi trạng thái refund.

Nếu không có eval suite, regression chỉ được phát hiện sau incident. Tool-choice eval bắt regression trước deploy.

## 6. Failure scenario & troubleshooting

**Symptom** → production tool-call rate hoặc error rate thay đổi sau model/prompt release.

**Evidence** → eval pass rate giảm ở tool selection/argument validation; traces cho thấy unnecessary calls.

**Hypothesis** → prompt/model/context change tạo regression.

**Diagnosis** → replay frozen eval dataset trên old/new version, diff tool decisions.

**Fix** → sửa tool descriptions/prompt/schema hoặc deterministic routing/policy; không chỉ “thêm prompt mạnh hơn” nếu logic có thể deterministic.

**Verification** → regression suite + canary traffic + production telemetry.

## 7. Common mistakes

- Chỉ đánh giá final prose.
- Dùng model làm judge duy nhất cho authorization/correctness.
- Eval dataset toàn happy path.
- Không version prompt/model/tool schema cùng results.
- Không có negative/adversarial cases.

## 8. Alternatives

Deterministic workflow/rules engine tốt hơn khi decision space cố định. LLM classification chỉ nên dùng nơi ambiguity thực sự cần probabilistic reasoning.

## 9. Trade-offs

### Advantages

- Phát hiện regression trước production.
- Cho phép so model/prompt versions có evidence.
- Tool correctness có thể kiểm bằng deterministic assertions.

### Costs / Risks

- Eval dataset cần maintenance.
- Dataset dễ overfit nếu quá nhỏ.
- Subjective quality vẫn cần human review ở một số dimensions.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LLM feature cũng cần test như software behavior.

### Middle

Viết eval cases cho tool name, schema và grounded response.

### Senior

Thiết kế adversarial/negative cases, versioning và production feedback loop.

### Technical Lead / Architect

Xác định phần nào được model quyết định, phần nào phải deterministic, và release gate nào bắt buộc trước khi model/prompt thay đổi.

## 11. Key takeaway

- Tool Calling cần eval ở action level, không chỉ text quality.
- Security/correctness assertions phải deterministic.
- Mọi model/prompt/tool-schema change nên được xem như software release có regression testing.
