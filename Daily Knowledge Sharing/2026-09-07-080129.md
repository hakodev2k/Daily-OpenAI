# 1. .NET Garbage Collector: generations, LOH và allocation pressure

## 1. What is it?

Garbage Collector (GC) của .NET quản lý managed heap bằng cách tìm object còn reachable và thu hồi memory của object không còn được tham chiếu. .NET dùng generational GC: object mới thường bắt đầu ở Gen 0, object sống lâu được promote lên Gen 1 rồi Gen 2. Large Object Heap (LOH) chứa các allocation lớn và thường có chi phí collection/fragmentation đáng chú ý hơn.

## 2. Why does it exist?

GC giúp developer không phải quản lý `free`/ownership thủ công cho mọi object. Đổi lại, allocation rate và object lifetime trở thành một phần của performance model; managed code vẫn có thể gặp memory pressure hoặc “leak” khi object còn reachable ngoài ý muốn.

## 3. How does it work?

```text
Allocation -> Gen 0 -> Gen 1 -> Gen 2
                    surviving objects

Large allocation -> LOH
```

GC bắt đầu từ roots như stack references, static fields và GC handles. Object graph còn reachable sẽ được giữ lại; object unreachable được thu hồi.

## 4. Practical implementation

Với hot path xử lý buffer, pooling có thể giảm allocation nếu profiling chứng minh cần thiết:

```csharp
byte[] buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);
}
```

Không dùng pooling theo thói quen vì nó tăng complexity và có thể giữ memory lâu hơn.

## 5. Real production scenario

API export report tạo nhiều `byte[]` vài MB cho mỗi request. Khi concurrency tăng, LOH tăng, Gen 2 collections xuất hiện thường xuyên hơn và p99 latency tăng dù business logic không đổi.

## 6. Failure scenario & troubleshooting

**Symptom → Evidence → Hypothesis → Diagnosis → Fix → Verification**  
Memory/p99 tăng → allocation rate/LOH/Gen 2 tăng → large temporary objects → profile allocations và retention paths → streaming/reuse/reduce object lifetime → load test lại và so sánh GC metrics.

## 7. Common mistakes

* Gọi `GC.Collect()` như một giải pháp mặc định.
* Giữ static/cache collection không giới hạn.
* Convert stream thành large `byte[]` khi có thể stream.
* Tối ưu allocation trước khi đo.

## 8. Alternatives

Streaming, `Span<T>`, `Memory<T>`, `ArrayPool<T>` hoặc thay đổi serialization/access pattern có thể giảm allocation. Chỉ chọn sau khi profiling xác định bottleneck.

## 9. Trade-offs

### Advantages

GC tăng memory safety và productivity; generational model tối ưu tốt cho short-lived objects.

### Costs / Risks

Allocation-heavy workload có thể tạo CPU cost, pause và tail-latency spikes; pooling lại tăng ownership complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu object managed không cần free thủ công nhưng vẫn tiêu thụ memory.

### Middle

Phân biệt short-lived, long-lived và large allocations.

### Senior

### Technical Lead / Architect

## 11. Key takeaway

* Managed memory không làm memory cost biến mất.
* Allocation rate quan trọng hơn chỉ nhìn RAM snapshot.
* Tối ưu GC phải dựa trên profiling evidence.

# 2. ASP.NET Core middleware ordering và request pipeline boundaries

## 1. What is it?

Middleware là các component nối tiếp trong ASP.NET Core request pipeline. Mỗi middleware có thể xử lý request trước `next`, xử lý response sau `next`, hoặc short-circuit pipeline. Thứ tự đăng ký quyết định behavior thực tế.

## 2. Why does it exist?

Exception handling, routing, authentication, authorization, logging, compression và rate limiting là cross-cutting concerns cần bao quanh endpoint execution. Nếu order sai, từng component có thể đúng riêng lẻ nhưng toàn pipeline vẫn sai.

## 3. How does it work?

```text
Request
 -> Exception Handler
 -> Routing
 -> Authentication
 -> Authorization
 -> Endpoint
 <- Response
```

Middleware đầu tiên là outer boundary và response đi ngược trở ra.

## 4. Practical implementation

```csharp
app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
```

Custom middleware phụ thuộc authenticated identity phải chạy sau authentication.

## 5. Real production scenario

Multi-tenant API resolve tenant từ claims. Tenant middleware chạy trước authentication nên Production không thấy claims tại thời điểm resolve, tạo tenant mismatch dù endpoint authorization vẫn đúng.

## 6. Failure scenario & troubleshooting

**Symptom**: 401/403 hoặc route/tenant behavior bất thường.  
**Evidence**: structured logs cho thấy state chưa tồn tại ở middleware tương ứng.  
**Fix**: vẽ pipeline, xác định dependency order, kiểm tra bằng integration test với real authentication scheme.

## 7. Common mistakes

* Authorization trước authentication.
* Custom middleware dùng route values trước routing.
* Exception handler đặt quá muộn.
* Dùng middleware cho business logic chỉ thuộc một use case.

## 8. Alternatives

MVC Filters hoặc Endpoint Filters phù hợp concern gần endpoint hơn; `DelegatingHandler` phù hợp outbound HTTP; domain concern phải nằm trong application/domain layer.

## 9. Trade-offs

### Advantages

Centralize cross-cutting behavior và tạo outer reliability/security boundary.

### Costs / Risks

Order dependency dễ bị ẩn; quá nhiều global middleware khiến behavior khó reasoning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request đi qua middleware theo thứ tự đăng ký.

### Middle

Đặt routing/authentication/authorization đúng boundary.

### Senior

Debug short-circuit và ordering bằng logs/traces/integration tests.

### Technical Lead / Architect

Quyết định concern nào thật sự global và concern nào phải ở application/domain boundary.

## 11. Key takeaway

* Middleware order là correctness, không phải style.
* State chỉ tồn tại sau boundary tạo ra state đó.
* Không biến middleware thành nơi chứa business logic.

# 3. EF Core transaction boundary: `SaveChanges`, explicit transaction và partial failure

## 1. What is it?

Một `SaveChanges`/`SaveChangesAsync` của EF Core thường được thực thi trong transaction do provider quản lý. Nhưng business operation có thể gồm nhiều DB operations hoặc external side effects; transaction boundary phải được định nghĩa theo invariant, không theo số method.

## 2. Why does it exist?

Approve timesheet có thể cần update status và insert audit atomically. Boundary quá nhỏ tạo partial state; boundary quá lớn giữ locks lâu, tăng blocking/deadlock risk.

## 3. How does it work?

```text
Business operation
  -> DB changes
  -> SaveChanges
      -> transaction
      -> commit / rollback
```

External HTTP call không tự động nằm trong database transaction.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);
try
{
    timesheet.Approve(userId);
    db.AuditEntries.Add(AuditEntry.ForApproval(timesheet.Id, userId));
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
catch
{
    await tx.RollbackAsync(ct);
    throw;
}
```

Nếu chỉ cần một `SaveChangesAsync`, explicit transaction thường không đem thêm giá trị.

## 5. Real production scenario

Order service gửi notification trước khi DB commit. Notification thành công nhưng commit thất bại; user nhận thông báo cho state chưa tồn tại. Đây là transaction-boundary mismatch giữa DB và external side effect.

## 6. Failure scenario & troubleshooting

Map toàn bộ transaction flow, tìm nơi side effect xảy ra trước durable commit. Với DB + messaging, cân nhắc Outbox Pattern để event chỉ xuất hiện sau state change hợp lệ.

## 7. Common mistakes

* Explicit transaction cho mọi `SaveChanges`.
* Giữ DB transaction mở trong remote call.
* Retry operation không idempotent.
* Generic Unit of Work che transaction boundary thực tế.

## 8. Alternatives

Một `SaveChanges` cho operation đơn giản; explicit transaction cho nhiều DB writes cần atomicity; Outbox/Saga khi consistency vượt qua một database.

## 9. Trade-offs

### Advantages

Atomicity và invariant ownership rõ ràng.

### Costs / Risks

Transaction dài tăng contention; DB transaction không giải quyết distributed consistency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu commit/rollback.

### Middle

Biết khi nào một `SaveChanges` đủ.

### Senior

Phân tích partial failure, isolation và side-effect boundary.

### Technical Lead / Architect

Chọn transaction boundary theo business invariant và distributed consistency requirement.

## 11. Key takeaway

* Transaction boundary nên theo invariant.
* Tránh remote call bên trong DB transaction nếu không có lý do mạnh.
* Outbox/Saga giải quyết bài toán khác database transaction.

# 4. SQL window functions: ranking, running total và top-N per group

## 1. What is it?

Window functions tính toán trên một tập rows liên quan nhưng không collapse rows như `GROUP BY`. Các hàm thường gặp gồm `ROW_NUMBER`, `RANK`, `DENSE_RANK`, `SUM(...) OVER`, `LAG`, `LEAD`.

## 2. Why does it exist?

Reporting thường cần giữ detail rows trong khi vẫn ranking, running total hoặc so sánh với row trước. Đưa toàn bộ data về C# để tính vừa tăng round trip vừa bỏ lợi thế set-based execution của database.

## 3. How does it work?

```sql
SELECT
    EmployeeId,
    WorkDate,
    Hours,
    SUM(Hours) OVER (
        PARTITION BY EmployeeId
        ORDER BY WorkDate
    ) AS RunningHours
FROM Timesheets;
```

`PARTITION BY` chia logical windows; `ORDER BY` xác định thứ tự trong mỗi window.

## 4. Practical implementation

Top 3 orders mới nhất mỗi customer:

```sql
WITH Ranked AS
(
    SELECT *,
           ROW_NUMBER() OVER (
               PARTITION BY CustomerId
               ORDER BY CreatedAt DESC, Id DESC) AS rn
    FROM Orders
)
SELECT Id, CustomerId, CreatedAt, Total
FROM Ranked
WHERE rn <= 3;
```

## 5. Real production scenario

CRM cần 3 activities gần nhất của mỗi account. Window function tránh pattern query accounts rồi query riêng từng account.

## 6. Failure scenario & troubleshooting

Query chậm có thể do large sort hoặc tempdb spill. Đọc execution plan, memory grant, logical reads và xem index có hỗ trợ partition/order pattern hay không.

## 7. Common mistakes

* Không có deterministic tie-breaker.
* `PARTITION BY` sai business boundary.
* Tính ranking trong application dù database đã có dữ liệu.
* Thêm index mà không đọc execution plan.

## 8. Alternatives

Correlated subquery/aggregate join vẫn hợp lý cho query nhỏ; application-side calculation chỉ nên dùng khi dataset nhỏ và đã cần materialize vì lý do khác.

## 9. Trade-offs

### Advantages

Expressive, set-based, giảm N+1/report logic phía application.

### Costs / Risks

Sort/memory grant có thể đắt và query khó đọc hơn với team chưa quen SQL.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt `GROUP BY` và window function.

### Middle

Dùng `ROW_NUMBER`, `LAG`, running total đúng semantics.

### Senior

Đọc execution plan, sort spill và index support.

### Technical Lead / Architect

Quyết định computation thuộc database, read model hay application dựa trên volume và ownership.

## 11. Key takeaway

* Window functions rất mạnh cho analytical/read-model queries.
* Ordering phải deterministic.
* Performance phải được xác nhận bằng plan và I/O.

# 5. Redis eviction, hot keys và memory pressure

## 1. What is it?

Redis sử dụng memory làm storage chính cho cache workload. Khi chạm `maxmemory`, eviction policy quyết định key nào có thể bị loại. Hot key là key nhận traffic cao bất thường so với phần còn lại và có thể tạo bottleneck dù hit rate rất cao.

## 2. Why does it exist?

Cache memory là hữu hạn. Không có capacity/eviction strategy, Redis có thể từ chối writes hoặc trở thành hidden critical dependency thay vì giảm tải hệ thống.

## 3. How does it work?

```text
Application -> Redis
                |- key lookup
                |- TTL
                |- memory accounting
                |- eviction at capacity
```

Traffic distribution quan trọng không kém data size distribution.

## 4. Practical implementation

```csharp
await cache.SetStringAsync(
    $"product:{productId}:summary:v1",
    json,
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
    },
    ct);
```

Key space, payload size và TTL phải có giới hạn.

## 5. Real production scenario

Homepage dùng một value cache rất lớn và mọi request đọc cùng key. CPU/network của Redis tăng mạnh dù cache hit rate gần 100%.

## 6. Failure scenario & troubleshooting

Đo command latency, memory, eviction count, payload size và access distribution. Nếu một key chiếm phần lớn traffic, cân nhắc local L1 cache, chia payload hoặc redesign access pattern.

## 7. Common mistakes

* Không cấu hình memory policy rõ.
* Cache value quá lớn.
* Dùng Redis như source of truth.
* Chỉ nhìn hit rate mà bỏ qua latency/CPU/network.

## 8. Alternatives

`IMemoryCache` cho local hot data, CDN cho public HTTP content, hoặc tối ưu DB query khi cache complexity không đáng.

## 9. Trade-offs

### Advantages

Low latency và giảm load downstream.

### Costs / Risks

Memory đắt, eviction tạo unpredictability, hot keys có thể biến cache thành bottleneck mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache không phải storage vô hạn.

### Middle

Thiết kế TTL/key và cache-miss behavior.

### Senior

Theo dõi eviction, hot key, memory pressure và degraded mode.

### Technical Lead / Architect

Quyết định dữ liệu nào nên cache và hệ thống hoạt động ra sao khi Redis unavailable.

## 11. Key takeaway

* Hit rate cao không đồng nghĩa cache khỏe.
* Capacity và traffic skew phải được quan sát.
* Redis phải giảm dependency cost, không trở thành dependency bí mật mới.

# 6. DDD Aggregate: boundary của invariant, transaction và consistency

## 1. What is it?

Aggregate là consistency boundary trong Domain-Driven Design. Aggregate Root là entry point bảo vệ invariant của cluster domain objects. Aggregate không đơn giản là “entity có nhiều children”.

## 2. Why does it exist?

Nếu mọi entity được mutate độc lập, invariant xuyên nhiều objects dễ bị phá. Aggregate xác định state nào phải thay đổi atomically trong cùng transaction.

## 3. How does it work?

```text
PurchaseOrder (Aggregate Root)
  |- OrderLine
  |- OrderLine
  |- ApprovalState
```

External code thao tác qua root thay vì bypass invariant bằng public setters.

## 4. Practical implementation

```csharp
public void AddLine(ProductId productId, int quantity, decimal unitPrice)
{
    if (quantity <= 0)
        throw new DomainException("Quantity must be positive.");

    _lines.Add(new OrderLine(productId, quantity, unitPrice));

    if (Total > ApprovalThreshold)
        Status = OrderStatus.RequiresApproval;
}
```

## 5. Real production scenario

Leave-management system cần bảo vệ entitlement khi approve leave. Việc xác định entitlement và request có cùng aggregate/bounded context hay không quyết định strong consistency có thực tế hay phải dùng workflow/reservation khác.

## 6. Failure scenario & troubleshooting

Aggregate quá lớn thường biểu hiện bằng query graph lớn, transaction dài và optimistic-concurrency conflict cao. Xác định invariant nào thực sự cần atomic consistency rồi thu nhỏ boundary.

## 7. Common mistakes

* Một Aggregate cho cả bounded context.
* Navigation graph quyết định aggregate boundary.
* Repository cho từng child entity.
* Public setters bypass invariant.

## 8. Alternatives

CRUD/application-service model thường đủ khi business logic đơn giản. DDD chỉ đáng chi phí khi domain complexity thực sự tồn tại.

## 9. Trade-offs

### Advantages

Invariant ownership và transaction boundary rõ.

### Costs / Risks

Aggregate quá lớn gây contention; quá nhỏ đẩy nhiều consistency sang eventual workflows.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt Entity, Aggregate và Aggregate Root.

### Middle

Đưa invariant vào behavior của root.

### Senior

Thiết kế boundary theo consistency và contention.

### Technical Lead / Architect

Quyết định invariant nào cần strong consistency, invariant nào chấp nhận eventual consistency và bounded context nào sở hữu state.

## 11. Key takeaway

* Aggregate là consistency boundary trước khi là object graph.
* Boundary nên nhỏ nhất có thể nhưng đủ bảo vệ invariant.
* Không ép DDD vào CRUD đơn giản.

# 7. Azure Functions vs Worker Service cho background processing

## 1. What is it?

Azure Functions là serverless execution model dựa trên triggers và platform-managed scaling. Worker Service là long-running .NET process cho phép team kiểm soát lifecycle, hosting và connection behavior rõ hơn.

## 2. Why does it exist?

Queue consumers, scheduled work, file processing và event handlers không nên mặc định chạy trong HTTP request. Chúng cần failure/retry/scale boundary riêng.

## 3. How does it work?

```text
Azure Function: Trigger -> Function instance -> handler
Worker Service: Host -> BackgroundService -> consumer loop
```

Functions và Worker đều có thể scale nhiều instances, vì vậy duplicate execution/idempotency vẫn phải được suy nghĩ.

## 4. Practical implementation

```csharp
public sealed class QueueWorker(IQueueConsumer consumer) : BackgroundService
{
    protected override Task ExecuteAsync(CancellationToken stoppingToken)
        => consumer.ConsumeAsync(stoppingToken);
}
```

Worker loop cần cancellation, backoff và bounded concurrency.

## 5. Real production scenario

Thumbnail processing có burst traffic lớn và event-driven trigger phù hợp Functions. Một processor chạy liên tục, giữ warm connections và cần throughput predictable có thể hợp Worker Service/Container Apps hơn.

## 6. Failure scenario & troubleshooting

Nếu message được xử lý lại sau timeout/restart, code giả định exactly-once sẽ tạo duplicate side effects. Test bằng fault injection tại boundary giữa processing và acknowledgement.

## 7. Common mistakes

* Chọn Functions chỉ vì “serverless”.
* Không thiết kế idempotency.
* Worker busy-loop polling.
* Scheduled job chạy trên nhiều replicas mà không nhận ra duplicate execution.

## 8. Alternatives

Azure Container Apps Jobs, Logic Apps, App Service Worker hoặc AKS tùy workload và platform ownership.

## 9. Trade-offs

### Advantages

Functions có trigger integration/elastic scale; Worker có runtime control và predictable process model.

### Costs / Risks

Functions có platform/cold-start/cost characteristics; Worker cần capacity planning và scaling rõ hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu background work khác request work.

### Middle

Implement cancellation, retries và idempotency.

### Senior

Đánh giá delivery semantics, scale, poison messages và graceful shutdown.

### Technical Lead / Architect

Chọn execution model theo workload shape, latency, cost và operational ownership.

## 11. Key takeaway

* Background job không đồng nghĩa Functions.
* Idempotency quan trọng hơn hosting brand.
* Chọn platform dựa trên workload shape.

# 8. IIS Application Pool recycling, warm-up và production lifecycle

## 1. What is it?

IIS Application Pool là process/isolation boundary cho web applications trên Windows. Worker/application process có thể recycle do configuration, deployment hoặc health behavior. Restart/recycle là normal production event, không phải trường hợp “không bao giờ xảy ra”.

## 2. Why does it exist?

IIS cung cấp isolation, identity, resource/process management và recovery cho enterprise workloads. Nhưng lifecycle này có nghĩa in-memory state và long-running work không được giả định là durable.

## 3. How does it work?

```text
Client -> IIS -> Application Pool -> Worker/Application Process
```

Khi process mới start, configuration, dependency initialization và cache warm-up có thể tạo cold-start latency.

## 4. Practical implementation

Background code phải hỗ trợ graceful cancellation:

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
        await ProcessNextAsync(stoppingToken);
}
```

Critical state không nên chỉ tồn tại trong process memory.

## 5. Real production scenario

Legacy application giữ workflow state trong memory. Sau nightly recycle, users mất state và issue chỉ xuất hiện quanh thời điểm recycle.

## 6. Failure scenario & troubleshooting

Correlate IIS/Event Viewer/process-start logs với latency/5xx. Nếu first requests chậm, kiểm tra startup work, warm-up, connection initialization và health behavior.

## 7. Common mistakes

* In-memory state được coi là durable.
* Scheduled jobs chạy trong web process không nghĩ tới recycle/multi-instance.
* Bỏ qua IIS/Event Viewer logs.
* Startup thực hiện remote work dài không có timeout.

## 8. Alternatives

Azure App Service, containers hoặc Kubernetes thay đổi hosting model nhưng không loại bỏ process restart/lifecycle concerns.

## 9. Trade-offs

### Advantages

Mature Windows hosting, process isolation và enterprise compatibility.

### Costs / Risks

Developer phải hiểu process lifecycle, warm-up và state externalization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu application process có thể restart.

### Middle

Đọc App Pool settings, IIS logs và startup errors.

### Senior

Thiết kế stateless app, warm-up và graceful shutdown.

### Technical Lead / Architect

Quyết định workload nào tiếp tục IIS và workload nào đáng modernize.

## 11. Key takeaway

* Restart là normal operational event.
* Web process không phải durable store.
* Hosting lifecycle phải nằm trong architecture reasoning.

# 9. React/Vue rendering: state, reactivity và tránh unnecessary work

## 1. What is it?

React và Vue đều biến application state thành UI nhưng dùng mental model khác nhau. React re-renders component tree dựa trên state/props changes; Vue dùng reactive dependency tracking để biết phần nào phụ thuộc vào state nào. Với full-stack engineer, điều quan trọng là hiểu khi nào frontend tạo thêm network/rendering work ngoài dự kiến.

## 2. Why does it exist?

UI hiện đại có state thay đổi liên tục. Framework cung cấp declarative model để developer mô tả UI theo state thay vì manually đồng bộ DOM.

## 3. How does it work?

```text
User event -> state change -> framework schedules update -> render/patch DOM
```

Một state change không nên tự động đồng nghĩa với fetch lại toàn bộ dữ liệu hoặc render lại expensive subtree.

## 4. Practical implementation

Vue computed state:

```ts
const filteredOrders = computed(() =>
  orders.value.filter(x => x.status === selectedStatus.value)
)
```

React memoization chỉ nên dùng khi profiling cho thấy expensive recomputation hoặc unstable references thực sự gây work đáng kể.

## 5. Real production scenario

Search box gọi API ở mỗi keystroke mà không debounce/cancel previous request. Slow response cũ về sau response mới và ghi đè UI bằng stale result.

## 6. Failure scenario & troubleshooting

Dùng Browser DevTools: Network waterfall, React/Vue DevTools và Performance panel. Nếu API bị gọi lặp hoặc component render quá nhiều, xác định state dependency và lifecycle/effect gây trigger.

## 7. Common mistakes

* Fetch trong render path.
* Không cancel/debounce search requests.
* Memoize mọi thứ theo thói quen.
* Global state cho dữ liệu chỉ thuộc local component.
* Ignore error/loading/race states.

## 8. Alternatives

Server-side rendering, server components tùy stack, hoặc đơn giản hóa state ownership có thể giảm client complexity. Không phải page nào cũng cần state-management library.

## 9. Trade-offs

### Advantages

Declarative UI và component reuse cao.

### Costs / Risks

State/effect graph phức tạp có thể tạo hidden network/render work và race conditions.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu props/state/reactivity và render cycle.

### Middle

Debug API calls, lifecycle và async race bằng DevTools.

### Senior

Thiết kế state ownership, cache/request behavior và frontend performance boundary.

### Technical Lead / Architect

Quyết định complexity nào cần ở client, API contract nào hỗ trợ UI tốt và khi nào SSR/client rendering phù hợp.

## 11. Key takeaway

* State ownership quyết định phần lớn frontend complexity.
* Đừng tối ưu rendering bằng memoization trước khi đo.
* Network race và stale response là production concern thực tế.

# 10. AI-assisted code review: probabilistic reasoning + deterministic verification

## 1. What is it?

AI-assisted code review dùng LLM/coding agent để đọc diff, repository context, tests và conventions rồi đề xuất bugs, missing tests hoặc architectural risks. Model nên được xem là probabilistic reviewer giúp mở rộng search space, không phải authority quyết định merge.

## 2. Why does it exist?

Human reviewers có bandwidth hạn chế và dễ bỏ sót repetitive cross-file issues. AI có thể tạo hypothesis nhanh, nhưng có thể hallucinate APIs, version behavior hoặc repository invariants.

## 3. How does it work?

```text
PR diff + repository context
        -> AI findings
        -> compile/tests/static analysis
        -> human verification
        -> merge decision
```

Deterministic checks phải đứng sau probabilistic suggestion.

## 4. Practical implementation

Review instruction nên yêu cầu mỗi finding có: file/line evidence, failure path, mức độ chắc chắn và minimal verification test. CI vẫn chạy `dotnet build`, unit/integration tests và static analysis.

## 5. Real production scenario

AI reviewer nhận ra cache key mới không chứa tenant ID và đề xuất cross-tenant collision scenario. Human reviewer viết integration test hai tenants để xác nhận trước khi sửa/merge.

## 6. Failure scenario & troubleshooting

Nếu AI tạo quá nhiều false positives, đo precision của findings. Bắt buộc source grounding, repository-specific rules và reproduction thay vì chấp nhận generic “best practices”.

## 7. Common mistakes

* Cho model quyết định merge.
* Tin package/API version từ model memory.
* Không cung cấp architecture/context.
* Chấp nhận generated tests chỉ vì tests pass.
* Không review security-critical changes bằng con người.

## 8. Alternatives

Compiler, SonarQube/static analyzers, security scanners và human review mạnh hơn ở nhiều rule deterministic. AI bổ sung reasoning rộng chứ không thay thế chúng.

## 9. Trade-offs

### Advantages

Tăng reviewer throughput, tốt cho repository navigation và hypothesis generation.

### Costs / Risks

False positives, hallucination, context/token cost, data-governance risk và automation bias.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Dùng AI để hiểu diff nhưng tự verify behavior.

### Middle

Yêu cầu evidence/reproduction/test cho finding.

### Senior

Phân biệt confirmed defect với architectural hypothesis.

### Technical Lead / Architect

Thiết kế policy: dữ liệu nào được gửi, rule nào deterministic, finding nào cần human approval và metrics nào đánh giá AI-review quality.

## 11. Key takeaway

* AI review tạo hypothesis; verification tạo confidence.
* Build/tests/static analysis vẫn là gate bắt buộc.
* Human ownership vẫn cần cho security và architecture decisions.
