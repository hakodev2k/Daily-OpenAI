# 1. `Span<T>` vs `Memory<T>`: zero-allocation slicing, lifetime rules và khi optimization làm API khó dùng hơn

## 1. What is it?

`Span<T>` là một view liên tục trên một vùng memory. Nó cho phép đọc, ghi, slice dữ liệu mà không cần tạo array/string mới trong nhiều trường hợp.

`Memory<T>` giải quyết một vấn đề khác: nó cũng đại diện cho một vùng memory nhưng có thể sống qua asynchronous boundaries và được lưu trong object fields.

Mental model:

```text
Array / string / pooled buffer
          ↓
       Span<T>
   synchronous view
          ↓
 slice without copying
```

Trong khi:

```text
buffer
  ↓
Memory<T>
  ↓
can cross async boundary
  ↓
.Span when synchronous access is needed
```

`Span<T>` là `ref struct`, vì vậy runtime/compiler hạn chế cách nó được lưu để tránh dangling references.

## 2. Why does it exist?

Trước đây, parsing hoặc slicing thường tạo temporary allocations:

```csharp
var prefix = input.Substring(0, 8);
```

Trong hot path, hàng triệu allocations nhỏ tạo GC pressure dù business logic rất đơn giản.

`Span<T>` tồn tại để cho phép thao tác trực tiếp trên dữ liệu hiện có.

Tuy nhiên, mục tiêu của nó không phải “làm mọi code nhanh hơn”, mà là giảm copy/allocation khi profiling chứng minh đó là bottleneck.

## 3. How does it work?

Một `Span<T>` chứa thông tin khái niệm về:

```text
reference/pointer to memory
+
length
```

Khi slice:

```csharp
var slice = span.Slice(5, 10);
```

không có array mới được tạo. Slice chỉ tạo một view khác trên cùng backing storage.

Vì backing storage có lifetime, compiler không cho phép `Span<T>` bị capture trong lambda, boxed hoặc sống tùy ý trên heap.

## 4. Practical implementation

Parsing một code dạng `ORD-20260908-12345`:

```csharp
public static bool TryParseOrderCode(
    ReadOnlySpan<char> input,
    out int orderNumber)
{
    orderNumber = 0;

    if (!input.StartsWith("ORD-", StringComparison.Ordinal))
        return false;

    var lastDash = input.LastIndexOf('-');
    if (lastDash < 0 || lastDash == input.Length - 1)
        return false;

    var numberPart = input[(lastDash + 1)..];
    return int.TryParse(numberPart, out orderNumber);
}
```

Không cần `Substring()` chỉ để parse phần cuối.

Nếu method phải await:

```csharp
public async Task ProcessAsync(
    ReadOnlyMemory<byte> payload,
    CancellationToken ct)
{
    await ValidateAsync(ct);

    var span = payload.Span;
    // synchronous work with span here
}
```

Dùng `Memory<T>` làm contract qua async boundary, rồi lấy `.Span` trong synchronous region.

## 5. Real production scenario

Một gateway parse hàng trăm nghìn headers và identifiers mỗi giây. Profiling cho thấy allocation rate cao chủ yếu do `Substring`, temporary arrays và encoding conversions.

Chuyển một số parsing hot paths sang `ReadOnlySpan<char>` giảm allocation đáng kể.

Nhưng nếu endpoint chỉ chạy 20 RPS, thêm `Span<T>` vào mọi abstraction có thể làm code khó đọc mà gần như không có lợi ích đo được.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU/GC cao trong parser hoặc serializer path.

**Evidence** → profiler cho thấy nhiều short-lived allocations từ slicing/copying.

**Hypothesis** → unnecessary temporary allocations.

**Diagnosis** → đo allocation count/bytes bằng BenchmarkDotNet hoặc profiler.

**Fix** → áp dụng `Span<T>`/`Memory<T>` ở đúng hot path.

**Verification** → so sánh allocations/op, throughput và latency trước/sau.

## 7. Common mistakes

* Dùng `Span<T>` khắp nơi chỉ vì “zero allocation”.
* Làm public API phức tạp hơn trước khi có benchmark.
* Cố giữ `Span<T>` qua `await`.
* Quên backing memory có thể đến từ `ArrayPool<T>` và bị reuse sau khi return.
* Assume “ít allocation hơn” luôn đồng nghĩa latency tốt hơn.

## 8. Alternatives

* `string`/array bình thường: đơn giản, phù hợp đa số business code.
* `ReadOnlyMemory<T>`: phù hợp asynchronous APIs.
* `ArrayPool<T>`: hữu ích khi cần reusable buffers lớn hơn.
* `SequenceReader<T>`/`ReadOnlySequence<T>`: phù hợp segmented buffers/network pipelines.

## 9. Trade-offs

### Advantages

* Giảm allocations và copying.
* Tốt cho parsing/serialization/network hot paths.

### Costs / Risks

* API/lifetime semantics khó hơn.
* Dễ over-optimize code không quan trọng.
* Pooled memory yêu cầu ownership discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slice không nhất thiết phải tạo object mới.

### Middle

Biết phân biệt `Span<T>` và `Memory<T>` theo lifetime/async boundary.

### Senior

Dùng profiling để chứng minh allocation problem trước khi tối ưu.

### Technical Lead / Architect

Giữ low-level optimization ở boundary/hot path phù hợp, không để complexity lan vào toàn domain model.

## 11. Key takeaway

* `Span<T>` tối ưu synchronous memory access.
* `Memory<T>` phù hợp khi lifetime phải vượt async boundary.
* Chỉ dùng khi measurement cho thấy allocation/copy thật sự đáng tối ưu.

# 2. ASP.NET Core middleware ordering: vì sao thứ tự pipeline là behavior, không phải cosmetic

## 1. What is it?

ASP.NET Core xử lý request qua một chuỗi middleware. Thứ tự đăng ký middleware chính là thứ tự request đi qua chúng, còn response quay ngược lại theo stack.

Mental model:

```text
Request
  ↓
Exception Handling
  ↓
Routing
  ↓
Authentication
  ↓
Authorization
  ↓
Endpoint
  ↑
Response travels back outward
```

## 2. Why does it exist?

Middleware cho phép cross-cutting concerns được composable: logging, security headers, authentication, exception handling, caching, routing.

Nhưng composability kéo theo ordering dependency. Một middleware chạy quá sớm có thể thiếu route metadata; chạy quá muộn có thể không bắt được exception hoặc không bảo vệ endpoint.

## 3. How does it work?

Mỗi middleware thường gọi `next()`:

```csharp
app.Use(async (context, next) =>
{
    // before downstream
    await next();
    // after downstream
});
```

Vì vậy pipeline giống nested calls hơn là một danh sách độc lập.

## 4. Practical implementation

Một cấu hình điển hình:

```csharp
app.UseExceptionHandler();
app.UseHttpsRedirection();

app.UseRouting();

app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();
```

Nếu custom middleware cần endpoint metadata:

```csharp
app.UseRouting();
app.UseMiddleware<TenantPolicyMiddleware>();
app.UseAuthentication();
app.UseAuthorization();
```

thì middleware phải chạy sau routing.

## 5. Real production scenario

Team thêm authorization middleware trước routing rồi đọc `context.GetEndpoint()?.Metadata`. Trong local test endpoint metadata null nên custom rule silently skip. Một số API production vô tình không áp policy mong muốn.

Đây không phải “middleware bug”; đó là pipeline-order bug.

## 6. Failure scenario & troubleshooting

**Symptom** → authentication/authorization/logging behavior khác endpoint hoặc exception không được format thống nhất.

**Evidence** → middleware order không phù hợp dependency; endpoint metadata unavailable hoặc exception handler nằm sau code có thể throw.

**Hypothesis** → pipeline ordering.

**Diagnosis** → trace request pipeline, log middleware enter/exit, kiểm tra docs/framework convention.

**Fix** → reorder middleware theo dependency.

**Verification** → integration tests cho authenticated, unauthorized, exception và endpoint metadata paths.

## 7. Common mistakes

* Coi thứ tự `UseX()` là không quan trọng.
* Đặt exception handler sau middleware có thể throw.
* Đặt custom authorization trước routing nhưng cần route metadata.
* Dùng duplicate auth logic trong custom middleware thay vì policy system.
* Chỉ test happy path.

## 8. Alternatives

* Endpoint filters cho logic gắn với endpoint.
* MVC filters cho MVC-specific concerns.
* Policy-based authorization cho access decisions.
* Middleware cho cross-cutting request/response behavior toàn application.

## 9. Trade-offs

### Advantages

* Pipeline composable và dễ mở rộng.
* Cross-cutting logic tập trung.

### Costs / Risks

* Ordering dependency có thể implicit.
* Custom middleware dễ trở thành nơi chứa business logic sai boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request đi qua middleware theo thứ tự đăng ký.

### Middle

Biết middleware nào phụ thuộc routing/authentication.

### Senior

Debug pipeline behavior và chọn đúng abstraction thay vì nhét mọi thứ vào middleware.

### Technical Lead / Architect

Định nghĩa middleware conventions và integration tests để tránh security/observability regressions.

## 11. Key takeaway

* Middleware order là runtime behavior.
* Security/exception/routing middleware có dependencies rõ.
* Dùng integration test để bảo vệ pipeline, không chỉ nhìn `Program.cs`.

# 3. EF Core split queries: tránh Cartesian explosion nhưng phải hiểu consistency và round-trip trade-off

## 1. What is it?

Khi include nhiều collection navigation, EF Core có thể tạo một SQL query lớn với nhiều joins. `AsSplitQuery()` yêu cầu EF tách việc load dữ liệu thành nhiều SQL queries thay vì một giant join.

## 2. Why does it exist?

Hai collections cùng include có thể nhân số rows:

```text
Order
  10 OrderLines
  8 Notes
```

Một join có thể trả gần 80 combinations cho một Order dù logical data chỉ là 19 records.

Đây là Cartesian explosion.

## 3. How does it work?

Single query:

```text
Orders
 JOIN OrderLines
 JOIN Notes
 → duplicated parent/child data
```

Split query:

```text
Query Orders
Query OrderLines for selected Orders
Query Notes for selected Orders
EF stitches graph in memory
```

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .AsNoTracking()
    .ToListAsync(ct);
```

Nhưng nếu API chỉ cần summary, projection thường tốt hơn:

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummaryDto
    {
        Id = x.Id,
        Total = x.Lines.Sum(l => l.Quantity * l.UnitPrice),
        NoteCount = x.Notes.Count
    })
    .ToListAsync(ct);
```

## 5. Real production scenario

Admin page load 100 Orders, mỗi order có lines, tags và audit events. Single join trả hàng chục nghìn rows, network payload và materialization CPU tăng mạnh.

Split query giảm duplicated rows nhưng tạo nhiều round trips. Projection có thể còn tốt hơn nếu UI không cần full graph.

## 6. Failure scenario & troubleshooting

**Symptom** → query có latency cao, result row count bất thường lớn.

**Evidence** → execution plan và generated SQL có nhiều collection joins.

**Hypothesis** → Cartesian explosion.

**Diagnosis** → log SQL, measure returned rows, compare single vs split vs projection.

**Fix** → `AsSplitQuery()` hoặc projection/access-pattern redesign.

**Verification** → đo DB duration, rows, payload, allocations và p95.

## 7. Common mistakes

* Dùng `Include` cho mọi navigation “cho chắc”.
* Coi split query là universal fix.
* Không nghĩ tới consistency giữa các queries nếu dữ liệu thay đổi giữa các round trips.
* Load full entity graph cho read-only summary.

## 8. Alternatives

* Projection.
* Explicit separate queries.
* Read model/materialized view.
* Single query nếu dataset nhỏ và duplication không đáng kể.

## 9. Trade-offs

### Advantages

* Giảm row duplication.
* Có thể giảm memory/materialization cost.

### Costs / Risks

* Nhiều database round trips.
* Có thể quan sát data ở các thời điểm hơi khác nhau tùy isolation.
* Vẫn có thể over-fetch nếu graph quá lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` có thể làm SQL lớn hơn nhiều so với entity count.

### Middle

Biết kiểm tra generated SQL và dùng split query khi phù hợp.

### Senior

So sánh projection, split và single query bằng measurement.

### Technical Lead / Architect

Thiết kế read model theo use case thay vì coi ORM entity graph là API response model.

## 11. Key takeaway

* Nhiều collection joins có thể tạo Cartesian explosion.
* `AsSplitQuery()` đổi duplication lấy round trips.
* Projection thường là lựa chọn mạnh nhất cho read-heavy API cụ thể.

# 4. SQL keyset pagination: ổn định latency trên bảng lớn và tránh deep `OFFSET`

## 1. What is it?

Keyset pagination lấy page tiếp theo dựa trên key cuối cùng của page trước thay vì bỏ qua N rows bằng `OFFSET`.

Ví dụ:

```sql
WHERE CreatedAt < @lastCreatedAt
ORDER BY CreatedAt DESC
FETCH NEXT 50 ROWS ONLY
```

## 2. Why does it exist?

Offset pagination thuận tiện:

```sql
OFFSET 500000 ROWS FETCH NEXT 50 ROWS ONLY
```

nhưng database vẫn phải tìm/sort/skip một lượng lớn rows trước khi trả 50 rows cuối.

Ngoài ra, khi dữ liệu insert/delete giữa page requests, offset pagination dễ tạo duplicate/missing items.

## 3. How does it work?

Giả sử order ổn định theo:

```text
CreatedAt DESC, Id DESC
```

Cursor lưu cặp cuối:

```text
(lastCreatedAt, lastId)
```

Query page sau:

```sql
WHERE CreatedAt < @lastCreatedAt
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC
```

## 4. Practical implementation

```sql
SELECT TOP (@PageSize)
    Id,
    CreatedAt,
    CustomerId,
    TotalAmount
FROM Orders
WHERE
    CreatedAt < @LastCreatedAt
    OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index phù hợp:

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON Orders (CreatedAt DESC, Id DESC)
INCLUDE (CustomerId, TotalAmount);
```

API có thể encode cursor thành opaque token thay vì expose raw fields.

## 5. Real production scenario

Orders API ban đầu dùng `page=10000&pageSize=50`. Table tăng lên 80 triệu rows, deep pages có p95 nhiều giây trong khi page đầu vẫn nhanh.

Chuyển sang cursor/keyset giữ query gần với indexed seek pattern.

## 6. Failure scenario & troubleshooting

**Symptom** → page càng sâu càng chậm.

**Evidence** → execution plan cho thấy scan/sort/skip lớn.

**Hypothesis** → deep offset cost.

**Diagnosis** → compare logical reads và elapsed time theo page depth.

**Fix** → stable keyset order + supporting index.

**Verification** → latency gần ổn định giữa early và deep navigation.

## 7. Common mistakes

* Cursor chỉ dùng `CreatedAt` dù nhiều rows có cùng timestamp.
* Không có deterministic tie-breaker như `Id`.
* Encode cursor nhưng không validate tampering/version.
* Dùng keyset khi product thật sự cần “jump to page 500”.

## 8. Alternatives

* Offset pagination: phù hợp dataset nhỏ hoặc UI cần page number/random access.
* Search-after trong Elasticsearch cho search result deep pagination.
* Precomputed snapshots cho reporting/export workflows.

## 9. Trade-offs

### Advantages

* Deep-page latency ổn định hơn.
* Ít duplicate/missing do concurrent inserts khi order hợp lý.

### Costs / Risks

* Không jump arbitrary page dễ dàng.
* Cursor contract phức tạp hơn.
* Index/order design phải chặt chẽ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `OFFSET` càng lớn có thể càng đắt.

### Middle

Biết thiết kế composite order/cursor.

### Senior

Đọc execution plan và chọn index theo access pattern.

### Technical Lead / Architect

Chọn pagination semantics dựa trên UX + data scale, không chỉ API convenience.

## 11. Key takeaway

* Keyset pagination tối ưu cho sequential navigation trên dataset lớn.
* Cursor cần stable ordering và tie-breaker.
* Pagination design là cả API contract lẫn database access pattern.

# 5. Elasticsearch aliases + zero-downtime reindexing

## 1. What is it?

Elasticsearch alias là logical name trỏ tới một hoặc nhiều indexes. Search API có thể query alias thay vì hard-code physical index name.

Ví dụ:

```text
products-search → products-v17
```

## 2. Why does it exist?

Một số mapping/analyzer changes không thể sửa in-place an toàn. Bạn phải tạo index mới và reindex dữ liệu.

Nếu application gọi trực tiếp `products-v17`, cutover sang `products-v18` đòi deploy/config synchronization và có thể tạo downtime hoặc inconsistent traffic.

Alias cho phép đổi target gần như atomic ở Elasticsearch layer.

## 3. How does it work?

```text
API
 ↓
products-search alias
 ↓
products-v17
```

Reindex flow:

```text
create products-v18
→ bulk/backfill data
→ verify
→ sync delta changes
→ atomically move alias
→ monitor
→ retire old index later
```

## 4. Practical implementation

Create new index:

```json
PUT products-v18
{
  "mappings": {
    "properties": {
      "name": { "type": "text" },
      "sku":  { "type": "keyword" }
    }
  }
}
```

Switch alias:

```json
POST _aliases
{
  "actions": [
    { "remove": { "index": "products-v17", "alias": "products-search" } },
    { "add":    { "index": "products-v18", "alias": "products-search" } }
  ]
}
```

## 5. Real production scenario

E-commerce thay analyzer cho product names để cải thiện search tiếng Việt/English. Rebuilding hàng chục triệu documents mất hàng giờ.

Old index vẫn serve traffic. New index được build/validated riêng, sau đó alias switch trong một operation.

## 6. Failure scenario & troubleshooting

**Symptom** → sau reindex search thiếu documents mới nhất.

**Evidence** → backfill chạy từ snapshot nhưng writes tiếp tục vào old index trong nhiều giờ.

**Hypothesis** → delta synchronization gap.

**Diagnosis** → compare source DB version/count, index timestamps và event lag.

**Fix** → dual-write có kiểm soát hoặc event replay/change capture để sync delta trước cutover.

**Verification** → count/sample/business-query comparison trước alias switch.

## 7. Common mistakes

* Reindex xong là switch ngay không verify.
* Không có strategy cho writes xảy ra trong lúc backfill.
* Xóa old index ngay lập tức nên rollback khó.
* Application hard-code physical index names.

## 8. Alternatives

* In-place compatible mapping update khi Elasticsearch cho phép.
* Blue/green search cluster trong migration lớn.
* Rebuild từ primary DB + replay event log.

## 9. Trade-offs

### Advantages

* Cutover nhanh.
* Rollback dễ nếu giữ old index.
* Decouple application khỏi physical index version.

### Costs / Risks

* Temporary storage gần gấp đôi.
* Reindex có thể tốn I/O/CPU.
* Delta synchronization là phần khó nhất.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu alias là stable logical name.

### Middle

Biết create/reindex/switch alias.

### Senior

Thiết kế verification và delta sync.

### Technical Lead / Architect

Xác định source of truth, recovery path và rollback window cho search schema evolution.

## 11. Key takeaway

* Alias giúp decouple API khỏi physical index version.
* Zero-downtime reindex cần cả backfill và delta synchronization.
* Không cut over trước khi có verification + rollback plan.

# 6. Bulkhead Pattern: cô lập dependency failure trước khi một downstream chậm kéo sập toàn service

## 1. What is it?

Bulkhead giới hạn resource/concurrency dành cho một dependency hoặc workload để failure ở một khu vực không chiếm toàn bộ capacity của process.

Tên lấy từ tàu biển: các khoang tách biệt để nước vào một khoang không làm chìm toàn tàu.

## 2. Why does it exist?

Giả sử service gọi Reviews API. Reviews chậm 10 giây. Nếu mọi request tới website đều tạo outbound call và chờ, hàng trăm requests có thể cùng giữ sockets, request slots hoặc downstream concurrency.

Dù Reviews chỉ là feature phụ, nó có thể làm Product API chính timeout.

## 3. How does it work?

```text
Incoming requests
   ↓
Reviews dependency bulkhead
   ↓ max 20 concurrent calls
20 active
rest rejected/queued briefly
```

Failure được bounded thay vì lan vô hạn.

## 4. Practical implementation

Với resilience pipeline có concurrency limiter:

```csharp
var options = new ConcurrencyLimiterOptions
{
    PermitLimit = 20,
    QueueLimit = 10,
    QueueProcessingOrder = QueueProcessingOrder.OldestFirst
};
```

Hoặc thiết kế separate worker pools/queues cho expensive workloads.

Bulkhead thường đi cùng timeout và Circuit Breaker, nhưng mỗi pattern giải quyết vấn đề khác nhau.

## 5. Real production scenario

Product page gọi CMS, Inventory, Reviews và Recommendations. Reviews vendor chậm 15 giây.

Không bulkhead: request concurrency tăng, ThreadPool/HTTP connections bị áp lực, toàn page latency tăng.

Có bulkhead + timeout + graceful degradation: Reviews section unavailable nhưng Product/Inventory vẫn hoạt động.

## 6. Failure scenario & troubleshooting

**Symptom** → một dependency chậm làm toàn service latency/error tăng.

**Evidence** → outbound call duration tăng, concurrent requests tới dependency tăng, unrelated endpoints cũng degrade.

**Hypothesis** → shared capacity bị dependency chiếm hết.

**Diagnosis** → dependency telemetry + concurrency/resource metrics.

**Fix** → concurrency isolation, timeout, fallback/degradation.

**Verification** → fault injection dependency chậm nhưng core endpoints vẫn giữ SLO.

## 7. Common mistakes

* Queue quá nhiều bên trong bulkhead, biến overload thành latency dài.
* Dùng một global semaphore cho mọi dependencies.
* Không có timeout nên permits bị giữ quá lâu.
* Retry bên trong bulkhead quá mạnh gây self-amplification.

## 8. Alternatives

* Circuit Breaker: ngừng gọi dependency đang fail.
* Timeout: giới hạn thời gian một call.
* Separate service/process: isolation mạnh hơn nhưng operational cost cao hơn.
* Queue-based load leveling cho async workload.

## 9. Trade-offs

### Advantages

* Giảm failure propagation.
* Bảo vệ scarce resources.

### Costs / Risks

* Có thể reject requests dù process còn capacity tổng thể.
* Cần sizing theo real workload.
* Thêm policy complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dependency chậm có thể làm caller cạn resource.

### Middle

Biết áp concurrency limit và timeout.

### Senior

Tune limits bằng telemetry và fault testing.

### Technical Lead / Architect

Quyết định dependency nào cần isolation và user-facing degradation behavior khi limit bị hit.

## 11. Key takeaway

* Bulkhead bảo vệ shared capacity.
* Timeout, retry, circuit breaker và bulkhead giải quyết các failure modes khác nhau.
* Isolation tốt phải được test bằng dependency failure injection.

# 7. Azure Functions concurrency + scale-out: throughput không chỉ phụ thuộc số instance

## 1. What is it?

Azure Functions có hai cấp liên quan throughput:

```text
concurrency per instance
×
number of instances
```

Scale-out thêm instances. Concurrency quyết định một instance xử lý bao nhiêu executions đồng thời.

## 2. Why does it exist?

Một function có thể CPU-bound, I/O-bound hoặc phụ thuộc database/API có capacity giới hạn.

Nếu concurrency per instance quá cao, function có thể tự saturate CPU/memory hoặc overload downstream trước khi platform kịp scale hợp lý.

Nếu quá thấp, resource bị underutilized và backlog tăng không cần thiết.

## 3. How does it work?

Ví dụ queue-triggered workload:

```text
Queue backlog
   ↓
Scale controller
   ↓
more Function instances
   ↓
Each instance processes N messages concurrently
```

Tổng pressure xuống SQL/Service Bus/third-party API phụ thuộc cả hai dimensions.

## 4. Practical implementation

Trong thiết kế function, handler phải idempotent và cancellation-aware:

```csharp
[Function("ProcessOrder")]
public async Task RunAsync(
    [ServiceBusTrigger("orders")] ServiceBusReceivedMessage message,
    CancellationToken ct)
{
    await processor.ProcessAsync(message.MessageId, message.Body, ct);
}
```

Sau đó capacity-plan downstream trước khi tăng concurrency.

Ví dụ SQL chỉ chịu 100 concurrent expensive writes thì 20 instances × 20 handlers có thể là design sai dù Function platform scale “tốt”.

## 5. Real production scenario

Queue backlog tăng. Team tăng per-instance concurrency và thấy throughput ban đầu tăng, sau đó SQL throttling/deadlocks xuất hiện, retries tăng và backlog còn tệ hơn.

Root cause là downstream saturation, không phải thiếu Functions instances.

## 6. Failure scenario & troubleshooting

**Symptom** → scale-out tăng nhưng throughput không tăng hoặc error tăng.

**Evidence** → SQL/HTTP dependency latency, throttling, connection pool và retry count tăng.

**Hypothesis** → downstream bottleneck.

**Diagnosis** → correlate instance count, concurrent executions, dependency metrics, queue age.

**Fix** → tune concurrency, batch, partition workload, improve downstream capacity/access pattern.

**Verification** → backlog drain rate tăng mà dependency SLO vẫn ổn.

## 7. Common mistakes

* “Thêm instance” như universal fix.
* Không tính downstream quotas.
* Handler không idempotent nên retries/scale tạo duplicate effects.
* Long I/O call không timeout.
* Không theo dõi oldest-message age.

## 8. Alternatives

* Worker Service/Container Apps cho workload cần control runtime/concurrency sâu hơn.
* Service Bus consumers với explicit processor settings.
* Batch processing nếu per-item overhead cao.

## 9. Trade-offs

### Advantages

* Scale-out nhanh, phù hợp event-driven workloads.
* Operational burden thấp hơn tự quản cluster.

### Costs / Risks

* Downstream có thể trở thành bottleneck.
* Cold start/concurrency behavior ảnh hưởng p95.
* Cost tăng nếu scale policy không phù hợp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu throughput = không chỉ “bao nhiêu instances”.

### Middle

Biết quan sát queue backlog và dependency latency.

### Senior

Tune concurrency dựa trên bottleneck thật.

### Technical Lead / Architect

Capacity-plan toàn pipeline từ trigger tới database/external APIs.

## 11. Key takeaway

* Scale-out và per-instance concurrency là hai knobs khác nhau.
* Downstream capacity giới hạn throughput end-to-end.
* Measure queue age + dependency saturation, không chỉ instance count.

# 8. Database connection pool exhaustion: điều tra từ symptom đến root cause thay vì chỉ tăng pool size

## 1. What is it?

ADO.NET connection pooling tái sử dụng physical database connections. Khi application gọi `OpenAsync`, nó thường lấy connection từ pool thay vì tạo TCP/database session mới.

Pool exhaustion xảy ra khi tất cả pooled connections đang bận và request mới phải chờ cho tới timeout.

## 2. Why does it exist?

Database connection setup đắt. Pooling tăng performance, nhưng pool cũng là bounded shared resource.

Nếu query chậm, transaction dài hoặc connection leak, pool có thể hết dù database CPU chưa 100%.

## 3. How does it work?

```text
Request
 ↓
Acquire pooled connection
 ↓
Execute DB work
 ↓
Dispose/return connection
```

Nếu step cuối bị trì hoãn hoặc DB work kéo dài:

```text
active connections ↑
free connections ↓
waiters ↑
request latency ↑
```

## 4. Practical implementation

Đúng ownership với EF Core:

```csharp
await using var db = await dbContextFactory.CreateDbContextAsync(ct);

var result = await db.Orders
    .AsNoTracking()
    .Where(x => x.Status == OrderStatus.Pending)
    .Take(100)
    .ToListAsync(ct);
```

Không giữ transaction qua remote call:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

// DB work only
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);

// Call external service after transaction if business design permits
```

## 5. Real production scenario

API có pool size 100. Một third-party call được đặt bên trong DB transaction. Vendor latency tăng từ 200 ms lên 8 giây. Mỗi request giữ connection/transaction trong lúc chờ vendor.

100 concurrent requests đủ làm pool cạn; endpoint khác dùng cùng DB cũng fail.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout khi mở connection, p95 tăng toàn API.

**Evidence** → pool waiters tăng, active connections gần max, query CPU không nhất thiết cao.

**Hypothesis** → connections bị giữ lâu hoặc leak.

**Diagnosis** → xem transaction duration, query duration, dependency calls trong transaction, connection lifetime.

**Fix** → rút ngắn DB critical section, dispose đúng, tối ưu slow query, tránh remote call trong transaction.

**Verification** → pool utilization, wait time và request p95 giảm.

## 7. Common mistakes

* Tăng `Max Pool Size` ngay mà không tìm root cause.
* Không dispose context/connection đúng ownership.
* Transaction quá rộng.
* Slow query khiến connection bị giữ lâu nhưng chỉ nhìn CPU.
* Retry connection timeout hàng loạt gây thêm pressure.

## 8. Alternatives

* Tăng pool size chỉ khi database thật sự còn capacity và workload hợp lệ.
* Separate databases/pools cho workload isolation.
* Queue async work để giảm concurrency spikes.

## 9. Trade-offs

### Advantages của pooling

* Giảm connection setup overhead.
* Tăng throughput đáng kể.

### Costs / Risks

* Bounded pool tạo queueing under pressure.
* Tăng pool quá lớn có thể chuyển bottleneck sang database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Dispose` thường trả connection về pool.

### Middle

Biết kiểm tra query/transaction duration.

### Senior

Correlate pool metrics với slow dependencies và transaction boundaries.

### Technical Lead / Architect

Thiết kế workload isolation và capacity để pool không trở thành hidden shared bottleneck.

## 11. Key takeaway

* Pool exhaustion thường là symptom của work giữ connection quá lâu.
* Tăng pool size có thể chỉ dời bottleneck.
* Điều tra transaction/query/dependency duration trước.

# 9. Managed Identity + Azure Key Vault: secretless authentication nhưng vẫn cần permission boundary và rotation strategy

## 1. What is it?

Managed Identity cho Azure resource một identity trong Microsoft Entra ID mà không cần application giữ client secret/password.

Application có thể dùng identity đó để lấy token truy cập Key Vault, Storage, SQL hoặc service khác hỗ trợ Entra authentication.

## 2. Why does it exist?

Client secrets trong configuration tạo nhiều rủi ro:

* leak vào source/logs
* hết hạn
* rotation khó
* copy giữa environments

Managed Identity chuyển credential lifecycle cho Azure platform.

## 3. How does it work?

```text
App Service / Function / VM
        ↓
Managed Identity
        ↓ token from Entra
Azure Key Vault
        ↓
secret/certificate/key if authorized
```

Application không cần biết raw identity credential.

## 4. Practical implementation

```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri(configuration["KeyVaultUri"]!),
    credential);

KeyVaultSecret secret = await client.GetSecretAsync(
    "PaymentsApiKey",
    cancellationToken: ct);
```

Trong local development, `DefaultAzureCredential` có thể dùng developer identity; production dùng Managed Identity nếu environment hỗ trợ.

## 5. Real production scenario

App Service cần gọi Key Vault để lấy API key của legacy vendor chưa hỗ trợ Entra. App Service itself không cần client secret để vào Key Vault; chỉ vendor key còn nằm trong vault.

Khi vendor key rotate, application config không cần chứa credential mới.

## 6. Failure scenario & troubleshooting

**Symptom** → production 403 khi đọc secret dù local chạy được.

**Evidence** → local developer account có quyền, Managed Identity của App Service không có role/access policy phù hợp.

**Hypothesis** → identity mismatch/permission boundary.

**Diagnosis** → xác định principal ID thực tế, role assignment, vault networking và secret name/version.

**Fix** → grant least-privilege role cho đúng managed identity; không cấp quyền rộng chỉ để unblock.

**Verification** → test bằng production identity path trong staging.

## 7. Common mistakes

* Nghĩ Managed Identity tự động có quyền mọi Azure resource.
* Dùng developer account behavior để suy ra production behavior.
* Grant `Owner`/broad permissions thay vì least privilege.
* Fetch secret mỗi request mà không có caching/lifecycle design.
* Log secret value khi debug.

## 8. Alternatives

* Service Principal + certificate/secret khi Managed Identity không khả dụng.
* Workload Identity cho Kubernetes scenarios.
* Direct Entra auth tới downstream để loại bỏ secret hoàn toàn nếu provider hỗ trợ.

## 9. Trade-offs

### Advantages

* Loại bỏ app credential secret cho Azure authentication.
* Rotation/lifecycle đơn giản hơn.
* Permission gắn với resource identity.

### Costs / Risks

* Local/prod identity khác nhau dễ gây confusion.
* RBAC/networking vẫn cần thiết kế đúng.
* Key Vault có latency/cost; không nên đọc secret mỗi request vô thức.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu identity khác secret value.

### Middle

Biết dùng `DefaultAzureCredential` và RBAC.

### Senior

Debug principal/role/networking differences giữa environments.

### Technical Lead / Architect

Thiết kế identity strategy, least privilege, rotation và fallback mà không phân phối raw credentials.

## 11. Key takeaway

* Managed Identity giảm credential-management risk, không xóa authorization design.
* Production identity phải được test như một principal riêng.
* Prefer direct token-based access khi downstream hỗ trợ, dùng Key Vault cho secrets còn bắt buộc.

# 10. Optimizely CMS content modeling: page type, block, content ownership và tránh object graph khó maintain

## 1. What is it?

Trong Optimizely CMS, content modeling định nghĩa các loại nội dung editor có thể tạo: page types, blocks, properties và relationships.

Mental model tốt:

```text
Page = route/page-level content responsibility
Block = reusable editorial component
Content reference = composition relationship
```

CMS model không nên chỉ mirror frontend component tree 1:1.

## 2. Why does it exist?

Editor cần cấu trúc nội dung có ý nghĩa business/editorial. Developer cần schema đủ ổn định để render, search, cache và migrate.

Nếu model chỉ bám layout hiện tại, một redesign frontend có thể buộc migrate hàng nghìn content items dù business content không đổi.

## 3. How does it work?

Ví dụ:

```text
ProductLandingPage
 ├─ Title
 ├─ Intro
 ├─ HeroBlock
 ├─ ContentArea
 │   ├─ PromoBlock
 │   ├─ RichTextBlock
 │   └─ FeaturedProductsBlock
```

Page sở hữu page-level intent. Blocks đại diện reusable editorial concepts, không phải mọi `<div>`.

## 4. Practical implementation

Ví dụ content types:

```csharp
[ContentType(
    DisplayName = "Campaign Landing Page",
    GUID = "11111111-1111-1111-1111-111111111111")]
public class CampaignLandingPage : PageData
{
    public virtual string Heading { get; set; } = string.Empty;
    public virtual ContentArea MainContent { get; set; } = null!;
}

[ContentType(
    DisplayName = "Promo Block",
    GUID = "22222222-2222-2222-2222-222222222222")]
public class PromoBlock : BlockData
{
    public virtual string Title { get; set; } = string.Empty;
    public virtual Url? Link { get; set; }
}
```

Tên/property nên phản ánh editorial meaning hơn là CSS/layout implementation.

## 5. Real production scenario

Marketing site ban đầu có `TwoColumnBlueBlock`, `TwoColumnRedBlock`, `ThreeColumnGrayBlock`. Sau redesign, color/layout system thay đổi và hàng nghìn blocks cũ trở thành technical debt.

Nếu model ban đầu là `PromoBlock` với semantic properties và presentation do frontend/template quyết định, redesign ít yêu cầu content migration hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → editor có hàng chục block types gần giống nhau, khó biết dùng cái nào; redesign yêu cầu migration lớn.

**Evidence** → content type names encode CSS/layout; duplicate properties; reuse không rõ boundary.

**Hypothesis** → content model mirror presentation layer.

**Diagnosis** → inventory content types, usage frequency, property overlap, editor workflows.

**Fix** → consolidate semantic content types, presentation variants có kiểm soát, migration plan.

**Verification** → editor testing + content migration dry run + rendering regression tests.

## 7. Common mistakes

* Một block cho mỗi visual variation.
* Giant page type có hàng chục unrelated properties.
* Reuse block chỉ vì code reuse, dù editorial meaning khác.
* Hard-code business data vào CMS thay vì authoritative backend.
* Không nghĩ đến search/indexing/cache khi thiết kế references.

## 8. Alternatives

* Headless CMS model tách rendering mạnh hơn nhưng vẫn cần semantic content modeling.
* Structured content/API-first model cho multi-channel delivery.
* Traditional page-centric model phù hợp khi website/editorial workflow là primary channel.

## 9. Trade-offs

### Advantages của semantic modeling

* Dễ reuse qua redesign/channel.
* Editor experience rõ hơn.
* Migration ít phụ thuộc presentation.

### Costs / Risks

* Cần discovery với content/editorial stakeholders.
* Quá generic có thể làm editing khó hiểu.
* Tách presentation khỏi content cần design system/rendering discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu page và block có responsibilities khác nhau.

### Middle

Biết tạo content types/property contracts rõ.

### Senior

Thiết kế model theo editorial semantics và migration impact.

### Technical Lead / Architect

Xác định content ownership giữa CMS, commerce, CRM/search và đảm bảo content model sống được qua nhiều frontend redesigns.

## 11. Key takeaway

* CMS content model nên đại diện editorial/business meaning, không mirror HTML/CSS.
* Reusable block cần semantic reuse, không chỉ code reuse.
* Content modeling tốt giảm migration cost và tăng editor usability lâu dài.
