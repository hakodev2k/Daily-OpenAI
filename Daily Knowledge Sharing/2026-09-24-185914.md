# 1. C# `CancellationToken`: cancellation là cooperative protocol, không phải kill switch

## 1. What is it?

Mental model: `CancellationToken` là tín hiệu “operation này không còn cần thiết”; code nhận token phải chủ động quan sát và dừng ở safe point. Runtime không cưỡng chế terminate thread.

## 2. Why does it exist?

Request đã disconnect hoặc deadline đã hết nhưng application vẫn query DB, gọi HTTP và serialize response là wasted work. Trong tải cao, wasted work có thể tiếp tục chiếm connection pool và CPU.

## 3. How does it work?

`CancellationTokenSource` phát tín hiệu; token được propagate xuống call chain. APIs hỗ trợ cancellation thường kết thúc bằng `OperationCanceledException`/`TaskCanceledException`.

```text
HTTP request aborted
 -> endpoint token
 -> application service
 -> EF Core / HttpClient
 -> underlying I/O cancellation
```

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id, AppDbContext db, CancellationToken ct) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

Library code nên nhận token và propagate thay vì tự tạo token không liên quan.

## 5. Real production scenario

Client timeout sau 2 giây trong khi report query mất 20 giây. Không propagate cancellation khiến SQL tiếp tục chạy dù response không còn consumer.

## 6. Failure scenario & troubleshooting

**Symptom** → request count giảm nhưng DB workload vẫn cao. **Evidence** → disconnected requests tương ứng long-running queries. **Hypothesis** → cancellation bị mất giữa layers. **Diagnosis** → trace token propagation và DB command duration. **Fix** → truyền token xuyên call chain. **Verification** → abort request và xác nhận dependency kết thúc sớm.

## 7. Common mistakes

Dùng `CancellationToken.None`; catch `OperationCanceledException` rồi log Error; cancellation giữa transaction ở điểm không an toàn; tạo `CancellationTokenSource` nhưng không dispose; nhầm cancellation với timeout policy.

## 8. Alternatives

Timeout giới hạn duration; cancellation truyền intent. Thường cần cả hai. Hard process termination chỉ phù hợp boundary khác và không thay cooperative cleanup.

## 9. Trade-offs

### Advantages
Giảm wasted work, hỗ trợ graceful shutdown.

### Costs / Risks
Phải thiết kế safe cancellation points và cleanup semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Biết token là signal.
### Middle
Propagate token qua async APIs.
### Senior
Phân biệt cancellation, timeout và failure; bảo vệ transaction invariants.
### Technical Lead / Architect
Định nghĩa deadline/cancellation contract xuyên service boundaries.

## 11. Key takeaway

- Cancellation là cooperative.
- Propagation quan trọng hơn chỉ thêm parameter.
- Không cancel giữa critical state transition nếu chưa thiết kế recovery.

# 2. ASP.NET Core DI lifetimes: captive dependency và scope boundary trong production

## 1. What is it?

ASP.NET Core DI có `Singleton`, `Scoped`, `Transient`. Lifetime không chỉ là optimization; nó định nghĩa ownership và thời gian state/resource được giữ.

## 2. Why does it exist?

Objects có lifecycle khác nhau. `DbContext` phù hợp request/unit-of-work scope; shared stateless service có thể singleton. Ghép sai lifetime tạo stale state, race condition hoặc disposed objects.

## 3. How does it work?

```text
Root container
 ├─ Singleton
 └─ Request scope
     ├─ Scoped DbContext
     └─ Transient services
```

Singleton giữ scoped dependency là captive dependency: object ngắn hạn bị kéo dài lifecycle ngoài boundary dự kiến.

## 4. Practical implementation

Background singleton cần tạo scope rõ ràng:

```csharp
public sealed class Worker(IServiceScopeFactory scopes) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await using var scope = scopes.CreateAsyncScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            await ProcessAsync(db, ct);
        }
    }
}
```

## 5. Real production scenario

Hosted service inject trực tiếp repository scoped vào singleton. Sau refactor/configuration, scope validation báo lỗi hoặc context sống sai lifecycle và tracking state tích tụ.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng hoặc `DbContext` state lạ trong background job. **Evidence** → scoped service bị giữ bởi singleton. **Hypothesis** → captive dependency. **Diagnosis** → inspect dependency graph/lifetimes. **Fix** → tạo scope theo unit of work. **Verification** → scope validation + memory/load test.

## 7. Common mistakes

Singleton chứa mutable request state; service locator khắp code; transient object giữ expensive unmanaged resource mà ownership không rõ; inject `IServiceProvider` để che dependency graph.

## 8. Alternatives

Explicit factories phù hợp khi lifecycle là domain/runtime concern. Không cần abstraction phức tạp nếu normal scoped injection đủ.

## 9. Trade-offs

### Advantages
DI quản lý composition/lifecycle nhất quán.
### Costs / Risks
Lifetime graph sai có thể chỉ lộ dưới concurrency/long-running process.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu ba lifetime.
### Middle
Chọn scoped cho request unit of work.
### Senior
Phát hiện captive dependencies và thread-safety issues.
### Technical Lead / Architect
Định nghĩa ownership boundary cho web/background processing.

## 11. Key takeaway

- Lifetime là correctness concern.
- Singleton dependency graph phải thread-safe và không giữ scoped state.
- Scope nên tương ứng một logical unit of work.

# 3. SQL Server covering index: giảm lookup nhưng không miễn phí

## 1. What is it?

Covering index chứa đủ columns để SQL Server đáp ứng query từ index mà không cần lookup về clustered index/heap. Key columns hỗ trợ seek/order; `INCLUDE` columns chủ yếu cung cấp payload.

## 2. Why does it exist?

Một nonclustered seek có thể tìm rows nhanh nhưng hàng chục nghìn Key Lookups sau đó tạo random I/O đáng kể.

## 3. How does it work?

```text
Nonclustered seek
 -> matching index rows
 -> Key Lookup per row
```

Covering index có thể bỏ bước lookup nếu query cần đúng dữ liệu index chứa.

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_Tenant_Status
ON dbo.Orders(TenantId, Status)
INCLUDE (CreatedAt, TotalAmount);
```

Xác minh bằng actual execution plan, logical reads và runtime statistics.

## 5. Real production scenario

Dashboard query 20k orders theo tenant/status và hiển thị date/amount. Existing index seek tốt nhưng Key Lookup chiếm phần lớn reads. `INCLUDE` hai projection columns giảm I/O đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → reads giảm nhưng write latency/storage tăng. **Evidence** → index size lớn, update workload phải maintain nhiều wide indexes. **Hypothesis** → over-indexing. **Diagnosis** → usage stats + write workload. **Fix** → consolidate/drop low-value indexes. **Verification** → đo read và write sau thay đổi.

## 7. Common mistakes

Include mọi column; bỏ qua selectivity; tạo overlapping indexes; tin estimated plan mà không đo logical reads; dùng covering index để che query trả quá nhiều rows.

## 8. Alternatives

Projection nhỏ hơn, query redesign, clustered key/schema change hoặc caching nếu workload thật sự phù hợp.

## 9. Trade-offs

### Advantages
Giảm lookups/I/O cho read hot path.
### Costs / Risks
Storage, memory và write amplification.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu seek và lookup.
### Middle
Đọc plan và `INCLUDE` đúng mục đích.
### Senior
Cân read gain với write/index maintenance.
### Technical Lead / Architect
Quản lý index portfolio theo workload thay vì từng query riêng lẻ.

## 11. Key takeaway

- Covering index là workload optimization.
- Đo logical reads trước/sau.
- Mỗi index mới đều có write cost.

# 4. Elasticsearch alias-based reindex: schema evolution không downtime

## 1. What is it?

Index alias là logical name trỏ tới physical index. Khi mapping/analyzer cần thay đổi không thể update in-place phù hợp, tạo index mới, reindex rồi atomically switch alias.

## 2. Why does it exist?

Search schema tiến hóa. Deploy application trực tiếp phụ thuộc physical index name làm migration và rollback khó.

## 3. How does it work?

```text
products-search -> products-v1
create products-v2
reindex/synchronize
atomic alias switch
products-search -> products-v2
```

Write synchronization trong migration phải được thiết kế để không mất changes phát sinh giữa initial copy và cutover.

## 4. Practical implementation

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v1", "alias": "products-search" }},
    { "add":    { "index": "products-v2", "alias": "products-search" }}
  ]
}
```

## 5. Real production scenario

Product search đổi analyzer cho multilingual names. Team build `products-v2`, backfill, replay changes, validate relevance rồi switch alias mà API không đổi endpoint.

## 6. Failure scenario & troubleshooting

**Symptom** → sau cutover thiếu products mới cập nhật. **Evidence** → documents thay đổi trong reindex window không tồn tại ở v2. **Hypothesis** → migration thiếu delta synchronization. **Diagnosis** → compare primary DB change sequence với indexed versions. **Fix** → CDC/outbox replay hoặc dual-write có kiểm soát. **Verification** → count/version sampling và search acceptance tests.

## 7. Common mistakes

Coi Elasticsearch là source of truth; reindex nhưng không xử lý concurrent writes; xóa v1 ngay sau switch; không test analyzer/relevance.

## 8. Alternatives

In-place mapping additions khi compatible. Blue/green application index strategy tương tự nhưng cần ownership rõ.

## 9. Trade-offs

### Advantages
Safe cutover/rollback, application decoupled khỏi physical index.
### Costs / Risks
Tạm thời cần double storage và synchronization pipeline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu alias khác physical index.
### Middle
Tạo/reindex/switch an toàn.
### Senior
Giải concurrent change và validation.
### Technical Lead / Architect
Thiết kế search index lifecycle và recovery từ primary source.

## 11. Key takeaway

- Alias là deployment boundary cho search schema.
- Reindex không đủ nếu production vẫn đang ghi dữ liệu.
- Giữ rollback path cho tới khi validation hoàn tất.

# 5. Modular Monolith: module boundary trước khi nghĩ đến Microservices

## 1. What is it?

Modular Monolith là một deployable application nhưng chia business capability thành modules có boundary/dependency rõ ràng. Module không đồng nghĩa folder hay technical layer.

## 2. Why does it exist?

Monolith không có boundaries dễ thành tightly coupled “big ball of mud”. Microservices giải deployment/ownership isolation nhưng thêm network, consistency và operational cost. Modular Monolith giữ process đơn giản trong khi ép business boundaries.

## 3. How does it work?

```text
Single deployment
 ├─ Orders module -> owns Orders model
 ├─ Catalog module -> owns Catalog model
 └─ Identity module -> owns Identity model
```

Cross-module access đi qua explicit contract; tránh module khác query trực tiếp internal tables/classes.

## 4. Practical implementation

Trong .NET, mỗi module có thể là assembly/project với public contracts tối thiểu và internal implementation. Architecture tests có thể ngăn dependency trái phép.

## 5. Real production scenario

E-commerce team có Orders, Catalog, Promotions. Scale hiện tại không cần independent deployment. Module boundaries cho phép team phát triển domain độc lập mà không gánh Service Bus, distributed tracing và eventual consistency cho mọi call.

## 6. Failure scenario & troubleshooting

**Symptom** → modules tồn tại trên solution diagram nhưng mọi module cùng đọc chung tables/classes. **Evidence** → dependency graph dày đặc. **Hypothesis** → cosmetic modularization. **Diagnosis** → analyze references/data ownership. **Fix** → contract + ownership boundaries. **Verification** → architecture tests và change-impact review.

## 7. Common mistakes

Một module cho mỗi CRUD entity; shared project chứa toàn domain; generic repository xuyên modules; thêm MediatR rồi gọi đó là architecture.

## 8. Alternatives

Simple layered monolith đủ cho domain nhỏ. Microservices hợp lý khi cần independent deployment/scaling/ownership và team chịu được operational complexity.

## 9. Trade-offs

### Advantages
Boundary tốt với deployment đơn giản.
### Costs / Risks
Không có process isolation; discipline phải được enforce trong codebase.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu module theo business capability.
### Middle
Tôn trọng public contracts.
### Senior
Thiết kế data/transaction ownership.
### Technical Lead / Architect
Quyết định khi nào boundary cần trở thành network boundary.

## 11. Key takeaway

- Architecture là boundary, không phải folder tree.
- Modular Monolith thường là bước hợp lý trước Microservices.
- Data ownership quyết định boundary mạnh hơn naming convention.

# 6. Distributed timeout budget: deadline phải co lại qua từng dependency hop

## 1. What is it?

Timeout budget là tổng thời gian request được phép tiêu tốn; mỗi downstream call phải dùng phần budget còn lại thay vì mỗi layer tự đặt timeout dài độc lập.

## 2. Why does it exist?

Client chờ 3 giây nhưng API gọi service A timeout 10 giây, service A gọi DB 30 giây: hệ thống tiếp tục làm work vô ích lâu sau khi caller đã bỏ cuộc.

## 3. How does it work?

```text
Client budget 3s
 -> API overhead 100ms
 -> Service A gets <= 2.9s
 -> DB gets remaining budget
```

Retries cũng tiêu budget; ba attempts x 2 giây không phù hợp request deadline 3 giây.

## 4. Practical implementation

Dùng linked cancellation token/deadline context và đặt per-attempt timeout nhỏ hơn remaining end-to-end deadline. Retry chỉ operation an toàn/idempotent.

## 5. Real production scenario

Checkout có SLO 2 giây. Inventory timeout 1.5 giây rồi payment timeout thêm 3 giây làm caller timeout trước server. Budget-based design dừng flow sớm và tránh zombie work.

## 6. Failure scenario & troubleshooting

**Symptom** → client thấy timeout 5 giây nhưng server traces kéo dài 30 giây. **Evidence** → dependency spans tiếp tục sau client disconnect. **Hypothesis** → independent timeout configuration. **Diagnosis** → trace critical path/deadlines. **Fix** → propagate deadline/cancellation. **Verification** → fault injection downstream latency.

## 7. Common mistakes

Timeout giống nhau ở mọi hop; retry không tính budget; timeout quá ngắn theo average thay vì tail latency; retry non-idempotent operation.

## 8. Alternatives

Asynchronous workflow tách khỏi request deadline cho long-running operations. Queueing phù hợp khi caller không cần synchronous completion.

## 9. Trade-offs

### Advantages
Bounded latency và giảm wasted work.
### Costs / Risks
Aggressive deadlines có thể giảm success rate khi dependency tạm chậm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu timeout là finite budget.
### Middle
Configure timeout/cancellation đúng.
### Senior
Thiết kế retry trong remaining budget.
### Technical Lead / Architect
Phân bổ latency budget theo SLO và dependency criticality.

## 11. Key takeaway

- Timeout phải được reasoning end-to-end.
- Retry tiêu latency budget.
- Long-running work thường nên rời synchronous request path.

# 7. Azure Service Bus lock renewal và duplicate processing

## 1. What is it?

Ở Peek-Lock mode, consumer nhận message với lock tạm thời. Nếu processing chưa xong trước lock expiry, message có thể được broker giao lại dù consumer đầu tiên vẫn đang chạy.

## 2. Why does it exist?

Broker cần recovery khi consumer crash. Permanent ownership sẽ làm message mắc kẹt; finite lock hỗ trợ at-least-once delivery.

## 3. How does it work?

```text
Consumer A receives + lock
 -> processing slow
 -> lock expires
Consumer B receives same message
A may still finish
B may also finish
```

Auto lock renewal kéo dài lock nhưng không tạo exactly-once semantics.

## 4. Practical implementation

Handler nên idempotent dựa trên stable message/business ID; configure `MaxAutoLockRenewalDuration` theo expected processing, đồng thời tránh handler vô hạn.

## 5. Real production scenario

Image processing thường 20 giây nhưng đôi lúc 3 phút. Lock 60 giây hết hạn làm hai workers cùng update status/send notification.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate side effects và `MessageLockLostException`. **Evidence** → processing duration vượt lock/renewal hoặc transient renewal failure. **Hypothesis** → handler duration không phù hợp lock semantics. **Diagnosis** → correlate delivery count, lock loss, processing duration. **Fix** → idempotency + renewal hoặc tách work. **Verification** → inject slow processing vượt initial lock.

## 7. Common mistakes

Tin `CompleteMessageAsync` bảo đảm message chỉ chạy một lần; side effect không idempotent; lock renewal vô hạn; concurrency quá cao làm handler chậm thêm.

## 8. Alternatives

Chunk long work, durable workflow hoặc lưu work state rồi ack message sớm nếu semantics cho phép.

## 9. Trade-offs

### Advantages
Peek-Lock hỗ trợ crash recovery.
### Costs / Risks
Duplicate delivery là normal condition phải thiết kế xử lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu receive không đồng nghĩa ownership vĩnh viễn.
### Middle
Settle message đúng và đọc delivery count.
### Senior
Thiết kế idempotency/lock renewal/failure recovery.
### Technical Lead / Architect
Quyết định message granularity và long-running workflow boundary.

## 11. Key takeaway

- Lock renewal không thay idempotency.
- At-least-once nghĩa là duplicate phải được dự kiến.
- Handler duration là một phần messaging design.

# 8. Application Insights dependency tracing: điều tra p99 thay vì nhìn average

## 1. What is it?

Dependency telemetry ghi các outbound operations như SQL/HTTP cùng duration, success và trace correlation. Nó cho phép phân rã request latency theo dependency spans.

## 2. Why does it exist?

Average 120 ms có thể che 1% requests mất 8 giây. Production UX thường bị chi phối bởi tail latency và dependency outliers.

## 3. How does it work?

```text
Request span 4.2s
 ├─ application 50ms
 ├─ SQL 80ms
 └─ HTTP inventory 4.0s
```

Correlation cho phép đi từ p99 metric tới traces cụ thể rồi dependency evidence.

## 4. Practical implementation

Theo dõi p50/p95/p99 theo route và dependency; dùng operation/trace ID để correlate. Tránh dimensions cardinality không bounded.

## 5. Real production scenario

Checkout average vẫn 300 ms nhưng p99 lên 5 giây. Traces cho thấy một inventory region có periodic 4.5-second responses; application CPU/SQL bình thường.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard “healthy” nhưng users báo chậm. **Evidence** → average bình thường, p99 cao. **Hypothesis** → tail dependency latency. **Diagnosis** → percentile → slow traces → dependency breakdown. **Fix** → dependency timeout/routing/capacity. **Verification** → p99 và error rate sau remediation.

## 7. Common mistakes

Chỉ dashboard average; log text không correlation; sampling làm mất critical errors; metric labels chứa IDs; alert trên CPU nhưng không trên user-facing SLI.

## 8. Alternatives

OpenTelemetry vendor-neutral instrumentation có thể export tới nhiều backends. Logs hữu ích cho events nhưng không thay traces/metrics.

## 9. Trade-offs

### Advantages
Nhanh localize distributed latency.
### Costs / Risks
Telemetry volume/cost, sampling và instrumentation quality.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt request và dependency telemetry.
### Middle
Dùng trace để tìm slow span.
### Senior
Reason bằng percentiles và critical path.
### Technical Lead / Architect
Định nghĩa SLI/SLO, sampling và telemetry cost policy.

## 11. Key takeaway

- Average latency thường không đủ.
- Trace phải trả lời “thời gian mất ở đâu?”.
- Observability tốt dẫn tới hypothesis có evidence.

# 9. OAuth/OIDC `state`, `nonce` và PKCE: ba cơ chế giải ba threat khác nhau

## 1. What is it?

`state`, `nonce` và PKCE thường xuất hiện cùng authorization flow nhưng không thay thế nhau. `state` liên kết authorization response với client-initiated transaction; OIDC `nonce` liên kết ID Token với authentication request; PKCE chứng minh client đổi code là client đã bắt đầu authorization request.

## 2. Why does it exist?

Redirect-based authentication đi qua browser/front channel, nơi response/code có thể bị mix-up, replay hoặc interception tùy threat model.

## 3. How does it work?

```text
Client creates state + nonce + code_verifier
 -> authorize(state, nonce, code_challenge)
 <- callback(code, state)
Client validates state
 -> token endpoint(code + code_verifier)
 <- ID token containing nonce
Client validates token + nonce
```

## 4. Practical implementation

Dùng standards-compliant OIDC middleware/library thay vì tự build protocol. Validate issuer, audience, signature, lifetime và correlation data; HTTPS bắt buộc.

## 5. Real production scenario

ASP.NET Core app federation qua Entra ID. Team tự viết callback chỉ đọc `code`, không validate correlation. Flow “login được” nhưng thiếu protocol security guarantees mà middleware chuẩn đã cung cấp.

## 6. Failure scenario & troubleshooting

**Symptom** → correlation/nonce validation fail sau load balancing. **Evidence** → cookie/state protection không đọc được ở instance khác. **Hypothesis** → Data Protection keys/cookie configuration không shared. **Diagnosis** → inspect auth logs, callback cookies và key persistence. **Fix** → shared Data Protection configuration/consistent host/proxy settings. **Verification** → cross-instance login test.

## 7. Common mistakes

Tự generate callback protocol; coi PKCE thay `state`; không validate redirect URI; log tokens; tắt correlation validation để “fix login”.

## 8. Alternatives

Backend-for-Frontend có thể giữ tokens khỏi browser nhưng vẫn phải tuân OIDC/OAuth security model. Cookie auth giải session sau login, không thay identity protocol.

## 9. Trade-offs

### Advantages
Standards-based defenses cho redirect flow.
### Costs / Risks
State/cookie/key management phức tạp trong distributed hosting nếu cấu hình sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Biết Authentication khác Authorization.
### Middle
Dùng OIDC middleware đúng.
### Senior
Hiểu threat mỗi mechanism xử lý và troubleshoot distributed callback.
### Technical Lead / Architect
Chọn flow/BFF/federation boundary và không tự phát minh auth protocol.

## 11. Key takeaway

- `state`, `nonce`, PKCE không đồng nghĩa.
- Dùng mature library và giữ validation bật.
- Login thành công không chứng minh flow an toàn.

# 10. CI/CD database migration: expand-and-contract để deploy backward-compatible

## 1. What is it?

Expand-and-contract là migration strategy chia breaking schema change thành các bước tương thích với cả application version cũ và mới trong deployment window.

## 2. Why does it exist?

Rolling/Blue-Green deployment khiến hai app versions có thể chạy đồng thời. Rename/drop column trong một migration atomic về DB nhưng breaking đối với old binaries.

## 3. How does it work?

```text
1. Expand: add new schema, keep old schema
2. Deploy compatible application
3. Backfill / dual-read-write if required
4. Move traffic / verify
5. Contract: remove obsolete schema later
```

## 4. Practical implementation

Ví dụ rename `Name` → `DisplayName`: trước tiên add nullable `DisplayName`, deploy code hỗ trợ cả hai, backfill, chuyển reads/writes, xác minh rồi mới drop `Name` ở release sau.

## 5. Real production scenario

10 App Service instances rolling deploy. Nếu migration drop column trước khi old instances dừng, chúng bắt đầu 500 ngay trong deployment dù new version khỏe.

## 6. Failure scenario & troubleshooting

**Symptom** → errors chỉ xuất hiện trong deployment window. **Evidence** → old app queries removed column. **Hypothesis** → schema migration không backward-compatible. **Diagnosis** → correlate deployment timeline, app version và SQL errors. **Fix** → restore compatible schema/rollback app, sau đó áp expand-contract. **Verification** → chạy old/new binaries cùng schema trong pre-production.

## 7. Common mistakes

Auto-run destructive migrations lúc app startup trên nhiều instances; rename/drop trong một release; long blocking migration giờ cao điểm; rollback binary nhưng schema không rollback-compatible.

## 8. Alternatives

Maintenance window có thể đủ cho hệ thống nhỏ chấp nhận downtime. Feature flags hỗ trợ staged activation nhưng không tự giải schema compatibility.

## 9. Trade-offs

### Advantages
Zero/low-downtime deployment và rollback an toàn hơn.
### Costs / Risks
Temporary schema duplication, backfill và nhiều release steps.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu app và schema versions có thể lệch nhau.
### Middle
Viết additive migrations an toàn.
### Senior
Plan backfill, compatibility và rollback.
### Technical Lead / Architect
Thiết kế deployment contract giữa application, database và release pipeline.

## 11. Key takeaway

- Database schema là deployment contract.
- Breaking migration thường nên tách qua nhiều releases.
- Rollback phải được thiết kế trước deployment, không sau incident.
