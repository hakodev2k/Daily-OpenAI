# 1. .NET `Channels`: bounded backpressure thay vì để producer phá memory

## 1. What is it?

`System.Threading.Channels` cung cấp queue asynchronous trong process với mô hình producer/consumer. Mental model quan trọng không phải “queue nhanh”, mà là một **concurrency boundary**: producer tạo work, consumer xử lý theo capacity đã kiểm soát. `BoundedChannel` còn biểu diễn backpressure — khi downstream không theo kịp, upstream phải chậm lại hoặc áp dụng policy rõ ràng.

## 2. Why does it exist?

Một `ConcurrentQueue<T>` chỉ giải quyết thread-safe enqueue/dequeue; nó không tự cung cấp asynchronous waiting hay capacity control. Nếu API nhận 10.000 jobs/s nhưng worker xử lý 1.000 jobs/s, queue không giới hạn sẽ biến throughput mismatch thành memory growth. Backpressure làm mismatch này trở thành behavior có chủ đích thay vì incident ngẫu nhiên.

## 3. How does it work?

```text
Producer(s)
    │ WriteAsync
    ▼
Bounded Channel [capacity = N]
    │
    ▼ ReadAllAsync
Consumer(s)
    │
    ▼
Dependency / CPU / I/O
```

Khi channel đầy, `FullMode = Wait` làm `WriteAsync` chờ capacity. Các mode như `DropOldest` chỉ phù hợp khi business semantics cho phép mất dữ liệu.

## 4. Practical implementation

```csharp
var channel = Channel.CreateBounded<EmailJob>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = false
});

await channel.Writer.WriteAsync(job, cancellationToken);

await foreach (var item in channel.Reader.ReadAllAsync(stoppingToken))
{
    await sender.SendAsync(item, stoppingToken);
}
```

Capacity phải xuất phát từ downstream throughput, acceptable queueing latency và memory footprint — không phải một con số tùy ý.

## 5. Real production scenario

Notification API nhận burst 20.000 events sau payroll run. SMTP provider chỉ chịu 200 concurrent requests. Bounded channel giúp web process không tạo 20.000 concurrent sends; consumer concurrency được giới hạn theo capacity thực của provider.

## 6. Failure scenario & troubleshooting

**Symptom** → request enqueue latency tăng và channel luôn đầy.  
**Evidence** → queue depth cao, consumer throughput thấp, dependency latency tăng.  
**Hypothesis** → downstream saturation chứ không phải channel “chậm”.  
**Diagnosis** → đo arrival rate, processing rate, queue wait time và dependency p95.  
**Fix** → giảm producer rate, tăng consumer capacity nếu downstream cho phép, hoặc chuyển workload cần durability sang external queue.  
**Verification** → queue depth quay về steady state và không còn memory growth.

## 7. Common mistakes

Dùng unbounded channel cho workload không giới hạn; tăng consumer count cho đến khi database bị overload; dùng drop mode cho financial/business events; coi in-memory channel là durable queue.

## 8. Alternatives

`SemaphoreSlim` phù hợp khi chỉ cần giới hạn concurrency. Azure Service Bus phù hợp khi cần durability, cross-process delivery và recovery sau process restart. `Channel<T>` mạnh khi workload local, latency thấp và mất queue khi process chết là chấp nhận được.

## 9. Trade-offs

### Advantages

API async tự nhiên, throughput cao, backpressure explicit, producer/consumer decoupling trong process.

### Costs / Risks

Không durable; capacity và shutdown semantics phải được thiết kế; queue có thể che downstream degradation nếu không có metrics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu producer nhanh hơn consumer sẽ tạo backlog.

### Middle

Implement bounded channel, cancellation và graceful completion.

### Senior

Định lượng capacity, consumer concurrency, queue latency và failure semantics.

### Technical Lead / Architect

Quyết định workload nào được phép in-memory và workload nào phải chuyển sang durable messaging; đặt backpressure boundary ở đâu để bảo vệ toàn hệ thống.

## 11. Key takeaway

- Queue không giới hạn chỉ chuyển overload thành memory problem.
- Backpressure là correctness/reliability mechanism, không chỉ performance tuning.
- `Channel<T>` không thay thế durable messaging khi work không được phép mất.

# 2. ASP.NET Core streaming responses: `IAsyncEnumerable<T>`, buffering và cancellation

## 1. What is it?

Streaming response cho phép server tạo và gửi dữ liệu dần thay vì materialize toàn bộ payload trước khi response bắt đầu. Với ASP.NET Core, `IAsyncEnumerable<T>` có thể biểu diễn nguồn dữ liệu được consume theo thời gian. Mental model: giảm **working set và time-to-first-byte**, không mặc định giảm tổng lượng bytes.

## 2. Why does it exist?

Export 500.000 records bằng `ToListAsync()` rồi serialize giữ toàn bộ dataset trong memory. Với nhiều request đồng thời, memory pressure và LOH/GC có thể trở thành bottleneck trước CPU hoặc database.

## 3. How does it work?

```text
Database cursor/query
      │ rows
      ▼
ASP.NET Core serializer
      │ chunks
      ▼
Kestrel / proxy
      │
      ▼
Client
```

Streaming end-to-end chỉ tồn tại nếu các tầng trung gian không buffer toàn bộ response. Reverse proxy, compression hoặc client behavior có thể thay đổi observable result.

## 4. Practical implementation

```csharp
app.MapGet("/api/orders/export", (AppDbContext db, CancellationToken ct) =>
{
    return db.Orders
        .AsNoTracking()
        .OrderBy(x => x.Id)
        .Select(x => new OrderDto(x.Id, x.Total))
        .AsAsyncEnumerable()
        .WithCancellation(ct);
});
```

Với file formats cần seek/finalization phức tạp, streaming strategy có thể khác; không phải serializer nào cũng stream tốt.

## 5. Real production scenario

CRM export lớn trước đây allocate 600 MB/request. Sau khi chuyển sang projection + streaming, working set giảm đáng kể và client bắt đầu nhận data sớm hơn. Database query vẫn phải được tối ưu; streaming không chữa execution plan xấu.

## 6. Failure scenario & troubleshooting

**Symptom** → server memory vẫn tăng dù endpoint “streaming”.  
**Evidence** → trace cho thấy `ToListAsync()` hoặc proxy buffers response.  
**Hypothesis** → pipeline có materialization/buffering hidden.  
**Diagnosis** → kiểm tra allocation profile, response headers, proxy settings và query execution.  
**Fix** → loại bỏ materialization, dùng streaming-compatible serialization, cấu hình proxy phù hợp.  
**Verification** → memory per request ổn định theo payload size và TTFB giảm.

## 7. Common mistakes

Stream entity đang tracking; giữ DbContext quá lâu mà không hiểu connection lifetime; bỏ qua cancellation khi client disconnect; giả định response compression luôn không buffer; dùng streaming cho payload nhỏ làm complexity tăng vô ích.

## 8. Alternatives

Pagination/keyset pagination tốt hơn cho interactive APIs. Background export + Blob Storage tốt hơn cho export rất lớn hoặc cần retry/resume. Streaming phù hợp khi client thực sự consume tuần tự và request lifetime chấp nhận được.

## 9. Trade-offs

### Advantages

Giảm peak memory, TTFB tốt hơn, không cần materialize toàn dataset.

### Costs / Risks

Connection/request sống lâu hơn; partial response khó rollback; proxy/client compatibility và cancellation trở nên quan trọng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt materialize toàn bộ với enumerate từng phần.

### Middle

Implement `IAsyncEnumerable<T>`, projection, `AsNoTracking` và cancellation.

### Senior

Theo dõi connection lifetime, buffering, serialization và partial-failure behavior.

### Technical Lead / Architect

Quyết định streaming, pagination hay asynchronous export dựa trên payload, UX, reliability và infrastructure limits.

## 11. Key takeaway

- Streaming giảm working set nhưng có thể kéo dài resource lifetime.
- Phải kiểm tra toàn pipeline, không chỉ controller code.
- Export rất lớn thường phù hợp background job + object storage hơn request dài.

# 3. EF Core `DbContext` vs Generic Repository: abstraction boundary và query capability

## 1. What is it?

`DbContext` đã cung cấp Unit of Work, identity map/change tracking và query abstraction qua `DbSet<T>`. Generic Repository thường thêm interface như `GetAll`, `Add`, `Delete` lên trên. Câu hỏi kiến trúc đúng không phải “Repository Pattern có tốt không?” mà là **abstraction này che giấu volatility nào và bảo vệ boundary nào?**

## 2. Why does it exist?

Repository trong DDD có giá trị khi biểu diễn collection-like access cho Aggregate và giữ persistence concern khỏi domain/application policy. Nhưng generic CRUD repository thường chỉ mirror EF Core API, làm mất query expressiveness mà không tạo business boundary.

## 3. How does it work?

```text
Application
   │
   ├── direct DbContext ─────► EF Core ─► DB
   │
   └── Domain Repository ────► EF Core ─► DB

Generic IRepository<T>
   └── nếu chỉ proxy DbSet<T>, abstraction value rất thấp
```

Repository boundary hữu ích khi contract mang semantic nghiệp vụ: `GetOpenOrderForCheckoutAsync`, không phải `GetById<T>` cho mọi entity.

## 4. Practical implementation

```csharp
public interface IOrderRepository
{
    Task<Order?> GetForCheckoutAsync(OrderId id, CancellationToken ct);
}

internal sealed class EfOrderRepository(AppDbContext db) : IOrderRepository
{
    public Task<Order?> GetForCheckoutAsync(OrderId id, CancellationToken ct) =>
        db.Orders
          .Include(x => x.Lines)
          .SingleOrDefaultAsync(x => x.Id == id, ct);
}
```

Read-only reporting query có thể dùng `DbContext`/query service trực tiếp thay vì ép qua aggregate repository.

## 5. Real production scenario

Một enterprise app có `IRepository<T>` với `GetAll()`. Application layer liên tục thêm `Include`, specification và expression plumbing để lấy dữ liệu. Abstraction cuối cùng phức tạp hơn EF Core và vẫn phụ thuộc LINQ semantics. Thay generic repository bằng direct query services và domain-specific repository làm boundary rõ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → query đơn giản cần nhiều extension abstractions và khó biết SQL thực tế.  
**Evidence** → repository expose `IQueryable` hoặc hàng chục overloads.  
**Hypothesis** → abstraction đang mirror ORM thay vì encapsulate business persistence boundary.  
**Diagnosis** → map từng method với business use case và dependency direction.  
**Fix** → bỏ generic wrapper nơi không tạo value; giữ repository theo aggregate/use case khi cần.  
**Verification** → query code ngắn hơn, SQL dễ inspect, tests tập trung vào behavior.

## 7. Common mistakes

Repository chỉ để “có Clean Architecture”; mock repository thay cho integration test database; expose `IQueryable` rồi tuyên bố persistence đã abstract; generic CRUD cho mọi aggregate phá invariants.

## 8. Alternatives

Direct `DbContext` phù hợp CRUD/application đơn giản. Domain-specific Repository phù hợp DDD aggregate. Query Object/Specification hữu ích khi query logic thực sự tái sử dụng và phức tạp.

## 9. Trade-offs

### Advantages

Repository đúng boundary có thể cô lập domain persistence semantics và test application policy dễ hơn.

### Costs / Risks

Abstraction thừa làm mất ORM capability, tăng boilerplate và che execution behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbContext` không chỉ là database connection.

### Middle

Viết query/projection hiệu quả và repository semantic khi được yêu cầu.

### Senior

Nhận diện abstraction leakage và quyết định query nào thuộc repository, query service hay trực tiếp persistence layer.

### Technical Lead / Architect

Đặt persistence boundary dựa trên domain complexity, test strategy và change pressure — không dựa trên template architecture.

## 11. Key takeaway

- Không cần wrap `DbContext` chỉ vì tên “Repository Pattern”.
- Abstraction tốt phải che volatility hoặc biểu diễn business boundary.
- Generic CRUD repository thường có value thấp trong EF Core systems.

# 4. SQL Server composite indexes: key order, selectivity và execution-plan reasoning

## 1. What is it?

Composite index có nhiều key columns theo thứ tự xác định. Mental model: B-tree được sắp theo **key sequence**, nên `(TenantId, CreatedAt)` không tương đương `(CreatedAt, TenantId)` cho mọi query.

## 2. Why does it exist?

Queries thường filter/sort theo nhiều columns. Một index phù hợp có thể giảm pages phải đọc, hỗ trợ seek và tránh sort. Nhưng mỗi index cũng tăng storage và write maintenance.

## 3. How does it work?

Với index:

```sql
CREATE INDEX IX_Orders_Tenant_CreatedAt
ON dbo.Orders(TenantId, CreatedAt DESC)
INCLUDE (Status, Total);
```

Query `WHERE TenantId=@tenant ORDER BY CreatedAt DESC` có access path tự nhiên. Query chỉ filter `CreatedAt` có thể không tận dụng leading key tốt như mong muốn.

## 4. Practical implementation

```sql
SELECT Id, CreatedAt, Status, Total
FROM dbo.Orders
WHERE TenantId = @TenantId
  AND CreatedAt < @Cursor
ORDER BY CreatedAt DESC
OFFSET 0 ROWS FETCH NEXT 50 ROWS ONLY;
```

Đánh giá actual execution plan, logical reads và row estimates trước/sau thay đổi; đừng chỉ nhìn elapsed time một lần.

## 5. Real production scenario

Multi-tenant order API có 80 triệu rows. Index riêng `TenantId` và `CreatedAt` khiến optimizer phải đọc/sort nhiều hơn. Composite index theo access pattern giảm I/O mạnh, nhưng chỉ sau khi team xác nhận query shape và data distribution.

## 6. Failure scenario & troubleshooting

**Symptom** → query vẫn scan dù “đã có index”.  
**Evidence** → execution plan, high logical reads, predicate không phù hợp leading key hoặc implicit conversion.  
**Hypothesis** → key order/query shape/statistics không phù hợp.  
**Diagnosis** → xem seek predicates, residual predicates, estimates và sort operator.  
**Fix** → chỉnh query/index dựa trên workload; cập nhật statistics khi evidence cho thấy cần.  
**Verification** → compare plan, reads, CPU và p95 dưới representative load.

## 7. Common mistakes

Đặt column selectivity cao nhất luôn ở đầu mà bỏ qua equality/range/order pattern; INCLUDE quá nhiều; tạo index cho từng slow query; bỏ qua write amplification; test trên dataset nhỏ.

## 8. Alternatives

Filtered index hữu ích cho subset ổn định. Columnstore phù hợp analytics khác OLTP B-tree. Đôi khi sửa access pattern/query tốt hơn thêm index.

## 9. Trade-offs

### Advantages

Giảm I/O, hỗ trợ seek/sort và có thể cover query.

### Costs / Risks

Storage, insert/update cost, maintenance và optimizer complexity tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu composite key có thứ tự.

### Middle

Đọc basic execution plan và logical reads.

### Senior

Reason về equality/range/order, cardinality estimates, covering và write cost.

### Technical Lead / Architect

Quản lý indexing theo workload toàn hệ thống thay vì tối ưu từng query cô lập.

## 11. Key takeaway

- Index design bắt đầu từ access pattern và execution evidence.
- Key order quyết định khả năng seek/order hữu ích.
- Read gain phải được cân với write/storage cost.

# 5. Redis outage design: cache failure không được mặc định trở thành application outage

## 1. What is it?

Redis thường là acceleration layer, nhưng khi mọi request bắt buộc phải đọc Redis trước khi tiếp tục, cache vô tình trở thành critical dependency. Mental model: cache failure policy phải được thiết kế theo **correctness và downstream capacity**, không mặc định fail-open hay fail-closed.

## 2. Why does it exist?

Cache giảm database load, nhưng outage Redis có thể tạo cache miss đồng loạt. Nếu tất cả requests fallback database, database có thể bị stampede và outage lan rộng.

## 3. How does it work?

```text
Request
  │
  ▼
Redis ── healthy ─► cached response
  │ unavailable
  ▼
Fallback policy
  ├─ DB with bounded concurrency
  ├─ stale/local cache
  └─ degrade/reject noncritical work
```

Fallback phải có budget; “just query DB” không phải resilience strategy nếu cache đang absorb 90% traffic.

## 4. Practical implementation

```csharp
try
{
    var cached = await cache.GetStringAsync(key, ct);
    if (cached is not null) return Deserialize(cached);
}
catch (RedisConnectionException ex)
{
    logger.LogWarning(ex, "Redis unavailable for {Key}", key);
}

await dbFallbackGate.WaitAsync(ct);
try { return await LoadFromDatabaseAsync(ct); }
finally { dbFallbackGate.Release(); }
```

`SemaphoreSlim` ở một instance chỉ bảo vệ local concurrency; distributed fleet vẫn cần capacity planning.

## 5. Real production scenario

Product catalog có 95% cache hit. Redis cluster outage làm traffic SQL tăng 20x. Nếu fallback không bounded, connection pool cạn và checkout cũng chết dù catalog cache vốn chỉ là optimization.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis errors trước, sau đó SQL latency/connection timeout tăng.  
**Evidence** → cache hit rate về 0, DB QPS tăng đột biến.  
**Hypothesis** → fallback amplification.  
**Diagnosis** → correlate Redis availability, DB load, request path và retry counts.  
**Fix** → bounded fallback, stale data nếu business cho phép, circuit breaking và traffic shedding.  
**Verification** → chaos test Redis outage mà critical paths vẫn trong SLO đã định.

## 7. Common mistakes

Retry Redis nhiều lần trên mỗi request; fallback DB không giới hạn; cache session/auth-critical state mà không có availability design; alert chỉ theo Redis CPU mà không theo hit rate/dependency errors.

## 8. Alternatives

`IMemoryCache` giảm remote dependency nhưng không shared và có consistency khác. Không cache là lựa chọn tốt nếu database đủ capacity và complexity không đáng giá.

## 9. Trade-offs

### Advantages

Redis giảm latency và origin load mạnh cho workload phù hợp.

### Costs / Risks

Tạo consistency, invalidation và outage mode mới; fallback có thể nguy hiểm hơn failure trực tiếp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache có thể unavailable và data có thể stale.

### Middle

Implement timeout/fallback và log dependency failures.

### Senior

Thiết kế stampede protection, fallback budget và chaos/load verification.

### Technical Lead / Architect

Quyết định Redis có phải critical dependency hay optimization; xác định degradation contract khi cache mất hoàn toàn.

## 11. Key takeaway

- Cache outage có thể khuếch đại thành database outage.
- Fallback cần capacity limit và business semantics rõ.
- Đôi khi hệ thống đơn giản hơn nếu không cache.

# 6. Microservices Bulkhead Pattern: cô lập dependency saturation và failure propagation

## 1. What is it?

Bulkhead chia resource/concurrency thành các vùng độc lập để một dependency hoặc workload lỗi không chiếm toàn bộ capacity. Tên đến từ khoang kín trên tàu: một khoang ngập không làm cả tàu chìm.

## 2. Why does it exist?

Nếu Orders API dùng cùng outbound connection/concurrency budget cho Payment, Reviews và Recommendations, một Recommendations service chậm có thể giữ hết request capacity và làm checkout timeout dù Payment khỏe.

## 3. How does it work?

```text
Orders API
 ├─ Payment pool        [critical]
 ├─ Inventory pool      [critical]
 └─ Recommendation pool [optional]
```

Bulkhead có thể là concurrency limiter, separate queue, process, connection pool hoặc service boundary. Nó không nhất thiết yêu cầu Microservices.

## 4. Practical implementation

```csharp
private readonly SemaphoreSlim _recommendationGate = new(20);

public async Task<Result?> GetRecommendationsAsync(CancellationToken ct)
{
    if (!await _recommendationGate.WaitAsync(TimeSpan.FromMilliseconds(50), ct))
        return null;

    try { return await client.GetAsync(ct); }
    finally { _recommendationGate.Release(); }
}
```

Production policy nên kết hợp timeout và metrics; local semaphore chỉ là một implementation form.

## 5. Real production scenario

Product page gọi Reviews service optional. Reviews latency tăng 10 s. Không bulkhead, web instances tích tụ pending calls và ThreadPool/socket pressure. Với bulkhead + short timeout, page vẫn trả product data nhưng ẩn reviews tạm thời.

## 6. Failure scenario & troubleshooting

**Symptom** → một dependency lỗi kéo error rate của endpoint không liên quan tăng.  
**Evidence** → traces cho thấy shared resource saturation và queue wait.  
**Hypothesis** → failure propagation qua shared capacity.  
**Diagnosis** → map critical path và resource pools.  
**Fix** → isolate concurrency/queues, timeout và degrade optional feature.  
**Verification** → fault injection dependency và xác nhận critical flow vẫn đạt SLO.

## 7. Common mistakes

Bulkhead capacity quá lớn nên không còn isolation; mỗi dependency một policy phức tạp không có metrics; retry bên trong bulkhead làm saturation nặng hơn; dùng service split thay vì resource isolation thực sự.

## 8. Alternatives

Circuit Breaker giảm calls khi dependency đang fail; Rate Limiter bảo vệ admission; timeout giới hạn duration. Chúng bổ sung chứ không thay thế hoàn toàn Bulkhead.

## 9. Trade-offs

### Advantages

Giới hạn blast radius và bảo vệ critical workloads.

### Costs / Risks

Capacity bị phân mảnh; tuning khó; policy complexity và telemetry tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu shared resource có thể truyền failure giữa features.

### Middle

Implement bounded concurrency và timeout.

### Senior

Phân tích saturation, queueing và retry interaction.

### Technical Lead / Architect

Xác định criticality tiers, capacity budgets và nơi isolation tạo business value thật.

## 11. Key takeaway

- Bulkhead giới hạn blast radius bằng resource isolation.
- Circuit Breaker, timeout và Bulkhead giải các failure dimensions khác nhau.
- Isolation phải dựa trên criticality và capacity evidence.

# 7. Azure Functions scale-out: duplicate execution, idempotency và concurrency control

## 1. What is it?

Azure Functions có thể scale nhiều instances để xử lý workload. Mental model: scale-out tăng **number of concurrent executors**, không tạo guarantee rằng business event chỉ được xử lý đúng một lần.

## 2. Why does it exist?

Event-driven workloads có burst lớn. Serverless scale giúp tăng consumers mà không quản lý fixed fleet, nhưng messaging thường có at-least-once semantics; retries, lock loss và host restart có thể tạo redelivery.

## 3. How does it work?

```text
Service Bus Queue
      │
      ├── Function instance A
      ├── Function instance B
      └── Function instance C

same logical event may be redelivered after failure
```

Scale controller dựa trên trigger/workload signals; downstream database/API vẫn có finite capacity.

## 4. Practical implementation

```csharp
public async Task Run(
    [ServiceBusTrigger("payments")] PaymentMessage message,
    CancellationToken ct)
{
    if (await inbox.ExistsAsync(message.EventId, ct))
        return;

    await processor.ProcessAsync(message, ct);
    await inbox.MarkProcessedAsync(message.EventId, ct);
}
```

Trong thực tế deduplication và business mutation cần transaction boundary phù hợp để tránh crash giữa “process” và “mark processed”.

## 5. Real production scenario

Invoice queue tăng từ 100 lên 100.000 messages. Functions scale nhanh, nhưng SQL Database chỉ chịu 300 concurrent writes. Không concurrency budget, serverless scale biến queue backlog thành DB saturation.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate invoices hoặc SQL throttling khi backlog tăng.  
**Evidence** → cùng event ID xuất hiện nhiều invocation; DB connections/DTU/vCore saturation.  
**Hypothesis** → at-least-once + uncontrolled scale.  
**Diagnosis** → inspect trigger retries, lock duration, invocation IDs, DB telemetry.  
**Fix** → idempotency/inbox, host concurrency tuning, batch/DB capacity alignment.  
**Verification** → replay duplicate messages và burst load mà chỉ một business effect xảy ra.

## 7. Common mistakes

Giả định Functions “exactly once”; dùng distributed lock cho mọi message thay vì idempotent design; scale consumers không xét downstream; poison message retry vô hạn; không theo dõi DLQ.

## 8. Alternatives

Worker Service/Container Apps phù hợp khi cần control concurrency/lifecycle mạnh. Functions tốt cho event-driven workload với operational model phù hợp và execution semantics được hiểu rõ.

## 9. Trade-offs

### Advantages

Elastic scale, trigger integration và ít host management.

### Costs / Risks

Cold start trong một số workload, duplicate delivery, downstream saturation và platform-specific tuning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một queue message có thể được delivery lại.

### Middle

Implement idempotent handler, retry/DLQ handling.

### Senior

Tune concurrency theo downstream capacity và trace duplicate execution.

### Technical Lead / Architect

Quyết định Functions hay Worker/Container dựa trên workload shape, cost, control và operational requirements.

## 11. Key takeaway

- Scale-out không thay thế idempotency.
- Consumer capacity phải tôn trọng downstream capacity.
- At-least-once delivery phải được xem là normal behavior.

# 8. Blue-Green deployment: backward compatibility giữa application và database

## 1. What is it?

Blue-Green giữ hai application environments: một đang phục vụ traffic, một chứa release mới. Cutover chuyển traffic sang environment mới. Mental model: application có thể đổi nhanh, nhưng **shared state/database thường không đổi atomically cùng traffic switch**.

## 2. Why does it exist?

Deploy in-place làm rollback khó khi binary/config đang được thay đổi. Blue-Green cho phép pre-validation và traffic cutover/rollback nhanh hơn.

## 3. How does it work?

```text
          ┌── Blue v1 ──┐
Traffic ──┤              ├── Shared DB
          └── Green v2 ─┘

before cutover: Blue active
cutover: router -> Green
```

Trong transition, schema phải tương thích với cả v1 và v2 nếu cả hai có thể chạy.

## 4. Practical implementation

Thay vì rename/drop column ngay:

```text
Release A: add NewColumn, app hiểu old + new
Release B: migrate/backfill data
Release C: app chỉ dùng NewColumn
Release D: drop OldColumn
```

Đây là expand-contract migration.

## 5. Real production scenario

Green release đổi `Customer.Name` thành `FirstName/LastName`. Nếu migration drop `Name` trước cutover, Blue đang active sẽ fail. Expand-contract cho phép hai versions coexist trong deployment window.

## 6. Failure scenario & troubleshooting

**Symptom** → rollback application thành công nhưng old version crash với schema mới.  
**Evidence** → SQL errors về missing column/changed constraint.  
**Hypothesis** → database migration không backward-compatible.  
**Diagnosis** → compare version contracts và migration order.  
**Fix** → forward-compatible schema, delayed destructive migration.  
**Verification** → compatibility tests chạy cả old/new binaries trên transitional schema.

## 7. Common mistakes

Gọi Blue-Green là zero-risk; destructive migration cùng release; environment config drift; Green smoke test không dùng realistic dependencies; không định nghĩa rollback window.

## 8. Alternatives

Canary giảm blast radius bằng gradual traffic. Deployment slots là managed variant phù hợp App Service. Rolling deployment tiết kiệm duplicate environment nhưng coexist versions vẫn tạo compatibility requirement.

## 9. Trade-offs

### Advantages

Fast cutover/rollback và pre-production validation.

### Costs / Risks

Duplicate environment cost, config drift và database compatibility complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Blue và Green là hai runnable versions.

### Middle

Biết smoke test, cutover và rollback flow.

### Senior

Thiết kế expand-contract migrations và observability gates.

### Technical Lead / Architect

Chọn deployment strategy dựa trên blast radius, state model, RTO và operational maturity.

## 11. Key takeaway

- Traffic switch nhanh không làm database rollback tự động.
- Backward-compatible schema là điều kiện quan trọng cho safe deployment.
- Deployment strategy phải bao gồm validation và rollback criteria.

# 9. React stale closure: async UI state, race condition và API correctness

## 1. What is it?

JavaScript closure giữ references/values theo lexical render context. Trong React function components, async callback có thể quan sát state từ một render cũ. Mental model: mỗi render tạo một snapshot logic; callback chạy sau có thể đang dùng snapshot không còn current.

## 2. Why does it exist?

UI có network requests, timers và event callbacks chạy sau render. Nếu callback giả định state captured luôn mới nhất, user interaction nhanh có thể tạo race và hiển thị data sai.

## 3. How does it work?

```text
Render A: query = "car"
  └─ request A starts
Render B: query = "cars"
  └─ request B starts
request B returns -> correct UI
request A returns later -> overwrites with stale result
```

Đây là frontend concurrency problem dù JavaScript execution single-threaded ở event-loop level.

## 4. Practical implementation

```tsx
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    const response = await fetch(`/api/search?q=${encodeURIComponent(query)}`, {
      signal: controller.signal
    });
    const data = await response.json();
    setResults(data);
  }

  load().catch(e => {
    if (e.name !== "AbortError") throw e;
  });

  return () => controller.abort();
}, [query]);
```

Cancellation giảm stale response race và work vô ích ở backend nếu request abort được propagate.

## 5. Real production scenario

Automotive marketplace search-as-you-type: user gõ `bmw`, rồi `bmw x5`. Request đầu chậm hơn request sau và overwrite result. User thấy list không khớp query hiện tại dù API trả hoàn toàn đúng cho từng request.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị kết quả của input cũ.  
**Evidence** → DevTools Network cho thấy response order khác request order.  
**Hypothesis** → stale async update.  
**Diagnosis** → correlate request query với state khi response commit.  
**Fix** → abort previous request hoặc sequence/version guard.  
**Verification** → throttle network và rapid-input test.

## 7. Common mistakes

Thiếu dependencies trong `useEffect`; ignore ESLint hook warnings mà không hiểu reason; chỉ debounce nhưng không handle out-of-order response; catch `AbortError` như production failure.

## 8. Alternatives

Data libraries như TanStack Query cung cấp caching/request lifecycle nhưng vẫn cần hiểu query keys và stale semantics. Sequence IDs có thể dùng khi API/client không hỗ trợ cancellation.

## 9. Trade-offs

### Advantages

Cancellation giảm stale updates và wasted network/backend work.

### Costs / Risks

Lifecycle logic phức tạp hơn; abort không rollback server-side side effect đã commit, nên mutation vẫn cần idempotency/correct API semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async response có thể về không theo thứ tự request.

### Middle

Implement effect cleanup/cancellation và dependency đúng.

### Senior

Phân biệt UI race với backend consistency và thiết kế mutation semantics an toàn.

### Technical Lead / Architect

Chuẩn hóa frontend data-access patterns, cancellation và observability để race không được xử lý tùy tiện ở từng component.

## 11. Key takeaway

- UI async code có race conditions dù JavaScript không chạy business callbacks song song như threads.
- Debounce không tự giải quyết out-of-order responses.
- Request cancellation nên nối với backend cancellation khi có thể.

# 10. Architecture Decision Record: lưu engineering context thay vì chỉ lưu quyết định

## 1. What is it?

Architecture Decision Record (ADR) là tài liệu ngắn ghi một quyết định kiến trúc, context, alternatives và consequences. Mental model: ADR không phải architecture specification; nó là **decision history** giúp người đến sau hiểu “vì sao hệ thống thành như vậy”.

## 2. Why does it exist?

Code cho biết hệ thống đang làm gì nhưng hiếm khi cho biết tại sao team chọn PostgreSQL thay Cosmos DB, vì sao không dùng Microservices, hoặc constraint nào từng tồn tại. Khi context mất, team dễ đảo lại quyết định cũ hoặc gọi intentional trade-off là technical debt.

## 3. How does it work?

```text
Context / forces
      │
      ▼
Options considered
      │
      ▼
Decision
      │
      ▼
Consequences + revisit triggers
```

ADR nên version cùng repository và có status như Proposed, Accepted, Superseded.

## 4. Practical implementation

```markdown
# ADR-012: Keep Orders and Inventory in Modular Monolith

Status: Accepted

## Context
Current load does not require independent scaling; team has one deployment unit.

## Decision
Keep module boundaries in-process and prohibit cross-module table access.

## Consequences
Lower operational cost; no independent deployment yet.

## Revisit when
Independent release ownership or scaling becomes a measured requirement.
```

Điểm quan trọng là decision drivers và revisit criteria, không phải prose dài.

## 5. Real production scenario

Hai năm sau, engineer hỏi tại sao không đưa Elasticsearch làm primary catalog store. ADR cũ cho thấy transactional consistency và operational skill constraints là lý do. Team có thể kiểm tra constraints còn đúng không thay vì tranh luận lại từ đầu.

## 6. Failure scenario & troubleshooting

**Symptom** → repository có 80 ADR nhưng không ai tin chúng.  
**Evidence** → status không cập nhật, quyết định code khác tài liệu.  
**Hypothesis** → ADR trở thành documentation ceremony.  
**Diagnosis** → review ownership và link giữa PR/design decision với ADR.  
**Fix** → chỉ ADR cho consequential decisions, supersede khi thay đổi, review cùng code/design.  
**Verification** → engineer mới có thể dùng ADR để giải thích current architecture và constraints đúng.

## 7. Common mistakes

Ghi “chúng ta chọn X vì X tốt”; không ghi alternatives; biến ADR thành 20-page design doc; không ghi consequence; dùng ADR để đóng tranh luận vĩnh viễn dù constraints thay đổi.

## 8. Alternatives

README/design docs mô tả current architecture tốt hơn. Wiki tiện collaborative documentation nhưng decision history có thể tách khỏi code version. ADR bổ sung chứ không thay thế các tài liệu này.

## 9. Trade-offs

### Advantages

Giữ context, giảm repeated debate, hỗ trợ onboarding và evolutionary architecture.

### Costs / Risks

Documentation maintenance; ADR stale gây misinformation nếu không có ownership.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết tìm decision context trước khi “refactor architecture”.

### Middle

Ghi alternatives và consequences cho quyết định có ảnh hưởng đáng kể.

### Senior

Xác định decision drivers, operational implications và revisit triggers.

### Technical Lead / Architect

Dùng ADR để quản lý architecture evolution, không biến nó thành approval bureaucracy; biết khi nào quyết định cũ cần supersede.

## 11. Key takeaway

- ADR lưu **why**, không chỉ **what**.
- Decision tốt luôn gắn với context và trade-offs tại thời điểm đó.
- Revisit criteria giúp architecture tiến hóa khi constraints thay đổi.
