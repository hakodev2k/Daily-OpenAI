# 1. C# `ArrayPool<T>` và Large Object Heap: tái sử dụng buffer để giảm allocation mà không tạo memory-corruption bug

## 1. What is it?

`ArrayPool<T>` là cơ chế tái sử dụng arrays giữa nhiều operation thay vì allocate một array mới mỗi lần. Mental model đơn giản:

```text
Allocate mới mỗi request
Request A -> new byte[100 KB] -> GC
Request B -> new byte[100 KB] -> GC
Request C -> new byte[100 KB] -> GC

ArrayPool
Request A -> Rent buffer -> Return
Request B -> Rent lại buffer cũ -> Return
Request C -> Rent lại buffer cũ -> Return
```

Điểm kỹ thuật quan trọng là array lớn có thể đi vào Large Object Heap (LOH). Nhiều allocation lớn lặp lại tạo GC pressure, fragmentation và pause dài hơn. `ArrayPool<T>` giảm số lượng allocation bằng cách giữ một pool các buffers có thể tái sử dụng.

## 2. Why does it exist?

Một API xử lý file upload, JSON serialization hoặc compression có thể cần buffers từ vài chục KB đến vài MB. Nếu mỗi request đều:

```csharp
var buffer = new byte[1024 * 1024];
```

thì dưới tải cao, application tạo rất nhiều objects lớn ngắn hạn. GC phải quản lý lượng memory này dù dữ liệu chỉ tồn tại trong vài milliseconds.

Vấn đề không phải chỉ là memory size. Allocation rate cao kéo theo nhiều GC cycles, CPU overhead và latency tail xấu hơn.

## 3. How does it work?

`ArrayPool<T>.Shared` quản lý các buckets theo kích thước. Khi gọi:

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
```

buffer trả về có thể lớn hơn kích thước yêu cầu. Sau khi dùng xong:

```csharp
ArrayPool<byte>.Shared.Return(buffer);
```

array được đưa lại pool để operation khác dùng.

Điểm quan trọng: pool không bảo đảm buffer sạch. Dữ liệu từ operation trước có thể vẫn còn trong array.

## 4. Practical implementation

Ví dụ đọc stream theo buffer pooled:

```csharp
public static async Task CopyWithPoolAsync(
    Stream source,
    Stream destination,
    CancellationToken cancellationToken)
{
    var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);

    try
    {
        int read;
        while ((read = await source.ReadAsync(
                   buffer.AsMemory(0, buffer.Length),
                   cancellationToken)) > 0)
        {
            await destination.WriteAsync(
                buffer.AsMemory(0, read),
                cancellationToken);
        }
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
    }
}
```

`clearArray: true` có chi phí CPU, nhưng phù hợp khi buffer chứa dữ liệu nhạy cảm như token, document hoặc PII.

## 5. Real production scenario

Một document-processing API nhận PDF 5–20 MB, đọc dữ liệu qua `MemoryStream` và nhiều buffers tạm. Khi load test 200 concurrent uploads, Gen 2 collections tăng mạnh, process memory dao động lớn và p99 latency tăng từ 800 ms lên hơn 4 giây.

Profiling cho thấy allocation lớn tập trung ở các temporary byte arrays. Sau khi chuyển một số hot buffers sang `ArrayPool<byte>` và giới hạn concurrency xử lý file, allocation rate giảm đáng kể và p99 ổn định hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu response đôi lúc chứa bytes không thuộc request hiện tại.

**Evidence** → bug chỉ xuất hiện dưới concurrent load; buffer được `Return` trước khi asynchronous consumer dùng xong.

**Hypothesis** → lifetime của pooled buffer ngắn hơn lifetime thực tế của operation.

**Diagnosis** → kiểm tra nơi buffer được rent/return, các `Task`, callback hoặc stream giữ reference tới buffer sau khi method kết thúc.

**Fix** → chỉ `Return` sau khi mọi consumer hoàn tất; không expose pooled array ra ngoài ownership boundary không kiểm soát.

**Verification** → stress test concurrent operations với data patterns khác nhau và kiểm tra output byte-for-byte.

## 7. Common mistakes

* Assume rented array luôn đúng kích thước yêu cầu.
* Return buffer trước khi async operation hoàn tất.
* Dùng lại buffer sau `Return`.
* Không clear dữ liệu nhạy cảm.
* Pool mọi allocation nhỏ dù không có evidence về GC pressure.
* Tối ưu allocation nhưng bỏ qua concurrency khiến tổng memory vẫn quá lớn.

## 8. Alternatives

`Memory<T>` và `Span<T>` giúp tránh copy nhưng không tự quản lý allocation. `MemoryPool<T>` phù hợp một số pipeline cần ownership rõ hơn. Với workload nhỏ, allocate bình thường đơn giản và an toàn hơn.

## 9. Trade-offs

### Advantages

* Giảm allocation rate.
* Giảm GC pressure trên hot path.
* Hữu ích cho networking, serialization, compression và file processing.

### Costs / Risks

* Ownership phức tạp hơn.
* Có nguy cơ data leakage hoặc corruption nếu return sai thời điểm.
* Pool giữ memory lâu hơn thay vì trả ngay cho GC.
* Optimization có thể không đáng nếu workload nhỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu allocation lớn lặp lại có chi phí và pooled buffer phải `Return` đúng cách.

### Middle

Biết dùng `try/finally`, `Memory<T>`, cancellation và giới hạn lifetime của buffer.

### Senior

Đọc allocation profile, phân biệt LOH pressure với leak, đánh giá security implications của buffer reuse.

### Technical Lead / Architect

Quyết định hot path nào đáng pool, đặt convention về buffer ownership và kết hợp pooling với concurrency limits thay vì tối ưu vi mô riêng lẻ.

## 11. Key takeaway

* `ArrayPool<T>` là công cụ giảm allocation, không phải default cho mọi array.
* Buffer ownership phải rõ ràng; `Return` sai thời điểm có thể gây corruption rất khó debug.
* Chỉ áp dụng sau khi profiler chứng minh allocation/GC thực sự là bottleneck.

# 2. ASP.NET Core `ProblemDetails`: biến exception và validation failure thành error contract ổn định thay vì trả lỗi tùy hứng

## 1. What is it?

`ProblemDetails` là format chuẩn hóa để API mô tả HTTP errors theo một contract có cấu trúc. Mental model:

```text
Internal exception / validation failure
              ↓
       error mapping boundary
              ↓
         ProblemDetails
              ↓
       stable API response
```

Mục tiêu không phải chỉ “JSON đẹp hơn”, mà là tách internal failure details khỏi external error contract.

## 2. Why does it exist?

Một API không chuẩn hóa thường trả lỗi kiểu:

```json
{"message":"Something went wrong"}
```

hoặc endpoint này trả string, endpoint khác trả `{ error: ... }`, endpoint khác lại serialize raw exception.

Client phải viết logic riêng cho từng endpoint. Tệ hơn, raw exception có thể leak stack trace, SQL hoặc implementation details.

## 3. How does it work?

ASP.NET Core có thể map exceptions và validation failures thành `ProblemDetails` với fields như:

```text
type
status
title
detail
instance
extensions
```

Một error contract tốt nên giữ ổn định các machine-readable identifiers, ví dụ:

```json
{
  "type": "https://errors.example.com/order-not-editable",
  "title": "Order cannot be edited",
  "status": 409,
  "code": "order_not_editable",
  "traceId": "..."
}
```

Client không nên parse text `title` để quyết định logic.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();

app.UseExceptionHandler();
```

Custom mapping có thể đặt ở exception handler:

```csharp
public sealed class DomainExceptionHandler : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext httpContext,
        Exception exception,
        CancellationToken cancellationToken)
    {
        if (exception is not OrderNotEditableException domainException)
            return false;

        var problem = new ProblemDetails
        {
            Status = StatusCodes.Status409Conflict,
            Title = "Order cannot be edited",
            Type = "https://errors.example.com/order-not-editable"
        };

        problem.Extensions["code"] = "order_not_editable";
        problem.Extensions["traceId"] = httpContext.TraceIdentifier;

        httpContext.Response.StatusCode = problem.Status.Value;
        await httpContext.Response.WriteAsJsonAsync(problem, cancellationToken);
        return true;
    }
}
```

Không đưa raw exception message ra client nếu message có thể chứa dữ liệu nội bộ.

## 5. Real production scenario

Frontend checkout cần phân biệt: inventory hết, payment bị decline, order conflict và lỗi hệ thống. Trước đây tất cả đều trả `400 Bad Request` cùng chuỗi text khác nhau. Frontend phải kiểm tra `message.includes(...)`, rất dễ vỡ khi backend đổi wording.

Sau khi error contract có `status + code`, frontend xử lý deterministic hơn và backend có thể thay message hiển thị mà không phá behavior.

## 6. Failure scenario & troubleshooting

**Symptom** → production trả `500` với HTML hoặc empty body thay vì JSON error contract.

**Evidence** → exception xảy ra trước/ngoài middleware boundary hoặc response đã bắt đầu ghi.

**Hypothesis** → exception handling middleware đặt sai vị trí hoặc streaming response đã bắt đầu.

**Diagnosis** → kiểm tra middleware order, response-started state, reverse proxy behavior và logs theo trace ID.

**Fix** → đặt exception handler đủ sớm trong pipeline, tránh write response trước khi validation/business operation hoàn tất khi semantics cho phép.

**Verification** → integration test các exception classes, malformed input, auth failure và unexpected exception.

## 7. Common mistakes

* Map mọi exception thành `400`.
* Trả stack trace production.
* Dùng human-readable `message` như machine contract.
* Có hàng chục error shapes khác nhau.
* Dùng `200 OK` rồi nhét `success=false` cho lỗi HTTP thực sự.
* Không có correlation/trace identifier.

## 8. Alternatives

Custom envelope có thể cần trong legacy ecosystem, nhưng nếu không có constraint đặc biệt, HTTP status + `ProblemDetails` thường interoperable và rõ hơn. GraphQL có error model khác vì transport semantics khác REST.

## 9. Trade-offs

### Advantages

* Error response nhất quán.
* Client integration đơn giản hơn.
* Giảm leak implementation detail.
* Tốt cho observability nếu gắn correlation IDs.

### Costs / Risks

* Phải governance error codes.
* Mapping domain error sang HTTP semantics cần engineering judgment.
* Error contract quá chi tiết dễ coupling clients vào implementation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP status và structured error response.

### Middle

Map validation/domain exceptions sang status codes phù hợp và viết integration tests.

### Senior

Thiết kế stable machine codes, security boundary và backward compatibility cho error contracts.

### Technical Lead / Architect

Chuẩn hóa cross-service error model, ownership của error taxonomy và quyết định khi nào transport-specific semantics nên được giữ hoặc abstract.

## 11. Key takeaway

* Error contract là một phần của public API contract.
* `ProblemDetails` giúp chuẩn hóa transport, nhưng mapping domain failure vẫn cần judgment.
* Không để raw exceptions quyết định nội dung client nhìn thấy.

# 3. EF Core compiled queries: query cache, expression shape và khi tối ưu CPU translation thực sự đáng làm

## 1. What is it?

EF Core phải biến LINQ expression thành database command. Mental model:

```text
LINQ expression
   ↓
expression analysis
   ↓
query compilation / cache lookup
   ↓
SQL
   ↓
database execution
```

EF Core đã có internal query compilation cache. Explicit compiled queries (`EF.CompileQuery` / `EF.CompileAsyncQuery`) precompile một query shape cụ thể để giảm overhead lookup/compilation trên hot path.

## 2. Why does it exist?

Trong phần lớn business applications, database I/O mất nhiều thời gian hơn query compilation. Nhưng với extremely high-throughput endpoints, query đơn giản chạy rất nhanh và được gọi hàng triệu lần, CPU spent trong EF query pipeline có thể trở nên đáng kể.

Compiled queries tồn tại cho trường hợp đó, không phải để chữa slow SQL.

## 3. How does it work?

Ví dụ:

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<OrderDto>>
    GetOrderById = EF.CompileAsyncQuery(
        (AppDbContext db, Guid id) =>
            db.Orders
                .AsNoTracking()
                .Where(x => x.Id == id)
                .Select(x => new OrderDto(x.Id, x.Number, x.Total)));
```

Mỗi lần gọi, EF không cần thực hiện toàn bộ query-compilation pipeline như một expression mới.

Tuy nhiên, database vẫn phải parse/execute SQL theo behavior riêng của provider và database plan cache.

## 4. Practical implementation

Consumer:

```csharp
public async Task<OrderDto?> GetAsync(Guid id, CancellationToken ct)
{
    await foreach (var order in GetOrderById(_db, id).WithCancellation(ct))
        return order;

    return null;
}
```

Trước khi dùng compiled query, benchmark với production-like data và endpoint behavior. Nếu query mất 40 ms ở database còn EF compilation chỉ chiếm vài microseconds, optimization này không đáng ưu tiên.

## 5. Real production scenario

Một pricing API có endpoint lookup cực đơn giản từ local Azure SQL region, query indexed trả về dưới 1 ms và chạy hơn 50.000 requests/second. CPU profile cho thấy EF expression processing/query-cache lookup xuất hiện đáng kể.

Team thử compiled query cho ba hot lookups, benchmark end-to-end và thấy CPU giảm measurable. Các query bình thường vẫn giữ LINQ tự nhiên để tránh unnecessary complexity.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries nhưng endpoint vẫn chậm 200 ms.

**Evidence** → distributed trace cho thấy 180 ms nằm ở SQL execution.

**Hypothesis** → bottleneck là database I/O/query plan, không phải EF compilation.

**Diagnosis** → đo application CPU, SQL duration, execution plan, logical reads và network latency.

**Fix** → tối ưu đúng bottleneck: projection, index/access pattern, data shape hoặc database design.

**Verification** → benchmark lại cả endpoint, không chỉ microbenchmark method gọi EF.

## 7. Common mistakes

* Dùng compiled query như fix cho slow SQL.
* Compile hàng trăm queries không có benchmark.
* Tạo dynamic query shape rồi cố nhét vào static compiled query.
* Nhầm EF query compilation cache với database execution-plan cache.
* Tối ưu CPU vài microseconds trong khi network/database tốn hàng chục milliseconds.

## 8. Alternatives

EF Core normal query cache thường đủ tốt. Raw SQL/Dapper có thể giảm ORM overhead trong specific hot paths nhưng đánh đổi abstraction và maintainability. Stored procedures giải quyết concern khác, không tự động nhanh hơn chỉ vì là procedure.

## 9. Trade-offs

### Advantages

* Giảm một phần CPU overhead cho stable hot queries.
* Predictable query shape.

### Costs / Risks

* Code khó đọc hơn LINQ inline.
* Tăng static plumbing.
* Lợi ích nhỏ nếu database I/O chiếm phần lớn latency.
* Khó phù hợp dynamic filtering phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ không chạy “trực tiếp”; EF phải translate thành SQL.

### Middle

Đọc generated SQL và biết `AsNoTracking`, projection, query execution timing.

### Senior

Profile query pipeline, phân biệt ORM CPU overhead với database bottleneck.

### Technical Lead / Architect

Đặt performance budget và guideline để compiled queries chỉ xuất hiện ở evidence-based hot paths, không trở thành premature optimization convention.

## 11. Key takeaway

* EF Core đã cache query compilation; explicit compiled query là optimization nâng cao.
* Slow endpoint thường cần đo SQL/I/O trước khi tối ưu EF CPU overhead.
* Benchmark end-to-end mới quyết định optimization có giá trị hay không.

# 4. SQL Server `READ COMMITTED SNAPSHOT`: giảm reader/writer blocking bằng row versioning nhưng không miễn phí

## 1. What is it?

`READ COMMITTED SNAPSHOT` (RCSI) thay đổi cách isolation level `READ COMMITTED` cung cấp consistent reads. Thay vì reader chờ writer release lock, SQL Server có thể đọc row version trước đó từ version store.

Mental model:

```text
Lock-based READ COMMITTED
Writer locks row
Reader waits

RCSI
Writer changes row
Old row version kept
Reader sees committed previous version
```

## 2. Why does it exist?

OLTP systems thường có nhiều reads và writes đồng thời. Lock-based reads có thể tạo blocking chains: một transaction update kéo dài làm hàng chục requests đọc cùng rows phải chờ.

RCSI giảm reader/writer blocking mà không yêu cầu application thêm `NOLOCK` và chấp nhận dirty reads.

## 3. How does it work?

Khi row được update, SQL Server giữ version cần thiết để readers đang chạy có thể thấy snapshot phù hợp. Reader dưới RCSI đọc committed version thay vì chờ exclusive lock của writer.

Điều này không có nghĩa mọi locks biến mất. Writers vẫn có thể block writers. Schema locks và nhiều loại locking khác vẫn tồn tại.

Version store sử dụng storage/resources và long-running transactions có thể giữ versions lâu hơn.

## 4. Practical implementation

Bật ở database level cần operational planning:

```sql
ALTER DATABASE OrdersDb
SET READ_COMMITTED_SNAPSHOT ON;
```

Không nên chạy câu lệnh này giữa production peak mà không hiểu connection/transaction requirements của thay đổi.

Sau khi bật, đo:

```text
blocking duration
version store usage
long-running transactions
query latency
write workload
```

## 5. Real production scenario

Một employee management system có batch payroll update hàng chục nghìn rows trong transaction lớn. Trong lúc batch chạy, employee self-service API đọc payroll status bị blocking 20–40 giây.

RCSI giảm reader/writer blocking đáng kể, nhưng team vẫn phải chia nhỏ batch transaction vì long-running writes gây version-store growth và writer contention.

## 6. Failure scenario & troubleshooting

**Symptom** → sau khi bật RCSI, blocking reads giảm nhưng storage/tempdb pressure tăng.

**Evidence** → version store usage tăng liên tục; một số transactions mở rất lâu.

**Hypothesis** → long-running transactions giữ old versions không thể cleanup sớm.

**Diagnosis** → tìm active transactions, duration, version-store metrics và workload tạo nhiều row versions.

**Fix** → rút ngắn transaction, xử lý batch hợp lý và capacity-plan tempdb/version store.

**Verification** → load test concurrent reads/writes và theo dõi cả latency lẫn storage/resource pressure.

## 7. Common mistakes

* Nghĩ RCSI loại bỏ mọi blocking.
* Dùng RCSI để che transaction boundary quá dài.
* Bật production mà không đo tempdb/version-store impact.
* Nhầm RCSI với `SNAPSHOT` isolation semantics ở transaction level.
* Dùng `NOLOCK` thay vì hiểu consistency requirement.

## 8. Alternatives

Lock-based `READ COMMITTED` đơn giản hơn khi contention thấp. `SNAPSHOT` isolation cho transaction-level snapshot semantics mạnh hơn nhưng có conflict considerations khác. Application-level read replicas có thể giảm read pressure nhưng tăng freshness/operational complexity.

## 9. Trade-offs

### Advantages

* Giảm reader/writer blocking.
* Giữ committed-read semantics tốt hơn dirty reads.
* Thường cải thiện concurrency cho read-heavy OLTP.

### Costs / Risks

* Row versioning tiêu tốn storage/I/O.
* Long transactions có thể gây version-store pressure.
* Writers vẫn có contention.
* Thay đổi isolation semantics có thể ảnh hưởng assumptions của application.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu blocking là consequence của concurrency control, không phải database “treo”.

### Middle

Phân biệt dirty read, committed read và row-versioned read.

### Senior

Điều tra blocking graphs, transaction duration và version-store pressure.

### Technical Lead / Architect

Chọn isolation strategy dựa trên consistency requirement, read/write mix và operational capacity thay vì bật snapshot theo trend.

## 11. Key takeaway

* RCSI giảm reader/writer blocking bằng row versioning, không bằng cách bỏ consistency.
* Nó không chữa writer contention hay transaction quá dài.
* Isolation-level change phải được đo cả correctness lẫn resource cost.

# 5. Redis hot keys và eviction: khi cache vẫn “healthy” nhưng một key hoặc policy memory làm cả hệ thống chậm

## 1. What is it?

Hot key là key nhận lượng traffic lớn bất thường so với phần còn lại. Eviction là cơ chế Redis loại keys khi memory đạt giới hạn theo `maxmemory-policy`.

Hai vấn đề này liên quan vì một cache có thể vẫn online nhưng hiệu năng và hit ratio suy giảm mạnh do workload skew hoặc memory pressure.

Mental model:

```text
Traffic bình thường
many keys -> distributed work

Hot key
50% traffic -> one key / one shard / one CPU path

Memory full
new writes -> eviction decisions -> keys disappear -> more misses
```

## 2. Why does it exist?

Cache thường được xem như cách giảm tải database. Nhưng nếu một product, tenant hoặc configuration key trở nên cực hot, cache layer itself trở thành bottleneck.

Tương tự, nếu memory policy không phù hợp, Redis có thể evict useful keys quá sớm, làm database traffic tăng và tạo feedback loop.

## 3. How does it work?

Redis xử lý commands rất nhanh nhưng một hot workload có thể tập trung CPU/network vào một node hoặc shard. Trong clustered architecture, hash slot distribution không giúp nếu phần lớn requests vẫn vào cùng key.

Eviction policies như LRU/LFU variants quyết định key nào bị loại khi memory đầy. Policy phải phù hợp với dữ liệu: cache disposable khác session/critical coordination data.

## 4. Practical implementation

Thiết kế cache key:

```csharp
var key = $"product:{productId}:summary:v3";
```

Theo dõi tối thiểu:

```text
keyspace hits / misses
evicted_keys
used_memory
CPU
network throughput
command latency
top hot keys / command distribution
```

Với hot data có thể duplicate/shard cache representation, use local `IMemoryCache` trước distributed cache cho ultra-hot immutable data, hoặc thay access pattern nếu consistency cho phép.

## 5. Real production scenario

Một e-commerce campaign đẩy một sản phẩm lên homepage. Traffic cho `product:123` tăng 100 lần. Redis overall memory chỉ 55%, nhưng node chứa key đó CPU chạm giới hạn và p99 GET tăng mạnh. Application threads chờ Redis, API latency tăng dù SQL gần như idle.

Root cause là workload skew, không phải thiếu capacity trung bình.

## 6. Failure scenario & troubleshooting

**Symptom** → cache hit ratio giảm dần và database CPU tăng cùng lúc.

**Evidence** → `evicted_keys` tăng nhanh sau khi memory chạm `maxmemory`; keys quan trọng bị mất liên tục.

**Hypothesis** → working set lớn hơn capacity hoặc eviction policy không phù hợp.

**Diagnosis** → phân tích key sizes, TTL distribution, memory fragmentation, eviction metrics và traffic miss path.

**Fix** → giảm value size, đặt TTL có chủ đích, tách workloads, tăng capacity khi justified hoặc loại dữ liệu không đáng cache.

**Verification** → load test tới memory pressure và xác nhận hit ratio/database load không tạo runaway feedback loop.

## 7. Common mistakes

* Chỉ monitor Redis uptime.
* Đặt mọi key TTL giống nhau.
* Cache objects quá lớn.
* Trộn session/coordination data với disposable cache mà không hiểu eviction risk.
* Scale cluster nhưng giữ một hot key duy nhất.
* Khi Redis chậm thì application retry aggressive và làm tình hình tệ hơn.

## 8. Alternatives

`IMemoryCache` tốt cho per-instance ultra-hot data nhưng không shared. CDN phù hợp public HTTP content. Database/materialized views đôi khi đủ nhanh và đơn giản hơn Redis. Nếu cached data không có clear invalidation/failure semantics, không cache có thể là lựa chọn tốt hơn.

## 9. Trade-offs

### Advantages

* Redis giảm latency và database load khi access pattern phù hợp.
* LFU/LRU policies có thể quản lý bounded memory tốt.

### Costs / Risks

* Hot keys tạo skew.
* Eviction có thể biến thành downstream load spike.
* Redis trở thành critical dependency nếu fallback không được thiết kế.
* Memory sizing và serialization cần operational discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache hit/miss và TTL.

### Middle

Monitor memory, eviction và key design.

### Senior

Phân tích workload skew, fallback amplification và memory-policy behavior.

### Technical Lead / Architect

Quyết định data nào thực sự nên ở Redis, isolation giữa workloads và failure strategy khi cache degraded/unavailable.

## 11. Key takeaway

* Redis “up” không có nghĩa Redis “healthy”.
* Hot keys và eviction cần workload-level telemetry, không chỉ node-level metrics.
* Cache failure phải được thiết kế để không đánh sập database phía sau.

# 6. DDD Anti-Corruption Layer: bảo vệ domain model khỏi legacy system và third-party contracts thay đổi liên tục

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary chuyển đổi giữa domain model của hệ thống và model của external/legacy system.

Mental model:

```text
External model
   ↓
Anti-Corruption Layer
   ↓
Internal domain language
```

Mục đích là ngăn concepts, field names, enum values và workflow assumptions của hệ thống bên ngoài “rò” vào core domain.

## 2. Why does it exist?

Legacy ERP có thể gọi khách hàng là `Account`, third-party CRM gọi là `Contact`, còn domain của bạn có `Customer`. Nếu application dùng external DTO xuyên toàn codebase, business logic dần bị định hình theo schema bên ngoài.

Khi provider đổi contract, impact lan rộng qua domain, application và UI.

ACL cô lập thay đổi đó.

## 3. How does it work?

Flow:

```text
CRM API DTO
   ↓
adapter / translator
   ↓
CustomerProfile
   ↓
domain/application logic
```

ACL có thể bao gồm:

* API client
* external DTOs
* mapping
* validation
* semantic translation
* error translation
* version compatibility

ACL không nhất thiết là microservice riêng. Trong Modular Monolith, nó có thể chỉ là infrastructure module rõ ownership.

## 4. Practical implementation

External contract:

```csharp
public sealed record LegacyCustomerDto(
    string AccountNo,
    string AccountState,
    string? MainEmail);
```

Internal model:

```csharp
public sealed record CustomerProfile(
    CustomerId Id,
    CustomerStatus Status,
    EmailAddress? Email);
```

Translator:

```csharp
public static CustomerProfile Translate(LegacyCustomerDto dto)
{
    var status = dto.AccountState switch
    {
        "A" => CustomerStatus.Active,
        "S" => CustomerStatus.Suspended,
        _ => CustomerStatus.Unknown
    };

    return new CustomerProfile(
        new CustomerId(dto.AccountNo),
        status,
        dto.MainEmail is null ? null : EmailAddress.Parse(dto.MainEmail));
}
```

Domain không cần biết `"A"` nghĩa là gì.

## 5. Real production scenario

Một e-commerce platform tích hợp ERP 15 năm tuổi. ERP dùng status codes `10`, `20`, `90`; application ban đầu copy các codes này vào order logic. Sau vài năm, hàng chục rules chứa `if (status == 20)`.

Khi ERP version mới đổi semantics, migration trở nên cực khó.

ACL chuyển external states thành explicit domain states ngay tại boundary, giúp business logic không phụ thuộc raw codes.

## 6. Failure scenario & troubleshooting

**Symptom** → provider thêm enum value mới và application bắt đầu reject nhiều messages.

**Evidence** → mapping layer không biết value mới; domain processing không nhận data.

**Hypothesis** → translator quá strict hoặc không có unknown-value strategy.

**Diagnosis** → inspect external payload/version, contract changelog, mapping telemetry và failed-message sample.

**Fix** → thêm explicit `Unknown`/quarantine path nếu domain cho phép, update mapping có kiểm soát và contract test provider integration.

**Verification** → replay representative payloads cũ/mới qua ACL.

## 7. Common mistakes

* Gọi bất kỳ repository/service wrapper nào là ACL.
* Copy external DTO vào domain rồi chỉ rename class.
* Để external enum/string values lan vào business rules.
* Build mapping framework rất lớn cho integration đơn giản.
* Không log unmapped semantic values.

## 8. Alternatives

Direct integration đủ tốt nếu external contract nhỏ, stable và không chạm core domain semantics. Separate integration service phù hợp khi nhiều systems cùng consume/translate provider hoặc operational isolation quan trọng. Canonical enterprise model có thể hữu ích nhưng dễ thành coupling khổng lồ nếu ép mọi system theo một schema chung.

## 9. Trade-offs

### Advantages

* Cô lập external change.
* Giữ ubiquitous language của domain sạch.
* Dễ test mapping và migration.

### Costs / Risks

* Thêm code và mapping maintenance.
* Có thể duplicate models.
* Overengineering nếu integration trivial.
* Semantic mismatch vẫn cần business decisions.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain model.

### Middle

Viết adapter/translator và tests cho mapping/error cases.

### Senior

Nhận diện semantic leakage, version compatibility và failure containment.

### Technical Lead / Architect

Quyết định boundary nào đáng có ACL, ownership ở module/service nào và mức isolation tương xứng với business dependency.

## 11. Key takeaway

* ACL bảo vệ business language khỏi model của hệ thống bên ngoài.
* Boundary này là semantic translation, không chỉ property mapping.
* Chỉ thêm ACL khi external coupling thực sự đáng cô lập.

# 7. Azure Functions scale-out + duplicate execution: idempotency, queue triggers và vì sao “serverless” không đồng nghĩa exactly-once

## 1. What is it?

Azure Functions có thể scale-out nhiều instances dựa trên trigger/workload. Với queue/message processing, một message thường có at-least-once semantics: hệ thống cố gắng xử lý ít nhất một lần, nhưng duplicate execution có thể xảy ra.

Mental model:

```text
Message
  ↓
Function instance A starts
  ↓
lock expires / process crashes / ack lost
  ↓
Message becomes visible again
  ↓
Function instance B processes again
```

## 2. Why does it exist?

Exactly-once execution xuyên network/process failure cực khó đảm bảo. Nếu platform chỉ remove message sau successful settlement, crash giữa side effect và settlement tạo ambiguity: side effect đã xảy ra nhưng message có thể được giao lại.

At-least-once + idempotent handler thường là model đáng tin cậy hơn.

## 3. How does it work?

Queue-triggered function nhận message, xử lý và platform settle/complete khi invocation thành công. Retry xảy ra khi exception, timeout hoặc lock/visibility semantics cho phép message xuất hiện lại.

Scale-out làm nhiều messages được xử lý song song; ordering và concurrency assumptions phải được thiết kế riêng.

## 4. Practical implementation

Idempotency table:

```sql
CREATE TABLE ProcessedMessages (
    MessageId nvarchar(100) NOT NULL PRIMARY KEY,
    ProcessedAtUtc datetime2 NOT NULL
);
```

Handler concept:

```csharp
public async Task HandleAsync(OrderPaid message, CancellationToken ct)
{
    if (await _inbox.ExistsAsync(message.MessageId, ct))
        return;

    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    await _orders.MarkPaidAsync(message.OrderId, ct);
    await _inbox.AddAsync(message.MessageId, ct);

    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
```

Idempotency record và business mutation nên nằm trong cùng transactional boundary khi database cho phép.

## 5. Real production scenario

Notification Function xử lý `OrderShipped` và gửi email. Một invocation gửi email thành công nhưng process restart trước khi message completion được ghi nhận. Message được deliver lại và khách hàng nhận hai email.

Với payment/refund operation, hậu quả còn nghiêm trọng hơn. Idempotency key phải được propagate tới downstream systems nếu side effect nằm ngoài local database.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng `MessageId` xuất hiện trong logs của nhiều invocations.

**Evidence** → first invocation kéo dài gần lock timeout; host restart hoặc dependency timeout xảy ra.

**Hypothesis** → message được redeliver theo expected at-least-once semantics.

**Diagnosis** → correlate message ID, dequeue count/delivery count, function invocation IDs và downstream side effects.

**Fix** → idempotent consumer, bounded processing duration, lock/visibility configuration phù hợp và dead-letter policy.

**Verification** → chaos test kill function sau business commit nhưng trước message settlement.

## 7. Common mistakes

* Assume Function chạy exactly once.
* Dùng random ID mới mỗi retry khiến downstream idempotency vô dụng.
* Retry non-idempotent HTTP side effect không có idempotency key.
* Không có poison-message/dead-letter strategy.
* Scale-out background work nhưng shared resource không chịu concurrency.

## 8. Alternatives

Worker Service + Service Bus vẫn có duplicate-delivery concern tương tự. Durable Functions cung cấp durable orchestration nhưng activities vẫn cần hiểu side-effect semantics. Scheduled App Service job đơn giản hơn một số workload nhưng multi-instance/leader concerns vẫn tồn tại.

## 9. Trade-offs

### Advantages

* Automatic scale và trigger integration.
* Operational simplicity cho bursty jobs.
* Good fit cho event-driven processing.

### Costs / Risks

* Duplicate execution cần design.
* Cold start/scale behavior ảnh hưởng latency.
* Retry có thể khuếch đại dependency failure.
* Stateful long-running workflows cần thêm abstraction.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry có thể chạy cùng logical work nhiều lần.

### Middle

Implement idempotency key, retry và dead-letter handling.

### Senior

Thiết kế transactional inbox/outbox, downstream idempotency và concurrency limits.

### Technical Lead / Architect

Chọn Azure Functions hay Worker/Container dựa trên workload, execution duration, scale pattern, cost và operational ownership.

## 11. Key takeaway

* Serverless không thay đổi distributed-systems fundamentals.
* Duplicate execution là behavior phải thiết kế trước, không phải edge case hiếm.
* Idempotency phải cover side effects thật sự, không chỉ code path local.

# 8. Kubernetes resource requests/limits: CPU throttling, `OOMKilled` và cách resource policy ảnh hưởng latency production

## 1. What is it?

Kubernetes `requests` mô tả resource cần để scheduler đặt Pod. `limits` đặt upper bound về resource container được phép dùng.

Mental model:

```text
request -> scheduling / reserved expectation
limit   -> runtime enforcement boundary
```

CPU và memory có enforcement khác nhau. CPU vượt limit thường bị throttled. Memory vượt limit có thể dẫn tới process/container bị killed.

## 2. Why does it exist?

Nếu không có resource boundaries, một noisy workload có thể chiếm CPU/memory và ảnh hưởng Pods khác trên cùng node. Nhưng limit đặt quá thấp cũng gây self-inflicted latency hoặc restart.

Resource policy tồn tại để cân bằng isolation, scheduling và utilization.

## 3. How does it work?

Ví dụ:

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
```

Scheduler dùng requests để quyết định node placement. Runtime/cgroup enforcement giới hạn CPU/memory.

Một .NET API cần burst CPU cho GC/JIT/serialization có thể bị CPU throttling dù node tổng thể còn CPU, nếu container chạm limit của mình.

## 4. Practical implementation

Bắt đầu bằng measurement:

```text
CPU usage and throttling
working set / RSS
GC heap size
allocation rate
OOM events
p95/p99 latency
restart count
```

Đừng đặt requests bằng peak observed usage một cách máy móc. Requests phục vụ scheduling/capacity; limits phục vụ isolation. Hai giá trị có thể cần policy khác nhau theo workload.

## 5. Real production scenario

Một ASP.NET Core API có CPU limit `500m`. Bình thường dùng 200m, nhưng khi traffic burst và JSON serialization tăng, container bị throttled. CPU dashboard node chỉ 45% nên team nghĩ application code chậm. p99 latency tăng mạnh trong khi request rate chưa quá lớn.

Metric `container_cpu_cfs_throttled_seconds_total` cho thấy throttling mới là root cause.

## 6. Failure scenario & troubleshooting

**Symptom** → Pod restart với reason `OOMKilled`.

**Evidence** → container memory gần `limits.memory`; Kubernetes events xác nhận exit due to OOM.

**Hypothesis** → working set legitimately vượt limit, allocation spike hoặc memory leak.

**Diagnosis** → phân tích process memory, GC heap, native memory, temporary buffers, concurrency và traffic pattern.

**Fix** → sửa leak/allocation spike, giảm concurrency hoặc tăng memory limit nếu working set hợp lệ.

**Verification** → stress/load test ở peak concurrency và theo dõi memory headroom.

## 7. Common mistakes

* Set limit cực thấp chỉ để “tiết kiệm”.
* Nhìn node CPU thay vì container throttling.
* Nhầm memory request với hard cap.
* Không tính startup/JIT/GC spikes.
* Autoscale theo CPU nhưng CPU đang bị throttled bởi limit không phù hợp.
* Tăng limit trước khi phân biệt leak với legitimate working set.

## 8. Alternatives

Không đặt CPU limit là policy một số platform chọn để tránh throttling, nhưng cần strong node isolation/capacity management. Vertical Pod Autoscaler hỗ trợ recommendation/adjustment trong một số scenarios. App Service/Container Apps abstract bớt Kubernetes resource controls nhưng vẫn có compute sizing constraints.

## 9. Trade-offs

### Advantages

* Isolation giữa workloads.
* Scheduler có capacity signal rõ.
* Resource usage predictable hơn.

### Costs / Risks

* Limits sai gây throttling/OOM.
* Requests quá cao làm cluster underutilized.
* Requests quá thấp làm overcommit và contention.
* Tuning cần production telemetry.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt requests và limits.

### Middle

Đọc Pod events, metrics và nhận diện `OOMKilled`/CPU throttling.

### Senior

Kết nối .NET GC/allocation/concurrency với cgroup resource behavior.

### Technical Lead / Architect

Định nghĩa resource policy, headroom, autoscaling strategy và capacity planning dựa trên SLO thay vì copy YAML defaults.

## 11. Key takeaway

* CPU limit và memory limit không fail theo cùng cách.
* Resource configuration có thể trực tiếp tạo p99 latency và restart incidents.
* Tuning phải dựa trên container-level telemetry và workload peaks.

# 9. Playwright E2E test isolation: test data, deterministic state và cách giảm flaky tests mà không biến suite thành chậm không dùng được

## 1. What is it?

E2E isolation nghĩa mỗi test chạy với state có thể dự đoán và không phụ thuộc vào thứ tự hoặc side effects của test khác.

Mental model:

```text
Bad suite
Test A creates user
Test B assumes same user exists
Test C edits same order
=> order-dependent failures

Isolated suite
Each test owns its required state
=> deterministic execution
```

## 2. Why does it exist?

E2E tests tương tác browser, network, API, database và authentication nên vốn có nhiều failure surfaces hơn unit tests. Nếu thêm shared mutable state, suite nhanh chóng flaky và team mất niềm tin vào CI.

Isolation tồn tại để test failure có ý nghĩa: fail vì product regression, không phải vì test khác vừa sửa dữ liệu.

## 3. How does it work?

Test nên tạo unique data hoặc reset known fixture. Playwright hỗ trợ parallelism, fixtures và browser contexts, nhưng data backend vẫn phải được isolate.

Ví dụ unique entity:

```ts
const email = `e2e-${crypto.randomUUID()}@example.test`;
```

Auth state có thể reuse có kiểm soát, nhưng mutable business records không nên được share giữa tests chạy parallel.

## 4. Practical implementation

```ts
import { test, expect } from '@playwright/test';

test('user can create a project', async ({ page, request }) => {
  const suffix = crypto.randomUUID();

  const user = await createTestUser(request, `user-${suffix}@example.test`);

  await login(page, user);
  await page.goto('/projects');
  await page.getByRole('button', { name: 'New project' }).click();
  await page.getByLabel('Title').fill(`E2E Project ${suffix}`);
  await page.getByRole('button', { name: 'Save' }).click();

  await expect(page.getByText(`E2E Project ${suffix}`)).toBeVisible();
});
```

Dùng API setup cho prerequisite thường nhanh và deterministic hơn click UI qua 10 màn hình chỉ để tạo state.

## 5. Real production scenario

Suite 300 Playwright tests mất 45 phút và fail ngẫu nhiên 10–15 tests mỗi run. Team rerun CI cho đến khi xanh.

Phân tích cho thấy nhiều tests dùng chung account và records; parallel workers overwrite settings của nhau. Sau khi tạo per-test/per-worker data và chỉ giữ vài flows thật sự E2E, suite ngắn hơn và failure rate giảm mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → một test pass khi chạy riêng nhưng fail khi chạy full suite.

**Evidence** → data/account giống nhau giữa nhiều tests; failure thay đổi tùy worker count.

**Hypothesis** → shared mutable state hoặc race giữa tests.

**Diagnosis** → chạy serial vs parallel, log unique entity IDs, inspect database/API calls và test ordering.

**Fix** → isolate data, namespace per worker, cleanup reliable hoặc use disposable environment where practical.

**Verification** → chạy suite nhiều lần với randomized order/parallelism và đo flake rate.

## 7. Common mistakes

* Dùng `waitForTimeout(5000)` thay proper condition.
* Share một account mutable cho mọi tests.
* Test mọi branch bằng browser thay vì lower-level tests.
* Cleanup phụ thuộc test pass.
* Selector theo CSS/layout dễ vỡ thay vì user-facing roles/labels.
* Treat rerun-until-pass như solution cho flaky test.

## 8. Alternatives

Integration/API tests nhanh hơn cho backend behavior. Unit tests tốt cho pure logic. Component tests phù hợp UI logic riêng. E2E nên giữ cho cross-system user journeys có business risk cao.

## 9. Trade-offs

### Advantages

* Bảo vệ critical user flows gần production behavior.
* Phát hiện integration issues giữa frontend/backend/auth.

### Costs / Risks

* Chậm hơn lower-level tests.
* Environment/data complexity cao.
* Flakiness tăng nếu isolation kém.
* Debug failure khó hơn unit/integration tests.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu test phải deterministic và không phụ thuộc execution order.

### Middle

Viết Playwright tests dùng robust selectors, fixtures và isolated data.

### Senior

Thiết kế test architecture, parallel strategy và phân bổ risk giữa unit/integration/E2E.

### Technical Lead / Architect

Quyết định journeys nào đáng E2E, CI budget, environment strategy và quality gates để suite giữ được signal cao.

## 11. Key takeaway

* E2E test đáng giá khi failure có signal cao; flaky suite gần như không có giá trị.
* Backend data isolation quan trọng không kém browser isolation.
* Dùng E2E cho critical journeys, không thay thế toàn bộ test pyramid.

# 10. Akamai/CDN `Cache-Control`: browser cache, edge cache, stale content và invalidation strategy cho production website

## 1. What is it?

CDN caching đặt copies của HTTP responses gần users hơn. `Cache-Control` và related cache metadata quyết định response có thể cache ở đâu, bao lâu và khi nào phải revalidate.

Mental model:

```text
Browser
   ↓
Akamai edge
   ↓
Origin / reverse proxy
   ↓
Application
```

Cùng một response có thể tồn tại ở browser cache và CDN edge cache với lifecycle khác nhau.

## 2. Why does it exist?

Nếu mỗi request image, CSS hoặc public page đều đi tới origin, latency và origin load tăng không cần thiết. CDN giảm round-trip distance và offload application.

Nhưng caching tạo trade-off giữa freshness và performance. TTL quá dài khiến stale content; TTL quá ngắn khiến CDN gần như không có giá trị.

## 3. How does it work?

Ví dụ static versioned asset:

```http
Cache-Control: public, max-age=31536000, immutable
```

phù hợp vì filename có content hash:

```text
app.a8f31c2.js
```

HTML/content page có thể dùng shorter TTL và revalidation:

```http
Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=30
```

`max-age` thường ảnh hưởng browser/shared cache semantics; `s-maxage` có thể áp dụng shared caches như CDN.

Exact Akamai behavior còn phụ thuộc property configuration, rules và cache key settings.

## 4. Practical implementation

ASP.NET Core response headers nên được thiết kế theo content type:

```csharp
app.Use(async (context, next) =>
{
    await next();

    if (context.Response.StatusCode == StatusCodes.Status200OK &&
        context.Request.Path.StartsWithSegments("/assets"))
    {
        context.Response.Headers.CacheControl =
            "public,max-age=31536000,immutable";
    }
});
```

Trong thực tế, static-file middleware/CDN rules thường phù hợp hơn custom middleware chung cho mọi path.

Dynamic/personalized responses phải tránh public caching nếu chứa user-specific data.

## 5. Real production scenario

Marketing team publish homepage hero mới trong Optimizely. Origin trả content mới ngay, nhưng users ở một số regions vẫn thấy hero cũ 20 phút.

Application logs không có vấn đề. Response headers cho thấy CDN edge đang serve cached HTML theo TTL cũ. Root cause nằm ở edge caching/invalidation, không phải CMS database.

## 6. Failure scenario & troubleshooting

**Symptom** → một số users thấy content cũ, một số thấy content mới.

**Evidence** → origin fetch trực tiếp trả version mới; CDN response có `Age` cao hoặc cache-status header cho thấy HIT.

**Hypothesis** → stale edge object hoặc cache key thiếu dimension.

**Diagnosis** → compare browser vs edge vs origin responses, inspect `Cache-Control`, `Age`, `Vary`, Akamai cache key/property rules và purge status.

**Fix** → purge/invalidate đúng object, chỉnh TTL/cache key hoặc version asset strategy.

**Verification** → test từ nhiều regions/edge paths và xác nhận new content propagates theo expected freshness SLO.

## 7. Common mistakes

* Cache personalized HTML publicly.
* TTL rất dài nhưng không có purge strategy.
* Version static assets không thay filename khi content đổi.
* Cache key bỏ query/header dimension thực sự ảnh hưởng representation.
* Blame application trước khi xác định response đến từ browser, edge hay origin.
* Dùng `no-cache` và `no-store` như cùng một nghĩa.

## 8. Alternatives

Browser caching alone giảm repeat requests của một user nhưng không offload global origin traffic như CDN. Reverse-proxy caching gần origin giảm app load nhưng không giảm geographic latency nhiều. Server-side output cache hữu ích cho generated content nhưng vẫn cần invalidation semantics riêng.

## 9. Trade-offs

### Advantages

* Giảm latency địa lý.
* Giảm origin load.
* Tăng resilience trước traffic spikes.
* Rất hiệu quả cho static/public content.

### Costs / Risks

* Stale content và purge complexity.
* Cache-key mistakes gây correctness/security issues.
* Debug path phức tạp hơn vì nhiều cache layers.
* CDN configuration trở thành một phần application behavior cần versioning/observability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser cache, CDN edge và origin là các layer khác nhau.

### Middle

Đọc `Cache-Control`, `Age`, `ETag`, `Vary` và troubleshoot cache hit/miss.

### Senior

Thiết kế cache keys, freshness policy, purge behavior và personalized-content boundaries.

### Technical Lead / Architect

Đặt caching strategy xuyên Browser → Akamai → Reverse Proxy → Application với explicit freshness SLO, security review và ownership rõ ràng.

## 11. Key takeaway

* CDN performance luôn đi kèm freshness policy.
* Khi content stale, phải xác định layer nào đang giữ object trước khi sửa.
* Cache key và invalidation là correctness concerns, không chỉ performance tuning.
