# 1. .NET `CancellationTokenSource.CreateLinkedTokenSource`: hợp nhất request abort, timeout và shutdown mà không làm mất cancellation ownership

## 1. What is it?

`CancellationTokenSource.CreateLinkedTokenSource` tạo một `CancellationTokenSource` mới bị cancel khi **bất kỳ** token đầu vào nào bị cancel.

Mental model:

```text
RequestAborted ─────┐
Timeout token ──────┼─> Linked token ─> downstream work
ApplicationStopping ┘
```

Điểm quan trọng là cancellation trong .NET là cơ chế **cooperative cancellation**. Token không “kill thread”; nó truyền tín hiệu để code chủ động dừng ở boundary phù hợp.

Linked token hữu ích khi một operation có nhiều lý do hợp lệ để dừng: client ngắt kết nối, budget thời gian hết, hoặc application đang shutdown.

## 2. Why does it exist?

Nếu chỉ truyền `HttpContext.RequestAborted`, request có thể sống quá lâu khi downstream dependency bị treo nhưng client vẫn còn kết nối.

Nếu chỉ dùng timeout nội bộ, server có thể tiếp tục xử lý dù client đã bỏ request.

Nếu chỉ dựa vào application shutdown, operation có thể giữ process trong graceful-shutdown window lâu hơn cần thiết.

Linked token cho phép kết hợp các cancellation scopes mà không làm downstream phải hiểu nguồn cancellation nào đang tồn tại.

## 3. How does it work?

Mỗi `CancellationToken` có thể đăng ký callback. Linked source đăng ký vào các source tokens; khi một token được cancel, linked source chuyển trạng thái sang canceled và phát tín hiệu tới các consumers.

Điều này cũng có chi phí: mỗi link tạo registrations và vì vậy linked `CancellationTokenSource` nên được dispose.

```csharp
using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(3));
using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(
    requestAborted,
    timeoutCts.Token,
    applicationStopping);

await repository.LoadAsync(id, linkedCts.Token);
```

Downstream nên propagate token tiếp tục:

```text
Endpoint
  ↓ token
Application service
  ↓ token
EF Core / HttpClient / Service Bus
```

## 4. Practical implementation

```csharp
app.MapGet("/reports/{id:guid}", async (
    Guid id,
    ReportService service,
    IHostApplicationLifetime lifetime,
    HttpContext httpContext) =>
{
    using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
    using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(
        httpContext.RequestAborted,
        timeoutCts.Token,
        lifetime.ApplicationStopping);

    try
    {
        var report = await service.BuildAsync(id, linkedCts.Token);
        return Results.Ok(report);
    }
    catch (OperationCanceledException) when (timeoutCts.IsCancellationRequested)
    {
        return Results.Problem(
            statusCode: StatusCodes.Status504GatewayTimeout,
            title: "Report generation timed out");
    }
});
```

`ReportService` không cần biết timeout đến từ request, host hay local budget; nó chỉ tôn trọng token.

## 5. Real production scenario

Một endpoint tổng hợp dữ liệu từ SQL và external Pricing API. Client timeout sau 10 giây, application đặt budget 6 giây, còn App Service shutdown có 30 giây graceful window.

Nếu request bị cancel ở giây thứ 2, linked token giúp SQL query và HTTP call dừng sớm. Điều này giải phóng connection, socket và ThreadPool capacity thay vì tiếp tục công việc không còn consumer.

## 6. Failure scenario & troubleshooting

**Symptom** → request đã trả 499/timeout nhưng SQL vẫn tiếp tục chạy.

**Evidence** → Application Insights thấy request duration 5 giây nhưng dependency span kéo dài 20 giây.

**Hypothesis** → `CancellationToken` bị mất ở một layer.

**Diagnosis** → tìm method gọi `ToListAsync()` / `SendAsync()` mà không truyền token.

**Fix** → propagate token xuyên suốt call chain.

**Verification** → hủy request trong load test; dependency duration phải kết thúc gần thời điểm request bị cancel.

## 7. Common mistakes

* Tạo `new CancellationTokenSource()` ở mỗi layer và vô tình cắt đứt cancellation từ caller.
* Bắt `OperationCanceledException` rồi log như lỗi Production.
* Dùng token nhưng downstream API không nhận token.
* Quên dispose linked `CancellationTokenSource`.
* Biến cancellation thành business failure thay vì lifecycle signal.

## 8. Alternatives

Timeout có thể đặt trực tiếp ở `HttpClient.Timeout` hoặc database command timeout. Các timeout này vẫn cần, nhưng chúng chỉ kiểm soát một dependency cụ thể.

Linked token phù hợp khi muốn quản lý **operation budget xuyên nhiều dependency**.

## 9. Trade-offs

### Advantages

* Giảm wasted work.
* Hợp nhất nhiều cancellation reasons.
* Giúp graceful shutdown sạch hơn.

### Costs / Risks

* Dễ tạo token graph phức tạp.
* Callback registrations có overhead.
* Xử lý sai `OperationCanceledException` có thể làm telemetry nhiễu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu token là tín hiệu cooperative, không phải thread abort.

### Middle

Biết propagate token qua EF Core, `HttpClient`, background work và dispose source đúng cách.

### Senior

Phân biệt client abort, timeout budget và host shutdown; không biến mọi cancellation thành error.

### Technical Lead / Architect

Định nghĩa timeout/cancellation policy theo request path, tránh mỗi service tự đặt timeout vô tổ chức dẫn tới failure cascade.

## 11. Key takeaway

* Cancellation phải được propagate xuyên call chain mới có giá trị.
* Linked token giúp hợp nhất lifecycle nhưng ownership của từng timeout vẫn phải rõ.
* Canceled work nên giải phóng resource sớm thay vì tiếp tục xử lý vô ích.

# 2. ASP.NET Core response streaming + backpressure: trả dữ liệu lớn mà không giữ toàn bộ payload trong memory

## 1. What is it?

Response streaming là cách gửi dữ liệu cho client theo từng phần thay vì xây dựng toàn bộ response trong memory rồi mới gửi.

Mental model:

```text
Database / generator
      ↓ chunks
ASP.NET Core
      ↓ flush
Network socket
      ↓
Client
```

Backpressure xuất hiện khi producer có thể tạo dữ liệu nhanh hơn network/client có thể tiêu thụ. Một implementation đúng phải để tốc độ downstream giới hạn producer thay vì buffer vô hạn.

## 2. Why does it exist?

Một CSV 2 GB hoặc file export hàng triệu records không nên được materialize thành `List<T>` rồi convert thành một `byte[]` khổng lồ.

Nếu làm vậy:

* allocation tăng mạnh
* LOH pressure tăng
* GC pause tăng
* memory có thể chạm container limit
* user phải chờ đến khi toàn bộ file hoàn tất mới nhận byte đầu tiên

Streaming giảm peak memory và time-to-first-byte.

## 3. How does it work?

ASP.NET Core viết response vào `HttpResponse.Body` hoặc `BodyWriter`. Khi `WriteAsync`/`FlushAsync` chưa hoàn tất vì socket chậm, `await` chính là điểm backpressure tự nhiên.

```text
Producer nhanh
   ↓
WriteAsync
   ↓ nếu socket buffer đầy
await
   ↓
Producer tạm dừng
```

Đây là lý do không nên fire-and-forget writes hoặc buffer vô hạn bằng `MemoryStream` trước khi gửi.

## 4. Practical implementation

```csharp
app.MapGet("/exports/orders.csv", async (
    AppDbContext db,
    HttpResponse response,
    CancellationToken ct) =>
{
    response.ContentType = "text/csv";
    response.Headers.ContentDisposition =
        "attachment; filename=orders.csv";

    await response.WriteAsync("Id,Number,Total\n", ct);

    await foreach (var order in db.Orders
        .AsNoTracking()
        .OrderBy(x => x.Id)
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        var line = $"{order.Id},{order.Number},{order.Total}\n";
        await response.WriteAsync(line, ct);
    }
});
```

Với file binary lớn nên dùng `FileStream`/Blob streaming thay vì đọc toàn bộ vào `byte[]`.

## 5. Real production scenario

SaaS cho phép finance team export 3 triệu invoice rows. Bản đầu dùng `ToListAsync()` rồi tạo CSV trong memory. Một vài exports đồng thời làm pod đạt 2 GB limit và bị OOMKilled.

Chuyển sang streaming giảm peak memory đáng kể, nhưng database connection bị giữ lâu hơn vì query sống suốt quá trình download. Đây là trade-off cần nhận diện.

## 6. Failure scenario & troubleshooting

**Symptom** → memory ổn nhưng connection pool bị exhaustion khi nhiều user tải export chậm.

**Evidence** → SQL connection duration tương ứng với network download duration.

**Hypothesis** → streaming trực tiếp từ database giữ reader/connection quá lâu.

**Diagnosis** → trace cho thấy query mở suốt hàng phút.

**Fix** → với exports rất lớn, generate file background vào Blob Storage rồi trả download URL; hoặc stream theo bounded batches.

**Verification** → load test với slow clients; connection pool utilization phải ổn định.

## 7. Common mistakes

* `ToListAsync()` trước khi stream.
* Dùng `MemoryStream` cho file nhiều GB.
* Không truyền `RequestAborted`.
* Flush sau từng byte/record nhỏ làm syscall overhead tăng.
* Giữ transaction hoặc DbContext quá lâu.

## 8. Alternatives

* Direct streaming: đơn giản, realtime, memory thấp.
* Background export + Blob Storage: tốt cho file cực lớn và retry/download lại.
* Pagination API: phù hợp interactive consumption hơn bulk export.

## 9. Trade-offs

### Advantages

* Peak memory thấp.
* Client nhận dữ liệu sớm.
* Có backpressure tự nhiên qua async I/O.

### Costs / Risks

* Connection/resource có thể sống lâu.
* Khi đã gửi response headers, xử lý lỗi giữa stream khó hơn.
* Retry giữa chừng phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác biệt giữa buffering và streaming.

### Middle

Biết dùng async streaming và cancellation.

### Senior

Nhìn thấy resource lifetime, backpressure, partial-response failure và slow-client risk.

### Technical Lead / Architect

Quyết định khi nào direct streaming đủ tốt, khi nào phải chuyển sang asynchronous export pipeline với Blob Storage/CDN.

## 11. Key takeaway

* Streaming giải quyết memory, không tự động giải quyết mọi scalability problem.
* Backpressure phải truyền ngược tới producer.
* Với export rất lớn, background generation thường cô lập failure tốt hơn direct request streaming.

# 3. EF Core optimistic concurrency với `rowversion`: phát hiện lost update thay vì âm thầm ghi đè dữ liệu

## 1. What is it?

Optimistic concurrency giả định xung đột ghi không xảy ra thường xuyên. Thay vì lock row từ lúc đọc tới lúc ghi, application kiểm tra rằng dữ liệu chưa bị thay đổi kể từ lần đọc.

Với SQL Server, `rowversion` là concurrency token phổ biến.

```text
Read entity + Version=42
          ↓
User edits
          ↓
UPDATE ... WHERE Id=@id AND Version=42
          ↓
0 rows updated => conflict
```

## 2. Why does it exist?

Trong web app, user có thể mở form vài phút. Không thực tế giữ database lock suốt khoảng đó.

Nếu không kiểm tra version:

1. User A đọc Order.
2. User B đọc cùng Order.
3. A cập nhật ShippingAddress.
4. B save snapshot cũ và vô tình ghi đè thay đổi của A.

Đây là lost update.

## 3. How does it work?

Entity:

```csharp
public sealed class Order
{
    public Guid Id { get; set; }
    public string Status { get; set; } = null!;

    [Timestamp]
    public byte[] Version { get; set; } = null!;
}
```

EF Core sinh SQL kiểu:

```sql
UPDATE Orders
SET Status = @p0
WHERE Id = @id
  AND Version = @originalVersion;
```

Nếu row đã đổi, `UPDATE` ảnh hưởng 0 rows và EF Core ném `DbUpdateConcurrencyException`.

## 4. Practical implementation

```csharp
try
{
    order.Status = request.Status;
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new ProblemDetails
    {
        Title = "The order was modified by another user.",
        Detail = "Reload the latest version before applying your changes."
    });
}
```

API tốt hơn nên expose version, ví dụ qua ETag hoặc field opaque, để client gửi lại version đã đọc.

## 5. Real production scenario

Hai support agents cùng xử lý customer account. Agent A khóa account vì fraud signal. Agent B đang mở UI cũ và save profile change.

Nếu application update toàn entity mà không concurrency check, B có thể vô tình đưa trạng thái account về giá trị cũ. `rowversion` buộc conflict phải được xử lý rõ ràng.

## 6. Failure scenario & troubleshooting

**Symptom** → user báo “dữ liệu của tôi tự biến mất”.

**Evidence** → audit log thấy hai updates gần nhau, update sau chứa state cũ.

**Hypothesis** → lost update.

**Diagnosis** → generated SQL không có concurrency predicate.

**Fix** → thêm concurrency token; chỉ update fields có chủ đích; thiết kế conflict response.

**Verification** → integration test với hai DbContext cùng đọc một row, save lần lượt; lần thứ hai phải conflict.

## 7. Common mistakes

* Bắt `DbUpdateConcurrencyException` rồi retry tự động mà không merge business intent.
* Dùng `rowversion` nhưng DTO không mang version tới client.
* Map toàn DTO vào entity và overwrite fields không đổi.
* Nhầm optimistic concurrency với transaction isolation.

## 8. Alternatives

* Pessimistic locking: phù hợp critical short transaction nhưng tăng blocking.
* Application-level version number: portable hơn giữa databases.
* ETag/If-Match ở HTTP layer: tốt để concurrency trở thành API contract.

## 9. Trade-offs

### Advantages

* Không giữ lock trong user think-time.
* Phát hiện lost update rõ ràng.
* Scale tốt khi conflict hiếm.

### Costs / Risks

* Conflict UX cần thiết kế.
* Auto-retry có thể làm sai business semantics.
* Client/API contract phức tạp hơn một chút.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hai users có thể đọc cùng snapshot và save chồng lên nhau.

### Middle

Biết cấu hình concurrency token và xử lý exception.

### Senior

Phân biệt retry-safe conflict với conflict cần user/business merge.

### Technical Lead / Architect

Quyết định aggregate nào cần concurrency protection và expose version theo contract nào.

## 11. Key takeaway

* Optimistic concurrency không ngăn conflict; nó biến conflict âm thầm thành conflict có thể xử lý.
* Không retry mù quáng khi update có business intent.
* Concurrency token nên được coi là một phần của API/data contract.

# 4. PostgreSQL MVCC + VACUUM: vì sao đọc không khóa ghi nhưng dead tuples vẫn có thể làm database chậm dần

## 1. What is it?

PostgreSQL dùng MVCC — Multi-Version Concurrency Control — để nhiều transactions nhìn thấy các phiên bản dữ liệu phù hợp với snapshot của chúng.

Một `UPDATE` thường không sửa row tại chỗ theo nghĩa đơn giản. PostgreSQL tạo tuple version mới và version cũ trở thành dead tuple khi không còn transaction nào cần thấy nó.

```text
row v1 ── UPDATE ──> row v2
  │                    │
old snapshot thấy v1   new snapshot thấy v2
```

`VACUUM` dọn metadata/space có thể tái sử dụng khi các old versions không còn cần thiết.

## 2. Why does it exist?

Nếu reader và writer phải block nhau liên tục, throughput giảm mạnh trong hệ thống nhiều concurrent requests.

MVCC cho phép đọc và ghi cùng tồn tại tốt hơn, nhưng đổi lại database phải quản lý nhiều row versions và lifecycle của chúng.

## 3. How does it work?

Mỗi tuple có transaction visibility metadata. Query chỉ thấy version phù hợp với snapshot và isolation semantics.

Long-running transaction có thể giữ old snapshot rất lâu. Khi đó VACUUM không thể reclaim tuples mà transaction đó vẫn có khả năng nhìn thấy.

```text
Long transaction starts
      ↓
Thousands of updates happen
      ↓
Old tuples cannot be fully reclaimed
      ↓
Table/index bloat + more I/O
```

## 4. Practical implementation

Một investigation cơ bản:

```sql
SELECT pid,
       now() - xact_start AS transaction_age,
       state,
       query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Tìm dead tuples:

```sql
SELECT relname,
       n_live_tup,
       n_dead_tup,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Không nên phản xạ bằng cách `VACUUM FULL` trên Production vì operation này có locking và operational cost đáng kể.

## 5. Real production scenario

Một reporting endpoint mở transaction, stream hàng triệu rows trong 20 phút. Trong thời gian đó background jobs update cùng bảng mạnh.

Autovacuum chạy nhưng không reclaim được nhiều old versions do snapshot lâu. Table bloat tăng, index pages nhiều hơn, cache locality xấu đi và latency tăng dần qua nhiều giờ.

## 6. Failure scenario & troubleshooting

**Symptom** → query vốn ổn định bắt đầu tăng I/O và latency dù row count business không tăng nhiều.

**Evidence** → `n_dead_tup` cao, long-running transaction tồn tại, table size tăng bất thường.

**Hypothesis** → MVCC bloat bị giữ bởi old snapshots.

**Diagnosis** → correlate transaction age, autovacuum activity và relation size.

**Fix** → rút ngắn transaction; điều chỉnh autovacuum theo workload; xử lý bloat có kế hoạch.

**Verification** → dead tuple ratio giảm và query I/O trở lại baseline.

## 7. Common mistakes

* Nghĩ MVCC đồng nghĩa “không có locking”.
* Để transaction mở trong lúc gọi external API.
* Dùng transaction scope quá rộng quanh stream/report.
* Chạy `VACUUM FULL` như quick fix không đánh giá lock impact.

## 8. Alternatives

SQL Server dùng cơ chế concurrency khác và có row-versioning options như RCSI/Snapshot Isolation. Cùng mục tiêu giảm contention nhưng operational behavior khác PostgreSQL.

## 9. Trade-offs

### Advantages

* Read/write concurrency tốt.
* Snapshot semantics mạnh.

### Costs / Risks

* Dead tuples và bloat cần maintenance.
* Long transactions có hậu quả hệ thống.
* Autovacuum tuning trở thành operational concern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một logical row có thể tồn tại nhiều physical versions.

### Middle

Biết đọc `pg_stat_activity` và `pg_stat_user_tables`.

### Senior

Nhận diện long transaction, bloat, autovacuum và query I/O là cùng một causal chain.

### Technical Lead / Architect

Thiết kế transaction boundaries và reporting strategy không giữ snapshot/database resources quá lâu.

## 11. Key takeaway

* MVCC đổi blocking thành version-management cost.
* Long-running transactions có thể gây performance degradation xa khỏi code tạo transaction.
* VACUUM là phần bình thường của PostgreSQL lifecycle, không phải emergency repair tool đơn thuần.

# 5. Elasticsearch aliases + zero-downtime reindex: thay mapping/index mà không bắt Search API biết về migration

## 1. What is it?

Elasticsearch alias là tên logic trỏ tới một hoặc nhiều physical indexes.

```text
Search API
   ↓
products-read alias
   ↓
products-v42 index
```

Khi cần mapping mới, tạo `products-v43`, reindex dữ liệu, rồi atomically chuyển alias từ v42 sang v43.

## 2. Why does it exist?

Một số mapping changes không thể sửa in-place an toàn. Nếu application gọi trực tiếp `products-v42`, tên index trở thành deployment contract và migration buộc code biết version vật lý.

Alias tách logical dependency khỏi physical index lifecycle.

## 3. How does it work?

Flow:

```text
DB / existing index
      ↓
create products-v43
      ↓
backfill / reindex
      ↓
validate count + queries
      ↓
atomic alias switch
      ↓
Search API now reads v43
```

Alias update có thể thực hiện trong một request để remove/add atomically.

## 4. Practical implementation

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v42", "alias": "products-read" } },
    { "add":    { "index": "products-v43", "alias": "products-read" } }
  ]
}
```

Trong .NET application, cấu hình chỉ biết `products-read`, không hard-code physical version.

Với writes, có thể dùng write alias riêng để kiểm soát cutover.

## 5. Real production scenario

E-commerce cần thay analyzer từ generic tokenizer sang language-aware analyzer. Mapping/index analysis chain yêu cầu reindex hàng chục triệu products.

Thay vì downtime, team tạo index mới, bulk backfill, chạy validation queries, sau đó switch alias trong vài milliseconds.

## 6. Failure scenario & troubleshooting

**Symptom** → sau cutover, một số products mới biến mất khỏi search.

**Evidence** → backfill hoàn tất nhưng writes xảy ra trong lúc migration chỉ nằm ở old index.

**Hypothesis** → reindex không xử lý write gap.

**Diagnosis** → so sánh primary DB sequence/timestamp với documents trong new index.

**Fix** → dùng change feed/outbox để replay delta hoặc dual-write có kiểm soát; chỉ cutover sau catch-up.

**Verification** → document counts, sampled business queries và lag metric đều đạt threshold.

## 7. Common mistakes

* Reindex rồi switch alias mà bỏ qua concurrent writes.
* Chỉ kiểm tra document count, không kiểm tra mapping/query semantics.
* Hard-code physical index trong app.
* Xóa old index ngay sau cutover, mất rollback path.

## 8. Alternatives

* In-place compatible mapping addition: đơn giản hơn nếu change cho phép.
* Full downtime migration: có thể đủ tốt cho internal system nhỏ.
* Blue/green index qua aliases: phù hợp production search cần rollback.

## 9. Trade-offs

### Advantages

* Gần zero downtime.
* Rollback nhanh.
* Physical index lifecycle không leak vào app.

### Costs / Risks

* Tạm thời cần gấp đôi storage.
* Write synchronization phức tạp.
* Validation/cutover pipeline cần discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu alias là logical name đứng trước physical index.

### Middle

Biết tạo index mới, reindex và switch alias.

### Senior

Xử lý write gap, rollback và eventual consistency.

### Technical Lead / Architect

Thiết kế index lifecycle, ownership và source-of-truth synchronization để Elasticsearch không trở thành database không kiểm soát.

## 11. Key takeaway

* Alias là abstraction cho index lifecycle, không chỉ convenience name.
* Reindex an toàn phải xử lý concurrent writes và rollback.
* Search index thường là derived state; validation phải quay về primary source of truth.

# 6. Modular Monolith module boundaries: cô lập thay đổi và ownership mà chưa cần trả giá vận hành của Microservices

## 1. What is it?

Modular Monolith là một deployable application duy nhất nhưng được chia thành modules có boundary rõ ràng về code, domain, data access và contracts.

```text
Single deployment
┌────────────────────────────┐
│ Orders │ Billing │ Catalog │
│   ↓       ↓         ↓      │
│ private internals/modules  │
└────────────────────────────┘
```

Điểm cốt lõi là **encapsulation boundary**, không phải folder naming.

## 2. Why does it exist?

Layered monolith dễ trượt thành hệ thống nơi mọi service gọi mọi repository và mọi table.

Microservices giải quyết isolation ở process/network boundary nhưng thêm rất nhiều chi phí: deployment, observability, messaging, retries, data consistency, ownership và infrastructure.

Modular Monolith cố đạt phần lớn lợi ích về change isolation trước khi cần distributed-systems complexity.

## 3. How does it work?

Mỗi module nên có:

* domain/application logic riêng
* public contract rõ ràng
* private implementation không bị module khác truy cập trực tiếp
* data ownership có chủ đích

Ví dụ Orders không nên query trực tiếp `BillingDbContext`.

```text
Orders ── public contract/event ──> Billing
   X direct repository access
```

Có thể dùng cùng database vật lý nhưng ownership logic vẫn cần phân biệt schema/table responsibility.

## 4. Practical implementation

```csharp
public interface IBillingFacade
{
    Task<PaymentStatus> GetPaymentStatusAsync(
        Guid orderId,
        CancellationToken ct);
}
```

Orders chỉ depend vào contract; implementation Billing được đăng ký trong composition root.

Có thể thêm architecture tests để cấm namespace dependency sai:

```csharp
// pseudo-near-production intent
// Orders domain must not depend on Billing.Infrastructure
```

Quan trọng hơn tool là dependency rule được enforce trong build/review.

## 5. Real production scenario

Một SaaS ban đầu có Orders, Notifications, Documents và Billing trong một ASP.NET Core deployment.

Billing thay đổi thường xuyên do payment provider, trong khi Documents ổn định. Module boundary giúp Billing tiến hóa mà không để provider-specific code rò vào Orders.

Nếu sau này Billing cần scale/deploy độc lập, boundary đã tồn tại sẽ giảm extraction cost.

## 6. Failure scenario & troubleshooting

**Symptom** → thay schema Billing làm Orders test vỡ hàng loạt.

**Evidence** → Orders queries trực tiếp tables hoặc internal classes của Billing.

**Hypothesis** → module boundary chỉ tồn tại trên sơ đồ.

**Diagnosis** → dependency graph cho thấy cross-module infrastructure references.

**Fix** → đưa interaction qua contract/event; xác định data ownership.

**Verification** → module có thể thay implementation nội bộ mà consumer tests không cần sửa hàng loạt.

## 7. Common mistakes

* Chia folders rồi gọi đó là Modular Monolith.
* Shared project chứa toàn bộ domain models, phá ownership.
* Dùng MediatR như bằng chứng rằng boundary đã tốt.
* Tách database/schema quá sớm khi chưa có lý do.
* Tạo cross-module generic repository.

## 8. Alternatives

* Simple Layered Architecture: tốt cho application nhỏ, domain ít thay đổi.
* Microservices: phù hợp khi cần independent deployment/scale/ownership thật sự.
* Modular Monolith: middle ground khi business complexity cao nhưng operational scale chưa yêu cầu distribution.

## 9. Trade-offs

### Advantages

* Transaction đơn giản hơn Microservices.
* Deployment và debugging dễ hơn.
* Có đường tiến hóa tới service extraction.

### Costs / Risks

* Boundary chỉ mạnh nếu được enforce.
* Shared database có thể khuyến khích coupling.
* Một deployment vẫn có blast radius chung.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business boundary, không chỉ folder.

### Middle

Biết code qua contracts và tránh direct cross-module internals.

### Senior

Nhìn data ownership, coupling, transaction boundary và migration path.

### Technical Lead / Architect

Quyết định khi nào Modular Monolith đủ tốt và chỉ tách Microservice khi có deployment/scale/team boundary thực sự.

## 11. Key takeaway

* Boundary tốt quan trọng hơn số lượng processes.
* Modular Monolith giảm coupling mà giữ operational simplicity.
* Microservices nên là câu trả lời cho pressure thực tế, không phải mặc định của “Senior architecture”.

# 7. Azure Functions retry + idempotency: retry tự động chỉ an toàn khi side effect có thể được xử lý lặp lại

## 1. What is it?

Azure Functions có thể retry execution tùy trigger/configuration. Retry giúp vượt qua transient failure nhưng đồng thời làm cùng logical work có thể chạy nhiều lần.

Do đó function tạo side effect phải được thiết kế idempotent hoặc có deduplication.

```text
Message
  ↓
Function attempt 1 ──> writes DB ──> crash before completion
  ↓ retry
Function attempt 2 ──> same logical message again
```

## 2. Why does it exist?

Distributed systems không thể luôn biết chắc operation đã hoàn tất hay chưa khi network/process failure xảy ra.

Nếu platform không retry, transient failure làm mất work. Nếu retry, duplicate execution trở thành khả năng bình thường.

Engineering phải chọn reliability model và xử lý ambiguity đó.

## 3. How does it work?

Với message trigger, message settlement và retry behavior phụ thuộc trigger/service. At-least-once delivery nghĩa là handler phải chịu được message lặp lại.

Idempotency có thể dựa trên business key hoặc message ID lưu trong Inbox table.

```text
Receive MessageId=abc
      ↓
Inbox contains abc?
  yes -> no-op
  no  -> business change + mark abc processed
```

Tốt nhất business change và inbox marker nằm cùng transaction nếu cùng relational database.

## 4. Practical implementation

```csharp
public async Task HandleAsync(OrderPaid message, CancellationToken ct)
{
    var exists = await db.ProcessedMessages
        .AnyAsync(x => x.MessageId == message.MessageId, ct);

    if (exists)
        return;

    await using var tx = await db.Database.BeginTransactionAsync(ct);

    var order = await db.Orders.SingleAsync(x => x.Id == message.OrderId, ct);
    order.MarkPaid();

    db.ProcessedMessages.Add(new ProcessedMessage(message.MessageId));

    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
```

Unique constraint trên `MessageId` vẫn cần để xử lý race giữa concurrent duplicate deliveries.

## 5. Real production scenario

Function nhận payment-confirmed event. Attempt đầu cập nhật order thành Paid nhưng process crash trước khi message được settled. Message quay lại.

Nếu handler gửi email, cộng loyalty points và tạo invoice mỗi lần mà không deduplicate, customer nhận side effects trùng.

## 6. Failure scenario & troubleshooting

**Symptom** → một payment tạo hai invoices.

**Evidence** → cùng `MessageId` xuất hiện ở hai invocation logs.

**Hypothesis** → retry/duplicate delivery không được xử lý idempotently.

**Diagnosis** → code side effect chạy trước khi dedup state được atomically ghi.

**Fix** → Inbox/unique key/business idempotency; tách non-transactional side effects qua Outbox.

**Verification** → replay cùng message hàng chục lần; business state chỉ thay đổi đúng một lần.

## 7. Common mistakes

* Tin rằng queue “chỉ gửi một lần”.
* Dùng in-memory dedup cache làm correctness mechanism.
* Retry HTTP POST không có idempotency key.
* Mark message processed trước business transaction rồi crash.
* Giả định dead-letter nghĩa là không còn duplicate elsewhere.

## 8. Alternatives

* At-most-once: giảm duplicate nhưng có nguy cơ mất work.
* Exactly-once end-to-end: thường không thực tế qua nhiều systems.
* At-least-once + idempotent consumer: mô hình phổ biến và khả thi.

## 9. Trade-offs

### Advantages

* Resilient trước transient failures.
* Có thể safely replay.

### Costs / Risks

* Cần persistence/dedup logic.
* Storage của processed message cần retention strategy.
* Side effects bên ngoài transaction vẫn cần Outbox/compensation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry có thể chạy lại cùng work.

### Middle

Biết dùng unique key/Inbox cho idempotency.

### Senior

Nhìn transaction boundary giữa DB, message settlement và external side effects.

### Technical Lead / Architect

Chọn delivery semantics và định nghĩa idempotency contract toàn workflow thay vì chỉ sửa từng handler.

## 11. Key takeaway

* Retry không miễn phí; nó chuyển transient failure thành duplicate-execution risk.
* Idempotency là correctness property của distributed workflow.
* External side effects thường cần Outbox hoặc idempotency key riêng.

# 8. OpenTelemetry span links: liên kết async work và messaging khi parent-child trace không còn phản ánh đúng causal graph

## 1. What is it?

Trong tracing thông thường, spans tạo cây parent-child. Nhưng messaging/batch workflows đôi khi không phải cây đơn giản.

`Span Link` cho phép một span tham chiếu tới một hoặc nhiều trace/span contexts mà không biến chúng thành parent trực tiếp.

```text
Request A ─┐
Request B ─┼─> batch worker span
Request C ─┘      links A,B,C
```

## 2. Why does it exist?

Một queue consumer có thể process message được tạo từ request khác, hoặc batch job có thể gộp nhiều upstream events.

Ép mọi quan hệ causal thành parent-child tạo trace topology sai hoặc trace cực dài khó quản lý.

Links biểu diễn “work này có liên quan tới context kia” mà không bắt buộc cùng lifecycle tree.

## 3. How does it work?

Producer inject trace context vào message metadata. Consumer có thể:

* tiếp tục trace bằng parent context khi one-to-one relationship hợp lý
* hoặc tạo new span/new trace và add link tới producer context khi async boundary cần tách lifecycle

OpenTelemetry backend có thể dùng links để điều tra causal relationship dù UI hỗ trợ mức độ khác nhau.

## 4. Practical implementation

```csharp
var parentContext = Propagators.DefaultTextMapPropagator.Extract(
    default,
    message.ApplicationProperties,
    static (props, key) =>
        props.TryGetValue(key, out var value)
            ? new[] { value?.ToString() ?? string.Empty }
            : Array.Empty<string>());

var links = new[]
{
    new ActivityLink(parentContext.ActivityContext)
};

using var activity = ActivitySource.StartActivity(
    "ProcessBatchItem",
    ActivityKind.Consumer,
    default(ActivityContext),
    tags: null,
    links: links);
```

Implementation thực tế cần giữ propagation contract nhất quán giữa producers và consumers.

## 5. Real production scenario

Một notification worker gom 100 events từ nhiều requests thành một batch gửi provider. Một batch span không thể có 100 parents.

Links cho phép batch execution là trace riêng nhưng vẫn lưu quan hệ với từng originating event.

## 6. Failure scenario & troubleshooting

**Symptom** → queue latency tăng nhưng trace từ API dừng ở publish operation; consumer nhìn như unrelated workload.

**Evidence** → message metadata không chứa trace context hoặc consumer bỏ propagation.

**Hypothesis** → trace context mất qua messaging boundary.

**Diagnosis** → inspect message headers và instrumentation configuration.

**Fix** → standardize propagation, use parent or links theo semantics.

**Verification** → từ producer event có thể điều hướng tới consumer processing hoặc query bằng shared correlation dimensions.

## 7. Common mistakes

* Dùng correlation ID thủ công thay cho full tracing context rồi mất timing topology.
* Ép long-running async workflow thành một trace kéo dài hàng giờ.
* Không sanitize baggage chứa sensitive data.
* Tin rằng links tự động hiển thị đẹp trong mọi backend.

## 8. Alternatives

* Parent-child propagation: tốt cho request → single message → single consumer gần causal chain.
* Correlation ID: đơn giản hơn nhưng ít semantic/timing context.
* Span links: tốt cho fan-in, batch, replay hoặc lifecycle tách biệt.

## 9. Trade-offs

### Advantages

* Mô hình causal graph chính xác hơn.
* Tránh trace tree giả tạo.

### Costs / Risks

* Backend support khác nhau.
* Query/visualization phức tạp hơn.
* Instrumentation discipline cao hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace không phải lúc nào cũng chỉ là một cây request đơn.

### Middle

Biết propagate trace context qua HTTP/messaging.

### Senior

Phân biệt khi nào dùng parent, khi nào dùng link.

### Technical Lead / Architect

Định nghĩa observability conventions cho asynchronous architecture để trace topology phản ánh business causality thay vì implementation accident.

## 11. Key takeaway

* Parent-child phù hợp tree; links phù hợp causal graph phức tạp.
* Messaging observability cần propagation contract rõ ràng.
* Trace topology nên phục vụ diagnosis, không chỉ tạo càng nhiều spans càng tốt.

# 9. Playwright flaky tests: auto-waiting, deterministic state và cách phân biệt product bug với timing bug

## 1. What is it?

Flaky test là test cùng code/build nhưng lúc pass lúc fail do timing, shared state, network, nondeterminism hoặc environment instability.

Playwright có auto-waiting cho nhiều actions/assertions, nhưng auto-waiting không thể sửa một test có state model sai.

Mental model:

```text
Deterministic setup
   ↓
User-visible action
   ↓
Observable condition
   ↓
Assertion
```

## 2. Why does it exist?

Browser apps là asynchronous systems: rendering, API calls, animations, retries và background state changes xảy ra không đồng bộ.

Test dùng fixed sleep:

```ts
await page.waitForTimeout(2000);
```

đang đoán thời gian thay vì chờ condition. Khi CI chậm hơn hoặc nhanh hơn local, test trở nên flaky.

## 3. How does it work?

Playwright locator/action thường chờ element đạt actionability conditions. Assertions như `toBeVisible()` cũng retry tới timeout.

Do đó pattern tốt là chờ observable business/UI state:

```ts
await page.getByRole('button', { name: 'Save' }).click();
await expect(page.getByText('Saved successfully')).toBeVisible();
```

Thay vì sleep rồi hy vọng save đã xong.

## 4. Practical implementation

```ts
test('user can update profile', async ({ page, request }) => {
  const user = await createIsolatedUser(request);

  await page.goto(`/users/${user.id}`);
  await page.getByLabel('Display name').fill('Ha Nguyen');
  await page.getByRole('button', { name: 'Save' }).click();

  await expect(page.getByText('Saved successfully')).toBeVisible();
  await expect(page.getByLabel('Display name')).toHaveValue('Ha Nguyen');
});
```

Mỗi test có test data riêng giúp loại shared-state race.

## 5. Real production scenario

Suite E2E chạy parallel trên CI. Nhiều tests dùng cùng account và sửa cùng shopping cart. Test fail ngẫu nhiên vì state của test khác chen vào, không phải vì UI timing.

Tăng timeout chỉ che symptom. Root cause là shared test state.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail 1/20 lần ở CI, local thường pass.

**Evidence** → trace/video cho thấy element xuất hiện đúng nhưng dữ liệu thuộc test khác.

**Hypothesis** → shared fixture/state collision.

**Diagnosis** → correlate user/order IDs giữa parallel workers.

**Fix** → isolated data per test; deterministic setup; condition-based waits.

**Verification** → chạy test lặp lại và parallel nhiều lần; flake rate về 0 hoặc threshold chấp nhận được.

## 7. Common mistakes

* Dùng `waitForTimeout` thay cho condition.
* Retry toàn test để “làm CI xanh”.
* Shared account/shared records giữa tests.
* Assert implementation detail thay vì behavior.
* Mock quá nhiều khiến E2E không còn kiểm tra integration thật.

## 8. Alternatives

* Integration tests: nhanh và ổn định hơn cho API/database flows.
* Component tests: tốt cho UI behavior cô lập.
* E2E: nên giữ cho critical user journeys, không phải mọi branch logic.

## 9. Trade-offs

### Advantages

* Bảo vệ integration thật từ browser tới backend.
* Phát hiện routing/auth/network/UI regressions.

### Costs / Risks

* Chậm hơn.
* Nhạy với environment/state.
* Debug khó hơn unit/integration tests.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu wait phải dựa trên condition, không phải sleep.

### Middle

Biết dùng locators, auto-waiting, trace và isolated fixtures.

### Senior

Phân biệt product race condition, test race và environment issue bằng evidence.

### Technical Lead / Architect

Định nghĩa test strategy để E2E chỉ bảo vệ risk có giá trị, còn correctness phần lớn được cover ở lớp nhanh và deterministic hơn.

## 11. Key takeaway

* Flakiness là engineering signal, không phải lý do tăng retry vô hạn.
* Deterministic data quan trọng ngang auto-waiting.
* E2E test nên bảo vệ critical journeys, không thay thế integration/unit testing.

# 10. Optimizely CMS content caching: content version, published state và invalidation trong hệ thống editorial có nhiều nodes

## 1. What is it?

Trong CMS, cache không chỉ là “cache page HTML”. Optimizely và các CMS tương tự có nhiều lớp state: content identity, language/version, published state, content references, rendered fragments và potentially CDN output.

Mental model:

```text
Editor publishes content
      ↓
CMS content state changes
      ↓
application cache invalidation
      ↓
rendered output changes
      ↓
CDN may still hold old response
```

Caching đúng phải tôn trọng lifecycle editorial và distributed deployment.

## 2. Why does it exist?

CMS pages thường đọc nhiều content blocks, metadata và references. Nếu mọi request đều hydrate toàn bộ content tree từ persistent store, latency và database load tăng mạnh.

Caching giúp read-heavy workloads, nhưng stale content sau publish là correctness problem rõ ràng với editors.

## 3. How does it work?

CMS thường cache content objects theo identity/version/language và phát invalidation events khi publish/change xảy ra.

Trong multi-node setup, invalidation phải propagate giữa nodes. Ngoài ra reverse proxy/CDN có cache riêng nên application invalidation không đảm bảo edge content đã mới.

```text
Node A publish
  ↓
invalidation event
  ├─> Node A cache
  ├─> Node B cache
  └─> Node C cache

CDN cache: separate lifecycle
```

## 4. Practical implementation

Application-level custom cache key phải chứa dimensions thực sự ảnh hưởng output:

```csharp
var key = $"hero:{contentLink.ID}:{language}:{contentVersion}";
```

Nếu chỉ dùng `contentLink.ID`, preview/published version hoặc language variants có thể collide.

Với HTTP caching, response public chỉ nên cache khi không chứa user-specific/personalized data.

```http
Cache-Control: public, max-age=60, stale-while-revalidate=300
```

Policy thực tế phải align với editorial freshness requirement.

## 5. Real production scenario

Marketing publish legal disclaimer mới lúc 10:00. CMS backoffice thấy version mới ngay, nhưng một số visitors qua CDN vẫn nhận HTML cũ 15 phút.

Application logs cho thấy content mới được render đúng ở origin. Root cause nằm ở edge TTL/purge, không phải Optimizely content cache.

## 6. Failure scenario & troubleshooting

**Symptom** → editor thấy content mới trong preview nhưng public site vẫn cũ.

**Evidence** → origin bypass trả mới; CDN response có `Age` cao và cache-hit header.

**Hypothesis** → stale edge cache.

**Diagnosis** → kiểm tra từng layer: CMS version → node cache → rendered response → CDN.

**Fix** → purge/invalidation phù hợp hoặc giảm TTL cho content class đó.

**Verification** → request từ nhiều POPs/regions phải nhận expected version và headers đúng.

## 7. Common mistakes

* Cache key bỏ qua language/version.
* Cache personalized response như public.
* Purge toàn site cho mỗi publish, gây origin spike.
* Debug stale content chỉ ở application layer mà quên CDN.
* Tự tạo cache song song với CMS cache nhưng không có invalidation ownership.

## 8. Alternatives

* Không custom cache: tốt khi CMS built-in caching đã đủ.
* Application fragment cache: hữu ích cho expensive composition có invalidation rõ.
* CDN caching: giảm origin traffic mạnh nhưng freshness/invalidation phức tạp hơn.

## 9. Trade-offs

### Advantages

* Giảm latency và database/content-store pressure.
* Scale read-heavy marketing traffic tốt.

### Costs / Risks

* Stale content.
* Invalidation complexity tăng theo số layers.
* Personalized content dễ bị cache sai nếu policy không chặt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CMS content có version/language/publish state, không chỉ một row tĩnh.

### Middle

Biết thiết kế cache key và phân biệt origin cache với CDN cache.

### Senior

Điều tra stale content xuyên nhiều layers bằng headers, cache metadata và content version evidence.

### Technical Lead / Architect

Quyết định layer nào sở hữu caching/invalidation, freshness SLA nào business thật sự cần và khi nào purge scope phải được giới hạn để tránh origin thundering herd.

## 11. Key takeaway

* CMS caching là multi-layer consistency problem, không chỉ performance trick.
* Invalidation ownership phải rõ giữa CMS, application và CDN.
* Khi content stale, debug theo từng layer thay vì đoán “cache bị lỗi”.
