# 1. C# records, equality và hash collections: value semantics rất hữu ích nhưng mutable state có thể làm `Dictionary`/`HashSet` hành xử sai khó đoán

## 1. What is it?

`record` trong C# cung cấp **value-based equality** thuận tiện hơn class thông thường. Hai record có cùng dữ liệu thành phần có thể được xem là bằng nhau dù là hai object khác nhau.

Mental model:

```text
class equality mặc định  -> identity/reference
record equality mặc định -> values/components
```

Điểm quan trọng không phải cú pháp `record` ngắn hơn class, mà là semantics của equality, immutability-by-convention và cách compiler sinh `Equals`, `GetHashCode`, `Deconstruct`, `with` expression.

Khi object được dùng làm key của `Dictionary<TKey, TValue>` hoặc member của `HashSet<T>`, `GetHashCode()` và `Equals()` phải giữ một invariant quan trọng: **trong thời gian object đang ở trong hash collection, các giá trị tham gia hash/equality không nên thay đổi**.

## 2. Why does it exist?

Nhiều domain concepts thực sự được nhận diện bởi value thay vì object identity: Money, Coordinates, DateRange, Address snapshot, configuration value.

Trước `record`, developer thường phải tự implement `IEquatable<T>`, `Equals`, `GetHashCode`, copy constructor và immutable update pattern. Điều này verbose và dễ sai.

`record` giảm boilerplate, nhưng value semantics tạo ra một trách nhiệm mới: nếu bạn mutate member tham gia equality sau khi object đã được hash, hash bucket cũ không còn khớp với hash mới.

## 3. How does it work?

`HashSet<T>` không scan toàn bộ collection mỗi lần lookup. Nó tính hash code để chọn bucket rồi mới so `Equals` trong bucket đó.

Ví dụ:

```text
CustomerKey("VN", 1001)
hash = 8123
        |
        v
bucket 8123
```

Nếu sau khi add vào set bạn đổi `Country` thành `US`, object có thể có hash mới là 9921 nhưng vẫn đang nằm vật lý trong bucket 8123. `Contains` tính hash mới, tìm bucket 9921 và có thể kết luận "không tồn tại" dù object vẫn nằm trong set.

Đây là lý do immutable value objects hợp với hash collections hơn mutable objects.

## 4. Practical implementation

Một immutable value object phù hợp:

```csharp
public sealed record Money(decimal Amount, string Currency)
{
    public Money Add(Money other)
    {
        if (!string.Equals(Currency, other.Currency, StringComparison.Ordinal))
            throw new InvalidOperationException("Currency mismatch");

        return this with { Amount = Amount + other.Amount };
    }
}
```

Dùng làm key:

```csharp
var prices = new Dictionary<Money, string>();
var key = new Money(100m, "USD");

prices[key] = "Standard";

Console.WriteLine(prices.ContainsKey(new Money(100m, "USD"))); // true
```

Nếu cần mutable aggregate/entity, đừng chọn toàn bộ mutable properties làm identity chỉ vì record làm điều đó dễ dàng.

## 5. Real production scenario

Một pricing engine dùng `HashSet<ProductPriceKey>` để deduplicate item theo `ProductId + Currency + PriceList`. Developer dùng mutable record class rồi đổi `Currency` sau normalization.

Kết quả:

```text
Add key -> normalize currency -> Contains(key) == false
```

System bắt đầu tạo duplicate price rows. Bug chỉ xảy ra với một số data path vì object chỉ bị mutate sau khi đã nằm trong set.

## 6. Failure scenario & troubleshooting

**Symptom:** `HashSet.Contains(x)` trả `false` dù debugger cho thấy object có trong collection.

**Evidence:** property tham gia equality/hash thay đổi sau `Add`; hash code trước/sau khác nhau.

**Hypothesis:** hash invariant bị phá.

**Diagnosis:** log hoặc debug `GetHashCode()` trước và sau mutation; kiểm tra generated/custom equality members.

**Fix:** làm key immutable; tạo object mới sau normalization; hoặc dùng explicit stable key type.

**Verification:** unit test mutation scenario và test deduplication qua toàn bộ pipeline.

## 7. Common mistakes

- Dùng `record` cho entity rồi vô tình coi tất cả properties là identity.
- Cho mutable property tham gia `GetHashCode()`.
- Override `Equals` nhưng không giữ contract tương ứng với `GetHashCode()`.
- Dùng `with` rồi tưởng nested mutable reference cũng được deep-copy.
- Dùng value equality cho object mà business identity thực ra là `Id`.

## 8. Alternatives

- **Class + explicit identity equality:** tốt cho entity có lifecycle riêng.
- **`readonly record struct`:** phù hợp small immutable values, nhưng cần chú ý copying cost với struct lớn.
- **Primitive/stable key:** dùng tuple/string/ID khi chỉ cần dictionary key đơn giản.

## 9. Trade-offs

### Advantages

- Value semantics rõ ràng và ít boilerplate.
- `with` expression thuận tiện cho immutable updates.
- Tốt cho value objects, messages và snapshots.

### Costs / Risks

- Generated equality có thể không khớp business identity.
- Shallow immutability: record vẫn có thể chứa mutable collections/references.
- Hash-based bugs rất khó thấy khi mutable state bị thay đổi sau insertion.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác nhau giữa reference equality và value equality.

### Middle

Biết thiết kế immutable record, custom equality khi cần và test với `Dictionary`/`HashSet`.

### Senior

Nhận diện equality semantics là domain decision, không chỉ language feature; hiểu hash invariants và mutable graph traps.

### Technical Lead / Architect

Quyết định loại nào là Entity, Value Object, DTO hay message; chuẩn hóa identity semantics để tránh mỗi team tự định nghĩa khác nhau.

## 11. Key takeaway

- `record` mạnh nhất khi value semantics thực sự đúng với domain.
- Object dùng làm hash key nên có stable equality/hash trong suốt thời gian nằm trong collection.
- Immutability là correctness tool, không chỉ code style.

# 2. ASP.NET Core middleware ordering: authentication, authorization, CORS, exception handling và endpoint routing chỉ đúng khi pipeline đúng thứ tự

## 1. What is it?

ASP.NET Core middleware pipeline là chuỗi components xử lý request/response theo thứ tự đăng ký.

Mental model:

```text
Request  -> M1 -> M2 -> M3 -> Endpoint
Response <- M1 <- M2 <- M3 <- Endpoint
```

Mỗi middleware có thể làm việc trước `next()`, gọi middleware kế tiếp, rồi làm thêm việc sau khi downstream trả về. Vì vậy thứ tự không chỉ ảnh hưởng feature nào chạy trước; nó còn quyết định middleware nào có thể quan sát, chặn hoặc transform request/response của middleware khác.

## 2. Why does it exist?

HTTP application có cross-cutting concerns: exception handling, HTTPS, static files, CORS, authentication, authorization, rate limiting, routing, metrics.

Nếu tất cả logic nằm trong controller, code bị lặp và boundary không rõ. Middleware cho phép composition quanh request lifecycle.

Nhưng composition chỉ đúng nếu dependency order đúng. Authorization cần identity đã được authentication thiết lập; exception handler cần đứng đủ sớm để catch lỗi từ downstream; CORS headers phải xuất hiện trên responses mà browser cần đọc.

## 3. How does it work?

Một pipeline phổ biến:

```text
Exception handler
    -> HTTPS / forwarded headers
    -> Routing
    -> CORS
    -> Authentication
    -> Authorization
    -> Rate limiting / endpoint policies
    -> Endpoint
```

Chi tiết thực tế phụ thuộc hosting/version/features, nhưng nguyên tắc là: **middleware downstream chỉ có thể dùng state mà upstream đã chuẩn bị**.

Authentication thường populate `HttpContext.User`; authorization đánh giá policies dựa trên user + endpoint metadata.

## 4. Practical implementation

```csharp
var app = builder.Build();

app.UseExceptionHandler();
app.UseHttpsRedirection();

app.UseRouting();
app.UseCors("Frontend");
app.UseAuthentication();
app.UseAuthorization();
app.UseRateLimiter();

app.MapControllers();

app.Run();
```

Không copy thứ tự này mù quáng vào mọi app. Ví dụ static file, reverse proxy, path base, forwarded headers hoặc custom tenant resolution có dependency riêng. Hãy xác định middleware đó **đọc state gì** và **tạo state gì**.

## 5. Real production scenario

SPA gọi API bằng bearer token. Sau refactor, team đặt custom authorization middleware trước `UseAuthentication()`.

Local test anonymous endpoint vẫn chạy, nhưng production protected endpoint trả `403` dù JWT hợp lệ vì `HttpContext.User` chưa được populate tại thời điểm custom middleware kiểm tra claim.

Một case khác: exception middleware đặt sau endpoints nên exceptions từ controller không được transform thành chuẩn `ProblemDetails`.

## 6. Failure scenario & troubleshooting

**Symptom:** token hợp lệ nhưng user bị coi anonymous; browser báo CORS error chỉ trên 401/500 responses.

**Evidence:** log pipeline cho thấy auth handler chưa chạy trước policy check; response lỗi thiếu CORS headers.

**Hypothesis:** middleware ordering sai.

**Diagnosis:** bật ASP.NET Core logs, inspect endpoint metadata, `HttpContext.User`, response headers; tạo integration test cho auth/CORS/error path.

**Fix:** sắp xếp lại theo dependency; bỏ custom middleware nếu built-in authorization policy đã giải quyết đúng vấn đề.

**Verification:** test success, 401, 403, validation error và exception path từ browser/integration test.

## 7. Common mistakes

- Nghĩ middleware giống event subscribers và thứ tự không quan trọng.
- Custom authorization trước authentication.
- Exception middleware quá muộn.
- CORS chỉ test happy path, không test 401/500.
- Gọi `next()` hai lần hoặc quên `await`.
- Viết middleware singleton nhưng giữ request-specific mutable state trong field.

## 8. Alternatives

- **Filters:** phù hợp MVC/action-specific concerns.
- **Endpoint filters:** phù hợp Minimal APIs ở endpoint boundary.
- **Authorization policies:** tốt hơn custom middleware cho permission logic.
- **DelegatingHandler:** dành cho outbound `HttpClient`, không phải inbound request pipeline.

## 9. Trade-offs

### Advantages

- Cross-cutting concerns được centralized.
- Composition rõ và testable.
- Có thể short-circuit request sớm.

### Costs / Risks

- Ordering dependency tạo implicit coupling.
- Middleware quá nhiều làm request path khó reasoning.
- Custom middleware dễ duplicate built-in behavior hoặc làm sai security boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request đi theo thứ tự đăng ký và response quay ngược lại.

### Middle

Biết chọn middleware/filter/policy đúng scope và viết integration tests cho pipeline.

### Senior

Debug state propagation, short-circuit, auth/CORS/error interactions và performance overhead.

### Technical Lead / Architect

Thiết kế cross-cutting concerns sao cho ordering dependency tối thiểu, ưu tiên framework primitives trước custom plumbing.

## 11. Key takeaway

- Middleware ordering là behavior, không phải formatting của `Program.cs`.
- Mỗi middleware nên có rõ input state và output state cho downstream.
- Auth, CORS và exception paths phải được integration-test, không chỉ happy path.

# 3. MongoDB compound indexes và ESR thinking: index order phải phục vụ equality, sort và range theo access pattern thực tế

## 1. What is it?

Compound index là index chứa nhiều fields theo một thứ tự xác định, ví dụ:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

Thứ tự fields quyết định query patterns nào có thể tận dụng index hiệu quả. MongoDB không coi compound index như “ba single-field indexes ghép lại”.

Một mental model hữu ích là ESR: **Equality → Sort → Range**. Đây là heuristic, không phải luật tuyệt đối, nhưng giúp thiết kế index dựa trên query shape.

## 2. Why does it exist?

Production query thường vừa filter vừa sort:

```text
tenant = X
status = Active
sort by createdAt desc
createdAt < cursor
```

Nếu chỉ tạo index riêng cho từng field, database vẫn có thể phải scan nhiều documents hoặc sort in memory. Compound index sắp xếp keys theo một cấu trúc có thể đáp ứng nhiều phần của query trong cùng access path.

## 3. How does it work?

Index:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

có prefix:

```text
tenantId
 tenantId + status
 tenantId + status + createdAt
```

Query có equality trên `tenantId`, `status` rồi sort/range trên `createdAt` có thể đi liên tục trong vùng index phù hợp.

Nếu đặt range field quá sớm, ví dụ `{ createdAt: -1, tenantId: 1 }`, database có thể phải scan một vùng thời gian lớn cho nhiều tenants rồi mới filter.

## 4. Practical implementation

Query:

```javascript
db.orders.find({
  tenantId: "acme",
  status: "Pending",
  createdAt: { $lt: ISODate("2026-09-13T00:00:00Z") }
})
.sort({ createdAt: -1 })
.limit(50)
```

Index candidate:

```javascript
db.orders.createIndex({
  tenantId: 1,
  status: 1,
  createdAt: -1
})
```

Luôn kiểm chứng bằng `explain("executionStats")`:

```javascript
db.orders.find({...})
  .sort({ createdAt: -1 })
  .limit(50)
  .explain("executionStats")
```

Quan sát `totalKeysExamined`, `totalDocsExamined`, returned rows và sort stage thay vì chỉ nhìn `IXSCAN` rồi kết luận “đã tối ưu”.

## 5. Real production scenario

Một SaaS có collection 80 triệu orders của hàng nghìn tenants. API `GET /orders?status=Pending` sort newest first.

Index ban đầu chỉ là `{ createdAt: -1 }`. Query vẫn dùng index nhưng phải scan rất nhiều keys từ tenants khác trước khi tìm đủ 50 rows của tenant hiện tại.

Đổi sang compound index theo access pattern làm keys examined giảm hàng nghìn lần.

## 6. Failure scenario & troubleshooting

**Symptom:** query trả 50 rows nhưng latency p95 tăng theo data size.

**Evidence:** `nReturned=50`, nhưng `totalKeysExamined=200000`, `totalDocsExamined` cao.

**Hypothesis:** index order không match selective equality + sort pattern.

**Diagnosis:** lấy real query shape, cardinality, explain stats và index inventory.

**Fix:** thiết kế compound index phù hợp; loại redundant index nếu không còn workload dùng.

**Verification:** so keys/docs examined, latency và write overhead trước/sau dưới representative data.

## 7. Common mistakes

- Tạo index cho từng field rồi nghĩ planner sẽ luôn combine tối ưu.
- Áp ESR như luật cứng mà không đo selectivity/workload.
- Index mọi query, làm write amplification và storage tăng mạnh.
- Không xem sort direction/prefix.
- Chỉ test với dev database vài nghìn documents.
- Không tính multi-tenant cardinality/hot tenants.

## 8. Alternatives

- **Single-field index:** đủ nếu query thực sự chỉ phụ thuộc một field.
- **Partial index:** hữu ích nếu chỉ subset documents cần index.
- **Wildcard index:** linh hoạt với schema dynamic nhưng không thay thế thiết kế access pattern cho hot queries.
- **Different document model:** đôi khi query chậm là modeling problem, không phải index problem.

## 9. Trade-offs

### Advantages

- Compound index có thể vừa filter vừa sort rất hiệu quả.
- Giảm scanned documents và latency.

### Costs / Risks

- Mỗi index làm write/update tốn thêm CPU/I/O/storage.
- Field order phục vụ workload này có thể không phục vụ workload khác.
- Index proliferation làm operational maintenance phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu compound index có thứ tự và prefix.

### Middle

Dùng `explain`, đọc keys/docs examined và thiết kế index theo query thật.

### Senior

Cân nhắc selectivity, sort, range, write amplification và multi-tenant distribution.

### Technical Lead / Architect

Quản lý index như một phần của data access architecture: inventory, ownership, capacity cost và deprecation strategy.

## 11. Key takeaway

- Index order phải bắt đầu từ access pattern, không từ schema fields.
- `IXSCAN` chưa đủ; keys/docs examined mới cho thấy hiệu quả thực.
- Index tốt cho read có cost trực tiếp lên write và storage.

# 4. DDD Bounded Context và Anti-Corruption Layer: cô lập business language và model ownership thay vì chia service theo bảng

## 1. What is it?

**Bounded Context** là boundary trong đó một domain model và vocabulary có ý nghĩa nhất quán.

Một từ có thể mang nghĩa khác ở context khác:

```text
Sales:    Customer = người mua hàng
Billing:  Customer = account chịu trách nhiệm thanh toán
Support:  Customer = contact / organization cần hỗ trợ
```

Không nhất thiết phải ép ba contexts dùng một `Customer` class duy nhất.

**Anti-Corruption Layer (ACL)** là lớp translation bảo vệ model nội bộ khỏi semantics/model của external hoặc legacy context.

## 2. Why does it exist?

Enterprise systems thường thất bại không phải vì thiếu layers, mà vì một “canonical model” khổng lồ bị mọi team dùng chung. Khi một field thay đổi nghĩa, blast radius lan khắp hệ thống.

Bounded Context cho phép model tối ưu theo business responsibility. ACL ngăn external terminology và quirks lan vào core model.

## 3. How does it work?

Ví dụ:

```text
Sales Context
  Order, Buyer, Promotion
       |
       | Integration contract
       v
Billing ACL
       |
       v
Billing Context
  Invoice, Account, PaymentTerm
```

Data ownership nên rõ: Sales sở hữu Order lifecycle; Billing sở hữu Invoice/payment state. Integration có thể sync facts cần thiết nhưng không tạo shared mutable database ownership mơ hồ.

Transaction thường dừng ở context boundary. Cross-context consistency thường cần messaging, idempotency hoặc workflow coordination thay vì một transaction xuyên mọi model.

## 4. Practical implementation

Application-owned contract:

```csharp
public sealed record CreateInvoiceRequest(
    Guid OrderId,
    string BillingAccountId,
    decimal Amount,
    string Currency);

public interface IBillingGateway
{
    Task<InvoiceReference> CreateInvoiceAsync(
        CreateInvoiceRequest request,
        CancellationToken ct);
}
```

ACL adapter map Sales concepts sang Billing contract thay vì expose trực tiếp vendor/legacy DTO vào domain.

```csharp
public sealed class BillingAcl : IBillingGateway
{
    private readonly BillingClient _client;

    public async Task<InvoiceReference> CreateInvoiceAsync(
        CreateInvoiceRequest request,
        CancellationToken ct)
    {
        var legacy = new LegacyInvoiceDto
        {
            ExternalOrderNo = request.OrderId.ToString(),
            DebtorCode = request.BillingAccountId,
            GrossAmount = request.Amount,
            IsoCurrency = request.Currency
        };

        var result = await _client.CreateAsync(legacy, ct);
        return new InvoiceReference(result.InvoiceNo);
    }
}
```

## 5. Real production scenario

Một commerce platform có CMS, product, checkout và finance. Ban đầu mọi service dùng chung `Product` DTO.

CMS cần editorial fields, Search cần denormalized searchable text, Checkout cần purchasability/price snapshot, Finance chỉ cần accounting references.

Shared model liên tục phình và mỗi thay đổi bắt buộc synchronized release. Tách bounded contexts giúp mỗi model phản ánh responsibility riêng.

## 6. Failure scenario & troubleshooting

**Symptom:** sửa field trong “shared domain package” kéo theo 12 services phải deploy; teams tranh luận một field tên gì vì mỗi domain hiểu khác nhau.

**Evidence:** shared assemblies/DB tables bị nhiều contexts mutate; DTO vendor xuất hiện sâu trong domain code.

**Hypothesis:** context boundary và ownership không rõ.

**Diagnosis:** map business capabilities, data owners, vocabulary conflicts và change coupling.

**Fix:** định nghĩa context boundaries; tạo explicit contracts/ACL tại high-friction boundaries; migrate dần thay vì rewrite toàn hệ thống.

**Verification:** thay đổi nội bộ một context không còn bắt buộc cascade deploy ở context khác trừ khi public contract đổi.

## 7. Common mistakes

- Đồng nhất Bounded Context với Microservice.
- Chia context theo database table (`CustomerService`, `OrderService`) mà không xét business capability.
- Tạo một `SharedKernel` khổng lồ để “reuse”.
- Duplicate data là thấy sai ngay; trong distributed contexts, local read model có thể là trade-off hợp lý.
- ACL chỉ rename fields nhưng không translate semantics.

## 8. Alternatives

- **Simple modular/layered model:** tốt khi domain nhỏ và vocabulary thực sự nhất quán.
- **Shared Kernel nhỏ:** hợp lý cho concepts ổn định, ownership rõ và governance chặt.
- **Direct integration:** chấp nhận được với low-risk internal boundary nếu mapping layer không tạo giá trị.

## 9. Trade-offs

### Advantages

- Change isolation và ownership rõ.
- Model phù hợp business responsibility thay vì compromise toàn doanh nghiệp.
- Legacy/vendor semantics được cô lập.

### Costs / Risks

- Mapping và data duplication tăng.
- Cross-context workflows cần eventual consistency/coordination.
- Boundary sai có thể tạo excessive integration overhead.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cùng một business noun không nhất thiết có một model toàn hệ thống.

### Middle

Biết map contracts giữa modules/services và giữ vendor DTO ngoài core logic.

### Senior

Nhìn ra semantic coupling, transaction boundary và data ownership problems.

### Technical Lead / Architect

Định nghĩa contexts dựa trên business capability/change patterns; quyết định boundary nào cần ACL và boundary nào không đáng complexity.

## 11. Key takeaway

- Bounded Context là semantic/business boundary, không phải deployment boundary mặc định.
- Một “universal domain model” thường tạo coupling nhiều hơn reuse hữu ích.
- ACL đáng dùng nơi external model có semantics khác hoặc change risk cao.

# 5. Idempotency Key cho HTTP POST và external side effects: retry an toàn mà không tạo payment/order/email trùng

## 1. What is it?

Một operation **idempotent** khi thực hiện lại cùng intent không tạo thêm effect ngoài kết quả logic ban đầu.

`GET` thường naturally idempotent. `POST /payments` thì không: client timeout sau khi server đã charge card có thể khiến retry tạo charge thứ hai.

Idempotency Key cho phép client gắn một stable operation identifier:

```http
POST /payments
Idempotency-Key: 8f9c...
```

Server lưu trạng thái/kết quả gắn với key và không thực thi side effect lần hai cho cùng operation.

## 2. Why does it exist?

Network không cung cấp “exactly once request delivery”. Một timeout chỉ nói caller không nhận response, không nói server có thực hiện operation hay chưa.

```text
Client -> Server: create payment
Server -> Provider: charged successfully
Server -> Client: response LOST
Client: timeout -> retry
```

Không có idempotency, retry — vốn là reliability mechanism — trở thành duplicate side-effect mechanism.

## 3. How does it work?

Server thường lưu:

```text
IdempotencyKey
RequestFingerprint
Status: InProgress / Succeeded / Failed-retryable
StoredResponse or ResourceId
ExpiresAt
```

Nếu key mới: reserve key atomically rồi execute.
Nếu key cũ + cùng request fingerprint + completed: trả lại stored result.
Nếu key cũ nhưng payload khác: reject conflict.
Nếu in-progress: wait/poll/reject tùy protocol.

Atomicity giữa key reservation và business write rất quan trọng.

## 4. Practical implementation

Simplified relational model:

```sql
CREATE TABLE IdempotencyRequests (
    IdempotencyKey varchar(100) NOT NULL PRIMARY KEY,
    RequestHash varchar(64) NOT NULL,
    ResourceId uniqueidentifier NULL,
    Status varchar(20) NOT NULL,
    CreatedAtUtc datetime2 NOT NULL
);
```

Pseudo-realistic transaction:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

var existing = await db.IdempotencyRequests
    .SingleOrDefaultAsync(x => x.IdempotencyKey == key, ct);

if (existing is not null)
    return ResolveExisting(existing, requestHash);

var record = new IdempotencyRequest(key, requestHash, "InProgress");
db.Add(record);
await db.SaveChangesAsync(ct); // PK uniqueness resolves race

var payment = Payment.Create(command);
db.Add(payment);

record.MarkSucceeded(payment.Id);
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Nếu external payment provider là side effect ngoài DB transaction, cần provider idempotency key hoặc workflow/outbox/inbox strategy phù hợp; local transaction một mình không đủ.

## 5. Real production scenario

Mobile app gọi checkout qua mạng 4G. Server tạo order thành công nhưng response rơi. App retry sau 3 giây.

Với idempotency key được tạo per checkout attempt, API trả lại cùng `OrderId` thay vì tạo Order thứ hai. Nếu payment provider cũng hỗ trợ idempotency, cùng key hoặc mapped provider key ngăn double charge.

## 6. Failure scenario & troubleshooting

**Symptom:** một user có hai orders/payments cùng vài giây, thường đi kèm client timeout.

**Evidence:** request logs có cùng business intent nhưng khác request IDs; provider charge timestamps gần nhau.

**Hypothesis:** retry không có idempotency boundary.

**Diagnosis:** trace client retry policy, gateway retries và server transaction timing.

**Fix:** define idempotency contract, unique key storage, request fingerprint và provider-side idempotency khi có.

**Verification:** fault-injection: drop response sau commit rồi retry cùng key; chỉ một side effect được tạo.

## 7. Common mistakes

- Dùng random key mới cho mỗi retry — mất toàn bộ tác dụng.
- Chỉ cache HTTP response in-memory trên một instance.
- Không validate cùng key có cùng payload/intent.
- Xóa key quá sớm trong khi client còn có thể retry.
- Nghĩ database transaction biến remote API call thành exactly-once.
- Retry non-idempotent dependency một cách mù quáng.

## 8. Alternatives

- **Natural business key + unique constraint:** tốt nếu domain đã có stable unique intent identifier.
- **PUT với client-chosen resource ID:** naturally idempotent trong một số APIs.
- **Message deduplication/inbox:** phù hợp asynchronous consumers.
- **No retry:** đơn giản hơn nhưng giảm reliability và UX nếu operation có thể thiết kế idempotent.

## 9. Trade-offs

### Advantages

- Cho phép retry an toàn hơn.
- Giảm duplicate financial/business side effects.
- Tạo audit trail rõ cho operation attempt.

### Costs / Risks

- Cần persistent state, TTL và cleanup.
- In-progress race và partial failure phức tạp.
- Stored response có thể chứa sensitive data nếu thiết kế sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không có nghĩa operation thất bại.

### Middle

Implement unique key, fingerprint và duplicate path có test.

### Senior

Reason về races, remote side effects, retry semantics và key retention.

### Technical Lead / Architect

Định nghĩa idempotency contract xuyên client/API/provider/message boundaries và xác định operation nào bắt buộc có.

## 11. Key takeaway

- Retry và idempotency phải được thiết kế cùng nhau.
- “Request thất bại ở client” không đồng nghĩa side effect chưa xảy ra ở server.
- Exactly-once end-to-end thường là illusion; durable deduplication và idempotent effects thực tế hơn.

# 6. Azure Container Apps revisions, traffic splitting và scale-to-zero: deployment linh hoạt nhưng cần hiểu cold start, concurrency và downstream capacity

## 1. What is it?

Azure Container Apps (ACA) là managed container platform cho HTTP services, workers và event-driven workloads mà không phải quản lý Kubernetes cluster trực tiếp.

Một **revision** đại diện immutable version của app configuration/container image theo revision model. Nhiều revisions có thể tồn tại đồng thời và HTTP traffic có thể được split giữa chúng.

ACA có autoscaling dựa trên KEDA-style triggers và có thể scale xuống zero trong nhiều workload types.

## 2. Why does it exist?

App Service đơn giản cho web apps; AKS mạnh nhưng operational burden cao. ACA nằm giữa: container portability, revisions, autoscaling và managed ingress mà team không cần vận hành control plane Kubernetes.

Traffic splitting hỗ trợ canary/blue-green style rollout. Scale-to-zero giảm compute cost cho workload ít traffic, nhưng đổi lại cold start và dependency burst risk.

## 3. How does it work?

Simplified flow:

```text
Client
  -> ACA ingress
      -> Revision A (90%)
      -> Revision B (10%)
           -> replicas scale based on trigger
```

Khi traffic tăng, scaler tạo replicas mới. Nhưng scale-out không tức thì: image pull/startup/readiness cần thời gian.

Mỗi replica mới đồng thời có thể mở DB connections, Redis connections hoặc call downstream APIs. Vì vậy app tier scale tốt không có nghĩa toàn architecture scale tốt.

## 4. Practical implementation

Application cần startup/readiness nhẹ và external config qua environment/secrets/identity.

Ví dụ ASP.NET Core health endpoints:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(builder.Configuration.GetConnectionString("Sql")!);

var app = builder.Build();

app.MapHealthChecks("/health/live", new()
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready");
```

Đừng biến liveness thành dependency check nặng khiến temporary SQL issue restart containers khỏe. Readiness có thể phản ánh khả năng phục vụ traffic; liveness nên trả lời process có cần restart hay không.

## 5. Real production scenario

API marketing campaign bình thường 2 replicas, đột ngột nhận 20x traffic. ACA scale lên 30 replicas. Mỗi replica dùng SQL pool max 100 connections theo default/config cũ.

Theoretical upper bound trở thành 3.000 connections — database không chịu được. Web tier autoscale “thành công” nhưng downstream bắt đầu timeout.

Team cần concurrency/budget controls, connection pool tuning và autoscale ceiling dựa trên toàn hệ thống.

## 6. Failure scenario & troubleshooting

**Symptom:** traffic tăng, replica count tăng, nhưng p95 xấu hơn và SQL timeout xuất hiện.

**Evidence:** ACA replica count correlated với SQL connections/DTU/CPU; startup logs bình thường.

**Hypothesis:** scale-out khuếch đại downstream concurrency.

**Diagnosis:** correlate ingress RPS, replica count, per-replica concurrency, pool size và dependency saturation.

**Fix:** giới hạn max replicas/concurrency, optimize pooling, add queue/backpressure hoặc scale downstream phù hợp.

**Verification:** load test ramp + spike, quan sát p95/p99 và dependency capacity trong toàn scale range.

## 7. Common mistakes

- Scale-to-zero cho latency-sensitive API mà không chấp nhận cold start.
- Dùng `latest` image tag khiến revision provenance mơ hồ.
- Traffic split nhưng schema/database change không backward compatible.
- Liveness probe gọi toàn bộ remote dependencies.
- Không giới hạn max scale theo downstream budget.
- Nhầm revision rollout với database/data migration rollback.

## 8. Alternatives

- **Azure App Service:** đơn giản hơn cho standard web apps.
- **Azure Functions:** phù hợp event/function execution model và bursty workloads.
- **AKS:** cần khi team thực sự cần Kubernetes primitives/control sâu.
- **VM/IIS:** phù hợp legacy constraints nhưng operational overhead cao hơn.

## 9. Trade-offs

### Advantages

- Container deployment với managed infrastructure.
- Revisions và traffic splitting hỗ trợ safer rollout.
- Event-driven scaling và scale-to-zero tiết kiệm chi phí.

### Costs / Risks

- Cold start và scaling lag.
- Networking/observability abstractions vẫn cần hiểu.
- Autoscale có thể chuyển bottleneck xuống dependency khác.
- Platform convenience không loại bỏ release/database compatibility concerns.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu container replica, revision và ingress.

### Middle

Deploy app, health checks, config/secrets và đọc scale metrics.

### Senior

Reason về cold start, concurrency, downstream budget và canary rollback.

### Technical Lead / Architect

Chọn ACA/App Service/Functions/AKS theo workload và team operations capability; đặt scale envelope cho toàn architecture, không riêng compute tier.

## 11. Key takeaway

- Autoscaling chỉ tốt khi downstream capacity scale hoặc được bảo vệ tương ứng.
- Revision traffic splitting không thay thế backward-compatible database/API design.
- Scale-to-zero là cost/latency trade-off, không phải free optimization.

# 7. Docker multi-stage builds và image layers: build nhanh hơn, image nhỏ hơn nhưng cache và secret leakage có thể biến Dockerfile thành supply-chain risk

## 1. What is it?

Docker image được xây từ các immutable layers. Mỗi instruction như `COPY`, `RUN`, `ENV` có thể tạo layer/cache boundary.

**Multi-stage build** dùng một stage có full SDK/toolchain để compile rồi copy artifact sang runtime image nhỏ hơn:

```text
SDK image -> build/publish
              |
              v
Runtime image <- published files only
```

Mục tiêu không chỉ giảm MB; nó giảm attack surface, tooling không cần thiết và dependency footprint trong production image.

## 2. Why does it exist?

Nếu chạy production bằng full .NET SDK image, container chứa compiler, NuGet tooling và nhiều packages không cần runtime. Image lớn làm pull/start chậm hơn và có thêm vulnerabilities.

Layer cache tồn tại để không rebuild dependency restore mỗi lần chỉ sửa một `.cs` file. Nhưng Docker cache phụ thuộc build context và instruction order.

## 3. How does it work?

Một Dockerfile tốt thường copy project metadata trước để cache restore:

```text
COPY *.csproj
RUN dotnet restore   <- cacheable nếu dependencies không đổi
COPY source
RUN dotnet publish
```

Nếu `COPY . .` trước restore, bất kỳ source file change nào cũng invalidates restore layer.

Quan trọng về secrets: xóa secret trong layer sau không đảm bảo secret biến mất khỏi image history/layer cũ. Secret không nên được baked vào image.

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

COPY MyApi/MyApi.csproj MyApi/
RUN dotnet restore MyApi/MyApi.csproj

COPY . .
RUN dotnet publish MyApi/MyApi.csproj \
    -c Release \
    -o /app/publish \
    --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .

USER $APP_UID
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

Thêm `.dockerignore` để loại `.git`, `bin`, `obj`, local secrets và unnecessary files khỏi build context.

## 5. Real production scenario

CI build image 1.8 GB vì dùng SDK image làm final stage và copy toàn repo. Deployment kéo image qua region/network mất lâu; vulnerability scanner báo hàng trăm packages không liên quan runtime.

Multi-stage build + runtime base làm image giảm mạnh, startup/deploy nhanh hơn và scan signal sạch hơn.

## 6. Failure scenario & troubleshooting

**Symptom:** CI build mất 8 phút dù chỉ sửa một controller; hoặc secret cũ vẫn bị scanner phát hiện sau khi Dockerfile đã `rm` file.

**Evidence:** build logs cho thấy `dotnet restore` cache miss mỗi lần; image history/layers chứa secret artifact.

**Hypothesis:** bad layer ordering/build context; secret đã được copied vào layer.

**Diagnosis:** inspect `docker history`, build cache output và context; scan image filesystem/layers.

**Fix:** reorder COPY/restore, `.dockerignore`, BuildKit secret mounts/CI secret injection; rotate secret đã leak.

**Verification:** rebuild clean, scan image, compare build cache hits và artifact size.

## 7. Common mistakes

- Dùng `COPY . .` quá sớm.
- Copy `.env`, credentials hoặc NuGet config có token vào image.
- Xóa secret ở later layer rồi nghĩ đã an toàn.
- Chạy container bằng root không cần thiết.
- Pin image bằng floating tags mà không có provenance/update policy.
- Tối thiểu hóa image tới mức mất CA cert/timezone/native dependency cần runtime mà không test.

## 8. Alternatives

- **Framework-dependent runtime image:** common balance cho .NET.
- **Self-contained/native/AOT images:** có thể giảm runtime dependency hoặc startup, nhưng tăng build/platform trade-offs.
- **VM deployment:** đơn giản cho legacy nhưng ít isolation/reproducibility hơn.

## 9. Trade-offs

### Advantages

- Smaller runtime image và attack surface.
- Better build caching.
- Build/runtime responsibilities tách rõ.

### Costs / Risks

- Dockerfile/cache behavior cần hiểu.
- Minimal images khó debug trực tiếp hơn vì thiếu shell/tools.
- Base image patching vẫn cần lifecycle process.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu image, layer, container và multi-stage build.

### Middle

Viết Dockerfile cache-friendly, non-root và `.dockerignore` đúng.

### Senior

Debug layer cache, CVEs, secret exposure và reproducible build issues.

### Technical Lead / Architect

Đặt base-image governance, SBOM/scanning, patch cadence và artifact provenance trong CI/CD.

## 11. Key takeaway

- Multi-stage build là security/release concern, không chỉ giảm image size.
- Secrets đã vào image layer phải coi là compromised và rotate.
- Layer ordering ảnh hưởng trực tiếp CI performance và reproducibility.

# 8. OAuth 2.0 Authorization Code + PKCE: bảo vệ browser/mobile client mà không giả vờ public client giữ được client secret

## 1. What is it?

Authorization Code flow tách browser redirect khỏi token issuance. Client nhận một short-lived authorization code, sau đó đổi code lấy tokens.

PKCE bổ sung một per-request secret tạm thời:

```text
code_verifier -> hash -> code_challenge
```

Authorization request gửi `code_challenge`; token request phải chứng minh biết original `code_verifier`.

PKCE đặc biệt quan trọng cho **public clients** như SPA/native mobile apps — nơi không thể bảo mật một static client secret.

## 2. Why does it exist?

Authorization code có thể bị intercept qua malicious app, redirect handling hoặc browser/device attack surface. Nếu ai có code cũng đổi được token, code theft nguy hiểm.

Client secret không giải quyết vấn đề cho SPA/mobile vì secret ship xuống user device/browser thì không còn secret.

PKCE bind code với client instance đã khởi tạo flow mà không cần static confidential secret.

## 3. How does it work?

```text
Client creates verifier
   |
   +-> challenge = BASE64URL(SHA256(verifier))
   |
Authorize request -> Identity Provider
                     |
                     -> user login/consent
                     -> auth code
Client receives code
   |
Token request: code + verifier
   |
IdP hashes verifier and compares challenge
   |
Tokens issued
```

OAuth handles delegated authorization. OpenID Connect thêm identity layer (`id_token`, user authentication semantics). Đừng dùng access token như arbitrary session data container.

## 4. Practical implementation

Với ASP.NET Core BFF/server-rendered app, dùng OIDC handler thay vì tự build protocol:

```csharp
builder.Services
    .AddAuthentication(options =>
    {
        options.DefaultScheme = "Cookies";
        options.DefaultChallengeScheme = "oidc";
    })
    .AddCookie("Cookies")
    .AddOpenIdConnect("oidc", options =>
    {
        options.Authority = configuration["Auth:Authority"];
        options.ClientId = configuration["Auth:ClientId"];
        options.ResponseType = "code";
        options.UsePkce = true;
        options.SaveTokens = false;
    });
```

Với SPA, dùng provider-supported OIDC library. Không tự implement verifier/challenge/state/nonce/token validation nếu không bắt buộc.

## 5. Real production scenario

Một mobile app từng dùng implicit-like token flow và hard-code `client_secret` trong binary. Reverse engineering lấy secret trong vài phút.

Migration sang Authorization Code + PKCE bỏ assumption sai rằng native app là confidential client. Provider vẫn cần strict redirect URI registration và token validation.

## 6. Failure scenario & troubleshooting

**Symptom:** login redirect thành công nhưng token exchange trả `invalid_grant`; hoặc Production bị redirect loop trong khi local ổn.

**Evidence:** code verifier mismatch, redirect URI khác, state/cookie bị mất, reverse proxy scheme sai.

**Hypothesis:** PKCE/session/redirect context không nhất quán.

**Diagnosis:** inspect protocol metadata và server logs an toàn; kiểm tra exact redirect URI, HTTPS forwarded headers, cookie `SameSite/Secure`, verifier lifecycle.

**Fix:** dùng standard library, đúng proxy config, stable correlation cookie và registered redirects.

**Verification:** login/logout/token refresh flows qua Production-like proxy/browser settings.

## 7. Common mistakes

- Nhúng client secret vào SPA/mobile.
- Tự decode JWT rồi tin claims mà không validate signature/issuer/audience/lifetime.
- Confuse ID token với access token.
- Log access/refresh tokens.
- Wildcard redirect URIs quá rộng.
- Disable state/nonce checks để “fix login”.
- Lưu long-lived tokens trong browser storage mà không đánh giá XSS risk.

## 8. Alternatives

- **BFF pattern:** browser chỉ giữ secure session cookie; server giữ token interaction, giảm token exposure trong JS.
- **Client Credentials:** dành cho service-to-service, không thay user login.
- **Device Authorization:** phù hợp input-constrained devices/CLI trong một số scenarios.

## 9. Trade-offs

### Advantages

- PKCE giảm risk từ intercepted authorization code.
- Không yêu cầu fake secret ở public client.
- Dùng standard IdP/library giảm protocol implementation bugs.

### Costs / Risks

- Redirect/cookie/proxy configuration phức tạp.
- Token lifecycle và refresh vẫn cần security design.
- BFF tăng server-side state/infrastructure nhưng giảm browser token exposure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Authentication, OAuth authorization và OIDC identity là các concepts khác nhau.

### Middle

Configure standard handlers/libraries, redirect URIs, scopes và token validation.

### Senior

Reason về PKCE, browser storage, XSS, refresh token, proxy/cookie failure modes.

### Technical Lead / Architect

Chọn SPA direct OIDC vs BFF theo threat model; đặt token lifetime, scopes và identity boundaries across services.

## 11. Key takeaway

- Public client không thể bảo vệ static client secret.
- Authorization Code + PKCE bind code exchange với client instance khởi tạo flow.
- Protocol security phải dựa trên standard libraries và strict validation, không custom shortcuts.

# 9. Production alerting bằng RED + saturation signals: alert theo user impact và capacity thay vì biến dashboard thành noise

## 1. What is it?

RED là mental model quan sát request-driven services:

- **Rate** — throughput/request rate.
- **Errors** — failure rate.
- **Duration** — latency distribution.

Nhưng RED không đủ cho mọi incident. Cần thêm **saturation** của constrained resources: ThreadPool, connection pool, queue depth, CPU, memory, DB worker/thread/IO capacity.

Alert tốt không chỉ hỏi “metric vượt 80% chưa?” mà hỏi: **user impact hoặc imminent service failure có đủ đáng để đánh thức con người không?**

## 2. Why does it exist?

Production có hàng nghìn metrics. Nếu alert mọi spike, on-call nhận noise và dần ignore alerts. Nếu chỉ nhìn CPU, system có thể outage vì connection pool exhausted trong khi CPU 20%.

RED cho customer-facing symptom; saturation cho nguyên nhân/capacity signal. Kết hợp hai loại giúp phân biệt “resource cao nhưng hệ thống vẫn khỏe” với “users đang bị ảnh hưởng”.

## 3. How does it work?

Ví dụ API:

```text
Rate:       requests/sec
Errors:     5xx + failed dependency ratio
Duration:   p50/p95/p99
Saturation: SQL pool usage, queue backlog, ThreadPool queue, CPU
```

Alert tiers:

```text
Page: sustained user impact / fast SLO burn
Ticket: capacity trend / non-urgent degradation
Dashboard: exploratory diagnostic signals
```

Metrics phát hiện pattern; traces/logs giúp localize nguyên nhân. Alert không nên encode mọi diagnosis vào một rule khổng lồ.

## 4. Practical implementation

Với OpenTelemetry/Application Insights, instrument latency và dependency outcomes; custom business metrics nên low-cardinality.

C# example:

```csharp
private static readonly Meter Meter = new("Checkout.Api");
private static readonly Histogram<double> CheckoutDuration =
    Meter.CreateHistogram<double>("checkout.duration", "ms");

public async Task<IActionResult> Checkout(CancellationToken ct)
{
    var start = Stopwatch.GetTimestamp();
    try
    {
        await service.ExecuteAsync(ct);
        return Ok();
    }
    finally
    {
        var elapsed = Stopwatch.GetElapsedTime(start);
        CheckoutDuration.Record(elapsed.TotalMilliseconds);
    }
}
```

Không gắn `userId`, `requestId`, arbitrary URL làm metric dimensions. High-cardinality context thuộc logs/traces hơn.

## 5. Real production scenario

API có CPU 35% nhưng p99 tăng từ 700 ms lên 12 s. Dashboard ban đầu không alert vì CPU threshold vẫn xanh.

Investigation cho thấy SQL connection pool gần max; requests xếp hàng chờ connection. Error rate ban đầu thấp nhưng duration tăng mạnh trước khi timeout/5xx bùng lên.

Nếu theo dõi p95/p99 + pool saturation, team có early warning rõ hơn.

## 6. Failure scenario & troubleshooting

**Symptom:** users báo chậm trước khi monitoring page; hoặc on-call bị 40 alerts cho cùng incident.

**Evidence:** alerts dựa vào raw resource thresholds; không correlate user impact; nhiều downstream alerts cascade.

**Hypothesis:** alert design không có service-level ownership/symptom-first strategy.

**Diagnosis:** review incident timeline: metric nào đổi đầu tiên, metric nào phản ánh user impact, alert nào actionable.

**Fix:** page trên sustained error/latency/SLO burn; dùng saturation alerts làm supporting/early signal; deduplicate dependency cascades.

**Verification:** replay historical incident data hoặc chaos/load test; kiểm tra alert timing và noise.

## 7. Common mistakes

- Alert CPU > 80% trong 1 phút cho mọi service.
- Dùng average latency thay p95/p99.
- Mỗi dependency tạo page riêng cho cùng root incident.
- Metric labels chứa request/user IDs.
- Dashboard có metric nhưng không có owner/runbook.
- Alert threshold không dựa trên baseline/SLO/business impact.

## 8. Alternatives

- **USE method:** Utilization, Saturation, Errors — phù hợp resource-centric investigation.
- **Golden Signals:** latency, traffic, errors, saturation — gần với RED + capacity.
- **SLO burn-rate alerts:** mạnh khi service có formal objective/error budget.

Chúng bổ sung nhau hơn là cạnh tranh tuyệt đối.

## 9. Trade-offs

### Advantages

- Symptom-first alerts giảm noise.
- Saturation signals cảnh báo capacity issue trước hard failure.
- RED dễ áp dụng cross-service.

### Costs / Risks

- Cần metric instrumentation và baseline tốt.
- SLO/percentile alerting phức tạp hơn static threshold.
- Quá nhiều metrics không đồng nghĩa observability tốt hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu logs, metrics, traces trả lời câu hỏi khác nhau.

### Middle

Instrument latency/errors và dùng dimensions low-cardinality.

### Senior

Thiết kế alert từ symptom → saturation → diagnosis; điều tra p95/p99 và dependency bottlenecks.

### Technical Lead / Architect

Định nghĩa service ownership, SLO/alert policy, escalation và capacity signals cần thiết; loại bỏ non-actionable paging.

## 11. Key takeaway

- Alert nên tối ưu cho actionability và user impact, không cho số lượng metrics.
- RED cho service symptoms; saturation cho capacity/failure pressure.
- p95/p99 và connection/queue saturation thường nói nhiều hơn average/CPU đơn lẻ.

# 10. AI-assisted repository engineering: source grounding, diff-first review và verification loop để AI tăng tốc mà không trở thành nguồn sự thật

## 1. What is it?

AI coding assistant/repository agent có thể đọc code, đề xuất patch, viết tests, refactor và phân tích architecture. Nhưng output của model là **probabilistic proposal**, không phải verified repository truth.

Một workflow đáng tin hơn:

```text
Ground context
 -> propose minimal change
 -> inspect diff
 -> build
 -> test
 -> static/security analysis
 -> human/domain review
 -> merge
```

Source grounding nghĩa là quyết định dựa trên actual repository files, package versions, tests, contracts và runtime configuration thay vì assumptions từ model training.

## 2. Why does it exist?

Model có thể hallucinate APIs, dùng package version không tồn tại, bỏ qua convention nội bộ hoặc viết test tự khẳng định implementation sai.

Khác với autocomplete nhỏ, repository-level changes có blast radius lớn: migrations, auth, concurrency, deployment config, public API compatibility.

Verification loop biến AI từ “authoritative answer generator” thành engineering accelerator có evidence gates.

## 3. How does it work?

Một repository task nên đi theo layers:

```text
Requirement
   |
   v
Relevant docs + code + tests + dependency versions
   |
   v
Change plan bounded by existing architecture
   |
   v
Patch/diff
   |
   +-> compiler/build
   +-> unit/integration tests
   +-> formatter/analyzer
   +-> security/static checks
   +-> targeted manual review
```

Mỗi gate loại một lớp uncertainty. Build chứng minh syntax/type compatibility; tests chứng minh selected behavior; static/security tools bắt classes of problems khác; human review kiểm tra requirement/architecture mà tests có thể chưa encode.

## 4. Practical implementation

Ví dụ prompt/task contract cho repository agent nội bộ:

```text
1. Read solution, Directory.Build.props and affected project files.
2. Identify existing implementation pattern before adding abstraction.
3. Change only files required by the requirement.
4. Do not invent package/API versions; verify from project references.
5. Add/modify tests that fail before the fix where practical.
6. Run dotnet build and targeted tests.
7. Return changed files, evidence and unresolved risks.
```

CI vẫn là enforcement boundary:

```bash
dotnet restore
dotnet build --no-restore -c Release
dotnet test --no-build -c Release
dotnet format --verify-no-changes
```

Thêm SAST/dependency scan theo project policy.

## 5. Real production scenario

Agent được yêu cầu thêm retry cho third-party API. Nó dùng Polly API từ version mới hơn project reference và retry mọi `POST` 5 lần.

Code sample trông thuyết phục nhưng có hai lỗi:

1. không compile với package version hiện tại;
2. retry non-idempotent POST có thể tạo duplicate order.

Grounding vào `.csproj`, existing `HttpClient` policy và API contract sẽ phát hiện cả compatibility lẫn semantics risk trước merge.

## 6. Failure scenario & troubleshooting

**Symptom:** AI-generated PR có nhiều files, tests pass nhưng production semantics sai hoặc code không build trong CI target.

**Evidence:** tests mirror implementation thay vì requirement; package APIs không match references; unrelated refactor làm diff lớn.

**Hypothesis:** agent thiếu repository grounding và verification gates.

**Diagnosis:** review prompt/context, diff scope, test intent và CI evidence; xác định assumption nào không có source.

**Fix:** require source references, minimal diff, failing regression test, build/test evidence và explicit unresolved assumptions.

**Verification:** rerun task với same repo state; compare diff size, compile/test success và human review findings.

## 7. Common mistakes

- Đưa requirement rồi cho agent tự “thiết kế lại” toàn architecture.
- Tin generated test chỉ vì test xanh.
- Không pin/inspect package versions.
- Cho AI quyết authorization/security rule từ natural language output runtime.
- Auto-merge large migration/auth/payment changes không review.
- Đánh giá chất lượng bằng số dòng code sinh ra.

## 8. Alternatives

- **Human-only implementation:** phù hợp high-risk changes khi context rất subtle nhưng tốc độ thấp hơn.
- **AI as reviewer only:** useful khi team muốn low-risk adoption.
- **AI for bounded subtasks:** test scaffolding, repetitive migration, docs, code search — thường ROI tốt và blast radius nhỏ.
- **Deterministic tooling:** compiler, analyzers, schema validators luôn nên giữ vai trò enforcement nơi có thể.

## 9. Trade-offs

### Advantages

- Tăng tốc code search, boilerplate, test generation và analysis.
- Có thể giúp review nhiều repository context nhanh hơn con người.
- Hữu ích cho migration/refactor có pattern rõ.

### Costs / Risks

- False confidence từ fluent output.
- Context window/source selection có thể bỏ sót constraint quan trọng.
- Verification compute/time tăng với autonomous workflows.
- Security/IP/data governance cần policy rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Dùng AI để học/accelerate nhưng luôn build, run và đọc code trước khi nhận.

### Middle

Cung cấp context tốt, giới hạn scope, yêu cầu tests và tự debug generated changes.

### Senior

Đánh giá assumptions, architecture fit, failure modes, package/runtime compatibility và security implications.

### Technical Lead / Architect

Thiết kế AI development workflow với permission boundaries, CI gates, repository grounding, auditability và rule rõ cho high-risk changes.

## 11. Key takeaway

- AI output là proposal; compiler, tests, source và human/domain review mới tạo evidence.
- Diff càng lớn và domain càng critical, verification càng phải mạnh.
- Deterministic security/business invariants không nên giao cho unconstrained model output.
