# 1. C# `async`/`await` state machine và sync-over-async: vì sao một `.Result` nhỏ có thể dẫn tới ThreadPool starvation dưới tải

## 1. What is it?

`async`/`await` là cú pháp để mô tả asynchronous control flow mà không phải tự viết callback chain. Compiler chuyển method `async` thành một state machine. Khi gặp một `await` chưa hoàn thành, method trả quyền điều khiển cho caller thay vì giữ thread chờ I/O.

Mental model:

```text
Request thread
   ↓
Start async method
   ↓
Issue I/O
   ↓
await incomplete Task
   ↓
return thread to ThreadPool
   ↓
I/O completes
   ↓
continuation scheduled
   ↓
resume state machine
```

Điểm quan trọng: `async` không có nghĩa là “tạo thread mới”. Với I/O-bound work, giá trị nằm ở việc thread không bị block trong lúc chờ network, database hoặc filesystem.

## 2. Why does it exist?

Một synchronous server có thể giữ một thread cho mỗi request trong suốt thời gian request chờ I/O. Khi dependency chậm, số thread bị giữ tăng, context switching tăng và cuối cùng throughput suy giảm.

`async`/`await` tồn tại để tách thời gian “đang chờ” khỏi thời gian “đang dùng CPU”. Điều đó đặc biệt quan trọng với ASP.NET Core vì một request thường đi qua nhiều external I/O: SQL, Redis, HTTP API, blob storage, messaging.

## 3. How does it work?

Compiler chia method thành các state tương ứng trước và sau mỗi `await`. Nếu `Task` đã completed, execution có thể tiếp tục đồng bộ. Nếu chưa completed, continuation được đăng ký và method trả về.

Ví dụ:

```csharp
public async Task<OrderDto?> GetOrderAsync(
    Guid id,
    CancellationToken cancellationToken)
{
    var entity = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    return entity is null
        ? null
        : new OrderDto(entity.Id, entity.Total);
}
```

Không có thread nào cần ngồi chờ SQL Server trả kết quả.

Vấn đề xuất hiện khi code chuyển asynchronous wait thành blocking wait:

```csharp
var result = service.GetOrderAsync(id, cancellationToken).Result;
```

hoặc:

```csharp
service.DoWorkAsync().GetAwaiter().GetResult();
```

Thread hiện tại bị giữ trong khi continuation của asynchronous operation lại cần ThreadPool capacity để tiếp tục.

## 4. Practical implementation

Giữ call chain “async all the way”:

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    OrderService service,
    CancellationToken cancellationToken) =>
{
    var order = await service.GetOrderAsync(id, cancellationToken);
    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

Không nên bọc I/O-bound work trong `Task.Run`:

```csharp
// Không cần thiết cho EF Core I/O.
await Task.Run(() => db.Orders.ToList());
```

`Task.Run` chỉ chuyển blocking work sang thread khác, không biến database call thành asynchronous I/O đúng nghĩa.

## 5. Real production scenario

Một API gọi ba downstream services. Team có một helper legacy dùng `.Result` để gọi `HttpClient`. Bình thường hệ thống vẫn chạy ổn. Khi downstream latency tăng từ 100 ms lên 2 giây, mỗi request giữ ThreadPool thread lâu hơn nhiều.

Khi traffic tăng, số blocked threads vượt khả năng ThreadPool bổ sung kịp. Request mới bị queue, health endpoint cũng chậm và p99 latency tăng mạnh dù CPU chưa chắc 100%.

Đây là dấu hiệu điển hình của ThreadPool starvation: không phải CPU thiếu, mà runnable continuation không có đủ worker threads đúng lúc.

## 6. Failure scenario & troubleshooting

**Symptom** → p95/p99 tăng mạnh, request queue tăng, CPU chỉ trung bình.

**Evidence** → ThreadPool queue length tăng, nhiều stack trace dừng ở `.Result`, `.Wait()` hoặc blocking network/database APIs.

**Hypothesis** → sync-over-async đang giữ worker threads.

**Diagnosis** → dùng `dotnet-counters`, `dotnet-trace`, Application Insights dependency duration và thread metrics để đối chiếu.

**Fix** → chuyển call chain sang async end-to-end; loại `.Result`/`.Wait()` khỏi request path; dùng API async native.

**Verification** → load test lại và quan sát ThreadPool queue, request throughput, p95/p99.

## 7. Common mistakes

* Nghĩ rằng `async` luôn nhanh hơn synchronous code.
* Dùng `Task.Run` cho mọi I/O operation.
* Gọi `.Result` trong ASP.NET Core vì “chỉ một chỗ thôi”.
* Quên propagate `CancellationToken` xuống EF Core/HttpClient.
* Tạo quá nhiều concurrent tasks mà không có backpressure.

## 8. Alternatives

* Synchronous code vẫn hợp lý cho CPU-bound logic rất ngắn hoặc tooling đơn giản.
* `Parallel.ForEachAsync` phù hợp khi cần bounded parallelism.
* `Channel<T>` hữu ích cho producer/consumer flow có backpressure.

## 9. Trade-offs

### Advantages

* Sử dụng threads hiệu quả hơn cho I/O-bound workload.
* Tăng scalability khi nhiều request cùng chờ external dependencies.
* Code dễ đọc hơn callback-based asynchronous programming.

### Costs / Risks

* Stack trace và control flow phức tạp hơn.
* Sai một boundary blocking có thể phá lợi ích của cả chain.
* Concurrency tăng có thể làm downstream dependency bị overload nếu không giới hạn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` thường giải phóng thread trong lúc chờ I/O; nó không đồng nghĩa tạo thread mới.

### Middle

Viết async end-to-end, dùng cancellation và tránh `.Result`/`.Wait()`.

### Senior

Chẩn đoán ThreadPool starvation, phân biệt CPU-bound với I/O-bound và thiết kế bounded concurrency.

### Technical Lead / Architect

Đánh giá toàn request path: concurrency budget, downstream capacity, timeout, cancellation và backpressure chứ không chỉ style của từng method.

## 11. Key takeaway

* `async` hiệu quả khi nó ngăn thread bị block trong lúc chờ I/O.
* Sync-over-async là production risk, đặc biệt dưới latency spike.
* Async scalability vẫn cần concurrency limits và downstream protection.

# 2. ASP.NET Core rate limiting: fixed window, sliding window, token bucket và partitioning theo client/business key

## 1. What is it?

Rate limiting giới hạn lượng work một caller hoặc một partition được phép tạo trong một khoảng thời gian.

Mục tiêu không chỉ chống abuse. Nó còn bảo vệ database, third-party API, CPU, queue và các resource hữu hạn khỏi traffic burst vượt capacity.

## 2. Why does it exist?

Một API có thể đúng về functional behavior nhưng vẫn sập nếu 1 client gửi 10.000 request/giây. Autoscaling không phải câu trả lời cho mọi loại overload, đặc biệt khi bottleneck là SQL connection pool hoặc API downstream có quota cố định.

Rate limiting tạo một admission-control boundary trước khi expensive work xảy ra.

## 3. How does it work?

Các thuật toán có behavior khác nhau:

* **Fixed window**: đơn giản nhưng burst có thể xảy ra ở ranh giới hai window.
* **Sliding window**: mượt hơn nhưng bookkeeping phức tạp hơn.
* **Token bucket**: cho phép burst ngắn trong khi vẫn kiểm soát average rate.
* **Concurrency limiter**: giới hạn số operation đang chạy đồng thời thay vì số request theo thời gian.

ASP.NET Core hỗ trợ `PartitionedRateLimiter`, cho phép limit theo user, API key, tenant hoặc IP.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("per-user", httpContext =>
    {
        var userId = httpContext.User.FindFirst("sub")?.Value
            ?? httpContext.Connection.RemoteIpAddress?.ToString()
            ?? "anonymous";

        return RateLimitPartition.GetTokenBucketLimiter(
            partitionKey: userId,
            factory: _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 20,
                ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                QueueLimit = 20,
                QueueProcessingOrder = QueueProcessingOrder.OldestFirst,
                AutoReplenishment = true
            });
    });
});

app.UseRateLimiter();
```

Endpoint có thể áp dụng policy cụ thể:

```csharp
app.MapPost("/checkout", HandleCheckout)
   .RequireRateLimiting("per-user");
```

## 5. Real production scenario

Một e-commerce API gọi payment provider có quota 500 requests/second. Frontend retry quá aggressive sau một incident, tạo traffic burst vượt quota. Payment provider bắt đầu trả 429, application lại retry tiếp và tự khuếch đại lỗi.

Rate limiter theo tenant hoặc user giảm load trước khi request chạm payment integration. Đồng thời system có thể trả `429 Too Many Requests` cùng `Retry-After` rõ ràng.

## 6. Failure scenario & troubleshooting

**Symptom** → backend khỏe nhưng user hợp lệ bị 429 hàng loạt.

**Evidence** → nhiều tenant cùng share một partition key như `anonymous` hoặc proxy IP.

**Hypothesis** → partition strategy quá thô.

**Diagnosis** → log partition key, limiter policy, rejection count và caller identity.

**Fix** → partition theo API key/tenant/user ổn định; chỉ fallback sang IP khi phù hợp.

**Verification** → test nhiều caller đồng thời và xác nhận one noisy tenant không ảnh hưởng tenant khác.

## 7. Common mistakes

* Limit theo IP phía sau reverse proxy nhưng đọc sai client IP.
* Dùng một global limiter khiến tenant lớn bóp nghẹt tenant nhỏ.
* Chỉ rate limit ở application nhưng quên CDN/API Gateway có thể chặn sớm hơn.
* Retry ngay lập tức sau 429.
* Không phân biệt rate limit với concurrency limit.

## 8. Alternatives

* API Gateway / Azure Front Door / WAF-level throttling để loại traffic trước application.
* Queue-based load leveling khi work không cần xử lý synchronous.
* Circuit Breaker bảo vệ dependency đang lỗi; rate limiter bảo vệ capacity. Hai pattern giải quyết bài toán khác nhau.

## 9. Trade-offs

### Advantages

* Chặn overload sớm.
* Cô lập noisy client.
* Bảo vệ dependencies có quota/capacity hữu hạn.

### Costs / Risks

* Policy sai làm giảm availability cho user hợp lệ.
* Distributed rate limiting cần shared state hoặc edge component.
* Quá nhiều policy làm operational behavior khó dự đoán.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 429 khác 500 và rate limiting là admission control.

### Middle

Cấu hình limiter, partition key và response headers đúng.

### Senior

Chọn thuật toán theo burst profile, dependency capacity và fairness.

### Technical Lead / Architect

Quyết định limiter nên nằm ở CDN, gateway, application hay nhiều tầng; ai sở hữu policy và SLO nào cần bảo vệ.

## 11. Key takeaway

* Rate limiting là reliability mechanism, không chỉ anti-abuse.
* Partition key quyết định fairness.
* Algorithm phải phù hợp workload chứ không chọn theo mặc định.

# 3. EF Core optimistic concurrency với `rowversion`: phát hiện lost update mà không khóa row suốt user interaction

## 1. What is it?

Optimistic concurrency giả định conflict hiếm và không giữ database lock trong suốt thời gian user đọc rồi chỉnh sửa dữ liệu.

Thay vào đó, mỗi update kiểm tra xem record có thay đổi kể từ lúc đọc hay chưa.

## 2. Why does it exist?

Scenario kinh điển:

```text
User A reads Order version 5
User B reads Order version 5
User A updates -> version 6
User B updates based on stale version 5
```

Nếu không có concurrency control, update của B có thể ghi đè thay đổi của A mà không ai biết: lost update.

Giữ lock từ lúc user mở form tới lúc bấm Save là không thực tế vì interaction có thể kéo dài hàng phút.

## 3. How does it work?

Với SQL Server, `rowversion` tự thay đổi khi row được update.

EF Core thêm concurrency token vào `WHERE` của `UPDATE`:

```sql
UPDATE Orders
SET Status = @status
WHERE Id = @id
  AND RowVersion = @originalRowVersion;
```

Nếu 0 rows affected, EF Core biết dữ liệu đã bị thay đổi và ném `DbUpdateConcurrencyException`.

## 4. Practical implementation

Entity:

```csharp
public sealed class Order
{
    public Guid Id { get; set; }
    public string Status { get; set; } = string.Empty;

    [Timestamp]
    public byte[] RowVersion { get; set; } = Array.Empty<byte>();
}
```

API update:

```csharp
public async Task<IResult> UpdateAsync(
    UpdateOrderRequest request,
    CancellationToken cancellationToken)
{
    var order = await db.Orders.FindAsync([request.Id], cancellationToken);
    if (order is null)
        return Results.NotFound();

    db.Entry(order)
      .Property(x => x.RowVersion)
      .OriginalValue = Convert.FromBase64String(request.RowVersion);

    order.Status = request.Status;

    try
    {
        await db.SaveChangesAsync(cancellationToken);
        return Results.Ok();
    }
    catch (DbUpdateConcurrencyException)
    {
        return Results.Conflict(new ProblemDetails
        {
            Title = "The order was modified by another user."
        });
    }
}
```

## 5. Real production scenario

Hai back-office operators chỉnh cùng một customer profile. Một người sửa billing limit, người khác đổi account state.

Nếu UI gửi toàn bộ entity và backend blind overwrite, thay đổi hợp lệ có thể bị mất. Với optimistic concurrency, second update bị reject và UI có thể yêu cầu user reload/merge thay đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → người dùng gặp `409 Conflict` thường xuyên.

**Evidence** → cùng aggregate bị nhiều background jobs và UI updates chạm đồng thời.

**Hypothesis** → conflict không còn “hiếm”; optimistic strategy đang bị pressure.

**Diagnosis** → log entity key, original token, operation type và conflict rate.

**Fix** → giảm update scope, tách hot fields, serialize critical workflow, hoặc dùng domain command với merge semantics thay vì full-row update.

**Verification** → đo conflict rate sau thay đổi.

## 7. Common mistakes

* Bắt exception rồi retry update vô điều kiện, vô tình ghi đè dữ liệu mới.
* Không gửi concurrency token tới client.
* Dùng DTO chứa toàn entity và overwrite mọi field.
* Nghĩ optimistic concurrency đồng nghĩa database transaction không cần nữa.

## 8. Alternatives

* Pessimistic locking phù hợp transaction ngắn và conflict rất đắt.
* Application-level version number dùng được khi database không có `rowversion`.
* Event sourcing lưu sequence/version theo aggregate nhưng complexity cao hơn nhiều.

## 9. Trade-offs

### Advantages

* Không giữ lock lâu.
* Scale tốt cho mostly-read và low-conflict workloads.
* Phát hiện lost update rõ ràng.

### Costs / Risks

* Conflict resolution chuyển lên application/user experience.
* Retry không thể tự động trong mọi domain.
* Hot records có thể tạo conflict rate cao.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu lost update và concurrency token.

### Middle

Cấu hình EF Core concurrency, map 409 và giữ original token đúng.

### Senior

Thiết kế conflict-resolution semantics theo business command thay vì generic retry.

### Technical Lead / Architect

Quyết định boundary nào cần strong write coordination, boundary nào chấp nhận optimistic conflict và user merge.

## 11. Key takeaway

* Optimistic concurrency phát hiện stale writes thay vì khóa dài hạn.
* Conflict là business outcome cần xử lý, không chỉ technical exception.
* Blind retry có thể phá correctness.

# 4. SQL keyset pagination: giữ latency ổn định khi dữ liệu lớn thay vì trả giá tuyến tính cho `OFFSET`

## 1. What is it?

Keyset pagination, còn gọi là seek pagination, dùng giá trị cuối của page trước làm điểm bắt đầu cho page tiếp theo thay vì yêu cầu database bỏ qua N rows.

## 2. Why does it exist?

`OFFSET 100000 ROWS` không có nghĩa database “nhảy ngay” tới row 100001. Execution plan thường vẫn phải locate/sort/scan rồi discard nhiều rows trước khi trả page nhỏ.

Khi offset tăng, I/O và CPU thường tăng theo.

Ngoài ra, nếu dữ liệu thay đổi giữa hai page, offset pagination dễ tạo duplicate hoặc missing records.

## 3. How does it work?

Giả sử sort theo `CreatedAt DESC, Id DESC`.

Page đầu:

```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
ORDER BY CreatedAt DESC, Id DESC;
```

Cursor lưu `(CreatedAt, Id)` cuối page.

Page tiếp:

```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE CreatedAt < @lastCreatedAt
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Composite index phù hợp:

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON Orders (CreatedAt DESC, Id DESC)
INCLUDE (Total);
```

## 4. Practical implementation

EF Core:

```csharp
var query = db.Orders
    .AsNoTracking()
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id);

if (cursor is not null)
{
    query = query.Where(x =>
        x.CreatedAt < cursor.CreatedAt ||
        (x.CreatedAt == cursor.CreatedAt && x.Id.CompareTo(cursor.Id) < 0));
}

var items = await query
    .Take(50)
    .Select(x => new OrderListItem(x.Id, x.CreatedAt, x.Total))
    .ToListAsync(cancellationToken);
```

Cursor nên opaque với client, thường encode thành Base64 hoặc signed token.

## 5. Real production scenario

Admin order history có 20 triệu rows. Page 1 nhanh 20 ms, page 2.000 mất vài giây vì `OFFSET` lớn.

Chuyển sang keyset pagination giữ query gần như seek-based và latency ổn định hơn theo depth.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate hoặc missing rows khi paging.

**Evidence** → sort chỉ theo `CreatedAt`, trong khi nhiều rows có cùng timestamp.

**Hypothesis** → ordering không deterministic.

**Diagnosis** → inspect order keys và query plan.

**Fix** → thêm unique tiebreaker như `Id` vào cả `ORDER BY`, cursor và index.

**Verification** → chạy pagination xuyên dataset có duplicated timestamps và concurrent inserts.

## 7. Common mistakes

* Cursor không chứa đủ sort keys.
* Sort bằng field thay đổi thường xuyên.
* Đòi jump trực tiếp đến page 10.000 nhưng vẫn dùng keyset.
* Tạo index không cùng leading key/order với access pattern.

## 8. Alternatives

* OFFSET pagination đơn giản và tốt cho dataset nhỏ hoặc shallow navigation.
* Snapshot/materialized result phù hợp report cần stable page numbering.
* Search engine cursor/search-after phù hợp full-text search workload.

## 9. Trade-offs

### Advantages

* Latency ổn định hơn ở deep pages.
* Ít work discard.
* Behavior tốt hơn khi concurrent inserts xảy ra.

### Costs / Risks

* Không tự nhiên cho “go to page N”.
* Cursor semantics phức tạp hơn UI page number.
* Sort keys phải ổn định và deterministic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu OFFSET bỏ qua rows vẫn có cost.

### Middle

Implement cursor đúng với composite ordering.

### Senior

Đọc execution plan và thiết kế index theo access pattern.

### Technical Lead / Architect

Chọn UX/API contract phù hợp: page number convenience hay scale/performance consistency.

## 11. Key takeaway

* Deep OFFSET thường không scale tốt.
* Keyset pagination cần deterministic ordering.
* Index phải phục vụ đúng seek pattern, không chỉ “có index”.

# 5. Redis cache stampede: single-flight, jitter và stale-while-revalidate để tránh hàng nghìn request cùng đập xuống database

## 1. What is it?

Cache stampede xảy ra khi một hot key hết hạn và nhiều request đồng thời đều thấy cache miss, sau đó cùng query database hoặc downstream service để rebuild cùng một dữ liệu.

## 2. Why does it exist?

Cache thường giảm load 100 lần hoặc hơn. Nhưng nếu một key rất hot hết hạn đúng lúc, backend đột ngột nhận lại toàn bộ load gốc.

Vấn đề tệ hơn khi nhiều key dùng cùng TTL và hết hạn gần như cùng lúc.

## 3. How does it work?

Naive cache-aside:

```text
1000 requests
     ↓
Redis miss
     ↓
1000 DB queries
```

Single-flight/coalescing:

```text
1000 requests
     ↓
Redis miss
     ↓
1 rebuild owner
999 wait/share result
     ↓
1 DB query
```

Jitter làm TTL lệch nhau để tránh synchronized expiration.

Stale-while-revalidate cho phép tạm phục vụ cached value cũ trong khi một worker refresh nền nếu domain chấp nhận stale data ngắn hạn.

## 4. Practical implementation

In-process coalescing đơn giản với `SemaphoreSlim` theo key có thể dùng cho single instance. Với multi-instance, cần distributed coordination hoặc chấp nhận mỗi instance rebuild một lần.

Pseudo-near-production flow:

```csharp
var cached = await cache.GetStringAsync(key, cancellationToken);
if (cached is not null)
    return Deserialize(cached);

await keyedLock.WaitAsync(key, cancellationToken);
try
{
    cached = await cache.GetStringAsync(key, cancellationToken);
    if (cached is not null)
        return Deserialize(cached);

    var value = await repository.LoadAsync(id, cancellationToken);

    var ttl = TimeSpan.FromMinutes(5)
        + TimeSpan.FromSeconds(Random.Shared.Next(0, 30));

    await cache.SetStringAsync(
        key,
        Serialize(value),
        new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = ttl },
        cancellationToken);

    return value;
}
finally
{
    keyedLock.Release(key);
}
```

## 5. Real production scenario

Product detail page nhận 5.000 RPS. Product catalog data cache 10 phút. Một hot product hết TTL và hàng nghìn request đồng thời query SQL.

SQL CPU tăng, latency toàn website tăng, connection pool bắt đầu queue. Cache vốn để bảo vệ DB lại tạo load spike đúng lúc hết hạn.

Giải pháp kết hợp TTL jitter + request coalescing + stale fallback giảm peak load đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → database spike lặp lại theo chu kỳ gần bằng cache TTL.

**Evidence** → Redis miss rate tăng theo burst; nhiều identical SQL queries cùng timestamp.

**Hypothesis** → synchronized expiry / stampede.

**Diagnosis** → correlate cache hit ratio, key TTL pattern, DB query count và request rate.

**Fix** → jitter TTL, single-flight, pre-refresh hoặc stale-while-revalidate tùy freshness requirement.

**Verification** → expire hot key trong load test và đo downstream spike.

## 7. Common mistakes

* Tất cả keys dùng TTL đúng 5 phút không jitter.
* Distributed lock không có expiry và biến cache miss thành deadlock.
* Phục vụ stale data mà business không cho phép.
* Redis outage làm application fail closed dù database vẫn khỏe.

## 8. Alternatives

* IMemoryCache cho per-instance hot data nhỏ.
* CDN/edge cache cho public HTTP responses.
* Database-side optimization nếu cache không thực sự cần.
* Precomputed/materialized read model cho expensive aggregations.

## 9. Trade-offs

### Advantages

* Giảm downstream burst mạnh.
* Tăng resilience khi hot key hết hạn.

### Costs / Risks

* Coordination complexity tăng.
* Stale serving ảnh hưởng freshness.
* Distributed lock có thể trở thành dependency mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss đồng thời có thể tạo burst lớn.

### Middle

Biết TTL, jitter và double-check sau lock.

### Senior

Chọn strategy theo hot-key profile, acceptable staleness và multi-instance behavior.

### Technical Lead / Architect

Quyết định cache có đáng tồn tại, ai sở hữu invalidation và fallback khi Redis unavailable.

## 11. Key takeaway

* Cache stampede là coordinated failure, không phải chỉ cache miss.
* TTL jitter và single-flight thường hiệu quả hơn chỉ tăng Redis capacity.
* Freshness requirement quyết định có thể stale-while-revalidate hay không.

# 6. Transactional Outbox Pattern: commit business data và integration event như một đơn vị, rồi chấp nhận delivery at-least-once

## 1. What is it?

Outbox Pattern giải quyết dual-write problem khi application vừa phải commit database transaction vừa publish message tới broker.

Thay vì cố commit database và broker trong một distributed transaction, application ghi business data và outbox message trong cùng local database transaction.

## 2. Why does it exist?

Naive flow:

```text
UPDATE Order
COMMIT DB
Publish OrderCreated
```

Nếu process crash sau DB commit nhưng trước publish, system mất event.

Đảo thứ tự:

```text
Publish OrderCreated
UPDATE Order
COMMIT DB
```

Nếu DB fail sau publish, consumer nhận event cho transaction chưa tồn tại.

Outbox đưa hai writes quan trọng vào cùng transaction boundary mà database đã hỗ trợ tốt.

## 3. How does it work?

```text
Application transaction
   ├─ update business tables
   └─ insert OutboxMessages row
              ↓
          COMMIT once
              ↓
Background publisher
              ↓
Message broker
              ↓
Consumer
```

Publisher đọc pending outbox rows, publish rồi đánh dấu processed.

Do crash có thể xảy ra sau publish nhưng trước mark processed, message có thể được publish lại. Vì vậy system phải chấp nhận at-least-once delivery và consumer cần idempotent.

## 4. Practical implementation

Trong cùng EF Core transaction:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(cancellationToken);

order.MarkPaid();

db.OutboxMessages.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    Type = "OrderPaid",
    Payload = JsonSerializer.Serialize(new OrderPaid(order.Id)),
    OccurredAtUtc = DateTimeOffset.UtcNow
});

await db.SaveChangesAsync(cancellationToken);
await tx.CommitAsync(cancellationToken);
```

Publisher:

```csharp
var batch = await db.OutboxMessages
    .Where(x => x.ProcessedAtUtc == null)
    .OrderBy(x => x.OccurredAtUtc)
    .Take(100)
    .ToListAsync(cancellationToken);
```

Sau publish thành công mới mark processed.

## 5. Real production scenario

Order service cần update order status và gửi event để notification service gửi email. Trước đây app publish trực tiếp sau `SaveChanges`.

Một deployment restart đúng thời điểm giữa hai operations làm vài orders đã Paid nhưng notification không bao giờ được tạo.

Outbox biến inconsistency này thành recoverable backlog thay vì silent data loss.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng event được xử lý hai lần.

**Evidence** → outbox row publish thành công nhưng process crash trước khi `ProcessedAtUtc` được ghi.

**Hypothesis** → duplicate delivery bình thường của at-least-once pipeline.

**Diagnosis** → inspect message ID, publish logs và consumer processing records.

**Fix** → consumer dùng deduplication/inbox hoặc business idempotency key.

**Verification** → cố tình crash publisher sau send và xác nhận consumer không tạo duplicate side effect.

## 7. Common mistakes

* Nghĩ Outbox tạo exactly-once end-to-end.
* Xóa row ngay khi publish mà không có retention/audit strategy.
* Không index pending rows.
* Publisher không có batching/backoff và gây pressure DB.
* Consumer không idempotent.

## 8. Alternatives

* Distributed transaction/2PC hiếm khi phù hợp cloud services và tăng coupling.
* CDC có thể đọc DB log thay vì polling table.
* Transactional broker integration khả thi trong một số platform-specific boundary nhưng không luôn portable.

## 9. Trade-offs

### Advantages

* Loại dual-write gap giữa DB và broker.
* Dễ audit/replay hơn direct publish.
* Dựa trên local transaction quen thuộc.

### Costs / Risks

* Thêm storage, publisher worker và cleanup.
* Message delivery bị eventual consistency.
* Duplicate vẫn có thể xảy ra.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dual-write failure window.

### Middle

Implement outbox insert cùng transaction và publisher worker.

### Senior

Thiết kế idempotency, batching, retries, ordering và cleanup.

### Technical Lead / Architect

Quyết định boundary nào cần Outbox, latency eventual consistency chấp nhận được bao nhiêu và ai sở hữu replay/recovery process.

## 11. Key takeaway

* Outbox đổi silent message loss thành durable backlog.
* At-least-once vẫn đòi consumer idempotent.
* “Exactly once” thường là business-effect property, không chỉ broker feature.

# 7. Azure Service Bus poison message và dead-letter queue: retry có giới hạn, settlement rõ ràng và recovery có chủ đích

## 1. What is it?

Poison message là message không thể xử lý thành công dù retry nhiều lần, thường do payload invalid, missing business prerequisite hoặc permanent downstream rejection.

Dead-letter queue (DLQ) là nơi giữ những message này để chúng không block hoặc làm nóng main queue mãi mãi.

## 2. Why does it exist?

Không phải mọi lỗi đều transient.

Nếu consumer retry vô hạn một message invalid, hệ thống lãng phí compute, tăng queue latency và có thể tạo retry storm.

DLQ tạo boundary giữa automatic recovery và manual/controlled recovery.

## 3. How does it work?

Azure Service Bus dùng PeekLock phổ biến:

```text
Receive locked message
      ↓
Process
 ┌────┴─────┐
 success   fail
   ↓         ↓
Complete   Abandon / let lock expire
             ↓
      delivery count increases
             ↓
       exceeds max delivery
             ↓
            DLQ
```

Consumer cũng có thể dead-letter chủ động nếu biết lỗi permanent.

## 4. Practical implementation

```csharp
processor.ProcessMessageAsync += async args =>
{
    try
    {
        var command = args.Message.Body.ToObjectFromJson<CreateInvoice>();

        if (command is null)
        {
            await args.DeadLetterMessageAsync(
                args.Message,
                deadLetterReason: "InvalidPayload",
                deadLetterErrorDescription: "Payload could not be deserialized");
            return;
        }

        await handler.HandleAsync(command, args.CancellationToken);
        await args.CompleteMessageAsync(args.Message, args.CancellationToken);
    }
    catch (TransientDependencyException)
    {
        await args.AbandonMessageAsync(args.Message, cancellationToken: args.CancellationToken);
    }
};
```

## 5. Real production scenario

Invoice consumer nhận message chứa currency code không được hỗ trợ. Retry 10 lần không giúp gì vì lỗi permanent.

Nếu consumer cứ abandon, same message tái xuất hiện liên tục. Sau max delivery count, message vào DLQ. Ops dashboard cảnh báo DLQ growth và team có thể sửa mapping rồi replay có kiểm soát.

## 6. Failure scenario & troubleshooting

**Symptom** → DLQ tăng nhanh sau deployment.

**Evidence** → dead-letter reason giống nhau trên hàng nghìn messages.

**Hypothesis** → breaking contract hoặc config regression, không phải isolated bad message.

**Diagnosis** → sample DLQ payload, compare producer schema version, deployment timestamp và consumer logs.

**Fix** → rollback/fix consumer; chỉ replay sau khi root cause đã giải quyết.

**Verification** → replay batch nhỏ, theo dõi success và duplicate effects.

## 7. Common mistakes

* Xem DLQ như trash và không monitor.
* Replay toàn bộ DLQ ngay lập tức sau fix chưa được xác minh.
* Dùng retry cho validation error permanent.
* Không log message ID/correlation ID/dead-letter reason.
* Không thiết kế idempotency trước replay.

## 8. Alternatives

* Storage quarantine table nếu cần domain-specific review workflow.
* Event Hubs phù hợp stream, nhưng semantics xử lý poison record khác queue.
* Kafka retry/DLQ thường cần topic design riêng.

## 9. Trade-offs

### Advantages

* Ngăn poison message làm nóng main queue.
* Tạo recovery workflow rõ ràng.
* Giữ evidence để điều tra.

### Costs / Risks

* DLQ là backlog cần ownership.
* Replay có thể tạo duplicate side effects.
* Max delivery count quá thấp có thể đẩy transient failures sang DLQ sớm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry không dành cho mọi error.

### Middle

Phân loại transient/permanent failure và dùng settlement đúng.

### Senior

Thiết kế retry policy, DLQ alerting, replay và idempotency.

### Technical Lead / Architect

Định nghĩa operational ownership: ai theo dõi DLQ, SLA xử lý, tooling replay và audit.

## 11. Key takeaway

* DLQ là operational queue, không phải thùng rác.
* Retry chỉ hữu ích cho lỗi có xác suất tự hồi phục.
* Replay phải được thiết kế cùng idempotency.

# 8. OpenTelemetry distributed tracing: propagate trace context qua HTTP và messaging để nối symptom thành causal path

## 1. What is it?

Distributed tracing theo dõi một request hoặc business flow đi qua nhiều process/services bằng trace ID và các span có quan hệ parent/child.

Một trace trả lời câu hỏi: thời gian đã tiêu ở đâu và dependency nào nằm trên critical path.

## 2. Why does it exist?

Trong microservices hoặc integration-heavy system, log của từng service chỉ cho thấy local event. Một request chậm có thể do API A, SQL ở service B, Redis ở service C hoặc queue backlog ở worker D.

Không có correlation xuyên service, incident investigation trở thành ghép timestamp thủ công.

## 3. How does it work?

W3C Trace Context dùng header như `traceparent` cho HTTP. OpenTelemetry instrumentation tạo span và propagate context qua supported libraries.

```text
Client
  ↓ trace abc
API span
  ↓
HTTP client span
  ↓ same trace abc
Catalog API span
  ↓
SQL span
```

Messaging phức tạp hơn vì send và process có thể cách nhau lâu, nhưng message properties vẫn có thể mang trace context.

## 4. Practical implementation

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation()
        .AddSource("MyCompany.Orders")
        .AddOtlpExporter());
```

Custom span:

```csharp
private static readonly ActivitySource ActivitySource =
    new("MyCompany.Orders");

using var activity = ActivitySource.StartActivity("ReserveInventory");
activity?.SetTag("order.id", orderId);
```

Không đưa secrets hoặc PII nhạy cảm vào tags.

## 5. Real production scenario

Checkout p95 tăng từ 800 ms lên 2.5 s. API logs chỉ cho biết tổng request chậm.

Trace cho thấy 1.6 s nằm ở inventory HTTP dependency, bên inventory lại 1.3 s ở SQL query. Team tránh tối ưu checkout code sai chỗ và tập trung execution plan tại inventory database.

## 6. Failure scenario & troubleshooting

**Symptom** → trace bị đứt khi qua queue.

**Evidence** → producer và consumer có trace IDs khác nhau, message không chứa propagated context.

**Hypothesis** → custom messaging code chưa inject/extract trace headers.

**Diagnosis** → inspect message application properties và instrumentation coverage.

**Fix** → inject W3C context khi send, extract khi receive, tạo consumer activity với correct semantic relationship.

**Verification** → gửi test message và xác nhận end-to-end trace hiển thị producer/consumer relation.

## 7. Common mistakes

* Sampling quá thấp khiến incident hiếm không có trace.
* Tag cardinality cao như full URL/user input làm telemetry cost bùng nổ.
* Log trace ID nhưng không instrument dependencies.
* Thu thập dữ liệu nhạy cảm vào span attributes.

## 8. Alternatives

* Correlation ID thủ công đơn giản hơn nhưng ít chuẩn hóa.
* Logs phù hợp discrete events; metrics phù hợp trend/alert; traces phù hợp causal path và latency decomposition.

Chúng bổ sung nhau, không thay thế nhau.

## 9. Trade-offs

### Advantages

* Rút ngắn root-cause localization.
* Hiểu critical path xuyên service.
* Liên kết request với dependencies.

### Costs / Risks

* Telemetry volume và storage cost.
* Sampling có thể bỏ lỡ edge cases.
* Instrumentation sai tạo false narrative.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace, span, trace ID.

### Middle

Instrument ASP.NET Core, HttpClient, EF Core và custom activity.

### Senior

Thiết kế sampling, cardinality, messaging propagation và incident queries.

### Technical Lead / Architect

Định nghĩa observability standard toàn platform: naming, propagation, retention, privacy và cost budget.

## 11. Key takeaway

* Tracing giúp tìm critical path, không chỉ “có thêm log”.
* Context phải propagate xuyên mọi boundary, đặc biệt messaging.
* Logs, metrics và traces phải được dùng cùng nhau.

# 9. Blue-Green deployment với database compatibility: deploy application không downtime chỉ đúng khi schema evolution cũng backward-compatible

## 1. What is it?

Blue-Green deployment duy trì hai application environments: phiên bản hiện tại và phiên bản mới. Traffic chỉ chuyển sang Green sau khi Green vượt health validation.

Mental model:

```text
Users
  ↓
Router
 ├─ Blue v1
 └─ Green v2
```

Rollback lý tưởng chỉ là đổi traffic về Blue.

## 2. Why does it exist?

In-place deployment có thể tạo downtime hoặc để server ở trạng thái half-updated.

Blue-Green giảm risk bằng cách chuẩn bị version mới song song trước khi switch traffic.

Nhưng application thường dùng chung database. Nếu migration của v2 phá schema mà v1 cần, rollback application không còn đơn giản nữa.

## 3. How does it work?

Safe database evolution thường dùng expand-and-contract:

```text
1. Expand schema: add nullable/new columns/tables
2. Deploy code compatible with old + new schema
3. Backfill/migrate data
4. Switch traffic
5. Observe
6. Later contract: remove old columns only when no old code depends on them
```

Deployment safety vì vậy là compatibility problem, không chỉ infrastructure routing problem.

## 4. Practical implementation

Thay vì rename column trực tiếp:

```sql
EXEC sp_rename 'Customers.Name', 'DisplayName', 'COLUMN';
```

nên tách phase:

```sql
ALTER TABLE Customers ADD DisplayName nvarchar(200) NULL;
```

Application v2 có thể đọc `DisplayName ?? Name`, write song song hoặc backfill dần.

Sau khi chắc chắn không version nào còn dùng `Name`, mới remove ở deployment sau.

## 5. Real production scenario

Team deploy v2 qua App Service deployment slot. Swap thành công nhưng v2 migration đã drop column mà v1 dùng.

Khi error rate tăng và team swap back, Blue v1 khởi động nhưng query fail vì schema cũ không còn tồn tại.

“Rollback” infrastructure thành công nhưng service vẫn outage.

## 6. Failure scenario & troubleshooting

**Symptom** → rollback application không khôi phục service.

**Evidence** → DB migration destructive đã chạy trước traffic switch.

**Hypothesis** → schema không backward-compatible.

**Diagnosis** → compare migration timeline, app version contract và failing SQL.

**Fix** → restore compatible schema hoặc roll forward fix; về lâu dài áp dụng expand-contract.

**Verification** → test Blue và Green cùng chạy trên same schema trước production switch.

## 7. Common mistakes

* Gộp destructive migration và app rollout trong cùng bước.
* Assume rollback binary đồng nghĩa rollback database.
* Health check chỉ test `/health` mà không chạm critical dependencies.
* Không test old/new version coexistence.

## 8. Alternatives

* Canary deployment giảm blast radius bằng traffic percentage nhỏ.
* Rolling deployment tiết kiệm capacity nhưng có giai đoạn mixed versions.
* Feature flags tách code deployment khỏi feature activation.

## 9. Trade-offs

### Advantages

* Traffic switch nhanh.
* Rollback application nhanh nếu compatibility được giữ.
* Dễ chạy pre-production smoke test trên Green.

### Costs / Risks

* Cần duplicate compute capacity tạm thời.
* Database vẫn là shared coupling point.
* Expand-contract kéo dài lifecycle của schema changes.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Blue và Green là hai version song song.

### Middle

Biết health validation, config parity và deployment slot behavior.

### Senior

Thiết kế backward-compatible migrations và coexistence window.

### Technical Lead / Architect

Xây release strategy kết hợp application, database, messaging contract và rollback policy chứ không chỉ chọn deployment tool.

## 11. Key takeaway

* Zero-downtime deployment là compatibility discipline.
* Database migration thường là điểm phá rollback.
* Expand-and-contract quan trọng hơn tên deployment strategy.

# 10. JWT validation thực chiến: issuer, audience, signing keys, clock skew và key rotation quan trọng hơn việc “decode thấy payload đúng”

## 1. What is it?

JWT là một token format. Decode payload chỉ là Base64Url parsing; nó không chứng minh token đáng tin.

Validation cần xác minh tối thiểu:

* signature,
* issuer,
* audience,
* lifetime,
* signing key,
* algorithm policy.

## 2. Why does it exist?

Token có thể bị sửa, phát hành cho application khác, hết hạn hoặc ký bởi key không còn hợp lệ.

Nếu backend chỉ đọc claims mà không validate trust chain, attacker có thể tự tạo payload như:

```json
{
  "sub": "attacker",
  "role": "Admin"
}
```

Payload nhìn hợp lệ nhưng không có giá trị security nếu signature/issuer/audience không được kiểm tra.

## 3. How does it work?

Typical validation flow:

```text
Read token
  ↓
Find signing key by kid
  ↓
Verify signature
  ↓
Validate iss
  ↓
Validate aud
  ↓
Validate exp/nbf
  ↓
Build ClaimsPrincipal
```

Identity provider thường publish signing keys qua OIDC discovery/JWKS endpoint. Key rotation nghĩa là application phải refresh metadata đúng cách.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = "https://login.example.com/tenant/v2.0";
        options.Audience = "api://orders-api";

        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ClockSkew = TimeSpan.FromMinutes(1)
        };
    });
```

Authorization sau authentication vẫn cần policy riêng:

```csharp
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("orders.write", policy =>
        policy.RequireClaim("scope", "orders.write"));
});
```

## 5. Real production scenario

Một company có nhiều APIs dùng cùng identity provider. Token cho `inventory-api` vô tình được `orders-api` chấp nhận vì backend chỉ validate signature mà không validate `aud`.

Attacker có token hợp lệ cho service A nhưng sử dụng sang service B. Signature hoàn toàn đúng, nhưng authorization boundary sai.

## 6. Failure scenario & troubleshooting

**Symptom** → authentication hoạt động local nhưng production trả 401 sau identity-provider key rotation.

**Evidence** → token `kid` không tồn tại trong cached signing keys.

**Hypothesis** → metadata/JWKS cache chưa refresh hoặc outbound access tới authority bị chặn.

**Diagnosis** → inspect JWT header `kid`, application authentication logs, metadata retrieval errors và network path.

**Fix** → đảm bảo metadata refresh hoạt động, connectivity đúng và không hard-code một signing key cố định.

**Verification** → validate token ký bằng key mới và cũ trong expected overlap window.

## 7. Common mistakes

* Dùng website decode JWT rồi coi token đã được validate.
* Disable issuer/audience validation để “fix 401”.
* Clock skew quá lớn kéo dài effective lifetime.
* Dùng role claim thay cho fine-grained authorization khi domain cần scope/policy.
* Log full access token vào production logs.

## 8. Alternatives

* Opaque token + introspection phù hợp một số centralized authorization model.
* Cookie authentication phù hợp browser server-rendered applications.
* mTLS hoặc workload identity có thể tốt hơn JWT tự quản cho service-to-service trong một số môi trường.

## 9. Trade-offs

### Advantages

* Stateless local validation.
* Claims có thể dùng cho distributed authorization decisions.
* Ecosystem tiêu chuẩn rộng.

### Costs / Risks

* Revocation khó hơn opaque token nếu token lifetime dài.
* Key rotation và metadata dependency cần vận hành đúng.
* Claims dễ bị dùng quá mức, tạo stale authorization data.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu decode khác validate.

### Middle

Cấu hình authority, audience, lifetime và authorization policy đúng.

### Senior

Chẩn đoán key rotation, claim mapping, multi-tenant issuer và token lifetime trade-offs.

### Technical Lead / Architect

Thiết kế trust boundaries giữa clients/services, chọn token type, scopes, rotation policy và revocation strategy.

## 11. Key takeaway

* JWT security nằm ở validation, không nằm ở việc payload đọc được.
* `iss`, `aud`, signature và lifetime đều là trust boundaries.
* Authentication chỉ xác minh identity/token; authorization vẫn là quyết định riêng.
