# 1. EF Core optimistic concurrency: bảo vệ lost update bằng concurrency token

## 1. What is it?

Optimistic concurrency là cách phát hiện hai transaction cùng sửa một logical record mà không giữ lock dài. Mental model: **đọc một version, sửa dữ liệu, và chỉ ghi nếu version trong database vẫn là version mình đã đọc**.

Trong EF Core, concurrency token như SQL Server `rowversion` được đưa vào điều kiện `UPDATE`. Nếu không còn row nào khớp, EF Core ném `DbUpdateConcurrencyException`.

## 2. Why does it exist?

Không có concurrency control, hai người cùng mở một đơn hàng có thể ghi đè thay đổi của nhau. “Last write wins” rất nguy hiểm khi dữ liệu mang business invariant như approval status, inventory hay profile configuration. Giữ pessimistic lock từ lúc UI đọc đến lúc user bấm Save lại không thực tế vì request web là stateless và thời gian suy nghĩ của user có thể kéo dài nhiều phút.

## 3. How does it work?

```text
User A reads Version=10
User B reads Version=10
B UPDATE ... WHERE Id=42 AND Version=10 -> success, Version=11
A UPDATE ... WHERE Id=42 AND Version=10 -> 0 rows -> concurrency conflict
```

EF Core dùng original value của concurrency token, không phải current value, để xây điều kiện update.

## 4. Practical implementation

```csharp
public sealed class Order
{
    public int Id { get; set; }
    public string Status { get; set; } = "";
    [Timestamp]
    public byte[] Version { get; set; } = [];
}

try
{
    order.Status = "Approved";
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new ProblemDetails
    {
        Title = "Order was modified by another user."
    });
}
```

API nên trả version/ETag cho client nếu workflow cần client tham gia conflict detection.

## 5. Real production scenario

Hai manager mở cùng timesheet. Một người Reject vì thiếu giờ; người kia Approve từ dữ liệu cũ. Concurrency token biến việc ghi đè âm thầm thành conflict có thể xử lý rõ ràng.

## 6. Failure scenario & troubleshooting

**Symptom** → thỉnh thoảng API trả 409 khi save.  
**Evidence** → log có `DbUpdateConcurrencyException`, SQL update chứa `WHERE Version = @original`.  
**Hypothesis** → record thực sự đã thay đổi hoặc application đang giữ entity quá lâu.  
**Diagnosis** → so sánh database values với original/current values trong change tracker.  
**Fix** → reload và yêu cầu user merge/retry theo business rule; không retry mù.  
**Verification** → chạy integration test với hai DbContext cùng sửa một row.

## 7. Common mistakes

Catch exception rồi tự động gọi `SaveChanges` lại sẽ biến optimistic concurrency thành last-write-wins trá hình. Một lỗi khác là dùng timestamp nghiệp vụ có precision không đủ hoặc cho client tự gửi version nhưng không validate đúng.

## 8. Alternatives

Pessimistic locking phù hợp với critical section rất ngắn trong database. Serializable transaction mạnh hơn nhưng tăng blocking. Application-level distributed lock chỉ hợp lý khi invariant vượt ra ngoài một row và operational cost được chấp nhận.

## 9. Trade-offs

### Advantages

Không giữ lock trong thời gian user tương tác; scale tốt cho workload conflict thấp; conflict trở nên explicit.

### Costs / Risks

Application phải có conflict policy. Với contention cao, retry/conflict liên tục có thể khiến optimistic strategy kém hiệu quả.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu lost update và ý nghĩa của version.

### Middle

Cấu hình concurrency token, bắt exception và trả 409 phù hợp.

### Senior

Phân biệt technical retry với business conflict; test concurrent writers và quan sát contention.

### Technical Lead / Architect

Quyết định aggregate nào cần concurrency boundary, client có cần merge hay không, và khi nào pessimistic strategy đơn giản hơn.

## 11. Key takeaway

- Concurrency token biến overwrite âm thầm thành conflict có thể kiểm soát.
- Không retry `DbUpdateConcurrencyException` một cách mù quáng.
- Conflict resolution là business decision, không chỉ là EF Core concern.

# 2. ASP.NET Core graceful shutdown: drain request và dừng background work đúng cách

## 1. What is it?

Graceful shutdown là quá trình instance ngừng nhận traffic mới, cho request/work đang chạy một khoảng thời gian để hoàn tất, rồi mới terminate process. Mental model: deployment không chỉ có “running” và “dead”; có một giai đoạn **draining**.

## 2. Why does it exist?

Rolling deployment, autoscaling và node maintenance đều có thể dừng process bình thường. Nếu process chết ngay, request đang ghi database, upload file hoặc consume message có thể bị cắt giữa chừng.

## 3. How does it work?

Host phát cancellation khi shutdown. Reverse proxy/orchestrator phải ngừng route traffic trước hoặc đồng thời. `BackgroundService.ExecuteAsync` nhận stopping token; `StopAsync` có shutdown deadline.

```text
remove from traffic -> signal shutdown -> drain in-flight work -> dispose -> terminate
```

## 4. Practical implementation

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
            await ProcessNextAsync(stoppingToken);
    }
}
```

Mọi I/O downstream nên nhận cùng `CancellationToken`. Với Kubernetes/App Service, health/readiness behavior phải khớp với shutdown semantics của ứng dụng.

## 5. Real production scenario

Một release mới rollout 10 instances. Instance cũ đang xử lý export 20 giây. Nếu readiness được rút trước và shutdown timeout đủ dài, request có thể hoàn tất thay vì trả 502 giữa deployment.

## 6. Failure scenario & troubleshooting

**Symptom** → 499/502 tăng đúng thời điểm deployment.  
**Evidence** → trace bị cắt; pod/process termination trùng timestamp.  
**Hypothesis** → termination grace period ngắn hơn thời gian request hoặc readiness chưa rút traffic kịp.  
**Diagnosis** → correlate deployment events với request duration.  
**Fix** → giới hạn request dài, propagate cancellation, điều chỉnh drain/shutdown window.  
**Verification** → rollout dưới synthetic load và kiểm tra error rate.

## 7. Common mistakes

Nuốt `OperationCanceledException` rồi log Error; dùng `CancellationToken.None`; bắt đầu work mới sau shutdown signal; coi readiness và liveness là cùng một thứ.

## 8. Alternatives

Long-running work có thể chuyển sang durable queue/worker thay vì cố giữ HTTP request sống. Job quan trọng có checkpoint sẽ phục hồi tốt hơn việc chỉ tăng shutdown timeout.

## 9. Trade-offs

### Advantages

Giảm lỗi deployment và partial work.

### Costs / Risks

Drain quá lâu làm rollout chậm; graceful shutdown không thay thế idempotency hay durable processing.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết cancellation là cooperative.

### Middle

Propagate token qua HTTP, EF Core và background work.

### Senior

Thiết kế shutdown deadline, request timeout và telemetry.

### Technical Lead / Architect

Quyết định work nào được drain, work nào phải durable/resumable và SLO deployment chấp nhận bao nhiêu disruption.

## 11. Key takeaway

- Shutdown là một lifecycle cần thiết kế.
- Cancellation phải đi xuyên dependency chain.
- Work dài và quan trọng nên durable thay vì phụ thuộc process lifetime.

# 3. SQL Server connection pool exhaustion: phân biệt pool pressure với database overload

## 1. What is it?

ADO.NET connection pooling tái sử dụng physical database connections. Pool exhaustion xảy ra khi request cần connection nhưng toàn bộ connection trong pool đang bận và không được trả lại đủ nhanh.

## 2. Why does it exist?

Mở TCP/TLS/login mới cho mọi query rất đắt. Pooling giảm overhead, nhưng tạo một bounded resource. Khi query chậm hoặc connection bị giữ lâu, application có thể nghẽn trước cả khi database CPU đạt 100%.

## 3. How does it work?

```text
Request -> pool -> leased connection -> SQL -> return to pool
              \-> pool full -> wait -> timeout
```

Pool thường được tách theo connection string. Transaction, streaming reader và scope giữ DbContext lâu đều kéo dài lease.

## 4. Practical implementation

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(ct);
await using var command = new SqlCommand(
    "SELECT Id, Status FROM Orders WHERE Id = @id", connection);
command.Parameters.AddWithValue("@id", id);
await using var reader = await command.ExecuteReaderAsync(ct);
```

Với EF Core, giữ `DbContext` scoped theo request và tránh singleton/context sống dài.

## 5. Real production scenario

Một downstream report query từ 200 ms tăng lên 25 giây. 100 concurrent requests giữ 100 connections; request mới timeout khi acquire connection dù SQL Server CPU chỉ 45%.

## 6. Failure scenario & troubleshooting

**Symptom** → “Timeout expired prior to obtaining a connection from the pool.”  
**Evidence** → active connections sát pool limit, query duration tăng, request queue tăng.  
**Hypothesis** → slow query hoặc leaked/long-held connection.  
**Diagnosis** → trace request→DB, inspect blocking/execution plans và connection lifetime.  
**Fix** → sửa query/blocking trước; dispose đúng; giảm thời gian transaction. Tăng pool size chỉ sau khi chứng minh database chịu được.  
**Verification** → load test và theo dõi acquire latency, DB waits, p95/p99.

## 7. Common mistakes

Tăng `Max Pool Size` ngay lập tức; tạo connection string khác nhau động làm phân mảnh pool; giữ transaction xuyên external HTTP call.

## 8. Alternatives

Connection multiplexing không phải đặc tính chung của SQL Server client. Queue/backpressure ở application có thể tốt hơn mở thêm connections khi database đã là bottleneck.

## 9. Trade-offs

### Advantages

Pooling giảm latency và login overhead mạnh.

### Costs / Risks

Pool che giấu scarcity cho đến khi workload vượt capacity; pool lớn có thể chuyển overload sang database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Luôn dispose connection/context đúng scope.

### Middle

Nhận biết pool timeout khác command timeout.

### Senior

Correlate pool metrics với query latency, locks và request concurrency.

### Technical Lead / Architect

Đặt concurrency budget từ application tới database thay vì coi pool size là tuning knob độc lập.

## 11. Key takeaway

- Pool exhaustion thường là triệu chứng, không phải root cause.
- Connection lifetime ngắn quan trọng hơn pool thật lớn.
- Điều tra query/transaction/blocking trước khi tăng capacity.

# 4. Azure Blob Storage large-file upload: streaming, SAS và failure recovery

## 1. What is it?

Azure Blob Storage là object storage; với file lớn, thiết kế tốt thường stream/chunk dữ liệu thay vì buffer toàn bộ file trong application memory. SAS cho phép cấp quyền giới hạn thời gian và phạm vi để client upload trực tiếp.

## 2. Why does it exist?

Proxy file 2 GB qua ASP.NET Core làm application chịu network bandwidth, memory pressure, timeout và scale cost không cần thiết. Object storage được tối ưu cho payload lớn và durability.

## 3. How does it work?

```text
Client -> API: request upload authorization
API -> Client: short-lived SAS
Client -> Blob Storage: upload blocks
Client -> API: finalize metadata
```

Block blob cho phép upload từng block rồi commit block list.

## 4. Practical implementation

```csharp
var blob = container.GetBlobClient(blobName);
await blob.UploadAsync(
    stream,
    new BlobUploadOptions
    {
        HttpHeaders = new BlobHttpHeaders { ContentType = contentType }
    },
    ct);
```

Trong production, ưu tiên Managed Identity cho backend; SAS nên short-lived, least privilege và giới hạn container/blob khi có thể.

## 5. Real production scenario

CMS cho editor upload video 800 MB. Direct-to-Blob giúp App Service không phải giữ request body và không scale chỉ vì bandwidth upload.

## 6. Failure scenario & troubleshooting

**Symptom** → upload dừng ở 70%, user phải làm lại.  
**Evidence** → client network reset; committed blob chưa tồn tại nhưng uncommitted blocks có thể còn.  
**Hypothesis** → upload không resumable hoặc SAS hết hạn giữa phiên.  
**Diagnosis** → kiểm tra block IDs, SAS expiry, client retry telemetry.  
**Fix** → chunk/resume strategy, đủ TTL nhưng không quá dài, idempotent finalize.  
**Verification** → fault injection giữa các block.

## 7. Common mistakes

SAS có quyền rộng; lưu storage account key trong frontend; buffer `IFormFile` lớn vào memory; tin Content-Type/file extension do client gửi.

## 8. Alternatives

Proxy qua API phù hợp file nhỏ hoặc khi phải inspect synchronously. Azure Data Lake phù hợp analytics hierarchy. SFTP có thể cần cho legacy integration nhưng operational model khác.

## 9. Trade-offs

### Advantages

Giảm tải app tier, scale upload tốt, retry/chunk linh hoạt.

### Costs / Risks

Client flow phức tạp hơn; phải quản lý orphan upload, malware scanning và authorization lifecycle.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu object storage khác filesystem local.

### Middle

Implement streaming/SAS và validation.

### Senior

Thiết kế resume, scanning, lifecycle cleanup và observability.

### Technical Lead / Architect

Quyết định trust boundary: ai cấp quyền, ai xác nhận upload, metadata transaction nằm ở đâu và failure recovery ra sao.

## 11. Key takeaway

- File lớn không nên mặc định đi xuyên app server.
- SAS là delegated capability, phải least privilege và short-lived.
- Upload success và business finalize là hai trạng thái cần xử lý riêng.

# 5. Distributed timeout budget: kiểm soát latency xuyên chuỗi dependency

## 1. What is it?

Timeout budget là giới hạn thời gian end-to-end được phân bổ cho từng dependency thay vì mỗi hop tự chọn timeout độc lập. Mental model: request chỉ có **một ngân sách latency**, không phải vô hạn ở mỗi service.

## 2. Why does it exist?

API timeout 3 giây nhưng gọi ba dependency mỗi cái timeout 10 giây là thiết kế mâu thuẫn. Khi failure xảy ra, work tiếp tục vô ích sau khi caller đã bỏ cuộc, gây resource amplification.

## 3. How does it work?

```text
Client budget 3s
  API work 200ms
  Catalog budget 800ms
  Pricing budget 700ms
  DB budget 600ms
  reserve 700ms
```

Cancellation/deadline phải propagate. Retry tiêu tốn cùng budget, không reset đồng hồ.

## 4. Practical implementation

```csharp
using var budget = CancellationTokenSource.CreateLinkedTokenSource(requestAborted);
budget.CancelAfter(TimeSpan.FromMilliseconds(800));

using var response = await httpClient.GetAsync(
    "/pricing/42", budget.Token);
```

Production code nên dùng policy rõ ràng và telemetry ghi remaining budget/dependency duration.

## 5. Real production scenario

Product page gọi CMS, pricing, reviews. Reviews chậm không nên giữ toàn trang 20 giây; có thể budget 400 ms và degrade phần reviews nếu business cho phép.

## 6. Failure scenario & troubleshooting

**Symptom** → caller timeout ở 3 giây nhưng downstream tiếp tục CPU/DB thêm 20 giây.  
**Evidence** → trace span downstream kết thúc rất lâu sau parent.  
**Hypothesis** → cancellation không propagate hoặc retry policy reset timeout.  
**Diagnosis** → inspect trace waterfall và token propagation.  
**Fix** → linked cancellation, per-hop budget, bounded retries.  
**Verification** → inject slow dependency và xác nhận spans dừng trong deadline.

## 7. Common mistakes

Timeout quá lớn “cho chắc”; retry mọi timeout; dùng cùng timeout cho interactive và batch workload; không phân biệt connection timeout với operation timeout.

## 8. Alternatives

Async messaging loại bỏ synchronous latency coupling khi business không cần response tức thì. Cached/stale data có thể là fallback nếu freshness cho phép.

## 9. Trade-offs

### Advantages

Giới hạn failure propagation và tail latency.

### Costs / Risks

Timeout quá aggressive gây false failure; fallback có thể làm semantics phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout là correctness/reliability concern.

### Middle

Propagate cancellation và cấu hình HttpClient timeout hợp lý.

### Senior

Thiết kế retry trong deadline và đọc distributed trace.

### Technical Lead / Architect

Phân bổ latency budget theo SLO và quyết định dependency nào bắt buộc, optional hay asynchronous.

## 11. Key takeaway

- Retry không được tạo ngân sách thời gian mới.
- Deadline phải propagate xuyên call chain.
- Latency budget buộc kiến trúc thể hiện dependency nào thực sự critical.

# 6. React/Vue request cancellation: tránh stale UI và race condition phía browser

## 1. What is it?

Request cancellation phía browser dùng `AbortController` để hủy fetch không còn cần thiết. Vấn đề sâu hơn là **response ordering**: request cũ có thể hoàn tất sau request mới và ghi đè state đúng bằng dữ liệu cũ.

## 2. Why does it exist?

Autocomplete/search/filter tạo request nhanh theo thao tác user. Network không đảm bảo request gửi trước sẽ trả trước.

## 3. How does it work?

```text
search "ca" ----slow----> response A
search "car" --fast--> response B -> UI = car
response A -----------------------> nếu không guard: UI = ca
```

Abort giúp giảm work thừa; sequence/version guard bảo vệ state kể cả khi cancellation không kịp.

## 4. Practical implementation

```typescript
let controller: AbortController | undefined;

async function search(term: string) {
  controller?.abort();
  controller = new AbortController();

  try {
    const r = await fetch(`/api/search?q=${encodeURIComponent(term)}`, {
      signal: controller.signal
    });
    results.value = await r.json();
  } catch (e) {
    if ((e as DOMException).name !== "AbortError") throw e;
  }
}
```

## 5. Real production scenario

Automotive marketplace filter thay đổi make/model/year liên tục. Response cũ ghi đè response mới khiến UI hiển thị inventory sai dù backend hoàn toàn đúng.

## 6. Failure scenario & troubleshooting

**Symptom** → kết quả đôi lúc “nhảy ngược” khi gõ nhanh.  
**Evidence** → DevTools Network cho thấy response completion order khác request order.  
**Hypothesis** → stale response updates state.  
**Diagnosis** → log query + sequence ID tại component.  
**Fix** → abort previous request và/hoặc chỉ accept latest sequence.  
**Verification** → throttle network và thao tác nhanh.

## 7. Common mistakes

Hiển thị AbortError như lỗi cho user; assume abort luôn ngăn server xử lý; dùng debounce như giải pháp duy nhất cho race condition.

## 8. Alternatives

Debounce giảm số request. Query libraries như TanStack Query cung cấp caching/cancellation patterns. Server-side request coalescing giải quyết vấn đề khác.

## 9. Trade-offs

### Advantages

Giảm stale state và work thừa.

### Costs / Risks

Lifecycle phức tạp hơn; cancellation browser không đảm bảo backend đã dừng nếu signal không propagate.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async completion order không cố định.

### Middle

Dùng AbortController và cleanup component lifecycle.

### Senior

Phân biệt debounce, cancellation, deduplication và cache semantics.

### Technical Lead / Architect

Định nghĩa frontend data-fetching convention và API semantics để UI race không biến thành business inconsistency.

## 11. Key takeaway

- Request order không đồng nghĩa response order.
- Cancellation và latest-response guard giải quyết hai phần khác nhau.
- DevTools network throttling là cách tái hiện race rất hiệu quả.

# 7. Modular Monolith: boundary và data ownership trước khi nghĩ đến Microservices

## 1. What is it?

Modular Monolith là một deployable application nhưng code/domain được chia thành module có boundary rõ: ownership, public contract và dependency rules. Nó không phải “monolith với nhiều folder”.

## 2. Why does it exist?

Một monolith không boundary trở thành tightly coupled. Microservices có thể tách deployment nhưng thêm network, eventual consistency, observability và operations. Modular Monolith giữ transaction/deployment đơn giản trong khi buộc team học cách tạo business boundaries.

## 3. How does it work?

```text
Host
 ├─ Orders module -> owns Orders tables
 ├─ Catalog module -> owns Catalog tables
 └─ Identity module -> owns identity concerns
```

Module khác không nên query trực tiếp bảng nội bộ chỉ vì cùng database. Communication có thể qua public application interface hoặc in-process event.

## 4. Practical implementation

```csharp
public interface IInventoryAvailability
{
    Task<Availability> GetAsync(ProductId id, CancellationToken ct);
}

// Orders depends on this contract, not Inventory DbContext.
```

Có thể enforce dependency bằng project boundaries/architecture tests.

## 5. Real production scenario

E-commerce 12 developers chưa cần independent scaling/deployment. Orders và Catalog thay đổi cùng release. Modular Monolith giảm operational burden nhưng vẫn cô lập business change.

## 6. Failure scenario & troubleshooting

**Symptom** → sửa Catalog làm Orders test vỡ liên tục.  
**Evidence** → Orders reference Catalog EF entities/tables trực tiếp.  
**Hypothesis** → module boundary chỉ tồn tại trên sơ đồ.  
**Diagnosis** → dependency graph và cross-module SQL.  
**Fix** → public contract, ownership rõ, migration dần cross-module reads.  
**Verification** → architecture tests cấm forbidden references.

## 7. Common mistakes

Một shared project chứa mọi domain model; generic repository dùng xuyên module; module gọi thẳng database table của nhau; dùng MediatR rồi gọi đó là modular architecture.

## 8. Alternatives

Simple layered monolith tốt cho domain nhỏ. Microservices hợp khi có nhu cầu independent deployment/scale/ownership đủ mạnh. Modulith có thể là bước tiến hóa, không nhất thiết là bước tạm thời.

## 9. Trade-offs

### Advantages

Operational simplicity, local transaction, boundary tốt hơn monolith tùy tiện.

### Costs / Risks

Boundary cần discipline; shared database dễ bị lạm dụng; không cung cấp failure isolation như process boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module đại diện business capability.

### Middle

Code chỉ qua public contract.

### Senior

Thiết kế ownership, dependency direction và transaction boundary.

### Technical Lead / Architect

Quyết định khi nào boundary cần process/deployment riêng dựa trên scale, team ownership và failure isolation chứ không theo xu hướng.

## 11. Key takeaway

- Boundary quan trọng hơn số lượng services.
- Một database không có nghĩa mọi module được sở hữu mọi table.
- Microservices chỉ đáng giá khi lợi ích vượt operational complexity.

# 8. Docker image layering: reproducible build, cache và attack surface

## 1. What is it?

Docker image gồm các immutable layers. Mỗi instruction thường tạo filesystem layer; build cache có thể tái sử dụng layer khi inputs không đổi. Multi-stage build tách môi trường build khỏi runtime image.

## 2. Why does it exist?

Nếu copy toàn source trước restore, một thay đổi nhỏ làm invalid cache và restore lại dependencies. Nếu ship SDK/compiler vào production, image lớn hơn và attack surface tăng.

## 3. How does it work?

```text
base runtime
  + app binaries
  + config-independent files
= runtime image

SDK/build tools remain in build stage only
```

Layer ordering ảnh hưởng build time và cache hit.

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY ["Api/Api.csproj", "Api/"]
RUN dotnet restore "Api/Api.csproj"
COPY . .
RUN dotnet publish "Api/Api.csproj" -c Release -o /out --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /out .
ENTRYPOINT ["dotnet", "Api.dll"]
```

Pinning base image digest có thể tăng reproducibility nhưng cần process cập nhật security patches.

## 5. Real production scenario

CI build 20 services. Chỉ thay một `.cs` file nhưng pipeline restore NuGet mỗi lần vì Dockerfile copy toàn repo quá sớm. Reorder layers giảm build time đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → image build “thành công” nhưng production thiếu native library hoặc base image có CVE cũ.  
**Evidence** → SBOM/scanner, container startup logs.  
**Hypothesis** → build stage và runtime stage khác dependency assumptions hoặc image pin quá lâu.  
**Diagnosis** → inspect layers/base digest và runtime dependencies.  
**Fix** → explicit runtime dependencies, automated base refresh, image scanning.  
**Verification** → run container smoke test từ chính artifact sẽ deploy.

## 7. Common mistakes

Dùng `latest`; copy secrets vào layer rồi xóa ở layer sau; chạy root không cần thiết; copy `.git`, test output và local artifacts vì thiếu `.dockerignore`.

## 8. Alternatives

Framework-dependent deployment không container vẫn phù hợp IIS/App Service scenarios. Native AOT giảm footprint trong một số workload nhưng có compatibility trade-offs.

## 9. Trade-offs

### Advantages

Reproducible packaging, isolation, consistent artifact promotion.

### Costs / Risks

Image supply chain, patching và registry lifecycle trở thành operational responsibilities.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu image khác container và layer là immutable.

### Middle

Viết multi-stage Dockerfile và `.dockerignore`.

### Senior

Tối ưu cache, non-root runtime, scanning và artifact provenance.

### Technical Lead / Architect

Quyết định container có thực sự cải thiện deployment model và xây policy cho base images, patch cadence, SBOM.

## 11. Key takeaway

- Dockerfile ordering là cả performance lẫn reproducibility concern.
- Xóa secret ở layer sau không xóa secret khỏi layer trước.
- Production image nên chứa đúng runtime cần thiết, không phải toàn build toolchain.

# 9. Technical SEO: canonical URL, redirects và HTTP semantics trong dynamic application

## 1. What is it?

Technical SEO ở góc độ engineering là làm cho crawler hiểu resource identity, status và navigation. Canonical URL nói URL nào đại diện chính cho nội dung tương đương; redirect nói resource đã chuyển; HTTP status mô tả kết quả thực tế.

## 2. Why does it exist?

Dynamic site dễ sinh nhiều URL cho cùng nội dung qua query strings, casing, locale, tracking parameters hoặc CMS routing. Nếu semantics sai, crawler có thể index duplicate content hoặc giữ URL cũ.

## 3. How does it work?

```text
/Products/42?utm=x
       |
       +-> canonical: /products/42

/old-product -> 301 -> /products/42
/deleted     -> 404/410
```

Canonical là hint về identity; nó không thay thế redirect khi URL thực sự đã chuyển.

## 4. Practical implementation

Trong ASP.NET Core/CMS, tạo canonical từ routing/content identity thay vì raw request URL:

```csharp
var canonical = $"{origin}/products/{product.Slug}";
ViewData["CanonicalUrl"] = canonical;
```

Razor layout render:

```html
<link rel="canonical" href="@ViewData["CanonicalUrl"]" />
```

Redirect map nên version/control như application data, không hard-code rải rác.

## 5. Real production scenario

Optimizely CMS đổi slug chiến dịch. Nếu URL cũ trả 200 với duplicate page, search engine có hai identities. 301 từ old slug sang new slug cùng canonical mới giữ semantics rõ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → Search Console báo duplicate/canonical mismatch; traffic organic giảm sau CMS migration.  
**Evidence** → crawl sample thấy 200 cho URL cũ, canonical trỏ sai host hoặc redirect chain.  
**Hypothesis** → migration không preserve URL semantics.  
**Diagnosis** → inspect HTTP headers, HTML canonical, sitemap và redirect map.  
**Fix** → 301 trực tiếp, canonical absolute đúng origin, sitemap chỉ chứa canonical URLs.  
**Verification** → crawl staging/prod và kiểm tra representative URL set.

## 7. Common mistakes

Trả 200 cho “not found” (soft 404); canonical mọi page về homepage; redirect chain nhiều hop; canonical chứa tracking query; render canonical chỉ bằng client-side JavaScript khi không cần thiết.

## 8. Alternatives

Không có canonical nếu mỗi URL thực sự unique. `noindex` giải quyết indexing intent khác canonicalization. Robots.txt kiểm soát crawl access, không phải công cụ xóa URL đã index.

## 9. Trade-offs

### Advantages

Resource identity rõ, migration URL an toàn hơn, giảm duplicate crawling.

### Costs / Risks

Rule sai có thể de-index nội dung hợp lệ ở quy mô lớn; SEO config trở thành production-critical behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 200/301/404 và canonical có semantics khác nhau.

### Middle

Implement redirect/canonical/sitemap đúng routing.

### Senior

Test migration, detect soft 404 và canonical drift.

### Technical Lead / Architect

Đưa URL identity vào content/data migration plan và release validation, không để nó thành việc “marketing sửa sau”.

## 11. Key takeaway

- Canonical không thay thế redirect.
- HTTP status là API contract với crawler.
- URL migration cần test như một production data migration.

# 10. Contract testing cho third-party API: bảo vệ integration trước silent breaking change

## 1. What is it?

Contract testing kiểm tra assumptions tại boundary giữa hệ thống của ta và external API: fields, types, required semantics, status/error behavior. Mục tiêu không phải test implementation của vendor mà là bảo vệ **những gì code của ta thực sự phụ thuộc**.

## 2. Why does it exist?

Unit test với mock tự viết có thể luôn xanh vì mock phản ánh điều ta mong đợi, không phản ánh provider thật. Vendor đổi nullable field, enum value hoặc error payload có thể phá production dù code không đổi.

## 3. How does it work?

```text
Our adapter -> explicit DTO/contract -> external API
      |
      +-> unit tests for mapping
      +-> integration/contract checks against sandbox/recorded schema
```

Boundary adapter cô lập vendor model khỏi domain model.

## 4. Practical implementation

```csharp
public sealed record ReviewResponse(
    string Id,
    decimal Rating,
    string? Comment);

public async Task<ReviewResponse> GetReviewAsync(
    string id, CancellationToken ct)
{
    using var response = await _client.GetAsync($"/reviews/{id}", ct);
    response.EnsureSuccessStatusCode();

    return (await response.Content.ReadFromJsonAsync<ReviewResponse>(
        cancellationToken: ct))!;
}
```

Contract test nên dùng representative provider response, đặc biệt unknown enum, nullable field, rate-limit và error shape.

## 5. Real production scenario

Review provider thêm enum state mới. Client dùng strict switch expression không có fallback và bắt đầu 500 trên product pages. Adapter + contract monitoring giúp failure bị phát hiện trước hoặc degrade có kiểm soát.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment không đổi nhưng deserialization error tăng đột ngột.  
**Evidence** → external dependency span 200 OK nhưng application exception tại JSON mapping.  
**Hypothesis** → provider contract drift.  
**Diagnosis** → capture sanitized response/schema diff và đối chiếu vendor changelog.  
**Fix** → tolerant reader ở nơi phù hợp, adapter mapping, pin API version nếu provider hỗ trợ.  
**Verification** → replay payload mới trong contract test và canary.

## 7. Common mistakes

Dùng vendor DTO xuyên domain; mock mọi HTTP call nên không bao giờ test serialization; log toàn raw payload chứa PII; retry deserialization error như transient network failure.

## 8. Alternatives

Consumer-driven contracts phù hợp khi ta kiểm soát provider hoặc có collaboration. Schema validation/OpenAPI diff hữu ích cho structural changes. E2E sandbox test bắt behavior thật nhưng thường chậm và flaky hơn.

## 9. Trade-offs

### Advantages

Phát hiện integration drift, cô lập vendor coupling, làm assumptions explicit.

### Costs / Risks

Sandbox có thể khác production; contract suite cần maintenance; quá strict sẽ báo lỗi với additive compatible changes.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external JSON không phải domain model của mình.

### Middle

Xây typed HttpClient/adapter, test mapping và error cases.

### Senior

Thiết kế tolerant boundaries, telemetry, timeout/retry và sanitized evidence.

### Technical Lead / Architect

Quyết định provider failure có được degrade không, API version strategy, ownership contract monitoring và migration/exit strategy nếu vendor thay đổi.

## 11. Key takeaway

- Mock tự viết không chứng minh provider vẫn giữ contract.
- Cô lập third-party model tại adapter boundary.
- Contract drift phải observable và có failure policy rõ ràng.
