# 1. C# records và value equality: mô hình hóa immutable data mà không nhầm identity với equality

## 1. What is it?

`record` là kiểu C# tối ưu cho dữ liệu mà equality thường dựa trên giá trị thay vì object identity. Hai record có cùng thành phần có thể bằng nhau dù là hai instance khác nhau. Mental model: Entity thường hỏi “có cùng identity không?”, còn Value Object hỏi “có cùng giá trị không?”.

## 2. Why does it exist?

DTO, command và Value Object thường cần equality, deconstruction và immutable-style update. Viết thủ công `Equals`, `GetHashCode` và copy logic vừa dài vừa dễ sai. Record giảm boilerplate nhưng không thay developer quyết định semantics.

## 3. How does it work?

Compiler sinh value-based equality cho record members và hỗ trợ `with` expression. Với `record class`, object vẫn là reference type; điều thay đổi là equality semantics.

```csharp
public sealed record Money(decimal Amount, string Currency);

var a = new Money(100, "USD");
var b = new Money(100, "USD");
Console.WriteLine(a == b); // True
```

## 4. Practical implementation

```csharp
public sealed record Address(string Line1, string City, string CountryCode);

public sealed class Customer
{
    public Guid Id { get; init; }
    public Address BillingAddress { get; private set; } = default!;

    public void ChangeBillingAddress(Address address) => BillingAddress = address;
}
```

`Customer` có identity; `Address` được xem như một giá trị trong aggregate.

## 5. Real production scenario

Một pricing service dùng `Money` làm Value Object. Equality theo `Amount + Currency` giúp tests, deduplication và domain rules rõ hơn. Ngược lại, nếu `Order` được đổi thành record chỉ vì muốn syntax ngắn, hai orders có field giống nhau có thể bị hiểu sai về domain identity.

## 6. Failure scenario & troubleshooting

**Symptom** → `HashSet`/dictionary behavior thay đổi bất ngờ. **Evidence** → record chứa mutable member tham gia hash code. **Hypothesis** → object bị mutate sau khi làm key. **Diagnosis** → kiểm tra equality members. **Fix** → giữ value objects immutable hoặc không dùng mutable object làm hashed key. **Verification** → tests equality/hash behavior.

## 7. Common mistakes

* Dùng record cho mọi entity.
* Cho mutable collection vào record rồi kỳ vọng deep structural equality.
* Nhầm `with` với deep clone.
* Dùng equality semantics mà không gắn với domain meaning.

## 8. Alternatives

Class thường phù hợp entity có lifecycle/identity. `readonly record struct` phù hợp value nhỏ khi copy cost hợp lý. Class + custom equality phù hợp khi semantics đặc biệt.

## 9. Trade-offs

### Advantages

* Equality/value semantics rõ.
* Ít boilerplate.
* Hợp DTO và Value Object immutable.

### Costs / Risks

* Dễ áp dụng sai cho entity.
* `with` copy nông.
* Mutable members có thể phá assumptions về equality/hash.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt reference identity và value equality.

### Middle

Dùng records cho DTO/Value Object và hiểu `with`.

### Senior

Đánh giá equality, mutability và collection semantics.

### Technical Lead / Architect

Đặt modeling convention: entity identity ở đâu, value semantics ở đâu, tránh chọn type chỉ theo syntax.

## 11. Key takeaway

* Record là công cụ cho value semantics, không phải “class mới tốt hơn”.
* Equality phải phản ánh domain meaning.
* Immutability làm record an toàn và dễ reasoning hơn.

# 2. ASP.NET Core Request Timeouts: deadline ở request boundary và cancellation propagation xuống dependency

## 1. What is it?

Request timeout đặt giới hạn thời gian một HTTP request được phép tiêu thụ trước khi application hủy work. Timeout chỉ có giá trị nếu cancellation được propagate xuống EF Core, `HttpClient` và các operation dài.

## 2. Why does it exist?

Không có deadline, một dependency treo có thể giữ request, memory và connection quá lâu. Khi traffic tăng, các request chậm tích tụ thành resource exhaustion.

## 3. How does it work?

ASP.NET Core timeout policy tạo cancellation signal khi deadline hết. Application code phải nhận `CancellationToken`; dependency async APIs phải dùng token đó. Timeout không “giết thread”; cooperative cancellation yêu cầu code tham gia.

## 4. Practical implementation

```csharp
builder.Services.AddRequestTimeouts(options =>
{
    options.AddPolicy("api", TimeSpan.FromSeconds(5));
});

app.UseRequestTimeouts();

app.MapGet("/orders/{id:guid}", async (
    Guid id, AppDbContext db, CancellationToken ct) =>
{
    var order = await db.Orders.AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);
    return order is null ? Results.NotFound() : Results.Ok(order);
}).WithRequestTimeout("api");
```

## 5. Real production scenario

Order API có SLO 2 giây nhưng downstream inventory client timeout 100 giây. Inventory degradation làm request backlog tăng. Đặt end-to-end deadline và propagate cancellation giúp giải phóng work sớm, đồng thời timeout của downstream phải nhỏ hơn remaining request budget.

## 6. Failure scenario & troubleshooting

**Symptom** → client đã timeout nhưng SQL vẫn chạy lâu. **Evidence** → trace cho thấy DB dependency tiếp tục sau request cancellation. **Hypothesis** → token bị bỏ qua. **Diagnosis** → kiểm tra call chain. **Fix** → propagate token và dùng async API hỗ trợ cancellation. **Verification** → cancel request trong test và quan sát dependency dừng.

## 7. Common mistakes

* Timeout ở reverse proxy nhưng backend không biết cancellation.
* Mỗi dependency có timeout lớn hơn total request budget.
* Catch `OperationCanceledException` rồi retry vô điều kiện.
* Dùng timeout như thay thế cho capacity management.

## 8. Alternatives

Gateway timeout bảo vệ edge; `HttpClient.Timeout` bảo vệ một dependency; resilience pipeline có timeout per attempt. Chúng cần phối hợp theo deadline budget.

## 9. Trade-offs

### Advantages

* Bound resource consumption.
* Failure nhanh và predictable hơn.
* Giảm backlog khi dependency degradation.

### Costs / Risks

* Timeout quá ngắn tạo false failures.
* Cancellation không cooperative sẽ không giải phóng work.
* Retry sau timeout có thể tăng tải.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout khác exception business.

### Middle

Propagate `CancellationToken` end-to-end.

### Senior

Thiết kế timeout budget, retry và dependency deadlines.

### Technical Lead / Architect

Định nghĩa latency budget theo SLO và failure propagation giữa services.

## 11. Key takeaway

* Timeout phải đi cùng cancellation propagation.
* Total deadline quan trọng hơn timeout rời rạc từng dependency.
* Timeout không sửa dependency chậm; nó giới hạn blast radius.

# 3. EF Core Temporal Tables: audit và point-in-time recovery mà không tự xây history table thiếu nhất quán

## 1. What is it?

SQL Server temporal table tự giữ lịch sử các phiên bản row theo system time. EF Core hỗ trợ mapping/query lịch sử, cho phép hỏi dữ liệu “đã trông như thế nào tại thời điểm X”.

## 2. Why does it exist?

Audit thủ công thường bị quên ở một code path, đặc biệt khi update đến từ migration, admin tool hoặc background job. Temporal tables đưa version history xuống database boundary.

## 3. How does it work?

Current table có period columns; SQL Server chuyển version cũ sang history table khi `UPDATE`/`DELETE`. EF Core có `TemporalAsOf`, `TemporalBetween` và related APIs.

## 4. Practical implementation

```csharp
modelBuilder.Entity<Employee>()
    .ToTable("Employees", b => b.IsTemporal());

var snapshot = await db.Employees
    .TemporalAsOf(incidentTime)
    .AsNoTracking()
    .SingleAsync(x => x.Id == employeeId, ct);
```

Migration phải được review vì bật temporal trên table lớn có operational impact.

## 5. Real production scenario

HR system cần điều tra vì sao employee grade thay đổi trước payroll run. Temporal query cho thấy row trước/sau deployment mà không cần restore full backup sang database khác.

## 6. Failure scenario & troubleshooting

**Symptom** → history table tăng rất nhanh. **Evidence** → hot rows update nhiều lần/phút. **Hypothesis** → retention chưa được thiết kế. **Diagnosis** → đo history growth và update frequency. **Fix** → retention/archive policy phù hợp compliance. **Verification** → monitor storage growth.

## 7. Common mistakes

* Xem temporal history như domain audit log hoàn chỉnh; nó không tự lưu “ai” hay “vì sao”.
* Không thiết kế retention.
* Query history như current table trong hot path.
* Bật temporal mà không đánh giá migration/table size.

## 8. Alternatives

Application audit log lưu actor/reason tốt hơn. Event Sourcing lưu domain events nhưng complexity cao hơn. CDC phục vụ change integration hơn point-in-time domain audit.

## 9. Trade-offs

### Advantages

* History nhất quán ở DB boundary.
* Point-in-time query tiện lợi.
* Ít application boilerplate.

### Costs / Risks

* Storage tăng.
* Không tự có business context.
* Migration/retention cần vận hành.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu current row và historical versions.

### Middle

Map/query temporal bằng EF Core.

### Senior

Đánh giá retention, indexing và audit semantics.

### Technical Lead / Architect

Quyết định temporal, audit events hay Event Sourcing dựa trên requirement thật.

## 11. Key takeaway

* Temporal tables tốt cho row history, không thay thế domain audit trail.
* Retention là phần của thiết kế.
* Dùng khi point-in-time recovery/audit có giá trị thực.

# 4. SQL constraints như invariant cuối cùng: dùng `UNIQUE`, `CHECK` và foreign key để bảo vệ dữ liệu trước race condition

## 1. What is it?

Database constraint là invariant được database enforce cho mọi writer. Nó là lớp bảo vệ cuối cùng sau validation ở UI/API/application.

## 2. Why does it exist?

Application check kiểu “SELECT xem email tồn tại chưa rồi INSERT” có race condition: hai transaction có thể cùng thấy chưa tồn tại. `UNIQUE` constraint biến invariant thành atomic guarantee tại database.

## 3. How does it work?

Constraint được kiểm tra trong write operation/transaction. `UNIQUE` thường dựa trên unique index; FK bảo vệ referential integrity; `CHECK` giới hạn giá trị hợp lệ.

## 4. Practical implementation

```sql
CREATE UNIQUE INDEX UX_Users_NormalizedEmail
ON Users(NormalizedEmail);

ALTER TABLE Orders ADD CONSTRAINT CK_Orders_Total
CHECK (Total >= 0);

ALTER TABLE Orders ADD CONSTRAINT FK_Orders_Customers
FOREIGN KEY (CustomerId) REFERENCES Customers(Id);
```

Application vẫn validate để trả lỗi thân thiện, nhưng phải xử lý constraint violation vì race vẫn có thể xảy ra.

## 5. Real production scenario

Hai requests đăng ký cùng email đến gần đồng thời. Cả hai pass application-level existence check. Unique index cho phép đúng một transaction commit; request còn lại map database error thành `409 Conflict`.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment thêm constraint thất bại. **Evidence** → dữ liệu legacy đã vi phạm invariant. **Hypothesis** → schema rule mới không tương thích existing data. **Diagnosis** → query duplicate/invalid rows. **Fix** → clean/backfill trước, sau đó enforce. **Verification** → pre-deployment validation query.

## 7. Common mistakes

* Chỉ validation ở API.
* Không có FK vì sợ performance mà chấp nhận orphan data.
* Dùng constraint quá phức tạp thay business workflow.
* Parse database error bằng message text không ổn định.

## 8. Alternatives

Application validation cần cho UX/business context. Trigger có thể enforce logic phức tạp hơn nhưng hidden behavior cao. Serializable transaction có thể giải một số race nhưng cost lớn hơn constraint đơn giản.

## 9. Trade-offs

### Advantages

* Enforce cho mọi writer.
* Chống race ở data boundary.
* Giữ dữ liệu đáng tin cậy lâu dài.

### Costs / Risks

* Write có thêm validation/index cost.
* Migration legacy data khó hơn.
* Một số invariant cross-service không thể đặt trong một DB.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu constraint không chỉ để document schema.

### Middle

Thiết kế UNIQUE/FK/CHECK và map violation.

### Senior

Reason về concurrency, migration và index cost.

### Technical Lead / Architect

Xác định invariant nào thuộc database ownership boundary và invariant nào cần domain coordination.

## 11. Key takeaway

* Application validation không thay database constraints.
* Constraint là công cụ concurrency correctness rất mạnh.
* Schema migration phải xử lý dữ liệu cũ trước khi enforce rule mới.

# 5. Cosmos DB Change Feed: xây asynchronous projection và integration flow từ ordered partition changes

## 1. What is it?

Cosmos DB Change Feed cung cấp stream các thay đổi của items theo thứ tự trong logical partition. Consumer có thể đọc incrementally để xây projection, trigger integration hoặc downstream processing.

## 2. Why does it exist?

Polling toàn container vừa tốn RU vừa khó xác định chính xác thay đổi mới. Change Feed biến database changes thành incremental processing source.

## 3. How does it work?

Change Feed Processor chia lease theo partitions cho nhiều worker instances. Mỗi worker đọc changes, checkpoint progress và lease có thể rebalance khi scale.

## 4. Practical implementation

```csharp
var processor = container
    .GetChangeFeedProcessorBuilder<Order>(
        "order-projection",
        async (changes, ct) =>
        {
            foreach (var order in changes)
                await projector.UpsertAsync(order, ct);
        })
    .WithInstanceName(Environment.MachineName)
    .WithLeaseContainer(leaseContainer)
    .Build();

await processor.StartAsync();
```

Projection phải idempotent vì processing có thể được lặp lại quanh failure/checkpoint boundary.

## 5. Real production scenario

Product container là source of truth; search projection cần cập nhật gần real-time. Change Feed consumer nhận product changes và update search index mà không scan toàn bộ container.

## 6. Failure scenario & troubleshooting

**Symptom** → projection lag tăng. **Evidence** → consumer RU throttling/429 và lease distribution lệch. **Hypothesis** → processor/downstream không đủ capacity. **Diagnosis** → theo dõi lag, RU, retry và partition distribution. **Fix** → scale processor/RU, batch hợp lý, tối ưu downstream. **Verification** → lag trở về SLO sau load test.

## 7. Common mistakes

* Giả định global ordering giữa partitions.
* Consumer không idempotent.
* Lease container cấu hình sai.
* Đẩy side effect chậm trực tiếp làm processor lag không giới hạn.

## 8. Alternatives

Outbox phù hợp relational transactional boundary. Event Grid phù hợp notification events. Service Bus phù hợp durable commands/work queues với settlement semantics rõ hơn.

## 9. Trade-offs

### Advantages

* Incremental processing tự nhiên.
* Scale theo partitions.
* Giảm polling waste.

### Costs / Risks

* Eventual consistency.
* Ordering chỉ có ý nghĩa trong partition boundary.
* Consumer lag và replay cần operational ownership.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Change Feed là stream thay đổi, không phải queue command.

### Middle

Cấu hình processor/lease và idempotent projection.

### Senior

Reason về partition ordering, RU, lag và recovery.

### Technical Lead / Architect

Chọn Change Feed khi database-owned changes là integration source phù hợp, thay vì dùng nó như event bus cho mọi workflow.

## 11. Key takeaway

* Partition key ảnh hưởng cả data scale lẫn processing semantics.
* Change Feed consumers phải chịu được replay.
* Theo dõi lag là requirement production.

# 6. Strangler Fig Pattern: hiện đại hóa legacy system theo vertical slice thay vì big-bang rewrite

## 1. What is it?

Strangler Fig là migration strategy trong đó traffic/capability được chuyển dần từ legacy system sang implementation mới qua một routing/boundary layer. Legacy co lại theo từng capability thay vì bị thay toàn bộ một lần.

## 2. Why does it exist?

Big-bang rewrite giữ business value “đóng băng” lâu, khó đạt feature parity và tạo cutover risk lớn. Incremental migration cho phép release, đo và rollback từng slice.

## 3. How does it work?

```text
Client
  ↓
Routing / Facade
  ├─ legacy capability
  └─ modern capability
```

Mỗi slice cần ownership rõ: request routing, data source, transaction boundary và synchronization strategy. Dependency direction của code mới không nên quay lại phụ thuộc sâu vào legacy internals.

## 4. Practical implementation

Một ASP.NET Core facade có thể route `/api/catalog/*` sang service mới trong khi `/api/orders/*` vẫn proxy legacy. Feature flag/canary có thể điều khiển traffic. Data migration nên chọn source of truth rõ thay vì dual-write tùy tiện.

## 5. Real production scenario

.NET Framework monolith chứa CMS, catalog và checkout. Team tách catalog read API trước vì boundary rõ và ít transaction coupling. Checkout vẫn ở legacy cho tới khi payment/inventory contracts được cô lập.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng business rule tồn tại ở legacy và service mới nhưng cho kết quả khác. **Evidence** → duplicated validation và dual ownership. **Hypothesis** → slice boundary chưa thực sự được chuyển ownership. **Diagnosis** → trace request/data ownership. **Fix** → xác định authoritative path và anti-corruption contract. **Verification** → contract/regression tests xuyên routing boundary.

## 7. Common mistakes

* Tách theo technical layer thay vì business capability.
* Dual-write hai databases không có reconciliation.
* Code mới gọi trực tiếp legacy database ở khắp nơi.
* Không có exit criteria để xóa legacy path.

## 8. Alternatives

In-place modularization rẻ hơn nếu deployment/runtime cũ vẫn đáp ứng. Big-bang rewrite chỉ hợp lý khi system nhỏ hoặc migration constraints đặc biệt.

## 9. Trade-offs

### Advantages

* Giảm cutover risk.
* Release value theo từng slice.
* Rollback/canary dễ hơn.

### Costs / Risks

* Tạm thời vận hành hai worlds.
* Routing/data synchronization tăng complexity.
* Migration kéo dài nếu không có ownership/exit plan.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu migration theo capability thay vì rewrite toàn bộ.

### Middle

Implement adapter/routing và compatibility tests.

### Senior

Thiết kế data ownership, anti-corruption boundary và rollback.

### Technical Lead / Architect

Chọn migration sequence theo business value, coupling, operational risk và khả năng xóa legacy thật sự.

## 11. Key takeaway

* Strangler là migration strategy, không phải microservices mandate.
* Data ownership quyết định độ khó nhiều hơn routing.
* Mỗi slice phải có exit criteria cho legacy.

# 7. Azure Event Grid: event notification fan-out khác gì Service Bus command/work queue

## 1. What is it?

Azure Event Grid là event routing service cho notification-style events: “điều gì đó đã xảy ra”. Nó phân phối event từ source tới nhiều handlers dựa trên subscriptions/filters.

## 2. Why does it exist?

Một producer không nên phải biết mọi consumer cần phản ứng với BlobCreated, resource change hay domain notification. Event Grid giảm direct coupling và hỗ trợ fan-out.

## 3. How does it work?

Publisher gửi event; Event Grid match subscriptions và push tới handlers. Delivery có retry và dead-letter options, nhưng semantics khác Service Bus queue với PeekLock, sessions và explicit settlement.

## 4. Practical implementation

```csharp
var client = new EventGridPublisherClient(topicEndpoint, credential);
await client.SendEventAsync(new EventGridEvent(
    subject: $"orders/{order.Id}",
    eventType: "Order.ExportReady",
    dataVersion: "1.0",
    data: new { order.Id, order.ExportUri }), ct);
```

Consumer vẫn phải idempotent vì duplicate delivery có thể xảy ra.

## 5. Real production scenario

Blob upload hoàn tất cần trigger thumbnail generation, malware scan telemetry và indexing. Event Grid fan-out notification phù hợp hơn để uploader gọi ba services trực tiếp.

## 6. Failure scenario & troubleshooting

**Symptom** → handler không nhận event. **Evidence** → delivery failures/endpoint 5xx hoặc filter không match subject. **Hypothesis** → subscription/filter/endpoint issue. **Diagnosis** → Event Grid metrics, dead-letter destination và handler logs. **Fix** → sửa filter/auth/endpoint; replay từ durable source nếu cần. **Verification** → publish synthetic event.

## 7. Common mistakes

* Dùng Event Grid như command queue cần strict ordering.
* Consumer không idempotent.
* Không cấu hình dead-letter cho critical events.
* Event payload chứa quá nhiều mutable business state.

## 8. Alternatives

Service Bus phù hợp commands, work queues, sessions và controlled settlement. Event Hubs phù hợp high-throughput telemetry streams. Direct HTTP đơn giản hơn khi chỉ có một synchronous dependency.

## 9. Trade-offs

### Advantages

* Fan-out và filtering tốt.
* Producer/consumer coupling thấp.
* Tích hợp Azure event sources thuận tiện.

### Costs / Risks

* Eventual delivery.
* Không thay thế queue semantics phức tạp.
* Recovery/replay phải được thiết kế theo source.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt event notification và command.

### Middle

Tạo subscription/filter và idempotent handler.

### Senior

Thiết kế retry, dead-letter, schema evolution và observability.

### Technical Lead / Architect

Chọn Event Grid, Service Bus hay Event Hubs dựa trên delivery semantics chứ không dựa trên việc “đều là messaging”.

## 11. Key takeaway

* Event Grid tối ưu event routing/fan-out.
* Service Bus mạnh hơn cho durable work/command semantics.
* Consumer event vẫn cần idempotency và failure recovery.

# 8. Connection-pool observability: tìm pool exhaustion từ latency, counters, traces và dependency behavior

## 1. What is it?

Connection pool tái sử dụng database connections vật lý. Pool exhaustion xảy ra khi request cần connection nhưng pool không còn connection khả dụng, nên phải chờ dù database CPU có thể vẫn thấp.

## 2. Why does it exist?

Mở connection vật lý cho mỗi query đắt. Pooling giảm handshake/authentication cost. Nhưng pool biến connection thành resource hữu hạn cần đo và release đúng lúc.

## 3. How does it work?

`OpenAsync` thường lấy connection từ pool. `Close`/`Dispose` trả connection về pool. Long transaction, leaked reader hoặc slow query giữ connection lâu làm waiters tăng.

## 4. Practical implementation

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(ct);

await using var command = connection.CreateCommand();
command.CommandText = "SELECT Status FROM Orders WHERE Id = @id";
command.Parameters.AddWithValue("@id", id);

var status = await command.ExecuteScalarAsync(ct);
```

Trong EF Core, giữ `DbContext` scoped ngắn và không giữ transaction xuyên remote API call.

## 5. Real production scenario

API timeout tăng nhưng SQL CPU 35%. Traces cho thấy thời gian trước SQL command lớn; một code path mở transaction rồi gọi third-party API 8 giây. Connections bị giữ trong lúc network wait, pool dần cạn.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout acquiring connection. **Evidence** → active connections gần pool max, DB CPU thấp, dependency duration cao. **Hypothesis** → connections bị giữ quá lâu. **Diagnosis** → traces + counters + transaction duration + code path. **Fix** → rút ngắn transaction, dispose đúng, tối ưu slow query. **Verification** → load test và đo pool wait/p95.

## 7. Common mistakes

* Tăng `Max Pool Size` trước khi tìm root cause.
* Giữ transaction trong lúc gọi HTTP.
* Singleton `DbContext`.
* Chỉ nhìn database CPU.

## 8. Alternatives

Tăng pool có thể phù hợp nếu DB capacity thực sự cho phép. Connection multiplexing/proxy có platform-specific use cases. Quan trọng nhất vẫn là giảm hold time và round trips.

## 9. Trade-offs

### Advantages

* Pooling giảm connection setup cost mạnh.
* Metrics pool giúp phát hiện bottleneck ngoài DB CPU.

### Costs / Risks

* Pool che giấu leak/long hold cho tới tải cao.
* Pool quá lớn có thể chuyển overload xuống database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Dispose` trả connection về pool.

### Middle

Dùng scoped lifetime và transaction ngắn.

### Senior

Correlation pool metrics, traces, SQL latency và downstream waits.

### Technical Lead / Architect

Thiết kế concurrency budget từ app instances × pool size × database capacity.

## 11. Key takeaway

* Pool exhaustion không đồng nghĩa database CPU cao.
* Connection hold time quan trọng như query time.
* Tăng pool size có thể chỉ di chuyển bottleneck.

# 9. CI/CD supply-chain hardening: immutable artifacts, pinned dependencies và verification trước promotion

## 1. What is it?

Supply-chain hardening bảo vệ đường đi từ source commit tới artifact production. Mục tiêu là biết chính xác source/dependencies nào tạo ra binary nào và chỉ promote artifact đã được kiểm tra.

## 2. Why does it exist?

Nếu mỗi environment build lại từ source, dependency floating hoặc mutable package có thể khiến staging và production không chạy cùng bits. Compromised dependency/build step cũng có thể chèn code ngoài review.

## 3. How does it work?

```text
commit
→ restore pinned dependencies
→ build
→ test/static/security checks
→ immutable artifact + provenance/hash
→ deploy staging
→ health validation
→ promote same artifact
→ production
→ monitor/rollback
```

## 4. Practical implementation

Với .NET, commit `packages.lock.json` khi phù hợp và dùng locked restore:

```bash
dotnet restore --locked-mode
dotnet test --no-restore
dotnet publish --no-restore -c Release -o ./artifact
```

Container image nên promote bằng digest, không rebuild/tag lại tùy môi trường.

## 5. Real production scenario

Team build Docker image riêng cho staging và production từ cùng Git SHA nhưng `latest` base image đã thay đổi giữa hai builds. Production nhận binary khác staging dù commit giống nhau. Build once/promote same digest loại drift này.

## 6. Failure scenario & troubleshooting

**Symptom** → production behavior khác staging. **Evidence** → image digests/package graph khác nhau. **Hypothesis** → rebuild/floating dependency. **Diagnosis** → compare provenance, hashes, lock files. **Fix** → immutable artifact promotion và pinned dependencies. **Verification** → deployment record cùng digest qua environments.

## 7. Common mistakes

* Dùng mutable `latest` để promotion.
* Secrets xuất hiện trong build logs/artifacts.
* CI cache được tin như source of truth.
* Security scan chạy nhưng không có policy/action.

## 8. Alternatives

Rebuild-per-environment đơn giản về config injection nhưng giảm reproducibility. Artifact promotion + runtime configuration thường rõ boundary hơn.

## 9. Trade-offs

### Advantages

* Reproducibility và auditability tốt.
* Giảm environment drift.
* Rollback chính xác artifact.

### Costs / Risks

* Cần artifact registry, retention và provenance discipline.
* Pinning dependencies cần quy trình update đều đặn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu build artifact là output cần version hóa.

### Middle

Thiết kế pipeline build/test/artifact/deploy rõ ràng.

### Senior

Quản lý lock files, hashes, secret boundaries và promotion.

### Technical Lead / Architect

Đặt trust model cho source, CI runners, registries, approvals, signing/provenance và rollback.

## 11. Key takeaway

* Cùng Git SHA chưa chắc cùng artifact nếu rebuild.
* Build once, promote same immutable artifact giảm drift.
* Supply-chain security là trust-chain problem xuyên toàn pipeline.

# 10. Content Security Policy: giảm XSS blast radius nhưng phải thiết kế policy theo asset/runtime thực tế

## 1. What is it?

Content Security Policy (CSP) là browser-enforced policy giới hạn nguồn script, style, frame, image và resource mà page được phép load/execute. Nó là defense-in-depth chống XSS, không thay input/output encoding.

## 2. Why does it exist?

Nếu attacker chèn được HTML/script, CSP chặt có thể ngăn inline script hoặc script từ domain không được phép chạy. Điều này giảm blast radius khi một injection bug lọt qua lớp validation/encoding.

## 3. How does it work?

Server trả header như:

```http
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-r4nd0m'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
```

Browser kiểm tra mỗi resource/execution với policy. Nonce cho phép script hợp lệ cụ thể mà không bật `'unsafe-inline'` toàn trang.

## 4. Practical implementation

ASP.NET Core middleware có thể tạo nonce per response và gắn CSP header:

```csharp
app.Use(async (context, next) =>
{
    var nonce = Convert.ToBase64String(RandomNumberGenerator.GetBytes(16));
    context.Items["CspNonce"] = nonce;
    context.Response.Headers.ContentSecurityPolicy =
        $"default-src 'self'; script-src 'self' 'nonce-{nonce}'; object-src 'none'; base-uri 'self'";
    await next();
});
```

Production implementation cần tích hợp rendering/template pipeline để nonce xuất hiện đúng script tags.

## 5. Real production scenario

Marketing/CMS site dùng nhiều third-party scripts. Team bật CSP ngay ở enforce mode và phá analytics/payment widget. Cách an toàn hơn là inventory sources, triển khai `Content-Security-Policy-Report-Only`, quan sát violations rồi siết policy dần.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend feature mất sau CSP rollout. **Evidence** → browser console/report endpoint báo blocked script. **Hypothesis** → legitimate source/nonce chưa được policy cho phép. **Diagnosis** → DevTools + CSP reports, không đơn giản thêm wildcard. **Fix** → chỉnh asset strategy/nonce hoặc allowlist tối thiểu. **Verification** → E2E tests và report-only monitoring trước enforce.

## 7. Common mistakes

* Thêm `'unsafe-inline'` để hết lỗi rồi coi CSP đã xong.
* Allowlist wildcard quá rộng.
* Nghĩ CSP thay output encoding/sanitization.
* Không test third-party integrations và CMS-authored content.

## 8. Alternatives

Output encoding, sanitization và framework auto-escaping là primary XSS controls. Trusted Types hỗ trợ giảm DOM XSS trong browser ecosystems phù hợp. CSP bổ sung chứ không thay các lớp đó.

## 9. Trade-offs

### Advantages

* Browser-enforced defense-in-depth.
* Giảm khả năng injected script thực thi.
* Có reporting hỗ trợ phát hiện policy violations.

### Costs / Risks

* Third-party-heavy sites khó triển khai.
* Policy maintenance là ongoing work.
* Misconfiguration có thể phá production hoặc tạo false sense of security.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CSP giới hạn resource/script execution ở browser.

### Middle

Đọc CSP violations và cấu hình basic directives.

### Senior

Thiết kế nonce/hash strategy, report-only rollout và third-party boundary.

### Technical Lead / Architect

Quyết định security baseline cho web properties, ownership policy và mức chấp nhận third-party script risk.

## 11. Key takeaway

* CSP là defense-in-depth, không thay secure coding.
* Nonce/hash tốt hơn mở rộng `'unsafe-inline'`.
* Rollout bằng evidence/reporting giúp tránh phá production.
