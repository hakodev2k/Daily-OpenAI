# 1. C# `Span<T>` vs `Memory<T>`: zero-copy processing, lifetime rules và boundary giữa synchronous với asynchronous code

## 1. What is it?

`Span<T>` và `ReadOnlySpan<T>` là lightweight views trên một vùng memory liên tục. Chúng cho phép cắt lát dữ liệu mà không cần tạo array/string mới cho mỗi thao tác.

Mental model:

```text
byte[] buffer
┌─────────────────────────────┐
│ header │ payload │ checksum │
└─────────────────────────────┘
    ↑         ↑
  Span      Span
```

`Span<T>` là `ref struct`, có lifetime bị compiler kiểm soát chặt và không thể sống trên heap. `Memory<T>`/`ReadOnlyMemory<T>` đại diện cho cùng kiểu vùng dữ liệu nhưng có thể được giữ lâu hơn và đi qua async boundary.

## 2. Why does it exist?

Trước đây, code parse protocol hoặc text thường dùng:

```csharp
var header = bytes.Skip(0).Take(16).ToArray();
```

hoặc:

```csharp
var prefix = input.Substring(0, 8);
```

Các thao tác này tạo allocation mới. Khi parser chạy hàng triệu lần, allocation nhỏ tích lũy thành GC pressure đáng kể.

`Span<T>` tồn tại để thao tác trên memory hiện có mà không copy khi không cần thiết.

## 3. How does it work?

Một `Span<T>` giữ reference tới memory cùng length. Slicing chỉ tạo view mới:

```csharp
Span<byte> payload = buffer.AsSpan(16, payloadLength);
```

Không có `byte[]` mới được tạo.

Nhưng vì `Span<T>` có thể trỏ vào stack memory hoặc memory có lifetime ngắn, compiler không cho phép nó được capture vào async state machine:

```csharp
// Không thể giữ Span qua await boundary.
```

Khi cần dữ liệu sống xuyên `await`, dùng `Memory<T>`:

```csharp
ReadOnlyMemory<byte> payload = buffer.AsMemory(offset, length);
await ProcessAsync(payload, ct);
```

## 4. Practical implementation

```csharp
public static bool TryReadFrame(
    ReadOnlySpan<byte> data,
    out ushort type,
    out ReadOnlySpan<byte> payload)
{
    type = 0;
    payload = default;

    if (data.Length < 4)
        return false;

    type = BinaryPrimitives.ReadUInt16BigEndian(data[..2]);
    var length = BinaryPrimitives.ReadUInt16BigEndian(data.Slice(2, 2));

    if (data.Length < 4 + length)
        return false;

    payload = data.Slice(4, length);
    return true;
}
```

Đây là synchronous parser tốt vì toàn bộ lifetime nằm trong call stack.

Nếu payload phải được gửi async:

```csharp
public Task SendAsync(ReadOnlyMemory<byte> payload, CancellationToken ct)
    => _stream.WriteAsync(payload, ct).AsTask();
```

## 5. Real production scenario

Một backend xử lý hàng chục nghìn telemetry messages mỗi giây. Version đầu chuyển nhiều đoạn `byte[]` thành arrays con và strings tạm thời.

CPU không cao vì business logic, mà phần lớn thời gian nằm ở allocation + GC. Chuyển hot parsing path sang `ReadOnlySpan<byte>` giảm allocation đáng kể mà không thay đổi kiến trúc hệ thống.

## 6. Failure scenario & troubleshooting

**Symptom** → throughput giảm khi traffic tăng, GC collections tăng mạnh nhưng SQL/HTTP dependencies vẫn nhanh.

**Evidence** → profiler cho thấy `Substring`, `ToArray`, LINQ materialization chiếm phần lớn allocations.

**Hypothesis** → hot parsing path copy dữ liệu quá nhiều.

**Diagnosis** → đo allocation per operation trước khi tối ưu.

**Fix** → dùng slicing/Span ở nơi lifetime đơn giản; không ép Span vào mọi layer.

**Verification** → benchmark lại allocations, throughput và p95 latency.

## 7. Common mistakes

* Dùng `Span<T>` ở code không nằm trên hot path rồi làm code khó đọc vô ích.
* Cố giữ `Span<T>` qua `await`.
* Dùng `Memory<T>` nhưng cuối cùng vẫn gọi `.ToArray()` ở mỗi layer.
* Tối ưu allocation trước khi profiler chứng minh allocation là bottleneck.

## 8. Alternatives

* `ArraySegment<T>`: cũ hơn, vẫn hữu ích nhưng API kém ergonomic hơn.
* `Memory<T>`: phù hợp khi cần async/lifetime dài hơn.
* Array/string bình thường: thường là lựa chọn tốt nhất nếu code không performance-sensitive.

## 9. Trade-offs

### Advantages

* Giảm copy và allocation.
* Tốt cho parsers, protocol handling, serialization và hot paths.
* Có thể giảm GC pressure đáng kể.

### Costs / Risks

* Lifetime semantics phức tạp hơn.
* Không phù hợp để giữ state lâu dài.
* Dễ over-optimize và làm code khó bảo trì.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slicing không nhất thiết phải copy dữ liệu.

### Middle

Biết khi nào dùng `Span<T>` và khi nào chuyển sang `Memory<T>`.

### Senior

Đánh giá allocation cost bằng profiler, không áp dụng zero-copy máy móc.

### Technical Lead / Architect

Xác định hot paths nào xứng đáng nhận complexity này và giữ API boundary đơn giản ở phần còn lại của hệ thống.

## 11. Key takeaway

* `Span<T>` phù hợp synchronous, short-lived memory views.
* `Memory<T>` phù hợp khi dữ liệu cần đi qua async boundary.
* Zero-copy chỉ đáng giá khi measurement cho thấy allocation/copy thực sự là bottleneck.

# 2. ASP.NET Core `ProblemDetails`: biến error response thành API contract ổn định thay vì mỗi endpoint trả một kiểu lỗi

## 1. What is it?

`ProblemDetails` là representation chuẩn cho HTTP API errors, thường dựa trên RFC 7807/9457-style problem details.

Mental model:

```text
Failure
  ↓
Exception / validation / domain conflict
  ↓
central error mapping
  ↓
ProblemDetails contract
  ↓
Client handles predictable structure
```

Thay vì endpoint A trả string, endpoint B trả `{ error }`, endpoint C trả HTML, API có một error envelope nhất quán.

## 2. Why does it exist?

Client-side error handling trở nên brittle nếu mỗi endpoint tự phát minh contract lỗi.

Ví dụ:

```json
"Something went wrong"
```

không cho client biết:

* failure category là gì
* có retry được không
* field nào invalid
* correlation ID nào dùng để support
* contract có ổn định qua versions không

`ProblemDetails` tồn tại để biến lỗi thành một phần rõ ràng của API contract.

## 3. How does it work?

ASP.NET Core có thể centralize exception handling và mapping:

```text
DomainValidationException -> 400
ResourceNotFoundException -> 404
ConcurrencyException      -> 409
Unexpected exception      -> 500
```

Response có các fields chuẩn như:

```json
{
  "type": "https://api.example.com/problems/order-conflict",
  "title": "Order update conflict",
  "status": 409,
  "detail": "The order was changed by another user.",
  "instance": "/orders/123"
}
```

Extensions có thể chứa `traceId`, error code hoặc validation details.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();

app.UseExceptionHandler();
app.UseStatusCodePages();
```

Với custom exception mapping:

```csharp
public sealed class ConflictExceptionHandler : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext context,
        Exception exception,
        CancellationToken ct)
    {
        if (exception is not OrderConcurrencyException)
            return false;

        context.Response.StatusCode = StatusCodes.Status409Conflict;

        await context.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Status = 409,
            Title = "Order update conflict",
            Type = "https://api.example.com/problems/order-conflict"
        }, ct);

        return true;
    }
}
```

Client nên branch theo stable machine-readable code/type, không branch theo human-readable `detail`.

## 5. Real production scenario

Mobile app và web app dùng cùng API. Backend thay text thông báo lỗi để dễ hiểu hơn.

Nếu frontend đang kiểm tra:

```ts
if (error.message === 'Order already exists')
```

thì UI có thể vỡ chỉ vì wording đổi.

Stable problem `type` hoặc error code tránh coupling này.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend hiển thị generic “Unknown error” cho một số endpoints.

**Evidence** → Network tab cho thấy có endpoint trả plain text, endpoint khác trả `ProblemDetails`.

**Hypothesis** → error mapping không đi qua centralized pipeline.

**Diagnosis** → endpoint tự catch exception và trả custom anonymous objects.

**Fix** → chuẩn hóa error taxonomy và central handling.

**Verification** → contract tests kiểm tra status + `type` + expected extensions.

## 7. Common mistakes

* Trả stack trace hoặc internal exception message trong `detail`.
* Dùng 200 OK với payload `{ success: false }` cho business/API error thông thường.
* Mọi exception đều map thành 500.
* Client parse `title`/`detail` thay vì stable code.
* Thay đổi error code mà không coi đó là breaking contract.

## 8. Alternatives

Custom error envelope có thể hợp lệ nếu toàn organization đã chuẩn hóa. Tuy nhiên `ProblemDetails` giảm nhu cầu tự phát minh schema và tương thích tốt với HTTP semantics.

## 9. Trade-offs

### Advantages

* Error contract nhất quán.
* Client dễ xử lý và test.
* Có chỗ rõ ràng cho trace/correlation metadata.

### Costs / Risks

* Cần error taxonomy có kỷ luật.
* Dễ leak internal details nếu mapping cẩu thả.
* Không thay thế domain-specific error design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP status và error body phục vụ hai mục đích bổ sung nhau.

### Middle

Biết centralize exception mapping và validation errors.

### Senior

Thiết kế stable error codes, retry semantics và không leak sensitive data.

### Technical Lead / Architect

Định nghĩa error contract dùng xuyên services/clients và quản lý backward compatibility như một public API surface.

## 11. Key takeaway

* Error response cũng là API contract.
* Client nên phụ thuộc stable machine-readable semantics, không phụ thuộc text.
* Central error mapping giảm inconsistency và giúp observability tốt hơn.

# 3. EF Core execution strategy + transaction: retry transient failure mà không vô tình chạy lại business side effect

## 1. What is it?

EF Core execution strategy có thể retry database operations khi gặp transient failures như temporary network interruption hoặc cloud database failover.

Mental model:

```text
Operation attempt
   ↓ transient failure
ExecutionStrategy
   ↓ retry
Operation attempt again
```

Điểm nguy hiểm: retry database operation không có nghĩa toàn bộ business workflow đều an toàn để chạy lại.

## 2. Why does it exist?

Cloud databases có transient failures bình thường: connection reset, failover, throttling, short outage.

Nếu application fail ngay lần đầu, availability giảm không cần thiết. Retry có thể che được transient faults.

Nhưng nếu transaction chứa cả database write lẫn side effect ngoài database, retry có thể nhân đôi side effect.

## 3. How does it work?

Một execution strategy wraps delegate và có thể gọi delegate nhiều lần.

Với explicit transaction, transaction thường phải nằm **bên trong** execution strategy delegate để toàn transaction có thể retry như một unit.

```text
ExecuteAsync(delegate)
  └─ BeginTransaction
      ├─ DB write A
      ├─ DB write B
      └─ Commit
```

Nếu delegate còn gửi email/payment request, retry có thể gửi lại.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    var order = await db.Orders.SingleAsync(x => x.Id == orderId, ct);
    order.MarkApproved();

    db.OutboxMessages.Add(OutboxMessage.For(new OrderApproved(order.Id)));

    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
});
```

Email/message publish không xảy ra trực tiếp trong retried transaction. Outbox worker thực hiện side effect sau đó.

## 5. Real production scenario

Checkout service cập nhật payment status rồi gọi email provider. Database commit thành công nhưng connection acknowledgement bị mất. Execution strategy retry toàn delegate.

Nếu email send nằm trong delegate, customer có thể nhận hai emails hoặc tệ hơn là payment API bị gọi hai lần.

## 6. Failure scenario & troubleshooting

**Symptom** → side effect trùng xuất hiện đúng lúc Azure SQL có transient connectivity issue.

**Evidence** → logs cho thấy cùng operation ID chạy nhiều attempts.

**Hypothesis** → retried delegate chứa non-idempotent side effect.

**Diagnosis** → trace execution strategy scope và external calls.

**Fix** → giữ transaction deterministic; external work đi qua Outbox/idempotency key.

**Verification** → fault injection database transient failure; side effect cuối cùng vẫn chỉ xảy ra một lần về business semantics.

## 7. Common mistakes

* Retry mọi exception.
* Bọc explicit transaction bên ngoài execution strategy.
* Gửi email/message/payment trực tiếp trong retry delegate.
* Nghĩ retry đồng nghĩa exactly-once.
* Không giới hạn retry budget, gây latency amplification.

## 8. Alternatives

* Không retry: phù hợp local/on-prem stable DB hoặc non-transient failures.
* Polly ở application layer: hữu ích nhưng cần phân biệt database resilience và business workflow resilience.
* Outbox Pattern: giải quyết atomic handoff giữa DB state và messaging.

## 9. Trade-offs

### Advantages

* Tăng resilience trước transient database faults.
* Giảm user-visible failures do sự cố ngắn.

### Costs / Risks

* Latency dài hơn khi retry.
* Duplicate side effects nếu workflow không idempotent.
* Debug phức tạp hơn vì một logical operation có nhiều attempts.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transient failure có thể đáng retry.

### Middle

Biết cấu hình execution strategy và transaction đúng scope.

### Senior

Nhận diện retry boundary, idempotency và commit ambiguity.

### Technical Lead / Architect

Thiết kế consistency model giữa database và external side effects thay vì coi retry là “resilience switch”.

## 11. Key takeaway

* Retry chỉ an toàn khi operation có semantics lặp lại được.
* Database transaction không bao phủ external side effects.
* Execution strategy nên kết hợp với idempotency/Outbox khi workflow vượt ra ngoài DB.

# 4. SQL Server deadlock graph: đọc victim, resource, lock order và sửa root cause thay vì chỉ retry

## 1. What is it?

Deadlock xảy ra khi hai hoặc nhiều transactions giữ resources mà transaction khác cần, tạo vòng chờ không thể tự giải quyết.

```text
Tx A giữ Row 1, chờ Row 2
Tx B giữ Row 2, chờ Row 1
```

SQL Server phát hiện cycle và chọn một transaction làm deadlock victim để rollback.

## 2. Why does it exist?

Locking là cần thiết để đảm bảo isolation/correctness. Nhưng khi application truy cập resources theo thứ tự không nhất quán, lock dependency có thể tạo cycle.

Deadlock không có nghĩa database “hỏng”; thường là interaction giữa transaction boundaries, access order, indexes và workload concurrency.

## 3. How does it work?

Deadlock graph cho biết:

* processes/sessions
* SQL statements đang chạy
* resources đang giữ/chờ
* lock modes
* victim process

Senior investigation không dừng ở câu “query nào bị kill?”, mà phải tìm cycle:

```text
Session A -> waits for resource owned by B
Session B -> waits for resource owned by A
```

## 4. Practical implementation

Ví dụ hai flows cập nhật theo thứ tự khác nhau:

```sql
-- Flow A
BEGIN TRAN;
UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1;
UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 2;
COMMIT;
```

```sql
-- Flow B
BEGIN TRAN;
UPDATE Accounts SET Balance = Balance - 50 WHERE Id = 2;
UPDATE Accounts SET Balance = Balance + 50 WHERE Id = 1;
COMMIT;
```

Một fix mạnh là chuẩn hóa lock order: luôn xử lý account ID nhỏ trước ID lớn.

## 5. Real production scenario

Payment reconciliation job và user transfer API cùng update `Accounts` + `LedgerEntries` nhưng theo thứ tự khác nhau.

Peak traffic làm deadlocks tăng. API retry khiến symptom giảm nhưng database vẫn tiêu tốn work và tail latency tăng.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL error 1205 tăng đột biến; p99 API cao nhưng CPU database chưa đầy.

**Evidence** → Extended Events deadlock graph cho thấy hai stored procedures khóa cùng resources theo thứ tự ngược nhau.

**Hypothesis** → inconsistent access order.

**Diagnosis** → map resource IDs/index keys về table/index và đối chiếu transaction logic.

**Fix** → chuẩn hóa access order, rút ngắn transaction, cải thiện index để giảm lock footprint khi phù hợp.

**Verification** → chạy concurrency load test; deadlock count về baseline gần 0.

## 7. Common mistakes

* Chỉ thêm retry rồi đóng incident.
* Dùng `NOLOCK` để “giải deadlock”.
* Tăng transaction scope không cần thiết.
* Không đọc deadlock graph.
* Thêm index máy móc mà không hiểu resource cycle.

## 8. Alternatives

* Optimistic concurrency: giảm một số contention patterns nhưng không thay thế mọi transaction need.
* Snapshot-based isolation: có thể giảm reader-writer blocking nhưng writer conflicts vẫn tồn tại.
* Queue/serialization: phù hợp khi business operation thực sự cần single-writer semantics.

## 9. Trade-offs

### Advantages

* Locking giữ correctness mạnh.
* Deadlock detector tự phá cycle thay vì treo vô hạn.

### Costs / Risks

* Transaction bị rollback cần retry/UX handling.
* High concurrency làm rare lock-order bugs xuất hiện rõ.
* Retry không sửa root cause.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deadlock là vòng chờ, khác với blocking thông thường.

### Middle

Biết đọc deadlock victim và transaction SQL.

### Senior

Phân tích resource cycle, index/access pattern và transaction scope.

### Technical Lead / Architect

Định nghĩa concurrency strategy và lock-order invariants cho critical workflows thay vì xử lý từng deadlock như lỗi ngẫu nhiên.

## 11. Key takeaway

* Deadlock là dependency cycle giữa locks.
* Deadlock graph là evidence chính để điều tra.
* Retry là safety net; root cause thường nằm ở access order, transaction scope hoặc lock footprint.

# 5. Cosmos DB partition key + hot partition: partitioning quyết định scalability, RU efficiency và cả data-model boundary

## 1. What is it?

Cosmos DB phân phối dữ liệu theo partition key. Logical partition chứa các items có cùng partition-key value; physical partitions chịu trách nhiệm lưu và phục vụ nhiều logical partitions.

Mental model:

```text
/items
  tenant=A ─┐
  tenant=B ─┼─ hash(partition key) -> physical partitions
  tenant=C ─┘
```

Partition key không chỉ là index field. Nó quyết định data locality, throughput distribution và transaction boundary.

## 2. Why does it exist?

Một distributed database không thể scale chỉ bằng cách “thêm server” nếu mọi request vẫn phải chạm cùng một node.

Partitioning chia dữ liệu/workload để capacity có thể phân phối ngang.

Nếu partition key tệ, toàn bộ throughput có thể dồn vào một vùng dù tổng RU/s còn dư.

## 3. How does it work?

Queries có partition key cụ thể có thể route tới đúng partition:

```text
GET orders WHERE tenantId = 'A'
        ↓
known partition
```

Cross-partition query phải fan out nhiều nơi hơn và thường tốn RU/latency hơn.

Hot partition xuất hiện khi một partition key value nhận phần lớn reads/writes, ví dụ dùng `Country = VN` cho hệ thống mà 90% users ở Việt Nam.

## 4. Practical implementation

Model multi-tenant thường cân nhắc:

```json
{
  "id": "order-123",
  "tenantId": "tenant-42",
  "status": "Pending",
  "total": 120.5
}
```

Container partition key:

```text
/tenantId
```

Query:

```csharp
var response = await container.ReadItemAsync<Order>(
    id,
    new PartitionKey(tenantId),
    cancellationToken: ct);
```

Đây là point read hiệu quả hơn query không biết partition key.

## 5. Real production scenario

Notification platform partition theo `NotificationType`. 80% traffic là `Email`, nên một logical partition trở thành hotspot.

Thêm RU/s không tăng throughput tương ứng vì một physical partition vẫn bị giới hạn. Data model phải thay đổi, ví dụ partition theo tenant/user/bucket phù hợp access pattern.

## 6. Failure scenario & troubleshooting

**Symptom** → 429 throttling xuất hiện dù overall RU utilization dashboard chỉ khoảng 60%.

**Evidence** → metrics cho thấy một partition-key range tiêu thụ gần capacity trong khi ranges khác nhàn.

**Hypothesis** → hot partition.

**Diagnosis** → phân tích top partition keys, access frequency và request charge.

**Fix** → redesign partition key hoặc workload sharding; không chỉ tăng RU blindly.

**Verification** → throughput phân bố đều hơn và 429 rate giảm.

## 7. Common mistakes

* Chọn partition key chỉ vì field có mặt ở mọi document.
* Chọn key cardinality thấp.
* Bỏ qua growth distribution theo thời gian.
* Cross-partition query cho mọi request rồi mới tối ưu sau.
* Nghĩ Cosmos DB transaction giống relational transaction toàn container.

## 8. Alternatives

* SQL Server/PostgreSQL: tốt khi relational consistency, joins và transactional model quan trọng hơn horizontal distribution.
* MongoDB: cũng có sharding nhưng operational/data-model semantics khác.
* Cosmos DB: mạnh khi cần globally distributed low-latency access với model phù hợp partitioning.

## 9. Trade-offs

### Advantages

* Horizontal scale và global distribution.
* Point reads hiệu quả khi key tốt.
* Data locality rõ.

### Costs / Risks

* Partition key khó thay đổi về sau.
* Cross-partition queries tốn hơn.
* Hot partition có thể giới hạn toàn workload path.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định dữ liệu nằm ở đâu.

### Middle

Biết thiết kế point reads và query theo key.

### Senior

Đọc RU, 429, distribution metrics và nhận diện hotspot.

### Technical Lead / Architect

Chọn partition key dựa trên access pattern, tenant growth, transaction boundary và future scale chứ không chỉ schema hiện tại.

## 11. Key takeaway

* Partition key là architectural decision, không phải tuning detail.
* Hot partition có thể xảy ra dù tổng RU chưa dùng hết.
* Data model của distributed database phải xuất phát từ access pattern.

# 6. Hexagonal Architecture + Anti-Corruption Layer: cô lập third-party APIs khỏi domain thay vì để external contract lan khắp codebase

## 1. What is it?

Hexagonal Architecture tổ chức application quanh domain/application core và các ports/adapters.

```text
External CRM
    ↓ adapter
[ CRM Port ]
    ↓
Application / Domain
    ↑
[ Persistence Port ]
    ↑ adapter
Database
```

Anti-Corruption Layer (ACL) dịch external model sang model mà hệ thống của mình hiểu, ngăn external semantics xâm nhập domain.

## 2. Why does it exist?

Third-party API thường có naming, status values, pagination, errors và lifecycle khác domain nội bộ.

Nếu controller/service khắp nơi dùng trực tiếp vendor DTO:

```csharp
VendorCustomerDto
VendorOrderStatus
VendorAddress
```

thì đổi vendor hoặc vendor contract change trở thành repo-wide migration.

ACL tạo boundary cho change.

## 3. How does it work?

Application depend vào port:

```csharp
public interface ICustomerRiskProvider
{
    Task<RiskAssessment> AssessAsync(Customer customer, CancellationToken ct);
}
```

Adapter biết external API:

```text
Domain Customer
   ↓ map
Vendor request
   ↓ remote API
Vendor response
   ↓ translate
Domain RiskAssessment
```

Domain không biết vendor response codes hoặc JSON shape.

## 4. Practical implementation

```csharp
public sealed class VendorRiskAdapter : ICustomerRiskProvider
{
    private readonly VendorRiskClient _client;

    public async Task<RiskAssessment> AssessAsync(
        Customer customer,
        CancellationToken ct)
    {
        var response = await _client.CheckAsync(new VendorRiskRequest
        {
            ExternalCustomerId = customer.Id.ToString(),
            CountryCode = customer.CountryCode
        }, ct);

        return response.Code switch
        {
            "LOW" => RiskAssessment.Low,
            "MED" => RiskAssessment.Medium,
            "HIGH" => RiskAssessment.High,
            _ => RiskAssessment.Unknown
        };
    }
}
```

Translation policy nằm ở adapter, không nằm rải rác trong use cases.

## 5. Real production scenario

E-commerce tích hợp review provider. Vendor đổi field `rating` từ integer 1–5 sang decimal 0–10.

Nếu domain dùng trực tiếp vendor DTO, hàng chục components/services bị ảnh hưởng. Nếu có ACL, chỉ adapter và contract tests cần cập nhật, còn domain vẫn giữ rating semantics nội bộ.

## 6. Failure scenario & troubleshooting

**Symptom** → vendor thêm status mới và application bắt đầu throw `ArgumentOutOfRangeException` ở nhiều nơi.

**Evidence** → external enum được deserialize thẳng vào internal enum.

**Hypothesis** → external contract đã leak qua boundary.

**Diagnosis** → search code cho vendor DTO/enum xuất hiện ngoài Infrastructure/Integration module.

**Fix** → translate unknown/unsupported states trong ACL và dùng internal model.

**Verification** → contract tests replay payload vendor cũ/mới; application core không đổi.

## 7. Common mistakes

* Tạo interface cho mọi class rồi gọi đó là Hexagonal Architecture.
* ACL chỉ copy DTO 1:1 không hề translate semantics.
* Vendor SDK type xuất hiện trong domain assembly.
* Overengineer ports/adapters cho CRUD app nhỏ không có volatile integrations.

## 8. Alternatives

* Direct integration trong application service: đủ tốt nếu integration đơn giản, ít thay đổi và không ảnh hưởng domain.
* Dedicated integration module/ACL: phù hợp external contract phức tạp hoặc high-change.
* Separate microservice: chỉ nên dùng nếu cần independent ownership/deployment thật sự.

## 9. Trade-offs

### Advantages

* Change isolation tốt.
* Domain language sạch hơn.
* Dễ test failure/translation logic.

### Costs / Risks

* Nhiều mapping code.
* Thêm abstraction nếu integration quá nhỏ.
* Có nguy cơ tạo generic ports không phản ánh business meaning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external model không nhất thiết là domain model.

### Middle

Biết tạo adapter và mapping rõ ràng.

### Senior

Thiết kế boundary dựa trên volatility, ownership và failure semantics.

### Technical Lead / Architect

Quyết định integration nào cần ACL, module riêng hoặc service riêng; tránh cả coupling lẫn abstraction ceremony vô ích.

## 11. Key takeaway

* ACL bảo vệ domain khỏi external semantics.
* Hexagonal Architecture nói về dependency direction và boundaries, không phải folder layout.
* Chỉ thêm abstraction khi volatility/complexity thực sự biện minh cho chi phí.

# 7. Azure App Service deployment slots + database schema evolution: zero-downtime deployment chỉ an toàn khi app versions tương thích cùng schema

## 1. What is it?

Deployment slots cho phép deploy version mới vào slot khác, warm-up/validate rồi swap vào Production.

```text
Production slot -> v1
Staging slot    -> v2
       ↓ validate
      swap
Production slot -> v2
```

Nhưng slot swap không tự giải quyết database compatibility. Trong thời gian deployment, v1 và v2 có thể cùng truy cập một database schema.

## 2. Why does it exist?

Deploy trực tiếp lên Production có startup risk, cold start và rollback chậm.

Slot giúp validate application process trước khi nhận traffic thật. Tuy nhiên nếu v2 migration xóa/rename column mà v1 vẫn cần, deployment vẫn có downtime dù slot swap hoàn hảo.

## 3. How does it work?

Zero-downtime schema change thường dùng expand-contract:

```text
Phase 1: add new schema, giữ old schema
Phase 2: deploy app đọc/ghi compatible
Phase 3: backfill data
Phase 4: migrate consumers
Phase 5: remove old schema sau
```

Không nên:

```text
DROP old column
↓
then deploy app that no longer uses it
```

vì old instances có thể vẫn chạy trong transition/rollback.

## 4. Practical implementation

Ví dụ đổi `FullName` thành `FirstName` + `LastName`:

Migration 1:

```sql
ALTER TABLE Customers ADD FirstName nvarchar(100) NULL;
ALTER TABLE Customers ADD LastName nvarchar(100) NULL;
```

Version mới tạm thời hỗ trợ cả old/new representation. Sau khi backfill và xác nhận mọi consumers đã chuyển, migration sau mới drop `FullName`.

CI/CD flow:

```text
build -> test -> deploy staging -> health check -> schema compatibility check -> swap -> monitor
```

## 5. Real production scenario

App Service v2 deploy vào Staging thành công. Health check pass. Migration trước swap rename column `Status` thành `OrderStatus`.

Production v1 vẫn đang nhận traffic và bắt đầu trả 500 vì column cũ biến mất. Slot feature không thể cứu lỗi schema incompatibility này.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment pipeline báo success nhưng Production v1 bắt đầu 500 trước khi swap.

**Evidence** → SQL errors `Invalid column name` xuất hiện ngay sau migration.

**Hypothesis** → migration breaking được apply trước khi toàn fleet compatible.

**Diagnosis** → compare SQL generated bởi v1/v2 với schema hiện tại.

**Fix** → rollback schema nếu an toàn hoặc forward-fix bằng restoring compatible columns/views; áp dụng expand-contract cho lần sau.

**Verification** → chạy v1 và v2 integration tests cùng schema intermediate.

## 7. Common mistakes

* Đồng nhất “slot swap” với zero downtime hoàn chỉnh.
* Auto-run destructive migrations khi startup.
* Không test rollback compatibility.
* Slot settings/secrets cấu hình nhầm giữa Staging và Production.
* Chỉ health-check `/health` mà không kiểm tra dependency critical path.

## 8. Alternatives

* Blue-Green ở infrastructure khác: cùng nguyên lý compatibility.
* Rolling deployment: cần app/schema backward compatibility tương tự.
* Maintenance window: đôi khi đơn giản và phù hợp hơn cho hệ thống internal nhỏ.

## 9. Trade-offs

### Advantages

* Warm-up trước Production.
* Rollback app version nhanh hơn.
* Giảm cold-start deployment risk.

### Costs / Risks

* Có thêm slot configuration/cost.
* Database vẫn là shared state khó rollback.
* Expand-contract cần nhiều deployment phases hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slot là parallel application environment, không phải parallel database mặc định.

### Middle

Biết deploy, warm-up, swap và quản lý slot settings.

### Senior

Thiết kế backward-compatible migrations và rollback plan.

### Technical Lead / Architect

Định nghĩa release contract giữa application versions, database schema và external consumers; chọn zero-downtime chỉ khi business thực sự cần.

## 11. Key takeaway

* Zero-downtime deployment là compatibility problem, không chỉ deployment-tool problem.
* Schema change phải hỗ trợ coexistence của old/new app versions.
* Expand-contract là kỹ thuật cốt lõi cho safe rolling/slot deployments.

# 8. Redis cache stampede + single-flight: khi một cache miss nhỏ biến thành hàng nghìn database queries đồng thời

## 1. What is it?

Cache stampede xảy ra khi nhiều requests cùng miss một hot cache key và đồng thời quay về database/external dependency để regenerate cùng dữ liệu.

```text
1000 requests
     ↓
cache key expired
     ↓
1000 cache misses
     ↓
1000 DB queries
```

Single-flight là cơ chế để một request thực hiện regeneration còn requests khác chờ hoặc dùng stale value.

## 2. Why does it exist?

Cache giúp giảm load khi hit. Nhưng TTL đồng bộ trên hot key tạo cliff: đúng lúc key hết hạn, load quay lại origin theo concurrency thực tế.

Nếu origin chỉ chịu được 200 QPS còn cache đang che 5000 QPS, một expiration có thể làm origin sập.

## 3. How does it work?

Một local single-flight có thể dùng keyed semaphore. Trong distributed environment, mỗi instance vẫn có thể regenerate một lần, nên cần cân nhắc distributed lock hoặc stale-while-revalidate semantics.

Flow:

```text
MISS
 ↓
Acquire regeneration ownership?
 ├─ yes -> load DB -> SET cache -> release
 └─ no  -> wait / serve stale
```

Lock TTL phải có giới hạn để không tạo deadlock nếu owner crash.

## 4. Practical implementation

Đơn giản trong một process:

```csharp
private static readonly ConcurrentDictionary<string, SemaphoreSlim> Gates = new();

public async Task<Product?> GetProductAsync(string id, CancellationToken ct)
{
    var key = $"product:{id}";
    var cached = await _cache.GetStringAsync(key, ct);
    if (cached is not null)
        return JsonSerializer.Deserialize<Product>(cached);

    var gate = Gates.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
    await gate.WaitAsync(ct);

    try
    {
        cached = await _cache.GetStringAsync(key, ct);
        if (cached is not null)
            return JsonSerializer.Deserialize<Product>(cached);

        var product = await _db.Products.FindAsync([id], ct);
        if (product is not null)
            await _cache.SetStringAsync(key, JsonSerializer.Serialize(product), ct);

        return product;
    }
    finally
    {
        gate.Release();
    }
}
```

Double-check sau khi acquire gate là cần thiết vì request khác có thể đã populate cache.

## 5. Real production scenario

Homepage có “top products” key TTL 5 phút. Traffic 3000 RPS. Mỗi 5 phút, SQL CPU spike đúng lúc key expire và p99 latency tăng mạnh.

Root cause không phải SQL query tự nhiên chậm; cache expiration đã đồng bộ hàng nghìn misses.

## 6. Failure scenario & troubleshooting

**Symptom** → database CPU spike theo chu kỳ TTL.

**Evidence** → Redis miss rate tăng đột ngột cùng thời điểm query count tăng hàng nghìn lần.

**Hypothesis** → stampede trên hot keys.

**Diagnosis** → correlate cache key TTL/miss metrics với dependency load.

**Fix** → single-flight, jitter TTL, stale-while-revalidate hoặc proactive refresh.

**Verification** → cache expiration test dưới load; origin QPS không còn spike theo request concurrency.

## 7. Common mistakes

* Dùng cùng TTL chính xác cho hàng nghìn keys.
* Distributed lock không có expiry.
* Mọi request chờ lock quá lâu và tạo latency queue.
* Cache failures được retry vô hạn rồi tạo retry storm.
* Cache dữ liệu correctness-critical mà không chấp nhận stale semantics rõ ràng.

## 8. Alternatives

* TTL jitter: giảm synchronized expiration.
* Stale-while-revalidate: ưu tiên availability/latency nếu stale data chấp nhận được.
* Proactive refresh: phù hợp very-hot predictable keys.
* Không cache: đôi khi DB đã đủ nhanh và complexity không đáng.

## 9. Trade-offs

### Advantages

* Bảo vệ origin khi hot key hết hạn.
* Giảm tail latency spikes.
* Tăng cache effectiveness thực tế.

### Costs / Risks

* Coordination complexity.
* Lock path có thể thành bottleneck mới.
* Stale serving cần business acceptance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss dưới concurrency khác hoàn toàn một cache miss đơn lẻ.

### Middle

Biết double-check + keyed synchronization.

### Senior

Thiết kế TTL jitter, stale policy và Redis failure behavior.

### Technical Lead / Architect

Quyết định cache có đáng tồn tại hay không, freshness SLA là gì và coordination nên local hay distributed.

## 11. Key takeaway

* Hot-key expiration có thể biến cache thành load amplifier.
* Single-flight giảm duplicate regeneration nhưng cần timeout/failure policy.
* TTL/freshness là một phần của system design, không chỉ config value.

# 9. IIS Application Pool recycle + graceful shutdown: vì sao process restart “bình thường” vẫn có thể làm mất background work và request đang chạy

## 1. What is it?

IIS Application Pool chạy ASP.NET application trong worker process (`w3wp.exe`). Recycle thay worker process cũ bằng process mới theo trigger như schedule, configuration change, memory condition hoặc manual action.

Mental model:

```text
IIS
 ├─ old w3wp -> draining/stopping
 └─ new w3wp -> starting/receiving traffic
```

Recycle là lifecycle event bình thường, không nên được coi là exception hiếm.

## 2. Why does it exist?

Worker process cần có khả năng restart để:

* apply deployment/configuration
* recover khỏi unhealthy state
* enforce operational policies
* recycle long-lived process resources

Nhưng application phải thiết kế để process có thể biến mất. In-process memory không phải durable storage.

## 3. How does it work?

Khi shutdown bắt đầu, ASP.NET Core host nhận cancellation signal thông qua application lifetime.

`BackgroundService.ExecuteAsync` nhận `stoppingToken`. Service cần stop nhận work mới và hoàn tất/abandon work hiện tại trong graceful window.

Nếu task không tôn trọng cancellation hoặc mất quá lâu, process có thể bị terminate.

## 4. Practical implementation

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var message = await _queue.ReceiveAsync(stoppingToken);

            try
            {
                await ProcessAsync(message, stoppingToken);
                await _queue.CompleteAsync(message, stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                // Không complete message; cho phép broker redeliver.
                break;
            }
        }
    }
}
```

Work cần durable queue để process restart không làm mất job.

## 5. Real production scenario

Legacy enterprise app chạy nightly import bằng in-memory timer trong IIS. Deployment recycle xảy ra khi import đang xử lý file 40 phút.

Process cũ chết giữa chừng; timer state mất và job không được resume. Không có durable checkpoint nên dữ liệu chỉ import một phần.

## 6. Failure scenario & troubleshooting

**Symptom** → background jobs thỉnh thoảng dừng giữa chừng quanh deployment hoặc recycle window.

**Evidence** → IIS event logs/process startup timestamps trùng với job interruption.

**Hypothesis** → in-process background work không resilient với lifecycle restart.

**Diagnosis** → kiểm tra shutdown logs, cancellation handling và durable queue/checkpoint state.

**Fix** → đưa critical work vào durable queue/Worker Service/Azure Functions hoặc thiết kế checkpoint + idempotency.

**Verification** → chủ động recycle process trong integration/staging test và xác nhận work được resume/redeliver đúng.

## 7. Common mistakes

* Giả định IIS process chạy mãi.
* Dùng `Timer` cho critical job nhưng không persistence.
* Ignore `CancellationToken`.
* Giữ singleton in-memory state như source of truth.
* Tăng shutdown timeout vô hạn thay vì sửa work lifecycle.

## 8. Alternatives

* Windows Service/Worker Service: tách background workload khỏi web process.
* Azure Functions: tốt cho event/scheduled work nếu phù hợp cloud model.
* Durable queue + multiple consumers: resilient và scale tốt hơn.
* In-process `BackgroundService`: vẫn ổn cho non-critical hoặc retryable lightweight work.

## 9. Trade-offs

### Advantages

* IIS recycle hỗ trợ maintainability và recovery.
* In-process background work đơn giản, ít infrastructure.

### Costs / Risks

* Web process lifecycle không phù hợp long-running critical jobs.
* Restart có thể mất memory state.
* Tách worker thêm deployment/monitoring component.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu web process có thể restart bất kỳ lúc nào.

### Middle

Biết dùng cancellation và graceful shutdown.

### Senior

Thiết kế idempotency, checkpoint và durable handoff.

### Technical Lead / Architect

Quyết định workload nào có thể ở in-process và workload nào phải tách thành durable background-processing architecture.

## 11. Key takeaway

* Process lifetime không phải business-work lifetime.
* Critical background work cần durable state và restart-safe semantics.
* Recycle phải được test như một production failure mode bình thường.

# 10. Git bisect + observability: khoanh vùng production regression bằng evidence thay vì đọc hàng trăm commits thủ công

## 1. What is it?

`git bisect` dùng binary search để tìm commit đầu tiên gây regression giữa một commit known-good và một commit known-bad.

Mental model:

```text
good ----------------------------- bad
                ↑ test middle
         good?        bad?
          ↓             ↓
      discard half   discard half
```

Thay vì kiểm tra 128 commits tuần tự, binary search chỉ cần khoảng 7 checks nếu test signal đáng tin cậy.

## 2. Why does it exist?

Production regressions thường xuất hiện sau nhiều merges. Human code review không hiệu quả để xác định commit gây lỗi nếu symptom chỉ xuất hiện khi chạy.

`git bisect` chuyển câu hỏi từ “commit nào trông đáng nghi?” sang “build nào thực sự có symptom?”.

## 3. How does it work?

Workflow:

```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-sha>
```

Git checkout commit giữa khoảng. Bạn chạy test hoặc reproduction script rồi mark:

```bash
git bisect good
# hoặc
git bisect bad
```

Lặp tới khi tìm first bad commit.

Có thể automate:

```bash
git bisect run ./scripts/regression-test.sh
```

Script trả exit code 0 cho good, non-zero cho bad.

## 4. Practical implementation

Giả sử regression là API p95 vượt 500 ms trong deterministic benchmark:

```bash
#!/usr/bin/env bash
set -e

dotnet test tests/PerformanceRegression.Tests \
  --filter FullyQualifiedName~SearchLatencyRegression
```

Sau đó:

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0
git bisect run ./scripts/regression-test.sh
```

Điều kiện quan trọng: test phải đủ deterministic để phân loại commit đúng.

## 5. Real production scenario

Sau release, Search API p95 tăng từ 180 ms lên 900 ms. Release chứa 70 commits.

Application Insights cho thấy dependency SQL time không đổi nhưng allocation/request tăng mạnh. Team tạo regression benchmark cho serialization path rồi dùng `git bisect` để tìm commit đổi DTO mapping khiến object graph lớn gấp nhiều lần.

## 6. Failure scenario & troubleshooting

**Symptom** → `git bisect` trả các kết quả khác nhau mỗi lần.

**Evidence** → cùng commit lúc pass lúc fail.

**Hypothesis** → reproduction signal flaky hoặc phụ thuộc environment/data.

**Diagnosis** → chạy test lặp lại cùng commit; kiểm tra external dependencies, warm-up, cache và test data.

**Fix** → làm reproduction deterministic hoặc dùng threshold/statistical rule hợp lý.

**Verification** → cùng commit luôn được phân loại ổn định trước khi tiếp tục bisect.

## 7. Common mistakes

* Chọn known-good commit chưa thực sự được xác nhận.
* Dùng flaky E2E test làm oracle.
* Bisect khi bug phụ thuộc migration/configuration ngoài Git history mà không tái tạo environment.
* Sau khi tìm commit thì revert ngay mà không hiểu root cause.
* Không kết hợp telemetry để thu hẹp symptom trước khi bisect.

## 8. Alternatives

* Manual commit inspection: phù hợp khoảng thay đổi rất nhỏ.
* Feature flags: có thể isolate behavior nhanh hơn nếu feature boundary rõ.
* Canary comparison: giúp xác định version regression trước khi code-level bisect.
* Profiling/tracing: cần để hiểu mechanism sau khi tìm commit.

## 9. Trade-offs

### Advantages

* Thu hẹp search space rất nhanh.
* Evidence-driven.
* Có thể automate hoàn toàn nếu regression test tốt.

### Costs / Risks

* Cần build/test historical commits.
* Migration/environment incompatibility có thể làm commits không test được.
* Chỉ tìm correlation với commit; vẫn cần root-cause analysis.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu binary search trên commit history.

### Middle

Biết xác định good/bad revisions và chạy bisect thủ công.

### Senior

Xây deterministic regression test từ production symptom và kết hợp telemetry/profiling.

### Technical Lead / Architect

Thiết kế release observability, artifact traceability và reproducible builds để incident có thể được thu hẹp nhanh thay vì phụ thuộc trí nhớ của team.

## 11. Key takeaway

* `git bisect` mạnh khi bạn có reliable good/bad signal.
* Observability giúp định nghĩa đúng regression trước khi tìm commit.
* Commit đầu tiên gây symptom là điểm bắt đầu root-cause analysis, không phải kết luận cuối cùng.
