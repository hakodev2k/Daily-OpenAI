# 1. C# `IAsyncDisposable` và `await using`: cleanup resource bất đồng bộ mà không block thread

## 1. What is it?

`IAsyncDisposable` là contract cho resource cần cleanup có thể phải thực hiện asynchronous I/O. Thay vì chỉ có:

```csharp
void Dispose();
```

nó cung cấp:

```csharp
ValueTask DisposeAsync();
```

và được sử dụng bằng `await using`.

Mental model:

```text
resource lifetime
    -> acquire
    -> use
    -> async cleanup / flush / close
    -> release
```

Điểm quan trọng: `IAsyncDisposable` không phải “phiên bản mới tốt hơn `IDisposable`”. Nó dành cho cleanup thực sự có asynchronous work.

## 2. Why does it exist?

Một số resource khi đóng cần gửi dữ liệu, flush buffer hoặc hoàn tất protocol qua network. Nếu cleanup đó bị ép chạy synchronous, thread có thể bị block chỉ để chờ I/O.

Ví dụ:

- asynchronous stream;
- database transaction/context có async cleanup;
- network writer cần flush;
- resource wrapper gọi remote close operation.

Trong high-throughput server, blocking cleanup có thể góp phần gây ThreadPool starvation.

## 3. How does it work?

Compiler biến:

```csharp
await using var resource = await CreateAsync();
```

thành lifetime tương đương `try/finally`, nhưng `finally` gọi `DisposeAsync()` và await nó.

```text
acquire
  -> try
       business work
     finally
       await DisposeAsync()
```

Cleanup vẫn chạy khi code throw exception, miễn là control flow thoát khỏi scope bình thường qua exception handling của runtime.

## 4. Practical implementation

EF Core transaction là ví dụ thực tế:

```csharp
await using var transaction =
    await db.Database.BeginTransactionAsync(ct);

try
{
    db.Orders.Add(order);
    await db.SaveChangesAsync(ct);

    await transaction.CommitAsync(ct);
}
catch
{
    await transaction.RollbackAsync(ct);
    throw;
}
```

Một custom resource có thể hỗ trợ cả hai contracts nếu cần:

```csharp
public sealed class AsyncWriter : IAsyncDisposable
{
    private readonly Stream _stream;

    public AsyncWriter(Stream stream) => _stream = stream;

    public async ValueTask DisposeAsync()
    {
        await _stream.FlushAsync();
        await _stream.DisposeAsync();
    }
}
```

## 5. Real production scenario

Một file-export service ghi dữ liệu vào compressed stream rồi upload ra Blob Storage. Code trả response trước khi asynchronous flush hoàn tất hoặc dùng synchronous dispose trên hot path. Dưới load lớn, request thread bị giữ lâu và p99 latency tăng.

Sử dụng đúng async lifetime giúp cleanup đi theo non-blocking path end-to-end.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng khi request kết thúc, ThreadPool queue length tăng dù business operation đã xong.

**Evidence** → profiler cho thấy synchronous `Dispose()` hoặc flush đang block trên I/O.

**Hypothesis** → resource hỗ trợ async cleanup nhưng caller dùng synchronous lifetime.

**Diagnosis** → inspect stack traces và resource lifetime; đo thời gian trước/sau scope dispose.

**Fix** → chuyển sang `await using` ở async call chain phù hợp; không gọi `.GetAwaiter().GetResult()` trên `DisposeAsync()`.

**Verification** → load test và so ThreadPool queue, request p95/p99, blocked-thread count.

## 7. Common mistakes

- Dùng `await using` cho object không có async cleanup chỉ vì trông “modern”.
- Gọi `DisposeAsync().AsTask().Wait()`.
- Quên dispose resource khi exception xảy ra.
- Giữ resource sống lâu hơn business scope cần thiết.
- Dùng async disposal để che resource ownership không rõ ràng.

## 8. Alternatives

`IDisposable` vẫn đúng cho resource chỉ release managed/native state synchronously. Một object có thể implement cả `IDisposable` và `IAsyncDisposable` nếu library cần support cả sync và async callers.

## 9. Trade-offs

### Advantages

- Non-blocking cleanup cho I/O-bound resource.
- Lifetime rõ ràng nhờ language syntax.
- Hỗ trợ exception-safe cleanup.

### Costs / Risks

- Async lifetime lan lên caller.
- API phức tạp hơn nếu support cả sync và async disposal.
- Không mang lợi ích nếu cleanup vốn synchronous.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dispose là ownership/lifetime, không chỉ “giải phóng memory”.

### Middle

Biết dùng `using` vs `await using` đúng resource và propagate async end-to-end.

### Senior

Nhận diện sync-over-async trong cleanup, đo ThreadPool impact và thiết kế resource lifetime nhỏ nhất hợp lý.

### Technical Lead / Architect

Quyết định library contract nào cần async disposal và tránh để infrastructure abstraction ép mọi consumer gánh complexity không cần thiết.

## 11. Key takeaway

- `IAsyncDisposable` chỉ có giá trị khi cleanup thực sự cần asynchronous work.
- `await using` giữ cleanup exception-safe mà không block thread.
- Resource ownership rõ ràng quan trọng hơn việc chọn syntax mới.

# 2. ASP.NET Core `ProblemDetails`: thiết kế error contract ổn định thay vì trả exception text tùy tiện

## 1. What is it?

`ProblemDetails` là cấu trúc chuẩn hóa HTTP error response, thường chứa các field như `type`, `title`, `status`, `detail`, `instance` và extension fields.

Mental model:

```text
internal failure
   -> classify
   -> map to public error contract
   -> HTTP status + ProblemDetails
```

Mục tiêu là tách internal exception model khỏi API contract mà client phụ thuộc.

## 2. Why does it exist?

Nếu mỗi endpoint tự trả error shape khác nhau:

```json
{ "error": "not found" }
```

```json
{ "message": "Validation failed", "code": 99 }
```

client phải viết parsing logic riêng cho từng API. Tệ hơn, trả `exception.ToString()` làm lộ stack trace, SQL, URL nội bộ hoặc sensitive data.

Một stable error contract cải thiện interoperability, observability và backward compatibility.

## 3. How does it work?

ASP.NET Core có thể map exception/validation failure sang ProblemDetails ở centralized boundary.

```text
Controller/Endpoint
  -> exception
  -> IExceptionHandler / middleware
  -> domain/infrastructure classification
  -> ProblemDetails
  -> client
```

HTTP status vẫn mang semantics chính. Error code extension nên dùng cho machine-readable business distinction khi status code chưa đủ.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();

app.UseExceptionHandler();
```

Handler:

```csharp
public sealed class GlobalExceptionHandler : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext context,
        Exception exception,
        CancellationToken ct)
    {
        var status = exception switch
        {
            NotFoundException => StatusCodes.Status404NotFound,
            ConflictException => StatusCodes.Status409Conflict,
            _ => StatusCodes.Status500InternalServerError
        };

        await Results.Problem(
            statusCode: status,
            title: status == 500 ? "Unexpected server error" : exception.Message,
            extensions: new Dictionary<string, object?>
            {
                ["traceId"] = context.TraceIdentifier
            })
            .ExecuteAsync(context);

        return true;
    }
}
```

Production `500` không nên expose raw exception detail.

## 5. Real production scenario

Mobile app, web frontend và partner integration cùng gọi một order API. Khi order state conflict, server trước đây trả lúc `400`, lúc `500`, body khác nhau theo endpoint.

Chuẩn hóa thành `409 Conflict` + stable `errorCode="ORDER_STATE_CONFLICT"` giúp client xử lý deterministic và support team correlate bằng `traceId`.

## 6. Failure scenario & troubleshooting

**Symptom** → client hiển thị generic “Something went wrong” vì không parse được response sau backend release.

**Evidence** → OpenAPI/contract diff cho thấy error shape hoặc status thay đổi.

**Hypothesis** → error contract bị xem như implementation detail.

**Diagnosis** → replay failing requests, inspect response body/status, compare supported client versions.

**Fix** → centralize mapping, contract-test error responses, giữ stable machine-readable codes.

**Verification** → integration tests cho validation, 404, conflict, unauthorized và 500.

## 7. Common mistakes

- Trả stack trace cho client.
- Dùng `200 OK` với `{ success:false }` cho mọi lỗi.
- Map mọi exception thành `400 Bad Request`.
- Đưa exception message thành stable error code.
- Mỗi controller tự tạo error JSON riêng.

## 8. Alternatives

Một organization có thể dùng custom envelope nếu ecosystem đã chuẩn hóa từ trước. Tuy nhiên HTTP status semantics vẫn nên được giữ. GraphQL có error model khác, nhưng vẫn cần stable machine-readable classification.

## 9. Trade-offs

### Advantages

- Error contract nhất quán.
- Giảm data leakage.
- Client code và support/debugging dễ hơn.

### Costs / Risks

- Cần taxonomy/error-code governance.
- Central handler quá lớn có thể trở thành switch statement khó maintain.
- Không nên che mất domain-specific semantics quan trọng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code và response body cùng tạo nên API contract.

### Middle

Implement centralized ProblemDetails mapping và tests.

### Senior

Phân loại validation, conflict, auth, dependency và unexpected failures đúng semantics; tránh leaking internals.

### Technical Lead / Architect

Định nghĩa error contract/versioning policy toàn platform, gồm correlation, client compatibility và observability ownership.

## 11. Key takeaway

- Error response là public contract, không phải nơi serialize exception.
- HTTP status + stable machine-readable code nên phản ánh semantics.
- Centralized mapping giúp consistency nhưng vẫn cần taxonomy có chủ đích.

# 3. EF Core `AsSplitQuery`: tránh cartesian explosion nhưng không vô tình tăng round trips và inconsistency

## 1. What is it?

Khi một EF Core query `Include` nhiều collection relationships, một single SQL query có thể tạo cartesian multiplication. `AsSplitQuery()` yêu cầu EF tách graph loading thành nhiều SQL queries rồi ghép kết quả phía client.

Ví dụ:

```text
Order
  -> 20 Items
  -> 10 Notes

single JOIN có thể tạo gần 20 x 10 = 200 rows cho cùng Order
```

## 2. Why does it exist?

Relational JOIN trả flat rows. Khi nhiều one-to-many collections được JOIN song song, parent và child data bị lặp lại rất nhiều. Điều này tăng:

- network payload;
- database I/O;
- materialization CPU;
- memory allocation.

Split query đổi duplication lấy thêm database round trips.

## 3. How does it work?

Single query:

```text
SELECT Order + Items + Notes
 -> one round trip
 -> potentially huge duplicated rowset
```

Split query:

```text
SELECT Orders
SELECT Items for selected Orders
SELECT Notes for selected Orders
 -> multiple result sets/round trips depending provider behavior
 -> EF performs identity correlation
```

Điểm quan trọng: giữa các queries, database state có thể thay đổi nếu transaction isolation không bảo đảm snapshot phù hợp.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Include(x => x.Items)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .Where(x => x.CustomerId == customerId)
    .Take(50)
    .ToListAsync(ct);
```

Tốt hơn nữa, nếu API chỉ cần summary, projection thường thắng cả hai:

```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummary(
        x.Id,
        x.Total,
        x.Items.Count,
        x.Notes.Count))
    .ToListAsync(ct);
```

## 5. Real production scenario

Order-detail endpoint include `Items`, `Discounts`, `Shipments`, `Notes`. SQL chạy 1.5 giây và trả hàng chục MB dù business object chỉ vài trăm KB.

Actual plan không hẳn có operator “xấu”; vấn đề là row multiplication do graph shape. Split query giảm payload mạnh. Sau đó team nhận ra frontend chỉ cần một phần graph và projection giảm thêm chi phí.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL query một lần nhưng API allocation/network tăng bất thường; hoặc đổi sang split query thì latency tăng vì DB ở xa.

**Evidence** → row count cao hơn entity count rất nhiều; traces cho thấy nhiều sequential DB calls sau `AsSplitQuery`.

**Hypothesis** → cartesian explosion hoặc round-trip cost đang chi phối.

**Diagnosis** → inspect generated SQL, result row counts, dependency traces, payload size.

**Fix** → projection trước; nếu cần full graph thì chọn split/single dựa trên shape và latency; transaction nếu consistency requirement cần.

**Verification** → đo SQL bytes/rows, DB duration, request allocation và p95.

## 7. Common mistakes

- `Include` toàn graph “cho tiện”.
- Bật `AsSplitQuery()` global mà không đo round trips.
- Nghĩ split query tự động nhanh hơn.
- Quên ordering/paging semantics khi query phức tạp.
- Dùng entities như API DTO.

## 8. Alternatives

Projection là lựa chọn ưu tiên cho read API. Explicit loading phù hợp khi navigation chỉ đôi lúc cần. Raw SQL/Dapper có thể hữu ích cho reporting shape đặc biệt nhưng tăng maintenance cost.

## 9. Trade-offs

### Advantages

- Giảm duplicated rows khi nhiều collections được include.
- Có thể giảm memory/network đáng kể.

### Costs / Risks

- Thêm query operations/round trips.
- Có consistency window giữa các reads.
- Query behavior khó hơn nếu bật mặc định mà team không hiểu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` không miễn phí; object graph phải được chuyển thành relational result.

### Middle

Biết inspect SQL và dùng projection/split query phù hợp.

### Senior

Đánh giá row multiplication, round-trip latency, isolation và materialization cost.

### Technical Lead / Architect

Đặt guideline read model: API không nên materialize domain graph chỉ vì ORM làm được.

## 11. Key takeaway

- `AsSplitQuery` giải quyết row multiplication bằng cách đổi sang nhiều reads.
- Projection thường là optimization có giá trị hơn nếu không cần full entity graph.
- Quyết định phải dựa trên shape, latency và consistency requirement.

# 4. ADO.NET connection pooling exhaustion: vì sao “database còn khỏe” nhưng API vẫn timeout khi hết connection

## 1. What is it?

ADO.NET connection pooling tái sử dụng physical database connections theo connection-string pool thay vì mở TCP/login session mới cho mỗi query.

Khi code gọi `OpenAsync`, thường nó lấy một connection từ pool. Khi dispose connection, physical connection thường được trả về pool, không đóng socket thật ngay.

Mental model:

```text
request
 -> acquire pooled connection
 -> query/transaction
 -> return connection
```

Pool exhaustion xảy ra khi mọi connection đang bận và request mới phải chờ tới khi có slot hoặc timeout.

## 2. Why does it exist?

Mở database connection mới rất đắt: network handshake, TLS, authentication, session setup. Pooling giảm latency và CPU.

Nhưng pool hữu hạn cũng là một backpressure boundary. Nếu queries giữ connection quá lâu, application có thể nghẽn ở pool trước khi database CPU đạt 100%.

## 3. How does it work?

Giả sử max pool size là 100:

```text
100 slow requests
 -> 100 leased connections
101st request
 -> waits for returned connection
 -> timeout if none returns in time
```

Một transaction mở rồi gọi external API 10 giây vẫn giữ database connection/locks dù lúc đó không query gì.

## 4. Practical implementation

Giữ database scope ngắn:

```csharp
var order = await db.Orders
    .AsNoTracking()
    .SingleAsync(x => x.Id == id, ct);

// connection can be returned after query
var quote = await _shippingClient.GetQuoteAsync(order, ct);
```

Không nên giữ transaction qua remote call:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

await db.SaveChangesAsync(ct);
await _remoteApi.CallAsync(ct); // dangerous: transaction remains open

await tx.CommitAsync(ct);
```

## 5. Real production scenario

Payment API chậm từ 300 ms lên 15 giây. Order service mở SQL transaction trước khi gọi payment. Trong vài phút, SQL pool cạn; health endpoint bắt đầu timeout dù SQL Server CPU chỉ 30%.

Root cause là connection hold time, không phải thiếu database horsepower.

## 6. Failure scenario & troubleshooting

**Symptom** → errors kiểu timeout obtaining/opening connection; DB CPU bình thường nhưng request queue tăng.

**Evidence** → active connection count gần pool limit, long transactions, traces có gap lớn giữa DB operations trong cùng transaction.

**Hypothesis** → connection leak hoặc long-held connection/transaction.

**Diagnosis** → Application Insights dependencies, DB sessions, transaction duration, connection-pool counters.

**Fix** → dispose scopes đúng, thu hẹp transaction, optimize slow queries, tách remote I/O khỏi DB transaction; chỉ tăng pool size khi database thật sự chịu được concurrency tăng.

**Verification** → load test dependency slowdown và theo dõi acquire latency + active connections.

## 7. Common mistakes

- Tăng `Max Pool Size` ngay lập tức.
- Không dispose connection/DbContext đúng lifetime.
- Transaction bao quanh network call.
- Retry timeout làm concurrency phình thêm.
- Có nhiều connection strings chỉ khác nhỏ khiến tạo nhiều pools riêng.

## 8. Alternatives

Không pooling gần như không hợp lý cho normal server workloads. Connection multiplexing/provider-specific behavior có thể khác, nhưng vẫn cần kiểm soát concurrent DB work. Queue/backpressure có thể hữu ích cho batch workload.

## 9. Trade-offs

### Advantages

- Connection reuse giảm latency lớn.
- Pool limit tạo bound cho database concurrency.

### Costs / Risks

- Exhaustion tạo queueing khó nhìn nếu chỉ monitor DB CPU.
- Pool quá lớn có thể đẩy overload sang database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Dispose` thường trả connection về pool, không nhất thiết đóng physical connection.

### Middle

Giữ DbContext/connection scope đúng và tránh long transaction.

### Senior

Correlate pool metrics với transaction duration, dependency latency và retry behavior.

### Technical Lead / Architect

Xác định concurrency budget từ API tới DB, không giải quyết saturation bằng cách tăng mọi limit.

## 11. Key takeaway

- Pool exhaustion thường là symptom của hold time/concurrency, không đơn giản là “pool quá nhỏ”.
- Transaction phải ngắn và không nên bao remote I/O.
- Theo dõi acquire latency và active connections cùng DB metrics.

# 5. Elasticsearch alias-based reindexing: thay đổi mapping gần zero-downtime mà không biến search index thành source of truth

## 1. What is it?

Một số Elasticsearch mapping changes không thể sửa in-place an toàn trên index đang chạy. Alias cho phép application gọi một logical name trong khi physical index có version khác nhau.

```text
products-read alias
       |
       v
products-v3
```

Khi cần mapping mới, tạo `products-v4`, reindex/backfill, validate rồi atomically chuyển alias.

## 2. Why does it exist?

Search schema evolve: analyzer mới, field type đổi, normalization khác. Rebuild index có thể mất phút hoặc giờ. Nếu application hardcode physical index name, rollout dễ tạo downtime hoặc mixed schema.

Alias tạo indirection để data-plane switch nhanh sau khi index mới đã sẵn sàng.

## 3. How does it work?

```text
Primary DB
   -> synchronization pipeline
   -> products-v3

create products-v4
   -> backfill from source of truth
   -> catch up recent changes
   -> validate counts/search quality
   -> switch alias v3 -> v4
```

Alias switch nhanh, nhưng correctness phụ thuộc synchronization pipeline không bỏ sót changes trong lúc backfill.

## 4. Practical implementation

Alias switch concept:

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v3", "alias": "products-read" } },
    { "add":    { "index": "products-v4", "alias": "products-read" } }
  ]
}
```

Application chỉ query alias:

```csharp
var response = await client.SearchAsync<ProductDocument>(s => s
    .Index("products-read")
    .Query(q => q.Match(m => m.Field(f => f.Name).Query(term))), ct);
```

## 5. Real production scenario

Product search cần chuyển `name` analyzer để hỗ trợ accent normalization. Thay mapping trực tiếp không khả thi. Team build `products-v4`, backfill từ SQL + replay change events, chạy relevance smoke tests rồi switch alias.

Nếu v4 lỗi, alias có thể quay lại v3 nhanh, miễn synchronization vẫn giữ v3 đủ mới trong rollback window.

## 6. Failure scenario & troubleshooting

**Symptom** → sau alias switch, search thiếu sản phẩm mới hoặc document count thấp hơn nguồn chính.

**Evidence** → backfill checkpoint/event lag không về 0; count/hash sampling khác giữa source và index.

**Hypothesis** → race giữa historical backfill và live updates.

**Diagnosis** → kiểm tra event offsets, indexing failures, DLQ, last-updated timestamps.

**Fix** → thiết kế dual-write/event replay/catch-up checkpoint rõ ràng trước cutover; không switch chỉ dựa vào “reindex task completed”.

**Verification** → compare representative queries, counts, lag và error rate trước/sau switch.

## 7. Common mistakes

- Dùng Elasticsearch làm transactional source of truth.
- Hardcode physical index name trong application.
- Switch alias trước khi live changes catch up.
- Không giữ rollback index đủ lâu.
- Chỉ validate document count mà không validate search semantics.

## 8. Alternatives

Small index có thể chấp nhận maintenance-window rebuild. Runtime fields có thể giải quyết một số needs mà không reindex nhưng có query cost. Database full-text search có thể đủ nếu requirements đơn giản.

## 9. Trade-offs

### Advantages

- Cutover nhanh.
- Rollback rõ ràng.
- Schema evolution tách khỏi application deployment.

### Costs / Risks

- Tạm thời cần storage cho hai indexes.
- Synchronization/catch-up phức tạp.
- Relevance validation vẫn cần human/business criteria.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index là derived search model có thể rebuild.

### Middle

Biết alias, mapping và reindex workflow.

### Senior

Thiết kế catch-up, validation, rollback và monitor indexing lag.

### Technical Lead / Architect

Quyết định source of truth, synchronization ownership và schema-evolution protocol cho search platform.

## 11. Key takeaway

- Alias là deployment indirection cho search indexes.
- Reindex correctness phụ thuộc live-change synchronization.
- Search index nên là rebuildable derived state, không phải transactional truth.

# 6. DDD Aggregate boundary: đặt invariant và transaction boundary đúng chỗ thay vì gom entity theo quan hệ database

## 1. What is it?

Aggregate trong DDD là một consistency boundary gồm một Aggregate Root và các entities/value objects phải thay đổi cùng nhau để bảo vệ business invariants.

Nó không có nghĩa “một object graph lớn chứa mọi foreign key liên quan”.

Ví dụ:

```text
Order (Aggregate Root)
 ├─ OrderLine
 └─ ShippingAddress (Value Object)
```

Customer có thể là aggregate khác dù Order có `CustomerId`.

## 2. Why does it exist?

Nếu mọi related entity đều nằm trong một aggregate khổng lồ, mỗi business change cần load/lock nhiều state, transaction contention tăng và boundary ownership mờ.

Nếu aggregate quá nhỏ, invariant cần atomic consistency có thể bị chia ra nhiều transaction và dễ vi phạm.

Aggregate tồn tại để trả lời: “State nào phải nhất quán ngay tại commit boundary này?”

## 3. How does it work?

External code thay đổi state thông qua Aggregate Root:

```csharp
order.AddLine(productId, quantity, unitPrice);
order.Confirm();
```

Root kiểm soát invariant:

```csharp
public void Confirm()
{
    if (_lines.Count == 0)
        throw new DomainException("Cannot confirm an empty order.");

    Status = OrderStatus.Confirmed;
}
```

Reference sang aggregate khác thường dùng identity thay vì object navigation bắt buộc.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public Guid Id { get; private set; }
    public Guid CustomerId { get; private set; }
    public OrderStatus Status { get; private set; }
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void AddLine(Guid productId, int quantity, decimal price)
    {
        if (Status != OrderStatus.Draft)
            throw new DomainException("Only draft orders can be modified.");

        _lines.Add(new OrderLine(productId, quantity, price));
    }
}
```

Inventory reservation không nhất thiết phải nằm trong Order aggregate; nó có lifecycle/consistency model riêng.

## 5. Real production scenario

Một commerce system ban đầu tạo aggregate `Customer` chứa Orders, Addresses, Payments và Preferences vì tất cả “liên quan customer”. Update email phải load graph lớn, concurrent order writes conflict vô lý.

Tách bounded aggregates theo invariants giảm contention và làm service/module ownership rõ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → frequent optimistic concurrency conflicts trên fields không liên quan hoặc transaction phải update quá nhiều tables.

**Evidence** → aggregate load graph lớn; domain method thay đổi unrelated subdomains; one root có hàng chục collections.

**Hypothesis** → aggregate boundary được chọn theo database relationship thay vì invariant.

**Diagnosis** → liệt kê invariants nào cần atomic commit; xác định lifecycle và ownership từng state.

**Fix** → tách aggregates; dùng domain events/workflow cho consistency không cần immediate atomicity.

**Verification** → concurrency tests và invariant tests ở từng boundary.

## 7. Common mistakes

- Đồng nhất Aggregate với EF navigation graph.
- Mỗi table là một Aggregate Root.
- Aggregate chứa mọi object liên quan business.
- Domain event dùng để né invariant đáng lẽ phải atomic.
- Repository cho từng entity con thay vì root.

## 8. Alternatives

CRUD/anemic model hoàn toàn phù hợp cho domain đơn giản. DDD aggregate chỉ đáng dùng khi business rules/invariants đủ phức tạp để cần explicit model.

## 9. Trade-offs

### Advantages

- Invariant ownership rõ.
- Transaction boundary có business meaning.
- Giảm accidental coupling nếu boundary tốt.

### Costs / Risks

- Modeling khó hơn CRUD.
- Boundary sai gây contention hoặc eventual-consistency complexity.
- Team phải hiểu domain, không chỉ framework patterns.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Aggregate Root là entry point bảo vệ state consistency.

### Middle

Implement methods bảo vệ invariant thay vì public setters khắp nơi.

### Senior

Phân tích transaction boundary, concurrency và cross-aggregate workflow.

### Technical Lead / Architect

Quyết định chỗ nào business complexity đủ để dùng DDD và chỗ nào CRUD đơn giản tốt hơn.

## 11. Key takeaway

- Aggregate boundary được quyết định bởi invariants, không bởi foreign keys.
- Aggregate quá lớn gây contention; quá nhỏ có thể phá atomic correctness.
- DDD chỉ có giá trị khi giải quyết business complexity thật.

# 7. Azure Key Vault + Managed Identity: secret rotation mà application không giữ credential dài hạn

## 1. What is it?

Azure Key Vault lưu secrets/keys/certificates ở managed security boundary. Managed Identity cho Azure workload một identity trong Microsoft Entra ID mà không cần lưu client secret.

Kết hợp:

```text
App Service / Function / Container App
        -> Managed Identity
        -> Entra token
        -> Key Vault RBAC
        -> retrieve secret when needed
```

Application không cần hardcode Key Vault credential.

## 2. Why does it exist?

Secret trong `appsettings.json`, environment variable pipeline hoặc repo dễ bị leak và rotation khó. Một root credential dùng lâu làm blast radius lớn.

Key Vault centralize secret lifecycle; Managed Identity giải quyết bootstrap problem: “lấy secret từ vault bằng credential nào?”

## 3. How does it work?

Azure platform cấp token cho workload identity. Key Vault authorize identity qua RBAC/access policy. App đọc secret version hiện tại hoặc specific version.

Rotation chỉ có hiệu lực với application khi app refresh secret. Nếu app cache secret suốt process lifetime, vault đã rotate nhưng app vẫn dùng giá trị cũ.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(keyVaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret =
    await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);

var apiKey = secret.Value;
```

Production nên có caching có TTL hợp lý để không gọi Key Vault trên mọi request.

Không log `secret.Value`.

## 5. Real production scenario

Payment provider yêu cầu rotate API key mỗi 90 ngày. Team cập nhật Key Vault secret version nhưng App Service giữ key cũ trong singleton config cho đến restart. Provider revoke key cũ và traffic bắt đầu 401.

Rotation workflow phải bao gồm application refresh semantics và overlap window.

## 6. Failure scenario & troubleshooting

**Symptom** → app startup hoặc downstream auth fail sau rotation; Key Vault requests 403/429.

**Evidence** → secret version đang dùng, identity object ID, RBAC logs, Key Vault dependency telemetry.

**Hypothesis** → stale cached secret, permission sai hoặc quá nhiều vault calls.

**Diagnosis** → xác minh Managed Identity của đúng slot/environment; inspect secret version/TTL; check throttling.

**Fix** → cache với controlled refresh, overlap old/new secret khi provider support, correct least-privilege RBAC.

**Verification** → rotate trong staging mà không restart và xác nhận service tự chuyển sang version mới theo SLA.

## 7. Common mistakes

- App có Key Vault nhưng vẫn lưu service-principal secret để truy cập vault dù Managed Identity khả dụng.
- Fetch secret mỗi request.
- Cache secret mãi tới process restart.
- Cho identity quyền quản trị vault khi chỉ cần read secret.
- Log configuration object chứa secret.

## 8. Alternatives

Environment variables đơn giản hơn cho low-risk local/dev. Certificates/federated identity tốt hơn shared secret cho service auth khi provider hỗ trợ. App Configuration phù hợp config thường nhưng không thay Key Vault cho secret material.

## 9. Trade-offs

### Advantages

- Giảm long-lived bootstrap credentials.
- Central audit/rotation.
- Least privilege theo workload identity.

### Costs / Risks

- Thêm runtime dependency.
- Caching/rotation semantics phải thiết kế.
- Networking/Private Endpoint/RBAC có thể làm troubleshooting khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu secret không nên nằm trong source code.

### Middle

Dùng `DefaultAzureCredential`, Managed Identity và least-privilege access.

### Senior

Thiết kế refresh, throttling, failure fallback và secret rotation test.

### Technical Lead / Architect

Định nghĩa secret ownership, rotation SLA, break-glass process và workload identity standard toàn platform.

## 11. Key takeaway

- Managed Identity giải quyết credential bootstrap cho Azure workloads.
- Secret rotation chỉ hoàn tất khi consumers thực sự refresh giá trị.
- Key Vault cần caching và failure design, không nên bị gọi trên từng request.

# 8. `git bisect`: tìm commit gây production regression bằng binary search thay vì đọc hàng trăm commit thủ công

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên làm behavior chuyển từ “good” sang “bad”.

Nếu có 1.024 commits trong khoảng nghi ngờ, lý thuyết chỉ cần khoảng 10 lần test để thu hẹp tới culprit commit.

## 2. Why does it exist?

Production regression thường xuất hiện sau nhiều commits được release cùng batch. Đọc diff tuần tự từng commit chậm và bị cognitive bias.

Nếu ta có test/reproduction deterministic phân biệt good/bad, binary search biến investigation thành process có bằng chứng.

## 3. How does it work?

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0
```

Git checkout commit ở giữa. Ta chạy reproduction rồi đánh dấu:

```bash
git bisect good
# hoặc
git bisect bad
```

Lặp đến khi Git chỉ ra first bad commit.

Kết thúc:

```bash
git bisect reset
```

## 4. Practical implementation

Có thể automate nếu test trả exit code:

```bash
git bisect start HEAD v1.8.0
git bisect run dotnet test tests/Regression.Tests \
  --filter FullyQualifiedName~CheckoutLatencyRegression
```

Script exit `0` cho good, non-zero cho bad. Nếu commit không build được vì unrelated transition, bisect có thể `skip` nhưng quá nhiều skips giảm precision.

## 5. Real production scenario

Sau release, API export tăng memory 3x. Release chứa 180 commits. Team tạo regression benchmark nhỏ chạy cùng dataset và threshold allocation. `git bisect run` tìm ra commit đổi serialization path trong vài bước thay vì review 180 PRs.

Culprit commit không nhất thiết là “developer sai”; nó là vị trí behavior đổi, từ đó investigation tiếp tục vào root cause.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit không liên quan hoặc kết quả thay đổi mỗi lần.

**Evidence** → reproduction flaky, external dependency/time-sensitive data khác nhau giữa runs.

**Hypothesis** → good/bad oracle không deterministic.

**Diagnosis** → chạy cùng commit nhiều lần; pin fixtures/dependencies/environment.

**Fix** → tạo deterministic regression test trước khi bisect; nếu issue phụ thuộc deployment config, repository history alone có thể không đủ.

**Verification** → checkout parent và culprit commit, chạy test lặp lại để xác nhận transition.

## 7. Common mistakes

- Bisect với flaky test.
- Chọn “good” commit chưa được xác minh.
- Kết luận culprit commit là root cause cuối cùng mà không inspect context.
- Quên config/database migration có thể nằm ngoài code commit.
- Không thêm regression test sau fix.

## 8. Alternatives

`git log`, PR history, deployment telemetry và feature-flag audit hữu ích khi khoảng thay đổi nhỏ. Canary/Blue-Green giúp giảm blast radius trước khi cần bisect.

## 9. Trade-offs

### Advantages

- Giảm search space logarithmically.
- Evidence-driven.
- Có thể automate hoàn toàn.

### Costs / Risks

- Cần reproducible good/bad test.
- Old commits có thể không build/run trên current environment.
- Không tìm được config/infrastructure regression nếu không nằm trong history được bisect.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Git history là công cụ diagnosis, không chỉ collaboration.

### Middle

Biết start/good/bad/reset và verify culprit diff.

### Senior

Tạo deterministic oracle và kết hợp bisect với metrics/profiling.

### Technical Lead / Architect

Đầu tư release traceability để map incident → artifact → commit/config, giúp techniques như bisect thực sự hiệu quả.

## 11. Key takeaway

- `git bisect` mạnh khi có deterministic regression test.
- Nó tìm first behavior-changing commit, không tự giải thích root cause.
- Sau fix phải giữ regression test để ngăn tái phát.

# 9. SLO burn-rate alerting: phát hiện reliability regression bằng error budget thay vì alert theo CPU đơn lẻ

## 1. What is it?

SLO (Service Level Objective) định nghĩa mức reliability mục tiêu dựa trên một SLI có ý nghĩa với user, ví dụ:

```text
99.9% checkout requests thành công trong 30 ngày
```

Error budget là phần failure được phép: với 99.9%, budget là 0.1%.

Burn rate đo tốc độ hệ thống đang tiêu error budget so với tốc độ “cho phép”.

## 2. Why does it exist?

Alert “CPU > 80%” không nói user có bị ảnh hưởng hay không. CPU 90% có thể vẫn khỏe; CPU 20% nhưng payment dependency fail thì business đã outage.

SLO chuyển alerting từ infrastructure symptom sang user-visible reliability outcome.

## 3. How does it work?

Giả sử budget cho 30 ngày. Burn rate `1x` nghĩa là tiếp tục như hiện tại sẽ dùng hết budget đúng cuối window. `10x` nghĩa là budget bị tiêu nhanh gấp 10 lần.

Multi-window alert thường kết hợp:

```text
fast window -> bắt outage mạnh nhanh
slow window -> tránh noise từ spike ngắn
```

Ví dụ alert chỉ fire nếu burn rate cao ở cả 5 phút và 1 giờ.

## 4. Practical implementation

Một SLI cho API có thể là:

```text
Good events:
HTTP requests < 2s và status không phải 5xx

Valid events:
Tất cả eligible checkout HTTP requests
```

Prometheus-like expression concept:

```text
error_ratio = bad_requests / total_requests
burn_rate = error_ratio / allowed_error_ratio
```

Trong Azure Monitor/Application Insights, có thể tạo metric/query tương đương và alert theo rolling windows.

## 5. Real production scenario

Checkout service SLO 99.95%. Một deployment gây 2% requests fail nhưng CPU/memory hoàn toàn bình thường. Burn-rate alert fire trong vài phút vì error budget bị tiêu rất nhanh, trong khi resource alerts không báo gì.

Ngược lại, batch job làm CPU 95% nhưng checkout SLI vẫn tốt; team không bị đánh thức vô ích.

## 6. Failure scenario & troubleshooting

**Symptom** → alert fire liên tục dù user không thấy vấn đề, hoặc incident lớn mà SLO không báo.

**Evidence** → SLI query include health probes/bots hoặc exclude critical route; denominator sai.

**Hypothesis** → SLI không đại diện user journey.

**Diagnosis** → sample good/bad events; compare SLO dashboard với incident timeline và support tickets.

**Fix** → sửa eligibility, latency threshold hoặc tách SLO theo critical journey.

**Verification** → replay historical incident data xem alert có fire đúng timing và severity không.

## 7. Common mistakes

- SLO bằng uptime của VM thay vì user outcome.
- Đặt 100% SLO không có business justification.
- Dùng average latency thay percentile/event threshold.
- Một SLO cho toàn bộ product với các journeys có criticality khác nhau.
- Burn budget nhưng không có release/incident decision process đi kèm.

## 8. Alternatives

Traditional threshold alerts vẫn hữu ích cho leading infrastructure signals như disk full, queue backlog, cert expiry. SLO alerts không thay mọi operational alert; chúng ưu tiên paging theo user impact.

## 9. Trade-offs

### Advantages

- Alert gần business impact.
- Giảm noise.
- Tạo language chung giữa reliability và delivery velocity.

### Costs / Risks

- Chọn SLI/SLO đúng cần product understanding.
- Query/data quality sai tạo false confidence.
- Multi-window alerts phức tạp hơn simple threshold.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu metrics khác nhau giữa resource health và user reliability.

### Middle

Biết định nghĩa good/valid events và dashboard SLI.

### Senior

Thiết kế burn-rate windows, correlate SLO với traces/dependencies và incident response.

### Technical Lead / Architect

Đàm phán SLO theo business criticality, error budget và operational cost; không đặt target theo cảm tính.

## 11. Key takeaway

- SLO nên đo điều user thực sự cảm nhận.
- Burn rate cho biết tốc độ tiêu reliability budget, không chỉ trạng thái tức thời.
- Resource metrics hỗ trợ diagnosis; SLO giúp quyết định khi nào cần page.

# 10. SSRF trong third-party HTTP integration: chặn server bị lợi dụng để gọi internal endpoint hoặc metadata service

## 1. What is it?

SSRF (Server-Side Request Forgery) xảy ra khi attacker kiểm soát hoặc ảnh hưởng URL mà server gọi, khiến server request tới destination không intended.

Ví dụ nguy hiểm:

```text
POST /preview?url=http://internal-admin/
```

Server có network privilege lớn hơn browser/user, nên SSRF có thể truy cập:

- internal services;
- loopback;
- private IP ranges;
- cloud metadata endpoints;
- management APIs.

## 2. Why does it exist?

Nhiều feature hợp lệ cần server fetch URL: webhook validation, image proxy, URL preview, import feed, PDF rendering, integration callback.

Nếu design chỉ kiểm tra “đây là URL hợp lệ”, attacker vẫn có thể đưa URL hợp lệ nhưng trỏ tới sensitive network target.

## 3. How does it work?

Attack path:

```text
attacker-controlled URL
 -> application resolves DNS
 -> server-side HttpClient
 -> internal/private destination
 -> response/data returned or side effect triggered
```

Validation phức tạp vì redirect và DNS rebinding có thể làm destination thay đổi sau bước kiểm tra ban đầu.

## 4. Practical implementation

Tốt nhất là allowlist destination khi business domain hữu hạn:

```csharp
private static readonly HashSet<string> AllowedHosts =
    new(StringComparer.OrdinalIgnoreCase)
    {
        "api.partner-a.com",
        "cdn.partner-a.com"
    };

public static Uri ValidatePartnerUri(string input)
{
    if (!Uri.TryCreate(input, UriKind.Absolute, out var uri))
        throw new ValidationException("Invalid URL.");

    if (uri.Scheme != Uri.UriSchemeHttps)
        throw new ValidationException("HTTPS required.");

    if (!AllowedHosts.Contains(uri.Host))
        throw new ValidationException("Host is not allowed.");

    return uri;
}
```

Với arbitrary URL preview, cần network egress isolation, DNS/IP validation, redirect controls và response-size/time limits — chỉ application string validation là chưa đủ.

## 5. Real production scenario

Marketing CMS có feature “preview remote image”. Backend tải URL để inspect dimensions. Attacker có editor account nhập URL tới internal admin endpoint. Backend chạy trong VNet nên endpoint nội bộ reachable, trong khi attacker từ Internet không truy cập trực tiếp được.

Feature vô tình trở thành proxy qua trust boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → outbound logs xuất hiện requests tới `127.0.0.1`, private IP hoặc unexpected internal hostname.

**Evidence** → correlation trace từ preview/import endpoint đến unusual destination; DNS resolution logs nếu có.

**Hypothesis** → user-controlled outbound target không được constrained.

**Diagnosis** → trace source parameter, redirects, resolved IP và egress path.

**Fix** → allowlist khi có thể; block private/link-local/loopback destinations; restrict redirects; isolate outbound fetcher; least-privilege network egress.

**Verification** → security tests với loopback, private IP, encoded IP forms, redirects và DNS changes.

## 7. Common mistakes

- Chỉ block string `localhost`.
- Validate hostname trước nhưng tự động follow redirect sang internal IP.
- Tin DNS result mãi mãi.
- Cho server fetch arbitrary URL từ high-trust network.
- Trả toàn bộ fetched response về client mà không size/content limits.

## 8. Alternatives

Client-side fetch phù hợp nếu CORS/security model cho phép và không cần server credentials. Dedicated isolated fetch service có restricted egress phù hợp khi arbitrary external URLs là core requirement.

## 9. Trade-offs

### Advantages

Server-side fetch cho phép integration, secret-based authentication và controlled processing.

### Costs / Risks

Server network identity trở thành attack surface. Arbitrary outbound access đòi hỏi network-level controls, timeout, size limits và auditability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu URL từ user không chỉ là input-validation problem; nó quyết định network destination của server.

### Middle

Implement HTTPS/host allowlist, timeout và redirect policy cho known integrations.

### Senior

Threat-model DNS rebinding, private ranges, metadata endpoints, proxy behavior và egress controls.

### Technical Lead / Architect

Quyết định feature có thật sự cần arbitrary URL fetch; nếu có, đặt nó trong low-trust isolated network boundary thay vì application core.

## 11. Key takeaway

- SSRF khai thác network privilege của server.
- Allowlist destination là mạnh nhất khi business domain hữu hạn.
- Với arbitrary URLs, application validation phải kết hợp network isolation và redirect/DNS controls.
