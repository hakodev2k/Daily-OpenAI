# 1. .NET Garbage Collector, generations và LOH: đọc memory pressure thay vì chỉ nhìn RAM

## 1. What is it?

Garbage Collector (GC) của .NET quản lý managed memory: object được cấp phát trên managed heap, còn GC quyết định khi nào object không còn reachable và có thể thu hồi. Mental model quan trọng là GC không “dọn RAM liên tục”; nó tối ưu theo giả định phần lớn object sống rất ngắn.

Managed heap được tổ chức chủ yếu theo generations:

- Generation 0: object mới, thường sống rất ngắn.
- Generation 1: vùng chuyển tiếp.
- Generation 2: object sống lâu.
- Large Object Heap (LOH): nơi các object lớn, điển hình array/string lớn, được cấp phát.

Một hệ thống có RAM cao chưa chắc có memory leak; vấn đề cần quan sát là allocation rate, collection frequency, promoted objects, Gen 2 pressure và LOH behavior.

## 2. Why does it exist?

Manual memory management buộc developer phải tự quyết định khi nào giải phóng object, dễ gây use-after-free, double free hoặc leak. GC đổi bài toán đó thành reachability tracking và collection.

Nhưng abstraction này không miễn phí. Nếu application tạo quá nhiều object tạm thời, serialize payload lớn, giữ cache vô hạn hoặc dùng large byte arrays liên tục, GC phải chạy thường xuyên hơn. Khi đó latency có thể tăng dù business logic không đổi.

## 3. How does it work?

Một flow đơn giản:

```text
Allocation
   |
   v
Gen 0
   |
   +--> object chết -> reclaim
   |
   +--> object sống -> promote Gen 1
                         |
                         +--> tiếp tục sống -> Gen 2
```

GC xác định object reachable từ roots như static fields, stack references và GC handles. Object không reachable có thể bị reclaim.

Generation giúp GC tránh scan toàn heap mỗi lần. Gen 0 collection thường nhanh hơn Gen 2 collection vì vùng cần kiểm tra nhỏ hơn.

LOH quan trọng vì object lớn làm allocation pressure tăng nhanh. Ví dụ mỗi request tạo một `byte[5_000_000]` sẽ tiêu thụ memory rất khác so với vài object DTO nhỏ.

## 4. Practical implementation

Một anti-pattern phổ biến khi xử lý file:

```csharp
public async Task<byte[]> DownloadAsync(
    BlobClient client,
    CancellationToken cancellationToken)
{
    using var memory = new MemoryStream();
    await client.DownloadToAsync(memory, cancellationToken);
    return memory.ToArray();
}
```

Với file lớn, `MemoryStream` và `ToArray()` có thể tạo nhiều large allocations.

Tốt hơn nếu HTTP layer hỗ trợ streaming:

```csharp
app.MapGet("/files/{name}", async (
    string name,
    BlobContainerClient container,
    HttpResponse response,
    CancellationToken cancellationToken) =>
{
    var blob = container.GetBlobClient(name);
    var download = await blob.DownloadStreamingAsync(
        cancellationToken: cancellationToken);

    response.ContentType = download.Value.Details.ContentType
        ?? "application/octet-stream";

    await download.Value.Content.CopyToAsync(
        response.Body,
        cancellationToken);
});
```

Ở đây mục tiêu không phải “không allocation”, mà là tránh buffer toàn file nếu không cần.

## 5. Real production scenario

Một API export báo cáo tạo JSON/Excel lớn. Trong môi trường test với vài request, mọi thứ ổn. Khi 50 users export đồng thời, working set tăng mạnh, Gen 2 GC chạy nhiều hơn và p99 latency của cả API tăng, kể cả endpoint không liên quan tới export.

Nguyên nhân không nhất thiết là memory leak. Có thể chỉ là allocation burst lớn làm GC pause và tăng CPU.

## 6. Failure scenario & troubleshooting

**Symptom**  
Memory tăng, CPU có spike định kỳ và p99 latency xấu.

**Evidence**  
`dotnet-counters` hoặc telemetry cho thấy allocation rate cao, Gen 2 collections tăng, LOH size lớn.

**Hypothesis**  
Một hot path tạo object/array lớn liên tục hoặc giữ reference quá lâu.

**Diagnosis**  
Dùng `dotnet-gcdump`, `dotnet-dump`, profiler hoặc Application Insights profiler để xác định allocation sources và retained objects.

**Fix**  
Streaming, giảm unnecessary materialization, dùng pooling khi phù hợp, giới hạn cache, tránh duplicate buffers.

**Verification**  
So sánh allocation rate, Gen 2 collection count, working set và p95/p99 trước/sau.

## 7. Common mistakes

- Thấy RAM cao là gọi ngay `GC.Collect()`.
- Tạo `MemoryStream`/`byte[]` lớn cho mọi file operation.
- Dùng `ArrayPool<T>` nhưng quên return buffer.
- Giữ object graph lớn trong Singleton/cache không TTL.
- Tối ưu vài allocation nhỏ trong khi bottleneck thật là database hoặc network.
- Không phân biệt memory leak với high allocation rate.

## 8. Alternatives

- Streaming thay vì buffering cho file/network payload lớn.
- `ArrayPool<T>` khi thực sự có hot path buffer reuse.
- `Span<T>`/`Memory<T>` cho processing cần giảm allocation, nhưng chỉ nên dùng khi profiling chứng minh có lợi.
- Cache bounded thay vì dictionary/static collection tăng không giới hạn.

## 9. Trade-offs

### Advantages

- GC giúp developer tránh phần lớn manual memory management.
- Generational collection tối ưu tốt cho object ngắn hạn.
- Managed memory an toàn và productive cho enterprise applications.

### Costs / Risks

- Allocation vẫn có chi phí.
- Gen 2/LOH pressure có thể ảnh hưởng latency toàn process.
- Pooling giảm allocation nhưng tăng lifecycle complexity và nguy cơ data leakage nếu dùng sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu rằng object không được “xóa ngay” khi ra khỏi scope; GC thu hồi dựa trên reachability.

### Middle

Biết tránh buffer file lớn không cần thiết và biết dùng `IDisposable` đúng cho unmanaged/resource lifecycle.

### Senior

Biết phân biệt leak, allocation pressure, Gen 2 pressure và LOH; dùng profiler thay vì đoán.

### Technical Lead / Architect

Quyết định memory budget, streaming strategy, cache limits và khi nào optimization phức tạp như pooling thực sự justified.

## 11. Key takeaway

- RAM cao không tự động đồng nghĩa memory leak.
- Hãy đo allocation rate, Gen 2 và LOH trước khi tối ưu.
- Streaming thường có giá trị hơn micro-optimizing object nhỏ trong workload file-heavy.

# 2. ASP.NET Core middleware ordering: exception handling, routing, CORS, authentication và authorization

## 1. What is it?

ASP.NET Core middleware pipeline là chuỗi component xử lý HTTP request/response. Mỗi middleware có thể làm việc trước khi gọi component tiếp theo và tiếp tục xử lý sau khi downstream trả về.

Ordering là semantic, không phải cosmetic. Một middleware đặt sai vị trí có thể khiến authentication chưa chạy, exception không được bắt, CORS headers thiếu hoặc request không map đúng endpoint metadata.

## 2. Why does it exist?

HTTP request có nhiều cross-cutting concerns: exception handling, HTTPS, static files, routing, CORS, authentication, authorization, logging, rate limiting.

Nếu mỗi controller tự xử lý chúng, logic bị duplicate và policy không nhất quán. Pipeline tạo một composable boundary cho toàn application.

## 3. How does it work?

Mental model:

```text
Request
  |
  v
Exception Handler
  |
  v
Routing / CORS
  |
  v
Authentication
  |
  v
Authorization
  |
  v
Endpoint
  |
  v
Response quay ngược qua pipeline
```

Một middleware có dạng:

```csharp
app.Use(async (context, next) =>
{
    // before downstream
    await next();
    // after downstream
});
```

Nếu middleware không gọi `next()`, pipeline short-circuit tại đó.

## 4. Practical implementation

Một pipeline điển hình:

```csharp
var app = builder.Build();

app.UseExceptionHandler();
app.UseHttpsRedirection();

app.UseRouting();
app.UseCors("Frontend");

app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();

app.Run();
```

Global exception handling với `ProblemDetails`:

```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler();
```

Mục tiêu là exception từ endpoint/application layer được convert thành error contract nhất quán thay vì mỗi controller `try/catch` riêng.

## 5. Real production scenario

Một SPA gọi API bằng bearer token. Developer đặt `UseAuthorization()` trước `UseAuthentication()`. Endpoint yêu cầu policy dựa trên claims, nhưng `HttpContext.User` chưa được populate đúng lúc authorization chạy.

Ở local có thể một số endpoint anonymous vẫn hoạt động, khiến lỗi chỉ lộ ra khi Production gọi protected endpoint.

## 6. Failure scenario & troubleshooting

**Symptom**  
401/403 bất thường hoặc browser báo CORS dù backend có policy.

**Evidence**  
Request logs cho thấy endpoint match đúng nhưng headers/claims thiếu.

**Hypothesis**  
Middleware order sai.

**Diagnosis**  
Review pipeline theo request lifecycle; bật debug logging cho routing/authentication/authorization.

**Fix**  
Sắp lại middleware dựa trên dependency semantics.

**Verification**  
Integration test cho anonymous, authenticated, forbidden và CORS preflight scenarios.

## 7. Common mistakes

- Đặt authentication sau authorization.
- Dùng `try/catch` trong mọi controller thay vì centralized exception handling.
- Tự viết middleware đọc request body nhưng không xử lý buffering đúng.
- Logging sensitive headers/token.
- Thêm middleware custom mà không hiểu short-circuit behavior.
- Giả định thứ tự không quan trọng vì “tất cả đều chạy”.

## 8. Alternatives

- Filters phù hợp MVC-specific concerns gần action execution.
- Endpoint filters phù hợp Minimal APIs cho logic gắn endpoint.
- Middleware phù hợp concerns cần áp dụng rộng ở HTTP pipeline level.

Không nên dùng middleware cho domain/business logic.

## 9. Trade-offs

### Advantages

- Centralized cross-cutting behavior.
- Consistent policy across endpoints.
- Dễ quan sát request lifecycle.

### Costs / Risks

- Order-dependent behavior dễ tạo subtle bugs.
- Middleware custom có thể tăng latency cho mọi request.
- Coupling với HTTP layer nếu nhét business logic vào pipeline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request đi qua middleware theo thứ tự đăng ký.

### Middle

Biết configure routing, CORS, auth, exception handling đúng order.

### Senior

Biết debug short-circuit, endpoint metadata và cross-cutting performance/security implications.

### Technical Lead / Architect

Định nghĩa pipeline conventions và quyết định concern nào thuộc middleware, filter hay application layer.

## 11. Key takeaway

- Middleware order là behavior của hệ thống.
- Authentication phải tạo identity trước khi authorization đánh giá policy.
- Cross-cutting concern nên centralized, business logic thì không.

# 3. EF Core transaction boundaries: SaveChanges, explicit transaction và external side effects

## 1. What is it?

Transaction boundary là phạm vi các thay đổi phải commit hoặc rollback như một đơn vị consistency.

Trong EF Core, một lần `SaveChanges()` thường được thực hiện trong transaction nếu provider hỗ trợ. Nhưng khi use case có nhiều `SaveChanges()`, raw SQL hoặc phối hợp nhiều persistence operations, developer có thể cần explicit transaction.

Điểm khó nhất xuất hiện khi transaction database bị trộn với external side effects như gửi email, gọi REST API hoặc publish message.

## 2. Why does it exist?

Nếu một approval workflow cập nhật `Timesheet.Status` rồi insert `AuditLog`, hai thay đổi này có thể cần atomicity. Nếu chỉ một thành công, data trở nên inconsistent.

Nhưng database transaction không thể đơn giản rollback một email đã gửi hoặc HTTP call đã hoàn tất. Vì vậy transaction boundary phải phù hợp với resource ownership.

## 3. How does it work?

Một `SaveChanges()` đơn giản:

```text
Begin transaction
  -> INSERT / UPDATE / DELETE
Commit
```

Một use case explicit transaction:

```text
Begin transaction
  -> SaveChanges #1
  -> SQL operation
  -> SaveChanges #2
Commit
```

External API không nằm trong ACID transaction đó.

## 4. Practical implementation

```csharp
public async Task ApproveAsync(
    Guid timesheetId,
    CancellationToken cancellationToken)
{
    await using var transaction =
        await db.Database.BeginTransactionAsync(cancellationToken);

    var timesheet = await db.Timesheets
        .SingleAsync(x => x.Id == timesheetId, cancellationToken);

    timesheet.Approve();

    db.AuditEntries.Add(new AuditEntry(
        timesheetId,
        "Approved",
        DateTimeOffset.UtcNow));

    await db.SaveChangesAsync(cancellationToken);
    await transaction.CommitAsync(cancellationToken);
}
```

Không nên làm thế này bên trong transaction nếu call có thể chậm:

```csharp
await externalPayrollApi.NotifyAsync(timesheetId, cancellationToken);
```

Vì database locks có thể bị giữ trong suốt network call.

## 5. Real production scenario

Một order service:

1. update Order thành Paid,
2. gọi payment provider,
3. publish `OrderPaid`.

Nếu publish message fail sau khi DB commit, downstream không biết order đã paid. Nếu publish trước commit rồi DB rollback, downstream nhận event cho state không tồn tại.

Đây là lý do Outbox Pattern thường xuất hiện: business change và outbox record commit cùng transaction; message được publish sau bởi worker.

## 6. Failure scenario & troubleshooting

**Symptom**  
Database blocking tăng bất thường và transaction duration dài.

**Evidence**  
Trace cho thấy transaction mở rồi chờ external API 3–5 giây.

**Hypothesis**  
Transaction boundary chứa remote I/O.

**Diagnosis**  
Xem code path, SQL locks và dependency spans.

**Fix**  
Thu hẹp DB transaction; tách side effect qua Outbox/queue hoặc workflow phù hợp.

**Verification**  
Đo transaction duration, lock waits và consistency under injected failures.

## 7. Common mistakes

- Explicit transaction cho mọi repository method.
- Giữ transaction mở khi gọi external service.
- Nhiều `SaveChanges()` không hiểu partial commit risk.
- Retry cả transaction mà side effect không idempotent.
- Dùng distributed transaction như default solution.
- Không xác định aggregate/consistency boundary trước khi code.

## 8. Alternatives

- Một `SaveChanges()` duy nhất cho use case đơn giản.
- Explicit transaction khi nhiều DB operations phải atomic.
- Outbox Pattern khi DB change cần dẫn tới messaging đáng tin cậy.
- Saga/compensation cho workflow cross-service dài.

## 9. Trade-offs

### Advantages

- Transaction bảo vệ invariants trong một data store.
- Explicit boundary làm consistency requirement rõ ràng.

### Costs / Risks

- Transaction dài tăng lock contention.
- Cross-resource atomicity rất phức tạp.
- Outbox tăng component và operational work.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction nghĩa là commit/rollback như một đơn vị.

### Middle

Biết `SaveChanges()` thường đã có transaction và biết khi nào dùng explicit transaction.

### Senior

Nhận diện long transaction, lock contention, retry và external side-effect problem.

### Technical Lead / Architect

Định nghĩa consistency boundary: việc gì cần ACID, việc gì chấp nhận eventual consistency và khi nào cần Outbox/Saga.

## 11. Key takeaway

- Transaction nên bao quanh consistency requirement nhỏ nhất cần thiết.
- Đừng giữ DB transaction trong lúc chờ remote dependency nếu tránh được.
- Database atomicity không tự giải quyết external side effects.

# 4. SQL window functions: ranking, running totals và cách tránh query vòng lặp trong application

## 1. What is it?

Window functions tính toán trên một tập rows liên quan mà không collapse chúng như `GROUP BY`.

Ví dụ:

- `ROW_NUMBER()` để đánh số theo nhóm.
- `RANK()`/`DENSE_RANK()` để xếp hạng.
- `SUM(...) OVER(...)` để running total.
- `LAG()`/`LEAD()` để so sánh row trước/sau.

Mental model: mỗi row vẫn được giữ, nhưng có thêm giá trị tính trên “window” của nó.

## 2. Why does it exist?

Nhiều developer kéo dữ liệu về C# rồi group/sort/loop để tìm “latest per customer”, “top 3 per category” hoặc running total. Điều đó tăng round trips, network transfer và allocations.

Window functions cho phép database xử lý tập dữ liệu set-based, thường hiệu quả và biểu đạt intent rõ hơn.

## 3. How does it work?

Ví dụ lấy order mới nhất mỗi customer:

```sql
WITH RankedOrders AS
(
    SELECT
        Id,
        CustomerId,
        CreatedAt,
        Total,
        ROW_NUMBER() OVER
        (
            PARTITION BY CustomerId
            ORDER BY CreatedAt DESC, Id DESC
        ) AS rn
    FROM Orders
)
SELECT Id, CustomerId, CreatedAt, Total
FROM RankedOrders
WHERE rn = 1;
```

`PARTITION BY` chia logical groups; `ORDER BY` xác định thứ tự trong mỗi group.

## 4. Practical implementation

Running total doanh thu:

```sql
SELECT
    OrderDate,
    Revenue,
    SUM(Revenue) OVER
    (
        ORDER BY OrderDate
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS RunningRevenue
FROM DailyRevenue
ORDER BY OrderDate;
```

So sánh với ngày trước:

```sql
SELECT
    OrderDate,
    Revenue,
    LAG(Revenue) OVER (ORDER BY OrderDate) AS PreviousRevenue
FROM DailyRevenue;
```

## 5. Real production scenario

Dashboard CRM cần top 3 opportunities theo từng sales owner. Cách naive là lấy toàn bộ opportunities về C#, group theo owner rồi sort từng group.

Với hàng triệu rows, network và memory tăng mạnh. Window function cho phép database trả đúng top rows cần thiết.

## 6. Failure scenario & troubleshooting

**Symptom**  
Query window function vẫn chậm dù trả ít rows.

**Evidence**  
Execution plan có large sort hoặc spill to temp storage.

**Hypothesis**  
Partition/order columns không được hỗ trợ tốt bởi index hoặc dataset quá lớn.

**Diagnosis**  
Đọc execution plan, sort cost, memory grant, logical reads.

**Fix**  
Tối ưu access pattern/index, filter sớm hơn, giảm dataset trước window computation khi semantics cho phép.

**Verification**  
So sánh elapsed time, logical reads và spill warnings.

## 7. Common mistakes

- Dùng window functions nhưng không hiểu `PARTITION BY`.
- Sort không deterministic khi tie values.
- Dùng `ROW_NUMBER()` rồi vẫn trả toàn dataset về app để filter tiếp.
- Tạo index chỉ vì query chậm mà không đọc execution plan.
- Nhầm `RANK()` với `ROW_NUMBER()` khi có ties.

## 8. Alternatives

- `GROUP BY` phù hợp khi cần collapse rows thành aggregate.
- Correlated subquery đôi khi đủ cho query nhỏ nhưng có thể khó tối ưu.
- Materialized/reporting tables phù hợp cho analytics nặng lặp lại thường xuyên.

## 9. Trade-offs

### Advantages

- Set-based, expressive.
- Giảm data transfer về application.
- Xử lý ranking/time-series tốt.

### Costs / Risks

- Có thể cần sort lớn.
- Execution plan phức tạp hơn query đơn giản.
- Developer phải hiểu tie behavior và frame semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu window function không giống `GROUP BY`: rows không bị collapse.

### Middle

Biết dùng `ROW_NUMBER`, `LAG`, running totals cho use case thực tế.

### Senior

Đọc execution plan, sort/spill behavior và index implications.

### Technical Lead / Architect

Quyết định computation nên chạy transactional DB, reporting DB hay analytics pipeline dựa trên workload.

## 11. Key takeaway

- Đừng kéo dữ liệu về C# chỉ để làm ranking mà SQL xử lý tốt hơn.
- Window functions mạnh nhưng có thể tốn sort/memory.
- Execution plan vẫn là bằng chứng chính khi performance có vấn đề.

# 5. Elasticsearch reindexing với aliases và eventual consistency khi search index lệch source of truth

## 1. What is it?

Elasticsearch index thường là read-optimized/search representation, không phải transactional source of truth.

Reindexing là tạo lại index khi mapping/analyzer/schema hoặc dữ liệu cần thay đổi. Alias là tên logical trỏ tới physical index, cho phép đổi từ index cũ sang index mới mà API không cần đổi endpoint/index name.

## 2. Why does it exist?

Một mapping quan trọng không phải lúc nào cũng sửa in-place an toàn. Ví dụ đổi analyzer của `ProductName` từ standard analyzer sang custom analyzer có thể yêu cầu rebuild index.

Nếu API gắn cứng vào `products-v1`, deployment sẽ khó. Alias như `products-read` tạo abstraction cho read side.

## 3. How does it work?

```text
Primary DB
   |
   v
Sync pipeline
   |
   +--> products-v1

Reindex:
products-v1 ---> products-v2
                     |
                     v
Alias switch: products-read -> products-v2
```

Một flow production thường gồm:

1. tạo `products-v2` với mapping mới,
2. backfill dữ liệu,
3. sync delta thay đổi trong lúc backfill,
4. validate count/query behavior,
5. atomically switch alias,
6. giữ index cũ trong thời gian rollback window.

## 4. Practical implementation

Alias switch ví dụ:

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v1", "alias": "products-read" } },
    { "add":    { "index": "products-v2", "alias": "products-read" } }
  ]
}
```

Search API luôn query `products-read`, không cần biết physical index version.

## 5. Real production scenario

E-commerce site đổi search requirement để hỗ trợ accent normalization và autocomplete tốt hơn. Analyzer mới đòi reindex toàn catalog.

Catalog có vài triệu products, backfill mất thời gian. Trong lúc đó product price/status vẫn thay đổi ở SQL. Nếu chỉ copy snapshot rồi switch alias, index mới có thể stale ngay khi cutover.

## 6. Failure scenario & troubleshooting

**Symptom**  
Sau alias switch, search trả product đã bị disable hoặc thiếu product vừa update.

**Evidence**  
SQL state mới hơn Elasticsearch `_source`; event backlog tăng trong thời gian reindex.

**Hypothesis**  
Backfill không kết hợp delta synchronization đúng.

**Diagnosis**  
So sánh source-of-truth timestamps/version, queue offsets và indexing failures.

**Fix**  
Thiết kế backfill + delta replay, checkpoint và idempotent indexing.

**Verification**  
Sampling reconciliation, document count, version checks và user-facing search tests.

## 7. Common mistakes

- Dùng Elasticsearch làm source of truth cho transactional state.
- Reindex trực tiếp production alias mà không rollback plan.
- Không xử lý changes xảy ra trong lúc backfill.
- Không monitor indexing failures/dead-letter.
- Assume document count bằng nhau nghĩa là data hoàn toàn consistent.

## 8. Alternatives

- Update mapping in-place chỉ khi Elasticsearch cho phép và semantics không đổi dữ liệu đã index.
- Blue/Green indices với aliases cho migration lớn.
- SQL full-text search có thể đủ nếu requirement search đơn giản hơn, giảm operational complexity.

## 9. Trade-offs

### Advantages

- Alias giúp zero/low-downtime cutover.
- Reindex cho phép thay đổi search model an toàn hơn.
- Rollback dễ hơn nếu giữ index cũ.

### Costs / Risks

- Cần double storage tạm thời.
- Backfill có thể tốn cluster resources.
- Eventual consistency và delta sync phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Elasticsearch index là derived read model trong nhiều kiến trúc.

### Middle

Biết mappings, aliases và basic reindex flow.

### Senior

Thiết kế backfill + delta, reconciliation và failure recovery.

### Technical Lead / Architect

Quyết định Elasticsearch có thực sự cần thiết, ownership của sync pipeline và consistency SLA với primary database.

## 11. Key takeaway

- Alias giúp tách logical search contract khỏi physical index version.
- Reindex không chỉ là copy dữ liệu; cần xử lý concurrent changes.
- Search index thường nên là derived state, không phải transactional truth.

# 6. DDD Aggregate Root: invariants, transaction boundary và tránh Aggregate quá lớn

## 1. What is it?

Trong Domain-Driven Design, Aggregate là một consistency boundary gồm các domain objects phải thay đổi theo invariants chung. Aggregate Root là entry point để external code tương tác với Aggregate.

Điểm cốt lõi không phải “Entity có Repository”, mà là: business rules nào phải luôn đúng trong một transaction?

Ví dụ `Order` có thể là Aggregate Root, còn `OrderLine` nằm bên trong Aggregate nếu quantity/price rules phải được bảo vệ thông qua `Order`.

## 2. Why does it exist?

Nếu mọi object được update tự do từ mọi nơi, business invariants dễ bị phá.

Ví dụ Order không được chuyển thành `Shipped` nếu chưa `Paid`. Nếu controller trực tiếp set status fields, rule có thể bị bypass ở nhiều code path.

Aggregate tập trung invariants và tạo transaction boundary có chủ đích.

## 3. How does it work?

```text
Application Service
      |
      v
Order Aggregate Root
  |       |
  |       +--> OrderLine
  |
  +--> enforce invariants
      |
      v
single transaction boundary
```

Domain method:

```csharp
public sealed class Order
{
    public OrderStatus Status { get; private set; }

    public void Ship()
    {
        if (Status != OrderStatus.Paid)
        {
            throw new DomainException(
                "Only paid orders can be shipped.");
        }

        Status = OrderStatus.Shipped;
    }
}
```

## 4. Practical implementation

Application layer:

```csharp
public async Task ShipOrderAsync(
    Guid orderId,
    CancellationToken cancellationToken)
{
    var order = await db.Orders
        .SingleAsync(x => x.Id == orderId, cancellationToken);

    order.Ship();

    await db.SaveChangesAsync(cancellationToken);
}
```

Business invariant nằm trong domain model, còn orchestration/persistence ở application/infrastructure boundary.

## 5. Real production scenario

Một approval workflow có `Request`, `Approvers`, `ApprovalSteps`, `Attachments`. Team gom tất cả thành một Aggregate duy nhất và `Include` toàn graph cho mọi command.

Khi graph lớn dần, mỗi update phải load quá nhiều data, lock/optimistic concurrency conflicts tăng và aggregate trở thành bottleneck.

## 6. Failure scenario & troubleshooting

**Symptom**  
Command đơn giản load hàng nghìn related rows và conflict concurrency cao.

**Evidence**  
Generated SQL lớn, tracking graph lớn, nhiều updates tranh cùng aggregate version.

**Hypothesis**  
Aggregate boundary quá rộng.

**Diagnosis**  
Hỏi invariant nào thực sự cần atomicity; phần nào có thể eventual consistent.

**Fix**  
Tách Aggregate theo consistency requirement; giao tiếp qua ID/domain event khi thích hợp.

**Verification**  
Command load ít state hơn, transaction ngắn hơn nhưng business invariants vẫn được bảo vệ.

## 7. Common mistakes

- Aggregate = toàn bộ object graph có foreign key.
- Một Repository cho mọi Entity dù Entity không phải Aggregate Root.
- Domain model chỉ chứa getter/setter, business logic vẫn ở service.
- Aggregate gọi external API trực tiếp.
- Dùng domain events như message broker contract một cách máy móc.
- Tạo Aggregate lớn để “đảm bảo consistency” mà không tính scalability.

## 8. Alternatives

CRUD-heavy module có thể không cần rich domain model. Application service + validation đơn giản có thể đủ.

DDD Aggregate hữu ích khi business invariants thực sự phức tạp và cần được bảo vệ nhất quán.

## 9. Trade-offs

### Advantages

- Business rules tập trung.
- Transaction boundary rõ.
- Giảm khả năng bypass invariants.

### Costs / Risks

- Modeling đòi hỏi hiểu domain sâu.
- Aggregate quá lớn gây performance/concurrency issues.
- Rich domain model không đáng giá cho CRUD đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Entity không chỉ là database row; domain object có thể bảo vệ rule.

### Middle

Biết implement methods bảo vệ invariant thay vì public setters.

### Senior

Biết xác định Aggregate boundary theo consistency requirement và concurrency behavior.

### Technical Lead / Architect

Quyết định module nào cần DDD, Aggregate nào nên nhỏ, và consistency nào có thể chuyển sang event-driven workflow.

## 11. Key takeaway

- Aggregate là consistency boundary, không phải navigation-property boundary.
- Aggregate càng lớn, transaction/concurrency cost càng cao.
- Chỉ dùng rich DDD nơi business complexity thực sự justify nó.

# 7. Azure Functions vs Worker Service cho scheduled/background work và bài toán duplicate execution

## 1. What is it?

Azure Functions và .NET Worker Service đều có thể xử lý background/scheduled work, nhưng operational model khác nhau.

- Azure Functions cung cấp managed triggers, scaling và serverless execution model.
- Worker Service là long-running process do bạn host trên App Service, Container Apps, VM, Kubernetes hoặc Windows Service.

Điểm quan trọng: “job chạy mỗi 5 phút” không tự động có nghĩa là chỉ chạy đúng một instance một lần trong distributed deployment.

## 2. Why does it exist?

Background work cần lifecycle riêng khỏi HTTP request: scheduled cleanup, queue consumption, file processing, notification, sync external systems.

Nếu nhét long-running job vào web request hoặc `Task.Run` fire-and-forget, process restart có thể làm mất việc và không có retry/visibility tốt.

## 3. How does it work?

Worker Service:

```text
Process starts
   |
   v
BackgroundService.ExecuteAsync
   |
   +--> loop / timer / queue consumer
```

Azure Functions:

```text
Trigger
  |
  v
Function invocation
  |
  +--> managed host handles scale/retry semantics
```

Scheduled work trong multi-instance environment cần hiểu coordination semantics của hosting platform.

## 4. Practical implementation

Worker Service dùng `PeriodicTimer`:

```csharp
public sealed class CleanupWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public CleanupWorker(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5));

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            using var scope = _scopeFactory.CreateScope();
            var job = scope.ServiceProvider
                .GetRequiredService<ICleanupJob>();

            await job.RunAsync(stoppingToken);
        }
    }
}
```

Code này chưa giải quyết duplicate execution nếu application scale ra nhiều replicas.

## 5. Real production scenario

Một App Service chạy 4 instances. Mỗi instance host cùng `BackgroundService` có timer 01:00 hàng ngày. Kết quả: cleanup job chạy 4 lần.

Nếu job gửi invoices hoặc charge payment, duplicate execution trở thành correctness incident.

## 6. Failure scenario & troubleshooting

**Symptom**  
Một scheduled operation xuất hiện nhiều audit records cùng timestamp.

**Evidence**  
Logs có cùng job name nhưng khác instance IDs.

**Hypothesis**  
Mỗi replica tự chạy local timer.

**Diagnosis**  
Kiểm tra deployment replica count và scheduler ownership.

**Fix**  
Chọn một distributed scheduler/trigger phù hợp, queue-based dispatch, leader election hoặc distributed lock nếu thật sự cần. Đồng thời làm job idempotent.

**Verification**  
Scale replicas lên/xuống và xác nhận business effect chỉ xảy ra một lần hoặc duplicate được xử lý an toàn.

## 7. Common mistakes

- `BackgroundService` timer trong multi-instance app nhưng giả định singleton toàn cluster.
- Fire-and-forget task từ controller.
- Không truyền `CancellationToken` khi shutdown.
- Job không idempotent.
- Distributed lock không có timeout/lease semantics rõ.
- Chọn Azure Functions chỉ vì “serverless rẻ hơn” mà không tính cold start, execution profile và ops model.

## 8. Alternatives

- Azure Functions Timer Trigger cho managed scheduling.
- Queue + consumer cho reliable dispatch.
- Worker Service khi process cần long-running stateful connection hoặc custom control.
- Logic Apps khi workflow integration thiên về orchestration hơn code-heavy processing.

## 9. Trade-offs

### Advantages

Azure Functions giảm infrastructure management và tích hợp trigger tốt. Worker Service cho control cao và phù hợp continuous workload.

### Costs / Risks

Functions có platform semantics/cost model riêng. Worker Service yêu cầu bạn sở hữu deployment, scaling, health và scheduling correctness nhiều hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu background work không nên giả định sống cùng HTTP request.

### Middle

Biết implement `BackgroundService`, scope và cancellation đúng.

### Senior

Biết duplicate execution, retry, shutdown, idempotency và multi-instance behavior.

### Technical Lead / Architect

Chọn Functions, Worker, queue hoặc orchestration platform dựa trên reliability, scale, cost và ownership.

## 11. Key takeaway

- Local timer không phải distributed scheduler.
- Multi-instance deployment thay đổi correctness của scheduled jobs.
- Idempotency vẫn cần dù platform cố gắng đảm bảo scheduling.

# 8. IIS Application Pool recycling, ASP.NET Core hosting và graceful shutdown trong production

## 1. What is it?

Khi ASP.NET Core chạy sau IIS, IIS đóng vai trò web server/reverse-proxy integration layer còn application thường chạy trong process model do ASP.NET Core Module quản lý.

Application Pool recycling là việc worker process được restart theo cấu hình hoặc operational event. Với developer, điều quan trọng là hiểu process có thể restart hợp lệ ngay cả khi code không crash.

## 2. Why does it exist?

Long-running server process cần lifecycle management: deployment, config change, health recovery, memory limits, scheduled recycle hoặc infrastructure maintenance.

Ứng dụng production phải giả định process không sống vĩnh viễn. Vì vậy state quan trọng không nên chỉ nằm trong memory và background work cần hỗ trợ graceful shutdown.

## 3. How does it work?

```text
Client
  |
  v
IIS
  |
  v
ASP.NET Core application process
  |
  +--> receives shutdown signal
  |
  +--> stop accepting/finish work within grace period
  |
  v
process exits / replacement starts
```

`IHostApplicationLifetime` và `CancellationToken` giúp components phản ứng với shutdown.

## 4. Practical implementation

Background worker:

```csharp
protected override async Task ExecuteAsync(
    CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        var message = await queue.ReceiveAsync(stoppingToken);

        await ProcessAsync(message, stoppingToken);
    }
}
```

Không nên bỏ qua token:

```csharp
await ProcessAsync(message, CancellationToken.None);
```

Nếu shutdown xảy ra, operation có thể kéo dài ngoài grace window và bị terminate giữa chừng.

## 5. Real production scenario

Một legacy enterprise app chạy IIS + ASP.NET Core và giữ session/business cache chỉ trong memory. Sau scheduled recycle, users bị mất state hoặc background sync đang chạy bị cắt giữa chừng.

Vấn đề không phải “IIS recycle lỗi”, mà application đã coi process memory như durable state.

## 6. Failure scenario & troubleshooting

**Symptom**  
Ứng dụng restart vào thời điểm gần cố định, background job dừng giữa chừng.

**Evidence**  
Windows Event Logs/IIS logs cho thấy App Pool recycle; application logs có shutdown event.

**Hypothesis**  
Operational recycle hoặc deployment lifecycle.

**Diagnosis**  
Kiểm tra App Pool settings, deployment history, process logs và hosting configuration.

**Fix**  
Loại bỏ durable state khỏi process memory, làm background work resumable/idempotent, honor shutdown token.

**Verification**  
Trigger controlled recycle và quan sát request drain/job recovery.

## 7. Common mistakes

- Lưu critical workflow state trong static memory.
- Không log startup/shutdown events.
- Background thread tự tạo không gắn host lifecycle.
- Assume restart luôn là crash.
- Deployment copy file trực tiếp gây inconsistent application state.
- Không phân biệt IIS issue với application startup failure.

## 8. Alternatives

Azure App Service abstractions giảm một phần IIS administration nhưng process restart vẫn tồn tại. Containers/Kubernetes có lifecycle khác nhưng cùng nguyên tắc: process ephemeral, cần graceful termination và externalized state.

## 9. Trade-offs

### Advantages

- IIS là mature hosting platform cho Windows enterprise environments.
- Có process management, bindings, TLS integration và operational tooling quen thuộc.

### Costs / Risks

- Lifecycle settings có thể khó hiểu nếu team chỉ biết application code.
- In-memory assumptions dễ vỡ khi recycle/scale-out.
- Legacy deployment processes có thể gây downtime nếu không thiết kế tốt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu web app process có thể restart và memory không durable.

### Middle

Biết đọc IIS/App Pool logs và implement cancellation/graceful shutdown.

### Senior

Debug recycle, startup failure, permission/binding/process issues và background work interruption.

### Technical Lead / Architect

Quyết định hosting strategy, externalized state, deployment model và operational runbook cho Windows/IIS workloads.

## 11. Key takeaway

- Process restart là normal operational event cần được thiết kế cho.
- Durable state không nên phụ thuộc một App Pool process.
- Background work phải hỗ trợ cancellation, retry và recovery.

# 9. Integration testing với real infrastructure: Testcontainers, database isolation và giới hạn của mocking

## 1. What is it?

Integration test kiểm tra nhiều components thật cùng hoạt động: application code + database/provider + serialization + middleware + external protocol boundary giả lập hoặc thật có kiểm soát.

Testcontainers là một cách chạy dependency thật như PostgreSQL, SQL Server-compatible container, Redis hoặc RabbitMQ trong test environment.

Mental model: mock kiểm tra interaction assumptions; integration test kiểm tra contract với infrastructure thật.

## 2. Why does it exist?

Repository mock không thể chứng minh LINQ query được EF Core translate đúng, migration chạy được hoặc isolation/constraint semantics đúng như production database.

Một unit test xanh có thể vẫn deploy ra SQL sai.

## 3. How does it work?

```text
Test process
   |
   +--> start disposable DB container
   |
   +--> apply migrations
   |
   +--> run application/test
   |
   +--> assert real persisted result
   |
   +--> destroy container
```

Mục tiêu là môi trường deterministic và isolated enough để tests không ảnh hưởng nhau.

## 4. Practical implementation

Ví dụ conceptual setup với Testcontainers for .NET:

```csharp
public sealed class DatabaseFixture : IAsyncLifetime

    private readonly PostgreSqlContainer _db =
        new PostgreSqlBuilder()
            .WithDatabase("tests")
            .WithUsername("postgres")
            .WithPassword("postgres")
            .Build();

    public Task InitializeAsync() => _db.StartAsync();

    public Task DisposeAsync() => _db.DisposeAsync().AsTask();
}
```

Sau đó application test dùng đúng EF Core provider như production.

## 5. Real production scenario

Một query dùng method C# không translate được với provider production. Unit test dùng in-memory collection pass vì LINQ-to-Objects chạy được. Production endpoint fail khi EF Core translate query.

Integration test với real provider bắt lỗi trước deployment.

## 6. Failure scenario & troubleshooting

**Symptom**  
Integration tests flaky khi chạy parallel CI.

**Evidence**  
Tests dùng chung rows/database schema và cleanup phụ thuộc order.

**Hypothesis**  
Test data isolation kém.

**Diagnosis**  
Review shared state, transaction usage, unique identifiers và cleanup strategy.

**Fix**  
Per-test schema/database khi cần, deterministic seeding, transaction rollback hoặc reset strategy phù hợp.

**Verification**  
Chạy tests lặp lại/parallel nhiều lần.

## 7. Common mistakes

- Mock `DbSet` để mô phỏng mọi EF Core behavior.
- Dùng SQLite/InMemory rồi giả định semantics giống SQL Server/PostgreSQL hoàn toàn.
- Integration test phụ thuộc data có sẵn ngoài test.
- Tests quá rộng tới mức lỗi rất khó localize.
- Dùng container cho mọi unit test nhỏ khiến suite chậm không cần thiết.
- Chạy E2E cho logic có thể kiểm tra bằng unit/integration test rẻ hơn.

## 8. Alternatives

- Unit tests cho pure business rules.
- Integration tests cho persistence/API contracts.
- Contract tests cho boundaries giữa services.
- E2E/Playwright cho critical user journeys.

Không có một loại test thay thế tất cả loại còn lại.

## 9. Trade-offs

### Advantages

- Phát hiện provider/schema/config bugs thật.
- Confidence cao hơn cho migrations và queries.
- Giảm false confidence từ mocks.

### Costs / Risks

- Chậm hơn unit tests.
- CI cần Docker/container support.
- Isolation và fixture management phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu unit test và integration test bảo vệ rủi ro khác nhau.

### Middle

Biết viết integration tests với DB thật và deterministic data.

### Senior

Thiết kế test boundaries, isolation, CI parallelism và tránh mocking sai abstraction.

### Technical Lead / Architect

Xây test strategy dựa trên risk: business rules, persistence, contracts, critical journeys và deployment confidence.

## 11. Key takeaway

- Mock không chứng minh database/provider thật hoạt động đúng.
- Integration test nên tập trung vào boundary có rủi ro thật.
- Test strategy tốt tối ưu confidence, không tối ưu coverage percentage.

# 10. Third-party API resilience: timeout budget, retry amplification, Circuit Breaker và idempotency

## 1. What is it?

Một remote dependency sẽ có lúc chậm, timeout hoặc fail. Resilience không phải chỉ là “thêm retry”, mà là quản lý failure propagation.

Bốn khái niệm cần kết nối:

- Timeout: giới hạn thời gian chờ.
- Retry: thử lại failure có khả năng transient.
- Circuit Breaker: tạm ngừng call khi dependency đang fail liên tục.
- Idempotency: retry không tạo business effect lặp.

Timeout budget là tổng thời gian request có thể chịu, không phải timeout độc lập tùy ý ở từng layer.

## 2. Why does it exist?

Nếu API A có request timeout 5 giây nhưng nó gọi B với timeout 10 giây, budget đã vô nghĩa. Nếu A retry 3 lần, B cũng retry 3 lần và database driver retry tiếp, một request user có thể khuếch đại thành nhiều calls downstream.

Đây là retry amplification.

## 3. How does it work?

Ví dụ budget:

```text
Client timeout: 3s
   |
   v
API processing budget: 2.5s
   |
   +--> dependency timeout: 700ms
   +--> at most one safe retry + jitter
```

Circuit Breaker state:

```text
Closed -> failures exceed threshold -> Open
Open   -> fail fast for cooldown
Half-open -> probe dependency
```

## 4. Practical implementation

Với modern .NET resilience pipeline, intent có thể được cấu hình qua `HttpClientFactory`/resilience handlers. Dù library cụ thể thay đổi theo version, policy design vẫn phải rõ.

Ví dụ business-level idempotency key:

```csharp
using var request = new HttpRequestMessage(
    HttpMethod.Post,
    "payments");

request.Headers.Add("Idempotency-Key", operationId.ToString());
request.Content = JsonContent.Create(payload);

var response = await httpClient.SendAsync(
    request,
    cancellationToken);
```

Retry POST chỉ an toàn nếu remote contract hỗ trợ idempotency hoặc operation bản chất idempotent.

## 5. Real production scenario

Checkout API gọi payment provider. Provider xử lý payment thành công nhưng response timeout trước khi client nhận được.

Application retry POST mà không có idempotency key. Payment bị charge hai lần.

Ở đây “retry tăng reliability” đã trực tiếp phá correctness.

## 6. Failure scenario & troubleshooting

**Symptom**  
Khi third-party chậm, request volume outbound tăng thay vì giảm và toàn API latency tăng mạnh.

**Evidence**  
Dependency telemetry cho thấy nhiều retries trên cùng correlation/operation ID; outbound rate tăng trong incident.

**Hypothesis**  
Retry storm/amplification.

**Diagnosis**  
Trace policy ở từng layer: application, SDK, proxy, database/client library.

**Fix**  
Giảm retry layers, đặt timeout budget, dùng exponential backoff + jitter, Circuit Breaker, idempotency và fallback khi business cho phép.

**Verification**  
Fault injection: delay/500/connection reset; đo outbound calls per inbound request và p95/p99.

## 7. Common mistakes

- Retry mọi 4xx/5xx.
- Retry POST không idempotent.
- Timeout quá dài nên request threads/tasks treo chờ.
- Timeout từng dependency cộng lại vượt request SLA.
- Circuit Breaker dùng để “che lỗi” thay vì fail fast có kiểm soát.
- Không log attempt count/correlation ID.
- Nhiều layers retry độc lập.

## 8. Alternatives

- Fail fast nếu dependency không critical và có fallback.
- Queue asynchronous workflow nếu user không cần synchronous result.
- Cache last-known-good data nếu freshness cho phép.
- Bulkhead/concurrency limit để dependency chậm không chiếm toàn resource pool.

## 9. Trade-offs

### Advantages

- Timeout/circuit breaker giới hạn failure propagation.
- Retry đúng chỗ cải thiện transient reliability.
- Idempotency bảo vệ correctness khi retry.

### Costs / Risks

- Resilience policy tăng behavioral complexity.
- Retry làm tăng load lúc dependency đang yếu.
- Fallback có thể trả stale/degraded data và cần business acceptance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu network call có thể fail/timeout và không nên chờ vô hạn.

### Middle

Biết cấu hình timeout/retry cơ bản và truyền `CancellationToken`.

### Senior

Thiết kế timeout budget, retry classification, jitter, idempotency và observability.

### Technical Lead / Architect

Quyết định dependency nào synchronous, fallback nào được phép, SLA propagation ra sao và team nào sở hữu failure policy.

## 11. Key takeaway

- Retry không mặc định làm hệ thống reliable hơn.
- Timeout phải được thiết kế theo end-to-end budget.
- Idempotency là điều kiện quan trọng cho safe retry của business operations.
- Khi dependency yếu, hệ thống tốt thường giảm pressure chứ không khuếch đại nó.
