# 1. C# source generators: chuyển reflection cost sang compile time mà không đánh đổi maintainability

## 1. What is it?

Source generator là compiler extension chạy trong quá trình build để phân tích source code/metadata rồi sinh thêm C# source trước khi compilation hoàn tất.

Mental model:

```text
Your source
   ↓
Roslyn compilation
   ↓
Source Generator inspects symbols
   ↓
Generated .cs source
   ↓
Final compilation
```

Khác với runtime reflection, generator có thể biết trước type/member structure ngay lúc build.

## 2. Why does it exist?

Nhiều framework/library từng dựa mạnh vào reflection để tìm handlers, serializers, mapping metadata hoặc registrations. Reflection linh hoạt nhưng có chi phí runtime, khó trimming/AOT và lỗi cấu hình thường chỉ lộ khi application chạy.

Source generation chuyển một phần công việc sang compile time, giúp giảm runtime discovery và có thể phát hiện sai sót sớm hơn.

## 3. How does it work?

Generator nhận `Compilation` và symbols từ Roslyn. Incremental generators còn cho phép pipeline chỉ recompute phần bị ảnh hưởng khi source đổi.

Ví dụ mental flow:

```text
Find classes with [GenerateMapper]
        ↓
Read source/target properties
        ↓
Generate strongly typed Map(...)
        ↓
Compiler type-checks generated code
```

Generator không nên phụ thuộc vào runtime state, database hay network. Build phải deterministic.

## 4. Practical implementation

Một generator thực tế có thể tạo serializer metadata hoặc registration code. Ở application side, developer thường chỉ dùng output:

```csharp
[JsonSerializable(typeof(OrderDto))]
[JsonSerializable(typeof(List<OrderDto>))]
internal partial class AppJsonContext : JsonSerializerContext
{
}
```

Sau đó:

```csharp
var json = JsonSerializer.Serialize(order, AppJsonContext.Default.OrderDto);
```

`System.Text.Json` source generation tránh một phần runtime metadata discovery và phù hợp với Native AOT hơn reflection-heavy serialization.

## 5. Real production scenario

Một API xử lý hàng chục nghìn messages/giây và serialize các DTO lặp lại liên tục. Runtime reflection không phải bottleneck duy nhất, nhưng profiler cho thấy metadata discovery/allocation có contribution đáng kể. Chuyển serializer metadata sang source generation giúp giảm startup/runtime overhead và làm AOT deployment khả thi hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → build chậm bất thường hoặc IntelliSense lag sau khi thêm custom generator.

**Evidence** → compiler timing cho thấy generator chạy lại trên nhiều files dù chỉ sửa một class.

**Hypothesis** → generator không incremental hoặc pipeline phụ thuộc quá rộng vào toàn bộ compilation.

**Diagnosis** → profile generator, kiểm tra inputs nào invalidation pipeline và tránh enumerate toàn solution không cần thiết.

**Fix** → dùng `IIncrementalGenerator`, thu hẹp syntax filters, cache intermediate transforms và giữ output deterministic.

**Verification** → đo clean build và incremental build trước/sau; sửa một file nhỏ phải không trigger toàn bộ generation path.

## 7. Common mistakes

* Dùng generator để thay thế logic runtime vốn phụ thuộc configuration động.
* Generate lượng code khổng lồ khó debug.
* Đọc file/network không deterministic trong build.
* Giấu quá nhiều business logic trong generated code.
* Dùng source generation chỉ vì “nhanh hơn reflection” mà không benchmark.

## 8. Alternatives

Reflection đơn giản hơn cho plugin-style runtime discovery. Hand-written code rõ nhất khi scope nhỏ. Expression trees phù hợp runtime code generation trong một số mapping/query scenarios. Source generator phù hợp khi metadata đã biết tại compile time và runtime overhead hoặc AOT thực sự quan trọng.

## 9. Trade-offs

### Advantages

* Giảm runtime reflection/discovery.
* Có thể hỗ trợ trimming và Native AOT tốt hơn.
* Một số lỗi xuất hiện ở build time.

### Costs / Risks

* Build pipeline phức tạp hơn.
* Debugging generator khó hơn application code.
* Generated API có thể làm developer experience khó hiểu nếu naming/output không rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu generator sinh source ở compile time, không phải magic runtime.

### Middle

Biết dùng generated APIs và inspect generated source khi debug.

### Senior

Đánh giá runtime benefit, build cost, incremental behavior và AOT implications.

### Technical Lead / Architect

Quyết định khi nào compile-time generation đáng thêm tooling complexity và đặt boundary để business logic không bị chôn trong codegen.

## 11. Key takeaway

* Source generator đổi runtime work thành compile-time work.
* Chỉ nên dùng khi metadata đã biết trước và lợi ích đo được.
* Incremental build performance là một phần của production-grade developer tooling.

# 2. ASP.NET Core rate limiting: bảo vệ tài nguyên theo workload thay vì chỉ chặn request theo IP

## 1. What is it?

Rate limiting kiểm soát số lượng operations được phép trong một khoảng thời gian hoặc mức concurrency nhất định.

Mental model:

```text
Incoming requests
      ↓
Partition key / policy
      ↓
Limiter
  ├─ allow
  └─ reject / queue
```

Điểm quan trọng là xác định đúng **resource đang cần bảo vệ** và **identity nào đang tiêu thụ resource đó**.

## 2. Why does it exist?

Một API có finite capacity: CPU, DB connections, external API quota, thread/connection pools. Nếu request tăng không kiểm soát, latency tăng trước khi error rate tăng và cuối cùng toàn hệ thống có thể collapse.

Chặn “100 request/phút/IP” chỉ là một policy đơn giản, không phù hợp mọi workload. Một enterprise tenant có thể hợp lệ khi gửi nhiều traffic hơn, còn một authenticated user có thể abuse từ nhiều IP.

## 3. How does it work?

ASP.NET Core hỗ trợ fixed window, sliding window, token bucket và concurrency limiter. Policy thường partition theo user, tenant, API key hoặc endpoint class.

Ví dụ:

```text
Tenant A → own limiter bucket
Tenant B → own limiter bucket
Anonymous → stricter shared policy
```

Rate limiting nên đứng đủ sớm trong request pipeline để tránh expensive work trước khi reject.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("tenant-api", context =>
    {
        var tenantId = context.User.FindFirst("tenant_id")?.Value ?? "anonymous";

        return RateLimitPartition.GetTokenBucketLimiter(
            partitionKey: tenantId,
            factory: _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 50,
                ReplenishmentPeriod = TimeSpan.FromSeconds(10),
                QueueLimit = 0,
                AutoReplenishment = true
            });
    });
});

app.UseRateLimiter();
```

Endpoint có thể yêu cầu policy cụ thể thay vì áp một policy cho mọi route.

## 5. Real production scenario

Một SaaS report endpoint chạy query nặng. Traffic bình thường thấp nhưng một tenant chạy script polling liên tục. CPU chưa cao ngay, nhưng SQL connection pool bão hòa và toàn bộ API bắt đầu timeout. Partitioned rate limit theo tenant bảo vệ shared database tốt hơn global IP limit.

## 6. Failure scenario & troubleshooting

**Symptom** → legitimate customers nhận `429` dù tổng traffic không cao.

**Evidence** → nhiều users của cùng doanh nghiệp đi qua một corporate NAT IP.

**Hypothesis** → limiter partition theo IP đang gộp nhiều identities hợp lệ.

**Diagnosis** → log limiter policy, partition key, endpoint và rejection reason; không log token/secrets.

**Fix** → với authenticated traffic, partition theo tenant/user/API key phù hợp business model; giữ IP-based policy chủ yếu cho anonymous/edge protection.

**Verification** → load test nhiều users sau cùng NAT và một abusive tenant riêng biệt.

## 7. Common mistakes

* Dùng cùng threshold cho cheap GET và expensive export.
* Rate limit sau khi query DB đã chạy.
* Queue quá nhiều requests khiến latency chỉ bị dời sang hàng chờ.
* Không trả `Retry-After` hoặc error contract rõ ràng.
* Xem rate limiting là thay thế cho autoscaling hoặc capacity planning.

## 8. Alternatives

Concurrency limiter phù hợp khi muốn bảo vệ số operations đồng thời. API gateway/CDN/WAF có thể limit ở edge. Backpressure qua queue phù hợp asynchronous workloads. Autoscaling tăng capacity nhưng không ngăn một tenant chiếm toàn bộ capacity.

## 9. Trade-offs

### Advantages

* Bảo vệ shared resources.
* Cô lập noisy neighbor.
* Giảm failure amplification khi load spike.

### Costs / Risks

* Threshold sai gây false rejection.
* Distributed enforcement cần shared/edge strategy nếu nhiều instances.
* Per-identity state tăng operational complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `429 Too Many Requests` và basic limiter.

### Middle

Biết cấu hình policy theo endpoint/identity và test rejection behavior.

### Senior

Thiết kế partition key, thresholds và phối hợp với downstream capacity.

### Technical Lead / Architect

Xác định overload-control strategy xuyên CDN/gateway/app/database và fairness giữa tenants.

## 11. Key takeaway

* Rate limiting là capacity protection, không chỉ anti-abuse.
* Partition key phải phản ánh ownership/fairness của workload.
* Limit nên đặt trước expensive work và được thiết kế cùng SLO/capacity.

# 3. EF Core split queries: tránh Cartesian explosion nhưng hiểu rõ consistency và round-trip trade-off

## 1. What is it?

Split query cho phép EF Core tải một object graph bằng nhiều SQL queries thay vì một JOIN lớn.

Mental model:

```text
Single query:
Blog JOIN Posts JOIN Comments

Split query:
SELECT Blogs
SELECT Posts for Blogs
SELECT Comments for Posts
```

Mục tiêu chính là tránh duplication/cartesian explosion khi include nhiều collection relationships.

## 2. Why does it exist?

Một JOIN qua nhiều collections có thể nhân số rows rất nhanh. 100 orders × 20 lines × 5 discounts có thể trả hàng chục nghìn rows dù object graph thực tế nhỏ hơn nhiều. Network payload, materialization và memory tăng mạnh.

## 3. How does it work?

EF Core chạy base query rồi các queries tiếp theo để lấy related collections, sau đó fix-up graph ở client side.

```csharp
var orders = await db.Orders
    .Include(x => x.Lines)
    .ThenInclude(x => x.Discounts)
    .AsSplitQuery()
    .ToListAsync(ct);
```

Đổi lại, nhiều SQL commands nghĩa là nhiều round trips và dữ liệu có thể thay đổi giữa các queries nếu transaction isolation không giữ snapshot phù hợp.

## 4. Practical implementation

Không bật split query mù quáng cho toàn application. Đầu tiên inspect generated SQL và actual row counts:

```csharp
var query = db.Orders
    .Where(x => x.CustomerId == customerId)
    .Include(x => x.Lines)
    .Include(x => x.Payments);

var sql = query.ToQueryString();
```

Nếu payload bị row multiplication đáng kể, thử `AsSplitQuery()` rồi đo total latency, rows transferred và DB calls.

## 5. Real production scenario

Admin order-details page include `Lines`, `Payments`, `Shipments` và `Notes`. Single JOIN trả hàng chục nghìn duplicated rows cho một order lớn. App CPU và response latency tăng dù SQL execution riêng lẻ không quá chậm. Split query giảm payload/materialization đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → sau khi chuyển split query, một request đôi khi thấy parent và children không hoàn toàn cùng snapshot.

**Evidence** → concurrent update xảy ra giữa query thứ nhất và thứ hai.

**Hypothesis** → workload yêu cầu consistency mạnh hơn default isolation đang cung cấp.

**Diagnosis** → capture SQL sequence, transaction boundary và concurrent writer timeline.

**Fix** → nếu cần snapshot consistency, dùng transaction/isolation phù hợp hoặc projection/query shape khác; đừng mặc định tăng isolation cho mọi request.

**Verification** → concurrency test với writers chạy giữa các split statements.

## 7. Common mistakes

* Dùng `Include` cho mọi navigation rồi mới tối ưu.
* Không projection, kéo cả entity graph khi chỉ cần vài fields.
* Nghĩ split query luôn nhanh hơn.
* Bỏ qua extra round trips khi DB latency cao.
* Không xét consistency giữa statements.

## 8. Alternatives

Projection DTO thường tốt hơn nếu endpoint chỉ cần subset fields. Explicit separate queries cho phép control rõ hơn. Single query vẫn tốt khi graph nhỏ hoặc network round-trip đắt hơn duplication.

## 9. Trade-offs

### Advantages

* Giảm Cartesian explosion.
* Giảm duplicated transfer/materialization.

### Costs / Risks

* Nhiều database round trips.
* Snapshot consistency có thể phức tạp hơn.
* Query plan/latency profile thay đổi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` có thể tạo JOIN lớn.

### Middle

Biết dùng `AsSplitQuery`, projection và inspect SQL.

### Senior

Đo row multiplication, round trips và consistency implications.

### Technical Lead / Architect

Đặt data-access guideline theo endpoint shape thay vì global toggle.

## 11. Key takeaway

* Split query chữa row explosion, không phải mọi slow include.
* Projection thường là lựa chọn đầu tiên cho read APIs.
* Performance decision phải tính cả network, DB round trips và consistency.

# 4. SQL Server keyset pagination: phân trang ổn định ở dataset lớn thay vì `OFFSET` ngày càng đắt

## 1. What is it?

Keyset pagination lấy “trang tiếp theo sau record cuối cùng đã thấy” thay vì bỏ qua N rows.

```text
OFFSET pagination:
page 5000 → skip 499,900 rows

Keyset pagination:
WHERE (CreatedAt, Id) < last_seen_key
```

## 2. Why does it exist?

`OFFSET ... FETCH` dễ dùng nhưng càng vào sâu, database vẫn phải locate/sort/skip lượng rows lớn. Dataset thay đổi giữa requests còn có thể gây duplicate/missing rows.

## 3. How does it work?

Cần deterministic ordering, thường gồm business sort key + unique tie-breaker.

```sql
SELECT TOP (100)
    Id, CreatedAt, Total
FROM Orders
WHERE
    CreatedAt < @LastCreatedAt
    OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index nên align với filter/order:

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON Orders (CreatedAt DESC, Id DESC)
INCLUDE (Total);
```

## 4. Practical implementation

API trả opaque cursor chứa `CreatedAt` + `Id`, được encode/sign nếu không muốn expose internal structure.

```json
{
  "items": [...],
  "nextCursor": "eyJjcmVhdGVkQXQiOi..."
}
```

Cursor nên versionable nếu query contract có thể đổi.

## 5. Real production scenario

Audit-log table có 200 triệu rows. Admin UI dùng `OFFSET 1000000 ROWS` và trang sâu mất vài giây. Chuyển sang keyset theo `(OccurredAt, Id)` giữ latency gần ổn định qua nhiều trang.

## 6. Failure scenario & troubleshooting

**Symptom** → một số rows bị lặp hoặc mất khi nhiều records có cùng timestamp.

**Evidence** → ordering chỉ dùng `CreatedAt`, không unique.

**Hypothesis** → cursor không có deterministic tie-breaker.

**Diagnosis** → tìm duplicate sort-key values và compare page boundaries.

**Fix** → thêm unique stable key như `Id` vào `ORDER BY` và cursor predicate.

**Verification** → insert concurrent rows có cùng timestamp trong khi paginate và kiểm tra sequence.

## 7. Common mistakes

* Cursor chỉ chứa timestamp không unique.
* Cho phép arbitrary sort columns nhưng không có index strategy.
* Dùng keyset khi UI bắt buộc nhảy trực tiếp tới page 937.
* Encode cursor nhưng không validate/tamper-protect khi chứa sensitive state.
* Không định nghĩa stable ordering khi rows được update.

## 8. Alternatives

`OFFSET/FETCH` vẫn ổn cho dataset nhỏ hoặc shallow pages. Search engines có `search_after`. Precomputed/reporting datasets phù hợp random page navigation trong analytical scenarios.

## 9. Trade-offs

### Advantages

* Latency ổn định hơn ở deep pagination.
* Ít scan/skip work.
* Tốt hơn dưới concurrent inserts.

### Costs / Risks

* Không hỗ trợ random page number tự nhiên.
* Cursor contract phức tạp hơn.
* Index phải phù hợp ordering.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `OFFSET` phải bỏ qua rows trước đó.

### Middle

Viết keyset predicate với unique tie-breaker.

### Senior

Thiết kế cursor, index và concurrency semantics.

### Technical Lead / Architect

Chọn UX/API pagination model dựa trên scale và navigation requirements.

## 11. Key takeaway

* Deep pagination là access-pattern problem, không chỉ syntax problem.
* Keyset cần deterministic order + aligned index.
* Nếu product yêu cầu random page jumps, phải chấp nhận trade-off hoặc đổi UX/data strategy.

# 5. Elasticsearch analyzers: vì sao mapping đúng nhưng search vẫn sai do tokenization và normalization

## 1. What is it?

Analyzer biến text thành tokens khi index và query. Nó thường gồm character filters, tokenizer và token filters.

```text
"ASP.NET-Core Guide"
      ↓ analyzer
["asp.net", "core", "guide"]
```

Search correctness phụ thuộc việc index-time và search-time analysis tương thích.

## 2. Why does it exist?

Full-text search không thể chỉ so sánh nguyên chuỗi. Người dùng muốn search không phân biệt hoa thường, từ gốc, dấu câu hoặc ngôn ngữ. Analyzer tạo representation phù hợp cho inverted index.

## 3. How does it work?

Field `text` được analyze; field `keyword` giữ exact value. Multi-fields rất phổ biến:

```json
"name": {
  "type": "text",
  "fields": {
    "raw": { "type": "keyword" }
  }
}
```

`name` phục vụ full-text; `name.raw` phục vụ sort/filter/aggregation exact.

## 4. Practical implementation

Dùng `_analyze` để inspect tokens trước khi đổ lỗi cho scoring:

```json
POST /products/_analyze
{
  "analyzer": "standard",
  "text": "C# Developer's Guide"
}
```

Nếu domain cần normalization riêng, define custom analyzer rõ ràng và version index thay vì đổi mapping trực tiếp trên live index.

## 5. Real production scenario

E-commerce search cho product codes như `AB-123-X`. Standard analyzer tách token khiến exact code lookup không ổn định. Team thêm `keyword` subfield cho exact lookup nhưng giữ analyzed field cho natural-language search.

## 6. Failure scenario & troubleshooting

**Symptom** → document tồn tại nhưng query phrase/product code không match.

**Evidence** → `_analyze` cho thấy index-side tokens khác expectation.

**Hypothesis** → analyzer/tokenizer làm mất hoặc tách domain-significant characters.

**Diagnosis** → compare index analyzer, search analyzer, mappings và actual tokens.

**Fix** → dùng field/analyzer phù hợp; reindex nếu mapping/analyzer index-time thay đổi.

**Verification** → regression corpus gồm exact code, typo, casing, punctuation và multilingual samples.

## 7. Common mistakes

* Dùng `text` cho sorting/aggregation.
* Dùng `keyword` cho full-text search.
* Thay analyzer rồi nghĩ existing documents tự được reprocessed.
* Tuning relevance trước khi inspect tokens.
* Một analyzer cho mọi languages/domain fields.

## 8. Alternatives

SQL full-text search có thể đủ cho nhu cầu đơn giản. Dedicated search SaaS giảm operational burden. Application-side normalization chỉ phù hợp exact lookup đơn giản, không thay inverted-index analysis.

## 9. Trade-offs

### Advantages

* Search phù hợp ngôn ngữ/domain hơn.
* Multi-fields hỗ trợ cả exact và full-text use cases.

### Costs / Risks

* Analyzer changes thường cần reindex.
* Custom chains tăng complexity và testing burden.
* Wrong analysis gây silent relevance bugs.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu text được tokenized chứ không lưu/search như raw string.

### Middle

Biết `text` vs `keyword` và dùng `_analyze`.

### Senior

Thiết kế analyzer theo domain, test corpus và reindex strategy.

### Technical Lead / Architect

Quyết định search requirements có đáng vận hành Elasticsearch hay giải pháp đơn giản hơn đủ dùng.

## 11. Key takeaway

* Trước khi tuning scoring, hãy kiểm tra tokens.
* `text` và `keyword` phục vụ hai semantics khác nhau.
* Analyzer là part của data contract; đổi nó thường kéo theo reindex.

# 6. Azure Blob Storage SAS: cấp quyền upload/download có giới hạn mà không phát tán storage credentials

## 1. What is it?

Shared Access Signature (SAS) là signed token cấp quyền có giới hạn tới Azure Storage resource trong khoảng thời gian nhất định.

Mental model:

```text
Backend authenticates user
      ↓
Backend issues scoped SAS
      ↓
Client talks directly to Blob Storage
      ↓
SAS expires
```

## 2. Why does it exist?

Nếu mọi file upload/download đi xuyên application server, app phải proxy large payloads và tốn bandwidth/CPU. Nhưng đưa storage account key cho client là không chấp nhận được vì key có quyền rộng và khó thu hồi theo từng operation.

## 3. How does it work?

SAS encode permissions, resource scope, expiry và signature. Có account SAS, service SAS và user delegation SAS. Với Azure AD/Managed Identity, user delegation SAS thường tốt hơn việc ký bằng long-lived account key.

## 4. Practical implementation

Backend dùng Managed Identity để tạo short-lived upload SAS cho đúng blob path:

```text
container: user-files
blob: user-123/8f3a...
permission: Create/Write
expiry: +10 minutes
```

Client upload trực tiếp Blob Storage rồi backend ghi metadata sau khi verify upload hoàn tất.

Không cho client tự chọn arbitrary storage path nếu authorization model dựa trên ownership.

## 5. Real production scenario

CMS cho editor upload video 500 MB. Proxy qua App Service làm request timeout và tăng egress/compute. Direct-to-Blob upload bằng short-lived SAS giảm tải app và hỗ trợ chunked/resumable upload tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → upload trả `403 AuthenticationFailed` dù SAS vừa được tạo.

**Evidence** → server/client clocks lệch hoặc SAS start time quá sát hiện tại.

**Hypothesis** → clock skew hoặc permission/resource mismatch.

**Diagnosis** → inspect signed permissions, resource path, expiry/start time và storage error details.

**Fix** → tránh start time quá chặt, dùng UTC, scope đúng resource và permission tối thiểu.

**Verification** → test upload/download từ browser/mobile, kể cả near-expiry behavior.

## 7. Common mistakes

* SAS lifetime hàng ngày/hàng tháng cho operation vài phút.
* Cho `Read+Write+Delete+List` khi chỉ cần upload.
* Log full SAS URL.
* Dùng account key trong frontend/mobile.
* Không verify MIME/type/size sau direct upload.

## 8. Alternatives

Backend proxy upload đơn giản hơn cho file nhỏ/sensitive workflows. Private endpoints và service-to-service access phù hợp backend-only storage. CDN signed URLs phù hợp distribution use cases nhưng khác storage authorization.

## 9. Trade-offs

### Advantages

* Giảm app-server bandwidth/load.
* Quyền granular và time-bound.
* Phù hợp large-file workflows.

### Costs / Risks

* Token leakage có giá trị tới khi hết hạn.
* CORS/client upload flow phức tạp hơn.
* Cần cleanup abandoned uploads.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SAS là delegated temporary permission, không phải account key.

### Middle

Tạo scoped SAS và xử lý direct upload.

### Senior

Thiết kế expiry, ownership, cleanup, validation và Managed Identity flow.

### Technical Lead / Architect

Chọn end-to-end file architecture gồm identity, CDN, lifecycle, malware scanning và retention.

## 11. Key takeaway

* SAS phải ngắn hạn và least privilege.
* Ưu tiên identity-based issuance thay vì phát tán storage keys.
* Direct upload giải quyết scale nhưng không loại bỏ validation/security workflow.

# 7. Azure Service Bus message settlement: `Complete`, `Abandon`, `DeadLetter`, lock expiry và duplicate delivery

## 1. What is it?

Trong Peek-Lock mode, consumer nhận message nhưng message chưa bị xóa. Broker giữ lock tạm thời cho consumer xử lý rồi consumer quyết định settlement.

```text
Receive
  ↓
Lock message
  ↓
Process
  ├─ Complete
  ├─ Abandon
  ├─ DeadLetter
  └─ lock expires → redelivery
```

## 2. Why does it exist?

Nếu broker xóa message ngay khi deliver, process crash sau đó sẽ mất dữ liệu. Nếu giữ message vĩnh viễn đến khi thành công, poison message có thể retry vô hạn. Settlement cho phép explicit reliability semantics.

## 3. How does it work?

* `Complete`: xử lý thành công, broker loại message.
* `Abandon`: trả lại để retry sớm.
* `DeadLetter`: chuyển sang DLQ vì message không nên retry bình thường.
* Lock expiry: nếu chưa settle kịp, message có thể được deliver lại.

Delivery count tăng qua retries và có thể trigger dead-letter khi vượt threshold.

## 4. Practical implementation

Handler cần idempotent:

```csharp
processor.ProcessMessageAsync += async args =>
{
    try
    {
        await HandleAsync(args.Message, args.CancellationToken);
        await args.CompleteMessageAsync(args.Message);
    }
    catch (PermanentContractException ex)
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            deadLetterReason: "invalid_contract",
            deadLetterErrorDescription: ex.Message);
    }
};
```

Transient exceptions có thể để processor retry theo policy; permanent validation failure không nên quay lại queue vô hạn.

## 5. Real production scenario

Invoice worker gọi external tax API. Call thành công nhưng process crash trước `Complete`. Message được deliver lại và invoice có nguy cơ được tạo lần hai. Idempotency key/database uniqueness mới ngăn duplicate side effect; Service Bus không tự biết business operation đã hoàn tất.

## 6. Failure scenario & troubleshooting

**Symptom** → same message được xử lý nhiều lần dù handler “không throw”.

**Evidence** → processing time vượt lock duration hoặc network issue làm settlement fail.

**Hypothesis** → lock lost trước `Complete`.

**Diagnosis** → inspect processing duration, lock-lost exceptions, auto lock renewal config và downstream latency.

**Fix** → rút ngắn handler, renew lock hợp lý, chuyển long-running work sang workflow khác và giữ handler idempotent.

**Verification** → inject delays dài hơn lock duration và kill worker trước settlement.

## 7. Common mistakes

* Nghĩ Peek-Lock = exactly-once.
* `Complete` trước khi durable side effect commit.
* Retry permanent schema/business errors.
* Không monitor DLQ.
* Handler chứa long-running external work không bounded timeout.

## 8. Alternatives

Receive-and-delete phù hợp telemetry có thể mất nhưng hiếm dùng cho business workflows. Event Hubs/Kafka có checkpoint/offset semantics khác. Durable workflow engine phù hợp orchestration dài nhiều bước.

## 9. Trade-offs

### Advantages

* At-least-once delivery an toàn hơn crash.
* Explicit failure routing.
* Hỗ trợ retry/DLQ workflows.

### Costs / Risks

* Duplicate delivery là expected behavior.
* Lock lifecycle cần quản lý.
* DLQ cần operational ownership.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu message chỉ biến mất sau settlement phù hợp.

### Middle

Phân biệt transient vs permanent failure và implement settlement đúng.

### Senior

Thiết kế idempotency, lock duration, retry và DLQ operations.

### Technical Lead / Architect

Định nghĩa messaging reliability contract xuyên producer, broker, consumer và data store.

## 11. Key takeaway

* Settlement là reliability protocol, không phải business idempotency.
* Duplicate processing phải được giả định sẽ xảy ra.
* DLQ chỉ hữu ích nếu có monitoring và recovery process.

# 8. SSRF trong backend integrations: vì sao “chỉ fetch URL do user nhập” có thể mở đường vào private network

## 1. What is it?

Server-Side Request Forgery (SSRF) xảy ra khi attacker khiến server gửi request tới destination mà attacker kiểm soát một phần hoặc toàn bộ.

```text
Attacker input URL
      ↓
Your backend fetches it
      ↓
Internal/private destination becomes reachable
```

Server thường có network privileges mà browser của attacker không có.

## 2. Why does it exist?

Các feature như URL preview, webhook tester, image importer, PDF-from-URL hoặc integration proxy thường cần server-side fetch. Nếu destination validation yếu, attacker có thể probe localhost, cloud metadata endpoints hoặc internal services.

## 3. How does it work?

Naive code:

```csharp
var html = await httpClient.GetStringAsync(userProvidedUrl, ct);
```

Validation chỉ check `https://` là chưa đủ. DNS có thể resolve private IP, redirects có thể nhảy sang internal host, IPv6/alternate numeric forms có thể bypass string checks.

## 4. Practical implementation

An toàn nhất là **allowlist destinations** khi business domain biết trước endpoints.

Nếu phải hỗ trợ arbitrary public URL:

* chỉ cho phép `http/https` theo policy;
* resolve DNS và reject loopback/private/link-local ranges;
* kiểm tra lại redirect destinations;
* giới hạn timeout, response size, redirects;
* dùng isolated egress network/proxy khi khả thi;
* không forward internal credentials/headers.

## 5. Real production scenario

CMS cho phép editor import image từ URL. Endpoint ban đầu chỉ check extension `.jpg`. Attacker dùng redirect chain trỏ tới internal admin endpoint và backend fetch nội dung bằng privileged network path. Feature “download image” trở thành SSRF primitive.

## 6. Failure scenario & troubleshooting

**Symptom** → logs xuất hiện outbound requests tới `127.0.0.1`, RFC1918 ranges hoặc metadata IP.

**Evidence** → request bắt đầu từ user-controlled import/preview API.

**Hypothesis** → URL validation không cover DNS resolution/redirect.

**Diagnosis** → trace original URL, redirects và resolved IPs; tránh thực hiện probing nguy hiểm ngoài controlled environment.

**Fix** → allowlist hoặc centralized outbound fetch service với strict network policy.

**Verification** → security tests cho loopback, private IPv4/IPv6, redirect, DNS rebinding-resistant design và oversized response.

## 7. Common mistakes

* Block chuỗi `localhost` nhưng bỏ qua `127.0.0.1`/IPv6/private DNS.
* Validate initial URL nhưng tự follow redirects.
* Cho backend forward Authorization header tới arbitrary host.
* Không giới hạn response body size.
* Tin rằng firewall mặc định đã chặn mọi internal endpoint.

## 8. Alternatives

Client-side fetch giảm server network privilege nhưng bị CORS và không phù hợp mọi use case. Pre-approved integration catalog tốt hơn arbitrary URLs cho enterprise systems. Isolated fetch microservice chỉ đáng dùng khi risk/scale biện minh operational cost.

## 9. Trade-offs

### Advantages của strict outbound policy

* Giảm blast radius tới internal network.
* Centralize auditing và limits.

### Costs / Risks

* Arbitrary URL features bị hạn chế.
* DNS/redirect validation phức tạp.
* Egress proxy thêm component vận hành.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu server fetch URL có quyền mạng khác browser user.

### Middle

Biết validate scheme, redirect, timeout và size.

### Senior

Hiểu DNS/IP tricks, cloud metadata risk và egress isolation.

### Technical Lead / Architect

Quyết định feature có thật sự cần arbitrary outbound access và thiết kế network trust boundary phù hợp.

## 11. Key takeaway

* SSRF là trust-boundary problem, không chỉ URL parsing bug.
* Allowlist tốt hơn denylist khi destination set biết trước.
* Network egress policy là defense quan trọng khi application validation thất bại.

# 9. Git bisect: tìm commit gây regression bằng binary search thay vì đọc hàng trăm commits bằng mắt

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên làm behavior chuyển từ good sang bad.

Mental model:

```text
100 commits nghi ngờ
→ test midpoint
→ còn 50
→ test midpoint
→ còn 25
...
```

Khoảng 1024 commits chỉ cần khoảng 10 lần phân loại good/bad nếu history phù hợp.

## 2. Why does it exist?

Production regression đôi khi chỉ biết “release tuần trước ổn, release hôm nay lỗi”. Đọc commit diff tuần tự vừa chậm vừa dễ thiên kiến. Bisect biến debugging history thành search problem có hệ thống.

## 3. How does it work?

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0
```

Git checkout midpoint. Bạn chạy test rồi đánh dấu:

```bash
git bisect good
# hoặc
git bisect bad
```

Cuối cùng Git chỉ ra first bad commit.

## 4. Practical implementation

Giá trị cao nhất đến từ automated reproducible test:

```bash
git bisect run ./scripts/repro-latency-regression.sh
```

Script phải trả exit code `0` cho good, non-zero cho bad; `125` có thể dùng khi commit không test được trong một số flows.

Ví dụ script build app, chạy integration test và fail nếu query count vượt threshold.

## 5. Real production scenario

Sau release, endpoint `/orders` tăng từ 120 ms lên 900 ms. Team biết tag `release-42` tốt và `release-43` xấu, giữa chúng có 180 commits. Automated bisect với benchmark threshold tìm ra commit thêm `.Include()` gây row explosion trong vài iterations thay vì review thủ công toàn history.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect cho kết quả không ổn định, mỗi lần ra commit khác.

**Evidence** → test good/bad dựa trên flaky timing benchmark.

**Hypothesis** → classifier không deterministic.

**Diagnosis** → chạy test lặp nhiều lần trên cùng commit, kiểm soát data/environment và measurement noise.

**Fix** → dùng deterministic reproduction hoặc robust statistical threshold; skip commits không build do historical dependency issues.

**Verification** → checkout identified commit và parent, tái hiện bad/good nhiều lần.

## 7. Common mistakes

* Chọn good commit không thực sự known-good.
* Dùng test flaky.
* Bisect merge-heavy history mà không hiểu semantic change spans multiple commits.
* Không reset sau khi xong: `git bisect reset`.
* Tìm commit xong rồi revert ngay mà không hiểu root cause.

## 8. Alternatives

Manual diff phù hợp khi chỉ vài commits. Feature flags/log correlation có thể xác định change nhanh hơn. APM deployment markers giúp khoanh release window nhưng không thay binary search trong source history.

## 9. Trade-offs

### Advantages

* Search rất hiệu quả trên lịch sử lớn.
* Giảm bias khi debug.
* Tự động hóa được.

### Costs / Risks

* Cần reproducible classifier.
* Historical commits có thể không build.
* Không tốt nếu bug phụ thuộc external state thay vì code revision.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết `bisect` dùng để tìm first bad commit.

### Middle

Chạy manual bisect và xác nhận parent/child.

### Senior

Automate repro script và kiểm soát flaky signals.

### Technical Lead / Architect

Đầu tư testability/deployment traceability để regressions có thể được bisect nhanh, giảm MTTR.

## 11. Key takeaway

* `git bisect` biến lịch sử thành binary-search problem.
* Quality của kết quả phụ thuộc quality của good/bad test.
* Khả năng reproduce regression là một phần của engineering operability.

# 10. Structured Outputs cho AI integration: ép schema nhưng vẫn phải giữ validation và business rules deterministic

## 1. What is it?

Structured Outputs là cách yêu cầu model trả dữ liệu theo schema định nghĩa trước thay vì free-form text.

Mental model:

```text
Prompt + schema
      ↓
Model output constrained to structure
      ↓
Application parses typed data
      ↓
Deterministic validation/business logic
```

Schema compliance không đồng nghĩa factual correctness hoặc business correctness.

## 2. Why does it exist?

Parsing free-form LLM text bằng regex/string matching rất dễ vỡ. Application integrations cần predictable fields/types để downstream code xử lý an toàn hơn.

Structured output giảm format ambiguity, nhưng model vẫn có thể đặt **giá trị sai** vào field hợp schema.

## 3. How does it work?

Ví dụ application cần triage support ticket:

```json
{
  "category": "billing",
  "priority": "high",
  "summary": "..."
}
```

Schema có thể ép `category` vào enum và `priority` vào allowed values. Nhưng việc ticket thật sự thuộc billing hay high priority vẫn là probabilistic classification.

## 4. Practical implementation

Trong .NET, map structured response vào DTO rồi validate tiếp:

```csharp
public sealed record TicketTriage(
    string Category,
    string Priority,
    string Summary);
```

Sau parse:

```csharp
if (!allowedCategories.Contains(result.Category))
    return FallbackToManualReview();

if (ticket.AccountIsSuspended)
{
    // Deterministic business rule remains in code.
}
```

Security/authorization/financial decisions không nên được delegated trực tiếp cho unconstrained model judgment.

## 5. Real production scenario

Customer-support platform dùng model phân loại ticket để route queue. Structured schema loại bỏ failures do malformed JSON. Tuy nhiên evaluation cho thấy model thỉnh thoảng đánh `priority=low` cho security incident. Team giữ deterministic escalation rules dựa trên known signals và manual-review threshold.

## 6. Failure scenario & troubleshooting

**Symptom** → response parse thành công 100% nhưng business outcome vẫn sai.

**Evidence** → schema-valid fields chứa wrong classification/unsupported facts.

**Hypothesis** → team đang nhầm structural validity với semantic correctness.

**Diagnosis** → build evaluation dataset, compare prediction với labeled expected outcomes và segment error by category.

**Fix** → deterministic guardrails, retrieval grounding, improved prompt/context và fallback/manual review cho high-risk cases.

**Verification** → rerun evaluation suite và production shadow testing; track precision/recall hoặc task-specific quality metric.

## 7. Common mistakes

* Schema-valid = trusted.
* Cho model tự quyết authorization/price/refund limit.
* Không version schema khi downstream contract đổi.
* Retry vô hạn khi refusal/validation failure.
* Không log model/version/prompt metadata cần thiết cho debugging.
* Không có evaluation dataset.

## 8. Alternatives

Function/tool calling phù hợp khi model chọn action cần gọi. Plain JSON có thể đủ cho low-risk prototypes nhưng parsing yếu hơn. Deterministic parser/rules engine tốt hơn khi problem vốn deterministic và không cần model.

## 9. Trade-offs

### Advantages

* Integration contract ổn định hơn free text.
* Typed parsing đơn giản hơn.
* Giảm format-related failures.

### Costs / Risks

* Không giải quyết hallucination.
* Schema evolution cần quản lý.
* Constrained structure không thay evaluation/security design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu schema chỉ kiểm soát shape.

### Middle

Parse typed output, validate và handle refusal/failure.

### Senior

Thiết kế evaluations, fallbacks, observability và deterministic guardrails.

### Technical Lead / Architect

Quyết định phần nào được giao cho probabilistic model, phần nào phải giữ deterministic và mức risk nào yêu cầu human review.

## 11. Key takeaway

* Structured Outputs giải quyết format reliability, không giải quyết truth.
* Business-critical rules vẫn phải deterministic và testable.
* AI integration production cần evaluation, fallback và observability như bất kỳ external dependency nào.
