# 1. `Span<T>`, `Memory<T>` và `ArrayPool<T>`: tối ưu allocation nhưng phải hiểu lifetime và ownership

## 1. What is it?

`Span<T>` là một view liên tục trên memory có thể trỏ vào array, stack memory hoặc unmanaged memory mà không cần tạo object mới cho mỗi slice. `Memory<T>` có vai trò gần giống nhưng có thể tồn tại qua async boundary. `ArrayPool<T>` cho phép thuê và trả lại arrays để giảm allocation pressure khi xử lý buffer lớn hoặc lặp lại nhiều lần.

Mental model quan trọng:

```text
Span<T>   → view ngắn hạn, stack-only, không đi qua await
Memory<T> → view có thể sống dài hơn và đi qua async boundary
ArrayPool → reuse backing arrays thay vì allocate mới liên tục
```

Đây không phải ba API “performance magic”. Chúng là công cụ quản lý memory ownership tinh vi hơn, đổi allocation thấp lấy lifecycle phức tạp hơn.

## 2. Why does it exist?

Trong hot path như parsing protocol, serialization, file processing hoặc network framing, việc liên tục tạo substring, array slice hoặc temporary buffers gây nhiều allocations. Nhiều allocations làm Gen0 collection diễn ra thường xuyên hơn; buffer lớn có thể đi vào LOH và gây memory pressure rõ rệt.

Trước khi dùng các API này, cách đơn giản thường là:

```csharp
var segment = buffer.Skip(offset).Take(length).ToArray();
```

Code dễ đọc nhưng mỗi lần tạo một array mới. Khi request rate lớn, chi phí GC có thể lớn hơn business computation.

## 3. How does it work?

`Span<T>` chứa reference tới memory + length, không copy dữ liệu. Slice cũng chỉ tạo view mới.

```csharp
Span<byte> payload = buffer.AsSpan(offset, length);
```

`ArrayPool<T>.Shared.Rent(size)` trả về một array có độ dài ít nhất bằng `size`. Caller phải trả lại:

```csharp
var rented = ArrayPool<byte>.Shared.Rent(size);
try
{
    // use rented
}
finally
{
    ArrayPool<byte>.Shared.Return(rented);
}
```

Array được trả lại pool vẫn chứa dữ liệu cũ trừ khi caller yêu cầu clear. Vì thế pool có cả correctness và security implications.

## 4. Practical implementation

Ví dụ đọc stream vào pooled buffer:

```csharp
public static async Task<int> ReadChunkAsync(
    Stream stream,
    Memory<byte> destination,
    CancellationToken ct)
{
    return await stream.ReadAsync(destination, ct);
}

public static async Task ProcessAsync(Stream stream, CancellationToken ct)
{
    var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);

    try
    {
        var memory = buffer.AsMemory(0, 64 * 1024);
        var read = await ReadChunkAsync(stream, memory, ct);

        ReadOnlySpan<byte> span = buffer.AsSpan(0, read);
        Parse(span);
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
    }
}
```

`Memory<T>` đi qua `await`; `Span<T>` chỉ được tạo sau khi async operation hoàn tất.

## 5. Real production scenario

Một API import CSV xử lý hàng trăm MB dữ liệu. Version đầu tạo `string.Split`, `Substring`, temporary arrays cho từng row. GC time tăng cao, p99 latency dao động mạnh và memory peak tăng theo file size.

Sau khi profiling chứng minh allocation là bottleneck, team chuyển parser sang `ReadOnlySpan<char>` và reuse buffers. Throughput tăng nhưng review phải tập trung vào lifetime: không giữ reference tới pooled buffer sau khi đã return.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu parse đôi lúc sai ngẫu nhiên hoặc xuất hiện bytes từ request khác.

**Evidence** → object giữ `Memory<byte>` trỏ tới rented array sau khi array đã được `Return`.

**Hypothesis** → use-after-return trên pooled buffer.

**Diagnosis** → trace ownership của buffer từ `Rent` tới `Return`; kiểm tra mọi async continuation và object lưu reference.

**Fix** → không expose pooled memory vượt lifetime owner; copy dữ liệu nếu cần giữ lâu; dùng `IMemoryOwner<T>`/MemoryPool khi ownership phức tạp hơn.

**Verification** → stress test concurrent requests, thêm tests kiểm tra lifetime và data integrity.

## 7. Common mistakes

* Dùng `ArrayPool<T>` trong code không có allocation problem thực tế.
* Return array quá sớm trong khi async work vẫn dùng nó.
* Giả định rented array có đúng requested length.
* Không clear sensitive data trước khi return.
* Dùng `Span<T>` rồi cố lưu vào field hoặc qua `await`.
* Tối ưu parser nhưng bỏ qua readability và verification.

## 8. Alternatives

Nếu workload nhỏ, array/string allocation bình thường thường đơn giản và an toàn hơn. `MemoryPool<T>` hữu ích khi cần ownership object rõ hơn. `PipeReader` phù hợp cho advanced streaming pipelines. Không phải hot path nào cũng cần low-level memory APIs.

## 9. Trade-offs

### Advantages

* Giảm temporary allocations.
* Giảm GC pressure ở hot paths.
* Cho phép zero-copy slicing trong nhiều trường hợp.

### Costs / Risks

* Lifetime/ownership phức tạp hơn.
* Bug có thể nondeterministic.
* Security risk nếu pooled buffer chứa sensitive data.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slicing không nhất thiết phải copy dữ liệu.

### Middle

Biết dùng `Span<T>`, `Memory<T>`, `ArrayPool<T>` đúng scope và `try/finally`.

### Senior

Chỉ áp dụng sau profiling; review ownership, async lifetime và data exposure.

### Technical Lead / Architect

Quyết định nơi nào low-level memory optimization đáng complexity và đặt coding conventions/tests để ngăn lifecycle bug.

## 11. Key takeaway

* Zero-copy optimization đổi allocation cost lấy ownership complexity.
* `Span<T>` ngắn hạn; `Memory<T>` phù hợp async hơn.
* Pooled buffer phải có owner và lifetime rõ ràng.

# 2. ASP.NET Core `ProblemDetails`: chuẩn hóa error contract mà không làm mất diagnostic context

## 1. What is it?

`ProblemDetails` là representation chuẩn cho HTTP API errors dựa trên RFC 7807/9457-style problem details. Nó cho client một contract nhất quán như `type`, `title`, `status`, `detail`, `instance` và extension fields.

Mental model:

```text
Internal exception / domain failure
        ↓ mapping boundary
ProblemDetails contract
        ↓
HTTP response ổn định cho client
```

Nó không phải cơ chế logging và cũng không nên expose raw exception detail ra ngoài.

## 2. Why does it exist?

Nếu mỗi endpoint tự trả lỗi theo format riêng:

```json
{ "error": "bad request" }
```

ở endpoint khác:

```json
{ "message": "invalid", "code": 12 }
```

client phải viết parsing logic rời rạc. Đồng thời developer dễ vô tình trả stack trace hoặc internal database error cho caller.

`ProblemDetails` tạo một boundary rõ giữa diagnostics nội bộ và public API contract.

## 3. How does it work?

Application phân loại failures:

```text
Validation failure     → 400
Authentication failure → 401
Authorization failure  → 403
Resource missing       → 404
Concurrency conflict   → 409
Unexpected exception   → 500
```

Sau đó tạo payload consistent. Correlation ID có thể nằm trong extension để support team nối client error với trace/log nội bộ.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails(options =>
{
    options.CustomizeProblemDetails = context =>
    {
        context.ProblemDetails.Extensions["traceId"] =
            context.HttpContext.TraceIdentifier;
    };
});

var app = builder.Build();

app.UseExceptionHandler();
app.UseStatusCodePages();
```

Với domain exception, có thể map tập trung:

```csharp
public sealed class OrderNotFoundException(Guid id) : Exception;
```

và exception handler convert thành 404 mà không expose exception message thô.

## 5. Real production scenario

Mobile app và SPA cùng gọi một backend. Trước đây mỗi team backend trả lỗi khác nhau, client phải dùng nhiều `if` theo endpoint. Sau khi chuẩn hóa ProblemDetails + stable machine-readable error code, client có thể xử lý uniformly mà không phụ thuộc human-readable `detail`.

## 6. Failure scenario & troubleshooting

**Symptom** → production API trả stack trace, SQL table name hoặc secret fragment trong response 500.

**Evidence** → exception middleware copy `exception.ToString()` vào `detail`.

**Hypothesis** → diagnostic boundary bị phá.

**Diagnosis** → review centralized exception mapping và environment-specific behavior.

**Fix** → public payload chỉ chứa safe message + traceId; full exception chỉ vào protected logs/traces.

**Verification** → integration tests assert 500 response không chứa internal exception text.

## 7. Common mistakes

* Dùng HTTP 200 cho mọi business error rồi nhét `success=false`.
* Expose stack trace ở Production.
* Dùng `detail` làm machine-readable key.
* Không phân biệt 401 và 403.
* Mỗi endpoint tự build error object khác nhau.
* Log cùng exception ở nhiều layers gây duplicate noise.

## 8. Alternatives

Custom error envelope có thể phù hợp legacy systems nhưng cần contract rõ. gRPC dùng status/details khác. GraphQL có error model riêng. Quan trọng là consistency và separation diagnostics/public contract, không phải ép mọi protocol dùng ProblemDetails.

## 9. Trade-offs

### Advantages

* Client contract nhất quán.
* Dễ map lỗi theo semantic HTTP.
* Hỗ trợ correlation mà không leak internals.

### Costs / Risks

* Cần governance về error codes.
* Mapping quá generic có thể làm mất business semantics.
* Client vẫn cần stable extension fields nếu muốn automation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu API error phải có status code đúng và format ổn định.

### Middle

Biết centralized mapping và integration tests.

### Senior

Thiết kế error taxonomy, diagnostics boundary và backward compatibility.

### Technical Lead / Architect

Chuẩn hóa error contract xuyên services, xác định field public nào stable và field nào chỉ phục vụ observability.

## 11. Key takeaway

* Error payload là public contract.
* Diagnostics nội bộ và client-facing detail phải tách biệt.
* Stable error semantics quan trọng hơn text message đẹp.

# 3. EF Core single query vs split query: tránh Cartesian explosion nhưng không tạo inconsistency vô thức

## 1. What is it?

Khi dùng nhiều `Include` cho collection relationships, EF Core có thể load toàn graph bằng một SQL query lớn hoặc chia thành nhiều queries. `AsSplitQuery()` yêu cầu EF Core load related collections bằng các round trips riêng để tránh row multiplication quá lớn.

## 2. Why does it exist?

Giả sử một `Order` có 20 `OrderLines` và 10 `Comments`. Một JOIN cả hai collections có thể tạo gần 200 rows cho cùng một order do Cartesian multiplication. Nếu thêm collection thứ ba, dữ liệu truyền và materialization có thể tăng nhanh.

Split query giảm duplication nhưng đổi lại có nhiều round trips và consistency semantics khác.

## 3. How does it work?

Single query:

```text
Orders
 JOIN Lines
 JOIN Comments
→ duplicated parent data
→ one round trip
```

Split query:

```text
Query Orders
Query Lines for selected Orders
Query Comments for selected Orders
→ multiple round trips
→ less duplication
```

EF Core fix-up các entities/relationships sau khi các result sets được load.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Include(x => x.Lines)
    .Include(x => x.Comments)
    .AsSplitQuery()
    .AsNoTracking()
    .ToListAsync(ct);
```

Nhưng nếu API chỉ cần summary, projection thường tốt hơn:

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummary(
        x.Id,
        x.Lines.Count,
        x.Comments.Count))
    .ToListAsync(ct);
```

## 5. Real production scenario

Admin dashboard load customer cùng orders, items, tags và comments. Single query trả hàng chục MB dù logical data chỉ vài MB. CPU DB và network tăng. Team bật split query và latency giảm, nhưng sau đó nhận ra dashboard chỉ cần aggregates; projection còn hiệu quả hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → result graph đôi lúc phản ánh trạng thái không hoàn toàn cùng một thời điểm khi concurrent writes xảy ra.

**Evidence** → split query thực thi nhiều statements mà không có snapshot/transaction phù hợp.

**Hypothesis** → dữ liệu thay đổi giữa các subqueries.

**Diagnosis** → capture SQL timings, kiểm tra isolation level và concurrent update pattern.

**Fix** → nếu consistency point-in-time quan trọng, dùng transaction/isolation phù hợp hoặc đổi query shape; nếu không, chấp nhận bounded inconsistency có chủ đích.

**Verification** → concurrency integration tests.

## 7. Common mistakes

* Bật `AsSplitQuery()` global mà không đo.
* `Include` cả graph trong API list endpoint.
* Không dùng projection khi chỉ cần vài fields.
* Giả định split query luôn nhanh hơn.
* Không tính round-trip latency tới remote database.

## 8. Alternatives

Projection DTO, explicit loading, dedicated read model, stored procedure/raw SQL cho complex reporting. Một query duy nhất vẫn tốt khi graph nhỏ và duplication không đáng kể.

## 9. Trade-offs

### Advantages của split query

* Giảm Cartesian explosion.
* Ít duplicated bytes trên network.

### Costs / Risks

* Nhiều database round trips.
* Point-in-time consistency khó hơn.
* Query count tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` có thể tạo SQL JOIN lớn.

### Middle

Biết inspect generated SQL và chọn projection/split query.

### Senior

Đánh giá row multiplication, round trips và isolation semantics.

### Technical Lead / Architect

Thiết kế read model theo use case, tránh entity graph trở thành API contract mặc định.

## 11. Key takeaway

* `Include` convenience có thể che giấu query explosion.
* Split query giải một cost nhưng thêm round trips và consistency trade-off.
* Projection thường là lựa chọn tốt nhất cho read-heavy API.

# 4. SQL keyset pagination: vì sao `OFFSET` chậm dần và cách thiết kế cursor đúng

## 1. What is it?

Keyset pagination lấy page tiếp theo dựa trên giá trị sort key cuối cùng của page trước thay vì bỏ qua N rows bằng `OFFSET`.

Ví dụ sort theo `CreatedAt DESC, Id DESC`, cursor chứa cặp `(CreatedAt, Id)` cuối cùng đã thấy.

## 2. Why does it exist?

Offset pagination:

```sql
ORDER BY CreatedAt DESC
OFFSET 500000 ROWS FETCH NEXT 50 ROWS ONLY;
```

Database vẫn phải locate/process một lượng lớn rows trước khi bỏ qua. Càng đi sâu, cost thường tăng. Đồng thời insert/delete giữa requests có thể làm user thấy duplicate hoặc skip rows.

## 3. How does it work?

Page đầu:

```sql
SELECT TOP (50) ...
FROM Orders
ORDER BY CreatedAt DESC, Id DESC;
```

Page sau:

```sql
WHERE CreatedAt < @lastCreatedAt
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC
```

Composite index phù hợp:

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON Orders (CreatedAt DESC, Id DESC);
```

## 4. Practical implementation

EF Core:

```csharp
var query = db.Orders.AsNoTracking();

if (cursor is not null)
{
    query = query.Where(x =>
        x.CreatedAt < cursor.CreatedAt ||
        (x.CreatedAt == cursor.CreatedAt && x.Id.CompareTo(cursor.Id) < 0));
}

var page = await query
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id)
    .Take(50)
    .Select(x => new OrderListItem(x.Id, x.CreatedAt, x.Status))
    .ToListAsync(ct);
```

Cursor nên opaque với client, ví dụ base64-encoded structured payload có validation/version.

## 5. Real production scenario

Audit log có hàng chục triệu rows. Admin UI dùng page number tới page 20.000; latency tăng từ 100 ms lên nhiều giây. Chuyển sang keyset cursor giữ latency ổn định hơn vì query seek từ last key thay vì scan/skip sâu.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate/missing items giữa các page.

**Evidence** → sort chỉ theo `CreatedAt`, trong khi nhiều rows có cùng timestamp.

**Hypothesis** → ordering không deterministic.

**Diagnosis** → kiểm tra duplicate sort values và cursor predicate.

**Fix** → thêm unique tiebreaker như `Id` vào cả `ORDER BY`, cursor và index.

**Verification** → property/integration tests với nhiều rows cùng timestamp và concurrent inserts.

## 7. Common mistakes

* Cursor chỉ chứa non-unique sort field.
* Cho client sửa cursor không validation.
* Dùng keyset nhưng vẫn expose “jump to page 5000”.
* Index không khớp sort/filter access pattern.
* Encode cursor nhưng coi base64 là security boundary.

## 8. Alternatives

Offset pagination đơn giản và phù hợp dữ liệu nhỏ hoặc UI cần random page navigation. Search engines thường có cursor/search-after concepts. Materialized snapshot phù hợp export/report cần stable full traversal.

## 9. Trade-offs

### Advantages

* Deep pagination ổn định hơn.
* Ít affected bởi concurrent inserts trước cursor.
* Tận dụng ordered index seek tốt.

### Costs / Risks

* Không dễ jump tới arbitrary page number.
* Cursor design/versioning phức tạp hơn.
* Dynamic multi-column sorting làm predicate khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `OFFSET` không miễn phí.

### Middle

Biết deterministic ordering và composite cursor.

### Senior

Thiết kế index + pagination contract theo access pattern thực.

### Technical Lead / Architect

Quyết định UX/API semantics: page number hay cursor, consistency expectation và compatibility khi sort contract thay đổi.

## 11. Key takeaway

* Deep `OFFSET` thường scale kém.
* Cursor cần deterministic unique ordering.
* Pagination design là API + index design cùng lúc.

# 5. Redis cache invalidation: ownership, versioned keys và khi stale data chấp nhận được

## 1. What is it?

Cache invalidation là quy tắc quyết định khi nào cached value không còn hợp lệ và ai chịu trách nhiệm remove/update nó. Đây là phần khó nhất của caching vì cache tạo một bản sao dữ liệu ngoài source of truth.

## 2. Why does it exist?

Cache giúp giảm latency/load, nhưng bất kỳ write nào vào source đều tạo câu hỏi:

```text
DB đã đổi
→ cache còn value cũ
→ ai xóa?
→ nếu xóa thất bại thì sao?
→ stale được phép bao lâu?
```

Không có ownership rõ, system có thể nhanh nhưng sai dữ liệu.

## 3. How does it work?

Cache-aside phổ biến:

```text
READ: cache → miss → DB → cache
WRITE: DB commit → invalidate cache
```

Một kỹ thuật khác là versioned keys:

```text
product:123:v42
```

Khi version tăng, readers chuyển key mới; key cũ tự expire. Cách này giảm delete coordination nhưng cần nơi authoritative lưu version.

## 4. Practical implementation

```csharp
public async Task UpdateProductAsync(Product product, CancellationToken ct)
{
    await repository.UpdateAsync(product, ct);

    try
    {
        await cache.RemoveAsync($"product:{product.Id}", ct);
    }
    catch (Exception ex)
    {
        logger.LogWarning(ex,
            "Cache invalidation failed for product {ProductId}", product.Id);
    }
}
```

Đây chưa phải “perfect consistency”. Nếu cache invalidation fail, stale value có thể tồn tại tới TTL. Vì vậy TTL là một safety bound, không chỉ eviction setting.

## 5. Real production scenario

E-commerce product description stale 2 phút có thể chấp nhận; inventory quantity hoặc authorization decision thì không. Cùng là “cache”, nhưng stale tolerance khác hoàn toàn.

Senior design bắt đầu bằng business correctness: **cái gì được stale, bao lâu, và consequence là gì?**

## 6. Failure scenario & troubleshooting

**Symptom** → user vừa update profile nhưng UI vẫn hiển thị dữ liệu cũ vài phút.

**Evidence** → DB đúng, Redis còn key cũ, invalidation call timeout.

**Hypothesis** → cache invalidation failure.

**Diagnosis** → trace write path, cache remove telemetry, TTL, retries.

**Fix** → bounded TTL; resilient invalidation; event-driven invalidation nếu nhiều consumers; không cache correctness-critical decisions khi invalidation khó đảm bảo.

**Verification** → fault injection khi Redis unavailable và kiểm tra stale bound.

## 7. Common mistakes

* TTL vô hạn cho mutable data.
* Cache authorization/permissions mà không có strong invalidation strategy.
* Nhiều services cùng nghĩ mình “own” cùng một key.
* Retry cache invalidation vô hạn sau DB commit.
* Cache key thiếu tenant/version dimension.

## 8. Alternatives

Không cache là lựa chọn đúng nếu origin đủ nhanh. Local `IMemoryCache` đơn giản hơn nhưng per-instance. Materialized read model/event projection phù hợp khi derived data có lifecycle rõ hơn simple cache.

## 9. Trade-offs

### Advantages

* Cache giảm latency và origin load.
* Versioned keys giảm một số delete race.

### Costs / Risks

* Data consistency trở nên phức tạp.
* Redis có thể thành critical dependency.
* Event-driven invalidation thêm operational components.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache là bản sao, không phải source of truth.

### Middle

Biết cache-aside, TTL và invalidation.

### Senior

Xác định stale tolerance và failure behavior.

### Technical Lead / Architect

Quyết định data nào không nên cache, ownership của keys và consistency contract giữa services.

## 11. Key takeaway

* Trước khi cache, phải định nghĩa stale tolerance.
* TTL là correctness safety bound.
* Cache invalidation cần owner rõ ràng.

# 6. Elasticsearch alias-based reindexing: thay mapping production mà không downtime

## 1. What is it?

Elasticsearch mapping không phải thay đổi nào cũng có thể update in-place an toàn. Alias-based reindexing dùng versioned physical indices và một stable alias để application không phụ thuộc tên index cụ thể.

Ví dụ:

```text
products-read → products-v3
```

Khi cần mapping mới, build `products-v4`, reindex, verify rồi atomically switch alias.

## 2. Why does it exist?

Search index là derived data structure. Mapping/analyzer thay đổi có thể yêu cầu reindex toàn bộ documents. Nếu application truy cập trực tiếp `products-v3`, migration có thể gây downtime hoặc cần coordinated deploy phức tạp.

Alias tạo indirection để tách logical index name khỏi physical generation.

## 3. How does it work?

```text
Primary DB
   ↓ sync
products-v3 ← alias products-read

Create products-v4
   ↓
Backfill/reindex
   ↓
Verify counts/search quality
   ↓
Atomic alias switch
products-read → products-v4
```

Sau switch, old index có thể giữ lại ngắn hạn để rollback.

## 4. Practical implementation

Alias switch request conceptually:

```json
{
  "actions": [
    { "remove": { "index": "products-v3", "alias": "products-read" } },
    { "add":    { "index": "products-v4", "alias": "products-read" } }
  ]
}
```

Application config chỉ dùng `products-read`.

Trước switch nên verify document count, representative queries, analyzer behavior và indexing lag.

## 5. Real production scenario

Search team đổi product name analyzer để hỗ trợ synonym/normalization tốt hơn. Mapping mới cần reindex 30 triệu documents. Thay vì stop search, team build index mới song song, backfill, replay changes trong thời gian backfill, verify rồi switch alias.

## 6. Failure scenario & troubleshooting

**Symptom** → sau alias switch, một số products mới nhất biến mất.

**Evidence** → backfill hoàn tất nhưng changes xảy ra trong lúc reindex chưa được replay hết.

**Hypothesis** → synchronization gap giữa snapshot/backfill và live updates.

**Diagnosis** → compare DB change sequence/event offsets với indexing checkpoint.

**Fix** → dual write/event replay strategy hoặc CDC/outbox với checkpoint rõ trước cutover.

**Verification** → compare counts, sampled IDs, lag metric và search acceptance tests.

## 7. Common mistakes

* Chỉ compare document count, không test query behavior.
* Xóa old index ngay sau switch.
* Không theo dõi indexing lag.
* Directly hard-code physical index name trong application.
* Reindex nhưng bỏ qua writes xảy ra trong migration window.

## 8. Alternatives

In-place compatible mapping updates đơn giản hơn khi thực sự được hỗ trợ. Blue/green search cluster có thể dùng cho infrastructure-level migration lớn. Nếu search requirement đơn giản, database full-text search có thể giảm operational complexity.

## 9. Trade-offs

### Advantages

* Cutover gần như atomic.
* Rollback dễ hơn khi giữ old index.
* Application không phụ thuộc physical generation.

### Costs / Risks

* Tạm thời cần gấp đôi storage.
* Backfill/replay pipeline phức tạp.
* Search correctness cần verification riêng, không chỉ health green.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Elasticsearch index là derived representation có thể rebuild.

### Middle

Biết aliases và basic reindex flow.

### Senior

Thiết kế replay/checkpoint để không mất updates.

### Technical Lead / Architect

Quyết định source-of-truth, reindex lifecycle, rollback window và operational cost của search architecture.

## 11. Key takeaway

* Stable alias tách application khỏi physical index generation.
* Reindex đúng phải xử lý concurrent writes.
* Cutover chỉ xảy ra sau verification, không chỉ sau “job complete”.

# 7. Anti-Corruption Layer: bảo vệ domain khỏi third-party model và contract churn

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary chuyển đổi model/semantics của external system sang model nội bộ của domain. Nó ngăn third-party concepts lan trực tiếp vào core business logic.

Mental model:

```text
External API model
      ↓ adapter/translator
Internal domain contract
      ↓
Application/domain logic
```

## 2. Why does it exist?

Nếu application dùng trực tiếp DTO/enum/status của vendor khắp codebase, vendor contract trở thành domain model de facto. Khi provider đổi naming, semantics hoặc version, thay đổi lan khắp hệ thống.

ACL tồn tại để isolate change và semantic mismatch.

## 3. How does it work?

External provider có status:

```text
PAID, SETTLED, VOIDED, CHARGEBACK
```

Domain nội bộ có thể chỉ quan tâm:

```text
PaymentPending
PaymentSucceeded
PaymentFailed
PaymentReversed
```

Translator quyết định mapping có chủ đích, kể cả unknown/new external values.

## 4. Practical implementation

```csharp
public sealed record ProviderPaymentDto(string Id, string Status);

public enum PaymentState
{
    Pending,
    Succeeded,
    Failed,
    Reversed
}

public static class PaymentTranslator
{
    public static PaymentState Map(string status) => status switch
    {
        "PAID" or "SETTLED" => PaymentState.Succeeded,
        "VOIDED" => PaymentState.Failed,
        "CHARGEBACK" => PaymentState.Reversed,
        _ => throw new UnsupportedProviderStatusException(status)
    };
}
```

Không nên silently map unknown status thành `Failed` nếu semantics chưa rõ.

## 5. Real production scenario

CRM vendor đổi field `customerTier` thành nested object và thêm giá trị mới. Nếu UI, domain và DB đều reference vendor DTO trực tiếp, migration lan rộng. Với ACL, chỉ integration module thay đổi, internal contract giữ ổn định.

## 6. Failure scenario & troubleshooting

**Symptom** → provider thêm status mới, application xử lý sai thành trạng thái business hợp lệ.

**Evidence** → default switch branch map mọi unknown value thành `Pending`.

**Hypothesis** → translation boundary fail-open.

**Diagnosis** → compare provider payload với mapping table; inspect logs for unknown values.

**Fix** → fail safely/explicitly, quarantine unsupported event, alert integration owner.

**Verification** → contract tests với documented + unknown provider values.

## 7. Common mistakes

* Gọi mọi wrapper là ACL dù chỉ pass-through raw DTO.
* Copy toàn bộ vendor schema vào internal domain.
* Swallow unknown enum values.
* Để vendor SDK types xuất hiện trong domain project.
* Overengineer ACL cho integration cực nhỏ và stable.

## 8. Alternatives

Simple adapter đủ cho integration nhỏ. Shared canonical model có thể phù hợp enterprise integration nhưng dễ trở thành “god schema”. Direct provider model có thể chấp nhận ở thin proxy không có domain semantics riêng.

## 9. Trade-offs

### Advantages

* Isolate provider churn.
* Bảo vệ domain language.
* Test business logic không phụ thuộc SDK/vendor DTO.

### Costs / Risks

* Thêm translation code.
* Có nguy cơ mất information nếu internal model quá nghèo.
* Cần ownership cho mapping semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain entity.

### Middle

Biết tạo adapter/translator và tests.

### Senior

Xử lý semantic mismatch, unknown values, versioning và failure isolation.

### Technical Lead / Architect

Quyết định integration boundary và mức isolation xứng đáng với volatility/risk của provider.

## 11. Key takeaway

* ACL bảo vệ semantics, không chỉ đổi tên field.
* External contract churn nên dừng ở integration boundary.
* Unknown external values phải có policy rõ.

# 8. Azure Managed Identity + Key Vault: secretless authentication và operational failure modes

## 1. What is it?

Managed Identity cho phép Azure resource có identity trong Microsoft Entra ID mà application không cần lưu client secret. Azure Key Vault lưu secrets/keys/certificates và kiểm soát access bằng identity/permissions.

Mental model:

```text
App Service / Function / VM
       ↓ Managed Identity token
Microsoft Entra ID
       ↓
Key Vault / SQL / Storage / other Azure resource
```

## 2. Why does it exist?

Client secrets trong config/env phải rotate, có thể leak qua source, CI logs hoặc support dumps. Managed Identity loại bỏ việc application tự quản credential bí mật cho nhiều Azure-to-Azure scenarios.

Key Vault vẫn cần khi third-party secret thực sự tồn tại, nhưng application có thể lấy nó bằng identity thay vì một bootstrap secret khác.

## 3. How does it work?

Azure platform cung cấp identity endpoint/credential chain. `DefaultAzureCredential` có thể dùng developer credentials local và Managed Identity trên Azure.

Authorization sau đó quyết định identity được đọc secret nào hoặc access resource nào.

## 4. Practical implementation

```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);

KeyVaultSecret secret = await client.GetSecretAsync(
    "ThirdPartyApiKey",
    cancellationToken: ct);
```

Tốt hơn nữa, nếu target resource hỗ trợ Entra authentication trực tiếp, không cần lấy secret từ Key Vault.

## 5. Real production scenario

App Service gọi Azure SQL. Version cũ dùng SQL password trong app settings và rotation gây outage do một slot chưa update. Chuyển sang Managed Identity giảm secret lifecycle, nhưng team vẫn phải quản database principal/permissions và monitor token/auth failures.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment mới nhận 403 từ Key Vault dù code không đổi.

**Evidence** → identity token được cấp nhưng RBAC role chưa áp dụng hoặc resource đang dùng identity khác giữa slot/environment.

**Hypothesis** → authorization/configuration mismatch, không phải “Managed Identity hỏng”.

**Diagnosis** → xác định exact principal/object ID, role assignment, vault network restrictions, deployment slot identity.

**Fix** → least-privilege role đúng identity; kiểm tra propagation/network path.

**Verification** → health check có dependency probe phù hợp + integration test trong environment.

## 7. Common mistakes

* Nghĩ Managed Identity tự động có quyền mọi resource.
* Log secret value sau khi đọc Key Vault.
* Gán role quá rộng như Owner để “fix nhanh”.
* Dùng shared user-assigned identity cho quá nhiều apps không boundary.
* Không xem Private Endpoint/network restrictions.

## 8. Alternatives

Service Principal + certificate/secret cần thiết ngoài Azure hoặc cross-boundary scenarios. Workload identity phù hợp Kubernetes. Key Vault references trong App Service config có thể giảm code nhưng vẫn cần hiểu caching/refresh semantics.

## 9. Trade-offs

### Advantages

* Loại bỏ nhiều long-lived secrets.
* Central identity/audit/RBAC.
* Rotation burden thấp hơn.

### Costs / Risks

* Azure identity/network troubleshooting phức tạp.
* RBAC propagation và environment differences gây deployment surprises.
* Vendor secrets vẫn cần lifecycle riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu authentication khác authorization.

### Middle

Biết dùng `DefaultAzureCredential` và least privilege.

### Senior

Debug token/RBAC/network/slot identity failure.

### Technical Lead / Architect

Thiết kế secretless-first architecture, identity ownership và break-glass policy mà không mở quyền quá mức.

## 11. Key takeaway

* Managed Identity loại credential management, không loại permission management.
* Prefer direct identity auth trước khi lưu secret trong Key Vault.
* Identity, RBAC và network đều là một phần của runtime path.

# 9. SSRF trong backend integrations: khi một URL do user cung cấp trở thành đường vào private network

## 1. What is it?

Server-Side Request Forgery (SSRF) xảy ra khi attacker khiến backend gửi request tới địa chỉ mà attacker lựa chọn hoặc ảnh hưởng được. Vì backend thường có network access rộng hơn browser/client, SSRF có thể chạm internal services, metadata endpoints hoặc management interfaces.

## 2. Why does it exist?

Feature tưởng vô hại:

```text
“Nhập URL ảnh để hệ thống tải về”
```

nếu backend fetch URL trực tiếp, attacker có thể thử:

```text
http://127.0.0.1:...
http://169.254.169.254/...
http://internal-service/...
```

Server trở thành proxy vượt qua external network boundary.

## 3. How does it work?

```text
Attacker input URL
      ↓
Backend resolver/http client
      ↓
Internal/private destination
      ↓
Response/content/timing leaks information
```

DNS rebinding và redirects làm validation khó hơn: hostname ban đầu có thể hợp lệ nhưng resolve/redirect tới private address sau đó.

## 4. Practical implementation

Ưu tiên allowlist domains nếu business use case cho phép. Nếu phải fetch arbitrary external URLs, cần validate scheme, resolve IP, block loopback/private/link-local ranges, kiểm soát redirects và egress network.

```csharp
if (uri.Scheme is not ("http" or "https"))
    throw new ValidationException("Unsupported scheme");

if (!allowedHosts.Contains(uri.Host))
    throw new ValidationException("Host is not allowed");
```

Application-level validation không nên là control duy nhất; network egress policy là defense-in-depth quan trọng.

## 5. Real production scenario

CMS cho editor import image bằng URL. Endpoint chạy trong VNet có access tới internal admin API. Attacker có editor-level account và dùng import URL để probe internal endpoints. Đây là ví dụ quyền application “thấp” nhưng network position của server “cao”.

## 6. Failure scenario & troubleshooting

**Symptom** → logs thấy backend gọi unusual private IPs hoặc metadata addresses.

**Evidence** → request URL đến từ user input; redirect chain hoặc DNS resolution trỏ internal range.

**Hypothesis** → SSRF attempt.

**Diagnosis** → inspect request logs, destination IP, DNS/redirect chain, egress telemetry.

**Fix** → strict allowlist, disable uncontrolled redirects, egress filtering, segmented network identity/permissions.

**Verification** → security tests với loopback, private IP, IPv6, DNS rebinding-style cases và redirects.

## 7. Common mistakes

* Chỉ block string `localhost`.
* Validate hostname trước nhưng không validate resolved IP.
* Cho phép redirects không giới hạn.
* Backend có egress/access rộng hơn cần thiết.
* Log full fetched secrets/content.
* Tin URL parse bằng regex đơn giản.

## 8. Alternatives

Upload file trực tiếp thay vì server fetch URL. Dedicated isolated fetcher service với restricted egress phù hợp use case cần arbitrary URLs. Pre-signed upload flow giảm nhu cầu backend truy cập external content.

## 9. Trade-offs

### Advantages của strict allowlist

* Security model đơn giản và mạnh.
* Dễ audit.

### Costs / Risks

* Giảm flexibility cho arbitrary integrations.
* Dynamic provider domains cần maintenance.
* Network controls thêm infrastructure complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu server request có quyền/network khác browser request.

### Middle

Biết validate URL/scheme/host và redirects.

### Senior

Threat-model DNS resolution, private ranges, metadata endpoints và egress.

### Technical Lead / Architect

Thiết kế isolated integration boundary, least-privilege networking và defense-in-depth thay vì dựa vào một regex validator.

## 11. Key takeaway

* User-controlled URL là security boundary.
* Validation hostname chưa đủ; destination network thực tế mới quan trọng.
* Egress restriction là lớp bảo vệ mạnh cho SSRF.

# 10. Kubernetes CPU/memory requests & limits: scheduling, throttling, OOMKill và capacity engineering

## 1. What is it?

Trong Kubernetes, `requests` mô tả lượng resource scheduler dùng để quyết định Pod đặt ở node nào; `limits` đặt upper bound runtime cho CPU/memory theo cơ chế cgroup/container runtime.

Mental model:

```text
requests → scheduling / guaranteed capacity assumption
limits   → runtime ceiling
```

CPU limit thường dẫn tới throttling. Memory limit có thể dẫn tới OOM kill khi process vượt giới hạn.

## 2. Why does it exist?

Nếu không có requests, scheduler không biết Pod thực sự cần bao nhiêu capacity. Node có thể bị overcommit. Nếu không có boundaries trong multi-tenant cluster, một workload có thể chiếm tài nguyên ảnh hưởng workloads khác.

Nhưng limit đặt sai cũng chính nó gây incident.

## 3. How does it work?

Ví dụ:

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "1Gi"
```

Scheduler coi Pod cần 0.5 CPU và 512 MiB để placement. Runtime có thể dùng tới giới hạn. CPU vượt limit bị throttled theo quota; memory vượt limit có thể khiến container bị OOMKilled.

## 4. Practical implementation

Không chọn numbers bằng cảm giác. Bắt đầu từ telemetry/load test:

* CPU usage p50/p95 under expected load.
* Working set/RSS + GC behavior.
* Startup spikes.
* Burst profile.
* Replica count và node capacity.

ASP.NET Core service có memory spike khi large response serialization cần headroom khác worker CPU-bound ổn định.

## 5. Real production scenario

API chạy ổn local nhưng trên AKS p99 tăng dù node CPU tổng chỉ 40%. Container CPU limit là 250m; dưới burst, cgroup throttling mạnh. Dashboard node-level che giấu Pod-level throttling.

Sau khi đo throttled CPU seconds và workload demand, team điều chỉnh request/limit và autoscaling target.

## 6. Failure scenario & troubleshooting

**Symptom** → Pod restart với `OOMKilled` hoặc latency spike không tương ứng node utilization.

**Evidence** → container status OOMKilled hoặc CPU throttling metrics cao; memory working set gần limit.

**Hypothesis** → resource limit mismatch.

**Diagnosis** → inspect `kubectl describe pod`, container metrics, GC/memory profile, HPA behavior, node pressure.

**Fix** → sửa leak/allocation nếu có; điều chỉnh request/limit dựa trên measured demand; scale replicas/nodes phù hợp.

**Verification** → load test và production monitoring sau deploy.

## 7. Common mistakes

* Copy cùng resource values cho mọi service.
* Set memory limit sát average usage.
* Chỉ xem node CPU, không xem throttling per container.
* Requests quá thấp để “nhét được nhiều Pods hơn”.
* Requests quá cao làm scheduler không place được Pods dù actual usage thấp.
* Fix OOM bằng tăng limit mà không profile memory growth.

## 8. Alternatives

Vertical Pod Autoscaler có thể gợi ý/điều chỉnh resources trong một số setups. HPA scale replicas theo metrics nhưng không thay thế right-sizing. Managed platforms giảm một phần Kubernetes tuning nhưng vẫn cần capacity model.

## 9. Trade-offs

### Advantages

* Scheduler có capacity signal.
* Isolation tốt hơn giữa workloads.
* Cost/capacity planning rõ hơn.

### Costs / Risks

* Sai values gây throttling, OOM hoặc wasted capacity.
* Workload bursty khó right-size bằng static values.
* Autoscaling + limits tương tác phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request khác limit.

### Middle

Biết đọc Pod resource config và OOM/restart status.

### Senior

Kết nối throttling, GC, HPA, latency và workload profile.

### Technical Lead / Architect

Xây capacity policy dựa trên SLO, cost, headroom, failure domains và measured workload thay vì template cố định.

## 11. Key takeaway

* Requests ảnh hưởng scheduling; limits ảnh hưởng runtime behavior.
* CPU throttling có thể gây latency dù node chưa full.
* Resource sizing phải dựa trên measurement và workload shape.
