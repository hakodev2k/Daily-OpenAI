# 1. C# `System.IO.Pipelines`: xử lý streaming I/O với buffer reuse và backpressure mà không tự quản lý buffer thủ công

## 1. What is it?

`System.IO.Pipelines` là abstraction trong .NET cho high-performance streaming I/O. Mental model của nó là tách producer và consumer bằng một buffer sequence được runtime quản lý:

```text
Socket / Stream
    ↓ write
PipeWriter
    ↓ buffered segments
PipeReader
    ↓ read/advance
Parser
```

Thay vì tự tạo `byte[]`, copy dữ liệu chưa parse sang buffer mới và tự xử lý partial reads, `PipeReader`/`PipeWriter` cung cấp buffer management, segmented memory và coordination sẵn.

## 2. Why does it exist?

Network/file protocols hiếm khi trả đúng một logical message trong một `ReadAsync`. Một header có thể bị cắt giữa hai reads; nhiều message có thể dính chung trong một buffer.

Cách thủ công thường dẫn đến:

* copy buffer lặp lại,
* allocation nhiều,
* khó xử lý partial message,
* lỗi lifetime,
* producer nhanh hơn consumer mà không có backpressure rõ ràng.

`Pipelines` tồn tại để chuẩn hóa những vấn đề này cho I/O hot path.

## 3. How does it work?

Consumer gọi `ReadAsync`, nhận `ReadResult.Buffer` dưới dạng `ReadOnlySequence<byte>`. Sau khi parse được một phần, consumer phải gọi `AdvanceTo(consumed, examined)`.

`consumed` cho runtime biết phần nào có thể giải phóng/reuse. `examined` cho biết consumer đã inspect đến đâu.

Nếu advance sai, pipeline có thể giữ memory lâu hoặc loop vô hạn.

## 4. Practical implementation

Ví dụ parse các line kết thúc bằng `\n`:

```csharp
static async Task ReadLinesAsync(
    PipeReader reader,
    CancellationToken ct)
{
    while (true)
    {
        var result = await reader.ReadAsync(ct);
        var buffer = result.Buffer;

        while (TryReadLine(ref buffer, out var line))
        {
            Process(line);
        }

        reader.AdvanceTo(buffer.Start, buffer.End);

        if (result.IsCompleted)
            break;
    }

    await reader.CompleteAsync();
}

static bool TryReadLine(
    ref ReadOnlySequence<byte> buffer,
    out ReadOnlySequence<byte> line)
{
    var position = buffer.PositionOf((byte)'\n');
    if (position is null)
    {
        line = default;
        return false;
    }

    line = buffer.Slice(0, position.Value);
    buffer = buffer.Slice(buffer.GetPosition(1, position.Value));
    return true;
}
```

## 5. Real production scenario

Một TCP ingestion service nhận telemetry frame liên tục. Implementation ban đầu dùng `NetworkStream.ReadAsync` + `byte[]` + `Array.Copy` để giữ leftover bytes giữa các reads. Khi throughput tăng, allocation và memory copy trở thành bottleneck.

Chuyển sang `Pipelines` giúp parser làm việc trực tiếp trên segmented buffer và giảm copying, nhưng chỉ đáng giá vì profiling đã xác nhận I/O parsing là hot path.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng đều dù throughput không đổi.

**Evidence** → heap không chứa business object lớn, nhưng pipeline buffers retained lâu.

**Hypothesis** → consumer không advance `consumed` đúng vị trí.

**Diagnosis** → trace buffer length sau mỗi read, kiểm tra `AdvanceTo` và protocol parser.

**Fix** → advance phần đã parse xong, giữ lại đúng incomplete frame.

**Verification** → stress test nhiều partial frames và theo dõi allocation/working set.

## 7. Common mistakes

* Giả định một `ReadAsync` tương ứng một message.
* Convert toàn bộ sequence sang array/string mỗi lần đọc.
* Dùng `examined` và `consumed` cùng một cách máy móc.
* Giữ reference vào buffer sau khi đã advance.
* Dùng `Pipelines` cho workload nhỏ, nơi `Stream` đơn giản hơn.

## 8. Alternatives

* `Stream`: đơn giản, phù hợp đa số business I/O.
* `ArrayPool<T>`: giảm allocation nhưng ownership thủ công hơn.
* `MemoryPool<T>`: phù hợp khi cần explicit memory ownership.
* `Channel<T>`: tốt cho message-level producer/consumer, không thay thế byte-stream parser.

## 9. Trade-offs

### Advantages

* Giảm copying và allocation trong streaming hot path.
* Hỗ trợ fragmented input tự nhiên.
* Có coordination/backpressure tốt hơn buffer thủ công.

### Costs / Risks

* API khó hiểu hơn `Stream`.
* Sai `AdvanceTo` tạo bug memory/performance tinh vi.
* Không đáng complexity nếu throughput thấp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu network reads không trùng ranh giới logical message.

### Middle

Có thể parse `ReadOnlySequence<byte>` và advance buffer đúng.

### Senior

Biết điều tra buffer retention, copying và backpressure dưới load.

### Technical Lead / Architect

Chỉ đưa `Pipelines` vào nơi profiling chứng minh cần throughput/latency cao; tránh lan abstraction này vào business layer.

## 11. Key takeaway

* `Pipelines` giải quyết streaming buffer management, không chỉ là API đọc nhanh hơn.
* `AdvanceTo` là phần của correctness và memory lifetime.
* Với workload bình thường, `Stream` có thể là lựa chọn tốt hơn.

# 2. ASP.NET Core Response Compression: dùng Brotli/gzip đúng boundary thay vì nén mọi response và tăng CPU vô ích

## 1. What is it?

Response Compression middleware nén HTTP response dựa trên client capability, thường thông qua `Accept-Encoding: br, gzip`.

Nó đánh đổi CPU để giảm bytes truyền qua network.

## 2. Why does it exist?

JSON, HTML, CSS và JavaScript thường compress rất tốt. Khi payload lớn hoặc network chậm, giảm transfer size có thể cải thiện latency và bandwidth cost.

Nhưng image/video đã compressed hoặc response cực nhỏ thường không hưởng lợi đáng kể.

## 3. How does it work?

Client gửi:

```http
Accept-Encoding: br, gzip
```

Server chọn encoding phù hợp và trả:

```http
Content-Encoding: br
Vary: Accept-Encoding
```

`Vary` rất quan trọng để CDN/proxy không dùng nhầm compressed representation cho client khác.

## 4. Practical implementation

```csharp
builder.Services.AddResponseCompression(options =>
{
    options.EnableForHttps = true;
    options.Providers.Add<BrotliCompressionProvider>();
    options.Providers.Add<GzipCompressionProvider>();
});

builder.Services.Configure<BrotliCompressionProviderOptions>(options =>
{
    options.Level = CompressionLevel.Fastest;
});

var app = builder.Build();
app.UseResponseCompression();
```

Không nên mặc định chọn compression level cao nhất trên API throughput lớn; CPU cost cần được đo.

## 5. Real production scenario

Một catalog API trả JSON 400 KB. Qua internet mobile, response latency đáng kể dù backend xử lý nhanh. Brotli giảm payload còn khoảng nhỏ hơn nhiều và cải thiện transfer time.

Ngược lại, nén thumbnail JPEG chỉ tăng CPU mà gần như không giảm size.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU application tăng sau khi bật compression, nhưng p95 không cải thiện.

**Evidence** → payload trung bình nhỏ, network không phải bottleneck.

**Hypothesis** → compression cost lớn hơn lợi ích.

**Diagnosis** → so sánh response size, CPU/request, throughput và latency với compression on/off.

**Fix** → giới hạn MIME types, tuning level hoặc để CDN nén static content.

**Verification** → load test lại với traffic profile thực tế.

## 7. Common mistakes

* Nén binary formats đã compressed.
* Chọn compression level tối đa trong hot path.
* Quên `Vary: Accept-Encoding` ở caching layer tự custom.
* Nén ở cả origin và proxy theo cách gây duplicate work.
* Bật compression rồi kết luận nhanh hơn mà không đo CPU/network.

## 8. Alternatives

* CDN/edge compression cho static assets.
* Pre-compressed `.br`/`.gz` assets.
* HTTP payload nhỏ hơn nhờ projection/pagination.
* Không compress nếu network không phải bottleneck.

## 9. Trade-offs

### Advantages

* Giảm transfer size và bandwidth.
* Có thể cải thiện latency trên mạng chậm.

### Costs / Risks

* Tăng CPU.
* Làm debugging caching/proxy phức tạp hơn.
* Lợi ích thấp với payload nhỏ hoặc đã compressed.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu compression đổi CPU lấy bandwidth.

### Middle

Cấu hình middleware, MIME type và verify headers.

### Senior

Đo CPU, payload, p95/p99 và hiểu CDN/proxy interaction.

### Technical Lead / Architect

Quyết định compression nằm ở app hay edge dựa trên topology và cost model.

## 11. Key takeaway

* Compression là performance trade-off, không phải checkbox miễn phí.
* JSON/text thường hưởng lợi; media đã compressed thường không.
* Phải đo cả network gain lẫn CPU cost.

# 3. EF Core `DbContext` pooling: giảm allocation nhưng phải kiểm soát state leakage giữa requests

## 1. What is it?

`AddDbContextPool` tái sử dụng các `DbContext` instance thay vì tạo instance mới cho mỗi scope.

Mental model là object pooling: context được reset rồi trả lại pool, không phải một singleton DbContext dùng chung concurrent.

## 2. Why does it exist?

Tạo `DbContext` thường không quá đắt, nhưng ở service throughput rất cao, setup internal services và allocations lặp lại có thể đáng kể.

Pooling giảm overhead đó. Đổi lại, mọi mutable per-request state gắn vào context phải được xử lý cẩn thận.

## 3. How does it work?

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Khi scope kết thúc, EF Core reset internal state trước khi đưa context về pool.

Nhưng state custom do application thêm vào context không tự động luôn được hiểu/reset đúng theo ý business.

## 4. Practical implementation

Rủi ro phổ biến là tenant state:

```csharp
public sealed class AppDbContext : DbContext
{
    public Guid TenantId { get; set; }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Order>()
            .HasQueryFilter(x => x.TenantId == TenantId);
    }
}
```

Nếu `TenantId` được set mutable trên pooled context mà reset không đúng, request sau có thể thấy tenant cũ.

Thiết kế tốt hơn thường tách tenant-aware factory/boundary rõ ràng và test reuse behavior.

## 5. Real production scenario

Một multi-tenant SaaS bật DbContext pooling để giảm allocation. Sau optimization, security test phát hiện một số query hiếm hoi sử dụng tenant state của request trước.

Root cause không phải EF query filter, mà là application gắn mutable request state trực tiếp vào pooled object.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu tenant khác xuất hiện rất hiếm dưới load concurrent.

**Evidence** → chỉ xảy ra khi pooling bật.

**Hypothesis** → mutable context state survive reuse.

**Diagnosis** → audit custom fields/properties/interceptors và reproduce với pool nhỏ + alternating tenants.

**Fix** → loại bỏ mutable request state khỏi pooled context hoặc dùng factory reset rõ ràng.

**Verification** → integration test nhiều tenant qua hàng nghìn iterations.

## 7. Common mistakes

* Nghĩ pooling biến DbContext thành thread-safe.
* Bật pooling trước khi đo context creation overhead.
* Gắn tenant/user state trực tiếp vào context mà không kiểm soát reset.
* Nhầm DbContext pooling với database connection pooling.
* Giữ reference context ra ngoài DI scope.

## 8. Alternatives

* `AddDbContext`: đơn giản và an toàn cho đa số ứng dụng.
* `IDbContextFactory<T>`: hữu ích khi scope không khớp context lifetime.
* Pooled factory: kiểm soát explicit hơn cho một số workload.

## 9. Trade-offs

### Advantages

* Giảm một phần allocation/setup overhead.
* Có lợi cho throughput cao nếu DbContext creation là hot path.

### Costs / Risks

* Mutable state leakage nếu thiết kế sai.
* Debug lifecycle phức tạp hơn.
* Không giúp query chậm hoặc database bottleneck.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DbContext vẫn không thread-safe dù được pooled.

### Middle

Biết cấu hình pooling và giữ context theo scope.

### Senior

Nhận diện stateful context nguy hiểm, benchmark trước/sau.

### Technical Lead / Architect

Chỉ chấp nhận pooling khi performance evidence đủ rõ và tenant/security boundaries đã được test.

## 11. Key takeaway

* DbContext pooling tối ưu object creation, không tối ưu SQL.
* Pooled object phải gần như stateless giữa requests.
* Multi-tenant state leakage là failure mode nghiêm trọng cần test riêng.

# 4. PostgreSQL advisory locks: điều phối business operation mà không biến lock ứng dụng thành mutex toàn hệ thống

## 1. What is it?

PostgreSQL advisory locks là application-defined locks dựa trên integer key. Database không tự gắn chúng với một row/table cụ thể; application quyết định key đại diện resource nào.

Có session-level và transaction-level advisory locks.

## 2. Why does it exist?

Có những coordination problem không map tự nhiên vào row lock, ví dụ:

* chỉ cho một job generate invoice cho một account,
* serialize một migration-like business operation,
* tránh hai workers xử lý cùng logical resource.

Distributed application memory lock không đủ khi có nhiều instances.

## 3. How does it work?

Transaction-scoped lock:

```sql
SELECT pg_advisory_xact_lock(123456);
```

Lock tự release khi transaction kết thúc.

Try-lock:

```sql
SELECT pg_try_advisory_xact_lock(123456);
```

trả `false` thay vì block.

## 4. Practical implementation

Một application có thể hash stable business identifier thành lock key rồi acquire trong transaction trước khi thực hiện critical section.

```sql
BEGIN;
SELECT pg_advisory_xact_lock(hashtextextended('invoice:customer:42', 0));

-- verify state
-- write invoice

COMMIT;
```

Critical section cần ngắn vì lock vẫn là serialization point.

## 5. Real production scenario

Hai worker cùng nhận trigger generate monthly invoice cho cùng customer. Unique constraint có thể chặn duplicate row cuối cùng, nhưng hai workers vẫn thực hiện expensive calculation và external calls.

Advisory lock có thể serialize phần database-owned critical section, miễn là mọi code path đều tuân theo cùng convention.

## 6. Failure scenario & troubleshooting

**Symptom** → requests treo chờ lock lâu.

**Evidence** → `pg_locks` cho thấy advisory lock contention.

**Hypothesis** → critical section quá rộng hoặc key quá thô.

**Diagnosis** → map lock key về business operation, đo transaction duration.

**Fix** → dùng finer-grained key, `try` lock hoặc rút ngắn transaction.

**Verification** → concurrency test theo cùng và khác resources.

## 7. Common mistakes

* Dùng một global lock key cho mọi customer.
* Giữ session-level lock rồi quên release.
* Thực hiện remote HTTP call lâu bên trong locked transaction.
* Tin rằng advisory lock được database enforce với row update; nó chỉ hoạt động nếu application hợp tác.
* Không có timeout/failure behavior.

## 8. Alternatives

* Unique constraint + retry.
* Row-level `SELECT ... FOR UPDATE` nếu resource map trực tiếp vào row.
* Distributed lock service/Redis lease khi coordination không nằm ở PostgreSQL boundary.
* Queue partitioning theo resource key.

## 9. Trade-offs

### Advantages

* Coordination nằm trong database transaction boundary.
* Không cần thêm infrastructure.
* Key linh hoạt cho logical resources.

### Costs / Risks

* Application-enforced convention.
* Dễ tạo contention khó nhìn nếu key design tệ.
* Không phù hợp critical section dài hoặc cross-system.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu lock dùng để serialize concurrent work.

### Middle

Phân biệt transaction-level và session-level advisory lock.

### Senior

Thiết kế key granularity, timeout và contention diagnostics.

### Technical Lead / Architect

Quyết định coordination nên nằm ở DB, queue hay distributed lock service dựa trên ownership và failure model.

## 11. Key takeaway

* Advisory lock là cooperative application lock do PostgreSQL giữ.
* Transaction-scoped lock thường an toàn hơn session-scoped cho business workflow.
* Lock key và critical-section duration quyết định khả năng scale.

# 5. Elasticsearch shard sizing và oversharding: nhiều shard hơn không đồng nghĩa scale tốt hơn

## 1. What is it?

Elasticsearch index được chia thành primary shards; mỗi shard là một Lucene index độc lập. Replica shards cung cấp redundancy và có thể phục vụ reads.

Shard là unit của distribution, recovery và nhiều hoạt động query/indexing.

## 2. Why does it exist?

Một index có thể lớn hơn khả năng của một node. Sharding cho phép phân phối dữ liệu và workload qua nhiều nodes.

Nhưng mỗi shard cũng có metadata, heap, file handles, segments và scheduling overhead.

## 3. How does it work?

Query thường fan out đến relevant shards rồi coordinator merge kết quả:

```text
Search request
    ↓
Coordinator
  ↙  ↓  ↘
S1  S2  S3
  ↘  ↓  ↙
 merge top hits
```

Nếu có hàng nghìn tiny shards, một query đơn giản có thể phải coordinate quá nhiều sub-queries.

## 4. Practical implementation

Thay vì tạo một index/ngày với nhiều primary shards cho low-volume data, cần estimate data size và retention.

Ví dụ strategy:

* rollover theo size/time,
* giữ shard size trong vùng phù hợp với workload,
* dùng ILM để rollover/merge/delete,
* benchmark search/index latency với production-like documents.

Không có một shard-size magic number đúng cho mọi cluster.

## 5. Real production scenario

Log cluster tạo 20 indices/ngày, mỗi index 5 primary shards dù mỗi index chỉ vài trăm MB. Sau vài tháng, cluster có hàng nghìn shards, master heap tăng và recovery chậm.

Vấn đề không phải thiếu nodes; data được chia quá vụn.

## 6. Failure scenario & troubleshooting

**Symptom** → cluster state update chậm, search latency tăng dù data volume chưa lớn.

**Evidence** → shard count cao, nhiều shards rất nhỏ.

**Hypothesis** → oversharding.

**Diagnosis** → kiểm tra shard size distribution, node heap, query fan-out, recovery time.

**Fix** → rollover policy mới, shrink/reindex khi cần, giảm primary shard count.

**Verification** → theo dõi heap, cluster state latency và search p95.

## 7. Common mistakes

* Tạo nhiều shards “để scale future” mà không có data estimate.
* Một tenant = một index/shard bất kể tenant nhỏ thế nào.
* Tăng replicas để chữa write bottleneck.
* Không tính recovery time khi shard quá lớn.
* Chỉ nhìn disk, bỏ qua heap/cluster-state overhead.

## 8. Alternatives

* Shared index với tenant field.
* Data streams + ILM rollover.
* Reindex sang topology khác khi scale thay đổi.
* SQL/full-text khác nếu search requirement đơn giản hơn.

## 9. Trade-offs

### Advantages

* Sharding cho horizontal distribution và recovery parallelism.
* Replica cải thiện availability và read capacity trong một số workload.

### Costs / Risks

* Quá nhiều shard tăng coordination/metadata overhead.
* Shard quá lớn làm recovery chậm.
* Topology thay đổi thường cần reindex/rollover planning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu shard là một Lucene index độc lập.

### Middle

Đọc shard distribution và index settings.

### Senior

Liên hệ shard count với heap, fan-out và recovery.

### Technical Lead / Architect

Thiết kế index lifecycle từ data growth, retention, search SLA và recovery objective thay vì theo template cố định.

## 11. Key takeaway

* Shard là capacity unit nhưng cũng là overhead unit.
* Oversharding có thể làm cluster chậm trước khi hết disk.
* Shard topology phải dựa trên data volume và workload thực tế.

# 6. Event schema evolution: thay đổi integration event mà không phá consumer cũ

## 1. What is it?

Event schema evolution là cách thay đổi contract của message qua thời gian trong hệ thống event-driven mà consumer cũ vẫn tiếp tục hoạt động.

Integration event là public contract giữa bounded contexts/services, không phải DTO nội bộ muốn sửa lúc nào cũng được.

## 2. Why does it exist?

Producer và consumer hiếm khi deploy atomically. Nếu producer rename/remove field và publish ngay, consumer chưa nâng cấp có thể fail hàng loạt.

Đây là deployment-coupling problem, không chỉ serialization problem.

## 3. How does it work?

Thay đổi backward-compatible thường là additive:

```json
{
  "eventType": "OrderPlaced",
  "version": 2,
  "orderId": "...",
  "currency": "USD",
  "channel": "web"
}
```

Consumer cũ bỏ qua field mới `channel`; consumer mới hiểu cả v1/v2 khi cần.

Breaking change có thể yêu cầu event version mới hoặc translation layer.

## 4. Practical implementation

C# consumer nên tránh phụ thuộc cứng vào fields không cần thiết:

```csharp
public sealed record OrderPlacedV2(
    Guid OrderId,
    string Currency,
    string? Channel);
```

Producer không nên đổi meaning của field cũ mà giữ nguyên tên.

Contract tests có thể verify serialized samples cho consumer expectations.

## 5. Real production scenario

Order team đổi `Total` từ decimal đơn currency thành money object `{ amount, currency }`. Nếu đổi in-place, analytics consumer cũ deserialize fail.

Giải pháp an toàn hơn là giữ contract cũ trong compatibility window hoặc publish event version mới rồi migrate consumers.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog tăng ngay sau producer deploy.

**Evidence** → consumer deserialize exceptions cho field/type mới.

**Hypothesis** → schema breaking change.

**Diagnosis** → compare payload trước/sau deploy và consumer contract versions.

**Fix** → rollback producer hoặc restore backward-compatible payload; lên migration plan.

**Verification** → replay representative messages qua old/new consumers.

## 7. Common mistakes

* Rename/remove field mà không compatibility window.
* Reuse cùng event name nhưng đổi semantic meaning.
* Publish internal EF entity trực tiếp làm event.
* Không giữ sample contracts trong tests.
* Nghĩ schema registry tự động giải quyết business semantics.

## 8. Alternatives

* Versioned event types.
* Envelope với explicit schema version.
* Upcaster/translator tại consumer boundary.
* API synchronous nếu coupling/deployment model phù hợp hơn.

## 9. Trade-offs

### Advantages

* Cho phép producer/consumer deploy độc lập.
* Giảm incident do contract drift.
* Tạo migration path có kiểm soát.

### Costs / Risks

* Phải support nhiều versions trong một giai đoạn.
* Contract governance và testing tăng.
* Event cũ có thể tồn tại lâu trong replay/archive.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu message contract là interface giữa services.

### Middle

Thiết kế additive change và tolerant deserialization.

### Senior

Quản lý compatibility window, replay và version migration.

### Technical Lead / Architect

Đặt ownership, contract policy và deprecation process giữa bounded contexts.

## 11. Key takeaway

* Event schema là public integration contract.
* Additive change thường an toàn hơn breaking replacement.
* Producer/consumer deploy độc lập yêu cầu explicit compatibility strategy.

# 7. Azure SQL transient failures và connection resiliency: retry đúng chỗ mà không nhân đôi transaction side effects

## 1. What is it?

Azure SQL có thể gặp transient failures: connection drop, failover, throttling hoặc brief service interruption. Connection resiliency cho phép client retry các operation được xem là transient.

EF Core SQL Server provider hỗ trợ execution strategy.

## 2. Why does it exist?

Cloud database không hứa mọi network/database operation luôn thành công lần đầu. Một hệ thống production cần phân biệt transient failure với permanent error.

Nhưng retry mù quáng có thể nhân đôi business effect nếu outcome trước đó không rõ.

## 3. How does it work?

```csharp
options.UseSqlServer(connectionString, sql =>
{
    sql.EnableRetryOnFailure(
        maxRetryCount: 5,
        maxRetryDelay: TimeSpan.FromSeconds(10),
        errorNumbersToAdd: null);
});
```

Execution strategy retry operation khi gặp lỗi được phân loại transient.

Explicit transaction cần phối hợp với execution strategy vì retry phải replay cả transactional unit.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    db.Orders.Add(order);
    await db.SaveChangesAsync(ct);

    await tx.CommitAsync(ct);
});
```

External side effects không nên nằm trong replayable delegate nếu không idempotent.

## 5. Real production scenario

Azure SQL failover gây một số requests nhận transient connection error. Không retry, user thấy 500 dù database hồi phục sau vài giây.

Sau khi bật retry, success rate tốt hơn. Nhưng một handler gọi payment API bên trong retry block có nguy cơ charge hai lần nếu operation replay.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate external action sau database transient fault.

**Evidence** → execution strategy replay toàn delegate.

**Hypothesis** → non-idempotent side effect nằm trong retry scope.

**Diagnosis** → trace retry attempt + correlation/idempotency key.

**Fix** → tách external effect, dùng Outbox/idempotency hoặc redesign transaction boundary.

**Verification** → inject transient failure và xác nhận business effect chỉ xảy ra một lần.

## 7. Common mistakes

* Retry mọi exception.
* Retry transaction mà không hiểu replay semantics.
* Gọi external API không idempotent trong execution strategy.
* Tăng retry count quá cao làm latency tail xấu.
* Không monitor retry rate như early warning signal.

## 8. Alternatives

* Application-level retry với Polly cho dependency khác.
* Queue-based async workflow.
* Fail fast nếu operation không an toàn để retry.
* Circuit Breaker cho sustained failure, không thay thế transient retry.

## 9. Trade-offs

### Advantages

* Che được brief transient outages khỏi user.
* Tăng resilience cho cloud database connectivity.

### Costs / Risks

* Retry tăng latency và load.
* Replay có thể duplicate side effects.
* Có thể che vấn đề capacity nếu retry rate không được quan sát.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transient failure khác permanent failure.

### Middle

Cấu hình `EnableRetryOnFailure` và đọc retry logs.

### Senior

Thiết kế retry boundary với transaction/idempotency.

### Technical Lead / Architect

Xác định operation nào có thể replay an toàn và khi nào cần async messaging/outbox thay vì retry trực tiếp.

## 11. Key takeaway

* Retry chỉ an toàn khi unit of work có replay semantics rõ ràng.
* Execution strategy không biến external side effects thành idempotent.
* Retry rate phải được monitor, không chỉ dùng như hidden recovery mechanism.

# 8. TeamCity build chain và artifact promotion: tách build khỏi deploy để cùng một artifact đi xuyên các môi trường

## 1. What is it?

TeamCity build chain cho phép nhiều build configurations phụ thuộc nhau qua snapshot/artifact dependencies.

Một release pipeline tốt thường build artifact một lần rồi promote chính artifact đó qua test/staging/production.

## 2. Why does it exist?

Nếu mỗi môi trường rebuild source code riêng, cùng commit vẫn có thể tạo binary khác do dependency restore, toolchain, timestamp hoặc config khác.

Điều đó phá tính reproducibility và làm production không còn deploy đúng artifact đã test.

## 3. How does it work?

```text
Commit
  ↓
Build + Unit Test
  ↓ artifact v1.4.27
Integration Test
  ↓ same artifact
Staging Deploy
  ↓ same artifact
Production Deploy
```

Environment-specific config được inject khi deploy/runtime thay vì rebuild binary.

## 4. Practical implementation

TeamCity có thể tạo build configuration `Build-App` publish ZIP/container image, sau đó `Deploy-Staging` dùng artifact dependency từ đúng build chain.

Artifact cần version immutable, ví dụ:

```text
myapp-1.4.27+sha.7607f6a.zip
```

Production deployment chỉ chọn artifact đã vượt qua validation stages.

## 5. Real production scenario

Một team rebuild .NET app cho Production sau khi QA sign-off. Giữa hai builds, NuGet floating dependency thay đổi. Production binary khác Staging dù source commit giống nhau.

Build-once/promote-many loại bỏ class lỗi này.

## 6. Failure scenario & troubleshooting

**Symptom** → staging pass nhưng production behavior khác ngay khi deploy cùng commit.

**Evidence** → artifact hashes khác nhau giữa environments.

**Hypothesis** → pipeline rebuild ở mỗi stage.

**Diagnosis** → trace artifact provenance và dependency lock state.

**Fix** → build once, publish immutable artifact, promote same checksum.

**Verification** → compare artifact digest ở staging/production.

## 7. Common mistakes

* Rebuild cho từng environment.
* Bundle production secrets vào artifact.
* Dùng floating package version không lock.
* Không lưu artifact metadata/commit SHA.
* Deploy thành công nhưng bỏ health validation.

## 8. Alternatives

* Jenkins pipeline với immutable artifacts.
* Azure DevOps multi-stage pipelines.
* GitHub Actions + artifact/container registry.
* Octopus Deploy cho release promotion.

## 9. Trade-offs

### Advantages

* Reproducibility tốt hơn.
* Artifact đã test chính là artifact production.
* Rollback rõ ràng theo version.

### Costs / Risks

* Cần artifact repository/registry và retention policy.
* Config phải externalize đúng.
* Build chain phức tạp nếu dependency graph quá lớn.

## 10. Junior → Middle → Senior → Technical Lead

Hiểu artifact là output immutable của build.

### Senior

Theo dõi provenance, checksum, config separation và rollback.

### Technical Lead / Architect

Thiết kế pipeline theo principle build-once/promote-many, health validation và controlled rollback.

## 11. Key takeaway

* Cùng commit không đảm bảo cùng binary nếu rebuild nhiều lần.

# 9. Coordinated omission trong load testing: vì sao benchmark có thể báo p99 đẹp dù production đang nghẽn

## 1. What is it?

Coordinated omission là lỗi đo latency khi load generator chờ request trước hoàn thành rồi mới gửi request tiếp theo. Khi system chậm, generator vô tình giảm arrival rate và bỏ sót thời gian mà user thật vẫn tiếp tục gửi traffic.

Kết quả là latency percentile trông đẹp giả tạo.

## 2. Why does it exist?

Closed-loop benchmark thường chạy:

```text
send request
wait response
send next
```

Nếu response tăng từ 100 ms lên 5 s, generator gửi ít request hơn đúng lúc hệ thống đang gặp vấn đề.

Production traffic thường gần open-loop hơn: arrivals vẫn xảy ra độc lập với latency hiện tại.

## 3. How does it work?

Giả sử 100 requests/s dự kiến. Service pause 10 giây.

Closed-loop tool có thể chỉ record vài requests mất 10 giây, vì các request lẽ ra đến trong pause chưa từng được gửi.

Open-loop model vẫn schedule arrivals, cho thấy queueing delay và p99 thực tế xấu hơn nhiều.

## 4. Practical implementation

Khi load test, cần định nghĩa arrival rate độc lập với response completion nếu workload production như vậy.

Cùng lúc monitor:

* p50/p95/p99,
* request rate,
* queue length,
* CPU,
* GC,
* ThreadPool,
* DB latency,
* connection pools.

Không chỉ nhìn tool summary.

## 5. Real production scenario

Một API load test báo p99 = 400 ms ở 500 virtual users. Production lại có p99 vài giây khi dependency chậm ngắn hạn.

Review cho thấy load generator dùng fixed virtual-user loop nên traffic tự giảm khi latency tăng. Test không mô phỏng arrival pattern thực.

## 6. Failure scenario & troubleshooting

**Symptom** → benchmark ổn nhưng production tail latency xấu.

**Evidence** → load generator request rate tụt đúng lúc service latency tăng.

**Hypothesis** → coordinated omission.

**Diagnosis** → plot request arrival rate cùng latency timeline.

**Fix** → dùng arrival-rate model/open-loop test hoặc tool có correction phù hợp.

**Verification** → gây deliberate pause và kiểm tra histogram phản ánh queueing delay.

## 7. Common mistakes

* Chỉ report average latency.
* Không kiểm tra actual achieved request rate.
* Dùng virtual users nhưng tưởng tương đương fixed RPS.
* Bỏ qua warm-up và GC/JIT effects.
* Benchmark local rồi suy luận trực tiếp production capacity.

## 8. Alternatives

* Closed-loop test vẫn hữu ích cho user-session workflow nếu đó là behavior thật.
* Open-loop/arrival-rate test cho service capacity.
* Replay traffic pattern từ production.

## 9. Trade-offs

### Advantages

* Correct arrival model cho tail latency realistic hơn.
* Phát hiện queue buildup và saturation rõ hơn.

### Costs / Risks

* Open-loop test có thể tạo tải cực lớn khi system chậm.
* Cần safety limit để không phá shared environment.
* Kịch bản phức tạp hơn simple virtual-user test.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu average không đủ; cần percentile.

### Middle

Biết kiểm tra achieved RPS và latency distribution.

### Senior

Nhận diện closed-loop bias, queueing và coordinated omission.

### Technical Lead / Architect

Thiết kế performance test từ production arrival model, SLO và bottleneck hypotheses.

## 11. Key takeaway

* Benchmark có thể sai ngay cả khi số liệu được ghi chính xác.
* Arrival model quyết định ý nghĩa của latency percentile.
* Luôn nhìn latency cùng achieved throughput và saturation signals.

# 10. Content Security Policy với nonce/hash: giảm blast radius của XSS mà không phá frontend runtime

## 1. What is it?

Content Security Policy (CSP) là browser security policy giới hạn nguồn script/style/resource được phép chạy hoặc load.

CSP không thay thế output encoding/sanitization; nó là defense-in-depth giúp giảm khả năng injected content trở thành executable script.

## 2. Why does it exist?

Nếu attacker đưa được:

```html
<script>stealCookies()</script>
```

vào rendered HTML, browser mặc định có thể execute. CSP có thể chặn inline script nếu không có nonce/hash được cho phép.

## 3. How does it work?

Header ví dụ:

```http
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-AbCd1234'; object-src 'none'; base-uri 'self'
```

Server tạo nonce random cho mỗi response và gắn cùng nonce vào script hợp lệ:

```html
<script nonce="AbCd1234" src="/app.js"></script>
```

Injected script không biết nonce hợp lệ nên bị browser chặn.

## 4. Practical implementation

ASP.NET Core middleware có thể generate cryptographically random nonce per response và expose qua request context/rendering layer.

```csharp
var nonceBytes = RandomNumberGenerator.GetBytes(16);
var nonce = Convert.ToBase64String(nonceBytes);

context.Response.Headers.ContentSecurityPolicy =
    $"default-src 'self'; script-src 'self' 'nonce-{nonce}'; " +
    "object-src 'none'; base-uri 'self'";
```

Production code cần cấu hình đầy đủ cho CDN, analytics, fonts và API endpoints thực tế.

## 5. Real production scenario

Marketing site dùng CMS cho phép rich text. Dù HTML sanitizer tồn tại, risk XSS vẫn cao vì nhiều editor integrations và third-party widgets.

CSP ở `Report-Only` mode trước giúp thu thập violations, sau đó policy được siết dần và enforce.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend script hợp lệ ngừng chạy sau khi bật CSP.

**Evidence** → browser console có CSP violation report.

**Hypothesis** → policy thiếu allowed source/nonce hoặc third-party script dùng unsafe inline code.

**Diagnosis** → xem `SecurityPolicyViolationEvent`, browser console và report endpoint.

**Fix** → thêm nonce/hash cụ thể hoặc thay third-party pattern; tránh mở rộng ngay bằng `'unsafe-inline'`.

**Verification** → regression test UI và confirm malicious inline script vẫn bị block.

## 7. Common mistakes

* Bật `'unsafe-inline'` rồi tưởng CSP vẫn chống inline XSS tốt.
* Reuse nonce cố định giữa responses.
* Dùng CSP thay cho HTML encoding/sanitization.
* Whitelist domain quá rộng.
* Enforce policy ngay production mà không chạy `Report-Only` trước.

## 8. Alternatives

* Strict output encoding và sanitization: bắt buộc, không phải alternative thực sự.
* Hash-based CSP cho static inline scripts.
* Trusted Types cho DOM XSS hardening ở frontend phức tạp.

## 9. Trade-offs

### Advantages

* Giảm impact của nhiều XSS injection paths.
* Cho browser enforce executable-content boundary.
* Report violations giúp phát hiện unsafe frontend behavior.

### Costs / Risks

* Third-party scripts khó tương thích.
* Nonce plumbing cần server-rendering discipline.
* Policy quá rộng tạo cảm giác an toàn giả.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CSP giới hạn code browser được phép execute/load.

### Middle

Đọc violation và cấu hình basic directives.

### Senior

Triển khai nonce/hash, Report-Only rollout và phân tích third-party risk.

### Technical Lead / Architect

Xác định CSP baseline toàn platform, exception governance và boundary với CMS/third-party scripts.

## 11. Key takeaway

* CSP là defense-in-depth cho XSS, không thay thế sanitization/encoding.
* Nonce phải random per response và chỉ gắn vào script tin cậy.
* Rollout bằng `Report-Only` giúp siết policy mà giảm breakage.
