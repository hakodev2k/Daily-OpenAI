# 1. C# `IAsyncEnumerable<T>`: streaming dữ liệu với backpressure tự nhiên và cancellation thay vì materialize toàn bộ collection

## 1. What is it?

`IAsyncEnumerable<T>` biểu diễn một sequence mà từng phần tử có thể xuất hiện bất đồng bộ. Consumer dùng `await foreach` và chỉ yêu cầu phần tử tiếp theo khi đã sẵn sàng xử lý phần tử hiện tại.

Mental model:

```text
Producer -> item 1 -> consumer
         -> item 2 -> consumer
         -> ...
```

Khác `Task<List<T>>`, producer không bắt buộc tạo toàn bộ collection trước khi consumer nhận dữ liệu.

## 2. Why does it exist?

Materialize 100.000 rows trước khi trả kết quả làm tăng memory, time-to-first-byte và latency. Streaming hữu ích khi dữ liệu lớn, sinh dần hoặc đến từ I/O bất đồng bộ.

Nó cũng tạo một dạng backpressure tự nhiên: consumer gọi `MoveNextAsync` cho phần tử tiếp theo thay vì producer đẩy vô hạn vào memory.

## 3. How does it work?

Compiler chuyển async iterator thành state machine. Mỗi `yield return` tạm dừng iterator; consumer tiếp tục bằng `MoveNextAsync`.

Cancellation phải được propagate vào iterator, đặc biệt khi client disconnect.

## 4. Practical implementation

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken cancellationToken)
{
    await foreach (var order in db.Orders
        .AsNoTracking()
        .OrderBy(x => x.Id)
        .AsAsyncEnumerable()
        .WithCancellation(cancellationToken))
    {
        yield return new OrderDto(order.Id, order.Total);
    }
}
```

Consumer:

```csharp
await foreach (var order in service.StreamOrdersAsync(cancellationToken))
{
    await writer.WriteAsync(order, cancellationToken);
}
```

## 5. Real production scenario

Một export endpoint đọc hàng trăm nghìn records. Phiên bản cũ gọi `ToListAsync`, khiến mỗi request giữ hàng trăm MB. Chuyển sang streaming giảm peak memory và client nhận dữ liệu sớm hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → client đã disconnect nhưng SQL query vẫn chạy lâu.

**Evidence** → cancellation không tới iterator/database call.

**Hypothesis** → async sequence không propagate request token.

**Diagnosis** → trace request abort và database duration.

**Fix** → dùng `[EnumeratorCancellation]`, `WithCancellation` và truyền token tới I/O.

**Verification** → hủy request giữa stream và xác nhận query dừng.

## 7. Common mistakes

* Streaming nhưng bên trong vẫn `ToListAsync` toàn bộ.
* Giữ `DbContext`/connection quá lâu mà không hiểu lifecycle.
* Không xử lý cancellation.
* Dùng streaming cho response nhỏ làm complexity tăng vô ích.

## 8. Alternatives

`Task<List<T>>` đơn giản hơn cho dataset nhỏ. Pagination phù hợp UI navigation. `Channel<T>` phù hợp producer/consumer độc lập cần buffering và explicit backpressure.

## 9. Trade-offs

### Advantages

* Giảm peak memory.
* Time-to-first-item thấp hơn.
* Hợp với large sequential workloads.

### Costs / Risks

* Resource lifetime kéo dài theo stream.
* Error có thể xảy ra sau khi response đã bắt đầu.
* Retry toàn operation khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async stream trả từng phần tử thay vì toàn bộ list.

### Middle

Implement `await foreach`, cancellation và disposal đúng.

### Senior

Đánh giá connection lifetime, serialization, partial failure và backpressure.

### Technical Lead / Architect

Chọn streaming, pagination hay batching dựa trên UX, resource budget và failure semantics.

## 11. Key takeaway

* Streaming giảm materialization cost nhưng kéo dài resource lifetime.
* Cancellation là phần bắt buộc của production streaming.
* Không dùng streaming chỉ vì API hỗ trợ nó.

# 2. ASP.NET Core Health Checks: phân biệt liveness, readiness và dependency health để orchestrator không tự khuếch đại incident

## 1. What is it?

Health check là machine-readable signal về khả năng process đang sống và khả năng instance phục vụ traffic. Liveness và readiness trả lời hai câu hỏi khác nhau.

## 2. Why does it exist?

Nếu một endpoint `/health` kiểm tra mọi dependency và orchestrator dùng nó làm liveness, một Redis outage có thể khiến toàn bộ pods restart dù restart không sửa Redis. Health design sai biến dependency incident thành restart storm.

## 3. How does it work?

Liveness nên trả lời “process có bị stuck/broken đến mức cần restart không?”. Readiness trả lời “instance hiện có nên nhận traffic không?”. Dependency check chỉ nên tham gia signal phù hợp với khả năng degrade của application.

## 4. Practical implementation

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, tags: ["ready"])
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready")
});
```

## 5. Real production scenario

API có SQL bắt buộc và Redis optional. Redis lỗi nhưng application có thể fallback SQL. Nếu readiness phụ thuộc Redis, toàn fleet bị rút khỏi load balancer dù service vẫn có thể phục vụ request.

## 6. Failure scenario & troubleshooting

**Symptom** → pods restart liên tục trong dependency outage.

**Evidence** → liveness endpoint gọi SQL/Redis và trả 503.

**Hypothesis** → liveness bị coupling với external dependency.

**Diagnosis** → inspect probe configuration và restart reason.

**Fix** → tách liveness/readiness; dependency optional không nên làm process bị restart.

**Verification** → mô phỏng Redis outage và xác nhận application degrade thay vì restart storm.

## 7. Common mistakes

* Một endpoint dùng cho mọi probe.
* Health check query quá đắt.
* Trả healthy chỉ vì process chạy, dù startup chưa hoàn tất.
* Không monitor health transitions ngoài orchestrator.

## 8. Alternatives

Synthetic monitoring kiểm tra end-to-end từ bên ngoài. Metrics/SLO alerting đo user impact. Chúng bổ sung health probes chứ không thay thế.

## 9. Trade-offs

### Advantages

* Traffic routing và recovery tự động tốt hơn.
* Startup/readiness rõ ràng.

### Costs / Risks

* Probe sai có thể tự gây outage.
* Dependency checks tăng load và coupling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt process alive và service ready.

### Middle

Cấu hình endpoint/tags/probes đúng.

### Senior

Thiết kế degrade behavior và dependency criticality.

### Technical Lead / Architect

Định nghĩa health contract nhất quán cho platform và tránh automation khuếch đại partial failure.

## 11. Key takeaway

* Liveness không phải dependency test tổng hợp.
* Readiness phải phản ánh khả năng nhận traffic thực tế.
* Health automation sai có thể làm incident nặng hơn.

# 3. EF Core `AsNoTrackingWithIdentityResolution`: cân bằng read performance với object identity khi entity graph có duplicate rows

## 1. What is it?

`AsNoTrackingWithIdentityResolution` không giữ entities trong `DbContext` change tracker để update, nhưng vẫn bảo đảm cùng primary key trong một query được materialize thành cùng object instance.

## 2. Why does it exist?

`AsNoTracking` tốt cho read-only queries nhưng join/include có thể làm cùng entity xuất hiện nhiều lần trong result shape. Identity resolution giảm duplicate object instances mà không bật full tracking.

## 3. How does it work?

EF Core dùng một temporary identity map trong quá trình materialization. Sau query, map này không trở thành long-lived tracking state của `DbContext`.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .AsNoTrackingWithIdentityResolution()
    .Include(x => x.Customer)
    .Include(x => x.Items)
    .Where(x => x.CreatedAt >= from)
    .ToListAsync(cancellationToken);
```

Nếu API chỉ cần DTO, projection thường còn tốt hơn:

```csharp
var rows = await db.Orders
    .Where(x => x.CreatedAt >= from)
    .Select(x => new OrderDto(x.Id, x.Customer.Name, x.Total))
    .ToListAsync(cancellationToken);
```

## 5. Real production scenario

Reporting endpoint load graph lớn có shared customer references. `AsNoTracking` giảm tracking memory nhưng duplicate materialization vẫn đáng kể. Identity resolution giảm duplicate instances trong graph.

## 6. Failure scenario & troubleshooting

**Symptom** → memory vẫn cao dù đã bỏ tracking.

**Evidence** → query trả entity graph khổng lồ với nhiều `Include`.

**Hypothesis** → vấn đề là result shape, không phải change tracker.

**Diagnosis** → inspect generated SQL, row count và allocation profile.

**Fix** → projection, pagination hoặc split query; identity resolution chỉ là một lựa chọn trung gian.

**Verification** → đo allocations và query latency lại.

## 7. Common mistakes

* Dùng entity graph cho API DTO đơn giản.
* Nghĩ `AsNoTrackingWithIdentityResolution` luôn nhanh hơn `AsNoTracking`.
* Bật `Include` theo object graph thay vì access pattern.

## 8. Alternatives

`AsTracking` cho update workflow. `AsNoTracking` cho read đơn giản. Projection thường tối ưu nhất khi chỉ cần một subset columns.

## 9. Trade-offs

### Advantages

* Không có long-lived change tracking.
* Tránh duplicate instances trong query graph.

### Costs / Risks

* Temporary identity map vẫn có CPU/memory cost.
* Không giải quyết query shape quá lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu tracking phục vụ update, không cần cho mọi read.

### Middle

Chọn tracking mode theo use case.

### Senior

Đo materialization/allocation và ưu tiên projection khi phù hợp.

### Technical Lead / Architect

Thiết kế read contracts để persistence graph không vô tình trở thành API contract.

## 11. Key takeaway

* No-tracking và identity resolution là hai concern khác nhau.
* Projection thường tốt hơn khi consumer không cần entity graph.
* Tối ưu phải dựa trên result shape và measurement.

# 4. PostgreSQL JSONB + GIN index: schema linh hoạt có kiểm soát thay vì biến relational database thành document store không kỷ luật

## 1. What is it?

`jsonb` lưu JSON ở binary representation hỗ trợ operators và indexing. GIN index phù hợp membership/containment queries trên nhiều keys/values.

## 2. Why does it exist?

Một số attributes thay đổi theo product type hoặc integration payload. Tạo hàng trăm nullable columns không hợp lý, nhưng chuyển toàn model sang document database cũng có thể quá mức.

JSONB cho phép hybrid model: relational columns giữ invariants cốt lõi, JSONB giữ phần linh hoạt.

## 3. How does it work?

Query containment:

```sql
SELECT id, sku
FROM products
WHERE attributes @> '{"color":"black"}';
```

Index:

```sql
CREATE INDEX ix_products_attributes_gin
ON products USING gin (attributes);
```

Planner cân nhắc selectivity/cost; GIN không bảo đảm được dùng cho mọi expression.

## 4. Practical implementation

Giữ các field quan trọng relational:

```sql
CREATE TABLE products (
    id uuid PRIMARY KEY,
    sku text NOT NULL UNIQUE,
    price numeric(18,2) NOT NULL CHECK (price >= 0),
    attributes jsonb NOT NULL DEFAULT '{}'
);
```

Không nên giấu `price`, `tenant_id`, foreign keys hoặc business constraints quan trọng trong JSON chỉ để “linh hoạt”.

## 5. Real production scenario

Marketplace có category-specific attributes: laptop có RAM/CPU, shoe có size/material. Core identity/pricing relational; optional searchable attributes nằm JSONB.

## 6. Failure scenario & troubleshooting

**Symptom** → query JSONB chậm dù có GIN index.

**Evidence** → execution plan dùng sequential scan; predicate dùng function/expression không match index strategy.

**Hypothesis** → index/operator mismatch hoặc predicate selectivity thấp.

**Diagnosis** → `EXPLAIN (ANALYZE, BUFFERS)` và inspect actual rows/I/O.

**Fix** → sửa access pattern, expression index phù hợp hoặc promote hot field thành typed column.

**Verification** → so actual execution plan và buffer reads.

## 7. Common mistakes

* Nhét toàn entity vào JSONB.
* Không validate JSON shape.
* Dùng JSONB để tránh schema migration cho core domain.
* Tạo GIN index lớn cho data ít query.

## 8. Alternatives

Typed relational columns mạnh về constraints/queryability. MongoDB phù hợp khi document model là primary aggregate. Elasticsearch phù hợp full-text/search use case, không phải transactional truth.

## 9. Trade-offs

### Advantages

* Linh hoạt cho sparse/evolving attributes.
* Query/index JSON trực tiếp.

### Costs / Risks

* Type safety và constraints yếu hơn columns.
* GIN index có write/storage cost.
* Dễ trở thành schema-less dumping ground.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu JSONB vẫn nằm trong relational database.

### Middle

Viết containment query và đọc basic plan.

### Senior

Thiết kế index/access pattern, constraints và promotion strategy.

### Technical Lead / Architect

Quyết định dữ liệu nào thực sự flexible và dữ liệu nào phải giữ relational invariants.

## 11. Key takeaway

* JSONB tốt cho flexibility có boundary.
* GIN index phải match operator/access pattern.
* Core business invariants không nên bị giấu trong JSON.

# 5. Elasticsearch refresh interval và near-real-time search: hiểu vì sao write thành công nhưng document chưa lập tức searchable

## 1. What is it?

Elasticsearch là near-real-time search engine. Sau khi index operation thành công, document không nhất thiết lập tức xuất hiện trong search cho tới khi refresh tạo searchable segment/view mới.

## 2. Why does it exist?

Refresh sau từng write sẽ làm giảm indexing throughput vì segment creation/search visibility có cost. Elasticsearch batch visibility để cân bằng write throughput và search freshness.

## 3. How does it work?

Write đi vào indexing structures/translog, sau đó refresh định kỳ làm dữ liệu mới visible cho search. Refresh khác durability: translog/replication liên quan khả năng recovery, còn refresh liên quan search visibility.

## 4. Practical implementation

Không gọi refresh thủ công sau mỗi document. Khi một workflow đặc biệt cần read-after-write search, có thể dùng `refresh=wait_for` có chủ đích thay vì force refresh liên tục.

Trong architecture phổ biến:

```text
SQL source of truth
  -> outbox/change feed
  -> indexer
  -> Elasticsearch
  -> Search API
```

UI nên hiểu search projection có thể lag.

## 5. Real production scenario

Editor publish CMS content rồi ngay lập tức search title mới. Database đã commit nhưng indexing worker và refresh chưa hoàn tất, nên search tạm thời không thấy item.

## 6. Failure scenario & troubleshooting

**Symptom** → data tồn tại trong primary DB nhưng search thiếu lâu hơn bình thường.

**Evidence** → indexing backlog tăng; refresh latency/cluster pressure tăng.

**Hypothesis** → không chỉ NRT delay mà synchronization pipeline đang lag.

**Diagnosis** → kiểm tra outbox/change stream lag, failed indexing, cluster health và refresh metrics.

**Fix** → xử lý bottleneck/failure pipeline; không che bằng force refresh.

**Verification** → đo end-to-end indexing lag percentile.

## 7. Common mistakes

* Coi Elasticsearch là transactional source of truth.
* Force refresh sau mọi write.
* Không expose/monitor indexing lag.
* User flow yêu cầu strong consistency nhưng lại phụ thuộc search projection.

## 8. Alternatives

Query primary DB cho immediate authoritative lookup. Search engine dùng khi full-text/relevance/filtering scale thực sự cần.

## 9. Trade-offs

### Advantages

* Batch refresh hỗ trợ indexing throughput cao.
* Search optimized data structures.

### Costs / Risks

* Eventual search visibility.
* Cần synchronization/recovery pipeline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index success không đồng nghĩa search visibility tức thì.

### Middle

Biết refresh semantics và tránh force refresh mặc định.

### Senior

Đo indexing lag và phân biệt refresh delay với pipeline failure.

### Technical Lead / Architect

Định nghĩa consistency expectation cho từng user journey và source of truth rõ ràng.

## 11. Key takeaway

* Elasticsearch là near-real-time, không phải transactional read model mặc định.
* Refresh frequency đổi freshness lấy indexing cost.
* Monitor end-to-end indexing lag, không chỉ cluster health.

# 6. Anti-Corruption Layer: cô lập model nội bộ khỏi third-party/legacy contract thay vì để external semantics lan khắp domain

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary dịch giữa model/semantics của hệ thống mình và model của external hoặc legacy system.

Nó không chỉ là DTO mapping. Nó bảo vệ ubiquitous language, invariants và dependency direction của bounded context nội bộ.

## 2. Why does it exist?

Third-party API thường có naming, lifecycle và error semantics khác domain nội bộ. Nếu application truyền external DTO xuyên controller/service/domain, mỗi thay đổi vendor lan ra toàn codebase.

## 3. How does it work?

```text
Domain/Application
      |
      v
Internal Port
      ^
      |
ACL Adapter
      |
      v
Vendor API
```

Domain phụ thuộc interface mang ngôn ngữ nội bộ. Infrastructure adapter chuyển request/response/error sang model đó.

Data ownership vẫn thuộc bounded context tương ứng; ACL không tạo distributed transaction magic.

## 4. Practical implementation

```csharp
public interface IPaymentGateway
{
    Task<PaymentResult> AuthorizeAsync(
        PaymentRequest request,
        CancellationToken cancellationToken);
}

public sealed class VendorPaymentGateway(HttpClient http) : IPaymentGateway
{
    public async Task<PaymentResult> AuthorizeAsync(
        PaymentRequest request,
        CancellationToken cancellationToken)
    {
        var vendorRequest = new VendorChargeRequest(request.Amount, request.Currency);
        var response = await http.PostAsJsonAsync("charges", vendorRequest, cancellationToken);

        return response.StatusCode switch
        {
            HttpStatusCode.OK => PaymentResult.Approved(),
            HttpStatusCode.PaymentRequired => PaymentResult.Declined(),
            _ => throw new PaymentGatewayUnavailableException()
        };
    }
}
```

## 5. Real production scenario

Legacy CRM gọi customer “Account” và có status codes `A`, `S`, `X`. Domain mới dùng Customer với explicit lifecycle. ACL map semantics một chỗ thay vì để `status == "A"` xuất hiện khắp business code.

## 6. Failure scenario & troubleshooting

**Symptom** → vendor thêm status mới và application silently map sai.

**Evidence** → tolerant deserialization nhận value nhưng mapping fallback về default business state.

**Hypothesis** → ACL không fail explicitly với unknown semantics.

**Diagnosis** → contract monitoring/log unknown enum values.

**Fix** → explicit unknown handling, contract tests và alerting.

**Verification** → fixture chứa status mới phải fail/route theo defined behavior.

## 7. Common mistakes

* Gọi mọi mapper là ACL dù không có semantic boundary.
* Đưa vendor SDK types vào Domain.
* Che toàn bộ lỗi vendor thành generic exception mất diagnostic context.
* Overengineer ACL cho stable internal service có cùng model.

## 8. Alternatives

Direct integration đơn giản hơn khi coupling thấp/chấp nhận được. Shared contract package phù hợp các services cùng ownership nhưng có versioning cost.

## 9. Trade-offs

### Advantages

* Cô lập vendor/legacy churn.
* Giữ domain language sạch.
* Tập trung resilience và mapping.

### Costs / Risks

* Thêm code và abstraction.
* Có nguy cơ duplicate model không cần thiết.
* Boundary mapping phải được test kỹ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain model.

### Middle

Implement adapter và mapping rõ ràng.

### Senior

Thiết kế error semantics, resilience, observability và contract tests.

### Technical Lead / Architect

Quyết định boundary nào cần protection, ownership và migration strategy nếu vendor bị thay thế.

## 11. Key takeaway

* ACL bảo vệ semantics, không chỉ đổi tên fields.
* External contracts nên dừng ở integration boundary.
* Chỉ thêm ACL khi coupling/churn thực sự đáng cô lập.

# 7. Timeout budget và deadline propagation: giới hạn tổng latency xuyên service thay vì mỗi dependency tự retry theo timeout riêng

## 1. What is it?

Timeout budget là tổng thời gian một operation được phép tiêu tốn. Deadline propagation truyền remaining budget xuống các dependency thay vì mỗi hop bắt đầu một timeout mới độc lập.

## 2. Why does it exist?

Nếu API có SLO 2 giây nhưng gọi ba services, mỗi service timeout 5 giây và retry ba lần, theoretical worst-case vượt xa thời gian client còn chờ. Work tiếp tục sau khi kết quả đã vô nghĩa, gây resource amplification.

## 3. How does it work?

```text
Client deadline: 2s
 API processing: 100ms
 remaining: 1.9s
   -> Service A budget <= 1.5s
      -> DB budget <= remaining
```

Retry phải tiêu từ cùng budget. Mỗi attempt không được reset toàn deadline.

## 4. Practical implementation

```csharp
using var budgetCts = CancellationTokenSource.CreateLinkedTokenSource(requestAborted);
budgetCts.CancelAfter(TimeSpan.FromSeconds(2));

await inventoryClient.ReserveAsync(orderId, budgetCts.Token);
```

Với `HttpClient`, timeout policy và cancellation cần phối hợp; tránh xếp nhiều timeout layers không rõ layer nào thắng.

## 5. Real production scenario

Checkout gọi pricing, inventory và payment. Inventory chậm. Retry policy độc lập khiến request tiếp tục 8 giây dù gateway đã timeout ở 3 giây. Zombie work làm connection pool và ThreadPool pressure tăng.

## 6. Failure scenario & troubleshooting

**Symptom** → gateway trả timeout nhưng backend vẫn có traffic/dependency calls kéo dài sau đó.

**Evidence** → trace spans vượt client request lifetime.

**Hypothesis** → cancellation/deadline không propagate.

**Diagnosis** → inspect trace timing, request abort token và retry configuration.

**Fix** → end-to-end deadline, bounded retries, cancellation propagation.

**Verification** → inject slow dependency và xác nhận downstream work dừng trong budget.

## 7. Common mistakes

* Timeout mỗi hop lớn hơn upstream timeout.
* Retry mà không xét remaining time.
* Catch `OperationCanceledException` rồi tiếp tục work.
* Dùng timeout như substitute cho capacity control.

## 8. Alternatives

Queue/asynchronous workflow phù hợp work không cần synchronous result. Circuit Breaker ngăn gọi dependency unhealthy nhưng không thay deadline.

## 9. Trade-offs

### Advantages

* Giảm zombie work.
* Tail latency predictable hơn.
* Failure propagation có giới hạn.

### Costs / Risks

* Budget quá ngắn tạo false timeout.
* Cần observability để biết layer nào cancel.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout là giới hạn thời gian, cancellation là signal dừng work.

### Middle

Propagate token qua HTTP/DB calls.

### Senior

Thiết kế retry trong remaining budget và đo tail latency.

### Technical Lead / Architect

Phân bổ latency budget theo critical path và SLO toàn hệ thống.

## 11. Key takeaway

* Timeout phải được thiết kế end-to-end.
* Retry tiêu latency budget, không tạo thêm budget.
* Cancellation propagation giảm failure amplification.

# 8. Azure Functions cold start và scaling: tối ưu startup chỉ sau khi hiểu trigger, hosting plan, concurrency và dependency initialization

## 1. What is it?

Cold start là latency khi platform cần tạo/khởi động một Functions instance mới trước khi xử lý workload. Nó gồm runtime startup, app initialization, dependency loading và connection establishment.

## 2. Why does it exist?

Serverless scale-to-zero/elasticity tiết kiệm capacity nhưng instance mới không tồn tại sẵn. Latency startup trở thành một phần request/event processing khi scale-out.

## 3. How does it work?

Trigger tạo demand; platform quyết định scale; instance khởi động; Functions host load app; DI/services initialize; handler bắt đầu nhận work. Hosting plan và trigger type ảnh hưởng mạnh behavior.

## 4. Practical implementation

Giữ startup nhẹ, tránh synchronous network calls trong DI registration:

```csharp
services.AddHttpClient<ICatalogClient, CatalogClient>();
services.AddSingleton(TimeProvider.System);
```

Không tải toàn bộ reference data từ remote API ngay trong constructor singleton nếu chỉ một function path cần nó.

## 5. Real production scenario

HTTP Function ít traffic ban đêm. Request đầu buổi sáng chậm vài giây vì instance mới load assemblies và tạo expensive client/configuration path. Team chuyển initialization sang lazy path và chọn hosting capacity phù hợp latency SLO.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 spike trùng scale-out nhưng steady-state nhanh.

**Evidence** → instance-start telemetry và dependency initialization chiếm phần lớn trace.

**Hypothesis** → cold-start path nặng.

**Diagnosis** → tách host startup, DI initialization, first dependency call.

**Fix** → giảm startup work, reuse clients, cân nhắc plan có warm capacity nếu SLO yêu cầu.

**Verification** → test from zero/scale-out state, không chỉ warm benchmark.

## 7. Common mistakes

* Tối ưu handler code khi bottleneck là startup.
* Tạo `HttpClient` mới mỗi invocation.
* Dùng Functions cho workload cần always-warm ultra-low latency mà không xét plan.
* Không tính downstream concurrency khi scale-out.

## 8. Alternatives

App Service/Container Apps/Worker Service phù hợp workload luôn chạy hoặc cần control khác. Logic Apps phù hợp orchestration low-code. Lựa chọn dựa workload, không dựa nhãn serverless.

## 9. Trade-offs

### Advantages

* Elastic scale và operational convenience.
* Tốt cho event-driven workloads.

### Costs / Risks

* Cold start/tail latency tùy plan.
* Scale-out có thể overload downstream.
* Cost behavior phụ thuộc execution profile.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu instance mới cần startup trước khi xử lý.

### Middle

Giữ initialization nhẹ và reuse clients.

### Senior

Correlate cold start với p99, concurrency và downstream capacity.

### Technical Lead / Architect

Chọn hosting model/plan dựa latency SLO, workload shape, networking, security và cost.

## 11. Key takeaway

* Cold start là system behavior, không chỉ code performance.
* Measure cold và warm paths riêng.
* Elastic scale phải đi cùng downstream capacity planning.

# 9. .NET memory leak investigation với `dotnet-counters` và dump: phân biệt high allocation rate với retained-object growth

## 1. What is it?

Trong managed .NET, “memory leak” thường là objects vẫn còn reachable ngoài ý muốn, nên GC không thể reclaim. Nó khác high allocation rate: nhiều object được tạo nhưng cũng được collect bình thường.

## 2. Why does it exist?

Nếu thấy memory tăng rồi kết luận “GC lỗi” hoặc “thêm RAM”, team dễ sửa sai. Investigation phải phân biệt allocation pressure, LOH behavior, native memory và retained managed graph.

## 3. How does it work?

Reasoning loop:

```text
RSS/heap grows
 -> observe GC counters
 -> compare heap after full collections
 -> capture dump
 -> inspect dominant types/roots
 -> find retention path
 -> fix ownership
 -> measure again
```

GC chỉ collect object unreachable. Static collections, event subscriptions, unbounded caches hoặc long-lived queues có thể giữ references hợp lệ về mặt runtime nhưng sai về application ownership.

## 4. Practical implementation

Quan sát trước:

```bash
dotnet-counters monitor -p <pid> System.Runtime
```

Các signal hữu ích gồm GC heap size, allocation rate, Gen 2 collections, LOH size và working set.

Khi cần dump:

```bash
dotnet-dump collect -p <pid>
dotnet-dump analyze core_*.dmp
```

Trong analyzer, xem heap statistics và roots của dominant type.

## 5. Real production scenario

Notification service tăng memory 100 MB mỗi giờ. Allocation rate không bất thường nhưng Gen 2 heap sau collection vẫn tăng. Dump cho thấy dictionary singleton giữ entries theo tenant mà không eviction.

## 6. Failure scenario & troubleshooting

**Symptom** → pod bị OOMKilled sau nhiều giờ.

**Evidence** → retained Gen 2 heap tăng qua nhiều GC cycles.

**Hypothesis** → long-lived root giữ objects.

**Diagnosis** → compare dumps theo thời gian và inspect GC roots.

**Fix** → bounded cache/eviction hoặc sửa subscription/lifecycle ownership.

**Verification** → soak test; heap phải đạt plateau thay vì tăng tuyến tính.

## 7. Common mistakes

* Chỉ nhìn working set.
* Capture một dump rồi đoán leak.
* Force `GC.Collect()` như production fix.
* Không phân biệt managed/native memory.
* Không chạy soak test sau fix.

## 8. Alternatives

`dotnet-gcdump`, PerfView, Visual Studio profiler và commercial APM/profilers có thể phù hợp tùy môi trường và mức overhead.

## 9. Trade-offs

### Advantages

* Evidence-based root-cause analysis.
* Counters có overhead thấp cho bước triage.

### Costs / Risks

* Dump lớn, nhạy cảm và tốn storage.
* Capture/analyze production dump cần operational discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu GC không collect object còn reachable.

### Middle

Đọc runtime counters và nhận biết heap trend.

### Senior

Phân tích retention roots, allocation vs retention và soak-test verification.

### Technical Lead / Architect

Thiết kế memory budgets, cache ownership, diagnostics policy và safe dump handling.

## 11. Key takeaway

* Memory tăng không tự động đồng nghĩa managed leak.
* Retained heap sau GC và root path là evidence quan trọng.
* Fix ownership, không “fix” bằng `GC.Collect()`.

# 10. Playwright test isolation: deterministic E2E bằng state ownership, test data và network boundaries thay vì tăng retry cho flaky tests

## 1. What is it?

Test isolation nghĩa là mỗi test có preconditions, state và cleanup đủ độc lập để kết quả không phụ thuộc thứ tự chạy hoặc test khác.

Trong E2E, isolation liên quan browser context, authenticated identity, database state, external APIs và asynchronous background work.

## 2. Why does it exist?

Flaky E2E thường không phải vì browser automation “không ổn định”, mà vì test share account/data, dùng sleep cố định hoặc phụ thuộc môi trường biến động.

Retry chỉ che nondeterminism và làm CI chậm hơn.

## 3. How does it work?

Mỗi test nên tạo unique business data hoặc reset state theo boundary rõ ràng. Playwright tạo isolated browser context; application state phía server cũng phải được quản lý.

```text
Test
 -> create unique fixture via API
 -> open isolated browser context
 -> perform user flow
 -> assert observable outcome
 -> cleanup/expire fixture
```

## 4. Practical implementation

```typescript
test('manager approves timesheet', async ({ page, request }) => {
  const id = crypto.randomUUID();

  await request.post('/test-api/timesheets', {
    data: { id, status: 'Submitted' }
  });

  await page.goto(`/timesheets/${id}`);
  await page.getByRole('button', { name: 'Approve' }).click();
  await expect(page.getByText('Approved')).toBeVisible();
});
```

Ưu tiên semantic locators và condition-based waits thay `waitForTimeout(5000)`.

## 5. Real production scenario

CI chạy 20 tests song song cùng account. Một test logout làm test khác mất session; hai test sửa cùng order. Suite pass local nhưng fail ngẫu nhiên CI.

Tách account/data per test worker và browser context loại phần lớn flakiness.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail ngẫu nhiên, rerun lại pass.

**Evidence** → screenshot cho thấy state từ test khác hoặc async job chưa hoàn tất.

**Hypothesis** → shared mutable state/timing assumption.

**Diagnosis** → chạy parallel/repeat, trace Playwright, inspect fixture IDs và server logs.

**Fix** → unique data, explicit readiness conditions, deterministic external stubs khi phù hợp.

**Verification** → repeat test hàng chục lần dưới parallelism giống CI.

## 7. Common mistakes

* Thêm retry trước khi tìm root cause.
* Dùng fixed sleeps.
* Share một user/entity cho cả suite.
* Mock mọi backend khiến E2E không còn bảo vệ integration risk.
* Assert implementation details thay user-visible behavior.

## 8. Alternatives

Integration tests rẻ hơn cho backend contracts. Unit tests tốt cho deterministic domain logic. E2E chỉ nên bảo vệ critical cross-component journeys.

## 9. Trade-offs

### Advantages

* Bảo vệ user journeys thật.
* Bắt integration/configuration/browser regressions.

### Costs / Risks

* Chậm và operationally expensive hơn unit/integration tests.
* Test data/environment ownership phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu flaky test là defect cần điều tra.

### Middle

Dùng isolated context, semantic locators và deterministic waits.

### Senior

Thiết kế fixture/data lifecycle, parallelism và test boundary theo risk.

### Technical Lead / Architect

Xây test strategy: phần nào unit, integration, contract, E2E; giữ E2E nhỏ nhưng có giá trị cao.

## 11. Key takeaway

* Retry không phải cure cho nondeterministic tests.
* Browser isolation chưa đủ nếu server data vẫn shared.
* E2E nên tập trung critical journeys và được thiết kế như production code.
