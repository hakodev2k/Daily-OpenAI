# 1. C# `ValueTask`: giảm allocation trong hot path nhưng dễ bị misuse khi consumer không hiểu single-consumption semantics

## 1. What is it?

`ValueTask<T>` là awaitable type trong .NET cho phép một operation hoàn thành theo hai cách chính:

- trả kết quả trực tiếp mà không cần tạo `Task<T>` mới;
- hoặc wrap một `Task<T>` khi operation thực sự asynchronous.

Mental model:

```text
Task<T>
  -> gần như luôn là một reference object đại diện cho operation

ValueTask<T>
  -> có thể chứa result trực tiếp
  -> hoặc wrap Task<T>
  -> hoặc dùng IValueTaskSource<T>
```

Lý do tồn tại chủ yếu là giảm allocation trong những hot path mà operation **rất thường hoàn thành synchronously**.

## 2. Why does it exist?

Một method async được gọi hàng triệu lần có thể tạo áp lực allocation nếu mỗi lần đều cần `Task<T>` mới dù phần lớn kết quả đã có sẵn trong memory/cache.

Ví dụ một parser, channel reader hoặc socket pipeline có thể thường có dữ liệu sẵn. Nếu 95% call hoàn thành ngay, `ValueTask<T>` cho phép tránh tạo `Task<T>` ở 95% trường hợp đó.

Nhưng abstraction này đổi simplicity lấy performance. Nếu workload không đủ nóng, lợi ích nhỏ hơn complexity.

## 3. How does it work?

Ví dụ:

```csharp
public ValueTask<User?> TryGetAsync(string id)
{
    if (_cache.TryGetValue(id, out var user))
        return ValueTask.FromResult<User?>(user);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id));
}
```

Nếu cache hit, result được chứa trực tiếp. Nếu miss, `ValueTask<T>` wrap `Task<T>` từ database call.

Điểm nguy hiểm: không nên giả định một `ValueTask<T>` có thể await nhiều lần giống `Task<T>`. Khi nó dựa trên `IValueTaskSource<T>`, source có thể được pool và tái sử dụng.

## 4. Practical implementation

Một API nội bộ hợp lý:

```csharp
public sealed class FeatureFlagReader
{
    private readonly ConcurrentDictionary<string, bool> _cache = new();

    public ValueTask<bool> IsEnabledAsync(
        string key,
        CancellationToken cancellationToken)
    {
        if (_cache.TryGetValue(key, out var value))
            return ValueTask.FromResult(value);

        return new ValueTask<bool>(LoadAsync(key, cancellationToken));
    }

    private async Task<bool> LoadAsync(
        string key,
        CancellationToken cancellationToken)
    {
        await Task.Delay(10, cancellationToken);
        return false;
    }
}
```

Consumer nên:

```csharp
var enabled = await reader.IsEnabledAsync("checkout-v2", ct);
```

Không nên lưu `ValueTask` lâu dài hoặc await lặp lại nếu contract không nói rõ.

## 5. Real production scenario

Một high-throughput gateway đọc configuration từ in-memory cache. 99% requests cache hit, nhưng method vẫn được gọi hàng chục nghìn lần mỗi giây.

Nếu mỗi call trả `Task<T>`, allocation nhỏ nhưng tích lũy đủ lớn để tăng GC pressure. `ValueTask<T>` có thể giảm allocation measurable.

Ngược lại, một CRUD API gọi SQL mỗi request không có synchronous fast path gần như sẽ không thu được lợi ích thực tế.

## 6. Failure scenario & troubleshooting

**Symptom:** code dùng `ValueTask` nhưng performance không cải thiện, thậm chí CPU tăng nhẹ.

**Evidence:** profiler cho thấy phần lớn calls vẫn chuyển thành real `Task`; struct copy và branching tăng nhưng allocation gần như không giảm.

**Hypothesis:** workload không có synchronous completion đủ cao.

**Diagnosis:** benchmark bằng BenchmarkDotNet, đo allocation/op và throughput.

**Fix:** quay lại `Task<T>` nếu simplicity tốt hơn; chỉ giữ `ValueTask<T>` ở measured hot path.

**Verification:** so sánh allocation và latency trước/sau dưới representative load.

## 7. Common mistakes

- Đổi mọi `Task<T>` thành `ValueTask<T>` chỉ vì nghe “nhanh hơn”.
- Await một `ValueTask` nhiều lần.
- Gọi `.AsTask()` mọi nơi, làm mất phần lớn lợi ích.
- Public API dùng `ValueTask` dù consumer ecosystem không cần complexity đó.
- Tối ưu allocation trước khi đo bottleneck.

## 8. Alternatives

- **`Task<T>`:** default tốt nhất cho đa số async APIs.
- **Synchronous method:** nếu operation thực sự luôn synchronous.
- **Caching:** đôi khi giảm I/O quan trọng hơn nhiều so với tối ưu task allocation.

## 9. Trade-offs

### Advantages

- Giảm allocation khi synchronous completion rất phổ biến.
- Hữu ích trong runtime/library/high-throughput code.

### Costs / Risks

- Semantics phức tạp hơn `Task`.
- Dễ misuse trong public API.
- Lợi ích nhỏ nếu operation thường asynchronous.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task<T>` là default; `ValueTask<T>` không phải “Task nhanh hơn”.

### Middle

Biết khi nào có synchronous fast path và dùng `ValueTask` đúng contract.

### Senior

Đo allocation/throughput trước khi áp dụng và hiểu `IValueTaskSource<T>` lifecycle.

### Technical Lead / Architect

Đặt performance policy: chỉ đưa complexity này vào nơi profile chứng minh có giá trị, tránh lan ra toàn API surface.

## 11. Key takeaway

- `ValueTask` là optimization tool, không phải default async primitive.
- Nó đáng dùng khi synchronous completion phổ biến và allocation thực sự là bottleneck.
- Simplicity của `Task` thường đáng giá hơn nếu chưa có evidence.

# 2. ASP.NET Core DI scopes trong `BackgroundService`: vì sao singleton worker không được giữ scoped dependency qua nhiều vòng xử lý

## 1. What is it?

`BackgroundService` được đăng ký như hosted service và về bản chất thường sống suốt lifetime của application. Trong khi đó, dependency như `DbContext` thường có **scoped lifetime**.

Mental model:

```text
Host lifetime
+-------------------------------------------+
| BackgroundService (singleton-ish lifetime)|
+-------------------------------------------+

Request / Unit of Work scopes
[ scope 1 ][ scope 2 ][ scope 3 ] ...
```

Một long-lived worker không nên capture `DbContext` hoặc scoped service rồi reuse mãi.

## 2. Why does it exist?

Scoped lifetime giúp nhóm dependencies theo một unit-of-work. Với HTTP request, ASP.NET Core tự tạo scope. Nhưng `BackgroundService` không có request scope tự động cho từng vòng xử lý.

Nếu inject trực tiếp một scoped dependency vào long-lived service, lifetime boundaries bị phá:

- stale state;
- Change Tracker phình;
- concurrency bug;
- disposed object;
- connection/transaction ownership mơ hồ.

## 3. How does it work?

Worker nên inject `IServiceScopeFactory` rồi tạo scope cho mỗi logical unit-of-work:

```text
BackgroundService
   |
   +--> CreateScope()
           |
           +--> DbContext
           +--> Repository/Application Service
           +--> Dispose scope
```

Mỗi scope giữ dependency graph riêng và được dispose sau batch/message.

## 4. Practical implementation

```csharp
public sealed class OrderWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public OrderWorker(IServiceScopeFactory scopeFactory)
        => _scopeFactory = scopeFactory;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = _scopeFactory.CreateAsyncScope();

            var processor = scope.ServiceProvider
                .GetRequiredService<OrderBatchProcessor>();

            await processor.ProcessNextBatchAsync(stoppingToken);
        }
    }
}
```

`OrderBatchProcessor` có thể inject `DbContext` scoped bình thường.

## 5. Real production scenario

Worker đọc Azure Service Bus và update SQL qua EF Core. Version lỗi giữ một `DbContext` suốt nhiều giờ.

Sau vài nghìn messages:

- tracker chứa rất nhiều entities;
- stale entity state tồn tại lâu;
- cùng context có thể bị dùng concurrent nếu handler parallel;
- memory tăng dần.

Tạo scope per message hoặc per bounded batch làm ownership rõ ràng.

## 6. Failure scenario & troubleshooting

**Symptom:** worker chạy tốt lúc startup nhưng sau vài giờ memory tăng và xuất hiện lỗi kiểu “A second operation was started on this context...”.

**Evidence:** cùng `DbContext` instance xuất hiện trong nhiều handler; tracker size tăng.

**Hypothesis:** scoped dependency bị giữ bởi long-lived hosted service.

**Diagnosis:** kiểm tra DI registrations và object lifetime; log context instance id nếu cần.

**Fix:** tạo scope theo unit-of-work; không cache scoped service trong field.

**Verification:** memory bounded, không còn concurrent-use exception.

## 7. Common mistakes

- Inject `DbContext` trực tiếp vào `BackgroundService` rồi giữ làm field.
- Tạo một scope duy nhất ngoài loop.
- Dùng service locator ở mọi nơi thay vì chỉ ở composition boundary của worker.
- Một scope bao hàng chục nghìn messages không có lý do.
- Tạo scope per tiny operation làm overhead/transaction fragmentation không cần thiết.

## 8. Alternatives

- **`IDbContextFactory<TContext>`:** tốt cho explicit context creation, đặc biệt khi concurrency hoặc unit-of-work không map tự nhiên vào DI scope.
- **Scope per batch:** giảm creation overhead nếu batch là transaction/business boundary hợp lý.
- **Azure Functions:** platform quản lý invocation scope khác, nhưng lifetime reasoning vẫn cần rõ.

## 9. Trade-offs

### Advantages

- Resource lifetime rõ ràng.
- `DbContext` và scoped dependencies được dispose đúng lúc.
- Giảm stale state và cross-message coupling.

### Costs / Risks

- Scope creation thêm chút overhead.
- Scope boundary sai có thể làm transaction quá nhỏ hoặc quá lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Singleton, Scoped, Transient và vì sao lifetime mismatch nguy hiểm.

### Middle

Biết tạo scope đúng trong worker và propagate cancellation.

### Senior

Thiết kế scope theo transaction/unit-of-work, không theo “mỗi method”.

### Technical Lead / Architect

Định nghĩa background processing boundary, concurrency model và ownership của database/message transaction rõ ràng.

## 11. Key takeaway

- Hosted service sống lâu; scoped dependency thì không.
- Tạo scope theo logical unit-of-work.
- Lifetime là correctness concern, không chỉ DI configuration detail.

# 3. EF Core compiled queries: khi query compilation thực sự đáng tối ưu và khi bottleneck nằm ở database chứ không phải LINQ

## 1. What is it?

EF Core phải xử lý LINQ expression tree để tạo query plan phía EF và SQL command tương ứng. EF có internal query caching, nhưng **compiled queries** cho phép precompile query delegate rõ ràng để giảm overhead lặp lại ở hot path.

Mental model:

```text
LINQ expression
 -> EF translation/normalization
 -> cached query pipeline
 -> SQL
 -> database execution
```

Compiled query tối ưu phần trước database execution, không làm SQL query tự nhiên nhanh hơn.

## 2. Why does it exist?

Ở workload cực nóng, cùng một query shape được gọi hàng trăm nghìn lần, overhead EF-side có thể trở nên measurable.

Nhưng với query SQL tốn 80 ms, tiết kiệm vài microseconds compilation overhead gần như vô nghĩa.

## 3. How does it work?

Ví dụ:

```csharp
private static readonly Func<AppDbContext, Guid, User?> GetUserById =
    EF.CompileQuery((AppDbContext db, Guid id) =>
        db.Users
          .AsNoTracking()
          .SingleOrDefault(x => x.Id == id));
```

Async variant:

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<User>> GetUsersByTenant =
    EF.CompileAsyncQuery((AppDbContext db, Guid tenantId) =>
        db.Users
          .AsNoTracking()
          .Where(x => x.TenantId == tenantId));
```

Delegate này reusable giữa context instances cùng model.

## 4. Practical implementation

Đo trước:

```csharp
var sw = Stopwatch.StartNew();
var user = await db.Users
    .AsNoTracking()
    .SingleOrDefaultAsync(x => x.Id == id, ct);
metrics.RecordQueryLatency(sw.Elapsed);
```

Sau đó benchmark representative hot query cả compiled và normal query. Đồng thời đo database execution time riêng qua telemetry/profiler.

Nếu SQL chiếm 99% latency, compiled query không phải nơi nên đầu tư.

## 5. Real production scenario

Authorization service kiểm tra tenant membership hàng chục nghìn lần/s. Query rất đơn giản, index tốt, SQL trả về trong sub-millisecond trên warm cache. Lúc đó EF pipeline overhead có thể chiếm tỷ lệ đáng kể.

Ngược lại, reporting endpoint join 8 tables và scan nhiều pages: compiled query gần như không giải quyết bottleneck.

## 6. Failure scenario & troubleshooting

**Symptom:** team thêm compiled query nhưng p95 API không đổi.

**Evidence:** tracing cho thấy database call vẫn chiếm 45 ms trong tổng 48 ms.

**Hypothesis:** tối ưu sai layer.

**Diagnosis:** tách application CPU time, EF translation/materialization time và DB execution.

**Fix:** xem execution plan, index, projection, round trips hoặc access pattern trước.

**Verification:** đo lại end-to-end latency, không chỉ microbenchmark helper method.

## 7. Common mistakes

- Compile mọi query để “tăng performance”.
- Bỏ qua projection và lấy cả entity graph.
- Dùng compiled query với dynamic shape phức tạp rồi tạo nhiều delegates.
- Benchmark local in-memory condition không giống production database.
- Không đo end-to-end impact.

## 8. Alternatives

- **Normal EF query:** default tốt nhất; EF đã có caching nội bộ.
- **Projection:** thường tạo lợi ích lớn hơn bằng giảm data transfer/materialization.
- **Raw SQL/Dapper:** phù hợp query đặc biệt khi cần control sâu hơn.
- **Database tuning:** thường quan trọng nhất nếu SQL execution là bottleneck.

## 9. Trade-offs

### Advantages

- Giảm EF query pipeline overhead trên hot query shape ổn định.
- Predictable delegate reuse.

### Costs / Risks

- Thêm static query definitions và complexity.
- Lợi ích rất nhỏ trong nhiều CRUD workloads.
- Dễ khiến team bỏ qua bottleneck thật ở DB.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu query chậm không đồng nghĩa EF “compile LINQ chậm”.

### Middle

Biết dùng projection, `AsNoTracking`, index và đo query latency.

### Senior

Tách client-side query pipeline cost khỏi database execution cost.

### Technical Lead / Architect

Đặt rule performance: compiled query chỉ được dùng khi benchmark/profiling chứng minh có ý nghĩa trên critical path.

## 11. Key takeaway

- Compiled query tối ưu EF-side overhead, không tối ưu SQL execution plan.
- Chỉ đáng dùng ở stable, high-frequency hot paths.
- Đo đúng layer trước khi tối ưu.

# 4. SQL Server connection pooling: connection leak, pool exhaustion và vì sao `OpenAsync` nhanh không có nghĩa là không có giới hạn

## 1. What is it?

ADO.NET connection pooling tái sử dụng physical database connections thay vì tạo TCP/login session mới cho mỗi request.

Mental model:

```text
Application
   -> SqlConnection.Open()
   -> connection pool
      -> reuse physical connection
      -> hoặc tạo mới nếu còn capacity
```

`SqlConnection.Dispose()` thường **trả connection về pool**, không nhất thiết đóng physical connection ngay.

## 2. Why does it exist?

Mở database connection mới tương đối đắt: network handshake, TLS, authentication, session setup. Pooling giảm latency và CPU bằng reuse.

Nhưng pool hữu hạn. Nếu code giữ connection quá lâu hoặc quên dispose, requests mới phải chờ connection trả về.

## 3. How does it work?

Pool thường phân chia theo connection string/identity. Khi gọi `OpenAsync`:

1. tìm idle connection trong pool;
2. nếu có, checkout;
3. nếu chưa đạt max pool size, tạo mới;
4. nếu pool đầy và tất cả đang bận, chờ đến timeout.

Một API có 500 concurrent requests nhưng pool 100 connections không nhất thiết lỗi — nếu mỗi query nhanh, connection quay vòng tốt. Vấn đề là **hold time**.

## 4. Practical implementation

Luôn giới hạn ownership:

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(ct);

await using var command = connection.CreateCommand();
command.CommandText = "SELECT Id, Name FROM Customers WHERE Id = @id";
command.Parameters.AddWithValue("@id", id);

await using var reader = await command.ExecuteReaderAsync(ct);
```

Với EF Core, `DbContext` thường tự mở/đóng connection quanh operation, trừ khi bạn explicitly quản connection/transaction.

Không giữ connection mở qua remote HTTP call.

## 5. Real production scenario

Endpoint bắt đầu transaction SQL, query order, gọi shipping API mất 3 giây, rồi update order và commit.

Trong 3 giây đó, database connection và locks vẫn bị giữ. Chỉ cần 100 concurrent requests là pool có thể cạn.

Thiết kế tốt hơn có thể tách remote call ra ngoài DB transaction hoặc thay đổi workflow để tránh giữ connection trong network wait.

## 6. Failure scenario & troubleshooting

**Symptom:** API đột nhiên timeout với message liên quan obtaining a connection from the pool; DB CPU chỉ 30%.

**Evidence:** active connections gần max pool size, query duration không quá cao nhưng connection hold duration dài.

**Hypothesis:** pool exhaustion do connection leak hoặc transaction scope quá rộng.

**Diagnosis:** xem dependency traces, `SqlClient` counters, stack traces, transaction duration.

**Fix:** dispose đúng, rút transaction boundary, tránh giữ connection qua external I/O.

**Verification:** pool wait time giảm, active connection ổn định dưới load.

## 7. Common mistakes

- Tăng `Max Pool Size` ngay mà không tìm lý do connections bị giữ lâu.
- Quên dispose reader/connection.
- Mở transaction trước khi gọi API bên ngoài.
- Tạo hàng loạt connection strings khác nhau vô tình chia thành nhiều pools.
- Nhầm connection pooling với DB server max connections.

## 8. Alternatives

- **Pool mặc định:** thường đủ cho đa số apps.
- **Connection multiplexing/proxy:** tùy database/platform, nhưng không thay thế việc quản hold time.
- **Queue/background processing:** giúp bound concurrency với DB cho workload bursty.

## 9. Trade-offs

### Advantages

- Giảm cost mở connection.
- Tăng throughput và ổn định latency.

### Costs / Risks

- Pool là shared finite resource.
- Leak/long hold có thể gây cascading timeout.
- Tăng pool size có thể chuyển bottleneck sang DB server.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Dispose` connection là trả về pool.

### Middle

Biết giữ connection scope ngắn và dùng async APIs.

### Senior

Chẩn đoán pool exhaustion bằng hold time, concurrency và transaction boundaries.

### Technical Lead / Architect

Capacity-plan connection budget theo số instances, pool size và database limit; tránh để mỗi service tự mở pool vô hạn.

## 11. Key takeaway

- Pooling giúp connection rẻ hơn nhưng không làm resource vô hạn.
- Hold time quan trọng ngang query time.
- Tăng pool size chỉ nên sau khi hiểu bottleneck thật.

# 5. Cosmos DB consistency levels: Strong, Session và Eventual dưới góc nhìn correctness, latency và multi-region cost

## 1. What is it?

Cosmos DB cung cấp nhiều consistency levels để kiểm soát mức độ “mới” và thứ tự của dữ liệu mà read có thể quan sát.

Ba mental models chính:

```text
Strong   -> read phải thấy state mới nhất theo guarantee mạnh
Session  -> cùng logical session thấy read-your-writes
Eventual -> read có thể thấy dữ liệu cũ tạm thời
```

Consistency không phải chỉ là “faster/slower”; nó ảnh hưởng trực tiếp business semantics.

## 2. Why does it exist?

Trong distributed database nhiều replicas/regions, không thể đồng thời tối đa hóa latency thấp, availability cao và consistency mạnh trong mọi failure condition.

Different workloads cần khác nhau:

- account balance cần guarantee mạnh hơn;
- product catalog có thể chấp nhận vài giây stale;
- user vừa update profile thường kỳ vọng chính họ thấy update ngay.

## 3. How does it work?

Với Session consistency, client/session token giúp đảm bảo một logical session có monotonic reads/read-your-writes trong phạm vi guarantee.

Eventual consistency cho phép replicas converge sau; read có thể tạm thời thấy version cũ.

Strong consistency yêu cầu coordination nhiều hơn và có constraints/costs cao hơn trong multi-region topology.

## 4. Practical implementation

Cấu hình client cần bám architecture decision; không đổi consistency tùy tiện ở từng call nếu team không hiểu semantics.

Ví dụ read theo session token thường được SDK hỗ trợ tự động khi dùng cùng client/session flow.

Application vẫn cần model business invariant riêng. Nếu “reserve inventory” cần atomic correctness, chỉ chọn consistency level không đủ nếu workflow spans multiple logical partitions/services.

## 5. Real production scenario

User update display name rồi redirect về profile page. Với Eventual consistency, user có thể thấy tên cũ trong một khoảng ngắn và nghĩ update thất bại.

Session consistency thường phù hợp hơn cho UX này vì same session có read-your-writes, trong khi các user khác có thể chưa thấy ngay.

## 6. Failure scenario & troubleshooting

**Symptom:** QA báo “save thành công nhưng refresh ngay vẫn thấy dữ liệu cũ”.

**Evidence:** write success, read đi tới replica khác, account dùng weaker consistency.

**Hypothesis:** behavior phù hợp consistency model nhưng không phù hợp UX requirement.

**Diagnosis:** kiểm tra configured consistency, region routing, session token handling.

**Fix:** dùng Session/stronger semantics cho flow cần read-your-writes hoặc thiết kế UI acknowledgement phù hợp.

**Verification:** test immediate read sau write qua topology production-like.

## 7. Common mistakes

- Chọn Strong “cho an toàn” mà không hiểu latency/availability/cost impact.
- Chọn Eventual chỉ để “nhanh” rồi phá business expectation.
- Cho rằng consistency level giải quyết distributed transaction giữa nhiều services.
- Tạo Cosmos client mới per request, làm mất connection/session efficiency.
- Không phân biệt partition-local atomicity với cross-partition workflow.

## 8. Alternatives

- **SQL database:** phù hợp nếu relational transaction/invariants là trọng tâm.
- **MongoDB:** document model tương tự ở một số use cases nhưng semantics/operations khác.
- **Application-level versioning:** có thể bổ sung conflict handling nhưng không thay datastore guarantees.

## 9. Trade-offs

### Advantages

- Cho phép chọn consistency phù hợp workload.
- Session thường là balance tốt cho user-centric applications.

### Costs / Risks

- Strong consistency tăng coordination cost.
- Eventual consistency đẩy complexity lên application/UX.
- Multi-region design làm trade-off rõ hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu distributed read có thể không thấy write mới ngay.

### Middle

Biết chọn consistency theo flow và kiểm tra session behavior.

### Senior

Phân tích correctness dưới region failure, replica lag và partition boundaries.

### Technical Lead / Architect

Định nghĩa consistency requirement theo business capability thay vì toàn database theo cảm tính.

## 11. Key takeaway

- Consistency là business correctness decision.
- Session thường phù hợp nhiều interactive apps vì read-your-writes.
- Stronger guarantee luôn có operational/cost trade-off.

# 6. Modular Monolith: giữ deployment đơn giản nhưng dùng module boundary để tránh biến monolith thành big ball of mud

## 1. What is it?

Modular Monolith là application deploy như một unit nhưng code/data ownership được chia thành các business modules có boundary rõ.

```text
Single deployable
+----------------------------------+
| Orders | Billing | Catalog       |
|-------- module boundaries -------|
| shared runtime / infrastructure  |
+----------------------------------+
```

Nó không phải “monolith có nhiều folders”. Boundary phải thể hiện ở dependency, contract và ownership.

## 2. Why does it exist?

Microservices giải quyết independent deployment/scaling/team ownership nhưng thêm distributed-system cost: network failure, observability, deployment orchestration, consistency, messaging.

Nhiều hệ thống chưa cần chi phí đó nhưng vẫn cần tránh mọi module query/update database của nhau tùy ý.

Modular Monolith cung cấp intermediate architecture: internal boundaries mạnh, operational model đơn giản.

## 3. How does it work?

Ví dụ module `Orders` không gọi thẳng repository nội bộ của `Billing`. Nó dùng explicit application contract hoặc internal event.

```text
Orders -> Billing public contract
Orders -X-> BillingDbContext/internal tables
```

Data có thể cùng physical database nhưng ownership vẫn logical. Một module không nên join tables module khác tùy tiện nếu muốn boundary giữ được giá trị.

## 4. Practical implementation

Cấu trúc chỉ là phần bề mặt:

```text
Modules/
  Orders/
    Application/
    Domain/
    Infrastructure/
  Billing/
    Application/
    Domain/
    Infrastructure/
```

Quan trọng hơn là enforce reference rules, ví dụ architecture tests:

```csharp
[Fact]
public void Orders_Domain_Must_Not_Depend_On_Billing_Infrastructure()
{
    // dùng NetArchTest/ArchUnitNET hoặc custom dependency test
}
```

Public contracts nên nhỏ và business-oriented.

## 5. Real production scenario

SaaS ban đầu có 10 developers. Nếu tách 12 microservices ngay, team phải vận hành 12 pipelines, distributed tracing, message contracts và failure modes.

Modular Monolith cho phép một deployable nhưng vẫn tách `Identity`, `Billing`, `Projects`, `Notifications`. Sau này module có scaling/ownership pressure thật mới cân nhắc extraction.

## 6. Failure scenario & troubleshooting

**Symptom:** code gọi trực tiếp tables/services nội bộ chéo modules; mỗi feature change chạm 5 modules.

**Evidence:** circular project references, shared “Common” project chứa business logic, cross-module joins khắp nơi.

**Hypothesis:** module boundary chỉ tồn tại trên folder structure.

**Diagnosis:** dependency graph và change-coupling analysis.

**Fix:** định nghĩa public contracts, ownership, remove circular dependencies, dùng events khi coupling phù hợp.

**Verification:** architecture tests và change review cho thấy module có thể thay đổi tương đối độc lập.

## 7. Common mistakes

- Tạo một `Shared` project khổng lồ.
- Module nào cũng dùng cùng entities/repositories.
- Áp CQRS/MediatR cho mọi operation dù không cần.
- Tuyên bố “modular” nhưng database ownership không có quy tắc.
- Tách microservices chỉ vì codebase lớn.

## 8. Alternatives

- **Layered Monolith:** đơn giản hơn, tốt khi domain nhỏ.
- **Microservices:** phù hợp khi independent deploy/scale/team ownership thực sự cần.
- **SOA:** có thể phù hợp enterprise integration lớn nhưng operational model khác.

## 9. Trade-offs

### Advantages

- Deployment/operations đơn giản hơn microservices.
- Boundary tốt giúp change isolation.
- Dễ transaction nội bộ hơn vì cùng process/database.

### Costs / Risks

- Module có thể lén coupling nếu enforcement yếu.
- Không scale/deploy độc lập từng module.
- Extraction sau này vẫn cần effort nếu data ownership mơ hồ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business boundary, không chỉ namespace.

### Middle

Giữ dependency direction và contract rõ khi implement feature.

### Senior

Nhận diện coupling, transaction boundary và data ownership.

### Technical Lead / Architect

Quyết định khi modular monolith đủ tốt và khi operational/business pressure thực sự justify service extraction.

## 11. Key takeaway

- Modular Monolith tối ưu cho simplicity + boundaries.
- Boundary phải được enforce bằng dependency/data ownership rules.
- Microservices không phải bước trưởng thành bắt buộc.

# 7. Azure App Service Health Check: phân biệt process sống, dependency khỏe và instance có nên nhận traffic hay không

## 1. What is it?

Health Check cho phép platform probe một endpoint để quyết định instance có đủ khỏe để nhận traffic hay không.

Mental model:

```text
Platform -> /health
            |
            +--> healthy   -> giữ trong rotation
            +--> unhealthy -> loại khỏi rotation/recycle theo policy
```

Health không đồng nghĩa “mọi dependency phải 100% available”. Probe cần phản ánh **khả năng phục vụ request hợp lệ**.

## 2. Why does it exist?

Process có thể vẫn chạy nhưng app unusable:

- startup config lỗi một phần;
- connection pool hỏng;
- deadlock nội bộ;
- dependency critical unavailable;
- deployment mới warm-up chưa xong.

Nếu load balancer chỉ kiểm tra TCP/process, traffic vẫn bị gửi vào broken instance.

## 3. How does it work?

ASP.NET Core health checks:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, name: "sql", tags: new[] { "ready" });

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

Nên phân biệt:

- **Liveness:** process có cần restart không?
- **Readiness:** instance có nên nhận traffic không?

App Service semantics không map 1:1 Kubernetes probes nhưng mental model này vẫn hữu ích.

## 4. Practical implementation

Không nên probe tất cả external services ở mọi request health check nếu điều đó khiến health endpoint chậm và tạo load mới.

Ví dụ critical DB có thể readiness-check; optional recommendation API có thể không làm instance unhealthy nếu app vẫn degrade gracefully.

Health endpoint cần nhanh, deterministic và không mutate data.

## 5. Real production scenario

Deployment mới thiếu Key Vault permission. Process khởi động nhưng endpoint business nào cần secret đều trả 500.

Nếu readiness health check validate critical configuration/dependency, instance có thể bị giữ ngoài rotation thay vì nhận user traffic.

## 6. Failure scenario & troubleshooting

**Symptom:** toàn bộ instances đồng loạt bị đánh unhealthy khi shared dependency chập chờn.

**Evidence:** health endpoint gọi external API non-critical và trả 503; App Service loại nhiều instances cùng lúc.

**Hypothesis:** health check quá nhạy và biến dependency outage thành capacity outage.

**Diagnosis:** xem health endpoint dependency graph và timestamps.

**Fix:** chỉ include dependencies thực sự quyết định khả năng serve; degrade optional feature thay vì fail readiness.

**Verification:** chaos test dependency outage và xác nhận traffic behavior đúng mong muốn.

## 7. Common mistakes

- `/health` luôn trả 200 hard-coded.
- Probe mọi dependency, kể cả optional.
- Health check chạy expensive query.
- Health endpoint cần authentication phức tạp khiến platform không probe được.
- Dùng health check thay observability/alerting.

## 8. Alternatives

- **Application Insights availability tests:** kiểm tra từ ngoài hệ thống, phù hợp end-to-end availability.
- **Synthetic monitoring:** mô phỏng user journey.
- **Kubernetes readiness/liveness probes:** tương tự concept nhưng control chi tiết hơn.

## 9. Trade-offs

### Advantages

- Loại broken instance khỏi traffic tự động.
- Hỗ trợ safer deployment và recovery.

### Costs / Risks

- Probe thiết kế sai có thể tạo false positive/negative.
- Shared dependency outage có thể làm toàn fleet bị unhealthy.
- Health check không thay root-cause telemetry.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu health check là machine-readable operational signal.

### Middle

Implement fast readiness checks cho critical dependencies.

### Senior

Thiết kế degraded mode và tránh cascading health failure.

### Technical Lead / Architect

Định nghĩa dependency nào critical, policy fail-open/fail-closed và health semantics nhất quán giữa environments.

## 11. Key takeaway

- “Process alive” khác “instance ready”.
- Health endpoint phải phản ánh serviceability, không phải dependency perfection.
- Probe sai có thể làm outage tệ hơn.

# 8. OpenTelemetry trace context propagation: nối một request xuyên API, queue và worker mà không biến correlation thành logging thủ công

## 1. What is it?

Distributed tracing gán một trace cho end-to-end operation và spans cho từng bước.

```text
Trace
  span: API request
    span: SQL
    span: HTTP dependency
    span: publish message
      span: worker consume
```

Trace context thường dùng W3C Trace Context (`traceparent`, `tracestate`) để propagation qua HTTP và messaging.

## 2. Why does it exist?

Trong distributed system, cùng một user action có thể đi qua 8 services. Log timestamp riêng lẻ rất khó ghép.

Trace context tạo causal relationship: span B là child của span A, giúp thấy critical path và failure propagation.

## 3. How does it work?

Qua HTTP, instrumentation tự inject/extract headers.

Qua queue, producer cần inject context vào message properties; consumer extract rồi tạo activity/span mới.

Không phải mọi message nên giữ một trace vô hạn. Long-lived workflow đôi khi hợp lý hơn dùng **span links** thay parent-child trực tiếp.

## 4. Practical implementation

ASP.NET Core + OpenTelemetry:

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddSqlClientInstrumentation()
        .AddSource("MyCompany.Orders"));
```

Custom activity:

```csharp
private static readonly ActivitySource Source = new("MyCompany.Orders");

using var activity = Source.StartActivity("orders.publish");
activity?.SetTag("messaging.system", "azure_service_bus");
```

Không add user email/order payload full vào tags nếu high-cardinality/sensitive.

## 5. Real production scenario

Checkout API nhanh 200 ms nhưng notification tới user chậm 20 giây. HTTP logs nhìn bình thường.

Trace qua publish → queue wait → consumer → email provider cho thấy 18 giây nằm ở queue backlog, không phải API.

## 6. Failure scenario & troubleshooting

**Symptom:** trace dừng ở producer; worker logs không cùng trace id.

**Evidence:** message properties thiếu trace context hoặc custom serializer drop headers.

**Hypothesis:** context propagation bị mất qua messaging boundary.

**Diagnosis:** inspect message metadata và instrumentation config.

**Fix:** inject/extract context đúng chuẩn; dùng links nếu workflow asynchronous dài.

**Verification:** trace topology thể hiện producer và consumer relationship nhất quán.

## 7. Common mistakes

- Tự tạo `CorrelationId` mới ở mỗi service.
- Log trace id nhưng không propagate.
- Đưa high-cardinality business IDs vào metrics labels thay vì trace/log attributes.
- Sample mất toàn bộ error traces do policy kém.
- Gửi PII vào telemetry backend.

## 8. Alternatives

- **Manual correlation ID:** đơn giản nhưng ít semantic hơn tracing chuẩn.
- **Structured logs:** vẫn cần, đặc biệt cho discrete events.
- **Metrics:** tốt cho aggregate signal nhưng không cho causal path từng request.

## 9. Trade-offs

### Advantages

- Thấy end-to-end latency và dependency chain.
- Giảm thời gian incident diagnosis.

### Costs / Risks

- Telemetry volume/cost.
- Sampling có thể bỏ miss trace cần thiết.
- Context propagation sai làm data misleading.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace/span và correlation.

### Middle

Instrument HTTP/SQL/custom operations và propagate context.

### Senior

Thiết kế sampling, baggage/tags và asynchronous trace semantics.

### Technical Lead / Architect

Chuẩn hóa observability contract toàn platform, data retention và privacy policy.

## 11. Key takeaway

- Distributed tracing cần propagation, không chỉ logging trace id.
- HTTP và messaging boundaries phải giữ causal context.
- Traces, logs và metrics bổ sung nhau chứ không thay thế nhau.

# 9. Vue.js reactivity và computed state: tránh duplicate derived state và bug do mutation không đúng ownership

## 1. What is it?

Vue reactivity theo dõi reactive dependencies để cập nhật UI khi source state thay đổi.

`computed` phù hợp cho state **được suy ra** từ state khác.

```text
source state: cartItems
      |
      v
computed: totalPrice
```

Nếu lưu cả `cartItems` và `totalPrice` như hai mutable states độc lập, chúng có thể lệch nhau.

## 2. Why does it exist?

UI thường có nhiều derived values: filtered list, total, validation summary, display name.

Nếu developer tự đồng bộ các state này bằng watchers/manual mutation, complexity tăng và dễ stale state.

## 3. How does it work?

Vue track dependencies mà computed getter đọc. Khi dependency đổi, computed được invalidated và evaluate lại khi cần.

```ts
const cartItems = ref<CartItem[]>([])

const totalPrice = computed(() =>
  cartItems.value.reduce((sum, item) => sum + item.price * item.quantity, 0)
)
```

Không cần `watch(cartItems, ...)` chỉ để cập nhật total.

## 4. Practical implementation

Component nên giữ clear ownership:

```ts
const props = defineProps<{ order: Order }>()
const emit = defineEmits<{ save: [OrderUpdate] }>()

const displayTotal = computed(() =>
  props.order.lines.reduce((sum, x) => sum + x.quantity * x.unitPrice, 0)
)
```

Không mutate prop trực tiếp. Nếu form cần editable local state, copy có chủ đích và define sync/save semantics.

## 5. Real production scenario

Checkout page giữ `items`, `subtotal`, `tax`, `grandTotal` như 4 mutable refs. Một code path update quantity nhưng quên recalc tax. UI hiển thị số không nhất quán.

Derived state bằng computed giảm số nguồn sự thật.

## 6. Failure scenario & troubleshooting

**Symptom:** UI chỉ sai sau một số sequence thao tác.

**Evidence:** Vue DevTools cho thấy source items đúng nhưng cached/manual total cũ.

**Hypothesis:** duplicated state và mutation order.

**Diagnosis:** map state ownership và dependencies.

**Fix:** giữ minimal source state, derive còn lại bằng computed hoặc server response rõ ràng.

**Verification:** sequence tests không còn divergence.

## 7. Common mistakes

- Dùng `watch` cho logic đáng lẽ là computed.
- Mutate props trực tiếp.
- Copy prop vào local state rồi nghĩ nó tự sync.
- Store mọi derived UI value vào Pinia/global store.
- Dùng deep watcher rộng làm performance khó đoán.

## 8. Alternatives

- **Computed:** derived synchronous state.
- **Watch:** side effects hoặc async reaction có chủ đích.
- **Server-calculated value:** đúng khi business rule authoritative ở backend.
- **Pinia:** shared application state khi ownership thực sự cross-component.

## 9. Trade-offs

### Advantages

- Ít duplicated state.
- Dependency graph rõ hơn.
- UI consistency tốt hơn.

### Costs / Risks

- Computed phức tạp/expensive vẫn có cost.
- Over-centralizing mọi state vào store có thể tăng coupling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt source state và derived state.

### Middle

Dùng computed/watch đúng mục đích và giữ prop ownership rõ.

### Senior

Thiết kế frontend state boundaries gắn với API/domain ownership.

### Technical Lead / Architect

Đảm bảo business-critical calculation vẫn authoritative ở backend khi cần, không để UI computed trở thành source of truth tài chính.

## 11. Key takeaway

- Derived state nên được derive, không duplicate nếu không cần.
- `computed` cho calculation; `watch` cho side effect.
- Frontend state ownership cần nhất quán với backend contract.

# 10. Git `bisect`: tìm commit gây regression bằng binary search thay vì đọc lịch sử bằng mắt

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên gây lỗi.

Mental model:

```text
Good ------------------------------ Bad
                  ^ test midpoint
```

Mỗi lần đánh dấu commit `good` hoặc `bad`, Git loại bỏ khoảng một nửa search space.

## 2. Why does it exist?

Nếu regression xuất hiện trong 500 commits gần đây, đọc diff tuần tự rất tốn thời gian. Binary search cần khoảng `log2(500)` ≈ 9 vòng nếu lịch sử phù hợp.

Đây là debugging tool dựa trên evidence, không phụ thuộc đoán developer nào “có vẻ gây lỗi”.

## 3. How does it work?

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
```

Git checkout midpoint. Bạn chạy test:

```bash
dotnet test tests/Regression.Tests
```

Nếu lỗi:

```bash
git bisect bad
```

Nếu pass:

```bash
git bisect good
```

Lặp lại tới khi Git xác định first bad commit.

Cuối cùng:

```bash
git bisect reset
```

## 4. Practical implementation

Có thể tự động:

```bash
git bisect start HEAD v2.4.0
git bisect run dotnet test tests/Regression.Tests/Regression.Tests.csproj --no-restore
```

Exit code `0` được coi good, non-zero bad; một số exit codes có semantics đặc biệt cho skip.

Automation hiệu quả khi có deterministic regression test.

## 5. Real production scenario

Sau release, API serialization đổi format ở một edge case. Team biết release tuần trước còn đúng nhưng có 180 commits từ đó tới nay.

Viết một regression test reproduce output sai rồi `git bisect run`. Trong vài vòng, commit đổi serializer options được xác định chính xác.

## 6. Failure scenario & troubleshooting

**Symptom:** bisect cho kết quả khác nhau mỗi lần.

**Evidence:** regression test flaky hoặc test phụ thuộc external environment.

**Hypothesis:** oracle good/bad không deterministic.

**Diagnosis:** chạy test lặp lại trên cùng commit.

**Fix:** isolate test data/dependencies hoặc dùng stable reproduction command.

**Verification:** same commit luôn cho cùng classification.

## 7. Common mistakes

- Chọn “good” commit thực ra đã có bug.
- Dùng flaky test.
- Quên build/migration compatibility khi checkout commit cũ.
- Bisect trên history có merge/large refactor mà không hiểu testability.
- Tìm được commit rồi blame cá nhân thay vì phân tích missing test/process gap.

## 8. Alternatives

- **`git log` / diff review:** tốt khi suspect range rất nhỏ.
- **`git blame`:** tìm nguồn dòng code, không phải first regression commit.
- **Feature flags/telemetry:** giúp khoanh deploy/config regression production.
- **Revert candidates:** đôi khi nhanh hơn trong incident nếu suspect commit rõ.

## 9. Trade-offs

### Advantages

- Giảm search space logarithmically.
- Kết hợp cực tốt với deterministic automated test.

### Costs / Risks

- Commit cũ có thể không build/test được.
- Flaky reproduction phá reliability.
- History phức tạp có thể cần skip/manual reasoning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết dùng `bisect` khi có known good và known bad commit.

### Middle

Tạo deterministic regression test và tự động `bisect run`.

### Senior

Kết hợp bisect với telemetry, deployment history và root-cause analysis.

### Technical Lead / Architect

Đảm bảo repository có build/test reproducibility đủ tốt để historical debugging thực sự khả thi.

## 11. Key takeaway

- `git bisect` biến regression hunting thành binary search có hệ thống.
- Regression test deterministic là điều kiện quan trọng nhất.
- Mục tiêu cuối không chỉ tìm commit, mà hiểu vì sao bug lọt qua verification pipeline.
