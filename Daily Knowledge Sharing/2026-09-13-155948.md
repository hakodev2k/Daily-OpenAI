# 1. C# `record`, value equality và mutable reference trap: khi value semantics giúp domain rõ hơn nhưng lại gây bug nếu state bên trong vẫn mutable

## 1. What is it?

`record` trong C# là một type được tối ưu cho **value-oriented semantics**: hai instances có cùng dữ liệu thành phần có thể được coi là bằng nhau về mặt giá trị thay vì chỉ bằng nhau vì cùng reference.

Mental model:

```text
class
A == B ? thường là reference identity

record
A == B ? structural/value equality theo members
```

Ví dụ:

```csharp
public sealed record Money(decimal Amount, string Currency);
```

```csharp
var a = new Money(100, "USD");
var b = new Money(100, "USD");

Console.WriteLine(a == b); // true
```

Điểm quan trọng: `record` không tự động biến object thành immutable. Nếu record chứa mutable collection hoặc mutable reference, equality có thể cho cảm giác “value object” trong khi state bên trong vẫn thay đổi được.

## 2. Why does it exist?

Nhiều domain concepts không có identity độc lập. `Money(100, "USD")`, `Coordinate(21.0, 105.8)` hoặc `DateRange` thường được hiểu bởi giá trị của chúng.

Nếu dùng class truyền thống, developer phải tự implement:

- `Equals`
- `GetHashCode`
- copy semantics
- deconstruction
- readable `ToString`

`record` giảm boilerplate và làm intent rõ hơn.

Nhưng nếu dùng record như một DTO tiện lợi mà không hiểu equality/hash semantics, bug có thể xuất hiện trong `Dictionary`, `HashSet`, caching hoặc domain logic.

## 3. How does it work?

Compiler generate value-based equality dựa trên components/properties tham gia equality.

```csharp
public sealed record ProductKey(Guid ProductId, string Market);
```

Hai `ProductKey` có cùng `ProductId` và `Market` sẽ có equality/hash tương ứng.

`with` expression tạo shallow copy:

```csharp
var original = new CustomerProfile("Ha", tags);
var changed = original with { Name = "Quang Ha" };
```

Nếu `tags` là `List<string>`, cả hai records vẫn có thể trỏ đến **cùng list**.

```text
original.Tags ----+
                  +--> same List<string>
changed.Tags -----+
```

Đây là shallow copy, không phải deep immutability.

## 4. Practical implementation

Một value object an toàn hơn:

```csharp
public sealed record Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        if (amount < 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        Currency = string.IsNullOrWhiteSpace(currency)
            ? throw new ArgumentException("Currency is required", nameof(currency))
            : currency.ToUpperInvariant();

        Amount = amount;
    }
}
```

Nếu có collection, prefer immutable collection hoặc defensively copy:

```csharp
public sealed record PermissionSet
{
    public ImmutableArray<string> Permissions { get; }

    public PermissionSet(IEnumerable<string> permissions)
        => Permissions = permissions
            .Select(x => x.Trim())
            .Distinct(StringComparer.OrdinalIgnoreCase)
            .Order(StringComparer.OrdinalIgnoreCase)
            .ToImmutableArray();
}
```

## 5. Real production scenario

Một pricing engine dùng:

```csharp
record PriceKey(Guid ProductId, string Currency);
```

làm key cho dictionary cache. Đây là use case tốt vì identity thực sự là tổ hợp `ProductId + Currency`.

Ngược lại, nếu record key chứa một mutable list của channels rồi list bị chỉnh sau khi đã insert vào `Dictionary`, hash code có thể không còn tương ứng với bucket ban đầu. Lookup có thể thất bại theo cách rất khó debug.

## 6. Failure scenario & troubleshooting

**Symptom**
→ một object vừa được add vào `HashSet` nhưng sau đó `Contains` trả `false`.

**Evidence**
→ equality/hash phụ thuộc vào state mutable bị thay đổi sau insert.

**Hypothesis**
→ object dùng làm hash key không immutable thực sự.

**Diagnosis**
→ inspect fields/properties tham gia equality; kiểm tra nested collections/references.

**Fix**
→ dùng immutable components, normalized scalar values hoặc custom equality phù hợp business identity.

**Verification**
→ tests kiểm tra equality/hash ổn định trước và sau các operations hợp lệ.

## 7. Common mistakes

- Nghĩ `record` mặc định immutable.
- Dùng mutable `List<T>` trong record value object.
- Dùng record entity có lifecycle/identity nhưng lại mong structural equality.
- Dùng `with` rồi nghĩ nested object cũng được clone.
- Dùng record làm dictionary key mà state sau đó vẫn thay đổi.
- Dùng record chỉ vì syntax ngắn mà không nghĩ về semantics.

## 8. Alternatives

- **Class:** tốt cho entity có identity/lifecycle rõ.
- **readonly record struct:** phù hợp small value type khi allocation/value-copy trade-off hợp lý.
- **record class:** tốt cho value-oriented reference type.
- **Manual class + custom equality:** khi equality phức tạp hoặc không khớp generated semantics.

## 9. Trade-offs

### Advantages

- Intent về value semantics rõ.
- Ít boilerplate equality/copy.
- Hữu ích cho DTO, commands, immutable domain values.

### Costs / Risks

- Shallow immutability dễ bị hiểu sai.
- Structural equality có thể tốn cost nếu object graph lớn.
- Không phù hợp tự nhiên cho mọi entity có identity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác biệt giữa reference identity và value equality.

### Middle

Biết dùng records cho DTO/value object và tránh mutable nested state.

### Senior

Nhận ra equality/hash semantics ảnh hưởng collection, caching, domain invariants và persistence model.

### Technical Lead / Architect

Quyết định coding convention: entity nào giữ identity semantics, value object nào dùng record, và mức immutability nào cần enforce toàn codebase.

## 11. Key takeaway

- `record` cung cấp value semantics, không tự bảo đảm deep immutability.
- Hash/equality chỉ an toàn khi state tham gia equality ổn định.
- Dùng record theo domain semantics, không chỉ vì syntax đẹp.

# 2. ASP.NET Core Forwarded Headers và trusted proxy: scheme, client IP và HTTPS redirect có thể sai hoàn toàn khi application đứng sau reverse proxy

## 1. What is it?

Khi ASP.NET Core chạy sau reverse proxy như Azure Front Door, Application Gateway, Nginx hoặc IIS, application thường không nhận kết nối trực tiếp từ client.

Mental model:

```text
Client HTTPS
   |
   v
Reverse Proxy
   |
   | HTTP/private network
   v
ASP.NET Core
```

Từ góc nhìn app:

- `RemoteIpAddress` có thể là IP proxy;
- `Request.Scheme` có thể là `http`;
- host có thể là internal host.

Forwarded headers như `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host` truyền original request information qua proxy boundary.

## 2. Why does it exist?

Application cần original scheme/IP cho:

- HTTPS redirect;
- secure cookie generation;
- audit/security logging;
- rate limiting theo client IP;
- redirect URL/OIDC callback;
- absolute URL generation.

Nếu app tin sai data hoặc không process forwarded headers, production behavior có thể khác hoàn toàn local environment.

## 3. How does it work?

Proxy thêm headers:

```http
X-Forwarded-For: 203.0.113.10
X-Forwarded-Proto: https
X-Forwarded-Host: api.example.com
```

Forwarded Headers Middleware có thể cập nhật `HttpContext.Connection.RemoteIpAddress`, `Request.Scheme` và `Request.Host`.

Điểm security-critical là **không được tin forwarded headers từ mọi nguồn**. Client Internet có thể tự gửi header giả nếu request có thể đi trực tiếp tới app.

```text
Trusted proxy -> forwarded header can be accepted
Untrusted client -> forwarded header must not control trusted context
```

## 4. Practical implementation

```csharp
using Microsoft.AspNetCore.HttpOverrides;

builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders =
        ForwardedHeaders.XForwardedFor |
        ForwardedHeaders.XForwardedProto;

    options.KnownProxies.Add(IPAddress.Parse("10.0.0.10"));
});

var app = builder.Build();

app.UseForwardedHeaders();
app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
```

`UseForwardedHeaders` cần đứng đủ sớm để downstream middleware thấy scheme/IP đã normalize.

Trong cloud networking, CIDR/proxy topology có thể thay đổi; production config phải dựa platform architecture thật chứ không hard-code từ laptop assumptions.

## 5. Real production scenario

API đứng sau Application Gateway terminate TLS. Gateway gọi backend qua HTTP.

Nếu forwarded scheme không được process:

```text
client -> HTTPS gateway
backend sees HTTP
UseHttpsRedirection -> redirects to HTTPS
client already HTTPS -> gateway forwards HTTP again
```

Kết quả có thể là redirect loop hoặc generated callback URL sai scheme.

## 6. Failure scenario & troubleshooting

**Symptom**
→ redirect loop, OAuth callback là `http://`, logs luôn thấy cùng một client IP, IP-based rate limiting chặn nhầm mọi user.

**Evidence**
→ inspect request headers tại proxy/app; trace `Request.Scheme`, `Host`, `RemoteIpAddress` trước/sau middleware.

**Hypothesis**
→ forwarded headers thiếu, middleware order sai hoặc trust boundary sai.

**Diagnosis**
→ map hop-by-hop path từ Internet → edge → proxy → app; xác định proxy nào append/overwrite header.

**Fix**
→ configure forwarded headers đúng và restrict trusted proxies/networks.

**Verification**
→ integration test qua chính proxy topology; kiểm tra redirect, OIDC callback và client IP.

## 7. Common mistakes

- Tin `X-Forwarded-For` trực tiếp từ request header.
- `UseHttpsRedirection` trước `UseForwardedHeaders`.
- Log client IP nhưng thực tế đang log load balancer IP.
- Mở backend trực tiếp ra Internet trong khi vẫn trust forwarded headers.
- Assume chỉ có một proxy hop.
- Dùng client IP như authentication identity.

## 8. Alternatives

- Proxy protocol hoặc platform-specific connection metadata trong architecture hỗ trợ.
- Network-layer enforcement không phụ thuộc application header.
- Không cần forwarded headers nếu app trực tiếp terminate client TLS và không có intermediary proxy.

## 9. Trade-offs

### Advantages

- App có original request metadata cần thiết.
- Redirect/auth/audit hoạt động đúng sau proxy.

### Costs / Risks

- Misconfiguration có thể thành spoofing/security issue.
- Multi-proxy chain khó reasoning.
- Platform topology thay đổi có thể làm assumptions cũ sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu app sau proxy không nhìn thấy kết nối client trực tiếp.

### Middle

Biết cấu hình middleware order và inspect forwarded headers.

### Senior

Reasoning về trust chain, proxy hops và security implications của spoofed metadata.

### Technical Lead / Architect

Thiết kế network boundary: proxy nào authoritative, backend có public exposure không, headers nào được overwrite và policy nào được kiểm chứng khi deploy.

## 11. Key takeaway

- Forwarded headers là trust-boundary problem, không chỉ middleware config.
- Process chúng trước logic phụ thuộc scheme/IP.
- Chỉ trust known proxy/network path.

# 3. EF Core `DbContext` vs Generic Repository: khi abstraction giúp boundary rõ hơn và khi nó chỉ che mất LINQ, transaction và query semantics

## 1. What is it?

`DbContext` đã mang nhiều đặc điểm của Unit of Work + Repository-like abstraction:

- `DbSet<T>` là entry point cho entity set;
- Change Tracker theo dõi unit of work;
- `SaveChanges` commit changes;
- LINQ thể hiện query intent.

Generic Repository thường thêm interface như:

```csharp
public interface IRepository<T>
{
    Task<T?> GetByIdAsync(Guid id);
    Task AddAsync(T entity);
    IQueryable<T> Query();
    void Remove(T entity);
}
```

Câu hỏi Senior không phải “Repository Pattern tốt hay xấu”, mà là abstraction đang **cô lập business boundary** hay chỉ bọc lại API của EF Core.

## 2. Why does it exist?

Repository hữu ích khi domain cần persistence contract mang ngôn ngữ business:

```csharp
IOrderRepository.GetPendingForCustomerAsync(...)
```

Nó có thể cô lập aggregate persistence rules và ngăn application layer biết chi tiết storage.

Generic Repository xuất hiện để chuẩn hóa CRUD, nhưng với EF Core nó thường mất lợi thế vì LINQ/query composition có nhiều semantics mà wrapper CRUD không biểu đạt hết.

## 3. How does it work?

Direct `DbContext`:

```text
Application handler
   -> DbContext/LINQ
   -> provider translates SQL
   -> SaveChanges
```

Domain-specific repository:

```text
Application
   -> IOrderRepository
        responsibility: aggregate persistence/query boundary
   -> EF implementation
```

Generic repository thường rơi vào hai trạng thái:

1. API quá hẹp → thiếu Include/projection/specification/transaction features.
2. Expose `IQueryable<T>` → abstraction lại leak toàn EF query semantics ra ngoài.

## 4. Practical implementation

Direct context phù hợp query-oriented application service:

```csharp
public async Task<IReadOnlyList<OrderListItem>> Handle(
    GetOrders query,
    CancellationToken ct)
{
    return await db.Orders
        .Where(x => x.CustomerId == query.CustomerId)
        .OrderByDescending(x => x.CreatedAtUtc)
        .Select(x => new OrderListItem(x.Id, x.Status, x.Total))
        .ToListAsync(ct);
}
```

Domain-specific repository phù hợp aggregate behavior:

```csharp
public interface IOrderRepository
{
    Task<Order?> GetForUpdateAsync(OrderId id, CancellationToken ct);
    void Add(Order order);
}
```

Application layer gọi aggregate behavior rồi `SaveChanges` qua Unit of Work/context boundary rõ ràng.

## 5. Real production scenario

Một project dùng `GenericRepository<T>` với methods `GetAll`, `Find`, `Update`. Sau vài tháng cần:

- projection;
- `AsSplitQuery`;
- compiled query;
- filtered include;
- optimistic concurrency;
- raw SQL;
- transaction;
- provider-specific optimization.

Team bắt đầu thêm hàng chục optional parameters vào repository. Abstraction cuối cùng phức tạp hơn EF Core mà vẫn không che được EF Core.

## 6. Failure scenario & troubleshooting

**Symptom**
→ query performance kém nhưng application layer không nhìn thấy generated SQL/translation choices vì generic abstraction che quá nhiều.

**Evidence**
→ repository materialize `ToList` sớm rồi filter trong memory; hoặc repository trả entities toàn bộ khi caller chỉ cần projection.

**Hypothesis**
→ abstraction boundary được thiết kế quanh CRUD thay vì access pattern/business need.

**Diagnosis**
→ trace SQL, round trips và data shape từ repository đến caller.

**Fix**
→ bỏ generic wrapper không tạo value hoặc thay bằng domain-specific query/repository methods.

**Verification**
→ query plan/SQL rõ hơn, tests vẫn bảo vệ behavior, code giảm accidental abstraction.

## 7. Common mistakes

- Tạo Generic Repository chỉ vì template architecture yêu cầu.
- Bọc `DbContext` nhưng expose `IQueryable`, cuối cùng không thực sự abstract gì.
- Repository method trả full entity cho read model đơn giản.
- Mock repository hàng trăm lần và tưởng persistence behavior đã được test.
- Nhét transaction orchestration vào từng repository riêng lẻ.
- Dùng repository để “có thể đổi SQL thành MongoDB một ngày nào đó” mà không có requirement thật.

## 8. Alternatives

- Direct `DbContext` trong application handlers.
- Domain-specific Repository cho Aggregate.
- Query objects/specifications khi repeated complex query thực sự cần reuse.
- Separate read model/query service cho CQRS-style read paths.

## 9. Trade-offs

### Advantages

Domain-specific repository có thể:

- bảo vệ aggregate boundary;
- diễn đạt business intent;
- cô lập persistence decisions quan trọng.

Direct context có thể:

- giữ LINQ/EF capability minh bạch;
- ít boilerplate;
- dễ tối ưu query.

### Costs / Risks

- Direct DbContext có thể làm application coupling chặt vào EF nếu boundary không kiểm soát.
- Generic repository dễ trở thành leaky abstraction hoặc lowest-common-denominator API.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbContext`, `DbSet`, tracking và `SaveChanges` đã giải quyết nhiều persistence concerns.

### Middle

Biết viết query trực tiếp hiệu quả và repository method có intent rõ.

### Senior

Nhận diện abstraction leakage, materialization sai và test strategy giả tạo do over-mocking.

### Technical Lead / Architect

Quyết định repository chỉ xuất hiện ở boundary nào có domain value; chấp nhận direct DbContext nơi nó đơn giản và minh bạch hơn.

## 11. Key takeaway

- Không cần bọc `DbContext` chỉ để nói rằng có Repository Pattern.
- Repository hữu ích nhất khi nó bảo vệ business/persistence boundary có ý nghĩa.
- Abstraction tốt phải giảm coupling thật, không chỉ thêm interface.

# 4. SQL constraints như integrity boundary: `UNIQUE`, `CHECK`, `FOREIGN KEY` và vì sao application validation không đủ để bảo vệ dữ liệu

## 1. What is it?

Database constraints là invariants được enforce trực tiếp bởi relational database.

Ví dụ:

```sql
ALTER TABLE Users
ADD CONSTRAINT UQ_Users_Email UNIQUE (NormalizedEmail);

ALTER TABLE Orders
ADD CONSTRAINT CK_Orders_Total_NonNegative
CHECK (Total >= 0);

ALTER TABLE OrderItems
ADD CONSTRAINT FK_OrderItems_Orders
FOREIGN KEY (OrderId) REFERENCES Orders(Id);
```

Mental model:

```text
Application validation -> user-friendly guard
Database constraint    -> final integrity boundary
```

## 2. Why does it exist?

Application validation chỉ bảo vệ code path đi qua application đó. Dữ liệu còn có thể được thay đổi bởi:

- background worker;
- migration script;
- admin tool;
- import job;
- second service;
- concurrent request.

Nếu invariant quan trọng chỉ tồn tại trong C# `if`, database không thực sự bảo vệ invariant đó.

## 3. How does it work?

Database kiểm tra constraint trong transaction trước commit.

Race-condition example:

```text
Request A: SELECT email -> not exists
Request B: SELECT email -> not exists
A: INSERT
B: INSERT
```

Application-level pre-check của cả hai đều pass. Chỉ `UNIQUE` constraint mới arbitrate đúng tại write boundary.

## 4. Practical implementation

Schema:

```sql
CREATE UNIQUE INDEX UX_Users_NormalizedEmail
ON Users(NormalizedEmail);
```

Application vẫn pre-check để UX tốt, nhưng phải handle database conflict:

```csharp
try
{
    db.Users.Add(user);
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateException ex) when (IsUniqueViolation(ex))
{
    throw new EmailAlreadyExistsException(user.Email, ex);
}
```

Điều quan trọng là map provider-specific error đủ chắc chắn; đừng catch mọi `DbUpdateException` rồi báo “email duplicate”.

## 5. Real production scenario

Signup API có validation:

```csharp
if (!await db.Users.AnyAsync(x => x.Email == email))
    db.Users.Add(...);
```

Ở load bình thường gần như luôn đúng. Trong campaign traffic, hai concurrent requests cùng email có thể vượt qua `AnyAsync` trước khi một transaction commit.

Không có unique constraint → duplicate account.

## 6. Failure scenario & troubleshooting

**Symptom**
→ migration thêm `UNIQUE` constraint fail ở production.

**Evidence**
→ dữ liệu lịch sử đã có duplicates do schema trước đây không enforce invariant.

**Hypothesis**
→ business invariant mới không khớp legacy data.

**Diagnosis**
→ query duplicates, xác định ownership và remediation rule.

**Fix**
→ clean/backfill data trước, deploy application compatible, sau đó add constraint theo safe migration sequence.

**Verification**
→ duplicate query về 0, migration pass, concurrent-write test chứng minh invariant được enforce.

## 7. Common mistakes

- Chỉ validate trong application.
- Tạo `CHECK` constraint chứa business rule thay đổi thường xuyên và khó deploy.
- Thêm `NOT NULL`/FK trực tiếp trên table lớn mà không nghĩ migration locking.
- Catch database exception quá rộng.
- Disable foreign keys để “insert nhanh hơn” rồi không có consistency strategy.
- Dùng constraint thay cho user-friendly validation hoàn toàn.

## 8. Alternatives

- Application-only validation: đơn giản nhưng không đủ cho strong invariant.
- Database trigger: mạnh nhưng hidden behavior và khó maintain hơn; chỉ dùng khi thực sự cần.
- Serializable transaction/explicit locking: giải quyết một số cross-row invariant nhưng có concurrency cost.

## 9. Trade-offs

### Advantages

- Integrity được enforce ở nơi dữ liệu tồn tại.
- Bảo vệ mọi writer, không chỉ một code path.
- Giải quyết race condition tốt cho uniqueness/referential integrity.

### Costs / Risks

- Schema change cần migration strategy.
- Constraint quá phức tạp có thể làm write path khó hiểu.
- Provider behavior/error codes cần được handle chính xác.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu PK/FK/UNIQUE/CHECK không chỉ là schema decoration.

### Middle

Biết kết hợp application validation với database constraints.

### Senior

Thiết kế migrations an toàn, handle concurrency và provider errors đúng.

### Technical Lead / Architect

Quyết định invariant nào thuộc database, invariant nào thuộc domain/application, và cách roll out constraint trên live data mà không gây downtime.

## 11. Key takeaway

- Validation cho UX; constraints bảo vệ integrity.
- Concurrent writes làm pre-check application không đủ.
- Schema constraint cần rollout strategy trên production data.

# 5. Elasticsearch `bool` query, filter context và scoring: tách “document có hợp lệ không” khỏi “document nào phù hợp hơn”

## 1. What is it?

Elasticsearch search thường có hai loại reasoning:

1. **Filtering:** document có thỏa điều kiện bắt buộc không?
2. **Scoring:** trong các document hợp lệ, document nào relevant hơn?

`bool` query kết hợp:

- `must`
- `should`
- `filter`
- `must_not`

Mental model:

```text
filter -> yes/no eligibility
query  -> relevance score
```

## 2. Why does it exist?

Một e-commerce search cho `"running shoes"` có thể cần:

- text relevance theo tên/mô tả;
- `market = VN`;
- `isActive = true`;
- `price <= 3000000`;
- category filter.

Nếu mọi điều kiện bị đưa vào scoring query, relevance trở nên khó dự đoán và Elasticsearch phải làm scoring work không cần thiết cho exact filters.

## 3. How does it work?

Ví dụ:

```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "name": "running shoes" } }
      ],
      "filter": [
        { "term": { "market": "VN" } },
        { "term": { "isActive": true } },
        { "range": { "price": { "lte": 3000000 } } }
      ]
    }
  }
}
```

`match` tham gia `_score`. `term`/`range` trong filter context chỉ quyết định document có được giữ lại không.

Filters cũng có cơ hội reuse/caching tốt hơn tùy query shape và Elasticsearch internals.

## 4. Practical implementation

Trong .NET client, tư duy query nên được tách thành:

```text
User text -> full-text clause
Business eligibility -> filter clauses
Optional ranking boosts -> should clauses
```

Ví dụ business rule “chỉ sản phẩm đang active” không nên trở thành boost. Nó là hard filter.

Khi debug relevance, dùng `_explain` có chọn lọc hoặc profile API trong môi trường phù hợp; không chạy expensive profiling bừa bãi production traffic.

## 5. Real production scenario

Search API ban đầu đưa tất cả conditions vào `must`. Sau khi thêm nhiều terms/ranges, relevance score thay đổi khó hiểu và latency tăng.

Refactor business predicates sang `filter` giúp relevance model dễ reasoning hơn:

```text
eligible set
   -> text relevance
   -> optional boosts
   -> final rank
```

## 6. Failure scenario & troubleshooting

**Symptom**
→ sản phẩm inactive vẫn xuất hiện hoặc exact filter làm kết quả rank kỳ lạ.

**Evidence**
→ query DSL cho thấy business constraint nằm trong `should`, hoặc `minimum_should_match` không đúng.

**Hypothesis**
→ team trộn eligibility với relevance.

**Diagnosis**
→ tách từng clause, inspect matched docs và score contribution.

**Fix**
→ hard conditions chuyển vào `filter`/`must_not`; text/relevance ở query context.

**Verification**
→ golden-query tests và search analytics xác nhận both correctness + ranking quality.

## 7. Common mistakes

- Dùng `match` cho keyword/exact field.
- Dùng `term` trên analyzed `text` field mà mong full-text behavior.
- Đưa mọi filter vào scoring context.
- Tối ưu scoring trước khi mapping/analyzer đúng.
- Không có representative query set để đánh giá relevance.
- Treat Elasticsearch như source of truth cho transactional eligibility.

## 8. Alternatives

- SQL search/filter: đủ tốt cho exact filters/simple prefix cases.
- Dedicated search engine: phù hợp full-text relevance, analyzers, ranking.
- Application-side filtering sau search: thường tệ vì pagination/count/relevance bị sai và data transfer tăng.

## 9. Trade-offs

### Advantages

- Tách correctness khỏi relevance.
- Query dễ reasoning và optimize hơn.
- Business filters không làm score nhiễu.

### Costs / Risks

- Search DSL phức tạp khi ranking rules tăng.
- Eventual consistency với source DB vẫn tồn tại.
- Relevance cần measurement chứ không chỉ unit tests.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu filter là yes/no còn scoring quyết định rank.

### Middle

Biết dùng `bool` query đúng và mapping đúng field type.

### Senior

Debug relevance, latency và query profile dựa evidence.

### Technical Lead / Architect

Định nghĩa search contract: dữ liệu nào authoritative từ DB, business eligibility nào sync sang index, ranking ownership thuộc team nào và stale search được chấp nhận bao lâu.

## 11. Key takeaway

- Hard business conditions thuộc filter context.
- Full-text relevance thuộc scoring query.
- Search correctness và search ranking là hai bài toán khác nhau.

# 6. HTTP Idempotency Key cho `POST`: chống duplicate side effect khi client retry nhưng request đầu tiên có thể đã thành công

## 1. What is it?

Idempotency Key là client-generated identifier đại diện cho **một logical operation**. Nếu cùng request được gửi lại với cùng key, server trả lại outcome trước đó thay vì thực hiện side effect lần nữa.

Mental model:

```text
POST /payments
Idempotency-Key: abc-123

retry same logical request
Idempotency-Key: abc-123

=> one logical payment, not two
```

## 2. Why does it exist?

Distributed systems có ambiguous failure:

```text
Client sends request
Server commits payment
Response is lost
Client sees timeout
```

Client không biết operation thất bại hay chỉ response bị mất.

Nếu retry `POST` bình thường, payment/order có thể được tạo hai lần.

## 3. How does it work?

Server lưu record:

```text
IdempotencyKey
RequestFingerprint
Status
ResponseCode
ResponseBody / ResultReference
CreatedAt
```

Flow:

```text
receive key
  -> key absent: reserve/process/store result
  -> key exists + same request: return stored result
  -> key exists + different payload: reject conflict
```

Concurrency cần được xử lý atomic; hai requests cùng key đến đồng thời không được cùng execute business action.

## 4. Practical implementation

Một persistence model đơn giản:

```csharp
public sealed class IdempotencyRecord
{
    public required string Key { get; init; }
    public required string RequestHash { get; init; }
    public string? ResourceId { get; set; }
    public int? StatusCode { get; set; }
    public DateTime CreatedAtUtc { get; init; }
}
```

Database cần unique constraint trên key.

Application flow có thể nằm trong transaction phù hợp nếu resource creation và idempotency record cùng database.

Nếu operation đi qua external payment provider, key của internal API nên map rõ với provider idempotency/transaction reference thay vì giả định local DB record đủ bảo vệ mọi side effect.

## 5. Real production scenario

Mobile app tạo order qua mạng 4G. Client timeout ở giây thứ 3, nhưng server đã commit order ở giây thứ 2.9.

Client retry.

Không idempotency → hai orders.

Có key → server nhận ra cùng logical operation và trả lại order đã tạo.

## 6. Failure scenario & troubleshooting

**Symptom**
→ duplicate payment vẫn xuất hiện dù API có idempotency table.

**Evidence**
→ local key reservation xảy ra sau khi external charge được gọi; process crash giữa charge và insert record.

**Hypothesis**
→ idempotency boundary không bao trùm side effect nguy hiểm nhất.

**Diagnosis**
→ vẽ timeline DB write + external call + crash windows.

**Fix**
→ dùng provider idempotency key nếu hỗ trợ; reorder workflow; kết hợp durable state machine/outbox tùy boundary.

**Verification**
→ fault injection ở từng step và xác nhận retry không double-charge.

## 7. Common mistakes

- Generate key ở server cho mỗi retry thay vì client giữ cùng key.
- Cùng key nhưng payload khác vẫn silently reuse result.
- Chỉ cache response in-memory nên restart mất idempotency state.
- TTL quá ngắn so với retry/business window.
- Nghĩ idempotency key biến toàn distributed transaction thành exactly-once.
- Không có unique constraint cho key.

## 8. Alternatives

- Natural unique business key, ví dụ external order number.
- Conditional create với unique constraint.
- PUT cho resource có client-defined stable identifier.
- Queue + deduplication/inbox pattern cho asynchronous command.

## 9. Trade-offs

### Advantages

- Giảm duplicate side effects khi retry.
- Làm client retry an toàn hơn.
- Rất phù hợp payment/order/create operations quan trọng.

### Costs / Risks

- Cần durable storage và cleanup policy.
- Phải định nghĩa request fingerprint và response retention.
- Cross-system side effects vẫn cần idempotency ở đúng boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không chứng minh request chưa được xử lý.

### Middle

Biết lưu key/result và enforce unique constraint.

### Senior

Reasoning về concurrent duplicate, payload mismatch, crash windows và external provider semantics.

### Technical Lead / Architect

Xác định operations nào bắt buộc idempotent, retention bao lâu, key ownership thuộc client hay gateway, và guarantee nào thực tế có thể cung cấp end-to-end.

## 11. Key takeaway

- Retry sau timeout luôn có khả năng duplicate side effect.
- Idempotency key đại diện cho logical operation, không phải một HTTP attempt.
- Guarantee phải bao phủ side effect thực sự quan trọng.

# 7. Azure App Service outbound SNAT port exhaustion: vì sao dependency timeout có thể đến từ connection behavior chứ không phải downstream chậm

## 1. What is it?

Khi App Service gọi outbound tới public endpoints, platform phải map internal connections qua SNAT (Source Network Address Translation). Mỗi active outbound connection sử dụng finite networking resources.

Mental model:

```text
App Service instance
   -> many outbound TCP connections
   -> SNAT translation
   -> public dependency
```

Nếu application liên tục tạo connection mới thay vì reuse, có thể cạn ephemeral/SNAT resources và new outbound connections bắt đầu timeout.

## 2. Why does it exist?

NAT cho phép nhiều private workloads chia sẻ public egress identity. Nhưng connection-oriented translation cần state.

Một antipattern .NET cổ điển:

```csharp
using var client = new HttpClient();
await client.GetAsync(url);
```

lặp với traffic cao có thể gây connection churn, DNS/socket issues và SNAT pressure.

## 3. How does it work?

TCP connection có lifecycle; sau close, một số resources không lập tức reusable theo cách developer tưởng.

```text
request
-> new TCP connection
-> TLS handshake
-> HTTP
-> close
-> another request creates another connection
```

Connection pooling đổi thành:

```text
request 1 --+
request 2 --+--> reusable connection pool --> dependency
request 3 --+
```

`IHttpClientFactory` và `SocketsHttpHandler` giúp quản lý handler/pooling/lifetime tốt hơn khi dùng đúng.

## 4. Practical implementation

```csharp
builder.Services.AddHttpClient<InventoryClient>(client =>
{
    client.BaseAddress = new Uri(builder.Configuration["Inventory:BaseUrl"]!);
    client.Timeout = TimeSpan.FromSeconds(5);
})
.SetHandlerLifetime(TimeSpan.FromMinutes(5));
```

Typed client:

```csharp
public sealed class InventoryClient(HttpClient httpClient)
{
    public async Task<InventoryDto?> GetAsync(Guid id, CancellationToken ct)
        => await httpClient.GetFromJsonAsync<InventoryDto>(
            $"inventory/{id}", ct);
}
```

Connection reuse chỉ là một phần; concurrency và downstream capacity vẫn phải được giới hạn hợp lý.

## 5. Real production scenario

Sau traffic spike, API gọi 4 third-party services trên mỗi request. Code tạo nhiều independent clients/connections. CPU app thấp, downstream dashboards bình thường, nhưng App Service bắt đầu có outbound connect timeout.

Scale-out đôi khi giảm symptom tạm thời vì có thêm instance/network resources, nhưng root cause vẫn là connection behavior.

## 6. Failure scenario & troubleshooting

**Symptom**
→ outbound timeout tăng, CPU/DB ổn, dependency server không thấy request tương ứng.

**Evidence**
→ high outbound connections, socket/SNAT diagnostics, application tạo clients/handlers quá thường xuyên.

**Hypothesis**
→ connection churn/SNAT exhaustion thay vì dependency processing latency.

**Diagnosis**
→ correlate App Service networking diagnostics, dependency telemetry, connection count và request rate.

**Fix**
→ reuse pooled connections, dùng `IHttpClientFactory`, reduce unnecessary fan-out, cân nhắc private/network architecture hoặc NAT Gateway khi phù hợp workload.

**Verification**
→ load test cho thấy stable connection count và connect timeout biến mất.

## 7. Common mistakes

- New `HttpClient` cho mọi request.
- Nghĩ dispose sớm luôn giải phóng network resource ngay.
- Chỉ tăng timeout.
- Scale-out để che root cause vô thời hạn.
- Retry connect timeout quá mạnh tạo thêm connection pressure.
- Không phân biệt connect timeout với server response timeout.

## 8. Alternatives

- App Service với connection pooling đúng: thường đủ cho nhiều workload.
- NAT Gateway/architecture egress khác khi cần scale/egress control cao hơn.
- Private Endpoint/VNet integration cho dependencies phù hợp, nhưng vẫn phải reuse connections.
- Async messaging để giảm synchronous fan-out nếu business flow cho phép.

## 9. Trade-offs

### Advantages

Connection reuse:

- giảm handshake cost;
- giảm SNAT/socket pressure;
- tăng throughput ổn định.

### Costs / Risks

- Handler lifetime/DNS refresh cần hiểu.
- Long-lived pools cần connection health management.
- Infrastructure egress changes tăng operational cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP request có TCP/TLS/network resources bên dưới.

### Middle

Dùng `IHttpClientFactory`, timeout và cancellation đúng.

### Senior

Phân biệt downstream latency với connect/SNAT/socket exhaustion bằng telemetry.

### Technical Lead / Architect

Quyết định egress topology, connection budget, fan-out limits và khi nào cần NAT/network architecture thay đổi thay vì chỉ sửa code.

## 11. Key takeaway

- Outbound timeout không luôn có nghĩa dependency chậm.
- Connection reuse là production requirement, không chỉ micro-optimization.
- Retry sai có thể làm SNAT pressure tệ hơn.

# 8. Managed memory leak trong .NET: GC vẫn hoạt động nhưng object không được collect vì còn GC root

## 1. What is it?

Managed memory leak không nhất thiết là memory “quên free” theo kiểu native code. Trong .NET, leak thường có nghĩa object **vẫn reachable từ một GC root**, nên GC đúng khi không collect nó dù application không còn cần object về mặt business.

Mental model:

```text
GC Root
  |
  v
Singleton / static field / event
  |
  v
Object graph
  |
  v
objects vẫn reachable -> không collect
```

## 2. Why does it exist?

GC chỉ biết reachability, không biết intent của developer.

Nếu cache không giới hạn, event subscription không unsubscribe, static dictionary tăng mãi hoặc singleton giữ scoped object graph, GC coi chúng là live objects hoàn toàn hợp lệ.

Do đó “có GC” không có nghĩa application không thể leak.

## 3. How does it work?

GC bắt đầu từ roots như:

- static references;
- active stack references;
- handles;
- runtime roots;
- finalization-related roots.

Object reachable từ root được giữ lại.

Leak pattern:

```csharp
public static event EventHandler? Changed;
```

Một long-lived publisher giữ delegate, delegate giữ subscriber target. Nếu subscriber đáng lẽ short-lived nhưng không unsubscribe, whole object graph có thể sống mãi.

## 4. Practical implementation

Unbounded cache antipattern:

```csharp
private static readonly ConcurrentDictionary<string, byte[]> Cache = new();
```

Nếu keys tăng không giới hạn, GC không thể collect values.

Thay bằng bounded cache policy:

```csharp
builder.Services.AddMemoryCache(options =>
{
    options.SizeLimit = 10_000;
});
```

Khi add:

```csharp
cache.Set(key, value, new MemoryCacheEntryOptions
{
    Size = 1,
    AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
});
```

Policy cụ thể phải dựa data size/freshness, không copy số ví dụ máy móc.

## 5. Real production scenario

Một multi-tenant API cache tenant configuration bằng static dictionary và không evict tenants inactive. Sau vài tuần, process memory tăng từ 800 MB lên 6 GB. CPU bình thường, GC vẫn chạy, nhưng memory sau full GC không giảm đáng kể.

Đây là retention leak, không phải “GC hỏng”.

## 6. Failure scenario & troubleshooting

**Symptom**
→ memory tăng liên tục qua nhiều giờ/ngày, restart thì giảm, sau đó tăng lại.

**Evidence**
→ Gen2/live heap size tăng; full GC không reclaim tương ứng.

**Hypothesis**
→ long-lived roots giữ object graph.

**Diagnosis**
→ `dotnet-counters` xác nhận trend; capture dump bằng `dotnet-dump`; inspect dominant types và `gcroot` path.

**Fix**
→ remove unintended root, bound cache, unsubscribe event, correct lifetime ownership.

**Verification**
→ soak test; live heap plateau thay vì tăng vô hạn.

## 7. Common mistakes

- Chỉ nhìn process working set rồi kết luận leak.
- Gọi `GC.Collect()` để “fix”.
- Tăng memory limit mà không tìm retention path.
- Dump một snapshot duy nhất mà không so sánh growth.
- Không phân biệt managed heap, native memory, mmap/file cache.
- Dùng static collection như global cache không TTL/size bound.

## 8. Alternatives

Không có “alternative” cho GC root concept, nhưng remediation có thể khác:

- bounded `IMemoryCache`;
- distributed cache;
- weak reference cho specialized scenarios;
- explicit unsubscribe/dispose;
- redesign ownership/lifetime.

WeakReference không nên dùng như generic fix cho cache leak.

## 9. Trade-offs

### Advantages

Managed GC giảm manual allocation/free burden rất lớn.

### Costs / Risks

- Reachability khác business usefulness.
- Long-lived graphs có thể tăng Gen2/LOH pressure.
- Memory diagnostics cần dump/root analysis, không chỉ code inspection.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu object chỉ collect khi không còn reachable.

### Middle

Nhận biết static cache/event/lifetime patterns gây retention.

### Senior

Dùng counters + dump + GC root để chứng minh leak path.

### Technical Lead / Architect

Thiết kế memory ownership, cache budgets, soak tests và production diagnostic runbook trước khi hệ thống có long-running memory incident.

## 11. Key takeaway

- GC không thể collect object vẫn reachable từ root.
- Managed leak thường là ownership/lifetime bug.
- Chứng minh bằng heap trend + GC root, không đoán bằng working set.

# 9. Canary deployment và automated rollback: release production dựa trên health evidence thay vì “deploy thành công = release thành công”

## 1. What is it?

Canary deployment đưa version mới tới một phần nhỏ traffic/instances trước, quan sát health metrics rồi mới mở rộng rollout.

Mental model:

```text
v1 -> 95% traffic
v2 -> 5% traffic

observe
  -> healthy: 25% -> 50% -> 100%
  -> unhealthy: rollback to v1
```

Đây là release-risk control, không chỉ deployment technique.

## 2. Why does it exist?

CI có thể pass nhưng production vẫn khác ở:

- data distribution;
- traffic concurrency;
- real external dependencies;
- configuration;
- memory behavior;
- latency tails.

Nếu đưa 100% traffic vào version mới ngay lập tức, blast radius của regression là toàn bộ user base.

## 3. How does it work?

Pipeline trưởng thành:

```text
commit
-> build
-> tests
-> immutable artifact
-> deploy canary
-> health validation
-> progressive traffic
-> monitor
-> promote or rollback
```

Health gates nên dựa signals như:

- error rate;
- p95/p99 latency;
- saturation;
- dependency errors;
- business KPI quan trọng;
- readiness/health.

“Container started” hoặc “deployment API returned 200” không đủ.

## 4. Practical implementation

Một simplified release policy:

```text
Canary = 5%
Observation = 10 min
Rollback if:
- HTTP 5xx > baseline + threshold
- p95 > agreed threshold
- critical dependency failure spikes
- business transaction success drops
```

Trong Azure, implementation có thể dùng deployment slots, Front Door/Application Gateway traffic split, Container Apps revisions hoặc Kubernetes rollout strategy tùy platform.

Artifact phải là cùng artifact được promote, tránh rebuild khác nhau giữa environments.

## 5. Real production scenario

Release mới thay JSON serialization option khiến 2% legacy clients nhận incompatible response. Unit/integration tests không cover old mobile versions.

Canary 5% làm client error metric tăng rõ. Automated gate dừng rollout và route traffic về stable version trước khi toàn bộ fleet bị ảnh hưởng.

## 6. Failure scenario & troubleshooting

**Symptom**
→ canary nhìn healthy nhưng full rollout mới fail.

**Evidence**
→ canary traffic quá nhỏ hoặc không representative; threshold chỉ nhìn average latency; DB load issue chỉ xuất hiện trên scale lớn.

**Hypothesis**
→ health gate không đủ sensitivity hoặc không cover saturation effect.

**Diagnosis**
→ so sánh canary cohort, workload, p95/p99, DB/queue metrics và baseline.

**Fix**
→ progressive stages phù hợp hơn, representative routing và richer gates.

**Verification**
→ controlled rollout/fault simulation chứng minh gate bắt được regression mục tiêu.

## 7. Common mistakes

- Canary chỉ 1 instance nhưng traffic gần như bằng 0.
- Chỉ check 5xx, bỏ qua latency/business errors.
- Rollback app nhưng migration DB đã breaking backward compatibility.
- Rebuild artifact khi promote.
- Giữ canary quá lâu mà không có decision policy.
- Feature flag/deployment strategy không có owner/cleanup.

## 8. Alternatives

- Blue-Green: switch toàn traffic giữa two environments, rollback nhanh nhưng không giảm blast radius trước switch như canary.
- Rolling deployment: thay instances dần, nhưng traffic exposure control có thể ít tinh tế hơn.
- Feature flags: giảm risk theo feature, nhưng không thay deployment validation hoàn toàn.

## 9. Trade-offs

### Advantages

- Giảm blast radius.
- Dùng production evidence trước full rollout.
- Rollback sớm hơn khi regression xuất hiện.

### Costs / Risks

- Pipeline/traffic control phức tạp hơn.
- Cần reliable metrics và baselines.
- DB/schema changes phải backward compatible để rollback thực sự khả thi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy artifact thành công chưa đồng nghĩa application healthy.

### Middle

Biết health checks, metrics và rollback flow.

### Senior

Thiết kế thresholds, progressive rollout và backward-compatible release.

### Technical Lead / Architect

Xác định release SLO, acceptable blast radius, telemetry gates, database compatibility policy và automation nào có quyền tự rollback.

## 11. Key takeaway

- Deployment success khác production health.
- Canary cần representative traffic + meaningful health gates.
- Rollback chỉ khả thi nếu app, config và database còn backward compatible.

# 10. Architecture Decision Record (ADR): ghi lại quyết định, context và trade-off để hệ thống không phụ thuộc vào trí nhớ của vài người

## 1. What is it?

ADR là tài liệu ngắn ghi lại một quyết định kiến trúc quan trọng cùng context, alternatives và consequences.

Một ADR không phải design document 50 trang. Mental model:

```text
Context
-> Decision
-> Alternatives considered
-> Consequences
-> Status
```

Ví dụ: “Dùng Modular Monolith cho Release 1 thay vì microservices”.

## 2. Why does it exist?

Sau 12 tháng, code cho thấy **chúng ta đã làm gì**, nhưng không cho biết rõ **vì sao**.

Nếu người ra quyết định rời team, assumptions biến mất. Team mới dễ lặp lại discussion cũ hoặc “sửa” một decision mà không hiểu constraint ban đầu.

ADR tạo historical reasoning trail.

## 3. How does it work?

ADR có lifecycle:

```text
Proposed
-> Accepted
-> Superseded / Deprecated
```

ADR cũ thường không nên bị rewrite để phản ánh hiện tại. Nếu decision thay đổi, tạo ADR mới và mark ADR cũ là superseded. Như vậy historical reasoning vẫn còn.

## 4. Practical implementation

Ví dụ:

```markdown
# ADR-004: Use Modular Monolith for Release 1

## Status
Accepted

## Context
Team 4 developers, one deployment unit, domains still evolving.
Microservices would require service ownership, distributed tracing,
message reliability and independent deployment maturity not currently needed.

## Decision
Use modular monolith with explicit module boundaries.

## Alternatives
- Microservices
- Traditional layered monolith

## Consequences
- Simpler deployment and transactions.
- Module boundaries must be enforced in code review/tests.
- Extraction remains possible later but is not free.
```

ADR nên link tới requirement/PR/design liên quan, nhưng không phụ thuộc vào chat message ephemeral.

## 5. Real production scenario

Team chọn Redis cho distributed cache vì latency requirement và multi-instance deployment. Hai năm sau, Redis outage cho thấy cache đã trở thành hard dependency.

ADR ban đầu ghi “stale fallback acceptable trong 10 phút”. Điều đó giúp incident review xác định implementation đã drift khỏi intended resilience design.

ADR không chỉ phục vụ architecture review; nó cũng giúp kiểm tra **decision drift**.

## 6. Failure scenario & troubleshooting

**Symptom**
→ repository có hàng chục ADR nhưng không ai tin chúng.

**Evidence**
→ status không cập nhật, decision đã thay đổi nhưng ADR cũ vẫn ghi accepted; documents quá dài và duplicate design docs.

**Hypothesis**
→ ADR process trở thành documentation ceremony thay vì decision record.

**Diagnosis**
→ kiểm tra bao nhiêu ADR còn refer trong architecture/code review và bao nhiêu bị stale.

**Fix**
→ giữ ADR ngắn, tạo ADR mới khi supersede, đặt owner/review trigger cho major decision changes.

**Verification**
→ architecture discussions link vào ADR thay vì lặp từ đầu; new team member hiểu rationale từ repository.

## 7. Common mistakes

- Viết ADR cho mọi class/library nhỏ.
- Chỉ ghi decision, không ghi alternatives/trade-offs.
- Rewrite ADR cũ và xóa historical context.
- Ghi “because best practice” thay vì actual constraints.
- ADR không link tới implementation/requirement nào.
- Dùng ADR để hợp thức hóa decision đã chốt mà không thật sự phân tích alternatives.

## 8. Alternatives

- Full architecture/design document: cần khi hệ thống/flow phức tạp và cần diagrams/spec chi tiết.
- PR description: tốt cho implementation-specific context nhưng khó làm long-term architecture index.
- Wiki: dễ discover nhưng có risk tách khỏi code/version history.
- Code comments: phù hợp local implementation nuance, không phù hợp system-level decision rationale.

## 9. Trade-offs

### Advantages

- Giữ decision history gần repository.
- Giảm repeated architecture debates.
- Tăng onboarding và review transparency.
- Giúp track trade-off và assumption drift.

### Costs / Risks

- Cần discipline cập nhật status.
- Quá nhiều ADR nhỏ tạo noise.
- Không thay thế code, tests hoặc detailed design khi chúng cần thiết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết đọc ADR để hiểu vì sao architecture hiện tại tồn tại.

### Middle

Biết đóng góp context/consequence từ implementation reality.

### Senior

Viết ADR cho decisions có long-term cost: storage, messaging, deployment, boundaries, consistency, security.

### Technical Lead / Architect

Quyết định decision nào đáng ghi, đảm bảo alternatives/trade-offs được đánh giá và dùng ADR như governance nhẹ thay vì bureaucracy.

## 11. Key takeaway

- ADR lưu “why”, không chỉ “what”.
- Decision thay đổi nên được supersede, không xóa history.
- Chỉ ghi những quyết định có consequence đủ lớn để tương lai cần hiểu lại.
