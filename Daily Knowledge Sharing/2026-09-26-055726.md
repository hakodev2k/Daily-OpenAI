# 1. .NET Garbage Collector, generations và Large Object Heap dưới production load

## 1. What is it?

Mental model: .NET GC quản lý lifetime của managed objects bằng cách tìm object còn reachable rồi thu hồi phần không còn reachable. Generational GC dựa trên quan sát rằng phần lớn object sống rất ngắn: Gen 0 chứa object mới, survivor có thể được promote lên Gen 1 rồi Gen 2. Large Object Heap (LOH) thường chứa allocation lớn, điển hình từ khoảng 85 KB trở lên.

Điểm quan trọng không phải “GC tự lo memory”, mà là application vẫn quyết định allocation rate, object lifetime và reference graph; các quyết định đó quyết định chi phí GC.

## 2. Why does it exist?

Manual memory management dễ tạo use-after-free, double-free và leak. GC đổi một phần quyền kiểm soát đó lấy memory safety và developer productivity. Generations giúp collector không phải scan toàn bộ heap cho mọi allocation burst.

Nhưng server có throughput cao vẫn phải trả CPU cho allocation và collection. Nếu object sống đủ lâu để bị promote hoặc buffer lớn liên tục đi vào LOH, pause time và memory footprint có thể tăng đáng kể.

## 3. How does it work?

```text
allocate -> Gen 0
          -> survives collection -> Gen 1
          -> survives again      -> Gen 2

large allocation -> LOH
```

GC xác định root từ stack, static fields, handles và runtime structures, rồi traverse object graph. Object không reachable được thu hồi. Small-object generations thường được compact; LOH có đặc điểm compaction khác và allocation lớn làm áp lực memory nhanh hơn.

Server GC tối ưu throughput cho server workload nhưng không biến allocation thành miễn phí.

## 4. Practical implementation

Đừng pool mọi thứ trước khi đo. Bắt đầu bằng giảm allocation vô ích:

```csharp
public static int CountErrors(ReadOnlySpan<char> payload)
{
    var count = 0;

    foreach (var line in payload.EnumerateLines())
    {
        if (line.Contains("ERROR", StringComparison.Ordinal))
            count++;
    }

    return count;
}
```

Với hot path cần buffer lớn, có thể cân nhắc `ArrayPool<byte>`, nhưng phải `Return` trong `finally` và kiểm soát dữ liệu nhạy cảm.

Để điều tra, dùng `dotnet-counters`, `dotnet-gcdump` hoặc profiler và quan sát allocation rate, GC heap size, Gen 2 collections, LOH size.

## 5. Real production scenario

API export tạo JSON/CSV cho hàng nghìn records. Implementation ban đầu build nhiều `string` lớn trong memory trước khi ghi response. Traffic tăng làm allocation rate bùng lên; object lớn vào LOH, Gen 2 collection tăng, p99 latency xấu dù database không chậm.

Giải pháp có thể là streaming, projection dữ liệu vừa đủ và giảm intermediate buffers thay vì “tăng RAM”.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng theo traffic, latency có spike.

**Evidence** → allocation rate cao, Gen 2/LOH tăng, CPU dành nhiều thời gian cho GC.

**Hypothesis** → endpoint export/serialization tạo object graph lớn.

**Diagnosis** → allocation profile chỉ ra `byte[]`, `string`, DTO lớn chiếm phần lớn bytes.

**Fix** → stream output, tránh materialize toàn bộ dataset, giảm copy, pool buffer khi profiling chứng minh có lợi.

**Verification** → load test lại và so allocation/sec, GC pause, p95/p99, working set.

## 7. Common mistakes

- Chỉ nhìn working set rồi kết luận memory leak.
- Gọi `GC.Collect()` để “fix” memory.
- Dùng `ArrayPool<T>` khắp nơi dù allocation chưa phải bottleneck.
- Giữ cache/static references vô hạn rồi đổ lỗi cho GC.
- Tối ưu allocation nhỏ trong cold path nhưng bỏ qua một response 20 MB.

## 8. Alternatives

Giảm object lifetime, streaming, chunking và thay đổi data access thường đơn giản hơn pooling. `Span<T>` hữu ích cho slicing/parsing synchronous; `Memory<T>` phù hợp hơn khi dữ liệu phải sống qua async boundary.

## 9. Trade-offs

### Advantages

GC tăng memory safety và giảm complexity của ownership thủ công. Pooling/zero-copy có thể giảm allocation trên hot path.

### Costs / Risks

Pooling làm ownership phức tạp; `Span<T>` tăng constraints; streaming thay đổi error boundary vì response có thể đã bắt đầu. Tối ưu memory quá sớm dễ làm code khó bảo trì.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu managed memory không đồng nghĩa memory “miễn phí”; biết Gen 0/1/2 và object phải hết reachable mới được collect.

### Middle

Đọc basic GC metrics, tránh allocation rõ ràng và biết khi nào streaming hợp lý.

### Senior

Liên hệ allocation rate, promotion, LOH, pause time và tail latency; profile trước khi tối ưu.

### Technical Lead / Architect

Quyết định memory budget, response-size limits, streaming boundary và khi nào complexity như pooling thực sự đáng giá.

## 11. Key takeaway

- GC quản lý lifetime, nhưng application quyết định allocation pressure.
- Production memory investigation cần metrics + allocation profile, không đoán.
- Giảm materialization thường giá trị hơn micro-optimization.

# 2. ASP.NET Core CancellationToken: propagation từ HTTP request đến database và external API

## 1. What is it?

`CancellationToken` là cooperative cancellation contract. Nó không “kill thread”; caller phát tín hiệu rằng kết quả không còn cần thiết, còn callee phải chủ động quan sát token và dừng ở safe point.

Trong ASP.NET Core, `HttpContext.RequestAborted` biểu diễn việc request bị hủy, ví dụ client disconnect.

## 2. Why does it exist?

Nếu client đóng request sau 200 ms nhưng backend vẫn chạy SQL 10 giây, gọi external API rồi serialize response không ai nhận, hệ thống lãng phí connection, CPU và dependency capacity. Khi load cao, abandoned work có thể góp phần gây pool exhaustion.

## 3. How does it work?

```text
Client disconnect
   -> RequestAborted cancelled
   -> endpoint receives token
   -> application service propagates token
   -> EF Core / HttpClient observes token
   -> operation stops cooperatively
```

Cancellation khác timeout. Timeout là policy về thời gian; cancellation là signal. Hai nguồn có thể được liên kết bằng `CancellationTokenSource.CreateLinkedTokenSource`.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:int}", async (
    int id,
    AppDbContext db,
    IHttpClientFactory httpClientFactory,
    CancellationToken ct) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new { x.Id, x.Status, x.Total })
        .SingleOrDefaultAsync(ct);

    if (order is null)
        return Results.NotFound();

    var client = httpClientFactory.CreateClient("risk");
    using var response = await client.GetAsync(
        $"/risk/orders/{id}",
        HttpCompletionOption.ResponseHeadersRead,
        ct);

    return Results.Ok(order);
});
```

## 5. Real production scenario

User mở product page rồi nhanh chóng chuyển route. Browser hủy request cũ. Nếu API propagate cancellation xuống SQL/search service, backend có thể giải phóng work sớm thay vì hoàn tất một query/search đã vô nghĩa.

## 6. Failure scenario & troubleshooting

**Symptom** → request timeout/client disconnect cao, nhưng dependency load vẫn tiếp tục tăng.

**Evidence** → traces cho thấy server spans kéo dài sau khi parent request đã kết thúc.

**Hypothesis** → token bị bỏ mất ở application/repository layer.

**Diagnosis** → tìm async calls không nhận `CancellationToken`.

**Fix** → propagate token xuyên boundary; phân biệt cancellation với genuine failure trong logging.

**Verification** → hủy request trong load test và xác nhận downstream operations kết thúc sớm.

## 7. Common mistakes

- Tạo `new CancellationToken()` ở layer dưới thay vì truyền token vào.
- Catch `OperationCanceledException` rồi log Error cho mọi cancellation bình thường.
- Dùng cancellation để rollback arbitrary in-memory state mà không thiết kế consistency.
- Không truyền token vào EF Core, `HttpClient`, queue operations.
- Nhầm request cancellation với server timeout policy.

## 8. Alternatives

Timeout policy vẫn cần cho dependency không đáng tin cậy. Server-side deadline có thể tồn tại ngay cả khi client không disconnect. Cancellation và timeout bổ sung nhau, không thay thế nhau.

## 9. Trade-offs

### Advantages

Giảm wasted work và giúp graceful shutdown/deadline propagation.

### Costs / Risks

Cancellation làm control flow phức tạp hơn; dừng giữa side effects có thể để trạng thái partial nếu transaction boundary sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cancellation là cooperative signal.

### Middle

Propagate token qua async call chain và test cancellation.

### Senior

Phân biệt cancellation, timeout, retry và partial side effects.

### Technical Lead / Architect

Định nghĩa deadline budget xuyên service và boundary nào được phép cancel sau khi side effect đã commit.

## 11. Key takeaway

- Token chỉ hữu ích khi được propagate.
- Cancellation không thay transaction design.
- Hủy abandoned work là một phần của capacity management.

# 3. EF Core projection: kiểm soát SQL, allocation và query boundary bằng `Select`

## 1. What is it?

Projection dùng `Select` để mô tả đúng shape dữ liệu cần lấy thay vì materialize cả entity graph. Với EF Core, expression trong `IQueryable` được dịch thành SQL nếu provider hỗ trợ.

Mental model: query shape ở C# ảnh hưởng trực tiếp đến columns, joins, materialization và tracking cost.

## 2. Why does it exist?

API list thường chỉ cần 5 fields nhưng entity có 30 columns và navigation properties. Load entity đầy đủ làm tăng network I/O, materialization, memory và nguy cơ accidental tracking. DTO projection đặt read contract gần query.

## 3. How does it work?

```text
IQueryable expression tree
   -> EF Core translation
   -> parameterized SQL
   -> database execution plan
   -> selected columns returned
   -> DTO materialization
```

Query chưa chạy khi chỉ compose `IQueryable`; execution thường xảy ra ở `ToListAsync`, `SingleAsync`, enumeration...

## 4. Practical implementation

```csharp
var page = await db.Products
    .AsNoTracking()
    .Where(p => p.IsActive && p.CategoryId == categoryId)
    .OrderBy(p => p.Id)
    .Select(p => new ProductListItem(
        p.Id,
        p.Name,
        p.Price,
        p.Category.Name))
    .Take(50)
    .ToListAsync(ct);
```

Kiểm tra SQL bằng logging hoặc `ToQueryString()` trong investigation.

## 5. Real production scenario

Product listing bị chậm vì endpoint dùng `Include` nhiều navigation rồi map entity sang DTO sau khi query xong. Projection loại các columns/relationships không cần thiết và giúp database trả đúng read model.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint list có payload nhỏ nhưng SQL/network bytes và allocation lớn.

**Evidence** → trace cho thấy query trả nhiều columns; heap profile có nhiều entity objects.

**Hypothesis** → materialize entity graph quá mức.

**Diagnosis** → xem generated SQL và query shape.

**Fix** → projection trực tiếp, pagination và chỉ load fields cần thiết.

**Verification** → so logical reads, duration, rows/bytes và allocation.

## 7. Common mistakes

- Gọi `ToListAsync` rồi mới `Select`, khiến projection chạy in-memory.
- Dùng `Include` cho read model chỉ cần vài fields.
- Trả EF entities trực tiếp ra API.
- Tin rằng `AsNoTracking` tự động giảm số columns.
- Tạo abstraction repository trả `IEnumerable<T>` làm mất khả năng compose SQL.

## 8. Alternatives

Entity materialization phù hợp khi cần update và domain behavior. Raw SQL/Dapper có thể hữu ích cho read path cực kỳ specialized, nhưng đổi lấy abstraction khác và mapping ownership.

## 9. Trade-offs

### Advantages

Ít I/O, allocation và coupling giữa persistence entity với API contract.

### Costs / Risks

Projection lớn có thể lặp mapping; query expression phức tạp có thể khó đọc hoặc không dịch được.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết `Select` có thể chạy ở database khi còn trong `IQueryable`.

### Middle

Thiết kế DTO projection và kiểm tra generated SQL.

### Senior

Đánh giá query shape bằng plan/I/O thay vì chỉ nhìn LINQ.

### Technical Lead / Architect

Chọn boundary giữa domain entity và read model; tránh generic abstraction làm che mất query semantics.

## 11. Key takeaway

- Read path nên lấy đúng dữ liệu cần dùng.
- `AsNoTracking` và projection giải quyết hai vấn đề khác nhau.
- Generated SQL là bằng chứng, LINQ chỉ là input.

# 4. SQL Server statistics và execution-plan regression: vì sao cùng một query hôm nay bỗng chậm

## 1. What is it?

Statistics mô tả distribution của dữ liệu để SQL Server cardinality estimator ước lượng số rows. Optimizer dùng ước lượng đó để chọn execution plan: join algorithm, index access, memory grant và nhiều quyết định khác.

Plan regression xảy ra khi optimizer chọn plan mới tệ hơn cho workload thực tế, dù query text không đổi.

## 2. Why does it exist?

Database không thể thử mọi plan khi mỗi query chạy; optimizer phải ước lượng. Khi distribution thay đổi, statistics cũ hoặc parameter-sensitive workload có thể làm estimate lệch mạnh.

## 3. How does it work?

```text
SQL + parameters
 -> statistics/cardinality estimate
 -> optimizer cost model
 -> execution plan
 -> I/O + CPU + locks + memory grant
 -> latency
```

Một estimate 100 rows nhưng actual 2,000,000 rows có thể khiến nested loops hợp lý trên giấy nhưng cực tệ trong thực tế.

## 4. Practical implementation

Investigation:

```sql
SELECT p.Id, p.CustomerId, p.CreatedAt
FROM dbo.Orders AS p
WHERE p.CustomerId = @CustomerId
  AND p.CreatedAt >= @FromDate
ORDER BY p.CreatedAt DESC;
```

Đừng bắt đầu bằng thêm index. Capture actual execution plan, so Estimated Rows với Actual Rows, xem logical reads, spills và plan history trong Query Store.

## 5. Real production scenario

Sau data import lớn, API order history từ 120 ms lên 8 giây. CPU database tăng nhưng application code không deploy. Query Store cho thấy plan mới dùng scan và memory grant khác hẳn plan trước.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 SQL tăng đột ngột sau data growth/deployment không liên quan.

**Evidence** → Query Store có plan change; actual vs estimated rows lệch lớn.

**Hypothesis** → stale statistics hoặc parameter-sensitive plan.

**Diagnosis** → kiểm tra statistics freshness, parameter distribution, execution plan và logical reads.

**Fix** → update statistics khi phù hợp, sửa query/index/data model; dùng plan forcing chỉ như biện pháp có kiểm soát, không che root cause lâu dài.

**Verification** → test representative parameter sets và theo dõi plan/latency sau fix.

## 7. Common mistakes

- “Query chậm = thiếu index”.
- Chỉ test một parameter.
- Clear toàn bộ plan cache trong Production.
- Dùng `OPTION (RECOMPILE)` mặc định mà không cân CPU compile.
- Không lưu baseline bằng Query Store.

## 8. Alternatives

Query rewrite, index redesign, filtered index, pre-aggregation hoặc tách workload có thể phù hợp hơn. PostgreSQL có planner/statistics khác nhưng mental model estimate → plan → runtime vẫn hữu ích.

## 9. Trade-offs

### Advantages

Statistics cho optimizer khả năng thích nghi với data distribution.

### Costs / Risks

Estimate luôn là approximation; plan tốt cho parameter này có thể xấu cho parameter khác.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu execution plan là cách database thực thi query.

### Middle

Đọc scan/seek, joins, estimated/actual rows và logical reads.

### Senior

Điều tra plan regression, statistics và parameter sensitivity bằng evidence.

### Technical Lead / Architect

Thiết kế observability/database change process để plan regression được phát hiện và rollback/mitigate an toàn.

## 11. Key takeaway

- Query text không đổi không đảm bảo execution plan không đổi.
- Estimate sai có thể kéo theo hàng loạt quyết định plan sai.
- Query Store + actual plan + I/O tốt hơn đoán bằng index.

# 5. MongoDB document modeling: embedding vs referencing theo access pattern

## 1. What is it?

MongoDB model dữ liệu quanh document. Quyết định quan trọng không phải “NoSQL không schema”, mà là dữ liệu nào nên nằm cùng document và dữ liệu nào nên được reference.

Embedding đặt dữ liệu liên quan cùng aggregate-like document; referencing lưu identifier và đọc dữ liệu liên quan qua query khác hoặc aggregation.

## 2. Why does it exist?

Relational modeling tối ưu integrity và composition qua joins. Document database ưu tiên locality theo access pattern. Nếu dữ liệu luôn được đọc/ghi cùng nhau, embedding có thể giảm round trips. Nhưng document quá lớn hoặc child có lifecycle độc lập sẽ làm coupling và write amplification tăng.

## 3. How does it work?

```text
Embedding:
Order { id, customerSnapshot, items[] }

Referencing:
Order { id, customerId }
Customer { id, ... }
```

MongoDB atomicity tự nhiên mạnh ở single-document update. Vì vậy document boundary ảnh hưởng cả consistency lẫn scalability.

## 4. Practical implementation

C# model:

```csharp
public sealed class OrderDocument
{
    public ObjectId Id { get; init; }
    public string CustomerId { get; init; } = "";
    public List<OrderItemDocument> Items { get; init; } = [];
    public decimal Total { get; init; }
}

public sealed record OrderItemDocument(
    string Sku,
    string NameSnapshot,
    int Quantity,
    decimal UnitPrice);
```

Tên/giá snapshot trong order có thể cố ý được embed để lịch sử order không thay đổi khi product catalog đổi.

## 5. Real production scenario

E-commerce order cần hiển thị đúng product name/price tại thời điểm mua. Reference trực tiếp product hiện tại có thể làm historical invoice thay đổi. Embedding snapshot phù hợp hơn cho dữ liệu lịch sử này.

## 6. Failure scenario & troubleshooting

**Symptom** → document update chậm, document size tăng liên tục.

**Evidence** → một parent chứa unbounded child array; write size và network payload tăng.

**Hypothesis** → embedding được dùng cho relationship có cardinality không giới hạn.

**Diagnosis** → xem document size distribution và access pattern thực tế.

**Fix** → tách child collection/reference hoặc bucket dữ liệu.

**Verification** → đo query count, document size, write latency và consistency behavior.

## 7. Common mistakes

- Chuyển schema SQL sang MongoDB 1:1 rồi gọi đó là document modeling.
- Embed unbounded collections.
- Reference mọi thứ và tạo application-side N+1.
- Tin “schema flexible” nghĩa là không cần schema governance.
- Chọn partition/shard key sau khi hệ thống đã scale.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp hơn khi relational constraints, joins và multi-row transaction là trung tâm. Cosmos DB cũng là document-oriented nhưng partition key, RU và consistency model làm design pressure khác.

## 9. Trade-offs

### Advantages

Embedding tăng locality, giảm round trips và đơn giản hóa atomic update trong document.

### Costs / Risks

Duplicate data, document growth, write amplification và synchronization responsibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu document là modeling boundary, không chỉ JSON thay cho row.

### Middle

Model embedding/reference theo read/write pattern.

### Senior

Đánh giá cardinality, document growth, consistency và indexing.

### Technical Lead / Architect

Quyết định liệu document database có thực sự phù hợp và ownership/synchronization của duplicated data.

## 11. Key takeaway

- MongoDB schema nên bắt đầu từ access pattern.
- Embedding đổi duplication lấy locality.
- Unbounded growth là dấu hiệu boundary cần xem lại.

# 6. Azure App Service deployment slots: zero-downtime deployment, warm-up và rollback

## 1. What is it?

Deployment slot là live environment riêng trong cùng App Service app, ví dụ `staging` và `production`. Code mới được deploy vào staging, warm-up/validate, sau đó swap routing/configuration theo slot semantics.

Mental model: slot giảm risk của application deployment; nó không tự giải quyết database compatibility.

## 2. Why does it exist?

Deploy trực tiếp lên production có thể tạo cold start, partial rollout và rollback chậm. Slot cho phép chuẩn bị version mới trước khi traffic production chuyển sang.

## 3. How does it work?

```text
Build artifact
   -> deploy staging slot
   -> warm-up + health validation
   -> swap
Production traffic -> warmed new version

rollback -> swap back when safe
```

Một số settings có thể được đánh dấu slot-specific. Managed Identity, networking, configuration và dependencies phải được hiểu rõ trước swap.

## 4. Practical implementation

ASP.NET Core health endpoints:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(builder.Configuration.GetConnectionString("Sql")!);

app.MapHealthChecks("/health/ready");
app.MapGet("/health/live", () => Results.Ok());
```

Readiness nên kiểm tra những dependency thực sự cần để nhận traffic, nhưng tránh biến một optional dependency thành nguyên nhân kéo toàn app khỏi rotation.

## 5. Real production scenario

Release checkout API deploy staging, warm JIT/cache, chạy smoke test rồi swap. Version mới bắt đầu nhận traffic mà không phải chờ process cold-start trên production.

## 6. Failure scenario & troubleshooting

**Symptom** → swap thành công nhưng request 500 ngay sau release.

**Evidence** → application logs báo column mới không tồn tại hoặc config slot sai.

**Hypothesis** → application version và database schema không backward-compatible.

**Diagnosis** → đối chiếu migration timeline, slot settings và dependency configuration.

**Fix** → dùng Expand–Migrate–Contract cho schema; validate slot-specific settings; rollback application chỉ khi old version vẫn tương thích schema.

**Verification** → health + smoke + business transaction test và telemetry sau swap.

## 7. Common mistakes

- Xem slot swap như rollback guarantee tuyệt đối.
- Chạy destructive migration trước khi old version ngừng tồn tại.
- Đưa secrets vào source/config file thay vì Key Vault/Managed Identity.
- Health check quá sâu làm optional dependency gây outage.
- Không warm-up endpoint thực tế.

## 8. Alternatives

Blue-Green trên Container Apps/Kubernetes cho control rộng hơn nhưng operational complexity cao hơn. Rolling deployment đơn giản ở một số platform nhưng rollback/cold-start semantics khác.

## 9. Trade-offs

### Advantages

Nhanh, phù hợp App Service, hỗ trợ pre-production validation và rollback application.

### Costs / Risks

Tăng configuration complexity; database/external side effects vẫn cần compatibility strategy; slot capacity có cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu staging slot là running deployment riêng.

### Middle

Deploy, health-check và swap an toàn.

### Senior

Thiết kế backward-compatible configuration/schema và quan sát post-deploy.

### Technical Lead / Architect

Chọn release strategy dựa trên blast radius, rollback requirement, database migration và team operational maturity.

## 11. Key takeaway

- Slot giải quyết traffic cutover tốt hơn database evolution.
- Rollback chỉ an toàn nếu contracts còn backward-compatible.
- Health validation phải phản ánh khả năng phục vụ traffic.

# 7. DDD Aggregate: đặt transaction boundary quanh business invariant, không quanh bảng

## 1. What is it?

Aggregate là cluster của domain objects được thay đổi như một consistency boundary. Aggregate Root là entry point kiểm soát invariants bên trong boundary.

Ví dụ `Order` có thể là Aggregate Root, `OrderLine` là entity bên trong. Caller không tùy ý sửa `OrderLine` ngoài các operation của `Order`.

## 2. Why does it exist?

Nếu mọi entity được update độc lập, business invariant dễ bị phá. Ví dụ order đã `Paid` không được thêm item. Aggregate gom những thay đổi cần strongly consistent trong một transaction.

DDD không yêu cầu mọi relation trong database nằm chung aggregate.

## 3. How does it work?

```text
Application Service
      |
      v
 Order Aggregate Root
   | enforce invariants
   v
OrderLines
      |
      v
single transaction boundary
```

Cross-aggregate coordination thường nên dùng identity/reference và eventual consistency khi business cho phép.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public OrderStatus Status { get; private set; }
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void AddItem(string sku, int quantity, decimal unitPrice)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Only draft orders can change.");

        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(nameof(quantity));

        _lines.Add(new OrderLine(sku, quantity, unitPrice));
    }
}
```

Application service chịu trách nhiệm orchestration; invariant nằm trong domain object.

## 5. Real production scenario

Approval workflow: một Timesheet chỉ được submit khi có entries và chưa locked. Aggregate boundary giúp đảm bảo hai rule được kiểm tra cùng state trước khi commit.

## 6. Failure scenario & troubleshooting

**Symptom** → transaction thường xuyên lock nhiều rows/tables, aggregate load cực lớn.

**Evidence** → command cần load graph hàng nghìn children.

**Hypothesis** → aggregate boundary được vẽ theo object graph/database relationship thay vì consistency requirement.

**Diagnosis** → hỏi invariant nào thực sự phải atomic.

**Fix** → thu nhỏ aggregate; chuyển cross-boundary workflow sang domain event/application orchestration khi phù hợp.

**Verification** → invariant tests + concurrency tests + transaction/lock metrics.

## 7. Common mistakes

- Aggregate = bảng có foreign key.
- Aggregate = toàn bộ graph có thể navigate.
- Repository cho mọi entity con.
- Đưa mọi validation vào aggregate dù cần external I/O.
- Dùng MediatR rồi gọi đó là DDD.

## 8. Alternatives

Anemic CRUD model đủ tốt cho domain đơn giản. Application-service validation có thể phù hợp khi business rules mỏng. DDD có giá trị khi business invariants và change complexity thực sự đáng kể.

## 9. Trade-offs

### Advantages

Invariant có owner rõ ràng; transaction boundary thể hiện business consistency.

### Costs / Risks

Modeling khó hơn CRUD; aggregate quá lớn làm contention, aggregate quá nhỏ làm consistency/orchestration phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt Entity, Aggregate và Aggregate Root.

### Middle

Implement invariant và persistence của aggregate.

### Senior

Thiết kế boundary theo consistency, concurrency và lifecycle.

### Technical Lead / Architect

Quyết định nơi cần strong consistency, nơi eventual consistency chấp nhận được, và liệu DDD có đáng complexity hay không.

## 11. Key takeaway

- Aggregate là consistency boundary, không phải folder hay table group.
- Invariant quyết định boundary.
- Domain đơn giản không cần ép DDD.

# 8. ASP.NET Core BackgroundService trên nhiều instance: duplicate execution và ownership của scheduled work

## 1. What is it?

`BackgroundService` chạy cùng host process của ASP.NET Core/Worker Service. Khi application scale thành N instances, mặc định sẽ có N copies của background loop.

Mental model: in-process scheduler có process ownership, không có cluster-wide singleton semantics.

## 2. Why does it exist?

BackgroundService tiện cho queue consumer, housekeeping và long-running worker. Nhưng assumption “job chạy một lần” chỉ đúng khi có đúng một process hoặc có coordination bên ngoài.

## 3. How does it work?

```text
App Service instance A -> BackgroundService -> job
App Service instance B -> BackgroundService -> same job
App Service instance C -> BackgroundService -> same job
```

Scale-out biến local timer thành distributed execution problem. Bạn phải chọn: duplicate-safe execution, distributed coordination, hoặc chuyển scheduling sang platform có ownership rõ hơn.

## 4. Practical implementation

Queue consumer thường tốt hơn timer quét việc:

```csharp
public sealed class InvoiceWorker(
    Channel<InvoiceJob> jobs,
    ILogger<InvoiceWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in jobs.Reader.ReadAllAsync(stoppingToken))
        {
            try
            {
                await ProcessAsync(job, stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                break;
            }
        }
    }

    private Task ProcessAsync(InvoiceJob job, CancellationToken ct)
        => Task.CompletedTask;
}
```

Trong distributed production, thay in-memory Channel bằng durable queue nếu work không được phép mất khi process restart.

## 5. Real production scenario

Một App Service có timer mỗi giờ gửi reminder. Scale từ 1 lên 4 instances làm user nhận 4 email. Code “đúng” ở local nhưng ownership model sai ở production.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng business action xuất hiện nhiều lần gần cùng timestamp.

**Evidence** → logs có cùng job key nhưng khác instance ID.

**Hypothesis** → scheduled loop chạy trên mọi replica.

**Diagnosis** → kiểm tra hosting topology và deployment scale.

**Fix** → làm operation idempotent; dùng durable queue/scheduler, distributed lock có semantics rõ ràng hoặc một dedicated worker tùy requirement.

**Verification** → scale nhiều replicas trong test và xác nhận business effect chỉ xảy ra theo contract.

## 7. Common mistakes

- Tin `BackgroundService` chỉ chạy một lần cho cả cluster.
- Dùng Redis lock nhưng không hiểu lease expiry/fencing.
- Không propagate `stoppingToken`.
- Giữ critical work chỉ trong in-memory queue.
- Retry side effect không idempotent.

## 8. Alternatives

Azure Functions Timer Trigger, Service Bus queue + competing consumers, dedicated Worker Service hoặc external scheduler. Nếu duplicate có thể xảy ra, idempotency vẫn nên được thiết kế ở business boundary.

## 9. Trade-offs

### Advantages

BackgroundService đơn giản, cùng codebase, DI/config/observability quen thuộc.

### Costs / Risks

Lifecycle gắn với web host; scale-out, restart và deployment ảnh hưởng work; cluster coordination là trách nhiệm của hệ thống.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hosted service sống cùng process.

### Middle

Implement cancellation, exception handling và graceful shutdown.

### Senior

Thiết kế idempotency, durability và multi-instance behavior.

### Technical Lead / Architect

Quyết định ownership: web process, dedicated worker, queue hay managed scheduler; đánh giá operational burden của distributed lock.

## 11. Key takeaway

- Scale-out biến timer local thành distributed-systems problem.
- Idempotency thường quan trọng hơn cố tạo “exactly once”.
- Critical work cần durable ownership.

# 9. TypeScript/JavaScript event loop: microtask, rendering và race condition trong frontend

## 1. What is it?

JavaScript trên browser thường chạy application code trên một main thread với event loop. Async I/O không có nghĩa callback chạy song song với JS hiện tại; completion được xếp lịch để event loop xử lý.

Promise continuations chạy qua microtask queue, trong khi timers/events thuộc task scheduling khác. Rendering phải chia sẻ main thread với JavaScript work.

## 2. Why does it exist?

Browser phải phối hợp input, network callbacks, timers và rendering mà không cho nhiều đoạn JS tùy ý mutate DOM cùng lúc. Event loop tạo execution model có thứ tự, nhưng long synchronous work vẫn block UI.

## 3. How does it work?

```text
task -> JavaScript stack
     -> microtasks drained
     -> rendering opportunity
     -> next task
```

Một Promise resolved không “interrupt” code đang chạy. Callback chỉ chạy khi stack hiện tại hoàn tất.

## 4. Practical implementation

Race khi user đổi search nhanh:

```typescript
let requestVersion = 0;

async function search(query: string) {
  const version = ++requestVersion;

  const response = await fetch(
    `/api/search?q=${encodeURIComponent(query)}`
  );
  const data = await response.json();

  if (version !== requestVersion) return;
  renderResults(data);
}
```

Tốt hơn nữa, có thể dùng `AbortController` để cancel request cũ nếu semantics phù hợp.

## 5. Real production scenario

User gõ “car”, rồi “cargo”. Request “cargo” trả trước và UI render đúng; request “car” chậm hơn trả sau rồi overwrite state bằng kết quả cũ. Đây là race về logical ordering, dù JavaScript callback không chạy đồng thời.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị data cũ hoặc spinner không tắt đúng.

**Evidence** → Network panel cho thấy responses về khác thứ tự gửi.

**Hypothesis** → component không quản lý request identity/cancellation.

**Diagnosis** → trace state transitions và request timestamps.

**Fix** → AbortController, request version, framework query library hoặc state machine phù hợp.

**Verification** → throttle network trong DevTools và tái tạo out-of-order responses.

## 7. Common mistakes

- Nghĩ `await` khóa toàn browser.
- Dùng `setTimeout(..., 0)` như guarantee “chạy ngay”.
- Không cancel/ignore stale response.
- Chạy CPU-heavy loop trên main thread.
- Debug chỉ bằng console log mà không xem Network/Performance timeline.

## 8. Alternatives

Web Worker phù hợp CPU-heavy work cần off-main-thread. Vue/React query libraries có thể quản lý caching/cancellation nhưng không loại nhu cầu hiểu ordering semantics.

## 9. Trade-offs

### Advantages

Single-threaded mutation model giảm một lớp data race truyền thống.

### Costs / Risks

Main-thread blocking làm UI freeze; async ordering tạo race logic khó tái hiện.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu call stack, Promise và event loop cơ bản.

### Middle

Xử lý loading/error/cancellation và stale response.

### Senior

Dùng Performance/Network evidence để phân biệt backend latency với main-thread/rendering bottleneck.

### Technical Lead / Architect

Chọn state/data-fetching abstraction và API semantics sao cho cancellation, caching và consistency dễ quản lý.

## 11. Key takeaway

- Async completion không đồng nghĩa parallel JS execution.
- Out-of-order responses vẫn tạo race condition.
- DevTools timeline là bằng chứng quan trọng.

# 10. Contract testing: bảo vệ API compatibility mà không biến E2E thành nút thắt

## 1. What is it?

Contract testing xác minh producer và consumer đồng ý về interface quan trọng: HTTP method/path, request/response schema, status/error semantics hoặc message schema.

Nó nằm giữa unit test và full E2E: tập trung vào boundary giữa components thay vì chạy toàn hệ thống.

## 2. Why does it exist?

Unit tests có thể xanh ở cả hai service nhưng integration vẫn vỡ vì field đổi tên, enum thay đổi hoặc status code đổi. E2E phát hiện được nhưng thường chậm, flaky và khó localize root cause.

## 3. How does it work?

```text
Consumer expectation
      |
      v
 versioned contract
      |
      v
Producer verification
```

Contract có thể dựa trên OpenAPI/schema hoặc consumer-driven contract. Quan trọng là test compatibility thực sự, không chỉ snapshot một JSON bất kỳ.

## 4. Practical implementation

ASP.NET Core integration test có thể khóa một public contract quan trọng:

```csharp
[Fact]
public async Task GetOrder_ReturnsStablePublicShape()
{
    using var client = _factory.CreateClient();

    var response = await client.GetAsync("/api/orders/123");
    response.EnsureSuccessStatusCode();

    var json = await response.Content.ReadFromJsonAsync<JsonElement>();

    Assert.True(json.TryGetProperty("id", out _));
    Assert.True(json.TryGetProperty("status", out _));
    Assert.True(json.TryGetProperty("total", out _));
}
```

Với contract nghiêm túc, validate OpenAPI/schema và compatibility rules trong CI thay vì chỉ assert vài fields.

## 5. Real production scenario

Frontend mobile version cũ vẫn dùng `status: "Pending"`. Backend đổi enum thành `"AwaitingApproval"` mà không versioning. Backend unit tests xanh, nhưng app cũ vỡ. Contract/compatibility gate có thể phát hiện breaking change trước deploy.

## 6. Failure scenario & troubleshooting

**Symptom** → producer deploy thành công nhưng một consumer bắt đầu parse error.

**Evidence** → traces/logs cho thấy response 200 nhưng deserialization fail ở consumer.

**Hypothesis** → breaking contract change.

**Diagnosis** → diff OpenAPI/schema, kiểm tra consumer version và release timeline.

**Fix** → restore backward compatibility, version contract hoặc additive migration.

**Verification** → chạy producer verification với supported consumer contracts và smoke test representative clients.

## 7. Common mistakes

- Contract test duplicate toàn bộ E2E flow.
- Chỉ snapshot response rồi accept diff máy móc.
- Không version contract/message schema.
- Mock producer trong consumer test theo assumption sai.
- Tin OpenAPI generation tự động đồng nghĩa compatibility được bảo vệ.

## 8. Alternatives

Integration tests với real API/database kiểm tra behavior rộng hơn. E2E kiểm tra critical user journey. Schema diff trong CI đơn giản hơn consumer-driven contracts khi ownership tập trung. Không cần thêm contract-testing platform nếu một monolith có boundary đơn giản và cùng release train.

## 9. Trade-offs

### Advantages

Phát hiện breaking changes sớm, nhanh hơn E2E và localize lỗi boundary tốt.

### Costs / Risks

Contract governance, versioning và CI integration tạo maintenance cost; quá nhiều contract nhỏ có thể làm thay đổi hợp lệ trở nên nặng nề.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu API contract không chỉ là JSON example mà là promise giữa producer và consumer.

### Middle

Viết integration/contract assertions cho boundary quan trọng.

### Senior

Phân biệt unit, integration, contract và E2E theo loại risk cần bảo vệ.

### Technical Lead / Architect

Quyết định consumer support window, compatibility policy, versioning và mức tooling phù hợp; không thêm platform khi team chưa có vấn đề cần giải quyết.

## 11. Key takeaway

- Contract tests bảo vệ compatibility boundary, không thay mọi integration/E2E test.
- Breaking change là release-management problem, không chỉ code problem.
- Chọn test theo risk, không theo mục tiêu coverage.
