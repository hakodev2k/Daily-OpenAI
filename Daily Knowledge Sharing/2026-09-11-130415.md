# 1. C# `IAsyncEnumerable<T>`: stream dữ liệu theo từng phần mà không buffer toàn bộ kết quả vào memory

## 1. What is it?

`IAsyncEnumerable<T>` là abstraction cho một sequence mà phần tử được tạo hoặc lấy về theo thời gian và mỗi bước lấy phần tử có thể cần asynchronous I/O.

Mental model:

```text
List<T>
-> load toàn bộ
-> caller nhận collection hoàn chỉnh

IAsyncEnumerable<T>
-> producer tạo từng item
-> caller await từng item
-> không bắt buộc giữ toàn bộ sequence trong memory
```

Điểm quan trọng không phải chỉ là cú pháp `await foreach`, mà là thay đổi **data-flow boundary**: consumer có thể xử lý item ngay khi producer tạo ra thay vì chờ toàn bộ dataset hoàn tất.

## 2. Why does it exist?

Nếu API phải đọc 500.000 records rồi convert tất cả thành `List<T>`, application có thể:

- tăng allocation mạnh;
- đẩy nhiều object lên Gen 2;
- tăng GC pressure;
- giữ database/network resources lâu hơn;
- tăng time-to-first-byte.

Trong nhiều workflow, consumer không cần toàn bộ dataset cùng lúc. Streaming cho phép xử lý theo pipeline.

## 3. How does it work?

Compiler chuyển async iterator thành state machine. Mỗi lần consumer gọi `MoveNextAsync()`, producer chạy tới `yield return` tiếp theo hoặc chờ asynchronous operation.

Flow:

```text
Consumer
  -> MoveNextAsync()
  -> producer đọc item tiếp theo
  -> await I/O nếu cần
  -> yield return item
  -> consumer xử lý
  -> lặp lại
```

Khác với `Task<List<T>>`, task chỉ hoàn tất khi toàn bộ list sẵn sàng. `IAsyncEnumerable<T>` cho phép completion theo từng phần tử.

## 4. Practical implementation

Ví dụ đọc dữ liệu từ EF Core:

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    DateTimeOffset from,
    [EnumeratorCancellation] CancellationToken cancellationToken = default)
{
    await foreach (var order in _db.Orders
        .AsNoTracking()
        .Where(x => x.CreatedAt >= from)
        .OrderBy(x => x.Id)
        .Select(x => new OrderDto(x.Id, x.Total))
        .AsAsyncEnumerable()
        .WithCancellation(cancellationToken))
    {
        yield return order;
    }
}
```

Consumer:

```csharp
await foreach (var order in service.StreamOrdersAsync(from, ct))
{
    await writer.WriteLineAsync(JsonSerializer.Serialize(order));
}
```

Điểm cần lưu ý: streaming từ EF Core thường giữ query/connection hoạt động trong suốt enumeration. Đó là trade-off vận hành thực tế.

## 5. Real production scenario

Một reporting API export hàng trăm nghìn transaction sang NDJSON. Phiên bản đầu gọi `ToListAsync()`, serialize toàn bộ list rồi mới trả response. Dưới tải cao, memory tăng mạnh và nhiều request export chạy đồng thời làm instance bị recycle.

Chuyển sang streaming giúp:

```text
SQL row
-> EF projection
-> serialize
-> response stream
```

Application không cần giữ toàn bộ report trong memory.

## 6. Failure scenario & troubleshooting

**Symptom** → memory thấp hơn sau khi chuyển sang streaming nhưng database connection pool lại cạn.

**Evidence** → request export kéo dài vài phút; active DB connections giữ lâu; các request khác timeout khi lấy connection.

**Hypothesis** → streaming giữ connection suốt lifetime của HTTP response.

**Diagnosis** → trace request duration, connection pool counters, SQL session duration và tốc độ client download.

**Fix** → tùy workload, có thể batch dữ liệu, materialize theo chunk, export async vào Blob Storage rồi trả link, hoặc giới hạn số export đồng thời.

**Verification** → load test với slow client, đo memory + active connections + p95 của request thông thường.

## 7. Common mistakes

- Nghĩ streaming luôn tốt hơn buffering.
- Stream trực tiếp query rất dài mà không xem connection lifetime.
- Không propagate `CancellationToken`, nên client disconnect nhưng producer vẫn query tiếp.
- Dùng `IAsyncEnumerable<T>` rồi phía sau lại gọi `ToListAsync()`, mất toàn bộ lợi ích streaming.
- Giả định async iterator tự tạo backpressure hoàn hảo cho mọi external producer.

## 8. Alternatives

### `Task<List<T>>`

Đơn giản hơn, phù hợp dataset nhỏ và khi caller thực sự cần random access toàn bộ collection.

### Pagination / batching

Tốt khi client làm việc theo page hoặc khi muốn giải phóng DB connection giữa các batch.

### Background export

Phù hợp export lớn: API tạo job, Worker tạo file, lưu Blob Storage, user tải sau.

## 9. Trade-offs

### Advantages

- giảm peak memory;
- cải thiện time-to-first-item;
- tự nhiên cho pipeline xử lý tuần tự;
- phù hợp large dataset và streaming protocol.

### Costs / Risks

- lifetime của DB/network resource có thể dài hơn;
- error có thể xảy ra giữa stream sau khi response đã bắt đầu;
- cancellation và partial result semantics phức tạp hơn;
- debugging khó hơn so với materialized collection.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `IAsyncEnumerable<T>` là async sequence chứ không phải “Task chứa list”.

### Middle

Implement `await foreach`, cancellation và projection đúng cách.

### Senior

Phân tích memory, connection lifetime, slow consumer, partial failure và streaming protocol.

### Technical Lead / Architect

Quyết định boundary nào nên stream, boundary nào nên paginate, và workload nào nên chuyển thành background export để không giữ HTTP + DB resources quá lâu.

## 11. Key takeaway

- Streaming giảm buffering nhưng có thể kéo dài resource lifetime.
- `IAsyncEnumerable<T>` là data-flow decision, không chỉ syntax feature.
- Đo memory **và** connection usage trước khi kết luận streaming tốt hơn.

# 2. ASP.NET Core middleware ordering: vì sao Authentication, Authorization, CORS và exception handling đặt sai thứ tự có thể làm hệ thống chạy “gần đúng” nhưng sai security boundary

## 1. What is it?

ASP.NET Core middleware pipeline là chuỗi component xử lý request theo thứ tự đăng ký. Mỗi middleware có thể:

- chạy logic trước middleware tiếp theo;
- gọi `next()`;
- chạy logic sau khi downstream hoàn tất;
- hoặc short-circuit request.

Mental model:

```text
Request
-> Middleware A
-> Middleware B
-> Middleware C
-> Endpoint
<- Middleware C
<- Middleware B
<- Middleware A
```

Vì vậy thứ tự là semantics, không phải style.

## 2. Why does it exist?

Các concern như exception handling, HTTPS, CORS, authentication, authorization và routing có dependency logic với nhau.

Ví dụ authorization cần `HttpContext.User` đã được authentication populate. Nếu `UseAuthorization()` chạy trước `UseAuthentication()`, policy evaluation có thể chạy trên anonymous principal.

## 3. How does it work?

Một pipeline điển hình:

```text
Exception Handler
   ↓
HTTPS / Forwarded Headers
   ↓
Routing
   ↓
CORS
   ↓
Authentication
   ↓
Authorization
   ↓
Endpoint
```

Không phải mọi app đều dùng đúng thứ tự này, nhưng dependency phải rõ:

```text
Authentication
-> establish identity

Authorization
-> evaluate what identity may do
```

Exception middleware muốn bắt exception từ downstream nên thường phải đứng sớm.

## 4. Practical implementation

```csharp
var app = builder.Build();

app.UseExceptionHandler();
app.UseHttpsRedirection();

app.UseRouting();
app.UseCors("WebClient");

app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();

app.Run();
```

Ví dụ policy:

```csharp
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("CanManageOrders", policy =>
        policy.RequireClaim("permission", "orders.manage"));
});
```

Nếu authentication không chạy đúng trước authorization, claim không tồn tại đúng lúc policy được evaluate.

## 5. Real production scenario

Local frontend gọi API trực tiếp nên CORS không gây vấn đề. Production thêm reverse proxy và SPA domain khác. Middleware order sai khiến preflight `OPTIONS` bị authorization chặn trước khi CORS headers được thêm.

Browser chỉ báo CORS error, trong khi API logs thấy 401/403. Team dễ debug sai layer.

## 6. Failure scenario & troubleshooting

**Symptom** → browser báo CORS error, API trực tiếp bằng Postman lại chạy.

**Evidence** → preflight request nhận 401/403 hoặc thiếu `Access-Control-Allow-Origin`.

**Hypothesis** → CORS middleware hoặc endpoint policy chạy sai thứ tự.

**Diagnosis** → inspect request pipeline, browser Network tab, server access logs và preflight response headers.

**Fix** → đặt CORS đúng vị trí giữa routing và endpoint execution, đồng thời kiểm tra authorization behavior cho preflight.

**Verification** → test actual browser flow, không chỉ curl/Postman.

## 7. Common mistakes

- Nghĩ middleware registration order không quan trọng.
- Đặt `UseAuthorization()` trước `UseAuthentication()`.
- Tự viết global try/catch trong controller thay vì exception middleware.
- Dùng CORS để “bảo mật API”, trong khi non-browser client không bị CORS hạn chế.
- Quên forwarded headers khi chạy sau reverse proxy, dẫn tới scheme/IP detection sai.

## 8. Alternatives

Endpoint filters hoặc MVC filters phù hợp concern ở endpoint/controller level. Middleware phù hợp concern cross-cutting toàn pipeline.

Một số functionality hiện có thể được cấu hình trực tiếp qua endpoint metadata, nhưng dependency ordering tổng thể vẫn tồn tại.

## 9. Trade-offs

### Advantages

Middleware tạo composition rõ ràng và centralized cross-cutting behavior.

### Costs / Risks

Pipeline càng phức tạp càng khó suy luận. Custom middleware có thể vô tình consume body, mutate headers hoặc short-circuit request không đúng lúc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu middleware là ordered pipeline.

### Middle

Biết đặt authentication/authorization/CORS/exception handling đúng dependency.

### Senior

Debug request flow xuyên reverse proxy, preflight, security middleware và endpoint metadata.

### Technical Lead / Architect

Giữ pipeline tối giản, document security boundaries và review custom middleware như infrastructure-critical code.

## 11. Key takeaway

- Middleware order là behavior.
- Authentication xác định identity; Authorization dùng identity đó để quyết định access.
- CORS là browser policy, không phải API authorization mechanism.

# 3. EF Core execution strategy + transaction: retry transient failure đúng cách mà không biến transaction thành nguồn duplicate side effect

## 1. What is it?

EF Core execution strategy là cơ chế retry cho transient database failures, ví dụ connection bị reset hoặc Azure SQL tạm thời unavailable.

Với provider hỗ trợ retry, một operation có thể được execute lại toàn bộ nếu failure được xem là transient.

Mental model:

```text
Operation
-> transient failure
-> delay/backoff
-> retry operation
```

Điểm khó xuất hiện khi application tự mở transaction hoặc có side effect ngoài database.

## 2. Why does it exist?

Cloud database có network hop và failover. Một transient lỗi ngắn không nhất thiết phải làm user request fail ngay.

Nhưng retry một statement đơn lẻ trong transaction không đủ nếu transaction cần được replay toàn bộ từ đầu.

## 3. How does it work?

Nếu application dùng explicit transaction:

```text
BEGIN
  write A
  write B
COMMIT
```

và connection fail sau `write A`, execution strategy cần replay cả transaction unit chứ không chỉ `write B`.

EF Core cho phép:

```text
execution strategy
  -> execute delegate
       -> begin transaction
       -> all DB work
       -> commit
```

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var transaction = await db.Database.BeginTransactionAsync(ct);

    order.MarkPaid();
    db.PaymentAttempts.Add(new PaymentAttempt(order.Id));

    await db.SaveChangesAsync(ct);
    await transaction.CommitAsync(ct);
});
```

Quan trọng: delegate có thể chạy nhiều lần. Vì vậy không nên đặt non-idempotent external side effect trực tiếp bên trong mà không có thiết kế phù hợp.

Ví dụ nguy hiểm:

```csharp
await strategy.ExecuteAsync(async () =>
{
    await paymentGateway.ChargeAsync(card, amount, ct); // có thể chạy lại
    await db.SaveChangesAsync(ct);
});
```

## 5. Real production scenario

Order service ghi `PaymentStatus=Paid` và audit record trong Azure SQL. Khi failover ngắn xảy ra, retry database transaction là hợp lý.

Nhưng nếu cùng transaction delegate gọi payment gateway, retry có thể charge khách hai lần nếu gateway request không idempotent.

## 6. Failure scenario & troubleshooting

**Symptom** → hiếm khi xuất hiện duplicate external transaction sau database connectivity incident.

**Evidence** → application logs cho thấy execution strategy retry; payment provider có hai request cùng business intent.

**Hypothesis** → non-idempotent side effect nằm trong replayable delegate.

**Diagnosis** → trace timeline giữa EF retry, external API request và transaction commit.

**Fix** → tách side effect bằng Outbox/workflow, hoặc dùng idempotency key ở external provider.

**Verification** → fault injection tại các điểm trước/sau commit và xác nhận không tạo duplicate business effect.

## 7. Common mistakes

- Enable retry rồi nghĩ mọi transaction tự nhiên an toàn.
- Mở explicit transaction bên ngoài execution strategy delegate.
- Retry operation chứa email/payment/webhook không idempotent.
- Không phân biệt transient failure với validation/constraint failure.
- Retry quá nhiều làm tăng load trong incident.

## 8. Alternatives

Application-level retry với Polly có thể phù hợp cho broader operation, nhưng database provider hiểu transient DB errors tốt hơn.

Outbox Pattern phù hợp khi cần nối DB state với message publishing.

Idempotency key phù hợp external command API.

## 9. Trade-offs

### Advantages

- tăng resilience trước transient failures;
- giảm user-visible error do failover/network glitch;
- tích hợp tốt với EF provider.

### Costs / Risks

- operation phải replay-safe;
- latency tăng khi retry;
- có thể khuếch đại load nếu retry policy quá aggressive;
- ambiguous commit outcome vẫn cần reasoning kỹ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transient error khác permanent error.

### Middle

Biết cấu hình retry và wrap explicit transaction đúng execution strategy.

### Senior

Phân tích replay safety, ambiguous commit và external side effects.

### Technical Lead / Architect

Định nghĩa transaction boundary, idempotency strategy và nơi retry được phép tồn tại trong toàn hệ thống.

## 11. Key takeaway

- Retry chỉ an toàn khi operation có thể replay.
- Transaction phải nằm **bên trong** execution strategy delegate khi cần replay toàn unit.
- External side effect cần idempotency hoặc workflow boundary riêng.

# 4. SQL connection pool exhaustion: phân biệt database chậm với application giữ connection quá lâu hoặc leak connection

## 1. What is it?

ADO.NET connection pooling giữ các physical database connection để tái sử dụng. `SqlConnection.OpenAsync()` thường không mở TCP/TDS connection mới mỗi lần; nó lấy connection từ pool nếu có.

Pool exhaustion xảy ra khi mọi pooled connection đang bị chiếm và request mới phải chờ connection được trả lại.

## 2. Why does it exist?

Thiết lập DB connection tốn handshake, authentication và network round-trip. Pooling giảm chi phí này rất nhiều.

Nhưng pool là finite resource. Nếu code giữ connection quá lâu, transaction dài, query treo hoặc không dispose đúng, throughput toàn application bị giới hạn.

## 3. How does it work?

```text
Request A -> pool -> connection #1
Request B -> pool -> connection #2
...
Request N -> pool -> connection #N

Request N+1
-> pool hết connection rảnh
-> chờ
-> timeout nếu không có connection quay lại
```

Little’s Law giúp reasoning trực giác:

```text
concurrent connections ≈ throughput × average connection hold time
```

Giảm hold time thường hiệu quả hơn chỉ tăng pool size.

## 4. Practical implementation

Code đúng lifetime:

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(ct);

await using var command = connection.CreateCommand();
command.CommandText = "SELECT Id, Name FROM Customers WHERE Id = @id";
command.Parameters.AddWithValue("@id", id);

await using var reader = await command.ExecuteReaderAsync(ct);
```

Với EF Core, `DbContext` scoped và query ngắn thường để provider tự quản connection. Không nên giữ transaction/database reader xuyên user interaction.

## 5. Real production scenario

API p95 tăng từ 300 ms lên 10 giây. Team nghĩ SQL Server CPU cao, nhưng DB CPU chỉ 25%.

Telemetry cho thấy:

- nhiều request chờ `OpenAsync()`;
- vài report query giữ connection 60–90 giây;
- pool đạt maximum concurrent connections.

Root cause là connection occupancy, không phải database compute saturation.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout kiểu “Timeout expired prior to obtaining a connection from the pool”.

**Evidence** → request trace chậm trước query execution; active connection count sát pool max; DB CPU bình thường.

**Hypothesis** → connection pool exhaustion.

**Diagnosis** → đo connection open wait, long-running SQL, transaction duration, request concurrency và code path không dispose reader/connection.

**Fix** → rút ngắn query/transaction, dispose đúng, tách report workload, giới hạn concurrency.

**Verification** → dưới cùng load, connection wait gần 0 và pool headroom ổn định.

## 7. Common mistakes

- Tăng `Max Pool Size` ngay lập tức mà không đo hold time.
- Giữ DB transaction trong lúc gọi HTTP external service.
- Stream result rất lâu trên connection chung với transactional traffic.
- Quên dispose data reader.
- Nhầm số `DbContext` với số physical DB connection.

## 8. Alternatives

Nếu workload reporting dài, dùng read replica, warehouse hoặc asynchronous export có thể phù hợp hơn.

Nếu traffic burst cần backpressure, application-level concurrency limit tốt hơn để 1000 requests cùng tranh 100 connections.

## 9. Trade-offs

### Advantages

Connection pooling tăng performance đáng kể và giảm DB connection setup overhead.

### Costs / Risks

Pool che giấu scarcity cho đến khi load tăng. Tăng pool size có thể đẩy bottleneck sang SQL Server thay vì giải quyết nó.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Close/Dispose` thường trả connection về pool, không nhất thiết đóng physical connection.

### Middle

Dispose đúng, tránh transaction dài và biết đọc pool timeout.

### Senior

Đo hold time, queueing, query duration và xác định true bottleneck.

### Technical Lead / Architect

Thiết kế workload isolation, concurrency limits và capacity giữa app replicas và database.

## 11. Key takeaway

- Pool exhaustion là queueing problem, không nhất thiết là SQL CPU problem.
- Connection hold time cực kỳ quan trọng.
- Tăng pool size chỉ hợp lý sau khi hiểu downstream capacity.

# 5. Redis cache stampede: ngăn hàng nghìn request cùng đánh database khi một hot key hết hạn

## 1. What is it?

Cache stampede xảy ra khi một hot cache entry hết hạn và nhiều request đồng thời miss cùng key, sau đó tất cả cùng truy vấn source-of-truth để rebuild cache.

Mental model:

```text
Hot key exists
-> 10.000 requests hit cache

TTL expires
-> 10.000 requests miss
-> 10.000 DB calls
```

Cache vốn dùng để bảo vệ database lại có thể tạo spike lớn hơn bình thường.

## 2. Why does it exist?

TTL tạo boundary sắc nét: trước expiry, gần như zero DB load; sau expiry, toàn bộ traffic chuyển sang DB cho tới khi cache được populate lại.

Hot key càng nổi tiếng, blast radius càng lớn.

## 3. How does it work?

Một mitigation phổ biến là single-flight:

```text
miss key X
  -> request A nhận quyền rebuild
  -> request B..N chờ hoặc dùng stale value
  -> A query DB
  -> A set Redis
  -> B..N dùng cache mới
```

Có thể kết hợp:

- TTL jitter;
- soft TTL + stale-while-revalidate;
- distributed lock ngắn;
- request coalescing trong instance;
- proactive refresh.

## 4. Practical implementation

Ví dụ đơn giản với `SemaphoreSlim` per key trong một instance:

```csharp
private readonly ConcurrentDictionary<string, SemaphoreSlim> _locks = new();

public async Task<ProductDto?> GetProductAsync(string key, CancellationToken ct)
{
    var cached = await _cache.GetStringAsync(key, ct);
    if (cached is not null)
        return JsonSerializer.Deserialize<ProductDto>(cached);

    var gate = _locks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
    await gate.WaitAsync(ct);

    try
    {
        cached = await _cache.GetStringAsync(key, ct);
        if (cached is not null)
            return JsonSerializer.Deserialize<ProductDto>(cached);

        var product = await _repository.GetAsync(key, ct);
        if (product is null) return null;

        var ttl = TimeSpan.FromMinutes(5)
            + TimeSpan.FromSeconds(Random.Shared.Next(0, 30));

        await _cache.SetStringAsync(
            key,
            JsonSerializer.Serialize(product),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = ttl
            },
            ct);

        return product;
    }
    finally
    {
        gate.Release();
    }
}
```

Đây chỉ coalesce trong một process. Multi-instance cần strategy phù hợp hơn.

## 5. Real production scenario

Homepage e-commerce có product catalog hot key được đọc 8.000 request/giây. TTL 10 phút giống nhau ở mọi instance.

Khi key expire, database load tăng đột ngột, connection pool cạn và API timeout. Cache “working fine” trong 9 phút 59 giây rồi outage theo chu kỳ.

## 6. Failure scenario & troubleshooting

**Symptom** → DB CPU/queries spike theo chu kỳ gần đúng TTL.

**Evidence** → Redis hit ratio tụt đúng thời điểm; nhiều identical query cùng xuất hiện.

**Hypothesis** → stampede trên hot key.

**Diagnosis** → correlate cache miss metrics theo key prefix với DB query count.

**Fix** → jitter TTL, single-flight, stale-while-revalidate hoặc prewarming.

**Verification** → force-expire hot key dưới load; DB query count phải tăng có kiểm soát thay vì theo request rate.

## 7. Common mistakes

- TTL mọi key giống hệt nhau.
- Dùng distributed lock mà lock timeout ngắn hơn rebuild duration.
- Lock toàn cache thay vì per key.
- Khi lock fail thì tất cả request fallback DB ngay.
- Không đo hit ratio theo category/hot key.

## 8. Alternatives

Nếu data rất nhỏ và mỗi instance có thể giữ riêng, `IMemoryCache` + local single-flight có thể đơn giản hơn Redis.

Nếu source query rẻ và traffic thấp, không cache có thể là lựa chọn tốt hơn.

## 9. Trade-offs

### Advantages

Cache giảm latency và source load khi access pattern phù hợp.

### Costs / Risks

Stampede mitigation thêm concurrency logic, stale-data policy và operational dependency. Distributed lock sai có thể tạo bottleneck mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss nhiều request đồng thời khác một cache miss đơn lẻ.

### Middle

Implement double-check + single-flight + TTL jitter.

### Senior

Phân tích multi-instance behavior, stale policy, hot-key distribution và Redis failure.

### Technical Lead / Architect

Quyết định có cần cache hay không, freshness SLA là gì và source system chịu được load bao nhiêu khi cache mất.

## 11. Key takeaway

- Hot-key expiry có thể biến cache thành traffic amplifier.
- Jitter + request coalescing thường quan trọng hơn chỉ “thêm Redis”.
- Luôn thiết kế behavior khi cache miss hàng loạt và khi Redis unavailable.

# 6. Saga Pattern + compensating transaction: xử lý business transaction xuyên nhiều service khi rollback kiểu ACID không còn khả thi

## 1. What is it?

Saga là chuỗi local transactions trong nhiều service. Mỗi bước commit riêng. Nếu bước sau thất bại, hệ thống thực hiện compensating action cho các bước trước khi business cho phép.

Mental model:

```text
Reserve Inventory
-> Authorize Payment
-> Create Shipment

nếu Shipment fail
-> Cancel Payment Authorization
-> Release Inventory
```

Compensation không phải database rollback. Nó là **business action mới**.

## 2. Why does it exist?

Trong microservices, mỗi service sở hữu database riêng. Không thể dễ dàng bọc SQL transaction quanh Inventory DB + Payment provider + Shipping API.

2PC/distributed transaction thường không khả dụng, tăng coupling và availability dependency.

## 3. How does it work?

Có hai style chính:

### Orchestration

```text
Saga Orchestrator
-> Inventory: reserve
-> Payment: authorize
-> Shipping: create
```

Orchestrator giữ state machine và quyết định bước tiếp theo.

### Choreography

```text
OrderCreated
-> InventoryReserved
-> PaymentAuthorized
-> ShipmentCreated
```

Service phản ứng event lẫn nhau.

Orchestration thường dễ quan sát hơn cho workflow dài; choreography giảm central coordinator nhưng dễ tạo implicit coupling.

## 4. Practical implementation

Một state record đơn giản:

```csharp
public sealed class OrderSaga
{
    public Guid OrderId { get; init; }
    public SagaState State { get; private set; }

    public void InventoryReserved() => State = SagaState.InventoryReserved;
    public void PaymentAuthorized() => State = SagaState.PaymentAuthorized;
    public void ShippingCreated() => State = SagaState.Completed;
    public void CompensationRequired() => State = SagaState.Compensating;
}
```

Handler phải idempotent vì message có thể delivery nhiều lần.

```csharp
if (await inbox.AlreadyProcessedAsync(message.Id, ct))
    return;

await inventory.ReleaseAsync(message.OrderId, ct);
await inbox.MarkProcessedAsync(message.Id, ct);
```

## 5. Real production scenario

Checkout cần:

1. reserve stock;
2. authorize payment;
3. create shipment.

Payment thành công nhưng shipping provider timeout. Không thể “rollback” HTTP call đã authorize payment như SQL rollback.

System phải biết payment authorization có API cancel/void hay không và compensation có thể fail tiếp.

## 6. Failure scenario & troubleshooting

**Symptom** → order stuck ở trạng thái “PaymentAuthorized” hàng giờ.

**Evidence** → saga state không tiến, shipping retries exhausted, compensation chưa chạy.

**Hypothesis** → workflow state machine thiếu timeout/recovery transition.

**Diagnosis** → inspect saga state, message history, retry count, DLQ và downstream responses.

**Fix** → explicit timeout event, compensation path, operator recovery và idempotent retries.

**Verification** → fault-injection từng bước và xác nhận saga luôn tới terminal state hoặc actionable manual state.

## 7. Common mistakes

- Nghĩ compensation luôn đảo ngược hoàn hảo.
- Không model intermediate states.
- Choreography quá nhiều event khiến không ai thấy toàn workflow.
- Không có idempotency/inbox.
- Không có manual recovery cho compensation failure.
- Giữ user HTTP request mở cho toàn saga dài.

## 8. Alternatives

Nếu mọi write nằm trong cùng database và cùng bounded context, local ACID transaction đơn giản hơn rất nhiều.

Modular Monolith có thể giữ business transaction local lâu hơn trước khi cần distributed saga.

## 9. Trade-offs

### Advantages

- hỗ trợ workflow cross-service;
- tránh global distributed transaction;
- resilience tốt hơn khi service độc lập.

### Costs / Risks

- eventual consistency;
- state machine phức tạp;
- compensation không hoàn hảo;
- observability và operator tooling bắt buộc;
- test matrix lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cross-service transaction không thể giả định rollback như một database.

### Middle

Implement state transitions, idempotent handlers và retry.

### Senior

Thiết kế compensation, timeout, DLQ, recovery và concurrency semantics.

### Technical Lead / Architect

Quyết định có thực sự cần phân tách service đến mức phải trả giá Saga hay một transaction local đơn giản hơn mới là design đúng.

## 11. Key takeaway

- Saga là business workflow, không phải ACID transaction kéo dài.
- Compensation là action mới và có thể thất bại.
- Nếu local transaction giải quyết được bài toán, đừng đưa Saga vào quá sớm.

# 7. Azure Service Bus lock duration + message settlement: tránh duplicate processing khi handler chạy lâu hơn message lock

## 1. What is it?

Trong Azure Service Bus `PeekLock` mode, consumer nhận message nhưng broker chưa xóa message. Consumer có một lock tạm thời để xử lý. Sau đó consumer phải settle message bằng:

- complete;
- abandon;
- dead-letter;
- defer.

Nếu lock hết hạn trước khi processing hoàn tất, message có thể được delivery lại.

## 2. Why does it exist?

Nếu broker xóa message ngay khi giao cho consumer và process crash giữa chừng, message bị mất.

`PeekLock` hỗ trợ at-least-once delivery: broker chỉ coi message hoàn tất sau explicit completion.

## 3. How does it work?

```text
Broker
-> deliver message + lock
-> consumer processing

success trước lock expiry
-> Complete
-> remove message

consumer crash / lock expires
-> message available lại
-> delivery count tăng
```

Lock renewal có thể kéo dài thời gian xử lý, nhưng không nên dùng để che handler kéo dài không kiểm soát.

## 4. Practical implementation

```csharp
var processor = client.CreateProcessor(queueName, new ServiceBusProcessorOptions
{
    MaxConcurrentCalls = 8,
    AutoCompleteMessages = false,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(10)
});

processor.ProcessMessageAsync += async args =>
{
    try
    {
        await handler.HandleAsync(args.Message, args.CancellationToken);
        await args.CompleteMessageAsync(args.Message, args.CancellationToken);
    }
    catch (KnownPermanentException ex)
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            "PermanentFailure",
            ex.Message,
            args.CancellationToken);
    }
};
```

Handler vẫn phải idempotent.

## 5. Real production scenario

Image-processing consumer mất 2–4 phút cho file lớn. Queue lock duration là 1 phút. Auto lock renewal bị disable trong deployment mới.

Một message bắt đầu xử lý trên worker A. Sau 1 phút lock expire, worker B nhận lại cùng message trong khi A vẫn chạy. Cả hai cùng ghi output.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng message ID xuất hiện nhiều lần, duplicate output, `MessageLockLostException` khi complete.

**Evidence** → processing duration > lock duration; delivery count > 1.

**Hypothesis** → lock expiry trước settlement.

**Diagnosis** → correlate message ID, delivery count, handler duration và lock renewal logs.

**Fix** → tune lock/renewal, giảm handler duration, split work, kiểm soát concurrency và bảo đảm idempotency.

**Verification** → test message vượt default lock time, confirm không duplicate side effect dù redelivery xảy ra.

## 7. Common mistakes

- Nghĩ `Complete` là optional.
- Tăng lock lên rất dài thay vì xử lý architecture của long-running work.
- Không idempotent vì “auto lock renewal đã bật”.
- Set `MaxConcurrentCalls` quá cao làm downstream DB/API overload.
- Dead-letter mọi transient error ngay lần đầu.

## 8. Alternatives

Nếu work rất dài, message có thể chỉ trigger một durable job record rồi worker khác xử lý theo state machine.

Azure Functions Service Bus trigger có abstraction cao hơn nhưng delivery/lock semantics vẫn cần hiểu.

## 9. Trade-offs

### Advantages

PeekLock bảo vệ khỏi message loss khi consumer crash.

### Costs / Risks

At-least-once đồng nghĩa duplicate delivery là behavior bình thường. Lock renewal và settlement làm handler lifecycle phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu nhận message chưa đồng nghĩa message đã bị xóa.

### Middle

Implement complete/abandon/dead-letter và đọc delivery count.

### Senior

Tune concurrency, lock renewal, idempotency và poison-message strategy.

### Technical Lead / Architect

Thiết kế processing SLA, long-running work boundary và downstream capacity thay vì chỉ tăng concurrency hoặc lock duration.

## 11. Key takeaway

- `PeekLock` hỗ trợ at-least-once, không phải exactly-once.
- Lock expiry có thể gây concurrent duplicate processing.
- Idempotency vẫn bắt buộc ngay cả khi lock renewal được cấu hình tốt.

# 8. Kubernetes resource requests/limits: hiểu scheduling, CPU throttling và `OOMKilled` thay vì chỉ “set vài con số YAML”

## 1. What is it?

Kubernetes `requests` mô tả lượng resource pod cần để scheduler placement. `limits` đặt upper bound runtime cho resource nhất định.

Với CPU và memory, behavior khác nhau:

- CPU vượt limit thường bị throttling;
- memory vượt limit có thể khiến container bị `OOMKilled`.

## 2. Why does it exist?

Cluster chứa nhiều workload cạnh tranh resource. Scheduler cần biết mức tối thiểu để đặt pod lên node phù hợp.

Không có request, cluster dễ overcommit thiếu kiểm soát. Không có limit, một workload runaway có thể ảnh hưởng workload khác.

## 3. How does it work?

Ví dụ:

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"
```

Scheduler dùng request:

```text
node allocatable
- sum(requests)
= capacity còn lại để schedule
```

Runtime container có thể dùng hơn request nếu node còn headroom, nhưng limit tạo ceiling.

## 4. Practical implementation

Với ASP.NET Core API, bắt đầu bằng measurement thay vì copy template:

```text
load test target: 300 req/s
observed CPU p95: 420m
observed memory steady: 310Mi
GC peak: 390Mi
```

Có thể chọn request/limit có margin rồi test lại dưới HPA và rolling deployment.

Health/metrics cần theo dõi:

- container CPU usage;
- CPU throttled time;
- working set;
- restart reason;
- `OOMKilled`;
- request latency.

## 5. Real production scenario

API có memory limit 256Mi được copy từ sample YAML. Bình thường dùng 180Mi, nhưng endpoint export tạo peak 300Mi. Pod bị `OOMKilled`, restart, traffic chuyển sang pod còn lại, chúng cũng tăng tải và lần lượt chết.

Incident nhìn giống “random pod restart” nhưng root cause là workload + limit mismatch.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng dù CPU usage graph chỉ quanh limit, hoặc pod restart với exit code 137.

**Evidence** → `kubectl describe pod` cho thấy `OOMKilled`; CPU metric cho thấy throttling time cao.

**Hypothesis** → resource limit không phù hợp workload.

**Diagnosis** → so request/limit với actual usage, GC metrics, concurrency và node pressure.

**Fix** → giảm peak allocation/concurrency hoặc điều chỉnh resource envelope có bằng chứng.

**Verification** → load test + chaos/rolling deployment, kiểm tra không OOM và p95 ổn định.

## 7. Common mistakes

- Set request = limit cho mọi workload mà không hiểu consequence.
- CPU limit quá thấp khiến app bị throttled dù node còn rảnh.
- Memory limit thấp hơn realistic GC peak.
- Tăng limit mãi mà không sửa memory leak.
- HPA scale theo CPU percentage nhưng request CPU đặt vô lý, làm signal scale méo.

## 8. Alternatives

Azure App Service/Container Apps che bớt scheduler details nhưng vẫn có resource sizing.

Nếu workload chưa cần Kubernetes complexity, managed compute đơn giản hơn có thể tốt hơn.

## 9. Trade-offs

### Advantages

- scheduling predictable hơn;
- workload isolation;
- hỗ trợ capacity planning và autoscaling.

### Costs / Risks

- cấu hình sai gây throttling/OOM;
- request quá cao lãng phí cluster;
- request quá thấp gây overcommit;
- cần profiling/load test liên tục theo workload mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt request và limit.

### Middle

Đọc `kubectl describe`, restart reason và resource metrics.

### Senior

Liên hệ GC, concurrency, throttling và HPA behavior.

### Technical Lead / Architect

Quyết định resource policy, cost headroom, autoscaling và liệu Kubernetes có đáng operational burden cho hệ thống hiện tại hay không.

## 11. Key takeaway

- CPU limit và memory limit không có failure behavior giống nhau.
- Resource sizing phải dựa trên measurement.
- `OOMKilled` và throttling là production signals, không phải “Kubernetes tự nhiên khó hiểu”.

# 9. Akamai/CDN cache key design: query string, headers và personalization có thể phá hit ratio hoặc leak dữ liệu nếu boundary cache sai

## 1. What is it?

CDN cache key là identity mà edge dùng để quyết định hai HTTP requests có thể dùng chung cached response hay không.

Một cache key có thể dựa trên:

```text
scheme + host + path + selected query params + selected headers
```

Nếu key quá chi tiết, hit ratio thấp. Nếu key thiếu dimension quan trọng, edge có thể phục vụ response sai cho user khác.

## 2. Why does it exist?

CDN muốn reuse response càng nhiều càng tốt để giảm origin latency/load. Nhưng “cùng URL” chưa chắc cùng representation.

Ví dụ:

```text
/products/123?currency=USD
/products/123?currency=EUR
```

Nếu currency ảnh hưởng body nhưng bị bỏ khỏi cache key, user có thể thấy giá sai.

## 3. How does it work?

```text
Browser request
-> Akamai edge
-> normalize request
-> compute cache key
-> HIT: trả edge object
-> MISS: gọi origin
-> cache response nếu policy cho phép
```

Cache key phải phản ánh mọi input làm thay đổi representation **mà CDN đang được phép cache**.

## 4. Practical implementation

Origin nên trả cache headers có chủ đích:

```http
Cache-Control: public, max-age=60, s-maxage=300
Vary: Accept-Encoding
```

Với personalization:

```http
Cache-Control: private, no-store
```

hoặc tách architecture:

```text
/public-product-shell   -> CDN cacheable
/user-specific-price   -> authenticated API, not shared-cacheable
```

Không nên thêm `Vary: Cookie` một cách máy móc vì gần như mỗi user có cookie khác nhau, hit ratio có thể sụp.

## 5. Real production scenario

Marketing page cache theo path nhưng origin render region-specific offer dựa trên header địa lý. Region không nằm trong cache key. User ở Singapore nhận offer được cache từ Australia edge variant.

Một lỗi cache key có thể là correctness bug hoặc security/privacy incident.

## 6. Failure scenario & troubleshooting

**Symptom** → user thỉnh thoảng thấy content/price sai region hoặc stale sau deployment.

**Evidence** → origin trả đúng khi bypass CDN; edge response có cache age và same object reused giữa requests khác dimension.

**Hypothesis** → cache key/purge policy không phản ánh representation.

**Diagnosis** → inspect cache status headers, query normalization, `Vary`, cookie/header rules và Akamai property configuration.

**Fix** → thêm dimension cần thiết hoặc chuyển personalized response thành non-cacheable/tách endpoint.

**Verification** → matrix test theo region/query/auth state và xác nhận HIT/MISS đúng mong đợi.

## 7. Common mistakes

- Cache mọi query string, làm hit ratio cực thấp do tracking params như `utm_source`.
- Bỏ toàn bộ query string dù một số param thay đổi response.
- Shared-cache response chứa user-specific data.
- Dùng `Vary: Cookie` rộng quá.
- Purge CDN nhưng quên browser cache/origin cache layer.

## 8. Alternatives

Browser cache chỉ tối ưu cho từng client, không giảm origin load giữa users.

Reverse-proxy cache gần origin đơn giản hơn cho một số hệ thống nhưng không có global edge distribution như CDN.

## 9. Trade-offs

### Advantages

- giảm latency;
- giảm origin traffic;
- hấp thụ traffic burst;
- cải thiện resilience cho static/public content.

### Costs / Risks

- cache invalidation;
- stale content;
- correctness/security nếu key sai;
- observability nhiều layer phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CDN cache theo key chứ không đơn giản “theo URL”.

### Middle

Dùng `Cache-Control`, `Vary` và debug HIT/MISS.

### Senior

Thiết kế cache key, query normalization, personalization boundary và purge strategy.

### Technical Lead / Architect

Quyết định content nào được shared-cache, content nào phải private và contract giữa CDN/origin/application ownership.

## 11. Key takeaway

- Cache key là correctness boundary.
- Key quá rộng làm hit ratio thấp; key quá hẹp có thể trả sai hoặc leak dữ liệu.
- Personalized content cần được tách khỏi shared-cache boundary cẩn thận.

# 10. Flaky integration tests với shared database: biến test ngẫu nhiên thành deterministic engineering signal

## 1. What is it?

Flaky test là test có thể pass hoặc fail với cùng code vì phụ thuộc timing, shared state, order hoặc external environment.

Với integration tests, shared database là nguồn flakiness phổ biến:

```text
Test A tạo Customer X
Test B kỳ vọng database trống
Test A/B chạy parallel
-> kết quả phụ thuộc timing
```

Test suite không deterministic làm mất giá trị như engineering signal.

## 2. Why does it exist?

Integration test cần infrastructure thật để kiểm chứng behavior mà mock không bắt được: SQL translation, constraints, transactions, migrations.

Nhưng dùng chung database không có isolation sẽ tạo hidden coupling giữa tests.

## 3. How does it work?

Một test tốt cần kiểm soát:

- schema state;
- seed data;
- transaction/data cleanup;
- unique identifiers;
- external time;
- parallelism.

Pattern phổ biến:

```text
Test fixture
-> start real SQL container
-> apply migrations
-> before each test reset data
-> run test
-> assert
```

Container có thể shared theo test collection để giảm startup cost, trong khi data reset per test.

## 4. Practical implementation

Ví dụ dùng unique data + cleanup strategy:

```csharp
public async Task Create_order_persists_items()
{
    var customerId = Guid.NewGuid();

    await SeedCustomerAsync(customerId);

    var response = await _client.PostAsJsonAsync("/orders", new
    {
        CustomerId = customerId,
        Items = new[] { new { Sku = "SKU-001", Quantity = 2 } }
    });

    response.EnsureSuccessStatusCode();

    await using var db = CreateDbContext();
    var order = await db.Orders
        .Include(x => x.Items)
        .SingleAsync(x => x.CustomerId == customerId);

    Assert.Single(order.Items);
}
```

Không assert `Orders.Count() == 1` nếu suite có thể chạy parallel.

## 5. Real production scenario

CI thỉnh thoảng fail 1 trong 50 runs. Team rerun pipeline đến khi xanh. Sau vài tháng, flaky test trở thành bình thường và developer ngừng tin CI.

Khi regression thật xuất hiện, mọi người cũng assume “chắc flaky”. Đây là quality-system failure, không chỉ inconvenience.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail ngẫu nhiên, rerun pass.

**Evidence** → failure correlation với parallel execution; cùng test ổn khi chạy riêng.

**Hypothesis** → shared mutable state hoặc timing dependency.

**Diagnosis** → chạy test nhiều lần, disable parallel tạm thời để isolate, log unique IDs/database state.

**Fix** → per-test isolation, deterministic reset, unique test data, fake clock, bounded external dependencies.

**Verification** → stress-run test suite nhiều vòng; failure rate phải về 0 hoặc nguyên nhân còn lại được định danh rõ.

## 7. Common mistakes

- Rerun flaky tests tự động rồi coi pipeline xanh là xong.
- `Thread.Sleep()` để “đợi hệ thống ổn định”.
- Dùng shared static fixture mutable state.
- Test phụ thuộc order chạy.
- Mock database rồi gọi đó là integration test.
- Cleanup bằng cách delete không đúng FK/order và để rác state lại.

## 8. Alternatives

Transaction rollback per test nhanh nhưng không phù hợp khi application mở connection/transaction riêng ngoài test scope.

Database per test isolation mạnh nhưng đắt hơn.

Schema-per-test hoặc Respawn-style reset thường cân bằng tốt cho relational DB integration testing.

## 9. Trade-offs

### Advantages

Integration tests với real database bắt được SQL, mapping và constraint bugs thực tế.

### Costs / Risks

Chậm hơn unit tests, cần lifecycle infrastructure và isolation strategy. Nếu không deterministic, chúng phá niềm tin vào CI.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu test phải độc lập với test khác.

### Middle

Tạo unique data, reset database và tránh timing hacks.

### Senior

Thiết kế fixture, parallelism, container lifecycle và failure diagnostics.

### Technical Lead / Architect

Định nghĩa test strategy theo risk: unit cho logic thuần, integration cho infrastructure contract, E2E cho critical user flow; đồng thời coi flakiness là defect cần xử lý chứ không phải noise chấp nhận được.

## 11. Key takeaway

- Flaky test làm hỏng trust của toàn CI pipeline.
- Integration test cần real infrastructure **và** deterministic isolation.
- Rerun không phải remediation; phải tìm hidden shared state hoặc timing dependency.
