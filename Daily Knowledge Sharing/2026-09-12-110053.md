# 1. C# exception filters (`catch when`) và observability: lọc exception trước khi stack unwind mà không biến logging thành side effect nguy hiểm

## 1. What is it?

Exception filter là điều kiện `when` đặt trên `catch`:

```csharp
try
{
    await ProcessAsync(ct);
}
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.NotFound)
{
    // handle only 404-like failures
}
```

Điểm quan trọng không phải syntax. Filter được đánh giá trong giai đoạn tìm handler, trước khi runtime unwind stack vào `catch` tương ứng. Điều này giúp chọn handler theo metadata của exception mà không phải bắt tất cả rồi rethrow.

Mental model:

```text
throw
  -> runtime tìm catch phù hợp
  -> evaluate when-filter
  -> filter true: chọn handler
  -> filter false: tiếp tục tìm handler khác
```

## 2. Why does it exist?

Trong code production, cùng một exception type có thể biểu diễn nhiều semantics khác nhau. Ví dụ `SqlException`, `HttpRequestException` hoặc domain exception có error code cụ thể.

Không có filter, developer thường viết:

```csharp
catch (HttpRequestException ex)
{
    if (ex.StatusCode != HttpStatusCode.NotFound)
        throw;

    ...
}
```

Cách này hoạt động, nhưng handler đã được chọn rồi. Filter cho phép diễn đạt intent rõ hơn: “chỉ catch khi điều kiện này đúng”.

## 3. How does it work?

Filter phải trả `bool`. Nếu filter throw exception, runtime coi filter như `false` và tiếp tục tìm handler khác. Vì vậy filter không phải nơi phù hợp để chạy logic phức tạp hoặc side effect quan trọng.

Một use case tốt là quyết định dựa trên dữ liệu sẵn có:

```csharp
catch (PaymentException ex) when (ex.Code == "card_declined")
{
    return PaymentResult.Declined();
}
```

Một use case xấu:

```csharp
catch (Exception ex) when (LogAndReturnTrue(ex))
{
    ...
}
```

Logging trong filter có thể khiến observability phụ thuộc vào một phase rất khó reasoning, đặc biệt nếu logger/provider tự throw hoặc logic filter thay đổi state.

## 4. Practical implementation

Một pattern rõ ràng:

```csharp
public async Task<Product?> GetAsync(
    string sku,
    CancellationToken ct)
{
    try
    {
        return await _client.GetProductAsync(sku, ct);
    }
    catch (ApiException ex) when (ex.StatusCode == 404)
    {
        return null;
    }
}
```

Nếu cần telemetry, log trong handler:

```csharp
catch (ApiException ex) when (ex.StatusCode == 429)
{
    _logger.LogWarning(
        ex,
        "Product API throttled for SKU {Sku}",
        sku);

    throw;
}
```

## 5. Real production scenario

Một integration gọi third-party product API. `ApiException` được dùng cho cả `404`, `429`, `500`.

Business muốn:

- `404` → coi là product không tồn tại;
- `429` → propagate để resilience layer retry/backoff;
- `500` → fail request và ghi telemetry.

Exception filter giúp mỗi failure semantics đi vào đúng path mà không biến một `catch` lớn thành switch statement khó bảo trì.

## 6. Failure scenario & troubleshooting

**Symptom** → exception đáng lẽ phải propagate nhưng bị nuốt, hoặc log xuất hiện hai lần.

**Evidence** → stack trace cho thấy nhiều nested catch/filter; filter gọi method có side effect.

**Hypothesis** → filter đang làm nhiều hơn nhiệm vụ lựa chọn handler.

**Diagnosis** → rút filter về pure predicate; kiểm tra handler nào thật sự được chọn; bật debugger break on thrown exception.

**Fix** → chỉ để điều kiện đơn giản trong `when`; logging/recovery để trong handler hoặc centralized exception middleware.

**Verification** → unit test từng error code và integration test behavior với retry layer.

## 7. Common mistakes

- `catch (Exception) when (...)` quá rộng.
- Dùng filter để mutate state.
- Log trong filter rồi log lại trong middleware.
- Dùng message string để phân loại exception thay vì type/error code.
- Rethrow bằng `throw ex;` làm mất original stack trace.

## 8. Alternatives

Pattern matching bên trong `catch` đơn giản hơn nếu logic cần nhiều nhánh. Domain-specific exception hierarchy phù hợp khi semantics ổn định và đáng encode thành type.

Trong ASP.NET Core, centralized exception middleware/`IExceptionHandler` phù hợp hơn cho mapping exception → HTTP response toàn hệ thống.

## 9. Trade-offs

### Advantages

- Handler selection rõ ràng.
- Không cần catch rộng rồi rethrow thủ công.
- Giữ semantics gần nơi exception được xử lý.

### Costs / Risks

- Filter phức tạp rất khó debug.
- Dễ lạm dụng cho logging/side effects.
- Không thay thế exception taxonomy tốt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `catch when` là điều kiện chọn handler, không phải một `if` bình thường sau khi catch.

### Middle

Dùng filter cho error code/status code cụ thể và giữ filter đơn giản.

### Senior

Hiểu thời điểm filter được evaluate, stack unwinding, rethrow semantics và interaction với centralized error handling.

### Technical Lead / Architect

Quyết định exception nào thuộc domain, infrastructure hay HTTP boundary; tránh để codebase dựa vào generic exception + ad-hoc filter khắp nơi.

## 11. Key takeaway

- Exception filter nên là pure predicate cho handler selection.
- Logging/recovery nên nằm trong handler hoặc centralized error pipeline.
- Phân loại exception bằng semantics ổn định, không bằng message text.

# 2. ASP.NET Core graceful shutdown và request draining: deploy/restart mà không cắt ngang request hoặc background work

## 1. What is it?

Graceful shutdown là quá trình application ngừng nhận workload mới, cho workload đang chạy cơ hội hoàn tất trong một khoảng thời gian, rồi mới terminate process.

Trong ASP.NET Core, host phát cancellation signal khi shutdown bắt đầu. Request pipeline, `BackgroundService`, database call và external I/O nên tôn trọng `CancellationToken`.

Mental model:

```text
SIGTERM / App Service recycle
       -> host begins stopping
       -> stop accepting new work
       -> in-flight work drains
       -> hosted services stop
       -> timeout reached
       -> process exits
```

## 2. Why does it exist?

Production process restart là bình thường: deployment, scaling, node maintenance, configuration change, container reschedule.

Nếu application coi restart như “kill process ngay”, user có thể thấy:

- upload bị cắt giữa chừng;
- transaction chưa commit;
- message đang xử lý bị redeliver;
- response socket đóng đột ngột;
- background job dừng ở state không rõ ràng.

## 3. How does it work?

Host cung cấp `ApplicationStopping`/shutdown token. `BackgroundService.ExecuteAsync` nhận `stoppingToken`.

Reverse proxy/orchestrator cũng cần phối hợp. Kubernetes có termination grace period; App Service/IIS có lifecycle riêng. Application chỉ graceful nếu infrastructure cho đủ thời gian.

Request draining không có nghĩa “đợi vô hạn”. Hệ thống phải có upper bound.

## 4. Practical implementation

Background worker:

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var message = await _queue.ReceiveAsync(stoppingToken);

            await ProcessAsync(message, stoppingToken);
        }
    }
}
```

Shutdown-specific cleanup:

```csharp
public override async Task StopAsync(CancellationToken cancellationToken)
{
    _logger.LogInformation("Queue worker is stopping.");

    await base.StopAsync(cancellationToken);
}
```

Không dùng `CancellationToken.None` cho dependency call dài:

```csharp
await _httpClient.SendAsync(request, stoppingToken);
```

## 5. Real production scenario

Một API xử lý file 30–60 giây và deploy bằng rolling update. Nếu pod cũ nhận SIGTERM rồi chết sau 5 giây, user nhận connection reset và phải upload lại.

Giải pháp không chỉ là tăng termination timeout. Có thể cần thay đổi architecture:

```text
Upload -> Blob Storage
       -> enqueue processing
       -> Worker xử lý async
```

Request ngắn hơn, shutdown đơn giản hơn và job có thể retry/idempotent.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment “successful” nhưng error rate tăng đúng lúc rollout; traces kết thúc giữa chừng.

**Evidence** → process shutdown logs trùng thời điểm 5xx/connection reset; request duration dài hơn grace period.

**Hypothesis** → workload không drain kịp hoặc cancellation không propagate.

**Diagnosis** → xem host lifecycle logs, reverse-proxy metrics, shutdown duration, in-flight requests, background task count.

**Fix** → propagate token, giới hạn work per request, tăng grace period khi hợp lý, chuyển long-running work sang queue.

**Verification** → rolling deployment dưới load và xác nhận error rate không tăng đáng kể.

## 7. Common mistakes

- Bỏ qua `CancellationToken`.
- Spawn fire-and-forget `Task.Run` không được host quản lý.
- Grace period quá ngắn so với p99 request duration.
- Grace period cực dài để che architecture problem.
- Shutdown nhưng vẫn nhận job mới từ queue.

## 8. Alternatives

Nếu task cần durability, dùng queue + Worker/Azure Functions thay vì giữ request lâu. Với batch job ngắn, synchronous endpoint vẫn đủ nếu shutdown window hợp lý.

## 9. Trade-offs

### Advantages

- Giảm request failure trong deploy/restart.
- Lifecycle predictable hơn.
- Dễ vận hành rolling deployment.

### Costs / Risks

- Shutdown có thể chậm.
- Cần idempotency cho work bị interrupt.
- Infrastructure và application phải cùng hỗ trợ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu restart production là expected event, không phải rare crash.

### Middle

Propagate cancellation và không tạo unmanaged background tasks.

### Senior

Phân tích drain time, retry/idempotency và shutdown behavior dưới load.

### Technical Lead / Architect

Quyết định workload nào được phép giữ request lâu và workload nào phải tách thành durable asynchronous workflow.

## 11. Key takeaway

- Graceful shutdown là reliability requirement của deploy/scale.
- `CancellationToken` phải đi xuyên dependency chain.
- Long-running durable work thường không nên gắn chặt vào HTTP request lifetime.

# 3. EF Core compiled queries: hiểu query-shape cache trước khi tối ưu hot path bằng `EF.CompileQuery`

## 1. What is it?

EF Core phải biến LINQ expression tree thành SQL command shape. EF đã có query compilation cache nội bộ dựa trên expression shape.

Compiled query (`EF.CompileQuery` / `EF.CompileAsyncQuery`) cho phép application precompile một query delegate để giảm overhead của việc tra cứu/compile query shape lặp lại trên hot path.

## 2. Why does it exist?

Ở đa số business APIs, database/network latency lớn hơn EF query-compilation overhead. Nhưng với query rất nhỏ, chạy cực nhiều lần, latency DB thấp và allocation/CPU application đã trở thành bottleneck, compiled query có thể có ý nghĩa.

Nó tồn tại cho hot path đã đo được, không phải default coding style.

## 3. How does it work?

Normal path:

```text
LINQ expression
 -> normalize/query cache lookup
 -> translation
 -> SQL command
 -> execute
 -> materialize
```

Compiled query:

```text
startup/static initialization
 -> compile expression once
 -> delegate(context, parameters)
 -> execute repeatedly
```

Parameter values không nên được baked vào expression shape, nếu không cache effectiveness giảm.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, Guid, Task<Customer?>>
    GetCustomerById =
        EF.CompileAsyncQuery(
            (AppDbContext db, Guid id) =>
                db.Customers
                    .AsNoTracking()
                    .SingleOrDefault(x => x.Id == id));

public Task<Customer?> FindAsync(Guid id)
    => GetCustomerById(_db, id);
```

Nếu projection đủ dùng, projection thường quan trọng hơn compiled query:

```csharp
private static readonly Func<AppDbContext, Guid, Task<CustomerSummary?>>
    GetCustomerSummary =
        EF.CompileAsyncQuery(
            (AppDbContext db, Guid id) =>
                db.Customers
                    .Where(x => x.Id == id)
                    .Select(x => new CustomerSummary(x.Id, x.Name))
                    .SingleOrDefault());
```

## 5. Real production scenario

Một authorization service lookup tenant configuration hàng chục nghìn lần/second. Query trả một row từ local-region SQL, execution rất nhanh. Profiling cho thấy EF query pipeline chiếm phần CPU đáng kể.

Compiled query + projection có thể giảm CPU, nhưng nếu query thực tế 20–50 ms thì lợi ích thường nhỏ hơn index/query-plan optimization.

## 6. Failure scenario & troubleshooting

**Symptom** → team dùng compiled query khắp nơi nhưng latency gần như không đổi, code khó đọc hơn.

**Evidence** → trace cho thấy database dependency vẫn chiếm 95% request time.

**Hypothesis** → tối ưu sai layer.

**Diagnosis** → profile request breakdown: EF client CPU vs DB execution vs materialization vs network.

**Fix** → xử lý query plan/index/round trips/projection trước; giữ compiled query chỉ cho measured hot path.

**Verification** → benchmark throughput, CPU và allocation trước/sau dưới realistic data volume.

## 7. Common mistakes

- Compiled query cho mọi repository method.
- Bỏ qua N+1 nhưng tối ưu compilation.
- Materialize entity lớn rồi compile query.
- Expression shape thay đổi động làm cache không hiệu quả.
- Benchmark in-memory hoặc local DB nhưng kết luận cho production network.

## 8. Alternatives

Normal LINQ + EF query cache đủ cho đa số workload. Raw SQL/Dapper phù hợp khi cần SQL control rất cao, nhưng tăng maintenance/abstraction cost.

## 9. Trade-offs

### Advantages

- Giảm CPU/overhead trên stable hot query.
- Delegate tái sử dụng rõ ràng.

### Costs / Risks

- Tăng ceremony.
- Ít linh hoạt cho dynamic query.
- Lợi ích thường nhỏ nếu DB mới là bottleneck.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ không trực tiếp “chạy như C#” trên database; EF phải translate.

### Middle

Biết projection, no-tracking và query shape trước khi nghĩ đến compiled query.

### Senior

Dùng profiler/benchmark để xác định EF client overhead thực sự đáng kể.

### Technical Lead / Architect

Đặt performance guideline theo evidence; không biến compiled query thành mandatory abstraction.

## 11. Key takeaway

- EF đã có query-shape cache; compiled query là optimization sâu hơn cho hot path.
- Projection/round-trip/query plan thường quan trọng hơn.
- Chỉ thêm compiled query khi measurement cho thấy CPU/query-compilation overhead thực sự đáng kể.

# 4. SQL Server parameter sniffing: vì sao cùng một query có thể lúc rất nhanh, lúc rất chậm vì execution plan reuse

## 1. What is it?

Parameter sniffing là behavior SQL Server dùng giá trị parameter tại thời điểm compile để estimate cardinality và chọn execution plan; plan đó sau đó có thể được cache và reuse cho parameter khác.

Đây không mặc định là bug. Reuse plan giúp giảm compilation cost. Vấn đề xuất hiện khi data distribution skewed và một plan tốt cho parameter A rất tệ cho parameter B.

## 2. Why does it exist?

Database cần chọn:

- index seek hay scan;
- nested loops hay hash join;
- memory grant bao nhiêu;
- join order nào.

Cardinality estimate phụ thuộc parameter value. Compile mỗi request sẽ tốn CPU, nên engine reuse plan.

## 3. How does it work?

Giả sử 99% orders thuộc tenant nhỏ, 1 tenant enterprise có 20 triệu rows.

```sql
SELECT *
FROM Orders
WHERE TenantId = @TenantId
  AND Status = @Status;
```

Compile lần đầu với tenant nhỏ có thể tạo plan seek + nested loops. Reuse plan đó cho tenant lớn có thể tạo hàng triệu lookups và latency tăng mạnh.

Flow:

```text
first parameter
 -> compile
 -> estimate rows
 -> choose plan
 -> cache plan

next parameter
 -> reuse same plan
 -> actual rows rất khác estimate
 -> bad runtime behavior
```

## 4. Practical implementation

Bắt đầu bằng evidence:

```sql
SET STATISTICS IO, TIME ON;
```

Xem Actual Execution Plan:

- estimated rows;
- actual rows;
- operator choice;
- memory grant;
- spills;
- logical reads.

Không nên ngay lập tức thêm `OPTION (RECOMPILE)` mọi nơi.

Có thể cân nhắc:

```sql
OPTION (RECOMPILE);
```

hoặc query shape khác, filtered index, statistics tốt hơn, hay tách workload skewed.

## 5. Real production scenario

API `/orders?tenantId=...` thường p95 80 ms nhưng thỉnh thoảng nhảy lên 8 giây sau deployment/restart. Incident chỉ xảy ra khi cache plan được “seed” bởi tenant có distribution đặc biệt.

Restart SQL/Application vô tình “fix” vì plan cache thay đổi, khiến root cause khó thấy.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng SQL text có latency variance rất lớn theo parameter hoặc sau plan-cache change.

**Evidence** → estimated vs actual rows lệch nhiều; Query Store cho thấy nhiều runtime profiles; plan reuse.

**Hypothesis** → parameter-sensitive plan.

**Diagnosis** → replay với representative parameters; xem Query Store, actual plan, statistics histogram.

**Fix** → chọn strategy theo workload: recompile có chọn lọc, query split, better indexing/statistics, parameter-sensitive optimization capabilities nếu phù hợp.

**Verification** → test cả small/large tenant parameters và đo CPU/IO/latency.

## 7. Common mistakes

- Gọi mọi slow query là parameter sniffing.
- Clear plan cache trong production như “fix”.
- `OPTION (RECOMPILE)` trên query RPS cao mà không tính compile CPU.
- Optimize cho một parameter duy nhất.
- Chỉ nhìn duration, không nhìn estimated/actual cardinality.

## 8. Alternatives

Dynamic SQL parameterized có thể tạo query shape phù hợp hơn khi optional filters khác nhau. Stored procedure không tự miễn nhiễm parameter sniffing; ad-hoc parameterized query cũng có plan reuse.

## 9. Trade-offs

### Advantages

Plan caching giảm compile CPU và thường hoạt động tốt khi data distribution tương đối đồng đều.

### Costs / Risks

Skewed data có thể khiến một plan không phù hợp cho mọi parameter. Recompile tăng CPU; nhiều plan variants tăng cache/management complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu execution plan là quyết định runtime của database, không chỉ SQL text.

### Middle

Đọc estimated vs actual rows và logical reads.

### Senior

Phân tích data skew, statistics, plan reuse và Query Store.

### Technical Lead / Architect

Thiết kế tenant/data model và query strategy để tránh một query shape phải phục vụ workload có cardinality chênh lệch cực lớn nếu không cần thiết.

## 11. Key takeaway

- Parameter sniffing là consequence của plan reuse + data distribution.
- Chẩn đoán bằng actual plan/Query Store, không bằng restart.
- Fix phải cân bằng execution quality và compilation cost.

# 5. Redis eviction và memory pressure: cache “đầy” không chỉ là lỗi capacity mà còn là correctness và latency problem

## 1. What is it?

Khi Redis đạt `maxmemory`, eviction policy quyết định key nào bị loại để giải phóng memory, hoặc từ chối write nếu policy là `noeviction`.

Ví dụ policy conceptually gồm:

- LRU/LFU-like eviction;
- TTL-based eviction;
- allkeys vs volatile keys;
- noeviction.

Cache correctness phụ thuộc việc application hiểu key có thể biến mất bất kỳ lúc nào.

## 2. Why does it exist?

Redis chạy trong memory hữu hạn. Nếu cache chỉ tăng không giới hạn, OS pressure hoặc OOM có thể giết process. Eviction biến hard capacity thành controlled degradation.

Nhưng nếu application dùng Redis như source of truth trá hình, eviction có thể trở thành data-loss incident.

## 3. How does it work?

```text
SET key
 -> memory below maxmemory? store
 -> memory at limit?
      -> eviction policy selects victim
      -> delete victim
      -> store new key
```

TTL expiration và eviction là hai cơ chế khác nhau. Key có TTL chưa chắc được delete chính xác ngay thời điểm TTL hết; Redis dùng lazy/active expiration mechanisms.

## 4. Practical implementation

Cache-aside phải chịu cache miss:

```csharp
var cached = await _cache.GetStringAsync(key, ct);

if (cached is not null)
    return JsonSerializer.Deserialize<ProductDto>(cached)!;

var product = await _repository.GetProductAsync(id, ct);

if (product is not null)
{
    await _cache.SetStringAsync(
        key,
        JsonSerializer.Serialize(product),
        new DistributedCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
        },
        ct);
}

return product;
```

Business data quan trọng phải nằm ở durable store.

## 5. Real production scenario

E-commerce product cache tăng mạnh sau campaign vì cache key chứa mọi query combination. Redis memory chạm limit, hot keys bị evict liên tục. Hit ratio giảm, SQL traffic tăng gấp 5, khiến database p95 tăng.

Incident nhìn ban đầu giống “database chậm”, nhưng root cause là cache churn.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis latency bình thường nhưng DB load và cache misses tăng mạnh.

**Evidence** → `evicted_keys` tăng, memory gần `maxmemory`, hit ratio giảm, key cardinality bùng nổ.

**Hypothesis** → eviction churn do key design/TTL/capacity.

**Diagnosis** → inspect memory usage, top key prefixes, object sizes, traffic patterns.

**Fix** → sửa key cardinality, TTL, payload size; tăng capacity nếu justified; chọn eviction policy đúng workload.

**Verification** → load test campaign pattern và theo dõi hit ratio + `evicted_keys` + DB traffic.

## 7. Common mistakes

- Lưu session/business state không recover được vào cache configured eviction.
- TTL tất cả key cùng một thời điểm gây synchronized expiry.
- Cache payload quá lớn.
- Không monitor `evicted_keys`.
- Tăng memory vô hạn thay vì sửa key explosion.

## 8. Alternatives

`IMemoryCache` đơn giản hơn cho single instance và data chấp nhận per-instance divergence. Database/materialized view phù hợp cho durable/shared state. CDN phù hợp cho public HTTP content.

## 9. Trade-offs

### Advantages

- Controlled behavior dưới memory limit.
- Redis tiếp tục phục vụ cache thay vì crash vì uncontrolled growth.

### Costs / Risks

- Hit ratio có thể collapse.
- Eviction policy sai phá workload quan trọng.
- Capacity planning và observability bắt buộc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache key có thể biến mất và application phải chịu miss.

### Middle

Thiết kế TTL/key và implement cache-aside đúng.

### Senior

Theo dõi eviction, hit ratio, memory fragmentation và downstream impact.

### Technical Lead / Architect

Quyết định Redis đang là optional accelerator hay critical dependency; nếu critical thì cần reliability/capacity design tương ứng.

## 11. Key takeaway

- Eviction là bình thường trong bounded cache.
- Cache miss phải là supported path.
- Memory pressure có thể lan thành database incident qua hit-ratio collapse.

# 6. Modular Monolith module boundaries: chia ownership, transaction và dependency mà chưa trả giá vận hành của microservices

## 1. What is it?

Modular Monolith là một deployable application duy nhất nhưng code/domain được chia thành modules có boundary rõ về responsibility, data ownership và dependency.

Nó không chỉ là folder:

```text
Monolith
├─ Orders
├─ Inventory
├─ Billing
└─ Identity
```

Boundary thật sự phải thể hiện ở public contracts, dependency direction và quyền sở hữu dữ liệu.

## 2. Why does it exist?

Layered monolith lớn dễ thành “big ball of mud”: module nào cũng query table của module khác, gọi service internals và share entity models.

Microservices có thể ép boundary bằng network/process nhưng thêm deployment, observability, messaging, retries, eventual consistency.

Modular Monolith tìm cách lấy phần lớn lợi ích boundary trước khi cần distributed systems cost.

## 3. How does it work?

Một module nên expose API/application contracts, không expose mọi internal repository/entity.

```text
Orders module
  owns Orders tables
  exposes PlaceOrder / GetOrder

Inventory module
  owns Stock tables
  exposes Reserve / Release
```

Cross-module communication trong process có thể synchronous. Transaction xuyên module vẫn technically có thể dùng một DB transaction, nhưng cần xem đó là intentional coupling hay convenience đang phá ownership.

## 4. Practical implementation

Contract:

```csharp
public interface IInventoryModule
{
    Task<ReservationResult> ReserveAsync(
        Guid productId,
        int quantity,
        CancellationToken ct);
}
```

Orders không trực tiếp inject `InventoryDbContext`.

Với EF Core, có thể dùng separate `DbContext` per module ngay cả khi cùng SQL Server database/schema separation.

## 5. Real production scenario

Enterprise platform có HR, Timesheets và Approvals. Ban đầu mọi feature dùng chung `AppDbContext`. Sau vài năm, Approval query trực tiếp Timesheet tables và HR service mutate approval state.

Tách thành modules trước giúp xác định ownership. Sau này nếu Timesheets cần scale/deploy độc lập, extraction sang service dễ hơn vì dependency đã được thu hẹp.

## 6. Failure scenario & troubleshooting

**Symptom** → sửa schema một module làm hàng chục unrelated feature fail.

**Evidence** → cross-module table queries/imports dày đặc; cyclic project references; shared “Common” chứa domain logic.

**Hypothesis** → boundary chỉ tồn tại trong folder structure.

**Diagnosis** → dependency graph, DB access map, ownership map.

**Fix** → define module contracts, cấm cross-context direct table access, move invariants về owner module.

**Verification** → architecture tests + build dependency rules + integration tests qua public contracts.

## 7. Common mistakes

- Mỗi folder gọi là “module” nhưng share entities/repositories.
- Tạo event bus nội bộ cho mọi call dù direct method đủ.
- Split module theo technical layer thay vì business capability.
- “SharedKernel” phình thành nơi chứa mọi thứ.
- Microservices hóa trước khi boundary trong monolith còn chưa rõ.

## 8. Alternatives

Simple layered monolith phù hợp hệ thống nhỏ. Microservices phù hợp khi independent deployment/scale/ownership thật sự cần và team chịu được operational complexity.

## 9. Trade-offs

### Advantages

- Boundary rõ hơn mà không cần network.
- Deployment/testing đơn giản hơn microservices.
- Có thể dùng transaction local dễ hơn.

### Costs / Risks

- Boundary cần discipline vì runtime không ép mạnh.
- Shared database dễ tạo backdoor coupling.
- Extraction sau này vẫn cần migration work.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business responsibility chứ không chỉ namespace.

### Middle

Tôn trọng public contract và ownership.

### Senior

Phân tích coupling, transaction boundary và data access leakage.

### Technical Lead / Architect

Quyết định boundary nào cần physical separation và boundary nào chỉ cần logical isolation; tránh distributed architecture khi chưa có business/operational pressure.

## 11. Key takeaway

- Modular Monolith là boundary discipline trong một deployment unit.
- Data ownership quan trọng hơn folder layout.
- Microservices chỉ đáng trả giá khi isolation/deployment/scale requirement thực sự cần.

# 7. Azure Functions + Service Bus poison messages: retry, dead-letter và idempotency khi một message không thể xử lý thành công

## 1. What is it?

Poison message là message liên tục thất bại và không thể hoàn tất bằng retry thông thường. Với Azure Service Bus-triggered Azure Functions, message có delivery count; sau khi vượt retry/delivery policy, nó có thể vào Dead-Letter Queue (DLQ).

DLQ không phải “thùng rác”. Nó là operational queue chứa work cần investigation/recovery.

## 2. Why does it exist?

At-least-once delivery nghĩa là message có thể được giao lại. Retry transient failure là tốt; retry permanent failure vô hạn là retry storm.

Ví dụ permanent failures:

- schema version không hỗ trợ;
- missing required business data;
- malformed payload;
- downstream reject deterministic.

## 3. How does it work?

```text
Message
 -> Function
 -> success -> complete
 -> transient failure -> abandon/retry
 -> repeated failure
 -> MaxDeliveryCount reached
 -> DLQ
```

Duplicate delivery vẫn có thể xảy ra trước hoặc sau crash, vì vậy handler phải idempotent.

## 4. Practical implementation

```csharp
[Function(nameof(ProcessOrder))]
public async Task Run(
    [ServiceBusTrigger("orders", Connection = "ServiceBus")]
    ServiceBusReceivedMessage message,
    ServiceBusMessageActions actions,
    CancellationToken ct)
{
    var command = message.Body.ToObjectFromJson<OrderCommand>();

    if (!await _inbox.TryStartAsync(message.MessageId, ct))
    {
        await actions.CompleteMessageAsync(message, ct);
        return;
    }

    await _handler.ProcessAsync(command, ct);
    await _inbox.MarkCompletedAsync(message.MessageId, ct);

    await actions.CompleteMessageAsync(message, ct);
}
```

Malformed message có thể dead-letter explicitly với reason phù hợp thay vì throw nhiều lần.

## 5. Real production scenario

Notification function nhận message có email template ID đã bị xóa. Mỗi retry đều fail deterministic. Nếu retry nhanh 10 lần cho hàng nghìn messages, dependency/logging cost tăng và queue backlog lan sang message hợp lệ.

Dead-letter sớm với reason “TemplateNotFound” giúp isolate và sửa data/workflow.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog tăng, Function executions tăng nhưng throughput success giảm.

**Evidence** → delivery count cao, repeated exception signature, DLQ growth.

**Hypothesis** → poison messages hoặc downstream permanent failure.

**Diagnosis** → group failures theo exception/reason/schema version; inspect representative DLQ messages.

**Fix** → phân loại transient/permanent; explicit DLQ permanent failures; fix producer/consumer contract; replay có kiểm soát sau remediation.

**Verification** → poison test message phải vào DLQ đúng reason; transient dependency failure phải retry rồi success.

## 7. Common mistakes

- Retry mọi exception như nhau.
- DLQ message nhưng không có alert/process xử lý.
- Replay toàn DLQ sau fix mà không kiểm tra idempotency.
- Dùng message body chứa secret/PII rồi log toàn payload.
- Handler side effect không idempotent.

## 8. Alternatives

Worker Service với Service Bus SDK cho control lifecycle chi tiết hơn. Storage Queue đơn giản hơn nhưng feature set khác. Nếu workflow synchronous và failure model đơn giản, messaging có thể là unnecessary complexity.

## 9. Trade-offs

### Advantages

- Isolate bad messages.
- Queue tiếp tục xử lý message hợp lệ.
- Có audit surface cho recovery.

### Costs / Risks

- DLQ cần operational ownership.
- Replay logic phức tạp.
- Idempotency state tăng storage/maintenance cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry không phải lúc nào cũng giải quyết được failure.

### Middle

Biết DLQ, delivery count và idempotent handler.

### Senior

Phân loại transient/permanent failure, thiết kế replay và telemetry.

### Technical Lead / Architect

Quy định ownership/SLO của queue và DLQ; quyết định khi nào message contract/versioning cần evolve.

## 11. Key takeaway

- Retry chỉ dành cho failure có khả năng tự hồi phục.
- DLQ phải có alert, diagnosis và replay process.
- At-least-once delivery yêu cầu idempotency.

# 8. Docker multi-stage build + container startup health: image nhỏ hơn chưa đủ nếu process lifecycle và health semantics sai

## 1. What is it?

Multi-stage build dùng nhiều `FROM` stages để compile/publish application trong SDK image rồi copy artifact sang runtime image nhỏ hơn.

```text
SDK image -> restore/build/publish
                |
                v
runtime image <- published output only
```

Image optimization chỉ là một phần. Container production còn cần startup, signal handling, readiness/liveness và configuration đúng.

## 2. Why does it exist?

Nếu deploy cả SDK, source, NuGet cache và build tools vào production image:

- image lớn;
- pull/start chậm;
- attack surface tăng;
- artifact không rõ ràng.

Multi-stage build tách build environment khỏi runtime artifact.

## 3. How does it work?

Ví dụ:

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

COPY . .
RUN dotnet restore
RUN dotnet publish -c Release -o /app/publish --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

Docker cache layer ordering ảnh hưởng build speed. Trong production, PID 1 phải nhận termination signal để ASP.NET Core graceful shutdown.

## 4. Practical implementation

Thường copy project files/restore trước để cache tốt hơn:

```dockerfile
COPY MyApi/*.csproj MyApi/
RUN dotnet restore MyApi/MyApi.csproj

COPY . .
RUN dotnet publish MyApi/MyApi.csproj \
    -c Release \
    -o /app/publish \
    --no-restore
```

Health endpoint:

```csharp
builder.Services.AddHealthChecks()
    .AddDbContextCheck<AppDbContext>();

app.MapHealthChecks("/health/ready");
```

Readiness không nên báo healthy trước khi application thật sự có thể serve critical traffic.

## 5. Real production scenario

Deployment lên Kubernetes có image tối ưu chỉ 200 MB, nhưng app mất 25 giây warm-up. Readiness probe bắt đầu quá sớm và fail liên tục; liveness probe kill container trước khi startup hoàn tất → `CrashLoopBackOff`.

Root cause không phải image size mà là health semantics.

## 6. Failure scenario & troubleshooting

**Symptom** → container restart loop hoặc rollout không đạt available replicas.

**Evidence** → `kubectl describe pod`, probe failure, container logs, termination reason.

**Hypothesis** → startup/readiness/liveness thresholds sai hoặc process không handle signal.

**Diagnosis** → đo startup time, dependency readiness, probe timing, exit code.

**Fix** → startup probe/readiness phù hợp, không để liveness phụ thuộc external service dễ chập chờn, propagate shutdown.

**Verification** → cold-start rollout + dependency degradation test.

## 7. Common mistakes

- Dùng SDK image làm runtime.
- `COPY . .` trước restore khiến cache invalidated mọi build.
- Health check database làm liveness fail khi DB chập chờn.
- Hardcode secrets trong image.
- Container chạy được local nhưng không test SIGTERM/shutdown.

## 8. Alternatives

Azure App Service không bắt buộc container nếu platform-managed runtime đủ. Container Apps/Kubernetes phù hợp khi cần container orchestration features; đừng containerize chỉ vì trend.

## 9. Trade-offs

### Advantages

- Reproducible artifact.
- Runtime image nhỏ và attack surface thấp hơn.
- Portable deployment unit.

### Costs / Risks

- Build/image lifecycle cần ownership.
- Health/network/storage semantics phức tạp hơn direct App Service deployment.
- Container không tự giải quyết architecture/reliability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu image là immutable artifact, container là running process instance.

### Middle

Viết multi-stage Dockerfile và đọc container logs/exit code.

### Senior

Tối ưu cache layers, startup/shutdown, probes và resource behavior.

### Technical Lead / Architect

Quyết định containerization có đem lại deployment/operational value đủ lớn hay platform-managed deployment đơn giản hơn.

## 11. Key takeaway

- Multi-stage build giảm runtime artifact, không thay thế lifecycle engineering.
- Readiness/liveness phải phản ánh đúng semantics.
- Container production phải được test cả startup, shutdown và dependency failure.

# 9. Playwright deterministic waiting: loại bỏ flaky E2E test bằng state-based synchronization thay vì `Task.Delay`

## 1. What is it?

Flaky E2E test là test pass/fail không deterministic dù application code không đổi. Một nguồn lớn là timing assumption: test “đợi 2 giây” rồi hy vọng UI đã sẵn sàng.

Playwright ưu tiên auto-waiting và assertions chờ condition thay vì fixed sleeps.

## 2. Why does it exist?

Browser application có nhiều asynchronous layers:

```text
click
 -> JS handler
 -> network request
 -> server
 -> response
 -> state update
 -> render
```

Thời gian thay đổi theo CPU, CI runner, network và backend load. `Task.Delay(2000)` chỉ encode một guess.

## 3. How does it work?

Playwright locator/action thường đợi element ở actionable state. Assertions như `ToBeVisibleAsync` polling condition trong timeout.

```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();

await Expect(
    page.GetByText("Saved successfully"))
    .ToBeVisibleAsync();
```

Nếu cần chờ API:

```csharp
var responseTask = page.WaitForResponseAsync(
    r => r.Url.Contains("/api/orders") && r.Status == 200);

await page.GetByRole(AriaRole.Button, new() { Name = "Submit" }).ClickAsync();

await responseTask;
```

## 4. Practical implementation

Không:

```csharp
await page.ClickAsync("#save");
await Task.Delay(3000);
Assert.Contains("Saved", await page.ContentAsync());
```

Nên:

```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();

await Expect(page.GetByTestId("save-status"))
    .ToHaveTextAsync("Saved");
```

Test IDs chỉ nên dùng khi semantic locator không đủ ổn định.

## 5. Real production scenario

Test checkout pass local nhưng fail 10–15% trên CI. Team tăng delay từ 1 lên 5 giây làm pipeline chậm gấp nhiều lần nhưng vẫn fail khi runner contention cao.

Root cause: test chờ thời gian, không chờ state “payment request complete + confirmation rendered”.

## 6. Failure scenario & troubleshooting

**Symptom** → rerun failed test thì pass.

**Evidence** → screenshot/trace cho thấy assertion chạy trước UI update; network call vẫn pending.

**Hypothesis** → race condition trong test synchronization.

**Diagnosis** → Playwright trace viewer, network logs, DOM snapshot, action timeline.

**Fix** → wait theo observable state/response; loại bỏ arbitrary delay; kiểm soát test data.

**Verification** → chạy test lặp nhiều lần và parallel trên CI.

## 7. Common mistakes

- `Task.Delay` như synchronization primitive.
- Selector dựa vào brittle CSS structure.
- Shared test data gây race giữa tests.
- Mock quá nhiều nên E2E không còn test integration thật.
- Retry test để che flakiness thay vì tìm root cause.

## 8. Alternatives

Integration/API tests nhanh hơn và nên bảo vệ nhiều business behavior không cần browser. Unit tests phù hợp pure logic. E2E chỉ nên cover critical user journeys và integration boundaries.

## 9. Trade-offs

### Advantages

- E2E deterministic hơn.
- Pipeline nhanh hơn khi bỏ unnecessary waits.
- Trace dễ điều tra hơn.

### Costs / Risks

- Vẫn là test đắt, phụ thuộc nhiều systems.
- Cần environment/test-data discipline.
- Overuse E2E làm feedback loop chậm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu “đợi đủ lâu” không đồng nghĩa deterministic.

### Middle

Dùng locator/assertion auto-waiting và trace.

### Senior

Tách UI race, backend race và test-data race; xây test pyramid theo risk.

### Technical Lead / Architect

Quyết định behavior nào thật sự cần E2E và đặt quality gate dựa trên deterministic signal thay vì retry pass.

## 11. Key takeaway

- Chờ state, không chờ thời gian.
- Flaky test là reliability bug của test suite.
- E2E nên ít nhưng bảo vệ critical integration journeys.

# 10. Optimizely CMS cache invalidation trên multi-instance: content publish, stale cache và consistency giữa các node

## 1. What is it?

CMS thường cache content để tránh đọc database/content store cho mọi request. Trong môi trường multi-instance, mỗi application node có thể giữ local cache riêng.

Khi editor publish content, hệ thống phải đảm bảo các node khác biết content version cũ không còn hợp lệ.

Mental model:

```text
Editor publishes
      -> content persisted
      -> invalidation event
      -> Node A cache evicts
      -> Node B cache evicts
      -> Node C cache evicts
```

## 2. Why does it exist?

CMS read traffic thường lớn hơn write traffic rất nhiều. Cache giúp page rendering nhanh. Nhưng cache local tạo consistency problem: nếu invalidation không propagate, user có thể thấy nội dung khác nhau tùy node/load balancer.

## 3. How does it work?

Optimizely CMS có caching/event mechanisms phục vụ content updates giữa instances tùy hosting/configuration/version. Engineering concern rộng hơn là:

- source of truth nằm ở content store;
- cache chỉ là derived state;
- publish event phải invalidate đúng key/dependencies;
- multi-node communication phải reliable đủ cho freshness requirement.

CDN phía trước có thể tạo thêm một cache layer nữa.

## 4. Practical implementation

Application-level code không nên cache content vô hạn bằng arbitrary static dictionary.

Nếu thêm custom cache:

```csharp
var key = $"article:{contentReference.ID}:{language}";

if (!_cache.TryGetValue(key, out ArticleViewModel? model))
{
    var content = _contentLoader.Get<ArticlePage>(contentReference);
    model = Map(content);

    _cache.Set(
        key,
        model,
        TimeSpan.FromMinutes(5));
}
```

Nhưng custom cache phải có invalidation owner. Nếu content publish phải visible ngay, chỉ TTL 5 phút có thể không đạt requirement.

## 5. Real production scenario

Marketing website chạy 4 App Service instances sau Akamai. Editor publish hero banner mới.

- Node A nhận invalidation.
- Node B giữ custom cache cũ.
- CDN cũng giữ HTML cũ 10 phút.

User refresh thấy lúc banner mới, lúc cũ tùy edge/node. Team đổ lỗi cho CMS nhưng thực tế có ba cache boundaries.

## 6. Failure scenario & troubleshooting

**Symptom** → editor thấy publish thành công nhưng end users nhận stale content không nhất quán.

**Evidence** → request qua từng origin instance trả khác nhau; CDN headers cho thấy cache hit; app cache key/version khác.

**Hypothesis** → invalidation propagation hoặc CDN purge/cache key issue.

**Diagnosis** → bypass CDN, pin request vào từng node, inspect content version and cache state, correlate publish timestamp.

**Fix** → dùng CMS-supported invalidation, tránh custom local cache thiếu propagation, thiết kế CDN TTL/purge theo content criticality.

**Verification** → automated publish test rồi probe nhiều origin nodes/edge locations.

## 7. Common mistakes

- Cache CMS content ở static singleton mà không invalidation.
- Chỉ purge CDN nhưng origin node vẫn stale.
- Chỉ clear origin cache nhưng browser/CDN vẫn giữ response.
- Cache key thiếu language/market/variant.
- TTL dài cho content business yêu cầu publish tức thời.

## 8. Alternatives

Nếu traffic thấp, không thêm custom cache có thể đơn giản và đủ nhanh. CDN phù hợp public page/static content. Distributed cache có thể giảm per-node divergence nhưng thêm network dependency và vẫn cần invalidation semantics.

## 9. Trade-offs

### Advantages

- Cache giảm content-store load và rendering latency.
- CDN giảm origin traffic mạnh.

### Costs / Risks

- Nhiều cache layer làm freshness/debugging phức tạp.
- Invalidation là distributed consistency problem.
- Purge/fine-grained dependency tracking có operational cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu publish vào database không đồng nghĩa mọi cache lập tức thấy version mới.

### Middle

Biết phân biệt browser/CDN/application/CMS cache và kiểm tra từng layer.

### Senior

Thiết kế key, invalidation, multilingual/variant semantics và debug multi-node stale content.

### Technical Lead / Architect

Định nghĩa freshness SLA cho từng loại content, chọn cache layer tối thiểu cần thiết và xác định ai sở hữu invalidation/purge.

## 11. Key takeaway

- CMS caching là consistency problem khi scale nhiều node.
- Mỗi cache layer cần owner và invalidation strategy.
- Freshness requirement phải được định nghĩa trước khi chọn TTL/purge complexity.
