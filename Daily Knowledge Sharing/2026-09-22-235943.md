# 1. .NET `ArrayPool<T>`: giảm allocation nhưng phải quản lý ownership và dữ liệu cũ trong buffer

## 1. What is it?

`ArrayPool<T>` là pool các array có thể tái sử dụng. Thay vì liên tục `new byte[largeSize]`, code `Rent` một buffer rồi `Return` sau khi dùng. Mental model quan trọng: caller **mượn** memory, không sở hữu vĩnh viễn nó.

## 2. Why does it exist?

Hot path như parsing, compression, serialization và file processing có thể tạo lượng lớn temporary arrays. Allocation lớn làm tăng GC pressure, đặc biệt khi buffer đủ lớn để đi vào LOH. Pooling đổi chi phí allocation/GC thành lifecycle management.

## 3. How does it work?

```text
ArrayPool
  | Rent(64 KB)
  v
Caller uses buffer
  |
  | Return
  v
ArrayPool -> reused by another caller
```

Array được trả về có thể lớn hơn kích thước yêu cầu và nội dung cũ không mặc định được xóa.

## 4. Practical implementation

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
    await ProcessAsync(buffer.AsMemory(0, read), ct);
}
finally
{
    pool.Return(buffer, clearArray: true);
}
```

`clearArray: true` đáng cân nhắc khi buffer chứa dữ liệu nhạy cảm; nó có CPU cost.

## 5. Real production scenario

Service xử lý hàng nghìn ảnh/file chunks mỗi phút. Profiler cho thấy allocation rate cao và Gen2/LOH collections. Pooling buffer ở đúng hot path giảm GC pause mà không thay đổi business flow.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu request trước xuất hiện trong log/output request sau. **Evidence** → code đọc toàn bộ rented array thay vì phần thực tế đã ghi. **Diagnosis** → hiểu sai ownership/length. **Fix** → luôn track logical length, clear khi có dữ liệu nhạy cảm. **Verification** → concurrency tests và memory profiling.

## 7. Common mistakes

Không `Return` trong `finally`; dùng buffer sau khi đã `Return`; giả định array có đúng requested length; pool mọi allocation dù không đo được benefit; giữ rented buffer quá lâu.

## 8. Alternatives

Array allocation thông thường đơn giản và thường đủ tốt. `MemoryPool<T>` phù hợp một số pipeline cần memory owner abstraction. `Span<T>` giúp slice không copy nhưng không tự giải quyết allocation ownership.

## 9. Trade-offs

### Advantages
Giảm allocation và GC pressure ở hot path.

### Costs / Risks
Ownership phức tạp hơn, nguy cơ data leakage/use-after-return và retained memory trong pool.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu Rent/Return và logical length.
### Middle
Dùng `try/finally`, benchmark allocation và xử lý sensitive data.
### Senior
Phân tích GC/LOH trước khi pooling và review lifetime safety.
### Technical Lead / Architect
Quyết định pooling có đáng complexity hay bottleneck thực tế nằm ở I/O/database.

## 11. Key takeaway

- Pooling tối ưu allocation, không tối ưu mọi workload.
- Buffer được mượn có thể chứa dữ liệu cũ và có kích thước lớn hơn yêu cầu.
- Chỉ dùng sau khi measurement chứng minh allocation/GC là bottleneck.

# 2. ASP.NET Core rate limiting: bảo vệ capacity thay vì chỉ “chặn bot”

## 1. What is it?

Rate limiting kiểm soát lượng work một client/tenant/API route được phép đưa vào hệ thống trong một khoảng thời gian. Mục tiêu production là bảo vệ finite capacity của application và downstream dependencies.

## 2. Why does it exist?

Một API có thể đúng chức năng nhưng sụp khi một tenant tạo traffic spike, retry storm hoặc expensive endpoint bị gọi quá nhiều. Autoscaling không phản ứng tức thời và database thường scale khác web tier.

## 3. How does it work?

```text
Client -> limiter -> accepted -> API -> DB
                  \-> rejected (429)
```

Fixed window, sliding window, token bucket và concurrency limiter giải quyết các pressure khác nhau. Partition key có thể là tenant, user, API key hoặc route.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddFixedWindowLimiter("writes", o =>
    {
        o.PermitLimit = 100;
        o.Window = TimeSpan.FromMinutes(1);
        o.QueueLimit = 0;
    });
});

app.UseRateLimiter();
```

Production policy nên partition theo identity/business boundary thay vì một global counter tùy tiện.

## 5. Real production scenario

Bulk-import client vô tình retry POST liên tục khi timeout. API instances vẫn sống nhưng SQL connection pool bão hòa. Limiter ở write endpoint chặn excess traffic trước khi mỗi request tiêu tốn DB connection.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều 429 từ khách hàng bình thường. **Evidence** → metrics cho thấy một global policy chia chung quota giữa tenants. **Diagnosis** → partition boundary sai. **Fix** → per-tenant policy và quota phù hợp workload. **Verification** → load test nhiều tenants đồng thời.

## 7. Common mistakes

Dùng IP làm identity duy nhất sau NAT; không trả `Retry-After` khi phù hợp; rate-limit sau expensive work; xem limiter như DDoS protection hoàn chỉnh; không đo rejected requests.

## 8. Alternatives

API Gateway/CDN/WAF có thể limit ở edge. Application-level limiter hiểu tenant/business semantics tốt hơn. Concurrency limit phù hợp khi vấn đề là số expensive operations đang chạy hơn là request count.

## 9. Trade-offs

### Advantages
Bảo vệ capacity, fairness và downstream systems.
### Costs / Risks
Sai quota gây false rejection; distributed/global quota phức tạp; cần observability và client retry contract.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu 429 và quota.
### Middle
Implement policy và test rejection behavior.
### Senior
Chọn algorithm/partition theo bottleneck và retry semantics.
### Technical Lead / Architect
Xác định capacity budget giữa edge, API và downstream dependencies.

## 11. Key takeaway

- Rate limiting là capacity control.
- Partition key quan trọng ngang permit count.
- Limit càng gần trước expensive work càng bảo vệ hệ thống tốt hơn.

# 3. EF Core split query: tránh Cartesian explosion nhưng chấp nhận nhiều database round trips

## 1. What is it?

Khi query nhiều collection navigation bằng `Include`, single SQL query có thể tạo Cartesian multiplication. `AsSplitQuery()` cho EF Core tải related collections bằng nhiều SQL queries rồi fix-up object graph phía client.

## 2. Why does it exist?

Một Order có 20 Lines và 10 Notes. JOIN cả hai collections có thể tạo 200 result rows cho một Order, lặp lại parent columns và tăng network/materialization cost.

## 3. How does it work?

```text
Single query: Order JOIN Lines JOIN Notes -> row multiplication
Split query : Orders
              + Lines for Orders
              + Notes for Orders
```

Split query đổi row explosion lấy additional round trips và consistency considerations giữa các queries.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .Where(x => x.Id == id)
    .SingleAsync(ct);
```

Nếu endpoint chỉ cần DTO, projection thường tốt hơn việc load cả graph.

## 5. Real production scenario

Order detail API chậm sau khi thêm Promotions collection. Generated SQL trả hàng chục nghìn rows cho vài chục entities. Split query giảm transferred rows đáng kể; sau đó team còn projection để bỏ fields không cần.

## 6. Failure scenario & troubleshooting

**Symptom** → đổi sang split query nhưng latency tăng ở môi trường DB xa. **Evidence** → trace cho thấy nhiều sequential DB round trips. **Diagnosis** → network latency lớn hơn lợi ích giảm row duplication. **Fix** → projection hoặc query shape khác. **Verification** → đo rows, bytes, round trips và p95 trước/sau.

## 7. Common mistakes

Bật split query global mà không đo; `Include` mọi navigation; không xem generated SQL; nghĩ split query giải quyết N+1; bỏ qua consistency khi dữ liệu thay đổi giữa các queries.

## 8. Alternatives

DTO projection, explicit queries, single query khi cardinality nhỏ hoặc raw SQL cho read model đặc biệt.

## 9. Trade-offs

### Advantages
Giảm Cartesian explosion và duplicated payload.
### Costs / Risks
Nhiều round trips, có thể quan sát snapshots khác nhau nếu concurrent writes, query orchestration phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `Include` có thể làm SQL result lớn hơn object count.
### Middle
Dùng `ToQueryString`, projection và `AsSplitQuery` có chủ đích.
### Senior
Đo cardinality, network cost và consistency requirement.
### Technical Lead / Architect
Quyết định read model/API contract thay vì để ORM graph quyết định data access.

## 11. Key takeaway

- Split query là trade-off giữa row multiplication và round trips.
- Projection thường là lựa chọn tốt nhất cho read-only API.
- Luôn đo generated SQL và cardinality thật.

# 4. SQL Server covering index: giảm lookup nhưng tăng write amplification và storage

## 1. What is it?

Covering index chứa đủ columns để SQL Server trả kết quả query từ index mà không cần quay lại clustered index/heap để lấy columns còn thiếu. Key columns phục vụ seek/order; `INCLUDE` thường chứa output columns.

## 2. Why does it exist?

Một nonclustered index có thể tìm đúng rows nhanh nhưng mỗi row lại cần Key Lookup để lấy thêm dữ liệu. Với nhiều rows, hàng nghìn random lookups có thể trở thành bottleneck.

## 3. How does it work?

```text
Query -> nonclustered seek -> Key Lookup -> base row

Covering index:
Query -> nonclustered seek -> result
```

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_Customer_CreatedAt
ON dbo.Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, Total);
```

Phù hợp cho query dạng:

```sql
SELECT CreatedAt, Status, Total
FROM dbo.Orders
WHERE CustomerId = @customerId
ORDER BY CreatedAt DESC;
```

## 5. Real production scenario

Customer history endpoint có p95 cao. Execution plan cho thấy seek tốt nhưng hàng chục nghìn Key Lookups. Sau khi xác nhận access pattern ổn định, `INCLUDE` giảm logical reads đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → read nhanh hơn nhưng write latency và storage tăng. **Evidence** → index usage cho thấy nhiều indexes rộng cùng overlap. **Diagnosis** → over-indexing. **Fix** → consolidate/drop unused indexes dựa trên workload evidence. **Verification** → đo reads, writes, index size và maintenance time.

## 7. Common mistakes

Đưa mọi column vào INCLUDE; thêm index cho từng slow query; bỏ qua selectivity/order; không kiểm tra statistics; giữ duplicate indexes.

## 8. Alternatives

Thay query/projection, filtered index, clustered key design hoặc precomputed read model tùy workload.

## 9. Trade-offs

### Advantages
Giảm lookups và I/O cho read path quan trọng.
### Costs / Risks
Tốn disk/memory, tăng write amplification, backup/maintenance cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu index không miễn phí.
### Middle
Đọc execution plan và phân biệt key/include columns.
### Senior
Đánh giá lookup count, selectivity, write cost và overlap.
### Technical Lead / Architect
Cân bằng read SLA với write/storage/operations của toàn workload.

## 11. Key takeaway

- Covering index tối ưu access pattern cụ thể.
- “Ít lookup hơn” phải được cân với write amplification.
- Execution plan và workload evidence phải đi trước index change.

# 5. Redis hot key: một key phổ biến có thể phá khả năng scale của cả cache cluster

## 1. What is it?

Hot key là key nhận tỷ lệ traffic quá lớn so với phần còn lại. Dù Redis cluster có nhiều nodes, một key thường nằm trên một shard, nên traffic không tự chia đều chỉ vì cluster lớn hơn.

## 2. Why does it exist?

Caching thường được thêm để giảm database load, nhưng skewed access pattern có thể chuyển bottleneck từ DB sang một Redis node/network path.

## 3. How does it work?

```text
100k req/s
   |
   v
key: homepage:global
   |
   v
Shard 3  << HOT
```

Hash partitioning phân phối keys, không phân phối một key duy nhất qua mọi shard.

## 4. Practical implementation

Với immutable/small data cực nóng, có thể thêm local cache ngắn phía trước Redis:

```csharp
if (memoryCache.TryGetValue(key, out ProductSummary? value))
    return value;

value = await redisCache.GetAsync<ProductSummary>(key, ct);
memoryCache.Set(key, value, TimeSpan.FromSeconds(5));
return value;
```

Phải chấp nhận freshness window rõ ràng.

## 5. Real production scenario

Homepage config được mọi request đọc từ cùng Redis key. Campaign traffic tăng 10x; Redis node chứa key đạt network/CPU ceiling trong khi nodes khác nhàn.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis latency tăng nhưng cluster average CPU bình thường. **Evidence** → per-node metrics và key frequency cho thấy một shard/key vượt trội. **Diagnosis** → hot-key skew. **Fix** → local cache, request coalescing hoặc redesign access pattern. **Verification** → per-node throughput cân hơn và p99 giảm.

## 7. Common mistakes

Chỉ scale thêm shards; TTL đồng loạt gây stampede; replicate key thủ công mà không có consistency design; cache data personalized dưới shared key.

## 8. Alternatives

`IMemoryCache` nếu consistency cross-instance không cần thiết; CDN cho public HTTP data; database trực tiếp nếu cache không tạo giá trị đủ lớn.

## 9. Trade-offs

### Advantages
Redis giảm source load và latency.
### Costs / Risks
Hot keys, network dependency, invalidation và hidden critical dependency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu cluster chia keys chứ không tự chia traffic của một key.
### Middle
Đo hit rate/latency và thiết kế TTL/key hợp lý.
### Senior
Phân tích skew, stampede và fallback.
### Technical Lead / Architect
Quyết định cache layer nào nên tồn tại và freshness/availability contract.

## 11. Key takeaway

- Scale-out Redis không tự chữa hot key.
- Quan sát per-node/per-key quan trọng hơn cluster average.
- Cache hierarchy chỉ hợp lý khi freshness trade-off được chấp nhận.

# 6. Saga và compensating transaction: xử lý business workflow khi không có distributed ACID transaction

## 1. What is it?

Saga chia một business transaction dài thành nhiều local transactions. Nếu bước sau thất bại, hệ thống thực hiện compensating actions cho những bước trước khi business cho phép.

Compensation không phải database rollback; nó là một **business action mới**.

## 2. Why does it exist?

Trong distributed systems, Order, Payment và Inventory có thể sở hữu database riêng. Giữ một ACID transaction xuyên services khó vận hành, coupling cao hoặc không được infrastructure hỗ trợ.

## 3. How does it work?

```text
Create Order -> Reserve Inventory -> Charge Payment
                      |                  X
                      v
             Release Inventory <- Cancel Order
```

Orchestration có coordinator quyết định bước tiếp; choreography dùng events để services phản ứng. Cả hai cần idempotency và durable state.

## 4. Practical implementation

```csharp
public async Task CompensateAsync(OrderSaga saga, CancellationToken ct)
{
    if (saga.InventoryReserved)
        await inventory.ReleaseAsync(saga.OrderId, ct);

    if (saga.OrderCreated)
        await orders.MarkCancelledAsync(saga.OrderId, ct);
}
```

Mỗi command/compensation cần idempotent vì delivery/retry có thể lặp.

## 5. Real production scenario

Checkout reserve stock thành công nhưng payment provider timeout. Không thể biết ngay charge có thành công hay không. Saga chuyển trạng thái `PaymentUnknown`, reconcile trước khi release stock thay vì đoán timeout = failure.

## 6. Failure scenario & troubleshooting

**Symptom** → compensation chạy hai lần và inventory tăng sai. **Evidence** → duplicate message delivery. **Diagnosis** → compensation không idempotent. **Fix** → inbox/deduplication và state transition có concurrency guard. **Verification** → replay cùng message nhiều lần mà state không đổi sai.

## 7. Common mistakes

Coi timeout là failure chắc chắn; compensation không idempotent; không lưu saga state; chain synchronous calls dài; giả định mọi action đều đảo ngược được.

## 8. Alternatives

Local ACID transaction tốt hơn nếu data có thể cùng ownership boundary. Outbox giải quyết atomic database-change/message-publication nhưng không thay Saga cho multi-step business compensation.

## 9. Trade-offs

### Advantages
Cho phép independent data ownership và resilient workflow.
### Costs / Risks
Eventual consistency, state-machine complexity, reconciliation và observability burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu compensation khác rollback.
### Middle
Implement idempotent step và explicit states.
### Senior
Xử lý unknown outcomes, retries và reconciliation.
### Technical Lead / Architect
Quyết định service boundaries có đáng Saga complexity hay nên giữ transaction local.

## 11. Key takeaway

- Saga là business consistency protocol, không phải distributed rollback.
- Unknown outcome là trạng thái thật cần model.
- Nếu một local transaction đủ dùng, đừng đưa Saga vào hệ thống.

# 7. Azure Managed Identity + Key Vault: bỏ secret khỏi application configuration nhưng không bỏ authorization design

## 1. What is it?

Managed Identity cung cấp identity do Azure quản lý cho workload. Application lấy token từ Azure identity platform để truy cập Key Vault hoặc resource khác mà không lưu client secret trong code/configuration.

## 2. Why does it exist?

Static secrets phải được tạo, phân phối, rotate và có nguy cơ leak qua config/log/CI. Managed Identity chuyển credential lifecycle sang platform và dùng token ngắn hạn.

## 3. How does it work?

```text
App Service identity
      |
      | token request
      v
Microsoft Entra ID
      |
      | access token
      v
Key Vault -- RBAC --> secret/key/certificate
```

Identity chỉ chứng minh “ai”; RBAC/access policy quyết định “được làm gì”.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(vaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("PaymentApiKey", ct);
```

Ở Azure, `DefaultAzureCredential` có thể dùng Managed Identity; local development dùng developer credential phù hợp.

## 5. Real production scenario

App Service cần đọc third-party API secret từ Key Vault. Deployment không còn inject Key Vault credential; workload identity được cấp role tối thiểu chỉ đọc secrets cần thiết.

## 6. Failure scenario & troubleshooting

**Symptom** → local chạy được, Production trả 403 từ Key Vault. **Evidence** → authentication thành công nhưng authorization denied. **Diagnosis** → Managed Identity tồn tại nhưng thiếu role/scope. **Fix** → cấp least-privilege RBAC đúng vault/resource. **Verification** → access thành công và audit logs xác nhận đúng principal.

## 7. Common mistakes

Cho `Key Vault Administrator`; nhầm authentication với authorization; hard-code secret fallback; gọi Key Vault mỗi request; không thiết kế rotation của chính third-party secret.

## 8. Alternatives

Workload identity/federation cho CI/Kubernetes; client certificate/secret khi platform không hỗ trợ managed identity. Environment secret đơn giản hơn nhưng lifecycle kém an toàn hơn.

## 9. Trade-offs

### Advantages
Không quản lý credential tĩnh cho Azure workload, audit/RBAC tốt hơn.
### Costs / Risks
Phụ thuộc identity platform/network, RBAC complexity và bootstrap/troubleshooting khác local.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt identity và secret.
### Middle
Dùng `DefaultAzureCredential`, Key Vault và RBAC.
### Senior
Thiết kế least privilege, caching/rotation và private connectivity.
### Technical Lead / Architect
Chuẩn hóa workload identity và secret lifecycle toàn platform.

## 11. Key takeaway

- Managed Identity loại bỏ app credential tĩnh, không loại bỏ secret của external systems.
- Authentication thành công không đồng nghĩa authorization đúng.
- Least privilege và rotation vẫn là trách nhiệm kiến trúc.

# 8. SLI/SLO và error budget: biến reliability thành quyết định kỹ thuật có thể đo

## 1. What is it?

SLI là chỉ số đo trải nghiệm/reliability, ví dụ tỷ lệ request thành công dưới 500 ms. SLO là target cho SLI trong window, ví dụ 99.9% trong 30 ngày. Error budget là phần failure được phép: với SLO 99.9%, budget lý thuyết là 0.1%.

## 2. Why does it exist?

“API phải ổn định” không đủ để quyết định release hay ưu tiên reliability work. SLO tạo ngôn ngữ định lượng giữa engineering và product.

## 3. How does it work?

```text
SLI measured good / total events
             |
             v
Compare with SLO
             |
             v
Error budget remaining/burn rate
             |
             v
Release / remediation decision
```

## 4. Practical implementation

Ví dụ SLI cho checkout:

```text
Good = HTTP 2xx AND duration < 1s
Valid = all checkout requests excluding explicit client cancellations
SLI = Good / Valid
SLO = 99.9% over rolling 30 days
```

Definition phải phản ánh user outcome, không chỉ process uptime.

## 5. Real production scenario

Service đạt 99.99% process uptime nhưng payment p99 thường 8 giây. Uptime metric che trải nghiệm xấu. Latency-success SLI cho thấy SLO đang burn nhanh và release mới bị hoãn để xử lý dependency timeout.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard “green” nhưng users complain. **Evidence** → SLI chỉ đo HTTP 5xx, không đo latency/business failures. **Diagnosis** → SLI không đại diện user experience. **Fix** → redefine good events và segment critical journeys. **Verification** → incident thực tế làm SLI phản ánh degradation.

## 7. Common mistakes

SLO = SLA; đặt 100%; dùng average latency; exclude quá nhiều errors; tạo hàng chục SLO không actionable; alert mỗi lần SLI dao động thay vì burn-rate phù hợp.

## 8. Alternatives

Traditional threshold alerts vẫn hữu ích cho resource symptoms. SLO bổ sung service-level objective chứ không thay mọi infrastructure alert.

## 9. Trade-offs

### Advantages
Ưu tiên reliability dựa trên evidence, cân bằng tốc độ release và ổn định.
### Costs / Risks
Cần telemetry tốt, definition governance và tránh metric gaming.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu SLI là measurement, SLO là target.
### Middle
Tạo dashboard và query good/total events.
### Senior
Thiết kế user-centric SLI và burn-rate alert.
### Technical Lead / Architect
Dùng error budget để ra quyết định release/reliability investment.

## 11. Key takeaway

- Reliability cần được định nghĩa theo user outcome.
- 100% SLO thường đắt và không thực tế.
- Error budget chỉ hữu ích nếu dẫn tới quyết định kỹ thuật cụ thể.

# 9. Playwright E2E: bảo vệ critical user journey mà không biến test suite thành bottleneck

## 1. What is it?

Playwright điều khiển browser thật để test application từ UI qua network/backend như người dùng. E2E test có giá trị cao cho critical integration paths nhưng đắt và dễ flaky hơn unit/integration tests.

## 2. Why does it exist?

Unit tests không phát hiện mọi lỗi giữa frontend routing, authentication, API contract, browser behavior và backend deployment. Một checkout/login flow có thể fail dù từng component test pass.

## 3. How does it work?

```text
Playwright -> Browser -> Frontend -> API -> DB/test dependencies
```

Test nên đồng bộ theo observable UI/network state, không dựa vào arbitrary sleep.

## 4. Practical implementation

```typescript
test('user can submit timesheet', async ({ page }) => {
  await page.goto('/timesheets/new');
  await page.getByLabel('Hours').fill('8');
  await page.getByRole('button', { name: 'Submit' }).click();
  await expect(page.getByText('Submitted')).toBeVisible();
});
```

Role/label locators thường bền hơn CSS selectors phụ thuộc implementation.

## 5. Real production scenario

Backend đổi error contract và frontend không handle field mới. Unit tests hai phía pass vì mocks cũ. E2E critical approval flow fail trước deployment và phát hiện integration regression.

## 6. Failure scenario & troubleshooting

**Symptom** → CI đỏ ngẫu nhiên, rerun lại pass. **Evidence** → test dùng `waitForTimeout(3000)` và shared test account/data. **Diagnosis** → timing/data coupling. **Fix** → deterministic fixtures, isolated data, semantic waits/locators. **Verification** → chạy lặp nhiều lần/parallel không flaky.

## 7. Common mistakes

E2E mọi edge case; shared mutable data; fixed sleeps; brittle selectors; test phụ thuộc third-party Production; retry quá nhiều che flakiness.

## 8. Alternatives

Unit tests cho pure logic, integration tests cho DB/API boundaries, contract tests cho service contracts. E2E nên tập trung journey có business risk cao.

## 9. Trade-offs

### Advantages
Bảo vệ wiring và behavior xuyên stack gần user nhất.
### Costs / Risks
Chậm, khó debug, environment/data maintenance và flakiness.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Viết stable locator/assertion.
### Middle
Quản lý fixtures, auth state và deterministic data.
### Senior
Phân bổ test pyramid theo risk và triage flakiness.
### Technical Lead / Architect
Quyết định journey nào xứng đáng E2E và quality gates nào chặn release.

## 11. Key takeaway

- E2E bảo vệ integration, không thay unit/integration tests.
- Flaky test là defect của test system.
- Test ít critical journeys nhưng đáng tin cậy tốt hơn hàng trăm UI tests mong manh.

# 10. Docker image layers cho .NET: build nhanh, image nhỏ và deployment reproducible

## 1. What is it?

Docker image gồm các immutable layers. Mỗi Dockerfile instruction tạo hoặc ảnh hưởng layer; layer cache cho phép reuse phần không đổi. Multi-stage build tách SDK/build environment khỏi runtime image cuối.

## 2. Why does it exist?

Nếu copy toàn source trước `dotnet restore`, thay một file `.cs` có thể invalidate restore cache. Nếu ship SDK image vào Production, image lớn hơn và attack surface tăng không cần thiết.

## 3. How does it work?

```text
SDK stage:
csproj -> restore (cached)
source -> build/publish

Runtime stage:
runtime base + published output
```

Layer order nên đặt artifacts ít thay đổi trước và source thay đổi thường xuyên sau.

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY MyApi.csproj .
RUN dotnet restore MyApi.csproj
COPY . .
RUN dotnet publish MyApi.csproj -c Release -o /app --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

Production còn cần pinning/update strategy, non-root execution khi phù hợp và `.dockerignore` tốt.

## 5. Real production scenario

CI restore toàn dependency mỗi commit dù chỉ sửa controller. Reorder Dockerfile để project metadata được copy/restore trước source giúp cache restore được reuse, giảm build time đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → image 2 GB và vulnerability scanner báo SDK/build tools. **Evidence** → final stage chính là SDK image và chứa source/cache. **Diagnosis** → không multi-stage. **Fix** → runtime-only final stage, copy published output. **Verification** → compare image size, SBOM/vulnerability scan và startup test.

## 7. Common mistakes

Dùng `latest`; copy secrets vào build context; chạy root không cần thiết; thiếu `.dockerignore`; cache dependency sai thứ tự; assume container image tự xử lý configuration/secrets.

## 8. Alternatives

App Service code deployment/IIS đơn giản hơn khi container portability không cần thiết. .NET SDK container publishing có thể giảm Dockerfile boilerplate trong một số workflow.

## 9. Trade-offs

### Advantages
Reproducible artifact, environment consistency, immutable deployment unit.
### Costs / Risks
Image lifecycle, registry, patching, scanning và container operational knowledge.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu image/container/layer khác nhau.
### Middle
Viết multi-stage Dockerfile và tối ưu cache cơ bản.
### Senior
Quản lý base image patching, security, size và runtime configuration.
### Technical Lead / Architect
Quyết định containerization có tạo giá trị deployment/operations hay chỉ thêm platform complexity.

## 11. Key takeaway

- Layer order ảnh hưởng trực tiếp build cache.
- Final image không nên chứa SDK chỉ vì build cần SDK.
- Container là deployment abstraction; vẫn cần patching, security và observability discipline.
