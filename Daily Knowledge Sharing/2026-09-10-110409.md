# 1. C# `ValueTask<T>`: giảm allocation trong hot path nhưng vì sao dùng sai còn tệ hơn `Task<T>`

## 1. What is it?

`ValueTask<T>` là một value type biểu diễn một asynchronous result có thể đã hoàn thành ngay hoặc được backed bởi một `Task<T>`/`IValueTaskSource<T>`.

Mental model:

```text
Task<T>
  └─ thường là object đại diện cho async completion

ValueTask<T>
  ├─ result có sẵn ngay
  └─ hoặc wrapper quanh async operation
```

Mục tiêu chính không phải làm code “async nhanh hơn”, mà giảm một số allocations trong hot path nơi operation **rất thường hoàn thành synchronously**.

Ví dụ điển hình là cache lookup hoặc reusable async primitive.

## 2. Why does it exist?

Một method trả `Task<T>` có thể cần một task object để đại diện cho completion. Trong code chạy hàng triệu lần, allocation nhỏ nhưng lặp lại nhiều có thể tạo GC pressure đáng kể.

Giả sử cache hit 99.9%:

```text
Request
  ↓
Cache lookup
  ├─ hit 99.9% → result đã có
  └─ miss 0.1% → phải async I/O
```

Nếu mỗi cache hit vẫn tạo một asynchronous object không cần thiết, allocation rate có thể trở thành measurable cost.

`ValueTask<T>` cho phép fast path trả trực tiếp value mà không nhất thiết tạo `Task<T>` mới.

## 3. How does it work?

Một `ValueTask<T>` có thể chứa trực tiếp `T` hoặc tham chiếu tới một backing asynchronous source.

Ví dụ:

```csharp
public ValueTask<User?> GetCachedUserAsync(Guid id)
{
    if (_cache.TryGetValue(id, out User? user))
        return ValueTask.FromResult(user);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id));
}
```

Nhưng semantics của `ValueTask<T>` phức tạp hơn `Task<T>`.

Một số `ValueTask` backed bởi `IValueTaskSource` chỉ được await **một lần**. Vì vậy pattern này có thể sai:

```csharp
var pending = service.GetAsync();

var a = await pending;
var b = await pending; // không phải lúc nào cũng hợp lệ
```

Với `Task<T>`, await nhiều lần thường an toàn. Với `ValueTask<T>`, caller phải tuân thủ contract chặt hơn.

## 4. Practical implementation

Một trường hợp hợp lý là reusable in-memory read path:

```csharp
public sealed class ProductLookup
{
    private readonly IMemoryCache _cache;
    private readonly AppDbContext _db;

    public ProductLookup(IMemoryCache cache, AppDbContext db)
    {
        _cache = cache;
        _db = db;
    }

    public ValueTask<ProductDto?> FindAsync(
        Guid id,
        CancellationToken cancellationToken)
    {
        if (_cache.TryGetValue(id, out ProductDto? cached))
            return ValueTask.FromResult(cached);

        return new ValueTask<ProductDto?>(
            LoadAsync(id, cancellationToken));
    }

    private async Task<ProductDto?> LoadAsync(
        Guid id,
        CancellationToken cancellationToken)
    {
        var product = await _db.Products
            .AsNoTracking()
            .Where(x => x.Id == id)
            .Select(x => new ProductDto(x.Id, x.Name, x.Price))
            .SingleOrDefaultAsync(cancellationToken);

        if (product is not null)
            _cache.Set(id, product, TimeSpan.FromMinutes(2));

        return product;
    }
}
```

Nếu consumer cần biến nó thành reusable `Task<T>`, có thể gọi:

```csharp
Task<ProductDto?> task = lookup.FindAsync(id, ct).AsTask();
```

Nhưng lúc đó một phần lợi ích allocation có thể mất đi.

## 5. Real production scenario

Một pricing service nhận 40.000 lookups/second. Phần lớn prices nằm trong memory và được trả synchronously. Profiling cho thấy allocation rate ở lookup abstraction đáng kể dù CPU business logic thấp.

Sau khi đo bằng profiler, team thay một hot API nội bộ từ `Task<Price>` sang `ValueTask<Price>`. Allocation giảm đủ để giảm GC frequency.

Điểm quan trọng: optimization này chỉ có ý nghĩa vì hot path đã được đo và synchronous completion cực cao.

## 6. Failure scenario & troubleshooting

**Symptom** → sau refactor sang `ValueTask<T>`, code khó hiểu hơn nhưng p95/p99 không cải thiện.

**Evidence** → profiler cho thấy bottleneck vẫn nằm ở SQL/network; allocation từ task chỉ chiếm phần rất nhỏ.

**Hypothesis** → team tối ưu abstraction không nằm trên critical path.

**Diagnosis** → so sánh allocation profile, CPU samples và latency dependency trước/sau.

**Fix** → revert về `Task<T>` nếu simplicity có giá trị hơn; chỉ giữ `ValueTask<T>` ở measured hot path.

**Verification** → benchmark và production telemetry phải cho thấy allocation/GC improvement có ý nghĩa.

## 7. Common mistakes

* Thay mọi `Task<T>` bằng `ValueTask<T>` vì nghĩ value type luôn nhanh hơn.
* Await cùng một `ValueTask` nhiều lần khi source không hỗ trợ.
* Gọi `.AsTask()` ở mọi consumer rồi mất lợi ích.
* Dùng trong API public mà không có performance evidence, làm contract khó dùng hơn.
* Benchmark micro-level nhưng không kiểm tra production bottleneck.

## 8. Alternatives

`Task<T>` nên là default vì semantics đơn giản, ecosystem support tốt và dễ compose với `Task.WhenAll`.

`ValueTask<T>` hợp lý khi:

* synchronous completion rất phổ biến
* method nằm trên hot path
* allocation đã được đo là vấn đề
* caller contract được kiểm soát

## 9. Trade-offs

### Advantages

* Có thể giảm allocations trong synchronous fast path.
* Hữu ích cho performance-sensitive libraries và reusable async primitives.

### Costs / Risks

* Contract phức tạp hơn `Task<T>`.
* Struct lớn hơn một reference đơn giản và việc copy cũng có cost.
* Dễ misuse khi await nhiều lần hoặc compose.
* Có thể là premature optimization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task<T>` vẫn là default cho async code; `ValueTask<T>` không phải “Task nhanh hơn”.

### Middle

Biết dùng `ValueTask<T>` đúng contract và nhận diện synchronous fast path.

### Senior

Chỉ áp dụng sau profiling, hiểu allocation/GC trade-off và `IValueTaskSource` semantics.

### Technical Lead / Architect

Quyết định có nên leak `ValueTask<T>` vào public contracts hay giữ optimization ở internal boundary để không tăng cognitive cost toàn hệ thống.

## 11. Key takeaway

* `Task<T>` là lựa chọn mặc định; `ValueTask<T>` là optimization có điều kiện.
* Tối ưu allocation chỉ đáng làm khi allocation thật sự nằm trên critical path.
* Performance gain nhỏ không nên đổi lấy API semantics khó sử dụng trên diện rộng.

# 2. `IHttpClientFactory` + connection pooling + DNS refresh: tránh socket exhaustion mà vẫn phản ứng đúng khi endpoint đổi IP

## 1. What is it?

`IHttpClientFactory` là abstraction trong .NET để tạo `HttpClient` với cấu hình tập trung trong khi quản lý lifetime của underlying handlers và connection pools.

Mental model:

```text
HttpClient instance
      ↓
HttpMessageHandler
      ↓
connection pool
      ↓
TCP/TLS connections
      ↓
remote service
```

Điểm cần hiểu: vấn đề không phải “phải singleton `HttpClient`” hay “phải tạo mới mỗi request” một cách máy móc. Resource thật sự đắt là handler/connection pool phía dưới.

## 2. Why does it exist?

Hai lỗi lịch sử phổ biến:

**Tạo `HttpClient` mới liên tục** và dispose ngay:

```csharp
using var client = new HttpClient();
await client.GetAsync(url);
```

Có thể tạo quá nhiều connection churn và `TIME_WAIT`, gây socket/port exhaustion.

**Giữ một client/handler mãi mãi** có thể lại giữ DNS resolution/connection quá lâu trong một số topology, khiến application tiếp tục gọi IP cũ sau khi service chuyển endpoint.

`IHttpClientFactory` giải quyết lifecycle orchestration này và còn cung cấp named/typed clients, delegating handlers và centralized policies.

## 3. How does it work?

Factory thường tạo `HttpClient` instances ngắn hạn nhưng **reuse handlers** phía dưới trong một khoảng thời gian.

`SocketsHttpHandler` quản lý connection pool theo destination.

Một connection có thể được reuse cho nhiều requests:

```text
Request 1 ─┐
Request 2 ─┼─> same connection pool
Request 3 ─┘
```

DNS thường được resolve khi connection mới được mở. Nếu connection sống quá lâu, DNS change có thể không được thấy ngay. `PooledConnectionLifetime` cho phép định kỳ retire connections để lần kết nối tiếp theo resolve DNS mới.

## 4. Practical implementation

```csharp
builder.Services
    .AddHttpClient<CatalogClient>(client =>
    {
        client.BaseAddress = new Uri("https://catalog.internal");
        client.Timeout = TimeSpan.FromSeconds(5);
    })
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(5),
        MaxConnectionsPerServer = 100
    });
```

Typed client:

```csharp
public sealed class CatalogClient
{
    private readonly HttpClient _httpClient;

    public CatalogClient(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }

    public async Task<ProductDto?> GetAsync(
        Guid id,
        CancellationToken cancellationToken)
    {
        using var response = await _httpClient.GetAsync(
            $"/products/{id}",
            cancellationToken);

        if (response.StatusCode == HttpStatusCode.NotFound)
            return null;

        response.EnsureSuccessStatusCode();

        return await response.Content.ReadFromJsonAsync<ProductDto>(
            cancellationToken: cancellationToken);
    }
}
```

## 5. Real production scenario

Một ASP.NET Core application gọi internal Catalog API chạy sau Kubernetes Service. Pods phía sau thay đổi IP liên tục nhưng DNS service name ổn định.

Application dùng static handler với connections sống rất lâu. Sau một infrastructure change, một số connections vẫn trỏ tới endpoint cũ và requests timeout từng đợt.

Thiết lập connection lifetime phù hợp giúp connection pool định kỳ tái thiết lập và lấy DNS state mới mà không tạo client/connection cho từng request.

## 6. Failure scenario & troubleshooting

**Symptom** → một số instances vẫn timeout tới service cũ sau DNS cutover, trong khi `nslookup` trên host trả IP mới.

**Evidence** → network traces cho thấy established connections vẫn tới old IP.

**Hypothesis** → connection pool giữ connections quá lâu, không phải DNS resolver sai.

**Diagnosis** → kiểm tra `SocketsHttpHandler` settings, connection lifetime và endpoint behavior.

**Fix** → cấu hình `PooledConnectionLifetime` hợp lý; tránh handler vô hạn nếu topology cần DNS rotation.

**Verification** → thực hiện controlled DNS/backend rotation và quan sát connections chuyển endpoint trong expected window.

## 7. Common mistakes

* Tạo/dispose `HttpClient` per request.
* Tin rằng `IHttpClientFactory` tự động làm mọi retry an toàn.
* Đặt retry cho mọi status code, kể cả non-idempotent POST.
* Đặt timeout cực lớn rồi để request giữ resource hàng phút.
* Không truyền `CancellationToken`.
* Không giới hạn concurrency tới downstream yếu hơn.

## 8. Alternatives

Một singleton `HttpClient` với `SocketsHttpHandler` cấu hình đúng hoàn toàn có thể hợp lệ.

`IHttpClientFactory` hữu ích hơn khi application có nhiều outbound dependencies, cần typed clients, lifecycle/policy tập trung hoặc observability nhất quán.

## 9. Trade-offs

### Advantages

* Quản lý handler/connection lifetime tốt.
* Typed/named client giúp rõ dependency boundary.
* Centralized configuration và instrumentation.

### Costs / Risks

* Dễ nhầm rằng factory giải quyết retry/circuit-breaking semantics tự động.
* Cấu hình handler lifetime sai vẫn gây DNS hoặc connection churn.
* Nhiều policies có thể che failure thật và tạo retry amplification.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `HttpClient` nằm trên connection pool chứ không tương đương một TCP connection.

### Middle

Biết dùng typed client, timeout, cancellation và cấu hình handler cơ bản.

### Senior

Hiểu DNS refresh, pool lifetime, connection limits, retry safety và downstream saturation.

### Technical Lead / Architect

Thiết kế outbound HTTP policy theo từng dependency: timeout budget, concurrency, retry eligibility, DNS/network topology và observability.

## 11. Key takeaway

* Quản lý `HttpClient` đúng là bài toán connection lifecycle, không chỉ object lifetime.
* DNS change chỉ có tác dụng với traffic mới khi connection lifecycle cho phép.
* Retry, timeout và connection pooling phải được thiết kế cùng nhau.

# 3. EF Core compiled queries: giảm query-compilation overhead nhưng chỉ đáng dùng sau khi profile đúng bottleneck

## 1. What is it?

EF Core compiled query cho phép chuẩn bị trước phần query pipeline từ LINQ expression tới executable query delegate, giảm overhead lặp lại của query compilation/lookup ở những hot queries.

Mental model:

```text
LINQ expression
    ↓
EF query processing
    ↓
SQL shape
    ↓
execute against DB
```

EF Core đã có internal query-plan caching theo query shape. `EF.CompileQuery`/`EF.CompileAsyncQuery` đi thêm một bước bằng cách tạo delegate compile sẵn để bỏ bớt overhead lookup/processing ở runtime.

## 2. Why does it exist?

Với phần lớn enterprise APIs, database network latency và query execution cost lớn hơn query-compilation cost nhiều lần.

Nhưng với một query cực nhanh, được gọi hàng trăm nghìn lần/second trong low-latency service, vài microseconds framework overhead có thể trở nên đáng kể.

Compiled query tồn tại cho trường hợp này — không phải để sửa SQL chậm, N+1 hoặc thiếu index.

## 3. How does it work?

Query được khai báo static để compile một lần:

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<ProductDto>>
    ProductByIdQuery =
        EF.CompileAsyncQuery(
            (AppDbContext db, Guid id) =>
                db.Products
                    .AsNoTracking()
                    .Where(x => x.Id == id)
                    .Select(x => new ProductDto(
                        x.Id,
                        x.Name,
                        x.Price)));
```

Mỗi invocation reuse compiled delegate thay vì đi lại đầy đủ query compilation path.

Database vẫn phải:

* nhận SQL
* chọn/reuse execution plan của DB
* đọc pages/index
* thực hiện locks/version visibility
* gửi result qua network

Compiled EF query **không** thay thế database execution-plan optimization.

## 4. Practical implementation

```csharp
public sealed class ProductRepository
{
    private static readonly Func<
        AppDbContext,
        Guid,
        IAsyncEnumerable<ProductDto>> ProductById =
        EF.CompileAsyncQuery(
            (AppDbContext db, Guid id) =>
                db.Products
                    .AsNoTracking()
                    .Where(x => x.Id == id)
                    .Select(x => new ProductDto(
                        x.Id,
                        x.Name,
                        x.Price)));

    private readonly AppDbContext _db;

    public ProductRepository(AppDbContext db) => _db = db;

    public async Task<ProductDto?> FindAsync(
        Guid id,
        CancellationToken cancellationToken)
    {
        await foreach (var item in ProductById(
            _db,
            id).WithCancellation(cancellationToken))
        {
            return item;
        }

        return null;
    }
}
```

Benchmark phải so sánh với query thông thường cùng database state, cùng connection conditions và realistic concurrency.

## 5. Real production scenario

Một internal authorization service thực hiện lookup nhỏ theo ID, query có index seek và thường hoàn tất rất nhanh. Sau khi SQL đã tối ưu, profiler cho thấy EF query pipeline chiếm phần measurable trong CPU.

Compiled query giảm CPU per request một lượng nhỏ nhưng có ý nghĩa ở throughput rất cao.

Ngược lại, trên CRUD API có SQL mất 120 ms, tiết kiệm vài microseconds ở EF không có giá trị thực tế.

## 6. Failure scenario & troubleshooting

**Symptom** → team triển khai compiled queries hàng loạt nhưng latency không đổi.

**Evidence** → traces cho thấy 95% thời gian nằm ở database execution và network.

**Hypothesis** → optimization nhắm sai layer.

**Diagnosis** → đo query translation CPU, dependency duration và execution plan.

**Fix** → tập trung vào access pattern, projection, indexes, round trips hoặc lock contention trước.

**Verification** → benchmark end-to-end và CPU allocation profile, không chỉ microbenchmark delegate.

## 7. Common mistakes

* Dùng compiled query để “fix” slow SQL.
* Compile mọi query làm code khó bảo trì.
* Nhầm EF compiled query với SQL Server compiled execution plan.
* Dynamic query shape quá phức tạp nhưng cố ép vào compiled query.
* Không đo production-like workload.

## 8. Alternatives

* Query EF Core thông thường: default tốt nhất cho phần lớn code.
* Raw SQL/Dapper: có thể giảm ORM overhead hơn nhưng đổi lấy abstraction/mapping cost.
* Stored procedure: hữu ích trong một số data-heavy contracts nhưng không tự động nhanh hơn.

## 9. Trade-offs

### Advantages

* Giảm một phần framework CPU overhead ở hot query ổn định.
* Predictable query shape.

### Costs / Risks

* Boilerplate và cognitive complexity tăng.
* Ít linh hoạt với dynamic query shape.
* Lợi ích thường nhỏ so với database/network latency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ORM query có hai phần: framework processing và database execution.

### Middle

Biết viết projection, `AsNoTracking` và đo generated SQL trước khi nghĩ tới compiled query.

### Senior

Biết profile để chứng minh query compilation thực sự là bottleneck.

### Technical Lead / Architect

Giữ compiled queries như targeted optimization, tránh biến performance folklore thành coding standard toàn codebase.

## 11. Key takeaway

* EF Core đã cache query shape; compiled query là optimization sâu hơn cho hot path đặc biệt.
* Đừng tối ưu vài microseconds khi database đang mất hàng chục milliseconds.
* Performance engineering phải đi từ measurement tới bottleneck thực tế.

# 4. MongoDB embedding vs referencing: thiết kế document theo access pattern thay vì bê mô hình relational sang NoSQL

## 1. What is it?

Trong MongoDB, **embedding** đặt dữ liệu liên quan bên trong cùng document; **referencing** lưu identifiers và giữ dữ liệu ở documents/collections riêng.

Embedding:

```json
{
  "orderId": "O-1001",
  "customer": {
    "name": "An",
    "email": "an@example.com"
  },
  "items": [
    { "sku": "A1", "quantity": 2, "price": 10.5 }
  ]
}
```

Referencing:

```json
{
  "orderId": "O-1001",
  "customerId": "C-42"
}
```

Quyết định đúng dựa trên **access pattern, consistency boundary, growth pattern và ownership**, không phải quy tắc “NoSQL thì denormalize mọi thứ”.

## 2. Why does it exist?

Relational model tối ưu cho normalized relationships và joins. Document database cho phép aggregate dữ liệu được đọc/cập nhật cùng nhau thành một unit gần với application access pattern.

Nếu mỗi page cần Order + 20 OrderItems và tất cả luôn được đọc cùng nhau, một document có thể tránh nhiều round trips/joins.

Nhưng nếu embedded array tăng vô hạn hoặc dữ liệu shared thay đổi thường xuyên, duplication trở thành operational problem.

## 3. How does it work?

MongoDB operations trên một document có atomicity mạnh ở document boundary.

Điều này làm embedding hấp dẫn cho dữ liệu có invariant chung:

```text
Order
 ├─ ShippingAddress snapshot
 └─ OrderItems
```

Nhưng một `Customer` được dùng bởi 100.000 orders không nên nhất thiết embed toàn bộ mutable customer profile nếu mọi thay đổi profile phải propagate tới toàn lịch sử.

Nhiều hệ thống cố ý embed **snapshot**:

```text
Order.CustomerNameAtPurchase
```

vì business semantics yêu cầu giữ lịch sử, không phải vì cache convenience.

## 4. Practical implementation

C# model:

```csharp
public sealed class OrderDocument
{
    public ObjectId Id { get; set; }
    public string OrderNumber { get; set; } = null!;
    public CustomerSnapshot Customer { get; set; } = null!;
    public List<OrderItemDocument> Items { get; set; } = [];
}

public sealed class CustomerSnapshot
{
    public Guid CustomerId { get; set; }
    public string Name { get; set; } = null!;
    public string Email { get; set; } = null!;
}
```

Query order detail là một read:

```csharp
var order = await collection
    .Find(x => x.OrderNumber == orderNumber)
    .SingleOrDefaultAsync(cancellationToken);
```

Customer ID vẫn được giữ để truy vết domain identity, nhưng order snapshot không phụ thuộc vào live Customer document để render lịch sử mua hàng.

## 5. Real production scenario

Marketplace lưu vehicle listings. Listing có photos metadata, headline, attributes và seller snapshot thường được đọc cùng nhau.

Embedding bounded listing data giúp read path đơn giản.

Nhưng messages/comments có thể tăng hàng trăm nghìn entries theo thời gian. Embed toàn bộ comments vào Listing document gây document growth, update contention và kích thước document khó kiểm soát. Comments phù hợp collection riêng với `listingId` index.

## 6. Failure scenario & troubleshooting

**Symptom** → update một customer profile phải chạy bulk update hàng triệu documents.

**Evidence** → cùng mutable customer profile bị duplicate ở nhiều collections mà business muốn tất cả luôn mới.

**Hypothesis** → dữ liệu có independent lifecycle nhưng đã bị embed như owned snapshot.

**Diagnosis** → xác định read/write access patterns và freshness requirement.

**Fix** → reference phần mutable/shared; chỉ embed immutable/bounded snapshot thực sự thuộc aggregate read model.

**Verification** → profile query count, document growth và update fan-out sau redesign.

## 7. Common mistakes

* Chuyển từng SQL table thành một MongoDB collection rồi tự làm joins trong application.
* Ngược lại, embed mọi relation vì “MongoDB không join”.
* Embed unbounded arrays.
* Không phân biệt snapshot data với canonical data.
* Chọn schema trước khi biết query/access pattern.

## 8. Alternatives

* SQL Server/PostgreSQL: tốt khi relationships, constraints và ad-hoc relational querying là trung tâm.
* MongoDB referencing: phù hợp shared entities có lifecycle riêng.
* MongoDB embedding: phù hợp bounded data thường đọc/cập nhật cùng nhau.

## 9. Trade-offs

### Advantages

Embedding có thể giảm round trips, đơn giản hóa read model và cung cấp atomic document update.

### Costs / Risks

Duplication, document growth và update fan-out tăng nếu boundary sai.

Referencing giảm duplication nhưng có thể tăng queries/aggregation complexity và eventual consistency ở application composition.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu document model không chỉ là JSON thay cho table row.

### Middle

Thiết kế schema dựa trên common reads/writes và index phù hợp.

### Senior

Đánh giá bounded growth, duplication semantics, atomicity và data lifecycle.

### Technical Lead / Architect

Chọn database/model dựa trên workload và consistency requirements, không dựa trên khẩu hiệu SQL vs NoSQL.

## 11. Key takeaway

* Embed dữ liệu thuộc cùng lifecycle và bounded access pattern; reference dữ liệu có lifecycle độc lập.
* Duplication chỉ đúng khi semantics của duplication được hiểu rõ.
* Document modeling bắt đầu từ access pattern, không bắt đầu từ class diagram.

# 5. Retry amplification + exponential backoff + jitter: một transient failure nhỏ có thể biến thành retry storm như thế nào

## 1. What is it?

Retry là chiến lược chạy lại operation sau transient failure. Nhưng trong distributed system, retry không có giới hạn và không phối hợp có thể **khuếch đại tải** đúng lúc dependency đang yếu nhất.

Ví dụ:

```text
1,000 requests
   ↓ dependency fails
1,000 retries immediately
   ↓ fail again
2nd wave: 1,000 more
   ↓
recovery becomes harder
```

Exponential backoff tăng delay giữa attempts. Jitter thêm randomness để clients không thức dậy cùng lúc.

## 2. Why does it exist?

Network reset, temporary 503 hoặc leader election có thể tự phục hồi sau vài trăm milliseconds. Retry hợp lý có thể biến failure tạm thời thành success mà user không nhận ra.

Nhưng nếu mỗi layer đều retry ba lần:

```text
Gateway: 3 attempts
  ↓
Service A: 3 attempts
  ↓
Service B: 3 attempts
```

Một logical request có thể tạo tới 27 downstream attempts trong trường hợp xấu.

Đây là retry amplification.

## 3. How does it work?

Backoff đơn giản:

```text
attempt 1 → wait ~200 ms
attempt 2 → wait ~400 ms
attempt 3 → wait ~800 ms
```

Nếu 10.000 clients cùng dùng chính xác delay này, tất cả vẫn retry thành waves đồng bộ.

Jitter biến delay thành khoảng ngẫu nhiên:

```text
attempt 2 → wait 250–650 ms
```

Load được trải ra theo thời gian.

Quan trọng hơn: retry phải nằm trong **overall timeout budget**. Không có ý nghĩa nếu client chỉ chờ 2 giây nhưng retry chain kéo 10 giây.

## 4. Practical implementation

Một policy đơn giản có thể được triển khai với resilience pipeline phù hợp của .NET, nhưng semantics quan trọng hơn library.

Pseudo-near-production configuration:

```csharp
var options = new HttpRetryStrategyOptions
{
    MaxRetryAttempts = 2,
    Delay = TimeSpan.FromMilliseconds(200),
    BackoffType = DelayBackoffType.Exponential,
    UseJitter = true
};
```

Chỉ retry operations thật sự retry-safe.

GET thường dễ retry hơn một POST tạo payment. POST chỉ an toàn nếu API có idempotency contract, ví dụ:

```http
Idempotency-Key: 4fc6c9...
```

## 5. Real production scenario

Inventory API bị CPU saturation và bắt đầu trả 503 cho 20% requests. Ba upstream services đều retry ngay ba lần.

Load thực tế tăng từ 5.000 RPS lên hơn 10.000 attempts/second, khiến dependency không còn cơ hội hồi phục.

Sau incident, team giới hạn retry ở một boundary, thêm jitter, timeout budget và circuit breaker. Recovery nhanh hơn vì traffic giảm thay vì tăng khi dependency unhealthy.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency có outage nhỏ nhưng request volume tới nó tăng mạnh hơn baseline.

**Evidence** → telemetry cho thấy attempts/request > 1, retry counters tăng đồng thời ở nhiều services.

**Hypothesis** → nested retries tạo amplification.

**Diagnosis** → trace một logical request xuyên các layers và đếm actual outbound attempts.

**Fix** → xác định retry owner; giảm attempts; thêm jitter; obey `Retry-After`; dùng circuit breaker/load shedding khi phù hợp.

**Verification** → chaos test dependency failure và xác nhận downstream attempt rate không vượt safety envelope.

## 7. Common mistakes

* Retry mọi exception.
* Retry authentication/validation 4xx không thể tự hồi phục.
* Retry non-idempotent side effect.
* Mỗi layer tự retry mà không có system-level budget.
* Không thêm jitter.
* Timeout mỗi attempt dài hơn toàn request budget.

## 8. Alternatives

* Fail fast: tốt khi error không transient hoặc dependency đang chắc chắn unavailable.
* Queue/asynchronous processing: tốt khi work không cần synchronous response.
* Circuit Breaker: giảm calls khi dependency đang failing liên tục.
* Bulkhead/concurrency limit: ngăn dependency failure ăn hết local resources.

Các patterns này bổ trợ nhau, không thay thế retry một cách máy móc.

## 9. Trade-offs

### Advantages

* Hấp thụ transient failures.
* Tăng success rate cho operations retry-safe.

### Costs / Risks

* Tăng latency.
* Tăng load đúng thời điểm dependency yếu.
* Có thể duplicate side effects.
* Policy phân tán khó reasoning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry là một request mới, không phải “miễn phí”.

### Middle

Biết exponential backoff, jitter, timeout và retry-safe methods.

### Senior

Nhìn nested retries, idempotency, overload và failure propagation.

### Technical Lead / Architect

Định nghĩa resilience budget end-to-end: layer nào retry, bao nhiêu lần, trong thời gian nào và khi nào phải fail fast/load shed.

## 11. Key takeaway

* Retry có thể chữa transient failure hoặc biến nó thành outage lớn hơn.
* Jitter giảm synchronized retry waves nhưng không sửa policy sai.
* Hãy thiết kế retry theo end-to-end budget và idempotency semantics.

# 6. Azure Key Vault + Managed Identity + secret rotation: tách credential khỏi deployment mà không biến Key Vault thành dependency trên mọi request

## 1. What is it?

Azure Key Vault lưu secrets, keys và certificates ngoài application deployment. Managed Identity cho Azure workload một identity để authenticate tới Azure services mà không cần lưu client secret trong config.

Flow:

```text
App Service / Function
      ↓ Managed Identity
Microsoft Entra ID
      ↓ access token
Azure Key Vault
      ↓ authorized secret/key
Application
```

Mục tiêu là giảm static credentials và centralize secret lifecycle/access control.

## 2. Why does it exist?

Hard-code secret hoặc để production credential trong `appsettings.json`, pipeline variables không kiểm soát, image/container hay source control làm rotation và incident response khó khăn.

Managed Identity loại bỏ một lớp bootstrap secret: application không cần secret để lấy một secret khác.

Nhưng Key Vault không nên bị hiểu như remote dictionary phải query cho từng HTTP request.

## 3. How does it work?

Azure runtime cấp identity cho workload. SDK dùng `DefaultAzureCredential`/Managed Identity credential để lấy Entra token. Key Vault kiểm tra authorization qua RBAC/access policy phù hợp.

Application thường fetch secret khi startup hoặc qua provider có caching/refresh strategy.

```text
Request path
   X→ Key Vault every request

Startup/config refresh
   → Key Vault
   → local application configuration/cache
```

Rotation cần hai phía phối hợp: secret mới tồn tại và application phải reload/reconnect mà không downtime.

## 4. Practical implementation

```csharp
var credential = new DefaultAzureCredential();

builder.Configuration.AddAzureKeyVault(
    new Uri(builder.Configuration["KeyVaultUri"]!),
    credential);
```

Hoặc dùng `SecretClient` cho use case cụ thể:

```csharp
var client = new SecretClient(
    new Uri(keyVaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync(
    "ExternalApiKey",
    cancellationToken: ct);
```

Trong production, cần tránh gọi `GetSecretAsync` trên mọi request nếu secret không cần freshness tức thời.

## 5. Real production scenario

Một App Service dùng API credential của payment provider. Security team rotate secret mỗi 90 ngày.

Version mới được tạo trong Key Vault, application configuration refresh nhận value mới, connection/client được rebuild có kiểm soát, sau đó provider revoke secret cũ.

Nếu revoke old secret trước khi app instances refresh, một phần fleet sẽ bắt đầu trả 401.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment thành công nhưng application startup trả 500 vì không đọc được Key Vault.

**Evidence** → logs có 403 từ Key Vault; Managed Identity tồn tại nhưng thiếu role hoặc network path bị chặn.

**Hypothesis** → authorization/network configuration mismatch.

**Diagnosis** → kiểm tra identity object, RBAC assignment, vault firewall/private endpoint/DNS và credential chain.

**Fix** → cấp minimum required role và sửa private connectivity/name resolution nếu dùng Private Endpoint.

**Verification** → identity của workload đọc đúng secret từ production network path; không dùng developer credential để chứng minh production access.

## 7. Common mistakes

* Dùng Key Vault nhưng vẫn lưu client secret cho app identity.
* Cấp quyền quá rộng như quản trị toàn vault.
* Fetch secret trên mỗi API request.
* Rotate secret mà không có overlap window.
* Log secret value khi debug.
* Development `DefaultAzureCredential` thành công bằng user account nhưng production Managed Identity thiếu quyền.

## 8. Alternatives

* Environment variables/pipeline secret store: đơn giản hơn cho hệ thống nhỏ nhưng rotation/governance có thể hạn chế.
* Workload identity/Managed Identity trực tiếp tới downstream: tốt hơn secret nếu service hỗ trợ Entra authentication.
* Key Vault: phù hợp khi vẫn cần quản lý credentials/keys/certificates có lifecycle riêng.

## 9. Trade-offs

### Advantages

* Centralized secret governance/audit.
* Giảm static bootstrap credentials với Managed Identity.
* Rotation và access control tốt hơn source/config secrets.

### Costs / Risks

* Thêm Azure dependency và network/RBAC complexity.
* Rotation vẫn cần application design hỗ trợ reload.
* Dùng trong hot request path có thể tăng latency và blast radius.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu secret không nên nằm trong source code và Managed Identity là workload identity.

### Middle

Biết cấu hình SDK, RBAC và inject configuration an toàn.

### Senior

Thiết kế caching/refresh, rotation overlap, startup failure behavior và Private Endpoint troubleshooting.

### Technical Lead / Architect

Ưu tiên secretless authentication khi có thể; nếu phải dùng secrets, định nghĩa ownership, rotation SLA, access boundary và outage behavior.

## 11. Key takeaway

* Managed Identity giải quyết bootstrap credential tốt hơn việc chỉ “chuyển secret sang nơi khác”.
* Key Vault không nên trở thành synchronous dependency của mọi request.
* Rotation là workflow giữa producer, vault và consumer—not chỉ thao tác đổi value.

# 7. OpenTelemetry metric cardinality: vì sao một label tưởng vô hại có thể làm observability pipeline tăng chi phí và mất ổn định

## 1. What is it?

Metric cardinality là số lượng unique time series được tạo từ một metric và tổ hợp attribute/label values.

Ví dụ:

```text
http_requests_total{method="GET",status="200"}
```

có cardinality thấp.

Nhưng:

```text
http_requests_total{user_id="...",request_id="..."}
```

có thể tạo hàng triệu series vì mỗi user/request khác nhau.

Metrics phù hợp với **bounded dimensions**. High-cardinality identifiers thường phù hợp logs/traces hơn.

## 2. Why does it exist?

Metrics systems tối ưu cho aggregation nhanh theo dimensions có giới hạn:

* endpoint template
* status code
* region
* dependency name

Nếu mỗi observation tạo một series mới, backend phải giữ/index nhiều series, memory tăng, ingestion cost tăng và dashboard queries chậm.

Observability có thể tự trở thành production cost/problem.

## 3. How does it work?

Giả sử metric có labels:

```text
endpoint: 50 values
status: 6 values
region: 5 values
customer_id: 100,000 values
```

Potential combinations có thể lên tới:

```text
50 × 6 × 5 × 100,000 = 150,000,000 series
```

Thực tế không phải mọi combination xuất hiện, nhưng multiplier cho thấy nguy cơ.

Một path raw như:

```text
/orders/12345
/orders/92811
```

nên được normalize thành route template:

```text
/orders/{id}
```

## 4. Practical implementation

Với custom metric, giữ dimensions bounded:

```csharp
private static readonly Meter Meter = new("Nexora.Orders");
private static readonly Counter<long> OrdersCreated =
    Meter.CreateCounter<long>("orders.created");

public void RecordOrderCreated(string channel, string region)
{
    OrdersCreated.Add(1,
        new KeyValuePair<string, object?>("channel", channel),
        new KeyValuePair<string, object?>("region", region));
}
```

Không thêm `order.id` vào metric attributes.

Nếu cần điều tra một order cụ thể, đưa ID vào trace/log:

```csharp
Activity.Current?.SetTag("order.id", orderId);
```

Trace sampling/retention strategy vẫn phải được quản lý riêng.

## 5. Real production scenario

Team thêm `tenant_id` vào mọi HTTP metric để dashboard có thể lọc từng customer. SaaS có 80.000 tenants.

Sau vài tuần, metric ingestion/storage tăng mạnh, dashboards chậm và observability bill tăng nhiều lần.

Giải pháp là aggregate tenants theo bounded service tier/region cho metrics; dùng traces/log search khi cần tenant-level diagnosis.

## 6. Failure scenario & troubleshooting

**Symptom** → telemetry cost tăng đột ngột sau release dù traffic chỉ tăng nhẹ.

**Evidence** → số active time series tăng hàng chục lần; metric attributes chứa IDs/raw URLs.

**Hypothesis** → cardinality explosion.

**Diagnosis** → thống kê unique values per attribute và series count trước/sau deployment.

**Fix** → drop/normalize unbounded attributes; dùng route templates; chuyển identifiers sang logs/traces.

**Verification** → active series và ingestion rate quay về expected range mà SLI dashboards vẫn giữ đủ dimensions.

## 7. Common mistakes

* Gắn `user_id`, `request_id`, GUID vào metric labels.
* Dùng raw URL làm route dimension.
* Cho exception message làm label.
* Nghĩ “thêm metadata không có cost”.
* Dùng metrics để thay toàn bộ tracing/logging.

## 8. Alternatives

* Metrics: aggregation/alerting trên bounded dimensions.
* Logs: rich event details, searchable records.
* Traces: causal request/dependency flow và per-request context.

Ba signal bổ sung nhau. Không signal nào nên bị ép làm vai trò của tất cả.

## 9. Trade-offs

### Advantages

Dimensions tốt giúp dashboards và alerts cực mạnh với chi phí hợp lý.

### Costs / Risks

Quá ít dimensions làm mất khả năng phân tích; quá nhiều/high-cardinality dimensions làm cost và reliability xấu đi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu metric label tạo nhiều time series khác nhau.

### Middle

Biết chọn bounded labels và route normalization.

### Senior

Đánh giá cardinality, ingestion cost, sampling và signal placement.

### Technical Lead / Architect

Đặt observability conventions và telemetry budget như một phần của architecture, không để mỗi team tự thêm arbitrary labels.

## 11. Key takeaway

* Metrics phù hợp aggregate dimensions, không phù hợp unique identifiers.
* Cardinality là multiplier cost ẩn nhưng rất lớn.
* Đưa per-request/per-entity identifiers sang traces/logs khi cần forensic detail.

# 8. JWT signing-key rotation + JWKS caching: token hợp lệ vẫn có thể bị reject khi identity provider đổi key

## 1. What is it?

JWT thường được identity provider ký bằng private key. Resource server validate chữ ký bằng public key tương ứng.

JWKS — JSON Web Key Set — là endpoint công bố public keys, thường có `kid` để chọn đúng key.

```text
Identity Provider
 private key K2
      ↓ signs JWT kid=K2

API
  ↓ reads kid=K2
JWKS cache
  ↓ public key K2
validate signature
```

Key rotation là quá trình identity provider chuyển từ key cũ sang key mới mà vẫn cho ecosystem thời gian thích nghi.

## 2. Why does it exist?

Signing key không nên tồn tại vĩnh viễn. Rotation giảm impact của key compromise và hỗ trợ lifecycle/certificate replacement.

Nhưng distributed APIs có cache metadata/JWKS. Nếu provider ký token bằng key mới trước khi APIs biết key đó, legitimate traffic có thể bị 401 hàng loạt.

## 3. How does it work?

JWT header thường chứa:

```json
{
  "alg": "RS256",
  "kid": "key-2026-09"
}
```

Validator lấy `kid`, tìm public key tương ứng trong cached signing keys và verify signature.

Well-designed metadata libraries có thể refresh signing keys khi gặp unknown `kid`, nhưng refresh behavior có throttling/caching để tránh attacker biến unknown keys thành metadata-fetch storm.

Provider thường publish old + new public keys trong overlap window:

```text
JWKS: K1 + K2
      ↓
start signing with K2
      ↓
old K1 tokens expire
      ↓
remove K1
```

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = "https://identity.example.com";
        options.Audience = "orders-api";
        options.RequireHttpsMetadata = true;
    });
```

Không nên hard-code signing public key nếu identity provider có chuẩn OpenID Connect metadata/JWKS rotation.

Ngoài signature, vẫn phải validate:

* issuer
* audience
* lifetime
* algorithm constraints
* required claims/policies

## 5. Real production scenario

Identity provider rotate signing certificate lúc 14:00. Một API fleet có metadata cache cũ. Một số instances refresh nhanh, số khác tiếp tục chỉ biết K1.

Users mới nhận tokens ký K2 và gặp intermittent 401 tùy request được load balance tới instance nào.

Đây trông giống authorization bug nhưng root cause là signing-key distribution/cache convergence.

## 6. Failure scenario & troubleshooting

**Symptom** → JWT vừa login xong thỉnh thoảng 401; token cũ lại hoạt động.

**Evidence** → failed token header có new `kid`; affected API instance chưa có key đó.

**Hypothesis** → JWKS/metadata cache stale hoặc network tới discovery endpoint lỗi.

**Diagnosis** → decode header an toàn, so sánh `kid` với current JWKS và kiểm tra metadata-refresh telemetry.

**Fix** → đảm bảo standard metadata manager/refresh behavior, network availability và key-overlap process ở IdP.

**Verification** → rotate test key trong staging; old/new tokens cùng validate trong overlap period.

## 7. Common mistakes

* Disable signature validation để “fix” unknown key.
* Chỉ decode JWT rồi tin claims.
* Hard-code một signing certificate mãi mãi.
* Cache JWKS vô hạn.
* Refresh JWKS cho mọi invalid token, tạo DoS vector.
* Chỉ validate signature nhưng bỏ issuer/audience/lifetime.

## 8. Alternatives

* Symmetric shared secret signing: đơn giản hơn nhưng key distribution khó và blast radius lớn hơn giữa nhiều services.
* Asymmetric signing + JWKS: phù hợp distributed resource servers vì chỉ IdP giữ private key.
* Token introspection: server gọi authorization server để kiểm tra token; tăng centralized control nhưng thêm network dependency/latency.

## 9. Trade-offs

### Advantages

* Asymmetric JWKS model scale tốt cho nhiều validators.
* Rotation không cần deploy public key thủ công nếu metadata flow đúng.

### Costs / Risks

* Caching/refresh/network behavior phức tạp.
* Rotation sai thứ tự gây widespread authentication failure.
* Metadata endpoint trở thành operational dependency dù không nhất thiết nằm trên mọi request.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu JWT phải được verify, không chỉ decode.

### Middle

Biết cấu hình Authority/Audience và đọc `kid`/JWKS khi debug.

### Senior

Hiểu key overlap, metadata caching, refresh throttling và intermittent fleet failures.

### Technical Lead / Architect

Định nghĩa identity trust model, rotation procedure và telemetry để key lifecycle không trở thành surprise outage.

## 11. Key takeaway

* JWT validation phụ thuộc signing-key lifecycle, không chỉ token content.
* Rotation an toàn cần overlap giữa old/new keys.
* Unknown `kid` là signal để điều tra key distribution—not lý do hạ validation security.

# 9. Vue reactivity + derived state: tránh duplicated state và những bug UI mà backend/full-stack engineer thường hiểu sai

## 1. What is it?

Vue reactivity theo dõi dependencies giữa reactive state và computations/rendering để cập nhật UI khi source state thay đổi.

Một nguyên tắc quan trọng là **derived state nên được tính từ source of truth**, không nên copy thành một state độc lập nếu không thật sự cần.

Ví dụ:

```ts
const firstName = ref('An')
const lastName = ref('Nguyen')

const fullName = computed(() =>
  `${firstName.value} ${lastName.value}`)
```

`fullName` được derive từ hai sources. Không cần một `ref` thứ ba rồi tự synchronize.

## 2. Why does it exist?

Frontend có nhiều state transformations: API result, filters, selected item, validation state, UI formatting.

Nếu cùng một fact được lưu ở nhiều nơi:

```text
server user.name
   ↓ copied to
store.userName
   ↓ copied to
component.displayName
```

một update có thể thay đổi một copy mà quên các copy khác, tạo stale UI.

Reactive derivation giảm synchronization code và invariant count.

## 3. How does it work?

Vue tracks reactive reads trong `computed`/effects. Khi dependency thay đổi, computed value được invalidated và recompute khi cần.

```ts
const products = ref<Product[]>([])
const search = ref('')

const filteredProducts = computed(() => {
  const q = search.value.trim().toLowerCase()
  return products.value.filter(p =>
    p.name.toLowerCase().includes(q))
})
```

Không cần:

```ts
const filteredProducts = ref<Product[]>([])
// rồi watch products + watch search + manually keep in sync
```

trừ khi derived data có lifecycle/side effect riêng thực sự.

## 4. Practical implementation

```vue
<script setup lang="ts">
import { computed, ref } from 'vue'

type Task = {
  id: string
  title: string
  completed: boolean
}

const tasks = ref<Task[]>([])
const filter = ref<'all' | 'open' | 'done'>('all')

const visibleTasks = computed(() => {
  if (filter.value === 'open')
    return tasks.value.filter(x => !x.completed)

  if (filter.value === 'done')
    return tasks.value.filter(x => x.completed)

  return tasks.value
})

const completedCount = computed(() =>
  tasks.value.filter(x => x.completed).length)
</script>
```

`visibleTasks` và `completedCount` không phải canonical state; chúng là views của `tasks`.

## 5. Real production scenario

Task-management UI nhận task từ API. Team lưu `tasks`, `openTasks`, `completedTasks` thành ba arrays trong store.

Khi websocket/event update một task từ Open sang Completed, code update `tasks` nhưng quên move item giữa hai arrays. Badge count và table hiển thị mâu thuẫn.

Chuyển `openTasks`/`completedTasks` thành computed derivations loại bỏ một class synchronization bugs.

## 6. Failure scenario & troubleshooting

**Symptom** → sau update API thành công, một phần UI hiện trạng thái mới nhưng counter/filter vẫn cũ.

**Evidence** → Vue DevTools cho thấy canonical task đã đổi nhưng secondary arrays không đổi.

**Hypothesis** → duplicated state bị desynchronized.

**Diagnosis** → trace nơi state được copied và watchers chịu trách nhiệm đồng bộ.

**Fix** → giữ một source of truth và derive views bằng `computed`; chỉ persist independent state khi business/UI semantics yêu cầu.

**Verification** → update task qua mọi path và đảm bảo all derived views thay đổi từ cùng source.

## 7. Common mistakes

* Copy props vào local state rồi kỳ vọng tự đồng bộ.
* Dùng `watch` cho thứ có thể là `computed`.
* Mutate nhiều copies của cùng entity.
* Dùng global store cho mọi local UI state.
* Gắn business invariants quan trọng chỉ ở client state; server vẫn phải enforce correctness.

## 8. Alternatives

* Local `ref/reactive`: phù hợp component-local mutable state.
* `computed`: phù hợp synchronous derived state.
* `watch`: phù hợp side effects khi state thay đổi, không phải default cho derivation.
* Pinia/global store: phù hợp state thật sự shared xuyên views/components.

## 9. Trade-offs

### Advantages

* Ít synchronization bugs.
* Data flow dễ reasoning hơn.
* Computed caching giúp tránh recompute không cần thiết trong nhiều cases.

### Costs / Risks

* Heavy computed operation vẫn có CPU cost.
* Reactive dependency graph quá phức tạp có thể khó debug.
* Không phải mọi remote/server state nên được tự thiết kế lại thành local reactive truth.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `ref/reactive` là source state, `computed` là derived value.

### Middle

Biết chọn `computed` vs `watch` và tránh duplicated state.

### Senior

Phân biệt server state, client cache, domain state và transient UI state; thiết kế update/error rollback rõ ràng.

### Technical Lead / Architect

Đặt frontend state boundaries sao cho client không duplicate backend invariants và không biến global store thành database thứ hai.

## 11. Key takeaway

* Một fact nên có một source of truth nếu có thể.
* `computed` dành cho derivation; `watch` chủ yếu dành cho side effects.
* Frontend reactivity không thay thế server-side correctness.

# 10. Database expand-contract migration: thay schema an toàn khi old và new application versions cùng chạy trong rolling deployment

## 1. What is it?

Expand-contract là migration strategy thay schema qua nhiều bước tương thích thay vì một breaking migration duy nhất.

Mental model:

```text
EXPAND
old schema + new compatible structure
       ↓
DEPLOY/MIGRATE DATA
old app + new app cùng hoạt động
       ↓
CONTRACT
remove old structure sau khi không còn consumer
```

Mục tiêu là giữ backward/forward compatibility trong khoảng thời gian nhiều application versions cùng chạy.

## 2. Why does it exist?

Rolling deployment, Kubernetes rolling update hoặc App Service slot swap không đảm bảo toàn fleet đổi version atomically.

Có thể tồn tại:

```text
Instance A → version 1
Instance B → version 1
Instance C → version 2
```

Nếu migration đổi tên/xóa column ngay trước khi v2 deploy, v1 có thể crash.

Nếu v2 yêu cầu column mới `NOT NULL` nhưng v1 không ghi field đó, writes từ v1 có thể fail.

## 3. How does it work?

Ví dụ đổi `FullName` thành `FirstName` + `LastName`.

Không nên làm một bước:

```sql
DROP COLUMN FullName;
ALTER TABLE Users ADD FirstName ...;
ALTER TABLE Users ADD LastName ...;
```

Thay vào đó:

**Expand:**

```sql
ALTER TABLE Users ADD FirstName nvarchar(100) NULL;
ALTER TABLE Users ADD LastName nvarchar(100) NULL;
```

**Deploy compatible app:** đọc new fields khi có, fallback `FullName`; writes có thể dual-write trong transition.

**Backfill:** migrate historical rows theo controlled batches.

**Switch:** new app chỉ phụ thuộc new fields sau khi data đầy đủ.

**Contract:** release sau mới remove `FullName`.

## 4. Practical implementation

EF Core migration bước expand:

```csharp
migrationBuilder.AddColumn<string>(
    name: "FirstName",
    table: "Users",
    type: "nvarchar(100)",
    maxLength: 100,
    nullable: true);

migrationBuilder.AddColumn<string>(
    name: "LastName",
    table: "Users",
    type: "nvarchar(100)",
    maxLength: 100,
    nullable: true);
```

Application compatibility code tạm thời:

```csharp
public string GetDisplayName(User user)
{
    if (!string.IsNullOrWhiteSpace(user.FirstName) ||
        !string.IsNullOrWhiteSpace(user.LastName))
    {
        return $"{user.FirstName} {user.LastName}".Trim();
    }

    return user.FullName;
}
```

Sau migration/backfill và một release window an toàn, compatibility code và old column mới được remove.

## 5. Real production scenario

SaaS chạy 12 pods. Release mới đổi `Status` numeric thành richer status model.

Nếu migration drop old column trước rolling update, pods chưa restart vẫn query old schema và trả 500.

Team dùng additive schema trước, deploy code hiểu cả old/new representation, backfill data, quan sát toàn fleet, rồi contract ở release sau.

Downtime không cần thiết dù schema thay đổi lớn hơn một `ADD COLUMN` đơn giản.

## 6. Failure scenario & troubleshooting

**Symptom** → ngay khi deployment bắt đầu, chỉ một phần requests trả SQL “Invalid column name”.

**Evidence** → errors chỉ đến từ old application instances trong mixed-version window.

**Hypothesis** → schema migration breaking old binary.

**Diagnosis** → map app version → SQL query → schema state theo deployment timeline.

**Fix** → rollback app hoặc restore compatibility schema nếu khả thi; về lâu dài áp dụng expand-contract.

**Verification** → staging test phải chạy old và new app versions đồng thời trên expanded schema trước production release.

## 7. Common mistakes

* Xóa/rename column trong cùng release với code switch.
* Thêm `NOT NULL` required column mà old app không populate.
* Backfill hàng triệu rows trong một transaction lớn.
* Dual-write nhưng không có reconciliation/measurement.
* Giữ compatibility code vô hạn và không bao giờ contract.
* Cho EF migration tự chạy đồng thời từ mọi app instance mà không có migration ownership rõ.

## 8. Alternatives

* Maintenance-window migration: đơn giản hơn nếu business chấp nhận downtime.
* Blue-Green với database tách biệt: isolation cao nhưng data synchronization/cutover phức tạp.
* Expand-contract trên shared DB: thực tế cho nhiều zero/minimal-downtime deployments.

## 9. Trade-offs

### Advantages

* Mixed application versions vẫn tương thích.
* Rollback dễ hơn vì old schema chưa bị phá ngay.
* Giảm deployment blast radius.

### Costs / Risks

* Migration kéo dài nhiều releases.
* Temporary dual-read/dual-write code tăng complexity.
* Backfill và reconciliation cần observability.
* Database chứa transitional structures trong một khoảng thời gian.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu database schema và application binaries không đổi atomically trong production.

### Middle

Biết ưu tiên additive migrations và tránh breaking schema changes trong same deployment.

### Senior

Thiết kế dual-read/write, backfill batches, rollback và mixed-version testing.

### Technical Lead / Architect

Định nghĩa database deployment protocol toàn team: migration ownership, compatibility window, contract criteria và observability trước khi destructive changes được phép chạy.

## 11. Key takeaway

* Zero-downtime deployment đòi hỏi schema compatibility, không chỉ deployment slots hay rolling update.
* Expand trước, migrate/observe, contract sau.
* Destructive schema change là release-management decision, không chỉ một dòng migration code.
