# 1. C# `CancellationToken`: cancellation là cooperative protocol, không phải kill switch

## 1. What is it?

`CancellationToken` là tín hiệu cooperative cancellation được truyền xuyên call chain. Mental model đúng không phải “dừng thread”, mà là caller thông báo rằng kết quả không còn cần thiết và từng operation có cơ hội dừng ở safe point.

## 2. Why does it exist?

Trong web backend, client disconnect, request timeout hoặc shutdown có thể khiến công việc đang chạy trở nên vô ích. Nếu downstream SQL/HTTP vẫn tiếp tục, hệ thống tiêu CPU, connection và I/O cho kết quả không ai nhận.

## 3. How does it work?

`CancellationTokenSource` phát signal; token được truyền xuống các API hỗ trợ cancellation. Operation quan sát token và thường ném `OperationCanceledException`.

```text
HTTP aborted
   ↓
RequestAborted
   ↓
Application → EF Core → SqlClient
            → HttpClient
```

Cancellation không rollback side effect đã commit.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id, AppDbContext db, CancellationToken ct) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

Ở application layer, tiếp tục truyền cùng token xuống mọi I/O operation có liên quan.

## 5. Real production scenario

Search endpoint gọi SQL rồi external pricing API. User đổi filter liên tục và browser hủy request cũ. Nếu token được propagate, SQL/HTTP work cũ có thể dừng sớm thay vì tích tụ dưới load.

## 6. Failure scenario & troubleshooting

**Symptom** → request đã timeout nhưng dependency telemetry vẫn cho thấy SQL chạy thêm nhiều giây. **Evidence** → controller nhận token nhưng repository gọi `ToListAsync()` không truyền token. **Hypothesis** → cancellation bị đứt call chain. **Diagnosis** → trace request và inspect signatures. **Fix** → propagate token xuyên boundary. **Verification** → abort request trong integration/load test và quan sát dependency duration giảm.

## 7. Common mistakes

Tạo `new CancellationTokenSource()` ở mọi layer; nuốt `OperationCanceledException` rồi log Error; check token sau khi irreversible side effect đã xảy ra và giả định transaction được undo; truyền `CancellationToken.None` cho tiện.

## 8. Alternatives

Timeout giới hạn thời lượng nhưng không thay thế caller cancellation. Queue/background job phù hợp khi work phải hoàn thành kể cả client disconnect. Hai cơ chế có thể kết hợp bằng linked token.

## 9. Trade-offs

### Advantages

Giải phóng capacity sớm, shutdown sạch hơn và giảm wasted work.

### Costs / Risks

Cần propagation discipline; cancellation ở sai boundary có thể để workflow business ở trạng thái khó hiểu nếu side effects không được thiết kế rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu token là signal cooperative và phải được truyền xuống.

### Middle

Implement cancellation cho EF Core, `HttpClient` và background loops; test canceled path.

### Senior

Phân biệt cancel-safe operation với business workflow phải hoàn thành; xử lý telemetry và transaction boundary.

### Technical Lead / Architect

Quyết định cancellation boundary cho request, job và distributed workflow; xác định operation nào được phép dừng và operation nào cần durable execution.

## 11. Key takeaway

- Cancellation phải được propagate end-to-end mới có giá trị.
- Cancellation không tự rollback side effects.
- Durable business work không nên phụ thuộc lifetime của HTTP request.

# 2. EF Core compiled queries: tối ưu query pipeline khi measurement chứng minh CPU overhead

## 1. What is it?

Compiled query cho phép EF Core tái sử dụng phần compilation của một LINQ query shape. Mental model: nó giảm overhead phía application khi chuẩn bị query; nó không làm SQL execution plan hoặc database I/O tự nhiên nhanh hơn.

## 2. Why does it exist?

EF Core đã cache query compilation theo shape, nên phần lớn ứng dụng không cần compiled query explicit. Nhưng hot path có query nhỏ chạy với tần suất rất cao có thể thấy query-processing overhead đáng kể so với database execution.

## 3. How does it work?

EF nhận expression tree, translate thành SQL/query pipeline rồi cache. `EF.CompileAsyncQuery` tạo delegate tái sử dụng pipeline rõ ràng cho stable query shape.

```text
LINQ shape → translation/compilation → SQL → DB execution
              ↑ compiled query tối ưu phần này
```

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<OrderDto>>
    GetOrder = EF.CompileAsyncQuery(
        (AppDbContext db, Guid id) =>
            db.Orders.AsNoTracking()
              .Where(x => x.Id == id)
              .Select(x => new OrderDto(x.Id, x.Status)));

await foreach (var item in GetOrder(db, id).WithCancellation(ct))
{
    return item;
}
return null;
```

Benchmark phải dùng realistic provider/database và warm process.

## 5. Real production scenario

Internal lookup API chạy một query projection rất nhỏ hàng chục nghìn lần/giây. Database latency thấp và profiling cho thấy EF query processing chiếm tỷ lệ CPU đáng kể. Compiled query có thể đáng thử sau measurement.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries nhưng p95 không đổi. **Evidence** → trace cho thấy 95% latency nằm ở SQL I/O. **Diagnosis** → tối ưu sai bottleneck. **Fix** → đọc execution plan, giảm rows/I/O hoặc sửa access pattern. **Verification** → benchmark end-to-end, không chỉ microbenchmark delegate.

## 7. Common mistakes

Compile mọi query; dynamic query shape làm abstraction khó dùng; nghĩ compiled query tạo database compiled plan; bỏ qua network/locking/I/O; hy sinh readability trước khi profiling.

## 8. Alternatives

EF query cache mặc định thường đủ. Raw SQL/Dapper có thể phù hợp specialized read path nhưng đổi abstraction và maintenance cost. Database optimization thường quan trọng hơn nếu execution time chiếm đa số.

## 9. Trade-offs

### Advantages

Giảm một phần CPU/allocation trên hot stable query paths.

### Costs / Risks

Boilerplate, giảm composability và dễ tối ưu nhầm tầng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ phải được translate trước khi DB thực thi.

### Middle

Biết projection, `AsNoTracking` và đo query trước khi tối ưu.

### Senior

Profile application CPU tách biệt database duration; benchmark compiled query có kiểm soát.

### Technical Lead / Architect

Cho phép optimization này ở measured hot paths, không biến nó thành coding standard toàn hệ thống.

## 11. Key takeaway

- Compiled query tối ưu EF pipeline, không sửa slow SQL.
- EF đã cache query shape; explicit compilation là optimization chuyên biệt.
- Measure end-to-end trước và sau thay đổi.

# 3. SQL Server statistics: execution plan có thể xấu dù index vẫn tồn tại

## 1. What is it?

Statistics mô tả phân bố dữ liệu để SQL Server cardinality estimator dự đoán số rows. Optimizer dùng ước lượng đó để chọn join strategy, index access, memory grant và execution plan.

## 2. Why does it exist?

Optimizer không thể thử mọi plan bằng cách chạy thật. Nó cần cost model dựa trên ước lượng. Nếu estimate sai lớn, index tốt vẫn có thể đi cùng plan tệ.

## 3. How does it work?

```text
SQL → predicates
    → statistics/cardinality estimate
    → candidate plans + cost
    → chosen plan
    → I/O + locks + CPU
    → latency
```

Statistics chứa histogram/density metadata, không phải full copy của data distribution.

## 4. Practical implementation

```sql
SELECT o.Id, o.CustomerId, o.Total
FROM dbo.Orders AS o
WHERE o.Status = @status
  AND o.CreatedAt >= @from;
```

Khi điều tra, xem actual execution plan và so sánh **Estimated Number of Rows** với **Actual Number of Rows**. Có thể kiểm tra statistics:

```sql
DBCC SHOW_STATISTICS ('dbo.Orders', 'IX_Orders_Status_CreatedAt');
```

Không chạy update statistics mù quáng trên production như “fix” mặc định.

## 5. Real production scenario

Bảng Orders tăng nhanh sau campaign. Query từng chạy 80 ms bỗng mất 5 giây. Index vẫn tồn tại nhưng plan chọn Nested Loops với estimate vài chục rows trong khi actual là hàng trăm nghìn.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 SQL tăng sau data growth. **Evidence** → estimated/actual rows lệch mạnh, logical reads tăng. **Hypothesis** → stale/inadequate statistics hoặc skew/parameter sensitivity. **Diagnosis** → inspect stats age, histogram và parameter values. **Fix** → update statistics phù hợp hoặc thiết kế lại query/index/parameter strategy tùy root cause. **Verification** → actual plan, reads và duration ổn định qua representative parameters.

## 7. Common mistakes

Chỉ kiểm tra “có index không”; rebuild mọi index để gián tiếp update stats; assume một plan phù hợp mọi parameter; nhìn estimated plan mà không lấy runtime evidence.

## 8. Alternatives

Query/index redesign, filtered statistics/indexes, parameter-sensitive plan features hoặc query decomposition có thể phù hợp tùy workload. Không có một remedy universal.

## 9. Trade-offs

### Advantages

Statistics giúp optimizer chọn plan mà không cần brute-force execution.

### Costs / Risks

Maintenance có CPU/I/O cost; sampled statistics có thể không mô tả tốt skew; data thay đổi làm estimate cũ dần.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index và statistics là hai khái niệm khác nhau.

### Middle

Đọc actual plan và so estimated/actual rows.

### Senior

Liên kết skew, parameter sensitivity, statistics và plan regression với production latency.

### Technical Lead / Architect

Thiết kế monitoring/maintenance dựa trên workload và data growth thay vì scheduled maintenance mù quáng.

## 11. Key takeaway

- Optimizer ra quyết định từ estimates; estimate sai có thể tạo plan sai.
- “Index tồn tại” không chứng minh query sẽ nhanh.
- Điều tra bằng actual plan, I/O và representative parameters.

# 4. Redis cache stampede: một key hết hạn có thể biến cache thành database outage

## 1. What is it?

Cache stampede xảy ra khi nhiều requests cùng miss một hot key và đồng thời tải lại cùng dữ liệu từ source. Cache vốn giảm tải lại trở thành trigger tạo burst vào database/API.

## 2. Why does it exist?

Cache-aside đơn giản thường làm `GET → miss → DB → SET`. Với một request thì ổn; với 5.000 concurrent requests đúng lúc TTL hết hạn, 5.000 database queries có thể chạy cùng lúc.

## 3. How does it work?

```text
Hot key expires
   ↓
N requests → cache miss × N
   ↓
Database load × N
   ↓
latency ↑ → concurrency ↑ → cascading failure
```

Mitigation có thể gồm single-flight/local lock, distributed coordination, stale-while-revalidate, TTL jitter hoặc proactive refresh.

## 4. Practical implementation

```csharp
private readonly SemaphoreSlim _gate = new(1, 1);

public async Task<Product> GetAsync(string key, CancellationToken ct)
{
    var cached = await cache.GetStringAsync(key, ct);
    if (cached is not null) return Deserialize(cached);

    await _gate.WaitAsync(ct);
    try
    {
        cached = await cache.GetStringAsync(key, ct); // double-check
        if (cached is not null) return Deserialize(cached);

        var value = await repository.LoadAsync(key, ct);
        await cache.SetStringAsync(key, Serialize(value), options, ct);
        return value;
    }
    finally { _gate.Release(); }
}
```

Đây chỉ chống stampede trong một process. Multi-instance cần strategy khác hoặc chấp nhận bounded duplication.

## 5. Real production scenario

Homepage product catalog có một key cực nóng TTL 10 phút. Mỗi lần expire, SQL CPU spike đúng chu kỳ 10 phút. Root cause không phải SQL query riêng lẻ mà là synchronized misses.

## 6. Failure scenario & troubleshooting

**Symptom** → latency/DB CPU spike theo chu kỳ TTL. **Evidence** → Redis misses tăng đột biến cùng key; SQL call volume tăng tương ứng. **Diagnosis** → stampede. **Fix** → TTL jitter, request coalescing hoặc stale refresh. **Verification** → expire key dưới load và đo downstream call amplification.

## 7. Common mistakes

Dùng distributed lock cho mọi cache miss dù overhead lớn; lock không timeout; không double-check cache sau lock; tất cả keys dùng cùng TTL; Redis outage fallback không có backpressure nên DB sập.

## 8. Alternatives

`IMemoryCache` + per-instance single-flight cho workload đơn giản; CDN cho public content; precomputed read model nếu dữ liệu vốn expensive; đôi khi bỏ cache và tối ưu DB đơn giản hơn.

## 9. Trade-offs

### Advantages

Coalescing giảm downstream burst và ổn định tail latency.

### Costs / Risks

Coordination tăng complexity; stale-while-revalidate đổi freshness lấy availability; distributed lock có thể thành dependency mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss đồng thời khác một cache miss đơn lẻ.

### Middle

Implement double-check và TTL jitter; load test expiration.

### Senior

Thiết kế fallback khi Redis/DB degraded và đo amplification factor.

### Technical Lead / Architect

Quyết định freshness budget, ownership invalidation và liệu cache có đáng tồn tại so với read model/CDN/database optimization.

## 11. Key takeaway

- Cache phải được test cả lúc hit lẫn lúc expire/fail.
- Hot-key expiration là concurrency event.
- Reliability của cache strategy phụ thuộc behavior khi cache không giúp được gì.

# 5. Outbox Pattern: nối database transaction với messaging mà không cần distributed transaction

## 1. What is it?

Outbox Pattern ghi business state và message-to-publish vào cùng local database transaction. Một publisher riêng đọc outbox rồi gửi message ra broker. Mental model: commit “ý định phát event” atomically với business change, còn delivery ra broker xảy ra sau.

## 2. Why does it exist?

Flow `SaveChanges → Publish` có crash window: DB commit thành công nhưng process chết trước publish. Flow `Publish → SaveChanges` có window ngược lại. Không có local transaction nào tự atomic giữa SQL và Service Bus.

## 3. How does it work?

```text
Transaction
 ├─ UPDATE Orders
 └─ INSERT Outbox
       ↓ commit
Publisher → Outbox → Service Bus
                         ↓
                  idempotent consumer
```

Outbox thường cho at-least-once publication; duplicate vẫn có thể xảy ra nếu publish thành công nhưng marking-sent thất bại.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

order.MarkPaid();
db.Outbox.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    Type = "OrderPaid",
    Payload = JsonSerializer.Serialize(new { order.Id }),
    OccurredAtUtc = DateTime.UtcNow
});

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Publisher phải retry có backoff và consumer phải idempotent theo message/event ID.

## 5. Real production scenario

Payment callback cập nhật order rồi cần phát `OrderPaid` cho fulfillment. Nếu Service Bus tạm down, transaction order vẫn commit cùng outbox record; publisher gửi event khi broker hồi phục.

## 6. Failure scenario & troubleshooting

**Symptom** → outbox backlog tăng. **Evidence** → DB commits bình thường, publish failures/timeouts tăng. **Hypothesis** → broker/network/credential issue. **Diagnosis** → metrics theo oldest pending age và retry reason. **Fix** → phục hồi dependency, bounded retry, scale publisher nếu cần. **Verification** → backlog drain mà downstream không tạo duplicate side effects.

## 7. Common mistakes

Cho rằng Outbox tạo exactly-once; xóa record ngay khi send mà không có retention/audit strategy; publisher nhiều instances nhưng không claim rows an toàn; payload schema không version; outbox table tăng vô hạn.

## 8. Alternatives

Distributed transaction chỉ khả thi ở một số technology boundary và tăng coupling. Change Data Capture có thể publish từ database log nhưng operational model khác. Nếu workflow không cần event reliability cao, direct publish có thể đủ đơn giản hơn.

## 9. Trade-offs

### Advantages

Đóng crash window giữa DB state và message intent, không cần distributed ACID.

### Costs / Risks

Eventual consistency, duplicate delivery, outbox cleanup, publisher monitoring và schema evolution.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hai external systems không cùng transaction một cách tự nhiên.

### Middle

Implement outbox record trong transaction và background publisher.

### Senior

Thiết kế claiming, retries, idempotency, retention và observability.

### Technical Lead / Architect

Quyết định workflow nào thực sự cần durable messaging; xác định consistency SLA và ownership của producer/consumer contracts.

## 11. Key takeaway

- Outbox giải quyết atomicity giữa business commit và publish intent.
- Nó không tạo exactly-once delivery.
- Idempotent consumer và backlog observability là phần của pattern, không phải optional extras.

# 6. Azure App Service deployment slots: zero-downtime deployment vẫn cần compatibility discipline

## 1. What is it?

Deployment slot là live environment riêng trong cùng App Service có hostname/configuration riêng, cho phép deploy và warm version mới trước khi swap vào Production.

## 2. Why does it exist?

Deploy trực tiếp có thể restart app hoặc đưa code chưa warm vào traffic. Slot cho phép validation trước cutover và swap nhanh hơn, nhưng không làm database/API contracts tự động backward-compatible.

## 3. How does it work?

```text
Build artifact → Staging slot → warm/health test
                                ↓ swap
Users → Production routing → new version
```

Một số settings có thể được đánh dấu slot-specific để không swap, ví dụ environment-specific secrets/configuration.

## 4. Practical implementation

Pipeline nên deploy cùng immutable artifact vào staging, chạy smoke/health tests rồi swap. Application cần health endpoint phản ánh khả năng phục vụ request mà không tạo destructive side effects.

```csharp
builder.Services.AddHealthChecks()
    .AddDbContextCheck<AppDbContext>();
app.MapHealthChecks("/health/ready");
```

Database migration nên theo expand/contract khi old và new versions có thể cùng tồn tại trong transition.

## 5. Real production scenario

API thêm column mới. Nếu migration rename/drop column trước khi swap, production slot cũ có thể lỗi ngay trong deployment window. Expand-first thêm schema tương thích, deploy code mới, rồi cleanup ở release sau.

## 6. Failure scenario & troubleshooting

**Symptom** → staging healthy nhưng ngay sau swap production trả 500. **Evidence** → configuration/connection string khác giữa slots. **Hypothesis** → slot setting bị swap hoặc staging không test production-like dependency. **Diagnosis** → compare configuration names, slot flags và telemetry. **Fix** → correct slot-specific settings, swap back nếu safe. **Verification** → pre-swap validation và post-swap synthetic checks.

## 7. Common mistakes

Xem slot như complete rollback cho destructive DB migration; staging dùng dependency giả khác production; không warm app; swap secrets sai; artifact giữa environments khác nhau.

## 8. Alternatives

Blue-Green trên infrastructure riêng cho isolation mạnh hơn nhưng tốn cost. Canary giảm blast radius. Rolling deployment phù hợp container/Kubernetes nhưng yêu cầu version coexistence tương tự.

## 9. Trade-offs

### Advantages

Warm-up, fast cutover, rollback application version thuận tiện.

### Costs / Risks

Thêm environment/configuration complexity và compute cost; shared database vẫn là compatibility boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu staging slot là running app riêng, không chỉ folder deploy.

### Middle

Deploy, health-check và swap với configuration đúng.

### Senior

Thiết kế database/API compatibility, smoke tests và rollback path.

### Technical Lead / Architect

Chọn slot, canary hay blue-green dựa trên blast radius/SLO/cost; định nghĩa release contract cho schema và external dependencies.

## 11. Key takeaway

- Zero-downtime deployment là compatibility problem, không chỉ routing problem.
- Slot swap không rollback destructive database change.
- Immutable artifact + production-like validation giảm deployment uncertainty.

# 7. Docker image layers: build reproducibility, cache và attack surface

## 1. What is it?

Docker image gồm các immutable filesystem layers tạo bởi build instructions. Container thêm writable layer khi chạy. Layering ảnh hưởng build cache, image size, reproducibility và những gì thực sự được ship vào production.

## 2. Why does it exist?

Layer reuse giúp distribution/build hiệu quả. Nhưng Dockerfile thiếu discipline có thể invalidate cache liên tục, copy secrets/source thừa hoặc ship SDK/compiler vào runtime image.

## 3. How does it work?

```text
base runtime layer
   + app dependencies
   + published binaries
   = image
   + writable container layer at runtime
```

Một thay đổi ở layer sớm làm các layer sau phải rebuild.

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY *.sln .
COPY src/MyApi/*.csproj src/MyApi/
RUN dotnet restore src/MyApi/MyApi.csproj
COPY . .
RUN dotnet publish src/MyApi/MyApi.csproj -c Release -o /app --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

Multi-stage build giữ SDK/build tooling khỏi runtime image.

## 5. Real production scenario

CI build .NET API mất 12 phút vì `COPY . .` đứng trước `dotnet restore`, khiến mọi code change invalidate package restore layer. Reorder Dockerfile giảm build time mà không đổi runtime behavior.

## 6. Failure scenario & troubleshooting

**Symptom** → image bất ngờ tăng hàng GB hoặc chứa file nhạy cảm. **Evidence** → inspect history/layers và build context. **Hypothesis** → `COPY . .` đưa artifacts/secrets vào image. **Diagnosis** → inspect `.dockerignore` và layer contents. **Fix** → narrow COPY, multi-stage build, rotate secret nếu đã leak. **Verification** → scan image và compare layer sizes.

## 7. Common mistakes

Dùng `latest` không pin strategy; copy `.git`, test artifacts hoặc secrets; chạy app bằng root không cần thiết; cài diagnostic tools vô hạn trong production image; optimize layer count mà bỏ qua clarity/security.

## 8. Alternatives

Native host/App Service deployment đơn giản hơn nếu container portability không cần thiết. Buildpacks có thể giảm Dockerfile maintenance nhưng đổi control model.

## 9. Trade-offs

### Advantages

Repeatable packaging, environment consistency, efficient layer distribution.

### Costs / Risks

Image lifecycle, CVE patching, registry/storage và container operational knowledge trở thành trách nhiệm mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu image immutable và container không phải VM đầy đủ.

### Middle

Viết multi-stage Dockerfile, `.dockerignore` và debug layers.

### Senior

Tối ưu cache, supply-chain/security scanning và runtime least privilege.

### Technical Lead / Architect

Quyết định container có tạo giá trị triển khai thực hay chỉ thêm platform complexity; chuẩn hóa base image/patch ownership.

## 11. Key takeaway

- Layer order ảnh hưởng build cache và artifact contents.
- Build tools không nên mặc định đi vào runtime image.
- Containerization tạo thêm security/patch lifecycle cần owner.

# 8. OpenTelemetry metrics: p95/p99 và cardinality trong production observability

## 1. What is it?

Metrics là aggregated numeric telemetry theo thời gian. Với latency, histogram cho phép phân tích distribution/percentiles thay vì chỉ average. Labels/attributes phân tách dimensions nhưng mỗi combination tạo thêm time series.

## 2. Why does it exist?

Average 100 ms có thể che 1% requests mất 5 giây. Production reliability thường nằm ở tail latency. Nhưng metrics có cardinality vô hạn như `userId` có thể làm telemetry backend tốn memory/cost nghiêm trọng.

## 3. How does it work?

```text
requests → histogram observations
              ↓ aggregate
        p50 / p95 / p99

metric name + attribute combinations = time series
```

Metrics trả lời “bao nhiêu/mức nào”; traces giúp giải thích từng request chậm; logs cung cấp event detail.

## 4. Practical implementation

```csharp
static readonly Meter Meter = new("Checkout.Api");
static readonly Histogram<double> Duration =
    Meter.CreateHistogram<double>("checkout.duration", "ms");

var sw = Stopwatch.StartNew();
try
{
    await service.CheckoutAsync(ct);
}
finally
{
    Duration.Record(sw.Elapsed.TotalMilliseconds,
        new KeyValuePair<string, object?>("result", "completed"));
}
```

Không gắn `orderId`, `userId` hoặc raw URL chứa IDs làm metric attributes.

## 5. Real production scenario

Checkout average latency chỉ tăng từ 180 lên 210 ms, nhưng p99 tăng từ 900 ms lên 8 s. Trace exemplars/dependency spans cho thấy một payment provider bị tail latency cao.

## 6. Failure scenario & troubleshooting

**Symptom** → telemetry bill/memory tăng mạnh. **Evidence** → số time series tăng theo traffic/user count. **Hypothesis** → high-cardinality attribute. **Diagnosis** → inspect dimensions như request ID/customer ID. **Fix** → bỏ/normalize attributes, chuyển detail sang traces/logs. **Verification** → active-series count và ingestion cost giảm.

## 7. Common mistakes

Chỉ dashboard average; dùng p99 với sample volume quá nhỏ mà không hiểu uncertainty; metric labels chứa unbounded values; alert mọi spike ngắn; logs thay cho metrics ở mọi thứ.

## 8. Alternatives

Application Insights native metrics có thể đủ nếu không cần vendor-neutral instrumentation. Logs thích hợp forensic detail; traces thích hợp critical path. Ba signal bổ sung nhau.

## 9. Trade-offs

### Advantages

Metrics rẻ hơn raw event telemetry cho aggregate monitoring và SLOs.

### Costs / Risks

Aggregation mất per-request detail; cardinality sai làm cost explode; percentile interpretation cần traffic context.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu average khác percentile và metric khác log.

### Middle

Instrument counters/histograms với bounded attributes.

### Senior

Thiết kế SLI, correlate metrics với traces và kiểm soát cardinality/cost.

### Technical Lead / Architect

Định nghĩa observability conventions, retention và telemetry budget; chọn signal dựa trên câu hỏi vận hành cần trả lời.

## 11. Key takeaway

- Tail latency thường quan trọng hơn average.
- Metric dimensions phải bounded.
- Logs + Metrics + Traces phục vụ các lớp câu hỏi khác nhau.

# 9. OAuth 2.0 access token validation: API phải xác minh issuer, audience, signature và lifetime

## 1. What is it?

Access token là credential cho resource server. Với JWT access token, API phải validate cryptographic signature và các claims/properties liên quan đến trust boundary như issuer, audience và lifetime trước khi authorization.

## 2. Why does it exist?

JWT chỉ là encoded structure; decode payload không chứng minh token đáng tin. Token hợp lệ cho API A cũng không mặc nhiên hợp lệ cho API B. Authentication phải xác lập identity/trust trước authorization policy.

## 3. How does it work?

```text
Client → Bearer token → API
                       ↓
        signature + issuer + audience + lifetime
                       ↓
                    claims
                       ↓
             authorization policy
```

API thường lấy signing keys từ trusted identity provider metadata/JWKS và xử lý key rotation.

## 4. Practical implementation

```csharp
builder.Services.AddAuthentication("Bearer")
    .AddJwtBearer("Bearer", options =>
    {
        options.Authority = configuration["Auth:Authority"];
        options.Audience = "orders-api";
        options.RequireHttpsMetadata = true;
    });

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("orders.read", p =>
        p.RequireClaim("scope", "orders.read"));
});
```

Production config phải dùng exact issuer/audience model của identity provider; scope/role semantics không nên đoán từ token shape.

## 5. Real production scenario

Company có Orders API và Admin API dùng cùng identity provider. Nếu Admin API không validate audience đúng, token cấp cho Orders API có thể bị chấp nhận sai boundary dù signature hoàn toàn hợp lệ.

## 6. Failure scenario & troubleshooting

**Symptom** → token hoạt động local nhưng production trả 401. **Evidence** → authentication logs cho thấy issuer/audience mismatch hoặc signing key resolution failure. **Hypothesis** → environment authority/configuration khác. **Diagnosis** → kiểm tra token metadata an toàn, issuer, audience và server clock. **Fix** → sửa trust configuration, không disable validation. **Verification** → tests gồm valid token, wrong audience, expired token và unauthorized scope.

## 7. Common mistakes

Chỉ decode JWT; disable issuer/audience validation để “fix” 401; log full access token; dùng authentication thay authorization; assume CORS bảo vệ API; chấp nhận token từ multiple issuers mà không có explicit trust model.

## 8. Alternatives

Opaque tokens + introspection chuyển validation về authorization server nhưng thêm network dependency. Cookie authentication phù hợp browser/server scenarios khác. Managed Identity phù hợp Azure service-to-service và giảm secret handling.

## 9. Trade-offs

### Advantages

JWT validation local giảm per-request call tới identity provider và hỗ trợ distributed APIs.

### Costs / Risks

Revocation không tức thời theo mặc định; key rotation/configuration và claims semantics cần quản trị chặt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt authentication và authorization; JWT decode không bằng validate.

### Middle

Configure `JwtBearer`, policies và integration tests negative cases.

### Senior

Hiểu key rotation, clock skew, issuer/audience boundaries và token leakage risks.

### Technical Lead / Architect

Thiết kế identity trust boundaries, token lifetime, service-to-service strategy và claims ownership giữa bounded systems.

## 11. Key takeaway

- Signature hợp lệ chưa đủ; token còn phải dành cho đúng issuer/audience và còn hiệu lực.
- Authentication xác minh credential; authorization quyết định hành động được phép.
- Không tắt validation để chữa configuration mismatch.

# 10. Vue/TypeScript request cancellation: tránh stale UI khi asynchronous responses về sai thứ tự

## 1. What is it?

Frontend request cancellation dùng `AbortController` để báo rằng fetch cũ không còn cần thiết. Mental model: UI state phải phản ánh intent mới nhất của user, không phải response nào về sau cùng theo network timing.

## 2. Why does it exist?

User gõ search `car`, rồi nhanh chóng đổi thành `cargo`. Request `car` có thể chậm hơn và trả về sau `cargo`, ghi đè state bằng kết quả cũ. Đây là race condition ở UI dù JavaScript chạy event loop một thread.

## 3. How does it work?

```text
intent A → request A ───────────────> late response
intent B → cancel A → request B → response B → render
```

Cancellation giảm wasted work phía browser và, nếu server propagate disconnect/cancellation, có thể giảm backend work.

## 4. Practical implementation

```ts
import { ref, watch } from 'vue'

const query = ref('')
const results = ref<Product[]>([])
let controller: AbortController | undefined

watch(query, async value => {
  controller?.abort()
  controller = new AbortController()

  try {
    const response = await fetch(`/api/search?q=${encodeURIComponent(value)}`, {
      signal: controller.signal
    })
    if (!response.ok) throw new Error(`HTTP ${response.status}`)
    results.value = await response.json()
  } catch (error) {
    if (error instanceof DOMException && error.name === 'AbortError') return
    throw error
  }
})
```

Search UI thường kết hợp debounce để tránh gửi request cho mọi keystroke.

## 5. Real production scenario

Automotive marketplace có filters make/model/price. User thay đổi liên tục trên mobile network. Không cancellation/versioning, response cũ có thể render sai filter và tạo cảm giác backend trả dữ liệu không nhất quán.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị kết quả của filter trước. **Evidence** → Network tab cho thấy request cũ hoàn tất sau request mới. **Hypothesis** → race giữa asynchronous responses. **Diagnosis** → log request sequence/filter snapshot ở client. **Fix** → abort previous request hoặc sequence-token check trước state update. **Verification** → throttle network trong DevTools và thay filter nhanh.

## 7. Common mistakes

Coi `AbortError` là production error; cancellation nhưng backend operation vẫn không nhận token; không debounce high-frequency input; mutate shared state từ nhiều request paths; assume Promise completion order bằng invocation order.

## 8. Alternatives

Sequence number/latest-request-wins guard vẫn hữu ích khi transport không cancel được. Debounce giảm request count nhưng không tự loại race. Data-fetching libraries có thể quản lý cancellation/cache nhưng thêm abstraction.

## 9. Trade-offs

### Advantages

UI đúng intent mới nhất, giảm wasted network/backend work và noise.

### Costs / Risks

State management phức tạp hơn; cancellation semantics phải được xử lý như expected control flow, không phải lỗi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async responses có thể về không đúng thứ tự gửi.

### Middle

Implement `AbortController`, debounce và loading/error state đúng.

### Senior

Trace race xuyên browser/API, phân biệt cancellation với failure và thiết kế cache/state ownership.

### Technical Lead / Architect

Quyết định client data-fetching conventions và contract với backend cancellation; tránh framework/library chỉ để giải quyết flow đơn giản nếu native primitives đủ dùng.

## 11. Key takeaway

- Single-threaded JavaScript vẫn có asynchronous race conditions.
- UI nên commit state theo current intent, không theo response arrival order.
- Frontend cancellation có giá trị lớn hơn khi backend cũng propagate cancellation.
