# 1. C# `ArrayPool<T>` và buffer ownership: giảm allocation mà không tạo data leak hoặc use-after-return logic bug

## 1. What is it?

`ArrayPool<T>` là cơ chế tái sử dụng arrays thay vì cấp phát array mới cho mỗi operation. Mental model đúng là **thuê một buffer dùng tạm rồi trả lại pool**, không phải nhận một array thuộc sở hữu của caller.

```text
Shared pool
   ↓ Rent
temporary buffer
   ↓ use
Return
   ↓
Shared pool
```

Pool đặc biệt hữu ích với hot paths xử lý serialization, networking hoặc file chunks nơi arrays trung bình/lớn được tạo liên tục.

## 2. Why does it exist?

Allocation ngắn hạn rất rẻ trong .NET, vì vậy pooling không phải mặc định tốt hơn. Nhưng workload tạo lượng lớn buffers có thể tăng allocation rate, Gen 0/Gen 1 collections và với buffers lớn có thể tạo pressure lên LOH.

Pooling đổi allocation pressure lấy ownership complexity. Nó đáng dùng khi profiling chứng minh allocation là bottleneck đáng kể.

## 3. How does it work?

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    // buffer.Length có thể lớn hơn kích thước yêu cầu.
    await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), cancellationToken);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);
}
```

`Rent(65536)` đảm bảo buffer ít nhất kích thước đó, không đảm bảo đúng bằng. Sau `Return`, code không còn quyền sử dụng buffer vì caller khác có thể thuê lại ngay.

## 4. Practical implementation

Với dữ liệu nhạy cảm, clear trước khi trả:

```csharp
byte[] buffer = ArrayPool<byte>.Shared.Rent(4096);
try
{
    var read = await source.ReadAsync(buffer.AsMemory(0, 4096), cancellationToken);
    await destination.WriteAsync(buffer.AsMemory(0, read), cancellationToken);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
}
```

`clearArray: true` có CPU cost; chỉ dùng khi threat/data-sensitivity model yêu cầu.

## 5. Real production scenario

Một file-processing API xử lý hàng nghìn chunks mỗi giây. Profiling cho thấy phần lớn allocation đến từ `new byte[64 * 1024]`. Pooling giảm allocation rate và GC frequency rõ rệt. Team chỉ pool buffer tại hot path này, không biến mọi array trong codebase thành pooled resource.

## 6. Failure scenario & troubleshooting

**Symptom** → payload đôi lúc chứa bytes của request trước.

**Evidence** → buffer được trả về pool nhưng một async operation vẫn giữ reference.

**Hypothesis** → ownership vượt quá lexical lifetime.

**Diagnosis** → trace buffer lifecycle và tìm nơi capture array trong task/callback.

**Fix** → chỉ `Return` sau operation cuối cùng; copy dữ liệu nếu ownership cần sống lâu hơn.

**Verification** → stress test concurrent requests và bật validation quanh buffer boundaries.

## 7. Common mistakes

* Dùng buffer sau `Return`.
* Giả định `Rent(n).Length == n`.
* Pool tiny arrays mà chưa đo allocation pressure.
* Trả buffer chứa secrets mà không cân nhắc clearing.
* Quên `finally`, làm buffer không được trả khi exception xảy ra.

## 8. Alternatives

`new T[]` đơn giản và thường đủ tốt. `MemoryPool<T>` phù hợp khi cần memory-owner abstraction. `stackalloc` hữu ích cho buffers rất nhỏ với lifetime ngắn và giới hạn stack rõ ràng.

## 9. Trade-offs

### Advantages

Giảm allocation/GC pressure trên hot path và tái sử dụng buffers lớn.

### Costs / Risks

Ownership phức tạp hơn, có nguy cơ data leakage, retention và correctness bug. Pool cũng giữ memory để tái sử dụng nên process memory không nhất thiết giảm tương ứng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Rent` là mượn, `Return` là mất ownership.

### Middle

Dùng `try/finally`, giới hạn slice đúng và không capture buffer quá lifetime.

### Senior

Chỉ áp dụng sau profiling; đánh giá security và concurrency implications.

### Technical Lead / Architect

Quyết định hot paths nào đáng đổi simplicity lấy memory-performance complexity.

## 11. Key takeaway

* Pooling tối ưu allocation, không phải business logic.
* Buffer ownership phải rõ hơn cả API syntax.
* Đừng dùng `ArrayPool<T>` nếu profiling chưa chỉ ra vấn đề cần giải quyết.

# 2. ASP.NET Core `ProblemDetails`: biến error contract thành API boundary ổn định thay vì trả exception text tùy hứng

## 1. What is it?

`ProblemDetails` là representation chuẩn hóa cho HTTP API errors, cung cấp các trường như `type`, `title`, `status`, `detail`, `instance` và extensions.

Nó tách **internal exception** khỏi **public API error contract**.

## 2. Why does it exist?

Nếu mỗi endpoint tự trả `{ error: ... }`, string hoặc stack trace, client phải xử lý nhiều shapes và server vô tình leak implementation details. Error contract cần ổn định giống success contract.

## 3. How does it work?

Request failure được phân loại thành domain/application/infrastructure outcome rồi map sang HTTP semantics.

```text
Exception / validation / domain conflict
             ↓
       error mapping
             ↓
       ProblemDetails
             ↓
400 / 404 / 409 / 500 ...
```

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler();

app.MapGet("/orders/{id:guid}", async (Guid id, AppDbContext db) =>
{
    var order = await db.Orders.FindAsync(id);
    return order is null
        ? Results.Problem(
            statusCode: StatusCodes.Status404NotFound,
            title: "Order not found",
            extensions: new Dictionary<string, object?> { ["code"] = "ORDER_NOT_FOUND" })
        : Results.Ok(order);
});
```

Machine-readable `code` nên ổn định hơn localized `detail`.

## 5. Real production scenario

Mobile app và web frontend cùng consume Orders API. Nếu backend đổi exception message, clients không nên hỏng. Client branch theo HTTP status + stable error code, còn human-readable message có thể thay đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → production response chứa connection string hoặc stack trace.

**Evidence** → middleware serialize `exception.ToString()` vào `detail`.

**Hypothesis** → internal diagnostics bị trộn với public contract.

**Diagnosis** → inspect 500 response và exception handler.

**Fix** → log full exception server-side với correlation/trace ID; client chỉ nhận generic 500 ProblemDetails.

**Verification** → integration test response không chứa sensitive internals.

## 7. Common mistakes

* Trả 200 với `success=false` cho mọi error.
* Dùng exception message làm stable client code.
* Map mọi exception thành 500.
* Leak stack trace/SQL details.
* Không document 409/422/429 contracts.

## 8. Alternatives

Custom envelope có thể cần cho legacy ecosystem, nhưng phải có schema rõ. gRPC dùng status/details semantics khác. Không có lý do bắt mọi protocol phải dùng ProblemDetails.

## 9. Trade-offs

### Advantages

Chuẩn hóa clients, observability và API documentation.

### Costs / Risks

Cần governance cho error taxonomy; over-modeling hàng trăm error codes cũng tạo maintenance burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP status và error body là contract.

### Middle

Map validation/not-found/conflict đúng và viết integration tests.

### Senior

Thiết kế taxonomy, security boundary và backward compatibility.

### Technical Lead / Architect

Chuẩn hóa error contract xuyên services mà không ép mọi domain dùng cùng một danh sách lỗi khổng lồ.

## 11. Key takeaway

* Exception là implementation detail; ProblemDetails là API contract.
* Client nên dựa vào stable semantics, không parse exception text.
* Diagnostics đầy đủ nằm trong telemetry, không nằm trong public 500 response.

# 3. EF Core transaction boundaries và execution strategy: retry transaction đúng cách khi transient database failure xảy ra

## 1. What is it?

EF Core execution strategy có thể retry database operations gặp transient failures. Nhưng khi application tự mở transaction, toàn bộ unit cần được execution strategy thực thi lại như một delegate có thể replay.

## 2. Why does it exist?

Cloud database connections có thể transiently fail. Retry một command riêng lẻ thường an toàn hơn fail ngay. Nhưng retry sai boundary có thể khiến transaction state không còn hợp lệ hoặc business side effect chạy hai lần.

## 3. How does it work?

Một execution strategy coi operation là replayable unit:

```text
Attempt transaction
  ↓ transient failure
Rollback/connection lost
  ↓
Retry entire transaction delegate
```

Không nên retry chỉ statement cuối trong một multi-step invariant.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var transaction =
        await db.Database.BeginTransactionAsync(cancellationToken);

    order.Approve();
    db.AuditEntries.Add(new AuditEntry(order.Id, "Approved"));

    await db.SaveChangesAsync(cancellationToken);
    await transaction.CommitAsync(cancellationToken);
});
```

External HTTP calls không nên đặt tùy tiện trong replayable DB transaction vì retry có thể gọi chúng nhiều lần.

## 5. Real production scenario

Approval workflow update request và insert audit row. Một transient disconnect xảy ra giữa operations. Nếu team retry `SaveChanges` không hiểu transaction boundary, state có thể khó xác định. Wrapping complete DB unit trong execution strategy giữ retry semantics rõ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → payment API bị gọi hai lần sau SQL transient error.

**Evidence** → external call nằm bên trong transaction delegate được retry.

**Hypothesis** → non-idempotent side effect bị replay.

**Diagnosis** → correlate retry logs, payment idempotency key và DB transaction attempts.

**Fix** → giữ external side effect ngoài replayable DB unit hoặc dùng Outbox/idempotency.

**Verification** → fault-injection transient DB failure và xác nhận payment effect chỉ xảy ra một lần.

## 7. Common mistakes

* Assume retry luôn safe.
* Mở transaction ngoài execution strategy delegate.
* Giữ transaction mở trong khi gọi slow HTTP dependency.
* Retry business conflict như transient network error.

## 8. Alternatives

Không retry nếu workload không cần hoặc error không transient. Outbox phù hợp khi DB state phải dẫn tới external message. Stored procedure có thể đóng gói một số database-only atomic operations.

## 9. Trade-offs

### Advantages

Tăng resilience với transient database failures và giữ atomic DB unit.

### Costs / Risks

Replay semantics phức tạp; transaction dài tăng locks; side effects ngoài DB cần idempotency/boundary khác.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction atomicity và transient failure khác business failure.

### Middle

Dùng execution strategy đúng với explicit transaction.

### Senior

Nhận diện replay-unsafe side effects và ambiguous commit scenarios.

### Technical Lead / Architect

Thiết kế transaction boundary nhỏ, retry policy và integration consistency như một hệ thống.

## 11. Key takeaway

* Retry phải bao quanh đúng atomic unit.
* Replayable database code không đồng nghĩa external side effects replayable.
* Transaction càng dài, operational cost càng cao.

# 4. PostgreSQL MVCC và VACUUM: vì sao reader không block writer nhưng dead tuples vẫn có thể làm database chậm dần

## 1. What is it?

PostgreSQL dùng Multi-Version Concurrency Control (MVCC): update tạo row version mới thay vì overwrite version cũ ngay tại chỗ. Transaction nhìn snapshot phù hợp với visibility rules.

## 2. Why does it exist?

MVCC giảm contention giữa readers và writers. Reader có thể tiếp tục đọc version phù hợp trong khi writer tạo version mới.

Đổi lại, old row versions không biến mất tức thì. Chúng trở thành dead tuples cần VACUUM reclaim.

## 3. How does it work?

```text
Row v1 visible to old snapshot
   ↓ UPDATE
Row v2 visible to new transactions
Row v1 becomes dead when no snapshot needs it
   ↓
VACUUM can reclaim space
```

Long-running transactions giữ old snapshot và có thể ngăn cleanup hiệu quả.

## 4. Practical implementation

Điều tra table churn:

```sql
SELECT relname, n_live_tup, n_dead_tup,
       last_autovacuum, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Tìm transactions sống lâu:

```sql
SELECT pid, xact_start, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

## 5. Real production scenario

Một SaaS table cập nhật status liên tục. Một reporting transaction giữ snapshot hàng giờ. Dead tuples tăng, table/index bloat tăng và queries đọc nhiều pages hơn dù logical row count gần như không đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → query latency và disk usage tăng dần.

**Evidence** → `n_dead_tup` cao, autovacuum chạy nhưng không reclaim đủ; có transaction rất cũ.

**Hypothesis** → long-running snapshot cản cleanup hoặc autovacuum tuning không phù hợp churn.

**Diagnosis** → inspect `pg_stat_activity`, table stats và I/O.

**Fix** → xử lý transaction cũ, tune autovacuum cho hot table, giảm transaction lifetime.

**Verification** → dead tuples và pages read giảm theo thời gian.

## 7. Common mistakes

* Nghĩ VACUUM giống database shrink.
* Giữ transaction mở quanh user interaction.
* Chỉ nhìn CPU mà bỏ qua bloat/I/O.
* Disable autovacuum vì thấy nó tiêu resource.

## 8. Alternatives

SQL Server cũng dùng row-versioning trong một số isolation modes nhưng storage/cleanup mechanics khác. Pessimistic locking đơn giản về version cleanup nhưng tăng reader/writer contention.

## 9. Trade-offs

### Advantages

Read/write concurrency tốt và snapshot semantics mạnh.

### Costs / Risks

Dead tuples, vacuum work, transaction-ID management và storage amplification là operational cost thực tế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu update có thể tạo version mới thay vì sửa tại chỗ.

### Middle

Đọc table/activity statistics và giữ transactions ngắn.

### Senior

Liên kết MVCC, bloat, vacuum, indexes và query I/O.

### Technical Lead / Architect

Thiết kế reporting/batch workloads không giữ OLTP snapshots vô hạn và đặt observability phù hợp.

## 11. Key takeaway

* MVCC mua concurrency bằng version-management cost.
* Long transactions có hậu quả vượt xa lock duration.
* VACUUM là phần bình thường của PostgreSQL operation, không phải repair tool cuối cùng.

# 5. MongoDB embedding vs referencing: document model phải theo access pattern và consistency boundary, không theo class diagram

## 1. What is it?

Embedding lưu related data trong cùng document; referencing lưu identifiers để dữ liệu nằm ở documents/collections khác.

MongoDB modeling bắt đầu từ cách dữ liệu được đọc/ghi và consistency cần thiết, không đơn giản từ quan hệ object-oriented.

## 2. Why does it exist?

Document database cho phép aggregate dữ liệu thường được đọc cùng nhau vào một document, giảm joins/round trips. Nhưng embedding không giới hạn có thể tạo document lớn, write amplification và ownership mơ hồ.

## 3. How does it work?

Embedding:

```json
{
  "orderId": "O1",
  "lines": [
    { "productId": "P1", "nameAtPurchase": "Keyboard", "price": 80 }
  ]
}
```

Tên/giá tại thời điểm mua thuộc order history nên snapshot embedded hợp lý.

Reference phù hợp khi entity có lifecycle độc lập hoặc fan-out lớn.

## 4. Practical implementation

C# model:

```csharp
public sealed record OrderLineSnapshot(
    string ProductId,
    string Name,
    decimal UnitPrice,
    int Quantity);

public sealed class OrderDocument
{
    public string Id { get; init; } = default!;
    public List<OrderLineSnapshot> Lines { get; init; } = [];
}
```

Đây là deliberate denormalization: order không cần product name hiện tại để hiển thị historical invoice.

## 5. Real production scenario

Marketplace product thay đổi title hàng ngày. Nếu order chỉ reference Product collection, historical invoice có thể hiển thị title hiện tại thay vì title lúc mua. Embedding snapshot giữ business history đúng.

Ngược lại, nhúng toàn bộ product catalog vào merchant document sẽ tạo unbounded growth và update amplification.

## 6. Failure scenario & troubleshooting

**Symptom** → update product cần sửa hàng trăm nghìn documents.

**Evidence** → mutable shared product fields bị duplicated ở mọi nơi dù consumers cần latest value.

**Hypothesis** → denormalization boundary sai.

**Diagnosis** → phân loại fields thành historical snapshot vs current shared state.

**Fix** → chỉ embed snapshot cần bất biến; reference current mutable data.

**Verification** → đo write fan-out và query round trips sau redesign.

## 7. Common mistakes

* Chuyển relational schema sang collections 1:1.
* Embed arrays tăng không giới hạn.
* Reference mọi thứ rồi tái tạo joins ở application.
* Denormalize mà không xác định owner/update propagation.

## 8. Alternatives

SQL phù hợp khi relational consistency và ad-hoc joins là trọng tâm. MongoDB references phù hợp independent lifecycle. Read models/materialized views phù hợp khi cần denormalized query shape nhưng source-of-truth vẫn relational.

## 9. Trade-offs

### Advantages

Embedding giảm round trips và có atomicity tốt trong document boundary.

### Costs / Risks

Duplication, document growth và update propagation. Referencing giảm duplication nhưng tăng lookup/consistency coordination.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu document không phải table đổi tên.

### Middle

Model theo common queries và update patterns.

### Senior

Đánh giá cardinality, growth, atomicity và duplication ownership.

### Technical Lead / Architect

Quyết định liệu document database thực sự phù hợp domain/access pattern hay relational model đơn giản hơn.

## 11. Key takeaway

* Embed theo ownership/access pattern, không theo object graph.
* Snapshot duplication có thể là correctness feature.
* Unbounded relationships thường không nên nhúng trực tiếp.

# 6. Saga + compensating transaction: giữ business workflow nhất quán khi một transaction ACID không thể bao trùm nhiều services

## 1. What is it?

Saga chia distributed business workflow thành nhiều local transactions. Nếu bước sau thất bại, hệ thống chạy compensating actions để đưa business state về trạng thái chấp nhận được.

Compensation không phải database rollback xuyên services; nó là một business operation mới.

## 2. Why does it exist?

Order, payment, inventory và shipping có thể thuộc services/databases khác nhau. Một SQL transaction không thể thực tế khóa tất cả chúng qua network trong vài giây/phút.

Saga chấp nhận intermediate states và eventual consistency để tránh distributed lock/2PC coupling.

## 3. How does it work?

```text
Create Order
   ↓
Reserve Inventory
   ↓
Charge Payment
   ↓ failure
Release Inventory
   ↓
Cancel Order
```

Mỗi command/event cần idempotency vì messages có thể duplicate.

## 4. Practical implementation

State nên explicit:

```csharp
public enum CheckoutState
{
    Pending,
    InventoryReserved,
    PaymentCaptured,
    Completed,
    Compensating,
    Cancelled
}
```

Orchestrator persist state trước/giữa transitions để restart không mất workflow position. Commands nên mang stable `SagaId` và idempotency key.

## 5. Real production scenario

Checkout reserve inventory thành công nhưng payment provider timeout. Không biết charge đã xảy ra hay chưa. Saga không được đơn giản gọi `ReleaseInventory` ngay nếu payment outcome ambiguous. Nó cần query/reconcile payment hoặc dùng provider idempotency key trước khi quyết định compensation.

## 6. Failure scenario & troubleshooting

**Symptom** → inventory được release nhưng payment thực tế đã capture.

**Evidence** → payment timeout được coi như definitive failure.

**Hypothesis** → workflow không model ambiguous outcome.

**Diagnosis** → inspect provider transaction/idempotency key và saga state history.

**Fix** → thêm reconciliation state/process; compensation chỉ chạy khi outcome đủ chắc chắn.

**Verification** → fault-injection timeout ở từng transition và kiểm tra final business invariants.

## 7. Common mistakes

* Gọi compensation là rollback và giả định nó luôn thành công.
* Không persist saga state.
* Không idempotent commands.
* Tạo saga cho workflow đơn giản trong cùng database.
* Không có manual recovery path.

## 8. Alternatives

Local ACID transaction tốt hơn nếu data cùng boundary. Outbox giải quyết reliable publication nhưng không tự giải quyết multi-step compensation. 2PC có strong atomicity nhưng operational coupling cao và thường không phù hợp SaaS/cloud integrations.

## 9. Trade-offs

### Advantages

Cho phép workflow xuyên autonomous services mà không giữ distributed locks.

### Costs / Risks

Intermediate inconsistency, complex recovery, compensation failures và observability burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu compensation là business action mới.

### Middle

Implement explicit states và idempotent handlers.

### Senior

Model timeout ambiguity, retries, compensation và manual recovery.

### Technical Lead / Architect

Quyết định service boundaries có thực sự cần Saga hay system đang tự tạo distributed complexity không cần thiết.

## 11. Key takeaway

* Saga quản lý workflow, không tạo distributed ACID magic.
* Compensation cũng có thể fail và phải được vận hành.
* Ambiguous outcomes là phần quan trọng nhất của real-world design.

# 7. Azure Functions idempotency: retry và scale-out khiến một event có thể chạy nhiều lần dù code chỉ trigger một lần

## 1. What is it?

Idempotent function cho phép cùng logical event được xử lý nhiều lần nhưng final business effect vẫn tương đương một lần.

Trong event-driven cloud systems, duplicate execution là expected failure mode chứ không phải anomaly hiếm.

## 2. Why does it exist?

Azure Functions triggers thường dựa trên delivery semantics có retry. Process có thể crash sau side effect nhưng trước acknowledgement/checkpoint. Platform sau đó giao event lại hoặc instance khác xử lý.

## 3. How does it work?

```text
Receive message M1
  ↓
Create invoice
  ↓
process crashes before completion acknowledged
  ↓
M1 delivered again
  ↓
Idempotency guard sees M1 already applied
  ↓
No duplicate invoice
```

## 4. Practical implementation

Business uniqueness thường tốt hơn memory cache:

```sql
CREATE UNIQUE INDEX UX_Invoices_SourceMessageId
ON Invoices(SourceMessageId);
```

Handler dùng message ID/idempotency key trong cùng persistence transaction với business effect. Nếu duplicate insert xảy ra, xử lý như already-completed outcome thay vì tạo entity thứ hai.

## 5. Real production scenario

Service Bus-triggered Function gửi loyalty credit sau order completion. Instance bị recycle sau khi ghi credit nhưng trước message completion. Message được redeliver. Nếu handler chỉ “insert credit”, user nhận gấp đôi.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate credits trùng vài giây.

**Evidence** → cùng MessageId xuất hiện ở hai invocation IDs.

**Hypothesis** → side effect không idempotent.

**Diagnosis** → correlate Function logs, Service Bus delivery count và DB records.

**Fix** → unique business/idempotency constraint + transactional dedupe.

**Verification** → replay cùng message nhiều lần và scale nhiều instances.

## 7. Common mistakes

* Dedupe bằng static `HashSet` trong Function process.
* Giả định retry count bằng zero trong happy path nên duplicates không tồn tại.
* Dùng generated ID mới cho mỗi retry thay vì stable event identity.
* Gọi external non-idempotent API không có reconciliation strategy.

## 8. Alternatives

Worker Service có cùng duplicate problem nếu broker at-least-once. Durable Functions hỗ trợ orchestration state nhưng activity side effects vẫn cần hiểu idempotency. Queue-less synchronous API có failure model khác nhưng không loại duplicate requests.

## 9. Trade-offs

### Advantages

Cho phép retry mạnh hơn mà không hy sinh correctness.

### Costs / Risks

Cần persistent dedupe state, unique keys và retention policy; external systems có thể không hỗ trợ idempotency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trigger một lần không đảm bảo execution một lần.

### Middle

Dùng stable event ID và unique constraints.

### Senior

Thiết kế atomic dedupe, retry và external reconciliation.

### Technical Lead / Architect

Định nghĩa business-level exactly-once effect thay vì phụ thuộc platform marketing semantics.

## 11. Key takeaway

* Duplicate delivery phải được coi là bình thường.
* Idempotency nên dựa vào durable business identity.
* Retry chỉ an toàn khi side effects có replay strategy.

# 8. Application Insights SLI/SLO alerting: alert theo user impact thay vì CPU threshold và log volume

## 1. What is it?

SLI là measurable indicator của service behavior, ví dụ request success rate hoặc latency. SLO là target cho SLI trong một window, ví dụ 99.9% successful requests trong 30 ngày.

Alerting tốt tập trung vào symptom người dùng trước, resource metrics dùng để chẩn đoán nguyên nhân.

## 2. Why does it exist?

CPU 90% không nhất thiết là incident nếu requests vẫn nhanh và thành công. CPU 20% cũng không chứng minh service khỏe nếu downstream timeout làm 30% requests fail.

Alert theo user-visible outcome giảm noise và ưu tiên đúng incident.

## 3. How does it work?

```text
Requests telemetry
  ↓
Success + latency indicators
  ↓
SLO / error budget
  ↓
Alert when burn/user impact is meaningful
  ↓
Use traces, dependencies, CPU, SQL metrics for diagnosis
```

## 4. Practical implementation

Application Insights KQL đơn giản:

```kusto
requests
| where timestamp > ago(15m)
| summarize
    total=count(),
    failures=countif(success == false),
    p95=percentile(duration, 95)
| extend successRate = 100.0 * (total - failures) / total
```

Alert có thể dựa trên success rate/p95 cùng minimum traffic để tránh false alarm khi chỉ có vài requests.

## 5. Real production scenario

SQL dependency latency tăng. CPU App Service vẫn 35%, memory ổn. Infrastructure alerts không báo gì, nhưng checkout p95 tăng từ 600 ms lên 4 s. User-centric latency SLI phát hiện incident sớm hơn host metrics.

## 6. Failure scenario & troubleshooting

**Symptom** → on-call bị alert liên tục nhưng không có user impact.

**Evidence** → alert dựa trên single CPU spike 1 phút.

**Hypothesis** → alert source-oriented thay vì symptom-oriented.

**Diagnosis** → compare alert timestamps với request SLI và incidents thực tế.

**Fix** → chuyển primary paging alerts sang availability/latency/error-budget signals; CPU trở thành diagnostic/warning signal.

**Verification** → review alert precision qua incident history.

## 7. Common mistakes

* Alert mọi exception log.
* Dùng average latency thay p95/p99.
* Không tách endpoint criticality.
* Không có minimum traffic guard.
* Dashboard đẹp nhưng không có actionable alert ownership.

## 8. Alternatives

Azure Monitor metrics có thể alert trực tiếp. Prometheus/Grafana phù hợp stack khác. Tool không quan trọng bằng SLI definition và response process.

## 9. Trade-offs

### Advantages

Giảm noise, align operations với user impact và reliability objective.

### Costs / Risks

SLO sai có thể che incident; telemetry sampling/cardinality/cost cần quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu logs, metrics, traces giải quyết câu hỏi khác nhau.

### Middle

Viết queries và dashboards cho success/latency.

### Senior

Thiết kế SLI, percentiles, burn alerts và incident correlation.

### Technical Lead / Architect

Chọn SLO phản ánh business criticality và gắn alert với ownership/actionability.

## 11. Key takeaway

* Page on-call vì user impact, không vì mọi resource spike.
* p95/p99 thường nói nhiều hơn average.
* Resource telemetry giải thích incident; SLI thường phát hiện incident.

# 9. Git `bisect`: tìm regression bằng binary search thay vì đọc hàng trăm commits theo cảm tính

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên gây regression, miễn là ta có thể phân loại một commit là `good` hoặc `bad`.

## 2. Why does it exist?

Nếu regression nằm trong 512 commits, kiểm tra tuần tự có thể cần hàng trăm lần. Binary search cần khoảng 9 checks trong ideal linear history.

## 3. How does it work?

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0
```

Git checkout midpoint. Ta chạy test rồi đánh dấu:

```bash
git bisect good
# hoặc
git bisect bad
```

Lặp đến khi Git xác định first bad commit.

## 4. Practical implementation

Tự động hóa với test script:

```bash
git bisect start HEAD v1.8.0
git bisect run dotnet test tests/RegressionTests/RegressionTests.csproj --filter FullyQualifiedName~CheckoutLatencyRegression
```

Exit code 0 = good, non-zero theo semantics `bisect run` phù hợp để phân loại.

Sau cùng:

```bash
git bisect reset
```

## 5. Real production scenario

Sau vài tuần releases, image upload bắt đầu corrupt EXIF metadata. Team có deterministic regression test nhưng không biết commit nào gây lỗi. `git bisect run` chạy test qua history và tìm commit đổi stream handling trong vài phút thay vì manual review.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect đưa ra commit không liên quan.

**Evidence** → test flaky, cùng commit lúc pass lúc fail.

**Hypothesis** → good/bad oracle không deterministic.

**Diagnosis** → rerun candidate commits nhiều lần và kiểm tra external dependencies/test data.

**Fix** → tạo deterministic reproduction trước khi bisect.

**Verification** → revert/fix identified commit và chạy regression test.

## 7. Common mistakes

* Bisect bằng cảm nhận thủ công thay vì reproducible test.
* Chọn “good” commit thực ra đã có bug.
* Không reset sau bisect.
* Dùng bisect cho production-only issue chưa tái hiện được.

## 8. Alternatives

`git log`, blame và PR review hữu ích khi suspect area nhỏ. Telemetry/deployment correlation tốt hơn nếu regression map rõ theo release. Bisect mạnh nhất khi có binary deterministic reproduction.

## 9. Trade-offs

### Advantages

Nhanh, evidence-driven và tận dụng version history như debugging tool.

### Costs / Risks

Build old commits có thể fail do dependency/environment drift; merge-heavy history làm reasoning phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu commit history có thể dùng để debug, không chỉ lưu code.

### Middle

Chạy bisect thủ công với good/bad boundaries.

### Senior

Tự động hóa bisect bằng deterministic regression test và xử lý skip/build failures.

### Technical Lead / Architect

Đầu tư testability/reproducibility để incident investigation trở thành evidence-driven workflow.

## 11. Key takeaway

* `git bisect` biến lịch sử thành search space có cấu trúc.
* Deterministic reproduction quan trọng hơn command syntax.
* Regression test tốt vừa tìm bug vừa ngăn bug quay lại.

# 10. Optimizely CMS content modeling: Page, Block và reusable composition là domain/editorial boundary chứ không chỉ C# inheritance

## 1. What is it?

CMS content model định nghĩa editor có thể tạo loại nội dung nào, compose chúng ra sao và content nào có lifecycle/URL/ownership riêng.

Trong Optimizely CMS, Page thường đại diện routable content trong site hierarchy; Block đại diện reusable/composable content component. Nhưng quyết định modeling phải bắt đầu từ editorial semantics, không phải chỉ từ class hierarchy.

## 2. Why does it exist?

Nếu mọi thứ là Page, editors phải tạo fake pages chỉ để tái sử dụng component. Nếu mọi thứ là Block, routing, hierarchy và page-level metadata trở nên khó hiểu.

Content model tốt giúp editors biểu diễn domain content ổn định mà frontend vẫn có cấu trúc predictable.

## 3. How does it work?

```text
ProductLandingPage
 ├─ SEO/page metadata
 ├─ HeroBlock
 ├─ PromoGridBlock
 │   ├─ PromoCardBlock
 │   └─ PromoCardBlock
 └─ RichText/ContentArea
```

Page sở hữu route/lifecycle cấp trang; blocks có thể local hoặc shared tùy reuse semantics.

## 4. Practical implementation

```csharp
[ContentType(DisplayName = "Campaign Page", GUID = "11111111-1111-1111-1111-111111111111")]
public class CampaignPage : PageData
{
    public virtual string Heading { get; set; } = string.Empty;
    public virtual ContentArea MainContent { get; set; } = default!;
}

[ContentType(DisplayName = "Call To Action", GUID = "22222222-2222-2222-2222-222222222222")]
public class CallToActionBlock : BlockData
{
    public virtual string Text { get; set; } = string.Empty;
    public virtual Url Link { get; set; } = default!;
}
```

Validation nên phản ánh editorial invariants thay vì nhồi mọi field thành required.

## 5. Real production scenario

Marketing cần CTA dùng lại trên 200 pages. Shared block phù hợp nếu business thực sự muốn một thay đổi propagate toàn bộ. Nhưng nếu mỗi page cần historical/independent copy, shared content tạo coupling nguy hiểm: editor sửa một block và vô tình đổi 200 pages.

## 6. Failure scenario & troubleshooting

**Symptom** → một edit nhỏ làm hàng chục pages thay đổi ngoài dự kiến.

**Evidence** → tất cả pages reference cùng shared block.

**Hypothesis** → reuse kỹ thuật không khớp ownership/editorial intent.

**Diagnosis** → inspect content references và publishing workflow.

**Fix** → phân biệt shared-global content với local page-owned blocks; migration/copy khi cần.

**Verification** → editor acceptance test: edit local component không ảnh hưởng pages khác.

## 7. Common mistakes

* Model theo database entities thay vì editor mental model.
* Tạo một mega-page type với hàng chục fields cho mọi campaign.
* Reuse mọi block chỉ vì platform cho phép.
* Không nghĩ tới content migration khi đổi model.
* Coupling rendering logic quá chặt vào CMS type hierarchy.

## 8. Alternatives

Headless CMS vẫn cần content modeling nhưng rendering boundary nằm ở client khác. Traditional MVC CMS đơn giản hơn khi server rendering và editorial model cùng platform. Static configuration phù hợp content hiếm thay đổi và không cần editor workflow.

## 9. Trade-offs

### Advantages

Content model tốt tăng editor autonomy, reuse có chủ đích và rendering consistency.

### Costs / Risks

Model quá generic làm editor khó dùng; model quá specific gây type explosion và migration cost. Shared content tăng reuse nhưng cũng tăng coupling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Page và Block khác nhau về role, không chỉ base class.

### Middle

Implement content types, rendering và validation theo editor workflow.

### Senior

Thiết kế reuse/ownership, caching, migration và backward compatibility.

### Technical Lead / Architect

Quyết định CMS boundary trong composable architecture, content ownership và cách model chịu được nhiều năm evolution.

## 11. Key takeaway

* Content modeling là domain/editorial design.
* Reuse luôn tạo coupling; shared block chỉ đúng khi shared ownership cũng đúng.
* Thiết kế CMS phải tính cả migration và editor workflow, không chỉ code compile được.
