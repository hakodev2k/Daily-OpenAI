# 1. .NET `ArrayPool<T>`: giảm allocation cho buffer lớn nhưng phải quản lý ownership, lifetime và dữ liệu nhạy cảm

## 1. What is it?

`ArrayPool<T>` là cơ chế tái sử dụng arrays thay vì cấp phát array mới cho mỗi operation. Mental model quan trọng không phải “array miễn phí”, mà là **borrow / use / return**:

```text
ArrayPool
   ↓ Rent
Caller temporarily owns buffer
   ↓ use
Return
   ↓
Buffer có thể được caller khác nhận lại
```

`ArrayPool<T>.Shared` đặc biệt hữu ích ở hot path có nhiều buffer tạm, ví dụ serialization, compression, file processing hoặc network protocol parsing.

Khác với array thông thường, buffer được `Rent()` không thuộc sở hữu lâu dài của caller. Sau khi `Return()`, code không được tiếp tục đọc hoặc ghi buffer đó.

## 2. Why does it exist?

Một service xử lý hàng nghìn requests/giây và mỗi request tạo array 128 KB có thể tạo lượng allocation rất lớn. Những arrays lớn có thể đi vào Large Object Heap, tăng GC pressure và khiến latency tail xấu đi.

Ví dụ đơn giản:

```csharp
var buffer = new byte[128 * 1024];
```

Nếu operation này xảy ra liên tục, runtime phải cấp phát và sau đó GC phải reclaim các buffers đó.

Pooling đổi bài toán từ:

```text
allocate → collect → allocate → collect
```

thành:

```text
rent → return → reuse
```

nhưng đổi lại developer phải quản lý lifecycle rõ ràng.

## 3. How does it work?

Khi gọi:

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
```

pool trả về một array có **ít nhất** kích thước yêu cầu. Length thực tế có thể lớn hơn.

Caller sử dụng một slice xác định:

```csharp
var span = buffer.AsSpan(0, bytesRead);
```

sau đó trả array:

```csharp
ArrayPool<byte>.Shared.Return(buffer);
```

Pool giữ lại một số arrays theo bucket kích thước để reuse. Nó không đảm bảo buffer vừa trả sẽ được giữ vĩnh viễn, cũng không đảm bảo nội dung buffer được zero hóa.

Điều này dẫn tới hai quy tắc production quan trọng:

1. chỉ xử lý vùng thực sự chứa dữ liệu hợp lệ;
2. dữ liệu nhạy cảm cần được clear trước khi return hoặc dùng `clearArray: true` khi phù hợp.

## 4. Practical implementation

Ví dụ đọc stream theo buffer dùng lại:

```csharp
public static async Task<long> CopyAndCountAsync(
    Stream input,
    Stream output,
    CancellationToken cancellationToken)
{
    var pool = ArrayPool<byte>.Shared;
    var buffer = pool.Rent(64 * 1024);

    try
    {
        long total = 0;

        while (true)
        {
            var read = await input.ReadAsync(
                buffer.AsMemory(0, 64 * 1024),
                cancellationToken);

            if (read == 0)
                break;

            await output.WriteAsync(
                buffer.AsMemory(0, read),
                cancellationToken);

            total += read;
        }

        return total;
    }
    finally
    {
        pool.Return(buffer);
    }
}
```

Nếu buffer chứa secret, token hoặc dữ liệu cá nhân:

```csharp
pool.Return(buffer, clearArray: true);
```

Clear có CPU cost, vì vậy không cần bật máy móc cho mọi buffer.

## 5. Real production scenario

Một API upload tài liệu nhận file 20–100 MB, tính hash rồi đẩy sang Azure Blob Storage. Version đầu tạo nhiều `byte[]` mới trong pipeline: đọc multipart, hash, transform và upload.

Dưới tải đồng thời, allocation rate tăng mạnh và GC pauses bắt đầu ảnh hưởng p99 latency của cả service.

Chuyển các transient buffers sang `ArrayPool<byte>` giảm allocation đáng kể. Tuy nhiên team phát hiện một helper trả buffer về pool trước khi asynchronous consumer hoàn tất, khiến dữ liệu bị ghi đè ngẫu nhiên bởi request khác.

Vấn đề không phải pool “không thread-safe”; vấn đề là **ownership bị vi phạm**.

## 6. Failure scenario & troubleshooting

**Symptom** → file upload thỉnh thoảng bị corrupt dù checksum nguồn đúng.

**Evidence** → corruption chỉ xuất hiện dưới concurrency cao; allocation giảm sau khi đưa pooling vào.

**Hypothesis** → buffer được return quá sớm hoặc được reuse sau khi return.

**Diagnosis** → trace ownership: ai `Rent`, ai `Return`, asynchronous operation nào vẫn giữ `Memory<byte>` tham chiếu tới array.

**Fix** → chỉ return sau khi consumer cuối cùng hoàn tất; không truyền pooled buffer ra ngoài lifetime contract.

**Verification** → stress test đồng thời + checksum end-to-end; bật assertions ở helper layer nếu cần.

## 7. Common mistakes

* Giả định `Rent(1000)` luôn trả array dài đúng 1000.
* Dùng toàn bộ `buffer.Length` thay vì logical length thực tế.
* Return buffer trước khi async consumer dùng xong.
* Double-return cùng array.
* Giữ reference sau `Return()`.
* Pool dữ liệu nhỏ, ít gọi và làm code phức tạp mà không có evidence về allocation pressure.
* Return buffer chứa secret mà không cân nhắc clear.

## 8. Alternatives

* `new byte[]`: đơn giản nhất, phù hợp khi allocation rate thấp.
* `stackalloc`: tốt cho buffer nhỏ, lifetime ngắn và synchronous scope.
* `MemoryPool<T>`: hữu ích khi cần ownership abstraction thông qua `IMemoryOwner<T>`.
* Streaming API không cần custom buffer: tốt hơn nếu framework/library đã quản lý buffering hiệu quả.

## 9. Trade-offs

### Advantages

* Giảm allocation và GC pressure ở hot path.
* Hữu ích với buffers tương đối lớn, lặp lại thường xuyên.
* Có thể cải thiện tail latency khi memory pressure là bottleneck thực.

### Costs / Risks

* Ownership phức tạp hơn array thường.
* Use-after-return tạo bug nondeterministic khó debug.
* Sensitive data có thể tồn tại trong reused buffer.
* Pooling sai chỗ làm code khó đọc mà không mang lại lợi ích đo được.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Rent` không phải cấp ownership vĩnh viễn; `Return` kết thúc quyền sử dụng buffer.

### Middle

Biết dùng `try/finally`, logical length, `Memory<T>` và cancellation đúng cách.

### Senior

Biết đo allocation/GC trước khi tối ưu, nhận diện use-after-return và cân nhắc sensitive-data clearing.

### Technical Lead / Architect

Quyết định pool ở boundary nào, có cần custom ownership abstraction hay không, và chỉ áp dụng khi profiling chứng minh allocation là vấn đề đáng giải quyết.

## 11. Key takeaway

* `ArrayPool<T>` tối ưu allocation bằng reuse, không phải array miễn phí.
* Ownership kết thúc ngay khi `Return()` được gọi.
* Chỉ dùng pooling khi measurement cho thấy memory allocation thực sự đáng tối ưu.

# 2. ASP.NET Core API Versioning + backward compatibility: tiến hóa contract mà không buộc mọi client nâng cấp đồng thời

## 1. What is it?

API versioning là cách cho phép nhiều contract versions cùng tồn tại trong một khoảng thời gian để clients có thể nâng cấp độc lập.

Mental model:

```text
Mobile v5 ───> API v1
Web current ─> API v2
Partner ERP ─> API v1

Server supports migration window
```

Versioning không chỉ là thêm `/v2/` vào URL. Bài toán thật là **contract evolution**: field semantics, status codes, validation rules, pagination, auth expectations và side effects phải được quản lý khi clients nâng cấp không đồng thời.

## 2. Why does it exist?

Một internal frontend có thể deploy cùng backend trong vài phút. Nhưng mobile app, partner integration hoặc public API client có release cadence hoàn toàn khác.

Nếu backend thay đổi response:

```json
{
  "fullName": "Ha Dinh"
}
```

thành:

```json
{
  "firstName": "Ha",
  "lastName": "Dinh"
}
```

và xóa `fullName` ngay lập tức, clients cũ có thể fail.

Versioning tồn tại để tạo migration window và explicit compatibility boundary.

## 3. How does it work?

Có nhiều cách identify version:

* URL segment: `/api/v1/orders`
* query string
* custom header
* media type

Điểm quan trọng hơn là policy:

```text
Introduce additive change
        ↓
Support old + new behavior
        ↓
Observe client migration
        ↓
Deprecate old version
        ↓
Remove only after agreed window
```

Backward-compatible changes thường gồm thêm optional field hoặc endpoint mới. Breaking changes thường gồm đổi meaning, xóa field, đổi type, siết validation hoặc đổi status semantics.

## 4. Practical implementation

Ví dụ tách contract versions rõ ràng:

```csharp
public sealed record OrderV1Dto(
    Guid Id,
    decimal Total);

public sealed record OrderV2Dto(
    Guid Id,
    MoneyDto Total,
    string Currency);
```

Endpoints không nên trả domain entity trực tiếp:

```csharp
app.MapGet("/api/v1/orders/{id:guid}", async (
    Guid id,
    AppDbContext db,
    CancellationToken ct) =>
{
    var result = await db.Orders
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new OrderV1Dto(x.Id, x.TotalAmount))
        .SingleOrDefaultAsync(ct);

    return result is null ? Results.NotFound() : Results.Ok(result);
});
```

V2 có mapper/shape riêng, dù application/domain logic có thể dùng chung.

## 5. Real production scenario

Một marketplace có mobile app cũ đang dùng field `price` kiểu number. Backend muốn hỗ trợ multi-currency nên cần `{ amount, currency }`.

Nếu sửa in-place, mobile versions chưa update sẽ crash parsing. Team giữ v1 trong 90 ngày, phát hành v2, đo adoption theo client/version header rồi mới deprecate v1.

Đây là release-engineering problem chứ không chỉ routing problem.

## 6. Failure scenario & troubleshooting

**Symptom** → sau deploy, error rate chỉ tăng ở một nhóm mobile versions.

**Evidence** → logs cho thấy JSON deserialization failures hoặc 400 tăng theo `X-App-Version`.

**Hypothesis** → backend change đã phá contract cũ.

**Diagnosis** → diff OpenAPI/schema và replay request từ client cũ.

**Fix** → restore compatible behavior hoặc route old clients vào previous contract version.

**Verification** → contract tests cho cả supported versions; telemetry phân tách theo API/client version.

## 7. Common mistakes

* Version mọi thay đổi, kể cả additive compatible changes.
* Nghĩ version chỉ nằm trong URL.
* Dùng cùng DTO rồi thêm nhiều `if (version == ...)` khắp business logic.
* Đổi validation rule mà không coi đó là contract change.
* Xóa old version dựa trên ngày dự kiến mà không đo client usage.
* Trả EF/domain entities trực tiếp và vô tình expose schema changes.

## 8. Alternatives

* Additive backward-compatible evolution: tốt nhất khi có thể.
* Consumer-driven contracts: bổ sung evidence về compatibility giữa provider/consumers.
* GraphQL schema deprecation: phù hợp hệ sinh thái GraphQL nhưng vẫn cần migration discipline.
* BFF riêng theo client: hữu ích khi mobile/web có evolution khác nhau đáng kể.

## 9. Trade-offs

### Advantages

* Clients nâng cấp độc lập.
* Giảm blast radius của breaking changes.
* Có deprecation window rõ ràng.

### Costs / Risks

* Nhiều versions làm tăng test/support surface.
* Data semantics có thể phân nhánh theo thời gian.
* Old versions dễ tồn tại vĩnh viễn nếu không có ownership và retirement plan.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu response/request schema là contract với client.

### Middle

Biết tạo versioned DTO, routing và contract tests.

### Senior

Phân loại additive vs breaking changes, theo dõi telemetry và thiết kế migration path.

### Technical Lead / Architect

Đặt compatibility policy, deprecation window, ownership và quyết định khi nào versioning cần thiết thay vì tạo versions không kiểm soát.

## 11. Key takeaway

* API versioning là quản lý contract evolution, không phải chỉ đổi URL.
* Ưu tiên backward-compatible additive change khi đủ.
* Old version chỉ an toàn khi có telemetry, owner và retirement plan rõ ràng.

# 3. EF Core execution strategy + explicit transaction: retry transient failure mà không vô tình replay transaction sai cách

## 1. What is it?

EF Core execution strategy là cơ chế retry operations khi database provider nhận diện transient failure, ví dụ connection drop ngắn hạn hoặc throttling.

Với SQL Server, connection resiliency có thể được bật bằng:

```csharp
options.UseSqlServer(
    connectionString,
    sql => sql.EnableRetryOnFailure());
```

Khó khăn xuất hiện khi application tự mở transaction: retry không còn chỉ là retry một command, mà phải retry **toàn bộ transaction unit** đúng cách.

## 2. Why does it exist?

Cloud/database network không hoàn hảo. Một query có thể fail vì transient connection issue rồi thành công ngay lần sau.

Nhưng transaction có ambiguity:

```text
BEGIN
UPDATE Order
COMMIT request sent
network drops
```

Client có thể không biết COMMIT đã thành công ở server hay chưa.

Retry sai cách có thể tạo duplicate side effects hoặc chạy transaction với state không còn như lần đầu.

## 3. How does it work?

Execution strategy wrap một delegate và có thể chạy lại delegate đó.

Khi dùng explicit transaction, pattern an toàn là để strategy execute toàn transaction:

```text
ExecutionStrategy.ExecuteAsync
   ↓ attempt
Begin transaction
   ↓
all EF operations
   ↓
Commit
```

Nếu transient failure phù hợp retry policy xảy ra, delegate transaction được chạy lại từ đầu.

Điều này yêu cầu work bên trong phải chịu được replay hoặc có correctness guard.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var transaction =
        await db.Database.BeginTransactionAsync(ct);

    var order = await db.Orders
        .SingleAsync(x => x.Id == orderId, ct);

    order.MarkConfirmed();

    db.OutboxMessages.Add(
        OutboxMessage.From(new OrderConfirmed(order.Id)));

    await db.SaveChangesAsync(ct);
    await transaction.CommitAsync(ct);
});
```

Đưa external HTTP call vào transaction/retry delegate là nguy hiểm:

```csharp
// Không nên coi remote side effect như DB transaction participant.
await paymentProvider.CaptureAsync(...);
```

Nếu delegate được replay, payment có thể bị capture hai lần nếu provider không hỗ trợ idempotency.

## 5. Real production scenario

Order service update trạng thái và ghi Outbox trong SQL Azure. Một transient failure xảy ra khi commit.

Nếu application retry riêng `SaveChangesAsync()` trên cùng transaction đã lỗi, transaction state có thể không còn hợp lệ.

Nếu toàn transaction được execution strategy retry, state có thể tái tạo đúng. Outbox unique/business constraints tiếp tục bảo vệ duplicate logical event.

## 6. Failure scenario & troubleshooting

**Symptom** → production thỉnh thoảng ghi duplicate external side effect sau database timeout.

**Evidence** → logs cho thấy execution strategy chạy attempt 2; external API được gọi trong delegate cả hai lần.

**Hypothesis** → retryable database transaction chứa non-idempotent remote side effect.

**Diagnosis** → inspect transaction boundary và retry scope.

**Fix** → giữ DB state + Outbox trong transaction; gửi external effect sau commit qua worker có idempotency.

**Verification** → fault-injection tại commit/network boundary; business effect vẫn xảy ra tối đa một lần theo idempotency contract.

## 7. Common mistakes

* Bật retry rồi cho rằng mọi operation đều tự động an toàn.
* Mở transaction ngoài execution strategy delegate.
* Retry non-idempotent external calls cùng DB operation.
* Retry mọi exception, kể cả constraint violation hoặc business failure.
* Không log attempt count/retry cause nên khó phân tích incident.

## 8. Alternatives

* Không retry ở application khi database/network ổn định và failure không transient.
* Provider/native retry ở lower layer: có thể hữu ích nhưng application vẫn phải hiểu semantics.
* Outbox Pattern: tách transactional database mutation khỏi external side effect.

## 9. Trade-offs

### Advantages

* Tăng resilience trước transient database failure.
* Giảm user-visible errors do sự cố ngắn hạn.

### Costs / Risks

* Retry làm tăng latency và load khi dependency đang suy giảm.
* Transaction replay yêu cầu idempotency/correctness reasoning.
* Failure ambiguity quanh commit không biến mất chỉ vì có retry.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transient failure khác business/constraint failure.

### Middle

Biết dùng `EnableRetryOnFailure` và execution strategy với explicit transaction.

### Senior

Nhìn thấy commit ambiguity, replay semantics và external side-effect risk.

### Technical Lead / Architect

Thiết kế retry budget, transaction boundary, Outbox/idempotency và telemetry thay vì bật retry như checkbox reliability.

## 11. Key takeaway

* Retry an toàn phải retry đúng **unit of work**, không chỉ command ngẫu nhiên.
* Explicit transaction nên nằm bên trong execution strategy delegate.
* Không đưa non-idempotent remote side effects vào retryable DB transaction.

# 4. SQL Server statistics + cardinality estimation: optimizer đoán số rows sai thì execution plan có thể sai dù index vẫn tồn tại

## 1. What is it?

SQL Server optimizer chọn execution plan dựa trên ước lượng chi phí. Một input quan trọng của việc ước lượng là **statistics**: thông tin phân bố dữ liệu giúp optimizer đoán có bao nhiêu rows sẽ match predicate.

Mental model:

```text
SQL query
   ↓
Statistics + cardinality estimator
   ↓ estimated rows
Cost model
   ↓
Join order / join type / seek vs scan / memory grant
```

Execution plan tốt phụ thuộc không chỉ vào index tồn tại hay không, mà còn vào việc optimizer có **ước lượng đúng** workload hay không.

## 2. Why does it exist?

Optimizer không thể thực thi mọi plan candidate để xem cái nào nhanh nhất. Nó phải dự đoán.

Nếu query:

```sql
WHERE Status = 'Pending'
```

optimizer cần biết `Pending` chiếm 0.1% hay 60% bảng.

Nếu estimate là 10 rows nhưng thực tế 500,000 rows, plan dùng Nested Loops + repeated lookups có thể cực chậm. Nếu estimate lớn đúng, Hash Join hoặc scan có thể hợp lý hơn.

## 3. How does it work?

Statistics thường chứa histogram và density information cho columns/index keys.

Khi data thay đổi đủ nhiều, auto-update statistics có thể refresh chúng, nhưng không phải lúc nào timing cũng phù hợp workload.

Trong execution plan cần so sánh:

```text
Estimated Number of Rows
vs
Actual Number of Rows
```

Chênh lệch lớn là dấu hiệu cardinality estimate có vấn đề, nhưng root cause có thể là stale statistics, data skew, correlation giữa columns, parameter sensitivity hoặc predicate khó estimate.

## 4. Practical implementation

Kiểm tra statistics metadata:

```sql
SELECT
    s.name AS stats_name,
    STATS_DATE(s.object_id, s.stats_id) AS last_updated
FROM sys.stats s
WHERE s.object_id = OBJECT_ID('dbo.Orders');
```

Refresh có chủ đích:

```sql
UPDATE STATISTICS dbo.Orders IX_Orders_Status;
```

Nhưng không nên biến `UPDATE STATISTICS` thành phản xạ máy móc. Trước tiên cần xem actual execution plan và data distribution.

Ví dụ query:

```sql
SELECT Id, CustomerId, CreatedAt
FROM dbo.Orders
WHERE Status = @Status
  AND CreatedAt >= @FromDate;
```

Nếu `Status` rất skewed, cùng query shape có thể cần plan khác nhau theo parameter.

## 5. Real production scenario

Một order table tăng từ 5 triệu lên 40 triệu rows sau migration. Status `Archived` chiếm 90%, `Pending` chỉ 0.2%.

Một maintenance process cập nhật hàng triệu rows nhưng statistics chưa phản ánh phân bố mới đúng lúc. Query Pending trước đây dùng seek hiệu quả, sau deploy bắt đầu estimate sai và memory grant/join choice thay đổi.

API p95 tăng dù không có code change đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → query latency tăng từ 80 ms lên 4 s.

**Evidence** → actual plan cho thấy estimated 500 rows nhưng actual 300,000 rows; logical reads tăng mạnh.

**Hypothesis** → cardinality estimation sai.

**Diagnosis** → kiểm tra stats freshness, histogram, parameter values, data skew và predicate correlation.

**Fix** → refresh statistics hoặc điều chỉnh schema/query/index/parameter strategy tùy root cause.

**Verification** → so sánh estimated vs actual rows, logical reads, CPU và duration sau thay đổi.

## 7. Common mistakes

* Thấy slow query rồi lập tức thêm index.
* Chỉ xem graphical icon cost mà không xem estimated vs actual rows.
* Update toàn bộ statistics liên tục và tạo maintenance overhead lớn.
* Nhầm stale stats với parameter sniffing dù hai vấn đề có thể liên quan nhưng không giống nhau.
* Không lưu Query Store/plan evidence trước khi thay đổi.

## 8. Alternatives

Không có “alternative” trực tiếp cho statistics vì optimizer cần cardinality information. Nhưng remediation có thể khác nhau:

* cập nhật statistics;
* filtered statistics/index cho skewed subset;
* query rewrite;
* parameter-sensitive plan support;
* schema/data-model change nếu access pattern không phù hợp.

## 9. Trade-offs

### Advantages

* Statistics tốt giúp optimizer chọn plan phù hợp mà không hard-code hints.
* Giữ query adaptable theo data growth.

### Costs / Risks

* Statistics maintenance tiêu tốn I/O/CPU.
* Sampling có thể không phản ánh tốt skew cực đoan.
* Chasing plan bằng hints có thể giải symptom hôm nay nhưng làm future workload brittle.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu optimizer chọn plan dựa trên ước lượng chứ không “biết” số rows trước khi chạy.

### Middle

Biết xem actual plan, estimated rows và actual rows.

### Senior

Biết nối data distribution → statistics → cardinality → operator choice → I/O/latency.

### Technical Lead / Architect

Thiết kế observability và database-maintenance strategy dựa trên workload, tránh biến tuning thành tập hợp hints/indexes không có evidence.

## 11. Key takeaway

* Index đúng vẫn có thể bị dùng sai nếu cardinality estimate sai.
* So sánh estimated và actual rows là bước diagnosis quan trọng.
* Sửa statistics chỉ khi evidence chỉ về statistics; đừng dùng nó như universal fix.

# 5. Redis cache penetration + negative caching: bảo vệ database trước những lookup luôn miss nhưng không cache dữ liệu “không tồn tại” quá lâu

## 1. What is it?

Cache penetration xảy ra khi requests liên tục hỏi các keys không tồn tại trong cache **và cũng không tồn tại trong source database**, khiến mỗi request xuyên qua cache xuống database.

```text
GET user:does-not-exist
       ↓ cache miss
Redis ──X
       ↓
Database lookup
       ↓ not found
(no cache entry)
       ↓
request tiếp theo lặp lại toàn bộ
```

Negative caching lưu tạm kết quả “không tồn tại” để tránh lookup lặp lại trong một khoảng ngắn.

## 2. Why does it exist?

Cache-aside thường chỉ cache dữ liệu tìm thấy:

```csharp
if (entity is not null)
    await cache.SetAsync(...);
```

Với key invalid phổ biến, bot traffic hoặc clients retry sai ID, cache hit ratio có thể nhìn “xấu” và database chịu toàn bộ requests không có giá trị.

Negative caching giảm load này, nhưng thêm freshness problem: object có thể được tạo ngay sau khi ta cache “not found”.

## 3. How does it work?

Thay vì chỉ có hai trạng thái:

```text
cache hit value
cache miss
```

ta có ba trạng thái logic:

```text
value exists
known-not-found
unknown / cache miss
```

Một sentinel có TTL ngắn đại diện cho not-found:

```text
user:123 -> value TTL 10 min
user:999 -> NOT_FOUND TTL 15 sec
```

TTL negative thường ngắn hơn positive TTL vì absence có thể thay đổi nhanh.

## 4. Practical implementation

```csharp
private const string NotFoundMarker = "__NOT_FOUND__";

public async Task<UserDto?> GetUserAsync(
    Guid id,
    CancellationToken ct)
{
    var key = $"user:{id:N}";
    var cached = await redis.StringGetAsync(key);

    if (cached == NotFoundMarker)
        return null;

    if (cached.HasValue)
        return JsonSerializer.Deserialize<UserDto>(cached!);

    var user = await db.Users
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new UserDto(x.Id, x.Name))
        .SingleOrDefaultAsync(ct);

    if (user is null)
    {
        await redis.StringSetAsync(
            key,
            NotFoundMarker,
            TimeSpan.FromSeconds(15));

        return null;
    }

    await redis.StringSetAsync(
        key,
        JsonSerializer.Serialize(user),
        TimeSpan.FromMinutes(10));

    return user;
}
```

Production code cần thêm failure policy nếu Redis unavailable.

## 5. Real production scenario

Một public product API bị crawler gửi hàng chục nghìn product IDs đã bị xóa. Mỗi ID không tồn tại nên Redis không cache gì và SQL nhận toàn bộ misses.

CPU database tăng dù request business hợp lệ gần như không đổi.

Negative cache 20 giây cho absent products giảm repeated lookups mạnh mà không giữ trạng thái not-found quá lâu.

## 6. Failure scenario & troubleshooting

**Symptom** → product vừa được tạo nhưng API vẫn trả 404 trong vài giây.

**Evidence** → Redis key chứa negative marker còn TTL.

**Hypothesis** → negative cache stale.

**Diagnosis** → trace create flow xem có invalidation key hay không.

**Fix** → invalidate negative key sau create hoặc giữ TTL đủ ngắn theo business freshness requirement.

**Verification** → integration test: miss → create → read phải trả dữ liệu ngay nếu workflow có invalidation.

## 7. Common mistakes

* Cache not-found bằng `null` nhưng code không phân biệt null-cached và cache miss.
* Negative TTL dài ngang positive data.
* Dùng negative caching để che bot/abuse nhưng không có rate limiting.
* Không invalidate khi object được tạo.
* Cho Redis outage fail toàn API dù database fallback vẫn có thể chấp nhận được.

## 8. Alternatives

* Rate limiting: xử lý abuse/load ở ingress nhưng không giải repeated legitimate misses.
* Bloom filter: hữu ích ở scale rất lớn để test membership gần đúng trước database; thêm false positives và operational complexity.
* Không negative cache: phù hợp khi miss rate thấp và DB lookup rẻ.

## 9. Trade-offs

### Advantages

* Giảm database load từ repeated misses.
* Implementation đơn giản hơn Bloom filter.

### Costs / Risks

* Tạo stale absence.
* Cần invalidation/TTL policy.
* Có thể cache attacker-controlled keyspace quá lớn nếu không giới hạn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss không đồng nghĩa object tồn tại ở database.

### Middle

Biết dùng sentinel + TTL để cache not-found.

### Senior

Cân nhắc stale absence, abuse traffic, key cardinality và Redis failure behavior.

### Technical Lead / Architect

Quyết định negative caching có đáng có không dựa trên miss distribution, DB cost và correctness requirement; không thêm Bloom filter nếu scale chưa biện minh complexity.

## 11. Key takeaway

* Cache penetration là load problem từ repeated absence.
* Negative cache cần TTL ngắn và invalidation khi object được tạo.
* Rate limiting và negative caching giải các lớp vấn đề khác nhau.

# 6. DDD Domain Event vs Integration Event: tách business fact nội bộ khỏi contract dùng để giao tiếp giữa bounded contexts

## 1. What is it?

Domain Event biểu diễn một business fact đã xảy ra **bên trong domain/bounded context**. Integration Event là message contract được publish ra ngoài boundary để context/service khác phản ứng.

Ví dụ:

```text
Order aggregate
   ↓
OrderConfirmedDomainEvent
   ↓ application boundary
Mapping / policy
   ↓
OrderConfirmedIntegrationEvent v1
   ↓
Service Bus
```

Hai loại event có thể cùng diễn tả một business occurrence nhưng có ownership và compatibility requirements khác nhau.

## 2. Why does it exist?

Nếu domain object publish trực tiếp event schema ra Service Bus, internal domain model vô tình trở thành public distributed contract.

Một refactor nội bộ như đổi Value Object hoặc field name có thể làm consumers khác vỡ.

Tách Domain Event và Integration Event cho phép:

* domain model thay đổi theo business nội bộ;
* external contract tiến hóa có versioning/backward compatibility riêng;
* chỉ publish facts thực sự cần ngoài boundary.

## 3. How does it work?

Domain Event thường được raised trong aggregate khi invariant transition hoàn tất:

```text
Order.Confirm()
  ├─ validate invariant
  ├─ state = Confirmed
  └─ raise OrderConfirmedDomainEvent
```

Application layer xử lý event, có thể ghi Outbox message chứa Integration Event.

```text
DB transaction
  ├─ Order state
  └─ Outbox integration event
          ↓ commit
Worker publishes
          ↓
Message broker
```

Domain Event không nhất thiết asynchronous hoặc distributed. Integration Event thường vượt process/bounded-context boundary và phải chịu duplicate delivery, versioning, schema compatibility.

## 4. Practical implementation

Domain event:

```csharp
public sealed record OrderConfirmedDomainEvent(
    Guid OrderId,
    DateTimeOffset ConfirmedAt);
```

Integration contract:

```csharp
public sealed record OrderConfirmedV1(
    Guid OrderId,
    string ConfirmedAtUtc,
    string EventId);
```

Mapping tại application boundary:

```csharp
var integrationEvent = new OrderConfirmedV1(
    domainEvent.OrderId,
    domainEvent.ConfirmedAt.UtcDateTime.ToString("O"),
    Guid.NewGuid().ToString("N"));
```

Không expose toàn bộ aggregate:

```csharp
// Tránh serialize Order entity trực tiếp thành integration message.
```

## 5. Real production scenario

Order context xác nhận order. Billing cần tạo payment instruction; Notifications cần gửi email.

Domain model nội bộ sau đó đổi `Money` implementation và thêm fraud state. Nếu Integration Event chỉ chứa contract ổn định mà consumers cần, Billing/Notifications không bị buộc thay đổi theo refactor nội bộ.

## 6. Failure scenario & troubleshooting

**Symptom** → deploy Order service làm consumer cũ fail deserialize message.

**Evidence** → message schema đổi theo domain entity mới.

**Hypothesis** → internal model bị dùng trực tiếp làm integration contract.

**Diagnosis** → inspect producer serialization path; thấy entity/domain event được publish thẳng.

**Fix** → introduce explicit versioned Integration Event; mapping tại boundary; giữ old contract trong migration window.

**Verification** → contract tests giữa producer schema và supported consumers.

## 7. Common mistakes

* Gọi mọi message là Domain Event.
* Serialize entity rồi publish lên broker.
* Cho Integration Event chứa internal implementation details.
* Dùng Domain Event để né explicit application workflow.
* Giả định event publish exactly-once.
* Không version external message contract.

## 8. Alternatives

* Direct synchronous API call: đơn giản hơn khi consumer cần immediate response và coupling chấp nhận được.
* Application command: phù hợp khi intent chưa xảy ra, khác với event là fact đã xảy ra.
* Shared database: đôi khi đơn giản cho monolith, nhưng không nên dùng để phá bounded-context ownership một cách vô thức.

## 9. Trade-offs

### Advantages

* Giảm coupling giữa domain model và distributed contract.
* Cho phép schema evolution độc lập.
* Boundary/ownership rõ hơn.

### Costs / Risks

* Thêm mapping và message types.
* Eventual consistency tăng reasoning/observability cost.
* Nếu dùng events quá mức, flow business trở nên khó theo dõi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event mô tả điều đã xảy ra, command mô tả intent muốn xảy ra.

### Middle

Biết raise Domain Event và map sang Integration Event có schema riêng.

### Senior

Hiểu transaction/Outbox, duplicate delivery, versioning và consumer compatibility.

### Technical Lead / Architect

Quyết định event nào thực sự cần vượt bounded context, ai sở hữu contract và khi nào synchronous call đơn giản hơn event-driven architecture.

## 11. Key takeaway

* Domain Event và Integration Event có boundary và lifecycle khác nhau.
* Không publish domain entity trực tiếp như distributed contract.
* Event-driven design chỉ đáng dùng khi coupling/consistency trade-off phù hợp business flow.

# 7. Azure Service Bus sessions: giữ ordering theo business key mà không biến toàn queue thành single-threaded bottleneck

## 1. What is it?

Azure Service Bus sessions cho phép nhóm messages theo `SessionId` và xử lý từng session theo thứ tự tương đối trong cùng session.

Mental model:

```text
Session Order-1001: M1 → M2 → M3
Session Order-1002: M1 → M2
Session Order-1003: M1 → M2 → M3 → M4

Consumers có thể xử lý nhiều sessions song song,
nhưng một session được ownership theo lock tại một thời điểm.
```

Ordering được giới hạn theo business key thay vì toàn bộ queue.

## 2. Why does it exist?

Một workflow có thể cần:

```text
OrderCreated
→ PaymentCaptured
→ OrderShipped
```

Nếu messages của cùng order bị xử lý đảo thứ tự, consumer có thể thấy `OrderShipped` trước `OrderCreated`.

Giải pháp “chỉ chạy một consumer cho toàn queue” giữ ordering nhưng phá throughput toàn hệ thống.

Sessions cho phép partition ordering concern theo aggregate/business key.

## 3. How does it work?

Producer set:

```csharp
message.SessionId = orderId.ToString();
```

Receiver accept session và giữ session lock. Messages trong session được receive tuần tự theo broker ordering semantics.

Tuy nhiên ordering không thay thế idempotency. Message có thể bị redelivered nếu lock mất hoặc settlement không hoàn tất.

```text
ordering + at-least-once
≠ exactly-once processing
```

Session state cũng có thể được dùng cho workflow metadata, nhưng cần tránh biến broker thành domain database.

## 4. Practical implementation

Producer:

```csharp
var message = new ServiceBusMessage(BinaryData.FromObjectAsJson(evt))
{
    MessageId = evt.EventId,
    SessionId = evt.OrderId.ToString("N")
};

await sender.SendMessageAsync(message, ct);
```

Processor configuration:

```csharp
var processor = client.CreateSessionProcessor(
    queueName,
    new ServiceBusSessionProcessorOptions
    {
        MaxConcurrentSessions = 16,
        MaxConcurrentCallsPerSession = 1,
        AutoCompleteMessages = false
    });
```

Handler vẫn phải idempotent:

```csharp
if (await inbox.AlreadyProcessedAsync(args.Message.MessageId, ct))
{
    await args.CompleteMessageAsync(args.Message, ct);
    return;
}
```

## 5. Real production scenario

Automotive marketplace nhận lifecycle events theo listing: Created, PriceChanged, Reserved, Sold.

Ordering chỉ cần đúng **trong từng listing**, không cần Listing A chờ Listing B.

`SessionId = ListingId` cho phép hàng trăm listings chạy song song nhưng mỗi listing giữ sequence hợp lý.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog tăng mạnh nhưng CPU consumers thấp.

**Evidence** → phần lớn messages tập trung vào một vài SessionIds; một session có hàng trăm nghìn messages.

**Hypothesis** → hot session đang serialize quá nhiều work.

**Diagnosis** → metric backlog theo business/session distribution; inspect `MaxConcurrentSessions`, processing duration và lock renewals.

**Fix** → xem lại session key granularity hoặc business design; tối ưu handler; không tăng concurrency bên trong session nếu ordering tuyệt đối cần giữ.

**Verification** → backlog age giảm mà ordering tests vẫn pass.

## 7. Common mistakes

* Dùng cùng một `SessionId` cho toàn queue.
* Nghĩ session bảo đảm exactly-once.
* Không thiết kế idempotency vì đã có ordering.
* Chọn session key quá coarse tạo hot session.
* Giữ session lock trong external call rất lâu mà không có timeout/retry discipline.

## 8. Alternatives

* Không dùng ordering: đơn giản nhất nếu business có thể xử lý out-of-order bằng version/timestamp.
* Partitioned Kafka-style log: phù hợp event streaming use case khác, nhưng operational model khác Service Bus.
* Single consumer: chỉ hợp lý với throughput thấp và ordering toàn cục thực sự bắt buộc.

## 9. Trade-offs

### Advantages

* Ordering theo key mà vẫn có parallelism giữa keys.
* Phù hợp aggregate/workflow-oriented messages.

### Costs / Risks

* Hot session giới hạn throughput.
* Lock/session lifecycle tăng complexity.
* Vẫn phải xử lý duplicate delivery và poison messages.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ordering thường cần theo entity/business key, không phải toàn hệ thống.

### Middle

Biết set `SessionId`, cấu hình session processor và manual settlement.

### Senior

Nhận diện hot session, lock loss, duplicate delivery và idempotency.

### Technical Lead / Architect

Quyết định business invariant nào thực sự cần ordering; nếu out-of-order có thể giải bằng versioning thì có thể bỏ sessions để giảm coupling/throughput constraint.

## 11. Key takeaway

* Sessions cung cấp ordering theo key, không phải exactly-once.
* Chọn `SessionId` chính là quyết định partitioning throughput.
* Nếu business không thật sự cần ordering, đừng thêm session complexity.

# 8. Kubernetes graceful termination: SIGTERM, readiness và `terminationGracePeriodSeconds` phải phối hợp để tránh drop request khi rollout

## 1. What is it?

Khi Kubernetes terminate Pod, process không nên bị kill ngay lập tức. Pod có một graceful-termination lifecycle để application ngừng nhận traffic mới và hoàn tất work đang chạy trước khi bị force kill.

Mental model:

```text
Pod termination starts
    ↓
endpoint/readiness removal begins
    ↓
SIGTERM sent to process
    ↓
application graceful shutdown
    ↓
termination grace expires
    ↓
SIGKILL if still running
```

Application, readiness behavior, load balancer propagation và grace period phải align.

## 2. Why does it exist?

Rolling deployment thay Pods liên tục. Nếu process biến mất ngay khi deployment controller quyết định terminate:

* in-flight HTTP requests bị reset;
* queue messages có thể bị xử lý dở;
* database transaction có thể rollback;
* clients retry và tạo retry storm.

Graceful shutdown giảm disruption nhưng không thể cứu work vô hạn; hệ thống vẫn cần bounded operation duration.

## 3. How does it work?

Kubernetes gửi termination signal và bắt đầu grace timer. ASP.NET Core host nhận shutdown signal và `ApplicationStopping` được trigger.

Readiness cần chuyển sang trạng thái không nhận traffic mới đủ sớm để service/load balancer ngừng route requests.

Một race thường gặp:

```text
SIGTERM
↓
app starts shutdown
↓
load balancer vẫn route request trong vài giây
↓
new request hits draining pod
```

Vì control-plane/network propagation không instantaneous, hệ thống có thể cần `preStop`, readiness coordination hoặc đủ shutdown budget tùy environment.

## 4. Practical implementation

ASP.NET Core background worker phải tôn trọng cancellation:

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await ProcessNextMessageAsync(stoppingToken);
        }
    }
}
```

Deployment example:

```yaml
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: my-api:1.4.0
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
```

Long-running operations cần timeout nhỏ hơn grace window hoặc resumable/idempotent design.

## 5. Real production scenario

Một API chạy 6 replicas, mỗi request mất tối đa 8 giây. Deployment rollout terminate từng Pod.

Version đầu có grace period 5 giây. Một số in-flight requests bị SIGKILL trước khi hoàn tất, clients retry và error rate tăng chỉ trong deployment window.

Tăng grace period hợp lý, giảm traffic mới qua readiness và đặt request/dependency timeout có budget rõ giúp rollout trở nên ổn định.

## 6. Failure scenario & troubleshooting

**Symptom** → 502/connection reset chỉ tăng trong deployment.

**Evidence** → errors trùng thời điểm Pod termination; container exit code/signal cho thấy forced kill; traces bị cắt giữa request.

**Hypothesis** → graceful shutdown budget hoặc readiness drain không đủ.

**Diagnosis** → compare request duration, `terminationGracePeriodSeconds`, load-balancer propagation và shutdown logs.

**Fix** → align readiness/drain/grace; propagate cancellation; giảm long-running synchronous request nếu cần.

**Verification** → repeated rolling deployment dưới load không làm error rate vượt SLO threshold.

## 7. Common mistakes

* Tăng grace period lên vài phút để che operation design không bounded.
* Readiness endpoint vẫn trả healthy khi app đã bắt đầu shutdown.
* Background worker bỏ qua `stoppingToken`.
* Fire-and-forget work trong Pod rồi giả định nó sẽ hoàn tất trước termination.
* Chỉ test startup, không test shutdown/rollout under load.

## 8. Alternatives

* External queue + resumable workers: tốt cho long-running work.
* Azure App Service/Container Apps có lifecycle khác nhưng vẫn cần graceful-shutdown reasoning.
* Blue-Green deployment giảm overlap risk nhưng vẫn không loại bỏ connection draining và in-flight work concerns.

## 9. Trade-offs

### Advantages

* Giảm request drops khi rollout/scale-down.
* Cho worker cơ hội settle/requeue work sạch hơn.

### Costs / Risks

* Grace period dài làm rollout/scale-down chậm.
* Shutdown correctness đòi hỏi cancellation propagation.
* Không bảo đảm completion nếu node/process crash đột ngột.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Pod termination không nên được coi như process kill tức thời.

### Middle

Biết readiness probe, `stoppingToken` và termination grace.

### Senior

Điều tra deployment-only failures bằng traces, signals, request duration và load-balancer drain behavior.

### Technical Lead / Architect

Thiết kế workload sao cho graceful shutdown chỉ là resilience layer, không phải correctness dependency; critical work phải resumable/idempotent khi process chết bất ngờ.

## 11. Key takeaway

* Graceful termination cần phối hợp app + readiness + networking + timeout budget.
* `terminationGracePeriodSeconds` không thay thế idempotency/resumability.
* Test rollout dưới traffic thực tế, không chỉ test steady state.

# 9. OpenTelemetry metric cardinality explosion: một label sai có thể làm observability backend tốn memory, chi phí và mất khả năng vận hành

## 1. What is it?

Metric cardinality là số lượng distinct time series sinh ra từ tên metric và tập attribute/label values.

Ví dụ tốt:

```text
http_requests_total{method="GET",status="200"}
```

số combinations bị giới hạn.

Ví dụ nguy hiểm:

```text
http_requests_total{user_id="..."}
```

với 10 triệu users có thể tạo hàng triệu series.

Mental model:

```text
1 metric name
× label A values
× label B values
× label C values
= possible time-series cardinality
```

## 2. Why does it exist?

Metrics được tối ưu cho aggregation trên dimensions có cardinality bounded: status, region, endpoint template, queue name.

Developer thường muốn “thêm context để debug” và vô tình đưa unique identifiers vào labels. Điều đó phù hợp hơn với logs/traces, không phải metrics.

High cardinality làm backend phải ingest, index, retain và query rất nhiều series.

## 3. How does it work?

Một counter:

```csharp
requests.Add(1,
    new("route", route),
    new("status", statusCode));
```

tạo series khác nhau theo combination attributes.

Nếu route là normalized template:

```text
/orders/{id}
```

cardinality thấp.

Nếu route là raw path:

```text
/orders/8c2...
/orders/a71...
/orders/991...
```

cardinality tăng theo số orders.

OpenTelemetry SDK/backend có views/processors/limits tùy stack, nhưng primary defense vẫn là **semantic discipline ở instrumentation source**.

## 4. Practical implementation

Tốt:

```csharp
private static readonly Meter Meter = new("Orders.Api");
private static readonly Counter<long> Requests =
    Meter.CreateCounter<long>("orders.requests");

public static void Record(string operation, string outcome)
{
    Requests.Add(
        1,
        new KeyValuePair<string, object?>("operation", operation),
        new KeyValuePair<string, object?>("outcome", outcome));
}
```

Không tốt:

```csharp
Requests.Add(1,
    new("order_id", orderId),
    new("user_email", email));
```

Unique business identifiers nên nằm trong trace/log nếu cần correlation.

## 5. Real production scenario

Một team thêm `customerId` vào custom latency histogram để “biết customer nào chậm”. Sau release, telemetry ingestion tăng hàng chục lần; dashboard query chậm và observability bill tăng mạnh.

Metric không sai về code syntax nhưng sai về **data model**.

Thay `customerId` bằng tier/region bounded dimensions, còn customer-specific investigation dùng trace search/log correlation.

## 6. Failure scenario & troubleshooting

**Symptom** → metric ingestion/cost tăng đột ngột sau deploy; dashboards timeout.

**Evidence** → series count của một metric tăng hàng trăm lần.

**Hypothesis** → attribute mới có unbounded cardinality.

**Diagnosis** → inspect top label distinct counts và instrumentation diff.

**Fix** → remove/normalize attribute; apply views/filtering nếu cần emergency mitigation.

**Verification** → active series count và ingestion volume trở lại expected baseline.

## 7. Common mistakes

* Dùng `userId`, `orderId`, URL raw hoặc exception message làm label.
* Nghĩ “thêm label không đáng kể”.
* Dùng metrics để thay logs/traces.
* Dashboard group-by dimension có hàng triệu values.
* Không review telemetry schema như một production data contract.

## 8. Alternatives

* Logs: tốt cho discrete events và rich context.
* Traces: tốt cho per-request causal investigation.
* Metrics: tốt cho aggregate trends, alerts, SLI/SLO và bounded dimensions.

Ba signal bổ sung nhau; không signal nào thay thế hoàn toàn signal khác.

## 9. Trade-offs

### Advantages

* Labels bounded cho phép slicing/aggregation rất hiệu quả.
* Metrics phù hợp alerting và trend analysis.

### Costs / Risks

* Cardinality tăng multiplicatively.
* Observability backend cost có thể tăng rất nhanh.
* Cắt labels quá mạnh lại làm mất khả năng phân đoạn hữu ích.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu label tạo nhiều time series chứ không chỉ là metadata miễn phí.

### Middle

Biết chọn bounded dimensions như status/region/operation.

### Senior

Theo dõi series count, ingestion cost và phân biệt dữ liệu nên ở metric, log hay trace.

### Technical Lead / Architect

Đặt telemetry schema conventions/cardinality budgets và review observability changes như production architecture, không phải debug detail tùy ý.

## 11. Key takeaway

* Metric labels phải có cardinality bounded và predictable.
* Unique identifiers thuộc logs/traces hơn là metrics.
* Observability data model sai có thể trở thành production/cost incident thật sự.

# 10. OAuth 2.0 / OpenID Connect signing-key rotation với JWKS: token validation phải sống sót qua key rollover thay vì hard-code certificate

## 1. What is it?

Identity Provider ký JWT bằng private key; applications validate signature bằng public key tương ứng.

JWKS — JSON Web Key Set — là endpoint metadata công bố các public signing keys hiện hành. JWT thường chứa `kid` để validator chọn đúng key.

```text
Identity Provider
 private key K2
      ↓ signs JWT kid=K2

API
  ↓ reads kid
JWKS cache: K1, K2
  ↓
validate signature with K2 public key
```

Key rotation là lifecycle bình thường, không phải incident bất thường.

## 2. Why does it exist?

Signing key không nên tồn tại vĩnh viễn. Identity Provider có thể rotate định kỳ, do certificate expiry, security policy hoặc emergency compromise response.

Nếu API hard-code một public certificate/key trong config, lần rotation tiếp theo có thể làm toàn bộ valid tokens fail ngay lập tức.

OIDC discovery + JWKS cho phép validator refresh signing-key metadata tự động.

## 3. How does it work?

OIDC authority exposes discovery metadata, thường gồm `jwks_uri`.

JWT header:

```json
{
  "alg": "RS256",
  "kid": "key-2026-09"
}
```

Validator:

1. đọc `kid`;
2. tìm matching key trong cached JWKS;
3. validate cryptographic signature;
4. validate issuer;
5. validate audience;
6. validate lifetime;
7. áp dụng authorization policy dựa trên claims đã tin cậy.

Trong rollover window, IdP có thể expose cả old và new public keys để tokens cũ chưa hết hạn vẫn validate được.

## 4. Practical implementation

ASP.NET Core nên cấu hình authority/metadata thay vì tự hard-code signing key:

```csharp
builder.Services
    .AddAuthentication("Bearer")
    .AddJwtBearer("Bearer", options =>
    {
        options.Authority = builder.Configuration["Auth:Authority"];
        options.Audience = "orders-api";

        options.TokenValidationParameters.ValidateIssuer = true;
        options.TokenValidationParameters.ValidateAudience = true;
        options.TokenValidationParameters.ValidateLifetime = true;
        options.TokenValidationParameters.ValidateIssuerSigningKey = true;
    });
```

Framework metadata manager có thể cache và refresh discovery/JWKS theo policy thay vì tải keys ở mọi request.

## 5. Real production scenario

Enterprise API validate tokens từ Microsoft Entra ID. Identity provider rotate signing certificate.

Một legacy service hard-code certificate thumbprint nên bắt đầu trả 401 cho toàn bộ traffic dùng key mới. Service khác dùng standard OIDC metadata/JWKS tiếp tục hoạt động vì keyset được refresh.

Incident nhìn giống “authentication randomly broken”, nhưng root cause là key lifecycle assumption sai.

## 6. Failure scenario & troubleshooting

**Symptom** → 401 tăng đột ngột; token issuer/audience vẫn đúng; error cho biết signing key không tìm thấy.

**Evidence** → JWT `kid` không tồn tại trong validator cache nhưng có trong current JWKS endpoint.

**Hypothesis** → metadata/JWKS cache chưa refresh hoặc outbound access tới IdP bị chặn.

**Diagnosis** → kiểm tra discovery URL, JWKS response, `kid`, cache refresh logs, DNS/proxy/firewall connectivity.

**Fix** → cho metadata refresh hoạt động; sửa networking; tránh hard-code single key.

**Verification** → validate tokens ký bởi old/new keys trong rollover window và test key refresh path.

## 7. Common mistakes

* Hard-code signing certificate/key.
* Chỉ kiểm tra signature mà bỏ issuer/audience/lifetime.
* Disable validation để “fix 401”.
* Fetch JWKS ở mọi request, tạo remote dependency không cần thiết.
* Không cho application outbound access tới authority/JWKS trong Production nhưng local thì có.
* Log toàn access token khi debug, gây sensitive-data leakage.

## 8. Alternatives

* Symmetric shared secret: đơn giản trong một số closed systems nhưng key distribution/rotation khó hơn và mọi validator giữ secret có khả năng ký.
* Introspection endpoint: phù hợp opaque tokens hoặc centralized validation, nhưng thêm runtime network dependency.
* Standard JWT + OIDC discovery/JWKS: phù hợp distributed APIs cần local signature validation và scalable verification.

## 9. Trade-offs

### Advantages

* Public-key distribution an toàn hơn shared signing secret.
* Validation local, không cần gọi IdP trên từng request.
* Hỗ trợ key rollover chuẩn hóa.

### Costs / Risks

* Metadata caching/refresh cần hoạt động đúng.
* Clock skew, issuer/audience config và networking vẫn có thể gây outage.
* JWT đã phát hành thường còn valid tới expiry trừ khi có cơ chế revocation bổ sung.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu private key dùng để ký, public key dùng để verify và `kid` chọn key phù hợp.

### Middle

Biết cấu hình `JwtBearer` với authority/audience và không hard-code key.

### Senior

Debug được unknown `kid`, metadata cache, issuer/audience/lifetime và Production networking differences.

### Technical Lead / Architect

Thiết kế identity validation dựa trên standard discovery/key rotation, xác định token lifetime/revocation model và đảm bảo auth dependency không trở thành single point of operational surprise.

## 11. Key takeaway

* Signing-key rotation là lifecycle bình thường và validator phải được thiết kế cho rollover.
* JWKS + `kid` giúp APIs chọn public key đúng mà không hard-code certificate.
* Signature hợp lệ chưa đủ: issuer, audience và lifetime vẫn phải được validate đầy đủ.
