# 1. C# Nullable Reference Types: biến nullability thành static contract thay vì chờ `NullReferenceException` ở runtime

## 1. What is it?

Mental model của Nullable Reference Types (NRT) không phải là CLR có thêm một loại reference mới. Runtime vẫn chỉ có reference có thể bằng `null`; NRT là **static analysis contract** do compiler theo dõi.

```text
string   -> compiler kỳ vọng non-null
string?  -> compiler cho phép null và yêu cầu caller xử lý
```

Ví dụ:

```csharp
string name = GetName();
string? middleName = TryGetMiddleName();
```

`string` và `string?` gần như giống nhau ở runtime metadata/layout, nhưng chúng mang semantic khác nhau cho compiler, tooling và API consumers.

## 2. Why does it exist?

Trong codebase lớn, `null` thường là một implicit contract không được viết ra:

- method có thể trả null nhưng signature không nói rõ;
- DTO field tưởng bắt buộc nhưng mapping có thể để trống;
- dependency được khởi tạo muộn;
- database column nullable nhưng model không phản ánh;
- legacy API trả dữ liệu thiếu.

Nếu chỉ phát hiện bằng `NullReferenceException`, bug xuất hiện muộn ở runtime và thường xa nơi contract bị phá.

NRT đẩy nhiều lỗi null từ production về build/code review.

## 3. How does it work?

Compiler thực hiện flow analysis:

```csharp
string? input = request.Name;

if (input is null)
    return Results.BadRequest();

Console.WriteLine(input.Length); // safe sau null check
```

Compiler theo dõi state như `not-null`, `maybe-null`, nhưng đây không phải proof hoàn hảo. Reflection, serializers, ORM materialization, interop và null-forgiving operator `!` có thể phá giả định.

`!` chỉ tắt warning:

```csharp
var length = possiblyNull!.Length;
```

Nó không tạo runtime guard.

## 4. Practical implementation

Đối với request contract, nên để nullability phản ánh semantics:

```csharp
public sealed record CreateCustomerRequest(
    string Email,
    string? MiddleName);
```

Trong domain object, nếu property buộc phải có sau construction, ưu tiên constructor hoặc `required`:

```csharp
public sealed class Customer
{
    public required string Email { get; init; }
    public string? MiddleName { get; init; }
}
```

Khi dùng EF Core, model nullability nên khớp schema. Nếu database cho phép null nhưng model khai báo non-null, application có thể compile sạch nhưng fail khi materialize hoặc dùng giá trị.

## 5. Real production scenario

Một CRM đồng bộ customer từ legacy system. `PhoneNumber` trong source không bắt buộc nhưng DTO nội bộ dùng `string`. Team quen với assumption “source luôn có phone”. Một record cũ không có phone đi qua mapper rồi gây `NullReferenceException` ở notification formatter.

Sau khi bật NRT theo project và sửa contract thành `string?`, warning lan tới mapper, formatter và validation layer. Team buộc phải quyết định rõ: field optional thật, hay integration phải reject record thiếu dữ liệu.

## 6. Failure scenario & troubleshooting

**Symptom** → project bật NRT nhưng production vẫn có `NullReferenceException`.

**Evidence** → code có nhiều `!`, DTOs được deserialize từ external JSON, reflection-based code hoặc database schema không khớp annotations.

**Hypothesis** → static contract đang được compiler tin nhưng runtime input không tuân theo contract.

**Diagnosis** → trace từ exception về boundary nhận dữ liệu; kiểm tra serializer, EF schema, external API và các `!` suppression gần đó.

**Fix** → validate ở boundary, sửa nullability annotation, dùng constructors/`required`, giảm suppression.

**Verification** → thêm negative integration tests với missing/null fields và bật warnings-as-errors cho nullable warnings quan trọng.

## 7. Common mistakes

- Đổi mọi warning thành `!` để build xanh.
- Khai báo tất cả reference là `?`, khiến static contract gần như vô nghĩa.
- Nghĩ non-nullable property tự động validate JSON request.
- Không đồng bộ nullability với database schema.
- Dùng `= null!;` rộng rãi mà không có lifecycle rõ ràng.
- Bật NRT toàn legacy solution một lần rồi nhận hàng nghìn warnings khó xử lý.

## 8. Alternatives

- Runtime guards như `ArgumentNullException.ThrowIfNull` vẫn cần ở public/runtime boundaries.
- Validation framework giải quyết business validation, không thay thế NRT.
- Option/Maybe types có thể biểu diễn optionality mạnh hơn trong một số domain nhưng tăng abstraction cost.

## 9. Trade-offs

### Advantages

- Phát hiện nhiều null bugs khi compile.
- Làm API contracts rõ ràng hơn.
- IDE/refactoring hiểu intent tốt hơn.

### Costs / Risks

- Migration legacy code có nhiều warnings.
- Static analysis không bảo vệ khỏi dữ liệu runtime sai contract.
- Suppression thiếu kỷ luật tạo false confidence.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `string?` nghĩa là caller phải xử lý khả năng null; `!` không phải null check.

### Middle

Thiết kế DTO/service signatures phản ánh optionality thực tế và xử lý warnings đúng nguyên nhân.

### Senior

Nhận diện boundary nơi compiler không thể đảm bảo: JSON, DB, reflection, external APIs; thiết kế runtime validation phù hợp.

### Technical Lead / Architect

Lập chiến lược bật NRT theo module, quy ước suppression, schema alignment và policy CI thay vì biến migration thành mass-edit warnings.

## 11. Key takeaway

- NRT là static contract, không phải runtime safety mechanism.
- Nullability phải phản ánh business/data contract thật.
- `!` nên là ngoại lệ có lý do, không phải công cụ dọn warning.

# 2. ASP.NET Core Response Compression: giảm payload có chọn lọc mà không đổi CPU, latency và security lấy vài KB một cách mù quáng

## 1. What is it?

Response Compression middleware nén HTTP response trước khi gửi tới client khi client khai báo hỗ trợ encoding như `gzip` hoặc `br`.

Mental model:

```text
Application response
      |
      v
Response Compression
      |
 Brotli / gzip
      |
      v
reverse proxy / CDN / client
```

Compression là trade-off giữa **network bytes** và **CPU work**. Nó hữu ích nhất với text-based payload lớn, lặp nhiều như JSON, HTML, CSS, JavaScript.

## 2. Why does it exist?

Network transfer có latency và bandwidth cost. JSON 500 KB có thể nén xuống nhỏ hơn nhiều, đặc biệt trên mobile/remote links.

Nhưng không phải response nào cũng nên nén:

- JPEG/PNG/MP4 đã compressed;
- payload rất nhỏ có overhead không đáng;
- TLS compression-related attack surfaces cần xem xét khi response chứa secrets phụ thuộc attacker-controlled input;
- CDN/reverse proxy có thể đã làm compression tốt hơn.

## 3. How does it work?

Client gửi:

```http
Accept-Encoding: br, gzip
```

Server chọn encoding và trả:

```http
Content-Encoding: br
Vary: Accept-Encoding
```

`Vary` quan trọng để cache phân biệt compressed variants.

Trong ASP.NET Core:

```csharp
builder.Services.AddResponseCompression(options =>
{
    options.EnableForHttps = true;
});

app.UseResponseCompression();
```

Middleware order cần đặt đủ sớm để response đi qua compression nhưng không phá static-file/CDN strategy.

## 4. Practical implementation

Một production configuration nên kiểm tra content types và providers thay vì bật mù:

```csharp
builder.Services.AddResponseCompression(options =>
{
    options.EnableForHttps = true;
    options.MimeTypes = ResponseCompressionDefaults.MimeTypes.Concat(
        new[] { "application/json" });
});
```

Sau đó benchmark:

```text
payload size before/after
CPU per request
p95 latency
throughput
CDN hit ratio
```

Nếu Azure Front Door/Akamai/CDN đang nén ở edge, origin compression có thể không còn nhiều giá trị hoặc làm CPU app tăng.

## 5. Real production scenario

Một product-list API trả 1.2 MB JSON. Team bật Brotli highest compression level ở app server. Bandwidth giảm mạnh nhưng CPU tăng tới mức App Service scale-out sớm hơn và p99 latency tăng trong peak traffic.

Giải pháp không phải “tắt compression”; team chuyển sang compression level cân bằng hơn, thu nhỏ DTO, thêm pagination, và để CDN xử lý static/text assets ở edge.

## 6. Failure scenario & troubleshooting

**Symptom** → network payload nhỏ hơn nhưng API latency/CPU xấu đi.

**Evidence** → profiler cho thấy compression chiếm CPU đáng kể; response size lớn do over-fetching.

**Hypothesis** → compression đang che payload-design problem hoặc level quá cao.

**Diagnosis** → so sánh response size, CPU, throughput và p95/p99 với compression on/off; inspect CDN/proxy behavior.

**Fix** → giảm payload, chọn compression level hợp lý, chỉ nén MIME types phù hợp, chuyển compression ra edge khi phù hợp.

**Verification** → load test realistic concurrency và đo end-to-end bytes + CPU + latency.

## 7. Common mistakes

- Bật compression cho ảnh/video đã nén.
- Chỉ nhìn response size mà không đo CPU.
- Quên `Vary: Accept-Encoding` khi tự implement caching/compression.
- Dùng compression để che API trả quá nhiều fields.
- Không kiểm tra reverse proxy/CDN đã compress hay chưa.
- Bật nén dynamic responses chứa secrets cùng attacker-controlled text mà không xem security model.

## 8. Alternatives

- Pagination/projection để giảm dữ liệu ngay từ nguồn.
- Binary formats như gRPC/protobuf cho service-to-service scenarios phù hợp.
- CDN edge compression cho public/cacheable content.
- Không nén payload nhỏ.

## 9. Trade-offs

### Advantages

- Giảm bandwidth và transfer time.
- Hữu ích cho JSON/HTML lớn.
- Có thể cải thiện user-perceived latency trên slow networks.

### Costs / Risks

- Tốn CPU.
- Compression level cao có diminishing returns.
- Cache/security behavior phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Accept-Encoding`/`Content-Encoding` và vì sao text nén tốt hơn media đã compressed.

### Middle

Cấu hình middleware, kiểm tra MIME types và đo payload size.

### Senior

Đánh giá CPU-vs-network trade-off, CDN interaction và security consequences.

### Technical Lead / Architect

Quyết định compression nằm ở app, proxy hay CDN và tránh tối ưu transport trong khi root cause là API over-fetching.

## 11. Key takeaway

- Compression không miễn phí; đổi network cost lấy CPU cost.
- Giảm dữ liệu ở source thường tốt hơn chỉ nén payload quá lớn.
- Đo end-to-end với CDN/proxy thực tế trước khi kết luận.

# 3. EF Core `FromSql` / `ExecuteSql`: dùng raw SQL khi cần nhưng vẫn giữ parameterization và transaction boundary an toàn

## 1. What is it?

EF Core cho phép dùng raw SQL khi LINQ không biểu diễn query tốt, cần stored procedure, database-specific feature hoặc set-based operation đặc biệt.

Mental model:

```text
LINQ / EF abstractions       Raw SQL
        \                    /
         \                  /
           DbConnection
               |
             SQL DB
```

Raw SQL không có nghĩa phải từ bỏ parameterization, transactions, cancellation và observability.

## 2. Why does it exist?

ORM tối ưu cho productivity và composability, nhưng không phải mọi database capability đều map đẹp sang LINQ. Ví dụ:

- complex CTE/window query;
- vendor-specific hints/functions;
- stored procedures;
- bulk maintenance scripts;
- hand-tuned reporting SQL.

Nếu ép mọi thứ qua LINQ, query có thể khó đọc hoặc translation không phù hợp.

## 3. How does it work?

Parameterized form:

```csharp
var minTotal = 1000m;

var customers = await db.Customers
    .FromSql($"SELECT * FROM Customers WHERE TotalSpend >= {minTotal}")
    .AsNoTracking()
    .ToListAsync(ct);
```

Interpolated API của EF Core parameterizes values. Ngược lại, tự ghép string có thể tạo SQL injection:

```csharp
var sql = $"SELECT * FROM Customers WHERE Name = '{name}'"; // unsafe
```

Identifiers như column/table names không parameterize giống scalar values, nên dynamic SQL cần whitelist rõ ràng.

## 4. Practical implementation

Khi cần command:

```csharp
await db.Database.ExecuteSqlAsync(
    $"UPDATE Orders SET Archived = 1 WHERE CreatedAt < {cutoff}",
    ct);
```

Nếu raw SQL và tracked EF operations phải atomic, dùng explicit transaction:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

await db.Database.ExecuteSqlAsync(
    $"UPDATE Inventory SET Reserved = Reserved + {qty} WHERE Id = {id}", ct);

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Transaction boundary phải dựa trên business invariant, không phải vì “raw SQL trông nguy hiểm”.

## 5. Real production scenario

Một reporting endpoint cần window functions và ranking trên hàng triệu rows. LINQ translation hoạt động nhưng generated SQL khó kiểm soát và plan không ổn định. Team dùng một hand-tuned SQL query được review cùng DBA, map kết quả vào keyless DTO và giữ parameterization.

Hiệu quả đến từ access pattern/query design, không phải vì raw SQL tự động nhanh hơn EF.

## 6. Failure scenario & troubleshooting

**Symptom** → security scan phát hiện SQL injection hoặc production xuất hiện syntax errors chỉ với một số input.

**Evidence** → query string được concatenated từ request values hoặc sort column tùy ý.

**Hypothesis** → dynamic SQL đang trộn user data với SQL syntax.

**Diagnosis** → inspect every raw SQL construction path và logging generated command text/parameters an toàn.

**Fix** → parameterize scalar values, whitelist identifiers, giảm dynamic SQL surface.

**Verification** → security tests với quotes/control characters + integration tests trên actual DB.

## 7. Common mistakes

- Nghĩ raw SQL luôn nhanh hơn LINQ.
- Concatenate user input.
- Log sensitive parameter values.
- Quên `AsNoTracking` cho read-only raw queries.
- Trộn raw command và `SaveChanges` mà không hiểu transaction semantics.
- Dùng `SELECT *` cho stable API/report mapping.
- Không test migration/schema change với raw SQL paths.

## 8. Alternatives

- LINQ khi query rõ ràng và provider translation tốt.
- Views/stored procedures khi database ownership/governance yêu cầu.
- Dapper cho query-heavy components cần explicit SQL nhưng lightweight mapping.
- Dedicated read model cho reporting complexity cao.

## 9. Trade-offs

### Advantages

- Full control SQL/database features.
- Dễ hand-tune các query đặc biệt.
- Có thể rõ hơn LINQ quá phức tạp.

### Costs / Risks

- Giảm compile-time/refactoring safety.
- Tăng coupling với schema/vendor.
- Security và migration burden cao hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết parameterization và tuyệt đối không ghép user input vào SQL.

### Middle

Dùng `FromSql`/`ExecuteSql` đúng, cancellation, mapping và transactions.

### Senior

Chọn raw SQL dựa trên measured query needs, review plans và migration impact.

### Technical Lead / Architect

Quy định raw SQL ownership/testing/security review và quyết định khi ORM abstraction không còn mang lợi ích cho một workload cụ thể.

## 11. Key takeaway

- Raw SQL là escape hatch hợp lệ, không phải failure của architecture.
- Parameterization và transaction semantics vẫn bắt buộc.
- Chọn raw SQL vì query/problem thực tế, không vì assumption “ORM chậm”.

# 4. SQL Server Query Store: điều tra plan regression bằng lịch sử execution thay vì restart database hoặc đoán index

## 1. What is it?

Query Store lưu lịch sử query texts, execution plans và runtime statistics theo thời gian.

Mental model:

```text
Query executes
   |
   +-> plan A + runtime stats
   +-> plan B + runtime stats
   +-> time windows
           |
           v
   compare before/after regression
```

Nó cung cấp temporal evidence cho câu hỏi: “Query này từng nhanh, từ lúc nào chậm và plan nào thay đổi?”

## 2. Why does it exist?

Nếu chỉ xem execution plan hiện tại, bạn mất context lịch sử. Production regressions thường xuất hiện sau:

- statistics update;
- data distribution change;
- deployment;
- index change;
- parameter-sensitive plan;
- database compatibility/version change.

Restart database hoặc clear plan cache có thể tạm thay behavior nhưng xóa evidence và không giải quyết root cause.

## 3. How does it work?

Query Store aggregate runtime stats theo interval: duration, CPU, reads, executions. Một query có thể có nhiều plans.

Workflow:

```text
latency alert
  -> identify query
  -> compare historical runtime
  -> inspect plan changes
  -> inspect estimates/indexes/statistics
  -> remediate
  -> verify after change
```

Plan forcing có thể là emergency mitigation nhưng không nên thay thế root-cause analysis.

## 4. Practical implementation

Một investigation thực tế:

```sql
SELECT TOP (20)
    q.query_id,
    p.plan_id,
    rs.avg_duration,
    rs.avg_cpu_time,
    rs.avg_logical_io_reads
FROM sys.query_store_query q
JOIN sys.query_store_plan p
    ON p.query_id = q.query_id
JOIN sys.query_store_runtime_stats rs
    ON rs.plan_id = p.plan_id
ORDER BY rs.avg_duration DESC;
```

Sau đó mở actual plan và kiểm tra:

- estimated vs actual rows;
- seek/scan;
- joins;
- spills;
- key lookups;
- memory grant;
- missing/stale statistics.

## 5. Real production scenario

Sau một deployment không thay SQL, checkout API p95 tăng từ 180 ms lên 2.5 s. Query Store cho thấy query order-summary chuyển từ plan A sang plan B ngay sau statistics refresh. Plan B underestimate một skewed predicate và dùng nested loops dẫn tới hàng triệu reads.

Team có evidence để fix statistics/index/query shape thay vì rollback application vô nghĩa.

## 6. Failure scenario & troubleshooting

**Symptom** → query “lúc nhanh lúc chậm”, team chỉ thấy current plan.

**Evidence** → Query Store cho thấy multiple plans và runtime distribution thay đổi theo time window.

**Hypothesis** → plan regression hoặc workload/data distribution change.

**Diagnosis** → correlate plan IDs với deployment/statistics/index timeline; compare actual row estimates.

**Fix** → root-cause fix; plan forcing chỉ dùng có kiểm soát nếu cần giảm incident impact.

**Verification** → theo dõi runtime stats sau fix qua representative intervals, không chỉ chạy query một lần.

## 7. Common mistakes

- Clear plan cache trước khi thu evidence.
- Force plan vĩnh viễn rồi quên nó.
- Chỉ nhìn average duration, bỏ p95/p99 ở application layer.
- Thêm index theo suggestion mà không xem write cost.
- So sánh staging nhỏ với production skew lớn.
- Bỏ qua Query Store storage/retention configuration.

## 8. Alternatives

- Extended Events cho event-level diagnostics sâu hơn.
- Application Insights/OpenTelemetry để locate query từ request trace.
- Actual execution plans và DMVs cho current-state investigation.

Các công cụ bổ sung nhau, không thay thế hoàn toàn nhau.

## 9. Trade-offs

### Advantages

- Có historical evidence.
- So sánh plans và runtime theo thời gian.
- Hỗ trợ nhanh trong regression incidents.

### Costs / Risks

- Có storage/collection overhead.
- Data aggregation không thay full trace.
- Plan forcing tạo operational debt nếu không review lại.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu execution plan có thể thay đổi theo thời gian.

### Middle

Dùng Query Store để tìm slow queries/plans và đọc basic runtime metrics.

### Senior

Correlate plan changes với statistics, data skew, deployment và I/O evidence.

### Technical Lead / Architect

Định nghĩa database observability, retention và emergency-plan-forcing procedure có owner/expiry rõ ràng.

## 11. Key takeaway

- Performance regression cần lịch sử, không chỉ current plan.
- Query Store giúp biến “DB tự nhiên chậm” thành hypothesis có evidence.
- Plan forcing là mitigation; root cause vẫn cần được sửa.

# 5. Azure Cosmos DB RU throttling: hiểu 429, partition cost và retry để phân biệt thiếu throughput với data-model problem

## 1. What is it?

Cosmos DB tính request cost bằng Request Units (RU). Khi workload tiêu thụ vượt provisioned/available throughput ở một partition hoặc container, service có thể trả HTTP `429 Too Many Requests` kèm thời gian retry.

Mental model:

```text
request
  |
  v
logical partition -> physical partition capacity
  |
RU consumed
  |
capacity exceeded
  -> 429 + retry-after
```

429 trong Cosmos không tự động nghĩa service “down”; thường là capacity control signal.

## 2. Why does it exist?

Distributed storage cần bảo vệ tài nguyên và cung cấp predictable throughput. RU abstraction gom CPU, I/O và memory cost của operations thành một unit.

Một point read theo partition key + id rẻ hơn cross-partition query scan nhiều dữ liệu. Vì vậy data model và query pattern quyết định RU economics.

## 3. How does it work?

SDK thường retry 429 theo server-provided delay. Nhưng retry không tạo thêm capacity. Nếu workload liên tục vượt budget, retries chỉ tăng latency.

Hot partition đặc biệt nguy hiểm: tổng RU toàn container có thể còn nhưng một partition key nhận phần lớn traffic.

```text
tenant-A: 80% traffic -> hot
others:   20%
```

Scale throughput không luôn chữa key distribution xấu.

## 4. Practical implementation

Ở application layer, log/measure RU charge:

```csharp
ItemResponse<Order> response = await container.ReadItemAsync<Order>(
    id,
    new PartitionKey(customerId),
    cancellationToken: ct);

_logger.LogInformation(
    "Cosmos read RU={RequestCharge}",
    response.RequestCharge);
```

Query luôn ưu tiên partition key khi business access pattern cho phép.

Monitoring cần ít nhất:

- normalized RU consumption;
- throttled requests;
- latency;
- partition distribution;
- request charge theo operation/query.

## 5. Real production scenario

Một SaaS dùng `TenantId` làm partition key. Phần lớn tenants nhỏ nhưng một enterprise tenant chiếm 50% traffic. Khi batch import chạy, tenant đó tạo hotspot, API đọc/ghi cùng partition bắt đầu nhận 429 dù overall container RU nhìn vẫn chưa quá cao.

Root cause là workload concentration, không chỉ total throughput.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 tăng, SDK retries nhiều, logs có 429.

**Evidence** → throttling tập trung ở một partition range/key; RU charge/query cao.

**Hypothesis** → hot partition hoặc query access pattern quá đắt.

**Diagnosis** → inspect partition-key distribution, request charge, cross-partition queries và traffic bursts.

**Fix** → tùy root cause: query redesign, better partition strategy, autoscale/provision throughput, queue/batch smoothing, caching phù hợp.

**Verification** → replay representative load và xác nhận 429 rate + RU per operation giảm.

## 7. Common mistakes

- Retry 429 vô hạn.
- Chỉ tăng RU mà không xem partition distribution.
- Chọn partition key theo field “có vẻ unique” thay vì access/growth pattern.
- Chạy cross-partition query thường xuyên ở hot API.
- Bỏ qua request charge telemetry.
- Dùng Cosmos cho workload relational/join-heavy chỉ vì cần scale.

## 8. Alternatives

- Azure SQL/PostgreSQL khi relational constraints/joins là trọng tâm.
- MongoDB-compatible/document database khác khi operational model phù hợp hơn.
- Cache/read model cho hot reads nhưng phải giải quyết freshness/invalidation.

## 9. Trade-offs

### Advantages

- Horizontal distribution và predictable throughput model.
- Strong tooling cho globally distributed document workloads.

### Costs / Risks

- Data-model errors trở thành cost/throttling problems.
- RU economics cần được đo liên tục.
- Repartition/migration sau này có thể khó.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RU là cost của operation và 429 là throttling signal.

### Middle

Biết truyền partition key, đọc request charge và cấu hình retry phù hợp.

### Senior

Phân biệt capacity shortage, hot partition và expensive query bằng telemetry.

### Technical Lead / Architect

Chọn partition key dựa trên cardinality, growth, access patterns và migration risk; quyết định khi Cosmos thực sự phù hợp.

## 11. Key takeaway

- 429 thường là symptom của throughput/access distribution, không đơn giản là service outage.
- Partition key là architectural decision, không phải mapping detail.
- Retry chỉ hấp thụ burst; nó không sửa workload liên tục vượt capacity.

# 6. Domain Events vs Integration Events: tách thay đổi bên trong Aggregate khỏi contract phát ra ngoài bounded context

## 1. What is it?

Domain Event mô tả một business fact có ý nghĩa **bên trong domain/bounded context**. Integration Event là contract dùng để thông báo cho hệ thống/bounded context khác.

Mental model:

```text
Aggregate
  |
Domain Event
  |
internal handlers / application boundary
  |
translate
  v
Integration Event
  |
Message Broker
  |
Other bounded context
```

Không phải mọi Domain Event đều cần publish ra broker.

## 2. Why does it exist?

Nếu publish domain object/event nội bộ trực tiếp ra ngoài, external consumers bị coupling với model đang tiến hóa nhanh bên trong service. Một rename hoặc invariant change trong domain có thể trở thành breaking distributed contract.

Tách hai loại event giúp giữ encapsulation và version integration contract độc lập.

## 3. How does it work?

Aggregate phát fact nội bộ:

```csharp
public sealed record OrderConfirmedDomainEvent(
    Guid OrderId,
    DateTimeOffset ConfirmedAt);
```

Application handler có thể map sang integration event:

```csharp
public sealed record OrderConfirmedV1(
    Guid OrderId,
    string CustomerId,
    decimal Total,
    DateTimeOffset OccurredAt);
```

Integration event cần ổn định, versionable và chỉ chứa dữ liệu consumers thực sự cần.

## 4. Practical implementation

Flow đáng tin cậy thường là:

```text
transaction:
  update Aggregate
  persist Domain state
  write Outbox integration event
commit

background publisher:
  Outbox -> Service Bus
```

Điều này tránh lỗi “database commit thành công nhưng publish event thất bại”.

Domain event handler nội bộ cũng cần cẩn thận với transaction boundary. Side effect external không nên chạy mơ hồ giữa `SaveChanges` nếu không có consistency strategy.

## 5. Real production scenario

Order service có `OrderConfirmedDomainEvent`. Ban đầu team publish object đó nguyên xi lên Service Bus. Sau vài tháng domain model đổi `Price` thành `Money` value object và thêm tax semantics. Ba consumers ngoài team bị break.

Tách `OrderConfirmedV1` cho external contract cho phép domain thay đổi mà vẫn duy trì event schema cũ trong migration period.

## 6. Failure scenario & troubleshooting

**Symptom** → một refactor nội bộ gây failures ở nhiều consumers sau deployment.

**Evidence** → message schema mirror trực tiếp domain class; consumers deserialize shared package type.

**Hypothesis** → bounded-context boundary bị xuyên qua bằng internal model.

**Diagnosis** → map producer domain types tới external contracts và inventory consumer dependencies.

**Fix** → introduce explicit integration contracts/versioning + translation layer + outbox nếu cần reliability.

**Verification** → contract tests với active consumers và replay old/new event versions.

## 7. Common mistakes

- Gọi mọi in-process notification là “integration event”.
- Publish EF entities trực tiếp lên broker.
- Dùng shared domain assembly giữa services.
- Assume broker publish nằm cùng transaction với database.
- Event schema chứa quá nhiều internal fields “phòng khi cần”.
- Không version/deprecate external event contract.

## 8. Alternatives

- Synchronous REST nếu consumer cần immediate request/response và consistency semantics khác.
- CDC/outbox projection khi muốn phát change từ persisted state.
- Không dùng Domain Events nếu use case đơn giản và direct application flow rõ hơn.

## 9. Trade-offs

### Advantages

- Giảm coupling giữa bounded contexts.
- Cho domain model evolve độc lập hơn.
- Integration contract có lifecycle/versioning rõ ràng.

### Costs / Risks

- Thêm mapping và event governance.
- Eventual consistency + duplicate delivery cần xử lý.
- Outbox/publisher tạo operational components mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event là một fact đã xảy ra, không phải command ngụy trang.

### Middle

Biết phân biệt in-process domain notification và external integration contract.

### Senior

Thiết kế transaction/outbox/idempotency và schema evolution.

### Technical Lead / Architect

Xác định bounded-context ownership, contract governance và khi event-driven integration thực sự đáng complexity hơn synchronous call.

## 11. Key takeaway

- Domain Event bảo vệ domain semantics; Integration Event bảo vệ system boundary.
- Không publish internal domain model trực tiếp như distributed contract.
- Reliability của event publication phải gắn với transaction strategy rõ ràng.

# 7. Azure SQL transient failures: connection resiliency, retry và transaction semantics trong môi trường cloud

## 1. What is it?

Transient failure là lỗi tạm thời có khả năng thành công nếu thử lại sau khoảng thời gian hợp lý: brief failover, throttling, network interruption, connection reset.

Mental model:

```text
request
  -> DB operation
      -> transient error
      -> backoff
      -> retry
      -> success / terminal failure
```

Không phải mọi SQL error đều transient và không phải mọi operation đều retry-safe.

## 2. Why does it exist?

Cloud databases là distributed managed services. Failover, maintenance và network events là expected operational behavior. Application cần chịu được short interruptions thay vì coi mọi connection reset là catastrophic outage.

Nhưng retry sai có thể nhân load hoặc lặp business side effect.

## 3. How does it work?

EF Core SQL Server provider hỗ trợ execution strategy:

```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString, sql =>
        sql.EnableRetryOnFailure()));
```

Provider nhận diện một số transient errors và retry với backoff.

Vấn đề phức tạp xuất hiện với explicit transactions vì execution strategy phải replay toàn transaction delegate, không chỉ statement cuối.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    order.MarkPaid();
    await db.SaveChangesAsync(ct);

    // chỉ DB work retry-safe trong transaction này

    await tx.CommitAsync(ct);
});
```

Không đặt external payment API call bên trong retryable delegate nếu retry có thể charge hai lần.

Nếu business operation kết hợp DB + remote side effect, dùng idempotency/outbox/workflow phù hợp.

## 5. Real production scenario

Azure SQL failover gây vài seconds connection errors. API có retry policy ngoài HTTP layer và EF cũng retry bên trong. Mỗi incoming request tạo nested retries, làm request kéo dài hàng chục giây và tạo connection storm khi database vừa phục hồi.

Root cause là retry hierarchy không được thiết kế như một budget thống nhất.

## 6. Failure scenario & troubleshooting

**Symptom** → incident ngắn ở DB biến thành latency spike dài, log có nhiều repeated operations.

**Evidence** → EF execution strategy + Polly/API gateway retries cùng hoạt động; database recover nhưng app tiếp tục retry backlog.

**Hypothesis** → retry amplification hoặc non-idempotent retry.

**Diagnosis** → trace retry count/layer, SQL error codes, transaction boundaries và downstream side effects.

**Fix** → một retry budget có backoff/jitter, giới hạn attempts, tách non-idempotent side effects khỏi replayable transaction.

**Verification** → fault injection với transient DB disconnect và theo dõi total attempts/latency/correctness.

## 7. Common mistakes

- Retry mọi `SqlException`.
- Nested retries ở nhiều layers không có total deadline.
- Retry transaction có external side effect.
- Retry ngay lập tức không backoff/jitter.
- Dùng retry để che connection pool exhaustion hoặc slow query.
- Không log attempt count/final reason.

## 8. Alternatives

- Queue-based async workflow khi operation chịu được eventual processing.
- Circuit breaker/degradation khi DB lỗi kéo dài; retry không phù hợp persistent failure.
- Fail-fast cho non-transient errors như constraint violations.

## 9. Trade-offs

### Advantages

- Hấp thụ brief platform/network disruptions.
- Tăng availability với transient faults thực sự.

### Costs / Risks

- Tăng tail latency.
- Có thể nhân load khi dependency đang yếu.
- Transaction replay cần correctness/idempotency reasoning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transient khác permanent error.

### Middle

Cấu hình EF connection resiliency và cancellation/timeouts.

### Senior

Thiết kế retry-safe transaction và tránh nested retry amplification.

### Technical Lead / Architect

Định nghĩa timeout/retry budget xuyên gateway, app, database và external services; quyết định operation nào chuyển sang durable async workflow.

## 11. Key takeaway

- Retry là reliability tool có điều kiện, không phải default cho mọi exception.
- Retry transaction phải đảm bảo side effects có thể replay an toàn.
- Thiết kế retry theo end-to-end budget, không theo từng library riêng lẻ.

# 8. IIS Application Pool identity & filesystem permissions: startup 500.30/500.31 thường là hosting boundary, không phải business bug

## 1. What is it?

IIS Application Pool chạy worker process dưới một Windows identity. Với ASP.NET Core hosting, IIS/ASP.NET Core Module khởi động hoặc reverse-proxy tới application process.

Mental model:

```text
Client
  -> IIS site/binding
  -> Application Pool identity
  -> ASP.NET Core Module
  -> dotnet / app process
  -> files, certs, network, DB
```

Identity quyết định process có quyền đọc deployment folder, ghi logs/temp files, truy cập network resources hoặc private certificate keys hay không.

## 2. Why does it exist?

Windows dùng ACL để enforce least privilege. Production server không nên chạy mọi website bằng Administrator. Nhưng quyền quá thiếu hoặc deployment ACL sai có thể khiến app không start hoặc chỉ fail khi chạm một resource cụ thể.

## 3. How does it work?

Default identity thường giống:

```text
IIS AppPool\MyAppPool
```

ACL có thể grant read/execute cho application files và write chỉ cho thư mục cần thiết.

Ví dụ kiểm tra:

```powershell
icacls D:\Sites\MyApp
```

Grant có chọn lọc:

```powershell
icacls D:\Sites\MyApp /grant "IIS AppPool\MyAppPool:(OI)(CI)RX"
```

Không nên grant `FullControl` toàn folder chỉ để nhanh hết lỗi.

## 4. Practical implementation

Production deployment checklist:

```text
1. App Pool runtime/hosting model đúng
2. deployment files tồn tại
3. identity có Read/Execute
4. writable folders tách riêng và có Write
5. certificate private key permission đúng
6. environment variables/config/secrets đúng
7. stdout/event logs có thể truy cập khi startup fail
```

Đối với database dùng Windows Integrated Security, identity/network account semantics cần được thiết kế rõ; local success không đảm bảo remote SQL access.

## 5. Real production scenario

Pipeline deploy version mới vào thư mục mới rồi switch IIS site. File copy kế thừa ACL khác thư mục cũ. App Pool identity không có quyền execute/read một số files nên site trả 500.30 sau release, dù build artifact hoàn toàn đúng.

Rollback “fix” vì folder cũ có ACL đúng, khiến team ban đầu tưởng code regression.

## 6. Failure scenario & troubleshooting

**Symptom** → 500.30/500.31, process không start, hoặc `Access denied` khi ghi file/read certificate.

**Evidence** → Windows Event Viewer, ANCM stdout logs, Process Monitor hoặc ACL inspection cho thấy denied access.

**Hypothesis** → hosting/runtime/permission boundary sai.

**Diagnosis** → chạy app trực tiếp bằng command line để tách IIS issue khỏi app issue; kiểm tra installed hosting bundle, identity, ACL, environment variables.

**Fix** → grant minimum required permissions hoặc sửa deployment/hosting configuration.

**Verification** → recycle App Pool, hit health endpoint và xác nhận worker identity truy cập đúng resources.

## 7. Common mistakes

- Grant `Everyone: FullControl`.
- Chạy App Pool bằng Administrator để hết lỗi.
- Chỉ xem application logs khi process chưa kịp start.
- Quên Hosting Bundle/runtime version.
- Ghi upload/log trực tiếp vào deployment directory mà không có ownership rõ.
- Không preserve ACL trong blue-green/folder-swap deployment.

## 8. Alternatives

- Azure App Service giảm nhiều Windows/IIS administration burden nhưng vẫn có identity/config/filesystem semantics.
- Windows Service cho non-HTTP worker workloads.
- Linux/systemd/container hosting khi platform/team conventions phù hợp.

## 9. Trade-offs

### Advantages

- IIS mature cho Windows enterprise hosting.
- ACL và App Pool isolation rõ ràng.

### Costs / Risks

- Runtime/ANCM/ACL/certificate layers tạo nhiều failure boundaries.
- Server drift nếu cấu hình thủ công.
- Operational knowledge cần được automation/documentation hóa.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết site, App Pool, process và filesystem permission là các lớp khác nhau.

### Middle

Troubleshoot startup bằng Event Viewer/stdout/ACL thay vì chỉ sửa code.

### Senior

Thiết kế least privilege, certificate permissions, deployment-folder ownership và repeatable release.

### Technical Lead / Architect

Quyết định khi IIS vẫn phù hợp, khi nên chuyển managed/container platform và cách giảm server drift bằng infrastructure/deployment automation.

## 11. Key takeaway

- Startup failure sau deploy không mặc định là code bug.
- App Pool identity là security boundary thật, cần minimum ACL rõ ràng.
- Troubleshoot từ hosting/process evidence trước khi thay đổi business code.

# 9. `dotnet-counters` trong incident triage: khoanh vùng CPU, GC, exceptions, ThreadPool và allocation trước khi chụp dump

## 1. What is it?

`dotnet-counters` là diagnostic tool đọc runtime/EventCounter/Meter metrics từ một .NET process đang chạy.

Mental model:

```text
production symptom
   |
   v
cheap live counters
   |
   +-> CPU?
   +-> GC/allocation?
   +-> exceptions?
   +-> ThreadPool?
   |
   v
choose deeper tool: trace / dump / profiler
```

Nó phù hợp cho **triage**: xác định hệ thống đang nghẽn theo hướng nào trước khi thu artifact nặng hơn.

## 2. Why does it exist?

Khi API chậm, lấy memory dump ngay có thể tốn thời gian, dung lượng và gây overhead. Nhiều incident chỉ cần vài runtime signals để phân biệt:

- CPU saturation;
- allocation/GC pressure;
- ThreadPool starvation;
- exception storm;
- connection/request behavior.

Điều tra tốt bắt đầu bằng cheapest useful evidence.

## 3. How does it work?

Ví dụ:

```bash
dotnet-counters monitor --process-id 1234 System.Runtime
```

Các signals đáng chú ý:

```text
cpu-usage
working-set
gc-heap-size
alloc-rate
gen-0/1/2-gc-count
exception-count
threadpool-thread-count
threadpool-queue-length
```

Một metric riêng lẻ hiếm khi đủ. Ví dụ heap lớn không đồng nghĩa leak; cần xem allocation rate, GC behavior và heap trend.

## 4. Practical implementation

Incident workflow:

```text
1. Xác nhận symptom: p99, error rate, CPU/memory
2. Chạy counters 2–5 phút dưới tải thật
3. Form hypothesis
4. Nếu CPU cao -> trace/profiler
5. Nếu heap tăng -> gcdump/dump
6. Nếu queue tăng -> inspect blocking/ThreadPool
7. Verify sau remediation
```

Ví dụ queue tăng trong khi CPU thấp có thể gợi ý blocking I/O/sync-over-async. Allocation rate cực cao + frequent Gen 2 collections có thể gợi ý allocation-heavy hot path.

## 5. Real production scenario

Sau release, API p95 tăng gấp đôi. Azure Monitor chỉ cho thấy CPU khoảng 40%. `dotnet-counters` phát hiện exception rate tăng hàng nghìn/giây dù exceptions bị catch và fallback. Việc tạo stack traces + logging làm CPU/alloc tăng và latency xấu.

Nếu chỉ nhìn HTTP 500 rate, incident gần như “không có lỗi”. Runtime counters chỉ ra hidden exception storm.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng nhưng không rõ leak hay traffic effect.

**Evidence** → working set tăng; cần xem GC heap + allocation rate + Gen2 count.

**Hypothesis A** → high allocation nhưng objects collectible.

**Hypothesis B** → retained objects tạo true leak.

**Diagnosis** → counters để chọn hướng; nếu heap sau full GC vẫn tăng, thu gcdump/dump để inspect retention paths.

**Fix** → dựa trên root cause, không “tăng RAM” trước khi biết retained vs transient memory.

**Verification** → cùng workload, counters trend ổn định sau fix.

## 7. Common mistakes

- Dùng một snapshot thay vì trend.
- Kết luận leak chỉ vì working set tăng.
- Chụp dump đầu tiên mà chưa biết cần tìm gì.
- Không correlate counters với traffic/deployment timeline.
- Tăng ThreadPool threads để che blocking.
- Chạy diagnostic collection quá nặng trong peak incident mà không đánh giá overhead.

## 8. Alternatives

- `dotnet-trace` cho CPU/events timeline sâu hơn.
- `dotnet-gcdump` cho managed heap snapshot tương đối nhẹ.
- Full memory dump cho retention/native investigation sâu.
- Application Insights/OpenTelemetry cho request/dependency-level context.

## 9. Trade-offs

### Advantages

- Overhead thấp hơn profiler/dump trong nhiều trường hợp.
- Nhanh để localize class of problem.
- Có thể dùng live trong incident.

### Costs / Risks

- Counters không cho root cause stack/object graph đầy đủ.
- Cần hiểu metrics để tránh kết luận sai.
- Production access/permissions phải được quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết CPU, memory, allocation, GC và ThreadPool là các signal khác nhau.

### Middle

Chạy counters và đọc trend cơ bản.

### Senior

Dùng counters để chọn đúng next diagnostic artifact và kiểm chứng hypothesis.

### Technical Lead / Architect

Chuẩn hóa incident runbook, diagnostic access, baseline metrics và evidence collection trước khi restart process làm mất state.

## 11. Key takeaway

- Triage nên bắt đầu bằng evidence rẻ nhất đủ để thu hẹp hypothesis.
- Working set cao không tự động là memory leak.
- Counters tốt để chọn bước tiếp theo; chúng không thay profiler/dump khi cần root cause sâu.

# 10. Mutation Testing: kiểm tra test suite có thật sự phát hiện bug hay chỉ chạy qua code

## 1. What is it?

Mutation Testing cố tình thay đổi nhỏ production code — gọi là mutant — rồi chạy test suite. Nếu tests fail, mutant bị “killed”. Nếu tests vẫn pass, test suite có thể không bảo vệ behavior đó.

Mental model:

```text
original:
if (balance >= amount)

mutant:
if (balance > amount)

run tests
  |
  +-> fail = mutant killed
  +-> pass = surviving mutant -> test gap / equivalent mutant
```

Nó đo **test effectiveness**, khác code coverage vốn chủ yếu đo code đã được execute.

## 2. Why does it exist?

100% line coverage vẫn có thể đi cùng assertions yếu:

```csharp
var result = calculator.Add(2, 2);
Assert.NotNull(result);
```

Line được cover nhưng test không bảo vệ correctness `4`.

Mutation Testing đặt câu hỏi mạnh hơn: nếu logic sai nhẹ, tests có nhận ra không?

## 3. How does it work?

Tool tạo variants như:

- `>` thành `>=`;
- `true` thành `false`;
- arithmetic operator thay đổi;
- bỏ method call;
- invert condition.

Sau đó chạy tests liên quan và tính mutation score.

Nhưng score không phải mục tiêu tuyệt đối. Một số mutants tương đương về behavior hoặc nằm ở code ít rủi ro.

## 4. Practical implementation

Trong .NET có thể dùng mutation-testing tooling như Stryker.NET cho selected projects.

Approach tốt:

```text
1. Chọn domain-critical module nhỏ
2. Chạy mutation baseline
3. Review surviving mutants
4. Bổ sung assertion/test chỉ khi mutant đại diện bug meaningful
5. Không ép 100% score toàn solution
```

Ví dụ pricing rule:

```csharp
public decimal ApplyDiscount(decimal price, decimal rate)
    => price * (1 - rate);
```

Tests nên fail nếu `-` bị mutate thành `+` hoặc boundary validation bị đảo.

## 5. Real production scenario

Checkout service có nhiều unit tests và 90% coverage. Một production bug xảy ra vì boundary `>= freeShippingThreshold` bị code thành `>`. Existing tests chỉ dùng values 1,000 và 2,000, không có exact threshold.

Mutation Testing tạo mutant ở comparison và nó sống sót, chỉ ra test suite thiếu boundary behavior.

## 6. Failure scenario & troubleshooting

**Symptom** → mutation run quá lâu và tạo hàng trăm survivors không actionable.

**Evidence** → chạy toàn monorepo, nhiều generated/DTO/logging code, integration tests chậm.

**Hypothesis** → scope mutation quá rộng và không risk-based.

**Diagnosis** → classify survivors theo business criticality/equivalent mutants/test design.

**Fix** → giới hạn domain modules, exclude generated/trivial code, optimize test selection và incremental CI usage.

**Verification** → mutation runtime hợp lý và survivors chủ yếu là findings có engineering value.

## 7. Common mistakes

- Dùng mutation score như KPI cá nhân/team.
- Cố đạt 100% score.
- Chạy trên DTO/getter/generated code không có risk.
- Viết tests vô nghĩa chỉ để kill mutant.
- Thay thế integration/E2E testing bằng mutation testing.
- Không xem equivalent mutants.

## 8. Alternatives

- Code coverage: rẻ hơn, tốt để tìm unexecuted code nhưng yếu hơn về assertion quality.
- Property-based testing: mạnh cho invariant/input-space exploration.
- Integration tests: bảo vệ component interactions thật.
- Static analysis: bắt defect classes mà tests không nhắm tới.

## 9. Trade-offs

### Advantages

- Đánh giá chất lượng assertions mạnh hơn coverage đơn thuần.
- Tìm missing boundary/error tests.
- Hữu ích cho business-critical pure logic.

### Costs / Risks

- Tốn compute/time.
- Có equivalent/noisy mutants.
- Có thể bị gaming nếu biến thành KPI.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu coverage không đồng nghĩa correctness.

### Middle

Viết tests theo behavior/boundaries và đọc surviving mutants.

### Senior

Chọn mutation targets theo risk và phân biệt meaningful survivor với noise.

### Technical Lead / Architect

Quyết định nơi mutation testing đáng CI cost, tránh biến quality engineering thành score chasing và kết hợp nó với unit/integration/contract/E2E strategy.

## 11. Key takeaway

- Mutation Testing hỏi tests có phát hiện logic sai hay không, không chỉ code có được chạy hay không.
- Dùng risk-based scope, không chạy như vanity metric toàn codebase.
- Một surviving mutant hữu ích khi nó đại diện bug thực tế mà tests hiện tại bỏ sót.
