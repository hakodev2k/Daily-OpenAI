# 1. C# `Channel<T>` và backpressure: thiết kế producer/consumer không để memory tăng vô hạn khi consumer chậm hơn producer

## 1. What is it?

`Channel<T>` là primitive trong .NET cho asynchronous producer/consumer communication trong cùng process. Một hoặc nhiều producer ghi item vào channel, một hoặc nhiều consumer đọc item và xử lý.

Mental model:

```text
Producer(s)
    |
    v
 Channel<T>
    |
    v
Consumer(s)
```

Điểm quan trọng nhất không phải queue syntax, mà là **backpressure**: khi consumer chậm hơn producer, hệ thống phải quyết định làm gì thay vì để buffer tăng mãi.

`Channel<T>` có hai family chính:

- unbounded channel;
- bounded channel.

Unbounded dễ dùng nhưng có thể biến traffic burst thành memory incident. Bounded channel buộc application thể hiện capacity policy.

## 2. Why does it exist?

Trước `Channel<T>`, code thường dùng:

- `ConcurrentQueue<T>` + polling;
- `BlockingCollection<T>`;
- custom queue + `SemaphoreSlim`;
- ad-hoc producer/consumer loops.

Những cách này có thể hoạt động nhưng dễ xuất hiện polling, blocking thread, race condition hoặc shutdown semantics không rõ.

`Channel<T>` cung cấp asynchronous reads/writes, multi-producer/multi-consumer support và bounded capacity policy phù hợp với server workload.

Engineering pressure thực sự là:

> Work arrives faster than it can be processed. What should the system do?

Nếu câu trả lời là “cứ giữ hết trong RAM”, hệ thống đang vay latency/memory để trì hoãn failure.

## 3. How does it work?

Bounded channel có capacity cố định:

```text
Producer rate: 1000 items/s
Consumer rate: 300 items/s
Capacity: 5000
```

Sau một thời gian queue đầy. Lúc đó behavior phụ thuộc `BoundedChannelFullMode`:

- `Wait`: producer chờ capacity;
- `DropNewest`;
- `DropOldest`;
- `DropWrite`.

`Wait` tạo backpressure rõ nhất vì producer bị chậm lại thay vì loss.

Ví dụ:

```csharp
var channel = Channel.CreateBounded<Job>(
    new BoundedChannelOptions(500)
    {
        FullMode = BoundedChannelFullMode.Wait,
        SingleWriter = false,
        SingleReader = false
    });
```

Producer gọi `WriteAsync`; nếu queue đầy, call sẽ asynchronously wait.

Consumer:

```csharp
await foreach (var job in channel.Reader.ReadAllAsync(ct))
{
    await ProcessAsync(job, ct);
}
```

## 4. Practical implementation

Một in-process work dispatcher:

```csharp
public sealed class WorkQueue
{
    private readonly Channel<Func<CancellationToken, Task>> _channel;

    public WorkQueue(int capacity)
    {
        _channel = Channel.CreateBounded<Func<CancellationToken, Task>>(
            new BoundedChannelOptions(capacity)
            {
                FullMode = BoundedChannelFullMode.Wait
            });
    }

    public ValueTask EnqueueAsync(
        Func<CancellationToken, Task> work,
        CancellationToken ct)
        => _channel.Writer.WriteAsync(work, ct);

    public IAsyncEnumerable<Func<CancellationToken, Task>> ReadAllAsync(
        CancellationToken ct)
        => _channel.Reader.ReadAllAsync(ct);
}
```

Worker:

```csharp
public sealed class QueueWorker : BackgroundService
{
    private readonly WorkQueue _queue;

    public QueueWorker(WorkQueue queue) => _queue = queue;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var work in _queue.ReadAllAsync(stoppingToken))
        {
            try
            {
                await work(stoppingToken);
            }
            catch (Exception ex)
            {
                // structured logging + retry policy if appropriate
            }
        }
    }
}
```

Quan trọng: queue này **không durable**. Process restart là mất queued work.

## 5. Real production scenario

Một ASP.NET Core API nhận webhook và enqueue việc parse/normalize nội bộ vào unbounded `Channel<T>`.

Traffic bình thường: 100 req/s.

Campaign bất ngờ: 5000 req/s.

Consumer chỉ xử lý 400 req/s. Queue tăng hàng trăm nghìn item, working set vượt vài GB, GC pressure tăng, latency toàn process xấu đi và cuối cùng OOM.

Root cause không phải `Channel<T>` chậm. Root cause là capacity policy không tồn tại.

Bounded channel + rejection/429 hoặc external durable queue là design tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng tuyến tính theo traffic, request vẫn accept nhưng xử lý ngày càng trễ.

**Evidence** → queue depth tăng liên tục; consumer throughput thấp hơn producer throughput; allocation/working set tăng.

**Hypothesis** → unbounded queue hoặc capacity quá lớn đang che downstream bottleneck.

**Diagnosis** → đo producer rate, consumer rate, queue depth, processing duration và time-in-queue.

**Fix** → bounded capacity, backpressure, tăng consumer concurrency nếu downstream chịu được, hoặc chuyển sang durable broker.

**Verification** → load test traffic lớn hơn steady-state capacity và xác nhận queue depth hội tụ thay vì tăng vô hạn.

## 7. Common mistakes

- Dùng unbounded channel mặc định cho workload có burst lớn.
- Tăng số consumer vô hạn rồi làm database/external API quá tải.
- Queue work trong RAM nhưng business lại yêu cầu durability.
- Không complete writer khi shutdown.
- Không đo queue wait time.
- Dùng channel như distributed message broker.

## 8. Alternatives

`ConcurrentQueue<T>` phù hợp cho simple synchronous coordination khi không cần async wait/backpressure.

Azure Service Bus, RabbitMQ hoặc Kafka phù hợp khi cần durability, cross-process communication, replay hoặc independent scaling.

Nếu workload nhỏ và không cần queue, gọi dependency trực tiếp có thể đơn giản hơn.

## 9. Trade-offs

### Advantages

- Async producer/consumer model rõ ràng.
- Bounded capacity hỗ trợ backpressure.
- Ít ceremony hơn custom synchronization.

### Costs / Risks

- In-process, không durable.
- Capacity tuning cần measurement.
- Concurrency quá cao dễ đẩy overload sang downstream.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue chỉ chuyển thời điểm xử lý; queue không tự làm hệ thống nhanh hơn.

### Middle

Biết dùng bounded channel, cancellation và consumer loop đúng lifecycle.

### Senior

Đo throughput, queue depth, wait time; nhận biết khi bottleneck cần admission control thay vì thêm workers.

### Technical Lead / Architect

Quyết định khi nào in-process queue đủ và khi nào workload cần durable messaging; đặt explicit capacity/failure policy cho traffic burst.

## 11. Key takeaway

- Backpressure là capacity contract, không phải implementation detail.
- Unbounded queue có thể đổi overload thành OOM.
- `Channel<T>` phù hợp in-process coordination; durability cần message broker.

# 2. ASP.NET Core request-body streaming: xử lý file/payload lớn mà không vô tình buffer toàn bộ vào memory

## 1. What is it?

Request-body streaming là xử lý dữ liệu HTTP khi bytes đến thay vì materialize toàn bộ request body vào `byte[]`, `string` hoặc object graph lớn trước khi làm việc.

Mental model:

```text
Client
  -> network chunks
  -> request body stream
  -> process/write incrementally
```

Streaming đặc biệt quan trọng với upload lớn, file processing hoặc proxying.

## 2. Why does it exist?

Một file 1 GB không nên yêu cầu 1 GB managed memory trên server chỉ để nhận upload.

Nếu 20 users upload đồng thời và server buffer mỗi file hoàn toàn:

```text
20 x 1 GB = 20 GB transient memory
```

Trước cả khi business logic chạy, application đã có nguy cơ GC pressure/OOM.

Streaming giữ memory footprint gần với buffer size thay vì payload size.

## 3. How does it work?

ASP.NET Core expose `HttpRequest.Body` là `Stream`.

Data flow:

```text
socket
 -> Kestrel
 -> Pipe/Stream
 -> application reads chunks
 -> Blob/File/Hasher/Parser
```

Model binding `IFormFile` có buffering semantics tùy kích thước/configuration. Vì vậy “tôi dùng `IFormFile` nên chắc chắn streaming” là hiểu sai.

Nếu use case thật sự là large-file upload, thường nên kiểm soát flow rõ ràng.

## 4. Practical implementation

Ví dụ stream trực tiếp vào Azure Blob Storage:

```csharp
app.MapPost("/uploads/{name}", async (
    string name,
    HttpRequest request,
    BlobContainerClient container,
    CancellationToken ct) =>
{
    var blob = container.GetBlobClient(name);

    await blob.UploadAsync(
        request.Body,
        overwrite: true,
        cancellationToken: ct);

    return Results.Accepted();
});
```

Với processing incremental:

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    int read;
    while ((read = await request.Body.ReadAsync(buffer, ct)) > 0)
    {
        await ProcessChunkAsync(buffer.AsMemory(0, read), ct);
    }
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);
}
```

Phải enforce request-size limit, authorization và content validation.

## 5. Real production scenario

CMS cho editor upload video 700 MB.

Implementation ban đầu:

```csharp
using var ms = new MemoryStream();
await request.Body.CopyToAsync(ms);
var bytes = ms.ToArray();
```

10 concurrent uploads làm memory tăng nhiều GB và LOH churn. API latency của endpoints không liên quan cũng xấu đi vì cùng process chịu GC pressure.

Streaming trực tiếp vào Blob Storage loại phần lớn allocation này.

## 6. Failure scenario & troubleshooting

**Symptom** → memory spike đúng lúc upload traffic tăng; Gen 2/LOH activity cao; đôi khi `OutOfMemoryException`.

**Evidence** → profiler thấy `MemoryStream`, large `byte[]`, `ToArray()` dominating allocations.

**Hypothesis** → request-body buffering/materialization.

**Diagnosis** → trace upload path, payload size, concurrency và memory allocation rate.

**Fix** → streaming, direct-to-storage upload, bounded buffer, request limits.

**Verification** → load test large concurrent uploads và so working set/allocation trước-sau.

## 7. Common mistakes

- Gọi `ReadToEndAsync()` với payload không giới hạn.
- Convert stream → `MemoryStream` → `byte[]` nhiều lần.
- Tin `Content-Type` từ client để xác định file an toàn.
- Stream nhưng không enforce max size.
- Giữ HTTP request mở cho processing rất dài thay vì upload rồi queue xử lý.

## 8. Alternatives

Direct-to-Blob upload bằng SAS thường tốt hơn khi client có thể upload trực tiếp.

Multipart form upload vẫn phù hợp file nhỏ và UX đơn giản.

Nếu payload bắt buộc parse toàn bộ như small JSON, buffering bình thường là hợp lý.

## 9. Trade-offs

### Advantages

- Memory gần như độc lập với payload size.
- Phù hợp concurrent large uploads.
- Giảm LOH/GC pressure.

### Costs / Risks

- Error handling phức tạp hơn khi processing incremental.
- Không thể rewind stream tùy ý nếu không enable buffering.
- Partial upload/cleanup cần lifecycle policy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu stream là đọc bytes dần, không cần giữ toàn bộ payload.

### Middle

Implement streaming + cancellation + size validation.

### Senior

Đánh giá buffering hidden trong framework, memory profile và partial-failure semantics.

### Technical Lead / Architect

Quyết định upload flow: proxy qua API, direct-to-storage hay async processing pipeline; cân bằng security, throughput và operational cost.

## 11. Key takeaway

- Payload lớn nên được stream, không materialize mặc định.
- Streaming phải đi cùng size/security controls.
- Upload và processing thường nên tách lifecycle nếu work dài.

# 3. EF Core `ExecuteUpdate` / `ExecuteDelete`: bulk mutation hiệu quả nhưng không đi qua Change Tracker như `SaveChanges`

## 1. What is it?

`ExecuteUpdate` và `ExecuteDelete` cho phép EF Core gửi `UPDATE`/`DELETE` trực tiếp xuống database từ LINQ query mà không load entities vào memory và không track chúng trước.

Ví dụ:

```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Expired)
    .ExecuteUpdateAsync(
        setters => setters.SetProperty(
            x => x.Status,
            OrderStatus.Archived),
        ct);
```

Database xử lý set-based operation trực tiếp.

## 2. Why does it exist?

Cách truyền thống:

```text
SELECT 100,000 rows
 -> materialize entities
 -> track entities
 -> modify properties
 -> SaveChanges
 -> many UPDATE commands/batches
```

Nếu business logic chỉ cần “update tất cả rows match predicate”, load 100,000 objects là overhead không cần thiết.

Set-based SQL giải quyết việc này tốt hơn.

## 3. How does it work?

`ExecuteUpdate` translate expression thành SQL tương tự:

```sql
UPDATE Orders
SET Status = @p0
WHERE Status = @p1;
```

Không có entity materialization.

Không có Change Tracker synchronization tự động.

Điều này có consequence rất quan trọng: nếu cùng `DbContext` đã track entity bị update bởi `ExecuteUpdate`, in-memory entity có thể chứa state cũ.

## 4. Practical implementation

Archiving expired rows:

```csharp
var affected = await db.Orders
    .Where(x => x.ExpiresAt < DateTimeOffset.UtcNow)
    .Where(x => x.Status == OrderStatus.Pending)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired)
        .SetProperty(x => x.UpdatedAt, DateTimeOffset.UtcNow), ct);
```

Delete cleanup:

```csharp
await db.AuditEvents
    .Where(x => x.CreatedAt < cutoff)
    .ExecuteDeleteAsync(ct);
```

Nếu operation phải cùng transaction với nhiều steps:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

await ...ExecuteUpdateAsync(..., ct);
await ...ExecuteDeleteAsync(ct);

await tx.CommitAsync(ct);
```

## 5. Real production scenario

Nightly cleanup cần mark 2 triệu notification records là expired.

Version cũ load entities theo batches 10k rồi modify + `SaveChanges`. Job kéo dài hàng chục phút, allocation cao và Change Tracker lớn.

Set-based `ExecuteUpdate` giảm network round trips và client-side work đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → sau `ExecuteUpdate`, API vẫn serialize giá trị cũ từ entity đang tracked.

**Evidence** → SQL update thành công; database row đúng; `DbContext` entry vẫn giữ old value.

**Hypothesis** → tracked state stale vì direct bulk mutation bypass Change Tracker.

**Diagnosis** → inspect `ChangeTracker.Entries()` và query sequence.

**Fix** → tránh mix tracked entities với set-based mutation trong cùng unit of work; reload/clear tracker khi cần.

**Verification** → integration test database state và in-memory state sau operation.

## 7. Common mistakes

- Giả định `ExecuteUpdate` trigger domain method/events trên entities.
- Mix tracked entities rồi gọi `SaveChanges` sau đó ghi đè bulk update.
- Bulk delete dữ liệu mà business invariant/audit yêu cầu per-entity processing.
- Không dùng transaction khi nhiều bulk statements phải atomic cùng nhau.
- Dùng bulk operation trước khi kiểm tra predicate thật kỹ.

## 8. Alternatives

Normal tracked update phù hợp khi cần domain behavior, validation, concurrency token semantics hoặc per-entity logic.

Raw SQL/stored procedure hữu ích cho DB-specific operation phức tạp.

Bulk-extension libraries có thể hỗ trợ use case khác nhưng thêm dependency.

## 9. Trade-offs

### Advantages

- Ít memory/allocation.
- Ít round trips.
- Tận dụng set-based database execution.

### Costs / Risks

- Bypass Change Tracker.
- Domain callbacks/events không tự chạy.
- Stale tracked state có thể gây correctness bug.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu set-based update khác với load object rồi save.

### Middle

Biết dùng `ExecuteUpdate/Delete` cho cleanup/bulk operation rõ ràng.

### Senior

Hiểu interaction với tracker, transaction, concurrency và domain invariants.

### Technical Lead / Architect

Quyết định operation nào là pure data maintenance và operation nào phải đi qua aggregate/domain workflow.

## 11. Key takeaway

- `ExecuteUpdate/Delete` tối ưu set-based mutation, không phải “SaveChanges nhanh hơn”.
- Bypass tracker đồng nghĩa in-memory state có thể stale.
- Không dùng bulk SQL để né business invariants một cách vô thức.

# 4. SQL covering index với `INCLUDE`: giảm key lookup nhưng không biến mọi query thành index-only bằng cách thêm tất cả columns

## 1. What is it?

Covering index là index chứa đủ dữ liệu cần cho một query để engine không phải quay lại base table/clustered index lấy thêm columns.

Trong SQL Server, key columns tham gia sort/search structure; `INCLUDE` columns nằm ở leaf level và không ảnh hưởng ordering theo cách key columns làm.

Ví dụ:

```sql
CREATE INDEX IX_Orders_CustomerId_CreatedAt
ON Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, Total);
```

## 2. Why does it exist?

Query:

```sql
SELECT Status, Total
FROM Orders
WHERE CustomerId = @CustomerId
ORDER BY CreatedAt DESC;
```

Nếu index chỉ có `(CustomerId, CreatedAt)`, engine có thể seek đúng rows nhưng phải key lookup vào clustered index để lấy `Status`, `Total`.

Với 10 rows thì rẻ. Với 100k rows, hàng chục nghìn random lookups có thể đắt.

Covering index giảm additional I/O.

## 3. How does it work?

Mental model:

```text
Nonclustered index seek
   -> key columns locate rows
   -> included columns already at leaf
   -> return result
```

Without include:

```text
Index seek
   -> row locator
   -> key lookup
   -> base row
```

Nhưng included columns làm index lớn hơn, tăng storage và write cost.

## 4. Practical implementation

Bắt đầu từ actual execution plan và `STATISTICS IO`:

```sql
SET STATISTICS IO, TIME ON;

SELECT TOP (100)
       Status,
       Total
FROM Orders
WHERE CustomerId = @CustomerId
ORDER BY CreatedAt DESC;
```

Nếu plan có nhiều Key Lookup và logical reads cao, có thể cân nhắc:

```sql
CREATE INDEX IX_Orders_Customer_Created
ON Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, Total);
```

Sau đó đo lại.

## 5. Real production scenario

Customer-order history endpoint query 50 rows nhưng table có 200 triệu records.

Index hiện có chỉ trên `CustomerId`. Engine seek được customer nhưng phải lookup từng row để lấy 6 display columns.

Covering index đúng access pattern giảm p95 đáng kể.

Nhưng team sau đó thêm 25 columns vào `INCLUDE` cho “mọi endpoint”, index lớn gần bằng table và write latency tăng.

## 6. Failure scenario & troubleshooting

**Symptom** → read query nhanh hơn nhưng insert/update throughput xấu đi; DB storage tăng mạnh.

**Evidence** → index size lớn, page splits/write I/O tăng, nhiều overlapping indexes.

**Hypothesis** → over-covering/duplicate indexes.

**Diagnosis** → xem index usage stats, write frequency, query plans, index size.

**Fix** → chỉ cover hot query có evidence; consolidate overlapping indexes; bỏ unused index có kiểm soát.

**Verification** → benchmark read + write workload, không chỉ isolated SELECT.

## 7. Common mistakes

- Thêm mọi selected column vào `INCLUDE`.
- Không phân biệt key order và include.
- Tạo index cho mỗi query mà bỏ qua overlap.
- Optimize read query hiếm nhưng làm chậm write path critical.
- Không kiểm tra actual plan sau khi tạo index.

## 8. Alternatives

Projection nhỏ hơn có thể loại nhu cầu include thêm columns.

Denormalized read model/materialized view phù hợp reporting-heavy workload.

Columnstore phù hợp analytic scan pattern, không phải transactional lookup mặc định.

## 9. Trade-offs

### Advantages

- Giảm key lookup và logical I/O.
- Có thể cải thiện latency đáng kể cho hot read path.

### Costs / Risks

- Index lớn hơn.
- Write amplification.
- Storage/maintenance overhead.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không miễn phí và không phải cứ thêm index là nhanh.

### Middle

Đọc seek + key lookup trong execution plan.

### Senior

Cân bằng read benefit, write cost, selectivity và index overlap.

### Technical Lead / Architect

Thiết kế access pattern/SLI trước khi index; review toàn workload thay vì tối ưu từng query độc lập.

## 11. Key takeaway

- `INCLUDE` giúp cover output columns mà không làm chúng thành search keys.
- Key lookup chỉ đáng tối ưu khi evidence cho thấy nó thật sự đắt.
- Index design luôn đánh đổi read speed với write/storage cost.

# 5. Cosmos DB hot partition: partition key “đúng cú pháp” vẫn có thể phá throughput và cost khi traffic phân bố lệch

## 1. What is it?

Cosmos DB partition key quyết định cách items được phân bố vào logical partitions và cuối cùng physical partitions.

Một **hot partition** xuất hiện khi phần lớn traffic/RU consumption tập trung vào một partition key range, dù tổng throughput của account/container còn dư.

Mental model:

```text
100 partitions
99 partitions: light traffic
1 partition: 70% requests
               -> throttling 429
```

## 2. Why does it exist?

Distributed database scale bằng cách chia dữ liệu/workload. Nếu partition key phân bố không đều, thêm tổng RU không nhất thiết giải quyết hiệu quả vì bottleneck tập trung ở một range.

Partition key vì vậy là workload-distribution decision, không chỉ schema field.

## 3. How does it work?

Giả sử partition key là `/tenantId`.

Nếu 10,000 tenant nhỏ và 1 giant enterprise tenant tạo 60% traffic, giant tenant trở thành hotspot.

Query có exact partition key:

```text
request -> route directly partition
```

Cross-partition query:

```text
request -> fan out multiple partitions
         -> aggregate
```

Một key tốt cân bằng:

- distribution;
- query locality;
- transaction scope;
- future growth.

## 4. Practical implementation

Ví dụ document:

```json
{
  "id": "evt-123",
  "tenantId": "t-42",
  "deviceId": "d-99",
  "timestamp": "2026-09-12T08:00:00Z"
}
```

Nếu single tenant có cực nhiều devices, hierarchical/composite partitioning strategy hoặc synthetic key có thể cần:

```text
tenantId + deviceBucket
```

Ví dụ synthetic:

```csharp
var bucket = Math.Abs(deviceId.GetHashCode()) % 32;
var partitionKey = $"{tenantId}:{bucket}";
```

Nhưng điều này làm query toàn tenant phải fan-out 32 buckets. Đó là trade-off thực, không free lunch.

## 5. Real production scenario

IoT backend dùng `/customerId` làm partition key.

Một automotive enterprise customer deploy 2 triệu devices, còn phần lớn customers chỉ vài nghìn.

Total RU nhìn đủ, nhưng customer lớn nhận nhiều `429 RequestRateTooLarge`. Tăng RU toàn container rất tốn nhưng hotspot vẫn tồn tại.

Root cause là data/traffic skew.

## 6. Failure scenario & troubleshooting

**Symptom** → 429 tập trung vào một tenant/device group trong khi average RU utilization không quá cao.

**Evidence** → metrics theo partition key range cho thấy normalized RU rất cao ở một range.

**Hypothesis** → hot partition.

**Diagnosis** → phân tích key cardinality, traffic distribution, item size và query locality.

**Fix** → redesign partition strategy, spread hot tenant, cache/aggregate high-frequency writes, batch khi phù hợp.

**Verification** → replay skewed production-like traffic và theo dõi 429 + RU distribution.

## 7. Common mistakes

- Chọn partition key chỉ vì field “luôn có”.
- Dùng low-cardinality key như country/status.
- Tối ưu storage distribution nhưng bỏ qua traffic distribution.
- Thay key mà không nghĩ migration cost.
- Dùng random UUID partition key rồi mọi business query thành cross-partition.

## 8. Alternatives

SQL/PostgreSQL phù hợp nếu workload cần joins/transactions và scale hiện tại không đòi distributed document store.

MongoDB sharding có bài toán shard-key tương tự.

Nếu data volume nhỏ, relational DB đơn giản hơn có thể tốt hơn Cosmos.

## 9. Trade-offs

### Advantages

Partitioning tốt cho horizontal scale và targeted routing.

### Costs / Risks

Partition key gần như architectural commitment; redesign/migration rất đắt.

Spread tốt cho writes có thể làm reads fan-out hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định dữ liệu nằm/chạy workload ở đâu.

### Middle

Biết đọc 429/RU metrics và query bằng exact partition key.

### Senior

Phân tích skew, cardinality, hot key và transaction/query locality.

### Technical Lead / Architect

Chọn partition strategy dựa trên growth model vài năm, không chỉ dataset hiện tại; cân nhắc migration path trước khi production scale lớn.

## 11. Key takeaway

- Partition key là workload distribution contract.
- Tổng RU đủ không đảm bảo mọi partition khỏe.
- Key tốt phải cân bằng write distribution và query locality.

# 6. Retry + Circuit Breaker: ngăn transient fault lan thành retry storm và cascading failure trong distributed system

## 1. What is it?

Retry thử lại operation khi failure có khả năng tạm thời.

Circuit Breaker tạm ngừng gọi dependency sau khi failure vượt threshold để tránh tiếp tục gửi workload vào một dependency đang unhealthy.

Chúng giải quyết hai câu hỏi khác nhau:

```text
Retry: "Có nên thử lại request này?"
Circuit Breaker: "Có nên tiếp tục gửi request mới tới dependency này không?"
```

## 2. Why does it exist?

Network failure là bình thường. Một timeout đơn lẻ có thể recover ở lần sau.

Nhưng khi dependency thực sự down, retry mọi request 3 lần sẽ nhân traffic:

```text
1000 req/s
x 3 retries
= up to 4000 attempts/s including originals
```

Dependency đã yếu lại bị đánh mạnh hơn. Application threads/connections cũng bị giữ lâu hơn.

Circuit Breaker tạo failure containment.

## 3. How does it work?

Circuit thường có states:

```text
Closed
  -> failures exceed threshold
Open
  -> reject fast for break duration
Half-Open
  -> allow limited probe calls
  -> success => Closed
  -> failure => Open
```

Retry thường dùng exponential backoff + jitter:

```text
100 ms
250 ms
600 ms
```

Jitter tránh hàng nghìn clients retry đồng bộ cùng thời điểm.

## 4. Practical implementation

Với resilience pipeline trong .NET:

```csharp
builder.Services.AddHttpClient<InventoryClient>()
    .AddStandardResilienceHandler(options =>
    {
        options.Retry.MaxRetryAttempts = 3;
        options.Retry.Delay = TimeSpan.FromMilliseconds(200);
        options.AttemptTimeout.Timeout = TimeSpan.FromSeconds(2);
        options.CircuitBreaker.BreakDuration = TimeSpan.FromSeconds(30);
    });
```

Policy thực tế cần dựa trên operation semantics. Không retry `POST` có side effect nếu không idempotent.

## 5. Real production scenario

Checkout API gọi review service, inventory service và payment provider.

Review service down nhưng không critical. Nếu mọi request chờ 5s timeout x 3 retries, checkout p99 tăng mạnh dù dependency không critical.

Circuit mở sớm và fallback “reviews unavailable” giúp checkout tiếp tục.

Payment thì khác: không được retry charge mù nếu không có idempotency key.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency incident khiến API thread/connection usage tăng và recovery chậm dù dependency đã khỏe lại.

**Evidence** → retry attempt count cao, outbound RPS gấp nhiều lần inbound, timeout correlation dày đặc.

**Hypothesis** → retry amplification/retry storm.

**Diagnosis** → measure original requests vs attempts, breaker state, timeout distribution.

**Fix** → retry fewer times, backoff+jitter, circuit breaker, bulkhead, idempotency, fallback.

**Verification** → fault injection dependency unavailable 1–2 phút; outbound attempts phải bounded.

## 7. Common mistakes

- Retry mọi 5xx/exception giống nhau.
- Retry timeout mà original request có thể vẫn đang chạy downstream.
- Không có jitter.
- Retry nested ở HTTP client + service + controller cùng lúc.
- Circuit breaker threshold quá nhạy tạo flapping.
- Retry non-idempotent payment/write operation.

## 8. Alternatives

Queue-based asynchronous processing phù hợp khi dependency không cần phản hồi trong request path.

Bulkhead/concurrency limiter bảo vệ local resources.

Fallback phù hợp optional dependency.

Đôi khi fail-fast ngay là lựa chọn tốt nhất.

## 9. Trade-offs

### Advantages

- Recover transient faults.
- Circuit breaker giảm cascading failure.
- Cải thiện resilience khi policy đúng semantics.

### Costs / Risks

- Retry tăng latency/load.
- Circuit breaker thêm state và tuning.
- Sai policy có thể làm duplicate side effect hoặc reject traffic quá mức.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry không phải universal error handler.

### Middle

Implement timeout, limited retry, backoff và cancellation.

### Senior

Thiết kế policy theo idempotency/failure taxonomy và đo retry amplification.

### Technical Lead / Architect

Quy định dependency criticality, resilience budget và failure containment giữa services.

## 11. Key takeaway

- Retry xử lý transient failure; Circuit Breaker xử lý sustained dependency failure.
- Retry phải bounded, có backoff/jitter và hiểu idempotency.
- Nhiều resilience layer chồng nhau có thể tạo amplification nguy hiểm.

# 7. Azure Front Door origin health + failover: global ingress chỉ đáng tin khi health probe phản ánh đúng khả năng phục vụ traffic

## 1. What is it?

Azure Front Door là global edge service có thể route HTTP traffic tới nhiều origins/regions. Nó dùng health probes để đánh giá origin nào đang healthy và có thể fail traffic sang origin khác theo routing policy.

Mental model:

```text
Client
  -> Azure Front Door edge
      -> Region A origin
      -> Region B origin
```

Failover quality phụ thuộc health signal. Nếu probe “xanh giả”, Front Door vẫn route traffic tới origin không thực sự phục vụ được.

## 2. Why does it exist?

Single-region ingress tạo blast radius lớn. Front Door có thể hỗ trợ:

- global routing;
- TLS termination;
- WAF;
- caching;
- origin failover;
- latency-based routing.

Nhưng multi-region chỉ hữu ích nếu application/data architecture cũng có failover semantics.

## 3. How does it work?

Front Door gửi periodic health probe tới configured endpoint.

Nếu Region A probe fail đủ threshold:

```text
Region A unhealthy
 -> stop routing new traffic there
 -> Region B receives traffic
```

Probe endpoint nên phản ánh khả năng phục vụ request critical, nhưng không nên phụ thuộc quá nhiều optional dependencies gây false-negative.

Ví dụ `/health/ready` có thể check critical DB connectivity nhưng không cần fail vì analytics API down.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddHealthChecks()
    .AddDbContextCheck<AppDbContext>("database", tags: ["ready"]);

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

Tách liveness:

```csharp
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false
});
```

Front Door nên probe readiness-like endpoint phù hợp origin routing.

## 5. Real production scenario

E-commerce có West Europe + North Europe.

Region A App Service process vẫn chạy và `/health` chỉ trả 200 hardcoded. Nhưng regional SQL endpoint bị network isolation issue. Front Door vẫn route 50% traffic vào Region A và users nhận 500.

Health probe không represent serving capability.

## 6. Failure scenario & troubleshooting

**Symptom** → một region có 5xx cao nhưng Front Door vẫn route traffic vào đó.

**Evidence** → Front Door origin health healthy; app dependency telemetry cho thấy DB unavailable.

**Hypothesis** → probe quá nông hoặc wrong endpoint.

**Diagnosis** → compare health probe semantics với dependencies critical cho serving path.

**Fix** → readiness probe có critical dependencies, routing threshold phù hợp, region failover runbook.

**Verification** → regional dependency fault injection và xác nhận traffic shift + user-facing SLI.

## 7. Common mistakes

- Health endpoint chỉ `return 200`.
- Probe mọi optional dependency rồi origin flaps.
- Multi-region app nhưng database vẫn single-region không có failover strategy.
- DNS/Front Door failover được nhưng session/state không portable.
- Không test disaster recovery thực tế.

## 8. Alternatives

Application Gateway là regional L7 load balancer, phù hợp VNet/regional ingress.

Traffic Manager là DNS-based routing, semantics khác Front Door proxy edge.

Single-region App Service đơn giản hơn khi business không yêu cầu multi-region availability.

## 9. Trade-offs

### Advantages

- Global edge routing/failover.
- WAF/TLS/caching integration.
- Giảm blast radius của regional failure khi backend support tốt.

### Costs / Risks

- Multi-region data consistency phức tạp.
- Health semantics/tuning khó.
- Chi phí hạ tầng và operational testing tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu load balancer chỉ route theo signal nó được cung cấp.

### Middle

Implement meaningful health checks và phân biệt liveness/readiness.

### Senior

Phân tích origin health, failover timing, state/data dependencies.

### Technical Lead / Architect

Quyết định availability target có justify multi-region không; thiết kế failover end-to-end từ edge tới database/state.

## 11. Key takeaway

- Global routing không cứu được backend không có failover semantics.
- Health probe phải phản ánh khả năng phục vụ critical traffic.
- Multi-region cần test failure thực tế, không chỉ architecture diagram.

# 8. CI/CD rollback với database migration: vì sao “rollback app” không đủ nếu schema đã đi qua destructive change

## 1. What is it?

Rollback là đưa production về một application artifact trước đó khi release mới có regression.

Nhưng deployment hiện đại thường thay cả:

```text
application binary
configuration
feature flags
database schema
background jobs
contracts
```

Nếu database migration destructive, old binary có thể không còn chạy được dù artifact rollback thành công.

## 2. Why does it exist?

CI/CD thường giả định artifact immutable nên rollback chỉ cần redeploy build trước. Điều đó đúng cho code-only change.

Database là shared persistent state có lifecycle khác. `DROP COLUMN`, rename trực tiếp, data transformation irreversible hoặc enum semantics mới có thể phá rollback.

## 3. How does it work?

Safe release sequence thường dùng compatibility window:

```text
Release N
 -> expand schema
 -> deploy compatible app
 -> migrate/backfill data
 -> observe

Release N+1
 -> stop using old schema
 -> observe

Release N+2
 -> contract/drop old schema
```

Rollback trong window này vẫn có đường quay lại.

## 4. Practical implementation

Không nên cùng release:

```sql
EXEC sp_rename 'Customers.Name', 'DisplayName', 'COLUMN';
```

và code chỉ biết `DisplayName`.

An toàn hơn:

```sql
ALTER TABLE Customers ADD DisplayName nvarchar(200) NULL;
```

Deploy code có fallback:

```csharp
var name = customer.DisplayName ?? customer.Name;
```

Sau migration/backfill + telemetry xác nhận, release sau mới remove `Name`.

## 5. Real production scenario

Deployment mới lên 20 pods. Migration drop `LegacyStatus` chạy đầu tiên. Sau đó app version mới có bug memory leak.

Team rollback pods về version cũ, nhưng version cũ query `LegacyStatus` và crash startup.

Rollback artifact thành công kỹ thuật nhưng service vẫn down.

## 6. Failure scenario & troubleshooting

**Symptom** → rollback completed nhưng old version trả 500/startup fail.

**Evidence** → SQL “invalid column”; migration history cho thấy destructive migration đã apply.

**Hypothesis** → database backward compatibility bị phá.

**Diagnosis** → map old/new application schema expectations và actual DB schema.

**Fix** → restore compatibility schema/data nếu có thể; deploy bridging version.

**Verification** → pre-production test old + new binaries cùng expanded schema.

## 7. Common mistakes

- Migration destructive chạy trước app rollout.
- Xem migration rollback script như guaranteed safe.
- Không tính background jobs/reporting consumers.
- Data conversion irreversible nhưng không backup/audit.
- Feature flag off nhưng schema đã phá old path.

## 8. Alternatives

Maintenance window + downtime có thể đơn giản hơn cho hệ thống nhỏ.

Blue-green database riêng tăng isolation nhưng data sync/cutover phức tạp.

Forward-fix đôi khi tốt hơn rollback nếu migration đã quá xa, nhưng cần incident judgment.

## 9. Trade-offs

### Advantages

Compatibility-first rollout giữ rollback path và giảm release blast radius.

### Costs / Risks

- Nhiều release stages.
- Transitional code/schema cần cleanup discipline.
- Backfill/dual-read có complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu rollback app không tự rollback persistent data/schema.

### Middle

Viết backward-compatible migration và test mixed versions.

### Senior

Thiết kế expand-contract, backfill, deployment ordering và rollback runbook.

### Technical Lead / Architect

Đặt release policy: destructive migration chỉ khi old versions đã hết traffic và rollback window đóng có chủ đích.

## 11. Key takeaway

- Rollback là system-level capability, không chỉ artifact redeploy.
- Database compatibility quyết định old binary có quay lại được hay không.
- Destructive schema change nên tách khỏi release giới thiệu behavior mới.

# 9. High-cardinality metrics: observability có thể tự trở thành performance/cost incident nếu label dimensions không được kiểm soát

## 1. What is it?

Metric cardinality là số combinations duy nhất của label/tag values.

Ví dụ metric:

```text
http_requests_total{route, method, status}
```

Có cardinality tương đối bounded.

Nếu thêm `user_id`:

```text
http_requests_total{route, method, status, user_id}
```

với 5 triệu users, time-series count có thể bùng nổ.

## 2. Why does it exist?

Metrics tối ưu cho aggregated numeric signal theo dimensions có bounded cardinality.

Logs/traces phù hợp hơn cho high-cardinality identifiers như:

- request ID;
- user ID;
- order ID;
- correlation ID.

Đưa những values này vào metric label biến monitoring backend thành distributed index khổng lồ.

## 3. How does it work?

Giả sử:

```text
20 routes
5 status groups
3 regions
1,000,000 user IDs
```

Potential combinations:

```text
20 x 5 x 3 x 1,000,000
= 300,000,000 series
```

Không phải mọi combination đều xuất hiện, nhưng cardinality vẫn có thể rất lớn.

Cost đến từ ingestion, memory index, storage và query fan-out.

## 4. Practical implementation

Metric tốt:

```csharp
requestCounter.Add(
    1,
    new KeyValuePair<string, object?>("route", routePattern),
    new KeyValuePair<string, object?>("status_class", "2xx"));
```

Không nên:

```csharp
requestCounter.Add(
    1,
    new("user_id", user.Id),
    new("request_id", httpContext.TraceIdentifier));
```

User/order/request ID nên vào logs/traces:

```csharp
_logger.LogInformation(
    "Processed order {OrderId} for user {UserId}",
    orderId,
    userId);
```

## 5. Real production scenario

Team thêm `customerId` vào every OpenTelemetry metric để “debug dễ hơn”. Sau campaign, monitoring bill tăng gấp nhiều lần, query dashboard timeout và collector/backend memory pressure tăng.

Application không chậm vì business workload mà vì telemetry pipeline.

## 6. Failure scenario & troubleshooting

**Symptom** → observability cost/infrastructure memory tăng nhanh; dashboard query chậm.

**Evidence** → time-series count tăng mạnh sau release; một label có hàng trăm nghìn unique values.

**Hypothesis** → high-cardinality dimension.

**Diagnosis** → cardinality report theo metric/attribute; compare before/after instrumentation changes.

**Fix** → remove/bucket high-cardinality labels; move identifiers sang logs/traces; aggregate route/status/class.

**Verification** → series count và ingestion rate giảm nhưng SLO dashboards vẫn giữ signal cần thiết.

## 7. Common mistakes

- Label metric bằng raw URL chứa IDs.
- `exception.message` làm label.
- user/order/request ID trong metrics.
- Mọi business field đều thành dimension.
- Sampling traces rồi cố dùng metrics high-cardinality để bù detail.

## 8. Alternatives

Logs phù hợp event-level detail.

Traces phù hợp causal path + identifiers.

Metrics phù hợp aggregate rate/latency/error/capacity signal.

Exemplars có thể link metric observation tới trace mà không biến trace ID thành full metric label dimension.

## 9. Trade-offs

### Advantages

Metrics với bounded labels cực mạnh cho dashboards, alerting và SLO.

### Costs / Risks

High cardinality có thể tăng cost phi tuyến, làm backend monitoring không ổn định.

Giảm labels quá mức lại mất segmentation hữu ích.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu metrics không phải logs dạng số.

### Middle

Dùng bounded labels như route template/status/region.

### Senior

Review cardinality, ingestion cost và signal quality.

### Technical Lead / Architect

Đặt observability schema governance: metric dimensions nào được phép, data nào thuộc logs/traces, budget telemetry theo service criticality.

## 11. Key takeaway

- Metrics cần bounded dimensions.
- High-cardinality identifiers thuộc logs/traces hơn là metric labels.
- Observability cũng là production workload và cần capacity/cost discipline.

# 10. React stale closure trong async callback: state cũ vẫn sống trong closure và tạo race condition khó thấy ở frontend

## 1. What is it?

Trong React function component, mỗi render tạo một snapshot của props/state và các closures gắn với render đó.

Async callback hoặc timer có thể tiếp tục giữ snapshot cũ sau khi component đã render state mới.

Ví dụ:

```tsx
const [count, setCount] = useState(0);

async function handleSave() {
  await saveAsync();
  console.log(count); // count từ render lúc callback được tạo
}
```

Đây là stale closure.

## 2. Why does it exist?

JavaScript closure capture lexical environment. React không mutate state variable hiện tại; mỗi render gọi component function lại và tạo bindings mới.

Mental model:

```text
Render #1: count = 0 -> callback A captures 0
Render #2: count = 1 -> callback B captures 1

callback A finishes later -> still sees 0
```

Async timing khiến bug chỉ xuất hiện khi response/order thay đổi.

## 3. How does it work?

Classic example:

```tsx
setCount(count + 1);
setCount(count + 1);
```

Cả hai dùng cùng captured `count`, nên result có thể chỉ +1.

Functional update dùng latest queued state:

```tsx
setCount(c => c + 1);
setCount(c => c + 1);
```

Với request race, closure có thể giữ query/filter cũ và ghi response cũ đè state mới.

## 4. Practical implementation

Search component:

```tsx
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    const response = await fetch(
      `/api/products?q=${encodeURIComponent(query)}`,
      { signal: controller.signal }
    );

    const data = await response.json();
    setProducts(data);
  }

  load().catch(error => {
    if (error.name !== "AbortError") {
      setError(error);
    }
  });

  return () => controller.abort();
}, [query]);
```

Cleanup aborts request associated với render/query cũ.

## 5. Real production scenario

User gõ search:

```text
"car" request starts
"camera" request starts later
"camera" response returns first
"car" response returns last
```

Nếu không cancel/version requests, response `car` cũ ghi đè state mới và UI hiển thị kết quả sai.

Backend hoàn toàn đúng; bug nằm ở frontend async lifecycle.

## 6. Failure scenario & troubleshooting

**Symptom** → UI đôi lúc quay lại data cũ khi user thao tác nhanh.

**Evidence** → browser Network tab cho thấy responses hoàn tất out-of-order; state update từ old request chạy sau new request.

**Hypothesis** → stale closure/request race.

**Diagnosis** → log request sequence/query/version; React DevTools + browser timeline.

**Fix** → abort stale requests, request sequence token, correct dependency arrays, functional state update.

**Verification** → throttle network trong DevTools và thao tác nhanh để force out-of-order responses.

## 7. Common mistakes

- Bỏ dependency khỏi `useEffect` để “ngăn rerender”.
- Disable ESLint hook dependency warning thay vì hiểu closure.
- `setState(state + x)` nhiều lần khi update phụ thuộc previous state.
- Không abort request khi query/component lifecycle thay đổi.
- Dùng global mutable variable để né stale state.

## 8. Alternatives

React Query/TanStack Query có request caching/lifecycle utilities và giúp giảm custom async state handling.

State machine/library có thể phù hợp flow phức tạp.

Với simple component, native `useEffect` + `AbortController` là đủ.

## 9. Trade-offs

### Advantages

React snapshot model giúp render reasoning predictable và immutable hơn.

### Costs / Risks

Closures + async work tạo subtle stale-state bugs nếu developer nghĩ state variable được mutate live.

Library data-fetching giảm boilerplate nhưng thêm abstraction.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mỗi render có state snapshot riêng.

### Middle

Biết functional update, dependency array và cleanup request.

### Senior

Phân tích async race, cancellation, cache invalidation và render lifecycle.

### Technical Lead / Architect

Quyết định data-fetching/state abstraction nào cần chuẩn hóa để tránh mỗi component tự viết race-prone request lifecycle.

## 11. Key takeaway

- Closure giữ state của render đã tạo ra nó.
- Async response có thể về sai thứ tự và ghi đè state mới.
- Cancellation/versioning/state-based ownership quan trọng hơn việc thêm delay.
