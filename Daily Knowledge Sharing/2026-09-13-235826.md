# 1. C# `TimeProvider`, `DateTimeOffset` và timezone correctness: thời gian là domain data, không chỉ là `DateTime.Now`

## 1. What is it?

Mental model quan trọng nhất là tách ba khái niệm:

```text
Instant       = một thời điểm tuyệt đối trên timeline
Offset        = độ lệch UTC tại instant đó
Time zone     = tập rule lịch sử/tương lai để map local time <-> instant
```

Trong .NET:

- `DateTimeOffset` phù hợp khi cần biểu diễn một instant cùng UTC offset.
- `DateTime` có thể mang `Kind`, nhưng thường dễ bị dùng sai khi local/UTC semantics không rõ.
- `TimeZoneInfo` biểu diễn timezone rules.
- `TimeProvider` tạo abstraction để application lấy “bây giờ”, timer và elapsed time theo cách testable.

`TimeProvider` không phải timezone library. Nó giải quyết clock abstraction; timezone vẫn là một concern riêng.

## 2. Why does it exist?

Code đơn giản như:

```csharp
var now = DateTime.Now;
```

trông vô hại nhưng tạo dependency trực tiếp vào system clock, local server timezone và wall-clock behavior. Điều này gây khó test các scenario như:

- subscription hết hạn sau 30 phút;
- daylight saving transition;
- job chạy “9:00 AM theo timezone của khách hàng”;
- token/window hết hạn;
- clock nhảy do synchronization;
- test phải chờ thời gian thật.

Production system thường cần một định nghĩa thời gian rõ hơn syntax của `DateTime`.

## 3. How does it work?

Một pattern hợp lý:

```text
External/business timestamp
        |
        v
normalize to UTC instant
        |
        +--> persist as UTC / DateTimeOffset
        |
        +--> compare durations/expiry in UTC
        |
        v
convert to user's timezone only at boundary
```

Ví dụ application clock:

```csharp
public sealed class SubscriptionService(TimeProvider clock)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => clock.GetUtcNow() >= expiresAt;
}
```

Production đăng ký:

```csharp
builder.Services.AddSingleton(TimeProvider.System);
```

Test có thể inject fake provider để điều khiển thời gian mà không `Task.Delay` thật.

## 4. Practical implementation

Giả sử approval request hết hạn sau 24 giờ:

```csharp
public sealed class ApprovalService(TimeProvider timeProvider)
{
    public Approval Create(Guid id)
    {
        var now = timeProvider.GetUtcNow();

        return new Approval
        {
            Id = id,
            CreatedAt = now,
            ExpiresAt = now.AddHours(24)
        };
    }

    public bool CanApprove(Approval approval)
        => timeProvider.GetUtcNow() < approval.ExpiresAt;
}
```

Khi hiển thị cho user:

```csharp
var zone = TimeZoneInfo.FindSystemTimeZoneById(userTimeZoneId);
var local = TimeZoneInfo.ConvertTime(approval.ExpiresAt, zone);
```

Không nên persist chỉ `2026-09-13 09:00` rồi hy vọng biết nó thuộc timezone nào.

## 5. Real production scenario

Một SaaS có customer ở Việt Nam, Mỹ và châu Âu. Business rule nói reminder phải gửi lúc 09:00 theo timezone của customer.

Nếu scheduled job chạy theo server local time, cùng một UTC instant sẽ không phải 09:00 ở mọi nơi. Khi daylight saving thay đổi, offset của một timezone có thể thay đổi dù timezone ID không đổi.

Thiết kế đúng cần persist timezone identity của customer, tính next occurrence theo timezone rule, rồi chuyển thành UTC instant để schedule/compare.

## 6. Failure scenario & troubleshooting

**Symptom** → reminder gửi lệch một giờ chỉ ở một số quốc gia sau DST transition.

**Evidence** → database lưu local timestamp nhưng không lưu timezone; code dùng fixed offset như `UTC-5` quanh năm.

**Hypothesis** → application đã nhầm offset với timezone.

**Diagnosis** → kiểm tra dữ liệu persist, timezone ID, conversion path và server timezone. Reproduce bằng date ngay trước/sau DST boundary.

**Fix** → persist instant + timezone identity khi business semantics cần local recurring time; dùng timezone rules thay fixed offset.

**Verification** → automated tests cover DST gaps/overlaps và multiple regions.

## 7. Common mistakes

- Dùng `DateTime.Now` khắp domain/application code.
- Nghĩ `UTC+7` là timezone đầy đủ cho mọi business case.
- Persist local time nhưng không có timezone identity.
- Convert UTC/local nhiều lần và mất semantic origin.
- Dùng `Thread.Sleep`/real delay để test expiry.
- Dùng wall clock để đo elapsed duration thay vì monotonic timestamp APIs.

## 8. Alternatives

- Inject custom `IClock`: vẫn hợp lệ nếu codebase đã có abstraction đơn giản.
- Noda Time: mạnh hơn khi domain có timezone/calendar complexity đáng kể.
- `DateTimeOffset.UtcNow`: đơn giản nhưng khó kiểm soát trong deterministic tests nếu gọi trực tiếp khắp code.

## 9. Trade-offs

### Advantages

- `TimeProvider` tăng testability mà không cần custom abstraction lớn.
- UTC instant giúp comparison/order nhất quán.
- Timezone conversion được giữ ở boundary rõ ràng.

### Costs / Risks

- Time-domain modeling phức tạp hơn `DateTime.Now`.
- Recurring local schedules cần timezone rules và DST tests.
- Timezone IDs/platform differences có thể cần normalization strategy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu UTC, local time và offset không phải cùng một thứ.

### Middle

Biết dùng `DateTimeOffset`, `TimeProvider` và `TimeZoneInfo` ở đúng boundary.

### Senior

Thiết kế expiration, recurring schedules, persistence và DST handling; phân biệt wall clock với elapsed time.

### Technical Lead / Architect

Đặt canonical time model cho hệ thống: dữ liệu nào là instant, dữ liệu nào là local scheduled time, timezone ownership nằm ở đâu và migration xử lý dữ liệu lịch sử thế nào.

## 11. Key takeaway

- Timezone là rule set, không chỉ một UTC offset.
- Persist/compare instant bằng UTC; convert sang local time ở boundary khi phù hợp.
- Abstract clock bằng `TimeProvider` để logic thời gian deterministic và testable.

# 2. ASP.NET Core Forwarded Headers và reverse-proxy trust: scheme, host và client IP chỉ đúng khi proxy boundary được cấu hình đúng

## 1. What is it?

Production ASP.NET Core thường không nhận traffic trực tiếp từ browser. Request đi qua một hoặc nhiều reverse proxies:

```text
Client
  |
  v
CDN / Load Balancer / Reverse Proxy
  |
  v
ASP.NET Core
```

Proxy có thể terminate TLS rồi forward request nội bộ bằng HTTP. Vì vậy application nhìn trực tiếp connection có thể thấy:

- scheme = `http` dù browser dùng `https`;
- remote IP = proxy IP thay vì client IP;
- host khác external host.

Forwarded headers truyền external request context vào backend, ví dụ `X-Forwarded-For`, `X-Forwarded-Proto`.

## 2. Why does it exist?

Nếu application không biết original scheme/host, nó có thể:

- generate HTTP redirect thay vì HTTPS;
- tạo callback URL sai cho OAuth/OIDC;
- log sai client IP;
- áp security policy sai;
- tạo redirect loop với HTTPS redirection.

Nhưng nếu application tin mọi `X-Forwarded-*` header từ internet, attacker có thể spoof chúng. Vì vậy đây vừa là networking concern vừa là trust-boundary concern.

## 3. How does it work?

Proxy chuẩn hóa request và thêm headers:

```text
Browser: HTTPS https://example.com
        |
Proxy terminates TLS
        |
Backend receives HTTP
X-Forwarded-Proto: https
X-Forwarded-For: client-ip
```

ASP.NET Core `ForwardedHeadersMiddleware` đọc các headers được tin cậy và cập nhật request properties.

Middleware order quan trọng: forwarded headers phải chạy đủ sớm trước components dựa vào scheme/host/client IP.

## 4. Practical implementation

Ví dụ:

```csharp
using Microsoft.AspNetCore.HttpOverrides;

builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders =
        ForwardedHeaders.XForwardedFor |
        ForwardedHeaders.XForwardedProto;

    options.KnownNetworks.Clear();
    options.KnownProxies.Clear();

    options.KnownProxies.Add(System.Net.IPAddress.Parse("10.0.0.10"));
});

var app = builder.Build();

app.UseForwardedHeaders();
app.UseHttpsRedirection();
```

Trong thực tế, `KnownNetworks`/`KnownProxies` phải phản ánh topology thực tế. Không nên clear trust restrictions rồi tin toàn internet chỉ để “cho chạy”.

## 5. Real production scenario

Một OIDC login hoạt động local nhưng production redirect về `http://internal-host/signin-oidc`. Identity provider reject callback vì URI không match registered HTTPS URL.

Backend chạy HTTP phía sau Application Gateway. Application chưa process forwarded proto trước authentication middleware, nên callback URL được build từ internal connection context.

## 6. Failure scenario & troubleshooting

**Symptom** → redirect loop HTTPS hoặc authentication callback dùng `http`.

**Evidence** → proxy access log cho thấy external HTTPS; application log cho thấy `Request.Scheme == "http"`.

**Hypothesis** → forwarded headers chưa được xử lý hoặc proxy không thuộc trusted chain.

**Diagnosis** → inspect request headers tại backend, middleware order, proxy configuration và trusted hop count/network.

**Fix** → cấu hình proxy gửi đúng headers; cấu hình ASP.NET Core trust đúng proxy/network; đặt middleware đúng vị trí.

**Verification** → test external URL, redirect, generated absolute URL và client-IP logging qua production-like proxy topology.

## 7. Common mistakes

- Tin `X-Forwarded-For` từ bất kỳ client nào.
- Dùng forwarded client IP như authentication factor.
- Đặt `UseForwardedHeaders` sau authentication/redirect middleware.
- Hard-code external base URL để che topology issue.
- Không hiểu có nhiều proxy hops/CDN + gateway.
- Log spoofable raw forwarding header thay vì resolved trusted context.

## 8. Alternatives

- Platform-specific integration có thể tự cấu hình một phần forwarding behavior.
- External URL configuration phù hợp một số URL-generation use cases nhưng không thay thế client IP/scheme trust handling.
- Direct TLS termination trong app loại một số forwarding concerns nhưng thường không phù hợp cloud ingress architecture.

## 9. Trade-offs

### Advantages

- Application hiểu đúng external request context.
- Authentication, redirects và observability hoạt động đúng sau proxy.

### Costs / Risks

- Trust-chain config sai có thể tạo security vulnerability.
- Multi-proxy topology làm troubleshooting phức tạp.
- Network changes có thể làm trusted proxy list lỗi thời.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu production request có thể đi qua proxy trước khi tới ASP.NET Core.

### Middle

Biết cấu hình forwarded headers và middleware order.

### Senior

Phân tích nhiều proxy hops, spoofing risk, OAuth callback và scheme/host behavior.

### Technical Lead / Architect

Định nghĩa ingress trust boundary, ownership giữa CDN/gateway/app và cách topology changes được rollout an toàn.

## 11. Key takeaway

- Backend connection metadata không luôn là original client metadata.
- Forwarded headers chỉ đáng tin khi source proxy đáng tin.
- Đây là security boundary, không chỉ một config để sửa redirect.

# 3. EF Core `DbContext` pooling: giảm setup cost nhưng có thể rò state giữa requests nếu context không thực sự stateless

## 1. What is it?

`AddDbContextPool<TContext>` cho phép EF Core tái sử dụng `DbContext` instances thay vì tạo mới hoàn toàn cho mỗi scope.

Mental model:

```text
without pooling:
request -> new DbContext -> dispose

with pooling:
request -> rent DbContext -> reset -> return to pool
next request -> rent reused instance
```

Pooling khác database connection pooling. `DbContext` pooling tái sử dụng EF object; ADO.NET connection pooling tái sử dụng physical database connections.

## 2. Why does it exist?

Khởi tạo `DbContext`, service graph và EF internal state có cost nhất định. Trong high-throughput workloads với context nhỏ và query ngắn, pooling có thể giảm allocation/setup overhead.

Nhưng lợi ích thường nhỏ hơn query/network/database cost. Vì vậy pooling là optimization cần benchmark, không phải default bắt buộc.

## 3. How does it work?

Pooled context được reset trước khi trả lại pool, nhưng EF không thể biết mọi custom mutable state mà developer thêm vào context.

Nguy hiểm:

```csharp
public sealed class AppDbContext : DbContext
{
    public Guid TenantId { get; set; }
}
```

Nếu `TenantId` được set cho request A và không reset đúng, request B có thể nhận context reused với state cũ.

Đây đặc biệt nguy hiểm cho global query filters hoặc multi-tenancy.

## 4. Practical implementation

Registration:

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Context nên tránh request-specific mutable state. Nếu tenant-aware query cần tenant ID, cân nhắc architecture nơi state được cung cấp qua scoped service/query parameter thay vì mutate pooled singleton-like instance assumptions.

Khi cần explicit contexts:

```csharp
builder.Services.AddPooledDbContextFactory<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Rồi tạo context theo logical operation.

## 5. Real production scenario

Một multi-tenant API dùng global query filter với `TenantId` property set sau resolve. Sau khi bật pooling để giảm allocation, hiếm khi test load cho thấy request tenant B trả dữ liệu tenant A.

Lỗi không xảy ra đều; nó phụ thuộc instance nào được rent từ pool. Đây là loại bug vừa nghiêm trọng vừa khó reproduce nếu chỉ test sequentially.

## 6. Failure scenario & troubleshooting

**Symptom** → intermittent cross-request state, query filter sai hoặc command interceptor dùng metadata cũ.

**Evidence** → cùng context object instance ID xuất hiện qua nhiều requests; custom fields giữ giá trị cũ.

**Hypothesis** → pooled context chứa mutable state mà EF reset mechanism không quản lý.

**Diagnosis** → audit context fields, interceptors, tenant/request metadata và lifecycle assumptions.

**Fix** → bỏ mutable request state khỏi pooled context hoặc bỏ pooling nếu design không phù hợp.

**Verification** → concurrent multi-tenant integration tests với context-instance tracing và repeated pool reuse.

## 7. Common mistakes

- Nhầm `DbContext` pooling với database connection pooling.
- Bật pooling vì nghĩ query sẽ nhanh đáng kể mà không benchmark.
- Lưu user/tenant/request state trong context.
- Giả định `OnConfiguring`/construction chạy lại cho mọi request như non-pooled context.
- Tự cache context ngoài DI scope.
- Bỏ qua thread-safety: pooled context vẫn không thread-safe.

## 8. Alternatives

- `AddDbContext`: đơn giản và thường đủ nhanh.
- `IDbContextFactory<T>`: explicit creation cho background/parallel UI scenarios.
- Optimize query/network/database trước nếu bottleneck nằm ở I/O.

## 9. Trade-offs

### Advantages

- Giảm context setup/allocation ở hot paths.
- Có thể cải thiện throughput trong benchmark phù hợp.

### Costs / Risks

- Lifecycle assumptions phức tạp hơn.
- Mutable custom state có thể rò giữa operations.
- Tối ưu nhầm chỗ nếu database latency chiếm phần lớn request.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbContext` vẫn là unit-of-work và không thread-safe.

### Middle

Phân biệt context pooling với connection pooling; biết cấu hình DI đúng.

### Senior

Benchmark benefit, audit mutable state và multi-tenant risks.

### Technical Lead / Architect

Chỉ chuẩn hóa pooling khi workload chứng minh benefit và context design đủ stateless để reuse an toàn.

## 11. Key takeaway

- `DbContext` pooling là optimization của EF object lifecycle, không phải database connection optimization.
- Reused context + mutable request state là risk nghiêm trọng.
- Benchmark trước; simplicity của non-pooled context thường đáng giá nếu setup cost không phải bottleneck.

# 4. PostgreSQL `jsonb` + GIN indexes: linh hoạt schema mà không biến mọi truy vấn thành full scan khó kiểm soát

## 1. What is it?

`jsonb` cho phép PostgreSQL lưu JSON ở binary representation tối ưu cho querying/indexing hơn raw `json` text.

Mental model:

```text
relational columns
  -> stable, constrained, frequently queried fields

jsonb column
  -> flexible attributes / sparse metadata
```

GIN index có thể index nhiều keys/values bên trong document và hỗ trợ operators như containment (`@>`).

## 2. Why does it exist?

Một product catalog có hàng trăm optional attributes khác nhau theo category:

- laptop: RAM, CPU, screen size;
- tire: diameter, width;
- shirt: material, size chart.

Tạo hàng trăm nullable columns hoặc EAV tables có thể làm model rất phức tạp. `jsonb` cung cấp flexibility nhưng vẫn giữ transaction/query capabilities của PostgreSQL.

## 3. How does it work?

Table:

```sql
CREATE TABLE products (
    id bigint PRIMARY KEY,
    sku text NOT NULL,
    category_id bigint NOT NULL,
    attributes jsonb NOT NULL DEFAULT '{}'::jsonb
);
```

Query containment:

```sql
SELECT id, sku
FROM products
WHERE attributes @> '{"color":"black"}';
```

GIN index:

```sql
CREATE INDEX ix_products_attributes_gin
ON products USING gin (attributes);
```

Index usefulness phụ thuộc operator/query shape. Không phải mọi JSON expression đều dùng cùng index hiệu quả.

## 4. Practical implementation

Nếu một property rất quan trọng và thường filter/sort, có thể promote nó thành relational/generated column thay vì chôn mọi thứ trong JSON.

Ví dụ expression index cho một field:

```sql
CREATE INDEX ix_products_brand
ON products ((attributes->>'brand'));
```

Query:

```sql
SELECT id, sku
FROM products
WHERE attributes->>'brand' = 'Contoso';
```

Điều này thường hiệu quả hơn GIN generic khi access pattern rất cụ thể.

## 5. Real production scenario

Marketplace lưu toàn bộ product metadata trong `jsonb` vì onboarding category nhanh. Sau một năm, search API thường filter `brand`, `condition` và `year`. Generic GIN index lớn, write cost cao, một số query sort/filter vẫn chậm.

Senior approach là review access patterns: giữ long-tail attributes trong JSON nhưng promote/index hot fields theo query workload.

## 6. Failure scenario & troubleshooting

**Symptom** → query JSON chậm dần khi table lớn; index tồn tại nhưng planner vẫn scan nhiều rows.

**Evidence** → `EXPLAIN (ANALYZE, BUFFERS)` cho thấy sequential scan hoặc bitmap result rất rộng; selectivity thấp.

**Hypothesis** → generic index không match query operator hoặc indexed data quá phổ biến.

**Diagnosis** → inspect query shape, operator class, row estimates, index size và actual selectivity.

**Fix** → targeted expression index, schema promotion, query rewrite hoặc chấp nhận scan nếu result set vốn quá lớn.

**Verification** → compare execution plan, buffers, write cost và storage before/after.

## 7. Common mistakes

- Đưa toàn bộ schema vào JSON để tránh migration.
- Không có validation cho JSON shape quan trọng.
- Tạo GIN index rồi nghĩ mọi JSON query đều nhanh.
- Extract numeric values dưới dạng text rồi sort lexicographically.
- Dùng JSON cho foreign-key relationships cần referential integrity.
- Index mọi key và làm write amplification lớn.

## 8. Alternatives

- Normalized relational columns/tables cho stable domain structure.
- EAV khi cần metadata model đặc biệt, dù query complexity cao.
- MongoDB/Cosmos DB khi document-centric model và distribution requirements phù hợp hơn.

## 9. Trade-offs

### Advantages

- Schema flexibility cho sparse/long-tail attributes.
- Vẫn ở trong PostgreSQL transaction/backup/tooling ecosystem.
- GIN/expression indexes hỗ trợ nhiều access patterns.

### Costs / Risks

- Constraints/type safety yếu hơn relational columns nếu không bổ sung validation.
- GIN index có storage/write cost.
- Query semantics phức tạp và dễ thành hidden schema.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `jsonb` không biến PostgreSQL thành schemaless database hoàn toàn.

### Middle

Biết query JSON operators và tạo index phù hợp access pattern.

### Senior

Đọc plans, đánh giá selectivity/write amplification và quyết định field nào nên promote thành column.

### Technical Lead / Architect

Định nghĩa boundary giữa relational core và flexible metadata để tránh “JSON blob architecture” không kiểm soát.

## 11. Key takeaway

- Dùng `jsonb` cho flexibility có chủ đích, không để né data modeling.
- Index phải theo query/operator/selectivity thực tế.
- Hot business fields thường xứng đáng có relational schema/index rõ ràng.

# 5. Modular Monolith boundaries: giữ một deployment nhưng tách ownership, dependency và transaction theo business modules

## 1. What is it?

Modular Monolith là một application deploy như một unit nhưng được chia thành các business modules có boundary rõ ràng.

Mental model:

```text
One deployable
+------------------------------------+
| Orders | Catalog | Billing | Users |
+------------------------------------+
   |         |         |
 explicit contracts, owned models/data
```

Điểm cốt lõi không phải folder `Modules/`. Boundary thật nằm ở:

- ownership của business capability;
- dependency direction;
- model/data access;
- transaction boundary;
- public/internal contracts.

## 2. Why does it exist?

Một layered monolith có thể bắt đầu đơn giản nhưng dần biến thành:

```text
mọi service gọi mọi repository
mọi module query mọi table
shared models lan toàn codebase
```

Microservices có thể tăng isolation nhưng thêm deployment, network, observability, consistency và DevOps cost. Modular Monolith là lựa chọn giữa: giữ operational simplicity của một deployment nhưng tạo structural boundaries đủ mạnh để codebase không thành big ball of mud.

## 3. How does it work?

Ví dụ modules:

```text
Catalog
  owns products/pricing model

Orders
  owns order lifecycle

Billing
  owns invoice/payment state
```

Orders không nên trực tiếp query `CatalogDbContext.Products` chỉ vì cùng process. Nó gọi contract/module API hoặc consume data được expose rõ ràng.

Internal communication có thể synchronous method call; không cần biến mọi module call thành message bus chỉ để “giống microservices”.

## 4. Practical implementation

Một contract đơn giản:

```csharp
public interface ICatalogQueries
{
    Task<ProductSnapshot?> GetProductAsync(
        ProductId productId,
        CancellationToken ct);
}
```

Orders chỉ reference Catalog contract, không reference Catalog persistence implementation.

At composition root:

```csharp
services.AddCatalogModule();
services.AddOrdersModule();
services.AddBillingModule();
```

Có thể dùng separate schemas/tables per module nếu data ownership cần rõ, nhưng không bắt buộc separate physical databases.

## 5. Real production scenario

Một e-commerce platform có 20 engineers. Microservices chưa cần vì team vẫn deploy cùng cadence và scale tương tự. Nhưng Orders thay đổi thường xuyên và Catalog có domain logic riêng.

Modular Monolith giúp teams review ownership, tránh Orders viết trực tiếp vào Catalog tables và giữ option extract module thành service sau này nếu operational requirements thực sự xuất hiện.

## 6. Failure scenario & troubleshooting

**Symptom** → module refactor nhỏ làm compile/test failures khắp system; database migration một module phá module khác.

**Evidence** → cross-module entity references, foreign-key writes từ nhiều modules, shared service layer với hàng trăm methods.

**Hypothesis** → logical modules tồn tại trên sơ đồ nhưng không có enforced dependency/data boundaries.

**Diagnosis** → dependency graph, database access audit, ownership map và transaction paths.

**Fix** → define contracts, remove cross-module persistence access, establish module-owned models và enforce references bằng project boundaries/tests.

**Verification** → thay implementation nội bộ module mà consumers không cần thay đổi ngoài contract.

## 7. Common mistakes

- Chỉ tạo folders theo module nhưng dùng chung toàn bộ entities/repositories.
- Copy microservice patterns như distributed messaging/network DTOs dù vẫn cùng process.
- Cho mọi module reference `SharedKernel` khổng lồ.
- Chia module theo technical layer thay vì business capability.
- Ép separate database per module dù transaction/application simplicity đang quan trọng hơn.

## 8. Alternatives

- Simple layered monolith: tốt hơn khi domain nhỏ và team nhỏ.
- Microservices: phù hợp khi cần independent deployment/scale/ownership/failure isolation đủ mạnh để trả operational cost.
- Vertical Slice Architecture: có thể complement modular boundaries ở use-case level.

## 9. Trade-offs

### Advantages

- Một deployment, một operational surface tương đối đơn giản.
- Boundary tốt hơn traditional coupled monolith.
- Có đường tiến hóa sang service extraction nếu cần.

### Costs / Risks

- Boundary enforcement cần discipline/tooling.
- Process/database sharing vẫn tạo một số shared failure modes.
- Có thể over-modularize domain đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business capability, không chỉ namespace.

### Middle

Implement use case trong module mà không bypass contract để query module khác.

### Senior

Thiết kế data ownership, transaction boundaries và cross-module integration phù hợp.

### Technical Lead / Architect

Quyết định khi monolith đủ tốt, khi modularization đủ, và dấu hiệu nào thực sự justify service extraction.

## 11. Key takeaway

- Modular Monolith tối ưu boundary mà chưa trả full distributed-system tax.
- Data/dependency ownership quan trọng hơn folder layout.
- Đừng dùng microservice mechanics trong-process nếu không có problem tương ứng.

# 6. Deadline propagation và timeout budgets: tránh mỗi service tự đặt timeout rồi cộng dồn thành latency không kiểm soát

## 1. What is it?

Timeout thường được đặt riêng cho từng dependency. Deadline là thời điểm cuối mà toàn operation còn giá trị.

Mental model:

```text
client gives total budget = 2s
        |
API uses 200ms
        |
remaining 1.8s
        |
service A gets remaining budget
        |
DB/API calls must fit inside it
```

Deadline propagation truyền remaining time budget xuống call chain thay vì mỗi layer tự khởi động một timeout độc lập.

## 2. Why does it exist?

Giả sử request có ba sequential dependencies, mỗi dependency timeout 5 giây. Worst case request có thể treo 15 giây hoặc lâu hơn khi có retries, dù caller chỉ sẵn sàng chờ 3 giây.

Independent timeouts không tạo end-to-end latency guarantee.

## 3. How does it work?

Caller xác định deadline/budget. Mỗi layer:

1. kiểm tra còn bao nhiêu thời gian;
2. không bắt đầu work nếu budget không đủ hợp lý;
3. truyền cancellation/deadline cho dependency;
4. dành margin cho response processing/cleanup.

Trong .NET có thể kết hợp request cancellation và timeout source:

```csharp
using var timeout = new CancellationTokenSource(remaining);
using var linked = CancellationTokenSource.CreateLinkedTokenSource(
    requestToken,
    timeout.Token);

await downstream.CallAsync(linked.Token);
```

Distributed protocols như gRPC hỗ trợ deadline semantics rõ hơn; HTTP custom APIs có thể truyền deadline header theo contract nội bộ.

## 4. Practical implementation

Một abstraction nhỏ:

```csharp
public sealed record RequestDeadline(DateTimeOffset ExpiresAt)
{
    public TimeSpan Remaining(TimeProvider clock)
        => ExpiresAt - clock.GetUtcNow();
}
```

Trước dependency call:

```csharp
var remaining = deadline.Remaining(clock);
if (remaining <= TimeSpan.FromMilliseconds(100))
    throw new TimeoutException("Insufficient request budget");

using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
cts.CancelAfter(remaining - TimeSpan.FromMilliseconds(50));

await inventory.GetAsync(id, cts.Token);
```

Margin cụ thể phải dựa trên system behavior, không copy magic number tùy tiện.

## 5. Real production scenario

Checkout API có client SLA 2.5 giây. Nó gọi Pricing, Inventory và Fraud. Mỗi service có timeout 2 giây và retry một lần. Khi Fraud chậm, checkout requests kéo dài 6–8 giây, giữ connections/threads/resources và tạo retry amplification.

Deadline propagation buộc downstream work nhận biết budget còn lại và dừng sớm khi outcome không còn hữu ích.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend timeout ở 3 giây nhưng backend traces tiếp tục chạy 10 giây.

**Evidence** → parent request span kết thúc; child dependency spans vẫn tiếp tục hoặc retries vượt client budget.

**Hypothesis** → cancellation/deadline không được propagate và timeout policies độc lập.

**Diagnosis** → inspect distributed traces, timeout settings và retry duration ở từng hop.

**Fix** → define total budget, propagate cancellation/deadline, cap retry by remaining time.

**Verification** → inject slow dependency và xác nhận backend work kết thúc trước/đúng budget, không có zombie calls.

## 7. Common mistakes

- Timeout mọi dependency cùng một con số mà không xét call graph.
- Retry sau khi remaining budget gần hết.
- Confuse timeout với cancellation semantics.
- Cancel sau irreversible side effect mà không có idempotency/reconciliation strategy.
- Chỉ timeout HTTP client nhưng DB/background work vẫn tiếp tục.
- Đặt timeout quá ngắn dựa trên p50 thay vì tail latency + SLO.

## 8. Alternatives

- Asynchronous workflow/queue khi operation không thể hoàn thành trong user-facing latency budget.
- Partial response/fallback khi business chấp nhận degraded dependency.
- Circuit Breaker để fail fast khi dependency đã known unhealthy; nó không thay thế deadline.

## 9. Trade-offs

### Advantages

- Giữ latency bounded theo caller expectation.
- Giảm wasted work khi request không còn giá trị.
- Hạn chế retry amplification.

### Costs / Risks

- Call chain cần shared deadline semantics.
- Timeout quá aggressive làm tăng false failures.
- Side-effecting operations cần idempotency/ambiguous-outcome handling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout giới hạn thời gian chờ một operation.

### Middle

Propagate `CancellationToken` và biết tránh retry vượt timeout.

### Senior

Thiết kế end-to-end budget dựa trên p95/p99, dependency graph và failure behavior.

### Technical Lead / Architect

Định nghĩa latency budget/SLO giữa services và quyết định operation nào phải synchronous, asynchronous hoặc degraded.

## 11. Key takeaway

- Per-hop timeout không đảm bảo end-to-end timeout.
- Remaining budget phải đi cùng request qua dependency chain.
- Retry, fallback và side effects đều phải tôn trọng deadline semantics.

# 7. Azure Storage Queue poison-message handling: retry hữu hạn, dequeue count và quarantine cho background processing đáng tin cậy

## 1. What is it?

Azure Storage Queue là queue đơn giản cho asynchronous work. Khi consumer nhận message, message bị invisible trong visibility timeout; nếu không delete trước khi timeout hết, nó có thể xuất hiện lại.

Mental model:

```text
producer -> queue -> consumer
                    |
                 process
                 /    \
             success  failure
               |        |
             delete   visible again
                        |
                   dequeue count++
```

Poison message là message liên tục fail do data/code/business condition và không thể thành công chỉ nhờ retry thêm.

## 2. Why does it exist?

Retry là cần thiết cho transient failures như network timeout. Nhưng malformed payload, missing business entity hoặc incompatible schema có thể fail mãi.

Nếu consumer retry vô hạn:

- waste compute;
- spam logs;
- giữ backlog;
- che real incident;
- có thể hammer downstream dependency.

## 3. How does it work?

Message metadata có `DequeueCount`. Consumer có thể định nghĩa threshold, ví dụ sau 5 attempts thì move/copy message sang poison queue và delete khỏi main queue.

Storage Queue không giống Azure Service Bus DLQ built-in semantics; poison handling thường cần application/trigger behavior cụ thể.

Azure Functions Queue trigger có poison queue behavior convention khi retries vượt limit, nhưng cần hiểu runtime/configuration thay vì assume mọi consumer tự động có DLQ.

## 4. Practical implementation

Custom worker pseudo-production flow:

```csharp
var message = await queue.ReceiveMessageAsync(
    visibilityTimeout: TimeSpan.FromMinutes(2),
    cancellationToken: ct);

if (message.Value is null)
    return;

try
{
    await processor.HandleAsync(message.Value.MessageText, ct);

    await queue.DeleteMessageAsync(
        message.Value.MessageId,
        message.Value.PopReceipt,
        ct);
}
catch (PermanentMessageException ex)
{
    await poisonQueue.SendMessageAsync(message.Value.MessageText, ct);
    await queue.DeleteMessageAsync(
        message.Value.MessageId,
        message.Value.PopReceipt,
        ct);
}
```

Transient/permanent classification cần domain knowledge; đừng coi mọi exception giống nhau.

## 5. Real production scenario

Image-processing worker nhận blob metadata. Một deploy thay schema từ `fileUrl` sang `blobName`, nhưng một batch messages cũ vẫn nằm trong queue. New worker deserialize fail mọi lần.

Nếu retry vô hạn, queue backlog không giảm. Poison queue giúp isolate incompatible messages để incident responder inspect/replay sau khi migration fix được triển khai.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng message ID/log payload fingerprint xuất hiện lặp lại, queue age tăng dù consumer vẫn active.

**Evidence** → `DequeueCount` cao, processing failure deterministic.

**Hypothesis** → permanent poison message hoặc handler bug đang retry như transient error.

**Diagnosis** → inspect payload/schema/version, exception type, dependency state và retry history.

**Fix** → quarantine sau threshold; sửa handler/data; provide controlled replay path.

**Verification** → poison messages không block main throughput; replay sau fix thành công và có audit trail.

## 7. Common mistakes

- Retry mọi exception vô hạn.
- Delete message trước khi business work hoàn tất.
- Không làm handler idempotent khi visibility timeout có thể dẫn tới duplicate processing.
- Đặt visibility timeout ngắn hơn normal processing duration.
- Poison queue nhưng không monitor/review nó.
- Replay hàng nghìn poison messages cùng lúc và tạo second incident.

## 8. Alternatives

- Azure Service Bus khi cần DLQ, sessions, richer settlement/routing semantics.
- Event Grid cho event notification patterns không cần queue-work semantics tương tự.
- Database job table cho low-scale workflows cần transactional coordination đơn giản.

## 9. Trade-offs

### Advantages

- Storage Queue đơn giản và cost-effective cho nhiều background jobs.
- Poison quarantine giữ main queue tiếp tục tiến.

### Costs / Risks

- Fewer broker features hơn Service Bus.
- Application phải sở hữu retry/idempotency/poison operational process.
- Visibility timeout cần tuning theo processing duration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu receive không đồng nghĩa message đã bị xóa vĩnh viễn.

### Middle

Implement delete-on-success, retry và poison threshold.

### Senior

Phân loại transient/permanent failures, idempotency và replay safety.

### Technical Lead / Architect

Chọn Storage Queue vs Service Bus dựa trên delivery/routing/operations requirements, không chỉ giá hoặc familiarity.

## 11. Key takeaway

- At-least-once behavior nghĩa consumer phải chịu được duplicate delivery.
- Poison messages cần bounded retry + quarantine + replay process.
- Queue đáng tin cậy là cả code lẫn operational workflow.

# 8. OpenTelemetry với RED metrics: kết nối request rate, errors, duration với traces thay vì nhìn dashboard rời rạc

## 1. What is it?

RED là một service-observability model:

```text
R = Rate      requests / second
E = Errors    error rate/count
D = Duration  latency distribution
```

OpenTelemetry cung cấp instrumentation model cho traces, metrics và logs correlation. RED metrics trả lời “service có khỏe không?”, traces giúp trả lời “latency/error đang nằm ở đâu?”.

## 2. Why does it exist?

Một dashboard có CPU, memory và request count nhưng không có latency percentiles/error rate thường không phản ánh user experience.

Ngược lại, có p99 cao mà không có trace context khiến engineer khó localize bottleneck giữa API, SQL, Redis hay downstream HTTP.

RED tạo entry point đơn giản cho service health rồi drill-down bằng telemetry chi tiết.

## 3. How does it work?

Request instrumentation tạo spans/metrics:

```text
HTTP request
  |
  +-> server span
       +-> SQL span
       +-> HTTP client span
       +-> Redis span

metrics:
request count
error count
latency histogram
```

Histogram buckets/distributions cho phép tính percentiles tốt hơn average. Trace ID kết nối events giữa components.

## 4. Practical implementation

ASP.NET Core setup ví dụ:

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation())
    .WithMetrics(metrics => metrics
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation());
```

Custom business metric nên có labels/tags cardinality kiểm soát:

```csharp
private static readonly Meter Meter = new("Orders");
private static readonly Counter<long> OrdersCreated =
    Meter.CreateCounter<long>("orders.created");

OrdersCreated.Add(1, new("channel", channel));
```

Không tag `userId`, `orderId`, raw URL IDs vào metrics nếu tạo unbounded cardinality.

## 5. Real production scenario

Sau deploy, checkout p99 tăng từ 800 ms lên 3 giây nhưng CPU không đổi. RED dashboard cho thấy rate ổn, errors thấp, duration tail tăng.

Trace samples từ slow requests cho thấy SQL dependency span tăng, và Query Store sau đó chỉ ra execution plan regression. Observability flow đi từ symptom → traces → database evidence thay vì đoán “App Service thiếu CPU”.

## 6. Failure scenario & troubleshooting

**Symptom** → monitoring bill tăng mạnh, backend telemetry chậm hoặc metrics backend có hàng triệu series.

**Evidence** → metric dimensions chứa order ID/user ID/full URL; cardinality explode.

**Hypothesis** → telemetry data model sai, dùng metrics như logs.

**Diagnosis** → inspect top dimensions/series count và collector/exporter queue.

**Fix** → giữ low-cardinality dimensions cho metrics; chuyển high-cardinality context sang traces/logs.

**Verification** → series count ổn định, RED dashboard vẫn đủ phân đoạn hữu ích.

## 7. Common mistakes

- Chỉ log text mà không có metrics/traces.
- Dùng average latency thay p95/p99.
- Tag metric bằng IDs không bounded.
- Alert trực tiếp trên raw noisy metric thay SLO/burn-rate hoặc meaningful threshold.
- Collect mọi trace 100% ở traffic cao mà không xét sampling/cost.
- Instrument nhưng không có runbook/dashboard linking telemetry.

## 8. Alternatives

- Vendor-native telemetry như Application Insights vẫn có thể triển khai RED model.
- Prometheus/Grafana cho metrics-centric stack.
- Structured logs có thể đủ cho small systems nhưng không thay distributed tracing khi dependency graph phức tạp.

## 9. Trade-offs

### Advantages

- RED tập trung vào user-visible service behavior.
- OpenTelemetry giảm vendor-specific instrumentation coupling.
- Trace + metric correlation rút ngắn localization time.

### Costs / Risks

- Telemetry volume/cost có thể lớn.
- Collector/exporter trở thành operational component.
- Poor cardinality/sampling design làm hệ thống observability tự trở thành bottleneck.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu logs, metrics, traces trả lời các loại câu hỏi khác nhau.

### Middle

Đọc rate/errors/p95-p99 và follow trace qua dependencies.

### Senior

Thiết kế dimensions, sampling và incident workflow symptom → evidence → root cause.

### Technical Lead / Architect

Đặt observability standards, SLOs, retention/cost budgets và ownership của dashboards/alerts/runbooks.

## 11. Key takeaway

- Bắt đầu service health bằng Rate, Errors, Duration.
- Metrics chỉ ra “có vấn đề”; traces thường giúp chỉ ra “vấn đề nằm ở đâu”.
- Cardinality và telemetry cost phải được thiết kế như production capacity concern.

# 9. Playwright test isolation: giảm flaky E2E bằng deterministic data, independent state và observable waits

## 1. What is it?

Test isolation nghĩa mỗi test có thể chạy độc lập, song song và theo thứ tự bất kỳ mà không phụ thuộc state do test khác tạo ra.

Mental model:

```text
Test A -> own data/state -> cleanup or unique namespace
Test B -> own data/state -> cleanup or unique namespace

A does not prepare B
B does not depend on A order
```

Trong Playwright, isolation còn bao gồm browser context, cookies/session và explicit readiness conditions.

## 2. Why does it exist?

E2E tests hay flaky vì phụ thuộc:

- shared account/data;
- execution order;
- fixed sleeps;
- background async work chưa xong;
- environment pollution;
- selector phụ thuộc layout/text không ổn định.

Flaky suite làm team mất trust. Khi test fail “thử rerun là xanh”, CI signal gần như mất giá trị.

## 3. How does it work?

Playwright tạo BrowserContext isolation tốt cho browser state. Nhưng backend/database state vẫn cần strategy.

Thay vì:

```ts
await page.waitForTimeout(3000);
```

hãy wait trên observable condition:

```ts
await expect(page.getByTestId('order-status'))
  .toHaveText('Approved');
```

Test data có thể được tạo qua API fixture thay vì click qua 15 UI steps chỉ để setup prerequisite.

## 4. Practical implementation

Fixture tạo unique customer:

```ts
import { test as base, expect } from '@playwright/test';

const test = base.extend<{ customerId: string }>({
  customerId: async ({ request }, use) => {
    const response = await request.post('/test-support/customers', {
      data: { name: `e2e-${crypto.randomUUID()}` }
    });

    const customer = await response.json();
    await use(customer.id);
  }
});
```

UI test chỉ validate behavior cần thiết:

```ts
test('approves customer', async ({ page, customerId }) => {
  await page.goto(`/customers/${customerId}`);
  await page.getByRole('button', { name: 'Approve' }).click();
  await expect(page.getByTestId('status')).toHaveText('Approved');
});
```

## 5. Real production scenario

CI chạy 80 Playwright tests parallel. 10 tests dùng chung account `qa@example.com` và sửa profile/settings. Từng test pass khi chạy riêng nhưng fail ngẫu nhiên khi parallel.

Tăng retry chỉ che race. Fix là unique test state hoặc immutable/shared read-only fixture, cùng deterministic cleanup/reset strategy.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail ngẫu nhiên ở CI nhưng local rerun pass.

**Evidence** → screenshot/trace cho thấy data/state khác expected; fixed wait đôi khi chưa đủ; test chạy cạnh test khác cùng entity.

**Hypothesis** → shared state hoặc race với async backend/UI readiness.

**Diagnosis** → bật trace/video cho failure, chạy repeated/parallel, inspect network calls và test-data ownership.

**Fix** → isolate data/context, replace sleeps bằng observable waits, stabilize selectors và seed deterministic prerequisites.

**Verification** → run suite nhiều lần với high parallelism và zero retries để đo real flake rate.

## 7. Common mistakes

- `waitForTimeout` khắp suite.
- Test B phụ thuộc Test A tạo data.
- Dùng một admin account cho mọi mutating test.
- Retry 3 lần rồi coi flakiness đã được giải quyết.
- Dùng brittle CSS selectors theo layout.
- Dùng E2E để kiểm tra mọi branch mà unit/integration test làm tốt hơn.

## 8. Alternatives

- API integration tests cho backend contracts nhanh và deterministic hơn.
- Component tests cho UI behavior hẹp.
- Unit tests cho pure business logic.

E2E nên tập trung critical user journeys và integration boundaries thực sự cần browser.

## 9. Trade-offs

### Advantages

- Isolated tests chạy parallel đáng tin hơn.
- Failure diagnosis rõ hơn khi mỗi test sở hữu state riêng.

### Costs / Risks

- Test-support APIs/fixtures cần governance để không leak production behavior.
- Data setup/cleanup có engineering cost.
- Full browser tests vẫn chậm hơn lower-level tests.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết dùng locators/waits thay fixed sleep khi có thể.

### Middle

Tạo independent test data và đọc Playwright traces/screenshots.

### Senior

Thiết kế test pyramid theo risk, xử lý backend async state và giảm flake systematic.

### Technical Lead / Architect

Đặt CI reliability target, test-data architecture và quy định khi nào E2E là đúng level thay vì thêm test vì coverage cảm tính.

## 11. Key takeaway

- Flaky test thường là nondeterministic state/timing problem, không phải lý do để thêm retry vô hạn.
- Wait trên observable condition, không wait theo thời gian đoán.
- E2E ít nhưng đáng tin có giá trị hơn suite lớn mà team không tin kết quả.

# 10. Optimizely CMS content cache & invalidation: cache content nhanh nhưng phải hiểu publishing, dependency và multi-instance invalidation

## 1. What is it?

CMS read workloads thường có tỷ lệ đọc cao và nội dung thay đổi ít hơn request traffic. Vì vậy content platform như Optimizely CMS tận dụng caching để tránh load/reconstruct cùng content cho mỗi request.

Mental model tổng quát:

```text
Editor publishes content
        |
content repository changes
        |
cache invalidation event
        |
web instances invalidate/update
        |
next request rebuilds/caches fresh content
```

Cache chỉ đúng khi invalidation phản ánh content dependency thực tế.

## 2. Why does it exist?

Một marketing page có thể dùng:

- page content;
- shared header/footer blocks;
- campaign blocks;
- navigation tree;
- personalization/search-derived components.

Nếu mọi request đều truy vấn CMS storage và build toàn cây content, latency và backend load tăng. Caching giúp scale read-heavy traffic, đặc biệt sau CDN vẫn có nhiều dynamic/authenticated requests hit origin.

## 3. How does it work?

CMS cache có thể gồm nhiều tầng:

```text
Browser/CDN cache
      |
ASP.NET output/fragment cache
      |
CMS content object cache
      |
content database/storage
```

Publishing một block dùng ở 200 pages có thể yêu cầu invalidation ở nhiều derived views. Dependency invalidation quan trọng hơn chỉ TTL.

Trong multi-instance deployment, cache invalidation phải propagate giữa instances; nếu chỉ clear local memory cache, users có thể thấy content khác nhau tùy instance.

## 4. Practical implementation

Application code nên dùng CMS content APIs/cache abstractions thay vì tự bypass repository với ad-hoc SQL.

Một fragment cache key cần gắn với content version/language/variation nếu output phụ thuộc chúng:

```csharp
var key = $"hero:{content.ContentGuid}:{content.Language.Name}:{contentVersion}";
```

Nếu output còn phụ thuộc user segment, market hoặc personalization context, key phải phản ánh variation đó hoặc fragment không nên cache ở level đó.

Quan trọng hơn code snippet là ownership: component nào biết dependency và ai invalidates khi editor publish.

## 5. Real production scenario

Global header là shared block xuất hiện toàn site. Editor đổi campaign link và publish. Một App Service instance hiển thị link mới, instance khác vẫn giữ local cached rendered fragment cũ 20 phút.

CMS content object cache đã invalidated đúng nhưng custom application fragment cache không subscribe dependency/invalidation event. Bug nằm ở cache layer tự thêm, không phải publishing.

## 6. Failure scenario & troubleshooting

**Symptom** → editor thấy published content nhưng end users ngẫu nhiên nhận version cũ.

**Evidence** → response khác nhau theo instance; direct content API trả version mới; custom cache key vẫn hit.

**Hypothesis** → stale application/CDN cache hoặc invalidation không propagate.

**Diagnosis** → trace từng cache layer: CDN headers, output cache, custom cache, CMS cache; correlate publish timestamp với invalidation logs.

**Fix** → correct dependency-based invalidation, distributed invalidation hoặc giảm/remove cache layer không cần thiết.

**Verification** → publish test content và xác nhận tất cả instances/regions thấy version mới trong expected freshness SLA.

## 7. Common mistakes

- Thêm cache ở mọi layer mà không biết layer nào sở hữu freshness.
- Cache key không chứa language/market/personalization dimension.
- Clear local memory cache nhưng app chạy nhiều instances.
- Dùng TTL dài để che expensive rendering mà không có invalidation.
- Purge toàn site cho mỗi content publish, tạo origin thundering herd.
- Đổ lỗi “CMS cache” trước khi phân biệt CDN/output/custom/content cache.

## 8. Alternatives

- CDN caching cho public pages/assets khi HTTP cache semantics phù hợp.
- ASP.NET Core output caching cho whole response/endpoint-specific workloads.
- No custom cache nếu CMS native cache đã đủ và render cost thấp.
- Pre-render/static generation cho một số marketing experiences có publishing workflow phù hợp.

## 9. Trade-offs

### Advantages

- Giảm content-store load và render latency.
- Tăng origin throughput cho read-heavy sites.
- Shared content có thể được phục vụ rất nhanh.

### Costs / Risks

- Invalidation complexity tăng nhanh với shared blocks/personalization/multi-instance.
- Nhiều cache layers làm stale-data diagnosis khó.
- Purge quá rộng gây load spikes.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu published content có thể đi qua nhiều cache trước khi đến user.

### Middle

Biết thiết kế cache key theo content/language context và debug stale cache layer.

### Senior

Thiết kế dependency invalidation, multi-instance propagation và freshness-vs-performance trade-off.

### Technical Lead / Architect

Quyết định layer nào thực sự cần cache, freshness SLA, CDN/CMS/app ownership và operational strategy khi publish hoặc purge lớn.

## 11. Key takeaway

- CMS caching không chỉ là TTL; publishing dependency và invalidation mới quyết định correctness.
- Multi-instance system cần invalidation semantics vượt local memory.
- Mỗi cache layer thêm performance benefit nhưng cũng thêm một stale-data failure mode.
