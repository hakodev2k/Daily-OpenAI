# 1. .NET Large Object Heap: allocation pressure, Gen 2 GC và pooling judgment

## 1. What is it?

Large Object Heap (LOH) là vùng managed heap mà CLR dùng cho các object lớn. Mental model quan trọng không phải “object lớn nằm ở heap khác”, mà là: **allocation shape có thể thay đổi chi phí Garbage Collection của toàn process**. Những buffer lớn, arrays lớn và serialization payloads có thể khiến GC pressure tăng mạnh dù application không có memory leak.

## 2. Why does it exist?

Di chuyển object lớn trong quá trình compact rất tốn CPU và memory bandwidth. CLR vì vậy xử lý large objects khác với phần lớn small objects. Điều này tối ưu trường hợp bình thường nhưng tạo trade-off: workload liên tục allocate rồi bỏ các buffers lớn có thể khiến Gen 2 collections, fragmentation và pause cost trở thành vấn đề production.

## 3. How does it work?

```text
Request
  │
  ├─ allocate small objects ─► Gen 0/1
  │
  └─ allocate large buffer ──► LOH
                                 │
                                 ▼
                            Gen 2 GC pressure
```

LOH gắn với full/Gen 2 collection behavior. Vì vậy “object đã hết reference” không có nghĩa memory lập tức trả về OS. GC chỉ reclaim khi collection phù hợp xảy ra; process working set còn chịu ảnh hưởng của allocator và runtime.

## 4. Practical implementation

Thay vì tạo buffer lớn cho mỗi operation:

```csharp
var buffer = new byte[1024 * 1024];
await stream.ReadExactlyAsync(buffer, ct);
```

có thể dùng pool khi profiling chứng minh allocation là bottleneck:

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(1024 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, 1024 * 1024), ct);
    Process(buffer.AsSpan(0, read));
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

Pooling là ownership contract: buffer sau `Return` không còn thuộc caller.

## 5. Real production scenario

File-processing API đọc mỗi upload 8 MB vào `byte[]`, sau đó base64-encode và serialize thêm một copy. Traffic tăng khiến memory saw-tooth lớn, Gen 2 GC thường xuyên và p99 latency tăng dù CPU business logic thấp.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng theo burst, GC pause và p99 tăng.  
**Evidence** → allocation profile cho thấy large arrays chiếm phần lớn bytes allocated; Gen 2 collections tăng.  
**Hypothesis** → large transient allocations gây LOH pressure.  
**Diagnosis** → dùng `dotnet-counters`, allocation profiler hoặc dump để phân biệt retained objects với allocation churn.  
**Fix** → streaming, giảm copies, reuse/pool buffers khi hợp lý.  
**Verification** → bytes allocated/request, Gen 2 frequency và tail latency giảm dưới cùng load.

## 7. Common mistakes

Gọi mọi memory growth là leak; pool mọi array trước khi đo; giữ pooled buffer trong async work sau khi đã `Return`; dùng `ToArray()` nhiều lần; load toàn file vào memory khi có thể stream.

## 8. Alternatives

Streaming thường tốt hơn pooling nếu dữ liệu có thể xử lý tuần tự. `Memory<T>`/`Span<T>` giúp giảm copies nhưng không tự giải quyết lifetime. Pooling phù hợp reusable temporary buffers có size và ownership rõ.

## 9. Trade-offs

### Advantages

Giảm allocation churn có thể giảm GC CPU, memory pressure và tail latency.

### Costs / Risks

Pooling tăng ownership complexity, giữ memory lâu hơn và dễ gây data corruption nếu reuse sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu GC quản lý lifetime, không phải mọi allocation đều có chi phí giống nhau.

### Middle

Biết đo allocation và tránh unnecessary copies.

### Senior

Phân biệt leak, retained memory và allocation churn; đánh giá streaming vs pooling.

### Technical Lead / Architect

Thiết kế payload/file-processing boundary để memory usage tăng theo bounded concurrency thay vì payload size × request concurrency.

## 11. Key takeaway

- LOH problem thường là allocation pattern problem, không nhất thiết là leak.
- Đo allocation và GC trước khi thêm pooling complexity.
- Streaming thường là architectural fix tốt hơn việc chỉ tối ưu allocator.

# 2. ASP.NET Core response streaming: giảm buffering nhưng thay đổi failure contract

## 1. What is it?

Response streaming gửi dữ liệu dần về client thay vì materialize toàn bộ response trước khi bắt đầu transmission. Mental model: **streaming đổi boundary từ “compute xong rồi trả” thành pipeline sống giữa producer và network**.

## 2. Why does it exist?

Large exports, event feeds hoặc file downloads có thể tốn memory và tăng time-to-first-byte nếu application buffer toàn bộ dữ liệu. Streaming giảm peak memory và cho client nhận dữ liệu sớm hơn.

## 3. How does it work?

```text
Database/API producer
      │ batches
      ▼
ASP.NET Core endpoint
      │ flush/write
      ▼
Kestrel / proxy
      │ chunks
      ▼
Client
```

Một khi response headers/body đã bắt đầu, server không còn tự do đổi sang một clean `500 ProblemDetails` như trước khi response start. Failure semantics vì vậy thay đổi.

## 4. Practical implementation

```csharp
app.MapGet("/export", async (HttpResponse response, AppDbContext db, CancellationToken ct) =>
{
    response.ContentType = "application/x-ndjson";

    await foreach (var row in db.Orders
        .AsNoTracking()
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        await JsonSerializer.SerializeAsync(response.Body, row, cancellationToken: ct);
        await response.WriteAsync("\n", ct);
    }
});
```

Cần propagate cancellation khi client disconnect và tránh unbounded producer buffering.

## 5. Real production scenario

Admin export 500.000 orders. Buffering thành `List<T>` rồi serialize tạo hàng trăm MB allocations. Streaming từng record giảm memory nhưng database connection có thể bị giữ lâu hơn, nên concurrency phải được kiểm soát.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận file nửa chừng rồi connection đóng, không có JSON error.  
**Evidence** → exception xảy ra sau `Response.HasStarted == true`.  
**Hypothesis** → streaming pipeline fail giữa response.  
**Diagnosis** → correlate request trace với downstream/database error và bytes sent.  
**Fix** → format có framing/checkpoint phù hợp, validate sớm, bounded retries trước khi stream bắt đầu; không giả vờ có thể rollback bytes đã gửi.  
**Verification** → injected mid-stream failure tạo observable partial-result behavior đúng contract.

## 7. Common mistakes

Gọi `ToListAsync()` trước rồi mới “stream”; flush mỗi byte; bỏ `CancellationToken`; giữ transaction dài suốt download; assume middleware có thể luôn đổi exception thành `ProblemDetails`.

## 8. Alternatives

Generate file asynchronously rồi upload Blob Storage phù hợp exports rất lớn. Pagination phù hợp interactive APIs. Streaming trực tiếp phù hợp khi producer có thể cung cấp incremental data và client hiểu partial-failure semantics.

## 9. Trade-offs

### Advantages

Lower peak memory, faster first byte, phù hợp large datasets.

### Costs / Risks

Connection/resource lifetime dài hơn, retry khó hơn và failure contract phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu buffering vs streaming.

### Middle

Implement async streaming và cancellation.

### Senior

Reason về backpressure, connection lifetime và partial failures.

### Technical Lead / Architect

Quyết định direct stream hay asynchronous export dựa trên payload size, concurrency, resumability và operational cost.

## 11. Key takeaway

- Streaming tối ưu memory nhưng không miễn phí.
- Response đã bắt đầu thì error handling contract thay đổi.
- Large export thường cần đánh giá async job + Blob Storage như một alternative.

# 3. EF Core split queries: Cartesian explosion, round trips và consistency window

## 1. What is it?

Split query cho phép EF Core load một object graph bằng nhiều SQL queries thay vì một JOIN query lớn. Mental model: đây là trade-off giữa **result-set duplication** và **nhiều database round trips/consistency window**.

## 2. Why does it exist?

Khi include nhiều collection siblings, JOIN có thể nhân rows. Một order có 20 lines và 10 tags có thể tạo 200 joined rows dù domain chỉ có 30 child objects.

## 3. How does it work?

```text
Single query:
Orders × Lines × Tags → duplicated rows

Split query:
Query Orders
Query Lines for Orders
Query Tags for Orders
→ EF materializes graph
```

EF Core identity resolution/materialization ghép dữ liệu thành entities. Split query giảm network payload duplication nhưng queries xảy ra ở các thời điểm khác nhau.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Include(x => x.Lines)
    .Include(x => x.Tags)
    .AsSplitQuery()
    .Where(x => x.CustomerId == customerId)
    .ToListAsync(ct);
```

Không chọn `AsSplitQuery()` theo thói quen; đo SQL shape, row counts và latency.

## 5. Real production scenario

CMS page load include blocks, assets và personalization rules. Single JOIN trả hàng chục nghìn rows cho vài chục logical objects. Split query giảm bytes transferred đáng kể, nhưng database latency cao có thể khiến tổng round-trip time tăng.

## 6. Failure scenario & troubleshooting

**Symptom** → query chuyển sang split thì memory giảm nhưng latency tăng.  
**Evidence** → dependency telemetry cho thấy 4 SQL calls thay vì 1; mỗi call chịu network latency.  
**Hypothesis** → round-trip cost lớn hơn duplication savings.  
**Diagnosis** → compare generated SQL, rows, bytes và duration.  
**Fix** → projection, reshape query hoặc quay lại single query nếu dataset phù hợp.  
**Verification** → benchmark representative cardinalities, không chỉ local DB.

## 7. Common mistakes

`Include` toàn graph; nghĩ split query luôn nhanh hơn; bỏ qua data consistency giữa các queries; không projection DTO cho read use case; benchmark với database localhost.

## 8. Alternatives

Projection thường tốt nhất khi endpoint chỉ cần subset fields. Explicit separate queries cho control cao hơn. Single query phù hợp graph nhỏ và network round trips đắt.

## 9. Trade-offs

### Advantages

Giảm Cartesian explosion và duplicated payload.

### Costs / Risks

Nhiều round trips, consistency window rộng hơn và query orchestration phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` biến thành database access, không phải object magic.

### Middle

Inspect generated SQL và dùng `AsSplitQuery` có chủ đích.

### Senior

Đánh giá cardinality, round trips và consistency requirement.

### Technical Lead / Architect

Định nghĩa read-model strategy thay vì để aggregate graph tự quyết API query shape.

## 11. Key takeaway

- Split query giải quyết một access-shape problem, không phải universal optimization.
- Projection thường đơn giản và hiệu quả hơn cho API reads.
- Luôn đo với realistic network và cardinality.

# 4. SQL Server statistics: cardinality estimation, plan regression và parameter-sensitive workload

## 1. What is it?

Statistics mô tả phân phối dữ liệu để optimizer ước lượng số rows. Mental model: optimizer không “biết” data thực tại compile time; nó dùng estimates để chọn join algorithm, access path và memory grant.

## 2. Why does it exist?

Một query có nhiều execution strategies. Nếu expected rows là 5, index seek + nested loops có thể tốt; nếu là 5 triệu, scan/hash join có thể tốt hơn. Cost-based optimizer cần cardinality estimates để quyết định.

## 3. How does it work?

```text
SQL + parameters
      ↓
Statistics / cardinality estimate
      ↓
Cost alternatives
      ↓
Execution plan
      ↓
I/O + CPU + memory + locks → latency
```

Data distribution thay đổi hoặc parameter values rất lệch có thể khiến một cached plan không phù hợp cho mọi execution.

## 4. Practical implementation

Query có skew:

```sql
SELECT Id, Status, CreatedAt
FROM Orders
WHERE TenantId = @TenantId
  AND Status = @Status;
```

Tenant nhỏ có 100 rows, tenant lớn có 20 triệu rows. Senior investigation phải so estimated vs actual rows trong execution plan thay vì chỉ nhìn index names.

## 5. Real production scenario

Sau bulk import, API p95 tăng đột ngột. Code không đổi. Execution plan cho endpoint chuyển từ seek strategy sang plan có memory spill do estimates lệch với distribution mới.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng query đôi lúc 30 ms, đôi lúc 8 s.  
**Evidence** → Query Store cho nhiều runtime profiles; actual vs estimated rows lệch lớn.  
**Hypothesis** → stale statistics hoặc parameter-sensitive plan.  
**Diagnosis** → inspect Query Store, actual plan, stats freshness và data skew.  
**Fix** → cập nhật statistics khi phù hợp, cải thiện index/query shape hoặc dùng engine features/targeted plan strategy; tránh blanket hints.  
**Verification** → test nhiều representative parameter distributions.

## 7. Common mistakes

“Add index” ngay; rebuild mọi index như routine fix; chỉ test một tenant; force plan vĩnh viễn mà không hiểu data evolution; nhìn average duration thay vì distribution.

## 8. Alternatives

Query rewrite, filtered indexes hoặc data partitioning có thể phù hợp tùy access pattern. Plan forcing là operational mitigation, không luôn là structural fix.

## 9. Trade-offs

### Advantages

Statistics cho phép optimizer thích nghi mà application không hard-code access strategy.

### Costs / Risks

Estimates không hoàn hảo; data skew và stale information có thể tạo plan regression.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không tự đảm bảo query nhanh.

### Middle

Đọc estimated/actual rows và basic execution plan.

### Senior

Reason từ distribution → estimate → plan → I/O/memory → latency.

### Technical Lead / Architect

Thiết kế observability/Query Store practice để plan regression là measurable incident, không phải đoán mò.

## 11. Key takeaway

- Optimizer quyết định dựa trên estimates.
- Data skew có thể quan trọng hơn query text.
- Performance diagnosis cần execution evidence, không phải index folklore.

# 5. MongoDB document modeling: embedding vs referencing theo access pattern

## 1. What is it?

MongoDB modeling quyết định dữ liệu nào nằm chung document và dữ liệu nào được reference. Mental model đúng: document boundary nên phản ánh **data được đọc/ghi cùng nhau và consistency cần giữ cùng nhau**, không phải chỉ chuyển relational tables thành collections.

## 2. Why does it exist?

Document database cho phép aggregate dữ liệu liên quan để một read lấy đủ information mà không join nhiều resources. Nhưng embedding không giới hạn sẽ tạo large documents, write amplification và ownership ambiguity.

## 3. How does it work?

```text
Embedded:
Order { customerSnapshot, lines[] }

Referenced:
Product ── productId ──► Reviews collection
```

Embedding ưu tiên locality. Referencing ưu tiên independent lifecycle, high cardinality hoặc reuse.

## 4. Practical implementation

```csharp
public sealed class OrderDocument
{
    public ObjectId Id { get; init; }
    public string CustomerId { get; init; } = default!;
    public CustomerSnapshot Customer { get; init; } = default!;
    public List<OrderLine> Lines { get; init; } = [];
}
```

Customer snapshot trong order có thể intentionally denormalized để lịch sử order không đổi khi customer profile thay đổi.

## 5. Real production scenario

Product reviews tăng hàng triệu entries. Embed reviews vào product document là boundary sai: product read không cần toàn bộ reviews, reviews có independent pagination và write rate cao.

## 6. Failure scenario & troubleshooting

**Symptom** → product updates chậm dần và document size tăng mạnh.  
**Evidence** → embedded array tăng không giới hạn; write payload và document relocation tăng.  
**Hypothesis** → unbounded one-to-many bị embed.  
**Diagnosis** → inspect document-size distribution và query patterns.  
**Fix** → tách high-cardinality children thành collection riêng, giữ summary cần đọc thường xuyên.  
**Verification** → bounded document size và predictable query latency.

## 7. Common mistakes

Model MongoDB như SQL không join; embed mọi thứ; normalize mọi thứ; bỏ index vì “document lookup nhanh”; không thiết kế theo query/write patterns.

## 8. Alternatives

Relational database phù hợp complex relational integrity và ad-hoc joins. Cosmos DB cũng document-oriented nhưng partition/RU model tạo thêm constraints. MongoDB referencing phù hợp khi lifecycle độc lập.

## 9. Trade-offs

### Advantages

Embedding đúng boundary giảm round trips và giữ related state atomic trong document.

### Costs / Risks

Denormalization tạo duplication; unbounded embedding gây size/write problems.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu document không phải table row có JSON syntax.

### Middle

Model bounded aggregates và indexes theo queries.

### Senior

Đánh giá cardinality, update frequency, duplication và consistency.

### Technical Lead / Architect

Chọn datastore/model theo workload thay vì theo khẩu hiệu SQL vs NoSQL.

## 11. Key takeaway

- Model theo access pattern và lifecycle.
- Embed bounded data thường được dùng cùng nhau.
- Unbounded child collections thường cần boundary riêng.

# 6. Modular Monolith: module boundary, data ownership và đường tiến hóa trước Microservices

## 1. What is it?

Modular Monolith là một deployable application nhưng chia thành modules có business boundaries rõ, dependency rules và ownership. Nó không phải “monolith có nhiều folders”; mục tiêu là **change isolation bên trong một deployment unit đơn giản**.

## 2. Why does it exist?

Một codebase có thể cần strong domain boundaries nhưng chưa cần network, independent deployment và operational overhead của Microservices. Modular Monolith giữ transaction/deployment đơn giản trong khi chống accidental coupling.

## 3. How does it work?

```text
Single deployment
┌─────────────────────────────┐
│ Orders Module               │
│  API → Application → Domain │
├─────────────────────────────┤
│ Catalog Module              │
├─────────────────────────────┤
│ Identity Module             │
└─────────────────────────────┘
       explicit contracts
```

Module A không nên query thẳng internal tables/classes của Module B chỉ vì cùng process.

## 4. Practical implementation

```csharp
public interface ICatalogQueries
{
    Task<ProductSummary?> GetProductAsync(Guid id, CancellationToken ct);
}

// Orders depends on a narrow module contract, not CatalogDbContext.
public sealed class CreateOrderHandler(ICatalogQueries catalog) { /* ... */ }
```

Boundary tests/static analysis có thể enforce forbidden references.

## 5. Real production scenario

E-commerce team có Orders, Catalog và Content. Scale hiện tại chỉ cần một App Service. Tách thành 12 Microservices sẽ thêm CI/CD, telemetry, retries, auth và network failures mà chưa có business benefit.

## 6. Failure scenario & troubleshooting

**Symptom** → “modules” không thể thay đổi độc lập vì mọi module đọc database tables của nhau.  
**Evidence** → cross-module DbContext/entity references dày đặc.  
**Hypothesis** → directory separation nhưng không có ownership boundary.  
**Diagnosis** → dependency graph và schema access review.  
**Fix** → explicit contracts, ownership, domain events/internal messaging khi phù hợp.  
**Verification** → module changes không cần sửa internals của module khác.

## 7. Common mistakes

Mỗi module thành generic repository layer; dùng MediatR rồi gọi mọi handler xuyên module; shared `Common` project chứa toàn domain; coi database schema chung là permission đọc mọi table.

## 8. Alternatives

Layered Monolith đơn giản hơn cho domain nhỏ. Microservices phù hợp khi independent scaling/deployment/team ownership thực sự tạo giá trị. Modular Monolith thường là intermediate architecture tốt nhưng không bắt buộc.

## 9. Trade-offs

### Advantages

Operational simplicity, local transactions, refactoring dễ hơn networked services.

### Costs / Risks

Boundary discipline cần enforcement; process failure vẫn ảnh hưởng toàn deployment; independent scaling hạn chế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là responsibility boundary.

### Middle

Implement contract mà không bypass internals.

### Senior

Reason về data ownership, transaction boundary và coupling.

### Technical Lead / Architect

Quyết định khi nào module nên remain in-process và bằng chứng nào đủ để extract thành service.

## 11. Key takeaway

- Architecture boundary không đồng nghĩa deployment boundary.
- Modular Monolith có thể cung cấp strong boundaries với operations đơn giản.
- Chỉ extract Microservice khi independent deployment/scaling/ownership đáng giá.

# 7. Azure Functions concurrency: scale-out, downstream pressure và idempotent processing

## 1. What is it?

Azure Functions có thể xử lý nhiều invocations đồng thời trong một instance và scale ra nhiều instances. Mental model: **serverless scale không tạo capacity cho downstream**; nó chỉ tăng số workers có khả năng gọi downstream nhanh hơn.

## 2. Why does it exist?

Event-driven workloads có burst. Platform cần tăng consumers để giảm backlog. Nhưng nếu SQL, third-party API hoặc storage có giới hạn thấp hơn, uncontrolled concurrency biến scale-out thành overload amplifier.

## 3. How does it work?

```text
Service Bus backlog
       │
       ▼
Functions scale controller
   ┌───┼────┐
   ▼   ▼    ▼
 Inst Inst Inst
   └───┼────┘
       ▼
   SQL / external API
```

At-least-once messaging nghĩa duplicate execution vẫn phải được coi là normal failure condition.

## 4. Practical implementation

Handler cần cancellation, idempotency và bounded downstream behavior:

```csharp
public async Task ProcessAsync(OrderMessage message, CancellationToken ct)
{
    if (await inbox.ExistsAsync(message.MessageId, ct)) return;

    await downstream.SendAsync(message.OrderId, ct);
    await inbox.MarkProcessedAsync(message.MessageId, ct);
}
```

Trong production, atomicity giữa side effect và inbox state phải được thiết kế theo dependency capabilities.

## 5. Real production scenario

Campaign tạo 200.000 notification messages. Functions scale nhanh, nhưng vendor API chỉ cho 500 requests/second. Nếu không throttle, 429 responses kích hoạt retries và backlog tăng thay vì giảm.

## 6. Failure scenario & troubleshooting

**Symptom** → instance count tăng đồng thời downstream 429/SQL timeout tăng.  
**Evidence** → queue backlog, concurrency và dependency failures correlated.  
**Hypothesis** → consumer throughput vượt downstream capacity.  
**Diagnosis** → đo arrival rate, processing rate, downstream quota và retry volume.  
**Fix** → tune concurrency, backoff/jitter, rate limiting hoặc buffer boundary.  
**Verification** → backlog drain ổn định mà dependency error rate không tăng.

## 7. Common mistakes

Cho rằng autoscale luôn cải thiện throughput; retry ngay lập tức; không idempotency; xử lý poison message vô hạn; không monitor queue age.

## 8. Alternatives

Worker Service/Container Apps phù hợp khi cần kiểm soát process/concurrency rõ. App Service background worker phù hợp workload nhỏ nhưng scale semantics phải hiểu. Logic Apps phù hợp orchestration integration-centric.

## 9. Trade-offs

### Advantages

Elastic event processing và giảm infrastructure management.

### Costs / Risks

Scale behavior, cold starts, quotas và downstream protection trở thành architectural concerns.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trigger không đồng nghĩa exactly-once.

### Middle

Implement idempotent handler, retries và DLQ handling.

### Senior

Tune concurrency theo downstream capacity và telemetry.

### Technical Lead / Architect

Chọn compute model dựa trên workload shape, ownership, cost và failure propagation.

## 11. Key takeaway

- Autoscale có thể khuếch đại downstream failure.
- Consumer concurrency phải gắn với dependency capacity.
- Idempotency là requirement, không phải optional optimization.

# 8. IIS Application Pool recycling: process lifetime, in-memory state và graceful recovery

## 1. What is it?

Application Pool trong IIS quản lý worker process chạy application. Recycling thay worker process theo configuration hoặc operational event. Mental model: **web process là disposable compute**, không phải nơi đáng tin cậy để giữ durable state.

## 2. Why does it exist?

Long-running processes cần lifecycle management cho configuration, deployments, memory conditions và operational recovery. Recycling cho IIS thay process mà không yêu cầu reboot server.

## 3. How does it work?

```text
IIS
 └─ App Pool
     ├─ old w3wp.exe → drain/terminate
     └─ new w3wp.exe → application startup/warm-up
```

ASP.NET Core behind IIS có hosting/process model riêng tùy deployment, nhưng nguyên tắc vẫn là process restart làm mất in-memory state.

## 4. Practical implementation

Không lưu critical job state trong static dictionary:

```csharp
// Không durable qua recycle.
private static readonly ConcurrentDictionary<Guid, JobState> Jobs = new();
```

Persist job state vào database/Redis phù hợp requirement, và thiết kế startup/shutdown với `CancellationToken`.

## 5. Real production scenario

Legacy enterprise app lưu user workflow tạm trong in-process session. App Pool recycle lúc đêm khiến users mất workflow. Root cause không phải “IIS random”; state ownership sai với process lifetime.

## 6. Failure scenario & troubleshooting

**Symptom** → 5xx ngắn hoặc state biến mất theo chu kỳ.  
**Evidence** → IIS/Event Viewer logs trùng thời điểm recycle/process start.  
**Hypothesis** → restart-sensitive state hoặc slow startup.  
**Diagnosis** → inspect recycle settings, process events, startup logs và health checks.  
**Fix** → externalize durable state, warm-up, graceful shutdown và deployment strategy phù hợp.  
**Verification** → intentional recycle không làm mất correctness và error rate nằm trong target.

## 7. Common mistakes

Tắt recycling để “fix”; giữ background scheduler chỉ trong web process; dùng local filesystem như shared durable store; không log startup/shutdown reason.

## 8. Alternatives

Azure App Service abstract nhiều IIS operations nhưng instance restart vẫn tồn tại. Containers cũng disposable. Windows Service phù hợp một số long-running workers nhưng vẫn cần durable state.

## 9. Trade-offs

### Advantages

Process recycling hỗ trợ recovery và lifecycle management.

### Costs / Risks

Startup latency, transient availability impact và state loss nếu architecture phụ thuộc process memory.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process có thể restart bất kỳ lúc nào.

### Middle

Đọc IIS logs và cấu hình App Pool cơ bản.

### Senior

Thiết kế shutdown, warm-up và external state.

### Technical Lead / Architect

Đảm bảo application correctness không phụ thuộc lifetime của một worker process.

## 11. Key takeaway

- Process memory không phải durable storage.
- Recycling phải là expected operational event.
- Tắt recycle không sửa state/lifecycle design sai.

# 9. Technical SEO canonical URLs: duplicate content, routing và cache boundary

## 1. What is it?

Canonical URL là tín hiệu cho search engine biết URL đại diện ưu tiên khi nhiều URLs có nội dung tương đương. Với engineer, đây là routing/content-identity problem chứ không chỉ là một `<link>` tag.

## 2. Why does it exist?

Một product có thể xuất hiện qua tracking parameters, category routes, uppercase/lowercase variants hoặc legacy paths. Nếu hệ thống phát sinh nhiều identities cho cùng content, crawling/indexing signals bị phân tán.

## 3. How does it work?

```text
/product/42?utm_source=x ─┐
/category/a/product/42 ───┼─► canonical: /product/42
/product/42 ──────────────┘
```

Canonical là hint; redirects, internal links, sitemap và actual response behavior nên nhất quán với chosen identity.

## 4. Practical implementation

Trong Razor/SSR output:

```html
<link rel="canonical" href="https://example.com/product/42" />
```

Application nên xây canonical URL từ trusted routing/content identity, không copy tùy ý toàn request query string.

## 5. Real production scenario

CMS migration tạo cả `/News/Article` và `/news/article`, CDN cache coi là hai keys và sitemap chứa cả hai. Search indexing phân tán trong khi analytics cũng khó aggregate.

## 6. Failure scenario & troubleshooting

**Symptom** → search console báo duplicate pages hoặc wrong canonical.  
**Evidence** → HTML canonical khác sitemap/internal links; redirects tạo chains.  
**Hypothesis** → routing/content identity không thống nhất.  
**Diagnosis** → crawl representative URLs, inspect status, canonical, redirects, sitemap và CDN behavior.  
**Fix** → define one URL policy, redirect true aliases và align generated links.  
**Verification** → crawler thấy consistent canonical/redirect graph.

## 7. Common mistakes

Canonical mọi page về homepage; canonical tới 404/redirect chain; để query parameters lọt vào canonical không chủ đích; dùng canonical thay cho redirect khi alias không cần tồn tại.

## 8. Alternatives

301/308 redirect mạnh hơn khi old URL thực sự nên biến mất. `noindex` giải quyết indexing intent khác và không phải replacement cho canonicalization.

## 9. Trade-offs

### Advantages

URL identity rõ giúp crawling, caching, analytics và content governance nhất quán.

### Costs / Risks

Sai canonical có thể làm search engine ưu tiên page không mong muốn; migration cần backward compatibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một resource có thể có nhiều URL aliases.

### Middle

Implement canonical output và redirects đúng HTTP semantics.

### Senior

Reason xuyên routing, CDN, sitemap, CMS và migration.

### Technical Lead / Architect

Định nghĩa URL identity policy như public contract lâu dài, không phải template detail.

## 11. Key takeaway

- Canonicalization bắt đầu từ resource identity.
- Redirects, sitemap, internal links và canonical tags phải kể cùng một câu chuyện.
- URL design là backward-compatibility concern.

# 10. RAG retrieval quality: chunking, embeddings, reranking và deterministic authorization boundary

## 1. What is it?

Retrieval-Augmented Generation (RAG) lấy context từ knowledge source rồi đưa context đó vào LLM. Mental model: RAG không “dạy model database”; nó xây một **retrieval pipeline** trước probabilistic generation.

## 2. Why does it exist?

Model không biết private/current repository documents một cách đáng tin cậy. Nhét toàn bộ corpus vào prompt vừa đắt vừa vượt context. Retrieval chọn subset có khả năng liên quan.

## 3. How does it work?

```text
Documents → chunk → embedding/index
                         ▲
User query → retrieve ───┘
               │
             rerank
               │
               ▼
        selected context
               │
               ▼
              LLM
```

Retrieval quality giới hạn answer quality. Nếu relevant chunk không được lấy ra, prompt engineering phía sau khó cứu được.

## 4. Practical implementation

Application nên giữ metadata phục vụ authorization và citations:

```csharp
public sealed record SearchChunk(
    string DocumentId,
    string ChunkId,
    string Text,
    string TenantId,
    string[] AllowedRoles);
```

Filter quyền truy cập phải được enforce bằng deterministic application/search layer trước khi context tới model, không hỏi model “user có được xem đoạn này không?”.

## 5. Real production scenario

Internal engineering assistant trả lời từ ADRs và runbooks. Naive fixed-size chunking cắt heading khỏi body nên retrieval lấy đoạn “Fix: restart consumer” nhưng mất điều kiện áp dụng. Team cải thiện chunking theo document structure và reranking.

## 6. Failure scenario & troubleshooting

**Symptom** → model trả lời sai dù source document có đáp án.  
**Evidence** → inspect retrieved top-k không chứa relevant section.  
**Hypothesis** → retrieval failure, không phải generation failure.  
**Diagnosis** → evaluation tách retrieval recall khỏi answer correctness; inspect query, chunks, metadata filters và ranking.  
**Fix** → cải thiện chunk boundaries, hybrid search, query rewriting/reranking khi evidence chứng minh cần.  
**Verification** → retrieval recall@k và end-to-end grounded-answer metrics tăng trên versioned eval set.

## 7. Common mistakes

Tăng `top_k` vô hạn; chunk theo số ký tự mà bỏ structure; không version index; dùng vector similarity như authorization; không log source IDs; đánh giá bằng vài demo queries.

## 8. Alternatives

Full-text/BM25 search có thể tốt hơn cho exact identifiers. Hybrid retrieval kết hợp lexical + semantic. Tool Calling phù hợp khi cần query structured system/API thay vì semantic document search.

## 9. Trade-offs

### Advantages

Ground model vào private/current knowledge và cho phép source attribution.

### Costs / Risks

Indexing pipeline, freshness, retrieval evaluation, authorization và token cost tạo operational burden mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retrieval và generation là hai stages khác nhau.

### Middle

Implement chunk/index/retrieve flow và metadata.

### Senior

Đo retrieval recall, grounding, latency và cost; debug từng stage.

### Technical Lead / Architect

Quyết định dữ liệu nào nên RAG, dữ liệu nào nên deterministic API/tool lookup, và enforce security trước model boundary.

## 11. Key takeaway

- RAG quality bắt đầu ở retrieval quality.
- Authorization phải deterministic trước khi context vào LLM.
- Đo retrieval và generation riêng để biết đang sửa đúng layer.
