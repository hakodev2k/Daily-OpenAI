# 1. C# `async`/`await` state machine và `ValueTask`: hiểu allocation, continuation và vì sao tối ưu async sai chỗ dễ làm code nguy hiểm

## 1. What is it?

`async`/`await` trong C# là syntax giúp viết asynchronous control flow gần giống synchronous code. Khi compiler gặp một method `async`, nó biến method đó thành một **state machine** có thể tạm dừng tại `await` rồi tiếp tục khi operation hoàn tất.

Mental model đơn giản:

```text
Call method
   |
   v
Run synchronously until first incomplete await
   |
   +--> operation already completed? continue immediately
   |
   +--> not completed? store state + return Task
                         |
                         v
                  operation completes
                         |
                         v
                   resume state machine
```

`Task` là representation của một asynchronous operation và thường là lựa chọn mặc định. `ValueTask` là một struct-based awaitable tối ưu một số hot paths nơi operation **rất thường hoàn tất synchronously** và allocation của `Task` đã được đo là đáng kể.

Điểm quan trọng: `ValueTask` không phải “Task nhanh hơn”. Nó đổi allocation cost lấy complexity và usage constraints.

## 2. Why does it exist?

Server workload thường bị giới hạn bởi I/O: SQL query, HTTP call, Redis, file/network. Nếu thread phải block trong lúc chờ I/O, server cần nhiều threads hơn để phục vụ cùng throughput, dẫn tới context switching và ThreadPool pressure.

`async`/`await` cho phép thread quay lại pool trong lúc I/O chưa xong.

Ví dụ:

```text
Request A -> SQL wait ---------> continuation
             thread released

Request B -> gets available ThreadPool thread
```

`ValueTask` xuất hiện vì một số low-level APIs có fast path rất phổ biến, ví dụ đọc từ buffer đã có sẵn. Nếu 99% call hoàn tất ngay mà mỗi call vẫn phải tạo một `Task`, allocation có thể đáng kể ở throughput rất cao.

## 3. How does it work?

Compiler tạo state machine chứa:

- current state;
- local variables cần sống qua `await`;
- builder (`AsyncTaskMethodBuilder`, tương tự);
- continuation logic.

Code:

```csharp
public async Task<int> LoadAsync(CancellationToken ct)
{
    var value = await repository.GetValueAsync(ct);
    return value + 1;
}
```

về mặt cơ chế gần với:

```text
State 0: call GetValueAsync
         if completed -> read result -> finish
         else save awaiter + state -> return

State 1: continuation invoked
         read awaiter result
         add 1
         complete Task
```

Không phải mọi `async` call đều lập tức tạo thread mới. Với I/O async thực, kernel/runtime notification hoàn tất operation rồi continuation được schedule.

`ValueTask<T>` có thể đại diện cho:

- kết quả đã có ngay;
- một `Task<T>` bên dưới;
- specialized source thông qua `IValueTaskSource<T>`.

Chính vì có nhiều representation, usage contract phức tạp hơn `Task<T>`.

## 4. Practical implementation

Default nên là `Task<T>`:

```csharp
public async Task<Customer?> GetCustomerAsync(
    Guid id,
    CancellationToken ct)
{
    return await db.Customers
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);
}
```

Chỉ dùng `ValueTask<T>` khi profiling chứng minh allocation của `Task` đáng kể và fast path phổ biến:

```csharp
public ValueTask<FeatureFlag> GetAsync(string key, CancellationToken ct)
{
    if (_memory.TryGetValue(key, out FeatureFlag? cached))
        return ValueTask.FromResult(cached);

    return new ValueTask<FeatureFlag>(LoadFromStoreAsync(key, ct));
}
```

Caller chỉ nên await trực tiếp một lần:

```csharp
var flag = await provider.GetAsync("CheckoutV2", ct);
```

Không nên lưu `ValueTask` lại rồi await nhiều lần hoặc dùng các APIs expect reusable `Task` semantics mà không chuyển sang `.AsTask()` khi thực sự cần.

## 5. Real production scenario

Một high-throughput gateway thực hiện hàng trăm nghìn cache lookups mỗi giây. 98% key có trong in-memory cache. Version đầu trả `Task.FromResult` cho fast path và allocation rate tăng đáng kể.

Sau profiling, team đổi low-level abstraction sang `ValueTask<T>` ở đúng hotspot. Allocation giảm và Gen 0 frequency giảm.

Ngược lại, nếu đây chỉ là business API 200 requests/s, đổi hàng trăm methods sang `ValueTask` có thể không tạo measurable benefit nhưng làm code review và composition khó hơn.

## 6. Failure scenario & troubleshooting

**Symptom:** latency tăng dưới load, ThreadPool queue length cao nhưng CPU chưa đạt 100%.

**Evidence:** traces cho thấy sync-over-async như `.Result`, `.Wait()` hoặc database/network calls synchronous trong request path.

**Hypothesis:** threads bị block trong lúc chờ I/O.

**Diagnosis:** kiểm tra thread stacks, `dotnet-counters`, traces và code paths.

**Fix:** async all the way, propagate cancellation, tránh sync-over-async.

Một failure khác:

**Symptom:** code dùng `ValueTask` đôi lúc ném lỗi bất thường hoặc behavior không deterministic.

**Evidence:** cùng một `ValueTask` được await nhiều lần.

**Fix:** await một lần hoặc convert sang `Task` nếu cần reusable semantics.

## 7. Common mistakes

- Nghĩ `async` tạo thread mới.
- Dùng `Task.Run` cho I/O để “biến nó thành async”.
- Gọi `.Result`/`.Wait()` trong ASP.NET Core request path.
- Dùng `ValueTask` mặc định cho mọi async method.
- Quên `CancellationToken` ở downstream I/O.
- Đo average latency nhưng bỏ qua ThreadPool starvation và p99.

## 8. Alternatives

- **Synchronous code:** hợp lý cho work CPU nhỏ hoặc tool đơn giản không cần scale concurrency.
- **Task:** default tốt nhất cho phần lớn application code.
- **ValueTask:** chỉ cho measured hot path có frequent synchronous completion.
- **Channels/queues:** dùng khi cần decouple producer/consumer, không thay thế async I/O.

## 9. Trade-offs

### Advantages

- `async` giúp server sử dụng threads hiệu quả hơn cho I/O-bound workload.
- `Task` có semantics đơn giản, tooling tốt, dễ compose.
- `ValueTask` có thể giảm allocation trong hotspot thật sự.

### Costs / Risks

- State machine vẫn có overhead.
- Async code làm stack traces/control flow khó hơn nếu observability kém.
- `ValueTask` tăng API complexity và dễ bị misuse.
- Async không làm CPU-bound algorithm tự nhanh hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` không đồng nghĩa “new thread”; nó là cơ chế suspend/resume asynchronous flow.

### Middle

Biết viết async all the way, propagate cancellation và tránh `.Result`/`.Wait()`.

### Senior

Đọc profiler/ThreadPool metrics để phân biệt I/O wait, CPU saturation và async misuse; chỉ dùng `ValueTask` khi có evidence.

### Technical Lead / Architect

Đặt guideline: `Task` mặc định, `ValueTask` chỉ ở performance-sensitive abstraction có benchmark; review API semantics chứ không chạy theo micro-optimization.

## 11. Key takeaway

- `async`/`await` là state-machine-based concurrency model cho I/O, không phải thread creation API.
- `Task` nên là mặc định của application code.
- `ValueTask` là optimization có cost về correctness và maintainability; chỉ dùng sau khi đo.

# 2. ASP.NET Core Forwarded Headers sau reverse proxy: scheme, host, client IP và security boundary khi app không nhìn thấy kết nối gốc

## 1. What is it?

Khi ASP.NET Core chạy sau reverse proxy như Azure Front Door, Application Gateway, Nginx hoặc IIS, application thường không nhận trực tiếp connection từ browser. Nó thấy connection từ proxy.

```text
Client HTTPS
   |
   v
Reverse Proxy
   |  HTTP/private network
   v
ASP.NET Core
```

Do đó `Request.Scheme`, client IP và host mà app nhìn thấy có thể không phản ánh request gốc. **Forwarded headers** như `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host` truyền metadata của original request qua proxy chain.

## 2. Why does it exist?

Nếu app không biết original scheme:

- generate redirect sai từ `https` về `http`;
- cookie `Secure`/OIDC redirect URI có thể sai;
- rate limit theo IP có thể gom toàn bộ users vào IP của proxy;
- audit log mất client origin.

Nhưng forwarded headers cũng là **security boundary**. Nếu app tin header do client tự gửi, attacker có thể spoof IP hoặc scheme.

## 3. How does it work?

Flow:

```text
Browser: HTTPS, IP 203.0.113.10
   |
Proxy receives request
   |
Proxy forwards:
X-Forwarded-For: 203.0.113.10
X-Forwarded-Proto: https
Host: app.internal
   |
ASP.NET Core ForwardedHeadersMiddleware
   |
Request.Scheme = https
RemoteIpAddress = 203.0.113.10
```

Middleware chỉ nên tin headers từ known proxies/networks. Nếu có nhiều proxy hops, cần hiểu order và forwarding limit.

## 4. Practical implementation

```csharp
using Microsoft.AspNetCore.HttpOverrides;
using System.Net;

var builder = WebApplication.CreateBuilder(args);

builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders =
        ForwardedHeaders.XForwardedFor |
        ForwardedHeaders.XForwardedProto;

    options.KnownProxies.Add(IPAddress.Parse("10.0.1.10"));
});

var app = builder.Build();

app.UseForwardedHeaders();
app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
```

Order quan trọng: forwarded headers phải được apply trước middleware phụ thuộc `Scheme`, `Host` hoặc `RemoteIpAddress`.

Trong cloud, IP proxy có thể dynamic hoặc bạn dùng `KnownNetworks`/platform guidance thay vì hard-code một IP không ổn định.

## 5. Real production scenario

OIDC login hoạt động local nhưng production redirect về:

```text
http://internal-app/signin-oidc
```

Identity provider reject vì registered redirect URI là HTTPS public URL.

Root cause không nằm ở OAuth library mà ở reverse proxy termination: TLS kết thúc ở edge, backend nhận HTTP và app không restore `X-Forwarded-Proto`.

## 6. Failure scenario & troubleshooting

**Symptom:** redirect loop HTTP↔HTTPS hoặc authentication callback URL sai.

**Evidence:** edge access log ghi HTTPS, ASP.NET log ghi `Request.Scheme=http`.

**Hypothesis:** forwarded headers chưa xử lý hoặc middleware order sai.

**Diagnosis:** inspect request headers ở trusted internal hop; verify proxy config và known proxy rules.

**Fix:** cấu hình proxy + `UseForwardedHeaders` đúng order và trust boundary.

**Verification:** log normalized scheme/IP sau middleware; chạy end-to-end qua production-like proxy.

Security failure:

**Symptom:** rate limiter/audit log thấy attacker có arbitrary IP.

**Diagnosis:** app chấp nhận `X-Forwarded-For` trực tiếp từ internet.

**Fix:** chỉ trust forwarding metadata từ known proxy path.

## 7. Common mistakes

- Tin mọi `X-Forwarded-*` header.
- Đặt `UseForwardedHeaders` sau `UseHttpsRedirection`.
- Dùng client IP làm authentication/authorization factor.
- Quên nhiều proxy hops như Front Door → Application Gateway → App Service.
- Test trực tiếp backend rồi suy ra behavior giống production edge path.

## 8. Alternatives

- **Direct Kestrel exposure:** ít translation hơn nhưng thường không phù hợp enterprise edge/security requirements.
- **Platform integration:** App Service/IIS có thể xử lý một phần forwarding behavior, nhưng vẫn phải hiểu trust model.
- **Proxy Protocol:** một số infrastructure dùng transport-level metadata thay HTTP headers, tùy stack.

## 9. Trade-offs

### Advantages

- App có thể reconstruct original request context.
- Redirect, logging, rate limiting và observability chính xác hơn.

### Costs / Risks

- Misconfiguration có thể tạo spoofing.
- Multi-hop proxy chains khó reasoning hơn.
- Infrastructure và application config phải đồng bộ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser không nhất thiết kết nối trực tiếp tới ASP.NET Core.

### Middle

Biết cấu hình forwarded headers và middleware order.

### Senior

Hiểu trusted proxy chain, spoofing risk, OIDC/HTTPS implications và log evidence.

### Technical Lead / Architect

Xác định authoritative ingress path, network trust boundary và chuẩn hóa edge architecture để teams không cấu hình forwarded headers tùy ý.

## 11. Key takeaway

- Reverse proxy làm thay đổi request context mà backend nhìn thấy.
- Forwarded headers chỉ đáng tin nếu đến từ trusted proxy path.
- Nhiều lỗi auth/redirect/rate-limit production thực chất là proxy-context bug.

# 3. EF Core optimistic concurrency với `rowversion`: phát hiện lost update và xử lý conflict theo business semantics thay vì overwrite im lặng

## 1. What is it?

Optimistic concurrency giả định conflict xảy ra không thường xuyên. Thay vì lock row từ lúc đọc tới lúc ghi, application đọc record cùng **concurrency token**, sau đó update chỉ khi token vẫn giống lúc đọc.

SQL Server `rowversion` là một token rất tiện cho case này.

Mental model:

```text
User A reads Version=10
User B reads Version=10

User A updates -> Version becomes 11
User B updates with expected Version=10
              -> 0 rows affected
              -> concurrency conflict
```

Mục tiêu là ngăn **lost update**: B vô tình ghi đè thay đổi của A mà không biết.

## 2. Why does it exist?

Web request thường không thể giữ database lock trong suốt thời gian user mở form vài phút. Pessimistic lock dài như vậy làm giảm concurrency và rất khó vận hành.

Optimistic concurrency cho phép nhiều users đọc cùng state, chỉ resolve conflict tại thời điểm write.

## 3. How does it work?

Entity:

```csharp
public sealed class Customer
{
    public Guid Id { get; set; }
    public string Name { get; set; } = null!;

    [Timestamp]
    public byte[] Version { get; set; } = null!;
}
```

EF Core tạo update conceptually như:

```sql
UPDATE Customers
SET Name = @name
WHERE Id = @id
  AND Version = @originalVersion;
```

Nếu affected rows = 0, EF Core ném `DbUpdateConcurrencyException`.

Đây chỉ là detection. Application vẫn phải quyết định **business resolution**.

## 4. Practical implementation

```csharp
try
{
    customer.Name = request.Name;
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new
    {
        code = "customer_conflict",
        message = "Customer was modified by another user. Reload and retry."
    });
}
```

Với REST API, có thể expose version dưới dạng ETag:

```http
ETag: "CwAAAAAAABQ="
```

Client update:

```http
PUT /customers/42
If-Match: "CwAAAAAAABQ="
```

Nếu version không match, server trả `412 Precondition Failed` hoặc contract tương đương đã thống nhất.

## 5. Real production scenario

Hai HR managers cùng sửa employee profile:

- A đổi department.
- B đổi manager.

Nếu endpoint map toàn DTO rồi update tất cả columns mà không concurrency check, B có thể overwrite department cũ vào record sau khi A đã đổi.

Optimistic concurrency phát hiện conflict. Sau đó domain quyết định:

- reject và yêu cầu reload;
- auto-merge nếu fields độc lập;
- preserve one side theo rule;
- escalate manual resolution.

## 6. Failure scenario & troubleshooting

**Symptom:** users phản ánh “dữ liệu vừa lưu bị quay lại giá trị cũ”.

**Evidence:** audit log cho thấy hai updates gần nhau; update sau chứa stale field values.

**Hypothesis:** lost update.

**Diagnosis:** kiểm tra update contract, token/version và generated SQL.

**Fix:** concurrency token + conflict response; giảm over-posting; update chỉ intended fields khi hợp lý.

**Verification:** integration test với hai `DbContext` đọc cùng version rồi update theo thứ tự cạnh tranh.

## 7. Common mistakes

- Bắt `DbUpdateConcurrencyException` rồi retry ngay với dữ liệu cũ.
- Nghĩ optimistic concurrency tự merge data.
- Dùng timestamp wall-clock (`DateTime`) làm token mà precision/clock semantics không đủ an toàn.
- Gửi toàn entity từ browser và overwrite mọi field.
- Dùng generic “last write wins” mà không đánh giá business impact.

## 8. Alternatives

- **Pessimistic locking:** phù hợp critical short transaction cần serialization.
- **Field-level merge:** tốt khi edits độc lập và domain cho phép.
- **Event/command model:** mỗi command mô tả intention thay vì replace full aggregate.
- **Last-write-wins:** đơn giản, hợp lý cho low-risk settings nhưng phải intentional.

## 9. Trade-offs

### Advantages

- Không giữ locks qua user think time.
- Phát hiện stale writes rõ ràng.
- Scale concurrency tốt khi conflicts hiếm.

### Costs / Risks

- Conflict resolution tăng UX/business complexity.
- Conflict nhiều có thể khiến users retry liên tục.
- Token phải đi xuyên API contract hoặc server state đúng cách.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu lost update và vì sao “SaveChanges thành công” chưa đủ nói concurrency đúng.

### Middle

Implement `rowversion`, catch conflict và viết integration tests.

### Senior

Thiết kế merge/retry semantics theo command và business invariant.

### Technical Lead / Architect

Quyết định aggregate nào cần optimistic token, endpoint nào dùng ETag, nơi nào conflict phải reject thay vì auto-merge.

## 11. Key takeaway

- Optimistic concurrency phát hiện conflict; nó không tự quyết định cách giải quyết.
- Retry mù có thể biến conflict thành overwrite.
- Concurrency policy phải gắn với business semantics, không chỉ EF Core configuration.

# 4. PostgreSQL/Npgsql connection pooling: vì sao pool exhaustion làm API treo dù database CPU vẫn thấp

## 1. What is it?

Database connection là resource đắt: mở TCP/TLS, authenticate, allocate server session. Npgsql dùng **connection pooling** để reuse physical connections thay vì mở mới mỗi query.

```text
API requests
   |
   v
Npgsql connection pool
[conn1][conn2][conn3]...[connN]
   |
   v
PostgreSQL
```

`OpenAsync()` thường lấy connection từ pool; `Close`/`Dispose` trả nó về pool, không nhất thiết đóng physical connection.

Pool exhaustion xảy ra khi tất cả pooled connections đang bận và request mới phải chờ connection available.

## 2. Why does it exist?

Không pooling:

```text
request -> open network/auth session -> query -> close
```

lặp hàng nghìn lần tạo latency và server overhead.

Pooling amortizes setup cost. Nhưng nó cũng tạo một **bounded shared resource**. Nếu code giữ connection quá lâu hoặc leak connection, pool trở thành bottleneck trước database CPU.

## 3. How does it work?

Giả sử pool max = 100:

```text
100 long-running/blocked operations
        |
        v
all connections occupied
        |
request 101..N wait for pool slot
        |
API latency explodes
```

Database có thể chỉ dùng 30% CPU vì bottleneck là locks, slow network, idle transaction hoặc application giữ connections trong lúc làm work khác.

EF Core thường mở connection khi cần query/SaveChanges và đóng sau operation, trừ khi transaction/explicit connection kéo dài hơn.

## 4. Practical implementation

Giữ DB scope ngắn:

```csharp
public async Task<OrderDto?> GetAsync(Guid id, CancellationToken ct)
{
    return await db.Orders
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new OrderDto(x.Id, x.Status, x.Total))
        .SingleOrDefaultAsync(ct);
}
```

Không mở transaction rồi gọi external API:

```csharp
// Bad shape
await using var tx = await db.Database.BeginTransactionAsync(ct);
await db.SaveChangesAsync(ct);
await paymentApi.CaptureAsync(..., ct); // connection/locks may remain occupied
await tx.CommitAsync(ct);
```

Nên thiết kế transaction ngắn và dùng Outbox/Saga khi cần coordinate external side effect.

Theo dõi:

- connection acquire latency;
- active/idle connections;
- database session states;
- long-running transactions;
- p95/p99 query duration.

## 5. Real production scenario

API có `Max Pool Size=100`. Một external payment API chậm 20 giây. Code vô tình mở transaction trước rồi gọi payment API bên trong transaction.

Chỉ cần 100 concurrent requests là 100 connections bị giữ. Request thứ 101 đợi pool. Database CPU vẫn thấp, nên team ban đầu nghĩ DB “không có vấn đề”.

Thực tế bottleneck là application transaction scope.

## 6. Failure scenario & troubleshooting

**Symptom:** API p99 tăng mạnh; lỗi timeout acquiring connection; PostgreSQL CPU thấp.

**Evidence:** nhiều sessions `idle in transaction` hoặc queries waiting lock; pool wait tăng.

**Hypothesis:** connections bị giữ quá lâu.

**Diagnosis:** correlate application traces với `pg_stat_activity`, transaction age và connection metrics.

**Fix:** rút ngắn transaction, dispose đúng, sửa slow query/lock, giới hạn downstream concurrency.

**Verification:** load test; connection acquisition trở về gần zero wait trong steady state.

## 7. Common mistakes

- Tăng `Max Pool Size` ngay lập tức để che root cause.
- Giữ `DbContext`/transaction quá lâu.
- Mở connection rồi quên dispose khi exception.
- Gọi remote API bên trong DB transaction.
- Chỉ monitor database CPU.
- Tạo nhiều connection strings khác nhau vô tình tạo nhiều pools.

## 8. Alternatives

- **PgBouncer:** external pooling/proxy có thể giảm server connection footprint, nhưng transaction/session features cần xem mode.
- **Direct pooling trong Npgsql:** đơn giản và đủ cho phần lớn applications.
- **Queue/bounded concurrency:** giảm simultaneous DB demand trong batch workloads.

## 9. Trade-offs

### Advantages

- Pooling giảm connection setup latency.
- Bounded pool bảo vệ database khỏi unbounded sessions.

### Costs / Risks

- Pool là shared bottleneck nếu sizing/scopes sai.
- Tăng pool size có thể đẩy bottleneck xuống database thay vì giải quyết.
- External pooler thêm operational component.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbConnection.Dispose` thường trả connection về pool.

### Middle

Viết code với short-lived contexts/transactions và inspect connection timeouts.

### Senior

Phân biệt DB CPU bottleneck với pool/lock/session bottleneck bằng evidence.

### Technical Lead / Architect

Sizing connection budget theo total replicas × pool size; quyết định khi cần PgBouncer, backpressure hoặc workload separation.

## 11. Key takeaway

- Connection pool là bounded capacity, không phải nguồn connection vô hạn.
- Database CPU thấp không loại trừ database-path bottleneck.
- Transaction lifetime thường quan trọng hơn việc tăng pool size.

# 5. Elasticsearch analyzers, `text` và `keyword`: mapping sai có thể khiến search “không tìm thấy” dù document tồn tại

## 1. What is it?

Elasticsearch không search string theo kiểu SQL `LIKE` mặc định. Với field `text`, dữ liệu đi qua **analyzer** gồm tokenizer + token filters để tạo terms trong inverted index.

Ví dụ:

```text
"Premium Running Shoes"
      |
 standard analyzer
      v
[premium] [running] [shoes]
```

Field `keyword` giữ giá trị như một term gần nguyên bản:

```text
"Premium Running Shoes"
      |
      v
[Premium Running Shoes]
```

`text` phù hợp full-text relevance. `keyword` phù hợp exact filter, aggregation, sorting.

## 2. Why does it exist?

Search user-facing cần hiểu tokenized language, case normalization, stemming/synonyms tùy use case. Database B-tree index không được thiết kế cho relevance ranking/full-text behavior phức tạp.

Tách `text` và `keyword` giúp cùng một logical field phục vụ hai access patterns khác nhau.

## 3. How does it work?

Mapping phổ biến:

```json
{
  "name": {
    "type": "text",
    "fields": {
      "keyword": {
        "type": "keyword"
      }
    }
  }
}
```

Khi index:

```text
name -> analyzer -> inverted terms
name.keyword -> exact value term
```

Query `match` phân tích query text; `term` query thường không phân tích input tương tự full-text analyzer.

Vì vậy:

```json
{ "term": { "name": "Running Shoes" } }
```

trên `text` field có thể cho kết quả khác developer kỳ vọng.

## 4. Practical implementation

Full-text search:

```json
{
  "query": {
    "match": {
      "name": "running shoes"
    }
  }
}
```

Exact filter:

```json
{
  "query": {
    "term": {
      "brand.keyword": "Contoso"
    }
  }
}
```

Aggregation:

```json
{
  "aggs": {
    "brands": {
      "terms": {
        "field": "brand.keyword"
      }
    }
  }
}
```

Trước khi đổi analyzer trong production, test bằng `_analyze` và representative queries; analyzer change thường cần reindex để dữ liệu cũ được tokenized lại.

## 5. Real production scenario

E-commerce index product names. Developer dùng `keyword` cho `ProductName` vì nghĩ “string thì keyword”. Search "wireless mouse" chỉ match exact entire name, nên product "Contoso Wireless Mouse Pro" không xuất hiện.

Sau đó team chuyển `ProductName` sang `text` + subfield `keyword`: full-text search dùng `text`, sorting/aggregation dùng `keyword`.

## 6. Failure scenario & troubleshooting

**Symptom:** document có trong index nhưng query không match.

**Evidence:** `_source` chứa giá trị; `_analyze` cho thấy tokens khác assumption; mapping field type không đúng.

**Hypothesis:** analyzer/query type mismatch.

**Diagnosis:** inspect mapping, analyzer output, query DSL và `explain` khi cần.

**Fix:** dùng đúng `match`/`term`, mapping đúng access pattern; reindex nếu analyzer thay đổi.

**Verification:** regression query set với expected ranking/results.

## 7. Common mistakes

- Dùng `term` query trên analyzed `text` rồi ngạc nhiên không match.
- Aggregate/sort trực tiếp trên `text`.
- Đổi analyzer nhưng không reindex.
- Dùng synonyms/stemming quá mạnh làm relevance tệ.
- Cho Elasticsearch làm source of truth cho transactional update.
- Không version mapping/index lifecycle.

## 8. Alternatives

- **PostgreSQL/SQL Server full-text search:** đủ cho simpler requirements và giảm operational stack.
- **Database `LIKE`/trigram:** hợp lý cho limited search use cases.
- **Dedicated search engine:** đáng giá khi relevance, autocomplete, facets, scale hoặc multilingual analysis thực sự cần.

## 9. Trade-offs

### Advantages

- Analyzer-based indexing cho relevance/search behavior mạnh.
- Multi-fields cho phép một value phục vụ nhiều access patterns.

### Costs / Risks

- Mapping/analyzer tạo complexity và cần reindex khi thay đổi.
- Search index có eventual consistency với primary DB.
- Relevance tuning cần evaluation data, không thể chỉ “cảm thấy đúng”.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `text` được analyzed, `keyword` dùng exact semantics.

### Middle

Viết mappings/query DSL đúng và dùng `_analyze` để debug.

### Senior

Thiết kế analyzers theo language/search behavior, quản lý reindex và relevance regression.

### Technical Lead / Architect

Quyết định khi nào Elasticsearch đáng cost vận hành; xác định source-of-truth, sync mechanism và index migration strategy.

## 11. Key takeaway

- Mapping quyết định search semantics từ lúc index, không chỉ lúc query.
- `text` và `keyword` giải quyết hai access patterns khác nhau.
- Analyzer changes là data migration/reindex concern, không phải config tweak đơn giản.

# 6. Modular Monolith: boundary, data ownership và transaction scope trước khi nhảy sang Microservices

## 1. What is it?

Modular Monolith là một application deployable unit nhưng được chia thành **business modules có boundary rõ**.

```text
+---------------------------------------+
|            Single deployment          |
|                                       |
|  Orders   Billing   Catalog   Identity|
|    |         |         |         |    |
|  own API  own API   own API   own API |
+---------------------------------------+
```

Khác với layered monolith nơi mọi feature có thể truy cập chung mọi tables/services, modular monolith cố gắng cô lập ownership và dependencies theo business capability.

## 2. Why does it exist?

Microservices giải quyết deployment/ownership/scale boundaries nhưng thêm network, distributed transactions, observability, deployment orchestration và operational cost.

Nhiều hệ thống cần **logical modularity** trước khi cần **physical distribution**.

Modular Monolith cho phép team luyện discipline về boundary mà vẫn giữ local call và single-process simplicity.

## 3. How does it work?

Mỗi module nên có:

- public contract/application API;
- internal domain/application implementation;
- data ownership rõ;
- controlled cross-module communication.

Ví dụ:

```text
Orders module
  -> owns Orders tables
  -> exposes PlaceOrder/GetOrder
  -> may publish OrderPlaced

Billing module
  -> must not query Orders internal tables directly
```

Có thể cùng một physical database nhưng schemas/tables ownership vẫn logical distinct.

Cross-module transaction có thể tồn tại nếu system thật sự cần, nhưng nên explicit vì đó là coupling signal.

## 4. Practical implementation

Một module contract đơn giản:

```csharp
public interface IInventoryModule
{
    Task<ReservationResult> ReserveAsync(
        ReserveInventoryCommand command,
        CancellationToken ct);
}
```

Orders chỉ biết contract, không biết `InventoryDbContext`.

Trong composition root:

```csharp
services.AddOrdersModule(configuration);
services.AddInventoryModule(configuration);
```

Boundary test có thể enforce namespace/project references để ngăn module A import internal types của B.

## 5. Real production scenario

E-commerce monolith có 200 tables và mọi service query chéo. Team muốn split microservices nhưng không ai biết bảng nào thuộc domain nào.

Thay vì network split ngay, team refactor thành modules:

- Catalog owns product metadata;
- Inventory owns stock;
- Orders owns order lifecycle;
- Payments adapter nằm ở Billing/Payment boundary.

Sau một thời gian, Inventory cần scale/deploy độc lập và boundary đã đủ sạch; khi đó extraction thành service thực sự ít rủi ro hơn.

## 6. Failure scenario & troubleshooting

**Symptom:** “modular monolith” nhưng một thay đổi Catalog làm Orders/Reporting/Checkout cùng compile-break.

**Evidence:** shared domain models, shared `DbContext`, direct table access khắp nơi.

**Hypothesis:** chỉ chia folders, chưa có boundary.

**Diagnosis:** dependency graph, DB access ownership, project references, cross-module call patterns.

**Fix:** narrow contracts, module-owned models/tables, events hoặc explicit APIs cho integration.

**Verification:** architecture tests và change impact: sửa internal Catalog type không buộc Orders đổi nếu contract giữ nguyên.

## 7. Common mistakes

- Gọi folder structure là architecture boundary.
- Tạo một `SharedKernel` chứa gần như toàn bộ domain models.
- Cho tất cả modules dùng chung generic repositories.
- Dùng in-process event bus rồi giả vờ đã có distributed guarantees.
- Split microservices trước khi hiểu business boundaries.
- Cấm mọi cross-module transaction dù business invariant thực sự cần atomicity.

## 8. Alternatives

- **Simple layered monolith:** tốt cho domain nhỏ/team nhỏ.
- **Modular Monolith:** phù hợp complexity trung bình/lớn khi deployment độc lập chưa cần.
- **Microservices:** phù hợp khi ownership, scale, deployment autonomy hoặc isolation justify distributed-system cost.

## 9. Trade-offs

### Advantages

- Giữ deployment/operations đơn giản.
- Tạo clear boundaries và extraction path.
- Local calls nhanh, transaction dễ hơn microservices.

### Costs / Risks

- Boundary enforcement cần discipline/tooling.
- Một process vẫn là shared failure/deployment unit.
- Module có thể coupling qua shared database nếu team không kiểm soát.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business responsibility, không chỉ project/folder.

### Middle

Implement module contracts, internal encapsulation và tests.

### Senior

Thiết kế data ownership, transaction boundary và communication semantics.

### Technical Lead / Architect

Quyết định module nào nên ở cùng process và module nào thật sự cần service extraction; cân bằng autonomy với operational cost.

## 11. Key takeaway

- Modularity là boundary và ownership, không phải folder naming.
- Microservices không sửa được monolith boundary mơ hồ; nó chỉ biến coupling thành network coupling.
- Modular Monolith thường là bước kiến trúc trưởng thành trước distribution.

# 7. Azure Private Endpoint + Managed Identity: tách network trust khỏi identity trust khi backend truy cập Key Vault/Storage

## 1. What is it?

`Managed Identity` trả lời câu hỏi: **workload này là ai?**

`Private Endpoint` trả lời: **workload này kết nối tới service qua network path nào?**

Đây là hai lớp security khác nhau.

```text
App Service / VM / Container
        |
        | identity: Managed Identity
        |
        | network: VNet -> Private Endpoint
        v
   Key Vault / Storage
```

Có identity đúng không đồng nghĩa traffic đang đi private. Có private network path cũng không đồng nghĩa caller được authorization.

## 2. Why does it exist?

Enterprise systems thường muốn:

- không lưu client secret trong config;
- hạn chế public network exposure;
- áp least privilege;
- audit identity rõ ràng.

Managed Identity loại secret distribution cho Azure-hosted workloads. Private Endpoint đưa PaaS service vào private IP namespace của VNet thông qua Private Link.

## 3. How does it work?

Managed Identity:

```text
Application
  -> Azure identity endpoint / credential chain
  -> receives token for target resource
  -> calls service with Bearer token
```

Private Endpoint:

```text
DNS vault.azure.net
  -> private DNS zone mapping
  -> private IP in VNet
  -> Private Link
  -> service
```

Nếu DNS vẫn resolve public IP, application có thể đi sai path dù Private Endpoint tồn tại.

## 4. Practical implementation

C# dùng `DefaultAzureCredential`:

```csharp
var client = new SecretClient(
    new Uri("https://contoso-kv.vault.azure.net/"),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync(
    "PaymentApiKey",
    cancellationToken: ct);
```

Production có thể sử dụng Managed Identity; local development có thể dùng developer credential theo chain.

Network side cần:

- VNet integration từ workload;
- Private Endpoint cho Key Vault/Storage;
- private DNS zone đúng;
- firewall/public access policy đúng.

## 5. Real production scenario

Team bật Private Endpoint cho Key Vault rồi disable public access. Production app đột nhiên không lấy được secrets.

Managed Identity/RBAC hoàn toàn đúng. Root cause: App Service không resolve private DNS record, nên vẫn cố gọi public endpoint và bị firewall từ chối.

Đây là ví dụ identity success nhưng network failure.

## 6. Failure scenario & troubleshooting

**Symptom:** `403` hoặc network timeout khi truy cập Key Vault sau security hardening.

**Evidence:** token acquisition thành công nhưng TCP/DNS path sai; `nslookup` từ workload resolve public IP.

**Hypothesis:** Private DNS/VNet integration sai.

**Diagnosis:** kiểm tra DNS resolution, route, private endpoint connection state, Key Vault firewall và RBAC separately.

**Fix:** sửa private DNS link/VNet integration; không “fix” bằng mở public access rộng.

**Verification:** confirm DNS private IP + successful authorized request + denied unauthorized identity.

## 7. Common mistakes

- Nghĩ Managed Identity thay thế network controls.
- Nghĩ Private Endpoint thay thế RBAC.
- Disable public access trước khi test DNS path.
- Dùng overly broad role như Contributor khi chỉ cần Secrets User/Storage Data role cụ thể.
- Hard-code secrets vì Managed Identity setup ban đầu lỗi.
- Không monitor Key Vault dependency latency/throttling.

## 8. Alternatives

- **Service endpoint:** cung cấp network restriction model khác, không phải private IP endpoint giống Private Link.
- **Public endpoint + firewall/IP rules:** đơn giản hơn nhưng exposure model rộng hơn.
- **Client secret/certificate:** cần khi Managed Identity không khả dụng, nhưng rotation/secret lifecycle phức tạp hơn.

## 9. Trade-offs

### Advantages

- Không cần credential secret cho Azure-hosted workload.
- Private network exposure tốt hơn.
- Identity + network controls độc lập giúp defense in depth.

### Costs / Risks

- DNS/network architecture phức tạp hơn.
- Private Endpoints có cost và operational overhead.
- Developer troubleshooting khó nếu không tách identity vs network layers.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu authentication/authorization khác network reachability.

### Middle

Dùng `DefaultAzureCredential`, RBAC và kiểm tra DNS/private connectivity.

### Senior

Troubleshoot token, RBAC, DNS, route, firewall theo từng layer thay vì đoán.

### Technical Lead / Architect

Thiết kế standard pattern cho workload identity, private connectivity, DNS ownership và least privilege trên toàn platform.

## 11. Key takeaway

- Managed Identity và Private Endpoint giải quyết hai vấn đề khác nhau.
- Security tốt cần cả identity authorization và network boundary.
- Khi PaaS access lỗi, tách troubleshooting thành DNS/network/token/RBAC layers.

# 8. OpenTelemetry trace context qua asynchronous messaging: nối HTTP request với background consumer mà không tạo correlation giả

## 1. What is it?

Distributed tracing theo dõi một logical operation qua nhiều components bằng trace/span context.

Synchronous HTTP flow dễ hình dung:

```text
Client -> API -> SQL -> HTTP dependency
```

Async messaging phức tạp hơn:

```text
HTTP request -> publish message
                    |
                    v
               queue delay
                    |
                    v
                consumer
                    |
                    v
                   DB
```

Trace context cần được propagate trong message metadata để producer và consumer có relationship trong telemetry.

## 2. Why does it exist?

Không propagation, incident investigation bị đứt:

- API log có request ID A;
- Service Bus message có message ID B;
- consumer log có correlation C;

Team phải ghép bằng timestamp thủ công.

Tracing chuẩn hóa causal relationship và latency decomposition.

## 3. How does it work?

W3C Trace Context dùng `traceparent`/`tracestate` cho context propagation.

Producer tạo/send span, inject context vào message application properties. Consumer extract context và tạo processing span.

Quan trọng: queue delay và process span khác nhau.

```text
Producer span ----send---->
                         [queue delay]
                                      Consumer process span
```

Message redelivery có thể tạo nhiều processing attempts cho cùng logical message. Tracing không nên giả vờ chỉ có một attempt duy nhất.

## 4. Practical implementation

Với OpenTelemetry/.NET instrumentation phù hợp, nhiều libraries có thể auto-propagate. Khi custom envelope, có thể lưu context explicitly.

Conceptual example:

```csharp
using var activity = ActivitySource.StartActivity("orders.publish");

if (activity is not null)
{
    message.ApplicationProperties["traceparent"] = activity.Id!;
}

await sender.SendMessageAsync(message, ct);
```

Consumer extract và start activity với parent context. Trong production nên dùng standard propagator APIs thay vì tự parse string tùy ý.

Business correlation ID vẫn có thể tồn tại riêng:

```text
TraceId = technical causal trace
OrderId = business correlation
MessageId = broker/message identity
```

Không trộn ba loại ID thành một.

## 5. Real production scenario

User submit order, API trả 202 trong 150 ms. Order confirmation email tới sau 45 giây.

Nếu trace chỉ đo request 150 ms, dashboard nhìn “API khỏe”. Nhưng async consumer backlog 40 giây mới là user-perceived delay.

Trace + queue metrics cho thấy:

```text
API 150 ms
queue wait 39 s
consumer 5 s
email provider 1 s
```

Root cause nằm ở backlog, không phải controller.

## 6. Failure scenario & troubleshooting

**Symptom:** trace bị tách thành nhiều roots sau message publish.

**Evidence:** producer/consumer có khác TraceId; message metadata thiếu trace context.

**Hypothesis:** context không inject/extract.

**Diagnosis:** inspect instrumentation config và message properties.

**Fix:** standardize propagation, ensure consumer starts span with extracted context.

**Verification:** end-to-end trace từ HTTP ingress tới consumer/dependencies.

Một lỗi khác: retry/redelivery span bị ghi như child tuần tự của attempt trước, làm causal graph sai. Mỗi attempt nên phản ánh đúng messaging semantics.

## 7. Common mistakes

- Dùng một `CorrelationId` cho mọi loại correlation.
- Log high-cardinality IDs thành metrics labels.
- Không propagate context qua queue.
- Giữ một Activity sống hàng giờ để đại diện queued message thay vì model send/process spans.
- Sampling chỉ ở consumer làm trace fragments khó ghép.
- Ghi payload nhạy cảm vào spans.

## 8. Alternatives

- **Structured logs + business IDs:** đủ cho hệ thống nhỏ, nhưng cross-service latency khó nhìn hơn.
- **Tracing + metrics + logs:** tốt cho distributed production systems.
- **Broker-native diagnostics:** bổ sung nhưng không thay application spans/business context.

## 9. Trade-offs

### Advantages

- Tìm causal path nhanh hơn.
- Phân biệt queue wait với processing latency.
- Correlate retries/dependencies tốt hơn.

### Costs / Risks

- Telemetry volume/cost tăng.
- Context propagation/security cần governance.
- Sampling sai có thể bỏ mất traces quan trọng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace, span, TraceId và business ID khác nhau.

### Middle

Propagate trace context qua HTTP/message và thêm structured attributes hữu ích.

### Senior

Thiết kế async trace semantics, sampling và incident queries.

### Technical Lead / Architect

Đặt observability contract toàn hệ thống: propagation standard, sensitive-data policy, retention/cost và dashboard/SLO strategy.

## 11. Key takeaway

- Async messaging cần explicit causal context propagation.
- Queue wait là latency riêng cần thấy được, không nên bị giấu trong “background processing”.
- Trace ID, message ID và business ID phục vụ ba mục tiêu khác nhau.

# 9. Vue 3 reactivity, `computed` và `watch`: tránh duplicate state, race async và side effect khó debug trong full-stack UI

## 1. What is it?

Vue 3 reactivity theo dõi dependencies của reactive state để update derived values và UI khi dependency thay đổi.

Ba khái niệm thường bị trộn:

- `ref` / `reactive`: source state;
- `computed`: derived state;
- `watch`: chạy side effect khi dependency thay đổi.

Mental model:

```text
source state
   |
   +--> computed derived value
   |
   +--> render
   |
   +--> watch -> side effect (API call, persistence...)
```

Nếu một value có thể tính từ state khác, thường không nên copy nó thành state thứ hai.

## 2. Why does it exist?

UI thay đổi liên tục theo user input, API response và route state. Manual DOM synchronization dễ tạo inconsistent state.

Reactive system tự theo dependency graph. Nhưng nếu developer dùng `watch` cho mọi thứ, code trở thành chuỗi side effects khó đoán.

## 3. How does it work?

Ví dụ:

```ts
const price = ref(100)
const quantity = ref(2)

const total = computed(() => price.value * quantity.value)
```

`total` không cần setter/update thủ công.

Nếu dùng duplicate state:

```ts
const total = ref(0)
watch([price, quantity], () => {
  total.value = price.value * quantity.value
})
```

thì bạn thêm một synchronization obligation không cần thiết.

`watch` phù hợp hơn với side effects như gọi API khi filter đổi.

## 4. Practical implementation

Search box có race async:

```ts
const query = ref('')
const results = ref<SearchResult[]>([])

watch(query, async (value, _, onCleanup) => {
  const controller = new AbortController()
  onCleanup(() => controller.abort())

  if (!value.trim()) {
    results.value = []
    return
  }

  const response = await fetch(
    `/api/search?q=${encodeURIComponent(value)}`,
    { signal: controller.signal }
  )

  results.value = await response.json()
})
```

Nếu user gõ nhanh, previous request bị cancel khi query mới xuất hiện. Nếu không, response cũ có thể đến sau response mới và overwrite results.

## 5. Real production scenario

Product search UI:

1. user gõ `iph`;
2. request A bắt đầu;
3. user gõ `iphone`;
4. request B bắt đầu;
5. B trả về sau 100 ms;
6. A trả về sau 700 ms;
7. A overwrite results của B.

Backend hoàn toàn đúng, nhưng frontend có stale async race.

Cancellation hoặc request sequence guard giải quyết vấn đề.

## 6. Failure scenario & troubleshooting

**Symptom:** UI đôi lúc hiển thị search results cũ dù network tab cho thấy request mới thành công.

**Evidence:** response order khác request order.

**Hypothesis:** stale async completion overwrites current state.

**Diagnosis:** browser DevTools network timing + component logs.

**Fix:** abort stale request hoặc compare request token/version trước khi assign.

**Verification:** throttle network, gõ nhanh, đảm bảo latest intent wins.

## 7. Common mistakes

- Dùng `watch` để maintain derived state thay vì `computed`.
- Deep-watch object lớn gây work không cần thiết.
- Gọi API ở nhiều watchers cho cùng state.
- Không cleanup timers/subscriptions/requests.
- Mutate props trực tiếp.
- Đưa toàn server response vào global store dù chỉ một component cần.

## 8. Alternatives

- **Computed:** derived synchronous state.
- **Watch:** side effects/react to changes.
- **Explicit action/event handler:** tốt khi side effect gắn trực tiếp user action.
- **Server-state library/query abstraction:** hữu ích khi caching, dedupe, retries và invalidation client-side trở nên phức tạp.

## 9. Trade-offs

### Advantages

- Reactivity giảm manual synchronization.
- `computed` tạo predictable derived state.
- Cleanup-aware `watch` xử lý async side effects tốt.

### Costs / Risks

- Dependency graph implicit có thể khó debug nếu watchers quá nhiều.
- Deep reactivity trên data lớn có overhead.
- Client caching/state layer phức tạp dễ duplicate backend semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt source state, computed state và side effect.

### Middle

Viết watchers có cleanup, xử lý race/cancellation và component ownership rõ.

### Senior

Thiết kế server-state vs UI-state boundary, tránh duplicated sources of truth.

### Technical Lead / Architect

Quyết định state-management complexity thực sự cần; chuẩn hóa patterns cho API cancellation, error/loading state và observability frontend.

## 11. Key takeaway

- Derived state nên được derive, không copy rồi synchronize.
- Async UI cần xử lý stale response như một concurrency problem.
- `watch` là side-effect tool, không nên trở thành default data-flow mechanism.

# 10. Optimizely CMS content modeling và cache invalidation: thiết kế content boundary để editor linh hoạt mà hệ thống vẫn predictable

## 1. What is it?

Trong CMS, content modeling là cách biến editorial concepts thành content types, properties, blocks/components và hierarchy.

Với Optimizely CMS, thường có:

- page types;
- block/content types;
- reusable references;
- language/version/publication lifecycle.

Mental model không nên là “mỗi UI section = một block”. Content model cần phản ánh **editorial meaning và reuse boundary**.

Cache invalidation xuất hiện vì CMS page rendering thường đọc nhiều content items. Khi một shared block thay đổi, nhiều pages có thể cần output mới.

## 2. Why does it exist?

Nếu hard-code content trong views, editor cần developer cho mọi thay đổi. Nếu model quá generic kiểu “JSON blob” hoặc `FlexibleBlock` chứa mọi field, editor có tự do nhưng system mất validation, reuse semantics và maintainability.

CMS modeling cân bằng:

- editorial flexibility;
- structured content;
- component reuse;
- rendering predictability;
- search/indexing;
- cacheability.

## 3. How does it work?

Ví dụ product marketing page:

```text
ProductPage
  |- HeroBlock reference
  |- FeatureListBlock
  |- PromoBannerBlock (shared)
  |- SEO metadata
```

Một `PromoBannerBlock` có thể được dùng trên 50 pages. Nếu output page được cached nhưng dependency graph không được invalidated khi banner đổi, users thấy stale content.

Cache strategy cần hiểu dependency:

```text
Page cache entry
   depends on
Page + referenced blocks + language + personalization context
```

## 4. Practical implementation

Content type nên business-oriented:

```csharp
[ContentType(
    DisplayName = "Promo Banner",
    GUID = "b67f1e49-f1f2-4f15-9897-123456789abc")]
public class PromoBannerBlock : BlockData
{
    [Display(Name = "Heading", Order = 10)]
    public virtual string? Heading { get; set; }

    [Display(Name = "Body", Order = 20)]
    public virtual XhtmlString? Body { get; set; }

    [Display(Name = "Link", Order = 30)]
    public virtual Url? Link { get; set; }
}
```

Không expose technical flags vô nghĩa cho editor như `UseDivWrapperV2` nếu chúng không phải content concept.

Với cache, key cần bao gồm dimensions có ảnh hưởng output như language/variant; invalidation cần gắn với content publication/change events hoặc framework-supported dependency mechanisms thay vì TTL dài duy nhất.

## 5. Real production scenario

Marketing team sửa legal disclaimer trong shared footer block. Authoring UI hiển thị version mới, nhưng public site một số pages vẫn hiển thị disclaimer cũ trong 30 phút vì CDN/app cache chỉ dựa TTL.

Đây không chỉ là “cache issue”. Với legal content, staleness budget có thể gần zero và purge/invalidation path phải rõ.

## 6. Failure scenario & troubleshooting

**Symptom:** editor publish thành công nhưng frontend vẫn thấy content cũ ở một subset users/regions.

**Evidence:** CMS API trả content mới; app cache/CDN edge trả response cũ.

**Hypothesis:** invalidation không propagate hết cache layers.

**Diagnosis:** trace request qua browser cache → CDN → application cache → CMS; inspect `Age`, cache headers, surrogate/cache keys nếu có.

**Fix:** correct invalidation/purge strategy hoặc short TTL cho content critical; ensure shared dependency invalidates dependent pages.

**Verification:** publish test content và quan sát propagation across layers/regions.

## 7. Common mistakes

- Thiết kế content types theo layout pixels thay vì editorial concept.
- Một mega-block có hàng chục optional fields cho mọi use case.
- Reuse shared block nhưng không nghĩ dependency invalidation.
- Cache personalized content bằng key thiếu segment/user dimension.
- Purge toàn site cho mọi content change dù impact nhỏ.
- Để editor tự nhập raw HTML/script không có security governance.

## 8. Alternatives

- **Traditional coupled CMS:** rendering trong cùng platform, đơn giản hơn cho nhiều website.
- **Headless CMS:** frontend độc lập, nhưng content delivery/cache/invalidation integration phức tạp hơn.
- **Composable architecture:** linh hoạt integrations nhưng tăng ownership/operations.
- **Hard-coded application content:** hợp lý cho UI labels/static engineering-owned text, không phải mọi text đều cần CMS.

## 9. Trade-offs

### Advantages

- Structured model cho editor autonomy và validation.
- Reusable blocks giảm duplication.
- Correct caching cải thiện performance và origin load.

### Costs / Risks

- Over-modeling làm authoring khó.
- Shared content tăng invalidation fan-out.
- Headless/composable flow thêm network/cache/search consistency complexity.
- CMS upgrades cần backward compatibility với existing content types/data.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu page/block/content type khác view component thuần kỹ thuật.

### Middle

Implement content types, validation, rendering và cache dimensions đúng.

### Senior

Thiết kế reuse boundary, publication behavior, search/cache invalidation và migration khi content model đổi.

### Technical Lead / Architect

Quyết định traditional vs headless/composable, ownership của content delivery/cache/CDN, và nơi nào CMS không nên được dùng để tránh unnecessary complexity.

## 11. Key takeaway

- Content model nên phản ánh editorial/business meaning, không chỉ layout.
- Shared content tạo dependency graph; cache invalidation phải hiểu graph đó.
- CMS architecture tốt cân bằng editor flexibility với predictability, security và operational cost.
