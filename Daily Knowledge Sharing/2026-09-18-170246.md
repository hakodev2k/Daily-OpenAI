# 1. .NET `IAsyncEnumerable<T>`: streaming, cancellation và backpressure boundary

## 1. What is it?

`IAsyncEnumerable<T>` biểu diễn một chuỗi phần tử được tạo bất đồng bộ theo thời gian. Mental model đúng không phải “`Task<List<T>>` nhưng hiện đại hơn”, mà là **pull-based asynchronous stream**: consumer yêu cầu phần tử tiếp theo và producer có thể chờ I/O trước khi trả nó.

## 2. Why does it exist?

Nếu API phải đọc 500.000 records rồi tạo `List<T>` trước khi xử lý, memory và time-to-first-result tăng. Streaming cho phép xử lý từng phần khi dữ liệu đến, nhưng chỉ hữu ích khi toàn pipeline không buffer lại ở layer khác.

## 3. How does it work?

```text
Consumer MoveNextAsync()
        │
        ▼
Producer waits for I/O
        │
        ▼
Yield item ─────► Consumer processes
        │
        └──── next MoveNextAsync()
```

Consumer tạo nhịp pull tự nhiên; tuy nhiên nếu producer đọc từ queue/push source nhanh hơn consumer, application vẫn cần bounded buffer/backpressure mechanism như `Channel<T>`.

## 4. Practical implementation

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct)
{
    await foreach (var order in db.Orders
        .AsNoTracking()
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        yield return new OrderDto(order.Id, order.Total);
    }
}
```

Nếu expose qua HTTP, phải kiểm tra serializer/server/proxy có thực sự flush streaming hay buffer response.

## 5. Real production scenario

Một export service đọc hàng trăm nghìn orders. Trước đây endpoint materialize toàn bộ list và memory spike. Chuyển sang stream giúp giảm peak memory và trả dữ liệu sớm hơn, nhưng database connection được giữ suốt thời gian enumeration nên slow client có thể kéo dài resource lifetime.

## 6. Failure scenario & troubleshooting

**Symptom** → memory giảm nhưng DB connection pool bắt đầu cạn.  
**Evidence** → traces cho thấy query/reader sống theo toàn bộ HTTP response.  
**Hypothesis** → slow consumers giữ streaming database reader quá lâu.  
**Diagnosis** → đo stream duration, connection pool metrics và client throughput.  
**Fix** → pagination/chunk boundary, intermediate bounded buffering hoặc async export job.  
**Verification** → connection hold time nằm trong budget và pool không saturation.

## 7. Common mistakes

Gọi `ToListAsync()` trước khi `yield`; quên cancellation; enumerate cùng stream hai lần; giữ `DbContext` quá lâu; dùng streaming cho workload mà client cuối cùng vẫn cần toàn dataset trước khi làm gì.

## 8. Alternatives

`Task<List<T>>` đơn giản và đúng cho result nhỏ. Pagination phù hợp interactive APIs. `Channel<T>` phù hợp producer/consumer concurrency cần bounded capacity. Background export phù hợp dữ liệu lớn và long-running.

## 9. Trade-offs

### Advantages

Giảm peak memory, time-to-first-item tốt hơn và composition tự nhiên với async I/O.

### Costs / Risks

Resource lifetime dài hơn, cancellation/error giữa stream phức tạp và HTTP intermediaries có thể buffer.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async stream trả từng item thay vì materialize cả collection.

### Middle

Implement cancellation và xử lý enumeration errors.

### Senior

Đo connection lifetime, buffering và slow-consumer behavior.

### Technical Lead / Architect

Quyết định streaming, pagination hay asynchronous export dựa trên workload và resource ownership.

## 11. Key takeaway

- Streaming giảm buffering nhưng có thể kéo dài resource lifetime.
- Cancellation phải đi xuyên enumeration.
- `IAsyncEnumerable<T>` không tự giải quyết push-source backpressure.

# 2. ASP.NET Core Health Checks: liveness/readiness không phải business monitoring

## 1. What is it?

Health Check là endpoint/mecanism cho platform đánh giá process có sống và có sẵn sàng nhận traffic hay không. Mental model quan trọng: **orchestrator control signal**, không phải dashboard tổng hợp mọi dependency trong doanh nghiệp.

## 2. Why does it exist?

Load balancer/Kubernetes cần biết instance nào nên nhận traffic và instance nào cần restart. Nếu một process đang startup migration/cache warm-up hoặc đã rơi vào trạng thái không phục vụ được, traffic routing phải phản ứng.

## 3. How does it work?

```text
Liveness ─► Process có cần restart?
Readiness ─► Instance có nên nhận traffic?
Business monitoring ─► Hệ thống có đang đáp ứng SLO?
```

Readiness có thể tạm fail khi instance không thể phục vụ. Liveness phải thận trọng: dependency tạm mất không có nghĩa restart process sẽ sửa được.

## 4. Practical implementation

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<StartupReadyCheck>("startup-ready",
        tags: new[] { "ready" });

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready")
});
```

Không nên chạy query nặng hoặc gọi mọi downstream service mỗi vài giây từ probe.

## 5. Real production scenario

API vừa deploy cần load reference data trước khi phục vụ. Liveness vẫn healthy để process không bị restart loop; readiness chỉ healthy sau khi startup state hoàn tất.

## 6. Failure scenario & troubleshooting

**Symptom** → toàn bộ pods restart liên tục khi SQL outage.  
**Evidence** → liveness probe phụ thuộc SQL.  
**Hypothesis** → external dependency failure bị diễn giải thành process failure.  
**Diagnosis** → inspect probe config, restart count và SQL incident timeline.  
**Fix** → liveness chỉ kiểm tra process-critical state; dependency degradation đi vào readiness/metrics/alerts phù hợp.  
**Verification** → SQL outage không tạo restart storm.

## 7. Common mistakes

Dùng cùng endpoint cho liveness/readiness; health check query quá nặng; trả 200 vì process sống dù startup chưa ready; dùng probe thay SLO monitoring.

## 8. Alternatives

Metrics/alerts theo error rate và latency dùng cho operational monitoring. Synthetic tests kiểm tra user journey. Health probes chỉ là một control surface cho traffic/process lifecycle.

## 9. Trade-offs

### Advantages

Automated routing/recovery và deployment validation tốt hơn.

### Costs / Risks

Probe sai có thể tự gây outage hoặc restart storm; dependency checks tạo extra load.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt alive và ready.

### Middle

Implement tagged health checks và probe endpoints.

### Senior

Thiết kế dependency degradation semantics và tránh probe-induced failures.

### Technical Lead / Architect

Định nghĩa health contract chung giữa application, orchestrator và release platform.

## 11. Key takeaway

- Liveness hỏi “restart có giúp không?”.
- Readiness hỏi “có nên route traffic không?”.
- SLO/business health cần metrics và synthetic monitoring riêng.

# 3. EF Core `AsNoTrackingWithIdentityResolution`: read performance và object identity

## 1. What is it?

`AsNoTrackingWithIdentityResolution()` chạy query không attach entities vào `DbContext` Change Tracker dài hạn, nhưng dùng temporary identity resolution để cùng một database entity trong result được biểu diễn bởi cùng một object instance.

## 2. Why does it exist?

`AsNoTracking()` giảm tracking overhead cho read-only query, nhưng join/include có thể materialize cùng entity nhiều lần. Một số object graphs cần reference identity nhất quán dù không cần update tracking.

## 3. How does it work?

```text
Rows
Order 1 + Customer 7
Order 2 + Customer 7
        │
        ▼
Temporary identity map
Customer 7 ─► một object instance
        │
        ▼
Result graph, không tracked bởi DbContext
```

Temporary tracker chỉ phục vụ materialization/identity resolution và không trở thành normal change tracking state.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .AsNoTrackingWithIdentityResolution()
    .Include(x => x.Customer)
    .Where(x => x.CreatedAt >= from)
    .ToListAsync(ct);
```

Nếu endpoint chỉ cần DTO, projection thường tốt hơn:

```csharp
var rows = await db.Orders
    .Where(x => x.CreatedAt >= from)
    .Select(x => new OrderRow(x.Id, x.Customer.Name, x.Total))
    .ToListAsync(ct);
```

## 5. Real production scenario

Reporting API load orders với repeated customer references. Normal tracking tốn memory không cần thiết; plain no-tracking tạo duplicate customer objects. Identity-resolution mode giảm duplicate materialization nhưng projection vẫn có thể là giải pháp đơn giản hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → team đổi sang identity resolution nhưng query vẫn chậm.  
**Evidence** → SQL trả hàng triệu joined rows.  
**Hypothesis** → bottleneck là query shape/I/O chứ không phải tracking.  
**Diagnosis** → inspect generated SQL, row count, execution plan và allocations.  
**Fix** → projection, pagination hoặc query shape trước.  
**Verification** → đo DB I/O, allocation và latency lại.

## 7. Common mistakes

Dùng cho mọi query; nhầm identity resolution với optimistic concurrency; load full entities khi chỉ cần vài fields; không đo cartesian expansion.

## 8. Alternatives

`AsTracking()` cho update workflow. `AsNoTracking()` đơn giản hơn khi duplicate reference identity không quan trọng. Projection thường tối ưu nhất cho API read model.

## 9. Trade-offs

### Advantages

Không giữ normal tracking state nhưng tránh duplicate entity instances trong result graph.

### Costs / Risks

Temporary identity map vẫn có CPU/memory cost và không sửa SQL access pattern xấu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu tracking dùng cho update state.

### Middle

Chọn tracking/no-tracking theo use case.

### Senior

Phân tích materialization, identity và query-shape cost riêng biệt.

### Technical Lead / Architect

Ưu tiên read-model projection và chỉ dùng entity graphs khi domain/application thực sự cần.

## 11. Key takeaway

- No-tracking không phải một chế độ duy nhất.
- Identity resolution giải quyết object identity, không giải quyết database I/O.
- Projection thường là baseline tốt cho read-only API.

# 4. PostgreSQL JSONB + GIN: flexible attributes nhưng không miễn phí schema design

## 1. What is it?

`jsonb` lưu JSON dưới binary representation hỗ trợ operators và indexing. GIN index phù hợp tra cứu membership/containment trên nhiều keys/values. Mental model: **semi-structured field trong relational database**, không phải lý do bỏ relational modeling.

## 2. Why does it exist?

Một product catalog có core fields ổn định nhưng category-specific attributes thay đổi. Tạo hàng trăm nullable columns hoặc EAV model có thể khó quản lý; `jsonb` cho phép phần flexible coexist với relational constraints.

## 3. How does it work?

```sql
CREATE TABLE products (
    id bigint PRIMARY KEY,
    sku text NOT NULL UNIQUE,
    attributes jsonb NOT NULL
);

CREATE INDEX ix_products_attributes_gin
ON products USING gin (attributes);
```

Query containment:

```sql
SELECT id, sku
FROM products
WHERE attributes @> '{"color":"black"}';
```

GIN index tăng write/storage cost vì index nhiều tokens/entries.

## 4. Practical implementation

Với field truy vấn cực thường xuyên và cần type/constraint rõ, cân nhắc generated/extracted column thay vì luôn query JSON path.

```sql
ALTER TABLE products
ADD COLUMN brand text
GENERATED ALWAYS AS (attributes ->> 'brand') STORED;

CREATE INDEX ix_products_brand ON products(brand);
```

## 5. Real production scenario

Marketplace có laptop attributes khác tyre attributes. `jsonb` giữ flexible metadata, còn `sku`, ownership, price và transactional invariants vẫn là relational columns/tables.

## 6. Failure scenario & troubleshooting

**Symptom** → search filter chậm và write amplification tăng.  
**Evidence** → GIN index rất lớn, query filters trên paths không phù hợp index.  
**Hypothesis** → JSONB trở thành dumping ground.  
**Diagnosis** → `EXPLAIN (ANALYZE, BUFFERS)`, index size, write rate và access patterns.  
**Fix** → selective indexes/extracted columns, schema cleanup hoặc search engine nếu workload là search-centric.  
**Verification** → giảm buffers/latency và write overhead trong representative workload.

## 7. Common mistakes

Đưa mọi column vào JSON; không validate shape; GIN index toàn document mặc định; dùng JSONB để tránh migrations; join/business invariant nằm trong opaque document.

## 8. Alternatives

Normal columns tốt nhất cho stable typed data. Child tables phù hợp relational multi-valued attributes. Elasticsearch phù hợp full-text/faceted search chuyên sâu nhưng không nên là transactional source of truth.

## 9. Trade-offs

### Advantages

Schema flexibility và queryability tốt trong cùng PostgreSQL transaction boundary.

### Costs / Risks

Index lớn, weaker schema guarantees và query complexity nếu lạm dụng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu JSONB là một data type, không phải schema-free database.

### Middle

Viết containment query và đọc plan.

### Senior

Thiết kế selective indexes theo access pattern và đo I/O/write cost.

### Technical Lead / Architect

Quyết định phần dữ liệu nào thật sự flexible và phần nào phải giữ relational invariant.

## 11. Key takeaway

- JSONB bổ sung relational model, không thay thế nó.
- GIN index phải dựa trên access pattern và write budget.
- Stable business fields nên có schema/constraints rõ.

# 5. Domain Event vs Integration Event: transaction boundary và contract ownership

## 1. What is it?

Domain Event mô tả điều có ý nghĩa vừa xảy ra trong domain boundary; Integration Event là contract phát ra ngoài boundary để hệ thống khác phản ứng. Chúng có thể liên quan cùng business fact nhưng có ownership, timing và compatibility requirements khác nhau.

## 2. Why does it exist?

Nếu internal domain object được serialize thẳng lên broker, thay đổi domain model trở thành breaking integration contract. Ngược lại, nếu mọi internal reaction đều đi qua external broker, local consistency và complexity bị đẩy ra distributed system không cần thiết.

## 3. How does it work?

```text
Order Aggregate
   │ raises Domain Event
   ▼
Application transaction
   ├─ local handlers / state changes
   └─ Outbox Integration Event
            │ after commit
            ▼
         Message Broker
            ▼
      Other Bounded Context
```

Data ownership thuộc Order bounded context. External consumer không được dựa vào internal aggregate shape.

## 4. Practical implementation

```csharp
public sealed record OrderConfirmedDomainEvent(Guid OrderId);

public sealed record OrderConfirmedV1(
    Guid OrderId,
    DateTimeOffset ConfirmedAt,
    string CustomerReference);
```

Application handler có thể map domain event sang versioned integration event và ghi Outbox trong cùng local transaction.

## 5. Real production scenario

Order confirmation cần cập nhật local audit state và thông báo Notification service. Local reaction có thể dùng domain event; cross-service notification dùng integration contract ổn định qua broker.

## 6. Failure scenario & troubleshooting

**Symptom** → refactor domain property làm consumer khác crash.  
**Evidence** → broker payload serialize trực tiếp aggregate/internal event.  
**Hypothesis** → internal model bị dùng như public contract.  
**Diagnosis** → trace event type ownership và consumer dependencies.  
**Fix** → explicit integration DTO/versioning + Outbox publication.  
**Verification** → internal refactor không đổi external contract nếu semantics không đổi.

## 7. Common mistakes

Gọi mọi event là integration event; publish trước transaction commit; domain event handler gọi remote API đồng bộ; không version external schema; chia sẻ event assembly giữa bounded contexts.

## 8. Alternatives

Direct application service call đơn giản hơn cho local reaction. REST phù hợp synchronous query/command khi caller cần immediate response. Event không cần tồn tại nếu coupling đơn giản và explicit call rõ hơn.

## 9. Trade-offs

### Advantages

Tách internal domain evolution khỏi external contract và làm transaction boundary rõ.

### Costs / Risks

Mapping/versioning thêm code; integration event đưa vào eventual consistency và operational burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event biểu diễn fact đã xảy ra.

### Middle

Phân biệt local handler và broker publication.

### Senior

Thiết kế transaction, Outbox, versioning và idempotent consumers.

### Technical Lead / Architect

Đặt bounded-context ownership và quyết định khi nào asynchronous integration thực sự cần thiết.

## 11. Key takeaway

- Domain model không nên vô tình trở thành public message contract.
- Integration event cần versioning và ownership rõ.
- Cross-boundary publication phải tôn trọng local transaction commit.

# 6. Bulkhead Pattern: cô lập capacity để dependency chậm không kéo sập toàn service

## 1. What is it?

Bulkhead chia resource/capacity thành các vùng độc lập để một workload hoặc dependency không tiêu thụ toàn bộ capacity. Tên đến từ vách ngăn tàu: một khoang ngập không làm toàn tàu chìm.

## 2. Why does it exist?

Nếu mọi outbound call dùng chung concurrency không giới hạn, một dependency chậm có thể khiến hàng nghìn requests chờ, giữ memory/connections và cuối cùng làm cả service mất khả năng phục vụ endpoints không liên quan.

## 3. How does it work?

```text
Incoming requests
   ├─ Pricing calls   ─► bounded concurrency 50
   ├─ Reviews calls   ─► bounded concurrency 20
   └─ Core DB work    ─► capacity riêng
```

Bulkhead thường kết hợp timeout, queue limit và rejection/fallback semantics.

## 4. Practical implementation

Một primitive đơn giản:

```csharp
private readonly SemaphoreSlim _pricingSlots = new(50, 50);

public async Task<Price> GetPriceAsync(string sku, CancellationToken ct)
{
    if (!await _pricingSlots.WaitAsync(TimeSpan.FromMilliseconds(100), ct))
        throw new PricingCapacityExceededException();

    try
    {
        return await pricingClient.GetAsync(sku, ct);
    }
    finally
    {
        _pricingSlots.Release();
    }
}
```

Production policy cần metrics cho active/queued/rejected work và không nên queue vô hạn.

## 5. Real production scenario

Product page gọi Reviews API. Reviews latency tăng 20 giây. Không bulkhead, request count tăng làm toàn web app cạn outbound capacity. Với bounded reviews capacity, reviews degrade nhưng checkout/core catalog vẫn phục vụ.

## 6. Failure scenario & troubleshooting

**Symptom** → một dependency incident làm unrelated endpoints latency tăng.  
**Evidence** → thread/tasks/connections tập trung chờ cùng dependency.  
**Hypothesis** → shared capacity exhaustion.  
**Diagnosis** → dependency traces, concurrency gauges, queue length và rejection rate.  
**Fix** → bounded concurrency/queue + timeout + fallback theo business priority.  
**Verification** → dependency load test không phá SLO của unrelated flows.

## 7. Common mistakes

Queue vô hạn trước bulkhead; capacity chọn tùy ý; reject nhưng không có metrics; đặt semaphore toàn service làm giảm throughput; nhầm bulkhead với circuit breaker.

## 8. Alternatives

Circuit Breaker ngừng gọi dependency đang lỗi; timeout giới hạn một attempt; separate process/service tạo isolation mạnh hơn nhưng operational cost cao hơn.

## 9. Trade-offs

### Advantages

Failure isolation và predictable resource usage tốt hơn.

### Costs / Risks

Có deliberate rejection, tuning complexity và nguy cơ underutilization nếu partition quá cứng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu bounded concurrency bảo vệ capacity.

### Middle

Implement limit + timeout + cancellation.

### Senior

Tune bằng dependency latency/capacity metrics và failure tests.

### Technical Lead / Architect

Phân loại workload theo business criticality và chọn isolation boundary phù hợp.

## 11. Key takeaway

- Bulkhead giới hạn blast radius của slow/failing dependency.
- Queue vô hạn chỉ trì hoãn failure.
- Isolation phải đi cùng timeout, metrics và business fallback.

# 7. Azure Functions cold start: latency, scaling và workload placement

## 1. What is it?

Cold start là latency phát sinh khi platform cần cấp/khởi tạo worker trước khi function xử lý invocation. Nó gồm infrastructure allocation, runtime/process startup và application initialization. Mức độ phụ thuộc hosting plan, runtime và workload.

## 2. Why does it exist?

Serverless elasticity cho phép scale down và scale out theo demand. Đổi lại, capacity không luôn warm sẵn như process chạy liên tục.

## 3. How does it work?

```text
Trigger arrives
   │
   ├─ warm worker ─► execute
   │
   └─ no capacity
        └─ allocate/start worker
             └─ load runtime/app
                  └─ execute
```

Scale behavior khác giữa hosting options; workload latency-sensitive cần chọn plan dựa trên requirement thực tế thay vì chỉ “serverless rẻ hơn”.

## 4. Practical implementation

Giữ startup nhẹ và tránh blocking initialization:

```csharp
public sealed class ProcessOrderFunction
{
    private readonly OrderProcessor _processor;

    public ProcessOrderFunction(OrderProcessor processor) => _processor = processor;

    [Function("ProcessOrder")]
    public Task Run(
        [ServiceBusTrigger("orders")] string message,
        CancellationToken ct) => _processor.ProcessAsync(message, ct);
}
```

External clients nên được reused qua DI; không tạo expensive client per invocation.

## 5. Real production scenario

Queue-triggered image processing chấp nhận vài giây startup delay nên Consumption-style elasticity hợp lý. Authentication API yêu cầu p99 thấp liên tục có thể phù hợp App Service/always-warm compute hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 spike sau idle hoặc burst traffic.  
**Evidence** → invocation telemetry correlate với new worker startup.  
**Hypothesis** → cold start/scale-out initialization.  
**Diagnosis** → Application Insights startup/invocation traces, dependency init và plan scaling metrics.  
**Fix** → giảm startup work, chọn hosting option/warm capacity phù hợp hoặc đổi workload placement.  
**Verification** → burst/idle load test đạt latency budget.

## 7. Common mistakes

Đổ mọi latency cho cold start; heavy startup dependency graph; synchronous network call khi startup; chọn plan chỉ theo compute price; không test burst scaling.

## 8. Alternatives

App Service/Worker Service phù hợp steady always-on workloads. Container Apps phù hợp containerized event/HTTP workloads với scaling khác. Logic Apps phù hợp workflow orchestration low-code hơn.

## 9. Trade-offs

### Advantages

Elastic scaling, event integration và giảm server-management burden.

### Costs / Risks

Startup latency, platform limits, scaling behavior và cost khó dự đoán với workload không phù hợp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

### Middle

### Senior

### Technical Lead / Architect

Chọn Functions/App Service/Container Apps theo latency, throughput, operational và cost requirements.

## 11. Key takeaway

- Cold start là trade-off của elastic capacity, không phải bug duy nhất của Functions.
- Hosting plan phải khớp latency SLO.
- Đo startup, queue và execution latency riêng biệt.

# 8. CI/CD database migration: expand/contract để release không khóa deployment

## 1. What is it?

Expand/contract là chiến lược thay schema qua nhiều bước tương thích ngược: đầu tiên mở rộng schema để cả code cũ/mới cùng chạy, sau đó chuyển traffic/data, cuối cùng mới xóa contract cũ.

## 2. Why does it exist?

Rolling/slot deployment tạo thời gian code version N và N+1 cùng tồn tại. Migration kiểu rename/drop column ngay có thể làm một version crash dù deployment artifact hoàn toàn đúng.

## 3. How does it work?

```text
Commit
 → Build
 → Test
 → Artifact
 → Expand schema
 → Deploy compatible code
 → Health validation
 → Monitor
 → Backfill/switch reads
 → Contract old schema later
```

Database migration là release concern, không chỉ startup concern.

## 4. Practical implementation

Thay vì rename `FullName -> DisplayName` trực tiếp:

```sql
ALTER TABLE Customers ADD DisplayName nvarchar(200) NULL;
```

Version mới dual-read/dual-write có kiểm soát, backfill data, chuyển reads, rồi release sau mới drop `FullName`.

## 5. Real production scenario

App Service deployment slot swap có old/new instances trong transition. Một migration drop column trước khi old instances drain tạo 500s ngay giữa release.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment health check fail ngay sau migration.  
**Evidence** → old application logs “invalid column” hoặc new app thiếu expected field.  
**Hypothesis** → schema/code compatibility window bị phá.  
**Diagnosis** → map artifact versions với migration order và active instances.  
**Fix** → restore compatible schema/roll-forward; thiết kế expand/contract cho lần sau.  
**Verification** → run N và N+1 đồng thời trên expanded schema trong staging.

## 7. Common mistakes

Auto-run destructive migration khi app startup; rollback binary nhưng schema không rollback; long table lock; backfill trong một transaction lớn; không test old/new compatibility.

## 8. Alternatives

Maintenance window đơn giản hơn nếu business chấp nhận downtime. Blue-Green vẫn cần schema compatibility nếu hai versions dùng chung database. Feature flags giúp tách activation khỏi deployment.

## 9. Trade-offs

### Advantages

Giảm release coupling và hỗ trợ zero/low-downtime deployment.

### Costs / Risks

Nhiều bước, temporary duplicate schema/code và cleanup dễ bị quên.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu migration có thể break code đang chạy.

### Middle

Viết backward-compatible schema changes.

### Senior

Thiết kế backfill, rollout, monitoring và rollback/roll-forward.

### Technical Lead / Architect

Định nghĩa database release policy xuyên CI/CD và ownership cleanup.

## 11. Key takeaway

- Database schema là shared runtime contract.
- Zero-downtime release thường cần expand trước, contract sau.
- Rollback application không đảm bảo rollback schema an toàn.

# 9. `dotnet-counters`: điều tra CPU, GC và ThreadPool bằng runtime evidence

## 1. What is it?

`dotnet-counters` là diagnostics tool đọc runtime/application counters từ process .NET. Mental model: **low-overhead live telemetry để định hướng hypothesis**, không phải profiler trả lời mọi root cause.

## 2. Why does it exist?

Khi API “chậm”, đoán do SQL, GC hay ThreadPool thường dẫn đến fix sai. Runtime counters cho signal nhanh về CPU, allocation, GC heap, exception rate, thread pool queue và nhiều metrics khác.

## 3. How does it work?

```text
Production symptom
      │
      ▼
dotnet-counters / metrics
      │
      ├─ CPU high
      ├─ allocation/GC high
      ├─ ThreadPool queue high
      └─ exception rate high
             │
             ▼
      chọn profiler/dump/trace tiếp theo
```

Counters là aggregate time-series; chúng không chỉ ra chính xác method nào allocate hoặc consume CPU.

## 4. Practical implementation

```bash
dotnet-counters monitor --process-id 1234 System.Runtime
```

Trong incident, capture cùng thời điểm với request metrics và dependency traces. Nếu allocation rate/GC cao, bước tiếp theo có thể là allocation profile; nếu CPU cao, dùng CPU trace/flame graph.

## 5. Real production scenario

Sau release, p99 tăng từ 300 ms lên 2 s. CPU chỉ 40%, nhưng ThreadPool queue length tăng và thread count leo dần. Investigation tiếp theo tìm thấy sync-over-async ở một dependency wrapper.

## 6. Failure scenario & troubleshooting

**Symptom** → team thấy GC count tăng và kết luận “GC là root cause”.  
**Evidence** → allocation rate tăng nhưng pause time nhỏ; SQL latency mới correlate với request latency.  
**Hypothesis** → counter bị diễn giải sai.  
**Diagnosis** → correlate logs + metrics + traces; dùng profiler/trace để xác nhận.  
**Fix** → xử lý bottleneck đã chứng minh.  
**Verification** → p95/p99 và runtime signals cải thiện sau change.

## 7. Common mistakes

Chụp counters khi incident đã hết; nhìn một metric cô lập; tối ưu allocation nhỏ khi bottleneck là I/O; chạy diagnostics quá nặng mà không hiểu production impact.

## 8. Alternatives

Application Insights/Azure Monitor phù hợp continuous monitoring. `dotnet-trace` thu event trace sâu hơn. `dotnet-dump` phù hợp memory/crash investigation. Profiler cung cấp call stacks/allocation attribution.

## 9. Trade-offs

### Advantages

Nhanh, tương đối low-overhead và hữu ích để localize runtime class của vấn đề.

### Costs / Risks

Aggregate signal thiếu code attribution; cần kỹ năng correlation để tránh false conclusion.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết CPU/memory/GC/ThreadPool là các signals khác nhau.

### Middle

Capture counters và correlate với request symptoms.

### Senior

Chuyển counter evidence thành hypothesis rồi dùng đúng diagnostic tool tiếp theo.

### Technical Lead / Architect

Xây incident playbook: metrics → traces → runtime diagnostics → remediation → verification.

## 11. Key takeaway

- Measure trước khi optimize.
- Counter giúp localize, không tự chứng minh root cause.
- Luôn correlate runtime signals với user-facing latency/error metrics.

# 10. Optimizely CMS content modeling: page/block boundary, editor workflow và cache impact

## 1. What is it?

Content modeling định nghĩa cách business content được biểu diễn thành page types, blocks/components, fields và hierarchy. Trong Optimizely CMS, code-defined content types cung cấp schema cho editors. Mental model: **content model là domain model cho editorial work**, không chỉ class hierarchy để render UI.

## 2. Why does it exist?

Nếu mỗi trang là một blob HTML tự do, editor có flexibility nhưng reuse, validation, search, personalization và design consistency giảm. Nếu model quá cứng, mỗi campaign nhỏ lại cần developer deployment.

## 3. How does it work?

```text
Editor
  │
  ▼
Content Type / Page / Block
  │ publish
  ▼
CMS content repository
  │
  ├─ rendering application
  ├─ cache
  └─ search/index synchronization
```

Page thường đại diện routable content/context; block đại diện reusable composable content. Boundary phải theo editorial reuse và ownership, không chỉ theo visual `<div>`.

## 4. Practical implementation

```csharp
[ContentType(DisplayName = "Article Page", GUID = "11111111-1111-1111-1111-111111111111")]
public class ArticlePage : PageData
{
    [Display(Name = "Heading", Order = 10)]
    public virtual string Heading { get; set; } = string.Empty;

    [Display(Name = "Main content", Order = 20)]
    public virtual ContentArea MainContent { get; set; } = default!;
}
```

Một reusable Promo Block nên có semantic fields như heading, image, CTA thay vì một raw HTML field.

## 5. Real production scenario

Marketing site có product landing pages dùng Hero, Promo và FAQ blocks. Reusable blocks giúp editors compose page mà vẫn giữ design system. Nhưng shared block update có thể invalidate nhiều pages/cache entries và ảnh hưởng search indexing.

## 6. Failure scenario & troubleshooting

**Symptom** → editor publish block mới nhưng một số pages vẫn hiển thị nội dung cũ.  
**Evidence** → CMS content version đúng nhưng CDN/application cache còn stale.  
**Hypothesis** → invalidation không propagate qua delivery layers.  
**Diagnosis** → trace publish event → CMS cache → app cache → CDN cache key/purge.  
**Fix** → xác định ownership của invalidation và version/cache strategy.  
**Verification** → publish test cập nhật đúng mọi dependent surfaces trong freshness SLA.

## 7. Common mistakes

Tạo block cho từng visual fragment; dùng raw HTML quá nhiều; content type chứa technical fields editors không hiểu; coupling renderer trực tiếp vào third-party API; thay schema breaking mà không có migration/default strategy.

## 8. Alternatives

Traditional CMS rendering đơn giản cho server-rendered site. Headless CMS phù hợp nhiều channels nhưng tăng frontend/API/cache complexity. Static content/config có thể đủ nếu editors không cần workflow.

## 9. Trade-offs

### Advantages

Structured content, reuse, validation và editor autonomy tốt hơn.

### Costs / Risks

Model evolution, cache invalidation, migrations và editorial training tạo operational cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu page, block và content field.

### Middle

Implement content types/rendering và editor-friendly validation.

### Senior

Thiết kế reuse, cache, search và upgrade-compatible model.

### Technical Lead / Architect

Cân bằng editorial autonomy, composability, delivery architecture và long-term content migration cost.

## 11. Key takeaway

- Content model phải phản ánh editorial semantics, không chỉ UI layout.
- Reuse tạo dependency và invalidation consequences.
- Headless/composable architecture chỉ đáng dùng khi channel/ownership requirements biện minh complexity.
