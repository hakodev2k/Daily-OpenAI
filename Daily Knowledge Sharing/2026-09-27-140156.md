# 1. .NET Large Object Heap: allocation pressure, compaction và pooling

## 1. What is it?

Large Object Heap (LOH) là vùng managed heap mà CLR thường dùng cho object lớn, điển hình từ khoảng 85 KB. Mental model quan trọng: object lớn không chỉ “tốn nhiều RAM”; allocation pattern của chúng có thể tạo GC pause, fragmentation và memory peak khác hẳn nhiều object nhỏ.

## 2. Why does it exist?

Copy/compact object lớn thường đắt. CLR tách chúng để tránh phải di chuyển lượng memory lớn trong các collection thông thường. Đổi lại, application tạo liên tục buffer lớn có thể gây áp lực Gen 2/LOH và làm latency biến động.

## 3. How does it work?

Allocation lớn đi vào LOH; LOH được thu gom cùng Gen 2. Object sống lâu, fragmentation và tốc độ allocation quyết định pressure. Vì vậy flow cần nghĩ là:

`request → allocate large buffer → retain/release → Gen 2 GC → pause/fragmentation → latency`.

## 4. Practical implementation

Thay vì tạo buffer lớn cho mỗi request:

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(256 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, buffer.Length), ct);
    await destination.WriteAsync(buffer.AsMemory(0, read), ct);
}
finally
{
    pool.Return(buffer);
}
```

Pooling giảm allocation rate, nhưng buffer thuê có thể lớn hơn yêu cầu và dữ liệu cũ phải được xử lý phù hợp nếu có yêu cầu bảo mật.

## 5. Real production scenario

API xử lý ảnh nhận hàng trăm request đồng thời, mỗi request tạo vài `byte[1_000_000]`. RAM trung bình chưa đầy nhưng p99 tăng theo chu kỳ vì Gen 2 GC. Streaming + bounded pooling làm allocation rate giảm mạnh hơn việc chỉ tăng memory của container.

## 6. Failure scenario & troubleshooting

**Symptom** → latency spike và memory dạng răng cưa.  
**Evidence** → `dotnet-counters` cho thấy Gen 2 collections/allocation rate cao, heap dump có nhiều large arrays.  
**Hypothesis** → request path tạo buffer lớn ngắn hạn.  
**Diagnosis** → allocation profiling xác nhận call site.  
**Fix** → streaming, chunk nhỏ hơn hoặc `ArrayPool<T>`.  
**Verification** → so sánh allocation/sec, GC pause và p95/p99 trước/sau.

## 7. Common mistakes

Ép `GC.Collect()`; giữ pooled buffer quá lâu; return buffer trong khi consumer còn dùng; tối ưu LOH khi chưa profile; cache object lớn vô hạn.

## 8. Alternatives

Streaming tránh materialize toàn bộ payload; `MemoryPool<T>` phù hợp một số pipeline; pooling hữu ích khi kích thước/lifetime có thể kiểm soát.

## 9. Trade-offs

### Advantages

Pooling/streaming giảm allocation và GC pressure.

### Costs / Risks

Pooling tăng lifetime complexity, memory retention và nguy cơ use-after-return ở cấp logic. Streaming làm code xử lý phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu object lớn có chi phí GC khác object nhỏ.

### Middle

Biết đo allocation và dùng streaming/pooling đúng lifetime.

### Senior

Phân biệt memory leak, retention, fragmentation và allocation pressure; đánh giá p99 thay vì chỉ RAM trung bình.

### Technical Lead / Architect

Quyết định payload limits, streaming boundary và memory budget cho từng instance thay vì “scale RAM” theo phản xạ.

## 11. Key takeaway

- LOH là vấn đề allocation/lifetime, không chỉ dung lượng RAM.
- Profile trước khi pooling.
- Streaming thường loại bỏ vấn đề tốt hơn tối ưu GC sau khi đã materialize payload.

# 2. ASP.NET Core ProblemDetails: error contract ổn định và observability

## 1. What is it?

`ProblemDetails` là representation chuẩn hóa lỗi HTTP. Mental model: exception nội bộ và API error contract là hai thứ khác nhau; client cần contract ổn định, operator cần diagnostic detail.

## 2. Why does it exist?

Nếu mỗi endpoint trả một shape lỗi khác nhau, frontend phải đoán cấu trúc và backend dễ làm lộ stack trace. Một contract thống nhất cho phép validation, domain conflict và unexpected failure được xử lý nhất quán.

## 3. How does it work?

Exception/validation failure đi qua exception handler, được map thành status + problem type + safe detail; correlation/trace ID nối response với telemetry.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler();

app.MapPost("/orders", async (CreateOrder cmd, IOrderService service, CancellationToken ct) =>
{
    var result = await service.CreateAsync(cmd, ct);
    return result.IsConflict
        ? Results.Problem(statusCode: 409, title: "Order conflict")
        : Results.Created($"/orders/{result.Id}", result);
});
```

Production handler nên log exception đầy đủ ở server nhưng chỉ trả thông tin an toàn cho client.

## 5. Real production scenario

Web app gọi API checkout. Duplicate business operation trả `409`, invalid input trả `400`, dependency outage trả `503`; UI có thể xử lý từng class lỗi mà không phụ thuộc message exception.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận 500 nhưng support không tìm được request.  
**Evidence** → response không có trace identifier.  
**Diagnosis** → error middleware tạo response nhưng không enrich correlation metadata.  
**Fix** → đưa trace ID vào extensions và structured logs.  
**Verification** → từ response ID truy được trace/log tương ứng.

## 7. Common mistakes

Trả `exception.Message`; dùng HTTP 200 cho business error; map mọi exception thành 500; thay đổi error code tùy tiện; log cùng exception ở nhiều layer gây duplicate noise.

## 8. Alternatives

Custom error envelope có thể phù hợp legacy contract, nhưng phải duy trì semantics riêng. gRPC dùng status/trailers thay vì HTTP JSON contract.

## 9. Trade-offs

### Advantages

Client contract nhất quán, dễ document và correlate.

### Costs / Risks

Mapping layer cần governance; quá nhiều custom problem types có thể trở thành taxonomy khó duy trì.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt status code và message.

### Middle

Implement centralized error handling và validation response.

### Senior

Thiết kế mapping theo retryability/security và observability.

### Technical Lead / Architect

Định nghĩa error contract dùng xuyên service mà không làm lộ implementation detail hoặc khóa hệ thống vào taxonomy quá phức tạp.

## 11. Key takeaway

- API error contract không phải stack trace.
- Status code phải phản ánh semantics.
- Trace correlation nối trải nghiệm client với production diagnosis.

# 3. EF Core query compilation: expression shape, parameterization và compiled queries

## 1. What is it?

EF Core phải biến LINQ expression tree thành SQL và cache compilation theo query shape. Compiled query cho phép bỏ bớt một phần lookup/compilation overhead ở hot path rất ổn định.

## 2. Why does it exist?

Database query không bắt đầu ở SQL string: EF phải phân tích expression, translate và tạo command. Với query cực nóng, overhead phía client có thể đáng kể; nhưng phần lớn hệ thống vẫn bị chi phối bởi network/database I/O.

## 3. How does it work?

`LINQ → expression tree → cache lookup/translation → SQL → DB plan → rows → materialization`. Parameterization giúp expression shape và database execution plan tái sử dụng tốt hơn.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, Guid, Task<Order?>>
    GetOrder = EF.CompileAsyncQuery(
        (AppDbContext db, Guid id) =>
            db.Orders.AsNoTracking().FirstOrDefault(x => x.Id == id));

var order = await GetOrder(db, id);
```

Chỉ dùng sau benchmark cho hot query.

## 5. Real production scenario

Product lookup chạy hàng chục nghìn lần/phút, SQL đã tối ưu và DB latency rất thấp. Profiling cho thấy EF-side CPU đáng kể; compiled query có thể có giá trị. Với report 300 ms ở DB, tối ưu compilation vài microseconds gần như vô nghĩa.

## 6. Failure scenario & troubleshooting

**Symptom** → API CPU tăng nhưng DB không chậm.  
**Evidence** → profiler cho thấy query construction/translation đáng kể.  
**Hypothesis** → dynamic expression tạo nhiều query shapes.  
**Fix** → parameterize, ổn định expression shape; compiled query nếu benchmark chứng minh.  
**Verification** → benchmark end-to-end và CPU/request.

## 7. Common mistakes

Compile mọi query; nhúng constants động vào expression; tối ưu EF trước execution plan; bỏ projection khiến materialization mới là bottleneck.

## 8. Alternatives

Query cache mặc định của EF Core đủ cho đa số trường hợp; raw SQL/Dapper hữu ích khi cần kiểm soát SQL/materialization rõ hơn, nhưng tăng maintenance cost.

## 9. Trade-offs

### Advantages

Giảm CPU overhead ở hot path predictable.

### Costs / Risks

Tăng code ceremony, giảm flexibility và có thể tối ưu sai tầng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ không tự động là SQL ngay khi viết.

### Middle

Biết inspect SQL, parameterization và execution timing.

### Senior

Profile để phân biệt translation, DB execution và materialization.

### Technical Lead / Architect

Không chuẩn hóa compiled query như rule; chỉ áp dụng nơi throughput profile chứng minh lợi ích.

## 11. Key takeaway

- Query shape ảnh hưởng cache.
- Database I/O thường quan trọng hơn compilation.
- Compiled query là optimization tool, không phải default pattern.

# 4. SQL Server isolation levels: blocking, consistency và row versioning

## 1. What is it?

Isolation level xác định transaction được phép quan sát thay đổi concurrent đến mức nào. Nó là lựa chọn giữa consistency semantics, blocking, version storage và anomaly risk.

## 2. Why does it exist?

Nhiều transaction cùng đọc/ghi dữ liệu. Không có isolation policy, kết quả có thể phụ thuộc timing theo cách phá business invariant; isolation quá mạnh lại giảm concurrency.

## 3. How does it work?

Lock-based isolation dùng shared/exclusive locks để điều phối. Row-versioning như `READ_COMMITTED_SNAPSHOT` cho reader thấy version phù hợp thay vì chờ writer trong nhiều trường hợp. `SNAPSHOT` còn cung cấp transaction-level snapshot với conflict semantics riêng.

## 4. Practical implementation

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN TRAN;

SELECT Balance
FROM Accounts
WHERE Id = @Id;

UPDATE Accounts
SET Balance = Balance - @Amount
WHERE Id = @Id;

COMMIT;
```

Đây không mặc nhiên là lựa chọn tốt: invariant và access pattern phải quyết định mức isolation.

## 5. Real production scenario

Approval workflow đọc trạng thái rồi cập nhật. Hai approver đồng thời có thể tạo transition sai nếu logic dựa trên stale read. Có thể giải bằng atomic conditional update/concurrency token thay vì nâng toàn hệ thống lên `SERIALIZABLE`.

## 6. Failure scenario & troubleshooting

**Symptom** → request chậm theo cụm.  
**Evidence** → waits/blocked process cho thấy lock chain.  
**Hypothesis** → transaction giữ lock lâu.  
**Diagnosis** → tìm blocker, transaction scope và query plan.  
**Fix** → rút ngắn transaction, index/access pattern đúng; cân nhắc row versioning nếu semantics phù hợp.  
**Verification** → giảm lock waits mà invariant tests vẫn pass.

## 7. Common mistakes

Dùng `NOLOCK` như performance fix; giữ transaction qua external HTTP call; chọn isolation theo tên “mạnh hơn”; không hiểu tempdb/version-store cost.

## 8. Alternatives

Optimistic concurrency ở application; atomic SQL update; application lock trong trường hợp đặc biệt. Mỗi lựa chọn bảo vệ invariant khác nhau.

## 9. Trade-offs

### Advantages

Isolation đúng giúp correctness dưới concurrency.

### Costs / Risks

Isolation mạnh tăng blocking; row versioning tăng storage/version maintenance; isolation yếu cho phép anomaly.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction không có nghĩa mọi concurrent read/write đều tự an toàn.

### Middle

Biết transaction scope và basic isolation anomalies.

### Senior

Đọc waits/locks và chọn mechanism theo invariant.

### Technical Lead / Architect

Đặt consistency requirement theo workflow, tránh policy toàn cục đắt đỏ khi local mechanism đơn giản hơn.

## 11. Key takeaway

- Isolation là business-correctness decision có performance cost.
- `NOLOCK` không phải thuốc chữa blocking.
- Giảm transaction scope thường là cải thiện đầu tiên đáng xem xét.

# 5. Cosmos DB partition key: data locality, RU và hot partition

## 1. What is it?

Partition key quyết định cách Cosmos DB phân phối logical data lên physical partitions. Mental model: đây là quyết định về locality và workload distribution, không chỉ một field bắt buộc.

## 2. Why does it exist?

Distributed database phải chia dữ liệu và throughput. Key tốt giúp request định tuyến hẹp và tải phân bố; key xấu gom traffic vào một vùng nóng dù tổng RU còn dư.

## 3. How does it work?

Item có partition-key value; query có key cụ thể có thể route trực tiếp. Cross-partition query fan-out. Physical partition có giới hạn throughput/storage riêng, nên cardinality và access distribution quan trọng.

## 4. Practical implementation

Với multi-tenant SaaS:

```csharp
var response = await container.ReadItemAsync<Order>(
    orderId,
    new PartitionKey(tenantId),
    cancellationToken: ct);
```

`tenantId` tốt nếu tenant phân bố hợp lý; một mega-tenant có thể làm key này nóng.

## 5. Real production scenario

Event platform partition theo `eventType`. 80% traffic là `PageView`, tạo hot partition. Partition theo tenant/user bucket có thể phân phối tốt hơn nhưng làm một số query analytics tốn fan-out.

## 6. Failure scenario & troubleshooting

**Symptom** → 429 tăng dù account tổng thể chưa dùng hết throughput.  
**Evidence** → metrics cho thấy normalized RU consumption lệch theo partition.  
**Diagnosis** → hot logical key.  
**Fix** → redesign key/hierarchical strategy hoặc workload; retry chỉ giảm triệu chứng.  
**Verification** → RU distribution đều hơn và 429 giảm.

## 7. Common mistakes

Chọn key có cardinality thấp; chỉ nghĩ đến storage; query không truyền partition key; tăng RU thay cho sửa hotspot; migrate schema mà không tính migration cost.

## 8. Alternatives

SQL/PostgreSQL phù hợp khi relational transaction/query flexibility quan trọng hơn global distributed access. MongoDB có sharding với trade-off tương tự về shard key.

## 9. Trade-offs

### Advantages

Partitioning đúng cho scale-out và predictable routing.

### Costs / Risks

Key khó đổi; access pattern tương lai có thể khác; denormalization tăng consistency responsibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định nơi data sống.

### Middle

Thiết kế key theo query và write pattern.

### Senior

Đọc RU/429/hot partition telemetry và đánh giá skew.

### Technical Lead / Architect

Quyết định liệu Cosmos DB có thực sự phù hợp và chấp nhận migration/data-model cost của partition strategy.

## 11. Key takeaway

- Partition key là architecture decision.
- Tổng RU không phản ánh hotspot.
- Thiết kế theo access distribution, không chỉ data shape.

# 6. Azure Service Bus dead-letter queue: poison message và recovery workflow

## 1. What is it?

Dead-letter queue (DLQ) là nơi giữ message không thể xử lý bình thường để chúng không retry vô hạn và chặn luồng chính. Nó là failure boundary, không phải thùng rác.

## 2. Why does it exist?

At-least-once messaging đồng nghĩa consumer phải chịu duplicate và transient failure. Nhưng malformed payload hoặc business state không thể sửa bằng retry; retry vô hạn chỉ đốt compute và tăng backlog.

## 3. How does it work?

`receive → process → complete`; lỗi transient có thể abandon/retry. Khi delivery count vượt ngưỡng hoặc consumer chủ động dead-letter, message sang DLQ cùng reason/description.

## 4. Practical implementation

```csharp
try
{
    await handler.HandleAsync(message, ct);
    await args.CompleteMessageAsync(args.Message, ct);
}
catch (UnsupportedSchemaException ex)
{
    await args.DeadLetterMessageAsync(
        args.Message,
        "UnsupportedSchema",
        ex.Message,
        ct);
}
```

Không dead-letter mọi exception; timeout ngắn hạn thường cần retry policy có giới hạn.

## 5. Real production scenario

Order consumer nhận schema version mới mà deployment cũ chưa hiểu. Message được DLQ thay vì retry hàng nghìn lần; operator deploy compatibility fix rồi replay có kiểm soát.

## 6. Failure scenario & troubleshooting

**Symptom** → DLQ tăng liên tục.  
**Evidence** → group theo dead-letter reason/schema/producer.  
**Hypothesis** → producer rollout phá backward compatibility.  
**Diagnosis** → correlate deployment và payload version.  
**Fix** → consumer compatibility + controlled replay.  
**Verification** → DLQ drain, no duplicate side effects, backlog trở về baseline.

## 7. Common mistakes

Không monitor DLQ; replay hàng loạt trước khi fix; không idempotent; ghi reason vô nghĩa; coi `MaxDeliveryCount` là retry strategy hoàn chỉnh.

## 8. Alternatives

Storage quarantine/custom error queue cho workflow đặc biệt; nhưng DLQ tích hợp sẵn lifecycle của broker và thường đơn giản hơn.

## 9. Trade-offs

### Advantages

Cô lập poison message và bảo vệ throughput.

### Costs / Risks

Cần ownership, alert, retention và replay tooling; DLQ im lặng biến failure thành data loss trì hoãn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry không phù hợp với mọi lỗi.

### Middle

Implement settlement và DLQ metadata.

### Senior

Phân loại transient/permanent failure, replay idempotently.

### Technical Lead / Architect

Thiết kế operational ownership: ai được replay, retention bao lâu, SLO backlog nào phải alert.

## 11. Key takeaway

- DLQ phải được vận hành như production queue.
- Retry chỉ dành cho lỗi có khả năng hồi phục.
- Replay phải idempotent và có kiểm soát.

# 7. API idempotency key: chống duplicate side effects

## 1. What is it?

Idempotency key cho phép client retry một operation tạo side effect mà server vẫn nhận diện cùng logical request. Mental model: network timeout không cho client biết operation “chưa chạy” hay “đã chạy nhưng response mất”.

## 2. Why does it exist?

POST payment/order có thể thành công ở server rồi connection đứt. Retry mù có thể tạo hai order hoặc charge hai lần.

## 3. How does it work?

Client gửi stable key; server atomically claim key cùng request fingerprint/result. Request trùng key trả kết quả cũ hoặc trạng thái đang xử lý.

```text
Client -> API: POST /payments + Idempotency-Key K
API -> Store: claim K
API -> Payment: execute
API -> Store: save result
API --x Client: response lost
Client -> API: retry K
API -> Store: existing completed result
API -> Client: same logical result
```

## 4. Practical implementation

```csharp
app.MapPost("/payments", async (
    HttpRequest req, PaymentCommand cmd, IIdempotencyStore store, CancellationToken ct) =>
{
    var key = req.Headers["Idempotency-Key"].ToString();
    var cached = await store.TryGetAsync(key, ct);
    if (cached is not null) return Results.Json(cached.Body, statusCode: cached.Status);

    // Claim must be atomic in the real implementation.
    return await ProcessAndPersistResultAsync(key, cmd, store, ct);
});
```

Store cần unique constraint/atomic insert; check-then-insert không atomic vẫn race.

## 5. Real production scenario

Mobile app mất mạng sau khi submit booking. User bấm lại; cùng key phải trả booking cũ thay vì tạo booking thứ hai.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate order dù client có key.  
**Evidence** → hai requests cùng key chạy song song.  
**Diagnosis** → store dùng read-then-write không unique/transactional claim.  
**Fix** → atomic uniqueness + request fingerprint.  
**Verification** → concurrency test hàng chục requests cùng key chỉ tạo một side effect.

## 7. Common mistakes

Key mới cho mỗi retry; lưu key sau side effect; không scope key theo tenant/user; cho cùng key đi với payload khác; giữ key vô hạn.

## 8. Alternatives

PUT với client-generated resource ID có natural idempotency; message consumer dùng Inbox/deduplication; database unique business key đôi khi đủ.

## 9. Trade-offs

### Advantages

Cho phép safe retry và UX tốt hơn khi network không chắc chắn.

### Costs / Risks

Thêm state, TTL, concurrency logic và security boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không đồng nghĩa failure.

### Middle

Implement key validation và persistence.

### Senior

Giải quyết race, payload fingerprint, TTL và downstream side effects.

### Technical Lead / Architect

Quyết định operation nào cần idempotency contract và boundary nào sở hữu deduplication.

## 11. Key takeaway

- Idempotency xử lý ambiguity của distributed systems.
- Claim key phải atomic.
- Unique business constraint có thể đơn giản hơn một framework idempotency tổng quát.

# 8. Testing với real database: Testcontainers, isolation và deterministic integration tests

## 1. What is it?

Database integration test chạy code persistence thật với database engine thật thay vì mock `DbContext`/repository behavior. Testcontainers là một cách provision disposable database bằng container.

## 2. Why does it exist?

Mock không kiểm tra LINQ translation, constraints, transaction, collation, index-specific behavior hoặc SQL dialect. Những bug này chỉ xuất hiện khi application gặp database thật.

## 3. How does it work?

Test suite khởi động DB container, apply migrations, seed tối thiểu, chạy test và teardown. Isolation có thể dùng database/schema riêng, transaction rollback hoặc deterministic cleanup.

## 4. Practical implementation

```csharp
var container = new MsSqlBuilder()
    .WithPassword("Strong_password123!")
    .Build();

await container.StartAsync();

var options = new DbContextOptionsBuilder<AppDbContext>()
    .UseSqlServer(container.GetConnectionString())
    .Options;

await using var db = new AppDbContext(options);
await db.Database.MigrateAsync();
```

Test nên assert observable behavior và DB constraints, không chỉ “method được gọi”.

## 5. Real production scenario

Query EF Core pass unit test với in-memory fake nhưng fail SQL Server vì translation unsupported. Integration test trên engine thật bắt regression trước deployment.

## 6. Failure scenario & troubleshooting

**Symptom** → CI test flaky theo thứ tự.  
**Evidence** → test pass riêng, fail khi chạy parallel.  
**Hypothesis** → shared mutable rows/database.  
**Diagnosis** → IDs/seed và cleanup overlap.  
**Fix** → namespace dữ liệu, transaction/isolation strategy hoặc separate DB.  
**Verification** → randomize order + parallel repeated runs.

## 7. Common mistakes

Mock ORM quá sâu; dùng SQLite thay SQL Server rồi tin semantics giống nhau; seed khổng lồ; phụ thuộc test order; container mới cho từng test khiến suite quá chậm.

## 8. Alternatives

Unit tests cho pure domain logic; shared staging DB thường chậm và không deterministic; local emulator phù hợp một số cloud services nhưng phải hiểu fidelity.

## 9. Trade-offs

### Advantages

Fidelity cao cho persistence behavior.

### Costs / Risks

CI chậm hơn, cần Docker/runtime và lifecycle discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu unit test và integration test bảo vệ rủi ro khác nhau.

### Middle

Viết test với migration/constraint thật.

### Senior

Thiết kế isolation để suite nhanh và deterministic.

### Technical Lead / Architect

Xây test portfolio theo risk: domain unit tests nhanh + persistence/API integration tests có fidelity + E2E chọn lọc.

## 11. Key takeaway

- Mock không chứng minh SQL thật chạy đúng.
- Fidelity và determinism đều quan trọng.
- Test strategy nên bảo vệ failure modes, không chạy theo coverage percentage.

# 9. Akamai/CDN Cache-Control: browser–edge–origin consistency

## 1. What is it?

CDN cache đặt response gần client ở edge. `Cache-Control` mô tả freshness/revalidation semantics giữa browser, shared cache và origin. Mental model: một response có thể tồn tại ở nhiều cache layers độc lập.

## 2. Why does it exist?

Không có edge caching, static/public content luôn quay về origin, tăng latency và origin load. Nhưng caching sai có thể phục vụ stale hoặc private content cho sai user.

## 3. How does it work?

```text
Browser -> Akamai edge -> reverse proxy -> ASP.NET Core -> origin/data
   |           |
browser TTL   shared TTL
```

`max-age` chủ yếu điều khiển freshness ở client; `s-maxage` có thể điều khiển shared cache. Validators như ETag hỗ trợ revalidation.

## 4. Practical implementation

Với versioned public asset:

```http
Cache-Control: public, max-age=31536000, immutable
```

Với HTML cần edge cache ngắn hơn browser:

```http
Cache-Control: public, max-age=60, s-maxage=300
```

Authenticated personalized response thường cần policy khác, ví dụ `private` hoặc `no-store` tùy sensitivity.

## 5. Real production scenario

Optimizely marketing site publish banner mới. Origin đã cập nhật nhưng Akamai vẫn phục vụ object cũ theo TTL. Release process cần hiểu purge/versioning thay vì restart application.

## 6. Failure scenario & troubleshooting

**Symptom** → một số region thấy content cũ.  
**Evidence** → response headers/edge diagnostics cho thấy cache hit và age cao.  
**Hypothesis** → edge object chưa expire/purge.  
**Diagnosis** → so sánh direct-origin và edge response.  
**Fix** → purge đúng key hoặc asset versioning; sửa cache policy.  
**Verification** → kiểm tra nhiều POP/request path và header age.

## 7. Common mistakes

Cache personalized response như public; purge toàn site thay vì key cụ thể; không version static asset; nhầm browser cache với CDN cache; set TTL dài mà không có invalidation plan.

## 8. Alternatives

Origin/reverse-proxy cache giảm backend load nhưng không giảm geographic latency như CDN. Versioned URLs thường đáng tin hơn purge cho immutable assets.

## 9. Trade-offs

### Advantages

Latency thấp, origin offload và resilience tốt hơn cho cacheable content.

### Costs / Risks

Freshness complexity, purge operations, cache-key bugs và khó debug nhiều layers.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser cache và CDN cache là hai layer.

### Middle

Đọc headers và thiết kế policy cho static/public content.

### Senior

Debug stale content theo từng layer, cache key và invalidation.

### Technical Lead / Architect

Phân loại content theo freshness/security requirement và định nghĩa ownership của purge/versioning.

## 11. Key takeaway

- Cache policy là consistency policy.
- Versioned immutable assets đơn giản hơn purge liên tục.
- Không cache public dữ liệu personalized nếu chưa chứng minh key isolation an toàn.

# 10. Git bisect: khoanh vùng deployment regression bằng lịch sử commit

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên chuyển hệ thống từ “good” sang “bad”. Đây là debugging tool dựa trên reproducible signal.

## 2. Why does it exist?

Nếu release chứa 200 commits, đọc diff tuần tự rất chậm và dễ bias. Khi có test/command phân loại commit tốt/xấu, binary search giảm số lần kiểm tra xuống logarithmic.

## 3. How does it work?

Chọn một commit known-good và một known-bad; Git checkout midpoint. Bạn test và đánh dấu `good`/`bad`; phạm vi tiếp tục bị chia đôi đến culprit.

## 4. Practical implementation

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
git bisect run dotnet test tests/Regression.Tests
git bisect reset
```

Script phải trả exit code ổn định: 0 = good, non-zero = bad; 125 có thể dùng để skip commit không test được.

## 5. Real production scenario

Sau deployment, endpoint search tăng memory liên tục. Team có regression test tái hiện leak trên branch hiện tại nhưng tag tuần trước pass. Automated bisect tìm commit thay đổi serialization options thay vì tranh luận dựa trên phỏng đoán.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit không liên quan hoặc kết quả thay đổi mỗi run.  
**Evidence** → regression test flaky/environment-dependent.  
**Hypothesis** → “good/bad oracle” không deterministic.  
**Fix** → cô lập data/time/external dependency, hoặc bisect thủ công với metric threshold đủ rõ.  
**Verification** → revert culprit làm test trở lại good và forward-apply tái tạo bad.

## 7. Common mistakes

Bisect khi không có known-good baseline; dùng flaky E2E làm oracle; kết luận culprit mà không verify causal change; quên migration/config ngoài Git.

## 8. Alternatives

`git log`, `git blame`, deployment telemetry và feature-flag comparison hữu ích khi phạm vi nhỏ hoặc regression phụ thuộc runtime configuration.

## 9. Trade-offs

### Advantages

Giảm search space rất nhanh và chống bias khi history lớn.

### Costs / Risks

Cần build/test được intermediate commits; regression không monotonic hoặc phụ thuộc environment làm kết quả khó tin.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết commit history là debugging evidence, không chỉ source archive.

### Middle

Bisect thủ công với good/bad commits.

### Senior

Tạo deterministic regression test và automate `bisect run`.

### Technical Lead / Architect

Đảm bảo release traceability từ production artifact đến commit, để incident có thể quay lại evidence nhanh thay vì phụ thuộc trí nhớ của team.

## 11. Key takeaway

- Bisect mạnh khi có reproducible oracle.
- Verify culprit bằng revert/reproduction.
- Traceable deployments biến Git history thành production-debugging tool.
