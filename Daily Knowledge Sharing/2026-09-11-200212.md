# 1. .NET LOH, pinned objects và GC pressure: vì sao “chỉ là allocation” có thể biến thành latency spike trong Production

## 1. What is it?

Trong .NET, object lớn thường được cấp phát vào Large Object Heap (LOH). Ngưỡng truyền thống là khoảng 85 KB cho một object đơn lẻ. LOH được quản lý bởi Garbage Collector nhưng có chi phí khác với các generation nhỏ: object lớn tốn nhiều memory bandwidth, có thể làm Gen 2 collection xảy ra thường xuyên hơn, và fragmentation có thể trở nên đáng kể.

Pinned object là object mà GC không được phép di chuyển vì native code, I/O hoặc interop đang giữ địa chỉ memory cố định. Pinning lâu hoặc nhiều object có thể cản trở compaction và làm heap phân mảnh.

Mental model:

```text
Nhiều allocation lớn
   -> LOH tăng nhanh
   -> Gen 2 pressure
   -> GC pause / memory growth
   -> p95 / p99 latency tăng
```

## 2. Why does it exist?

GC tối ưu mạnh cho rất nhiều object nhỏ, sống ngắn. Di chuyển object lớn thường tốn copy cost đáng kể, nên runtime xử lý chúng khác để tránh compaction quá đắt trên mọi collection.

Pinned object tồn tại vì có tình huống native API cần địa chỉ memory ổn định. Vấn đề không phải pinning tự thân, mà là pinning dài hạn hoặc allocation pattern khiến GC mất khả năng sắp xếp heap hiệu quả.

## 3. How does it work?

Object nhỏ thường bắt đầu ở Gen 0. Nếu sống lâu, chúng được promote lên Gen 1 rồi Gen 2. Object lớn thường đi thẳng vào LOH, và việc reclaim LOH gắn với Gen 2 collection.

Một workload như export file, image processing hoặc JSON buffer lớn có thể tạo hàng nghìn `byte[]` lớn. Nếu mỗi request tạo buffer mới, memory allocation rate tăng rất nhanh dù mỗi object chỉ sống vài trăm millisecond.

```text
Request -> allocate 5 MB byte[] -> process -> discard
100 concurrent requests
-> hàng trăm MB transient memory
-> GC phải làm việc liên tục
```

## 4. Practical implementation

Không nên luôn tạo buffer lớn mới:

```csharp
public async Task<byte[]> DownloadAsync(CancellationToken ct)
{
    using var stream = new MemoryStream();
    await _blobClient.DownloadToAsync(stream, ct);
    return stream.ToArray();
}
```

Với file lớn, ưu tiên streaming:

```csharp
app.MapGet("/files/{name}", async (
    string name,
    BlobService service,
    HttpResponse response,
    CancellationToken ct) =>
{
    response.ContentType = "application/octet-stream";

    await using var source = await service.OpenReadAsync(name, ct);
    await source.CopyToAsync(response.Body, ct);
});
```

Nếu thực sự cần reusable buffer, có thể dùng `ArrayPool<byte>` nhưng phải quản lý lifetime rất chặt:

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(128 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(), ct);
    // process buffer[..read]
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);
}
```

## 5. Real production scenario

Một API tạo ZIP export cho user. Mỗi request build toàn bộ file trong `MemoryStream`, gọi `ToArray()` rồi trả response. Khi có 50 request concurrent, memory tăng hàng GB, Gen 2 collections dày lên và p99 latency tăng mạnh.

CPU chưa chắc 100%; bottleneck thực tế là allocation rate, GC và memory bandwidth.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng nhanh, latency spike theo chu kỳ, đôi lúc process bị OOM.

**Evidence** → `dotnet-counters` cho thấy allocation rate cao, Gen 2 collection tăng, LOH size lớn.

**Hypothesis** → transient large allocations hoặc pinned buffers.

**Diagnosis** → dùng `dotnet-gcdump`, profiler hoặc memory dump để xem object type nào chiếm LOH; kiểm tra code path tạo `byte[]`, `MemoryStream`, serialization buffer.

**Fix** → streaming, buffer reuse có kiểm soát, giảm concurrency hoặc thay đổi data flow để không materialize toàn bộ payload.

**Verification** → load test lại và so allocation rate, Gen 2 count, working set và p95/p99.

## 7. Common mistakes

- Chỉ nhìn memory cuối cùng sau GC mà bỏ qua allocation rate.
- Dùng `ArrayPool<T>` nhưng giữ reference sau khi return buffer.
- Pool mọi thứ trước khi đo.
- Materialize file lớn vào memory dù HTTP response có thể stream.
- Pin object lâu hơn lifecycle thực sự cần thiết.

## 8. Alternatives

Streaming là lựa chọn tốt nhất khi consumer có thể xử lý tuần tự. `ArrayPool<T>` phù hợp khi cần buffer tạm thời. Memory-mapped file hoặc temp file có thể phù hợp khi dữ liệu quá lớn nhưng cần random access.

## 9. Trade-offs

### Advantages

Giảm allocation lớn thường cải thiện throughput và tail latency đáng kể trong hot path.

### Costs / Risks

Pooling và manual buffer lifecycle tăng độ phức tạp, dễ tạo data corruption hoặc security bug nếu tái sử dụng buffer sai cách.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu rằng object lớn không “rẻ” chỉ vì GC tự quản lý memory.

### Middle

Biết nhận diện allocation lớn, dùng streaming và đọc basic GC metrics.

### Senior

Phân tích LOH, Gen 2 pressure, pinned memory và benchmark bằng production-like load.

### Technical Lead / Architect

Quyết định endpoint nào phải stream, giới hạn concurrency ở đâu, payload size nào chấp nhận được và operational telemetry nào bắt buộc phải có.

## 11. Key takeaway

- Large allocation ảnh hưởng tail latency trước cả khi process hết memory.
- Streaming thường tốt hơn materialize toàn bộ payload.
- Tối ưu GC phải dựa trên measurement, không dựa trên cảm giác.

# 2. ASP.NET Core middleware ordering: vì sao Authentication, Authorization, CORS và exception handling sai thứ tự có thể tạo bug rất khó đoán

## 1. What is it?

ASP.NET Core request pipeline là chuỗi middleware chạy theo thứ tự đăng ký. Mỗi middleware có thể xử lý request trước khi gọi middleware tiếp theo và xử lý response khi stack unwind.

Thứ tự là behavior, không phải style.

## 2. Why does it exist?

Cross-cutting concerns như exception handling, routing, CORS, authentication và authorization cần áp dụng ở đúng phase của request lifecycle. Nếu thứ tự sai, component có thể không nhìn thấy context cần thiết hoặc response có thể thiếu header quan trọng.

## 3. How does it work?

```text
Request
  -> Exception Handler
  -> Routing
  -> CORS
  -> Authentication
  -> Authorization
  -> Endpoint
Response
  <- unwind theo chiều ngược lại
```

`UseAuthentication()` tạo `HttpContext.User` từ credential. `UseAuthorization()` dựa trên `User` và endpoint metadata để quyết định access. Nếu đảo hai bước này, authorization có thể chạy khi identity chưa được thiết lập.

## 4. Practical implementation

```csharp
var app = builder.Build();

app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseRouting();
app.UseCors("frontend");
app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();
```

Không nên đặt exception middleware quá muộn:

```csharp
app.UseAuthentication();
app.MapControllers();
app.UseExceptionHandler(); // quá muộn để catch endpoint exception
```

## 5. Real production scenario

Frontend gọi API từ domain khác. Endpoint yêu cầu JWT. Backend trả `401`, nhưng browser báo CORS error vì CORS middleware không được áp dụng đúng trên unauthorized response. Developer tưởng token sai trong khi root cause thực tế là pipeline ordering.

## 6. Failure scenario & troubleshooting

**Symptom** → local gọi bằng Postman được nhưng browser fail; hoặc policy authorization không nhận claims.

**Evidence** → response thiếu CORS headers, logs cho thấy `User.Identity.IsAuthenticated == false` trước authorization.

**Hypothesis** → middleware order sai.

**Diagnosis** → xem pipeline registration, enable structured logs và minimal reproduction.

**Fix** → sắp xếp middleware theo lifecycle semantics.

**Verification** → test cả success, 401, 403, exception và preflight `OPTIONS`.

## 7. Common mistakes

- Nghĩ middleware order chỉ ảnh hưởng readability.
- Map endpoint trước middleware cần bao quanh endpoint execution.
- Dùng custom auth middleware thay vì chuẩn Authentication/Authorization mà không hiểu consequences.
- Chỉ test happy path.

## 8. Alternatives

Endpoint filters hoặc MVC filters có thể phù hợp cho logic gần endpoint hơn, nhưng không thay thế middleware cho concern toàn pipeline như exception handling, CORS hoặc tracing.

## 9. Trade-offs

### Advantages

Middleware cho phép composition rõ và reusable cross-cutting behavior.

### Costs / Risks

Pipeline dài, nhiều custom middleware và implicit ordering dependency làm hệ thống khó reasoning nếu không có integration test.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request đi qua middleware theo thứ tự đăng ký.

### Middle

Thiết lập đúng routing, CORS, auth và error handling.

### Senior

Debug behavior khác nhau giữa browser, reverse proxy và direct API call.

### Technical Lead / Architect

Giữ pipeline đơn giản, quy định nơi đặt cross-cutting concern và yêu cầu tests cho critical ordering behavior.

## 11. Key takeaway

- Middleware order là execution semantics.
- Authentication phải cung cấp identity trước Authorization.
- CORS, exception handling và endpoint mapping phải được test cả failure path.

# 3. EF Core connection resiliency + explicit transaction: retry transient failure mà không vô tình chạy lại transaction sai cách

## 1. What is it?

EF Core execution strategy có thể retry database operation khi gặp transient failure như connection reset hoặc temporary failover. Khi dùng explicit transaction, retry phải bao toàn bộ transactional unit như một operation có thể replay.

## 2. Why does it exist?

Cloud database không đảm bảo network connection bất tử. Transient fault là chuyện bình thường. Retry từng command riêng lẻ trong một transaction tự quản có thể tạo state không nhất quán hoặc EF Core không thể replay đúng transaction.

## 3. How does it work?

```text
ExecutionStrategy
  -> begin transaction
  -> command A
  -> command B
  -> commit

Transient failure ở B
  -> rollback / connection lost
  -> replay toàn bộ unit
```

Execution strategy cần control lifecycle của transaction để retry từ đầu.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    var order = new Order { CustomerId = request.CustomerId };
    db.Orders.Add(order);

    db.AuditLogs.Add(new AuditLog
    {
        Message = $"Created order {order.Id}"
    });

    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
});
```

Nếu transaction có external side effect như gọi payment API, replay có thể gây duplicate side effect. Lúc đó cần idempotency hoặc tách external effect ra bằng Outbox/workflow.

## 5. Real production scenario

Azure SQL failover ngắn xảy ra đúng lúc service tạo order và audit record. Nếu code chỉ retry `SaveChangesAsync` mà transaction/state bên ngoài không replay đúng, request có thể fail không nhất quán.

## 6. Failure scenario & troubleshooting

**Symptom** → intermittent error kiểu “execution strategy does not support user-initiated transactions” hoặc duplicate external calls sau retry.

**Evidence** → logs cho thấy transaction explicit kết hợp retry strategy; trace có cùng request thực hiện downstream call nhiều lần.

**Hypothesis** → retry boundary sai.

**Diagnosis** → xác định operation nào được EF replay và operation nào có side effect bên ngoài database.

**Fix** → wrap transaction trong execution strategy, đưa external side effect ra khỏi replay boundary hoặc thêm idempotency.

**Verification** → fault injection trong transaction và xác nhận final state đúng, không duplicate effect.

## 7. Common mistakes

- Retry toàn method có cả payment/email mà không có idempotency.
- Nghĩ transaction làm external HTTP call atomic với database.
- Dùng retry policy ở nhiều layer chồng lên nhau tạo retry amplification.
- Không log attempt number và transient error category.

## 8. Alternatives

Không phải operation nào cũng cần explicit transaction; một `SaveChanges` đã có transaction semantics phù hợp cho nhiều case. Với cross-system consistency, Outbox/Saga thường phù hợp hơn transaction dài.

## 9. Trade-offs

### Advantages

Tăng resilience trước transient database faults.

### Costs / Risks

Replay làm correctness khó hơn nếu unit có non-idempotent side effects hoặc transaction kéo dài.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transient failure khác permanent failure.

### Middle

Biết cấu hình retry và transaction đúng cách.

### Senior

Thiết kế retry boundary, idempotency và fault-injection tests.

### Technical Lead / Architect

Quyết định khi nào retry hợp lý, layer nào sở hữu retry và tránh retry storm xuyên nhiều dependency.

## 11. Key takeaway

- Retry phải replay đúng transactional unit.
- Không retry mù quáng operation có side effect bên ngoài database.
- Retry policy là correctness concern, không chỉ availability feature.

# 4. PostgreSQL transaction isolation: hiểu Read Committed, Repeatable Read và Serializable bằng anomaly thay vì học thuộc tên

## 1. What is it?

Transaction isolation xác định transaction nhìn thấy thay đổi của transaction khác ở mức nào và database ngăn anomaly nào.

Trong PostgreSQL, `Read Committed` là default. `Repeatable Read` dùng snapshot ổn định hơn trong transaction. `Serializable` cố đảm bảo kết quả tương đương một thứ tự serial hợp lệ, nhưng có thể abort transaction để duy trì tính đúng.

## 2. Why does it exist?

Isolation cao hơn giảm anomaly nhưng tăng contention, retry requirement hoặc giảm concurrency. Không có một level tối ưu cho mọi workload.

## 3. How does it work?

Ví dụ write skew:

```text
Doctor A đọc: còn Doctor B trực
Doctor B đọc: còn Doctor A trực
A bỏ ca
B bỏ ca
Kết quả: không còn ai trực
```

Hai transaction có thể cùng thấy invariant hợp lệ lúc đọc nhưng tổng kết lại phá invariant. Serializable có thể phát hiện dependency cycle và abort một transaction.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(
    System.Data.IsolationLevel.Serializable,
    ct);

var activeCount = await db.OnCallDoctors
    .CountAsync(x => x.Day == day && x.IsActive, ct);

if (activeCount <= 1)
    return Results.Conflict("At least one doctor must remain on call.");

entry.IsActive = false;
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Code vẫn phải xử lý serialization failure và retry transaction nếu business operation cho phép.

## 5. Real production scenario

Approval workflow yêu cầu ít nhất một active approver. Hai admin đồng thời deactivate hai approver khác nhau. Mỗi request nhìn thấy một approver còn lại và đều commit nếu isolation/boundary không bảo vệ invariant.

## 6. Failure scenario & troubleshooting

**Symptom** → invariant hiếm khi bị phá dưới concurrency dù unit tests đều pass.

**Evidence** → audit log cho thấy hai transaction overlap.

**Hypothesis** → anomaly do isolation level không đủ cho invariant.

**Diagnosis** → dựng concurrent integration test và quan sát transaction behavior.

**Fix** → redesign invariant, constraint, lock phù hợp hoặc dùng isolation mạnh hơn với retry.

**Verification** → stress test concurrent operation và chứng minh invariant giữ đúng.

## 7. Common mistakes

- Nghĩ transaction mặc định ngăn mọi race condition.
- Tăng lên Serializable cho toàn hệ thống mà không đo impact.
- Không retry serialization failure.
- Giữ transaction mở trong lúc gọi remote API.

## 8. Alternatives

Unique/partial constraints thường tốt hơn nếu invariant biểu diễn được ở schema. Explicit locking (`SELECT ... FOR UPDATE`) phù hợp một số hot-row workflow. Optimistic concurrency phù hợp lost-update case đơn giản.

## 9. Trade-offs

### Advantages

Isolation mạnh bảo vệ invariant khó đảm bảo bằng application logic rời rạc.

### Costs / Risks

Có thể tăng abort/retry, lock contention hoặc giảm throughput.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction không tự động nghĩa là “không có concurrency bug”.

### Middle

Biết chọn isolation cho use case phổ biến và viết concurrent test.

### Senior

Reason về anomalies, constraints, locking và retry.

### Technical Lead / Architect

Đưa invariant xuống boundary thấp nhất có thể bảo vệ chắc chắn: schema, transaction hoặc domain workflow.

## 11. Key takeaway

- Chọn isolation theo anomaly cần ngăn, không theo tên “mạnh hơn”.
- Serializable có thể abort transaction; application phải chuẩn bị retry.
- Database constraint thường đáng tin hơn check-then-write ở application.

# 5. Elasticsearch filter vs query context: tối ưu search bằng cách tách relevance scoring khỏi exact filtering

## 1. What is it?

Trong Elasticsearch, query context tính relevance score; filter context chỉ quyết định document có match hay không. Exact constraints như category, tenant, availability, status thường nên nằm trong filter thay vì tham gia scoring.

## 2. Why does it exist?

Không phải mọi điều kiện search đều mang ý nghĩa relevance. Nếu `status = active` hoặc `tenantId = 123` ảnh hưởng score, ta vừa tốn compute vừa làm ranking khó hiểu.

## 3. How does it work?

```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "name": "wireless mouse" } }
      ],
      "filter": [
        { "term": { "tenantId": "t-123" } },
        { "term": { "isActive": true } },
        { "range": { "price": { "lte": 100 } } }
      ]
    }
  }
}
```

`match` đóng góp `_score`; `term`/`range` trong filter chỉ giới hạn candidate set.

## 4. Practical implementation

Với .NET client, conceptual request vẫn nên phản ánh boundary rõ:

```csharp
var response = await client.SearchAsync<ProductDocument>(s => s
    .Query(q => q.Bool(b => b
        .Must(m => m.Match(mm => mm
            .Field(f => f.Name)
            .Query(searchText)))
        .Filter(
            f => f.Term(t => t.Field(x => x.TenantId).Value(tenantId)),
            f => f.Term(t => t.Field(x => x.IsActive).Value(true))))));
```

## 5. Real production scenario

Search API vừa full-text theo product name vừa filter brand, price, market và availability. Team để tất cả vào `must` query và score trở nên khó explain. Sau khi tách exact constraints vào filter, query dễ reasoning hơn và ranking chỉ phản ánh text relevance.

## 6. Failure scenario & troubleshooting

**Symptom** → result ranking “lạ”, cùng keyword nhưng product bị đẩy lên/xuống do exact conditions.

**Evidence** → `_explain` cho thấy clauses không liên quan business relevance đang đóng góp score.

**Hypothesis** → dùng query context sai.

**Diagnosis** → inspect query DSL, mappings và analyzer.

**Fix** → chuyển exact conditions sang filter; giữ scoring clauses cho relevance.

**Verification** → test ranking corpus và đo latency/profile query.

## 7. Common mistakes

- Dùng `match` cho keyword field exact value.
- Filter tenant sau khi search ở application, gây security/data leakage risk.
- Tối ưu query mà không kiểm tra mapping/analyzer.
- Coi score như business ranking cuối cùng mà không có relevance evaluation.

## 8. Alternatives

SQL phù hợp nếu search chủ yếu exact filter/sort và không cần full-text relevance phức tạp. Elasticsearch chỉ đáng giá khi search requirements thực sự cần inverted index và ranking.

## 9. Trade-offs

### Advantages

Query rõ semantics, ranking dễ kiểm soát, filter có thể được tối ưu tốt hơn.

### Costs / Risks

Search architecture vẫn có sync lag, operational cost và mapping complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt full-text relevance với exact filtering.

### Middle

Viết `bool.must` và `bool.filter` đúng semantics.

### Senior

Dùng `_explain`, profiler và relevance tests để tune search.

### Technical Lead / Architect

Quyết định search concern nào thuộc Elasticsearch, concern nào nên giữ ở transactional database và cách bảo vệ tenant/security boundary.

## 11. Key takeaway

- Exact constraint không nên mặc định ảnh hưởng relevance score.
- Mapping, analyzer và query DSL phải được reasoning cùng nhau.
- Elasticsearch không thay thế database source of truth.

# 6. CQRS với một database: tách intent đọc/ghi mà chưa phải trả giá của distributed read/write stores

## 1. What is it?

CQRS là separation of intent giữa command thay đổi state và query đọc state. Nó không bắt buộc hai database, Event Sourcing hay Microservices.

Một hệ thống có thể dùng cùng SQL database nhưng command path và query path có model khác nhau.

## 2. Why does it exist?

Read model và write model thường có nhu cầu khác nhau. Write side cần invariant và transaction boundary. Read side cần projection nhanh, DTO phù hợp UI và có thể không cần domain model đầy đủ.

## 3. How does it work?

```text
HTTP POST
 -> Command Handler
 -> Domain / DbContext
 -> SQL

HTTP GET
 -> Query Handler
 -> Projection / SQL
 -> DTO
```

Cả hai dùng cùng database nhưng boundary code khác nhau.

## 4. Practical implementation

Command:

```csharp
public sealed record ApproveTimesheet(Guid Id);

public async Task Handle(ApproveTimesheet command, CancellationToken ct)
{
    var timesheet = await _db.Timesheets
        .SingleAsync(x => x.Id == command.Id, ct);

    timesheet.Approve();
    await _db.SaveChangesAsync(ct);
}
```

Query:

```csharp
public Task<TimesheetDto?> GetAsync(Guid id, CancellationToken ct) =>
    _db.Timesheets
       .AsNoTracking()
       .Where(x => x.Id == id)
       .Select(x => new TimesheetDto(x.Id, x.Status, x.TotalHours))
       .SingleOrDefaultAsync(ct);
```

## 5. Real production scenario

Timesheet application có write workflow phức tạp: submit, approve, reject. Dashboard read cần joins/projections tối ưu cho reporting. Dùng cùng entity graph cho cả hai khiến read code kéo quá nhiều navigation và write code bị phụ thuộc UI shape.

CQRS nhẹ giúp tách hai concern mà chưa cần separate read database.

## 6. Failure scenario & troubleshooting

**Symptom** → team tạo hàng chục handler chỉ để CRUD đơn giản, tracing trở nên khó và code ceremony tăng.

**Evidence** → command/query layer không tạo boundary thực, mỗi handler chỉ forward một dòng vào repository generic.

**Hypothesis** → pattern được áp dụng vì convention, không vì complexity.

**Diagnosis** → đánh giá change isolation và business value của separation.

**Fix** → giữ CQRS ở flow cần rõ intent; đơn giản hóa CRUD path nếu không có lợi ích.

**Verification** → code review xem business rule có boundary rõ hơn và query có tối ưu độc lập không.

## 7. Common mistakes

- Nghĩ CQRS bắt buộc MediatR.
- Nghĩ CQRS bắt buộc hai database.
- Tách command/query nhưng vẫn dùng một generic repository làm mọi thứ.
- Dùng pattern cho mọi CRUD endpoint bất kể complexity.

## 8. Alternatives

Layered service đơn giản thường đủ cho CRUD. Domain service/application service có thể rõ hơn nếu read/write complexity thấp.

## 9. Trade-offs

### Advantages

Intent rõ, read optimization độc lập và domain write path sạch hơn.

### Costs / Risks

Tăng số type/file, conventions và cognitive overhead.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu command thay state, query chỉ đọc state.

### Middle

Implement handler và projection không kéo domain model dư thừa.

### Senior

Biết khi nào CQRS tạo giá trị và khi nào là ceremony.

### Technical Lead / Architect

Quyết định có cần một DB hay split stores, consistency model nào phù hợp và team có đủ operational capacity cho bước phức tạp hơn không.

## 11. Key takeaway

- CQRS không đồng nghĩa Microservices, Event Sourcing hay hai database.
- Bắt đầu từ separation of intent đơn giản.
- Chỉ tăng complexity khi read/write pressures thực sự khác nhau.

# 7. Azure Service Bus lock duration, settlement và duplicate delivery: thiết kế consumer chịu được xử lý lâu và redelivery

## 1. What is it?

Trong PeekLock mode, Azure Service Bus giao message cho consumer nhưng chưa xóa message ngay. Consumer giữ lock tạm thời và phải `Complete` khi xử lý thành công. Nếu lock hết hạn hoặc consumer crash, message có thể được giao lại.

## 2. Why does it exist?

Nếu broker xóa message ngay khi giao, consumer crash giữa chừng sẽ làm mất work. PeekLock cho phép at-least-once delivery: ưu tiên không mất message, đổi lại consumer phải chịu duplicate.

## 3. How does it work?

```text
Receive message
 -> lock acquired
 -> process
 -> Complete

Nếu crash / lock expires
 -> message visible lại
 -> redelivery
```

`Abandon` trả message lại queue. `DeadLetter` chuyển message sang DLQ. Auto lock renewal có thể kéo dài thời gian xử lý nhưng không nên dùng để che operation vô hạn.

## 4. Practical implementation

```csharp
var processor = client.CreateProcessor(queueName, new ServiceBusProcessorOptions
{
    AutoCompleteMessages = false,
    MaxConcurrentCalls = 8,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(5)
});

processor.ProcessMessageAsync += async args =>
{
    if (await _inbox.AlreadyProcessedAsync(args.Message.MessageId))
    {
        await args.CompleteMessageAsync(args.Message);
        return;
    }

    await _handler.HandleAsync(args.Message, args.CancellationToken);
    await _inbox.MarkProcessedAsync(args.Message.MessageId);
    await args.CompleteMessageAsync(args.Message);
};
```

## 5. Real production scenario

Consumer resize image và update database mất 90 giây. Queue lock chỉ 30 giây, nên broker redeliver message khi first consumer vẫn đang chạy. Hai workers cùng ghi kết quả và tạo duplicate side effect.

## 6. Failure scenario & troubleshooting

**Symptom** → same `MessageId` xuất hiện nhiều lần, delivery count tăng, duplicate records sinh ra.

**Evidence** → logs cho thấy processing time vượt lock duration hoặc lock renewal fail.

**Hypothesis** → lock expiry hoặc consumer crash.

**Diagnosis** → đo processing duration, lock lost exceptions, delivery count và DLQ reason.

**Fix** → giảm processing time, renew lock hợp lý, chia nhỏ work hoặc dùng idempotent Inbox.

**Verification** → inject delay/crash và xác nhận redelivery không gây duplicate business effect.

## 7. Common mistakes

- Nghĩ queue đảm bảo exactly-once.
- Complete message trước khi durable business state được commit.
- Tăng lock duration cực lớn thay vì thiết kế idempotency.
- Không theo dõi DLQ.
- Retry poison message mãi mãi.

## 8. Alternatives

Nếu workflow dài nhiều bước, orchestration/Saga hoặc durable workflow có thể phù hợp hơn một message lock kéo dài. Nếu latency thấp và operation idempotent, simple consumer có thể đủ.

## 9. Trade-offs

### Advantages

At-least-once delivery giảm nguy cơ mất work và hỗ trợ recovery tốt.

### Costs / Risks

Consumer phải chịu duplicate, lock management, poison message và operational monitoring.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu receive không đồng nghĩa message đã bị xóa.

### Middle

Biết Complete/Abandon/DeadLetter và cấu hình processor.

### Senior

Thiết kế idempotency, lock renewal, retry và DLQ handling.

### Technical Lead / Architect

Quyết định granularity của message, ownership của retry và khi nào workflow cần orchestration thay vì queue consumer đơn giản.

## 11. Key takeaway

- Service Bus delivery là at-least-once trong nhiều flow thực tế.
- Lock expiry là behavior bình thường, không phải edge case hiếm.
- Idempotent consumer quan trọng hơn cố kéo lock thật dài.

# 8. IIS Application Pool recycling: process restart “bình thường” vẫn có thể thành production incident nếu startup/shutdown không đúng

## 1. What is it?

IIS Application Pool chứa worker process phục vụ web application. Recycling thay worker process cũ bằng process mới theo config, health condition, deployment hoặc manual action.

Recycle không nhất thiết là lỗi. Nhưng application phải chịu được process replacement.

## 2. Why does it exist?

Process cần được restart vì deployment, configuration change, memory policy hoặc operational maintenance. IIS cung cấp lifecycle management để process không sống vô hạn.

## 3. How does it work?

```text
Old w3wp.exe serving traffic
        |
        | recycle
        v
New w3wp.exe starts
        |
        +-> app startup / warm-up
        |
Old process drains / exits
```

Nếu startup chậm hoặc background work không hỗ trợ cancellation, request có thể fail trong transition.

## 4. Practical implementation

ASP.NET Core hosted trên IIS nên xử lý shutdown token đúng cách:

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await ProcessNextAsync(stoppingToken);
        }
    }
}
```

Không nên fire-and-forget work quan trọng trong request:

```csharp
_ = Task.Run(() => SendInvoiceAsync(invoiceId));
```

Recycle có thể terminate process trước khi task hoàn tất.

## 5. Real production scenario

Legacy enterprise app chạy IIS có background timer gửi email. Mỗi recycle, timer task đang chạy bị terminate và một số notification bị mất. Không có durable queue nên hệ thống không thể biết work nào chưa hoàn tất.

## 6. Failure scenario & troubleshooting

**Symptom** → request 502/503 ngắn hoặc background job mất đúng thời điểm deployment/recycle.

**Evidence** → Windows Event Logs/IIS logs cho thấy worker process restart; app logs có startup sequence mới.

**Hypothesis** → lifecycle handling sai, startup quá chậm hoặc in-process background work không durable.

**Diagnosis** → correlate process ID, deployment time, app startup logs và missing work.

**Fix** → graceful shutdown, health/warm-up, externalize durable work vào queue/Worker Service.

**Verification** → chủ động recycle dưới load và xác nhận request draining/work durability.

## 7. Common mistakes

- Coi process memory là durable storage.
- Chạy critical scheduled job trong web instance duy nhất mà không có coordination.
- Không log process ID/startup/shutdown.
- Tắt recycle hoàn toàn để tránh bug lifecycle.

## 8. Alternatives

Azure App Service, Windows Service, Worker Service hoặc container platform đều có lifecycle riêng nhưng nguyên tắc process replacement vẫn giống nhau.

## 9. Trade-offs

### Advantages

IIS cung cấp mature process hosting và operational controls.

### Costs / Risks

Legacy configuration, recycle semantics và Windows-specific operations tăng complexity so với modern container/cloud hosting.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu web process có thể restart bất kỳ lúc nào.

### Middle

Viết code shutdown-aware và đọc IIS logs.

### Senior

Thiết kế warm-up, request draining và durable background processing.

### Technical Lead / Architect

Quyết định workload nào còn phù hợp IIS và migration nào mang lại giá trị thực thay vì rewrite chỉ vì công nghệ cũ.

## 11. Key takeaway

- Process restart là normal operating condition.
- Critical work không nên phụ thuộc lifetime của web process.
- Recycle testing nên là một phần của production readiness.

# 9. OpenTelemetry distributed tracing: nối request, database và downstream dependency thành một causal chain để điều tra latency

## 1. What is it?

Distributed tracing ghi lại một trace cho toàn bộ request flow qua nhiều component. Trace gồm nhiều span: server request, HTTP dependency, database call, queue publish/consume...

OpenTelemetry cung cấp chuẩn instrumentation và context propagation độc lập backend quan sát cụ thể.

## 2. Why does it exist?

Trong distributed system, log riêng lẻ của từng service không đủ để trả lời “request này chậm ở đâu?”. Correlation ID thủ công hữu ích nhưng thường không biểu diễn parent-child timing và dependency topology rõ bằng trace.

## 3. How does it work?

```text
Trace abc
  Span API /checkout          900 ms
    Span SQL SELECT            40 ms
    Span Product API          120 ms
    Span Payment API          680 ms
```

Context như `traceparent` được propagate qua HTTP/message headers để downstream tạo child span đúng trace.

## 4. Practical implementation

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation()
        .AddSource("Orders.Application")
        .AddOtlpExporter());
```

Custom span:

```csharp
private static readonly ActivitySource Source =
    new("Orders.Application");

using var activity = Source.StartActivity("ValidateOrder");
activity?.SetTag("order.type", request.Type);
```

Không tag sensitive data hoặc high-cardinality values một cách vô tội vạ.

## 5. Real production scenario

Checkout p95 tăng từ 500 ms lên 1.4 s. CPU app bình thường, SQL cũng bình thường. Trace waterfall cho thấy payment API có tail latency tăng mạnh ở một region. Điều tra chuyển từ “đoán database” sang evidence cụ thể.

## 6. Failure scenario & troubleshooting

**Symptom** → traces bị đứt giữa services hoặc consumer không nối với producer.

**Evidence** → mỗi service có trace ID khác nhau cho cùng business operation.

**Hypothesis** → context propagation bị mất qua custom HTTP client/message header.

**Diagnosis** → inspect `traceparent`, instrumentation config và message propagation.

**Fix** → dùng chuẩn propagator, instrumentation library và tránh overwrite headers thủ công.

**Verification** → synthetic request phải hiện thành một end-to-end trace duy nhất.

## 7. Common mistakes

- Log `TraceId` nhưng không propagate context.
- Tạo span cho mọi method nhỏ gây telemetry noise/cost.
- Gắn user email/token vào span tags.
- Sampling quá mạnh mà không giữ error/critical traces cần thiết.
- Dùng tracing thay metrics cho mọi thứ.

## 8. Alternatives

Structured logs + correlation ID đủ cho hệ thống nhỏ. Metrics tốt hơn cho aggregate trend/SLO. Production observability thường cần cả logs + metrics + traces.

## 9. Trade-offs

### Advantages

Cho causal view end-to-end và đặc biệt mạnh khi debug distributed latency.

### Costs / Risks

Telemetry volume, storage cost, sampling và privacy governance cần được quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace là một request journey, span là từng đoạn work.

### Middle

Instrument ASP.NET Core, HTTP client, EF Core và đọc waterfall.

### Senior

Thiết kế sampling, custom spans, propagation qua messaging và incident workflow.

### Technical Lead / Architect

Đặt observability standard cho toàn hệ thống và cân bằng diagnostic value với cost/cardinality/privacy.

## 11. Key takeaway

- Trace trả lời “request này đã đi qua đâu và mất thời gian ở đâu?”.
- Context propagation là nền tảng; thiếu nó trace bị chia nhỏ.
- Tracing bổ sung cho logs/metrics, không thay thế chúng.

# 10. Vue/TypeScript async race condition: response cũ ghi đè state mới và cách kiểm soát request lifecycle ở frontend

## 1. What is it?

Async race condition ở frontend xảy ra khi nhiều request được gửi theo thứ tự A rồi B nhưng response về theo thứ tự B rồi A. Nếu code update state mỗi khi response về, dữ liệu cũ từ A có thể ghi đè dữ liệu mới từ B.

## 2. Why does it exist?

Network latency không deterministic. UI reactive khiến người dùng thay filter/search nhanh, nên nhiều request overlap là bình thường.

## 3. How does it work?

```text
User search "ca"  -> Request A
User search "car" -> Request B

B returns 100 ms -> UI shows "car"
A returns 500 ms -> UI overwritten with "ca"
```

Backend hoàn toàn đúng nhưng frontend state sai temporal ordering.

## 4. Practical implementation

Dùng `AbortController`:

```ts
let currentController: AbortController | null = null;

async function searchProducts(query: string) {
  currentController?.abort();
  currentController = new AbortController();

  const response = await fetch(
    `/api/products?q=${encodeURIComponent(query)}`,
    { signal: currentController.signal }
  );

  if (!response.ok) throw new Error("Search failed");

  products.value = await response.json();
}
```

Hoặc dùng request sequence:

```ts
let requestVersion = 0;

async function load(query: string) {
  const version = ++requestVersion;
  const result = await api.search(query);

  if (version === requestVersion) {
    products.value = result;
  }
}
```

## 5. Real production scenario

Marketplace UI có autocomplete. User gõ rất nhanh. Search request cũ trả chậm vì cache miss, request mới trả nhanh nhờ cache hit. UI cuối cùng hiển thị result cũ, khiến user thấy search “nhảy ngược”.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị data không khớp input hiện tại.

**Evidence** → browser Network tab cho thấy request/response completion order khác request order.

**Hypothesis** → stale response race.

**Diagnosis** → log request sequence/query và state update timestamp.

**Fix** → cancel superseded request hoặc ignore stale response.

**Verification** → throttle network trong DevTools và nhập liên tục; state cuối phải luôn khớp latest intent.

## 7. Common mistakes

- Debounce rồi nghĩ race đã biến mất hoàn toàn.
- Cancel request nhưng catch `AbortError` như real application error.
- Dùng global loading boolean cho nhiều concurrent requests.
- Update state từ response mà không kiểm tra request còn current hay không.

## 8. Alternatives

Libraries như TanStack Query/Vue Query cung cấp request deduplication, cancellation và stale-state management tốt hơn khi data fetching phức tạp. Với form đơn giản, `AbortController` đủ rõ và nhẹ.

## 9. Trade-offs

### Advantages

Cancellation/sequence guard làm UI deterministic hơn và giảm work không cần thiết.

### Costs / Risks

State machine frontend phức tạp hơn khi có retry, optimistic update và pagination.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request gửi trước không đảm bảo response về trước.

### Middle

Dùng cancellation, loading/error state và DevTools để debug.

### Senior

Thiết kế data-fetching abstraction, stale policy và race-safe state transitions.

### Technical Lead / Architect

Chọn mức abstraction phù hợp: native fetch cho flow đơn giản hay query library cho app có caching/invalidation phức tạp; đồng thời đảm bảo frontend behavior khớp API semantics.

## 11. Key takeaway

- Async UI phải xử lý out-of-order response như một normal condition.
- Debounce giảm request nhưng không thay thế race control.
- Latest user intent phải thắng, không phải response đến cuối cùng một cách ngẫu nhiên.
