# 1. C# `IAsyncEnumerable<T>`: streaming bất đồng bộ, cancellation và consumer-driven backpressure

## 1. What is it?

`IAsyncEnumerable<T>` là abstraction cho một chuỗi dữ liệu được tạo bất đồng bộ theo thời gian. Thay vì chờ toàn bộ dataset hoàn tất rồi trả `Task<List<T>>`, producer có thể yield từng phần tử khi chúng sẵn sàng và consumer đọc bằng `await foreach`.

Mental model:

```text
Task<List<T>>
request → load all → allocate all → return all

IAsyncEnumerable<T>
request → item 1 → item 2 → item 3 → ...
           ↑ consumer pulls progressively
```

Điểm quan trọng là đây là pull-based asynchronous iteration. Consumer quyết định khi nào yêu cầu phần tử tiếp theo, nhờ đó producer tự nhiên không chạy vô hạn nhanh hơn consumer trong nhiều use case.

## 2. Why does it exist?

Một endpoint export hàng trăm nghìn records, một data-processing pipeline hoặc một SDK đọc stream network không nên luôn materialize toàn bộ dữ liệu trong memory trước khi caller bắt đầu xử lý.

Streaming giúp:

* giảm time-to-first-item;
* giảm peak memory;
* cho phép pipeline xử lý từng phần tử;
* dừng sớm khi consumer cancel hoặc đã đủ dữ liệu.

Nhưng streaming cũng làm lifetime của database connection, HTTP connection hoặc iterator kéo dài hơn, nên không phải lúc nào cũng tốt hơn materialization.

## 3. How does it work?

Compiler biến async iterator thành state machine tương tự `async` method nhưng có thêm iteration state.

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken cancellationToken = default)
{
    await foreach (var order in _repository.StreamAsync(cancellationToken))
    {
        yield return new OrderDto(order.Id, order.Total);
    }
}
```

Mỗi lần consumer gọi `MoveNextAsync()`, producer chạy tới `yield return` kế tiếp hoặc tới khi hoàn tất.

`[EnumeratorCancellation]` cho phép token truyền từ `.WithCancellation(token)` vào iterator parameter đúng cách.

## 4. Practical implementation

EF Core có thể expose query dạng async stream:

```csharp
public IAsyncEnumerable<OrderDto> StreamRecentAsync(
    DateTimeOffset from,
    CancellationToken cancellationToken)
{
    return _db.Orders
        .AsNoTracking()
        .Where(x => x.CreatedAt >= from)
        .OrderBy(x => x.Id)
        .Select(x => new OrderDto(x.Id, x.Total))
        .AsAsyncEnumerable()
        .WithCancellation(cancellationToken);
}
```

Consumer:

```csharp
await foreach (var order in service
    .StreamRecentAsync(from, cancellationToken)
    .WithCancellation(cancellationToken))
{
    await writer.WriteAsync(order, cancellationToken);
}
```

Nếu endpoint trả JSON array thông thường, serializer vẫn phải giữ response contract phù hợp. Với NDJSON hoặc streaming protocol, từng record có thể được flush độc lập.

## 5. Real production scenario

Một reporting API export 500.000 invoices. Version đầu gọi `ToListAsync()`, tạo object graph lớn rồi serialize. Working set tăng mạnh và request có time-to-first-byte hơn 20 giây.

Chuyển sang streaming giúp response bắt đầu sớm và giữ memory gần như ổn định. Tuy nhiên DB connection tồn tại lâu hơn, vì vậy team phải giới hạn concurrent exports và dùng read replica để không làm cạn pool của transactional API.

## 6. Failure scenario & troubleshooting

**Symptom** → memory giảm nhưng DB connection pool lại cạn khi nhiều exports chạy đồng thời.

**Evidence** → mỗi request giữ active reader/connection trong vài phút.

**Hypothesis** → streaming kéo dài resource lifetime.

**Diagnosis** → correlate active streams với pool usage, request duration và query execution.

**Fix** → giới hạn concurrent streams, chunk theo cursor hoặc đưa export sang background job/object storage nếu workload quá dài.

**Verification** → load test với concurrent slow consumers, không chỉ consumer đọc nhanh trong local environment.

## 7. Common mistakes

* Nghĩ streaming luôn dùng ít tài nguyên hơn mọi mặt.
* Không propagate cancellation khi client disconnect.
* Thực hiện `ToListAsync()` bên trong iterator rồi tưởng vẫn đang stream.
* Giữ scoped dependencies sau khi request scope đã dispose.
* Dùng một `DbContext` stream đồng thời nhiều operations.

## 8. Alternatives

`Task<List<T>>` đơn giản và phù hợp dataset nhỏ. Cursor pagination phù hợp user-facing list. Background export tạo file trong Blob Storage phù hợp report rất lớn hoặc cần retry/resume.

## 9. Trade-offs

### Advantages

* Time-to-first-item thấp.
* Peak memory thấp.
* Hỗ trợ early termination.

### Costs / Risks

* Resource lifetime dài.
* Error có thể xảy ra sau khi response đã bắt đầu.
* Retry toàn stream khó hơn retry một request nhỏ.
* Consumer chậm có thể giữ server resources lâu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async stream khác với `Task<List<T>>`.

### Middle

Biết `await foreach`, cancellation và tránh accidental materialization.

### Senior

Đánh giá connection lifetime, slow consumer, chunking và failure-after-response-started.

### Technical Lead / Architect

Chọn streaming, pagination hay asynchronous export dựa trên data size, concurrency, retry và infrastructure limits.

## 11. Key takeaway

* `IAsyncEnumerable<T>` tối ưu data flow, không tự động tối ưu toàn bộ resource usage.
* Streaming giảm memory nhưng có thể kéo dài connection lifetime.
* Cancellation và concurrency limits là phần bắt buộc của production streaming.

# 2. EF Core `AsSplitQuery`: tránh cartesian explosion nhưng phải hiểu consistency và round-trip trade-off

## 1. What is it?

Khi query entity cùng nhiều collection navigations bằng `Include`, EF Core có thể tạo một SQL query với nhiều joins. Nếu hai collections cùng fan-out, số rows trung gian có thể nhân lên rất lớn — hiện tượng thường gọi là cartesian explosion.

`AsSplitQuery()` yêu cầu EF Core tải root entities và related collections bằng nhiều SQL queries thay vì một join khổng lồ.

## 2. Why does it exist?

Giả sử một `Blog` có 50 `Posts` và 20 `Contributors`. Join cả hai collection có thể tạo 1.000 rows cho một blog dù domain chỉ có 71 objects.

Network payload, sorting, materialization và duplicate column transfer đều tăng. Split query đánh đổi số round trips để giảm row multiplication.

## 3. How does it work?

Single query mental model:

```text
Blogs
 JOIN Posts
 JOIN Contributors
 → rows multiply
```

Split query:

```text
SELECT Blogs...
SELECT Posts WHERE BlogId IN (...)
SELECT Contributors WHERE BlogId IN (...)
```

EF Core sau đó fix-up relationships trong memory.

## 4. Practical implementation

```csharp
var blogs = await db.Blogs
    .AsNoTracking()
    .Include(x => x.Posts)
    .Include(x => x.Contributors)
    .AsSplitQuery()
    .Where(x => x.IsActive)
    .ToListAsync(cancellationToken);
```

Tốt hơn nữa, nếu endpoint chỉ cần DTO summary, projection thường rẻ hơn `Include`:

```csharp
var result = await db.Blogs
    .Where(x => x.IsActive)
    .Select(x => new BlogSummary(
        x.Id,
        x.Name,
        x.Posts.Count,
        x.Contributors.Count))
    .ToListAsync(cancellationToken);
```

## 5. Real production scenario

Một CMS admin page load page tree cùng blocks, languages và permissions. Query single-join trả hàng trăm MB dữ liệu trung gian dù kết quả cuối chỉ vài nghìn entities.

`AsSplitQuery()` giảm payload đáng kể. Sau đó team tiếp tục tối ưu bằng projection cho list view để không load full graph.

## 6. Failure scenario & troubleshooting

**Symptom** → sau khi chuyển split query, đôi lúc parent và children phản ánh hai thời điểm dữ liệu khác nhau.

**Evidence** → có write concurrent giữa các SELECT của split query.

**Hypothesis** → multi-query read không có snapshot consistency mong muốn.

**Diagnosis** → xem isolation level và khoảng thời gian giữa statements.

**Fix** → nếu cần consistent snapshot, dùng transaction/isolation phù hợp hoặc chọn single query/projection.

**Verification** → concurrency test có writer chạy giữa các query phases.

## 7. Common mistakes

* Bật split query toàn project mà không hiểu access patterns.
* Dùng `Include` cho DTO endpoint nơi projection là đủ.
* Chỉ đo SQL duration mà không đo bytes transferred.
* Quên rằng nhiều statements tạo nhiều round trips.
* Giả định tất cả statements thấy cùng snapshot ở mọi isolation level.

## 8. Alternatives

Projection, explicit loading, manually batched queries, raw SQL hoặc read model riêng có thể phù hợp hơn với complex read path.

## 9. Trade-offs

### Advantages

* Giảm row multiplication.
* Giảm duplicate network payload.
* Có thể giảm memory/materialization cost.

### Costs / Risks

* Nhiều DB round trips.
* Consistency giữa statements cần xem xét.
* Không sửa được over-fetching nếu vẫn load graph quá lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu nhiều `Include` collections có thể nhân rows.

### Middle

Biết dùng `AsSplitQuery()` và projection theo use case.

### Senior

Đo network payload, round trips, isolation và concurrency semantics.

### Technical Lead / Architect

Đặt query-shaping conventions cho transactional path, CMS screens và reporting workloads.

## 11. Key takeaway

* `AsSplitQuery()` giải quyết row explosion, không phải universal performance switch.
* Projection thường tốt hơn nếu API chỉ cần một phần dữ liệu.
* Split query đổi một query lớn thành nhiều queries, nên consistency và latency phải được cân nhắc.

# 3. Elasticsearch alias-based reindex: zero-downtime schema evolution cho search index

## 1. What is it?

Elasticsearch mapping có nhiều thay đổi không thể chỉnh in-place an toàn, đặc biệt khi đổi field type hoặc analyzer. Pattern phổ biến là tạo index mới, reindex dữ liệu rồi đổi alias từ index cũ sang index mới atomically.

```text
products-read → products-v12

create products-v13
reindex + validate
alias switch
products-read → products-v13
```

## 2. Why does it exist?

Search index là derived data store nhưng production clients vẫn phụ thuộc availability của nó. Nếu drop/recreate index trực tiếp, search có downtime hoặc trả kết quả thiếu trong lúc rebuild.

Versioned indices + aliases tách physical index lifecycle khỏi logical name mà application dùng.

## 3. How does it work?

Application đọc từ alias như `products-read`. Deployment tạo `products-v13` với mapping/settings mới, backfill dữ liệu, đồng bộ writes mới, validate, sau đó thực hiện alias action atomically.

Alias switch bản thân có thể atomic, nhưng correctness của dữ liệu trước switch mới là phần khó.

## 4. Practical implementation

Tạo index mới:

```json
PUT products-v13
{
  "settings": {
    "number_of_shards": 3
  },
  "mappings": {
    "properties": {
      "name": { "type": "text" },
      "sku": { "type": "keyword" }
    }
  }
}
```

Sau khi backfill và validate:

```json
POST _aliases
{
  "actions": [
    { "remove": { "index": "products-v12", "alias": "products-read" } },
    { "add":    { "index": "products-v13", "alias": "products-read" } }
  ]
}
```

Write alias có thể được quản lý riêng để tránh application ghi nhầm nhiều indices.

## 5. Real production scenario

E-commerce search cần đổi `category` từ analyzed text sang keyword-compatible structure và thay analyzer cho product name. Rebuilding 80 triệu documents mất hàng giờ.

Team tạo index version mới, backfill từ source-of-truth database, replay changes trong thời gian backfill, so sánh document count/sample queries rồi switch alias trong vài milliseconds.

## 6. Failure scenario & troubleshooting

**Symptom** → sau alias switch, một số sản phẩm vừa cập nhật bị quay về dữ liệu cũ.

**Evidence** → backfill snapshot ghi document cũ sau một live-update đã được dual-write vào index mới.

**Hypothesis** → race giữa historical backfill và incremental updates.

**Diagnosis** → compare source version/timestamp hoặc sequence number của records bị sai.

**Fix** → dùng version-aware indexing, CDC/event replay hoặc high-watermark strategy thay vì blind writes.

**Verification** → test update xảy ra đồng thời với backfill và xác nhận newest source version thắng.

## 7. Common mistakes

* Chỉ quan tâm alias switch mà bỏ qua synchronization window.
* Dùng Elasticsearch làm source of truth trong reindex workflow.
* Không validate analyzer/query behavior trước cutover.
* Xóa index cũ ngay sau switch nên rollback không còn nhanh.
* Hard-code physical index name trong application.

## 8. Alternatives

In-place mapping update chỉ phù hợp additive compatible changes. Runtime fields có thể tránh reindex trong vài cases nhưng có query cost. Blue/green search clusters chỉ cần khi thay đổi lớn hơn index schema.

## 9. Trade-offs

### Advantages

* Gần zero-downtime cutover.
* Rollback nhanh bằng alias.
* Physical schema version rõ ràng.

### Costs / Risks

* Tạm thời cần gấp đôi storage.
* Backfill + live synchronization phức tạp.
* Validation phải bao gồm relevance, không chỉ document count.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu alias tách logical name khỏi physical index.

### Middle

Biết create/reindex/validate/switch alias.

### Senior

Thiết kế synchronization, versioning, rollback và relevance verification.

### Technical Lead / Architect

Chuẩn hóa search-index lifecycle và source-of-truth ownership trong architecture.

## 11. Key takeaway

* Zero-downtime reindex khó nhất ở data synchronization, không phải alias API.
* Index mới phải được validate cả completeness lẫn search behavior.
* Giữ index cũ đủ lâu để rollback có kiểm soát.

# 4. SQL Server filtered index: tối ưu selective workload mà không nhân bản index vô hạn

## 1. What is it?

Filtered index là nonclustered index chỉ chứa rows thỏa một predicate. Thay vì index toàn bộ table, database duy trì index cho subset có giá trị truy cập cao.

Ví dụ:

```sql
CREATE INDEX IX_Jobs_Pending
ON Jobs(CreatedAt)
INCLUDE (Id, QueueName)
WHERE Status = 'Pending';
```

## 2. Why does it exist?

Một job table có 100 triệu rows nhưng chỉ 50.000 pending jobs. Worker luôn query pending rows. Full-table index trên `Status, CreatedAt` lớn hơn cần thiết và phải maintain cho cả completed history.

Filtered index làm index nhỏ hơn, selective hơn và rẻ hơn cho đúng hot subset.

## 3. How does it work?

Optimizer chỉ dùng filtered index khi nó chứng minh query predicate tương thích với filter. Statistics của filtered index cũng phản ánh subset, thường cho cardinality estimate tốt hơn với highly skewed data.

## 4. Practical implementation

```sql
SELECT TOP (100)
    Id,
    QueueName,
    CreatedAt
FROM Jobs
WHERE Status = 'Pending'
ORDER BY CreatedAt;
```

Index:

```sql
CREATE INDEX IX_Jobs_Pending_CreatedAt
ON Jobs(CreatedAt)
INCLUDE (Id, QueueName)
WHERE Status = 'Pending';
```

Đo bằng Actual Execution Plan và `SET STATISTICS IO ON` trước/sau.

## 5. Real production scenario

Notification system giữ lịch sử 18 tháng. 99,8% rows ở trạng thái `Sent`; dispatcher chỉ cần `Pending`. Full index chiếm nhiều GB và tăng write cost.

Filtered index cho pending queue nhỏ hơn nhiều và cải thiện polling latency mà không cần index toàn history.

## 6. Failure scenario & troubleshooting

**Symptom** → filtered index tồn tại nhưng query vẫn scan index/table khác.

**Evidence** → execution plan không chọn filtered index.

**Hypothesis** → query predicate/parameterization khiến optimizer không chứng minh được filter compatibility hoặc index không cover access path.

**Diagnosis** → inspect actual predicate, parameter type, implicit conversion và estimated rows.

**Fix** → align predicate/type, cải thiện query shape hoặc index columns; không force index trước khi hiểu lý do optimizer bỏ qua.

**Verification** → benchmark representative parameter values và writes.

## 7. Common mistakes

* Tạo filtered index cho quá nhiều status values.
* Dùng filter trên condition thay đổi liên tục và bỏ qua write churn.
* Không xem parameterization/implicit conversion.
* Force index bằng hint để che statistics/query issue.
* Chỉ đo read mà không đo storage/write cost.

## 8. Alternatives

Composite full index, partitioning, archival table hoặc queue table riêng có thể tốt hơn nếu hot/cold lifecycle rất rõ.

## 9. Trade-offs

### Advantages

* Index nhỏ và selective.
* Statistics sát hot subset.
* Giảm maintenance so với full index trong nhiều workloads.

### Costs / Risks

* Chỉ hữu ích cho matching predicates.
* Query shape phải tương thích.
* Nhiều filtered indices vẫn tạo schema complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không nhất thiết phải chứa mọi row.

### Middle

Biết thiết kế filter theo hot access pattern và đọc plan.

### Senior

Đánh giá skew, parameterization, write churn và archival strategy.

### Technical Lead / Architect

Quyết định khi filtered index đủ hay cần tách hot/cold data model.

## 11. Key takeaway

* Filtered index rất mạnh khi workload chỉ đọc một subset nhỏ và ổn định.
* Index tồn tại không đảm bảo optimizer dùng nó.
* Data lifecycle và write cost phải được tính cùng read latency.

# 5. Transactional Inbox + idempotent side effects: exactly-once business outcome trên at-least-once delivery

## 1. What is it?

Message brokers thường cung cấp at-least-once delivery: một message có thể được giao lại. Inbox Pattern lưu message identifier đã xử lý trong cùng transaction với business state để consumer nhận duplicate nhưng không áp dụng business transition hai lần.

Điều cần đạt thường không phải “exactly-once message delivery” mà là **effectively-once business outcome**.

## 2. Why does it exist?

Consumer có thể commit database rồi crash trước khi ACK message. Broker sẽ redeliver. Nếu handler charge card, cộng points hoặc tạo invoice lần nữa, duplicate delivery biến thành duplicate business effect.

## 3. How does it work?

```text
receive message M123
      ↓
begin DB transaction
      ↓
insert Inbox(M123) with unique key
      ↓
apply business state
      ↓
commit
      ↓
ack broker
```

Khi M123 tới lại, unique inbox record cho biết business transition đã được commit.

## 4. Practical implementation

Schema:

```sql
CREATE TABLE InboxMessages (
    MessageId uniqueidentifier NOT NULL PRIMARY KEY,
    ProcessedAt datetime2 NOT NULL
);
```

Handler:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

var alreadyProcessed = await db.InboxMessages
    .AnyAsync(x => x.MessageId == message.Id, ct);

if (alreadyProcessed)
{
    await tx.CommitAsync(ct);
    return;
}

db.InboxMessages.Add(new InboxMessage(message.Id, clock.UtcNow));
order.ApplyPayment(message.PaymentId, message.Amount);

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Trong production nên dựa vào unique constraint để xử lý race, không chỉ `AnyAsync()`.

## 5. Real production scenario

Payment-confirmed event được xử lý bởi loyalty service. Consumer update points rồi process crash trước broker settlement. Event được giao lại sau restart.

Inbox unique key ngăn cộng points lần hai. Nếu handler còn gọi external coupon service, side effect đó cũng cần idempotency key; database inbox không magically bao phủ external API.

## 6. Failure scenario & troubleshooting

**Symptom** → DB state không duplicate nhưng external email/coupon vẫn gửi hai lần.

**Evidence** → inbox transaction bảo vệ database change, nhưng external call nằm ngoài transactional boundary.

**Hypothesis** → team nhầm inbox với exactly-once side effects toàn hệ thống.

**Diagnosis** → liệt kê mọi side effect trong handler và ownership boundary của từng cái.

**Fix** → external API dùng idempotency key, hoặc ghi outgoing work vào Outbox rồi xử lý riêng.

**Verification** → fault-injection sau DB commit, trước ACK và giữa external calls.

## 7. Common mistakes

* Check duplicate bằng query nhưng không có unique constraint.
* Xóa inbox records quá sớm.
* Message ID không ổn định qua retry.
* Đặt external side effect trong DB transaction rồi tưởng atomic.
* ACK trước khi transaction commit.

## 8. Alternatives

Business entity có natural idempotency key, deduplication ở broker hoặc compare-and-set state transition có thể đủ trong vài workflows. Saga cần khi nhiều services cùng tham gia long-running transaction.

## 9. Trade-offs

### Advantages

* Robust với redelivery.
* Audit được message processing.
* Phù hợp at-least-once brokers.

### Costs / Risks

* Inbox table cần retention/cleanup.
* External side effects vẫn cần idempotency riêng.
* Transaction contention có thể tăng ở high throughput.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu message có thể được giao nhiều lần.

### Middle

Implement inbox + unique constraint + transaction.

### Senior

Thiết kế idempotency xuyên DB và external effects, retention và replay.

### Technical Lead / Architect

Đặt messaging reliability contract cho toàn ecosystem thay vì để từng consumer tự đoán semantics.

## 11. Key takeaway

* At-least-once delivery yêu cầu consumer idempotency.
* Inbox bảo vệ business state trong DB boundary, không tự bảo vệ external side effects.
* Exactly-once business outcome là architecture property, không phải broker checkbox.

# 6. Azure App Configuration + feature flags: dynamic configuration mà không biến config thành distributed mutable state

## 1. What is it?

Azure App Configuration là centralized configuration store cho application settings và feature flags. Application có thể refresh configuration mà không cần redeploy, nhưng cần kiểm soát caching, rollout và failure behavior.

## 2. Why does it exist?

Khi nhiều services/environments có cùng operational settings, hard-code hoặc copy config qua deployment variables dễ drift. Feature flags cũng cần lifecycle, targeting và gradual rollout độc lập với code deployment.

Centralized config giải quyết distribution; nó không loại bỏ nhu cầu versioning và ownership.

## 3. How does it work?

Application thường load một snapshot rồi refresh theo trigger/interval. Managed Identity có thể authenticate tới App Configuration mà không dùng connection string secret.

```text
App starts
  ↓
load config snapshot
  ↓
serve requests from local cache
  ↓
refresh periodically/on sentinel change
```

Hot path không nên gọi remote config store trên mỗi request.

## 4. Practical implementation

```csharp
builder.Configuration.AddAzureAppConfiguration(options =>
{
    options.Connect(
        new Uri(endpoint),
        new DefaultAzureCredential())
    .Select("MyApp:*")
    .ConfigureRefresh(refresh =>
    {
        refresh.Register("MyApp:Sentinel", refreshAll: true)
               .SetRefreshInterval(TimeSpan.FromSeconds(30));
    })
    .UseFeatureFlags();
});

builder.Services.AddAzureAppConfiguration();
builder.Services.AddFeatureManagement();
```

Request pipeline có middleware refresh nhưng local cached values vẫn là read path chính.

## 5. Real production scenario

Team cần disable recommendation engine khi downstream vendor degraded. Feature flag cho phép tắt integration trong vài chục giây mà không redeploy toàn fleet.

Nhưng nếu flag quyết định core financial invariant, thay đổi live không qua deployment review có thể nguy hiểm. Không phải mọi business rule đều nên biến thành mutable flag.

## 6. Failure scenario & troubleshooting

**Symptom** → một số instances dùng flag mới, số khác vẫn dùng flag cũ.

**Evidence** → refresh timestamps khác nhau hoặc instances mất connectivity tới config service.

**Hypothesis** → distributed cache convergence delay.

**Diagnosis** → log config version/sentinel và refresh outcome theo instance.

**Fix** → thiết kế bounded staleness, health telemetry và rollout window; với critical synchronized change, dùng versioned protocol thay vì mong refresh tức thời.

**Verification** → test config-service outage và mixed-version instances.

## 7. Common mistakes

* Remote lookup mỗi request.
* Dùng feature flag như permanent if/else branching.
* Không có owner/expiry date cho flags.
* Đưa secrets vào App Configuration thay vì Key Vault.
* Giả định toàn fleet cập nhật cùng millisecond.

## 8. Alternatives

Deployment-time environment variables đơn giản hơn cho immutable config. Key Vault dành cho secrets. Database/business admin settings phù hợp khi cần audit domain-level changes.

## 9. Trade-offs

### Advantages

* Centralized configuration.
* Dynamic operational controls.
* Tách deployment khỏi release.

### Costs / Risks

* Eventual convergence giữa instances.
* Runtime mutable behavior khó debug hơn.
* Flag debt và governance cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu config load/caching khác database lookup.

### Middle

Dùng Managed Identity, refresh và feature management đúng cách.

### Senior

Thiết kế stale-config behavior, observability và flag lifecycle.

### Technical Lead / Architect

Phân định immutable deployment config, secret, operational flag và domain setting thành các ownership khác nhau.

## 11. Key takeaway

* Centralized config không nên trở thành synchronous runtime dependency cho mỗi request.
* Dynamic flags có convergence delay và cần lifecycle governance.
* Secrets, operational flags và business settings không phải cùng một loại dữ liệu.

# 7. Kubernetes PodDisruptionBudget: bảo vệ availability khi voluntary disruption xảy ra

## 1. What is it?

PodDisruptionBudget (PDB) đặt giới hạn số Pods của một workload có thể đồng thời unavailable do **voluntary disruptions** như node drain, cluster upgrade hoặc autoscaler eviction.

Ví dụ:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: orders-api-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: orders-api
```

## 2. Why does it exist?

Một deployment có 3 replicas nhưng nếu maintenance drain hai nodes cùng lúc, scheduler/operator có thể evict quá nhiều Pods và làm service mất capacity dù application không crash.

PDB cho orchestration layer biết availability floor cần giữ trong planned disruptions.

## 3. How does it work?

PDB tính healthy Pods matching selector và cho phép hoặc từ chối eviction tùy `minAvailable` hoặc `maxUnavailable`.

PDB không ngăn node crash, OOM kill hoặc hardware failure. Nó không phải high-availability guarantee cho involuntary outages.

## 4. Practical implementation

Với 4 replicas:

```yaml
spec:
  replicas: 4
```

PDB:

```yaml
spec:
  maxUnavailable: 1
```

Node drain sẽ cố không evict quá một matching Pod unavailable cùng lúc. Deployment readiness probes phải chính xác, vì PDB dựa trên health/readiness state.

## 5. Real production scenario

Managed Kubernetes cluster upgrade tuần tự drain nodes. Stateful-ish API có warm cache và startup 90 giây. Không PDB, nhiều replicas bị evict gần nhau, p99 tăng và traffic dồn vào một instance.

PDB + topology spread + đủ replicas giữ capacity trong maintenance.

## 6. Failure scenario & troubleshooting

**Symptom** → node drain treo hàng chục phút và không evict được Pod.

**Evidence** → eviction trả thông tin PDB violation.

**Hypothesis** → budget quá strict so với số replicas/healthy Pods hiện có.

**Diagnosis** → xem desired replicas, current ready Pods, selector và PDB status.

**Fix** → tăng capacity/repair unhealthy Pod trước; chỉ nới PDB nếu business availability cho phép.

**Verification** → thực hiện controlled drain trong staging/load environment.

## 7. Common mistakes

* `minAvailable: 100%` khiến maintenance gần như không tiến hành được.
* Chỉ có 1 replica nhưng kỳ vọng PDB tạo HA.
* Selector sai nên PDB không bảo vệ workload.
* Nghĩ PDB bảo vệ khỏi node crash.
* Không kết hợp topology spread/anti-affinity.

## 8. Alternatives

Deployment rolling-update settings, topology spread constraints, node anti-affinity và autoscaling giải quyết các phần khác của availability problem. PDB chỉ quản voluntary eviction concurrency.

## 9. Trade-offs

### Advantages

* Bảo vệ capacity trong maintenance.
* Làm cluster operations tôn trọng application availability target.

### Costs / Risks

* Budget quá strict có thể block upgrades/drains.
* Không cứu được insufficient replica count.
* Phụ thuộc readiness correctness.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu PDB liên quan planned eviction, không phải mọi failure.

### Middle

Cấu hình `minAvailable`/`maxUnavailable` theo replica count.

### Senior

Kết hợp PDB, rollout, topology và startup capacity.

### Technical Lead / Architect

Đặt availability policy phù hợp SLO và cluster maintenance strategy.

## 11. Key takeaway

* PDB là contract giữa workload availability và cluster operations.
* Nó không tạo thêm replicas và không ngăn involuntary failure.
* Budget phải đủ bảo vệ service nhưng vẫn cho phép maintenance tiến triển.

# 8. OpenTelemetry baggage vs span attributes: context propagation, cardinality và privacy boundary

## 1. What is it?

Span attributes là metadata gắn với một span cụ thể. Baggage là key/value context có thể được propagate qua process/service boundaries cùng request context.

```text
Trace context: trace/span identity
Baggage: propagating business context
Span attributes: telemetry metadata on current span
```

Baggage tiện nhưng nguy hiểm vì một value có thể được forward qua nhiều services.

## 2. Why does it exist?

Một platform có thể muốn propagate tenant tier hoặc experiment cohort để downstream instrumentation enrich traces mà không truyền parameter qua mọi method signature.

Nhưng propagation mở thêm privacy, trust và payload concerns. Không phải mọi log field đều nên thành baggage.

## 3. How does it work?

W3C Baggage có thể đi qua HTTP headers. Service downstream đọc baggage rồi có thể copy selected values thành span attributes.

Baggage bản thân không đảm bảo authenticity. Nếu nhận từ external client mà không sanitize, user có thể inject context giả.

## 4. Practical implementation

```csharp
Baggage.SetBaggage("tenant.tier", tenantTier);

using var activity = ActivitySource.StartActivity("ProcessOrder");
activity?.SetTag("tenant.tier", tenantTier);
activity?.SetTag("order.type", orderType);
```

Identity-sensitive values nên được derive từ authenticated server context, không tin baggage do browser gửi.

## 5. Real production scenario

Team thêm `customer.email` và `user.id` vào baggage để “debug dễ hơn”. Các values bị propagate qua nhiều services và exporter, vô tình mở rộng PII footprint tới telemetry vendors và logs.

Giải pháp là dùng bounded, non-sensitive context như tenant tier hoặc request class; identity chi tiết chỉ lưu nơi có policy phù hợp.

## 6. Failure scenario & troubleshooting

**Symptom** → downstream traces có tenant tier không hợp lệ hoặc value do client tự chọn.

**Evidence** → incoming `baggage` header được trust trực tiếp.

**Hypothesis** → telemetry context bị coi là authorization context.

**Diagnosis** → trace source của baggage và middleware propagation.

**Fix** → strip untrusted keys tại ingress, regenerate server-owned context, không dùng baggage cho security decisions.

**Verification** → gửi crafted baggage header và xác nhận application authorization không đổi.

## 7. Common mistakes

* Đưa secrets/PII vào baggage.
* Dùng baggage làm authorization input.
* Propagate high-cardinality data không giới hạn.
* Copy mọi baggage key thành metric dimension.
* Không đặt size/key allowlist.

## 8. Alternatives

Explicit method parameters rõ nhất cho business-critical context. Claims phù hợp authenticated identity. Logs/traces có thể enrich locally mà không propagate nếu downstream không cần value.

## 9. Trade-offs

### Advantages

* Cross-service context propagation tiện.
* Giảm plumbing cho observability metadata.

### Costs / Risks

* Privacy footprint lan rộng.
* Header size tăng.
* Context có thể bị spoof nếu ingress không kiểm soát.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt trace identity, baggage và span tags.

### Middle

Propagate selected safe keys và enrich spans.

### Senior

Thiết kế trust, privacy, cardinality và propagation boundaries.

### Technical Lead / Architect

Đặt telemetry-context governance toàn hệ thống và explicit allowlist cho propagated metadata.

## 11. Key takeaway

* Baggage là propagation mechanism, không phải trusted identity channel.
* Chỉ propagate bounded, non-sensitive context thực sự cần downstream.
* Không biến baggage thành metric-label explosion hoặc PII distribution bus.

# 9. CORS với credentialed browser requests: preflight, origin policy và vì sao CORS không phải authorization

## 1. What is it?

CORS là browser-enforced policy cho phép server chỉ định origin nào được JavaScript đọc response cross-origin. Nó không phải cơ chế ngăn server nhận request từ attacker và không thay authentication/authorization.

Credentialed request dùng cookies hoặc browser credentials và có rules chặt hơn wildcard origin.

## 2. Why does it exist?

Same-Origin Policy bảo vệ browser khỏi một website tùy ý đọc dữ liệu từ website khác bằng JavaScript. CORS là controlled relaxation do server công bố.

Ví dụ SPA ở `https://app.example.com` gọi API `https://api.example.com` là cross-origin dù cùng parent domain.

## 3. How does it work?

Với non-simple request, browser gửi preflight:

```http
OPTIONS /orders
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type,authorization
```

Server trả allowed origin/method/headers. Sau đó browser mới gửi request thật nếu policy cho phép.

Credentialed response cần explicit origin; `Access-Control-Allow-Origin: *` không được dùng cùng credentials.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("spa", policy =>
    {
        policy.WithOrigins("https://app.example.com")
              .AllowAnyHeader()
              .AllowAnyMethod()
              .AllowCredentials();
    });
});

app.UseCors("spa");
```

Origin list phải là trusted configuration, không phản chiếu mọi incoming `Origin` header.

## 5. Real production scenario

Team fix lỗi CORS bằng middleware “echo Origin” và `AllowCredentials`. Bất kỳ malicious site nào cũng được browser cho phép đọc authenticated API response nếu victim đang đăng nhập bằng cookie.

CORS misconfiguration ở đây làm yếu browser isolation nhưng root security vẫn phải được củng cố bằng authentication, authorization và CSRF strategy phù hợp.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend báo CORS error nhưng API logs cho thấy request trả 500.

**Evidence** → error response thiếu CORS headers vì exception middleware/order sai.

**Hypothesis** → browser che underlying HTTP failure vì response không thỏa CORS.

**Diagnosis** → inspect Network tab, server logs và preflight riêng biệt; không chỉ đọc console message.

**Fix** → sửa root 500 và pipeline ordering; cấu hình CORS đúng boundary.

**Verification** → test allowed origin, denied origin, preflight và credentialed request.

## 7. Common mistakes

* Xem CORS như authorization.
* `AllowAnyOrigin` + credentials bằng custom header reflection.
* Cho phép origins từ user-controlled input.
* Quên reverse proxy/CDN xử lý OPTIONS.
* Debug CORS mà không kiểm tra actual server error.

## 8. Alternatives

Serve SPA và API cùng origin để tránh CORS complexity. Backend-for-Frontend có thể giữ browser boundary đơn giản hơn. Token-based auth không tự loại bỏ toàn bộ CORS considerations nếu browser vẫn gọi cross-origin.

## 9. Trade-offs

### Advantages

* Cho phép browser integration cross-origin có kiểm soát.
* Policy rõ theo trusted frontend origins.

### Costs / Risks

* Preflight thêm request/latency.
* Misconfiguration dễ tạo security exposure hoặc false debugging signal.
* Browser-specific concern không bảo vệ non-browser clients.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CORS là browser policy, không phải API permission system.

### Middle

Cấu hình origins/methods/credentials và debug preflight.

### Senior

Đánh giá cookie, CSRF, proxy caching và origin trust together.

### Technical Lead / Architect

Chọn same-origin, BFF hay cross-origin architecture dựa trên security và deployment topology.

## 11. Key takeaway

* CORS không thay authentication hay authorization.
* Credentialed CORS phải dùng explicit trusted origins.
* Console “CORS error” có thể che một server failure khác phía sau.

# 10. Load testing open vs closed workload: coordinated omission và cách benchmark có thể che production tail latency

## 1. What is it?

Closed workload thường có số virtual users cố định: mỗi user gửi request tiếp theo sau khi request trước hoàn tất. Open workload tạo arrivals theo rate độc lập với response time.

```text
Closed:
request slow → user waits → fewer new requests generated

Open:
request slow → new arrivals still come
              → queue builds like real traffic spike
```

Coordinated omission xảy ra khi load generator giảm số request đúng lúc system chậm, từ đó bỏ sót latency mà users thực tế sẽ trải nghiệm.

## 2. Why does it exist?

Một benchmark có thể báo p99 = 300 ms nhưng production p99 = 8 s vì test tool ngừng phát traffic khi requests trước đang chậm. Hệ thống tự được “thưởng” bằng load thấp hơn lúc degraded.

Capacity testing cần mô hình arrival gần thực tế để thấy queueing và saturation.

## 3. How does it work?

Theo Little’s Law:

```text
Concurrency ≈ Throughput × Latency
```

Nếu arrival rate giữ nguyên mà latency tăng, concurrency tự tăng. Khi worker/thread/connection pool đạt giới hạn, queue tích lũy và tail latency tăng phi tuyến.

Closed model với fixed users có thể vô tình giới hạn concurrency và che overload knee.

## 4. Practical implementation

Thay vì chỉ test “200 virtual users”, định nghĩa workload:

```text
steady state: 500 requests/s
burst: 900 requests/s for 2 minutes
request mix:
  70% reads
  20% writes
  10% expensive search
```

Theo dõi cùng lúc:

* achieved arrival rate;
* p50/p95/p99;
* queue length;
* DB pool usage;
* CPU;
* rejection/timeout rate;
* dependency latency.

## 5. Real production scenario

Checkout service test với 300 concurrent users luôn xanh. Khi payment provider chậm từ 200 ms lên 2 s, production arrivals vẫn 400 RPS nên active requests tăng gần 10 lần, connection pool bão hòa và retries xuất hiện.

Closed test lại tự giảm effective RPS khi response chậm, nên không tái hiện incident.

## 6. Failure scenario & troubleshooting

**Symptom** → benchmark latency đẹp nhưng production overload ở RPS tương tự.

**Evidence** → test report chỉ nói virtual users, không ghi achieved request arrival rate theo thời gian.

**Hypothesis** → coordinated omission/closed-loop throttling.

**Diagnosis** → chart actual request starts per second và compare khi latency spike.

**Fix** → bổ sung open-arrival test, dependency latency injection và bounded retry behavior.

**Verification** → system phải thể hiện overload knee/rejection behavior giống production telemetry hơn.

## 7. Common mistakes

* Chỉ benchmark average latency.
* Tăng virtual users nhưng không biết arrival rate.
* Test dependency luôn nhanh hơn production.
* Không warm connection/cache/JIT một cách có chủ đích.
* Client generator trở thành bottleneck trước server.
* Retry trong load script làm traffic profile không rõ ràng.

## 8. Alternatives

Closed workload vẫn đúng cho systems có finite interactive sessions hoặc khi muốn đo concurrency-specific behavior. Trace replay hữu ích để tái tạo request mix; stress/soak/spike tests trả lời các câu hỏi khác nhau.

## 9. Trade-offs

### Advantages

* Open model phản ánh queueing dưới arrival rate độc lập.
* Dễ tìm capacity knee và overload behavior.

### Costs / Risks

* Dễ tạo load lớn ngoài dự kiến.
* Cần generator đủ mạnh.
* Mô hình traffic sai vẫn cho kết luận sai dù tool chính xác.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu virtual users và requests/second không phải cùng metric.

### Middle

Đo throughput, percentiles và resource saturation cùng nhau.

### Senior

Thiết kế open/closed workloads, fault injection và tránh coordinated omission.

### Technical Lead / Architect

Định nghĩa capacity model, overload policy và performance gates dựa trên production arrival patterns.

## 11. Key takeaway

* Load test phải mô hình hóa traffic arrival, không chỉ số virtual users.
* Closed-loop tests có thể che latency collapse khi hệ thống chậm.
* Tail latency chỉ có ý nghĩa khi throughput và saturation được đo cùng lúc.
