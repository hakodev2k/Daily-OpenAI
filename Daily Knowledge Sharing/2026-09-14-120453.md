# 1. C# `Span<T>` và `Memory<T>`: giảm allocation bằng cách làm việc trên vùng nhớ mà không copy dữ liệu

## 1. What is it?

`Span<T>` biểu diễn một vùng nhớ liên tục mà code có thể truy cập như một view, không cần tạo một array/string mới cho mỗi lát cắt. Nó có thể trỏ vào array, stack memory hoặc unmanaged memory. `ReadOnlySpan<T>` là phiên bản chỉ đọc.

`Memory<T>` và `ReadOnlyMemory<T>` mang ý tưởng tương tự nhưng có lifetime linh hoạt hơn, có thể được giữ trên heap và đi qua asynchronous boundary.

Mental model:

```text
byte[] buffer
+----+----+----+----+----+----+----+
| 10 | 11 | 12 | 13 | 14 | 15 | 16 |
+----+----+----+----+----+----+----+
          ^--------------^
             Span<byte>
             không copy
```

## 2. Why does it exist?

Nhiều parser, protocol handler và text-processing pipeline chỉ cần nhìn một phần dữ liệu. Nếu mỗi thao tác `Substring`, `ToArray`, `Split` hoặc slice đều tạo object mới, allocation rate và GC pressure tăng rất nhanh.

Điểm quan trọng không phải “Span luôn nhanh”, mà là nó cho phép **zero/low-allocation data access** khi profiling cho thấy copying/allocation nằm trên hot path.

## 3. How does it work?

`Span<T>` là `ref struct`. Runtime/compiler áp đặt restriction để reference tới vùng nhớ không sống lâu hơn vùng nhớ gốc. Vì thế `Span<T>` không thể được boxing, không thể là field của class thông thường và không thể sống xuyên qua `await`.

Ví dụ:

```csharp
ReadOnlySpan<char> input = "order:12345";
var separator = input.IndexOf(':');

ReadOnlySpan<char> prefix = input[..separator];
ReadOnlySpan<char> idText = input[(separator + 1)..];

if (prefix.SequenceEqual("order") &&
    int.TryParse(idText, out var id))
{
    Console.WriteLine(id);
}
```

Không có `Substring` nào bắt buộc phải tạo string mới.

## 4. Practical implementation

Một parser trước đây:

```csharp
public static (string Key, string Value) Parse(string input)
{
    var parts = input.Split(':', 2);
    return (parts[0], parts[1]);
}
```

Với request volume lớn, `Split` tạo array và string mới. Có thể chuyển thành parser chỉ đọc:

```csharp
public static bool TryParse(
    ReadOnlySpan<char> input,
    out ReadOnlySpan<char> key,
    out ReadOnlySpan<char> value)
{
    var index = input.IndexOf(':');
    if (index <= 0 || index == input.Length - 1)
    {
        key = default;
        value = default;
        return false;
    }

    key = input[..index];
    value = input[(index + 1)..];
    return true;
}
```

Nếu dữ liệu phải tồn tại sau method hoặc đi qua `await`, chuyển ownership rõ ràng sang `string`, array hoặc `Memory<T>`.

## 5. Real production scenario

Một service ingest log nhận hàng trăm nghìn records/phút. Profiling cho thấy CPU không nằm ở business logic mà ở GC và string allocation do `Split`, `Substring`, `ToArray`.

Sau khi thay parser bằng `ReadOnlySpan<char>`, allocation/request giảm đáng kể. Nhưng team chỉ tối ưu parser nóng nhất, không rewrite toàn bộ codebase thành low-level memory code.

## 6. Failure scenario & troubleshooting

**Symptom** → Gen0 collections nhiều, allocation rate cao, throughput giảm khi traffic tăng.

**Measure** → dùng `dotnet-counters`, `dotnet-trace`, profiler hoặc BenchmarkDotNet để đo allocated bytes/op.

**Hypothesis** → slicing/parsing đang copy dữ liệu quá nhiều.

**Test** → benchmark implementation hiện tại và phiên bản Span trên dữ liệu đại diện.

**Fix** → giữ view vào buffer khi lifetime cho phép; chỉ materialize tại ownership boundary.

**Verify** → so sánh allocation, CPU và p95/p99, không chỉ microbenchmark nanoseconds.

## 7. Common mistakes

- Dùng `Span<T>` ở mọi nơi dù code không nằm trên hot path.
- Cố giữ `Span<T>` qua `await` hoặc trong object sống lâu.
- Trả view vào pooled buffer sau khi buffer đã được trả về pool.
- Tối ưu allocation nhưng làm code khó đọc hơn rất nhiều mà không có benchmark.
- Nhầm zero-copy với zero-cost: bounds checks, parsing và encoding vẫn có chi phí.

## 8. Alternatives

- `string`/array bình thường: mặc định tốt nhất khi simplicity quan trọng hơn allocation.
- `ReadOnlyMemory<T>`: khi cần data slice sống qua async boundary.
- `ArrayPool<T>`: khi cần buffer lớn tái sử dụng với ownership rõ ràng.
- `SequenceReader<T>` / `ReadOnlySequence<T>`: phù hợp pipeline dữ liệu có nhiều segment.

## 9. Trade-offs

### Advantages

- Giảm copy và allocation trên hot path.
- Rất phù hợp parser, serialization, networking và protocol processing.
- Có thể giữ API type-safe hơn so với pointer arithmetic.

### Costs / Risks

- Lifetime/ownership phức tạp hơn.
- Debugging khó hơn code dùng immutable strings đơn giản.
- Có restriction do `ref struct`.
- Tối ưu sai chỗ có thể tăng complexity mà gần như không tạo business value.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slice không nhất thiết phải copy dữ liệu.

### Middle

Biết phân biệt `Span<T>` và `Memory<T>` theo lifetime, synchronous/async boundary.

### Senior

Dùng profiler/benchmark để xác định hot path, quản lý pooled-buffer ownership và tránh use-after-return logic bug.

### Technical Lead / Architect

Đặt performance budget và abstraction boundary để low-allocation code chỉ xuất hiện ở nơi đáng giá, không lan complexity khắp business layer.

## 11. Key takeaway

- `Span<T>` là view lên vùng nhớ, không phải “array nhanh hơn”.
- Giá trị chính là giảm copy/allocation khi parsing và slicing.
- Lifetime/ownership correctness quan trọng hơn vài microseconds tối ưu được.

# 2. ASP.NET Core Output Caching: cache response ở server theo policy thay vì nhầm lẫn với HTTP Response Caching

## 1. What is it?

Output Caching lưu response do ASP.NET Core tạo ra và có thể trả lại response đó cho request tương lai nếu request khớp cache policy. Đây là **server-controlled cache**.

Nó khác Response Caching middleware, vốn chủ yếu tuân theo HTTP cache semantics/header và có thể phụ thuộc client/proxy behavior.

```text
Request
   |
   v
Output Cache lookup
   | hit                 | miss
   v                     v
cached response        Endpoint
                         |
                         v
                     cache store
```

## 2. Why does it exist?

Nhiều endpoint đọc dữ liệu giống nhau liên tục nhưng không cần thực thi controller, database query và serialization mỗi lần. Cache tại server có thể giảm latency và backend load.

Điểm khó là cache key và invalidation. Nếu key thiếu dimension quan trọng như tenant, locale hoặc authorization context, cache có thể trở thành **data leakage bug** chứ không chỉ performance bug.

## 3. How does it work?

ASP.NET Core cho phép khai báo policy và vary theo query/header/value. Cache middleware quyết định request nào có thể lookup/store.

Ví dụ cấu hình cơ bản:

```csharp
builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("catalog", policy =>
        policy
            .Expire(TimeSpan.FromSeconds(30))
            .SetVaryByQuery("page", "category"));
});

var app = builder.Build();
app.UseOutputCache();

app.MapGet("/catalog", GetCatalog)
   .CacheOutput("catalog");
```

## 4. Practical implementation

Không cache authenticated/personalized endpoint một cách mù quáng:

```text
GET /api/profile
Authorization: Bearer <user A>
```

Nếu cache key chỉ dựa vào path, user B có thể nhận response của user A.

An toàn hơn là chỉ cache public data, hoặc thiết kế policy vary đúng tenant/user dimension nếu use case thật sự yêu cầu. Với mutable resources, dùng cache tags và explicit eviction khi write path thay đổi dữ liệu.

Pseudo-flow:

```text
Update product
  -> commit DB
  -> evict tag product:<id>
  -> evict tag catalog:<category>
```

## 5. Real production scenario

Catalog API có 90% request đọc cùng top categories. Database không quá chậm nhưng serialization + query lặp tạo load lớn. Output cache 15–30 giây giảm request xuống database mạnh.

Sau đó bug xuất hiện khi team thêm `currency` query parameter nhưng quên vary cache theo currency. Người dùng EUR nhận giá USD đã cache. Root cause nằm ở cache key contract.

## 6. Failure scenario & troubleshooting

**Symptom** → response “đúng với người khác nhưng sai với tôi”, dữ liệu cũ không nhất quán hoặc hit ratio thấp.

**Measure** → log cache hit/miss, key dimensions, endpoint latency và backend query count.

**Hypothesis** → cache key thiếu dimension hoặc cardinality quá cao.

**Test** → gửi matrix request theo tenant, locale, query, auth state và kiểm tra isolation.

**Fix** → sửa vary policy, giảm cache scope hoặc loại endpoint khỏi cache.

**Verify** → integration test cho isolation + cache invalidation, không chỉ benchmark hit path.

## 7. Common mistakes

- Cache endpoint personalized mà không xét authorization boundary.
- Vary theo mọi header làm cardinality nổ.
- TTL rất dài để “tăng hit rate” nhưng không có invalidation strategy.
- Chỉ kiểm tra latency mà không test correctness sau update.
- Nhầm Output Cache với browser/CDN caching.

## 8. Alternatives

- `IMemoryCache`: cache object/application data trong process.
- Distributed cache/Redis: chia sẻ cached data giữa instances.
- CDN: cache public HTTP content gần client.
- Database/query optimization: nếu root cause là query/index, cache không nên che vấn đề mãi.

## 9. Trade-offs

### Advantages

- Giảm endpoint execution cost trực tiếp.
- Policy tập trung và dễ áp dụng trên endpoints.
- Tốt cho public/read-heavy responses.

### Costs / Risks

- Invalidation và identity isolation phức tạp.
- Stale data là behavior có chủ ý cần được chấp nhận.
- Cache stampede/hot key vẫn cần cân nhắc ở scale lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache là đổi freshness lấy latency/backend load.

### Middle

Biết cấu hình TTL, vary và phân biệt output/data/CDN cache.

### Senior

Thiết kế cache key theo security boundary, đo hit ratio và kiểm thử invalidation.

### Technical Lead / Architect

Xác định cache consistency model theo domain, nơi nào được stale bao lâu và ownership của invalidation nằm ở write path nào.

## 11. Key takeaway

- Cache correctness bắt đầu từ cache key, không phải TTL.
- Public, deterministic, read-heavy endpoint là candidate tốt nhất.
- Mọi dimension ảnh hưởng response phải được xem xét trong cache policy.

# 3. EF Core `ExecuteUpdate` / `ExecuteDelete`: bulk mutation hiệu quả nhưng có thể làm Change Tracker giữ state lỗi thời

## 1. What is it?

`ExecuteUpdate` và `ExecuteDelete` cho phép EF Core gửi `UPDATE`/`DELETE` trực tiếp xuống database từ LINQ predicate mà không load từng entity vào memory và không đi qua normal change tracking pipeline.

```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Expired)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Archived), ct);
```

Tương đương ý tưởng:

```sql
UPDATE Orders
SET Status = 'Archived'
WHERE Status = 'Expired';
```

## 2. Why does it exist?

Pattern load N entities → sửa từng object → `SaveChanges` có overhead materialization, tracking và có thể phát nhiều statements. Với bulk operation, database engine nên thực hiện set-based mutation.

Nhưng optimization này thay đổi semantics: Change Tracker không tự đồng bộ lại những entity đã được track trước đó.

## 3. How does it work?

`ExecuteUpdate/Delete` execute ngay, không chờ `SaveChanges`. Nó không sử dụng tracked entity state để tính mutation.

Ví dụ nguy hiểm:

```csharp
var order = await db.Orders.SingleAsync(x => x.Id == id, ct);

await db.Orders
    .Where(x => x.Id == id)
    .ExecuteUpdateAsync(s => s.SetProperty(x => x.Total, 500m), ct);

// order.Total vẫn có thể là giá trị cũ trong memory
order.Note = "reviewed";
await db.SaveChangesAsync(ct);
```

Tùy mapping/concurrency behavior, tracked state cũ có thể tạo update ngoài ý muốn hoặc đơn giản làm application logic đọc dữ liệu stale.

## 4. Practical implementation

Dùng bulk mutation trong unit-of-work nơi không trộn tracked entities cùng rows, hoặc clear/reload tracker có chủ đích:

```csharp
var affected = await db.Sessions
    .Where(x => x.ExpiresAt < now && x.RevokedAt == null)
    .ExecuteUpdateAsync(s => s
        .SetProperty(x => x.RevokedAt, now), ct);

logger.LogInformation("Revoked {Count} sessions", affected);
```

Nếu business invariant cần concurrency check, thêm predicate:

```csharp
var affected = await db.Accounts
    .Where(x => x.Id == id && x.Version == expectedVersion)
    .ExecuteUpdateAsync(s => s
        .SetProperty(x => x.Balance, newBalance)
        .SetProperty(x => x.Version, expectedVersion + 1), ct);

if (affected == 0)
    throw new ConcurrencyException();
```

## 5. Real production scenario

Background job cần expire 500k records. Implementation cũ load batch entities rồi `SaveChanges`, gây memory pressure và round-trips lớn. Set-based `ExecuteUpdate` giảm thời gian đáng kể.

Sau đó một admin workflow reuse cùng `DbContext`, đã track vài records trước bulk update. UI hiển thị state cũ. Fix không phải “gọi SaveChanges lần nữa” mà là làm rõ tracking boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → database có giá trị mới nhưng object đang track vẫn cũ, hoặc update sau đó ghi đè dữ liệu khó giải thích.

**Measure** → inspect generated SQL, `ChangeTracker.DebugView`, transaction boundaries và entity states.

**Hypothesis** → bulk SQL đã bypass tracker.

**Test** → reproduce trong cùng `DbContext`: query entity → bulk update → đọc tracked entity.

**Fix** → tách context/unit-of-work, reload entity hoặc clear tracker khi semantics cho phép.

**Verify** → test cả database state lẫn in-memory state sau mutation.

## 7. Common mistakes

- Nghĩ `ExecuteUpdate` giống thay property rồi `SaveChanges`.
- Trộn bulk update với nhiều tracked entities trong context sống lâu.
- Quên transaction khi nhiều bulk statements phải atomic.
- Không kiểm tra `affected rows` cho optimistic concurrency.
- Dùng bulk API để bypass domain invariants nằm trong aggregate logic mà không thiết kế lại guard.

## 8. Alternatives

- Normal tracked `SaveChanges`: tốt cho aggregate logic và small mutation set.
- Raw SQL/stored procedure: khi cần SQL-specific feature hoặc performance control sâu hơn.
- Dedicated bulk library: khi cần insert/update semantics lớn hơn capability built-in.

## 9. Trade-offs

### Advantages

- Set-based, ít round-trips và không cần materialize entities.
- Rất phù hợp maintenance/background operations.
- LINQ vẫn giữ type-safe predicate/property mapping.

### Costs / Risks

- Bypass Change Tracker.
- Domain event/audit logic gắn vào entity/SaveChanges có thể không chạy.
- Concurrency/invariant cần được encode rõ trong predicate/transaction.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu bulk SQL khác entity-by-entity update.

### Middle

Biết lúc nào nên dùng `ExecuteUpdate/Delete` và theo dõi affected rows.

### Senior

Thiết kế tracking/transaction/concurrency boundary để bulk mutation không phá correctness.

### Technical Lead / Architect

Quyết định invariant nào phải nằm ở domain service/database constraint và không phụ thuộc duy nhất vào tracked entity lifecycle.

## 11. Key takeaway

- `ExecuteUpdate/Delete` là set-based database operation, không phải shortcut của `SaveChanges`.
- Performance tốt hơn đi kèm semantics khác.
- Tránh trộn tracked state và direct bulk mutation mà không có ownership rõ ràng.

# 4. SQL Server parameter sniffing và Parameter Sensitive Plan: một execution plan tốt cho giá trị này có thể rất tệ cho giá trị khác

## 1. What is it?

Khi SQL Server compile parameterized query/stored procedure, optimizer có thể sử dụng parameter value tại thời điểm compilation để chọn execution plan. Đây thường là optimization tốt: optimizer biết selectivity thực tế.

Vấn đề xuất hiện khi distribution skew lớn. Plan tối ưu cho parameter rất selective có thể tệ cho parameter trả về phần lớn bảng.

```text
Tenant A -> 12 rows
Tenant B -> 8,000,000 rows

cùng query:
WHERE TenantId = @tenantId
```

## 2. Why does it exist?

Compile plan có chi phí. Plan cache cho phép reuse. Nhưng reuse giả định một plan đủ tốt cho nhiều parameter values. Khi assumption này sai, latency có thể thay đổi hàng trăm lần tùy parameter.

Vì thế “query đôi lúc nhanh, đôi lúc chậm” không phải lúc nào cũng do network/database load; có thể do plan selection.

## 3. How does it work?

Optimizer dùng statistics để estimate cardinality. Parameter value lúc compile ảnh hưởng estimate và operator choice:

```text
ít rows -> Index Seek + Nested Loops
nhiều rows -> Scan + Hash Join có thể hợp lý hơn
```

Các SQL Server versions mới có Parameter Sensitive Plan optimization cho một số workload, cho phép nhiều plan variants theo cardinality ranges thay vì một plan duy nhất.

## 4. Practical implementation

Bắt đầu bằng đo plan và distribution, không thêm hint theo cảm tính.

```sql
SELECT TenantId, COUNT(*) AS RowCount
FROM Orders
GROUP BY TenantId
ORDER BY RowCount DESC;
```

Sau đó kiểm tra actual execution plan, Query Store, estimated vs actual rows và plan history.

Mitigation có thể gồm:

- sửa index/statistics,
- cho engine dùng PSP khi đủ điều kiện,
- `OPTION (RECOMPILE)` cho query hiếm nhưng parameter-sensitive mạnh,
- tách query path khi business shapes thực sự khác nhau,
- `OPTIMIZE FOR` chỉ khi hiểu rõ trade-off.

## 5. Real production scenario

SaaS multi-tenant có 95% tenant nhỏ, 5 tenant cực lớn. Procedure report compile lần đầu bằng tenant nhỏ nên dùng nested loops. Khi tenant lớn chạy report, query đọc hàng triệu rows và timeout.

Restart database “fix” tạm thời vì plan được compile lại, rồi lỗi quay lại khi first caller khác. Đây là dấu hiệu kinh điển của plan sensitivity, không phải giải pháp restart.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng SQL text nhưng runtime variance cực lớn theo parameter hoặc sau plan eviction/recompile.

**Measure** → Query Store, actual plans, logical reads, duration, estimated/actual rows.

**Hypothesis** → cardinality skew + cached plan không phù hợp.

**Test** → chạy representative values riêng biệt, xem operator/reads.

**Fix** → ưu tiên statistics/index/query shape; chỉ dùng hints/recompile khi có bằng chứng.

**Verify** → test cả small/medium/large parameter distributions và theo dõi production Query Store.

## 7. Common mistakes

- Dùng `OPTION (RECOMPILE)` cho mọi query chậm.
- Xóa plan cache toàn server như “fix”.
- Chỉ test bằng một tenant/sample data nhỏ.
- Nhìn duration mà không nhìn logical reads/cardinality estimate.
- Ép một index vì plan hiện tại xấu mà không hiểu distribution.

## 8. Alternatives

- Dynamic SQL parameterized đúng cách cho distinct query shapes.
- Query splitting theo workload class.
- Pre-aggregation/materialized reporting model cho report rất lớn.
- Separate analytics store nếu OLTP query shape không còn phù hợp.

## 9. Trade-offs

### Advantages của plan reuse

- Giảm compilation CPU.
- Stable cho workload có distribution tương đối đều.

### Costs / Risks

- Data skew có thể làm một plan không phù hợp cho mọi values.
- Hints dễ trở thành technical debt khi data distribution đổi.
- Recompile đổi CPU compilation lấy execution stability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết execution plan phụ thuộc statistics và cardinality.

### Middle

Biết đọc actual plan, logical reads và phát hiện estimated/actual mismatch.

### Senior

Chẩn đoán plan cache, data skew, Query Store và parameter sensitivity thay vì restart/clear cache.

### Technical Lead / Architect

Thiết kế tenant/data partitioning và reporting architecture dựa trên distribution thực tế, không giả định mọi tenant giống nhau.

## 11. Key takeaway

- Parameter sniffing tự nó không phải bug; plan reuse gặp skew mới thành vấn đề.
- Luôn test representative parameter distributions.
- Query Store + actual plans đáng tin hơn “restart thấy nhanh lại”.

# 5. MongoDB schema validation: schemaless không có nghĩa là bỏ data contract và invariant ở database boundary

## 1. What is it?

MongoDB cho phép documents trong cùng collection có shape linh hoạt, nhưng vẫn hỗ trợ schema validation bằng validator như `$jsonSchema` để từ chối hoặc cảnh báo documents vi phạm contract.

Ví dụ:

```javascript
{
  $jsonSchema: {
    bsonType: "object",
    required: ["tenantId", "status", "createdAt"],
    properties: {
      tenantId: { bsonType: "string" },
      status: { enum: ["pending", "paid", "cancelled"] },
      createdAt: { bsonType: "date" }
    }
  }
}
```

## 2. Why does it exist?

Flexible schema giúp evolution nhanh, nhưng production systems vẫn có invariants. Nếu mọi producer tự quyết định shape, một service bug hoặc migration dở dang có thể tạo documents mà code khác không thể đọc an toàn.

Database validation là lớp defense-in-depth, đặc biệt khi nhiều applications/scripts ghi vào cùng collection.

## 3. How does it work?

Validator chạy khi insert/update. Validation level/action quyết định mức độ áp dụng và behavior khi vi phạm.

Mental model:

```text
API validation
   |
Domain validation
   |
MongoDB validator  <- cuối boundary chống invalid persisted shape
   |
Storage
```

Các lớp không thay thế nhau. API validation cho UX; domain rules cho business semantics; DB validation bảo vệ persisted contract.

## 4. Practical implementation

Không cố nhét mọi business rule vào JSON Schema. Tập trung invariant dữ liệu cơ bản:

- required field,
- BSON type,
- enum/range,
- nested object shape,
- field combinations đơn giản khi hỗ trợ.

Rollout an toàn với legacy data thường theo flow:

```text
1. Audit invalid existing documents
2. Deploy readers compatible với old/new shape
3. Backfill/migrate
4. Enable validation ở mode phù hợp
5. Tighten enforcement
6. Remove compatibility code
```

## 5. Real production scenario

Collection `payments` ban đầu lưu `amount` là number. Một import script mới ghi `"100.00"` dạng string cho 2% records. API chính vẫn chạy cho tới khi aggregation `$sum` hoặc downstream deserializer gặp dữ liệu lẫn type.

Validator ngăn producer mới tiếp tục làm bẩn dữ liệu và giúp lỗi xuất hiện ngay tại write boundary, nơi root cause dễ truy ra hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → query/aggregation fail cho một số records, deserialization exception hoặc index/query behavior bất thường.

**Measure** → query documents theo `$type`, sample invalid shapes và theo dõi write errors.

**Hypothesis** → collection drift vì nhiều writer hoặc migration không hoàn tất.

**Test** → chạy audit query với expected schema.

**Fix** → repair data + enforce validator + fix offending writer.

**Verify** → CI/integration tests ghi invalid documents phải fail như kỳ vọng.

## 7. Common mistakes

- Hiểu “document database” thành “không cần schema”.
- Enforce validator trước khi audit legacy data.
- Copy toàn bộ C# model thành DB schema mà không xét backward compatibility.
- Đặt business workflow phức tạp vào validator khó maintain.
- Cho nhiều services ghi chung collection mà không có ownership contract.

## 8. Alternatives

- Application-only validation: đơn giản nhưng yếu khi có nhiều writers.
- Separate collections theo schema version/use case.
- Event schema registry cho event-driven boundary.
- Relational DB constraints nếu domain có quan hệ/invariant phù hợp relational model hơn.

## 9. Trade-offs

### Advantages

- Chặn invalid persisted shape gần data boundary.
- Giảm silent schema drift.
- Hữu ích khi scripts/integration cùng ghi dữ liệu.

### Costs / Risks

- Schema evolution cần rollout có kế hoạch.
- Validation không thay thế domain logic.
- Strict rules quá sớm có thể làm migration/deployment khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu MongoDB linh hoạt schema nhưng vẫn có shape kỳ vọng.

### Middle

Biết dùng validator cho required/type/enum và audit existing data.

### Senior

Thiết kế backward-compatible schema migration qua nhiều application versions.

### Technical Lead / Architect

Đặt data ownership, writer boundaries và schema-evolution policy cho toàn hệ thống.

## 11. Key takeaway

- Schemaless là schema flexibility, không phải absence of contract.
- Validation nên bảo vệ persisted invariants cơ bản.
- Evolution an toàn cần reader compatibility + migration + enforcement theo giai đoạn.

# 6. Git `bisect`: biến việc tìm commit gây regression từ dò tuyến tính thành binary search có thể tự động hóa

## 1. What is it?

`git bisect` tìm commit đầu tiên gây bug bằng binary search trên commit history. Bạn đánh dấu một commit “good” và một commit “bad”; Git checkout điểm giữa để bạn test, rồi thu hẹp phạm vi.

```text
good ----------------------------- bad
  |                                 |
  +-------------- test ------------+
                  |
             good or bad?
                  |
          phạm vi còn một nửa
```

## 2. Why does it exist?

Nếu có 1,024 commits giữa phiên bản tốt và xấu, kiểm tra tuyến tính có thể cần hàng trăm lần. Binary search lý tưởng chỉ khoảng 10 bước.

Giá trị lớn nhất xuất hiện khi regression có automated test/reproduction command đáng tin cậy.

## 3. How does it work?

Flow thủ công:

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.4.0

# chạy test trên commit Git checkout
# nếu lỗi:
git bisect bad
# nếu không lỗi:
git bisect good

# khi xong
git bisect reset
```

Có thể tự động:

```bash
git bisect run dotnet test tests/Regression.Tests/Regression.Tests.csproj
```

Exit code 0 = good, non-zero thường = bad; script có thể dùng exit code 125 để skip commit không test được.

## 4. Practical implementation

Trước khi bisect, tạo reproduction nhỏ và deterministic:

```csharp
[Fact]
public async Task Export_should_preserve_unicode_filename()
{
    var result = await ExportAsync("Báo-cáo-2026");
    Assert.Equal("Báo-cáo-2026.docx", result.FileName);
}
```

Sau đó chạy `git bisect run` với test này. Khi tìm được first bad commit, đọc diff và context; **first bad commit là evidence mạnh, không tự động chứng minh toàn bộ root cause**.

## 5. Real production scenario

Sau hai tháng development, memory usage của worker tăng từ 300 MB lên 2 GB. Không ai nhớ commit nào gây ra. Team có benchmark script tạo workload và fail nếu retained memory vượt threshold.

Bisect tự động thu hẹp hàng trăm commits xuống một commit thay đổi caching ownership. Investigation chuyển từ “đọc mọi PR” thành một diff nhỏ có bằng chứng.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect trả kết quả không ổn định hoặc chỉ ra commit vô lý.

**Measure** → rerun test nhiều lần trên same commit.

**Hypothesis** → flaky reproduction, environment drift hoặc bad/good boundary sai.

**Test** → xác nhận known-good thật sự pass và known-bad thật sự fail.

**Fix** → làm test deterministic, pin dependencies/environment, dùng `bisect skip` khi commit không build được.

**Verify** → checkout parent của first bad phải good, first bad phải reproduce bug.

## 7. Common mistakes

- Bisect khi chưa có deterministic symptom.
- Chọn “good” commit mà thực ra bug đã tồn tại.
- Dùng build failure như business regression mà không phân biệt.
- Kết luận author của commit là “nguyên nhân” thay vì phân tích system interaction.
- Quên `git bisect reset`.

## 8. Alternatives

- `git log -S` / `-G`: khi biết symbol/text thay đổi.
- `git blame`: khi biết chính xác dòng code hiện tại.
- PR/commit search: khi có issue keyword rõ.
- Profiler/tracing: khi chưa biết regression bắt đầu từ commit nào hoặc symptom không deterministic.

## 9. Trade-offs

### Advantages

- Thu hẹp history theo logarithmic search.
- Automation rất mạnh nếu có test command.
- Giảm confirmation bias khi investigation.

### Costs / Risks

- History có merge/cherry-pick phức tạp làm interpretation khó hơn.
- Old commits có thể không build với current environment.
- Flaky tests phá binary-search assumption.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết checkout commit và đánh dấu good/bad.

### Middle

Biết viết regression test rồi dùng `bisect run`.

### Senior

Xử lý flaky/environment/merge-history edge cases và xác minh causal chain sau khi tìm commit.

### Technical Lead / Architect

Đầu tư reproducible builds/tests để historical debugging trở thành workflow có thể tự động hóa thay vì archaeology thủ công.

## 11. Key takeaway

- `git bisect` hữu ích nhất khi có executable definition của “good/bad”.
- Nó tìm boundary commit, không thay thế root-cause analysis.
- Regression test tốt vừa giúp bisect vừa ngăn bug quay lại.

# 7. Azure App Configuration Feature Management: tách deployment khỏi release nhưng phải quản lý targeting và cleanup như production code

## 1. What is it?

Feature flag cho phép code được deploy nhưng behavior chỉ bật cho một nhóm user/environment/time window nhất định. Azure App Configuration cung cấp centralized configuration/feature management để applications có thể đọc và đánh giá flags.

```text
Deploy code once
      |
      v
Feature flag OFF -> old behavior
      |
      +--> 5% users
      +--> internal users
      +--> one tenant
      +--> 100% when proven safe
```

## 2. Why does it exist?

Deployment và release là hai risk events khác nhau. Nếu mọi code deployment lập tức bật behavior cho 100% traffic, rollback là công cụ duy nhất khi lỗi xảy ra.

Feature flags cho phép progressive delivery, operational kill switch và experimentation. Nhưng flag cũng tạo thêm runtime branch/state cần quản lý.

## 3. How does it work?

Application lấy flag definitions từ configuration provider và evaluate filter/targeting policy. Quyết định thường cần ổn định cho cùng user trong một session/cohort, nếu không UX có thể flip giữa variants.

Pseudo-code:

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
{
    return await newCheckout.ExecuteAsync(ct);
}

return await legacyCheckout.ExecuteAsync(ct);
```

## 4. Practical implementation

Mỗi flag nên có metadata/ownership ngoài tên:

```text
Name: NewCheckout
Owner: Payments Team
Purpose: progressive rollout
Created: 2026-09-14
Target removal: after rollout + 2 weeks
Failure default: OFF
Metrics: checkout success, p95, payment errors
```

Rollout:

```text
internal -> 1% -> 5% -> 25% -> 50% -> 100%
            |      |      |       |
         observe business + technical SLOs
```

Đừng chỉ monitor HTTP 500; feature có thể “technically successful” nhưng làm conversion giảm.

## 5. Real production scenario

Checkout rewrite đã deploy vào production nhưng chỉ enable cho employees. Sau đó 5% customers được bật. Error rate bình thường nhưng payment authorization decline tăng ở một payment provider.

Team tắt flag trong vài phút mà không rollback unrelated code vừa deploy. Sau fix, rollout tiếp tục theo cohort.

## 6. Failure scenario & troubleshooting

**Symptom** → behavior khác nhau khó reproduce giữa users/instances.

**Measure** → log evaluated flag + variant + user/tenant key vào structured telemetry, tránh log sensitive raw identity nếu không cần.

**Hypothesis** → targeting/context khác nhau hoặc config refresh không đồng bộ.

**Test** → reproduce với cùng targeting context và inspect flag state/version.

**Fix** → chuẩn hóa evaluation context, cache/refresh semantics và default behavior.

**Verify** → contract/integration tests cho OFF, ON và representative targeting variants.

## 7. Common mistakes

- Flag tồn tại vĩnh viễn sau rollout.
- Nested flags tạo combinatorial state explosion.
- Dùng flag để che incompatible database migration.
- Không có owner/removal date.
- Không log variant nên production incident không biết request đi path nào.
- Kill switch phụ thuộc chính dependency đang bị outage mà nó cần tắt.

## 8. Alternatives

- Environment config: hợp với static per-environment behavior.
- Blue/green deployment: traffic split theo deployment version.
- Canary at ingress/service mesh: phù hợp rollout binary/service version.
- A/B experimentation platform: khi statistical experiment là mục tiêu chính.

## 9. Trade-offs

### Advantages

- Giảm blast radius khi release.
- Tách deployment cadence khỏi user exposure.
- Cho phép targeted rollout/kill switch.

### Costs / Risks

- Runtime branches tăng test matrix.
- Stale flags tạo technical debt.
- Central config trở thành operational dependency cần resilience.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu flag là runtime decision, không phải comment bật/tắt code.

### Middle

Biết implement ON/OFF path và test cả hai.

### Senior

Thiết kế targeting, telemetry, fallback, config refresh và cleanup lifecycle.

### Technical Lead / Architect

Đặt governance: naming, owner, expiry, rollout gates, audit và maximum flag lifetime.

## 11. Key takeaway

- Feature flags giảm release blast radius nhưng tăng state-space complexity.
- Mỗi flag cần owner, metric và removal plan.
- Progressive rollout chỉ có giá trị nếu telemetry đủ tốt để quyết định tiếp tục hay dừng.

# 8. Docker multi-stage build và non-root runtime: giảm attack surface, image size và khoảng cách giữa build environment với production runtime

## 1. What is it?

Multi-stage Docker build dùng nhiều `FROM` stages. Build toolchain nằm ở build stage; runtime image chỉ copy artifact cần chạy.

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
USER app
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

## 2. Why does it exist?

Nếu production image chứa SDK, source tree, compiler, package caches và shell tooling không cần thiết, image lớn hơn và attack surface tăng. Root runtime còn làm container compromise có hậu quả lớn hơn tùy host/runtime controls.

Mục tiêu là principle of least privilege + minimal runtime artifact.

## 3. How does it work?

Mỗi stage có filesystem riêng. `COPY --from=build` chỉ mang output cần thiết sang runtime image.

Security boundary cần mental model đúng:

```text
Container != VM security boundary tuyệt đối

App process privilege
 + filesystem permissions
 + Linux capabilities
 + container runtime
 + host/kernel
```

`USER app` là một lớp hardening, không biến image thành “an toàn tuyệt đối”.

## 4. Practical implementation

Ngoài multi-stage + non-root:

- pin base-image strategy theo policy,
- không copy secrets vào image layer,
- `.dockerignore` source artifacts không cần thiết,
- read-only filesystem nếu app cho phép,
- mount writable volume chỉ nơi cần,
- expose/bind port phù hợp non-root,
- scan image/SBOM trong CI,
- rebuild khi base image có security update.

Đừng dùng:

```dockerfile
COPY . .
RUN echo "$PROD_SECRET" > /app/secret.txt
```

Secrets trong build layer/history có thể bị lộ ngay cả khi file bị delete ở layer sau.

## 5. Real production scenario

Một API image 2+ GB chứa full SDK, npm cache và source. CI/CD pull/push chậm; vulnerability scanner báo hàng trăm packages mà runtime không dùng.

Multi-stage build đưa image về runtime-only artifact. Chạy non-root lại phát hiện application đang ghi log/temp vào `/app`, vốn trước đây chỉ hoạt động vì root. Fix permission làm ownership requirement rõ hơn thay vì “chmod 777”.

## 6. Failure scenario & troubleshooting

**Symptom** → container chạy local/root nhưng fail khi non-root với `Permission denied` hoặc bind port/file error.

**Measure** → inspect UID/GID, mounted volume ownership, working directories và filesystem writes.

**Hypothesis** → application ngầm phụ thuộc root-owned path.

**Test** → chạy image với same user/security settings như production.

**Fix** → cấp quyền tối thiểu cho exact directories hoặc thay writable path.

**Verify** → integration/startup test image với production-equivalent security context.

## 7. Common mistakes

- Multi-stage nhưng cuối cùng vẫn dùng SDK image làm runtime.
- Copy toàn bộ repo sang final image.
- Chạy root vì “container đã isolate rồi”.
- `chmod -R 777` để hết permission error.
- Bake secrets vào `ARG`/layers.
- Dùng `latest` tùy ý và không có patch/rebuild policy.

## 8. Alternatives

- Distroless/minimal images: attack surface nhỏ hơn nhưng debugging khó hơn.
- Native AOT/single-file: có thể giảm runtime footprint cho workload phù hợp.
- Buildpacks: chuẩn hóa build pipeline nếu team không muốn maintain Dockerfile chi tiết.

## 9. Trade-offs

### Advantages

- Image nhỏ hơn, pull/deploy nhanh hơn.
- Ít tooling/packages không cần thiết trong runtime.
- Least-privilege runtime rõ ràng hơn.

### Costs / Risks

- Debug production container khó hơn nếu image quá tối giản.
- File permissions/diagnostics cần design trước.
- Base-image patching vẫn là ongoing responsibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết phân biệt SDK build image và runtime image.

### Middle

Viết multi-stage Dockerfile, `.dockerignore`, health/startup config hợp lý.

### Senior

Hardening non-root, filesystem, secret handling, image scanning và reproducible builds.

### Technical Lead / Architect

Thiết lập golden image/pipeline policy, provenance/SBOM và patch SLA thay vì mỗi repo tự quyết định security baseline.

## 11. Key takeaway

- Final image chỉ nên chứa thứ cần để chạy.
- Non-root giúp phát hiện hidden privilege assumptions và giảm blast radius.
- Container security là nhiều lớp; Dockerfile chỉ là một lớp.

# 9. TypeScript structural typing và excess property checks: type-compatible không đồng nghĩa domain-safe

## 1. What is it?

TypeScript chủ yếu dùng **structural typing**: hai values compatible nếu shape cần thiết tương thích, không cần nominal inheritance/name giống nhau.

```ts
type User = { id: string; name: string };

const payload = {
  id: "u1",
  name: "Ha",
  isAdmin: true
};

const user: User = payload; // thường hợp lệ structurally
```

`user` có type `User`, nhưng runtime object vẫn có `isAdmin`.

## 2. Why does it exist?

JavaScript ecosystem thiên về duck typing và composition. Structural typing làm interop ergonomic, nhưng developer dễ hiểu nhầm compile-time type như runtime sanitizer/security boundary.

TypeScript types bị erase khi build. API payload từ network vẫn là untrusted runtime data.

## 3. How does it work?

Excess property checks mạnh hơn với object literal trực tiếp:

```ts
const user: User = {
  id: "u1",
  name: "Ha",
  isAdmin: true // compiler có thể báo excess property
};
```

Nhưng qua intermediate variable, structural assignability có thể chấp nhận object có thêm fields.

Điều này không phải loophole bảo mật; nó phản ánh mục tiêu của type system. Runtime validation là responsibility khác.

## 4. Practical implementation

Ở trust boundary, parse/validate dữ liệu thật sự:

```ts
type CreateUserInput = {
  name: string;
  email: string;
};

function parseCreateUser(value: unknown): CreateUserInput {
  if (!value || typeof value !== "object") {
    throw new Error("Invalid payload");
  }

  const v = value as Record<string, unknown>;

  if (typeof v.name !== "string" || typeof v.email !== "string") {
    throw new Error("Invalid payload");
  }

  return { name: v.name, email: v.email };
}
```

Trong production, schema-validation libraries có thể giúp, nhưng principle vẫn là: `unknown` ở boundary → validate → trusted domain type.

## 5. Real production scenario

Frontend nhận JSON rồi dùng `as UserResponse`. Backend đổi field nullable; TypeScript compile vẫn xanh vì assertion ép type. Runtime sau đó fail ở `.toLowerCase()`.

Root cause không phải TypeScript “sai”, mà team dùng type assertion như runtime validation.

## 6. Failure scenario & troubleshooting

**Symptom** → production `undefined is not a function/property` dù TypeScript build không báo lỗi.

**Measure** → inspect raw network payload và nơi dùng `as`/non-null assertion `!`.

**Hypothesis** → compile-time contract lệch runtime data.

**Test** → feed malformed/old/new payload vào parser boundary.

**Fix** → validate/parse tại boundary, derive internal type từ validated value.

**Verify** → contract tests với backend schema + negative payload tests.

## 7. Common mistakes

- `JSON.parse(...) as MyType` rồi tin dữ liệu đã validate.
- Dùng `any` để “sửa” compiler errors.
- Nhầm excess property check với runtime field stripping.
- Reuse database entity/interface trực tiếp cho API/UI input.
- Dùng optional `?` cho mọi field thay vì model state chính xác.

## 8. Alternatives

- Runtime schema validation libraries.
- Generated API clients/types từ OpenAPI/schema.
- Branded/opaque types để thêm nominal semantics cho IDs/unit values.
- Discriminated unions để model finite states.

## 9. Trade-offs

### Advantages của structural typing

- Composition/interoperability rất thuận tiện.
- Ít boilerplate hierarchy.
- Phù hợp JavaScript object model.

### Costs / Risks

- Semantic distinction có thể bị mất nếu shapes giống nhau.
- Compile-time safety dừng tại runtime boundary.
- Type assertions dễ che contract drift.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu TypeScript type không tồn tại như validator ở runtime.

### Middle

Dùng `unknown` + narrowing thay vì `any` ở external boundary.

### Senior

Thiết kế DTO/domain types, runtime validation và generated contracts để giảm drift.

### Technical Lead / Architect

Xác định schema source-of-truth và CI contract checks giữa frontend/backend thay vì tin rằng shared interface tự đảm bảo compatibility.

## 11. Key takeaway

- Structural typing kiểm tra shape ở compile time, không sanitize runtime object.
- `as` là assertion cho compiler, không phải validation.
- External data nên bắt đầu là `unknown` cho tới khi được parse/validate.

# 10. RAG evaluation: tách retrieval quality khỏi answer quality để biết hệ thống AI sai ở tầng nào

## 1. What is it?

Retrieval-Augmented Generation (RAG) thường có ít nhất hai hệ thống con:

```text
User question
    |
    v
Retriever ----------> documents/chunks
    |
    v
Prompt construction
    |
    v
LLM ----------> answer
```

Evaluation tốt không chỉ hỏi “câu trả lời có đúng không?” mà phải tách:

- retrieval có lấy đúng evidence không,
- evidence có đủ không,
- answer có grounded vào evidence không,
- final answer có giải quyết user task không.

## 2. Why does it exist?

Nếu answer sai, team cần biết sửa embedding/index/query expansion, chunking/ranking hay prompt/model. Một single overall score không chỉ ra layer nào thất bại.

Ví dụ retriever không lấy policy mới nhất thì model không thể grounded-answer đúng; đổi model lớn hơn chỉ che symptom hoặc hallucinate tự tin hơn.

## 3. How does it work?

Một evaluation set nên chứa representative questions + expected evidence/answer criteria.

Retrieval metrics có thể gồm:

```text
Recall@K
Precision@K
MRR / rank of relevant evidence
```

Generation metrics có thể gồm:

```text
Correctness
Groundedness / faithfulness
Citation correctness
Instruction adherence
Completeness
```

Không phải metric nào cũng cần dùng; chọn theo failure cost.

## 4. Practical implementation

Tạo dataset từ production-like cases:

```json
{
  "question": "Khách hàng Enterprise có thể export định dạng nào?",
  "required_evidence": ["DOCX", "Markdown"],
  "forbidden_claims": ["PDF", "HTML"],
  "source_ids": ["release1-export-policy"]
}
```

Pipeline evaluation:

```text
1. Run retrieval only
2. Record top-K source IDs + scores
3. Score whether required evidence appears
4. Run generation with retrieved context
5. Score groundedness/correctness
6. Slice failures by query type, source, tenant, recency
```

Quan trọng: lưu retrieval trace. Nếu chỉ lưu final answer, debugging sẽ mất evidence chain.

## 5. Real production scenario

Internal knowledge assistant trả lời sai một policy mới. Team ban đầu sửa system prompt. Offline evaluation cho thấy 92% answer failures có cùng pattern: retriever ưu tiên historical document có lexical overlap cao hơn current amendment.

Fix thực sự là metadata filter + authority/recency ranking, không phải thêm “hãy trả lời chính xác” vào prompt.

## 6. Failure scenario & troubleshooting

**Symptom** → câu trả lời fluent nhưng dùng source cũ hoặc thiếu decisive document.

**Measure** → top-K retrieval, source authority, rank, chunk content, answer citations.

**Hypothesis** → retrieval failure hay generation failure.

**Test** → đưa gold evidence trực tiếp cho model. Nếu answer đúng, retrieval là bottleneck; nếu vẫn sai, generation/prompt/model cần điều tra.

**Fix** → sửa đúng layer: chunking, filters, hybrid search, reranker, prompt, model hoặc post-validation.

**Verify** → rerun frozen eval set + shadow production sample; không chỉ thử vài câu demo đẹp.

## 7. Common mistakes

- Chấm chỉ bằng “LLM judge overall score” mà không có failure taxonomy.
- Eval set toàn câu dễ, không giống production distribution.
- Không version dataset/index/model/prompt nên kết quả không reproducible.
- Đo retrieval Recall@K nhưng không đo answer groundedness.
- Dùng current model để tự chấm mà không calibrate với human labels ở high-risk cases.
- Không có adversarial/stale/conflicting-source cases.

## 8. Alternatives

- Closed-book fine-tuning nếu knowledge ổn định và retrieval không cần citation/update nhanh.
- Deterministic rules/search cho narrow domain có structured source.
- SQL/API tool calling nếu câu hỏi thực chất cần live structured data hơn document retrieval.
- Human review workflow cho high-impact decisions.

## 9. Trade-offs

### Advantages

- Tách failure theo component nên iteration có mục tiêu.
- Cho phép regression testing khi đổi embeddings/chunking/model.
- Biến “AI cảm giác tốt hơn” thành engineering measurements.

### Costs / Risks

- Gold data tạo và maintain tốn công.
- LLM-as-judge có bias/variance.
- Production distribution thay đổi nên eval set phải evolve.
- Một metric aggregate có thể che failure nghiêm trọng ở slice nhỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG gồm retrieval + generation, lỗi có thể nằm ở cả hai.

### Middle

Biết tạo test cases và inspect top-K context trước khi chỉnh prompt.

### Senior

Thiết kế offline eval, failure slices, groundedness/citation checks và regression gates.

### Technical Lead / Architect

Đặt quality model theo business risk: source authority, freshness, access control, evaluation ownership và release criteria cho retrieval/model changes.

## 11. Key takeaway

- Đừng tối ưu final answer trước khi biết evidence có được retrieve đúng không.
- Gold evidence giúp phân biệt retrieval failure với generation failure rất nhanh.
- RAG cần versioned eval dataset giống software cần regression test suite.

# Cross-topic synthesis

Mười chủ đề hôm nay cùng chia sẻ một nguyên tắc kỹ thuật quan trọng: **optimization hoặc flexibility luôn tạo thêm một correctness boundary mới**.

- `Span<T>` giảm allocation nhưng làm lifetime/ownership quan trọng hơn.
- Output Cache giảm backend load nhưng làm cache-key isolation và invalidation trở thành correctness problem.
- `ExecuteUpdate/Delete` nhanh hơn tracked mutation nhưng bỏ qua Change Tracker semantics.
- Plan reuse tiết kiệm compilation nhưng data skew tạo parameter-sensitive performance.
- MongoDB flexible schema giúp evolution nhanh nhưng persisted contracts vẫn cần protection.
- `git bisect` tăng tốc regression search nhưng phụ thuộc deterministic test.
- Feature flags giảm blast radius nhưng tăng runtime state space.
- Minimal/non-root containers giảm attack surface nhưng buộc application ownership/permission phải rõ.
- TypeScript structural typing tăng interoperability nhưng không thay runtime validation.
- RAG tăng khả năng dùng knowledge ngoài model nhưng cần evaluation tách retrieval khỏi generation.

Một Senior/Technical Lead không chỉ hỏi “feature này có dùng được không?”, mà hỏi thêm:

```text
Boundary mới nằm ở đâu?
Failure mode mới là gì?
Measurement nào chứng minh nó tốt hơn?
Invariant nào phải giữ?
Ai sở hữu cleanup/invalidation/evolution?
```
