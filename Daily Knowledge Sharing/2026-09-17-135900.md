# 1. .NET `Task.WhenAll`: exception semantics, fan-out và bounded concurrency

## 1. What is it?

`Task.WhenAll` tạo một task đại diện cho việc hoàn thành của nhiều task con. Mental model quan trọng: nó **join concurrent operations**, nhưng không tự giới hạn concurrency, không biến synchronous work thành asynchronous và không cung cấp resource budget.

## 2. Why does it exist?

Nếu ba I/O độc lập mất lần lượt 200 ms, 300 ms và 250 ms, await tuần tự có thể tốn khoảng 750 ms; bắt đầu chúng cùng lúc rồi `WhenAll` có thể tiến gần dependency chậm nhất. Nhưng fan-out không kiểm soát có thể chuyển latency optimization thành downstream overload.

## 3. How does it work?

Các task được tạo trước rồi `WhenAll` quan sát completion của toàn bộ. Nếu một hay nhiều task fault, task tổng fault; nếu không fault nhưng có cancellation thì task tổng canceled. Khi troubleshooting nhiều lỗi, cần inspect các task hoặc aggregate exception thay vì giả định chỉ dependency đầu tiên thất bại.

## 4. Practical implementation

```csharp
var productTask = productClient.GetAsync(id, ct);
var stockTask = inventoryClient.GetAsync(id, ct);
var reviewsTask = reviewClient.GetAsync(id, ct);

await Task.WhenAll(productTask, stockTask, reviewsTask);

return new ProductPage(
    await productTask,
    await stockTask,
    await reviewsTask);
```

Với danh sách lớn, dùng bounded concurrency thay vì tạo hàng chục nghìn task:

```csharp
await Parallel.ForEachAsync(ids,
    new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct },
    async (id, token) => await ProcessAsync(id, token));
```

## 5. Real production scenario

Product API cần Catalog, Inventory và Reviews. Ba dependency độc lập được gọi concurrent để giảm latency. Khi Reviews chậm, endpoint phải quyết định reviews là mandatory hay degradable; `WhenAll` thuần túy khiến toàn response chờ dependency optional.

## 6. Failure scenario & troubleshooting

**Symptom** → latency giảm ở test nhỏ nhưng production xuất hiện 429/connection exhaustion. **Evidence** → dependency concurrency và socket/DB pool tăng mạnh. **Hypothesis** → unbounded fan-out. **Diagnosis** → trace số child spans mỗi request và concurrency thực tế. **Fix** → concurrency limit, timeout budget, fallback cho optional dependency. **Verification** → load test lại p95/p99 và downstream saturation.

## 7. Common mistakes

Tạo `Select(async ...)` trên hàng trăm nghìn items rồi `WhenAll`; dùng `Task.Run` cho I/O; không truyền cancellation; coi mọi dependency là bắt buộc; chỉ log exception được throw ra mà bỏ mất lỗi sibling task.

## 8. Alternatives

Await tuần tự đơn giản và đúng khi operations phụ thuộc nhau hoặc traffic thấp. `Parallel.ForEachAsync`, `SemaphoreSlim` hay Channel phù hợp khi cần bounded work queue.

## 9. Trade-offs

### Advantages

Giảm wall-clock latency cho I/O độc lập và code composition rõ.

### Costs / Risks

Tăng instantaneous load, connection usage và blast radius; error semantics phức tạp hơn sequential flow.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu concurrency khác parallelism và `WhenAll` không tạo thêm CPU.

### Middle

Fan-out I/O độc lập, truyền cancellation và xử lý lỗi đúng.

### Senior

Đo concurrency, downstream capacity, timeout budget và partial failure.

### Technical Lead / Architect

Quyết định dependency nào được fan-out, concurrency budget bao nhiêu và khi nào nên aggregate dữ liệu ở boundary khác.

## 11. Key takeaway

- `WhenAll` là join primitive, không phải concurrency limiter.
- Tối ưu latency phải tôn trọng capacity của downstream.
- Optional dependency cần degradation policy riêng.

# 2. EF Core interceptors: cross-cutting persistence behavior mà không làm domain phụ thuộc infrastructure

## 1. What is it?

EF Core interceptors cho phép quan sát hoặc can thiệp vào operations như command execution và `SaveChanges`. Mental model: interceptor là infrastructure hook, phù hợp cho cross-cutting persistence concerns, không phải nơi chứa business policy tùy ý.

## 2. Why does it exist?

Auditing, diagnostics hoặc enforcement kỹ thuật thường cần áp dụng nhất quán cho nhiều DbContext operations. Copy logic vào từng repository/service dễ thiếu và làm application code nhiễu.

## 3. How does it work?

EF Core gọi interceptor tại lifecycle point xác định. `SaveChangesInterceptor` có thể inspect tracked entries trước khi SQL được gửi. Command interceptor có thể đo command hoặc annotate diagnostics.

## 4. Practical implementation

```csharp
public sealed class AuditInterceptor(TimeProvider clock)
    : SaveChangesInterceptor
{
    public override InterceptionResult<int> SavingChanges(
        DbContextEventData eventData,
        InterceptionResult<int> result)
    {
        var db = eventData.Context!;
        foreach (var entry in db.ChangeTracker.Entries<IAudited>())
            if (entry.State == EntityState.Modified)
                entry.Entity.UpdatedAt = clock.GetUtcNow();

        return result;
    }
}
```

Đăng ký interceptor theo DI lifetime phù hợp với state mà nó giữ.

## 5. Real production scenario

Enterprise platform yêu cầu `UpdatedAt` nhất quán cho nhiều aggregates. Interceptor giúp kỹ thuật auditing không bị lặp trong handlers, trong khi domain vẫn sở hữu các business invariants thực sự.

## 6. Failure scenario & troubleshooting

**Symptom** → test pass nhưng production audit user bị lẫn tenant. **Evidence** → interceptor giữ mutable request state và được đăng ký singleton. **Diagnosis** → lifetime/state leakage. **Fix** → stateless interceptor hoặc scoped dependency đúng boundary. **Verification** → concurrent integration tests nhiều users/tenants.

## 7. Common mistakes

Đặt business workflow trong interceptor; gọi external API từ `SavingChanges`; thay SQL bí mật khiến query khó debug; giữ scoped state trong singleton.

## 8. Alternatives

Override `SaveChanges` đơn giản hơn cho một DbContext. Domain events phù hợp cho business semantics. Middleware không nhìn được persistence lifecycle chi tiết.

## 9. Trade-offs

### Advantages

Centralized, reusable, giảm duplication cho persistence cross-cutting concern.

### Costs / Risks

Behavior trở nên implicit; debugging khó nếu interceptor thay đổi dữ liệu hoặc command quá nhiều.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu interceptor chạy quanh EF lifecycle.

### Middle

Dùng cho audit/diagnostics và viết integration tests.

### Senior

Quản lý lifetime, transaction semantics và implicit behavior.

### Technical Lead / Architect

Xác định concern nào thuộc infrastructure hook và concern nào phải explicit trong domain/application flow.

## 11. Key takeaway

- Interceptor tốt cho technical cross-cutting behavior.
- Business invariant không nên bị giấu trong persistence hook.
- Lifetime và implicit side effects phải được kiểm soát.

# 3. SQL Server Query Store: tìm plan regression bằng evidence thay vì đoán query chậm

## 1. What is it?

Query Store lưu lịch sử query, execution statistics và execution plans theo thời gian. Mental model: nó là “flight recorder” cho query performance, cho phép so sánh trước/sau thay vì chỉ nhìn plan hiện tại.

## 2. Why does it exist?

Query có thể đột nhiên chậm sau deploy, statistics change hoặc plan recompilation. Nếu chỉ lấy execution plan sau incident, plan tốt cũ đã mất khỏi memory cache và ta thiếu baseline.

## 3. How does it work?

Query Store persist query text, plans và runtime stats theo intervals. Ta có thể tìm query có duration/CPU/reads tăng và xem plan ID thay đổi ở thời điểm regression.

## 4. Practical implementation

```sql
SELECT TOP (20)
    q.query_id,
    p.plan_id,
    rs.avg_duration,
    rs.avg_logical_io_reads
FROM sys.query_store_query q
JOIN sys.query_store_plan p ON p.query_id = q.query_id
JOIN sys.query_store_runtime_stats rs ON rs.plan_id = p.plan_id
ORDER BY rs.avg_duration DESC;
```

Plan forcing có thể là mitigation, nhưng root cause vẫn cần được hiểu.

## 5. Real production scenario

Timesheet report từ 400 ms tăng lên 12 s mà code không đổi. Query Store cho thấy plan mới chuyển từ selective seek + lookup sang scan do cardinality estimate khác sau data growth.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 DB latency tăng sau một thời điểm rõ. **Evidence** → Query Store runtime stats cho query ID và plan transition. **Hypothesis** → plan regression. **Diagnosis** → so operators, estimated/actual rows, reads và parameter distribution. **Fix** → query/index/statistics design; force known plan chỉ khi cần giảm incident nhanh. **Verification** → reads, duration và production distribution sau fix.

## 7. Common mistakes

Force plan rồi coi incident kết thúc; chỉ nhìn duration mà bỏ logical reads; thêm index không kiểm tra write cost; không cấu hình retention/storage phù hợp.

## 8. Alternatives

Extended Events tốt cho event-level diagnostics. Application Insights cho end-to-end dependency latency nhưng không thay thế plan history.

## 9. Trade-offs

### Advantages

Historical evidence, regression detection và plan comparison mạnh.

### Costs / Risks

Có storage/collection overhead và cần operational ownership; plan forcing có thể giữ một plan không còn phù hợp khi workload đổi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết query performance có thể thay dù SQL text không đổi.

### Middle

Tìm expensive queries và đọc basic plan/runtime stats.

### Senior

Phân tích plan regression bằng I/O, cardinality, parameters và locks.

### Technical Lead / Architect

Thiết lập database performance baseline, retention và incident workflow thay vì tối ưu ad hoc.

## 11. Key takeaway

- Query Store cung cấp lịch sử, không chỉ snapshot.
- Plan regression cần evidence từ plan + I/O + workload.
- Force plan là mitigation có trade-off, không phải mặc định root-cause fix.

# 4. Elasticsearch shard sizing: scale search bằng distribution nhưng tránh oversharding

## 1. What is it?

Shard là đơn vị phân phối Lucene index trong Elasticsearch. Primary shard chứa một phần dữ liệu; replica cung cấp redundancy và read capacity. Mental model: shard là operational unit có cost, không phải “chia càng nhỏ càng scale”.

## 2. Why does it exist?

Một index lớn hơn capacity của một node cần phân phối storage và query workload. Shards cho phép data nằm trên nhiều nodes và phục hồi khi node lỗi.

## 3. How does it work?

Search request có thể fan-out tới shards liên quan rồi coordinating node merge kết quả. Nhiều shards tăng parallelism nhưng cũng tăng metadata, heap, file handles và coordination overhead.

## 4. Practical implementation

```json
PUT products-v3
{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1
  }
}
```

Shard count phải dựa trên data volume, growth, node topology và measured workload, không dùng một con số cố định cho mọi index.

## 5. Real production scenario

Search platform tạo index theo tenant, mỗi index 5 shards dù tenant chỉ có vài MB. Sau hàng nghìn tenants, cluster có hàng chục nghìn tiny shards; heap/cluster-state pressure tăng dù tổng data không lớn.

## 6. Failure scenario & troubleshooting

**Symptom** → search latency và GC tăng khi data volume còn thấp. **Evidence** → shard count rất cao, shards nhỏ, cluster-state operations chậm. **Hypothesis** → oversharding. **Diagnosis** → kiểm tra shard distribution, heap, query fan-out. **Fix** → consolidate indices, rollover strategy, reindex với shard count hợp lý. **Verification** → latency, heap và recovery time sau migration.

## 7. Common mistakes

Một index per customer không đánh giá scale; quá nhiều replicas để “tăng performance”; shard count dựa trên folklore; dùng Elasticsearch làm transactional source of truth.

## 8. Alternatives

Shared index với tenant field giảm shard explosion nhưng cần security/filter discipline. SQL full-text/search có thể đủ cho requirement đơn giản hơn.

## 9. Trade-offs

### Advantages

Distribution, horizontal scale và recovery linh hoạt.

### Costs / Risks

Mỗi shard có operational overhead; re-sharding thường cần reindex và migration planning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index có thể gồm nhiều primary/replica shards.

### Middle

Quan sát shard allocation và query fan-out.

### Senior

Thiết kế shard/rollover dựa trên workload, growth và recovery.

### Technical Lead / Architect

Quyết định tenancy/index topology và operational budget cho search cluster.

## 11. Key takeaway

- Shard là cost-bearing distribution unit.
- Oversharding có thể làm cluster chậm trước khi storage đầy.
- Sizing phải dựa trên measurement và growth model.

# 5. DDD Bounded Context integration: ownership, translation và consistency boundary

## 1. What is it?

Bounded Context là boundary nơi một domain model và ubiquitous language có nghĩa nhất quán. Integration giữa contexts cần explicit contract; cùng một từ như `Customer` không buộc phải là cùng object model ở Sales, Billing và Support.

## 2. Why does it exist?

Một enterprise-wide canonical model thường tạo coupling: thay đổi field cho Billing làm Sales phải release, shared database làm ownership mơ hồ. Bounded Context cho phép mỗi business capability sở hữu model phù hợp với invariants của nó.

## 3. How does it work?

```text
Sales Context             Billing Context
Orders DB                 Billing DB
    │                         ▲
    └─ Integration Contract ──┘
       translation/versioning
```

Sales sở hữu Order transaction. Billing nhận dữ liệu cần thiết qua API/event và translate sang model của Billing. Cross-context operation không mặc định là một ACID transaction.

## 4. Practical implementation

```csharp
public sealed record OrderConfirmedV1(
    Guid OrderId,
    Guid CustomerId,
    decimal Amount,
    string Currency);
```

Billing map contract này sang `InvoiceDraft`; nó không deserialize trực tiếp Sales aggregate rồi dùng như domain entity của mình.

## 5. Real production scenario

E-commerce có Catalog, Orders và Billing. Orders cần product snapshot tại thời điểm mua; nếu nó luôn query live Catalog model, đổi tên/giá sau purchase có thể phá historical correctness.

## 6. Failure scenario & troubleshooting

**Symptom** → deploy Billing bị vỡ khi Sales thêm/đổi schema. **Evidence** → consumers phụ thuộc internal DTO/database table. **Diagnosis** → integration contract không có ownership/versioning. **Fix** → stable contract, translation layer, compatibility policy. **Verification** → consumer contract tests và replay event versions.

## 7. Common mistakes

Một shared `Domain` package cho mọi service; shared database tables; dùng Entity/Value Object chỉ vì DDD terminology; tạo distributed transaction để giữ illusion một model toàn hệ thống.

## 8. Alternatives

Một bounded context hoặc layered monolith đủ khi business language thật sự thống nhất. Không nên chia context chỉ để đạt số lượng module đẹp.

## 9. Trade-offs

### Advantages

Change isolation, ownership rõ, model phù hợp business capability.

### Costs / Risks

Translation, duplicate data, eventual consistency và contract governance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt cùng tên business không nhất thiết cùng model.

### Middle

Không bypass public context contract.

### Senior

Thiết kế translation, event/API contracts, consistency và failure recovery.

### Technical Lead / Architect

Xác định boundaries theo business capability, team ownership và change patterns; quyết định khi nào một context duy nhất đơn giản hơn.

## 11. Key takeaway

- Bounded Context là semantic/ownership boundary, không phải folder.
- Integration contract phải explicit và versionable.
- Eventual consistency là hệ quả cần thiết kế, không phải chi tiết implementation.

# 6. Azure SQL Failover Groups: database continuity, DNS failover và application retry behavior

## 1. What is it?

Failover Group cung cấp replication/failover giữa Azure SQL logical servers và stable listener endpoints. Mental model: database failover không làm in-flight transaction “teleport”; connection hiện tại vẫn có thể chết và application phải chịu transient failure.

## 2. Why does it exist?

Region/server failure cần recovery path mà không hard-code đổi connection string thủ công. Listener abstraction giúp application reconnect tới current primary.

## 3. How does it work?

Primary replicate dữ liệu sang secondary. Khi failover, role đổi và listener DNS/routing đưa connection mới tới primary mới. RPO/RTO phụ thuộc replication/failover mode và workload.

## 4. Practical implementation

Application dùng failover-group listener trong connection string và EF Core connection resiliency có kiểm soát:

```csharp
options.UseSqlServer(connectionString, sql =>
    sql.EnableRetryOnFailure(
        maxRetryCount: 5,
        maxRetryDelay: TimeSpan.FromSeconds(10),
        errorNumbersToAdd: null));
```

Retry không được dùng để lặp lại arbitrary external side effects.

## 5. Real production scenario

SaaS API chạy ở hai regions. Primary SQL region mất connectivity; failover chuyển secondary thành primary. Requests đang giữa transaction lỗi, requests mới reconnect sau DNS/connection retry.

## 6. Failure scenario & troubleshooting

**Symptom** → 5xx spike trong failover dù secondary healthy. **Evidence** → SQL transient connection errors, retry telemetry, DNS transition. **Hypothesis** → app không resilient hoặc retry budget sai. **Diagnosis** → kiểm tra connection strings, retry policy, transaction idempotency. **Fix** → listener, bounded retry, graceful degradation và tested failover runbook. **Verification** → planned failover exercise với p95/error-rate/RTO measurement.

## 7. Common mistakes

Tin rằng failover = zero errors; retry cả transaction có external side effect; không test failover; secondary region app không có network/identity config tương đương.

## 8. Alternatives

Geo-replication tự quản cho topology khác; backup/restore rẻ hơn nhưng RTO lớn. Single-region có thể đủ nếu business RTO cho phép.

## 9. Trade-offs

### Advantages

Continuity tốt hơn, stable endpoint và operational failover mechanism.

### Costs / Risks

Replication cost, complexity, possible data lag và application resilience vẫn bắt buộc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu failover chỉ ảnh hưởng connection mới sau role change.

### Middle

Cấu hình listener/retry và nhận diện transient SQL errors.

### Senior

Thiết kế transaction retry, idempotency, RPO/RTO tests và observability.

### Technical Lead / Architect

Chọn DR topology dựa trên business RPO/RTO, cost, regional dependencies và operational drills.

## 11. Key takeaway

- Database HA không loại bỏ transient application errors.
- Retry phải bounded và transaction-aware.
- DR chỉ đáng tin khi được failover-test định kỳ.

# 7. CI/CD database migration orchestration: expand-contract để release không khóa deployment

## 1. What is it?

Migration orchestration là cách phối hợp schema change với nhiều application versions trong release. Expand-contract tách breaking migration thành bước tương thích ngược rồi cleanup sau.

## 2. Why does it exist?

Trong rolling/slot/canary deployment, old và new code có thể chạy đồng thời. Rename/drop column ngay lập tức làm một version hỏng. Database là shared state nên rollback application không tự rollback schema an toàn.

## 3. How does it work?

```text
commit → build → test → artifact
→ EXPAND schema
→ deploy compatible app
→ health validation → monitor
→ migrate/backfill data
→ CONTRACT ở release sau
```

Transaction boundary của migration thuộc database; deployment pipeline phải biết migration nào online-safe và migration nào cần maintenance strategy.

## 4. Practical implementation

Thay vì rename trực tiếp `Name` → `DisplayName`:

1. Add nullable `DisplayName`.
2. New app đọc fallback `DisplayName ?? Name`, ghi cả hai nếu cần.
3. Backfill.
4. Chuyển readers sang `DisplayName`.
5. Release sau mới drop `Name`.

## 5. Real production scenario

App Service có staging slot và production cùng truy cập database. New build cần column mới. Expand migration chạy trước swap nên old production vẫn hoạt động; contract chỉ chạy khi không còn binary cũ.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment rollback app nhưng old version crash. **Evidence** → migration đã drop/rename schema old binary cần. **Diagnosis** → app rollback path không tương thích database forward state. **Fix** → expand-contract, backup không thay thế compatibility design. **Verification** → test old/new binaries trên expanded schema trong CI/integration environment.

## 7. Common mistakes

`Database.Migrate()` từ mọi web instance; long table rewrite giờ cao điểm; destructive migration cùng release; không monitor lock duration; artifact không immutable giữa environments.

## 8. Alternatives

Maintenance-window migration đơn giản hơn cho low-availability internal systems. Blue-Green database riêng cực phức tạp với write synchronization và thường không cần thiết.

## 9. Trade-offs

### Advantages

Giảm downtime, hỗ trợ rolling rollback và tách risk.

### Costs / Risks

Temporary dual-schema/dual-write complexity, cleanup chậm và cần release discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu schema và binary versions có thể overlap.

### Middle

Viết backward-compatible migration và integration tests.

### Senior

Đánh giá locks, backfill, rollback và data correctness.

### Technical Lead / Architect

Đặt migration ownership/gates trong pipeline và quyết định khi nào maintenance window đơn giản hơn.

## 11. Key takeaway

- Database rollback không đồng nghĩa application rollback.
- Expand trước, contract sau giúp version overlap an toàn.
- Migration là release-engineering concern, không chỉ EF command.

# 8. OpenTelemetry RED metrics: từ symptom đến trace mà không tạo telemetry cardinality explosion

## 1. What is it?

RED là ba signal chính cho request-driven services: Rate, Errors, Duration. Nó cung cấp health view ở service boundary; traces/logs sau đó giúp giải thích nguyên nhân.

## 2. Why does it exist?

Log-only monitoring khó thấy xu hướng và SLO. Metrics cho biết hệ thống đang xấu đi; trace cho biết request đi đâu; logs cung cấp detail. Mỗi signal giải một câu hỏi khác nhau.

## 3. How does it work?

```text
Alert: error rate/p95
        │
        ▼
Metrics (RED)
        │ locate service/route
        ▼
Trace
        │ locate dependency/span
        ▼
Structured logs
        └─ detailed evidence
```

Metric labels phải bounded. `userId`, raw URL hay order ID tạo high cardinality và chi phí lớn.

## 4. Practical implementation

```csharp
var meter = new Meter("Orders.Api");
var failures = meter.CreateCounter<long>("orders.failures");

failures.Add(1,
    new KeyValuePair<string, object?>("operation", "create-order"),
    new KeyValuePair<string, object?>("reason", "inventory-unavailable"));
```

Dùng bounded semantic dimensions thay unique identifiers.

## 5. Real production scenario

Order API p95 tăng từ 250 ms lên 2 s. RED dashboard cho thấy rate ổn, errors thấp nhưng duration tăng ở `/orders`. Trace chỉ ra Inventory dependency chiếm 1.7 s; logs xác nhận timeout retries.

## 6. Failure scenario & troubleshooting

**Symptom** → telemetry bill/memory tăng mạnh. **Evidence** → metric series count explosion. **Hypothesis** → high-cardinality labels. **Diagnosis** → inspect attributes như URL/user/order IDs. **Fix** → normalize route, bounded labels, đưa identifiers sang traces/logs. **Verification** → series count/cost giảm mà incident drill vẫn điều tra được.

## 7. Common mistakes

Alert mọi exception; metric label bằng raw exception message; chỉ có averages; traces không correlation với logs; health dashboard không gắn SLO.

## 8. Alternatives

USE metrics phù hợp resource-centric view như CPU/disk. RED và USE bổ sung nhau, không cạnh tranh.

## 9. Trade-offs

### Advantages

Fast health detection và path rõ từ symptom tới evidence.

### Costs / Risks

Instrumentation/cardinality/storage cost; alert design kém tạo noise.

## 11. Key takeaway

# 9. Optimizely CMS cache invalidation: content publish, distributed instances và stale delivery

## 1. What is it?

CMS caching giữ content/rendered data gần application để giảm database/content-provider reads. Với Optimizely chạy nhiều instances, invalidation phải được truyền giữa nodes để publish mới không chỉ visible trên một process.

## 2. Why does it exist?

Content pages được đọc nhiều hơn ghi. Cache giảm latency và backend load. Nhưng editor kỳ vọng publish có freshness semantics rõ; stale cache làm CMS trông như publish thất bại.

## 3. How does it work?

```text
Editor → Publish → Content store
                    │
                    ├─ invalidate Node A cache
                    └─ invalidate Node B cache
                              │
Browser ← CDN ← Web instances
```

Ngoài CMS cache còn có output/CDN/browser caches; mỗi tầng có ownership và TTL khác nhau.

## 4. Practical implementation

Khi thêm custom cache cho derived content, key phải chứa identity/version/language phù hợp và invalidation phải gắn content-change event thay vì TTL dài tùy ý. Không cache editor-specific/personalized response ở shared layer.

## 5. Real production scenario

Marketing publish campaign block. Node A nhận invalidation nhưng Node B custom `IMemoryCache` không được clear; load balancer khiến user thấy nội dung lúc mới lúc cũ.

## 6. Failure scenario & troubleshooting

**Symptom** → refresh luân phiên old/new content. **Evidence** → response headers/instance ID correlate stale result với một node. **Hypothesis** → node-local custom cache. **Diagnosis** → trace publish invalidation qua CMS, app cache, CDN. **Fix** → distributed invalidation/versioned key hoặc bỏ cache không cần thiết. **Verification** → publish test trên multi-instance và edge cache.

## 7. Common mistakes

Thêm `IMemoryCache` quanh CMS API mà không invalidation; purge toàn CDN cho mọi publish; cache personalized page; nhầm CMS cache với CDN cache.

## 8. Alternatives

Không thêm custom cache nếu built-in CMS/content cache đã đủ. Headless delivery/cache layer phù hợp khi architecture thực sự cần independent frontend scaling.

## 9. Trade-offs

### Advantages

Read latency thấp, giảm content-store load.

### Costs / Risks

Freshness complexity tăng theo số cache layers và instances.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu publish không đồng nghĩa mọi cache tự động biến mất.

### Middle

Xác định cache layer và test invalidation.

### Senior

Thiết kế multi-instance freshness, personalization và CDN interaction.

### Technical Lead / Architect

Đặt freshness SLA, cache ownership và quyết định layer nào thực sự cần tồn tại.

## 11. Key takeaway

- Cache layer nào tạo ra thì phải có invalidation ownership.
- Multi-instance làm local cache correctness khó hơn.
- Debug stale CMS phải đi từ content store tới app, CDN và browser.

# 10. OAuth refresh token rotation: session continuity, replay detection và revocation boundary

## 1. What is it?

Refresh token cho client lấy access token mới mà không bắt user đăng nhập lại. Rotation thay refresh token sau mỗi successful use; token cũ bị invalidated hoặc đánh dấu đã dùng để phát hiện replay.

## 2. Why does it exist?

Access token nên có lifetime ngắn để giảm blast radius. Refresh token sống lâu hơn nên nếu bị đánh cắp, static token có thể bị reuse lâu dài. Rotation giảm cửa sổ và tạo tín hiệu khi cùng token bị dùng hai lần.

## 3. How does it work?

```text
Client ── refresh token R1 ─► Authorization Server
Client ◄─ access token + R2 ──

R1 reused later
      │
      └─ replay detected → revoke token family/session policy
```

Authorization server sở hữu token lifecycle; resource API chỉ validate access token theo issuer/audience/signature/policy.

## 4. Practical implementation

SPA không nên tự invent refresh-token storage protocol. Dùng OpenID Connect/OAuth client library và provider flow phù hợp. Backend API vẫn enforce authorization deterministic từ validated access token claims/policies.

```csharp
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("Orders.Write",
        p => p.RequireClaim("scope", "orders.write"));
});
```

## 5. Real production scenario

Mobile app giữ session nhiều tuần. Access token 10 phút; refresh rotation cho continuity. Nếu attacker copy R1 rồi legitimate client đã đổi sang R2, reuse R1 có thể kích hoạt session revocation theo provider policy.

## 6. Failure scenario & troubleshooting

**Symptom** → users bị logout ngẫu nhiên khi nhiều refresh requests chạy đồng thời. **Evidence** → hai requests dùng cùng refresh token gần đồng thời; một request bị reuse detection. **Hypothesis** → client refresh race. **Diagnosis** → network traces/client concurrency. **Fix** → single-flight refresh logic và provider-recommended token handling. **Verification** → concurrent expiry tests nhiều tabs/requests.

## 7. Common mistakes

Lưu refresh token trong insecure browser storage không đánh giá XSS; tự parse JWT mà không validate; retry refresh vô hạn; log tokens; coi CORS là authorization.

## 8. Alternatives

Cookie/BFF session có thể giảm token exposure trong browser. Reauthentication thường xuyên đơn giản hơn nhưng UX kém. Chọn flow theo client type và threat model.

## 9. Trade-offs

### Advantages

Access token ngắn hạn, session dài và khả năng replay detection tốt hơn static refresh token.

### Costs / Risks

Client state machine phức tạp, race conditions và revocation behavior cần hiểu rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt access token và refresh token.

### Middle

Dùng chuẩn provider/library, không tự chế token protocol.

### Senior

Hiểu rotation, replay, storage, concurrency và revocation.

### Technical Lead / Architect

Chọn SPA/BFF/mobile auth architecture dựa trên threat model, UX, identity provider capability và operational ownership.

## 11. Key takeaway

- Refresh token là credential nhạy cảm hơn vì lifetime dài.
- Rotation hữu ích cho replay detection nhưng tạo client concurrency concerns.
- Authentication protocol nên dựa trên chuẩn/provider, authorization vẫn phải deterministic ở API.
