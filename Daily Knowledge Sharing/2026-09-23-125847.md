# 1. .NET `Channel<T>`: bounded producer-consumer pipelines và backpressure

## 1. What is it?

Mental model: `Channel<T>` là một asynchronous queue trong process, tách producer khỏi consumer. Điểm quan trọng không phải “queue nhanh”, mà là **capacity boundary**: bounded channel cho phép hệ thống phản ứng khi producer tạo work nhanh hơn consumer xử lý.

## 2. Why does it exist?

Nếu request cứ đẩy work vào `ConcurrentQueue` không giới hạn, memory trở thành queue. Khi downstream chậm, backlog tăng cho đến GC pressure hoặc OOM. Bounded channel buộc ta quyết định: chờ, drop, reject hay chuyển sang durable broker.

## 3. How does it work?

```text
Producer -> Channel(capacity=100) -> Consumer
              |
              +-- full -> Wait / Drop / Reject policy
```

`ChannelReader` và `ChannelWriter` hỗ trợ asynchronous waiting, tránh polling loop.

## 4. Practical implementation

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true
});

await channel.Writer.WriteAsync(job, ct);

await foreach (var item in channel.Reader.ReadAllAsync(stoppingToken))
    await processor.ProcessAsync(item, stoppingToken);
```

## 5. Real production scenario

API nhận thumbnail jobs. Image processor chỉ xử lý 20 jobs/s nhưng burst đạt 200 jobs/s. Bounded channel hấp thụ burst nhỏ; sustained overload phải được reject hoặc chuyển sang durable queue.

## 6. Failure scenario & troubleshooting

**Symptom** → request latency tăng khi enqueue. **Evidence** → channel thường xuyên full. **Hypothesis** → consumer throughput thấp hơn arrival rate. **Diagnosis** → đo enqueue rate, processing rate, queue depth. **Fix** → tối ưu/scale consumer hoặc đổi sang broker; không chỉ tăng capacity. **Verification** → overload test và quan sát bounded memory.

## 7. Common mistakes

Unbounded channel cho workload không giới hạn; fire-and-forget consumer; không complete writer; không propagate cancellation; coi in-memory queue là durable.

## 8. Alternatives

`ConcurrentQueue` phù hợp primitive synchronous đơn giản. Azure Service Bus phù hợp durability, cross-process delivery và retry. `BackgroundService` thường là consumer host chứ không thay queue.

## 9. Trade-offs

### Advantages

Async coordination nhẹ, backpressure rõ, throughput tốt trong process.

### Costs / Risks

Mất work khi process chết và capacity/policy phải được thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu producer/consumer và queue depth.
### Middle
Implement bounded channel, cancellation và shutdown.
### Senior
Đo throughput, backpressure và overload behavior.
### Technical Lead / Architect
Quyết định khi nào in-process queue đủ và khi nào durability yêu cầu broker.

## 11. Key takeaway

- Queue capacity là reliability decision.
- Backpressure tốt hơn memory growth vô hạn.
- `Channel<T>` không thay durable messaging.

# 2. ASP.NET Core graceful shutdown: hoàn tất in-flight work có giới hạn

## 1. What is it?

Graceful shutdown là quá trình application ngừng nhận work mới, phát tín hiệu cancellation và cho work đang chạy một khoảng thời gian hữu hạn để hoàn tất trước khi process kết thúc.

## 2. Why does it exist?

Container/App Service/Kubernetes thường restart instance trong deployment hoặc maintenance. Kill ngay có thể cắt request, transaction hoặc message handler giữa chừng.

## 3. How does it work?

```text
SIGTERM
 -> host stopping
 -> stop accepting new work
 -> CancellationToken signaled
 -> drain in-flight work
 -> timeout
 -> process exits
```

## 4. Practical implementation

```csharp
public sealed class Worker(IService service) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
            await service.ProcessNextAsync(stoppingToken);
    }
}
```

Mọi blocking dependency phải nhận cancellation/timeout hợp lý; nếu không shutdown token không có tác dụng.

## 5. Real production scenario

Rolling deployment thay 10 pods. Worker đang xử lý messages 30 giây. Graceful shutdown ngừng nhận message mới và cho handler hiện tại settle trước termination deadline.

## 6. Failure scenario & troubleshooting

**Symptom** → deploy tạo spike 499/5xx hoặc duplicate message. **Evidence** → termination trùng request/message đang chạy. **Hypothesis** → drain window quá ngắn hoặc handler bỏ qua cancellation. **Diagnosis** → correlate shutdown logs/traces. **Fix** → align termination grace, host shutdown timeout và workload duration. **Verification** → deploy dưới load.

## 7. Common mistakes

Bắt `OperationCanceledException` rồi tiếp tục loop; start background task ngoài host lifecycle; shutdown timeout vô hạn; readiness vẫn true khi instance đang drain.

## 8. Alternatives

Durable queue + idempotent consumer giảm yêu cầu phải hoàn tất mọi work. Long-running job có thể cần external worker/orchestrator.

## 9. Trade-offs

### Advantages
Giảm dropped work và deployment disruption.
### Costs / Risks
Shutdown chậm hơn và vẫn cần hard deadline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu cancellation là cooperative.
### Middle
Propagate `CancellationToken` xuyên call chain.
### Senior
Thiết kế drain, idempotency và termination timing.
### Technical Lead / Architect
Định nghĩa lifecycle contract giữa app, load balancer và orchestrator.

## 11. Key takeaway

- Graceful shutdown không phải chờ vô hạn.
- Cancellation phải đi xuyên dependencies.
- Deployment reliability cần test dưới traffic thật tương đương.

# 3. EF Core execution strategy: retry transient failure đúng transaction boundary

## 1. What is it?

Execution strategy là cơ chế retry database operations khi gặp transient failures như temporary network/database unavailability. Với SQL Server, retry có thể được cấu hình qua provider.

## 2. Why does it exist?

Cloud database/network có partial failures ngắn. Một operation idempotent có thể thành công khi retry, nhưng retry sai transaction boundary có thể tạo state khó đoán.

## 3. How does it work?

EF execution strategy chạy delegate như một retryable unit. Nếu tự mở transaction, toàn transaction cần nằm trong delegate để retry toàn bộ unit thay vì một command riêng lẻ.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);
    order.MarkPaid();
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
});
```

External side effects không nên đặt tùy tiện trong retry delegate.

## 5. Real production scenario

Checkout ghi Order và PaymentAttempt trong transaction. Failover Azure SQL gây transient disconnect. Retry toàn transaction có thể phục hồi, nhưng gọi payment provider bên trong delegate có thể charge hai lần.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate external action sau DB retry. **Evidence** → execution logs có retry; provider nhận hai calls. **Hypothesis** → non-idempotent side effect nằm trong retry scope. **Diagnosis** → map transaction/retry boundary. **Fix** → transactional DB state + Outbox/idempotency key. **Verification** → inject transient fault.

## 7. Common mistakes

Retry mọi SQL exception; nested manual retry + provider retry; transaction ngoài execution strategy; không giới hạn attempts; retry deadlock mà không điều tra root cause.

## 8. Alternatives

Application-level resilience có thể phù hợp multi-resource workflow. Outbox tách commit khỏi message delivery. Không retry permanent constraint/business errors.

## 9. Trade-offs

### Advantages
Che transient failures ngắn.
### Costs / Risks
Tăng latency và có thể duplicate side effects nếu boundary sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt transient/permanent error.
### Middle
Cấu hình retry và transaction đúng.
### Senior
Reason về commit ambiguity/idempotency.
### Technical Lead / Architect
Thiết kế side-effect boundaries và recovery model.

## 11. Key takeaway

- Retry phải bao quanh đúng unit of work.
- Database retry không làm external side effect exactly-once.
- Fault injection cần nằm trong integration tests quan trọng.

# 4. PostgreSQL MVCC và vacuum: UPDATE tạo row version

## 1. What is it?

MVCC cho phép transaction đọc snapshot phù hợp mà không buộc reader và writer luôn block nhau. PostgreSQL thực hiện bằng nhiều tuple versions; `UPDATE` về bản chất tạo version mới và version cũ trở thành dead tuple khi không còn transaction cần nó.

## 2. Why does it exist?

Nếu mọi read phải khóa row đang được write, concurrency giảm mạnh. MVCC đổi lock contention thành version-management cost.

## 3. How does it work?

```text
Row v1 visible to old snapshot
UPDATE -> Row v2
new snapshot -> v2
old snapshot -> may still see v1
later VACUUM -> reclaim obsolete v1
```

## 4. Practical implementation

Quan sát dead tuples và autovacuum thay vì chỉ nhìn table row count:

```sql
SELECT relname, n_live_tup, n_dead_tup,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

## 5. Real production scenario

High-write audit/status table update liên tục. Disk/table bloat tăng dù logical row count ổn định vì autovacuum không theo kịp workload.

## 6. Failure scenario & troubleshooting

**Symptom** → table/index lớn, query I/O tăng. **Evidence** → dead tuples cao, vacuum lag. **Hypothesis** → churn + vacuum insufficient hoặc long transaction giữ old versions. **Diagnosis** → inspect activity/vacuum stats. **Fix** → rút ngắn transaction, tune autovacuum theo table, sửa access pattern. **Verification** → dead tuple trend và query I/O giảm.

## 7. Common mistakes

Tắt autovacuum; giữ transaction idle lâu; nghĩ MVCC nghĩa là không có locks; chạy `VACUUM FULL` như routine fix mà không xét exclusive lock.

## 8. Alternatives

Các relational engines có MVCC implementation khác; SQL Server row-versioning isolation có storage/semantics khác. Không áp dụng tuning PostgreSQL máy móc.

## 9. Trade-offs

### Advantages
Reader/writer concurrency tốt.
### Costs / Risks
Version cleanup, bloat và transaction hygiene trở thành operational concern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu snapshot/version.
### Middle
Quan sát dead tuples/vacuum.
### Senior
Phân tích long transactions và bloat.
### Technical Lead / Architect
Thiết kế workload/maintenance phù hợp write intensity.

## 11. Key takeaway

- MVCC giảm blocking bằng versioning, không miễn phí.
- Long transactions có thể cản cleanup.
- Vacuum health là phần của database reliability.

# 5. Elasticsearch alias-based reindex: đổi mapping an toàn

## 1. What is it?

Index alias là tên logic trỏ tới physical index. Khi mapping/analyzer thay đổi không thể áp dụng trực tiếp như mong muốn, tạo index mới, reindex rồi atomically chuyển alias giúp consumer không phụ thuộc version index.

## 2. Why does it exist?

Search schema evolution có thể yêu cầu rebuild toàn bộ inverted index. Nếu API gọi trực tiếp `products-v17`, deployment và migration bị coupling.

## 3. How does it work?

```text
products alias -> products-v17
build products-v18
reindex/backfill
validate
atomic alias switch -> products-v18
```

## 4. Practical implementation

```json
POST /_aliases
{
  "actions": [
    {"remove":{"index":"products-v17","alias":"products"}},
    {"add":{"index":"products-v18","alias":"products"}}
  ]
}
```

Trong migration dài, cần strategy cho writes xảy ra trong lúc backfill.

## 5. Real production scenario

E-commerce đổi analyzer cho product names. Index mới được bulk-build, shadow-query kiểm tra relevance rồi alias chuyển khi đạt acceptance criteria.

## 6. Failure scenario & troubleshooting

**Symptom** → sau switch thiếu sản phẩm mới. **Evidence** → documents tạo trong backfill chỉ nằm index cũ. **Hypothesis** → write synchronization gap. **Diagnosis** → compare source-of-truth IDs/timestamps. **Fix** → CDC/outbox replay hoặc controlled dual-write với reconciliation. **Verification** → count + sampled semantic checks.

## 7. Common mistakes

Coi document count bằng nhau là đủ; không rollback alias; xóa old index ngay; dual-write không reconciliation; để application hard-code versioned index.

## 8. Alternatives

In-place update phù hợp settings/mappings được phép thay. Blue/green search cluster cần cho infrastructure migration lớn nhưng operational cost cao hơn.

## 9. Trade-offs

### Advantages
Cutover nhanh, rollback rõ, schema evolution tách khỏi app.
### Costs / Risks
Tốn storage gấp đôi tạm thời và cần đồng bộ writes.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu alias/index.
### Middle
Tạo reindex/cutover script.
### Senior
Thiết kế consistency/reconciliation.
### Technical Lead / Architect
Định nghĩa search migration và rollback strategy.

## 11. Key takeaway

- Search schema migration là data migration.
- Alias giải coupling nhưng không giải write consistency.
- Cutover phải có validation và rollback.

# 6. DDD Aggregate boundary: consistency boundary, không phải object graph

## 1. What is it?

Aggregate là nhóm domain objects được thay đổi như một consistency boundary, với Aggregate Root là entry point bảo vệ invariants. Boundary nên dựa trên những gì **phải nhất quán atomically**, không dựa trên quan hệ database hay màn hình UI.

## 2. Why does it exist?

Nếu một aggregate chứa quá nhiều entities, mỗi command tải/lock/update graph lớn. Nếu quá nhỏ, invariant cần atomicity bị phân tán và race condition xuất hiện.

## 3. How does it work?

```text
Command -> Aggregate Root -> invariant check -> state change
                 |
                 +-- transaction boundary
```

Cross-aggregate workflow thường dùng IDs, application orchestration/domain events và eventual consistency khi business cho phép.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void AddLine(ProductId productId, int quantity)
    {
        if (quantity <= 0) throw new DomainException("Quantity must be positive");
        _lines.Add(new OrderLine(productId, quantity));
    }
}
```

Không expose mutable collection để caller bypass invariant.

## 5. Real production scenario

Order và Inventory ban đầu nằm trong một “mega aggregate”. Mỗi cart update phải chạm inventory graph và gây contention. Tách ownership cho phép Order giữ order invariants; inventory reservation trở thành workflow riêng với failure handling.

## 6. Failure scenario & troubleshooting

**Symptom** → transaction dài, concurrency conflict cao. **Evidence** → command đơn giản load/update hàng trăm rows. **Hypothesis** → aggregate quá rộng. **Diagnosis** → xác định invariants nào thực sự cần atomicity. **Fix** → redraw boundary và thiết kế cross-boundary workflow. **Verification** → concurrency tests + invariant tests.

## 7. Common mistakes

Aggregate = EF navigation graph; một aggregate cho cả bounded context; repository cho child entity; domain event dùng để né invariant đáng lẽ atomic.

## 8. Alternatives

Transaction Script phù hợp domain đơn giản. Rich aggregate đáng giá khi invariant/business behavior thực sự phức tạp.

## 9. Trade-offs

### Advantages
Ownership và consistency rõ.
### Costs / Risks
Boundary sai gây contention hoặc eventual-consistency complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt entity và aggregate root.
### Middle
Encapsulate invariants.
### Senior
Reason về transaction/concurrency boundary.
### Technical Lead / Architect
Chọn aggregate dựa trên business consistency, scale và ownership.

## 11. Key takeaway

- Aggregate là consistency boundary.
- Database relationship không tự quyết định aggregate.
- Boundary càng lớn, contention và transaction cost càng đáng chú ý.

# 7. Azure Key Vault + Managed Identity: bỏ secrets khỏi config

## 1. What is it?

Managed Identity cho Azure workload một identity do platform quản lý. Application dùng identity đó lấy token từ Microsoft Entra ID và truy cập Key Vault theo authorization policy, thay vì lưu client secret trong config.

## 2. Why does it exist?

Secret trong environment variable/config vẫn phải được phân phối, rotate và bảo vệ. Managed Identity loại bỏ credential bootstrap cho supported Azure resources.

## 3. How does it work?

```text
App Service/AKS workload
 -> Managed Identity credential
 -> Entra token
 -> Key Vault
 -> authorized secret/key/certificate
```

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(configuration["KeyVaultUri"]!),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("ExternalApiKey", ct);
```

Production identity cần least-privilege role; local development có thể dùng developer credential chain phù hợp.

## 5. Real production scenario

App Service cần third-party API key. App identity chỉ được đọc secret cụ thể/đúng vault policy; deployment artifact không chứa credential truy cập vault.

## 6. Failure scenario & troubleshooting

**Symptom** → Production 403 từ Key Vault. **Evidence** → authentication thành công nhưng authorization denied. **Hypothesis** → role/policy sai hoặc wrong identity. **Diagnosis** → kiểm tra principal, RBAC, vault/network access. **Fix** → cấp tối thiểu quyền cần thiết. **Verification** → application identity đọc được secret qua production network path.

## 7. Common mistakes

Cho Contributor/Owner quá rộng; log secret; gọi Key Vault mỗi request; nhầm Managed Identity giải quyết secret của third-party; bỏ qua Private Endpoint/network policy.

## 8. Alternatives

Environment secrets đơn giản hơn cho nhỏ/local nhưng rotation/distribution khó hơn. Workload identity federation phù hợp Kubernetes/GitHub-style federation scenarios.

## 9. Trade-offs

### Advantages
Không phải quản lý credential truy cập Azure resource trong app.
### Costs / Risks
Thêm dependency vào identity/vault/network và cần cache/availability strategy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu secret khác identity.
### Middle
Dùng `DefaultAzureCredential` đúng môi trường.
### Senior
Debug token/RBAC/network và rotation.
### Technical Lead / Architect
Thiết kế identity boundary và secret lifecycle toàn hệ thống.

## 11. Key takeaway

- Prefer identity over stored credential khi platform hỗ trợ.
- Least privilege áp dụng cho workload identity.
- Key Vault access vẫn là network/availability dependency.

# 8. SLI/SLO error budget: reliability thành quyết định đo được

## 1. What is it?

SLI là chỉ số đo trải nghiệm/reliability; SLO là mục tiêu cho SLI trong window; error budget là phần failure được phép trước khi vi phạm SLO. Ví dụ availability SLO 99.9% cho một window cho phép khoảng 0.1% unsuccessful requests theo định nghĩa SLI.

## 2. Why does it exist?

“System phải luôn ổn định” không actionable. 100% reliability thường có chi phí cực lớn và vẫn không thực tế. SLO tạo ngôn ngữ chung giữa feature velocity và reliability.

## 3. How does it work?

```text
valid events = good + bad
SLI = good / valid
SLO = target(SLI, window)
error budget = allowed bad events/time
```

## 4. Practical implementation

Ví dụ PromQL-style concept:

```text
successful_requests / total_valid_requests
```

Định nghĩa “good” phải phản ánh user outcome, không chỉ process alive. Một HTTP 200 trả dữ liệu sai không nhất thiết là good event.

## 5. Real production scenario

Checkout có SLO latency + success. Sau hai regressions tiêu thụ phần lớn error budget, team tạm ưu tiên reliability fixes và rollout chậm hơn thay vì tranh luận cảm tính.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard SLO xanh nhưng users phàn nàn. **Evidence** → SLI chỉ đo 5xx, bỏ timeout client/latency. **Hypothesis** → indicator không đại diện user experience. **Diagnosis** → trace request journey và exclusions. **Fix** → redefine SLI. **Verification** → incidents lịch sử phải phản ánh vào SLI.

## 7. Common mistakes

SLO = SLA; chọn 99.99% không dựa business; alert trên mọi error; denominator sai; loại bỏ failures “xấu” để metric đẹp.

## 8. Alternatives

Raw uptime/CPU alerts vẫn hữu ích diagnostic nhưng không thay user-centric reliability target.

## 9. Trade-offs

### Advantages
Ưu tiên reliability bằng dữ liệu.
### Costs / Risks
SLI sai tạo false confidence; SLO quá cao tăng engineering cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu metric vs objective.
### Middle
Instrument good/bad events.
### Senior
Thiết kế burn-rate alert và diagnose SLO breach.
### Technical Lead / Architect
Cân reliability target với business impact và architecture cost.

## 11. Key takeaway

- SLO chỉ tốt bằng SLI phía dưới.
- Error budget là decision mechanism, không KPI trang trí.
- Reliability nên gắn với user-visible outcomes.

# 9. Contract testing: bảo vệ integration boundary

## 1. What is it?

Contract testing xác minh provider và consumer đồng ý về interface observable: HTTP schema/status/semantics hoặc message schema. Nó nằm giữa unit test và full E2E: tập trung vào boundary thay vì dựng toàn hệ thống.

## 2. Why does it exist?

Microservice/API integrations thường break vì provider đổi field, enum hoặc semantics. Full E2E chậm/flaky và khó bao phủ mọi consumer expectation.

## 3. How does it work?

```text
Consumer expectation -> contract artifact/check
                         |
                         v
Provider verification against implementation
```

Schema compatibility chỉ là một phần; semantics quan trọng cũng cần test.

## 4. Practical implementation

ASP.NET Core integration test có thể khóa response contract:

```csharp
var response = await client.GetAsync("/api/orders/42");
response.EnsureSuccessStatusCode();

var dto = await response.Content.ReadFromJsonAsync<OrderDto>();
Assert.NotNull(dto);
Assert.Equal(42, dto.Id);
Assert.NotNull(dto.Status);
```

Consumer-driven contract tooling hữu ích khi nhiều independently deployed consumers/providers.

## 5. Real production scenario

Order API đổi `status` từ string sang object. Provider unit tests pass, nhưng mobile client cũ crash. Contract verification trong CI phát hiện breaking shape trước deploy.

## 6. Failure scenario & troubleshooting

**Symptom** → contract tests pass nhưng integration vẫn fail. **Evidence** → schema đúng nhưng auth/rate-limit/business semantics khác. **Hypothesis** → contract quá hẹp. **Diagnosis** → compare actual failure với modeled contract. **Fix** → thêm meaningful interaction/semantic assertion. **Verification** → reproduce incident in contract/integration suite.

## 7. Common mistakes

Snapshot toàn payload khiến test brittle; contract test thay toàn bộ integration test; mock provider behavior khác Production; version artifact không gắn provider/consumer release.

## 8. Alternatives

OpenAPI schema checks tốt cho structural compatibility. E2E cần cho critical journeys. Integration tests cần cho infrastructure behavior. Các lớp bổ sung nhau.

## 9. Trade-offs

### Advantages
Feedback nhanh và ownership boundary rõ.
### Costs / Risks
Contract lifecycle/tooling overhead và false confidence nếu chỉ test shape.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu public API contract.
### Middle
Viết integration/contract assertions.
### Senior
Thiết kế compatibility và provider verification.
### Technical Lead / Architect
Quyết định test layer nào bảo vệ boundary nào.

## 11. Key takeaway

- Contract tests bảo vệ integration boundary, không toàn system behavior.
- Schema compatibility chưa đủ cho semantic compatibility.
- Test strategy cần unit + integration + contract + selective E2E.

# 10. Optimizely CMS content modeling: reusable nhưng có governance

## 1. What is it?

Content modeling định nghĩa các content types, properties, blocks/pages và composition rules mà editor dùng để tạo nội dung. Mental model: CMS model là **editorial domain model**, không phải generic JSON/database để nhét mọi application state.

## 2. Why does it exist?

Hard-code content buộc developer deploy cho mỗi thay đổi editorial. Nhưng model quá generic khiến editor khó dùng, validation yếu và frontend phải đoán semantics.

## 3. How does it work?

```text
Editor
 -> Content Type (Page/Block)
 -> validated properties
 -> published content version
 -> rendering/API delivery
 -> cache/CDN
```

Optimizely content types trong .NET cung cấp strongly modeled fields và editorial metadata/workflow.

## 4. Practical implementation

```csharp
[ContentType(DisplayName = "Hero Block", GUID = "11111111-1111-1111-1111-111111111111")]
public class HeroBlock : BlockData
{
    [Display(Name = "Heading", Order = 10)]
    public virtual string? Heading { get; set; }

    [Display(Name = "Body", Order = 20)]
    public virtual XhtmlString? Body { get; set; }
}
```

Stable GUID/content-type evolution cần được xem như compatibility concern.

## 5. Real production scenario

Marketing cần Hero ở nhiều landing pages. Reusable block cho editor reuse composition, nhưng pricing/inventory vẫn đến commerce service thay vì copy vào CMS rồi stale.

## 6. Failure scenario & troubleshooting

**Symptom** → publish content mới nhưng site vẫn hiển thị cũ. **Evidence** → CMS version đúng, origin/cache/CDN response cũ. **Hypothesis** → invalidation boundary sai. **Diagnosis** → trace CMS publish → app cache → CDN. **Fix** → explicit cache keys/purge strategy. **Verification** → publish test và quan sát từng layer.

## 7. Common mistakes

Một “UniversalBlock” hàng chục optional fields; lưu transactional data trong CMS; coupling rendering trực tiếp vào editor labels; breaking content-type changes không migration; cache không gắn publish lifecycle.

## 8. Alternatives

Headless CMS tách delivery/rendering mạnh hơn; traditional rendering đơn giản hơn cho server-driven site. Static configuration phù hợp nội dung không cần editorial workflow.

## 9. Trade-offs

### Advantages
Editor autonomy, reuse, workflow/versioning.
### Costs / Risks
Model governance, migration, cache invalidation và editor UX trở thành engineering concerns.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu page/block/content type.
### Middle
Model reusable content và validation.
### Senior
Thiết kế caching, migration, delivery contract.
### Technical Lead / Architect
Quyết định dữ liệu nào thuộc CMS, commerce/domain service hay search; giữ ownership boundary rõ.

## 11. Key takeaway

- CMS model phục vụ editorial domain.
- Reuse không đồng nghĩa generic hóa vô hạn.
- Content ownership, cache và migration phải được thiết kế cùng nhau.
