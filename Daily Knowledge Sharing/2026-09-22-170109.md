# 1. ASP.NET Core DI lifetimes: captive dependency và lifetime boundary

## 1. What is it?

Mental model quan trọng của Dependency Injection lifetime không phải là “cách đăng ký service”, mà là **ai sở hữu lifetime của object và object đó được phép giữ state trong bao lâu**.

ASP.NET Core có ba lifetime phổ biến: `Singleton` sống cùng application container, `Scoped` thường sống trong một HTTP request, và `Transient` được tạo theo lần resolve. Captive dependency xuất hiện khi một object sống lâu giữ reference tới dependency đáng lẽ phải sống ngắn hơn, điển hình `Singleton → Scoped`.

## 2. Why does it exist?

Object có lifetime khác nhau vì tài nguyên và state có semantics khác nhau. `DbContext` cần unit-of-work scope ngắn; stateless metadata cache có thể sống lâu; lightweight formatter có thể transient.

Nếu lifetime bị trộn sai, vấn đề không chỉ là memory. Ta có thể giữ `DbContext` quá lâu, dùng state của request cũ, chia sẻ object không thread-safe giữa nhiều requests hoặc giữ connection/resource ngoài boundary dự kiến.

## 3. How does it work?

Root service provider tạo singleton. Mỗi request tạo một scope riêng và resolve scoped services trong scope đó.

```text
Root container
 ├── Singleton A ------------------------- lifetime app
 │      └── [không nên giữ Scoped B]
 ├── Request scope #1
 │      └── Scoped B1
 └── Request scope #2
        └── Scoped B2
```

Nếu singleton capture scoped object từ một scope, object đó không còn tuân theo request boundary về mặt sử dụng, dù container có thể phát hiện một số trường hợp khi scope validation bật.

## 4. Practical implementation

Sai:

```csharp
builder.Services.AddDbContext<AppDbContext>();
builder.Services.AddSingleton<ReportScheduler>();

public sealed class ReportScheduler(AppDbContext db)
{
    public Task RunAsync(CancellationToken ct) => db.Reports.CountAsync(ct);
}
```

Với singleton/background component cần scoped dependency, tạo scope cho từng unit of work:

```csharp
public sealed class ReportScheduler(IServiceScopeFactory scopeFactory)
{
    public async Task RunAsync(CancellationToken ct)
    {
        await using var scope = scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var count = await db.Reports.CountAsync(ct);
    }
}
```

Boundary ở đây là **một lần chạy job**, không phải lifetime của scheduler.

## 5. Real production scenario

Một `BackgroundService` poll queue liên tục. Nếu nó giữ một `DbContext` từ lúc process start, change tracker tăng dần, entity cũ bị giữ, connection behavior khó đoán và concurrent processing có thể đụng thread-safety. Tạo scope cho từng message/batch khiến unit of work và disposal rõ ràng.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi concurrency của `DbContext`, memory tăng hoặc dữ liệu request-specific xuất hiện sai request.

**Evidence** → inspect registrations và object graph; log instance IDs; bật scope validation ở môi trường phù hợp.

**Hypothesis** → long-lived service capture short-lived dependency.

**Diagnosis** → trace dependency chain từ singleton/background worker tới scoped service.

**Fix** → sửa lifetime hoặc tạo explicit scope tại đúng work boundary.

**Verification** → concurrency test nhiều requests/jobs và kiểm tra disposal/state isolation.

## 7. Common mistakes

- Đổi mọi service thành singleton để “nhanh hơn”.
- Inject `IServiceProvider` khắp nơi rồi resolve tùy tiện, biến DI thành Service Locator.
- Nghĩ transient luôn thread-safe vì được tạo nhiều lần.
- Tạo scope nhưng giữ object resolved ra ngoài scope.
- Đăng ký stateful service singleton mà không thiết kế synchronization.

## 8. Alternatives

Nếu component không cần state scoped, tách dependency thành stateless singleton-safe abstraction. `IDbContextFactory<T>` hữu ích khi cần tạo `DbContext` theo unit of work ngoài request scope, nhưng vẫn phải dispose đúng.

## 9. Trade-offs

### Advantages

Lifetime đúng làm ownership, disposal và concurrency semantics rõ ràng.

### Costs / Risks

Quá nhiều scope thủ công làm code phức tạp; abstraction sai có thể che lifecycle thực tế của resource.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Singleton/Scoped/Transient là lifetime, không phải performance level.

### Middle

Chọn lifetime đúng, tránh capture scoped service và biết tạo scope trong worker.

### Senior

Review object graph theo thread-safety, disposal, state ownership và resource lifetime.

### Technical Lead / Architect

Đặt lifetime boundary theo unit of work và hosting model; không để container configuration thay thế thiết kế ownership.

## 11. Key takeaway

- Lifetime là ownership boundary.
- Long-lived object không nên vô tình giữ short-lived state.
- Background processing cần explicit unit-of-work scope.

# 2. REST API idempotency key: chống duplicate side effect khi client retry

## 1. What is it?

Idempotency key là identifier do client gửi cùng một logical command để server nhận biết các lần gửi lại thuộc **cùng một operation**, từ đó không tạo side effect lần hai.

Nó đặc biệt quan trọng với `POST` tạo payment, order, booking hoặc workflow command vốn không tự nhiên idempotent.

## 2. Why does it exist?

Distributed system có ambiguity: client timeout không cho biết server chưa xử lý hay đã commit nhưng response bị mất. Nếu client retry `POST /payments`, server có thể charge hai lần.

“Không retry” cũng không giải quyết tốt vì user không biết operation đã thành công hay chưa. Idempotency biến retry thành protocol có semantics rõ.

## 3. How does it work?

```text
Client -- POST key=abc --> API -- commit --> DB
Client <-- response X network lost
Client -- POST key=abc --> API -- lookup abc --> return stored result
```

Server lưu key cùng request fingerprint, trạng thái và kết quả. Cùng key + cùng logical request trả lại kết quả trước; cùng key + payload khác phải bị reject.

## 4. Practical implementation

Một schema đơn giản:

```sql
CREATE TABLE IdempotencyRequests (
    IdempotencyKey varchar(100) PRIMARY KEY,
    RequestHash char(64) NOT NULL,
    StatusCode int NULL,
    ResponseBody nvarchar(max) NULL,
    CreatedAt datetime2 NOT NULL
);
```

Trong ASP.NET Core, transaction cần atomic giữa việc claim key và business state khi có thể. Unique constraint là lớp bảo vệ cuối trước concurrent duplicate requests.

```csharp
var key = request.Headers["Idempotency-Key"].ToString();
if (string.IsNullOrWhiteSpace(key))
    return Results.BadRequest();

// Claim key + execute command + persist result using a transactional strategy.
```

## 5. Real production scenario

Mobile checkout gửi create-order qua mạng 4G. Server commit order nhưng response timeout. App retry sau 2 giây. Với idempotency key, lần hai nhận cùng `OrderId`; không có key, inventory reservation và payment workflow có thể chạy hai lần.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate orders có timestamps cách nhau vài giây.

**Evidence** → cùng client correlation nhưng hai request IDs; retry xảy ra sau timeout.

**Hypothesis** → command không có idempotency boundary.

**Diagnosis** → kiểm tra API gateway/client retry và unique business constraints.

**Fix** → idempotency key + atomic persistence + downstream idempotency.

**Verification** → fault injection làm mất response sau commit rồi retry cùng key.

## 7. Common mistakes

- Dùng request ID mới cho mỗi retry rồi gọi đó là idempotency.
- Chỉ cache response in-memory nên scale-out mất deduplication.
- Không kiểm tra payload khi reuse key.
- Giữ key vô hạn không có retention policy.
- Nghĩ idempotency ở API tự động làm downstream payment provider idempotent.

## 8. Alternatives

Natural idempotency bằng resource identifier do client chọn (`PUT /orders/{id}`) có thể đơn giản hơn. Unique business constraint bảo vệ một số invariant nhưng không luôn tái tạo được response semantics.

## 9. Trade-offs

### Advantages

Cho phép retry an toàn hơn và xử lý network ambiguity rõ ràng.

### Costs / Risks

Cần storage, retention, request hashing và concurrency control; boundary giữa API và downstream vẫn phải thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không có nghĩa operation thất bại.

### Middle

Implement key validation, unique constraint và replay result.

### Senior

Xử lý concurrent duplicates, in-progress state, retention và downstream side effects.

### Technical Lead / Architect

Định nghĩa end-to-end retry/idempotency contract cho các command có giá trị kinh doanh cao.

## 11. Key takeaway

- Retry và idempotency phải được thiết kế cùng nhau.
- Timeout tạo trạng thái “unknown”, không phải “failed”.
- Unique constraint/transaction là phần correctness, cache chỉ là optimization.

# 3. PostgreSQL MVCC và VACUUM: vì sao UPDATE không đơn giản là ghi đè row

## 1. What is it?

PostgreSQL dùng Multi-Version Concurrency Control (MVCC): transaction nhìn snapshot phù hợp thay vì mọi reader/writer tranh một phiên bản row duy nhất. `UPDATE` thường tạo row version mới; version cũ trở thành dead tuple sau khi không transaction nào còn cần nó. `VACUUM` thu hồi không gian có thể tái sử dụng và duy trì metadata cần thiết.

## 2. Why does it exist?

Nếu reader phải khóa writer hoặc ngược lại cho mọi truy cập, concurrency giảm mạnh. MVCC cho phép reader ổn định hơn trong khi writer tiến hành thay đổi.

Đổi lại, old versions không thể biến mất ngay vì transaction cũ có thể vẫn cần snapshot đó.

## 3. How does it work?

```text
T1 snapshot sees row v1
T2 UPDATE: v1 -> dead-for-future + v2
T1 still sees v1
T1 ends
VACUUM can reclaim obsolete tuple space
```

Autovacuum chạy dựa trên thresholds và activity. Long-running transaction có thể giữ horizon cũ, khiến dead tuples chưa reclaim được.

## 4. Practical implementation

Điều tra bằng statistics thay vì chạy `VACUUM FULL` ngay:

```sql
SELECT relname, n_live_tup, n_dead_tup,
       last_autovacuum, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Tìm long transaction:

```sql
SELECT pid, now() - xact_start AS age, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

## 5. Real production scenario

Một worker mở transaction rồi stream xử lý hàng giờ. Bảng orders bị update liên tục. Autovacuum chạy nhưng không thể dọn nhiều tuple vì snapshot cũ vẫn active; table/index bloat tăng và query latency xấu dần.

## 6. Failure scenario & troubleshooting

**Symptom** → storage và scan cost tăng dù số business rows gần như không đổi.

**Evidence** → `n_dead_tup` cao, transaction age lớn, autovacuum activity có nhưng reclaim hạn chế.

**Hypothesis** → long-running transaction giữ old versions.

**Diagnosis** → correlate `pg_stat_activity`, table stats và workload update.

**Fix** → rút ngắn transaction, tune autovacuum cho bảng hot nếu cần, xử lý root workload.

**Verification** → dead tuple ratio giảm và query I/O/latency cải thiện.

## 7. Common mistakes

- Nghĩ MVCC nghĩa là không có lock.
- Tắt autovacuum vì thấy nó dùng I/O.
- Chạy `VACUUM FULL` production mà không hiểu lock/space implications.
- Giữ transaction mở qua network/user think-time.
- Chỉ nhìn row count mà bỏ qua dead tuples và bloat.

## 8. Alternatives

Các database khác triển khai versioning/undo khác nhau. SQL Server có row versioning isolation tùy cấu hình; không nên áp mental model PostgreSQL nguyên xi sang engine khác.

## 9. Trade-offs

### Advantages

Reader/writer concurrency tốt và snapshot semantics mạnh.

### Costs / Risks

Dead tuples, vacuum overhead, transaction ID maintenance và operational tuning trở thành phần của hệ thống.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một logical row có thể có nhiều physical versions.

### Middle

Biết xem transaction và table statistics.

### Senior

Liên hệ long transaction, bloat, vacuum, index và query latency.

### Technical Lead / Architect

Thiết kế transaction boundary và batch processing phù hợp MVCC behavior, không chỉ business correctness.

## 11. Key takeaway

- PostgreSQL UPDATE tạo versioning consequences.
- Long transaction có thể gây hậu quả xa hơn lock duration.
- VACUUM là phần bình thường của engine, không phải cleanup tùy chọn.

# 4. Redis cache stampede: single-flight, TTL jitter và stale-while-revalidate

## 1. What is it?

Cache stampede xảy ra khi nhiều requests cùng miss một hot key và đồng thời truy cập origin/database để rebuild cùng dữ liệu. Cache vốn nhằm giảm tải lại trở thành cơ chế đồng bộ một “đợt tấn công” vào dependency.

## 2. Why does it exist?

TTL tạo thời điểm hết hạn. Nếu hot key có 20.000 requests/s, khoảnh khắc key expire có thể khiến hàng nghìn request cùng query database trước khi entry mới được ghi.

## 3. How does it work?

```text
Hot key expires
  ├─ request 1 -> DB
  ├─ request 2 -> DB
  ├─ request 3 -> DB
  └─ ...       -> DB
```

Single-flight chỉ cho một worker refresh; TTL jitter tránh nhiều keys expire cùng lúc; stale-while-revalidate cho phép trả dữ liệu cũ trong một cửa sổ chấp nhận được trong khi refresh nền.

## 4. Practical implementation

Trong một instance, có thể coalesce bằng keyed lock/semaphore. Với scale-out, cần cân nhắc distributed coordination hoặc thiết kế stale cache.

```csharp
var value = await cache.GetStringAsync(key, ct);
if (value is not null) return Deserialize(value);

await gate.WaitAsync(ct);
try
{
    value = await cache.GetStringAsync(key, ct);
    if (value is not null) return Deserialize(value);

    var fresh = await repository.LoadAsync(ct);
    await cache.SetStringAsync(key, Serialize(fresh),
        new DistributedCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
        }, ct);
    return fresh;
}
finally { gate.Release(); }
```

Double-check sau khi lấy gate tránh rebuild lần nữa.

## 5. Real production scenario

Homepage e-commerce cache promotion catalog 5 phút. Deploy lúc traffic peak làm hàng chục app instances cùng cold cache. Nếu mỗi instance lập tức query SQL, connection pool và database CPU spike trước khi cache kịp warm.

## 6. Failure scenario & troubleshooting

**Symptom** → DB latency spike đúng chu kỳ TTL.

**Evidence** → Redis miss rate và DB QPS tăng đồng thời; spike có periodicity.

**Hypothesis** → synchronized expiration/stampede.

**Diagnosis** → inspect hot keys, TTL distribution và cache miss traces.

**Fix** → jitter, single-flight, stale serving hoặc proactive refresh tùy freshness requirement.

**Verification** → load test qua expiration boundary, không chỉ warm-cache steady state.

## 7. Common mistakes

- Thêm distributed lock cho mọi key dù cost lớn hơn benefit.
- Lock không có timeout/failure strategy.
- Mọi key cùng TTL chính xác.
- Redis outage làm application fail hoàn toàn dù DB còn sống.
- Cache null/error quá lâu.

## 8. Alternatives

Local `IMemoryCache` giảm network cost nhưng mỗi instance có state riêng. CDN phù hợp public response. Không cache có thể là lựa chọn đúng nếu origin đủ nhanh và đơn giản hơn.

## 9. Trade-offs

### Advantages

Coalescing và stale serving bảo vệ origin, đặc biệt với hot keys.

### Costs / Risks

Thêm consistency semantics, coordination và stale-data policy; distributed lock có thể trở thành dependency mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu miss không phải lúc nào cũng chỉ là một DB query.

### Middle

Implement double-check, TTL và metrics hit/miss.

### Senior

Thiết kế jitter, stale window, failure fallback và hot-key strategy.

### Technical Lead / Architect

Quyết định freshness budget và cache ownership; hỏi liệu Redis có đang trở thành critical path không cần thiết.

## 11. Key takeaway

- Test cache tại expiration boundary.
- TTL là correctness/performance policy, không chỉ một con số.
- Cache phải bảo vệ origin cả khi miss và khi Redis gặp sự cố.

# 5. Modular Monolith: module boundary, data ownership và transaction boundary

## 1. What is it?

Modular Monolith là một deployable application nhưng được chia thành business modules có boundary rõ về code, dependency và data ownership. Nó không đơn giản là “một monolith có nhiều folders”.

Mental model: **deployment chung, ownership tách**.

## 2. Why does it exist?

Một monolith không có boundary dễ thành shared-everything: mọi module query bảng của nhau, gọi internal class tùy ý và sửa một feature gây ripple toàn hệ thống. Microservices ép boundary mạnh hơn nhưng thêm network, deployment, observability và distributed consistency cost.

Modular Monolith tìm điểm giữa: boundary logic mạnh mà chưa trả distributed-systems tax.

## 3. How does it work?

```text
Single deployable
├── Orders module ---- owns Orders data
├── Catalog module --- owns Catalog data
└── Billing module --- owns Billing data

Orders -> Billing contract/event
Orders -X-> Billing internal tables/classes
```

Modules có public contract nhỏ; internals không được tham chiếu tùy tiện. Database có thể cùng physical server/database nhưng ownership logic vẫn tách.

## 4. Practical implementation

Trong .NET solution, có thể dùng assemblies/projects để compiler giúp enforce boundary:

```text
Modules.Orders.Contracts
Modules.Orders.Application
Modules.Orders.Infrastructure
Modules.Billing.Contracts
Modules.Billing.Application
Modules.Billing.Infrastructure
Host
```

Architecture tests có thể kiểm tra `Orders` không reference `Billing.Infrastructure`.

## 5. Real production scenario

SaaS ban đầu có 8 engineers và một deployment pipeline. Orders, Billing, Notifications thay đổi ở tốc độ khác nhau nhưng chưa cần scale/deploy độc lập. Modular Monolith giữ transaction local và operations đơn giản trong khi chuẩn bị boundary nếu sau này cần extract.

## 6. Failure scenario & troubleshooting

**Symptom** → “module” nào cũng join trực tiếp bảng của module khác.

**Evidence** → thay schema Billing làm Orders build/runtime fail; cross-module SQL phổ biến.

**Hypothesis** → boundary chỉ tồn tại ở folder naming.

**Diagnosis** → dependency graph + database access ownership.

**Fix** → public contracts, module-owned persistence access, integration events/API nội bộ khi cần.

**Verification** → architecture tests và change-impact review.

## 7. Common mistakes

- Tạo một `Shared` project chứa mọi domain model.
- Generic repository dùng chung xuyên modules.
- Bắt chước microservices bằng internal HTTP calls trong cùng process.
- Cấm mọi transaction cross-module dù business invariant thực sự cần atomicity.
- Thiết kế 30 modules trước khi hiểu domain.

## 8. Alternatives

Layered monolith đơn giản hơn cho domain nhỏ. Microservices phù hợp khi independent deployment/scaling/ownership mang giá trị đủ lớn. Modulith không phải bước bắt buộc trước microservices.

## 9. Trade-offs

### Advantages

Operational simplicity, local transactions, refactoring dễ hơn distributed system và vẫn có change isolation tốt.

### Costs / Risks

Boundary cần discipline/tooling; shared database làm việc “đi đường tắt” rất dễ; deployment vẫn coupled.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module theo business capability, không theo technical folder.

### Middle

Tôn trọng public contract và data ownership.

### Senior

Thiết kế cross-module communication và transaction semantics.

### Technical Lead / Architect

Quyết định khi nào modular monolith đủ tốt và khi nào independent deployment thực sự biện minh cho extraction.

## 11. Key takeaway

- Module boundary quan trọng hơn folder structure.
- Shared process không có nghĩa shared internals/data ownership.
- Microservices chỉ đáng giá khi lợi ích vượt operational complexity.

# 6. Azure Key Vault + Managed Identity: secret retrieval, rotation và failure boundary

## 1. What is it?

Azure Key Vault lưu secrets/keys/certificates; Managed Identity cho Azure workload lấy token từ Microsoft Entra ID mà không cần nhúng client secret vào application. Kết hợp hai thứ giúp app authenticate tới Key Vault bằng identity của workload rồi đọc secret theo quyền được cấp.

## 2. Why does it exist?

Nếu connection string/API key nằm trong source, image hoặc pipeline variable được copy rộng, rotation khó và blast radius lớn. Managed Identity loại bỏ bootstrap secret dùng để lấy secret khác.

## 3. How does it work?

```text
App Service / VM / Container
        │ workload identity
        ▼
Microsoft Entra ID ---- token ----> App
        │
        ▼
Key Vault <---- authenticated request
```

Authorization tại vault quyết định identity được đọc secret nào. Network controls như Private Endpoint có thể thu hẹp đường truy cập nhưng làm DNS/network vận hành phức tạp hơn.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(configuration["KeyVaultUri"]!),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("PaymentApiKey", ct);
```

Trong production Azure, `DefaultAzureCredential` có thể dùng Managed Identity; local development có developer credential phù hợp. Không log secret value.

## 5. Real production scenario

Payment API key được rotate. Nếu app chỉ load secret lúc startup, instance cũ có thể giữ value cũ cho tới restart. Nếu đọc Key Vault mỗi request, latency/cost/dependency tăng. Thực tế thường cần cache có refresh strategy và overlap window với provider.

## 6. Failure scenario & troubleshooting

**Symptom** → deploy thành công nhưng startup trả 500 vì không đọc được vault.

**Evidence** → `403` khác `timeout/DNS failure`; identity ID và Key Vault audit logs.

**Hypothesis** → RBAC sai hoặc private DNS/network sai.

**Diagnosis** → tách authentication, authorization và connectivity thành ba lớp kiểm tra.

**Fix** → least-privilege role/access, DNS/network route đúng, retry bounded cho transient failures.

**Verification** → restart/scale-out và rotation test thực tế.

## 7. Common mistakes

- Cho app quyền quản trị toàn vault khi chỉ cần `Get` secret.
- Dùng Managed Identity nhưng vẫn lưu credential dự phòng trong config production.
- Gọi Key Vault trên mọi request.
- Rotation secret mà không thiết kế consumer refresh.
- Log exception chứa secret/config nhạy cảm.

## 8. Alternatives

Platform configuration có thể đủ cho non-secret settings. Certificate/managed service authentication có thể loại bỏ secret hoàn toàn. Kubernetes workload identity + secret store có model khác nhưng cùng mục tiêu giảm static credentials.

## 9. Trade-offs

### Advantages

Giảm secret sprawl, centralized audit/rotation và loại bỏ credential bootstrap trong Azure workload.

### Costs / Risks

Key Vault/network/identity trở thành startup/runtime dependency; private networking tăng operational complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt identity với secret.

### Middle

Dùng `DefaultAzureCredential`, RBAC và không log secrets.

### Senior

Thiết kế caching, rotation, failure/retry và private connectivity.

### Technical Lead / Architect

Giảm số secret cần tồn tại, xác định ownership/rotation SLO và blast radius thay vì chỉ “đưa hết vào vault”.

## 11. Key takeaway

- Managed Identity tốt hơn việc bảo vệ một static client secret khác.
- Rotation chỉ hoàn tất khi consumer thực sự nhận credential mới.
- Phân biệt lỗi identity, authorization và network khi troubleshoot.

# 7. .NET ThreadPool starvation: nhận diện sync-over-async dưới production load

## 1. What is it?

ThreadPool starvation xảy ra khi work cần thread nhưng các worker threads hiện tại bị giữ/block đủ lâu khiến queue tăng nhanh hơn ThreadPool có thể bổ sung capacity. Trong ASP.NET Core, nguyên nhân kinh điển là blocking trên asynchronous I/O bằng `.Result`, `.Wait()` hoặc synchronous dependency call dưới concurrency cao.

## 2. Why does it exist?

Thread là tài nguyên hữu hạn và tạo thêm thread có cost. Async I/O cho phép trả thread về pool trong lúc chờ network/database. Nếu code block thread để chờ I/O, scalability advantage này mất đi.

## 3. How does it work?

```text
1000 requests
  -> each blocks a worker waiting for I/O
  -> ThreadPool queue grows
  -> continuations/new requests wait for workers
  -> latency explodes although CPU may not be 100%
```

ThreadPool hill-climbing có thể tăng workers nhưng phản ứng không tức thời và quá nhiều threads gây context switching/memory overhead.

## 4. Practical implementation

Sai:

```csharp
public IActionResult Get()
{
    var data = _client.GetStringAsync("inventory").Result;
    return Ok(data);
}
```

Đúng:

```csharp
public async Task<IActionResult> Get(CancellationToken ct)
{
    var data = await _client.GetStringAsync("inventory", ct);
    return Ok(data);
}
```

Dùng `dotnet-counters`/runtime metrics để quan sát ThreadPool thread count, queue length, completed work item rate cùng request latency.

## 5. Real production scenario

Endpoint mới gọi legacy SDK synchronous mất 800 ms. Ở staging 5 users không vấn đề; production 500 concurrent requests làm queue tăng, p99 lên hàng chục giây dù database và CPU chưa saturated.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng mạnh theo concurrency, CPU trung bình không quá cao.

**Evidence** → ThreadPool queue length tăng, thread count leo, traces có khoảng chờ lớn.

**Hypothesis** → blocking work/sync-over-async.

**Diagnosis** → collect trace/thread stacks; tìm `.Wait`, `.Result`, blocking I/O hoặc long CPU work trên request threads.

**Fix** → async end-to-end; isolate unavoidable blocking work bằng bounded concurrency thay vì `Task.Run` vô hạn.

**Verification** → load test cùng concurrency và so sánh queue/p95/p99.

## 7. Common mistakes

- Thêm `Task.Run` quanh mọi synchronous I/O rồi gọi đó là async.
- Chỉ tăng minimum threads để che root cause.
- Nhầm starvation với CPU saturation.
- Dùng unbounded parallelism làm vấn đề nặng hơn.
- Không propagate cancellation nên abandoned requests vẫn giữ work.

## 8. Alternatives

Nếu SDK chỉ synchronous, bounded worker pool/queue có thể bảo vệ request path. Với CPU-bound work lớn, background queue hoặc compute service có thể phù hợp hơn request thread.

## 9. Trade-offs

### Advantages

Async I/O cho throughput tốt với ít blocked threads.

### Costs / Risks

Async không làm CPU work nhanh hơn; concurrency không bounded vẫn có thể làm downstream collapse.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` không giữ thread chỉ để chờ I/O.

### Middle

Viết async end-to-end và tránh `.Result/.Wait()`.

### Senior

Đọc runtime counters/traces và phân biệt CPU saturation, pool starvation, dependency latency.

### Technical Lead / Architect

Đặt concurrency boundary cho legacy/blocking dependencies và performance-test theo realistic concurrency.

## 11. Key takeaway

- Low CPU không loại trừ ThreadPool starvation.
- Async I/O chỉ hiệu quả nếu call chain không bị block.
- Chẩn đoán bằng queue/thread/trace evidence, không bằng đoán.

# 8. Contract Testing: bảo vệ integration contract mà không biến test thành E2E suite

## 1. What is it?

Contract testing xác minh producer và consumer đồng ý về interface: request/response schema, status semantics, required fields hoặc message shape. Nó tập trung vào **boundary compatibility**, không kiểm tra toàn bộ user journey như E2E.

## 2. Why does it exist?

Unit test có thể xanh ở cả hai services nhưng integration vẫn vỡ nếu producer rename field hoặc thay enum. Full E2E phát hiện được nhưng chậm, brittle và thường cần nhiều environment/data coordination.

## 3. How does it work?

Consumer expectations được mô tả thành contract hoặc producer schema được validate ngược với consumers. Pipeline chặn breaking change trước deployment.

```text
Consumer expectation
       │
       ▼
   Contract artifact
       │
       ▼
Producer verification
```

## 4. Practical implementation

Với HTTP API, OpenAPI diff là lớp cơ bản nhưng chưa đủ semantic. Integration test có thể pin behavior quan trọng:

```csharp
var response = await client.GetAsync("/api/orders/123");
response.StatusCode.Should().Be(HttpStatusCode.OK);

var order = await response.Content.ReadFromJsonAsync<OrderContract>();
order!.Id.Should().Be("123");
order.Status.Should().BeOneOf("Pending", "Paid", "Cancelled");
```

Contract nên tập trung fields consumer thực sự phụ thuộc, tránh snapshot toàn response nếu không cần.

## 5. Real production scenario

Orders API thêm enum value `PartiallyShipped`. Backend change backward-compatible theo JSON schema nhưng frontend dùng exhaustive switch không có fallback và crash. Contract cần phản ánh semantic compatibility, không chỉ field existence.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment producer phá consumer dù producer tests xanh.

**Evidence** → consumer phụ thuộc behavior không được encode trong contract.

**Hypothesis** → contract quá structural hoặc stale.

**Diagnosis** → so sánh incident với contract coverage.

**Fix** → thêm semantic expectation ở boundary có rủi ro cao.

**Verification** → replay breaking producer change và đảm bảo pipeline fail.

## 7. Common mistakes

- Snapshot mọi JSON byte làm test quá brittle.
- Mock producer rồi gọi đó là contract verification.
- Contract không version/không publish cùng pipeline.
- Cố thay thế toàn bộ E2E bằng contract tests.
- Test implementation detail thay vì observable boundary.

## 8. Alternatives

Integration test với real dependency phù hợp khi services deploy cùng nhau. E2E cần cho critical journeys. Schema registry hữu ích cho event/message contracts. Không có một tầng test thay thế mọi tầng khác.

## 9. Trade-offs

### Advantages

Feedback nhanh hơn E2E, ownership rõ và phát hiện breaking integration sớm.

### Costs / Risks

Cần contract lifecycle/tooling; semantic assumptions khó encode đầy đủ; stale contracts tạo false confidence.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu test boundary khác unit test implementation.

### Middle

Viết contract cho request/response/message quan trọng.

### Senior

Phân loại backward compatibility và semantic breaking changes.

### Technical Lead / Architect

Thiết kế test portfolio theo risk: unit + integration + contract + một lượng E2E có chủ đích.

## 11. Key takeaway

- Contract test bảo vệ compatibility, không bảo vệ toàn user journey.
- Test điều consumer thực sự phụ thuộc.
- Coverage percentage không nói contract có đúng risk hay không.

# 9. CDN/Akamai stale-while-revalidate: freshness, origin load và cache-control semantics

## 1. What is it?

`stale-while-revalidate` cho phép cache phục vụ response đã stale trong một khoảng thời gian trong khi cache refresh response từ origin ở background. Mental model: **freshness có thể là một budget**, không nhất thiết binary fresh/stale.

## 2. Why does it exist?

Khi một popular object hết TTL, request đầu tiên phải chờ origin; nhiều edge/request đồng thời có thể gây latency spike hoặc origin burst. Nếu business chấp nhận dữ liệu cũ thêm vài chục giây, serving stale giữ latency thấp trong lúc refresh.

## 3. How does it work?

Ví dụ:

```http
Cache-Control: public, max-age=60, stale-while-revalidate=30
```

Trong 60 giây response fresh. Sau đó cache có thể phục vụ stale trong cửa sổ 30 giây và trigger revalidation tùy cache/CDN implementation/policy.

```text
Browser -> CDN cache (stale but allowed) -> immediate response
              |
              +---- revalidate ----> Origin
```

CDN như Akamai có policy/config riêng; phải xác nhận behavior thực tế của property thay vì giả định header luôn được xử lý giống nhau.

## 4. Practical implementation

ASP.NET Core có thể set header cho public content phù hợp:

```csharp
context.Response.Headers.CacheControl =
    "public, max-age=60, stale-while-revalidate=30";
```

Quan trọng hơn syntax là xác định resource nào public, cache key có vary đúng query/header và purge strategy khi emergency update.

## 5. Real production scenario

CMS homepage hero thay đổi vài lần/ngày nhưng traffic rất lớn. Cho phép stale 30 giây giảm origin spikes và cải thiện tail latency. Checkout price endpoint thì không thể copy cùng policy vì freshness/correctness khác hẳn.

## 6. Failure scenario & troubleshooting

**Symptom** → editor publish content nhưng user vẫn thấy bản cũ lâu hơn dự kiến.

**Evidence** → inspect `Age`, cache headers, CDN cache status và purge logs.

**Hypothesis** → nhiều cache layers có TTL khác nhau hoặc purge không tới đúng cache key.

**Diagnosis** → trace Browser → CDN → reverse proxy → application.

**Fix** → thống nhất cache ownership, TTL/purge semantics và cache key.

**Verification** → publish synthetic change rồi đo propagation qua nhiều edge locations.

## 7. Common mistakes

- Cache authenticated/personalized response ở shared edge.
- Nghĩ browser TTL và CDN TTL luôn giống nhau.
- Purge URL nhưng quên variants/query keys.
- Đặt TTL rất thấp thay vì thiết kế invalidation.
- Không có observability cho hit/miss/stale/origin latency.

## 8. Alternatives

Hard TTL đơn giản hơn. Purge-on-publish phù hợp CMS freshness cao. Versioned static assets gần như loại bỏ invalidation ambiguity. Origin shielding giảm fan-out tới origin ở kiến trúc CDN phù hợp.

## 9. Trade-offs

### Advantages

Giảm tail latency và origin burst, tăng resilience khi origin chậm ngắn hạn.

### Costs / Risks

User có thể thấy stale content; debugging nhiều cache layers khó; semantics phụ thuộc CDN configuration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser cache, edge cache và origin là các tầng khác nhau.

### Middle

Đọc cache headers và kiểm tra hit/miss.

### Senior

Thiết kế cache key, purge, stale budget và incident diagnostics.

### Technical Lead / Architect

Xác định freshness SLO theo loại dữ liệu thay vì áp một cache policy toàn site.

## 11. Key takeaway

- Freshness là business/correctness decision.
- CDN cache phải được quan sát như một production component.
- `stale-while-revalidate` hữu ích khi stale window được chấp nhận rõ ràng.

# 10. RAG evaluation: đo retrieval và answer quality thay vì đánh giá bằng cảm giác

## 1. What is it?

RAG evaluation đo riêng chất lượng retrieval và chất lượng answer generation. Mental model: một câu trả lời sai có thể do **không lấy đúng evidence**, hoặc đã lấy đúng evidence nhưng model **suy luận/trình bày sai**. Nếu không tách hai tầng, team dễ chỉnh prompt cho lỗi thực ra nằm ở search/indexing.

## 2. Why does it exist?

Demo vài câu hỏi thủ công thường tạo false confidence. Khi corpus lớn, user phrasing đa dạng và tài liệu thay đổi, quality regression khó thấy nếu không có evaluation dataset và metrics.

## 3. How does it work?

```text
Question
  -> Retrieval -> retrieved chunks
       |              |
       |              +-> retrieval evaluation
       v
  LLM with context -> Answer
                       |
                       +-> groundedness / correctness evaluation
```

Retrieval có thể đo Recall@K/MRR/nDCG tùy bài toán. Answer layer cần groundedness, correctness, citation support và task-specific criteria. LLM-as-judge có thể hỗ trợ nhưng không nên là oracle duy nhất.

## 4. Practical implementation

Một eval case nên giữ expected evidence thay vì chỉ expected exact string:

```json
{
  "question": "Chính sách hoàn tiền enterprise là gì?",
  "relevantDocumentIds": ["refund-policy-v7"],
  "requiredFacts": [
    "30-day window",
    "approval required above threshold"
  ]
}
```

Pipeline chạy retrieval trước, ghi top-K document IDs/scores, sau đó generate answer và chấm groundedness/correctness. Mọi thay đổi embedding model, chunking, reranker hoặc prompt phải chạy lại eval set.

## 5. Real production scenario

Internal support assistant trả lời policy cũ. Prompt rất tốt nhưng vector index vẫn chứa document v5 ngang hàng v7. Answer evaluator thấy câu trả lời “có vẻ hợp lý”; retrieval evidence cho thấy source version sai. Root cause là document lifecycle/index metadata, không phải LLM.

## 6. Failure scenario & troubleshooting

**Symptom** → answer quality giảm sau khi đổi chunk size.

**Evidence** → Recall@5 giảm trong khi groundedness trên các case retrieve đúng vẫn ổn.

**Hypothesis** → chunking làm mất context/retrieval signal.

**Diagnosis** → compare retrieved chunks trước/sau theo fixed eval dataset.

**Fix** → điều chỉnh chunking/metadata/hybrid search/reranking dựa evidence.

**Verification** → eval offline rồi canary online với user feedback/production telemetry.

## 7. Common mistakes

- Chỉ đánh giá final answer.
- Dùng chính model production làm judge duy nhất rồi coi score tuyệt đối là sự thật.
- Eval set toàn happy path.
- Không version corpus/prompt/model/index config.
- Optimize token cost nhưng không đo quality regression.
- Cho model quyết định authorization dựa trên retrieved text.

## 8. Alternatives

Keyword/BM25 search có thể đủ cho corpus có terminology rõ. Hybrid retrieval kết hợp lexical + vector. Với dữ liệu nhỏ, curated deterministic lookup đôi khi tốt hơn RAG phức tạp.

## 9. Trade-offs

### Advantages

Evaluation tách bottleneck, hỗ trợ regression testing và làm model/index changes có engineering discipline.

### Costs / Risks

Gold dataset tốn công duy trì; judge có bias; metrics offline không phản ánh hoàn toàn production utility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG gồm retrieval và generation, không phải một black box.

### Middle

Log retrieved evidence, model response và version metadata; tạo repeatable eval cases.

### Senior

Phân tích Recall@K, reranking, groundedness, cost/latency và failure slices.

### Technical Lead / Architect

Định nghĩa quality gate, deterministic security boundary, corpus ownership và release process cho AI changes.

## 11. Key takeaway

- Tách retrieval quality khỏi generation quality.
- Eval dataset phải versioned và đại diện failure cases thực tế.
- LLM output vẫn cần deterministic boundaries cho authorization, security và financial correctness.
