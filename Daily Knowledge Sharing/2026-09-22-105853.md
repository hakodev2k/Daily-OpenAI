# 1. C# `IAsyncEnumerable<T>`: streaming dữ liệu mà không materialize toàn bộ result

## 1. What is it?

`IAsyncEnumerable<T>` biểu diễn một chuỗi phần tử được tạo bất đồng bộ theo thời gian. Mental model quan trọng: consumer không cần đợi producer tạo toàn bộ collection rồi mới bắt đầu xử lý; mỗi phần tử có thể được `await` và tiêu thụ dần.

## 2. Why does it exist?

`Task<List<T>>` buộc producer hoàn thành toàn bộ query/read trước khi trả dữ liệu. Với hàng trăm nghìn rows, cách này tăng memory, time-to-first-item và có thể tạo LOH/GC pressure. Streaming hữu ích khi consumer có thể xử lý tuần tự.

## 3. How does it work?

Compiler biến async iterator thành state machine. `await foreach` gọi `MoveNextAsync()` lặp lại; producer chỉ tiến tới phần tử tiếp theo khi consumer yêu cầu. Điều này tạo natural pull-based flow, nhưng không tự động tạo bounded buffering nếu downstream khác vẫn buffer toàn bộ.

## 4. Practical implementation

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    await foreach (var order in db.Orders
        .AsNoTracking()
        .OrderBy(x => x.Id)
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        yield return new OrderDto(order.Id, order.Total);
    }
}
```

Ở HTTP boundary, cần kiểm tra serializer/protocol có thực sự flush incrementally hay vẫn buffer.

## 5. Real production scenario

Một export service đọc 500.000 orders rồi ghi CSV trực tiếp vào Blob Storage. Streaming giúp memory gần như bounded theo buffer thay vì tỷ lệ với số rows.

## 6. Failure scenario & troubleshooting

**Symptom** → đã dùng `IAsyncEnumerable<T>` nhưng memory vẫn tăng mạnh. **Evidence** → downstream gọi `ToListAsync()` hoặc serializer/buffer giữ toàn bộ payload. **Hypothesis** → streaming boundary bị phá. **Diagnosis** → trace allocation và kiểm tra từng layer. **Fix** → stream end-to-end, giới hạn buffer và propagate cancellation. **Verification** → memory ổn định khi dataset tăng 10x.

## 7. Common mistakes

Cho rằng async stream tự tạo parallelism; enumerate hai lần trên nguồn không replay-safe; quên cancellation; giữ DbContext sống quá lâu; stream transaction dài làm giữ connection/lock lâu.

## 8. Alternatives

Pagination phù hợp API interactive. `Channel<T>` phù hợp producer/consumer concurrent có bounded buffer. `Task<List<T>>` vẫn đơn giản và đúng cho dataset nhỏ.

## 9. Trade-offs

### Advantages

Giảm peak memory và time-to-first-item; phù hợp pipeline lớn.

### Costs / Risks

Resource lifetime dài hơn; error có thể xảy ra sau khi response đã bắt đầu; retry khó hơn sau partial output.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu streaming khác materialization.

### Middle

Implement async iterator, cancellation và disposal đúng.

### Senior

Đánh giá connection lifetime, buffering, partial failure và backpressure.

### Technical Lead / Architect

Quyết định streaming boundary theo protocol, retry semantics và resource budget toàn pipeline.

## 11. Key takeaway

- Streaming chỉ hiệu quả khi end-to-end không re-buffer.
- Async stream không đồng nghĩa parallel processing.
- Resource lifetime và partial failure phải được thiết kế trước.

# 2. ASP.NET Core Request Timeouts: deadline budget thay vì timeout rời rạc ở từng dependency

## 1. What is it?

Request timeout là giới hạn tổng thời gian một request được phép tiêu thụ. Deadline budget là mental model mạnh hơn: request có một ngân sách thời gian chung, và mỗi dependency phải hoạt động bên trong ngân sách còn lại.

## 2. Why does it exist?

Nếu API timeout 5 giây nhưng SQL timeout 30 giây và HTTP dependency timeout 100 giây, request có thể chết ở client trong khi server vẫn giữ tài nguyên. Timeout không thống nhất tạo wasted work và retry amplification.

## 3. How does it work?

ASP.NET Core có thể áp timeout policy tại endpoint. Cancellation signal phải được propagate xuống EF Core/HttpClient. Downstream timeout nên nhỏ hơn deadline còn lại để application còn thời gian xử lý failure.

## 4. Practical implementation

```csharp
builder.Services.AddRequestTimeouts(options =>
{
    options.AddPolicy("interactive", TimeSpan.FromSeconds(3));
});

app.UseRequestTimeouts();

app.MapGet("/search", SearchAsync)
   .WithRequestTimeout("interactive");
```

Service methods nhận `CancellationToken` từ request và forward xuống mọi I/O operation.

## 5. Real production scenario

Search API gọi SQL rồi pricing service. SLO yêu cầu 2 giây. Nếu SQL đã tiêu 1.6 giây, không hợp lý bắt đầu remote call có timeout 5 giây rồi mong request vẫn đạt SLO.

## 6. Failure scenario & troubleshooting

**Symptom** → client timeout nhưng dependency telemetry tiếp tục. **Evidence** → trace parent kết thúc trước child spans. **Diagnosis** → cancellation/deadline không propagate. **Fix** → linked cancellation/deadline budget, dependency timeout bounded. **Verification** → abort/timeout request và xác nhận child operations kết thúc sớm.

## 7. Common mistakes

Timeout mọi thứ cùng một giá trị; retry trong deadline quá ngắn; catch cancellation thành 500; timeout critical side effect giữa chừng mà không có idempotency.

## 8. Alternatives

Queue/background processing phù hợp work dài. Circuit Breaker giảm calls vào dependency đang unhealthy nhưng không thay timeout.

## 9. Trade-offs

### Advantages

Bounded resource usage và predictable latency.

### Costs / Risks

Timeout quá aggressive tạo false failures; deadline propagation tăng contract complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout giới hạn resource lifetime.

### Middle

Propagate cancellation và cấu hình endpoint policy.

### Senior

Phân bổ timeout budget giữa dependencies và retries.

### Technical Lead / Architect

Thiết kế end-to-end deadline theo SLO thay vì cấu hình từng SDK độc lập.

## 11. Key takeaway

- Timeout phải được nhìn end-to-end.
- Dependency timeout phải nằm trong request budget.
- Cancellation propagation ngăn request đã chết tiếp tục tiêu thụ capacity.

# 3. EF Core `DbContext` pooling: giảm setup cost nhưng không được để request state rò rỉ

## 1. What is it?

`AddDbContextPool` tái sử dụng instance `DbContext` sau khi EF reset internal state. Nó khác database connection pooling: một cái reuse context object, cái kia reuse physical database connections.

## 2. Why does it exist?

Khởi tạo DbContext, services nội bộ và model-related state có overhead. Ở high-throughput workload, pooling có thể giảm allocation/setup cost sau khi query/database đã được tối ưu.

## 3. How does it work?

Context được lấy từ pool cho scope, dùng, reset rồi trả lại. Vì instance được reuse, state tùy biến gắn trực tiếp vào context có thể trở thành cross-request bug nếu không được quản lý đúng.

## 4. Practical implementation

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Không đặt mutable tenant/request state tùy tiện vào pooled context. Với multi-tenant query filters, dùng factory/scope design có lifecycle rõ và test isolation.

## 5. Real production scenario

API 10k RPS có DbContext rất ngắn. Profiling cho thấy context setup/allocation đáng kể sau khi SQL đã nhanh. Pooling giúp giảm allocation nhưng không chữa slow query hay connection exhaustion.

## 6. Failure scenario & troubleshooting

**Symptom** → hiếm khi tenant A thấy query filter của tenant B. **Evidence** → custom `TenantId` nằm trên pooled context instance. **Diagnosis** → mutable request state không reset đúng. **Fix** → tách request state khỏi reusable context hoặc dùng factory pattern an toàn. **Verification** → concurrent multi-tenant integration tests.

## 7. Common mistakes

Nhầm DbContext pool với connection pool; bật pooling trước profiling; lưu request-scoped state trên context; giữ context quá lâu; nghĩ pooling cho phép concurrent use một context.

## 8. Alternatives

`AddDbContext` thông thường đơn giản và đủ cho phần lớn hệ thống. `IDbContextFactory<T>` hữu ích khi cần tạo context theo unit of work ngoài request scope.

## 9. Trade-offs

### Advantages

Giảm allocation/setup overhead trong hot path phù hợp.

### Costs / Risks

Lifecycle khó hơn và bug state leakage nguy hiểm hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DbContext không thread-safe.

### Middle

Phân biệt context pooling và connection pooling.

### Senior

Benchmark allocation/throughput và kiểm tra state leakage.

### Technical Lead / Architect

Chỉ đưa pooling vào khi measurement chứng minh lợi ích và team hiểu lifecycle constraint.

## 11. Key takeaway

- DbContext pooling là optimization, không phải default requirement.
- Pooled instance không được mang request state ngoài kiểm soát.
- SQL/access pattern thường quan trọng hơn context allocation.

# 4. PostgreSQL `JSONB` + GIN index: linh hoạt schema nhưng vẫn phải thiết kế access pattern

## 1. What is it?

`JSONB` lưu JSON ở binary representation có thể query/index. GIN index phù hợp membership/containment trên nhiều keys/values. Nó cho phép một relational table giữ phần dữ liệu semi-structured mà không biến toàn bộ schema thành document store.

## 2. Why does it exist?

Một số attributes thay đổi theo product/category hoặc external payload. Tạo column cho mọi biến thể có thể khó quản lý; nhưng lưu raw text JSON làm query chậm và mất indexability.

## 3. How does it work?

```sql
CREATE INDEX ix_products_attrs
ON products USING GIN (attributes jsonb_path_ops);

SELECT id, name
FROM products
WHERE attributes @> '{"color":"black"}';
```

GIN index lưu inverted entries cho JSON structure/operator class phù hợp.

## 4. Practical implementation

Giữ fields dùng cho identity, joins, constraints và high-frequency sorting thành relational columns. Dùng `JSONB` cho extension attributes thực sự linh hoạt.

## 5. Real production scenario

Marketplace có electronics, tyres và accessories với thuộc tính khác nhau. Core product fields relational; category-specific specs ở `JSONB` giúp tránh hàng trăm nullable columns.

## 6. Failure scenario & troubleshooting

**Symptom** → table/index phình lớn và writes chậm. **Evidence** → GIN index size/write I/O cao; query chỉ dùng vài fields. **Diagnosis** → index toàn JSON cho workload không cần. **Fix** → expression index cho paths quan trọng hoặc normalize hot fields. **Verification** → compare plan, index size và write latency.

## 7. Common mistakes

Đưa mọi thứ vào JSONB; không có constraints cho critical fields; GIN index toàn document mặc định; dùng JSONB để né schema design.

## 8. Alternatives

Normalized tables cho strongly structured relational data; MongoDB cho document-centric aggregate; expression/generated columns cho một số JSON paths.

## 9. Trade-offs

### Advantages

Schema linh hoạt và queryable hơn raw JSON text.

### Costs / Risks

Validation, indexing và migration semantics phức tạp; index/write amplification.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu JSONB vẫn nằm trong relational database.

### Middle

Query operators và đọc execution plan.

### Senior

Thiết kế GIN/expression indexes theo workload.

### Technical Lead / Architect

Quyết định boundary giữa relational core và flexible attributes dựa invariants/access patterns.

## 11. Key takeaway

- JSONB không loại bỏ nhu cầu data modeling.
- Index phải theo query shape, không theo “có JSON”.
- Critical invariants nên giữ ở schema rõ ràng khi có thể.

# 5. Redis hot key: một key có thể phá scalability dù cluster còn rất nhiều capacity

## 1. What is it?

Hot key là key nhận tỷ lệ traffic bất thường lớn. Trong distributed Redis, một key thuộc một shard/node cụ thể; thêm nodes không tự chia một key thành nhiều owners.

## 2. Why does it exist?

Cache thường được kỳ vọng giảm load, nhưng skewed access có thể chuyển bottleneck từ database sang một Redis node/network path.

## 3. How does it work?

Nếu 40% requests đọc cùng `homepage:catalog`, slot chứa key đó chịu gần 40% cache traffic dù các shards khác rảnh. Throughput cluster tổng không phản ánh bottleneck per-key.

## 4. Practical implementation

Đo top keys/latency trước. Với immutable/small data có thể thêm near-cache `IMemoryCache` TTL ngắn trên mỗi app instance để hấp thụ hot reads; hoặc redesign key/data distribution nếu semantics cho phép.

## 5. Real production scenario

Flash sale khiến mọi request đọc cùng promotion configuration. Redis node CPU/network saturate, API latency tăng dù hit ratio 99%.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis cluster average CPU thấp nhưng một node latency cao. **Evidence** → per-node metrics và key access distribution. **Hypothesis** → hot key. **Diagnosis** → map key→slot/node. **Fix** → local cache, replication/read strategy hoặc redesign. **Verification** → per-node traffic cân bằng và p99 giảm.

## 7. Common mistakes

Chỉ nhìn cluster average; thêm shards rồi mong hot key tự chia; TTL đồng loạt gây stampede; cache object quá lớn.

## 8. Alternatives

CDN/output cache cho public response; in-process cache cho tiny read-mostly config; database trực tiếp nếu cache complexity không đáng.

## 9. Trade-offs

### Advantages

Redis vẫn cho low latency và shared cache semantics.

### Costs / Risks

Hot key tạo hidden single-shard bottleneck; multi-layer cache tăng stale-data complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu key được map tới shard.

### Middle

Đo hit rate và per-node metrics.

### Senior

Phân tích skew, TTL, payload size và fallback.

### Technical Lead / Architect

Quyết định liệu cache layer có đang giải đúng bottleneck hay tạo dependency mới.

## 11. Key takeaway

- Scale-out Redis không tự scale một hot key.
- Đo distribution, không chỉ average.
- Local/CDN caching có thể hấp thụ hot reads nếu freshness cho phép.

# 6. Domain Event vs Integration Event: tách transaction boundary khỏi cross-service contract

## 1. What is it?

Domain Event biểu diễn điều đã xảy ra có ý nghĩa trong domain boundary. Integration Event là contract phát ra ngoài bounded context để hệ thống khác phản ứng. Hai loại có thể liên quan nhưng không nên mặc định là cùng một object/schema.

## 2. Why does it exist?

Nếu internal domain model trở thành public message contract, thay đổi domain sẽ coupling consumers. Ngược lại, publish external message ngay giữa transaction có thể tạo dual-write inconsistency.

## 3. How does it work?

```text
Aggregate → Domain Event → Application handler
                         → Outbox record (same DB transaction)
                         → Publisher → Integration Event → Other service
```

Transaction boundary kết thúc trước network delivery; Outbox nối atomic state change với eventual publication.

## 4. Practical implementation

Domain event có thể chứa rich internal identifiers/value objects. Application layer map nó sang versioned integration DTO rồi ghi Outbox trong cùng transaction với aggregate changes.

```csharp
public sealed record OrderPaidDomainEvent(Guid OrderId, Money Amount);
public sealed record OrderPaidV1(Guid OrderId, decimal Amount, string Currency);
```

## 5. Real production scenario

Ordering service đánh dấu order Paid. Inventory và notification cần biết. Internal domain event kích hoạt local policy; integration event `OrderPaidV1` là stable external contract.

## 6. Failure scenario & troubleshooting

**Symptom** → rename domain property làm consumer service lỗi. **Evidence** → broker message serialize trực tiếp domain entity/event. **Diagnosis** → boundary coupling. **Fix** → explicit integration contract + versioning + Outbox. **Verification** → contract compatibility tests.

## 7. Common mistakes

Publish broker message từ aggregate; gọi remote service trong DB transaction; coi domain event là distributed transaction; không version external schema.

## 8. Alternatives

Synchronous API call đơn giản hơn khi immediate response thật sự cần. Shared database có thể đủ cho modular monolith nhưng làm ownership yếu hơn nếu lạm dụng.

## 9. Trade-offs

### Advantages

Giữ domain model độc lập, explicit external contract và failure isolation tốt hơn.

### Costs / Risks

Mapping, Outbox, eventual consistency và message operations tăng complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event mô tả điều đã xảy ra.

### Middle

Tách internal event và external DTO.

### Senior

Thiết kế transaction/outbox/idempotency/versioning.

### Technical Lead / Architect

Xác định bounded-context ownership và contract evolution strategy.

## 11. Key takeaway

- Domain Event và Integration Event phục vụ hai boundaries khác nhau.
- External contract không nên leak domain internals.
- Outbox giải dual-write, không tạo distributed ACID transaction.

# 7. Azure Functions cold start: latency, scaling và khi serverless không phải lựa chọn tốt nhất

## 1. What is it?

Cold start là latency khi platform phải cấp compute instance, khởi động host/runtime và initialize application trước invocation. Mức độ phụ thuộc hosting plan, runtime, deployment package và initialization path.

## 2. Why does it exist?

Serverless có thể scale về ít/zero capacity để tiết kiệm tài nguyên. Đổi lại, request đầu tiên sau idle hoặc scale-out có thể trả chi phí startup.

## 3. How does it work?

Trigger đến khi không có warm worker → platform provision/activate instance → Functions host khởi động → DI/config/JIT/library init → function chạy. Scale-out burst có thể tạo nhiều cold starts song song.

## 4. Practical implementation

Giữ startup nhẹ: tránh network call synchronous trong startup, giảm dependency/package không cần thiết, reuse clients, đo initialization riêng. Chọn hosting plan có warm/prewarmed capacity khi latency SLO yêu cầu.

## 5. Real production scenario

HTTP Function ít traffic xử lý login callback. Sau idle, p50 tốt nhưng request đầu có latency vài giây, gây UX không ổn định.

## 6. Failure scenario & troubleshooting

**Symptom** → sporadic high latency sau idle/deployment/scale-out. **Evidence** → instance start telemetry trùng latency spikes. **Hypothesis** → cold start. **Diagnosis** → tách platform startup, app initialization và dependency latency. **Fix** → plan phù hợp, giảm startup, warm capacity hoặc đổi compute model. **Verification** → test after idle và burst scale-out.

## 7. Common mistakes

Gọi mọi latency spike là cold start; initialize SDK/network nặng trong startup; chọn Functions chỉ vì “serverless rẻ”; bỏ qua VNet/private dependency startup effects.

## 8. Alternatives

App Service/Container Apps/Worker Service phù hợp workload steady hoặc latency-sensitive. Logic Apps phù hợp orchestration integration ít code.

## 9. Trade-offs

### Advantages

Operational simplicity, event-driven scaling, cost tốt cho intermittent workload.

### Costs / Risks

Cold start, platform constraints và cost có thể tăng với steady high utilization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu scale-to-zero có startup cost.

### Middle

Đo startup và tối ưu initialization.

### Senior

So sánh plans, burst behavior, networking và dependency latency.

### Technical Lead / Architect

Chọn compute theo workload/SLO/cost, không theo xu hướng serverless.

## 11. Key takeaway

- Cold start là trade-off của elasticity, không phải bug ngẫu nhiên.
- Đo startup riêng khỏi dependency latency.
- Workload steady/latency-critical có thể phù hợp compute luôn-warm hơn.

# 8. CI/CD Canary Deployment: giảm blast radius bằng progressive delivery và measurable rollback

## 1. What is it?

Canary deployment đưa version mới tới một phần nhỏ traffic/instances trước, quan sát health rồi tăng dần. Nó là risk-control mechanism, không chỉ là deployment style.

## 2. Why does it exist?

Test/staging không tái tạo hoàn toàn production data, traffic và dependency behavior. Deploy 100% biến defect nhỏ thành full outage.

## 3. How does it work?

```text
Build → Test → Artifact → Deploy 5%
                         ↓
                   Observe SLO
                  ↙          ↘
              healthy       regression
                ↓              ↓
              25%          rollback/stop
                ↓
              100%
```

Promotion phải dựa metrics có threshold, không chỉ “đợi 10 phút thấy ổn”.

## 4. Practical implementation

Pipeline dùng immutable artifact, route weighted traffic, kiểm tra error rate/p95/p99/saturation/business KPI rồi promote. Database migration phải backward-compatible vì old/new versions cùng chạy.

## 5. Real production scenario

Checkout release mới gây timeout chỉ với một payment method hiếm. Canary 5% giới hạn blast radius và telemetry cho thấy dependency timeout tăng trước full rollout.

## 6. Failure scenario & troubleshooting

**Symptom** → canary healthy nhưng full rollout fail. **Evidence** → canary traffic quá nhỏ/không representative hoặc bottleneck chỉ xuất hiện ở scale. **Diagnosis** → validation window/segment sai. **Fix** → representative routing, load-sensitive metrics và staged percentages. **Verification** → replay/production progression với automated gates.

## 7. Common mistakes

Canary nhưng không có rollback criterion; migration breaking; compare raw counts thay vì rates; canary chỉ nhận internal users không đại diện workload; feature flag và deployment coupling khó rollback.

## 8. Alternatives

Blue-Green chuyển traffic gần như tức thì; rolling deployment đơn giản hơn; feature flags tách release khỏi deploy nhưng tạo flag lifecycle debt.

## 9. Trade-offs

### Advantages

Giảm blast radius và dùng production evidence trước full rollout.

### Costs / Risks

Routing, telemetry, compatibility và pipeline phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy khác release.

### Middle

Build pipeline artifact→deploy→health validation.

### Senior

Thiết kế gates, rollback và backward compatibility.

### Technical Lead / Architect

Chọn release strategy theo risk, traffic và recovery capability.

## 11. Key takeaway

- Canary chỉ có giá trị khi health được đo khách quan.
- Old/new versions phải coexist an toàn.
- Progressive delivery giảm blast radius nhưng không thay testing.

# 9. `dotnet-counters` + `dotnet-trace`: điều tra CPU, allocation và ThreadPool trước khi sửa code

## 1. What is it?

`dotnet-counters` cho runtime metrics live; `dotnet-trace` thu EventPipe trace để phân tích sâu hơn. Chúng giúp chuyển từ “API chậm” sang evidence về CPU, GC, allocation, ThreadPool hoặc exceptions.

## 2. Why does it exist?

Latency symptom có nhiều nguyên nhân. Tăng thread, cache hoặc rewrite query trước measurement dễ sửa sai tầng và thậm chí làm production tệ hơn.

## 3. How does it work?

Runtime phát counters/events qua diagnostic pipeline. Counters cho overview ít overhead; trace thu sample/events chi tiết hơn để mở bằng PerfView/Speedscope/tool tương thích.

## 4. Practical implementation

```bash
dotnet-counters monitor -p <PID> System.Runtime

dotnet-trace collect -p <PID> --duration 00:00:30
```

Quan sát CPU, allocation rate, GC heap size, Gen2 collections, ThreadPool queue length và exception rate trong lúc tái tạo incident.

## 5. Real production scenario

API p99 tăng từ 300 ms lên 4 s. CPU chỉ 30%, nhưng ThreadPool queue tăng và thread count tăng dần. Trace phát hiện synchronous blocking trong async request path.

## 6. Failure scenario & troubleshooting

**Symptom** → latency cao. **Evidence** → queue length tăng trong khi CPU chưa saturated. **Hypothesis** → ThreadPool starvation/blocking. **Diagnosis** → trace stacks tìm `.Result`, `.Wait()` hoặc blocking I/O. **Fix** → async end-to-end/bound concurrency. **Verification** → cùng load, queue giảm và p99 phục hồi.

## 7. Common mistakes

Chỉ nhìn CPU average; collect trace quá lâu trên production; không correlate với traffic/deploy; đo khi incident đã hết; coi một counter là root cause.

## 8. Alternatives

Application Insights/OpenTelemetry cho distributed request view; profiler/APM cho code hotspots; dump phù hợp leak/hang state.

## 9. Trade-offs

### Advantages

Nhanh, runtime-native và rất hữu ích cho hypothesis-driven diagnosis.

### Costs / Risks

Trace chi tiết có overhead/storage; cần kỹ năng đọc evidence và production access policy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết latency không đồng nghĩa CPU cao.

### Middle

Dùng counters để phân loại bottleneck.

### Senior

Correlate trace, GC, ThreadPool và request telemetry.

### Technical Lead / Architect

Chuẩn hóa incident playbook và safe diagnostics access.

## 11. Key takeaway

- Measure trước khi optimize.
- Counters định hướng; trace xác nhận mechanism.
- Root cause cần correlation giữa runtime và request/dependency telemetry.

# 10. CSRF + SameSite cookies: vì sao authenticated browser request vẫn có thể bị giả mạo

## 1. What is it?

CSRF xảy ra khi browser tự động gửi credential như authentication cookie tới site đích trong một request do site độc hại kích hoạt. Attacker không cần đọc cookie; chỉ cần khiến browser của victim gửi request có quyền.

## 2. Why does it exist?

Cookie authentication tiện vì browser tự attach cookie theo domain/path rules. Chính automatic credential attachment tạo CSRF risk cho state-changing endpoints.

## 3. How does it work?

Victim đăng nhập `bank.example`; cookie còn hiệu lực. Trang attacker tạo form/request tới endpoint mutation. Nếu browser gửi cookie và server chỉ kiểm tra authentication, server có thể coi request là hợp lệ. SameSite giảm cross-site cookie sending nhưng không thay mọi CSRF defense scenario.

## 4. Practical implementation

Với ASP.NET Core cookie-authenticated form/app, dùng antiforgery token cho unsafe methods và cấu hình cookie `SameSite`, `Secure`, `HttpOnly` phù hợp. API bearer token đặt explicit trong `Authorization` header có threat model khác vì browser không tự attach token như cookie.

```csharp
builder.Services.AddAntiforgery(options =>
{
    options.HeaderName = "X-CSRF-TOKEN";
});
```

Frontend lấy token qua trusted flow rồi gửi header cho mutation.

## 5. Real production scenario

Admin CMS dùng cookie auth. Endpoint `/content/publish` nhận POST nhưng không antiforgery validation. Admin mở trang độc hại trong tab khác; browser vẫn có session cookie và request publish có thể chạy dưới identity admin.

## 6. Failure scenario & troubleshooting

**Symptom** → state-changing request hợp lệ dù không xuất phát UI chính thức. **Evidence** → cookie auth, missing antiforgery/origin controls. **Diagnosis** → CSRF exposure. **Fix** → antiforgery token, SameSite strategy, validate request semantics. **Verification** → security integration test cross-site request không có token bị reject.

## 7. Common mistakes

Nhầm CORS với CSRF protection; cho rằng `HttpOnly` ngăn CSRF; dùng GET cho mutation; đặt `SameSite=None` mà không hiểu lý do; tắt antiforgery để “fix frontend”.

## 8. Alternatives

Bearer token explicit header giảm classic CSRF nhưng tăng XSS/token-storage concerns. BFF pattern có thể giữ tokens server-side nhưng cookie session vẫn cần CSRF design.

## 9. Trade-offs

### Advantages

Antiforgery + SameSite giảm unauthorized cross-site mutations đáng kể.

### Costs / Risks

Cross-origin login/payment flows có thể cần SameSite exceptions; token lifecycle thêm integration work.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu authentication thành công không chứng minh request do user chủ ý gửi.

### Middle

Implement antiforgery và cookie settings.

### Senior

Phân biệt CSRF, CORS, XSS và bearer/cookie threat models.

### Technical Lead / Architect

Chọn browser authentication architecture dựa trust boundaries và cross-site flows.

## 11. Key takeaway

- Cookie tự động gửi là gốc của classic CSRF risk.
- CORS không phải CSRF defense.
- SameSite hữu ích nhưng phải kết hợp đúng authentication/request design.
