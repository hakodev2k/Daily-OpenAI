# 1. `IDisposable` và `IAsyncDisposable`: resource lifetime trong .NET không giống garbage collection

## 1. What is it?

`IDisposable` và `IAsyncDisposable` là contract để giải phóng resource theo thời điểm xác định. Garbage Collector quản lý managed memory; disposal quản lý lifetime của file handle, stream, socket, unmanaged resource hoặc object cần cleanup rõ ràng.

```text
Managed memory → GC quyết định reclaim
External resource → application release theo scope
```

## 2. Why does it exist?

Một process có thể còn nhiều memory nhưng đã cạn file handles hoặc database connections. Chờ GC chạy không đáp ứng yêu cầu deterministic cleanup của resource khan hiếm.

## 3. How does it work?

`using` được compiler bảo vệ bằng `try/finally` để `Dispose()` chạy khi scope kết thúc. `await using` await `DisposeAsync()` nếu cleanup cần asynchronous I/O. Finalizer chỉ là safety net cho unmanaged resource, không phải cleanup path bình thường.

## 4. Practical implementation

```csharp
public sealed class ReportWriter : IAsyncDisposable
{
    private readonly StreamWriter _writer;

    public ReportWriter(Stream stream)
        => _writer = new StreamWriter(stream, leaveOpen: false);

    public Task WriteAsync(string line, CancellationToken ct)
        => _writer.WriteLineAsync(line.AsMemory(), ct).AsTask();

    public async ValueTask DisposeAsync()
    {
        await _writer.FlushAsync();
        await _writer.DisposeAsync();
    }
}

await using var writer = new ReportWriter(stream);
await writer.WriteAsync("hello", cancellationToken);
```

## 5. Real production scenario

Một worker xử lý hàng nghìn file nhưng giữ `FileStream` lâu và trông chờ GC. Sau vài giờ, process không mở được file mới dù heap không lớn. Đây là resource leak, không nhất thiết là managed-memory leak.

## 6. Failure scenario & troubleshooting

**Symptom** → handle/connection count tăng liên tục.  
**Evidence** → OS metrics tăng nhưng managed heap tương đối ổn.  
**Hypothesis** → resource không được dispose đúng scope.  
**Diagnosis** → audit ownership, `using`, exception path.  
**Fix** → deterministic cleanup và lifetime rõ ràng.  
**Verification** → load test dài, resource count trở về baseline sau mỗi batch.

## 7. Common mistakes

* Nghĩ GC thay thế `Dispose()`.
* Dispose object do DI container sở hữu.
* Dispose quá sớm resource đang được consumer khác dùng.
* Tạo/dispose `HttpClient` liên tục thay vì quản lý connection lifetime đúng cách.

## 8. Alternatives

DI container có thể quản lý disposal cho services do container sở hữu. `SafeHandle` phù hợp khi wrapping native handle. Object pooling phù hợp resource reusable nhưng đắt để tạo.

## 9. Trade-offs

### Advantages
* Cleanup deterministic.
* Giảm leak resource khan hiếm.

### Costs / Risks
* Ownership phức tạp.
* Sai owner có thể gây use-after-dispose.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu GC và disposal là hai cơ chế khác nhau.

### Middle
Dùng `using`/`await using` đúng scope.

### Senior
Phân tích ownership, pooling, handle leak và finalization.

### Technical Lead / Architect
Đặt lifecycle convention rõ giữa framework, DI container, application và infrastructure.

## 11. Key takeaway

* GC quản lý memory, không quản lý urgency của external resource.
* Disposal đúng owner quan trọng hơn chỉ “có gọi Dispose”.
* Resource leak thường lộ ra dưới load dài hạn.

# 2. ASP.NET Core API Versioning và backward compatibility

## 1. What is it?

API versioning cho phép transport contract tiến hóa mà consumer cũ vẫn hoạt động. Vấn đề chính không phải `/v1` hay header; vấn đề là compatibility.

## 2. Why does it exist?

Backend có thể deploy mỗi ngày trong khi mobile app hoặc partner integration upgrade chậm. Một field đổi type hoặc semantics có thể phá consumer đang chạy production.

## 3. How does it work?

Thay đổi nên được phân loại thành additive, behavioral hoặc breaking. Version boundary nằm ở API contract; domain logic không nên bị duplicate chỉ vì tồn tại nhiều transport versions.

```text
Client v1 → Contract v1 ┐
                        ├→ Application/Domain
Client v2 → Contract v2 ┘
```

## 4. Practical implementation

```csharp
public sealed record CustomerV1Dto(Guid Id, string FullName);
public sealed record CustomerV2Dto(Guid Id, string FirstName, string LastName);
```

Giữ DTO theo version giúp transport evolve độc lập với domain model.

## 5. Real production scenario

Mobile app cũ cần `FullName`, app mới dùng `FirstName` và `LastName`. Backend giữ v1 trong deprecation window, phát hành v2, đo traffic theo client version rồi retire v1 khi usage đủ thấp.

## 6. Failure scenario & troubleshooting

**Symptom** → app version cũ parse JSON lỗi sau backend release.  
**Evidence** → error chỉ xảy ra ở client cũ.  
**Hypothesis** → breaking contract change.  
**Diagnosis** → compare schema trước/sau.  
**Fix** → restore v1 hoặc route client cũ về contract cũ.  
**Verification** → contract tests và telemetry theo consumer version.

## 7. Common mistakes

* Nghĩ có version number là đủ.
* Version mọi thay đổi nhỏ.
* Reuse persistence entity làm API DTO.
* Không có deprecation telemetry.
* Đổi semantics nhưng giữ type rồi gọi là non-breaking.

## 8. Alternatives

Additive evolution khi không breaking; BFF khi client needs khác biệt lớn; GraphQL vẫn cần schema compatibility discipline.

## 9. Trade-offs

### Advantages
* Consumer release độc lập hơn.
* Rollout breaking change an toàn hơn.

### Costs / Risks
* Nhiều code paths phải test.
* Version cũ tạo maintenance debt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu breaking change không chỉ là đổi URL.

### Middle
Biết version endpoint và DTO.

### Senior
Đánh giá semantic compatibility và deprecation.

### Technical Lead / Architect
Định nghĩa support window, retirement criteria và ownership consumer migration.

## 11. Key takeaway

* Versioning là contract governance.
* Additive change thường rẻ hơn version mới.
* Không retire version nếu chưa có usage evidence.

# 3. EF Core Change Tracker và `DetectChanges`

## 1. What is it?

Change Tracker theo dõi entity states như `Added`, `Modified`, `Deleted`, `Unchanged` để `SaveChanges()` biết cần phát SQL gì.

## 2. Why does it exist?

Nó giảm boilerplate khi update entity graph, nhưng convenience này có CPU và memory cost theo số entity được track.

## 3. How does it work?

EF giữ state/snapshot của tracked entities và phát hiện thay đổi trước khi save. Context sống càng lâu và track càng nhiều entities, cost càng lớn.

## 4. Practical implementation

Read-only:

```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.Status == OrderStatus.Pending)
    .Select(x => new OrderDto(x.Id, x.Number))
    .ToListAsync(ct);
```

Set-based update:

```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Expired)
    .ExecuteUpdateAsync(s => s.SetProperty(
        x => x.Status,
        OrderStatus.Archived), ct);
```

## 5. Real production scenario

Nightly job giữ một `DbContext` cho 200.000 rows. Batch sau chậm hơn batch trước vì tracker giữ ngày càng nhiều entities dù SQL mỗi batch không thay đổi đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → batch process chậm dần.  
**Evidence** → tracked entity count và CPU trong change detection tăng.  
**Hypothesis** → context quá dài.  
**Diagnosis** → inspect `ChangeTracker.Entries()`.  
**Fix** → context theo batch, `AsNoTracking`, `ChangeTracker.Clear()` khi phù hợp, hoặc set-based update.  
**Verification** → throughput ổn định từ batch đầu tới cuối.

## 7. Common mistakes

* Tracking mọi read query.
* Long-lived `DbContext`.
* Tắt auto detect changes mà không hiểu correctness.
* Load entity chỉ để update một field hàng loạt.

## 8. Alternatives

No-tracking projections, `ExecuteUpdate`, raw SQL, bulk library hoặc short-lived context.

## 9. Trade-offs

### Advantages
* CRUD đơn giản.
* Automatic state management.

### Costs / Risks
* Hidden CPU/memory cost.
* Stale state trong long-lived context.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt tracked và untracked entity.

### Middle
Biết `AsNoTracking()` và context lifetime.

### Senior
Đo tracking cost và chọn set-based operation.

### Technical Lead / Architect
Chọn persistence approach theo workload thay vì một style duy nhất.

## 11. Key takeaway

* Change Tracker có cost tăng theo tracked graph.
* `DbContext` dài hạn thường cần xem lại boundary.
* Bulk/read workloads không nên mặc định dùng tracked entities.

# 4. Composite index order trong SQL Server

## 1. What is it?

Composite index có nhiều key columns và thứ tự key ảnh hưởng trực tiếp tới khả năng seek.

```sql
CREATE INDEX IX_Orders_Tenant_Status_CreatedAt
ON Orders (TenantId, Status, CreatedAt DESC);
```

## 2. Why does it exist?

Query thường filter/sort theo nhiều fields. “Index có đủ columns” chưa đủ nếu thứ tự không phản ánh access pattern.

## 3. How does it work?

B-tree được sắp left-to-right. Pattern phổ biến:

```text
Equality predicates → range/order columns → INCLUDE payload columns
```

Đây là heuristic, không phải luật tuyệt đối; execution plan và statistics vẫn quyết định.

## 4. Practical implementation

```sql
SELECT TOP (100) Id, Number, Total, CreatedAt
FROM Orders
WHERE TenantId = @TenantId
  AND Status = @Status
  AND CreatedAt >= @From
ORDER BY CreatedAt DESC;
```

```sql
CREATE INDEX IX_Orders_Tenant_Status_CreatedAt
ON Orders (TenantId, Status, CreatedAt DESC)
INCLUDE (Id, Number, Total);
```

## 5. Real production scenario

Multi-tenant SaaS có 80 triệu Orders. Index bắt đầu bằng `CreatedAt` khiến engine đọc range rộng rồi filter tenant. Đổi key order theo access pattern giảm logical reads đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → query “có index” nhưng I/O rất cao.  
**Evidence** → plan có scan/seek rộng và residual predicate.  
**Hypothesis** → key order sai.  
**Diagnosis** → compare rows read vs returned.  
**Fix** → redesign index theo predicates/sort.  
**Verification** → logical reads và latency giảm trên parameter set đại diện production.

## 7. Common mistakes

* Chỉ kiểm tra index có column hay không.
* Chọn order chỉ theo cardinality.
* Over-cover mọi query.
* Bỏ qua write amplification.

## 8. Alternatives

Single-column index, filtered index, query rewrite hoặc partitioning tùy workload.

## 9. Trade-offs

### Advantages
* Seek hiệu quả và có thể giảm lookup.

### Costs / Risks
* Tăng storage và write cost.
* Tối ưu một query có thể làm index portfolio phình to.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu composite index có thứ tự.

### Middle
Đọc seek/scan cơ bản.

### Senior
Phân tích residual predicates, selectivity và write cost.

### Technical Lead / Architect
Quản lý index như workload portfolio, không tối ưu từng query cô lập.

## 11. Key takeaway

* Key order là một phần của query access pattern.
* Execution plan và logical reads quan trọng hơn checklist “đã có index”.
* Index tốt phải cân bằng read và write cost.

# 5. Redis cache invalidation ownership

## 1. What is it?

Cache invalidation quyết định khi nào cached copy không còn hợp lệ và component nào chịu trách nhiệm loại bỏ/update nó.

## 2. Why does it exist?

Ngay khi có source of truth và cache, hệ thống có hai bản dữ liệu. Freshness trở thành consistency problem.

## 3. How does it work?

Các chiến lược gồm TTL-only, explicit invalidation sau write, event-driven invalidation và versioned keys.

```text
DB commit → ProductChanged → cache invalidator → DEL product:{id}
```

## 4. Practical implementation

```csharp
await db.SaveChangesAsync(ct);
await cache.RemoveAsync($"product:{productId}", ct);
```

Nếu DB commit thành công nhưng delete cache thất bại, stale window vẫn tồn tại. Với dữ liệu quan trọng có thể cần Outbox/event-driven invalidation và TTL làm safety net.

## 5. Real production scenario

Product price thay đổi nhưng Redis TTL là 30 phút trong khi business yêu cầu cập nhật trong vài giây. TTL-only không đáp ứng freshness requirement.

## 6. Failure scenario & troubleshooting

**Symptom** → user thấy giá cũ.  
**Evidence** → DB mới, Redis cũ.  
**Hypothesis** → invalidation thất bại.  
**Diagnosis** → trace write, delete/event consumer.  
**Fix** → reliable invalidation + TTL safety net.  
**Verification** → test DB success nhưng Redis/event failure.

## 7. Common mistakes

* TTL tùy tiện.
* Không có owner cho key.
* Cache authorization-sensitive data quá lâu.
* Không version serialized schema.

## 8. Alternatives

Không cache; `IMemoryCache`; CDN; dedicated read model.

## 9. Trade-offs

### Advantages
* Giảm DB load và latency.

### Costs / Risks
* Consistency complexity và hidden dependency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Cache là bản sao, không phải source of truth.

### Middle
Dùng TTL/cache-aside đúng.

### Senior
Thiết kế stale tolerance và failure path.

### Technical Lead / Architect
Quyết định dữ liệu nào đáng cache và freshness SLO.

## 11. Key takeaway

* Invalidation bắt đầu từ ownership.
* TTL không phải universal consistency strategy.
* Đôi khi lựa chọn Senior nhất là không cache.

# 6. Anti-Corruption Layer trong DDD

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary chuyển đổi giữa domain model nội bộ và contract/model của external system.

```text
Our Domain → ACL → Vendor / Legacy System
```

## 2. Why does it exist?

Nếu vendor DTO, enum hoặc naming lan vào domain, external contract trở thành coupling sâu. Vendor đổi API sẽ buộc business code thay đổi theo.

## 3. How does it work?

ACL làm translation về semantics, error model và concepts, ví dụ vendor code `A/S/X` thành `Active/Suspended/Closed` của domain.

## 4. Practical implementation

```csharp
public interface ICustomerRiskProvider
{
    Task<RiskLevel> GetRiskAsync(CustomerId id, CancellationToken ct);
}

public sealed class VendorRiskAdapter : ICustomerRiskProvider
{
    public async Task<RiskLevel> GetRiskAsync(CustomerId id, CancellationToken ct)
    {
        var r = await _client.GetRiskAsync(id.Value, ct);
        return r.Code switch
        {
            "L" => RiskLevel.Low,
            "M" => RiskLevel.Medium,
            "H" => RiskLevel.High,
            _ => throw new InvalidOperationException("Unknown risk code")
        };
    }
}
```

## 5. Real production scenario

CRM mới tích hợp legacy customer master có numeric codes và naming cũ. ACL giữ legacy semantics ở integration boundary thay vì để chúng trở thành ubiquitous language của hệ thống mới.

## 6. Failure scenario & troubleshooting

**Symptom** → vendor thêm code mới và mapping lỗi.  
**Evidence** → raw response có value chưa biết.  
**Hypothesis** → external contract evolved.  
**Diagnosis** → contract/log comparison.  
**Fix** → explicit unknown handling và mapping update.  
**Verification** → contract tests cho known/unknown values.

## 7. Common mistakes

* Chỉ wrap HTTP client rồi gọi là ACL.
* Leak vendor DTO vào domain.
* Translate field name nhưng không translate meaning.
* Overengineer ACL cho integration rất đơn giản.

## 8. Alternatives

Direct integration khi coupling chấp nhận được; shared model trong cùng bounded context; event translation tại messaging boundary.

## 9. Trade-offs

### Advantages
* Cô lập external change.
* Domain language sạch hơn.

### Costs / Risks
* Mapping code tăng.
* Có thể thành pass-through abstraction vô ích.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Không để vendor DTO đi xuyên hệ thống.

### Middle
Viết adapter/mapping rõ ràng.

### Senior
Đánh giá semantic mismatch và contract evolution.

### Technical Lead / Architect
Chọn boundary nào cần ACL và boundary nào direct coupling đơn giản hơn.

## 11. Key takeaway

* ACL bảo vệ semantics, không chỉ che HTTP.
* Translation phải diễn ra ở boundary.
* Không phải integration nào cũng cần abstraction nặng.

# 7. Azure App Service scale-out

## 1. What is it?

Scale-out chạy nhiều App Service instances. Request của cùng user có thể được xử lý bởi process khác nhau.

## 2. Why does it exist?

Một instance có giới hạn CPU/memory/concurrency. Scale-out tăng capacity và resilience, nhưng phơi bày assumptions từng bị che khi chạy single-instance.

## 3. How does it work?

```text
Client → load distribution → Instance A/B/C
```

Memory, local lock và local filesystem không được share. State cần shared visibility phải externalize sang Redis, Blob Storage, database hoặc messaging/coordination phù hợp.

## 4. Practical implementation

```csharp
builder.Services.AddStackExchangeRedisCache(o =>
    o.Configuration = configuration.GetConnectionString("Redis"));
```

Không nên tự động thêm distributed session nếu API có thể stateless hơn.

## 5. Real production scenario

Checkout app scale từ 1 lên 4 instances. Cart nằm trong `IMemoryCache`, nên request sang instance khác thấy cart trống. Scale-out chỉ làm visible architecture assumption sai.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi chỉ xảy ra khi nhiều instances.  
**Evidence** → request correlation cho thấy user đi qua nhiều hosts.  
**Hypothesis** → process-local state.  
**Diagnosis** → audit static state, local files, `IMemoryCache`, locks, scheduled jobs.  
**Fix** → externalize hoặc redesign stateless.  
**Verification** → multi-instance load test + instance termination.

## 7. Common mistakes

* Dùng sticky session làm giải pháp lâu dài.
* Lưu durable file vào local disk.
* Dùng `lock` cho distributed coordination.
* Scale app tier khi bottleneck nằm ở SQL.

## 8. Alternatives

Scale-up, Container Apps/AKS hoặc queue-based processing tùy workload.

## 9. Trade-offs

### Advantages
* Horizontal capacity và instance resilience.

### Costs / Risks
* Distributed state/dependencies tăng.
* Cost và downstream load tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Nhiều instances không share memory.

### Middle
Biết externalize shared state.

### Senior
Tìm hidden single-instance assumptions.

### Technical Lead / Architect
Quyết định state placement, scaling boundary và downstream capacity.

## 11. Key takeaway

* Stateless là architectural property.
* Scale-out phơi bày local-state assumptions.
* Scale web tier không tự động scale database/cache.

# 8. SLI, SLO và alerting

## 1. What is it?

**SLI** đo reliability thực tế; **SLO** là mục tiêu cho SLI; **SLA** là business contract có thể gắn consequence.

## 2. Why does it exist?

Dashboard có nhiều metrics nhưng không nhất thiết trả lời “user có đang nhận service tốt không?”. SLO tạo reliability target có thể dùng để ra quyết định.

## 3. How does it work?

```text
Telemetry → SLI → compare SLO → error budget → action
```

Ví dụ SLO availability 99.9% trong 30 ngày để lại 0.1% error budget.

## 4. Practical implementation

Availability SLI nên dựa trên valid requests và success semantics, không đơn giản coi mọi 4xx là server failure. OpenTelemetry/Application Insights cung cấp request/dependency metrics để xây SLI trước khi tạo custom metrics tràn lan.

## 5. Real production scenario

CPU dưới 40% nhưng 3% checkout timeout vì payment provider. Resource dashboard xanh nhưng user experience đỏ. Checkout success-rate SLI phản ánh vấn đề đúng hơn CPU.

## 6. Failure scenario & troubleshooting

**Symptom** → on-call nhận rất nhiều alert không cần hành động.  
**Evidence** → alerts chỉ dựa CPU spike ngắn.  
**Hypothesis** → alert không gắn user impact.  
**Diagnosis** → review false-positive incidents.  
**Fix** → symptom/SLO-oriented alerts; resource metrics dùng để diagnose.  
**Verification** → alert noise giảm nhưng real incident vẫn được bắt.

## 7. Common mistakes

* Lẫn SLI/SLO/SLA.
* Đặt 100% SLO.
* Alert từng exception.
* Có SLO nhưng không ảnh hưởng engineering priorities.

## 8. Alternatives

Simple threshold cho system nhỏ; synthetic monitoring cho critical journey; business KPI bổ sung technical SLI.

## 9. Trade-offs

### Advantages
* Alert gần user impact.
* Reliability có objective rõ.

### Costs / Risks
* Chọn SLI sai sẽ tối ưu sai.
* Telemetry cost tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Logs/metrics không tự động tạo reliability.

### Middle
Biết đọc SLI/SLO.

### Senior
Thiết kế actionable alert.

### Technical Lead / Architect
Chọn SLO theo business criticality và cost of reliability.

## 11. Key takeaway

* SLI nên đo điều user quan tâm.
* SLO phải dẫn tới decision.
* Alert tốt phải actionable.

# 9. Git bisect trong production regression

## 1. What is it?

`git bisect` dùng binary search giữa known-good và known-bad commit để tìm first bad commit.

## 2. Why does it exist?

Nếu regression xuất hiện qua hàng trăm commits, đọc diff tuần tự chậm và dễ bias. Binary search giảm search space theo cấp số nhân.

## 3. How does it work?

```bash
git bisect start
git bisect bad
git bisect good <known-good-sha>
```

Test commit Git checkout rồi đánh dấu `good`/`bad` cho tới khi thu hẹp culprit.

## 4. Practical implementation

```bash
git bisect start HEAD v1.8.0
git bisect run dotnet test tests/Regression.Tests \
  --filter FullyQualifiedName~CheckoutRegression
```

Một classifier deterministic giúp tự động hóa toàn bộ quá trình.

## 5. Real production scenario

p99 tăng sau 180 commits. Team reproduce regression và dùng bisect để tìm commit đổi EF query shape gây SQL đắt.

## 6. Failure scenario & troubleshooting

**Symptom** → mỗi lần bisect ra culprit khác nhau.  
**Evidence** → performance test variance cao.  
**Hypothesis** → classifier nondeterministic.  
**Diagnosis** → chạy cùng commit nhiều lần.  
**Fix** → isolate environment/test data hoặc dùng functional reproduction.  
**Verification** → repeated bisect chỉ ra cùng commit.

## 7. Common mistakes

* Không có reliable good/bad test.
* Chọn known-good sai.
* Bỏ qua config/data changes ngoài Git.
* Xem culprit commit là root cause cuối cùng.

## 8. Alternatives

Deployment diff, feature-flag isolation, trace comparison hoặc controlled revert khi change set nhỏ.

## 9. Trade-offs

### Advantages
* Thu hẹp history nhanh.
* Giảm guessing bias.

### Costs / Risks
* Cần reproducibility.
* Commit cũ có thể không build vì tooling drift.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Git history là debugging tool, không chỉ backup.

### Middle
Biết bisect thủ công.

### Senior
Tự động hóa classifier và verify mechanism.

### Technical Lead / Architect
Đầu tư build reproducibility và deployment traceability.

## 11. Key takeaway

* Bisect biến regression hunt thành binary search.
* Test classification phải deterministic.
* Culprit commit chỉ là đầu mối để root-cause analysis.

# 10. Vue.js reactivity và async data flow

## 1. What is it?

Vue reactivity theo dõi dependency giữa reactive state và UI. State đổi thì Vue schedule update cho component phụ thuộc state đó.

## 2. Why does it exist?

Thay vì manual DOM synchronization, UI được derive từ state. Tuy nhiên reactivity không tự giải quyết race condition của asynchronous network calls.

## 3. How does it work?

`ref`/`reactive` tạo reactive values. Component đọc state sẽ được track. Async search có thể hoàn thành không theo thứ tự request được gửi.

```text
query "a"   → request 1 ───────┐
query "app" → request 2 ──┐    │
                          response 2
                               response 1 → stale overwrite
```

## 4. Practical implementation

```ts
import { ref, watch } from 'vue'

const query = ref('')
const results = ref<Product[]>([])
let requestId = 0

watch(query, async value => {
  const current = ++requestId
  const response = await fetch(`/api/products?q=${encodeURIComponent(value)}`)
  const data = await response.json()

  if (current === requestId) {
    results.value = data
  }
})
```

Production code có thể dùng `AbortController` để cancel request cũ.

## 5. Real production scenario

Autocomplete gửi requests cho `a`, `ap`, `app`. Response `a` về cuối và ghi đè result mới. Backend response đều đúng nhưng UI vẫn sai do async ordering.

## 6. Failure scenario & troubleshooting

**Symptom** → UI đôi lúc quay về result cũ.  
**Evidence** → DevTools cho thấy responses về khác thứ tự gửi.  
**Hypothesis** → stale async response overwrite state.  
**Diagnosis** → correlate request sequence và state update.  
**Fix** → debounce + cancellation hoặc sequence guard.  
**Verification** → network throttling và rapid input test.

## 7. Common mistakes

* Phát request mỗi keystroke không debounce/cancel.
* Dùng watcher cho state có thể derive bằng computed.
* Store duplicate derived state.
* Backend engineer chỉ nhìn server log, không inspect browser network timing.

## 8. Alternatives

React có mental model khác nhưng cùng async ordering problem. Data-fetching libraries có thể cung cấp caching, cancellation và deduplication.

## 9. Trade-offs

### Advantages
* UI synchronization rõ hơn manual DOM.
* Update batching hiệu quả.

### Costs / Risks
* Reactive dependency khó debug nếu state model rối.
* Network race và stale state vẫn tồn tại.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu UI derive từ reactive state.

### Middle
Biết `ref`, computed, watcher và loading/error flow.

### Senior
Debug race, over-fetching và network waterfall.

### Technical Lead / Architect
Thiết kế frontend data ownership và API interaction đủ đơn giản cho team full-stack.

## 11. Key takeaway

* Reactivity không thay thế async correctness.
* Network timing là một phần của frontend correctness.
* Full-stack debugging cần nối browser behavior với backend telemetry.
