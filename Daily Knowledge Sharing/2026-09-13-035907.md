# 1. C# exception filters và `when`: phân loại exception mà không phá stack trace hoặc nuốt lỗi sai tầng

## 1. What is it?

Exception filter trong C# là điều kiện `when` gắn vào `catch` để quyết định một exception có thuộc responsibility của block đó hay không.

```csharp
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.NotFound)
{
    // chỉ xử lý 404
}
```

Mental model quan trọng: filter không chỉ là cú pháp đẹp hơn `if` trong `catch`. Nó cho runtime quyết định **có bắt exception ở frame này hay tiếp tục unwind lên caller** trước khi thực sự enter catch body.

## 2. Why does it exist?

Một exception type có thể đại diện nhiều failure semantics khác nhau. `HttpRequestException`, `SqlException`, `IOException` hay domain exception thường cần xử lý khác nhau tùy code/status/state.

Nếu catch quá rộng rồi tự `if/else`, developer dễ:

- nuốt exception không thuộc responsibility;
- wrap lại mất context;
- log cùng lỗi nhiều tầng;
- biến transient failure thành business error;
- retry lỗi deterministic.

Exception filter giúp catch boundary chính xác hơn.

## 3. How does it work?

Khi exception được throw, runtime xét các catch từ stack hiện tại đi lên. Với filter:

```text
Exception thrown
   |
   v
catch type matches?
   |
   v
filter evaluates true?
   | yes           | no
   v               v
enter catch     continue unwind
```

Điểm quan trọng là filter expression nên gần như side-effect free. Nếu filter tự throw exception khác hoặc gọi logic phức tạp, troubleshooting trở nên khó hiểu.

## 4. Practical implementation

Ví dụ mapping một upstream 404 thành domain-specific result, nhưng để timeout/network failure đi lên resilience layer:

```csharp
public async Task<Product?> GetProductAsync(
    string id,
    CancellationToken ct)
{
    try
    {
        return await _client.GetFromJsonAsync<Product>(
            $"/products/{id}", ct);
    }
    catch (HttpRequestException ex)
        when (ex.StatusCode == HttpStatusCode.NotFound)
    {
        return null;
    }
}
```

Nếu cần rethrow cùng exception, dùng:

```csharp
throw;
```

không dùng:

```csharp
throw ex;
```

vì `throw ex` làm stack trace bắt đầu lại từ vị trí rethrow.

## 5. Real production scenario

Một service gọi pricing provider. Provider trả:

- `404`: sản phẩm chưa tồn tại — business-meaningful;
- `429`: rate limit — transient/integration failure;
- `500`: provider unhealthy;
- timeout: dependency degradation.

Catch toàn bộ `HttpRequestException` rồi trả `null` sẽ biến provider outage thành “không có giá”, gây sai business behavior.

Filter cho phép xử lý đúng semantic boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → API trả `200` với dữ liệu thiếu thay vì `503` khi provider outage.

**Evidence** → logs chỉ thấy warning “product not found”; provider telemetry lại có 500/timeout.

**Hypothesis** → catch quá rộng đã convert infrastructure failure thành domain result.

**Diagnosis** → trace exception mapping qua application/integration layers.

**Fix** → dùng filter cho status cụ thể, để các failure còn lại propagate tới resilience/error middleware.

**Verification** → integration test riêng 404, 429, timeout và 500.

## 7. Common mistakes

- `catch (Exception)` ở repository/service rồi return default value.
- Log exception ở mọi layer rồi rethrow, tạo log duplication.
- `throw ex;` làm mất call-site stack context.
- Dùng filter gọi database/remote service.
- Retry dựa trên exception type mà không xét status/error code.
- Chuyển mọi technical exception thành cùng một domain exception.

## 8. Alternatives

- Pattern matching trong catch body: hợp lý nếu đã quyết định catch toàn type đó.
- Result type / discriminated result: tốt cho expected business outcomes, không thay thế unexpected failures.
- Global exception middleware: tốt cho HTTP response mapping ở outer boundary, không nên chứa business-specific recovery logic.

## 9. Trade-offs

### Advantages

- Catch boundary chính xác hơn.
- Giữ stack propagation tự nhiên cho lỗi không thuộc responsibility.
- Code mapping failure semantics rõ ràng hơn.

### Costs / Risks

- Filter phức tạp làm error flow khó đọc.
- Nếu domain/infrastructure boundaries không rõ, filter chỉ che thiết kế exception taxonomy kém.
- Quá nhiều status-specific branches có thể cần một centralized integration policy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu exception là control flow cho failure bất thường; không catch chỉ để “app không crash”.

### Middle

Biết dùng `when`, `throw;`, mapping error đúng boundary và viết integration tests cho failure paths.

### Senior

Phân biệt business absence, transient dependency failure và programming bug; tránh retry/logging duplication.

### Technical Lead / Architect

Thiết kế error taxonomy và responsibility boundary: failure nào recover local, failure nào propagate, failure nào translate ở API boundary.

## 11. Key takeaway

- Catch đúng **semantic failure**, không chỉ đúng exception type.
- `throw;` giữ stack trace; `throw ex;` thường là sai lựa chọn.
- Exception handling tốt là boundary design, không phải thêm nhiều `try/catch`.

# 2. ASP.NET Core Response Compression: Brotli/gzip giảm bandwidth nhưng có thể đổi CPU thành bottleneck và cache sai biến thể

## 1. What is it?

Response Compression trong ASP.NET Core nén HTTP response trước khi gửi qua network, thường bằng `gzip` hoặc Brotli khi client quảng bá support qua `Accept-Encoding`.

Mental model:

```text
Application response
      |
      v
compression middleware
      |
      v
smaller bytes over network
```

Nén giảm bandwidth và transfer time nhưng tiêu CPU, thêm latency ở server và ảnh hưởng caching semantics.

## 2. Why does it exist?

JSON, HTML, CSS và JavaScript thường compress rất tốt. Nếu API trả 500 KB JSON qua mobile network, transfer time có thể lớn hơn application processing time.

Không nén thì origin/CDN trả nhiều bytes hơn. Nhưng bật compression cho mọi payload cũng sai: image/video đã compressed, payload nhỏ không đủ lợi ích, và high CPU workload có thể bị compression làm nặng hơn.

## 3. How does it work?

Client gửi:

```http
Accept-Encoding: br, gzip
```

Server chọn encoding phù hợp và trả:

```http
Content-Encoding: br
Vary: Accept-Encoding
```

`Vary` quan trọng vì cache phải phân biệt compressed variant theo request headers. Nếu reverse proxy/CDN xử lý không đúng, client có thể nhận variant không tương thích.

## 4. Practical implementation

```csharp
builder.Services.AddResponseCompression(options =>
{
    options.EnableForHttps = true;
});

var app = builder.Build();
app.UseResponseCompression();
```

Không nên chỉ “bật rồi quên”. Load test cần đo:

- response size;
- CPU;
- p95/p99 latency;
- throughput;
- CDN/origin bandwidth.

Static assets thường nên được CDN/web server xử lý hiệu quả hơn là nén động mỗi request trong application process.

## 5. Real production scenario

Search API trả JSON 1.2 MB cho một trang nhiều facets. Bật Brotli giảm payload còn 180 KB, mobile latency tốt hơn rõ rệt.

Nhưng khi traffic tăng, CPU App Service lên 85–90%. Compression level quá cao khiến application throughput giảm mặc dù database latency không đổi.

Optimization đúng là chọn compression level/boundary phù hợp, giảm response shape hoặc để edge handle static content.

## 6. Failure scenario & troubleshooting

**Symptom** → network bytes giảm nhưng API p99 tăng sau release.

**Evidence** → CPU tăng; trace cho thấy application/dependency time gần như cũ; benchmark cho thấy compression cost lớn.

**Hypothesis** → dynamic compression trở thành CPU bottleneck.

**Diagnosis** → so CPU/profile trước-sau, payload distribution, content types và negotiated encoding.

**Fix** → giảm compression effort, loại content type không đáng nén, giảm payload, offload edge khi phù hợp.

**Verification** → đo lại latency/CPU/bandwidth dưới cùng load.

## 7. Common mistakes

- Nén JPEG/PNG/MP4 rồi kỳ vọng giảm đáng kể.
- Không kiểm tra `Vary: Accept-Encoding` và CDN behavior.
- Bật compression mức cao nhất trong latency-sensitive API.
- Dùng compression để che API response quá lớn.
- Chỉ đo response size mà không đo CPU và tail latency.

## 8. Alternatives

- CDN/edge compression: phù hợp static/cacheable responses.
- Precompressed static assets: tránh compression cost runtime.
- Smaller DTO/projection/pagination: giảm bytes ngay từ source.
- Binary formats: có thể giảm payload nhưng đổi interoperability/debuggability.

## 9. Trade-offs

### Advantages

- Giảm bandwidth.
- Cải thiện transfer time trên network chậm.
- Có thể giảm egress cost.

### Costs / Risks

- Tăng CPU.
- Có thể tăng tail latency khi CPU saturation.
- Caching phức tạp hơn do encoding variants.
- Không giải quyết API contract quá “béo”.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu compression đổi CPU để lấy bandwidth.

### Middle

Cấu hình middleware, kiểm tra headers và đo response size/latency.

### Senior

Nhận diện khi compression đẩy hệ thống sang CPU-bound và tác động tới CDN/cache.

### Technical Lead / Architect

Quyết định layer nào chịu trách nhiệm compression: app, reverse proxy hay CDN; cân bằng latency, compute cost và operational simplicity.

## 11. Key takeaway

- Compression là trade-off CPU ↔ bandwidth.
- `Vary` và cache behavior quan trọng ngang với compression algorithm.
- Payload design tốt thường có giá trị hơn việc nén một response quá lớn.

# 3. EF Core compiled query cache: query shape, parameterization và vì sao dynamic LINQ có thể tự phá cache

## 1. What is it?

EF Core không gửi LINQ trực tiếp xuống database. Nó phải parse expression tree, translate sang SQL và chuẩn bị execution pipeline.

EF Core cache query compilation theo **query shape**. Hai query cùng shape nhưng khác parameter values có thể reuse compiled representation.

```text
LINQ expression tree
   -> translate/compile
   -> cached by shape
   -> SQL + parameters
```

## 2. Why does it exist?

Query translation có chi phí CPU. Nếu mỗi request phải compile lại cùng logical query, throughput giảm không cần thiết.

Cache hoạt động tốt khi values được parameterize. Nhưng dynamic expression building có thể embed constants làm mỗi request tạo expression shape mới, khiến cache hit thấp.

## 3. How does it work?

Tốt:

```csharp
var customerId = request.CustomerId;
var query = db.Orders.Where(x => x.CustomerId == customerId);
```

Shape ổn định, value trở thành parameter.

Nguy hiểm khi tự build expression constants khác nhau:

```text
Order.CustomerId == Constant(101)
Order.CustomerId == Constant(102)
Order.CustomerId == Constant(103)
```

Nếu expression shape khác, EF có thể compile nhiều lần; database cũng có thể nhận nhiều SQL shapes/literals gây plan-cache pressure.

## 4. Practical implementation

Dynamic filtering nên composition bằng parameterized expressions tự nhiên:

```csharp
IQueryable<Order> query = db.Orders.AsNoTracking();

if (request.CustomerId is not null)
{
    var customerId = request.CustomerId.Value;
    query = query.Where(x => x.CustomerId == customerId);
}

if (request.Status is not null)
{
    var status = request.Status.Value;
    query = query.Where(x => x.Status == status);
}

var items = await query
    .OrderByDescending(x => x.CreatedAt)
    .Take(100)
    .ToListAsync(ct);
```

`EF.CompileQuery`/`EF.CompileAsyncQuery` có thể hữu ích cho cực hot query đã đo được, nhưng không nên dùng như mặc định.

## 5. Real production scenario

Reporting API cho phép hàng chục filters. Team dùng custom expression builder embed constant trực tiếp. Sau release:

- CPU app tăng;
- query compilation metric/cache behavior xấu;
- DB plan cache có nhiều variants;
- p95 tăng dù SQL execution time riêng lẻ không đổi nhiều.

Root cause nằm ở query generation strategy, không phải database load thuần túy.

## 6. Failure scenario & troubleshooting

**Symptom** → app CPU tăng theo traffic; DB query duration không tăng tương ứng.

**Evidence** → profiler cho thấy nhiều thời gian trong EF query compilation/expression processing; SQL text có nhiều constant variants.

**Hypothesis** → dynamic query shapes phá cache.

**Diagnosis** → inspect generated expressions/SQL và query-cache metrics/logging.

**Fix** → parameterize, giới hạn query shapes, tránh custom expression builder không cần thiết.

**Verification** → compilation rate giảm, cache hit tăng, CPU/p95 tốt hơn.

## 7. Common mistakes

- Dùng `EF.CompileQuery` trước khi đo bottleneck.
- Nhầm database execution plan cache với EF query compilation cache.
- Build expression bằng constants cho user input.
- Dynamic `Include`/projection không kiểm soát tạo quá nhiều shapes.
- Tối ưu compile cost trong query vốn bị DB I/O 2 giây — sai bottleneck.

## 8. Alternatives

- LINQ bình thường + EF cache: đủ tốt cho đa số workloads.
- Compiled queries: cho hot stable query cực thường xuyên.
- Raw SQL/stored procedure: có thể hợp lý khi query cần DB-specific tuning mạnh.
- Dedicated read model: khi query complexity bản chất quá cao cho generic endpoint.

## 9. Trade-offs

### Advantages

- Stable query shape giảm CPU translation.
- Parameterization giúp cả EF và DB cache behavior.

### Costs / Risks

- Compiled query thêm rigidity và code complexity.
- Dynamic requirements có thể thực sự cần nhiều shapes.
- Micro-optimization có thể không đáng nếu latency chủ yếu ở I/O.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ được translate chứ không “chạy trực tiếp” trên DB.

### Middle

Biết compose `IQueryable`, parameterize input và inspect generated SQL.

### Senior

Đo compilation overhead, phân biệt app-side query cache với DB execution plan cache.

### Technical Lead / Architect

Quyết định khi nào generic filtering vẫn phù hợp, khi nào cần bounded query shapes/dedicated read model.

## 11. Key takeaway

- EF cache theo query shape; parameterization giữ shape ổn định.
- Dynamic LINQ sai cách có thể tạo CPU/plan-cache pressure.
- Chỉ dùng explicit compiled query khi measurement chứng minh đáng giá.

# 4. SQL Server parameter sniffing và plan instability: cùng một query nhưng dữ liệu khác nhau có thể cần execution plan khác nhau

## 1. What is it?

Parameter sniffing là hành vi SQL Server dùng parameter values tại thời điểm compile để estimate cardinality và chọn execution plan.

Điều này thường tốt vì optimizer biết giá trị thực. Nhưng với data distribution skewed, plan tối ưu cho một value có thể rất tệ cho value khác.

```text
@CustomerId = VIP customer -> 2,000,000 rows
@CustomerId = normal       -> 8 rows
```

Một plan duy nhất không nhất thiết tối ưu cho cả hai.

## 2. Why does it exist?

Optimizer cần estimate row counts để chọn:

- index seek vs scan;
- nested loops vs hash join;
- memory grant;
- join order;
- parallelism.

Parameter value cung cấp signal hữu ích. Vấn đề không phải “sniffing luôn xấu”; vấn đề là **plan reuse + skewed data + workload variability**.

## 3. How does it work?

Lần compile đầu:

```text
parameter value
   -> histogram/statistics
   -> cardinality estimate
   -> plan choice
   -> plan cache
```

Các execution sau có thể reuse plan dù parameter distribution khác mạnh.

Vì vậy incident có thể xuất hiện “ngẫu nhiên sau deploy/restart” khi plan cache bị reset và query đầu tiên có value bất thường.

## 4. Practical implementation

Bắt đầu bằng đo evidence:

```sql
SET STATISTICS IO, TIME ON;

EXEC dbo.GetOrdersByCustomer @CustomerId = 42;
EXEC dbo.GetOrdersByCustomer @CustomerId = 900001;
```

Xem actual execution plan, estimated vs actual rows, memory grant, reads và duration.

Các remediation có thể gồm:

- index/data model tốt hơn;
- query rewrite;
- SQL Server Parameter Sensitive Plan feature khi platform/version hỗ trợ;
- `OPTION (RECOMPILE)` cho một số query hiếm nhưng biến động mạnh;
- `OPTIMIZE FOR` trong trường hợp hiểu rõ workload.

Không có một hint universal.

## 5. Real production scenario

CRM query lấy activities theo account. 99.9% account có dưới 100 records; vài enterprise account có hàng triệu.

Sau failover, query đầu tiên chạy cho account nhỏ, optimizer chọn nested loops + seeks. Sau đó request enterprise account reuse plan và mất 40 giây.

DB CPU tăng nhưng chỉ trên một nhóm requests.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng stored procedure lúc 50 ms, lúc 30 s tùy parameter; release không đổi code.

**Evidence** → estimated rows lệch xa actual; plan history/Query Store cho thấy plan regression.

**Hypothesis** → parameter-sensitive workload + plan reuse.

**Diagnosis** → Query Store, actual plan, statistics histogram, compare representative parameter classes.

**Fix** → chọn remediation theo distribution và query semantics, không chỉ clear plan cache.

**Verification** → benchmark nhiều parameter classes và theo dõi p95/p99 sau change.

## 7. Common mistakes

- Gọi mọi slow query là parameter sniffing.
- `DBCC FREEPROCCACHE` như production fix lâu dài.
- `OPTION (RECOMPILE)` cho hot query hàng nghìn lần/giây mà không tính compile CPU.
- Chỉ test với một parameter “đẹp”.
- Thêm index theo một bad plan mà không hiểu data skew.

## 8. Alternatives

- Parameter Sensitive Plan optimization: tốt nếu engine/version hỗ trợ và workload phù hợp.
- Recompile per execution: tốt cho query ít chạy, giá trị biến động lớn.
- Split query paths: explicit cho “small tenant” vs “large tenant” khi domain biết phân loại.
- Pre-aggregated/read model: khi query pattern bản chất quá nặng.

## 9. Trade-offs

### Advantages

- Plan reuse giảm compilation CPU.
- Sniffing thường giúp optimizer chọn plan tốt cho parameter hiện tại.

### Costs / Risks

- Skewed data làm một plan không phù hợp mọi values.
- Recompile tăng CPU.
- Query hints tạo maintenance coupling vào data distribution hiện tại.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu query plan phụ thuộc estimates, không chỉ SQL text.

### Middle

Đọc estimated/actual rows và dùng Query Store/execution plan.

### Senior

Phân biệt statistics problem, parameter sensitivity và index/access-pattern problem.

### Technical Lead / Architect

Quyết định liệu query tuning đủ hay tenant/data distribution cần partitioning/read-model strategy khác.

## 11. Key takeaway

- Parameter sniffing là optimizer feature; chỉ trở thành vấn đề khi plan reuse không phù hợp data distribution.
- Test nhiều representative parameter classes, không chỉ một sample.
- Fix dựa trên plan/statistics evidence, không clear cache theo cảm tính.

# 5. SQL Server clustered key design: primary key đúng business chưa chắc là clustered key tốt cho I/O và index maintenance

## 1. What is it?

Primary key là **logical uniqueness constraint**. Clustered index là **physical row organization/access structure** của table trong SQL Server.

Hai khái niệm thường trùng nhau theo convention nhưng không bắt buộc.

Mental model:

```text
PRIMARY KEY  -> business/data integrity identity
CLUSTERED    -> physical storage/order access characteristics
```

## 2. Why does it exist?

Clustered key xuất hiện trong leaf structure và còn được carry vào nonclustered indexes như row locator. Vì vậy một clustered key rộng, random hoặc mutable có thể làm nhiều indexes lớn hơn và tăng page splits.

Business-natural key có thể hoàn toàn đúng làm PK nhưng chưa chắc tốt làm clustered key.

## 3. How does it work?

Nếu clustered key là random `uniqueidentifier`, inserts phân bố khắp B-tree:

```text
page A <- random insert
page M <- random insert
page C <- random insert
```

Khi page đầy, engine có thể split page, tăng fragmentation/write amplification.

Một increasing narrow key thường append-friendly hơn, nhưng có thể tạo last-page contention ở extreme write concurrency. Không có key universal.

## 4. Practical implementation

Một design có thể dùng business key unique nonclustered và surrogate clustered key:

```sql
CREATE TABLE Orders
(
    OrderId bigint IDENTITY(1,1) NOT NULL,
    OrderNumber varchar(30) NOT NULL,
    CustomerId bigint NOT NULL,
    CreatedAt datetime2 NOT NULL,

    CONSTRAINT PK_Orders
        PRIMARY KEY CLUSTERED (OrderId),

    CONSTRAINT UQ_Orders_OrderNumber
        UNIQUE (OrderNumber)
);
```

Nếu dùng GUID cho distributed generation, cân nhắc sequential variants/UUID strategies tùy stack và requirement — nhưng phải đo behavior thật.

## 5. Real production scenario

E-commerce table `OrderLines` có 500 triệu rows. Clustered key là 36-byte string order code. Mọi nonclustered index phải carry key lớn đó.

Storage tăng, buffer cache chứa ít rows/page hơn, I/O tăng. Chuyển clustered locator sang narrow `bigint` có thể giảm index footprint đáng kể mà vẫn giữ business key unique.

## 6. Failure scenario & troubleshooting

**Symptom** → write latency tăng, index size lớn, page splits cao, maintenance kéo dài.

**Evidence** → DMVs/index stats cho thấy fragmentation/page split; nonclustered indexes rộng bất thường.

**Hypothesis** → clustered key width/randomness góp phần write amplification.

**Diagnosis** → inspect index definitions, row size, insertion pattern, waits và actual workload.

**Fix** → redesign trong migration có kế hoạch; có thể điều chỉnh fill factor tạm thời nhưng không coi đó là chữa gốc.

**Verification** → compare write throughput, logical reads, index size và maintenance duration.

## 7. Common mistakes

- Đồng nhất primary key với clustered index theo thói quen.
- Chọn clustered key chỉ vì “GUID global unique”.
- Đổi clustered index production trên table lớn mà không plan migration/log space/downtime.
- Dùng fragmentation % như metric duy nhất.
- Tối ưu storage layout khi table nhỏ và không có bottleneck.

## 8. Alternatives

- `bigint` identity clustered key: đơn giản, narrow, locality tốt.
- Sequential GUID-like key: phù hợp một số distributed scenarios.
- Natural business key: tốt nếu narrow, immutable và access pattern phù hợp.
- Heap: hợp lý trong một số staging/bulk workloads, nhưng không phải default OLTP recommendation.

## 9. Trade-offs

### Advantages

- Narrow stable clustered key giảm index footprint.
- Locality tốt có thể cải thiện write/read behavior.

### Costs / Risks

- Surrogate key thêm mapping với business identity.
- Sequential key có thể tạo hotspot ở extreme concurrency.
- Redesign clustered key rất đắt trên large table.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt logical key và physical index.

### Middle

Đọc index definition, hiểu nonclustered row locator và page split basics.

### Senior

Đánh giá key width, insertion pattern, index footprint và workload evidence.

### Technical Lead / Architect

Chọn identity strategy dựa trên scale, replication/distribution, migration cost và operational constraints thay vì convention.

## 11. Key takeaway

- PK và clustered index giải quyết hai vấn đề khác nhau.
- Clustered key ảnh hưởng mọi nonclustered index và write behavior.
- Chỉ redesign khi workload evidence chứng minh benefit đáng migration cost.

# 6. CQRS với một database: tách intent và model đọc/ghi mà không cần Microservices hay Event Sourcing

## 1. What is it?

CQRS — Command Query Responsibility Segregation — tách **operations thay đổi state** khỏi **operations chỉ đọc state**.

```text
Command -> validates intent -> changes state
Query   -> reads/projection -> returns data
```

CQRS không bắt buộc:

- hai databases;
- Event Sourcing;
- message broker;
- Microservices;
- MediatR.

Có thể áp dụng CQRS rất nhẹ trong một Modular Monolith dùng cùng một SQL database.

## 2. Why does it exist?

Write model thường cần bảo vệ business invariant. Read model lại cần shape dữ liệu tối ưu cho UI/reporting.

Ép cả hai qua cùng generic CRUD abstraction dễ dẫn tới:

- domain entity bị biến thành DTO;
- query load quá nhiều entity graph;
- write path cho phép cập nhật field tùy ý;
- read requirements làm domain model méo mó.

CQRS tách intent để mỗi side tối ưu theo trách nhiệm.

## 3. How does it work?

Một database vẫn có thể phục vụ cả hai:

```text
API
 |
 +--> Command Handler --> Domain/EF tracked entities --> SQL
 |
 +--> Query Handler ----> projection/AsNoTracking ----> SQL
```

Transaction boundary của command vẫn là local DB transaction. Query có thể join/projection trực tiếp mà không cần repository trả aggregate nếu không có business mutation.

## 4. Practical implementation

Command:

```csharp
public sealed record ApproveTimesheet(Guid TimesheetId, Guid ApproverId);

public sealed class ApproveTimesheetHandler
{
    private readonly AppDbContext _db;

    public async Task Handle(ApproveTimesheet cmd, CancellationToken ct)
    {
        var timesheet = await _db.Timesheets
            .SingleAsync(x => x.Id == cmd.TimesheetId, ct);

        timesheet.Approve(cmd.ApproverId);
        await _db.SaveChangesAsync(ct);
    }
}
```

Query:

```csharp
public Task<TimesheetDetailsDto?> GetDetails(Guid id, CancellationToken ct) =>
    _db.Timesheets
       .AsNoTracking()
       .Where(x => x.Id == id)
       .Select(x => new TimesheetDetailsDto(
           x.Id,
           x.Employee.Name,
           x.Status,
           x.TotalHours))
       .SingleOrDefaultAsync(ct);
```

Không cần separate read database để nhận benefit đầu tiên.

## 5. Real production scenario

Approval platform có workflow rules phức tạp nhưng dashboard cần 15 joins + aggregations. Nếu dashboard load aggregates rồi mapping, query chậm và tracking vô ích.

Tách query projection giúp read path tối ưu mà write model vẫn giữ invariants.

## 6. Failure scenario & troubleshooting

**Symptom** → codebase có “CQRS” nhưng mỗi handler chỉ gọi generic repository CRUD; query vẫn trả domain entities.

**Evidence** → nhiều boilerplate, ít boundary benefit, domain model bị expose sang API.

**Hypothesis** → pattern được áp theo ceremony thay vì problem.

**Diagnosis** → xem command/query có khác responsibility hay chỉ khác class name.

**Fix** → giữ separation ở intent/model nơi có giá trị; bỏ abstraction không tạo isolation.

**Verification** → write invariants rõ, query shape đơn giản hơn, test boundaries dễ hơn.

## 7. Common mistakes

- Đồng nhất CQRS với MediatR.
- Tách hai databases quá sớm.
- Mọi endpoint đều một handler + repository dù domain CRUD đơn giản.
- Cho query mutate state.
- Dùng Event Sourcing chỉ vì “CQRS chuẩn”.
- Tạo eventual consistency khi business chưa cần.

## 8. Alternatives

- Simple layered CRUD service: tốt cho domain đơn giản.
- Rich domain model không CQRS: vẫn hợp lý nếu read/write shapes gần nhau.
- CQRS separate stores: phù hợp khi read scale/model thực sự khác mạnh.
- Event Sourcing: dành cho requirement audit/history/rebuild state đặc thù, không phải mặc định.

## 9. Trade-offs

### Advantages

- Intent rõ.
- Read path tự do projection/tuning.
- Write model tập trung invariants.

### Costs / Risks

- Nhiều classes/concepts hơn.
- Separate stores làm consistency/operations phức tạp mạnh.
- Pattern hóa quá mức tạo ceremony.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu command thay đổi state, query không thay đổi state.

### Middle

Implement handlers/projections và giữ write transaction rõ.

### Senior

Nhận biết khi separation giảm coupling, và khi chỉ thêm boilerplate.

### Technical Lead / Architect

Quyết định mức CQRS phù hợp: logical separation, separate model hay separate storage dựa trên business/scale, không dựa trên trend.

## 11. Key takeaway

- CQRS bắt đầu từ separation of intent, không từ infrastructure.
- Một database vẫn có thể cho phần lớn lợi ích.
- Chỉ thêm separate stores/Event Sourcing khi requirement thực sự biện minh complexity.

# 7. Azure App Service autoscale và downstream connection budget: scale-out web tier có thể làm SQL/Redis/API sụp nhanh hơn

## 1. What is it?

Autoscale tăng/giảm số application instances dựa trên metrics hoặc rules. Nhưng scale-out chỉ tăng capacity của **web tier**. Mỗi instance mới cũng tạo thêm concurrency tới dependencies.

```text
2 app instances -> SQL 200 concurrent connections
10 instances     -> SQL có thể thấy 1000
```

Mental model: autoscaling một tier thay đổi load shape của toàn hệ thống.

## 2. Why does it exist?

Traffic biến động, CPU/memory/request queue có thể vượt capacity một instance. Autoscale giúp elasticity và availability.

Nhưng nếu bottleneck thật là SQL, Redis, Service Bus consumer downstream hoặc third-party API quota, scale web tier có thể khuếch đại pressure thay vì giải quyết.

## 3. How does it work?

Scale controller quan sát metric/rule rồi add instances. Mỗi process có:

- ThreadPool;
- HTTP connection pools;
- DB connection pool;
- in-memory cache;
- background workers.

Do đó scale 5x không chỉ tăng HTTP capacity, nó còn tăng tổng pool/concurrency budget ở dependencies.

## 4. Practical implementation

Thiết kế capacity bằng budget thay vì chỉ max instance count.

Ví dụ:

```text
Azure SQL safe concurrent queries ~ 300
App Service max instances = 6
Target DB concurrency per instance <= 50
```

Ứng dụng có thể dùng bounded concurrency cho expensive operation:

```csharp
private static readonly SemaphoreSlim Gate = new(initialCount: 20);

public async Task<Result> ExecuteAsync(CancellationToken ct)
{
    await Gate.WaitAsync(ct);
    try
    {
        return await DoDatabaseHeavyWorkAsync(ct);
    }
    finally
    {
        Gate.Release();
    }
}
```

Đây chỉ là một local guard; architectural capacity planning vẫn cần ở system level.

## 5. Real production scenario

Campaign traffic tăng. CPU App Service vượt 70%, autoscale từ 3 lên 12 instances. Mỗi instance có DB pool tối đa lớn và endpoint report phát nhiều parallel queries.

Kết quả:

- Azure SQL workers/connections tăng mạnh;
- query latency tăng;
- API instances chờ DB lâu hơn;
- autoscale tiếp tục thấy CPU/request pressure và scale thêm.

Feedback loop này biến elasticity thành overload amplifier.

## 6. Failure scenario & troubleshooting

**Symptom** → sau autoscale, API latency tệ hơn dù có nhiều instances hơn.

**Evidence** → app instance count tăng trùng DB sessions/connections/throttling; dependency p95 tăng trước request p95.

**Hypothesis** → downstream saturation.

**Diagnosis** → correlate App Service scaling events, DB metrics, connection pool telemetry, dependency traces.

**Fix** → bounded concurrency, optimize query, cache/read model nếu phù hợp, scale downstream hoặc đặt queue/backpressure.

**Verification** → load test scale transition và xác nhận dependency utilization vẫn dưới safe envelope.

## 7. Common mistakes

- Scale web tier rồi gọi đó là “system scaling”.
- Max pool size lớn ở mọi instance không có global capacity calculation.
- BackgroundService chạy trên mọi instance ngoài ý muốn.
- Autoscale theo CPU khi bottleneck là remote dependency latency.
- Không có cooldown nên scale oscillation.

## 8. Alternatives

- Queue + asynchronous worker: phù hợp burst workload có thể delay.
- Rate limiting/backpressure: bảo vệ dependency trước overload.
- Scale database/cache tier: khi bottleneck đúng ở đó.
- Read replica/read model: cho read-heavy workloads.
- Vertical scaling: đôi khi đơn giản hơn nếu load profile ổn định.

## 9. Trade-offs

### Advantages

- Elastic capacity và resilience trước instance failure.
- Tránh provision peak capacity 24/7.

### Costs / Risks

- Tăng connection/concurrency downstream.
- Scale decisions có delay và có thể oscillate.
- Nhiều instances tăng cost và distributed coordination complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu scale-out = nhiều process, không phải một app “mạnh hơn” một cách cô lập.

### Middle

Theo dõi instance metrics, pool behavior và dependency telemetry.

### Senior

Tính concurrency budget và nhận biết feedback loop khi downstream saturated.

### Technical Lead / Architect

Đặt scaling strategy toàn hệ thống: web, queue, DB, cache, quota, cost và graceful degradation.

## 11. Key takeaway

- Autoscale một tier có thể làm tier khác quá tải.
- Capacity planning cần global concurrency/connection budget.
- Backpressure quan trọng ngang với scale-out.

# 8. IIS Application Pool recycle và warm-up: hiểu process lifecycle trước khi gọi mọi startup 5xx là “deploy lỗi”

## 1. What is it?

IIS Application Pool quản lý worker process (`w3wp.exe`) cho application. Recycle nghĩa là worker process cũ được thay bằng process mới theo configuration, health event hoặc administrative action.

Application vẫn có thể dùng cùng site/binding nhưng runtime process, static state, in-memory cache và connections được tạo lại.

## 2. Why does it exist?

Recycle hỗ trợ:

- process health/lifecycle management;
- config/application updates;
- recovery khỏi unhealthy process;
- operational policies ở legacy/enterprise hosting.

Nhưng recycle cũng tạo cold-start window. Nếu application startup nặng, request đầu có thể chậm/fail.

## 3. How does it work?

Simplified lifecycle:

```text
IIS receives traffic
   |
   v
App Pool worker process
   |
   +--> recycle triggered
           |
           +--> new worker starts
           +--> application initializes
           +--> old worker drains/exits
```

Behavior cụ thể phụ thuộc IIS settings, start mode, preload, idle timeout và deployment mechanism.

## 4. Practical implementation

Ứng dụng nên giữ startup deterministic và bounded:

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddHealthChecks()
    .AddSqlServer(builder.Configuration.GetConnectionString("MainDb")!);

var app = builder.Build();

app.MapHealthChecks("/health/ready");
app.Run();
```

Đừng chạy migration dài, download reference data lớn hoặc gọi nhiều external APIs synchronously trong startup nếu không thật sự cần.

Với IIS, dùng preload/warm-up phù hợp deployment architecture và health validation.

## 5. Real production scenario

Legacy ASP.NET application trên Windows Server có in-memory catalog cache. App Pool recycle lúc rạng sáng. Request đầu sau recycle phải load 500 MB dữ liệu từ SQL, mất 40 giây và đôi khi timeout.

Team tưởng database “chậm theo giờ”, nhưng root cause là lifecycle + cold cache.

## 6. Failure scenario & troubleshooting

**Symptom** → một khoảng 5xx/latency spike lặp theo thời điểm cố định.

**Evidence** → IIS event logs/process start timestamp trùng spike; app logs bắt đầu session mới; cache hit rate reset.

**Hypothesis** → recycle/cold start.

**Diagnosis** → correlate IIS logs, Windows Event Viewer, process ID, startup logs và deployment/recycle schedule.

**Fix** → warm-up, giảm startup dependency, điều chỉnh recycle policy nếu justified, đưa critical cache sang appropriate external store nếu cần.

**Verification** → controlled recycle và theo dõi readiness/first-request latency.

## 7. Common mistakes

- Giữ critical durable state chỉ trong process memory.
- Không log process start/version/instance ID.
- Chạy DB migration nặng ở startup của mọi instance.
- Tắt recycle hoàn toàn để che memory leak.
- Không phân biệt application restart với server/network outage.

## 8. Alternatives

- Azure App Service: quản lý hosting khác nhưng vẫn có restart/instance lifecycle.
- Windows Service/Kestrel reverse proxy: phù hợp một số workload nhưng tăng ownership operations.
- Containers/Kubernetes: lifecycle rõ hơn theo pod nhưng cold-start/readiness vẫn tồn tại.

## 9. Trade-offs

### Advantages

- IIS cung cấp mature process management cho Windows workloads.
- Recycle có thể phục hồi process và hỗ trợ operational policy.

### Costs / Risks

- Cold start và cache loss.
- Legacy configuration phức tạp.
- In-process scheduled work/state dễ bị interruption.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu web app chạy trong process có lifecycle; process có thể bị thay dù server vẫn sống.

### Middle

Đọc IIS logs/events, health endpoint và startup logs.

### Senior

Thiết kế startup/warm-up, cache ownership và restart-safe background work.

### Technical Lead / Architect

Quyết định workload nào còn phù hợp IIS, modernization nào đáng làm và process-lifecycle assumptions nào phải loại khỏi architecture.

## 11. Key takeaway

- Recycle là normal lifecycle event, không nhất thiết là incident.
- Application phải chịu được process restart mà không mất durable business state.
- Cold-start telemetry cần tách khỏi steady-state telemetry.

# 9. Tail latency p95/p99: average latency có thể xanh trong khi một phần người dùng vẫn gặp hệ thống rất chậm

## 1. What is it?

Percentile latency mô tả phân bố thời gian phản hồi.

- p50: 50% requests nhanh hơn giá trị này.
- p95: 95% requests nhanh hơn; 5% chậm hơn.
- p99: 99% nhanh hơn; 1% chậm hơn.

Average có thể bị che bởi số lượng requests nhanh lớn.

## 2. Why does it exist?

Production latency không đồng đều vì:

- GC pause;
- slow SQL plans;
- cache misses;
- cold starts;
- retries;
- noisy neighbors;
- lock contention;
- dependency tails.

User quan tâm request của họ, không quan tâm average đẹp.

## 3. How does it work?

Ví dụ 100 requests:

```text
99 requests = 100 ms
1 request   = 10,000 ms
```

Average ~199 ms — nghe có vẻ chấp nhận được.

Nhưng p99 phản ánh request rất chậm. Với workflow gọi nhiều dependencies nối tiếp, tail latency còn compound.

```text
Client -> API -> Service A -> SQL -> Service B
```

Chỉ cần một hop rơi vào tail là end-to-end request chậm.

## 4. Practical implementation

Trong Application Insights/OpenTelemetry backend, theo dõi latency histogram và percentiles theo route/dependency, nhưng tránh high-cardinality dimensions.

Load test nên report ít nhất:

```text
Throughput: 800 req/s
p50: 120 ms
p95: 450 ms
p99: 1.8 s
error rate: 0.4%
```

Khi tối ưu, so distribution trước-sau chứ không chỉ mean.

## 5. Real production scenario

Checkout average latency 350 ms, dashboard “xanh”. Support vẫn nhận complaint checkout quay spinner 5–8 giây.

Phân tích p99 theo dependency thấy inventory API thỉnh thoảng timeout 2 giây rồi retry, khiến một nhóm requests kéo dài 4–6 giây.

Average không làm lộ rõ failure mode.

## 6. Failure scenario & troubleshooting

**Symptom** → users phàn nàn nhưng average monitoring bình thường.

**Evidence** → p99 tăng mạnh, retry/dependency tail trùng thời điểm.

**Hypothesis** → long-tail dependency/lock/GC behavior.

**Diagnosis** → trace slow exemplars, phân đoạn theo endpoint/instance/dependency.

**Fix** → xử lý root cause: timeout policy, query, contention, GC, concurrency…

**Verification** → p95/p99 giảm dưới cùng traffic; không chỉ average.

## 7. Common mistakes

- Chỉ dashboard average.
- So p99 trên sample quá nhỏ mà không hiểu statistical noise.
- Aggregate mọi endpoints thành một percentile chung.
- Tạo metric labels theo request/user ID làm cardinality nổ.
- Tối ưu p50 trong khi user pain nằm ở p99.

## 8. Alternatives

- Histograms: giữ distribution và cho phép tính percentiles ở backend.
- SLO theo latency threshold: ví dụ 99% requests < 1 s.
- Tracing slow exemplars: giúp từ metric đi tới root cause cụ thể.

## 9. Trade-offs

### Advantages

- Phản ánh user experience tốt hơn average.
- Giúp phát hiện intermittent/long-tail failures.

### Costs / Risks

- Percentiles cần sample/histogram đúng cách.
- p99 có thể noisy ở low traffic.
- Quá nhiều dimensions làm telemetry đắt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu average không mô tả toàn distribution.

### Middle

Đọc p50/p95/p99 và correlate với traces/dependencies.

### Senior

Phân biệt systemic slowdown với tail-specific failure mode.

### Technical Lead / Architect

Đặt SLO phù hợp user journey và capacity/reliability budget, không chọn percentile chỉ vì dashboard tool có sẵn.

## 11. Key takeaway

- Average latency có thể che user pain nghiêm trọng.
- p95/p99 hữu ích nhất khi kết nối với trace evidence.
- Tối ưu đúng percentile phải dựa trên business SLO và traffic volume.

# 10. Contract testing cho third-party API: phát hiện schema drift và breaking change trước khi Production biến integration thành incident

## 1. What is it?

Contract testing kiểm tra assumptions giữa consumer và provider ở boundary: request shape, response schema, required fields, enum values, status semantics và compatibility.

Với third-party API, bạn thường không kiểm soát provider deployment. Vì vậy contract test tập trung vào **những gì application của bạn thực sự phụ thuộc**.

## 2. Why does it exist?

Unit test mock HTTP response chỉ chứng minh code hoạt động với fixture do chính team viết. Nếu provider đổi:

- field nullable;
- enum thêm giá trị mới;
- endpoint version;
- auth requirement;
- error shape;

mock vẫn xanh trong khi production có thể fail.

Contract/integration verification giảm khoảng cách giữa fixture và reality.

## 3. How does it work?

Một strategy thực tế:

```text
Consumer assumptions
   -> machine-readable schema/fixtures
   -> scheduled/CI verification against sandbox/provider
   -> compatibility alert
```

Với provider nội bộ, consumer-driven contract tooling có thể formal hơn. Với SaaS bên ngoài, thường cần schema validation + sandbox smoke tests + version monitoring.

## 4. Practical implementation

Ví dụ deserialize defensive hơn và test schema:

```csharp
public sealed record ReviewSummaryResponse(
    decimal AverageRating,
    int ReviewCount,
    string? NextCursor);
```

Integration test against sandbox:

```csharp
[Fact]
public async Task Review_summary_contract_is_compatible()
{
    using var response = await _client.GetAsync("/v1/reviews/known-product");
    response.EnsureSuccessStatusCode();

    var payload = await response.Content
        .ReadFromJsonAsync<ReviewSummaryResponse>();

    Assert.NotNull(payload);
    Assert.InRange(payload.AverageRating, 0m, 5m);
    Assert.True(payload.ReviewCount >= 0);
}
```

Không nên assert mọi field provider trả nếu application không phụ thuộc chúng; contract test quá chặt sẽ báo breaking change giả.

## 5. Real production scenario

Review provider trước đây luôn trả:

```json
{"rating":4.7,"count":120}
```

Sau update, sản phẩm chưa có review trả:

```json
{"rating":null,"count":0}
```

Code C# dùng non-nullable decimal và fail deserialize. Unit tests vẫn xanh vì fixtures chỉ có sản phẩm có review.

Một sandbox contract test với edge-case resource có thể phát hiện sớm.

## 6. Failure scenario & troubleshooting

**Symptom** → integration bắt đầu 500 ngay sau provider release; code của bạn không deploy.

**Evidence** → dependency response body/schema khác baseline; provider changelog/webhook status xác nhận change.

**Hypothesis** → external contract drift.

**Diagnosis** → capture sanitized response, compare schema/headers/status semantics với contract assumptions.

**Fix** → backward-compatible parser/mapping, feature flag/provider adapter update; coordinate provider nếu change thật sự breaking.

**Verification** → replay captured cases + sandbox contract tests + canary production monitoring.

## 7. Common mistakes

- Mock provider 100% và gọi đó là integration test.
- Assert full provider payload dù application chỉ cần 3 fields.
- Không test null/unknown enum/additional fields.
- Log raw provider payload có PII/secrets.
- Chạy contract test production-mutating endpoint.
- Không có timeout/rate-limit cho test suite gọi sandbox.

## 8. Alternatives

- JSON Schema/OpenAPI validation: tốt cho structural compatibility.
- Consumer-driven contract: mạnh khi provider thuộc cùng tổ chức và pipeline có thể phối hợp.
- Sandbox smoke tests: gần thực tế nhưng phụ thuộc provider availability/data.
- Recorded fixtures: deterministic, nhanh nhưng có nguy cơ stale.

Tốt nhất thường là kết hợp nhiều lớp thay vì chọn một.

## 9. Trade-offs

### Advantages

- Phát hiện drift trước production incident.
- Làm explicit dependency assumptions.
- Giảm false confidence từ mocks.

### Costs / Risks

- External sandbox có thể flaky.
- Provider không phải lúc nào có stable test data.
- Contract quá chặt tạo maintenance noise.
- CI phụ thuộc external network có thể giảm determinism.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mock chỉ kiểm tra assumption do team tự định nghĩa.

### Middle

Viết schema/integration tests cho critical fields và failure cases.

### Senior

Thiết kế test pyramid giữa fixture, sandbox, production canary; xử lý versioning/schema drift.

### Technical Lead / Architect

Quyết định contract ownership, provider risk tier, compatibility policy, fallback và operational response khi vendor breaking change.

## 11. Key takeaway

- Third-party contract sẽ thay đổi; integration phải được verify liên tục.
- Contract test nên bảo vệ assumptions thật, không mirror toàn bộ provider schema.
- Mocks + real sandbox verification + observability tạo defense-in-depth tốt hơn một lớp đơn lẻ.
