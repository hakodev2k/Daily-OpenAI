# 1. .NET `Span<T>`: zero-allocation slicing, lifetime boundary và khi optimization phản tác dụng

## 1. What is it?

`Span<T>` là một `ref struct` biểu diễn một vùng bộ nhớ liên tục mà không sở hữu vùng nhớ đó. Mental model quan trọng: nó là **borrowed view** lên memory, không phải collection mới. `Slice` chỉ tạo view khác nên thường không allocate.

## 2. Why does it exist?

Các parser truyền thống thường tạo substring hoặc temporary arrays. Với hot path như protocol parsing, serialization hay text processing, hàng triệu allocation nhỏ tạo GC pressure. `Span<T>` cho phép xử lý trực tiếp buffer hiện có.

## 3. How does it work?

`Span<T>` giữ reference tới vị trí đầu và length. Vì có thể trỏ vào stack memory, compiler giới hạn lifetime: nó không được boxing, lưu vào heap object hoặc sống xuyên `await` theo cách làm reference vượt scope.

```text
buffer: [A][B][C][D][E]
          └── Span(1,3) ──┘
              [B][C][D]
```

## 4. Practical implementation

```csharp
static bool TryParseHeader(ReadOnlySpan<char> value, out int id)
{
    const string prefix = "ID:";
    if (!value.StartsWith(prefix, StringComparison.Ordinal))
    {
        id = default;
        return false;
    }

    return int.TryParse(value[prefix.Length..].Trim(), out id);
}
```

Không có `Substring` cho phần ID.

## 5. Real production scenario

Một ingestion API parse hàng trăm nghìn CSV-like records mỗi phút. Profiling cho thấy temporary strings chiếm phần lớn allocation. Chuyển riêng parser hot path sang `ReadOnlySpan<char>` giảm allocation mà không thay đổi architecture.

## 6. Failure scenario & troubleshooting

**Symptom** → code phức tạp hơn nhưng latency gần như không đổi.  
**Evidence** → profiler cho thấy allocation không phải bottleneck; database chiếm 80% request time.  
**Hypothesis** → tối ưu sai tầng.  
**Diagnosis** → so CPU/allocation profile trước và sau.  
**Fix** → revert complexity nếu benefit không đáng kể.  
**Verification** → benchmark end-to-end thay vì microbenchmark duy nhất.

## 7. Common mistakes

Dùng `Span<T>` mọi nơi vì nghĩ luôn nhanh hơn; cố giữ span trong async workflow; trả span tham chiếu tới lifetime không hợp lệ; làm API khó đọc chỉ để tránh allocation không đáng kể.

## 8. Alternatives

`string`/array đơn giản và an toàn hơn cho normal business code. `Memory<T>` có thể sống trên heap và đi qua async boundary. `ArrayPool<T>` phù hợp khi cần reusable owned buffer lớn hơn.

## 9. Trade-offs

### Advantages

Giảm temporary allocation, slicing rẻ, phù hợp parsing hot path.

### Costs / Risks

Lifetime rules chặt, API complexity cao hơn, dễ premature optimization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu span là view, không sở hữu dữ liệu.

### Middle

Dùng span cho parsing/slicing và hiểu compiler restrictions.

### Senior

Đo allocation trước khi áp dụng; phân biệt `Span<T>`, `Memory<T>`, pooled buffer.

### Technical Lead / Architect

Quyết định hot path nào xứng đáng đổi maintainability lấy performance và yêu cầu benchmark evidence.

## 11. Key takeaway

- `Span<T>` tối ưu memory access, không phải architecture pattern.
- Chỉ dùng khi profiling chứng minh allocation đáng kể.
- Lifetime restriction là correctness feature, không phải inconvenience.

# 2. ASP.NET Core idempotent POST: retry-safe API bằng idempotency key

## 1. What is it?

Idempotency nghĩa là nhiều lần thực hiện cùng một logical operation tạo cùng hiệu ứng business như một lần. Với `POST` tạo payment/order, client gửi `Idempotency-Key` để server nhận diện retry của cùng operation.

## 2. Why does it exist?

Network timeout tạo ambiguity: client không biết request chưa tới server hay server đã commit nhưng response bị mất. Retry mù có thể tạo hai orders hoặc charge hai lần.

## 3. How does it work?

Server lưu key cùng fingerprint request và outcome. Request đầu xử lý; retry cùng key trả outcome đã lưu. Cùng key nhưng payload khác phải bị reject.

```text
Client -- POST key=abc --> API --> commit Order #42
Client <-- response lost --X
Client -- POST key=abc --> API --> stored result --> Order #42
```

## 4. Practical implementation

```csharp
public sealed record IdempotencyRecord(
    string Key,
    string RequestHash,
    int StatusCode,
    string ResponseJson);
```

Trong production, reserve key và business write phải có atomicity phù hợp; với SQL có thể dùng unique constraint trên key và transaction.

```sql
CREATE UNIQUE INDEX UX_Idempotency_Key
ON ApiIdempotency(IdempotencyKey);
```

## 5. Real production scenario

Mobile app tạo booking, nhận timeout do mạng yếu rồi retry. API đã commit booking lần đầu. Idempotency key khiến lần hai trả booking cũ thay vì tạo booking thứ hai.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate orders dù client gửi key.  
**Evidence** → hai instances cùng không thấy key rồi cùng insert.  
**Hypothesis** → check-then-act không atomic.  
**Diagnosis** → xem transaction và unique constraint.  
**Fix** → database-enforced uniqueness/reservation protocol.  
**Verification** → concurrency test gửi cùng key từ nhiều clients.

## 7. Common mistakes

Lưu key chỉ trong `IMemoryCache`; không hash payload; TTL quá ngắn; retry side effect ngoài transaction mà không có downstream idempotency; coi HTTP method tự giải quyết business idempotency.

## 8. Alternatives

PUT tới client-generated resource ID tự nhiên idempotent hơn khi domain phù hợp. Message consumers có Inbox/deduplication. Không cần idempotency infrastructure cho operation read-only.

## 9. Trade-offs

### Advantages

Retry an toàn hơn, giảm duplicate business effects, xử lý network ambiguity.

### Costs / Risks

Cần storage, expiry, concurrency control và policy cho payload mismatch.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry có thể duplicate side effect.

### Middle

Implement key validation, storage và unique constraint.

### Senior

Thiết kế atomicity, TTL, downstream idempotency và ambiguous failures.

### Technical Lead / Architect

Xác định operation nào cần idempotency guarantee và boundary ownership giữa API, database, messaging, payment provider.

## 11. Key takeaway

- Timeout không chứng minh operation thất bại.
- Idempotency cần server-side durable state, không chỉ client retry policy.
- Database constraint thường là hàng rào cuối chống race condition.

# 3. EF Core compiled queries: giảm query compilation overhead nhưng không chữa SQL chậm

## 1. What is it?

EF Core phải biến LINQ expression thành query representation/SQL. EF đã cache query theo shape; explicit compiled query (`EF.CompileQuery`/`EF.CompileAsyncQuery`) giảm thêm overhead lookup/compilation trên hot query path.

## 2. Why does it exist?

Trong endpoint cực nóng với query đơn giản và database rất nhanh, client-side EF query processing có thể trở thành phần đo được của latency. Compiled query tối ưu phần đó.

## 3. How does it work?

Delegate compiled được tạo một lần cho một query shape và tái sử dụng với parameters. Nó không thay đổi execution plan của database và không làm query thiếu index trở nên nhanh.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, int, IAsyncEnumerable<Order>>
    OrdersByCustomer = EF.CompileAsyncQuery(
        (AppDbContext db, int customerId) =>
            db.Orders
              .AsNoTracking()
              .Where(x => x.CustomerId == customerId)
              .OrderByDescending(x => x.CreatedAt)
              .Take(20));
```

Benchmark với realistic database/network trước khi giữ optimization.

## 5. Real production scenario

Lookup endpoint chạy hàng chục nghìn lần/giây, query trả một row từ local low-latency database. Profiling cho thấy EF processing có tỷ lệ đáng kể; compiled query có thể có ý nghĩa. Với report query 800 ms, nó gần như không đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → thêm compiled query nhưng p95 không cải thiện.  
**Evidence** → trace cho thấy SQL execution 95% latency.  
**Diagnosis** → bottleneck ở database/I/O, không ở EF compilation.  
**Fix** → xem execution plan/access pattern.  
**Verification** → đo từng stage trước/sau.

## 7. Common mistakes

Compile mọi query; tạo dynamic shapes làm delegate proliferation; bỏ qua SQL; benchmark InMemory provider rồi suy ra production; hy sinh readability cho micro-optimization.

## 8. Alternatives

Query cache mặc định của EF đủ cho đa số workloads. Raw SQL/Dapper có thể giảm ORM overhead hơn nhưng đổi lấy abstraction/maintainability. Projection và index đúng thường có impact lớn hơn.

## 9. Trade-offs

### Advantages

Giảm overhead ở stable hot path, predictable delegate reuse.

### Costs / Risks

Thêm static plumbing, hạn chế flexibility và dễ tối ưu nhầm bottleneck.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ phải được translate trước khi database chạy.

### Middle

Biết đo generated SQL và query latency.

### Senior

Phân biệt ORM overhead với database latency và benchmark compiled query đúng cách.

### Technical Lead / Architect

Chỉ chuẩn hóa optimization khi workload evidence chứng minh lợi ích đáng kể.

## 11. Key takeaway

- Compiled query tối ưu EF-side overhead, không tối ưu SQL plan.
- Đa số slow query cần xử lý access pattern/index/I/O trước.
- Measure trước khi thêm complexity.

# 4. PostgreSQL keyset pagination: ổn định latency và correctness khi dataset thay đổi

## 1. What is it?

Keyset pagination lấy trang kế tiếp dựa trên giá trị sort cuối cùng của trang trước thay vì `OFFSET N`. Cursor thường chứa `(created_at, id)` để tạo thứ tự deterministic.

## 2. Why does it exist?

`OFFSET 500000` vẫn buộc database đi qua lượng lớn rows trước khi trả 20 rows. Đồng thời insert/delete giữa hai request có thể làm row bị lặp hoặc bị bỏ qua.

## 3. How does it work?

```sql
SELECT id, created_at, total
FROM orders
WHERE (created_at, id) < (@createdAt, @id)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Index phù hợp:

```sql
CREATE INDEX ix_orders_created_id
ON orders (created_at DESC, id DESC);
```

## 4. Practical implementation

API trả opaque cursor encode sort values thay vì page number. Server decode/validate cursor và dùng predicate tương ứng. Cursor không nên cho phép client inject arbitrary SQL sort state.

## 5. Real production scenario

Activity feed có 50 triệu rows. Trang đầu nhanh nhưng page 5000 với OFFSET chậm rõ rệt. Keyset giữ work gần với page size và ổn định hơn khi feed có records mới.

## 6. Failure scenario & troubleshooting

**Symptom** → items lặp giữa pages.  
**Evidence** → sort chỉ theo `created_at`, nhiều rows có cùng timestamp.  
**Diagnosis** → ordering không unique.  
**Fix** → thêm stable tie-breaker `id` vào ORDER BY, cursor và index.  
**Verification** → pagination test với duplicate timestamps và concurrent inserts.

## 7. Common mistakes

Dùng non-deterministic ordering; cursor không chứa toàn bộ sort keys; cho phép nhảy trực tiếp page 1000 nhưng vẫn gọi đó là keyset; index không match ordering/filter.

## 8. Alternatives

OFFSET phù hợp dataset nhỏ và UX cần page number/random access. Keyset phù hợp infinite scroll/feed/large tables. Snapshot/export có thể cần isolation strategy khác.

## 9. Trade-offs

### Advantages

Latency ổn định hơn, ít scan bỏ đi, tốt với changing datasets.

### Costs / Risks

Không thuận tiện random page access; cursor contract phức tạp hơn; dynamic sorting cần nhiều index/design hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu OFFSET bỏ qua rows chứ không “teleport”.

### Middle

Implement cursor với deterministic order.

### Senior

Thiết kế composite index, filter interaction và cursor versioning.

### Technical Lead / Architect

Chọn pagination contract dựa trên UX, data size và consistency requirement.

## 11. Key takeaway

- Keyset pagination là access-pattern decision, không chỉ SQL trick.
- Sort phải deterministic.
- Index phải hỗ trợ cùng filter/order path.

# 5. Elasticsearch indexing pipeline: primary DB, Outbox và recovery khi projection bị lag

## 1. What is it?

Trong kiến trúc phổ biến, relational database là source of truth còn Elasticsearch là search projection. Indexing pipeline biến committed business changes thành search documents theo eventual consistency.

## 2. Why does it exist?

Dual-write trực tiếp `DB.SaveChanges()` rồi `Elasticsearch.Index()` không atomic. DB có thể commit còn Elasticsearch fail, tạo dữ liệu search thiếu mà không có durable record để replay.

## 3. How does it work?

```text
Business transaction
   ├─ update Primary DB
   └─ insert Outbox event
          |
          v
     Publisher/Worker
          |
          v
    Elasticsearch
```

Outbox record commit cùng business data. Worker retry độc lập và đánh dấu processed sau successful indexing.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);
order.ChangeName(request.Name);
db.Outbox.Add(OutboxMessage.Create("ProductChanged", order.Id));
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Indexer nên upsert idempotently theo document ID/version.

## 5. Real production scenario

Product price được cập nhật trong commerce DB. Elasticsearch outage 15 phút. Checkout vẫn dùng DB chính xác; search có thể stale. Sau recovery, outbox backlog được replay để projection bắt kịp.

## 6. Failure scenario & troubleshooting

**Symptom** → DB có product nhưng search không thấy.  
**Evidence** → outbox backlog tăng, indexing failures/429.  
**Hypothesis** → Elasticsearch degraded hoặc consumer throughput thấp.  
**Diagnosis** → đo oldest-message age, retry count, bulk latency.  
**Fix** → recover cluster, tune batch/backoff, replay failed messages.  
**Verification** → lag về baseline và reconciliation không còn missing IDs.

## 7. Common mistakes

Dual-write không durable; retry vô hạn không DLQ/reconciliation; indexer không idempotent; coi Elasticsearch là transactional truth; không expose freshness/lag metric.

## 8. Alternatives

CDC từ database giảm application outbox publishing code nhưng thêm infrastructure. Synchronous indexing đơn giản cho low-risk system nhưng failure coupling cao. Scheduled full reindex dễ vận hành nhưng freshness thấp.

## 9. Trade-offs

### Advantages

Decouple transactional availability khỏi search availability, replay được, scale indexing riêng.

### Costs / Risks

Eventual consistency, outbox storage/worker/reconciliation và operational complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DB và search có vai trò khác nhau.

### Middle

Implement outbox publisher và idempotent indexing.

### Senior

Thiết kế retry, lag metrics, reindex/reconciliation và ordering/version conflict.

### Technical Lead / Architect

Quyết định freshness SLA và liệu search complexity có thực sự cần thiết.

## 11. Key takeaway

- Search projection phải có recovery path khi indexing fail.
- Outbox giải quyết durable handoff, không loại bỏ eventual consistency.
- Indexing lag phải là metric production chính thức.

# 6. Hexagonal Architecture: ports/adapters để cô lập business policy khỏi infrastructure

## 1. What is it?

Hexagonal Architecture đặt application/domain logic ở trung tâm; interactions với database, HTTP, messaging hay filesystem đi qua **ports** (contracts) và **adapters** (implementations). Mục tiêu là dependency boundary, không phải hình lục giác hay folder convention.

## 2. Why does it exist?

Business policy thay đổi vì requirement; infrastructure thay đổi vì vendor, deployment hoặc technology. Nếu domain gọi trực tiếp EF/HTTP SDK ở mọi nơi, hai loại thay đổi coupling vào nhau và test business behavior khó cô lập.

## 3. How does it work?

```text
          HTTP Adapter
              |
              v
        Application Port
              |
              v
            Domain
              ^
              |
     Persistence Port
              ^
              |
        EF Core Adapter
```

Dependencies compile-time hướng vào policy/contracts; composition root nối adapters.

## 4. Practical implementation

```csharp
public interface IPaymentGateway
{
    Task<PaymentResult> ChargeAsync(
        PaymentRequest request,
        CancellationToken ct);
}

public sealed class CheckoutService(IPaymentGateway payments)
{
    public Task<PaymentResult> CheckoutAsync(
        PaymentRequest request,
        CancellationToken ct)
        => payments.ChargeAsync(request, ct);
}
```

Interface chỉ có giá trị nếu nó biểu diễn boundary có ý nghĩa, không phải tạo interface cho mọi class.

## 5. Real production scenario

Checkout dùng third-party payment provider. Domain/application cần khái niệm `Charge`, không cần biết SDK/vendor DTO. Adapter chuyển contract nội bộ sang provider API và cô lập retry/authentication mapping.

## 6. Failure scenario & troubleshooting

**Symptom** → đổi payment provider đòi sửa domain model, controllers và tests.  
**Evidence** → vendor types xuất hiện xuyên layers.  
**Diagnosis** → infrastructure contract đã leak vào core.  
**Fix** → tạo boundary theo business capability và anti-corruption mapping.  
**Verification** → adapter mới thay được mà core use case giữ nguyên.

## 7. Common mistakes

Interface cho mọi repository/service; generic ports không phản ánh domain; domain phụ thuộc EF attributes/provider DTO; architecture ceremony lớn hơn business complexity.

## 8. Alternatives

Layered Architecture đơn giản hơn cho CRUD app nhỏ. Modular Monolith giải quyết module ownership ở scale lớn hơn. Clean/Onion chia sẻ nguyên tắc dependency direction tương tự.

## 9. Trade-offs

### Advantages

Change isolation, testability, vendor boundary rõ, core ít phụ thuộc infrastructure.

### Costs / Risks

Mapping/abstraction overhead, nhiều types, dễ overengineering nếu system đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu core business không nên biết mọi infrastructure detail.

### Middle

Implement port/adapter ở external boundary thực sự.

### Senior

Phân biệt useful abstraction với interface ceremony; quản lý transaction/data ownership.

### Technical Lead / Architect

Chọn boundary theo volatility/business complexity và sẵn sàng không dùng Hexagonal nếu layered design đủ tốt.

## 11. Key takeaway

- Ports/adapters là dependency management, không phải folder template.
- Abstract ở boundary có volatility/ownership thực.
- Architecture tốt có thể kết luận “không cần thêm abstraction”.

# 7. Azure Service Bus sessions: ordering boundary, concurrency và poison-session risk

## 1. What is it?

Service Bus sessions nhóm messages có cùng `SessionId` thành ordered stream được một receiver lock theo session xử lý. Nó hữu ích khi ordering cần giữ **trong một business key**, không phải toàn queue.

## 2. Why does it exist?

Competing consumers tăng throughput nhưng có thể xử lý messages cùng aggregate sai thứ tự. Global single consumer giữ ordering nhưng phá scalability. Session cho phép serialize per key và parallelize giữa keys.

## 3. How does it work?

```text
Session Order-1: M1 -> M2 -> M3  -- receiver A
Session Order-2: M1 -> M2        -- receiver B
Session Order-3: M1 -> M2 -> M3  -- receiver C
```

Delivery vẫn cần idempotency; session không biến transport thành exactly-once.

## 4. Practical implementation

```csharp
var options = new ServiceBusSessionProcessorOptions
{
    MaxConcurrentSessions = 16,
    MaxConcurrentCallsPerSession = 1,
    AutoCompleteMessages = false
};

var processor = client.CreateSessionProcessor(queueName, options);
```

Complete message chỉ sau khi business effect đã thành công theo processing protocol.

## 5. Real production scenario

Order lifecycle phát `Created`, `Paid`, `Shipped`. `SessionId = orderId` giúp cùng order xử lý tuần tự trong khi hàng nghìn orders khác chạy song song.

## 6. Failure scenario & troubleshooting

**Symptom** → backlog lớn dù nhiều instances rảnh.  
**Evidence** → một vài sessions có hàng nghìn messages hoặc poison message retry liên tục.  
**Hypothesis** → hot session/blocked session.  
**Diagnosis** → group queue age/count theo SessionId, inspect delivery count/DLQ.  
**Fix** → xử lý poison message, reconsider partition key/business granularity.  
**Verification** → session age và overall throughput hồi phục.

## 7. Common mistakes

Dùng một `SessionId` cho toàn queue; nghĩ session loại bỏ duplicate; long-running handler giữ session lock; không có DLQ/recovery; chọn session key gây hotspot.

## 8. Alternatives

Không cần sessions nếu operations commutative/idempotent và ordering không quan trọng. Partitioned event stream phù hợp event-log workloads. Database optimistic concurrency có thể xử lý reorder ở application layer.

## 9. Trade-offs

### Advantages

Ordering per business key với parallelism giữa keys, stateful session workflow khả dụng.

### Costs / Risks

Hot sessions giới hạn throughput, lock management phức tạp, poison message có thể block progression.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ordering chỉ trong session.

### Middle

Configure processor, settlement và retry/DLQ.

### Senior

Thiết kế session key, lock duration, idempotency và poison-session recovery.

### Technical Lead / Architect

Hỏi liệu ordering có thật sự là invariant hay có thể thiết kế operations order-independent để giảm coupling.

## 11. Key takeaway

- Session tạo serialization boundary theo key, không phải exactly-once.
- Chọn `SessionId` là scalability decision.
- Poison/hot session cần observability riêng.

# 8. Docker image layers: build cache, reproducibility và supply-chain surface

## 1. What is it?

Docker image là chuỗi immutable filesystem layers tạo từ Dockerfile instructions. Layer ordering ảnh hưởng build cache, image size và nội dung cuối cùng được ship.

## 2. Why does it exist?

Layer reuse làm build/pull hiệu quả hơn. Nhưng nếu Dockerfile copy toàn source trước restore, thay một file nhỏ có thể invalidate expensive restore layer. Nếu build tools nằm trong runtime image, attack surface tăng.

## 3. How does it work?

Mỗi build step tạo layer/cache key dựa trên instruction và inputs. Multi-stage build cho phép compile ở SDK image rồi copy artifact sang runtime image.

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY MyApp.csproj .
RUN dotnet restore MyApp.csproj
COPY . .
RUN dotnet publish MyApp.csproj -c Release -o /out --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime
WORKDIR /app
COPY --from=build /out .
ENTRYPOINT ["dotnet", "MyApp.dll"]
```

Pinning strategy và vulnerability scanning vẫn cần release policy riêng.

## 5. Real production scenario

CI build .NET service hàng chục lần/ngày. Tách `COPY *.csproj` trước source giúp dependency restore cache tồn tại khi chỉ code thay đổi; multi-stage giữ SDK khỏi production image.

## 6. Failure scenario & troubleshooting

**Symptom** → build chậm bất thường sau mọi commit.  
**Evidence** → build log cho thấy restore layer luôn cache miss.  
**Diagnosis** → broad `COPY . .` trước restore hoặc volatile build arg invalidate layer.  
**Fix** → reorder stable dependencies trước volatile source.  
**Verification** → subsequent build dùng cached restore.

## 7. Common mistakes

Ship SDK image; copy `.git`, secrets hoặc local artifacts vào context; dùng floating base tag mà không có update governance; chạy process root không cần thiết; tối ưu layer count nhưng bỏ qua readability/security.

## 8. Alternatives

Framework-dependent deployment không container đơn giản hơn trên App Service/IIS. Container phù hợp khi cần portable packaging/runtime isolation. Không phải mọi .NET app đều cần Kubernetes chỉ vì dùng Docker.

## 9. Trade-offs

### Advantages

Reproducible artifact boundary, layer caching, runtime dependency packaging.

### Costs / Risks

Base image patching, registry/scanning, image provenance và operational tooling trở thành trách nhiệm mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu image khác container và Dockerfile tạo layers.

### Middle

Viết multi-stage build, `.dockerignore`, cache-friendly ordering.

### Senior

Đánh giá image size, CVEs, non-root execution và reproducibility.

### Technical Lead / Architect

Quyết định container có giải quyết deployment problem thật hay chỉ thêm platform complexity.

## 11. Key takeaway

- Layer ordering ảnh hưởng build cache trực tiếp.
- Runtime image nên chứa tối thiểu thứ cần chạy.
- Containerization kéo theo supply-chain ownership.

# 9. SLO + error budget: biến reliability thành engineering constraint có thể đo

## 1. What is it?

SLI là measurement về service behavior; SLO là target cho SLI; error budget là phần unreliability được phép trong target. Ví dụ availability SLO 99.9% cho phép khoảng 0.1% unsuccessful requests trong window định nghĩa.

## 2. Why does it exist?

“Service phải luôn ổn định” không actionable. 100% reliability thường quá đắt. SLO tạo ngôn ngữ chung để cân bằng feature velocity và reliability bằng dữ liệu.

## 3. How does it work?

Ví dụ request-based availability:

```text
SLI = good requests / eligible requests
SLO = SLI >= 99.9% over 30 days
Error budget = 0.1% eligible requests
```

Burn rate cho biết budget đang bị tiêu nhanh thế nào và hỗ trợ alert theo mức ảnh hưởng thay vì alert mọi exception.

## 4. Practical implementation

Một API có thể định nghĩa “good request” là server responses không phải 5xx và latency dưới threshold cho endpoint critical. Dashboard theo dõi SLI window; alert khi multi-window burn rate vượt policy.

## 5. Real production scenario

Checkout có SLO cao hơn admin reporting. Một dependency gây 1% checkout failures trong 30 phút làm burn budget nhanh; team ưu tiên mitigation ngay. Một lỗi admin hiếm có thể xử lý theo priority thấp hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → hàng trăm alerts nhưng user impact nhỏ.  
**Evidence** → alerts dựa CPU/log count, không map tới SLI.  
**Hypothesis** → monitoring signal không gắn reliability objective.  
**Diagnosis** → so alerts với failed/slow user journeys.  
**Fix** → thiết kế symptom-based SLI/SLO và supporting diagnostic alerts.  
**Verification** → alerts ít hơn nhưng correlate tốt hơn với impact.

## 7. Common mistakes

Đồng nhất SLA với SLO; chọn 99.99% không dựa business need; SLI denominator sai; exclude failures để metric đẹp; chỉ đo average latency; error budget không ảnh hưởng engineering decisions.

## 8. Alternatives

Traditional threshold alerts vẫn cần cho capacity/security signals nhưng không thay user-centric objective. SLA là external/business commitment; SLO thường là internal reliability target chặt hơn hoặc phục vụ SLA.

## 9. Trade-offs

### Advantages

Reliability measurable, ưu tiên incident/engineering work rõ hơn, giảm alert noise.

### Costs / Risks

Cần telemetry chất lượng và governance; SLO sai tạo incentive sai; quá nhiều SLO gây bureaucracy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt metric với user-visible reliability.

### Middle

Đọc SLI dashboard và trace incident tới failed requests.

### Senior

Thiết kế SLI denominator, percentile/availability objective và burn-rate alert.

### Technical Lead / Architect

Chọn reliability target theo business impact/cost và dùng budget để quyết định feature vs reliability work.

## 11. Key takeaway

- SLO phải đo behavior user quan tâm.
- Error budget biến “độ ổn định” thành constraint có thể ra quyết định.
- Reliability cao hơn luôn có cost; target phải có business justification.

# 10. SonarQube/code coverage: quality signal, risk-based testing và false confidence

## 1. What is it?

Code coverage đo phần code được test execution đi qua; SonarQube/static analysis tìm patterns, bugs, vulnerabilities và maintainability issues theo rules. Chúng là **signals**, không phải bằng chứng hệ thống đúng.

## 2. Why does it exist?

Review thủ công không scale hoàn toàn. Automation giúp phát hiện regression classes và vùng chưa được exercise. Nhưng metric dễ bị gaming nếu target trở thành “80% bằng mọi giá”.

## 3. How does it work?

Coverage instrumentation ghi statements/branches được chạy. Static analysis phân tích source/bytecode mà không cần chạy mọi path. Hai tín hiệu trả lời câu hỏi khác nhau: “đã chạy qua?” và “code có pattern đáng ngờ?”.

## 4. Practical implementation

Một strategy thực tế:

```text
Domain invariants -> focused unit tests
EF mappings/queries -> integration tests with real DB
HTTP contracts -> API integration tests
Critical user flow -> small Playwright suite
Static analysis -> CI quality gate on new code
```

Coverage nên được đọc cùng mutation risk, production history và criticality.

## 5. Real production scenario

Payment module có 95% line coverage nhưng tests mock payment gateway và database quá sâu. Serialization contract đổi làm production fail dù unit tests xanh. Integration/contract test mới là protection thiếu.

## 6. Failure scenario & troubleshooting

**Symptom** → CI xanh, coverage cao nhưng regression production vẫn nhiều.  
**Evidence** → tests assert implementation details, nhiều mocks, thiếu boundary tests.  
**Hypothesis** → metric tối ưu sai mục tiêu.  
**Diagnosis** → map incidents về test layer đáng lẽ bắt được.  
**Fix** → thêm risk-based integration/contract/E2E tests; giảm brittle mocks.  
**Verification** → replay production bug thành deterministic regression test.

## 7. Common mistakes

Chặn merge chỉ vì coverage giảm 0.1%; test getter/setter để tăng số; coi Sonar issue nào cũng severity như nhau; ignore false positives không có governance; không phân biệt new code và legacy debt.

## 8. Alternatives

Mutation testing đo test sensitivity sâu hơn nhưng đắt. Code review bắt context/design issues static rules không hiểu. Production telemetry/canary bắt failure class không thể cover hết trước deploy.

## 9. Trade-offs

### Advantages

Fast automated feedback, visibility vào untested code và common defects, hỗ trợ quality governance.

### Costs / Risks

False confidence, false positives, pipeline time và incentive gaming nếu metric trở thành mục tiêu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu coverage không đồng nghĩa correctness.

### Middle

Viết tests bảo vệ behavior và xử lý static-analysis findings có lý do.

### Senior

Chọn test layer theo failure risk, tránh over-mocking, review quality gates.

### Technical Lead / Architect

Thiết kế quality strategy kết hợp unit/integration/contract/E2E/static analysis và production feedback thay vì một con số coverage.

## 11. Key takeaway

- Coverage là measurement của execution, không phải chất lượng assertion.
- Test strategy phải map tới risk và boundaries thực.
- Quality gate tốt ngăn regression mà không biến metric thành trò chơi.
