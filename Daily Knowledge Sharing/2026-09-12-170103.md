# 1. C# `Span<T>` vs `Memory<T>`: tối ưu buffer mà không đưa stack-only lifetime ra khỏi boundary an toàn

## 1. What is it?

`Span<T>` là một view liên tục trên vùng memory, có thể trỏ tới array, stack allocation hoặc vùng memory khác mà không cần copy dữ liệu. `ReadOnlySpan<T>` là phiên bản chỉ đọc.

`Memory<T>`/`ReadOnlyMemory<T>` có mental model tương tự nhưng có lifetime linh hoạt hơn và có thể đi qua asynchronous boundary.

```text
byte[] / string / unmanaged memory
          |
          v
     Span<T>          -> stack-only view
     Memory<T>        -> heap-storable view
```

Điểm quan trọng nhất: `Span<T>` là `ref struct`. Runtime/compiler cố tình giới hạn nó để không sống ở nơi có thể vượt quá lifetime của memory mà nó tham chiếu.

## 2. Why does it exist?

Nhiều code xử lý text/binary trước đây tạo allocation chỉ để cắt dữ liệu:

```csharp
var prefix = value.Substring(0, 8);
```

hoặc:

```csharp
var chunk = buffer.Skip(offset).Take(length).ToArray();
```

Nếu thao tác này nằm trong parser/hot path, hàng triệu temporary objects có thể tăng allocation rate và GC pressure.

`Span<T>` cho phép slicing bằng metadata `(reference, length)` thay vì copy payload.

## 3. How does it work?

Ví dụ:

```csharp
ReadOnlySpan<char> input = "ORD-20260912-0001";
var prefix = input[..3];
var date = input.Slice(4, 8);
```

`prefix` và `date` không tạo string mới. Chúng chỉ nhìn vào vùng memory gốc.

Nhưng vì `Span<T>` có thể trỏ vào stack:

```csharp
Span<byte> temp = stackalloc byte[256];
```

compiler không cho phép giữ `Span<T>` trong field của class hoặc sống qua một `await`, vì stack frame có thể không còn tồn tại khi continuation chạy.

Khi cần buffer sống qua async boundary, dùng `Memory<T>`:

```csharp
async Task<int> ReadAsync(Memory<byte> buffer, CancellationToken ct)
    => await _stream.ReadAsync(buffer, ct);
```

## 4. Practical implementation

Parse protocol header mà không allocate substring:

```csharp
public static bool TryParseHeader(
    ReadOnlySpan<char> value,
    out int version,
    out ReadOnlySpan<char> payload)
{
    version = default;
    payload = default;

    var separator = value.IndexOf(':');
    if (separator <= 0)
        return false;

    if (!int.TryParse(value[..separator], out version))
        return false;

    payload = value[(separator + 1)..];
    return true;
}
```

Với async stream, API boundary nên dùng `Memory<byte>`:

```csharp
public async Task<int> FillAsync(
    Memory<byte> destination,
    CancellationToken ct)
{
    return await _stream.ReadAsync(destination, ct);
}
```

Nếu caller dùng pooled array:

```csharp
var rented = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var memory = rented.AsMemory(0, 64 * 1024);
    var read = await reader.FillAsync(memory, ct);
    Process(memory.Span[..read]);
}
finally
{
    ArrayPool<byte>.Shared.Return(rented);
}
```

## 5. Real production scenario

Một API import CSV 200 MB. Parser cũ dùng `string.Split`, `Substring` và `ToArray()` trên từng field. Database không chậm, CPU chỉ khoảng 60%, nhưng allocation rate hàng GB/phút và Gen 0/Gen 1 GC xảy ra liên tục.

Sau khi chuyển parser hot path sang `ReadOnlySpan<char>` và chỉ materialize string cho fields thật sự cần persist, throughput tăng và GC pressure giảm rõ rệt.

Engineering lesson không phải “dùng Span ở mọi nơi”, mà là: allocation ở parser có thể là bottleneck dù business logic đơn giản.

## 6. Failure scenario & troubleshooting

**Symptom** → parser throughput thấp, allocation rate cao, GC frequency tăng dù payload chỉ được đọc một lần.

**Evidence** → profiler cho thấy nhiều `Substring`, `char[]`, `byte[]`, LINQ iterator allocations.

**Hypothesis** → slicing/copying không cần thiết trên hot path.

**Diagnosis** → benchmark realistic payload bằng BenchmarkDotNet hoặc production-like load; xem allocation/op.

**Fix** → dùng span-based parsing có chọn lọc; giữ `Memory<T>` cho async/lifetime dài hơn.

**Verification** → so throughput, allocation/op và GC count trước/sau.

## 7. Common mistakes

- Đổi mọi API sang `Span<T>` dù không nằm trên hot path.
- Cố giữ `Span<T>` qua `await` thay vì hiểu lifetime restriction.
- Dùng `stackalloc` với buffer kích thước lớn/không kiểm soát.
- Return pooled buffer trước khi consumer dùng xong `Memory<T>`.
- Tối ưu allocation nhưng làm code parser khó kiểm chứng hơn mà không benchmark.

## 8. Alternatives

`string`, `byte[]` và collection bình thường là lựa chọn tốt khi workload nhỏ hoặc readability quan trọng hơn micro-allocation.

`ArrayPool<T>` giải quyết buffer reuse; nó không thay thế `Span<T>`. `SequenceReader<T>`/`ReadOnlySequence<T>` phù hợp khi dữ liệu không contiguous, ví dụ pipelines/network buffers.

## 9. Trade-offs

### Advantages

- Giảm copy/allocation trên parser và buffer hot path.
- Slicing rẻ.
- API có thể biểu diễn read-only intent rõ bằng `ReadOnlySpan<T>`.

### Costs / Risks

- Lifetime rules phức tạp hơn.
- Debugging/readability có thể giảm nếu lạm dụng.
- Pooling + memory views tạo ownership bugs nếu lifetime không rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slicing không nhất thiết phải copy dữ liệu.

### Middle

Biết khi nào dùng `Span<T>` trong synchronous scope và `Memory<T>` qua async boundary.

### Senior

Đo allocation, hiểu `ref struct`, stack lifetime, pooling và zero-copy trade-offs.

### Technical Lead / Architect

Giới hạn low-level optimization vào performance-sensitive components thay vì để toàn codebase gánh complexity không cần thiết.

## 11. Key takeaway

- `Span<T>` tối ưu view/slicing; `Memory<T>` phù hợp lifetime dài hơn và async.
- Lifetime safety là một phần của design, không chỉ syntax restriction.
- Chỉ dùng zero-copy abstraction khi measurement cho thấy allocation/copy thực sự đáng quan tâm.

# 2. `HttpClientFactory` handler lifetime + DNS rotation: tránh socket exhaustion nhưng cũng không giữ DNS cũ quá lâu

## 1. What is it?

`IHttpClientFactory` tạo `HttpClient` theo logical configuration nhưng quản lý/pool underlying `HttpMessageHandler` để tránh tạo TCP connection mới cho từng request.

Mental model:

```text
HttpClient instance
      |
      v
pooled HttpMessageHandler
      |
      v
connection pool
      |
      v
DNS-resolved remote endpoints
```

Vấn đề production có hai cực:

1. tạo/dispose handler liên tục → socket churn/exhaustion;
2. giữ connection/handler quá lâu → có thể tiếp tục dùng endpoint/DNS cũ khi infrastructure thay đổi.

## 2. Why does it exist?

Code kiểu này từng rất phổ biến:

```csharp
using var client = new HttpClient();
await client.GetAsync(url);
```

`HttpClient.Dispose()` không đồng nghĩa OS socket biến mất ngay; TCP connection có thể vào `TIME_WAIT`. Ở RPS cao, tạo client/handler per request làm cạn ephemeral ports.

Ngược lại, một singleton handler sống vô hạn có thể giữ pooled connections lâu hơn DNS topology mong muốn.

`HttpClientFactory` giải quyết lifecycle ở mức handler và centralize resilience/configuration.

## 3. How does it work?

Factory tạo client object mới nhẹ, nhưng tái sử dụng handler trong configured lifetime.

```text
Request A -> Client A -> Handler #1
Request B -> Client B -> Handler #1
...
handler lifetime expires
Request N -> Client N -> Handler #2
```

`SocketsHttpHandler.PooledConnectionLifetime` có thể kiểm soát tuổi connection để connection mới buộc resolve/connect lại theo thời gian.

## 4. Practical implementation

Named client:

```csharp
builder.Services.AddHttpClient("catalog", client =>
{
    client.BaseAddress = new Uri("https://catalog.internal/");
    client.Timeout = TimeSpan.FromSeconds(3);
})
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(5),
    PooledConnectionIdleTimeout = TimeSpan.FromMinutes(2)
});
```

Typed client:

```csharp
public sealed class CatalogClient(HttpClient httpClient)
{
    public async Task<ProductDto?> GetAsync(
        string sku,
        CancellationToken ct)
    {
        using var response = await httpClient.GetAsync(
            $"products/{Uri.EscapeDataString(sku)}",
            ct);

        if (response.StatusCode == HttpStatusCode.NotFound)
            return null;

        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<ProductDto>(ct);
    }
}
```

## 5. Real production scenario

Một service gọi internal API sau load balancer. Platform thay backend IP trong rolling deployment. Một subset application instances tiếp tục có latency/error cao vì pooled connection cũ vẫn trỏ tới endpoint không còn healthy.

Team restart app và “hết lỗi”, nhưng đó chỉ reset connection pool. Root cause là connection/DNS lifecycle không khớp infrastructure behavior.

## 6. Failure scenario & troubleshooting

**Symptom** → external dependency timeout chỉ ở vài instances; restart process tạm thời chữa được; hoặc server báo socket errors dưới load.

**Evidence** → connection metrics, DNS lookup, destination IP từ network trace, nhiều sockets `TIME_WAIT` nếu client lifecycle sai.

**Hypothesis** → handler/connection lifetime không phù hợp hoặc tạo `HttpClient` sai cách.

**Diagnosis** → inspect DI registration, `SocketsHttpHandler`, connection pool metrics và current DNS answers.

**Fix** → dùng factory, đặt connection lifetime có chủ đích, propagate timeout/cancellation; không tạo handler per request.

**Verification** → test DNS/backend rotation dưới sustained traffic, không chỉ happy-path HTTP call.

## 7. Common mistakes

- `new HttpClient()` cho mỗi request.
- Nghĩ `IHttpClientFactory` tự quyết định timeout/retry tốt cho mọi dependency.
- Retry `POST` không idempotent một cách mù quáng.
- Handler lifetime cực ngắn làm mất connection reuse.
- Handler/connection sống vô hạn trong môi trường endpoint thay đổi thường xuyên.

## 8. Alternatives

Singleton `HttpClient` với `SocketsHttpHandler` được cấu hình đúng cũng có thể tốt. Factory hữu ích hơn khi có nhiều named/typed dependencies, centralized policies và DI integration.

Service mesh/proxy có thể quản lý một phần connection/resilience, nhưng application vẫn cần timeout, cancellation và HTTP semantics đúng.

## 9. Trade-offs

### Advantages

- Connection pooling đúng lifecycle.
- Centralized client configuration.
- Hỗ trợ typed clients và observability tốt hơn.

### Costs / Risks

- Sai handler policy vẫn gây DNS/stale connection issue.
- Resilience pipeline quá aggressive có thể tạo retry storm.
- Nhiều named clients cần governance/config consistency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP call dùng connection pool phía dưới, không phải mỗi request là kết nối độc lập “miễn phí”.

### Middle

Dùng typed/named clients, timeout và cancellation đúng.

### Senior

Debug socket exhaustion, DNS rotation, connection lifetime và retry interaction.

### Technical Lead / Architect

Định nghĩa policy theo dependency: latency budget, retry safety, connection lifecycle, ownership và telemetry.

## 11. Key takeaway

- `HttpClient` lifecycle thực chất phải reasoning ở handler/connection level.
- Reuse quá ít gây socket churn; reuse quá lâu có thể giữ topology cũ.
- Mỗi remote dependency cần timeout và resilience policy riêng theo semantics.

# 3. EF Core `SaveChanges` batching và transaction boundary: giảm round trip mà không biến một unit of work thành transaction khổng lồ

## 1. What is it?

EF Core thu thập pending entity changes trong `ChangeTracker`, tạo SQL commands và có thể batch nhiều commands vào ít database round trips hơn khi gọi `SaveChanges`/`SaveChangesAsync`.

Batching là transport/execution optimization. Transaction boundary lại là correctness boundary: tập thay đổi nào phải commit hoặc rollback cùng nhau.

Hai khái niệm liên quan nhưng không giống nhau.

## 2. Why does it exist?

Nếu insert 500 rows bằng 500 network round trips, latency có thể bị network/command overhead chi phối. Batching giảm số lần client ↔ database trao đổi.

Nhưng “càng batch nhiều càng tốt” cũng sai. Một transaction cực lớn:

- giữ locks lâu hơn;
- transaction log lớn;
- rollback đắt;
- tăng contention;
- `DbContext` track quá nhiều objects.

## 3. How does it work?

Flow đơn giản:

```text
Add/Modify entities
      -> ChangeTracker
      -> SaveChanges
      -> detect changes
      -> generate commands
      -> batch commands
      -> transaction
      -> execute
      -> accept changes
```

Mặc định một `SaveChanges` có tính transactional với set commands cần thực thi cho operation đó. Nếu business workflow cần nhiều `SaveChanges` cùng atomic, có thể dùng explicit transaction — nhưng cần hiểu retry/side effects.

## 4. Practical implementation

Một import có thể batch business-wise:

```csharp
const int batchSize = 500;

foreach (var batch in rows.Chunk(batchSize))
{
    foreach (var row in batch)
    {
        db.Products.Add(Map(row));
    }

    await db.SaveChangesAsync(ct);
    db.ChangeTracker.Clear();
}
```

Cách này **không** atomic cho toàn bộ file. Nếu requirement là all-or-nothing, transaction semantics phải được thiết kế khác.

Với một order aggregate nhỏ:

```csharp
db.Orders.Add(order);
db.OrderItems.AddRange(order.Items);
await db.SaveChangesAsync(ct);
```

một unit of work tự nhiên thường tốt hơn gọi `SaveChanges` sau từng entity.

## 5. Real production scenario

Một nightly synchronization import 300.000 records. Implementation giữ toàn bộ entities trong một `DbContext` rồi `SaveChanges` một lần.

Memory tăng hàng GB, change detection chậm, transaction dài và log file tăng mạnh. Khi row gần cuối fail constraint, rollback cực đắt.

Chuyển sang bounded batches + checkpoint/idempotent import giúp memory ổn định và failure recovery rõ hơn. Business không cần all-or-nothing cho toàn file, nên transaction khổng lồ vốn không có giá trị.

## 6. Failure scenario & troubleshooting

**Symptom** → `SaveChanges` mất hàng chục giây, memory tăng trước khi gửi SQL, blocking/deadlock tăng.

**Evidence** → `ChangeTracker.Entries().Count()` rất lớn; transaction duration dài; DB log/locks tăng.

**Hypothesis** → unit of work quá lớn hoặc quá nhiều round trips ở cực ngược lại.

**Diagnosis** → đo command count, batch size, tracked entity count, transaction duration, DB waits.

**Fix** → chọn batch size theo workload; clear context giữa batches nếu semantics cho phép; không chia transaction nếu invariant yêu cầu atomicity.

**Verification** → benchmark throughput, memory, lock duration và recovery behavior khi inject failure ở giữa.

## 7. Common mistakes

- Gọi `SaveChanges` trong từng vòng lặp.
- Giữ `DbContext` cho cả job hàng giờ.
- Tăng batch size vô hạn vì muốn “ít round trip”.
- Chia transaction chỉ vì performance rồi phá business invariant.
- Dùng EF tracked entities cho bulk workload mà bulk API/SQL phù hợp hơn.

## 8. Alternatives

`ExecuteUpdate`/`ExecuteDelete`, bulk library hoặc database-native bulk copy phù hợp với mass mutation/import. Raw SQL/stored procedure có thể tốt cho data-processing-heavy workload.

Nếu workload chỉ vài chục entities, `SaveChanges` bình thường là đủ; đừng thêm batching abstraction không cần thiết.

## 9. Trade-offs

### Advantages

- Batching giảm round trips.
- Bounded unit of work kiểm soát memory/lock tốt hơn.
- Transaction boundary có thể align business invariant.

### Costs / Risks

- Chia batch làm mất all-or-nothing nếu business cần.
- Retry/recovery phức tạp hơn với partial progress.
- Bulk optimization có thể bypass domain hooks/change tracking.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `SaveChanges` là persistence boundary, không chỉ “flush object”.

### Middle

Biết tránh `SaveChanges` per row và quản lý `DbContext` scope hợp lý.

### Senior

Đo tracking cost, batching, lock/log impact và partial-failure semantics.

### Technical Lead / Architect

Quyết định transaction boundary theo business correctness trước, sau đó chọn batching/bulk mechanism phù hợp với scale.

## 11. Key takeaway

- Batch size là performance decision; transaction boundary là correctness decision.
- Unit of work quá nhỏ gây round trips; quá lớn gây memory/locking/recovery cost.
- Bulk workload cần design riêng, không nên ép qua tracked entity workflow mặc định.

# 4. PostgreSQL window functions: tính ranking/running total mà không phá row cardinality bằng `GROUP BY`

## 1. What is it?

Window function tính giá trị trên một “window” các rows liên quan nhưng vẫn giữ từng row trong result set.

Khác với `GROUP BY`:

```text
GROUP BY        -> nhiều rows thành một row/group
window function -> giữ rows, thêm derived value theo group/order
```

Ví dụ: `ROW_NUMBER`, `RANK`, `SUM(...) OVER`, `LAG`, `LEAD`.

## 2. Why does it exist?

Nhiều report/query cần cả detail row và context aggregate:

- mỗi order + tổng doanh thu customer;
- top 3 products mỗi category;
- running balance;
- so sánh giá trị hiện tại với row trước.

Nếu dùng subquery/self-join cho mọi trường hợp, SQL dài hơn và có thể làm optimizer xử lý phức tạp hơn.

## 3. How does it work?

Ví dụ ranking theo customer:

```sql
SELECT
    customer_id,
    id,
    total,
    ROW_NUMBER() OVER (
        PARTITION BY customer_id
        ORDER BY total DESC, id
    ) AS rn
FROM orders;
```

`PARTITION BY` chia logical groups; `ORDER BY` trong `OVER` xác định thứ tự trong từng group.

Running total:

```sql
SUM(amount) OVER (
    PARTITION BY account_id
    ORDER BY occurred_at, id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

Frame semantics (`ROWS`, `RANGE`) rất quan trọng khi có duplicate ordering values.

## 4. Practical implementation

Top 3 orders mỗi customer:

```sql
WITH ranked AS (
    SELECT
        o.id,
        o.customer_id,
        o.total,
        ROW_NUMBER() OVER (
            PARTITION BY o.customer_id
            ORDER BY o.total DESC, o.id
        ) AS rn
    FROM orders o
    WHERE o.created_at >= now() - interval '30 days'
)
SELECT id, customer_id, total
FROM ranked
WHERE rn <= 3;
```

Index có thể hỗ trợ filter/order, nhưng phải kiểm tra execution plan thay vì đoán.

## 5. Real production scenario

CRM dashboard cần “3 opportunities lớn nhất của mỗi sales rep trong tháng” cùng total pipeline. Application cũ query từng rep riêng → N+1 database calls.

Một query window function trả toàn bộ result trong một round trip, giảm latency và application-side grouping.

## 6. Failure scenario & troubleshooting

**Symptom** → query window function spill ra disk hoặc sort rất lớn khi dataset tăng.

**Evidence** → `EXPLAIN (ANALYZE, BUFFERS)` cho thấy Sort/WindowAgg cost cao, temp read/write, rows trước filter quá nhiều.

**Hypothesis** → window áp trên dataset quá rộng hoặc ordering không được hỗ trợ tốt.

**Diagnosis** → xem rows đi vào WindowAgg, sort keys, filter selectivity, memory/temp usage.

**Fix** → filter sớm, index phù hợp với access pattern, pre-aggregate nếu business cho phép, tránh tính nhiều windows không cần thiết.

**Verification** → so buffers, execution time và temp usage với production-like cardinality.

## 7. Common mistakes

- Dùng `RANK` khi thật sự cần unique sequence như `ROW_NUMBER`.
- Bỏ tie-breaker khiến ordering không deterministic.
- Không hiểu default window frame với duplicate sort values.
- Tính window trên toàn bảng rồi mới filter subset có thể filter trước.
- Kéo data về C# để ranking dù DB làm tốt hơn.

## 8. Alternatives

`GROUP BY` phù hợp khi output chỉ cần aggregate per group. Correlated subquery có thể đủ cho query nhỏ. Materialized view phù hợp report đắt được đọc nhiều và freshness cho phép.

## 9. Trade-offs

### Advantages

- Giữ detail row cùng aggregate/ranking context.
- Giảm application-side processing và round trips.
- Expressive cho analytics/reporting.

### Costs / Risks

- Sort/window trên dataset lớn có thể tốn memory/temp I/O.
- Frame/order semantics dễ bị hiểu sai.
- Query phức tạp cần execution-plan literacy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt `GROUP BY` làm mất detail row còn window function thì không.

### Middle

Viết `ROW_NUMBER`, `SUM OVER`, `LAG/LEAD` với deterministic ordering.

### Senior

Đọc `EXPLAIN ANALYZE`, đánh giá sort/spill/index và cardinality.

### Technical Lead / Architect

Quyết định logic analytics nên chạy realtime query, read model hay precomputed reporting store dựa trên scale/freshness.

## 11. Key takeaway

- Window function giải quyết “aggregate/rank nhưng vẫn giữ từng row”.
- Ordering và frame là correctness semantics.
- Query analytics lớn vẫn phải được đo bằng execution plan và I/O evidence.

# 5. Bulkhead isolation + bounded concurrency: ngăn một dependency chậm ăn hết ThreadPool, connection pool hoặc request capacity

## 1. What is it?

Bulkhead Pattern chia capacity thành các khu vực giới hạn để failure/overload của một dependency hoặc workload không tiêu thụ toàn bộ resource chung.

Tên đến từ khoang kín trên tàu: một khoang thủng không làm nước tràn toàn bộ tàu.

Trong backend, bulkhead có thể là:

- concurrency limit;
- worker pool riêng;
- connection pool riêng;
- queue/capacity riêng;
- service/process isolation.

## 2. Why does it exist?

Giả sử API gọi Review service. Review service chậm từ 100 ms lên 15 giây. Nếu mỗi incoming request tiếp tục giữ một outbound operation:

```text
traffic vẫn đến
 -> in-flight calls tăng
 -> sockets/connections/tasks tăng
 -> request queue tăng
 -> unrelated endpoints cũng chậm
```

Timeout giúp giới hạn duration, nhưng trước khi timeout xảy ra, hàng nghìn calls vẫn có thể đồng thời chiếm capacity.

Bulkhead giới hạn **bao nhiêu work được phép in-flight**.

## 3. How does it work?

Ví dụ dùng `SemaphoreSlim` như local concurrency gate:

```text
Requests -> Bulkhead(limit=50)
              | accepted <= 50
              v
          Review API

extra requests -> wait bounded / reject / fallback
```

Bulkhead thường phối hợp với timeout, retry và circuit breaker. Thứ tự/policy phải có chủ đích; retry nằm trong bulkhead sai cách có thể giữ permit quá lâu.

## 4. Practical implementation

```csharp
public sealed class ReviewGateway
{
    private readonly SemaphoreSlim _gate = new(50, 50);
    private readonly HttpClient _http;

    public ReviewGateway(HttpClient http) => _http = http;

    public async Task<ReviewSummary?> GetAsync(
        Guid productId,
        CancellationToken ct)
    {
        if (!await _gate.WaitAsync(TimeSpan.FromMilliseconds(100), ct))
            return null; // explicit degraded behavior

        try
        {
            using var timeout = CancellationTokenSource.CreateLinkedTokenSource(ct);
            timeout.CancelAfter(TimeSpan.FromSeconds(2));

            return await _http.GetFromJsonAsync<ReviewSummary>(
                $"reviews/{productId}",
                timeout.Token);
        }
        finally
        {
            _gate.Release();
        }
    }
}
```

Trong production có thể dùng resilience pipeline/library, nhưng mental model capacity vẫn giống nhau.

## 5. Real production scenario

Product page compose data từ Product API, Reviews, Inventory và Recommendations. Recommendations bị latency spike.

Không isolation, requests chờ recommendations chiếm phần lớn outbound sockets và request concurrency; Product endpoint core cũng chậm.

Bulkhead giới hạn recommendation calls, sau đó UI nhận product page không có recommendations trong vài phút. Business chấp nhận degraded feature tốt hơn full outage.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency A chậm nhưng toàn API latency tăng, connection pool/ThreadPool queue tăng.

**Evidence** → traces cho thấy nhiều in-flight spans tới A; unrelated routes chậm theo; bulk capacity không tồn tại.

**Hypothesis** → failure propagation qua shared resource exhaustion.

**Diagnosis** → đo concurrent calls per dependency, queue wait, timeout count, pool saturation.

**Fix** → bounded concurrency, short timeout theo latency budget, reject/fallback, tách worker/pool nếu cần.

**Verification** → fault injection dependency A và xác nhận route/dependency B vẫn giữ SLO.

## 7. Common mistakes

- Chỉ thêm retry, làm in-flight work tăng hơn nữa.
- Bulkhead queue vô hạn.
- Limit quá thấp tùy ý gây self-throttling.
- Fallback trả data sai business semantics.
- Một global semaphore cho mọi dependency khiến isolation biến mất.

## 8. Alternatives

Rate limiting giới hạn arrival rate; bulkhead giới hạn concurrent resource use. Circuit breaker giảm calls khi dependency đang fail. Queue tách temporal coupling nhưng thêm eventual consistency.

Ở workload nhỏ, timeout tốt có thể đủ; không cần mọi integration đều có dedicated bulkhead.

## 9. Trade-offs

### Advantages

- Giảm cascading failure.
- Bảo vệ shared resources.
- Cho phép graceful degradation.

### Costs / Risks

- Capacity tuning phức tạp.
- Có thể reject request dù dependency còn phục vụ được thêm.
- Nhiều isolation pools tăng operational/configuration overhead.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dependency chậm có thể làm service khác chậm dù không crash.

### Middle

Implement timeout và bounded concurrency đúng cleanup/cancellation.

### Senior

Đo concurrency, queueing, retry amplification và downstream capacity.

### Technical Lead / Architect

Xác định feature nào được degraded, capacity budget theo dependency và mức isolation vật lý/logical cần thiết.

## 11. Key takeaway

- Timeout giới hạn thời gian; bulkhead giới hạn số operation đồng thời.
- Isolation chỉ có giá trị khi failure của một dependency không chiếm resource của phần còn lại.
- Capacity phải được đo và bounded; queue vô hạn chỉ trì hoãn overload.

# 6. Azure App Service deployment slots: warm-up, swap và rollback mà không nhầm “zero downtime” với “zero risk”

## 1. What is it?

Deployment slot là environment chạy song song trong cùng App Service, ví dụ `production` và `staging`. Code version mới có thể deploy vào staging, warm up/validate rồi swap vào production.

```text
v1 -> production slot
v2 -> staging slot

validate v2
   -> swap
v2 -> production
v1 -> staging
```

Swap giảm deployment interruption nhưng không tự bảo đảm application/version mới đúng.

## 2. Why does it exist?

In-place deployment có thể làm process restart đúng lúc files đang được thay, startup cold, hoặc health chưa sẵn sàng. Slot cho phép prepare version mới trước khi nhận production traffic.

Nó cũng tạo rollback path nhanh hơn nếu old version vẫn tồn tại trong slot kia.

## 3. How does it work?

Một số configuration có thể đánh dấu “slot setting” để không swap, ví dụ environment-specific secrets/endpoints. Những settings khác đi theo slot swap behavior.

Warm-up phải thực sự khởi tạo những gì request đầu cần: application startup, JIT, config validation, dependency connectivity ở mức phù hợp.

Database là shared external state, nên slot rollback application không tự rollback schema/data migration.

## 4. Practical implementation

Health endpoints tách semantics:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<StartupHealthCheck>("startup");

app.MapHealthChecks("/health/ready");
```

CI/CD flow:

```text
build immutable artifact
 -> deploy staging slot
 -> apply compatible config
 -> warm-up
 -> smoke/integration checks
 -> swap
 -> observe error/latency metrics
 -> swap back if application regression
```

Migration destructive không nên nằm trong flow mà rollback binary cũ sẽ không còn tương thích.

## 5. Real production scenario

Team deploy API v2 vào staging, smoke test pass, swap production. Error rate tăng vì production-only tenant config khác staging expectation.

Swap back nhanh, nhưng database migration đã rename column trước đó nên v1 cũng fail.

Bài học: slot giải quyết compute deployment boundary; schema compatibility vẫn phải dùng expand/migrate/contract hoặc strategy tương đương.

## 6. Failure scenario & troubleshooting

**Symptom** → swap thành công ở Azure nhưng production trả 5xx hoặc latency tăng ngay sau swap.

**Evidence** → deployment event trùng error spike; startup/health logs; slot-specific configuration diff.

**Hypothesis** → warm-up không cover real dependency/config hoặc code/schema incompatibility.

**Diagnosis** → compare slot settings, dependency endpoints, app version, DB schema, health telemetry.

**Fix** → restore compatible version/config; swap back nếu schema cho phép; sửa pre-swap validation.

**Verification** → production-like smoke test + post-swap SLO gate.

## 7. Common mistakes

- Gọi slot swap là zero-risk deployment.
- Secrets/connection strings không được đánh dấu slot-specific đúng.
- Health check chỉ trả `200` hardcoded.
- Chạy destructive DB migration trước swap.
- Không monitor sau swap vì “deployment đã success”.

## 8. Alternatives

Blue-Green deployment ở infrastructure riêng cho isolation mạnh hơn. Canary giảm blast radius bằng cách route một phần traffic. Rolling deployment đơn giản hơn trên platforms hỗ trợ nhiều replicas.

Với application ít traffic và downtime chấp nhận được, slot có thể là complexity không cần thiết.

## 9. Trade-offs

### Advantages

- Warm-up trước production traffic.
- Rollback application nhanh.
- Giảm in-place deployment interruption.

### Costs / Risks

- Thêm slot/configuration management.
- Shared dependencies vẫn là coupling point.
- Có cost compute tùy App Service plan/setup.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy artifact và release traffic có thể là hai bước khác nhau.

### Middle

Biết deploy staging, health-check và swap đúng configuration.

### Senior

Thiết kế smoke/SLO gates, rollback và schema compatibility.

### Technical Lead / Architect

Chọn slot, blue-green, canary hay rolling dựa trên blast radius, rollback requirement, database lifecycle và cost.

## 11. Key takeaway

- Slot swap giảm downtime nhưng không loại bỏ application/data risk.
- Rollback binary chỉ an toàn nếu schema/config vẫn backward-compatible.
- Deploy phải kết thúc bằng health/SLO verification, không phải bằng “swap succeeded”.

# 7. ThreadPool starvation trong ASP.NET Core: phân biệt CPU saturation với blocking-induced queue growth

## 1. What is it?

ThreadPool starvation xảy ra khi application cần thread để tiếp tục xử lý work nhưng available worker threads không đủ, thường vì nhiều threads đang bị block lâu trên synchronous waits hoặc external operations.

Nó khác CPU saturation:

```text
CPU saturation:
threads đang chạy computation -> CPU ~100%

ThreadPool starvation:
threads bị giữ/block -> work queue tăng
CPU có thể chưa 100%
```

## 2. Why does it exist?

ASP.NET Core dựa mạnh vào asynchronous I/O để một số lượng threads hữu hạn phục vụ nhiều concurrent requests.

Nếu code biến I/O async thành blocking:

```csharp
var result = SomeAsync().Result;
```

thread phải đứng chờ. Với nhiều request đồng thời, ThreadPool phải inject thêm threads nhưng ramp-up không tức thời; queue latency tăng.

## 3. How does it work?

Normal async:

```text
request thread
 -> start DB I/O
 -> thread returns to pool
 -> DB completes
 -> continuation gets a thread
```

Blocking:

```text
request thread
 -> DB async call
 -> .Result / Wait()
 -> thread remains blocked
 -> more requests block more threads
 -> queue grows
```

Starvation cũng có thể đến từ lock contention, synchronous file/network I/O hoặc long-running CPU work chạy sai chỗ.

## 4. Practical implementation

Propagate async:

```csharp
public async Task<IResult> GetOrderAsync(
    Guid id,
    CancellationToken ct)
{
    var order = await _repository.GetAsync(id, ct);
    return order is null ? Results.NotFound() : Results.Ok(order);
}
```

Không:

```csharp
var order = _repository.GetAsync(id, ct).Result;
```

Khi cần CPU-heavy work, không mặc định `Task.Run` trong request để “fix”. Nếu workload lớn/durable, cân nhắc background queue/worker và admission control.

## 5. Real production scenario

API p95 tăng từ 200 ms lên 6 giây trong peak traffic. CPU chỉ 45%, SQL latency bình thường. Team ban đầu scale CPU nhưng không cải thiện.

`dotnet-counters` cho thấy ThreadPool queue length tăng; dump stack có nhiều threads blocked ở `.GetAwaiter().GetResult()` trong legacy SDK wrapper.

Root cause là sync-over-async, không phải thiếu CPU.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng mạnh, request queue tăng, CPU chưa tương ứng cao.

**Evidence** → ThreadPool queue length cao, available threads thấp/threads tăng dần, stacks có `.Wait`, `.Result`, monitor locks hoặc sync I/O.

**Hypothesis** → starvation/lock contention.

**Diagnosis** → `dotnet-counters`, `dotnet-trace`, dump/profiler; correlate with request traces.

**Fix** → async end-to-end, giảm blocking critical sections, isolate CPU-heavy work, bound concurrency.

**Verification** → load test cùng concurrency; queue length không tăng tuyến tính, p95/p99 phục hồi.

## 7. Common mistakes

- Chỉ nhìn CPU metric.
- Tăng minimum ThreadPool threads như permanent fix mà không xử lý blocking.
- Dùng `Task.Run` quanh synchronous network/database call trong server code.
- Lock quanh I/O.
- Fire-and-forget work trong request process làm contention khó thấy.

## 8. Alternatives

Nếu library chỉ có synchronous API và không thể thay đổi, có thể cần bounded dedicated worker/concurrency isolation thay vì đẩy vô hạn work vào ThreadPool.

CPU-bound workload thực sự có thể scale bằng more compute/parallelism, nhưng phải phân biệt đúng trước.

## 9. Trade-offs

### Advantages

Async I/O giúp throughput cao với ít threads và giảm queueing khi dependency latency tăng vừa phải.

### Costs / Risks

Async call chain đòi hỏi cancellation/error handling đúng. Không phải mọi operation đều có async API. Concurrency không bounded vẫn có thể overload downstream.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async I/O không cần giữ thread trong lúc chờ.

### Middle

Tránh `.Result/.Wait()` và propagate cancellation.

### Senior

Phân tích counters/stacks, tách CPU saturation khỏi starvation và lock contention.

### Technical Lead / Architect

Đặt capacity model, chọn isolation/queueing cho legacy blocking dependencies và không dùng thread-count tuning để che architectural bottleneck.

## 11. Key takeaway

- CPU thấp không có nghĩa server còn nhiều request capacity.
- ThreadPool queue + stack evidence quan trọng khi latency tăng mà CPU không bão hòa.
- Fix root blocking/concurrency pattern trước khi tuning thread counts.

# 8. Octopus Deploy variable scoping + secret ownership: giữ artifact bất biến nhưng configuration thay đổi theo environment an toàn

## 1. What is it?

Trong release pipeline, artifact nên bất biến: cùng package/build được promote qua Dev → Test → Staging → Production. Configuration khác nhau theo environment được inject tại deployment/runtime.

Octopus Deploy hỗ trợ variables scoped theo environment, target, role, channel... và sensitive variables cho secrets.

Mental model:

```text
one artifact
  -> Dev config
  -> Test config
  -> Prod config
```

Không rebuild binary riêng cho từng environment nếu không có lý do rất đặc biệt.

## 2. Why does it exist?

Nếu build Production khác build QA, QA không thực sự kiểm thử đúng artifact sẽ chạy Production.

Nếu connection strings/API keys hardcode trong package:

- secret leak vào artifact/log/source;
- rotation cần rebuild;
- artifact không portable;
- environment drift khó kiểm soát.

Variable scoping tách code artifact khỏi deployment configuration.

## 3. How does it work?

Deployment engine resolve effective variable theo scope/context:

```text
Variable: CatalogApiUrl
Dev  -> https://catalog-dev/...
Prod -> https://catalog-prod/...
```

Sensitive value nên được mask/encrypted theo platform capabilities và không echo vào script output.

Quan trọng hơn tool: phải xác định **source of truth**. Secret có thể nằm ở Key Vault và deployment chỉ inject reference/identity thay vì copy secret qua nhiều systems.

## 4. Practical implementation

App configuration:

```csharp
var catalogUrl = builder.Configuration["Catalog:BaseUrl"]
    ?? throw new InvalidOperationException("Catalog BaseUrl missing");
```

Pipeline deploy cùng artifact:

```text
MyApi.1.4.2.zip
   -> Dev: Catalog__BaseUrl=...
   -> QA:  Catalog__BaseUrl=...
   -> Prod:Catalog__BaseUrl=...
```

Với Azure-hosted app, ưu tiên Managed Identity + Key Vault cho secret thay vì đưa long-lived credential qua nhiều variable stores.

## 5. Real production scenario

Team rebuild release package cho mỗi environment bằng config transform. Một hotfix được QA test với build #A nhưng Production build lại thành #B do pipeline rebuild; package dependency resolution khác và Production crash.

Chuyển sang immutable artifact promotion loại một lớp drift. Environment differences chỉ còn configuration được version/control riêng.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng version chạy QA nhưng fail Production do endpoint/secret/config sai.

**Evidence** → deployment snapshot variable scope, environment config diff, startup validation logs.

**Hypothesis** → variable scope collision hoặc configuration ownership không rõ.

**Diagnosis** → xác định effective value tại target; không dump sensitive value; kiểm tra precedence/source.

**Fix** → giảm scope complexity, startup validation, centralize secret source, immutable artifact.

**Verification** → deployment dry-run/smoke test và compare non-secret config contract giữa environments.

## 7. Common mistakes

- Rebuild artifact cho Production.
- Dùng một variable name với quá nhiều overlapping scopes khó dự đoán.
- Echo secrets trong PowerShell/log để debug.
- Copy Key Vault secret sang nhiều deployment stores không cần thiết.
- Không fail-fast khi required config thiếu.

## 8. Alternatives

Azure DevOps/GitHub Actions/Jenkins có configuration mechanisms khác nhưng nguyên tắc artifact immutability giống nhau. Runtime Key Vault/config provider giảm secret replication hơn deployment-time substitution.

## 9. Trade-offs

### Advantages

- QA/Prod chạy cùng artifact.
- Rollback/version trace rõ hơn.
- Configuration/secret rotation độc lập build.

### Costs / Risks

- Scope hierarchy có thể phức tạp.
- Nhiều configuration sources gây precedence confusion.
- Secret management cần ownership/audit riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu code artifact và environment configuration là hai concerns khác nhau.

### Middle

Biết scope variables, startup validation và không log secrets.

### Senior

Debug configuration precedence, immutable promotion và secret rotation path.

### Technical Lead / Architect

Định nghĩa source of truth cho config/secrets, promotion model và governance để tránh environment drift.

## 11. Key takeaway

- Build once, promote the same artifact.
- Secret càng bị copy qua nhiều systems, blast radius và rotation cost càng lớn.
- Configuration precedence phải đơn giản đủ để operator hiểu giá trị thực tế đến từ đâu.

# 9. Technical SEO với canonical URL + redirect chain: tránh duplicate indexing và latency do URL normalization sai

## 1. What is it?

Canonical URL là URL mà site tuyên bố là phiên bản ưu tiên của một page khi cùng nội dung có thể xuất hiện dưới nhiều URL.

Redirect normalization là việc đưa các URL variants về một URL chính bằng HTTP redirect, thường `301`/`308` cho redirect lâu dài tùy semantics.

Ví dụ variants:

```text
/products/123
/products/123?utm_source=email
/Products/123
/product?id=123
```

Canonical hint và redirect giải quyết vấn đề khác nhau: canonical là tín hiệu indexing; redirect là HTTP navigation behavior.

## 2. Why does it exist?

Duplicate URLs có thể phát sinh từ:

- tracking query strings;
- CMS aliases;
- uppercase/lowercase routes;
- trailing slash policy;
- legacy URL migration;
- filtering/sorting pages.

Nếu hệ thống không có URL ownership rõ, crawler phân tán crawl/index signals, analytics phân mảnh và user đi qua nhiều redirect hops làm latency tăng.

## 3. How does it work?

Một request legacy có thể đi:

```text
http://example.com/Product/123
 -> https redirect
 -> lowercase redirect
 -> new route redirect
 -> /products/123
```

Ba hops là waste. Tốt hơn normalize trực tiếp đến final target khi có thể.

HTML final page:

```html
<link rel="canonical" href="https://example.com/products/123" />
```

Canonical không nên trỏ vòng, chain hoặc tới URL trả lỗi.

## 4. Practical implementation

ASP.NET Core redirect legacy route trực tiếp:

```csharp
app.MapGet("/product", (HttpRequest request) =>
{
    if (!int.TryParse(request.Query["id"], out var id))
        return Results.BadRequest();

    return Results.Redirect(
        $"/products/{id}",
        permanent: true,
        preserveMethod: true);
});
```

Razor/SSR page canonical:

```html
<link rel="canonical" href="@Model.CanonicalUrl" />
```

Canonical URL nên được tạo từ routing/content identity, không lấy nguyên query string của request.

## 5. Real production scenario

E-commerce migration đổi `/p?id=42` sang `/products/blue-shirt`. CDN/reverse proxy thêm HTTP→HTTPS redirect, application thêm lowercase redirect, CMS redirect legacy path. Bot/user đi qua 3–4 hops trước final page.

Lighthouse/network waterfall cho thấy navigation chậm; crawler log cho thấy lượng request vào aliases rất lớn.

Team xây redirect map trực tiếp old → final canonical URL và giảm hops.

## 6. Failure scenario & troubleshooting

**Symptom** → search engine index nhiều URL cho cùng product, crawl traffic cao bất thường hoặc redirect latency đáng kể.

**Evidence** → server/CDN logs, redirect chains, canonical tags khác nhau, Search Console/crawler data khi có.

**Hypothesis** → URL normalization/canonical policy không nhất quán giữa CDN, app và CMS.

**Diagnosis** → trace từng variant qua HTTP status/location; kiểm tra final canonical, robots/indexability và sitemap.

**Fix** → một canonical policy; redirect trực tiếp tới final URL; loại loop/chain; sitemap chỉ chứa canonical URLs.

**Verification** → automated URL test cho legacy/variant paths và crawl representative pages.

## 7. Common mistakes

- Canonical tất cả pagination/filter pages về một page dù content intent khác.
- Canonical URL trả redirect hoặc 404.
- Redirect chain qua nhiều layers.
- Dùng `302` cho migration vĩnh viễn mà không có chủ đích.
- App, CMS và CDN mỗi nơi tự normalize theo rule khác nhau.

## 8. Alternatives

Nếu duplicate URL không thể tránh, canonical hint có thể đủ. Khi old URL không còn cần tồn tại, permanent redirect rõ hơn. `robots.txt` không phải công cụ canonicalization và không nên dùng để “fix duplicate content” một cách máy móc.

## 9. Trade-offs

### Advantages

- URL identity rõ.
- Giảm duplicate crawling/index fragmentation.
- Ít redirect hops cải thiện latency.

### Costs / Risks

- Redirect map lớn cần lifecycle/test.
- Sai permanent redirect có thể ảnh hưởng traffic lâu dài.
- Canonical rules cho faceted navigation cần business/search judgment.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một content entity có thể bị expose bởi nhiều URLs và HTTP redirect khác canonical tag.

### Middle

Implement canonical/redirect đúng status và test chain.

### Senior

Phân tích CDN/CMS/app routing, crawl logs, pagination/filter semantics và performance impact.

### Technical Lead / Architect

Đặt ownership URL strategy giữa CMS, commerce, CDN và application; đảm bảo migration/backward compatibility có redirect plan có thể vận hành.

## 11. Key takeaway

- Canonical là indexing signal; redirect là navigation/protocol behavior.
- URL normalization nên kết thúc ở một final target với ít hops nhất.
- SEO engineering tốt cần phối hợp routing, CMS, CDN và observability chứ không chỉ thêm meta tag.

# 10. ADR (Architecture Decision Record): lưu quyết định, context và trade-off để architecture không phụ thuộc trí nhớ của vài người

## 1. What is it?

ADR là một record ngắn lưu một quyết định kỹ thuật/kiến trúc có ý nghĩa cùng context, alternatives và consequences.

Một ADR tốt không chỉ ghi:

> “Dùng Redis.”

Nó nên trả lời:

```text
Context: vấn đề nào đang tồn tại?
Decision: chọn gì?
Alternatives: đã cân nhắc gì?
Consequences: lợi ích/cost/risk nào chấp nhận?
Status: proposed / accepted / superseded...
```

## 2. Why does it exist?

Sau 6–12 tháng, code chỉ cho biết **hệ thống đang làm gì**, thường không cho biết **tại sao**.

Không có decision history, team dễ:

- lặp lại tranh luận cũ;
- xóa workaround mà không biết constraint lịch sử;
- giữ technology mãi vì “chắc có lý do”; 
- onboarding chậm;
- architecture phụ thuộc tribal knowledge.

ADR tạo institutional memory nhẹ hơn tài liệu thiết kế dài.

## 3. How does it work?

Lifecycle ví dụ:

```text
Problem emerges
 -> gather constraints/evidence
 -> evaluate alternatives
 -> ADR proposed
 -> review
 -> accepted
 -> implementation
 -> later constraint changes
 -> ADR superseded by new ADR
```

ADR nên immutable-ish về historical decision: nếu quyết định thay đổi, tạo record mới supersede record cũ thay vì rewrite history như chưa từng tồn tại.

## 4. Practical implementation

Ví dụ Markdown:

```markdown
# ADR-014: Use Redis cache for product summaries

## Status
Accepted

## Context
Product API p95 is dominated by repeated catalog reads...

## Decision
Use cache-aside Redis with 60s TTL for public product summaries.

## Alternatives
- No cache
- IMemoryCache
- CDN-only caching

## Consequences
- Redis becomes a shared dependency
- Stale data up to 60s is accepted
- Invalidation owner is Catalog service
```

ADR nên nằm gần repository/docs nơi engineers có thể discover và review cùng code change.

## 5. Real production scenario

Một team thấy custom generic repository phức tạp và muốn xóa. Không ai nhớ abstraction tồn tại vì trước đây application phải support SQL Server và một temporary external store trong migration.

ADR cho thấy migration đã hoàn tất hai năm trước và constraint không còn. Team có evidence để simplify architecture thay vì giữ abstraction vô thời hạn hoặc xóa mù.

## 6. Failure scenario & troubleshooting

**Symptom** → ADR folder có hàng trăm files nhưng không ai đọc; decisions trong code khác tài liệu.

**Evidence** → ADR “Accepted” nhưng implementation đã thay; không có superseded links; documents dài như design spec.

**Hypothesis** → ADR trở thành compliance artifact thay vì decision tool.

**Diagnosis** → review recent architecture changes: quyết định nào đáng ADR, record nào còn discoverable/current status.

**Fix** → giữ ADR ngắn, chỉ record consequential decisions, link superseding record, review ADR trong PR/architecture review.

**Verification** → một engineer mới có thể tìm lý do của một major technology/boundary decision mà không hỏi tác giả cũ.

## 7. Common mistakes

- Viết ADR cho mọi coding choice nhỏ.
- Chỉ ghi quyết định, không ghi context/trade-offs.
- Rewrite ADR cũ làm mất lịch sử.
- Ghi “best practice” thay vì constraint cụ thể của system.
- ADR không có owner/review link và bị drift khỏi code.

## 8. Alternatives

Design doc phù hợp thay đổi lớn cần nhiều diagram/analysis trước implementation. README phù hợp hướng dẫn current state. Issue/PR discussion hữu ích nhưng thường khó discover lâu dài.

ADR bổ sung, không thay thế tất cả tài liệu khác.

## 9. Trade-offs

### Advantages

- Decision history ngắn và searchable.
- Giảm tribal knowledge.
- Làm trade-off/constraint explicit.
- Hữu ích khi revisit/refactor architecture.

### Costs / Risks

- Cần discipline để cập nhật status/supersede.
- Quá nhiều ADR tạo noise.
- Record kém chất lượng có thể rationalize quyết định sau sự kiện thay vì phản ánh reasoning thật.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết tìm decision context trước khi thay major architecture component.

### Middle

Đóng góp evidence/alternatives và link implementation với ADR.

### Senior

Viết ADR dựa trên constraints, failure modes và measurable trade-offs thay vì preference.

### Technical Lead / Architect

Quyết định cái gì đủ consequential để record, ensure review, và chủ động supersede decision khi context thay đổi thay vì bảo vệ quyết định cũ vô thời hạn.

## 11. Key takeaway

- Architecture cần lưu “why”, không chỉ “what”.
- ADR nên ngắn, consequential và có alternatives/consequences.
- Quyết định tốt ở thời điểm cũ có thể không còn đúng; supersede history thay vì xóa lịch sử.
