# 1. C# nullable reference types: biến nullability thành contract ở compile time, không phải runtime guard tự động

## 1. What is it?

Nullable reference types (NRT) cho compiler biết một reference được kỳ vọng có thể `null` (`string?`) hay không (`string`). Đây là static-analysis contract; nó không thay đổi CLR representation và không tự chèn runtime null check.

## 2. Why does it exist?

Trước NRT, `string` không nói được caller có thể nhận `null` hay không. Contract mơ hồ đẩy lỗi sang production dưới dạng `NullReferenceException`, đặc biệt tại API, database và third-party integration boundaries.

## 3. How does it work?

Compiler thực hiện flow analysis: theo dõi assignment, branch và annotation để cảnh báo dereference có khả năng null. Metadata nullability cũng giúp tooling và libraries truyền contract qua assembly boundary.

## 4. Practical implementation

```csharp
public sealed record CustomerDto(string Id, string? MiddleName);

public string NormalizeEmail(string email)
{
    ArgumentException.ThrowIfNullOrWhiteSpace(email);
    return email.Trim().ToLowerInvariant();
}
```

Không dùng `!` chỉ để làm compiler im lặng; hãy validate tại boundary rồi giữ core model càng non-null càng tốt.

## 5. Real production scenario

CRM import nhận `middleName` optional nhưng `customerId` bắt buộc. DTO thể hiện đúng nullability, validation loại request thiếu ID, application layer không phải lặp `if (id is null)` ở mọi nơi.

## 6. Failure scenario & troubleshooting

**Symptom:** production vẫn có `NullReferenceException` dù project bật NRT. **Evidence:** stack trace đi từ deserialization hoặc legacy library. **Hypothesis:** runtime input vi phạm compile-time contract. **Diagnosis:** kiểm tra boundary và warning suppression. **Fix:** validate/deserialization contract, annotation đúng, bỏ `!` không có bằng chứng. **Verification:** integration test payload thiếu/null.

## 7. Common mistakes

Dùng `!` tràn lan; đổi mọi property thành `?` để hết warning; tin rằng NRT là runtime validation; không annotate legacy boundary; map database nullable column sang non-null property mà không migration dữ liệu.

## 8. Alternatives

Runtime validation (`DataAnnotations`, FluentValidation, guard clauses) bảo vệ input thật; NRT bảo vệ compile-time flow. Hai cơ chế bổ sung nhau, không thay thế nhau.

## 9. Trade-offs

### Advantages

Contract rõ hơn, IDE/compiler phát hiện lỗi sớm, refactoring an toàn hơn.

### Costs / Risks

Migration codebase cũ tạo nhiều warning; annotation sai tạo false confidence; interop với library cũ cần judgment.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `T` và `T?` là contract về khả năng null.

### Middle

Thiết kế DTO/domain mapping và validation boundary đúng, xử lý warning thay vì suppress.

### Senior

Nhận diện nơi static contract không đủ: deserialization, database, reflection, legacy/third-party code.

### Technical Lead / Architect

Lập chiến lược enable NRT theo module, warning policy và migration boundary mà không biến rollout thành refactor khổng lồ.

## 11. Key takeaway

- NRT là static contract, không phải runtime validation.
- Validate dữ liệu ở boundary rồi giữ core model chặt.
- `!` chỉ hợp lý khi có invariant mà compiler không chứng minh được.

# 2. ASP.NET Core request timeout: thiết kế latency budget xuyên request thay vì đặt timeout rời rạc

## 1. What is it?

Request timeout là giới hạn thời gian một operation còn có giá trị. Mental model tốt hơn một con số timeout là **end-to-end latency budget** được tiêu thụ dần qua API, database và remote dependencies.

## 2. Why does it exist?

Nếu client chỉ chờ 2 giây nhưng backend giữ HTTP call 30 giây và SQL command 60 giây, work vô ích vẫn giữ connection, memory và downstream capacity. Dưới tải cao, slow dependency biến thành queueing và cascading failure.

## 3. How does it work?

ASP.NET Core nhận cancellation từ request; application truyền token xuống dependency. Mỗi downstream operation cần timeout nhỏ hơn remaining budget, còn retry phải nằm trong cùng tổng budget.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:int}", async (
    int id, OrderService service, HttpContext ctx) =>
{
    var order = await service.GetAsync(id, ctx.RequestAborted);
    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

`HttpClient`, EF Core và application service đều phải nhận token thay vì tạo một cancellation island riêng.

## 5. Real production scenario

Product page có SLO p95 dưới 800 ms và gọi Product API + Reviews API. Reviews chậm không nên giữ toàn request 10 giây; team dành budget cho từng dependency và có degradation path nếu reviews không critical.

## 6. Failure scenario & troubleshooting

**Symptom:** reverse proxy trả 504 nhưng CPU/DB vẫn cao sau đó. **Evidence:** trace span tiếp tục sau client disconnect. **Hypothesis:** cancellation không được propagate. **Diagnosis:** tìm method thiếu token hoặc library không hỗ trợ cancellation. **Fix:** propagate token, align timeout/retry. **Verification:** inject slow dependency và xác nhận work dừng theo deadline.

## 7. Common mistakes

Đặt timeout độc lập ở từng layer; retry 3 lần với timeout bằng toàn budget; catch `OperationCanceledException` thành 500; không phân biệt caller cancellation và dependency timeout.

## 8. Alternatives

Với non-critical work, chuyển sang queue/background processing. Với operation cần kết quả đồng bộ, timeout + degradation/circuit breaker thường phù hợp hơn.

## 9. Trade-offs

### Advantages

Bảo vệ capacity, giới hạn tail latency, failure behavior dự đoán được hơn.

### Costs / Risks

Timeout quá ngắn tạo false failure; cancellation support không đồng đều; retry budget cần thiết kế cẩn thận.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout khác retry và cancellation phải được truyền xuống.

### Middle

Implement token propagation và test slow dependency.

### Senior

Thiết kế timeout/retry/degradation theo latency distribution và idempotency.

### Technical Lead / Architect

Phân bổ end-to-end budget theo SLO và criticality, quyết định dependency nào được phép làm request fail.

## 11. Key takeaway

- Timeout là capacity protection, không chỉ UX.
- Retry phải tiêu thụ cùng latency budget.
- Trace phải cho thấy work dừng khi request không còn giá trị.

# 3. PostgreSQL JSONB + GIN index: linh hoạt schema nhưng vẫn phải thiết kế theo query pattern

## 1. What is it?

`jsonb` lưu JSON ở dạng binary đã parse, hỗ trợ operator và indexing. GIN index phù hợp cho containment/existence queries trên nhiều keys, nhưng không biến JSONB thành lựa chọn mặc định cho mọi cột linh hoạt.

## 2. Why does it exist?

Một số thuộc tính thay đổi theo product type hoặc integration payload, khiến schema cột cố định quá cứng. JSONB cho phép giữ phần dữ liệu biến thiên trong relational database mà vẫn query được.

## 3. How does it work?

PostgreSQL parse JSON thành `jsonb`; GIN index lưu inverted entries để tìm documents chứa key/value. Query planner chọn index dựa trên operator, statistics và estimated cost.

## 4. Practical implementation

```sql
CREATE TABLE products (
    id bigint PRIMARY KEY,
    sku text NOT NULL UNIQUE,
    attributes jsonb NOT NULL DEFAULT '{}'::jsonb
);

CREATE INDEX ix_products_attributes_gin
ON products USING gin (attributes jsonb_path_ops);

SELECT id, sku
FROM products
WHERE attributes @> '{"color":"black"}';
```

## 5. Real production scenario

Marketplace có category Laptop, Tire và Phone với attributes khác nhau. Core fields như SKU, price, owner vẫn là typed columns; category-specific searchable attributes nằm trong JSONB.

## 6. Failure scenario & troubleshooting

**Symptom:** filter JSONB chậm dù có GIN index. **Evidence:** `EXPLAIN (ANALYZE, BUFFERS)` cho sequential scan. **Hypothesis:** operator không được index hỗ trợ hoặc selectivity thấp. **Diagnosis:** kiểm tra operator class, row estimate, I/O. **Fix:** đổi query/index hoặc promote hot attribute thành typed/generated column. **Verification:** so sánh plan và buffer reads.

## 7. Common mistakes

Nhét toàn entity vào JSONB; dùng JSONB để tránh migration; index toàn bộ payload lớn; không validate shape; dùng expression khiến index không match.

## 8. Alternatives

Typed columns cho fields ổn định; child table/EAV cho mô hình khác; document database khi aggregate/document workload thực sự chi phối.

## 9. Trade-offs

### Advantages

Schema linh hoạt, vẫn có transaction/joins của PostgreSQL, query JSON mạnh.

### Costs / Risks

Validation yếu hơn typed schema, index lớn, statistics/query planning khó hơn, application dễ tạo hidden schema.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu JSONB không đồng nghĩa “không schema”.

### Middle

Viết containment query, GIN index và đọc execution plan cơ bản.

### Senior

Đánh giá selectivity, write amplification, index size và promote hot fields khi cần.

### Technical Lead / Architect

Quyết định boundary giữa relational columns, JSONB và document store dựa trên access pattern, ownership và vận hành.

## 11. Key takeaway

- JSONB linh hoạt nhưng vẫn có schema ở cấp application/business.
- Index phải theo operator và query pattern.
- Đo plan/I/O trước khi kết luận GIN sẽ giải quyết latency.

# 4. Elasticsearch refresh interval: hiểu Near Real-Time search trước khi ép dữ liệu “searchable ngay lập tức”

## 1. What is it?

Elasticsearch là Near Real-Time (NRT): document được index chưa nhất thiết xuất hiện ngay trong search cho tới khi refresh tạo search-visible segments.

## 2. Why does it exist?

Nếu mỗi write phải đồng bộ tạo searchable segment, indexing throughput và I/O sẽ rất tệ. Refresh batching cân bằng freshness với indexing efficiency.

## 3. How does it work?

Write đi vào indexing buffer/translog; refresh mở segment mới cho search. Refresh không đồng nghĩa durable commit, và `refresh=true` trên mọi request có thể phá throughput.

## 4. Practical implementation

```http
POST /products/_doc/123?refresh=wait_for
{
  "name": "Road Tire",
  "status": "active"
}
```

`refresh=wait_for` chỉ nên dùng khi business flow thật sự cần read-after-write qua search; bulk ingestion thường để refresh tự nhiên.

## 5. Real production scenario

CMS publish product rồi editor mở search ngay. Customer search chấp nhận trễ vài giây, nhưng editor preview cần thấy thay đổi sớm. Hai use case có freshness requirement khác nhau.

## 6. Failure scenario & troubleshooting

**Symptom:** DB đã update nhưng search chưa thấy. **Evidence:** document GET/search khác nhau hoặc indexing lag metric tăng. **Hypothesis:** refresh delay hoặc sync pipeline lag. **Diagnosis:** tách refresh latency khỏi event-consumer backlog. **Fix:** điều chỉnh workflow/refresh policy đúng nguyên nhân. **Verification:** đo publish-to-searchable latency.

## 7. Common mistakes

Gọi refresh sau từng write; nhầm refresh với durability; coi Elasticsearch là source of truth; không đo lag từ primary DB tới index.

## 8. Alternatives

Read trực tiếp primary database cho read-after-write critical path; cache/search index chỉ phục vụ use case chấp nhận eventual consistency.

## 9. Trade-offs

### Advantages

Refresh batching cho indexing throughput tốt và search latency ổn định.

### Costs / Risks

Dữ liệu có freshness window; refresh quá thường xuyên tăng segment churn/merge pressure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index thành công không có nghĩa search thấy ngay.

### Middle

Phân biệt indexing failure, refresh delay và sync lag.

### Senior

Tuning refresh theo workload, bulk ingestion và freshness SLO.

### Technical Lead / Architect

Định nghĩa nơi eventual consistency được chấp nhận và flow nào phải đọc source of truth.

## 11. Key takeaway

- Elasticsearch là NRT, không phải transactional read model tức thời.
- Đừng dùng forced refresh như bản vá cho architecture không rõ freshness requirement.
- Monitor end-to-end indexing lag.

# 5. Anti-Corruption Layer: bảo vệ domain model khỏi contract và semantics của hệ thống bên ngoài

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary chuyển đổi model, vocabulary và semantics của external/legacy system sang model mà bounded context của ta hiểu.

## 2. Why does it exist?

Nếu domain import trực tiếp DTO/status code của vendor, thay đổi external contract lan khắp codebase. Tệ hơn, semantics bên ngoài có thể làm méo business model nội bộ.

## 3. How does it work?

```text
Domain/Application -> Port -> ACL Adapter -> External API
                         <- mapping <-
```

Dependency của domain hướng vào abstraction nội bộ; infrastructure adapter biết external contract và mapping.

## 4. Practical implementation

```csharp
public interface IInventoryAvailability
{
    Task<Availability> GetAsync(Sku sku, CancellationToken ct);
}

internal sealed class VendorInventoryAdapter(HttpClient client)
    : IInventoryAvailability
{
    public async Task<Availability> GetAsync(Sku sku, CancellationToken ct)
    {
        var dto = await client.GetFromJsonAsync<VendorStockDto>(
            $"stock/{sku.Value}", ct) ?? throw new InvalidOperationException();

        return dto.State switch
        {
            "AVL" => Availability.Available(dto.Quantity),
            "OOS" => Availability.Unavailable,
            _ => Availability.Unknown
        };
    }
}
```

## 5. Real production scenario

E-commerce tích hợp ERP legacy dùng `AVL/OOS/BKO`. Domain storefront dùng `Available/Unavailable/Backorder`. ACL sở hữu mapping và policy khi ERP thêm trạng thái mới.

## 6. Failure scenario & troubleshooting

**Symptom:** vendor thêm status khiến order bị reject sai. **Evidence:** raw integration telemetry có code mới. **Hypothesis:** mapping assumption hết hạn. **Diagnosis:** contract test và adapter logs. **Fix:** cập nhật ACL + explicit unknown handling. **Verification:** replay fixture mới và integration tests.

## 7. Common mistakes

Chỉ đổi tên DTO rồi gọi đó là ACL; leak vendor enum vào domain; mapping nằm rải rác; ACL chứa toàn business logic nội bộ; không version contract tests.

## 8. Alternatives

Integration trực tiếp hợp lý với dependency đơn giản, ổn định và semantics gần domain. ACL đáng giá khi mismatch/change risk đủ lớn.

## 9. Trade-offs

### Advantages

Cô lập change, giữ ubiquitous language, test integration mapping riêng.

### Costs / Risks

Thêm adapter/mapping code, có nguy cơ abstraction quá sớm và duplicated models.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain model.

### Middle

Implement adapter và mapping có tests.

### Senior

Nhận diện semantic mismatch, fallback và contract drift.

### Technical Lead / Architect

Quyết định boundary, ownership và mức isolation dựa trên business criticality và vendor volatility.

## 11. Key takeaway

- ACL bảo vệ semantics, không chỉ class names.
- Domain không nên phụ thuộc trực tiếp vocabulary của vendor khi mismatch đáng kể.
- Chỉ thêm ACL khi change/risk biện minh cho complexity.

# 6. Azure Private Endpoint + DNS: private connectivity chỉ hoạt động khi name resolution đúng

## 1. What is it?

Azure Private Endpoint gắn một private IP trong VNet với một Azure PaaS resource. Application vẫn thường dùng hostname chuẩn; DNS phải resolve hostname đó sang private IP phù hợp.

## 2. Why does it exist?

Public endpoint có thể không đáp ứng yêu cầu network isolation. Private Endpoint cho traffic đi qua private network path và cho phép tắt public network access.

## 3. How does it work?

```text
App/VNet -> DNS -> private IP -> Private Endpoint -> PaaS resource
```

Private DNS Zone và VNet link thường là phần quyết định. Network route đúng nhưng DNS trả public IP thì connection vẫn sai path.

## 4. Practical implementation

Trong incident, kiểm tra từ chính workload:

```bash
nslookup myvault.vault.azure.net
```

Sau đó xác nhận IP private, VNet link, private DNS zone và firewall/public access policy thay vì chỉ ping endpoint.

## 5. Real production scenario

App Service VNet Integration truy cập Key Vault qua Private Endpoint. Dev hoạt động, Production trả timeout vì Production VNet chưa link private DNS zone.

## 6. Failure scenario & troubleshooting

**Symptom:** timeout/403 chỉ ở một environment. **Evidence:** DNS ở Prod trả public IP. **Hypothesis:** private DNS link thiếu/sai. **Diagnosis:** compare resolution và network config giữa environments. **Fix:** link đúng zone/forwarder. **Verification:** DNS trả private IP và dependency health thành công.

## 7. Common mistakes

Tạo Private Endpoint nhưng quên DNS; hard-code private IP; giả định “private” tự động nghĩa firewall đúng; không xét on-prem/custom DNS forwarder.

## 8. Alternatives

Service Endpoint đơn giản hơn trong một số service/VNet scenarios; public endpoint + firewall có thể đủ nếu threat model cho phép.

## 9. Trade-offs

### Advantages

Network isolation mạnh hơn, giảm public exposure, phù hợp enterprise topology.

### Costs / Risks

DNS/topology phức tạp, chi phí endpoint, troubleshooting khó hơn, nhiều environment cần quản trị nhất quán.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hostname phải resolve đúng private IP.

### Middle

Debug DNS/VNet/firewall theo từng lớp.

### Senior

Thiết kế hybrid DNS, environment isolation và observability.

### Technical Lead / Architect

Quyết định PaaS nào thực sự cần private connectivity dựa trên threat model, compliance và operational cost.

## 11. Key takeaway

- Private Endpoint là network + DNS design.
- Troubleshoot name resolution trước khi đoán application bug.
- Private connectivity có operational cost thật.

# 7. .NET memory leak investigation với `dotnet-dump`: từ triệu chứng memory growth tới retention path

## 1. What is it?

Managed memory leak thường là object vẫn reachable nên GC không thể thu hồi, dù application không còn muốn dùng nó. `dotnet-dump` giúp phân tích heap và GC roots từ process dump.

## 2. Why does it exist?

GC giải phóng unreachable objects, không biết “business object này không còn cần”. Static collection, event subscription, cache không bounded hoặc long-lived reference có thể giữ graph lớn mãi mãi.

## 3. How does it work?

Investigation đi từ process memory → GC heap size → dominant types → suspicious instances → `gcroot` để tìm reference chain giữ object sống.

## 4. Practical implementation

```bash
dotnet-dump collect -p <PID>
dotnet-dump analyze core_*.dmp
```

Trong analyzer:

```text
> dumpheap -stat
> dumpheap -type MyCompany.OrderSnapshot
> gcroot <object-address>
```

## 5. Real production scenario

Worker xử lý file mỗi giờ. Working set tăng 200 MB/ngày và không giảm. Heap dump cho thấy `Dictionary<string, ParsedFile>` static giữ mọi file từng xử lý.

## 6. Failure scenario & troubleshooting

**Symptom:** memory tăng liên tục, pod restart do OOM. **Evidence:** GC heap tăng sau mỗi batch. **Hypothesis:** retained managed objects. **Diagnosis:** compare dump trước/sau, `dumpheap -stat`, `gcroot`. **Fix:** bounded cache/remove references/dispose subscription. **Verification:** soak test nhiều chu kỳ, heap đạt plateau.

## 7. Common mistakes

Gọi `GC.Collect()` như fix; nhìn working set duy nhất; chụp một dump không có baseline; kết luận type lớn nhất chính là leak; bỏ qua native memory khi managed heap ổn định.

## 8. Alternatives

`dotnet-counters`/metrics dùng để phát hiện trend; profiler cho allocation/retention sâu hơn; `dotnet-gcdump` nhẹ hơn trong một số tình huống.

## 9. Trade-offs

### Advantages

Dump cho bằng chứng object-level và retention path.

### Costs / Risks

Dump lớn, có dữ liệu nhạy cảm, collection có thể ảnh hưởng process; cần kỹ năng phân tích.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu GC không cứu object vẫn reachable.

### Middle

Đọc heap statistics và tìm root cơ bản.

### Senior

Phân biệt managed leak, allocation pressure và native memory; thiết kế reproducible soak test.

### Technical Lead / Architect

Thiết lập memory telemetry, dump handling policy và capacity guardrail cho production.

## 11. Key takeaway

- Memory leak trong .NET thường là unwanted reachability.
- Đi từ telemetry tới heap evidence rồi mới sửa.
- `GC.Collect()` hiếm khi là remediation đúng.

# 8. Playwright network mocking: kiểm thử UI failure path có kiểm soát mà không biến E2E thành mock-only test

## 1. What is it?

Playwright route interception cho phép test kiểm soát HTTP response để tái tạo timeout, 500, malformed payload hoặc edge case khó tạo ổn định ở backend thật.

## 2. Why does it exist?

UI phải xử lý dependency failure nhưng staging backend không thể luôn được ép lỗi đúng lúc. Nếu không kiểm soát network, negative-path E2E dễ flaky hoặc không được cover.

## 3. How does it work?

Browser request được Playwright intercept theo URL/pattern; test có thể fulfill, abort hoặc sửa response rồi quan sát UI behavior.

## 4. Practical implementation

```ts
await page.route('**/api/reviews*', async route => {
  await route.fulfill({
    status: 503,
    contentType: 'application/json',
    body: JSON.stringify({ title: 'Service unavailable' })
  });
});

await page.goto('/products/123');
await expect(page.getByText('Reviews are temporarily unavailable')).toBeVisible();
```

## 5. Real production scenario

Product page vẫn phải hiển thị product detail khi Reviews API lỗi. Test inject 503 và xác nhận reviews degradation không làm blank toàn page.

## 6. Failure scenario & troubleshooting

**Symptom:** test xanh nhưng production integration hỏng. **Evidence:** mọi E2E đều mock API. **Hypothesis:** contract drift không được kiểm chứng. **Diagnosis:** so test matrix với real integration coverage. **Fix:** giữ một lớp integration/E2E dùng backend thật và dùng mocking cho targeted failure paths. **Verification:** contract test + smoke E2E thật cùng pass.

## 7. Common mistakes

Mock mọi request; fixture không theo schema thật; assert implementation detail; route pattern quá rộng; quên test authentication/cookie behavior thật.

## 8. Alternatives

Test backend thật cho happy-path critical flows; service virtualization cho environment lớn; component test cho UI logic hẹp.

## 9. Trade-offs

### Advantages

Deterministic failure injection, nhanh, cover edge cases khó tạo.

### Costs / Risks

Có thể che contract/integration bug và tạo false confidence nếu lạm dụng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mock network dùng để kiểm soát dependency behavior.

### Middle

Viết failure-path tests deterministic và assert user-visible outcome.

### Senior

Phân bổ real vs mocked coverage theo risk, contract và flakiness.

### Technical Lead / Architect

Thiết kế test portfolio bảo vệ cả UI resilience lẫn integration correctness.

## 11. Key takeaway

- Network mocking tốt cho failure injection, không thay backend integration test.
- Assert trải nghiệm người dùng khi dependency degrade.
- Test portfolio phải tránh false confidence từ mock-only E2E.

# 9. CSRF + SameSite: cookie authentication cần bảo vệ request state-changing khỏi cross-site submission

## 1. What is it?

Cross-Site Request Forgery (CSRF) lợi dụng việc browser tự gửi authentication cookie tới site đích. Attacker không cần đọc response; chỉ cần khiến browser nạn nhân gửi request thay đổi trạng thái.

## 2. Why does it exist?

Cookie authentication ambient: browser tự attach cookie theo domain/path rules. Vì vậy server không thể coi “có cookie hợp lệ” là bằng chứng request được user chủ động tạo từ UI tin cậy.

## 3. How does it work?

Bảo vệ thường kết hợp SameSite cookie policy, anti-forgery token và kiểm tra Origin/Referer phù hợp. Token tạo một giá trị attacker site không thể tự lấy rồi gửi đúng.

## 4. Practical implementation

Với ASP.NET Core MVC/Razor, dùng anti-forgery mechanisms chuẩn cho state-changing form. Với SPA dùng cookie auth, expose token theo pattern được framework hỗ trợ và gửi qua custom header; không tắt validation chỉ để request “chạy được”.

## 5. Real production scenario

Admin portal dùng auth cookie. Endpoint `POST /users/{id}/disable` thiếu anti-forgery protection; attacker dụ admin mở trang ngoài và browser gửi request với cookie admin.

## 6. Failure scenario & troubleshooting

**Symptom:** anti-forgery fail chỉ ở Production. **Evidence:** cookie/header token thiếu hoặc SameSite/Secure khác local. **Hypothesis:** reverse proxy/HTTPS/cross-site frontend topology thay đổi cookie behavior. **Diagnosis:** browser DevTools + server logs + Origin. **Fix:** cấu hình cookie/proxy/token flow đúng topology. **Verification:** legitimate request pass, forged cross-site request fail.

## 7. Common mistakes

Cho rằng CORS ngăn CSRF; dùng GET để thay đổi state; `SameSite=None` mà không hiểu rủi ro; disable anti-forgery vì SPA; log token/cookie nhạy cảm.

## 8. Alternatives

Bearer token trong `Authorization` header không tự được browser attach theo kiểu cookie, giảm classic CSRF exposure nhưng đưa ra threat model khác như token storage/XSS.

## 9. Trade-offs

### Advantages

Anti-forgery token + SameSite giảm class attack quan trọng cho cookie-auth apps.

### Costs / Risks

Cross-site SSO/embed scenarios phức tạp hơn; proxy/domain topology cần cấu hình chính xác.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser tự gửi cookie là nguyên nhân gốc của CSRF.

### Middle

Implement anti-forgery đúng framework và test state-changing endpoints.

### Senior

Phân tích SameSite, CORS, XSS và auth topology như các concern khác nhau.

### Technical Lead / Architect

Chọn auth model và cross-origin topology dựa trên threat model, UX và operational constraints.

## 11. Key takeaway

- CORS không phải CSRF defense.
- Cookie-auth state-changing requests cần explicit CSRF protection.
- SameSite hữu ích nhưng không thay thế việc hiểu topology và threat model.

# 10. AI evaluation: đo chất lượng LLM bằng dataset, rubric và deterministic checks thay vì “prompt trông ổn”

## 1. What is it?

AI evaluation là quy trình đo behavior của LLM workflow trên tập test đại diện bằng metrics/rubric rõ ràng. Nó tương đương regression discipline cho phần probabilistic của hệ thống.

## 2. Why does it exist?

Prompt/model thay đổi có thể cải thiện vài ví dụ nhưng làm hỏng nhóm khác. Manual spot-check không phát hiện regression có hệ thống, đặc biệt khi output có nhiều cách diễn đạt hợp lệ.

## 3. How does it work?

Dataset chứa input + expected properties. Deterministic checks kiểm schema, required fields, citations/tool constraints; rubric/model-assisted judge có thể đánh giá semantic quality nhưng phải được calibrate bằng human labels.

## 4. Practical implementation

```csharp
public sealed record SupportAnswer(string Category, string Answer, string[] Sources);

static bool DeterministicChecks(SupportAnswer x) =>
    !string.IsNullOrWhiteSpace(x.Category) &&
    !string.IsNullOrWhiteSpace(x.Answer) &&
    x.Sources.Length > 0;
```

Pipeline CI có thể chạy representative eval set, so pass rate/cost/latency với baseline trước khi đổi model hoặc prompt.

## 5. Real production scenario

Support assistant phải phân loại ticket và trích nguồn nội bộ. Team giữ dataset gồm normal, ambiguous, injection và missing-context cases; release bị chặn nếu structured-output validity hoặc grounded-answer rate giảm quá threshold.

## 6. Failure scenario & troubleshooting

**Symptom:** offline eval tăng nhưng user complaints tăng. **Evidence:** production traces chứa query distribution khác dataset. **Hypothesis:** eval set không đại diện hoặc judge bias. **Diagnosis:** sample failure thật, phân nhóm, so với dataset. **Fix:** cập nhật dataset/rubric và thêm deterministic checks. **Verification:** backtest trên incidents cũ rồi canary production.

## 7. Common mistakes

Chỉ dùng 10 happy-path prompts; dùng cùng model làm generator và judge mà không calibration; gộp quality thành một score; bỏ cost/latency; để LLM tự quyết authorization/financial correctness.

## 8. Alternatives

Pure deterministic tests phù hợp logic có expected output chính xác; human review phù hợp golden-set calibration và high-risk samples. AI eval nên bổ sung, không thay thế chúng.

## 9. Trade-offs

### Advantages

Phát hiện regression, so sánh model/prompt có bằng chứng, quản lý quality-cost-latency.

### Costs / Risks

Dataset maintenance, judge variance, metric gaming và chi phí inference.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LLM output cần được kiểm thử chứ không chỉ demo.

### Middle

Tạo representative cases và deterministic validators.

### Senior

Thiết kế rubric, failure taxonomy, calibration và production feedback loop.

### Technical Lead / Architect

Quyết định quality gates, risk thresholds và logic nào bắt buộc deterministic ngoài LLM.

## 11. Key takeaway

- Eval dataset là regression suite cho probabilistic behavior.
- Deterministic rules phải kiểm những invariant có thể kiểm chính xác.
- Offline score chỉ hữu ích khi dataset phản ánh production traffic và failure modes.
