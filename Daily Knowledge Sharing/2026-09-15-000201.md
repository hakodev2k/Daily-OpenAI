# 1. C# `IDisposable`, `IAsyncDisposable` và finalizer: quản lý resource ownership thay vì dựa vào Garbage Collector để “dọn hộ”

## 1. What is it?

Garbage Collector quản lý **managed memory**, không đảm bảo giải phóng resource bên ngoài runtime đúng thời điểm. File handle, socket, database connection wrapper, unmanaged memory và OS handle cần lifecycle rõ ràng.

Mental model:

```text
Managed object lifetime
        ↓
GC decides memory reclamation time

External resource lifetime
        ↓
Application must release deterministically
```

`IDisposable` cho synchronous cleanup; `IAsyncDisposable` cho cleanup cần `await`, ví dụ flush/close asynchronous. Finalizer chỉ là safety net cuối cùng cho unmanaged resource ownership đặc biệt, không phải cơ chế cleanup chính.

## 2. Why does it exist?

Nếu application chờ GC rồi mới release resource, resource có thể bị giữ quá lâu dù object không còn dùng nữa. Một API xử lý file có thể hết file handles; một service có thể giữ connection/socket lâu hơn cần thiết.

GC biết object còn reachable hay không, nhưng không hiểu semantic như “transaction đã kết thúc”, “stream nên close ngay” hay “buffer unmanaged cần trả cho OS”.

## 3. How does it work?

`using` được compiler chuyển thành `try/finally` gọi `Dispose`:

```csharp
using var stream = File.OpenRead(path);
```

Tương đương về ý tưởng:

```csharp
var stream = File.OpenRead(path);
try
{
    // use stream
}
finally
{
    stream.Dispose();
}
```

Với async cleanup:

```csharp
await using var resource = await OpenAsyncResource(ct);
```

Nếu type có finalizer, object phải đi qua finalization queue trước khi memory được reclaim, làm lifecycle đắt hơn và thường sống ít nhất thêm một GC cycle.

## 4. Practical implementation

Một wrapper sở hữu unmanaged handle nên express ownership rõ:

```csharp
public sealed class NativeBuffer : IDisposable
{
    private IntPtr _pointer;
    private bool _disposed;

    public NativeBuffer(int size)
    {
        _pointer = Marshal.AllocHGlobal(size);
    }

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);
    }

    private void Dispose(bool disposing)
    {
        if (_disposed)
            return;

        if (_pointer != IntPtr.Zero)
        {
            Marshal.FreeHGlobal(_pointer);
            _pointer = IntPtr.Zero;
        }

        _disposed = true;
    }

    ~NativeBuffer()
    {
        Dispose(false);
    }
}
```

Trong code production, ưu tiên `SafeHandle` khi có thể thay vì tự viết finalizer logic.

## 5. Real production scenario

Một batch service mở nhiều `FileStream` để xử lý tài liệu nhưng giữ reference trong collection đến cuối batch. Memory vẫn ổn nhưng process bắt đầu báo lỗi “too many open files” trên Linux.

Root cause không phải memory leak; đó là **resource lifetime leak**. Fix là thu hẹp scope và dispose từng stream ngay sau khi xử lý.

## 6. Failure scenario & troubleshooting

**Symptom** → process memory không quá cao nhưng request bắt đầu fail khi mở file/socket.

**Evidence** → OS handle count tăng liên tục; GC collection không giảm số handle.

**Hypothesis** → disposable resource sống dài hơn business scope.

**Diagnosis** → kiểm tra ownership path, `using` scope, object pooling và các object giữ reference.

**Fix** → dispose deterministic, dùng `await using` khi cần, tránh finalizer trừ khi thực sự sở hữu unmanaged resource.

**Verification** → stress test và theo dõi handle count ổn định qua nhiều chu kỳ workload.

## 7. Common mistakes

* Nghĩ GC tự động đóng file/socket đúng thời điểm.
* Dispose object mà class không thực sự sở hữu.
* Viết finalizer cho mọi `IDisposable` type.
* Quên `GC.SuppressFinalize` khi finalizer đã có.
* Dispose resource quá sớm trong async flow rồi task khác vẫn còn dùng.
* Giữ `DbContext`, stream hoặc response object sống lâu hơn scope cần thiết.

## 8. Alternatives

* `using` / `await using`: lựa chọn mặc định cho scope ngắn.
* Dependency Injection container: phù hợp khi container sở hữu lifecycle của disposable service.
* `SafeHandle`: tốt hơn raw finalizer cho OS handles.
* Pooling: chỉ phù hợp khi resource được thiết kế để reuse và ownership rõ ràng.

## 9. Trade-offs

### Advantages

* Deterministic cleanup giảm resource exhaustion.
* Ownership rõ giúp code dễ reason và test hơn.
* `IAsyncDisposable` cho phép cleanup không block thread.

### Costs / Risks

* Ownership không rõ dễ gây double-dispose hoặc dispose nhầm dependency.
* Finalizer làm object lifecycle đắt hơn.
* Async disposal tăng complexity nếu call chain chưa hỗ trợ async.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu GC quản lý managed memory, không thay thế `Dispose` cho external resources.

### Middle

Biết dùng `using`, `await using`, định nghĩa ownership và tránh leak lifecycle.

### Senior

Phân biệt memory leak với resource leak, hiểu finalization cost và chọn `SafeHandle` khi phù hợp.

### Technical Lead / Architect

Đặt convention ownership cho infrastructure code, DI lifecycle và resource-heavy components; tránh abstractions làm mờ ai chịu trách nhiệm cleanup.

## 11. Key takeaway

* GC không phải resource lifecycle manager.
* `Dispose` nên phản ánh ownership rõ ràng và deterministic.
* Finalizer là safety net hiếm dùng, không phải cleanup strategy mặc định.

# 2. `HttpClientFactory`, handler lifetime và connection pooling: tránh socket exhaustion nhưng vẫn phải hiểu DNS refresh và connection reuse

## 1. What is it?

`HttpClient` là high-level API; connection pooling thực tế nằm bên dưới `HttpMessageHandler`/`SocketsHttpHandler`.

`IHttpClientFactory` giúp quản lý handler lifecycle, configuration, policies và typed/named clients mà không tạo handler mới cho mỗi request.

Mental model:

```text
HttpClient
   ↓
HttpMessageHandler
   ↓
Connection pool
   ↓
DNS / TCP / TLS
   ↓
Remote API
```

## 2. Why does it exist?

Pattern `new HttpClient()` cho từng request từng gây socket exhaustion vì connections đi vào `TIME_WAIT` và pool không được reuse hiệu quả.

Ngược lại, giữ một handler vĩnh viễn có thể làm DNS thay đổi nhưng process tiếp tục reuse connections tới endpoint cũ nếu lifetime không được kiểm soát.

## 3. How does it work?

`IHttpClientFactory` tạo lightweight `HttpClient` instances nhưng reuse handlers theo lifetime policy.

```csharp
builder.Services.AddHttpClient<PaymentsClient>(client =>
{
    client.BaseAddress = new Uri("https://payments.example.com");
    client.Timeout = TimeSpan.FromSeconds(10);
});
```

Có thể cấu hình connection lifetime:

```csharp
builder.Services.AddHttpClient<PaymentsClient>()
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(5)
    });
```

`PooledConnectionLifetime` buộc connection cũ dần được thay mới, giúp phản ứng với DNS/backend rotation.

## 4. Practical implementation

Typed client giữ API contract gần code integration:

```csharp
public sealed class PaymentsClient(HttpClient httpClient)
{
    public async Task<PaymentStatus?> GetStatusAsync(
        string paymentId,
        CancellationToken ct)
    {
        using var response = await httpClient.GetAsync(
            $"payments/{Uri.EscapeDataString(paymentId)}",
            ct);

        response.EnsureSuccessStatusCode();

        return await response.Content
            .ReadFromJsonAsync<PaymentStatus>(cancellationToken: ct);
    }
}
```

Timeout, retry và circuit breaker nên dựa trên semantics của API, không copy một policy cho mọi dependency.

## 5. Real production scenario

Một service chạy ổn nhiều ngày rồi remote provider chuyển traffic sang IP mới. Một số instance vẫn giữ connection tới backend cũ lâu hơn mong muốn và có intermittent failures.

Sau khi kiểm tra DNS + connection lifetime, team đặt `PooledConnectionLifetime` phù hợp với hạ tầng provider thay vì restart service để “fix”.

## 6. Failure scenario & troubleshooting

**Symptom** → request tới dependency timeout tăng nhưng DNS lookup thủ công trả IP mới đúng.

**Evidence** → process reuse connection lâu; failures tập trung trên vài instance.

**Hypothesis** → stale pooled connections hoặc backend rotation.

**Diagnosis** → kiểm tra connection telemetry, handler config, DNS TTL và remote load balancer behavior.

**Fix** → điều chỉnh handler/connection lifetime, timeout và resilience policy.

**Verification** → theo dõi connection churn vừa đủ và error rate sau backend rotation test.

## 7. Common mistakes

* `new HttpClient()` cho mỗi request.
* Giữ handler mãi mà không cân nhắc DNS/backend changes.
* Retry mọi `POST` mà không xem idempotency.
* Đặt timeout quá dài khiến request threads/resources tích tụ.
* Không propagate `CancellationToken`.
* Log full authorization headers hoặc sensitive payload.

## 8. Alternatives

* Long-lived `HttpClient` với `SocketsHttpHandler.PooledConnectionLifetime`: hoàn toàn hợp lý nếu quản lý tốt.
* `IHttpClientFactory`: phù hợp với DI, nhiều integrations và policy management.
* Generated clients từ OpenAPI: hữu ích khi contract lớn, nhưng vẫn cần hiểu handler/network behavior.

## 9. Trade-offs

### Advantages

* Reuse connection hiệu quả.
* Centralize configuration và observability.
* Dễ áp dụng typed clients, handlers và resilience policies.

### Costs / Risks

* Factory không tự sửa retry semantics sai.
* Handler policy quá phức tạp có thể che failure thực.
* Connection lifetime quá ngắn làm tăng TCP/TLS handshake cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `HttpClient` nên reuse connection thay vì tạo socket mới liên tục.

### Middle

Biết dùng typed client, timeout, cancellation và handler configuration.

### Senior

Hiểu DNS, connection pooling, retry/idempotency và dependency failure propagation.

### Technical Lead / Architect

Chuẩn hóa integration boundary, resilience budget và observability cho remote dependencies thay vì để mỗi team tự cấu hình tùy ý.

## 11. Key takeaway

* Vấn đề nằm ở handler/connection lifecycle, không chỉ ở object `HttpClient`.
* Reuse connection và refresh DNS phải được cân bằng.
* Resilience policy phải theo semantics của dependency.

# 3. EF Core `IQueryable` vs `IEnumerable`: execution boundary quyết định query chạy ở database hay bị kéo về memory

## 1. What is it?

`IQueryable<T>` biểu diễn một expression tree có thể được provider như EF Core dịch thành SQL. `IEnumerable<T>` biểu diễn sequence chạy bằng .NET enumeration semantics.

Mental model:

```text
IQueryable
   ↓ build expression
EF Core translator
   ↓
SQL
   ↓
Database

IEnumerable
   ↓
.NET code over materialized/in-memory data
```

Execution boundary thường xảy ra tại `ToListAsync`, `FirstAsync`, `CountAsync`, `AsEnumerable` hoặc khi dữ liệu đã materialize.

## 2. Why does it exist?

LINQ cho cảm giác thống nhất nhưng execution target rất khác nhau. Một filter chạy ở database có thể giảm từ 10 triệu rows xuống 50 rows. Cùng filter chạy sau materialization có thể kéo 10 triệu rows qua network rồi mới lọc.

## 3. How does it work?

Query này vẫn được compose ở database:

```csharp
var query = db.Orders
    .Where(x => x.Status == OrderStatus.Open)
    .OrderByDescending(x => x.CreatedAt);

var page = await query
    .Take(50)
    .ToListAsync(ct);
```

Nhưng nếu materialize sớm:

```csharp
var orders = await db.Orders.ToListAsync(ct);
var page = orders
    .Where(x => x.Status == OrderStatus.Open)
    .Take(50)
    .ToList();
```

thì filtering xảy ra ở process.

## 4. Practical implementation

Projection nên xảy ra trước materialization:

```csharp
var result = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .OrderByDescending(x => x.CreatedAt)
    .Select(x => new OrderSummary(
        x.Id,
        x.CreatedAt,
        x.TotalAmount))
    .Take(100)
    .ToListAsync(ct);
```

Điều này giảm columns, rows và Change Tracker overhead.

## 5. Real production scenario

Một report endpoint dùng repository trả `IEnumerable<Order>`. Vì abstraction đã materialize toàn bộ dữ liệu, application layer không thể thêm database-side filter/pagination hiệu quả.

Team tưởng “EF query chậm”, nhưng vấn đề thực là abstraction đã đặt execution boundary quá sớm.

## 6. Failure scenario & troubleshooting

**Symptom** → API memory tăng mạnh và network bytes từ SQL tăng dù response chỉ có 20 items.

**Evidence** → generated SQL không có expected `WHERE`/`TOP` hoặc query log cho thấy fetch toàn bảng.

**Hypothesis** → materialization xảy ra trước filter/pagination.

**Diagnosis** → inspect LINQ chain, type boundary và `ToList`/`AsEnumerable` placement.

**Fix** → giữ `IQueryable` compose bên trong data-access boundary hoặc expose query-specific methods/projections.

**Verification** → inspect SQL, row count, execution plan và memory allocation.

## 7. Common mistakes

* Gọi `ToListAsync` quá sớm.
* Repository generic trả collection rồi application tự filter.
* Cho `IQueryable` leak khắp architecture khiến persistence semantics lan ra ngoài boundary.
* Dùng method custom không translate được mà không kiểm tra generated SQL.
* Load full entity khi chỉ cần vài fields.

## 8. Alternatives

* Direct `DbContext` query trong application handler: đơn giản và transparent ở nhiều codebase.
* Query-specific repository: giữ persistence boundary nhưng không phá composition.
* Specification pattern: hữu ích khi query rules thực sự cần reuse, nhưng có complexity riêng.
* Raw SQL/Dapper: phù hợp hot query đặc biệt khi cần control sâu.

## 9. Trade-offs

### Advantages

* `IQueryable` cho database-side composition mạnh.
* Projection giúp giảm I/O và tracking overhead.

### Costs / Risks

* Leak `IQueryable` ra quá xa làm architecture coupling với ORM.
* LINQ nhìn giống nhau nhưng translation capability khác .NET execution.
* Query quá phức tạp có thể sinh SQL khó tối ưu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ chưa chắc chạy ngay và `ToList` thường là execution point.

### Middle

Biết filter/project/page trước materialization và đọc generated SQL.

### Senior

Nhận diện abstraction làm mất query composition, phân tích round trip, plan và data volume.

### Technical Lead / Architect

Thiết kế data-access boundary cân bằng transparency với encapsulation; tránh generic repository làm query performance trở nên vô hình.

## 11. Key takeaway

* Execution boundary là quyết định performance lớn.
* Hãy đẩy filtering/projection/pagination xuống database khi phù hợp.
* Abstraction tốt không nên che mất cost thật của query.

# 4. SQL connection pooling và pool exhaustion: API có thể timeout dù database CPU vẫn thấp

## 1. What is it?

ADO.NET connection pooling giữ các physical database connections để reuse. `SqlConnection.Open()` thường không tạo TCP connection mới; nó mượn connection từ pool matching connection string.

Mental model:

```text
Application requests connection
          ↓
Connection Pool
   ├─ free connection → hand out
   └─ none free → wait until available / timeout
          ↓
Database
```

## 2. Why does it exist?

Mở database connection mới cần authentication, network handshake và server resources. Pooling giảm cost này rất lớn.

Nhưng pool có giới hạn. Nếu code giữ connection quá lâu hoặc concurrency vượt capacity, request có thể chờ pool thay vì chờ database query.

## 3. How does it work?

Connection được trả về pool khi `Close`/`Dispose`. Connection string khác nhau thường tạo pool khác nhau.

Trong EF Core, `DbContext` không giữ physical connection mở suốt lifetime mặc định; connection thường mở khi query/save và đóng sau operation, trừ khi application chủ động mở thủ công hoặc transaction/lifecycle yêu cầu khác.

## 4. Practical implementation

Scope ngắn và async I/O là nền tảng:

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(ct);

await using var command = connection.CreateCommand();
command.CommandText = "SELECT Id, Name FROM Products WHERE Id = @id";
command.Parameters.AddWithValue("@id", id);

await using var reader = await command.ExecuteReaderAsync(ct);
```

Không giữ connection trong singleton/service field.

## 5. Real production scenario

API bắt đầu timeout sau khi release mới thêm một external HTTP call bên trong database transaction. Query database chỉ mất 20 ms, nhưng transaction giữ connection 5 giây trong lúc chờ remote API.

Database CPU thấp nhưng pool nhanh chóng cạn dưới tải cao.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi timeout khi obtaining/opening connection; DB CPU và query duration bình thường.

**Evidence** → active connections gần pool limit; request concurrency tăng; transaction duration dài.

**Hypothesis** → pool exhaustion, không phải slow query.

**Diagnosis** → correlate connection pool counters, transaction duration, thread/request concurrency và dependency timings.

**Fix** → thu hẹp connection/transaction lifetime, loại network calls khỏi transaction, giới hạn concurrency nếu cần.

**Verification** → load test và xác nhận wait-for-connection gần zero ở steady state.

## 7. Common mistakes

* Tăng max pool size trước khi tìm leak/lifetime issue.
* Giữ transaction qua external API call.
* Quên dispose reader/connection.
* Dùng nhiều connection strings gần giống nhau tạo nhiều pools nhỏ.
* Nhầm pool exhaustion với database CPU saturation.

## 8. Alternatives

* Tăng pool size: chỉ hợp lý khi database và workload thật sự chịu được concurrency cao hơn.
* Concurrency limiter: hữu ích để bảo vệ database khi burst traffic.
* Queue/background processing: phù hợp non-interactive workload.
* Read replicas: giải quyết read capacity, không giải quyết connection leak.

## 9. Trade-offs

### Advantages

* Pooling giảm connection establishment cost đáng kể.
* Cho throughput cao với số physical connections hữu hạn.

### Costs / Risks

* Pool có thể trở thành hidden queue.
* Tăng pool size quá mức có thể chuyển bottleneck sang database.
* Long transaction giữ cả connection và locks lâu hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu connection cần dispose và thường được reuse qua pool.

### Middle

Biết giữ connection/transaction scope ngắn và đọc timeout context.

### Senior

Phân biệt query bottleneck với pool contention và dependency-induced lifetime inflation.

### Technical Lead / Architect

Capacity-plan concurrency từ API tới database, đặt limits và telemetry thay vì chỉ dựa vào default settings.

## 11. Key takeaway

* Database có thể “rảnh” nhưng application vẫn hết connection.
* Connection lifetime và transaction duration quan trọng hơn việc chỉ tăng pool size.
* Pool metrics phải được theo dõi cùng query và dependency telemetry.

# 5. Elasticsearch `text`, `keyword` và analyzer: mapping sai có thể làm search “đúng syntax nhưng sai semantics”

## 1. What is it?

Elasticsearch index field theo mapping. Hai kiểu thường gặp:

* `text`: được analyze thành tokens cho full-text search.
* `keyword`: giữ nguyên value để exact match, sorting, aggregation.

Analyzer là pipeline gồm character filters, tokenizer và token filters.

## 2. Why does it exist?

Search “red running shoes” không giống database equality. User mong match theo terms, normalization, stemming hoặc language behavior.

Ngược lại, SKU `ABC-123`, email, status code hoặc category ID thường cần exact semantics. Nếu dùng `text` cho chúng, analyzer có thể biến dữ liệu thành tokens không phù hợp.

## 3. How does it work?

Ví dụ field:

```json
"name": {
  "type": "text",
  "fields": {
    "keyword": { "type": "keyword" }
  }
}
```

`name` dùng full-text query; `name.keyword` dùng sorting/aggregation/exact filtering.

```text
"Running Shoes"
      ↓ analyzer
["running", "shoes"]
```

Query analyzer phải tương thích với index analyzer để semantics hợp lý.

## 4. Practical implementation

Mapping cho product:

```json
{
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "fields": {
          "keyword": { "type": "keyword", "ignore_above": 256 }
        }
      },
      "sku": { "type": "keyword" },
      "description": { "type": "text" },
      "categoryId": { "type": "keyword" }
    }
  }
}
```

Search endpoint nên dùng full-text fields cho relevance và keyword fields cho filters.

## 5. Real production scenario

E-commerce search dùng `term` query trên `productName` kiểu `text`. Developer kỳ vọng exact word match nhưng query không trả như mong muốn vì analyzed representation khác raw input.

Sau khi hiểu mapping, team dùng `match` cho text và `term` cho keyword/filter fields.

## 6. Failure scenario & troubleshooting

**Symptom** → document tồn tại trong index nhưng query “đúng giá trị” vẫn không match.

**Evidence** → `_analyze` cho thấy tokenization khác kỳ vọng.

**Hypothesis** → query type hoặc analyzer/mapping không phù hợp.

**Diagnosis** → kiểm tra mapping, analyze input và inspect query DSL.

**Fix** → chọn đúng field/query; nếu mapping cần đổi loại/analyzer, tạo index mới và reindex qua alias cutover.

**Verification** → relevance test set và exact filter tests qua representative data.

## 7. Common mistakes

* Dùng `term` trên analyzed `text` field rồi nghĩ Elasticsearch lỗi.
* Dùng `text` cho ID/status/SKU.
* Aggregation trên field không phù hợp.
* Thay analyzer production mà không chuẩn bị reindex.
* Chỉ test vài keyword đẹp, không có relevance evaluation dataset.

## 8. Alternatives

* Database full-text search: đủ tốt với use case vừa phải và muốn ít hạ tầng.
* PostgreSQL `tsvector`: phù hợp nếu search requirements không quá phức tạp.
* Dedicated search engine khác như OpenSearch/Solr tùy ecosystem.

## 9. Trade-offs

### Advantages

* Analyzer cho full-text semantics mạnh.
* Multi-fields cho phép cùng logical value phục vụ search + exact operations.

### Costs / Risks

* Mapping/analyzer decisions khó đổi in-place.
* Search behavior có thể khó giải thích nếu team không hiểu tokenization.
* Reindexing và relevance tuning tạo operational cost.

### Middle

# 6. DDD Aggregate boundary và invariant: transaction boundary phải theo business consistency chứ không theo entity graph

## 1. What is it?

Aggregate là một consistency boundary trong domain. Aggregate Root là entry point mà bên ngoài dùng để thay đổi state bên trong boundary.

Mental model:

```text
Order Aggregate
  ├─ Order (Root)
  ├─ OrderLine
  └─ ShippingAddress value object

External code
   ↓
Order methods
   ↓
Invariant enforced inside boundary
```

Aggregate không có nghĩa “mọi object liên quan đều nhét chung vào một object graph lớn”.

## 2. Why does it exist?

Business invariants cần nơi chịu trách nhiệm rõ ràng. Ví dụ:

* Order không thể có total âm.
* Không thể ship order chưa paid.
* Quantity mỗi line phải > 0.

Nếu mọi layer đều mutate entity trực tiếp, invariant dễ bị phá tùy code path.

## 3. How does it work?

Aggregate Root expose behavior thay vì public setters:

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public IReadOnlyCollection<OrderLine> Lines => _lines;
    public OrderStatus Status { get; private set; }

    public void AddProduct(Guid productId, int quantity, decimal unitPrice)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Order is not editable.");

        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(nameof(quantity));

        _lines.Add(new OrderLine(productId, quantity, unitPrice));
    }
}
```

Invariant cần strongly consistent trong một transaction thường nên nằm cùng aggregate boundary.

## 4. Practical implementation

Cross-aggregate rule không nhất thiết cần synchronous transaction.

Ví dụ `CustomerCredit` và `Order` là hai aggregates. Nếu business cho phép eventual consistency, order placement có thể tạo event để credit subsystem xử lý riêng.

Nếu rule “không bao giờ vượt credit limit” phải tuyệt đối synchronous, boundary hoặc coordination design phải phản ánh yêu cầu đó.

## 5. Real production scenario

Team thiết kế `Customer` aggregate chứa toàn bộ Orders, Addresses, Payments và Notifications vì “đều thuộc customer”. EF Core phải load graph lớn, transaction contention tăng và nhiều thao tác không liên quan cùng chạm một root.

Refactor theo invariants thực tế tạo nhiều aggregates nhỏ hơn, giảm contention và ownership rõ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → update một phần domain thường xuyên gây optimistic concurrency conflicts ở phần không liên quan.

**Evidence** → aggregate quá lớn, nhiều workflows cùng update cùng root/version token.

**Hypothesis** → consistency boundary rộng hơn invariant thực sự cần.

**Diagnosis** → liệt kê invariants và xác định dữ liệu nào thật sự phải commit atomically.

**Fix** → tách aggregates, dùng domain events/integration events cho cross-boundary coordination.

**Verification** → concurrency tests và business invariant tests.

## 7. Common mistakes

* Aggregate = database table.
* Aggregate = toàn bộ object graph có relationship.
* Repository cho mọi child entity bên trong aggregate.
* Dùng public setters rồi kỳ vọng service layer luôn nhớ invariant.
* Tạo aggregate quá lớn để “tránh eventual consistency”.

## 8. Alternatives

* Transaction Script: phù hợp domain đơn giản, ít invariants.
* Anemic model + application services: có thể đủ cho CRUD-heavy systems.
* Rich domain model: đáng giá khi business rules phức tạp và thay đổi nhiều.

## 9. Trade-offs

### Advantages

* Invariant ownership rõ.
* Transaction boundary gần business semantics.
* Giảm accidental mutation từ ngoài domain.

### Costs / Risks

* Domain model phức tạp hơn CRUD model.
* Aggregate boundaries sai gây contention hoặc eventual consistency không cần thiết.
* DDD có thể overkill nếu nghiệp vụ đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Aggregate Root kiểm soát thay đổi trong consistency boundary.

### Middle

Implement behavior methods, encapsulation và invariant tests.

### Senior

Phân tích concurrency, transaction và eventual consistency giữa aggregates.

### Technical Lead / Architect

Quyết định boundary từ business invariants và operational cost, không từ sơ đồ database hay folder structure.

## 11. Key takeaway

* Aggregate là consistency boundary, không phải “nhóm entity có quan hệ”.
* Invariant quyết định transaction scope.
* Aggregate càng lớn càng phải trả giá bằng contention và coupling.

# 8. `BackgroundService` + `Channel<T>`: xây producer/consumer có backpressure thay vì tạo background tasks không giới hạn

## 1. What is it?

`Channel<T>` là async producer/consumer primitive trong .NET. Bounded channel có thể tạo **backpressure**: khi queue nội bộ đầy, producer phải chờ hoặc xử lý theo configured full mode.

Mental model:

```text
Producer(s)
    ↓
Bounded Channel
    ↓
Consumer BackgroundService
```

## 2. Why does it exist?

Pattern nguy hiểm:

```csharp
_ = Task.Run(() => ProcessAsync(item));
```

cho mỗi request/item có thể tạo unbounded concurrent work. Khi dependency chậm, tasks tích tụ, memory tăng và shutdown khó kiểm soát.

Channel biến concurrency thành explicit capacity decision.

## 3. How does it work?

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(1000)
{
    FullMode = BoundedChannelFullMode.Wait
});
```

Producer dùng `WriteAsync`; khi buffer đầy, await tạo backpressure. Consumer đọc bằng `ReadAllAsync(stoppingToken)`.

## 4. Practical implementation

```csharp
public sealed class JobWorker(Channel<Job> channel) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in channel.Reader.ReadAllAsync(stoppingToken))
        {
            await ProcessJobAsync(job, stoppingToken);
        }
    }

    private static Task ProcessJobAsync(Job job, CancellationToken ct)
    {
        // real work
        return Task.CompletedTask;
    }
}
```

Nếu cần parallelism, tạo số consumer workers hữu hạn thay vì `Task.Run` vô hạn.

## 5. Real production scenario

Một API nhận webhook rồi fire-and-forget background task. Khi downstream email provider chậm 30 giây, hàng chục nghìn tasks tích tụ trong process, memory tăng và deploy không shutdown sạch.

Bounded channel làm API bắt đầu chịu backpressure hoặc reject theo policy rõ ràng thay vì âm thầm tích nợ công việc.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng cùng traffic spike; process shutdown lâu; số task pending tăng.

**Evidence** → unbounded task creation và dependency latency cao.

**Hypothesis** → không có queue capacity/backpressure.

**Diagnosis** → đo enqueue rate, processing rate, queue depth và task count.

**Fix** → bounded channel hoặc durable external queue; giới hạn consumer concurrency.

**Verification** → overload test và xác nhận memory/queue behavior predictable.

## 7. Common mistakes

* Dùng in-memory channel cho công việc không được phép mất khi process restart.
* Channel unbounded rồi tưởng đã giải quyết overload.
* Không complete writer khi lifecycle kết thúc.
* Không propagate cancellation.
* Xử lý work quá lâu trong một consumer duy nhất mà không tính throughput.

## 8. Alternatives

* Azure Service Bus / RabbitMQ: durable queue, multi-instance distribution.
* TPL Dataflow: pipeline transformations phức tạp hơn.
* `SemaphoreSlim`: giới hạn concurrency nhưng không phải durable queue.
* Direct synchronous processing: đơn giản nhất nếu latency chấp nhận được.

## 9. Trade-offs

### Advantages

* Backpressure rõ ràng.
* Async API tốt, allocation tương đối thấp.
* Phù hợp intra-process pipelines.

### Costs / Risks

* In-memory queue mất khi process crash.
* Multi-instance coordination không được giải quyết.
* Capacity phải được chọn và monitor.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu producer có thể nhanh hơn consumer và cần queue.

### Middle

Implement bounded channel + hosted consumer + cancellation.

### Senior

Thiết kế capacity, concurrency, overload behavior và shutdown semantics.

### Technical Lead / Architect

Quyết định khi in-memory queue đủ và khi workload cần durable broker.

## 11. Key takeaway

* Background work cũng cần capacity boundary.
* Bounded queue biến overload thành hành vi có thể dự đoán.
* Không dùng in-memory channel cho work cần durability qua restart.

# 9. HTTP caching với `Cache-Control`, ETag và `stale-while-revalidate`: giảm origin load mà vẫn kiểm soát freshness

## 1. What is it?

HTTP caching cho browser/CDN/proxy reuse response theo cache directives. `Cache-Control` mô tả freshness policy; ETag hỗ trợ conditional revalidation.

Ví dụ:

```http
Cache-Control: public, max-age=60, stale-while-revalidate=300
ETag: "product-42-v17"
```

## 2. Why does it exist?

Nếu mọi request đều quay về origin dù content hiếm thay đổi, hệ thống lãng phí latency, bandwidth và compute.

Cache giúp phục vụ gần client hơn, nhưng stale content có thể gây lỗi business nếu freshness requirement không được định nghĩa.

## 3. How does it work?

Khi response còn fresh, cache trả trực tiếp. Khi stale, cache có thể revalidate:

```http
If-None-Match: "product-42-v17"
```

Origin trả:

```http
304 Not Modified
```

không cần gửi lại full body.

`stale-while-revalidate` cho phép phục vụ bản stale trong một khoảng thời gian trong khi cache refresh phía sau, giảm latency spike tại expiry boundary.

## 4. Practical implementation

ASP.NET Core có thể set headers phù hợp với resource semantics:

```csharp
app.MapGet("/catalog/{id:int}", async (int id, CatalogService service, HttpContext ctx) =>
{
    var item = await service.GetAsync(id, ctx.RequestAborted);
    if (item is null)
        return Results.NotFound();

    ctx.Response.Headers.CacheControl =
        "public,max-age=60,stale-while-revalidate=300";

    ctx.Response.Headers.ETag = $"\"catalog-{id}-v{item.Version}\"";

    return Results.Ok(item);
});
```

Production implementation cần xử lý `If-None-Match` đúng contract nếu muốn revalidation end-to-end.

## 5. Real production scenario

Marketing/CMS pages nhận traffic lớn nhưng content chỉ publish vài lần mỗi ngày. Cache 60 giây ở edge giúp giảm origin load rất mạnh.

Ngược lại, cart hoặc account balance không nên được public-cache chỉ vì “cache giúp nhanh hơn”.

## 6. Failure scenario & troubleshooting

**Symptom** → user thấy content cũ sau publish.

**Evidence** → CDN response header cho biết cached object còn fresh theo TTL.

**Hypothesis** → invalidation/freshness policy không khớp publishing requirement.

**Diagnosis** → inspect `Age`, `Cache-Control`, ETag, CDN cache key và purge logs.

**Fix** → điều chỉnh TTL, versioned URLs, purge/invalidation hoặc revalidation strategy.

**Verification** → publish test và trace browser → CDN → origin behavior.

## 7. Common mistakes

* Cache personalized response với `public`.
* Dùng TTL dài mà không có invalidation path.
* Cache key bỏ qua query/header làm response bị dùng sai context.
* Dùng `no-cache` và tưởng là “không lưu cache”; thực tế nó thường yêu cầu revalidate.
* Purge toàn CDN thường xuyên thay vì thiết kế key/version hợp lý.

## 8. Alternatives

* Server-side Redis cache: giảm backend work nhưng request vẫn tới origin.
* Application output cache: phù hợp server-side response reuse.
* Browser-only cache: giảm client traffic nhưng không giảm tải toàn edge population như CDN.
* Không cache: đúng khi freshness/security quan trọng hơn latency.

## 9. Trade-offs

### Advantages

* Giảm latency và origin load.
* ETag giảm bandwidth khi content không đổi.
* Edge caching cải thiện global delivery.

### Costs / Risks

* Staleness trở thành business concern.
* Cache key và invalidation có complexity.
* Sai header có thể leak personalized data.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser/CDN có thể reuse response theo headers.

### Middle

Biết `max-age`, ETag và conditional request.

### Senior

Debug multi-layer cache, key, purge, stale behavior và privacy implications.

### Technical Lead / Architect

Định nghĩa freshness SLO theo loại dữ liệu và chọn cache layer phù hợp thay vì blanket caching.

## 11. Key takeaway

* Cache policy là data-freshness contract.
* ETag giúp revalidate rẻ hơn full response.
* Public caching chỉ an toàn khi response thực sự không phụ thuộc user context.

# 10. RAG retrieval quality: chunking, metadata filtering và hybrid search quyết định chất lượng trước khi LLM bắt đầu trả lời

## 1. What is it?

RAG (Retrieval-Augmented Generation) lấy context từ external knowledge source rồi đưa vào LLM. Chất lượng answer phụ thuộc mạnh vào retrieval stage.

Mental model:

```text
User question
    ↓
Retrieval
    ├─ vector similarity
    ├─ keyword search
    └─ metadata filters
    ↓
Selected context
    ↓
LLM generation
```

Nếu context sai hoặc thiếu, model có thể trả lời trôi chảy nhưng groundedness thấp.

## 2. Why does it exist?

LLM không tự có knowledge mới nhất/private repository data và không nên được coi là source of truth cho enterprise documents.

RAG cho phép grounding vào documents hiện hành mà không cần fine-tune cho mọi thay đổi nội dung.

## 3. How does it work?

Documents được chunk, embed/index và lưu metadata. Query được transform thành retrieval request; top candidates được rank rồi đưa vào model.

Chunk quá lớn làm similarity thiếu chính xác và tốn tokens. Chunk quá nhỏ mất context và quan hệ giữa đoạn.

Hybrid search kết hợp lexical match với semantic similarity để xử lý cả exact identifiers lẫn natural-language meaning.

## 4. Practical implementation

Một pipeline thực tế nên giữ metadata như:

```json
{
  "documentId": "api-security-guide",
  "section": "JWT validation",
  "version": "2026-09",
  "tenantId": "tenant-a",
  "classification": "internal"
}
```

Retrieval phải filter authorization/tenant boundary **trước khi** context được đưa cho model.

Pseudo-flow:

```text
Authorize user
   ↓
Build retrieval filters
   ↓
Hybrid search
   ↓
Rerank
   ↓
Select context
   ↓
Generate answer + citations
```

## 5. Real production scenario

Internal support assistant có 50,000 documents. Vector search trả đúng chủ đề nhưng đôi khi lấy policy của tenant khác vì index không filter `tenantId`.

Đây không phải “hallucination problem” đầu tiên; nó là security/data-boundary bug trong retrieval layer.

## 6. Failure scenario & troubleshooting

**Symptom** → answer sai dù model mạnh và prompt ổn.

**Evidence** → retrieved passages không chứa facts cần thiết hoặc chứa version cũ.

**Hypothesis** → retrieval recall/ranking kém, không phải generation failure.

**Diagnosis** → đánh giá retrieval riêng bằng labeled query set: Recall@K, MRR/nDCG tùy use case; inspect chunks và filters.

**Fix** → cải thiện chunking, metadata, hybrid retrieval, reranking hoặc document freshness pipeline.

**Verification** → tách evaluation thành retrieval metrics và answer-groundedness metrics.

## 7. Common mistakes

* Tuning prompt trong khi retrieval trả sai documents.
* Chỉ dùng vector search cho identifiers/version numbers.
* Chunk theo fixed token count mà bỏ document structure.
* Không version metadata, khiến policy cũ cạnh tranh với policy mới.
* Filter tenant/security sau retrieval hoặc sau generation.
* Không log retrieved document IDs cho debugging.

## 8. Alternatives

* Direct database/API lookup: tốt hơn nếu câu hỏi có deterministic structured source.
* Full-text search: đủ với exact terms và corpus nhỏ.
* Fine-tuning: không thay thế dynamic knowledge retrieval cho dữ liệu cập nhật thường xuyên.
* Tool Calling: phù hợp khi model cần gọi deterministic systems thay vì đọc document text.

## 9. Trade-offs

### Advantages

* Knowledge có thể cập nhật độc lập với model.
* Có thể trích nguồn và audit context.
* Hybrid retrieval thích nghi nhiều query types.

### Costs / Risks

* Indexing, chunking và evaluation tạo pipeline complexity.
* Retrieval có thể leak data nếu filter sai.
* More context không đồng nghĩa answer tốt hơn; token cost và distraction tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG = retrieve context trước rồi mới generate.

### Middle

### Senior

Tách retrieval failure khỏi model failure, xây evaluation set và debug ranking.

### Technical Lead / Architect

Quyết định dữ liệu nào nên dùng RAG, dữ liệu nào phải qua deterministic tool/API; thiết kế authorization, observability, freshness và cost boundary.

## 11. Key takeaway

* RAG quality bắt đầu ở retrieval, không bắt đầu ở prompt.
* Metadata/security filtering là application boundary, không giao cho LLM tự quyết.
* Đánh giá retrieval và generation riêng để biết cần sửa tầng nào.
