# 1. .NET ThreadPool starvation: khi `async` code vẫn làm server nghẽn vì sync-over-async và blocking

## 1. What is it?

ThreadPool starvation xảy ra khi application có nhiều work đang chờ một thread nhưng số thread khả dụng không đủ để phục vụ kịp. Trong ASP.NET Core, điều nguy hiểm là code có thể “trông có vẻ async” nhưng vẫn block worker thread bằng `.Result`, `.Wait()`, synchronous I/O hoặc long-running CPU work.

Mental model:

```text
Request đến
   ↓
ThreadPool worker
   ↓
Code block thread để chờ I/O
   ↓
worker không phục vụ request khác
   ↓
queue tăng
   ↓
p95/p99 tăng mạnh
```

`async` chỉ giúp nếu thread thực sự được giải phóng trong thời gian chờ I/O.

## 2. Why does it exist?

ASP.NET Core được tối ưu cho lượng concurrent I/O lớn. Nếu mỗi request giữ một thread trong lúc chờ database, HTTP hoặc file I/O, throughput cuối cùng bị giới hạn bởi số worker threads thay vì bởi downstream resource.

ThreadPool có khả năng tăng số threads theo thời gian, nhưng tăng chậm có chủ đích để tránh tạo hàng nghìn threads và context-switch overhead. Vì vậy khi nhiều requests đồng loạt block, latency có thể tăng rất nhanh trước khi pool kịp phản ứng.

## 3. How does it work?

Một đoạn code nguy hiểm:

```csharp
public IActionResult Get()
{
    var data = _client.GetStringAsync("https://example.com").Result;
    return Ok(data);
}
```

`GetStringAsync` dùng asynchronous I/O, nhưng `.Result` giữ worker thread cho tới khi Task complete.

Nếu 500 requests cùng làm vậy:

```text
500 requests
→ 500 worker threads bị block/chờ
→ requests mới xếp queue
→ ThreadPool hill-climbing tăng thread từ từ
→ latency tăng trước khi throughput hồi phục
```

CPU có thể không cao. Đây là lý do “CPU chỉ 25%” không loại trừ ThreadPool starvation.

## 4. Practical implementation

Viết end-to-end async:

```csharp
public async Task<IResult> GetAsync(CancellationToken ct)
{
    using var response = await _httpClient.GetAsync(
        "https://example.com",
        HttpCompletionOption.ResponseHeadersRead,
        ct);

    response.EnsureSuccessStatusCode();

    var content = await response.Content.ReadAsStringAsync(ct);
    return Results.Ok(content);
}
```

Với CPU-bound work nặng trong request path, không mặc định dùng `Task.Run`. Nếu operation thật sự expensive, cân nhắc queue/background processing hoặc giới hạn concurrency.

Monitoring hữu ích:

```bash
dotnet-counters monitor System.Runtime
```

Quan sát:

* ThreadPool Thread Count
* ThreadPool Queue Length
* CPU Usage
* GC metrics
* request latency

## 5. Real production scenario

Một API gọi ba downstream services. Team đã chuyển controller thành `async Task<IActionResult>` nhưng một helper cũ vẫn dùng:

```csharp
_httpClient.SendAsync(request).GetAwaiter().GetResult();
```

Ở 50 RPS mọi thứ ổn. Khi traffic tăng 10x, CPU vẫn chỉ 40% nhưng p99 từ 300 ms lên 12 giây, request queue dài và health check timeout.

Root cause không phải downstream chậm hơn; worker threads bị giữ trong sync-over-async.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng mạnh, request queue tăng, CPU không nhất thiết cao.

**Evidence** → ThreadPool queue length tăng; thread count tăng dần; stack traces có `.Wait`, `.Result`, `GetAwaiter().GetResult()` hoặc synchronous I/O.

**Hypothesis** → worker threads bị block thay vì được trả về pool.

**Diagnosis** → dùng `dotnet-counters`, profiler/thread dump, trace slow requests, tìm sync-over-async trong hot path.

**Fix** → propagate `async/await`, loại synchronous I/O, giới hạn CPU-bound work, tránh lock dài.

**Verification** → queue length giảm, p95/p99 ổn định khi load test cùng throughput.

## 7. Common mistakes

* Chỉ đổi signature thành `async` nhưng bên trong vẫn block.
* Dùng `Task.Run` để “biến” synchronous database/HTTP call thành async.
* Tạo quá nhiều parallel Tasks mà không bound concurrency.
* Tăng ThreadPool minimum threads như fix mặc định.
* Chỉ nhìn CPU rồi kết luận application còn dư capacity.
* Không propagate `CancellationToken` khi client đã disconnect.

## 8. Alternatives

Nếu thư viện chỉ có synchronous API và operation ngắn, đôi khi synchronous execution vẫn chấp nhận được với concurrency thấp. Nếu operation dài hoặc unbounded, hãy tách khỏi request path qua queue/worker.

Tăng minimum ThreadPool threads đôi khi giảm transient starvation trong workload đã hiểu rõ, nhưng không sửa root cause blocking.

## 9. Trade-offs

### Advantages

* End-to-end async tăng scalability cho I/O-bound services.
* Giảm số worker threads cần thiết cho cùng concurrency.

### Costs / Risks

* Async lan xuyên nhiều layers.
* Debugging cancellation/lifetime phức tạp hơn.
* Unbounded async concurrency vẫn có thể làm downstream chết dù ThreadPool khỏe.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` giúp thread được dùng cho việc khác khi I/O chưa hoàn tất.

### Middle

Biết nhận diện `.Result`, `.Wait()`, synchronous I/O và đo ThreadPool counters.

### Senior

Phân biệt ThreadPool starvation với CPU saturation, database bottleneck hoặc network latency.

### Technical Lead / Architect

Thiết kế concurrency boundaries, queueing strategy và capacity model để request path không phụ thuộc unbounded blocking work.

## 11. Key takeaway

* `async` signature không đảm bảo application non-blocking.
* ThreadPool starvation có thể xảy ra khi CPU còn thấp.
* Điều tra bằng queue/thread evidence, không chỉ bằng cảm giác.

# 2. ASP.NET Core ETag + conditional requests: giảm bandwidth mà vẫn giữ đúng HTTP concurrency semantics

## 1. What is it?

ETag là HTTP validator đại diện cho một version cụ thể của resource representation. Client có thể gửi `If-None-Match` để hỏi “resource có thay đổi chưa?” hoặc `If-Match` để yêu cầu update chỉ khi version vẫn khớp.

Mental model:

```text
GET resource
→ ETag: "v42"

GET lại + If-None-Match: "v42"
→ unchanged → 304 Not Modified

PUT + If-Match: "v42"
→ update chỉ nếu version vẫn là v42
```

ETag vừa có giá trị cho caching vừa có thể làm optimistic concurrency ở HTTP boundary.

## 2. Why does it exist?

Nếu client cứ tải lại 500 KB JSON dù dữ liệu không đổi, bandwidth và serialization cost bị lãng phí. Nếu client update resource mà không biết version đã thay đổi, lost update có thể xảy ra.

ETag cung cấp một contract chuẩn ở protocol level thay vì invent `version` query parameter riêng cho từng API.

## 3. How does it work?

Server trả:

```http
HTTP/1.1 200 OK
ETag: "order-123-v7"
Content-Type: application/json
```

Client sau đó gửi:

```http
If-None-Match: "order-123-v7"
```

Nếu representation không đổi:

```http
HTTP/1.1 304 Not Modified
```

Với mutation:

```http
PUT /orders/123
If-Match: "order-123-v7"
```

Nếu version hiện tại là v8, server nên từ chối precondition thay vì overwrite âm thầm.

## 4. Practical implementation

Một Minimal API dùng `RowVersion` từ EF Core:

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    HttpContext http,
    AppDbContext db,
    CancellationToken ct) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new
        {
            x.Id,
            x.Status,
            x.Total,
            x.RowVersion
        })
        .SingleOrDefaultAsync(ct);

    if (order is null)
        return Results.NotFound();

    var etag = $"\"{Convert.ToBase64String(order.RowVersion)}\"";

    if (http.Request.Headers.IfNoneMatch == etag)
        return Results.StatusCode(StatusCodes.Status304NotModified);

    http.Response.Headers.ETag = etag;
    return Results.Ok(order);
});
```

Trong production nên encapsulate validator logic và xử lý weak/strong ETag semantics rõ ràng.

## 5. Real production scenario

Mobile app refresh order status mỗi 10 giây. 95% polls không có thay đổi. Nếu mỗi lần server serialize và trả full payload, bandwidth và CPU tăng không cần thiết.

ETag + `If-None-Match` biến phần lớn requests thành 304 nhỏ. Nếu cùng resource được edit từ web portal, `If-Match` còn giúp tránh stale write.

## 6. Failure scenario & troubleshooting

**Symptom** → cache revalidation luôn trả 200 dù dữ liệu không đổi, hoặc 304 được trả sai khi representation đã thay đổi.

**Evidence** → ETag được tính từ `updatedAt` có precision thấp; hoặc representation phụ thuộc user/locale nhưng ETag chỉ dựa trên database row.

**Hypothesis** → validator không đại diện đầy đủ cho representation.

**Diagnosis** → so sánh response body thay đổi với ETag generation inputs; kiểm tra `Vary`, authorization và content negotiation.

**Fix** → ETag phải thay đổi khi representation thay đổi; scope cache đúng theo user/variant.

**Verification** → integration tests cho unchanged/changed representation và concurrent update.

## 7. Common mistakes

* Hash toàn payload lớn mỗi request dù database đã có version token rẻ hơn.
* Dùng ETag giống nhau cho personalized responses khác nhau.
* Trả 304 nhưng vẫn query/load toàn graph cực nặng trước đó.
* Dùng `If-Match` nhưng ignore khi header thiếu trong endpoint cần concurrency protection.
* Nhầm ETag với authorization boundary.

## 8. Alternatives

`Last-Modified`/`If-Modified-Since` đơn giản hơn nhưng precision và semantics yếu hơn cho một số use cases. Application-level version field dễ hiểu nhưng không tận dụng chuẩn HTTP. CDN/browser caching phù hợp static/public content nhưng không thay thế concurrency control cho mutable APIs.

## 9. Trade-offs

### Advantages

* Giảm payload/bandwidth.
* Tận dụng semantics chuẩn của HTTP.
* Có thể hỗ trợ optimistic concurrency tại API boundary.

### Costs / Risks

* Validator generation có cost.
* Personalized/variant responses làm cache semantics phức tạp.
* Sai ETag logic có thể phục vụ stale data.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 304 nghĩa là dùng bản đã cache, không phải “không có dữ liệu”.

### Middle

Biết implement `ETag`, `If-None-Match`, `If-Match` và tests.

### Senior

Đánh giá validator correctness, representation variants và concurrency semantics.

### Technical Lead / Architect

Quyết định resource nào đáng revalidate, boundary nào thuộc CDN/browser/API và consistency contract nào client phải tuân theo.

## 11. Key takeaway

* ETag là version của representation, không chỉ là một cache header trang trí.
* `If-None-Match` tối ưu reads; `If-Match` có thể bảo vệ writes.
* Validator sai còn nguy hiểm hơn không dùng cache.

# 3. EF Core `DbContext` pooling vs database connection pooling: hai pool khác nhau và failure mode khác nhau

## 1. What is it?

`DbContext` pooling tái sử dụng instance `DbContext` đã được reset để giảm allocation/setup cost. Database connection pooling tái sử dụng physical database connections ở ADO.NET provider level.

Hai pool hoàn toàn khác nhau:

```text
DbContext Pool
→ reuse EF Core context object

Connection Pool
→ reuse physical DB connection
```

Một pooled `DbContext` vẫn mượn/ trả database connection từ connection pool khi query thực thi.

## 2. Why does it exist?

Tạo `DbContext` thường không quá đắt, nhưng ở high-throughput services, model setup/state initialization có thể tạo overhead. Pooling giảm cost đó.

Database connection lại là resource mạng đắt hơn nhiều. Connection pooling tồn tại để tránh TCP/TLS/login handshake cho mỗi query.

Nhầm hai khái niệm dẫn đến chẩn đoán sai khi connection pool exhausted.

## 3. How does it work?

Cấu hình:

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Khi request kết thúc, context được reset rồi đưa về pool. Nhưng EF Core không giữ một connection riêng vĩnh viễn cho context.

Typical lifecycle:

```text
Request
→ rent DbContext
→ query
→ open DB connection from ADO.NET pool
→ execute
→ close/return connection
→ reset DbContext
→ return DbContext to context pool
```

## 4. Practical implementation

Pooled context không nên chứa mutable per-request state theo cách unsafe:

```csharp
public sealed class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options)
        : base(options) { }

    public DbSet<Order> Orders => Set<Order>();
}
```

Nếu cần tenant-specific filter, đừng set tenant ID một lần trong constructor của pooled context rồi giả định instance chỉ thuộc một request.

Một approach tốt hơn là cung cấp tenant context qua scoped service/factory với lifecycle rõ, hoặc dùng mechanism đã được thiết kế để state được reset đúng.

## 5. Real production scenario

Một SaaS API bật `AddDbContextPool` để giảm allocations. Team sau đó nghĩ “đã pooling rồi nên connection exhaustion chắc không thể xảy ra”. Nhưng endpoint export giữ data reader mở 45 giây, 100 concurrent exports chiếm gần hết SQL connection pool.

DbContext pool khỏe; database connection pool mới là bottleneck.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout kiểu “Timeout expired prior to obtaining a connection from the pool”.

**Evidence** → long-running queries/readers; connection pool counters/telemetry cao; DbContext creation time không đáng kể.

**Hypothesis** → connection pool exhaustion, không phải thiếu DbContext instances.

**Diagnosis** → đo query duration, active connections, transaction duration, streaming behavior.

**Fix** → giảm thời gian giữ connection, bound concurrency, tối ưu query, tránh transaction/network call dài.

**Verification** → connection wait giảm dưới load test.

## 7. Common mistakes

* Bật DbContext pooling trước khi đo bottleneck.
* Lưu mutable tenant/user state trong pooled context.
* Inject scoped service vào logic lifecycle không tương thích với pooling.
* Cho rằng `DbContext` pooling làm queries nhanh hơn bản chất.
* Tăng connection pool size vô hạn thay vì giảm hold time.

## 8. Alternatives

`AddDbContext` bình thường đủ tốt cho phần lớn applications. `IDbContextFactory<T>` hữu ích khi cần tạo nhiều context theo unit of work rõ. Connection pool sizing thuộc provider/connection string và nên dựa trên database capacity, không chỉ application demand.

## 9. Trade-offs

### Advantages

* Giảm allocation/setup cost ở high-throughput scenarios.
* Có thể cải thiện latency nhẹ khi context creation measurable.

### Costs / Risks

* Mutable state phải được quản lý cực kỳ cẩn thận.
* Dễ tạo ảo giác rằng database connection cũng được giải quyết.
* Complexity tăng nếu multi-tenant context state phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbContext` và DB connection không phải cùng một object/lifecycle.

### Middle

Biết cấu hình pooling và tránh state leak.

### Senior

Phân tích connection hold time, query concurrency và context lifecycle riêng biệt.

### Technical Lead / Architect

Chỉ bật pooling khi benchmark chứng minh lợi ích và thiết kế multi-tenant/lifecycle không vi phạm reset semantics.

## 11. Key takeaway

* DbContext pool và connection pool giải quyết hai cost khác nhau.
* Connection exhaustion thường liên quan hold time/concurrency hơn context creation.
* Pooling là optimization, không phải default architecture requirement.

# 4. PostgreSQL MVCC + autovacuum: vì sao UPDATE không đơn giản là “ghi đè một row”

## 1. What is it?

PostgreSQL dùng MVCC (Multi-Version Concurrency Control): update thường tạo một row version mới thay vì ghi đè trực tiếp version cũ. Transaction khác có thể nhìn version phù hợp với snapshot của nó.

Mental model:

```text
row v1 visible to transaction A
UPDATE
→ row v2 created
→ v1 becomes dead later
→ VACUUM eventually reclaims space
```

Đây là nền tảng giúp readers và writers ít block nhau hơn.

## 2. Why does it exist?

Nếu read phải block write và write phải block read trên cùng row, concurrency sẽ giảm mạnh. MVCC cho phép transaction đọc một snapshot consistent trong khi transaction khác đang tạo version mới.

Trade-off là database phải quản dead tuples và cleanup.

## 3. How does it work?

Mỗi tuple có metadata về transaction visibility. Khi UPDATE:

1. version mới được insert.
2. version cũ không còn visible cho transactions mới sau commit.
3. transaction cũ có thể vẫn cần version cũ.
4. khi không transaction nào cần nữa, vacuum có thể reclaim.

Một long-running transaction có thể giữ old snapshots và ngăn cleanup lâu hơn dự kiến.

## 4. Practical implementation

Theo dõi dead tuples:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Tìm long-running transactions:

```sql
SELECT
    pid,
    now() - xact_start AS transaction_age,
    state,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Không nên disable autovacuum để “giảm I/O” mà không hiểu hậu quả.

## 5. Real production scenario

Một table session có hàng triệu UPDATE/ngày. Query latency tăng dần, disk usage lớn hơn data logical rất nhiều. Autovacuum chạy nhưng một transaction reporting giữ snapshot hàng giờ.

Dead tuples tích tụ; indexes/table bloat tăng; cache efficiency giảm.

## 6. Failure scenario & troubleshooting

**Symptom** → table size tăng mạnh, queries chậm dần, autovacuum thường xuyên nhưng cleanup không hiệu quả.

**Evidence** → `n_dead_tup` cao; long-running transaction; vacuum logs cho thấy tuples chưa removable.

**Hypothesis** → MVCC cleanup bị cản hoặc autovacuum thresholds không phù hợp workload.

**Diagnosis** → inspect transaction age, table churn, vacuum frequency, index bloat.

**Fix** → kết thúc long transactions, tune autovacuum theo table, giảm unnecessary updates, batch hợp lý.

**Verification** → dead tuples/bloat giảm, query I/O và latency cải thiện.

## 7. Common mistakes

* Nghĩ UPDATE luôn in-place.
* Disable autovacuum vì thấy nó dùng CPU/I/O.
* Mở transaction rồi giữ qua user interaction/network calls.
* Chỉ nhìn row count mà bỏ qua dead tuples.
* VACUUM FULL production tùy tiện mà không hiểu locking/downtime implications.

## 8. Alternatives

SQL Server cũng có versioning mechanisms nhưng implementation khác. Pessimistic locking models có trade-off khác. Partitioning có thể giúp lifecycle data lớn nhưng không thay thế MVCC cleanup.

## 9. Trade-offs

### Advantages

* Read/write concurrency tốt.
* Snapshot semantics mạnh.

### Costs / Risks

* Dead tuples cần vacuum.
* Long transactions có operational consequence lớn.
* Write-heavy tables cần tuning riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu database có thể giữ nhiều versions của cùng logical row.

### Middle

Biết xem `pg_stat_activity`, `pg_stat_user_tables` và autovacuum basics.

### Senior

Liên kết write churn → dead tuples → bloat → I/O → latency.

### Technical Lead / Architect

Thiết kế transaction lifetime, retention và write patterns phù hợp MVCC thay vì coi maintenance là việc DBA “tự lo”.

## 11. Key takeaway

* PostgreSQL UPDATE thường tạo version mới.
* Autovacuum là correctness/maintenance mechanism quan trọng, không phải noise.
* Long-running transactions có thể gây hậu quả hệ thống dù chúng “chỉ đọc”.

# 5. MongoDB embedding vs referencing: thiết kế document theo access pattern thay vì mô phỏng relational schema

## 1. What is it?

Embedding lưu related data trực tiếp bên trong cùng document. Referencing lưu ID/reference tới document khác.

Ví dụ embedding:

```json
{
  "orderId": "O-1001",
  "customer": {
    "name": "Ha",
    "email": "ha@example.com"
  },
  "items": [
    { "sku": "A1", "qty": 2 }
  ]
}
```

Referencing sẽ tách customer/items sang collections khác rồi nối logic ở application hoặc aggregation pipeline.

## 2. Why does it exist?

Document database tối ưu cho việc đọc/ghi aggregate data cùng nhau. Nếu bạn normalize mọi thứ giống relational schema, application có thể phải tạo nhiều round trips/lookup và mất lợi thế locality.

Ngược lại, embed mọi thứ có thể tạo document quá lớn, duplicate data và update fan-out.

## 3. How does it work?

Quyết định phụ thuộc access pattern:

```text
Data luôn đọc cùng nhau?
Ownership rõ?
Cardinality bounded?
Update cùng lifecycle?
        ↓ yes
Embedding thường hợp lý

Shared independently?
Unbounded growth?
Update riêng thường xuyên?
        ↓ yes
Referencing thường hợp lý
```

Không có rule “NoSQL = denormalize tất cả”.

## 4. Practical implementation

Một order thường nên snapshot commercial data cần audit:

```csharp
public sealed class OrderDocument
{
    public string Id { get; init; } = null!;
    public CustomerSnapshot Customer { get; init; } = null!;
    public List<OrderItem> Items { get; init; } = [];
    public decimal Total { get; init; }
}
```

`CustomerSnapshot` có thể intentionally duplicate name/address tại thời điểm order để history không đổi khi customer profile thay đổi.

Ngược lại, reviews cho product có thể tăng không bounded và phù hợp collection riêng với `productId` index hơn embedding vô hạn vào product document.

## 5. Real production scenario

Marketplace lưu product với toàn bộ reviews embedded. Lúc đầu product có vài reviews. Sau hai năm, sản phẩm hot có hàng chục nghìn reviews; document updates ngày càng nặng, payload khổng lồ và có nguy cơ đụng document size limits.

Access pattern thực tế chỉ cần product summary + 10 reviews mới nhất. Boundary ban đầu sai.

## 6. Failure scenario & troubleshooting

**Symptom** → document lớn dần, write latency tăng, network payload lớn, update conflicts tăng.

**Evidence** → unbounded embedded array; API hiếm khi cần toàn bộ array.

**Hypothesis** → embedding vượt quá ownership/access-pattern boundary.

**Diagnosis** → đo document sizes, read patterns, update frequency và cardinality distribution.

**Fix** → tách unbounded child collection, giữ summary/counter hoặc recent items embedded nếu cần.

**Verification** → document size ổn định, read/write latency và payload giảm.

## 7. Common mistakes

* Chuyển relational tables thành Mongo collections 1:1 rồi lookup khắp nơi.
* Embed unbounded arrays.
* Duplicate mutable data nhưng không có consistency strategy.
* Chọn model theo “schema flexibility” thay vì query patterns.
* Không tạo indexes cho referenced lookup patterns.

## 8. Alternatives

Relational database tốt hơn khi cross-entity constraints/joins/transactions là trung tâm. Cosmos DB có document modeling tương tự nhưng partition key/RU model làm decision khác hơn nữa. MongoDB aggregation `$lookup` có thể hỗ trợ reference nhưng không nên biến thành replacement cho mọi relational join.

## 9. Trade-offs

### Advantages của embedding

* Ít round trips.
* Atomic update trong một document.
* Read locality tốt.

### Costs / Risks

* Duplication.
* Document growth.
* Update fan-out nếu duplicated mutable data.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu document không phải table row có JSON syntax.

### Middle

Model theo read/write access patterns và bounded cardinality.

### Senior

Đánh giá duplication consistency, document growth và operational limits.

### Technical Lead / Architect

Chọn data store/model dựa trên invariants, query shape, scaling và ownership thay vì trào lưu SQL vs NoSQL.

## 11. Key takeaway

* Embedding là ownership/locality decision.
* Referencing phù hợp independent lifecycle hoặc unbounded cardinality.
* Model document theo access pattern, không copy relational schema máy móc.

# 6. DDD Aggregate boundary: bảo vệ invariant mà không biến một transaction thành “siêu aggregate”

## 1. What is it?

Aggregate là consistency boundary trong domain model. Aggregate Root là entry point chịu trách nhiệm giữ các invariants phải đúng ngay khi transaction commit.

Mental model:

```text
Command
→ Aggregate Root
→ enforce invariants
→ mutate entities/value objects bên trong boundary
→ commit một transaction
```

Aggregate không đơn giản là object graph “có quan hệ với nhau”.

## 2. Why does it exist?

Nếu domain logic cho phép bất kỳ code nào sửa bất kỳ entity nào, invariants dễ bị phá. Nhưng nếu gom quá nhiều entities vào cùng aggregate, mỗi operation phải load/lock một graph lớn và concurrency giảm.

Aggregate boundary cân bằng correctness và contention.

## 3. How does it work?

Ví dụ Order aggregate có invariant:

* không add item sau khi Order đã submitted.
* total phải bằng tổng line items.

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public OrderStatus Status { get; private set; }
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void AddItem(ProductId productId, int quantity, Money price)
    {
        if (Status != OrderStatus.Draft)
            throw new DomainException("Only draft orders can be changed.");

        if (quantity <= 0)
            throw new DomainException("Quantity must be positive.");

        _lines.Add(new OrderLine(productId, quantity, price));
    }
}
```

Inventory không nhất thiết nằm trong Order aggregate chỉ vì checkout liên quan inventory.

## 4. Practical implementation

Application layer orchestration:

```csharp
public async Task HandleAsync(AddItemCommand cmd, CancellationToken ct)
{
    var order = await db.Orders
        .Include(x => x.Lines)
        .SingleAsync(x => x.Id == cmd.OrderId, ct);

    order.AddItem(cmd.ProductId, cmd.Quantity, cmd.Price);

    await db.SaveChangesAsync(ct);
}
```

Nếu cần reserve inventory, đó có thể là coordination giữa aggregates/bounded contexts qua application service hoặc event, không nhất thiết cùng transaction database.

## 5. Real production scenario

Team tạo `Customer` aggregate chứa Orders, Addresses, Payments, Loyalty, Preferences để “giữ mọi thứ consistent”. Mỗi customer update load graph lớn và các flows không liên quan cạnh tranh cùng row/version.

Kết quả là concurrency conflicts và repository queries phức tạp.

Boundary tốt hơn: chỉ những invariants cần atomic consistency mới ở cùng aggregate.

## 6. Failure scenario & troubleshooting

**Symptom** → optimistic concurrency conflicts cao và aggregate load cực lớn.

**Evidence** → nhiều commands độc lập cùng sửa một giant aggregate root; includes sâu; transaction duration tăng.

**Hypothesis** → aggregate boundary quá rộng.

**Diagnosis** → liệt kê invariants thật sự cần atomicity; map command ownership và contention hotspots.

**Fix** → tách aggregates/bounded contexts, dùng eventual consistency cho cross-boundary workflows khi business cho phép.

**Verification** → transaction scope nhỏ hơn, conflict rate giảm, invariants vẫn được test.

## 7. Common mistakes

* Aggregate = mọi entity có FK liên quan.
* Mỗi table = một aggregate root mà không xét invariant.
* Dùng public setters cho toàn domain model rồi gọi đó là DDD.
* Cross-aggregate transaction khổng lồ để tránh eventual consistency bằng mọi giá.
* Domain event cho mọi method call dù không có boundary value.

## 8. Alternatives

Transaction Script đơn giản hơn cho domain CRUD ít invariant. Rich domain model có giá trị khi business rules phức tạp. CQRS có thể tách read model khỏi aggregate write model nhưng không bắt buộc.

## 9. Trade-offs

### Advantages

* Invariants có owner rõ.
* Transaction boundaries rõ.
* Domain logic ít rò rỉ ra application layer.

### Costs / Risks

* Boundary sai gây contention hoặc eventual-consistency complexity.
* Rich model có learning/maintenance cost.
* Không đáng dùng cho domain đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Aggregate Root kiểm soát thay đổi bên trong một consistency boundary.

### Middle

Implement commands qua aggregate methods thay vì sửa state tùy ý.

### Senior

Thiết kế aggregate theo invariant và contention, không theo FK graph.

### Technical Lead / Architect

Quyết định nơi cần strong consistency và nơi business chấp nhận eventual consistency để giữ scale và simplicity.

## 11. Key takeaway

* Aggregate là consistency boundary, không phải folder hoặc graph navigation.
* Boundary quá lớn làm concurrency và performance tệ.
* Chỉ gom cùng aggregate những invariants cần atomic consistency.

# 7. Azure App Service deployment slots: zero-downtime rollout, warm-up và configuration swap traps

## 1. What is it?

Deployment slot là một live environment riêng trong cùng App Service app, ví dụ `staging` và `production`. Bạn deploy phiên bản mới vào staging, warm/test nó rồi swap routing/configuration sang production.

Mental model:

```text
Deploy v2 → staging
           ↓
      warm + verify
           ↓
          swap
           ↓
production chạy v2
```

Mục tiêu là giảm downtime và rollback nhanh hơn deployment trực tiếp.

## 2. Why does it exist?

Deploy in-place có thể làm process restart giữa traffic, cache/JIT cold, migration chưa tương thích hoặc startup fail. Slot cho phép chuẩn bị artifact trong environment gần production trước khi traffic chính chuyển sang.

Nhưng “slot swap” không tự động đảm bảo zero downtime nếu application không tương thích nhiều versions hoặc config bị swap sai.

## 3. How does it work?

Một số settings có thể đánh dấu “deployment slot setting” để chúng bám theo slot thay vì swap. Điều này rất quan trọng cho secrets/endpoints environment-specific.

Flow:

```text
Production slot: v1 + prod config
Staging slot:    v2 + staging/warmup
        ↓ swap
Production slot: v2 + prod slot-specific config
```

Application initialization và health validation cần hoàn tất trước khi nhận production traffic.

## 4. Practical implementation

Checklist triển khai:

```text
1. Deploy artifact v2 vào staging.
2. Apply compatible DB migration trước hoặc theo expand-contract.
3. Hit warm-up/health endpoints.
4. Run smoke tests với staging hostname.
5. Verify dependencies, Key Vault, DB, cache.
6. Swap staging → production.
7. Monitor error rate/p95/dependency failures.
8. Swap back nếu regression và schema vẫn backward compatible.
```

Đánh dấu environment-specific config là slot setting khi cần, ví dụ staging API endpoints không được “đi theo” code sang production.

## 5. Real production scenario

Team deploy v2 vào staging và smoke test tốt. Khi swap, production bắt đầu gọi sandbox payment endpoint vì setting đó không được đánh dấu slot-specific và đã swap cùng slot.

Code hoàn toàn đúng; deployment semantics của configuration mới là failure.

## 6. Failure scenario & troubleshooting

**Symptom** → app healthy ở staging nhưng production lỗi ngay sau swap.

**Evidence** → dependency endpoints/config values khác sau swap; startup logs hoặc secret resolution fail.

**Hypothesis** → slot setting/configuration swap mismatch hoặc cold dependency.

**Diagnosis** → compare effective config trước/sau swap; inspect App Service activity logs/Application Insights.

**Fix** → classify slot-specific settings đúng, warm-up thật, smoke test production dependencies an toàn.

**Verification** → repeat swap in pre-production và validate config snapshot.

## 7. Common mistakes

* Coi slot như một environment hoàn toàn tách biệt mọi resource.
* Database schema breaking change khiến swap-back không còn an toàn.
* Không warm application/dependencies.
* Health endpoint chỉ trả 200 mà không kiểm critical startup state.
* Swap secrets/endpoints ngoài ý muốn.
* Rollback code nhưng database migration đã irreversible.

## 8. Alternatives

Blue/green ở Container Apps/Kubernetes cho control rộng hơn nhưng operational complexity cao hơn. Rolling deployment đơn giản hơn nhưng rollback behavior khác. Canary deployment giảm blast radius tốt hơn nhưng cần routing/telemetry maturity.

## 9. Trade-offs

### Advantages

* Giảm downtime.
* Rollback nhanh bằng swap khi schema compatible.
* Có môi trường để warm/smoke test artifact thật.

### Costs / Risks

* Slot/config semantics cần hiểu kỹ.
* Database vẫn thường là shared dependency.
* Không thay thế backward-compatible migration design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu staging slot là live deployment target trước production.

### Middle

Biết deploy, warm, smoke test và swap settings đúng.

### Senior

Thiết kế rollback, config classification và database compatibility.

### Technical Lead / Architect

Chọn slot/blue-green/canary dựa trên blast radius, traffic control, schema strategy và operational maturity.

## 11. Key takeaway

* Slot swap giảm deployment risk nhưng không loại bỏ application/data compatibility risk.
* Slot-specific configuration phải được thiết kế có chủ đích.
* Rollback chỉ thật sự an toàn khi cả code và schema còn backward compatible.

# 8. SLI/SLO/Error Budget: biến reliability thành quyết định kỹ thuật thay vì cảm giác

## 1. What is it?

SLI là measurement của reliability, ví dụ successful-request ratio hoặc latency percentile. SLO là target cho SLI trong một khoảng thời gian. Error Budget là phần unreliability còn được phép trước khi vượt SLO.

Ví dụ:

```text
SLI: tỷ lệ requests thành công
SLO: 99.9% trong 30 ngày
Error budget: 0.1% requests được phép fail
```

SLA là cam kết thương mại/pháp lý với khách hàng và không nên bị nhầm với internal SLO.

## 2. Why does it exist?

Nếu mục tiêu chỉ là “hệ thống phải ổn định”, team khó quyết định nên ưu tiên feature hay reliability work. 100% availability thường quá đắt và không thực tế.

SLO tạo một reliability target có thể đo. Error Budget biến nó thành decision mechanism: nếu budget đang cháy nhanh, giảm release risk và tập trung reliability.

## 3. How does it work?

Ví dụ 30 ngày có 10 triệu requests, SLO 99.9% success:

```text
allowed failed requests ≈ 10,000
```

Nếu incident làm fail 7,000 requests chỉ trong một giờ, team đã dùng 70% monthly budget.

Burn rate quan trọng hơn chỉ nhìn current error rate vì nó cho biết budget đang bị tiêu nhanh tới mức nào.

## 4. Practical implementation

Một SLI query conceptual:

```text
good_requests / total_valid_requests
```

Không nên tính mọi 4xx là server failure. Ví dụ client gửi invalid request 400 có thể không thuộc availability SLI; nhưng 500/503 thường có.

Với latency SLO:

```text
99% requests < 500 ms
```

Application Insights/OpenTelemetry metrics có thể cung cấp request duration và result dimensions, nhưng cardinality cần kiểm soát.

## 5. Real production scenario

Team đặt alert “5xx > 1% trong 5 phút”. Một service low-traffic chỉ có 20 requests/5 phút; một lỗi đơn lẻ tạo 5% và pager liên tục. Ngược lại, service high-traffic có 0.4% lỗi cả ngày nhưng burn error budget rất nhanh.

SLO-based alerting theo burn rate giúp alert phản ánh user impact tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → alerts noisy nhưng incidents quan trọng vẫn bị bỏ qua.

**Evidence** → thresholds tuyệt đối không liên hệ với SLO/user journey.

**Hypothesis** → observability đo infrastructure symptoms nhưng không đo service reliability objective.

**Diagnosis** → map critical user journeys, define valid events, inspect historical incidents.

**Fix** → chọn SLI meaningful, SLO realistic, multi-window burn-rate alerts.

**Verification** → replay incident history: critical incidents trigger, normal noise không trigger quá mức.

## 7. Common mistakes

* SLO = 100% vì “khách hàng quan trọng”.
* Dùng average latency làm SLI.
* Đếm client errors giống server failures mà không phân loại.
* Chọn SLO không dựa trên user/business impact.
* Dùng SLO chỉ để làm dashboard đẹp, không ảnh hưởng release decisions.

## 8. Alternatives

Simple threshold alerts vẫn phù hợp cho resource saturation cụ thể như disk full hoặc queue backlog. SLO không thay thế metrics/logs/traces; nó cung cấp objective để ưu tiên và alert theo user impact.

## 9. Trade-offs

### Advantages

* Reliability target có thể đo.
* Giúp cân bằng feature velocity và stability.
* Alerting gần user impact hơn.

### Costs / Risks

* SLI sai dẫn tới behavior sai.
* Cần historical data và review định kỳ.
* Error budget policy cần organizational buy-in.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu availability không phải chỉ “server up”.

### Middle

Biết tạo request/error/latency metrics có thể làm SLI.

### Senior

Thiết kế SLI đúng denominator và burn-rate investigation.

### Technical Lead / Architect

Dùng SLO/error budget để điều khiển release risk, capacity và reliability investment.

## 11. Key takeaway

* SLI là measurement; SLO là target; SLA là commitment.
* Error Budget giúp reliability trở thành decision framework.
* Một SLO tệ có thể tối ưu team theo sai mục tiêu.

# 9. Optimizely CMS content modeling: page type, block, shared content và coupling với rendering code

## 1. What is it?

Trong Optimizely CMS, content model xác định cấu trúc nội dung mà editor quản lý: page types, blocks/content types, properties và content hierarchy. Rendering code ánh xạ model đó thành UI.

Mental model:

```text
Editor content model
      ↓
Page / Block instances
      ↓
Content delivery/query
      ↓
Rendering component
      ↓
HTML/UI
```

Content model là API giữa editorial workflow và application code.

## 2. Why does it exist?

Nếu mọi page chỉ là một giant rich-text field, editor linh hoạt nhưng consistency, reuse và validation thấp. Nếu model quá cứng, mọi content change cần developer deploy.

Page types/blocks tồn tại để cân bằng reusable structure và editorial freedom.

## 3. How does it work?

Ví dụ conceptual:

```csharp
[ContentType(DisplayName = "Article Page")]
public class ArticlePage : PageData
{
    public virtual string Heading { get; set; } = null!;
    public virtual XhtmlString Body { get; set; } = null!;
    public virtual ContentArea RelatedContent { get; set; } = null!;
}
```

`ContentArea` cho phép editor compose blocks. Shared block có thể được reuse nhiều nơi; local block chỉ thuộc context cụ thể tùy modeling approach.

Vấn đề thật sự không phải API attribute mà là ownership/reuse semantics.

## 4. Practical implementation

Một Hero block reusable:

```csharp
[ContentType(DisplayName = "Hero Block")]
public class HeroBlock : BlockData
{
    public virtual string Heading { get; set; } = null!;
    public virtual string? Subheading { get; set; }
    public virtual ContentReference? Image { get; set; }
    public virtual Url? CtaUrl { get; set; }
    public virtual string? CtaText { get; set; }
}
```

Rendering component nên xử lý missing optional content có chủ đích và không giả định mọi property luôn tồn tại từ historical content.

## 5. Real production scenario

Marketing muốn đổi CTA Hero trên 80 pages. Nếu mỗi page copy riêng Hero fields, editor phải update 80 nơi. Shared block giúp reuse nhưng nếu dùng shared content cho thứ vốn cần local variation, một edit có thể thay đổi hàng chục pages ngoài ý muốn.

Reuse là product/editorial decision, không chỉ code reuse.

## 6. Failure scenario & troubleshooting

**Symptom** → CMS deployment làm một số pages cũ render lỗi hoặc editor không hiểu field mới.

**Evidence** → property rename/remove breaking; rendering code assume non-null; content migration thiếu.

**Hypothesis** → content model backward compatibility bị phá.

**Diagnosis** → inspect historical content instances, model changes, serialization/property mapping và editor impact.

**Fix** → additive model changes, migration plan, safe defaults, deprecate trước khi remove.

**Verification** → render representative old content, editor smoke test, content migration validation.

## 7. Common mistakes

* Model CMS theo component tree hiện tại thay vì editorial concept ổn định.
* Giant universal block có hàng chục optional fields.
* Shared blocks cho content thực ra cần local ownership.
* Rename/remove property mà không migration.
* Cho rendering logic chứa quá nhiều business integration calls synchronous.

## 8. Alternatives

Headless CMS tách delivery/rendering mạnh hơn nhưng thêm API/cache/preview complexity. Traditional CMS rendering đơn giản hơn cho integrated .NET sites. Hard-coded content phù hợp khi nội dung không cần editor ownership.

## 9. Trade-offs

### Advantages

* Editor tự quản nội dung có cấu trúc.
* Reuse và consistency tốt.
* Validation/content governance rõ hơn free-form HTML.

### Costs / Risks

* Content schema trở thành long-lived contract.
* Shared content có blast radius lớn.
* Model quá chi tiết làm editorial workflow khó dùng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu page/block là content schema, không chỉ view model.

### Middle

Implement content types, validation và rendering defensive.

### Senior

Thiết kế backward-compatible content model và cache/delivery behavior.

### Technical Lead / Architect

Cân bằng editorial freedom, reuse, migration cost, headless/traditional architecture và ownership giữa CMS với downstream systems.

## 11. Key takeaway

* Content model là contract lâu dài giữa editor và code.
* Shared block reuse có lợi nhưng làm blast radius lớn hơn.
* CMS schema change cần backward-compatibility thinking giống API/database schema change.

# 10. Git `bisect`: điều tra regression bằng binary search thay vì đọc hàng trăm commits thủ công

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên gây regression. Bạn cung cấp một commit “good” và một commit “bad”; Git checkout commit giữa, bạn test rồi đánh dấu good/bad, lặp lại tới khi tìm culprit.

Mental model:

```text
1000 commits
→ test giữa
→ loại 500
→ test giữa phần còn lại
→ loại 250
→ ...
→ culprit commit
```

Thay vì kiểm tra tuyến tính O(n), binary search cần khoảng O(log n) bước.

## 2. Why does it exist?

Production regression thường chỉ biết “release tháng trước ổn, release hôm nay lỗi”. History giữa hai mốc có thể hàng trăm commits. Đọc diff thủ công dễ bias theo commit message và tốn thời gian.

`git bisect` biến investigation thành evidence-driven search.

## 3. How does it work?

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0
```

Git checkout commit trung gian. Sau khi test:

```bash
git bisect good
```

hoặc:

```bash
git bisect bad
```

Kết thúc:

```bash
git bisect reset
```

Có thể tự động hóa bằng script trả exit code 0 = good, non-zero = bad:

```bash
git bisect run ./scripts/repro-regression.sh
```

## 4. Practical implementation

Một script đơn giản cho .NET regression:

```bash
#!/usr/bin/env bash
set -euo pipefail

dotnet test tests/Checkout.Tests/Checkout.Tests.csproj \
  --filter "FullyQualifiedName~PricingRegression"
```

Nếu historical commits cần dependencies/build steps thay đổi, script phải xử lý deterministically hoặc dùng `git bisect skip` cho commit không test được.

## 5. Real production scenario

API memory usage tăng 30% giữa release 2.4 và 2.5. Có 180 commits. Team nghi một caching change nhưng không chắc.

Một benchmark/repro script ổn định + `git bisect run` có thể tìm commit culprit trong khoảng 8–9 test steps thay vì review 180 commits.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit không liên quan hoặc kết quả thay đổi giữa các runs.

**Evidence** → test flaky; environment/config/database state không deterministic; historical commit không build.

**Hypothesis** → oracle “good/bad” không reliable.

**Diagnosis** → chạy repro nhiều lần trên known good/bad; isolate external dependencies.

**Fix** → deterministic test/benchmark, pin environment, reset test data, dùng `bisect skip` khi cần.

**Verification** → culprit commit revert/cherry-pick comparison tái tạo regression ổn định.

## 7. Common mistakes

* Bắt đầu bisect khi chưa chứng minh known-good thực sự good.
* Dùng flaky E2E test làm oracle.
* Không reset environment state giữa commits.
* Kết luận commit culprit = root cause mà không đọc diff và verify.
* Bisect qua merge history phức tạp mà không hiểu topology.

## 8. Alternatives

Manual diff phù hợp khi chỉ có vài commits. `git log -S`/`-G` hữu ích khi biết symbol/text thay đổi. Performance regression có thể dùng benchmark history/CI telemetry nếu đã có. `git bisect` mạnh nhất khi có deterministic pass/fail signal.

## 9. Trade-offs

### Advantages

* Giảm search space rất nhanh.
* Ít phụ thuộc intuition.
* Có thể tự động hóa hoàn toàn với test script.

### Costs / Risks

* Cần reliable oracle.
* Historical commits có thể không build trong current environment.
* Không tự giải thích root cause sau khi tìm culprit.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu good/bad commit và binary search.

### Middle

Dùng `git bisect` thủ công và viết repro test.

### Senior

Tạo deterministic oracle, xử lý skipped commits và verify causal change.

### Technical Lead / Architect

Đầu tư regression tests/benchmarks để historical investigation có thể tự động hóa thay vì phụ thuộc tribal knowledge.

## 11. Key takeaway

* `git bisect` biến regression hunting thành binary search có evidence.
* Chất lượng kết quả phụ thuộc vào test oracle.
* Culprit commit là điểm bắt đầu root-cause analysis, không phải kết luận cuối cùng.
