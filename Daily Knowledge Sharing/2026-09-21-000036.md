# 1. .NET Dependency Injection captive dependency: khi `Singleton` vô tình giữ `Scoped` state

## 1. What is it?

Captive dependency xảy ra khi service có lifetime dài giữ reference tới dependency có lifetime ngắn hơn. Trường hợp nguy hiểm nhất trong ASP.NET Core là `Singleton` giữ `Scoped` service như `DbContext` hoặc request-specific state. Mental model: DI lifetime không chỉ quyết định lúc object được tạo; nó quyết định object được phép sống và chia sẻ state trong boundary nào.

## 2. Why does it exist?

ASP.NET Core dùng scopes để cô lập state theo request. `DbContext`, transaction state và nhiều request services không được thiết kế để dùng đồng thời xuyên requests. Nếu một singleton giữ chúng, boundary đó bị phá: state sống quá lâu, thread-safety sai và disposal không còn đúng lúc.

## 3. How does it work?

```text
Application lifetime
└── Singleton
    └── Scoped dependency  <-- bị giữ vượt request scope

Request A scope ── expected lifetime ──X
Request B ---------------------------> vẫn dùng cùng instance
```

Built-in container có scope validation giúp phát hiện một số cấu hình sai, nhưng runtime factories/service locator có thể che lỗi khỏi validation tĩnh.

## 4. Practical implementation

Sai:

```csharp
public sealed class ReportCache(AppDbContext db)
{
    public Task<int> CountAsync(CancellationToken ct) =>
        db.Reports.CountAsync(ct);
}

builder.Services.AddSingleton<ReportCache>();
builder.Services.AddDbContext<AppDbContext>();
```

Nếu singleton thực sự cần tạo unit of work độc lập, dùng factory có ownership rõ:

```csharp
builder.Services.AddDbContextFactory<AppDbContext>();
builder.Services.AddSingleton<ReportCounter>();

public sealed class ReportCounter(IDbContextFactory<AppDbContext> factory)
{
    public async Task<int> CountAsync(CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);
        return await db.Reports.CountAsync(ct);
    }
}
```

## 5. Real production scenario

Một singleton background coordinator được thêm để cache metadata. Developer inject `DbContext` trực tiếp. Dưới concurrent requests/jobs, change tracker tích lũy entities và xuất hiện lỗi concurrent operation trên cùng context. Local test ít concurrency nên tưởng ổn.

## 6. Failure scenario & troubleshooting

**Symptom** → `A second operation was started on this context...`, stale tracked entities hoặc memory tăng. **Evidence** → cùng `DbContext` instance ID xuất hiện xuyên requests. **Hypothesis** → lifetime mismatch. **Diagnosis** → inspect registrations và dependency graph. **Fix** → đổi owner lifetime hoặc tạo scope/factory tại operation boundary. **Verification** → concurrency test, scope validation và telemetry instance lifetime.

## 7. Common mistakes

Cho rằng DI container tự làm mọi dependency thread-safe; inject `IServiceProvider` vào singleton rồi resolve scoped service từ root provider; đổi scoped service thành singleton để “sửa” exception; giữ request `HttpContext` trong singleton.

## 8. Alternatives

Nếu component không cần singleton, đăng ký `Scoped` thường đơn giản nhất. Background workers có thể tạo scope bằng `IServiceScopeFactory`. `IDbContextFactory<T>` phù hợp khi cần explicit independent contexts.

## 9. Trade-offs

### Advantages

Lifetime đúng giúp isolation, disposal và concurrency semantics rõ ràng.

### Costs / Risks

Factory/scope creation thêm ownership code; lạm dụng service locator làm dependency graph khó nhìn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Transient`, `Scoped`, `Singleton` là lifetime/ownership, không phải performance presets.

### Middle

Biết phát hiện dependency lifetime dài giữ lifetime ngắn và dùng scope/factory đúng chỗ.

### Senior

Debug state leakage, concurrency và disposal issues phát sinh từ lifetime graph.

### Technical Lead / Architect

Định nghĩa lifetime conventions theo application boundaries; tránh singleton nếu không có lý do về shared state/cost rõ ràng.

## 11. Key takeaway

- Lifetime là correctness boundary.
- `Singleton → Scoped` trực tiếp là dấu hiệu phải xem lại ownership.
- Không sửa lifetime mismatch bằng cách kéo mọi dependency lên `Singleton`.

# 2. ASP.NET Core graceful shutdown: ngừng nhận traffic trước khi hủy work đang chạy

## 1. What is it?

Graceful shutdown là quá trình application nhận tín hiệu dừng, ngừng nhận work mới, cho work đang chạy một khoảng thời gian để hoàn tất, propagate cancellation và cuối cùng terminate. Mental model: shutdown là một distributed lifecycle event, không phải chỉ `Process.Exit`.

## 2. Why does it exist?

Deployment, autoscaling, node maintenance và process recycling đều dừng instances bình thường. Nếu process chết ngay, HTTP requests, message handlers và background work có thể bị cắt giữa transaction hoặc side effect.

## 3. How does it work?

```text
SIGTERM / host stop
      ↓
remove from traffic
      ↓
stop accepting new work
      ↓
CancellationToken signaled
      ↓
drain in-flight work within timeout
      ↓
process exits
```

HTTP load balancer, host và application phải phối hợp; application graceful nhưng load balancer vẫn gửi request mới thì drain không bao giờ sạch.

## 4. Practical implementation

```csharp
public sealed class QueueWorker(ILogger<QueueWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var item = await ReceiveAsync(stoppingToken);
            await ProcessAsync(item, stoppingToken);
        }
    }

    public override async Task StopAsync(CancellationToken ct)
    {
        log.LogInformation("Worker draining");
        await base.StopAsync(ct);
    }
}
```

Operation dài phải quyết định checkpoint/retry semantics thay vì giả định shutdown timeout luôn đủ.

## 5. Real production scenario

App Service deployment thay instance trong lúc API đang upload/transform file. Nếu readiness/traffic drain và cancellation đúng, request mới chuyển sang instance khỏe; operation đang chạy hoặc hoàn tất trong window hoặc dừng ở safe checkpoint.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment tạo spike 499/5xx hoặc duplicate background jobs. **Evidence** → failures trùng timestamp process stop; logs thiếu completion event. **Hypothesis** → work bị kill sau shutdown timeout. **Diagnosis** → correlate host lifecycle, request duration và cancellation logs. **Fix** → giảm critical section, persist work vào durable queue, tune drain timeout hợp lý. **Verification** → rolling deployment dưới load không làm mất work.

## 7. Common mistakes

Nuốt `OperationCanceledException` rồi tiếp tục loop; bắt đầu work mới sau cancellation; shutdown hook thực hiện cleanup vô hạn; giữ business-critical long-running work chỉ trong memory; không test deployment under load.

## 8. Alternatives

Durable queue + Worker/Function phù hợp work dài cần retry. Synchronous HTTP phù hợp work ngắn. Kubernetes termination lifecycle hoặc App Service behavior cung cấp hosting primitives nhưng application vẫn phải cooperate.

## 9. Trade-offs

### Advantages

Giảm dropped requests, partial work và deployment regression.

### Costs / Risks

Drain lâu làm rollout chậm; timeout quá ngắn mất work, quá dài làm capacity replacement chậm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cancellation là cooperative signal.

### Middle

Propagate `CancellationToken` qua I/O và background loops.

### Senior

Thiết kế safe interruption, idempotent retry và telemetry cho shutdown.

### Technical Lead / Architect

Chọn synchronous/durable execution boundary và deployment strategy dựa trên maximum operation duration và loss tolerance.

## 11. Key takeaway

- Shutdown là production path phải được test.
- Cancellation phải đi xuyên dependency chain.
- Work dài/quan trọng thường cần durable ownership thay vì process memory.

# 3. SQL covering index: giảm lookup nhưng không biến mọi query thành một index khổng lồ

## 1. What is it?

Covering index là index chứa đủ columns để database trả kết quả query mà không phải quay lại base table/clustered index để lấy thêm dữ liệu. “Covering” là quan hệ giữa index và query, không phải một loại index tuyệt đối.

## 2. Why does it exist?

Một seek có thể tìm đúng rows nhanh nhưng hàng nghìn key lookups sau đó vẫn tạo random I/O. Với read-heavy hot query, include thêm selected columns có thể loại bỏ lookup cost.

## 3. How does it work?

```text
Query
  ↓
Index seek on (CustomerId, CreatedAt)
  ├─ index contains Status, Total -> return directly
  └─ missing columns -> Key Lookup -> clustered/base row
```

Query plan và actual row count quyết định lookup có đáng kể hay không.

## 4. Practical implementation

```sql
SELECT CreatedAt, Status, Total
FROM Orders
WHERE CustomerId = @customerId
  AND CreatedAt >= @from
ORDER BY CreatedAt DESC;
```

Một candidate trên SQL Server:

```sql
CREATE INDEX IX_Orders_Customer_CreatedAt
ON Orders(CustomerId, CreatedAt DESC)
INCLUDE(Status, Total);
```

Sau đó so sánh actual execution plan, logical reads và write overhead; không deploy chỉ vì missing-index hint.

## 5. Real production scenario

Customer order-history API chạy hàng triệu lần/ngày. Plan hiện tại seek đúng 200 rows nhưng thực hiện 200 key lookups/request. Cover query giảm logical reads đáng kể, trong khi write rate của Orders vẫn đủ thấp để chấp nhận index rộng hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → reads nhanh hơn nhưng insert/update latency và storage tăng. **Evidence** → index size lớn, write I/O tăng, nhiều overlapping indexes. **Hypothesis** → over-indexing. **Diagnosis** → usage stats + workload analysis. **Fix** → consolidate/drop redundant indexes hoặc giảm included columns. **Verification** → benchmark cả read lẫn write workload.

## 7. Common mistakes

Include mọi column; coi missing-index recommendation là lệnh; bỏ qua selectivity/order; tạo index cho query hiếm; không đo maintenance/storage; quên query shape thay đổi có thể làm index không còn cover.

## 8. Alternatives

Projection nhỏ hơn có thể đủ. Clustered/index key khác có thể phù hợp workload tổng thể. Cache/read model chỉ nên dùng khi latency/freshness requirements biện minh thêm complexity.

## 9. Trade-offs

### Advantages

Giảm lookup, I/O và latency cho hot read query.

### Costs / Risks

Tăng storage, write amplification và index maintenance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không chỉ giúp `WHERE`; selected columns cũng ảnh hưởng I/O.

### Middle

Đọc execution plan và nhận biết Key Lookup.

### Senior

Đo read benefit đối với write/storage cost và index overlap.

### Technical Lead / Architect

Quản lý index portfolio theo workload thay vì tối ưu từng query cô lập.

## 11. Key takeaway

- “Covering” phải được đánh giá theo query cụ thể.
- Execution plan + logical reads quan trọng hơn intuition.
- Mỗi index đọc nhanh hơn đều phải trả chi phí khi ghi.

# 4. Cosmos DB hot partition: partition key quyết định scalability nhiều hơn số RU tổng

## 1. What is it?

Hot partition xảy ra khi workload tập trung quá nhiều request/data vào một logical partition hoặc một vùng physical partition, khiến capacity phân bố không đều. Mental model: distributed database chỉ scale khi workload cũng phân bố được.

## 2. Why does it exist?

Cosmos DB partitioning cho phép data và throughput trải trên nhiều partitions. Nếu key như `TenantId` có một tenant chiếm 70% traffic, tăng tổng RU có thể vẫn không giải quyết local bottleneck hiệu quả.

## 3. How does it work?

```text
Requests
 ├─ Tenant A ███████████████ -> Partition X (hot)
 ├─ Tenant B ██              -> Partition Y
 └─ Tenant C █               -> Partition Z
```

Partition key ảnh hưởng routing, transaction scope và khả năng phân phối load. Cross-partition query còn tăng RU/query fan-out.

## 4. Practical implementation

Thay vì chỉ `/tenantId`, workload rất lớn có thể cần synthetic key theo access pattern, ví dụ:

```csharp
var partitionKey = $"{tenantId}:{eventDate:yyyyMM}";
var item = new UsageEvent
{
    Id = Guid.NewGuid().ToString(),
    PartitionKey = partitionKey,
    TenantId = tenantId,
    OccurredAt = eventDate
};
```

Đây chỉ đúng nếu queries thường biết tenant + time bucket; partition key không được chọn bằng một công thức chung.

## 5. Real production scenario

SaaS telemetry có một enterprise tenant tạo phần lớn events. `/tenantId` ban đầu đơn giản nhưng tenant đó trở thành hotspot. Time-bucket key phân tán writes, đổi lại queries dài ngày phải fan-out qua nhiều buckets.

## 6. Failure scenario & troubleshooting

**Symptom** → `429 Too Many Requests` dù account-level RU còn dư. **Evidence** → normalized RU consumption tập trung theo partition key. **Hypothesis** → skew. **Diagnosis** → phân tích top keys, request charge và access pattern. **Fix** → redesign key/bucketing hoặc workload; migration nếu cần. **Verification** → load distribution và 429 rate cải thiện.

## 7. Common mistakes

Chọn key có cardinality thấp; chọn random GUID làm key rồi phá query locality; chỉ nhìn total RU; cross-partition query không giới hạn; đổi partition strategy mà không tính migration cost.

## 8. Alternatives

SQL/PostgreSQL phù hợp nếu relational transactions/querying quan trọng hơn global distribution. MongoDB sharding có bài toán shard key tương tự. Azure SQL partitioning không có semantics/cost model giống Cosmos DB.

## 9. Trade-offs

### Advantages

Partition key tốt cho horizontal scale và request routing hiệu quả.

### Costs / Risks

Key sai rất khó sửa sau khi data lớn; key phân tán tốt có thể làm queries phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định data colocate ở đâu.

### Middle

Đo RU, query pattern và tránh obvious low-cardinality keys.

### Senior

Phân tích skew, hot tenants, cross-partition cost và migration.

### Technical Lead / Architect

Chọn store/key từ workload forecast và growth model; xác định trước escape path nếu tenant distribution thay đổi.

## 11. Key takeaway

- Tổng RU không phản ánh distribution quality.
- Partition key là architecture decision khó đổi.
- Tối ưu writes phải cân bằng query locality và transaction boundary.

# 5. DDD Aggregate boundary: invariant và transaction boundary trước Repository hay MediatR

## 1. What is it?

Aggregate là nhóm domain objects được thay đổi như một consistency boundary; Aggregate Root là entry point bảo vệ invariants bên trong boundary đó. Entity có identity; Value Object được định nghĩa bởi value; Domain Service chứa domain operation không thuộc tự nhiên về một entity; Application Service orchestration use case; Domain Event biểu diễn sự kiện domain; Bounded Context xác định model/language boundary lớn hơn.

## 2. Why does it exist?

Nếu mọi entity có thể được sửa độc lập, business invariants xuyên objects dễ bị phá. Ngược lại, aggregate quá lớn làm transaction contention, load graph nặng và coupling cao. Aggregate tồn tại để nói rõ “cái gì phải nhất quán ngay trong một transaction”.

## 3. How does it work?

```text
Bounded Context: Timesheets

Application Service
       ↓
Timesheet (Aggregate Root)
 ├─ Entries (Entities)
 └─ ApprovalPolicy (Value/domain concepts)
       ↓
transaction commits one aggregate change
       ↓
Domain Event -> side effects outside boundary
```

Cross-aggregate consistency thường không nên giả vờ atomic nếu hệ thống phân tán.

## 4. Practical implementation

```csharp
public sealed class Timesheet
{
    private readonly List<Entry> _entries = [];
    public TimesheetStatus Status { get; private set; }

    public void AddEntry(DateOnly day, decimal hours)
    {
        if (Status != TimesheetStatus.Draft)
            throw new DomainException("Only draft timesheets can change.");
        if (hours <= 0 || hours > 24)
            throw new DomainException("Invalid hours.");

        _entries.Add(new Entry(day, hours));
    }

    public void Submit()
    {
        if (_entries.Count == 0) throw new DomainException("Empty timesheet.");
        Status = TimesheetStatus.Submitted;
    }
}
```

Invariant nằm trong model thay vì controller/service rải rác.

## 5. Real production scenario

Timesheet phải đảm bảo submitted sheet không được chỉnh entries. Nếu endpoint update entry bypass root và update row trực tiếp, invariant có thể bị phá dù từng SQL statement hợp lệ.

## 6. Failure scenario & troubleshooting

**Symptom** → production có submitted timesheet vẫn thay đổi entries. **Evidence** → một bulk endpoint update child table trực tiếp. **Hypothesis** → aggregate boundary bị bypass. **Diagnosis** → trace write paths. **Fix** → route mutation qua root/application policy hoặc xác định lại invariant nếu bulk operation là legitimate. **Verification** → domain + integration tests cho mọi write path.

## 7. Common mistakes

Gọi mọi entity group là aggregate; aggregate chứa toàn bộ domain graph; Repository cho từng child entity; dùng MediatR rồi gọi đó là DDD; domain model chỉ có getters/setters còn rules nằm hết trong handlers.

## 8. Alternatives

Transaction Script/CRUD service phù hợp domain đơn giản. Rich domain model đáng giá khi invariants và behavior thực sự phức tạp. Database constraints vẫn nên bảo vệ invariants phù hợp ở storage level.

## 9. Trade-offs

### Advantages

Business rules có owner rõ, transaction boundary dễ reasoning, giảm invalid state.

### Costs / Risks

Modeling effort cao; aggregate quá lớn gây performance/coupling; quá nhỏ gây coordination complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt Entity, Value Object và Aggregate Root theo responsibility.

### Middle

Implement behavior/invariants trong đúng model và test chúng.

### Senior

Đánh giá transaction size, concurrency và cross-aggregate workflow.

### Technical Lead / Architect

Xác định Bounded Context, aggregate boundary và nơi eventual consistency được chấp nhận; chọn simpler model nếu domain không đủ phức tạp.

## 11. Key takeaway

- Aggregate trước hết là consistency/transaction boundary.
- DDD không đồng nghĩa `Repository + MediatR`.
- Boundary phải xuất phát từ invariant và business ownership.

# 6. Azure Functions retries: at-least-once execution đòi hỏi idempotency, không chỉ retry policy

## 1. What is it?

Retry trong Azure Functions cho phép invocation thất bại được thực hiện lại tùy trigger/runtime policy. Mental model: retry tăng cơ hội hoàn tất transient failure nhưng đồng thời tăng khả năng cùng business operation chạy nhiều lần.

## 2. Why does it exist?

Network, database và downstream services có transient failures. Bỏ event ngay lần đầu lỗi làm hệ thống brittle. Nhưng distributed execution không thể giả định exactly-once chỉ vì platform quản lý retry.

## 3. How does it work?

```text
Event -> Function attempt 1 -> DB commit -> response/settlement fails
                   ↓ retry
        Function attempt 2 -> same event again
```

Nếu side effect không idempotent, retry sau ambiguous failure có thể tạo duplicate payment/email/order update.

## 4. Practical implementation

```csharp
public async Task HandleAsync(OrderPaid evt, CancellationToken ct)
{
    if (await db.ProcessedEvents.AnyAsync(x => x.Id == evt.EventId, ct))
        return;

    await using var tx = await db.Database.BeginTransactionAsync(ct);
    db.ProcessedEvents.Add(new ProcessedEvent(evt.EventId));
    await ApplyPaymentAsync(evt, ct);
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
```

Unique constraint trên `ProcessedEvents.Id` cần hỗ trợ race protection; check-then-insert đơn thuần chưa đủ dưới concurrency.

## 5. Real production scenario

Service Bus-triggered Function update loyalty points. DB commit thành công nhưng message settlement timeout. Message được redeliver. Idempotency key ngăn cộng điểm lần hai.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate side effects sau transient outage. **Evidence** → cùng message/event ID có nhiều invocation IDs. **Hypothesis** → retry/redelivery sau ambiguous completion. **Diagnosis** → correlate trigger delivery count, logs và business rows. **Fix** → durable idempotency + atomic boundary. **Verification** → fault injection sau commit vẫn chỉ tạo một business effect.

## 7. Common mistakes

Retry mọi exception; exponential retry nhưng không jitter; gọi non-idempotent third-party API không có idempotency key; dedupe chỉ trong memory; assume Function host cung cấp exactly-once.

## 8. Alternatives

Worker Service + Service Bus có nhiều control hơn nhưng cùng delivery semantics. Durable Functions phù hợp orchestration dài nhưng không xóa nhu cầu idempotent activities. Synchronous API đơn giản hơn nếu workflow không cần asynchronous decoupling.

## 9. Trade-offs

### Advantages

Tăng resilience với transient failures và giảm manual recovery.

### Costs / Risks

Duplicate execution, retry storm, downstream load và operational complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry nghĩa là cùng work có thể chạy lại.

### Middle

Implement idempotency key, classify transient errors và observe retry count.

### Senior

Xử lý ambiguous commit/settlement, poison messages và downstream limits.

### Technical Lead / Architect

Định nghĩa delivery semantics, retry budget, DLQ/recovery ownership và side-effect contracts xuyên services.

## 11. Key takeaway

- Retry và idempotency phải được thiết kế cùng nhau.
- At-least-once delivery nghĩa là duplicate là normal condition.
- Test failure ngay sau side effect/commit, không chỉ failure trước operation.

# 7. Database migration trong CI/CD: Expand/Contract để deploy không phá phiên bản đang chạy

## 1. What is it?

Expand/Contract là migration strategy thay schema theo các bước backward-compatible: trước tiên mở rộng schema để old/new app cùng chạy, chuyển code/data, rồi mới xóa contract cũ. Mental model: trong rolling/slot deployment, nhiều application versions có thể truy cập cùng database đồng thời.

## 2. Why does it exist?

`DROP COLUMN` hoặc rename trực tiếp có thể làm instance cũ lỗi ngay cả khi deployment mới chưa hoàn tất. Database schema thường là shared compatibility boundary và rollback application không tự rollback data/schema an toàn.

## 3. How does it work?

```text
Release A: add NewColumn (nullable/default)       [expand]
Release B: app writes old + new / backfill
Release C: app reads new only
Release D: stop old writes, verify
Release E: drop OldColumn                        [contract]
```

Migration lifecycle có thể kéo qua nhiều releases thay vì một deployment.

## 4. Practical implementation

Ví dụ đổi `FullName` thành `FirstName` + `LastName` không nên rename/drop một lần. Migration đầu:

```sql
ALTER TABLE Customers ADD FirstName nvarchar(100) NULL;
ALTER TABLE Customers ADD LastName  nvarchar(100) NULL;
```

Application version tiếp theo hỗ trợ cả schema cũ/mới và backfill theo batch có telemetry trước khi contract.

## 5. Real production scenario

App Service deployment slot swap giữ old slot để rollback. Nếu migration đã drop column mà old binary vẫn query column đó, rollback trở thành không khả thi. Expand/Contract giữ compatibility window.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment health check fail ở một số instances với “Invalid column name”. **Evidence** → mixed app versions cùng DB; destructive migration chạy trước khi traffic drain. **Hypothesis** → schema không backward-compatible. **Diagnosis** → map binary version ↔ expected schema. **Fix** → restore compatibility hoặc roll forward migration/code. **Verification** → old/new binaries chạy integration tests trên expanded schema.

## 7. Common mistakes

Auto-run destructive migrations khi app startup; migration lock trên bảng lớn trong peak traffic; rollback binary nhưng không tính schema; backfill hàng triệu rows trong một transaction; không monitor duration/blocking.

## 8. Alternatives

Maintenance window phù hợp hệ nhỏ có downtime chấp nhận được. Blue-Green với database tách riêng rất phức tạp khi cần data continuity. Feature flags hỗ trợ staged code behavior nhưng không thay schema compatibility.

## 9. Trade-offs

### Advantages

Safer zero-downtime deployment, rollback window tốt hơn, giảm coupling giữa release và schema cutover.

### Costs / Risks

Nhiều releases, temporary duplication và cleanup discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu migration là production change, không chỉ generated SQL.

### Middle

Viết backward-compatible migrations và integration tests.

### Senior

Đánh giá locks, backfill, rollback và mixed-version behavior.

### Technical Lead / Architect

Định nghĩa migration governance trong CI/CD, ownership và criteria để contract schema cũ.

## 11. Key takeaway

- Application rollback không đồng nghĩa database rollback.
- Zero-downtime yêu cầu schema compatibility giữa nhiều versions.
- Destructive change nên là bước cuối sau evidence, không phải bước đầu.

# 8. .NET ThreadPool starvation: async endpoint vẫn có thể nghẽn vì blocking work

## 1. What is it?

ThreadPool starvation xảy ra khi available worker threads không đủ để chạy queued work kịp thời, thường do threads bị block lâu. Mental model: `async` chỉ giúp nếu call chain thực sự giải phóng thread trong I/O wait; `.Result`, `.Wait()` hoặc blocking I/O có thể giữ thread và phá scalability.

## 2. Why does it exist?

ASP.NET Core xử lý nhiều requests bằng một pool threads hữu hạn và điều chỉnh động. Nếu mỗi request giữ thread chờ network/lock, requests mới queue lại. ThreadPool có thể inject threads nhưng phản ứng không tức thời và quá nhiều threads gây context switching.

## 3. How does it work?

```text
100 request threads
 ├─ 80 blocked on .Result
 ├─ 20 doing work
 └─ queued continuations cannot run quickly
          ↓
       latency explodes
```

Đây là queueing problem; CPU có thể không đạt 100% nhưng latency vẫn rất cao.

## 4. Practical implementation

Sai:

```csharp
public IActionResult Get()
{
    var result = httpClient.GetStringAsync(url).Result;
    return Ok(result);
}
```

Đúng boundary:

```csharp
public async Task<IResult> GetAsync(CancellationToken ct)
{
    var result = await httpClient.GetStringAsync(url, ct);
    return Results.Ok(result);
}
```

CPU-bound work lớn không nên chỉ bọc `Task.Run` vô hạn trong request path; cần bounded concurrency/worker architecture khi phù hợp.

## 5. Real production scenario

Sau khi thêm legacy SDK synchronous vào checkout API, p99 tăng từ 400ms lên 8s dưới load trong khi CPU chỉ 45%. ThreadPool queue length và thread count tăng; downstream latency bình thường.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng mạnh, CPU không tương ứng. **Evidence** → ThreadPool queue length tăng, blocked stacks ở `.Wait`/lock, request rate vượt completion rate. **Hypothesis** → starvation. **Diagnosis** → runtime counters, traces/dumps. **Fix** → async I/O, bounded blocking isolation hoặc giảm concurrency. **Verification** → load test: queue length ổn định, p95/p99 phục hồi.

## 7. Common mistakes

Nhìn CPU thấp rồi loại trừ capacity issue; tăng min threads như permanent fix; `Task.Run` cho mọi blocking call; dùng locks quanh I/O; async controller gọi synchronous repository/client sâu bên dưới.

## 8. Alternatives

Nếu library chỉ synchronous, isolate bằng bounded worker/concurrency limit. Queue background processing cho non-interactive work. Thay client/library hỗ trợ async nếu hot path cần scale.

## 9. Trade-offs

### Advantages

Async I/O đúng giúp một số threads phục vụ nhiều concurrent operations.

### Costs / Risks

Async không làm CPU work nhanh hơn; call chain và cancellation/error handling phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt waiting I/O với CPU work và tránh `.Result/.Wait()` trong async path.

### Middle

Propagate async + cancellation end-to-end và dùng runtime metrics cơ bản.

### Senior

Chẩn đoán starvation từ counters, traces, dumps và queueing behavior.

### Technical Lead / Architect

Đặt concurrency boundary cho legacy/blocking dependencies và quyết định khi nào cần asynchronous architecture.

## 11. Key takeaway

- CPU thấp không loại trừ ThreadPool starvation.
- Async phải xuyên call chain mới giải phóng thread hiệu quả.
- Bounded concurrency thường an toàn hơn tạo thêm threads vô hạn.

# 9. Contract testing: bảo vệ integration boundary mà không dựng toàn bộ E2E environment

## 1. What is it?

Contract testing kiểm tra assumptions giữa consumer và provider tại API/message boundary: field, type, status, semantics quan trọng. Nó nằm giữa unit test và full E2E: không chứng minh toàn hệ thống chạy đúng, nhưng phát hiện breaking integration sớm hơn.

## 2. Why does it exist?

Unit tests của hai services có thể đều xanh trong khi provider đổi response làm consumer hỏng. Full E2E environment đắt, chậm và flaky nếu dùng cho mọi compatibility check.

## 3. How does it work?

```text
Consumer expectation
      ↓
contract artifact/spec
      ↓
Provider verification
      ↓
compatible? yes/no
```

Contract nên bảo vệ những gì consumer thực sự phụ thuộc, không freeze toàn bộ provider implementation.

## 4. Practical implementation

Một integration test đơn giản có thể verify OpenAPI/error contract với real test server:

```csharp
[Fact]
public async Task Missing_order_has_stable_contract()
{
    var response = await client.GetAsync("/api/orders/00000000-0000-0000-0000-000000000001");
    response.StatusCode.Should().Be(HttpStatusCode.NotFound);

    var problem = await response.Content.ReadFromJsonAsync<ProblemDetails>();
    problem!.Title.Should().Be("order_not_found");
}
```

Consumer-driven contract tooling có thể formalize cross-repository verification khi teams/services độc lập.

## 5. Real production scenario

Frontend/mobile client phụ thuộc `409 business_conflict` khi approval đã hoàn tất. Backend refactor vô tình trả `400`. Unit tests domain vẫn xanh; contract test chặn breaking behavior trước deploy.

## 6. Failure scenario & troubleshooting

**Symptom** → contract suite xanh nhưng production vẫn lỗi semantic. **Evidence** → test chỉ verify JSON shape, không verify status/error meaning. **Hypothesis** → contract quá nông. **Diagnosis** → map actual consumer assumptions. **Fix** → thêm behaviorally relevant expectations, không snapshot toàn payload. **Verification** → reproduce production break bằng contract test đỏ trước fix.

## 7. Common mistakes

Snapshot mọi field; mock provider rồi gọi đó là provider verification; contract thay thế integration/E2E tests; freeze optional fields khiến evolution khó; không version/own contract artifacts.

## 8. Alternatives

Integration tests trong provider tốt cho internal boundaries. E2E cần cho critical journeys. OpenAPI schema validation hữu ích nhưng không tự kiểm tra business semantics.

## 9. Trade-offs

### Advantages

Feedback nhanh, phát hiện compatibility break, ít infrastructure hơn E2E.

### Costs / Risks

Governance/artifact lifecycle và false confidence nếu contract không phản ánh real consumer behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu unit test không chứng minh hai services tương thích.

### Middle

Viết integration/contract tests cho status, schema và critical semantics.

### Senior

Chọn đúng boundary và tránh brittle over-specification.

### Technical Lead / Architect

Thiết kế test portfolio: unit, integration, contract, E2E theo risk và team ownership; không ép một loại test giải quyết mọi lỗi.

## 11. Key takeaway

- Contract test bảo vệ integration assumptions, không thay E2E.
- Test semantics consumer cần, không snapshot implementation noise.
- Compatibility là một phần của API architecture.

# 10. CDN `Cache-Control`: freshness, revalidation và stale response qua Akamai

## 1. What is it?

`Cache-Control` là HTTP contract mô tả response có được cache không, ở đâu và trong bao lâu. Với CDN như Akamai, mental model là nhiều cache layers: browser và shared edge có thể có freshness policy khác nhau trước khi request chạm origin.

## 2. Why does it exist?

CDN giảm latency, bandwidth và origin load bằng cách phục vụ response gần user. Nhưng cache không hiểu business freshness tự nhiên; nếu headers/purge strategy sai, user nhận stale hoặc private data bị cache không đúng boundary.

## 3. How does it work?

```text
Browser
  ↓ cache miss/revalidate
Akamai Edge
  ↓ cache miss/revalidate
Origin / ASP.NET Core
```

Ví dụ:

```http
Cache-Control: public, max-age=60, s-maxage=300
ETag: "product-42-v17"
```

Browser có thể coi fresh 60s; shared cache có thể dùng 300s. Khi stale, conditional request với `ETag` cho phép `304 Not Modified` nếu representation chưa đổi.

## 4. Practical implementation

```csharp
app.MapGet("/catalog/{slug}", async (string slug, CatalogService svc, CancellationToken ct) =>
{
    var page = await svc.GetAsync(slug, ct);
    return Results.Ok(page);
})
.WithMetadata(new ResponseCacheAttribute
{
    Duration = 60,
    Location = ResponseCacheLocation.Any
});
```

Trong production cần kiểm tra actual response headers và CDN configuration; framework metadata không tự bảo đảm Akamai policy cuối cùng.

## 5. Real production scenario

Marketing product page thay hero content. Origin đã publish version mới nhưng một edge POP vẫn phục vụ bản cũ do TTL 30 phút. Đây không phải application DB inconsistency; freshness contract nằm ở CDN layer.

## 6. Failure scenario & troubleshooting

**Symptom** → một số users thấy nội dung cũ. **Evidence** → origin response mới, edge `Age` cao/cache HIT. **Hypothesis** → TTL/purge chưa áp dụng đúng cache key. **Diagnosis** → inspect headers, cache key, POP và purge status. **Fix** → purge/version asset hoặc chỉnh policy. **Verification** → request nhiều edge locations và kiểm tra `Age`/version marker.

## 7. Common mistakes

Cache personalized response dưới `public`; dùng TTL dài nhưng không có invalidation; purge URL nhưng cache key còn query/variant khác; coi browser cache và CDN cache là một; cache HTML và hashed static assets cùng policy.

## 8. Alternatives

Browser-only cache giảm edge complexity nhưng không giảm origin load toàn cầu bằng CDN. Versioned immutable assets (`max-age` dài) phù hợp JS/CSS hash. Dynamic personalized API thường cần private/no-store hoặc carefully designed surrogate caching.

## 9. Trade-offs

### Advantages

Latency thấp, origin protection, bandwidth giảm và global scalability tốt hơn.

### Costs / Risks

Freshness/invalidation complexity, cache-key bugs và security risk nếu shared cache chứa personalized data.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser, CDN và origin là ba layers khác nhau.

### Middle

Đọc `Cache-Control`, `Age`, `ETag` và debug HIT/MISS.

### Senior

Thiết kế cache key, TTL, purge và personalized-content boundaries; đo origin offload và stale risk.

### Technical Lead / Architect

Phân loại content theo freshness/security requirements và quyết định CDN strategy; không cache chỉ vì “performance tốt hơn”.

## 11. Key takeaway

- CDN cache là consistency trade-off giữa latency và freshness.
- `Cache-Control` là contract; CDN configuration và cache key quyết định behavior thực tế.
- Personalized data cần shared-cache boundary đặc biệt cẩn thận.
