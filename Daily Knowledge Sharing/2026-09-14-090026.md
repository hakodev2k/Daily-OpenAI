# 1. .NET Large Object Heap và GC pressure: buffer lớn có thể làm latency xấu đi dù allocation rate không quá cao

## 1. What is it?

Mental model:

```text
small allocations
   -> Gen 0 -> Gen 1 -> Gen 2

large allocations (thường >= ~85 KB)
   -> Large Object Heap (LOH)
```

LOH là vùng heap dành cho các object lớn. Trong thực tế, các `byte[]`, `char[]`, image buffers, serialization buffers hoặc payload lớn rất dễ đi vào LOH.

Điểm cần nhớ: object lớn không chỉ tốn memory; nó ảnh hưởng GC behavior, fragmentation và tail latency.

## 2. Why does it exist?

Di chuyển object rất lớn trong mỗi compacting GC có chi phí đáng kể. Vì vậy runtime xử lý large objects khác small objects.

Nếu application liên tục allocate rồi bỏ các buffer vài trăm KB hoặc vài MB, hệ thống có thể tạo nhiều khoảng trống khó tái sử dụng hiệu quả. Memory footprint tăng dù tổng live data không lớn.

## 3. How does it work?

Một allocation lớn thường đi thẳng vào LOH và được thu gom cùng Gen 2 collection.

```text
request -> allocate 2 MB byte[]
request ends -> object unreachable
             -> chưa chắc được reclaim ngay
             -> chờ Gen 2 GC
```

Gen 2 GC thường đắt hơn Gen 0/Gen 1. Nếu traffic tạo nhiều large transient buffers, p99 latency có thể xuất hiện spikes liên quan full GC.

LOH có thể compact trong một số tình huống/configuration, nhưng không nên coi compaction là cách chữa workload allocation kém.

## 4. Practical implementation

Thay vì mỗi request tạo một buffer lớn:

```csharp
var buffer = new byte[1024 * 1024];
```

có thể dùng `ArrayPool<byte>` khi lifetime rõ ràng:

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(1024 * 1024);
try
{
    // use buffer
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
}
```

Nếu có thể, streaming còn tốt hơn materialize toàn payload:

```csharp
await source.CopyToAsync(destination, ct);
```

## 5. Real production scenario

Một API export báo cáo tạo file lớn bằng `MemoryStream`, sau đó gọi `ToArray()`. Với mỗi request, hệ thống giữ cả internal buffer và bản copy cuối cùng.

Ở traffic thấp, endpoint vẫn nhanh. Khi nhiều exports chạy đồng thời, memory tăng đột biến và full GC xuất hiện. CPU không nhất thiết đạt 100%, nhưng p99 của toàn service tăng vì GC pause.

## 6. Failure scenario & troubleshooting

**Symptom** → memory sawtooth lớn, Gen 2 GC tăng, latency spikes theo chu kỳ.

**Evidence** → allocation profiler cho thấy nhiều `byte[]`/`char[]` lớn; GC counters cho thấy LOH size và Gen 2 collections tăng.

**Hypothesis** → large transient allocations đang tạo GC pressure.

**Diagnosis** → dùng `dotnet-counters`, `dotnet-gcdump`, profiler; xác định allocation call sites và object lifetime.

**Fix** → stream dữ liệu, reuse buffers, tránh duplicate copies, giới hạn concurrency cho workload memory-heavy.

**Verification** → load test cùng payload size thật; so sánh LOH size, Gen 2 frequency, allocated bytes/sec và p95/p99.

## 7. Common mistakes

- Chỉ nhìn total memory mà không nhìn allocation profile.
- Thấy LOH rồi bật compaction như fix mặc định.
- Pool buffer nhưng quên clear dữ liệu nhạy cảm.
- Dùng `ToArray()` vô thức tạo thêm bản copy lớn.
- Cho phép quá nhiều large-file operations chạy concurrent.
- Tối ưu small allocations trong khi vài large buffers mới là bottleneck.

## 8. Alternatives

- Streaming: tốt nhất khi không cần toàn dữ liệu cùng lúc.
- `ArrayPool<T>`: phù hợp temporary reusable buffers.
- Chunking: xử lý dữ liệu theo blocks nhỏ.
- External object storage: tránh giữ payload lớn trong process nếu workflow cho phép.

## 9. Trade-offs

### Advantages

- Giảm large allocations có thể giảm Gen 2 pressure và tail latency.
- Streaming giữ memory gần với chunk size thay vì payload size.

### Costs / Risks

- Buffer pooling tăng complexity ownership.
- Streaming làm code/error handling phức tạp hơn.
- Concurrency control có thể giảm peak throughput nhưng tăng stability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu allocation lớn có behavior khác allocation nhỏ và GC không phải “free memory ngay lập tức”.

### Middle

Biết tìm large buffers, tránh copy thừa và dùng streaming/pooling đúng lifetime.

### Senior

Liên hệ LOH, Gen 2 GC, concurrency và p99 latency; đo trước/sau bằng runtime telemetry.

### Technical Lead / Architect

Thiết kế memory budget cho export/upload/serialization workloads và quyết định khi nào phải chuyển sang streaming hoặc asynchronous processing.

## 11. Key takeaway

- Large transient allocations có thể gây tail-latency spikes dù average memory nhìn vẫn chấp nhận được.
- Ưu tiên giảm copy và streaming trước khi tinh chỉnh GC.
- Memory-heavy endpoints cần concurrency budget giống database/network dependencies.

# 2. ASP.NET Core rate limiting: giới hạn theo đúng identity/resource thay vì chỉ chặn theo IP

## 1. What is it?

Rate limiting là cơ chế kiểm soát lượng request được chấp nhận trong một khoảng thời gian hoặc theo số concurrent operations.

Mental model:

```text
request
  |
identify partition
  |-- user/account/API key/tenant/IP
  |
rate-limit policy
  |
allow or 429
```

Điểm quan trọng là chọn đúng partition key. IP chỉ là một tín hiệu, không phải universal identity.

## 2. Why does it exist?

Nếu một client có thể tạo traffic vô hạn, một endpoint đắt tiền có thể làm cạn ThreadPool, DB connections, downstream quota hoặc compute budget.

Rate limiting bảo vệ capacity boundary, fairness và đôi khi cả cost.

## 3. How does it work?

ASP.NET Core có rate-limiting middleware với fixed window, sliding window, token bucket và concurrency limiter.

Một policy có thể partition theo authenticated user:

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("per-user", context =>
    {
        var userId = context.User.FindFirst("sub")?.Value
                     ?? context.Connection.RemoteIpAddress?.ToString()
                     ?? "anonymous";

        return RateLimitPartition.GetFixedWindowLimiter(
            userId,
            _ => new FixedWindowRateLimiterOptions
            {
                PermitLimit = 100,
                Window = TimeSpan.FromMinutes(1),
                QueueLimit = 0
            });
    });
});
```

## 4. Practical implementation

```csharp
app.UseRateLimiter();

app.MapPost("/reports/generate", GenerateReport)
   .RequireRateLimiting("per-user");
```

Với endpoint đắt, concurrency limiter đôi khi phản ánh resource pressure tốt hơn request/minute:

```text
max 5 concurrent report generations per tenant
```

## 5. Real production scenario

Một SaaS API giới hạn theo IP. Nhiều customers đi qua cùng corporate NAT nên vô tình share một public IP và cùng bị 429.

Ngược lại, attacker dùng botnet có nhiều IP nên IP-based limit không đủ bảo vệ expensive endpoint.

Partition theo tenant/user/API key giúp align rate limit với business ownership hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → khách hàng hợp lệ bị 429 hàng loạt hoặc backend vẫn overload dù đã bật rate limiting.

**Evidence** → nhiều users share cùng IP; hoặc mỗi request dùng IP khác nhưng cùng account/tenant.

**Hypothesis** → partition key không tương ứng resource ownership.

**Diagnosis** → correlate 429s với user/tenant/IP và downstream utilization.

**Fix** → partition theo authenticated identity/resource; thêm global/concurrency guardrail cho shared dependencies.

**Verification** → load test nhiều tenants, shared NAT và abusive client patterns.

## 7. Common mistakes

- Chỉ rate limit theo IP.
- Dùng cùng limit cho cheap GET và expensive export.
- Queue quá nhiều requests thay vì reject sớm.
- Không trả `Retry-After` khi contract phù hợp.
- Rate limit ở app nhưng bỏ qua upstream gateway/CDN controls.
- Coi rate limiting là thay thế authorization hoặc abuse detection.

## 8. Alternatives

- API Gateway/WAF rate limiting cho edge protection.
- Concurrency limiting cho expensive operations.
- Quota theo ngày/tháng cho commercial usage.
- Queue/background processing cho long-running workloads.

## 9. Trade-offs

### Advantages

- Bảo vệ shared resources và fairness.
- Giảm blast radius khi client lỗi hoặc abusive.

### Costs / Risks

- Sai partition làm block người dùng hợp lệ.
- Distributed rate limiting cần shared state hoặc edge component.
- Limit quá thấp ảnh hưởng UX và throughput.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `429 Too Many Requests` là capacity/fairness control.

### Middle

Implement middleware và policy theo user/tenant/IP.

### Senior

Chọn algorithm, partition key và concurrency controls theo dependency bottleneck.

### Technical Lead / Architect

Định nghĩa rate-limit hierarchy giữa CDN/gateway/app/downstream và mapping với product quota/cost.

## 11. Key takeaway

- Rate limiting chỉ tốt khi partition key phản ánh đúng consumer/resource.
- Request rate và concurrency là hai pressure khác nhau.
- Rate limits nên bảo vệ dependency thật, không chỉ “có middleware cho đủ”.

# 3. EF Core compiled queries: giảm query-compilation overhead nhưng chỉ đáng dùng ở hot path đã đo được

## 1. What is it?

Compiled query cho phép EF Core reuse một query delegate đã compile thay vì lặp lại một phần query-compilation work cho mỗi invocation.

Mental model:

```text
LINQ expression
   -> parse/normalize/translate/cache lookup
   -> SQL

compiled query
   -> precompiled delegate
   -> execute with parameters
```

EF Core bản thân đã cache query plans theo shape, nên compiled query là optimization nâng cao chứ không phải default.

## 2. Why does it exist?

Trong hot path cực nhiều calls với query shape ổn định, overhead CPU nhỏ của expression processing/cache lookup có thể tích lũy đáng kể.

Nhưng nếu database round trip mất 20 ms, tiết kiệm vài microseconds ở client gần như không quan trọng.

## 3. How does it work?

```csharp
private static readonly Func<AppDbContext, int, Product?>
    FindProduct = EF.CompileQuery(
        (AppDbContext db, int id) =>
            db.Products.AsNoTracking().SingleOrDefault(x => x.Id == id));
```

Caller:

```csharp
var product = FindProduct(db, id);
```

Async variant:

```csharp
private static readonly Func<AppDbContext, int, IAsyncEnumerable<Product>>
    FindByCategory = EF.CompileAsyncQuery(
        (AppDbContext db, int categoryId) =>
            db.Products
              .AsNoTracking()
              .Where(x => x.CategoryId == categoryId));
```

## 4. Practical implementation

Chỉ áp dụng khi benchmark cho thấy query compilation overhead đáng kể.

Checklist:

```text
1. query chạy rất thường xuyên?
2. DB latency đã thấp?
3. query shape ổn định?
4. allocation/CPU phía app là bottleneck?
5. benchmark production-like workload xác nhận lợi ích?
```

## 5. Real production scenario

Một lookup service gọi cùng query hàng trăm nghìn lần/phút vào local read replica rất nhanh. DB latency ~1 ms nên app-side overhead trở nên đáng kể hơn.

Team benchmark compiled query và thấy CPU giảm đủ để justify complexity. Các queries thông thường khác vẫn giữ LINQ bình thường.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries khắp nơi nhưng latency gần như không đổi, code lại khó maintain hơn.

**Evidence** → tracing cho thấy phần lớn thời gian nằm ở DB I/O, không phải query compilation.

**Hypothesis** → optimization nhắm sai bottleneck.

**Diagnosis** → đo query latency, CPU, allocations, DB duration và call frequency.

**Fix** → bỏ compiled-query complexity nếu không có measurable gain; ưu tiên projection/index/round-trip reduction.

**Verification** → BenchmarkDotNet hoặc load test với representative DB/network conditions.

## 7. Common mistakes

- Nghĩ compiled query giống database compiled plan hoàn toàn.
- Dùng nó trước khi sửa N+1 hoặc over-fetching.
- Tạo delegate động theo mọi query variation.
- Benchmark in-memory provider rồi suy luận production gain.
- Hy sinh readability cho micro-optimization không đo được.

## 8. Alternatives

- EF Core normal query caching: default phù hợp phần lớn trường hợp.
- Raw SQL/Dapper: khi cần tighter SQL/control và đã chấp nhận abstraction trade-off.
- Database tuning: thường có impact lớn hơn query-compilation optimization.

## 9. Trade-offs

### Advantages

- Giảm một phần CPU/allocation overhead ở extremely hot query paths.
- Query shape cố định dễ benchmark.

### Costs / Risks

- Tăng code ceremony.
- Dễ premature optimization.
- Không giải quyết slow SQL, network latency hoặc bad indexes.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu EF phải translate LINQ trước khi DB thực thi SQL.

### Middle

Biết projection, `AsNoTracking` và query shape quan trọng hơn compiled-query optimization trong phần lớn cases.

### Senior

Benchmark app-side query overhead và biết khi compiled queries thực sự có value.

### Technical Lead / Architect

Ngăn micro-optimization trở thành codebase convention khi bottleneck chưa được chứng minh.

## 11. Key takeaway

- EF Core đã cache query shapes; compiled queries là optimization chuyên biệt.
- Chỉ dùng ở hot path có evidence.
- Đừng tối ưu query-compilation overhead trước round trips, SQL và indexes.

# 4. SQL Server deadlocks: đọc deadlock graph để sửa lock ordering và transaction boundary thay vì chỉ retry

## 1. What is it?

Deadlock xảy ra khi hai hoặc nhiều transactions giữ locks mà transaction khác cần và tạo vòng chờ.

Mental model:

```text
Tx A holds Row 1 -> waits Row 2
Tx B holds Row 2 -> waits Row 1

cycle detected
-> SQL Server chọn deadlock victim
-> rollback một transaction
```

Deadlock khác blocking thông thường: blocking có thể chờ rồi tiếp tục; deadlock tạo cycle không tự giải quyết.

## 2. Why does it exist?

Transactional consistency cần locks. Khi concurrent transactions truy cập resources theo thứ tự khác nhau, vòng chờ có thể hình thành.

Database phải chọn một victim để phá cycle.

## 3. How does it work?

Ví dụ:

Transaction A:

```sql
UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1;
UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 2;
```

Transaction B chạy ngược thứ tự:

```sql
UPDATE Accounts SET Balance = Balance - 50 WHERE Id = 2;
UPDATE Accounts SET Balance = Balance + 50 WHERE Id = 1;
```

Nếu timing trùng nhau, mỗi transaction có thể giữ một lock và chờ lock còn lại.

## 4. Practical implementation

Fix thường bắt đầu bằng consistency của access order:

```text
always lock lower AccountId first
then higher AccountId
```

Ngoài ra giảm transaction duration:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

// only database work that must be atomic
await ApplyChangesAsync(ct);
await db.SaveChangesAsync(ct);

await tx.CommitAsync(ct);
```

Không gọi external HTTP API bên trong transaction nếu không thật sự cần.

## 5. Real production scenario

Một approval workflow update `Request` rồi `EmployeeBalance`; một background reconciliation job update `EmployeeBalance` rồi `Request`.

Hai code paths đúng khi chạy riêng nhưng lock resources theo thứ tự ngược nhau. Production peak tạo deadlocks mà test đơn luồng không bao giờ thấy.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL error 1205 xuất hiện ngẫu nhiên dưới concurrency.

**Evidence** → deadlock graph cho thấy hai statements, resources, lock modes và victim.

**Hypothesis** → inconsistent lock ordering hoặc transaction quá rộng.

**Diagnosis** → capture Extended Events/deadlock XML; đọc resource list/process list; map statements về application call paths.

**Fix** → align lock order, giảm transaction scope, cải thiện access path/index nếu scans giữ locks rộng, và chỉ sau đó áp controlled retry cho transient deadlock victims.

**Verification** → concurrency test tái tạo access pattern và xác nhận deadlock rate về gần zero.

## 7. Common mistakes

- Chỉ thêm retry vô hạn.
- Tăng command timeout để “fix” deadlock.
- Không đọc deadlock graph.
- Giữ transaction qua network call.
- Update cùng tables theo thứ tự khác nhau ở nhiều workflows.
- Nghĩ isolation thấp hơn luôn giải quyết được deadlocks.

## 8. Alternatives

- Optimistic concurrency cho business conflicts không cần lock dài.
- Queue serialization cho một số hot aggregate keys.
- Snapshot-based isolation có thể giảm reader/writer blocking nhưng không loại mọi writer/writer deadlock.

## 9. Trade-offs

### Advantages

- Locking bảo vệ transactional correctness.
- Deadlock detection cho phép database recover thay vì treo vô hạn.

### Costs / Risks

- Retry tăng duplicate-side-effect risk nếu transaction boundary với external systems không rõ.
- Over-serialization giảm throughput.
- Query/index thay đổi có thể đổi lock footprint.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt blocking và deadlock.

### Middle

Biết transaction scope và consistent update order.

### Senior

Đọc deadlock graph, map về code path và phân tích lock footprint.

### Technical Lead / Architect

Thiết kế transaction boundaries/workflow ownership để concurrency behavior predictable thay vì phụ thuộc retries.

## 11. Key takeaway

- Deadlock là cycle của lock dependencies, không phải “query chạy chậm”.
- Deadlock graph là bằng chứng chính để chẩn đoán.
- Retry chỉ là safety net; root fix thường nằm ở lock order, transaction scope hoặc access path.

# 5. Redis eviction & memory pressure: cache đầy không chỉ là vấn đề dung lượng mà còn là correctness và latency

## 1. What is it?

Redis giữ dữ liệu trong memory. Khi đạt `maxmemory`, eviction policy quyết định key nào bị loại hoặc write có bị reject hay không.

Mental model:

```text
used memory -> maxmemory
      |
      +-> noeviction -> write fails
      +-> LRU/LFU/random/TTL-based eviction
```

Eviction là runtime behavior có thể thay đổi cache hit ratio và load lên origin database.

## 2. Why does it exist?

Memory là hữu hạn. Cache phải có policy khi dataset lớn hơn capacity.

Nếu không hiểu eviction, team có thể nghĩ “Redis tự xóa cache cũ” nhưng thực tế có thể xóa hot key, reject writes hoặc đẩy traffic trở lại DB.

## 3. How does it work?

Ví dụ `allkeys-lfu` ưu tiên giữ keys truy cập thường xuyên hơn, trong khi `volatile-*` chỉ xét keys có TTL.

Điểm thiết kế quan trọng:

```text
cache keys + TTL policy + maxmemory + eviction policy
                  |
                  v
             hit ratio
                  |
                  v
             DB traffic
```

## 4. Practical implementation

Application cần chịu được cache miss:

```csharp
var cached = await cache.GetStringAsync(key, ct);
if (cached is not null)
    return Deserialize(cached);

var value = await repository.LoadAsync(id, ct);
await cache.SetStringAsync(
    key,
    Serialize(value),
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
    },
    ct);

return value;
```

Nếu Redis là pure cache, DB vẫn phải là source of truth.

## 5. Real production scenario

Một e-commerce site thêm hàng triệu personalized cache keys nhưng không resize Redis. Evictions tăng liên tục. Hit ratio giảm từ 95% xuống 60%, database QPS tăng hơn gấp nhiều lần và chính DB trở thành bottleneck.

Incident nhìn ban đầu giống “SQL chậm”, nhưng root cause là cache capacity/eviction.

## 6. Failure scenario & troubleshooting

**Symptom** → DB load tăng đột ngột, application latency tăng, Redis vẫn “up”.

**Evidence** → `evicted_keys` tăng, hit ratio giảm, used memory sát maxmemory.

**Hypothesis** → Redis memory pressure đang biến cache thành churn machine.

**Diagnosis** → inspect memory usage by key pattern, TTL distribution, eviction policy và hot-key frequency.

**Fix** → loại cache value ít giá trị, giảm payload, sửa TTL/key design, chọn eviction policy phù hợp hoặc resize nếu economics hợp lý.

**Verification** → hit ratio ổn định và origin QPS trở lại expected baseline dưới load.

## 7. Common mistakes

- Theo dõi uptime Redis nhưng không theo dõi evictions/hit ratio.
- Cache mọi response “cho nhanh”.
- Không đặt TTL với volatile-only eviction policy rồi ngạc nhiên khi behavior khác mong đợi.
- Giữ payload rất lớn cho low-value keys.
- Dùng Redis như source of truth nhưng vẫn cho eviction.
- Scale memory trước khi hiểu key cardinality.

## 8. Alternatives

- `IMemoryCache` cho instance-local, non-shared data.
- CDN/browser cache cho HTTP/static content.
- Database/materialized read model nếu data cần durability/querying mạnh.
- Không cache khi query đủ rẻ và invalidation quá phức tạp.

## 9. Trade-offs

### Advantages

- Eviction cho phép Redis tiếp tục hoạt động trong finite memory budget.
- Policy phù hợp có thể giữ high-value hot data.

### Costs / Risks

- Evictions chuyển load xuống dependencies.
- Hit ratio có thể tụt nhanh dưới key explosion.
- Cache correctness/lifecycle trở nên khó quan sát nếu key ownership kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Redis memory hữu hạn và cache miss là expected behavior.

### Middle

Biết TTL, `maxmemory`, eviction policy và cache-aside fallback.

### Senior

Theo dõi hit ratio/evicted keys/key cardinality và liên hệ chúng với DB load.

### Technical Lead / Architect

Đặt cache budget, ownership và failure policy; quyết định dữ liệu nào không nên vào Redis.

## 11. Key takeaway

- Redis “healthy” không có nghĩa cache đang hiệu quả.
- Eviction rate và hit ratio phải được correlate với origin load.
- Capacity planning bắt đầu từ key/value economics, không chỉ tăng RAM.

# 6. Modular Monolith boundaries: tách module theo business capability mà không trả operational cost của microservices quá sớm

## 1. What is it?

Modular Monolith là một application deployable unit duy nhất nhưng bên trong có các module với boundaries rõ ràng.

Mental model:

```text
Single deployable process

+-------------------------------+
| Orders | Catalog | Identity   |
|-------- module boundaries ----|
| shared technical platform     |
+-------------------------------+
```

Module boundary phải thể hiện business ownership và dependency rules, không chỉ namespace/folder.

## 2. Why does it exist?

Monolith không modular dễ thành tightly coupled codebase. Microservices tách deployment nhưng kéo theo network failure, distributed tracing, deployment orchestration, eventual consistency và platform overhead.

Modular Monolith cố lấy phần lớn code-boundary benefits trước khi trả distributed-systems cost.

## 3. How does it work?

Mỗi module nên sở hữu application/domain logic và expose contract có chủ đích.

Ví dụ:

```text
Orders
  Application
  Domain
  Infrastructure
  Contracts

Catalog
  Application
  Domain
  Infrastructure
  Contracts
```

Orders không nên query trực tiếp internal tables của Catalog chỉ vì cùng database.

## 4. Practical implementation

Có thể enforce dependency bằng project boundaries:

```text
MyApp.Orders
MyApp.Catalog
MyApp.SharedKernel
MyApp.Host
```

`Host` composition root wire modules; module public API giữ nhỏ.

Nếu cần communication trong process, direct interface call thường đơn giản hơn internal message bus trừ khi decoupling semantics thực sự cần.

## 5. Real production scenario

Một commerce platform bắt đầu bằng API duy nhất. Team tách Orders, Catalog và Promotions thành modules nhưng deploy chung.

Sau này Catalog cần scale/deploy độc lập. Vì data ownership và contract boundary đã rõ, extraction sang service ít đau hơn so với codebase nơi mọi module đọc tables của nhau.

## 6. Failure scenario & troubleshooting

**Symptom** → gọi là modular monolith nhưng một feature change phải sửa 8 modules và join trực tiếp tables khắp nơi.

**Evidence** → cyclic project references, shared entities, cross-module DbSet access.

**Hypothesis** → boundaries là folder-level chứ không phải dependency/data boundary.

**Diagnosis** → map module dependencies và ownership của tables/contracts.

**Fix** → define public contracts, move invariants vào owner module, giảm shared mutable model.

**Verification** → module tests/build rules chứng minh internal types không bị consumers truy cập trực tiếp.

## 7. Common mistakes

- Tạo 40 projects nhưng vẫn share toàn domain model.
- Dùng MediatR chỉ để làm mọi call khó trace hơn.
- Cho modules update cùng tables.
- Gọi mọi module là bounded context mà không có business rationale.
- Chuyển sang microservices chỉ vì codebase lớn.

## 8. Alternatives

- Simple layered monolith: tốt nếu domain nhỏ và coupling vẫn manageable.
- Microservices: khi independent scaling/deployment/ownership đủ mạnh để justify operational cost.
- Plugin/module architecture: khi cần runtime extensibility khác business boundaries.

## 9. Trade-offs

### Advantages

- Transaction và deployment đơn giản hơn microservices.
- Boundary discipline giúp change isolation.
- Có đường tiến hóa sang services nếu thực sự cần.

### Costs / Risks

- Boundary enforcement cần tooling/review discipline.
- Shared database dễ tạo shortcut coupling.
- Không có independent scaling/deployment theo module.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là responsibility boundary, không chỉ folder.

### Middle

Implement module contracts và tránh internal cross-access.

### Senior

Thiết kế data ownership, dependency direction và cross-module workflows.

### Technical Lead / Architect

Quyết định khi monolith vẫn đủ và criteria nào thực sự justify service extraction.

## 11. Key takeaway

- Modular Monolith là boundary strategy, không phải project-count strategy.
- Shared process/database không cho phép bỏ qua ownership.
- Microservices chỉ nên xuất hiện khi independent operation có giá trị đủ lớn.

# 7. Azure Functions concurrency & scale-out: tăng instance không đồng nghĩa tăng throughput an toàn cho mọi dependency

## 1. What is it?

Azure Functions có thể xử lý nhiều invocations đồng thời và scale ra nhiều instances tùy trigger/plan/configuration.

Mental model:

```text
queue backlog
   |
Functions scale controller
   |
+-- instance A -> concurrency N
+-- instance B -> concurrency N
+-- instance C -> concurrency N
   |
   v
shared SQL / API / Service Bus dependency
```

Total concurrency = concurrency per instance × number of instances.

## 2. Why does it exist?

Serverless scale giúp hấp thụ variable workload. Nhưng downstream systems không tự scale cùng tốc độ.

Nếu Functions scale từ 2 lên 50 instances, SQL/API dependency có thể nhận load tăng 25x.

## 3. How does it work?

Trigger type ảnh hưởng concurrency. Queue/message triggers có prefetch/batch/concurrency settings; HTTP functions phụ thuộc hosting plan/runtime behavior.

Scale-out tối ưu function compute, không đảm bảo end-to-end capacity.

## 4. Practical implementation

Consumer cần bounded parallelism và idempotency:

```csharp
public async Task Run(
    ServiceBusReceivedMessage message,
    CancellationToken ct)
{
    var orderId = message.ApplicationProperties["orderId"]?.ToString();

    if (await _inbox.AlreadyProcessedAsync(message.MessageId, ct))
        return;

    await _processor.ProcessAsync(orderId!, ct);
    await _inbox.MarkProcessedAsync(message.MessageId, ct);
}
```

Hosting configuration phải align với downstream connection/quota budgets.

## 5. Real production scenario

Một queue backlog tăng sau downstream outage. Khi dependency phục hồi, Functions scale mạnh để drain backlog. SQL connection pool và third-party API quota bị saturation, tạo timeout/retry và backlog lại tăng.

Autoscaling đã biến recovery thành retry storm.

## 6. Failure scenario & troubleshooting

**Symptom** → số Functions instances tăng nhưng throughput plateau hoặc giảm; downstream 429/timeout tăng.

**Evidence** → dependency latency, DB connections hoặc API quota saturation correlate với scale-out.

**Hypothesis** → bottleneck nằm ngoài Functions compute.

**Diagnosis** → trace invocation concurrency, instance count, dependency metrics và retry rate.

**Fix** → cap concurrency, tune batch/prefetch, introduce queue buffering, increase dependency capacity khi justified, implement backoff/idempotency.

**Verification** → backlog recovery test chứng minh throughput tăng mà error/retry rate vẫn bounded.

## 7. Common mistakes

- Nghĩ serverless = infinite scale.
- Tăng concurrency để chữa backlog mà không đo dependency.
- Retry ngay lập tức khi dependency đang overloaded.
- Không idempotent consumer.
- Không monitor queue age/backlog và downstream saturation cùng nhau.

## 8. Alternatives

- Worker Service/Container Apps khi cần concurrency control và predictable long-running process.
- App Service background worker cho tightly coupled workloads nhỏ.
- Kubernetes khi orchestration/control requirements thực sự justify complexity.

## 9. Trade-offs

### Advantages

- Scale theo workload, operational overhead compute thấp.
- Trigger integrations tiện lợi.

### Costs / Risks

- Scale behavior có thể khuếch đại load vào dependency.
- Cold start/plan limits tùy workload.
- Concurrency và retries cần hiểu rõ để tránh duplicate/storm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu nhiều instances nghĩa là nhiều concurrent invocations hơn.

### Middle

Biết tune trigger concurrency và propagate cancellation/idempotency.

### Senior

Capacity-plan end-to-end, correlate scale với dependency saturation.

### Technical Lead / Architect

Đặt maximum safe throughput dựa trên toàn dependency chain, không dựa riêng Functions capacity.

## 11. Key takeaway

- Autoscale chỉ giải quyết compute bottleneck của Function.
- Downstream capacity mới quyết định safe throughput.
- Recovery path cần backpressure, idempotency và bounded retry.

# 8. OpenTelemetry distributed tracing: correlation end-to-end để tìm latency bị mất ở đâu trong hệ thống phân tán

## 1. What is it?

Distributed tracing ghi lại một request xuyên nhiều components bằng trace/span relationships.

Mental model:

```text
Trace: checkout request

API span
 ├─ SQL span
 ├─ Redis span
 └─ HTTP inventory span
       └─ inventory SQL span
```

Mỗi span có timing, attributes, status và parent/child context.

## 2. Why does it exist?

Trong distributed system, “API mất 2 giây” không cho biết 2 giây nằm ở API code, database, DNS, downstream service hay queue.

Logs riêng lẻ khó reconstruct timing và causal chain nếu correlation yếu.

## 3. How does it work?

OpenTelemetry instrumentation tạo spans và truyền trace context qua HTTP/messaging headers.

ASP.NET Core + HttpClient + database instrumentation có thể tạo phần lớn trace tự động.

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddSource("MyApp"));
```

Custom spans cho business operation:

```csharp
using var activity = ActivitySource.StartActivity("price.calculate");
activity?.SetTag("tenant.id", tenantId);
```

Không đưa PII/high-cardinality secrets vào tags.

## 4. Practical implementation

Một trace tốt nên trả lời:

```text
request mất bao lâu?
span nào chiếm thời gian?
dependency nào fail?
retry xảy ra mấy lần?
trace có đi qua service boundary đúng không?
```

Sampling cần được thiết kế để chi phí telemetry không tăng vô hạn.

## 5. Real production scenario

Checkout p95 tăng từ 600 ms lên 2.5 s. Application logs không có lỗi. Trace cho thấy inventory HTTP call mất 1.6 s, trong đó DNS/connect/TLS chiếm đáng kể sau deployment networking change.

Không có trace, team có thể tối ưu SQL sai chỗ.

## 6. Failure scenario & troubleshooting

**Symptom** → trace bị đứt giữa API A và API B hoặc message consumer tạo trace mới không liên quan producer.

**Evidence** → trace IDs khác nhau, missing propagation headers/context.

**Hypothesis** → instrumentation/custom client/message pipeline không propagate context.

**Diagnosis** → inspect HTTP/message headers, instrumentation registration và custom libraries.

**Fix** → propagate standard context, instrument custom boundaries và chuẩn hóa telemetry attributes.

**Verification** → synthetic request phải tạo một continuous trace xuyên expected services.

## 7. Common mistakes

- Log correlation ID nhưng không có span timings.
- Gắn user email/token vào span attributes.
- Instrument mọi function nhỏ tạo trace noise.
- Không sample strategy.
- Chỉ xem traces khi incident nhưng không có dependency metrics.
- Dùng custom correlation format thay chuẩn nếu không cần.

## 8. Alternatives

- Structured logs: tốt cho discrete events/detail.
- Metrics: tốt cho aggregation/trends/alerts.
- Application Insights proprietary instrumentation: vẫn hữu ích, nhưng OpenTelemetry tạo vendor-neutral instrumentation model.

Ba loại telemetry bổ sung nhau, không thay thế nhau.

## 9. Trade-offs

### Advantages

- Cho end-to-end causal/timing view.
- Giảm guesswork khi latency/failure lan qua services.

### Costs / Risks

- Telemetry volume/cost có thể lớn.
- Sampling có thể bỏ mất trace hiếm.
- High-cardinality attributes làm backend analytics đắt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace gồm spans và parent-child relationships.

### Middle

Biết instrument ASP.NET Core/HttpClient và đọc critical path.

### Senior

Thiết kế propagation, custom spans, sampling và privacy-safe attributes.

### Technical Lead / Architect

Chuẩn hóa observability semantic conventions, retention/cost và correlation across HTTP/messaging boundaries.

## 11. Key takeaway

- Tracing trả lời “thời gian biến mất ở đâu” tốt hơn logs đơn lẻ.
- Context propagation phải xuyên mọi service/message boundary.
- Logs, metrics và traces cần được dùng cùng nhau.

# 9. IIS Application Pool recycling: process restart có thể là hành vi platform bình thường nhưng vẫn phá request/background work nếu app không sẵn sàng

## 1. What is it?

IIS Application Pool chứa worker process (`w3wp.exe`) chạy application. Recycling tạo worker process mới theo policy/configuration hoặc khi xảy ra một số lifecycle events.

Mental model:

```text
IIS App Pool
   |
   +-> w3wp old process
   |
   +-> recycle
   |
   +-> w3wp new process
```

Application không nên giả định process sẽ sống mãi.

## 2. Why does it exist?

Recycling hỗ trợ process lifecycle management, configuration changes, scheduled recycling và recovery. Nhưng in-process memory/state/background work có thể mất khi process dừng.

## 3. How does it work?

Tùy cấu hình, IIS có thể overlap old/new worker trong recycle. Nhưng request draining và application shutdown vẫn có giới hạn thời gian.

Nếu app giữ session/in-memory cache/job state chỉ trong process, recycle có thể làm mất state đó.

## 4. Practical implementation

ASP.NET Core app nên xử lý shutdown signal thông qua host lifetime/CancellationToken.

Background work:

```csharp
public sealed class Worker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await DoOneUnitAsync(stoppingToken);
        }
    }
}
```

Critical jobs nên có durable checkpoint/idempotency thay vì giả định worker hoàn thành trước recycle.

## 5. Real production scenario

Legacy enterprise site chạy nightly job bên trong web app bằng timer. App Pool recycle lúc 2 AM trùng job. Process cũ dừng giữa batch, không có checkpoint; sáng hôm sau dữ liệu chỉ xử lý một phần.

Root issue không phải IIS “random restart”, mà job durability đặt sai boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → app “tự restart”, user session mất hoặc job dừng giữa chừng.

**Evidence** → IIS event logs/App Pool recycle logs trùng thời điểm; process ID thay đổi.

**Hypothesis** → lifecycle event/recycle làm mất in-process state/work.

**Diagnosis** → inspect recycle settings, idle timeout, config/deployment events, Windows Event Viewer và application startup/shutdown logs.

**Fix** → externalize durable state, dùng distributed session/cache nếu cần, move critical scheduled work sang Worker/Functions/queue system phù hợp.

**Verification** → trigger controlled recycle và xác nhận requests drain, app warm-up, jobs resume/reprocess an toàn.

## 7. Common mistakes

- Lưu critical state trong static variables.
- Chạy durable scheduler trong web process mà không persistence.
- Tắt recycle hoàn toàn để che bug.
- Không log startup/shutdown/process ID.
- Không test recycle/deployment behavior.
- Nhầm App Pool recycle với machine reboot hoặc application crash.

## 8. Alternatives

- Windows Service/Worker Service cho long-running background work.
- Azure Functions/queue consumers cho event-driven jobs.
- App Service với external durable job architecture khi migrate cloud.

## 9. Trade-offs

### Advantages

- IIS process lifecycle management hỗ trợ recovery/operations.
- Overlapped recycle có thể giảm downtime.

### Costs / Risks

- In-memory state không durable.
- Warm-up/startup dependency có thể tạo brief errors nếu readiness kém.
- Background jobs trong web host bị coupling với web lifecycle.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu web process có thể restart bất kỳ lúc nào.

### Middle

Biết xem IIS logs/settings và tránh critical in-memory state.

### Senior

Thiết kế graceful shutdown, durable jobs và reproduce recycle-related failures.

### Technical Lead / Architect

Quyết định workload nào thuộc web process và workload nào phải tách thành durable execution component.

## 11. Key takeaway

- Process lifetime không phải application durability boundary.
- App Pool recycle phải là expected operational event.
- Critical background work cần persistence, idempotency và resume/retry strategy.

# 10. React stale closures: UI có thể dùng state cũ dù code nhìn hoàn toàn hợp lệ

## 1. What is it?

Trong React function components, mỗi render tạo một snapshot của props/state và các closures có thể giữ snapshot đó.

Mental model:

```text
render #1: count = 0
callback captures count=0

render #2: count = 5
old callback still references snapshot from render #1
```

Stale closure xảy ra khi async callback/effect/event handler sử dụng state cũ ngoài ý muốn.

## 2. Why does it exist?

JavaScript closures capture lexical environment. React function component không mutate cùng một `count` variable giữa renders; mỗi render là một invocation mới.

Điều này giúp render model predictable nhưng làm dependency management của effects/callbacks quan trọng.

## 3. How does it work?

Sai phổ biến:

```tsx
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1);
  }, 1000);

  return () => clearInterval(id);
}, []);
```

Callback capture `count` của initial render.

Fix bằng functional update:

```tsx
setCount(current => current + 1);
```

Hoặc dependency đúng nếu effect semantics cần recreate.

## 4. Practical implementation

Data fetching theo filter cần tránh response cũ overwrite response mới:

```tsx
useEffect(() => {
  const controller = new AbortController();

  (async () => {
    const response = await fetch(`/api/search?q=${query}`, {
      signal: controller.signal
    });

    if (response.ok) {
      setResults(await response.json());
    }
  })();

  return () => controller.abort();
}, [query]);
```

Dependency array là correctness contract, không chỉ performance hint.

## 5. Real production scenario

Search UI đổi filter nhanh. Request cho filter A chậm, request B nhanh. B render trước, sau đó A trả về và overwrite results dù UI đang hiển thị filter B.

User thấy kết quả “nhảy ngược”. Đây là temporal race, không phải backend trả sai data.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng dùng state cũ hoặc response không khớp filter hiện tại.

**Evidence** → network timeline cho thấy responses hoàn tất out of order; callback giữ old props/state.

**Hypothesis** → stale closure hoặc uncontrolled async race.

**Diagnosis** → inspect effect dependencies, captured values và request lifecycle trong DevTools.

**Fix** → correct dependencies, functional state updates, cancellation/sequence guards.

**Verification** → automate rapid input/filter changes và introduce artificial network delay.

## 7. Common mistakes

- Xóa dependency để effect “chỉ chạy một lần”.
- Disable exhaustive-deps rule mà không hiểu semantics.
- Dùng state value cũ trong timer/callback.
- Không cancel stale request.
- Nhầm `useCallback` là công cụ fix stale closures tự động.
- Thêm mọi thứ vào dependency array mà không hiểu effect lifecycle.

## 8. Alternatives

- Vue reactivity có mental model khác nhưng async race vẫn tồn tại.
- Data-fetching libraries có request deduplication/cancellation/cache semantics tích hợp.
- Server-driven navigation có thể giảm một số client state complexity nhưng không loại async ordering issues.

## 9. Trade-offs

### Advantages

- React render snapshots giúp reasoning về immutable render state.
- Explicit dependencies làm data-flow rõ khi dùng đúng.

### Costs / Risks

- Closures + async callbacks tạo subtle bugs.
- Overuse effects làm synchronization logic khó hiểu.
- Abstractions/data-fetching libraries thêm dependency nhưng có thể chuẩn hóa race handling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mỗi render có state snapshot riêng.

### Middle

Biết dependency arrays, functional updates và cleanup/cancellation.

### Senior

Chẩn đoán temporal races bằng network timeline và design state flow để giảm effect coupling.

### Technical Lead / Architect

Đặt frontend data-fetching/state conventions để correctness không phụ thuộc từng developer tự xử lý stale-request logic.

## 11. Key takeaway

- React closures có thể giữ state từ render cũ.
- Async response ordering là correctness problem, không chỉ UX detail.
- Dependency management và cancellation phải được xem như lifecycle semantics.
