# 1. .NET `Channel<T>`: bounded queue, backpressure và producer-consumer an toàn trong process

## 1. What is it?

`System.Threading.Channels.Channel<T>` là abstraction producer-consumer asynchronous trong .NET. Mental model đúng không phải “một `Queue<T>` có async”, mà là **một boundary giữa tốc độ sinh work và tốc độ xử lý work**.

Producer ghi item vào `ChannelWriter<T>`, consumer đọc qua `ChannelReader<T>`. Với bounded channel, capacity được giới hạn. Khi consumer chậm hơn producer, hệ thống phải có policy rõ ràng: chờ, drop item hoặc từ chối work. Đây chính là backpressure.

## 2. Why does it exist?

Một `ConcurrentQueue<T>` chỉ giải quyết thread safety của collection; nó không giải quyết signaling, async waiting hay capacity control. Một loop kiểu “enqueue rồi polling mỗi 100 ms” gây latency, wake-up không cần thiết và rất dễ tạo unbounded memory growth.

Trong production, producer thường có thể nhanh hơn consumer: HTTP request tạo notification nhanh hơn SMTP provider gửi mail, file watcher phát event nhanh hơn parser xử lý, hoặc API nhận telemetry nhanh hơn downstream batch writer. Nếu queue không bounded, RAM trở thành queue vô hạn.

## 3. How does it work?

```text
Producers
   |
   v
Bounded Channel<T>
   |
   | capacity = N
   | full mode = Wait / Drop...
   v
Consumers
   |
   v
External dependency / CPU work
```

Với `BoundedChannelFullMode.Wait`, `WriteAsync` sẽ chờ khi channel đầy. Backpressure lan ngược về producer thay vì âm thầm tăng memory.

## 4. Practical implementation

```csharp
builder.Services.AddSingleton(Channel.CreateBounded<EmailJob>(
    new BoundedChannelOptions(500)
    {
        SingleReader = true,
        SingleWriter = false,
        FullMode = BoundedChannelFullMode.Wait
    }));

public sealed class EmailWorker(
    Channel<EmailJob> channel,
    IEmailSender sender,
    ILogger<EmailWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in channel.Reader.ReadAllAsync(stoppingToken))
        {
            try
            {
                await sender.SendAsync(job, stoppingToken);
            }
            catch (Exception ex)
            {
                logger.LogError(ex, "Failed email job {JobId}", job.Id);
            }
        }
    }
}
```

Producer:

```csharp
await channel.Writer.WriteAsync(job, cancellationToken);
```

Nếu request không được phép chờ khi channel full, có thể dùng `TryWrite` và trả `429`/`503` tùy semantics.

## 5. Real production scenario

Một employee platform cho phép bulk-send 20.000 notifications. Nếu API tạo 20.000 `Task.Run()` cùng lúc, ThreadPool, SMTP connection pool và memory đều chịu spike.

Một bounded channel cho phép API đưa work vào một buffer có giới hạn, worker xử lý theo concurrency budget đã định. Nếu backlog vượt capacity, API có thể fail fast hoặc chuyển sang durable queue như Azure Service Bus.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng đều, latency của notification tăng từ vài giây lên hàng chục phút.

**Evidence** → producer rate lớn hơn consumer rate; queue depth tăng liên tục; downstream SMTP p95 latency tăng.

**Hypothesis** → application thiếu backpressure hoặc channel capacity/concurrency không phù hợp downstream capacity.

**Diagnosis** → đo enqueue rate, dequeue rate, queue depth, processing duration và failure rate.

**Fix** → bounded capacity, giới hạn consumer concurrency, fail fast khi quá tải hoặc chuyển sang durable external queue.

**Verification** → memory ổn định dưới load test, queue depth quay về baseline sau burst, downstream không bị overload.

## 7. Common mistakes

* Dùng unbounded channel vì “RAM server còn nhiều”.
* Spawn thêm consumer vô hạn khi backlog tăng.
* Dùng in-memory channel cho work cần survive process restart.
* Không propagate `CancellationToken` khi shutdown.
* Không có metric cho queue depth và oldest-item age.
* Nhầm bounded queue với durable message broker.

## 8. Alternatives

* `ConcurrentQueue<T>`: phù hợp khi chỉ cần thread-safe data structure và lifecycle đơn giản.
* `SemaphoreSlim`: giới hạn concurrency, nhưng không tự quản queue semantics.
* Azure Service Bus / RabbitMQ: phù hợp khi cần durability, cross-process delivery, retries, DLQ.
* `TPL Dataflow`: mạnh hơn cho processing graph nhưng thêm abstraction và dependency.

## 9. Trade-offs

### Advantages

* Async-native producer-consumer.
* Backpressure rõ ràng.
* Ít allocation/polling hơn nhiều custom queue implementation.
* Dễ giới hạn memory trong process.

### Costs / Risks

* Không durable.
* Process restart làm mất queued items.
* Capacity và full-mode là business decision, không chỉ technical setting.
* Consumer quá chậm vẫn tạo backlog; channel không tự sửa downstream bottleneck.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu producer và consumer có thể chạy khác tốc độ và queue không nên mặc định vô hạn.

### Middle

Biết tạo bounded channel, đọc bằng `ReadAllAsync`, xử lý cancellation và metrics cơ bản.

### Senior

Biết thiết kế capacity, overload behavior, concurrency budget và phân biệt in-memory buffering với durable messaging.

### Technical Lead / Architect

Quyết định work nào được phép mất khi process restart, khi nào channel đủ đơn giản, khi nào phải dùng external broker và downstream capacity budget là bao nhiêu.

## 11. Key takeaway

* `Channel<T>` giải quyết coordination + backpressure, không chỉ thread-safe queue.
* Bounded capacity biến overload thành behavior có kiểm soát thay vì memory growth.
* Work cần durability không nên chỉ tồn tại trong process memory.

# 2. HTTP `ETag` và conditional requests trong ASP.NET Core: giảm bandwidth mà vẫn giữ cache correctness

## 1. What is it?

`ETag` là validator của một representation HTTP. Server trả một opaque identifier cho phiên bản hiện tại của resource; client gửi lại `If-None-Match` để hỏi liệu representation có thay đổi hay chưa.

Mental model: `ETag` không phải TTL. TTL trả lời “trong bao lâu tôi tin cache mà không hỏi server”; validator trả lời “khi hỏi lại server, phiên bản tôi đang giữ còn đúng không?”.

## 2. Why does it exist?

Một product page JSON 200 KB có thể được request nhiều lần nhưng dữ liệu hiếm khi đổi. Nếu server luôn trả full payload, bandwidth, serialization CPU và network time bị lãng phí.

`ETag` cho phép server trả `304 Not Modified` không có response body khi representation chưa đổi. Điều này đặc biệt hữu ích khi freshness cần cao nên không thể đặt `max-age` dài.

## 3. How does it work?

```text
Client -> GET /products/42
Server -> 200 + ETag: "v17" + body

Client -> GET /products/42
          If-None-Match: "v17"

Server compares current validator
   |
   +-- same --> 304 Not Modified
   |
   +-- changed --> 200 + ETag: "v18" + new body
```

`ETag` phải đại diện cho **representation**, không nhất thiết chỉ database row. Nếu response phụ thuộc product + price + localization, validator phải phản ánh các inputs đó.

## 4. Practical implementation

```csharp
app.MapGet("/products/{id:int}", async (
    int id,
    ProductDbContext db,
    HttpContext http,
    CancellationToken ct) =>
{
    var item = await db.Products
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new
        {
            x.Id,
            x.Name,
            x.Price,
            x.Version
        })
        .SingleOrDefaultAsync(ct);

    if (item is null)
        return Results.NotFound();

    var etag = $"\"{item.Version}\"";

    if (http.Request.Headers.IfNoneMatch == etag)
        return Results.StatusCode(StatusCodes.Status304NotModified);

    http.Response.Headers.ETag = etag;
    return Results.Ok(item);
});
```

Trong hệ thống thực, `Version` có thể là row version, content hash hoặc version aggregate đã được tính deterministic.

## 5. Real production scenario

Mobile app gọi `/api/configuration` mỗi lần mở màn hình. Config thay đổi vài lần mỗi ngày nhưng payload chứa hàng trăm feature settings.

Nếu dùng ETag, app vẫn revalidate mỗi lần để giữ freshness nhưng phần lớn requests chỉ nhận `304`, giảm đáng kể payload bytes và serialization work.

## 6. Failure scenario & troubleshooting

**Symptom** → client tiếp tục thấy dữ liệu cũ dù server trả `304`.

**Evidence** → ETag chỉ dựa trên bảng `Products`, trong khi response còn lấy promotion từ bảng khác.

**Hypothesis** → validator không phản ánh toàn bộ representation dependencies.

**Diagnosis** → trace cách ETag được tạo, so sánh inputs của response và inputs của version/hash.

**Fix** → version aggregate đúng boundary hoặc dùng content hash sau khi build representation nếu cost chấp nhận được.

**Verification** → thay đổi từng dependency và xác nhận ETag đổi đúng khi representation đổi.

## 7. Common mistakes

* Dùng timestamp format không ổn định hoặc precision không đủ làm validator.
* Tạo random ETag mỗi request, khiến cache không bao giờ hit.
* Coi `304` như response có body mới.
* Quên `Vary` khi response phụ thuộc header như `Accept-Language`.
* Hash payload rất lớn mỗi request rồi tốn CPU hơn số bandwidth tiết kiệm.
* Trộn CDN cache policy với application validator mà không hiểu interaction.

## 8. Alternatives

* `Last-Modified` + `If-Modified-Since`: đơn giản hơn nhưng timestamp precision/semantics hạn chế hơn.
* `Cache-Control: max-age`: tốt khi có thể chấp nhận freshness window mà không revalidate.
* Output Cache / CDN: giảm cả application execution nếu cacheable ở server/edge.

## 9. Trade-offs

### Advantages

* Giảm response body transfer.
* Giữ freshness cao nhờ revalidation.
* Dựa trên HTTP semantics chuẩn.

### Costs / Risks

* Server vẫn nhận request và có thể vẫn phải query để tính validator.
* Validator design sai tạo stale content.
* Representation variants làm key/version phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `200` trả body mới, `304` nói client dùng lại cache hiện có.

### Middle

Biết implement `ETag`, `If-None-Match`, `Cache-Control` và test HTTP behavior.

### Senior

Hiểu validator boundary, `Vary`, CDN/browser interaction và cost tính hash/version.

### Technical Lead / Architect

Quyết định resource nào nên revalidate, resource nào nên edge-cache, freshness SLA là gì và representation version được ownership ở layer nào.

## 11. Key takeaway

* `ETag` là validator, không phải TTL.
* Validator phải thay đổi khi bất kỳ input nào ảnh hưởng representation thay đổi.
* HTTP caching tốt bắt đầu từ semantics đúng, không phải middleware “cache everything”.

# 3. EF Core `ExecuteUpdate` / `ExecuteDelete`: bulk update nhanh hơn nhưng có thể lệch Change Tracker

## 1. What is it?

`ExecuteUpdateAsync` và `ExecuteDeleteAsync` cho phép EF Core gửi `UPDATE`/`DELETE` trực tiếp xuống database từ LINQ query mà không load từng entity vào memory và không đi qua normal tracked-entity `SaveChanges` flow.

Mental model: đây là **set-based database operation**, không phải “SaveChanges nhanh hơn”.

## 2. Why does it exist?

Nếu cần deactivate 100.000 expired sessions, cách load 100.000 entities, mutate từng entity rồi `SaveChanges` tạo memory pressure, Change Tracker cost và nhiều SQL batches không cần thiết.

Relational database vốn tối ưu cho set-based operation:

```sql
UPDATE Sessions
SET IsActive = 0
WHERE ExpiresAt < @now;
```

EF Core bulk APIs đưa khả năng đó vào LINQ mà vẫn parameterized và composable.

## 3. How does it work?

```text
LINQ predicate
   |
   v
EF query translation
   |
   v
Single set-based UPDATE/DELETE
   |
   v
Database rows changed

Change Tracker is NOT synchronized automatically
```

Đây là điểm quan trọng: tracked entity đang nằm trong `DbContext` có thể giữ state cũ sau khi database đã bị bulk update.

## 4. Practical implementation

```csharp
var affected = await db.Sessions
    .Where(x => x.ExpiresAt < clock.UtcNow && x.IsActive)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.IsActive, false)
        .SetProperty(x => x.UpdatedAt, clock.UtcNow), ct);
```

Delete:

```csharp
await db.AuditLogs
    .Where(x => x.CreatedAt < cutoff)
    .ExecuteDeleteAsync(ct);
```

Không cần gọi `SaveChangesAsync()` cho hai operations này; SQL chạy ngay khi method execute.

## 5. Real production scenario

Nightly cleanup job disable expired API tokens. Trước đây job load từng token rồi update, chạy 12 phút và allocation rất cao. Chuyển sang set-based update giảm xuống vài giây.

Nhưng một admin workflow reuse cùng `DbContext` đã load token trước bulk update; UI response sau đó map từ tracked entity và vẫn thấy `IsActive = true`. Database đúng nhưng process state stale.

## 6. Failure scenario & troubleshooting

**Symptom** → log nói bulk update thành công nhưng response cùng request hiển thị giá trị cũ.

**Evidence** → `ExecuteUpdate` affected rows > 0; query database bên ngoài thấy dữ liệu mới; tracked entity trong context vẫn state cũ.

**Hypothesis** → Change Tracker divergence.

**Diagnosis** → kiểm tra entity đã được tracked trước operation hay chưa; inspect `db.ChangeTracker.Entries()`.

**Fix** → tránh mix tracked entity workflow với bulk update cùng context; reload/clear tracker khi thật sự cần; thiết kế bulk operation ở boundary riêng.

**Verification** → integration test xác minh cả database state và application state sau operation.

## 7. Common mistakes

* Gọi `SaveChanges` và nghĩ nó quản transaction cho bulk operation đã chạy trước đó.
* Mix `ExecuteUpdate` với tracked mutations rồi giả định atomic automatically.
* Bỏ qua domain invariants vì bulk SQL bypass entity methods.
* Dùng bulk operation cho aggregate rule phức tạp chỉ để nhanh.
* Không kiểm tra affected row count khi business cần optimistic expectation.

## 8. Alternatives

* Tracked entities + `SaveChanges`: phù hợp khi domain behavior/invariants xảy ra per entity.
* Raw SQL: linh hoạt nhất nhưng ít type safety hơn.
* Bulk library: phù hợp import/update volume lớn với nhiều features hơn, nhưng thêm dependency.

## 9. Trade-offs

### Advantages

* Ít round trips và allocation.
* Không cần materialize entities.
* Tận dụng set-based execution của database.

### Costs / Risks

* Bypass Change Tracker synchronization.
* Có thể bypass domain methods/events.
* Transaction semantics phải được thiết kế rõ nếu phối hợp nhiều operations.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu database có thể update cả set rows mà không cần load object từng row.

### Middle

Biết dùng `ExecuteUpdate/Delete` và kiểm tra generated SQL/affected rows.

### Senior

Hiểu tracker divergence, transaction boundary, domain invariant và concurrency implication.

### Technical Lead / Architect

Quyết định bulk operation thuộc maintenance/application boundary nào, khi nào performance đáng để bypass rich domain workflow và cách audit/recover operation lớn.

## 11. Key takeaway

* `ExecuteUpdate/Delete` là set-based SQL execution, không phải tracked update.
* Performance gain đi cùng việc bỏ qua Change Tracker và có thể bỏ qua domain behavior.
* Dùng nó ở boundary mà invariant và transaction semantics đã rõ.

# 4. PostgreSQL MVCC và `VACUUM`: vì sao update/delete không lập tức giải phóng row version

## 1. What is it?

PostgreSQL dùng MVCC (Multi-Version Concurrency Control) để nhiều transactions có thể thấy các snapshot dữ liệu khác nhau mà không cần serialize mọi read/write bằng lock.

Mental model: một `UPDATE` thường không sửa row “tại chỗ” theo nghĩa logical duy nhất. PostgreSQL tạo tuple version mới; version cũ trở thành dead tuple sau khi không còn transaction nào cần nhìn thấy nó. `VACUUM` thu hồi khả năng reuse storage của các dead tuples và duy trì health của MVCC metadata.

## 2. Why does it exist?

Nếu reader phải block writer hoặc writer phải block reader trên mọi row, concurrency của OLTP workload giảm mạnh. MVCC cho phép một transaction đang đọc snapshot cũ tiếp tục thấy version phù hợp trong khi transaction khác update data.

Trade-off là old versions phải được quản lý. Nếu dead tuples tích tụ, table/index bloat tăng, I/O tăng và query latency có thể xấu đi.

## 3. How does it work?

```text
Transaction A snapshot
    sees tuple v1

Transaction B UPDATE
    v1 -> old version
    v2 -> new version

After old snapshots no longer need v1
    |
    v
VACUUM can mark/reclaim space for reuse
```

`VACUUM` không phải lúc nào cũng làm file table trên disk nhỏ lại. Normal vacuum chủ yếu làm space reusable trong relation. `VACUUM FULL` rewrite table và có operational cost/locking cao hơn.

## 4. Practical implementation

Kiểm tra dead tuples:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Xem long-running transactions:

```sql
SELECT
    pid,
    xact_start,
    state,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Một transaction mở quá lâu có thể giữ snapshot cũ và ngăn cleanup hiệu quả.

## 5. Real production scenario

Một CRM có bảng `LeadEvents` bị update status hàng triệu lần/ngày. Autovacuum settings mặc định phản ứng không đủ nhanh với access pattern. Dead tuples tăng, indexes phình và p95 query latency tăng dần qua vài ngày dù data logical không tăng nhiều.

Team ban đầu “thêm index” làm write cost và bloat tệ hơn. Root cause là churn + vacuum behavior, không đơn giản thiếu index.

## 6. Failure scenario & troubleshooting

**Symptom** → disk usage tăng, query đọc cùng dataset ngày càng chậm, CPU không phải bottleneck chính.

**Evidence** → `n_dead_tup` cao, autovacuum lag, relation/index size tăng, có long-running transactions.

**Hypothesis** → dead tuple accumulation/table bloat do write churn hoặc snapshot giữ lâu.

**Diagnosis** → kiểm tra `pg_stat_user_tables`, active transactions, autovacuum logs/settings, query plan và relation sizes.

**Fix** → xử lý long-running transaction, tune autovacuum per table nếu cần, giảm unnecessary updates; maintenance rewrite chỉ khi evidence justify.

**Verification** → dead tuple ratio giảm, autovacuum cadence ổn, I/O và p95 query cải thiện.

## 7. Common mistakes

* Nghĩ `DELETE` lập tức làm file nhỏ đi.
* Disable autovacuum để “giảm CPU”.
* Chạy `VACUUM FULL` thường xuyên trong production mà không hiểu lock/rewrite cost.
* Giữ transaction idle rất lâu.
* Add nhiều indexes trên high-churn table mà không tính write amplification.

## 8. Alternatives

MVCC là core PostgreSQL behavior chứ không phải feature có thể đổi đơn giản. Engineering alternatives nằm ở data/access pattern: partitioning, append-only model, giảm update churn hoặc archival strategy.

## 9. Trade-offs

### Advantages

* Reader/writer concurrency tốt.
* Snapshot semantics mạnh.
* Ít lock contention hơn mô hình khóa đọc thô.

### Costs / Risks

* Dead tuples và bloat.
* Vacuum là operational concern bắt buộc.
* Long-running transactions có hậu quả system-wide khó thấy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu update/delete có thể để lại old row versions tạm thời.

### Middle

Biết đọc `pg_stat_user_tables`, transaction state và basic `EXPLAIN` evidence.

### Senior

Hiểu MVCC snapshot, bloat, autovacuum tuning và write amplification từ indexes.

### Technical Lead / Architect

Thiết kế high-churn schema, partition/archival strategy và operational SLO cho vacuum/storage growth thay vì chỉ tối ưu query riêng lẻ.

## 11. Key takeaway

* PostgreSQL concurrency tốt nhờ giữ nhiều row versions, và đó tạo cleanup cost.
* `VACUUM` là phần bình thường của MVCC lifecycle, không phải “repair tool khi database lỗi”.
* Long-running transactions và write-heavy tables phải được quan sát như production risks.

# 5. Redis distributed lock: lease, expiry, fencing token và giới hạn của “SET NX là đủ”

## 1. What is it?

Distributed lock là cơ chế giúp nhiều process/instances phối hợp để giảm khả năng cùng thực hiện một critical operation tại cùng thời điểm. Redis thường được dùng với atomic `SET key value NX PX ttl`.

Mental model quan trọng: distributed lock thực tế thường là **lease có thời hạn**, không phải mutex hoàn hảo. Sau TTL, ownership có thể chuyển cho process khác dù process cũ vẫn đang chạy.

## 2. Why does it exist?

Khi application scale-out, in-process `lock` chỉ bảo vệ threads trong một process. Hai App Service instances vẫn có thể cùng chạy scheduled reconciliation hoặc cùng process một singleton-like task.

Redis lock tạo shared coordination point. Nhưng network pause, process suspension, GC pause và lock expiry làm correctness phức tạp hơn local mutex.

## 3. How does it work?

```text
Worker A -> SET lock tokenA NX PX 30000 -> success
Worker A starts work

30s expires before A finishes

Worker B -> SET lock tokenB NX PX 30000 -> success
Worker B starts same work

Worker A wakes up and continues
```

Đây là lý do “có lock” không đồng nghĩa “không thể có overlap”. Với operations cần correctness cao, downstream resource có thể cần fencing token/version để từ chối stale owner.

## 4. Practical implementation

Acquire:

```csharp
var token = Guid.NewGuid().ToString("N");
var acquired = await db.StringSetAsync(
    key: "jobs:inventory-sync",
    value: token,
    expiry: TimeSpan.FromSeconds(30),
    when: When.NotExists);
```

Release phải chỉ xóa lock nếu token còn thuộc caller. Dùng Lua atomic compare-and-delete:

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
```

Không nên `DEL` vô điều kiện vì có thể xóa lock mới của instance khác sau khi lease cũ đã expired.

## 5. Real production scenario

Một scheduled invoice job được deploy trên 4 instances. Redis lock TTL 60 giây, nhưng cuối tháng job mất 90 giây. Instance A giữ lock rồi hết TTL ở giây 60; instance B acquire và bắt đầu chạy; A vẫn tiếp tục tới giây 90. Duplicate invoices xuất hiện.

Fix tốt hơn có thể là idempotent invoice creation với unique business key, external scheduler hoặc durable queue, thay vì chỉ kéo TTL lên 10 phút.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate side effects thỉnh thoảng xảy ra dù log nói lock acquisition chỉ một instance tại một thời điểm.

**Evidence** → operation duration vượt lease TTL; process pause/network latency; lock owner đổi trước khi first worker hoàn tất.

**Hypothesis** → expired lease + stale worker tiếp tục side effect.

**Diagnosis** → log lock token, acquired-at, expiry, operation duration, instance ID và downstream idempotency key.

**Fix** → lease renewal có kiểm soát, fencing/version ở downstream, idempotent business operation hoặc thay coordination model.

**Verification** → chaos/load test với artificial pauses vượt TTL và xác minh không tạo duplicate business state.

## 7. Common mistakes

* `SET NX` không TTL, process crash khiến lock tồn tại mãi.
* `DEL` lock vô điều kiện.
* TTL được chọn nhỏ hơn worst-case operation duration.
* Tin distributed lock thay thế idempotency.
* Dùng Redis lock cho correctness tài chính nghiêm ngặt mà không có downstream guard.
* Không thiết kế behavior khi Redis unavailable.

## 8. Alternatives

* Database unique constraint/advisory lock: đôi khi gần business data hơn và đơn giản hơn.
* Azure Service Bus competing consumers: phù hợp queue work.
* External scheduler: tốt cho singleton scheduled trigger.
* Leader election: phù hợp long-running ownership model nhưng phức tạp hơn.

## 9. Trade-offs

### Advantages

* Dễ triển khai cho coordination nhẹ.
* Latency thấp.
* Có thể dùng chung nhiều app instances.

### Costs / Risks

* Lease expiry tạo edge cases.
* Redis trở thành coordination dependency.
* Network partition/process pause làm mutual exclusion không tuyệt đối theo intuition local lock.
* Correctness thường vẫn cần idempotency/fencing.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu local `lock` không bảo vệ nhiều servers.

### Middle

Biết acquire/release bằng unique token + TTL an toàn hơn.

### Senior

Hiểu lease expiry, stale owner, renewal, fencing và failure behavior.

### Technical Lead / Architect

Quyết định có thực sự cần distributed lock hay business invariant nên được bảo vệ bằng unique constraint, idempotency, queue partitioning hoặc scheduler ownership.

## 11. Key takeaway

* Redis lock là lease, không phải mutex tuyệt đối.
* Compare-and-delete token là tối thiểu để release an toàn hơn.
* Correctness quan trọng nên dựa thêm vào idempotency/fencing ở business boundary.

# 6. Domain Event vs Integration Event: tách business reaction khỏi distributed contract

## 1. What is it?

Domain Event biểu diễn một fact có ý nghĩa **bên trong domain/bounded context**, ví dụ `TimesheetApproved`. Integration Event là contract dùng để thông báo **ra ngoài boundary** cho module/service khác, ví dụ `TimesheetApprovalCompletedV1`.

Hai loại có thể phát sinh từ cùng business action nhưng không nên mặc định là cùng class/message.

## 2. Why does it exist?

Nếu domain object publish trực tiếp external message schema, business model bị coupling với transport, versioning và nhu cầu của consumers bên ngoài.

Ngược lại, nếu mọi event chỉ là internal callback, các bounded contexts khác không có contract ổn định để integrate.

Tách hai khái niệm giúp internal model evolve độc lập hơn external contract.

## 3. How does it work?

```text
Aggregate
   |
   | raises
   v
Domain Event
   |
   v
Application handler
   |
   +--> update local read model
   +--> create Outbox Integration Event
                  |
                  v
             Message Broker
                  |
                  v
           Other bounded context
```

Domain event có thể dispatch in-process trong transaction/application workflow. Integration event thường phải đi qua durable publication path như Outbox.

## 4. Practical implementation

Domain event:

```csharp
public sealed record TimesheetApproved(
    Guid TimesheetId,
    Guid EmployeeId,
    DateTimeOffset ApprovedAt) : IDomainEvent;
```

Integration contract:

```csharp
public sealed record TimesheetApprovalCompletedV1(
    Guid TimesheetId,
    Guid EmployeeId,
    DateTimeOffset OccurredAt);
```

Application handler mapping domain → integration event có thể ghi Outbox trong cùng DB transaction.

## 5. Real production scenario

Employee module approve timesheet. Nội bộ cần recalculate monthly totals; Payroll module cần biết approval đã hoàn tất.

`TimesheetApproved` internal event có thể chứa rich domain information hoặc thay đổi theo model. Payroll chỉ nên phụ thuộc một stable integration contract nhỏ, versioned rõ và không cần biết aggregate internals.

## 6. Failure scenario & troubleshooting

**Symptom** → refactor domain property làm consumer ngoài service deserialization fail.

**Evidence** → external broker message dùng trực tiếp internal domain-event type; không có contract versioning.

**Hypothesis** → boundary bị xuyên thủng bởi shared event model.

**Diagnosis** → trace ownership của message schema và package references giữa bounded contexts.

**Fix** → tách integration contract, version, map ở application boundary và publish qua Outbox.

**Verification** → contract tests đảm bảo old consumer vẫn đọc được supported event version.

## 7. Common mistakes

* Gọi mọi message là “domain event”.
* Shared NuGet package chứa domain entities/events cho nhiều services.
* Publish broker message trực tiếp trong aggregate method.
* Domain event handler làm remote HTTP call trong DB transaction.
* Không định nghĩa ownership/versioning của integration schema.

## 8. Alternatives

* Direct application service call: đơn giản hơn nếu vẫn cùng module/process và coupling chấp nhận được.
* REST integration: phù hợp synchronous query/command cần immediate response.
* Integration events: tốt khi cần asynchronous decoupling và eventual consistency.

## 9. Trade-offs

### Advantages

* Boundary và ownership rõ hơn.
* External contract có lifecycle/version riêng.
* Domain model không bị transport concerns chi phối.

### Costs / Risks

* Thêm mapping và message types.
* Eventual consistency khi đi distributed.
* Outbox/consumer observability tăng operational complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event là “fact đã xảy ra”, khác command là “yêu cầu làm gì”.

### Middle

Biết raise domain event, handle local reaction và map integration DTO.

### Senior

Hiểu transaction boundary, Outbox, idempotent consumer và schema evolution.

### Technical Lead / Architect

Định bounded-context ownership, event taxonomy và quyết định interaction nào nên synchronous, local event hay integration event.

## 11. Key takeaway

* Domain Event phục vụ domain boundary; Integration Event phục vụ contract giữa boundaries.
* Không nên expose internal domain model chỉ để “reuse message class”.
* Distributed event publication cần transaction/retry/idempotency strategy riêng.

# 7. Azure Private Endpoint + Private DNS: private connectivity và failure mode “IP đúng nhưng DNS sai”

## 1. What is it?

Azure Private Endpoint tạo một network interface có private IP trong Virtual Network để truy cập một PaaS resource như Storage, Key Vault, SQL hoặc Cosmos DB qua private connectivity.

Mental model: Private Endpoint không chỉ là firewall rule. Nó thay đổi **network path + DNS resolution**. Application vẫn thường gọi hostname public-style của service, nhưng DNS trong private network phải resolve hostname đó sang private endpoint IP.

## 2. Why does it exist?

Enterprise workloads thường không muốn traffic tới PaaS service đi qua public endpoint, kể cả có TLS/authentication. Private Endpoint cho phép private IP addressing, network isolation và giảm exposure surface.

Nhưng nếu chỉ tạo endpoint mà không thiết kế DNS, app có thể vẫn resolve public IP hoặc không resolve được hostname.

## 3. How does it work?

```text
App in VNet
   |
   | DNS query vault.azure.net
   v
Private DNS Zone
   |
   | CNAME / private record
   v
Private IP
   |
   v
Private Endpoint NIC
   |
   v
Azure PaaS Resource
```

Private DNS Zone thường cần link đúng VNet. Hybrid/on-prem DNS có thể cần conditional forwarding tới Azure DNS resolver path.

## 4. Practical implementation

Troubleshooting từ Linux container:

```bash
nslookup myvault.vault.azure.net
getent hosts myvault.vault.azure.net
curl -v https://myvault.vault.azure.net/
```

Từ .NET có thể log resolved addresses khi diagnostic, nhưng không nên hard-code private IP vì PaaS TLS certificate và service routing vẫn dựa vào hostname.

```csharp
var addresses = await Dns.GetHostAddressesAsync("myvault.vault.azure.net");
logger.LogInformation("Resolved Key Vault addresses: {Addresses}", addresses);
```

## 5. Real production scenario

App Service được VNet Integration và Key Vault có Private Endpoint. Local developer access hoạt động, nhưng Production startup fail khi load secrets.

Network security team thấy private endpoint “Approved” nên cho rằng networking đúng. Thực tế App Service VNet resolve `myvault.vault.azure.net` ra public IP vì Private DNS Zone chưa link với integration VNet.

## 6. Failure scenario & troubleshooting

**Symptom** → Managed Identity authentication đúng nhưng request timeout hoặc `403` network access denied.

**Evidence** → DNS từ app resolve public IP; public network access trên Key Vault đã disabled.

**Hypothesis** → DNS path không đi tới Private Endpoint.

**Diagnosis** → kiểm tra hostname resolution **từ chính runtime network**, Private DNS Zone links, custom DNS server/forwarder và route/NSG nếu có.

**Fix** → link đúng zone/VNet hoặc cấu hình forwarding đúng; giữ application dùng FQDN.

**Verification** → DNS resolve private IP, TLS/auth request thành công, Azure diagnostics cho thấy private endpoint traffic.

## 7. Common mistakes

* Chỉ kiểm tra endpoint status `Approved` mà bỏ qua DNS.
* Hard-code private IP vào config.
* Test DNS từ laptop thay vì từ App Service/AKS/container network.
* Nhầm App Service VNet Integration với việc inbound app tự private.
* Disable public access trước khi private DNS path được validate.

## 8. Alternatives

* Public endpoint + firewall/IP restrictions: đơn giản hơn, đôi khi đủ cho risk profile thấp hơn.
* Service Endpoint: mô hình khác, không cấp private IP cho PaaS resource và hỗ trợ services khác nhau tùy Azure capability.
* Private Endpoint: phù hợp khi cần strong network isolation/private addressing.

## 9. Trade-offs

### Advantages

* Private IP connectivity tới PaaS.
* Có thể disable public network access.
* Tốt hơn cho enterprise network segmentation/compliance.

### Costs / Risks

* DNS architecture phức tạp hơn.
* Hybrid networking dễ lỗi khó debug.
* Thêm endpoint/DNS resources và cost vận hành.
* Deployment order cần cẩn thận để không tự cắt connectivity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hostname phải resolve đúng IP trước khi authentication có ý nghĩa.

### Middle

Biết dùng `nslookup`, kiểm tra Private DNS Zone link và validate từ runtime environment.

### Senior

Hiểu split DNS, custom resolver, App Service/AKS VNet integration và failure isolation giữa DNS, route, firewall, identity.

### Technical Lead / Architect

Thiết kế private connectivity pattern thống nhất, ownership của DNS zones, rollout order và operational runbook cho nhiều subscriptions/VNets.

## 11. Key takeaway

* Private Endpoint là networking + DNS problem, không chỉ checkbox security.
* Luôn troubleshoot từ runtime network path, không từ laptop.
* Giữ FQDN; sửa DNS/routing thay vì hard-code private IP.

# 8. Canary deployment + feature flags: giảm blast radius nhưng không thay thế backward compatibility

## 1. What is it?

Canary deployment đưa version mới tới một tỷ lệ nhỏ traffic/instances trước khi mở rộng rollout. Feature flag tách việc **deploy code** khỏi **enable behavior**.

Mental model: canary giảm blast radius của binary/release; feature flag giảm blast radius của feature behavior. Hai kỹ thuật bổ trợ nhau nhưng không tự giải quyết database/API compatibility.

## 2. Why does it exist?

Staging không thể tái tạo hoàn toàn production traffic, data distribution và dependency behavior. Big-bang deployment 100% khiến một regression nhỏ ảnh hưởng toàn bộ users ngay lập tức.

Canary cho phép thu evidence từ production trên phạm vi nhỏ. Feature flag cho phép disable feature mà không cần rollback toàn deployment.

## 3. How does it work?

```text
Build artifact v2
   |
   v
Deploy canary 5%
   |
   v
Observe health + business metrics
   |
   +-- bad --> stop / rollback
   |
   +-- good --> 25% --> 50% --> 100%

Feature flag can independently enable behavior for cohort
```

Trong giai đoạn rollout, v1 và v2 có thể cùng chạy. Database schema và shared contracts phải hỗ trợ coexistence.

## 4. Practical implementation

Feature flag boundary:

```csharp
if (await featureManager.IsEnabledAsync("NewPricingEngine"))
{
    return await newPricing.CalculateAsync(request, ct);
}

return await legacyPricing.CalculateAsync(request, ct);
```

Database migration nên theo Expand-Contract:

```text
1. Add new nullable/backward-compatible column
2. Deploy code that can read/write both versions
3. Backfill data
4. Switch behavior gradually
5. Remove old contract in later deployment
```

## 5. Real production scenario

E-commerce team deploy pricing engine mới. Canary 5% cho thấy technical error rate bình thường, nhưng conversion rate của cohort giảm 8% vì rounding behavior sai.

Nếu chỉ monitor CPU/5xx, rollout sẽ được coi là healthy. Canary tốt cần cả technical SLI và business guardrail.

## 6. Failure scenario & troubleshooting

**Symptom** → canary instances healthy nhưng old instances bắt đầu fail DB query sau migration.

**Evidence** → migration rename/drop column trước khi rollout hoàn tất; v1 binary vẫn phụ thuộc old schema.

**Hypothesis** → release strategy không backward compatible trong mixed-version window.

**Diagnosis** → map compatibility matrix giữa app versions, DB schema và message/API versions.

**Fix** → restore compatible schema, rollback migration nếu safe; áp dụng Expand-Contract cho lần sau.

**Verification** → load test mixed versions trên same schema và simulate rollback.

## 7. Common mistakes

* Canary chỉ nhìn HTTP 5xx.
* Feature flag tồn tại vĩnh viễn thành technical debt.
* Database destructive migration cùng release với code mới.
* Rollback binary nhưng schema không rollback-compatible.
* Dùng user-level feature flag cho security authorization.
* Không có automatic stop criteria.

## 8. Alternatives

* Blue-Green: switch traffic giữa hai full environments; rollback nhanh nhưng cost cao hơn.
* Rolling deployment: đơn giản, nhưng traffic distribution/control thường ít tinh hơn canary.
* Deployment slot trên App Service: hữu ích cho swap/prewarming nhưng vẫn cần schema compatibility.

## 9. Trade-offs

### Advantages

* Giảm blast radius.
* Evidence production trước full rollout.
* Feature flags cho phép disable behavior nhanh.

### Costs / Risks

* Mixed-version complexity.
* Monitoring/traffic routing phức tạp hơn.
* Flags cần lifecycle/ownership.
* Không cứu được destructive schema change đã phá old version.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy code và enable feature là hai hành động có thể tách rời.

### Middle

Biết instrument canary metrics, feature flag và rollback path.

### Senior

Thiết kế mixed-version compatibility, business guardrail và stop criteria.

### Technical Lead / Architect

Chọn rollout strategy dựa trên risk/cost, đặt compatibility policy cho API/DB/events và quản lifecycle feature flags ở cấp hệ thống.

## 11. Key takeaway

* Canary giảm blast radius, không thay thế compatibility engineering.
* Monitor business outcome cùng technical health.
* Rollback chỉ đáng tin khi schema/contracts vẫn hỗ trợ version cũ.

# 9. OpenTelemetry metrics cardinality: một label sai có thể biến observability thành bottleneck

## 1. What is it?

Metric cardinality là số lượng unique time series tạo ra từ combinations của metric name + attribute labels.

Ví dụ metric:

```text
http_requests_total{method="GET",status="200",route="/products/{id}"}
```

có cardinality thấp. Nếu label là raw URL `/products/123456`, mỗi product ID có thể tạo một time series riêng, cardinality tăng cực lớn.

Mental model: metric labels phải mô tả **bounded dimensions**, không phải arbitrary data.

## 2. Why does it exist?

Metrics backend tối ưu aggregate numeric time series. Chúng rất mạnh cho rate, percentile histogram, saturation và alerting. Nhưng mỗi unique attribute combination cần storage/indexing/query resources.

Nếu developer gắn `userId`, `requestId`, `email` hoặc full URL vào metric labels, telemetry cost có thể tăng nhanh hơn application traffic.

## 3. How does it work?

```text
Metric name
  + label A values
  + label B values
  + label C values
        |
        v
Cartesian combination of time series
```

Ví dụ 10 methods × 20 statuses × 100 routes = 20.000 potential series. Thêm 1 triệu user IDs có thể làm explosion khổng lồ.

Logs/traces phù hợp high-cardinality identifiers hơn metrics.

## 4. Practical implementation

Tốt:

```csharp
private static readonly Counter<long> Requests =
    meter.CreateCounter<long>("checkout.requests");

Requests.Add(1,
    new KeyValuePair<string, object?>("result", "success"),
    new KeyValuePair<string, object?>("channel", "web"));
```

Không tốt:

```csharp
Requests.Add(1,
    new("user.id", userId),
    new("request.id", http.TraceIdentifier));
```

`userId` và request ID nên nằm trong trace/log context, không phải metric dimension.

## 5. Real production scenario

Team thêm `search.query` làm label để biết từ khóa nào chậm. Search traffic có hàng trăm nghìn unique queries/ngày. Application vẫn healthy nhưng telemetry ingestion cost tăng mạnh và metrics dashboard chậm/time out.

Đúng hơn: metric giữ dimensions như `result`, `endpoint`, `region`; sample search query vào structured logs/traces khi cần investigation.

## 6. Failure scenario & troubleshooting

**Symptom** → monitoring bill tăng, dashboard query chậm, exporter/drop metrics xuất hiện.

**Evidence** → number of active time series tăng sau deployment; một attribute có gần-unbounded unique values.

**Hypothesis** → high-cardinality label explosion.

**Diagnosis** → inspect telemetry schema, top attributes by unique count và backend ingestion statistics.

**Fix** → remove/normalize label, dùng route template thay raw URL, chuyển identifiers sang logs/traces, apply Views/filtering nếu OpenTelemetry pipeline hỗ trợ.

**Verification** → active series và ingestion volume giảm, alert/query latency trở lại baseline.

## 7. Common mistakes

* Dùng `requestId` làm metric label.
* Dùng exception message nguyên văn làm dimension.
* Raw URL thay route template.
* Tạo metric name động theo tenant/customer.
* Instrument mọi thứ trước rồi mới nghĩ cost.
* Dùng metrics để debug một request cụ thể thay vì traces.

## 8. Alternatives

* Logs: tốt cho discrete events và rich context.
* Traces: tốt cho per-request causal path và high-cardinality correlation.
* Metrics: tốt cho aggregate health, rate, latency distribution và alerting.

Ba signals bổ sung nhau, không thay thế nhau.

## 9. Trade-offs

### Advantages

* Metrics rất hiệu quả cho aggregate health khi cardinality được kiểm soát.
* Query/alert nhanh trên bounded dimensions.
* Histograms cho latency/throughput analysis tốt.

### Costs / Risks

* Label explosion làm storage/cost/query load tăng.
* Over-aggregation làm mất diagnostic detail.
* Telemetry schema cần governance ở scale lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu metric labels tạo nhiều time series, không phải metadata miễn phí.

### Middle

Biết chọn bounded dimensions và phân biệt logs/metrics/traces.

### Senior

Theo dõi telemetry cost, histogram design, route normalization và cardinality failure.

### Technical Lead / Architect

Định observability schema/guidelines, retention/cost budget và signal nào dùng cho SLI/alerting hay forensic debugging.

## 11. Key takeaway

* Metric dimensions phải có cardinality hữu hạn và dự đoán được.
* Request/user identifiers thuộc logs/traces, không thuộc aggregate metric labels.
* Observability cũng là production system cần capacity và cost discipline.

# 10. Technical SEO engineering: canonical URL, redirect và HTTP status code như một phần của system contract

## 1. What is it?

Technical SEO ở góc nhìn engineering là việc đảm bảo crawler và browser nhận được URL semantics, HTTP status, canonical relationship và rendered content nhất quán.

Mental model quan trọng: crawler là một client của hệ thống. Nó suy luận site structure từ URL, links, redirects, status codes, canonical tags và renderable content. Đây là protocol/application behavior, không chỉ marketing metadata.

## 2. Why does it exist?

Một product có thể được truy cập bằng nhiều URLs:

```text
/products/123
/products/123?utm_source=x
/category/shoes/products/123
/Products/123
```

Nếu tất cả trả `200` và tự nhận là canonical, search engine có thể coi đây là duplicate representations, chia signals và crawl budget.

Redirect/status code sai còn tệ hơn: soft-404 trả `200`, deleted page redirect về homepage, hoặc redirect chain dài làm crawler/user tốn thêm round trips.

## 3. How does it work?

```text
Request old URL
   |
   v
301/308 redirect
   |
   v
Canonical URL
   |
   v
200 representation
   |
   +--> <link rel="canonical" ...>
   +--> internal links use canonical URL
   +--> sitemap lists canonical URL
```

Các signals nên đồng thuận. Canonical tag không phải magic override cho redirect/internal-link architecture lộn xộn.

## 4. Practical implementation

ASP.NET Core redirect:

```csharp
app.MapGet("/legacy-products/{id:int}", (int id) =>
    Results.Redirect($"/products/{id}", permanent: true));
```

Razor canonical:

```html
<link rel="canonical" href="https://www.example.com/products/@Model.Slug" />
```

Deleted resource nên phản ánh semantics thực:

```csharp
if (product is null)
    return Results.NotFound();
```

Không nên trả `200` với HTML “Product not found” chỉ để UI đẹp.

## 5. Real production scenario

CMS migration đổi URL từ `/insights/2025/article-name` sang `/articles/article-name`. Team chỉ update navigation nhưng không tạo permanent redirect map cho backlinks cũ.

Users từ search gặp 404, search engine phải rediscover structure, external link equity bị mất. Một redirect registry/versioned migration plan là technical requirement, không phải việc “SEO team xử lý sau”.

## 6. Failure scenario & troubleshooting

**Symptom** → search index chứa nhiều duplicate URLs hoặc organic traffic giảm sau CMS migration.

**Evidence** → crawler logs cho thấy redirect chains, canonical targets không khớp sitemap, URLs có query tracking được self-canonicalize sai.

**Hypothesis** → URL normalization/canonical contract không nhất quán.

**Diagnosis** → crawl site, inspect HTTP status + `Location`, canonical tags, sitemap, internal links và server logs.

**Fix** → chọn canonical URL policy, direct permanent redirects, normalize internal links, sửa sitemap và status semantics.

**Verification** → crawl lại: một logical resource có một canonical destination, không redirect chain, deleted pages trả đúng 404/410 theo policy.

## 7. Common mistakes

* Mọi missing page trả `200` với error UI.
* Redirect toàn bộ deleted URLs về homepage.
* Multiple-hop redirect chains sau nhiều migrations.
* Canonical URL trỏ sang page trả redirect/404.
* Sitemap chứa non-canonical URLs.
* JavaScript-only critical content mà không verify crawler rendering behavior.

## 8. Alternatives

Không có một “SEO framework” thay thế HTTP correctness. SSR/static rendering có thể giúp crawlability cho content-heavy site; CSR vẫn có thể phù hợp nếu rendering/indexing requirements được validate.

## 9. Trade-offs

### Advantages

* URL contract rõ giúp crawler, analytics và users nhất quán.
* Permanent redirects bảo vệ migration compatibility.
* Correct status codes cải thiện monitoring ngoài SEO.

### Costs / Risks

* Redirect map cần lifecycle lâu dài.
* URL normalization có thể ảnh hưởng backward compatibility.
* SSR/canonical generation multi-locale/multi-domain tăng complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `200`, `301/308`, `404` mang semantics khác nhau và canonical URL là preferred representation.

### Middle

Biết implement redirects, canonical tags, sitemap và test bằng HTTP tools/crawler.

### Senior

Thiết kế URL normalization, migration redirect strategy, locale/query handling và monitoring crawl failures.

### Technical Lead / Architect

Đưa URL compatibility vào CMS/platform architecture, xác định ownership giữa engineering/content/SEO và đảm bảo migrations có rollback + redirect plan.

## 11. Key takeaway

* Technical SEO bắt đầu từ HTTP và URL semantics đúng.
* Canonical, redirects, sitemap và internal links phải kể cùng một câu chuyện.
* URL migration là compatibility change của production system, không chỉ content task.
