# 1. C# `Task.WhenAll`: exception semantics, fan-out và bounded concurrency

## 1. What is it?

`Task.WhenAll` tạo một task đại diện cho việc hoàn thành của nhiều task. Mental model quan trọng: nó giúp **đồng bộ hóa completion**, nhưng không tự giới hạn concurrency, không tạo retry policy và không biến một tập operation thành transaction.

## 2. Why does it exist?

Khi nhiều I/O độc lập có thể chạy đồng thời, chờ tuần tự làm tổng latency gần bằng tổng latency từng dependency. `Task.WhenAll` cho phép overlap thời gian chờ. Tuy nhiên fan-out không kiểm soát có thể chuyển latency optimization thành dependency overload.

## 3. How does it work?

Các task thường đã bắt đầu khi được đưa vào `WhenAll`. Task tổng chỉ hoàn thành khi tất cả task con hoàn thành. Nếu nhiều task fault, task tổng giữ nhiều exception; `await` thường ném một exception đại diện, nên khi điều tra batch failure cần quan sát từng task hoặc `Exception` của task tổng.

## 4. Practical implementation

```csharp
var tasks = ids.Select(id => client.GetAsync($"items/{id}", ct)).ToArray();
try
{
    var responses = await Task.WhenAll(tasks);
}
catch
{
    foreach (var task in tasks.Where(t => t.IsFaulted))
        logger.LogError(task.Exception, "Fan-out request failed");
    throw;
}
```

Với hàng nghìn item, dùng `Parallel.ForEachAsync` với `MaxDegreeOfParallelism`, `SemaphoreSlim`, hoặc `Channel<T>` thay vì tạo hàng nghìn outbound requests cùng lúc.

## 5. Real production scenario

Product API cần lấy price, inventory và review từ ba dependency độc lập. Chạy song song có thể giảm latency từ gần tổng ba call xuống gần dependency chậm nhất. Nhưng batch endpoint 5.000 products không nên fan-out 15.000 calls không giới hạn.

## 6. Failure scenario & troubleshooting

**Symptom:** p99 tăng và upstream trả 429 sau khi “tối ưu bằng WhenAll”. → **Evidence:** outbound concurrency và socket count tăng mạnh. → **Hypothesis:** unbounded fan-out. → **Diagnosis:** trace cho thấy hàng trăm request bắt đầu cùng lúc. → **Fix:** concurrency limit + timeout budget. → **Verification:** throughput ổn định, 429 và p99 giảm.

## 7. Common mistakes

Nhầm concurrency với parallel CPU execution; tạo task trước rồi mới đặt semaphore sai chỗ; bỏ qua cancellation; chỉ log exception đầu tiên; retry toàn batch dù chỉ một phần thất bại.

## 8. Alternatives

Chờ tuần tự phù hợp khi operation phụ thuộc nhau. `Parallel.ForEachAsync` phù hợp batch có giới hạn concurrency. `Channel<T>` phù hợp producer/consumer dài hạn.

## 9. Trade-offs

### Advantages

Giảm wall-clock latency cho I/O độc lập và code composition đơn giản.

### Costs / Risks

Tăng pressure lên connection pool, rate limit và downstream; failure aggregation khó quan sát hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `WhenAll` chờ nhiều task và không đồng nghĩa tạo thread mới.

### Middle

Biết cancellation, exception handling và giới hạn concurrency.

### Senior

Đánh giá fan-out amplification, rate limit, timeout budget và partial failure.

### Technical Lead / Architect

Quyết định khi nào synchronous fan-out còn phù hợp và khi nào nên chuyển batch sang queue/asynchronous workflow.

## 11. Key takeaway

- `Task.WhenAll` là completion coordination, không phải concurrency control.
- Tối ưu latency phải đi cùng giới hạn fan-out.
- Quan sát toàn bộ failure set, không chỉ exception được `await` ném ra.

# 2. ASP.NET Core Health Checks: readiness, liveness và dependency health không phải cùng một tín hiệu

## 1. What is it?

Health check là tín hiệu machine-readable cho platform biết process có sống và có sẵn sàng nhận traffic hay không. `liveness` trả lời “process có cần restart không?”, còn `readiness` trả lời “instance có nên nhận request mới không?”.

## 2. Why does it exist?

Một HTTP 200 từ root endpoint không chứng minh application đã warm-up, load configuration hoặc sẵn sàng phục vụ. Ngược lại, database tạm timeout không nhất thiết có nghĩa process phải restart.

## 3. How does it work?

Platform gọi endpoint theo probe policy. Liveness failure có thể trigger restart; readiness failure thường loại instance khỏi load balancing. Dependency checks phải được phân loại để tránh biến outage của SQL thành restart storm của toàn bộ application fleet.

## 4. Practical implementation

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<SelfHealthCheck>("self", tags: ["live"])
    .AddCheck<DatabaseReadyCheck>("database", tags: ["ready"]);

app.MapHealthChecks("/health/live", new() {
    Predicate = r => r.Tags.Contains("live")
});
app.MapHealthChecks("/health/ready", new() {
    Predicate = r => r.Tags.Contains("ready")
});
```

## 5. Real production scenario

Một App Service/container vừa start cần load metadata trong 20 giây. Readiness giữ traffic lại đến khi warm-up hoàn tất; liveness vẫn healthy để platform không restart process đang khởi động hợp lệ.

## 6. Failure scenario & troubleshooting

**Symptom:** SQL outage khiến toàn bộ pods restart liên tục. → **Evidence:** liveness endpoint kiểm tra SQL. → **Diagnosis:** dependency health bị gắn sai semantics. → **Fix:** liveness chỉ kiểm tra process-critical state; dependency readiness được thiết kế theo khả năng phục vụ. → **Verification:** SQL outage không còn gây restart loop.

## 7. Common mistakes

Dùng cùng endpoint cho mọi probe; thực hiện query nặng; trả chi tiết secret/connection string; coi mọi dependency degraded là unhealthy; không đặt timeout cho health check.

## 8. Alternatives

Platform-specific probes có thể dùng TCP/process checks, nhưng application-level readiness cung cấp semantic tốt hơn về khả năng phục vụ.

## 9. Trade-offs

### Advantages

Tự động traffic management và phát hiện startup/failure state.

### Costs / Risks

Probe sai semantics có thể khuếch đại incident và tạo load bổ sung lên dependency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt alive và ready.

### Middle

Implement endpoint, tags, timeout và test failure behavior.

### Senior

Thiết kế dependency health tránh restart cascade và false positive.

### Technical Lead / Architect

Định nghĩa health contract theo failure model, load balancer và deployment strategy của hệ thống.

## 11. Key takeaway

- Liveness không phải dependency check tổng hợp.
- Readiness quyết định traffic; liveness quyết định restart.
- Probe là control-plane signal nên sai semantics có thể làm incident nặng hơn.

# 3. EF Core Interceptors: cross-cutting persistence behavior mà không làm repository phình to

## 1. What is it?

EF Core interceptor là extension point quan sát hoặc can thiệp vào operation như command execution, connection, transaction và `SaveChanges`. Nó phù hợp cho behavior persistence-level thực sự cross-cutting.

## 2. Why does it exist?

Nếu mọi application service đều phải lặp audit metadata, query instrumentation hoặc policy persistence giống nhau, logic dễ phân tán. Interceptor tập trung behavior ở đúng persistence boundary.

## 3. How does it work?

EF Core phát callback trước/sau lifecycle event. Interceptor có thể quan sát, thay đổi hoặc suppress một số operation. Vì nó nằm dưới application use case, không nên nhét business decision cần context domain vào đây.

## 4. Practical implementation

```csharp
public sealed class AuditInterceptor(TimeProvider clock)
    : SaveChangesInterceptor
{
    public override InterceptionResult<int> SavingChanges(
        DbContextEventData data, InterceptionResult<int> result)
    {
        var now = clock.GetUtcNow();
        foreach (var e in data.Context!.ChangeTracker.Entries<IAuditable>()
                     .Where(x => x.State == EntityState.Modified))
            e.Entity.UpdatedAt = now;
        return result;
    }
}
```

Đăng ký interceptor với `DbContextOptionsBuilder.AddInterceptors(...)`.

## 5. Real production scenario

SaaS platform cần cập nhật `UpdatedAt` nhất quán cho hàng chục aggregate persistence mappings mà không phụ thuộc developer nhớ set field ở từng handler.

## 6. Failure scenario & troubleshooting

**Symptom:** save chậm bất thường. → **Evidence:** trace cho thấy thời gian trước SQL lớn. → **Hypothesis:** interceptor scan toàn ChangeTracker và gọi external API. → **Diagnosis:** persistence hook chứa I/O. → **Fix:** giữ interceptor deterministic/local; external effect dùng Outbox. → **Verification:** SaveChanges latency trở lại baseline.

## 7. Common mistakes

Ẩn business rule; gọi network trong `SavingChanges`; mutate entity ngoài phạm vi dự kiến; interceptor singleton giữ mutable state; dùng interceptor thay authorization.

## 8. Alternatives

Override `SaveChanges`, domain/application service explicit logic, database trigger. Chọn theo ownership: domain rule nên explicit; DB invariant có thể dùng constraint/trigger; telemetry phù hợp interceptor.

## 9. Trade-offs

### Advantages

Centralized, khó quên, bám đúng EF lifecycle.

### Costs / Risks

Behavior trở nên implicit; debugging khó nếu team không biết interceptor tồn tại.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết interceptor là hook quanh EF operation.

### Middle

Implement audit/telemetry đơn giản và test integration.

### Senior

Phân biệt cross-cutting persistence concern với domain behavior.

### Technical Lead / Architect

Quyết định policy nào được phép implicit ở persistence boundary và cách giữ observability/testability.

## 11. Key takeaway

- Interceptor tốt cho persistence concern, không phải nơi giấu business workflow.
- Tránh external I/O trong `SaveChanges` interceptor.
- Behavior implicit phải được test và documented rõ.

# 4. SQL Server Query Store: phát hiện plan regression thay vì đoán “database hôm nay chậm”

## 1. What is it?

Query Store lưu lịch sử query text, execution plans và runtime statistics theo thời gian. Nó giúp so sánh “trước” và “sau” khi một query đột nhiên chậm vì plan thay đổi.

## 2. Why does it exist?

Execution plan phụ thuộc statistics, parameter distribution, schema/index và optimizer decisions. Query text không đổi vẫn có thể chạy với plan khác sau deployment hoặc statistics update.

## 3. How does it work?

SQL Server ghi nhận query/plan/runtime stats vào Query Store. Khi latency regression xuất hiện, engineer có thể tìm query tăng duration/CPU/read, so sánh plan IDs và xác định regression thay vì chỉ nhìn current plan.

## 4. Practical implementation

```sql
SELECT TOP (20)
    qt.query_sql_text,
    p.plan_id,
    rs.avg_duration,
    rs.avg_logical_io_reads
FROM sys.query_store_query_text qt
JOIN sys.query_store_query q ON q.query_text_id = qt.query_text_id
JOIN sys.query_store_plan p ON p.query_id = q.query_id
JOIN sys.query_store_runtime_stats rs ON rs.plan_id = p.plan_id
ORDER BY rs.avg_duration DESC;
```

Đọc execution plan cùng logical reads, cardinality estimate và wait/locking evidence; không force plan chỉ vì plan cũ “trông nhanh hơn”.

## 5. Real production scenario

Sau release, order search p95 tăng từ 120 ms lên 4 s. Application code không đổi query. Query Store cho thấy plan mới chọn scan + hash join do estimate lệch sau data distribution thay đổi.

## 6. Failure scenario & troubleshooting

**Symptom:** CPU DB tăng sau statistics update. → **Evidence:** Query Store cho thấy plan ID mới và logical reads tăng 30x. → **Hypothesis:** plan regression. → **Diagnosis:** compare estimates/actual data distribution. → **Fix:** sửa query/index/statistics; plan forcing chỉ là mitigation có kiểm soát. → **Verification:** reads và p95 giảm ở workload thật.

## 7. Common mistakes

Chỉ xem average duration; force plan vĩnh viễn; bỏ qua blocking; không quản lý retention/storage; kết luận index thiếu trước khi xem access pattern.

## 8. Alternatives

Extended Events và Application Insights giúp correlation; actual execution plan giúp phân tích một execution. Query Store mạnh ở historical comparison.

## 9. Trade-offs

### Advantages

Có lịch sử regression và plan evolution ngay trong database.

### Costs / Risks

Tốn storage/overhead; plan forcing có thể đóng băng một quyết định không còn phù hợp khi dữ liệu thay đổi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu query text giống nhau có thể có plan khác nhau.

### Middle

Đọc Query Store, plan, logical reads và duration.

### Senior

Phân biệt plan regression với lock/I/O/app regression và chọn remediation đúng.

### Technical Lead / Architect

Thiết kế database observability, retention và runbook cho regression thay vì phụ thuộc DBA intuition.

## 11. Key takeaway

- Query performance là query → plan → I/O/locks → latency.
- Historical evidence quan trọng hơn current plan khi điều tra regression.
- Force plan là mitigation, không thay thế root-cause fix.

# 5. Redis cache invalidation ownership: cache-aside chỉ đơn giản khi ownership rõ ràng

## 1. What is it?

Cache invalidation ownership xác định component nào chịu trách nhiệm làm cached representation hết hiệu lực khi source-of-truth thay đổi. Cache-aside không tự giải quyết câu hỏi này.

## 2. Why does it exist?

TTL chỉ giới hạn thời gian stale tối đa; nó không bảo đảm người dùng thấy dữ liệu mới ngay sau write. Khi nhiều service cùng ghi dữ liệu nhưng chỉ một service biết cache key, stale-data bug trở thành vấn đề ownership.

## 3. How does it work?

Read path: cache → miss → database → cache. Write path cần strategy: invalidate after commit, update cache, publish integration event để cache owner invalidate, hoặc chấp nhận bounded staleness bằng TTL.

## 4. Practical implementation

```csharp
await db.SaveChangesAsync(ct);
await cache.RemoveAsync($"product:{product.Id}", ct);
```

Nếu write và cache nằm khác service, không thể tạo atomic transaction giữa SQL và Redis. Có thể phát event bằng Outbox rồi cache-owning service invalidate idempotently.

## 5. Real production scenario

CMS publish product description nhưng storefront giữ Redis cache 30 phút. Editor thấy “Published” trong CMS nhưng khách vẫn thấy nội dung cũ vì CMS không sở hữu storefront cache key.

## 6. Failure scenario & troubleshooting

**Symptom:** một số instance trả giá cũ. → **Evidence:** DB mới, Redis cũ. → **Hypothesis:** invalidation bị mất sau commit. → **Diagnosis:** log cho thấy Redis timeout sau DB commit. → **Fix:** bounded TTL hoặc durable invalidation event; không rollback business transaction chỉ vì cache unavailable. → **Verification:** chaos test Redis outage và đo stale window.

## 7. Common mistakes

Cache dữ liệu không chấp nhận stale; key design không version; invalidation trước DB commit; coi Redis là source of truth; retry cache operation vô hạn.

## 8. Alternatives

Không cache; `IMemoryCache` cho single-instance/local data; CDN cho HTTP representation; database optimization nếu bottleneck thật nằm ở query.

## 9. Trade-offs

### Advantages

Giảm latency và database load.

### Costs / Risks

Thêm consistency model, invalidation ownership, serialization và outage behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache có thể stale.

### Middle

Implement key/TTL/invalidation và fallback.

### Senior

Thiết kế stale tolerance, outage behavior và event-driven invalidation.

### Technical Lead / Architect

Quyết định cache có thực sự cần tồn tại, ai sở hữu nó và consistency contract với business.

## 11. Key takeaway

- TTL không thay thế ownership của invalidation.
- SQL + Redis không có atomic commit mặc định.
- Cache chỉ đáng tồn tại khi lợi ích lớn hơn consistency/operational cost.

# 6. Anti-Corruption Layer: bảo vệ domain model khỏi contract của hệ thống bên ngoài

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary dịch model/protocol của external hoặc legacy system sang model mà bounded context nội bộ hiểu. Nó bảo vệ domain language khỏi bị “nhiễm” bởi contract không thuộc quyền sở hữu của team.

## 2. Why does it exist?

Nếu external DTO đi xuyên application và domain, thay đổi field, enum hoặc semantics của vendor lan khắp codebase. Coupling không chỉ là technical schema mà còn là business meaning.

## 3. How does it work?

```text
External API -> Adapter/ACL -> Application model -> Domain
```

ACL sở hữu authentication, transport mapping, contract normalization và semantic translation. Domain không phụ thuộc vendor SDK. Data ownership vẫn ở bounded context tương ứng; ACL không tạo distributed transaction kỳ diệu.

## 4. Practical implementation

```csharp
public sealed class VendorCustomerAdapter(VendorClient client)
{
    public async Task<CustomerStatus> GetStatus(CustomerId id, CancellationToken ct)
    {
        var dto = await client.GetCustomerAsync(id.Value, ct);
        return dto.State switch
        {
            "A" => CustomerStatus.Active,
            "S" => CustomerStatus.Suspended,
            _ => CustomerStatus.Unknown
        };
    }
}
```

## 5. Real production scenario

E-commerce domain dùng `Availability`, trong khi ERP trả `ATP_CODE`, warehouse flags và magic values. ACL chuyển contract ERP thành business concept ổn định cho storefront.

## 6. Failure scenario & troubleshooting

**Symptom:** vendor thêm enum mới làm order bị reject. → **Evidence:** deserialization/mapping unknown value. → **Diagnosis:** ACL giả định enum đóng. → **Fix:** tolerant reader + explicit `Unknown` + telemetry. → **Verification:** contract test với payload mới.

## 7. Common mistakes

Chỉ rename DTO rồi gọi đó là ACL; để vendor exception/type lọt vào domain; duplicate business rules trong adapter; đặt ACL cho mọi internal class dù không có semantic boundary.

## 8. Alternatives

Direct integration đủ tốt khi contract đơn giản, ổn định và cùng ownership. Separate integration service phù hợp khi nhiều bounded contexts dùng chung protocol phức tạp.

## 9. Trade-offs

### Advantages

Change isolation, domain language sạch, testability và vendor replacement dễ hơn.

### Costs / Risks

Mapping code, duplicate representations và nguy cơ abstraction không cần thiết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain entity.

### Middle

Implement adapter và contract tests.

### Senior

Xác định semantic mismatch, failure mapping và retry boundary.

### Technical Lead / Architect

Quyết định boundary, ownership, communication pattern, deployment coupling và khi direct integration đơn giản hơn.

## 11. Key takeaway

- ACL bảo vệ semantics, không chỉ đổi tên field.
- Domain không nên phụ thuộc vendor contract khi hai model có ownership khác nhau.
- Chỉ thêm ACL khi change isolation thực sự có giá trị.

# 7. Azure Event Grid delivery semantics: event notification, retry và idempotent handler

## 1. What is it?

Azure Event Grid là event routing service phù hợp notification kiểu “một sự kiện đã xảy ra”. Nó không nên bị nhầm với queue workflow cần ordering/long processing semantics của Azure Service Bus.

## 2. Why does it exist?

Producer không nên biết mọi subscriber. Event Grid tách event publisher khỏi routing tới webhook, Azure Functions và các event handlers.

## 3. How does it work?

Publisher gửi event tới topic/system topic; Event Grid match subscription/filter rồi deliver. Delivery có retry và có thể duplicate, vì vậy handler phải idempotent. Networking, authentication và dead-letter destination cần được thiết kế rõ.

## 4. Practical implementation

```csharp
app.MapPost("/events/blob", async (CloudEvent evt, EventInbox inbox, CancellationToken ct) =>
{
    if (await inbox.ExistsAsync(evt.Id, ct)) return Results.Ok();
    await ProcessAsync(evt, ct);
    await inbox.MarkProcessedAsync(evt.Id, ct);
    return Results.Ok();
});
```

Trong workload quan trọng, dedup state và side effect phải có transaction boundary phù hợp; ví dụ ghi inbox + local DB effect trong cùng database transaction.

## 5. Real production scenario

Blob upload hoàn tất phát event để Function tạo thumbnail. Upload service không cần synchronous call image processor.

## 6. Failure scenario & troubleshooting

**Symptom:** thumbnail được tạo hai lần. → **Evidence:** cùng event ID được deliver nhiều lần. → **Hypothesis:** handler giả định exactly-once. → **Diagnosis:** retry xảy ra vì response timeout. → **Fix:** idempotency/inbox. → **Verification:** replay cùng event không tạo thêm side effect.

## 7. Common mistakes

Dùng Event Grid cho command yêu cầu strict processing; không cấu hình dead-letter; webhook không xác thực; handler làm công việc dài trước khi acknowledge; không monitor delivery failure.

## 8. Alternatives

Azure Service Bus cho durable business messaging, ordering/sessions và queue semantics; Storage Queue cho queue đơn giản; direct HTTP cho synchronous request/response.

## 9. Trade-offs

### Advantages

Loose coupling, filtering, managed routing và scale tốt cho event notification.

### Costs / Risks

At-least-once-like duplicate handling, eventual consistency, thêm monitoring và idempotency burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt event notification với synchronous API.

### Middle

Publish/subscribe, auth, retry và dead-letter.

### Senior

Thiết kế idempotency, failure recovery, metrics và network security.

### Technical Lead / Architect

Chọn Event Grid vs Service Bus dựa trên semantics, ownership, reliability, cost và operational model.

## 11. Key takeaway

- Event delivery có thể lặp; handler phải idempotent.
- Event Grid không phải universal message broker.
- Chọn messaging service theo delivery semantics, không theo tên “event”.

# 8. CI/CD database migration orchestration: deploy application và schema mà không tạo breaking window

## 1. What is it?

Migration orchestration là cách phối hợp schema change với application rollout để version cũ và mới có thể cùng tồn tại trong deployment window.

## 2. Why does it exist?

Rolling/Canary deployment luôn có giai đoạn nhiều application versions chạy đồng thời. Migration kiểu rename/drop column ngay lập tức có thể làm version cũ crash dù pipeline “deploy thành công”.

## 3. How does it work?

Dùng expand → migrate/backfill → switch application → contract. Pipeline: commit → build → test → immutable artifact → apply backward-compatible expansion → deploy → health validation → monitor → later cleanup.

## 4. Practical implementation

Thay vì:

```sql
EXEC sp_rename 'Orders.CustomerName', 'BuyerName', 'COLUMN';
```

Release A thêm `BuyerName` nullable, code tạm đọc fallback từ `CustomerName`; backfill; Release B chuyển write/read; chỉ khi không còn version cũ mới drop `CustomerName`.

## 5. Real production scenario

Octopus deploy 10 IIS nodes theo rolling strategy. Nếu migration drop column chạy trước node cuối cùng được nâng version, các node cũ bắt đầu trả 500.

## 6. Failure scenario & troubleshooting

**Symptom:** deployment 50% thì error rate tăng. → **Evidence:** old nodes báo invalid column. → **Diagnosis:** schema contract bị phá trước khi fleet converge. → **Fix:** rollback application nếu schema còn compatible; nếu destructive migration đã chạy, recovery khó hơn. → **Verification:** staging test với N và N+1 app versions cùng schema.

## 7. Common mistakes

Auto-run destructive migrations ở app startup; nhiều instances cùng migrate; migration không timeout/lock plan; không test rollback; artifact khác nhau giữa environments.

## 8. Alternatives

Maintenance window phù hợp hệ thống nhỏ chấp nhận downtime. Blue-Green vẫn cần schema compatibility nếu hai environments dùng chung DB.

## 9. Trade-offs

### Advantages

Giảm downtime và blast radius; rollback application dễ hơn.

### Costs / Risks

Temporary dual-schema complexity, backfill và cleanup cần discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu schema và app version có thể coexist.

### Middle

Viết backward-compatible migration và integration tests.

### Senior

Thiết kế rollout, backfill, lock/timeout và rollback.

### Technical Lead / Architect

Định nghĩa organization-wide migration policy, ownership và release gates theo data criticality.

## 11. Key takeaway

- Database schema là shared contract trong rolling deployment.
- Destructive change nên tách khỏi release giới thiệu replacement.
- “Migration chạy thành công” không đồng nghĩa release an toàn.

# 9. OpenTelemetry alert design: từ telemetry tới actionable alert thay vì alert fatigue

## 1. What is it?

Alert là decision rule biến telemetry thành hành động vận hành. Logs, metrics và traces cung cấp evidence; alert phải chỉ ra condition đáng phản ứng, không phải mọi anomaly nhỏ.

## 2. Why does it exist?

Dashboard cần con người nhìn. Production 24/7 cần cơ chế phát hiện degradation chủ động. Nhưng quá nhiều alert không actionable làm on-call bỏ qua cả tín hiệu quan trọng.

## 3. How does it work?

Metrics phát hiện nhanh: request rate, error rate, duration, saturation. Trace giúp localize dependency/path; logs cung cấp event context. Alert nên bám user impact/SLO và có window đủ chống transient noise.

## 4. Practical implementation

Ví dụ policy:

```text
Page: checkout 5xx ratio > 5% for 10m AND request rate > minimum traffic
Ticket: p95 > SLO for 30m
Dashboard only: single dependency timeout
```

OpenTelemetry attributes phải kiểm soát cardinality; không dùng `user.id` hoặc raw URL IDs làm metric labels.

## 5. Real production scenario

Checkout API có 200 transient 500s trong một phút khi deploy. Alert theo single error tạo hàng trăm notifications; alert theo error ratio + sustained window + traffic threshold phản ánh impact thật.

## 6. Failure scenario & troubleshooting

**Symptom:** on-call nhận 300 alerts nhưng không biết incident nào chính. → **Evidence:** nhiều alert cùng root cause SQL outage. → **Hypothesis:** alert theo component symptom thay vì service impact. → **Diagnosis:** thiếu dedup/dependency correlation. → **Fix:** page trên SLO symptom, dùng traces để tìm cause; secondary alerts phục vụ diagnosis. → **Verification:** incident drill tạo ít alert nhưng đủ evidence.

## 7. Common mistakes

Alert mọi exception; threshold không theo traffic; metric labels cardinality cao; không có runbook; alert không owner; page trên CPU dù user không bị ảnh hưởng.

## 8. Alternatives

Azure Monitor/Application Insights có thể là backend alerting; Prometheus/Grafana stack là lựa chọn khác. OpenTelemetry chuẩn hóa instrumentation/export, không tự thay thế alert backend.

## 9. Trade-offs

### Advantages

Phát hiện degradation sớm và kết nối logs + metrics + traces.

### Costs / Risks

Telemetry cost, cardinality, tuning effort và alert fatigue nếu policy kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt log, metric, trace và alert.

### Middle

Instrument request/dependency và tạo dashboard cơ bản.

### Senior

Thiết kế SLO-oriented alerts, cardinality và incident correlation.

### Technical Lead / Architect

Định nghĩa observability standards, ownership, retention/cost và paging philosophy toàn hệ thống.

## 11. Key takeaway

- Alert phải dẫn tới hành động, không chỉ báo “có dữ liệu lạ”.
- Metrics phát hiện; traces localize; logs giải thích chi tiết.
- Page theo user impact/SLO thường tốt hơn page theo mọi component symptom.

# 10. Optimizely CMS content cache: editorial freshness, invalidation và scale-out consistency

## 1. What is it?

CMS content cache giữ content đã load/render gần application để giảm repeated repository/database work. Trong Optimizely CMS, caching là phần của content delivery architecture, nhưng mental model chung vẫn là source content → cache → rendering/API.

## 2. Why does it exist?

Marketing site có read-heavy traffic và content thay đổi ít hơn số lần đọc. Không cache khiến mỗi page request lặp content lookup, composition và đôi khi search/external calls.

## 3. How does it work?

Content được publish tạo version mới; delivery nodes phải biết cached representation nào hết hiệu lực. Trong scale-out, invalidation cần lan tới các nodes hoặc cache layer chung. Ngoài CMS cache còn có browser/CDN cache; mỗi layer có freshness contract riêng.

## 4. Practical implementation

Ở custom component, cache key phải bao gồm content identity/version và dimensions ảnh hưởng output:

```csharp
var key = $"promo:{content.ContentLink.ID}:{content.Language.Name}:{content.ContentLink.WorkID}";
var html = await cache.GetOrCreateAsync(key, _ => RenderPromoAsync(content));
```

Không cache output personalized dưới key chỉ theo page ID. Với Optimizely, ưu tiên framework content caching/invalidation primitives trước khi tự tạo một Redis cache song song.

## 5. Real production scenario

Editor publish campaign block lúc 09:00. CMS node A nhận invalidation nhưng CDN vẫn cache HTML 15 phút. Editor thấy preview mới, một số khách vẫn thấy campaign cũ. Đây là multi-layer freshness issue, không chỉ “Optimizely cache lỗi”.

## 6. Failure scenario & troubleshooting

**Symptom:** nội dung mới xuất hiện không đồng nhất giữa users. → **Evidence:** origin node trả mới nhưng CDN HIT trả cũ. → **Hypothesis:** invalidation dừng ở CMS layer. → **Diagnosis:** kiểm tra content version, node, response cache headers và CDN cache key. → **Fix:** align publish workflow với purge/TTL strategy. → **Verification:** publish synthetic content và trace Browser → CDN → origin.

## 7. Common mistakes

Tự cache content mà bỏ qua framework invalidation; cache personalized content chung; TTL quá dài không gắn editorial SLA; purge toàn site mỗi publish; không phân biệt preview/editor và public delivery.

## 8. Alternatives

Không cache cho low-traffic admin surfaces; CDN cache cho public HTTP representation; Redis cho custom distributed derived data khi framework cache không đáp ứng use case.

## 9. Trade-offs

### Advantages

Giảm latency/origin load và tăng throughput cho read-heavy CMS.

### Costs / Risks

Freshness complexity, multi-layer invalidation và khó debug khi cache key/dimension sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CMS content có version và cache có thể stale.

### Middle

Biết content key, language/version, cache headers và invalidation.

### Senior

Điều tra Browser/CDN/CMS cache chain, personalization và scale-out behavior.

### Technical Lead / Architect

Định nghĩa freshness SLA, cache ownership, purge strategy, content delivery topology và khi custom cache là unnecessary complexity.

## 11. Key takeaway

- CMS caching phải gắn với content version và editorial freshness requirement.
- Scale-out và CDN tạo nhiều cache layers với ownership khác nhau.
- Trước khi thêm Redis/custom cache, hiểu framework cache và invalidation sẵn có.
