# 1. .NET ThreadPool starvation: khi async code vẫn làm API nghẽn

## 1. What is it?
ThreadPool starvation xảy ra khi application cần worker threads nhanh hơn ThreadPool có thể cung cấp. Mental model: async không tự động đồng nghĩa với non-blocking. Endpoint có thể khai báo async nhưng vẫn giữ thread bằng synchronous I/O, blocking wait hoặc CPU work dài.

## 2. Why does it exist?
ThreadPool tái sử dụng số lượng thread hữu hạn. I/O await đúng cách trả worker về pool; blocking call giữ worker trong lúc request mới tiếp tục xếp hàng.

## 3. How does it work?
Request → worker → blocking dependency → worker bị giữ → queue tăng → p95/p99 tăng. ThreadPool có thể inject thêm threads nhưng không tức thời, nên burst blocking work tạo latency spike dù CPU chưa bão hòa.

## 4. Practical implementation
~~~csharp
public async Task<IResult> GetAsync(CancellationToken ct)
{
    var result = await httpClient.GetStringAsync(url, ct);
    return Results.Ok(result);
}
~~~
Tránh Result/Wait. CPU-bound work lớn cần bounded concurrency hoặc background worker thay vì Task.Run tùy tiện trong request path.

## 5. Real production scenario
Checkout API có CPU 35% nhưng p99 vượt 8 giây sau deployment. Một SDK mới dùng synchronous network call trong middleware, khiến worker threads bị giữ.

## 6. Failure scenario & troubleshooting
Symptom → latency tăng, CPU chưa bão hòa. Evidence → ThreadPool queue length tăng và traces có khoảng chờ dài. Hypothesis → blocking work. Diagnosis → dotnet-counters + stack traces. Fix → async I/O end-to-end. Verification → queue length và tail latency giảm dưới cùng load.

## 7. Common mistakes
Dùng Result/Wait; bọc synchronous I/O bằng Task.Run; tăng min threads trước khi tìm root cause; bỏ CancellationToken; nhìn CPU thấp rồi kết luận không có capacity problem.

## 8. Alternatives
Nếu dependency chỉ có synchronous API, cô lập bằng queue/worker với bounded concurrency có thể an toàn hơn giữ trong request path.

## 9. Trade-offs
### Advantages
Async I/O phục vụ concurrency cao với ít workers.
### Costs / Risks
Async lan qua call chain; cancellation và exception flow cần thiết kế; CPU work vẫn cần capacity riêng.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Phân biệt thread, Task và asynchronous I/O.
### Middle
Viết async end-to-end và debug sync-over-async.
### Senior
Nhận diện starvation bằng metrics/traces thay vì đoán từ CPU.
### Technical Lead / Architect
Quyết định workload nào ở request path và workload nào phải chuyển sang worker; đặt concurrency budget.

## 11. Key takeaway
- async keyword không đảm bảo non-blocking.
- Queue length + traces quan trọng hơn CPU khi điều tra starvation.
- Đừng tăng thread count để che blocking dependency.

# 2. ASP.NET Core ProblemDetails: thiết kế error contract ổn định cho client

## 1. What is it?
ProblemDetails chuẩn hóa representation cho lỗi HTTP. Mental model: error response là public API contract, không phải nơi dump exception.

## 2. Why does it exist?
Nếu mỗi endpoint trả shape khác nhau, frontend/mobile/partners phải parsing theo từng lỗi. Contract ổn định giúp client phân biệt validation, conflict, authorization và transient failure.

## 3. How does it work?
Exception hoặc validation result được map thành HTTP status cùng type, title, status, detail, instance và extensions có kiểm soát.

## 4. Practical implementation
~~~csharp
builder.Services.AddProblemDetails();
app.UseExceptionHandler();

return Results.Problem(
    statusCode: 409,
    title: "Order state conflict",
    extensions: new Dictionary<string, object?> {
        ["code"] = "ORDER_STATE_CONFLICT"
    });
~~~
Machine code nên ổn định; detail không nên chứa dependency exception.

## 5. Real production scenario
Web, mobile và partner API cùng gọi Order API. Team đổi wording nhưng consumers vẫn hoạt động vì branch theo status + stable code.

## 6. Failure scenario & troubleshooting
Symptom → client coi lỗi là Unknown. Evidence → 409/422/503 có payload khác nhau. Diagnosis → error mapping phân tán. Fix → central mapping + documented taxonomy. Verification → contract tests kiểm tra status, content type và code.

## 7. Common mistakes
Trả 200 với success=false; expose stack trace; dùng 500 cho business conflict; parse message text; map mọi exception thành 400.

## 8. Alternatives
Custom envelope phù hợp legacy ecosystem nhưng tạo proprietary contract; ProblemDetails interoperable hơn.

## 9. Trade-offs
### Advantages
Client behavior, documentation và observability nhất quán.
### Costs / Risks
Cần governance cho error taxonomy và backward compatibility.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu status code và payload đều thuộc contract.
### Middle
Map validation/domain/infrastructure errors.
### Senior
Phân biệt retryable failure, conflict và caller error.
### Technical Lead / Architect
Định nghĩa taxonomy xuyên services mà không leak implementation.

## 11. Key takeaway
- Error contract là API contract.
- Stable machine code tốt hơn parse message.
- Không expose internal exception details.

# 3. EF Core split queries: tránh Cartesian explosion nhưng không che giấu N+1

## 1. What is it?
AsSplitQuery tải object graph bằng nhiều SQL queries thay vì một JOIN query lớn. Nó xử lý Cartesian explosion khi nhiều collection Include cùng xuất hiện.

## 2. Why does it exist?
Order có 20 Lines và 10 Notes có thể tạo 200 joined rows cho cùng root. Data transfer, materialization và memory tăng dù logical data nhỏ.

## 3. How does it work?
Single query JOIN collections; split query lấy root rồi collections riêng và EF ghép graph ở client.

## 4. Practical implementation
~~~csharp
var order = await db.Orders
    .Where(x => x.Id == id)
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .AsNoTracking()
    .SingleAsync(ct);
~~~
Nếu response chỉ cần vài fields, projection thường tốt hơn cả hai.

## 5. Real production scenario
CMS API include Blocks, Assets và Localizations; SQL trả hàng chục nghìn rows cho một page. Split query giảm duplicated rows; projection giảm dữ liệu sâu hơn.

## 6. Failure scenario & troubleshooting
Symptom → endpoint allocate nhiều memory. Evidence → generated SQL có sibling collection JOIN. Fix → đo projection/split query và round trips. Verification → compare logical reads, rows, allocations, latency.

## 7. Common mistakes
Bật split query global; nhầm với N+1; Include toàn graph vì tiện; bỏ qua consistency giữa nhiều queries.

## 8. Alternatives
Projection cho read API; explicit loading cho workflow có chủ đích; single query khi graph nhỏ và round-trip latency quan trọng.

## 9. Trade-offs
### Advantages
Giảm row multiplication và memory pressure.
### Costs / Risks
Nhiều round trips; dữ liệu có thể thay đổi giữa queries tùy isolation.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu Include biến thành SQL/data transfer.
### Middle
Đọc generated SQL và dùng projection.
### Senior
Đo Cartesian explosion, round trips và consistency.
### Technical Lead / Architect
Thiết kế read model/API contract để tránh graph quá rộng.

## 11. Key takeaway
- Include không miễn phí.
- Split query không giải mọi query problem.
- Projection thường tốt nhất cho read API.

# 4. SQL Server deadlock: đọc deadlock graph thay vì tăng timeout

## 1. What is it?
Deadlock là dependency cycle giữa transactions đang giữ và chờ locks. SQL Server chọn một victim để phá cycle.

## 2. Why does it exist?
Concurrent transactions cần locks để giữ consistency. Lock acquisition order khác nhau có thể tạo cycle dù từng query riêng lẻ nhanh.

## 3. How does it work?
Tx A lock Order 1 rồi chờ Order 2; Tx B lock Order 2 rồi chờ Order 1; SQL Server chọn victim và trả error 1205.

## 4. Practical implementation
~~~sql
BEGIN TRAN;
UPDATE Orders SET Status='Processing' WHERE Id=@LowerId;
UPDATE Orders SET Status='Processing' WHERE Id=@HigherId;
COMMIT;
~~~
Giữ ordering nhất quán; retry victim chỉ khi operation safe/idempotent và retry bounded.

## 5. Real production scenario
Hai workers process invoices theo order khác nhau. Peak load tạo 1205 dù database CPU bình thường.

## 6. Failure scenario & troubleshooting
Symptom → intermittent 1205. Evidence → Extended Events deadlock graph. Diagnosis → xác định processes/resources/statements/indexes. Fix → consistent ordering, transaction ngắn hơn, access path phù hợp. Verification → load test và deadlock count.

## 7. Common mistakes
Tăng timeout; thêm NOLOCK; retry vô hạn; chỉ nhìn victim; giữ transaction qua external HTTP call.

## 8. Alternatives
Snapshot-based isolation có thể giảm read/write blocking nhưng có semantics và tempdb cost riêng; optimistic concurrency giải loại conflict khác.

## 9. Trade-offs
### Advantages
Locking giữ transactional consistency.
### Costs / Risks
Contention, blocking, deadlock nếu transaction/access pattern kém.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Phân biệt blocking với deadlock.
### Middle
Giữ transaction nhỏ và xử lý 1205.
### Senior
Đọc deadlock graph và reason về lock order/index.
### Technical Lead / Architect
Thiết kế transaction boundaries và workload partitioning.

## 11. Key takeaway
- Deadlock là cycle, không phải chỉ query chậm.
- Deadlock graph là bằng chứng chính.
- Retry không thay root-cause fix.

# 5. Cosmos DB partition key: quyết định data distribution trước khi scale

## 1. What is it?
Partition key quyết định cách Cosmos DB phân phối logical items. Đây là topology decision nằm trong data model.

## 2. Why does it exist?
Distributed database cần chia data/throughput. Nếu traffic tập trung một key, tăng tổng RU không tự động chữa hot partition.

## 3. How does it work?
Items cùng logical key được colocate theo partition semantics. Point read có key route chính xác; cross-partition query phải fan out.

## 4. Practical implementation
~~~csharp
var item = await container.ReadItemAsync<Order>(
    orderId,
    new PartitionKey(customerId),
    cancellationToken: ct);
~~~
Chọn customerId chỉ khi access pattern, cardinality và traffic distribution phù hợp.

## 5. Real production scenario
SaaS partition theo TenantId nhưng một enterprise tenant tạo 60% traffic, gây hot partition.

## 6. Failure scenario & troubleshooting
Symptom → 429 tập trung một partition. Evidence → RU skew. Diagnosis → hot/low-cardinality key. Fix → redesign hoặc synthetic partitioning khi justified; respect Retry-After. Verification → distribution và 429 rate cải thiện.

## 7. Common mistakes
Chọn constant/type làm key; query không truyền key; coi autoscale là thuốc chữa hot key; thiết kế schema trước access patterns.

## 8. Alternatives
SQL/PostgreSQL phù hợp hơn nếu relational transactions và flexible joins là dominant requirement; MongoDB vẫn đòi hỏi distribution reasoning riêng.

## 9. Trade-offs
### Advantages
Scale-out và targeted routing tốt khi key phù hợp.
### Costs / Risks
Key khó đổi; key sai tạo operational ceiling và migration khó.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu key quyết định data placement.
### Middle
Dùng key cho point reads và đo RU.
### Senior
Phân tích cardinality/skew/access pattern.
### Technical Lead / Architect
Quyết định workload có phù hợp Cosmos DB và migration cost nếu key sai.

## 11. Key takeaway
- Partition key là architectural decision.
- Scale tổng không chữa hot partition.
- Model theo access pattern.

# 6. Azure Service Bus dead-letter queue: poison message, retry và recovery workflow

## 1. What is it?
DLQ giữ messages không thể xử lý bình thường. Nó là failure-isolation boundary, không phải thùng rác tự dọn.

## 2. Why does it exist?
At-least-once messaging cần ngăn poison message retry vô hạn, tiêu compute và chặn throughput.

## 3. How does it work?
Message được abandon/retry; vượt MaxDeliveryCount hoặc dead-letter explicit thì chuyển DLQ cùng reason/metadata.

## 4. Practical implementation
~~~csharp
catch (InvalidPayloadException ex)
{
    await receiver.DeadLetterMessageAsync(
        message, "InvalidPayload", ex.Message, ct);
}
~~~
Transient error retry bounded; permanent schema/business error dead-letter rõ lý do.

## 5. Real production scenario
Producer deploy schema mới, consumer rollback và không deserialize được. Messages vào DLQ thay vì tạo retry storm.

## 6. Failure scenario & troubleshooting
Symptom → DLQ tăng. Evidence → reason + producer version correlation. Diagnosis → contract incompatibility. Fix → compatible consumer + idempotent replay tool. Verification → replay subset rồi drain có kiểm soát.

## 7. Common mistakes
Không alert DLQ; auto replay vô hạn; mất correlation ID; retry validation error; purge để hết alert.

## 8. Alternatives
Storage quarantine riêng hợp workflow audit phức tạp; DLQ tích hợp broker lifecycle tốt hơn.

## 9. Trade-offs
### Advantages
Cô lập poison message, giữ evidence.
### Costs / Risks
Cần monitoring, owner, replay tooling, retention policy.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu complete/abandon/dead-letter.
### Middle
Phân loại transient vs permanent.
### Senior
Thiết kế idempotent replay và observability.
### Technical Lead / Architect
Định nghĩa ownership, recovery SLA và schema evolution.

## 11. Key takeaway
- DLQ cần owner và runbook.
- Retry permanent error chỉ tạo load.
- Replay phải idempotent.

# 7. Managed Identity + Key Vault: bỏ credential khỏi application configuration

## 1. What is it?
Managed Identity cho Azure workload lấy Entra token mà không lưu client secret. Key Vault giữ secret/key/certificate khi application vẫn cần secret material.

## 2. Why does it exist?
Secret trong appsettings, pipeline hoặc environment có rotation/leakage risk. Identity-based access giảm credential phải phân phối.

## 3. How does it work?
App Service → Managed Identity → Entra token → Key Vault authorization → secret. Quyền phải least-privilege.

## 4. Practical implementation
~~~csharp
var client = new SecretClient(
    new Uri(vaultUri),
    new DefaultAzureCredential());

var secret = await client.GetSecretAsync(
    "PartnerApiKey", cancellationToken: ct);
~~~

## 5. Real production scenario
App Service cần legacy payment API key. Managed Identity chỉ được đọc vault scope cần thiết; payment key vẫn ở Key Vault vì provider chưa hỗ trợ federation.

## 6. Failure scenario & troubleshooting
Symptom → production 403, local chạy. Evidence → local developer identity khác production Managed Identity. Diagnosis → role/network/private endpoint. Fix → grant tối thiểu đúng principal + kiểm tra DNS/network. Verification → vault audit logs.

## 7. Common mistakes
Nghĩ Managed Identity loại bỏ mọi secret; cấp Contributor rộng; log secret; fetch secret mỗi request; không thiết kế rotation.

## 8. Alternatives
Workload identity/federation hợp Kubernetes/container scenarios. Environment secret đơn giản hơn nhưng rotation/audit yếu.

## 9. Trade-offs
### Advantages
Không quản lý workload client secret; audit tốt.
### Costs / Risks
Identity/network config phức tạp; Key Vault trở thành dependency.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Phân biệt identity và secret storage.
### Middle
Cấu hình credential chain/RBAC.
### Senior
Debug principal, vault network, rotation.
### Technical Lead / Architect
Quyết định secret nào còn cần tồn tại và failure behavior khi vault unavailable.

## 11. Key takeaway
- Managed Identity không loại bỏ mọi secret.
- Least privilege phải gắn đúng principal.
- Identity + network + policy cùng nằm trong failure path.

# 8. OpenTelemetry metrics và SLO: từ telemetry thành reliability decision

## 1. What is it?
Metrics đo hệ thống theo thời gian; SLO đặt reliability target có thể đo. Telemetry có giá trị khi trả lời user experience có đạt mục tiêu không.

## 2. Why does it exist?
CPU/memory/request count không tự nói service có đáng tin cậy. SLO buộc team chọn indicator gắn với user impact.

## 3. How does it work?
Ví dụ SLI: tỷ lệ request thành công dưới 500 ms. SLO: 99.9% trong 30 ngày. Error budget là phần không đạt được phép.

## 4. Practical implementation
~~~csharp
static readonly Meter Meter = new("Checkout.Api");
static readonly Histogram<double> Duration =
    Meter.CreateHistogram<double>("checkout.duration", "ms");

Duration.Record(sw.Elapsed.TotalMilliseconds);
~~~
Không dùng userId làm metric label vì high cardinality.

## 5. Real production scenario
Average latency 180 ms nhưng p99 >4 giây do payment dependency. Tail metrics/SLO cho thấy user impact bị average che khuất.

## 6. Failure scenario & troubleshooting
Symptom → monitoring cost tăng. Evidence → series explosion vì labels chứa IDs. Fix → bounded dimensions, route templates, trace sampling phù hợp. Verification → series count giảm mà SLI vẫn đo được.

## 7. Common mistakes
Alert mọi metric; dùng average; high-cardinality labels; chọn SLO theo khẩu hiệu; nhầm SLA với SLO.

## 8. Alternatives
Application Insights/Azure Monitor vẫn là backend tốt; OpenTelemetry cung cấp instrumentation portability chứ không thay backend analysis.

## 9. Trade-offs
### Advantages
Reliability đo được và gắn engineering priority.
### Costs / Risks
Instrumentation/storage cost và governance.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Phân biệt logs, metrics, traces.
### Middle
Instrument latency/error đúng labels.
### Senior
Thiết kế SLI và correlate với traces.
### Technical Lead / Architect
Chọn SLO phản ánh business impact và dùng error budget để cân reliability/delivery.

## 11. Key takeaway
- Metric phải hỗ trợ quyết định.
- Tail latency quan trọng hơn average trong nhiều hệ thống.
- SLO nối user experience với engineering priorities.

# 9. Playwright E2E testing: bảo vệ critical journey mà không tạo test suite mong manh

## 1. What is it?
Playwright điều khiển browser thật để kiểm tra behavior xuyên UI, network và backend. E2E bảo vệ integration seams mà unit test không thấy.

## 2. Why does it exist?
Login/checkout/approval có thể fail do cookies, CORS, routing, rendering hoặc deployment dù component tests đều pass.

## 3. How does it work?
Test tương tác qua stable locators, chờ browser state và assert observable behavior thay vì DOM implementation details.

## 4. Practical implementation
~~~typescript
test('manager approves timesheet', async ({ page }) => {
  await page.goto('/timesheets/42');
  await page.getByRole('button', { name: 'Approve' }).click();
  await expect(page.getByText('Approved')).toBeVisible();
});
~~~

## 5. Real production scenario
Backend đổi cookie SameSite; API tests xanh nhưng browser login redirect loop. Smoke E2E trên deployed environment bắt regression trước promotion.

## 6. Failure scenario & troubleshooting
Symptom → flaky CI. Evidence → fixed sleeps và brittle CSS selectors. Fix → role/test-id locators, web-first assertions, deterministic data. Verification → repeated parallel runs ổn định.

## 7. Common mistakes
E2E mọi edge case; waitForTimeout; shared mutable account; mock quá nhiều; coi flaky là bình thường.

## 8. Alternatives
Unit tests cho logic; integration/API tests cho backend; contract tests cho boundaries. E2E chỉ nên bảo vệ critical journeys.

## 9. Trade-offs
### Advantages
Confidence cao cho real user flow.
### Costs / Risks
Chậm, đắt, khó isolate failure, dễ flaky nếu thiết kế kém.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Viết locator/assertion ổn định.
### Middle
Quản lý fixtures/auth/test data.
### Senior
Chọn risk cần E2E và debug cross-layer failure.
### Technical Lead / Architect
Thiết kế test portfolio thay vì đẩy mọi coverage lên browser.

## 11. Key takeaway
- E2E bảo vệ journey, không thay unit/integration.
- Test observable behavior.
- Flakiness là engineering defect.

# 10. .NET Framework → modern .NET: incremental modernization thay vì big-bang rewrite

## 1. What is it?
Modernization là di chuyển runtime, hosting, dependencies và boundaries từ .NET Framework sang modern .NET trong khi giữ business continuity. Nó không đồng nghĩa rewrite.

## 2. Why does it exist?
Legacy app thường phụ thuộc System.Web, Windows-only libraries, old EF, IIS assumptions và packages cũ. Big-bang rewrite tạo migration risk lớn và thời gian dài không tạo business value.

## 3. How does it work?
Inventory dependencies → characterization tests → isolate portable code → migrate một boundary → observe → chuyển traffic → retire legacy slice.

## 4. Practical implementation
~~~xml
<TargetFrameworks>net48;net8.0</TargetFrameworks>
~~~
Multi-targeting chỉ nên là transition technique khi dependencies hỗ trợ; không biến nó thành permanent complexity.

## 5. Real production scenario
Enterprise CMS .NET Framework có jobs và integrations. Team tách pricing capability sang .NET 8 trước, chuyển từng consumer thay vì rewrite CMS cùng lúc.

## 6. Failure scenario & troubleshooting
Symptom → tests pass nhưng production behavior khác. Evidence → serialization, culture, TLS hoặc configuration defaults khác. Diagnosis → golden request/response comparison. Fix → explicit compatibility/version contract. Verification → shadow comparison trước cutover.

## 7. Common mistakes
Rewrite vì code xấu; upgrade runtime và architecture cùng lúc; bỏ undocumented behavior; không rollback; dual-target vô hạn; kiểm tra dependency compatibility quá muộn.

## 8. Alternatives
In-place upgrade khi app nhỏ; strangler migration khi boundary rõ; giữ legacy có chủ đích nếu migration cost vượt risk/value.

## 9. Trade-offs
### Advantages
Supportability, performance và ecosystem hiện đại.
### Costs / Risks
Migration effort, temporary duplication, behavior drift và transition complexity.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu runtime/framework compatibility và regression tests.
### Middle
Migrate library/service nhỏ và configuration.
### Senior
Tìm hidden coupling, compatibility risk, cutover telemetry.
### Technical Lead / Architect
Chọn boundary, sequencing, rollback và quyết định phần nào chưa nên migrate.

## 11. Key takeaway
- Modernization là risk-management problem.
- Characterization tests + observability bảo vệ behavior.
- Incremental migration thường giảm blast radius hơn big-bang rewrite.
