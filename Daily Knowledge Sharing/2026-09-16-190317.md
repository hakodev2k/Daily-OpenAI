# 1. .NET `Channel<T>`: bounded backpressure thay vì queue vô hạn trong process

## 1. What is it?

`Channel<T>` là abstraction producer/consumer asynchronous trong .NET. Mental model quan trọng không phải “một `ConcurrentQueue` async”, mà là một **capacity boundary** giữa tốc độ producer và consumer. Với bounded channel, hệ thống có thể buộc producer chờ khi consumer không theo kịp.

## 2. Why does it exist?

Một queue vô hạn che giấu overload bằng cách tích lũy work trong memory. Latency tăng dần, heap phình ra rồi process có thể chết. Backpressure làm overload xuất hiện sớm tại boundary thay vì biến thành memory incident muộn hơn.

## 3. How does it work?

```text
Producers -> bounded Channel -> Consumers
                 |
                 +-- full -> Wait / Drop policy
```

`ChannelWriter.WriteAsync` có thể suspend khi capacity đầy. Consumer đọc bằng `ReadAllAsync`. Full mode quyết định wait, drop newest hoặc drop oldest.

## 4. Practical implementation

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = false
});

await channel.Writer.WriteAsync(job, cancellationToken);

await foreach (var item in channel.Reader.ReadAllAsync(stoppingToken))
{
    await processor.ProcessAsync(item, stoppingToken);
}
```

Capacity phải dựa trên acceptable queueing delay và throughput, không chọn số lớn chỉ để “không full”.

## 5. Real production scenario

API nhận image-processing requests nhanh hơn worker xử lý. Unbounded in-memory queue giữ hàng chục nghìn payload references và GC pressure tăng. Bounded channel giới hạn outstanding work; API có thể chờ ngắn hoặc từ chối theo capacity policy.

## 6. Failure scenario & troubleshooting

**Symptom** → request enqueue latency tăng. **Evidence** → channel depth gần capacity, consumer throughput thấp. **Hypothesis** → downstream processor là bottleneck. **Diagnosis** → đo processing duration và dependency latency. **Fix** → tăng consumer capacity nếu downstream chịu được, giảm producer rate hoặc chuyển sang durable broker. **Verification** → queue depth và p95 ổn định dưới sustained load.

## 7. Common mistakes

Dùng unbounded channel mặc định; enqueue object lớn; coi in-memory channel là durable messaging; không gọi `TryComplete`; tăng số consumers mà bỏ qua database/API downstream capacity.

## 8. Alternatives

`ConcurrentQueue<T>` phù hợp khi không cần async waiting/backpressure. Azure Service Bus phù hợp khi cần durability, retry và cross-process delivery. `Channel<T>` tốt cho coordination nội bộ process.

## 9. Trade-offs

### Advantages

API async rõ ràng, backpressure có chủ đích, throughput tốt.

### Costs / Risks

Work mất khi process chết; capacity tuning cần measurement; drop policy có thể làm mất dữ liệu nếu business không cho phép.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu producer/consumer và bounded capacity.
### Middle
Implement reader/writer, cancellation và completion đúng.
### Senior
Đo throughput, queue delay và downstream saturation trước khi scale consumers.
### Technical Lead / Architect
Quyết định boundary nào chỉ cần in-process coordination và boundary nào cần durable broker.

## 11. Key takeaway

- Backpressure là cơ chế reliability, không chỉ performance.
- Queue dài không tạo thêm throughput.
- `Channel<T>` không thay thế durable messaging.

# 2. ASP.NET Core response streaming: giảm memory nhưng kéo dài resource lifetime

## 1. What is it?

Streaming gửi response từng phần thay vì materialize toàn bộ payload trước khi ghi ra network. Nó giảm peak memory và time-to-first-byte nhưng làm request sống lâu hơn.

## 2. Why does it exist?

Export hàng trăm nghìn rows thành một `List<T>` rồi serialize có thể tạo allocation lớn và LOH/GC pressure. Streaming cho phép pipeline đọc → serialize → gửi theo nhịp.

## 3. How does it work?

```text
Database cursor -> serializer -> response body -> network
```

Backpressure từ network có thể làm `WriteAsync` chậm; vì vậy database reader hoặc resource upstream có thể bị giữ lâu hơn dự kiến.

## 4. Practical implementation

```csharp
app.MapGet("/orders/export", async (AppDbContext db, HttpResponse response, CancellationToken ct) =>
{
    response.ContentType = "application/x-ndjson";

    await foreach (var order in db.Orders
        .AsNoTracking()
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        await JsonSerializer.SerializeAsync(response.Body, order, cancellationToken: ct);
        await response.WriteAsync("\n", ct);
    }
});
```

## 5. Real production scenario

Admin export 500k orders. Materialization tạo memory spike; streaming giữ memory thấp nhưng một client mạng chậm có thể giữ SQL reader trong nhiều phút.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tốt hơn nhưng connection pool exhaustion xuất hiện. **Evidence** → long-lived requests đồng thời giữ DB connections. **Diagnosis** → streaming lifetime gắn trực tiếp database cursor với client speed. **Fix** → chunk/buffer theo page, tạo export background file hoặc giới hạn concurrency. **Verification** → connection hold time giảm và export vẫn ổn định.

## 7. Common mistakes

Cho rằng streaming luôn tốt hơn; không propagate cancellation; flush quá thường xuyên; stream trực tiếp từ DB cho download rất dài; không giới hạn export concurrency.

## 8. Alternatives

Buffered response đơn giản cho payload nhỏ. Background export ra Blob Storage tốt cho file lớn. Pagination phù hợp interactive API.

## 9. Trade-offs

### Advantages
Giảm peak memory, phản hồi sớm.
### Costs / Risks
Giữ request/resource lâu, error contract khó thay đổi sau khi headers/body đã gửi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu buffer toàn bộ khác streaming.
### Middle
Implement cancellation và async enumeration.
### Senior
Reason về connection lifetime, slow clients và partial response failure.
### Technical Lead / Architect
Chọn synchronous streaming hay asynchronous export dựa trên payload, SLA và resource isolation.

## 11. Key takeaway

- Streaming đổi memory pressure lấy resource lifetime complexity.
- Client chậm có thể trở thành server-side capacity problem.
- Export lớn thường nên tách khỏi request transaction path.

# 3. EF Core compiled queries: tối ưu query pipeline đúng chỗ thay vì chữa database latency sai chỗ

## 1. What is it?

Compiled query cho phép EF Core tái sử dụng query compilation delegate cho query shape chạy rất thường xuyên. Nó tối ưu CPU overhead phía EF, không làm SQL execution hoặc network I/O tự nhanh hơn.

## 2. Why does it exist?

EF phải xử lý expression tree, translation và query cache lookup. Trong hot path rất nhỏ nhưng tần suất cực cao, overhead này có thể đáng kể sau khi database đã được tối ưu.

## 3. How does it work?

Query shape cố định được compile thành delegate; parameters thay đổi nhưng pipeline translation có thể được reuse hiệu quả hơn.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, int, Task<Order?>> FindOrder =
    EF.CompileAsyncQuery((AppDbContext db, int id) =>
        db.Orders.AsNoTracking().SingleOrDefault(x => x.Id == id));

var order = await FindOrder(db, orderId);
```

Chỉ áp dụng sau profiling.

## 5. Real production scenario

Lookup endpoint chạy hàng chục nghìn lần/giây, SQL mất 2 ms nhưng application CPU cao. Profiling cho thấy query pipeline overhead có ý nghĩa. Compiled query có thể giúp; nếu SQL mất 300 ms thì đây gần như không phải đòn bẩy chính.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries nhưng p95 gần như không đổi. **Evidence** → trace cho thấy phần lớn thời gian nằm ở SQL I/O. **Diagnosis** → tối ưu sai layer. **Fix** → execution plan/access pattern trước; benchmark EF overhead riêng. **Verification** → CPU/request và latency breakdown thay đổi đo được.

## 7. Common mistakes

Compile mọi query; bỏ qua projection/index; benchmark bằng unrealistic in-memory setup; làm code khó đọc để tiết kiệm microseconds không đáng kể.

## 8. Alternatives

EF query cache mặc định đủ cho đa số workloads. Raw SQL/Dapper có thể giảm ORM overhead hơn nhưng tăng mapping/maintenance cost.

## 9. Trade-offs

### Advantages
Giảm overhead trên hot path ổn định.
### Costs / Risks
Code ceremony và flexibility thấp hơn; lợi ích nhỏ nếu bottleneck là database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu EF translation khác SQL execution.
### Middle
Biết đo generated SQL và query duration.
### Senior
Profile CPU để xác nhận compilation overhead.
### Technical Lead / Architect
Giữ optimization policy evidence-driven thay vì biến compiled query thành convention.

## 11. Key takeaway

- Compiled query tối ưu ORM overhead, không tối ưu database plan.
- Đo bottleneck trước khi đổi abstraction.
- Readability cost phải được trả bằng lợi ích đo được.

# 4. SQL Server covering index: giảm lookup nhưng phải trả write amplification

## 1. What is it?

Covering index chứa đủ key và included columns để query lấy dữ liệu trực tiếp từ nonclustered index mà không cần Key Lookup về clustered index/base table.

## 2. Why does it exist?

Một seek chọn nhiều rows rồi lookup từng row có thể tạo random I/O lớn. Include columns có thể biến seek + thousands of lookups thành một index access hiệu quả hơn.

## 3. How does it work?

```text
Predicate -> Index Seek -> included output
```

Thay vì:

```text
Index Seek -> Key Lookup x N -> output
```

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_Customer_CreatedAt
ON dbo.Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, TotalAmount);
```

Query shape và selectivity phải được kiểm tra trong actual execution plan.

## 5. Real production scenario

Customer order history đọc `Status` và `TotalAmount` cho 50 rows gần nhất. Index chỉ có `(CustomerId, CreatedAt)` khiến lookup; include hai output columns loại lookup mà không làm chúng thành search keys.

## 6. Failure scenario & troubleshooting

**Symptom** → reads nhanh hơn nhưng write latency và storage tăng. **Evidence** → nhiều overlapping indexes, page writes cao. **Diagnosis** → over-indexing. **Fix** → consolidate/remove redundant indexes dựa trên workload evidence. **Verification** → read SLA giữ được trong khi write cost giảm.

## 7. Common mistakes

Include mọi column; nhầm key order với include; tạo index theo từng query mà không xét tổng workload; bỏ qua filtered index khi phù hợp.

## 8. Alternatives

Narrow index + lookup tốt khi chỉ vài rows. Projection nhỏ hơn có thể tránh cần cover. Columnstore phù hợp analytical workload khác bản chất.

## 9. Trade-offs

### Advantages
Giảm lookup và I/O cho read hot path.
### Costs / Risks
Tăng storage, cache footprint và write amplification.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu seek và lookup.
### Middle
Đọc actual plan và logical reads.
### Senior
Cân bằng read gain với write/storage cost.
### Technical Lead / Architect
Quản trị index như workload-level design, không phải query-by-query patching.

## 11. Key takeaway

- Covering index là workload trade-off.
- `INCLUDE` không thay thế đúng key order.
- Đo reads và write cost trước/sau.

# 5. MongoDB embedding vs referencing: thiết kế document theo access pattern và consistency boundary

## 1. What is it?

Embedding lưu related data trong cùng document; referencing lưu identity liên kết sang document khác. Quyết định này chủ yếu dựa trên access pattern, ownership, cardinality và update behavior.

## 2. Why does it exist?

Document database tối ưu aggregate-shaped access. Nếu model y hệt normalized relational schema, application có thể phải thực hiện nhiều round trips/joins phía client. Nhưng embedding vô hạn tạo document growth và duplication.

## 3. How does it work?

```text
Order { customer snapshot, lines[] }   <- embedded ownership
Order { customerId } -> Customer       <- referenced independent lifecycle
```

## 4. Practical implementation

Order line thường phù hợp embedding vì thuộc lifecycle của order; customer profile thường reference hoặc snapshot có chủ đích vì customer tồn tại độc lập.

```json
{
  "_id": "order-42",
  "customerId": "c-9",
  "shippingName": "Nguyen Van A",
  "lines": [{ "sku": "A1", "qty": 2, "unitPrice": 120000 }]
}
```

## 5. Real production scenario

E-commerce cần order history giữ tên/giá tại thời điểm mua. Snapshot embedded là đúng business history; join live Product/Customer cho mọi field có thể làm lịch sử thay đổi khi master data đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → document tăng rất lớn và update chậm. **Evidence** → unbounded embedded activity array. **Diagnosis** → child lifecycle/cardinality không phù hợp embedding. **Fix** → tách collection và query theo partition/access key. **Verification** → document size và update latency ổn định.

## 7. Common mistakes

Chọn embedding vì “MongoDB không join”; reference mọi thứ như SQL; duplicate dữ liệu mà không định nghĩa source of truth; embed unbounded collections.

## 8. Alternatives

Relational DB phù hợp khi relational constraints/ad-hoc joins là trọng tâm. MongoDB reference phù hợp independent aggregates; embedding phù hợp owned bounded data.

## 9. Trade-offs

### Advantages
Embedding giảm round trips và cho atomic update trong document.
### Costs / Risks
Duplication, document growth và synchronization nếu embedded data không phải snapshot.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu document ownership.
### Middle
Model theo read/write pattern.
### Senior
Reason về cardinality, atomicity và duplicated truth.
### Technical Lead / Architect
Chọn storage model dựa trên business boundary thay vì database fashion.

## 11. Key takeaway

- SQL vs NoSQL không phải structured vs unstructured.
- Embed khi data thực sự thuộc cùng aggregate/lifecycle.
- Duplication phải có semantics: snapshot hay synchronized copy.

# 6. Inbox Pattern: biến at-least-once delivery thành idempotent message processing

## 1. What is it?

Inbox Pattern lưu message identity đã xử lý ở consumer để duplicate delivery không tạo duplicate side effects. Nó bổ sung cho broker có at-least-once delivery.

## 2. Why does it exist?

Consumer có thể commit database rồi crash trước khi acknowledge message. Broker redeliver; nếu handler chạy lại không có deduplication, payment/order/email có thể thực hiện hai lần.

## 3. How does it work?

```text
Message -> transaction
           |- INSERT Inbox(MessageId)
           |- apply business change
           `- COMMIT
        -> Complete broker message
```

Unique constraint trên `MessageId` biến duplicate thành detectable state.

## 4. Practical implementation

```sql
CREATE TABLE InboxMessages (
    MessageId uniqueidentifier NOT NULL PRIMARY KEY,
    ProcessedAt datetime2 NOT NULL
);
```

Handler mở transaction, kiểm tra/insert inbox record và business mutation trong cùng local transaction.

## 5. Real production scenario

`OrderPaid` được Service Bus redeliver sau worker restart. Consumer shipment đã tạo shipment lần đầu. Inbox phát hiện message ID và bỏ qua side effect lần hai rồi complete message.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate business records dù broker message ID giống nhau. **Evidence** → dedup check và business write nằm ở hai transactions. **Diagnosis** → crash window giữa hai writes. **Fix** → atomic local transaction hoặc business operation tự idempotent. **Verification** → inject crash ở từng boundary và redeliver.

## 7. Common mistakes

Dedup trong memory; xóa inbox quá sớm; dùng payload hash không ổn định thay message identity; assume broker exactly-once; complete message trước commit.

## 8. Alternatives

Natural idempotency bằng business unique key thường đơn giản hơn. Inbox hữu ích khi generic message identity cần durable tracking.

## 9. Trade-offs

### Advantages
Recovery rõ ràng, duplicate-safe processing.
### Costs / Risks
Thêm storage, cleanup policy và transaction contention.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu duplicate delivery là bình thường.
### Middle
Implement unique message ID và transaction.
### Senior
Test crash windows, retention và poison-message behavior.
### Technical Lead / Architect
Chuẩn hóa idempotency contract giữa producers/consumers và quyết định nơi Inbox thực sự cần thiết.

## 11. Key takeaway

- At-least-once yêu cầu consumer nghĩ về duplicates.
- Deduplication state phải durable nếu side effect durable.
- Atomic boundary quan trọng hơn bản thân bảng Inbox.

# 7. Azure Front Door: edge routing, health probes và origin failure isolation

## 1. What is it?

Azure Front Door là global edge entry point cung cấp HTTP routing, acceleration, health-based origin selection và có thể kết hợp WAF/CDN capabilities.

## 2. Why does it exist?

Multi-region web application cần một stable public endpoint có thể đưa traffic tới healthy origin gần/phù hợp thay vì client biết từng region.

## 3. How does it work?

```text
Client -> Front Door edge -> routing policy -> healthy origin
                               |- West Europe
                               `- Southeast Asia
```

Health probes ảnh hưởng origin eligibility; probe endpoint vì vậy là một operational contract.

## 4. Practical implementation

Origin health endpoint nên phản ánh khả năng phục vụ traffic nhưng không biến mọi optional dependency thành lý do loại toàn region.

```csharp
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready")
});
```

## 5. Real production scenario

Một App Service region trả 5xx sau deployment. Front Door health probes đánh dấu origin unhealthy và chuyển traffic sang region còn lại trong khi team rollback.

## 6. Failure scenario & troubleshooting

**Symptom** → cả hai origins healthy theo app metrics nhưng Front Door không route tới một origin. **Evidence** → probe status/path/host mismatch. **Diagnosis** → health probe contract hoặc networking sai. **Fix** → sửa probe endpoint, host header, Private Link/network policy. **Verification** → origin health chuyển healthy và traffic phân phối đúng.

## 7. Common mistakes

Health endpoint phụ thuộc quá nhiều services; cache dynamic personalized response; coi Front Door là thay thế application resilience; không capacity-test failover region.

## 8. Alternatives

Application Gateway thiên về regional Layer 7 ingress. Load Balancer là Layer 4. DNS failover đơn giản hơn nhưng convergence/control khác.

## 9. Trade-offs

### Advantages
Global routing, edge termination và failover abstraction.
### Costs / Risks
Thêm cost/configuration layer; cache/routing/WAF misconfiguration có blast radius lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu edge và origin.
### Middle
Cấu hình routes/origins/health endpoint.
### Senior
Troubleshoot probe, TLS, caching và failover capacity.
### Technical Lead / Architect
Chọn global ingress architecture theo regions, RTO/RPO, security và cost.

## 11. Key takeaway

- Health probe là một phần của failover design.
- Failover chỉ hữu ích nếu secondary có đủ capacity.
- Edge routing không sửa lỗi consistency của backend.

# 8. Docker image layers: reproducible build, cache efficiency và attack surface

## 1. What is it?

Docker image gồm immutable filesystem layers. Dockerfile instruction tạo/cache layers; runtime container thêm writable layer tạm thời.

## 2. Why does it exist?

Layering cho phép reuse/caching và distribution hiệu quả. Nhưng build order và base image ảnh hưởng build time, image size, reproducibility và vulnerabilities.

## 3. How does it work?

```text
base runtime
  + app dependencies
  + published binaries
  = immutable image
```

Thay đổi layer sớm có thể invalidate các layers phía sau.

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY *.sln .
COPY src/App/App.csproj src/App/
RUN dotnet restore src/App/App.csproj
COPY . .
RUN dotnet publish src/App/App.csproj -c Release -o /out --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /out .
ENTRYPOINT ["dotnet", "App.dll"]
```

Multi-stage build giữ SDK khỏi production image.

## 5. Real production scenario

CI build mất 8 phút vì `COPY . .` trước `dotnet restore`; mỗi source change làm restore layer mất cache. Tách project metadata trước restore giúp cache dependency layer.

## 6. Failure scenario & troubleshooting

**Symptom** → image phình lớn và vulnerability scan có nhiều packages không cần runtime. **Evidence** → production stage dùng SDK image. **Diagnosis** → build/runtime boundary sai. **Fix** → multi-stage runtime image nhỏ hơn và pin/update base image policy. **Verification** → image size/CVE surface/build time giảm.

## 7. Common mistakes

Đưa secrets vào build args/layers; chạy process root không cần thiết; dùng `latest`; copy repository artifacts không cần; tin rằng layer đã xóa file thì secret chắc chắn biến mất khỏi history.

## 8. Alternatives

Native host deployment đơn giản hơn ở một số IIS/App Service workloads. Containers đáng giá khi cần packaging/runtime consistency và orchestration boundary.

## 9. Trade-offs

### Advantages
Reproducible artifact, isolation và deployment portability tốt.
### Costs / Risks
Base-image patching, registry/scanning và container operations trở thành trách nhiệm mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu image khác container.
### Middle
Viết multi-stage Dockerfile và tận dụng cache.
### Senior
Quản lý supply-chain, non-root runtime và image lifecycle.
### Technical Lead / Architect
Quyết định containerization có giải quyết deployment problem thực hay chỉ thêm operational layer.

## 11. Key takeaway

- Dockerfile order ảnh hưởng cache và CI time.
- Build tools không nên tự động đi vào runtime image.
- Container adoption tạo thêm patching/security responsibilities.

# 9. OpenTelemetry baggage vs tags: correlation xuyên service mà không tạo telemetry explosion

## 1. What is it?

Span tags/attributes mô tả span hiện tại. Baggage là key/value context có thể propagate qua process/service boundaries. Baggage không nên bị xem như “global tags miễn phí”.

## 2. Why does it exist?

Một request có thể cần propagate tenant tier hoặc workflow context để downstream instrumentation hiểu request. Nhưng propagation sai có thể làm lộ dữ liệu hoặc tăng cardinality/cost.

## 3. How does it work?

```text
Service A Activity + Baggage
        -> HTTP headers
        -> Service B Activity
```

Span attributes chỉ cần gắn nơi cần query; baggage đi xa hơn và vì thế cần governance chặt hơn.

## 4. Practical implementation

```csharp
Activity.Current?.SetTag("checkout.channel", "web");
Activity.Current?.AddBaggage("tenant.tier", "enterprise");
```

Không propagate email, token, raw user input hoặc unbounded identifiers.

## 5. Real production scenario

Team muốn so latency theo subscription tier. `tenant.tier` có vài giá trị bounded là hợp lý; `tenant.id` hàng trăm nghìn giá trị đưa vào metrics dimensions có thể gây cardinality explosion.

## 6. Failure scenario & troubleshooting

**Symptom** → telemetry ingestion/cost tăng mạnh. **Evidence** → dimension cardinality tăng sau release. **Diagnosis** → high-cardinality attribute/baggage được export rộng. **Fix** → remove/hash không phải lúc nào cũng đủ; dùng logs/traces có sampling hoặc bounded dimensions phù hợp. **Verification** → cardinality và ingestion trở lại budget.

## 7. Common mistakes

Propagate PII; gắn mọi ID vào metrics; nhầm baggage với secure context; dùng telemetry context cho authorization decision.

## 8. Alternatives

Correlation ID đơn giản đủ cho hệ thống nhỏ. Structured logs chứa high-cardinality diagnostic identifiers tốt hơn metric labels trong nhiều trường hợp.

## 9. Trade-offs

### Advantages
Context propagation giúp cross-service diagnosis.
### Costs / Risks
Privacy, header size, cardinality và telemetry cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu trace/span/context.
### Middle
Gắn bounded attributes hữu ích.
### Senior
Quản lý propagation, sampling, PII và cardinality.
### Technical Lead / Architect
Định nghĩa telemetry schema/governance xuyên services.

## 11. Key takeaway

- Baggage là propagated context, không phải nơi nhét mọi metadata.
- High cardinality là cost và operability concern.
- Telemetry context không phải security authority.

# 10. File-upload security: streaming, validation và trust boundary trong ASP.NET Core

## 1. What is it?

File upload là trust boundary nơi application nhận bytes do client kiểm soát. Security không chỉ là kiểm tra extension; cần giới hạn size, validate content, kiểm soát storage path, authorization và xử lý downstream an toàn.

## 2. Why does it exist?

Upload endpoint có thể bị dùng để gây memory/disk exhaustion, path traversal, lưu executable content hoặc đưa malicious payload vào parser/scanner downstream.

## 3. How does it work?

```text
Client -> size/rate limits -> stream -> quarantine storage
                              -> validation/scanning
                              -> trusted publication
```

Tên file từ client là metadata không đáng tin; storage key nên do server sinh.

## 4. Practical implementation

```csharp
app.MapPost("/documents", async (IFormFile file, BlobContainerClient container, CancellationToken ct) =>
{
    if (file.Length is <= 0 or > 20 * 1024 * 1024)
        return Results.BadRequest();

    var blobName = $"{Guid.NewGuid():N}.upload";
    await using var stream = file.OpenReadStream(20 * 1024 * 1024);
    await container.UploadBlobAsync(blobName, stream, ct);

    return Results.Accepted();
});
```

Production flow nên quarantine/scan trước khi content được serve hoặc parser tin cậy xử lý.

## 5. Real production scenario

HR system nhận CV/documents. File được upload trực tiếp vào Blob quarantine; metadata lưu DB; background scanner xác nhận rồi mới chuyển trạng thái `Available`. Web tier không giữ toàn file trong memory.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng mạnh khi nhiều uploads đồng thời. **Evidence** → request buffering và large form payloads. **Hypothesis** → application materialize file hoặc concurrency không giới hạn. **Diagnosis** → inspect request size, buffering và allocation profile. **Fix** → streaming/direct-to-Blob SAS khi phù hợp, rate/size limits và bounded processing. **Verification** → load test concurrent uploads, memory và storage behavior.

## 7. Common mistakes

Tin `Content-Type`; dùng client filename làm path; chỉ whitelist extension; serve upload từ executable/static directory; log file content; scan đồng bộ trong request quá lâu; SAS permission quá rộng.

## 8. Alternatives

Client-to-Blob upload bằng short-lived SAS giảm web-tier bandwidth. API-proxied upload đơn giản hơn khi cần kiểm soát chặt và file nhỏ. Hai cách vẫn cần validation workflow.

## 9. Trade-offs

### Advantages
Streaming/quarantine giảm blast radius và resource pressure.
### Costs / Risks
Thêm asynchronous state, scanner dependency, storage lifecycle và UX “processing”.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Coi mọi upload là untrusted input.
### Middle
Implement size limits, safe names, authorization và storage separation.
### Senior
Thiết kế streaming, scanning, rate limiting và failure recovery.
### Technical Lead / Architect
Xác định trust transition, retention, malware scanning, direct upload và compliance boundary.

## 11. Key takeaway

- Extension và `Content-Type` không chứng minh file an toàn.
- Upload pipeline cần explicit trust transition trước khi publish/process.
- Direct-to-object-storage có thể bảo vệ web capacity nhưng phải giới hạn SAS và lifecycle.
