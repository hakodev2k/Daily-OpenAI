# 1. CLR ThreadPool starvation trong ASP.NET Core

## 1. What is it?
ThreadPool starvation xảy ra khi work item cần thread nhanh hơn tốc độ CLR có thể cung cấp thread khả dụng. Mental model: async I/O giải phóng thread trong lúc chờ; blocking giữ thread dù CPU có thể không làm gì.

## 2. Why does it exist?
ASP.NET Core xử lý concurrency cao nhờ ThreadPool. Nếu code dùng `.Result`, `.Wait()`, synchronous I/O hoặc giữ thread quá lâu, request mới phải xếp hàng; latency tăng trước cả khi CPU đạt 100%.

## 3. How does it work?
Request vào Kestrel được xử lý bởi ThreadPool. Một `await` trên I/O chưa hoàn thành trả thread về pool; continuation được schedule khi I/O hoàn tất. Blocking biến thời gian chờ thành thread occupancy. CLR hill-climbing có thể thêm thread, nhưng phản ứng này không tức thời và quá nhiều thread làm tăng context switching.

## 4. Practical implementation
```csharp
app.MapGet("/orders/{id:int}", async (
    int id, OrderDbContext db, CancellationToken ct) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    return order is null ? Results.NotFound() : Results.Ok(order);
});
```
Không thay `await` bằng `Task.Run(() => db...)`: database I/O vốn đã asynchronous.

## 5. Real production scenario
Sau deployment, một integration SDK mới gọi HTTP đồng bộ. Traffic tăng làm request duration tăng từ 150 ms lên nhiều giây dù SQL và CPU bình thường.

## 6. Failure scenario & troubleshooting
**Symptom** → p95 tăng, request queue tăng. **Evidence** → `dotnet-counters`: ThreadPool queue length/thread count tăng, CPU chưa bão hòa. **Hypothesis** → blocking. **Diagnosis** → trace/thread dump tìm `Wait`, `Result`, synchronous socket/file calls. **Fix** → async end-to-end. **Verification** → load test lại và so p95/p99, queue length.

## 7. Common mistakes
Dùng `Task.Run` để “async hóa” I/O; sync-over-async; bỏ `CancellationToken`; nhìn CPU thấp rồi kết luận app còn capacity.

## 8. Alternatives
CPU-bound work ngắn có thể chạy trực tiếp; CPU-bound nặng nên tách worker/queue thay vì chiếm request workers.

## 9. Trade-offs
### Advantages
Async I/O tăng concurrency và giảm thread occupancy.
### Costs / Risks
Async lan qua call chain; cancellation/error handling phức tạp hơn; không làm CPU-bound work nhanh hơn.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Phân biệt thread với Task và blocking với awaiting.
### Middle
Viết async end-to-end, propagate cancellation, dùng counters.
### Senior
Chẩn đoán starvation từ telemetry và dump thay vì đoán.
### Technical Lead / Architect
Quyết định workload nào thuộc request path, workload nào phải tách queue/worker và đặt capacity limits.

## 11. Key takeaway
- CPU thấp không loại trừ ThreadPool starvation.
- Async I/O là capacity mechanism, không chỉ syntax.
- Điều tra bằng queue/thread telemetry và traces.

# 2. HTTP conditional requests với ETag

## 1. What is it?
ETag là validator đại diện cho một version của representation. Client gửi `If-None-Match` để tránh tải lại dữ liệu không đổi hoặc `If-Match` để tránh ghi đè version mới hơn.

## 2. Why does it exist?
GET lặp lại gây bandwidth/serialization không cần thiết; PUT/PATCH không có concurrency guard có thể gây lost update.

## 3. How does it work?
Server trả `ETag: "v42"`. GET sau gửi `If-None-Match: "v42"`; nếu representation không đổi server trả `304 Not Modified`. Với update, `If-Match` sai trả `412 Precondition Failed`.

## 4. Practical implementation
```csharp
var etag = $"\"{Convert.ToHexString(order.RowVersion)}\"";
if (Request.Headers.IfNoneMatch == etag)
    return Results.StatusCode(StatusCodes.Status304NotModified);

Response.Headers.ETag = etag;
return Results.Ok(order);
```

## 5. Real production scenario
Product API phục vụ mobile app. ETag giảm payload khi người dùng refresh; admin update dùng `If-Match` để không ghi đè thay đổi của editor khác.

## 6. Failure scenario & troubleshooting
**Symptom** → client nhận 304 dù nội dung đáng lẽ đổi. **Evidence** → ETag không thay đổi. **Diagnosis** → validator chỉ dựa trên entity chính nhưng response còn phụ thuộc price/stock. **Fix** → ETag phải đại diện toàn representation. **Verification** → integration test thay từng dependency.

## 7. Common mistakes
Hash không ổn định; ETag không bao phủ dữ liệu phụ thuộc; nhầm ETag với authentication; proxy/CDN strip header.

## 8. Alternatives
`Last-Modified` đơn giản hơn nhưng precision thấp; version field thích hợp concurrency; CDN caching giảm origin traffic nhưng không thay optimistic concurrency.

## 9. Trade-offs
### Advantages
Giảm bandwidth và hỗ trợ concurrency semantics chuẩn HTTP.
### Costs / Risks
Phải định nghĩa đúng representation version; composite response khó tạo validator rẻ.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu 200/304/412.
### Middle
Implement conditional GET/update và tests.
### Senior
Thiết kế validator đúng với aggregate response và cache layers.
### Technical Lead / Architect
Quyết định ETag dùng cho caching, concurrency hay cả hai và compatibility với CDN/API gateway.

## 11. Key takeaway
- ETag là version của representation.
- `If-Match` có thể bảo vệ lost update.
- Validator sai nguy hiểm hơn không có validator.

# 3. EF Core transaction boundaries và SaveChanges

## 1. What is it?
Một lần `SaveChanges` mặc định được EF Core bao trong transaction nếu provider hỗ trợ. Transaction boundary phải phản ánh business invariant cần commit atomically.

## 2. Why does it exist?
Nhiều thay đổi liên quan không được phép commit một phần. Nhưng transaction quá rộng giữ locks/connections lâu và tăng contention.

## 3. How does it work?
Change Tracker tạo commands; EF mở transaction, thực thi commands, commit hoặc rollback. Nhiều `SaveChanges` tách rời không tự nhiên trở thành một atomic unit.

## 4. Practical implementation
```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);
order.Approve(userId);
db.AuditEntries.Add(AuditEntry.For(order));
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```
External HTTP call không nên nằm trong database transaction chỉ để “đảm bảo tất cả cùng thành công”.

## 5. Real production scenario
Approval workflow phải cập nhật trạng thái order và audit record atomically; notification được phát sau bằng Outbox thay vì giữ SQL transaction trong lúc gọi email API.

## 6. Failure scenario & troubleshooting
**Symptom** → locks kéo dài, timeout tăng. **Evidence** → transaction duration và blocking chain. **Diagnosis** → transaction bao cả HTTP call. **Fix** → thu hẹp DB transaction, dùng Outbox cho side effect. **Verification** → lock duration giảm và failure test vẫn giữ invariant.

## 7. Common mistakes
Transaction per repository method; gọi external service trong transaction; tưởng nhiều DbContext tự chia sẻ transaction; retry cả transaction mà side effect không idempotent.

## 8. Alternatives
Một `SaveChanges` cho đơn giản; explicit transaction khi nhiều save phải atomic; distributed workflow dùng Outbox/Saga thay vì distributed transaction nếu phù hợp.

## 9. Trade-offs
### Advantages
Atomicity bảo vệ invariant.
### Costs / Risks
Transaction rộng tăng lock duration, deadlock risk và coupling.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu commit/rollback.
### Middle
Đặt transaction quanh một business operation.
### Senior
Phân tích isolation, retry, concurrency và side effects.
### Technical Lead / Architect
Xác định transaction boundary theo aggregate/service ownership, không theo folder/repository.

## 11. Key takeaway
- Transaction boundary là business boundary.
- Giữ transaction ngắn.
- External side effect thường cần Outbox/Saga, không phải transaction dài.

# 4. SQL Server parameter sniffing và execution-plan regression

## 1. What is it?
SQL Server có thể compile plan dựa trên parameter values quan sát khi compilation và reuse plan đó. Data distribution lệch khiến plan tốt cho value này nhưng tệ cho value khác.

## 2. Why does it exist?
Plan compilation tốn CPU; plan cache tăng hiệu quả. Vấn đề xuất hiện khi một plan không phù hợp mọi cardinality.

## 3. How does it work?
Query → parameter → cardinality estimate → join/index strategy → cached plan → reuse. Một tenant có 20 rows và tenant khác 20 triệu rows có thể cần strategy khác.

## 4. Practical implementation
```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE TenantId = @TenantId
  AND CreatedAt >= @From;
```
Điều tra actual execution plan, estimated vs actual rows, Query Store. Không thêm `OPTION (RECOMPILE)` trước khi có evidence.

## 5. Real production scenario
Multi-tenant SaaS nhanh với đa số khách hàng nhưng cực chậm với tenant lớn sau plan recompilation.

## 6. Failure scenario & troubleshooting
**Symptom** → cùng query text lúc nhanh lúc chậm. **Evidence** → Query Store cho plan change; actual rows lệch estimate lớn. **Hypothesis** → skew/plan reuse. **Fix** → cải thiện index/statistics/query shape, parameter-sensitive plan features hoặc targeted recompile khi hợp lý. **Verification** → test representative tenants và p95/p99.

## 7. Common mistakes
“Fix” bằng index ngẫu nhiên; dùng local variables để che sniffing; clear toàn plan cache trong production; benchmark chỉ một parameter.

## 8. Alternatives
Query rewrite, filtered index, separate query paths cho cardinality classes, recompile có chọn lọc.

## 9. Trade-offs
### Advantages
Plan reuse giảm compilation overhead.
### Costs / Risks
Skew làm tail latency khó dự đoán; recompile quá nhiều tốn CPU.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu execution plan và statistics.
### Middle
Đọc actual plan và Query Store.
### Senior
Phân biệt bad index, stale stats và parameter-sensitive plan.
### Technical Lead / Architect
Thiết kế tenant/data partitioning và performance test phản ánh distribution thật.

## 11. Key takeaway
- Query giống nhau không đồng nghĩa workload giống nhau.
- Đo plan + cardinality trước khi sửa.
- Tail latency cần dữ liệu representative.

# 5. MongoDB embedding vs referencing

## 1. What is it?
Embedding lưu dữ liệu liên quan trong cùng document; referencing lưu riêng và liên kết bằng identifier. Đây là quyết định access-pattern và consistency boundary, không phải “NoSQL không có relation”.

## 2. Why does it exist?
Document model tối ưu việc đọc một aggregate trong một operation, nhưng document quá lớn hoặc dữ liệu shared/high-churn làm embedding gây duplication và write amplification.

## 3. How does it work?
Embed: một read lấy parent + children và atomicity trong document. Reference: nhiều collection/read hoặc aggregation, đổi lại lifecycle độc lập.

## 4. Practical implementation
```json
{
  "_id": "order-42",
  "customerId": "c-9",
  "shippingAddressSnapshot": {
    "city": "Hanoi",
    "line1": "..."
  },
  "items": [{"sku":"A1","quantity":2,"unitPrice":120000}]
}
```
Snapshot address/price hợp lý vì order cần lịch sử tại thời điểm mua.

## 5. Real production scenario
E-commerce embed order lines nhưng reference product catalog; product title hiện tại có thể đổi mà order history không được đổi theo.

## 6. Failure scenario & troubleshooting
**Symptom** → document tăng nhanh, update chậm. **Evidence** → document size/write metrics. **Diagnosis** → embed unbounded event/history list. **Fix** → tách collection theo access pattern và pagination. **Verification** → load test growth profile.

## 7. Common mistakes
Embed mọi thứ để tránh join; normalize MongoDB y như SQL; không giới hạn array growth; không xác định ownership.

## 8. Alternatives
Relational schema khi cross-entity constraints/join mạnh; Cosmos DB có partition-key economics khác; reference trong MongoDB khi lifecycle độc lập.

## 9. Trade-offs
### Advantages
Embedding giảm round trips và làm atomic update đơn giản.
### Costs / Risks
Duplication, document growth, write amplification.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu document boundary.
### Middle
Model theo read/write patterns.
### Senior
Đánh giá growth, indexes, consistency và migration.
### Technical Lead / Architect
Chọn storage/model dựa trên invariants, scale và operational burden.

## 11. Key takeaway
- Model document theo access pattern và ownership.
- Embed bounded data có lifecycle chung.
- Reference khi dữ liệu độc lập/shared/unbounded.

# 6. Azure Functions scale-out và duplicate scheduled execution

## 1. What is it?
Serverless runtime có thể scale nhiều instances; background work phải được thiết kế với giả định retry, restart và duplicate execution tùy trigger/architecture.

## 2. Why does it exist?
Scale-out tăng throughput và resilience. Nhưng tư duy “một process chạy đúng một lần” không còn là invariant an toàn trong distributed execution.

## 3. How does it work?
Trigger → host instance → invocation → checkpoint/settlement. Failure trước khi checkpoint có thể khiến work được chạy lại. Timer coordination không nên bị suy rộng thành exactly-once business processing.

## 4. Practical implementation
```csharp
public async Task ProcessAsync(JobMessage msg, CancellationToken ct)
{
    if (await db.ProcessedMessages.AnyAsync(x => x.Id == msg.Id, ct))
        return;

    // business mutation + inbox marker in one transaction
}
```

## 5. Real production scenario
Nightly billing chạy lại sau host failure. Nếu charge API không có idempotency key, customer có thể bị charge hai lần.

## 6. Failure scenario & troubleshooting
**Symptom** → duplicate invoice. **Evidence** → invocation IDs khác nhưng business key giống. **Diagnosis** → retry sau partial success. **Fix** → business idempotency key/inbox, atomic state transition. **Verification** → fault injection giữa side effect và checkpoint.

## 7. Common mistakes
Dựa vào singleton process; distributed lock là toàn bộ correctness strategy; không xử lý retry; idempotency chỉ ở memory.

## 8. Alternatives
Worker Service + Service Bus khi cần consumer semantics rõ; scheduled orchestrator tạo message; App Service background job phù hợp workload đơn giản nhưng phải hiểu multi-instance.

## 9. Trade-offs
### Advantages
Functions giảm server management và scale theo workload.
### Costs / Risks
Execution lifecycle ít deterministic hơn; cold start, retries và cost theo usage cần quan sát.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Không giả định exactly-once.
### Middle
Implement idempotent handler.
### Senior
Thiết kế retry, poison handling và observability.
### Technical Lead / Architect
Chọn Functions hay worker dựa trên workload, SLA, cost và control cần thiết.

## 11. Key takeaway
- Distributed execution phải chịu được duplicate.
- Idempotency thuộc business boundary.
- Test failure giữa các bước, không chỉ happy path.

# 7. OpenTelemetry baggage, trace context và correlation

## 1. What is it?
Trace context truyền trace/span identity xuyên service boundaries; baggage truyền metadata có chủ đích cùng context. Correlation cho phép ghép logs, metrics và traces quanh cùng operation.

## 2. Why does it exist?
Trong distributed system, một request có thể qua API, queue và nhiều services. Log riêng lẻ không cho biết causal path.

## 3. How does it work?
W3C `traceparent` truyền trace/span IDs qua HTTP; messaging instrumentation propagate context qua headers. Activity tạo spans; exporter gửi telemetry tới backend.

## 4. Practical implementation
```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation());
```
Không đặt access token, email hoặc dữ liệu nhạy cảm vào baggage.

## 5. Real production scenario
Checkout chậm. Trace cho thấy API chỉ mất 40 ms local nhưng downstream pricing service mất 1.8 s và SQL span bên dưới bị blocking.

## 6. Failure scenario & troubleshooting
**Symptom** → trace bị đứt tại queue. **Evidence** → consumer tạo trace mới. **Diagnosis** → producer không inject hoặc consumer không extract context. **Fix** → chuẩn hóa propagation headers. **Verification** → một trace nối HTTP → publish → consume.

## 7. Common mistakes
Log correlation ID thủ công nhưng không propagate; baggage chứa PII; sampling làm mất critical traces mà không hiểu policy; cardinality quá cao trong metrics.

## 8. Alternatives
Vendor-specific tracing hoạt động nhưng tăng coupling; correlation ID tự quản đơn giản hơn nhưng thiếu span hierarchy/standard propagation.

## 9. Trade-offs
### Advantages
End-to-end causality và vendor-neutral instrumentation.
### Costs / Risks
Telemetry volume/cost, sampling complexity, data governance.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Phân biệt log, metric, trace.
### Middle
Instrument HTTP/DB và propagate context.
### Senior
Thiết kế sampling, attributes và incident workflow.
### Technical Lead / Architect
Đặt observability contract xuyên teams và kiểm soát cost/privacy.

## 11. Key takeaway
- Correlation phải xuyên boundary.
- Trace context là causality; baggage không phải chỗ chứa tùy ý.
- Observability cần thiết kế như một system contract.

# 8. Blue-Green deployment với database compatibility

## 1. What is it?
Blue-Green giữ hai application environments; traffic chuyển từ version cũ sang mới. Database thường vẫn shared nên schema compatibility quyết định rollback có thực sự an toàn hay không.

## 2. Why does it exist?
Cần giảm downtime và rollback nhanh. Nhưng rollback binary không giúp nếu migration đã phá schema mà version cũ cần.

## 3. How does it work?
Build → test → deploy Green → health validation → shift traffic → observe → retire Blue. Schema thay đổi theo expand/migrate/contract thay vì destructive migration ngay.

## 4. Practical implementation
Release 1 thêm nullable `NormalizedEmail`; app ghi cả old/new fields. Backfill dữ liệu. Release 2 đọc field mới. Chỉ release sau mới drop field cũ khi không còn consumer.

## 5. Real production scenario
App Service slot swap thành công nhưng app cũ không thể rollback vì column đã rename. Expand-contract biến schema thành backward-compatible trong cửa sổ rollout.

## 6. Failure scenario & troubleshooting
**Symptom** → Green health tốt nhưng Blue crash sau rollback. **Evidence** → SQL invalid column. **Diagnosis** → destructive migration. **Fix** → restore compatible schema hoặc forward-fix; sau incident áp dụng expand-contract. **Verification** → chạy compatibility tests cho N và N-1.

## 7. Common mistakes
Gộp drop/rename với deployment; coi health endpoint 200 là đủ; migration chạy từ nhiều instances; không xác định rollback window.

## 8. Alternatives
Rolling deployment đơn giản hơn; Canary giảm blast radius; feature flags tách release khỏi deploy nhưng không giải quyết schema incompatibility.

## 9. Trade-offs
### Advantages
Fast traffic rollback, giảm downtime.
### Costs / Risks
Double environment cost; schema transition kéo dài; operational orchestration phức tạp.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu artifact, environment và rollback.
### Middle
Viết backward-compatible migration.
### Senior
Thiết kế health validation và failure rollback.
### Technical Lead / Architect
Định nghĩa compatibility window, migration ownership và release policy.

## 11. Key takeaway
- Blue-Green không tự làm database rollback-safe.
- Schema cần expand → migrate → contract.
- Validate cả version N và N-1.

# 9. Optimizely CMS content modeling: page, block và domain boundary

## 1. What is it?
Content modeling định nghĩa cấu trúc mà editor quản lý. Trong Optimizely CMS, Page/Block là editorial abstractions; chúng không nên mặc định trở thành domain model cho pricing, inventory hay order.

## 2. Why does it exist?
Editor cần composition/reuse/workflow. Business transactional systems cần invariants và ownership khác. Trộn hai boundary tạo coupling giữa publishing lifecycle và runtime commerce logic.

## 3. How does it work?
Editor → content types → published content → rendering/API → cache/CDN. Product page có thể chứa CMS content nhưng price/stock đến từ Product API.

## 4. Practical implementation
```csharp
[ContentType(DisplayName = "Hero Block")]
public class HeroBlock : BlockData
{
    public virtual string? Heading { get; set; }
    public virtual ContentReference? Image { get; set; }
    public virtual Url? CtaUrl { get; set; }
}
```
Block chứa editorial data; không nhúng logic gọi inventory vào content model.

## 5. Real production scenario
Marketing đổi hero copy và publish độc lập; product availability vẫn do commerce service sở hữu. Web layer compose hai nguồn theo failure policy rõ ràng.

## 6. Failure scenario & troubleshooting
**Symptom** → publish CMS làm page chậm mạnh. **Evidence** → trace cho thấy renderer gọi external API theo từng block. **Diagnosis** → N+1 integration calls trong rendering. **Fix** → aggregate/batch data, cache phù hợp hoặc tách composition layer. **Verification** → đo request count và p95.

## 7. Common mistakes
Dùng CMS làm transactional source of truth; block quá generic; content type phản ánh component CSS thay vì editorial intent; external call ẩn trong property/rendering.

## 8. Alternatives
Headless CMS cho multi-channel; traditional rendering đơn giản hơn khi một web channel; commerce/catalog service sở hữu transactional product data.

## 9. Trade-offs
### Advantages
Editor autonomy, reuse, workflow.
### Costs / Risks
Content migrations, cache invalidation, upgrade burden và integration latency.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu page/block/publish lifecycle.
### Middle
Tạo content types dễ dùng và test rendering.
### Senior
Giữ CMS boundary khỏi transactional domain, xử lý cache/failure.
### Technical Lead / Architect
Quyết định content ownership, composition architecture và headless/traditional dựa trên channels/team needs.

## 11. Key takeaway
- CMS model phục vụ editorial lifecycle.
- Transactional truth nên có owner riêng.
- Composition phải làm dependency/failure rõ ràng.

# 10. RAG retrieval boundaries và deterministic authorization

## 1. What is it?
RAG đưa dữ liệu truy xuất được vào context để model trả lời dựa trên knowledge ngoài model. Retrieval relevance không phải authorization: quyền truy cập phải được enforce bằng deterministic code trước khi content vào prompt.

## 2. Why does it exist?
LLM không biết dữ liệu private/current của doanh nghiệp. RAG bổ sung context nhưng tạo risk data leakage nếu vector search trả document người dùng không được phép xem.

## 3. How does it work?
User → authenticate → authorize/filter scope → retrieve → rerank → construct context → LLM → validate/output. Authorization phải nằm trước model và không được giao cho prompt kiểu “chỉ trả dữ liệu user được phép xem”.

## 4. Practical implementation
```csharp
var scope = await authorization.GetDocumentScopeAsync(user, ct);

var chunks = await search.SearchAsync(
    query,
    tenantId: scope.TenantId,
    allowedDocumentIds: scope.DocumentIds,
    cancellationToken: ct);

var answer = await llm.AnswerAsync(query, chunks, ct);
```
Tenant/document filters phải được enforce tại retrieval layer hoặc trusted data service.

## 5. Real production scenario
Internal HR assistant index policy và employee documents. Hai nhân viên hỏi cùng câu nhưng retrieval scope khác nhau theo tenant/role/document ACL.

## 6. Failure scenario & troubleshooting
**Symptom** → answer trích nội dung từ tenant khác. **Evidence** → retrieved chunk metadata có tenant mismatch. **Hypothesis** → authorization chỉ nằm trong system prompt. **Diagnosis** → vector query không filter tenant. **Fix** → mandatory server-side scope filter + security tests. **Verification** → adversarial cross-tenant retrieval tests.

## 7. Common mistakes
Coi prompt là security boundary; index không mang ACL metadata; log prompt chứa confidential data; retry LLM không có cost limit; cho model tự quyết action quan trọng.

## 8. Alternatives
Deterministic search UI khi không cần generation; fine-tuning không thay thế private retrieval; tool calling phù hợp dữ liệu live nhưng tool vẫn phải authorize server-side.

## 9. Trade-offs
### Advantages
RAG dùng knowledge current/private mà không retrain model và có thể cung cấp provenance.
### Costs / Risks
Retrieval quality, latency, token cost, ACL complexity, prompt injection và data leakage.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu retrieve rồi generate.
### Middle
Implement chunking/search/context và citations.
### Senior
Đánh giá retrieval quality, latency, injection và ACL leakage.
### Technical Lead / Architect
Quyết định dữ liệu nào được đưa vào AI boundary, logic nào bắt buộc deterministic, ownership/evaluation/audit strategy.

## 11. Key takeaway
- RAG không phải authorization.
- Filter quyền trước khi dữ liệu vào model.
- Security-critical decisions phải deterministic và auditable.
