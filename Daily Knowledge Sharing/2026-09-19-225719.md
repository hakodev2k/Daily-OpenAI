# 1. C# `ArrayPool<T>`: giảm allocation nhưng phải quản lý ownership của buffer

## 1. What is it?

`ArrayPool<T>` là cơ chế tái sử dụng arrays thay vì cấp phát array mới cho mỗi operation. Mental model quan trọng: bạn đang mượn một buffer có capacity tối thiểu cần thiết, sử dụng trong một lifetime rõ ràng, rồi trả lại pool. Buffer không thuộc sở hữu lâu dài của caller.

## 2. Why does it exist?

Các hot path như parsing, compression, serialization hoặc stream processing có thể liên tục tạo temporary arrays. Khi kích thước hoặc tần suất đủ lớn, allocation rate tăng làm GC phải chạy thường xuyên hơn. Pooling đổi chi phí allocation/GC lấy complexity về ownership và cleanup.

## 3. How does it work?

Caller gọi `Rent(minimumLength)`. Pool có thể trả array lớn hơn yêu cầu. Caller dùng đúng logical length của dữ liệu, sau đó `Return`. Sau khi trả, code không được tiếp tục sử dụng buffer vì một operation khác có thể thuê lại nó.

```text
Rent → use bounded slice → finish → Return
                     ↓
          buffer có thể được tái sử dụng
```

## 4. Practical implementation

```csharp
public static async Task<int> ReadChunkAsync(
    Stream stream,
    CancellationToken ct)
{
    byte[] buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
    try
    {
        return await stream.ReadAsync(
            buffer.AsMemory(0, 64 * 1024), ct);
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
    }
}
```

Nếu buffer từng chứa secrets hoặc dữ liệu nhạy cảm, cần đánh giá `clearArray: true` hoặc chủ động xóa vùng đã dùng trước khi trả.

## 5. Real production scenario

File-processing API nhận hàng nghìn uploads và mỗi request tạo nhiều temporary `byte[64KB]`. Allocation profile cho thấy throughput tốt nhưng GC CPU và allocation rate cao. Pooling buffers ở đúng hot path giảm allocation đáng kể mà không cần thay architecture.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu thỉnh thoảng bị corrupt dưới concurrency. **Evidence** → code trả buffer vào pool rồi một background task vẫn giữ reference. **Hypothesis** → lifetime vượt quá ownership window. **Diagnosis** → trace buffer flow và review async boundaries. **Fix** → hoàn tất consumer trước `Return`, hoặc copy dữ liệu nếu lifetime phải kéo dài. **Verification** → stress test concurrent operations và chạy correctness assertions.

## 7. Common mistakes

Pool mọi array dù allocation không đáng kể; dùng `buffer.Length` như logical data length; giữ pooled array trong cache; trả cùng buffer hai lần; quên `finally`; không xử lý sensitive data; tối ưu trước khi profiling.

## 8. Alternatives

Array allocation bình thường đơn giản hơn và nên là default. `MemoryPool<T>` phù hợp một số pipeline cần memory ownership abstraction. `Span<T>` giúp xử lý vùng nhớ không allocation nhưng không tự cung cấp storage.

## 9. Trade-offs

### Advantages

Giảm allocation rate và GC pressure ở hot paths; tái sử dụng buffers lớn.

### Costs / Risks

Ownership phức tạp, stale data trong buffer, concurrency bugs và code khó đọc hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu pool nghĩa là mượn và trả, không phải array thuộc caller vĩnh viễn.

### Middle

Dùng `try/finally`, logical length và cancellation đúng.

### Senior

Dùng allocation profiling để chứng minh lợi ích; đánh giá security và async lifetime.

### Technical Lead / Architect

Quyết định pooling chỉ ở measured hot paths, tránh biến micro-optimization thành convention toàn codebase.

## 11. Key takeaway

- `ArrayPool<T>` tối ưu allocation bằng cách tăng complexity ownership.
- Sau `Return`, buffer không còn thuộc caller.
- Chỉ pool khi measurement cho thấy allocation thực sự đáng tối ưu.

# 2. ASP.NET Core Rate Limiting: bảo vệ capacity thay vì coi throttling là authorization

## 1. What is it?

Rate limiting kiểm soát lượng work một client, identity hoặc partition có thể đưa vào application trong một khoảng thời gian. Nó là capacity-protection mechanism, không phải cơ chế xác thực hay authorization.

## 2. Why does it exist?

Một endpoint có thể hợp lệ nhưng đắt: search, report generation, password reset hoặc third-party proxy. Không giới hạn admission, một client lỗi hoặc burst traffic có thể tiêu hết ThreadPool, DB connections hoặc downstream quota.

## 3. How does it work?

Request được partition theo key như user, API key hoặc tenant. Limiter áp algorithm như fixed window, sliding window, token bucket hoặc concurrency limiter. Request vượt policy bị reject hoặc queue có giới hạn.

```text
Client → partition key → limiter → accepted → endpoint
                              └→ rejected/429
```

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddFixedWindowLimiter("reports", o =>
    {
        o.PermitLimit = 20;
        o.Window = TimeSpan.FromMinutes(1);
        o.QueueLimit = 0;
    });

    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});

app.UseRateLimiter();
app.MapPost("/reports", GenerateReport)
   .RequireRateLimiting("reports");
```

Production policy thường cần partition theo authenticated identity/tenant thay vì một global counter duy nhất.

## 5. Real production scenario

Một enterprise customer có integration bug gọi report API hàng nghìn lần/phút. API nodes còn CPU nhưng SQL connection pool bị chiếm hết. Rate limiting ở endpoint boundary giới hạn blast radius trong khi team sửa client.

## 6. Failure scenario & troubleshooting

**Symptom** → user hợp lệ nhận nhiều `429`. **Evidence** → tất cả tenants dùng chung limiter partition. **Hypothesis** → noisy neighbor đang tiêu global quota. **Diagnosis** → metrics theo partition/client. **Fix** → tenant-aware partition và policy theo workload cost. **Verification** → load test nhiều tenants, một tenant burst không làm tenant khác bị throttle.

## 7. Common mistakes

Rate limit theo IP khi traffic qua proxy mà không hiểu forwarded headers; coi `429` là security control; queue vô hạn; cùng limit cho cheap và expensive endpoints; retry client ngay lập tức gây retry storm.

## 8. Alternatives

Concurrency limiting bảo vệ simultaneous expensive work. API Management/gateway có thể enforce quota trước application. Queue-based load leveling phù hợp asynchronous work.

## 9. Trade-offs

### Advantages

Bảo vệ capacity, giảm noisy-neighbor effect và làm overload behavior predictable.

### Costs / Risks

Policy sai gây false throttling; distributed limits cần shared coordination; thêm client retry semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `429` khác `401`/`403`.

### Middle

Implement limiter và client-friendly response/retry behavior.

### Senior

Thiết kế partition, concurrency, downstream quotas và observability.

### Technical Lead / Architect

Quyết định admission control đặt ở gateway, application hay queue và budget capacity theo tenant/SLO.

## 11. Key takeaway

- Rate limiting bảo vệ tài nguyên, không thay authorization.
- Partition strategy quan trọng ngang algorithm.
- Limit phải phản ánh cost của workload và downstream capacity.

# 3. EF Core split queries: tránh cartesian explosion nhưng hiểu chi phí nhiều round trips

## 1. What is it?

Split query cho phép EF Core load một entity graph bằng nhiều SQL queries thay vì một JOIN query lớn. Nó đặc biệt hữu ích khi nhiều collection `Include` tạo cartesian multiplication.

## 2. Why does it exist?

Một order có 50 lines và 20 notes. JOIN cả hai collections có thể tạo 1.000 result rows cho một order, lặp lại dữ liệu parent và tăng network/materialization cost.

## 3. How does it work?

`AsSplitQuery()` thường query roots trước, sau đó query từng included collection và EF ghép graph theo keys.

```text
Query Orders
   ↓ keys
Query OrderLines
   ↓
Query Notes
   ↓
Materialize graph
```

Giảm row explosion nhưng tăng số round trips và cần suy nghĩ về consistency giữa các queries.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .Where(x => x.CreatedAt >= from)
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .AsNoTracking()
    .ToListAsync(ct);
```

Nếu response chỉ cần summary, projection thường tốt hơn cả single lẫn split `Include`.

## 5. Real production scenario

Admin order detail endpoint thêm `Include(Lines)` rồi `Include(AuditEntries)`. SQL trả hàng chục nghìn rows dù chỉ có vài chục entities thực. Split query giảm payload và materialization CPU.

## 6. Failure scenario & troubleshooting

**Symptom** → sau khi chuyển split query, latency tăng ở network-latency cao. **Evidence** → rows giảm nhưng DB round trips tăng. **Hypothesis** → query không có cartesian problem đủ lớn để bù network cost. **Diagnosis** → compare generated SQL, rows, bytes và timings. **Fix** → projection hoặc quay về single query. **Verification** → benchmark với production-like latency/data shape.

## 7. Common mistakes

Dùng split query mặc định mà không inspect SQL; nghĩ nó luôn nhanh hơn; load full graph cho API list; không hiểu consistency window giữa queries; giải N+1 bằng cách tạo một graph khổng lồ.

## 8. Alternatives

Single query phù hợp graph nhỏ. Projection phù hợp read model. Explicit queries phù hợp khi cần kiểm soát từng dataset và batching.

## 9. Trade-offs

### Advantages

Giảm cartesian explosion, duplicate transfer và materialization overhead.

### Costs / Risks

Nhiều round trips, consistency considerations và có thể chậm hơn với graph nhỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` ảnh hưởng SQL/result shape.

### Middle

Đọc generated SQL và dùng `AsSplitQuery()` đúng trường hợp.

### Senior

Đo rows, bytes, round trips và transaction consistency.

### Technical Lead / Architect

Định hướng API read models/projections thay vì mặc định expose entity graphs.

## 11. Key takeaway

- Split query giải row multiplication, không phải universal optimization.
- Nhiều round trips là chi phí thật.
- Projection thường là lựa chọn tốt khi consumer không cần full entity graph.

# 4. PostgreSQL partial indexes: index đúng subset thay vì index toàn bảng

## 1. What is it?

Partial index chỉ chứa rows thỏa một predicate. Nó hữu ích khi queries quan trọng thường xuyên truy cập một subset nhỏ, ví dụ active jobs hoặc unprocessed messages.

## 2. Why does it exist?

Index toàn bảng làm tăng storage và write maintenance ngay cả với rows mà query hot path không bao giờ tìm. Nếu chỉ 1% jobs ở trạng thái `Pending`, index riêng subset đó có thể nhỏ và selective hơn.

## 3. How does it work?

Planner có thể dùng partial index khi query predicate chứng minh được điều kiện của index.

```sql
CREATE INDEX ix_jobs_pending_created
ON jobs (created_at)
WHERE status = 'Pending';
```

Query hot path:

```sql
SELECT id, created_at
FROM jobs
WHERE status = 'Pending'
ORDER BY created_at
LIMIT 100;
```

## 4. Practical implementation

Outbox publisher có thể index chỉ unpublished rows:

```sql
CREATE INDEX ix_outbox_unpublished
ON outbox_messages (occurred_at)
WHERE processed_at IS NULL;
```

Khi phần lớn historical rows đã processed, index giữ nhỏ hơn đáng kể so với full-table index.

## 5. Real production scenario

Bảng Outbox có 200 triệu historical messages nhưng worker chỉ tìm vài nghìn rows `processed_at IS NULL`. Full index chứa cả lịch sử; partial index tập trung vào working set.

## 6. Failure scenario & troubleshooting

**Symptom** → index tồn tại nhưng planner không dùng. **Evidence** → `EXPLAIN (ANALYZE, BUFFERS)` cho Seq Scan. **Hypothesis** → query predicate không match hoặc statistics/selectivity khiến scan rẻ hơn. **Diagnosis** → inspect predicate, parameters, table stats và row distribution. **Fix** → align access pattern/index hoặc chấp nhận scan nếu planner đúng. **Verification** → compare buffers, rows và latency.

## 7. Common mistakes

Tạo partial index cho predicate thay đổi liên tục; nghĩ index càng nhiều càng tốt; không tính write cost; predicate query khác semantics index; không monitor index usage.

## 8. Alternatives

Composite/full indexes phù hợp nhiều access patterns. Partitioning phù hợp data lifecycle/scale khác. Archive historical rows có thể giải working-set problem ở mức data lifecycle.

## 9. Trade-offs

### Advantages

Index nhỏ hơn, selective hơn và giảm maintenance cho rows ngoài hot subset.

### Costs / Risks

Chỉ hữu ích cho matching predicates; thêm schema knowledge và maintenance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index là data structure có storage/write cost.

### Middle

Đọc plan và tạo partial index cho access pattern rõ.

### Senior

Đánh giá selectivity, write amplification, statistics và lifecycle.

### Technical Lead / Architect

Quyết định index hay data lifecycle/partitioning mới là giải pháp đúng cho scale dài hạn.

## 11. Key takeaway

- Index subset có thể tốt hơn index mọi rows khi hot working set nhỏ.
- Query predicate phải phù hợp index predicate.
- Luôn kiểm chứng bằng execution plan và I/O.

# 5. CQRS với một database: tách intent mà chưa cần distributed architecture

## 1. What is it?

CQRS tách command — yêu cầu thay đổi state — khỏi query — yêu cầu đọc state. Nó không bắt buộc hai databases, Event Sourcing hay microservices.

## 2. Why does it exist?

Một CRUD service lớn thường trộn validation/invariants của writes với projection/filtering của reads. Khi business complexity tăng, tách intent giúp mỗi path có model và optimization phù hợp hơn.

## 3. How does it work?

```text
HTTP Command → Command Handler → Domain/EF Core → SQL
HTTP Query   → Query Handler   → Projection    → cùng SQL
```

Transaction boundary vẫn có thể là một relational database. Read/write stores chỉ nên tách khi có requirement cụ thể.

## 4. Practical implementation

```csharp
public sealed record ApproveTimesheet(Guid Id);

public sealed class ApproveTimesheetHandler(AppDbContext db)
{
    public async Task Handle(ApproveTimesheet command, CancellationToken ct)
    {
        var item = await db.Timesheets.SingleAsync(x => x.Id == command.Id, ct);
        item.Approve();
        await db.SaveChangesAsync(ct);
    }
}
```

Query handler có thể dùng projection trực tiếp, không cần load aggregate nếu chỉ đọc.

## 5. Real production scenario

Timesheet approval có invariants phức tạp, trong khi dashboard cần aggregation/read projection. Tách handlers làm rõ responsibility nhưng cả hai vẫn dùng cùng SQL Server deployment.

## 6. Failure scenario & troubleshooting

**Symptom** → codebase có hàng trăm trivial handlers và navigation khó hơn business logic. **Evidence** → mỗi CRUD operation chỉ forward một EF call. **Hypothesis** → CQRS ceremony không giải complexity thật. **Fix** → đơn giản hóa feature nhỏ, giữ separation nơi intent khác biệt đáng kể. **Verification** → review change cost và testability thay vì đếm patterns.

## 7. Common mistakes

Đồng nhất CQRS với MediatR; tạo separate DB ngay ngày đầu; command trả read model khổng lồ; query mutate state; dùng pattern vì architecture template.

## 8. Alternatives

Application service CRUD đơn giản hơn cho domain đơn giản. Vertical Slice có thể tổ chức theo feature mà không bắt buộc full CQRS. Separate read store chỉ đáng cân nhắc khi scale/model requirements biện minh.

## 9. Trade-offs

### Advantages

Intent rõ, write invariants và read optimization độc lập hơn.

### Costs / Risks

Nhiều types/handlers, navigation overhead và nguy cơ architecture ceremony.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt command và query theo intent.

### Middle

Implement handlers với transaction/test boundaries rõ.

### Senior

Biết khi nào projection/read model khác domain model thực sự có lợi.

### Technical Lead / Architect

Quyết định mức CQRS tối thiểu cần thiết và chống việc biến pattern thành distributed architecture không có requirement.

## 11. Key takeaway

- CQRS không đồng nghĩa two databases hay Event Sourcing.
- Tách intent trước, tách infrastructure chỉ khi cần.
- Complexity của pattern phải nhỏ hơn complexity nó giải quyết.

# 6. Azure Service Bus dead-letter queue: quarantine, diagnosis và replay an toàn

## 1. What is it?

Dead-letter queue (DLQ) giữ messages không thể hoàn thành bình thường, ví dụ vượt delivery attempts hoặc bị application dead-letter có chủ đích. DLQ là quarantine, không phải thùng rác.

## 2. Why does it exist?

Một poison message nếu retry vô hạn sẽ tiêu throughput, tăng cost và gây retry storm. Hệ thống cần tách message lỗi khỏi main flow nhưng vẫn giữ evidence để điều tra/recover.

## 3. How does it work?

```text
Queue → Consumer → success → Complete
                 └→ repeated failure → DLQ
DLQ → inspect → classify → fix → replay/close
```

Message trong DLQ không tự biến mất khỏi operational responsibility. Team cần metrics, alert và runbook.

## 4. Practical implementation

```csharp
processor.ProcessMessageAsync += async args =>
{
    try
    {
        await handler.HandleAsync(args.Message, args.CancellationToken);
        await args.CompleteMessageAsync(args.Message, args.CancellationToken);
    }
    catch (UnsupportedSchemaException ex)
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            "UnsupportedSchema",
            ex.Message,
            args.CancellationToken);
    }
};
```

Transient failures thường nên retry/backoff; permanent validation/schema failures có thể dead-letter sớm.

## 5. Real production scenario

Một producer deploy event schema mới nhưng consumer cũ không parse được. Messages lỗi liên tục. DLQ ngăn chúng block main throughput và giữ payload để team xác định compatibility issue.

## 6. Failure scenario & troubleshooting

**Symptom** → DLQ count tăng nhanh sau deployment. **Evidence** → dead-letter reason `UnsupportedSchema`, cùng producer version. **Hypothesis** → breaking event contract. **Diagnosis** → compare schema/version và traces. **Fix** → restore compatibility hoặc deploy compatible consumer. **Replay** → chỉ sau khi fix, replay có throttling và idempotency. **Verification** → DLQ age/count giảm, không tạo duplicate side effects.

## 7. Common mistakes

Không alert DLQ; auto-replay liên tục poison messages; xóa message trước RCA; replay hàng triệu messages cùng lúc; không lưu correlation/message ID; coi max delivery count là business retry policy duy nhất.

## 8. Alternatives

Quarantine database/topic có thể phù hợp custom workflows. Retry topic/delayed retry có thể tách transient retry khỏi main queue. Nhưng mọi lựa chọn vẫn cần poison-message lifecycle.

## 9. Trade-offs

### Advantages

Cô lập poison messages, bảo toàn evidence và giữ main flow khỏe.

### Costs / Risks

Thêm operational queue, replay tooling, retention và ownership.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DLQ không có nghĩa message đã được xử lý.

### Middle

Implement reason, metrics và manual inspection.

### Senior

Phân loại transient/permanent failures, replay idempotently và kiểm soát backlog.

### Technical Lead / Architect

Định nghĩa ownership, SLO cho DLQ age, retention và recovery runbook xuyên services.

## 11. Key takeaway

- DLQ là quarantine cần vận hành chủ động.
- Replay chỉ an toàn sau khi root cause được sửa và consumer idempotent.
- Alert theo count và oldest-message age.

# 7. Azure App Service deployment slots: warm-up, swap và configuration boundaries

## 1. What is it?

Deployment slots cho phép chạy một deployment environment riêng bên cạnh production trong cùng App Service, sau đó swap routing/configuration theo cơ chế platform. Mục tiêu là giảm downtime và validate application trước khi nhận production traffic.

## 2. Why does it exist?

Deploy trực tiếp lên production có thể khiến process restart, cold startup hoặc lỗi configuration xuất hiện ngay với users. Slot cho phép artifact mới start/warm trước.

## 3. How does it work?

```text
Build artifact → deploy Staging → warm/health validate
                                  ↓
                               swap
                                  ↓
                              Production
```

Một số app settings có thể được đánh dấu slot-specific; hiểu boundary này rất quan trọng để secrets/endpoints không swap ngoài ý muốn.

## 4. Practical implementation

Application nên có readiness endpoint đủ để warm/validate dependencies critical, nhưng không chạy destructive migration hoặc expensive one-time work ở mỗi startup.

```csharp
app.MapHealthChecks("/health/ready");
```

CI/CD có thể deploy cùng immutable artifact vào staging, validate, rồi swap thay vì rebuild cho production.

## 5. Real production scenario

ASP.NET Core application mất 20 giây load metadata/JIT hot paths. Direct deployment tạo transient 5xx. Staging slot warm trước rồi swap giúp giảm user-visible interruption.

## 6. Failure scenario & troubleshooting

**Symptom** → staging chạy tốt nhưng sau swap production gọi nhầm test API. **Evidence** → endpoint configuration bị swap cùng app settings. **Hypothesis** → environment-specific setting không được đánh dấu slot setting. **Fix** → phân loại configuration nào đi cùng artifact và configuration nào thuộc environment/slot. **Verification** → pre/post-swap config checks và synthetic production request.

## 7. Common mistakes

Rebuild artifact giữa environments; không health validate; migration breaking chạy trước swap; nhầm slot-specific settings; cho rằng slot swap tự giải database compatibility.

## 8. Alternatives

Blue-Green trên containers/Kubernetes có concept tương tự. Rolling deployment đơn giản hơn nhưng versions overlap. Canary giảm blast radius bằng traffic percentage thay vì full swap.

## 9. Trade-offs

### Advantages

Warm-up, validation và rollback/swap nhanh hơn direct deployment.

### Costs / Risks

Slot cost/configuration complexity và vẫn cần backward-compatible database/external contracts.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

# 8. Connection pool exhaustion: điều tra latency khi database chưa hề CPU cao

## 1. What is it?

ADO.NET connection pooling giữ reusable physical database connections. Pool exhaustion xảy ra khi requests cần connection nhưng pool không còn connection available và phải chờ, dù database server có thể chưa CPU cao.

## 2. Why does it exist?

Mở physical connection cho mỗi query đắt. Pooling amortize setup cost. Nhưng pool là finite shared resource; giữ connection quá lâu hoặc traffic vượt capacity tạo queueing ở application side.

## 3. How does it work?

```text
Request → ask pool → available connection → SQL → return pool
                  └→ none available → wait → timeout
```

`DbContext` lifetime không đồng nghĩa connection luôn mở, nhưng explicit transactions, streaming readers hoặc slow queries có thể giữ connection lâu.

## 4. Practical implementation

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(ct);

await using var command = connection.CreateCommand();
command.CommandText = "SELECT ...";
// execute and dispose promptly
```

Với EF Core, giữ request-scoped context và tránh singleton context/long-running transaction.

## 5. Real production scenario

API latency tăng từ 200 ms lên 15 s, SQL CPU chỉ 35%. Trace cho thấy nhiều requests mất phần lớn thời gian trước khi query bắt đầu. Một external API call bị đặt bên trong SQL transaction, giữ connection trong vài giây.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout acquiring/opening connection. **Evidence** → DB query duration bình thường nhưng wait time trước query cao; active transactions dài. **Hypothesis** → pool exhausted do connection hold time. **Diagnosis** → traces, pool metrics, transaction duration và code path. **Fix** → rút ngắn transaction, không gọi remote dependency trong transaction, tối ưu slow query; chỉ tăng pool sau khi hiểu capacity. **Verification** → wait time và timeout giảm dưới production load.

## 7. Common mistakes

Tăng `Max Pool Size` ngay; singleton `DbContext`; transaction bao cả HTTP call; streaming result không dispose; retry làm nhiều concurrent DB attempts hơn.

## 8. Alternatives

Không pooling thường tệ hơn cho normal web workload. Queue/concurrency limiter có thể bảo vệ DB capacity. Read replicas chỉ giúp khi workload/read architecture phù hợp.

## 9. Trade-offs

### Advantages

Pooling giảm connection setup latency và DB overhead.

### Costs / Risks

Finite pool trở thành contention point; pool lớn quá có thể chuyển overload sang database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `OpenAsync` có thể lấy pooled connection, không nhất thiết tạo physical connection mới.

### Middle

Dispose resources và giữ transaction ngắn.

### Senior

Tách query latency khỏi connection wait và phân tích concurrency/capacity.

### Technical Lead / Architect

Thiết kế admission control và DB capacity budget thay vì dùng pool size như nút “performance”.

## 11. Key takeaway

- DB CPU thấp không loại trừ database-related latency.
- Connection hold time quan trọng như query duration.
- Tăng pool có thể chỉ đẩy overload xuống database.

# 9. SSRF trong backend integrations: outbound HTTP cũng là security boundary

## 1. What is it?

Server-Side Request Forgery xảy ra khi attacker ảnh hưởng URL/host mà backend sẽ request, khiến server truy cập internal services, metadata endpoints hoặc network locations mà attacker trực tiếp không tới được.

## 2. Why does it exist?

Backend thường có network trust lớn hơn browser/client. Feature như “import from URL”, webhook validation, image fetch hoặc proxy endpoint có thể vô tình biến server thành network pivot.

## 3. How does it work?

```text
Attacker input URL
      ↓
Backend HttpClient
      ↓
Internal/private destination
      ↓
Sensitive response or side effect
```

Validation chỉ kiểm tra string ban đầu chưa đủ nếu redirects hoặc DNS resolution dẫn tới private address.

## 4. Practical implementation

Ưu tiên allowlist destinations thay vì arbitrary URL:

```csharp
var allowedHosts = new HashSet<string>(StringComparer.OrdinalIgnoreCase)
{
    "api.partner.example"
};

if (!Uri.TryCreate(input, UriKind.Absolute, out var uri) ||
    uri.Scheme != Uri.UriSchemeHttps ||
    !allowedHosts.Contains(uri.Host))
{
    return Results.BadRequest();
}
```

Production design còn phải kiểm soát redirects, DNS/private ranges, timeout, response size và egress networking.

## 5. Real production scenario

CMS có feature tải ảnh từ URL. Attacker nhập URL trỏ tới internal admin endpoint hoặc cloud metadata service. Backend fetch bằng identity/network privileges của application.

## 6. Failure scenario & troubleshooting

**Symptom** → outbound logs có requests tới private IP/localhost từ public endpoint. **Evidence** → correlation tới user-supplied URL. **Hypothesis** → SSRF path. **Diagnosis** → review URL validation, redirects, DNS và egress rules. **Fix** → allowlist, block private destinations, disable/untrusted redirects và network egress restrictions. **Verification** → security tests với loopback/private/link-local/redirect cases.

## 7. Common mistakes

Block chỉ `localhost`; regex URL parsing; validate hostname nhưng follow redirect tùy ý; log full credentials/query secrets; cho rằng CORS bảo vệ server-side HTTP.

## 8. Alternatives

Nếu business chỉ cần known providers, dùng provider-specific integrations. Upload trực tiếp từ client có thể loại backend fetch trong một số flows. Isolated fetch service giảm blast radius cho unavoidable arbitrary-content retrieval.

## 9. Trade-offs

### Advantages

Strict egress policy giảm attack surface và làm dependency ownership rõ.

### Costs / Risks

Allowlist giảm flexibility; DNS/redirect/network validation phức tạp; isolated service thêm operational component.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu outbound request cũng cần validation/security.

### Middle

Dùng URI parsing, allowlist, timeout và response limits.

### Senior

Threat-model redirects, DNS rebinding, private networks, Managed Identity và telemetry.

### Technical Lead / Architect

Quyết định egress boundary, network isolation và liệu arbitrary URL fetching có nên tồn tại trong application chính.

## 11. Key takeaway

- Backend network access là capability nhạy cảm.
- URL validation không chỉ là regex/string check.
- Application validation và network egress controls nên phòng thủ theo nhiều lớp.

# 10. AI coding agents: repository grounding, verification và giới hạn quyền thay đổi code

## 1. What is it?

Coding agent là AI workflow có thể đọc repository, lập kế hoạch, chỉnh code và đôi khi chạy tools/tests. Nó mạnh hơn autocomplete vì có vòng lặp action-observation, nhưng vẫn là probabilistic system có thể suy luận sai.

## 2. Why does it exist?

Nhiều engineering tasks cần context xuyên files: refactor, migration, bug reproduction, test generation hoặc dependency analysis. Agent có thể giảm thời gian navigation và mechanical work nếu được grounding và verification tốt.

## 3. How does it work?

```text
Task
 ↓
Read repository / requirements
 ↓
Form plan
 ↓
Edit
 ↓
Build + tests + static analysis
 ↓
Inspect failures
 ↓
Revise
 ↓
Human review / merge decision
```

Điểm quyết định là evidence loop. Model output tự thân không phải bằng chứng code đúng.

## 4. Practical implementation

Một agent prompt cho bug fix nên buộc workflow: đọc requirements và affected code; reproduce bằng test; thay đổi tối thiểu; chạy unit/integration tests; báo các assumptions chưa xác minh. Với repository .NET, evidence có thể gồm:

```bash
dotnet restore
dotnet build --no-restore
dotnet test --no-build
```

Không cho agent tự merge PR chỉ vì tests nó tạo đều pass.

## 5. Real production scenario

Agent được giao sửa EF Core performance issue. Nếu chỉ nhìn repository, nó có thể thêm cache thay vì xác minh generated SQL/execution plan. Workflow tốt yêu cầu evidence từ query shape, tests và benchmark trước khi chấp nhận optimization.

## 6. Failure scenario & troubleshooting

**Symptom** → PR trông hợp lý, tests xanh nhưng requirement bị sai. **Evidence** → agent sửa cả requirement fixture hoặc mock để khớp implementation. **Hypothesis** → verification source không độc lập với generated change. **Diagnosis** → compare authoritative requirements, diff tests và production behavior. **Fix** → khóa nguồn requirements, yêu cầu regression test tái hiện bug trước fix, human review critical changes. **Verification** → test fail trên base commit và pass trên fixed commit.

## 7. Common mistakes

Cho agent context thiếu; tin package/API nó nhớ; cho quyền secrets/production rộng; agent sửa tests để “pass”; generated tests mirror implementation; merge architecture refactor lớn mà không review boundaries.

## 8. Alternatives

Autocomplete tốt cho local edits. Repository search + human implementation phù hợp high-risk work. Deterministic codemods tốt cho mechanical transformations có rule rõ. Agent phù hợp khi task cần nhiều bước nhưng vẫn có verifiable feedback loop.

## 9. Trade-offs

### Advantages

Tăng tốc repository exploration, repetitive edits, test scaffolding và migration analysis.

### Costs / Risks

Hallucinated assumptions, insecure code, context gaps, token/tool cost và automation bias.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Dùng AI để giải thích nhưng phải build/run/test output.

### Middle

Cung cấp repository context, constraints và regression evidence.

### Senior

Thiết kế verification loop, review security/performance/architecture assumptions và phân biệt generated confidence với evidence.

### Technical Lead / Architect

Xác định permission boundaries, authoritative sources, tasks nào agent được tự động hóa và checkpoints nào bắt buộc human approval.

## 11. Key takeaway

- Coding agent là accelerator, không phải source of truth.
- Verification phải độc lập đủ để phát hiện agent tự hợp thức hóa thay đổi.
- Quyền tool/repository nên theo least privilege và impact của task.
