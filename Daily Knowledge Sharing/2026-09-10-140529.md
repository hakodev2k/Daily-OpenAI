# 1. C# `Task.WhenAll` + exception propagation: chạy concurrent I/O đúng cách mà không làm mất lỗi, cancellation và partial failure

## 1. What is it?

`Task.WhenAll` cho phép chờ nhiều asynchronous operations hoàn tất như một nhóm. Mental model quan trọng là **concurrency**, không nhất thiết là parallelism:

```text
Request
  ├─ HTTP call A ─────┐
  ├─ HTTP call B ─────┼─> await Task.WhenAll(...)
  └─ SQL call C ──────┘
```

Nếu các operations chủ yếu chờ I/O và độc lập nhau, khởi động chúng trước rồi `await` cùng lúc có thể giảm tổng latency từ gần tổng thời gian xuống gần operation chậm nhất.

Điểm khó không nằm ở syntax mà ở failure semantics: một task fail, một task cancel và một task succeed có thể cùng tồn tại trong một batch.

## 2. Why does it exist?

Code tuần tự:

```csharp
var profile = await profileClient.GetAsync(userId, ct);
var orders = await orderClient.GetAsync(userId, ct);
var rewards = await rewardClient.GetAsync(userId, ct);
```

sẽ cộng dồn latency nếu ba dependency độc lập. Nếu mỗi call mất khoảng 200 ms, tổng thời gian có thể gần 600 ms thay vì khoảng 200–250 ms.

Nhưng concurrency chỉ có ích khi dependencies thực sự độc lập và hệ thống downstream chịu được lượng đồng thời tăng lên.

## 3. How does it work?

Tạo tasks trước:

```csharp
var profileTask = profileClient.GetAsync(userId, ct);
var ordersTask = orderClient.GetAsync(userId, ct);
var rewardsTask = rewardClient.GetAsync(userId, ct);

await Task.WhenAll(profileTask, ordersTask, rewardsTask);
```

Các async operations bắt đầu tới điểm I/O mà không cần tạo một thread riêng cho mỗi task.

Nếu bất kỳ task nào fault, `WhenAll` hoàn thành ở trạng thái Faulted. Nếu không có fault nhưng có task canceled, nhóm hoàn thành Canceled. Khi `await` task tổng hợp, exception được rethrow theo await semantics; vì vậy khi cần điều tra **mọi** lỗi trong batch, phải xem trạng thái/`Exception` của từng task hoặc aggregate task thay vì giả định một `catch` cho biết toàn bộ câu chuyện.

## 4. Practical implementation

```csharp
public async Task<DashboardDto> GetDashboardAsync(
    Guid userId,
    CancellationToken ct)
{
    var profileTask = _profileClient.GetAsync(userId, ct);
    var ordersTask = _ordersClient.GetRecentAsync(userId, ct);
    var rewardsTask = _rewardsClient.GetBalanceAsync(userId, ct);

    var all = Task.WhenAll(profileTask, ordersTask, rewardsTask);

    try
    {
        await all;
    }
    catch
    {
        _logger.LogWarning(
            "Dashboard fan-out failed. Profile={ProfileStatus}, Orders={OrdersStatus}, Rewards={RewardsStatus}",
            profileTask.Status,
            ordersTask.Status,
            rewardsTask.Status);
        throw;
    }

    return new DashboardDto(
        await profileTask,
        await ordersTask,
        await rewardsTask);
}
```

Nếu một dependency là optional, có thể xử lý degradation riêng thay vì fail toàn dashboard.

## 5. Real production scenario

Một e-commerce product page gọi Pricing, Inventory và Reviews. Pricing và Inventory là critical; Reviews là optional.

Nếu dùng một `Task.WhenAll` rồi fail toàn response chỉ vì Reviews timeout, availability của product page bị phụ thuộc vào service không critical. Senior design phải phân loại dependency trước khi chọn failure semantics.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 giảm sau khi chuyển sang concurrent fan-out nhưng downstream bắt đầu rate-limit.

**Evidence** → trace cho thấy mỗi request tạo ba outgoing calls cùng lúc và dependency concurrency tăng gấp nhiều lần.

**Hypothesis** → tối ưu latency ở caller đã chuyển pressure sang downstream.

**Diagnosis** → so sánh request concurrency, outgoing dependency concurrency, 429/503 và connection usage trước/sau thay đổi.

**Fix** → giới hạn concurrency, cache dữ liệu phù hợp, batch API hoặc loại bỏ fan-out không cần thiết.

**Verification** → load test ở traffic thực tế; đo cả caller latency lẫn downstream saturation.

## 7. Common mistakes

* Dùng `Task.Run` để “làm async” cho I/O methods vốn đã async.
* Khởi chạy hàng nghìn tasks không giới hạn.
* Cho rằng `Task.WhenAll` luôn nhanh hơn code tuần tự.
* Fail toàn request vì một optional dependency.
* Bắt exception rồi mất context của task nào đã fail/cancel.

## 8. Alternatives

* Sequential await: đơn giản và đúng khi operation phụ thuộc kết quả trước.
* `Parallel.ForEachAsync`: phù hợp collection work có bounded parallelism.
* `Channel<T>`/worker queue: phù hợp workload dài hạn cần backpressure.
* Batch endpoint ở downstream: thường hiệu quả hơn fan-out nhiều network calls.

## 9. Trade-offs

### Advantages

* Giảm wall-clock latency cho independent I/O.
* Code orchestration tương đối đơn giản.
* Tận dụng async I/O thay vì block threads.

### Costs / Risks

* Tăng instantaneous load lên dependencies.
* Partial failure phức tạp hơn.
* Observability và timeout budget phải rõ ràng hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task.WhenAll` chạy nhiều asynchronous operations cùng khoảng thời gian chờ, không phải tự động tạo threads.

### Middle

Biết propagate `CancellationToken`, xử lý exceptions và không dùng concurrency cho dependent work.

### Senior

Đánh giá fan-out amplification, dependency criticality, partial failure và timeout budgets.

### Technical Lead / Architect

Quyết định dependency nào nên gọi song song, dependency nào nên batch/cache/degrade, và giới hạn concurrency ở đâu để bảo vệ hệ thống.

## 11. Key takeaway

* `Task.WhenAll` tối ưu wall-clock latency, nhưng có thể tăng pressure lên downstream.
* Concurrency strategy phải đi cùng failure semantics và observability.
* Không phải dependency nào cũng đáng làm cả request thất bại.

# 2. ASP.NET Core `IOptionsMonitor<T>` + configuration reload: thay đổi runtime config mà không biến configuration thành distributed-state problem

## 1. What is it?

ASP.NET Core Options Pattern bind configuration thành strongly typed objects. `IOptionsMonitor<T>` cho phép singleton hoặc long-lived services đọc current value và nhận callback khi configuration provider báo thay đổi.

```text
Configuration providers
      ↓
Options binding
      ↓
IOptionsMonitor<T>.CurrentValue
      ↓
long-lived service
```

Nó khác `IOptions<T>` ở chỗ value không cố định một lần cho application lifetime, và khác `IOptionsSnapshot<T>` vốn scoped theo request.

## 2. Why does it exist?

Một số cấu hình như feature threshold, polling interval hoặc integration timeout có thể cần thay đổi mà không restart process.

Nhưng runtime reload không nên được hiểu là distributed configuration protocol. Khi application có nhiều instances, từng process có thể nhận thay đổi ở thời điểm hơi khác nhau hoặc provider không hỗ trợ reload giống nhau.

## 3. How does it work?

Ví dụ:

```csharp
public sealed class PricingOptions
{
    public int TimeoutSeconds { get; init; } = 3;
}
```

Registration:

```csharp
builder.Services
    .AddOptions<PricingOptions>()
    .Bind(builder.Configuration.GetSection("Pricing"))
    .Validate(x => x.TimeoutSeconds is > 0 and <= 30)
    .ValidateOnStart();
```

Consumer:

```csharp
public sealed class PricingGateway
{
    private readonly IOptionsMonitor<PricingOptions> _options;

    public PricingGateway(IOptionsMonitor<PricingOptions> options)
        => _options = options;

    public TimeSpan CurrentTimeout =>
        TimeSpan.FromSeconds(_options.CurrentValue.TimeoutSeconds);
}
```

`OnChange` hữu ích khi cần rebuild derived state, nhưng callback phải thread-safe và lifecycle/disposal phải được quản lý.

## 4. Practical implementation

```csharp
public sealed class PollingWorker : BackgroundService
{
    private readonly IOptionsMonitor<PollingOptions> _options;
    private readonly ILogger<PollingWorker> _logger;

    public PollingWorker(
        IOptionsMonitor<PollingOptions> options,
        ILogger<PollingWorker> logger)
    {
        _options = options;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await PollOnceAsync(stoppingToken);

            var delay = TimeSpan.FromSeconds(
                _options.CurrentValue.IntervalSeconds);

            await Task.Delay(delay, stoppingToken);
        }
    }
}
```

Worker đọc config tại mỗi iteration nên không cần restart để đổi interval.

## 5. Real production scenario

Một SaaS chạy 12 App Service instances. Ops giảm external API timeout từ 10 xuống 3 giây để bảo vệ hệ thống khi provider degraded.

Nếu config source/reload propagation không đồng nhất, một số nodes dùng 3 giây còn nodes khác vẫn dùng 10 giây. Từ phía client, behavior trở nên nondeterministic theo load balancing.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng một endpoint có hai nhóm timeout behavior khác nhau giữa instances.

**Evidence** → structured log ghi `instanceId` và effective timeout cho thấy config versions khác nhau.

**Hypothesis** → runtime configuration drift.

**Diagnosis** → kiểm tra provider reload support, deployment/config propagation và timestamp/version của config.

**Fix** → dùng configuration source có consistency phù hợp hoặc coi config thay đổi critical như một deployment có versioning/health validation.

**Verification** → telemetry phải cho thấy toàn fleet đạt cùng expected config version.

## 7. Common mistakes

* Inject `IOptionsSnapshot<T>` vào singleton.
* Dùng `OnChange` callback để chạy async work phức tạp không kiểm soát.
* Cho phép reload security-critical settings mà không có audit/versioning.
* Không validate config mới.
* Giả định config file reload local tương đương distributed rollout.

## 8. Alternatives

* `IOptions<T>`: tốt cho immutable configuration sau startup.
* `IOptionsSnapshot<T>`: tốt khi muốn value mới theo DI scope/request.
* Feature-management/configuration service: phù hợp rollout có targeting, audit và fleet consistency cao hơn.
* Deployment-driven config: đơn giản và dễ rollback với settings critical.

## 9. Trade-offs

### Advantages

* Strong typing và validation.
* Long-lived services có thể nhận runtime changes.
* Giảm restart cho một số operational tuning.

### Costs / Risks

* Runtime state thay đổi làm debugging khó hơn.
* Multi-instance consistency không tự được giải quyết.
* Callback/lifecycle có thể tạo race conditions.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Options Pattern là typed view của configuration.

### Middle

Biết khác nhau giữa `IOptions`, `IOptionsSnapshot` và `IOptionsMonitor`.

### Senior

Quan tâm validation, thread safety, reload semantics và instance drift.

### Technical Lead / Architect

Quyết định cấu hình nào được phép dynamic, cấu hình nào phải qua deployment/change-control, và cách chứng minh fleet đã hội tụ cùng version.

## 11. Key takeaway

* Dynamic config là runtime state, vì vậy phải được quan sát và quản trị như state.
* `IOptionsMonitor<T>` không tự giải quyết distributed consistency.
* Security/correctness-critical settings thường cần rollout discipline mạnh hơn một file reload.

# 3. EF Core projection-first querying: giảm materialization, tracking và database I/O thay vì lạm dụng `Include`

## 1. What is it?

Projection-first nghĩa là query trực tiếp shape mà use case cần bằng `Select`, thay vì load một object graph entity lớn rồi mới map sang DTO.

```text
Database rows
   ↓ SELECT only needed columns
DTO / read model
```

Ví dụ một list page chỉ cần `Id`, `Number`, `CustomerName`, `Total`; nó không cần materialize toàn bộ `Order`, `Customer`, `Lines`, navigation collections.

## 2. Why does it exist?

`Include` rất tiện nhưng dễ biến read query thành “load domain graph”. Chi phí có thể gồm:

* nhiều columns hơn cần thiết
* join payload lớn
* entity materialization
* Change Tracker overhead
* Cartesian multiplication khi nhiều collections
* serialization accidental navigation data

Read model nên phản ánh nhu cầu của endpoint, không phải cấu trúc entity persistence.

## 3. How does it work?

```csharp
var rows = await db.Orders
    .AsNoTracking()
    .Where(x => x.Status == OrderStatus.Open)
    .Select(x => new OrderListItem(
        x.Id,
        x.Number,
        x.Customer.Name,
        x.Lines.Sum(l => l.Quantity * l.UnitPrice)))
    .ToListAsync(ct);
```

EF Core dịch expression tree thành SQL projection. Nếu translation thành công, database chỉ trả shape cần thiết thay vì entity graph đầy đủ.

Điểm Senior cần kiểm tra là generated SQL, database round trips và query plan, không chỉ code C# nhìn “gọn”.

## 4. Practical implementation

```csharp
public sealed record ProductSearchItem(
    Guid Id,
    string Name,
    decimal Price,
    bool InStock);

var products = await db.Products
    .AsNoTracking()
    .Where(p => p.IsPublished && p.Name.Contains(term))
    .OrderBy(p => p.Name)
    .Select(p => new ProductSearchItem(
        p.Id,
        p.Name,
        p.Price,
        p.Inventory.AvailableQuantity > 0))
    .Take(50)
    .ToListAsync(ct);
```

Đây là read-specific contract; domain entity vẫn có thể giàu behavior cho write path.

## 5. Real production scenario

Admin grid hiển thị 100 orders. Bản đầu dùng ba `Include`, load hàng nghìn line items và customer addresses dù UI chỉ hiện 6 fields.

Application CPU, allocation và SQL payload đều cao. Chuyển sang projection giảm data transfer và materialization đáng kể mà không cần cache hay scale database.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint list trả 100 records nhưng response mất 1.5 giây và query trả hàng chục MB dữ liệu.

**Evidence** → generated SQL có nhiều joins/columns; allocation profile cho thấy entity graph lớn.

**Hypothesis** → over-fetching.

**Diagnosis** → so sánh UI/API contract với columns/navigation thực sự được load.

**Fix** → projection, pagination, aggregate trong SQL khi hợp lý.

**Verification** → đo query bytes, duration, allocations và p95 endpoint sau thay đổi.

## 7. Common mistakes

* Dùng `Include` theo thói quen cho mọi navigation.
* Load entity rồi AutoMapper in-memory trong read-heavy endpoint.
* Cho DTO projection chứa method không translate được.
* Nghĩ `AsNoTracking` đã giải quyết over-fetching.
* Projection nhưng vẫn trả collection không bounded.

## 8. Alternatives

* `Include`: phù hợp khi thực sự cần entity graph, đặc biệt write/business operation.
* Raw SQL/Dapper: hữu ích cho read query rất đặc thù hoặc khi cần kiểm soát SQL tối đa.
* Database view/materialized view: phù hợp read model phức tạp, ổn định và được tái sử dụng nhiều.

## 9. Trade-offs

### Advantages

* Giảm data transfer và allocations.
* Read contract rõ ràng.
* Tránh accidental tracking.

### Costs / Risks

* Có nhiều DTO/read models hơn.
* Projection phức tạp có thể khó đọc.
* Không phải expression nào cũng translate tốt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` load related data còn `Select` định hình dữ liệu trả về.

### Middle

Biết projection DTO, `AsNoTracking`, pagination và kiểm tra SQL.

### Senior

Đo over-fetching, round trips, plan và materialization cost trước khi tối ưu.

### Technical Lead / Architect

Định nghĩa read/write boundary đủ rõ để API không phụ thuộc trực tiếp persistence entity graph.

## 11. Key takeaway

* Read endpoint nên query đúng shape cần dùng.
* `AsNoTracking` không sửa query đang tải quá nhiều dữ liệu.
* Tối ưu EF Core phải quan sát SQL và I/O, không chỉ C# syntax.

# 4. PostgreSQL transaction isolation + write skew: khi hai transaction đều hợp lệ riêng lẻ nhưng kết hợp lại phá invariant

## 1. What is it?

Write skew là anomaly nơi hai concurrent transactions đọc một điều kiện chung, sau đó cập nhật **khác rows**, nên không xảy ra lost update trực tiếp nhưng invariant toàn hệ thống vẫn bị phá.

Ví dụ invariant: luôn phải có ít nhất một bác sĩ on-call.

```text
T1 reads: A=true, B=true
T2 reads: A=true, B=true
T1 sets A=false
T2 sets B=false
Result: A=false, B=false
```

Mỗi transaction nghĩ vẫn còn người kia trực.

## 2. Why does it exist?

MVCC giúp concurrency tốt nhưng snapshot consistency không đồng nghĩa business invariant tự được serialize.

Nếu invariant trải qua nhiều rows hoặc predicate, row-level optimistic checks đơn giản có thể không đủ.

## 3. How does it work?

Ở isolation thấp hơn `Serializable`, mỗi transaction có thể đọc snapshot hợp lệ nhưng không nhận ra rằng transaction khác đồng thời làm thay đổi predicate mà business rule phụ thuộc.

PostgreSQL `Serializable` dùng Serializable Snapshot Isolation để phát hiện một số dangerous dependency structures và abort một transaction với serialization failure thay vì cho kết quả không serializable commit.

Application vì vậy phải sẵn sàng retry **toàn transaction** nếu operation thực sự retry-safe.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(
    System.Data.IsolationLevel.Serializable,
    ct);

var activeApprovers = await db.Approvers
    .CountAsync(x => x.TeamId == teamId && x.IsActive, ct);

if (activeApprovers <= 1)
    throw new InvalidOperationException("At least one active approver is required.");

approver.IsActive = false;
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Nếu database trả serialization failure, retry policy phải bao toàn read-check-write unit, không chỉ `SaveChanges`.

## 5. Real production scenario

Approval system yêu cầu project luôn có ít nhất một active approver. Hai admins disable hai approvers khác nhau gần như cùng lúc.

Không có row conflict vì họ update hai rows khác nhau. Invariant chỉ tồn tại ở predicate “count active approvers >= 1”.

## 6. Failure scenario & troubleshooting

**Symptom** → audit log cho thấy cả hai requests đều validation pass nhưng final state vi phạm rule.

**Evidence** → transactions overlap và mỗi request đọc snapshot trước khi request kia commit.

**Hypothesis** → write skew / insufficient isolation for cross-row invariant.

**Diagnosis** → mô phỏng hai concurrent transactions với controlled barriers.

**Fix** → `Serializable`, explicit lock trên coordination row, hoặc remodel invariant để database constraint/atomic operation bảo vệ được.

**Verification** → concurrency integration test phải chứng minh tối đa một transaction commit khi invariant bị cạnh tranh.

## 7. Common mistakes

* Đồng nhất optimistic concurrency với mọi loại concurrency anomaly.
* Chỉ đặt `rowversion` trên từng row khi invariant trải nhiều rows.
* Retry serialization failure sau khi đã phát external side effect.
* Nâng isolation toàn hệ thống mà không đo contention.

## 8. Alternatives

* Explicit advisory/row lock trên aggregate coordination record.
* Database constraint nếu invariant biểu diễn được bằng schema.
* Serializable transaction cho critical unit.
* Queue/serialized command processing nếu contention domain rất cao.

## 9. Trade-offs

### Advantages

* Bảo vệ cross-row invariant chính xác hơn.
* Serializable cho reasoning gần sequential execution.

### Costs / Risks

* Có thể tăng abort/retry dưới contention.
* Transaction scope phải rất sạch.
* External side effect trong transaction làm retry nguy hiểm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu concurrency bug không chỉ là hai users update cùng một row.

### Middle

Biết isolation level ảnh hưởng snapshot/locking behavior.

### Senior

Nhận diện invariant theo predicate, thiết kế retry-safe transaction và test concurrency chủ động.

### Technical Lead / Architect

Quyết định invariant nào phải enforce ở database boundary, invariant nào cần aggregate/serialization strategy, và chi phí contention chấp nhận được.

## 11. Key takeaway

* Cross-row business rules có thể bị phá dù không có lost update.
* Isolation level là correctness decision, không chỉ tuning knob.
* Retry chỉ an toàn khi toàn transaction và side effects được thiết kế cho retry.

# 5. MongoDB compound indexes + ESR rule: thiết kế index theo Equality → Sort → Range thay vì ghép field theo cảm tính

## 1. What is it?

Compound index chứa nhiều fields theo thứ tự xác định, ví dụ:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

Một heuristic phổ biến là ESR: Equality fields trước, sau đó Sort, rồi Range. Đây không phải định luật tuyệt đối, nhưng là mental model hữu ích khi thiết kế index từ access pattern.

## 2. Why does it exist?

Index chỉ hữu ích nếu key order giúp engine thu hẹp search space và/hoặc trả dữ liệu theo order mong muốn.

Cùng ba fields nhưng đổi thứ tự có thể tạo execution behavior rất khác. “Các field đều nằm trong index” không đồng nghĩa query sử dụng index hiệu quả.

## 3. How does it work?

Query:

```javascript
db.orders.find({
  tenantId: "t1",
  status: "Open",
  createdAt: { $gte: ISODate("2026-09-01") }
}).sort({ createdAt: -1 })
```

Index hợp lý:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

Equality prefix giới hạn branch index; `createdAt` tiếp theo phục vụ sort/range tốt hơn.

Nhưng nếu range field đứng trước sort field, engine có thể không sử dụng index order cho sort như mong muốn.

## 4. Practical implementation

```javascript
db.orders.createIndex(
  { tenantId: 1, status: 1, createdAt: -1 },
  { name: "ix_orders_tenant_status_created" }
)
```

Sau đó kiểm tra:

```javascript
db.orders.find({
  tenantId: "t1",
  status: "Open"
}).sort({ createdAt: -1 }).limit(50).explain("executionStats")
```

Quan tâm `totalKeysExamined`, `totalDocsExamined`, returned rows và có blocking sort hay không.

## 5. Real production scenario

Multi-tenant SaaS có 50 triệu documents. API list orders luôn filter `tenantId`, thường filter `status`, sort newest first.

Index chỉ `{ createdAt: -1 }` khiến engine scan rất nhiều keys rồi mới filter tenant/status. Latency đặc biệt xấu với tenant nhỏ nằm rải trong global timeline.

## 6. Failure scenario & troubleshooting

**Symptom** → query trả 50 documents nhưng examine hàng trăm nghìn keys.

**Evidence** → `executionStats` cho tỷ lệ examined/returned rất cao.

**Hypothesis** → compound index order không phù hợp access pattern.

**Diagnosis** → đối chiếu equality, sort, range và index prefixes.

**Fix** → thiết kế index theo dominant query shape; bỏ duplicate/redundant indexes sau đo lường.

**Verification** → execution stats và p95 giảm, write cost vẫn nằm trong budget.

## 7. Common mistakes

* Tạo một index cho mỗi field rồi kỳ vọng tương đương compound index.
* Copy ESR máy móc mà không xem cardinality/query distribution.
* Bỏ qua prefix rule.
* Tạo quá nhiều indexes khiến write amplification và RAM usage tăng.
* Chỉ nhìn query duration, không xem examined keys/docs.

## 8. Alternatives

* Single-field indexes: đủ cho query đơn giản.
* Index intersection: có thể giúp nhưng thường không thay thế compound index tối ưu cho hot path.
* Denormalized/read-model collection: hữu ích nếu query shape rất quan trọng và khác write model.

## 9. Trade-offs

### Advantages

* Query/filter/sort hiệu quả hơn khi index đúng access pattern.
* Giảm documents/keys examined.

### Costs / Risks

* Mỗi index tăng write/storage/memory cost.
* Index order tối ưu query này có thể kém cho query khác.
* Workload thay đổi có thể làm index cũ thành dead weight.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu compound index có thứ tự và prefix, không phải unordered set fields.

### Middle

Biết dùng `explain("executionStats")` và đọc examined vs returned.

### Senior

Cân bằng read latency với write amplification, memory và workload distribution.

### Technical Lead / Architect

Thiết kế data model/index strategy từ access patterns và tenant scale thay vì bê relational indexing habits sang MongoDB.

## 11. Key takeaway

* Compound-index key order là một phần của query design.
* ESR là heuristic, evidence từ `explain` mới quyết định.
* Index tốt cho read luôn có write/storage cost tương ứng.

# 6. CQRS với một database vs read/write stores riêng: tách intent mà không bắt buộc tạo distributed system

## 1. What is it?

CQRS — Command Query Responsibility Segregation — trước hết là tách **intent** giữa operations thay đổi state và operations đọc state.

Nó không tự động đồng nghĩa:

```text
Command DB + Event Sourcing + Message Bus + Read DB
```

Một hệ thống hoàn toàn có thể dùng CQRS với cùng một SQL database:

```text
Command handlers ─┐
                  ├─> SQL Database
Query handlers ───┘
```

## 2. Why does it exist?

Read và write thường có nhu cầu khác nhau. Write path quan tâm invariants, authorization và transaction. Read path quan tâm projection, filtering, pagination và performance.

Ép cả hai qua cùng generic service/repository abstraction có thể làm model trở nên khó tối ưu và khó diễn đạt intent.

## 3. How does it work?

Một command có thể load aggregate, enforce invariant và commit transaction:

```csharp
public sealed record ApproveInvoice(Guid InvoiceId);
```

Một query có thể projection trực tiếp:

```csharp
public sealed record GetInvoiceSummary(Guid InvoiceId);
```

Cùng database không tạo eventual consistency giữa command/query side. Khi scale/read requirement thực sự khác, read store riêng có thể được bổ sung sau qua events/outbox.

## 4. Practical implementation

```csharp
public async Task<InvoiceSummary?> Handle(
    GetInvoiceSummary query,
    CancellationToken ct)
{
    return await _db.Invoices
        .AsNoTracking()
        .Where(x => x.Id == query.InvoiceId)
        .Select(x => new InvoiceSummary(
            x.Id,
            x.Number,
            x.Status,
            x.Total))
        .SingleOrDefaultAsync(ct);
}
```

Write handler không cần reuse query repository nếu hai paths có mục đích khác nhau.

## 5. Real production scenario

Finance platform có command workflow phức tạp cho invoice approval nhưng dashboard read đơn giản. Tách handlers giúp dashboard dùng projection hiệu quả mà không bắt domain aggregate chịu trách nhiệm trình bày dữ liệu.

Team chưa có nhu cầu scale read độc lập, vì vậy thêm Elasticsearch/read database ngay sẽ chỉ tăng replication, monitoring và failure modes.

## 6. Failure scenario & troubleshooting

**Symptom** → team nói dùng CQRS nhưng mỗi feature phải sửa command model, read model, events, projector và hai databases dù traffic thấp.

**Evidence** → operational components tăng nhưng không có measurable requirement tương ứng.

**Hypothesis** → pattern bị đồng nhất với kiến trúc tối đa thay vì problem statement.

**Diagnosis** → review actual read/write scaling, latency, consistency và team ownership constraints.

**Fix** → giữ command/query separation nhưng collapse infrastructure nếu chưa cần distributed read model.

**Verification** → architecture đơn giản hơn mà business behavior/performance vẫn đáp ứng SLO.

## 7. Common mistakes

* Nghĩ CQRS bắt buộc Event Sourcing.
* Tạo một database cho read và một database cho write từ ngày đầu.
* Dùng MediatR rồi tuyên bố hệ thống đã có CQRS architecture.
* Không định nghĩa consistency expectation cho read model riêng.
* Duplicate code vô nghĩa chỉ để giữ “purity”.

## 8. Alternatives

* CRUD/application service: tốt cho domain đơn giản.
* CQRS cùng database: tốt khi muốn tách intent/model nhưng giữ consistency đơn giản.
* Separate read store: tốt khi read scale/query shape thực sự cần độc lập.
* Event Sourcing: giải quyết một tập vấn đề khác và có operational/domain cost lớn hơn.

## 9. Trade-offs

### Advantages

* Command/query intent rõ.
* Read path dễ tối ưu độc lập.
* Có đường tiến hóa nếu scale sau này.

### Costs / Risks

* Tăng số types/handlers.
* Separate stores tạo eventual consistency và replication burden.
* Overengineering dễ xảy ra nếu domain đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu command thay đổi state, query chỉ đọc state.

### Middle

Biết implement handlers và projection riêng mà không duplicate vô lý.

### Senior

Hiểu consistency, transaction và operational cost khi thêm read store.

### Technical Lead / Architect

Chọn mức CQRS tối thiểu đáp ứng complexity/scale hiện tại và chỉ phân tán khi có pressure thực tế.

## 11. Key takeaway

* CQRS là separation of intent trước khi là infrastructure topology.
* Một database vẫn có thể là CQRS hợp lệ.
* Separate read store phải được trả giá bằng eventual consistency và operations.

# 7. Azure Front Door origin health + failover: routing toàn cầu chỉ đáng tin khi health probes phản ánh đúng khả năng phục vụ traffic

## 1. What is it?

Azure Front Door đứng ở edge và route HTTP traffic tới origins dựa trên route, priority, weight, health và latency-related behavior.

```text
Users worldwide
      ↓
Azure Front Door
   ┌──┴───┐
Region A  Region B
```

Failover chỉ tốt nếu health probe trả lời câu hỏi đúng: “origin này có nên nhận production traffic ngay bây giờ không?”

## 2. Why does it exist?

DNS failover thường có propagation/caching delay và ít request-level visibility. Edge routing có thể phát hiện unhealthy origin và chuyển traffic nhanh hơn.

Nhưng health endpoint sai có thể tạo hai lỗi đối nghịch:

* báo Healthy khi app không thực sự phục vụ được traffic
* báo Unhealthy do dependency không critical, khiến toàn region bị rút traffic

## 3. How does it work?

Front Door gửi probes tới origin health path. Origin được đánh giá theo probe results và routing configuration.

Health endpoint nên phản ánh **traffic-serving readiness**, không phải “mọi dependency trong universe đều perfect”.

Ví dụ:

```text
/liveness  -> process sống
/readiness -> app có thể nhận request chính
/deep-check -> diagnostics, không nhất thiết dùng cho routing
```

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<DatabaseReadinessCheck>("database", tags: new[] { "ready" });

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = registration => registration.Tags.Contains("ready")
});
```

Không nên đưa optional Reviews API vào readiness của checkout service nếu checkout vẫn có fallback hợp lệ khi Reviews chết.

## 5. Real production scenario

E-commerce active/passive hai regions. Region A database connection pool bị exhaustion nên requests trả 503, nhưng `/health` chỉ trả process-alive và vẫn 200.

Front Door tiếp tục gửi traffic vào region A, biến failover architecture thành hình thức mà không có behavior thực tế.

## 6. Failure scenario & troubleshooting

**Symptom** → region gặp outage nhưng traffic không failover.

**Evidence** → origin request 5xx cao trong khi health probes vẫn 200.

**Hypothesis** → readiness check không đại diện serving capability.

**Diagnosis** → đối chiếu dependency failure với health-check implementation và Front Door origin status.

**Fix** → thiết kế readiness có timeout ngắn, dependency critical đúng mức và tránh expensive checks.

**Verification** → chaos test làm critical dependency fail; routing phải chuyển traffic trong expected recovery objective.

## 7. Common mistakes

* Health endpoint luôn trả 200 vì chỉ kiểm tra process.
* Check quá nhiều dependencies khiến optional outage kéo cả region xuống.
* Health probe thực hiện expensive database query.
* Không bảo vệ health endpoint khỏi dependency timeout dài.
* Có secondary region nhưng không test failover định kỳ.

## 8. Alternatives

* Azure Traffic Manager: DNS-based routing, phù hợp một số scenarios nhưng failover semantics khác.
* Application Gateway: regional L7 load balancing/WAF, không thay thế global edge routing hoàn toàn.
* Single-region App Service: đơn giản hơn nếu business RTO/RPO chưa cần multi-region.

## 9. Trade-offs

### Advantages

* Global edge entry point.
* Faster origin failover ở request-routing layer.
* Centralized routing/WAF/CDN capabilities.

### Costs / Risks

* Health semantics trở thành critical architecture contract.
* Multi-region data consistency vẫn phải giải quyết riêng.
* Cost và operational complexity tăng đáng kể.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Front Door route traffic tới origins và dùng probes để đánh giá health.

### Middle

Biết cấu hình health endpoint/readiness và phân biệt liveness.

### Senior

Thiết kế probe semantics, dependency criticality và chaos verification.

### Technical Lead / Architect

Quyết định multi-region có thực sự cần thiết, data failover hoạt động ra sao và RTO/RPO nào architecture phải chứng minh.

## 11. Key takeaway

* Failover tốt phụ thuộc health signal tốt.
* Readiness phải phản ánh khả năng phục vụ traffic, không phải kiểm tra mọi dependency.
* Multi-region routing không tự giải quyết multi-region data correctness.

# 8. `BackgroundService` + bounded `Channel<T>`: kiểm soát backpressure, graceful shutdown và memory khi producer nhanh hơn consumer

## 1. What is it?

`Channel<T>` là primitive producer-consumer trong .NET. Bounded channel giới hạn số items có thể buffer, tạo backpressure khi producer nhanh hơn consumer.

```text
Producer(s)
    ↓
[ bounded Channel ]
    ↓
BackgroundService consumer
```

Nếu channel đầy, producer có thể chờ thay vì tiếp tục cấp phát memory vô hạn.

## 2. Why does it exist?

Một `ConcurrentQueue<T>` + polling loop rất dễ trở thành unbounded queue. Khi downstream chậm, queue tăng cho tới khi process memory tăng, GC pressure cao hoặc OOM.

Bounded capacity biến overload thành behavior có thể kiểm soát thay vì memory leak logic.

## 3. How does it work?

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(1000)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true,
    SingleWriter = false
});
```

Khi có 1000 items chưa xử lý, `WriteAsync` phải chờ capacity. Pressure truyền ngược về producer.

Consumer dùng `ReadAllAsync(stoppingToken)` để nhận items cho tới cancellation/completion.

## 4. Practical implementation

```csharp
public sealed class JobWorker : BackgroundService
{
    private readonly Channel<Job> _channel;

    public JobWorker(Channel<Job> channel) => _channel = channel;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in _channel.Reader.ReadAllAsync(stoppingToken))
        {
            try
            {
                await ProcessAsync(job, stoppingToken);
            }
            catch (Exception ex)
            {
                // record failure / retry according to explicit policy
            }
        }
    }
}
```

Nếu jobs phải survive process restart, in-memory `Channel<T>` không đủ; cần durable queue như Azure Service Bus.

## 5. Real production scenario

API nhận image-processing requests. Version đầu enqueue vào in-memory queue không giới hạn. Khi image service chậm 10 phút, API vẫn nhận hàng chục nghìn jobs và process OOM.

Bounded channel cho internal best-effort workload có thể bảo vệ memory. Nếu jobs không được phép mất, durable broker mới là boundary đúng.

## 6. Failure scenario & troubleshooting

**Symptom** → API latency tăng sau khi channel đầy.

**Evidence** → queue depth chạm capacity, producer `WriteAsync` duration tăng.

**Hypothesis** → backpressure đang hoạt động vì consumer throughput thấp hơn arrival rate.

**Diagnosis** → đo arrival rate, service rate, queue depth và downstream latency.

**Fix** → tăng consumer capacity nếu bottleneck cho phép, giảm arrival rate, batch, hoặc chuyển sang durable distributed queue.

**Verification** → queue depth ổn định dưới sustained expected load và shutdown không bỏ work ngoài policy.

## 7. Common mistakes

* Dùng unbounded channel cho workload không bounded.
* Nghĩ channel là durable queue.
* Không propagate shutdown token.
* Spawn task cho từng item rồi phá bounded concurrency.
* Không có telemetry cho queue depth/process latency.

## 8. Alternatives

* `BlockingCollection`: legacy/synchronous producer-consumer scenarios.
* Azure Service Bus: durable, distributed, retry/dead-letter.
* `Parallel.ForEachAsync`: bounded processing cho finite collection.
* Direct synchronous processing: đơn giản nhất khi workload nhỏ và client cần kết quả ngay.

## 9. Trade-offs

### Advantages

* Backpressure rõ ràng.
* Async producer-consumer API.
* Peak memory bounded tốt hơn.

### Costs / Risks

* In-memory work mất khi process chết.
* Multi-instance coordination không được giải quyết.
* Capacity và full-mode trở thành product/reliability decision.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue có capacity và producer có thể phải chờ consumer.

### Middle

Biết implement `Channel<T>` với cancellation và hosted worker.

### Senior

Đo throughput, queue depth, overload behavior và graceful shutdown.

### Technical Lead / Architect

Quyết định workload nào chấp nhận in-memory loss và workload nào cần durable broker/distributed ownership.

## 11. Key takeaway

* Bounded queues biến overload thành backpressure thay vì memory explosion.
* In-memory queue không phải durable messaging.
* Queue capacity phải gắn với throughput và failure policy thực tế.

# 9. CORS vs CSRF: hai cơ chế thường bị nhầm lẫn nhưng giải quyết hai threat model hoàn toàn khác nhau

## 1. What is it?

CORS là browser policy kiểm soát **cross-origin JavaScript access** tới responses. CSRF là attack lợi dụng browser tự động gửi credentials, thường là cookies, để thực hiện request mà user không chủ ý.

CORS không phải authentication và cũng không phải CSRF protection tổng quát.

## 2. Why does it exist?

Same-Origin Policy ngăn JavaScript từ origin tùy ý đọc dữ liệu origin khác. CORS cho server chủ động nới quyền này cho origins tin cậy.

CSRF tồn tại vì browser có thể tự attach cookie vào request tới target site dù request bắt nguồn từ attacker page.

Threat models khác nhau:

```text
CORS: attacker JS có được đọc response cross-origin không?
CSRF: browser có thể gửi authenticated state-changing request ngoài ý user không?
```

## 3. How does it work?

CORS response có thể chứa:

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
```

Browser enforce policy; non-browser clients không bị CORS ngăn.

CSRF defenses thường gồm SameSite cookies, anti-forgery token và tránh unsafe state change qua GET.

Nếu API dùng bearer token mà JavaScript chủ động đặt trong `Authorization` header và attacker origin không có token, CSRF threat khác cookie-auth flow.

## 4. Practical implementation

ASP.NET Core CORS:

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("Frontend", policy =>
        policy.WithOrigins("https://app.example.com")
              .AllowAnyHeader()
              .AllowAnyMethod()
              .AllowCredentials());
});
```

Cookie auth nên cấu hình SameSite/Secure phù hợp và antiforgery cho unsafe browser form/API flows khi threat model yêu cầu.

Không dùng:

```csharp
AllowAnyOrigin().AllowCredentials()
```

vì credentialed cross-origin policy phải có origin boundary rõ ràng.

## 5. Real production scenario

Internal admin app dùng cookie authentication. Team nghĩ “chúng tôi đã khóa CORS nên không cần CSRF token”. Attacker gửi auto-submitting HTML form tới admin endpoint.

Form submission không cần attacker đọc response để gây side effect. Nếu cookie được browser gửi và endpoint không có CSRF defense phù hợp, CORS không cứu được.

## 6. Failure scenario & troubleshooting

**Symptom** → browser frontend bị CORS error nhưng Postman/curl gọi API bình thường.

**Evidence** → network tab cho thấy preflight/response thiếu CORS headers.

**Hypothesis** → browser cross-origin policy, không phải server authentication failure.

**Diagnosis** → kiểm tra request origin, preflight method/headers, middleware ordering và credentials mode.

**Fix** → allow chính xác origin/method/header cần thiết; không mở wildcard để “fix nhanh”.

**Verification** → trusted origin hoạt động; untrusted origin vẫn bị browser chặn; CSRF controls được test riêng.

## 7. Common mistakes

* Dùng CORS như firewall/API security.
* `AllowAnyOrigin` để sửa frontend lỗi nhanh.
* Nghĩ CORS ngăn curl/server-to-server attackers.
* Nghĩ CORS tự chống CSRF.
* Dùng GET cho state-changing operation.

## 8. Alternatives

Không có một “alternative” duy nhất vì đây là hai lớp khác nhau:

* Reverse proxy/network ACL bảo vệ network boundary.
* Authentication/authorization bảo vệ identity/access.
* SameSite/antiforgery bảo vệ CSRF scenarios.
* CORS kiểm soát browser cross-origin JS access.

## 9. Trade-offs

### Advantages

* CORS cho phép browser integration có boundary origin rõ.
* CSRF controls bảo vệ cookie-authenticated state changes.

### Costs / Risks

* Misconfiguration dễ tạo false sense of security.
* Cross-site product requirements có thể làm cookie/CORS policy phức tạp.
* Quá rộng làm tăng attack surface; quá chặt làm integration hỏng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt origin policy với authentication.

### Middle

Biết cấu hình CORS, preflight và cookie/antiforgery cơ bản.

### Senior

Threat-model cookie auth, bearer tokens, SameSite và cross-origin flows đúng cách.

### Technical Lead / Architect

Định nghĩa browser trust boundaries và security controls theo từng authentication model thay vì áp một policy chung cho mọi API.

## 11. Key takeaway

* CORS và CSRF giải quyết hai vấn đề khác nhau.
* CORS được browser enforce, không phải API firewall.
* Security design phải bắt đầu từ credential model và threat model.

# 10. TypeScript discriminated unions cho API state: loại bỏ impossible UI states thay vì rải boolean flags khắp frontend

## 1. What is it?

Discriminated union dùng một field literal chung để biểu diễn các state hợp lệ dưới dạng type-safe union.

Thay vì:

```ts
isLoading: boolean
hasError: boolean
data?: Product[]
error?: string
```

có thể dùng:

```ts
type LoadState<T> =
  | { kind: 'idle' }
  | { kind: 'loading' }
  | { kind: 'success'; data: T }
  | { kind: 'error'; message: string };
```

Compiler loại bỏ combinations vô nghĩa như `isLoading=true`, `hasError=true`, `data` cũng tồn tại nhưng không rõ state nào thắng.

## 2. Why does it exist?

Boolean flags scale rất kém khi state machine phức tạp. Ba booleans có thể tạo tám combinations dù business chỉ cho phép bốn states.

Frontend bugs thường xuất hiện từ **impossible state được code cho phép biểu diễn**.

Type system có thể encode invariant trước khi runtime phải xử lý nó.

## 3. How does it work?

`kind` là discriminator. Trong `switch`, TypeScript narrow union tự động:

```ts
function render<T>(state: LoadState<T>) {
  switch (state.kind) {
    case 'idle':
      return null;
    case 'loading':
      return 'Loading...';
    case 'success':
      return state.data;
    case 'error':
      return state.message;
  }
}
```

Có thể dùng exhaustive check để compile fail khi thêm state mới mà quên xử lý.

## 4. Practical implementation

```ts
type ProductState =
  | { kind: 'loading' }
  | { kind: 'loaded'; products: Product[] }
  | { kind: 'empty' }
  | { kind: 'failed'; problem: ApiProblem };

function assertNever(value: never): never {
  throw new Error(`Unhandled state: ${JSON.stringify(value)}`);
}

function statusText(state: ProductState): string {
  switch (state.kind) {
    case 'loading': return 'Loading';
    case 'loaded': return `${state.products.length} products`;
    case 'empty': return 'No products';
    case 'failed': return state.problem.title;
    default: return assertNever(state);
  }
}
```

Pattern này cũng hữu ích cho API result models, payment state và workflow UI.

## 5. Real production scenario

Checkout frontend có `isSubmitting`, `isSuccess`, `hasError`, `requires3DS`. Một race khiến success response đến sau khi timeout handler đã set error; UI hiện cả success modal lẫn error banner.

Chuyển sang explicit state machine/union khiến transition phải chọn một state duy nhất và compiler buộc render logic xử lý từng state.

## 6. Failure scenario & troubleshooting

**Symptom** → UI hiển thị hai trạng thái mâu thuẫn sau concurrent async callbacks.

**Evidence** → state snapshot có nhiều booleans true cùng lúc.

**Hypothesis** → state representation cho phép invalid combinations.

**Diagnosis** → viết ra state-transition diagram và đếm combinations hiện tại so với business-valid states.

**Fix** → discriminated union hoặc reducer/state machine với explicit transitions.

**Verification** → tests cover legal transitions; TypeScript exhaustive checks bắt missing cases khi schema thay đổi.

## 7. Common mistakes

* Dùng optional fields cho mọi state rồi phải null-check khắp nơi.
* Cast `as` để ép compiler im lặng.
* Union type nhưng vẫn giữ duplicate booleans cũ.
* Không version/validate API contract nên runtime data vẫn có thể sai dù compile-time type đẹp.
* Biến state machine rất đơn giản thành framework phức tạp không cần thiết.

## 8. Alternatives

* Simple enum + separate data: đủ khi states ít và data giống nhau.
* Reducer: tốt khi transitions phức tạp hơn local setters.
* Dedicated state-machine library: hữu ích cho workflow nhiều transitions/guards nhưng có learning/complexity cost.

## 9. Trade-offs

### Advantages

* Impossible states khó biểu diễn hơn.
* Narrowing và exhaustive checking mạnh.
* UI logic rõ theo state machine.

### Costs / Risks

* Nhiều explicit types hơn.
* Team cần hiểu TypeScript narrowing.
* Runtime API payload vẫn cần validation nếu nguồn không trusted.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu union cho phép một trong các shapes xác định.

### Middle

Biết dùng discriminator, narrowing và exhaustive switch.

### Senior

Nhìn state modeling như correctness tool cho async UI, không chỉ TypeScript trick.

### Technical Lead / Architect

Quyết định nơi type-level state machine đủ tốt và nơi workflow cần reducer/state-machine architecture rõ ràng hơn.

## 11. Key takeaway

* Data model tốt nên khiến invalid state khó biểu diễn.
* Boolean flags nhanh lúc đầu nhưng complexity tăng theo combinations.
* Compile-time types không thay thế runtime validation của external API data.
