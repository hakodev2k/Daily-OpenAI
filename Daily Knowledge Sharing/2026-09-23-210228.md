# 1. .NET `ArrayPool<T>`: giảm allocation nhưng đổi lại ownership phức tạp hơn

## 1. What is it?

Mental model: `ArrayPool<T>` cho phép thuê một array đã tồn tại, sử dụng tạm thời rồi trả lại pool thay vì luôn tạo array mới và chờ GC thu hồi. Nó là kỹ thuật quản lý buffer, không phải cache business data.

Pool đặc biệt hữu ích ở hot path tạo nhiều buffer ngắn hạn, nhất là buffer đủ lớn để gây allocation/GC pressure đáng kể.

## 2. Why does it exist?

Allocation managed memory rất tiện, nhưng workload serialization, compression, parsing hoặc network processing có thể tạo hàng nghìn buffers mỗi giây. Allocation rate cao làm GC chạy thường xuyên; buffer lớn còn có thể gây áp lực lên LOH.

Pool đổi bài toán từ “allocate/collect” thành “borrow/return”. Đổi lại developer phải chịu trách nhiệm lifecycle.

## 3. How does it work?

```text
Rent(minLength)
   -> pool chọn array có capacity >= minLength
   -> caller tạm sở hữu buffer
   -> sử dụng
Return(array)
   -> buffer có thể được caller khác thuê lại
```

`Rent(4096)` không đảm bảo array dài chính xác 4096. Sau `Return`, caller không còn quyền sử dụng buffer.

## 4. Practical implementation

```csharp
using System.Buffers;

static async Task<int> ReadChunkAsync(Stream stream, CancellationToken ct)
{
    byte[] buffer = ArrayPool<byte>.Shared.Rent(16 * 1024);
    try
    {
        return await stream.ReadAsync(buffer.AsMemory(0, 16 * 1024), ct);
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
    }
}
```

Nếu buffer chứa secret hoặc dữ liệu nhạy cảm, cân nhắc clear trước khi return. Việc clear có CPU cost nên không bật máy móc cho mọi workload.

## 5. Real production scenario

Một API upload xử lý hàng trăm file đồng thời và mỗi chunk tạo `new byte[64 KB]`. Allocation rate tăng, Gen 2 collections xuất hiện thường xuyên hơn và p99 latency rung mạnh. Pooling buffer làm giảm allocation pressure, nhưng chỉ sau khi profiler xác nhận buffer allocation là contributor đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu thỉnh thoảng bị corrupt. **Evidence** → một async operation giữ reference tới buffer sau khi caller đã `Return`. **Hypothesis** → use-after-return. **Diagnosis** → trace ownership và lifetime quanh async boundaries. **Fix** → chỉ return sau khi consumer hoàn tất; copy dữ liệu nếu ownership phải chuyển. **Verification** → concurrency/load test và allocation profiling.

## 7. Common mistakes

Return buffer quá sớm; giả định `Rent(n).Length == n`; giữ rented buffer lâu như cache; quên `finally`; pool mọi allocation nhỏ dù profiler không chỉ ra vấn đề; để sensitive bytes tồn tại trong pooled buffer mà không đánh giá security.

## 8. Alternatives

`new T[]` đơn giản và đúng cho phần lớn code. `MemoryPool<T>` phù hợp khi cần memory-owner abstraction. `stackalloc`/`Span<T>` hữu ích cho buffer nhỏ, lifetime ngắn và có giới hạn stack rõ ràng.

## 9. Trade-offs

### Advantages

Giảm allocation rate và GC pressure trong hot paths.

### Costs / Risks

Ownership phức tạp, dễ use-after-return/data leakage, retained pool memory và code khó reasoning hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu allocation và GC trước khi dùng pool.

### Middle
Biết `Rent`/`Return` với `try/finally` và giới hạn valid slice.

### Senior
Dùng profiler để chứng minh lợi ích, kiểm soát async ownership và sensitive data.

### Technical Lead / Architect
Quyết định hot path nào xứng đáng nhận complexity của manual buffer lifecycle.

## 11. Key takeaway

- Pooling là optimization cho measured allocation pressure.
- Rented array có ownership tạm thời và capacity có thể lớn hơn yêu cầu.
- Sau `Return`, tuyệt đối không tiếp tục dùng buffer.

# 2. ASP.NET Core graceful shutdown: shutdown cũng là một production workflow

## 1. What is it?

Graceful shutdown là quá trình application nhận tín hiệu dừng, ngừng nhận work mới, cho work đang chạy cơ hội hoàn tất trong một deadline, flush/close resources rồi process mới thoát.

## 2. Why does it exist?

Container restart, App Service recycle, deployment và node maintenance đều có thể terminate process. Nếu process biến mất tức thì, request có thể bị cắt giữa response, message đang xử lý mất lock, background operation dừng giữa side effect.

## 3. How does it work?

```text
SIGTERM / host stop
 -> application stopping token cancelled
 -> server stops accepting new work
 -> in-flight work gets grace period
 -> hosted services StopAsync
 -> process exits
```

Graceful không có nghĩa chờ vô hạn. Platform luôn cần hard deadline.

## 4. Practical implementation

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var job = await ReceiveAsync(stoppingToken);
            await ProcessAsync(job, stoppingToken);
        }
    }
}
```

Truyền `stoppingToken` xuyên I/O chain. Với message broker, settlement chỉ xảy ra sau khi side effects hoàn tất theo idempotency contract.

## 5. Real production scenario

Rolling deployment thay 20 pods. Worker cũ không observe cancellation và tiếp tục xử lý job dài. Platform kill pod sau termination grace period; message được redeliver trong khi side effect đầu tiên đã commit. Idempotency + shutdown-aware processing biến duplicate thành tình huống dự kiến thay vì corruption.

## 6. Failure scenario & troubleshooting

**Symptom** → deploy làm tăng 499/5xx hoặc duplicate jobs. **Evidence** → logs kết thúc đột ngột, request duration vượt shutdown window. **Hypothesis** → work không observe cancellation hoặc grace period không đủ. **Diagnosis** → correlate termination events, in-flight work và broker delivery. **Fix** → bounded work, cancellation propagation, idempotency, readiness removal trước termination. **Verification** → kill/restart test dưới load.

## 7. Common mistakes

Nuốt `OperationCanceledException` rồi tiếp tục loop; bắt đầu work mới khi stopping; dùng fire-and-forget task; kỳ vọng shutdown luôn đủ thời gian; flush telemetry bằng sleep; không test deployment termination path.

## 8. Alternatives

Work dài có thể đưa sang durable queue/workflow thay vì giữ trong HTTP request. Checkpointing phù hợp batch có thể resume.

## 9. Trade-offs

Grace period tăng correctness nhưng làm rollout chậm nếu work không bounded. Durable orchestration thêm infrastructure nhưng chịu process death tốt hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `CancellationToken` là cooperative cancellation.

### Middle
Propagate token và implement `BackgroundService` đúng lifecycle.

### Senior
Thiết kế idempotency, bounded shutdown và test termination.

### Technical Lead / Architect
Chọn work nào được phép sống trong process và work nào cần durable execution boundary.

## 11. Key takeaway

- Process termination là normal operation, không phải edge case.
- Cancellation chỉ hiệu quả khi toàn call chain hợp tác.
- Graceful shutdown không thay thế idempotency/durability.

# 3. PostgreSQL MVCC và vacuum: update không đơn giản là ghi đè row

## 1. What is it?

MVCC (Multi-Version Concurrency Control) cho phép transactions nhìn các phiên bản dữ liệu phù hợp với snapshot của chúng thay vì buộc readers và writers luôn block nhau. Trong PostgreSQL, `UPDATE` thường tạo row version mới; version cũ trở thành dead tuple khi không còn transaction cần nó.

## 2. Why does it exist?

Nếu mọi read phải khóa chặn write hoặc mọi write phải chờ readers, concurrency giảm mạnh. MVCC cung cấp snapshot semantics với ít reader/writer blocking hơn, đổi lại database phải quản lý nhiều row versions và reclaim chúng.

## 3. How does it work?

```text
T1 snapshot sees row version V1
T2 UPDATE -> creates V2
T2 COMMIT
T1 can still see V1 according to snapshot
new transaction sees V2

later VACUUM -> reclaim obsolete V1 when safe
```

Visibility dựa trên transaction metadata, không chỉ timestamp application.

## 4. Practical implementation

Đừng “implement MVCC”; hãy vận hành workload phù hợp. Theo dõi long-running transactions và autovacuum health. Ví dụ tìm transactions giữ snapshot lâu:

```sql
SELECT pid, xact_start, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Một transaction mở hàng giờ có thể giữ versions mà vacuum chưa thể reclaim.

## 5. Real production scenario

Reporting job mở transaction rồi stream dữ liệu trong 3 giờ. Trong lúc đó bảng Orders nhận update liên tục. Dead tuples tăng, table/index bloat và query latency dần xấu dù traffic không đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → table size tăng nhanh, scans chậm, dead tuples cao. **Evidence** → long transaction + vacuum lag. **Hypothesis** → old snapshot ngăn cleanup. **Diagnosis** → `pg_stat_activity`, vacuum statistics, table/index size. **Fix** → rút ngắn transaction/report strategy, tune autovacuum khi evidence yêu cầu. **Verification** → dead tuple trend và query latency giảm.

## 7. Common mistakes

Giữ transaction mở quanh remote API; coi `UPDATE` là in-place overwrite; disable autovacuum để “giảm CPU”; chạy manual `VACUUM FULL` như routine fix mà không hiểu lock/operational impact.

## 8. Alternatives

SQL Server cũng có row-versioning isolation modes nhưng implementation khác. Pessimistic locking có semantics khác và có thể phù hợp cho critical section ngắn.

## 9. Trade-offs

MVCC tăng concurrency và snapshot consistency nhưng tạo storage cleanup work, transaction-ID/version management và operational sensitivity với long transactions.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu transaction có thể thấy snapshot khác nhau.

### Middle
Không giữ transaction lâu và biết kiểm tra active transactions.

### Senior
Liên hệ MVCC, vacuum, bloat và query performance.

### Technical Lead / Architect
Thiết kế reporting/batch boundary không gây áp lực kéo dài lên transactional store.

## 11. Key takeaway

- MVCC đổi lock contention lấy version-management cost.
- Long-running transaction có thể gây hậu quả lâu sau câu query ban đầu.
- Vacuum là phần thiết yếu của PostgreSQL operation.

# 4. Elasticsearch alias-based reindexing: thay index mà giảm downtime

## 1. What is it?

Alias là tên logic trỏ tới một hoặc nhiều Elasticsearch indices. Application query alias thay vì hard-code physical index. Khi mapping/analyzer thay đổi cần reindex, ta xây index mới rồi chuyển alias.

## 2. Why does it exist?

Nhiều mapping changes không thể biến đổi toàn bộ dữ liệu hiện hữu in-place theo cách an toàn. Nếu application phụ thuộc trực tiếp `products-v17`, migration buộc code/deploy và data lifecycle dính chặt nhau.

## 3. How does it work?

```text
Search API -> products-read -> products-v17

build products-v18
bulk reindex + catch up changes
atomic alias switch
Search API -> products-read -> products-v18
```

Alias switch nhỏ; phần khó là đảm bảo v18 đầy đủ và synchronized trước cutover.

## 4. Practical implementation

Conceptual alias update:

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v17", "alias": "products-read" } },
    { "add":    { "index": "products-v18", "alias": "products-read" } }
  ]
}
```

Trước switch cần validate document count, representative queries, mapping và synchronization watermark.

## 5. Real production scenario

E-commerce đổi analyzer để hỗ trợ synonym/search normalization. Team tạo index mới, backfill từ primary database, replay changes phát sinh trong thời gian backfill rồi chạy smoke queries trước alias switch.

## 6. Failure scenario & troubleshooting

**Symptom** → sau switch, search thiếu products mới cập nhật. **Evidence** → v18 backfill hoàn tất nhưng change events trong cửa sổ migration chưa replay hết. **Hypothesis** → migration thiếu catch-up phase. **Diagnosis** → so source-of-truth watermark với index watermark. **Fix** → replay missing changes hoặc rollback alias nếu old index vẫn valid. **Verification** → reconciliation counts + sampled business queries.

## 7. Common mistakes

Chỉ so document count; xóa old index ngay sau switch; dual-write không có reconciliation; hard-code physical index; thay mapping mà không test query relevance.

## 8. Alternatives

In-place update phù hợp thay đổi không yêu cầu rebuild. Blue/green search cluster mạnh hơn nhưng operational cost lớn hơn. Database full-text search có thể đủ nếu requirements đơn giản.

## 9. Trade-offs

Alias migration giảm downtime và rollback nhanh nhưng tạm thời nhân storage, cần synchronization/reconciliation và migration tooling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt alias và physical index.

### Middle
Thực hiện reindex + alias switch có validation.

### Senior
Thiết kế catch-up/reconciliation và rollback.

### Technical Lead / Architect
Quyết định search schema lifecycle, source of truth và migration SLO.

## 11. Key takeaway

- Alias tách application contract khỏi physical index lifecycle.
- Reindex correctness phụ thuộc backfill + catch-up + validation.
- Giữ rollback path cho đến khi index mới được chứng minh ổn định.

# 5. Saga orchestration vs choreography: transaction xuyên service không còn là một `BEGIN TRANSACTION`

## 1. What is it?

Saga chia business transaction dài thành chuỗi local transactions. Nếu bước sau thất bại, hệ thống chạy compensating actions phù hợp business thay vì rollback ACID toàn bộ. Orchestration có coordinator quyết định bước tiếp; choreography để services phản ứng với events.

## 2. Why does it exist?

Database transaction không tự mở rộng an toàn qua Payment, Inventory, Shipping và external providers. Giữ distributed lock/2PC qua network làm availability và operational complexity tăng mạnh, nhiều external API cũng không hỗ trợ.

## 3. How does it work?

```text
Orchestration:
Order Saga -> Reserve Inventory -> Charge Payment -> Create Shipment
     | failure payment
     +-> Release Inventory

Choreography:
OrderCreated -> InventoryReserved -> PaymentCharged -> ShipmentRequested
```

Compensation là business operation mới, không phải time-travel rollback.

## 4. Practical implementation

Saga state nên durable:

```csharp
public sealed record OrderSagaState(
    Guid OrderId,
    bool InventoryReserved,
    bool PaymentCharged,
    string Status);
```

Mỗi command/event cần correlation ID, idempotency key và explicit timeout. Persist state trước/đồng thời với reliable messaging bằng Outbox khi cần.

## 5. Real production scenario

Checkout reserve stock thành công nhưng payment provider timeout. Không biết payment đã charge hay chưa. Saga không được lập tức “retry charge” vô hạn; cần idempotency key/query status và compensation theo confirmed state.

## 6. Failure scenario & troubleshooting

**Symptom** → order mắc `Processing` hàng giờ. **Evidence** → saga state cho thấy inventory reserved, payment unknown, timeout event không chạy. **Hypothesis** → missing timeout/recovery transition. **Diagnosis** → inspect saga state + broker history + provider correlation. **Fix** → durable timeout/reconciliation workflow. **Verification** → chaos test mất message, duplicate và provider timeout.

## 7. Common mistakes

Gọi mọi event flow là Saga; compensation giả định luôn thành công; không persist workflow state; choreography tạo dependency graph không ai nhìn thấy; orchestration biến thành god-service chứa domain logic của mọi service.

## 8. Alternatives

Một database transaction vẫn đơn giản hơn nếu modules có thể nằm cùng transactional boundary. Modular Monolith thường tránh Saga complexity khi organizational/scale pressure chưa cần Microservices.

## 9. Trade-offs

### Advantages

Cho phép workflow xuyên autonomous services và chịu partial failure.

### Costs / Risks

Eventual consistency, compensation complexity, observability khó hơn và nhiều intermediate states.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu local transaction không rollback remote service.

### Middle
Implement idempotent steps/correlation.

### Senior
Thiết kế timeout, compensation, recovery và observability.

### Technical Lead / Architect
Quyết định có thực sự cần service boundary khiến Saga trở thành bắt buộc hay không.

## 11. Key takeaway

- Saga quản lý business consistency qua local transactions.
- Compensation không tương đương database rollback.
- Nếu một transaction local giải quyết được, nó thường đơn giản hơn Saga.

# 6. Azure Key Vault + Managed Identity: application không cần sở hữu credential để đọc secret

## 1. What is it?

Managed Identity cung cấp identity cho Azure workload; Key Vault lưu secrets/keys/certificates và authorize identity truy cập. Mental model: application chứng minh “tôi là workload này” thay vì mang một client secret dài hạn để chứng minh danh tính.

## 2. Why does it exist?

Secret trong `appsettings.json`, environment variable hay CI/CD variable vẫn phải được phân phối, rotate và tránh leak. Managed Identity loại bỏ một lớp bootstrap credential khi workload chạy trên Azure service hỗ trợ.

## 3. How does it work?

```text
App Service / VM / Container workload
 -> Azure identity endpoint
 -> token for Key Vault
 -> Key Vault authorization
 -> requested secret/key operation
```

Application không nhận password của Managed Identity.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(configuration["KeyVaultUri"]!),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("PaymentsApiKey", ct);
```

Local development có thể dùng developer credential chain; Production dùng Managed Identity. RBAC/access policy phải theo least privilege.

## 5. Real production scenario

App Service cần API key của legacy payment provider. Identity của app chỉ được `get` secret cụ thể cần thiết; deployment pipeline không cần copy secret vào app settings.

## 6. Failure scenario & troubleshooting

**Symptom** → Production startup 403 khi đọc Key Vault. **Evidence** → identity token acquisition thành công nhưng vault authorization denied. **Hypothesis** → RBAC scope/identity sai. **Diagnosis** → xác định principal thực tế, role assignment và network access. **Fix** → cấp đúng minimum permission, không cấp Owner để “test”. **Verification** → request secret và audit logs.

## 7. Common mistakes

Managed Identity nhưng vẫn hard-code fallback secret; quyền vault quá rộng; đọc Key Vault trên mọi request; không cache/refresh có chủ đích; quên Private Endpoint/DNS khi vault network-restricted; log secret value khi exception.

## 8. Alternatives

Workload identity ở Kubernetes; client certificate/service principal khi Managed Identity không khả dụng. Mỗi lựa chọn khác nhau về bootstrap credential và rotation burden.

## 9. Trade-offs

Giảm secret distribution nhưng tăng dependency vào identity/RBAC/networking của cloud và cần thiết kế startup/degradation behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt secret store và identity.

### Middle
Dùng `DefaultAzureCredential`, RBAC đúng scope.

### Senior
Troubleshoot token/RBAC/network, rotation và caching.

### Technical Lead / Architect
Thiết kế identity-first access và loại bỏ long-lived credentials nơi có thể.

## 11. Key takeaway

- Key Vault bảo vệ secret; Managed Identity giải quyết workload identity.
- Không cấp quyền rộng để chữa lỗi cấu hình.
- Identity, network và secret lifecycle phải được thiết kế cùng nhau.

# 7. Kubernetes resource requests/limits: scheduler, CPU throttling và OOMKilled

## 1. What is it?

`requests` mô tả lượng resource scheduler dùng để đặt Pod lên node; `limits` đặt trần runtime theo resource. CPU và memory có failure behavior khác: CPU có thể bị throttled; vượt memory limit có thể dẫn tới OOM kill.

## 2. Why does it exist?

Không có resource contracts, một noisy workload có thể chiếm node và làm neighbors suy giảm. Nhưng limit đặt sai cũng tự tạo incident.

## 3. How does it work?

```text
Pod requests -> scheduler capacity decision
Pod running:
 CPU > limit -> throttling
 memory > limit -> process/container may be OOMKilled
```

Requests còn ảnh hưởng utilization nhìn bởi autoscaling tùy configuration.

## 4. Practical implementation

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
```

Giá trị phải đến từ profiling/load tests và Production telemetry, không copy từ service khác.

## 5. Real production scenario

.NET API có memory limit 256 MiB nhưng startup cache + normal heap peak đạt 300 MiB. Pod chạy local tốt, Production liên tục `OOMKilled`, restart rồi lặp lại thành `CrashLoopBackOff`.

## 6. Failure scenario & troubleshooting

**Symptom** → latency p99 tăng nhưng node CPU còn rảnh. **Evidence** → container CPU throttling cao và CPU limit thấp. **Hypothesis** → limit bóp burst cần thiết. **Diagnosis** → container metrics + request latency + runtime counters. **Fix** → tune resource contract hoặc giảm CPU work. **Verification** → load test với same limits.

## 7. Common mistakes

Requests bằng zero; memory limit quá sát average; chỉ nhìn node metrics; tăng limit thay vì điều tra leak; đặt CPU limit giống nhau cho mọi workload; không load test container với production constraints.

## 8. Alternatives

Dedicated nodes/isolation cho workload đặc biệt; Vertical Pod Autoscaler recommendations; application-level concurrency control để giảm peak pressure.

## 9. Trade-offs

Resource constraints tăng isolation/scheduling predictability nhưng sai sizing gây throttling, OOM và lãng phí capacity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu request khác limit.

### Middle
Đọc Pod status/events và container metrics.

### Senior
Liên hệ .NET GC/heap, throttling, HPA và load shape.

### Technical Lead / Architect
Đặt capacity model/SLO và ownership cho resource tuning.

## 11. Key takeaway

- Requests phục vụ scheduling; limits kiểm soát runtime consumption.
- CPU pressure và memory pressure thất bại khác nhau.
- Sizing phải dựa trên workload thực và telemetry.

# 8. Contract testing: kiểm tra integration boundary thay vì mock theo tưởng tượng

## 1. What is it?

Contract testing xác minh producer và consumer đồng ý về interface: endpoint, fields, types, required/optional semantics, status codes hoặc message schema. Nó nằm giữa unit tests và full E2E.

## 2. Why does it exist?

Consumer unit test có thể mock response mà producer chưa bao giờ trả. Full E2E cho mọi service combination chậm, flaky và khó ownership. Contract test tập trung vào boundary có nguy cơ breaking change.

## 3. How does it work?

```text
Consumer expectation
 -> contract artifact/schema
 -> producer verification
 -> CI blocks incompatible change
```

Contract không chứng minh business workflow toàn hệ thống đúng; nó chứng minh interface compatibility trong phạm vi đã mô tả.

## 4. Practical implementation

Với HTTP API, có thể kiểm tra OpenAPI compatibility và consumer-driven examples. Ví dụ integration test tối thiểu:

```csharp
var response = await client.GetAsync("/api/orders/42");
response.EnsureSuccessStatusCode();

var order = await response.Content.ReadFromJsonAsync<OrderContract>();
Assert.NotNull(order);
Assert.NotEqual(Guid.Empty, order.Id);
```

Giá trị lớn hơn nằm ở việc producer verification dùng contract consumer thực sự phụ thuộc, không phải DTO snapshot vô nghĩa.

## 5. Real production scenario

Order API đổi `total` từ number sang object `{ amount, currency }`. Producer tests pass; frontend build cũng pass vì fixture cũ. Contract verification phát hiện consumer vẫn yêu cầu numeric `total` trước deployment.

## 6. Failure scenario & troubleshooting

**Symptom** → contract suite đỏ sau thay đổi additive tưởng là safe. **Evidence** → consumer parser dùng strict schema. **Hypothesis** → compatibility assumptions khác nhau. **Diagnosis** → xem exact consumer expectation. **Fix** → version/evolve contract hoặc sửa consumer trước. **Verification** → producer + consumer CI.

## 7. Common mistakes

Snapshot toàn response khiến tests brittle; contract test thay thế E2E hoàn toàn; mock provider behavior không có verification; consumer yêu cầu fields nó không thật sự dùng; không quản lý version contract.

## 8. Alternatives

Integration test với real service mạnh hơn nhưng đắt hơn; schema compatibility ở broker phù hợp event contracts; E2E vẫn cần cho vài critical journeys.

## 9. Trade-offs

Contract tests feedback nhanh và localize ownership nhưng thêm CI/artifact workflow và không bắt mọi semantic integration bug.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu API contract không chỉ là URL.

### Middle
Viết boundary tests với realistic provider verification.

### Senior
Thiết kế compatibility/versioning strategy.

### Technical Lead / Architect
Quyết định boundary nào cần contract test và tránh biến test topology thành distributed monolith.

## 11. Key takeaway

- Mock chỉ có giá trị nếu expectation khớp producer thực.
- Contract testing bảo vệ compatibility, không thay mọi E2E.
- Test đúng fields/semantics consumer thực sự phụ thuộc.

# 9. Akamai/CDN `Cache-Control`: cache policy là một distributed data policy

## 1. What is it?

`Cache-Control` mô tả cacheability và freshness semantics cho browser/shared caches. CDN như Akamai có thể giữ response gần user, giảm origin latency/load, nhưng cache policy sai có thể phân phối stale hoặc private data ở quy mô rất lớn.

## 2. Why does it exist?

Static assets không cần quay về origin mỗi request. Ngược lại account page cá nhân không được shared-cache như public asset. HTTP caching cung cấp contract giữa origin, intermediary và browser.

## 3. How does it work?

```text
Browser -> Akamai edge
           | fresh HIT -> response
           | miss/stale
           v
        Origin -> Cache-Control -> edge stores/forwards
```

Ví dụ immutable fingerprinted asset:

```http
Cache-Control: public, max-age=31536000, immutable
```

HTML thay đổi thường xuyên cần policy khác; không copy header này sang mọi response.

## 4. Practical implementation

ASP.NET Core static assets nên dùng content-hashed filenames khi muốn TTL dài. Với dynamic response, thiết kế `public/private/no-store`, `max-age`, `s-maxage` theo data ownership và invalidation capability.

Kiểm tra thực tế bằng response headers và CDN cache status; đừng suy luận chỉ từ application config.

## 5. Real production scenario

Marketing site deploy CSS mới với cùng `/site.css` nhưng edge TTL 24 giờ. HTML mới reference URL cũ nên một số POP/browser tiếp tục dùng CSS cũ. Fingerprinted `/site.a81f.css` biến deploy thành URL mới thay vì phụ thuộc purge timing.

## 6. Failure scenario & troubleshooting

**Symptom** → user ở region A thấy content cũ, region B thấy mới. **Evidence** → edge HIT với object age cao; origin trả bản mới. **Hypothesis** → CDN freshness/purge mismatch. **Diagnosis** → inspect cache key, headers, age và POP behavior. **Fix** → purge đúng object hoặc version URL; sửa cache policy. **Verification** → request nhiều edge locations và kiểm tra origin load.

## 7. Common mistakes

Cache authenticated response ở shared cache; TTL dài cho URL không version; cache key bỏ query/header thực sự ảnh hưởng representation; purge toàn site như routine deployment; nhầm browser cache với CDN cache.

## 8. Alternatives

Origin caching/Redis giảm backend work nhưng không giảm network distance như CDN. Browser cache chỉ phục vụ một client. CDN phù hợp content có reuse giữa users/regions.

## 9. Trade-offs

TTL dài giảm latency/origin cost nhưng tăng stale risk và invalidation burden. Purge tăng control nhưng không nên thay versioned asset design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu browser cache khác edge cache.

### Middle
Đọc `Cache-Control`, `Age`, cache status và dùng fingerprinting.

### Senior
Thiết kế cache key/invalidation và điều tra regional stale content.

### Technical Lead / Architect
Định nghĩa caching policy theo data sensitivity, freshness SLO và origin capacity.

## 11. Key takeaway

- CDN caching là distributed state.
- TTL dài an toàn nhất khi URL content-addressed/versioned.
- Cache policy phải xét cả correctness và security.

# 10. AI coding agent verification: agent tăng throughput, không chuyển ownership correctness

## 1. What is it?

AI coding agent có thể đọc repository, sửa nhiều files, chạy tests và đề xuất implementation. Mental model đúng là một probabilistic engineering worker có tool access, không phải compiler, specification engine hay security authority.

## 2. Why does it exist?

Nhiều engineering tasks gồm repository navigation, repetitive edits, test scaffolding và migration work. Agent giảm thời gian thao tác, nhưng model có thể hiểu sai requirement, dùng API/version không tồn tại hoặc tạo tests chỉ chứng minh implementation của chính nó.

## 3. How does it work?

```text
Requirement
 -> repository/context retrieval
 -> model plans edits
 -> tools modify code
 -> build/tests/static analysis
 -> human/automated verification
 -> review/merge decision
```

Quality phụ thuộc context và verification loop, không chỉ model capability.

## 4. Practical implementation

Một workflow an toàn nên yêu cầu agent:

```text
1. Read authoritative requirements from main branch.
2. Inspect implementation and existing tests.
3. Make minimal scoped changes.
4. Build with pinned SDK/package versions.
5. Run unit + integration + E2E where relevant.
6. Report commands, failures and unresolved assumptions.
7. Never weaken tests merely to obtain green CI.
```

Security-sensitive logic như authorization vẫn phải dựa trên deterministic code, threat model và explicit review.

## 5. Real production scenario

Agent thêm retry quanh payment API và tests đều xanh. Review production semantics phát hiện POST charge không có idempotency key; timeout có thể dẫn tới double charge. Generated unit tests mocked provider nên không thể phát hiện failure mode đó.

## 6. Failure scenario & troubleshooting

**Symptom** → PR lớn, tests xanh nhưng behavior sai requirement. **Evidence** → tests assert implementation details, không có integration scenario. **Hypothesis** → agent grounded vào code hiện tại thay vì authoritative requirement. **Diagnosis** → trace requirement-to-test coverage và run real dependencies/test containers. **Fix** → constrain source hierarchy, add independent acceptance tests, inspect diff. **Verification** → build/test/E2E + manual review của critical invariants.

## 7. Common mistakes

Cho agent tự sửa requirement để khớp code; tin package/API hallucination; coi generated tests là independent evidence; trao merge/deploy quyền không có guardrails; đưa secrets/production data vào context; yêu cầu “make tests pass” mà không bảo vệ test intent.

## 8. Alternatives

IDE assistant phù hợp edits nhỏ có human-in-loop liên tục. Deterministic codemod tốt hơn cho mechanical transformation. Static analyzers/compiler phù hợp rules có thể formalize.

## 9. Trade-offs

Agent tăng tốc repository-scale work nhưng tăng nhu cầu provenance, sandboxing, deterministic verification và review discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Dùng AI để giải thích/gợi ý nhưng luôn build và hiểu code trước khi nhận.

### Middle
Cung cấp context tốt, kiểm tra APIs và viết acceptance tests độc lập.

### Senior
Threat-model generated changes, kiểm tra failure semantics và production behavior.

### Technical Lead / Architect
Thiết kế agent permissions, authoritative sources, CI gates, auditability và phạm vi nào tuyệt đối cần human approval.

## 11. Key takeaway

- Agent output là candidate change, không phải bằng chứng correctness.
- Verification phải độc lập với chính implementation được sinh ra.
- Source hierarchy, tool permissions và CI gates là một phần của AI engineering architecture.
