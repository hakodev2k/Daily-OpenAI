# 1. `TimeProvider` và `DateTimeOffset`: làm time-dependent .NET code có thể test và vận hành đúng

## 1. What is it?

`DateTimeOffset` biểu diễn một thời điểm kèm UTC offset; `TimeProvider` cung cấp abstraction chuẩn của .NET cho current time và timer behavior. Mental model quan trọng: business code không nên phụ thuộc trực tiếp vào đồng hồ hệ điều hành nếu thời gian là một phần của rule cần kiểm thử.

## 2. Why does it exist?

Code gọi `DateTime.UtcNow` rải rác khó tạo deterministic test cho expiration, retry window, scheduled behavior hoặc token lifetime. Ngoài ra, `DateTime` với `Kind` không rõ ràng dễ tạo bug khi convert timezone.

## 3. How does it work?

Production dùng `TimeProvider.System`; test có thể cung cấp provider kiểm soát được. Domain/application logic nhận một nguồn thời gian thay vì tự đọc global clock. Persist instant thường dùng UTC/`DateTimeOffset`; timezone là rule riêng khi cần hiển thị hoặc tính lịch địa phương.

## 4. Practical implementation

```csharp
public sealed class PromotionService(TimeProvider clock)
{
    public bool IsActive(Promotion p)
    {
        var now = clock.GetUtcNow();
        return p.StartsAt <= now && now < p.EndsAt;
    }
}

builder.Services.AddSingleton(TimeProvider.System);
```

Test inject fake provider và advance clock thay vì `Task.Delay` hoặc sửa system clock.

## 5. Real production scenario

Một promotion e-commerce hết hạn lúc 00:00 theo business timezone. Backend lưu instant UTC nhưng UI gửi local time không kèm offset. Nếu boundary không rõ, campaign có thể kết thúc lệch một giờ khi DST thay đổi ở thị trường khác.

## 6. Failure scenario & troubleshooting

**Symptom** → test expiration flaky hoặc Production sai giờ nhưng local đúng. **Evidence** → log cả UTC instant, offset và timezone input. **Hypothesis** → code trộn local time với UTC hoặc đọc clock trực tiếp. **Diagnosis** → trace conversion boundaries. **Fix** → chuẩn hóa instant và inject `TimeProvider`. **Verification** → test trước/sau boundary và DST cases.

## 7. Common mistakes

Dùng `DateTime.Now` cho persisted timestamps; convert timezone nhiều lần; mock static clock bằng framework phức tạp; coi offset và timezone là một khái niệm; dùng sleep trong test time-based logic.

## 8. Alternatives

Một custom `IClock` vẫn hợp lệ và đơn giản trong codebase cũ. `TimeProvider` giảm abstraction tự chế và hỗ trợ timer APIs hiện đại. Với domain rất đơn giản, truyền `DateTimeOffset now` trực tiếp vào method còn minh bạch hơn.

## 9. Trade-offs

### Advantages

Deterministic tests, rõ time boundary, giảm flaky behavior.

### Costs / Risks

Thêm dependency vào services; vẫn phải thiết kế timezone/business-calendar semantics đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt UTC instant, offset và local display.

### Middle

Inject clock và viết boundary tests.

### Senior

Thiết kế persistence/API timezone contract và DST scenarios.

### Technical Lead / Architect

Chuẩn hóa time semantics toàn hệ thống; quyết định nơi business timezone được áp dụng.

## 11. Key takeaway

- Time là dependency khi business logic phụ thuộc vào nó.
- Persist instant và timezone rule là hai concerns khác nhau.
- Deterministic clock tốt hơn sleep-based tests.

# 2. ASP.NET Core Health Checks: phân biệt liveness, readiness và dependency health

## 1. What is it?

Health Check là endpoint machine-readable mô tả khả năng process sống và khả năng instance nhận traffic. Liveness trả lời “process có cần restart không?”, readiness trả lời “instance có sẵn sàng phục vụ request không?”.

## 2. Why does it exist?

Một process có thể chạy nhưng chưa warm-up, mất dependency quan trọng hoặc đang drain trước shutdown. Nếu load balancer chỉ nhìn process existence, traffic vẫn được gửi tới instance chưa sẵn sàng.

## 3. How does it work?

Orchestrator/load balancer gọi endpoints định kỳ. Readiness failure thường loại instance khỏi traffic; liveness failure có thể trigger restart. Không nên biến liveness thành một chuỗi kiểm tra mọi dependency vì outage database có thể khiến toàn bộ pods restart đồng loạt.

## 4. Practical implementation

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, tags: ["ready"]);

app.MapHealthChecks("/health/live", new()
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new()
{
    Predicate = r => r.Tags.Contains("ready")
});
```

## 5. Real production scenario

Sau rolling deployment, instance mới cần load configuration và establish required state. Readiness giữ nó ngoài traffic cho tới khi startup hoàn tất, trong khi liveness vẫn xác nhận process không bị deadlock/crash.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency outage làm tất cả containers restart liên tục. **Evidence** → liveness endpoint gọi SQL và fail cùng lúc với database. **Hypothesis** → dependency health bị đặt sai probe. **Diagnosis** → xem probe config và restart count. **Fix** → liveness tối giản; readiness phản ánh traffic capability. **Verification** → simulate SQL outage, instances không restart storm nhưng được xử lý traffic theo policy.

## 7. Common mistakes

Health endpoint luôn trả 200; liveness phụ thuộc external APIs; check quá nặng gây load; expose sensitive diagnostics public; readiness không tính startup/shutdown state.

## 8. Alternatives

Synthetic monitoring kiểm tra user journey từ bên ngoài nhưng không thay probe. Application metrics/alerts phát hiện degradation dài hạn; health checks chủ yếu phục vụ routing/orchestration decisions.

## 9. Trade-offs

### Advantages

Tự động traffic management và safer deployments.

### Costs / Risks

Probe sai có thể tạo outage amplification; dependency checks tăng traffic và coupling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu live khác ready.

### Middle

Cấu hình endpoints và tags đúng.

### Senior

Thiết kế degraded behavior, startup/drain và probe cost.

### Technical Lead / Architect

Quyết định dependency nào thực sự chặn traffic và tránh restart cascade.

## 11. Key takeaway

- Liveness không phải dependency dashboard.
- Readiness là traffic-routing contract.
- Probe sai có thể làm failure lớn hơn failure gốc.

# 3. EF Core Interceptors: cross-cutting database behavior mà không làm mờ transaction boundary

## 1. What is it?

EF Core Interceptors cho phép quan sát hoặc can thiệp lifecycle của database commands, connections, transactions và `SaveChanges`. Chúng phù hợp cho concern hạ tầng có tính hệ thống như telemetry hoặc auditing kỹ thuật.

## 2. Why does it exist?

Nếu mỗi repository tự log SQL timing, add audit metadata hoặc enforce cùng technical policy, code bị lặp và dễ thiếu. Interceptor tạo một extension point tập trung mà không yêu cầu wrapper quanh mọi `DbContext` call.

## 3. How does it work?

EF Core gọi interceptor callbacks trước/sau operation. Interceptor có thể observe, modify hoặc suppress operation tùy API. Vì nó nằm dưới application layer, business decision quan trọng không nên bị ẩn trong interceptor.

## 4. Practical implementation

```csharp
public sealed class SlowCommandInterceptor(ILogger<SlowCommandInterceptor> log)
    : DbCommandInterceptor
{
    public override async ValueTask<DbDataReader> ReaderExecutedAsync(
        DbCommand command, CommandExecutedEventData data,
        DbDataReader result, CancellationToken ct = default)
    {
        if (data.Duration > TimeSpan.FromSeconds(1))
            log.LogWarning("Slow SQL {Duration} {Command}", data.Duration, command.CommandText);
        return result;
    }
}
```

Đăng ký interceptor trong `DbContextOptionsBuilder`.

## 5. Real production scenario

SaaS API cần phát hiện query chậm theo deployment. Command interceptor thêm structured telemetry nhất quán mà không sửa hàng trăm query handlers.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng sau khi thêm auditing interceptor. **Evidence** → trace cho thấy interceptor gọi network service trong `SavingChanges`. **Hypothesis** → cross-cutting hook đưa external I/O vào transaction path. **Diagnosis** → profile callback duration. **Fix** → giữ interceptor nhẹ; đưa external side effect qua Outbox sau commit. **Verification** → transaction duration trở lại baseline.

## 7. Common mistakes

Nhét business rule vào interceptor; sửa SQL tùy tiện; log parameter chứa PII/secrets; gọi external service trong transaction callback; assume interceptor thay Repository/Application boundary.

## 8. Alternatives

Decorator phù hợp application-level behavior; middleware phù hợp HTTP concern; domain events phù hợp business semantics. Interceptor phù hợp EF/database lifecycle concern.

## 9. Trade-offs

### Advantages

Centralized, consistent, ít boilerplate.

### Costs / Risks

Behavior trở nên implicit; hook sai có thể ảnh hưởng mọi query/transaction.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết interceptor là EF lifecycle hook.

### Middle

Implement telemetry/audit concern an toàn.

### Senior

Phân biệt technical cross-cutting với business logic và đánh giá transaction impact.

### Technical Lead / Architect

Đặt policy rõ cho interceptor để tránh hidden architecture.

## 11. Key takeaway

- Interceptor tốt cho infrastructure concern, không phải nơi giấu business workflow.
- Callback nằm trên critical database path nên phải nhẹ.
- Quan sát transaction boundary trước khi thêm side effect.

# 4. SQL Server Query Store: phát hiện execution-plan regression bằng evidence

## 1. What is it?

Query Store lưu lịch sử query text, execution plans và runtime statistics. Nó giúp so sánh một query qua thời gian thay vì chỉ xem plan hiện tại.

## 2. Why does it exist?

SQL có thể đột nhiên chậm dù application code không đổi: statistics, data distribution hoặc plan compilation tạo plan mới tệ hơn. Khi incident xảy ra, plan cũ thường đã biến mất khỏi cache.

## 3. How does it work?

Query Store persist query/plan/runtime data trong database. Engineer có thể tìm query có duration/CPU/reads tăng, so plan IDs trước/sau và xác định regression. Plan forcing có thể là mitigation nhưng không thay root-cause analysis.

## 4. Practical implementation

```sql
ALTER DATABASE Sales SET QUERY_STORE = ON;

SELECT TOP (20)
    q.query_id,
    p.plan_id,
    rs.avg_duration,
    rs.avg_logical_io_reads
FROM sys.query_store_query q
JOIN sys.query_store_plan p ON p.query_id = q.query_id
JOIN sys.query_store_runtime_stats rs ON rs.plan_id = p.plan_id
ORDER BY rs.avg_duration DESC;
```

## 5. Real production scenario

Orders API p95 tăng ngay sau data import. Application trace chỉ ra SQL. Query Store cho thấy query chuyển từ seek-oriented plan sang scan-heavy plan và logical reads tăng mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng sau một thời điểm rõ. **Measure** → dependency p95 và Query Store runtime stats. **Localize** → một query/plan ID. **Hypothesis** → plan regression. **Test** → so plans, estimates, statistics. **Change** → sửa access pattern/statistics/index hoặc force plan tạm thời. **Measure again** → reads và p95 giảm.

## 7. Common mistakes

Force plan vĩnh viễn mà không hiểu nguyên nhân; chỉ nhìn duration; bỏ qua data distribution; bật capture không quản lý storage; coi Query Store thay cho execution-plan literacy.

## 8. Alternatives

Extended Events cho event-level diagnostics; Application Insights tìm request path; actual execution plan phân tích một execution cụ thể. Query Store mạnh ở historical comparison.

## 9. Trade-offs

### Advantages

Có lịch sử regression và runtime evidence ngay trong database.

### Costs / Risks

Storage/overhead cần quản lý; plan forcing có thể trở nên stale khi workload đổi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu query có thể có nhiều plans.

### Middle

Tìm query regression và đọc basic metrics.

### Senior

Liên hệ estimates, I/O, statistics, locking và latency.

### Technical Lead / Architect

Đưa Query Store vào production diagnostic/runbook và governance.

## 11. Key takeaway

- Query regression cần historical evidence, không chỉ plan hiện tại.
- Logical reads và cardinality thường giải thích latency tốt hơn cảm giác.
- Plan forcing nên là mitigation có kiểm soát.

# 5. Cosmos DB 429 throttling: RU budget, partition pressure và retry behavior

## 1. What is it?

Cosmos DB trả HTTP `429 Too Many Requests` khi operation vượt provisioned Request Units hoặc capacity khả dụng. Response thường cung cấp retry delay; SDK có retry behavior nhưng latency vẫn tăng.

## 2. Why does it exist?

RU là capacity model bảo vệ shared/distributed storage resources. Unlimited request rate không thể được phục vụ với fixed provisioned throughput; throttling tạo backpressure rõ ràng.

## 3. How does it work?

Request được route theo partition key. Một logical/physical partition nóng có thể throttle dù tổng RU toàn container nhìn có vẻ còn dư trong một số cấu hình. Query cross-partition cũng tiêu thụ RU trên nhiều partitions.

## 4. Practical implementation

```csharp
var response = await container.ReadItemAsync<Order>(
    id,
    new PartitionKey(customerId),
    cancellationToken: ct);

logger.LogInformation("RU={Ru}", response.RequestCharge);
```

Theo dõi `RequestCharge`, 429 rate, retry count và partition-key distribution.

## 5. Real production scenario

Một tenant enterprise import dữ liệu hàng loạt với cùng partition key. Tổng traffic tăng vừa phải nhưng partition đó trở thành hotspot; API của tenant có p99 tăng do retries.

## 6. Failure scenario & troubleshooting

**Symptom** → p95/p99 tăng, SDK không luôn surface exception vì retry thành công. **Evidence** → 429 metrics, RU charge, partition distribution. **Hypothesis** → hot partition hoặc under-provisioned throughput. **Diagnosis** → correlate throttling theo partition/workload. **Fix** → redesign key, smooth writes, autoscale/provision phù hợp hoặc giảm query cost. **Verification** → 429/retry latency giảm.

## 7. Common mistakes

Chỉ tăng RU mà không kiểm tra hot key; query không có partition key; retry layer chồng lên SDK gây retry amplification; coi 429 luôn là outage.

## 8. Alternatives

Azure SQL phù hợp relational/transaction-heavy workload; MongoDB có capacity/index model khác. Cosmos phù hợp khi distribution, latency và global scale thực sự cần thiết.

## 9. Trade-offs

### Advantages

Capacity measurable, distributed scaling và predictable service model.

### Costs / Risks

Partition-key decision khó đổi; RU cost và retry latency có thể bất ngờ nếu access pattern kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RU và partition key.

### Middle

Đo request charge và xử lý SDK retry đúng.

### Senior

Phân tích hotspot, cross-partition cost và tail latency.

### Technical Lead / Architect

Chọn partition strategy theo workload growth và cost model trước khi schema ổn định.

## 11. Key takeaway

- 429 là capacity signal cần đo, không chỉ exception.
- Partition distribution quan trọng hơn tổng request count.
- Retry che lỗi khỏi caller nhưng không xóa latency/cost.

# 6. Bulkhead Pattern: giới hạn blast radius khi một dependency bị chậm

## 1. What is it?

Bulkhead chia capacity thành các pool/limits để failure ở một dependency hoặc workload không chiếm hết resources của hệ thống. Tên lấy từ vách ngăn tàu: một khoang ngập không làm cả tàu chìm.

## 2. Why does it exist?

Nếu mọi request cùng dùng một concurrency pool, dependency chậm có thể giữ toàn bộ outbound slots, threads hoặc connections. Các endpoint không liên quan cũng suy giảm dù dependency của chúng khỏe.

## 3. How does it work?

Mỗi dependency/workload có concurrency limit và queue nhỏ hoặc fail-fast policy. Bulkhead không sửa dependency; nó giới hạn số resource được phép mắc kẹt vì dependency đó.

## 4. Practical implementation

```csharp
private readonly SemaphoreSlim _reviewsLimit = new(20);

public async Task<ReviewDto?> GetAsync(string id, CancellationToken ct)
{
    if (!await _reviewsLimit.WaitAsync(TimeSpan.FromMilliseconds(50), ct))
        return null; // business-approved degradation
    try { return await CallReviewsAsync(id, ct); }
    finally { _reviewsLimit.Release(); }
}
```

Production có thể dùng resilience library/pipeline thay custom primitive.

## 5. Real production scenario

Product page gọi Reviews API. Reviews latency tăng 20 giây. Bulkhead giới hạn 20 calls; phần còn lại fallback “reviews temporarily unavailable”, trong khi checkout và account APIs không bị resource starvation.

## 6. Failure scenario & troubleshooting

**Symptom** → một dependency outage kéo toàn API xuống. **Evidence** → outbound concurrency, queue length và connection usage đều tập trung ở dependency. **Hypothesis** → shared capacity không có isolation. **Diagnosis** → map resource pools. **Fix** → timeout + bulkhead + degradation policy. **Verification** → chaos test dependency chậm; unrelated endpoints giữ SLO.

## 7. Common mistakes

Limit quá cao nên không có isolation; queue vô hạn; bulkhead nhưng timeout dài; fallback trả dữ liệu sai business; mỗi request tự tạo semaphore.

## 8. Alternatives

Separate process/service cho isolation mạnh hơn nhưng operational cost lớn. Queue-based async boundary phù hợp work không cần synchronous response. Bulkhead in-process là bước nhẹ hơn.

## 9. Trade-offs

### Advantages

Giảm blast radius, bảo vệ capacity và graceful degradation.

### Costs / Risks

Có thể reject request sớm; cần sizing và per-dependency telemetry.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu resource isolation.

### Middle

Implement bounded concurrency và timeout.

### Senior

Sizing limit theo downstream capacity và SLO.

### Technical Lead / Architect

Quyết định isolation boundary: in-process, queue, service hay dedicated infrastructure.

## 11. Key takeaway

- Resilience không chỉ retry; capacity isolation thường quan trọng hơn.
- Queue vô hạn phá mục tiêu bulkhead.
- Degradation phải được business chấp nhận trước incident.

# 7. Azure App Service autoscale: scale theo tín hiệu capacity thay vì CPU một cách máy móc

## 1. What is it?

Autoscale thay đổi số App Service instances dựa trên metric/rule hoặc schedule. Nó giải quyết capacity elasticity, không sửa bottleneck ở database, external API hay inefficient code.

## 2. Why does it exist?

Traffic enterprise thay đổi theo giờ/campaign. Fixed instance count hoặc lãng phí cost hoặc thiếu capacity. Tuy nhiên CPU không phải luôn là metric tốt cho I/O-bound ASP.NET Core workload.

## 3. How does it work?

Azure Monitor metrics kích hoạt scale rules với threshold, duration và cooldown. Instance mới cần startup/warm-up; load balancer chỉ nên gửi traffic khi application sẵn sàng.

## 4. Practical implementation

Thiết kế rule dựa trên evidence: CPU cho CPU-bound workload; request queue/response time hoặc custom metric khi phù hợp. Application dùng Managed Identity, config externalized và không phụ thuộc local in-memory session để scale-out an toàn.

```text
Azure Monitor metric -> Autoscale rule -> App Service Plan instances
                                      -> readiness/warm-up -> traffic
```

## 5. Real production scenario

Marketing campaign làm request rate tăng 4x. API CPU chỉ 45% vì phần lớn thời gian chờ SQL; response time vẫn tăng. Scale theo CPU đơn thuần phản ứng quá muộn, trong khi database đã gần connection limit.

## 6. Failure scenario & troubleshooting

**Symptom** → autoscale thêm instances nhưng p95 tiếp tục tăng. **Evidence** → SQL connections/latency tăng, app CPU thấp. **Hypothesis** → bottleneck downstream. **Diagnosis** → distributed trace + capacity metrics. **Fix** → xử lý database/access pattern và đặt max scale bảo vệ dependency. **Verification** → load test toàn critical path.

## 7. Common mistakes

Scale theo CPU mặc định không đo workload; cooldown quá ngắn gây oscillation; state lưu local memory; không tính cold/warm-up; scale app vượt database capacity.

## 8. Alternatives

Container Apps/Kubernetes có scaling model linh hoạt hơn nhưng vận hành phức tạp. Vertical scale đơn giản cho workload nhỏ. Scheduled scale phù hợp peak dự đoán được.

## 9. Trade-offs

### Advantages

Elastic capacity và cost control tốt hơn fixed overprovisioning.

### Costs / Risks

Scale lag, downstream amplification và chi phí tăng nhanh; metric/rule cần tuning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu scale-up và scale-out.

### Middle

Cấu hình rule và stateless app.

### Senior

Chọn metric theo bottleneck, warm-up và dependency capacity.

### Technical Lead / Architect

Thiết kế capacity envelope toàn hệ thống, identity/networking/monitoring và cost guardrails.

## 11. Key takeaway

- Autoscale chỉ hữu ích nếu metric đại diện capacity pressure.
- Scale application không tự scale downstream dependencies.
- Load test phải đo toàn critical path.

# 8. Trunk-based development + Feature Flags: tách deployment khỏi feature release

## 1. What is it?

Trunk-based development giữ branches ngắn và integrate thường xuyên vào main/trunk. Feature Flag cho phép code đã deploy nhưng behavior mới chưa được bật cho toàn bộ users.

## 2. Why does it exist?

Long-lived branches tạo merge risk và delayed integration. Nếu deployment đồng nghĩa release feature, team buộc phải giữ code chưa hoàn chỉnh ngoài main hoặc gom release lớn.

## 3. How does it work?

```text
commit -> build -> tests -> artifact -> deploy
                              |
                              v
                        feature disabled
                              |
                    targeted enablement
                              |
                    monitor -> expand/rollback
```

Flag evaluation là runtime decision; artifact vẫn immutable giữa environments.

## 4. Practical implementation

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
    return await newCheckout.ExecuteAsync(ct);

return await legacyCheckout.ExecuteAsync(ct);
```

Flag phải có owner, expiry/cleanup date và telemetry theo variant.

## 5. Real production scenario

Checkout rewrite được merge từng increment nhưng flag off. Pipeline commit → build → unit/integration tests → artifact → deploy → health validation. Team bật 5% internal users, monitor errors/latency rồi mở rộng.

## 6. Failure scenario & troubleshooting

**Symptom** → codebase đầy flags và combinations không test được. **Evidence** → flags tồn tại nhiều tháng, owner không rõ. **Hypothesis** → flag trở thành permanent configuration. **Diagnosis** → inventory flags và dependency graph. **Fix** → lifecycle policy, cleanup task sau rollout. **Verification** → dead branch bị xóa và tests đơn giản lại.

## 7. Common mistakes

Flag authorization/security-critical behavior không kiểm soát; dùng flag như config vĩnh viễn; không test cả on/off; environment-specific artifacts; rollback bằng rebuild thay vì promote immutable artifact.

## 8. Alternatives

Short release branches phù hợp một số regulated flow. Blue-Green/Canary điều khiển deployment traffic, còn Feature Flag điều khiển product behavior; hai cơ chế có thể kết hợp.

## 9. Trade-offs

### Advantages

Integration sớm, release linh hoạt, giảm batch size và rollback behavior nhanh.

### Costs / Risks

Runtime branches, testing matrix và flag debt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu merge thường xuyên và flag on/off.

### Middle

Viết tests cho variants và pipeline đúng.

### Senior

Thiết kế rollout/telemetry/cleanup và database compatibility.

### Technical Lead / Architect

Đặt release governance: commit → build → test → artifact → deploy → health → monitor → rollback/roll-forward.

## 11. Key takeaway

- Deployment và release không nhất thiết là cùng một sự kiện.
- Feature Flag cần lifecycle, không phải permanent architecture.
- Trunk-based hiệu quả khi CI đủ mạnh để bảo vệ main.

# 9. RED metrics: thiết kế observability cho API từ Rate, Errors, Duration

## 1. What is it?

RED là heuristic quan sát request-driven service qua `Rate`, `Errors`, `Duration`. Nó cung cấp starting point cho dashboard/alerts thay vì thu thập hàng trăm metrics không gắn với user impact.

## 2. Why does it exist?

CPU/memory khỏe không có nghĩa API khỏe. User quan tâm request có được xử lý, có lỗi và mất bao lâu. RED chuyển observability về service behavior trước khi đào sâu resource metrics.

## 3. How does it work?

Metrics cho aggregate trend; traces localize critical path; logs cung cấp event detail. Alerts nên gắn với SLO/user impact thay vì mọi biến động nhỏ.

```text
Rate + Errors + Duration
          |
          v
       Alert/SLO
          |
          v
Trace -> dependency -> logs -> root cause
```

## 4. Practical implementation

ASP.NET Core/OpenTelemetry thu request duration/status. Dashboard nên có request rate, 5xx/error ratio, p50/p95/p99; drill-down theo route/service nhưng tránh dimensions cardinality cao như raw user ID.

## 5. Real production scenario

Sau deployment, CPU không đổi nhưng p99 `/checkout` tăng và 5xx từ payment dependency xuất hiện. RED alert phát hiện user impact; trace xác định dependency; logs cho request-specific evidence.

## 6. Failure scenario & troubleshooting

**Symptom** → alert fatigue nhưng incident thật vẫn bị phát hiện muộn. **Evidence** → nhiều threshold alerts trên CPU, memory, instance count; không có SLO-oriented request alert. **Hypothesis** → signals không gắn user impact. **Fix** → RED dashboard + error-budget/SLO alert, resource alerts làm diagnostic/supporting signals. **Verification** → incident simulation tạo actionable alert.

## 7. Common mistakes

Chỉ dùng average duration; label cardinality vô hạn; log Error cho expected 4xx; metrics không liên kết trace IDs; alert mọi transient spike.

## 8. Alternatives

USE (`Utilization`, `Saturation`, `Errors`) phù hợp resource-centric diagnosis. RED phù hợp service/API view. Thực tế dùng RED để phát hiện và USE để đào bottleneck hạ tầng.

## 9. Trade-offs

### Advantages

Dashboard nhỏ, gắn user experience, dễ xây SLO.

### Costs / Risks

Không đủ để tìm root cause một mình; route aggregation sai có thể che endpoint quan trọng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Rate/Errors/Duration.

### Middle

Tạo dashboard và đọc percentiles.

### Senior

Kết nối logs + metrics + traces + alerts thành investigation loop.

### Technical Lead / Architect

Định nghĩa SLI/SLO, telemetry schema, sampling/cardinality và alert ownership.

## 11. Key takeaway

- RED đo service từ góc nhìn request/user impact.
- Metrics phát hiện; traces/logs giải thích.
- Alert tốt phải dẫn tới hành động cụ thể.

# 10. React stale closure: khi async UI dùng state cũ và tạo bug khó tái hiện

## 1. What is it?

JavaScript closure giữ các bindings từ render nơi function được tạo. Trong React, callback async/timer/effect có thể quan sát state của render cũ nếu dependency hoặc update pattern không đúng; đó thường được gọi là stale closure.

## 2. Why does it exist?

React render tạo snapshot state/props. Async callback hoàn tất sau render mới, nhưng callback cũ không tự biến thành callback của render mới. Bug xuất hiện rõ với rapid user actions và network race.

## 3. How does it work?

```text
Render A: query="car" -> start request A
Render B: query="cars" -> start request B
request B returns -> show cars
request A returns later -> stale callback overwrites UI
```

Đây vừa là closure issue vừa là async ordering issue.

## 4. Practical implementation

```tsx
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${encodeURIComponent(query)}`, {
    signal: controller.signal
  })
    .then(r => r.json())
    .then(setResults)
    .catch(e => {
      if (e.name !== "AbortError") setError(e);
    });

  return () => controller.abort();
}, [query]);
```

Với state update dựa trên previous value, dùng functional update: `setCount(c => c + 1)`.

## 5. Real production scenario

Autocomplete gửi request theo mỗi query. Network response cũ về sau response mới khiến kết quả nhảy ngược. Backend đúng nhưng UI hiển thị stale data và QA khó reproduce vì phụ thuộc timing.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị response cũ. **Evidence** → DevTools Network cho request order khác response order. **Hypothesis** → stale async work. **Diagnosis** → kiểm tra effect dependencies, cleanup và callback capture. **Fix** → abort obsolete request hoặc sequence/version responses. **Verification** → throttle network và gõ nhanh; kết quả cuối luôn khớp query mới nhất.

## 7. Common mistakes

Bỏ dependency để “effect chỉ chạy một lần”; dùng state captured trong timer; không cleanup subscription; backend retry để sửa frontend race; dùng `useMemo`/`useCallback` như correctness fix chung.

## 8. Alternatives

Data-fetching libraries có cancellation/cache/request identity abstractions. Với flow nhỏ, `AbortController` và effect cleanup đủ đơn giản. State machine hữu ích khi UI workflow phức tạp thật sự.

## 9. Trade-offs

### Advantages

Hiểu render snapshot giúp xử lý async UI deterministic hơn.

### Costs / Risks

Cancellation và request identity thêm state; abstraction library có learning/operational complexity riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu closure và render snapshot.

### Middle

Viết effect dependencies/cleanup đúng và dùng functional updates.

### Senior

Reason về request races, cancellation, cache và API semantics.

### Technical Lead / Architect

Chuẩn hóa frontend data-fetching pattern phù hợp độ phức tạp, không thêm state framework nếu chưa cần.

## 11. Key takeaway

- Async callback có thể thuộc render cũ dù UI đã render state mới.
- Cancellation/request identity xử lý obsolete work tốt hơn đoán timing.
- DevTools Network là evidence quan trọng cho race ở frontend.
