# 1. C# `IAsyncDisposable`: giải phóng asynchronous resources đúng cách mà không biến cleanup thành blocking work

## 1. What is it?

`IAsyncDisposable` là contract cho resource cần cleanup bằng asynchronous operation. Thay vì chỉ có `Dispose()`, object cung cấp `DisposeAsync()` để caller có thể `await` quá trình giải phóng.

Mental model:

```text
use resource
   ↓
cleanup cần I/O
   ↓
await DisposeAsync()
```

Nó phù hợp khi cleanup có thể cần flush network buffer, hoàn tất asynchronous protocol, commit/close stream hoặc giải phóng resource mà API gốc đã thiết kế theo async.

## 2. Why does it exist?

`IDisposable` giả định cleanup synchronous và nhanh. Nhưng nếu cleanup thật sự phụ thuộc I/O, ép nó về synchronous bằng `.Wait()` hoặc `.GetAwaiter().GetResult()` có thể block thread, tăng latency hoặc tạo starvation.

`IAsyncDisposable` tồn tại để giữ call chain asynchronous đến cả giai đoạn teardown.

## 3. How does it work?

C# hỗ trợ:

```csharp
await using var resource = await CreateResourceAsync();
```

Compiler bảo đảm `DisposeAsync()` được gọi khi rời scope, kể cả khi có exception.

Flow:

```text
Create
  ↓
Use
  ↓
exception hoặc success
  ↓
DisposeAsync
  ↓
resource released
```

## 4. Practical implementation

```csharp
public sealed class AsyncBatchWriter : IAsyncDisposable
{
    private readonly Stream _stream;

    public AsyncBatchWriter(Stream stream)
    {
        _stream = stream;
    }

    public async ValueTask DisposeAsync()
    {
        await _stream.FlushAsync();
        await _stream.DisposeAsync();
    }
}
```

Caller:

```csharp
await using var writer = new AsyncBatchWriter(stream);
// write data
```

Nếu type có cả synchronous và asynchronous cleanup path, có thể implement cả `IDisposable` và `IAsyncDisposable`, nhưng semantics phải rõ.

## 5. Real production scenario

Một file-processing service ghi output vào Azure Blob thông qua stream wrapper. Nếu cleanup chỉ gọi synchronous dispose trong request path, flush cuối có thể block thread và tăng tail latency khi blob storage chậm.

Dùng `await using` giữ teardown non-blocking và làm behavior nhất quán với asynchronous pipeline.

## 6. Failure scenario & troubleshooting

**Symptom** → request hoàn tất logic chính nhưng latency vẫn cao ở cuối request.

**Evidence** → trace cho thấy thời gian nằm trong dispose/flush; ThreadPool queue tăng dưới load.

**Hypothesis** → async resource bị cleanup qua synchronous path.

**Diagnosis** → inspect ownership và disposal path của stream/client/resource.

**Fix** → propagate `await using`, tránh sync-over-async trong cleanup.

**Verification** → load test lại và kiểm tra p95/p99 cùng ThreadPool telemetry.

## 7. Common mistakes

* Implement `IAsyncDisposable` dù cleanup không có asynchronous work thực sự.
* Quên dispose resource vì nghĩ DI container hoặc GC sẽ tự xử lý đúng thời điểm.
* Gọi `DisposeAsync().AsTask().Wait()` trong ASP.NET Core.
* Không xác định rõ component nào sở hữu resource và chịu trách nhiệm dispose.

## 8. Alternatives

`IDisposable` vẫn đúng cho resource cleanup hoàn toàn synchronous như unmanaged handle đóng nhanh.

Nếu resource được DI container quản lý, thường để container dispose theo lifetime thay vì manually dispose injected singleton/scoped services.

## 9. Trade-offs

### Advantages

Cleanup không block thread, phù hợp với asynchronous I/O và giúp ownership rõ ràng.

### Costs / Risks

API phức tạp hơn, caller phải dùng `await using`, và dual-interface disposal có thể gây ambiguity nếu semantics không nhất quán.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dispose là deterministic resource cleanup, không phải GC.

### Middle

Biết khi nào dùng `await using` và propagate async cleanup.

### Senior

Nhận diện ownership, lifetime và starvation từ blocking teardown.

### Technical Lead / Architect

Định nghĩa resource ownership contract giữa layers và tránh để infrastructure lifetime bị quản lý tùy tiện bởi application code.

## 11. Key takeaway

* `IAsyncDisposable` dành cho cleanup thật sự asynchronous.
* Cleanup cũng là một phần của latency và resource management.
* Ownership phải rõ hơn cả việc chọn interface nào.

# 2. ASP.NET Core `ProblemDetails`: chuẩn hóa error contract mà vẫn giữ business semantics và observability

## 1. What is it?

`ProblemDetails` là representation chuẩn cho HTTP API errors với các field như `type`, `title`, `status`, `detail` và `instance`.

Mental model:

```text
Exception / domain failure
        ↓
error mapping
        ↓
HTTP status + ProblemDetails
```

Mục tiêu không phải chỉ để response “đẹp”, mà để client có contract lỗi nhất quán và server giữ mapping giữa technical failure với HTTP semantics.

## 2. Why does it exist?

Nếu mỗi endpoint trả một shape lỗi khác nhau, client phải viết nhiều nhánh parsing và behavior trở nên không ổn định.

Ngược lại, nếu mọi lỗi đều thành `500`, API che mất business semantics như validation failure, not found, conflict hoặc authorization failure.

## 3. How does it work?

ASP.NET Core có thể centralize exception handling và tạo `ProblemDetails` theo error category.

```text
Validation → 400
Unauthorized → 401
Forbidden → 403
Missing resource → 404
Concurrency conflict → 409
Unhandled defect → 500
```

Technical details nhạy cảm không nên leak ra client; correlation/trace identifier có thể được đưa vào extension để support điều tra.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();
app.UseExceptionHandler();
```

Với custom handler:

```csharp
public sealed class ConcurrencyExceptionHandler : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext httpContext,
        Exception exception,
        CancellationToken ct)
    {
        if (exception is not DbUpdateConcurrencyException)
            return false;

        httpContext.Response.StatusCode = StatusCodes.Status409Conflict;
        await httpContext.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Status = 409,
            Title = "Concurrency conflict",
            Detail = "The resource changed before this update was saved."
        }, ct);

        return true;
    }
}
```

## 5. Real production scenario

Một SPA gọi nhiều APIs. Nếu service A trả `{ error: ... }`, service B trả plain text và service C trả stack trace, frontend error handling nhanh chóng trở thành conditional maze.

Chuẩn hóa `ProblemDetails` giúp frontend có một generic error pipeline, còn business-specific cases dựa trên stable status/type.

## 6. Failure scenario & troubleshooting

**Symptom** → client báo “unknown error” dù backend log có business exception rõ ràng.

**Evidence** → same exception được map khác nhau ở các endpoints.

**Hypothesis** → error handling phân tán.

**Diagnosis** → audit middleware/filter/controller mappings.

**Fix** → centralize category mapping, giữ stable error types và telemetry correlation.

**Verification** → contract tests cho representative failures.

## 7. Common mistakes

* Trả stack trace trong `detail` ở Production.
* Dùng `200 OK` với body `{ success:false }` cho mọi lỗi.
* Map mọi exception thành `400 Bad Request`.
* Dùng human-readable `title` làm machine-readable error code.

## 8. Alternatives

Custom envelope có thể hợp lý nếu tổ chức đã có mature API standard, nhưng nên giữ HTTP semantics rõ và tránh duplicate concepts.

gRPC dùng status model khác, nhưng vẫn cần consistent mapping giữa domain failures và transport errors.

## 9. Trade-offs

### Advantages

Contract nhất quán, frontend đơn giản hơn, observability và support tốt hơn.

### Costs / Risks

Central mapping có thể trở thành giant switch nếu domain boundaries kém; thay đổi error type cũng là breaking contract đối với client.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP status và error body có vai trò khác nhau.

### Middle

Biết implement central exception handling và `ProblemDetails`.

### Senior

Thiết kế stable error taxonomy, tránh leakage và test backward compatibility.

### Technical Lead / Architect

Định nghĩa API-wide error contract và ownership giữa domain/application/transport layers.

## 11. Key takeaway

* `ProblemDetails` giải quyết consistency, không thay thế domain modeling.
* Error mapping phải giữ đúng HTTP semantics.
* Machine-readable error identity nên stable hơn message hiển thị.

# 3. EF Core savepoints trong transaction: rollback cục bộ mà không phá toàn bộ unit of work

## 1. What is it?

Savepoint là mốc bên trong database transaction cho phép rollback về một điểm trung gian thay vì rollback toàn bộ transaction.

Mental model:

```text
BEGIN TRANSACTION
  step A
  SAVEPOINT S1
  step B
  rollback to S1
  step C
COMMIT
```

## 2. Why does it exist?

Một workflow đôi khi có nhiều persistence steps trong cùng transaction nhưng muốn retry hoặc phục hồi một phần mà vẫn giữ các thay đổi trước đó.

EF Core cũng sử dụng savepoint trong một số tình huống khi `SaveChanges` chạy bên trong transaction đã tồn tại.

## 3. How does it work?

Khi transaction active và savepoint được tạo, database ghi nhận vị trí logical trong transaction log. Rollback tới savepoint hoàn tác các thay đổi sau mốc nhưng transaction vẫn còn active.

Nó không biến transaction thành nested transactions thực sự.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

await SaveHeaderAsync(db, ct);
await tx.CreateSavepointAsync("BeforeLines", ct);

try
{
    await SaveLinesAsync(db, ct);
    await db.SaveChangesAsync(ct);
}
catch
{
    await tx.RollbackToSavepointAsync("BeforeLines", ct);
    // corrective path
}

await tx.CommitAsync(ct);
```

Cần hiểu provider behavior thay vì giả định mọi database xử lý savepoint giống hệt nhau.

## 5. Real production scenario

Import pipeline tạo batch record trước, rồi persist hàng nghìn line items. Một subset lỗi validation sau khi transform. Team muốn giữ batch metadata nhưng rollback line insertion để đánh dấu batch failed trong cùng controlled transaction flow.

Savepoint có thể hỗ trợ, nhưng nếu workflow có external side effects thì rollback database không rollback được email, file upload hay message đã publish.

## 6. Failure scenario & troubleshooting

**Symptom** → code rollback savepoint nhưng external side effect vẫn tồn tại.

**Evidence** → database state quay lại đúng nhưng downstream đã nhận message.

**Hypothesis** → transaction boundary bị hiểu nhầm là system-wide atomicity.

**Diagnosis** → map tất cả side effects ra ngoài database.

**Fix** → Outbox, compensation hoặc tách workflow phù hợp.

**Verification** → failure-injection tests tại từng boundary.

## 7. Common mistakes

* Coi savepoint như distributed transaction.
* Tạo quá nhiều savepoints trong loop mà không cần thiết.
* Không kiểm tra provider limitations.
* Dùng savepoint để che một transaction boundary thiết kế sai.

## 8. Alternatives

Nhiều transaction nhỏ hơn thường đơn giản hơn nếu business không yêu cầu atomicity rộng.

Compensating action phù hợp khi workflow đi qua nhiều services/resources.

## 9. Trade-offs

### Advantages

Cho phép partial rollback và controlled retry trong một database transaction.

### Costs / Risks

Transaction sống lâu hơn, lock/version retention kéo dài và reasoning phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction và rollback toàn phần trước.

### Middle

Biết tạo và rollback savepoint đúng provider.

### Senior

Đánh giá lock duration, external side effects và retry semantics.

### Technical Lead / Architect

Quyết định liệu partial rollback có thực sự cần hay workflow nên chia thành transaction boundaries nhỏ hơn.

## 11. Key takeaway

* Savepoint là rollback point bên trong một transaction.
* Nó không mở rộng atomicity ra ngoài database.
* Transaction càng dài, operational cost càng cần được xem xét.

# 4. PostgreSQL MVCC + VACUUM: vì sao reader không block writer nhưng dead tuples vẫn tạo operational cost

## 1. What is it?

MVCC (Multi-Version Concurrency Control) cho phép PostgreSQL giữ nhiều phiên bản logical của row để transactions đọc snapshot phù hợp thay vì luôn phải block lẫn nhau.

Khi `UPDATE`, PostgreSQL thường tạo tuple version mới; version cũ trở thành dead tuple sau khi không còn transaction nào cần nó.

`VACUUM` dọn space có thể tái sử dụng và duy trì health của storage/index visibility metadata.

## 2. Why does it exist?

Nếu readers và writers phải lock nhau thường xuyên, throughput giảm mạnh dưới concurrency.

MVCC giảm reader-writer blocking nhưng đổi lại hệ thống phải quản lý nhiều row versions và garbage lifecycle.

## 3. How does it work?

Simplified flow:

```text
T1 reads row version A
T2 updates row → creates version B
T1 vẫn thấy A theo snapshot
new transactions thấy B
A hết visible → trở thành dead tuple
VACUUM reclaim/reuse space
```

Nếu autovacuum không theo kịp, table/index bloat và statistics/visibility behavior có thể xấu đi.

## 4. Practical implementation

Điều tra table activity:

```sql
SELECT relname,
       n_live_tup,
       n_dead_tup,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Không nên phản xạ bằng `VACUUM FULL` trên Production vì nó có locking/operational impact lớn hơn regular vacuum.

## 5. Real production scenario

Một audit-heavy SaaS update trạng thái cùng bảng hàng triệu lần/ngày. Query latency tăng dần dù index không đổi.

Telemetry cho thấy dead tuples tăng và autovacuum không theo kịp write rate. Root cause không phải “PostgreSQL chậm” mà là maintenance settings không phù hợp workload.

## 6. Failure scenario & troubleshooting

**Symptom** → table size tăng nhanh, scans đọc nhiều pages hơn, query latency tăng.

**Evidence** → `n_dead_tup` cao, autovacuum lag, I/O tăng.

**Hypothesis** → dead tuple accumulation/bloat.

**Diagnosis** → kiểm tra write rate, long-running transactions, vacuum frequency và table-specific settings.

**Fix** → xử lý long transactions, tune autovacuum có bằng chứng, review access pattern.

**Verification** → dead tuple ratio giảm, I/O và latency ổn định hơn.

## 7. Common mistakes

* Nghĩ MVCC nghĩa là “không có lock”.
* Giữ transaction mở rất lâu, làm old versions không reclaim được.
* Chạy `VACUUM FULL` như routine maintenance.
* Chỉ nhìn database size mà không nhìn churn rate.

## 8. Alternatives

SQL Server có row-versioning isolation modes nhưng storage/versioning mechanics khác. Pessimistic locking vẫn hợp lý cho một số short critical sections.

## 9. Trade-offs

### Advantages

Concurrency đọc/ghi tốt hơn và giảm reader-writer blocking.

### Costs / Risks

Dead tuples, bloat, vacuum overhead và long-running transaction sensitivity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu update không nhất thiết “ghi đè tại chỗ”.

### Middle

Biết đọc `pg_stat_user_tables` và nhận diện dead tuples.

### Senior

Liên hệ MVCC với transaction age, I/O, bloat và autovacuum tuning.

### Technical Lead / Architect

Thiết kế workload và operational guardrails để maintenance không trở thành afterthought.

## 11. Key takeaway

* MVCC giảm blocking bằng row versions.
* Row versions tạo garbage cần vacuum quản lý.
* Long-running transactions có thể làm maintenance khó hơn đáng kể.

# 5. Azure Cosmos DB partition key + hot partition: scale theo data distribution chứ không chỉ theo tổng RU/s

## 1. What is it?

Partition key quyết định cách Cosmos DB phân phối items vào logical partitions và sau đó physical partitions.

Một hot partition xảy ra khi phần lớn traffic tập trung vào một partition key range, khiến một phần hệ thống bị throttled dù tổng capacity nhìn vẫn còn dư.

## 2. Why does it exist?

Distributed database cần chia data/workload để scale ngang. Partition key là cơ chế định tuyến request và phân phối storage/throughput.

Sai partition key có thể khóa scalability vào một access pattern tệ ngay từ model dữ liệu.

## 3. How does it work?

```text
request with partition key
       ↓
route to logical partition
       ↓
physical partition
       ↓
RU budget + storage
```

Nếu key như `TenantId` có một tenant tạo 70% traffic, workload không được phân phối đều dù có hàng nghìn tenants khác gần như idle.

Cross-partition query cũng tốn cost hơn vì phải fan out.

## 4. Practical implementation

Ví dụ document:

```json
{
  "id": "evt-123",
  "tenantId": "tenant-42",
  "deviceId": "dev-9",
  "timestamp": "2026-09-11T00:00:00Z"
}
```

Nếu workload chủ yếu là device telemetry, `deviceId` hoặc hierarchical partition strategy có thể hợp lý hơn chỉ `tenantId`, tùy access patterns và cardinality.

Trong SDK, luôn truyền partition key cho point reads khi biết:

```csharp
var response = await container.ReadItemAsync<EventDocument>(
    id,
    new PartitionKey(deviceId),
    cancellationToken: ct);
```

## 5. Real production scenario

IoT backend có 100,000 devices nhưng một fleet gateway gửi phần lớn messages dưới cùng customer key. Cosmos DB trả `429 Too Many Requests` ở partition nóng dù overall RU/s dashboard chưa đạt mức team kỳ vọng.

## 6. Failure scenario & troubleshooting

**Symptom** → intermittent 429 tập trung ở một subset keys.

**Evidence** → RU consumption và throttling lệch mạnh theo partition key.

**Hypothesis** → hot partition.

**Diagnosis** → analyze key cardinality, per-key traffic, item size và query routing.

**Fix** → redesign partition strategy, distribute writes, dùng synthetic/hierarchical key nếu phù hợp.

**Verification** → throttling giảm và RU distribution cân bằng hơn dưới peak load.

## 7. Common mistakes

* Chọn partition key chỉ vì field “luôn có”.
* Chỉ nhìn cardinality mà bỏ qua traffic skew.
* Dùng cross-partition query cho hot endpoint rồi cố giải quyết bằng tăng RU/s.
* Chọn key dễ đổi theo business state.

## 8. Alternatives

SQL Server/PostgreSQL có thể phù hợp hơn nếu data cần strong relational constraints và scale hiện tại chưa biện minh distributed partitioning.

MongoDB sharding có bài toán shard key tương tự về cardinality và skew.

## 9. Trade-offs

### Advantages

Partitioning tốt cho scale ngang, routing hiệu quả và predictable point reads.

### Costs / Risks

Sai key rất khó sửa về sau; cross-partition operations tăng latency/cost; data modeling bị ràng buộc bởi access pattern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định nơi dữ liệu nằm.

### Middle

Biết thiết kế point reads và tránh fan-out không cần thiết.

### Senior

Phân tích RU, hot keys, traffic skew và migration implications.

### Technical Lead / Architect

Chọn partition strategy từ access patterns, growth model và operational limits chứ không từ schema convenience.

## 11. Key takeaway

* Tổng RU/s không kể hết câu chuyện nếu traffic tập trung.
* Partition key là architecture decision dài hạn.
* Data distribution phải phản ánh workload distribution.

# 6. DDD Aggregate boundary: bảo vệ invariant và transaction boundary thay vì gom entity theo object graph

## 1. What is it?

Aggregate là consistency boundary trong Domain-Driven Design. Nó gồm một Aggregate Root và các objects được thay đổi thông qua root để bảo vệ business invariants.

Mental model:

```text
Command
  ↓
Aggregate Root
  ↓
validate invariant
  ↓
state change
  ↓
one transaction boundary
```

Aggregate không đơn giản là object graph “Order có OrderLines”.

## 2. Why does it exist?

Business rules thường cần đảm bảo nhiều fields thay đổi nhất quán. Nếu mọi entity đều được update trực tiếp từ bất cứ layer nào, invariant rất dễ bị bypass.

Aggregate tạo một boundary mà bên trong đó consistency mạnh được đảm bảo đồng bộ.

## 3. How does it work?

Ví dụ `Order` có invariant: không được add line khi order đã submitted.

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public OrderStatus Status { get; private set; }

    public void AddLine(ProductId productId, int quantity)
    {
        if (Status != OrderStatus.Draft)
            throw new DomainException("Submitted order cannot be modified.");

        _lines.Add(new OrderLine(productId, quantity));
    }
}
```

Caller không nên bypass bằng cách mutate collection trực tiếp.

## 4. Practical implementation

Repository nếu dùng nên load/save Aggregate Root theo boundary domain-specific:

```csharp
public interface IOrderRepository
{
    Task<Order?> GetAsync(OrderId id, CancellationToken ct);
    Task AddAsync(Order order, CancellationToken ct);
}
```

Không cần generic repository chỉ vì đang dùng DDD.

## 5. Real production scenario

Approval workflow có rule: một request chỉ chuyển sang `Approved` khi tất cả mandatory approvers đã quyết định. Nếu approval records và request status được cập nhật qua nhiều services/application paths độc lập, invariant dễ bị phá.

Aggregate boundary đúng có thể gom consistency cần thiết; phần notification hoặc analytics nên ra ngoài qua event để tránh aggregate quá lớn.

## 6. Failure scenario & troubleshooting

**Symptom** → database xuất hiện state technically valid theo schema nhưng impossible theo business rule.

**Evidence** → nhiều code paths update child entities trực tiếp.

**Hypothesis** → invariant không có single enforcement boundary.

**Diagnosis** → trace mutation paths và transaction boundaries.

**Fix** → đưa invariant vào aggregate behavior, hạn chế direct setters/repository access.

**Verification** → domain tests và integration tests cho competing commands.

## 7. Common mistakes

* Aggregate = mọi entity có foreign key liên quan.
* Tạo aggregate quá lớn dẫn đến contention và load graph nặng.
* Dùng domain event để né một invariant cần synchronous consistency.
* Cho controller/EF mapping mutate internal state trực tiếp.

## 8. Alternatives

Anemic model + application service có thể đủ cho CRUD domain đơn giản.

Database constraints vẫn cần cho invariants mà database enforce tốt như uniqueness hoặc FK integrity.

## 9. Trade-offs

### Advantages

Business rules có boundary rõ, transaction reasoning dễ hơn, mutation paths được kiểm soát.

### Costs / Risks

Aggregate lớn gây contention; aggregate nhỏ quá lại đẩy consistency sang distributed workflow.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Entity khác Value Object và Aggregate Root là entry point mutation.

### Middle

Biết encode invariant trong domain behavior.

### Senior

Thiết kế aggregate size dựa trên consistency/transaction needs.

### Technical Lead / Architect

Quyết định boundary giữa synchronous invariant và eventual consistency giữa aggregates/bounded contexts.

## 11. Key takeaway

* Aggregate là consistency boundary, không phải folder hay object graph.
* Invariant quyết định boundary nhiều hơn foreign key.
* Không phải domain nào cũng cần rich aggregates.

# 7. Azure Private Endpoint + private DNS: private connectivity chỉ hoạt động khi network path và name resolution cùng đúng

## 1. What is it?

Azure Private Endpoint tạo private IP trong Virtual Network cho một PaaS resource như Storage, Key Vault hoặc SQL.

Nhưng private IP chưa đủ. DNS phải resolve service hostname về private endpoint đúng trong network context của application.

## 2. Why does it exist?

Public endpoint dù có firewall vẫn đi qua public addressing model. Private Endpoint cho phép traffic tới PaaS service thông qua private network path và hỗ trợ kiểm soát ingress chặt hơn.

## 3. How does it work?

```text
App Service / VM / AKS
        ↓ DNS lookup
service.azure...
        ↓
Private DNS Zone
        ↓
10.x.x.x Private Endpoint
        ↓
PaaS resource
```

Nếu DNS vẫn trả public IP trong khi public network access đã disabled, app sẽ timeout dù private endpoint tồn tại hoàn toàn bình thường.

## 4. Practical implementation

Operational check từ workload environment:

```bash
nslookup <service-hostname>
```

Sau đó kiểm tra route/connectivity đến private IP. Với hybrid DNS, on-prem resolver có thể cần conditional forwarding về Azure DNS resolver architecture.

Application connection string thường vẫn dùng normal service hostname; không hard-code private IP vì TLS/SNI và service semantics dựa vào hostname.

## 5. Real production scenario

Team tạo Private Endpoint cho Key Vault và tắt public access. Developer laptop qua VPN resolve hostname public, còn Production VNet resolve private. Local test lỗi nhưng Production chạy; hoặc ngược lại nếu DNS zone link bị thiếu.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout sau khi bật Private Endpoint.

**Evidence** → `nslookup` trả public IP thay vì private IP.

**Hypothesis** → DNS zone/virtual network link hoặc forwarding sai.

**Diagnosis** → kiểm tra resolution từ chính workload, không chỉ từ laptop admin.

**Fix** → correct private DNS zone linkage/forwarding và network integration.

**Verification** → hostname resolve private IP và request thành công khi public access vẫn disabled.

## 7. Common mistakes

* Hard-code private IP vào application config.
* Chỉ test portal configuration mà không test DNS từ workload.
* Tắt public endpoint trước khi private DNS path sẵn sàng.
* Nghĩ Private Endpoint tự động giải quyết egress, NSG, DNS và identity cùng lúc.

## 8. Alternatives

Service endpoints đơn giản hơn trong một số scenarios nhưng security/network semantics khác.

Public endpoint + firewall có thể đủ nếu threat model và compliance cho phép.

## 9. Trade-offs

### Advantages

Private connectivity, giảm public exposure và phù hợp enterprise network segmentation.

### Costs / Risks

DNS/network complexity tăng, troubleshooting khó hơn và hybrid environments cần design cẩn thận.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hostname cần resolve tới đúng endpoint.

### Middle

Biết kiểm tra DNS, route và service reachability.

### Senior

Troubleshoot hybrid DNS, rollout sequencing và failure modes.

### Technical Lead / Architect

Quyết định service nào cần private connectivity dựa trên threat model thay vì áp dụng mặc định cho mọi resource.

## 11. Key takeaway

* Private Endpoint và private DNS là hai nửa của cùng connectivity path.
* Test từ workload thực tế.
* Không hard-code private IP cho PaaS hostname.

# 8. Docker image layers + multi-stage build: giảm attack surface và deployment weight bằng cách tách build-time khỏi runtime

## 1. What is it?

Docker image được cấu thành từ immutable layers. Multi-stage build cho phép dùng SDK/tooling ở build stage nhưng chỉ copy artifact cần thiết sang runtime stage.

Mental model:

```text
SDK image
  ↓ build/publish
artifacts
  ↓ copy
runtime image
```

## 2. Why does it exist?

Nếu Production image chứa compiler, package caches, source code và build tools, image lớn hơn, pull chậm hơn và attack surface rộng hơn.

Multi-stage build giữ runtime image tối thiểu hơn mà vẫn có reproducible build pipeline.

## 3. How does it work?

Mỗi `FROM` mở một stage. Artifact được copy giữa stages bằng `COPY --from=`.

Layer caching còn giúp rebuild nhanh nếu Dockerfile sắp xếp dependency restore và source copy hợp lý.

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY *.sln .
COPY src/MyApi/MyApi.csproj src/MyApi/
RUN dotnet restore src/MyApi/MyApi.csproj
COPY . .
RUN dotnet publish src/MyApi/MyApi.csproj -c Release -o /out --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /out .
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

## 5. Real production scenario

CI trước đây build image 1.8 GB vì copy cả repository và dùng SDK image làm runtime. Kubernetes rollout mất lâu do nodes pull image lớn.

Sau multi-stage build, runtime image giảm đáng kể, startup distribution nhanh hơn và vulnerability scan không còn hàng loạt build-only packages.

## 6. Failure scenario & troubleshooting

**Symptom** → image rebuild luôn invalidate cache và mất nhiều phút.

**Evidence** → layer history cho thấy `COPY . .` trước `dotnet restore`.

**Hypothesis** → source changes invalidate dependency restore layer.

**Diagnosis** → inspect Docker build layer cache hits.

**Fix** → copy project files trước, restore, rồi mới copy source.

**Verification** → code-only change reuse restore layer.

## 7. Common mistakes

* Dùng SDK image làm runtime không cần thiết.
* Copy secrets vào build context/layers.
* Dựa vào `latest` tag cho reproducibility.
* Tối ưu image size nhưng bỏ qua patching/base-image update policy.

## 8. Alternatives

Self-contained/single-file publish có deployment model khác nhưng vẫn có image-layer concerns.

Không phải workload nào cũng cần container; App Service package deployment có thể đơn giản hơn cho team nhỏ.

## 9. Trade-offs

### Advantages

Image nhỏ hơn, pull/deploy nhanh hơn, attack surface giảm và build/runtime boundary rõ.

### Costs / Risks

Dockerfile phức tạp hơn, caching strategy cần hiểu và base image lifecycle vẫn phải quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu image khác container và layer là immutable filesystem delta.

### Middle

Biết viết multi-stage Dockerfile cho .NET.

### Senior

Tối ưu cache, security scanning, deterministic tags và runtime dependencies.

### Technical Lead / Architect

Quyết định khi nào containerization đáng operational cost so với simpler hosting model.

## 11. Key takeaway

* Build tools không nên tự động đi vào runtime image.
* Docker layer order ảnh hưởng build performance.
* Containerization chỉ có giá trị khi operational model thực sự cần nó.

# 9. SLI/SLO + error budget: biến reliability thành một engineering constraint có thể đo thay vì khẩu hiệu “99.9% uptime”

## 1. What is it?

SLI là metric đo một aspect của service reliability, ví dụ tỷ lệ requests thành công hoặc latency dưới threshold.

SLO là target cho SLI trong một thời gian xác định.

Error budget là phần failure được phép xảy ra trong phạm vi SLO.

Ví dụ:

```text
SLI: successful requests / valid requests
SLO: 99.9% trong 30 ngày
Error budget: 0.1%
```

## 2. Why does it exist?

“Service phải luôn ổn định” không phải engineering requirement có thể trade-off. Reliability tuyệt đối gần như không tồn tại và chi phí để tăng thêm một số 9 có thể rất cao.

SLO giúp team cân bằng feature velocity với reliability bằng một target đo được.

## 3. How does it work?

Nếu SLO 99.9% cho 1,000,000 valid requests/tháng, budget cho phép khoảng 1,000 requests không đạt criterion.

Burn rate cho biết team đang tiêu budget nhanh thế nào. Alert theo burn rate thường hữu ích hơn chỉ alert khi một metric vượt threshold tức thời.

## 4. Practical implementation

Ví dụ pseudo-query logic cho availability SLI:

```text
Good = HTTP 2xx/3xx + accepted business outcomes
Total = all valid user requests excluding health probes
SLI = Good / Total
```

Với latency:

```text
Good = requests < 500 ms
Total = valid requests
SLO = 99% good over 30 days
```

Trong Application Insights/Azure Monitor, dashboard nên hiển thị current SLI, remaining budget và burn rate.

## 5. Real production scenario

API có average latency 120 ms nhưng 2% requests mất hơn 3 giây. Average nhìn đẹp, nhưng user experience ở tail không đạt target.

Team đổi sang latency SLI dựa trên threshold hoặc percentile phù hợp, từ đó release decisions phản ánh user impact tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều alerts nhưng team không biết alert nào đáng wake-up.

**Evidence** → alerts dựa trên raw CPU/memory thresholds không gắn user impact.

**Hypothesis** → monitoring không nối với service objectives.

**Diagnosis** → map technical metrics sang customer-visible SLIs.

**Fix** → define SLO và multi-window burn-rate alerts.

**Verification** → incidents user-impacting được detect sớm hơn, noise giảm.

## 7. Common mistakes

* Đồng nhất SLA contractual với SLO engineering target.
* Chọn SLI vì metric có sẵn thay vì vì nó phản ánh user experience.
* Dùng average latency làm duy nhất reliability signal.
* Đặt SLO 100% rồi biến mọi failure thành emergency.

## 8. Alternatives

Basic threshold alerts vẫn cần cho hard infrastructure failures, nhưng không thay thế service-level objectives.

Apdex hoặc business KPIs có thể bổ sung góc nhìn trải nghiệm nhưng không phải lúc nào cũng thay SLI/SLO.

## 9. Trade-offs

### Advantages

Reliability có target rõ, alerting gắn user impact và release/risk decisions có dữ liệu.

### Costs / Risks

Chọn SLI sai sẽ tối ưu nhầm mục tiêu; instrumentation và governance cần effort liên tục.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SLI là measurement, SLO là target.

### Middle

Biết xây dashboard và alert từ meaningful metrics.

### Senior

Thiết kế error-budget/burn-rate reasoning và loại bỏ alert noise.

### Technical Lead / Architect

Chọn reliability target phù hợp business cost, architecture cost và operational maturity.

## 11. Key takeaway

* SLO biến reliability thành mục tiêu đo được.
* Error budget cho phép trade-off có chủ đích.
* Alert tốt nên phản ánh user impact, không chỉ machine health.

# 10. Optimizely CMS content modeling + cache invalidation: thiết kế content boundary để editor linh hoạt mà không tạo coupling và stale content

## 1. What is it?

Content modeling trong CMS định nghĩa các content types, page types, blocks, fields và quan hệ editorial. Trong Optimizely CMS, model tốt cần cân bằng editor usability, reuse và delivery performance.

Cache invalidation là phần vận hành của model đó: khi content thay đổi, các cached representations liên quan phải được invalidated đúng phạm vi.

## 2. Why does it exist?

Nếu mọi page là một giant content type, editor khó reuse và developer khó evolve schema.

Nếu chia thành quá nhiều tiny blocks, authoring trở nên phức tạp và rendering phải tải nhiều dependencies.

Caching giảm repeated content resolution/rendering cost nhưng tạo bài toán freshness.

## 3. How does it work?

Một page có thể reference reusable blocks:

```text
ProductLandingPage
 ├─ HeroBlock
 ├─ PromoBlock
 └─ FAQBlock
```

Nếu `PromoBlock` được reuse ở 50 pages, publish một block có thể ảnh hưởng nhiều rendered pages. Cache key/invalidation strategy phải hiểu dependency graph hoặc dùng platform-level invalidation semantics phù hợp.

## 4. Practical implementation

Ví dụ strongly typed content model:

```csharp
[ContentType(DisplayName = "Promo Block")]
public class PromoBlock : BlockData
{
    public virtual string Heading { get; set; } = string.Empty;
    public virtual XhtmlString Body { get; set; } = new();
}
```

Application-level caching nếu thêm vào phải dùng stable key gồm content identity + version/language khi relevant:

```text
promo:{contentId}:{language}:{version}
```

Không nên cache theo URL duy nhất nếu cùng content có multi-language/version semantics khác nhau.

## 5. Real production scenario

Marketing site dùng Akamai phía trước Optimizely. Editor publish campaign block mới nhưng CDN vẫn giữ page HTML cũ trong 20 phút.

CMS publish thành công; origin cũng render đúng. User vẫn thấy stale content vì invalidation boundary kéo dài sang CDN.

Flow thật:

```text
Editor publish
  ↓
CMS cache invalidation
  ↓
origin updated
  ↓
CDN cache still stale
```

## 6. Failure scenario & troubleshooting

**Symptom** → editor preview đúng nhưng public page vẫn cũ.

**Evidence** → origin trả content mới, CDN cache header cho thấy HIT với old object.

**Hypothesis** → CDN invalidation/TTL mismatch.

**Diagnosis** → test từng layer: CMS → app cache → reverse proxy/CDN → browser.

**Fix** → correct cache-control/purge strategy và publish integration.

**Verification** → publish test content và đo propagation time end-to-end.

## 7. Common mistakes

* Thiết kế block theo developer component thay vì editorial concept.
* Reuse quá mức làm content dependency graph khó hiểu.
* Cache content mà không tính language/version/personalization.
* Chỉ purge CMS cache nhưng quên CDN/browser cache.

## 8. Alternatives

Headless CMS tách delivery frontend khỏi traditional rendering nhưng không loại content modeling hay cache invalidation problems.

Với site nhỏ, server-side rendering trực tiếp và modest caching có thể đơn giản hơn composable/headless architecture.

## 9. Trade-offs

### Advantages

Content model tốt tăng reuse, editor autonomy và maintainability; caching giảm origin load.

### Costs / Risks

Nhiều reusable dependencies làm invalidation phức tạp; personalization và multi-language tăng key space/correctness burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu page type, block và content instance khác nhau.

### Middle

Biết tạo typed models, rendering và cache keys cơ bản.

### Senior

Thiết kế reuse boundary, dependency-aware invalidation và multi-layer cache troubleshooting.

### Technical Lead / Architect

Quyết định traditional vs headless/composable model dựa trên editorial workflow, team ownership, performance và operational complexity.

## 11. Key takeaway

* Content model là business/editorial boundary, không chỉ class hierarchy.
* Cache invalidation phải xét toàn bộ đường đi tới browser.
* Reuse tốt cần cân bằng flexibility với dependency complexity.
