# 1. C# Source Generators vs Reflection: chuyển work từ runtime sang compile time nhưng không đánh đổi maintainability chỉ để “tránh reflection”

## 1. What is it?

Source Generator là compiler extension chạy trong quá trình build và sinh thêm C# source code dựa trên source/metadata hiện có.

Mental model:

```text
Your source
   +
Generator
   |
   v
Generated C# source
   |
   v
Compiler
   |
   v
Assembly
```

Reflection thì ngược lại: application đã build xong, runtime mới inspect types, attributes, members và metadata để quyết định behavior.

Source Generator phù hợp khi work có thể xác định ở compile time và lặp lại nhiều lần ở runtime.

## 2. Why does it exist?

Reflection rất linh hoạt nhưng có ba cost phổ biến:

- runtime discovery;
- dynamic code paths khó trim/AOT;
- lỗi chỉ xuất hiện khi application chạy.

Source Generators chuyển một phần discovery/boilerplate sang build time. Điều này hữu ích cho serializers, mapping metadata, logging helpers, dependency registration hoặc strongly typed APIs.

Nhưng mục tiêu không phải “reflection luôn xấu”. Một admin tool chạy mỗi ngày một lần không cần generator chỉ để tiết kiệm vài microseconds.

## 3. How does it work?

Generator nhận immutable compiler model, thường inspect syntax/semantic model rồi emit source.

```text
Compilation
  -> inspect symbols/attributes
  -> determine generated artifacts
  -> AddSource(...)
  -> compiler compile cả handwritten + generated code
```

Incremental Generators tối ưu pipeline bằng cách chỉ recompute khi relevant inputs thay đổi.

Generated source vẫn là source bình thường với type safety và diagnostics từ compiler.

## 4. Practical implementation

Ví dụ một application muốn đánh dấu services tự đăng ký:

```csharp
[AttributeUsage(AttributeTargets.Class)]
public sealed class AutoRegisterAttribute : Attribute
{
}

[AutoRegister]
public sealed class InvoiceService : IInvoiceService
{
}
```

Generator có thể emit:

```csharp
public static class GeneratedServiceRegistration
{
    public static IServiceCollection AddGeneratedServices(
        this IServiceCollection services)
    {
        services.AddScoped<IInvoiceService, InvoiceService>();
        return services;
    }
}
```

Runtime không còn phải scan assembly mỗi startup.

Với production code, generator nên emit diagnostics rõ khi metadata thiếu/sai thay vì generate code lỗi khó hiểu.

## 5. Real production scenario

Một API lớn có hàng nghìn DTO dùng `System.Text.Json`. Source-generated serialization metadata có thể giảm reflection startup cost và hỗ trợ Native AOT tốt hơn.

Một scenario khác là strongly typed logging: source generation tránh boxing/formatting không cần thiết trong hot path và bắt một số lỗi template sớm hơn.

## 6. Failure scenario & troubleshooting

**Symptom:** build CI chậm hơn nhiều hoặc generated code biến mất sau refactor.

**Evidence:** generator execution time cao; diagnostics từ compiler/generator; generated files khác local và CI do package/version mismatch.

**Hypothesis:** generator scan toàn compilation thay vì incremental filtering hoặc phụ thuộc fragile syntax shape.

**Diagnosis:** profile build, inspect generated source, pin package/compiler version và kiểm tra analyzer logs.

**Fix:** dùng Incremental Generator, dựa trên semantic symbols thay vì text parsing khi cần correctness, thu hẹp candidate set.

**Verification:** build time giảm và generated output ổn định qua clean build/CI.

## 7. Common mistakes

- Dùng generator cho business logic thay vì boilerplate/metadata.
- Generate code rất lớn làm IDE/build chậm.
- Không emit diagnostics hữu ích.
- Coupling generator vào exact syntax thay vì semantic model.
- Nghĩ Source Generator tự động làm application nhanh hơn dù bottleneck nằm ở database/network.
- Bỏ reflection chỉ vì “Senior code phải compile-time”.

## 8. Alternatives

- **Reflection:** linh hoạt, đơn giản cho dynamic/plugin scenarios.
- **Manual registration/code:** minh bạch và đủ tốt khi số lượng nhỏ.
- **Source Generator:** tốt khi compile-time knowledge rõ và runtime cost/trim/AOT thực sự quan trọng.
- **Code generation ngoài compiler:** phù hợp OpenAPI/schema-driven generation nhưng có thêm build tooling.

## 9. Trade-offs

### Advantages

- Fail sớm hơn ở build time.
- Có thể giảm startup/runtime reflection.
- Hỗ trợ trimming/Native AOT tốt hơn.

### Costs / Risks

- Build pipeline phức tạp hơn.
- Debug generator khó hơn code application thông thường.
- Generated API có thể trở thành hidden coupling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác biệt compile time vs runtime và generator sinh C# chứ không “inject magic bytecode”.

### Middle

Biết inspect generated files, consume source-generated APIs và debug diagnostics.

### Senior

Biết xác định runtime reflection nào thực sự đáng thay bằng generation; theo dõi build-time cost và AOT constraints.

### Technical Lead / Architect

Quyết định liệu compile-time complexity có đáng với startup/runtime/compatibility benefits hay manual/reflection vẫn đơn giản hơn cho team.

## 11. Key takeaway

- Source Generator chuyển một số work từ runtime sang compile time.
- Dùng nó khi build-time knowledge tạo lợi ích thật về safety/performance/AOT.
- Đừng biến generator thành hidden framework chỉ để tránh reflection bằng mọi giá.

# 2. ASP.NET Core Options validation và configuration reload: cấu hình sai phải fail ở boundary đúng thay vì phát nổ ngẫu nhiên giữa production traffic

## 1. What is it?

Options Pattern map configuration thành strongly typed objects. Điểm quan trọng ở production không phải chỉ là `IOptions<T>`, mà là **lifetime + validation + reload semantics**.

Ba mental model thường gặp:

```text
IOptions<T>        -> singleton snapshot
IOptionsSnapshot<T>-> scoped/per-request recomputation
IOptionsMonitor<T> -> singleton access + change notifications
```

## 2. Why does it exist?

Đọc `configuration["Payments:Timeout"]` khắp code tạo stringly-typed dependency, khó validate và khó biết option nào thuộc component nào.

Typed options gom configuration contract lại một chỗ và cho phép fail-fast khi config bất hợp lệ.

Nếu không validate sớm, application có thể startup thành công rồi request đầu tiên mới fail vì timeout âm, URL sai hoặc secret missing.

## 3. How does it work?

Configuration providers tạo một composite configuration tree. Options binder map subtree vào object.

```text
appsettings.json
Environment Variables
Key Vault provider
        |
        v
IConfiguration
        |
        v
Options binding + validation
```

`ValidateOnStart()` ép validation trong startup path thay vì lazy validation lần đầu resolve option.

`IOptionsMonitor<T>` có thể nhận reload khi provider hỗ trợ change tokens.

## 4. Practical implementation

```csharp
public sealed class PaymentOptions
{
    public const string SectionName = "Payments";

    public required Uri BaseUrl { get; init; }
    public int TimeoutSeconds { get; init; }
}

builder.Services
    .AddOptions<PaymentOptions>()
    .Bind(builder.Configuration.GetSection(PaymentOptions.SectionName))
    .Validate(o => o.TimeoutSeconds is >= 1 and <= 60,
        "TimeoutSeconds must be between 1 and 60")
    .Validate(o => o.BaseUrl.Scheme == Uri.UriSchemeHttps,
        "Payments BaseUrl must use HTTPS")
    .ValidateOnStart();
```

Consumer:

```csharp
public sealed class PaymentClient
{
    private readonly IOptionsMonitor<PaymentOptions> _options;

    public PaymentClient(IOptionsMonitor<PaymentOptions> options)
        => _options = options;
}
```

Không phải mọi option nên hot reload. Connection topology, DI wiring hoặc auth authority thay đổi runtime có thể cần controlled restart để reasoning dễ hơn.

## 5. Real production scenario

Một App Service release dùng environment variable `Payments__TimeoutSeconds=6000` vì nhầm milliseconds với seconds. Không validation, request đến payment provider treo quá lâu, connection usage tăng và p99 latency bùng lên.

Fail-on-start biến lỗi này thành deployment failure rõ ràng trước khi instance nhận traffic.

## 6. Failure scenario & troubleshooting

**Symptom:** sau config change, một số requests dùng value mới, một số component vẫn dùng value cũ.

**Evidence:** code trộn `IOptions<T>` và `IOptionsMonitor<T>`; singleton captured giá trị `_options.Value.TimeoutSeconds` trong constructor.

**Hypothesis:** expectation về reload không khớp options lifetime.

**Diagnosis:** map consumer lifetime và thời điểm đọc `.Value`/`.CurrentValue`.

**Fix:** chọn rõ reloadable vs restart-required configuration; dùng monitor khi thật sự cần dynamic value.

**Verification:** change config trong controlled environment và xác nhận behavior của từng consumer.

## 7. Common mistakes

- Không `ValidateOnStart` cho critical options.
- Hot reload secret/network config mà không thiết kế reinitialization.
- Dùng `IOptionsSnapshot<T>` trong singleton.
- Đọc option một lần trong constructor rồi tưởng `IOptionsMonitor` sẽ tự thay field cached.
- Log toàn bộ options chứa secret.
- Cho default value che mất config deployment bị thiếu.

## 8. Alternatives

- **Direct `IConfiguration`:** hợp lý cho trivial bootstrap logic nhưng không tốt khi lan rộng.
- **Typed Options:** default tốt cho component configuration.
- **External dynamic configuration/feature flags:** phù hợp runtime behavior cần audit/targeting hơn là raw app settings.

## 9. Trade-offs

### Advantages

- Strongly typed contract.
- Centralized validation.
- Có lifecycle/reload model rõ hơn.

### Costs / Risks

- Dynamic reload tăng complexity.
- Validation quá strict có thể làm deployment fail vì optional downstream tạm thời không available nếu validator thực hiện network I/O.
- Options object vẫn không thay business validation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết bind section thành typed object và không rải config keys khắp code.

### Middle

Biết `IOptions`, `IOptionsSnapshot`, `IOptionsMonitor` khác nhau và validate values.

### Senior

Thiết kế fail-fast startup, secret handling và reload semantics phù hợp component lifecycle.

### Technical Lead / Architect

Quyết định config nào hot-reload, config nào restart-required, ai sở hữu validation và deployment gate nào chặn config sai trước production traffic.

## 11. Key takeaway

- Configuration là runtime dependency cần contract và validation như code.
- Fail-fast thường tốt hơn fail ngẫu nhiên giữa traffic.
- Reload semantics phải được thiết kế, không xuất hiện tự động chỉ vì dùng `IOptionsMonitor`.

# 3. EF Core projection và query translation: chỉ lấy dữ liệu cần dùng thay vì materialize entity graph rồi mới lọc trong memory

## 1. What is it?

Projection là dùng `Select` để shape result thành DTO/value chỉ chứa fields cần thiết thay vì load full entity.

```text
Entity query -> SELECT many columns -> track/materialize graph
Projection   -> SELECT needed columns -> DTO
```

Trong EF Core, `IQueryable<T>` được build thành expression tree để provider translate thành SQL. Điều gì nằm trong SQL và điều gì chạy trong memory là boundary quan trọng.

## 2. Why does it exist?

API list page thường chỉ cần `Id`, `Name`, `Status`, nhưng entity có 40 columns và navigations. Load full entity tạo:

- network payload DB lớn hơn;
- materialization cost;
- tracking overhead nếu quên `AsNoTracking`;
- temptation dùng `Include` quá mức.

Projection đưa computation xuống database khi translate được và chỉ trả data cần dùng.

## 3. How does it work?

```csharp
var query = db.Orders
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderListItem(
        x.Id,
        x.Number,
        x.Status,
        x.Total));
```

EF Core inspect expression tree và translate thành SQL gần như:

```sql
SELECT Id, Number, Status, Total
FROM Orders
WHERE CustomerId = @customerId;
```

Nếu gọi `ToListAsync` quá sớm rồi `.Where(...)`, phần sau chạy trong memory.

## 4. Practical implementation

Bad:

```csharp
var orders = await db.Orders
    .Include(x => x.Items)
    .ToListAsync(ct);

return orders
    .Where(x => x.Status == OrderStatus.Open)
    .Select(MapToDto)
    .ToList();
```

Better:

```csharp
return await db.Orders
    .Where(x => x.Status == OrderStatus.Open)
    .OrderByDescending(x => x.CreatedAt)
    .Select(x => new OrderDto(
        x.Id,
        x.Number,
        x.Items.Count,
        x.Total))
    .Take(100)
    .ToListAsync(ct);
```

Luôn inspect generated SQL khi performance quan trọng:

```csharp
var sql = query.ToQueryString();
```

## 5. Real production scenario

Product API trả 50 products. Version đầu load full product entity + media + categories + pricing history rồi map DTO. SQL result hàng MB, request latency tăng theo catalog complexity.

Projection chỉ lấy current price, title, thumbnail URL và availability làm query nhỏ hơn đáng kể mà không cần đổi database.

## 6. Failure scenario & troubleshooting

**Symptom:** endpoint có 50 items nhưng database reads/network bytes rất cao.

**Evidence:** SQL SELECT hàng chục columns, joins lớn, materialized entity count cao.

**Hypothesis:** over-fetching hoặc premature materialization.

**Diagnosis:** inspect `ToQueryString`, execution plan, row count/bytes, trace EF command duration.

**Fix:** project sớm, filter/sort trước materialization, tránh unnecessary `Include`.

**Verification:** compare SQL, logical reads, payload và request p95 trước/sau.

## 7. Common mistakes

- Gọi `ToListAsync` trước filter/pagination.
- Dùng helper method không translate được trong query mà không nhận ra boundary.
- `Include` mọi navigation để “đỡ N+1” rồi tạo cartesian explosion.
- Map bằng reflection sau khi load full entity trong hot list endpoint.
- Assume DTO projection luôn nhanh mà không xem plan/index.

## 8. Alternatives

- **Full tracked entity:** đúng khi business operation cần mutate aggregate.
- **Projection:** tốt cho read models/API responses.
- **Raw SQL/Dapper:** hữu ích khi query phức tạp hoặc cần kiểm soát SQL chặt, đổi lấy abstraction khác.
- **Materialized read model:** phù hợp khi query business quá đắt dù projection đã tốt.

## 9. Trade-offs

### Advantages

- Ít data transfer và materialization.
- Query intent rõ.
- Phù hợp CQRS-style read side mà không cần full CQRS infrastructure.

### Costs / Risks

- Projection lớn có thể duplicate mapping code.
- Provider translation limitations cần hiểu.
- Query vẫn có thể chậm nếu access pattern/index kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `IQueryable` chưa chạy cho tới khi materialize và `Select` có thể shape SQL.

### Middle

Viết projection, inspect SQL và tránh `Include` không cần thiết.

### Senior

Phân biệt ORM overhead với DB plan/I/O; chọn entity mutation vs read projection theo use case.

### Technical Lead / Architect

Quyết định khi direct EF projection đủ, khi cần dedicated read model/query layer và khi complexity của CQRS riêng chưa đáng.

## 11. Key takeaway

- Đừng load object graph lớn chỉ để trả DTO nhỏ.
- Materialization boundary quyết định phần nào chạy ở database vs memory.
- Projection là optimization về data access pattern, không phải phép chữa mọi slow query.

# 4. SQL Server parameter sniffing và plan cache: cùng một query có thể nhanh với parameter này nhưng chậm khủng khiếp với parameter khác

## 1. What is it?

SQL Server thường compile execution plan khi query/procedure chạy và cache plan để tái sử dụng. **Parameter sniffing** là việc optimizer dùng parameter value tại compile time để estimate cardinality và chọn plan.

Điều này thường tốt. Vấn đề xuất hiện khi data distribution skewed:

```text
Tenant A: 50 rows
Tenant B: 50,000,000 rows
```

Một plan tối ưu cho A có thể rất tệ cho B, hoặc ngược lại.

## 2. Why does it exist?

Compile query mỗi lần tốn CPU. Reusing plan giúp throughput tốt hơn.

Optimizer cần cardinality estimate để quyết định index seek/scan, join algorithm, memory grant và parallelism. Parameter actual value cho estimate tốt hơn generic assumption — nếu workload tương đối đồng đều.

## 3. How does it work?

Stored procedure:

```sql
CREATE PROCEDURE dbo.GetOrdersByCustomer
    @CustomerId bigint
AS
BEGIN
    SELECT Id, CreatedAt, Total
    FROM dbo.Orders
    WHERE CustomerId = @CustomerId;
END
```

First execution có thể compile với customer chỉ có 3 orders và cache seek-oriented plan. Later execution cho mega-customer hàng triệu rows reuse cùng plan.

Mental flow:

```text
query + parameters
   -> plan cache hit? yes -> reuse plan
   -> no -> compile using estimates -> cache
```

## 4. Practical implementation

Đừng nhảy ngay tới `OPTION (RECOMPILE)`. Đầu tiên đo.

Query diagnostic:

```sql
SELECT qs.execution_count,
       qs.total_elapsed_time,
       qs.total_logical_reads,
       st.text
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
ORDER BY qs.total_elapsed_time DESC;
```

Các mitigation có thể gồm:

```sql
OPTION (RECOMPILE)
```

hoặc plan-sensitive query features/version-specific optimizer behavior, query rewrite, index/data-model adjustment.

`RECOMPILE` đổi plan reuse lấy compile cost; chỉ dùng khi evidence hợp lý.

## 5. Real production scenario

Multi-tenant SaaS: 95% tenants nhỏ, 5% tenants cực lớn. API cùng stored procedure. Sau deployment/restart, tenant nào gọi đầu tiên ảnh hưởng plan được cache. Production latency “ngẫu nhiên” thay đổi dù code không đổi.

Đây là dấu hiệu cần nhìn plan cache/cardinality, không chỉ scale App Service.

## 6. Failure scenario & troubleshooting

**Symptom:** cùng endpoint/query text, có lúc 50 ms, có lúc 20 giây; restart hoặc plan eviction làm behavior đổi.

**Evidence:** actual row count khác estimate rất lớn; plan hash thay đổi; slow cases correlate parameter skew.

**Hypothesis:** cached plan không phù hợp subset parameter.

**Diagnosis:** capture actual execution plan cho fast/slow parameter, Query Store, statistics distribution.

**Fix:** chọn mitigation nhỏ nhất: update stats nếu stale, index/data distribution fix, recompile/selective plan strategy hoặc query split.

**Verification:** test representative small/medium/large parameter values, không chỉ một happy case.

## 7. Common mistakes

- Gọi mọi plan-cache issue là parameter sniffing.
- Clear toàn bộ plan cache trong production để “fix”.
- Dùng `RECOMPILE` khắp nơi.
- Test chỉ parameter phổ biến.
- Không xem statistics/data skew.
- Thêm index mới mà không xem memory grant/join/cardinality.

## 8. Alternatives

- **Plan reuse:** default tốt cho workload ổn định.
- **Per-execution recompile:** tốt khi query ít chạy nhưng parameter skew rất lớn.
- **Separate query paths:** explicit cho fundamentally different workloads.
- **Different data model/partitioning:** khi skew phản ánh architectural hotspot sâu hơn.

## 9. Trade-offs

### Advantages

- Plan caching tiết kiệm compile CPU.
- Sniffing thường tạo plan rất tốt cho typical parameter.

### Costs / Risks

- Skewed data làm một plan khó phù hợp tất cả cases.
- Recompile tăng CPU.
- Query hints có thể trở thành technical debt khi data thay đổi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SQL query không chỉ “chạy text”; optimizer tạo execution plan.

### Middle

Biết đọc estimated vs actual rows, Query Store và statistics cơ bản.

### Senior

Phân biệt stale stats, bad indexing, parameter skew và plan regression.

### Technical Lead / Architect

Thiết kế tenant/data partitioning và performance test để skewed workloads được đại diện; không dùng operational restart như performance strategy.

## 11. Key takeaway

- Parameter sniffing là optimization bình thường, chỉ thành vấn đề khi one-plan-fits-all không còn đúng.
- Evidence nằm ở plans, estimates và parameter distribution.
- Fix tốt nhất thường nhỏ và targeted hơn clear cache hoặc hint toàn hệ thống.

# 5. MongoDB compound indexes và ESR reasoning: thiết kế index theo Equality–Sort–Range thay vì “index mọi field hay query”

## 1. What is it?

Compound index chứa nhiều fields theo thứ tự xác định:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

Thứ tự fields ảnh hưởng query nào có thể dùng index hiệu quả.

Một heuristic phổ biến là **ESR**:

- Equality fields trước;
- Sort fields tiếp theo;
- Range fields sau.

Đây là reasoning guideline, không phải luật bất biến.

## 2. Why does it exist?

MongoDB B-tree-like indexes sắp xếp keys theo prefix order. Nếu query phù hợp prefix, engine thu hẹp search space và đôi khi đáp ứng sort trực tiếp từ index.

Index riêng từng field không tự động tương đương một compound index phù hợp access pattern.

## 3. How does it work?

Query:

```javascript
db.orders.find({
  tenantId: "t1",
  status: "Open",
  createdAt: { $gte: ISODate("2026-09-01") }
}).sort({ createdAt: -1 })
```

Index:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

Equality trên `tenantId`, `status` thu hẹp prefix; `createdAt` vừa hỗ trợ sort vừa phục vụ range theo access pattern cụ thể.

`explain("executionStats")` cho biết keys examined, docs examined và stage plan.

## 4. Practical implementation

```javascript
db.orders.createIndex(
  { tenantId: 1, status: 1, createdAt: -1 },
  { name: "ix_orders_tenant_status_created" }
)
```

Kiểm tra:

```javascript
db.orders.find({
  tenantId: "t1",
  status: "Open"
})
.sort({ createdAt: -1 })
.limit(50)
.explain("executionStats")
```

Quan sát `totalKeysExamined`, `totalDocsExamined`, returned count và blocking sort có xuất hiện không.

## 5. Real production scenario

Order dashboard luôn filter tenant + status, sort newest first. Team tạo ba single-field indexes. Query vẫn scan nhiều keys và sort tốn memory.

Một compound index theo real access pattern giảm scan đáng kể. Nhưng thêm index này làm write cost và disk footprint tăng — cần cân bằng.

## 6. Failure scenario & troubleshooting

**Symptom:** query chỉ trả 50 rows nhưng examine hàng trăm nghìn keys/docs.

**Evidence:** `explain` cho thấy IXSCAN prefix không selective hoặc SORT stage lớn.

**Hypothesis:** field order/index không match query shape hoặc low-selectivity predicate dẫn scan rộng.

**Diagnosis:** inspect query shapes thực tế, cardinality và existing indexes.

**Fix:** thiết kế compound index theo dominant access pattern; loại redundant indexes nếu an toàn.

**Verification:** compare examined/returned ratio, latency và write overhead.

## 7. Common mistakes

- Index mọi field riêng lẻ.
- Chỉ nhìn read latency mà bỏ write amplification.
- Tạo compound index theo object field order thay vì query pattern.
- Không tính multi-tenant prefix.
- Copy ESR rule máy móc khi range selectivity/sort requirement khác.
- Giữ nhiều overlapping indexes lâu dài.

## 8. Alternatives

- **Single-field index:** đủ cho query đơn giản.
- **Compound index:** tốt cho stable multi-field access pattern.
- **Partial index:** giảm footprint khi subset rõ.
- **Different document model:** khi query pattern liên tục cần joins/references phức tạp mà indexing không cứu được.

## 9. Trade-offs

### Advantages

- Giảm scanned keys/docs.
- Có thể tránh in-memory sort.
- Rất hiệu quả cho known hot query shapes.

### Costs / Risks

- Mỗi index tăng disk, RAM pressure và write cost.
- Index proliferation làm maintenance khó.
- Data/query distribution thay đổi có thể làm index cũ kém giá trị.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index là ordered structure và field order có ý nghĩa.

### Middle

Dùng `explain`, đọc examined/returned ratio và thiết kế compound index cho query cụ thể.

### Senior

Cân bằng read optimization với write amplification, memory và index overlap.

### Technical Lead / Architect

Đánh giá access patterns trước document model/index strategy; quyết định MongoDB có còn phù hợp khi query requirements đổi sâu.

## 11. Key takeaway

- Compound index phải xuất phát từ access pattern thực tế.
- ESR là heuristic để reasoning, không phải công thức tuyệt đối.
- Đo cả read benefit và write/storage cost trước khi thêm index.

# 6. CQRS với một database vs separate read/write stores: separation of intent không đồng nghĩa phải nhân đôi hạ tầng

## 1. What is it?

CQRS tách **Command** — intent thay đổi state — khỏi **Query** — intent đọc state.

Điều quan trọng:

```text
CQRS != bắt buộc 2 database
CQRS != bắt buộc Event Sourcing
CQRS != bắt buộc message broker
```

Bạn có thể dùng CQRS trong một monolith với cùng SQL database nhưng khác models/handlers cho read và write.

## 2. Why does it exist?

Read và write thường có yêu cầu khác:

- write cần invariant, transaction và domain behavior;
- read cần projection, joins, pagination và response shape tối ưu UI.

Ép cả hai đi qua cùng entity/repository abstraction đôi khi làm model vừa phức tạp vừa kém hiệu quả.

CQRS cho phép separation of intent mà không cần distributed architecture ngay lập tức.

## 3. How does it work?

Level đơn giản:

```text
POST /orders
 -> CreateOrderCommandHandler
 -> Domain + EF Core
 -> SQL DB

GET /orders/{id}
 -> GetOrderQueryHandler
 -> EF projection / SQL
 -> cùng SQL DB
```

Level phức tạp hơn:

```text
Write DB -> events -> projection pipeline -> Read Store
```

Level hai thêm eventual consistency và operational burden.

## 4. Practical implementation

Command:

```csharp
public sealed record ApproveTimesheet(Guid Id, Guid ApproverId);

public sealed class ApproveTimesheetHandler
{
    private readonly AppDbContext _db;

    public async Task Handle(ApproveTimesheet command, CancellationToken ct)
    {
        var sheet = await _db.Timesheets
            .SingleAsync(x => x.Id == command.Id, ct);

        sheet.Approve(command.ApproverId);
        await _db.SaveChangesAsync(ct);
    }
}
```

Query:

```csharp
public Task<TimesheetDetails?> GetAsync(Guid id, CancellationToken ct) =>
    _db.Timesheets
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new TimesheetDetails(x.Id, x.Status, x.TotalHours))
        .SingleOrDefaultAsync(ct);
```

Cùng DB, nhưng models và optimization khác nhau.

## 5. Real production scenario

Employee platform có approval workflows giàu invariant nhưng dashboard cần aggregate hàng nghìn records. Dùng full domain aggregate cho dashboard rất nặng.

Tách query model giúp read path đơn giản mà không phải dựng Kafka/Service Bus/read database riêng chỉ vì label “CQRS”.

## 6. Failure scenario & troubleshooting

**Symptom:** team triển khai separate read store, nhưng user thấy dữ liệu “vừa approve xong vẫn Pending”.

**Evidence:** write commit thành công; projection consumer backlog 30 giây.

**Hypothesis:** eventual consistency bị đưa vào UX mà không thiết kế expectation.

**Diagnosis:** trace event publish, consumer lag, projection timestamp.

**Fix:** nếu freshness requirement strict, dùng same DB/read-your-write strategy hoặc expose processing state; scale/fix projection nếu separate store thực sự cần.

**Verification:** define và đo freshness SLO.

## 7. Common mistakes

- Đồng nhất CQRS với MediatR.
- Tách 2 DB trước khi có scaling/query pressure thật.
- Cho command handler return giant read DTO để “đỡ gọi query”.
- Tạo one-handler-per-trivial-method ceremony không mang giá trị.
- Bỏ transaction/invariant chỉ vì command/query đã tách class.

## 8. Alternatives

- **Simple service + DbContext:** tốt cho CRUD/domain đơn giản.
- **CQRS same DB:** separation tốt với operational cost thấp.
- **CQRS separate stores:** phù hợp khi read scale/model/freshness trade-off justify.
- **Event Sourcing:** giải bài toán lịch sử/event model khác, không phải mặc định của CQRS.

## 9. Trade-offs

### Advantages

- Read/write model độc lập hơn.
- Query optimization không làm bẩn domain write model.
- Có đường tiến hóa dần khi scale tăng.

### Costs / Risks

- Thêm code paths/concepts.
- Separate stores tạo eventual consistency, replay và operations.
- Overuse tạo ceremony trong system đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu command thay đổi state, query đọc state và hai intent không bắt buộc dùng hai databases.

### Middle

Viết command/query handlers với transaction/read projection rõ.

### Senior

Biết khi nào separate read model mang performance/complexity benefit và cách debug projection lag.

### Technical Lead / Architect

Chọn mức CQRS nhỏ nhất đủ giải quyết problem; xác định consistency/freshness contract trước khi tách infrastructure.

## 11. Key takeaway

- CQRS trước hết là separation of intent.
- Same-database CQRS thường đủ cho nhiều enterprise systems.
- Separate read/write stores chỉ nên xuất hiện khi scale/model requirements trả được operational cost.

# 7. Azure Private Endpoint và Private DNS: kết nối private đúng network path nhưng vẫn có thể fail chỉ vì name resolution sai

## 1. What is it?

Private Endpoint tạo một network interface với private IP trong VNet để truy cập một Azure PaaS resource qua private connectivity thay vì public endpoint path.

Mental model:

```text
App in VNet
   |
DNS: account.blob.core.windows.net
   |
   v
private IP
   |
Private Endpoint
   |
Azure Storage
```

Network path và DNS resolution phải cùng đúng.

## 2. Why does it exist?

Nhiều enterprise workloads không muốn traffic tới Storage, SQL, Key Vault hoặc other PaaS services đi qua public ingress, kể cả khi TLS vẫn bảo vệ payload.

Private Endpoint cho phép private routing và kết hợp network policy/disable public access.

Nhưng resource hostname thường vẫn là public-style DNS name; private DNS override mapping nó sang private IP.

## 3. How does it work?

Azure dùng Private DNS Zone, ví dụ service-specific `privatelink` zone. Application resolve normal hostname; DNS chain trả CNAME/private record phù hợp.

```text
Application
 -> DNS lookup
 -> private zone link to VNet
 -> 10.x private endpoint IP
 -> service
```

Nếu DNS zone không link đúng VNet, app có thể resolve public IP dù private endpoint tồn tại hoàn hảo.

## 4. Practical implementation

Ở application layer, connection string thường không cần đổi sang raw IP. Vẫn dùng service hostname để TLS certificate/SNI và SDK behavior đúng.

Troubleshoot từ runtime environment:

```bash
nslookup mystorage.blob.core.windows.net
```

và network test:

```bash
curl -v https://mystorage.blob.core.windows.net/
```

Trong container/App Service integrated VNet, cần test **từ chính hosting environment**, không chỉ laptop.

## 5. Real production scenario

App Service kết nối Azure SQL qua Private Endpoint. Infrastructure team tạo endpoint và disable public network. Deployment xong API trả 500 database connection timeout.

Endpoint healthy nhưng App Service VNet không resolve private DNS zone, nên hostname vẫn ra public IP bị block.

## 6. Failure scenario & troubleshooting

**Symptom:** TCP timeout sau khi disable public access.

**Evidence:** `nslookup` từ app instance trả public IP; Private Endpoint status Approved.

**Hypothesis:** DNS/VNet link hoặc custom DNS forwarding sai.

**Diagnosis:** kiểm tra hostname resolution, effective DNS, zone links, VNet integration, route/NSG khi relevant.

**Fix:** link Private DNS Zone đúng VNet hoặc cấu hình DNS forwarding/conditional resolver chuẩn.

**Verification:** hostname resolve private IP và application dependency telemetry trở lại bình thường.

## 7. Common mistakes

- Tạo Private Endpoint rồi nghĩ thế là đủ.
- Hardcode private IP vào connection string.
- Test DNS từ local machine thay vì app environment.
- Disable public network trước khi validate private path.
- Không tính on-premises/custom DNS forwarding.
- Confuse Private Endpoint với service authentication; network private không thay Managed Identity/credentials.

## 8. Alternatives

- **Public endpoint + firewall/IP rules:** đơn giản hơn, có thể đủ cho lower-risk workloads.
- **Service Endpoints:** network model khác, không cấp private endpoint NIC cho service.
- **Private Endpoint:** isolation mạnh hơn nhưng DNS/infra complexity cao hơn.

## 9. Trade-offs

### Advantages

- Private address path tới PaaS service.
- Có thể disable public network exposure.
- Phù hợp enterprise security/network segmentation.

### Costs / Risks

- DNS trở thành critical infrastructure.
- Chi phí endpoint và operational troubleshooting tăng.
- Multi-VNet/on-prem connectivity phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hostname resolution quyết định endpoint IP trước khi TCP connection bắt đầu.

### Middle

Biết test DNS/network từ hosting environment và không hardcode IP.

### Senior

Trace dependency failure xuyên DNS, VNet, routing, NSG và identity; phân biệt timeout network với auth failure.

### Technical Lead / Architect

Quyết định resource nào cần Private Endpoint dựa trên threat model/compliance; chuẩn hóa private DNS architecture thay vì cấu hình ad hoc từng app.

## 11. Key takeaway

- Private connectivity không hoạt động nếu DNS vẫn dẫn app ra public endpoint.
- Network isolation và application authentication là hai boundary khác nhau.
- Với Private Endpoint incident, kiểm tra name resolution trước khi đoán SDK/database lỗi.

# 8. IIS Application Pool recycle với ASP.NET Core: process restart, in-memory state và startup failure trong enterprise Windows hosting

## 1. What is it?

Trong IIS hosting, Application Pool quản lý worker process lifecycle. Với ASP.NET Core, IIS thường đứng phía trước và chuyển request tới ASP.NET Core Module/application process theo hosting model.

Recycle nghĩa là process hosting application có thể được thay thế/restart vì configuration, schedule, memory limits, deployment hoặc health behavior.

Mental model:

```text
Client -> IIS -> ASP.NET Core hosting module -> .NET application process
                                      |
                                      +-> recycle/restart lifecycle
```

## 2. Why does it exist?

Long-running web processes cần lifecycle management:

- recover unhealthy process;
- apply deployment/config changes;
- isolate applications;
- manage identity/resources.

Nhưng recycle phá mọi state chỉ tồn tại trong process memory. Vì vậy application production phải coi process là disposable.

## 3. How does it work?

Khi recycle/restart xảy ra, process cũ stop và process mới startup. Tùy configuration có overlap, idle timeout, preload/warm-up behavior.

In-memory cache, static dictionaries, local sessions và fire-and-forget tasks biến mất cùng process.

Request routing chỉ an toàn khi app startup thành công và health validation hợp lý.

## 4. Practical implementation

Session/business state cần external store nếu phải survive process restart:

```csharp
builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = builder.Configuration
        .GetConnectionString("Redis");
});

builder.Services.AddSession();
```

Health endpoint nên kiểm tra readiness có ý nghĩa nhưng tránh biến mọi optional dependency thành reason restart loop.

Startup logging cần ghi rõ configuration validation/migration/dependency initialization failures.

## 5. Real production scenario

Legacy enterprise site chạy IIS, lưu shopping cart bằng static dictionary để “nhanh”. Mỗi recycle user mất cart ngẫu nhiên. Team tưởng browser/session bug.

Root cause là state ownership sai: process memory bị coi như durable/shared state.

## 6. Failure scenario & troubleshooting

**Symptom:** sau deploy site trả 502.5/500.30 hoặc IIS repeatedly restarts app.

**Evidence:** Windows Event Log, stdout/startup logs, ASP.NET Core Module errors, application startup exception.

**Hypothesis:** process không start được do config, binding, permissions, missing runtime hoặc startup migration.

**Diagnosis:** đọc host/module logs, chạy app trực tiếp nếu phù hợp, kiểm tra identity/file permissions/env vars/runtime.

**Fix:** sửa startup dependency/config; không tăng recycle limits để che startup exception.

**Verification:** clean restart + request/health check + monitoring qua vài recycle cycles.

## 7. Common mistakes

- Dùng local memory làm durable state.
- Fire-and-forget long job trong web process.
- Chạy schema migration nặng trong startup của mọi instance.
- Không bật/thu startup logs khi troubleshooting.
- Coi recycle là memory-leak fix vĩnh viễn.
- Đặt App Pool identity quyền filesystem quá rộng.

## 8. Alternatives

- **IIS:** phù hợp Windows enterprise/legacy integration.
- **Azure App Service:** managed hosting giảm OS/IIS ops nhưng process vẫn disposable.
- **Windows Service/Worker:** tốt cho background workloads.
- **Containers/Linux:** lifecycle model khác nhưng principle stateless/disposable process vẫn giữ nguyên.

## 9. Trade-offs

### Advantages

- Mature Windows process management.
- Integration tốt với enterprise Windows environment.
- Isolation theo application pool.

### Costs / Risks

- Nhiều hosting layers khiến diagnosis cần biết IIS + ASP.NET Core Module + .NET process.
- Process lifecycle có thể làm lộ các design sai về in-memory state.
- Windows/IIS operations là thêm platform knowledge cần duy trì.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu web process có thể restart bất kỳ lúc nào; memory không phải durable storage.

### Middle

Biết đọc startup logs/Event Viewer, cấu hình environment và App Pool identity cơ bản.

### Senior

Debug recycle/startup incidents, phân biệt platform lifecycle với application leak/state bugs.

### Technical Lead / Architect

Quyết định workload nào còn hợp IIS, workload nào nên modernize; loại bỏ assumptions về sticky/local state trước scale/migration.

## 11. Key takeaway

- IIS recycle là lifecycle bình thường; application phải chịu được process replacement.
- In-memory state chỉ phù hợp khi mất nó là acceptable.
- Startup/recycle incidents cần evidence từ hosting layer và application layer cùng lúc.

# 9. p99 latency và load testing: average latency có thể đẹp trong khi một nhóm user vẫn gặp trải nghiệm production tệ

## 1. What is it?

Latency percentile trả lời “bao nhiêu phần trăm requests hoàn thành dưới ngưỡng này”.

```text
p50 = median
p95 = 95% requests nhanh hơn giá trị này
p99 = 99% requests nhanh hơn giá trị này
```

Average có thể bị che bởi phần lớn requests nhanh dù tail latency cực xấu.

## 2. Why does it exist?

Distributed systems có variability: GC pause, lock contention, cold cache, network retries, slow DB plan, noisy neighbor.

Nếu 1% requests mất 8 giây ở hệ thống 10 triệu requests/ngày, đó vẫn là 100.000 trải nghiệm tệ.

Percentiles cho thấy tail behavior mà average không mô tả tốt.

## 3. How does it work?

Ví dụ 100 requests:

```text
99 requests = 100 ms
1 request   = 10,000 ms
```

Average khoảng 199 ms — nhìn vẫn “không quá tệ”. Nhưng p99 gần 10 giây, phản ánh user pain ở tail.

Load test cần realistic concurrency, arrival rate và duration đủ để warm-up + saturation behavior xuất hiện.

## 4. Practical implementation

Một test plan nên capture ít nhất:

- throughput/request rate;
- p50/p95/p99;
- error rate;
- CPU/memory/GC;
- DB dependency p95/p99;
- connection/thread pool saturation.

Trong Application Insights/OpenTelemetry metrics, histogram là cấu trúc phù hợp hơn chỉ average timer.

Khi test, thay đổi một variable chính tại một thời điểm và giữ dataset representative.

## 5. Real production scenario

API search average 220 ms, dashboard xanh. User complaint “thỉnh thoảng mất 5–10 giây”. p99 cho thấy 7.4 s, trace chậm correlate Elasticsearch timeout + retry.

Average đã che cascade ở 1% traffic.

## 6. Failure scenario & troubleshooting

**Symptom:** load test average ổn nhưng production tail latency cao.

**Evidence:** test dùng closed-loop nhỏ; dataset ít; cache luôn warm; không simulate slow dependency.

**Hypothesis:** benchmark không đại diện arrival/concurrency/data distribution production.

**Diagnosis:** compare test traffic model với production telemetry; inspect saturation point và slow traces.

**Fix:** realistic arrival pattern, larger dataset, cold/warm phases, fault scenarios và dependency limits.

**Verification:** test percentile shape gần production baseline trước khi dùng nó đánh giá optimization.

## 7. Common mistakes

- Chỉ report average.
- So p99 của sample quá nhỏ.
- Load test từ cùng machine với server.
- Không warm JIT/cache hoặc ngược lại luôn warm cache không realistic.
- Tăng concurrency vô hạn rồi kết luận app “không scale”.
- Optimize p50 trong khi incident nằm ở retry/timeout tail.

## 8. Alternatives

Không có alternative trực tiếp cho percentiles; chúng bổ sung average, max và distributions.

- **Average:** hữu ích cost/aggregate reasoning.
- **Percentiles:** user experience/SLO.
- **Traces:** tìm root cause từng slow request.
- **Profiles/counters:** tìm runtime bottleneck.

## 9. Trade-offs

### Advantages

- Tail latency phản ánh reliability/user pain tốt hơn average.
- Percentile SLO tạo performance target rõ.

### Costs / Risks

- p99 cần đủ volume để stable.
- High-cardinality breakdown sai có thể làm metrics cost cao.
- Tối ưu cực đoan tail mà không business value có thể lãng phí engineering effort.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu average và percentile trả lời câu hỏi khác nhau.

### Middle

Biết đọc p50/p95/p99 và correlate slow requests với traces/dependencies.

### Senior

Thiết kế representative load test, nhận diện saturation/retry/GC/DB tail effects.

### Technical Lead / Architect

Đặt performance SLO theo user journey và business criticality; quyết định optimization nào đáng cost thay vì chạy benchmark để lấy số đẹp.

## 11. Key takeaway

- Average latency có thể che hàng nghìn user requests tệ.
- p95/p99 phải được đọc cùng throughput, errors và dependency telemetry.
- Load test chỉ có giá trị khi traffic/data model đủ giống production problem cần trả lời.

# 10. AI coding agents với verification gates: dùng agent tăng tốc nhưng build, test, static analysis và diff review mới là correctness boundary

## 1. What is it?

AI coding agent có thể đọc repository, sửa nhiều files, chạy commands và tạo patch/commit theo goal.

Mental model đúng:

```text
Intent/spec
   -> Agent proposes changes
   -> deterministic verification
   -> human/system review
   -> merge/release
```

Agent là probabilistic change producer, không phải authority quyết định code đúng.

## 2. Why does it exist?

Nhiều software tasks có lượng mechanical work lớn: migration, boilerplate, test generation, repetitive refactor, repository discovery.

Agent có thể rút ngắn thời gian explore + edit, nhưng cũng có thể:

- dùng API/package không tồn tại;
- hiểu sai architecture boundary;
- làm test “pass” bằng cách giảm assertion;
- sửa ngoài scope;
- tạo code compile nhưng sai business semantics.

Verification gates biến speed thành usable engineering throughput.

## 3. How does it work?

Workflow nên tách probabilistic và deterministic parts:

```text
Agent reasoning/edit
      |
      v
formatter/linter
      |
      v
build
      |
      v
unit/integration tests
      |
      v
static/security checks
      |
      v
diff review + CI
```

Repository instructions, scoped task, tests và tool outputs là grounding signals.

## 4. Practical implementation

Một minimal verification script cho .NET repo:

```bash
set -euo pipefail

dotnet restore
dotnet build --no-restore -c Release
dotnet test --no-build -c Release
```

Có thể thêm formatter/static analysis/security scan tùy repo.

Agent instruction nên rõ constraint:

```text
- chỉ sửa slice X
- không đổi public contract ngoài requirement
- không merge PR
- phải chạy build + relevant tests
- nếu test fail vì pre-existing issue, ghi evidence thay vì sửa unrelated code
```

Quan trọng: test do agent tự viết không tự chứng minh correctness; test cần trace về requirement/risk.

## 5. Real production scenario

Agent migrate một service từ custom HTTP wrapper sang `IHttpClientFactory`. Code compile và unit tests pass, nhưng default timeout/retry behavior đổi làm production request timeout khác trước.

Human/diff review + integration test với slow dependency phát hiện semantic regression mà compile không thể bắt.

## 6. Failure scenario & troubleshooting

**Symptom:** agent report “all tests pass”, nhưng PR có regression.

**Evidence:** agent đã sửa test assertion để phù hợp implementation mới; requirement không được encode trong independent test.

**Hypothesis:** verification artifacts cùng nguồn với implementation nên không độc lập đủ.

**Diagnosis:** diff test files, compare acceptance criteria, run existing integration/contract tests, inspect public behavior.

**Fix:** protected tests/contracts, review test changes, add requirement-driven cases từ separate source.

**Verification:** independent CI + reviewer xác nhận behavior, không chỉ green status.

## 7. Common mistakes

- Cho agent quyền sửa mọi thứ để “tự giải quyết”.
- Tin summary thay vì inspect diff/tool output.
- Cho agent xóa failing tests.
- Không pin package/API versions.
- Merge code chưa chạy build/test.
- Dùng agent cho security/financial authorization decision mà không deterministic guardrails.
- Đánh giá productivity chỉ bằng số lines/commits generated.

## 8. Alternatives

- **AI autocomplete:** scope nhỏ, control cao.
- **Chat-based assistant:** human chủ động apply changes.
- **Repository agent:** phù hợp multi-file tasks nhưng cần stronger verification.
- **Manual implementation:** vẫn tốt cho ambiguous/high-risk work khi context transfer cost cao.

## 9. Trade-offs

### Advantages

- Tăng tốc repository exploration và mechanical edits.
- Có thể chạy verification loop nhiều lần.
- Giảm thời gian cho repetitive migration/refactor.

### Costs / Risks

- Review burden có thể chuyển từ writing sang validation.
- Large diffs làm hallucination/mis-scope khó phát hiện.
- Tool access mạnh làm blast radius lớn hơn nếu instruction sai.
- CI cost có thể tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Học dùng agent như pair tool nhưng luôn đọc code và hiểu test result.

### Middle

Viết scoped prompts/tasks, kiểm tra diff, build/test và phát hiện API hallucination.

### Senior

Thiết kế verification strategy theo risk; phân biệt generated confidence với independent evidence.

### Technical Lead / Architect

Xác định guardrails, repository permissions, protected branches/tests, task classes phù hợp cho agents và metrics đo lead time + defect rate thay vì generated volume.

## 11. Key takeaway

- AI agent có thể tăng tốc change production nhưng không phải source of truth.
- Deterministic build/test/static checks và human review là correctness boundary.
- Verification phải độc lập đủ để phát hiện cả implementation lẫn generated-test mistakes.
