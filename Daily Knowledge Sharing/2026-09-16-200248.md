# 1. .NET `ArrayPool<T>`: giảm allocation nhưng đổi lấy ownership complexity

## 1. What is it?

`ArrayPool<T>` là pool tái sử dụng arrays. Mental model đúng là **mượn một buffer có capacity tối thiểu rồi phải trả lại**, không phải cấp phát một array mới thuộc sở hữu riêng của caller.

## 2. Why does it exist?

Các hot path xử lý serialization, parsing, compression hoặc network buffers có thể tạo rất nhiều temporary arrays. Allocation lớn và liên tục làm tăng GC pressure; buffers đủ lớn còn có thể đi vào LOH. Pooling giảm số lần allocate bằng reuse memory.

## 3. How does it work?

`Rent(minimumLength)` trả một array có `Length >= minimumLength`; kích thước không được đảm bảo bằng đúng yêu cầu. `Return` đưa buffer về pool để caller khác có thể nhận lại. Vì vậy reference tới buffer không được dùng sau khi return.

```text
Rent -> use owned slice -> Return
                    |
                    +-- sau Return: dữ liệu không còn thuộc caller
```

## 4. Practical implementation

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
    await destination.WriteAsync(buffer.AsMemory(0, read), ct);
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

Chỉ phần `[0..read]` chứa dữ liệu hợp lệ. Với dữ liệu nhạy cảm, cân nhắc `clearArray: true` hoặc thiết kế tránh đưa secret vào shared pool.

## 5. Real production scenario

API xử lý hàng nghìn file chunks mỗi giây. Mỗi request tạo `byte[64KB]` mới làm allocation rate tăng mạnh và Gen 2 collections xuất hiện thường xuyên. Pooling buffers giảm allocation nhưng chỉ có ý nghĩa sau profiling chứng minh buffer allocation nằm trên hot path.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu response thỉnh thoảng bị corruption.  
**Evidence** → buffer được return rồi một async operation vẫn giữ reference.  
**Hypothesis** → ownership lifetime vượt quá lexical scope.  
**Diagnosis** → trace nơi `Rent`/`Return`, kiểm tra deferred/async consumers.  
**Fix** → giữ buffer đến khi consumer hoàn tất hoặc copy phần cần giữ.  
**Verification** → stress test concurrent workloads và kiểm tra allocation profile.

## 7. Common mistakes

Giả định rented array có đúng length; quên `Return`; double-return; dùng buffer sau return; pool mọi allocation nhỏ mà chưa đo; vô tình để dữ liệu nhạy cảm tồn tại trong pooled memory.

## 8. Alternatives

Array allocation bình thường đơn giản và thường đủ tốt. `MemoryPool<T>` hữu ích khi cần ownership object (`IMemoryOwner<T>`). `stackalloc`/`Span<T>` phù hợp với buffer nhỏ, bounded và synchronous lifetime.

## 9. Trade-offs

### Advantages

Giảm allocation rate, GC pressure và LOH churn trên hot paths.

### Costs / Risks

Ownership khó hơn, buffer có thể lớn hơn yêu cầu, dữ liệu cũ có thể còn trong memory, bug lifetime gây corruption khó tái hiện.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Rent`/`Return` và chỉ dùng logical slice.

### Middle

Dùng `try/finally`, quản lý async lifetime và benchmark allocation.

### Senior

Đánh giá GC evidence, security implications và ownership bugs.

### Technical Lead / Architect

Quyết định pooling chỉ ở measured hot paths; tránh biến optimization thành complexity mặc định toàn codebase.

## 11. Key takeaway

- Pooling đổi allocation cost lấy ownership complexity.
- Không dùng rented buffer sau `Return`.
- Chỉ tối ưu sau khi allocation/GC telemetry chứng minh vấn đề.

# 2. ASP.NET Core `IHttpClientFactory`: handler lifetime, DNS rotation và connection reuse

## 1. What is it?

`IHttpClientFactory` tạo `HttpClient` instances trong khi quản lý underlying `HttpMessageHandler` pools. Giá trị chính không phải “factory pattern”, mà là quản lý connection reuse, handler lifetime, configuration và resilience boundary cho outbound HTTP.

## 2. Why does it exist?

Tạo/dispose `HttpClient` cho từng request có thể gây connection churn và socket exhaustion. Ngược lại, giữ một handler mãi có thể giữ DNS resolution cũ quá lâu trong môi trường endpoints thay đổi.

## 3. How does it work?

```text
Application -> HttpClient (short-lived object)
                    |
                    v
          pooled HttpMessageHandler
                    |
                    v
             connection pool -> remote API
```

Factory có thể recycle handlers theo lifetime. `SocketsHttpHandler` quản lý connection pools; DNS được áp dụng khi connection mới được thiết lập, nên connection lifetime cũng quan trọng.

## 4. Practical implementation

```csharp
builder.Services.AddHttpClient<InventoryClient>(client =>
{
    client.BaseAddress = new Uri("https://inventory.internal/");
    client.Timeout = TimeSpan.FromSeconds(3);
})
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(5)
});
```

```csharp
public sealed class InventoryClient(HttpClient http)
{
    public Task<HttpResponseMessage> GetAsync(string sku, CancellationToken ct) =>
        http.GetAsync($"api/items/{Uri.EscapeDataString(sku)}", ct);
}
```

## 5. Real production scenario

Product API gọi inventory service. Sau failover, DNS trỏ sang endpoint mới nhưng một số application instances vẫn gửi traffic tới endpoint cũ vì long-lived connections. Cấu hình connection lifetime phù hợp giúp connections được tái tạo định kỳ.

## 6. Failure scenario & troubleshooting

**Symptom** → outbound failures chỉ xảy ra ở vài instances sau DNS/failover.  
**Evidence** → DNS hiện tại đúng nhưng established connections vẫn tới IP cũ.  
**Hypothesis** → connection lifetime quá dài.  
**Diagnosis** → kiểm tra handler/connection configuration và network telemetry.  
**Fix** → cấu hình `PooledConnectionLifetime` phù hợp; không recycle quá nhanh.  
**Verification** → failover test và theo dõi destination IP/error rate.

## 7. Common mistakes

`new HttpClient()` mỗi request; đặt timeout rất lớn; retry mọi status code; nhầm handler lifetime với request timeout; đưa bearer token mutable vào shared default headers không đúng ownership.

## 8. Alternatives

Một static `HttpClient` với `SocketsHttpHandler.PooledConnectionLifetime` có thể hoàn toàn tốt cho service đơn giản. Factory hữu ích khi có nhiều named/typed clients, policies và configuration boundaries.

## 9. Trade-offs

### Advantages

Connection reuse, centralized configuration, typed clients, testable integration boundary.

### Costs / Risks

Sai resilience policy vẫn gây retry storm; quá nhiều named clients/policies làm outbound behavior khó hiểu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `HttpClient` không tương ứng một TCP connection.

### Middle

Cấu hình typed client, timeout và cancellation.

### Senior

Reason về DNS, connection pooling, retry/timeout budgets và observability.

### Technical Lead / Architect

Định nghĩa outbound dependency standards theo SLA và failure propagation thay vì copy cùng policy cho mọi API.

## 11. Key takeaway

- Reuse connections nhưng phải cho phép endpoint rotation.
- Timeout, retry và connection lifetime là các knobs khác nhau.
- `IHttpClientFactory` hữu ích nhất khi outbound HTTP được coi là production dependency boundary.

# 3. EF Core `AsSplitQuery`: tránh cartesian explosion nhưng tăng round trips

## 1. What is it?

`AsSplitQuery` yêu cầu EF Core tải một query có nhiều included collections bằng nhiều SQL statements thay vì một JOIN lớn. Nó đổi **row multiplication** lấy **nhiều database round trips/commands**.

## 2. Why does it exist?

Khi include hai sibling collections, JOIN có thể tạo tích Descartes. Một Order có 20 Lines và 10 Notes có thể tạo 200 rows cho cùng Order, lặp lại parent columns và tăng network/materialization cost.

## 3. How does it work?

Single query:

```text
Orders JOIN Lines JOIN Notes -> parent rows bị nhân
```

Split query:

```text
SELECT Orders
SELECT Lines for Orders
SELECT Notes for Orders
```

EF ghép entities theo keys ở client side.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .Where(x => x.CustomerId == customerId)
    .ToListAsync(ct);
```

Trước khi dùng, đo generated SQL, row counts và payload. Projection thường tốt hơn nếu API chỉ cần một subset.

## 5. Real production scenario

Admin screen load 100 orders với Lines và AuditEntries. Một SQL JOIN trả hàng chục nghìn rows dù UI chỉ hiển thị summary. `AsSplitQuery` giảm duplicated payload, nhưng projection thành DTO summary còn hiệu quả hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → đổi sang split query nhưng latency tăng khi database ở region xa.  
**Evidence** → payload giảm nhưng số commands và network latency tăng.  
**Hypothesis** → round-trip cost lớn hơn row multiplication cost.  
**Diagnosis** → compare command count, bytes và duration.  
**Fix** → projection, reshape endpoint hoặc chọn single query nếu measured workload phù hợp.  
**Verification** → benchmark với realistic cardinality.

## 7. Common mistakes

Bật split query global để “fix performance”; include toàn graph; không dùng projection; quên consistency implications khi nhiều statements đọc dữ liệu đang thay đổi.

## 8. Alternatives

Projection (`Select`) thường tốt nhất cho read API. Explicit queries cho phép kiểm soát shape rõ hơn. Single query phù hợp khi cardinality nhỏ hoặc chỉ một collection.

## 9. Trade-offs

### Advantages

Giảm cartesian explosion và duplicated parent payload.

### Costs / Risks

Nhiều commands hơn, thêm latency và có thể quan sát dữ liệu thay đổi giữa các statements tùy transaction/isolation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` có thể làm số rows tăng.

### Middle

So generated SQL giữa single/split query.

### Senior

Đo cardinality, payload, round trips và consistency.

### Technical Lead / Architect

Định hướng API read models thay vì dùng entity graph loading như default query architecture.

## 11. Key takeaway

- `AsSplitQuery` là trade-off, không phải performance switch.
- Projection thường loại bỏ vấn đề tốt hơn khi endpoint chỉ cần subset.
- Đo rows, bytes và round trips cùng nhau.

# 4. PostgreSQL transaction isolation: `READ COMMITTED` không bảo vệ business invariant

## 1. What is it?

Isolation level xác định những thay đổi concurrent transaction có thể quan sát. PostgreSQL mặc định `READ COMMITTED`: mỗi statement nhìn snapshot tại thời điểm statement bắt đầu, không phải một snapshot cố định cho toàn transaction.

## 2. Why does it exist?

Concurrency cần cân bằng throughput và consistency. Một transaction có nhiều statements kiểu “check rồi update” có thể bị transaction khác chen vào, khiến business invariant bị phá dù từng statement riêng lẻ hợp lệ.

## 3. How does it work?

Ví dụ hai transaction cùng kiểm tra còn một slot:

```text
T1: SELECT available = 1
T2: SELECT available = 1
T1: reserve
T2: reserve
```

Nếu invariant không được encode bằng atomic update/constraint/locking phù hợp, cả hai có thể tin rằng mình hợp lệ.

## 4. Practical implementation

Ưu tiên atomic conditional mutation khi có thể:

```sql
UPDATE inventory
SET available = available - 1
WHERE sku = $1
  AND available > 0
RETURNING available;
```

Nếu không trả row, reservation thất bại. Cách này thường đơn giản hơn nâng isolation cho toàn transaction.

## 5. Real production scenario

Event registration còn một chỗ. API đọc count rồi insert registration trong hai statements. Hai requests concurrent cùng pass check. Unique/constraint hoặc atomic capacity model phải bảo vệ invariant tại database boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → overselling/overbooking hiếm khi xảy ra, không tái hiện single-user test.  
**Evidence** → concurrent traces cho thấy check và write xen kẽ.  
**Hypothesis** → application-level check không atomic.  
**Diagnosis** → reproduce bằng concurrent integration test.  
**Fix** → constraint, conditional update, row lock hoặc isolation mạnh hơn tùy invariant.  
**Verification** → stress concurrent transactions và assert invariant.

## 7. Common mistakes

Cho rằng transaction tự động loại mọi race condition; nâng lên `SERIALIZABLE` mà không xử lý serialization retry; giữ transaction mở qua remote API call; dùng distributed lock thay database constraint cho invariant cục bộ.

## 8. Alternatives

Database constraint là mạnh nhất cho invariant biểu diễn được. `SELECT ... FOR UPDATE` phù hợp pessimistic coordination. `SERIALIZABLE` cho semantics mạnh hơn nhưng transaction có thể abort và phải retry an toàn.

## 9. Trade-offs

### Advantages

Isolation mạnh/locking đúng bảo vệ correctness dưới concurrency.

### Costs / Risks

Blocking, abort/retry và throughput cost tăng. Atomic SQL đơn giản thường tốt hơn blanket isolation escalation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction không có nghĩa “không ai khác chạy cùng lúc”.

### Middle

Viết atomic update và constraints.

### Senior

Reason về snapshots, locks, retries và invariant.

### Technical Lead / Architect

Đặt invariant ở ownership boundary đúng và chọn cơ chế consistency tối thiểu nhưng đủ mạnh.

## 11. Key takeaway

- `READ COMMITTED` không bảo vệ multi-statement check-then-act.
- Encode invariant càng gần database càng tốt.
- Isolation mạnh hơn có correctness benefit nhưng mang concurrency cost.

# 5. Redis hot key: khi cache hit cao vẫn trở thành bottleneck

## 1. What is it?

Hot key là key nhận tỷ lệ traffic vượt trội so với các keys khác. Cache hit ratio có thể rất cao nhưng một Redis node/core/network path vẫn bị tập trung tải vào một key hoặc partition.

## 2. Why does it exist?

Caching thường được kỳ vọng giảm database load, nhưng workload distribution không đều. Flash sale, homepage config hoặc celebrity profile có thể biến một key thành shared choke point.

## 3. How does it work?

```text
Thousands of clients -> GET product:flash-sale
                         |
                         v
                 same Redis shard
```

Trong clustered systems, key hash quyết định shard. Replicas/read scaling chỉ giúp nếu architecture/client cho phép và consistency semantics phù hợp.

## 4. Practical implementation

Một lựa chọn là two-level cache cho dữ liệu stale-tolerant:

```csharp
if (memoryCache.TryGetValue(key, out ProductDto? value))
    return value;

value = await distributedCache.GetAsync<ProductDto>(key, ct);
memoryCache.Set(key, value, TimeSpan.FromSeconds(5));
return value;
```

Local TTL ngắn hấp thụ burst; cần chấp nhận per-instance staleness.

## 5. Real production scenario

Homepage campaign config được đọc ở mọi request. Redis CPU tăng mạnh dù database gần như idle. Một local cache 2–5 giây hoặc edge caching có thể phù hợp hơn vì dữ liệu không cần freshness theo millisecond.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis latency tăng trong traffic spike nhưng overall keyspace nhỏ.  
**Evidence** → command/key sampling cho thấy một key chiếm phần lớn operations.  
**Hypothesis** → hot-key concentration.  
**Diagnosis** → correlate key access distribution với shard CPU/network.  
**Fix** → local/edge cache, redesign access pattern hoặc controlled replication.  
**Verification** → shard utilization và p99 Redis latency cân bằng hơn.

## 7. Common mistakes

Chỉ nhìn hit ratio; tăng Redis size dù bottleneck là single hot path; random-shard cùng value nhưng không thiết kế invalidation; cache dữ liệu authorization-sensitive trong local cache không đúng scope.

## 8. Alternatives

`IMemoryCache` giảm network nhưng không shared consistency. CDN/edge cache phù hợp public HTTP content. Database có thể đủ nhanh nếu query/index tốt và traffic thấp.

## 9. Trade-offs

### Advantages

Multi-level caching có thể hấp thụ extreme read bursts.

### Costs / Risks

Staleness, invalidation complexity và memory duplication tăng; Redis có thể trở thành critical dependency ẩn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hit ratio cao không đồng nghĩa cache khỏe.

### Middle

Đo key distribution và TTL behavior.

### Senior

Reason về shard concentration, local caching và freshness budget.

### Technical Lead / Architect

Quyết định dữ liệu nên cache ở browser/CDN/app/Redis hay không cache dựa trên ownership và consistency.

## 11. Key takeaway

- Quan sát distribution, không chỉ hit ratio.
- Hot key là capacity/concentration problem.
- Cache layer gần client hơn có thể tốt hơn nếu business chấp nhận stale data.

# 6. Modular Monolith: module boundary, data ownership và transaction locality

## 1. What is it?

Modular Monolith là một deployable application nhưng được chia thành modules có ownership và dependency boundaries rõ. Nó không phải “monolith với nhiều folders”; module phải kiểm soát API, data access và coupling.

## 2. Why does it exist?

Microservices cho independent deployment nhưng thêm network failure, observability, messaging và operational cost. Khi business domains cần boundaries nhưng scale/team chưa cần distributed deployment, Modular Monolith giữ transaction/local-call simplicity.

## 3. How does it work?

```text
Host
 ├─ Orders Module -> Orders data
 ├─ Inventory Module -> Inventory data
 └─ Billing Module -> Billing data

Orders --public contract/event--> Inventory
```

Một module không nên query tables/private classes của module khác chỉ vì cùng process/database.

## 4. Practical implementation

```csharp
public interface IInventoryModule
{
    Task<ReservationResult> ReserveAsync(
        ReserveInventory command,
        CancellationToken ct);
}
```

Contract nên nhỏ và domain-oriented. Infrastructure có thể cùng SQL Server instance nhưng schema/table ownership vẫn rõ.

## 5. Real production scenario

E-commerce team có Orders, Catalog và Promotions. Traffic chưa yêu cầu independent scaling; một deploy pipeline vẫn chấp nhận được. Module boundaries giúp tránh shared-domain blob mà không phải vận hành ba services, queues và distributed tracing ngay lập tức.

## 6. Failure scenario & troubleshooting

**Symptom** → thay đổi Catalog làm Orders tests vỡ thường xuyên.  
**Evidence** → Orders reference Catalog EF entities/tables trực tiếp.  
**Hypothesis** → boundary chỉ tồn tại ở folder.  
**Diagnosis** → dependency graph và database access review.  
**Fix** → public contracts, ownership rules và architecture tests.  
**Verification** → module internals có thể refactor mà consumers không đổi.

## 7. Common mistakes

Một shared `Common` project chứa mọi domain type; modules cùng sửa tables; event bus in-process được dùng để che circular dependency; ép Clean Architecture đầy đủ bên trong từng module nhỏ.

## 8. Alternatives

Layered monolith đơn giản hơn cho domain nhỏ. Microservices phù hợp khi independent deployment/scaling/ownership thực sự cần. Modular Monolith là bước giữa hữu ích nhưng không bắt buộc phải tiến hóa thành microservices.

## 9. Trade-offs

### Advantages

Local transactions, simple deployment, lower operational cost, vẫn tạo change boundaries.

### Costs / Risks

Boundary enforcement cần discipline/tooling; một process failure/deployment vẫn ảnh hưởng toàn application.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là responsibility boundary, không phải folder.

### Middle

Tôn trọng public contracts và data ownership.

### Senior

Thiết kế transaction boundary, integration events và dependency direction.

### Technical Lead / Architect

Quyết định khi nào independent deployment đáng trả distributed-systems tax.

## 11. Key takeaway

- Module boundary phải tồn tại trong dependencies và data ownership.
- Một process/database không buộc mọi module chia sẻ model.
- Microservices chỉ nên xuất hiện khi deployment/scale/ownership pressure thực sự yêu cầu.

# 7. Azure Service Bus dead-letter queue: DLQ là recovery workflow, không phải thùng rác

## 1. What is it?

Dead-letter queue (DLQ) chứa messages không thể hoàn tất processing bình thường, ví dụ vượt `MaxDeliveryCount`, explicit dead-letter hoặc vi phạm một số broker rules. Message vẫn cần ownership và recovery decision.

## 2. Why does it exist?

Poison message retry vô hạn làm consumer tốn capacity và che backlog. DLQ tách message lỗi khỏi main flow để healthy messages tiếp tục, đồng thời giữ evidence phục vụ diagnosis/replay.

## 3. How does it work?

```text
Queue -> Consumer -> transient failure -> abandon/retry
                   -> repeated failure
                   -> DLQ -> inspect -> fix -> replay/discard
```

Azure Service Bus cung cấp at-least-once semantics; DLQ không biến processing thành exactly-once.

## 4. Practical implementation

```csharp
processor.ProcessMessageAsync += async args =>
{
    try
    {
        await handler.HandleAsync(args.Message, args.CancellationToken);
        await args.CompleteMessageAsync(args.Message, args.CancellationToken);
    }
    catch (InvalidMessageException ex)
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            "InvalidSchema",
            ex.Message,
            args.CancellationToken);
    }
};
```

Transient exceptions thường nên throw/abandon theo bounded retry policy thay vì dead-letter ngay.

## 5. Real production scenario

Notification consumer nhận message schema cũ sau deployment. Deserialization thất bại mọi lần. Sau vài deliveries message vào DLQ; alert dựa trên DLQ growth dẫn engineer tới contract incompatibility.

## 6. Failure scenario & troubleshooting

**Symptom** → main queue ổn nhưng DLQ tăng liên tục.  
**Evidence** → dead-letter reason tập trung ở `InvalidSchema`.  
**Hypothesis** → breaking producer/consumer contract.  
**Diagnosis** → compare message version và deployment timeline.  
**Fix** → backward-compatible consumer/migration; replay sau khi fix.  
**Verification** → replay sample, main processing thành công và DLQ rate về baseline.

## 7. Common mistakes

Không monitor DLQ; auto-replay vô hạn; dead-letter mọi exception; mất correlation metadata; manual delete messages mà không ghi decision/audit.

## 8. Alternatives

Quarantine store riêng hữu ích khi cần rich workflow/audit. Retry topic/queue có thể hỗ trợ delayed retries. DLQ built-in đơn giản và gắn trực tiếp broker lifecycle.

## 9. Trade-offs

### Advantages

Failure isolation, forensic evidence, controlled recovery.

### Costs / Risks

Cần tooling, alerts, retention và operational ownership; replay sai có thể tạo duplicate side effects.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DLQ chứa work chưa được giải quyết.

### Middle

Phân biệt transient/permanent failure và inspect reason.

### Senior

Thiết kế idempotent replay, alerting và schema compatibility.

### Technical Lead / Architect

Gán ownership/SLO cho DLQ và recovery runbook; không để broker failure state trở thành data graveyard.

## 11. Key takeaway

- DLQ là một phần của processing lifecycle.
- Replay phải idempotent và có chủ đích.
- Monitor DLQ rate/age, không chỉ main queue depth.

# 8. Kubernetes resource requests/limits: scheduling, throttling và OOM behavior

## 1. What is it?

`requests` mô tả resource mà scheduler dùng để đặt Pod; `limits` đặt trần runtime. CPU limit thường dẫn tới throttling; memory limit có thể dẫn tới OOM kill khi container vượt giới hạn.

## 2. Why does it exist?

Cluster cần chia sẻ finite CPU/memory giữa workloads. Không có requests, scheduler khó lập kế hoạch capacity. Không có boundaries, một workload runaway có thể ảnh hưởng workloads khác trên node.

## 3. How does it work?

```text
Scheduler: sum(requests) -> chọn Node
Runtime:
 CPU > limit    -> throttling
 Memory > limit -> container may be OOMKilled
```

Requests quá cao làm capacity bị “đặt chỗ” không cần thiết; quá thấp gây overcommit và contention.

## 4. Practical implementation

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
```

Values phải dựa trên load tests và production percentiles, không copy từ template.

## 5. Real production scenario

ASP.NET Core API có memory steady-state 300 MiB nhưng limit đặt 256 MiB từ boilerplate. Pods restart dưới traffic, readiness flap và deployment không ổn định dù code không có memory leak.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng nhưng CPU metric không đạt node capacity.  
**Evidence** → container CPU throttling cao.  
**Hypothesis** → CPU limit quá chặt.  
**Diagnosis** → correlate throttling với p95 latency/GC.  
**Fix** → tune requests/limits sau load test; xem xét autoscaling.  
**Verification** → throttling và p95 giảm mà cluster utilization vẫn hợp lý.

## 7. Common mistakes

Copy cùng limits cho mọi service; nhầm request với minimum guaranteed performance tuyệt đối; đặt memory limit sát average; troubleshoot `OOMKilled` chỉ bằng restart; autoscale dựa trên CPU nhưng request cấu hình sai.

## 8. Alternatives

VM/App Service abstractions giảm Kubernetes tuning burden. Vertical/Horizontal Pod Autoscaler hỗ trợ sizing/scaling nhưng vẫn cần hiểu workload và metrics.

## 9. Trade-offs

### Advantages

Predictable scheduling, workload isolation và capacity planning tốt hơn.

### Costs / Risks

Sai values gây waste hoặc throttling/OOM; thêm operational tuning responsibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt request và limit.

### Middle

Đọc `OOMKilled`, throttling và pod metrics.

### Senior

Tune theo load/GC/latency, hiểu HPA interaction.

### Technical Lead / Architect

Quyết định Kubernetes có đáng operational complexity so với managed compute đơn giản hơn hay không.

## 11. Key takeaway

- Requests ảnh hưởng scheduling; limits ảnh hưởng runtime behavior.
- Memory limit sai có thể biến healthy app thành restart loop.
- Resource values phải xuất phát từ measurement.

# 9. Git `bisect`: biến deployment regression thành bounded search problem

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên chuyển behavior từ good sang bad. Thay vì kiểm tra tuần tự hàng trăm commits, số lần test xấp xỉ `log2(N)`.

## 2. Why does it exist?

Production regression thường xuất hiện sau nhiều commits được release cùng lúc. Đọc diff thủ công dễ bị confirmation bias; bisect biến diagnosis thành repeatable experiment nếu có test oracle đáng tin cậy.

## 3. How does it work?

```text
known good ---------------- known bad
              ^ test midpoint
        good / bad -> halve range -> repeat
```

Git checkout midpoint; engineer hoặc script đánh dấu `good`, `bad`, đôi khi `skip`.

## 4. Practical implementation

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
# run reproduction/test
git bisect good   # or: git bisect bad
git bisect reset
```

Có thể automate:

```bash
git bisect run dotnet test tests/Regression.Tests/Regression.Tests.csproj
```

## 5. Real production scenario

Release gồm 80 commits làm API rounding sai trong một edge case. Viết regression test tái hiện bug rồi `git bisect run` có thể localize introducing commit nhanh hơn review toàn release diff.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit không liên quan hoặc kết quả thay đổi giữa runs.  
**Evidence** → reproduction test flaky/environment-dependent.  
**Hypothesis** → good/bad oracle không deterministic.  
**Diagnosis** → chạy test nhiều lần tại cùng commit.  
**Fix** → stabilize fixture/environment trước khi bisect.  
**Verification** → introducing commit và parent cho kết quả bad/good lặp lại.

## 7. Common mistakes

Bisect khi build history không reproducible; đánh dấu bad dựa trên flaky test; quên database/config migration tương ứng commit; coi introducing commit tự động là root cause hoàn chỉnh.

## 8. Alternatives

Deployment diff, feature flags, telemetry correlation và revert analysis có thể nhanh hơn khi suspect nhỏ. Bisect mạnh khi search range lớn và behavior testable.

## 9. Trade-offs

### Advantages

Giảm search space nhanh, evidence-driven, automate được.

### Costs / Risks

Phụ thuộc reproducible builds/tests; historical commits có thể không build độc lập.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết xác định good/bad commits.

### Middle

Viết deterministic regression test và chạy bisect.

### Senior

Kết hợp bisect với telemetry/deployment context để tìm root cause thực.

### Technical Lead / Architect

Đầu tư reproducible builds và regression harness để incident diagnosis không phụ thuộc trí nhớ cá nhân.

## 11. Key takeaway

- Bisect hiệu quả khi có deterministic oracle.
- Nó tìm introducing commit, không thay thế root-cause analysis.
- Reproducibility là production engineering capability.

# 10. Vue/TypeScript request cancellation: ngăn stale response ghi đè UI state

## 1. What is it?

Request cancellation ở browser dùng `AbortController` để hủy `fetch` khi kết quả không còn cần thiết. Nhưng vấn đề sâu hơn là **response ordering**: request cũ có thể hoàn thành sau request mới và ghi đè state mới.

## 2. Why does it exist?

Autocomplete/search UI phát request khi input thay đổi nhanh. Network latency không đảm bảo thứ tự completion. Nếu UI chỉ `await` rồi assign state, stale response có thể thắng race.

## 3. How does it work?

```text
query A ----slow----------> response A
query B ------> response B
                state=B
                       response A -> stale overwrite
```

Abort request A khi B bắt đầu giảm wasted work và ngăn nhiều stale completions; UI vẫn nên có request identity/version guard nếu cancellation không thể đảm bảo server đã dừng.

## 4. Practical implementation

```ts
let controller: AbortController | undefined;
let requestVersion = 0;

async function search(query: string) {
  controller?.abort();
  controller = new AbortController();
  const version = ++requestVersion;

  try {
    const response = await fetch(`/api/search?q=${encodeURIComponent(query)}`, {
      signal: controller.signal
    });
    const data = await response.json();

    if (version === requestVersion) {
      results.value = data;
    }
  } catch (error) {
    if ((error as DOMException).name !== "AbortError") throw error;
  }
}
```

## 5. Real production scenario

User gõ `car`, rồi nhanh chóng `cargo`. Request `car` gặp cache miss nên chậm; `cargo` hit cache và trả trước. Không có ordering guard, UI cuối cùng hiển thị kết quả `car` dù textbox đang là `cargo`.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị kết quả không khớp input hiện tại.  
**Evidence** → DevTools Network cho thấy responses hoàn thành khác thứ tự request.  
**Hypothesis** → stale response race.  
**Diagnosis** → log request version/query tại state mutation.  
**Fix** → abort previous request và/or version guard.  
**Verification** → network throttling test với typing nhanh.

## 7. Common mistakes

Debounce rồi cho rằng race đã biến mất; hiển thị `AbortError` như lỗi cho user; nghĩ browser abort đảm bảo server rollback; dùng một global controller cho unrelated requests.

## 8. Alternatives

Debounce giảm số requests nhưng không đảm bảo ordering. Libraries như TanStack Query cung cấp query lifecycle/caching. Sequence/version guard là deterministic protection cho state mutation.

## 9. Trade-offs

### Advantages

Giảm wasted network work, stale UI và unnecessary rendering.

### Costs / Risks

Thêm lifecycle state; cancellation không đảo ngược server-side side effects đã xảy ra.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async responses có thể về sai thứ tự.

### Middle

Dùng `AbortController`, debounce và error handling đúng.

### Senior

Phân biệt cancellation với ordering/correctness và server-side side effects.

### Technical Lead / Architect

Thiết kế API/UI contracts để read requests cancellable, mutations idempotent và frontend state transitions deterministic.

## 11. Key takeaway

- Debounce giảm traffic; nó không đảm bảo response ordering.
- Abort giúp efficiency, version guard bảo vệ state correctness.
- Client cancellation không có nghĩa server-side work chắc chắn chưa xảy ra.
