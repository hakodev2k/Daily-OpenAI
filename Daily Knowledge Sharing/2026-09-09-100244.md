# 1. .NET Garbage Collector latency modes: giảm pause đúng workload thay vì “tuning GC” theo cảm tính

## 1. What is it?

.NET Garbage Collector quản lý heap của managed objects và tự động reclaim memory không còn reachable. GC latency mode là cách runtime cân bằng giữa hai mục tiêu thường xung đột:

* giảm thời gian pause của application;
* thu hồi memory đủ mạnh để giữ heap khỏe.

Mental model:

```text
Application allocates
      ↓
Managed heap grows
      ↓
GC decides collection scope
      ↓
mark / compact / reclaim
      ↓
application resumes
```

Không có “GC mode nhanh nhất” cho mọi hệ thống. Một low-latency API và một background batch processor có yêu cầu khác nhau.

## 2. Why does it exist?

GC phải dừng hoặc phối hợp với managed threads ở một số phase. Nếu application giữ nhiều live objects, tạo allocation rate cao hoặc để heap fragment, collection có thể gây latency spikes.

Trong API có SLO p99 chặt, pause 150–300 ms có thể gây timeout chain dù average latency vẫn đẹp. Ngược lại, batch job có thể chấp nhận pause dài hơn nếu throughput tổng cao hơn.

Vì vậy runtime cần cơ chế điều chỉnh trade-off giữa latency và collection aggressiveness.

## 3. How does it work?

.NET có Server GC và Workstation GC. Server GC thường dùng nhiều heaps/GC threads để tối ưu throughput trên server multi-core; Workstation GC phù hợp interactive/desktop workload hơn.

Runtime cũng hỗ trợ latency modes như:

* `Interactive`
* `LowLatency`
* `SustainedLowLatency`
* `Batch`

Ví dụ:

```csharp
var previous = GCSettings.LatencyMode;

try
{
    GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency;
    await ProcessLatencySensitiveWindowAsync();
}
finally
{
    GCSettings.LatencyMode = previous;
}
```

Điểm quan trọng: latency mode không xóa nhu cầu GC. Nếu memory pressure đủ cao, runtime vẫn phải collect.

## 4. Practical implementation

Bắt đầu bằng measurement, không bắt đầu bằng config.

Ví dụ dùng `dotnet-counters`:

```bash
dotnet-counters monitor \
  --counters System.Runtime \
  --process-id <PID>
```

Quan sát:

* allocation rate;
* Gen 0 / Gen 1 / Gen 2 collections;
* LOH size;
* GC pause time;
* heap size;
* thread pool counters.

Nếu endpoint hot path tạo quá nhiều temporary objects, sửa allocation pattern thường hiệu quả hơn thay latency mode.

Ví dụ projection tránh intermediate collections:

```csharp
var result = source
    .Where(x => x.IsActive)
    .Select(x => new ItemDto(x.Id, x.Name))
    .ToArray();
```

Sau đó profile để xem optimization có thật sự giảm pressure hay chỉ chuyển complexity sang code.

## 5. Real production scenario

Một ASP.NET Core pricing service có p50 ~25 ms nhưng p99 thỉnh thoảng lên 700 ms. CPU trung bình 45%, database bình thường.

Telemetry cho thấy mỗi spike latency trùng Gen 2 collection. Root cause không phải “GC chậm”, mà là request pipeline deserialize payload lớn, tạo nhiều temporary collections và giữ vài object graph sống lâu hơn dự kiến.

Team ban đầu muốn bật low-latency mode toàn process. Sau profiling, họ giảm allocations và lifetime trước; p99 cải thiện mà không cần ép GC vào mode rủi ro hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → latency spike định kỳ, CPU không nhất thiết cao.

**Evidence** → spikes tương quan với Gen 2/LOH collections hoặc GC pause metrics.

**Hypothesis** → allocation/liveness pattern tạo GC pressure.

**Diagnosis** → dùng `dotnet-counters`, `dotnet-gcdump`, profiler; xác định loại object nào chiếm heap và allocation rate.

**Fix** → giảm allocation, giảm object lifetime, tránh giữ cache/reference không cần thiết; chỉ tune latency mode sau khi hiểu workload.

**Verification** → load test lại và so sánh p95/p99, allocation rate, GC pause percentage.

## 7. Common mistakes

* Gọi `GC.Collect()` định kỳ để “dọn memory”.
* Chọn low-latency mode cho toàn application mà không đo.
* Chỉ nhìn heap size mà không nhìn live set và allocation rate.
* Nghĩ Server GC luôn tốt hơn cho mọi process.
* Tối ưu micro-allocation ở cold path trong khi hot path vẫn tạo object graph lớn.

## 8. Alternatives

Trước khi tune GC, thường nên xem:

* pooling cho buffer thật sự hot;
* streaming thay vì materialize payload lớn;
* giảm retention trong caches;
* background processing thay vì giữ request state lâu;
* native/unmanaged memory chỉ khi có lý do rất rõ.

## 9. Trade-offs

### Advantages

* GC tuning đúng workload có thể giảm tail latency.
* Server GC có thể tăng throughput đáng kể trên multi-core server.
* Latency modes hữu ích cho time-sensitive windows.

### Costs / Risks

* Low-latency mode có thể làm heap tăng.
* Tuning sai che root cause allocation.
* Càng can thiệp runtime càng tăng operational complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu GC không “xóa object sau khi ra khỏi scope”; nó reclaim object không còn reachable theo collection cycles.

### Middle

Biết đọc basic GC counters, phân biệt Gen 0/1/2, LOH và allocation rate.

### Senior

Chẩn đoán tail latency do GC, phân tích live set, allocation hot path và memory retention.

### Technical Lead / Architect

Quyết định có cần runtime tuning không hay nên sửa data flow/object lifetime; đặt performance budget dựa trên p95/p99 thay vì cảm giác.

## 11. Key takeaway

* GC tuning chỉ nên đến sau measurement.
* Tail latency thường liên quan allocation/liveness pattern hơn là “GC bug”.
* Giảm allocations và object lifetime thường an toàn hơn ép runtime bằng manual collection hoặc aggressive latency mode.

# 2. ASP.NET Core graceful shutdown: request draining, `CancellationToken` và shutdown budget trong production

## 1. What is it?

Graceful shutdown là quá trình application ngừng nhận work mới, cho work đang chạy cơ hội hoàn tất trong giới hạn thời gian, rồi thoát process có kiểm soát.

Mental model:

```text
SIGTERM / App Service recycle / Pod termination
                ↓
stop accepting new work
                ↓
finish or cancel in-flight work
                ↓
flush critical state / close resources
                ↓
process exits
```

Nó khác với “process bị kill”. Trong production, distinction này quyết định request có bị cắt giữa chừng hay background message có bị xử lý dở dang hay không.

## 2. Why does it exist?

Deploy, scale-in, host maintenance và container orchestration đều có thể terminate process bình thường. Nếu application không xử lý shutdown đúng:

* HTTP requests đang chạy bị reset;
* message consumer commit side effect nhưng chưa settle message;
* file processing để lại partial output;
* buffered telemetry chưa flush;
* background loops tiếp tục work cho tới khi host kill cứng.

Graceful shutdown tạo một budget hữu hạn để application đóng đúng boundary.

## 3. How does it work?

ASP.NET Core Generic Host phát cancellation qua `IHostApplicationLifetime.ApplicationStopping` và truyền token vào `BackgroundService.ExecuteAsync`.

Ví dụ:

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var message = await ReceiveAsync(stoppingToken);
            await ProcessAsync(message, stoppingToken);
        }
    }
}
```

Khi host dừng, `stoppingToken` được cancel. Worker phải tôn trọng token và kết thúc ở safe point.

## 4. Practical implementation

Cấu hình shutdown timeout có chủ đích:

```csharp
builder.Services.Configure<HostOptions>(options =>
{
    options.ShutdownTimeout = TimeSpan.FromSeconds(30);
});
```

Background work không nên bắt đầu operation dài 5 phút khi shutdown đã bắt đầu:

```csharp
if (stoppingToken.IsCancellationRequested)
    return;

await ProcessBatchAsync(stoppingToken);
```

Với HTTP request, propagate `HttpContext.RequestAborted` xuống DB/HTTP dependencies để work có thể dừng khi connection không còn hữu ích.

## 5. Real production scenario

Một App Service chạy worker đọc Azure Service Bus. Trong deployment, instance recycle. Worker đang xử lý invoice export mất 90 giây, nhưng host shutdown budget chỉ 30 giây.

Sau 30 giây process bị terminate. Message lock hết hạn và message được delivery lại. Nếu export không idempotent, hệ thống có thể tạo hai files hoặc gửi hai notifications.

Root problem không chỉ là shutdown timeout; operation boundary dài hơn host lifecycle budget và không có idempotency.

## 6. Failure scenario & troubleshooting

**Symptom** → 5xx/reset tăng đúng lúc deployment/scale-in; background jobs chạy duplicate sau restart.

**Evidence** → logs có shutdown event ngay trước incomplete operations; message redelivery tăng.

**Hypothesis** → work không hoàn thành trong termination budget hoặc ignore cancellation.

**Diagnosis** → đo duration của in-flight operations, host shutdown timeout, platform termination grace period.

**Fix** → giảm work unit size, propagate cancellation, checkpoint/idempotency, không nhận work mới khi stopping.

**Verification** → terminate instance có chủ đích trong staging và kiểm tra request drain/message recovery.

## 7. Common mistakes

* `catch (Exception)` rồi swallow `OperationCanceledException` như lỗi bình thường.
* Background loop dùng `CancellationToken.None`.
* Shutdown timeout lớn vô hạn thay vì chia nhỏ operation.
* Flush toàn bộ cache/state sync trong shutdown path làm vượt budget.
* Giả định deployment luôn chờ request tới khi xong.

## 8. Alternatives

Long-running workloads có thể phù hợp hơn với:

* queue + idempotent consumer;
* Durable Functions/workflow engine;
* resumable job checkpointing;
* separate Worker Service thay vì chạy trong web process.

## 9. Trade-offs

### Advantages

* Giảm request reset trong deployment.
* Cho background work đóng boundary an toàn.
* Tăng release reliability.

### Costs / Risks

* Shutdown budget dài làm scale-in/release chậm.
* Work unit lớn vẫn có thể bị kill cứng.
* Cần idempotency vì graceful shutdown không bao giờ đảm bảo 100% completion.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu application có lifecycle và shutdown không đồng nghĩa `Environment.Exit()`.

### Middle

Propagate stopping token, xử lý `BackgroundService` và request cancellation đúng.

### Senior

Thiết kế work unit có checkpoint/idempotency và kiểm tra behavior khi process terminate giữa operation.

### Technical Lead / Architect

Đặt shutdown budget phù hợp platform và quyết định workload nào không nên sống trong web process.

## 11. Key takeaway

* Graceful shutdown là bounded opportunity, không phải completion guarantee.
* Long-running side effects vẫn cần idempotency/checkpoint.
* Deployment reliability phụ thuộc application lifecycle semantics, không chỉ CI/CD pipeline.

# 3. EF Core `ExecuteUpdate` / `ExecuteDelete`: bulk mutation nhanh nhưng bypass Change Tracker và domain behavior

## 1. What is it?

`ExecuteUpdate` và `ExecuteDelete` cho phép EF Core phát lệnh `UPDATE` / `DELETE` trực tiếp từ LINQ query mà không load entities vào memory và không đi qua normal Change Tracker flow.

Mental model:

```text
Traditional EF update
query rows → materialize entities → track → modify → SaveChanges

ExecuteUpdate
LINQ predicate → SQL UPDATE directly
```

Đây là set-based database mutation, không phải shortcut cho mọi domain update.

## 2. Why does it exist?

Nếu cần archive 200.000 rows, load từng entity chỉ để đổi một field là lãng phí:

* memory tăng;
* change tracking cost cao;
* nhiều entity materialization;
* có thể phát nhiều statements/batches.

Database vốn tối ưu cho set-based operations, nên EF Core cung cấp API để dùng khả năng đó mà không rơi về raw SQL trong mọi trường hợp.

## 3. How does it work?

Ví dụ:

```csharp
await db.Orders
    .Where(x => x.CreatedAt < cutoff && x.Status == OrderStatus.Completed)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.IsArchived, true)
        .SetProperty(x => x.ArchivedAt, now),
        cancellationToken);
```

EF translate thành một `UPDATE ... WHERE ...` trực tiếp.

Điểm quan trọng: tracked entity instances trong current `DbContext` không tự đồng bộ lại với database state mới.

## 4. Practical implementation

Với bulk delete:

```csharp
var deleted = await db.AuditLogs
    .Where(x => x.CreatedAt < cutoff)
    .ExecuteDeleteAsync(cancellationToken);
```

Sau đó cần cân nhắc transaction boundary nếu bulk mutation đi cùng writes khác:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

await db.Orders
    .Where(x => x.BatchId == batchId)
    .ExecuteUpdateAsync(
        x => x.SetProperty(o => o.Status, OrderStatus.Processed), ct);

await db.BatchRuns
    .Where(x => x.Id == batchId)
    .ExecuteUpdateAsync(
        x => x.SetProperty(b => b.CompletedAt, DateTimeOffset.UtcNow), ct);

await tx.CommitAsync(ct);
```

## 5. Real production scenario

Nightly retention job cần mark hàng triệu notification records là expired. Version cũ load entities theo pages, thay đổi property rồi `SaveChanges`.

Job mất hàng giờ và tạo memory pressure. `ExecuteUpdate` giảm round trips và tracking overhead rõ rệt.

Nhưng team phát hiện domain event `NotificationExpired` không còn được raise vì business behavior trước đây nằm trong entity method. Bulk SQL đã bypass nó.

## 6. Failure scenario & troubleshooting

**Symptom** → database state đúng nhưng downstream event/audit không xuất hiện.

**Evidence** → code chuyển từ entity method + `SaveChanges` sang `ExecuteUpdate`.

**Hypothesis** → domain side effects nằm trong tracked entity flow bị bypass.

**Diagnosis** → trace application behavior trước/sau; kiểm tra interceptors/domain event dispatch/audit hooks.

**Fix** → chỉ dùng set-based mutation khi business semantics cho phép; nếu cần event, thiết kế explicit batch event/outbox path.

**Verification** → integration test cả database mutation và expected side effects.

## 7. Common mistakes

* Dùng bulk mutation cho aggregate có invariants phức tạp.
* Nghĩ Change Tracker sẽ biết database vừa đổi.
* Quên transaction khi nhiều bulk statements phải atomic.
* Chạy huge update một lần gây lock escalation/log growth.
* Dùng `ExecuteDelete` thay retention design có audit/legal requirements.

## 8. Alternatives

* Normal tracked entities: tốt khi cần domain behavior/concurrency per aggregate.
* Raw SQL/stored procedure: phù hợp database-specific logic hoặc extreme tuning.
* Bulk library: hữu ích cho import/update patterns phức tạp nhưng thêm dependency.
* Background batch với chunking: giảm lock/log pressure.

## 9. Trade-offs

### Advantages

* Giảm materialization và tracking overhead.
* Ít round trips hơn.
* Tận dụng set-based SQL.

### Costs / Risks

* Bypass entity behavior/interceptors dựa trên Change Tracker.
* Tracked state có thể stale.
* Bulk writes có lock/log impact lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu EF có hai kiểu path: tracked entity flow và direct set-based mutation.

### Middle

Biết dùng `ExecuteUpdate`/`ExecuteDelete`, transaction và kiểm tra generated SQL.

### Senior

Đánh giá lock behavior, stale tracked state, concurrency và domain side effects.

### Technical Lead / Architect

Quyết định boundary nào cho phép set-based mutation và boundary nào bắt buộc aggregate invariants/domain events.

## 11. Key takeaway

* `ExecuteUpdate` nhanh vì bỏ qua materialization/tracking, nhưng chính điều đó cũng bỏ qua behavior gắn với tracking.
* Set-based mutation là persistence optimization, không phải domain-model replacement.
* Đo lock/log impact khi update số lượng rows lớn.

# 4. Redis cache stampede: single-flight, TTL jitter và stale-while-revalidate để tránh database bị đánh sập

## 1. What is it?

Cache stampede xảy ra khi nhiều requests cùng miss hoặc cùng thấy một hot key vừa hết hạn, rồi tất cả đồng thời gọi database/upstream để rebuild cùng dữ liệu.

Mental model:

```text
hot key expires
   ↓
1000 concurrent requests
   ↓
1000 cache misses
   ↓
1000 DB queries
   ↓
DB overload
```

Cache được thêm để giảm load nhưng expiry đồng bộ có thể vô tình biến cache thành load multiplier.

## 2. Why does it exist?

TTL là cơ chế đơn giản để freshness tự hết hạn. Nhưng với hot data, thời điểm expiry trở thành một synchronized event.

Nếu request rate cao hơn khả năng backend rebuild value, thundering herd có thể tạo cascading failure: Redis miss → DB saturation → API timeout → retries → load tăng thêm.

## 3. How does it work?

Ba kỹ thuật phổ biến:

1. **single-flight / request coalescing**: chỉ một caller rebuild key, callers khác chờ cùng result;
2. **TTL jitter**: thêm random offset để nhiều keys không expire cùng lúc;
3. **stale-while-revalidate**: tạm phục vụ dữ liệu hơi stale trong khi một worker refresh.

Single-flight per key:

```text
miss key=A
  ↓
acquire refresh ownership
  ↓
one owner? wait
owner? rebuild once
```

## 4. Practical implementation

Một single-process single-flight đơn giản:

```csharp
private readonly ConcurrentDictionary<string, SemaphoreSlim> _locks = new();

public async Task<T> GetOrCreateAsync<T>(
    string key,
    Func<CancellationToken, Task<T>> factory,
    CancellationToken ct)
{
    var cached = await _cache.GetAsync<T>(key, ct);
    if (cached is not null)
        return cached;

    var gate = _locks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
    await gate.WaitAsync(ct);

    try
    {
        cached = await _cache.GetAsync<T>(key, ct);
        if (cached is not null)
            return cached;

        var value = await factory(ct);
        var ttl = TimeSpan.FromMinutes(5)
                  + TimeSpan.FromSeconds(Random.Shared.Next(0, 30));

        await _cache.SetAsync(key, value, ttl, ct);
        return value;
    }
    finally
    {
        gate.Release();
    }
}
```

Trong multi-instance system, local semaphore chỉ coalesce trong một instance; vẫn cần strategy phù hợp distributed topology.

## 5. Real production scenario

Product detail endpoint có một hot SKU xuất hiện trên homepage. Cache TTL 5 phút. Mỗi lần key expire, hàng nghìn requests cùng query pricing DB.

Database CPU spike đúng chu kỳ 5 phút, p99 tăng và autoscaling app không giúp vì bottleneck nằm ở database.

Single-flight + TTL jitter + short stale serving window loại bỏ spike đồng bộ.

## 6. Failure scenario & troubleshooting

**Symptom** → DB load spike theo chu kỳ TTL dù average traffic ổn định.

**Evidence** → cache miss ratio tăng đột ngột cùng thời điểm; nhiều identical queries.

**Hypothesis** → hot-key stampede.

**Diagnosis** → correlate cache misses theo key với DB query volume.

**Fix** → coalesce refresh, jitter TTL, pre-warm hoặc stale-while-revalidate.

**Verification** → load test tại thời điểm forced expiry và xác nhận backend chỉ rebuild giới hạn lần.

## 7. Common mistakes

* Distributed lock cho mọi cache key dù load thấp, tăng complexity không cần thiết.
* TTL giống hệt nhau cho hàng nghìn keys được tạo cùng batch.
* Chờ lock nhưng không re-check cache sau khi lấy lock.
* Cache failure làm request fail dù database vẫn khỏe.
* Không giới hạn refresh duration khiến lock owner treo.

## 8. Alternatives

* CDN/edge cache cho public content.
* IMemoryCache cho per-instance read-mostly data.
* Precomputation/materialized view nếu rebuild quá đắt.
* Không cache nếu database query đã đủ nhanh và traffic thấp.

## 9. Trade-offs

### Advantages

* Giảm synchronized backend load.
* Tail latency ổn định hơn.
* Stale-while-revalidate giúp availability cao hơn.

### Costs / Risks

* Single-flight có coordination cost.
* Stale data cần business tolerance rõ.
* Distributed coordination có thể biến Redis thành critical dependency hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss không chỉ ảnh hưởng latency; nhiều miss đồng thời có thể đánh backend.

### Middle

Implement double-check + single-flight + TTL jitter.

### Senior

Đánh giá hot-key pattern, stale tolerance, failure fallback và multi-instance behavior.

### Technical Lead / Architect

Quyết định dữ liệu nào đáng cache, freshness contract là gì và cache có đang trở thành hidden system dependency hay không.

## 11. Key takeaway

* Cache expiry là một traffic event, không chỉ timestamp.
* Hot keys cần refresh coordination hoặc stale strategy.
* Cache nên giảm blast radius, không tạo thêm một blast radius mới.

# 5. Modular Monolith boundaries: giữ module độc lập trong một deployable unit mà không biến codebase thành distributed monolith nội bộ

## 1. What is it?

Modular Monolith là một application deploy như một unit nhưng được chia thành các modules có boundary rõ về business responsibility, dependencies và data ownership.

Mental model:

```text
Single deployable application
┌───────────────────────────────┐
│ Orders │ Billing │ Identity   │
│   ↓         ↓         ↓       │
│ explicit module contracts     │
└───────────────────────────────┘
```

Điểm cốt lõi không phải folder `Modules/`. Boundary phải được enforce trong code và dữ liệu.

## 2. Why does it exist?

Layered monolith lớn thường bị coupling ngang:

* module A query trực tiếp table của B;
* service nào cũng inject repository nào cũng được;
* shared project chứa mọi DTO/entity;
* thay một feature gây regression khắp solution.

Microservices giải quyết một số boundary bằng process/network, nhưng mang theo deployment, observability và distributed failure complexity.

Modular Monolith tìm cách có business boundaries trước khi trả operational cost của microservices.

## 3. How does it work?

Mỗi module nên có:

* public contract/API nội bộ;
* application/domain riêng;
* persistence ownership rõ;
* dependency rules một chiều;
* integration thông qua explicit commands/events/contracts.

Ví dụ:

```text
Orders module
  owns Orders tables
  exposes IOrderQueries / commands

Billing module
  does NOT query Orders tables directly
  consumes OrderCompleted event or module contract
```

Có thể dùng cùng database server nhưng nên tránh cross-module table access tùy tiện.

## 4. Practical implementation

Structure ví dụ:

```text
src/
  Modules/
    Orders/
      Orders.Api/
      Orders.Application/
      Orders.Domain/
      Orders.Infrastructure/
    Billing/
      Billing.Api/
      Billing.Application/
      Billing.Domain/
      Billing.Infrastructure/
  Host/
```

Một contract hẹp:

```csharp
public interface IOrderStatusReader
{
    Task<OrderStatusDto?> GetAsync(
        Guid orderId,
        CancellationToken cancellationToken);
}
```

Không expose `DbContext`, entity hoặc internal repository qua boundary.

## 5. Real production scenario

Một SaaS bắt đầu với Orders, Billing, Notifications trong một ASP.NET Core application. Nếu team chia microservices từ đầu, mỗi feature cần service discovery, messaging, tracing, deployment pipelines và failure handling.

Họ giữ một deployable unit nhưng enforce module ownership. Sau hai năm, Billing có scale/release needs riêng; boundary đã rõ nên extraction sang service dễ hơn đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → project được gọi “modular” nhưng mọi module reference Infrastructure/Common và query cùng tables.

**Evidence** → dependency graph dense; cross-module entity/repository usage.

**Hypothesis** → modules chỉ là folders, boundary không enforce.

**Diagnosis** → dependency analysis + search direct schema/table access.

**Fix** → contract rõ, ownership rõ, architecture tests chặn forbidden dependencies.

**Verification** → build-time test fail nếu module A reference internals của B.

## 7. Common mistakes

* `SharedKernel` phình thành nơi chứa mọi thứ.
* Dùng cùng entity classes cho nhiều modules.
* Mỗi module có layer riêng nhưng vẫn cross-query database.
* Tạo internal event bus phức tạp như Kafka dù process vẫn đơn.
* Thiết kế module theo technical layer thay vì business capability.

## 8. Alternatives

* Simple layered monolith: tốt khi domain nhỏ/team nhỏ.
* Microservices: phù hợp khi ownership, scaling hoặc deployment independence thực sự cần.
* Service-based architecture: vài coarse-grained services thay vì nhiều microservices nhỏ.

## 9. Trade-offs

### Advantages

* Giữ deployment/operations đơn giản.
* Boundary tốt giúp maintainability và future extraction.
* Transaction local vẫn dễ hơn distributed transaction.

### Costs / Risks

* Boundary phải enforce bằng discipline/tests.
* Shared database dễ tạo temptation cross-module access.
* Một deployable vẫn có coordinated release và shared runtime blast radius.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business boundary, không chỉ namespace.

### Middle

Implement module contract và tránh reference internals.

### Senior

Thiết kế data ownership, transaction boundary và communication giữa modules.

### Technical Lead / Architect

Quyết định khi nào modular monolith đủ tốt và tiêu chí thực tế nào justify extraction sang service riêng.

## 11. Key takeaway

* Boundary chất lượng quan trọng hơn số lượng services.
* Modular Monolith tốt khi cần structure nhưng chưa cần distributed operations.
* Data ownership và dependency enforcement quyết định architecture có thật hay chỉ là folder layout.

# 6. Webhook security + idempotency: signature verification, replay protection và duplicate delivery từ third-party systems

## 1. What is it?

Webhook là HTTP callback từ external system vào application của bạn. Vì endpoint công khai trên internet và sender có thể retry, webhook handler cần giải quyết đồng thời:

* authenticity: request có thật từ provider không?
* integrity: payload có bị sửa không?
* replay: request cũ có bị gửi lại maliciously không?
* duplicate delivery: provider retry cùng event hợp lệ nhiều lần.

Mental model:

```text
Provider
  ↓ signed request
Webhook endpoint
  ↓ verify signature + timestamp
Deduplicate event
  ↓
Persist / enqueue
  ↓
Process idempotently
```

## 2. Why does it exist?

Chỉ dùng secret query string hoặc IP allowlist thường không đủ. Proxy/CDN có thể làm IP model phức tạp; secret URL có thể leak trong logs.

Ngoài ra, webhook delivery gần như luôn theo at-least-once semantics. Provider không nhận được 2xx do network timeout có thể retry dù application đã xử lý thành công.

## 3. How does it work?

Nhiều providers ký HMAC trên raw request body + timestamp.

Ví dụ conceptual:

```text
signature = HMAC_SHA256(secret, timestamp + "." + rawBody)
```

Server:

1. đọc raw bytes;
2. kiểm tra timestamp nằm trong tolerance window;
3. recompute HMAC;
4. constant-time compare;
5. dùng provider event ID làm deduplication key.

## 4. Practical implementation

```csharp
static bool VerifySignature(
    string secret,
    string timestamp,
    ReadOnlySpan<byte> body,
    string providedHex)
{
    var prefix = Encoding.UTF8.GetBytes(timestamp + ".");
    var payload = new byte[prefix.Length + body.Length];

    prefix.CopyTo(payload, 0);
    body.CopyTo(payload.AsSpan(prefix.Length));

    using var hmac = new HMACSHA256(Encoding.UTF8.GetBytes(secret));
    var computed = hmac.ComputeHash(payload);
    var provided = Convert.FromHexString(providedHex);

    return CryptographicOperations.FixedTimeEquals(
        computed,
        provided);
}
```

Deduplicate event bằng unique constraint:

```sql
CREATE UNIQUE INDEX UX_WebhookInbox_Provider_EventId
ON WebhookInbox(Provider, EventId);
```

Persist inbox record trước khi asynchronous processing.

## 5. Real production scenario

Payment provider gửi `payment.succeeded`. Application commit order state nhưng response 200 bị mất trên network. Provider retry sau 30 giây.

Nếu handler gọi shipping/payment side effect trực tiếp mà không deduplicate, order có thể được fulfilled hai lần.

Nếu chỉ dedup in-memory, restart giữa hai retries làm protection biến mất.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate emails/shipments dù provider event IDs giống nhau.

**Evidence** → logs cho thấy cùng event được nhận nhiều lần.

**Hypothesis** → handler không idempotent hoặc dedup state không durable.

**Diagnosis** → trace event ID từ ingress tới side effect; kiểm tra unique constraint/inbox table.

**Fix** → durable inbox + idempotent processor; trả 2xx khi duplicate đã được chấp nhận trước đó.

**Verification** → replay cùng signed event nhiều lần và xác nhận side effect chỉ xảy ra một lần.

## 7. Common mistakes

* Parse JSON rồi mới verify signature khi provider ký raw body.
* String compare signature thông thường thay constant-time compare.
* Không kiểm tra timestamp/replay window.
* Dùng request body hash nhưng không có event identity.
* Thực hiện business side effect trước khi durable dedup state được ghi.

## 8. Alternatives

* Polling API: đơn giản trust boundary hơn nhưng latency/cost cao hơn.
* Message broker integration: tốt khi partner hỗ trợ private messaging.
* API callback qua mTLS: stronger transport identity nhưng vẫn cần idempotency.

## 9. Trade-offs

### Advantages

* Webhook giảm polling và latency.
* Signature verification cung cấp sender authenticity/integrity.
* Durable idempotency làm retries an toàn.

### Costs / Risks

* Provider-specific signature scheme.
* Secret rotation cần quản lý.
* Replay/dedup storage thêm complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu webhook là inbound untrusted request dù URL chỉ provider biết.

### Middle

Verify HMAC/timestamp và dùng event ID dedup.

### Senior

Thiết kế inbox, idempotent side effects, secret rotation và retry semantics.

### Technical Lead / Architect

Đặt standard cho third-party ingress: trust model, signature, replay window, observability và ownership khi provider behavior thay đổi.

## 11. Key takeaway

* Signature verification và idempotency giải quyết hai vấn đề khác nhau; cần cả hai.
* Verify raw payload theo đúng provider contract.
* At-least-once delivery phải được coi là normal behavior, không phải rare edge case.

# 7. Azure App Service deployment slots: warm-up, slot settings và swap strategy để giảm release risk

## 1. What is it?

Deployment slot là một live App Service environment nằm cạnh production slot. Bạn có thể deploy version mới vào staging slot, warm/test nó, rồi swap routing/configuration để đưa version đó lên production.

Mental model:

```text
Build artifact
   ↓
Staging slot
   ↓ warm + validate
Swap
   ↓
Production traffic → new version
```

Slots không tự làm deployment zero-risk; chúng chỉ cung cấp primitive để tách deploy khỏi traffic cutover.

## 2. Why does it exist?

Deploy trực tiếp lên production có thể gây:

* cold start;
* incomplete startup;
* config mismatch;
* application lỗi ngay khi traffic tới;
* rollback chậm nếu artifact mới replace version cũ.

Slot cho phép version mới sống và được kiểm tra trước khi nhận production traffic.

## 3. How does it work?

Một số settings có thể được đánh dấu **Deployment slot setting** để “stick” với slot thay vì swap cùng application.

Ví dụ staging có connection string khác hoặc feature flag chỉ staging.

Swap thay đổi slot content/config theo Azure semantics; application trong target slot có thể được warm trước khi routing hoàn tất.

Điểm quan trọng: database/shared dependencies thường vẫn là external state, không được “swap”.

## 4. Practical implementation

Một release flow:

```text
1. Deploy artifact to staging slot
2. Run health endpoint
3. Run smoke/integration checks
4. Verify telemetry
5. Swap staging → production
6. Observe production SLI
7. Swap back if regression
```

Health endpoint nên kiểm tra startup readiness nhưng không chạy expensive business workload.

Feature/configuration cần phân biệt slot-specific:

```text
APP_ENV=Staging               # slot-sticky
ConnectionStrings__Main=...   # tùy strategy
Feature__NewCheckout=true     # có thể slot-sticky
```

## 5. Real production scenario

ASP.NET Core app mất 40 giây warm JIT/cache/config. Deploy trực tiếp làm 503 tăng mỗi release.

Team dùng staging slot, gọi warm-up endpoints và kiểm tra Application Insights trước swap. 503 cold-start gần như biến mất.

Sau đó một release vẫn fail vì migration DB breaking được chạy trước swap, làm version production cũ không còn compatible. Slot không giải quyết database backward compatibility.

## 6. Failure scenario & troubleshooting

**Symptom** → swap thành công nhưng production trả 500 ngay lập tức.

**Evidence** → app health ở staging xanh nhưng production dependencies/config khác.

**Hypothesis** → slot-specific config hoặc database/network boundary khác.

**Diagnosis** → compare app settings, Managed Identity permissions, Private Endpoint/DNS, connection strings, health traces.

**Fix** → mark correct settings sticky, test production-equivalent dependencies, dùng expand/contract DB migration.

**Verification** → pre-swap validation + post-swap SLI monitoring.

## 7. Common mistakes

* Coi slot như full isolated environment trong khi DB vẫn shared.
* Không hiểu slot-sticky settings.
* Swap nhưng không warm application.
* Health check chỉ trả 200 hard-coded.
* Dùng slot swap để che breaking database migration.

## 8. Alternatives

* Blue-Green bằng hai App Services.
* Canary/traffic splitting khi cần progressive exposure.
* Container Apps/AKS rolling deployment cho containerized platform.
* Direct deployment khi app nhỏ và downtime chấp nhận được.

## 9. Trade-offs

### Advantages

* Tách artifact deploy khỏi traffic switch.
* Rollback nhanh bằng swap-back trong nhiều trường hợp.
* Giảm cold-start exposure.

### Costs / Risks

* Slot config management phức tạp.
* External state vẫn shared.
* Extra slot có cost/operational overhead tùy tier.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slot là live environment, không chỉ folder deploy.

### Middle

Deploy staging, configure sticky settings, health check và swap.

### Senior

Debug config/identity/network differences và database compatibility qua swap.

### Technical Lead / Architect

Chọn slot, Blue-Green hay Canary theo rollback need, blast radius, traffic control và platform cost.

## 11. Key takeaway

* Deployment slot giảm release risk nhưng không thay backward-compatible database design.
* Warm-up và health validation phải kiểm tra behavior thật.
* Config/identity/network differences giữa slots là nguồn lỗi production phổ biến.

# 8. OpenTelemetry trace sampling: head sampling, tail sampling và cách giữ lại traces quan trọng mà không đốt telemetry budget

## 1. What is it?

Trace sampling quyết định requests nào được giữ đầy đủ distributed trace thay vì lưu 100% traffic.

Hai strategy chính:

* **head sampling**: quyết định ngay đầu trace;
* **tail sampling**: quyết định sau khi đã quan sát đủ spans/outcome.

Mental model:

```text
Head:
request starts → sample? yes/no → trace continues

Tail:
request completes → inspect error/latency/attributes → keep/drop
```

## 2. Why does it exist?

Giữ 100% traces ở service hàng chục nghìn RPS có thể rất đắt. Nhưng sample quá mạnh lại dễ bỏ mất rare errors hoặc p99 outliers—chính những traces cần nhất khi incident xảy ra.

Sampling là bài toán cân bằng observability fidelity với ingestion/storage cost.

## 3. How does it work?

Head sampling thường deterministic theo trace ID và sampling probability, ví dụ 10%.

Ưu điểm: giảm telemetry volume sớm.

Nhược điểm: quyết định trước khi biết request có lỗi hay latency cao.

Tail sampling ở Collector có thể áp policy:

```text
keep if status=ERROR
OR duration > 2s
OR tenantTier=critical
OR random 5% baseline
```

Nhưng collector phải buffer trace đủ lâu để quyết định.

## 4. Practical implementation

Head sampling trong OpenTelemetry .NET:

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .SetSampler(new ParentBasedSampler(
            new TraceIdRatioBasedSampler(0.10)))
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation());
```

Tail sampling thường cấu hình ở OpenTelemetry Collector, ví dụ conceptual:

```yaml
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: errors
        type: status_code
        status_code:
          status_codes: [ERROR]
      - name: slow
        type: latency
        latency:
          threshold_ms: 2000
```

## 5. Real production scenario

Checkout API chạy 8.000 RPS. Team giữ 1% head sample để giảm bill. Rare payment timeout chỉ xảy ra 0.05% requests; incident xảy ra nhưng gần như không có failed traces để điều tra.

Họ chuyển sang baseline head sampling cao hơn ở critical path hoặc tail policy giữ toàn bộ error/slow traces. Telemetry cost vẫn bounded nhưng investigation coverage tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → metrics báo 500 errors nhưng trace search không thấy request lỗi.

**Evidence** → aggressive head sampler drop trước khi biết outcome.

**Hypothesis** → sampling policy không phù hợp incident-detection need.

**Diagnosis** → inspect sampler config, trace flags, collector drop counts.

**Fix** → tail sampling hoặc targeted sampling cho critical traffic/error/latency.

**Verification** → inject controlled failures và xác nhận trace được giữ theo policy.

## 7. Common mistakes

* 100% traces vô thời hạn rồi bất ngờ vì telemetry bill.
* 1% sample toàn hệ thống nhưng kỳ vọng giữ mọi error.
* Tail sampling mà collector memory không đủ.
* High-cardinality rules làm sampling policy phức tạp/đắt.
* Không propagate sampling decision qua service boundaries.

## 8. Alternatives

* Adaptive sampling của platform-specific agents.
* Logs + exemplars để drill down từ metrics.
* Dynamic sampling theo incident mode.
* Full tracing chỉ cho low-volume critical services.

## 9. Trade-offs

### Advantages

* Head sampling rẻ và đơn giản.
* Tail sampling giữ được interesting traces dựa trên outcome.
* Sampling có chủ đích giúp control observability cost.

### Costs / Risks

* Head sampling có thể mất rare failures.
* Tail sampling cần buffering/memory và collector reliability.
* Policy phức tạp có thể khó hiểu khi incident.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace sampling nghĩa là không phải request nào cũng được lưu đầy đủ.

### Middle

Cấu hình basic sampler và biết sampling propagation.

### Senior

Thiết kế policy giữ errors/slow traces, monitor collector drops và telemetry cost.

### Technical Lead / Architect

Đặt observability retention/sampling strategy theo SLO, incident needs và cost budget toàn platform.

## 11. Key takeaway

* Sampling policy phải bảo vệ diagnostic value, không chỉ giảm volume.
* Head sampling rẻ nhưng quyết định quá sớm để biết outcome.
* Tail sampling mạnh hơn nhưng chuyển complexity sang collector infrastructure.

# 9. Frontend stale-response race: khi hai API calls trả về sai thứ tự và UI hiển thị dữ liệu cũ

## 1. What is it?

Stale-response race xảy ra khi frontend phát nhiều asynchronous requests cho state thay đổi nhanh, nhưng responses quay về không theo thứ tự gửi.

Mental model:

```text
Search "car"      → Request A (slow)
Search "camera"   → Request B (fast)

B returns first → UI shows camera
A returns later → UI overwritten with car  ❌
```

Đây là race condition ở client-side state, không phải backend trả sai dữ liệu.

## 2. Why does it exist?

Network latency không deterministic. Typing search box, changing filters, switching routes hoặc rapidly selecting items có thể tạo concurrent requests.

Nếu component đơn giản “set state khi Promise resolve”, response cũ có thể thắng response mới.

## 3. How does it work?

Có ba common strategies:

* cancel previous request bằng `AbortController`;
* sequence/version token và chỉ apply latest response;
* library-level query state management có request identity.

Ví dụ sequence:

```text
requestVersion = 7
send query A(version=7)
requestVersion = 8
send query B(version=8)

A returns → 7 != current 8 → ignore
B returns → 8 == current 8 → apply
```

## 4. Practical implementation

TypeScript với `AbortController`:

```ts
let activeController: AbortController | null = null;

async function search(query: string) {
  activeController?.abort();
  activeController = new AbortController();

  try {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(query)}`,
      { signal: activeController.signal }
    );

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    const result = await response.json();
    render(result);
  } catch (error) {
    if ((error as DOMException).name === "AbortError") {
      return;
    }

    showError(error);
  }
}
```

Cancellation phía browser không đảm bảo backend rollback side effect; với read/search path nó chủ yếu bảo vệ UI/resource waste.

## 5. Real production scenario

Automotive marketplace có autocomplete. User nhập nhanh `to` → `toy` → `toyota`. Request `toy` gặp cache miss nên chậm, còn `toyota` cache hit trả trước.

UI hiển thị Toyota đúng trong 100 ms rồi bị response `toy` cũ overwrite. User thấy kết quả “nhảy ngược”.

## 6. Failure scenario & troubleshooting

**Symptom** → UI đôi lúc hiển thị kết quả của input trước đó.

**Evidence** → Network panel cho thấy requests hoàn tất out-of-order.

**Hypothesis** → component apply mọi response không kiểm tra request identity.

**Diagnosis** → log query + request sequence + response application time.

**Fix** → abort previous reads hoặc latest-only sequence guard.

**Verification** → throttle network trong DevTools và nhập/chuyển filter nhanh để ép out-of-order completion.

## 7. Common mistakes

* Debounce và nghĩ như vậy loại bỏ mọi race.
* Abort request nhưng vẫn update state trong generic `finally` sai cách.
* Ignore stale response cho GET nhưng apply cùng pattern mù quáng cho POST side effects.
* Component unmount nhưng Promise vẫn update state.
* Không phân biệt loading state theo request identity.

## 8. Alternatives

* React Query/TanStack Query hoặc Vue query libraries quản lý query identity/caching tốt hơn.
* Server-side autocomplete streaming cho use case đặc thù.
* Debounce/throttle giảm request volume nhưng không thay latest-response correctness.

## 9. Trade-offs

### Advantages

* Abort giảm wasted network/client work.
* Sequence guard rất đơn giản và deterministic.
* Query libraries giảm custom state complexity.

### Costs / Risks

* Cancellation support khác nhau theo transport/library.
* State management phức tạp hơn với concurrent UI workflows.
* Latest-wins không phù hợp mọi mutation semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async completion order không đảm bảo bằng request order.

### Middle

Implement abort/sequence guard và test với network throttling.

### Senior

Phân biệt read race với mutation consistency, loading/error state và browser lifecycle.

### Technical Lead / Architect

Đặt frontend data-fetching conventions, query library strategy và API semantics để client concurrency không tạo hidden correctness bugs.

## 11. Key takeaway

* Debounce giảm volume nhưng không đảm bảo response ordering.
* UI phải có rule rõ cho request nào được phép update state.
* Network races là production behavior bình thường, không phải edge case hiếm.

# 10. Architecture fitness functions: biến nguyên tắc kiến trúc thành checks tự động thay vì slide hoặc ADR chỉ để đọc

## 1. What is it?

Architecture fitness function là một kiểm tra có thể chạy tự động để xác nhận hệ thống vẫn giữ một thuộc tính kiến trúc quan trọng khi code thay đổi.

Ví dụ:

* Domain không reference Infrastructure;
* module Billing không access Orders persistence internals;
* public API không có breaking schema change ngoài policy;
* critical endpoint latency không vượt budget trong benchmark;
* container không chạy root.

Mental model:

```text
Architecture decision
       ↓
executable constraint
       ↓
CI check
       ↓
regression caught during change
```

## 2. Why does it exist?

Architecture thường degrade không phải vì team “quên kiến trúc”, mà vì từng thay đổi nhỏ hợp lý cục bộ tích tụ:

* thêm một reference tiện lợi;
* query table module khác “chỉ lần này”;
* expose DTO nội bộ;
* bypass validation để ship nhanh.

ADR và diagram giải thích intent nhưng không chặn regression. Fitness function biến một phần intent thành feedback tự động.

## 3. How does it work?

Không phải mọi architecture property đều test được. Nhưng nhiều dependency/boundary rules có thể kiểm tra bằng reflection/static analysis.

Ví dụ:

```text
Rule:
Orders.Domain must not depend on Orders.Infrastructure

CI:
architecture test scans assemblies
→ forbidden reference found
→ build fails
```

Performance/security rules cũng có thể là fitness functions nếu threshold và measurement đủ ổn định.

## 4. Practical implementation

Ví dụ conceptual với architecture test library:

```csharp
[Fact]
public void Domain_Should_Not_Depend_On_Infrastructure()
{
    var result = Types
        .InAssembly(typeof(Order).Assembly)
        .ShouldNot()
        .HaveDependencyOn("Orders.Infrastructure")
        .GetResult();

    Assert.True(result.IsSuccessful);
}
```

Hoặc module contract:

```csharp
[Fact]
public void Billing_Should_Not_Reference_Orders_Infrastructure()
{
    // scan Billing assemblies and fail on forbidden namespace/assembly reference
}
```

CI chạy tests như unit tests bình thường.

## 5. Real production scenario

Một modular monolith có rule: chỉ module API/contracts được cross-reference. Sau vài tháng, developer thêm reference từ Billing trực tiếp vào `OrdersDbContext` để làm report nhanh.

Code review bỏ sót vì thay đổi nhỏ. Architecture test fail ngay trong PR và chỉ ra forbidden dependency.

Boundary được bảo vệ trước khi coupling trở thành precedent.

## 6. Failure scenario & troubleshooting

**Symptom** → architecture tests fail liên tục và developers bắt đầu disable chúng.

**Evidence** → rules quá rộng, nhiều false positives hoặc không phản ánh current architecture.

**Hypothesis** → fitness function không actionable hoặc architecture decision đã thay đổi nhưng rule không cập nhật.

**Diagnosis** → review từng rule với owner/ADR; phân biệt drift thực với obsolete constraint.

**Fix** → giữ rules nhỏ, deterministic, business-relevant; update ADR + test cùng lúc nếu decision đổi.

**Verification** → intentional forbidden dependency phải fail; valid refactor không tạo noise.

## 7. Common mistakes

* Cố encode mọi kiến trúc decision thành test.
* Naming convention brittle nhưng coi như architecture guarantee.
* Test folder structure thay vì actual dependency/data ownership.
* Không có owner cho failing rule.
* Build fail do performance threshold flaky và cuối cùng mọi người bỏ qua.

## 8. Alternatives

* Code review + ADR: cần thiết nhưng manual.
* Static analyzers/custom Roslyn analyzers: mạnh cho code-level rules.
* Repository dependency graph checks.
* Runtime policy/authorization tests cho constraints chỉ xuất hiện khi chạy.

## 9. Trade-offs

### Advantages

* Feedback sớm trong CI.
* Boundary rules trở nên explicit.
* Giảm architecture drift do thay đổi nhỏ.

### Costs / Risks

* Rule maintenance có cost.
* Có thể tạo false confidence: test pass không nghĩa architecture tốt toàn diện.
* Quá nhiều constraints làm development chậm và architecture cứng nhắc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu architecture rule có thể được kiểm tra giống code rule.

### Middle

Viết dependency tests đơn giản và hiểu failure message.

### Senior

Chọn rules có signal cao, tránh brittle tests và nối chúng với actual boundaries.

### Technical Lead / Architect

Quyết định architecture qualities nào đáng tự động enforce, quality nào cần review/judgment, và khi nào rule phải evolve cùng system.

## 11. Key takeaway

* ADR giải thích quyết định; fitness function bảo vệ một phần quyết định khỏi regression.
* Chỉ automate constraints có signal cao và deterministic.
* Architecture governance tốt là feedback loop, không phải bộ luật bất biến.
