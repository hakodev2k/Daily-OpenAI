# 1. C# `IAsyncDisposable`: resource cleanup khi chính việc dispose cũng là asynchronous I/O

## 1. What is it?

`IAsyncDisposable` biểu diễn resource có cleanup path cần `await`. Mental model: `IDisposable` phù hợp cleanup synchronous; `IAsyncDisposable` tồn tại khi đóng/flush resource có thể cần I/O và ta không muốn block thread.

## 2. Why does it exist?

Một resource như asynchronous stream, database transaction hoặc network-backed writer có thể cần flush/close qua I/O. Ép cleanup đó chạy synchronously dễ dẫn tới blocking hoặc sync-over-async.

## 3. How does it work?

`await using` được compiler hạ thành `try/finally`; trong `finally`, runtime gọi `DisposeAsync()` và await `ValueTask` trả về. Cleanup vẫn xảy ra khi block thoát do exception.

## 4. Practical implementation

```csharp
await using var transaction =
    await db.Database.BeginTransactionAsync(ct);

await service.ApplyChangesAsync(ct);
await db.SaveChangesAsync(ct);
await transaction.CommitAsync(ct);
```

Nếu class sở hữu async resource, class đó nên propagate ownership rõ ràng thay vì để caller đoán ai phải dispose.

## 5. Real production scenario

Worker ghi large export vào stream có buffered async writer. Nếu chỉ đóng process hoặc bỏ cleanup, phần cuối file có thể chưa flush. `await using` đảm bảo cleanup nằm trong structured lifetime của operation.

## 6. Failure scenario & troubleshooting

**Symptom** → connection/resource count tăng hoặc file bị thiếu cuối. **Evidence** → resource không được dispose trên exception path. **Hypothesis** → ownership/lifetime sai. **Diagnosis** → inspect call path và counters. **Fix** → structured `await using`, propagate cancellation hợp lý cho operation nhưng không bỏ cleanup. **Verification** → fault injection giữa operation.

## 7. Common mistakes

Gọi `DisposeAsync().GetAwaiter().GetResult()`; vừa `using` vừa `await using` tùy tiện; dispose resource mà object không sở hữu; quên cleanup khi exception xảy ra.

## 8. Alternatives

`IDisposable` vẫn đúng cho purely synchronous cleanup. Không cần `IAsyncDisposable` chỉ vì method khác trong class là async.

## 9. Trade-offs

### Advantages

Không block thread trong cleanup I/O và làm ownership rõ.

### Costs / Risks

API/lifetime phức tạp hơn; caller phải dùng đúng async disposal semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dispose là resource lifetime, không phải garbage collection.

### Middle

Dùng `await using` đúng với async resource.

### Senior

Reason về ownership, exception path và cleanup failure.

### Technical Lead / Architect

Thiết kế resource boundary để cleanup là deterministic và observable.

## 11. Key takeaway

- GC không thay thế deterministic cleanup.
- Async cleanup nên được await thay vì block.
- Ownership phải rõ trước khi nói về dispose.

# 2. ASP.NET Core DI scopes: lifetime boundary, captive dependency và background processing

## 1. What is it?

ASP.NET Core DI có `Singleton`, `Scoped`, `Transient`. Mental model quan trọng: lifetime không mô tả “object dùng bao lâu cho tiện”; nó mô tả **ownership và sharing boundary**.

## 2. Why does it exist?

Một `DbContext` cần unit-of-work boundary theo request, trong khi stateless configuration/cache client có thể sống lâu hơn. Nếu Singleton giữ Scoped service, scoped object bị “captive” và lifetime semantics bị phá.

## 3. How does it work?

HTTP request tạo một service scope. Scoped services được resolve và dispose cùng scope. Singleton nằm ở root container. Vì root sống lâu hơn request, nó không được trực tiếp giữ dependency chỉ hợp lệ trong request scope.

## 4. Practical implementation

Background worker phải tạo scope riêng cho mỗi unit of work:

```csharp
public sealed class BillingWorker(
    IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await using var scope = scopeFactory.CreateAsyncScope();
            var handler = scope.ServiceProvider
                .GetRequiredService<BillingHandler>();

            await handler.ProcessBatchAsync(ct);
            await Task.Delay(TimeSpan.FromSeconds(10), ct);
        }
    }
}
```

## 5. Real production scenario

Một Singleton queue consumer inject trực tiếp `DbContext`. Under load, concurrent messages dùng cùng context và phát sinh tracking/thread-safety errors. Root cause là lifetime boundary, không phải EF Core “random lỗi”.

## 6. Failure scenario & troubleshooting

**Symptom** → disposed-object, concurrency hoặc stale tracked state. **Evidence** → Singleton giữ Scoped dependency. **Hypothesis** → captive dependency. **Diagnosis** → inspect registrations + dependency graph. **Fix** → tạo scope theo message/job/request. **Verification** → concurrent integration test.

## 7. Common mistakes

Mọi service đều Scoped; Singleton giữ mutable state không thread-safe; resolve service từ root provider; dùng Service Locator để che dependency graph.

## 8. Alternatives

Factory abstraction hữu ích khi lifetime creation là domain/application concern. Manual construction có thể đơn giản hơn ở small isolated component.

## 9. Trade-offs

### Advantages

DI scopes chuẩn hóa ownership và disposal.

### Costs / Risks

Sai lifetime tạo bug khó thấy; quá nhiều indirection làm dependency graph khó đọc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết ba lifetime cơ bản.

### Middle

Chọn lifetime đúng cho DbContext, handlers và stateless services.

### Senior

Phát hiện captive dependency, thread-safety và disposal bugs.

### Technical Lead / Architect

Định nghĩa lifetime boundaries theo execution model, không theo convention mù quáng.

## 11. Key takeaway

- Lifetime là ownership boundary.
- Background worker không có request scope tự nhiên.
- Singleton phải đặc biệt cẩn thận với mutable/scoped dependencies.

# 3. SQL Server parameter sniffing: cùng query, execution plan khác workload

## 1. What is it?

Parameter sniffing là việc SQL Server compile execution plan dựa trên parameter values thấy tại compile time rồi cache plan đó để reuse. Đây thường là optimization tốt, nhưng data distribution lệch có thể làm một plan không phù hợp mọi parameter.

## 2. Why does it exist?

Compile plan mỗi execution tốn CPU. Plan reuse giảm compilation cost. Vấn đề xuất hiện khi `CustomerId=1` trả 2 triệu rows còn customer thông thường chỉ 20 rows.

## 3. How does it work?

```text
first execution -> parameter value
               -> optimizer estimates
               -> plan compiled
               -> plan cached
later values   -> reuse same plan
```

Query → estimates/statistics → plan → I/O/CPU → latency.

## 4. Practical implementation

Bắt đầu bằng evidence:

```sql
SELECT OrderId, CreatedAt, Total
FROM dbo.Orders
WHERE CustomerId = @CustomerId
ORDER BY CreatedAt DESC;
```

So sánh actual execution plan cho representative values, estimated vs actual rows, logical reads và Query Store history. Không thêm `OPTION (RECOMPILE)` trước khi hiểu workload.

## 5. Real production scenario

Order API bình thường 30 ms nhưng enterprise customer mất 8 giây. Plan cache dùng nested loops tối ưu cho customer nhỏ. Với customer lớn, reads bùng nổ.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng endpoint lúc nhanh lúc chậm theo parameter. **Evidence** → Query Store có plan/latency variance lớn. **Hypothesis** → skew + cached plan. **Diagnosis** → plans, statistics, cardinality. **Fix** → index/query shape/statistics hoặc targeted plan strategy. **Verification** → test nhiều parameter classes.

## 7. Common mistakes

Clear toàn bộ plan cache; thêm index không đo I/O; dùng `RECOMPILE` mọi nơi; kết luận parameter sniffing chỉ từ latency variance.

## 8. Alternatives

Query Store plan forcing/hints, `OPTIMIZE FOR`, recompilation hoặc query decomposition—mỗi cách chỉ hợp khi evidence phù hợp.

## 9. Trade-offs

### Advantages

Plan reuse giảm compilation overhead.

### Costs / Risks

Skewed data có thể làm cached plan gây tail latency nghiêm trọng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SQL execution plan phụ thuộc statistics/data distribution.

### Middle

Đọc actual plan và logical reads.

### Senior

Phân biệt parameter sniffing với bad index, stale stats hoặc blocking.

### Technical Lead / Architect

Thiết lập Query Store/observability và performance regression process thay vì chữa từng query bằng folklore.

## 11. Key takeaway

- Parameter sniffing không mặc định là bug.
- Data skew làm plan reuse trở thành vấn đề.
- Diagnosis phải dựa trên plan + runtime evidence.

# 4. Cosmos DB consistency levels: latency, availability và read-your-writes

## 1. What is it?

Cosmos DB consistency level quy định client có thể quan sát replicas “mới” đến mức nào. Mental model: consistency là contract về visibility/order của writes trong distributed storage.

## 2. Why does it exist?

Replicate dữ liệu qua regions tạo latency và failure boundaries. Không thể đồng thời tối đa hóa mọi thuộc tính consistency, latency và availability cho mọi workload.

## 3. How does it work?

Strong yêu cầu visibility chặt hơn. Session cung cấp read-your-writes trong client session và thường phù hợp application workflows. Eventual cho phép replicas hội tụ sau.

```text
write -> replica A
      -> replication
      -> replica B/C
read contract determines what a client may observe
```

## 4. Practical implementation

Trong .NET SDK, consistency được cấu hình ở account/client/request tùy scenario. Quan trọng hơn API syntax là giữ session token đúng qua request flow nếu business yêu cầu read-your-writes.

## 5. Real production scenario

User cập nhật profile rồi redirect sang page đọc từ Cosmos DB. Với eventual consistency, page đôi lúc hiển thị dữ liệu cũ. Session consistency phù hợp hơn nếu request chain giữ đúng session context.

## 6. Failure scenario & troubleshooting

**Symptom** → user vừa ghi nhưng đọc thấy stale data. **Evidence** → consistency config/session token path. **Hypothesis** → expectation mạnh hơn configured contract. **Diagnosis** → trace region, request charge, session token và write/read sequence. **Fix** → consistency phù hợp hoặc redesign UX/data flow. **Verification** → multi-region tests.

## 7. Common mistakes

Chọn Strong “cho chắc”; nhầm consistency với transaction; bỏ qua partition boundary; nghĩ eventual nghĩa dữ liệu sẽ tùy ý sai mãi mãi.

## 8. Alternatives

SQL database phù hợp nếu workload cần relational constraints/transactions mạnh hơn. Cache + relational DB có consistency problem khác, không tự động đơn giản hơn.

## 9. Trade-offs

### Advantages

Có thể chọn contract phù hợp workload và topology.

### Costs / Risks

Consistency mạnh hơn có latency/availability/cost implications; consistency yếu hơn đẩy complexity lên application/UX.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu replica có thể không nhìn thấy write cùng thời điểm.

### Middle

Chọn và test session/read behavior.

### Senior

Reason về partition, region failover và stale-read business impact.

### Technical Lead / Architect

Chọn datastore/consistency dựa trên invariant và user expectation, không theo “NoSQL scales better”.

## 11. Key takeaway

- Consistency là business-visible contract.
- Session consistency thường là practical middle ground.
- Chọn mức mạnh nhất không phải luôn tốt nhất.

# 5. Redis outage strategy: cache failure không nên tự động biến thành database outage

## 1. What is it?

Redis cache thường nằm trên read path để giảm latency/load. Nhưng khi Redis unavailable, fallback trực tiếp toàn bộ traffic về database có thể tạo **cache failure amplification**.

## 2. Why does it exist?

Cache làm downstream quen với traffic thấp hơn. Khi cache biến mất, origin/database có thể bất ngờ nhận 10–100 lần query và sập theo.

## 3. How does it work?

```text
normal: API -> Redis hit -> response
outage: API -> Redis fail -> Database
                    thousands of requests -> overload
```

Resilience cần bounded timeout, fallback policy, request coalescing/rate limiting và stale-data strategy tùy domain.

## 4. Practical implementation

```csharp
var cached = await cache.TryGetAsync<ProductDto>(key, ct);
if (cached is not null) return cached;

await gate.WaitAsync(ct);
try
{
    // Re-check after entering a bounded single-flight section.
    cached = await cache.TryGetAsync<ProductDto>(key, ct);
    return cached ?? await repository.GetProductAsync(id, ct);
}
finally { gate.Release(); }
```

Production distributed strategy cần tránh biến local gate thành false sense of global protection.

## 5. Real production scenario

Catalog API có 5k RPS, DB bình thường chỉ thấy 300 RPS nhờ Redis. Redis cluster outage làm 5k RPS đập thẳng DB, connection pool cạn và checkout bị ảnh hưởng.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis errors trước, vài giây sau DB latency/connections tăng. **Evidence** → dependency timeline. **Hypothesis** → fallback storm. **Diagnosis** → correlate Redis miss/error rate với DB QPS. **Fix** → fail-fast, stale cache/local fallback, rate limiting, capacity isolation. **Verification** → chaos test cache outage.

## 7. Common mistakes

Retry Redis nhiều lần trong request; fallback vô hạn; không monitor hit ratio; cache critical authorization data mà không có correctness strategy.

## 8. Alternatives

`IMemoryCache` giảm remote dependency nhưng không shared. CDN phù hợp public cacheable content. Không cache có thể tốt hơn nếu DB đã đáp ứng SLO/capacity.

## 9. Trade-offs

### Advantages

Cache giảm latency và origin load.

### Costs / Risks

Tạo thêm consistency và failure mode; origin có thể trở nên phụ thuộc ngầm vào cache.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache là optimization layer.

### Middle

Implement cache-aside với timeout/TTL.

### Senior

Thiết kế cache outage và stampede protection.

### Technical Lead / Architect

Quyết định origin phải chịu được bao nhiêu degraded traffic và stale data có chấp nhận được không.

## 11. Key takeaway

- Cache outage có thể cascade sang database.
- Fallback cũng cần capacity policy.
- “Không cache” đôi khi là kiến trúc tốt hơn.

# 6. DDD Aggregate: boundary của invariant và transaction

## 1. What is it?

Aggregate là consistency boundary gồm Aggregate Root và các entities/value objects được thay đổi như một unit để bảo vệ business invariants. Nó không phải “load toàn bộ object graph liên quan”.

## 2. Why does it exist?

Business rule cần một nơi chịu trách nhiệm. Nếu mọi service sửa mọi table/entity trực tiếp, invariant như “approved order không được sửa line items” dễ bị bypass.

## 3. How does it work?

Application Service load Aggregate Root → gọi behavior → aggregate kiểm tra invariant → persist trong một transaction. Cross-aggregate coordination thường dùng application workflow/domain events/eventual consistency khi không cần atomic transaction.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public void AddLine(ProductId productId, int quantity)
    {
        if (Status != OrderStatus.Draft)
            throw new DomainException("Only draft orders can change.");

        if (quantity <= 0)
            throw new DomainException("Quantity must be positive.");

        _lines.Add(new OrderLine(productId, quantity));
    }
}
```

## 5. Real production scenario

Approval workflow cần bảo đảm approved timesheet không còn chỉnh entries. `Timesheet` aggregate giữ invariant; payroll integration là boundary khác và nhận event sau commit.

## 6. Failure scenario & troubleshooting

**Symptom** → aggregate load chậm và update contention cao. **Evidence** → root chứa hàng chục nghìn child rows. **Hypothesis** → consistency boundary quá lớn. **Diagnosis** → inspect invariants: có thật mọi child phải atomic cùng nhau? **Fix** → thu nhỏ aggregate và chuyển coordination phù hợp. **Verification** → concurrency/load tests + invariant tests.

## 7. Common mistakes

Aggregate = EF navigation graph; một aggregate cho cả bounded context; repository cho mọi entity; domain event để né transaction mà không hiểu consistency requirement.

## 8. Alternatives

Anemic CRUD model hoàn toàn hợp với domain đơn giản. Transaction Script có thể rõ và rẻ hơn full DDD.

## 9. Trade-offs

### Advantages

Invariant ownership rõ và change isolation tốt.

### Costs / Risks

Modeling effort; boundary sai tạo contention hoặc eventual-consistency complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Entity, Value Object và Aggregate Root khác nhau.

### Middle

Đưa behavior/invariant vào aggregate thay vì controller.

### Senior

Thiết kế transaction boundary và cross-aggregate consistency.

### Technical Lead / Architect

Quyết định domain nào đáng dùng DDD và domain nào chỉ cần CRUD.

## 11. Key takeaway

- Aggregate là consistency boundary.
- Boundary càng lớn không càng “DDD”.
- Invariant quyết định transaction boundary.

# 7. OpenTelemetry trace sampling: giảm telemetry cost mà vẫn điều tra được production

## 1. What is it?

Trace sampling quyết định request/traces nào được record/export. Mental model: observability pipeline cũng có capacity và cost; “collect everything forever” hiếm khi scale.

## 2. Why does it exist?

High-traffic service có thể tạo hàng tỷ spans. Storage, ingestion và query cost tăng; exporter overload thậm chí ảnh hưởng application.

## 3. How does it work?

Head sampling quyết định sớm, rẻ nhưng chưa biết outcome. Tail sampling có thể xem toàn trace/error/latency rồi quyết định, nhưng cần collector giữ dữ liệu tạm.

## 4. Practical implementation

```csharp
services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .SetSampler(new TraceIdRatioBasedSampler(0.10))
        .AddOtlpExporter());
```

Errors/critical flows có thể cần policy khác tại collector.

## 5. Real production scenario

API 20k RPS export 100% traces vào backend. Telemetry bill tăng mạnh và collector lag. Team chuyển sang sampled normal traffic nhưng giữ errors/high-latency traces bằng tail policy.

## 6. Failure scenario & troubleshooting

**Symptom** → incident xảy ra nhưng trace quan trọng không có. **Evidence** → aggressive head sampling. **Hypothesis** → sampling policy bỏ rare failures. **Diagnosis** → compare error metrics/logs với retained traces. **Fix** → tail/error-aware sampling và correlation. **Verification** → synthetic failures phải xuất hiện.

## 7. Common mistakes

Sample logs/metrics giống traces; sampling mà không document effective rate; mất parent-child sampling consistency; dùng telemetry volume thay quality.

## 8. Alternatives

100% tracing hợp low-volume critical systems. Adaptive/vendor sampling đơn giản vận hành hơn nhưng giảm control.

## 9. Trade-offs

### Advantages

Giảm ingestion/storage cost.

### Costs / Risks

Có thể mất rare evidence; tail sampling tăng collector complexity/resources.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu logs, metrics, traces có vai trò khác nhau.

### Middle

Instrument và correlate trace IDs.

### Senior

Thiết kế sampling giữ failure evidence.

### Technical Lead / Architect

Đặt observability budget/SLO và quyết định telemetry nào thực sự phục vụ operations.

## 11. Key takeaway

- Observability có cost và capacity.
- Sampling phải giữ signal, không chỉ giảm volume.
- Metrics phát hiện; traces thường giúp localize.

# 8. Kubernetes resource requests/limits: scheduler, throttling và OOMKilled

## 1. What is it?

`requests` nói scheduler lượng CPU/memory workload cần để placement. `limits` giới hạn resource container có thể sử dụng theo cơ chế tương ứng.

## 2. Why does it exist?

Nhiều workloads chia sẻ nodes. Không có resource contracts, một pod có thể gây noisy-neighbor hoặc scheduler đặt quá nhiều workloads lên node.

## 3. How does it work?

Scheduler chủ yếu dùng requests để placement. Memory vượt limit có thể dẫn tới OOM kill. CPU limit có thể gây throttling thay vì kill, làm latency tăng dù node còn capacity theo cách quan sát khác.

## 4. Practical implementation

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
```

Values phải đến từ load test/production metrics, không copy template.

## 5. Real production scenario

ASP.NET Core pod có CPU limit quá thấp. Traffic burst làm throttling, p99 tăng và readiness timeout. HPA lại scale chậm vì resource assumptions sai.

## 6. Failure scenario & troubleshooting

**Symptom** → pod restart với `OOMKilled` hoặc latency cao không tương ứng node CPU. **Evidence** → pod status, cgroup/container metrics, throttling counters. **Hypothesis** → limit/resource sizing. **Diagnosis** → `kubectl describe pod` + metrics. **Fix** → sửa memory behavior hoặc resource policy. **Verification** → load test dưới cùng constraints.

## 7. Common mistakes

Requests=limits theo template; tăng memory limit để che leak; không set requests rồi mong autoscaling/capacity predictable; liveness probe quá aggressive khi throttled.

## 8. Alternatives

Vertical Pod Autoscaler có thể hỗ trợ recommendations/adjustment; App Service/Container Apps giảm Kubernetes operational burden nếu requirements không cần cluster-level control.

## 9. Trade-offs

### Advantages

Predictable scheduling và isolation tốt hơn.

### Costs / Risks

Sizing sai gây waste, throttling hoặc eviction/OOM behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt request với limit.

### Middle

Đọc pod events và resource metrics.

### Senior

Liên hệ GC/CPU/latency với container limits và autoscaling.

### Technical Lead / Architect

Quyết định platform/resource policy theo workload economics và team maturity.

## 11. Key takeaway

- Requests ảnh hưởng scheduling; limits ảnh hưởng runtime constraint.
- CPU throttling có thể là latency problem.
- Resource values phải được đo.

# 9. Feature flags trong deployment: tách code deployment khỏi feature release

## 1. What is it?

Feature flag cho phép code đã deploy nhưng behavior mới chỉ bật cho selected users/traffic. Deployment và business release trở thành hai operations khác nhau.

## 2. Why does it exist?

Big-bang release tăng blast radius. Flag hỗ trợ progressive rollout, kill switch và experimentation mà không rebuild artifact.

## 3. How does it work?

Request → flag evaluation → old/new path. Evaluation có thể dựa trên environment, user cohort hoặc percentage. Flag state phải observable và configuration propagation phải có semantics rõ.

## 4. Practical implementation

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
    return await newCheckout.HandleAsync(command, ct);

return await legacyCheckout.HandleAsync(command, ct);
```

Cả hai paths cần tương thích với data/schema trong rollout period.

## 5. Real production scenario

New pricing engine deploy tới toàn fleet nhưng flag bật 5% accounts. Metrics được segment theo flag state. Error rate tăng ở new cohort, team tắt flag mà không rollback artifact.

## 6. Failure scenario & troubleshooting

**Symptom** → production behavior khác giữa requests khó reproduce. **Evidence** → flag targeting/config history. **Hypothesis** → stale/inconsistent flag state. **Diagnosis** → log flag decision với safe identifiers/version. **Fix** → deterministic targeting, propagation policy, audit. **Verification** → cohort-specific tests.

## 7. Common mistakes

Flag sống vĩnh viễn; nested flags tạo combinatorial states; dùng flag thay authorization; không test off-path; schema migration phá old path.

## 8. Alternatives

Canary deployment ở infrastructure layer; branch/release train đơn giản hơn nếu release risk thấp.

## 9. Trade-offs

### Advantages

Giảm blast radius và rollback behavior nhanh.

### Costs / Risks

Code paths tăng, testing matrix lớn, flag service trở thành operational dependency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy khác release.

### Middle

Implement flag với tests cho on/off.

### Senior

Thiết kế observability, cleanup và data compatibility.

### Technical Lead / Architect

Đặt governance: owner, expiry date, kill-switch semantics và dependency strategy.

## 11. Key takeaway

- Feature flag là temporary control plane.
- Flag không thay thế backward-compatible data design.
- Flag không cleanup sẽ trở thành technical debt.

# 10. AI Tool Calling: giữ business action deterministic và coi model output là untrusted input

## 1. What is it?

Tool Calling cho phép model chọn một tool/function và tạo structured arguments để application thực thi. Mental model: model **đề xuất intent/arguments**; application vẫn là security và correctness boundary.

## 2. Why does it exist?

LLM giỏi hiểu natural language nhưng không nên trực tiếp có quyền tùy ý sửa database, gửi tiền hoặc gọi internal systems. Tool layer tạo explicit interface giữa probabilistic reasoning và deterministic code.

## 3. How does it work?

```text
User
 -> LLM
 -> tool name + arguments
 -> application validation/authorization
 -> deterministic tool execution
 -> tool result
 -> LLM response
```

Model output phải được schema-validated và policy-checked như untrusted input.

## 4. Practical implementation

```csharp
public sealed record CreateTicketArgs(
    string Title,
    string Description,
    string Priority);

public async Task<Ticket> CreateTicketAsync(
    CreateTicketArgs args,
    UserContext user,
    CancellationToken ct)
{
    authorization.Require(user, Permission.CreateTicket);
    validator.ValidateAndThrow(args);

    return await ticketService.CreateAsync(args, ct);
}
```

LLM không được tự quyết định `user`, permission hoặc tenant ID từ prompt text.

## 5. Real production scenario

Support assistant hiểu câu “tạo ticket P1 cho lỗi checkout”, gọi tool tạo ticket. Tool layer map authenticated tenant/user từ server context, validate priority và deduplicate request. Model chỉ cung cấp business content được phép.

## 6. Failure scenario & troubleshooting

**Symptom** → model gọi sai tool hoặc arguments hợp schema nhưng sai business semantics. **Evidence** → tool-call traces/evaluation cases. **Hypothesis** → ambiguous tool contract hoặc missing deterministic validation. **Diagnosis** → inspect tool selection, schema, policy checks. **Fix** → narrow tools, stronger validation, confirmation cho high-impact action. **Verification** → adversarial/evaluation suite.

## 7. Common mistakes

Tin tool arguments vì “structured”; để model truyền tenant/user authorization context; retry side-effecting tool không idempotent; expose tool quá quyền; log sensitive prompt/tool payload.

## 8. Alternatives

Deterministic UI/workflow tốt hơn khi intent đã rõ. RAG phù hợp retrieval; Tool Calling phù hợp action/live data. Không phải mọi chatbot cần Agent architecture.

## 9. Trade-offs

### Advantages

Natural-language orchestration trên deterministic capabilities.

### Costs / Risks

Prompt injection, incorrect tool choice, security boundary, evaluation/observability và token/latency cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu model output không phải trusted command.

### Middle

Implement schema validation, timeout và error handling.

### Senior

Thiết kế authorization, idempotency, audit và prompt-injection boundaries.

### Technical Lead / Architect

Quyết định logic nào có thể probabilistic và logic nào bắt buộc deterministic; giới hạn blast radius của agent/tool system.

## 11. Key takeaway

- Model đề xuất; application quyết định và thực thi.
- Authorization không được delegate cho LLM.
- Tool surface càng nhỏ và deterministic càng dễ bảo vệ/evaluate.
