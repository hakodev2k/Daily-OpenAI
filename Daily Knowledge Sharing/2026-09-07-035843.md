# 1. `Span<T>`, `Memory<T>` và `ArrayPool<T>` trong hot path .NET

## 1. What is it?

`Span<T>` là một view trên vùng memory liên tục; nó không sở hữu dữ liệu. `Memory<T>` có mental model tương tự nhưng có thể đi qua asynchronous boundary. `ArrayPool<T>` cho phép thuê và trả lại arrays để giảm repeated allocations.

## 2. Why does it exist?

Trong parsing, serialization và file processing, allocation rate cao có thể làm Gen 0/Gen 1 collections dày và tăng tail latency. Các abstraction này giúp giảm copy/allocation khi profiler chứng minh memory churn là bottleneck.

## 3. How does it work?

```csharp
ReadOnlySpan<char> prefix = input.AsSpan(0, 8);
```

Đoạn trên tạo view thay vì string mới. Với pooling:

```text
Rent -> Use -> Return -> Reuse
```

Pool có thể trả buffer lớn hơn requested size và không đảm bảo dữ liệu cũ đã được zeroed.

## 4. Practical implementation

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(64 * 1024);
try
{
    var read = await source.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
    await target.WriteAsync(buffer.AsMemory(0, read), ct);
}
finally
{
    pool.Return(buffer, clearArray: true);
}
```

## 5. Real production scenario

Một CSV ingestion service dùng `Split()` cho từng dòng và tạo hàng triệu strings. Allocation profiler cho thấy phần lớn CPU time nằm ở allocation/GC chứ không phải business logic. Streaming + slicing giảm pressure rõ rệt.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU tăng, p99 dao động, GC collections dày. **Evidence** → profiler chỉ ra `ToArray()`, `Split()`, temporary buffers. **Fix** → chỉ tối ưu hot path đã đo; kiểm tra lại allocation rate, GC pause và throughput.

## 7. Common mistakes

Dùng `Span<T>` khắp nơi; quên trả pooled buffer; giữ rented array lâu; assume exact length; không clear sensitive data; convert ngược thành array/string ở cuối mọi bước.

## 8. Alternatives

Code arrays/strings thông thường thường tốt hơn nếu allocation không phải bottleneck. `System.IO.Pipelines` hợp với protocol/high-throughput streaming phức tạp.

## 9. Trade-offs

### Advantages

Giảm allocations, GC pressure và có thể tăng throughput.

### Costs / Risks

Code khó đọc hơn, lifetime constraints phức tạp hơn và pooling mang thêm lifecycle/security responsibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slice/view không nhất thiết tạo copy.

### Middle

Dùng `Span<T>`, `Memory<T>` và pool đúng API boundary.

### Senior

Đọc allocation profile và GC metrics trước khi tối ưu.

### Technical Lead / Architect

Giới hạn low-allocation complexity vào hot paths có business value.

## 11. Key takeaway

* Tối ưu allocation phải dựa trên measurement.
* `Span<T>` là view, không phải owner.
* Pooling đổi allocation cost lấy lifecycle discipline.

# 2. ASP.NET Core API Versioning và backward compatibility

## 1. What is it?

API versioning quản lý sự tiến hóa của public contract khi server và client không deploy đồng thời. Backward compatibility rộng hơn versioning: thêm optional field hoặc giữ semantics cũ có thể tránh tạo version mới.

## 2. Why does it exist?

Mobile apps, partner integrations và cached frontend assets có release cadence riêng. Một rename field hoặc đổi status-code semantics có thể làm client production hỏng dù backend deployment thành công.

## 3. How does it work?

```text
Introduce new contract -> support old + new -> migrate clients
-> observe usage -> deprecate -> remove old contract
```

Version có thể qua URL, header, query parameter hoặc media type; lựa chọn phải nhất quán hơn là chạy theo pattern.

## 4. Practical implementation

```csharp
public sealed record OrderResponse(
    Guid Id,
    string Status,
    decimal Total,
    string? Currency = null);
```

Thêm `Currency` optional thường an toàn hơn thay đổi shape của `Total`. Nếu cần `/v2`, hai versions nên dùng chung application/domain logic khi business semantics không đổi.

## 5. Real production scenario

Backend đổi `fullName` thành `displayName`. Mobile version cũ vẫn deserialize `fullName`, dẫn đến blank UI. Correct rollout là additive field + migration window + deprecation.

## 6. Failure scenario & troubleshooting

**Symptom** → client errors tăng nhưng server exceptions thấp. **Evidence** → OpenAPI/schema diff có breaking change. **Diagnosis** → replay request từ client version cũ. **Fix** → restore compatible contract hoặc route tới version cũ.

## 7. Common mistakes

Version mọi thay đổi; đổi enum semantics âm thầm; version business logic thay vì transport contract; xóa version cũ mà không đo usage.

## 8. Alternatives

Additive evolution, capability negotiation hoặc field deprecation thường đơn giản hơn full endpoint versioning.

## 9. Trade-offs

### Advantages

Independent deployment và controlled migration.

### Costs / Risks

Nhiều versions tăng testing, support burden và technical debt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu public API là contract.

### Middle

Phân biệt additive vs breaking change và viết contract tests.

### Senior

Thiết kế migration/deprecation dựa trên client telemetry.

### Technical Lead / Architect

Đặt compatibility policy và lifecycle ownership.

## 11. Key takeaway

* Versioning giải quyết independent deployment.
* Backward-compatible evolution thường rẻ hơn tạo version mới.
* Client impact quan trọng hơn server compile success.

# 3. EF Core optimistic concurrency và lost update

## 1. What is it?

Optimistic concurrency dùng concurrency token để phát hiện dữ liệu đã thay đổi từ lúc client đọc tới lúc update. Nó tránh giữ database lock xuyên suốt user interaction.

## 2. Why does it exist?

Hai users có thể cùng đọc Version 10. A ghi Version 11; B dùng stale state và vô tình overwrite A. Đó là lost update.

## 3. How does it work?

Với SQL Server `rowversion`, logic update trở thành:

```sql
UPDATE Employees
SET Title = @title
WHERE Id = @id AND RowVersion = @originalVersion;
```

0 rows affected khiến EF Core throw `DbUpdateConcurrencyException`.

## 4. Practical implementation

```csharp
public sealed class Employee
{
    public Guid Id { get; set; }
    public string Title { get; set; } = string.Empty;

    [Timestamp]
    public byte[] RowVersion { get; set; } = Array.Empty<byte>();
}
```

```csharp
try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict();
}
```

## 5. Real production scenario

Hai managers sửa cùng timesheet. Nếu update chỉ theo `Id`, thay đổi sau có thể silently overwrite thay đổi trước. Concurrency token biến corruption âm thầm thành explicit conflict.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu “quay lại” giá trị cũ. **Evidence** → audit logs có hai updates với stale state. **Fix** → concurrency token + conflict strategy. **Verification** → integration test bằng hai `DbContext` cùng đọc rồi update.

## 7. Common mistakes

Catch exception rồi auto-retry; dùng business timestamp có precision yếu; trả 500; update toàn entity dù user chỉ sửa một field.

## 8. Alternatives

HTTP ETag/`If-Match`, pessimistic locking cho transaction ngắn, hoặc domain-specific merge.

## 9. Trade-offs

### Advantages

Không giữ lock dài và phát hiện silent overwrite.

### Costs / Risks

Conflict UX và merge/retry logic phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu lost update.

### Middle

Implement `rowversion` và conflict response.

### Senior

Quyết định retry, merge, reject hoặc reload theo business semantics.

### Technical Lead / Architect

Chọn aggregate nào cần optimistic concurrency và boundary nào cần stronger serialization.

## 11. Key takeaway

* Concurrency token bảo vệ correctness.
* Conflict không nên bị che bằng retry mù quáng.
* HTTP và persistence concurrency nên có semantics thống nhất.

# 4. SQL Server deadlock: lock graph và transaction order

## 1. What is it?

Deadlock là cycle chờ: transaction A giữ resource mà B cần, trong khi B giữ resource mà A cần. SQL Server phát hiện cycle và rollback một victim.

## 2. Why does it exist?

Locking bảo vệ consistency nhưng transactions truy cập resources theo thứ tự khác nhau có thể tạo circular wait.

## 3. How does it work?

```text
T1 giữ Row A -> chờ Row B
T2 giữ Row B -> chờ Row A
```

Đây khác blocking thông thường: blocking có thể tự kết thúc khi holder commit; deadlock là cycle.

## 4. Practical implementation

Một biện pháp quan trọng là consistent ordering:

```csharp
var ids = new[] { fromId, toId }.OrderBy(x => x).ToArray();
var accounts = await db.Accounts
    .Where(x => ids.Contains(x.Id))
    .OrderBy(x => x.Id)
    .ToListAsync(ct);
```

Ngoài ra phải giữ transaction ngắn và access path hiệu quả.

## 5. Real production scenario

Order workflow update `Orders` rồi `Inventory`; reconciliation job làm ngược lại. Under load, deadlocks xuất hiện dù từng query riêng lẻ nhanh.

## 6. Failure scenario & troubleshooting

**Symptom** → error 1205 dưới concurrency. **Evidence** → deadlock graph. **Diagnosis** → đọc processes, resources, lock modes, statements và execution plans. **Fix** → consistent order, giảm transaction scope, cải thiện access path. **Verification** → replay concurrent load.

## 7. Common mistakes

Chỉ thêm retry; transaction xuyên external API call; không capture deadlock graph; tăng isolation level theo cảm tính.

## 8. Alternatives

Optimistic concurrency cho user-edit workflow; queue serialization cho hot aggregate; snapshot isolation có thể giảm reader/writer blocking nhưng không xóa mọi deadlock.

## 9. Trade-offs

### Advantages

Locking cung cấp strong transaction consistency.

### Costs / Risks

Concurrency cao làm lock interaction phức tạp; retry amplification có thể tăng load.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt blocking và deadlock.

### Middle

Giữ transaction scope ngắn và resource order nhất quán.

### Senior

Đọc deadlock graph và execution plan.

### Technical Lead / Architect

Thiết kế transaction/data ownership để contention không lan giữa workflows.

## 11. Key takeaway

* Deadlock là cycle, không chỉ query chậm.
* Retry là safety net, không phải root-cause fix.
* Deadlock graph là evidence chính.

# 5. Redis cache stampede và jittered TTL

## 1. What is it?

Cache stampede xảy ra khi nhiều requests cùng miss một hot key và đồng thời rebuild từ database/source-of-truth.

## 2. Why does it exist?

Cache che backend load khi hit nhưng khi key hết hạn, toàn traffic có thể đổ xuống database trong cùng thời điểm.

## 3. How does it work?

```text
1000 requests -> Redis MISS -> 1000 DB queries
```

Single-flight/coalescing biến nó gần hơn thành:

```text
1000 requests -> MISS -> 1 rebuild -> shared result
```

Random jitter trên TTL giảm synchronized expiration giữa nhiều keys.

## 4. Practical implementation

```csharp
var ttl = TimeSpan.FromMinutes(5) +
          TimeSpan.FromSeconds(Random.Shared.Next(0, 60));

await cache.SetAsync(key, value, ttl, ct);
```

In-process `SemaphoreSlim` có thể coalesce trong một instance, nhưng multi-instance cần đánh giá distributed coordination hoặc stale-while-revalidate.

## 5. Real production scenario

Top product keys được warm cùng lúc khi deploy và cùng TTL 10 phút. Database CPU spike theo chu kỳ 10 phút. Jitter + staggered warming phá synchronization này.

## 6. Failure scenario & troubleshooting

**Symptom** → DB p95 spike theo chu kỳ. **Evidence** → cache miss rate và identical query count tăng đồng thời. **Fix** → jitter, coalescing hoặc stale-while-revalidate. **Verification** → miss burst và DB logical work giảm.

## 7. Common mistakes

TTL giống nhau hàng loạt; distributed lock cho mọi key; cache correctness-critical data mà không định nghĩa staleness; không có fallback khi Redis unavailable.

## 8. Alternatives

`IMemoryCache`, short TTL, stale-while-revalidate hoặc không cache nếu query vốn đủ rẻ.

## 9. Trade-offs

### Advantages

Giảm duplicate rebuild work và bảo vệ database.

### Costs / Risks

Coordination tăng complexity; stale serving ảnh hưởng freshness; Redis có thể thành hidden critical dependency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss vẫn tạo backend work.

### Middle

Biết TTL, jitter và invalidation basics.

### Senior

Thiết kế hot-key, fallback và cache-loss capacity.

### Technical Lead / Architect

Quyết định dữ liệu nào thực sự đáng cache và operational dependency có chấp nhận được không.

## 11. Key takeaway

* Cache expiry có thể tạo load burst.
* Jitter là mitigation rẻ và hữu ích.
* Luôn hỏi: Redis unavailable thì hệ thống còn chạy được không?

# 6. CQRS với một database vs separate read/write stores

## 1. What is it?

CQRS tách command thay đổi state khỏi query đọc state. Nó không bắt buộc Event Sourcing, Microservices hay hai databases.

## 2. Why does it exist?

Write model cần invariants/transactions; read model cần projection/filtering/latency. Ép cả hai qua cùng generic abstraction có thể làm cả hai kém rõ ràng.

## 3. How does it work?

Một database:

```text
Command -> Domain/Application -> SQL
Query   -> Read projection ----> SQL
```

Separate stores:

```text
Command -> Write DB -> Event -> Read DB <- Query
```

Phương án hai thêm eventual consistency và synchronization machinery.

## 4. Practical implementation

```csharp
var summary = await db.Orders
    .AsNoTracking()
    .Where(x => x.Id == id)
    .Select(x => new OrderSummary(
        x.Id,
        x.Status,
        x.Items.Sum(i => i.Quantity * i.UnitPrice)))
    .SingleOrDefaultAsync(ct);
```

Read projection không cần materialize domain aggregate nếu không có business invariant phải thực thi.

## 5. Real production scenario

Order write model phức tạp, dashboard chỉ cần aggregate theo status/day. Separate query projection trên cùng SQL database giải quyết nhu cầu mà chưa phải vận hành second datastore.

## 6. Failure scenario & troubleshooting

**Symptom** → hệ thống nhỏ có broker, projection workers và read DB nhưng debugging data lag rất khó. **Diagnosis** → architecture ceremony vượt requirement. **Fix** → simplify về logical CQRS trên cùng DB nếu SLO vẫn đạt.

## 7. Common mistakes

CQRS = MediatR; CQRS = Event Sourcing; separate DB quá sớm; không thiết kế eventual consistency UX.

## 8. Alternatives

Traditional layered design hoặc direct DbContext query cho CRUD đơn giản.

## 9. Trade-offs

### Advantages

Read/write concerns tối ưu độc lập và có thể tiến hóa dần.

### Costs / Risks

Nhiều models/code paths; separate stores thêm synchronization và operations.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu command vs query.

### Middle

Biết tách read projection khi có ích.

### Senior

Phân biệt logical CQRS với distributed CQRS.

### Technical Lead / Architect

Chọn mức complexity nhỏ nhất đạt requirement.

## 11. Key takeaway

* CQRS không bắt buộc hai databases.
* Tách intent có thể hữu ích trong Modular Monolith.
* Separate read store chỉ khi scale/workload justify cost.

# 7. Azure Front Door vs Application Gateway vs Load Balancer

## 1. What is it?

Azure Front Door là global HTTP(S) edge/router; Application Gateway là regional Layer 7 reverse proxy/load balancer thường đi kèm WAF; Azure Load Balancer làm Layer 4 TCP/UDP balancing.

## 2. Why does it exist?

Global routing, WAF, path-based HTTP routing và raw TCP distribution là các vấn đề khác nhau; một service không tối ưu cho tất cả.

## 3. How does it work?

```text
Global users -> Front Door -> Region A / Region B
Regional HTTP -> Application Gateway -> backends
TCP/UDP -> Load Balancer -> VM/VMSS
```

## 4. Practical implementation

Ứng dụng sau reverse proxy phải hiểu forwarding headers:

```csharp
builder.Services.Configure<ForwardedHeadersOptions>(o =>
{
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor |
                         ForwardedHeaders.XForwardedProto;
});

app.UseForwardedHeaders();
```

## 5. Real production scenario

Global e-commerce site dùng Front Door để route giữa hai regions. Thêm Application Gateway chỉ có giá trị nếu regional WAF/private routing hoặc topology khác thực sự cần; nếu không, đó chỉ là thêm hop.

## 6. Failure scenario & troubleshooting

**Symptom** → redirect loop hoặc OAuth callback sai scheme. **Evidence** → forwarded headers/proxy config sai. **Fix** → kiểm tra TLS termination, host và forwarding chain. **Verification** → test full ingress path.

## 7. Common mistakes

Nhầm L4/L7; xếp nhiều proxy layers không cần thiết; health probe phụ thuộc quá nhiều downstream; không bảo vệ origin khỏi bypass.

## 8. Alternatives

App Service ingress, AKS ingress/Gateway API hoặc enterprise CDN/WAF khác như Akamai.

## 9. Trade-offs

### Advantages

Mỗi service giải đúng layer/scope của nó.

### Costs / Risks

Mỗi hop tăng cost, latency và troubleshooting surface.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu L4 vs L7.

### Middle

Biết TLS, health probe và forwarding headers.

### Senior

Trace request xuyên edge tới app.

### Technical Lead / Architect

Chọn ít tầng nhất đáp ứng availability, security và networking requirements.

## 11. Key takeaway

* Ba services không interchangeable.
* Chọn theo layer, scope và security need.
* Đừng thêm proxy nếu không giải quyết vấn đề thật.

# 8. CI/CD database migration với Expand/Contract

## 1. What is it?

Expand/Contract biến breaking schema change thành nhiều releases tương thích để old và new application versions có thể cùng chạy trong rolling/Blue-Green deployment.

## 2. Why does it exist?

Deployment không atomic trên toàn fleet. Nếu migration drop/rename column khi old instance còn traffic, rollback binary cũng không cứu được schema đã phá compatibility.

## 3. How does it work?

```text
Add new column
-> deploy code ghi old + new
-> backfill
-> deploy code đọc new
-> stop old version
-> drop old column ở release sau
```

## 4. Practical implementation

```csharp
migrationBuilder.AddColumn<string>(
    name: "DisplayName",
    table: "Users",
    type: "nvarchar(200)",
    nullable: true);
```

Transitional code có thể dual-write trong migration window, sau đó feature flag chuyển read path.

## 5. Real production scenario

App Service slot mới warm-up trong khi slot cũ vẫn nhận traffic. Migration rename column trước swap làm slot cũ throw `Invalid column name`. Root cause là deployment contract, không phải EF Core.

## 6. Failure scenario & troubleshooting

**Symptom** → old instances 500 ngay sau schema migration. **Evidence** → SQL errors mapping vào removed column. **Fix** → restore compatibility, sau đó dùng additive migration. **Verification** → test old + new binaries trên transitional schema.

## 7. Common mistakes

Destructive migration cùng release; startup migration từ nhiều instances; backfill lớn trong deployment path; assume rollback app = rollback database.

## 8. Alternatives

Dedicated migration job, maintenance window, online schema-change technique hoặc planned downtime khi business cho phép.

## 9. Trade-offs

### Advantages

Giảm blast radius và hỗ trợ safer rollout/rollback.

### Costs / Risks

Transitional schema/code tồn tại nhiều releases và cleanup cần discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu schema change có thể break running binaries.

### Middle

Viết additive migration.

### Senior

Plan backfill, locking và multi-version coexistence.

### Technical Lead / Architect

Đặt deployment contract và quyết định khi zero downtime không đáng complexity.

## 11. Key takeaway

* Database rollback không giống binary rollback.
* Expand trước, migrate, contract sau.
* Test coexistence của old/new version.

# 9. Vue.js / TypeScript event loop và async race condition

## 1. What is it?

JavaScript main thread chủ yếu single-threaded, nhưng asynchronous I/O hoàn tất theo thứ tự không deterministic. Vì vậy race condition vẫn xảy ra khi response cũ về sau response mới và overwrite state.

## 2. Why does it exist?

Search-as-you-type, filter switching và route navigation có thể tạo nhiều in-flight requests cùng lúc. Single-threaded chỉ nói callbacks chạy tuần tự, không nói network hoàn tất tuần tự.

## 3. How does it work?

```text
"car"  -> Request A
"card" -> Request B
B returns -> UI = card
A returns -> stale UI = car
```

## 4. Practical implementation

```ts
let controller: AbortController | null = null;

async function search(query: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(
    `/api/search?q=${encodeURIComponent(query)}`,
    { signal: controller.signal }
  );

  results.value = await response.json();
}
```

## 5. Real production scenario

Vue product search gửi request mỗi keystroke. Under slow network, response của query cũ overwrite query mới khiến UI “nhảy lùi”.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng không khớp filter. **Evidence** → DevTools cho thấy request cũ complete sau request mới. **Fix** → cancellation hoặc request sequence/version. **Verification** → throttle network và thao tác nhanh.

## 7. Common mistakes

“Single-threaded nên không race”; debounce nhưng không cancel request cũ; update state sau component unmount; retry writes không idempotent.

## 8. Alternatives

Sequence ID, query libraries với stale-state management hoặc server push tùy access pattern.

## 9. Trade-offs

### Advantages

Cancellation giảm stale UI và wasted work.

### Costs / Risks

Request lifecycle/state machine phức tạp hơn; abort ở client không đảm bảo mọi server-side downstream work dừng tức thì.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event loop và async completion order.

### Middle

Implement cancellation/debounce/error state.

### Senior

Thiết kế stale-data semantics và frontend/backend idempotency.

### Technical Lead / Architect

Chuẩn hóa data-fetching, cache, cancellation và observability conventions.

## 11. Key takeaway

* Single-threaded không loại bỏ race condition.
* Completion order không bằng request order.
* Request cancellation/versioning là correctness concern.

# 10. Optimizely CMS caching và content invalidation

## 1. What is it?

CMS website thường có nhiều cache layers: browser, CDN/Akamai, reverse proxy, ASP.NET Core cache, Optimizely content cache và database/content store.

## 2. Why does it exist?

CMS pages read-heavy và có thể compose nhiều blocks/content sources. Caching giảm latency và load, nhưng freshness trở thành distributed responsibility.

## 3. How does it work?

```text
Browser -> CDN -> App -> Optimizely cache -> Content store
```

Publish trong CMS có thể invalidate CMS cache nhưng edge CDN vẫn còn representation cũ cho tới TTL/purge.

## 4. Practical implementation

```csharp
if (context.Response.StatusCode == 200 &&
    context.Request.Path.StartsWithSegments("/content"))
{
    context.Response.Headers.CacheControl =
        "public,max-age=60,s-maxage=300";
}
```

Trong thực tế policy phải xét authentication, personalization, locale, content type và preview mode.

## 5. Real production scenario

Editor publish legal disclaimer. Preview và origin đã mới nhưng Akamai vẫn trả old content. Nếu chỉ kiểm tra CMS, team dễ kết luận publish bị lỗi dù root cause nằm ở edge TTL/purge.

## 6. Failure scenario & troubleshooting

**Symptom** → editor thấy mới, public user thấy cũ. **Evidence** → origin response mới nhưng CDN cache-hit/`Age` lớn. **Fix** → targeted purge hoặc policy TTL phù hợp. **Verification** → kiểm tra response headers và content version qua edge.

## 7. Common mistakes

Public-cache personalized page; purge toàn site mỗi publish; cache key thiếu locale/variant; preview đi qua public cache; không có hit/miss observability.

## 8. Alternatives

Short TTL, event-driven targeted purge, stale-while-revalidate hoặc bypass cache cho dynamic/personalized fragments.

## 9. Trade-offs

### Advantages

Giảm origin load và tăng global performance.

### Costs / Risks

Invalidation nhiều layer khó debug; cache key sai có thể trở thành correctness/security issue; purge-all gây miss storm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một page có thể được cache ở nhiều tầng.

### Middle

Biết đọc cache headers và xác định layer đang stale.

### Senior

Thiết kế cache key, invalidation và personalization-safe behavior.

### Technical Lead / Architect

Đặt ownership cho publish → purge flow và freshness SLO theo content type.

## 11. Key takeaway

* CMS publish không đồng nghĩa mọi cache layer đã fresh.
* Cache key correctness quan trọng ngang TTL.
* Targeted invalidation tốt hơn purge-all khi dependency model đủ chính xác.
