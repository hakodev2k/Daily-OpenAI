# 1. C# `Task.WhenAll`: exception semantics và bounded fan-out trong production

## 1. What is it?

`Task.WhenAll` tạo một task hoàn thành khi toàn bộ tasks đầu vào hoàn thành. Mental model quan trọng: nó giúp phối hợp các asynchronous operations độc lập; nó không tự giới hạn concurrency và cũng không biến mọi workload thành nhanh hơn.

## 2. Why does it exist?

Nếu ba I/O calls độc lập được `await` tuần tự, latency gần bằng tổng thời gian của chúng. Khởi chạy đồng thời rồi `await Task.WhenAll` có thể đưa latency gần về operation chậm nhất. Nhưng với danh sách lớn, fan-out không giới hạn có thể phá connection pool, rate limit hoặc downstream capacity.

## 3. How does it work?

```text
start A ─────┐
start B ─────┼─> Task.WhenAll -> continue
start C ─────┘
```

Nếu một hoặc nhiều tasks fault, aggregate task fault. Khi `await`, exception được rethrow theo async semantics; muốn điều tra toàn bộ failures cần giữ reference tới tasks/aggregate và quan sát trạng thái, không chỉ log exception đầu tiên rồi kết luận.

## 4. Practical implementation

```csharp
var gate = new SemaphoreSlim(8);

var tasks = ids.Select(async id =>
{
    await gate.WaitAsync(ct);
    try
    {
        return await client.GetProductAsync(id, ct);
    }
    finally
    {
        gate.Release();
    }
});

var products = await Task.WhenAll(tasks);
```

`SemaphoreSlim` ở đây là concurrency budget; con số 8 phải dựa trên downstream capacity và load test, không phải magic number.

## 5. Real production scenario

Một product page cần enrich 30 SKUs từ remote pricing service. Fan-out 30 requests cho mỗi incoming request khiến 200 concurrent users tạo hàng nghìn outbound calls. Bounded concurrency giữ throughput ổn định hơn dù một request riêng lẻ có thể chậm hơn vài milliseconds.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 tăng mạnh, outbound timeout và `429` xuất hiện sau khi “parallelize” code. **Evidence** → trace cho thấy số concurrent dependency calls tăng đột biến. **Hypothesis** → unbounded fan-out. **Diagnosis** → đo active requests, connection pool, rate-limit responses. **Fix** → giới hạn concurrency, batch nếu API hỗ trợ, propagate cancellation. **Verification** → load test lại và so p95/p99 cùng dependency error rate.

## 7. Common mistakes

Tạo hàng nghìn tasks rồi `WhenAll`; dùng parallelism cho operations có dependency; bỏ `CancellationToken`; assume `WhenAll` fail-fast sẽ cancel tasks còn lại; log một exception rồi bỏ mất context của các failures khác.

## 8. Alternatives

`Parallel.ForEachAsync` cung cấp bounded parallelism tự nhiên hơn cho collection processing. `Channel<T>` phù hợp producer/consumer dài hạn. Sequential await đơn giản hơn khi volume nhỏ hoặc downstream nhạy cảm.

## 9. Trade-offs

### Advantages

Giảm wall-clock latency cho I/O độc lập và tận dụng concurrency.

### Costs / Risks

Tăng pressure lên sockets, pools, rate limits và downstream services; failure surface lớn hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu concurrency khác parallel CPU execution và `WhenAll` không giới hạn concurrency.

### Middle

Biết fan-out các I/O độc lập, propagate cancellation và xử lý lỗi đúng.

### Senior

Đặt concurrency budget dựa trên capacity, timeout và dependency behavior.

### Technical Lead / Architect

Quyết định khi nào fan-out trực tiếp, batch, queue hoặc cache; xem downstream capacity là một phần của end-to-end design.

## 11. Key takeaway

- `Task.WhenAll` là coordination primitive, không phải concurrency limiter.
- Tối ưu latency phải đi cùng downstream capacity budget.
- Đo p95/p99 và failure rate sau thay đổi, không chỉ benchmark happy path.

# 2. ASP.NET Core Request Timeout: deadline propagation thay vì timeout rời rạc

## 1. What is it?

Request timeout là giới hạn thời gian một request được phép tiêu thụ trước khi hệ thống ngừng cố gắng hoàn thành nó. Mental model tốt hơn là deadline: mọi downstream operation phải biết phần time budget còn lại, thay vì mỗi layer tự đặt timeout độc lập.

## 2. Why does it exist?

Một request đã mất client hoặc vượt SLA vẫn có thể giữ thread, DB connection và outbound socket nếu server tiếp tục xử lý. Các timeout rời rạc 30s ở HTTP + 30s SQL + retries còn có thể biến SLA 5s thành một operation kéo dài hàng phút.

## 3. How does it work?

```text
Client deadline 5s
   ↓
ASP.NET Core request budget
   ↓ CancellationToken
Application
   ├─ SQL query
   └─ HTTP dependency
```

Timeout ở boundary phải propagate cancellation xuống EF Core, `HttpClient` và background work liên quan. Cancellation là cooperative: code/dependency phải thực sự quan sát token.

## 4. Practical implementation

```csharp
builder.Services.AddRequestTimeouts(options =>
{
    options.AddPolicy("api", TimeSpan.FromSeconds(5));
});

app.UseRequestTimeouts();

app.MapGet("/orders/{id}", async (
    Guid id, AppDbContext db, CancellationToken ct) =>
{
    var order = await db.Orders.AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    return order is null ? Results.NotFound() : Results.Ok(order);
}).WithRequestTimeout("api");
```

Outbound calls cũng cần nhận cùng hoặc budget nhỏ hơn deadline còn lại.

## 5. Real production scenario

Checkout API có SLA 3s nhưng inventory service đôi lúc treo 20s. Không có deadline propagation, request timeout ở proxy nhưng backend vẫn giữ connection và tiếp tục gọi SQL. Sau vài phút, pool exhaustion làm cả traffic khỏe mạnh thất bại.

## 6. Failure scenario & troubleshooting

**Symptom** → client thấy timeout 5s nhưng server dependency spans kéo dài 30s. **Evidence** → traces tồn tại sau request span. **Hypothesis** → token không được propagate hoặc library không hỗ trợ cancellation. **Diagnosis** → trace call chain và kiểm tra API signatures. **Fix** → truyền token, đặt dependency timeout nhỏ hơn overall budget, tránh detached work. **Verification** → fault injection cho dependency và quan sát resource release.

## 7. Common mistakes

Chỉ timeout ở reverse proxy; catch `OperationCanceledException` rồi tiếp tục; retry sau khi deadline gần hết; dùng một timeout cho mọi endpoint; tạo background task từ request nhưng giữ scoped services.

## 8. Alternatives

Per-dependency timeout vẫn cần thiết như guardrail. Queue/background workflow phù hợp operations không thể hoàn thành trong interactive SLA. Circuit Breaker giúp tránh gọi dependency đang lỗi nhưng không thay deadline.

## 9. Trade-offs

### Advantages

Giải phóng resources sớm, giới hạn tail latency và làm failure predictable hơn.

### Costs / Risks

Timeout quá ngắn tạo false failures; cancellation không tự rollback external side effects.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout là resource/correctness boundary, không chỉ UX.

### Middle

Propagate `CancellationToken` xuyên controller, EF Core và HTTP calls.

### Senior

Thiết kế nested timeout budgets, retries và idempotency cho side effects.

### Technical Lead / Architect

Đặt end-to-end latency budget theo SLO và quyết định workflow nào phải chuyển asynchronous.

## 11. Key takeaway

- Deadline phải xuyên toàn call chain.
- Timeout không tự cancel side effects đã xảy ra.
- Retry chỉ hợp lý khi còn đủ time budget và operation retry-safe.

# 3. EF Core `DbContext` pooling: giảm setup cost nhưng không được leak request state

## 1. What is it?

`AddDbContextPool` tái sử dụng `DbContext` instances sau khi EF Core reset internal state. Nó khác database connection pooling: một cái reuse context object, cái kia reuse physical DB connections.

## 2. Why does it exist?

Ở throughput cao, tạo context và internal EF services lặp lại có allocation/setup cost. Pooling có thể giảm overhead khi profiling cho thấy context creation đáng kể; với phần lớn CRUD apps, SQL và network vẫn lớn hơn nhiều.

## 3. How does it work?

```text
Request A -> rent DbContext -> use -> reset -> return pool
Request B -> rent same instance -> use -> reset -> return pool
```

Vì instance được reuse, request-specific mutable state đặt trực tiếp trên context có nguy cơ leak nếu không được thiết kế đúng.

## 4. Practical implementation

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));

public sealed class OrderService(AppDbContext db)
{
    public Task<OrderDto?> GetAsync(Guid id, CancellationToken ct) =>
        db.Orders.AsNoTracking()
          .Where(x => x.Id == id)
          .Select(x => new OrderDto(x.Id, x.Status))
          .SingleOrDefaultAsync(ct);
}
```

Tenant/request context nên được truyền vào query/service boundary thay vì giữ mutable field tùy request trên pooled context.

## 5. Real production scenario

Multi-tenant SaaS thêm `TenantId` property mutable vào custom `DbContext` và dùng global query filter. Sau khi bật pooling, bug cấu hình khiến context được reuse với tenant cũ. Đây là data-isolation incident nghiêm trọng hơn mọi allocation benefit.

## 6. Failure scenario & troubleshooting

**Symptom** → hiếm khi request tenant A thấy dữ liệu tenant B. **Evidence** → xảy ra chỉ khi pooling bật, correlation logs cho thấy context reused. **Hypothesis** → request state sống lâu hơn request. **Diagnosis** → audit mutable fields/interceptors/query filters. **Fix** → đưa tenant state vào scoped abstraction/factory an toàn. **Verification** → high-concurrency isolation tests với nhiều tenants.

## 7. Common mistakes

Nhầm context pool với connection pool; bật pooling trước profiling; lưu user/tenant/request ID trong context instance; assume reset xử lý mọi custom mutable state; giữ context ngoài scoped operation.

## 8. Alternatives

`AddDbContext` đơn giản và an toàn hơn cho đa số applications. `IDbContextFactory<T>` phù hợp background/concurrent scopes. Tối ưu SQL/query round trips thường đem lại lợi ích lớn hơn context pooling.

## 9. Trade-offs

### Advantages

Giảm allocation/setup overhead của EF Core trong hot workloads.

### Costs / Risks

State leakage risk và cognitive complexity tăng; lợi ích nhỏ nếu bottleneck ở database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt `DbContext` lifetime với DB connection lifetime.

### Middle

Dùng scoped context đúng và viết query không phụ thuộc mutable request state.

### Senior

Profile allocation, audit interceptors/query filters và test concurrency isolation.

### Technical Lead / Architect

Chỉ bật pooling khi evidence đủ mạnh và threat model/data isolation được kiểm chứng.

## 11. Key takeaway

- `DbContext` pooling và connection pooling là hai cơ chế khác nhau.
- Reuse object làm mutable request state trở thành rủi ro.
- Tối ưu EF setup chỉ sau khi đo bottleneck thực tế.

# 4. SQL Server sargability: khi một predicate nhỏ phá index seek và tăng I/O

## 1. What is it?

Sargable predicate là điều kiện mà optimizer có thể dùng hiệu quả để tìm range trong index. Function hoặc implicit conversion đặt lên indexed column thường khiến engine khó seek và phải scan nhiều dữ liệu hơn.

## 2. Why does it exist?

Index được sắp xếp theo key. Predicate phải có hình dạng cho phép engine xác định key range. `YEAR(CreatedAt) = 2026` mô tả kết quả của function trên từng row, trong khi range trực tiếp mô tả vị trí cần đọc.

## 3. How does it work?

Bad:

```sql
WHERE YEAR(CreatedAt) = 2026
```

Better:

```sql
WHERE CreatedAt >= '20260101'
  AND CreatedAt <  '20270101'
```

Với index trên `CreatedAt`, dạng range có thể cho Index Seek và giảm logical reads đáng kể.

## 4. Practical implementation

```sql
SET STATISTICS IO, TIME ON;

SELECT Id, CustomerId, CreatedAt
FROM dbo.Orders
WHERE CreatedAt >= @from
  AND CreatedAt < @to;
```

So sánh actual execution plan, logical reads, CPU và elapsed time trước/sau. Đừng kết luận chỉ dựa vào icon “Seek”.

## 5. Real production scenario

Reporting endpoint chạy tốt với 100k orders nhưng chậm khi bảng lên 50 triệu rows. Predicate dùng `CONVERT(date, CreatedAt) = @date`, làm scan hàng triệu pages mỗi request dù đã có index.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 DB latency tăng theo table size. **Evidence** → high logical reads và scan trong actual plan. **Hypothesis** → non-sargable predicate. **Diagnosis** → kiểm tra scalar functions/conversions và parameter data types. **Fix** → rewrite predicate thành range hoặc computed/indexed design khi cần. **Verification** → plan mới, I/O giảm và latency ổn định dưới production-like data volume.

## 7. Common mistakes

Thêm index mới nhưng giữ predicate non-sargable; implicit convert vì parameter type khác column; dùng leading wildcard `%term`; chỉ nhìn duration trên dev database nhỏ; assume mọi Index Seek đều rẻ.

## 8. Alternatives

Persisted computed column có index phù hợp nếu business query thật sự cần transformed value. Full-text search phù hợp text search. Table scan có thể đúng với low-selectivity query hoặc bảng nhỏ.

## 9. Trade-offs

### Advantages

Sargable predicates tận dụng existing index tốt hơn mà không nhất thiết thêm storage.

### Costs / Risks

Query rewrite có thể phức tạp hơn; thêm computed index tăng write/storage cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu function trên indexed column có thể làm index khó sử dụng.

### Middle

Đọc basic plan và `STATISTICS IO` để xác nhận.

### Senior

Reason về selectivity, parameter types, statistics, I/O và locks thay vì chỉ “add index”.

### Technical Lead / Architect

Thiết kế query/index contract theo access patterns và cân bằng read benefit với write/storage cost.

## 11. Key takeaway

- Query shape quyết định khả năng dùng index.
- Đo logical reads và actual plan, không đoán từ SQL text.
- Index mới không chữa được mọi access pattern xấu.

# 5. Anti-Corruption Layer: bảo vệ domain khỏi contract của hệ thống bên ngoài

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary dịch model/protocol của external hoặc legacy system sang model mà bounded context của mình hiểu. Nó bảo vệ domain language khỏi bị vendor DTO, legacy status codes và integration quirks lan khắp codebase.

## 2. Why does it exist?

Nếu application dùng trực tiếp `LegacyCustomerDto` ở domain, mọi thay đổi schema hoặc semantics bên ngoài xuyên qua toàn hệ thống. Coupling không chỉ là class reference mà còn là business meaning.

## 3. How does it work?

```text
Our Domain -> Port -> ACL Adapter -> Legacy/Partner API
                       |
                  translate models,
                  errors, semantics
```

Domain sở hữu interface/port. Infrastructure adapter phụ thuộc outward vào remote contract. Transaction ownership vẫn ở từng system; ACL không tạo distributed transaction.

## 4. Practical implementation

```csharp
public interface ICreditProfileGateway
{
    Task<CreditProfile> GetAsync(CustomerId id, CancellationToken ct);
}

internal sealed class LegacyCreditAdapter(HttpClient http)
    : ICreditProfileGateway
{
    public async Task<CreditProfile> GetAsync(CustomerId id, CancellationToken ct)
    {
        var dto = await http.GetFromJsonAsync<LegacyCreditDto>(
            $"credit/{id.Value}", ct) ?? throw new InvalidOperationException();

        return new CreditProfile(
            dto.RiskCode switch { "L" => Risk.Low, "H" => Risk.High, _ => Risk.Unknown });
    }
}
```

## 5. Real production scenario

Legacy CRM dùng `A/I/D` cho customer state; new platform dùng domain states khác. ACL centralizes mapping và failure semantics. Khi CRM thêm code mới, chỉ integration boundary cần thay đổi thay vì hàng chục domain handlers.

## 6. Failure scenario & troubleshooting

**Symptom** → business logic đầy checks theo vendor-specific codes. **Evidence** → external DTO referenced trong Domain/Application projects. **Hypothesis** → boundary bị thủng. **Diagnosis** → dependency graph và code search. **Fix** → define domain-facing port, move translation vào adapter. **Verification** → domain tests không cần vendor DTO/package.

## 7. Common mistakes

ACL chỉ rename fields nhưng giữ nguyên semantics; đặt domain model phụ thuộc SDK vendor; swallow integration errors thành default business values; xây generic “integration framework” quá sớm.

## 8. Alternatives

Direct integration đơn giản hơn nếu contract nhỏ, stable và semantics gần domain. Shared Kernel phù hợp khi hai bounded contexts thực sự đồng sở hữu model, nhưng coupling cao hơn.

## 9. Trade-offs

### Advantages

Change isolation, domain language sạch hơn, testability và vendor migration tốt hơn.

### Costs / Risks

Thêm mapping code, ownership và nguy cơ duplicated concepts nếu boundary không cần thiết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain entity.

### Middle

Implement adapter, mapping và tests cho contract translation.

### Senior

Thiết kế error/failure semantics, timeout, versioning và observability tại boundary.

### Technical Lead / Architect

Xác định bounded-context ownership, dependency direction và khi direct integration đơn giản hơn ACL.

## 11. Key takeaway

- ACL bảo vệ business semantics, không chỉ che HTTP client.
- Domain nên sở hữu language của mình.
- Không thêm boundary nếu external contract nhỏ và coupling chấp nhận được.

# 6. Azure Functions cold start: latency, scaling và lựa chọn hosting model

## 1. What is it?

Cold start là latency khi platform phải tạo/warm một Functions host instance trước khi function xử lý request. Nó gồm provisioning/runtime startup, app initialization và dependency setup; mức ảnh hưởng phụ thuộc hosting plan, runtime và workload.

## 2. Why does it exist?

Serverless tiết kiệm capacity bằng elastic scale và có thể scale xuống khi idle ở một số hosting modes. Đổi lại, request đầu tiên sau idle/scale-out có thể trả chi phí startup thay vì luôn có warm process chờ sẵn.

## 3. How does it work?

```text
Event/HTTP -> scale decision -> new host -> runtime/app init -> invoke
                                      ^ cold-start path
```

Scale-out còn tạo nhiều cold instances đồng thời. Startup code, package size, DI graph và network dependencies có thể làm latency lớn hơn platform baseline.

## 4. Practical implementation

```csharp
var host = new HostBuilder()
    .ConfigureFunctionsWorkerDefaults()
    .ConfigureServices(services =>
    {
        services.AddHttpClient<ProductClient>();
        // Avoid remote I/O during service registration/startup.
    })
    .Build();

await host.RunAsync();
```

Giữ startup deterministic và tránh tải dữ liệu remote lớn trước khi host có thể phục vụ.

## 5. Real production scenario

Webhook HTTP Function có traffic burst sau nhiều phút idle. p50 tốt nhưng p99 cao ở burst đầu, làm provider retry và tạo duplicate deliveries. Hosting choice và idempotency đều quan trọng; chỉ “optimize code” không giải quyết toàn bộ.

## 6. Failure scenario & troubleshooting

**Symptom** → request đầu sau idle mất vài giây, request sau nhanh. **Evidence** → Application Insights cho thấy host startup/instance changes correlate với tail latency. **Hypothesis** → cold start. **Diagnosis** → tách startup time khỏi dependency latency. **Fix** → giảm startup work hoặc chọn plan/warm capacity phù hợp SLA. **Verification** → test sau idle và trong scale-out burst, không chỉ steady-state load.

## 7. Common mistakes

Đổ mọi latency cho cold start; thực hiện Key Vault/API calls blocking trong startup; chọn serverless chỉ vì “rẻ”; bỏ idempotency khi upstream retries; không đo p99.

## 8. Alternatives

App Service/Worker Service giữ process ổn định hơn cho always-on workloads. Container Apps phù hợp containerized event-driven workloads nhưng vẫn có scaling semantics. Dedicated/Premium-style capacity phù hợp khi latency/SLA yêu cầu warm instances.

## 9. Trade-offs

### Advantages

Elastic scaling, event integration và giảm operational management.

### Costs / Risks

Tail latency, platform-specific scaling behavior và cost có thể kém tối ưu với steady high load.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu serverless không có nghĩa “không có server/startup”.

### Middle

Giảm startup work và quan sát invocation/dependency telemetry.

### Senior

Phân tích p95/p99, burst behavior, retries và hosting-plan economics.

### Technical Lead / Architect

Chọn Functions hay App Service/Worker/Container Apps dựa trên workload shape, SLA, operational burden và cost.

## 11. Key takeaway

- Cold start là tail-latency problem, không nên đánh giá bằng average.
- Hosting model là architecture decision gắn với workload shape.
- Test cả idle-to-burst và scale-out, không chỉ warm steady state.

# 7. CI/CD database migration: expand-contract để release không biến schema thành single point of failure

## 1. What is it?

Expand-contract là cách thay đổi schema theo nhiều bước backward-compatible: trước tiên mở rộng schema để old/new code cùng chạy, chuyển traffic/data, rồi mới xóa contract cũ.

## 2. Why does it exist?

Deployment thực tế không atomic: nhiều app instances có thể chạy version khác nhau trong rolling/slot/canary release. Migration `DROP/Rename` ngay có thể làm old instances crash dù application artifact hoàn toàn đúng.

## 3. How does it work?

```text
commit -> build -> test -> artifact
   -> expand schema
   -> deploy compatible app
   -> migrate/backfill
   -> health + monitor
   -> contract old schema later
```

Database là shared state nên rollback application không tự rollback schema/data an toàn.

## 4. Practical implementation

Ví dụ đổi `FullName` thành `GivenName` + `FamilyName`:

```sql
ALTER TABLE Customer ADD GivenName nvarchar(100) NULL;
ALTER TABLE Customer ADD FamilyName nvarchar(100) NULL;
```

Release 1 đọc/ghi tương thích cả schema cũ và mới; backfill dữ liệu; release sau chuyển hoàn toàn; chỉ khi không còn consumer cũ mới `DROP FullName`.

## 5. Real production scenario

Octopus deploy 8 IIS nodes theo rolling strategy. Nếu migration rename column chạy trước node cuối cùng được nâng cấp, node cũ trả 500. Expand-contract cho phép mixed-version window an toàn.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment app rollback nhưng Production vẫn lỗi. **Evidence** → schema migration đã drop column và không reversible với dữ liệu hiện tại. **Hypothesis** → destructive migration coupling. **Diagnosis** → compare app versions với schema compatibility. **Fix** → restore compatibility bằng additive migration/hotfix; tránh rollback destructive data blindly. **Verification** → old/new version integration tests trên cùng schema.

## 7. Common mistakes

Chạy migration destructive cùng artifact; assume rollback code = rollback database; long blocking DDL trong peak traffic; không test migration trên production-scale data; mỗi app instance tự migrate khi startup.

## 8. Alternatives

Maintenance window phù hợp hệ nhỏ chấp nhận downtime. Blue-Green database riêng cực phức tạp với shared writes. Feature flags có thể tách code activation khỏi schema rollout.

## 9. Trade-offs

### Advantages

Zero/low-downtime release, rollback flexibility và mixed-version safety.

### Costs / Risks

Nhiều release steps, temporary duplicated schema/code và cần cleanup discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu schema thay đổi độc lập với binary deployment.

### Middle

Viết additive migrations và integration tests.

### Senior

Thiết kế backfill, lock impact, backward compatibility và rollback path.

### Technical Lead / Architect

Định nghĩa release protocol, ownership và policy cho destructive migrations trên toàn hệ thống.

## 11. Key takeaway

- Database migration là production release engineering.
- Add trước, migrate traffic/data, remove sau.
- Rollback application không đồng nghĩa rollback dữ liệu.

# 8. `dotnet-counters` và EventCounters: điều tra CPU, GC và ThreadPool trước khi đoán

## 1. What is it?

`dotnet-counters` là diagnostic tool đọc runtime/application counters từ process .NET. Nó cung cấp low-overhead signals như CPU, GC heap, allocation rate, exception rate và ThreadPool để localize bottleneck trước khi dùng profiler/dump nặng hơn.

## 2. Why does it exist?

CPU 90% hoặc API chậm không cho biết root cause. Có thể là allocation/GC, ThreadPool starvation, exception storm hay application CPU work. Counters giúp chuyển từ symptom sang evidence nhanh.

## 3. How does it work?

```text
symptom
  ↓
dotnet-counters
  ├─ CPU
  ├─ GC / allocation
  ├─ ThreadPool queue/thread count
  └─ exceptions
  ↓
hypothesis -> profiler/trace/dump if needed
```

Counters là time-series indicators, không tự chỉ ra method nào gây CPU.

## 4. Practical implementation

```bash
dotnet-counters monitor --process-id 1234 System.Runtime
```

Khi memory tăng, quan sát GC heap size và allocation rate. Khi latency tăng với CPU thấp, quan sát ThreadPool queue length/thread count và dependency telemetry trước khi kết luận database chậm.

## 5. Real production scenario

Sau release, p99 tăng nhưng SQL vẫn nhanh. Counters cho thấy ThreadPool queue tăng trong khi CPU trung bình. Code review tìm thấy `.Result` trên outbound HTTP trong hot path; sync-over-async gây starvation.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng. **Evidence** → heap size tăng nhưng allocation rate không bất thường. **Hypothesis** → long-lived retention thay vì churn. **Diagnosis** → counters chỉ localize; tiếp tục `dotnet-gcdump`/`dotnet-dump` để xem retained types/roots. **Fix** → sửa owner/lifetime. **Verification** → soak test và heap plateau sau GC cycles.

## 7. Common mistakes

Dùng counters như root-cause proof; chỉ nhìn average CPU; collect không đúng process/container; restart app trước khi capture evidence; bỏ correlation với deployment và traffic.

## 8. Alternatives

Application Insights/OpenTelemetry tốt cho distributed request/dependency view. `dotnet-trace` và profiler cung cấp method-level detail. Memory dump phù hợp retention/leak investigation nhưng cost cao hơn.

## 9. Trade-offs

### Advantages

Nhanh, low overhead và rất hữu ích cho first-pass triage.

### Costs / Risks

Không có call-stack/root detail đầy đủ; interpretation sai dễ dẫn tới false diagnosis.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết các runtime signals cơ bản thay vì restart process ngay.

### Middle

Capture counters và correlate với request symptoms.

### Senior

Chọn bước diagnostic tiếp theo dựa trên evidence: trace, profile hay dump.

### Technical Lead / Architect

Chuẩn hóa incident runbook, baseline và telemetry để team có evidence trước remediation.

## 11. Key takeaway

- Counters giúp localize bottleneck, không thay root-cause analysis.
- Baseline khỏe mạnh quan trọng để biết số hiện tại có bất thường hay không.
- Capture evidence trước restart khi điều kiện cho phép.

# 9. CORS: browser trust policy không phải API authentication

## 1. What is it?

CORS là cơ chế browser quyết định JavaScript từ origin nào được phép đọc response cross-origin. Nó không ngăn `curl`, backend service hay attacker gửi request trực tiếp tới API.

## 2. Why does it exist?

Same-Origin Policy bảo vệ browser user khỏi trang web tùy ý đọc dữ liệu từ origin khác. CORS cho server nới policy có kiểm soát cho trusted frontend origins.

## 3. How does it work?

Với request cần preflight:

```text
Browser -> OPTIONS /api
Server  -> Access-Control-Allow-Origin/Methods/Headers
Browser -> actual request nếu policy cho phép
```

Authorization vẫn phải được API thực hiện bằng token/cookie/claims/policy.

## 4. Practical implementation

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("frontend", policy =>
        policy.WithOrigins("https://app.example.com")
              .AllowAnyHeader()
              .AllowAnyMethod());
});

app.UseCors("frontend");
app.UseAuthentication();
app.UseAuthorization();
```

Nếu dùng credentials/cookies, origin policy cần explicit và CSRF/SameSite design phải được xem riêng.

## 5. Real production scenario

SPA Production đổi domain nhưng API CORS config chưa update. Browser báo CORS error dù API trả 200 khi test bằng Postman. Đây là browser policy mismatch, không phải network/API authentication failure.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend không đọc được response, Postman hoạt động. **Evidence** → DevTools Network cho thấy preflight thiếu/không khớp `Access-Control-Allow-Origin`. **Hypothesis** → CORS config/order. **Diagnosis** → kiểm tra origin chính xác gồm scheme/host/port và preflight response. **Fix** → allow explicit trusted origin/method/header. **Verification** → browser test từ allowed và disallowed origins.

## 7. Common mistakes

Dùng CORS như authentication; `AllowAnyOrigin` theo thói quen; nhầm server-to-server error với CORS; cho credentials với policy quá rộng; disable browser security để “fix”.

## 8. Alternatives

Same-origin deployment/reverse proxy tránh cross-origin requirement. Backend-for-Frontend có thể giảm browser integration complexity nhưng thêm component. Không có alternative nào thay authorization của API.

## 9. Trade-offs

### Advantages

Cho phép browser integrations cross-origin có kiểm soát.

### Costs / Risks

Configuration dễ sai và tạo false sense of security; credentialed flows cần threat model kỹ hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Nhớ CORS là browser policy, không phải access control cho API.

### Middle

Debug preflight bằng DevTools và configure explicit origins.

### Senior

Kết nối CORS với cookie, CSRF, SameSite và frontend deployment topology.

### Technical Lead / Architect

Quyết định same-origin/BFF/cross-origin architecture và security boundary rõ ràng.

## 11. Key takeaway

- CORS không thay authentication/authorization.
- Debug CORS trong browser/preflight, không chỉ Postman.
- Credentialed cross-origin requests cần thiết kế CSRF/cookie riêng.

# 10. React render và memoization: tối ưu dựa trên profiling thay vì phủ `useMemo` khắp UI

## 1. What is it?

React render là quá trình component function chạy để tạo representation UI mới; render không đồng nghĩa DOM luôn bị thay đổi. `memo`, `useMemo` và `useCallback` có thể tránh một số work nhưng bản thân chúng cũng thêm comparison, dependency và cognitive cost.

## 2. Why does it exist?

UI state thay đổi thường xuyên và component tree có thể lớn. Memoization hữu ích khi expensive calculation hoặc child render thực sự là bottleneck. Nếu áp dụng mù quáng, code phức tạp hơn mà performance không cải thiện.

## 3. How does it work?

```text
state/props change
    ↓
component render
    ↓
reconciliation
    ↓
commit only necessary DOM changes
```

Referential identity quan trọng với memoized children: tạo object/function mới mỗi render có thể làm shallow comparison không giúp được.

## 4. Practical implementation

```tsx
const visibleOrders = useMemo(
  () => expensiveFilter(orders, filter),
  [orders, filter]
);

const onSelect = useCallback((id: string) => {
  setSelectedId(id);
}, []);
```

Chỉ giữ optimization nếu React Profiler chứng minh calculation/render này đáng kể.

## 5. Real production scenario

Admin dashboard lag khi gõ filter. Network không có request mới; React Profiler cho thấy bảng 5.000 rows re-render và chạy expensive transformation mỗi keystroke. Memoization hoặc virtualization đúng điểm giảm interaction latency.

## 6. Failure scenario & troubleshooting

**Symptom** → thêm `useMemo` khắp nơi nhưng UI vẫn chậm. **Evidence** → profiler cho thấy bottleneck là 5.000 DOM nodes hoặc network waterfall, không phải calculation. **Hypothesis** → tối ưu sai layer. **Diagnosis** → measure render duration, commits và network. **Fix** → virtualization/pagination hoặc API/query optimization. **Verification** → đo interaction latency lại.

## 7. Common mistakes

Memoize primitive calculations rẻ; dependency array sai tạo stale value; dùng `useCallback` cho mọi handler; ignore list keys; tối ưu render trong khi API là bottleneck; đo bằng cảm giác.

## 8. Alternatives

Component decomposition có thể cô lập state updates. Virtualization phù hợp large lists. Server pagination giảm cả network và render load. Đôi khi không tối ưu gì là lựa chọn đúng nếu profiler cho thấy cost nhỏ.

## 9. Trade-offs

### Advantages

Giảm expensive recomputation/render khi dependency ổn định và bottleneck đã được chứng minh.

### Costs / Risks

Code khó đọc hơn, stale dependency bugs và overhead comparison/cache.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu render không đồng nghĩa DOM rewrite toàn bộ.

### Middle

Dùng Profiler và memoization đúng dependency.

### Senior

Phân biệt CPU render, DOM size, network và state architecture bottlenecks.

### Technical Lead / Architect

Giữ performance strategy end-to-end: API pagination, caching, component boundaries và UX budgets thay vì local micro-optimization.

## 11. Key takeaway

- Profile trước khi memoize.
- Tối ưu đúng bottleneck: calculation, render, DOM hay network.
- Simpler code là lựa chọn tốt khi performance đã đạt budget.
