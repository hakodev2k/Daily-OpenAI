## 1. C# / .NET — `ValueTask<T>` là optimization có điều kiện, không phải `Task<T>` “nhanh hơn”

### Mental model
`Task<T>` là reference type đại diện cho asynchronous completion và có semantics đơn giản: có thể await nhiều lần, cache, truyền qua nhiều layer. `ValueTask<T>` là struct có thể chứa trực tiếp kết quả synchronous hoặc wrap một `Task<T>`/`IValueTaskSource<T>`.

```csharp
public ValueTask<User?> GetCachedAsync(int id, CancellationToken ct)
{
    if (_cache.TryGetValue(id, out var user))
        return ValueTask.FromResult<User?>(user);

    return new ValueTask<User?>(LoadAsync(id, ct));
}
```

### Khi nào nó có lợi
Nếu method nằm trên hot path và **thường hoàn tất synchronously**, `ValueTask<T>` có thể tránh allocation của `Task<T>` cho fast path. Ví dụ điển hình là buffer/channel/cache primitives.

### Cost bị bỏ qua
`ValueTask<T>` lớn hơn một reference và consumer phải tuân thủ contract chặt hơn. Với một số backing source, await nhiều lần, gọi `AsTask()` tùy tiện hoặc dùng sau khi source được recycle có thể sai. Nếu operation hầu như luôn asynchronous, lợi ích allocation thường biến mất trong khi API phức tạp hơn.

### Engineering judgment
Mặc định dùng `Task`/`Task<T>`. Chỉ chuyển sang `ValueTask<T>` khi profiling chứng minh allocation của async result là đáng kể và synchronous-completion rate đủ cao. Optimization ở API surface có maintenance cost lâu dài.

### Review checklist
- Fast path có thật sự synchronous và thường xuyên không?
- Call site có cần cache/combine/await nhiều lần không?
- Benchmark có đo allocation lẫn throughput không?
- Có đang tối ưu trước khi profiling không?

## 2. ASP.NET Core — `HttpClientFactory` giải quyết handler lifetime, nhưng không tự giải quyết resilience

### Mental model
Tạo/dispose `HttpClient` cho từng request có thể dẫn tới connection churn; giữ một handler quá lâu lại có thể làm DNS changes không được phản ánh đúng. `IHttpClientFactory` quản lý handler pooling/lifetime và cho phép cấu hình client theo downstream dependency.

```csharp
builder.Services.AddHttpClient<InventoryClient>(client =>
{
    client.BaseAddress = new Uri(configuration["Inventory:BaseUrl"]!);
    client.Timeout = TimeSpan.FromSeconds(2);
});
```

### Boundary quan trọng
Một typed client nên biểu diễn contract với **một dependency cụ thể**, không phải generic wrapper quanh mọi HTTP call. Điều này cho phép timeout, auth, telemetry và resilience policy bám theo đặc tính của dependency đó.

### Resilience không phải retry mọi thứ
Retry một `GET` transient failure có thể hợp lý. Retry `POST /payments` không có idempotency có thể tạo duplicate side effect. Timeout, retry, circuit breaker và rate limiter phải được thiết kế cùng latency budget và semantics của operation.

### Production failure
Một downstream đang overload trả 503. Nếu 20 API instances mỗi instance retry 3 lần ngay lập tức, hệ thống có thể khuếch đại load đúng lúc dependency yếu nhất. Exponential backoff + jitter và retry budget thường quan trọng hơn số retry lớn.

### Engineering judgment
`HttpClientFactory` là connection-management primitive; resilience là system-design problem. Review outbound call theo dependency, idempotency, deadline, concurrency và failure amplification.

## 3. EF Core — `ExecuteUpdateAsync`/`ExecuteDeleteAsync` thay đổi dữ liệu mà không đi qua Change Tracker

### Problem
Load hàng nghìn entity chỉ để đổi một field tạo query + materialization + tracking + nhiều update không cần thiết:

```csharp
var expired = await db.Sessions
    .Where(x => x.ExpiresAt < now)
    .ToListAsync(ct);

foreach (var session in expired)
    session.Status = SessionStatus.Expired;

await db.SaveChangesAsync(ct);
```

Set-based update phù hợp hơn:

```csharp
await db.Sessions
    .Where(x => x.ExpiresAt < now)
    .ExecuteUpdateAsync(s => s
        .SetProperty(x => x.Status, SessionStatus.Expired), ct);
```

### Điều thực sự thay đổi
Operation chạy trực tiếp trên database và **không đồng bộ state của entity đang tracked trong `DbContext`**. Nếu cùng context đã load một `Session`, object trong memory có thể vẫn mang giá trị cũ.

### Trade-off
Set-based DML giảm round trips và allocations, rất tốt cho bulk state transition. Nhưng domain hooks, per-entity validation hoặc logic nằm trong entity setter không tự chạy. Đây là lý do không nên thay `SaveChanges` bằng bulk API một cách cơ học.

### Engineering judgment
Dùng set-based operation khi rule có thể biểu diễn an toàn ở database predicate/update expression. Nếu invariant cần domain orchestration trên từng aggregate, materialization có thể là chi phí cần thiết.

### Test checklist
- Test predicate trên production-like data.
- Kiểm tra tracked state nếu context còn được reuse.
- Xác minh concurrency/audit semantics.
- Đo affected-row count nếu đó là invariant quan trọng.

## 4. SQL — SARGability quyết định optimizer có thể tận dụng index hiệu quả hay không

### Mental model
Predicate có index không đồng nghĩa query dùng index hiệu quả. Nếu biến đổi indexed column trước khi so sánh, database có thể phải scan nhiều dữ liệu hơn.

Không tốt:

```sql
WHERE CAST(CreatedAt AS date) = @date
```

Thường tốt hơn:

```sql
WHERE CreatedAt >= @date
  AND CreatedAt < DATEADD(day, 1, @date)
```

### Tại sao
Dạng range giữ column ở dạng có thể seek theo ordered index. Tương tự, `LOWER(Name) = ...`, arithmetic trên column hoặc implicit conversion có thể phá khả năng seek tùy engine/schema.

### Production implication
Một query chạy nhanh trên 20.000 rows có thể trở thành bottleneck ở 200 triệu rows. CPU tăng, logical reads tăng và buffer pool bị chiếm bởi dữ liệu không cần thiết. Sau đó vấn đề lan thành contention cho workload khác.

### Senior-level workflow
Không đoán từ LINQ/SQL text. Xem actual execution plan, estimated-vs-actual rows, seek/scan predicate, logical reads và implicit conversion warning. Index design và query shape phải được đánh giá cùng nhau.

### Review checklist
- Predicate có function/conversion trên indexed column không?
- Data type của parameter có khớp column không?
- Cardinality estimate có lệch lớn không?
- Composite index order có phù hợp filter + sort không?

## 5. MongoDB — Compound index tuân theo access pattern; thứ tự field là một quyết định query-planning

### Mental model
Index `{ tenantId: 1, status: 1, createdAt: -1 }` không tương đương mọi permutation của ba field. Với workload:

```javascript
db.orders.find({ tenantId: t, status: "Open" })
         .sort({ createdAt: -1 })
         .limit(50)
```

index trên có thể hỗ trợ equality filters trước rồi cung cấp ordering theo `createdAt` trong phạm vi phù hợp.

### ESR heuristic
Một heuristic hữu ích là **Equality → Sort → Range** khi thiết kế compound index. Đây không phải luật tuyệt đối; selectivity, query variants và optimizer behavior vẫn cần đo bằng `explain()`.

### Prefix behavior
Compound index có thể hỗ trợ các prefix nhất định. Nếu query thường bỏ `tenantId` nhưng filter `status`, index bắt đầu bằng `tenantId` có thể kém hữu ích. Điều này rất quan trọng trong multi-tenant schema: tenant scope thường nên xuất hiện nhất quán trong query và index.

### Trade-off
Mỗi index làm read nhanh hơn cho một số pattern nhưng tăng storage, memory pressure và write amplification. “Index mọi field” là cách chuyển latency từ read sang write và làm working set lớn hơn.

### Engineering judgment
Bắt đầu từ top query shapes và SLA, không từ document schema. Dùng `explain("executionStats")`, kiểm tra keys/docs examined và xác minh index thực sự phục vụ workload.

## 6. Redis — Distributed lock không biến distributed workflow thành transaction

### Problem framing
Một lock kiểu `SET key value NX PX ttl` có thể giúp giảm concurrent execution, nhưng không đảm bảo toàn bộ business operation trở thành exactly-once.

```text
Worker A acquires lock for 10s
→ operation stalls 12s
→ lock expires
→ Worker B acquires new lock
→ A resumes
```

Lúc này A và B có thể cùng thực hiện side effect nếu hệ thống không có cơ chế bảo vệ khác.

### Ownership token
Release lock phải kiểm tra token của owner, không đơn giản `DEL key`, để worker cũ không xóa lock mới của worker khác. Nhưng token vẫn không giải quyết stale owner thực hiện write sau khi lease hết hạn.

### Fencing token
Với resource hỗ trợ, monotonically increasing fencing token có thể giúp downstream từ chối writer cũ. Đây là protection mạnh hơn việc chỉ “tin lock”.

### Engineering judgment
Nếu invariant có thể enforce bằng database unique constraint, conditional update hoặc compare-and-swap, ưu tiên enforcement gần source of truth. Distributed lock phù hợp cho coordination/efficiency; correctness-critical invariant nên có lớp bảo vệ cuối cùng tại resource được mutate.

### Failure checklist
- Lock hết hạn giữa operation thì sao?
- Process pause/GC/network partition thì sao?
- Release có ownership check không?
- Side effect có idempotent/conditional không?
- Có metric cho contention và lock timeout không?

## 7. REST API Design — ETag biến cache validation và optimistic concurrency thành protocol-level contract

### Cache validation
Server trả:

```http
ETag: "order-42-v7"
```

Client có thể gửi:

```http
If-None-Match: "order-42-v7"
```

Nếu representation chưa đổi, server trả `304 Not Modified`, tránh gửi lại body.

### Concurrency control
Với update, client gửi:

```http
If-Match: "order-42-v7"
```

Nếu resource đã thành v8, server có thể trả `412 Precondition Failed` thay vì âm thầm overwrite state mới hơn.

### Strong vs weak validators
Strong ETag biểu diễn byte-equivalent representation theo semantics HTTP; weak ETag (`W/`) phù hợp khi representation semantically equivalent nhưng byte-level có thể khác. Concurrency write thường cần validator đủ mạnh để đại diện version mà business muốn bảo vệ.

### Architecture value
ETag đưa version contract ra boundary HTTP thay vì để client biết chi tiết `rowversion`/database implementation. Persistence token có thể thay đổi mà protocol semantics vẫn ổn định.

### Common mistakes
- Generate ETag từ timestamp có độ phân giải không đủ.
- Chấp nhận update khi thiếu `If-Match` dù API yêu cầu safe concurrent edit.
- Dùng representation hash đắt trên payload lớn mà không cân nhắc cost.
- Không test stale writer.

## 8. Security — Mass Assignment/Over-posting xuất hiện khi transport model được bind thẳng vào persistence model

### Scenario
Entity có field nội bộ:

```csharp
public sealed class User
{
    public Guid Id { get; set; }
    public string DisplayName { get; set; } = "";
    public bool IsAdmin { get; set; }
    public decimal CreditLimit { get; set; }
}
```

Nếu API bind trực tiếp entity từ JSON, client có thể gửi các property mà UI không hề hiển thị.

### Safer contract
Dùng command/request DTO chỉ chứa field được phép thay đổi:

```csharp
public sealed record UpdateProfileRequest(string DisplayName);
```

Sau đó application layer map explicit field vào aggregate/entity.

### Why it matters
Authorization không chỉ là “user có được gọi endpoint không?”. Còn có **field-level authorization** và invariant: user có quyền sửa thuộc tính nào của resource. Generic mapper hoặc patch operation có thể vô tình mở rộng write surface.

### Engineering judgment
DTO không chỉ để “clean architecture”; nó là security boundary và versioning boundary. Với admin endpoint, dùng contract riêng thay vì reuse public request rồi hy vọng authorization ở controller đủ bảo vệ.

### Test checklist
- Gửi thêm privileged fields trong JSON.
- Test role khác nhau trên cùng resource.
- Test nested object/collection over-posting.
- Review PATCH semantics và allowed paths.

## 9. Testing / QA — Property-based testing tìm invariant violation mà example-based tests dễ bỏ sót

### Mental model
Example test kiểm tra vài input do developer chọn. Property-based test sinh nhiều input và kiểm tra invariant luôn phải đúng.

Ví dụ pricing rule có property:

```text
Total(quantity, unitPrice, discount) >= 0
```

hoặc serialization round-trip:

```text
Deserialize(Serialize(x)) ≈ x
```

### Giá trị thực tế
Boundary bugs thường nằm ở combination mà developer không nghĩ tới: zero, max value, duplicate item, Unicode, empty collection, decimal rounding, ordering khác nhau. Generator mở rộng search space có hệ thống hơn vài `[InlineData]` thủ công.

### Shrinking
Framework property-based thường cố thu nhỏ failing input thành counterexample đơn giản. Thay vì báo lỗi với collection 200 phần tử, nó có thể tìm ra case tối thiểu 2 phần tử gây invariant fail, giúp debugging nhanh hơn.

### Không thay thế example tests
Business scenarios quan trọng vẫn cần example tests dễ đọc. Property tests phù hợp cho algebraic/domain invariants, parsers, transformations, serializers và state-machine behavior.

### Engineering judgment
Một test suite mạnh không đo bằng số test case mà bằng failure classes nó có khả năng phát hiện. Kết hợp examples cho intent + properties cho state space thường hiệu quả hơn tăng số lượng mock-based unit test.

## 10. Architecture / Reliability — Backpressure là cách hệ thống nói “tốc độ producer đang vượt capacity consumer”

### Problem
Nếu API nhận 10.000 jobs/giây nhưng worker chỉ xử lý 2.000 jobs/giây, queue tăng 8.000 jobs/giây. Queue không tạo capacity; nó chỉ dời thời điểm failure nếu overload kéo dài.

### Bounded channel trong .NET
Trong process, `Channel<T>` bounded có thể biểu diễn capacity rõ ràng:

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(1_000)
{
    FullMode = BoundedChannelFullMode.Wait
});
```

Khi đầy, producer phải chờ thay vì allocation/queue tăng vô hạn.

### Distributed systems
Với broker, backpressure có thể được thực hiện bằng consumer concurrency limit, prefetch limit, admission control, rate limiting hoặc trả `429/503` khi hệ thống không thể nhận thêm work an toàn. Cơ chế đúng phụ thuộc việc request có thể retry, queue có durable hay không và SLA là latency hay throughput.

### Capacity reasoning
Metric quan trọng không chỉ là queue length mà còn **oldest message age**, arrival rate, service rate và time-to-drain. Queue length 100.000 có thể bình thường nếu xử lý 50.000/s; queue 5.000 có thể nghiêm trọng nếu chỉ xử lý 10/s.

### Failure mode
Unbounded queue thường biến overload thành memory exhaustion hoặc latency hàng giờ. Retry không giới hạn còn tạo feedback loop làm arrival rate tăng thêm.

### Engineering judgment
Thiết kế overload behavior trước khi production bị overload: giới hạn ở đâu, ai bị reject, retry-after thế nào, priority nào được giữ và degradation mode nào chấp nhận được. Capacity limit rõ ràng thường an toàn hơn “cố nhận hết”.
