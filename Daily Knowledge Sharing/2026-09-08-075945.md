# 1. `CancellationToken` trong .NET: cooperative cancellation, linked tokens và ranh giới giữa cancel với failure

## 1. What is it?

`CancellationToken` là cơ chế cooperative cancellation trong .NET. Nó không “giết thread” hay dừng code từ bên ngoài. Thay vào đó, caller phát tín hiệu cancellation và code ở downstream chủ động kiểm tra hoặc truyền token xuống API hỗ trợ cancellation.

Mental model:

```text
caller requests cancellation
        ↓
CancellationToken becomes signaled
        ↓
downstream code observes token
        ↓
operation stops at a safe boundary
```

## 2. Why does it exist?

Request có thể bị client abort, application shutdown, timeout hoặc workflow bị superseded. Nếu backend tiếp tục query database, gọi external API và serialize response dù caller không còn chờ kết quả, hệ thống đang tiêu tốn tài nguyên vô ích.

Nhưng hard-abort arbitrary code rất nguy hiểm vì có thể cắt giữa transaction hoặc corrupt state. Cooperative cancellation tồn tại để operation tự dừng tại boundary an toàn.

## 3. How does it work?

Các API async thường nhận `CancellationToken`:

```csharp
await db.Orders
    .Where(x => x.CustomerId == customerId)
    .ToListAsync(cancellationToken);
```

Khi token được signal, API có thể ném `OperationCanceledException` hoặc `TaskCanceledException`.

Linked token kết hợp nhiều nguồn cancellation:

```csharp
using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(
    requestAborted,
    timeoutCts.Token);
```

Operation dừng khi request bị abort hoặc timeout nội bộ xảy ra.

## 4. Practical implementation

ASP.NET Core handler:

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    AppDbContext db,
    CancellationToken ct) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    return order is null
        ? Results.NotFound()
        : Results.Ok(order);
});
```

Background worker cũng phải propagate stopping token:

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        var message = await queue.ReceiveAsync(stoppingToken);
        await ProcessAsync(message, stoppingToken);
    }
}
```

## 5. Real production scenario

User mở trang search rồi đổi filter liên tục. Request cũ bị browser abort nhưng backend vẫn chạy query 8 giây và gọi Elasticsearch. Nếu traffic lớn, hàng nghìn operations “orphaned” vẫn dùng CPU, connection pool và downstream capacity.

Propagate `RequestAborted` giúp giải phóng resource sớm hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → database CPU hoặc outbound calls vẫn cao dù client-side traffic đã giảm.

**Evidence** → nhiều requests bị aborted nhưng dependency calls vẫn hoàn thành đầy đủ.

**Hypothesis** → cancellation token không được propagate.

**Diagnosis** → trace call chain; tìm các API async không nhận token; kiểm tra custom loops.

**Fix** → truyền token xuyên suốt call stack; tránh tạo `CancellationToken.None` tùy tiện.

**Verification** → abort request và xác nhận downstream operation dừng sớm.

## 7. Common mistakes

* Catch `OperationCanceledException` rồi log như lỗi 500.
* Dùng cancellation để rollback một operation đã commit side effect bên ngoài.
* Tạo timeout bằng `Task.WhenAny` nhưng để operation thật tiếp tục chạy ngầm.
* Không propagate token xuống EF Core/HTTP client.
* Dùng request cancellation cho cleanup critical cần hoàn tất sau request abort.

## 8. Alternatives

Timeout, cancellation và retry giải quyết vấn đề khác nhau. Timeout là policy về thời gian; cancellation là signal dừng; retry là thực thi lại. Có thể phối hợp nhưng không nên thay thế lẫn nhau.

## 9. Trade-offs

### Advantages

* Giảm wasted work.
* Shutdown sạch hơn.
* Giảm pressure lên downstream dependencies.

### Costs / Risks

* Phải thiết kế safe cancellation points.
* Một số business side effects không thể “cancel” sau khi commit.
* Propagation xuyên nhiều layers làm API signatures dài hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cancellation là cooperative, không phải thread abort.

### Middle

Biết truyền token xuyên async call chain.

### Senior

Phân biệt cancellation trước/đang/sau side effect và xử lý telemetry đúng.

### Technical Lead / Architect

Thiết kế timeout/cancellation boundaries phù hợp với request lifecycle, background processing và external side effects.

## 11. Key takeaway

* `CancellationToken` chỉ hiệu quả khi được propagate.
* Cancel khác failure và khác timeout.
* Không phải side effect nào cũng có thể rollback bằng cancellation.

# 2. ASP.NET Core Output Caching: giảm compute/read load nhưng không biến response động thành stale data ngoài kiểm soát

## 1. What is it?

Output Caching cache response đã được tạo bởi ASP.NET Core và trả lại cho các request tương đương mà không chạy lại toàn bộ endpoint pipeline/application logic.

Mental model:

```text
request
  ↓
cache lookup
  ├─ hit  → cached response
  └─ miss → endpoint → dependencies → response → cache
```

## 2. Why does it exist?

Một endpoint read-heavy có thể lặp lại cùng DB query, mapping và serialization hàng nghìn lần dù response giống nhau trong vài giây. Output caching giảm work ở application layer mà không cần tự cache từng repository call.

Nhưng vì nó cache **HTTP output**, sai key hoặc policy có thể làm user nhận dữ liệu của context khác.

## 3. How does it work?

ASP.NET Core Output Caching middleware quyết định request nào cache được, key gồm những dimensions nào, TTL bao lâu và khi nào invalidation xảy ra.

Cache key có thể vary theo query string, route, header hoặc custom value. Nếu endpoint phụ thuộc tenant/user nhưng key không chứa identity phù hợp, cache có thể leak dữ liệu.

## 4. Practical implementation

```csharp
builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("catalog", policy =>
        policy
            .Expire(TimeSpan.FromSeconds(30))
            .SetVaryByQuery("category", "page"));
});

app.UseOutputCache();

app.MapGet("/catalog", async (
    string? category,
    int page,
    CatalogService service,
    CancellationToken ct) =>
{
    return await service.GetPageAsync(category, page, ct);
})
.CacheOutput("catalog");
```

## 5. Real production scenario

Product-listing page nhận hàng nghìn request/phút. Data chỉ thay đổi vài lần mỗi phút. Cache output 15–30 giây có thể giảm DB reads và JSON serialization đáng kể.

Nhưng price hoặc inventory nếu yêu cầu freshness cao hơn có thể cần cache policy khác hoặc không cache.

## 6. Failure scenario & troubleshooting

**Symptom** → user thấy dữ liệu sai tenant hoặc content cũ quá lâu.

**Evidence** → cache hit trên request có authorization context khác nhau; key không vary theo dimension business quan trọng.

**Hypothesis** → cache key/policy không phản ánh response semantics.

**Diagnosis** → log cache key dimensions, compare inputs giữa hit requests.

**Fix** → vary đúng dimensions, không cache private response khi không an toàn, thiết kế invalidation/TTL.

**Verification** → integration test nhiều tenant/query combinations.

## 7. Common mistakes

* Cache endpoint authenticated mà không xem response có user-specific hay không.
* TTL lớn chỉ để tăng hit rate.
* Không phân biệt browser/CDN/output/data cache.
* Cache lỗi 500 hoặc transient failure không chủ đích.
* Dùng output cache để che query chậm thay vì sửa access pattern.

## 8. Alternatives

* Redis/data cache cho reusable domain data.
* CDN cho public edge-cacheable content.
* Browser cache qua HTTP headers.
* Không cache nếu freshness/correctness quan trọng hơn cost.

## 9. Trade-offs

### Advantages

* Giảm application/DB work nhanh.
* Dễ áp dụng ở HTTP boundary.
* Có thể giảm p95 đáng kể cho read-heavy endpoints.

### Costs / Risks

* Stale data.
* Cache-key complexity.
* Risk data leakage nếu identity dimension sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu output cache lưu response cuối cùng.

### Middle

Biết TTL và vary-by.

### Senior

Đánh giá cache correctness, invalidation và privacy.

### Technical Lead / Architect

Quyết định cache boundary giữa browser, CDN, application output và domain data.

## 11. Key takeaway

* Cache key là correctness boundary.
* Hit rate cao không quan trọng bằng đúng dữ liệu.
* Output caching nên dựa trên response semantics, không chỉ performance.

# 3. EF Core compiled queries: giảm query-pipeline overhead nhưng không cứu được access pattern tệ

## 1. What is it?

EF Core compiled query cho phép compile trước query expression thành delegate để giảm overhead lặp lại của query compilation cho một hot query shape.

## 2. Why does it exist?

EF Core đã cache query plan nội bộ, nhưng với extremely hot paths, việc matching/processing expression tree vẫn có overhead. Compiled queries giúp giảm phần overhead ở application side.

Tuy nhiên database I/O thường lớn hơn nhiều. Nếu query đọc 500.000 rows, compiled query không làm access pattern đó trở nên tốt.

## 3. How does it work?

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<OrderDto>>
    GetOrdersByCustomer =
        EF.CompileAsyncQuery((AppDbContext db, Guid customerId) =>
            db.Orders
                .AsNoTracking()
                .Where(x => x.CustomerId == customerId)
                .OrderByDescending(x => x.CreatedAt)
                .Select(x => new OrderDto(x.Id, x.Total)));
```

Query shape được compile một lần rồi reuse.

## 4. Practical implementation

```csharp
await foreach (var order in GetOrdersByCustomer(db, customerId)
    .WithCancellation(ct))
{
    results.Add(order);
}
```

Trước khi áp dụng, benchmark hot path bằng realistic dataset và đo DB duration riêng khỏi application overhead.

## 5. Real production scenario

Một internal pricing lookup chạy hàng chục nghìn lần/giây, query rất nhỏ và DB latency cực thấp. Lúc này EF query-pipeline overhead có thể đủ đáng kể để compiled query có giá trị.

Ngược lại, endpoint report chạy 2 giây SQL thì compiled query gần như không thay đổi user latency.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled query nhưng p95 gần như không đổi.

**Evidence** → SQL duration chiếm 95% latency.

**Hypothesis** → optimization nhắm sai bottleneck.

**Diagnosis** → trace application vs DB time.

**Fix** → tối ưu query/data access/indexes trước.

**Verification** → benchmark before/after đúng layer.

## 7. Common mistakes

* Compile mọi query “cho nhanh”.
* Không benchmark.
* Dùng giant query shape khó maintain.
* Tối ưu EF overhead trong khi network/DB mới là bottleneck.
* Quên `AsNoTracking`/projection trong read path.

## 8. Alternatives

Normal LINQ query thường đủ tốt. Dapper/raw SQL phù hợp hot paths cần control sâu hơn nhưng tăng maintenance cost. Stored procedure có thể phù hợp một số database-centric workloads.

## 9. Trade-offs

### Advantages

* Giảm query pipeline overhead.
* Predictable cho hot stable query shapes.

### Costs / Risks

* Code ít linh hoạt hơn.
* Optimization benefit thường nhỏ nếu I/O chiếm phần lớn latency.
* Tăng complexity và benchmark burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu EF query không chỉ là SQL string.

### Middle

Biết projection/tracking quan trọng hơn micro-optimization.

### Senior

Benchmark đúng layer trước khi dùng compiled query.

### Technical Lead / Architect

Xác định khi nào ORM overhead thực sự đáng tối ưu hoặc khi nào nên đổi data-access approach.

## 11. Key takeaway

* Compiled query là micro-optimization cho hot paths.
* Nó không sửa query/data model tệ.
* Measure trước, tối ưu đúng bottleneck.

# 4. PostgreSQL partial index: index đúng subset dữ liệu thay vì index toàn bảng một cách mù quáng

## 1. What is it?

Partial index chỉ index các rows thỏa một predicate.

Ví dụ:

```sql
CREATE INDEX ix_orders_open_created_at
ON orders (created_at DESC)
WHERE status = 'OPEN';
```

## 2. Why does it exist?

Nếu bảng có 100 triệu orders nhưng chỉ 2% đang `OPEN`, index toàn bộ `status, created_at` có thể lớn và tốn maintenance hơn cần thiết. Nếu workload chủ yếu query open orders, partial index tập trung vào hot subset.

## 3. How does it work?

PostgreSQL optimizer có thể dùng partial index khi query predicate chứng minh được tương thích với index predicate.

Query:

```sql
SELECT id, created_at
FROM orders
WHERE status = 'OPEN'
ORDER BY created_at DESC
LIMIT 100;
```

có thể scan index rất nhỏ thay vì toàn bộ bảng/index lớn.

## 4. Practical implementation

Trước:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at
FROM orders
WHERE status = 'OPEN'
ORDER BY created_at DESC
LIMIT 100;
```

Sau khi xác nhận access pattern:

```sql
CREATE INDEX CONCURRENTLY ix_orders_open_created_at
ON orders (created_at DESC)
WHERE status = 'OPEN';
```

Dùng `CONCURRENTLY` trong production khi phù hợp để giảm blocking, nhưng hiểu trade-off build time và failure handling.

## 5. Real production scenario

Support dashboard luôn hiển thị “pending approvals” chiếm 1% tổng records. Full composite index trên toàn bảng làm write cost tăng và storage lớn. Partial index cho active subset có thể giảm footprint đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → index tồn tại nhưng query không dùng.

**Evidence** → execution plan dùng seq scan hoặc index khác.

**Hypothesis** → query predicate không match partial predicate, statistics/selectivity khác expectation hoặc query quá rộng.

**Diagnosis** → `EXPLAIN ANALYZE`, kiểm tra predicate, row counts, statistics.

**Fix** → align index với real query, không ép planner bằng assumptions.

**Verification** → compare buffers, execution time và write overhead.

## 7. Common mistakes

* Tạo partial index theo status hiếm khi query.
* Không xem write/update pattern.
* Assume index sẽ được dùng mọi lúc.
* Tạo quá nhiều overlapping indexes.
* Không theo dõi index bloat/storage.

## 8. Alternatives

Composite full index, covering index, partitioning, materialized view hoặc query redesign. Partial index tốt khi hot subset ổn định và predicate rõ.

## 9. Trade-offs

### Advantages

* Index nhỏ hơn.
* Lower write/storage cost so với full index.
* Tốt cho sparse hot subsets.

### Costs / Risks

* Chỉ hữu ích cho compatible predicates.
* Dễ tạo specialized indexes khó quản lý.
* Business distribution thay đổi có thể làm lợi ích giảm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không nhất thiết chứa mọi row.

### Middle

Biết dùng `EXPLAIN ANALYZE` để kiểm tra.

### Senior

Đánh giá selectivity, write cost và planner behavior.

### Technical Lead / Architect

Đặt index strategy dựa trên workload thay vì schema aesthetics.

## 11. Key takeaway

* Partial index tối ưu theo access pattern.
* Query plan là bằng chứng, không phải intuition.
* Mỗi index đều có write/storage cost.

# 5. Elasticsearch `text` vs `keyword`: analyzer, exact match và vì sao mapping sai làm search “không hiểu nổi”

## 1. What is it?

Trong Elasticsearch, `text` field được analyzed cho full-text search; `keyword` giữ nguyên giá trị để exact match, sorting và aggregations.

Ví dụ một field có thể được multi-field mapping:

```json
{
  "name": {
    "type": "text",
    "fields": {
      "raw": { "type": "keyword" }
    }
  }
}
```

## 2. Why does it exist?

Search “wireless headphones” cần tokenize, normalize và scoring. Nhưng filter `status = "PUBLISHED"` hoặc sort theo SKU cần exact value. Một data type không tối ưu cho cả hai semantics.

## 3. How does it work?

`text` đi qua analyzer:

```text
"Running Shoes"
→ tokenizer
→ [running, shoes]
→ normalization/filtering
→ inverted index
```

`keyword` thường giữ toàn chuỗi như một term duy nhất.

## 4. Practical implementation

Mapping:

```json
PUT products
{
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "fields": {
          "keyword": { "type": "keyword" }
        }
      },
      "status": { "type": "keyword" }
    }
  }
}
```

Query full text:

```json
{ "match": { "name": "running shoes" } }
```

Exact filter:

```json
{ "term": { "status": "PUBLISHED" } }
```

## 5. Real production scenario

E-commerce team map `categoryName` chỉ thành `text`, sau đó aggregation theo category trả kết quả khó dự đoán hoặc không dùng được như mong muốn. Họ cần `keyword` subfield cho aggregation và `text` cho search.

## 6. Failure scenario & troubleshooting

**Symptom** → exact filter không match hoặc aggregation behavior lạ.

**Evidence** → mapping/analyzer không phù hợp query semantics.

**Hypothesis** → field type sai.

**Diagnosis** → inspect mapping, `_analyze`, actual query DSL.

**Fix** → mapping đúng và reindex qua alias strategy.

**Verification** → test tokens, filter results và relevance.

## 7. Common mistakes

* Dùng `term` query trên analyzed text rồi ngạc nhiên không match.
* Dùng `match` query cho identifier.
* Cho mọi string cả `text` và `keyword` mà không cân nhắc index size.
* Thay analyzer trên existing index mà quên reindex.

## 8. Alternatives

Normalizers cho keyword, custom analyzers, search-as-you-type fields, edge n-gram cho autocomplete. Mỗi cách phục vụ semantics khác nhau.

## 9. Trade-offs

### Advantages

* Mapping đúng giúp query rõ và predictable.
* Multi-fields hỗ trợ nhiều access patterns trên cùng logical data.

### Costs / Risks

* Nhiều subfields tăng index size.
* Mapping evolution thường cần reindex.
* Analyzer design ảnh hưởng relevance toàn hệ thống.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `text` là analyzed, `keyword` là exact term.

### Middle

Biết chọn `match`, `term`, sorting, aggregation đúng field.

### Senior

Debug analyzer/mapping bằng evidence.

### Technical Lead / Architect

Thiết kế search schema theo query/relevance requirements và migration strategy.

## 11. Key takeaway

* Field type phải phản ánh search semantics.
* `text` và `keyword` giải quyết bài toán khác nhau.
* Mapping sai thường buộc reindex, nên thiết kế trước khi production-scale.

# 6. Saga Pattern + compensating transaction: khi một business transaction đi xuyên nhiều services

## 1. What is it?

Saga chia một business transaction dài thành nhiều local transactions, mỗi bước có action và khi cần có compensating action để đưa business state về trạng thái chấp nhận được.

```text
Create Order
→ Reserve Inventory
→ Authorize Payment
→ Arrange Shipment
```

Nếu bước sau thất bại, system chạy compensation phù hợp.

## 2. Why does it exist?

Distributed transaction/2PC thường không thực tế hoặc không được hỗ trợ xuyên microservices, SaaS và cloud services. Nhưng business operation vẫn cần consistency ở mức workflow.

Saga chấp nhận intermediate states và explicit failure recovery.

## 3. How does it work?

Ví dụ orchestration:

```text
Order Service: create pending order
       ↓
Inventory: reserve
       ↓
Payment: authorize
       ↓
Shipment: create
       ↓
Success → confirm order
```

Nếu payment fail:

```text
release inventory
cancel order
```

Compensation không phải database rollback; nó là business operation mới.

## 4. Practical implementation

Pseudo-C# orchestration gần production:

```csharp
try
{
    await inventory.ReserveAsync(orderId, ct);
    await payment.AuthorizeAsync(orderId, ct);
    await shipping.CreateAsync(orderId, ct);
    await orders.ConfirmAsync(orderId, ct);
}
catch
{
    await inventory.ReleaseIfReservedAsync(orderId, ct);
    await payment.VoidIfAuthorizedAsync(orderId, ct);
    await orders.CancelAsync(orderId, ct);
    throw;
}
```

Thực tế cần persistence state, idempotency, retries và durable orchestration thay vì giữ workflow trong một request memory-only.

## 5. Real production scenario

Checkout reserve inventory thành công nhưng payment provider timeout. Không thể biết ngay payment thất bại hay response bị mất. Retry vô điều kiện có thể charge hai lần. Workflow cần idempotency key, status reconciliation và compensation.

## 6. Failure scenario & troubleshooting

**Symptom** → order canceled nhưng inventory vẫn reserved.

**Evidence** → compensation step fail hoặc process crash giữa steps.

**Hypothesis** → saga state không durable/idempotent.

**Diagnosis** → inspect workflow state, message history, side-effect status.

**Fix** → persist saga state, retries bounded, compensations idempotent, reconciliation job.

**Verification** → inject failure tại từng step và kiểm tra eventual business state.

## 7. Common mistakes

* Gọi compensation là “rollback” và giả định nó hoàn hảo.
* Không idempotent actions.
* Giữ saga trong synchronous HTTP request dài.
* Không model unknown outcome từ remote timeout.
* Không có operational dashboard cho stuck sagas.

## 8. Alternatives

Single-database transaction nếu boundary có thể nằm trong một service. Transactional Outbox + eventual consumers khi workflow đơn giản. Durable orchestrator cho multi-step long-running flows.

## 9. Trade-offs

### Advantages

* Phù hợp distributed workflows.
* Không cần global transaction coordinator.

### Costs / Risks

* Intermediate inconsistency.
* Compensation complexity.
* Debugging và observability khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu local transaction không rollback service khác.

### Middle

Biết action/compensation/idempotency.

### Senior

Xử lý unknown outcome, retries và stuck workflow.

### Technical Lead / Architect

Quyết định có thật sự cần distributed workflow hay boundary nên được gom lại để giữ local transaction.

## 11. Key takeaway

* Compensation là business action mới, không phải magic rollback.
* Saga cần durable state và idempotency.
* Nếu có thể giữ consistency trong một local transaction đơn giản hơn, hãy cân nhắc nó trước.

# 7. Azure Private Endpoint + Private DNS: private connectivity không chỉ là “bật một checkbox”

## 1. What is it?

Azure Private Endpoint gán private IP trong Virtual Network cho một Azure PaaS resource như Storage, SQL, Key Vault hoặc Cosmos DB thông qua Private Link.

Client trong network dùng private IP thay vì public endpoint path.

## 2. Why does it exist?

Doanh nghiệp thường muốn traffic tới PaaS không đi qua public internet path, enforce network isolation và giảm attack surface. Nhưng hostname dịch vụ vẫn thường giữ dạng public DNS name, nên DNS phải resolve đúng private IP.

## 3. How does it work?

```text
App Service / VM / AKS
        ↓ DNS query
Private DNS Zone
        ↓ private IP
Private Endpoint NIC
        ↓ Private Link
Azure PaaS Service
```

Nếu DNS sai, app có thể resolve public IP và connection fail sau khi public access bị disable.

## 4. Practical implementation

Ví dụ Key Vault thường dùng private DNS zone tương ứng, liên kết vào VNet. Verification từ workload:

```bash
nslookup myvault.vault.azure.net
```

Kết quả phải resolve theo private path mong muốn.

Application vẫn dùng normal SDK endpoint:

```csharp
var client = new SecretClient(
    new Uri("https://myvault.vault.azure.net/"),
    new DefaultAzureCredential());
```

Network private không thay thế identity/authentication.

## 5. Real production scenario

Team disable public access trên Storage sau khi tạo Private Endpoint. Production app ngay lập tức lỗi vì custom DNS server không forward Private DNS Zone đúng. Network topology đúng trên portal nhưng name resolution sai.

## 6. Failure scenario & troubleshooting

**Symptom** → connection timeout hoặc 403 sau khi enable private access.

**Evidence** → DNS resolve public IP hoặc route không reach private IP.

**Hypothesis** → DNS/VNet integration misconfiguration.

**Diagnosis** → `nslookup`, route inspection, network watcher, app VNet integration.

**Fix** → correct Private DNS linkage/forwarding và routing.

**Verification** → resolve private IP và connect thành công từ workload subnet.

## 7. Common mistakes

* Nghĩ Private Endpoint tự xử lý mọi DNS topology.
* Disable public access trước khi test workload path.
* Nhầm network isolation với authorization.
* Không kiểm tra on-prem/hybrid DNS forwarding.
* Tạo endpoints nhưng không quản subnet/IP capacity.

## 8. Alternatives

Service Endpoints cho một số services/use cases, public endpoint + firewall restrictions, VNet-injected service nếu platform hỗ trợ. Chọn theo isolation, complexity và cost.

## 9. Trade-offs

### Advantages

* Private network path.
* Giảm public exposure.
* Hỗ trợ enterprise network controls.

### Costs / Risks

* DNS complexity tăng mạnh.
* Tốn IP/endpoint management.
* Hybrid networking khó troubleshoot hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu private IP không đồng nghĩa bỏ authentication.

### Middle

Biết kiểm tra DNS + route.

### Senior

Troubleshoot cross-network/private-link issues.

### Technical Lead / Architect

Thiết kế private connectivity, DNS ownership và rollout plan không gây outage.

## 11. Key takeaway

* Private Endpoint là network path; DNS quyết định app có dùng path đó hay không.
* Network isolation không thay thế identity.
* Test resolution/connectivity trước khi disable public access.

# 8. Sampling trong distributed tracing: giảm telemetry cost mà vẫn giữ khả năng điều tra production

## 1. What is it?

Sampling quyết định trace/span nào được giữ lại thay vì lưu 100% telemetry. Mục tiêu là kiểm soát cost và volume nhưng vẫn đủ evidence cho debugging và SLO analysis.

## 2. Why does it exist?

Một service chạy hàng chục nghìn RPS có thể tạo hàng tỷ spans/ngày. Lưu toàn bộ rất đắt và đôi khi làm observability backend trở thành bottleneck riêng.

Nhưng sampling ngây thơ có thể loại đúng trace hiếm chứa error production.

## 3. How does it work?

Head sampling quyết định sớm khi trace bắt đầu. Tail sampling quyết định sau khi đã thấy toàn trace hoặc một phần lớn, nên có thể ưu tiên error/slow traces nhưng cần collector infrastructure phức tạp hơn.

```text
request
→ trace created
→ spans emitted
→ sampler decision
→ export / drop
```

## 4. Practical implementation

OpenTelemetry .NET head sampling:

```csharp
services.AddOpenTelemetry()
    .WithTracing(builder =>
    {
        builder
            .SetSampler(new ParentBasedSampler(
                new TraceIdRatioBasedSampler(0.10)))
            .AddAspNetCoreInstrumentation()
            .AddHttpClientInstrumentation();
    });
```

Parent-based sampling giúp downstream spans theo cùng trace decision.

## 5. Real production scenario

Checkout chạy 5.000 RPS. 100% traces làm telemetry bill tăng mạnh. Team giảm xuống 1%, sau đó intermittent payment failure 0.05% gần như không còn trace evidence.

Sampling policy cần preserve errors hoặc route criticality bằng collector/tail rules phù hợp.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard thấy error count từ metrics nhưng không tìm thấy trace tương ứng.

**Evidence** → aggressive head sampling và low-frequency failures.

**Hypothesis** → useful traces bị dropped.

**Diagnosis** → inspect sampler config và sampled/error proportions.

**Fix** → adjust ratio, critical-route policy hoặc tail sampling.

**Verification** → inject known errors và xác nhận trace retention.

## 7. Common mistakes

* Dùng một sampling rate cho mọi environment/service.
* Sample logs/metrics/traces như cùng một loại dữ liệu.
* Không preserve parent decision xuyên services.
* Giảm sampling chỉ theo cost mà không test incident diagnosability.

## 8. Alternatives

100% tracing cho low-volume services; adaptive/tail sampling; metrics + selective traces; dynamic sampling policies theo endpoint/error class.

## 9. Trade-offs

### Advantages

* Giảm ingestion/storage cost.
* Giảm telemetry pipeline load.

### Costs / Risks

* Mất rare-event evidence.
* Tail sampling phức tạp hơn.
* Sampling policy trở thành production design concern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu không phải trace nào cũng nhất thiết được lưu.

### Middle

Biết head sampling và parent-based behavior.

### Senior

Đánh giá cost vs diagnosability.

### Technical Lead / Architect

Thiết kế telemetry retention/sampling theo SLO, critical paths và incident requirements.

## 11. Key takeaway

* Sampling là engineering trade-off, không chỉ cost knob.
* Rare failures cần policy bảo vệ evidence.
* Metrics, logs và traces có retention strategy khác nhau.

# 9. CORS vs CSRF: hai cơ chế khác nhau thường bị nhầm lẫn trong frontend/backend security

## 1. What is it?

CORS là browser policy kiểm soát việc JavaScript từ origin A đọc/gửi cross-origin requests tới origin B theo server-approved rules.

CSRF là attack lợi dụng browser tự động gửi credentials như cookies để thực hiện action dưới identity của victim.

CORS không phải CSRF protection mặc định.

## 2. Why does it exist?

Browser Same-Origin Policy ngăn website tùy ý đọc data từ site khác. CORS mở có kiểm soát cross-origin access.

CSRF tồn tại vì browser có thể tự attach cookie vào request. Attacker không nhất thiết cần đọc response; chỉ cần khiến action được gửi thành công.

## 3. How does it work?

CORS:

```text
frontend origin
→ request/preflight
→ server CORS headers
→ browser decides whether JS may access response
```

CSRF:

```text
victim logged in with cookie
→ malicious page submits request
→ browser sends victim cookie
→ server may accept action
```

## 4. Practical implementation

ASP.NET Core CORS:

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("frontend", policy =>
        policy
            .WithOrigins("https://app.example.com")
            .AllowAnyHeader()
            .AllowAnyMethod()
            .AllowCredentials());
});
```

Cookie-authenticated state-changing endpoints vẫn cần CSRF strategy như anti-forgery token/SameSite đúng và request design phù hợp.

## 5. Real production scenario

Team cấu hình CORS chỉ cho frontend domain rồi nghĩ POST `/payments/refund` đã an toàn khỏi CSRF. Nhưng browser vẫn có thể gửi credentialed form request trong một số attack flows; CORS chủ yếu kiểm soát JS access to response, không tự đảm bảo intent của user.

## 6. Failure scenario & troubleshooting

**Symptom** → unauthorized state change xảy ra từ victim session dù CORS restrictive.

**Evidence** → endpoint dùng cookie auth, không có anti-forgery control.

**Hypothesis** → CSRF protection missing.

**Diagnosis** → inspect auth mechanism, SameSite, content types, anti-forgery validation.

**Fix** → CSRF token/origin checks/SameSite strategy phù hợp.

**Verification** → security test cross-site form/fetch scenarios.

## 7. Common mistakes

* `AllowAnyOrigin` + credentials.
* Dùng CORS như authentication.
* Nghĩ bearer token API và cookie API có cùng CSRF profile.
* Disable CORS để “fix frontend”.
* Không phân biệt browser-enforced policy với server authorization.

## 8. Alternatives

Bearer token trong `Authorization` header giảm classic CSRF exposure nhưng tăng concern về token storage/XSS. SameSite cookies giảm một số vectors nhưng không nên là control duy nhất trong mọi threat model.

## 9. Trade-offs

### Advantages

* CORS cho phép controlled cross-origin frontend architecture.
* CSRF protections bảo vệ intent trong cookie-authenticated flows.

### Costs / Risks

* Cấu hình phức tạp với multiple origins.
* Security assumptions thay đổi theo auth mechanism/browser behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CORS không phải authentication.

### Middle

Biết cấu hình origin policy và CSRF token.

### Senior

Threat-model cookie vs bearer flows.

### Technical Lead / Architect

Chọn auth/browser security model phù hợp frontend topology và risk.

## 11. Key takeaway

* CORS và CSRF giải quyết hai vấn đề khác nhau.
* Cookie authentication cần xem xét CSRF rõ ràng.
* Browser policy không thay thế server authorization.

# 10. Architecture Decision Record (ADR): giữ lại lý do kỹ thuật để hệ thống không lặp lại cùng một tranh luận

## 1. What is it?

ADR là tài liệu ngắn ghi lại một quyết định kiến trúc quan trọng: context, decision, alternatives và consequences.

Một ADR tốt trả lời:

```text
What problem existed?
What options were considered?
Why was this option chosen?
What trade-offs were accepted?
```

## 2. Why does it exist?

Sau 12 tháng, code chỉ cho thấy **đã chọn gì**, không cho thấy **vì sao chọn**. Team mới có thể nhìn một constraint cũ như “code xấu” rồi đảo quyết định, sau đó tái phát vấn đề trước đây.

ADR lưu decision context, không phải documentation trang trí.

## 3. How does it work?

Một lifecycle đơn giản:

```text
Problem / constraint
→ options
→ decision
→ consequences
→ accepted ADR
→ later superseded if context changes
```

ADR không cần immutable vĩnh viễn; decision mới có thể supersede decision cũ nhưng nên giữ lịch sử.

## 4. Practical implementation

Ví dụ template:

```markdown
# ADR-012: Use Modular Monolith for Core Platform

## Status
Accepted

## Context
Team size, deployment model, consistency requirements...

## Decision
Use Modular Monolith with module-owned schemas.

## Alternatives
- Layered Monolith
- Microservices

## Consequences
- Simpler deployment
- Requires module-boundary discipline
- Future extraction remains possible
```

## 5. Real production scenario

Một team chọn Redis không phải để “performance chung” mà vì session state phải shared giữa 20 App Service instances. Hai năm sau một developer muốn bỏ Redis vì thấy phần lớn cache hit thấp. ADR giúp nhận ra dependency ban đầu còn phục vụ distributed session, không chỉ caching.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng tranh luận kiến trúc lặp lại mỗi quý; team không biết constraint ban đầu.

**Evidence** → Slack/meeting history thất lạc, không có decision record.

**Hypothesis** → rationale không được institutionalized.

**Diagnosis** → review recurring decisions và undocumented trade-offs.

**Fix** → ADR cho high-impact decisions, link từ design docs/PRs.

**Verification** → người mới có thể hiểu decision mà không cần hỏi tác giả cũ.

## 7. Common mistakes

* ADR dài như specification 40 trang.
* Ghi decision nhưng không ghi alternatives/trade-offs.
* ADR cho mọi naming convention nhỏ.
* Không cập nhật status khi decision bị supersede.
* Dùng ADR để hợp thức hóa quyết định đã chốt mà không nêu evidence.

## 8. Alternatives

Design docs cho thay đổi lớn cần nhiều detail; RFC cho collaborative proposal; README cho current usage; issue/PR cho implementation discussion. ADR phù hợp decision memory ngắn gọn và lâu dài.

## 9. Trade-offs

### Advantages

* Giữ rationale.
* Giảm repeated debate.
* Giúp onboarding và architecture review.

### Costs / Risks

* Cần discipline cập nhật.
* Quá nhiều ADR nhỏ tạo noise.
* Decision context có thể stale nếu không supersede rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu code không lưu đầy đủ lý do kiến trúc.

### Middle

Biết đọc ADR trước khi refactor boundary lớn.

### Senior

Viết ADR với alternatives, evidence và consequences rõ.

### Technical Lead / Architect

Quản decision lifecycle: accepted, deprecated, superseded và traceability tới constraints/NFRs.

## 11. Key takeaway

* ADR lưu **rationale**, không chỉ decision.
* Chỉ ghi các quyết định có consequence đáng kể.
* Architecture history giúp tránh lặp lại lỗi và tranh luận cũ.
