# 1. C# `Task.WhenAll` và bounded fan-out: chạy concurrent work mà không biến một batch thành resource storm

## 1. What is it?

`Task.WhenAll` cho phép chờ nhiều asynchronous operations hoàn tất. Mental model quan trọng là: `Task.WhenAll` **không tự giới hạn concurrency**. Nó chỉ compose nhiều `Task` thành một task đại diện cho toàn bộ tập công việc.

Ví dụ:

```csharp
var tasks = ids.Select(id => LoadAsync(id, cancellationToken));
var results = await Task.WhenAll(tasks);
```

Nếu `ids` có 10 phần tử, cách này có thể hợp lý. Nếu có 100.000 phần tử và `LoadAsync` gọi database hoặc HTTP API, code có thể khởi động hàng chục nghìn operations gần như cùng lúc.

Vì vậy cần phân biệt:

* concurrency composition: chờ nhiều task,
* concurrency control: giới hạn số operation được chạy đồng thời,
* failure aggregation: hiểu nhiều task có thể fail cùng lúc.

## 2. Why does it exist?

Sequential I/O thường lãng phí thời gian chờ:

```text
Call A ----wait---- done
                  Call B ----wait---- done
```

Với independent I/O, concurrency có thể giảm total latency:

```text
Call A ----wait---- done
Call B ----wait---- done
Call C ----wait---- done
```

Nhưng “concurrent hơn” không luôn “nhanh hơn”. Mỗi dependency có capacity giới hạn: connection pool, socket, database worker, remote rate limit, CPU hoặc memory.

Một Senior engineer phải hỏi:

* dependency chịu được bao nhiêu parallel requests?
* client connection pool có giới hạn gì?
* retry có nhân concurrency lên không?
* cancellation có được propagate không?
* kết quả partial failure được xử lý thế nào?

## 3. How does it work?

Khi collection tasks đã được tạo, `Task.WhenAll` theo dõi completion của tất cả task.

```csharp
var all = Task.WhenAll(task1, task2, task3);
await all;
```

Nếu mọi task thành công, `all` hoàn tất thành công.

Nếu một hoặc nhiều task fault, task tổng cũng fault. `await` thường rethrow một exception đại diện; nếu cần xem toàn bộ failures, có thể inspect task tổng hoặc capture lỗi ở từng operation.

Nếu task bị cancel và không task nào fault, task tổng có thể chuyển sang canceled state.

Điểm quan trọng: exception semantics của concurrent batch khác sequential flow. Nhiều operation có thể fail độc lập và cùng tồn tại bằng chứng.

## 4. Practical implementation

Với .NET hiện đại, `Parallel.ForEachAsync` là một cách rõ ràng để giới hạn concurrency:

```csharp
var options = new ParallelOptions
{
    MaxDegreeOfParallelism = 8,
    CancellationToken = cancellationToken
};

await Parallel.ForEachAsync(orderIds, options, async (orderId, ct) =>
{
    await ProcessOrderAsync(orderId, ct);
});
```

Hoặc dùng `SemaphoreSlim` nếu cần return results:

```csharp
var gate = new SemaphoreSlim(8);

var tasks = ids.Select(async id =>
{
    await gate.WaitAsync(cancellationToken);
    try
    {
        return await LoadAsync(id, cancellationToken);
    }
    finally
    {
        gate.Release();
    }
});

var results = await Task.WhenAll(tasks);
```

Với batch cực lớn, tốt hơn nữa là dùng `Channel<T>` hoặc queue consumer thay vì materialize hàng trăm nghìn tasks.

## 5. Real production scenario

Một API cần enrich 3.000 product records bằng pricing service. Bản đầu tiên dùng:

```csharp
await Task.WhenAll(products.Select(EnrichAsync));
```

Trong test với vài chục products thì rất nhanh. Production traffic tạo batch lớn hơn, dẫn tới:

* outbound HTTP sockets tăng mạnh,
* remote pricing service trả 429,
* retry policy làm request volume tăng thêm,
* memory tăng vì hàng nghìn state machines và response buffers cùng tồn tại,
* p99 latency xấu hơn sequential batch nhỏ.

Fix đúng không phải quay về sequential hoàn toàn, mà là xác định concurrency budget phù hợp, ví dụ 16 hoặc 32 concurrent calls tùy capacity thực tế.

## 6. Failure scenario & troubleshooting

**Symptom** → API latency tăng mạnh khi batch size lớn, outbound error 429/503 tăng.

**Evidence** → dependency request count tăng gần bằng batch size tại cùng thời điểm; socket/connection metrics tăng; retry count tăng.

**Hypothesis** → unbounded fan-out đang tạo load burst vượt capacity dependency.

**Diagnosis** → correlate batch size, concurrent outbound requests, dependency latency, connection pool và retry volume.

**Fix** → thêm bounded concurrency, retry budget và cancellation propagation.

**Verification** → load test nhiều batch sizes, so sánh throughput và p95/p99 trước/sau; xác nhận dependency không còn bị overload.

## 7. Common mistakes

* Dùng `Task.WhenAll` và nghĩ nó tự giới hạn số request đồng thời.
* Khởi tạo hàng chục nghìn tasks trước khi chờ.
* Bỏ qua `CancellationToken` ở downstream calls.
* Retry mọi lỗi mà không giới hạn tổng work.
* Chỉ log exception đầu tiên và mất các failure khác trong batch.
* Dùng concurrency cho CPU-bound work mà không hiểu ThreadPool/CPU saturation.

## 8. Alternatives

* Sequential loop: đúng và đơn giản khi volume nhỏ hoặc dependency nhạy cảm.
* `Parallel.ForEachAsync`: tốt cho bounded concurrent processing.
* `Channel<T>`: phù hợp producer-consumer và backpressure.
* Message queue: phù hợp work dài, cần retry/durability và không cần synchronous response.
* Batch API phía dependency: tốt nhất nếu remote service hỗ trợ xử lý nhiều items trong một request.

## 9. Trade-offs

### Advantages

* Concurrent I/O có thể giảm wall-clock latency đáng kể.
* `Task.WhenAll` đơn giản để compose independent async work.
* Bounded fan-out tận dụng parallelism mà vẫn bảo vệ dependency.

### Costs / Risks

* Concurrency tăng memory, sockets và pressure lên remote services.
* Failure handling phức tạp hơn sequential flow.
* Sai concurrency limit có thể vẫn underutilize hoặc overload hệ thống.
* Retry kết hợp fan-out có thể khuếch đại outage.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task.WhenAll` chạy/chờ nhiều asynchronous operations nhưng không đồng nghĩa tạo thread mới cho mỗi operation.

### Middle

Biết triển khai bounded concurrency bằng `Parallel.ForEachAsync` hoặc `SemaphoreSlim`, propagate cancellation và xử lý failure.

### Senior

Biết đo connection pressure, dependency rate limits, memory, p95/p99 và thiết kế retry budget khi fan-out.

### Technical Lead / Architect

Quyết định synchronous fan-out có phù hợp hay nên chuyển sang batching, queue hoặc architectural decomposition; đặt concurrency budget theo capacity thật của toàn chuỗi dependency.

## 11. Key takeaway

* `Task.WhenAll` compose tasks, không giới hạn concurrency.
* Concurrency phải có budget dựa trên capacity dependency.
* Retry + unbounded fan-out là công thức dễ tạo retry storm.
* Batch lớn thường cần backpressure hoặc queue, không chỉ nhiều tasks hơn.

# 2. ASP.NET Core idempotency key cho POST: retry an toàn khi client không biết request trước đã thành công hay chưa

## 1. What is it?

Idempotency key là một client-generated identifier đại diện cho **một business operation duy nhất**. Khi client retry cùng operation, server dùng key để nhận ra request đã được xử lý trước đó và tránh tạo side effect lần hai.

Ví dụ:

```http
POST /api/payments
Idempotency-Key: 7f715f2d-0cf1-4de8-9016-82d443151541
```

Nếu network timeout sau khi server đã commit payment nhưng trước khi client nhận response, client có thể retry cùng key. Server trả lại outcome cũ thay vì charge lần nữa.

## 2. Why does it exist?

Distributed systems có một ambiguity rất phổ biến:

```text
Client sends request
      ↓
Server commits successfully
      ↓
Response lost due to network timeout
```

Client chỉ biết “không nhận được response”, không biết server đã xử lý hay chưa.

Nếu POST tạo side effect và client retry mù quáng, có thể tạo:

* duplicate payment,
* duplicate order,
* duplicate booking,
* duplicate webhook registration.

Idempotency key tồn tại để biến retry từ “làm lại operation” thành “hỏi lại outcome của cùng operation”.

## 3. How does it work?

Typical flow:

```text
Client POST + key K
       ↓
Check Idempotency Store
       ↓
K absent → reserve K
       ↓
Execute business transaction
       ↓
Store response/outcome for K
       ↓
Return response
```

Retry:

```text
Client POST + same key K
       ↓
K exists
       ↓
Return stored result
```

Server cũng nên validate rằng cùng idempotency key không được dùng lại với payload khác. Có thể lưu request fingerprint/hash cùng key.

## 4. Practical implementation

Một schema đơn giản:

```sql
CREATE TABLE IdempotencyRecords
(
    IdempotencyKey nvarchar(100) NOT NULL PRIMARY KEY,
    RequestHash varbinary(32) NOT NULL,
    StatusCode int NULL,
    ResponseBody nvarchar(max) NULL,
    CreatedAt datetime2 NOT NULL,
    CompletedAt datetime2 NULL
);
```

Pseudo implementation trong ASP.NET Core:

```csharp
public async Task<IResult> CreatePaymentAsync(
    HttpRequest request,
    CreatePayment command,
    CancellationToken ct)
{
    var key = request.Headers["Idempotency-Key"].ToString();
    if (string.IsNullOrWhiteSpace(key))
        return Results.BadRequest("Idempotency-Key is required.");

    var hash = ComputeHash(command);
    var existing = await store.GetAsync(key, ct);

    if (existing is not null)
    {
        if (!CryptographicOperations.FixedTimeEquals(existing.RequestHash, hash))
            return Results.Conflict();

        if (existing.CompletedAt is not null)
            return Results.Json(existing.ResponseBody, statusCode: existing.StatusCode!.Value);
    }

    // Reserve key atomically, execute business transaction, persist outcome.
    // Details depend on storage and concurrency model.

    return Results.Ok();
}
```

Phần khó nhất không phải header parsing mà là atomic reservation + business effect + persisted outcome.

## 5. Real production scenario

Mobile app gửi `POST /orders`, user ở mạng chập chờn. Server tạo order thành công nhưng response mất. App retry sau 3 giây.

Nếu server không hỗ trợ idempotency, user có hai order giống nhau. Nếu client dùng cùng idempotency key cho operation, server trả lại order đã tạo.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate orders vẫn xuất hiện dù client đã gửi idempotency key.

**Evidence** → hai application instances cùng thấy key chưa tồn tại rồi cùng xử lý.

**Hypothesis** → check-then-insert không atomic.

**Diagnosis** → xem database unique constraint và transaction around reservation.

**Fix** → dùng unique key/conditional insert để chỉ một request giành quyền xử lý; request khác đọc outcome hoặc chờ trạng thái hoàn tất.

**Verification** → concurrency test gửi cùng key từ nhiều threads/instances, xác nhận business side effect chỉ xảy ra một lần.

## 7. Common mistakes

* Chỉ cache response in-memory nên scale-out instance khác không biết key.
* Không có unique constraint ở persistence layer.
* Cho phép cùng key với payload khác.
* Xóa idempotency record quá sớm trong khi client vẫn có thể retry.
* Coi idempotency key như authentication mechanism.
* Trả 500 cho request đang được xử lý song song mà không có rõ retry semantics.

## 8. Alternatives

* Natural business unique key, ví dụ merchant order number.
* PUT với resource identifier do client chọn nếu API semantics phù hợp.
* Message queue + deduplication/inbox nếu operation asynchronous.
* Không hỗ trợ idempotency nếu operation vốn không có side effect hoặc duplicate được business chấp nhận.

## 9. Trade-offs

### Advantages

* Làm retry của unsafe operations an toàn hơn.
* Giảm duplicate side effects do network ambiguity.
* Tạo audit trail cho repeated client attempts.

### Costs / Risks

* Cần storage, TTL/cleanup và concurrency control.
* Phải xác định canonical request hash và response replay semantics.
* Long-running requests tạo trạng thái “in progress” khó xử lý.
* Không thay thế transaction hoặc domain uniqueness rules.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu vì sao POST retry có thể tạo duplicate side effect.

### Middle

Implement idempotency key parsing, persistence và unique constraint.

### Senior

Xử lý concurrent duplicate requests, payload mismatch, TTL và failure giữa business commit với outcome persistence.

### Technical Lead / Architect

Quyết định operation nào bắt buộc idempotent, owner của idempotency store và semantics across APIs, gateways và asynchronous workflows.

## 11. Key takeaway

* Retry an toàn cần nhận diện cùng business operation, không chỉ gửi lại HTTP request.
* Idempotency reservation phải atomic ở shared persistence layer.
* Cùng key với payload khác phải được coi là conflict.
* Idempotency không thay thế authorization, transaction hoặc domain constraints.

# 3. EF Core `ValueConverter` và `ValueComparer`: map Value Object đúng cách mà không làm Change Tracker hiểu sai state

## 1. What is it?

`ValueConverter` chuyển đổi giữa representation trong domain model và representation lưu trong database.

Ví dụ domain dùng:

```csharp
public readonly record struct EmailAddress(string Value);
```

Database vẫn lưu `nvarchar`.

`ValueComparer` giải quyết vấn đề khác: giúp EF Core hiểu cách so sánh, snapshot và hash một value khi Change Tracker cần xác định nó đã thay đổi hay chưa.

Hai khái niệm thường bị nhầm:

* converter = persistence representation,
* comparer = change tracking semantics.

## 2. Why does it exist?

Domain model không nhất thiết phải dùng primitive ở mọi nơi. `string Email`, `string Currency`, `Guid CustomerId` dễ dẫn tới primitive obsession và cho phép invalid state đi sâu vào system.

Value Object giúp encode invariant:

```csharp
public sealed record CurrencyCode
{
    public string Value { get; }

    public CurrencyCode(string value)
    {
        if (value is not ("USD" or "EUR" or "VND"))
            throw new ArgumentException("Unsupported currency.");

        Value = value;
    }
}
```

Nhưng ORM cần biết cách persist value này.

## 3. How does it work?

Converter có hai expressions:

```text
Domain value → Provider value
Provider value → Domain value
```

Ví dụ:

```csharp
var converter = new ValueConverter<EmailAddress, string>(
    email => email.Value,
    value => new EmailAddress(value));
```

Với immutable scalar-like Value Object, structural equality thường đơn giản.

Với mutable collections hoặc custom objects, EF snapshot có thể giữ cùng reference; khi object mutate in-place, Change Tracker có thể không nhận ra thay đổi. Lúc đó cần `ValueComparer` với logic equality + hash + snapshot copy.

## 4. Practical implementation

Configuration:

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    var emailConverter = new ValueConverter<EmailAddress, string>(
        v => v.Value,
        v => new EmailAddress(v));

    modelBuilder.Entity<Customer>()
        .Property(x => x.Email)
        .HasConversion(emailConverter)
        .HasMaxLength(320);
}
```

Với mutable tags serialized thành JSON:

```csharp
var comparer = new ValueComparer<List<string>>(
    (a, b) => a!.SequenceEqual(b!),
    value => value.Aggregate(0, (hash, item) => HashCode.Combine(hash, item.GetHashCode())),
    value => value.ToList());
```

Một Senior engineer cũng phải hỏi liệu JSON-converted collection có thật sự là model phù hợp cho query/indexing hay nên normalize thành relational table.

## 5. Real production scenario

Một CRM dùng `Money` Value Object gồm `Amount` và `Currency`. Team serialize toàn bộ object vào một string column để “đỡ tạo nhiều cột”. Sau này cần query tổng doanh thu theo currency và phát hiện model persistence rất khó index/query.

Bài học: converter giúp persistence, nhưng không nên che giấu access pattern. Có khi owned type hoặc hai columns riêng là representation tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → object property đã mutate nhưng `SaveChanges` không tạo UPDATE.

**Evidence** → entity state vẫn `Unchanged`; property chứa mutable collection đã được sửa in-place.

**Hypothesis** → EF snapshot và current value trỏ cùng mutable object hoặc comparer không phản ánh structural equality.

**Diagnosis** → inspect Change Tracker debug view và comparer configuration.

**Fix** → dùng immutable value, replace whole object hoặc định nghĩa `ValueComparer` snapshot đúng.

**Verification** → integration test thay đổi value và kiểm tra generated SQL + persisted result.

## 7. Common mistakes

* Dùng converter nhưng quên column constraints như length/precision.
* Serialize object phức tạp vào một column rồi mất khả năng query/index hiệu quả.
* Dùng mutable reference type mà không có comparer/snapshot strategy.
* Đưa database concern vào Value Object chỉ để làm EF dễ mapping.
* Tạo generic converter cho mọi domain type và che mất schema semantics.

## 8. Alternatives

* Owned Entity Type / Complex Type cho multi-property value.
* Separate entity/table nếu lifecycle hoặc query pattern cần độc lập.
* Primitive property + domain validation nếu domain thật sự đơn giản.
* Custom type mapping/provider-specific feature khi database có native type phù hợp.

## 9. Trade-offs

### Advantages

* Domain model expressive hơn primitive-only model.
* Persistence representation có thể tách khỏi domain API.
* Converter cấu hình tập trung và test được.

### Costs / Risks

* Một số conversion làm query translation khó hơn.
* Mutable values cần comparer/snapshot discipline.
* Serialized columns có thể làm reporting/indexing phức tạp.
* Abstraction có thể che cost/shape thật của database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu converter biến domain type thành provider type khi lưu/đọc.

### Middle

Biết cấu hình converter và constraints, viết integration test cho persistence.

### Senior

Hiểu Change Tracker snapshot, equality semantics và query/index implications của representation.

### Technical Lead / Architect

Quyết định khi nào Value Object nên map thành scalar, owned/complex type hay separate table dựa trên invariant và access pattern.

## 11. Key takeaway

* `ValueConverter` và `ValueComparer` giải quyết hai vấn đề khác nhau.
* Immutable Value Object giúp change tracking đơn giản và an toàn hơn.
* Persistence representation phải phục vụ query/indexing, không chỉ “lưu được”.
* Domain abstraction không được che khuất cost của database model.

# 4. SQL Server Query Store và plan regression: điều tra query chậm sau deploy dựa trên execution evidence thay vì đoán index

## 1. What is it?

Query Store là cơ chế của SQL Server lưu lịch sử query text, execution plans và runtime statistics theo thời gian.

Mental model:

```text
Query
  ↓
Optimizer chooses plan
  ↓
Execution runtime stats
  ↓
Query Store keeps history
```

Điều này rất hữu ích khi một query “hôm qua nhanh, hôm nay chậm” nhưng lúc investigation plan hiện tại đã khác plan trước đây.

## 2. Why does it exist?

SQL optimizer có thể chọn plan khác khi:

* statistics thay đổi,
* data distribution thay đổi,
* parameter pattern thay đổi,
* index/schema thay đổi,
* compatibility level thay đổi,
* memory/parallelism context thay đổi.

Nếu chỉ xem current execution plan, team thiếu baseline lịch sử.

Query Store giúp trả lời:

* query nào regression?
* plan nào từng tốt hơn?
* regression bắt đầu từ thời điểm nào?
* CPU/duration/read thay đổi ra sao?

## 3. How does it work?

Query Store lưu các objects logic như:

* query,
* plan,
* runtime statistics,
* wait statistics trong các phiên bản hỗ trợ.

Một query có thể có nhiều plan IDs theo thời gian.

Ví dụ investigation flow:

```text
API p95 tăng
   ↓
Find slow database dependency
   ↓
Identify query hash/query id
   ↓
Compare historical plans
   ↓
Compare logical reads / CPU / duration
   ↓
Find plan regression
```

## 4. Practical implementation

Một số query cơ bản có thể bắt đầu từ Query Store views:

```sql
SELECT TOP (20)
    q.query_id,
    p.plan_id,
    rs.avg_duration,
    rs.avg_cpu_time,
    rs.avg_logical_io_reads,
    rsi.start_time,
    rsi.end_time
FROM sys.query_store_query q
JOIN sys.query_store_plan p
    ON p.query_id = q.query_id
JOIN sys.query_store_runtime_stats rs
    ON rs.plan_id = p.plan_id
JOIN sys.query_store_runtime_stats_interval rsi
    ON rsi.runtime_stats_interval_id = rs.runtime_stats_interval_id
ORDER BY rs.avg_duration DESC;
```

Đơn vị cần kiểm tra theo version/view documentation; quan trọng hơn là so sánh trend và plan history, không chỉ một con số.

Nếu xác nhận một known-good plan và cần mitigation khẩn cấp, SQL Server có khả năng force plan. Nhưng plan forcing nên là controlled mitigation, không phải thay thế root-cause analysis.

## 5. Real production scenario

Sau deploy, API search từ p95 180 ms lên 2.5 s. Application code hầu như không đổi query. Query Store cho thấy cùng query ID bắt đầu dùng một plan mới với nested loops + nhiều key lookups thay vì plan cũ phù hợp data volume hiện tại.

Team có thể:

1. force plan cũ để giảm incident impact,
2. điều tra statistics/index/query shape,
3. sửa nguyên nhân,
4. bỏ force sau verification.

## 6. Failure scenario & troubleshooting

**Symptom** → latency database tăng đột ngột sau một thời điểm rõ ràng.

**Evidence** → Query Store cho thấy plan ID mới xuất hiện cùng lúc duration/logical reads tăng.

**Hypothesis** → plan regression do changed cardinality estimate hoặc parameter distribution.

**Diagnosis** → so sánh estimated vs actual rows, statistics freshness, predicates, indexes và parameter values.

**Fix** → sửa query/index/statistics hoặc dùng plan forcing như temporary mitigation.

**Verification** → theo dõi runtime stats qua nhiều representative parameter values, không chỉ một test case.

## 7. Common mistakes

* Thấy query chậm là thêm index ngay.
* Force plan vĩnh viễn mà không hiểu nguyên nhân.
* Chỉ nhìn average duration và bỏ qua workload mix.
* Không correlate database regression với application deployment/config change.
* Xóa Query Store history ngay khi cần evidence nhất.

## 8. Alternatives

* Actual execution plan + live query stats cho investigation hiện tại.
* Extended Events cho event-level diagnostics.
* Application Insights/OpenTelemetry dependency telemetry để tìm query/dependency chậm từ application side.
* Database monitoring platform bên thứ ba cho long-term baselines.

## 9. Trade-offs

### Advantages

* Có historical evidence về plan và runtime behavior.
* Hữu ích cho regression sau deploy/data change.
* Plan forcing có thể là mitigation nhanh trong incident.

### Costs / Risks

* Query Store dùng storage và cần retention/capture policy hợp lý.
* Runtime aggregation có thể che parameter-specific behavior.
* Force plan sai có thể làm workload khác tệ hơn.
* Evidence database vẫn phải được nối với application traces.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một SQL text có thể chạy với nhiều execution plans theo thời gian.

### Middle

Biết dùng Query Store để tìm top regressions và xem plan history.

### Senior

Đọc plan, cardinality, logical I/O, wait và parameter behavior để tìm root cause.

### Technical Lead / Architect

Thiết lập diagnostic strategy: Query Store retention, telemetry correlation, mitigation policy và guardrail cho plan forcing.

## 11. Key takeaway

* Query performance regression cần historical evidence, không chỉ current plan.
* Query Store giúp nối thời điểm regression với plan change.
* Plan forcing là mitigation có kiểm soát, không phải root-cause fix.
* Tối ưu SQL nên đi từ query → plan → I/O → locks/waits → latency.

# 5. Lease và fencing token trong distributed coordination: khóa phân tán chưa đủ nếu owner cũ vẫn có thể ghi dữ liệu

## 1. What is it?

Lease là quyền sở hữu tạm thời có expiration. Distributed lock thường được triển khai như một lease để tránh lock tồn tại mãi nếu owner crash.

Nhưng lease có một vấn đề tinh vi: một process có thể bị pause lâu, lease hết hạn, process khác nhận lease mới, sau đó process cũ tỉnh lại và vẫn tiếp tục ghi.

Fencing token là một số monotonically increasing được cấp cho mỗi lease owner mới. Downstream resource chỉ chấp nhận operation có token mới hơn token đã thấy trước đó.

## 2. Why does it exist?

Ví dụ:

```text
Worker A gets lease token 41
Worker A pauses for 60s
Lease expires
Worker B gets lease token 42
Worker B writes new state
Worker A resumes and writes stale state
```

Nếu chỉ dựa vào “A nghĩ mình đang giữ lock”, stale owner có thể overwrite dữ liệu mới.

Distributed systems không có assumption an toàn rằng process sẽ luôn nhận biết lease expiry đúng thời điểm.

## 3. How does it work?

Fencing biến ownership thành ordering:

```text
A -> token 41
B -> token 42
Storage remembers maxToken = 42
A tries write token 41 -> reject
```

Storage phải enforce token ordering. Nếu fencing token chỉ được log nhưng database/resource không kiểm tra, nó không bảo vệ gì.

Token có thể là sequence number, database version hoặc monotonically increasing lease generation.

## 4. Practical implementation

Một simplified SQL boundary:

```sql
UPDATE ScheduledJobs
SET LastProcessedAt = @time,
    LastFencingToken = @token
WHERE JobName = @jobName
  AND LastFencingToken < @token;
```

Application kiểm tra affected rows:

```csharp
var rows = await db.Database.ExecuteSqlInterpolatedAsync($"""
    UPDATE ScheduledJobs
    SET LastProcessedAt = {now},
        LastFencingToken = {token}
    WHERE JobName = {jobName}
      AND LastFencingToken < {token}
    """, ct);

if (rows == 0)
    throw new StaleLeaseOwnerException();
```

Production implementation còn cần atomic token issuance và lease store semantics.

## 5. Real production scenario

Một scheduled billing job chạy trên nhiều app instances. Team dùng Redis lock TTL 30 giây. Một instance bị long GC pause hoặc network partition. Lock hết hạn, instance khác tiếp quản và xử lý customer batch.

Instance cũ quay lại, vẫn còn code path đang chạy và ghi trạng thái cũ. Nếu operation không idempotent/fenced, billing có thể bị double processing hoặc state regression.

## 6. Failure scenario & troubleshooting

**Symptom** → log cho thấy tại một thời điểm có hai workers đều “đã lấy lock” ở các generation khác nhau.

**Evidence** → write từ worker cũ xảy ra sau write của worker mới.

**Hypothesis** → lock TTL hết hạn trong khi old owner vẫn thực thi.

**Diagnosis** → correlate lease generation, process pauses, network latency và write timestamps.

**Fix** → thêm fencing token tại resource boundary, cộng với idempotency nếu side effect external.

**Verification** → fault-injection pause worker vượt TTL rồi xác nhận stale write bị reject.

## 7. Common mistakes

* Nghĩ distributed lock tạo mutual exclusion tuyệt đối trong mọi failure mode.
* Renew lease bằng background timer nhưng không xử lý timer pause/network partition.
* Không enforce token ở resource cuối cùng.
* Dùng wall-clock timestamp làm fencing token mà không đảm bảo monotonic ordering.
* Dùng lock thay cho idempotency của business operation.

## 8. Alternatives

* Database row lock/transaction nếu coordination nằm trong cùng database và transaction ngắn.
* Unique constraints / compare-and-swap nếu invariant có thể encode trực tiếp.
* Queue partitioning/single consumer per key để tránh shared lock.
* Leader election platform-native cho control-plane style workloads.
* Idempotent operation nếu duplicate execution chấp nhận được.

## 9. Trade-offs

### Advantages

* Fencing bảo vệ khỏi stale owner sau lease expiry.
* Lease tránh lock vô hạn khi owner crash.
* Token tạo ordering evidence hữu ích khi troubleshooting.

### Costs / Risks

* Resource phải hỗ trợ conditional write/token validation.
* Token generation phải monotonic và atomic.
* Complexity cao hơn simple lock.
* External systems không hỗ trợ fencing vẫn cần idempotency/compensation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu lock có TTL để process crash không giữ lock mãi.

### Middle

Biết implement lease acquire/renew/release và xử lý cancellation.

### Senior

Hiểu stale-owner problem, network partition, pause và fencing requirement.

### Technical Lead / Architect

Quyết định coordination có thực sự cần lock hay invariant nên được enforce bằng database/queue/idempotency; thiết kế fencing tại đúng resource boundary.

## 11. Key takeaway

* Lease expiration không đảm bảo old owner đã dừng.
* Fencing token bảo vệ resource khỏi stale owner bằng monotonic ordering.
* Distributed lock không thay thế idempotency hoặc database invariant.
* Nếu có thể tránh shared lock bằng ownership/partitioning, thường đơn giản hơn.

# 6. Azure Event Grid retry, dead-letter và idempotent handler: event delivery đáng tin cậy không đồng nghĩa exactly-once processing

## 1. What is it?

Azure Event Grid là event routing service cho publish/subscribe integration. Publisher phát event; Event Grid route tới subscriptions như webhook, Azure Function, Service Bus hoặc các supported destinations.

Điểm cần nhớ: delivery có thể được retry và event có thể được giao hơn một lần. Consumer phải được thiết kế để duplicate không gây duplicate business effect.

## 2. Why does it exist?

Nếu mỗi publisher gọi trực tiếp mọi downstream service, coupling tăng nhanh:

```text
Order Service
 ├─ calls Email
 ├─ calls Analytics
 ├─ calls Search
 └─ calls Audit
```

Event routing tách publisher khỏi danh sách subscriber:

```text
Order Service → Event Grid → Email
                         → Analytics
                         → Search
                         → Audit
```

Publisher chỉ phát fact/event; subscribers tự sở hữu reaction của mình.

## 3. How does it work?

Delivery flow:

```text
Publisher
   ↓
Topic / Event Grid
   ↓
Subscription filter
   ↓
Endpoint
   ├─ 2xx → success
   └─ failure → retry policy
                 ↓
              eventually dead-letter
```

Consumer cần phân biệt:

* transport delivery success,
* business processing success,
* duplicate handling,
* poison event handling.

## 4. Practical implementation

Một webhook handler có thể deduplicate bằng event ID:

```csharp
app.MapPost("/events/order", async (
    CloudEvent evt,
    EventDbContext db,
    CancellationToken ct) =>
{
    var exists = await db.ProcessedEvents.AnyAsync(
        x => x.EventId == evt.Id,
        ct);

    if (exists)
        return Results.Ok();

    await using var tx = await db.Database.BeginTransactionAsync(ct);

    // Apply business effect.
    await HandleOrderEventAsync(evt, db, ct);

    db.ProcessedEvents.Add(new ProcessedEvent(evt.Id!, DateTimeOffset.UtcNow));
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);

    return Results.Ok();
});
```

Deduplication record và business effect nên nằm trong cùng transaction nếu cùng database.

## 5. Real production scenario

Product catalog publish `ProductUpdated`. Search indexing subscriber tạm unavailable 5 phút. Event Grid retry. Một event được deliver nhiều lần trong recovery window.

Nếu handler chỉ upsert search document theo product ID/version, duplicate thường harmless. Nếu handler “increment counter” mỗi event, duplicate có thể tạo sai dữ liệu trừ khi có deduplication.

## 6. Failure scenario & troubleshooting

**Symptom** → downstream record được xử lý hai lần dù publisher chỉ phát một event.

**Evidence** → same event ID xuất hiện ở handler logs nhiều lần.

**Hypothesis** → retry/redelivery sau transient endpoint failure hoặc timeout ambiguity.

**Diagnosis** → kiểm tra subscription delivery logs, endpoint response codes và processing duration.

**Fix** → idempotent handler/dedup store; cấu hình dead-letter destination; giảm processing time bằng queue nếu cần.

**Verification** → replay cùng event nhiều lần và xác nhận business state không thay đổi ngoài lần đầu.

## 7. Common mistakes

* Giả định event chỉ được deliver một lần.
* Handler làm work dài rồi timeout HTTP endpoint.
* Không có dead-letter destination cho event không deliver được.
* Event payload chứa quá nhiều mutable state mà không version contract.
* Consumer dependency failure nhưng vẫn trả 2xx trước khi durable handoff.

## 8. Alternatives

* Azure Service Bus: phù hợp command/work queue, lock/settlement, ordering/session cần mạnh hơn.
* Direct HTTP: đơn giản khi chỉ có một dependency và synchronous result thực sự cần thiết.
* Event Hubs: phù hợp high-throughput event streaming/telemetry.
* Database outbox + broker: cần khi publisher phải atomically persist state + event intent.

## 9. Trade-offs

### Advantages

* Loose coupling giữa publisher và subscribers.
* Filtering/routing managed service.
* Retry/dead-letter giúp xử lý transient failures.

### Costs / Risks

* Eventual consistency.
* Duplicate delivery vẫn phải xử lý.
* Debugging end-to-end khó hơn direct call.
* Contract/version governance trở thành kiến trúc concern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Event Grid route events từ publisher tới subscribers.

### Middle

Implement subscription handler, filter và dead-letter awareness.

### Senior

Thiết kế idempotency, schema evolution, retry, timeout và observability.

### Technical Lead / Architect

Chọn đúng primitive giữa Event Grid, Service Bus, Event Hubs và direct HTTP; xác định ownership của event contracts và delivery SLO.

## 11. Key takeaway

* Event delivery managed không đồng nghĩa exactly-once business processing.
* Consumer phải chịu được duplicate và transient failure.
* Dead-letter chỉ hữu ích khi có owner, alert và replay procedure.
* Chọn messaging service theo semantics, không theo việc “đều gửi message”.

# 7. Kubernetes resource requests, limits, CPU throttling và `OOMKilled`: capacity configuration có thể tự tạo latency và restart loop

## 1. What is it?

Kubernetes `requests` mô tả lượng resource scheduler dùng để placement pod. `limits` đặt upper bound cho một số resource behavior.

Ví dụ:

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"
```

CPU và memory có failure semantics khác nhau:

* CPU limit có thể dẫn tới throttling.
* Memory vượt hard limit thường dẫn tới container bị kill với `OOMKilled`.

## 2. Why does it exist?

Cluster có nhiều workloads cạnh tranh tài nguyên. Scheduler cần estimate để đặt pods lên nodes mà không oversubscribe hoàn toàn.

Không có resource boundaries:

* noisy neighbor có thể chiếm node,
* scheduling khó dự đoán,
* autoscaling signal thiếu context,
* outage của một workload lan sang workload khác.

Nhưng resource config sai cũng tự tạo incident.

## 3. How does it work?

Scheduler chủ yếu dùng requests khi placement.

CPU là compressible resource: khi thiếu CPU, process chậm hơn/throttled.

Memory là incompressible: nếu process cần thêm memory mà không còn headroom, container có thể bị killed.

```text
Traffic ↑
  ↓
CPU usage reaches quota
  ↓
CPU throttling
  ↓
request duration ↑
  ↓
timeout / retry ↑
```

Memory:

```text
Working set ↑ > limit
  ↓
OOM kill
  ↓
container restart
  ↓
possible CrashLoopBackOff
```

## 4. Practical implementation

Không nên copy resource values từ service khác. Bắt đầu từ measurement dưới representative load.

Useful signals:

* CPU usage vs request vs limit,
* CPU throttled seconds,
* working set/RSS,
* OOM kill count,
* restart count,
* request latency,
* GC heap/LOH cho .NET,
* node pressure.

Với .NET service, đo bằng application telemetry + container metrics + `dotnet-counters` khi cần.

## 5. Real production scenario

Một API .NET có CPU limit `250m` vì “service nhẹ”. Bình thường ổn. Khi traffic tăng, serialization + TLS + JSON processing dùng CPU cao hơn. Container bị throttled, request latency tăng, upstream retry, load lại tăng.

Không có crash, nên team ban đầu tưởng database chậm. Container metrics mới cho thấy CPU throttling là bottleneck thật.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 latency tăng nhưng application CPU metric nhìn như không bao giờ vượt 25% core.

**Evidence** → container CPU throttling time cao, CPU limit thấp.

**Hypothesis** → cgroup quota đang giới hạn process.

**Diagnosis** → compare usage, request, limit, throttling, node capacity và load pattern.

**Fix** → điều chỉnh CPU limit/request hoặc bỏ CPU limit theo platform policy; scale appropriately.

**Verification** → load test, xác nhận throttling giảm và latency cải thiện mà không gây node contention.

Với memory:

**Symptom** → pod restart, exit code/OOMKilled.

**Evidence** → working set tiến sát memory limit.

**Fix** → phân biệt memory leak với legitimate peak, tăng limit hoặc sửa allocation/retention root cause.

## 7. Common mistakes

* Set request = limit cho mọi workload mà không hiểu QoS/capacity implication.
* CPU limit quá thấp gây throttling rồi tăng replica để chữa triệu chứng.
* Tăng memory limit vô hạn thay vì điều tra leak.
* Không reserve memory đủ cho native/runtime overhead ngoài managed heap.
* Chỉ xem pod restart mà không xem reason `OOMKilled`.

## 8. Alternatives

* App Service/Container Apps nếu team không cần trực tiếp quản lý Kubernetes scheduling/resource semantics.
* Vertical Pod Autoscaler cho recommendation/automation phù hợp use case.
* Horizontal Pod Autoscaler khi scale-out theo CPU/custom metrics hợp lý.
* Dedicated nodes/node pools cho workloads có isolation requirements.

## 9. Trade-offs

### Advantages

* Requests giúp scheduling predictable hơn.
* Limits giảm khả năng một workload chiếm toàn node.
* Resource policy tốt hỗ trợ capacity planning và autoscaling.

### Costs / Risks

* Limit sai có thể gây throttling/OOM.
* Request quá cao làm cluster utilization kém.
* Request quá thấp gây overcommit và node pressure.
* Tuning cần production-like measurement, không chỉ local test.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request dùng cho scheduling và memory limit có thể dẫn tới OOM kill.

### Middle

Đọc pod status, resource metrics và xác định throttling/OOM symptoms.

### Senior

Correlate container resources với .NET runtime metrics, latency và autoscaling behavior.

### Technical Lead / Architect

Thiết lập resource policy, SLO/capacity model và quyết định Kubernetes có đáng operational complexity hay không.

## 11. Key takeaway

* CPU saturation và memory exhaustion có failure semantics khác nhau.
* Resource limits không phải giá trị “an toàn mặc định”; chúng là capacity policy cần đo.
* Container metrics phải được correlate với application latency và runtime telemetry.
* Scale-out không chữa được mọi resource misconfiguration.

# 8. Application Insights dependency correlation: nối request, SQL, HTTP và messaging thành một distributed trace có thể điều tra

## 1. What is it?

Dependency correlation là việc liên kết incoming request với các downstream operations như HTTP call, SQL query, Redis call hoặc message handling trong cùng distributed trace.

Thay vì chỉ có log rời rạc:

```text
API request slow
SQL query slow
HTTP dependency slow
```

trace cho thấy quan hệ cha-con:

```text
Request /checkout 820ms
 ├─ SQL Orders 35ms
 ├─ HTTP Pricing 610ms
 └─ Redis 8ms
```

## 2. Why does it exist?

Trong distributed system, một user request có thể đi qua nhiều services. Không có correlation, production investigation thường dựa vào timestamp gần đúng và text search.

Điều đó đặc biệt tệ khi:

* traffic cao,
* nhiều requests cùng lúc,
* retry tạo nhiều dependency calls,
* async messaging tách execution theo thời gian.

Distributed tracing tạo causal context thay vì chỉ temporal proximity.

## 3. How does it work?

OpenTelemetry/modern .NET dùng trace/span model. W3C Trace Context truyền identifiers qua HTTP headers như `traceparent`.

```text
Browser
  ↓ traceparent
API A span
  ↓ traceparent
API B span
  ↓
SQL dependency span
```

Application Insights có thể ingest telemetry và hiển thị operation/dependency relationship. Với messaging, producer và consumer có thể link context tùy instrumentation và propagation model.

## 4. Practical implementation

ASP.NET Core với OpenTelemetry:

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddSqlClientInstrumentation()
        .AddSource("Checkout.Application"));
```

Custom span:

```csharp
private static readonly ActivitySource ActivitySource =
    new("Checkout.Application");

using var activity = ActivitySource.StartActivity("CalculateCheckout");
activity?.SetTag("checkout.mode", "standard");
```

Không nên đưa PII hoặc high-cardinality identifiers thiếu kiểm soát vào tags.

## 5. Real production scenario

Checkout p95 tăng từ 400 ms lên 1.2 s. API logs không có exception. Application Insights trace cho thấy 80% thời gian nằm trong Pricing HTTP dependency, riêng khi request retry hai lần thì tổng latency tăng mạnh.

Team không cần tối ưu SQL vì SQL chỉ chiếm 40 ms. Evidence đổi hướng investigation ngay lập tức.

## 6. Failure scenario & troubleshooting

**Symptom** → trace bị đứt giữa API A và API B.

**Evidence** → API B tạo trace ID mới thay vì tiếp tục incoming context.

**Hypothesis** → custom HTTP client/proxy/message transport không propagate trace headers.

**Diagnosis** → inspect headers/Activity context và instrumentation coverage.

**Fix** → dùng supported instrumentation hoặc explicit context propagation tại boundary.

**Verification** → end-to-end request hiển thị cùng trace tree qua tất cả expected services.

## 7. Common mistakes

* Chỉ log `TraceIdentifier` của từng process mà không propagate distributed context.
* Gắn user IDs, full payload hoặc secrets vào span tags.
* Sampling quá mạnh làm mất traces của rare failures mà không có strategy.
* Tạo custom spans cho mọi method khiến telemetry noise lớn.
* Không instrument outbound dependencies nên root span chỉ cho biết “request chậm”.

## 8. Alternatives

* Structured logs + correlation ID: đơn giản hơn nhưng ít causal structure.
* Metrics: tốt cho aggregate symptom, không thay trace detail.
* Vendor-specific APM auto-instrumentation.
* Full OpenTelemetry pipeline export sang backend khác ngoài Application Insights.

## 9. Trade-offs

### Advantages

* Cho thấy latency nằm ở dependency nào.
* Hỗ trợ root-cause investigation nhanh hơn text log search.
* Correlate retry, fan-out và nested operations.

### Costs / Risks

* Telemetry volume/cost tăng nếu không sampling hợp lý.
* Instrumentation gaps tạo trace không hoàn chỉnh.
* High-cardinality tags có cost và privacy risk.
* Trace không thay thế metrics/alerts cho system-wide symptom detection.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace gồm parent/child spans mô tả một request qua nhiều operations.

### Middle

Enable ASP.NET Core/HttpClient/SQL instrumentation và dùng trace để debug latency.

### Senior

Thiết kế sampling, custom spans, attribute conventions và message propagation.

### Technical Lead / Architect

Đặt observability standard xuyên services: Logs + Metrics + Traces + Alerts, retention/cost budget và incident workflow.

## 11. Key takeaway

* Distributed trace trả lời “thời gian đi đâu” theo causal path.
* Correlation phải được propagate qua mọi boundary quan trọng.
* Trace là một signal; metrics phát hiện symptom, logs chứa detail, alerts kích hoạt response.
* Instrumentation phải có cardinality, privacy và cost discipline.

# 9. Mutation testing: kiểm tra test suite có thật sự bắt lỗi logic hay chỉ đang tăng coverage percentage

## 1. What is it?

Mutation testing cố ý tạo các thay đổi nhỏ vào production code rồi chạy test suite xem tests có phát hiện được không.

Ví dụ original:

```csharp
return total >= threshold;
```

Mutant:

```csharp
return total > threshold;
```

Nếu tests vẫn pass, mutant “survived”. Điều đó cho thấy code đã được execute có thể có coverage, nhưng assertions chưa đủ mạnh để phân biệt behavior đúng/sai.

## 2. Why does it exist?

Code coverage trả lời chủ yếu:

> Dòng/branch này có được chạy trong test không?

Nó không đảm bảo:

> Test có thật sự kiểm tra outcome đúng không?

Một test có thể execute 100% method nhưng không assert kết quả quan trọng.

Mutation testing tạo pressure lên **test effectiveness**, không chỉ execution.

## 3. How does it work?

Mutation engine tạo biến thể như:

* `>` thành `>=`,
* `true` thành `false`,
* `+` thành `-`,
* bỏ method call,
* thay logical operator.

Sau đó chạy targeted tests.

```text
Original code
   ↓
Generate mutants
   ↓
Run tests per mutant
   ├─ test fails → mutant killed
   └─ tests pass → mutant survived
```

Mutation score thường là tỷ lệ mutants bị killed trên tập mutants có ý nghĩa.

## 4. Practical implementation

Trong .NET, tool phổ biến như Stryker.NET có thể chạy mutation tests cho project test.

Một test có giá trị:

```csharp
[Fact]
public void IsEligible_WhenScoreEqualsThreshold_ReturnsTrue()
{
    var result = Eligibility.IsEligible(score: 80, threshold: 80);

    Assert.True(result);
}
```

Test boundary này sẽ kill mutant `>=` → `>`.

Điều quan trọng là dùng mutation testing có chọn lọc cho domain logic có risk cao, không nhất thiết chạy toàn monorepo mỗi commit.

## 5. Real production scenario

Payroll rule có nhiều boundary conditions. Coverage report 92%, nhưng bug vẫn lọt ở trường hợp `hours == overtimeThreshold`.

Mutation testing cho thấy mutant đổi `>=` thành `>` vẫn sống. Team thêm boundary tests và cải thiện confidence đúng chỗ thay vì tăng thêm trivial tests cho DTO constructors.

## 6. Failure scenario & troubleshooting

**Symptom** → mutation run cực chậm, hàng nghìn mutants không mang nhiều giá trị.

**Evidence** → tool mutate generated code, logging glue và trivial property mapping.

**Hypothesis** → scope quá rộng.

**Diagnosis** → inspect surviving/timeout mutants theo namespace/module.

**Fix** → tập trung domain-critical modules, exclude generated/infrastructure code hợp lý và chạy theo pipeline tier.

**Verification** → mutation run ngắn hơn nhưng vẫn bao phủ high-risk business rules.

## 7. Common mistakes

* Dùng mutation score như KPI buộc team đạt 100%.
* Viết tests vô nghĩa chỉ để kill mutant.
* Chạy mutation toàn solution ở mỗi commit dù mất hàng chục phút.
* Coi surviving mutant luôn là bug; một số mutant có thể equivalent.
* Bỏ qua test readability/maintenance để tối đa score.

## 8. Alternatives

* Branch/condition coverage: nhanh hơn, ít sâu hơn về assertion quality.
* Property-based testing: mạnh với invariants và input space rộng.
* Integration/E2E tests: kiểm tra wiring/behavior xuyên boundary.
* Manual fault injection/chaos testing cho operational failures.

## 9. Trade-offs

### Advantages

* Phát hiện tests chạy code nhưng không assert behavior.
* Tốt cho business rules và edge cases.
* Tạo feedback cụ thể về weak tests.

### Costs / Risks

* Compute cost cao hơn normal test suite.
* Có equivalent mutants và noise.
* Dễ bị biến thành vanity metric.
* Không thay integration testing cho infrastructure behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu coverage cao không đảm bảo tests tốt.

### Middle

Đọc surviving mutants và bổ sung boundary assertions hợp lý.

### Senior

Chọn module nào đáng mutation test dựa trên risk và business criticality.

### Technical Lead / Architect

Thiết kế test strategy theo risk: unit, integration, E2E, mutation, contract tests; kiểm soát pipeline cost thay vì tối đa mọi metric.

## 11. Key takeaway

* Coverage cho biết code được chạy; mutation testing kiểm tra test có phân biệt đúng/sai hay không.
* Mutation testing có giá trị nhất ở logic critical, không phải mọi file.
* Mutation score là diagnostic signal, không nên trở thành mục tiêu tuyệt đối.
* Test quality phải gắn với business risk và failure impact.

# 10. Risk-based PR review: tập trung review vào blast radius, invariants và rollback risk thay vì đọc mọi dòng với cùng mức độ ưu tiên

## 1. What is it?

Risk-based PR review là cách phân bổ attention của reviewer theo **mức độ rủi ro của thay đổi**, không chỉ theo số dòng code.

Một PR 20 dòng thay đổi authorization check có thể rủi ro hơn PR 500 dòng refactor CSS.

Mental model:

```text
Review priority ≈ probability of defect × impact if defect occurs
```

Các dimension thường gồm:

* security boundary,
* money/data integrity,
* transaction behavior,
* backward compatibility,
* concurrency,
* migration/deployment,
* irreversible side effects,
* observability/rollback.

## 2. Why does it exist?

Reviewer attention là resource hữu hạn. Đọc mọi dòng với cùng depth dẫn tới hai vấn đề:

1. review tốn thời gian nhưng vẫn bỏ sót critical risks,
2. team tập trung style/naming trong khi transaction, authorization hoặc migration risk chưa được kiểm tra.

Senior review cần chuyển câu hỏi từ:

> “Code có sạch không?”

sang:

> “Thay đổi này có thể phá invariant nào, ở failure mode nào, và chúng ta phát hiện/rollback thế nào?”

## 3. How does it work?

Một reviewer có thể đi theo flow:

```text
Understand intent
   ↓
Map changed boundaries
   ↓
Identify high-risk invariants
   ↓
Inspect implementation
   ↓
Verify tests/evidence
   ↓
Check rollout + observability + rollback
```

Ví dụ với payment PR:

* request retry có idempotent không?
* database transaction boundary ở đâu?
* external payment timeout thì state nào tồn tại?
* webhook có duplicate không?
* logs có correlation ID không?
* rollback có ảnh hưởng schema/data không?

## 4. Practical implementation

Một PR description hữu ích nên nêu:

```text
Change:
- Add partial refund flow.

Risk boundaries:
- Payment provider call.
- Refund idempotency.
- Order financial state transition.

Verification:
- Integration tests for duplicate webhook.
- Failure test for provider timeout.
- Dashboard query for refund errors.

Rollout:
- Feature flag 10% -> 100%.
- Roll back application only; schema is backward-compatible.
```

Reviewer sau đó có thể ưu tiên kiểm tra các boundary này trước style detail.

## 5. Real production scenario

Một PR thêm field optional vào API chỉ 30 dòng nhưng thay đổi database migration thành `NOT NULL` với default computation trên bảng hàng trăm triệu rows. Functional tests pass, code nhìn đơn giản.

Risk-based review nhận ra deployment risk:

* table lock/long migration,
* old application version compatibility,
* rollback incompatibility.

Giải pháp có thể là Expand–Migrate–Contract thay vì migration trực tiếp.

## 6. Failure scenario & troubleshooting

**Symptom** → production incident xảy ra ở behavior không ai thảo luận trong PR dù test coverage cao.

**Evidence** → review comments chủ yếu naming/style; không có discussion về retry, migration hoặc authorization.

**Hypothesis** → review process tối ưu code aesthetics thay vì system risk.

**Diagnosis** → post-incident mapping: failure boundary có xuất hiện trong diff/PR description không? reviewer có evidence để nhận ra không?

**Fix** → thêm risk prompts vào PR template, owner-specific review cho security/data/deployment changes và yêu cầu rollout evidence ở PR rủi ro cao.

**Verification** → audit các PR sau đó xem high-risk changes có explicit risk + test + rollback plan không.

## 7. Common mistakes

* Đánh giá PR bằng số dòng thay đổi.
* Review style thủ công dù formatter/analyzer xử lý được.
* Chỉ đọc diff mà không hiểu runtime flow trước/sau.
* Approve migration mà không xem data volume/backward compatibility.
* Xem unit tests như bằng chứng đủ cho integration boundary.
* Yêu cầu mọi PR cùng một checklist khổng lồ, tạo compliance fatigue.

## 8. Alternatives

* Traditional line-by-line review: vẫn cần nhưng không đủ cho system risk.
* Pair programming/mob review: tốt cho thay đổi phức tạp cần shared reasoning.
* Architecture review/ADR: phù hợp decision có blast radius dài hạn.
* Automated static analysis/security scanning: giảm review effort cho machine-detectable issues.

## 9. Trade-offs

### Advantages

* Reviewer attention tập trung vào failure impact cao.
* Tăng khả năng phát hiện design/operational issues trước merge.
* Giảm noise từ style issues đã tự động hóa được.

### Costs / Risks

* Risk assessment phụ thuộc kinh nghiệm và domain knowledge.
* Có thể bỏ sót low-risk-looking bug nếu reviewer quá chủ quan.
* PR template quá nặng làm team bypass process.
* Cần ownership rõ cho security/data/platform boundaries.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Học đọc PR theo intent và test behavior, không chỉ syntax.

### Middle

Nhận diện common risks: nullability, validation, transactions, API compatibility, missing tests.

### Senior

Đánh giá blast radius, failure modes, data consistency, concurrency, rollout và observability.

### Technical Lead / Architect

Thiết kế review policy theo risk tiers, ownership và automated controls; quyết định khi nào PR cần architecture/security/database review chuyên sâu.

## 11. Key takeaway

* Không phải mọi dòng code có cùng mức rủi ro.
* Review tốt tập trung vào invariants, boundaries, failure modes và rollback.
* Automation nên xử lý style/static checks để con người tập trung vào engineering judgment.
* High-risk change cần evidence: tests, observability, rollout và recovery plan.
