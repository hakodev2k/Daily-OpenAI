# 1. C# covariance / contravariance: generic type safety, API design và những giới hạn thực tế

## 1. What is it?

Covariance và contravariance là cơ chế cho phép một số generic interfaces và delegates giữ được quan hệ type hierarchy một cách an toàn.

Mental model ngắn gọn:

- **Covariance**: type chỉ đi “ra ngoài” — producer.
- **Contravariance**: type chỉ đi “vào trong” — consumer.

Ví dụ: nếu `Dog : Animal`, thì `IEnumerable<Dog>` có thể được dùng như `IEnumerable<Animal>` vì collection này chỉ expose `Dog` ra ngoài; caller đọc `Dog` dưới dạng `Animal` là an toàn.

Ngược lại, `IComparer<Animal>` có thể được dùng nơi cần `IComparer<Dog>` vì comparer nhận input là `Dog`, mà mọi `Dog` cũng là `Animal`.

## 2. Why does it exist?

Không có variance, generic APIs sẽ quá cứng nhắc. Một API chỉ đọc dữ liệu kiểu `Dog` nhưng không thể truyền vào nơi cần sequence của `Animal` sẽ khiến developer phải copy collection hoặc viết adapter vô nghĩa.

Variance tồn tại để giữ type safety nhưng vẫn cho phép reuse theo hướng mà runtime có thể chứng minh là an toàn.

## 3. How does it work?

C# dùng `out` và `in` trên generic type parameter:

```csharp
public interface IProducer<out T>
{
    T Create();
}

public interface IConsumer<in T>
{
    void Handle(T value);
}
```

`out T` nghĩa là `T` chỉ được dùng ở output position phù hợp.

`in T` nghĩa là `T` chỉ được dùng ở input position phù hợp.

Ví dụ:

```csharp
IProducer<Dog> dogProducer = new DogProducer();
IProducer<Animal> animalProducer = dogProducer;

IConsumer<Animal> animalConsumer = new AnimalConsumer();
IConsumer<Dog> dogConsumer = animalConsumer;
```

Nếu generic type vừa đọc vừa ghi cùng `T`, variance thường không thể áp dụng an toàn.

## 4. Practical implementation

Một message pipeline:

```csharp
public interface IMessageHandler<in TMessage>
{
    Task HandleAsync(TMessage message, CancellationToken ct);
}

public abstract record IntegrationMessage;
public sealed record CustomerCreated(Guid CustomerId) : IntegrationMessage;

public sealed class AuditHandler : IMessageHandler<IntegrationMessage>
{
    public Task HandleAsync(IntegrationMessage message, CancellationToken ct)
    {
        Console.WriteLine($"Audit: {message.GetType().Name}");
        return Task.CompletedTask;
    }
}
```

Vì handler chỉ consume message, contravariance cho phép dùng `IMessageHandler<IntegrationMessage>` ở context xử lý `CustomerCreated`.

## 5. Real production scenario

Trong integration platform, nhiều domain events kế thừa từ một base event. Một cross-cutting audit handler xử lý mọi event, trong khi các handlers chuyên biệt chỉ xử lý từng loại.

Nếu interface generic được thiết kế đúng variance, registration và composition trở nên đơn giản hơn. Nếu interface vô tình expose `T` theo cả input/output directions, flexibility này biến mất.

## 6. Failure scenario & troubleshooting

**Symptom**  
Developer nghĩ type hierarchy là hợp lệ nhưng compiler không cho assign `ICollection<Dog>` sang `ICollection<Animal>`.

**Evidence**  
`ICollection<T>` cho phép vừa đọc vừa thêm phần tử.

**Hypothesis**  
Generic abstraction đang invariant vì write path có thể phá type safety.

**Diagnosis**  
Kiểm tra `T` xuất hiện ở input hay output position nào.

**Fix**  
Nếu caller chỉ cần đọc, expose `IReadOnlyCollection<T>` hoặc `IEnumerable<T>` thay vì mutable collection.

**Verification**  
API compile được mà không cần cast nguy hiểm, đồng thời mutation boundary vẫn rõ.

## 7. Common mistakes

* Nghĩ mọi generic collection đều covariance.
* Dùng cast để “ép” variance thay vì sửa abstraction.
* Expose mutable collection dù caller chỉ cần read access.
* Thêm `in` / `out` chỉ để compiler hết lỗi mà không hiểu safety rule.
* Over-engineer domain model bằng inheritance chỉ để tận dụng variance.

## 8. Alternatives

* Composition thay vì inheritance nếu type hierarchy không phản ánh domain.
* Non-generic interface khi abstraction thực sự không cần type parameter.
* Explicit adapter khi conversion có business meaning chứ không chỉ type compatibility.

## 9. Trade-offs

### Advantages

* API linh hoạt hơn mà vẫn compile-time safe.
* Giảm adapters/copies không cần thiết.
* Giúp diễn đạt rõ producer vs consumer responsibilities.

### Costs / Risks

* Generic API khó đọc hơn với team ít quen variance.
* Thiết kế sai direction làm interface khó evolve.
* Không áp dụng được cho mọi mutable abstraction.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu covariance = produce, contravariance = consume.

### Middle

Biết đọc `in` / `out`, hiểu tại sao `IEnumerable<T>` và `IComparer<T>` có behavior khác nhau.

### Senior

Thiết kế generic boundary có chủ đích thay vì expose mutable types quá rộng.

### Technical Lead / Architect

Đánh giá liệu abstraction generic có thật sự cải thiện reuse hay đang tạo type-system complexity không cần thiết.

## 11. Key takeaway

* Variance là type-safety mechanism, không phải syntax trick.
* Read-only abstractions thường linh hoạt hơn mutable abstractions.
* Thiết kế API theo producer/consumer responsibility giúp generic contracts rõ hơn.

# 2. ASP.NET Core Options Pattern: validation, reload và tránh biến configuration thành hidden mutable state

## 1. What is it?

Options Pattern map configuration vào strongly typed classes để application không phải đọc raw string keys ở khắp nơi.

Ba abstractions phổ biến:

- `IOptions<T>`: snapshot gần như cố định theo application lifetime.
- `IOptionsSnapshot<T>`: resolve theo scope, thường hữu ích trong web requests.
- `IOptionsMonitor<T>`: hỗ trợ change notifications và đọc giá trị hiện tại.

Mental model quan trọng: configuration là một dependency. Nếu configuration có thể thay đổi runtime, nó trở thành mutable dependency và cần được thiết kế giống mọi mutable state khác.

## 2. Why does it exist?

Code kiểu này khó maintain:

```csharp
var timeout = configuration["Payments:TimeoutSeconds"];
```

String key dễ typo, parsing lặp lại và validation bị phân tán. Options Pattern gom contract configuration thành object rõ ràng.

Nhưng chỉ bind object chưa đủ. Production failure thường đến từ config thiếu, sai range hoặc reload không được application xử lý nhất quán.

## 3. How does it work?

```text
appsettings / env vars / Key Vault
            |
            v
    Configuration providers
            |
            v
      Binder -> Options<T>
            |
            +--> validation
            +--> snapshot/monitor semantics
```

Config provider precedence cũng quan trọng. Environment variables có thể override JSON config, vì vậy giá trị runtime không nhất thiết giống file trong repository.

## 4. Practical implementation

```csharp
public sealed class PaymentOptions
{
    public const string SectionName = "Payments";

    [Range(1, 60)]
    public int TimeoutSeconds { get; init; }

    [Required]
    public string BaseUrl { get; init; } = string.Empty;
}
```

Đăng ký:

```csharp
builder.Services
    .AddOptions<PaymentOptions>()
    .Bind(builder.Configuration.GetSection(PaymentOptions.SectionName))
    .ValidateDataAnnotations()
    .Validate(o => Uri.TryCreate(o.BaseUrl, UriKind.Absolute, out _),
        "Payments:BaseUrl must be an absolute URI")
    .ValidateOnStart();
```

Consumer:

```csharp
public sealed class PaymentClient
{
    private readonly PaymentOptions _options;

    public PaymentClient(IOptions<PaymentOptions> options)
    {
        _options = options.Value;
    }
}
```

## 5. Real production scenario

Production deployment override `Payments__TimeoutSeconds=0` do typo trong pipeline variable. Nếu application chỉ bind config mà không validate, bug chỉ xuất hiện khi payment API được gọi.

Với `ValidateOnStart()`, instance fail fast ngay trong startup/health validation, trước khi nhận traffic.

## 6. Failure scenario & troubleshooting

**Symptom**  
Production trả timeout ngay lập tức hoặc gọi sai endpoint dù code release không đổi.

**Evidence**  
Deployment artifact giống staging, nhưng environment variables khác.

**Hypothesis**  
Runtime configuration override sai.

**Diagnosis**  
Inspect effective configuration source theo key, không log secrets. Kiểm tra options validation failure trong startup logs.

**Fix**  
Validate range/URI/required values; promotion pipeline phải kiểm tra required config trước traffic cutover.

**Verification**  
Startup health pass với config hợp lệ và fail có chủ đích khi config invalid.

## 7. Common mistakes

* Inject `IConfiguration` vào mọi class và đọc raw keys.
* Không `ValidateOnStart()` cho config critical.
* Dùng `IOptionsMonitor<T>` rồi giả định mọi dependency có thể đổi config an toàn giữa request.
* Log full options object chứa secrets.
* Bind config vào mutable static singleton.
* Dùng runtime reload cho những setting lẽ ra cần restart để giữ consistency.

## 8. Alternatives

* Direct `IConfiguration`: hợp lý ở composition root hoặc infrastructure glue nhỏ.
* Strongly typed Options: mặc định tốt cho application code.
* Dynamic feature/config service: phù hợp khi business thực sự cần runtime control, nhưng phải có audit/versioning/fallback.

## 9. Trade-offs

### Advantages

* Strong typing và validation.
* Config contract dễ test/document.
* Fail fast tốt hơn runtime surprise.

### Costs / Risks

* Dynamic reload làm semantics phức tạp.
* `IOptionsSnapshot`/`Monitor` không tự giải quyết consistency giữa nhiều services.
* Strong type không thay thế secret-management policy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết map config sang class thay vì đọc string key khắp nơi.

### Middle

Biết chọn `IOptions`, `IOptionsSnapshot`, `IOptionsMonitor` và validation.

### Senior

Hiểu provider precedence, startup validation, dynamic reload failure modes và secret exposure.

### Technical Lead / Architect

Quyết định config nào immutable theo release, config nào runtime mutable, ai sở hữu change control và rollback.

## 11. Key takeaway

* Configuration là dependency, không phải global bag of strings.
* Critical config nên fail fast bằng validation.
* Runtime reload chỉ nên dùng khi system có semantics rõ cho mutable configuration.

# 3. EF Core compiled queries: query-shape caching, parameterization và khi tối ưu này thực sự đáng giá

## 1. What is it?

EF Core phải biến LINQ expression thành query representation và SQL. EF Core đã cache query compilation dựa trên query shape trong nhiều trường hợp.

Compiled query APIs như `EF.CompileQuery` / `EF.CompileAsyncQuery` cho phép precompile một query delegate để giảm overhead lookup/compilation trong hot path.

Mental model quan trọng: compiled query tối ưu **client-side query processing overhead**, không làm database scan nhanh hơn và không sửa execution plan xấu.

## 2. Why does it exist?

Trong API throughput rất cao với query cực nhanh ở database, phần overhead LINQ expression processing có thể trở nên đáng kể tương đối.

Nhưng trong phần lớn enterprise queries, network + database I/O vẫn chiếm phần lớn latency. Vì vậy compiled query là optimization có điều kiện, không phải default style.

## 3. How does it work?

```text
LINQ expression
   |
   v
Query shape lookup / compile
   |
   v
SQL generation
   |
   v
DB execution plan
   |
   v
I/O + locks + rows
```

Compiled query chủ yếu tối ưu phần phía trên database boundary.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<EmployeeDto>>
    GetEmployeeById =
        EF.CompileAsyncQuery(
            (AppDbContext db, Guid id) =>
                db.Employees
                    .AsNoTracking()
                    .Where(x => x.Id == id)
                    .Select(x => new EmployeeDto(x.Id, x.Name)));
```

Usage:

```csharp
await foreach (var employee in GetEmployeeById(db, employeeId).WithCancellation(ct))
{
    return employee;
}

return null;
```

Trước khi làm vậy, đo bằng benchmark hoặc production profiling để xác minh query compilation overhead thực sự đáng kể.

## 5. Real production scenario

Một lookup API được gọi hàng chục nghìn lần/phút, query dùng PK index và database trả kết quả dưới 1 ms trong cùng region. CPU app cao hơn dự kiến dù DB load thấp.

Profiling cho thấy một phần đáng kể thời gian nằm ở repeated EF query setup. Đây là trường hợp compiled query có thể có ích.

Ngược lại, query report mất 300 ms vì I/O lớn sẽ gần như không được cứu bởi compiled query.

## 6. Failure scenario & troubleshooting

**Symptom**  
Team thêm compiled queries nhưng p95 vẫn gần như không đổi.

**Evidence**  
Trace cho thấy 95% latency nằm ở SQL execution.

**Hypothesis**  
Tối ưu sai layer.

**Diagnosis**  
Tách latency thành application overhead, network và database execution.

**Fix**  
Điều tra execution plan, indexes, result-set size, round trips trước; chỉ giữ compiled query nếu benchmark chứng minh lợi ích.

**Verification**  
So sánh CPU/request và p95 dưới load thực tế.

## 7. Common mistakes

* Compile mọi query vì nghĩ “compiled luôn nhanh hơn”.
* Dùng compiled query để che N+1 hoặc bad access pattern.
* Constant hóa dynamic values làm query shape thay đổi không cần thiết.
* Benchmark in-memory hoặc không có representative DB latency.
* Tối ưu microseconds trong khi endpoint có external dependency 200 ms.

## 8. Alternatives

* Normal LINQ query: default tốt cho đa số cases.
* Raw SQL / Dapper: khi cần control SQL mapping/overhead rõ ràng.
* Stored procedures: khi logic dữ liệu/operational ownership justify.

## 9. Trade-offs

### Advantages

* Giảm app-side overhead cho hot, stable query shapes.
* Có thể giảm CPU ở high-throughput scenarios.

### Costs / Risks

* Code kém tự nhiên hơn.
* Ít linh hoạt với dynamic query composition.
* Dễ tạo cảm giác “đã tối ưu” trong khi bottleneck nằm ở DB.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ không chạy trực tiếp; EF phải translate sang SQL.

### Middle

Biết dùng projection, `AsNoTracking`, parameterized queries trước khi nghĩ compiled query.

### Senior

Biết profiling client vs server latency và benchmark hot path.

### Technical Lead / Architect

Đặt performance discipline: tối ưu dựa trên evidence, không biến compiled query thành convention toàn codebase.

## 11. Key takeaway

* Compiled query không sửa execution plan xấu.
* Đây là optimization cho hot path đã được đo.
* Query shape, round trips và DB I/O thường quan trọng hơn micro-optimization phía EF.

# 4. SQL window functions: ranking, running totals và tránh query lồng phức tạp không cần thiết

## 1. What is it?

Window functions tính toán trên một tập rows liên quan đến current row mà không collapse rows như `GROUP BY`.

Các hàm phổ biến:

- `ROW_NUMBER()`
- `RANK()` / `DENSE_RANK()`
- `SUM() OVER(...)`
- `LAG()` / `LEAD()`

Mental model: mỗi row vẫn tồn tại, nhưng được “nhìn” trong một window được xác định bởi `PARTITION BY` và `ORDER BY`.

## 2. Why does it exist?

Nhiều bài toán reporting cần vừa giữ row detail vừa tính rank, running total, previous value hoặc top-N per group.

Nếu không có window functions, developer thường dùng correlated subqueries hoặc self-joins phức tạp, khó đọc và có thể tốn I/O hơn.

## 3. How does it work?

Ví dụ xếp hạng nhân viên theo giờ làm trong từng department:

```sql
SELECT
    DepartmentId,
    EmployeeId,
    TotalHours,
    ROW_NUMBER() OVER (
        PARTITION BY DepartmentId
        ORDER BY TotalHours DESC
    ) AS RankInDepartment
FROM MonthlyHours;
```

`PARTITION BY` chia logical groups; `ORDER BY` xác định thứ tự trong từng group.

## 4. Practical implementation

Lấy 3 nhân viên có nhiều giờ overtime nhất mỗi department:

```sql
WITH Ranked AS
(
    SELECT
        DepartmentId,
        EmployeeId,
        OvertimeHours,
        ROW_NUMBER() OVER (
            PARTITION BY DepartmentId
            ORDER BY OvertimeHours DESC, EmployeeId
        ) AS rn
    FROM EmployeeMonthlySummary
    WHERE MonthKey = @MonthKey
)
SELECT DepartmentId, EmployeeId, OvertimeHours
FROM Ranked
WHERE rn <= 3;
```

Tie-breaker `EmployeeId` giúp ordering deterministic.

## 5. Real production scenario

Dashboard management cần top 5 sellers mỗi region, kèm tổng sales và previous-month delta. Một query có thể dùng `ROW_NUMBER()` + `LAG()` thay vì nhiều round trips hoặc load toàn bộ data lên application để xử lý.

## 6. Failure scenario & troubleshooting

**Symptom**  
Window query chậm sau khi data tăng từ 1 triệu lên 50 triệu rows.

**Evidence**  
Execution plan có large sort và tempdb spill.

**Hypothesis**  
`PARTITION BY` / `ORDER BY` yêu cầu sort lớn mà index hiện tại không hỗ trợ tốt.

**Diagnosis**  
Xem actual execution plan, sort memory grant, spill warnings, input row count và predicate selectivity.

**Fix**  
Giảm input rows trước window operation, xem xét index phù hợp với filter/order, hoặc pre-aggregate nếu report không cần row-level detail.

**Verification**  
Đo logical reads, elapsed time, tempdb spill và memory grant sau thay đổi.

## 7. Common mistakes

* Dùng `ROW_NUMBER()` nhưng không có deterministic tie-breaker.
* Window trên toàn bảng rồi filter quá muộn.
* Giả định window function luôn nhanh hơn group/join.
* Không xem sort/spill trong execution plan.
* Đẩy dữ liệu sang C# để rank trong memory dù SQL xử lý tốt hơn.

## 8. Alternatives

* `GROUP BY`: khi chỉ cần aggregate, không cần giữ row detail.
* Self-join/correlated subquery: đôi khi đơn giản cho cases rất nhỏ nhưng thường khó maintain.
* Precomputed summary table/materialized view: khi dashboard query rất nặng và freshness cho phép.

## 9. Trade-offs

### Advantages

* SQL expressive hơn cho analytical patterns.
* Có thể tránh nhiều round trips và app-side processing.

### Costs / Risks

* Sort lớn tiêu tốn memory/tempdb.
* Query plan khó hơn cho developer chưa quen.
* Không thay thế data-model/reporting architecture cho workload cực lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác biệt giữa aggregate làm mất row detail và window giữ row detail.

### Middle

Viết được ranking, running total, previous-value queries.

### Senior

Đọc execution plan cho sort, spill, index support và row-count explosion.

### Technical Lead / Architect

Quyết định computation nên nằm ở transactional DB, reporting store hay precomputed projection.

## 11. Key takeaway

* Window functions giải quyết analytical query rất tự nhiên.
* `PARTITION BY` + `ORDER BY` có cost thực tế về sort/memory.
* Luôn lọc dữ liệu sớm và đọc execution plan khi workload lớn.

# 5. Redis distributed locking: lease, expiry, fencing và vì sao “SET NX” chưa đủ cho mọi bài toán

## 1. What is it?

Distributed lock cố đảm bảo nhiều process/instances không thực hiện cùng critical section đồng thời.

Redis thường được dùng với pattern kiểu `SET key value NX PX ttl` để giành lock có expiry.

Mental model quan trọng: distributed lock không giống `lock {}` trong một process. Network delay, process pause, clock behavior, lease expiry và Redis failover tạo ra uncertainty.

## 2. Why does it exist?

Khi application scale nhiều instances, in-memory lock chỉ bảo vệ bên trong một process. Scheduled job, inventory update hoặc singleton reconciliation có thể chạy song song trên nhiều nodes.

Distributed lock tạo coordination point bên ngoài process.

## 3. How does it work?

```text
Instance A ---- SET NX + lease ----> Redis
Instance B ---- SET NX -----------> Redis

A gets lock
B fails to acquire

A performs work
A releases only if token still matches
```

Token ownership rất quan trọng. Instance không nên `DEL` lock nếu lease cũ đã expire và instance khác đã acquire lock mới.

## 4. Practical implementation

Pseudo-realistic Redis command flow:

```csharp
var lockKey = "reconciliation:daily";
var token = Guid.NewGuid().ToString("N");
var ttl = TimeSpan.FromSeconds(30);

var acquired = await db.StringSetAsync(
    lockKey,
    token,
    ttl,
    When.NotExists);

if (!acquired)
{
    return;
}

try
{
    await RunReconciliationAsync(ct);
}
finally
{
    const string releaseScript = """
        if redis.call('get', KEYS[1]) == ARGV[1] then
            return redis.call('del', KEYS[1])
        else
            return 0
        end
        """;

    await db.ScriptEvaluateAsync(
        releaseScript,
        [new RedisKey(lockKey)],
        [new RedisValue(token)]);
}
```

Nếu critical section có external side effect quan trọng, còn phải nghĩ tới lease expiry trong khi work chưa xong.

## 5. Real production scenario

Hai App Service instances chạy settlement job. Instance A lấy 30-second lock nhưng bị GC pause + downstream latency 45 giây. Lock expire, instance B lấy lock mới và bắt đầu xử lý cùng batch.

Cả hai giờ đều nghĩ mình có quyền xử lý. Nếu downstream không idempotent, duplicate settlement có thể xảy ra.

## 6. Failure scenario & troubleshooting

**Symptom**  
Duplicate side effects vẫn xảy ra dù “đã có Redis lock”.

**Evidence**  
Logs cho thấy critical section dài hơn TTL; lock token đổi giữa execution.

**Hypothesis**  
Lease hết hạn trước khi owner hoàn thành.

**Diagnosis**  
Correlate lock acquisition token, execution duration, Redis latency và lease TTL.

**Fix**  
Rút ngắn critical section, renew lease cẩn thận, thêm idempotency ở business boundary và cân nhắc fencing token nếu downstream resource hỗ trợ.

**Verification**  
Chaos test với process pause/network delay và xác minh duplicate effect không xảy ra.

## 7. Common mistakes

* `SETNX` lock không expiry → deadlock sau process crash.
* Có expiry nhưng release bằng `DEL` không check owner token.
* TTL ngắn hơn worst-case work duration.
* Dùng distributed lock thay cho idempotency.
* Cho rằng Redis failover đồng nghĩa linearizable lock guarantee trong mọi topology.
* Lock coarse-grained gây throughput collapse.

## 8. Alternatives

* Database unique constraint: thường đơn giản hơn cho duplicate insert prevention.
* Idempotency key: tốt cho external/business side effects.
* Queue partition/session: serialize work theo business key.
* Leader election/external scheduler: phù hợp singleton background process.

## 9. Trade-offs

### Advantages

* Dễ triển khai khi Redis đã tồn tại.
* Coordination cross-instance tương đối đơn giản cho workload vừa phải.

### Costs / Risks

* Lease semantics phức tạp.
* Redis trở thành availability dependency.
* Lock contention làm giảm throughput.
* Không tự đảm bảo exactly-once side effect.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu in-process lock không bảo vệ nhiều instances.

### Middle

Biết token + TTL + safe release.

### Senior

Hiểu lease expiry, process pause, idempotency và failure modes.

### Technical Lead / Architect

Quyết định bài toán thật sự cần distributed lock hay constraint/idempotency/queue partition đơn giản hơn.

## 11. Key takeaway

* Distributed lock là lease-based coordination, không phải magic mutex.
* Safe release phải kiểm tra ownership token.
* Idempotency vẫn cần thiết cho critical business side effects.

# 6. Modular Monolith: module boundary, data ownership và transaction boundary trước khi nghĩ tới microservices

## 1. What is it?

Modular Monolith là một deployable application duy nhất nhưng được chia thành modules có boundary rõ về domain responsibility, dependencies và data ownership.

Mental model: **một process không có nghĩa một khối spaghetti**. Boundaries có thể được thực thi trong code trước khi tách thành network boundaries.

## 2. Why does it exist?

Layered monolith thường bắt đầu đơn giản nhưng theo thời gian mọi feature có thể gọi mọi repository/service. Database trở thành shared mutable state toàn hệ thống.

Microservices giải quyết một số organizational/deployment scaling concerns nhưng đổi lại network failure, eventual consistency, distributed observability và deployment complexity.

Modular Monolith cho phép xây domain boundaries trước, giữ transactional simplicity lâu hơn.

## 3. How does it work?

```text
Single deployable application

+-----------------------------+
| Timesheets Module           |
|  - Application              |
|  - Domain                   |
|  - Persistence ownership    |
+-----------------------------+
| Leave Module                |
|  - Application              |
|  - Domain                   |
|  - Persistence ownership    |
+-----------------------------+
| Notifications Module        |
+-----------------------------+
```

Module communication nên qua explicit contracts, application interfaces hoặc internal events thay vì truy cập repository/table của nhau tùy ý.

## 4. Practical implementation

Một contract giữa modules:

```csharp
public interface IEmployeeDirectory
{
    Task<EmployeeSummary?> GetEmployeeAsync(
        Guid employeeId,
        CancellationToken ct);
}
```

`Timesheets` module consume interface này thay vì inject `EmployeeDbContext` trực tiếp.

Ở persistence, có thể vẫn cùng SQL database nhưng dùng schema/table ownership rõ:

```text
hr.Employees
work.Timesheets
leave.LeaveRequests
```

Cùng database không đồng nghĩa cross-module query tùy ý là tốt.

## 5. Real production scenario

Employee platform có Timesheet, Leave, Payroll, Notification. Nếu Payroll query trực tiếp tables của Timesheet và Leave, mỗi schema change gây coupling lớn.

Bằng module contracts, team có thể giữ một deployment nhưng giới hạn blast radius của thay đổi. Sau này nếu Payroll cần scale/deploy độc lập, boundary đã tồn tại sẵn.

## 6. Failure scenario & troubleshooting

**Symptom**  
Mỗi feature nhỏ yêu cầu sửa 5 modules và migration nhiều tables không liên quan.

**Evidence**  
Cross-module repository injection, shared DTOs khắp solution, foreign keys xuyên mọi domain area.

**Hypothesis**  
Monolith thiếu ownership boundaries.

**Diagnosis**  
Vẽ dependency graph theo module, không chỉ theo technical layer.

**Fix**  
Định module ownership, public contracts, hạn chế cross-module persistence access; migrate dần chứ không rewrite toàn bộ.

**Verification**  
Feature change trong một module giảm số downstream compile/runtime impacts.

## 7. Common mistakes

* Chỉ tạo folder `Modules/` nhưng vẫn shared DbContext/repositories tự do.
* Mỗi module copy utility/framework boilerplate vô nghĩa.
* Dùng MediatR như thể nó tự tạo boundary.
* Tách module quá nhỏ theo entity CRUD.
* Cố tránh mọi transaction cross-module dù business invariant thực sự cần atomicity.
* Nhảy sang microservices trước khi module ownership rõ.

## 8. Alternatives

* Simple layered architecture: tốt cho hệ thống nhỏ/ít domain complexity.
* Modular Monolith: tốt khi domain lớn nhưng chưa cần independent deployment.
* Microservices: hợp lý khi ownership, scaling, release cadence hoặc isolation thực sự yêu cầu.

## 9. Trade-offs

### Advantages

* Giữ local transactions và operational simplicity.
* Boundary rõ giúp maintainability.
* Tạo migration path tới services nếu sau này cần.

### Costs / Risks

* Boundary enforcement cần discipline/tooling.
* Một deployment vẫn có shared blast radius release.
* Resource contention vẫn có thể xảy ra trong cùng process/database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business responsibility, không chỉ folder.

### Middle

Implement module contracts và tránh repository access xuyên boundary.

### Senior

Thiết kế data ownership, transaction boundary và internal integration.

### Technical Lead / Architect

Quyết định khi modular monolith đủ tốt và tiêu chí cụ thể nào mới justify microservices.

## 11. Key takeaway

* Architecture boundary có thể tồn tại trước network boundary.
* Data ownership quan trọng hơn folder layout.
* Microservices không nên là cách đầu tiên để sửa coupling trong codebase.

# 7. Azure Service Bus Sessions: ordering theo business key, competing consumers và throughput trade-off

## 1. What is it?

Azure Service Bus Sessions cho phép group messages theo `SessionId` để một receiver xử lý tuần tự messages thuộc cùng session.

Mental model: session không tạo global ordering cho toàn queue. Nó tạo ordered processing **theo business partition key** như `OrderId`, `CustomerId` hoặc `WorkflowId`.

## 2. Why does it exist?

Competing consumers tăng throughput nhưng có thể xử lý messages out of order.

Ví dụ:

```text
OrderCreated
OrderPaid
OrderCancelled
```

Nếu các message cùng order được xử lý bởi nhiều consumers đồng thời, business state có thể bị apply sai thứ tự.

Sessions cung cấp serialization boundary mà vẫn cho phép nhiều sessions chạy song song.

## 3. How does it work?

```text
Queue
 ├─ Session A: A1 -> A2 -> A3  (one active session receiver)
 ├─ Session B: B1 -> B2        (another receiver)
 └─ Session C: C1 -> C2 -> C3  (another receiver)
```

Throughput tổng đến từ parallelism giữa sessions, không phải trong cùng session.

## 4. Practical implementation

Sender:

```csharp
var message = new ServiceBusMessage(BinaryData.FromObjectAsJson(evt))
{
    SessionId = evt.OrderId.ToString(),
    MessageId = evt.EventId.ToString()
};

await sender.SendMessageAsync(message, ct);
```

Processor:

```csharp
var processor = client.CreateSessionProcessor(queueName, new ServiceBusSessionProcessorOptions
{
    AutoCompleteMessages = false,
    MaxConcurrentSessions = 16,
    MaxConcurrentCallsPerSession = 1
});
```

Business handler vẫn cần idempotency vì at-least-once delivery không biến mất.

## 5. Real production scenario

E-commerce order workflow publish status events. Team dùng `OrderId` làm `SessionId` để giữ order transitions tuần tự, trong khi hàng nghìn orders khác nhau vẫn được xử lý song song.

Nếu dùng `CustomerId` thay vì `OrderId`, một customer có nhiều orders lớn có thể tạo unnecessary serialization và hot session.

## 6. Failure scenario & troubleshooting

**Symptom**  
Queue backlog tăng nhưng CPU consumers thấp.

**Evidence**  
Một vài sessions có hàng chục nghìn messages; đa số sessions nhỏ.

**Hypothesis**  
Session key tạo hot partition và giới hạn concurrency.

**Diagnosis**  
Đo backlog theo session/business key, session processing duration và lock renewals.

**Fix**  
Chọn granularity SessionId đúng invariant ordering; tối ưu slow handler; tăng parallelism giữa sessions nếu downstream chịu được.

**Verification**  
Backlog giảm mà ordering trong cùng business aggregate vẫn đúng.

## 7. Common mistakes

* Nghĩ sessions cho exactly-once processing.
* Dùng một `SessionId` cho toàn tenant và serialize quá mức.
* Handler lâu nhưng không xử lý lock renewal/failure.
* Không DLQ poison message khiến session bị chặn.
* Không idempotent consumer.
* Chọn ordering requirement theo technical entity thay vì business invariant.

## 8. Alternatives

* Queue không session: tốt khi messages độc lập.
* Partitioned processing ở Kafka/Event Hubs: phù hợp streaming model khác.
* Database serialized workflow: đơn giản hơn khi throughput thấp và transaction boundary local.

## 9. Trade-offs

### Advantages

* Ordering theo key rõ ràng.
* Vẫn scale song song giữa nhiều sessions.
* Hữu ích cho workflow stateful.

### Costs / Risks

* Hot session giới hạn throughput.
* Operational complexity tăng.
* Không loại bỏ retries, duplicates hay poison messages.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue processing có thể out of order khi nhiều consumers.

### Middle

Biết set `SessionId` và configure session processor.

### Senior

Hiểu hot session, lock semantics, idempotency và DLQ.

### Technical Lead / Architect

Quyết định business key nào thực sự cần ordering và liệu ordering có đáng đánh đổi throughput không.

## 11. Key takeaway

* Sessions cho ordering theo key, không phải global ordering.
* Chọn SessionId là architecture decision ảnh hưởng throughput.
* At-least-once + idempotency vẫn áp dụng đầy đủ.

# 8. Blue-Green deployment + feature flags: deploy code an toàn khi database schema không thể rollback tức thời

## 1. What is it?

Blue-Green deployment giữ hai application environments hoặc revisions: một đang phục vụ traffic, một chứa release mới. Traffic được chuyển khi release mới healthy.

Feature flags tách **deployment** khỏi **feature activation**.

Mental model quan trọng: application rollback dễ hơn database rollback. Vì vậy database schema evolution phải backward-compatible trong khoảng thời gian blue và green có thể cùng tồn tại.

## 2. Why does it exist?

Traditional deployment thay code tại chỗ làm rollback chậm và tạo downtime risk.

Blue-Green giảm cutover risk, nhưng nếu release mới chạy migration phá schema cũ thì môi trường blue không còn rollback được thật sự.

Feature flags giúp ship code inactive, test production behavior theo subset users và activate độc lập.

## 3. How does it work?

```text
             +--> Blue v1 ----+
Client -> Router               +--> Shared DB
             +--> Green v2 ---+

Phase 1: Blue receives traffic
Phase 2: Green deploy + health validate
Phase 3: switch traffic
Phase 4: observe
Phase 5: retire Blue later
```

Database change nên theo expand-and-contract:

```text
Expand schema -> deploy compatible code -> migrate data -> switch reads/writes -> remove old schema later
```

## 4. Practical implementation

Ví dụ đổi `FullName` thành `FirstName` + `LastName`.

Không nên release migration xóa `FullName` ngay.

Phase 1:

```sql
ALTER TABLE Customers ADD FirstName nvarchar(100) NULL;
ALTER TABLE Customers ADD LastName nvarchar(100) NULL;
```

Code mới có thể dual-write tạm thời hoặc fallback đọc `FullName` nếu fields mới chưa populated.

Sau migration data và khi mọi version cũ đã retire, mới contract schema.

Feature flag:

```csharp
if (await featureManager.IsEnabledAsync("CustomerNameV2"))
{
    return BuildV2Model(customer);
}

return BuildLegacyModel(customer);
```

## 5. Real production scenario

App Service slot swap deploy release mới. Green slot health check pass, nhưng migration đã rename column mà Blue vẫn cần. Khi error rate tăng và team swap back, Blue bắt đầu lỗi SQL.

Rollback application thành công về routing nhưng không thành công về data contract.

## 6. Failure scenario & troubleshooting

**Symptom**  
Rollback release nhưng app cũ trả 500.

**Evidence**  
Database schema đã contract incompatibly.

**Hypothesis**  
Deployment strategy chỉ xem code artifact, không xem schema compatibility.

**Diagnosis**  
Compare application version compatibility matrix với migration history.

**Fix**  
Dùng expand-and-contract, migration phases và compatibility tests giữa N và N-1 versions.

**Verification**  
Run old app version against expanded schema trong pre-production before release.

## 7. Common mistakes

* Gọi slot swap là Blue-Green nhưng dùng shared schema breaking change.
* Feature flag không có owner/expiry → permanent dead code.
* Flag security-critical logic mà default state không an toàn.
* Cleanup old column quá sớm.
* Không test rollback path.
* Migration chạy cùng startup của mọi instances và race nhau.

## 8. Alternatives

* Rolling deployment: đơn giản hơn nhưng multiple versions vẫn cùng chạy tạm thời.
* Canary: chuyển một phần traffic trước, tốt cho risk reduction.
* Feature flags: bổ sung chứ không thay thế deployment strategy.

## 9. Trade-offs

### Advantages

* Cutover/rollback nhanh ở application layer.
* Giảm blast radius khi kết hợp health validation/canary.
* Feature activation độc lập với deploy.

### Costs / Risks

* Tốn thêm environment/resources.
* Schema compatibility phức tạp hơn.
* Flags tạo code paths cần test/cleanup.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy code và thay database schema là hai lifecycle khác nhau.

### Middle

Biết feature flag, health check và non-breaking migrations.

### Senior

Thiết kế expand-and-contract, rollback validation và multi-version compatibility.

### Technical Lead / Architect

Đặt release policy: thời gian compatibility window, migration ownership, rollback SLA và feature-flag governance.

## 11. Key takeaway

* Blue-Green không cứu được breaking database migration.
* Database change an toàn thường cần expand-and-contract.
* Feature flag tách deployment khỏi activation nhưng phải có lifecycle governance.

# 9. Technical SEO cho application engineer: canonical URL, redirects, SSR và crawlability trong SPA / CMS

## 1. What is it?

Technical SEO là các cơ chế kỹ thuật giúp crawler khám phá, hiểu và index đúng URL/content.

Với engineer, trọng tâm không phải marketing keywords mà là:

- status codes
- redirects
- canonical URLs
- server-rendered/accessible content
- sitemap/robots
- performance
- duplicate URL control

Mental model: crawler là một HTTP client có crawling budget và rendering constraints; nó cần stable URL semantics.

## 2. Why does it exist?

Modern CMS/e-commerce site dễ tạo nhiều URL cho cùng content:

```text
/product?id=123
/products/red-shoe
/products/red-shoe?utm_source=x
```

Nếu hệ thống không định canonical/redirect strategy, search engine có thể phân tán indexing signals hoặc crawl duplicate pages.

SPA còn có risk HTML ban đầu gần như rỗng nếu rendering phụ thuộc hoàn toàn JavaScript.

## 3. How does it work?

```text
Crawler
  |
  v
DNS/CDN
  |
  v
HTTP status + redirect
  |
  v
HTML response
  |
  +--> canonical
  +--> meta robots
  +--> structured data
  +--> internal links
```

`301`/`308` thường dùng permanent redirect; `302`/`307` dùng temporary semantics.

Canonical tag gợi ý preferred URL nhưng không thay thế redirect khi URL cũ thực sự không còn là canonical route.

## 4. Practical implementation

ASP.NET Core permanent redirect:

```csharp
app.MapGet("/old-products/{slug}", (string slug) =>
    Results.Redirect($"/products/{slug}", permanent: true));
```

Canonical trong server-rendered layout:

```html
<link rel="canonical" href="https://www.example.com/products/red-shoe" />
```

Trong CMS, canonical URL nên được resolve từ content routing model thay vì editor nhập thủ công trên mọi page.

## 5. Real production scenario

Optimizely CMS site đổi URL structure `/insights/article-x` → `/knowledge/article-x`. Team update navigation nhưng không tạo redirects.

Old indexed URLs trả 404, backlinks mất giá trị và crawler phải discover lại content mới.

Proper redirect registry hoặc automatic redirect mapping giúp giữ user/search continuity.

## 6. Failure scenario & troubleshooting

**Symptom**  
Organic landing pages giảm sau release dù content không đổi.

**Evidence**  
Crawl logs/Search Console cho thấy redirect chains, 404 tăng, canonical mismatch hoặc pages render content quá muộn.

**Hypothesis**  
Technical URL/rendering regression.

**Diagnosis**  
Dùng `curl`, browser DevTools, Lighthouse và crawler để kiểm tra status, response HTML, canonical, redirects và Core Web Vitals.

**Fix**  
Rút redirect chain, restore permanent mappings, sửa canonical generation, SSR/pre-render critical content khi cần.

**Verification**  
Crawl lại sitemap/URLs và monitor 404, indexing status, Web Vitals.

## 7. Common mistakes

* Redirect mọi 404 về homepage.
* Có canonical nhưng URL cũ vẫn indexable với conflicting signals.
* `robots.txt` block CSS/JS cần thiết cho rendering.
* SPA route trả 200 cho mọi unknown URL thay vì proper 404.
* Infinite URL variants từ filters/query params.
* Chỉ test bằng browser đã chạy JavaScript đầy đủ.

## 8. Alternatives

* SSR: tốt cho content-heavy/public pages cần reliable initial HTML.
* CSR-only: phù hợp authenticated/internal apps nơi SEO không quan trọng.
* Static generation: tốt cho content tương đối ổn định và high cacheability.

## 9. Trade-offs

### Advantages

* Stable crawl/index behavior.
* Better user navigation qua redirects.
* SSR/static rendering có thể cải thiện initial content availability.

### Costs / Risks

* SSR tăng server complexity/cost.
* Redirect registries cần governance.
* Dynamic filters/search pages có thể tạo crawl-space explosion.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code, redirect và canonical khác nhau.

### Middle

Implement redirect/canonical/sitemap đúng HTTP semantics.

### Senior

Debug crawl/render/performance regressions bằng evidence.

### Technical Lead / Architect

Chọn SSR/CSR/static strategy theo product type, SEO requirement, operational cost và CMS architecture.

## 11. Key takeaway

* SEO engineering bắt đầu từ HTTP semantics và URL stability.
* Canonical không thay thế redirect strategy.
* Public content cần được test bằng crawler mindset, không chỉ bằng browser UX.

# 10. TypeScript discriminated unions: làm state machine rõ hơn trong frontend API workflows

## 1. What is it?

Discriminated union là TypeScript pattern dùng một literal field chung để biểu diễn nhiều state variants an toàn.

Ví dụ:

```ts
type LoadState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: string };
```

Mental model: thay vì object có nhiều optional fields mâu thuẫn, mỗi state chỉ chứa dữ liệu hợp lệ cho chính state đó.

## 2. Why does it exist?

Frontend thường có state kiểu:

```ts
{
  loading: boolean,
  data?: T,
  error?: string
}
```

Object này cho phép impossible combinations:

```text
loading = true
error = "Timeout"
data != null
```

Discriminated union biến state machine thành type contract để compiler loại bỏ nhiều invalid combinations.

## 3. How does it work?

TypeScript narrow type theo discriminator:

```ts
function render<T>(state: LoadState<T>) {
  switch (state.status) {
    case 'loading':
      return 'Loading...';
    case 'success':
      return state.data;
    case 'error':
      return state.error;
    case 'idle':
      return null;
  }
}
```

Trong branch `success`, compiler biết `data` tồn tại.

## 4. Practical implementation

Vue composable:

```ts
type Employee = {
  id: string;
  name: string;
};

type EmployeeState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; employee: Employee }
  | { status: 'notFound' }
  | { status: 'error'; message: string };

const state = ref<EmployeeState>({ status: 'idle' });

async function loadEmployee(id: string) {
  state.value = { status: 'loading' };

  const response = await fetch(`/api/employees/${id}`);

  if (response.status === 404) {
    state.value = { status: 'notFound' };
    return;
  }

  if (!response.ok) {
    state.value = { status: 'error', message: `HTTP ${response.status}` };
    return;
  }

  state.value = {
    status: 'success',
    employee: await response.json()
  };
}
```

## 5. Real production scenario

Approval workflow UI có states: draft, submitting, approved, rejected, conflict. Nếu dùng booleans như `isLoading`, `isApproved`, `hasError`, UI dễ render buttons không phù hợp sau race/error.

Union state giúp component logic bám sát business/API lifecycle rõ hơn.

## 6. Failure scenario & troubleshooting

**Symptom**  
UI vừa hiển thị success data vừa hiện stale error banner.

**Evidence**  
State object cho phép `data` và `error` tồn tại đồng thời.

**Hypothesis**  
State model không encode mutually exclusive states.

**Diagnosis**  
Inspect state transitions theo request timeline.

**Fix**  
Refactor về discriminated union + explicit transitions; cancel stale requests nếu cần.

**Verification**  
TypeScript compile-time checks và component tests cover từng state variant.

## 7. Common mistakes

* Một union có quá nhiều states nhưng không phản ánh real workflow.
* `as any` phá narrowing.
* Convert mọi DTO thành huge union không cần thiết.
* Không handle exhaustive switch khi thêm state mới.
* State machine frontend khác semantics backend status codes/domain states.

## 8. Alternatives

* Simple booleans: đủ cho component rất nhỏ.
* Enum + separate payload fields: dễ tạo invalid combinations hơn.
* Formal state-machine library: đáng cân nhắc khi workflow nhiều transitions/guards, nhưng có thêm complexity.

## 9. Trade-offs

### Advantages

* Impossible states khó biểu diễn hơn.
* Refactor an toàn hơn.
* UI logic rõ theo state transition.

### Costs / Risks

* Verbose hơn cho simple components.
* Có thể over-model nếu workflow đơn giản.
* Type safety không tự giải quyết async race conditions.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu union type và narrowing theo discriminator.

### Middle

Dùng union để model API loading/error/success states.

### Senior

Thiết kế state transitions, exhaustive handling và concurrency behavior.

### Technical Lead / Architect

Quyết định khi nào simple state đủ, khi nào workflow cần explicit state machine và cách đồng bộ semantics với backend contracts.

## 11. Key takeaway

* Discriminated unions giúp encode valid states vào type system.
* Chúng giảm inconsistent UI state nhưng không thay thế cancellation/concurrency control.
* Dùng khi state variants thực sự mutually exclusive và có business meaning.
