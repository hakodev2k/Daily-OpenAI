# 1. C# `ValueTask`: giảm allocation đúng chỗ, nhưng tăng complexity nếu dùng sai

## 1. What is it?

Mental model: `Task<T>` là một object đại diện cho asynchronous operation; `ValueTask<T>` là một struct có thể đại diện cho kết quả hoàn tất đồng bộ hoặc một asynchronous operation. Nó tồn tại chủ yếu để tránh tạo `Task<T>` mới trong hot path nơi operation rất thường hoàn tất synchronously.

## 2. Why does it exist?

Nếu API được gọi hàng triệu lần và phần lớn trả kết quả ngay từ cache/buffer, allocation một `Task<T>` cho mỗi lần gọi có thể tạo GC pressure không cần thiết. Nhưng optimization này đổi allocation lấy API semantics phức tạp hơn.

## 3. How does it work?

`ValueTask<T>` có thể chứa trực tiếp `T`, wrap một `Task<T>`, hoặc dựa trên `IValueTaskSource<T>`. Vì backing source có thể được tái sử dụng, caller không nên tùy tiện await nhiều lần hoặc gọi `.Result`/`AsTask()` lặp lại.

## 4. Practical implementation

```csharp
public ValueTask<User?> FindAsync(int id, CancellationToken ct)
{
    if (_memory.TryGetValue(id, out User? user))
        return ValueTask.FromResult<User?>(user);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id, ct));
}
```

Nếu operation hầu như luôn asynchronous, `Task<T>` thường đơn giản và phù hợp hơn.

## 5. Real production scenario

Một protocol parser đọc từ buffer và 95% lần gọi đã có đủ dữ liệu trong memory. Profiling chứng minh `Task` allocations đáng kể. `ValueTask` có thể giảm allocation ở đây; áp dụng đại trà cho service methods thông thường thường không đáng.

## 6. Failure scenario & troubleshooting

**Symptom** → behavior khó hiểu hoặc exception khi consumer reuse một `ValueTask`. **Evidence** → cùng instance bị await/convert nhiều lần. **Hypothesis** → caller vi phạm consumption contract. **Diagnosis** → trace call site và backing implementation. **Fix** → await trực tiếp một lần hoặc dùng `Task` nếu API cần semantics linh hoạt. **Verification** → benchmark allocation và tests consumer behavior.

## 7. Common mistakes

Dùng `ValueTask` vì nghĩ luôn nhanh hơn; dùng trong mọi public API; benchmark micro-allocation nhưng bỏ qua database/network latency; lưu `ValueTask` để await lại.

## 8. Alternatives

`Task<T>` là default tốt hơn cho đa số application code. Cached `Task` hoặc synchronous API cũng có thể phù hợp tùy semantics.

## 9. Trade-offs

### Advantages

Có thể giảm allocation trong measured hot paths có tỷ lệ synchronous completion cao.

### Costs / Risks

Struct lớn hơn reference, consumption rules phức tạp, tooling/debugging và API usability kém hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `Task` không đồng nghĩa thread.
### Middle
Dùng `Task` làm default và biết `ValueTask` có contract khác.
### Senior
Profile allocation trước khi đổi API và hiểu `IValueTaskSource` lifecycle.
### Technical Lead / Architect
Quyết định optimization có đáng đổi API complexity hay không.

## 11. Key takeaway

- `ValueTask` là optimization tool, không phải `Task` phiên bản tốt hơn.
- Chỉ dùng khi measurement cho thấy allocation thực sự đáng kể.
- API simplicity thường quan trọng hơn micro-optimization.

# 2. ASP.NET Core graceful shutdown: dừng service mà không cắt work tùy tiện

## 1. What is it?

Graceful shutdown là quá trình application nhận tín hiệu dừng, ngừng nhận work mới, cho in-flight work một khoảng thời gian hoàn tất, truyền cancellation và giải phóng resource trước khi process bị terminate.

## 2. Why does it exist?

Container restart, deployment, autoscaling và host maintenance là bình thường. Nếu process bị kill ngay, request đang ghi database, upload hoặc message handler có thể bị cắt giữa chừng.

## 3. How does it work?

```text
SIGTERM / host stop
  -> readiness false / traffic drain
  -> stop accepting new work
  -> cancellation propagated
  -> in-flight work finishes or aborts safely
  -> dispose resources
  -> process exits
```

Host shutdown timeout và orchestrator termination grace period phải tương thích.

## 4. Practical implementation

```csharp
app.MapPost("/imports", async (
    ImportService service,
    CancellationToken ct) =>
{
    await service.ImportAsync(ct);
    return Results.Accepted();
});
```

Background worker cũng phải honor token:

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
        await ProcessNextAsync(stoppingToken);
}
```

## 5. Real production scenario

Rolling deployment thay 10 pods. Nếu readiness/termination không phối hợp, load balancer vẫn gửi request vào pod đang shutdown hoặc pod bị kill trước khi message settlement hoàn tất, tạo duplicate processing.

## 6. Failure scenario & troubleshooting

**Symptom** → 502/499 tăng đúng lúc deploy; duplicate message sau restart. **Evidence** → logs có termination timestamp trùng request cancellation. **Hypothesis** → drain/shutdown window quá ngắn hoặc code bỏ qua cancellation. **Diagnosis** → correlate ingress, pod lifecycle và application traces. **Fix** → align readiness, grace period, host timeout và idempotent work. **Verification** → rolling-deploy test dưới load.

## 7. Common mistakes

Nuốt `OperationCanceledException` rồi tiếp tục work; bắt đầu long-running task mới sau stop signal; shutdown timeout dài hơn orchestrator grace period; coi graceful shutdown là đảm bảo mọi work luôn hoàn tất.

## 8. Alternatives

Work dài nên chuyển sang durable queue/worker thay vì giữ request mở. Checkpointing phù hợp batch dài.

## 9. Trade-offs

### Advantages
Giảm interrupted work và deployment errors.
### Costs / Risks
Shutdown chậm hơn; vẫn cần idempotency vì hard kill luôn có thể xảy ra.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu cancellation là cooperative.
### Middle
Propagate `CancellationToken` xuyên call chain.
### Senior
Thiết kế shutdown-safe transaction/message handling.
### Technical Lead / Architect
Đồng bộ application lifecycle với load balancer/orchestrator và workload durability.

## 11. Key takeaway

- Graceful shutdown là protocol giữa host, traffic routing và application.
- Cancellation phải đi xuyên toàn bộ work path.
- Durable/idempotent design vẫn cần vì process có thể chết không graceful.

# 3. EF Core `IQueryable` vs `IEnumerable`: ranh giới execution

## 1. What is it?

`IQueryable<T>` giữ expression tree để provider như EF Core dịch operation sang SQL. `IEnumerable<T>` biểu diễn iteration phía .NET. Chuyển ranh giới quá sớm có thể biến filter/sort từ database work thành in-memory work.

## 2. Why does it exist?

LINQ cung cấp syntax thống nhất nhưng execution engine khác nhau. Database có index, optimizer và set-based execution; application memory thì không.

## 3. How does it work?

```text
IQueryable + Where + Select
 -> expression tree
 -> EF translation
 -> SQL
 -> DB execution
 -> materialization
 -> IEnumerable objects
```

Terminal operation như `ToListAsync` kích hoạt execution.

## 4. Practical implementation

```csharp
var query = db.Orders
    .Where(x => x.Status == OrderStatus.Paid)
    .OrderByDescending(x => x.CreatedAt)
    .Select(x => new OrderRow(x.Id, x.Total));

var rows = await query.Take(100).ToListAsync(ct);
```

Tránh `AsEnumerable()` trước filter lớn trừ khi cố ý chuyển sang client logic.

## 5. Real production scenario

Developer gọi `ToListAsync()` trên 2 triệu orders rồi mới `.Where(...)` vì helper nhận `IEnumerable`. Endpoint local data nhỏ vẫn nhanh; Production memory và latency tăng mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → DB trả rất nhiều rows nhưng response ít. **Evidence** → SQL thiếu predicate/pagination. **Hypothesis** → query materialized quá sớm. **Diagnosis** → tìm terminal operation và inspect generated SQL. **Fix** → giữ translatable operations trên `IQueryable`. **Verification** → compare rows read, bytes, allocations và duration.

## 7. Common mistakes

Expose `IQueryable` xuyên mọi architectural boundary; gọi custom C# method không translate; nhầm deferred execution với caching; enumerate query nhiều lần.

## 8. Alternatives

Repository/query object có thể encapsulate query semantics. Raw SQL/Dapper phù hợp query cần control đặc thù.

## 9. Trade-offs

### Advantages
Database thực thi filter/project hiệu quả.
### Costs / Risks
`IQueryable` làm persistence concerns leak nếu truyền quá xa và translation limitations dễ bị bỏ qua.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Biết query chưa chạy trước terminal operation.
### Middle
Kiểm tra generated SQL.
### Senior
Quản lý translation/materialization boundary.
### Technical Lead / Architect
Chọn query abstraction giữ được performance transparency mà không leak provider toàn hệ thống.

## 11. Key takeaway

- LINQ giống nhau về syntax không có nghĩa chạy cùng nơi.
- Materialization boundary là performance boundary.
- Xác minh SQL thay vì suy đoán từ C#.

# 4. SQL Server covering index: giảm key lookup có chủ đích

## 1. What is it?

Covering index là index chứa đủ columns để đáp ứng query mà engine không cần quay lại clustered index/heap lấy thêm dữ liệu. Key columns hỗ trợ seek/order; `INCLUDE` columns có thể cung cấp payload.

## 2. Why does it exist?

Một nonclustered index hẹp tìm row nhanh nhưng nếu query cần columns không có trong index, engine có thể thực hiện Key Lookup cho nhiều rows. Lookup ít thì tốt; hàng trăm nghìn lookup có thể thành random I/O đắt đỏ.

## 3. How does it work?

```text
Nonclustered Index Seek
   -> matching keys
   -> Key Lookup x N
```

Covering index có thể biến flow thành seek/scan trên một index đủ dữ liệu, nhưng index lớn hơn cũng tốn storage và write maintenance.

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_CustomerId_CreatedAt
ON dbo.Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, Total);
```

Phải dựa trên actual query và execution plan, không copy mọi SELECT column vào `INCLUDE`.

## 5. Real production scenario

Order-history endpoint query 50 rows theo customer rất nhanh. Một reporting variant bỏ `TOP` và lấy 200k rows; plan vẫn lookup từng row để lấy `Total`, khiến logical reads tăng mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → plan có Key Lookup chiếm cost/I/O lớn. **Evidence** → actual rows qua lookup cao. **Hypothesis** → access path không cover payload ở cardinality thực tế. **Diagnosis** → actual plan + `STATISTICS IO`. **Fix** → cover có chọn lọc hoặc redesign query. **Verification** → đo reads, duration và write overhead.

## 7. Common mistakes

Tạo index cực rộng; duplicate indexes; chỉ nhìn estimated cost percentage; không xét UPDATE/INSERT; cover query hiếm nhưng làm write-heavy table đắt hơn.

## 8. Alternatives

Projection hẹp hơn, clustered index strategy khác, columnstore cho analytical workload, hoặc read model riêng.

## 9. Trade-offs

### Advantages
Giảm lookup và I/O cho read path quan trọng.
### Costs / Risks
Tăng storage, memory footprint, write amplification và maintenance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu seek và lookup.
### Middle
Đọc actual plan và logical reads.
### Senior
Cân read benefit với write cost/index overlap.
### Technical Lead / Architect
Quyết định workload có cần transactional index hay analytical/read model riêng.

## 11. Key takeaway

- Covering index tối ưu access pattern cụ thể.
- Lookup không xấu; lookup với cardinality lớn mới đáng điều tra.
- Mọi index đều có write và operational cost.

# 5. Distributed timeout budget: deadline phải được chia, không nhân lên

## 1. What is it?

Timeout budget là tổng thời gian một operation được phép tiêu thụ theo SLO/client deadline. Mỗi downstream call phải dùng một phần budget còn lại thay vì tự có timeout độc lập dài bằng toàn request.

## 2. Why does it exist?

API có deadline 3 giây nhưng gọi tuần tự ba dependencies, mỗi dependency timeout 3 giây, thì worst case đã gần 9 giây chưa tính retries. Retry càng làm tail latency tệ hơn.

## 3. How does it work?

```text
Client deadline 3s
 API work 200ms -> 2.8s left
 Dependency A budget 800ms
 Dependency B budget 1.2s
 reserve for response/retry/fallback
```

Deadline propagation giúp downstream biết work đã hết giá trị khi caller không còn chờ.

## 4. Practical implementation

```csharp
using var budget = CancellationTokenSource.CreateLinkedTokenSource(requestAborted);
budget.CancelAfter(TimeSpan.FromSeconds(2));

using var response = await httpClient.GetAsync(
    uri,
    HttpCompletionOption.ResponseHeadersRead,
    budget.Token);
```

Production code nên centralize resilience policy và phân biệt connection timeout, request timeout, cancellation và retry budget.

## 5. Real production scenario

Product page gọi pricing, inventory và reviews. Reviews chậm không nên giữ toàn page đến 10 giây. Budget + fallback cho optional dependency giữ critical path trong SLO.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 vượt client timeout; server tiếp tục work sau client disconnect. **Evidence** → traces cho thấy nested calls dài hơn remaining deadline. **Hypothesis** → timeout policies độc lập. **Diagnosis** → waterfall trace. **Fix** → propagate cancellation/deadline và bounded retry. **Verification** → inject latency/failure và đo end-to-end deadline.

## 7. Common mistakes

Timeout mọi dependency cùng một giá trị; retry sau khi budget gần hết; timeout quá thấp dựa trên p50; retry non-idempotent operation; không cancel database/HTTP work khi caller rời đi.

## 8. Alternatives

Async messaging bỏ synchronous deadline cho deferred workflows. Cached/stale fallback phù hợp optional read dependencies.

## 9. Trade-offs

### Advantages
Giới hạn failure propagation và tail latency.
### Costs / Risks
Budget quá chặt gây false timeout; fallback có thể giảm freshness/completeness.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt timeout và retry.
### Middle
Propagate cancellation.
### Senior
Thiết kế deadline/retry/fallback theo traces và percentiles.
### Technical Lead / Architect
Xác định dependency nào thuộc critical path và SLO budget của từng boundary.

## 11. Key takeaway

- End-to-end deadline là hữu hạn.
- Retry tiêu thụ cùng budget, không tạo thêm thời gian.
- Trace waterfall là bằng chứng tốt để phân bổ timeout.

# 6. Azure Managed Identity + Key Vault: bỏ secret tĩnh khỏi application

## 1. What is it?

Managed Identity cung cấp identity do Azure quản lý cho workload. Application dùng identity đó lấy token từ Microsoft Entra ID để truy cập Key Vault hoặc Azure resources mà không lưu client secret trong config.

## 2. Why does it exist?

Credential tĩnh phải được tạo, phân phối, bảo vệ và rotate. Một secret bị copy vào appsettings, pipeline variable hoặc log có thể tồn tại lâu hơn dự kiến.

## 3. How does it work?

```text
App Service / VM / workload
 -> Managed Identity
 -> Entra token
 -> Key Vault authorization
 -> secret/key/certificate
```

Authorization vẫn cần least-privilege role/policy; identity không tự động có quyền.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(vaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("PaymentsApiKey", cancellationToken: ct);
```

Local development có thể dùng developer credential chain; Production dùng Managed Identity.

## 5. Real production scenario

App Service cần API key của legacy vendor. Azure resources dùng Managed Identity; vendor key vẫn nằm trong Key Vault. App không cần credential để truy cập vault, còn vendor secret có rotation/audit boundary riêng.

## 6. Failure scenario & troubleshooting

**Symptom** → Production trả 403 từ Key Vault. **Evidence** → token lấy được nhưng authorization denied. **Hypothesis** → identity đúng nhưng role/scope sai. **Diagnosis** → xác định principal, vault RBAC, network access và audit logs. **Fix** → cấp minimum role đúng scope. **Verification** → restart-independent secret retrieval và deny negative test.

## 7. Common mistakes

Cho identity quyền quá rộng; nghĩ Key Vault giải quyết secret leakage trong logs; gọi vault mỗi request; hard-code vault secret làm fallback; nhầm authentication với authorization.

## 8. Alternatives

Workload identity trong Kubernetes, service principal với certificate/secret khi Managed Identity không khả dụng, configuration service cho non-secret values.

## 9. Trade-offs

### Advantages
Giảm credential lifecycle và secret distribution.
### Costs / Risks
Tăng dependency vào identity/network/RBAC; vẫn phải quản lý secrets không thể loại bỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt identity và secret.
### Middle
Cấu hình `DefaultAzureCredential` và RBAC.
### Senior
Thiết kế caching, rotation, network/private endpoint và diagnostics.
### Technical Lead / Architect
Loại bỏ static credentials ở nơi có thể và thiết kế ownership/least privilege toàn hệ thống.

## 11. Key takeaway

- Managed Identity loại bỏ credential của application khi truy cập Azure resource.
- Key Vault không thay thế least privilege hay safe logging.
- Authentication, authorization, secret storage và rotation là các concerns khác nhau.

# 7. Docker multi-stage build: build toolchain không cần đi vào Production image

## 1. What is it?

Multi-stage build dùng nhiều `FROM` stages: stage đầu compile/publish, stage cuối chỉ copy runtime artifacts cần thiết. Build SDK và source code không cần tồn tại trong runtime image.

## 2. Why does it exist?

SDK image lớn hơn, có compiler/tooling không cần thiết và mở rộng attack surface. Runtime container nên chứa tối thiểu thứ cần để chạy application.

## 3. How does it work?

```text
SDK stage: restore -> build -> publish
                     |
                     v
Runtime stage: copy /publish -> run
```

Docker cache layers cũng ảnh hưởng build time; copy project files trước source thường giúp restore cache tốt hơn.

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY MyApi.csproj .
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /app/publish --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

Pinning/version policy và vulnerability scanning vẫn cần trong CI.

## 5. Real production scenario

Team ship SDK image gần 1 GB lên cluster cho một API nhỏ. Pull/start chậm và scanner báo nhiều packages chỉ dùng lúc build. Multi-stage runtime image giảm artifacts không cần thiết.

## 6. Failure scenario & troubleshooting

**Symptom** → container chạy local build stage nhưng final stage lỗi thiếu native library/file. **Evidence** → publish output/runtime dependencies khác. **Hypothesis** → runtime image không chứa dependency cần thiết. **Diagnosis** → inspect final filesystem/base distro/runtime identifier. **Fix** → thêm runtime dependency có chủ đích hoặc chọn compatible base. **Verification** → run final image trong CI.

## 7. Common mistakes

Copy toàn repo vào final stage; bake secrets vào image layer; dùng `latest`; build trên một architecture rồi deploy architecture khác mà không kiểm tra; chạy container bằng root không cần thiết.

## 8. Alternatives

Buildpacks/container tooling có thể generate images; self-contained/native deployment có trade-off khác về size/runtime dependency.

## 9. Trade-offs

### Advantages
Runtime image nhỏ và ít tooling hơn.
### Costs / Risks
Dockerfile/build pipeline phức tạp hơn; base image compatibility vẫn cần quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu image khác container.
### Middle
Viết multi-stage Dockerfile và cache restore.
### Senior
Phân tích supply-chain, base image, native dependency và non-root execution.
### Technical Lead / Architect
Chuẩn hóa image policy, scanning, provenance và patch cadence.

## 11. Key takeaway

- Build environment và runtime environment có trách nhiệm khác nhau.
- Image nhỏ không tự động an toàn; provenance và patching vẫn cần.
- Luôn test chính final image sẽ deploy.

# 8. Contract testing: kiểm tra boundary thay vì mock theo trí tưởng tượng

## 1. What is it?

Contract test xác minh producer và consumer đồng ý về interface: endpoint, method, schema, required fields, status semantics hoặc message shape. Nó nằm giữa unit test và full E2E về scope.

## 2. Why does it exist?

Consumer có thể mock API theo assumption cũ và unit tests vẫn xanh dù producer đã đổi field/status. Full E2E cho mọi consumer thường chậm, brittle và khó vận hành.

## 3. How does it work?

```text
Consumer expectation
      -> contract
      -> verify against Provider
```

Có consumer-driven contracts và schema/spec-based approaches. Mục tiêu là kiểm tra compatibility ở boundary.

## 4. Practical implementation

Ví dụ integration test với ASP.NET Core test host xác minh public contract:

```csharp
var response = await client.GetAsync("/api/orders/42");
response.EnsureSuccessStatusCode();

var dto = await response.Content.ReadFromJsonAsync<OrderResponse>();
Assert.NotNull(dto);
Assert.Equal(42, dto.Id);
```

Ở hệ thống nhiều service, contract artifact/versioning nên được verify trong CI của provider.

## 5. Real production scenario

Inventory API đổi `quantity` từ number sang nested object. Provider unit tests và frontend mocked tests đều pass; integration vỡ khi deploy. Contract verification sẽ bắt breaking schema trước release.

## 6. Failure scenario & troubleshooting

**Symptom** → contract tests quá brittle, fail khi thêm optional field. **Evidence** → assertion so toàn JSON snapshot. **Hypothesis** → test đang khóa implementation hơn compatibility requirement. **Diagnosis** → phân loại breaking vs non-breaking changes. **Fix** → assert semantics consumer thực sự phụ thuộc. **Verification** → thử additive và breaking changes.

## 7. Common mistakes

Biến contract test thành E2E; snapshot mọi byte; không version contract; chỉ test happy path; mock provider mà không verify mock với provider thật.

## 8. Alternatives

Integration tests trực tiếp phù hợp monolith; E2E cần cho critical user journeys; OpenAPI schema validation hữu ích nhưng không luôn kiểm tra behavioral semantics.

## 9. Trade-offs

### Advantages
Feedback nhanh hơn E2E và giảm integration surprises.
### Costs / Risks
Contract lifecycle/tooling cần ownership; contract quá chi tiết tạo coupling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu test boundary khác unit test.
### Middle
Viết integration/contract assertions theo API semantics.
### Senior
Phân biệt backward-compatible và breaking changes.
### Technical Lead / Architect
Thiết kế contract ownership/versioning và CI verification giữa teams.

## 11. Key takeaway

- Mock chỉ đáng tin nếu assumption được verify với provider.
- Contract test bảo vệ compatibility, không nên khóa implementation detail.
- E2E vẫn cần nhưng không phải công cụ duy nhất cho integration risk.

# 9. HTTP idempotency keys: retry POST mà không tạo side effect lần hai

## 1. What is it?

Idempotency key là identifier do client gửi cho một logical operation. Server ghi nhận key cùng outcome để retry cùng operation không tạo thêm payment/order/booking.

## 2. Why does it exist?

Network timeout tạo ambiguity: client không biết server chưa xử lý hay đã commit nhưng response bị mất. Không retry thì có thể mất operation; retry mù thì có thể duplicate side effect.

## 3. How does it work?

```text
POST + Idempotency-Key K
 -> reserve/store K
 -> execute transaction
 -> persist result for K
 -> response lost

retry K
 -> find completed K
 -> return same logical result
```

Key scope, request fingerprint, retention và concurrent duplicate behavior phải được định nghĩa.

## 4. Practical implementation

```csharp
app.MapPost("/payments", async (
    HttpRequest request,
    PaymentService payments,
    CancellationToken ct) =>
{
    var key = request.Headers["Idempotency-Key"].ToString();
    if (string.IsNullOrWhiteSpace(key))
        return Results.BadRequest();

    return await payments.ExecuteIdempotentlyAsync(key, ct);
});
```

Persistence cần atomicity phù hợp; chỉ dùng Redis `GET` rồi `SET` tách rời có thể race.

## 5. Real production scenario

Mobile app gửi checkout, server commit order nhưng mạng rớt trước response. App retry. Cùng idempotency key trả lại order đã tạo thay vì tạo order thứ hai.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate vẫn xảy ra dưới concurrent retries. **Evidence** → hai requests cùng key đều thấy “not found”. **Hypothesis** → check-and-create không atomic. **Diagnosis** → inspect unique constraint/transaction/lock path. **Fix** → unique key + transactional state machine. **Verification** → fire concurrent identical requests và inject response loss.

## 7. Common mistakes

Key không scoped theo tenant/operation; reuse key với payload khác; giữ records mãi; cache-only implementation mất state khi eviction; coi idempotency key là authorization control.

## 8. Alternatives

PUT với resource identifier tự nhiên có idempotent semantics; unique business constraint có thể đủ; message consumers dùng inbox/deduplication tương tự nhưng ở asynchronous boundary.

## 9. Trade-offs

### Advantages
Cho phép safe retry của side-effecting operations.
### Costs / Risks
Cần persistent state, retention, concurrency handling và response replay semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu retry có thể duplicate side effect.
### Middle
Implement key validation và unique persistence.
### Senior
Thiết kế atomic state, expiry, payload fingerprint và failure recovery.
### Technical Lead / Architect
Xác định operation nào cần idempotency contract xuyên client/API/downstream.

## 11. Key takeaway

- Timeout không cho biết operation đã commit hay chưa.
- Idempotency phải atomic ở boundary tạo side effect.
- Key là reliability mechanism, không phải security mechanism.

# 10. AI RAG grounding: retrieval cung cấp evidence, không đảm bảo truth

## 1. What is it?

Retrieval-Augmented Generation (RAG) lấy các đoạn dữ liệu liên quan từ corpus rồi đưa chúng vào model context để model tạo câu trả lời dựa trên nguồn được chọn. Mental model: retrieval là **context acquisition layer**, generation vẫn là probabilistic synthesis.

## 2. Why does it exist?

Model weights không chứa chắc chắn dữ liệu nội bộ mới nhất và context window không thể luôn chứa toàn bộ knowledge base. Retrieval chọn subset có khả năng liên quan tại runtime.

## 3. How does it work?

```text
Question
 -> query transformation
 -> embedding / lexical / hybrid search
 -> top-k documents
 -> reranking/filtering
 -> prompt context
 -> LLM response
 -> citations/evaluation
```

Chất lượng cuối phụ thuộc retrieval recall, chunking, metadata filters, source freshness và generation discipline.

## 4. Practical implementation

Backend nên giữ deterministic controls ngoài model:

```csharp
var docs = await search.FindAsync(query, tenantId, ct);
var context = docs.Take(5).Select(x => x.Content).ToArray();

var answer = await llm.AnswerAsync(new AnswerRequest(
    Question: query,
    Context: context,
    RequireCitations: true), ct);
```

Authorization filter phải áp dụng trước khi tài liệu vào model context; không yêu cầu model tự quyết định user được xem document nào.

## 5. Real production scenario

Internal support assistant trả lời từ runbooks. Search index còn tài liệu cũ và tài liệu mới cùng tồn tại; retrieval chọn bản cũ khiến model trả lời trôi chảy nhưng sai procedure. Vấn đề không chỉ là “hallucination” mà là source lifecycle và ranking.

## 6. Failure scenario & troubleshooting

**Symptom** → câu trả lời sai dù nguồn đúng tồn tại. **Evidence** → trace cho thấy relevant document không nằm trong top-k. **Hypothesis** → retrieval failure, metadata/filter/chunking/ranking issue. **Diagnosis** → đánh giá retrieval riêng khỏi generation bằng labeled queries. **Fix** → hybrid search, reranking, chunk/schema improvements hoặc freshness filters. **Verification** → retrieval recall@k + answer groundedness evaluation trên regression set.

## 7. Common mistakes

Chỉ đánh giá câu trả lời cuối; tăng top-k vô hạn; index dữ liệu user không được phép xem; không version source; coi vector similarity là truth; để prompt injection trong retrieved document điều khiển tools.

## 8. Alternatives

Direct database/API lookup tốt hơn cho deterministic facts có schema; fine-tuning phù hợp behavior/style hơn dynamic knowledge; long-context có thể phù hợp corpus nhỏ nhưng vẫn cần authorization và freshness.

## 9. Trade-offs

### Advantages
Cập nhật knowledge mà không retrain, có thể cung cấp source evidence và dùng private corpus.

### Costs / Risks
Thêm search infrastructure, latency, token cost, evaluation burden, access-control và prompt-injection surface.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu retrieval và generation là hai bước.
### Middle
Implement chunk/search/context pipeline và citations.
### Senior
Đo retrieval riêng, kiểm soát security/freshness và trace token/cost/latency.
### Technical Lead / Architect
Quyết định dữ liệu nào nên dùng RAG, dữ liệu nào phải đi deterministic API, và đặt authorization/tool boundary ngoài model.

## 11. Key takeaway

- RAG giảm thiếu context; nó không biến LLM thành database.
- Đánh giá retrieval và generation riêng biệt.
- Authorization và correctness-critical logic phải deterministic bên ngoài model.
