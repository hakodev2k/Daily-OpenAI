# 1. .NET ThreadPool starvation: phân biệt blocked workers với CPU saturation

## 1. What is it?

Mental model: ThreadPool là nguồn worker threads dùng để chạy phần lớn continuation và work item của .NET. **ThreadPool starvation** xảy ra khi các worker hiện có bị giữ quá lâu bởi công việc blocking, trong khi những work item mới phải chờ được phục vụ. Đây không nhất thiết là tình trạng CPU cao: CPU có thể thấp nhưng request latency tăng mạnh.

## 2. Why does it exist?

ASP.NET Core xử lý nhiều I/O requests đồng thời mà không cần một thread cố định cho mỗi request. Nếu code gọi HTTP, SQL hoặc Redis theo kiểu đồng bộ, worker phải đứng chờ network. Khi tải tăng, số worker hữu dụng giảm; ThreadPool có thể bổ sung threads nhưng không lập tức giải quyết được mọi hàng đợi. Async I/O tồn tại để giải phóng worker trong lúc chờ.

## 3. How does it work?

Request đến Kestrel → endpoint lấy worker → code chờ I/O. Với await thực sự asynchronous, worker được trả về pool; khi I/O hoàn tất, continuation được scheduling. Với Task.Result hoặc Wait(), worker bị chiếm trong lúc chờ. Một burst có thể làm queue length tăng, thread count tăng dần và p99 latency tăng dù CPU chưa bão hòa.

Phân biệt: **CPU saturation** có CPU utilization cao và runnable work tranh CPU; **starvation** có nhiều blocked threads, pending work và đôi khi CPU thấp. Cả hai có thể cùng xảy ra.

## 4. Practical implementation

~~~csharp
// Không nên: chặn worker khi network I/O chưa xong.
var response = httpClient.GetAsync(url).Result;

// Nên: propagate CancellationToken và await.
using var response = await httpClient.GetAsync(
    url, HttpCompletionOption.ResponseHeadersRead, ct);
response.EnsureSuccessStatusCode();
await using var body = await response.Content.ReadAsStreamAsync(ct);
~~~

Trong môi trường chẩn đoán, dùng dotnet-counters để xem System.Runtime thread-pool metrics và CPU, sau đó dùng dotnet-stack hoặc dotnet-trace để kiểm tra call stacks. Metric names thay đổi theo runtime/tool version; đối chiếu với version đang vận hành.

## 5. Real production scenario

API tính báo giá gọi ba vendor. Một thư viện cũ dùng sync HTTP bên trong mỗi request. Khi marketing campaign đẩy concurrency lên 600 requests, nhiều worker chờ network; health endpoint cũng chậm vì dùng cùng worker pool. Tăng instance tạm giảm áp lực nhưng không xử lý nguyên nhân.

## 6. Failure scenario & troubleshooting

**Symptom:** p99 tăng từ 400 ms lên 12 s, CPU chỉ 35%. **Evidence:** ThreadPool queue length và thread count tăng, stacks có Task.Wait/Result. **Hypothesis:** sync-over-async trong integration. **Diagnosis:** trace xác nhận phần lớn thời gian chờ socket response. **Fix:** chuyển toàn bộ call chain sang async, đặt timeout và concurrency budget cho vendor. **Verification:** load test cùng concurrency; queue giảm, throughput ổn định, p95/p99 trở lại baseline.

## 7. Common mistakes

Cho rằng Task.Run biến blocking I/O thành nonblocking; tăng MinThreads như giải pháp mặc định; dùng async ở controller nhưng gọi thư viện sync phía dưới; bỏ qua timeout; suy đoán nguyên nhân từ CPU utilization đơn lẻ.

## 8. Alternatives

Nếu SDK chỉ có API synchronous, cô lập workload bằng worker riêng và giới hạn concurrency; cân nhắc SDK khác có async API. ThreadPool tuning có thể là biện pháp tạm thời sau đo đạc, không thay thế việc loại bỏ blocking.

## 9. Trade-offs

### Advantages

Async I/O nâng khả năng phục vụ nhiều request mà không giữ một worker cho mỗi network wait.

### Costs / Risks

Async lan qua call chain, cancellation và exception paths cần được kiểm thử; async không tự tăng tốc CPU-bound work. Giới hạn concurrency có thể tạo hàng chờ có chủ đích nhưng bảo vệ downstream.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu await không có nghĩa tạo thread mới và blocking khác waiting asynchronously.

### Middle

Tìm Task.Result/Wait, propagate CancellationToken và đo latency dưới load.

### Senior

Đọc ThreadPool telemetry cùng stacks, phân biệt CPU saturation với blocked workers và xác định saturation boundary.

### Technical Lead / Architect

Quyết định isolation của vendor integration, capacity budget, timeout policy và yêu cầu async compatibility của SDK.

## 11. Key takeaway

- CPU thấp không loại trừ ThreadPool starvation.
- Đo queue, worker count, stacks và tail latency trước khi tuning.
- Async I/O phải xuyên suốt call chain; Task.Run không sửa blocking I/O.

# 2. ASP.NET Core streaming response: memory, cancellation và proxy buffering

## 1. What is it?

Streaming response là gửi dữ liệu từng phần thay vì dựng toàn bộ payload trong memory. Mental model: API tạo một dòng bytes với tốc độ phụ thuộc cả database, serializer, network và tốc độ đọc của client.

## 2. Why does it exist?

Xuất báo cáo hàng triệu rows bằng ToListAsync rồi Serialize có thể gây allocations lớn, LOH pressure và OOM. Streaming giảm peak memory và cho phép bắt đầu gửi dữ liệu sớm hơn, nhưng không bảo đảm end-to-end streaming nếu reverse proxy hoặc CDN buffer response.

## 3. How does it work?

Database cursor → IAsyncEnumerable → encoder/writer → Kestrel response body → proxy → client. Khi client chậm, WriteAsync có thể chờ; đó là backpressure. Khi client ngắt kết nối, HttpContext.RequestAborted báo cancellation; database query và writer nên dừng. Sau khi response headers/body đã gửi, không thể đổi sang ProblemDetails bình thường.

## 4. Practical implementation

~~~csharp
app.MapGet("/reports/orders.csv", async (
    AppDbContext db, HttpContext context) =>
{
    var ct = context.RequestAborted;
    context.Response.ContentType = "text/csv; charset=utf-8";
    context.Response.Headers.ContentDisposition =
        "attachment; filename=\"orders.csv\"";

    await using var writer = new StreamWriter(
        context.Response.Body,
        new UTF8Encoding(false), 1024, leaveOpen: true);

    await writer.WriteLineAsync("Id,Total".AsMemory(), ct);

    var rows = db.Orders.AsNoTracking()
        .OrderBy(x => x.Id)
        .Select(x => new { x.Id, x.Total })
        .AsAsyncEnumerable();

    await foreach (var row in rows.WithCancellation(ct))
    {
        await writer.WriteLineAsync(
            $"{row.Id},{row.Total.ToString(
                System.Globalization.CultureInfo.InvariantCulture)}"
                .AsMemory(), ct);
    }
});
~~~

Ví dụ cố ý chỉ xuất numeric columns; CSV chứa text cần escaping quotes/newlines và phòng spreadsheet formula injection.

## 5. Real production scenario

Bộ phận finance tải 800.000 transactions. Streaming giữ memory mỗi request tương đối ổn định, nhưng database connection bị giữ suốt thời gian enumerate. Khi client mạng chậm, thời gian chiếm connection kéo dài; cần giới hạn số exports đồng thời hoặc chuyển sang asynchronous file generation.

## 6. Failure scenario & troubleshooting

**Symptom:** ứng dụng streaming nhưng browser chỉ nhận file sau 90 giây. **Evidence:** Kestrel logs cho thấy bytes được ghi sớm; reverse proxy buffering được bật. **Hypothesis:** proxy gom response trước khi gửi. **Diagnosis:** so sánh trực tiếp origin và qua ingress bằng network timings. **Fix:** cấu hình buffering phù hợp từng proxy, hoặc tạo file vào Blob Storage rồi trả download link. **Verification:** time-to-first-byte và memory profile qua đường production.

## 7. Common mistakes

Gọi ToListAsync trước khi streaming; giữ transaction dài; không xử lý RequestAborted; ghi dữ liệu nhạy cảm trước khi authorization; flush sau mỗi row gây overhead; mặc định cho rằng response compression và proxy không buffer.

## 8. Alternatives

Export nhỏ dùng buffered JSON/CSV cho đơn giản. Export rất lớn dùng BackgroundService hoặc Azure Functions tạo file trong Blob Storage rồi cấp URL có thời hạn. NDJSON hữu ích cho stream nhiều records, nhưng client phải hỗ trợ.

## 9. Trade-offs

### Advantages

Giảm peak memory và cải thiện time-to-first-byte khi network path hỗ trợ.

### Costs / Risks

Giữ database connection lâu, khó trả lỗi HTTP sau khi bắt đầu stream, khó retry từng phần và phải quản lý slow consumers.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt buffering toàn bộ response và streaming từng chunk.

### Middle

Triển khai IAsyncEnumerable, cancellation, CSV encoding và integration test với client disconnect.

### Senior

Đo allocations, database connection duration, proxy buffering và slow-client behavior.

### Technical Lead / Architect

Chọn synchronous streaming hay asynchronous export theo kích thước, SLA, quota, chi phí lưu trữ và failure recovery.

## 11. Key takeaway

- Streaming là end-to-end property, không chỉ là một vòng await foreach.
- Memory giảm nhưng connection duration và slow-client risk có thể tăng.
- Export cực lớn thường phù hợp background generation hơn HTTP request kéo dài.

# 3. EF Core ExecuteUpdate: set-based update, Change Tracker và concurrency

## 1. What is it?

ExecuteUpdateAsync cập nhật nhiều rows bằng SQL UPDATE trực tiếp, không materialize entities và không đi qua Change Tracker/SaveChanges. Mental model: đây là **set-based database command**, không phải thao tác sửa từng object đã tracked.

## 2. Why does it exist?

Với 50.000 records cần đổi trạng thái, load entities rồi foreach và SaveChanges tốn network transfer, allocations và nhiều update operations. Một UPDATE có điều kiện thường nhanh và rõ ràng hơn, miễn là business invariants không phụ thuộc vào per-entity domain behavior.

## 3. How does it work?

LINQ Where được dịch thành predicate SQL; SetProperty tạo SET expression. Lệnh thực thi ngay, trả số rows affected. Tracked entities trong cùng DbContext không tự cập nhật. ExecuteUpdate không tự gọi SaveChanges, không tự tạo transaction gộp nhiều commands và không tự áp dụng optimistic concurrency theo cách SaveChanges dùng concurrency tokens; phải tự đưa guard vào predicate khi cần.

## 4. Practical implementation

~~~csharp
var affected = await db.Orders
    .Where(o => o.Id == orderId
             && o.TenantId == tenantId
             && o.Status == OrderStatus.Pending)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(o => o.Status, OrderStatus.Approved)
        .SetProperty(o => o.ApprovedAtUtc, DateTime.UtcNow), ct);

if (affected == 0)
    return Results.Conflict(new { message = "Order changed or unavailable" });
~~~

Đây là state-transition guard tối thiểu. Nếu cần RowVersion, thêm expected token vào Where; với nhiều commands phải chủ động tạo transaction và xác định rollback policy.

## 5. Real production scenario

Một admin duyệt batch 20.000 timesheets. Update set-based phù hợp nếu mọi record đã được validate và transition không cần phát domain event riêng theo từng aggregate. Nếu mỗi timesheet cần audit và event, cần thiết kế audit/outbox trong cùng transaction thay vì chỉ chạy UPDATE.

## 6. Failure scenario & troubleshooting

**Symptom:** endpoint trả Approved nhưng response sau đó lại hiển thị Pending. **Evidence:** trước ExecuteUpdate, DbContext đã tracked Order với Status=Pending. **Hypothesis:** stale tracked entity. **Diagnosis:** kiểm tra ChangeTracker và SQL log; UPDATE thực sự thành công. **Fix:** không trộn tracked instance với set-based mutation trong cùng unit of work, hoặc reload/clear tracker có chủ đích. **Verification:** integration test đọc lại bằng DbContext mới.

## 7. Common mistakes

Giả định SaveChanges mới commit ExecuteUpdate; quên tenant predicate; tưởng concurrency token tự được kiểm tra; bỏ qua rows affected; dùng ExecuteUpdate cho aggregate có invariants/domain events; cho rằng EF tracked objects tự đồng bộ.

## 8. Alternatives

Tracked entities + SaveChanges phù hợp với domain logic và concurrency management từng entity. Raw SQL dùng cho database-specific operations. Bulk library có thể hỗ trợ staging/upsert phức tạp nhưng thêm dependency và semantics riêng.

## 9. Trade-offs

### Advantages

Ít round trips, giảm materialization và rõ ràng cho bulk state transitions.

### Costs / Risks

Bypass Change Tracker, một số domain hooks và optimistic concurrency tự động; logic invariants/audit dễ bị bỏ quên.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt tracked entity mutation và SQL UPDATE trực tiếp.

### Middle

Dùng ExecuteUpdate có filter an toàn, kiểm tra rows affected và test với database thật.

### Senior

Đánh giá concurrency guard, transaction, audit, tracker staleness và SQL generated.

### Technical Lead / Architect

Quyết định khi nào set-based update được phép vượt qua aggregate boundary và ai chịu trách nhiệm audit/events.

## 11. Key takeaway

- ExecuteUpdate chạy ngay, không chờ SaveChanges.
- Concurrency, tenant isolation và audit phải được thiết kế rõ.
- Không đổi correctness lấy throughput mà không kiểm tra business invariants.

# 4. PostgreSQL keyset pagination: composite index và stable ordering

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên vị trí cuối của trang trước, thay vì bỏ qua N rows bằng OFFSET. Mental model: client giữ một **cursor định vị trong thứ tự ổn định**, không giữ page number.

## 2. Why does it exist?

OFFSET 500000 LIMIT 50 thường buộc database duyệt/bỏ qua nhiều entries; khi có inserts giữa hai lần đọc, pages có thể lặp hoặc bỏ sót records. Keyset giảm công việc theo độ sâu trang và thường ổn định hơn với feed có dữ liệu mới.

## 3. How does it work?

ORDER BY created_at DESC, id DESC tạo total order nếu id unique. Cursor gồm cả created_at và id. Điều kiện tuple (created_at, id) < (cursorCreatedAt, cursorId) lấy records đứng sau cursor trong thứ tự DESC. Composite B-tree index bắt đầu bằng equality filter tenant_id rồi các order columns giúp index scan hiệu quả. EXPLAIN (ANALYZE, BUFFERS) xác nhận actual plan và I/O.

## 4. Practical implementation

~~~sql
CREATE INDEX CONCURRENTLY idx_orders_tenant_feed
ON orders (tenant_id, created_at DESC, id DESC)
WHERE deleted_at IS NULL;

SELECT id, created_at, total
FROM orders
WHERE tenant_id = $1
  AND deleted_at IS NULL
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 51;
~~~

Lần đầu bỏ predicate cursor; trả 50 rows và dùng row thứ 51 để xác định hasMore. Cursor phải encode cả hai values, có validation/signing nếu cần chống sửa filter/tenant scope.

## 5. Real production scenario

CRM hiển thị activity feed 5 triệu rows cho nhiều tenants. OFFSET trang 10000 tăng latency rõ rệt; keyset dùng index scan lấy 51 records kế tiếp. Khi có record mới, pagination không bị dịch theo số lượng inserts ở đầu feed.

## 6. Failure scenario & troubleshooting

**Symptom:** records bị lặp khi nhiều events có cùng created_at. **Evidence:** query chỉ ORDER BY created_at; timestamp không unique. **Hypothesis:** thứ tự không xác định trong nhóm cùng timestamp. **Diagnosis:** tái hiện với nhiều rows cùng millisecond. **Fix:** thêm id làm tie-breaker và cursor; kiểm tra index match. **Verification:** test pages dưới concurrent inserts và EXPLAIN BUFFERS trên dataset lớn.

## 7. Common mistakes

Chỉ lưu timestamp trong cursor; dùng OFFSET để jump đến trang rất sâu rồi gọi là keyset; thiếu tenant_id trong index/filter; không xét NULL sort semantics; quên soft-delete predicate; kết luận index tốt mà không xem actual buffers/rows.

## 8. Alternatives

OFFSET/LIMIT đơn giản, hợp bảng nhỏ hoặc UI cần nhảy tới trang bất kỳ. Snapshot-based pagination hợp báo cáo cần tập kết quả bất biến. Search-after của Elasticsearch dùng cơ chế cursor tương tự nhưng có semantics và snapshot riêng.

## 9. Trade-offs

### Advantages

Latency ít phụ thuộc độ sâu trang; ít duplicate/skip do inserts phía trước cursor; index-friendly.

### Costs / Risks

Khó nhảy tới trang số 300; cursor phải gắn với filters/sort; updates vào sort key vẫn có thể gây dịch chuyển; index làm tăng write/storage cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu tại sao ORDER BY cần tie-breaker unique.

### Middle

Viết cursor predicate, index tương ứng và test dữ liệu trùng timestamp.

### Senior

Đọc execution plan, phân tích MVCC/concurrent updates và đo p95 ở deep pages.

### Technical Lead / Architect

Chọn contract pagination theo UX, consistency requirements, data growth và migration compatibility.

## 11. Key takeaway

- Cursor phải phản ánh toàn bộ stable sort key.
- Query, index và tenant predicate phải được thiết kế cùng nhau.
- Keyset tối ưu scrolling, không tự cung cấp snapshot consistency.

# 5. Elasticsearch zero-downtime reindex: aliases và dữ liệu thay đổi trong lúc migrate

## 1. What is it?

Reindex là xây một index mới khi cần đổi mapping/analyzer hoặc tái cấu trúc search documents. Alias là tên logic mà Search API dùng thay cho tên index vật lý. Mental model: **build new → validate → switch pointer**, thay vì sửa mapping không tương thích trên index đang phục vụ traffic.

## 2. Why does it exist?

Một số mapping changes không thể áp dụng in-place. Rebuild hàng triệu documents có thể mất hàng giờ; nếu ứng dụng query trực tiếp index vật lý, deployment buộc downtime hoặc chạy với mapping không đồng nhất.

## 3. How does it work?

Primary database vẫn là source of truth. Pipeline tạo products_v2 với mapping mới, backfill documents, rồi replay changes phát sinh trong thời gian backfill. Sau validation, một request _aliases có thể remove alias khỏi v1 và add vào v2 atomically ở mức alias update. Atomic alias switch **không** tự đảm bảo dữ liệu v2 mới nhất hoặc đồng bộ tuyệt đối với database.

~~~text
SQL primary → outbox/change stream → indexer → products_v1 / products_v2
Search API → products_read alias → active index
~~~

## 4. Practical implementation

~~~http
POST /_aliases
Content-Type: application/json

{
  "actions": [
    { "remove": { "index": "products_v1", "alias": "products_read" } },
    { "add":    { "index": "products_v2", "alias": "products_read" } }
  ]
}
~~~

Trước switch: tạo index với analyzer mới, backfill theo stable cursor, replay outbox đến checkpoint xác định, refresh nếu cần, so sánh counts/sample queries/relevance và kiểm tra indexer lag. Với write alias, cấu hình write index riêng và xác định chính sách dual-write/replay.

## 5. Real production scenario

E-commerce muốn autocomplete tiếng Việt tốt hơn. products_v2 dùng analyzer mới; backfill mất 3 giờ. Trong lúc đó giá và trạng thái hàng thay đổi liên tục. Indexer replay events theo version để không ghi đè update mới bằng snapshot cũ.

## 6. Failure scenario & troubleshooting

**Symptom:** sau alias switch, sản phẩm vừa ngừng bán vẫn xuất hiện. **Evidence:** v2 document version thấp hơn primary DB; indexer lag còn 8 phút. **Hypothesis:** switch trước khi replay hoàn tất. **Diagnosis:** so sánh checkpoint, event offsets và document versions. **Fix:** rollback alias nếu cần, replay missing events, đặt readiness gate cho cutover. **Verification:** sampling theo version và lag dashboard trước/sau switch.

## 7. Common mistakes

Reindex rồi switch ngay mà bỏ qua concurrent writes; dùng Elasticsearch làm transactional source of truth; dual-write không có retry/reconciliation; kiểm tra chỉ document count; quên mapping compatibility của Search API; xóa v1 quá sớm.

## 8. Alternatives

Nếu chỉ thay query logic, có thể không cần reindex. Rolling schema evolution với additive fields phù hợp khi mapping cho phép. External search service giảm vận hành cluster nhưng vẫn cần synchronization và consistency strategy.

## 9. Trade-offs

### Advantages

Cho phép migration analyzer/mapping không downtime; rollback alias nhanh nếu index cũ còn hợp lệ.

### Costs / Risks

Tốn gấp đôi storage và indexing throughput tạm thời; phải quản lý event replay, version ordering và relevance regression.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt index vật lý, alias và primary database.

### Middle

Tạo mapping, backfill, query alias và kiểm thử search results.

### Senior

Thiết kế replay/checkpoint, đo lag, xử lý out-of-order events và cutover validation.

### Technical Lead / Architect

Quyết định search freshness SLA, rollback window, index ownership và chi phí migration.

## 11. Key takeaway

- Atomic alias switch không đồng nghĩa atomic data synchronization.
- Backfill phải đi cùng replay và version control.
- Giữ index cũ đủ lâu để rollback có kiểm soát.

# 6. Transactional Outbox: database commit không đồng nghĩa message delivery

## 1. What is it?

Transactional Outbox ghi business change và event record vào **cùng một database transaction**. Một relay riêng đọc outbox rồi publish lên message broker. Mental model: đảm bảo event cần gửi được ghi bền cùng transaction, không đảm bảo broker chỉ nhận đúng một lần.

## 2. Why does it exist?

Flow SaveChanges → Publish có cửa sổ lỗi: database commit thành công nhưng process crash trước khi publish. Flow Publish → SaveChanges có lỗi ngược: consumer nhận event dù transaction database rollback. Không có distributed transaction, hai hệ thống không thể được xem là một commit duy nhất.

## 3. How does it work?

Command handler ghi Order và OutboxMessage, commit một transaction. Relay claim pending records, publish và đánh dấu delivered. Nếu crash sau publish nhưng trước mark delivered, event có thể được publish lại. Consumer cần dedup/idempotency; ordering cần strategy theo aggregate/version nếu nghiệp vụ yêu cầu.

~~~text
HTTP command → DB transaction [Order + Outbox]
                             ↓
                         Relay poll
                             ↓
                          Broker
                             ↓
                    Idempotent consumer
~~~

## 4. Practical implementation

~~~csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

db.Orders.Add(order);
db.OutboxMessages.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    AggregateId = order.Id,
    EventType = "OrderPlaced",
    PayloadJson = JsonSerializer.Serialize(
        new { order.Id, order.Total }),
    CreatedAtUtc = DateTime.UtcNow
});

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
~~~

Relay phải có cơ chế claim an toàn cho nhiều instances (ví dụ row locking/lease), retry có backoff, monitoring age của oldest pending message và dead-letter/quarantine cho payload lỗi.

## 5. Real production scenario

Checkout ghi đơn hàng thành công nhưng Azure Service Bus outage 12 phút. API không mất event vì outbox nằm trong SQL. Khi broker phục hồi, relay publish backlog; inventory consumer xử lý event theo EventId để không trừ hàng hai lần.

## 6. Failure scenario & troubleshooting

**Symptom:** khách bị gửi hai confirmation emails. **Evidence:** cùng EventId xuất hiện hai lần sau relay restart. **Hypothesis:** relay publish thành công nhưng crash trước update outbox. **Diagnosis:** đối chiếu broker logs và outbox timestamps. **Fix:** consumer Inbox table có unique constraint trên EventId; side effect cần idempotency key. **Verification:** fault-injection tại điểm sau publish, trước mark; xác nhận email chỉ gửi một lần theo business rule.

## 7. Common mistakes

Nói Outbox bảo đảm exactly-once delivery; xóa record trước khi broker ack; không có retention/cleanup; chạy nhiều relay mà không claim rows; thiếu event schema version; cho rằng idempotency trong database tự bảo vệ external email/payment side effects.

## 8. Alternatives

Nếu mất event chấp nhận được, best-effort publish có thể đủ cho analytics không trọng yếu. Change Data Capture đọc database log thay relay polling; giảm một số polling cost nhưng tăng hạ tầng. Distributed transactions chỉ phù hợp khi các hệ thống thực sự hỗ trợ và chi phí vận hành được chấp nhận.

## 9. Trade-offs

### Advantages

Loại bỏ dual-write gap giữa business transaction và durable intent-to-publish.

### Costs / Risks

Thêm outbox table, relay, backlog handling, dedup và eventual consistency; end-to-end exactly-once side effects vẫn khó.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Nhận diện hai thao tác DB và broker không commit atomically.

### Middle

Ghi outbox trong transaction, xây relay retry và consumer dedup.

### Senior

Thiết kế claim/lease, ordering, poison events, schema evolution và observability.

### Technical Lead / Architect

Quyết định bounded context, delivery SLA, reconciliation và chi phí consistency model.

## 11. Key takeaway

- Outbox giải quyết durable intent, không loại bỏ duplicate delivery.
- Consumer phải idempotent theo business side effect.
- Backlog age và replay correctness là production requirements.

# 7. Azure Service Bus PeekLock: settlement, lock renewal và poison messages

## 1. What is it?

PeekLock cho phép consumer nhận message nhưng chưa xóa ngay. Broker cấp lock tạm thời; consumer xử lý xong thì Complete, lỗi có thể Abandon hoặc DeadLetter. Mental model: **nhận message là một lease có hạn**, không phải quyền sở hữu vĩnh viễn.

## 2. Why does it exist?

Receive-and-delete mất message nếu worker crash ngay sau receive. PeekLock hỗ trợ at-least-once processing: message được phát lại nếu worker không settle trước khi lock hết hạn. Vì thế consumer phải chấp nhận duplicates.

## 3. How does it work?

Broker giao message + lock token → handler chạy → Complete khi side effect đã bền. Nếu lock expires, message có thể được delivery lại và Complete từ handler cũ thất bại. MaxDeliveryCount vượt ngưỡng dẫn đến DLQ theo broker configuration. Auto lock renewal kéo dài lease nhưng không sửa handler bị treo mãi; cần execution timeout riêng.

## 4. Practical implementation

~~~csharp
var processor = client.CreateProcessor("order-events",
    new ServiceBusProcessorOptions
    {
        AutoCompleteMessages = false,
        MaxConcurrentCalls = 8,
        MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(5)
    });

processor.ProcessMessageAsync += async args =>
{
    var eventId = args.Message.MessageId;
    try
    {
        await orderHandler.ProcessIdempotentlyAsync(
            eventId, args.Message.Body, args.CancellationToken);
        await args.CompleteMessageAsync(args.Message,
            args.CancellationToken);
    }
    catch (InvalidOrderEventException ex)
    {
        await args.DeadLetterMessageAsync(args.Message,
            "InvalidPayload", ex.Message, args.CancellationToken);
    }
};

processor.ProcessErrorAsync += args =>
{
    logger.LogError(args.Exception,
        "Service Bus processor failure: {Source}", args.ErrorSource);
    return Task.CompletedTask;
};
~~~

Transient failures nên để retry/redelivery theo policy; cần logging có MessageId, DeliveryCount và correlation metadata.

## 5. Real production scenario

Inventory consumer cần gọi ERP mất 45 giây. Khi burst, 8 consumers hoạt động đồng thời; message locks được renew trong lúc xử lý. Một vài requests ERP timeout và messages được retry, nhưng unique EventId trong Inbox ngăn double decrement.

## 6. Failure scenario & troubleshooting

**Symptom:** Duplicate stock deductions và MessageLockLost exceptions. **Evidence:** handler mất 7 phút trong khi max auto-renew là 5 phút; cùng MessageId được giao lại. **Hypothesis:** lease hết hạn trước khi side effect hoàn tất. **Diagnosis:** trace thời gian ERP, lock renewal failures và delivery count. **Fix:** rút ngắn/timeout ERP calls, tách long-running workflow, tăng renewal có giới hạn và bảo đảm idempotency. **Verification:** test slow ERP và crash giữa side effect với Complete.

## 7. Common mistakes

Giả định FIFO mặc định cho mọi queue; AutoComplete=true dù handler cần explicit settlement; Complete trước database commit; retry vĩnh viễn poison payload; coi MessageId unique do broker cấp cho mọi producer; tăng concurrency mà không xét ERP capacity.

## 8. Alternatives

Receive-and-delete chỉ phù hợp với work mất được. Azure Storage Queues đơn giản hơn nhưng khác features và semantics. Durable workflow hoặc orchestrator phù hợp operation kéo dài hàng giờ thay vì giữ message lock quá lâu.

## 9. Trade-offs

### Advantages

At-least-once recovery, DLQ, broker-managed retry và concurrency control.

### Costs / Risks

Duplicates, lock management, poison-message handling, throughput limits và vận hành backlog.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Complete, Abandon, DeadLetter và lock expiry.

### Middle

Viết explicit settlement, handler idempotent và error telemetry.

### Senior

Tối ưu MaxConcurrentCalls, lock duration, renewal, retries và poison-message policy.

### Technical Lead / Architect

Quyết định event ordering, throughput budget, recovery objectives và ownership của DLQ/replay.

## 11. Key takeaway

- PeekLock tạo at-least-once behavior, không phải exactly-once.
- Lock renewal không thay thế bounded processing time.
- Complete chỉ sau khi side effect đã được xử lý bền vững.

# 8. Kubernetes probes: readiness khác liveness và shutdown đúng cách

## 1. What is it?

Readiness probe trả lời “Pod này có nên nhận traffic không?”. Liveness probe trả lời “Container có cần restart để phục hồi không?”. Startup probe cho phép ứng dụng khởi động chậm mà không bị liveness giết quá sớm. Ba câu hỏi khác nhau không nên dùng một endpoint duy nhất mà không suy xét.

## 2. Why does it exist?

Một process có thể vẫn chạy nhưng chưa sẵn sàng phục vụ: migration chưa hoàn tất, warm-up chưa xong, hoặc đang shutdown. Ngược lại, database tạm thời unavailable không nhất thiết có nghĩa restart process sẽ sửa được sự cố. Phân biệt probes giúp tránh cascade failures.

## 3. How does it work?

Kubelet gọi probes định kỳ. Readiness failure loại Pod khỏi endpoints của Service (sau thời gian propagation); liveness failure kích hoạt restart container. Khi terminate, Kubernetes bắt đầu grace period và gửi termination signal theo lifecycle; app cần ngừng nhận work mới và hoàn tất in-flight work trong giới hạn. Readiness failure không trực tiếp kill Pod.

## 4. Practical implementation

~~~yaml
containers:
  - name: api
    image: example/api:1.2.3
    ports:
      - containerPort: 8080
    readinessProbe:
      httpGet: { path: /health/ready, port: 8080 }
      periodSeconds: 5
      failureThreshold: 2
    livenessProbe:
      httpGet: { path: /health/live, port: 8080 }
      periodSeconds: 10
      failureThreshold: 3
    startupProbe:
      httpGet: { path: /health/live, port: 8080 }
      periodSeconds: 5
      failureThreshold: 24
terminationGracePeriodSeconds: 45
~~~

ASP.NET Core có thể dùng AddHealthChecks và MapHealthChecks với predicates khác nhau. /health/live chỉ nên kiểm tra process health cơ bản; /health/ready kiểm tra khả năng phục vụ thật sự nhưng tránh khiến toàn bộ fleet NotReady vì dependency chung bị outage nếu app vẫn có degraded-mode hữu ích.

## 5. Real production scenario

Deployment 6 replicas của Order API. New Pods cần 25 giây warm-up. Startup probe bảo vệ giai đoạn khởi động; readiness chỉ bật sau warm-up. Khi rolling update, old Pods chuyển sang draining để giảm 502 từ requests đang xử lý.

## 6. Failure scenario & troubleshooting

**Symptom:** tất cả Pods restart liên tục khi Redis outage. **Evidence:** liveness endpoint kiểm tra Redis và trả 503; kubelet restart mọi container. **Hypothesis:** dependency outage bị hiểu nhầm là process deadlock. **Diagnosis:** kubectl describe pod cho thấy liveness failures; Redis metrics cho thấy outage độc lập. **Fix:** bỏ Redis khỏi liveness, xác định readiness/degraded policy riêng. **Verification:** chaos test Redis outage; Pods không restart storm, traffic behavior đúng thiết kế.

## 7. Common mistakes

Dùng cùng deep dependency check cho cả liveness và readiness; threshold quá thấp; không có startup probe cho cold start; chỉ dựa vào preStop sleep; bỏ qua ingress/load-balancer propagation; shutdown không propagate CancellationToken.

## 8. Alternatives

Đối với App Service có Health Check và deployment slots, lifecycle khác nhưng vẫn cần phân biệt “process alive” và “ready for traffic”. Trong Kubernetes, application-level draining có thể bổ sung readiness và termination grace period.

## 9. Trade-offs

### Advantages

Rolling deployment an toàn hơn, tránh route traffic vào Pod chưa sẵn sàng và phát hiện process wedged.

### Costs / Risks

Probe sai gây restart storm hoặc traffic blackhole; graceful shutdown dài làm rollout chậm và giữ tài nguyên.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Nhớ readiness điều khiển traffic, liveness điều khiển restart.

### Middle

Cấu hình endpoints, probes và test startup/shutdown.

### Senior

Phân tích rollout race, dependency outage, draining và kubelet events.

### Technical Lead / Architect

Định nghĩa service availability semantics, degraded mode, rollout SLO và shutdown budget.

## 11. Key takeaway

- Không dùng dependency outage làm lý do restart toàn bộ fleet.
- Readiness, liveness và startup là ba tín hiệu khác nhau.
- Graceful shutdown phải được kiểm thử qua network path thực tế.

# 9. ASP.NET Core resource-based authorization: ngăn Broken Object Level Authorization

## 1. What is it?

Resource-based authorization kiểm tra quyền truy cập trên **đối tượng cụ thể**, không chỉ kiểm tra user đã đăng nhập hay có role chung. Mental model: “user là Manager” không đồng nghĩa “user xem được mọi invoice”.

## 2. Why does it exist?

API GET /invoices/123 có thể được bảo vệ bằng RequireAuthorization nhưng vẫn lộ dữ liệu nếu attacker thay ID thành 124 thuộc tenant khác. Đây là Broken Object Level Authorization (BOLA/IDOR): authentication đúng, object authorization sai.

## 3. How does it work?

Authenticate identity → xác định tenant/user scope đáng tin cậy → query resource trong boundary → authorize action với resource → trả DTO. Tenant ID từ request body/query string không phải nguồn đáng tin nếu chưa được xác thực. Resource-based handler có thể kiểm tra owner, department, state và delegated permissions.

## 4. Practical implementation

~~~csharp
app.MapGet("/invoices/{id:guid}", async (
    Guid id, ClaimsPrincipal user, AppDbContext db,
    IAuthorizationService authz, CancellationToken ct) =>
{
    var tenantId = user.FindFirst("tenant_id")?.Value;
    if (tenantId is null) return Results.Forbid();

    var invoice = await db.Invoices.AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id
            && x.TenantId == tenantId, ct);

    if (invoice is null) return Results.NotFound();

    var decision = await authz.AuthorizeAsync(
        user, invoice, "InvoiceRead");

    if (!decision.Succeeded) return Results.Forbid();

    return Results.Ok(new {
        invoice.Id, invoice.Number, invoice.Total
    });
}).RequireAuthorization();
~~~

Cần đăng ký policy InvoiceRead và AuthorizationHandler phù hợp. Claim tenant_id phải do trusted identity/token validation cung cấp; với multi-tenant membership phức tạp, resolve tenant từ server-side membership thay vì tin bất kỳ claim chưa được kiểm chứng.

## 5. Real production scenario

SaaS invoicing có hàng nghìn tenants. Nhân viên Finance thuộc tenant A chỉ được xem invoice của A; trong tenant A, một số invoices thuộc restricted department cần handler kiểm tra thêm. Tenant predicate giảm phạm vi dữ liệu ngay từ query, handler quyết định business permission.

## 6. Failure scenario & troubleshooting

**Symptom:** pentest phát hiện user A đọc invoice của user B bằng cách thay GUID. **Evidence:** endpoint chỉ có [Authorize] và query FindAsync(id). **Hypothesis:** không có object-level authorization. **Diagnosis:** integration test với hai tenants tái hiện 200 thay vì 404/403. **Fix:** scoped query + resource policy, review các list/export/download endpoints. **Verification:** matrix tests cross-tenant, same-tenant different-owner và role changes.

## 7. Common mistakes

Dựa vào GUID khó đoán để bảo mật; kiểm tra role nhưng không kiểm tra ownership; tin tenantId client gửi; authorize sau khi đã serialize/log sensitive data; chỉ bảo vệ GET mà quên PATCH/download; lạm dụng global query filter như lớp bảo vệ duy nhất.

## 8. Alternatives

Policy-based authorization phù hợp rule không phụ thuộc object. Database row-level security có thể bổ sung defense-in-depth nhưng không thay thế business authorization và cần quản lý session context cẩn thận.

## 9. Trade-offs

### Advantages

Giảm cross-tenant data leakage, policy rõ và testable, có thể tái sử dụng authorization handlers.

### Costs / Risks

Có thêm lookup và policy complexity; permission changes/caching cần freshness strategy; 403/404 semantics phải thống nhất để tránh information disclosure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt authentication, role authorization và resource authorization.

### Middle

Viết scoped query, handler và negative integration tests.

### Senior

Threat-model IDOR ở list/export/download, đánh giá TOCTOU và tenant-context trust boundary.

### Technical Lead / Architect

Thiết kế authorization ownership, centralized policies, audit và multi-tenant isolation strategy.

## 11. Key takeaway

- Đăng nhập thành công không có nghĩa được phép truy cập mọi object.
- Tenant scope phải được áp dụng từ data access boundary.
- Negative authorization tests là yêu cầu bắt buộc cho multi-tenant APIs.

# 10. React + TypeScript: hủy request cũ và tránh stale response ghi đè state

## 1. What is it?

Trong frontend, nhiều HTTP requests có thể hoàn thành khác thứ tự được gửi. Stale response race xảy ra khi request cho input cũ hoàn thành sau request mới rồi ghi đè state hiện tại. Mental model: **response hợp lệ về HTTP nhưng không còn hợp lệ với UI intent mới nhất**.

## 2. Why does it exist?

Autocomplete, product search và filter UI thường gửi request khi user thay đổi input. Network latency không cố định. Nếu query "car" mất 800 ms và "cargo" mất 100 ms, kết quả "car" có thể đến cuối cùng, khiến UI hiển thị sai dù backend trả đúng.

## 3. How does it work?

React useEffect chạy khi dependency thay đổi; cleanup của effect cũ có thể AbortController.abort() request đang chờ. Abort giảm work không cần thiết, nhưng vẫn nên guard state update vì request có thể hoàn thành ngay trước cleanup hoặc asynchronous post-processing tiếp tục. Development StrictMode có thể setup/cleanup effect thêm lần để phát hiện side effects không an toàn.

## 4. Practical implementation

~~~tsx
useEffect(() => {
  const controller = new AbortController();
  let active = true;

  async function load() {
    try {
      const response = await fetch(
        "/api/products?q=" + encodeURIComponent(query),
        { signal: controller.signal }
      );
      if (!response.ok) throw new Error("Search failed");
      const data: Product[] = await response.json();
      if (active) setProducts(data);
    } catch (error) {
      if (active && !controller.signal.aborted) {
        setError("Unable to load products");
      }
    }
  }

  void load();
  return () => {
    active = false;
    controller.abort();
  };
}, [query]);
~~~

Ở production cần thêm loading/error reset và debounce khi cần; AbortController không bảo đảm backend đã dừng query nếu cancellation không được propagate.

## 5. Real production scenario

Vue/React storefront có search-as-you-type. User nhập liên tục, 10 requests được tạo trong 2 giây. Frontend hủy requests cũ, backend nhận cancellation khi connection đóng nếu framework/proxy propagate, nhưng vẫn áp dụng rate limiting và index optimization vì cancellation không thay thế capacity management.

## 6. Failure scenario & troubleshooting

**Symptom:** ô search hiển thị "cargo" nhưng list kết quả lại là "car". **Evidence:** browser Network waterfall cho thấy request cũ hoàn thành sau request mới. **Hypothesis:** race giữa async callbacks. **Diagnosis:** thêm request sequence IDs vào logs, tái hiện bằng network throttling. **Fix:** abort + active guard hoặc dùng query library với cache key theo input. **Verification:** test thay input nhanh với response delays đảo thứ tự.

## 7. Common mistakes

Chỉ debounce mà không xử lý in-flight requests; bỏ qua response.ok; dùng một global loading flag cho nhiều queries; không cleanup effect; nghĩ abort bảo đảm server rollback; không encode query string; để lỗi request cũ ghi đè error state của request mới.

## 8. Alternatives

TanStack Query hoặc SWR quản lý cache keys, stale state và refetch policy; phù hợp UI nhiều screens cùng dùng server state. Debounce giảm request rate nhưng không giải quyết mọi race. Server-driven search với explicit request IDs hữu ích khi có streaming updates.

## 9. Trade-offs

### Advantages

UI phản ánh intent mới nhất, giảm network waste và tránh stale overwrite.

### Costs / Risks

Tăng lifecycle complexity; hủy quá mạnh gây loading flicker; query caching thêm invalidation policy và memory footprint.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu requests có thể hoàn thành khác thứ tự khởi tạo.

### Middle

Dùng AbortController, cleanup effect, debounce và test network throttling.

### Senior

Phân biệt client race, server cancellation, cache freshness và state ownership.

### Technical Lead / Architect

Chọn fetch trực tiếp hay query library, thống nhất API cancellation/error contracts và UX consistency.

## 11. Key takeaway

- Response mới về thời gian không nhất thiết thuộc query mới nhất.
- AbortController và state guard giải quyết hai khía cạnh khác nhau.
- Frontend race conditions cần được test với network delay đảo thứ tự.
