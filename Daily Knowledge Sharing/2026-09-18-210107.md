# 1. .NET `Channel<T>`: backpressure và bounded producer/consumer pipelines

## 1. What is it?

`Channel<T>` là asynchronous producer/consumer primitive trong .NET. Mental model đúng không phải “một queue nhanh hơn”, mà là **một boundary điều tiết tốc độ giữa nơi tạo work và nơi xử lý work**. Producer ghi vào `ChannelWriter<T>`, consumer đọc từ `ChannelReader<T>`; bounded channel có thể tạo backpressure khi consumer chậm hơn producer.

## 2. Why does it exist?

Một API có thể nhận work nhanh hơn background processor xử lý. Nếu chỉ đẩy mọi item vào `ConcurrentQueue<T>` không giới hạn, queue length trở thành memory leak hợp pháp: throughput đầu vào vượt throughput đầu ra đủ lâu sẽ làm process cạn memory.

`Channel<T>` cung cấp async waiting, completion semantics và bounded capacity để overload được biểu diễn thành hành vi có kiểm soát.

## 3. How does it work?

```text
Producer(s)
    │
    ▼
┌──────────────────────┐
│ Bounded Channel: 100 │
└──────────────────────┘
    │            ▲
    │            │ full → writer waits/rejects/drops theo policy
    ▼
Consumer(s)
```

`BoundedChannelFullMode` quyết định khi đầy: `Wait`, `DropNewest`, `DropOldest`, hoặc `DropWrite`. Đây là business/reliability decision, không chỉ performance option.

## 4. Practical implementation

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true,
    SingleWriter = false
});

async Task ProduceAsync(Job job, CancellationToken ct)
{
    await channel.Writer.WriteAsync(job, ct);
}

async Task ConsumeAsync(CancellationToken ct)
{
    await foreach (var job in channel.Reader.ReadAllAsync(ct))
    {
        await ProcessAsync(job, ct);
    }
}
```

Nếu request HTTP không được phép chờ lâu khi channel đầy, có thể dùng `TryWrite` và trả `429`/`503`, hoặc tốt hơn chuyển durable work sang broker.

## 5. Real production scenario

Một ASP.NET Core service nhận yêu cầu tạo thumbnail. Resize mất 200 ms nhưng request ingress có thể burst 2.000 items/s. Unbounded in-memory queue khiến memory tăng liên tục. Bounded channel giới hạn work đang chờ và buộc hệ thống thể hiện overload thay vì giả vờ nhận vô hạn.

## 6. Failure scenario & troubleshooting

**Symptom** → API latency tăng mạnh dù CPU consumer chỉ ở mức ổn định.  
**Evidence** → channel luôn gần capacity, writers chờ lâu.  
**Hypothesis** → sustained producer rate lớn hơn consumer capacity.  
**Diagnosis** → đo enqueue wait time, queue depth, processing rate và dependency latency.  
**Fix** → tăng consumer capacity nếu bottleneck cho phép, giảm ingress, reject có kiểm soát, hoặc chuyển sang durable queue.  
**Verification** → queue depth hồi phục sau burst và p95 enqueue latency nằm trong budget.

## 7. Common mistakes

Dùng unbounded channel cho traffic không giới hạn; coi channel như durable queue; fire-and-forget writer không quan sát failure; không complete writer khi shutdown; tăng consumer count dù downstream database đã saturated.

## 8. Alternatives

`ConcurrentQueue<T>` phù hợp khi tự quản synchronization và capacity. `BlockingCollection<T>` phù hợp legacy synchronous producer/consumer. Azure Service Bus phù hợp khi cần durability, cross-process delivery, retries và scale-out.

## 9. Trade-offs

### Advantages

Async-friendly, throughput tốt, backpressure rõ và giảm manual synchronization.

### Costs / Risks

In-memory nên mất dữ liệu khi process chết; bounded policy có thể block/drop work; capacity tuning cần đo thực tế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu producer, consumer và bounded queue.

### Middle

Implement cancellation, completion và capacity policy.

### Senior

Đo throughput mismatch, shutdown semantics và downstream saturation.

### Technical Lead / Architect

Quyết định boundary nào chỉ cần in-process pipeline và boundary nào phải dùng durable messaging.

## 11. Key takeaway

- Backpressure là correctness/reliability concern, không chỉ performance.
- Unbounded queue có thể biến traffic burst thành memory exhaustion.
- `Channel<T>` không thay thế durable broker khi work không được phép mất.

# 2. ASP.NET Core `ProblemDetails`: biến error handling thành API contract ổn định

## 1. What is it?

`ProblemDetails` là representation chuẩn cho HTTP API errors theo RFC 7807/9457-style problem details. Mental model: error response là **public API contract**, không phải nơi serialize exception nội bộ.

## 2. Why does it exist?

Nếu mỗi endpoint trả lỗi theo format khác nhau — string, anonymous object, stack trace, `null` — clients phải viết parsing logic theo từng endpoint. Khi backend refactor exception types, client có thể vô tình bị break.

## 3. How does it work?

```text
Exception / validation / domain failure
              │
              ▼
      Error mapping boundary
              │
              ▼
HTTP status + ProblemDetails
              │
              ▼
            Client
```

Public `type`, `title`, `status`, `detail`, `instance` và extensions nên mô tả contract cần thiết; internal stack trace đi vào telemetry, không đi ra internet.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails(options =>
{
    options.CustomizeProblemDetails = context =>
    {
        context.ProblemDetails.Extensions["traceId"] =
            Activity.Current?.TraceId.ToString() ?? context.HttpContext.TraceIdentifier;
    };
});

var app = builder.Build();
app.UseExceptionHandler();
app.UseStatusCodePages();
```

Domain exceptions nên được map có chủ đích, ví dụ stale concurrency thành `409` hoặc precondition failure thành `412`, thay vì mọi exception thành `500`.

## 5. Real production scenario

Frontend Vue và mobile app cùng gọi employee approval API. Backend chuẩn hóa lỗi validation, authorization và conflict bằng ProblemDetails; clients có thể dựa trên `status` và stable application error code thay vì parse message tiếng Anh.

## 6. Failure scenario & troubleshooting

**Symptom** → Production response lộ SQL query/connection string fragments.  
**Evidence** → middleware đặt `exception.ToString()` vào `detail`.  
**Hypothesis** → internal diagnostic data bị trộn với public contract.  
**Diagnosis** → inspect response samples và centralized exception mapping.  
**Fix** → log exception server-side với trace ID; trả generic detail + stable code.  
**Verification** → security test xác nhận response không chứa stack trace/secrets nhưng log vẫn correlation được.

## 7. Common mistakes

Trả HTTP 200 kèm `{ success:false }`; dùng exception message làm machine-readable code; mọi lỗi đều 500; expose stack trace; format validation khác hoàn toàn domain errors; không version/ổn định custom extension names.

## 8. Alternatives

Custom error envelope có thể cần nếu legacy clients đã phụ thuộc contract đó, nhưng nên có schema nhất quán. GraphQL có error model riêng. Không cần ProblemDetails cho internal exceptions không vượt HTTP boundary.

## 9. Trade-offs

### Advantages

Client integration nhất quán, observability tốt hơn và giảm coupling với exception implementation.

### Costs / Risks

Cần mapping taxonomy; quá nhiều application error codes tạo maintenance burden; sai mapping có thể che server defect thành 4xx.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code và public error payload khác exception.

### Middle

Implement centralized mapping và validation responses.

### Senior

Thiết kế stable error taxonomy, correlation và security boundary.

### Technical Lead / Architect

Định nghĩa error contract xuyên APIs và backward compatibility policy cho clients.

## 11. Key takeaway

- Error response là API contract.
- Diagnostics chi tiết thuộc telemetry, không thuộc public response.
- Status code, stable error code và trace correlation phải có vai trò riêng.

# 3. EF Core Split Queries: tránh cartesian explosion mà không tạo consistency illusion

## 1. What is it?

Split query cho phép EF Core load một object graph bằng nhiều SQL queries thay vì một query JOIN lớn. Mental model: **đổi duplication/cartesian explosion lấy nhiều database round trips và một consistency window lớn hơn**.

## 2. Why does it exist?

Khi include nhiều sibling collections, một query có thể nhân rows. Một Blog có 20 Posts và 30 Contributors có thể tạo 600 rows cho một Blog, lặp lại parent columns nhiều lần.

## 3. How does it work?

```text
Single query:
Blog JOIN Posts JOIN Contributors
→ row multiplication

Split query:
SELECT Blogs
SELECT Posts for Blogs
SELECT Contributors for Blogs
→ multiple result sets / round trips
```

`AsSplitQuery()` giảm duplication nhưng các queries không tự động trở thành một atomic snapshot ở mọi isolation level.

## 4. Practical implementation

```csharp
var blogs = await db.Blogs
    .AsNoTracking()
    .Include(x => x.Posts)
    .Include(x => x.Contributors)
    .AsSplitQuery()
    .Where(x => x.IsPublished)
    .ToListAsync(ct);
```

Nếu chỉ cần DTO summary, projection thường tốt hơn cả `Include` single lẫn split query.

## 5. Real production scenario

CMS endpoint load page cùng blocks, tags và related content. Single JOIN trả hàng chục MB vì repeated content fields. Split query giảm payload DB→app đáng kể, nhưng endpoint vẫn cần đo tổng round trips.

## 6. Failure scenario & troubleshooting

**Symptom** → response đôi lúc chứa parent và child state không hoàn toàn cùng thời điểm.  
**Evidence** → update xảy ra giữa các split statements.  
**Hypothesis** → application giả định split query là một snapshot atomic.  
**Diagnosis** → inspect isolation level và timing giữa statements.  
**Fix** → nếu consistency yêu cầu nghiêm ngặt, dùng transaction/isolation phù hợp hoặc query shape khác.  
**Verification** → concurrency test dưới write load.

## 7. Common mistakes

Bật split queries globally mà không đo; dùng `Include` khi projection đủ; bỏ qua network latency của nhiều round trips; nghĩ `AsSplitQuery` luôn nhanh hơn; không có deterministic ordering khi kết hợp pagination ở các phiên bản/scenarios nhạy cảm.

## 8. Alternatives

Projection giảm columns và graph materialization. Explicit separate queries cho phép control rõ hơn. Single query tốt khi graph nhỏ và JOIN không gây explosion.

## 9. Trade-offs

### Advantages

Giảm row duplication, network payload và memory materialization trong graph lớn.

### Costs / Risks

Nhiều round trips hơn, consistency window rộng hơn và execution complexity tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` biến thành SQL JOIN/query work.

### Middle

Nhận diện cartesian explosion và dùng `AsSplitQuery` có chủ đích.

### Senior

So sánh payload, round trips, isolation và projection.

### Technical Lead / Architect

Đặt query-shaping conventions dựa trên read use case thay vì mặc định load entity graph.

## 11. Key takeaway

- Split query giải quyết một cost nhưng tạo cost khác.
- Projection thường là lựa chọn tốt nhất cho API read models.
- Consistency giữa nhiều statements phải được đánh giá theo isolation requirement.

# 4. SQL Keyset Pagination: ổn định latency và dữ liệu khi dataset thay đổi

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên giá trị sort key cuối cùng đã thấy, thay vì `OFFSET N`. Mental model: **seek từ vị trí logic đã biết**, không yêu cầu database bỏ qua ngày càng nhiều rows.

## 2. Why does it exist?

`OFFSET 100000` thường vẫn buộc engine xử lý/skip lượng lớn rows. Ngoài ra khi rows được insert/delete giữa requests, offset có thể khiến client thấy duplicate hoặc bỏ sót item.

## 3. How does it work?

```text
Page 1: ORDER BY CreatedAt DESC, Id DESC LIMIT 20
cursor = (last.CreatedAt, last.Id)

Page 2:
WHERE (CreatedAt, Id) < cursor
ORDER BY CreatedAt DESC, Id DESC
LIMIT 20
```

Cần deterministic ordering; `CreatedAt` một mình có thể trùng nên thường thêm unique tiebreaker như `Id`.

## 4. Practical implementation

SQL Server:

```sql
SELECT TOP (20) Id, CreatedAt, Total
FROM Orders
WHERE TenantId = @TenantId
  AND (
       CreatedAt < @LastCreatedAt
       OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
  )
ORDER BY CreatedAt DESC, Id DESC;
```

Index phù hợp có thể bắt đầu bằng `(TenantId, CreatedAt DESC, Id DESC)` tùy workload và selectivity.

## 5. Real production scenario

Order history có hàng triệu rows/tenant. Page 1 nhanh nhưng page 5.000 với offset chậm hàng giây. Cursor pagination giữ access pattern gần index seek và latency ổn định hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → cursor pagination vẫn scan nhiều rows.  
**Evidence** → execution plan dùng scan, logical reads cao.  
**Hypothesis** → predicate/order không khớp index hoặc cursor expression không sargable.  
**Diagnosis** → actual plan, logical reads, index definition và parameter values.  
**Fix** → align access pattern/index; tránh function trên indexed sort column.  
**Verification** → logical reads và p95 gần ổn định ở page sâu.

## 7. Common mistakes

Cursor chỉ chứa timestamp không unique; encode raw DB details không versioning; cho phép arbitrary sort fields nhưng không có index strategy; dùng keyset khi UI bắt buộc nhảy trực tiếp page 973.

## 8. Alternatives

Offset pagination đơn giản và phù hợp dataset nhỏ hoặc random page navigation. Search engine `search_after` có mental model tương tự cho deep pagination. Snapshot/export workflow phù hợp khi cần toàn bộ dataset ổn định.

## 9. Trade-offs

### Advantages

Latency ổn định hơn, ít skip work và chịu concurrent inserts tốt hơn.

### Costs / Risks

Khó random page jump; cursor contract phức tạp; multi-column sorting cần predicate/index cẩn thận.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu offset và cursor khác nhau.

### Middle

Implement deterministic keyset predicate.

### Senior

Đọc execution plan và thiết kế composite index theo access pattern.

### Technical Lead / Architect

Chọn pagination contract dựa trên UX, scale, consistency và API compatibility.

## 11. Key takeaway

- Deep offset là work, không phải phép nhảy miễn phí.
- Keyset cần deterministic unique ordering.
- Pagination contract và index design phải được thiết kế cùng nhau.

# 5. MongoDB Embedding vs Referencing: modeling theo access pattern và document boundary

## 1. What is it?

Embedding đặt related data trong cùng document; referencing lưu identity để truy cập document khác. Mental model: MongoDB modeling nên bắt đầu từ **data được đọc/ghi cùng nhau như thế nào**, không phải chuyển relational tables thành collections 1:1.

## 2. Why does it exist?

Document database cho phép aggregate data gần nhau để đọc atomic/local hơn, nhưng document có size/lifecycle boundary. Embed mọi thứ tạo unbounded documents; reference mọi thứ biến MongoDB thành relational database không có join ergonomics tương tự.

## 3. How does it work?

```text
Embedding
Order
 ├─ CustomerSnapshot
 └─ Lines[]

Referencing
Product ── productId ──► Reviews collection
```

Data có ownership/lifecycle gắn chặt và bounded thường là candidate tốt để embed. Shared, independently changing hoặc unbounded data thường nghiêng về reference.

## 4. Practical implementation

```json
{
  "_id": "order-123",
  "customerId": "cust-9",
  "shippingAddress": {
    "city": "Hanoi",
    "country": "VN"
  },
  "lines": [
    { "sku": "SKU-1", "quantity": 2, "unitPrice": 120000 }
  ]
}
```

Order nên giữ price/address snapshot tại thời điểm mua thay vì luôn reference current product/customer state nếu business cần historical truth.

## 5. Real production scenario

E-commerce product có hàng trăm nghìn reviews. Embed tất cả reviews vào Product sẽ tạo unbounded growth và write contention. Reviews nên tách collection; một vài aggregate fields như rating summary có thể denormalize vào Product.

## 6. Failure scenario & troubleshooting

**Symptom** → update product document ngày càng chậm và document tiến gần size limit.  
**Evidence** → embedded array tăng không giới hạn.  
**Hypothesis** → unbounded one-to-many bị embed sai boundary.  
**Diagnosis** → đo document size distribution, update frequency và query patterns.  
**Fix** → tách child collection, giữ bounded summary/reference cần thiết.  
**Verification** → document growth ổn định và critical reads vẫn đạt latency target.

## 7. Common mistakes

Model collections giống tables; normalize mọi thứ; embed unbounded arrays; duplicate data nhưng không xác định source of truth; dùng `$lookup` cho mọi request rồi mất lợi ích locality.

## 8. Alternatives

SQL phù hợp khi relational constraints, joins và cross-entity transactions là trung tâm. Cosmos DB cũng cần access-pattern modeling nhưng thêm partition-key/distribution constraints khác.

## 9. Trade-offs

### Advantages

Embedding giảm round trips và có locality/atomicity tốt trong document.

### Costs / Risks

Duplication, document growth và update fan-out. Referencing giảm duplication nhưng tăng query/consistency complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu embed và reference không tương đương “NoSQL vs SQL”.

### Middle

Model theo read/write pattern và bounded growth.

### Senior

Đánh giá update frequency, duplication, atomicity và document size.

### Technical Lead / Architect

Chọn database/model dựa trên invariants và access patterns thay vì trend công nghệ.

## 11. Key takeaway

- Document boundary nên phản ánh data thay đổi và được đọc cùng nhau.
- Unbounded child collection là cảnh báo lớn với embedding.
- Denormalization cần source-of-truth và synchronization semantics rõ.

# 6. DDD Aggregate Boundary: bảo vệ invariant mà không biến aggregate thành distributed transaction

## 1. What is it?

Aggregate là consistency boundary trong domain model; Aggregate Root là entry point kiểm soát thay đổi bên trong boundary đó. Mental model: **những invariant nào bắt buộc phải đúng ngay sau một transaction local?** — đó mới là câu hỏi dẫn tới aggregate boundary.

## 2. Why does it exist?

Nếu bất kỳ code nào cũng sửa mọi entity trực tiếp, business invariants bị phân tán. Ngược lại, nếu gom cả hệ thống vào một aggregate khổng lồ để “giữ consistency”, concurrency và scalability sẽ tệ.

## 3. How does it work?

```text
Order Aggregate
┌─────────────────────────────┐
│ Order (Root)                │
│ ├─ OrderLine                │
│ └─ ShippingSelection        │
│ Invariants enforced here    │
└─────────────────────────────┘
          │ domain event
          ▼
Other Aggregate / process
```

Cross-aggregate consistency thường cần eventual workflow/domain events thay vì một object graph transaction khổng lồ.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void AddLine(ProductId productId, int quantity, Money price)
    {
        if (quantity <= 0) throw new DomainException("Quantity must be positive.");
        if (_lines.Count >= 100) throw new DomainException("Order line limit exceeded.");

        _lines.Add(new OrderLine(productId, quantity, price));
    }
}
```

Không expose mutable list để application bypass invariant.

## 5. Real production scenario

Approval system có `ApprovalRequest` và `Employee` aggregates. “Request phải có ít nhất một approver” có thể nằm trong request boundary. “Employee dashboard phải phản ánh request mới ngay lập tức” thường không đáng kéo Employee vào cùng transaction; projection có thể cập nhật eventual.

## 6. Failure scenario & troubleshooting

**Symptom** → mỗi update Order lock/load hàng nghìn child records.  
**Evidence** → aggregate chứa history, comments, payments và shipments không bounded.  
**Hypothesis** → aggregate được thiết kế theo navigation convenience thay vì invariant.  
**Diagnosis** → liệt kê invariants nào thực sự cần atomic consistency.  
**Fix** → tách boundaries và dùng IDs/events cho cross-aggregate workflow.  
**Verification** → transaction nhỏ hơn nhưng business invariants vẫn được test và giữ đúng.

## 7. Common mistakes

DDD = Entities + Repository + MediatR; aggregate = database table; load toàn graph mỗi command; reference trực tiếp aggregate khác bằng object graph; tạo domain model phức tạp cho CRUD đơn giản.

## 8. Alternatives

Transaction Script/Application Service đơn giản hơn cho domain ít business rules. Rich domain model hữu ích khi invariants và state transitions phức tạp. Modular Monolith vẫn có thể áp DDD boundaries mà không cần microservices.

## 9. Trade-offs

### Advantages

Business rules tập trung, transaction boundary rõ và giảm invalid state.

### Costs / Risks

Modeling khó, có eventual consistency giữa aggregates và dễ overengineer CRUD system.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Entity, Aggregate và Aggregate Root khác nhau.

### Middle

Implement methods bảo vệ invariant thay vì public setters tùy ý.

### Senior

Xác định transactional invariant và tránh aggregate quá lớn.

### Technical Lead / Architect

Đặt domain boundary dựa trên business consistency, ownership và change patterns; không map aggregate thành microservice một cách máy móc.

## 11. Key takeaway

- Aggregate là consistency boundary, không phải folder pattern.
- Chỉ invariant cần atomicity mới nên kéo data vào cùng boundary.
- Cross-aggregate workflow thường cần explicit eventual consistency.

# 7. Azure Functions queue processing: retries, poison messages và idempotent execution

## 1. What is it?

Queue-triggered Azure Function xử lý message theo event-driven execution. Mental model: **message có thể được xử lý nhiều lần**, và failure phải có bounded retry/dead-letter/poison strategy thay vì giả định mỗi message chỉ chạy một lần.

## 2. Why does it exist?

Background work không nên giữ HTTP request mở. Queue decouple producer khỏi consumer và hấp thụ burst, nhưng distributed delivery tạo duplicate/retry semantics.

## 3. How does it work?

```text
Producer → Queue → Function instance
                    │
                    ├─ success → complete/delete
                    └─ failure → retry
                                │
                                └─ max attempts → poison/DLQ path
```

Chi tiết retry/poison phụ thuộc binding/service (Storage Queue, Service Bus), nên architecture phải biết broker semantics cụ thể.

## 4. Practical implementation

```csharp
[Function("ProcessInvoice")]
public async Task Run(
    [ServiceBusTrigger("invoice-jobs", Connection = "ServiceBus")]
    InvoiceMessage message,
    CancellationToken ct)
{
    if (await store.WasProcessedAsync(message.MessageId, ct))
        return;

    await processor.ProcessAsync(message, ct);
    await store.MarkProcessedAsync(message.MessageId, ct);
}
```

Trong production, `ProcessAsync` + inbox marker cần atomic design phù hợp; check rồi mark rời rạc có thể vẫn duplicate sau crash.

## 5. Real production scenario

Invoice Function gọi email provider. Provider gửi email thành công nhưng Function crash trước message settlement. Message được redeliver; nếu handler không idempotent, customer nhận hai invoices.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng business action xuất hiện nhiều lần.  
**Evidence** → message delivery count > 1 và first attempt mất ack/settlement.  
**Hypothesis** → handler giả định exactly-once.  
**Diagnosis** → correlate message ID, Function invocation ID và downstream side effect.  
**Fix** → idempotency key/inbox, bounded retry và DLQ workflow.  
**Verification** → force crash sau side effect và chứng minh retry không tạo duplicate effect.

## 7. Common mistakes

Retry mọi exception như nhau; poison message retry vô hạn; không alert DLQ; dùng non-idempotent external API không có key; tăng concurrency khi downstream đã rate-limited.

## 8. Alternatives

Worker Service + Service Bus cho lifecycle/control rõ hơn. Container Apps Jobs phù hợp một số batch workloads. Synchronous API phù hợp work ngắn cần immediate result.

## 9. Trade-offs

### Advantages

Elastic event-driven processing, decoupling và operational integration tốt với Azure.

### Costs / Risks

Cold/startup behavior tùy hosting, duplicate delivery, retry storms, DLQ operations và cost theo workload/plan.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue trigger không đảm bảo exactly-once.

### Middle

Implement cancellation, retry-aware handler và poison handling.

### Senior

Thiết kế idempotency, concurrency và downstream protection.

### Technical Lead / Architect

Chọn Function/Worker/Container dựa trên workload, operational control, scaling và delivery semantics.

## 11. Key takeaway

- Retry là bình thường trong message processing.
- Idempotency phải bao gồm side effect thực, không chỉ database handler.
- DLQ/poison queue cần owner, alert và recovery procedure.

# 8. Kubernetes resource requests/limits: scheduling, throttling và OOMKilled

## 1. What is it?

`requests` mô tả resource mà scheduler dùng để placement Pod; `limits` đặt upper boundary cho container resource usage. Mental model: request là **scheduling reservation signal**, limit là **runtime enforcement boundary** — chúng không phải cùng một thứ.

## 2. Why does it exist?

Không có resource declarations, cluster khó placement workloads và một noisy container có thể tranh CPU/memory với workloads khác. Nhưng limit sai cũng có thể tự gây outage.

## 3. How does it work?

```text
Pod requests: CPU 500m, Memory 512Mi
        │
        ▼
Scheduler tìm Node đủ requested capacity
        │
        ▼
Runtime
 ├─ CPU vượt limit → throttling
 └─ Memory vượt limit → có thể OOMKilled
```

CPU là compressible resource: process có thể bị throttle. Memory không thể “throttle” tương tự khi vượt cgroup limit; termination có thể xảy ra.

## 4. Practical implementation

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "768Mi"
```

Giá trị phải dựa trên observed workload, startup behavior, GC/memory characteristics và SLO, không copy từ service khác.

## 5. Real production scenario

.NET API có memory limit 256Mi nhưng startup + JIT + caches + concurrent requests cần 350Mi. Pod chạy local bình thường nhưng production lặp `OOMKilled`, restart và fail readiness.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng dù node CPU chưa 100%.  
**Evidence** → container CPU throttling metrics cao, CPU limit thấp.  
**Hypothesis** → cgroup throttling, không phải code CPU regression.  
**Diagnosis** → inspect `kubectl describe`, container metrics, throttling, restart reason và working set.  
**Fix** → tune request/limit dựa trên profile; tối ưu app nếu usage thực sự bất thường.  
**Verification** → p95 latency và throttling/OOM events cải thiện dưới load test.

## 7. Common mistakes

Request = limit cho mọi workload mà không hiểu burst; memory limit sát average; không set request khiến autoscaling/scheduling khó dự đoán; thấy OOM rồi chỉ tăng limit mà không kiểm tra leak.

## 8. Alternatives

App Service/Container Apps che bớt scheduler-level complexity. VM/IIS cho resource model khác nhưng vẫn cần capacity planning. Kubernetes chỉ đáng giá nếu operational requirements biện minh complexity.

## 9. Trade-offs

### Advantages

Scheduling predictable hơn, isolation tốt hơn và hỗ trợ cluster capacity planning.

### Costs / Risks

Over-request làm lãng phí cluster; under-request tạo contention; limits quá chặt gây throttling/OOM.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt request và limit.

### Middle

Đọc Pod events và metrics khi restart/throttle.

### Senior

Tune dựa trên load, GC, HPA và SLO.

### Technical Lead / Architect

Quyết định resource governance và liệu Kubernetes operational burden có phù hợp hệ thống/team.

## 11. Key takeaway

- Scheduler dùng requests; runtime enforce limits.
- CPU throttling và memory OOM là failure modes khác nhau.
- Resource values phải đến từ measurement, không từ YAML folklore.

# 9. Optimizely CMS content modeling: Page, Block và reusable editorial boundaries

## 1. What is it?

Content modeling định nghĩa các content types và quan hệ mà editor sử dụng để xây nội dung. Trong Optimizely CMS, Page và Block là implementation concepts hữu ích, nhưng mental model rộng hơn là **editorial domain model**: cái gì có identity/navigation riêng, cái gì là reusable composition, và cái gì chỉ là field/value.

## 2. Why does it exist?

Nếu mọi page là một blob HTML tự do, editor có flexibility nhưng consistency, reuse, accessibility và migration rất khó. Nếu model quá cứng, mỗi thay đổi marketing lại cần deployment.

## 3. How does it work?

```text
Site
└── Product Landing Page
    ├── Hero Block
    ├── Rich Text Block
    └── Promo Grid
        ├── Promo Block
        └── Promo Block
```

Page thường có route/context riêng; Block là composable/reusable content. Nhưng không nên biến mọi vài fields thành Block nếu không có reuse/editorial value.

## 4. Practical implementation

```csharp
[ContentType(DisplayName = "Hero Block", GUID = "11111111-2222-3333-4444-555555555555")]
public class HeroBlock : BlockData
{
    [Display(Name = "Heading", Order = 10)]
    public virtual string? Heading { get; set; }

    [Display(Name = "Call to action", Order = 20)]
    public virtual Url? CallToAction { get; set; }
}
```

Model cần validation/editor hints và naming theo ngôn ngữ business/editor, không theo database/backend implementation.

## 5. Real production scenario

Marketing site có Hero dùng ở 40 landing pages. Shared Block giúp reuse, nhưng nếu editors cần mỗi page tùy chỉnh độc lập thì shared instance có thể tạo accidental global change. “Reusable type” và “shared content instance” là hai quyết định khác nhau.

## 6. Failure scenario & troubleshooting

**Symptom** → editor sửa banner ở một page nhưng 20 pages khác thay đổi theo.  
**Evidence** → tất cả pages reference cùng shared Block instance.  
**Hypothesis** → reuse semantics không phù hợp editorial expectation.  
**Diagnosis** → inspect content references và editor workflow.  
**Fix** → dùng local block/property hoặc clone content khi ownership phải độc lập.  
**Verification** → editorial acceptance test xác nhận scope thay đổi đúng mong đợi.

## 7. Common mistakes

Model theo UI pixel/layout hiện tại; tạo một mega-page type hàng trăm properties; shared Block cho content thực ra page-owned; business naming kém; migration content bị bỏ quên khi đổi model.

## 8. Alternatives

Headless CMS tách rendering mạnh hơn nhưng vẫn cần content model tốt. Hard-coded frontend config phù hợp content hiếm khi đổi. Traditional CMS rendering đơn giản hơn khi editorial + web app cùng lifecycle.

## 9. Trade-offs

### Advantages

Reuse, governance, editor autonomy và structured content tốt hơn.

### Costs / Risks

Model evolution/migration, caching complexity và editor confusion nếu abstraction quá kỹ thuật.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Page, Block và content property.

### Middle

Implement content types có validation và rendering rõ.

### Senior

Thiết kế reuse/ownership, caching và migration impact.

### Technical Lead / Architect

Đặt content boundaries dựa trên editorial workflow, multi-channel needs và evolution cost; không map CMS model trực tiếp từ component tree.

## 11. Key takeaway

- Content model là domain model cho editors.
- Reusable type không nhất thiết đồng nghĩa shared instance.
- Modeling phải cân bằng editor flexibility với governance và migration cost.

# 10. MCP security boundary: tool capability, prompt injection và least privilege cho AI agents

## 1. What is it?

Model Context Protocol (MCP) chuẩn hóa cách AI applications kết nối tools/resources. Mental model quan trọng: MCP mở **capability boundary** giữa probabilistic model và deterministic external systems. Tool schema giúp model biết cách gọi tool; nó không tự làm tool call an toàn.

## 2. Why does it exist?

AI agent cần truy cập repository, database, ticketing hoặc internal services. Nếu mỗi integration có protocol riêng, orchestration phức tạp. Chuẩn hóa interface giảm integration friction, nhưng đồng thời làm blast radius lớn hơn nếu permissions quá rộng.

## 3. How does it work?

```text
User / external content
        │
        ▼
      LLM/Agent
        │ tool decision
        ▼
   MCP Client/Host
        │
        ▼
   MCP Server / Tool
        │
        ▼
External System
```

Untrusted content có thể chứa prompt injection kiểu “hãy xóa repository”. Security boundary phải nằm ở permissions, validation, approvals và deterministic policy — không nằm ở việc hy vọng model bỏ qua instruction độc hại.

## 4. Practical implementation

Application-side policy có thể giới hạn tool surface:

```csharp
public static bool CanInvoke(string toolName, UserContext user) =>
    toolName switch
    {
        "repo.read" => user.CanReadRepository,
        "repo.create_pr" => user.CanCreatePullRequest,
        "repo.delete" => false,
        _ => false
    };
```

Tool arguments tiếp tục phải validate như mọi external input. Read-only và write capabilities nên tách riêng khi có thể.

## 5. Real production scenario

Repository agent đọc issue chứa text do external user viết. Issue cố instruct agent upload secrets hoặc modify CI workflow. Nếu agent có broad repository token và write tool không guard, prompt injection có thể chuyển từ text attack thành real action.

## 6. Failure scenario & troubleshooting

**Symptom** → agent thực hiện write action không phù hợp với user intent.  
**Evidence** → tool trace cho thấy decision bắt nguồn từ untrusted document content.  
**Hypothesis** → instruction/data boundary bị trộn và tool permission quá rộng.  
**Diagnosis** → inspect tool audit log, provenance của context, authorization decision và granted scopes.  
**Fix** → least privilege, read/write separation, deterministic authorization, confirmation/approval cho high-impact action, sanitize/label untrusted context.  
**Verification** → adversarial prompt-injection evals không thể vượt permission boundary.

## 7. Common mistakes

Tin system prompt là security control duy nhất; cho agent admin token; expose destructive tool khi không cần; tool server không re-authorize; log secrets trong tool traces; coi tool output là trusted chỉ vì đến từ integration.

## 8. Alternatives

Direct API integration có thể đơn giản hơn cho một workflow cố định. Function/Tool Calling của provider giải quyết model-to-tool contract nhưng security principles vẫn giống nhau. Human-in-the-loop phù hợp high-impact actions.

## 9. Trade-offs

### Advantages

Integration chuẩn hóa, tool ecosystem dễ tái sử dụng và agent có thể thực hiện workflows phong phú.

### Costs / Risks

Capability expansion tăng attack surface, permission governance, audit requirements và prompt-injection exposure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu MCP kết nối model với tools; model output không phải authorization.

### Middle

Implement schema validation, scoped credentials và audit logs.

### Senior

Threat-model prompt injection, data provenance và write actions.

### Technical Lead / Architect

Thiết kế capability architecture: tool nào tồn tại, ai được gọi, scope nào, action nào cần approval, và blast radius khi model sai là bao nhiêu.

## 11. Key takeaway

- Tool protocol không thay security model.
- Deterministic authorization và least privilege phải nằm ngoài LLM reasoning.
- Untrusted content phải được giả định có thể cố điều khiển agent.
- AI agent an toàn khi sai decision vẫn bị giới hạn bởi capability boundary.
