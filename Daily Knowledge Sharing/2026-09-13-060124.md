# 1. C# generic variance (`in` / `out`): type safety, substitutability và vì sao variance chỉ hợp lệ ở đúng direction

## 1. What is it?

Generic variance mô tả việc một generic interface hoặc delegate có thể giữ quan hệ assignability dựa trên quan hệ kế thừa của type argument hay không.

Ví dụ nếu `Cat : Animal`, câu hỏi là:

```text
IEnumerable<Cat> có thể dùng ở nơi cần IEnumerable<Animal> không?
Action<Animal> có thể dùng ở nơi cần Action<Cat> không?
```

Trong C#:

- `out T` là **covariance**: type chỉ đi ra khỏi abstraction.
- `in T` là **contravariance**: type chỉ đi vào abstraction.
- không có `in/out` là invariant.

Mental model:

```text
Producer<T>  -> thường covariant  -> out T
Consumer<T>  -> thường contravariant -> in T
Mutable container<T> -> thường invariant
```

Variance không phải cú pháp trang trí. Nó là cam kết compile-time rằng abstraction chỉ sử dụng `T` theo direction an toàn.

## 2. Why does it exist?

Không có variance, code generic rất dễ ép developer cast hoặc duplicate adapters chỉ để truyền collection/handler giữa các type có quan hệ kế thừa.

Ví dụ `IEnumerable<Cat>` chỉ cho đọc `Cat`. Vì mọi `Cat` đều là `Animal`, consumer đọc `Animal` là an toàn. Nhưng `List<Cat>` vừa đọc vừa ghi. Nếu cho phép coi `List<Cat>` là `List<Animal>`, caller có thể thêm `Dog`, phá invariant của list.

Đây là lý do C# cho phép variance với interface/delegate phù hợp nhưng không cho phép tùy ý trên generic class mutable.

## 3. How does it work?

Covariance:

```csharp
public interface IProducer<out T>
{
    T Produce();
}
```

`T` xuất hiện ở output position. Vì vậy:

```csharp
IProducer<Cat> cats = ...;
IProducer<Animal> animals = cats;
```

Contravariance:

```csharp
public interface IConsumer<in T>
{
    void Consume(T item);
}
```

Nếu một consumer xử lý được mọi `Animal`, nó chắc chắn xử lý được `Cat`:

```csharp
IConsumer<Animal> animalConsumer = ...;
IConsumer<Cat> catConsumer = animalConsumer;
```

Nếu compiler thấy `out T` bị dùng làm input hoặc `in T` bị return theo cách không an toàn, nó từ chối compile.

## 4. Practical implementation

Ví dụ event pipeline chỉ đọc event:

```csharp
public interface IEventHandler<in TEvent>
{
    Task HandleAsync(TEvent message, CancellationToken ct);
}

public sealed class AuditHandler : IEventHandler<DomainEvent>
{
    public Task HandleAsync(DomainEvent message, CancellationToken ct)
    {
        Console.WriteLine($"Audit {message.GetType().Name}");
        return Task.CompletedTask;
    }
}

public abstract record DomainEvent;
public sealed record OrderCreated(Guid OrderId) : DomainEvent;

IEventHandler<DomainEvent> allEvents = new AuditHandler();
IEventHandler<OrderCreated> orderHandler = allEvents;
```

Ở đây contravariance hợp lý vì handler nhận event vào nhưng không trả ra `TEvent`.

## 5. Real production scenario

Một application có nhiều domain events và middleware decorators cho logging, validation, telemetry. Nếu handler interface được thiết kế đúng variance, một decorator hoặc fallback handler cho base event có thể dùng lại cho derived events mà không cần cast nguy hiểm.

Ngược lại, một repository vừa nhận vừa trả entity thường không nên cố biến thành covariant/contravariant abstraction vì nó vừa consume vừa produce cùng `T`.

## 6. Failure scenario & troubleshooting

**Symptom:** developer thêm `out T` để “cho dễ assign” nhưng compiler báo `Invalid variance`.

**Evidence:** `T` được dùng trong method parameter hoặc mutable member.

**Hypothesis:** abstraction thực chất vừa produce vừa consume `T`.

**Diagnosis:** nhìn từng vị trí `T` xuất hiện, không chỉ nhìn tên interface.

**Fix:** bỏ variance hoặc tách abstraction thành read-only producer và write-only consumer nếu domain thật sự có hai responsibilities riêng.

**Verification:** compile-time assignability phản ánh đúng behavior mong muốn và không cần unsafe cast.

## 7. Common mistakes

- Nghĩ `List<Cat>` phải assign được cho `List<Animal>` chỉ vì `Cat : Animal`.
- Thêm `out`/`in` để “fix compile error” mà không hiểu direction.
- Tạo inheritance hierarchy quá sâu rồi dựa vào variance để chữa thiết kế domain yếu.
- Dùng cast runtime thay vì sửa contract compile-time.
- Áp variance cho abstraction mutable có semantics không rõ.

## 8. Alternatives

- **Invariant generic:** default an toàn khi type vừa input vừa output.
- **Base interface riêng:** ví dụ `IReadOnlyRepository<out T>` nếu thực sự chỉ đọc.
- **Adapter:** hợp lý khi hai contracts có semantics khác nhau, không chỉ khác type.
- **Composition thay inheritance:** thường đơn giản hơn nếu hierarchy tồn tại chỉ để reuse.

## 9. Trade-offs

### Advantages

- API linh hoạt hơn mà vẫn type-safe.
- Giảm cast và adapter vô nghĩa.
- Làm producer/consumer responsibility rõ hơn.

### Costs / Risks

- Signature khó hiểu hơn với team chưa quen.
- Variance có thể đẩy thiết kế thành abstraction quá tinh vi nếu business không cần.
- Không giải quyết được mismatch semantics giữa hai types dù compiler cho phép assign.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu vì sao collection vừa đọc vừa ghi không thể tự do thay type argument theo inheritance.

### Middle

Biết đọc và thiết kế `in`/`out` cho interface/delegate thực tế.

### Senior

Nhận diện khi compile error đang tiết lộ abstraction có responsibilities trộn lẫn, thay vì chỉ tìm cách cast.

### Technical Lead / Architect

Quyết định mức abstraction nào giúp hệ thống rõ hơn; tránh generic API quá thông minh chỉ để tối ưu reuse nhỏ.

## 11. Key takeaway

- `out` dành cho producer, `in` dành cho consumer, mutable generic thường invariant.
- Variance là type-safety contract, không phải convenience syntax.
- Nếu variance khó áp dụng, có thể abstraction đang trộn nhiều responsibilities.

# 2. ASP.NET Core model binding và validation boundary: phân biệt malformed input, invalid request và broken business invariant

## 1. What is it?

ASP.NET Core model binding chuyển dữ liệu HTTP — route, query string, headers, form, JSON body — thành .NET parameters/models. Validation sau đó kiểm tra request model có đáp ứng các rules ở boundary hay không.

Mental model đúng:

```text
HTTP bytes
  -> parsing / deserialization
  -> model binding
  -> request validation
  -> application use case
  -> domain invariants
```

Ba loại lỗi khác nhau cần được phân biệt:

1. **Malformed input**: JSON sai cú pháp, kiểu dữ liệu không parse được.
2. **Invalid request**: field thiếu, format/range không hợp lệ ở API contract.
3. **Business rule violation**: request structurally hợp lệ nhưng action không được phép theo domain state.

## 2. Why does it exist?

Nếu mọi validation bị nhồi vào controller hoặc entity, hệ thống mất boundary rõ ràng. API-specific concerns như `pageSize <= 100` khác với domain invariant như “không thể approve timesheet đã Locked”.

Boundary validation giúp reject request sớm. Domain validation bảo vệ business state kể cả command đến từ HTTP, queue hay batch job.

## 3. How does it work?

Với `[ApiController]`, ASP.NET Core có thể tự động trả 400 khi model state invalid. JSON deserializer parse request body trước khi endpoint/application code chạy.

Flow điển hình:

```text
POST /timesheets/123/approve
  -> route binds timesheetId
  -> body binds ApproveTimesheetRequest
  -> contract validation
  -> handler loads aggregate
  -> aggregate checks business invariant
  -> SaveChanges
```

Validation ở API boundary không nên query database cho mọi rule chỉ vì framework gọi nó là “validation”. Database-dependent business rule thường thuộc application/domain layer.

## 4. Practical implementation

Request DTO:

```csharp
public sealed record CreateEmployeeRequest(
    [property: Required, EmailAddress] string Email,
    [property: Range(1, 50)] int WeeklyHours);
```

Endpoint:

```csharp
app.MapPost("/employees", async (
    CreateEmployeeRequest request,
    EmployeeService service,
    CancellationToken ct) =>
{
    try
    {
        var id = await service.CreateAsync(request.Email, request.WeeklyHours, ct);
        return Results.Created($"/employees/{id}", new { id });
    }
    catch (DuplicateEmployeeException ex)
    {
        return Results.Conflict(new ProblemDetails
        {
            Title = "Employee already exists",
            Detail = ex.Message,
            Status = StatusCodes.Status409Conflict
        });
    }
});
```

Email format/range là request-contract concern. Duplicate employee là business/data state conflict, phù hợp hơn với `409 Conflict` thay vì ép thành generic 400.

## 5. Real production scenario

Một timesheet API nhận request hợp lệ về JSON và field types. Nhưng user cố submit timesheet sau payroll cutoff.

Nếu rule chỉ nằm trong controller, queue consumer hoặc admin job có thể bypass nó. Nếu invariant nằm trong application/domain boundary, mọi entry point đều phải tuân thủ.

## 6. Failure scenario & troubleshooting

**Symptom:** mobile client nhận toàn bộ lỗi dưới dạng `400 Bad Request`, không phân biệt input typo với business conflict.

**Evidence:** controller có hàng chục `if`, trả string lỗi tùy ý; domain service không bảo vệ state.

**Hypothesis:** validation boundaries bị trộn.

**Diagnosis:** phân loại từng rule: transport/contract, application authorization, business invariant, persistence constraint.

**Fix:** chuẩn hóa `ProblemDetails`, giữ lightweight contract validation ở API, chuyển business rules vào application/domain, map exception/result sang HTTP semantics.

**Verification:** contract tests xác nhận malformed → 400, conflict → 409, forbidden → 403, not found → 404 theo policy hệ thống.

## 7. Common mistakes

- Dùng Data Annotations cho mọi business rule.
- Query database trong custom model validator khiến binding path có hidden I/O.
- Tin rằng frontend validation đủ nên backend bỏ validate.
- Trả stack trace/internal exception message cho client.
- Dùng `400` cho mọi failure.
- Cho entity chấp nhận invalid state rồi hy vọng controller đã kiểm tra trước.

## 8. Alternatives

- **Data Annotations:** đơn giản cho basic contract rules.
- **FluentValidation:** phù hợp rules phức tạp ở request/application boundary nếu team muốn explicit validator classes.
- **Domain methods/value objects:** bảo vệ invariants cần tồn tại ngoài HTTP.
- **Database constraints:** lớp bảo vệ cuối cho uniqueness/referential/data integrity.

## 9. Trade-offs

### Advantages

- Failure semantics rõ hơn.
- Business rules không phụ thuộc transport.
- API contract dễ test và document.

### Costs / Risks

- Cùng một rule có thể cần representation ở nhiều tầng với mục tiêu khác nhau.
- Over-engineering validation pipeline có thể làm simple CRUD phức tạp không cần thiết.
- Mapping domain failure sang HTTP cần policy nhất quán.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu model binding khác validation và request validation khác business rule.

### Middle

Thiết kế DTO, status code, `ProblemDetails` và validation tests rõ ràng.

### Senior

Phân định transport, application, domain và persistence constraints; tránh hidden database I/O trong binding/validation.

### Technical Lead / Architect

Đặt error contract dùng chung, quyết định rule nào phải được bảo vệ ở domain boundary và rule nào chỉ thuộc API surface.

## 11. Key takeaway

- “Invalid input” có nhiều loại; không nên collapse tất cả thành generic 400.
- API validation bảo vệ contract, domain logic bảo vệ business state.
- `ProblemDetails` và HTTP semantics giúp client xử lý failure có chủ đích.

# 3. EF Core `AddDbContextPool`: giảm allocation nhưng có thể giữ stale per-request state nếu coi pooled `DbContext` như scoped object bình thường

## 1. What is it?

`AddDbContextPool<TContext>` cho phép EF Core tái sử dụng `DbContext` instances giữa các scopes thay vì tạo mới hoàn toàn mỗi request.

Mental model:

```text
Request A -> rent DbContext -> use -> reset -> return pool
Request B -> rent same instance -> use -> reset -> return pool
```

Pooling giảm allocation và setup overhead của context, nhưng nó thay đổi một assumption quan trọng: object instance có thể sống vật lý lâu hơn một request dù logic scope vẫn là một unit-of-work.

## 2. Why does it exist?

Tạo `DbContext` thường không phải bottleneck lớn, nhưng ở high-throughput services, allocation/setup lặp lại có thể đáng kể. Pooling giảm chi phí này.

Tuy nhiên, `DbContext` là stateful object. Nếu developer thêm custom mutable fields như `TenantId`, `UserId`, timezone hoặc request flags vào context constructor/properties mà không hiểu pooling, state có thể rò từ request trước sang request sau.

## 3. How does it work?

EF Core reset internal state cần thiết khi context trả về pool. Nhưng framework không tự hiểu mọi custom state do application thêm vào.

```text
Context instance #7
Request A: TenantId = 101
return pool
Request B: same instance #7
Nếu TenantId không được set/reset đúng -> query filter có thể dùng 101
```

Đây là failure nghiêm trọng trong multi-tenant system.

Connection pooling và `DbContext` pooling là hai thứ khác nhau:

- ADO.NET connection pool tái sử dụng database connections.
- EF Core context pool tái sử dụng context objects.

## 4. Practical implementation

Registration:

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("AppDb")));
```

Không nên inject request-specific state trực tiếp vào pooled context constructor theo kiểu stateful. Một approach an toàn hơn là truyền tenant condition trong query/application layer hoặc dùng scoped factory wrapper được thiết kế rõ.

Ví dụ explicit query:

```csharp
public Task<List<Order>> GetOrdersAsync(
    Guid tenantId,
    CancellationToken ct)
{
    return db.Orders
        .Where(x => x.TenantId == tenantId)
        .AsNoTracking()
        .ToListAsync(ct);
}
```

Nếu dùng global query filter multi-tenant cùng pooling, cần thiết kế tenant state theo guidance chính thức và test leakage đặc biệt kỹ.

## 5. Real production scenario

SaaS API có `TenantId` lấy từ JWT. Team thêm property `CurrentTenantId` vào `DbContext` và bật pooling để cải thiện benchmark.

Trong concurrency test, hiếm khi một request tenant B đọc data tenant A vì context reused với stale tenant state. Đây là security incident chứ không chỉ bug performance.

## 6. Failure scenario & troubleshooting

**Symptom:** rất hiếm request trả dữ liệu sai tenant hoặc query filter có tenant ID không khớp current request.

**Evidence:** context instance IDs lặp lại; custom property giữ value từ request trước; lỗi chỉ xuất hiện khi pooling bật.

**Hypothesis:** custom per-request state bị lưu trong pooled context.

**Diagnosis:** audit mọi mutable field/property/service dependency trên context; test concurrent multi-tenant requests.

**Fix:** loại request state khỏi pooled object hoặc set/reset bằng pattern được thiết kế riêng; nếu complexity/risk cao, tắt context pooling.

**Verification:** stress test cross-tenant isolation và security tests; log correlation không chứa sensitive data nhưng đủ xác nhận tenant boundary.

## 7. Common mistakes

- Nhầm `DbContext` pooling với SQL connection pooling.
- Bật pooling trước khi benchmark cho thấy cần.
- Giữ tenant/user/request state trong context.
- Dùng context từ nhiều threads vì nghĩ pool khiến nó thread-safe.
- Giữ reference tới pooled context ngoài scope.
- Giả định framework reset custom fields tự động.

## 8. Alternatives

- **`AddDbContext` thông thường:** đơn giản và thường đủ nhanh.
- **`IDbContextFactory<T>`:** phù hợp background/concurrent scopes nơi cần explicit context creation.
- **Context pooling:** phù hợp hot path đã đo được context setup/allocation đáng kể và state model đơn giản.

## 9. Trade-offs

### Advantages

- Giảm allocations/context initialization cost.
- Có thể cải thiện throughput ở workload rất nhiều short-lived contexts.

### Costs / Risks

- State leakage risk với custom mutable context state.
- Debugging lifecycle khó hơn.
- Performance gain có thể nhỏ so với SQL/query/network cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbContext` vẫn là unit-of-work và không thread-safe.

### Middle

Biết dùng `AddDbContext`/`AddDbContextPool`, đo performance và tránh giữ state tùy ý.

### Senior

Phân biệt context pool, connection pool và request scope; đánh giá security/correctness risk trong multi-tenant system.

### Technical Lead / Architect

Chỉ bật pooling khi measured benefit đáng complexity; đặt test isolation/security bắt buộc nếu context mang tenant-aware behavior.

## 11. Key takeaway

- `DbContext` pooling là optimization, không phải default requirement.
- Pooled context có thể được reuse vật lý qua requests; custom state phải được thiết kế cực kỳ cẩn thận.
- Correctness và tenant isolation quan trọng hơn benchmark allocation nhỏ.

# 4. SQL Server recursive CTE: traversal hierarchy, cycle risk và khi relational recursion bắt đầu không còn là lựa chọn tốt

## 1. What is it?

Recursive Common Table Expression (CTE) cho phép một query tham chiếu lại chính result của nó để đi qua dữ liệu dạng hierarchy/graph đơn giản.

Mental model:

```text
Anchor rows
   -> recursive step
      -> recursive step
         -> ... until no new rows
```

Use case điển hình: organizational hierarchy, category tree, parent-child comments, folder structure.

## 2. Why does it exist?

Nếu dữ liệu hierarchy nằm trong relational table kiểu adjacency list:

```text
Employee(Id, ManagerId)
```

application có thể query từng level trong loop, nhưng cách đó tạo nhiều round trips và khó tối ưu. Recursive CTE cho database engine thực hiện traversal trong một statement.

## 3. How does it work?

Ví dụ lấy toàn bộ direct/indirect reports:

```sql
WITH Org AS
(
    SELECT Id, ManagerId, Name, 0 AS Depth
    FROM dbo.Employees
    WHERE Id = @ManagerId

    UNION ALL

    SELECT e.Id, e.ManagerId, e.Name, o.Depth + 1
    FROM dbo.Employees e
    INNER JOIN Org o ON e.ManagerId = o.Id
)
SELECT Id, ManagerId, Name, Depth
FROM Org;
```

Phần anchor chạy trước. Recursive member join với result trước đó cho tới khi không còn row mới hoặc đạt recursion limit.

Index trên relationship column như `ManagerId` thường quan trọng vì recursive step repeatedly tìm children.

## 4. Practical implementation

Nếu cần path:

```sql
WITH CategoryTree AS
(
    SELECT
        Id,
        ParentId,
        Name,
        CAST(Name AS nvarchar(max)) AS Path,
        0 AS Depth
    FROM dbo.Categories
    WHERE ParentId IS NULL

    UNION ALL

    SELECT
        c.Id,
        c.ParentId,
        c.Name,
        CAST(t.Path + N' > ' + c.Name AS nvarchar(max)),
        t.Depth + 1
    FROM dbo.Categories c
    JOIN CategoryTree t ON c.ParentId = t.Id
)
SELECT *
FROM CategoryTree
OPTION (MAXRECURSION 100);
```

`MAXRECURSION` là guardrail, không phải substitute cho data integrity.

## 5. Real production scenario

CMS có content hierarchy hàng nghìn nodes. API cần render breadcrumb hoặc invalidate cache toàn subtree sau publish.

Recursive CTE có thể phù hợp nếu tree depth vừa phải và access pattern không quá nhiều lần mỗi request. Nếu cùng traversal chạy hàng nghìn lần/giây, materialized path, closure table hoặc precomputed structure có thể tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom:** query hierarchy chạy rất lâu hoặc lỗi max recursion.

**Evidence:** execution plan cho repeated scans; data có cycle như A -> B -> C -> A; `ManagerId`/`ParentId` thiếu useful index.

**Hypothesis:** data không còn là tree hợp lệ hoặc traversal path quá đắt.

**Diagnosis:** kiểm tra cycle/integrity, row count per level, execution plan, logical reads.

**Fix:** enforce hierarchy rules trong write path, thêm index hợp lý, giới hạn traversal; nếu access pattern đòi đọc subtree liên tục, cân nhắc mô hình khác.

**Verification:** đo logical reads/elapsed time với depth/size thực tế và test malformed hierarchy.

## 7. Common mistakes

- Dùng recursive CTE mà không nghĩ tới cycle.
- Set `MAXRECURSION 0` như “fix” mặc định.
- Query từng node từ C# tạo N+1 database calls.
- Materialize toàn cây khi chỉ cần ancestors hoặc một subtree nhỏ.
- Coi relational adjacency list là lựa chọn tối ưu cho mọi graph workload.

## 8. Alternatives

- **Adjacency list + recursive CTE:** đơn giản cho hierarchy vừa phải.
- **Materialized path:** đọc descendants/path nhanh hơn, write/move node phức tạp hơn.
- **Closure table:** query ancestors/descendants mạnh, storage/write complexity cao hơn.
- **Graph database:** chỉ đáng cân nhắc khi traversal graph là core workload thực sự, không chỉ vì có parent-child table.

## 9. Trade-offs

### Advantages

- Giữ schema relational đơn giản.
- Một query thay nhiều round trips.
- Phù hợp hierarchy thay đổi thường xuyên nhưng depth hợp lý.

### Costs / Risks

- Recursive plans có thể đắt với cây lớn/deep.
- Cycle làm query sai hoặc không kết thúc trong guardrail.
- Path/subtree queries tần suất cao có thể cần mô hình tối ưu hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu anchor + recursive member và parent-child relationship.

### Middle

Viết recursive CTE, đọc plan cơ bản, dùng index và recursion guard.

### Senior

Đánh giá logical I/O, cycle/data integrity và access pattern thay vì chỉ syntax query.

### Technical Lead / Architect

Chọn adjacency list, materialized path, closure table hay specialized store theo read/write profile và operational cost.

## 11. Key takeaway

- Recursive CTE giải quyết traversal relational tốt khi hierarchy vừa phải.
- Cycle và repeated scans là hai failure modes phải thiết kế trước.
- Data model nên theo access pattern, không theo độ “đẹp” của schema.

# 5. Elasticsearch đồng bộ với primary database: eventual consistency, reindex lag và cách tránh biến search index thành source of truth trá hình

## 1. What is it?

Trong kiến trúc phổ biến, SQL/MongoDB giữ transactional source of truth, còn Elasticsearch giữ một search-oriented projection được đồng bộ bất đồng bộ.

```text
Primary DB
   -> change/event/outbox
   -> indexing pipeline
   -> Elasticsearch
   -> Search API
```

Search index được tối ưu cho full-text, filters, relevance và aggregations; nó không nên mặc định trở thành nơi duy nhất lưu business state cần transaction integrity.

## 2. Why does it exist?

Relational database có thể search cơ bản, nhưng relevance, analyzers, tokenization, autocomplete và aggregations phức tạp thường phù hợp hơn với Elasticsearch.

Đổi lại, khi dữ liệu được replicate sang search index, hệ thống chấp nhận một khoảng **eventual consistency**: database đã commit nhưng search chưa nhất thiết thấy thay đổi ngay.

## 3. How does it work?

Một robust flow thường là:

```text
DB transaction
  -> business row + outbox record commit cùng nhau
  -> publisher reads outbox
  -> sends/indexes document
  -> Elasticsearch acknowledges
  -> outbox marked processed
```

Nếu index write fail, business transaction vẫn tồn tại trong DB và publisher retry sau. Đây là lý do direct “SaveChanges rồi gọi Elasticsearch” trong cùng request dễ tạo inconsistency không quan sát được.

Delete cũng phải được model hóa: tombstone/event/version giúp indexer biết document cần xóa thay vì chỉ xử lý upsert.

## 4. Practical implementation

Ví dụ outbox entry trong cùng transaction:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

product.ChangeName(request.Name);

var payload = JsonSerializer.Serialize(new ProductSearchChanged(
    product.Id,
    product.Version));

db.OutboxMessages.Add(new OutboxMessage(
    Guid.NewGuid(),
    "ProductSearchChanged",
    payload,
    DateTimeOffset.UtcNow));

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Indexer consumer đọc product từ source of truth hoặc payload đủ dữ liệu, rồi index với version/idempotency strategy.

## 5. Real production scenario

E-commerce admin đổi product name. Product detail page đọc SQL nên hiển thị tên mới ngay, nhưng search result vẫn thấy tên cũ trong vài giây.

Đó có thể là consistency model chấp nhận được. Nhưng nếu pricing/authorization-critical decision đọc Elasticsearch vì “nhanh hơn”, stale index có thể gây correctness/security issue.

## 6. Failure scenario & troubleshooting

**Symptom:** search trả product cũ hàng giờ sau update.

**Evidence:** DB version mới, outbox backlog tăng, index consumer error rate cao hoặc document version trong Elasticsearch thấp hơn DB.

**Hypothesis:** synchronization pipeline bị lag/fail chứ không phải search query sai.

**Diagnosis:** đo `outbox age`, queue backlog, indexing latency, failed document count, Elasticsearch cluster health.

**Fix:** khôi phục consumer, xử lý poison documents, replay idempotently; nếu schema mapping đổi, có thể reindex qua alias.

**Verification:** compare sample DB/index versions và đảm bảo lag metric trở về SLO.

## 7. Common mistakes

- Gọi Elasticsearch trực tiếp sau DB commit và không có durable retry.
- Dùng search index để quyết định authorization.
- Không có version/idempotency nên event cũ ghi đè event mới.
- Không model delete.
- Reindex full dataset mà không alias/cutover strategy.
- Chỉ monitor Elasticsearch CPU, không monitor data freshness/lag.

## 8. Alternatives

- **SQL full-text/search features:** đủ cho simpler requirements và giảm operational component.
- **Database read model/materialized view:** phù hợp filters/aggregations không cần relevance engine.
- **Managed search service:** giảm cluster operations nhưng consistency pipeline vẫn phải thiết kế.

## 9. Trade-offs

### Advantages

- Search UX và query flexibility mạnh.
- Decouple search workload khỏi transactional database.

### Costs / Risks

- Thêm replication pipeline, lag, retries và reindex complexity.
- Eventual consistency phải được product/business chấp nhận.
- Cluster/index cost và operational burden đáng kể.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Elasticsearch thường là search projection, không phải transactional truth.

### Middle

Implement idempotent indexing, mapping, retries và health metrics cơ bản.

### Senior

Thiết kế outbox/versioning/replay, điều tra lag và phân biệt query bug với synchronization bug.

### Technical Lead / Architect

Quyết định dữ liệu nào được phép stale, SLO freshness bao nhiêu và liệu search engine có thực sự đáng operational cost.

## 11. Key takeaway

- Search index là projection; source of truth phải rõ ràng.
- Eventual consistency cần metrics về lag/freshness, không chỉ cluster health.
- Durable change capture + idempotent indexing quan trọng hơn “retry API call”.

# 6. Bulkhead Pattern: giới hạn concurrency theo dependency để một upstream chậm không chiếm hết thread, connection và request capacity

## 1. What is it?

Bulkhead Pattern cô lập capacity giữa các loại work/dependencies để failure hoặc overload ở một nơi không tiêu thụ toàn bộ tài nguyên của process/system.

Tên gọi đến từ khoang kín trên tàu: một khoang bị ngập không làm cả tàu chìm.

Mental model:

```text
Request capacity
  ├─ Inventory API: max 30 concurrent
  ├─ Reviews API:   max 10 concurrent
  └─ Email API:     max 5 concurrent
```

Bulkhead không làm dependency nhanh hơn. Nó giới hạn blast radius.

## 2. Why does it exist?

Giả sử Reviews API tăng latency từ 100 ms lên 15 giây. Nếu application cho phép unlimited concurrent calls:

- nhiều requests giữ sockets/connections;
- request tasks tích lũy;
- thread/queue pressure tăng;
- memory tăng;
- unrelated endpoints cũng chậm.

Timeout giúp cắt thời gian mỗi call, nhưng nếu arrival rate cao hơn completion rate, vẫn có thể có quá nhiều calls đồng thời. Bulkhead đặt concurrency budget.

## 3. How does it work?

Một semaphore-like gate chỉ cho N operations vào dependency cùng lúc. Operations vượt capacity có thể:

- chờ bounded queue;
- fail fast;
- fallback nếu business cho phép.

```text
incoming -> [bulkhead queue] -> N concurrent slots -> dependency
               full?
                 |
              reject/fallback
```

Bulkhead thường kết hợp với timeout và circuit breaker, nhưng mỗi pattern giải quyết vấn đề khác nhau.

## 4. Practical implementation

Một implementation đơn giản bằng `SemaphoreSlim`:

```csharp
public sealed class ReviewsClient
{
    private readonly HttpClient _http;
    private readonly SemaphoreSlim _gate = new(20, 20);

    public ReviewsClient(HttpClient http) => _http = http;

    public async Task<string> GetAsync(string productId, CancellationToken ct)
    {
        if (!await _gate.WaitAsync(TimeSpan.FromMilliseconds(100), ct))
            throw new ReviewsCapacityExceededException();

        try
        {
            using var timeout = CancellationTokenSource.CreateLinkedTokenSource(ct);
            timeout.CancelAfter(TimeSpan.FromSeconds(2));
            return await _http.GetStringAsync($"/reviews/{productId}", timeout.Token);
        }
        finally
        {
            _gate.Release();
        }
    }
}
```

Production code có thể dùng resilience library/pipeline, nhưng vẫn phải chọn limits dựa trên downstream capacity và SLO.

## 5. Real production scenario

Product page gọi CMS, Product API, Reviews và Recommendations. Reviews provider chậm nhưng reviews không critical.

Không bulkhead: request count tăng, toàn site latency degrade.

Có bulkhead: chỉ 20 review calls chạy đồng thời; request vượt budget có thể render page không có reviews. Core product path tiếp tục hoạt động.

## 6. Failure scenario & troubleshooting

**Symptom:** một third-party API chậm làm unrelated endpoints p99 tăng và process memory/request queue tăng.

**Evidence:** dependency latency spike, concurrent outbound calls tăng, thread/request queue saturation, connection usage cao.

**Hypothesis:** dependency không có concurrency isolation.

**Diagnosis:** correlate traces với active request count, connection pool, bulkhead/rejection metrics.

**Fix:** thêm timeout, per-dependency concurrency limit, bounded waiting và fallback cho optional feature.

**Verification:** chaos/load test dependency latency cao; unrelated endpoints giữ latency trong SLO.

## 7. Common mistakes

- Chỉ thêm retry, khiến chậm thành còn nhiều calls hơn.
- Set một global semaphore cho mọi dependency, tạo coupling giả.
- Queue vô hạn trước bulkhead.
- Limit quá thấp theo cảm tính làm hệ thống tự throttle dù dependency khỏe.
- Fallback trả stale/empty data mà product không chấp nhận.

## 8. Alternatives

- **Timeout:** giới hạn duration, không giới hạn concurrency trực tiếp.
- **Circuit Breaker:** ngừng gọi khi failure threshold đạt, không thay concurrency budget.
- **Rate limiting:** giới hạn arrivals theo thời gian, khác concurrent in-flight limit.
- **Queue-based async processing:** tốt khi work không cần response synchronous.

## 9. Trade-offs

### Advantages

- Giảm blast radius.
- Bảo vệ scarce resources và downstream.
- Làm overload behavior predictable hơn.

### Costs / Risks

- Cần chọn/tune capacity.
- Có thể reject request sớm trong traffic burst dù dependency sắp hồi phục.
- Thêm fallback/metrics/operational policy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu concurrency vô hạn không phải scalability.

### Middle

Implement bounded concurrency, timeout và cancellation đúng cách.

### Senior

Chọn limits dựa trên throughput, latency, connection budget và downstream SLO; phân biệt bulkhead với rate limiter/circuit breaker.

### Technical Lead / Architect

Quyết định dependency nào cần isolation, feature nào degrade được và capacity budget nào bảo vệ toàn hệ thống.

## 11. Key takeaway

- Bulkhead bảo vệ capacity, không chữa dependency chậm.
- Retry mà không có isolation có thể khuếch đại incident.
- Limits phải dựa trên measured capacity và degradation policy.

# 7. Azure Functions Timer Trigger trong hệ thống scale-out: hiểu singleton scheduling, duplicate execution và idempotent job design

## 1. What is it?

Azure Functions Timer Trigger chạy function theo schedule. Với scale-out, nền tảng phối hợp để tránh việc mọi instance đơn giản chạy cùng timer độc lập như một `System.Threading.Timer` trong mỗi process.

Tuy vậy, scheduled execution vẫn không nên được coi là exactly-once business guarantee. Restart, host recovery, retry hoặc execution overlap có thể tạo tình huống cần idempotency.

## 2. Why does it exist?

Một scheduled task đặt trong ASP.NET Core process kiểu:

```text
every instance -> timer -> run job
```

sẽ dễ bị duplicate khi App Service scale từ 1 lên 5 instances. Timer Trigger cung cấp scheduling integration phù hợp cloud host hơn.

Nhưng platform scheduling không thay thế business-level deduplication nếu job side effects quan trọng.

## 3. How does it work?

Conceptual flow:

```text
Schedule
  -> Functions host coordination
  -> invoke function
  -> job reads durable state
  -> performs idempotent batch
  -> records checkpoint/result
```

Timer Trigger có schedule monitor behavior tùy configuration/runtime. Execution có thể bắt đầu muộn nếu host down và có thể overlap nếu run dài hơn interval hoặc architecture cho phép concurrent work downstream.

## 4. Practical implementation

Function nên xử lý bounded batch và có deterministic execution key:

```csharp
public sealed class ExpireInvitations
{
    private readonly AppDbContext _db;

    public ExpireInvitations(AppDbContext db) => _db = db;

    [Function("ExpireInvitations")]
    public async Task Run(
        [TimerTrigger("0 */5 * * * *")] TimerInfo timer,
        CancellationToken ct)
    {
        var now = DateTimeOffset.UtcNow;

        await _db.Invitations
            .Where(x => x.Status == InvitationStatus.Pending && x.ExpiresAt <= now)
            .ExecuteUpdateAsync(
                setters => setters.SetProperty(
                    x => x.Status,
                    InvitationStatus.Expired),
                ct);
    }
}
```

Set-based update mang tính idempotent tốt hơn loop gửi side effect cho từng row. Nếu cần gửi email, nên ghi durable work/outbox và consumer riêng xử lý idempotently.

## 5. Real production scenario

Mỗi 5 phút hệ thống expire pending approvals và gửi notifications. Nếu timer function trực tiếp update + gửi email, retry sau partial failure có thể gửi email trùng.

Thiết kế tốt hơn:

```text
Timer -> mark expired + outbox transaction
Outbox -> Service Bus -> Notification consumer
Consumer -> dedupe/idempotency -> send
```

## 6. Failure scenario & troubleshooting

**Symptom:** sau host restart có notification duplicate hoặc một scheduled batch chạy lâu và batch kế tiếp bắt đầu khi batch trước chưa xong.

**Evidence:** invocation logs overlap; same business IDs processed nhiều lần; side effect không có idempotency key.

**Hypothesis:** team dựa vào scheduler như exactly-once guarantee.

**Diagnosis:** correlate function invocation IDs, business entity IDs, outbox/message delivery và retry logs.

**Fix:** checkpoint/batch, transactional outbox, idempotent consumer; nếu overlap không được phép, dùng durable coordination phù hợp.

**Verification:** simulate restart/retry và xác nhận business outcome vẫn đúng dù function invoked nhiều hơn một lần.

## 7. Common mistakes

- Chuyển code từ `BackgroundService` sang Timer Trigger rồi kết luận duplicate problem biến mất hoàn toàn.
- Chạy batch hàng giờ trong một invocation không checkpoint.
- Gửi email/payment trực tiếp trước khi durable state commit.
- Không propagate `CancellationToken`.
- Không monitor last-success time và job lag.

## 8. Alternatives

- **BackgroundService:** đơn giản khi app một instance hoặc work đã có distributed coordination.
- **Worker Service + Service Bus:** phù hợp continuous queue processing.
- **Logic Apps:** tốt cho workflow integration ít code và connector-heavy.
- **Container Apps Jobs / Kubernetes CronJob:** phù hợp containerized scheduled workloads tùy platform strategy.

## 9. Trade-offs

### Advantages

- Cloud-managed schedule, không gắn vào web request process.
- Scale/operations đơn giản cho nhiều periodic workloads.

### Costs / Risks

- Cold start/host lifecycle ảnh hưởng timing.
- Exactly-once vẫn không phải business guarantee.
- Function runtime, storage coordination và monitoring là dependencies cần hiểu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu schedule trigger khác loop timer trong web app.

### Middle

Viết timer function bounded, cancellable và observable.

### Senior

Thiết kế idempotency, checkpoint, outbox và recovery khi invocation retry/overlap.

### Technical Lead / Architect

Chọn Timer Function, Worker, Service Bus hay container job theo durability, latency, ownership và operational model.

## 11. Key takeaway

- Scheduler tốt không đồng nghĩa business exactly-once.
- Scheduled side effects phải chịu được retry/restart.
- Tách scheduling khỏi durable work processing thường làm hệ thống dễ phục hồi hơn.

# 8. Feature Flags trong CI/CD: tách deployment khỏi release nhưng tránh biến production thành mê cung cấu hình không kiểm soát

## 1. What is it?

Feature Flag cho phép code đã deploy nhưng behavior chỉ bật cho một số users, tenants, environments hoặc tỷ lệ traffic.

```text
Deploy code != Release feature
```

Deployment là đưa artifact vào environment. Release là làm capability đó có hiệu lực với users. Feature flags tách hai thời điểm này.

## 2. Why does it exist?

Nếu mọi feature chỉ có hai trạng thái “chưa deploy” và “đã bật cho 100% users”, rollback phải redeploy binary. Với change lớn, team khó canary hoặc disable nhanh.

Feature flag cho phép:

- ship code sớm nhưng hidden;
- canary theo tenant/user cohort;
- emergency disable behavior;
- migrate backend/frontend theo nhiều bước.

## 3. How does it work?

Một flag evaluation cần context:

```text
flag key + user/tenant/environment + targeting rules -> true/false/config
```

Ví dụ:

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
{
    return await newCheckout.ExecuteAsync(request, ct);
}

return await legacyCheckout.ExecuteAsync(request, ct);
```

Quan trọng: cả hai paths có thể cùng tồn tại trong production. Test surface tăng và data migration phải tương thích với cả hai nếu rollout kéo dài.

## 4. Practical implementation

Không rải string flag tùy ý khắp code. Encapsulate behavior boundary:

```csharp
public sealed class CheckoutRouter
{
    private readonly IFeatureManager _features;
    private readonly NewCheckout _newFlow;
    private readonly LegacyCheckout _legacyFlow;

    public async Task<CheckoutResult> ExecuteAsync(
        CheckoutRequest request,
        CancellationToken ct)
    {
        if (await _features.IsEnabledAsync("CheckoutV2"))
            return await _newFlow.ExecuteAsync(request, ct);

        return await _legacyFlow.ExecuteAsync(request, ct);
    }
}
```

Mỗi flag nên có owner, purpose, created date và expiry/removal plan.

## 5. Real production scenario

Team deploy pricing engine mới. Bật 1% tenant trước, compare error rate/p95/business metric, rồi tăng 10% → 50% → 100%.

Nếu metric xấu, disable flag trong vài phút mà không rollback toàn artifact chứa các fixes khác.

## 6. Failure scenario & troubleshooting

**Symptom:** bug chỉ xảy ra ở một tenant; production code path khác staging dù cùng commit SHA.

**Evidence:** flag targeting rules khác; telemetry không ghi evaluated variant.

**Hypothesis:** runtime configuration/flag state là part of effective release nhưng không được quan sát.

**Diagnosis:** log/trace flag variant ở mức không high-cardinality quá mức, audit flag changes và correlate với incident timeline.

**Fix:** chuẩn hóa flag ownership, audit trail, rollout dashboard và default/failure behavior.

**Verification:** reproduce cùng flag context trong staging/test và kiểm tra disable path hoạt động.

## 7. Common mistakes

- Giữ temporary flags nhiều năm.
- Nested flags tạo combinatorial state explosion.
- Dùng flag cho security authorization thay vì policy deterministic.
- Không test cả ON và OFF path.
- Flag provider outage làm application fail vì không có sensible default/cache.
- Rollout 100% rồi quên xóa legacy code.

## 8. Alternatives

- **Blue-Green:** switch whole environment/version, tốt cho coarse-grained release.
- **Canary deployment:** route traffic sang binary/version khác thay vì branch trong code.
- **Configuration setting:** phù hợp behavior lâu dài, không phải temporary rollout.
- **Simple deploy + rollback:** tốt hơn nếu system nhỏ và change low-risk.

## 9. Trade-offs

### Advantages

- Rollout/rollback behavior nhanh.
- Giảm blast radius.
- Cho phép trunk-based development và incremental release tốt hơn.

### Costs / Risks

- Nhiều runtime states cần test.
- Flag debt làm code khó hiểu.
- External flag service trở thành operational dependency.
- Data/schema compatibility có thể phức tạp khi old/new paths cùng sống.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deployment không nhất thiết đồng nghĩa feature đã bật.

### Middle

Implement flag boundary, test ON/OFF và telemetry variant.

### Senior

Thiết kế rollout metrics, fail-safe default, flag cleanup và backward-compatible data behavior.

### Technical Lead / Architect

Quy định lifecycle/ownership và chọn khi nào feature flag, canary deployment hay rollback đơn giản là đủ.

## 11. Key takeaway

- Feature flag là release-control mechanism, không phải permanent architecture layer.
- Runtime flag state phải observable như code version.
- Flag không được có removal plan sẽ trở thành technical debt rất nhanh.

# 9. JavaScript Event Loop, microtask và rendering: vì sao UI có thể freeze dù mọi I/O đều dùng `async`/`await`

## 1. What is it?

Browser JavaScript thường chạy application code trên main thread. Event Loop phối hợp tasks, microtasks và rendering opportunities.

Mental model đơn giản:

```text
Task (click/timer/script)
  -> run JS stack
  -> drain microtasks (Promise callbacks)
  -> browser may render
  -> next task
```

`async`/`await` giúp không block khi **chờ I/O**, nhưng code CPU-bound sau `await` vẫn chạy trên main thread và có thể freeze UI.

## 2. Why does it exist?

Browser cần phối hợp input events, timers, network callbacks, Promise continuations và rendering. Nếu JavaScript code chạy liên tục quá lâu, browser không có cơ hội paint hoặc xử lý user input.

Đây là lý do “API call async” không đảm bảo page responsive nếu callback parse/transform 100 MB JSON hoặc loop hàng triệu items trên main thread.

## 3. How does it work?

Ví dụ:

```javascript
button.addEventListener('click', async () => {
  const response = await fetch('/api/data');
  const data = await response.json();

  // Đây vẫn chạy trên main thread.
  const result = expensiveTransform(data);

  render(result);
});
```

`fetch` chờ network không block main thread. Nhưng `expensiveTransform` vẫn synchronous CPU work.

Promise continuations vào microtask queue. Một chuỗi microtasks tự tạo liên tục cũng có thể trì hoãn rendering.

## 4. Practical implementation

Chunk CPU-ish UI work để trả quyền điều khiển cho browser hoặc dùng Web Worker khi thật sự nặng:

```typescript
async function processInChunks(items: Item[]) {
  const result: ProcessedItem[] = [];

  for (let i = 0; i < items.length; i += 500) {
    const chunk = items.slice(i, i + 500);
    result.push(...chunk.map(processItem));

    await new Promise<void>(resolve => setTimeout(resolve, 0));
  }

  return result;
}
```

Đây chỉ là technique minh họa. Với CPU-heavy real workload, Web Worker phù hợp hơn vì thật sự chuyển compute khỏi main thread.

## 5. Real production scenario

Admin dashboard fetch 50.000 rows rồi group/sort/filter client-side. Network chỉ 300 ms nhưng page freeze 4 giây sau response. Backend team nhìn API telemetry thấy nhanh nên tưởng frontend “random lag”.

Browser Performance panel cho thấy long task trong JavaScript transform, không phải network bottleneck.

## 6. Failure scenario & troubleshooting

**Symptom:** click không phản hồi, spinner đứng, Core Web Vitals/input responsiveness xấu dù API p95 tốt.

**Evidence:** Chrome DevTools Performance có long task > 50 ms, call stack nằm trong JS transform/render.

**Hypothesis:** CPU/rendering work block main thread.

**Diagnosis:** profile scripting/rendering time, check DOM size, repeated renders, large JSON parsing và microtask chains.

**Fix:** server-side pagination/aggregation, virtualize list, memoize hợp lý, chunk work hoặc Web Worker.

**Verification:** measure interaction latency và main-thread long tasks sau thay đổi.

## 7. Common mistakes

- Nghĩ `async function` tự động chạy trên background thread.
- Fetch toàn bộ dataset rồi paginate ở browser.
- Render hàng nghìn DOM nodes cùng lúc.
- Dùng Promise chain dài để “chia nhỏ” nhưng toàn bộ vẫn nằm trong microtask queue.
- Chỉ optimize backend khi bottleneck nằm ở browser.

## 8. Alternatives

- **Server-side pagination/filter/sort:** thường tốt nhất cho large enterprise data.
- **Virtualized rendering:** chỉ render rows visible.
- **Web Worker:** phù hợp CPU-heavy transformation cần giữ UI responsive.
- **Precompute/backend aggregation:** phù hợp business aggregation lớn.

## 9. Trade-offs

### Advantages

- Hiểu event loop giúp debug UI latency bằng evidence.
- Offload đúng chỗ cải thiện responsiveness đáng kể.

### Costs / Risks

- Worker/message serialization thêm complexity.
- Chunking có overhead và không giảm tổng CPU work.
- Đẩy mọi work về backend có thể tăng server cost/network coupling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` không đồng nghĩa multithreading.

### Middle

Dùng DevTools tìm long tasks, network waterfalls và render bottlenecks.

### Senior

Phân bổ work giữa browser/backend/worker dựa trên dataset size và interaction SLO.

### Technical Lead / Architect

Đặt API shape/pagination và frontend data strategy để tránh chuyển database-sized workload vào browser.

## 11. Key takeaway

- Async I/O không giải quyết CPU-bound main-thread work.
- Browser rendering chỉ có cơ hội chạy khi JavaScript nhường execution.
- Profile browser trước khi đoán backend là nguyên nhân UI chậm.

# 10. Architecture Decision Record (ADR): lưu reasoning và trade-off để quyết định kỹ thuật không bị biến thành “truyền miệng”

## 1. What is it?

Architecture Decision Record là tài liệu ngắn ghi lại một quyết định kỹ thuật đáng kể cùng context, options, trade-offs và consequences.

Một ADR tốt trả lời:

```text
Context -> Decision -> Why -> Alternatives -> Consequences -> Status
```

Nó không phải design document dài và không phải meeting minutes.

## 2. Why does it exist?

Sau vài tháng, team thường còn nhớ “chúng ta dùng Redis” nhưng quên:

- vấn đề ban đầu là gì;
- alternatives nào đã xem xét;
- constraint nào khiến quyết định hợp lý;
- điều kiện nào có thể làm quyết định không còn đúng.

Khi reasoning biến mất, engineer mới có thể “sửa” architecture về phương án đã từng bị loại vì cùng lý do cũ.

## 3. How does it work?

Một ADR có lifecycle:

```text
Proposed -> Accepted -> Superseded / Deprecated
```

ADR thường immutable-ish: khi decision thay đổi, tạo ADR mới và mark ADR cũ `Superseded by ADR-00xx` thay vì rewrite history.

Ví dụ structure:

```markdown
# ADR-0042: Use Azure Service Bus for durable order events

Status: Accepted

## Context
...

## Decision
...

## Alternatives considered
...

## Consequences
...
```

## 4. Practical implementation

Ví dụ rút gọn:

```markdown
# ADR-0017: Keep checkout as a Modular Monolith

Status: Accepted

## Context
Team 6 engineers, one deployment pipeline, cross-module transactions common,
current scale fits one application process.

## Decision
Use module boundaries inside one deployable application.
Do not split checkout into Microservices in Release 1.

## Alternatives
- Microservices now
- Continue unstructured layered monolith

## Consequences
+ simpler operations and transactions
+ module ownership can evolve
- deployment remains coupled
- boundaries require code review enforcement

## Revisit when
Independent scaling/deployment or ownership becomes a measured constraint.
```

“Revisit when” rất có giá trị vì nó biến architecture từ niềm tin vĩnh viễn thành quyết định theo constraints.

## 5. Real production scenario

Team chọn Cosmos DB thay SQL cho một workload. Hai năm sau cost tăng và engineer mới hỏi “tại sao dùng Cosmos?”. Không có ADR nên không ai nhớ requirement ban đầu là global distribution và low-latency multi-region — requirement giờ đã biến mất.

Nếu ADR tồn tại, team có thể đánh giá: constraints ban đầu còn đúng không? Nếu không, migration trở thành engineering decision có evidence thay vì tranh luận cá nhân.

## 6. Failure scenario & troubleshooting

**Symptom:** cùng một architecture debate lặp lại mỗi quý; mỗi team member kể một phiên bản khác về lý do quyết định.

**Evidence:** không có artifact ghi options/constraints; PR chỉ chứa implementation cuối cùng.

**Hypothesis:** decision history bị mất.

**Diagnosis:** tìm các decision có blast radius lớn nhưng chỉ tồn tại trong chat/meeting memory.

**Fix:** tạo ADR cho quyết định mới; không cố retrospective-document mọi thứ nếu value thấp, ưu tiên high-impact/current decisions.

**Verification:** architecture review sau này có thể truy ngược decision, owner, trade-offs và trigger để revisit.

## 7. Common mistakes

- Viết ADR sau khi đã quyết định xong chỉ để hợp thức hóa lựa chọn.
- ADR dài hàng chục trang nên không ai đọc.
- Ghi “chọn X vì X tốt hơn” mà không ghi constraints/trade-offs.
- Rewrite ADR cũ, làm mất history.
- Tạo ADR cho mọi naming convention nhỏ nhặt.
- Không liên kết ADR với code/module/repository nơi decision có hiệu lực.

## 8. Alternatives

- **README/design doc:** tốt cho current architecture overview nhưng thường không giữ decision history tốt bằng ADR.
- **RFC:** phù hợp proposal lớn cần review rộng trước khi quyết định.
- **PR description:** hữu ích cho implementation-level reasoning nhưng khó discover lâu dài.
- **Không document:** chấp nhận được với reversible, low-impact decisions.

## 9. Trade-offs

### Advantages

- Giữ context và rationale lâu dài.
- Hỗ trợ onboarding, review và revisit.
- Giảm tranh luận lặp lại không có evidence.

### Costs / Risks

- Tốn discipline để cập nhật status/linking.
- Quá nhiều ADR nhỏ tạo noise.
- ADR không thay thế prototype, benchmark hoặc production evidence.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết đọc ADR để hiểu “tại sao” trước khi sửa architecture.

### Middle

Viết context/options/consequences rõ cho quyết định module-level.

### Senior

Dùng evidence, constraints và reversibility để đề xuất ADR; biết khi nào không cần ADR.

### Technical Lead / Architect

Thiết lập lightweight decision process, đảm bảo major architectural choices có owner, status và trigger để revisit thay vì biến pattern thành doctrine.

## 11. Key takeaway

- ADR lưu reasoning, không chỉ lưu kết quả.
- Quyết định tốt luôn gắn với constraints và trade-offs tại một thời điểm.
- Architecture có thể thay đổi; history giúp team biết khi nào nên thay đổi và vì sao.
