# 1. .NET `ArrayPool<T>`: tái sử dụng buffer để giảm allocation nhưng phải kiểm soát ownership và dữ liệu nhạy cảm

## 1. What is it?

Mental model:

```text
request A -> Rent buffer -----------+
                                     |
request A <- Return buffer <--------+
                                     |
request B -> Rent same buffer ------+
```

`ArrayPool<T>` là cơ chế cho phép application mượn và trả lại arrays để tái sử dụng thay vì liên tục cấp phát array mới rồi chờ Garbage Collector thu hồi.

Nó đặc biệt hữu ích với temporary buffers trong serialization, parsing, compression, file/network processing hoặc protocol handling.

Điểm quan trọng là pool **không chuyển ownership vĩnh viễn** cho caller. Caller chỉ mượn buffer trong một khoảng lifetime xác định.

## 2. Why does it exist?

Allocation nhỏ, ngắn hạn thường rẻ trong .NET, nhưng allocation với throughput rất cao hoặc buffer lớn có thể tạo GC pressure đáng kể.

Ví dụ một service xử lý 20.000 requests/giây, mỗi request tạo một `byte[64 * 1024]` temporary buffer:

```text
20,000 × 64 KB ≈ 1.28 GB allocation / second
```

Không phải toàn bộ số đó tồn tại cùng lúc, nhưng GC phải xử lý tốc độ allocation rất lớn. Buffer lớn còn có thể đi vào Large Object Heap tùy kích thước.

`ArrayPool<T>` đổi bài toán từ:

```text
allocate -> use -> abandon -> GC
```

thành:

```text
rent -> use -> return -> reuse
```

## 3. How does it work?

Pool duy trì các buckets array theo kích thước. Khi gọi:

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(4096);
```

array trả về có thể **lớn hơn** 4096 bytes. Caller phải dùng logical length riêng thay vì giả định `buffer.Length` chính xác bằng size yêu cầu.

Sau khi dùng xong:

```csharp
ArrayPool<byte>.Shared.Return(buffer);
```

Buffer trở lại pool và có thể được cấp cho code khác.

Pool không đảm bảo array được zero hóa. Dữ liệu cũ có thể còn tồn tại.

## 4. Practical implementation

Ví dụ đọc stream bằng buffer pool:

```csharp
public static async Task<int> ReadChunkAsync(
    Stream stream,
    Memory<byte> destination,
    CancellationToken ct)
{
    byte[] rented = ArrayPool<byte>.Shared.Rent(16 * 1024);

    try
    {
        var read = await stream.ReadAsync(
            rented.AsMemory(0, 16 * 1024), ct);

        rented.AsMemory(0, read).CopyTo(destination);
        return read;
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(rented);
    }
}
```

Nếu buffer chứa secrets, tokens hoặc plaintext nhạy cảm:

```csharp
ArrayPool<byte>.Shared.Return(rented, clearArray: true);
```

Việc clear có CPU cost nên không nên bật vô điều kiện chỉ vì “an toàn hơn”; phải dựa trên data classification.

## 5. Real production scenario

Một image-processing API nhận file, parse metadata và tạo thumbnails. Profiling cho thấy phần lớn allocation đến từ temporary byte buffers giữa decoder, compressor và blob upload.

Team ban đầu cố tối ưu LINQ nhỏ, nhưng GC pause không giảm đáng kể. Sau khi đo allocation profile, họ chuyển hot buffers sang `ArrayPool<byte>` và giới hạn concurrency của image processing.

Kết quả tốt không đến chỉ từ pool; concurrency control cũng quan trọng vì 1.000 requests cùng rent buffer lớn vẫn tạo memory pressure.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu request trước đôi khi xuất hiện trong buffer request sau hoặc application có corruption khó tái hiện.

**Evidence** → code return buffer về pool nhưng vẫn giữ reference và tiếp tục đọc/ghi sau đó.

**Hypothesis** → ownership boundary bị vi phạm.

**Diagnosis** → trace lifetime của rented buffer; kiểm tra async work có giữ `Memory<T>` trỏ vào array sau khi method đã return array hay không.

**Fix** → chỉ return khi toàn bộ consumers hoàn tất; dùng `try/finally`; không expose rented buffer ra API có lifetime dài hơn owner.

**Verification** → stress test concurrent requests và bật assertions/canary data để phát hiện reuse sai lifecycle.

## 7. Common mistakes

- Quên `Return()` khi exception xảy ra.
- Return buffer hai lần.
- Dùng buffer sau khi đã return.
- Giả định rented length đúng bằng requested length.
- Pool mọi allocation dù profiler không cho thấy vấn đề.
- Dùng pooled buffer làm cache/state lâu dài.
- Không clear buffer chứa secrets.

## 8. Alternatives

- Array allocation bình thường: đơn giản và thường đúng cho non-hot path.
- `stackalloc`: tốt cho small, short-lived buffers với kích thước kiểm soát được.
- `MemoryPool<T>`: hữu ích khi cần memory-owner abstraction thay vì raw array.
- Streaming APIs: đôi khi loại bỏ nhu cầu giữ large temporary buffer hoàn toàn.

## 9. Trade-offs

### Advantages

- Giảm allocation rate và GC pressure trong hot path.
- Có thể tái sử dụng large buffers hiệu quả.

### Costs / Risks

- Ownership phức tạp hơn.
- Use-after-return tạo bug concurrency/corruption rất khó debug.
- Sensitive data có thể tồn tại trong pooled memory.
- Pool giữ memory để reuse nên process footprint không nhất thiết giảm ngay.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu pool là cơ chế **mượn/trả**, không phải replacement mặc định cho `new byte[]`.

### Middle

Biết dùng `try/finally`, logical length và không dùng buffer sau `Return()`.

### Senior

Biết profile allocation, đánh giá GC impact, data sensitivity và concurrency trước khi pooling.

### Technical Lead / Architect

Quyết định abstraction nào được phép expose pooled memory, đặt conventions về ownership và xác định hot path nào đáng tăng complexity để giảm allocation.

## 11. Key takeaway

- `ArrayPool<T>` tối ưu allocation bằng reuse, nhưng đổi lại complexity về ownership.
- Chỉ dùng sau khi profiling cho thấy allocation thực sự là bottleneck.
- Buffer chứa dữ liệu nhạy cảm cần explicit clearing policy.

# 2. ASP.NET Core API versioning & backward compatibility: thay đổi contract mà không biến mỗi release thành một breaking event

## 1. What is it?

Mental model:

```text
Client v1 ---> API contract v1
Client v2 ---> API contract v2
                  |
                  v
           shared application/domain
```

API versioning là cách quản lý nhiều contract generations khi clients không thể nâng cấp đồng thời với server.

Backward compatibility rộng hơn versioning: rất nhiều thay đổi có thể được triển khai tương thích mà không cần tạo version mới.

## 2. Why does it exist?

Server có thể deploy trong vài phút nhưng mobile apps, partner integrations, internal services hoặc cached frontend bundles có thể tiếp tục dùng contract cũ hàng tuần hoặc hàng tháng.

Nếu server đổi:

```json
{
  "name": "Product A"
}
```

thành:

```json
{
  "displayName": "Product A"
}
```

mà xóa `name`, client cũ có thể hỏng ngay dù business logic server vẫn đúng.

## 3. How does it work?

Versioning thường được thể hiện qua:

- URL: `/api/v1/orders`
- query parameter: `?api-version=1.0`
- header/media type

Nhưng trước khi version, phải phân loại change:

```text
Add optional response field      -> thường backward-compatible
Add optional request field       -> thường compatible
Remove/rename response field     -> breaking
Change meaning/status semantics  -> có thể breaking dù schema không đổi
Make optional field required     -> breaking
```

Version chỉ là routing mechanism; compatibility policy mới là phần quan trọng.

## 4. Practical implementation

Với ASP.NET Core, versioned endpoints nên map rõ contract:

```csharp
app.MapGet("/api/v1/products/{id:int}", async (
    int id,
    ProductService service,
    CancellationToken ct) =>
{
    var product = await service.GetAsync(id, ct);

    return product is null
        ? Results.NotFound()
        : Results.Ok(new ProductV1Response(
            product.Id,
            product.Name,
            product.Price));
});
```

Version mới:

```csharp
public sealed record ProductV2Response(
    int Id,
    string DisplayName,
    MoneyResponse Price,
    string Currency);
```

Không nên expose EF entity trực tiếp vì persistence changes có thể vô tình trở thành API breaking change.

## 5. Real production scenario

Một e-commerce API được dùng bởi website, mobile app và marketplace partner. Backend muốn đổi `price` từ number sang object có `amount` + `currency`.

Website có thể migrate ngay, nhưng mobile app cũ vẫn tồn tại trong store.

Một migration an toàn có thể là:

1. giữ v1 contract;
2. tạo v2 với richer price model;
3. đo usage theo version;
4. thông báo deprecation;
5. chỉ retire v1 sau khi consumer population giảm dưới threshold được chấp nhận.

## 6. Failure scenario & troubleshooting

**Symptom** → deploy backend thành công nhưng một nhóm clients bắt đầu deserialize failure hoặc business behavior sai.

**Evidence** → error rate chỉ tăng ở user-agent/app version cụ thể; telemetry cho thấy response shape/status semantics đã đổi.

**Hypothesis** → breaking contract change chưa được version/deprecation đúng cách.

**Diagnosis** → compare OpenAPI/contract diff và inspect affected client versions.

**Fix** → restore compatible field/behavior hoặc route client cũ sang old version.

**Verification** → contract tests với active client versions và production telemetry theo API version.

## 7. Common mistakes

- Tạo version mới cho mọi field bổ sung.
- Nghĩ chỉ schema breaking mới là breaking change.
- Expose EF entities trực tiếp.
- Không có deprecation policy.
- Version domain/application layer theo API version một cách máy móc.
- Maintain v1/v2 code copy-paste hoàn toàn riêng biệt.

## 8. Alternatives

- Evolutionary compatibility trong cùng version nếu changes additive.
- Consumer-specific BFF khi clients có contract needs rất khác nhau.
- GraphQL có schema evolution model khác, nhưng vẫn có compatibility/deprecation problems.

## 9. Trade-offs

### Advantages

- Cho clients thời gian migration.
- Giảm coordinated deployment giữa nhiều consumers.
- Làm breaking changes explicit.

### Costs / Risks

- Nhiều versions tăng test surface và maintenance cost.
- Version support quá lâu tạo duplicated code và security burden.
- Versioning không thay thế contract governance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu API là contract với consumer, không chỉ controller output.

### Middle

Biết nhận diện additive vs breaking changes và giữ DTO tách khỏi persistence entity.

### Senior

Thiết kế migration/deprecation, telemetry theo consumer/version và contract tests.

### Technical Lead / Architect

Quyết định compatibility policy, support window và cách tránh version proliferation toàn platform.

## 11. Key takeaway

- API versioning chỉ cần khi compatibility không thể giữ hợp lý.
- Behavioral changes có thể breaking dù JSON schema vẫn hợp lệ.
- Deprecation phải dựa trên consumer telemetry, không chỉ lịch release.

# 3. EF Core N+1 và projection: tối ưu round trip trước khi tối ưu từng câu SQL riêng lẻ

## 1. What is it?

N+1 xảy ra khi application chạy một query để lấy danh sách parent, sau đó thêm một query cho từng parent để lấy related data.

Mental model:

```text
1 query: 100 Orders
+
100 queries: OrderItems cho từng Order
=
101 database round trips
```

Điểm đau thường không phải từng query chậm; tổng số round trips mới là bottleneck.

## 2. Why does it exist?

Object navigation rất tự nhiên trong C#:

```csharp
foreach (var order in orders)
{
    Console.WriteLine(order.Items.Count);
}
```

Nếu lazy loading hoặc manual repository calls kích hoạt query bên trong loop, code nhìn đơn giản nhưng network/database overhead tăng tuyến tính theo số rows.

## 3. How does it work?

Ba khái niệm cần tách:

```text
Include
-> load entities + relationships

Projection
-> chỉ select shape thật sự cần

Separate explicit queries
-> có thể đúng nếu intentional và bounded
```

Với read endpoint, projection thường tốt hơn `Include` khi client chỉ cần subset fields.

## 4. Practical implementation

Không tối ưu:

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .ToListAsync(ct);

foreach (var order in orders)
{
    await db.Entry(order)
        .Collection(x => x.Items)
        .LoadAsync(ct);
}
```

Projection:

```csharp
var result = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummaryDto(
        x.Id,
        x.CreatedAtUtc,
        x.Items.Count,
        x.Items.Sum(i => i.Quantity * i.UnitPrice)))
    .ToListAsync(ct);
```

EF Core có thể translate aggregate thành SQL set-based query.

## 5. Real production scenario

Order history endpoint trả 50 orders. Local database rất nhanh nên N+1 không được nhận ra. Production database nằm qua network boundary và mỗi round trip mất vài milliseconds.

50 queries × 4 ms network/processing overhead đã thêm khoảng 200 ms trước khi xét actual SQL work.

Sau projection, endpoint giảm xuống một hoặc vài predictable queries và p95 giảm rõ rệt.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint latency tăng theo số records trả về.

**Evidence** → trace cho thấy hàng chục/hàng trăm SQL commands giống nhau với parameter khác nhau.

**Hypothesis** → N+1 từ lazy loading, explicit loading hoặc repository loop.

**Diagnosis** → bật EF command telemetry, correlation theo request và đếm DB spans/round trips.

**Fix** → projection, set-based aggregate, `Include` phù hợp hoặc batch query intentional.

**Verification** → integration/load test và assert query count ở critical path nếu team có tooling phù hợp.

## 7. Common mistakes

- Chỉ thêm index cho child query nhưng giữ 500 round trips.
- `Include` mọi navigation rồi tạo Cartesian explosion.
- Materialize bằng `ToList()` quá sớm rồi xử lý LINQ in-memory.
- Generic repository che mất `IQueryable` và ép nhiều calls nhỏ.
- Bật lazy loading toàn hệ thống mà không hiểu query behavior.

## 8. Alternatives

- `Include` khi cần tracked aggregate graph.
- Projection cho read models/API DTOs.
- Raw SQL/Dapper cho hot complex read query khi EF translation không phù hợp.
- CQRS/read model nếu read requirements quá khác write model.

## 9. Trade-offs

### Advantages

- Projection giảm columns, entities và round trips.
- Set-based query tận dụng database optimizer tốt hơn.

### Costs / Risks

- Projection expressions có thể phức tạp.
- Một mega-query không phải lúc nào tốt hơn split queries.
- Read DTO coupling với query shape cần maintain có chủ đích.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Nhìn thấy loop có database call là tín hiệu cảnh báo.

### Middle

Biết dùng projection, `Include`, `AsNoTracking` và xem generated SQL.

### Senior

Tối ưu dựa trên round trips, cardinality, payload và plan thay vì chỉ query duration riêng lẻ.

### Technical Lead / Architect

Quyết định read-model strategy và tránh abstraction che mất database access behavior.

## 11. Key takeaway

- N+1 là vấn đề access pattern trước khi là vấn đề index.
- Đếm round trips trong trace, không chỉ đo từng SQL statement.
- Projection thường là default tốt cho read-only API endpoints.

# 4. SQL covering index với `INCLUDE`: giảm key lookup nhưng không biến index thành bản sao của cả bảng

## 1. What is it?

Một nonclustered index có thể chứa:

```text
key columns
-> dùng để seek/order

included columns
-> không tham gia key order
-> giúp query lấy đủ dữ liệu từ index
```

Ví dụ:

```sql
CREATE INDEX IX_Orders_CustomerId_CreatedAt
ON Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, TotalAmount);
```

Nếu query cần đúng các columns này, SQL Server có thể tránh quay lại clustered index/base table để lấy thêm dữ liệu.

## 2. Why does it exist?

Query có index seek tốt nhưng vẫn có thể thực hiện hàng nghìn `Key Lookup` operations.

Ví dụ:

```sql
SELECT CreatedAt, Status, TotalAmount
FROM Orders
WHERE CustomerId = @customerId
ORDER BY CreatedAt DESC;
```

Index chỉ có `(CustomerId, CreatedAt)` sẽ tìm row nhanh, nhưng để lấy `Status` và `TotalAmount`, engine phải lookup từng matching row.

Khi số rows lớn, lookup cost có thể chiếm phần lớn plan.

## 3. How does it work?

B-tree key order quyết định khả năng seek/sort. `INCLUDE` columns nằm ở leaf level và không làm thay đổi seek semantics như key columns.

Mental model:

```text
Index key:
(CustomerId, CreatedAt)
        |
        v
leaf row also stores:
(Status, TotalAmount)
```

Query có thể được “covered” bởi index.

## 4. Practical implementation

Workflow đúng:

```text
slow query
-> actual execution plan
-> inspect seeks/scans/lookups
-> measure logical reads
-> evaluate candidate index
-> test write/storage impact
```

Không thêm index chỉ vì execution plan hiện “Missing Index”.

Kiểm tra bằng:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

Sau đó so sánh logical reads và duration trước/sau.

## 5. Real production scenario

CRM có endpoint lấy 100 recent interactions theo `AccountId`. Existing index giúp seek theo account nhưng mỗi row cần lookup để lấy `Type`, `OwnerId`, `Summary`.

Ở tenant nhỏ không đáng kể. Tenant lớn có hàng chục nghìn interactions và repeated page requests tạo nhiều random lookups.

Một covering index đúng scope giảm I/O rõ rệt mà không cần cache toàn endpoint.

## 6. Failure scenario & troubleshooting

**Symptom** → query plan dùng index seek nhưng vẫn chậm với large result sets.

**Evidence** → plan cho thấy `Key Lookup` execution count rất lớn; logical reads cao.

**Hypothesis** → access path tìm keys tốt nhưng payload retrieval quá tốn lookup.

**Diagnosis** → inspect operator costs, actual rows và IO statistics.

**Fix** → cân nhắc `INCLUDE` chỉ các columns thực sự cần hoặc redesign query để trả ít dữ liệu hơn.

**Verification** → đo logical reads, CPU, duration và write overhead sau deployment.

## 7. Common mistakes

- INCLUDE mọi columns để “cover everything”.
- Tạo nhiều indexes overlap nhau.
- Bỏ qua write cost và storage.
- Không xem selectivity/key order.
- Tối ưu query trả hàng triệu rows thay vì sửa pagination/access pattern.
- Giữ obsolete indexes sau khi workload thay đổi.

## 8. Alternatives

- Projection trả ít columns hơn.
- Clustered index design khác nếu access pattern cực kỳ dominant.
- Indexed view/materialized strategy cho aggregation workload đặc biệt.
- Read replica/read model cho reporting workload tách biệt.

## 9. Trade-offs

### Advantages

- Giảm key lookup và logical reads.
- Có thể phục vụ query hoàn toàn từ nonclustered index.

### Costs / Risks

- Tăng index size.
- INSERT/UPDATE/DELETE phải maintain thêm index data.
- Quá nhiều covering indexes làm write-heavy system chậm và khó quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không chỉ giúp `WHERE`; nó cũng có thể cung cấp data cho `SELECT`.

### Middle

Biết đọc plan và nhận ra Key Lookup.

### Senior

Đánh giá lookup cost, cardinality, write amplification và overlapping indexes.

### Technical Lead / Architect

Đặt index governance dựa trên production workload thay vì phát triển index riêng cho từng query một cách không kiểm soát.

## 11. Key takeaway

- `INCLUDE` hữu ích khi lookup cost thật sự đáng kể.
- Covering index đổi read speed lấy storage và write cost.
- Luôn đo execution plan + logical reads trước khi thêm index.

# 5. Elasticsearch synchronization từ transactional database: dùng Outbox + replay để search eventual consistency nhưng recoverable

## 1. What is it?

Mental model:

```text
SQL Database = source of truth
        |
        | business transaction
        +--> entity changes
        +--> outbox event
                 |
                 v
             publisher
                 |
                 v
          Elasticsearch index
```

Elasticsearch thường là search/read projection, không phải transactional source of truth. Vì vậy hệ thống cần cơ chế đồng bộ thay đổi từ primary database sang search index.

## 2. Why does it exist?

Naive flow:

```text
1. Save database
2. Index Elasticsearch
```

có failure gap:

- DB save thành công, Elasticsearch fail → search stale.
- Elasticsearch thành công, DB transaction rollback → search chứa dữ liệu chưa tồn tại.

Distributed transaction giữa SQL và Elasticsearch thường không thực tế.

## 3. How does it work?

Outbox Pattern ghi business state và integration event trong **cùng local database transaction**.

Sau commit, publisher đọc outbox và cập nhật Elasticsearch.

Nếu publisher chết:

```text
outbox row vẫn tồn tại
-> restart
-> replay
-> eventual consistency phục hồi
```

Indexer phải idempotent vì event có thể được xử lý nhiều lần.

## 4. Practical implementation

Trong EF Core transaction:

```csharp
product.UpdateName(request.Name);

db.OutboxMessages.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    Type = "ProductChanged",
    AggregateId = product.Id.ToString(),
    OccurredAtUtc = DateTime.UtcNow,
    Payload = JsonSerializer.Serialize(new
    {
        product.Id,
        product.Name,
        product.Price
    })
});

await db.SaveChangesAsync(ct);
```

Indexer dùng deterministic Elasticsearch document ID:

```text
product:{ProductId}
```

để replay cùng state không tạo duplicate documents.

## 5. Real production scenario

Automotive marketplace cho seller sửa giá xe. SQL update hoàn tất ngay, nhưng search result có thể cập nhật sau vài giây.

Business chấp nhận eventual consistency 5–10 giây, nhưng không chấp nhận index mất vĩnh viễn.

Outbox + retry + reconciliation job đáp ứng requirement tốt hơn cố ép synchronous dual-write trong request.

## 6. Failure scenario & troubleshooting

**Symptom** → product tồn tại trong SQL nhưng mất hoặc stale trong search.

**Evidence** → outbox backlog tăng, consumer errors xuất hiện hoặc index document version cũ hơn source.

**Hypothesis** → synchronization pipeline bị lag/fail chứ không phải database corruption.

**Diagnosis** → đo outbox age, queue lag, indexing error rate và sample compare SQL vs Elasticsearch.

**Fix** → repair consumer, replay outbox hoặc chạy controlled reindex/reconciliation.

**Verification** → backlog về bình thường và consistency checks không còn mismatch ngoài tolerated lag window.

## 7. Common mistakes

- Dual-write DB + Elasticsearch trực tiếp trong HTTP request.
- Xóa outbox event trước khi downstream processing hoàn thành an toàn.
- Không idempotent document updates.
- Không có replay/reindex path.
- Coi eventual consistency là “không cần monitor”.
- Dùng Elasticsearch làm transactional source chỉ vì search query tiện.

## 8. Alternatives

- Change Data Capture nếu platform/database hỗ trợ và operational model phù hợp.
- Queue-first/event-sourced systems nếu event log đã là nguồn chính.
- Scheduled batch reindex cho low-change, non-critical datasets.

## 9. Trade-offs

### Advantages

- Không cần distributed ACID transaction.
- Recoverable sau downstream outage.
- Search indexing tách khỏi request latency.

### Costs / Risks

- Eventual consistency trở thành product behavior.
- Cần monitoring backlog/replay/idempotency.
- Schema evolution của events và search documents cần quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SQL và Elasticsearch có thể tạm thời khác nhau.

### Middle

Implement outbox publisher và idempotent indexing.

### Senior

Thiết kế replay, reconciliation, ordering/versioning và monitoring lag.

### Technical Lead / Architect

Quyết định consistency SLA, source of truth, recovery strategy và mức complexity có xứng với search requirements hay không.

## 11. Key takeaway

- Dual-write trực tiếp tạo inconsistency gap khó phục hồi.
- Outbox biến failed synchronization thành backlog có thể replay.
- Eventual consistency chỉ an toàn khi có observability và repair path.

# 6. Retry, Circuit Breaker và Bulkhead: ba resilience patterns giải quyết ba failure mode khác nhau

## 1. What is it?

Ba pattern thường bị gom thành “resilience”, nhưng mục tiêu khác nhau:

```text
Retry
-> thử lại transient failure

Circuit Breaker
-> tạm ngừng gọi dependency đang fail

Bulkhead
-> giới hạn blast radius/capacity consumption
```

Một system có thể cần một, hai hoặc cả ba — nhưng không nên bật tất cả theo template.

## 2. Why does it exist?

Distributed systems có partial failure. Dependency có thể:

- timeout tạm thời;
- trả 503 trong vài giây;
- fail kéo dài;
- chỉ chịu được 50 concurrent calls;
- phục hồi nhưng bị retry storm đánh sập lần nữa.

Một retry policy không giải quyết tất cả các trường hợp trên.

## 3. How does it work?

Retry:

```text
request -> fail transiently -> wait + jitter -> retry
```

Circuit Breaker:

```text
Closed -> failures exceed threshold -> Open
Open -> fail fast
After cooldown -> Half-open probe
Success -> Closed
```

Bulkhead:

```text
1000 incoming requests
        |
        v
concurrency limit = 50
        |
        +--> 50 downstream calls
        +--> excess waits/rejects
```

## 4. Practical implementation

Trong .NET, policy phải gắn với idempotency semantics.

Ví dụ `GET` inventory có thể retry controlled; `POST /payments` không nên retry mù nếu outcome của attempt đầu không rõ.

Pseudo-configuration:

```csharp
var pipeline = new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddRetry(new HttpRetryStrategyOptions
    {
        MaxRetryAttempts = 2,
        Delay = TimeSpan.FromMilliseconds(200),
        UseJitter = true
    })
    .AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
    {
        FailureRatio = 0.5,
        MinimumThroughput = 20,
        BreakDuration = TimeSpan.FromSeconds(30)
    })
    .Build();
```

Bulkhead/concurrency limiter nên phản ánh capacity thực tế của downstream.

## 5. Real production scenario

Checkout API gọi tax provider. Provider bắt đầu timeout 8 giây. Không có protection, mỗi request giữ outbound connection và server resources, backlog tăng.

Team thêm retry 3 lần ngay lập tức và traffic tới provider tăng 4×, làm incident tệ hơn.

Thiết kế tốt hơn:

- strict timeout;
- 1–2 retries với jitter chỉ cho safe failures;
- circuit breaker khi failure kéo dài;
- concurrency limit để bảo vệ cả hai hệ thống;
- fallback/business degradation nếu có thể.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency bắt đầu chậm và outbound request count tăng đột biến thay vì giảm.

**Evidence** → telemetry cho thấy retry attempts chiếm phần lớn traffic; same correlation ID tạo nhiều dependency calls.

**Hypothesis** → retry amplification/retry storm.

**Diagnosis** → phân tích attempt count, timeout hierarchy, breaker state và concurrency.

**Fix** → giảm retry, thêm exponential backoff+jitter, fail fast khi breaker open và giới hạn concurrent calls.

**Verification** → chaos/load test dependency failure và xác nhận system degrade bounded thay vì collapse.

## 7. Common mistakes

- Retry mọi 5xx.
- Retry non-idempotent operation không có idempotency key.
- Timeout 30s rồi retry 3 lần khiến user chờ >90s.
- Circuit breaker threshold quá nhạy gây flapping.
- Bulkhead limit cao hơn capacity thật của downstream.
- Không expose metrics cho retries/breaker/rejections.

## 8. Alternatives

- Queue/asynchronous workflow cho operations không cần synchronous response.
- Cached/stale fallback cho read dependency.
- No retry khi failure không transient hoặc operation không safe.

## 9. Trade-offs

### Advantages

- Retry che transient glitches.
- Circuit breaker ngăn waste khi dependency đang fail kéo dài.
- Bulkhead giới hạn blast radius.

### Costs / Risks

- Policy composition làm behavior khó dự đoán nếu không observability.
- Retry tăng load và tail latency.
- Bulkhead rejection trở thành product behavior cần xử lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry không đồng nghĩa resilience.

### Middle

Biết timeout, backoff, jitter và safe retry conditions.

### Senior

Thiết kế policy theo idempotency, downstream capacity và failure modes.

### Technical Lead / Architect

Quyết định synchronous dependency nào nên tồn tại, failure budget và degradation strategy toàn hệ thống.

## 11. Key takeaway

- Retry, Circuit Breaker và Bulkhead giải quyết các vấn đề khác nhau.
- Retry không kiểm soát có thể khuếch đại outage.
- Resilience policy phải đi cùng timeout, idempotency và telemetry.

# 7. Azure Service Bus Sessions: giữ ordering theo business key mà không đánh đổi toàn bộ queue thành single-threaded system

## 1. What is it?

Service Bus Sessions cho phép group messages bằng `SessionId`. Messages trong cùng session được xử lý theo ordered stream bởi một session receiver tại một thời điểm.

Mental model:

```text
Order-100 session:
Created -> Paid -> Shipped

Order-200 session:
Created -> Cancelled

Hai sessions có thể xử lý song song,
nhưng mỗi session giữ ordering riêng.
```

## 2. Why does it exist?

Queue bình thường tối ưu throughput qua competing consumers. Nhưng distributed processing có thể làm messages liên quan cùng aggregate hoàn thành không đúng thứ tự.

Ví dụ:

```text
OrderPaid
OrderCancelled
```

nếu xử lý song song mà domain yêu cầu ordering, final state có thể sai.

Global ordering cho toàn queue sẽ giết throughput không cần thiết. Session tạo ordering theo partition/business key.

## 3. How does it work?

Producer gán:

```text
SessionId = OrderId
```

Consumer accept một session và xử lý messages sequentially trong session đó.

Service vẫn có thể process nhiều sessions concurrently:

```text
Session A -> worker 1
Session B -> worker 2
Session C -> worker 3
```

Session lock, message lock và retry semantics vẫn phải được quản lý.

## 4. Practical implementation

Producer:

```csharp
var message = new ServiceBusMessage(payload)
{
    MessageId = eventId.ToString(),
    SessionId = orderId.ToString()
};

await sender.SendMessageAsync(message, ct);
```

Consumer vẫn cần idempotency:

```text
(SessionId ordering) != exactly-once delivery
```

Một message có thể được redeliver sau crash trước settlement.

## 5. Real production scenario

Fulfillment system nhận lifecycle events cho mỗi shipment. Các shipment khác nhau không liên quan nên cần throughput cao, nhưng events của cùng shipment phải được xử lý đúng order.

Dùng `ShipmentId` làm `SessionId` cho phép hàng nghìn shipments xử lý song song trong khi mỗi shipment giữ sequential semantics.

## 6. Failure scenario & troubleshooting

**Symptom** → backlog toàn queue tăng dù tổng worker CPU thấp.

**Evidence** → một số sessions chứa rất nhiều messages hoặc session handler processing lâu; hot session trở thành bottleneck.

**Hypothesis** → `SessionId` cardinality hoặc workload phân bố không tốt.

**Diagnosis** → đo backlog/processing time theo session key nếu telemetry cho phép; inspect business key distribution.

**Fix** → chọn session boundary nhỏ hơn nếu domain cho phép, tối ưu per-message work hoặc tách long-running work khỏi ordered critical section.

**Verification** → load test skewed session distribution và kiểm tra throughput toàn queue.

## 7. Common mistakes

- Nghĩ Sessions cung cấp exactly-once.
- Dùng một `SessionId` cho toàn queue để “đảm bảo order”.
- Gắn session theo tenant lớn khiến hot tenant serial hóa toàn bộ work.
- Không xử lý session lock expiration.
- Giữ session open trong long external calls không cần thiết.

## 8. Alternatives

- Sequence number + application-side reorder nếu requirements đặc biệt.
- Partitioned event stream như Kafka/Event Hubs cho high-throughput ordered partitions.
- Không dùng ordering nếu business operation đã idempotent/commutative và thứ tự không quan trọng.

## 9. Trade-offs

### Advantages

- Ordering theo business key.
- Vẫn có concurrency giữa independent sessions.

### Costs / Risks

- Hot sessions giới hạn throughput.
- Session state/lifecycle tăng operational complexity.
- Idempotency và duplicate handling vẫn bắt buộc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ordering thường cần theo aggregate, không phải toàn hệ thống.

### Middle

Biết set `SessionId`, xử lý session receiver và settlement.

### Senior

Thiết kế session cardinality, hot-key behavior và idempotent consumer.

### Technical Lead / Architect

Quyết định ordering có thực sự là business invariant hay chỉ là implementation convenience, và chọn messaging technology phù hợp.

## 11. Key takeaway

- Sessions tạo ordering theo key, không phải exactly-once processing.
- Session key sai có thể biến scalable queue thành serial bottleneck.
- Ordering requirements phải xuất phát từ domain invariant.

# 8. Azure App Service Health Check + autoscale: instance “đang chạy” chưa chắc đủ khỏe để nhận traffic

## 1. What is it?

Health Check là endpoint giúp platform đánh giá application instance có đủ khỏe để nhận traffic hay không.

Mental model:

```text
Load Balancer
   |
   +--> Instance A /health = healthy
   +--> Instance B /health = unhealthy
   +--> Instance C /health = healthy

traffic -> A, C
```

Process tồn tại hoặc port mở chưa đủ chứng minh application hoạt động đúng.

## 2. Why does it exist?

Một instance có thể:

- process vẫn chạy;
- HTTP server vẫn accept connection;
- nhưng thread pool bị nghẽn;
- critical configuration lỗi;
- startup migration chưa xong;
- memory pressure nghiêm trọng;
- dependency bắt buộc không usable.

Nếu platform vẫn route traffic tới instance đó, user thấy intermittent 5xx/timeout.

## 3. How does it work?

Health endpoint nên phản ánh “có nên nhận traffic không”, không phải dump toàn bộ diagnostics.

Trong ASP.NET Core:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<StartupStateHealthCheck>("startup");

app.MapHealthChecks("/health");
```

Không nên biến health check thành dependency fan-out kiểm tra 15 services mỗi vài giây nếu một dependency optional bị down không có nghĩa instance phải bị remove.

## 4. Practical implementation

Tách mental model:

```text
Liveness: process có bị dead/hung không?
Readiness/traffic health: instance có thể phục vụ request không?
Dependency health: downstream nào đang degraded?
```

App Service health endpoint nên nhanh, deterministic và không yêu cầu authentication phức tạp từ platform probe.

Autoscale metrics cũng cần nhìn ngoài CPU. Một I/O-bound app có thể bị connection pool exhaustion với CPU chỉ 20%.

## 5. Real production scenario

Deploy mới lên 6 App Service instances. Hai instances fail warm-up vì configuration lookup timeout nhưng process vẫn start.

Nếu health check chỉ trả 200 khi process alive, 1/3 traffic nhận 500 ngẫu nhiên. Nếu endpoint phản ánh startup readiness, unhealthy instances bị loại khỏi traffic cho đến khi phục hồi.

## 6. Failure scenario & troubleshooting

**Symptom** → error rate khoảng 15–30%, nhưng restart một số instances làm lỗi giảm.

**Evidence** → Application Insights dimensions cho thấy failures tập trung ở vài instance IDs.

**Hypothesis** → instance-specific degradation nhưng load balancer vẫn route traffic.

**Diagnosis** → compare health endpoint, startup logs, memory, connections và dependency telemetry theo instance.

**Fix** → health semantics đúng, remove unhealthy instances, sửa root cause và cấu hình autoscale/capacity hợp lý.

**Verification** → simulate broken instance và xác nhận traffic bị drain khỏi instance đó.

## 7. Common mistakes

- `/health` luôn trả 200 chỉ vì app process đang sống.
- Health check query database rất nặng mỗi vài giây.
- Mark app unhealthy khi optional dependency fail.
- Autoscale chỉ theo CPU.
- Health endpoint expose sensitive diagnostics ra public internet.
- Dùng health check thay cho observability.

## 8. Alternatives

- Kubernetes readiness/liveness probes trong container orchestration.
- External synthetic monitoring để kiểm tra end-to-end user path.
- Azure Front Door/Application Gateway health probes ở edge/ingress layer.

## 9. Trade-offs

### Advantages

- Loại unhealthy instances khỏi traffic.
- Hỗ trợ safer deployment và scaling.
- Giảm intermittent failures do bad instance.

### Costs / Risks

- Health criteria quá strict có thể remove tất cả instances cùng lúc.
- Dependency checks không cẩn thận có thể tạo cascading failure.
- Probe endpoint cần security/network design phù hợp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process running khác application healthy.

### Middle

Implement lightweight health endpoint và phân biệt critical/optional dependencies.

### Senior

Dùng per-instance telemetry, scale signals và failure drills để validate health semantics.

### Technical Lead / Architect

Định nghĩa readiness policy, autoscale signals và cách tránh health checks trở thành nguồn cascading outage.

## 11. Key takeaway

- “Alive” không đồng nghĩa “ready for traffic”.
- Health check phải phản ánh serving capability, không phải checklist mọi dependency.
- Autoscale cần chọn metric gắn với saturation thật của workload.

# 9. Git bisect trong production regression: tìm commit gây lỗi bằng binary search thay vì đọc hàng trăm commits thủ công

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên gây regression.

Mental model:

```text
Good ------------------------------ Bad
                    ^
                  test mid
             good / bad ?
                    |
          loại bỏ nửa history
```

Thay vì kiểm tra 128 commits tuần tự, binary search lý tưởng cần khoảng 7 lần test.

## 2. Why does it exist?

Production regression thường xuất hiện sau một khoảng commit/release, nhưng không phải commit cuối cùng chắc chắn gây lỗi.

Manual review dễ bị bias:

- nghi commit lớn;
- bỏ qua config change nhỏ;
- đọc diff nhưng không reproduce runtime behavior.

`bisect` biến điều tra thành experiment có phương pháp.

## 3. How does it work?

Bắt đầu:

```bash
git bisect start
git bisect bad <bad-commit>
git bisect good <known-good-commit>
```

Git checkout một midpoint. Bạn test rồi đánh dấu:

```bash
git bisect good
```

hoặc:

```bash
git bisect bad
```

Lặp đến khi Git chỉ ra first bad commit.

## 4. Practical implementation

Tốt nhất tự động hóa test:

```bash
git bisect start <bad> <good>
git bisect run ./scripts/repro-regression.sh
```

Script trả:

```text
0   -> good
1-127 (trừ special codes) -> bad
125 -> skip
```

Một integration/performance regression reproducible có thể được bisect hoàn toàn tự động.

## 5. Real production scenario

API p95 tăng từ 300 ms lên 1.8 s trong release chứa 90 commits. Team nghi database migration nhưng không chắc.

Họ viết script chạy endpoint benchmark với local fixture và threshold. `git bisect run` chỉ ra commit thay `IQueryable` projection thành `ToListAsync()` trước filter, khiến phần lớn data được materialize sớm.

Điều tra chuyển từ “đọc diff và đoán” thành reproducible proof.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect cho kết quả không ổn định hoặc chỉ ra commit vô lý.

**Evidence** → cùng commit lúc test pass, lúc fail.

**Hypothesis** → reproduction nondeterministic, environment/state leakage hoặc performance threshold quá nhiễu.

**Diagnosis** → chạy repeated trials, reset database/cache và pin dependencies/config.

**Fix** → làm reproduction deterministic trước khi tiếp tục bisect; dùng `git bisect skip` cho unbuildable commits.

**Verification** → checkout parent và bad commit để xác nhận behavior thay đổi đúng boundary.

## 7. Common mistakes

- Bisect khi chưa có reliable reproduction.
- Dùng “build pass” như proxy cho behavior bug không liên quan.
- Không reset external state giữa runs.
- Kết luận first bad commit là toàn bộ root cause mà không hiểu mechanism.
- Quên `git bisect reset` sau khi xong.

## 8. Alternatives

- `git log`/`git blame` khi phạm vi thay đổi rất nhỏ và deterministic.
- Feature flags để isolate behavior.
- Deployment comparison/observability nếu regression đến từ configuration/infrastructure chứ không phải code.

## 9. Trade-offs

### Advantages

- Giảm số commits cần kiểm tra theo logarithmic search.
- Tạo evidence rõ ràng cho regression boundary.
- Tự động hóa được.

### Costs / Risks

- Cần test/repro deterministic.
- Historical commits có thể không build vì dependency/environment drift.
- Không giúp nếu failure do external data/config không nằm trong Git history.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết Git history có thể được dùng để điều tra bug, không chỉ lưu code.

### Middle

Biết chạy `git bisect` thủ công và xác định known-good/known-bad commits.

### Senior

Tự động hóa reproduction, kiểm soát environment và phân biệt code regression với external-change regression.

### Technical Lead / Architect

Đảm bảo system có reproducible tests/artifacts đủ tốt để incident investigation dùng evidence thay vì intuition.

## 11. Key takeaway

- `git bisect` hiệu quả khi có một test phân loại commit thành good/bad đáng tin cậy.
- Deterministic reproduction quan trọng hơn bản thân câu lệnh Git.
- Sau khi tìm commit, vẫn phải phân tích mechanism/root cause trước khi fix.

# 10. RAG evaluation cho AI systems: retrieval tốt phải được đo riêng khỏi generation tốt

## 1. What is it?

RAG thường gồm ít nhất hai subsystems:

```text
User query
   |
   v
Retrieval
   |
relevant chunks?
   |
   v
LLM generation
   |
answer grounded?
```

Nếu answer sai, cần biết lỗi nằm ở retrieval hay generation. Một metric tổng “answer quality” không đủ để debug architecture.

## 2. Why does it exist?

Một RAG system có thể fail theo nhiều kiểu:

- document đúng không được retrieve;
- retrieve đúng nhưng rank thấp và bị cắt khỏi context;
- chunk thiếu surrounding context;
- model có evidence đúng nhưng hallucinate;
- answer đúng nhưng citation sai;
- retrieval quá rộng làm context nhiễu.

Nếu chỉ nhìn output cuối, team dễ đổi prompt trong khi root cause là index/chunking/retrieval.

## 3. How does it work?

Evaluation nên tách layers:

```text
Retrieval metrics
- Recall@K
- Precision@K
- MRR / ranking quality khi phù hợp

Generation metrics
- factual correctness
- groundedness
- completeness
- citation correctness

System metrics
- latency
- token usage
- cost
- failure rate
```

Golden dataset cần gồm user questions và expected supporting sources/evidence, không chỉ expected prose answer.

## 4. Practical implementation

Ví dụ evaluation record:

```json
{
  "question": "Chính sách hoàn tiền áp dụng trong bao nhiêu ngày?",
  "expectedDocumentIds": ["refund-policy-v3"],
  "requiredFacts": [
    "30 days",
    "original payment method"
  ]
}
```

Pipeline test:

```text
1. Run retriever only
2. Assert expected document/chunk appears in top K
3. Run generator with captured context
4. Evaluate grounded answer against required facts
5. Record latency/tokens/cost
```

Security/authorization filtering phải deterministic trước hoặc trong retrieval boundary; không để model tự quyết định user có quyền thấy document nào.

## 5. Real production scenario

Internal knowledge assistant trả lời sai HR policy. Team đổi system prompt nhiều lần nhưng accuracy gần như không đổi.

Evaluation tách layer cho thấy đúng policy document chỉ xuất hiện top-20, trong khi application chỉ gửi top-5 vào model. Root cause là ranking và metadata filter, không phải prompt.

Sau khi sửa retrieval, grounded answer rate tăng mà không đổi model.

## 6. Failure scenario & troubleshooting

**Symptom** → model trả câu trả lời tự tin nhưng thiếu fact chính dù document tồn tại trong corpus.

**Evidence** → retrieval logs cho thấy expected source không vào context.

**Hypothesis** → chunking, embedding, metadata filtering hoặc ranking failure.

**Diagnosis** → inspect Recall@K theo query category; test lexical vs vector/hybrid retrieval; kiểm tra access filters.

**Fix** → cải thiện chunk boundaries, metadata, hybrid search/reranking hoặc query transformation tùy evidence.

**Verification** → rerun fixed evaluation set và kiểm tra regression trên categories khác.

## 7. Common mistakes

- Chỉ benchmark final answer và không lưu retrieved context.
- Dùng LLM-as-judge duy nhất mà không có deterministic required facts.
- Thay model lớn hơn để che retrieval yếu.
- Không version corpus/index/prompt/model trong evaluation result.
- Dùng production user documents trong eval mà không kiểm soát privacy.
- Để model quyết định authorization dựa trên prompt instruction.

## 8. Alternatives

- Fine-tuning khi kiến thức cần encode vào behavior/model và không cần frequently changing external facts.
- Search-only UX khi user cần source discovery hơn synthesized answer.
- Deterministic database/API lookup cho structured, correctness-critical facts.

## 9. Trade-offs

### Advantages

- Layered evaluation giúp localize regressions nhanh.
- Cho phép optimize model/retriever độc lập.
- Giúp kiểm soát cost/latency cùng quality.

### Costs / Risks

- Golden datasets tốn công maintain.
- Human judgment vẫn cần cho nuanced questions.
- Metrics có thể bị game nếu không phản ánh production query distribution.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG gồm retrieval + generation, không chỉ “đưa docs cho LLM”.

### Middle

Biết log context, build small golden dataset và đo Recall@K/basic groundedness.

### Senior

Phân tích failure theo retrieval/ranking/chunking/generation, đồng thời đo latency/token/cost.

### Technical Lead / Architect

Quyết định phần nào dùng probabilistic AI, phần nào phải deterministic; đặt evaluation gates, security boundaries và acceptable quality/cost thresholds.

## 11. Key takeaway

- Không thể cải thiện RAG hiệu quả nếu retrieval và generation bị đo chung thành một điểm số.
- Golden set nên chứa expected evidence, không chỉ expected answer.
- Authorization và correctness-critical logic phải giữ deterministic ngoài quyền tự quyết của model.
