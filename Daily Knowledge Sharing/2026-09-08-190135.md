# 1. C# `async` / `await` state machine và sync-over-async: vì sao `.Result` có thể biến latency thành ThreadPool starvation

## 1. What is it?

`async` / `await` là cú pháp compiler biến một method bất đồng bộ thành một state machine. Khi gặp một `await` chưa hoàn thành, method không “giữ thread để chờ”; nó lưu state cần thiết, đăng ký continuation và trả quyền sử dụng thread về runtime.

Mental model:

```text
Request thread
   ↓
call async method
   ↓
I/O not completed
   ↓
save state + register continuation
   ↓
return thread to ThreadPool
   ↓
I/O completes
   ↓
continuation scheduled
```

Ngược lại, `.Result`, `.Wait()` hoặc `GetAwaiter().GetResult()` trên một operation chưa hoàn thành sẽ block thread hiện tại. Trong ASP.NET Core, lỗi lớn không thường là classic UI deadlock mà là ThreadPool starvation: nhiều request block, continuation không có đủ thread để chạy, latency tăng theo cấp số nhân.

## 2. Why does it exist?

Server phải xử lý nhiều I/O-bound operations như SQL, HTTP, Redis, Blob Storage. Nếu mỗi request giữ một OS thread trong toàn bộ thời gian chờ network, scalability sẽ nhanh chóng bị giới hạn bởi số thread và context switching.

`async` tồn tại để tách **concurrency** khỏi số lượng thread đang blocked. Một request vẫn “đang chờ”, nhưng thread có thể phục vụ request khác.

## 3. How does it work?

Compiler sinh một struct/class state machine chứa local variables cần sống qua `await`, state integer và builder như `AsyncTaskMethodBuilder`.

Flow đơn giản:

```text
State 0: before await
   ↓ incomplete awaitable
store locals + state = 1
   ↓ return Task
I/O completes
   ↓ MoveNext()
State 1: resume after await
```

Continuation trong ASP.NET Core thường không cần quay lại một request-specific `SynchronizationContext`, nhưng vẫn cần ThreadPool worker để tiếp tục CPU work. Vì vậy sync-over-async vẫn nguy hiểm dưới load.

## 4. Practical implementation

Bad:

```csharp
public OrderDto GetOrder(Guid id)
{
    // Blocks current ThreadPool worker.
    return _client.GetOrderAsync(id).Result;
}
```

Better:

```csharp
public async Task<OrderDto> GetOrderAsync(
    Guid id,
    CancellationToken cancellationToken)
{
    return await _client.GetOrderAsync(id, cancellationToken);
}
```

Nếu cần chạy nhiều I/O độc lập:

```csharp
var customerTask = _customerClient.GetAsync(customerId, cancellationToken);
var pricingTask = _pricingClient.GetAsync(productId, cancellationToken);

await Task.WhenAll(customerTask, pricingTask);

var customer = await customerTask;
var pricing = await pricingTask;
```

Điều này tạo concurrency giữa hai remote calls mà không cần `Task.Run`.

## 5. Real production scenario

Một checkout API gọi payment profile, inventory và promotion service. Developer thêm `.Result` trong adapter legacy để “tránh đổi signature”. Local test vẫn chạy tốt.

Khi traffic tăng, request threads block trên remote calls. ThreadPool phải inject thêm thread từ từ, queue length tăng, p99 latency từ 800 ms lên 15 giây dù CPU chỉ 30–40%.

## 6. Failure scenario & troubleshooting

**Symptom** → request timeout tăng mạnh, CPU không bão hòa, dependency latency chỉ tăng nhẹ.

**Evidence** → .NET runtime metrics cho thấy ThreadPool queue length tăng, thread count tăng dần, traces có khoảng trống dài trước continuation.

**Hypothesis** → blocking trong async request path.

**Diagnosis** → tìm `.Result`, `.Wait()`, blocking lock quanh I/O, synchronous database/network APIs.

**Fix** → async all the way; loại bỏ `Task.Run` bao quanh I/O; propagate cancellation.

**Verification** → load test cùng traffic; queue length ổn định và p95/p99 giảm.

## 7. Common mistakes

* Dùng `Task.Run` cho EF Core/HTTP I/O để “biến thành async”.
* Gọi `.Result` vì “ASP.NET Core không có SynchronizationContext nên an toàn”. Không deadlock không có nghĩa là scalable.
* Tạo fire-and-forget task trong request mà không có ownership/lifetime.
* Sequential `await` cho các I/O hoàn toàn độc lập.
* Parallel hóa vô hạn mà không có concurrency limit.

## 8. Alternatives

Nếu code legacy bắt buộc synchronous, có thể giữ synchronous boundary riêng và cô lập workload thay vì trộn sync/async tùy tiện. Với CPU-bound work, `Task.Run` hoặc dedicated background processing có thể phù hợp, nhưng đó là bài toán khác I/O-bound async.

## 9. Trade-offs

### Advantages

* Sử dụng thread hiệu quả hơn cho I/O.
* Tăng concurrency của server.
* Cancellation và timeout dễ propagate hơn.

### Costs / Risks

* Async signature lan qua call chain.
* Debug stack và exception flow phức tạp hơn với người chưa quen.
* Concurrency dễ bị lạm dụng, tạo overload ở downstream dependency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` không đồng nghĩa “tạo thread mới”; nó thường giải phóng thread trong lúc chờ I/O.

### Middle

Biết async all the way, tránh `.Result`, dùng `Task.WhenAll` có chủ đích và propagate `CancellationToken`.

### Senior

Nhận diện ThreadPool starvation bằng telemetry, phân biệt CPU-bound và I/O-bound, kiểm soát concurrency với capacity downstream.

### Technical Lead / Architect

Định nghĩa async boundary, migration strategy cho synchronous legacy code và capacity model để concurrency không biến thành overload.

## 11. Key takeaway

* `async` chủ yếu giúp không giữ thread trong lúc chờ I/O.
* Sync-over-async có thể gây starvation dù không deadlock.
* “Async all the way” phải đi cùng concurrency control và observability.

# 2. ASP.NET Core Output Caching: cache cả HTTP response nhưng phải kiểm soát identity, vary key và invalidation

## 1. What is it?

Output Caching lưu kết quả HTTP response đã render của endpoint và trả lại response đó cho request tương lai phù hợp policy. Nó khác `IMemoryCache` ở chỗ cache nằm ở HTTP output boundary thay vì application object boundary.

Mental model:

```text
Request
  ↓
Output Cache policy lookup
  ├─ hit  → cached HTTP response
  └─ miss → endpoint → DB/services → response → cache
```

## 2. Why does it exist?

Nhiều endpoint read-heavy trả cùng payload cho nhiều request: product catalog, public CMS content, lookup data. Nếu mỗi request đều chạy controller, service, EF Core và serialization, hệ thống lặp lại work không cần thiết.

Output Caching cho phép bỏ qua gần như toàn bộ downstream work khi cache hit.

## 3. How does it work?

Policy quyết định request nào được cache và cache key gồm những dimension nào: route, query string, header hoặc custom vary values.

Một key sai có thể tạo correctness/security bug. Ví dụ response phụ thuộc tenant hoặc language nhưng cache key không vary theo tenant/language sẽ trả nhầm dữ liệu.

Request có `Authorization` thường phải được cân nhắc đặc biệt; public cache policy không nên vô tình cache personalized response.

## 4. Practical implementation

```csharp
builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("ProductCatalog", policy =>
        policy
            .Expire(TimeSpan.FromSeconds(30))
            .SetVaryByQuery("category", "page"));
});

app.UseOutputCache();

app.MapGet("/api/products", async (
    string? category,
    int page,
    ProductService service,
    CancellationToken cancellationToken) =>
{
    return await service.GetPageAsync(category, page, cancellationToken);
})
.CacheOutput("ProductCatalog");
```

Nếu response phụ thuộc locale:

```csharp
policy.SetVaryByHeader("Accept-Language");
```

Trong production, invalidation theo tag có thể tốt hơn chỉ chờ TTL nếu dữ liệu phải phản ánh publish/update nhanh.

## 5. Real production scenario

Một Optimizely-backed marketing site có public API trả navigation tree. Mỗi page load gọi endpoint này, trong khi navigation chỉ đổi vài lần mỗi ngày.

Output Cache 60 giây làm giảm hàng nghìn CMS reads và serialization operations, nhưng cache key phải vary theo site/language.

## 6. Failure scenario & troubleshooting

**Symptom** → user ở tenant A đôi lúc thấy navigation của tenant B.

**Evidence** → origin trace không chạy vì request cache hit; cache key chỉ gồm route và query.

**Hypothesis** → tenant dimension không nằm trong vary key.

**Diagnosis** → log/cache debug policy, so sánh request headers/host và generated key dimensions.

**Fix** → vary theo host/tenant identifier hoặc không cache personalized endpoint ở output layer.

**Verification** → integration test nhiều tenant/language và kiểm tra cache isolation.

## 7. Common mistakes

* Cache response có dữ liệu user-specific mà không vary theo identity/tenant.
* Vary theo quá nhiều header làm cache hit ratio gần 0.
* Dùng TTL dài để “tăng performance” nhưng không có invalidation ownership.
* Cache error response hoặc transient failure không chủ đích.
* Dùng Output Cache khi business logic đã có distributed cache với semantics khác, tạo hai lớp stale state khó debug.

## 8. Alternatives

* `IMemoryCache`: object-level, per-instance.
* Redis: distributed object/data cache.
* CDN: edge cache gần client, phù hợp public HTTP content.
* No cache: đúng lựa chọn khi freshness/correctness quan trọng hơn cost.

## 9. Trade-offs

### Advantages

* Bỏ qua phần lớn request pipeline downstream.
* Giảm DB/CMS/API load.
* Cải thiện latency cho read-heavy endpoint.

### Costs / Risks

* Staleness.
* Cache-key correctness trở thành business/security concern.
* Invalidation và observability phức tạp hơn.
* Nhiều cache layer dễ tạo hidden behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache hit trả lại HTTP response cũ thay vì chạy endpoint lại.

### Middle

Biết cấu hình TTL và vary policy theo query/header.

### Senior

Đánh giá identity isolation, invalidation, cache hit ratio và interaction với Redis/CDN.

### Technical Lead / Architect

Quyết định cache layer nào sở hữu freshness, tránh redundant caching và đặt security boundary rõ ràng.

## 11. Key takeaway

* Output Cache tối ưu ở HTTP boundary, không chỉ ở data layer.
* Cache key sai có thể là data leak, không chỉ performance bug.
* Luôn xác định ai sở hữu invalidation và mức stale chấp nhận được.

# 3. EF Core transaction savepoints và execution strategy: retry chỉ an toàn khi hiểu transaction boundary

## 1. What is it?

Savepoint là mốc bên trong một database transaction cho phép rollback một phần transaction về mốc đó thay vì rollback toàn bộ. EF Core có thể sử dụng savepoint quanh `SaveChanges` khi đã có transaction hiện hữu.

Execution Strategy là cơ chế retry transient database failures. Hai khái niệm giao nhau ở một điểm quan trọng: retry một operation bên trong transaction không đơn giản như retry một câu SQL độc lập.

## 2. Why does it exist?

Một business operation có thể thực hiện nhiều mutation liên quan. Khi bước thứ hai fail, đôi khi ta muốn giữ transaction mở và quay lại state trước `SaveChanges` thay vì vứt toàn bộ transaction.

Mặt khác, cloud database có transient failures. Retry tự động hữu ích, nhưng nếu application tự mở transaction thủ công mà execution strategy không kiểm soát toàn bộ unit of work, retry có thể không an toàn.

## 3. How does it work?

Flow đơn giản:

```text
Begin transaction
  ↓
Mutation A
  ↓
Savepoint S1
  ↓
SaveChanges B
  ├─ success → continue
  └─ failure → rollback to S1
```

Với retry strategy, toàn bộ transaction phải nằm trong delegate được strategy execute để có thể chạy lại từ đầu khi connection/transient failure xảy ra.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var transaction =
        await db.Database.BeginTransactionAsync(cancellationToken);

    var order = new Order(...);
    db.Orders.Add(order);
    await db.SaveChangesAsync(cancellationToken);

    db.OutboxMessages.Add(OutboxMessage.From(order));
    await db.SaveChangesAsync(cancellationToken);

    await transaction.CommitAsync(cancellationToken);
});
```

Điểm quan trọng: nếu operation retry từ đầu, business side effect ngoài database không được thực hiện tùy tiện bên trong delegate nếu nó không idempotent.

## 5. Real production scenario

Order creation ghi `Orders`, `OrderLines` và Outbox event trong cùng SQL transaction. Azure SQL có transient connectivity issue đúng lúc commit.

Nếu retry chỉ câu `SaveChanges` cuối mà không hiểu transaction state, application có thể ở trạng thái không xác định. Execution strategy cần sở hữu toàn unit of work, và external side effect phải ra ngoài transaction hoặc được bảo vệ bằng idempotency.

## 6. Failure scenario & troubleshooting

**Symptom** → production log báo “execution strategy does not support user-initiated transactions” hoặc retry tạo duplicate call tới external payment API.

**Evidence** → transaction được mở ngoài retry delegate; external side effect nằm trong retry scope.

**Hypothesis** → transaction/retry boundary sai.

**Diagnosis** → trace toàn bộ unit of work, xác định operation nào database-local và operation nào external.

**Fix** → để execution strategy execute toàn transaction; dùng Outbox để defer integration side effect.

**Verification** → fault injection ở connection/commit và kiểm tra không duplicate business effect.

## 7. Common mistakes

* Nghĩ retry database luôn an toàn.
* Gọi external API trong retry delegate mà không idempotent.
* Giữ transaction quá lâu qua network calls.
* Dùng savepoint như substitute cho business compensation.
* Không hiểu transaction isolation/locking cost.

## 8. Alternatives

Một `SaveChanges` duy nhất trong implicit transaction thường đơn giản và đủ. Manual transaction chỉ nên dùng khi cần nhiều database operations phải atomic. Distributed side effects thường nên dùng Outbox/Saga thay vì cố mở transaction xuyên service.

## 9. Trade-offs

### Advantages

* Atomicity rõ ràng trong database.
* Retry transient errors có cấu trúc.
* Savepoint hỗ trợ partial rollback trong transaction.

### Costs / Risks

* Transaction giữ lock lâu hơn nếu scope rộng.
* Retry có thể duplicate side effect ngoài DB.
* Debugging commit ambiguity phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction là all-or-nothing boundary trong database.

### Middle

Biết dùng transaction với `SaveChangesAsync` và execution strategy đúng scope.

### Senior

Đánh giá retry safety, commit ambiguity, lock duration và side effects.

### Technical Lead / Architect

Quyết định transaction boundary, Outbox usage và quy tắc retry toàn hệ thống.

## 11. Key takeaway

* Retry chỉ an toàn khi toàn unit of work có semantics rõ ràng.
* Manual transaction và execution strategy phải được phối hợp.
* External side effect không nên bị retry vô thức cùng database transaction.

# 4. PostgreSQL partial index và selectivity: index nhỏ hơn có thể tốt hơn index “phủ toàn bảng”

## 1. What is it?

Partial index chỉ index các rows thỏa một predicate. Thay vì index toàn bộ bảng, database giữ index cho subset thực sự quan trọng với query pattern.

Ví dụ:

```sql
CREATE INDEX ix_orders_pending_created_at
ON orders (created_at)
WHERE status = 'Pending';
```

## 2. Why does it exist?

Nếu bảng có 100 triệu orders nhưng chỉ 1% ở trạng thái `Pending`, một index toàn bảng trên `(status, created_at)` có thể lớn, tốn write cost và cache memory. Nếu workload quan trọng chủ yếu query pending orders, partial index có thể nhỏ và selective hơn nhiều.

## 3. How does it work?

Planner chỉ dùng partial index khi có thể chứng minh query predicate phù hợp với index predicate.

```sql
SELECT id, created_at
FROM orders
WHERE status = 'Pending'
ORDER BY created_at
LIMIT 100;
```

Index nhỏ hơn nghĩa là ít pages hơn, có thể resident trong memory tốt hơn và giảm index maintenance cho rows không thuộc subset.

## 4. Practical implementation

Đo trước:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at
FROM orders
WHERE status = 'Pending'
ORDER BY created_at
LIMIT 100;
```

Sau đó tạo partial index phù hợp access pattern:

```sql
CREATE INDEX CONCURRENTLY ix_orders_pending_created_at
ON orders (created_at, id)
WHERE status = 'Pending';
```

`CONCURRENTLY` giúp giảm blocking khi tạo index production, nhưng có trade-offs và thời gian build riêng.

## 5. Real production scenario

Một approval platform lưu hàng chục triệu workflow records, trong đó 98% đã Completed. Dashboard “pending approvals” là hot path.

Partial index chỉ cho `Pending` giúp dashboard query ít I/O hơn và giảm index size đáng kể so với index toàn bộ status history.

## 6. Failure scenario & troubleshooting

**Symptom** → partial index tồn tại nhưng query vẫn sequential scan.

**Evidence** → `EXPLAIN` cho thấy predicate query dùng expression/cast khác hoặc planner không chứng minh implication.

**Hypothesis** → query predicate không match index predicate đủ rõ.

**Diagnosis** → so sánh exact filter expression, statistics và row selectivity.

**Fix** → chuẩn hóa predicate/query hoặc chọn index design khác.

**Verification** → `EXPLAIN (ANALYZE, BUFFERS)` trước/sau và đo write overhead.

## 7. Common mistakes

* Tạo partial index theo data hiện tại nhưng workload thay đổi nhanh.
* Index mọi status riêng lẻ mà không đo write amplification.
* Chỉ nhìn execution time local, không xem buffers/I/O.
* Nghĩ index nhỏ luôn tốt nếu query cần nhiều columns ngoài index.
* Bỏ qua maintenance khi predicate subset trở nên lớn.

## 8. Alternatives

* Composite full index: phù hợp nhiều status đều được query.
* Covering index: giảm heap access cho read-heavy path.
* Partitioning: giải quyết data lifecycle/distribution khác, không phải substitute trực tiếp cho partial index.
* Materialized/read model: phù hợp aggregate/reporting phức tạp.

## 9. Trade-offs

### Advantages

* Index nhỏ hơn.
* Có thể giảm read I/O.
* Ít write maintenance cho irrelevant rows.

### Costs / Risks

* Chỉ hữu ích cho subset cụ thể.
* Query predicate phải phù hợp.
* Tăng số index specialized cần governance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không bắt buộc phải chứa mọi row.

### Middle

Biết đọc `EXPLAIN ANALYZE` và tạo partial index theo filter phổ biến.

### Senior

Đánh giá selectivity, buffer hit, write amplification và planner behavior.

### Technical Lead / Architect

Quyết định khi nào specialized index đáng maintenance cost và khi nào cần thay đổi read model/partitioning.

## 11. Key takeaway

* Index design phải dựa trên access pattern và selectivity.
* Partial index đặc biệt mạnh khi hot subset nhỏ so với toàn bảng.
* Luôn đo query plan và write cost, không chỉ “thêm index”.

# 5. MongoDB compound index và ESR reasoning: Equality → Sort → Range không phải mẹo thuộc lòng mà là access-path design

## 1. What is it?

Compound index chứa nhiều fields theo thứ tự xác định. ESR là heuristic phổ biến: đặt field dùng Equality trước, sau đó Sort, rồi Range để tăng khả năng database dùng index hiệu quả.

Ví dụ:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

## 2. Why does it exist?

MongoDB không chỉ cần tìm document; nhiều query còn filter theo tenant/status và sort theo thời gian. Nếu index order không phù hợp, engine có thể phải scan nhiều keys hoặc làm in-memory sort.

Compound index tồn tại để biến multi-dimensional access pattern thành ordered access path.

## 3. How does it work?

B-tree index được sắp theo prefix fields trước. Với:

```text
(tenantId, status, createdAt)
```

engine có thể nhanh chóng định vị một tenant + status cụ thể rồi đọc documents theo `createdAt` order.

Nếu query bỏ qua leading prefix, index utility có thể giảm đáng kể.

## 4. Practical implementation

Index:

```javascript
db.orders.createIndex({
  tenantId: 1,
  status: 1,
  createdAt: -1
})
```

Query:

```javascript
db.orders.find({
  tenantId: "tenant-42",
  status: "Pending",
  createdAt: { $lt: ISODate("2026-09-01T00:00:00Z") }
})
.sort({ createdAt: -1 })
.limit(50)
.explain("executionStats")
```

Quan sát `totalKeysExamined`, `totalDocsExamined`, sort stage và returned count.

## 5. Real production scenario

Một SaaS notification store lưu hàng trăm triệu documents. UI luôn query theo tenant, notification state và newest-first. Single-field indexes riêng lẻ buộc planner/intersection xử lý nhiều work hơn một compound index đúng access pattern.

## 6. Failure scenario & troubleshooting

**Symptom** → query latency tăng khi tenant lớn dù index tồn tại.

**Evidence** → `keysExamined` cao hơn rất nhiều `nReturned`; xuất hiện blocking sort.

**Hypothesis** → compound index order không khớp filter/sort pattern hoặc range đặt quá sớm.

**Diagnosis** → inspect `explain`, query shape, cardinality của equality fields và sort requirements.

**Fix** → thiết kế index theo dominant query shape; tránh tạo index chỉ dựa trên field popularity.

**Verification** → compare execution stats và write/storage overhead.

## 7. Common mistakes

* Tạo một index cho mỗi field rồi kỳ vọng planner luôn combine tối ưu.
* Bỏ qua leading-prefix behavior.
* Tạo quá nhiều compound indexes làm write chậm và cache pressure tăng.
* Áp dụng ESR như luật tuyệt đối mà không đo cardinality/query plan.
* Không xét multi-tenant skew: tenant lớn và nhỏ có behavior khác nhau.

## 8. Alternatives

* Single-field index: đủ cho query đơn giản.
* Different compound order: phù hợp query shape khác.
* Denormalized read model: khi query requirements mâu thuẫn nhau quá nhiều.
* Elasticsearch: phù hợp full-text/relevance, không thay MongoDB transactional/document workload.

## 9. Trade-offs

### Advantages

* Giảm keys/docs examined.
* Có thể phục vụ sort trực tiếp từ index.
* Latency ổn định hơn cho hot query shapes.

### Costs / Risks

* Tăng storage và write amplification.
* Một index hiếm khi phục vụ mọi query.
* Data skew có thể làm plan behavior khó dự đoán.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu compound index có thứ tự fields và prefix matters.

### Middle

Biết dùng `explain("executionStats")` để đánh giá query/index.

### Senior

Đánh giá cardinality, sort, range, data skew và write cost.

### Technical Lead / Architect

Thiết kế data model/index portfolio theo access patterns thực tế thay vì schema aesthetics.

## 11. Key takeaway

* Index order là query access-path decision.
* ESR là heuristic để reasoning, không phải công thức bất biến.
* Đo `keysExamined`, `docsExamined` và write cost cùng nhau.

# 6. Saga Pattern: orchestration vs choreography khi một business transaction đi qua nhiều service

## 1. What is it?

Saga là cách phối hợp một business transaction kéo dài qua nhiều service mà không dùng một distributed ACID transaction duy nhất. Mỗi bước commit local transaction của service mình; nếu bước sau thất bại, hệ thống chạy compensating action cho các bước trước khi phù hợp.

Hai style phổ biến:

* **Orchestration:** một coordinator quyết định bước tiếp theo.
* **Choreography:** services phản ứng với events mà không có coordinator trung tâm.

## 2. Why does it exist?

Trong microservices, Order, Payment và Inventory có database ownership riêng. Một transaction SQL không thể đơn giản bao cả ba mà không tạo coupling/distributed transaction phức tạp.

Saga chấp nhận eventual consistency và biến failure handling thành phần rõ ràng của business workflow.

## 3. How does it work?

Orchestration:

```text
Order Saga
  ↓ ReserveInventory
Inventory
  ↓ success
Order Saga
  ↓ AuthorizePayment
Payment
  ↓ failure
Order Saga
  ↓ ReleaseInventory
```

Choreography:

```text
OrderCreated event
  ↓
Inventory reserves → InventoryReserved
  ↓
Payment authorizes → PaymentFailed
  ↓
Inventory reacts → release
```

Mỗi message có thể được deliver hơn một lần; consumer phải idempotent.

## 4. Practical implementation

Một orchestration state đơn giản:

```csharp
public sealed record CheckoutSagaState(
    Guid OrderId,
    bool InventoryReserved,
    bool PaymentAuthorized,
    string Status);
```

Command handlers phải có idempotency key/business key:

```csharp
if (await _processedMessages.ExistsAsync(message.Id, cancellationToken))
    return;

await _inventory.ReleaseAsync(message.OrderId, cancellationToken);
await _processedMessages.MarkAsync(message.Id, cancellationToken);
```

Production implementation thường cần durable saga state, Outbox/Inbox và timeout handling.

## 5. Real production scenario

Checkout flow:

1. create order;
2. reserve stock;
3. authorize payment;
4. create shipment request.

Payment success nhưng shipment service unavailable. Business phải quyết định: giữ order ở pending fulfillment, retry shipment, hay compensate payment. Đây là business decision, không chỉ technical retry.

## 6. Failure scenario & troubleshooting

**Symptom** → inventory bị release hai lần hoặc payment refund duplicate.

**Evidence** → broker redelivery cùng message ID; consumer không có deduplication.

**Hypothesis** → compensating command không idempotent.

**Diagnosis** → trace saga ID/message ID qua services, kiểm tra Inbox/processing table.

**Fix** → idempotent handlers, durable state, explicit transition guards.

**Verification** → replay duplicate/out-of-order messages và kiểm tra final business invariant.

## 7. Common mistakes

* Gọi Saga chỉ là “chuỗi message”.
* Compensation được coi là exact rollback; thực tế business effect có thể không đảo ngược hoàn toàn.
* Choreography quá nhiều events làm workflow khó quan sát.
* Orchestrator trở thành god-service chứa business logic của mọi domain.
* Không thiết kế timeout/manual intervention state.

## 8. Alternatives

* Single database transaction: đơn giản hơn nếu modules có thể cùng data boundary.
* Modular Monolith: tránh distributed transaction nếu business chưa cần service separation.
* Two-phase commit: consistency mạnh hơn nhưng coupling/availability/operational cost cao, thường không phù hợp web microservices.

## 9. Trade-offs

### Advantages

* Tôn trọng data ownership giữa services.
* Failure/compensation explicit.
* Hỗ trợ long-running business process.

### Costs / Risks

* Eventual consistency.
* Workflow state và observability phức tạp.
* Compensation logic tăng business complexity.
* Debugging cần correlation toàn hệ thống.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu local transaction không tự mở rộng xuyên nhiều services.

### Middle

Biết implement idempotent message handlers và saga state cơ bản.

### Senior

Reason về compensation, duplicate delivery, timeout, ordering và failure recovery.

### Technical Lead / Architect

Quyết định có nên phân service đến mức cần Saga, chọn orchestration/choreography và ownership của workflow state.

## 11. Key takeaway

* Saga là business consistency pattern, không chỉ messaging pattern.
* Compensation không nhất thiết đưa thế giới về trạng thái “chưa từng xảy ra”.
* Nếu single transaction đủ, đừng tạo distributed saga chỉ để trông “microservices hơn”.

# 7. Azure Blob Storage block upload: streaming file lớn, retry từng block và tránh biến App Service thành temporary file server

## 1. What is it?

Block Blob cho phép file lớn được chia thành blocks, upload độc lập rồi commit thành một blob hoàn chỉnh. Client hoặc backend không cần giữ toàn bộ file trong memory.

Mental model:

```text
File stream
  ↓ block 1 → upload
  ↓ block 2 → upload
  ↓ block 3 → upload
  ↓
commit block list
```

## 2. Why does it exist?

Upload file nhiều GB qua web application có rủi ro memory pressure, request timeout và failure giữa đường. Chia block cho phép retry phần thất bại thay vì upload lại toàn bộ file.

Trong nhiều architecture, tốt hơn nữa là browser upload trực tiếp Blob Storage bằng scoped SAS, còn backend chỉ cấp quyền và quản lý metadata.

## 3. How does it work?

Blob client có thể stream source và SDK tự dùng block upload tùy kích thước/options. Với direct-to-Blob:

```text
Browser → API: request upload authorization
API → Blob: generate scoped access
Browser → Blob: upload blocks
Browser/API → finalize metadata
```

Điều này loại application server khỏi data path lớn.

## 4. Practical implementation

Backend streaming:

```csharp
var blobClient = containerClient.GetBlobClient(blobName);

await blobClient.UploadAsync(
    request.Body,
    new BlobUploadOptions
    {
        HttpHeaders = new BlobHttpHeaders
        {
            ContentType = request.ContentType
        }
    },
    cancellationToken);
```

Với browser direct upload, SAS phải có scope tối thiểu, expiry ngắn và blob name do server kiểm soát.

## 5. Real production scenario

Một automotive marketplace cho dealer upload video inspection 1–3 GB. Nếu request đi Browser → App Service → Blob, App Service phải giữ connection và bandwidth lớn cho mọi upload.

Direct upload giảm App Service egress/ingress pressure và cho phép Blob SDK/browser retry block hiệu quả hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → file 2 GB thường fail ở phút thứ 8 và user phải upload lại từ đầu.

**Evidence** → upload proxy qua API, reverse proxy timeout 8 phút, không resumable.

**Hypothesis** → web tier đang sở hữu data transfer không cần thiết.

**Diagnosis** → xem request duration, App Service bandwidth, proxy timeout và Blob request logs.

**Fix** → direct-to-Blob hoặc block/resumable upload; metadata finalize sau upload thành công.

**Verification** → kill network giữa upload, resume/retry và kiểm tra final hash/size.

## 7. Common mistakes

* Đọc toàn file vào `byte[]` trước khi upload.
* SAS cấp quyền container quá rộng hoặc expiry quá dài.
* Tin `Content-Type`/filename từ user mà không validate.
* Không có malware/content validation workflow cho uploaded files.
* Lưu temporary file trên local App Service filesystem và giả định nó durable/shared.

## 8. Alternatives

* Proxy qua backend: đơn giản cho file nhỏ và policy strict.
* Direct-to-Blob SAS: tốt cho file lớn.
* Azure Data Lake/other object storage: tùy workload/data analytics requirements.

## 9. Trade-offs

### Advantages

* Giảm memory/bandwidth pressure trên app.
* Retry từng block.
* Scale storage path độc lập web tier.

### Costs / Risks

* Upload authorization/security phức tạp hơn.
* Cần finalize/orphan cleanup workflow.
* Client phải xử lý retry/progress tốt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu object storage tốt hơn local filesystem cho durable large files.

### Middle

Biết stream upload và dùng Blob SDK/SAS đúng scope.

### Senior

Thiết kế resumability, checksum, orphan cleanup, security scanning và failure handling.

### Technical Lead / Architect

Quyết định data path, identity model, lifecycle/cost tiering và operational ownership cho large-file platform.

## 11. Key takeaway

* File lớn không nên bị buffer toàn bộ trong web process.
* Direct-to-Blob thường giảm coupling và web-tier pressure.
* SAS scope, expiry và post-upload validation là security boundary quan trọng.

# 8. `git bisect`: khoanh vùng production regression bằng binary search thay vì đọc hàng trăm commit bằng mắt

## 1. What is it?

`git bisect` tìm commit đầu tiên gây lỗi bằng binary search giữa một known-good commit và một known-bad commit.

Nếu có 1024 commits, linear inspection có thể cần xem hàng trăm commits; binary search lý thuyết chỉ cần khoảng 10 bước để khoanh vùng.

## 2. Why does it exist?

Production regression thường xuất hiện sau nhiều merge/commits. Đọc commit history bằng mắt dễ bias và chậm, đặc biệt khi bug không nằm ở commit “đáng nghi nhất”.

`git bisect` biến debugging history thành experiment có cấu trúc: checkout midpoint, test, đánh dấu good/bad, lặp lại.

## 3. How does it work?

```text
Good ----------------------------- Bad
                 ↑ test midpoint

If midpoint bad:
Good ----------- Bad
        ↑ next midpoint
```

Git thu hẹp search space sau mỗi kết quả.

## 4. Practical implementation

Manual:

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.1

# Run the reproduction test
git bisect good   # or: git bisect bad

# When done
git bisect reset
```

Automated:

```bash
git bisect start HEAD v2.4.1
git bisect run dotnet test tests/RegressionTests/RegressionTests.csproj
```

Exit code 0 = good, non-zero = bad; scripts có thể dùng 125 để skip commit không test được.

## 5. Real production scenario

Sau release, checkout API tăng 5xx. Release chứa 180 commits từ nhiều teams. Một deterministic integration test tái hiện lỗi serializer.

`git bisect run` tìm commit đổi custom converter trong vài vòng thay vì review toàn bộ diff release.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit vô lý hoặc kết quả thay đổi mỗi lần.

**Evidence** → test flaky hoặc cần external state không deterministic.

**Hypothesis** → classification good/bad không đáng tin cậy.

**Diagnosis** → chạy reproduction nhiều lần trên cùng commit; cô lập test data/environment.

**Fix** → tạo deterministic regression test, pin dependency/environment hoặc dùng skip cho commits không build được.

**Verification** → checkout parent và culprit commit, test nhiều lần để chứng minh transition good→bad.

## 7. Common mistakes

* Chọn “good” commit chưa thực sự được xác minh.
* Dùng flaky E2E test làm oracle.
* Quên dependency/config ngoài Git thay đổi theo thời gian.
* Dừng ở culprit commit mà không hiểu root cause.
* Không tạo regression test sau khi fix.

## 8. Alternatives

* Compare release diff: nhanh nếu change set nhỏ.
* Feature-flag isolation: tốt khi feature boundaries rõ.
* Observability/traces: giúp localize subsystem trước khi bisect.
* Revert candidate commit: có thể phục hồi nhanh nhưng không phải root-cause method.

## 9. Trade-offs

### Advantages

* Giảm search space rất nhanh.
* Evidence-driven.
* Có thể tự động hóa bằng test script.

### Costs / Risks

* Cần reproducible test.
* Historical commits có thể không build với environment hiện tại.
* Không bắt được external/config regression không nằm trong Git history.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu binary search trên commit history.

### Middle

Biết chạy manual/automated bisect.

### Senior

Xây deterministic regression harness và kết hợp telemetry với history search.

### Technical Lead / Architect

Thiết kế release traceability, artifact/version metadata và testability để production regression có thể được khoanh vùng nhanh.

## 11. Key takeaway

* `git bisect` hữu ích khi có known-good, known-bad và deterministic test.
* Nó tìm culprit nhanh nhưng không thay root-cause analysis.
* Một regression test tốt biến incident hôm nay thành protection cho release sau.

# 9. React effect race condition: stale request, `AbortController` và vì sao UI có thể hiển thị data của request cũ

## 1. What is it?

Effect race xảy ra khi component phát nhiều async requests theo state/props thay đổi và response đến không theo thứ tự request được gửi.

Ví dụ user chọn customer A rồi ngay lập tức customer B:

```text
Request A starts
Request B starts
Response B arrives → UI shows B
Response A arrives later → UI incorrectly shows A
```

Đây không phải data race giữa CPU threads; nó là ordering race trong async UI behavior.

## 2. Why does it exist?

Network latency không deterministic. React effect lifecycle cũng cho phép cleanup khi dependencies thay đổi/unmount. Nếu code chỉ `fetch().then(setState)`, stale response vẫn có thể update state sau khi context đã đổi.

## 3. How does it work?

Effect chạy khi dependency thay đổi. Cleanup của effect trước chạy trước effect mới. Đây là nơi tự nhiên để abort request cũ.

## 4. Practical implementation

```tsx
useEffect(() => {
  const controller = new AbortController();

  async function loadCustomer() {
    try {
      const response = await fetch(`/api/customers/${customerId}`, {
        signal: controller.signal
      });

      if (!response.ok) {
        throw new Error(`HTTP ${response.status}`);
      }

      const data = await response.json();
      setCustomer(data);
    } catch (error) {
      if ((error as DOMException).name !== "AbortError") {
        setError(error as Error);
      }
    }
  }

  loadCustomer();

  return () => controller.abort();
}, [customerId]);
```

Backend cũng nên nhận request cancellation nếu client disconnect/abort được propagate qua HTTP stack.

## 5. Real production scenario

CRM UI có search-as-you-type. Request cho query `mic` chậm 800 ms; request `micro` chỉ 100 ms. Nếu response cũ ghi đè response mới, user thấy kết quả không khớp text hiện tại.

Frontend bug này có thể bị nhầm thành backend caching bug.

## 6. Failure scenario & troubleshooting

**Symptom** → kết quả UI đôi lúc “nhảy ngược” về lựa chọn trước.

**Evidence** → browser Network tab cho thấy request cũ hoàn thành sau request mới.

**Hypothesis** → stale response updates state.

**Diagnosis** → correlate request start/end với current dependency value và component lifecycle.

**Fix** → abort stale request hoặc dùng request sequence/version guard.

**Verification** → throttle network trong DevTools và đổi selection nhanh liên tục.

## 7. Common mistakes

* Dùng empty dependency array trong effect đọc prop thay đổi.
* Ignore cleanup.
* Catch `AbortError` rồi log như production error.
* Chỉ disable button nhưng không xử lý stale async path.
* Duplicate server requests từ effects do component lifecycle nhưng không hiểu nguyên nhân.

## 8. Alternatives

Data-fetching libraries như TanStack Query có request/caching lifecycle giàu hơn. Sequence IDs có thể dùng khi API không hỗ trợ abort. Server-driven cancellation không thay frontend stale-state guard.

## 9. Trade-offs

### Advantages

* UI correctness tốt hơn.
* Giảm wasted network work khi abort được support.
* Lifecycle rõ ràng.

### Costs / Risks

* Error/cancellation handling phức tạp hơn.
* Cache libraries thêm abstraction và configuration.
* Abort không đảm bảo server đã rollback side effect.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu response có thể đến khác thứ tự request gửi.

### Middle

Biết effect cleanup và `AbortController`.

### Senior

Phân biệt stale UI, cache issue, server latency và cancellation semantics.

### Technical Lead / Architect

Chuẩn hóa frontend data-fetching pattern, cache ownership và API cancellation/idempotency contract.

## 11. Key takeaway

* Async UI correctness phụ thuộc ordering, không chỉ HTTP success.
* Cleanup effect nên hủy hoặc vô hiệu stale work.
* Client abort không đồng nghĩa mọi server side effect đã biến mất.

# 10. Incremental modernization từ .NET Framework: strangler boundary, compatibility và rollback thay vì rewrite toàn hệ thống

## 1. What is it?

Incremental modernization chuyển dần chức năng từ legacy .NET Framework sang modern .NET qua các boundaries rõ ràng thay vì rewrite toàn bộ application trong một lần.

Strangler-style mental model:

```text
Client
  ↓
Routing / facade
  ├─ legacy capability → .NET Framework app
  └─ migrated capability → modern .NET service/module
```

Mục tiêu là giảm migration risk bằng từng slice có thể deploy, verify và rollback độc lập.

## 2. Why does it exist?

Enterprise application lâu năm thường có:

* packages chỉ hỗ trợ .NET Framework;
* ASP.NET/System.Web assumptions;
* Windows/IIS-specific dependencies;
* database stored procedures và shared schema;
* third-party SDK cũ;
* deployment pipeline legacy;
* business behavior không được test đầy đủ.

Big-bang rewrite đòi team tái tạo cả functional behavior lẫn operational behavior cùng lúc. Risk thường cao hơn estimate ban đầu.

## 3. How does it work?

Một migration thực dụng thường bắt đầu bằng inventory dependency và chọn boundary có coupling thấp.

```text
Legacy monolith
  ├─ Auth
  ├─ Orders
  ├─ Reporting  ← migrate first
  └─ Admin
```

Routing có thể ở reverse proxy, gateway hoặc application facade. Data ownership có thể chưa tách ngay; điều quan trọng là dependency direction và release independence được cải thiện từng bước.

## 4. Practical implementation

Một compatibility facade có thể giữ contract cũ:

```csharp
public interface IReportingClient
{
    Task<ReportDto> GenerateAsync(
        ReportRequest request,
        CancellationToken cancellationToken);
}
```

Legacy caller ban đầu dùng adapter in-process; sau migration implementation có thể gọi modern .NET reporting service qua HTTP mà caller contract ít thay đổi.

Database migration nên dùng expand-contract:

1. thêm schema compatible;
2. deploy code đọc/ghi compatible;
3. migrate data;
4. chuyển traffic;
5. xóa old schema sau rollback window.

## 5. Real production scenario

Một ASP.NET MVC 5 application trên .NET Framework có 120 modules. Reporting là workload CPU/memory cao nhưng ít transactional coupling.

Team tách Reporting sang .NET 10 Worker/API trước. Main application vẫn xử lý authentication/orders. Sau khi operational model ổn định, tiếp tục migrate các slices khác.

## 6. Failure scenario & troubleshooting

**Symptom** → module mới chạy functional tests tốt nhưng production lỗi authentication/session hoặc file-path behavior.

**Evidence** → legacy app phụ thuộc Windows identity, shared session hoặc local filesystem mà migration inventory không ghi nhận.

**Hypothesis** → hidden runtime dependency bị bỏ sót.

**Diagnosis** → trace process/environment/network/filesystem dependencies, không chỉ NuGet references.

**Fix** → explicitize dependency, tạo compatibility adapter hoặc trì hoãn slice đó nếu boundary chưa đủ sạch.

**Verification** → shadow traffic/canary, parity metrics và rollback test.

## 7. Common mistakes

* Rewrite vì “code cũ xấu” mà không xác định business value.
* Migrate framework đồng thời đổi architecture, database và UI trong một release.
* Tách microservice nhưng vẫn shared database/table ownership không rõ.
* Không có behavior characterization tests trước migration.
* Không test rollback sau schema change.

## 8. Alternatives

* In-place upgrade: tốt khi dependency compatibility cao.
* Keep legacy stable: đúng nếu business value thấp và operational risk chấp nhận được.
* Big-bang rewrite: chỉ hợp lý khi system nhỏ, scope hiểu rõ và parallel run/migration risk thấp.

## 9. Trade-offs

### Advantages

* Giảm blast radius.
* Có learning loop qua từng slice.
* Rollback khả thi hơn.
* Business delivery có thể tiếp tục song song.

### Costs / Risks

* Tạm thời vận hành hai stacks.
* Compatibility layer tạo complexity trung gian.
* Migration kéo dài cần governance mạnh.
* Shared data boundary có thể là bottleneck tổ chức/architecture.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu modernization không nhất thiết là rewrite.

### Middle

Biết migrate một slice với tests, config và deployment riêng.

### Senior

Inventory hidden dependencies, design compatibility, canary và rollback.

### Technical Lead / Architect

Quyết định migration sequence dựa trên coupling, business value, operational risk và target architecture; biết khi nào **không nên migrate ngay**.

## 11. Key takeaway
