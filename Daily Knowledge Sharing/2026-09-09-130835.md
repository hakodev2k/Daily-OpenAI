# 1. C# `ValueTask<T>`: giảm allocation đúng chỗ mà không biến async API thành bẫy correctness

## 1. What is it?

`ValueTask<T>` là awaitable value type trong .NET có thể đại diện cho một kết quả đã có sẵn hoặc một asynchronous operation chưa hoàn tất. Nó tồn tại chủ yếu để giảm allocation của `Task<T>` trong những hot path mà phần lớn lời gọi hoàn tất synchronously.

Mental model đơn giản:

```text
Task<T>
  └─ thường cần object đại diện operation

ValueTask<T>
  ├─ có thể chứa trực tiếp T nếu đã có kết quả
  └─ hoặc wrap Task<T>/IValueTaskSource<T> nếu phải chờ
```

Nó không phải phiên bản “nhanh hơn mặc định” của `Task<T>`.

## 2. Why does it exist?

Giả sử một cache API được gọi hàng triệu lần và 99% hit memory cache. Nếu API luôn trả `Task<T>`, implementation có thể phải tạo nhiều task objects không cần thiết. `ValueTask<T>` cho phép cache hit trả về synchronously mà không tạo một `Task<T>` mới cho mỗi call.

Lợi ích chỉ đáng kể khi allocation thực sự nằm trên hot path. Với business API bình thường, readability và composability của `Task<T>` thường quan trọng hơn vài allocation nhỏ.

## 3. How does it work?

Một method có thể trả trực tiếp giá trị khi đã có dữ liệu:

```csharp
public ValueTask<Product?> GetAsync(
    string key,
    CancellationToken cancellationToken)
{
    if (_cache.TryGetValue(key, out Product? cached))
        return ValueTask.FromResult(cached);

    return new ValueTask<Product?>(LoadAsync(key, cancellationToken));
}
```

Consumer vẫn dùng:

```csharp
var product = await repository.GetAsync(key, ct);
```

Điểm khác biệt quan trọng là một `ValueTask<T>` không nên được xem như reusable promise. Một số backing implementations dựa trên `IValueTaskSource<T>` chỉ cho phép await một lần.

## 4. Practical implementation

Dùng `ValueTask<T>` khi có bằng chứng rằng synchronous completion xảy ra rất thường xuyên:

```csharp
public sealed class FeatureFlagStore
{
    private readonly ConcurrentDictionary<string, bool> _cache = new();
    private readonly IRemoteFlagClient _remote;

    public FeatureFlagStore(IRemoteFlagClient remote) => _remote = remote;

    public ValueTask<bool> IsEnabledAsync(
        string name,
        CancellationToken cancellationToken)
    {
        if (_cache.TryGetValue(name, out var enabled))
            return ValueTask.FromResult(enabled);

        return LoadAndCacheAsync(name, cancellationToken);
    }

    private async ValueTask<bool> LoadAndCacheAsync(
        string name,
        CancellationToken cancellationToken)
    {
        var enabled = await _remote.GetAsync(name, cancellationToken);
        _cache[name] = enabled;
        return enabled;
    }
}
```

Nếu caller cần lưu operation, await nhiều lần hoặc phối hợp bằng `Task.WhenAll`, chuyển rõ ràng bằng `.AsTask()` khi cần thay vì dựa vào assumptions.

## 5. Real production scenario

Một authorization component kiểm tra feature/permission cache trên mỗi request. Profiling cho thấy hàng chục triệu `Task<bool>` allocations mỗi phút dù hầu hết lookup hoàn tất ngay trong memory. Sau khi benchmark xác nhận allocation pressure đáng kể, team chuyển riêng hot cache API sang `ValueTask<bool>` và giảm Gen 0 GC pressure.

Điểm quan trọng: team không đổi toàn bộ async codebase sang `ValueTask`; chỉ đổi nơi profiler chứng minh lợi ích.

## 6. Failure scenario & troubleshooting

**Symptom** → intermittent exception hoặc undefined behavior khi cùng một `ValueTask<T>` được await nhiều lần.

**Evidence** → code lưu `ValueTask<T>` vào field/local rồi nhiều consumer cùng await; backing source dùng pooled `IValueTaskSource<T>`.

**Hypothesis** → caller đang dùng `ValueTask<T>` như một `Task<T>` reusable.

**Diagnosis** → tìm chỗ lưu, await lại, gọi `.Result`, hoặc combine operation sau khi đã consume.

**Fix** → await trực tiếp một lần; nếu cần reuse/composition, chuyển thành `Task<T>` bằng `.AsTask()` hoặc đổi API về `Task<T>`.

**Verification** → stress test concurrent consumers và chạy allocation benchmark để chắc rằng optimization vẫn có giá trị.

## 7. Common mistakes

* Dùng `ValueTask<T>` cho mọi async API chỉ vì nghĩ value type luôn nhanh hơn.
* Await cùng instance nhiều lần.
* Gọi `.AsTask()` ở mọi caller, làm mất phần lớn lợi ích allocation.
* Tăng complexity mà không benchmark.
* Dùng nó cho method gần như luôn asynchronous nên chỉ tăng kích thước state machine/copy cost.

## 8. Alternatives

`Task<T>` vẫn là mặc định tốt nhất cho phần lớn application code. Synchronous API phù hợp nếu operation thực sự không bao giờ async. Caching ở layer khác đôi khi loại bỏ hot allocation tốt hơn thay đổi return type.

## 9. Trade-offs

### Advantages

* Có thể giảm allocation khi synchronous completion rất phổ biến.
* Hữu ích cho high-throughput libraries/cache primitives.

### Costs / Risks

* Semantics khó hơn `Task<T>`.
* Composability kém hơn.
* Dễ misuse nếu caller không hiểu single-consumption constraints.
* Optimization có thể không đáng kể nếu operation chủ yếu I/O.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Dùng `Task<T>` mặc định và hiểu `await` semantics.

### Middle

Biết `ValueTask<T>` phù hợp khi operation thường hoàn tất synchronously.

### Senior

Benchmark allocation, hiểu `IValueTaskSource<T>`, pooling và consumption rules.

### Technical Lead / Architect

Đặt API guideline: chỉ đưa `ValueTask<T>` vào public/internal contracts khi performance evidence bù được cognitive cost.

## 11. Key takeaway

* `ValueTask<T>` là optimization tool, không phải async default.
* Lợi ích lớn nhất xuất hiện ở hot path có tỷ lệ synchronous completion cao.
* Nếu API cần reuse/composition đơn giản, `Task<T>` thường an toàn và dễ bảo trì hơn.

# 2. EF Core optimistic concurrency: `rowversion`, concurrency token và chiến lược resolve conflict có chủ đích

## 1. What is it?

Optimistic concurrency giả định nhiều transactions hiếm khi sửa cùng một record đồng thời. Thay vì lock record từ lúc đọc đến lúc ghi, application ghi kèm điều kiện rằng dữ liệu vẫn ở version đã đọc.

Với SQL Server, một pattern phổ biến là `rowversion`:

```text
Read:  Order(Id=42, Status=Pending, Version=0x0012)
Update: ... WHERE Id = 42 AND Version = 0x0012
```

Nếu row đã bị người khác sửa, `UPDATE` ảnh hưởng 0 rows và EF Core ném `DbUpdateConcurrencyException`.

## 2. Why does it exist?

Không có concurrency control, hai users có thể gây lost update:

```text
A đọc Quantity = 10
B đọc Quantity = 10
A lưu 11
B lưu 8
=> thay đổi của A biến mất
```

Optimistic concurrency phát hiện xung đột thay vì âm thầm overwrite.

## 3. How does it work?

Entity:

```csharp
public sealed class Order
{
    public Guid Id { get; set; }
    public string Status { get; set; } = null!;

    [Timestamp]
    public byte[] Version { get; set; } = null!;
}
```

EF Core giữ original `Version`. Khi `SaveChangesAsync()` chạy, generated SQL thêm token vào `WHERE`. Nếu không row nào match, EF biết snapshot đã stale.

Concurrency token cũng có thể là application-managed field, không nhất thiết `rowversion`.

## 4. Practical implementation

API nên đưa version về client, ví dụ bằng opaque ETag hoặc Base64 token:

```csharp
try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new
    {
        code = "order_concurrency_conflict",
        message = "The order was changed by another operation. Reload and retry."
    });
}
```

Không nên catch rồi tự retry toàn bộ update một cách mù quáng. Nếu request dựa trên business decision từ dữ liệu cũ, retry có thể ghi một quyết định không còn hợp lệ.

## 5. Real production scenario

Một back-office order screen cho phép Operations và Finance cùng cập nhật đơn hàng. Operations đổi `Status`, Finance sửa credit approval. Trước concurrency token, thao tác Save cuối cùng overwrite cả snapshot cũ và làm mất thay đổi của người kia.

Sau khi thêm token, UI nhận `409 Conflict`, reload server state và cho user merge hoặc thực hiện action lại trên dữ liệu mới.

## 6. Failure scenario & troubleshooting

**Symptom** → số lượng `DbUpdateConcurrencyException` tăng đột biến sau khi thêm background worker.

**Evidence** → cùng entity bị web API và worker update rất thường xuyên.

**Hypothesis** → aggregate đang trở thành contention hotspot hoặc các fields độc lập bị ép chung vào một write model.

**Diagnosis** → log entity key, original token, workflow/action và conflict frequency; không log dữ liệu nhạy cảm.

**Fix** → giảm unnecessary writes, tách mutable concerns nếu domain cho phép, hoặc thiết kế explicit conflict-resolution policy.

**Verification** → concurrency test với nhiều writers và kiểm tra không còn lost update, đồng thời conflict rate ở mức chấp nhận được.

## 7. Common mistakes

* Catch exception rồi retry vô hạn.
* Trả `500` cho conflict có thể dự đoán.
* Chỉ bảo vệ một số write paths, để raw SQL/background job bypass token.
* Cho client gửi cả entity snapshot rồi overwrite mọi column.
* Hiểu optimistic concurrency như distributed lock.

## 8. Alternatives

Pessimistic locking phù hợp khi conflict rất đắt và critical section ngắn. Serialized command processing phù hợp aggregate có write contention cao. Event sourcing có model concurrency riêng bằng stream version. Atomic SQL updates (`SET Count = Count + 1`) phù hợp một số counter operations.

## 9. Trade-offs

### Advantages

* Không giữ lock dài qua user think-time.
* Phát hiện lost update rõ ràng.
* Scale tốt khi conflicts hiếm.

### Costs / Risks

* Conflict resolution phải được thiết kế.
* User experience phức tạp hơn.
* High-contention aggregates có thể retry/conflict liên tục.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu lost update và `DbUpdateConcurrencyException`.

### Middle

Biết cấu hình token và trả conflict semantics phù hợp.

### Senior

Thiết kế merge/reload/retry dựa trên business semantics.

### Technical Lead / Architect

Nhận diện contention hotspot và chọn consistency model ở cấp workflow/aggregate thay vì chỉ sửa EF mapping.

## 11. Key takeaway

* Optimistic concurrency biến silent overwrite thành explicit conflict.
* Conflict là business/consistency event, không chỉ exception kỹ thuật.
* Retry chỉ đúng khi operation vẫn hợp lệ trên state mới.

# 3. PostgreSQL partial index: index ít hơn nhưng đúng workload thay vì index mọi row

## 1. What is it?

Partial index là index chỉ chứa rows thỏa một predicate. Ví dụ hệ thống có 100 triệu orders nhưng màn hình vận hành chủ yếu truy vấn vài trăm nghìn orders chưa hoàn tất:

```sql
CREATE INDEX ix_orders_active_created_at
ON orders (created_at DESC)
WHERE status IN ('Pending', 'Processing');
```

Index nhỏ hơn full-table index và tập trung vào working set quan trọng.

## 2. Why does it exist?

Full index có chi phí storage, cache footprint và write amplification. Nếu 98% rows đã `Completed` nhưng query operational luôn lọc active rows, indexing cả 100% dataset có thể lãng phí.

Partial index cho phép tối ưu theo data distribution và access pattern thực tế.

## 3. How does it work?

PostgreSQL planner chỉ dùng partial index khi có thể chứng minh query predicate phù hợp với index predicate. Query:

```sql
SELECT id, created_at
FROM orders
WHERE status = 'Pending'
ORDER BY created_at DESC
LIMIT 100;
```

có thể tận dụng index trên active statuses. Nhưng predicate viết khác hoặc parameterization khiến implication khó chứng minh có thể làm planner không chọn index như mong đợi.

## 4. Practical implementation

Trước khi tạo index, đo distribution:

```sql
SELECT status, count(*)
FROM orders
GROUP BY status;
```

Sau đó kiểm tra plan:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at
FROM orders
WHERE status = 'Pending'
ORDER BY created_at DESC
LIMIT 100;
```

Theo dõi index usage sau rollout thay vì chỉ thấy query test nhanh hơn một lần.

## 5. Real production scenario

Một job queue lưu lịch sử 12 tháng trong cùng bảng. 99,5% jobs ở trạng thái terminal; worker chỉ poll `Queued`. Full index `(status, scheduled_at)` lớn, tốn RAM và bị update liên tục. Partial index chỉ cho queued/retryable jobs giảm đáng kể index size và buffer churn.

## 6. Failure scenario & troubleshooting

**Symptom** → đã tạo partial index nhưng production query vẫn sequential scan.

**Evidence** → `EXPLAIN` cho thấy planner không dùng index.

**Hypothesis** → query predicate không imply index predicate, statistics/cost model khác test environment, hoặc result set quá lớn.

**Diagnosis** → so sánh exact SQL, parameters, row distribution, `ANALYZE` state và `EXPLAIN (ANALYZE, BUFFERS)`.

**Fix** → chỉnh predicate/index theo query thật; không ép planner bằng workaround trước khi hiểu cost.

**Verification** → kiểm tra latency, buffer reads, write overhead và index size dưới production-like data.

## 7. Common mistakes

* Tạo partial index theo dữ liệu hiện tại nhưng không xét distribution thay đổi.
* Predicate quá đặc thù khiến ít query dùng được.
* Chỉ nhìn execution time, bỏ qua write cost.
* Giữ cả full index và partial index trùng lặp lâu dài.
* Không xác minh planner có thể match predicate.

## 8. Alternatives

Composite/full indexes phù hợp access patterns rộng. Table partitioning phù hợp lifecycle/data isolation lớn hơn. Archiving historical rows có thể giải quyết cả storage lẫn operational working set. BRIN phù hợp bảng rất lớn có correlation vật lý tốt.

## 9. Trade-offs

### Advantages

* Index nhỏ hơn.
* Ít write amplification hơn full index tương đương.
* Cache locality tốt cho hot subset.

### Costs / Risks

* Query phải phù hợp predicate.
* Data distribution thay đổi có thể giảm hiệu quả.
* Nhiều partial indexes riêng lẻ dễ thành maintenance burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không miễn phí.

### Middle

Biết đọc `EXPLAIN` và tạo index theo query pattern.

### Senior

Kết hợp distribution, selectivity, write cost và planner behavior.

### Technical Lead / Architect

Thiết kế retention/partition/index strategy như một lifecycle tổng thể, không chữa từng slow query riêng lẻ.

## 11. Key takeaway

* Partial index hữu ích khi workload tập trung vào một subset ổn định của bảng.
* Index design phải dựa trên query + distribution, không chỉ schema.
* Luôn xác minh bằng actual plan và production-like data.

# 4. Azure Cosmos DB partitioning: chọn partition key để tránh hot partition và RU bottleneck

## 1. What is it?

Cosmos DB phân phối dữ liệu và throughput qua logical/physical partitions. Partition key quyết định dữ liệu nào được colocate và cách requests được phân phối.

Một partition key tốt cần cân bằng hai mục tiêu:

```text
locality cho queries/transactions
             +
phân phối đều storage và request load
```

## 2. Why does it exist?

Distributed database không thể scale vô hạn nếu mọi request dồn vào một partition. Dù container có tổng RU/s cao, một hot logical key vẫn có thể trở thành bottleneck vì physical partition có giới hạn riêng.

## 3. How does it work?

Nếu chọn `/tenantId`, toàn bộ dữ liệu của một tenant nằm cùng logical partition key value. Điều này rất tốt cho tenant-scoped queries, nhưng một “mega tenant” có thể tạo hotspot.

Nếu chọn key cardinality rất cao như `/id`, distribution tốt nhưng nhiều query nghiệp vụ phải fan-out cross-partition và multi-item transactional scope bị hạn chế.

## 4. Practical implementation

Bắt đầu từ access patterns:

```text
Commands: theo entity nào?
Queries: thường scope theo tenant/user/device nào?
Growth: key nào có thể trở thành rất lớn?
Traffic: key nào có burst không cân đối?
TransactionalBatch: cần atomic trong partition nào?
```

Ví dụ telemetry có thể dùng synthetic key:

```text
partitionKey = deviceId + ':' + yyyyMM
```

nhằm tránh một device cực nóng tích tụ mãi trong một logical partition, nhưng đổi lại query toàn lịch sử device phải đọc nhiều partitions.

## 5. Real production scenario

Một SaaS chọn `tenantId` vì domain tự nhiên theo tenant. Sau khi onboard enterprise customer chiếm 40% traffic, throttling `429` xuất hiện chỉ cho tenant này dù tổng container RU chưa dùng hết. Root cause không phải “Cosmos thiếu RU” mà là traffic skew vào hot partition range.

## 6. Failure scenario & troubleshooting

**Symptom** → `429 Too Many Requests` tăng nhưng overall RU utilization nhìn không quá cao.

**Evidence** → metrics cho thấy request/normalized RU tập trung vào vài partition key ranges.

**Hypothesis** → hot partition do skewed key hoặc hot item.

**Diagnosis** → phân tích RU theo partition key, top tenants/items, query fan-out và payload size.

**Fix** → giảm hot writes, cache/read model, redesign/synthetic partition key khi cần; migration partition strategy phải được lập kế hoạch vì key không phải field có thể đổi tùy tiện trên existing items.

**Verification** → load test với skewed traffic giống production, không chỉ uniform random load.

## 7. Common mistakes

* Chọn low-cardinality key như `status` hoặc `country` mà không tính skew.
* Chỉ tối ưu storage distribution, bỏ qua request distribution.
* Chọn `/id` rồi mọi business query cross-partition.
* Giả định tăng RU luôn chữa được hotspot.
* Không tính growth của một logical key trong nhiều năm.

## 8. Alternatives

Relational database có sharding strategy khác nếu transactional/query model phù hợp hơn. Azure SQL/PostgreSQL có thể đơn giản hơn khi joins và relational integrity là trọng tâm. Trong Cosmos, materialized read models hoặc duplicate data đôi khi hợp lý để tránh cross-partition queries.

## 9. Trade-offs

### Advantages

* Key tốt cho phép horizontal scale hiệu quả.
* Có locality cho tenant/entity-centric operations.

### Costs / Risks

* Quyết định partition key có chi phí thay đổi rất cao.
* Locality và distribution thường xung đột.
* Synthetic keys làm query model phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key không chỉ là field bắt buộc khi insert.

### Middle

Biết tránh low-cardinality key và query cross-partition vô ý.

### Senior

Phân tích RU, skew, growth, transactional boundary và migration impact.

### Technical Lead / Architect

Chọn partition strategy dựa trên tenant model, SLO, growth forecast và operational telemetry; yêu cầu skewed-load test trước production.

## 11. Key takeaway

* Partition key là quyết định kiến trúc về scale và locality.
* Hot partition có thể tồn tại ngay cả khi tổng RU còn dư.
* Hãy model theo traffic distribution thật, không theo dataset trung bình.

# 5. Saga orchestration vs choreography: quản lý transaction phân tán bằng compensation thay vì giả vờ có ACID xuyên service

## 1. What is it?

Saga là chuỗi local transactions giữa nhiều services, trong đó mỗi bước commit riêng và failure được xử lý bằng compensating actions hoặc forward recovery.

Ví dụ checkout:

```text
Create Order
  → Reserve Inventory
  → Authorize Payment
  → Arrange Shipment
```

Nếu shipment thất bại, hệ thống có thể release inventory và void payment thay vì rollback một database transaction toàn cục.

## 2. Why does it exist?

Microservices sở hữu databases riêng. Giữ distributed ACID transaction xuyên HTTP/message boundaries thường làm coupling, latency và failure semantics rất khó quản lý. Saga chấp nhận intermediate states và biến recovery thành một phần explicit của workflow.

## 3. How does it work?

**Orchestration** có coordinator quyết định bước tiếp theo:

```text
OrderSaga → Inventory → Payment → Shipping
```

**Choreography** để services phản ứng với events:

```text
OrderCreated
  → InventoryReserved
      → PaymentAuthorized
          → ShipmentRequested
```

Orchestration dễ nhìn workflow tổng thể; choreography giảm central coordinator nhưng dễ tạo event chain khó truy vết nếu lạm dụng.

## 4. Practical implementation

Saga state cần persistence:

```csharp
public sealed record CheckoutSagaState(
    Guid OrderId,
    bool InventoryReserved,
    bool PaymentAuthorized,
    bool ShipmentRequested,
    string Status);
```

Mỗi command/event handler phải idempotent. Outbox/inbox patterns giúp tránh khoảng trống giữa database commit và message publish/consume.

Compensation phải có semantics rõ:

```text
ReserveInventory -> ReleaseInventory
AuthorizePayment -> VoidAuthorization
CapturePayment   -> RefundPayment
```

## 5. Real production scenario

Payment đã authorize nhưng inventory service timeout. Nếu hệ thống chỉ trả “checkout failed” và bỏ state, authorization có thể treo tới khi expire. Saga persisted state cho phép retry inventory nếu uncertainty, hoặc void payment nếu business deadline vượt quá.

## 6. Failure scenario & troubleshooting

**Symptom** → order ở `Processing` hàng giờ, một số steps đã chạy nhưng workflow không tiến.

**Evidence** → message duplicate/out-of-order hoặc saga state không có transition tương ứng.

**Hypothesis** → missing idempotency, poison message, lost publish hoặc state-machine gap.

**Diagnosis** → correlate bằng `OrderId/SagaId`, xem persisted saga transitions, outbox/inbox records và dependency traces.

**Fix** → deterministic transition, timeout event, idempotent handler, manual recovery command cho irrecoverable cases.

**Verification** → chaos test kill process giữa từng commit/publish boundary.

## 7. Common mistakes

* Gọi compensation là “rollback” dù side effect ngoài đời không thể đảo hoàn toàn.
* Không persist workflow state.
* Choreography đến mức không ai biết ai sở hữu business process.
* Không có timeout/recovery cho stuck saga.
* Retry payment commands không có idempotency key.

## 8. Alternatives

Single database transaction tốt hơn nếu boundary thực sự nằm trong một service/modular monolith. Two-phase commit phù hợp rất ít môi trường và làm availability/coupling phức tạp. Workflow engines có thể cung cấp durable execution cho long-running processes.

## 9. Trade-offs

### Advantages

* Phù hợp distributed ownership.
* Recovery explicit và audit được.
* Không cần giữ global transaction dài.

### Costs / Risks

* Eventual consistency.
* Compensation phức tạp.
* Nhiều intermediate states.
* Testing/observability khó hơn local transaction.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu local transaction khác distributed workflow.

### Middle

Viết idempotent consumers và compensation handlers.

### Senior

Thiết kế state machine, timeout, outbox/inbox và recovery paths.

### Technical Lead / Architect

Quyết định khi nào thật sự cần service split; chọn orchestration/choreography dựa trên business ownership và operability.

## 11. Key takeaway

* Saga không tạo ACID xuyên services; nó quản lý inconsistency có kiểm soát.
* Compensation là business operation, không phải technical undo.
* Durable state + idempotency + observability là ba nền tảng của saga đáng tin cậy.

# 6. Azure Service Bus sessions: ordering, state và scale-out cho message streams cần xử lý tuần tự

## 1. What is it?

Service Bus sessions nhóm messages theo `SessionId` để một consumer giữ exclusive session lock và xử lý messages của cùng session theo thứ tự nhận trong session.

Ví dụ:

```text
SessionId = Order-42
  Created
  PaymentAuthorized
  Shipped
```

Nhiều sessions vẫn có thể được xử lý song song bởi nhiều consumers.

## 2. Why does it exist?

Một queue bình thường scale bằng competing consumers. Điều đó tốt cho throughput nhưng không bảo đảm cùng một business stream luôn được xử lý tuần tự bởi một consumer. Với state transitions phụ thuộc thứ tự, parallel processing có thể gây invalid state.

## 3. How does it work?

Producer gán cùng `SessionId` cho messages thuộc cùng ordering scope. Receiver chấp nhận một session, giữ session lock và xử lý các messages của session đó. Khi session được release, receiver khác mới tiếp quản.

Ordering boundary phải nhỏ vừa đủ. `SessionId = TenantId` có thể serialize cả tenant lớn và phá throughput; `SessionId = OrderId` thường granular hơn nếu ordering chỉ cần per order.

## 4. Practical implementation

Producer:

```csharp
var message = new ServiceBusMessage(BinaryData.FromObjectAsJson(evt))
{
    SessionId = evt.OrderId.ToString(),
    MessageId = evt.EventId.ToString()
};

await sender.SendMessageAsync(message, ct);
```

Consumer vẫn cần idempotency dựa trên `MessageId` hoặc business event ID. Session ordering không loại bỏ duplicate delivery semantics.

## 5. Real production scenario

Order service phát `OrderCreated`, `OrderCancelled`, `RefundRequested`. Không có sessions, consumers scale-out và `RefundRequested` đôi khi được xử lý trước `OrderCancelled`, khiến state transition fail. Session theo `OrderId` giữ sequence per order trong khi hàng nghìn orders khác vẫn chạy song song.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog lớn dù CPU consumer thấp.

**Evidence** → một vài sessions có rất nhiều messages hoặc session handler giữ lock lâu.

**Hypothesis** → session key quá coarse hoặc poison message block progression trong hot session.

**Diagnosis** → metrics active sessions/backlog, processing duration, session lock loss, dead-letter reason và distribution của `SessionId`.

**Fix** → chọn ordering boundary nhỏ hơn khi domain cho phép, giới hạn handler duration, dead-letter poison messages và giữ external calls bounded.

**Verification** → load test với skewed sessions, không chỉ hàng triệu unique IDs đồng đều.

## 7. Common mistakes

* Dùng sessions chỉ vì muốn “reliable messaging”.
* Gán một `SessionId` duy nhất cho toàn queue.
* Nghĩ ordering đồng nghĩa exactly-once.
* Handler chạy quá lâu làm mất session lock.
* Không có strategy cho stuck/poison message.

## 8. Alternatives

Partitioned streams như Kafka/Event Hubs phù hợp ordered event streams lớn. Optimistic state transitions có thể chịu out-of-order bằng version checks. Một orchestrator có thể serialize commands theo aggregate nếu workflow ownership rõ hơn.

## 9. Trade-offs

### Advantages

* Ordering theo business key.
* Vẫn scale song song giữa sessions.
* Hữu ích cho stateful workflows.

### Costs / Risks

* Hot session giới hạn throughput.
* Lock/session lifecycle tăng operational complexity.
* Duplicate handling vẫn bắt buộc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue order không tự đồng nghĩa business ordering khi có nhiều consumers.

### Middle

Biết set `SessionId`, lock handling và idempotency.

### Senior

Thiết kế session granularity, throughput và poison-message recovery.

### Technical Lead / Architect

Chọn messaging primitive theo ordering scope, throughput target và replay/recovery requirements.

## 11. Key takeaway

* Sessions cung cấp ordering theo một key, không phải global exactly-once.
* Session key chính là concurrency boundary.
* Hãy test skew và stuck-session behavior trước khi gọi thiết kế là scalable.

# 7. Kubernetes startup/readiness/liveness probes: phân biệt “đã khởi động”, “sẵn sàng nhận traffic” và “đang sống”

## 1. What is it?

Kubernetes có ba loại health probe với mục đích khác nhau:

* **startupProbe**: application đã khởi động xong chưa?
* **readinessProbe**: pod có nên nhận traffic lúc này không?
* **livenessProbe**: process có bị mắc kẹt đến mức cần restart không?

Dùng cùng một `/health` cho mọi probe mà không hiểu semantics có thể gây self-inflicted outage.

## 2. Why does it exist?

Một process có thể còn sống nhưng chưa sẵn sàng vì đang warm cache. Nó cũng có thể sẵn sàng lúc đầu rồi mất dependency tạm thời. Restart process vì database timeout 10 giây thường làm tình hình tệ hơn; remove pod khỏi traffic có thể hợp lý hơn.

## 3. How does it work?

Kubelet thực hiện probes định kỳ. Readiness failure loại pod khỏi Service endpoints nhưng không nhất thiết restart. Liveness failure có thể restart container. Startup probe bảo vệ app khởi động chậm khỏi bị liveness giết trước khi nó có cơ hội ready.

## 4. Practical implementation

ASP.NET Core có thể tách checks:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<StartupStateCheck>("startup", tags: ["startup"])
    .AddCheck<DatabaseReadinessCheck>("db", tags: ["ready"]);

app.MapHealthChecks("/health/startup", new()
{
    Predicate = x => x.Tags.Contains("startup")
});

app.MapHealthChecks("/health/ready", new()
{
    Predicate = x => x.Tags.Contains("ready")
});

app.MapGet("/health/live", () => Results.Ok());
```

Liveness endpoint thường không nên phụ thuộc trực tiếp vào mọi external service; nếu database outage làm tất cả pods restart cùng lúc, recovery có thể chậm hơn.

## 5. Real production scenario

Một API có liveness check gọi SQL. Khi SQL failover kéo dài 20 giây, mọi pod cùng fail liveness và restart. Sau restart, connection pools cold, startup migrations/checks tăng tải đúng lúc database đang hồi phục. Một dependency blip biến thành multi-minute outage.

## 6. Failure scenario & troubleshooting

**Symptom** → pods liên tục `CrashLoopBackOff` hoặc restart trong khi application logs chỉ có dependency timeout.

**Evidence** → Kubernetes events ghi liveness probe failures ngay trước restart.

**Hypothesis** → liveness đang kiểm tra dependency/transient condition thay vì process health.

**Diagnosis** → inspect probe definitions, timeout/failureThreshold và health endpoint dependencies.

**Fix** → chuyển dependency availability sang readiness nếu phù hợp; giữ liveness cho deadlock/hung-process signals; thêm startup probe cho cold start dài.

**Verification** → chaos test database/network outage và xác nhận pods rời traffic nhưng không tạo restart storm.

## 7. Common mistakes

* Một endpoint cho cả ba probe với cùng dependencies.
* Probe timeout quá ngắn hơn normal latency variance.
* Liveness gọi nhiều downstream APIs.
* Readiness luôn trả 200 dù app không thể phục vụ request cốt lõi.
* Startup probe window ngắn hơn worst-case startup hợp lệ.

## 8. Alternatives

Application-level graceful degradation có thể vẫn giữ readiness khi optional dependency fail. External synthetic monitoring kiểm tra end-to-end availability nhưng không thay thế pod probes. Process supervisors không hiểu service routing như Kubernetes readiness.

## 9. Trade-offs

### Advantages

* Tách lifecycle states rõ ràng.
* Tự động traffic draining/recovery tốt hơn.
* Giảm false restart nếu thiết kế đúng.

### Costs / Risks

* Health model phải phản ánh dependency criticality.
* Probe sai có thể trực tiếp gây outage.
* Quá nhiều expensive checks tạo tải nền.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt readiness với liveness.

### Middle

Cấu hình endpoints, thresholds và startup behavior.

### Senior

Model critical vs optional dependencies, degradation và failure amplification.

### Technical Lead / Architect

Chuẩn hóa probe contract/SLO và chaos-test health behavior như một phần release readiness.

## 11. Key takeaway

* Liveness hỏi “có cần restart process không?”, không hỏi “mọi dependency có healthy không?”.
* Readiness là traffic-routing decision.
* Probe configuration là resilience code dưới dạng infrastructure configuration.

# 8. SQL deadlock troubleshooting: wait-for graph, lock ordering và vì sao retry chỉ là lớp bảo hiểm cuối

## 1. What is it?

Deadlock xảy ra khi hai hoặc nhiều transactions giữ resources mà transaction khác cần và tạo vòng chờ:

```text
T1 giữ A → chờ B
T2 giữ B → chờ A
```

Database engine phát hiện cycle và chọn một victim để rollback, phá vòng chờ.

## 2. Why does it exist?

Concurrency cho phép throughput cao nhưng resource acquisition order không nhất quán có thể tạo cycles. Deadlock không nhất thiết nghĩa database “quá tải”; nó thường là interaction cụ thể giữa transaction shape, lock order, indexes và isolation level.

## 3. How does it work?

Ví dụ:

```text
Transaction A: UPDATE Accounts ...; UPDATE Ledger ...
Transaction B: UPDATE Ledger ...; UPDATE Accounts ...
```

Nếu hai transactions chạm cùng logical entities theo thứ tự ngược nhau, cycle có thể xảy ra. Missing index còn có thể khiến statement lock nhiều rows/pages hơn dự kiến, tăng deadlock surface.

## 4. Practical implementation

Khi điều tra, lấy deadlock graph/event thay vì đoán từ exception text. Xác định:

```text
victim
processes
resources/keys/pages
lock modes
statements
transaction order
```

Sau đó sửa root cause: nhất quán access order, rút ngắn transaction, thêm index phù hợp hoặc giảm lock scope khi semantics cho phép.

Retry có bounded backoff cho known deadlock victim là hợp lý vì một transaction đã bị rollback hoàn toàn:

```csharp
// Pseudocode: chỉ retry operation idempotent/re-runnable,
// với giới hạn nhỏ và telemetry rõ ràng.
```

## 5. Real production scenario

Checkout flow update `Inventory` rồi `Order`; reconciliation worker update `Order` rồi `Inventory`. Dưới load thấp không thấy vấn đề. Peak traffic tạo deadlocks liên tục. Thêm retry giảm error rate nhưng latency tail tăng và DB load cao hơn. Root fix là thống nhất lock acquisition order và rút ngắn transaction.

## 6. Failure scenario & troubleshooting

**Symptom** → intermittent SQL deadlock exceptions, thường tăng khi traffic cao.

**Evidence** → deadlock graphs lặp cùng hai stored procedures/statements.

**Hypothesis** → deterministic lock-order inversion.

**Diagnosis** → map resources trong graph về indexes/tables/business operations; so sánh statement order.

**Fix** → enforce consistent order, tối ưu query/index và giảm transaction duration.

**Verification** → concurrency load test tái tạo pattern cũ; theo dõi deadlock rate về gần zero, không chỉ application retry success.

## 7. Common mistakes

* Chỉ tăng retry count.
* Dùng `NOLOCK` như deadlock thuốc chữa chung.
* Không lấy deadlock graph.
* Transaction chứa HTTP calls/user think-time.
* Access entities theo random/unordered collection khiến lock order thay đổi.

## 8. Alternatives

Snapshot-based isolation có thể giảm reader/writer blocking nhưng không loại bỏ mọi writer/writer deadlock. Queue/serialized processing phù hợp hotspot rất cao. Optimistic concurrency giải quyết lost update nhưng khác deadlock prevention.

## 9. Trade-offs

### Advantages

* Root-cause fix giảm latency tail và wasted work.
* Giảm pressure từ retries.
* Hành vi predictable hơn.

### Costs / Risks

* Cần production evidence và concurrency reproduction.
* Index/isolation changes có side effects khác.
* Không phải mọi deadlock đều cùng pattern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deadlock khác timeout và blocking dài.

### Middle

Đọc basic deadlock graph và biết bounded retry.

### Senior

Map graph về transaction design, lock order và indexing.

### Technical Lead / Architect

Thiết kế data-access conventions, transaction boundaries và observability để deadlock không trở thành “random DB error”.

## 11. Key takeaway

* Deadlock là cycle cụ thể; cần evidence cụ thể.
* Retry bảo vệ availability nhưng không thay root-cause fix.
* Consistent lock ordering và transaction ngắn là hai biện pháp mạnh nhất.

# 9. Contract testing cho service integration: bắt API incompatibility trước production mà không phụ thuộc full end-to-end environment

## 1. What is it?

Contract testing kiểm tra agreement giữa service consumer và provider: endpoint, payload shape, status semantics, headers hoặc message schema mà consumer thực sự phụ thuộc.

Nó nằm giữa unit test và full end-to-end test:

```text
Unit test → component correctness
Contract test → integration compatibility
E2E → whole workflow/environment
```

## 2. Why does it exist?

Hai services có thể pass toàn bộ unit tests nhưng vẫn fail khi provider rename field, đổi nullability hoặc thay status code. Full E2E tests thường chậm, flaky và khó chạy cho mọi commit. Contract tests tập trung đúng compatibility boundary.

## 3. How does it work?

Có hai hướng phổ biến:

* **schema/provider contract**: provider publish OpenAPI/AsyncAPI/schema và consumers validate.
* **consumer-driven contract**: consumer ghi rõ interactions cần; provider verify contracts trong pipeline của mình.

Contract không nên chỉ kiểm tra JSON deserialize; status codes, required headers, error shapes và semantics cũng có thể quan trọng.

## 4. Practical implementation

Ví dụ consumer phụ thuộc:

```json
{
  "id": "P-100",
  "available": true,
  "quantity": 12
}
```

Contract test phải thể hiện field nào required và consumer xử lý optional/additive fields ra sao. Provider CI verify rằng version mới vẫn đáp ứng contract trước deploy.

Với OpenAPI, pipeline có thể diff breaking changes và chạy generated/client compatibility tests; với messaging cần schema compatibility rules tương ứng.

## 5. Real production scenario

Inventory API đổi `quantity` từ non-null integer sang nullable vì một nguồn dữ liệu mới chưa biết stock. Provider tests pass. Orders client dùng `int` non-nullable và logic `quantity > 0`. Contract verification phát hiện breaking assumption trước khi provider release.

## 6. Failure scenario & troubleshooting

**Symptom** → contract suite pass nhưng production consumer vẫn fail.

**Evidence** → failure nằm ở authentication header, timeout/error semantics hoặc data invariant không được mô tả trong contract.

**Hypothesis** → contract quá structural, không capture behavior consumer dựa vào.

**Diagnosis** → trace actual request/response và so với assertions trong contract.

**Fix** → thêm meaningful interaction/semantic assertions; tránh biến contract thành copy toàn implementation.

**Verification** → tái hiện exact breaking change và xác nhận provider CI fail trước deployment.

## 7. Common mistakes

* Snapshot toàn response rồi gọi đó là contract.
* Contract quá chặt với fields consumer không dùng, làm mọi additive change trở thành failure.
* Chỉ test happy path.
* Không version/deprecate contract.
* Nghĩ contract tests thay thế integration/E2E tests hoàn toàn.

## 8. Alternatives

OpenAPI schema validation đơn giản hơn nếu organization có strong API governance. Integration tests với real provider phù hợp critical paths nhưng tốn environment. Backward-compatible versioning discipline vẫn cần dù có contract testing.

## 9. Trade-offs

### Advantages

* Feedback sớm về breaking changes.
* Tests nhanh và ownership rõ hơn E2E-only strategy.
* Consumer dependencies trở nên explicit.

### Costs / Risks

* Contract lifecycle cần governance.
* Có thể tạo false coupling nếu assert quá nhiều.
* Không chứng minh network, auth, deployment và real data đều đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu compatibility không chỉ là compile success.

### Middle

Viết contract cho request/response/error cases consumer dùng.

### Senior

Thiết kế tolerance, versioning và CI verification giữa teams.

### Technical Lead / Architect

Đặt compatibility policy, deprecation window và contract ownership cho toàn service ecosystem.

## 11. Key takeaway

* Contract tests bảo vệ boundary giữa teams/services với feedback sớm.
* Assert consumer-relevant semantics, không snapshot mọi byte.
* Đây là một lớp trong test pyramid, không phải thay thế mọi integration test.

# 10. Optimizely CMS content caching: cache correctness, invalidation và cách tránh biến CMS thành nguồn stale content khó chẩn đoán

Trong Optimizely CMS, content thường được đọc rất nhiều lần nhưng publish/change ít hơn. Caching giúp tránh lặp lại storage/provider work trên mỗi request. Editor publishes content

```text
content state changes
      ↓
invalidation / dependency propagation
      ↓
next read sees current published content
```

```text
homepage-render-model
```

là quá thô nếu output phụ thuộc language, market, personalization hoặc nhiều referenced contents.

Key có thể cần context:

```text
home:{contentReference}:{language}:{market}
```

3. Liệt kê dependencies của derived result.
4. Invalidate khi content/reference/config liên quan đổi.
5. Tách preview/edit behavior khỏi published visitor cache khi cần.

**Diagnosis** → trace cache key, instance, content references, language và publish event; so sánh raw content với derived model.

**Fix** → loại custom cache nếu không cần, hoặc gắn invalidation vào đúng content dependencies và topology; tránh chỉ dựa TTL dài.

**Verification** → publish/update/delete/move content trong multi-instance test và xác nhận visible output đổi đúng sau propagation window mong đợi.

* Cache lại dữ liệu mà CMS đã cache tốt.
* Cache `IContent`/derived view model bằng key không có language/context.
* TTL dài thay cho invalidation.
* Không test multi-instance environment.
* Preview/editor mode dùng chung cached output với anonymous visitors.
* Cache personalized output bằng key chung.

## 8. Alternatives

Output/response caching phù hợp pages hoặc fragments có semantics rõ. CDN caching tốt cho public static/semi-static responses nhưng cần purge/vary policy. Precomputed navigation/read model phù hợp site cực lớn nếu build/invalidation pipeline rõ ràng.

## 9. Trade-offs

### Advantages

* Giảm repeated content resolution và rendering cost.
* Cải thiện latency cho read-heavy sites.

### Costs / Risks

* Stale content là correctness bug, không chỉ performance issue.
* Context dimensions làm cache key explosion.
* Multi-instance invalidation khó hơn local development.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết ưu tiên CMS APIs và không thêm cache chỉ vì thấy read operation.

### Middle

Hiểu cache key, TTL, language/context và preview differences.

### Senior

Thiết kế dependency invalidation, multi-instance behavior và đo hit ratio/latency.

### Technical Lead / Architect

Đặt caching strategy xuyên CMS → application → reverse proxy/CDN, với ownership và freshness SLO rõ ràng.

## 11. Key takeaway

* CMS caching phải bảo vệ correctness trước rồi mới tối ưu latency.
* Custom cache cần hiểu content dependencies, language/context và multi-instance invalidation.
* Nếu không chứng minh custom cache tạo giá trị bằng profiling, framework-managed behavior thường là lựa chọn an toàn hơn.
