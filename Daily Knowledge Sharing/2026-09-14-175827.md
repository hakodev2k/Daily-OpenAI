# 1. C# `IDisposable`, finalizer và `SafeHandle`: quản lý unmanaged resources mà không biến GC thành cơ chế cleanup chính

## 1. What is it?

`IDisposable` là contract cho deterministic cleanup: caller chủ động giải phóng resource ngay khi không còn cần. Finalizer là safety net do GC gọi không xác định thời điểm trước khi object bị thu hồi. `SafeHandle` là abstraction của .NET để bọc native handle an toàn hơn so với tự viết finalizer trực tiếp.

Mental model nên là:

```text
Managed object
   │
   ├─ managed memory → GC xử lý
   │
   └─ unmanaged resource → phải release chủ động
                         │
                         ├─ Dispose / using: đường chính
                         └─ Finalizer/SafeHandle: safety net
```

GC quản lý managed memory, không hiểu semantic của file descriptor, socket handle, native memory, database native handle hoặc OS resource khác.

## 2. Why does it exist?

Unmanaged resource thường có giới hạn hệ thống và cần được release sớm. Nếu chờ GC:

* file vẫn bị lock,
* socket/file descriptor tiếp tục chiếm tài nguyên,
* native memory không được trả kịp,
* process có thể cạn handle dù managed heap chưa lớn,
* cleanup latency phụ thuộc GC pressure thay vì business lifetime.

Do đó deterministic cleanup tồn tại để resource lifetime bám theo scope logic, không bám theo thời điểm GC tình cờ chạy.

## 3. How does it work?

Pattern phổ biến:

```csharp
using var stream = File.OpenRead(path);
```

compiler chuyển thành `try/finally` tương đương để đảm bảo `Dispose()` được gọi cả khi exception xảy ra.

Với `IAsyncDisposable`:

```csharp
await using var resource = await CreateAsyncResource();
```

cho phép cleanup có asynchronous I/O.

Nếu class thật sự sở hữu native handle, nên ưu tiên `SafeHandle` thay vì tự giữ `IntPtr` + finalizer vì `SafeHandle` tích hợp tốt với CLR lifetime semantics.

## 4. Practical implementation

Ví dụ wrapper native handle:

```csharp
using Microsoft.Win32.SafeHandles;
using System.Runtime.InteropServices;

public sealed class NativeSessionHandle : SafeHandleZeroOrMinusOneIsInvalid
{
    private NativeSessionHandle() : base(ownsHandle: true) { }

    protected override bool ReleaseHandle()
        => NativeMethods.CloseSession(handle);
}

internal static class NativeMethods
{
    [DllImport("native-lib")]
    internal static extern bool CloseSession(IntPtr handle);
}
```

Class business dùng `NativeSessionHandle` có thể dispose handle mà không cần tự viết finalizer phức tạp.

## 5. Real production scenario

Một service xử lý image dùng native codec. Managed memory nhìn bình thường, nhưng sau vài giờ production bắt đầu mở file thất bại. Investigation cho thấy native handles không được release trên exception path.

Thêm `using` đúng scope và wrapper `SafeHandle` làm số handle ổn định trở lại. Vấn đề không phải “memory leak” theo nghĩa managed heap mà là unmanaged resource leak.

## 6. Failure scenario & troubleshooting

**Symptom** → process handle count tăng liên tục, file bị lock hoặc native allocation tăng dù GC vẫn chạy.

**Evidence** → managed heap snapshot không tương xứng với process private bytes/handle count.

**Hypothesis** → resource có ownership nhưng không được dispose.

**Diagnosis** → trace creation/disposal path, kiểm tra exception/cancellation path, dùng OS/process diagnostics để đo handle count.

**Fix** → xác định owner, áp dụng `using`/`await using`, dùng `SafeHandle` cho native handle.

**Verification** → stress test nhiều vòng và xác nhận handle/native memory quay về baseline.

## 7. Common mistakes

* Nghĩ GC sẽ tự đóng file/socket “sớm”.
* Gọi `Dispose` ở nhiều owner khác nhau gây double-dispose semantics khó đoán.
* Giữ disposable trong Singleton nhưng không nghĩ tới lifetime process.
* Tự viết finalizer dù có thể dùng `SafeHandle`.
* Dispose object do DI container sở hữu ngay trong consumer.
* Quên `await using` với resource cleanup bất đồng bộ.

## 8. Alternatives

* Pure managed object không giữ resource thì không cần `IDisposable`.
* `SafeHandle` nên ưu tiên cho native handles.
* Object pool có thể reuse resource đắt tiền, nhưng ownership/lifetime phức tạp hơn.
* DI container có thể quản lý disposal cho services do container tạo.

## 9. Trade-offs

### Advantages

* Release resource đúng lifetime.
* Giảm phụ thuộc vào GC timing.
* `SafeHandle` giảm lỗi finalizer/native handle ownership.

### Costs / Risks

* Ownership convention phải rõ.
* Dispose sai owner có thể làm resource bị đóng quá sớm.
* Finalizer làm object sống lâu hơn qua GC generations và tăng GC cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu managed memory và unmanaged resource là hai vấn đề khác nhau; biết dùng `using`.

### Middle

Thiết kế scope disposal đúng trên success, exception và cancellation path.

### Senior

Phân tích handle leak, native memory, DI ownership và `IAsyncDisposable` semantics.

### Technical Lead / Architect

Đặt convention ownership cho resource wrappers và quyết định khi nào cần pooling, `SafeHandle` hoặc abstraction khác.

## 11. Key takeaway

* GC không thay thế deterministic resource cleanup.
* `Dispose` là đường chính; finalizer chỉ là safety net.
* Với native handle, ưu tiên `SafeHandle` hơn tự viết finalizer.

# 2. ASP.NET Core request timeout và deadline propagation: giới hạn work theo ngân sách thời gian thay vì để dependency chậm giữ tài nguyên vô hạn

## 1. What is it?

Request timeout là giới hạn thời gian một request được phép tiêu tốn trước khi application ngừng work. Deadline propagation là việc truyền ngân sách thời gian còn lại xuống các dependency thay vì mỗi tầng tự chọn timeout độc lập.

Mental model:

```text
Client deadline: 2s
   ↓
API còn 1.8s
   ↓
Database / HTTP dependency chỉ nên dùng phần ngân sách còn lại
```

Timeout không chỉ để “trả lỗi sớm”; nó là cơ chế bảo vệ tài nguyên và chặn failure propagation.

## 2. Why does it exist?

Nếu một downstream API treo 30 giây trong khi client chỉ chờ 3 giây, server vẫn giữ:

* request slot,
* database connection,
* HTTP connection,
* memory buffer,
* worker/concurrency budget.

Khi traffic tăng, một dependency chậm có thể gây queueing, connection pool exhaustion và cascading failure.

## 3. How does it work?

ASP.NET Core có request cancellation khi client disconnect và có thể áp dụng request timeout policy. Application nên combine token request với timeout/deadline của operation.

Một dependency call cần nhận `CancellationToken`:

```csharp
await httpClient.SendAsync(request, cancellationToken);
```

Nếu tầng dưới không tôn trọng token, deadline propagation bị gãy.

## 4. Practical implementation

Ví dụ endpoint với timeout policy:

```csharp
builder.Services.AddRequestTimeouts(options =>
{
    options.AddPolicy("api-default", TimeSpan.FromSeconds(3));
});

var app = builder.Build();
app.UseRequestTimeouts();

app.MapGet("/orders/{id}", async (
    Guid id,
    OrderService service,
    CancellationToken ct) =>
{
    var order = await service.GetAsync(id, ct);
    return order is null ? Results.NotFound() : Results.Ok(order);
})
.WithRequestTimeout("api-default");
```

Ở HTTP client, đặt timeout phù hợp với budget tổng; tránh để dependency timeout dài hơn request deadline.

## 5. Real production scenario

Order API có SLA 2 giây nhưng payment dependency timeout 30 giây. Khi payment service chậm, request từ client đã bỏ cuộc từ lâu nhưng backend vẫn giữ outbound connection và work.

Sau khi đặt request deadline và propagate cancellation, số request “zombie” giảm rõ rệt và recovery nhanh hơn khi dependency outage.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 tăng, request timeout hàng loạt và outbound connection pool đầy.

**Evidence** → dependency duration cao hơn client/request deadline.

**Hypothesis** → timeout budget không nhất quán hoặc cancellation không propagate.

**Diagnosis** → distributed trace xem từng span duration, kiểm tra token có đi qua repository/HTTP client hay không.

**Fix** → thiết kế end-to-end timeout budget, propagate token, giới hạn retry bên trong deadline.

**Verification** → inject dependency latency và xác nhận request dừng gần deadline, tài nguyên được release.

## 7. Common mistakes

* Mỗi dependency đặt timeout 30 giây rồi gọi tuần tự ba dependency trong request SLA 5 giây.
* Retry ba lần mà mỗi attempt dùng nguyên timeout ban đầu.
* Catch `OperationCanceledException` rồi tiếp tục work.
* Không truyền `CancellationToken` xuống EF Core hoặc `HttpClient`.
* Nhầm timeout với retry strategy.

## 8. Alternatives

* Queue asynchronous work nếu operation không cần đồng bộ với client.
* Circuit Breaker để fail fast khi dependency đang unhealthy.
* Bulkhead để giới hạn concurrency vào dependency chậm.
* Client polling hoặc webhook cho long-running operation.

## 9. Trade-offs

### Advantages

* Chặn resource retention quá lâu.
* Giảm cascading failure.
* Làm latency budget explicit.

### Costs / Risks

* Timeout quá ngắn tạo false failures.
* Cancellation có thể đến sau side effect đã xảy ra.
* Cần thiết kế idempotency nếu client retry sau timeout.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout là giới hạn thời gian operation.

### Middle

Truyền `CancellationToken` xuyên suốt call chain.

### Senior

Thiết kế retry + timeout budget và hiểu side-effect semantics sau cancellation.

### Technical Lead / Architect

Định nghĩa latency SLO, deadline giữa service boundaries và degradation strategy.

## 11. Key takeaway

* Timeout phải được thiết kế end-to-end, không độc lập từng tầng.
* Cancellation chỉ hữu ích khi mọi layer thực sự tôn trọng nó.
* Retry phải nằm trong cùng latency budget.

# 3. EF Core interceptors và query diagnostics: quan sát database behavior ở đúng boundary mà không rải logging thủ công khắp repository

## 1. What is it?

EF Core interceptors cho phép hook vào lifecycle của database commands, connections, transactions hoặc `SaveChanges` để quan sát hoặc can thiệp có kiểm soát.

Mental model:

```text
Application LINQ
   ↓
EF Core pipeline
   ↓  ← interceptor quan sát command/transaction/save
ADO.NET provider
   ↓
Database
```

Interceptor khác business repository logging ở chỗ nó nhìn thấy behavior thực tế sau khi EF đã translate thành command.

## 2. Why does it exist?

Nhiều production issue nằm dưới LINQ abstraction:

* query chạy quá lâu,
* command bị gọi quá nhiều lần,
* transaction mở lâu,
* N+1 xuất hiện,
* audit metadata cần set nhất quán.

Nếu mỗi repository tự log, coverage không đồng nhất và dễ bỏ sót code path.

## 3. How does it work?

Các interceptor như `DbCommandInterceptor` nhận callback trước/sau command execution. `SaveChangesInterceptor` nhận lifecycle của save operation.

Quan trọng: interceptor nằm trên hot path nên chính nó phải nhẹ, deterministic và không gây recursion.

## 4. Practical implementation

Ví dụ cảnh báo query chậm:

```csharp
public sealed class SlowCommandInterceptor : DbCommandInterceptor
{
    private readonly ILogger<SlowCommandInterceptor> _logger;

    public SlowCommandInterceptor(ILogger<SlowCommandInterceptor> logger)
        => _logger = logger;

    public override ValueTask<InterceptionResult<DbDataReader>> ReaderExecutingAsync(
        DbCommand command,
        CommandEventData eventData,
        InterceptionResult<DbDataReader> result,
        CancellationToken cancellationToken = default)
    {
        // Không đo duration ở callback này; có thể dùng event data/diagnostics
        // hoặc pair start/end nếu cần custom timing.
        _logger.LogDebug("EF command: {CommandText}", command.CommandText);
        return ValueTask.FromResult(result);
    }
}
```

Đăng ký:

```csharp
options.AddInterceptors(slowCommandInterceptor);
```

Trong production, không nên log full SQL + parameters vô điều kiện vì volume và sensitive data risk.

## 5. Real production scenario

Một SaaS API tăng database QPS đột ngột sau release. Code review không thấy vòng loop query rõ ràng. Command telemetry cho thấy cùng một SQL shape được gọi hàng chục lần trong một request, dẫn tới N+1.

Interceptor/diagnostic events giúp localize vấn đề ở persistence boundary thay vì đoán từ application logs.

## 6. Failure scenario & troubleshooting

**Symptom** → logging volume tăng mạnh và request latency tăng sau khi bật diagnostics.

**Evidence** → mỗi command serialize full SQL + large parameter payload.

**Hypothesis** → observability code trên hot path quá nặng.

**Diagnosis** → so sánh CPU/allocation trước và sau interceptor, đo log ingestion volume.

**Fix** → sampling, structured metadata, slow-query threshold, redaction.

**Verification** → giữ đủ diagnostic value mà overhead nằm trong budget.

## 7. Common mistakes

* Dùng interceptor để nhét business rules vào persistence layer.
* Log secrets/PII từ parameters.
* Thực hiện network call đồng bộ trong interceptor.
* Dùng interceptor thay thế query optimization thực sự.
* Interceptor tự truy cập cùng DbContext và tạo recursion.

## 8. Alternatives

* EF Core built-in logging và `DiagnosticSource`.
* OpenTelemetry instrumentation.
* Database-native Query Store / slow-query logs.
* Explicit application logging cho business-relevant events.

## 9. Trade-offs

### Advantages

* Cross-cutting diagnostics nhất quán.
* Quan sát SQL/transaction behavior gần database boundary.
* Hữu ích cho audit kỹ thuật và performance investigation.

### Costs / Risks

* Hot-path overhead.
* Sensitive data leakage nếu log sai.
* Có thể tạo coupling ngầm nếu dùng để thay đổi behavior quá nhiều.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ cuối cùng trở thành database command.

### Middle

Biết bật EF logging và dùng interceptor cho concern phù hợp.

### Senior

Thiết kế sampling/redaction và kết hợp database evidence với application traces.

### Technical Lead / Architect

Đặt observability boundary và policy để instrumentation không trở thành hidden business layer.

## 11. Key takeaway

* Interceptor phù hợp cross-cutting persistence concerns, không phải business logic.
* Diagnostics phải có privacy và performance budget.
* SQL evidence gần database boundary thường đáng tin hơn suy đoán từ LINQ.

# 4. SQL Server connection pool exhaustion và pool fragmentation: API có thể timeout dù database CPU vẫn thấp

## 1. What is it?

ADO.NET connection pooling tái sử dụng physical database connections thay vì mở TCP/TLS/login mới cho mỗi request.

Connection pool exhaustion xảy ra khi tất cả connections trong pool đang được giữ và caller mới phải chờ connection được trả lại.

Pool fragmentation xảy ra khi nhiều connection strings khác nhau tạo nhiều pool riêng, làm tổng capacity bị chia nhỏ ngoài ý muốn.

## 2. Why does it exist?

Mở physical database connection là operation đắt. Pooling giảm latency và server overhead. Nhưng pooling chỉ hiệu quả nếu application:

* mở connection muộn,
* dùng ngắn,
* trả sớm,
* không tạo hàng loạt pool khác nhau.

## 3. How does it work?

Mỗi normalized connection string thường map vào pool riêng. Khi code gọi `Open`, provider lấy idle connection hoặc tạo mới tới giới hạn. Khi `Dispose`, connection logic được trả về pool chứ thường không đóng physical socket ngay.

```text
Request → Open()
          ↓
     Connection Pool
      ├─ busy
      ├─ busy
      └─ idle → reuse
```

Nếu không có connection rảnh, request chờ tới connection timeout.

## 4. Practical implementation

Đúng pattern:

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(ct);

await using var command = connection.CreateCommand();
command.CommandText = "SELECT ...";

await using var reader = await command.ExecuteReaderAsync(ct);
```

Scope ngắn; không giữ connection trong singleton hoặc xuyên qua network call.

Trong EF Core, `DbContext` scoped đúng request thường giúp quản lý connection lifetime hợp lý, nhưng transaction/query streaming vẫn có thể giữ connection lâu.

## 5. Real production scenario

API bắt đầu timeout sau khi thêm integration call bên trong database transaction. Database CPU chỉ 25%, nhưng connection pool active count chạm max. Mỗi request giữ transaction/connection trong lúc chờ remote API vài giây.

Root cause là connection occupancy, không phải query CPU.

## 6. Failure scenario & troubleshooting

**Symptom** → exception kiểu “timeout while obtaining a connection from the pool”, DB CPU thấp.

**Evidence** → active connections sát giới hạn, request duration tăng, transaction duration dài.

**Hypothesis** → connection leak hoặc lifetime quá dài.

**Diagnosis** → correlate active connections, request traces, long transactions và dependency calls.

**Fix** → thu hẹp connection/transaction scope, dispose đúng, giảm fragmentation, chỉ tăng pool size sau khi hiểu bottleneck.

**Verification** → load test và xác nhận active connection ổn định dưới concurrency dự kiến.

## 7. Common mistakes

* Tăng `Max Pool Size` ngay mà không sửa leak/lifetime.
* Giữ transaction khi gọi external HTTP service.
* Dynamic connection string khác nhau chỉ vì thứ tự/metadata nhỏ.
* Không dispose reader/command/connection đúng scope.
* Mở connection quá sớm ở đầu request.

## 8. Alternatives

* Queue/backpressure để giới hạn database concurrency.
* Read replicas cho workload đọc nếu bottleneck thực sự là DB capacity.
* Connection multiplexing/proxy tùy database/platform.
* Tăng pool size nếu database chịu được và occupancy là workload hợp lệ.

## 9. Trade-offs

### Advantages

* Pooling giảm connection setup cost rất lớn.
* Reuse connection tăng throughput.

### Costs / Risks

* Pool là bounded resource.
* Pool quá lớn có thể chuyển bottleneck sang database.
* Fragmentation làm capacity khó quan sát.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Dispose` trả connection về pool.

### Middle

Giữ connection/transaction scope ngắn và đo active connections.

### Senior

Phân biệt DB CPU bottleneck với pool occupancy/locking bottleneck.

### Technical Lead / Architect

Thiết kế concurrency budget giữa app instances và database capacity.

## 11. Key takeaway

* Database timeout không đồng nghĩa database CPU quá tải.
* Connection pool là shared bounded resource.
* Giảm connection hold time thường tốt hơn chỉ tăng pool size.

# 5. MongoDB Change Streams và resume token: đồng bộ thay đổi gần real-time mà vẫn phải thiết kế cho disconnect và duplicate processing

## 1. What is it?

MongoDB Change Streams cho phép application subscribe các thay đổi trên collection/database dựa trên replication log. Consumer nhận event khi document được insert, update, replace hoặc delete.

Mental model:

```text
Primary write
   ↓
Replication log
   ↓
Change Stream
   ↓
Consumer
   ↓
Search index / cache / integration
```

Nó phù hợp cho synchronization và event-like processing, không biến MongoDB thành broker đầy đủ semantics như mọi messaging system.

## 2. Why does it exist?

Polling database theo `UpdatedAt`:

* tạo query load,
* có latency theo polling interval,
* khó xử lý edge case timestamp,
* có thể miss/update duplicate nếu cursor không chắc chắn.

Change Streams cho consumer nhận thay đổi theo thứ tự log với resume capability.

## 3. How does it work?

Mỗi change event có resume token. Consumer persist token sau khi xử lý để có thể reconnect từ vị trí gần nhất.

Nếu consumer crash sau side effect nhưng trước khi persist token, event có thể được xử lý lại. Vì vậy downstream side effect vẫn nên idempotent.

## 4. Practical implementation

C# MongoDB driver:

```csharp
var options = new ChangeStreamOptions
{
    FullDocument = ChangeStreamFullDocumentOption.UpdateLookup
};

using var cursor = await collection.WatchAsync(options, cancellationToken: ct);

await cursor.ForEachAsync(change =>
{
    // Process change and persist resume token safely.
    return HandleAsync(change, ct);
}, ct);
```

Production implementation cần persist resume token ngoài process memory.

## 5. Real production scenario

Product catalog dùng MongoDB làm primary store và Elasticsearch cho search. Thay vì request ghi trực tiếp cả hai nơi, một synchronizer đọc Change Stream rồi cập nhật Elasticsearch.

Nếu Elasticsearch outage, consumer có thể retry/reconnect thay vì làm product write thất bại ngay.

## 6. Failure scenario & troubleshooting

**Symptom** → search index thiếu hoặc duplicate processing sau restart.

**Evidence** → resume token chỉ giữ trong memory hoặc persist trước khi side effect hoàn tất.

**Hypothesis** → checkpoint boundary sai.

**Diagnosis** → so sánh event token, target document version và consumer logs.

**Fix** → persist token sau successful idempotent side effect; có replay/reconciliation strategy.

**Verification** → kill consumer giữa processing và checkpoint, xác nhận recovery đúng.

## 7. Common mistakes

* Coi Change Stream là exactly-once delivery.
* Không persist resume token.
* Không có reconciliation job khi sync target drift.
* Đưa business transaction critical vào asynchronous sync mà không chấp nhận eventual consistency.
* Không monitor stream lag.

## 8. Alternatives

* Polling theo watermark.
* Application-level Outbox.
* CDC platform chuyên dụng.
* Publish event trực tiếp từ application khi transaction model cho phép.

## 9. Trade-offs

### Advantages

* Near-real-time synchronization.
* Giảm polling load.
* Resume sau disconnect.

### Costs / Risks

* Eventual consistency.
* Resume token/checkpoint management.
* Consumer cần idempotency và lag monitoring.
* Không thay thế broker khi cần routing/delivery semantics phong phú.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu consumer nhận database changes bất đồng bộ.

### Middle

Implement watcher và persist resume token.

### Senior

Thiết kế idempotency, retry, lag và reconciliation.

### Technical Lead / Architect

Quyết định Change Stream có phù hợp integration boundary hay cần Outbox/message broker rõ ràng hơn.

## 11. Key takeaway

* Change Streams giảm polling nhưng không loại bỏ duplicate/recovery concerns.
* Resume token là checkpoint, không phải guarantee exactly-once.
* Eventual consistency cần reconciliation và observability.

# 6. Anti-Corruption Layer trong DDD: tích hợp legacy hoặc third-party model mà không để contract bên ngoài làm nhiễm domain model

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary dịch model/contract của external hoặc legacy system sang model mà bounded context của mình hiểu.

```text
Our Domain
   ↑
Application Port
   ↑
Anti-Corruption Adapter
   ↑
Legacy / Third-party API
```

Mục tiêu không phải “thêm một layer cho đẹp”, mà là ngăn semantics bên ngoài lan vào core model.

## 2. Why does it exist?

External API có thể dùng naming, lifecycle hoặc invariant khác domain của bạn. Nếu import DTO trực tiếp vào domain:

* external naming lan khắp codebase,
* vendor change gây blast radius lớn,
* business rule bị bẻ theo contract bên ngoài,
* testing domain phụ thuộc third-party shape.

## 3. How does it work?

ACL thường gồm:

* outbound/inbound adapter,
* DTO mapping,
* semantic translation,
* error mapping,
* sometimes caching/retry ở integration boundary.

Data ownership vẫn rõ: external system sở hữu model của nó; bounded context của bạn sở hữu domain semantics của mình.

Transaction boundary không kéo xuyên hai hệ thống. Cross-system consistency cần workflow/compensation nếu có side effects.

## 4. Practical implementation

Domain-facing port:

```csharp
public interface ICustomerCreditGateway
{
    Task<CreditAssessment> AssessAsync(
        CustomerId customerId,
        Money amount,
        CancellationToken ct);
}
```

Adapter:

```csharp
public sealed class LegacyCreditGateway : ICustomerCreditGateway
{
    private readonly LegacyCreditClient _client;

    public async Task<CreditAssessment> AssessAsync(
        CustomerId customerId,
        Money amount,
        CancellationToken ct)
    {
        var response = await _client.CheckAsync(
            customerId.Value,
            amount.Value,
            ct);

        return response.Code switch
        {
            "A" => CreditAssessment.Approved(response.Limit),
            "D" => CreditAssessment.Declined(),
            _ => CreditAssessment.Unavailable()
        };
    }
}
```

Domain không biết vendor dùng code `A/D`.

## 5. Real production scenario

E-commerce platform tích hợp ERP legacy gọi “Item” là cả product lẫn inventory record. Nếu dùng ERP DTO khắp application, team dần phụ thuộc vào model không phản ánh business hiện tại.

ACL tách `Product`, `InventoryPosition` và `Price` theo domain local, còn adapter chịu trách nhiệm dịch ERP representation.

## 6. Failure scenario & troubleshooting

**Symptom** → vendor thêm trạng thái mới làm domain flow rơi vào exception ở nhiều nơi.

**Evidence** → DTO/vendor enum được dùng trực tiếp xuyên application/domain.

**Hypothesis** → external contract vượt qua integration boundary.

**Diagnosis** → trace dependency direction và type references.

**Fix** → centralize translation trong ACL, map unknown state thành explicit local behavior.

**Verification** → contract test adapter với cả known/unknown vendor responses.

## 7. Common mistakes

* Tạo ACL chỉ là one-to-one mapper vô nghĩa nhưng vẫn leak external semantics.
* Đặt retry/business rules lẫn lộn trong mapping code.
* Copy toàn bộ external schema thành internal model dù chỉ cần vài fields.
* Biến ACL thành shared library dùng bởi mọi bounded context.
* Không version/test external contract.

## 8. Alternatives

* Direct integration nếu external model rất nhỏ, ổn định và semantics trùng khớp.
* Shared Kernel khi hai context thật sự cùng model và cùng ownership discipline.
* Event translation service nếu integration chủ yếu asynchronous.

## 9. Trade-offs

### Advantages

* Cô lập vendor/legacy change.
* Bảo vệ ubiquitous language và domain invariant.
* Test domain không cần external DTO.

### Costs / Risks

* Thêm mapping code.
* Có thể overengineering với integration rất nhỏ.
* Translation semantics cần ownership rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain entity.

### Middle

Implement adapter và mapping rõ boundary.

### Senior

Thiết kế error/semantic translation và failure isolation.

### Technical Lead / Architect

Quyết định bounded context ownership, deployment boundary và khi nào ACL đáng chi phí.

## 11. Key takeaway

* ACL bảo vệ domain semantics, không phải chỉ đổi tên field.
* External model không nên tự động trở thành internal model.
* Boundary tốt giảm blast radius của vendor và legacy changes.

# 7. Azure App Service autoscale và Health Check: scale-out chỉ hữu ích khi instance thực sự sẵn sàng nhận traffic

## 1. What is it?

Azure App Service autoscale tăng/giảm số instance dựa trên metric/rule. Health Check giúp platform phát hiện instance unhealthy và tránh route traffic tới instance đó trong các tình huống được hỗ trợ.

Mental model:

```text
Traffic
   ↓
App Service front ends
   ↓
Healthy instances only
   ├─ instance A
   ├─ instance B
   └─ instance C
```

Scale-out giải quyết capacity; Health Check giải quyết readiness/instance health. Hai vấn đề liên quan nhưng không giống nhau.

## 2. Why does it exist?

Nếu traffic tăng mà chỉ có một instance, CPU/request queue có thể vượt capacity. Nhưng scale-out mà instance mới mất 40 giây warm-up, load balancer gửi traffic quá sớm thì error rate vẫn tăng.

Tương tự, một instance bị stuck nhưng process chưa chết có thể tiếp tục nhận traffic nếu không có health signal phù hợp.

## 3. How does it work?

Autoscale quan sát metric như CPU, memory hoặc custom/queue metrics tùy setup và thay đổi instance count theo policy.

Health endpoint nên kiểm tra application readiness thiết yếu, nhưng không nên phụ thuộc mọi downstream dependency theo cách làm toàn bộ fleet bị đánh unhealthy khi một dependency bên ngoài outage.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<StartupReadyCheck>("startup-ready");

var app = builder.Build();

app.MapHealthChecks("/health");
```

Health endpoint nên nhanh, không auth phức tạp và không tạo workload đáng kể.

Autoscale rule cần cooldown để tránh scale in/out liên tục.

## 5. Real production scenario

API traffic tăng sau campaign. CPU rule scale từ 2 lên 8 instances, nhưng startup tải metadata lớn từ external API. Instance mới nhận request trước khi cache warm, gây 5xx spike.

Fix gồm readiness signal đúng, startup optimization và scale rule anticipatory hơn thay vì chỉ tăng max instances.

## 6. Failure scenario & troubleshooting

**Symptom** → instance count tăng nhưng p95 và 5xx vẫn xấu.

**Evidence** → error tập trung trên instance mới vài phút đầu.

**Hypothesis** → warm-up/readiness không phù hợp.

**Diagnosis** → split telemetry theo instance, xem health history và startup duration.

**Fix** → health/readiness endpoint đúng semantics, pre-warm cần thiết, giảm startup dependency.

**Verification** → scale-out test dưới load và xác nhận instance chỉ nhận traffic khi ready.

## 7. Common mistakes

* Health endpoint gọi tất cả downstream services rồi trả unhealthy nếu một service phụ bị lỗi.
* Scale theo CPU dù bottleneck thực sự là database connection pool.
* Không có cooldown và hysteresis.
* Scale App Service vô hạn trong khi database không scale tương ứng.
* Không quan sát per-instance metrics.

## 8. Alternatives

* Manual/static scale nếu traffic ổn định.
* Azure Container Apps/Kubernetes nếu cần scaling model khác.
* Queue-based worker scaling cho background workloads.
* Performance optimization trước nếu bottleneck không phải instance capacity.

## 9. Trade-offs

### Advantages

* Scale-out hấp thụ burst tốt hơn.
* Health Check giảm traffic tới unhealthy instance.
* Platform-managed operation đơn giản hơn self-hosting.

### Costs / Risks

* Nhiều instances tăng cost.
* Downstream dependency có thể trở thành bottleneck mới.
* Sai health semantics có thể làm fleet tự loại khỏi traffic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu scale-out = nhiều instance, không phải app tự nhiên nhanh hơn.

### Middle

Implement health endpoint và đọc autoscale metrics.

### Senior

Phân tích per-instance behavior, warm-up, downstream capacity và cooldown.

### Technical Lead / Architect

Thiết kế capacity model end-to-end và chọn metric scale phản ánh bottleneck thật.

## 11. Key takeaway

* Autoscale không sửa mọi bottleneck.
* Health endpoint phải phản ánh readiness thực tế nhưng không quá nhạy với dependency ngoài.
* Capacity plan phải bao gồm database, cache và external services.

# 8. Expand–Migrate–Contract cho database deployment: thay đổi schema zero-downtime bằng compatibility window thay vì deploy application và migration như một bước atomic giả định

## 1. What is it?

Expand–Migrate–Contract là migration strategy theo nhiều release:

1. **Expand**: thêm schema mới theo cách backward-compatible.
2. **Migrate**: backfill/chuyển traffic dữ liệu sang shape mới.
3. **Contract**: xóa schema cũ khi không còn consumer dùng.

Nó tạo compatibility window giữa version cũ và mới của application.

## 2. Why does it exist?

Rolling deployment, multiple instances và rollback nghĩa là trong một khoảng thời gian nhiều application versions có thể chạy đồng thời.

Migration phá compatibility như rename/drop column tức thì có thể khiến old instance lỗi ngay khi schema đổi.

## 3. How does it work?

Ví dụ đổi `FullName` thành `FirstName` + `LastName`:

```text
Release N: add new nullable columns
Release N+1: write both old + new
Backfill old rows
Release N+2: read new columns
Observe
Release N+3: stop old writes
Release N+4: drop old column
```

Dependency direction trong deployment là application versions cùng phụ thuộc schema đủ tương thích cho cả hai.

## 4. Practical implementation

SQL expand:

```sql
ALTER TABLE Customers ADD FirstName nvarchar(100) NULL;
ALTER TABLE Customers ADD LastName  nvarchar(100) NULL;
```

Application release tiếp theo dual-write hoặc transform theo migration plan. Backfill nên batch nhỏ thay vì update toàn table trong một transaction lớn.

Contract chỉ thực hiện sau khi telemetry xác nhận không còn old reader/writer.

## 5. Real production scenario

App Service deployment slot swap có old/new workers cùng tồn tại trong rollout. Team deploy migration `DROP COLUMN LegacyStatus` trước khi tất cả old instances dừng. Một số request đi vào old binary và crash.

Expand–Contract loại bỏ giả định “code và schema đổi cùng một millisecond”.

## 6. Failure scenario & troubleshooting

**Symptom** → chỉ một phần requests lỗi sau deployment.

**Evidence** → lỗi `Invalid column name` hoặc missing field chỉ trên old instances.

**Hypothesis** → schema mới không backward-compatible với binary cũ.

**Diagnosis** → correlate instance version và DB migration timestamp.

**Fix** → restore compatibility, roll forward hoặc rollback schema an toàn nếu có thể.

**Verification** → deployment rehearsal với mixed-version instances.

## 7. Common mistakes

* Rename/drop column trong cùng release với code change.
* Backfill hàng triệu rows trong một transaction.
* Không có rollback plan.
* Dual-write vô thời hạn mà không cleanup.
* Migration chạy tự động trên startup của mọi instance cùng lúc mà không coordination.

## 8. Alternatives

* Maintenance window nếu downtime được business chấp nhận.
* Blue-Green database riêng nếu architecture/cost cho phép.
* Versioned API/storage layer cho migration cực lớn.
* One-shot migration cho hệ thống nhỏ, single instance và rollback không cần thiết.

## 9. Trade-offs

### Advantages

* Hỗ trợ rolling deployment và rollback tốt hơn.
* Giảm risk của breaking schema change.
* Cho phép backfill có kiểm soát.

### Costs / Risks

* Nhiều release hơn.
* Tạm thời có duplicated schema/data paths.
* Cần cleanup discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu database schema là contract với application versions.

### Middle

Viết backward-compatible migration cơ bản.

### Senior

Thiết kế backfill, dual-read/write và rollback.

### Technical Lead / Architect

Định nghĩa deployment protocol giữa application, database và release tooling.

## 11. Key takeaway

* Production deployment hiếm khi atomic giữa code và schema.
* Compatibility window giúp rolling deployment an toàn.
* Contract phase phải dựa trên evidence rằng consumer cũ đã biến mất.

# 9. RED metrics và alerting theo symptom: dùng Rate, Errors, Duration để phát hiện incident trước khi đào sâu root cause

## 1. What is it?

RED là mental model cho service-level telemetry:

* **Rate**: số request/work units theo thời gian.
* **Errors**: tỷ lệ/số lỗi.
* **Duration**: latency distribution, thường quan tâm p50/p95/p99.

RED giúp quan sát điều người dùng cảm nhận trước khi tìm nguyên nhân CPU, memory hay database.

## 2. Why does it exist?

Infrastructure metric như CPU 85% chưa chắc là incident. Ngược lại, service có thể trả 500 hàng loạt khi CPU chỉ 20% vì dependency hoặc config lỗi.

Alert tốt nên bắt symptom có user impact, sau đó dùng resource/dependency telemetry để chẩn đoán.

## 3. How does it work?

Ví dụ request telemetry:

```text
Rate     = requests/sec
Errors   = 5xx / total
Duration = p50, p95, p99
```

Logs cung cấp event detail, metrics cho aggregate trend, traces cho request path. Alert kích hoạt trên SLO symptom; investigation dùng cả ba signal.

## 4. Practical implementation

Với OpenTelemetry metrics, có thể tạo counter/histogram hoặc dùng ASP.NET Core instrumentation sẵn có.

Alert ví dụ:

```text
5xx rate > 2% for 5 minutes
AND request rate > minimum traffic threshold
```

Latency alert nên dùng percentile hoặc SLO burn thay vì average duy nhất.

Dashboard nên drill từ service → endpoint → dependency → instance.

## 5. Real production scenario

Checkout p95 tăng từ 400 ms lên 3 s nhưng CPU/memory đều bình thường. RED dashboard phát hiện duration regression ngay. Trace drill-down cho thấy payment dependency tăng latency.

Nếu chỉ alert CPU, incident có thể không được phát hiện cho tới khi support ticket xuất hiện.

## 6. Failure scenario & troubleshooting

**Symptom** → alert spam lúc traffic gần zero.

**Evidence** → một request lỗi tạo error rate 100%.

**Hypothesis** → alert không có minimum volume hoặc multi-window logic.

**Diagnosis** → inspect denominator/rate calculation và traffic pattern.

**Fix** → thêm traffic floor, window phù hợp hoặc SLO burn-rate alert.

**Verification** → replay low-traffic và real incident scenarios.

## 7. Common mistakes

* Alert trên mọi exception log.
* Chỉ dùng average latency.
* Không tách endpoint critical với endpoint background.
* Alert CPU trước user-impact symptom.
* Dashboard có metric nhưng không có actionable threshold/runbook.

## 8. Alternatives

* USE method cho resource: Utilization, Saturation, Errors.
* SLI/SLO burn-rate alerting.
* Business KPI alerting cho flow critical.

RED và USE bổ sung nhau: RED nhìn service experience; USE nhìn resource pressure.

## 9. Trade-offs

### Advantages

* Bám sát user-visible behavior.
* Đơn giản để chuẩn hóa giữa services.
* Hỗ trợ incident triage nhanh.

### Costs / Risks

* RED không tự cho root cause.
* Metric aggregation sai có thể che endpoint critical.
* Alert threshold tĩnh có thể không phù hợp mọi traffic pattern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu rate, error rate và latency percentile.

### Middle

Tạo dashboard/alert cơ bản và correlate logs/traces.

### Senior

Thiết kế SLI, threshold, traffic floor và dependency drill-down.

### Technical Lead / Architect

Chuẩn hóa observability contract và ưu tiên alerts theo user impact/SLO.

## 11. Key takeaway

* Alert trước hết nên phản ánh symptom người dùng thấy.
* p95/p99 thường hữu ích hơn average cho tail latency.
* RED phát hiện vấn đề; logs/traces/resources giúp tìm root cause.

# 10. React stale closures và async effects: tránh state cũ, race condition và update sau khi component lifecycle đã thay đổi

## 1. What is it?

Trong React function component, callback capture values từ render nơi callback được tạo. Nếu asynchronous operation hoàn tất sau một render mới, callback cũ có thể vẫn giữ state/props cũ: đây là stale closure.

Mental model:

```text
Render A: query = "car"
  └─ start request A
Render B: query = "car seat"
  └─ start request B
Request B returns first → UI correct
Request A returns later → stale result overwrites UI
```

## 2. Why does it exist?

JavaScript closures giữ lexical values. React render tạo một snapshot mới của state/props, không mutate snapshot cũ.

Async request, timer và event handler sống lâu hơn một render nên dễ dùng dữ liệu đã stale.

## 3. How does it work?

`useEffect` dependency array quyết định khi effect được tạo lại. Cleanup chạy trước effect mới hoặc khi unmount.

Có thể dùng `AbortController` để cancel request cũ:

```tsx
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(query)}`,
      { signal: controller.signal }
    );

    const data = await response.json();
    setResults(data);
  }

  load().catch(error => {
    if (error.name !== "AbortError") throw error;
  });

  return () => controller.abort();
}, [query]);
```

## 4. Practical implementation

Ngoài cancellation, state update dựa trên state trước nên dùng functional update:

```tsx
setCount(current => current + 1);
```

thay vì callback async giữ `count` cũ:

```tsx
setCount(count + 1);
```

Frontend cancellation nên đi cùng backend cancellation nếu request bị abort ở network layer và server framework propagate disconnect token.

## 5. Real production scenario

Search-as-you-type gọi API sau mỗi input. Request cho chuỗi ngắn đôi khi chậm hơn request mới, rồi overwrite kết quả mới bằng kết quả cũ.

Bug chỉ xuất hiện khi latency thay đổi nên local development thường khó tái hiện.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị data không khớp input hiện tại.

**Evidence** → Network tab cho thấy response cũ về sau response mới.

**Hypothesis** → race giữa async effects/stale closure.

**Diagnosis** → thêm request sequence/correlation ID, xem lifecycle effect và dependency array.

**Fix** → abort old request, ignore stale sequence hoặc dùng data-fetching library quản lý concurrency.

**Verification** → throttle network và nhập nhanh để stress ordering.

## 7. Common mistakes

* Bỏ dependency khỏi `useEffect` để “không chạy lại”.
* Không cleanup timer/subscription/request.
* Dùng stale state trong async callback.
* Tin rằng response luôn về theo thứ tự request gửi đi.
* Đưa quá nhiều mutable state vào component thay vì derive/cache hợp lý.

## 8. Alternatives

* TanStack Query / SWR để quản lý server state, caching và request lifecycle.
* Sequence number để ignore stale response.
* Debounce/throttle để giảm request volume.
* Backend endpoint hỗ trợ idempotent/search semantics và cancellation.

## 9. Trade-offs

### Advantages

* Cancellation giảm wasted network/work.
* Functional state update tránh stale-value bugs.
* Data-fetching libraries chuẩn hóa caching/race handling.

### Costs / Risks

* Lifecycle/concurrency logic tăng complexity.
* Abort không đảm bảo server side effect chưa xảy ra.
* Debounce tăng intentional latency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mỗi render có snapshot state riêng.

### Middle

Dùng dependency array, cleanup và `AbortController` đúng.

### Senior

Debug race bằng Network/React DevTools, phân biệt client cancellation với server semantics.

### Technical Lead / Architect

Định nghĩa server-state strategy, caching và request ownership giữa component, store và API layer.

## 11. Key takeaway

* Async response không đảm bảo về đúng thứ tự request.
* Cleanup/cancellation là phần của effect lifecycle.
* Functional updates và server-state tooling giúp giảm stale closure/race bugs.
