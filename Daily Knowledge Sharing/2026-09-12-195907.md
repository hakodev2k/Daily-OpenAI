# 1. C# `IAsyncDisposable` và `await using`: cleanup asynchronous resource mà không block ThreadPool lúc shutdown hoặc high load

## 1. What is it?

`IAsyncDisposable` là contract dành cho resource cần cleanup có thao tác asynchronous. Thay vì chỉ có:

```csharp
void Dispose();
```

nó cung cấp:

```csharp
ValueTask DisposeAsync();
```

và được consume bằng `await using`.

Mental model:

```text
Acquire async-capable resource
        -> use
        -> async cleanup
        -> return connection/buffer/session cleanly
```

Điểm quan trọng là cleanup cũng có thể cần I/O: flush network stream, close protocol session, commit/rollback async transaction, hoặc dispose object graph chứa resource asynchronous.

## 2. Why does it exist?

`IDisposable` giả định cleanup có thể hoàn tất synchronously. Nhưng trong modern .NET, nhiều resource liên quan network/database không nên block thread để chờ I/O.

Nếu cleanup asynchronous bị ép thành synchronous bằng `.Wait()` hoặc `.GetAwaiter().GetResult()`, high-concurrency service có thể giữ ThreadPool threads chỉ để chờ resource đóng, làm latency và shutdown time xấu đi.

## 3. How does it work?

Compiler chuyển:

```csharp
await using var resource = await OpenAsync(ct);
```

thành logic gần tương đương:

```text
resource = await OpenAsync()
try
    execute body
finally
    await resource.DisposeAsync()
```

`finally` vẫn được đảm bảo về control flow, nhưng cleanup có thể suspend thay vì block thread.

Nếu object implement cả `IDisposable` và `IAsyncDisposable`, caller chọn contract phù hợp với context. Async code path thường nên ưu tiên async disposal khi resource thực sự có async cleanup.

## 4. Practical implementation

Ví dụ với EF Core transaction:

```csharp
await using var transaction =
    await db.Database.BeginTransactionAsync(ct);

try
{
    db.Orders.Add(order);
    await db.SaveChangesAsync(ct);

    await transaction.CommitAsync(ct);
}
catch
{
    await transaction.RollbackAsync(ct);
    throw;
}
```

Custom resource:

```csharp
public sealed class AsyncSession : IAsyncDisposable
{
    private readonly Stream _stream;

    public AsyncSession(Stream stream) => _stream = stream;

    public async ValueTask DisposeAsync()
    {
        await _stream.FlushAsync();
        await _stream.DisposeAsync();
    }
}
```

## 5. Real production scenario

Một background worker mở database transaction và network stream cho từng batch. Code dispose stream synchronously sau mỗi batch. Khi downstream storage chậm, nhiều worker threads cùng block trong cleanup. Queue throughput giảm dù CPU chỉ 30–40%.

Đổi resource lifecycle sang async end-to-end giúp thread quay lại pool trong lúc I/O cleanup đang chờ.

## 6. Failure scenario & troubleshooting

**Symptom** → p95/p99 tăng, ThreadPool queue length tăng, CPU không tương ứng cao; shutdown mất rất lâu.

**Evidence** → dump/trace cho thấy nhiều threads ở synchronous dispose/flush hoặc `.GetResult()`.

**Hypothesis** → async-capable resource bị cleanup synchronously.

**Diagnosis** → inspect resource ownership và disposal path, dùng `dotnet-trace`/profiler xem blocking stacks.

**Fix** → propagate async disposal, dùng `await using`, tránh sync-over-async.

**Verification** → load test lại, so ThreadPool queue, active threads, shutdown duration và p99.

## 7. Common mistakes

- Implement `IAsyncDisposable` nhưng caller vẫn dùng `using`.
- Dùng `DisposeAsync().AsTask().Wait()`.
- Quên dispose resource khi exception xảy ra.
- Implement async disposal chỉ để `return default;` dù resource hoàn toàn synchronous.
- Không làm rõ object nào sở hữu resource và chịu trách nhiệm dispose.

## 8. Alternatives

`IDisposable` vẫn đúng cho memory/native handle cleanup thuần synchronous. Không nên thêm `IAsyncDisposable` chỉ vì method khác trong class là async.

## 9. Trade-offs

### Advantages

- Không block thread trong cleanup I/O.
- Lifecycle rõ với `await using`.
- Phù hợp high-throughput service và graceful shutdown.

### Costs / Risks

- API phức tạp hơn nếu hỗ trợ cả sync và async disposal.
- Caller phải propagate async lifecycle.
- Cleanup chậm vẫn có thể kéo dài shutdown nếu dependency không phản hồi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dispose là ownership/lifetime, không phải “GC sẽ tự dọn mọi thứ”.

### Middle

Biết dùng `await using` cho resource hỗ trợ async disposal.

### Senior

Nhận diện sync-over-async trong cleanup, đo ThreadPool impact và thiết kế cancellation/timeout hợp lý.

### Technical Lead / Architect

Đặt resource-lifecycle convention toàn codebase và tránh abstraction che mất ai là owner của connection/stream/session.

## 11. Key takeaway

- Cleanup có I/O cũng cần asynchronous semantics.
- `await using` giúp giữ `finally` semantics mà không block thread.
- Async disposal chỉ có giá trị khi resource thực sự có async cleanup.

# 2. ASP.NET Core request body streaming: xử lý payload/file lớn mà không materialize toàn bộ request vào memory

## 1. What is it?

Request body streaming là xử lý dữ liệu khi bytes được đọc dần từ `HttpRequest.Body` thay vì load toàn bộ payload vào `byte[]`, `string` hoặc `MemoryStream` trước khi xử lý.

Mental model:

```text
Client upload
   -> network chunks
   -> ASP.NET Core request stream
   -> process/copy incrementally
   -> destination
```

Mục tiêu là bounded memory usage theo buffer size, không theo total payload size.

## 2. Why does it exist?

Một request 500 MB materialize toàn bộ vào memory có thể tạo LOH pressure rất lớn. Với 20 uploads đồng thời, application có thể cần nhiều GB transient memory chỉ để giữ bytes đang đi qua.

Streaming tồn tại để biến memory cost từ:

```text
O(payload size × concurrency)
```

thành gần:

```text
O(buffer size × concurrency)
```

## 3. How does it work?

ASP.NET Core expose request body dưới dạng stream. Backpressure tự nhiên xuất hiện: application chỉ đọc thêm khi có khả năng xử lý/write tiếp.

```text
Socket -> Kestrel -> request stream -> destination stream
```

Nếu destination chậm, `CopyToAsync` await I/O thay vì tích lũy vô hạn dữ liệu trong application memory.

Streaming không tự giải quyết security. Application vẫn phải giới hạn request size, validate metadata/content và xử lý cancellation.

## 4. Practical implementation

Ví dụ upload trực tiếp sang storage abstraction:

```csharp
app.MapPost("/files/{name}", async (
    string name,
    HttpRequest request,
    IFileStore store,
    CancellationToken ct) =>
{
    if (request.ContentLength is > 500_000_000)
        return Results.StatusCode(StatusCodes.Status413PayloadTooLarge);

    await store.WriteAsync(name, request.Body, ct);
    return Results.Accepted();
});
```

Destination cũng nên stream:

```csharp
public async Task WriteAsync(
    string name,
    Stream source,
    CancellationToken ct)
{
    await using var destination = File.Create(GetSafePath(name));
    await source.CopyToAsync(destination, 64 * 1024, ct);
}
```

## 5. Real production scenario

Một CMS cho editor upload video 1 GB. Endpoint cũ gọi `CopyToAsync(new MemoryStream())`, rồi mới upload tiếp sang Blob Storage.

Khi vài editors upload đồng thời, working set tăng nhanh, Gen 2 GC dày và App Service restart do memory pressure.

Streaming trực tiếp từ request sang Blob Storage loại bỏ intermediate full-memory copy.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng theo kích thước upload, p99 spike hoặc process OOM.

**Evidence** → heap dump có nhiều `byte[]`/`MemoryStream`; allocation rate tăng theo upload throughput.

**Hypothesis** → request đang bị buffered/materialized.

**Diagnosis** → trace code path từ model binding đến storage; kiểm tra multipart/form buffering và intermediate transformations.

**Fix** → stream end-to-end, giới hạn payload, tránh `ToArray()`/`ReadToEndAsync()` trên large body.

**Verification** → upload file lớn với concurrency cao và xác nhận memory giữ ổn định theo concurrency/buffer, không theo file size.

## 7. Common mistakes

- Stream request nhưng lại `ToArray()` ngay trước storage call.
- Không giới hạn request size.
- Tin filename/MIME type do client gửi.
- Không propagate `RequestAborted`/`CancellationToken`.
- Giữ database transaction mở suốt thời gian upload dài.

## 8. Alternatives

Direct-to-Blob upload bằng SAS phù hợp file rất lớn và giảm bandwidth qua application. Buffered model binding đơn giản hơn cho JSON/form nhỏ và thường hoàn toàn đủ.

## 9. Trade-offs

### Advantages

- Memory bounded hơn.
- Throughput ổn định hơn với payload lớn.
- Giảm GC pressure.

### Costs / Risks

- Validation/transformation khó hơn nếu cần random access toàn payload.
- Partial upload cần cleanup strategy.
- Security scanning có thể cần staging workflow.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Stream` cho phép xử lý dữ liệu dần thay vì giữ toàn bộ trong memory.

### Middle

Implement streaming, size limit và cancellation.

### Senior

Phân tích buffering ở Kestrel/model binding/storage layers và thiết kế backpressure/cleanup.

### Technical Lead / Architect

Quyết định upload nào đi qua app, upload nào direct-to-storage và pipeline scanning/authorization nằm ở đâu.

## 11. Key takeaway

- Large payload nên được thiết kế như data flow, không như một object lớn trong memory.
- Streaming phải xuyên suốt pipeline mới có lợi.
- Size limit, cancellation và file security vẫn bắt buộc.

# 3. EF Core transaction boundary và external side effects: vì sao `SaveChanges` + gọi API bên ngoài không tạo thành một transaction

## 1. What is it?

EF Core transaction đảm bảo atomicity cho operations trong database transaction boundary. Nó không bao phủ HTTP call, email, payment provider hay message broker nằm ngoài cùng transaction coordinator.

Mental model sai:

```text
BEGIN SQL TRANSACTION
  Save order
  Call payment API
COMMIT
```

Không có nghĩa database và payment cùng rollback được.

## 2. Why does it exist?

Business workflow thường vừa thay đổi database vừa tạo side effect bên ngoài. Nếu developer giả định một `try/catch` có thể rollback mọi thứ, partial failure sẽ tạo inconsistency.

Network có thể fail sau khi remote system đã nhận request nhưng trước khi response quay lại. Đây là uncertainty mà local DB transaction không giải quyết được.

## 3. How does it work?

Một local transaction chỉ atomic trong database:

```text
DB transaction: [Insert Order + Insert Audit] -> atomic
HTTP Payment: separate failure domain
Message Broker: separate failure domain
```

Nếu call external API trước commit, API có thể thành công nhưng DB rollback.

Nếu commit DB trước rồi call API, DB có thể thành công nhưng API fail.

Không có ordering nào tự tạo global atomicity.

## 4. Practical implementation

Một cách an toàn hơn khi cần publish event là Outbox:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

db.Orders.Add(order);
db.OutboxMessages.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    Type = "OrderCreated",
    Payload = JsonSerializer.Serialize(new { order.Id }),
    CreatedAtUtc = DateTime.UtcNow
});

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Publisher riêng gửi Outbox sau commit.

Với payment API, dùng idempotency key/workflow state chứ không giữ SQL transaction xuyên network call.

## 5. Real production scenario

Checkout service tạo order rồi charge payment. Payment provider xử lý charge thành công nhưng response timeout. Application catch exception và rollback order.

Kết quả: khách bị trừ tiền nhưng hệ thống không có order.

Correct design cần payment intent/idempotency key và recovery flow để query trạng thái provider thay vì giả định timeout = failure.

## 6. Failure scenario & troubleshooting

**Symptom** → có external side effect nhưng database state không tương ứng, hoặc ngược lại.

**Evidence** → provider transaction ID tồn tại nhưng DB transaction rollback; traces có timeout sau outbound request.

**Hypothesis** → transaction boundary bị hiểu sai.

**Diagnosis** → dựng timeline: DB begin/commit/rollback, outbound request, remote confirmation, retry.

**Fix** → explicit workflow state, idempotency, Outbox/Saga khi cần; không giữ transaction qua slow external I/O.

**Verification** → fault injection ở trước/sau commit và trước/sau external response.

## 7. Common mistakes

- Giữ SQL transaction trong lúc gọi HTTP API.
- Retry external call không có idempotency key.
- Nghĩ rollback DB sẽ “undo” email/payment.
- Publish message sau `SaveChanges` nhưng trước process crash mà không Outbox.
- Dùng distributed transaction như default để né workflow design.

## 8. Alternatives

Nếu toàn bộ operation nằm trong một database, local ACID transaction là đơn giản và đúng nhất. Saga phù hợp workflow nhiều service dài. Outbox phù hợp atomic DB change + eventual message publication.

## 9. Trade-offs

### Advantages

Tách failure domains làm reliability semantics rõ hơn và tránh lock dài.

### Costs / Risks

Eventual consistency, recovery state và idempotency làm application logic phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu database transaction chỉ bảo vệ database work nằm trong transaction đó.

### Middle

Biết đặt `BeginTransaction`/`Commit` đúng boundary và không kéo HTTP call vào transaction dài.

### Senior

Thiết kế idempotency/recovery cho ambiguous network failure.

### Technical Lead / Architect

Xác định consistency requirement thật sự; chọn local transaction, Outbox hay Saga thay vì áp distributed pattern máy móc.

## 11. Key takeaway

- Local transaction không tạo atomicity với remote side effects.
- Timeout không chứng minh remote operation thất bại.
- Idempotency + persisted workflow state là nền tảng của recovery.

# 4. SQL Server covering index với `INCLUDE`: giảm key lookup nhưng không biến mọi query thành một index khổng lồ

## 1. What is it?

Một covering index chứa đủ columns để SQL Server trả query mà không cần quay lại clustered index/heap để lấy thêm data.

Key columns quyết định ordering/search structure; `INCLUDE` columns nằm ở leaf level để “cover” output mà không trở thành phần chính của index key.

Ví dụ:

```sql
CREATE INDEX IX_Orders_CustomerId_CreatedAt
ON Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, Total);
```

## 2. Why does it exist?

Một nonclustered index có thể tìm row nhanh theo `CustomerId`, nhưng query còn cần `Status`, `Total`. Nếu những columns không có trong index, engine có thể thực hiện key lookup cho từng matched row.

Với vài rows, lookup rẻ. Với hàng chục nghìn rows, random lookups có thể trở thành bottleneck.

## 3. How does it work?

Không cover:

```text
Index Seek -> 10,000 keys -> Key Lookup × 10,000 -> result
```

Cover:

```text
Index Seek/Range Scan -> leaf đã có Status/Total -> result
```

`INCLUDE` không giúp predicate seek như key column. Nó chủ yếu giảm lookup cho data cần trả.

## 4. Practical implementation

Query:

```sql
SELECT CreatedAt, Status, Total
FROM Orders
WHERE CustomerId = @customerId
ORDER BY CreatedAt DESC;
```

Index phù hợp:

```sql
CREATE INDEX IX_Orders_Customer_Created
ON Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, Total);
```

Đánh giá bằng Actual Execution Plan và:

```sql
SET STATISTICS IO, TIME ON;
```

## 5. Real production scenario

Customer order history trả 100 rows mới nhất. Query dùng index theo `CustomerId`, nhưng mỗi row phải key lookup để lấy `Status` và `Total`. Ở traffic cao, logical reads tăng đáng kể.

Thêm hai `INCLUDE` columns loại lookup và giảm read latency mà không cần tạo index key rộng hơn mức cần thiết.

## 6. Failure scenario & troubleshooting

**Symptom** → query có Index Seek nhưng vẫn chậm khi result set tăng.

**Evidence** → execution plan có Key Lookup với high execution count; logical reads cao.

**Hypothesis** → index tìm đúng keys nhưng không cover output.

**Diagnosis** → so lookup cost, result cardinality và write workload.

**Fix** → cân nhắc INCLUDE chỉ các columns thật sự cần; projection nhỏ hơn cũng có thể tốt hơn.

**Verification** → so plan/logical reads/latency và đo write cost sau index change.

## 7. Common mistakes

- INCLUDE mọi column để “cover tất cả”.
- Đưa filter/sort column cần seek vào INCLUDE thay vì key.
- Chỉ nhìn read query mà bỏ write amplification/storage.
- Duplicate nhiều indexes gần giống nhau.
- Tạo index theo ORM entity thay vì query access pattern.

## 8. Alternatives

Projection nhỏ hơn có thể loại nhu cầu cover. Clustered index thay đổi là quyết định lớn hơn. Materialized/read model phù hợp nếu workload báo cáo quá khác OLTP pattern.

## 9. Trade-offs

### Advantages

- Giảm key lookup và logical I/O.
- Giữ key tương đối hẹp.
- Có thể cải thiện read-heavy endpoint đáng kể.

### Costs / Risks

- Index lớn hơn, tốn storage/cache memory.
- INSERT/UPDATE phải maintain thêm data.
- Quá nhiều covering indexes làm write workload nặng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không chỉ là “có hay không”, mà còn chứa columns nào.

### Middle

Đọc Key Lookup trong execution plan và dùng INCLUDE đúng vai trò.

### Senior

Cân bằng read gain với write amplification, storage và overlapping indexes.

### Technical Lead / Architect

Thiết kế indexing theo workload portfolio, không optimize một endpoint gây hại toàn OLTP system.

## 11. Key takeaway

- Covering index giúp tránh lookup khi leaf đã có đủ output data.
- `INCLUDE` không thay key column cho seek/sort semantics.
- Index optimization luôn phải tính write/storage cost.

# 5. Elasticsearch alias-based reindexing: thay mapping/index mà Search API không cần downtime

## 1. What is it?

Elasticsearch alias là tên logic trỏ tới một hoặc nhiều physical indexes. Search API gọi alias ổn định, còn backend có thể tạo index version mới rồi atomically chuyển alias.

```text
products-read -> products-v1
```

Sau reindex:

```text
products-read -> products-v2
```

## 2. Why does it exist?

Một số mapping/analyzer changes không thể áp an toàn in-place. Nếu application hardcode physical index name, migration yêu cầu coordinated deployment hoặc downtime.

Alias tạo indirection boundary giữa client/search service và index lifecycle.

## 3. How does it work?

Typical flow:

```text
1. create products-v2 with new mapping
2. backfill/reindex documents
3. verify counts/search behavior
4. catch up changes since backfill started
5. atomically switch alias
6. monitor
7. delete v1 later
```

Alias switch có thể atomic ở cluster-state level, nên readers không nhìn thấy trạng thái alias “trống” giữa remove/add khi dùng một `_aliases` request.

## 4. Practical implementation

Create versioned index và switch alias:

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v1", "alias": "products-read" } },
    { "add":    { "index": "products-v2", "alias": "products-read" } }
  ]
}
```

Application config chỉ dùng:

```text
products-read
```

không dùng `products-v2` trực tiếp.

## 5. Real production scenario

E-commerce search đổi analyzer để hỗ trợ synonym/tokenization mới. Reindex 40 triệu products mất hàng giờ.

Nếu overwrite index hiện tại, search quality/availability có rủi ro lớn. Versioned index + alias cho phép build/validate song song rồi cutover nhanh.

## 6. Failure scenario & troubleshooting

**Symptom** → sau alias switch, một số products mới nhất biến mất.

**Evidence** → v2 document count gần đúng nhưng missing updates trong thời gian backfill.

**Hypothesis** → reindex snapshot không catch up writes phát sinh sau khi job bắt đầu.

**Diagnosis** → compare source-of-truth change sequence/timestamps với v2 indexing watermark.

**Fix** → dual-write có kiểm soát hoặc change-feed/outbox replay đến watermark trước cutover.

**Verification** → count không đủ; cần query representative docs, freshness watermark và search behavior tests.

## 7. Common mistakes

- Hardcode physical index name trong app.
- Switch alias trước khi catch up delta changes.
- Chỉ so document count, không test analyzer/query behavior.
- Xóa old index ngay nên mất rollback path.
- Dùng Elasticsearch như transactional source of truth.

## 8. Alternatives

In-place mapping addition phù hợp non-breaking changes được Elasticsearch hỗ trợ. Blue/green search cluster cần thiết khi cluster-level upgrade/risk lớn hơn index-level migration.

## 9. Trade-offs

### Advantages

- Low-downtime index evolution.
- Rollback alias nhanh nếu old index còn giữ.
- Search client contract ổn định.

### Costs / Risks

- Temporary double storage.
- Delta synchronization phức tạp.
- Reindex CPU/I/O có thể ảnh hưởng cluster production.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu alias là logical name tách application khỏi physical index version.

### Middle

Biết create/reindex/verify/switch alias.

### Senior

Thiết kế delta catch-up, rollback và cluster-capacity protection.

### Technical Lead / Architect

Định nghĩa source of truth, indexing pipeline và release protocol cho schema/analyzer evolution.

## 11. Key takeaway

- Reindexing là data migration, không chỉ Elasticsearch command.
- Alias giúp cutover atomically nhưng không tự giải quyết delta writes.
- Giữ rollback path cho đến khi v2 được verify đủ lâu.

# 6. Outbox Pattern với polling publisher: commit business data và integration event atomically trước khi gửi message

## 1. What is it?

Outbox Pattern lưu business change và message cần publish vào cùng database transaction. Một publisher riêng đọc Outbox rows đã commit rồi gửi chúng ra broker.

```text
DB transaction
  -> update business data
  -> insert Outbox message
COMMIT

Publisher
  -> read pending Outbox
  -> publish broker
  -> mark sent
```

## 2. Why does it exist?

Nếu code làm:

```text
SaveChanges()
PublishMessage()
```

process có thể crash giữa hai bước. Database đã commit nhưng message không bao giờ gửi.

Nếu publish trước rồi DB rollback, consumers nhận event về state chưa tồn tại.

Outbox tạo atomicity ở local database boundary.

## 3. How does it work?

Business transaction chỉ cần đảm bảo hai writes local cùng commit. Publisher chạy eventually.

Publisher có thể crash sau khi broker nhận message nhưng trước khi Outbox được mark sent. Vì vậy duplicate publication vẫn có thể xảy ra.

Outbox giải quyết **lost publication**, không tạo exactly-once delivery. Consumer vẫn nên idempotent.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

db.Orders.Add(order);

db.OutboxMessages.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    OccurredAtUtc = DateTime.UtcNow,
    Type = "OrderCreated",
    Payload = JsonSerializer.Serialize(
        new OrderCreated(order.Id, order.CustomerId))
});

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Polling publisher lấy batch nhỏ:

```csharp
var batch = await db.OutboxMessages
    .Where(x => x.ProcessedAtUtc == null)
    .OrderBy(x => x.OccurredAtUtc)
    .Take(100)
    .ToListAsync(ct);
```

Sau publish thành công, mark processed. Multi-instance publisher cần claim/locking strategy phù hợp.

## 5. Real production scenario

Order service commit order rồi phát `OrderCreated` cho notification/inventory. Trước Outbox, thỉnh thoảng order tồn tại nhưng inventory không reserve vì process restart ngay sau DB commit.

Outbox biến “message bị mất vĩnh viễn” thành “message còn pending và publisher sẽ thử lại”.

## 6. Failure scenario & troubleshooting

**Symptom** → Outbox backlog tăng liên tục hoặc downstream nhận duplicate events.

**Evidence** → pending count/oldest age tăng; broker traces có cùng `MessageId` nhiều lần.

**Hypothesis** → publisher unhealthy hoặc crash giữa publish và mark-sent.

**Diagnosis** → đo backlog age, publish errors, database locking và broker availability.

**Fix** → retry/backoff, idempotent consumer, stable event ID, batch/claim strategy.

**Verification** → kill publisher ở các điểm khác nhau và xác nhận không mất message; duplicates phải được consumer xử lý an toàn.

## 7. Common mistakes

- Insert Outbox ngoài business transaction.
- Xóa row ngay thay vì giữ retention/audit đủ cho recovery.
- Giả định Outbox mang lại exactly-once.
- Publisher nhiều instances đọc cùng rows mà không coordination.
- Payload serialize toàn domain entity làm contract coupling.

## 8. Alternatives

Nếu producer và consumer nằm cùng process/database, direct method call có thể đơn giản hơn. CDC/change feed có thể thay polling trong một số platform. Distributed transaction chỉ nên dùng nếu ecosystem support tốt và complexity justified.

## 9. Trade-offs

### Advantages

- Không mất event sau local commit.
- Broker outage không block business transaction lâu.
- Recovery/backlog observable.

### Costs / Risks

- Eventual publication latency.
- Outbox table growth/cleanup.
- Duplicate delivery và publisher coordination vẫn phải giải quyết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DB commit và broker publish là hai failure domains.

### Middle

Implement Outbox write trong cùng transaction và publisher retry.

### Senior

Thiết kế claim, idempotency, ordering, retention và backlog telemetry.

### Technical Lead / Architect

Quyết định khi nào reliability requirement đáng thêm Outbox thay vì direct synchronous flow đơn giản hơn.

## 11. Key takeaway

- Outbox đảm bảo intent-to-publish không bị mất sau DB commit.
- Duplicate publication vẫn có thể xảy ra.
- Backlog age là operational signal quan trọng.

# 7. Azure App Service deployment slots: warm-up, swap settings và database compatibility trong zero/low-downtime release

## 1. What is it?

Deployment slot là một live deployment environment trong cùng App Service app, ví dụ `production` và `staging`. Code mới được deploy vào staging, warm-up/verify trước, sau đó swap routing/configuration sang production.

Mental model:

```text
Production slot -> v1
Staging slot    -> v2

validate v2
   -> swap
Production -> v2
Staging    -> v1
```

## 2. Why does it exist?

Deploy trực tiếp vào production có thể khiến startup/JIT/config validation xảy ra khi users đã gửi traffic. Slot cho phép chuẩn bị instance trước cutover và cung cấp rollback path nhanh hơn code redeploy.

## 3. How does it work?

Slot có app settings có thể đánh dấu “deployment slot setting” để không swap, ví dụ environment-specific secrets/endpoints.

Swap không rollback database migration. Nếu v2 đã thực hiện destructive schema change, swap v1 trở lại có thể vẫn fail.

Zero-downtime application swap vì vậy phụ thuộc backward-compatible database release.

## 4. Practical implementation

Config design:

```text
APP_ENVIRONMENT=Staging          [slot-specific]
DATABASE_CONNECTION=...         [thường slot-specific theo strategy]
FEATURE_X_ENABLED=false          [có thể slot-specific]
```

Health endpoint nên kiểm tra application có thể serve traffic thật:

```csharp
app.MapHealthChecks("/health/ready");
```

Release flow:

```text
build artifact
 -> deploy staging
 -> warm-up
 -> smoke/integration checks
 -> swap
 -> monitor
 -> rollback swap if app regression
```

## 5. Real production scenario

ASP.NET Core app mất 20 giây startup vì load configuration, JIT và cache warm-up. Direct deployment tạo 5xx spike mỗi release.

Staging slot được warm trước, health check pass rồi swap. Error spike biến mất, nhưng team vẫn phải giữ DB migration compatible với cả v1/v2 trong swap window.

## 6. Failure scenario & troubleshooting

**Symptom** → staging healthy nhưng ngay sau swap production lỗi config hoặc DB compatibility.

**Evidence** → setting values khác sau swap; application logs báo missing secret/invalid column.

**Hypothesis** → slot-setting semantics hoặc destructive migration không tương thích.

**Diagnosis** → diff slot config, migration version và binaries trước/sau swap.

**Fix** → mark đúng settings slot-specific, dùng expand-migrate-contract, smoke test production-equivalent dependencies.

**Verification** → test swap + swap-back trong pre-prod với schema compatibility.

## 7. Common mistakes

- Nghĩ swap là rollback toàn hệ thống kể cả DB.
- Staging dùng dependency khác quá xa production nên smoke test không có giá trị.
- Secret/config nhầm swap behavior.
- Không warm-up critical paths.
- Swap xong không monitor SLO/error rate.

## 8. Alternatives

Rolling deployment đơn giản hơn trong một số hosting. Blue-Green trên Container Apps/Kubernetes cung cấp control rộng hơn nhưng vận hành phức tạp hơn. Feature flags tách deployment khỏi release behavior nhưng không thay deployment health validation.

## 9. Trade-offs

### Advantages

- Warm-up trước traffic.
- Cutover nhanh.
- Application rollback bằng swap tương đối nhanh.

### Costs / Risks

- Slot configuration complexity.
- Có thêm runtime capacity/cost trong staging.
- Database/external side effects không tự rollback.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slot là live environment, không chỉ folder deploy khác.

### Middle

Deploy/validate/swap và quản lý slot-specific settings.

### Senior

Thiết kế health, warm-up, rollback và DB compatibility.

### Technical Lead / Architect

Chọn release strategy dựa trên risk/SLO; định nghĩa rõ phần nào swap rollback được và phần nào cần migration/recovery riêng.

## 11. Key takeaway

- Slot swap giảm application cutover risk nhưng không rollback database.
- Warm-up và health validation phải phản ánh traffic thật.
- Config swap semantics cần được kiểm soát như code.

# 8. CI/CD artifact promotion: build một lần, promote cùng artifact qua environments thay vì rebuild ở mỗi stage

## 1. What is it?

Artifact promotion là release model trong đó source commit được build/test thành immutable artifact một lần, rồi cùng artifact đó được promote qua Dev/Test/Staging/Production.

```text
Commit
 -> Build
 -> Test
 -> Artifact A
     -> Dev
     -> Test
     -> Staging
     -> Production
```

Environment-specific behavior đến từ configuration/secrets, không từ rebuild binary khác nhau.

## 2. Why does it exist?

Nếu pipeline rebuild ở mỗi environment:

```text
build-dev
build-test
build-prod
```

thì production binary không còn chính xác là binary đã được test. Package restore, source state, compiler/toolchain hoặc build timestamp có thể khác.

Promotion tạo provenance: “artifact đang chạy production chính là artifact đã qua các gates trước”.

## 3. How does it work?

Build stage tạo versioned artifact, ví dụ container image digest hoặc ZIP package. Pipeline lưu metadata:

```text
commit SHA
build ID
artifact hash/digest
test results
SBOM/signature when applicable
```

Deploy stages chỉ lấy artifact theo immutable identifier và inject environment config.

## 4. Practical implementation

Ví dụ conceptual Azure DevOps/TeamCity/Octopus flow:

```text
Build:
  dotnet restore
  dotnet test
  dotnet publish
  package MyApi-1.42.0.zip

Release:
  deploy MyApi-1.42.0.zip -> Test
  approve
  deploy same SHA/package -> Production
```

Không chạy `dotnet publish` lại trong Production stage.

## 5. Real production scenario

Team deploy staging từ build #100, nhưng production stage rebuild source vào hôm sau. Một transitive package feed trả version khác hoặc build environment đã thay đổi. Production bug không tái hiện trên staging vì binaries không giống nhau.

Artifact promotion loại bỏ lớp uncertainty này.

## 6. Failure scenario & troubleshooting

**Symptom** → “same commit” nhưng staging pass, production binary behavior khác.

**Evidence** → hashes/build IDs khác; production artifact được rebuild.

**Hypothesis** → pipeline không promote immutable artifact.

**Diagnosis** → trace provenance từ deployed files/image digest về build record.

**Fix** → publish artifact một lần, deploy theo immutable version/digest, externalize config.

**Verification** → compare artifact hash giữa environments; release audit phải chỉ ra cùng build ID.

## 7. Common mistakes

- Rebuild ở mỗi environment.
- Đóng environment secret vào artifact.
- Dùng mutable Docker tag như `latest` làm release identity.
- Không giữ artifact đủ lâu để rollback.
- Manual copy file ngoài pipeline làm mất provenance.

## 8. Alternatives

Very small internal tools có thể chấp nhận pipeline đơn giản hơn, nhưng vẫn nên giữ release artifact identity. GitOps với image digest là một cách khác để thực hiện cùng nguyên tắc immutable promotion.

## 9. Trade-offs

### Advantages

- Reproducibility và auditability tốt hơn.
- Test đúng binary sẽ lên production.
- Rollback nhanh hơn nếu artifact cũ còn lưu.

### Costs / Risks

- Cần artifact repository/retention.
- Configuration phải tách khỏi build.
- Promotion workflow/gates cần governance phù hợp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu build artifact khác source commit: production chạy binary/package cụ thể.

### Middle

Biết version/hash artifact và deploy cùng artifact qua stages.

### Senior

Thiết kế provenance, immutable tags/digests, config separation và rollback.

### Technical Lead / Architect

Đặt release-control model đủ chặt cho risk của hệ thống mà không biến pipeline thành bureaucracy thừa.

## 11. Key takeaway

- Build once, promote many giúp môi trường khác nhau chạy cùng binary.
- Artifact identity phải immutable và trace được về commit/build.
- Environment differences nên nằm ở config/secrets, không ở rebuild.

# 9. .NET ThreadPool starvation: phân biệt CPU saturation với thread starvation khi ASP.NET Core latency tăng đột biến

## 1. What is it?

ThreadPool starvation xảy ra khi work cần ThreadPool thread nhưng threads hiện tại đang bị chiếm/block, còn pool chưa tăng đủ nhanh để đáp ứng queue. Application có thể có CPU chưa đầy nhưng request vẫn chờ lâu để được chạy.

Mental model:

```text
Incoming async continuations/work
        -> ThreadPool queue grows
        -> existing threads blocked
        -> work waits
        -> latency explodes
```

## 2. Why does it exist?

ThreadPool cố cân bằng số threads để tránh tạo quá nhiều threads gây context switching/memory overhead. Nếu application block threads bằng `.Result`, `.Wait()`, synchronous network/database I/O hoặc long locks, concurrency cao có thể tiêu hết worker threads.

## 3. How does it work?

Ví dụ sync-over-async:

```csharp
public IActionResult Get()
{
    var result = _service.GetAsync().Result;
    return Ok(result);
}
```

Thread request block chờ async operation. Khi operation hoàn tất, continuation cũng cần thread để chạy. Dưới tải lớn, nhiều threads cùng block và continuations xếp hàng.

ASP.NET Core không có classic request `SynchronizationContext`, nhưng blocking vẫn làm giảm ThreadPool capacity nghiêm trọng.

## 4. Practical implementation

Correct propagation:

```csharp
public async Task<IActionResult> Get(CancellationToken ct)
{
    var result = await _service.GetAsync(ct);
    return Ok(result);
}
```

Đo runtime counters:

```bash
dotnet-counters monitor System.Runtime
```

Quan sát các signals như ThreadPool thread count, queue length, CPU, GC cùng request latency.

## 5. Real production scenario

API p95 từ 150 ms tăng lên 8 giây khi traffic gấp đôi. CPU chỉ 45%. Team định scale CPU, nhưng trace cho thấy một legacy SDK gọi synchronous HTTP trong request path.

Hundreds worker threads block chờ network; queue length tăng mạnh. Chuyển SDK path sang true async hoặc cô lập concurrency giải quyết root cause tốt hơn scale CPU.

## 6. Failure scenario & troubleshooting

**Symptom** → latency cao, throughput giảm, CPU không 100%, ThreadPool thread count/queue tăng.

**Evidence** → dumps có nhiều blocked stacks; `dotnet-counters` queue length tăng; traces có gaps trước continuation.

**Hypothesis** → blocking work/starvation chứ không phải CPU-bound saturation.

**Diagnosis** → capture trace/dump, tìm `.Result`, `.Wait`, synchronous I/O, long monitor locks.

**Fix** → async end-to-end, giới hạn blocking work, tách CPU-bound/background workloads, giảm lock contention.

**Verification** → load test cùng RPS; queue length thấp, latency ổn định, không chỉ tăng thread count.

## 7. Common mistakes

- Thấy latency cao là tăng instance ngay mà không tìm blocked stacks.
- Dùng `Task.Run` bọc synchronous I/O trong ASP.NET Core rồi nghĩ đã async.
- Tăng minimum ThreadPool threads như permanent fix.
- Nhầm starvation với CPU saturation.
- Không propagate cancellation nên abandoned requests vẫn giữ resources.

## 8. Alternatives

Nếu library chỉ có synchronous API, có thể isolate workload trong bounded worker/concurrency pool hoặc chọn library async-capable. Scale-out giúp capacity nhưng không loại bỏ blocking design.

## 9. Trade-offs

### Advantages

Async I/O giúp một số lượng threads nhỏ phục vụ nhiều concurrent operations.

### Costs / Risks

Async không làm CPU-bound work rẻ hơn. Chuyển mọi thứ sang async không chữa lock contention hoặc external dependency latency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async I/O giải phóng thread trong lúc chờ; `.Result` lại block thread.

### Middle

Propagate `async/await` và cancellation end-to-end.

### Senior

Phân biệt ThreadPool starvation, CPU saturation, GC pause và dependency latency bằng telemetry.

### Technical Lead / Architect

Đặt concurrency model cho service, audit legacy blocking dependencies và quyết định isolation/scaling strategy dựa trên evidence.

## 11. Key takeaway

- CPU thấp không đồng nghĩa service còn concurrency capacity.
- ThreadPool queue + blocked stacks là evidence quan trọng của starvation.
- Async end-to-end tốt hơn “tăng threads” để che blocking I/O.

# 10. Webhook signature verification + replay protection: coi callback từ third party là untrusted input dù request đến đúng endpoint

## 1. What is it?

Webhook là HTTP callback từ external provider tới endpoint của hệ thống. Signature verification dùng shared secret/public-key scheme để xác minh payload thật sự do provider ký và chưa bị sửa.

Replay protection ngăn attacker gửi lại một request hợp lệ đã capture để kích hoạt side effect lần nữa.

Mental model:

```text
Request
 -> read raw payload
 -> verify signature
 -> validate timestamp/replay window
 -> deduplicate event ID
 -> parse/process
```

## 2. Why does it exist?

Endpoint public có thể bị bất kỳ ai gọi. IP allowlist không luôn đủ vì provider ranges thay đổi/proxy/CDN và không bảo vệ payload khỏi replay.

Nếu webhook tạo order, activate account hoặc mark payment paid, giả mạo/replay có thể trở thành security/financial incident.

## 3. How does it work?

Provider thường ký canonical message, ví dụ:

```text
HMAC_SHA256(secret, timestamp + "." + rawBody)
```

Receiver tự tính signature trên **raw bytes** và so sánh constant-time.

Sau đó kiểm tra timestamp nằm trong allowed skew window và event ID chưa xử lý.

Signature chứng minh authenticity/integrity; idempotency/dedup xử lý duplicate/replay semantics.

## 4. Practical implementation

Ví dụ simplified HMAC verification:

```csharp
static bool Verify(
    ReadOnlySpan<byte> body,
    string providedHex,
    byte[] secret)
{
    using var hmac = new HMACSHA256(secret);
    var expected = hmac.ComputeHash(body.ToArray());

    var provided = Convert.FromHexString(providedHex);

    return provided.Length == expected.Length &&
           CryptographicOperations.FixedTimeEquals(
               provided,
               expected);
}
```

Production implementation phải follow chính xác provider canonicalization: timestamp/header/version/payload bytes.

Sau verify:

```csharp
if (await inbox.ExistsAsync(eventId, ct))
    return Results.Ok();
```

## 5. Real production scenario

Payment provider gửi `payment.succeeded`. Application parse JSON trước, reserialize rồi verify trên JSON mới. Whitespace/property-order thay đổi làm signature luôn fail.

Một team khác verify đúng signature nhưng không deduplicate event ID; provider retry sau timeout khiến order fulfillment chạy hai lần.

## 6. Failure scenario & troubleshooting

**Symptom** → valid webhooks bị 401/400 hoặc duplicate side effect xuất hiện.

**Evidence** → signature mismatch chỉ ở production proxy path; same event ID xuất hiện nhiều lần.

**Hypothesis** → raw body bị thay đổi/canonicalization sai hoặc thiếu replay/idempotency control.

**Diagnosis** → log safe metadata: event ID, signature version, timestamp, body hash — không log secret/full sensitive payload.

**Fix** → verify raw body theo provider spec, fixed-time compare, timestamp window, durable dedup key.

**Verification** → test valid signature, modified byte, old timestamp, duplicate event và rotated secret.

## 7. Common mistakes

- Trust webhook vì URL khó đoán.
- Parse/reformat body trước verification khi provider ký raw bytes.
- So signature bằng normal string equality.
- Không xử lý provider retries.
- Log webhook secret/signature material quá mức.
- Verify authenticity nhưng bỏ authorization/business validation của referenced resource.

## 8. Alternatives

Mutual TLS hoặc signed JWT callbacks có thể được provider hỗ trợ, nhưng vẫn cần replay/idempotency semantics. Polling giảm inbound attack surface nhưng tăng latency/API cost và không loại bỏ authentication requirement.

## 9. Trade-offs

### Advantages

- Xác minh source/integrity của callback.
- Replay protection giảm duplicate malicious/accidental processing.
- Cho phép endpoint public nhưng có cryptographic trust boundary.

### Costs / Risks

- Secret rotation/canonicalization phức tạp.
- Clock skew cần xử lý.
- Durable dedup storage tăng state/retention requirement.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu webhook request là external untrusted input.

### Middle

Implement signature verification đúng provider spec và idempotent event handling.

### Senior

Thiết kế secret rotation, replay window, constant-time comparison, dedup retention và observability.

### Technical Lead / Architect

Đặt trust boundary cho third-party integrations; quyết định side effect nào cần stronger approval/reconciliation thay vì chỉ dựa webhook.

## 11. Key takeaway

- Signature verification và idempotency giải quyết hai vấn đề khác nhau.
- Verify trên canonical/raw data đúng provider specification.
- Webhook hợp lệ về cryptography vẫn phải qua business authorization/validation.
