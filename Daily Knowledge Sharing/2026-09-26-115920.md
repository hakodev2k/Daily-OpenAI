# 1. C# `Span<T>` và `Memory<T>`: giảm allocation mà không phá vỡ memory safety

## 1. What is it?

Mental model: `Span<T>` là một “view” liên tục lên vùng memory đã tồn tại thay vì một container sở hữu dữ liệu mới. Nó cho phép slice array, stack memory hoặc buffer mà không cần tạo array/string trung gian. `Memory<T>` phục vụ ý tưởng tương tự nhưng có thể đi qua async boundary; `Span<T>` là `ref struct` nên bị giới hạn để không thoát khỏi lifetime an toàn của vùng memory mà nó tham chiếu.

Điểm quan trọng là zero-copy không có nghĩa zero-cost: ta giảm allocation/copy nhưng đổi lại code có lifetime constraints và complexity cao hơn.

## 2. Why does it exist?

Parser, serializer, protocol handler hoặc hot path thường cắt nhiều đoạn nhỏ từ một buffer. Với `Substring`, `ToArray` hay temporary collections, mỗi request có thể tạo hàng loạt allocation ngắn hạn. Ở throughput cao, vấn đề không phải một allocation mà là allocation rate làm Gen 0 collection tăng liên tục.

## 3. How does it work?

```text
byte[] buffer
+--------------------------------+
| header | payload | checksum    |
+--------------------------------+
   ^          ^
 Span slice   Span slice

Không copy dữ liệu; mỗi Span giữ reference + offset/length.
```

Compiler/runtime áp dụng escape rules cho `Span<T>`: nó không thể trở thành field của class thông thường, bị boxing, hoặc sống xuyên một `await`.

## 4. Practical implementation

```csharp
static bool TryReadHeader(ReadOnlySpan<byte> packet, out ushort version)
{
    version = 0;
    if (packet.Length < 2) return false;

    version = System.Buffers.Binary.BinaryPrimitives
        .ReadUInt16BigEndian(packet[..2]);

    return true;
}

static ReadOnlyMemory<byte> GetPayload(ReadOnlyMemory<byte> packet)
{
    if (packet.Length <= 2) return ReadOnlyMemory<byte>.Empty;
    return packet[2..];
}
```

Dùng `ReadOnlySpan<T>` khi method chỉ cần xử lý synchronous. Dùng `ReadOnlyMemory<T>` nếu dữ liệu phải tồn tại qua async operation.

## 5. Real production scenario

Một API nhận binary payload từ thiết bị. Bản đầu tiên dùng `ToArray()` cho header, body và checksum. Load test cho thấy CPU chưa cao nhưng allocation rate lớn và GC time tăng. Chuyển parser hot path sang `ReadOnlySpan<byte>` giảm copy mà không thay đổi public API toàn hệ thống.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 latency tăng khi throughput tăng.  
**Evidence** → profiler cho thấy allocation hotspot ở slicing/parsing; GC counters tăng mạnh.  
**Hypothesis** → temporary arrays/strings gây allocation pressure.  
**Diagnosis** → benchmark parser độc lập và allocation profile xác nhận.  
**Fix** → dùng span ở hot path, giữ implementation cũ ở code không nhạy performance.  
**Verification** → so sánh allocations/op, throughput, p95/p99 và GC pause trước/sau.

## 7. Common mistakes

Dùng `Span<T>` ở mọi nơi vì nghĩ “nhanh hơn”; cố lưu span trong object dài hạn; gọi `ToArray()` ngay sau khi slice khiến lợi ích biến mất; tối ưu trước khi profiler chỉ ra allocation thực sự là bottleneck.

## 8. Alternatives

Array/string đơn giản hơn và thường đủ tốt. `ArrayPool<T>` phù hợp khi cần buffer mutable có lifetime dài hơn một stack scope. `Memory<T>` phù hợp cho async API. Streams/Pipelines phù hợp khi dữ liệu lớn hoặc incremental.

## 9. Trade-offs

### Advantages

Giảm copy, giảm allocation và GC pressure; rất hữu ích cho parsing/serialization hot path.

### Costs / Risks

API khó dùng hơn, lifetime rules phức tạp hơn, dễ làm code business trở nên khó đọc. Performance gain có thể không đáng kể nếu bottleneck thực sự nằm ở database/network.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu view khác ownership: slice không nhất thiết tạo dữ liệu mới.

### Middle

Biết chọn `Span<T>`, `Memory<T>`, array và `ArrayPool<T>`; biết benchmark allocation.

### Senior

Đọc profiler, xác định hot path, hiểu GC pressure và không tối ưu mù.

### Technical Lead / Architect

Quyết định nơi zero-copy API thực sự đáng complexity và giữ optimization không lan vào domain/application code.

## 11. Key takeaway

- `Span<T>` tối ưu việc nhìn vào memory hiện có, không phải “collection nhanh hơn”.
- Chỉ áp dụng khi measurement chứng minh allocation/copy đáng kể.
- Với async lifetime, cân nhắc `Memory<T>` thay vì ép `Span<T>`.

# 2. ASP.NET Core exception boundary và `ProblemDetails`: thiết kế error contract có thể vận hành

## 1. What is it?

Exception boundary là điểm tập trung biến unhandled exception thành HTTP response ổn định. `ProblemDetails` cung cấp contract chuẩn cho lỗi HTTP thay vì mỗi endpoint trả một JSON shape khác nhau.

Mental model: exception là implementation failure signal bên trong; HTTP error contract là public protocol bên ngoài. Không nên để hai thứ đồng nhất.

## 2. Why does it exist?

Nếu controller tự `try/catch` mọi nơi, mapping lỗi bị lặp, status code không nhất quán và stack trace dễ bị leak. Client cũng khó phân biệt validation, conflict, authentication failure và server fault.

## 3. How does it work?

```text
Client
  -> ExceptionHandler middleware
     -> Authentication/Authorization
        -> Endpoint
           -> Application
              -> Infrastructure
                    throws
              <- exception propagates
     <- map to ProblemDetails
<- stable HTTP contract + correlation/trace id
```

Boundary nên map expected domain/application failures thành 4xx và unexpected failures thành 500, đồng thời log full internal context server-side.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();

app.UseExceptionHandler();

app.MapPost("/orders", async (CreateOrder request, OrderService service) =>
{
    var result = await service.CreateAsync(request);
    return Results.Created($"/orders/{result.Id}", result);
});
```

Với custom `IExceptionHandler`, map `ConcurrencyException` → 409, validation → 400/422 tùy contract; unknown exception → 500. Không đưa SQL text, connection string hoặc stack trace vào response Production.

## 5. Real production scenario

Mobile app và web app cùng dùng Order API. Một release đổi exception message làm frontend dựa trên string parsing bị hỏng. Sau đó API chuẩn hóa machine-readable `type`, `status`, stable error code và `traceId`; UI không còn phụ thuộc message nội bộ.

## 6. Failure scenario & troubleshooting

**Symptom** → client chỉ nhận 500 không đủ thông tin, support không nối được với log.  
**Evidence** → response không có correlation identifier.  
**Diagnosis** → exception middleware log request nhưng response không trả trace identifier.  
**Fix** → thêm trace ID vào extension của `ProblemDetails`, structured log cùng ID.  
**Verification** → từ một lỗi client có thể truy ngược đúng trace/log mà không lộ sensitive detail.

## 7. Common mistakes

Trả `exception.Message` trực tiếp; biến mọi exception thành 400; catch rồi trả 200 với `success=false`; dùng exception cho flow control bình thường; thay đổi error code mà không xem đó là API compatibility.

## 8. Alternatives

Endpoint-specific result types hữu ích cho expected outcomes. Result pattern có thể giảm exception cho business failure. Tuy nhiên vẫn cần global boundary cho lỗi không dự kiến.

## 9. Trade-offs

### Advantages

Contract nhất quán, observability tốt, giảm duplicated error handling.

### Costs / Risks

Mapping quá tổng quát có thể che mất semantic khác nhau; một global handler phình to thành nơi chứa business logic nếu boundary không rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt 4xx do request/business condition và 5xx do server failure.

### Middle

Implement `ProblemDetails`, validation mapping và integration tests cho error contract.

### Senior

Thiết kế stable error taxonomy, security-safe diagnostics và traceability.

### Technical Lead / Architect

Quyết định error contract xuyên nhiều API, backward compatibility và ownership giữa domain error với transport mapping.

## 11. Key takeaway

- Exception nội bộ không phải public API contract.
- Client cần stable machine-readable errors; operator cần full internal diagnostics.
- Error handling phải được test như một phần của API compatibility.

# 3. EF Core `AsSplitQuery`: tránh cartesian explosion nhưng hiểu rõ consistency và round trip

## 1. What is it?

Khi `Include` nhiều collection, single SQL query có thể tạo cartesian multiplication. `AsSplitQuery()` yêu cầu EF Core tải graph bằng nhiều SQL queries thay vì một JOIN khổng lồ.

## 2. Why does it exist?

Một Order có 20 Lines và 10 AuditEntries có thể tạo 200 joined rows cho một Order dù dữ liệu thực tế chỉ có 31 logical records. Network payload, materialization và memory tăng mạnh.

## 3. How does it work?

```text
Single query:
Orders JOIN Lines JOIN AuditEntries
=> duplicated parent/child columns

Split query:
SELECT Orders...
SELECT Lines ... WHERE OrderId IN (...)
SELECT AuditEntries ... WHERE OrderId IN (...)
=> EF materializes and fixes relationships
```

Đổi lại, nhiều query nghĩa là nhiều database commands và có thể quan sát dữ liệu ở các thời điểm khác nhau nếu không có transaction isolation phù hợp.

## 4. Practical implementation

```csharp
var order = await db.Orders
    .AsNoTracking()
    .Include(x => x.Lines)
    .Include(x => x.AuditEntries)
    .AsSplitQuery()
    .SingleAsync(x => x.Id == id, cancellationToken);
```

Nếu API chỉ cần DTO, projection thường còn tốt hơn:

```csharp
var dto = await db.Orders
    .Where(x => x.Id == id)
    .Select(x => new OrderDto(
        x.Id,
        x.Lines.Select(l => new LineDto(l.Id, l.Quantity)).ToList()))
    .SingleAsync(cancellationToken);
```

## 5. Real production scenario

Order detail endpoint bắt đầu chậm khi audit history lớn. SQL execution time không quá cao nhưng response từ DB rất lớn. Query inspection cho thấy hai collection `Include` nhân số row. Projection hoặc split query giảm dữ liệu truyền đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → memory và latency tăng theo số collection.  
**Evidence** → generated SQL có nhiều sibling JOIN; row count lớn bất thường.  
**Hypothesis** → cartesian explosion.  
**Diagnosis** → đo row count, payload và compare single/split/projection.  
**Fix** → ưu tiên projection nếu contract không cần entity graph; nếu cần graph, cân nhắc split query.  
**Verification** → đo DB round trips, bytes transferred, allocations và latency.

## 7. Common mistakes

Thêm `AsSplitQuery` như universal fix; load cả graph khi DTO chỉ cần vài field; bỏ qua consistency giữa các split queries; không benchmark network latency.

## 8. Alternatives

Projection thường tốt nhất cho read API. Explicit loading cho workflow có điều kiện. Single query vẫn hợp lý với graph nhỏ hoặc latency giữa app và DB cao.

## 9. Trade-offs

### Advantages

Giảm duplicated rows và memory/network cost khi nhiều collection được include.

### Costs / Risks

Tăng round trips/commands, consistency semantics phức tạp hơn và có thể tệ hơn khi DB ở xa.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` không miễn phí và LINQ cuối cùng trở thành SQL.

### Middle

Biết xem generated SQL và dùng projection/split query đúng tình huống.

### Senior

Đánh giá row multiplication, round trips, isolation và materialization cost.

### Technical Lead / Architect

Định nghĩa query boundary cho read model và tránh để persistence convenience quyết định API shape.

## 11. Key takeaway

- `AsSplitQuery` giải quyết một class vấn đề, không phải mọi slow query.
- Projection thường là lựa chọn tốt hơn cho API read model.
- Luôn đo SQL shape, row count, round trips và consistency requirement.

# 4. SQL connection pool exhaustion: khi API timeout dù database chưa hết CPU

## 1. What is it?

ADO.NET connection pooling tái sử dụng physical database connections. Pool exhaustion xảy ra khi request cần connection nhưng pool không còn connection khả dụng; request phải chờ và cuối cùng timeout.

## 2. Why does it exist?

Mở connection vật lý cho mỗi query rất đắt. Pooling giảm handshake/authentication cost. Nhưng pool hữu hạn cũng là resource boundary: connection bị giữ quá lâu sẽ biến concurrency của API thành queue chờ database connection.

## 3. How does it work?

```text
HTTP requests
   |
   v
Connection Pool [conn][conn][conn] ... max
   |                         ^
   v                         |
SQL Server <--- return connection on Close/Dispose
```

`OpenAsync` thường lấy connection từ pool; `Close/Dispose` trả nó về pool, không nhất thiết đóng TCP connection.

## 4. Practical implementation

Giữ transaction/connection scope ngắn và luôn dispose:

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(cancellationToken);

await using var command = connection.CreateCommand();
command.CommandText = """
    SELECT Id, Status
    FROM Orders
    WHERE Id = @id
    """;
command.Parameters.AddWithValue("@id", orderId);

await using var reader = await command.ExecuteReaderAsync(cancellationToken);
```

Với EF Core, scoped `DbContext` và async query đúng cách thường quản lý open/close tự động; vấn đề thường đến từ long-running transaction/query hoặc manual connection misuse.

## 5. Real production scenario

API có 200 concurrent requests. Một external call vô tình được thực hiện bên trong database transaction, khiến connection bị giữ 5–10 giây. SQL CPU chỉ 30%, nhưng pool đầy và request mới timeout ở bước lấy connection.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout tăng, SQL CPU bình thường.  
**Evidence** → waiting requests tăng, connection metrics chạm giới hạn; traces cho thấy thời gian trước query execution dài.  
**Hypothesis** → pool exhaustion.  
**Diagnosis** → kiểm tra long transactions, slow queries, leaked readers/connections và dependency call trong transaction.  
**Fix** → rút ngắn connection ownership, tối ưu slow path; chỉ tăng pool size sau khi hiểu bottleneck.  
**Verification** → connection wait giảm, pool headroom ổn định, p95/p99 hồi phục.

## 7. Common mistakes

Tăng `Max Pool Size` ngay lập tức; giữ transaction xuyên HTTP call; tạo nhiều connection strings hơi khác nhau làm phân mảnh pool; quên dispose reader/connection; nhầm pool exhaustion với “database cần scale”.

## 8. Alternatives

Không có thay thế trực tiếp cho pooling trong relational access; có thể giảm concurrency bằng backpressure, tối ưu query, cache read phù hợp hoặc thay đổi workload architecture.

## 9. Trade-offs

### Advantages

Pooling cho throughput cao với chi phí kết nối thấp.

### Costs / Risks

Pool lớn hơn có thể đẩy áp lực sang SQL Server; pool nhỏ tạo queue sớm hơn nhưng đôi khi bảo vệ database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu connection là resource hữu hạn và phải dispose.

### Middle

Biết đọc timeout stack, metrics và scope transaction.

### Senior

Phân biệt query latency, pool wait và DB saturation; thiết kế backpressure.

### Technical Lead / Architect

Chọn concurrency budget giữa application instances và database capacity thay vì cấu hình từng service độc lập.

## 11. Key takeaway

- SQL CPU thấp không loại trừ database-path bottleneck.
- Connection lifetime dài có thể nguy hiểm hơn số query.
- Tăng pool size không sửa root cause và có thể chuyển outage xuống database.

# 5. Redis cache stampede: single-flight, TTL jitter và stale-data strategy

## 1. What is it?

Cache stampede xảy ra khi nhiều request đồng thời miss cùng một hot key và cùng truy cập origin/database để rebuild cache. Cache vốn để giảm load lại trở thành trigger tạo load spike.

## 2. Why does it exist?

TTL tạo một thời điểm mà key biến mất. Với key có traffic lớn, hàng nghìn request có thể cùng quan sát miss trong vài millisecond. Cache-aside đơn giản không coordination giữa các caller.

## 3. How does it work?

```text
1000 requests -> Redis: MISS
               -> 1000 DB queries  <-- stampede

Single-flight:
1000 requests -> one loader -> DB
              -> others wait/share result
              -> Redis SET
```

TTL jitter làm các key không expire cùng lúc; stale-while-revalidate cho phép trả dữ liệu cũ trong freshness budget trong lúc một worker refresh.

## 4. Practical implementation

Trong một instance có thể dùng keyed `SemaphoreSlim` để single-flight; multi-instance cần chiến lược khác vì in-process lock không coordinate toàn cluster. Đừng mặc định distributed lock là câu trả lời duy nhất.

```csharp
var cached = await cache.GetStringAsync(key, ct);
if (cached is not null)
    return JsonSerializer.Deserialize<Product>(cached)!;

var product = await db.Products
    .AsNoTracking()
    .SingleAsync(x => x.Id == id, ct);

var ttl = TimeSpan.FromMinutes(5)
          + TimeSpan.FromSeconds(Random.Shared.Next(0, 30));

await cache.SetStringAsync(
    key,
    JsonSerializer.Serialize(product),
    new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = ttl },
    ct);

return product;
```

Đoạn trên có jitter nhưng chưa single-flight cross-instance; đó là quyết định kiến trúc riêng.

## 5. Real production scenario

Homepage cache chứa campaign data hết hạn đúng 09:00. 20 app instances cùng miss, SQL read tăng đột biến và timeout. Root cause không phải Redis chậm mà là synchronized expiration.

## 6. Failure scenario & troubleshooting

**Symptom** → DB spike theo chu kỳ TTL.  
**Evidence** → cache miss ratio tăng đột ngột cùng timestamp; hot key rõ ràng.  
**Hypothesis** → synchronized expiration/stampede.  
**Diagnosis** → correlate Redis misses với DB QPS.  
**Fix** → jitter, request coalescing, refresh-ahead hoặc stale serving theo business tolerance.  
**Verification** → miss distribution phẳng hơn và DB không còn burst.

## 7. Common mistakes

Đặt cùng TTL cho hàng nghìn key; distributed lock không timeout; giữ lock khi gọi dependency chậm; không có fallback khi Redis down; cache dữ liệu không được phép stale.

## 8. Alternatives

No-cache nếu database đủ nhanh; IMemoryCache cho instance-local data; CDN cho HTTP/static content; materialized read model nếu vấn đề thực sự là expensive aggregation.

## 9. Trade-offs

### Advantages

Cache giảm latency và origin load.

### Costs / Risks

Freshness, invalidation, failure mode và coordination complexity tăng. Một cache critical có thể trở thành dependency cần SLO riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss dẫn tới origin load.

### Middle

Implement TTL, key design và metrics.

### Senior

Thiết kế stampede protection, stale budget và outage behavior.

### Technical Lead / Architect

Quyết định cache có nên tồn tại, ownership invalidation và acceptable consistency.

## 11. Key takeaway

- Hot-key expiration là concurrency event, không chỉ là cache event.
- TTL jitter và single-flight giải quyết hai khía cạnh khác nhau.
- Freshness budget phải là business decision.

# 6. Azure Service Bus idempotent consumer: xử lý at-least-once delivery mà không double side effect

## 1. What is it?

Idempotent consumer đảm bảo xử lý lại cùng logical message không tạo thêm side effect ngoài ý muốn. Azure Service Bus có thể redeliver message khi lock hết hạn, connection mất hoặc settlement không tới broker.

## 2. Why does it exist?

Trong distributed system không thể giả định “handler chạy đúng một lần”. Một handler có thể commit database thành công rồi crash trước `CompleteMessageAsync`; broker hợp lý khi giao lại message.

## 3. How does it work?

```text
Service Bus -> Consumer
Consumer -> DB: commit business change + processed MessageId
Consumer -> Service Bus: Complete
                       X connection lost

Service Bus -> redeliver same message
Consumer -> DB: MessageId already processed
Consumer -> Complete without duplicate side effect
```

Deduplication phải nằm gần side effect cần bảo vệ. Broker duplicate detection không thay thế hoàn toàn application idempotency.

## 4. Practical implementation

Tạo unique constraint trên `ProcessedMessages(MessageId, Consumer)`. Trong cùng transaction với business update, insert marker:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

if (await db.ProcessedMessages.AnyAsync(
        x => x.MessageId == messageId && x.Consumer == "Billing", ct))
{
    await tx.RollbackAsync(ct);
    return;
}

invoice.MarkPaid();

db.ProcessedMessages.Add(new ProcessedMessage(messageId, "Billing"));
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Race condition cuối cùng nên được bảo vệ bằng unique constraint, không chỉ `AnyAsync`.

## 5. Real production scenario

PaymentConfirmed được xử lý thành công nhưng worker restart trước settlement. Message được giao lại; nếu handler gửi email và cộng loyalty points lần nữa, user nhận duplicate side effect. Database idempotency key ngăn update lặp; email/outbound event cần boundary riêng, thường kết hợp Outbox.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate order state/email sau restart.  
**Evidence** → cùng `MessageId` xuất hiện ở nhiều processing attempts.  
**Hypothesis** → redelivery sau lost settlement/lock expiry.  
**Diagnosis** → trace broker delivery count và transaction timeline.  
**Fix** → durable deduplication + idempotent state transition + Outbox cho side effect tiếp theo.  
**Verification** → replay cùng message nhiều lần và assert state chỉ thay đổi một lần.

## 7. Common mistakes

Tin rằng queue là exactly-once; dedupe bằng in-memory cache; đánh dấu processed trước business commit; dùng message ID không stable qua retry; retry non-idempotent external API không có idempotency key.

## 8. Alternatives

Business operation tự nhiên idempotent có thể không cần inbox table. Azure Service Bus duplicate detection giúp ở producer/broker layer nhưng không bao phủ mọi consumer failure window.

## 9. Trade-offs

### Advantages

Cho phép retry/redelivery an toàn và tăng reliability.

### Costs / Risks

Thêm storage, retention/cleanup và transaction logic; idempotency key design sai có thể suppress message hợp lệ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu message có thể được giao nhiều lần.

### Middle

Implement dedupe và integration test replay.

### Senior

Phân tích crash windows, transaction boundary và external side effects.

### Technical Lead / Architect

Định nghĩa delivery semantics, message identity, retention và ownership giữa Outbox/Inbox/broker.

## 11. Key takeaway

- At-least-once delivery yêu cầu consumer nghĩ theo replay.
- Dedupe phải durable và gần transaction chứa side effect.
- “Complete sau success” vẫn có failure window; idempotency đóng failure window đó.

# 7. Kubernetes readiness vs liveness probe: tránh biến health check thành nguyên nhân outage

## 1. What is it?

Readiness trả lời “Pod này có nên nhận traffic không?”. Liveness trả lời “process này có cần restart không?”. Hai câu hỏi khác nhau và dùng sai có thể tạo outage.

## 2. Why does it exist?

Process chạy không đồng nghĩa application sẵn sàng phục vụ. Startup có thể cần warm-up; dependency có thể tạm unavailable. Kubernetes cần tín hiệu để route traffic và restart process đúng mục đích.

## 3. How does it work?

```text
readiness fails -> Pod stays alive, removed from Service endpoints
liveness fails  -> kubelet restarts container
```

Nếu liveness phụ thuộc trực tiếp vào SQL/Redis, một dependency outage có thể khiến mọi pod restart đồng loạt dù restart không sửa được dependency.

## 4. Practical implementation

ASP.NET Core có thể tag checks:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, tags: ["ready"]);

app.MapHealthChecks("/health/live", new()
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new()
{
    Predicate = check => check.Tags.Contains("ready")
});
```

Deployment:

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
```

## 5. Real production scenario

SQL có outage 2 phút. Liveness endpoint kiểm tra SQL nên tất cả pods fail và restart. Khi SQL hồi phục, pods đồng loạt startup gây connection storm. Nếu SQL chỉ ảnh hưởng readiness phù hợp, pods có thể giữ process sống và hồi phục nhẹ nhàng.

## 6. Failure scenario & troubleshooting

**Symptom** → `RESTARTS` tăng mạnh cùng dependency outage.  
**Evidence** → `kubectl describe pod` cho thấy liveness failures.  
**Hypothesis** → liveness quá sâu.  
**Diagnosis** → inspect endpoint dependency graph.  
**Fix** → liveness chỉ kiểm tra process-level viability; readiness phản ánh ability phục vụ traffic theo thiết kế.  
**Verification** → mô phỏng dependency failure và xác nhận pod không restart loop.

## 7. Common mistakes

Dùng cùng endpoint cho cả hai probe; timeout quá ngắn; probe gọi expensive dependency; không có startup probe cho app warm-up lâu; health endpoint trả 200 dù check nội bộ failed.

## 8. Alternatives

Ở App Service có health-check semantics khác nhưng nguyên tắc vẫn là phân biệt process health với traffic readiness. Với worker không nhận HTTP traffic, readiness cần được thiết kế theo workload thay vì copy web pattern.

## 9. Trade-offs

### Advantages

Traffic routing và self-healing tốt hơn.

### Costs / Risks

Probe sai tạo false positive/negative, restart storm và dependency amplification.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Nhớ readiness = nhận traffic; liveness = restart.

### Middle

Implement endpoint và cấu hình probe.

### Senior

Thiết kế dependency semantics, timeout và startup behavior.

### Technical Lead / Architect

Quyết định failure isolation: dependency nào khiến instance unavailable, dependency nào chỉ degrade feature.

## 11. Key takeaway

- Liveness không nên là “mọi dependency đều khỏe”.
- Restart chỉ hữu ích nếu restart có khả năng sửa trạng thái lỗi.
- Health checks là control-plane input, không chỉ monitoring endpoint.

# 8. Vue/TypeScript async race: response cũ ghi đè state mới và cách kiểm soát request lifecycle

## 1. What is it?

Async race ở frontend xảy ra khi nhiều request được phát theo thứ tự A rồi B nhưng response về B rồi A; code naïve cập nhật state theo arrival order khiến UI hiển thị dữ liệu cũ.

## 2. Why does it exist?

Network latency không deterministic. Search-as-you-type, route change và filter UI dễ tạo overlapping requests. `await` làm code trông tuần tự trong từng function call nhưng không serialize nhiều invocations.

## 3. How does it work?

```text
User types "ca"  -> request A ----------------> response A (late)
User types "car" -> request B -----> response B
                                   UI = "car"
                                             UI = "ca"  <-- stale overwrite
```

## 4. Practical implementation

Dùng `AbortController` để hủy request cũ:

```typescript
let currentController: AbortController | undefined;

async function search(term: string) {
  currentController?.abort();
  const controller = new AbortController();
  currentController = controller;

  try {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(term)}`,
      { signal: controller.signal }
    );

    if (!response.ok) throw new Error(`HTTP ${response.status}`);

    const data = await response.json();
    if (currentController === controller) {
      results.value = data;
    }
  } catch (error) {
    if ((error as DOMException).name !== "AbortError") throw error;
  }
}
```

## 5. Real production scenario

Marketplace filter thay đổi brand rồi price rất nhanh. Response của filter cũ về sau và overwrite Pinia/component state. Backend đúng nhưng UI “nhảy ngược”, tạo bug khó reproduce trên mạng local nhanh.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị result không khớp filter hiện tại.  
**Evidence** → DevTools Network cho thấy request order khác response completion order.  
**Hypothesis** → stale response writes.  
**Diagnosis** → thêm request sequence ID vào logs/dev instrumentation.  
**Fix** → cancellation hoặc latest-request-wins guard.  
**Verification** → throttle network và thao tác filter liên tục.

## 7. Common mistakes

Chỉ debounce mà nghĩ đã hết race; abort request nhưng vẫn update state trong catch/finally sai; global loading boolean cho nhiều concurrent requests; backend response không chứa enough context để debug.

## 8. Alternatives

Debounce giảm số request nhưng không bảo đảm ordering. Sequence number/latest-token guard đơn giản nếu transport không hỗ trợ cancel. RxJS `switchMap` giải quyết pattern tương tự nhưng có thể quá nặng cho Vue app nhỏ.

## 9. Trade-offs

### Advantages

Cancellation giảm wasted work và stale UI.

### Costs / Risks

Lifecycle phức tạp hơn; backend có thể đã nhận request dù browser abort, nên cancellation không thay thế server-side idempotency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request có thể hoàn thành khác thứ tự gửi.

### Middle

Implement cancellation, loading/error state và network tests.

### Senior

Phân biệt UI cancellation với server cancellation/idempotency và quan sát race bằng telemetry.

### Technical Lead / Architect

Đặt convention cho data-fetch lifecycle và tránh mỗi component tự phát minh concurrency semantics.

## 11. Key takeaway

- `await` không ngăn race giữa nhiều function invocations.
- Debounce giảm traffic; cancellation/latest-wins bảo vệ state correctness.
- Test frontend race bằng network throttling, không chỉ localhost.

# 9. Feature flags trong CI/CD: tách deployment khỏi release nhưng không tạo “distributed if statement”

## 1. What is it?

Feature flag cho phép code đã deploy nhưng behavior được bật/tắt độc lập. Nó tách “artifact đã tới Production” khỏi “user đã được sử dụng feature”.

## 2. Why does it exist?

Big-bang release làm rollback artifact trở thành công cụ duy nhất khi feature lỗi. Flag cho phép progressive rollout, kill switch và kiểm soát exposure mà không cần build/deploy lại.

## 3. How does it work?

```text
commit -> build -> test -> artifact -> deploy
                                  |
                                  v
                         feature disabled
                                  |
                         enable 5% -> 25% -> 100%
                                  |
                              telemetry
```

Flag evaluation có thể dựa trên environment, user cohort hoặc percentage. Nhưng business-critical authorization không được thay bằng feature flag.

## 4. Practical implementation

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
{
    return await newCheckout.ExecuteAsync(request, ct);
}

return await legacyCheckout.ExecuteAsync(request, ct);
```

Cả hai paths phải tương thích với database schema trong rollout window. Migration nên theo expand/contract thay vì drop column trước khi old path ngừng dùng.

## 5. Real production scenario

New checkout deploy cùng release nhưng chỉ bật cho internal users. Metrics ổn mới tăng rollout. Khi payment error tăng, team disable flag trong vài phút mà không rollback unrelated fixes trong artifact.

## 6. Failure scenario & troubleshooting

**Symptom** → behavior khác nhau giữa instances/users khó reproduce.  
**Evidence** → logs không ghi flag evaluation/cohort.  
**Hypothesis** → dynamic configuration hoặc stale flag cache.  
**Diagnosis** → correlate request với flag state/version.  
**Fix** → observable evaluation, bounded cache TTL, explicit default behavior.  
**Verification** → canary tests cho both enabled/disabled paths.

## 7. Common mistakes

Flag tồn tại vĩnh viễn; nested flags tạo combinatorial state; dùng flag thay authorization; không test off-path sau nhiều tháng; database migration không backward compatible.

## 8. Alternatives

Deployment slots/Blue-Green đổi toàn environment; Canary routing rollout theo traffic; branch/redeploy đơn giản hơn với feature nhỏ ít rủi ro. Các kỹ thuật có thể kết hợp nhưng không đồng nghĩa.

## 9. Trade-offs

### Advantages

Release control nhanh, progressive delivery, giảm blast radius.

### Costs / Risks

Tăng state space, testing burden, config dependency và technical debt nếu không xóa flag.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy và release có thể là hai sự kiện khác nhau.

### Middle

Implement flag và tests cho cả hai paths.

### Senior

Thiết kế telemetry, rollback semantics và schema compatibility.

### Technical Lead / Architect

Đặt lifecycle/owner/expiry cho flag và quyết định khi nào progressive rollout đáng complexity.

## 11. Key takeaway

- Feature flag là release-control mechanism, không phải authorization.
- Mỗi flag tạo thêm runtime state phải test và quan sát.
- Flag cần owner và ngày xóa, nếu không sẽ trở thành kiến trúc vĩnh viễn.

# 10. SSRF trong third-party integration: bảo vệ outbound HTTP như một security boundary

## 1. What is it?

Server-Side Request Forgery (SSRF) xảy ra khi attacker ảnh hưởng được URL mà server gọi, khiến server truy cập tài nguyên attacker không thể truy cập trực tiếp: loopback, private network, cloud metadata endpoint hoặc internal admin service.

Mental model: outbound HTTP từ backend mang network trust của backend, không phải trust của user.

## 2. Why does it exist?

Các feature như “import image from URL”, webhook tester, PDF-from-URL hoặc proxy API thường nhận URL từ user. Nếu backend gọi URL tùy ý, firewall perimeter có thể bị vượt qua từ bên trong.

## 3. How does it work?

```text
Attacker
  -> Public API: fetch http://internal-service/admin
       -> Backend outbound HTTP
            -> private network resource
       <- sensitive response
  <- leaked/derived information
```

Chặn chỉ hostname ban đầu chưa đủ nếu redirect hoặc DNS resolution dẫn tới private address.

## 4. Practical implementation

Ưu tiên allowlist destination rõ ràng thay vì blacklist:

```csharp
static bool IsAllowed(Uri uri)
{
    if (uri.Scheme != Uri.UriSchemeHttps)
        return false;

    var allowedHosts = new HashSet<string>(StringComparer.OrdinalIgnoreCase)
    {
        "api.partner.example",
        "cdn.partner.example"
    };

    return allowedHosts.Contains(uri.Host);
}
```

Production design còn phải kiểm soát redirects, DNS/IP ranges, timeout, response size, content type và egress networking. Với fixed third-party integration, URL base nên nằm trong trusted configuration; user chỉ cung cấp resource identifier.

## 5. Real production scenario

CMS cho editor nhập remote image URL. Backend tải image để resize. Một compromised editor account nhập URL tới internal admin endpoint. Nếu service có private network access, feature image import trở thành network pivot.

## 6. Failure scenario & troubleshooting

**Symptom** → outbound logs xuất hiện request tới loopback/private IP hoặc hostname lạ.  
**Evidence** → trace nối request user với `HttpClient` destination.  
**Hypothesis** → user-controlled URL bypass validation/redirect.  
**Diagnosis** → kiểm tra input flow, DNS resolution, redirects và egress policy.  
**Fix** → strict allowlist, disable/validate redirects, network egress restriction, least privilege.  
**Verification** → security tests với localhost, RFC1918/private ranges, alternate encodings và redirect chain.

## 7. Common mistakes

Blacklist `localhost` nhưng bỏ private IP; validate string prefix thay vì parsed URI; cho phép redirect sang host khác; không giới hạn response size; log full URL có secret query string; dùng user-supplied URL trực tiếp trong `HttpClient`.

## 8. Alternatives

Nếu integration có known partner, nhận ID rồi server tự xây URL trusted là đơn giản và an toàn hơn. Với arbitrary user content, upload trực tiếp vào Blob Storage qua controlled upload flow thường tốt hơn server fetch URL.

## 9. Trade-offs

### Advantages

URL fetching mang lại UX tiện và integration flexibility.

### Costs / Risks

Mở thêm outbound attack surface, DNS/redirect complexity và operational controls. Strict allowlist giảm flexibility nhưng giảm mạnh SSRF risk.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu input URL cũng là untrusted input.

### Middle

Validate URI, timeout, size và destination.

### Senior

Hiểu DNS rebinding, redirect, private network exposure, telemetry và egress controls.

### Technical Lead / Architect

Quyết định service có thực sự cần arbitrary outbound access, thiết kế network boundary và least-privilege connectivity.

## 11. Key takeaway

- Outbound request do user điều khiển là security boundary.
- Allowlist + egress restriction mạnh hơn blacklist URL.
- Cách an toàn nhất thường là không cho user quyết định destination ngay từ đầu.
