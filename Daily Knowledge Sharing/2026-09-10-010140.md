# 1. .NET Tiered Compilation + Dynamic PGO: JIT tối ưu hot code theo runtime behavior thay vì tối ưu mọi method ngay từ đầu

## 1. What is it?

Mental model đơn giản:

```text
IL code
  ↓
JIT compile nhanh để application khởi động
  ↓
Runtime quan sát method nào thực sự nóng
  ↓
Recompile hot methods với optimization mạnh hơn
```

Tiered Compilation cho phép CLR dùng nhiều mức JIT optimization thay vì compile mọi method ngay lập tức với mức tối ưu cao nhất. Dynamic PGO (Profile-Guided Optimization) bổ sung runtime profile như branch behavior, type distribution hoặc call patterns để JIT tối ưu dựa trên workload thực tế.

Điểm quan trọng: đây là runtime optimization strategy, không phải lý do để developer bỏ qua algorithm, allocation hoặc I/O bottleneck.

## 2. Why does it exist?

Nếu JIT tối ưu mọi method rất mạnh ngay khi startup, startup time và CPU compile cost tăng. Nhiều method có thể chỉ chạy một lần hoặc không bao giờ chạy.

Nếu JIT chỉ compile nhanh và đơn giản, startup tốt nhưng long-running throughput kém.

Tiered Compilation giải quyết mâu thuẫn:

```text
startup latency ↔ steady-state throughput
```

Dynamic PGO còn giúp JIT ra quyết định dựa trên runtime data thay vì giả định generic.

## 3. How does it work?

Một method có thể bắt đầu ở tier nhanh, ít optimization. Khi runtime xác định method đủ hot, CLR có thể yêu cầu compile lại với optimization mạnh hơn.

Dynamic PGO có thể quan sát branch probabilities hoặc concrete types thường xuất hiện để hỗ trợ devirtualization, inlining hoặc code layout tốt hơn.

Ví dụ interface call:

```csharp
public decimal CalculateTotal(IPricingStrategy strategy, Order order)
    => strategy.Calculate(order);
```

Nếu runtime gần như luôn thấy cùng một implementation của `IPricingStrategy`, JIT có thể có cơ hội tối ưu call path tốt hơn so với trường hợp type distribution hoàn toàn ngẫu nhiên.

## 4. Practical implementation

Bạn thường không “code Dynamic PGO” trực tiếp. Việc cần làm là benchmark workload đúng:

```csharp
[MemoryDiagnoser]
public class PricingBenchmark
{
    private readonly PricingService _service = new();
    private readonly Order _order = Order.CreateSample();

    [Benchmark]
    public decimal Calculate()
        => _service.Calculate(_order);
}
```

Khi benchmark, phân biệt:

* cold-start measurement
* warm steady-state measurement
* throughput sau khi JIT đã optimize hot methods

Không lấy một lần gọi đầu tiên làm đại diện cho production throughput.

## 5. Real production scenario

Một ASP.NET Core API có endpoint pricing được gọi hàng nghìn lần/giây. Sau deploy, p95 30 giây đầu cao hơn rõ rệt, sau đó ổn định.

Nếu chỉ đo local warm process, team có thể không thấy cold-start regression. Nếu chỉ đo startup, lại có thể bỏ qua lợi ích steady-state của tiered optimization.

Ở autoscaling workload, cả hai đều quan trọng vì pods mới được tạo thường xuyên.

## 6. Failure scenario & troubleshooting

**Symptom** → benchmark kết quả rất biến động giữa run đầu và các run sau.

**Evidence** → CPU profile cho thấy JIT activity cao lúc đầu, throughput cải thiện dần.

**Hypothesis** → đang trộn cold-start cost với steady-state measurement.

**Diagnosis** → tách warmup, đo JIT events nếu cần, dùng BenchmarkDotNet và production-like request profile.

**Fix** → benchmark đúng phase; tối ưu startup riêng nếu autoscaling/cold start là SLO quan trọng.

**Verification** → so sánh startup latency, p95 steady-state và CPU sau warmup.

## 7. Common mistakes

* Benchmark một method đúng một lần rồi kết luận runtime chậm.
* Tắt runtime optimization để “ổn định benchmark” nhưng production lại chạy config khác.
* Tập trung JIT trong khi bottleneck thực là SQL hoặc network.
* Dùng microbenchmark để suy ra end-to-end latency.
* Giả định code đã warm trên mỗi container mới.

## 8. Alternatives

ReadyToRun hoặc Native AOT giải quyết startup/deployment trade-off theo cách khác. Tuy nhiên chúng có constraints và optimization model riêng. Không có lựa chọn “tốt nhất cho mọi application”.

## 9. Trade-offs

### Advantages

* Startup nhanh hơn so với tối ưu toàn bộ ngay lập tức.
* Hot code có thể đạt steady-state performance tốt hơn.
* Dynamic profile giúp tối ưu theo workload thực.

### Costs / Risks

* Performance thay đổi theo thời gian chạy.
* Benchmark khó hơn.
* Cold-start và warm performance có thể khác đáng kể.
* Runtime optimization không thay thế thiết kế application tốt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu C# được compile thành IL và CLR/JIT biến IL thành machine code lúc runtime.

### Middle

Biết warmup ảnh hưởng benchmark và startup.

### Senior

Phân biệt cold-path, hot-path, JIT cost và steady-state throughput khi profiling.

### Technical Lead / Architect

Quyết định khi startup SLO đủ quan trọng để xem xét Native AOT/ReadyToRun hoặc pre-warming; không tối ưu runtime chỉ vì microbenchmark đẹp hơn.

## 11. Key takeaway

* Tiered Compilation cân bằng startup và steady-state performance.
* Dynamic PGO tối ưu hot paths dựa trên runtime behavior.
* Luôn đo cold-start và steady-state riêng nếu workload scale động.

# 2. ASP.NET Core Rate Limiting: Token Bucket, Concurrency Limiter và cách partition limiter theo user/API key

## 1. What is it?

Rate limiting kiểm soát lượng công việc một client hoặc nhóm clients được phép tạo trong một khoảng thời gian.

Mental model:

```text
request
  ↓
identify partition
  ↓
apply limiter policy
  ↓
permit / queue / reject
```

Trong ASP.NET Core, limiter có thể dựa trên fixed window, sliding window, token bucket hoặc concurrency.

## 2. Why does it exist?

Nếu API chỉ có một global limit, một noisy client có thể dùng hết quota của tất cả users. Nếu không limit gì, brute force, crawler, accidental retry loop hoặc partner integration bug có thể kéo database/downstream service xuống theo.

Rate limiter bảo vệ capacity và fairness, nhưng không thay authorization, anti-DDoS infrastructure hoặc backpressure nội bộ.

## 3. How does it work?

Token Bucket cho phép burst có kiểm soát:

```text
bucket có N tokens
mỗi request tiêu 1 token
tokens được refill theo thời gian
```

Concurrency limiter lại giới hạn số operations đồng thời, hữu ích cho endpoint giữ expensive database connection hoặc gọi dependency latency cao.

Partitioning quan trọng: quota thường nên tách theo API key, tenant, authenticated user hoặc IP tùy trust model.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("per-user", httpContext =>
    {
        var userId = httpContext.User.FindFirst("sub")?.Value
                     ?? httpContext.Connection.RemoteIpAddress?.ToString()
                     ?? "anonymous";

        return RateLimitPartition.GetTokenBucketLimiter(
            partitionKey: userId,
            factory: _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 20,
                ReplenishmentPeriod = TimeSpan.FromSeconds(10),
                AutoReplenishment = true,
                QueueLimit = 0
            });
    });
});

app.UseRateLimiter();
```

Response reject nên dùng `429 Too Many Requests`, và khi hợp lý trả `Retry-After`.

## 5. Real production scenario

Một public search API có 2.000 tenants. Một tenant deploy bug và gửi 5.000 requests/second thay vì 50.

Global limiter làm 1 tenant khiến 1.999 tenants còn lại bị reject. Partitioned limiter theo tenant giữ blast radius nhỏ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → người dùng hợp lệ nhận nhiều `429` dù tổng traffic thấp.

**Evidence** → quota key đang dựa trên IP; toàn bộ office users đi qua cùng NAT IP.

**Hypothesis** → partition key không phản ánh identity/fairness boundary.

**Diagnosis** → log limiter partition key, reject count, endpoint và authenticated principal.

**Fix** → với authenticated traffic, partition theo user/tenant/API key; giữ IP limiter như lớp bổ sung cho anonymous abuse.

**Verification** → load test nhiều tenants với skewed traffic và xác nhận noisy tenant không ảnh hưởng tenant khác.

## 7. Common mistakes

* Một global limit cho tất cả users.
* Chỉ limit theo IP trong enterprise/NAT environment.
* Queue hàng nghìn requests thay vì reject, khiến latency bùng nổ.
* Retry `429` ngay lập tức từ client.
* Không rate limit login/password reset endpoints.
* Rate limit ở app nhưng bỏ qua CDN/API gateway capacity phía trước.

## 8. Alternatives

Azure API Management, Azure Front Door/WAF, reverse proxy hoặc CDN có thể enforce limit trước application. App-level limiter phù hợp khi policy cần user/tenant/business context.

## 9. Trade-offs

### Advantages

* Bảo vệ downstream capacity.
* Tạo fairness giữa clients.
* Giảm blast radius của retry loop hoặc integration bug.

### Costs / Risks

* Policy sai có thể reject legitimate traffic.
* Distributed instances cần hiểu policy state nằm ở đâu.
* Queueing làm tăng latency nếu dùng sai.
* Rate limit không tự giải quyết overload nội bộ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `429` là capacity/policy response, không phải random server error.

### Middle

Cấu hình limiter và partition key phù hợp endpoint.

### Senior

Thiết kế limiter theo fairness, burst, retry behavior và downstream budget.

### Technical Lead / Architect

Quyết định enforcement layer: edge, gateway, application hoặc phối hợp nhiều lớp; định nghĩa quota theo business tier và SLO.

## 11. Key takeaway

* Rate limiting phải gắn với đúng partition boundary.
* Token Bucket phù hợp burst; Concurrency Limiter phù hợp scarce concurrent resources.
* `429` cần client retry strategy hợp lý, không retry storm.

# 3. SQL keyset pagination: tránh chi phí OFFSET lớn và giữ pagination ổn định khi dữ liệu thay đổi

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên giá trị sort cuối cùng của trang trước, thay vì bỏ qua N rows bằng `OFFSET`.

Mental model:

```text
OFFSET:
skip 100000 rows → take 50

Keyset:
WHERE (CreatedAt, Id) > last_seen_key → take 50
```

## 2. Why does it exist?

Offset pagination đơn giản:

```sql
ORDER BY CreatedAt, Id
OFFSET 100000 ROWS FETCH NEXT 50 ROWS ONLY;
```

Nhưng database vẫn phải xử lý/skip một lượng rows lớn. Trang càng sâu, cost thường càng tăng.

Ngoài ra dữ liệu insert/delete giữa hai page requests có thể làm duplicate/missing rows.

## 3. How does it work?

Giả sử sort ổn định theo `CreatedAt DESC, Id DESC`.

Trang đầu:

```sql
SELECT TOP (50) Id, CreatedAt, Title
FROM Orders
ORDER BY CreatedAt DESC, Id DESC;
```

Trang sau dùng last row:

```sql
SELECT TOP (50) Id, CreatedAt, Title
FROM Orders
WHERE CreatedAt < @LastCreatedAt
   OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Composite index phải phù hợp sort/access pattern.

## 4. Practical implementation

ASP.NET Core có thể encode cursor opaque:

```csharp
public sealed record OrderCursor(DateTime CreatedAt, long Id);

public async Task<IReadOnlyList<OrderDto>> GetPageAsync(
    OrderCursor? cursor,
    int pageSize,
    CancellationToken ct)
{
    var query = _db.Orders.AsNoTracking();

    if (cursor is not null)
    {
        query = query.Where(x =>
            x.CreatedAt < cursor.CreatedAt ||
            (x.CreatedAt == cursor.CreatedAt && x.Id < cursor.Id));
    }

    return await query
        .OrderByDescending(x => x.CreatedAt)
        .ThenByDescending(x => x.Id)
        .Take(pageSize)
        .Select(x => new OrderDto(x.Id, x.CreatedAt, x.Total))
        .ToListAsync(ct);
}
```

Cursor không nên để client sửa tùy ý nếu nó chứa state nhạy cảm; có thể Base64/sign khi cần.

## 5. Real production scenario

Admin portal hiển thị 20 triệu audit records. Trang 1 nhanh 30 ms, trang 10.000 mất vài giây vì OFFSET lớn.

Chuyển sang keyset theo `(OccurredAt, Id)` giữ latency gần ổn định giữa các page sâu, miễn là index phù hợp.

## 6. Failure scenario & troubleshooting

**Symptom** → records bị lặp giữa pages.

**Evidence** → sort chỉ dùng `CreatedAt`, nhiều rows có cùng timestamp.

**Hypothesis** → sort key không unique, cursor không xác định total order.

**Diagnosis** → kiểm tra duplicate sort values và generated SQL.

**Fix** → thêm stable tie-breaker như unique `Id` vào sort và cursor.

**Verification** → insert concurrent rows trong khi paginate và kiểm tra không duplicate/missing trong semantics mong muốn.

## 7. Common mistakes

* Cursor chỉ dùng non-unique field.
* Sort direction và cursor predicate không khớp.
* Không có composite index phù hợp.
* Expose raw internal fields khi API muốn opaque cursor.
* Dùng keyset dù UX bắt buộc “jump to page 500”.

## 8. Alternatives

OFFSET phù hợp datasets nhỏ và UI cần page numbers trực tiếp. Snapshot/materialized result phù hợp báo cáo cần stable total pages. Search engines có cursor/search-after semantics riêng.

## 9. Trade-offs

### Advantages

* Deep-page performance ổn định hơn.
* Ít duplicate/missing do row shifts.
* Phù hợp infinite scroll/feed.

### Costs / Risks

* Không nhảy page tùy ý dễ dàng.
* Cursor contract phức tạp hơn.
* Sort key phải ổn định và indexable.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu OFFSET phải skip rows trước khi lấy trang.

### Middle

Implement composite cursor đúng sort order.

### Senior

Đọc execution plan, thiết kế index và concurrency semantics.

### Technical Lead / Architect

Chọn pagination model theo UX, data size và consistency requirement thay vì mặc định OFFSET cho mọi API.

## 11. Key takeaway

* Keyset pagination tránh deep OFFSET cost.
* Cursor cần stable total ordering.
* Pagination strategy là API/data-access decision, không chỉ UI concern.

# 4. Redis hot key: khi một key duy nhất phá throughput dù cluster còn rất nhiều capacity

## 1. What is it?

Hot key là một Redis key nhận lượng traffic không cân đối so với các keys còn lại.

Mental model:

```text
100 nodes capacity
but
80% requests → one logical key → one shard/primary path
```

Horizontal scaling không giúp nhiều nếu workload không phân phối đều.

## 2. Why does it exist?

Redis rất nhanh, nên team thường nhìn aggregate CPU/memory và cho rằng cluster còn dư capacity. Nhưng sharding phân phối theo key; một key cực nóng có thể saturate một shard, network path hoặc command processing thread trong khi shards khác nhàn rỗi.

## 3. How does it work?

Ví dụ key:

```text
homepage:global
```

được đọc 100.000 lần/giây, trong khi hàng triệu keys khác gần như không được truy cập. Nếu mọi request đều về cùng shard, bottleneck là single-shard load.

Hot key còn nguy hiểm hơn nếu value lớn, command đắt hoặc thường xuyên invalidated.

## 4. Practical implementation

Phát hiện bằng telemetry/slowlog/command statistics và application metrics.

Mitigation tùy semantics:

* local `IMemoryCache` tầng trước cho cực-hot immutable/short-lived data
* request coalescing
* replicate derived data theo shard key nếu chấp nhận complexity
* giảm payload/value size
* tránh invalidation quá thường xuyên
* cache ở CDN nếu data public

Ví dụ two-level cache:

```csharp
if (_memoryCache.TryGetValue(key, out ProductDto? value))
    return value;

value = await _redis.GetAsync<ProductDto>(key, ct);
_memoryCache.Set(key, value, TimeSpan.FromSeconds(5));
return value;
```

Local cache chỉ hợp khi stale window chấp nhận được.

## 5. Real production scenario

E-commerce homepage cache một promotion configuration toàn cầu trong Redis. Campaign traffic tăng 20 lần. Redis cluster aggregate CPU chỉ 35%, nhưng shard chứa `campaign:homepage` lên 95% CPU/network.

Scale thêm shards không thay đổi hash placement của key đó theo cách giải quyết root cause.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis latency p99 tăng, nhưng cluster average CPU bình thường.

**Evidence** → một shard có command rate/CPU cao bất thường và top key chiếm phần lớn traffic.

**Hypothesis** → hot key skew.

**Diagnosis** → xem per-node metrics, hot-key analysis và application request distribution.

**Fix** → giảm fan-in vào key bằng local/edge cache hoặc redesign data access.

**Verification** → load test với skewed access pattern giống production, không chỉ random keys.

## 7. Common mistakes

* Chỉ xem average CPU toàn cluster.
* Tăng cluster size mà không thay access pattern.
* Shard một value logically rồi tăng consistency complexity vô lý.
* Dùng local cache cho security-critical data cần immediate revocation.
* Không giới hạn value size.

## 8. Alternatives

CDN phù hợp public cacheable data. `IMemoryCache` phù hợp per-instance fast path. Database direct read có thể đơn giản hơn nếu workload không thực sự cần Redis. Application-level snapshot có thể phù hợp configuration ít đổi.

## 9. Trade-offs

### Advantages của mitigation

* Giảm single-shard pressure.
* Giảm network round trips.
* Có thể giảm Redis dependency criticality.

### Costs / Risks

* Multi-layer cache tăng invalidation complexity.
* Local cache tạo stale divergence giữa instances.
* Key splitting có thể phá atomicity hoặc đơn giản hóa hiện tại.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache cluster không đồng nghĩa mọi key tự scale ngang.

### Middle

Biết xem per-node metrics và key distribution.

### Senior

Phân tích skew, cache hierarchy, freshness và failure behavior.

### Technical Lead / Architect

Quyết định có nên giữ Redis trong request path, thêm edge/local cache hay redesign ownership của hot data.

## 11. Key takeaway

* Aggregate cluster capacity có thể che giấu single-key bottleneck.
* Hot-key troubleshooting phải xem distribution, không chỉ averages.
* Mitigation luôn phải cân bằng throughput với freshness/correctness.

# 5. Inbox Pattern + idempotent consumer: xử lý duplicate message mà không biến “at-least-once” thành double side effect

## 1. What is it?

Inbox Pattern lưu dấu vết message đã xử lý trong cùng transactional boundary với business change của consumer.

Mental model:

```text
message arrives
  ↓
check Inbox(MessageId)
  ↓
not processed?
  ↓
apply business change + insert Inbox row
  ↓
commit atomically
```

Nếu message được giao lại, consumer thấy `MessageId` đã tồn tại và bỏ qua side effect.

## 2. Why does it exist?

Queue systems thường cung cấp at-least-once delivery. Message có thể được xử lý thành công nhưng acknowledgement bị mất do network/process crash. Broker giao lại message.

Nếu consumer thực hiện:

```text
Charge credit card
Increment balance
Send fulfillment command
```

mà không idempotent, duplicate delivery trở thành duplicate business action.

## 3. How does it work?

Consumer cần stable unique message identity.

Pseudo transaction:

```sql
BEGIN TRANSACTION;

IF EXISTS (SELECT 1 FROM Inbox WHERE MessageId = @MessageId)
    RETURN;

UPDATE Orders
SET Status = 'Paid'
WHERE Id = @OrderId;

INSERT INTO Inbox(MessageId, ProcessedAt)
VALUES (@MessageId, SYSUTCDATETIME());

COMMIT;
```

Unique constraint trên `Inbox.MessageId` là lớp correctness quan trọng khi nhiều consumers race.

## 4. Practical implementation

```csharp
public async Task HandleAsync(OrderPaid message, CancellationToken ct)
{
    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    var alreadyProcessed = await _db.InboxMessages
        .AnyAsync(x => x.MessageId == message.MessageId, ct);

    if (alreadyProcessed)
        return;

    var order = await _db.Orders.SingleAsync(x => x.Id == message.OrderId, ct);
    order.MarkPaid();

    _db.InboxMessages.Add(new InboxMessage
    {
        MessageId = message.MessageId,
        ProcessedAt = DateTimeOffset.UtcNow
    });

    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
```

Database unique index vẫn cần để chống concurrent duplicate race.

## 5. Real production scenario

Azure Service Bus consumer cập nhật loyalty points. Process commit DB xong nhưng bị kill trước `CompleteMessageAsync`. Broker redeliver message.

Không Inbox: points cộng hai lần.

Có Inbox: second delivery được detect và no-op.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate message logs xuất hiện nhưng business state vẫn đúng; Inbox table tăng nhanh.

**Evidence** → nhiều redeliveries hợp lệ do lock timeout/restart.

**Hypothesis** → dedup correctness tốt nhưng retention chưa được thiết kế.

**Diagnosis** → đo dedup hit rate, message age và Inbox growth.

**Fix** → retention/partition cleanup dựa trên broker maximum replay/redelivery window và business audit needs.

**Verification** → crash process sau DB commit trước broker settlement; redelivery không tạo side effect lần hai.

## 7. Common mistakes

* Check Inbox rồi commit business change và Inbox ở hai transactions khác nhau.
* Không có unique constraint.
* Dùng random ID mới ở mỗi retry từ producer.
* Xóa Inbox quá sớm.
* Nghĩ idempotency chỉ là “handler không throw”.

## 8. Alternatives

Business-level natural idempotency như `PUT`/upsert theo immutable operation ID đôi khi không cần Inbox table riêng. Broker duplicate detection giúp giảm duplicates nhưng không thay consumer-side correctness hoàn toàn. Exactly-once claims phải kiểm tra boundary cụ thể, không dùng như assumption chung.

## 9. Trade-offs

### Advantages

* Chống duplicate side effects đáng tin cậy.
* Audit được processed messages.
* Phù hợp at-least-once messaging.

### Costs / Risks

* Storage/cleanup overhead.
* Transaction dependency vào database consumer.
* Message identity/versioning phải ổn định.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu message có thể được giao nhiều lần.

### Middle

Implement dedup với unique message ID.

### Senior

Thiết kế atomic transaction, crash windows và retention.

### Technical Lead / Architect

Quyết định idempotency boundary ở business operation nào, phối hợp Outbox/Inbox và đặt recovery/audit policy toàn workflow.

## 11. Key takeaway

* At-least-once delivery đòi hỏi idempotent consumer.
* Inbox chỉ đúng khi dedup record và business state commit cùng boundary.
* Unique constraint là correctness mechanism, không chỉ performance detail.

# 6. Azure Blob Storage SAS: Shared Key, Service SAS và User Delegation SAS dưới góc nhìn least privilege

## 1. What is it?

Shared Access Signature (SAS) là signed token cấp quyền giới hạn tới Azure Storage resource mà không trao storage account key cho client.

Mental model:

```text
trusted backend
  ↓ signs constrained permission
short-lived SAS
  ↓
client accesses Blob directly
```

SAS có thể giới hạn resource, permission, protocol, IP và expiry.

## 2. Why does it exist?

Nếu browser upload file 2 GB qua application server:

```text
Browser → App → Blob
```

application trở thành data proxy, tốn bandwidth, memory/socket và scale cost.

SAS cho phép:

```text
Browser → Blob directly
```

trong khi backend vẫn kiểm soát authorization trước khi phát token.

## 3. How does it work?

Hai hướng quan trọng:

* Service/Account SAS có thể được ký bằng storage account key.
* User Delegation SAS được ký dựa trên Microsoft Entra credentials và delegation key, phù hợp hướng least privilege hơn khi backend dùng Managed Identity.

SAS không phải identity của user. Nó là bearer capability: ai có token thì dùng được trong phạm vi token.

## 4. Practical implementation

Backend flow:

```text
1. User authenticated
2. API authorizes upload for Order/Document
3. API creates blob name controlled by server
4. API issues short-lived write-only SAS
5. Client uploads direct to Blob
6. API validates/finalizes metadata if workflow requires
```

Không để client tự chọn arbitrary container/path nếu path có authorization meaning.

Ví dụ policy nên tối thiểu:

```text
resource: one blob
permission: create/write
protocol: HTTPS only
expiry: 10 minutes
```

## 5. Real production scenario

CMS cho editors upload video. Ban đầu file đi qua ASP.NET Core API, gây request timeout và App Service memory/network pressure.

Chuyển sang direct-to-Blob bằng short-lived SAS giảm application data path. API vẫn quyết định editor có quyền upload và blob nằm ở namespace nào.

## 6. Failure scenario & troubleshooting

**Symptom** → SAS URL bị leak trong logs và vẫn dùng được 24 giờ.

**Evidence** → query string chứa signature xuất hiện trong request logging/analytics.

**Hypothesis** → token lifetime quá dài và logging policy không redact URL query.

**Diagnosis** → audit logs, expiry, permissions và token issuance flow.

**Fix** → expiry ngắn, permission nhỏ nhất, redact sensitive query parameters, ưu tiên User Delegation SAS khi phù hợp.

**Verification** → token hết hạn đúng, không xuất hiện trong logs, không thể access resource ngoài scope.

## 7. Common mistakes

* SAS expiry nhiều ngày vì “tiện”.
* Cấp container-wide write/delete khi chỉ cần một blob create.
* Gửi storage account key xuống client.
* Log full SAS URL.
* Cho client quyết định blob path dẫn tới object-level authorization bypass.

## 8. Alternatives

Backend proxy upload đơn giản hơn cho file nhỏ và security workflow cần inspect stream trực tiếp. Managed Identity phù hợp service-to-service, nhưng browser không dùng Managed Identity của backend. CDN/private origin pattern phù hợp download distribution khác use case upload.

## 9. Trade-offs

### Advantages

* Offload bandwidth khỏi application.
* Scale upload/download tốt hơn.
* Permission có thể giới hạn theo resource/time.

### Costs / Risks

* SAS là bearer secret.
* Revocation khó hơn token sống ngắn nếu không thay policy/key.
* Direct upload cần post-upload validation/quarantine nếu file untrusted.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SAS khác storage account key.

### Middle

Tạo scope/permission/expiry đúng và upload direct.

### Senior

Thiết kế authorization, filename ownership, malware scanning và secret logging policy.

### Technical Lead / Architect

Chọn Shared Key vs User Delegation, direct upload architecture và storage network/security controls theo threat model.

## 11. Key takeaway

* SAS phải ngắn hạn và least privilege.
* User Delegation SAS phù hợp hướng identity-first hơn việc phụ thuộc Shared Key.
* Direct-to-Blob giảm app load nhưng không bỏ qua authorization/file security.

# 7. Kubernetes resource requests/limits: CPU throttling, OOMKilled và vì sao cấu hình tài nguyên là một phần của application design

## 1. What is it?

`requests` mô tả tài nguyên pod cần để scheduler placement; `limits` đặt upper bound mà container có thể sử dụng theo resource type.

Mental model:

```text
request = scheduling reservation signal
limit   = runtime ceiling/constraint
```

CPU và memory có failure behavior khác nhau: CPU thường bị throttled; vượt memory limit có thể dẫn tới OOM kill.

## 2. Why does it exist?

Cluster nhiều workloads chia sẻ nodes. Không có requests/limits, một app runaway có thể ảnh hưởng neighbors. Nhưng cấu hình quá thấp cũng làm application tự tạo latency hoặc restart storm.

Resource settings vì vậy không chỉ là DevOps YAML; chúng ảnh hưởng trực tiếp .NET runtime behavior, GC, ThreadPool và SLO.

## 3. How does it work?

Ví dụ:

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "512Mi"
  limits:
    cpu: "1000m"
    memory: "1Gi"
```

Scheduler dùng requests để quyết định node placement. Runtime enforcement dựa trên cgroups.

Một .NET app CPU-bound chạm CPU limit có thể thấy request latency tăng mà process không crash. Memory limit vượt quá có thể làm container bị `OOMKilled`.

## 4. Practical implementation

Không copy resource values từ service khác. Bắt đầu bằng profiling/load test:

```text
traffic target
→ CPU p95/p99
→ managed memory
→ native memory
→ GC behavior
→ headroom
```

Theo dõi:

* container CPU usage
* CPU throttling time
* working set/RSS
* GC heap size
* restart reason
* node pressure

## 5. Real production scenario

API chạy tốt local với 8 cores. Production limit `250m` CPU vì team muốn tiết kiệm. Under load, request queue tăng, p99 tăng gấp 5 nhưng CPU graph “chỉ” quanh limit.

Root cause là throttling, không phải SQL.

Một service khác set memory limit 300 MiB, trong khi .NET process bình thường cần 350–450 MiB dưới burst, dẫn tới `OOMKilled` lặp lại.

## 6. Failure scenario & troubleshooting

**Symptom** → pod restart không có managed `OutOfMemoryException` trong application logs.

**Evidence** → Kubernetes status `OOMKilled`.

**Hypothesis** → kernel/cgroup kill process trước khi CLR có thể xử lý/log exception.

**Diagnosis** → xem pod events, memory metrics, GC heap/native allocations và limit.

**Fix** → tìm leak/large allocation nếu có; nếu baseline hợp lệ thì tăng memory limit/headroom dựa trên measurement.

**Verification** → sustained load + burst test, không OOM/restart, memory plateau hợp lý.

## 7. Common mistakes

* Requests = limits cho mọi app mà không hiểu trade-off.
* Memory limit sát average usage, không có burst headroom.
* Chỉ nhìn managed heap, bỏ qua native buffers/runtime overhead.
* CPU limit quá thấp rồi debug database trước.
* Autoscale theo CPU nhưng request/limit settings làm signal méo.

## 8. Alternatives

VM/App Service có resource model khác nhưng vẫn có CPU/memory ceiling. Vertical Pod Autoscaler có thể hỗ trợ recommendation trong một số môi trường; HPA giải quyết replica count chứ không chữa một pod bị limit sai.

## 9. Trade-offs

### Advantages

* Scheduling predictable hơn.
* Cô lập noisy neighbors.
* Capacity planning rõ hơn.

### Costs / Risks

* Limit sai gây throttling/OOM.
* Requests quá cao làm cluster utilization kém.
* Requests quá thấp tạo overcommit và node pressure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt CPU throttling với process crash và memory OOM.

### Middle

Đọc pod resource config/events/metrics.

### Senior

Liên hệ cgroups với CLR/GC, latency và autoscaling signals.

### Technical Lead / Architect

Đặt resource policy theo SLO, cost và workload class; yêu cầu load-test evidence thay vì copy-paste YAML.

## 11. Key takeaway

* Requests ảnh hưởng scheduling; limits ảnh hưởng runtime ceiling.
* CPU throttling thường biểu hiện như latency, memory limit có thể biểu hiện như `OOMKilled`.
* Resource config là một phần của performance/reliability design.

# 8. W3C Trace Context trong OpenTelemetry: propagation, traceparent và cách distributed trace bị đứt giữa services

## 1. What is it?

Distributed tracing cần một cách chuẩn để truyền trace identity qua service boundaries. W3C Trace Context định nghĩa headers như `traceparent` để downstream service biết request hiện tại thuộc trace nào.

Mental model:

```text
Client
  traceparent: trace A/span 1
      ↓
API
  creates span 2
      ↓ propagates trace A
Service B
  creates span 3
```

Nếu propagation bị mất, telemetry vẫn tồn tại nhưng trace bị chia thành nhiều cây độc lập.

## 2. Why does it exist?

Trong microservice/distributed architecture, request có thể đi qua API Gateway, ASP.NET Core API, Service Bus consumer, SQL và external API.

Không có correlation chuẩn, incident investigation trở thành grep theo timestamp và guesswork.

## 3. How does it work?

`traceparent` chứa version, trace ID, parent span ID và flags.

Ứng dụng instrumented bởi OpenTelemetry thường tự extract/inject context qua supported HTTP clients/server libraries.

Custom transports/messages cần propagation rõ ràng. Ví dụ khi publish message, trace context phải được inject vào message properties; consumer extract rồi tạo child span.

## 4. Practical implementation

Với built-in ASP.NET Core + `HttpClient` instrumentation, phần lớn HTTP propagation là tự động.

Custom background message có thể cần activity source:

```csharp
private static readonly ActivitySource Source = new("Orders.Worker");

using var activity = Source.StartActivity("process-order");
activity?.SetTag("messaging.system", "servicebus");
activity?.SetTag("order.id", orderId);
```

Không gắn PII/secrets vào tags/baggage chỉ vì tracing tiện tìm kiếm.

## 5. Real production scenario

Checkout request gọi Payment API rồi publish fulfillment message. HTTP trace nối đúng đến Payment, nhưng queue consumer xuất hiện thành trace mới.

Team tưởng “OpenTelemetry bị lỗi”. Thực tế producer không inject trace context vào message metadata hoặc consumer không extract.

## 6. Failure scenario & troubleshooting

**Symptom** → spans có đầy đủ trong telemetry nhưng service graph không nối end-to-end.

**Evidence** → trace IDs khác nhau trước và sau custom queue/HTTP middleware.

**Hypothesis** → propagation bị mất ở custom boundary.

**Diagnosis** → inspect outgoing headers/message properties và incoming extraction.

**Fix** → dùng propagator chuẩn, tránh tự phát minh correlation header nếu không cần.

**Verification** → một synthetic transaction phải hiển thị một trace xuyên các boundaries mong muốn.

## 7. Common mistakes

* Chỉ thêm `CorrelationId` log field rồi gọi đó là distributed tracing.
* Overwrite incoming trace context thay vì create child span.
* Đưa user token/PII vào baggage.
* Dùng custom HTTP client không qua instrumentation và không propagate headers.
* Sampling ở upstream khiến hiểu nhầm downstream “mất trace”.

## 8. Alternatives

Custom correlation IDs vẫn hữu ích cho business/request search nhưng không thay span hierarchy. Vendor-specific tracing có thể hoạt động, nhưng W3C/OpenTelemetry giảm coupling với một backend telemetry cụ thể.

## 9. Trade-offs

### Advantages

* End-to-end causal visibility.
* Chuẩn interoperable giữa libraries/vendors.
* Hỗ trợ latency decomposition tốt hơn logs đơn lẻ.

### Costs / Risks

* Instrumentation/propagation gaps dễ xảy ra ở custom transports.
* High-cardinality tags tăng telemetry cost.
* Sampling cần policy phù hợp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace gồm nhiều spans của cùng request flow.

### Middle

Biết HTTP propagation thường tự động và custom boundaries cần kiểm tra.

### Senior

Debug broken propagation, sampling, baggage và telemetry cardinality.

### Technical Lead / Architect

Chuẩn hóa observability contract xuyên HTTP/messaging và chọn sampling/data-governance policy toàn platform.

## 11. Key takeaway

* Trace continuity phụ thuộc context propagation qua mọi boundary.
* `traceparent` là standard correlation mechanism, không chỉ một custom request ID.
* Custom transports là nơi trace thường bị đứt nhất.

# 9. Integration testing với real infrastructure: Testcontainers, isolation và khi mock database làm test trở nên vô nghĩa

## 1. What is it?

Integration test kiểm tra application với các boundaries thực như database, Redis hoặc message broker ở mức đủ gần production để bắt lỗi mapping, transaction, SQL translation, migration và protocol behavior.

Mental model:

```text
unit test: business logic isolated
integration test: application + real boundary
E2E: nhiều thành phần/end-user flow
```

Testcontainers là một cách spin up disposable infrastructure bằng containers cho test run.

## 2. Why does it exist?

Mock `DbSet`, mock repository hoặc in-memory fake có thể làm test pass trong khi production fail vì:

* LINQ không translate sang SQL
* unique constraint không được enforce
* transaction/isolation behavior khác
* migration thiếu column/index
* provider-specific SQL khác

Test double chỉ hữu ích khi nó bảo vệ đúng abstraction; mock database semantics thường rất dễ tạo false confidence.

## 3. How does it work?

Test suite khởi động real PostgreSQL/SQL Server/Redis container, apply migrations, chạy application test và dispose sau suite.

Isolation strategies:

* database per test class
* transaction rollback per test
* schema reset tool
* unique tenant/test IDs

Mục tiêu là deterministic và parallel-safe.

## 4. Practical implementation

Ví dụ conceptual fixture:

```csharp
public sealed class DatabaseFixture : IAsyncLifetime
{
    private readonly PostgreSqlContainer _postgres =
        new PostgreSqlBuilder()
            .WithImage("postgres:17")
            .Build();

    public string ConnectionString => _postgres.GetConnectionString();

    public async Task InitializeAsync()
        => await _postgres.StartAsync();

    public async Task DisposeAsync()
        => await _postgres.DisposeAsync();
}
```

Sau đó application test dùng connection string thực và chạy migrations.

Image version nên pin phù hợp production; `latest` làm CI không deterministic.

## 5. Real production scenario

EF Core query dùng method C# custom trong `Where`. Unit test với in-memory collection pass vì LINQ-to-Objects chạy được. Production SQL provider không translate expression và request fail.

Integration test với real provider phát hiện lỗi ngay trong CI.

## 6. Failure scenario & troubleshooting

**Symptom** → integration tests flaky khi chạy parallel.

**Evidence** → tests dùng cùng database rows/static IDs và cleanup lẫn nhau.

**Hypothesis** → test isolation không đúng.

**Diagnosis** → chạy single-thread thì pass; parallel thì fail với missing/duplicate rows.

**Fix** → unique test data, isolated schema/database hoặc reset strategy deterministic.

**Verification** → chạy suite lặp nhiều lần với parallelism giống CI.

## 7. Common mistakes

* Dùng SQLite thay SQL Server/PostgreSQL rồi giả định provider semantics giống nhau.
* Container image `latest`.
* Một shared mutable database cho toàn suite mà không reset.
* Integration tests quá nhiều business permutations đáng ra là unit tests.
* Mock external API protocol đến mức không test serialization/HTTP contract.

## 8. Alternatives

LocalDB/dev shared DB đơn giản nhưng dễ state leakage. In-memory fake phù hợp tests không phụ thuộc provider semantics. Contract tests phù hợp external service compatibility. Full E2E environment chỉ nên dùng cho critical workflows vì cost cao hơn.

## 9. Trade-offs

### Advantages

* Bắt provider/infrastructure bugs thực tế.
* Test migrations/constraints/serialization đúng hơn.
* Giảm false confidence từ mocks.

### Costs / Risks

* CI chậm hơn unit tests.
* Cần Docker/container runtime.
* Isolation/setup complexity tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết unit test và integration test bảo vệ các risk khác nhau.

### Middle

Viết test với real DB, deterministic fixtures và cleanup.

### Senior

Thiết kế test pyramid theo failure risk, parallelism và provider fidelity.

### Technical Lead / Architect

Quyết định infrastructure nào phải real trong CI và nơi nào mocks/contracts đủ giá trị; giữ suite nhanh nhưng không đánh đổi correctness.

## 11. Key takeaway

* Mock database thường không mô phỏng được SQL/provider semantics.
* Real infrastructure tests nên tập trung vào boundary risks, không thay toàn bộ unit tests.
* Isolation và version pinning quyết định độ tin cậy của integration suite.

# 10. AI Structured Outputs + Tool Calling boundary: để LLM xử lý interpretation nhưng giữ business invariants trong deterministic code

Structured Outputs cho phép application yêu cầu model trả dữ liệu theo schema xác định. Tool Calling cho phép model chọn gọi function/tool với arguments có cấu trúc.

Mental model đúng:

```text
LLM:
understand intent
choose proposed action
produce structured arguments

Application:
authenticate
authorize
validate business rules
execute deterministic side effect
```

LLM không nên tự trở thành authorization engine hoặc financial transaction authority.

## 2. Why does it exist?

Free-form text khó integrate an toàn:

```text
"Please transfer 5 million VND to account X"
```

Application phải parse ngôn ngữ tự do và có thể hiểu sai. Structured output giảm ambiguity ở interface.

Nhưng schema-valid không đồng nghĩa business-valid hoặc authorized.

## 3. How does it work?

```json
{
  "name": "create_refund_request",
  "arguments": {
    "orderId": "ORD-123",
    "amount": 250000
  }
}
```

Application vẫn phải kiểm tra:

```text
user có quyền với order?
order có refundable?
amount <= refundable balance?
currency đúng?
idempotency key hợp lệ?
```

Model chỉ đề xuất structured intent.

## 4. Practical implementation

Một deterministic handler:

```csharp
public async Task<RefundResult> CreateRefundAsync(
    ClaimsPrincipal user,
    RefundArgs args,
    CancellationToken ct)
{
    var order = await _orders.GetAsync(args.OrderId, ct)
        ?? throw new NotFoundException();

    _authorization.EnsureCanRefund(user, order);

    if (args.Amount <= 0 || args.Amount > order.RefundableAmount)
        throw new ValidationException("Invalid refund amount.");

    return await _payments.CreateRefundAsync(
        order,
        args.Amount,
        ct);
}
```

Không truyền raw model output thẳng vào payment API.

Agent UI hiển thị proposal, deterministic backend kiểm tra order ownership, payment state, refund ceiling và permission. Nếu policy cần human approval, tool chỉ tạo draft request thay vì execute refund ngay.

## 6. Failure scenario & troubleshooting

**Symptom** → model gọi tool với order ID tồn tại nhưng thuộc tenant khác.

**Evidence** → schema hợp lệ, tool call technically correct, nhưng object-level authorization sai.

**Hypothesis** → backend tin model-provided resource identifier.

**Diagnosis** → review tool boundary và authorization checks.

**Fix** → mọi tool action resolve resource dưới authenticated tenant/user scope; model input không bao giờ bypass authorization.

**Verification** → adversarial tests với prompt injection, cross-tenant IDs và manipulated arguments phải bị deterministic layer reject.

## 7. Common mistakes

* Schema-valid = safe.
* Cho model quyết định role/permission.
* Tool có quyền quá rộng.
* Gửi secrets/full database context vào model không cần thiết.
* Không log tool decision/validation outcome theo cách audit-safe.
* Retry side-effect tool mà không có idempotency.

Rule-based NLP hoặc forms phù hợp workflows rõ và ít ambiguity. Human-in-the-loop tốt cho high-impact actions. RAG giúp model grounding context nhưng không thay authorization hoặc transactional correctness.

### Advantages

* Natural-language UX tốt hơn.
* Structured boundary dễ validate/test hơn free-form parsing.
* Tool layer giữ deterministic control.

### Costs / Risks

* Model vẫn probabilistic.
* Prompt injection/context leakage vẫn tồn tại.
* Tool governance và observability tăng complexity.
* High-impact actions cần additional approval/idempotency safeguards.
