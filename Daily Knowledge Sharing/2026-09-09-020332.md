# 1. C# `ValueTask`: tối ưu allocation hay đang biến async API thành contract khó dùng?

## 1. What is it?

`ValueTask<T>` là một awaitable value type có thể đại diện cho kết quả đã có sẵn hoặc một asynchronous operation chưa hoàn thành. Mental model quan trọng nhất:

```text
Task<T>
→ luôn trả về một object đại diện cho operation

ValueTask<T>
→ có thể chứa trực tiếp T
→ hoặc wrap một Task<T>
→ hoặc dùng IValueTaskSource<T>
```

Nó tồn tại chủ yếu để giảm allocation trong hot path nơi operation thường hoàn thành synchronously, ví dụ đọc từ cache/buffer đã có dữ liệu.

## 2. Why does it exist?

Nếu một method được gọi hàng triệu lần và 95% lần có kết quả ngay, tạo `Task<T>` mới cho mọi call có thể tạo allocation pressure không cần thiết.

Ví dụ một parser, pipeline, socket abstraction hoặc high-throughput cache layer có thể trả kết quả ngay phần lớn thời gian. Ở đây `ValueTask<T>` có thể giảm allocation.

Nhưng với business application thông thường, network/database I/O thường lớn hơn nhiều so với cost tạo Task. Nếu dùng `ValueTask` không đo đạc, complexity thường lớn hơn lợi ích.

## 3. How does it work?

Một `ValueTask<T>` có thể ở các trạng thái khác nhau:

```text
synchronous result
    ↓
ValueTask<T> stores T directly

asynchronous result
    ↓
ValueTask<T> wraps Task<T> / IValueTaskSource<T>
```

Khác với `Task`, một `ValueTask` không nên được await nhiều lần hoặc lưu trữ tùy tiện nếu nó dựa trên `IValueTaskSource<T>`.

Đây là điểm dễ sai nhất: developer nhìn thấy nó giống Task và đối xử như Task.

## 4. Practical implementation

Use case hợp lý:

```csharp
public sealed class ProductNameCache
{
    private readonly Dictionary<Guid, string> _cache = new();
    private readonly ProductRepository _repository;

    public ProductNameCache(ProductRepository repository)
    {
        _repository = repository;
    }

    public ValueTask<string?> GetNameAsync(
        Guid productId,
        CancellationToken cancellationToken)
    {
        if (_cache.TryGetValue(productId, out var value))
        {
            return ValueTask.FromResult<string?>(value);
        }

        return new ValueTask<string?>(
            LoadAsync(productId, cancellationToken));
    }

    private async Task<string?> LoadAsync(
        Guid productId,
        CancellationToken cancellationToken)
    {
        var name = await _repository.GetNameAsync(
            productId,
            cancellationToken);

        if (name is not null)
            _cache[productId] = name;

        return name;
    }
}
```

Nếu không có synchronous fast path rõ ràng, `Task<T>` thường đơn giản hơn.

## 5. Real production scenario

Một high-throughput protocol gateway đọc metadata từ local in-memory table. 98% requests hit local state, 2% phải query external source.

Profiling cho thấy hàng triệu `Task<T>` allocations nhỏ nhưng liên tục. Chuyển đúng hot path sang `ValueTask<T>` giảm allocation rate.

Ngược lại, một CRUD API gọi SQL Server 40 ms mỗi request sẽ gần như không được lợi đáng kể từ việc đổi toàn bộ service methods sang `ValueTask<T>`.

## 6. Failure scenario & troubleshooting

**Symptom** → async code thỉnh thoảng throw hoặc behavior không nhất quán sau refactor sang `ValueTask`.

**Evidence** → cùng một `ValueTask` bị await hai lần hoặc được cache để reuse.

**Hypothesis** → caller đang vi phạm single-consumption semantics của underlying source.

**Diagnosis** → tìm nơi lưu `ValueTask`, gọi `.AsTask()` nhiều lần hoặc await lại cùng instance.

**Fix** → await trực tiếp một lần; nếu cần nhiều consumers hoặc reuse, chuyển thành `Task`.

**Verification** → concurrency tests + allocation benchmark trên hot path thực tế.

## 7. Common mistakes

* Thay tất cả `Task<T>` thành `ValueTask<T>` vì nghĩ value type luôn nhanh hơn.
* Await cùng một `ValueTask` nhiều lần.
* Lưu `ValueTask` vào field/cache.
* Dùng `ValueTask` trong API public mà không có measured reason.
* Benchmark micro-level nhưng bỏ qua DB/network latency.

## 8. Alternatives

`Task<T>` vẫn là default tốt nhất cho phần lớn application code. Nếu optimization tập trung vào buffer/memory, có thể cần `Span<T>`, pooling hoặc giảm round trips trước khi nghĩ tới `ValueTask`.

## 9. Trade-offs

### Advantages

* Có thể giảm allocation ở synchronous-completion hot path.
* Hữu ích cho low-level/high-throughput libraries.

### Costs / Risks

* Contract phức tạp hơn Task.
* Dễ misuse khi await nhiều lần.
* Có thể làm code khó maintain vì optimization nhỏ.
* Performance benefit phụ thuộc workload thực.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `ValueTask` không phải “Task nhanh hơn”.

### Middle

Biết dùng khi có synchronous fast path rõ và await đúng một lần.

### Senior

Biết đo allocation, phân biệt bottleneck runtime với bottleneck I/O và đánh giá API ergonomics.

### Technical Lead / Architect

Chỉ chuẩn hóa `ValueTask` ở library/hot-path có bằng chứng; không lan optimization này qua business layers vô cớ.

## 11. Key takeaway

* `Task<T>` vẫn là default cho application code.
* `ValueTask<T>` chỉ đáng dùng khi synchronous completion thường xuyên và allocation đã được đo là vấn đề.
* Complexity của async contract cũng là một loại cost.

# 2. ASP.NET Core Rate Limiting: giới hạn lưu lượng theo identity, endpoint và capacity thay vì chặn request một cách tùy tiện

## 1. What is it?

Rate limiting kiểm soát số lượng request được phép đi qua trong một khoảng thời gian hoặc theo available concurrency.

Mental model:

```text
Client
  ↓
reverse proxy / API gateway
  ↓
ASP.NET Core rate limiter
  ↓
endpoint
  ↓
database / external dependency
```

Mục tiêu không chỉ là chống abuse. Rate limiting còn bảo vệ finite downstream capacity.

## 2. Why does it exist?

Một API có thể chịu 5.000 RPS ở web tier nhưng database chỉ xử lý ổn định 800 heavy queries/second. Nếu không có admission control, burst traffic có thể làm queue dài, timeout tăng, retries xuất hiện rồi tạo overload cascade.

Rate limiting giúp hệ thống từ chối sớm một phần request thay vì nhận tất cả rồi timeout muộn.

## 3. How does it work?

Các strategy phổ biến:

* Fixed Window
* Sliding Window
* Token Bucket
* Concurrency limiter

Token Bucket phù hợp khi muốn cho phép burst nhỏ nhưng vẫn giới hạn average rate.

Partitioned limiting cho phép policy khác nhau theo:

* user ID;
* API key;
* tenant;
* client application;
* endpoint category.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode =
        StatusCodes.Status429TooManyRequests;

    options.AddPolicy("per-user", httpContext =>
    {
        var userId = httpContext.User.FindFirst("sub")?.Value
            ?? httpContext.Connection.RemoteIpAddress?.ToString()
            ?? "anonymous";

        return RateLimitPartition.GetTokenBucketLimiter(
            userId,
            _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 50,
                ReplenishmentPeriod = TimeSpan.FromSeconds(10),
                AutoReplenishment = true,
                QueueLimit = 0
            });
    });
});

app.UseRateLimiter();

app.MapGet("/api/orders", GetOrders)
   .RequireRateLimiting("per-user");
```

## 5. Real production scenario

Một partner integration bị bug và retry request mỗi 100 ms khi nhận timeout. Trong vài phút, một tenant tạo hàng chục nghìn requests, làm SQL pool cạn và ảnh hưởng mọi tenant khác.

Per-tenant rate limiting cô lập blast radius và trả 429 sớm cho client lỗi.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều 429 xuất hiện sau deploy dù backend CPU còn thấp.

**Evidence** → rate limiter metrics cho thấy một partition hit limit liên tục.

**Hypothesis** → threshold quá thấp hoặc partition key sai khiến nhiều users dùng chung một bucket.

**Diagnosis** → inspect partition key, request distribution, endpoint latency và capacity baseline.

**Fix** → chỉnh policy dựa trên actual capacity; phân tách lightweight/heavy endpoints.

**Verification** → load test burst traffic và kiểm tra p95/p99 của accepted requests.

## 7. Common mistakes

* Rate limit chỉ theo IP trong hệ thống NAT/proxy lớn.
* Dùng cùng limit cho mọi endpoint.
* Queue quá nhiều requests trong limiter, biến rate limiter thành latency amplifier.
* Retry 429 ngay lập tức từ client.
* Không trả `Retry-After` hoặc guidance phù hợp.
* Nghĩ rate limiting thay thế authorization hoặc DDoS protection ở edge.

## 8. Alternatives

Rate limiting có thể đặt ở Azure Front Door, API Management, reverse proxy hoặc application. Concurrency limiting hữu ích hơn fixed RPS với endpoint có latency biến động mạnh.

## 9. Trade-offs

### Advantages

* Bảo vệ downstream capacity.
* Cô lập noisy neighbor.
* Fail fast thay vì timeout muộn.

### Costs / Risks

* Threshold sai làm reject legitimate traffic.
* Distributed rate limit cần shared state hoặc edge/gateway support.
* Per-user/tenant cardinality có cost quản lý state.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 429 là admission control chứ không phải server crash.

### Middle

Implement partitioned policies và client retry behavior hợp lý.

### Senior

Thiết kế limit theo capacity, endpoint cost và tenant fairness.

### Technical Lead / Architect

Quyết định enforcement boundary: edge, gateway, app hay kết hợp; xác định policy theo business SLA và failure isolation.

## 11. Key takeaway

* Rate limit nên phản ánh capacity và fairness, không chỉ một con số RPS tùy ý.
* Partition key sai có thể làm policy vô nghĩa.
* Reject sớm thường tốt hơn nhận tất cả rồi timeout đồng loạt.

# 3. PostgreSQL MVCC và VACUUM: vì sao đọc không block ghi nhưng dead tuples vẫn có thể làm database chậm dần

## 1. What is it?

PostgreSQL sử dụng MVCC — Multi-Version Concurrency Control — để nhiều transaction có thể nhìn thấy các version dữ liệu khác nhau mà không cần lock read/write theo cách đơn giản.

Mental model:

```text
UPDATE row
  ↓
old tuple remains temporarily
new tuple is created
  ↓
transactions see version allowed by snapshot
  ↓
VACUUM later reclaims dead tuples
```

## 2. Why does it exist?

Nếu đọc luôn block ghi và ghi luôn block đọc, concurrency sẽ giảm mạnh trong OLTP workload.

MVCC cho phép reader thường không block writer và writer không cần chờ reader chỉ để thay đổi một row version.

Trade-off là database phải giữ old versions đủ lâu cho transaction đang dùng snapshot cũ.

## 3. How does it work?

Mỗi tuple có metadata transaction visibility. Khi UPDATE, PostgreSQL không overwrite row tại chỗ theo nghĩa đơn giản; nó tạo tuple version mới.

Tuple cũ trở thành dead khi không transaction nào cần nữa.

`VACUUM` thu hồi storage có thể reuse và cập nhật visibility metadata. `autovacuum` tự chạy dựa trên thresholds.

Long-running transaction có thể giữ old snapshot quá lâu và ngăn cleanup hiệu quả.

## 4. Practical implementation

Kiểm tra bảng có dead tuples cao:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Tìm transaction chạy lâu:

```sql
SELECT
    pid,
    usename,
    xact_start,
    state,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

## 5. Real production scenario

Một reporting process mở transaction rồi giữ connection hơn 2 giờ. Trong lúc đó Orders table nhận hàng triệu updates.

Autovacuum vẫn chạy nhưng không thể reclaim nhiều tuple versions vì old snapshot còn active. Table/index bloat tăng, query I/O tăng dần dù application code không đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → database storage tăng nhanh, query latency tăng dù row count gần như không đổi.

**Evidence** → `n_dead_tup` cao, long-running transactions tồn tại, autovacuum bị chậm.

**Hypothesis** → MVCC cleanup bị giữ bởi old snapshots hoặc autovacuum config chưa đủ.

**Diagnosis** → inspect transaction age, dead tuples, vacuum activity, table/index bloat.

**Fix** → xử lý transaction dài, tune autovacuum cho hot tables, tránh idle-in-transaction.

**Verification** → theo dõi dead tuples, storage growth và logical/physical I/O sau remediation.

## 7. Common mistakes

* Nghĩ MVCC nghĩa là PostgreSQL không có locking.
* Giữ transaction mở trong lúc gọi external API.
* Ignore `idle in transaction` connections.
* Tắt autovacuum để “giảm load”.
* Chỉ nhìn row count mà không nhìn bloat/dead tuples.

## 8. Alternatives

SQL Server cũng có version-based isolation mechanisms nhưng implementation/storage semantics khác. Pessimistic locking vẫn phù hợp trong một số critical sections.

## 9. Trade-offs

### Advantages

* High read/write concurrency.
* Snapshot semantics rõ.
* Readers thường không block writers.

### Costs / Risks

* Dead tuples cần vacuum.
* Long transactions gây retention/bloat.
* Storage/I/O có thể tăng nếu maintenance không theo workload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu update có thể tạo row version mới thay vì overwrite đơn giản.

### Middle

Biết xem transaction age, dead tuples và autovacuum state.

### Senior

Liên hệ MVCC với bloat, transaction design và performance incidents.

### Technical Lead / Architect

Đặt transaction-duration policy, maintenance baseline và observability cho write-heavy PostgreSQL systems.

## 11. Key takeaway

* MVCC đổi blocking cost lấy version-management cost.
* Long-running transaction có thể làm cleanup trì trệ.
* Autovacuum là correctness/performance infrastructure, không phải optional housekeeping.

# 4. Redis cache stampede: khi hàng nghìn cache miss cùng lúc biến database thành điểm sụp đổ

## 1. What is it?

Cache stampede xảy ra khi nhiều requests đồng thời miss cùng một hot key rồi tất cả cùng query origin/database.

```text
Hot key expires
     ↓
1000 concurrent requests
     ↓
1000 cache misses
     ↓
1000 DB queries
```

Cache vốn dùng để giảm load lại vô tình tạo load spike tập trung.

## 2. Why does it exist?

TTL tạo một thời điểm mà dữ liệu biến mất khỏi cache. Nếu key rất hot và regeneration đắt, nhiều callers sẽ cùng tái tạo dữ liệu trước khi request đầu tiên kịp ghi cache lại.

## 3. How does it work?

Các mitigation phổ biến:

* single-flight / request coalescing;
* distributed lock ngắn hạn;
* stale-while-revalidate;
* early/probabilistic refresh;
* jitter TTL;
* background refresh.

Không có một technique phù hợp mọi data type.

## 4. Practical implementation

Single-instance coalescing với `SemaphoreSlim`:

```csharp
private readonly ConcurrentDictionary<string, SemaphoreSlim> _locks = new();

public async Task<ProductDto?> GetProductAsync(
    string key,
    CancellationToken cancellationToken)
{
    var cached = await _cache.GetStringAsync(key, cancellationToken);
    if (cached is not null)
        return JsonSerializer.Deserialize<ProductDto>(cached);

    var gate = _locks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
    await gate.WaitAsync(cancellationToken);

    try
    {
        cached = await _cache.GetStringAsync(key, cancellationToken);
        if (cached is not null)
            return JsonSerializer.Deserialize<ProductDto>(cached);

        var product = await _repository.GetAsync(cancellationToken);
        if (product is not null)
        {
            await _cache.SetStringAsync(
                key,
                JsonSerializer.Serialize(product),
                new DistributedCacheEntryOptions
                {
                    AbsoluteExpirationRelativeToNow =
                        TimeSpan.FromMinutes(5)
                },
                cancellationToken);
        }

        return product;
    }
    finally
    {
        gate.Release();
    }
}
```

Trong multi-instance app, local semaphore chỉ bảo vệ từng process, không bảo vệ toàn cluster.

## 5. Real production scenario

Product detail page có một key chứa pricing rules được đọc 10.000 lần/phút. TTL 10 phút, regeneration query join nhiều bảng mất 800 ms.

Đúng phút thứ 10, hàng trăm requests cùng miss và SQL CPU spike. p99 tăng, client retries, incident lan rộng.

## 6. Failure scenario & troubleshooting

**Symptom** → DB load spike có chu kỳ đúng bằng TTL.

**Evidence** → Redis miss rate tăng đột ngột trên một số hot keys.

**Hypothesis** → synchronized expiration + expensive regeneration.

**Diagnosis** → correlate cache key expiry, DB query count và endpoint latency.

**Fix** → jitter TTL, stale-while-revalidate hoặc request coalescing.

**Verification** → load test expiry event thay vì chỉ steady-state cache-hit test.

## 7. Common mistakes

* Dùng cùng TTL chính xác cho hàng nghìn keys.
* Distributed lock quá dài làm request queue lớn.
* Không double-check cache sau khi lấy lock.
* Cache null vô thời hạn.
* Khi Redis lỗi thì mọi request lập tức fallback DB không giới hạn.

## 8. Alternatives

Nếu dữ liệu đủ ổn định, background precompute/read model có thể tốt hơn runtime caching. CDN hoặc browser cache phù hợp static/public data. `IMemoryCache` đơn giản hơn khi consistency cross-instance không cần thiết.

## 9. Trade-offs

### Advantages

* Coalescing giảm origin amplification.
* Stale-while-revalidate giữ latency ổn định.

### Costs / Risks

* Locks thêm complexity.
* Stale data có thể được phục vụ.
* Distributed coordination có operational cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss đồng thời có thể nguy hiểm hơn một cache miss đơn lẻ.

### Middle

Implement double-check + coalescing/jitter đúng cách.

### Senior

Phân tích hot-key behavior, stale tolerance và fallback overload.

### Technical Lead / Architect

Quyết định data nào nên cache runtime, data nào nên precompute/read-model; đặt failure policy khi Redis unavailable.

## 11. Key takeaway

* Cache cần được test cả lúc hit lẫn lúc expire.
* Hot-key regeneration phải có concurrency control hoặc stale strategy.
* Cache outage/miss không được biến database thành fallback không giới hạn.

# 5. Modular Monolith: boundary, data ownership và dependency direction trước khi nghĩ tới Microservices

## 1. What is it?

Modular Monolith là một application deployable nhưng được chia thành các modules có boundary nghiệp vụ rõ.

```text
One deployable application
├── Orders
├── Catalog
├── Payments
└── Identity
```

Điểm cốt lõi không phải folder structure. Module phải kiểm soát dependency, data ownership và public contracts.

## 2. Why does it exist?

Layered monolith lớn thường có vấn đề:

* mọi service gọi mọi repository;
* shared database schema không ownership;
* business rules nằm rải rác;
* thay đổi một feature kéo theo nhiều feature khác.

Microservices giải quyết một số boundary/deployment problems nhưng thêm network, observability, deployment, consistency và operational complexity.

Modular Monolith cho phép thiết lập boundaries trước mà chưa trả cost của distribution.

## 3. How does it work?

Một module nên sở hữu:

* application use cases;
* domain model;
* persistence mapping;
* public contracts;
* module-specific schema/tables nếu có thể.

Ví dụ dependency:

```text
Orders Module
   │
   ├─ owns Orders tables
   ├─ exposes Orders API/contracts
   │
   └─ does NOT let Catalog write Orders tables directly
```

Cross-module communication có thể là synchronous internal API hoặc in-process events nhưng vẫn phải qua explicit contract.

## 4. Practical implementation

Folder chỉ là biểu hiện, boundary mới quan trọng:

```text
src/
  Modules/
    Orders/
      Orders.Api/
      Orders.Application/
      Orders.Domain/
      Orders.Infrastructure/
    Catalog/
      Catalog.Api/
      Catalog.Application/
      Catalog.Domain/
      Catalog.Infrastructure/
```

Một module khác không được inject `OrdersDbContext` trực tiếp. Nó gọi public application contract:

```csharp
public interface IOrderQuery
{
    Task<OrderSummary?> GetAsync(
        Guid orderId,
        CancellationToken cancellationToken);
}
```

## 5. Real production scenario

Một enterprise platform có 8 business areas nhưng traffic vừa phải. Team 12 developers không có platform team chuyên vận hành distributed systems.

Nếu tách 20 microservices sớm, CI/CD, telemetry, secrets, networking và data consistency trở thành phần lớn workload.

Modular Monolith giúp cô lập business changes trong một deployable unit, sau này module có pressure độc lập mới được extract.

## 6. Failure scenario & troubleshooting

**Symptom** → project gọi là modular nhưng thay đổi Catalog vẫn cần sửa trực tiếp Orders repositories.

**Fix** → tách contracts, enforce internal visibility, schema ownership và architecture tests.

**Verification** → thử thay implementation của một module mà consumers chỉ cần public contract.

## 7. Common mistakes

* Mỗi module dùng chung mọi entity/domain model.
* Shared `Common` project trở thành nơi chứa business logic của tất cả modules.
* Cross-module FK/write tùy tiện không có ownership.

* Nghĩ modular monolith là “microservices nhưng deploy chung”.

## 8. Alternatives

Simple layered architecture phù hợp app nhỏ ít business complexity. Microservices phù hợp khi cần independent scaling/deployment/ownership và organization đủ sức vận hành distributed system.

## 9. Trade-offs

### Costs / Risks

* Deploy vẫn là một unit.
* Shared process có thể chia sẻ blast radius.

## 10. Junior → Middle → Senior → Technical Lead

Quyết định khi nào monolith đủ tốt và khi nào một module thực sự cần extraction dựa trên scale, team ownership và release pressure.

## 11. Key takeaway

# 6. Outbox Pattern với EF Core + Azure Service Bus: commit business state và event mà không cần distributed transaction

## 1. What is it?

Outbox Pattern lưu business change và message cần publish trong cùng local database transaction.

```text
HTTP request
   ↓
EF Core transaction
   ├─ update Order
   └─ insert OutboxMessage
        ↓ commit
Background publisher
        ↓
Azure Service Bus
```

## 2. Why does it exist?

Classic dual-write problem:

```text
1. UPDATE database succeeds
2. Publish message fails
```

hoặc:

```text
1. Publish message succeeds
2. DB transaction rolls back
```

Không có atomicity giữa database và broker khi dùng hai systems độc lập.

## 3. How does it work?

Business transaction chỉ commit vào một transactional resource: database.

Outbox worker sau đó đọc unpublished rows và gửi tới Service Bus. Sau publish, row được mark sent hoặc retained theo audit policy.

Delivery thường là at-least-once, nên consumer vẫn phải idempotent.

## 4. Practical implementation

Entity:

```csharp
public sealed class OutboxMessage
{
    public Guid Id { get; init; }
    public DateTimeOffset OccurredAt { get; init; }
    public string Type { get; init; } = null!;
    public string Payload { get; init; } = null!;
    public DateTimeOffset? PublishedAt { get; set; }
}
```

Trong cùng `SaveChanges` transaction:

```csharp
order.MarkPaid();

db.OutboxMessages.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    OccurredAt = DateTimeOffset.UtcNow,
    Type = "OrderPaid",
    Payload = JsonSerializer.Serialize(
        new { order.Id, order.Total })
});

await db.SaveChangesAsync(cancellationToken);
```

Publisher:

```csharp
var batch = await db.OutboxMessages
    .Where(x => x.PublishedAt == null)
    .OrderBy(x => x.OccurredAt)
    .Take(100)
    .ToListAsync(cancellationToken);
```

## 5. Real production scenario

Order payment được commit nhưng Service Bus transiently unavailable. Nếu code publish trực tiếp sau `SaveChanges`, event có thể mất và Fulfillment không bao giờ chạy.

Outbox giữ event trong DB. Worker retry sau khi Service Bus phục hồi.

## 6. Failure scenario & troubleshooting

**Symptom** → outbox backlog tăng liên tục.

**Evidence** → unpublished row count tăng, Service Bus send latency/errors cao.

**Hypothesis** → publisher stalled, broker degraded hoặc poison payload.

**Diagnosis** → inspect backlog age, retry count, serialization failures, Service Bus metrics.

**Fix** → bounded retries, poison-message handling, alert theo oldest-unpublished-age.

**Verification** → simulate broker outage rồi xác nhận backlog drain sau recovery mà consumers không double-apply side effects.

## 7. Common mistakes

* Insert outbox record sau transaction riêng.
* Delete outbox row ngay khi send call return mà không nghĩ tới ambiguous outcome.
* Assume exactly-once delivery.
* Không idempotency ở consumer.
* Poll database quá aggressive.
* Không cleanup/archive outbox table.

## 8. Alternatives

CDC/transaction log streaming có thể publish changes mà không polling app table. Distributed transaction hiếm khi thực tế trong cloud-native architecture. Nếu workflow không cần event, synchronous call đơn giản có thể phù hợp hơn.

## 9. Trade-offs

### Advantages

* Loại bỏ lost-message dual-write window.
* Dùng local DB transaction quen thuộc.
* Broker outage không làm mất business event.

### Costs / Risks

* Eventual delivery thay vì immediate guarantee.
* Outbox worker/backlog cần monitoring.
* Duplicate publish vẫn có thể xảy ra.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DB update + broker publish là hai writes không atomic.

### Middle

Implement outbox table, publisher và idempotent consumer.

### Senior

Thiết kế retry, ordering, backlog monitoring và ambiguous send handling.

### Technical Lead / Architect

Quyết định transactional event boundary, retention và khi nào CDC tốt hơn application outbox.

## 11. Key takeaway

* Outbox giải quyết atomicity của business state + intent-to-publish.
* Nó không tạo exactly-once delivery.
* Consumer idempotency và backlog observability vẫn bắt buộc.

# 7. Azure Key Vault + Managed Identity: secret rotation đúng cách mà application không phụ thuộc secret tĩnh trong config

## 1. What is it?

Managed Identity cho Azure resource một identity trong Microsoft Entra ID mà không cần application giữ client secret. Azure Key Vault lưu secrets/keys/certificates và authorize access bằng identity.

```text
App Service / Function / Container App
           ↓ Managed Identity
      Microsoft Entra ID
           ↓ token
       Key Vault
```

## 2. Why does it exist?

Nếu application giữ database password hoặc API key trong `appsettings.json`, pipeline variable hoặc environment variable lâu dài, secret phải được phân phối, rotate và audit ở nhiều nơi.

Managed Identity loại bỏ một lớp credential bootstrap cho Azure-to-Azure access.

## 3. How does it work?

Application sử dụng Azure Identity credential chain. Trong Azure, SDK nhận token cho Managed Identity; local development có thể dùng developer credential.

RBAC hoặc access policy xác định identity nào được đọc secret nào.

## 4. Practical implementation

```csharp
var credential = new DefaultAzureCredential();

var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);

KeyVaultSecret secret = await client.GetSecretAsync(
    "PartnerApiKey",
    cancellationToken: cancellationToken);
```

Nếu secret thay đổi runtime, application phải có refresh/cache strategy; đọc Key Vault cho mỗi request thường không phù hợp.

## 5. Real production scenario

Một partner API key cần rotate mỗi 90 ngày. Version cũ lưu key trong deployment variables nên mỗi rotation yêu cầu sửa pipeline + redeploy nhiều services.

Sau khi đưa secret vào Key Vault, services dùng Managed Identity. Rotation workflow cập nhật secret centrally, còn application refresh theo controlled interval.

## 6. Failure scenario & troubleshooting

**Symptom** → application start được local nhưng 403 khi chạy Azure.

**Evidence** → Key Vault audit log cho thấy identity không có `secrets/get` permission.

**Hypothesis** → RBAC/identity binding sai, không phải secret value sai.

**Diagnosis** → xác nhận identity object, role assignment, vault networking/private endpoint và credential chain.

**Fix** → cấp least-privilege role đúng scope; sửa network path nếu vault private-only.

**Verification** → deploy với same identity và test secret retrieval + rotation.

## 7. Common mistakes

* Managed Identity có nhưng vẫn lưu client secret trong config.
* Cấp `Key Vault Administrator` cho application chỉ để đọc một secret.
* Fetch secret từ Key Vault trên mọi HTTP request.
* Cache secret vô hạn nên rotation không có tác dụng.
* Log secret khi debug authentication.
* Quên private DNS khi dùng Private Endpoint.

## 8. Alternatives

Environment variables đơn giản hơn cho low-risk/small systems nhưng rotation/audit kém. Azure App Configuration phù hợp non-secret configuration. Certificate-based auth hoặc workload identity có use cases khác.

## 9. Trade-offs

### Advantages

* Giảm secret distribution.
* Audit và rotation centralized.
* Least privilege dựa trên identity.

### Costs / Risks

* Thêm dependency vào Entra ID/Key Vault/networking.
* Cache/refresh semantics cần thiết kế.
* RBAC và private networking có operational complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu secret storage khác identity.

### Middle

Dùng `DefaultAzureCredential`, Key Vault RBAC và không log secrets.

### Senior

Thiết kế refresh, rotation, fallback và private networking troubleshooting.

### Technical Lead / Architect

Đặt identity-first policy: khi nào dùng Managed Identity, secret ownership, rotation SLA và permission model toàn platform.

## 11. Key takeaway

* Managed Identity giảm nhu cầu giữ Azure credentials trong application.
* Key Vault centralize secret lifecycle nhưng không tự giải quyết refresh semantics.
* Least privilege + rotation + observability phải đi cùng nhau.

# 8. IIS Application Pool recycling: process lifecycle, graceful shutdown và hidden state trong enterprise hosting

## 1. What is it?

IIS Application Pool quản lý worker process (`w3wp.exe`) cho hosted applications. Recycling là việc worker process cũ được thay bằng process mới theo config, deployment hoặc health condition.

Mental model:

```text
IIS
 └─ App Pool
     ├─ old w3wp
     └─ new w3wp during recycle
```

Application không nên giả định process sống vĩnh viễn.

## 2. Why does it exist?

Recycle giúp:

* áp dụng config/deployment;
* recover từ process degradation;
* giới hạn long-lived process issues;
* thực hiện maintenance.

Nhưng recycle cũng expose mọi hidden in-memory assumptions của application.

## 3. How does it work?

Trong overlapped recycle, IIS có thể start process mới trước khi process cũ hoàn toàn dừng để giảm downtime.

Application phải xử lý shutdown signal và stop accepting/finishing work hợp lý.

State chỉ nằm trong:

* static fields;
* in-memory cache;
* local singleton;
* local scheduled timer;

có thể mất hoặc duplicate khi process lifecycle thay đổi.

## 4. Practical implementation

ASP.NET Core background work phải honor cancellation:

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await ProcessNextAsync(stoppingToken);
        }
    }
}
```

Không chạy fire-and-forget task từ request mà không ownership/lifecycle.

## 5. Real production scenario

Legacy enterprise app dùng static dictionary làm session-like state. Mỗi đêm App Pool recycle theo schedule. Users thỉnh thoảng mất workflow state đúng thời điểm đó.

Root cause không phải “IIS random”; application đã giữ durable business state trong process memory.

## 6. Failure scenario & troubleshooting

**Symptom** → intermittent 502/503 hoặc background job dừng giữa chừng đúng lúc deploy/recycle.

**Evidence** → IIS event logs cho thấy recycle; application logs có shutdown/startup gần cùng thời điểm.

**Hypothesis** → process lifecycle không được application xử lý graceful.

**Diagnosis** → inspect App Pool recycle config, startup time, shutdown timeout, long-running work.

**Fix** → externalize durable state, honor cancellation, chuyển long-running jobs sang worker/queue phù hợp.

**Verification** → chủ động recycle trong staging dưới traffic và theo dõi request/job outcome.

## 7. Common mistakes

* Lưu business state quan trọng trong static memory.
* Chạy recurring job trong mỗi IIS instance mà không coordination.
* Tăng recycle timeout vô hạn để che job design sai.
* Không warm critical dependencies sau startup.
* Không correlate IIS logs với application telemetry.

## 8. Alternatives

Azure App Service vẫn có process restarts và scale-out semantics tương tự ở mức khái niệm. Dedicated Worker Service/Windows Service phù hợp background processing dài hạn. Containers/Kubernetes đổi orchestration nhưng không loại bỏ process lifecycle.

## 9. Trade-offs

### Advantages

* IIS cung cấp mature process hosting và recovery.
* Recycling hỗ trợ maintenance/recovery.

### Costs / Risks

* In-memory assumptions dễ vỡ.
* Cold start và background work cần xử lý.
* Legacy hosting behavior có thể khó quan sát nếu telemetry yếu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu web process có thể restart bất cứ lúc nào.

### Middle

Biết đọc IIS logs, App Pool settings và viết graceful background code.

### Senior

Chẩn đoán recycle/cold-start/state-loss incidents.

### Technical Lead / Architect

Quyết định workload nào nên ở IIS web process và workload nào cần external worker/durable state.

## 11. Key takeaway

* Process lifetime không phải application lifetime vô hạn.
* Durable business state không nên sống chỉ trong memory của `w3wp.exe`.
* Recycle testing nên là một phần của production-readiness cho legacy IIS systems.

# 9. Playwright E2E testing: bảo vệ critical user journeys mà không biến test suite thành một hệ thống flaky khổng lồ

## 1. What is it?

Playwright là browser automation framework có thể chạy Chromium, Firefox và WebKit để test behavior gần với user thật.

E2E test kiểm tra chuỗi integration xuyên nhiều layers:

```text
Browser
  ↓
Frontend
  ↓
API
  ↓
Database / external dependencies
```

Giá trị lớn nhất của E2E là bảo vệ critical journeys, không phải cover mọi branch.

## 2. Why does it exist?

Unit tests có thể chứng minh component/function hoạt động riêng lẻ nhưng không chứng minh:

* routing đúng;
* auth redirect đúng;
* frontend gọi API đúng;
* API contract khớp;
* browser rendering/event behavior đúng.

E2E test bắt lỗi integration mà lower-level tests bỏ sót.

## 3. How does it work?

Playwright điều khiển browser thật/headless, tìm elements theo role/test id/text và chờ browser conditions tự động ở nhiều operations.

Test tốt nên dựa vào user-observable behavior, không phụ thuộc DOM implementation quá chi tiết.

## 4. Practical implementation

```typescript
import { test, expect } from '@playwright/test';

test('employee can submit timesheet', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('Email').fill('employee@example.com');
  await page.getByLabel('Password').fill('Password123!');
  await page.getByRole('button', { name: 'Sign in' }).click();

  await page.getByRole('link', { name: 'Timesheets' }).click();
  await page.getByRole('button', { name: 'Submit' }).click();

  await expect(
    page.getByText('Timesheet submitted')
  ).toBeVisible();
});
```

## 5. Real production scenario

Backend đổi authorization policy và frontend vẫn build thành công. Unit tests cả hai phía xanh nhưng actual browser flow bị redirect loop sau login.

Một Playwright smoke journey phát hiện lỗi trước release.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail ngẫu nhiên trong CI nhưng pass local.

**Evidence** → fixed sleeps, shared test users/data, race giữa async UI và assertions.

**Hypothesis** → test không deterministic hoặc environment shared state.

**Diagnosis** → inspect trace/video/network logs, test isolation, selectors và explicit waits.

**Fix** → bỏ `waitForTimeout`, seed deterministic data, isolate accounts, dùng role/test-id selectors.

**Verification** → chạy test lặp lại nhiều lần song song trong CI.

## 7. Common mistakes

* Dùng E2E để test mọi validation branch.
* Dùng CSS selector phụ thuộc structure.
* `waitForTimeout(5000)` để chữa race.
* Shared mutable test data.
* Mock quá nhiều khiến E2E không còn kiểm tra integration thật.
* Chạy 1.000 browser tests thay vì dùng unit/integration tests phù hợp.

## 8. Alternatives

Unit tests nhanh cho logic thuần. Integration tests phù hợp API/database boundaries. Component tests hữu ích cho UI logic. E2E chỉ nên giữ critical cross-system journeys.

## 9. Trade-offs

### Advantages

* Bắt lỗi integration thực tế.
* Validate browser behavior và deployment wiring.
* Giá trị cao cho smoke/regression critical flows.

### Costs / Risks

* Chậm hơn lower-level tests.
* Environment/data dependency cao.
* Flakiness tăng nếu test design kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu E2E test hành vi user xuyên nhiều layers.

### Middle

Viết selectors ổn định, deterministic data và debug traces.

### Senior

Chọn đúng test layer cho từng risk và giảm flakiness systematically.

### Technical Lead / Architect

Thiết kế test portfolio: nhiều unit/integration tests, ít nhưng mạnh E2E critical journeys; đặt CI gates theo risk.

## 11. Key takeaway

* E2E test nên bảo vệ business-critical journeys, không phải mọi code path.
* Flaky test là engineering defect, không phải chuyện bình thường.
* Dùng đúng test layer giúp suite vừa nhanh vừa đáng tin.

# 10. Optimizely CMS content modeling: page type, block, content ownership và cache boundary cho website enterprise
