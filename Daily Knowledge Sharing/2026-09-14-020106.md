# 1. C# `IAsyncEnumerable<T>`: stream dữ liệu theo nhịp consumer thay vì materialize toàn bộ collection

## 1. What is it?

`IAsyncEnumerable<T>` là abstraction cho một sequence mà từng phần tử có thể được tạo ra bất đồng bộ. Mental model không phải “một `List<T>` được trả về chậm hơn”, mà là producer tạo dữ liệu theo thời gian và consumer xử lý từng item khi sẵn sàng.

```text
Producer
  |
  | item 1
  v
Consumer
  |
  | item 2
  v
Consumer
  |
  ...
```

Consumer dùng `await foreach` thay vì chờ toàn bộ sequence hoàn tất rồi mới bắt đầu xử lý.

## 2. Why does it exist?

Nếu query trả 500,000 rows, cách đơn giản sau tạo pressure lớn:

```csharp
var rows = await query.ToListAsync(ct);
```

Application phải chờ materialize toàn bộ dữ liệu, giữ memory cho cả collection rồi mới bắt đầu serialize/process.

Với streaming, time-to-first-item giảm và memory footprint thường ổn định hơn vì không cần giữ toàn bộ result set cùng lúc.

## 3. How does it work?

Method có thể `yield return` trong async iterator:

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    await foreach (var order in _db.Orders
        .AsNoTracking()
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        yield return new OrderDto(order.Id, order.Total);
    }
}
```

`await foreach` gọi asynchronous move-next operation lặp lại. Producer chỉ tiến khi consumer yêu cầu phần tử tiếp theo.

Điểm quan trọng: đây không tự động là một bounded queue hoàn chỉnh. Nếu phía trong iterator prefetch quá nhiều hoặc dependency buffer toàn bộ response, lợi ích streaming có thể biến mất.

## 4. Practical implementation

ASP.NET Core có thể stream JSON sequence ở một số API shapes:

```csharp
app.MapGet("/orders/stream", (
    OrderService service,
    CancellationToken ct) =>
{
    return service.StreamOrdersAsync(ct);
});
```

Nếu consumer xử lý từng item:

```csharp
await foreach (var order in client.StreamOrdersAsync(ct))
{
    await ProcessAsync(order, ct);
}
```

Khi iterator thực hiện I/O, hãy propagate `CancellationToken` và không giữ resource lâu hơn lifetime cần thiết.

## 5. Real production scenario

Một export service xuất hàng trăm nghìn transaction sang downstream processor. Bản cũ gọi `ToListAsync`, tạo peak memory hàng GB và thời gian chờ ban đầu dài. Chuyển sang `IAsyncEnumerable<T>` giúp downstream bắt đầu xử lý ngay từ những records đầu tiên và memory ổn định hơn.

Tuy nhiên team vẫn phải giới hạn export concurrency; streaming không đồng nghĩa có thể chạy vô hạn exports song song.

## 6. Failure scenario & troubleshooting

**Symptom** → API được gọi là “streaming” nhưng memory vẫn tăng theo tổng số records.

**Evidence** → profiler cho thấy một `List<T>` hoặc serializer buffer toàn payload trước khi gửi; database provider có thể materialize trước.

**Hypothesis** → một layer trong pipeline phá streaming semantics.

**Diagnosis** → trace từng boundary: database reader, mapping, iterator, serializer, reverse proxy và client buffering.

**Fix** → loại materialization không cần thiết; kiểm tra response buffering; dùng batch nếu end-to-end streaming không khả thi.

**Verification** → đo working set và time-to-first-byte với dataset tăng dần.

## 7. Common mistakes

- Chuyển `List<T>` thành `IAsyncEnumerable<T>` nhưng bên trong vẫn `ToListAsync`.
- Quên cancellation khi client disconnect.
- Giữ `DbContext`/connection mở trong stream rất lâu mà không hiểu capacity impact.
- Stream object cực nhỏ nhưng thực hiện N+1 query cho từng item.
- Nghĩ streaming tự động giải quyết backpressure cho mọi producer.

## 8. Alternatives

- Pagination/keyset pagination khi client cần pages rõ ràng.
- Batch processing nếu downstream làm việc theo chunks.
- `Channel<T>` khi cần producer/consumer decoupling và bounded buffering trong process.
- Queue/messaging khi work cần durable asynchronous processing.

## 9. Trade-offs

### Advantages

- Giảm peak memory.
- Giảm time-to-first-item.
- Phù hợp large result sets và pipelines.

### Costs / Risks

- Resource như DB connection có thể sống lâu.
- Error sau khi response bắt đầu stream khó chuyển thành HTTP error cleanly.
- Debugging/cancellation semantics phức tạp hơn materialized collection.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await foreach` xử lý sequence bất đồng bộ từng phần tử.

### Middle

Biết implement async iterator, cancellation và tránh materialization ngầm.

### Senior

Đánh giá connection lifetime, serialization buffering, failure giữa stream và throughput.

### Technical Lead / Architect

Quyết định khi streaming phù hợp hơn pagination/batch/queue và đặt resource budgets cho long-lived streams.

## 11. Key takeaway

- `IAsyncEnumerable<T>` hữu ích khi dữ liệu xuất hiện theo thời gian hoặc result set lớn.
- Streaming chỉ hiệu quả nếu toàn pipeline không buffer lại dữ liệu.
- Memory giảm có thể đổi lấy connection/resource lifetime dài hơn.

# 2. ASP.NET Core Endpoint Filters: cross-cutting logic ở Minimal APIs mà không biến middleware thành nơi xử lý mọi thứ

## 1. What is it?

Endpoint Filters là cơ chế cho Minimal APIs chạy logic trước/sau một endpoint handler cụ thể.

Mental model:

```text
Request
  |
Middleware
  |
Endpoint Filter 1
  |
Endpoint Filter 2
  |
Handler
  |
Response
```

Middleware áp dụng ở request pipeline rộng; endpoint filter gần endpoint hơn và nhìn thấy arguments/return value của handler.

## 2. Why does it exist?

Nếu mọi cross-cutting concern đều nhét vào middleware, middleware phải tự hiểu route-specific semantics. Ngược lại, copy validation/auditing logic vào từng handler tạo duplication.

Endpoint Filters tồn tại để xử lý concern gắn với endpoint invocation nhưng không đủ global để thành middleware.

## 3. How does it work?

Filter implement `IEndpointFilter`:

```csharp
public sealed class ValidationFilter<T> : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var argument = context.Arguments.OfType<T>().FirstOrDefault();

        if (argument is null)
            return Results.BadRequest();

        return await next(context);
    }
}
```

Filter có thể short-circuit trước handler hoặc inspect kết quả sau handler.

## 4. Practical implementation

Ví dụ check idempotency header cho nhóm endpoints:

```csharp
public sealed class RequireIdempotencyKeyFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var request = context.HttpContext.Request;

        if (!request.Headers.ContainsKey("Idempotency-Key"))
        {
            return Results.BadRequest(new
            {
                error = "missing_idempotency_key"
            });
        }

        return await next(context);
    }
}
```

Áp dụng:

```csharp
app.MapPost("/payments", HandlePayment)
   .AddEndpointFilter<RequireIdempotencyKeyFilter>();
```

Filter nên nhỏ, deterministic và focused.

## 5. Real production scenario

Một API có vài endpoints mutation cần audit business metadata đặc biệt. Middleware global không biết argument nào là aggregate ID; copy audit extraction vào từng endpoint gây duplication.

Endpoint filter cho phép lấy arguments đã bind, xác định aggregate identifier rồi thêm structured logging scope trước khi handler chạy.

## 6. Failure scenario & troubleshooting

**Symptom** → behavior khác nhau giữa endpoints dù cùng filter, hoặc filter chạy sau một middleware khiến context expected chưa tồn tại.

**Evidence** → invocation order cho thấy concern được đặt sai layer.

**Hypothesis** → team dùng filter cho concern thực ra phải xử lý global ở middleware/authentication hoặc ngược lại.

**Diagnosis** → map request lifecycle: middleware → routing → endpoint filters → handler.

**Fix** → chuyển concern về boundary đúng: global HTTP concern ở middleware, authorization ở policy, endpoint-specific invocation concern ở filter.

**Verification** → integration tests trên filter order và short-circuit paths.

## 7. Common mistakes

- Dùng Endpoint Filters thay authorization policy.
- Viết một filter “god object” validate/log/cache/auth tất cả.
- Throw arbitrary exceptions trong filter thay vì dùng error contract thống nhất.
- Depend vào argument index cứng dễ vỡ khi handler signature đổi.
- Đưa business rules vào filter khiến domain logic ẩn khỏi application layer.

## 8. Alternatives

- Middleware cho global request/response concerns.
- MVC filters khi dùng controllers/MVC pipeline.
- Authorization policies cho access control.
- Decorator/application pipeline behaviors cho application-command concerns.

## 9. Trade-offs

### Advantages

- Reuse logic ở endpoint boundary.
- Access được bound arguments.
- Dễ áp dụng chọn lọc theo endpoint/group.

### Costs / Risks

- Thêm một pipeline layer cần hiểu order.
- Có thể phân tán business logic nếu lạm dụng.
- Không phù hợp mọi cross-cutting concern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu endpoint filter nằm gần handler hơn middleware.

### Middle

Biết viết filter nhỏ, test short-circuit và đăng ký đúng endpoint.

### Senior

Phân biệt concern thuộc middleware, filter, authorization hay application layer.

### Technical Lead / Architect

Định nghĩa conventions để pipeline không trở thành tập hợp cross-cutting abstractions chồng chéo.

## 11. Key takeaway

- Endpoint Filters là endpoint-invocation boundary, không phải middleware replacement tổng quát.
- Dùng chúng cho concern có scope hẹp và cần bound arguments.
- Business rules cốt lõi vẫn nên ở application/domain layer.

# 3. EF Core Temporal Tables: audit và point-in-time recovery cho entity history mà không tự xây lịch sử thủ công

## 1. What is it?

Temporal Table của SQL Server tự động lưu historical versions mỗi khi row thay đổi hoặc bị xóa. EF Core có hỗ trợ query history của temporal tables.

Mental model:

```text
Current table
   |
UPDATE/DELETE
   |
old row version
   v
History table
```

Database, không phải application code, chịu trách nhiệm ghi versions theo system time.

## 2. Why does it exist?

Nếu application tự ghi audit snapshot trong `SaveChanges`, rất dễ bỏ sót paths như raw SQL, migration script hoặc integration khác ghi trực tiếp database.

Temporal tables cho history ở database boundary, hữu ích cho audit kỹ thuật, debugging và point-in-time reconstruction.

## 3. How does it work?

SQL Server duy trì hai period columns, ví dụ `ValidFrom` và `ValidTo`, rồi chuyển old row sang history table khi data thay đổi.

EF configuration:

```csharp
modelBuilder.Entity<Employee>()
    .ToTable("Employees", b => b.IsTemporal());
```

Query history:

```csharp
var history = await db.Employees
    .TemporalAll()
    .Where(x => x.Id == employeeId)
    .OrderBy(x => EF.Property<DateTime>(x, "PeriodStart"))
    .ToListAsync(ct);
```

## 4. Practical implementation

Point-in-time query:

```csharp
var employeeAtTime = await db.Employees
    .TemporalAsOf(incidentTimeUtc)
    .SingleOrDefaultAsync(x => x.Id == employeeId, ct);
```

Đây hữu ích khi production incident hỏi: “Record này có giá trị gì lúc 14:03 UTC trước deployment?”

Temporal history không thay business audit log. Nếu cần biết **ai** thay đổi và **vì sao**, vẫn cần actor/reason metadata ở layer phù hợp.

## 5. Real production scenario

Một payroll configuration bị update sai vào buổi chiều. Current table chỉ còn giá trị mới. Temporal history cho phép team reconstruct exact row trước incident và xác định thời điểm thay đổi, sau đó restore có kiểm soát.

Business audit log bổ sung user ID và ticket/reason để điều tra trách nhiệm và workflow.

## 6. Failure scenario & troubleshooting

**Symptom** → history table tăng rất nhanh, storage/cost tăng hoặc historical query chậm.

**Evidence** → high-churn entities tạo hàng triệu versions; retention không được định nghĩa.

**Hypothesis** → temporal được enable rộng mà không có retention/storage strategy.

**Diagnosis** → đo churn rate, history size, query patterns và retention requirement.

**Fix** → chỉ temporalize entities có giá trị; thiết kế retention/archive/indexing phù hợp.

**Verification** → monitor history growth và test point-in-time query performance.

## 7. Common mistakes

- Nghĩ temporal table thay thế business audit trail.
- Enable temporal cho mọi table không cần lịch sử.
- Không tính storage growth cho hot rows.
- Query `TemporalAll` không filter khiến scan history lớn.
- Cho phép restore tự động mà không kiểm tra dependent state.

## 8. Alternatives

- Application audit table có actor/reason rõ ràng.
- Event Sourcing khi domain cần event history là source of truth.
- CDC/change feed khi mục tiêu là integration/data pipeline.

## 9. Trade-offs

### Advantages

- History được ghi ở database boundary.
- Query point-in-time đơn giản.
- Giúp production debugging và accidental-change recovery.

### Costs / Risks

- Storage tăng theo update frequency.
- Không tự chứa business intent/actor.
- Retention/indexing cần quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu current row và historical versions là hai views của cùng entity qua thời gian.

### Middle

Biết configure/query temporal data trong EF Core.

### Senior

Thiết kế retention, indexing và phân biệt temporal history với audit/event sourcing.

### Technical Lead / Architect

Quyết định entities nào đáng temporalize và policy restore/compliance nào cần đi cùng.

## 11. Key takeaway

- Temporal tables là database-level history, rất hữu ích cho debugging và recovery.
- Chúng không thay thế business audit metadata.
- History growth phải được tính như một production storage concern.

# 4. SQL Server lock escalation: khi hàng nghìn row locks biến thành table lock và kéo theo blocking chain

## 1. What is it?

Lock escalation là cơ chế SQL Server có thể chuyển nhiều fine-grained locks như row/page locks thành lock coarse-grained hơn, thường là table lock, để giảm memory/lock-management overhead.

Mental model:

```text
many row locks
   + row
   + row
   + row
   + ...
      |
      v
possible escalation
      |
   table lock
```

Nó là resource-management behavior, không đơn giản là “SQL Server tự nhiên khóa cả bảng”.

## 2. Why does it exist?

Mỗi lock có memory/management cost. Transaction update hàng trăm nghìn rows có thể tạo lượng locks rất lớn. Escalation giảm overhead nhưng đánh đổi concurrency.

Một transaction vốn chỉ đụng nhiều rows có thể sau escalation block queries trên toàn table.

## 3. How does it work?

Ví dụ batch lớn:

```sql
UPDATE Orders
SET Archived = 1
WHERE CreatedAt < '2024-01-01';
```

Nếu query ảnh hưởng rất nhiều rows và giữ locks lâu, engine có thể chọn escalation. Khi transaction chưa commit, readers/writers khác có thể bị block tùy isolation mode và lock compatibility.

Performance path cần hiểu:

```text
query
 -> execution plan
 -> rows touched
 -> lock count/duration
 -> escalation/blocking
 -> latency
```

## 4. Practical implementation

Thay vì update hàng triệu rows trong một transaction, có thể batch:

```sql
WHILE 1 = 1
BEGIN
    UPDATE TOP (5000) Orders
    SET Archived = 1
    WHERE CreatedAt < '2024-01-01'
      AND Archived = 0;

    IF @@ROWCOUNT = 0 BREAK;
END
```

Batch size phải đo dựa trên log growth, lock duration và throughput; không có số universal.

Index phù hợp cho predicate cũng giúp giảm rows/pages phải scan/lock, nhưng chỉ sau khi xem plan/I/O.

## 5. Real production scenario

Một nightly cleanup job update 8 triệu records lúc 01:00. Bình thường user traffic thấp nên không thấy vấn đề. Một hôm business batch khác chạy cùng giờ; cleanup giữ table-level lock vài chục giây, API requests bắt đầu queue và p99 tăng mạnh.

Root cause là interaction giữa transaction size, execution plan và lock duration, không chỉ “database chậm”.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều queries cùng chờ trên một table dù chúng truy cập rows khác nhau.

**Evidence** → blocking tree cho thấy session batch lớn ở root blocker; lock DMVs/Extended Events cho thấy escalation/table lock.

**Hypothesis** → transaction touches quá nhiều rows hoặc scan quá rộng.

**Diagnosis** → inspect actual plan, row counts, lock waits, transaction duration, index usage.

**Fix** → batch transaction, cải thiện access path, schedule/partition workload phù hợp; không disable escalation mặc định như phản xạ đầu tiên.

**Verification** → rerun representative batch dưới concurrent traffic và đo lock waits/p95/p99.

## 7. Common mistakes

- Dùng `NOLOCK` để “fix blocking”.
- Disable lock escalation toàn table mà không hiểu memory consequence.
- Update/delete millions rows trong một transaction chỉ vì code đơn giản.
- Không index cleanup predicate khiến full scan.
- Chỉ nhìn query duration mà không xem blocking tree.

## 8. Alternatives

- Smaller batches.
- Partition switch/archive strategy cho very large datasets.
- Snapshot-based isolation có thể giảm reader-writer blocking nhưng không giải quyết mọi writer contention.
- Background maintenance windows nếu business chấp nhận.

## 9. Trade-offs

### Advantages

- Escalation bảo vệ engine khỏi quá nhiều fine-grained locks.
- Coarse lock management rẻ hơn.

### Costs / Risks

- Concurrency giảm mạnh khi table lock xuất hiện.
- Long transactions khuếch đại blocking/log growth.
- Batch processing thêm orchestration/restart semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu locks có scope và transaction giữ lock trong khoảng thời gian nhất định.

### Middle

Biết đọc blocking sessions và tránh huge transactions không cần thiết.

### Senior

Liên kết execution plan, rows touched, lock count và transaction duration.

### Technical Lead / Architect

Thiết kế data-maintenance strategy để operational jobs không cạnh tranh trực tiếp với online workload.

## 11. Key takeaway

- Lock escalation thường là symptom của large lock footprint, không phải root cause độc lập.
- Batching và access path tốt thường an toàn hơn disable escalation.
- Điều tra blocking bằng evidence: blocker, plan, rows, locks, transaction duration.

# 5. Redis eviction policies: khi cache đầy thì key nào bị loại và vì sao lựa chọn policy ảnh hưởng correctness

## 1. What is it?

Redis eviction policy quyết định chuyện gì xảy ra khi memory đạt `maxmemory` và một write mới cần thêm RAM.

Mental model:

```text
Redis memory full
      |
new write
      |
policy decision
  /      |      \
evict   reject   choose keys
```

Cache không chỉ có TTL; khi memory pressure xuất hiện, policy có thể loại key trước khi TTL hết.

## 2. Why does it exist?

Redis không thể tăng memory vô hạn. Production cache cần bounded resource behavior. Nếu không hiểu eviction, team có thể nghĩ “TTL 30 phút” nghĩa key chắc chắn tồn tại 30 phút, trong khi key có thể bị evict sau 2 phút do memory pressure.

## 3. How does it work?

Một số policy phổ biến gồm concepts như:

- `noeviction`: write mới fail khi memory đầy;
- `allkeys-lru`: chọn keys gần least-recently-used trong toàn keyspace;
- `allkeys-lfu`: ưu tiên giữ keys truy cập thường xuyên;
- `volatile-*`: chỉ xét keys có TTL.

Redis sử dụng approximations chứ không phải perfect global LRU theo nghĩa textbook.

## 4. Practical implementation

Đầu tiên phân loại Redis role:

```text
pure cache?
shared session store?
rate-limit counters?
distributed coordination?
```

Nếu cùng Redis instance chứa both cache và correctness-sensitive state, eviction policy trở thành architectural risk.

Monitor:

- used memory;
- evicted keys;
- hit/miss ratio;
- key count/TTL distribution;
- largest key patterns.

## 5. Real production scenario

Một e-commerce app dùng cùng Redis cho product cache và session. Policy `allkeys-lru` được bật để cache tự giải phóng memory. Trong traffic spike, session keys cũng có thể bị evict, user bị logout ngẫu nhiên.

Vấn đề không chỉ là chọn policy sai; hai workloads có correctness requirements khác nhau nhưng bị đặt chung resource pool.

## 6. Failure scenario & troubleshooting

**Symptom** → hit ratio tụt và database load tăng dù TTL không đổi.

**Evidence** → `evicted_keys` tăng mạnh, memory sát `maxmemory`, key size distribution lớn.

**Hypothesis** → memory pressure đang evict hot/useful data.

**Diagnosis** → xác định key categories, sizes, access frequency và policy hiện tại.

**Fix** → chọn policy phù hợp, giới hạn key size, chia workloads hoặc tăng capacity nếu justified.

**Verification** → load test memory pressure và theo dõi eviction rate + downstream DB QPS.

## 7. Common mistakes

- Dùng Redis làm critical durable store nhưng bật eviction.
- Không đặt `maxmemory` rõ ràng.
- Chỉ monitor CPU, không monitor evictions/memory fragmentation.
- Cho một vài giant keys chiếm phần lớn RAM.
- Nghĩ TTL đảm bảo minimum lifetime.
- Trộn session/locks/cache trong cùng instance mà không đánh giá failure semantics.

## 8. Alternatives

- `IMemoryCache` cho per-instance disposable cache.
- Separate Redis instances/pools theo workload criticality.
- Database/read model nếu data không thể mất.
- No cache nếu source đủ nhanh và cache complexity không đáng giá.

## 9. Trade-offs

### Advantages

- Eviction giúp Redis giữ bounded memory.
- LRU/LFU-style policies thích hợp pure cache workloads.

### Costs / Risks

- Hit ratio có thể giảm đột ngột dưới pressure.
- Wrong policy có thể ảnh hưởng correctness-sensitive keys.
- Tách instances tăng cost/operations.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu key có thể biến mất vì TTL hoặc eviction.

### Middle

Biết monitor memory, evictions và chọn policy theo cache workload.

### Senior

Đánh giá key criticality, memory sizing và downstream impact khi cache churn.

### Technical Lead / Architect

Quyết định workloads nào được phép share Redis và workloads nào cần isolation/durability khác.

## 11. Key takeaway

- Eviction policy là failure behavior của cache dưới memory pressure.
- TTL không đảm bảo key sống đủ lâu.
- Không nên trộn disposable cache với correctness-critical state mà không có isolation rõ ràng.

# 6. Bulkhead Pattern: cô lập resource pool để một dependency chậm không kéo sập toàn service

## 1. What is it?

Bulkhead Pattern chia tài nguyên/concurrency thành các vùng độc lập, giống khoang kín trên tàu. Nếu một dependency/workload bị treo hoặc overload, nó không được phép chiếm toàn bộ capacity của process.

Mental model:

```text
Service capacity
  |
  +--> Inventory calls: max 50
  +--> Reviews calls:   max 20
  +--> Search calls:    max 40
```

Thay vì mọi outbound call cạnh tranh một pool vô hạn, mỗi dependency có concurrency budget.

## 2. Why does it exist?

Một downstream chậm làm request giữ connection/thread/task slot lâu hơn. Nếu application tiếp tục mở thêm hàng nghìn concurrent calls, socket pool, memory hoặc downstream itself có thể collapse.

Timeout giúp giới hạn duration, nhưng không giới hạn số concurrent operations đang chờ. Bulkhead giải quyết dimension concurrency/isolation.

## 3. How does it work?

Một semaphore-style limiter có thể đặt trước dependency call:

```csharp
private readonly SemaphoreSlim _gate = new(40);

public async Task<Response> CallAsync(CancellationToken ct)
{
    await _gate.WaitAsync(ct);
    try
    {
        return await _client.GetAsync(ct);
    }
    finally
    {
        _gate.Release();
    }
}
```

Production implementation nên có queue limit/rejection semantics, telemetry và integration với timeout/retry policy.

## 4. Practical implementation

Mục tiêu không phải “chặn tất cả quá 40” một cách tùy tiện. Capacity cần dựa trên:

- downstream documented/observed capacity;
- latency distribution;
- local connection limits;
- acceptable queue time;
- request priority.

Nếu queue đã đầy, fail fast hoặc degrade thường tốt hơn giữ request vô hạn.

## 5. Real production scenario

Product page gọi inventory, reviews và recommendations. Recommendation service chậm 10 giây. Không có isolation, hàng nghìn pending recommendation calls chiếm outbound resources và làm inventory cũng timeout.

Bulkhead riêng cho recommendations giới hạn blast radius; khi full, page bỏ recommendation block nhưng vẫn trả inventory/product core data.

## 6. Failure scenario & troubleshooting

**Symptom** → một dependency degradation làm unrelated endpoints latency tăng.

**Evidence** → connection/task counts cho dependency lỗi tăng mạnh; shared pools saturated.

**Hypothesis** → không có concurrency isolation hoặc retry đang khuếch đại traffic.

**Diagnosis** → correlate dependency latency, active calls, queue depth, connection pool và endpoint latency.

**Fix** → per-dependency concurrency limits, timeout, bounded retry, fallback/degradation.

**Verification** → fault injection cho một dependency và xác nhận unrelated traffic vẫn khỏe.

## 7. Common mistakes

- Bulkhead limit cao đến mức không còn isolation.
- Không giới hạn waiting queue.
- Retry ngay bên trong saturated bulkhead tạo retry storm.
- Một global semaphore cho mọi dependency.
- Chọn number theo cảm giác, không đo.
- Fail closed với optional dependency khiến core request chết vô ích.

## 8. Alternatives

- Rate limiting kiểm soát request rate theo thời gian, không giống active concurrency.
- Circuit Breaker ngừng gọi dependency đang fail; thường dùng cùng bulkhead.
- Queue-based async processing cho work không cần synchronous response.

## 9. Trade-offs

### Advantages

- Giới hạn blast radius.
- Làm overload behavior predictable hơn.
- Bảo vệ local và downstream resources.

### Costs / Risks

- Request có thể bị reject dù còn tổng capacity elsewhere.
- Capacity tuning cần telemetry.
- Nhiều pools/limits tăng operational knobs.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dependency chậm có thể giữ resource dù chưa fail.

### Middle

Biết giới hạn concurrency và luôn release permit đúng cách.

### Senior

Kết hợp bulkhead với timeout, retry, circuit breaker và degradation.

### Technical Lead / Architect

Định nghĩa dependency budgets và business priority để optional failures không kéo core journey xuống.

## 11. Key takeaway

- Timeout giới hạn thời gian; bulkhead giới hạn concurrency/blast radius.
- Isolation đặc biệt quan trọng khi một service gọi nhiều remote dependencies.
- Capacity limits phải dựa trên measurements và business degradation strategy.

# 7. Azure Blob Storage lifecycle & access tiers: tối ưu retention/cost mà vẫn kiểm soát latency và recovery

## 1. What is it?

Azure Blob Storage access tiers và lifecycle policies cho phép dữ liệu chuyển giữa các mức lưu trữ có cost/latency/availability characteristics khác nhau theo age hoặc conditions.

Mental model:

```text
Hot
 |
 | after 30 days
 v
Cool
 |
 | after 180 days
 v
Cold/Archive
 |
 | retention policy
 v
Delete
```

Mục tiêu là tách **data value over time** khỏi việc giữ mọi blob ở tier đắt nhất vĩnh viễn.

## 2. Why does it exist?

Log exports, media originals, invoices hoặc backup artifacts thường truy cập nhiều ngay sau khi tạo rồi gần như không dùng. Nếu giữ tất cả ở hot tier, storage cost không phản ánh actual access pattern.

Nhưng hạ tier quá sớm có thể tăng retrieval cost/latency hoặc minimum-retention penalties.

## 3. How does it work?

Lifecycle management rule match theo prefix/tags/age rồi thực hiện transition/delete. Archive tier có retrieval semantics khác hot/cool; application không nên giả định mọi blob đọc được ngay lập tức.

Security vẫn nằm ở identity/SAS/private networking; lifecycle không thay access-control model.

## 4. Practical implementation

Ví dụ policy concept:

```text
container: exports/
0-30 days   -> Hot
31-180 days -> Cool
>180 days   -> Archive
>730 days   -> Delete
```

Trước khi áp dụng phải hỏi:

- có legal retention không?
- user có thể tải file cũ ngay lập tức không?
- restore SLA là gì?
- file nào là source-of-truth?

Monitor capacity theo tier, read/rehydration operations và policy effects.

## 5. Real production scenario

Một SaaS giữ monthly report PDFs 7 năm. 95% downloads xảy ra trong 60 ngày đầu. Lifecycle chuyển older reports sang lower-cost tier. Tuy nhiên reports thuộc regulatory requests phải retrievable trong một SLA cụ thể nên không được đẩy vào Archive nếu rehydration quá chậm cho requirement.

## 6. Failure scenario & troubleshooting

**Symptom** → user request file 2 năm tuổi và application timeout vì blob đang archived.

**Evidence** → blob tier là Archive; code giả định normal `DownloadAsync` sẽ trả ngay.

**Hypothesis** → product SLA không được map vào tiering policy.

**Diagnosis** → review access distribution, lifecycle rules, rehydration process và user-facing behavior.

**Fix** → giữ required data ở online tier hoặc implement asynchronous rehydration workflow/status notification.

**Verification** → test old-file retrieval path thực tế, không chỉ fresh blobs.

## 7. Common mistakes

- Chọn tier chỉ theo storage price/GB.
- Không tính read/retrieval/early deletion costs.
- Archive data mà UX yêu cầu instant access.
- Delete tự động mà không map legal retention.
- Lifecycle rule dùng prefix quá rộng xóa nhầm category.
- Không có monitoring/audit cho policy changes.

## 8. Alternatives

- Giữ tất cả ở Hot khi dataset nhỏ và simplicity đáng giá hơn optimization.
- Separate storage accounts/containers theo retention class.
- External archival system khi compliance/workflow yêu cầu khác Blob lifecycle.

## 9. Trade-offs

### Advantages

- Giảm long-term storage cost.
- Tự động hóa retention/tiering.
- Scale tốt cho large object datasets.

### Costs / Risks

- Lower tiers có retrieval/latency/cost trade-offs.
- Policy sai có thể gây data loss hoặc poor UX.
- Compliance mapping phải rõ ràng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu blob storage có tiers và lifecycle không đồng nghĩa backup.

### Middle

Biết cấu hình rule theo age/prefix và hiểu basic retrieval implications.

### Senior

Đánh giá access pattern, costs, retention và rehydration failure paths.

### Technical Lead / Architect

Map product/compliance SLA vào storage class, lifecycle policy và recovery workflow.

## 11. Key takeaway

- Storage tiering là business-SLA decision, không chỉ cost optimization.
- Archive tier cần explicit rehydration behavior.
- Lifecycle rules phải được review như production automation có khả năng xóa dữ liệu.

# 8. p99 latency và coordinated omission: load test có thể “đẹp giả” nếu tool ngừng gửi request khi hệ thống chậm

## 1. What is it?

p99 latency là ngưỡng mà 99% requests hoàn thành nhanh hơn hoặc bằng nó; 1% còn lại chậm hơn. Coordinated omission là measurement error khi load generator chờ request trước hoàn tất rồi mới gửi request tiếp, làm nó vô tình giảm offered load đúng lúc system chậm.

Mental model:

```text
Expected: send every 10 ms
System stalls 1 s

Naive closed loop:
send -> wait 1 s -> send next

Reality users/traffic:
requests vẫn có thể đến trong 1 s đó
```

Kết quả test bỏ sót queueing pain và tail latency thật.

## 2. Why does it exist?

Average latency che tail. Một API average 100 ms nhưng p99 5 giây vẫn gây experience xấu cho volume lớn.

Load testing còn dễ tự điều tiết khi server chậm, khiến throughput giảm và latency report trông tốt hơn workload thật.

## 3. How does it work?

Phải phân biệt:

- **closed-loop workload**: next request phụ thuộc response trước;
- **open-loop/arrival-rate workload**: requests đến theo schedule/rate độc lập response latency.

Nếu production traffic gần open-loop, test cũng cần mô phỏng arrival pattern đó hoặc correction phù hợp.

## 4. Practical implementation

Investigation loop:

```text
measure p50/p95/p99
    -> identify bottleneck
    -> hypothesis
    -> controlled change
    -> repeat same workload
```

Ví dụ test ở 500 requests/s phải cố giữ offered load 500 rps trong incident-like slowdown, rồi quan sát queueing, timeout và rejection—not silently drop to 100 rps because generator is waiting.

## 5. Real production scenario

Team chạy load test và thấy p99 400 ms ở 1,000 “virtual users”. Production event lại có p99 8 giây. Test tool mỗi virtual user gửi request mới chỉ sau khi response cũ trả về. Khi backend chậm, request arrival tự giảm, trong khi production mobile clients vẫn tiếp tục gửi từ hàng chục nghìn users độc lập.

Test workload model sai, không phải production “mysteriously worse”.

## 6. Failure scenario & troubleshooting

**Symptom** → lab test đẹp nhưng production queue/latency collapse dưới traffic spike.

**Evidence** → load generator achieved RPS giảm đúng lúc latency tăng; configured concurrency khác actual arrival rate.

**Hypothesis** → coordinated omission hoặc workload model không đại diện production.

**Diagnosis** → so sánh intended vs achieved RPS, concurrency, latency histogram và production arrival pattern.

**Fix** → dùng arrival-rate/open-loop model phù hợp, capture full percentile distribution và overload behavior.

**Verification** → test giữ offered load ổn định và xác nhận saturation/rejection curve giống production hơn.

## 7. Common mistakes

- Chỉ báo average latency.
- Không ghi achieved throughput.
- Tăng virtual users nhưng không biết actual request arrival model.
- Loại timeouts khỏi percentile report.
- So sánh test environments có data/dependency latency khác production.
- Tune app dựa trên benchmark micro không liên quan bottleneck thật.

## 8. Alternatives

- Trace-based replay từ production traffic patterns.
- Capacity test + stress test + soak test riêng cho các mục tiêu khác nhau.
- Synthetic monitoring cho low-volume continuous validation, không thay load testing.

## 9. Trade-offs

### Advantages

- Tail percentiles phản ánh user pain tốt hơn average.
- Correct arrival model giúp thấy queueing/overload thật.

### Costs / Risks

- Open-loop test có thể tạo tải rất lớn; cần safety controls.
- Production-like datasets/dependencies tốn công.
- Percentile interpretation cần sufficient sample size.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu p99 nói về tail, không phải 99% availability.

### Middle

Biết ghi p50/p95/p99 và achieved RPS.

### Senior

Nhận diện coordinated omission và model workload đúng theo arrival behavior.

### Technical Lead / Architect

Định nghĩa performance SLO/capacity test để system behavior dưới saturation được biết trước release.

## 11. Key takeaway

- Average latency không đủ để đánh giá user experience dưới load.
- Load generator có thể tự giảm tải khi server chậm và tạo kết quả “đẹp giả”.
- Luôn xem intended load, achieved load, queueing và tail latency cùng nhau.

# 9. CORS vs CSRF: hai security problem khác nhau nhưng thường bị cấu hình lẫn lộn

## 1. What is it?

CORS và CSRF giải quyết hai vấn đề khác nhau.

```text
CORS
-> Browser có cho JavaScript origin A đọc/gửi cross-origin request tới origin B không?

CSRF
-> Attacker site có thể khiến browser của victim gửi authenticated request ngoài ý muốn không?
```

CORS là browser cross-origin access policy. CSRF là abuse của ambient credentials như cookies.

## 2. Why does it exist?

Same-Origin Policy hạn chế JavaScript đọc tài nguyên từ origin khác. CORS cho server nới quyền có kiểm soát.

CSRF xuất hiện khi browser tự động đính kèm credential, thường là cookie, vào request tới target site. User không cần JavaScript của attacker đọc response để damage xảy ra; chỉ cần request mutation được gửi thành công.

## 3. How does it work?

CORS có preflight cho một số requests:

```text
Browser -> OPTIONS
Server  -> Access-Control-Allow-Origin / Methods / Headers
Browser -> actual request (nếu policy cho phép)
```

CSRF defense thường gồm SameSite cookies, anti-forgery token và design không dùng GET cho mutations.

Bearer token trong `Authorization` header mà attacker site không thể tự lấy thường có CSRF profile khác cookie auth, nhưng XSS/token leakage vẫn là risk riêng.

## 4. Practical implementation

ASP.NET Core CORS policy:

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("frontend", policy =>
    {
        policy.WithOrigins("https://app.example.com")
              .AllowAnyHeader()
              .AllowAnyMethod()
              .AllowCredentials();
    });
});
```

Không dùng `AllowAnyOrigin()` cùng credentialed requests.

Với cookie-authenticated form/app, dùng anti-forgery mechanism phù hợp và SameSite policy được test xuyên actual login flow.

## 5. Real production scenario

Team thấy frontend khác domain bị CORS error và đổi policy thành allow-all. Sau đó họ tin rằng “CSRF đã được xử lý vì CORS restrict browser”. Nhưng API dùng cookie auth và endpoint mutation vẫn chấp nhận forged form POST từ site khác.

CORS không phải CSRF token replacement.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend báo CORS error nhưng request đã có thể chạm server; hoặc CSRF vulnerability tồn tại dù CORS restrictive.

**Evidence** → browser DevTools cho thấy preflight/response headers; server logs cho biết request mutation vẫn được nhận.

**Hypothesis** → team đang dùng CORS để giải quyết authentication/CSRF problem.

**Diagnosis** → xác định credential type, origin model, preflight behavior, SameSite/anti-forgery settings.

**Fix** → CORS whitelist đúng origins; implement CSRF defense cho ambient-cookie authentication.

**Verification** → browser integration tests từ allowed/disallowed origins và explicit CSRF attack simulation.

## 7. Common mistakes

- `AllowAnyOrigin` production chỉ để hết browser error.
- Nghĩ CORS là server firewall.
- Nghĩ CORS chặn direct HTTP clients/curl.
- Nghĩ SameSite luôn đủ cho mọi flow.
- Dùng GET cho state-changing operations.
- Disable anti-forgery vì SPA “không phải MVC form”.

## 8. Alternatives

- Same-origin BFF architecture có thể giảm cross-origin complexity.
- Bearer-token APIs có security model khác cookie-auth apps.
- Reverse proxy để frontend/backend cùng origin khi phù hợp.

## 9. Trade-offs

### Advantages

- CORS cho phép controlled cross-origin browser integration.
- CSRF defenses bảo vệ cookie-authenticated mutations.

### Costs / Risks

- Multi-origin setups phức tạp với credentials/preflight.
- Misconfiguration dễ tạo overly broad trust.
- Security behavior phụ thuộc browser + authentication model.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt CORS browser policy với CSRF attack.

### Middle

Cấu hình explicit origins và anti-forgery đúng auth model.

### Senior

Debug preflight, SameSite, credential flow và attack surface xuyên environments.

### Technical Lead / Architect

Chọn browser/auth architecture giảm unnecessary cross-origin trust và chuẩn hóa secure defaults.

## 11. Key takeaway

- CORS và CSRF không thay thế nhau.
- CORS giới hạn browser cross-origin access; CSRF bảo vệ authenticated side effects.
- Bắt đầu từ credential model rồi mới chọn security controls.

# 10. Incremental modernization từ .NET Framework sang modern .NET: giảm migration risk bằng strangler-style boundaries thay vì rewrite toàn hệ thống

## 1. What is it?

Incremental modernization là chuyển dần capability từ legacy .NET Framework sang modern .NET thay vì rewrite toàn application trong một lần.

Mental model:

```text
Legacy App
  |
  +--> Module A remains
  +--> Module B extracted -> modern .NET
  +--> Module C migrated later

Traffic/integration boundaries dịch chuyển dần
```

Mục tiêu là giảm blast radius và cho phép business tiếp tục release trong quá trình migration.

## 2. Why does it exist?

Big-bang rewrite có ba rủi ro lớn:

1. business logic implicit bị bỏ sót;
2. migration kéo dài nên source system tiếp tục thay đổi;
3. value chỉ xuất hiện cuối project.

Enterprise legacy code thường chứa years of edge cases mà docs không ghi lại. Migration cần evidence, not optimism.

## 3. How does it work?

Trước tiên inventory:

- target framework/package compatibility;
- `System.Web`, WCF, Windows-only dependencies;
- authentication/session model;
- EF/ADO.NET usage;
- IIS assumptions;
- background jobs;
- deployment/configuration;
- shared database coupling.

Sau đó tạo seams: API boundary, reverse proxy route, shared library extracted theo compatible target, hoặc module ownership rõ ràng.

## 4. Practical implementation

Một migration flow thực dụng:

```text
1. Add characterization tests around legacy behavior
2. Identify low-coupling module
3. Define API/data contract
4. Implement module in modern .NET
5. Route small traffic slice
6. Compare telemetry/results
7. Expand traffic
8. Remove legacy path only after confidence
```

Nếu legacy và modern app cùng truy cập database, schema ownership phải cực kỳ rõ. Shared database có thể là bridge tạm thời, không nên mặc định trở thành permanent coupling.

## 5. Real production scenario

Một ASP.NET MVC 5 commerce admin chạy .NET Framework với hàng trăm screens. Team không rewrite toàn bộ. Họ migrate reporting/export module trước vì ít write coupling, expose internal API và chạy modern .NET service song song.

Sau đó authentication/session và high-coupling checkout admin được xử lý sau khi team đã xây deployment/observability patterns cho stack mới.

## 6. Failure scenario & troubleshooting

**Symptom** → migration module “works” functionally nhưng production behavior khác: auth claims thiếu, date/time formatting khác, config/env assumptions sai.

**Evidence** → characterization tests chỉ cover happy path; telemetry hai systems khác nhau.

**Hypothesis** → hidden runtime/hosting behavior chưa được captured.

**Diagnosis** → compare requests, headers, config, DB transactions, serialization, culture/timezone, auth/session semantics.

**Fix** → contract tests + side-by-side validation + explicit compatibility adapters.

**Verification** → shadow/dual-run representative traffic khi safe và compare outputs/metrics.

## 7. Common mistakes

- Rewrite vì code “xấu” mà không có business justification.
- Upgrade framework và architecture cùng lúc trên toàn system.
- Chuyển sang microservices chỉ vì đang modernization.
- Không có characterization tests cho legacy behavior.
- Shared database vô thời hạn khiến “new service” vẫn coupled như cũ.
- Cắt production một lần mà không rollback route.

## 8. Alternatives

- In-place framework/runtime upgrade nếu application compatible và architecture chưa cần thay.
- Replatform hosting trước, refactor sau.
- Full rewrite chỉ khi domain nhỏ, legacy behavior hiểu rõ và migration economics thực sự thuận lợi.

## 9. Trade-offs

### Advantages

- Giảm blast radius.
- Deliver value theo từng increment.
- Có rollback/fallback tốt hơn big-bang.
- Team học modern stack trong production từng bước.

### Costs / Risks

- Tạm thời phải vận hành hai stacks.
- Integration/contract boundaries thêm complexity.
- Migration có thể kéo dài nếu không có ownership/end-state rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu migration không chỉ là đổi target framework rồi compile.

### Middle

Biết inventory dependencies, fix APIs/config và viết regression tests.

### Senior

Thiết kế compatibility boundary, rollout, observability và rollback.

### Technical Lead / Architect

Quyết định sequencing theo business risk, xác định end-state và tránh modernization biến thành architecture rewrite không kiểm soát.

## 11. Key takeaway

- Modernization tốt nhất thường là một chuỗi migrations nhỏ có verification, không phải big-bang rewrite.
- Characterization tests và observability quan trọng ngang code conversion.
- Đừng gắn migration runtime với microservices/architecture rewrite nếu không có vấn đề thực sự cần giải quyết.
