# 1. C# `IAsyncEnumerable<T>` và streaming backpressure: xử lý dữ liệu theo dòng thay vì materialize toàn bộ collection vào memory

## 1. What is it?

`IAsyncEnumerable<T>` biểu diễn một sequence mà từng phần tử có thể được tạo bất đồng bộ theo thời gian. Thay vì chờ toàn bộ dữ liệu hoàn thành rồi trả `List<T>`, consumer có thể đọc từng item bằng `await foreach`.

Mental model:

```text
List<T>
producer -> load everything -> return full collection -> consumer

IAsyncEnumerable<T>
producer -> item 1 -> consumer
         -> item 2 -> consumer
         -> item 3 -> consumer
```

Điểm quan trọng không phải syntax `await foreach`, mà là **streaming boundary**: producer chỉ cần giữ một phần nhỏ dữ liệu tại một thời điểm.

## 2. Why does it exist?

Một export endpoint đọc 2 triệu rows rồi `ToListAsync()` sẽ giữ toàn bộ objects trong memory trước khi serialize. Điều này tăng:

- allocation;
- GC pressure;
- time-to-first-byte;
- nguy cơ OutOfMemory;
- thời gian giữ dữ liệu không cần thiết.

Streaming cho phép bắt đầu xử lý sớm và giữ memory gần với kích thước batch/item hiện tại.

## 3. How does it work?

Compiler biến async iterator thành state machine. Mỗi lần consumer gọi `MoveNextAsync`, producer chạy tới `yield return` tiếp theo.

```text
consumer asks next
   |
   v
producer performs async I/O
   |
   v
yield item
   |
   v
consumer processes item
```

Đây tạo một dạng natural backpressure: producer không cần chạy xa hơn tốc độ consumer nếu pipeline được thiết kế đúng.

## 4. Practical implementation

```csharp
public async IAsyncEnumerable<OrderExportRow> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    await foreach (var row in db.Orders
        .AsNoTracking()
        .OrderBy(x => x.Id)
        .Select(x => new OrderExportRow(x.Id, x.Number, x.Total))
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        yield return row;
    }
}
```

Consumer:

```csharp
await foreach (var row in service.StreamOrdersAsync(ct))
{
    await csvWriter.WriteAsync(row, ct);
}
```

Nếu output là HTTP streaming, cần hiểu serializer và reverse proxy có thực sự flush incremental hay vẫn buffer response.

## 5. Real production scenario

Một finance export trước đây query 800k transactions rồi tạo `List<TransactionDto>`. Pod memory tăng từ 300 MB lên hơn 2 GB và đôi lúc bị restart.

Chuyển sang streaming theo ordered query và viết CSV theo dòng làm working set ổn định hơn. Time-to-first-byte cũng giảm vì client bắt đầu nhận dữ liệu trước khi toàn bộ query hoàn tất.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint đã chuyển sang `IAsyncEnumerable<T>` nhưng memory vẫn tăng gần như trước.

**Evidence** → phía trước iterator vẫn có `ToListAsync()`, hoặc serializer/reverse proxy buffer toàn response.

**Hypothesis** → pipeline chỉ “streaming ở API surface”, nhưng một layer vẫn materialize toàn bộ dữ liệu.

**Diagnosis** → trace allocation, inspect SQL/data access path, response buffering và network flush behavior.

**Fix** → loại materialization không cần thiết, pagination/batching đúng chỗ, cấu hình response path phù hợp.

**Verification** → load test với dataset lớn; theo dõi working set, allocation rate và time-to-first-byte.

## 7. Common mistakes

- Trả `IAsyncEnumerable<T>` nhưng bên trong gọi `ToListAsync()`.
- Không propagate `CancellationToken` khi client disconnect.
- Giữ `DbContext`/reader quá lâu mà không hiểu connection usage.
- Chạy nhiều async iterators song song trên cùng `DbContext`.
- Dùng streaming cho dataset nhỏ rồi tăng complexity không cần thiết.
- Nghĩ streaming tự động giải quyết slow query.

## 8. Alternatives

- `List<T>`: đơn giản nhất khi dataset nhỏ và bounded.
- Pagination: tốt khi client cần random access/pages hơn là stream liên tục.
- Batch processing: tốt cho background jobs cần checkpoint/retry.
- Channel/Pipeline: phù hợp producer-consumer có concurrency và buffering chủ động.

## 9. Trade-offs

### Advantages

- Memory footprint thấp hơn cho dataset lớn.
- Time-to-first-item/byte tốt hơn.
- Natural pacing giữa producer và consumer.

### Costs / Risks

- Resource lifetime dài hơn.
- Error có thể xảy ra giữa stream sau khi response đã bắt đầu.
- Retry toàn operation khó hơn sau khi đã emit một phần output.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu streaming khác với load toàn bộ collection rồi mới xử lý.

### Middle

Biết implement async iterator, cancellation và tránh hidden materialization.

### Senior

Reasoning về connection lifetime, buffering, partial failure và backpressure toàn pipeline.

### Technical Lead / Architect

Quyết định endpoint/workload nào thực sự cần streaming, và contract xử lý partial failure/resume phải như thế nào.

## 11. Key takeaway

- `IAsyncEnumerable<T>` chỉ có giá trị khi toàn pipeline thực sự incremental.
- Streaming giảm memory nhưng kéo dài resource lifetime và làm retry phức tạp hơn.
- Đo working set và buffering behavior thay vì chỉ nhìn method signature.

# 2. ASP.NET Core Partitioned Rate Limiting: bảo vệ capacity theo user/API key/IP thay vì áp một global limit mù quáng

## 1. What is it?

Rate limiting giới hạn tốc độ request được phép đi qua một boundary. **Partitioned rate limiting** chia quota theo một key như authenticated user, tenant, API key hoặc client IP.

Mental model:

```text
User A -> quota A
User B -> quota B
Tenant X -> quota X
```

Thay vì một noisy client tiêu hết quota toàn hệ thống, mỗi partition có budget riêng.

## 2. Why does it exist?

API luôn có finite capacity: worker threads, DB connections, downstream quotas và CPU đều hữu hạn.

Không có rate limiting, một bug client retry loop hoặc crawler có thể tạo load đủ lớn để ảnh hưởng mọi user. Global limit bảo vệ tổng capacity nhưng có thể gây unfairness. Partitioning giúp isolation tốt hơn.

## 3. How does it work?

ASP.NET Core Rate Limiting middleware chọn limiter dựa trên partition key. Mỗi partition có state riêng theo algorithm như fixed window, sliding window, token bucket hoặc concurrency limiter.

```text
request
  -> resolve partition key
  -> limiter state for key
  -> permit? yes -> endpoint
             no  -> 429
```

Rate limit không thay thế authorization. Một client được authenticated vẫn có thể bị giới hạn.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("per-user", context =>
    {
        var key = context.User.Identity?.IsAuthenticated == true
            ? context.User.FindFirst("sub")?.Value ?? "unknown"
            : context.Connection.RemoteIpAddress?.ToString() ?? "anonymous";

        return RateLimitPartition.GetTokenBucketLimiter(
            key,
            _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 50,
                ReplenishmentPeriod = TimeSpan.FromSeconds(10),
                AutoReplenishment = true,
                QueueLimit = 0
            });
    });
});

app.UseRateLimiter();
app.MapGet("/api/search", SearchAsync)
   .RequireRateLimiting("per-user");
```

Production cần thêm `Retry-After`/error contract và telemetry cho rejected requests.

## 5. Real production scenario

Search API gọi Elasticsearch và downstream pricing API. Một partner có bug retry 20 lần/second cho mỗi failed request. Không partitioning, partner này làm connection pool và downstream quota cạn, user bình thường cũng timeout.

Per-partner limiter chặn blast radius trong khi tổng system limit vẫn bảo vệ capacity chung.

## 6. Failure scenario & troubleshooting

**Symptom** → hàng nghìn users bị 429 dù chỉ một tenant tạo load bất thường.

**Evidence** → limiter dùng global key cố định; rejected requests tập trung sau traffic spike của một tenant.

**Hypothesis** → partition strategy không phản ánh fairness boundary.

**Diagnosis** → group request rate/rejection theo tenant/user/API key và dependency load.

**Fix** → partition theo identity phù hợp, đồng thời giữ global protection nếu cần.

**Verification** → load test noisy-neighbor scenario; tenant xấu bị throttle nhưng healthy tenants vẫn đạt SLO.

## 7. Common mistakes

- Dùng raw IP cho mọi case dù nhiều users đi chung NAT/proxy.
- Tin `X-Forwarded-For` từ nguồn không trusted.
- Partition theo unbounded attacker-controlled string gây state explosion.
- Retry 429 ngay lập tức ở client.
- Rate limit sau khi expensive DB work đã xảy ra.
- Dùng rate limit để che capacity problem thay vì sửa bottleneck.

## 8. Alternatives

- API Gateway/Front Door rate limiting: chặn sớm ngoài application.
- Concurrency limiter: hữu ích khi mục tiêu là giới hạn simultaneous expensive work.
- Queue: phù hợp workload có thể trì hoãn thay vì reject.
- Downstream-specific bulkhead: bảo vệ dependency riêng.

## 9. Trade-offs

### Advantages

- Isolation giữa tenants/users.
- Bảo vệ downstream và application capacity.
- Có thể phản ánh commercial quota.

### Costs / Risks

- Chọn partition key sai gây unfairness.
- Distributed deployments có thể cần centralized gateway/state nếu quota phải globally exact.
- Too-strict policy làm giảm legitimate burst traffic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 429 nghĩa là capacity/quota policy từ chối request, không phải authentication failure.

### Middle

Biết cấu hình limiter, partition key và response contract.

### Senior

Thiết kế quota theo traffic shape, tenant isolation và downstream capacity.

### Technical Lead / Architect

Quyết định rate limit ở edge, app hay cả hai; quota nào là business policy và quota nào là reliability control.

## 11. Key takeaway

- Rate limiting hiệu quả phải gắn với đúng fairness boundary.
- Partitioned limiter giảm noisy-neighbor blast radius.
- Limit phải dựa capacity evidence, không phải con số ngẫu nhiên.

# 3. EF Core `AsSplitQuery` và cartesian explosion: khi một query lớn cần được tách để giảm duplicated rows mà vẫn kiểm soát consistency

## 1. What is it?

Khi `Include` nhiều collection navigations, một single SQL query có thể tạo cartesian-like multiplication của rows. EF Core vẫn materialize đúng object graph, nhưng database phải gửi rất nhiều duplicated column data.

`AsSplitQuery()` yêu cầu EF Core phát nhiều SQL queries thay vì một joined query lớn.

## 2. Why does it exist?

Giả sử một `Order` có 50 `Items` và 20 `Comments`. Join cả hai collections có thể tạo khoảng 1,000 result rows cho chỉ một order, dù domain object cuối cùng vẫn chỉ có 50 items + 20 comments.

```text
Order
 x 50 Items
 x 20 Comments
 = 1000 joined rows
```

Network payload, DB CPU và materialization cost có thể tăng mạnh.

## 3. How does it work?

Single query:

```text
SELECT Order + Items + Comments
JOIN ...
JOIN ...
```

Split query gần hơn:

```text
Query 1 -> Orders
Query 2 -> Items for selected Orders
Query 3 -> Comments for selected Orders
```

EF Core correlate results lại trong memory.

Trade-off chính: giảm row duplication nhưng tăng round trips và có thể quan sát dữ liệu ở các thời điểm khác nhau nếu concurrent update xảy ra giữa các queries.

## 4. Practical implementation

```csharp
var order = await db.Orders
    .Where(x => x.Id == orderId)
    .Include(x => x.Items)
    .Include(x => x.Comments)
    .AsSplitQuery()
    .AsNoTracking()
    .SingleAsync(ct);
```

Tuy nhiên với API read model, projection thường tốt hơn:

```csharp
var order = await db.Orders
    .Where(x => x.Id == orderId)
    .Select(x => new OrderDetailsDto(
        x.Id,
        x.Items.Select(i => new ItemDto(i.Id, i.Quantity)).ToList(),
        x.Comments.Select(c => new CommentDto(c.Id, c.Text)).ToList()))
    .SingleAsync(ct);
```

Không dùng `AsSplitQuery` như reflex cho mọi `Include`.

## 5. Real production scenario

Admin order-details page thêm shipments, items, payments và audit notes bằng nhiều `Include`. Sau release, SQL duration chỉ tăng vừa phải nhưng response payload DB → app tăng hàng chục lần và API p95 tăng mạnh.

Execution plan/result row count cho thấy data duplication. Projection hoặc split query giảm transferred rows đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → query “chỉ lấy một order” nhưng trả hàng chục nghìn SQL rows.

**Evidence** → multiple sibling collection includes; actual row count lớn hơn domain cardinality rất nhiều.

**Hypothesis** → cartesian explosion.

**Diagnosis** → bật command logging hợp lý, inspect generated SQL, actual execution plan và row count.

**Fix** → projection, split query hoặc tách UI/read model boundary.

**Verification** → so sánh bytes/rows, DB duration, application allocation và p95.

## 7. Common mistakes

- `Include` mọi navigation vì “đỡ query sau”.
- Dùng split query nhưng bỏ qua multiple round trips.
- Không nghĩ tới consistency giữa split statements.
- Load entity graph chỉ để trả DTO nhỏ.
- Giải quyết N+1 bằng một mega-join rồi tạo vấn đề ngược lại.

## 8. Alternatives

- Projection: thường tốt nhất cho read-only API contract.
- Explicit loading: phù hợp workflow có điều kiện rõ.
- Separate queries thủ công: khi cần kiểm soát batching/caching riêng.
- Single query: vẫn tốt khi graph nhỏ và row multiplication thấp.

## 9. Trade-offs

### Advantages

- Split query giảm duplicated rows từ sibling collections.
- Có thể giảm network/memory cost đáng kể.

### Costs / Risks

- Nhiều round trips.
- Snapshot consistency có thể khác single statement.
- Không thay thế query modeling tốt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` ảnh hưởng SQL shape chứ không chỉ object graph.

### Middle

Biết inspect generated SQL và thử projection/split query.

### Senior

Đánh đổi round trip, consistency, row multiplication và allocation bằng measurement.

### Technical Lead / Architect

Đặt read-model conventions để API không mặc định load aggregate graph khổng lồ bằng ORM.

## 11. Key takeaway

- Một object graph nhỏ có thể sinh result set SQL rất lớn.
- `AsSplitQuery` là một trade-off, không phải universal fix.
- Projection thường là boundary rõ nhất cho read API.

# 4. SQL Server deadlock: đọc deadlock graph, lock order và transaction scope thay vì chỉ retry rồi bỏ qua root cause

## 1. What is it?

Deadlock xảy ra khi hai hoặc nhiều transactions giữ resources mà transaction khác cần, tạo vòng chờ không thể tự giải phóng.

```text
Tx A holds Row 1 -> waits Row 2
Tx B holds Row 2 -> waits Row 1
```

SQL Server phát hiện cycle và chọn một victim để rollback, thường trả error 1205.

## 2. Why does it exist?

Locking bảo vệ isolation/correctness. Deadlock là hệ quả có thể xảy ra khi nhiều transactions acquire locks theo thứ tự khác nhau hoặc giữ lock quá lâu.

Không thể kết luận “database bị lỗi”; thường transaction/access pattern của application tạo điều kiện cho cycle.

## 3. How does it work?

SQL Server deadlock monitor phát hiện wait-for graph có cycle. Một transaction bị chọn victim dựa trên deadlock priority/cost.

Deadlock khác blocking:

```text
Blocking: A giữ lock, B chờ, A cuối cùng commit -> B tiếp tục
Deadlock: A chờ B và B chờ A -> không ai tự tiến được
```

## 4. Practical implementation

Một cách giảm risk là giữ consistent lock order:

```csharp
var orderedIds = accountIds.OrderBy(x => x).ToArray();

await using var tx = await db.Database.BeginTransactionAsync(ct);

foreach (var id in orderedIds)
{
    var account = await db.Accounts.SingleAsync(x => x.Id == id, ct);
    account.Recalculate();
}

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Đây chỉ minh họa nguyên tắc; query/locking strategy thực tế phải dựa workload và plan.

## 5. Real production scenario

Transfer workflow A cập nhật AccountFrom rồi AccountTo. Một workflow khác đôi lúc đi theo thứ tự ngược. Khi hai transfers chéo account chạy đồng thời, deadlock xuất hiện vài lần mỗi giờ.

Retry giúp request đôi khi thành công nhưng không giải thích tại sao pattern tồn tại.

## 6. Failure scenario & troubleshooting

**Symptom** → sporadic SQL error 1205 dưới concurrency; local không reproduce.

**Evidence** → Extended Events deadlock graph chỉ ra objects, statements, lock modes và victim.

**Hypothesis** → inconsistent access order hoặc transaction giữ locks quá lâu.

**Diagnosis** → đọc deadlock graph, map statements về application flow, xem indexes và transaction scope.

**Fix** → consistent ordering, index tốt hơn để giảm locked rows, transaction ngắn hơn; retry chỉ cho residual transient deadlock.

**Verification** → concurrency/load test và production deadlock event rate giảm.

## 7. Common mistakes

- Chỉ thêm Polly retry rồi đóng incident.
- Nhầm blocking dài với deadlock.
- Mở transaction trước khi gọi external API.
- Query thiếu index làm lock nhiều rows hơn cần thiết.
- Thêm `NOLOCK` để “fix deadlock” rồi chấp nhận dirty/inconsistent reads không chủ đích.

## 8. Alternatives

- Optimistic concurrency cho lost-update scenarios khác locking conflict.
- Snapshot-based isolation có thể giảm read/write blocking trong một số workload nhưng có semantics/cost riêng.
- Queue/serialization theo business key khi concurrent mutation không có giá trị.

## 9. Trade-offs

### Advantages

- Locking giữ consistency mạnh.
- Deadlock detection giúp hệ thống thoát cycle thay vì treo vĩnh viễn.

### Costs / Risks

- Concurrency pattern phức tạp có thể tạo deadlock hiếm khó reproduce.
- Retry tăng work nếu root cause vẫn tồn tại.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt blocking và deadlock.

### Middle

Biết lấy deadlock graph và nhận diện statements/resources.

### Senior

Reasoning về lock order, index, isolation và transaction duration.

### Technical Lead / Architect

Thiết kế mutation boundary và concurrency model sao cho contention được kiểm soát thay vì xử lý từng deadlock như lỗi ngẫu nhiên.

## 11. Key takeaway

- Deadlock là cycle của resource waits; retry chỉ là safety net.
- Deadlock graph là evidence chính, không đoán bằng CPU/log message chung chung.
- Consistent access order và transaction ngắn thường quan trọng hơn “magic hint”.

# 5. MongoDB schema evolution: versioning document và lazy/eager migration mà không dừng cả hệ thống để sửa dữ liệu lịch sử

## 1. What is it?

MongoDB không ép mọi documents trong collection phải có schema vật lý giống nhau. Điều này linh hoạt, nhưng application vẫn có **logical schema** và nó thay đổi theo thời gian.

Schema evolution là strategy để code mới đọc/ghi được dữ liệu qua nhiều versions trong quá trình migration.

## 2. Why does it exist?

Production collection có thể chứa hàng trăm triệu documents. Thay đổi field từ:

```json
{"name":"Ha"}
```

sang:

```json
{"profile":{"displayName":"Ha"}}
```

không có nghĩa ta có thể rewrite toàn bộ collection tức thời trước khi deploy code mới.

Cần compatibility window giữa old data, new code và đôi khi old code trong rollback.

## 3. How does it work?

Một approach là document version:

```json
{
  "_id": "...",
  "schemaVersion": 2,
  "profile": { "displayName": "Ha" }
}
```

Reader có thể normalize old versions thành current domain model:

```text
v1 document -> upgrader -> current model
v2 document -> current model
```

Migration có thể eager (batch rewrite trước/sau deploy) hoặc lazy (upgrade khi read/write).

## 4. Practical implementation

```csharp
public Customer ReadCustomer(BsonDocument doc)
{
    var version = doc.GetValue("schemaVersion", 1).AsInt32;

    return version switch
    {
        1 => new Customer(
            doc["name"].AsString,
            email: doc.GetValue("email", "").AsString),

        2 => new Customer(
            doc["profile"]["displayName"].AsString,
            doc["contact"]["email"].AsString),

        _ => throw new NotSupportedException($"Unsupported schema {version}")
    };
}
```

Writer chỉ nên emit current version. Batch migration cần idempotent update và checkpoint.

## 5. Real production scenario

CRM đổi `address` từ free-text sang structured object. Rewrite 80 million documents trong maintenance window là rủi ro lớn.

Team deploy reader hỗ trợ v1+v2, writer chỉ tạo v2, sau đó background migration chuyển dần v1. Khi tỷ lệ v1 về 0 và rollback window kết thúc, code compatibility v1 mới được xóa.

## 6. Failure scenario & troubleshooting

**Symptom** → deploy mới lỗi deserialize chỉ với một số old accounts.

**Evidence** → documents có field shape/version khác nhau; test fixtures chỉ dùng schema mới.

**Hypothesis** → reader không backward-compatible trong migration window.

**Verification** → contract tests trên representative v1/v2 documents và migration dry run.

## 7. Common mistakes

- Nghĩ “schemaless” nghĩa là không cần schema governance.
- Rename field và deploy writer trước khi reader hiểu cả hai versions.
- Batch update toàn collection không throttle/checkpoint.
- Lazy migration có side effect trên read path mà không kiểm soát latency.
- Không có telemetry biết còn bao nhiêu old documents.

- Lazy migration: giảm one-time blast nhưng kéo dài compatibility complexity.
- Dual-read/dual-write tạm thời: hữu ích cho migration phức tạp nhưng dễ tăng bug.
- Collection mới: phù hợp thay đổi lớn cần reindex/rebuild rồi switch traffic.

## 9. Trade-offs

### Advantages

- Cho phép zero/low-downtime schema change.
- Rollout và rollback an toàn hơn.

### Costs / Risks

- Migration kéo dài tạo operational debt.

# 6. Azure Service Bus Sessions: giữ ordered processing theo business key mà không biến toàn queue thành single-threaded bottleneck

## 1. What is it?

Service Bus Sessions nhóm messages có cùng `SessionId` và cho phép một receiver xử lý session đó độc quyền trong một khoảng thời gian.

Mental model:

```text
Order A: A1 -> A2 -> A3  (SessionId=A)
Order B: B1 -> B2 -> B3  (SessionId=B)

A and B can process in parallel
within A, processing order is controlled
```

## 2. Why does it exist?

Một global FIFO consumer bảo toàn order nhưng hy sinh throughput toàn queue. Nhiều business flows chỉ cần ordering **theo aggregate/business key**, ví dụ events của cùng order, customer hoặc workflow instance.

Sessions cho phép parallelism giữa keys nhưng serialization trong cùng key.

## 3. How does it work?

Sender gán `SessionId`. Session-enabled queue/subscription giữ session-aware semantics. Processor accept sessions và lock một session để xử lý messages của session đó.

Session state còn có thể lưu một lượng nhỏ workflow state, nhưng không nên biến broker thành primary business database.

## 4. Practical implementation

Sender:

```csharp
var message = new ServiceBusMessage(payload)
{
    MessageId = eventId.ToString(),
    SessionId = orderId.ToString()
};

await sender.SendMessageAsync(message, ct);
```

Receiver:

```csharp
var processor = client.CreateSessionProcessor(
    queueName,
    new ServiceBusSessionProcessorOptions
    {
        MaxConcurrentSessions = 16,
        MaxConcurrentCallsPerSession = 1,
        AutoCompleteMessages = false
    });
```

Consumer vẫn phải idempotent; session ordering không loại duplicate delivery.

## 5. Real production scenario

Order workflow nhận `OrderCreated`, `PaymentConfirmed`, `OrderCancelled`. Nếu events của cùng order chạy concurrent/out-of-order, state transition có thể sai. SessionId = OrderId cho phép mỗi order tuần tự, trong khi hàng nghìn orders khác vẫn xử lý song song.

## 6. Failure scenario & troubleshooting

**Symptom** → queue tổng thể có capacity nhưng backlog của một vài sessions tăng rất cao.

**Evidence** → một `SessionId` chiếm nhiều messages hoặc handler của session đó chậm.

**Hypothesis** → hot session tạo head-of-line blocking theo business key.

**Diagnosis** → metric backlog/processing duration theo session key class, inspect handler dependencies.

**Fix** → giảm work trong critical session, tách aggregate key nếu business semantics cho phép, hoặc move expensive side effect sang downstream asynchronous step.

**Verification** → hot-session age giảm mà ordering invariant vẫn giữ.

## 7. Common mistakes

- Dùng một SessionId cho toàn queue.
- Nghĩ sessions đảm bảo exactly-once.
- Handler giữ session lock trong external call rất lâu.
- Không thiết kế duplicate detection/idempotency.
- Dùng session state như database lâu dài.

## 8. Alternatives

- Partitioning theo key với broker khác.
- Optimistic state transition trong database không cần strict broker order.
- Saga/workflow engine cho process phức tạp.
- Single consumer: đơn giản nhưng throughput thấp nếu global ordering thật sự bắt buộc.

## 9. Trade-offs

### Advantages

- Ordered processing theo business key.
- Parallelism giữa sessions.
- Mapping tốt với aggregate/workflow instance.

### Costs / Risks

- Hot key tạo bottleneck.
- Session lock/lifecycle tăng operational complexity.
- Ordering không thay idempotency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ordering thường cần theo key chứ không nhất thiết toàn queue.

### Middle

Biết set `SessionId` và cấu hình session processor.

### Senior

Reasoning về hot sessions, duplicate, lock duration và failure recovery.

### Technical Lead / Architect

Quyết định business invariant nào thực sự cần ordered processing và partition key nào cho throughput tốt nhất.

## 11. Key takeaway

- Sessions cho ordering theo business key, không phải global FIFO miễn phí.
- Hot session vẫn có thể trở thành bottleneck.
- Ordered delivery và idempotent processing là hai concern khác nhau.

# 7. Azure Key Vault + Managed Identity: loại secret khỏi source/config nhưng vẫn phải thiết kế rotation, cache và failure behavior

## 1. What is it?

Azure Key Vault lưu secrets, keys và certificates ngoài application deployment artifact. Managed Identity cho workload lấy Azure AD token mà không cần nhúng client secret để authenticate tới Key Vault.

```text
App Service / VM / Function
  -> Managed Identity token
  -> Key Vault authorization
  -> secret/key access
```

## 2. Why does it exist?

Secret trong `appsettings.json`, environment pipeline variable hoặc source code dễ bị copy, log hoặc tồn tại lâu ngoài kiểm soát.

Central secret store cung cấp access policy, audit, rotation và lifecycle tách khỏi source deployment.

Nhưng “đưa vào Key Vault” không tự động giải quyết cách application xử lý secret thay đổi hoặc Key Vault outage.

## 3. How does it work?

Managed Identity được platform cấp identity. Azure SDK dùng credential chain để lấy token cho Key Vault. Vault kiểm tra RBAC/access policy rồi trả secret version phù hợp.

Có hai common models:

```text
startup/config provider -> load secret -> app uses cached value
runtime client           -> request secret when needed
```

Gọi Key Vault cho mỗi business request thường không phải thiết kế tốt.

## 4. Practical implementation

```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri(builder.Configuration["KeyVaultUri"]!),
    credential);

var secret = await client.GetSecretAsync("PaymentsApiKey", cancellationToken: ct);
```

Trong production, identity chỉ nên có quyền cần thiết. Nếu secret cần rotation không restart, cần cache với refresh policy và behavior khi refresh fail.

## 5. Real production scenario

Nếu application chỉ đọc một lần lúc startup, rotation có thể yêu cầu restart/deploy; điều đó không sai nếu được thiết kế rõ.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment mới startup fail với 403 Key Vault nhưng local chạy bình thường.

**Evidence** → managed identity principal khác local developer identity; RBAC chưa assign hoặc private endpoint/DNS chặn network path.

**Hypothesis** → identity/network boundary, không phải secret “không tồn tại”.

**Diagnosis** → kiểm tra principal ID, RBAC scope, Key Vault audit logs, DNS/private endpoint và SDK credential used.

**Fix** → cấp least-privilege role đúng identity, sửa network path/DNS, fail-fast với error rõ.

**Verification** → test từ production-like environment bằng chính managed identity.

## 7. Common mistakes

- Dùng Key Vault nhưng vẫn giữ fallback secret trong source.
- Cho app quyền quản trị vault rộng hơn read cần thiết.
- Fetch secret trên từng request.
- Không có rotation runbook.
- Log secret value khi debug config.
- Assume managed identity local và production giống nhau.

## 8. Alternatives

- Environment variables: đơn giản hơn nhưng lifecycle/audit yếu hơn.
- Kubernetes Secrets + external secret operator: phù hợp cluster architecture.
- Managed service identity không cần secret: tốt nhất khi downstream hỗ trợ Entra ID trực tiếp.

## 9. Trade-offs

### Advantages

- Secret tách khỏi code/artifact.
- Central audit và rotation.
- Managed Identity loại credential bootstrap secret.

### Costs / Risks

- Thêm network/identity dependency.
- Rotation/cache semantics cần thiết kế.
- Startup có thể phụ thuộc vault availability nếu không có strategy phù hợp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

### Middle

### Senior

Thiết kế caching, rotation, startup failure và private networking.

## 11. Key takeaway

# 8. Kubernetes requests/limits: CPU throttling, `OOMKilled` và scheduling pressure có thể làm pod chậm dù application code không đổi

## 1. What is it?

Kubernetes `requests` mô tả resource scheduler dùng để đặt pod; `limits` đặt upper boundary cho CPU/memory theo runtime/cgroup behavior.

```text
requests -> placement/capacity planning
limits   -> runtime ceiling
```

CPU và memory khi vượt limit có behavior khác nhau: CPU thường bị throttled; memory có thể dẫn tới OOM kill.

## 2. Why does it exist?

Không có resource governance, một noisy pod có thể chiếm node capacity và làm các workloads khác unstable. Requests giúp scheduler tránh overcommit vô thức; limits tạo isolation nhất định.

Nhưng cấu hình quá thấp cũng tự tạo incident.

## 3. How does it work?

Ví dụ:

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
```

Nếu process muốn hơn 500m CPU liên tục, cgroup có thể throttle. Nếu memory vượt 512Mi, container có thể bị killed và pod restart.

Scheduler nhìn requests để quyết định node placement, không dựa peak usage thực tế.

## 4. Practical implementation

Với .NET API, bắt đầu từ load test/production telemetry thay vì copy numbers:

```text
measure CPU p50/p95 under expected concurrency
measure working set + GC peaks
add headroom for burst/startup
set request to realistic steady need
set limit only khi isolation policy thực sự yêu cầu
```

Theo dõi container CPU throttling, restart reason, working set, GC heap và request latency cùng nhau.

## 5. Real production scenario

API version mới thêm JSON processing nặng. CPU limit vẫn 300m như cũ. Pod không crash, CPU dashboard “không vượt limit”, nhưng p99 tăng gấp 3 vì process bị throttled.

Team ban đầu điều tra SQL vì CPU metric nhìn thấp; cgroup throttling metric mới chỉ ra root cause.

## 6. Failure scenario & troubleshooting

**Symptom** → pod restart với exit reason `OOMKilled` hoặc latency tăng nhưng CPU không đạt 100% node.

**Evidence** → container memory gần limit, restart reason 137; hoặc throttled CPU seconds tăng.

**Hypothesis** → resource limit chứ không phải code exception trực tiếp.

**Diagnosis** → correlate pod metrics, GC/runtime metrics, request traces và deployment change.

**Fix** → tune requests/limits theo measured workload, sửa allocation leak/hot path nếu thực sự tồn tại, scale replicas khi phù hợp.

**Verification** → load test và observe throttling/OOM/restart/p95 after change.

## 7. Common mistakes

- Copy resource values từ service khác.
- Set memory limit quá sát average working set.
- Chỉ tăng limit mà không điều tra memory leak.
- HPA dựa CPU nhưng requests không phản ánh reality.
- Nhầm CPU throttling với downstream latency.
- Không reserve capacity cho startup spike.

## 8. Alternatives

- Vertical Pod Autoscaler recommendation để hỗ trợ sizing.
- HPA scale-out khi workload parallelizable.
- Node sizing thay đổi nếu workloads không fit.
- Không đặt CPU limit trong một số controlled environments, nhưng vẫn cần requests/governance.

## 9. Trade-offs

### Advantages

- Scheduler có capacity signal.
- Resource isolation giữa workloads.
- Hỗ trợ predictable multi-tenant cluster operation.

### Costs / Risks

- Limits sai tạo throttling/OOM do chính platform policy.
- Requests cao quá làm cluster underutilized.
- Requests thấp quá làm node overpacked.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt request và limit.

### Middle

Biết đọc `OOMKilled`, restart count và basic resource metrics.

### Senior

Correlate cgroup behavior với .NET GC/CPU/latency và autoscaling.

### Technical Lead / Architect

Định nghĩa resource sizing policy dựa SLO/cost/capacity, không dựa template cố định.

## 11. Key takeaway

- CPU limit có thể làm app chậm mà không crash; memory limit có thể kill container.
- Requests ảnh hưởng scheduling và autoscaling assumptions.
- Resource values phải đến từ workload measurement.

# 9. JWT signing-key rotation và JWKS caching: token có thể hợp lệ nhưng production vẫn 401 nếu verifier quản lý key lifecycle sai

## 1. What is it?

JWT thường được ký bằng private key của Identity Provider. API verify signature bằng public key, thường lấy qua JWKS endpoint.

Key rotation là quá trình IdP chuyển sang signing key mới trong khi token ký bằng key cũ có thể vẫn chưa hết hạn.

```text
JWT header: kid=key-B
API -> JWKS cache -> find key-B -> verify signature
```

## 2. Why does it exist?

Signing key không nên tồn tại mãi. Rotation giảm blast radius và hỗ trợ security lifecycle. Nhưng distributed caches và token lifetime tạo một compatibility window giữa old/new keys.

Nếu API pin một public key vĩnh viễn, rotation có thể làm mọi request mới 401 ngay lập tức.

## 3. How does it work?

JWT header thường có `kid`. Verifier tìm matching key trong cached JWKS. Khi gặp unknown `kid`, middleware/library có thể refresh metadata/JWKS theo policy.

Trong rotation an toàn:

```text
publish new public key
keep old key available
start signing with new key
wait old-token lifetime/overlap
retire old key
```

## 4. Practical implementation

ASP.NET Core thường dùng authority metadata thay vì tự download JWKS:

```csharp
builder.Services
    .AddAuthentication("Bearer")
    .AddJwtBearer("Bearer", options =>
    {
        options.Authority = config["Auth:Authority"];
        options.Audience = "orders-api";
        options.RequireHttpsMetadata = true;
    });
```

Để library xử lý metadata refresh đúng chuẩn thường an toàn hơn custom static key cache. Nếu dùng custom validation, cần refresh/backoff/cache strategy rõ.

## 5. Real production scenario

IdP rotate key lúc 02:00. Một subset API instances đã cache JWKS cũ và chưa refresh. Token cũ vẫn pass, token mới có `kid` mới bị 401 trên một số instances, tạo lỗi intermittent sau load balancer.

## 6. Failure scenario & troubleshooting

**Symptom** → 401 tăng đột ngột nhưng chỉ với tokens mới; restart instance đôi khi “fix”.

**Evidence** → token `kid` không có trong cached JWKS; IdP JWKS endpoint đã publish key mới.

**Hypothesis** → stale metadata/JWKS cache hoặc refresh failure.

**Diagnosis** → compare token kid, cached keys, IdP current keys, metadata refresh logs và outbound network/DNS.

**Fix** → dùng supported metadata manager/refresh behavior, đảm bảo overlap window và network access tới authority.

**Verification** → controlled key rotation test; old + new tokens pass trong overlap, old key fail sau retirement đúng thời điểm.

## 7. Common mistakes

- Hard-code one signing certificate/key forever.
- Refresh JWKS trên mọi request.
- Khi unknown `kid` thì disable signature validation để “khắc phục”.
- Retire old key trước khi old tokens hết hạn.
- Chỉ log “401” mà không capture safe validation reason/kid metadata.
- Confuse signature validation với authorization.

## 8. Alternatives

- Symmetric shared secret: đơn giản nhưng distribution/rotation khó hơn giữa nhiều services.
- Introspection/reference token: central validation nhưng thêm network dependency.
- Short-lived access token + managed IdP rotation vẫn là common default cho APIs.

## 9. Trade-offs

### Advantages

- Asymmetric keys cho phép verifier không giữ private signing secret.
- Rotation giảm long-lived credential risk.

### Costs / Risks

- Cache/refresh/network path trở thành auth availability dependency.
- Rotation overlap cần operational coordination.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu JWT signature được verify bằng key tương ứng với `kid`.

### Middle

Biết cấu hình Authority/Audience và đọc validation logs.

### Senior

Debug rotation/cache/clock/network issues và phân biệt authn/authz failure.

### Technical Lead / Architect

Đặt token lifetime, key rotation/overlap, metadata availability và incident runbook cho toàn platform.

## 11. Key takeaway

- Key rotation là normal lifecycle, không phải exceptional event.
- JWKS caching phải vừa tránh request-per-token vừa refresh kịp key mới.
- Test rotation trước production thay vì chỉ test static happy path.

```text
User request
  -> model interprets intent
  -> structured tool call
  -> deterministic validation/policy
  -> application executes tool
  -> result returned to model/user
```

Model không nên trực tiếp sở hữu quyền thực thi business side effect chỉ vì output có JSON hợp lệ.

## 2. Why does it exist?

Parsing natural-language response bằng regex/string manipulation rất fragile. Structured schema làm integration contract rõ hơn.

Nhưng schema correctness chỉ nói output có đúng shape; nó không chứng minh action hợp lệ về authorization, business invariant, amount, target resource hoặc security policy.

```text
Is user authorized?
Does order exist?
Is refund amount <= refundable amount?
Has this idempotency key already executed?
Does action require human approval?
```

Only then execute external payment API.

```csharp
public async Task<RefundResult> ExecuteRefundAsync(

        throw new ForbiddenException();

        ?? throw new NotFoundException();

        order.PaymentId,
        args.Amount,
        idempotencyKey: args.RequestId,
        ct);
}
```

Model supplies intent/arguments; code owns validation and side effects.

## 6. Failure scenario & troubleshooting

**Symptom** → model generates valid JSON but attempts refund for unauthorized order or repeats tool after timeout.

**Evidence** → schema validation passes; business authorization/idempotency missing.

**Hypothesis** → team confused syntactic structure with semantic safety.

**Fix** → deterministic validation, least-privilege tool surface, idempotency, approval gates and audit log.

**Verification** → adversarial tests: prompt injection, wrong tenant ID, excessive amount, duplicate call, timeout-after-success.

- Cho model arbitrary SQL/HTTP executor thay vì narrow tools.
- Coi schema-valid output là authorized output.
- Đặt business rule chỉ trong prompt.
- Retry tool call mà không có idempotency.
- Gửi secrets/PII vào model context không cần thiết.
- Không log tool decision/result đủ để audit.

- Intent classification + conventional code: đơn giản hơn agent loop cho workflow nhỏ.
- Human approval: cần cho high-impact/irreversible actions.

### Advantages
