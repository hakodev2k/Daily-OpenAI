# 1. C# `Span<T>` / `Memory<T>` và allocation-aware programming: tối ưu hot path mà không biến toàn bộ codebase thành unsafe-style code

## 1. What is it?

`Span<T>` là một view liên tục trên vùng memory, có thể trỏ tới array, stack memory hoặc một slice của buffer mà không cần copy. `Memory<T>` giải quyết bài toán tương tự nhưng có thể tồn tại qua async boundary và được lưu trong object heap.

Mental model:

```text
buffer: [A][B][C][D][E][F]
            ^--------^
             Span<T>
```

Slice tạo một view mới, không tạo một array mới chứa dữ liệu đã copy.

## 2. Why does it exist?

Code xử lý text, protocol, serialization hoặc parsing thường tạo nhiều temporary objects:

```csharp
var parts = input.Split(':');
var prefix = parts[0].Substring(0, 3);
```

Ở low traffic, allocations này không đáng kể. Ở hot path chạy hàng triệu lần, temporary allocations làm Gen0 GC xảy ra thường xuyên, tăng CPU và tail latency.

`Span<T>` cho phép xử lý trực tiếp trên buffer hiện có.

## 3. How does it work?

`Span<T>` là `ref struct`, nên compiler ngăn nó escape sang heap. Vì vậy nó không thể là field của class, không thể box, và không thể sống qua `await`.

```text
stack frame
  |
  +--> Span<char> ----> existing buffer

await boundary
  X  Span cannot survive here
```

`Memory<T>` thì có thể sống trên heap và có `.Span` để truy cập synchronously khi cần.

## 4. Practical implementation

Ví dụ parse key/value mà không tạo substring:

```csharp
static bool TryParseHeader(ReadOnlySpan<char> input,
    out ReadOnlySpan<char> key,
    out ReadOnlySpan<char> value)
{
    var separator = input.IndexOf(':');
    if (separator <= 0)
    {
        key = default;
        value = default;
        return false;
    }

    key = input[..separator].Trim();
    value = input[(separator + 1)..].Trim();
    return true;
}
```

Với async I/O, nhận `ReadOnlyMemory<byte>` từ buffer owner, sau đó chỉ lấy `.Span` trong synchronous region.

## 5. Real production scenario

Một ingestion API đọc hàng trăm nghìn telemetry messages mỗi phút. Parser cũ gọi `Substring`, `Split` và `ToArray` nhiều lần trên mỗi message. Allocation rate tăng mạnh, GC time chiếm tỷ lệ đáng kể dù business logic rất đơn giản.

Thay hot parser bằng `ReadOnlySpan<char>` giảm allocation mà không thay toàn bộ application architecture.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU tăng, p99 tăng khi throughput cao dù database và downstream ổn.

**Evidence** → profiler cho thấy nhiều allocations từ `Substring`, `Split`, temporary arrays; GC collections tăng.

**Hypothesis** → hot path đang allocation-bound.

**Diagnosis** → đo bằng `dotnet-counters`, allocation profiler hoặc BenchmarkDotNet trên parser cô lập.

**Fix** → tối ưu đúng hot path bằng span/slicing, tránh copy không cần thiết.

**Verification** → allocation/request giảm và load test cho thấy throughput/p99 cải thiện.

## 7. Common mistakes

- Dùng `Span<T>` khắp nơi trước khi đo.
- Cố giữ span qua `await` thay vì chuyển boundary sang `Memory<T>`.
- Tối ưu allocation trong code chạy vài lần mỗi phút.
- Viết unsafe code dù API span an toàn đã đủ.
- Benchmark micro-operation nhưng bỏ qua cost database/network lớn hơn nhiều.

## 8. Alternatives

- String/array API thông thường: rõ ràng nhất và thường là default tốt.
- `ArrayPool<T>`: hữu ích khi cần buffer lớn tái sử dụng.
- `Memory<T>`: dùng khi buffer phải đi qua async/lifetime dài hơn stack frame.

## 9. Trade-offs

### Advantages

- Giảm copy và allocation.
- Hữu ích cho parsers, serializers, protocol handlers.
- Giữ type safety tốt hơn raw pointer.

### Costs / Risks

- Code khó đọc hơn.
- Lifetime rules phức tạp hơn.
- Dễ premature optimization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slice là view trên buffer chứ không phải bản copy.

### Middle

Biết dùng `Span<T>`/`Memory<T>` đúng async boundary và benchmark trước/sau.

### Senior

Phân biệt allocation bottleneck với I/O bottleneck, chọn đúng hot path để tối ưu.

### Technical Lead / Architect

Quyết định nơi performance complexity được phép tồn tại và đặt benchmark/regression guard thay vì lan low-level optimization toàn codebase.

## 11. Key takeaway

- `Span<T>` hữu ích khi copy/allocation thật sự là bottleneck.
- `Memory<T>` phù hợp hơn khi lifetime đi qua async boundary.
- Đo trước, tối ưu hot path, rồi đo lại.

# 2. ASP.NET Core Output Caching: giảm repeated work nhưng vẫn giữ đúng semantics theo route, query, header và invalidation

## 1. What is it?

Output Caching lưu toàn bộ HTTP response đã render để request tương đương sau đó có thể nhận response mà không chạy lại endpoint, database query và serialization.

Mental model:

```text
Request
  -> cache key lookup
      -> hit  -> cached HTTP response
      -> miss -> endpoint -> DB -> serialize -> cache -> response
```

Nó khác data cache ở chỗ cache nằm gần HTTP boundary và chứa response đã hoàn thành.

## 2. Why does it exist?

Một endpoint catalog public có thể nhận hàng nghìn request giống nhau trong vài giây. Nếu mỗi request đều query DB và serialize cùng payload, hệ thống lãng phí CPU, DB connections và I/O.

Output cache phù hợp khi nhiều request có thể chia sẻ cùng representation trong một freshness window chấp nhận được.

## 3. How does it work?

Cache key thường phải phản ánh những input làm response thay đổi: route, query, header hoặc policy tùy chỉnh.

```text
/products?page=1&culture=vi
/products?page=1&culture=en
```

Hai request này không được map vào cùng entry nếu response khác theo culture.

Invalidation có thể dựa vào TTL hoặc tag để xóa một nhóm entry khi dữ liệu thay đổi.

## 4. Practical implementation

```csharp
builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("catalog", policy =>
        policy.Expire(TimeSpan.FromSeconds(30))
              .SetVaryByQuery("page", "category")
              .Tag("catalog"));
});

var app = builder.Build();
app.UseOutputCache();

app.MapGet("/products", async (AppDbContext db, int page, CancellationToken ct) =>
{
    return await db.Products
        .OrderBy(x => x.Id)
        .Skip((page - 1) * 20)
        .Take(20)
        .Select(x => new { x.Id, x.Name, x.Price })
        .ToListAsync(ct);
}).CacheOutput("catalog");
```

Khi catalog thay đổi, application có thể evict theo tag thay vì đợi TTL nếu freshness requirement yêu cầu.

## 5. Real production scenario

Một marketing/catalog API bị traffic spike sau campaign. DB CPU tăng vì 90% request đọc cùng top products. Output caching 15–30 giây giảm repeated DB work mạnh mà business vẫn chấp nhận freshness đó.

## 6. Failure scenario & troubleshooting

**Symptom** → user A thấy dữ liệu của user B hoặc response sai culture/query.

**Evidence** → cache hit cao nhưng cache key không vary theo identity/header/query ảnh hưởng output.

**Hypothesis** → cache key policy không phản ánh response semantics.

**Diagnosis** → map toàn bộ input ảnh hưởng response và inspect cache policy.

**Fix** → không cache personalized endpoint hoặc thêm variation đúng; thêm invalidation/tag khi cần.

**Verification** → integration tests với nhiều users, query và culture xác nhận không cross-contaminate response.

## 7. Common mistakes

- Cache endpoint personalized mà không hiểu authorization boundary.
- Dùng TTL dài để “tối ưu” rồi gây stale content.
- Quên vary theo query/header ảnh hưởng representation.
- Cache lỗi 500 hoặc transient response không chủ đích.
- Chồng CDN + output cache + Redis nhưng không định nghĩa ownership/invalidation.

## 8. Alternatives

- `IMemoryCache`: cache data/object trong một instance.
- Redis: shared data cache giữa nhiều instances.
- CDN: cache gần client/edge, đặc biệt static/public content.
- Không cache: đúng khi data phải strongly fresh hoặc hit rate thấp.

## 9. Trade-offs

### Advantages

- Giảm latency, DB load và serialization CPU.
- Dễ áp dụng cho read-heavy public endpoints.

### Costs / Risks

- Staleness và invalidation complexity.
- Cache key sai có thể trở thành correctness/security bug.
- Multi-layer caching làm troubleshooting khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache hit bỏ qua repeated endpoint work.

### Middle

Biết thiết kế TTL, vary rules và test cache behavior.

### Senior

Reasoning về freshness, privacy, invalidation và interaction với CDN/Redis.

### Technical Lead / Architect

Quyết định cache layer nào sở hữu responsibility và freshness contract nào business chấp nhận.

## 11. Key takeaway

- Output cache là HTTP-response cache, không chỉ “cache cho nhanh”.
- Cache key phải phản ánh mọi input làm response thay đổi.
- Freshness và invalidation là correctness requirement.

# 3. EF Core transaction boundaries và savepoints: giữ business operation atomic mà không kéo transaction dài qua network calls

## 1. What is it?

Transaction boundary xác định tập database changes phải commit hoặc rollback như một đơn vị atomic. EF Core mặc định bọc một `SaveChanges` trong transaction khi provider hỗ trợ.

Savepoint là mốc bên trong transaction cho phép rollback một phần về trạng thái trước đó mà không hủy toàn transaction.

## 2. Why does it exist?

Business operation thường cập nhật nhiều rows/tables. Nếu update order thành công nhưng inventory update fail mà transaction boundary sai, hệ thống rơi vào partial state.

Ngược lại, transaction kéo dài qua HTTP call 5 giây giữ locks/resources quá lâu và tăng contention.

## 3. How does it work?

```text
BEGIN TRANSACTION
  update Order
  update Inventory
  SAVEPOINT S1
  update Audit
COMMIT
```

Nếu một operation sau savepoint lỗi, có thể rollback về S1 tùy workflow. EF Core cũng dùng savepoint trong một số trường hợp `SaveChanges` bên trong transaction đang tồn tại.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

order.Approve();
inventory.Reserve(order.Items);
await db.SaveChangesAsync(ct);

await tx.CreateSavepointAsync("BeforeAudit", ct);

try
{
    db.AuditEntries.Add(AuditEntry.For(order));
    await db.SaveChangesAsync(ct);
}
catch
{
    await tx.RollbackToSavepointAsync("BeforeAudit", ct);
    throw;
}

await tx.CommitAsync(ct);
```

Không đặt external HTTP call vào transaction chỉ để “mọi thứ cùng atomic”. Database transaction không thể rollback side effect đã xảy ra ở remote API.

## 5. Real production scenario

Approval workflow cập nhật request, budget reservation và audit rows. Tất cả là cùng SQL database nên một local transaction hợp lý. Notification email thì đưa ra ngoài transaction, thường qua outbox/event sau commit.

## 6. Failure scenario & troubleshooting

**Symptom** → deadlock/lock timeout tăng sau khi thêm call sang external HR API vào workflow.

**Evidence** → transaction duration kéo dài đúng bằng dependency latency; locks sống lâu.

**Hypothesis** → transaction boundary vượt quá database consistency boundary.

**Diagnosis** → trace transaction lifetime, SQL locks và dependency spans.

**Fix** → commit database state trước; dùng outbox/saga/idempotency cho external side effect.

**Verification** → transaction duration giảm, lock waits giảm và failure của dependency không làm DB transaction kéo dài.

## 7. Common mistakes

- Mở transaction quá sớm.
- Giữ transaction qua user interaction hoặc network call.
- Tưởng `TransactionScope` làm mọi external system atomic miễn phí.
- Gọi `SaveChanges` nhiều lần mà không hiểu boundary.
- Catch exception rồi vẫn commit state chưa được kiểm chứng.

## 8. Alternatives

- Một `SaveChanges` mặc định: tốt cho phần lớn single-unit persistence.
- Explicit transaction: khi cần nhiều `SaveChanges` trong cùng atomic boundary.
- Outbox/Saga: khi consistency đi qua process/service/broker boundary.

## 9. Trade-offs

### Advantages

- Atomicity rõ.
- Dễ reasoning khi tất cả changes nằm cùng database.

### Costs / Risks

- Transaction dài tăng locks/contention.
- Cross-system atomicity không được giải quyết bằng local DB transaction.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu commit/rollback và atomicity.

### Middle

Biết khi nào `SaveChanges` đủ và khi nào cần explicit transaction.

### Senior

Thiết kế transaction ngắn, tránh remote I/O và phân tích lock/deadlock.

### Technical Lead / Architect

Xác định consistency boundary: local transaction ở đâu, eventual consistency bắt đầu ở đâu, outbox/saga có cần thiết không.

## 11. Key takeaway

- Transaction boundary nên bám business consistency boundary, không bám method boundary tùy tiện.
- Giữ transaction ngắn và không kéo qua network call.
- Cross-system consistency cần pattern khác local transaction.

# 4. SQL Server covering index và key lookup: đọc execution plan để biết khi nào `INCLUDE` đáng giá và khi nào index trở nên quá đắt

## 1. What is it?

Covering index là index chứa đủ columns để SQL Server trả query mà không cần quay về clustered index/heap lấy thêm dữ liệu. Columns dùng filter/sort thường nằm ở key; columns chỉ cần trả về có thể nằm trong `INCLUDE`.

## 2. Why does it exist?

Một nonclustered index có thể tìm row rất nhanh theo `CustomerId`, nhưng nếu query còn cần `Total`, `Status`, `CreatedAt`, engine có thể phải thực hiện nhiều Key Lookup.

Một lookup rẻ. Hàng trăm nghìn lookup có thể đắt hơn scan.

## 3. How does it work?

Query:

```sql
SELECT OrderId, Status, Total
FROM Orders
WHERE CustomerId = @customerId;
```

Index chưa cover:

```sql
CREATE INDEX IX_Orders_CustomerId
ON Orders(CustomerId);
```

Plan có thể là:

```text
Index Seek -> Key Lookup -> Nested Loops
```

Covering index:

```sql
CREATE INDEX IX_Orders_CustomerId
ON Orders(CustomerId)
INCLUDE (OrderId, Status, Total);
```

Lookup có thể biến mất.

## 4. Practical implementation

Không thêm `INCLUDE` theo cảm giác. Capture actual execution plan và logical reads:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT OrderId, Status, Total
FROM Orders
WHERE CustomerId = @customerId;
```

Sau khi index thay đổi, so sánh reads, duration và write cost ở workload thực tế.

## 5. Real production scenario

Order history endpoint nhanh cho customer có 20 orders nhưng chậm cho enterprise customer có 200k orders. Plan dùng seek + lookup hàng trăm nghìn lần. Cover đúng columns và pagination phù hợp có thể giảm I/O mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → read query nhanh hơn nhưng insert/update throughput giảm, storage tăng mạnh.

**Evidence** → index size lớn, page splits/write I/O tăng; nhiều overlapping indexes.

**Hypothesis** → over-indexing hoặc covering index quá rộng.

**Diagnosis** → xem usage stats, write workload, duplicate/overlapping indexes và actual plans.

**Fix** → thu hẹp include columns, merge overlapping indexes khi hợp lý hoặc loại index ít dùng.

**Verification** → benchmark cả read và write workload.

## 7. Common mistakes

- Thêm mọi SELECT column vào index.
- Không xem cardinality và actual rows.
- Tin hoàn toàn missing-index suggestion.
- Tạo nhiều index gần giống nhau.
- Tối ưu một query nhưng bỏ qua write-heavy workload.

## 8. Alternatives

- Clustered index phù hợp hơn nếu access pattern chính cần range theo key đó.
- Columnstore cho analytic workload khác OLTP lookup.
- Query rewrite/pagination có thể giảm rows cần đọc trước khi thêm index.

## 9. Trade-offs

### Advantages

- Giảm lookup và logical reads cho query mục tiêu.
- Có thể cải thiện latency rất lớn ở read-heavy path.

### Costs / Risks

- Tốn storage.
- Mỗi insert/update phải maintain thêm index.
- Index rộng làm cache efficiency kém hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không miễn phí và lookup là truy cập bổ sung.

### Middle

Biết đọc seek/scan/key lookup và dùng `STATISTICS IO`.

### Senior

Đánh đổi read gain với write/storage cost dựa workload.

### Technical Lead / Architect

Đặt index governance: đo workload, review overlapping indexes và không tối ưu theo từng ticket riêng lẻ.

## 11. Key takeaway

- `INCLUDE` có ích khi loại lookup đắt, không phải để cover mọi query.
- Execution plan + logical reads quan trọng hơn phỏng đoán.
- Mọi index đều có write và storage cost.

# 5. MongoDB transaction vs document-level atomicity: thiết kế aggregate để tránh dùng distributed-style transaction cho mọi business operation

## 1. What is it?

MongoDB đảm bảo atomicity cho update trên một document. Multi-document transaction mở rộng atomicity qua nhiều documents/collections, nhưng có thêm runtime và operational cost.

Mental model:

```text
One aggregate in one document
-> atomic update naturally

Many documents
-> transaction may be required
```

## 2. Why does it exist?

Document database phát huy lợi thế khi dữ liệu cần thay đổi cùng nhau được model gần nhau. Nếu schema buộc một business invariant phải update 12 collections trong transaction, có thể ta đang dùng relational modeling mindset trên document store.

## 3. How does it work?

Single document update:

```javascript
db.orders.updateOne(
  { _id: id, status: "Pending" },
  { $set: { status: "Approved" }, $push: { history: event } }
)
```

Status và history trong cùng document thay đổi atomic.

Multi-document transaction dùng session:

```csharp
using var session = await client.StartSessionAsync(cancellationToken: ct);
session.StartTransaction();

await orders.UpdateOneAsync(session, orderFilter, orderUpdate, cancellationToken: ct);
await budgets.UpdateOneAsync(session, budgetFilter, budgetUpdate, cancellationToken: ct);

await session.CommitTransactionAsync(ct);
```

## 4. Practical implementation

Trước khi thêm transaction, hỏi: hai phần state này có thực sự thuộc cùng aggregate và bounded consistency boundary không? Nếu có, embedding đôi khi đơn giản hơn reference + transaction.

Nếu documents lớn/unbounded hoặc lifecycle khác nhau, tách chúng vẫn đúng; khi đó transaction hoặc eventual consistency có thể cần thiết.

## 5. Real production scenario

Event platform lưu event và attendee check-in. Nhét toàn bộ check-ins vào một event document có thể tạo document lớn/hot. Tách check-ins thành collection riêng hợp lý hơn, và invariant tổng số vé có thể cần atomic counter/conditional update thay vì transaction khổng lồ mỗi lần scan QR.

## 6. Failure scenario & troubleshooting

**Symptom** → transaction abort/retry tăng dưới load, latency tăng dù individual queries nhanh.

**Evidence** → transaction duration cao, nhiều documents touched, contention trên hot documents.

**Hypothesis** → transaction boundary quá rộng hoặc schema tạo hotspot.

**Diagnosis** → inspect transaction metrics, document access pattern và retry reasons.

**Fix** → thu hẹp transaction, redesign aggregate, dùng conditional atomic update hoặc eventual workflow.

**Verification** → transaction duration/retry rate giảm dưới concurrency test.

## 7. Common mistakes

- Dùng transaction cho mọi update vì quen SQL.
- Embed unbounded arrays chỉ để tránh transaction.
- Không xử lý transient transaction retry.
- Chia documents quá nhỏ khiến business invariant luôn cross-document.
- Chọn MongoDB nhưng modeling như normalized relational schema 1:1.

## 8. Alternatives

- Single-document atomic update.
- Optimistic conditional update.
- Eventual consistency/outbox.
- Relational database nếu workload chủ yếu relational transactions phức tạp.

## 9. Trade-offs

### Advantages

- Multi-document transaction cho semantics quen thuộc khi thật sự cần.
- Document-level atomicity rất mạnh nếu aggregate được model tốt.

### Costs / Risks

- Transaction dài/large tăng contention và retry.
- Embedding quá mức gây document growth/hotspot.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một document update là atomic.

### Middle

Biết dùng session/transaction và conditional updates.

### Senior

Thiết kế aggregate dựa access pattern, consistency và document growth.

### Technical Lead / Architect

Quyết định MongoDB có phù hợp workload hay relational transaction model sẽ đơn giản hơn về lâu dài.

## 11. Key takeaway

- Ưu tiên schema cho đúng consistency boundary trước khi thêm transaction.
- Multi-document transaction là công cụ, không phải default modeling strategy.
- Database choice phải phản ánh workload thật.

# 6. Transactional Outbox Pattern: publish integration event đáng tin cậy mà không cần distributed transaction giữa database và broker

## 1. What is it?

Transactional Outbox ghi business state và message cần publish vào cùng một local database transaction. Một background publisher đọc outbox sau đó gửi message tới broker.

```text
API transaction
  -> update Order
  -> insert OutboxMessage
  -> COMMIT

Publisher
  -> read OutboxMessage
  -> publish broker
  -> mark processed
```

## 2. Why does it exist?

Naive flow:

```text
Save DB
Publish message
```

có failure window: DB commit thành công nhưng process crash trước publish. Reverse order cũng lỗi: publish thành công nhưng DB rollback.

Không có atomic transaction chung đáng tin cậy giữa SQL database và message broker trong nhiều modern architectures.

## 3. How does it work?

Business state và outbox row commit cùng nhau. Publisher có thể retry publish. Vì retry có thể tạo duplicate, consumer vẫn cần idempotency.

Outbox đạt **at-least-once delivery tendency**, không biến distributed system thành exactly-once end-to-end.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

order.MarkPaid();

db.OutboxMessages.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    Type = "OrderPaid",
    Payload = JsonSerializer.Serialize(new { order.Id, order.Total }),
    OccurredAtUtc = DateTime.UtcNow
});

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Worker publish batch, lưu `ProcessedAtUtc`, dùng bounded retry và metrics cho oldest pending message.

## 5. Real production scenario

Payment API phải cập nhật order và gửi `OrderPaid` để fulfillment bắt đầu. Nếu service restart ngay sau DB commit, outbox worker vẫn thấy pending event khi process lên lại và publish tiếp.

## 6. Failure scenario & troubleshooting

**Symptom** → outbox table tăng liên tục, downstream không nhận events.

**Evidence** → oldest pending age tăng, broker publish errors, publisher heartbeat mất.

**Hypothesis** → publisher stuck, auth/network broker lỗi hoặc poison payload chặn batch.

**Diagnosis** → metrics theo pending count/age, logs theo message ID, inspect broker dependency.

**Fix** → isolate failed messages, bounded retry, circuit/backoff và không để một poison row chặn toàn queue.

**Verification** → backlog drain về normal và event latency SLO phục hồi.

## 7. Common mistakes

- Xóa outbox row ngay sau publish mà không đủ audit/idempotency strategy.
- Tưởng outbox loại duplicate hoàn toàn.
- Không index pending rows.
- Poll toàn bảng liên tục.
- Không có retention cleanup.
- Serialize domain object trực tiếp thành public integration contract.

## 8. Alternatives

- Broker transaction nếu broker + workflow hỗ trợ phù hợp.
- CDC/outbox connector để stream DB changes.
- Direct publish đơn giản nếu mất event thực sự chấp nhận được.
- Distributed transaction: thường operationally nặng và ít phù hợp cloud-native boundary.

## 9. Trade-offs

### Advantages

- Không mất event giữa DB commit và publish do process crash.
- Dựa vào local DB transaction quen thuộc.

### Costs / Risks

- Event delivery có delay.
- Cần publisher, cleanup, monitoring và idempotent consumer.
- Thêm storage/write load.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu failure window của `save rồi publish`.

### Middle

Implement outbox table + worker + retry cơ bản.

### Senior

Thiết kế idempotency, ordering, batching, retention và observability.

### Technical Lead / Architect

Quyết định service nào cần outbox dựa reliability requirement; tránh áp pattern này cho side effect không quan trọng.

## 11. Key takeaway

- Outbox đóng failure gap giữa DB và broker bằng local transaction.
- Consumers vẫn phải chịu duplicate.
- Monitor backlog age, không chỉ publisher exceptions.

# 7. Azure Service Bus dead-letter queue và retry policy: phân biệt transient failure với poison message để tránh retry storm

## 1. What is it?

Dead-letter queue (DLQ) là nơi chứa messages không thể được xử lý thành công sau policy nhất định hoặc bị reject có chủ đích.

Retry dành cho lỗi transient; DLQ dành cho message cần investigation/remediation thay vì retry vô hạn.

## 2. Why does it exist?

Nếu consumer cứ retry malformed message mỗi giây:

```text
receive -> fail -> retry -> fail -> retry ...
```

nó tiêu tốn compute, logs và broker operations, đồng thời có thể làm healthy messages bị chậm.

## 3. How does it work?

Service Bus sử dụng delivery count. Nếu message bị abandon/re-deliver nhiều lần và vượt `MaxDeliveryCount`, message có thể chuyển DLQ.

Consumer cũng có thể dead-letter explicit với reason/description khi lỗi được xác định là non-transient.

## 4. Practical implementation

```csharp
processor.ProcessMessageAsync += async args =>
{
    try
    {
        var command = Deserialize(args.Message.Body);
        await handler.HandleAsync(command, args.CancellationToken);
        await args.CompleteMessageAsync(args.Message, args.CancellationToken);
    }
    catch (InvalidMessageException ex)
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            deadLetterReason: "InvalidContract",
            deadLetterErrorDescription: ex.Message,
            cancellationToken: args.CancellationToken);
    }
    catch (TransientDependencyException)
    {
        await args.AbandonMessageAsync(args.Message,
            cancellationToken: args.CancellationToken);
    }
};
```

Không đưa secret/PII vào DLQ description.

## 5. Real production scenario

Sau schema deployment, 0.5% old messages thiếu required field. Nếu tất cả retry 10 lần, backlog và log volume tăng mạnh. Contract-invalid messages nên DLQ để replay sau migration hoặc xử lý manual.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog tăng, same message IDs xuất hiện lặp lại, dependency bị overload.

**Evidence** → delivery count cao, exception type giống nhau, retry interval quá ngắn.

**Hypothesis** → permanent failure đang bị phân loại thành transient.

**Diagnosis** → group failures theo reason/message contract/dependency.

**Fix** → classification rõ, exponential backoff ở nơi phù hợp, DLQ poison message và tạo replay workflow có kiểm soát.

**Verification** → retry rate giảm, healthy throughput phục hồi, DLQ growth có alert.

## 7. Common mistakes

- Retry mọi exception.
- Không monitor DLQ.
- Manual replay toàn DLQ mà chưa fix root cause.
- Không idempotent nên replay gây duplicate side effects.
- MaxDeliveryCount quá cao chỉ để “đỡ mất message”.

## 8. Alternatives

- Deferred messages cho business condition tạm thời.
- Scheduled enqueue cho delayed retry workflow.
- Separate retry topic/queue khi cần policy phức tạp.
- Fail fast + alert nếu message loss/repair được quản lý bên ngoài.

## 9. Trade-offs

### Advantages

- Isolate poison messages.
- Giữ main queue healthy.
- Tạo forensic trail cho failed work.

### Costs / Risks

- Cần runbook, replay tooling và monitoring.
- DLQ có thể trở thành “nghĩa địa” nếu không có owner.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry không phải giải pháp cho lỗi permanent.

### Middle

Biết complete/abandon/dead-letter và đọc delivery count.

### Senior

Thiết kế error taxonomy, idempotency, backoff và replay.

### Technical Lead / Architect

Đặt ownership/SLO cho DLQ, backlog và recovery workflow thay vì chỉ cấu hình broker.

## 11. Key takeaway

- Retry transient failure; dead-letter poison/permanent failure.
- DLQ phải có monitoring và replay procedure.
- Retry sai có thể tự tạo outage thứ hai.

# 8. Redis distributed lock và lease semantics: lock không phải mutex hoàn hảo khi process crash, network partition hoặc lease hết hạn

## 1. What is it?

Distributed lock dùng shared system như Redis để nhiều process/instances cố giành quyền thực hiện một critical section. Thực tế nó thường là một **lease có timeout**, không phải mutex tuyệt đối như trong một process.

## 2. Why does it exist?

Khi application scale 5 instances, local `lock` chỉ đồng bộ threads trong từng process. Scheduled job có thể chạy 5 lần.

Distributed coordination cần một shared ownership signal.

## 3. How does it work?

Một primitive phổ biến:

```text
SET job:daily owner-token NX PX 30000
```

- `NX`: chỉ set nếu key chưa tồn tại.
- `PX`: lease hết hạn tự động.
- token: owner unique.

Release phải chỉ xóa key nếu token vẫn thuộc owner; thường dùng Lua để compare-and-delete atomically.

## 4. Practical implementation

Pseudo-near-production release logic:

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
```

Không dùng `DEL key` trực tiếp: lease cũ có thể hết hạn, instance B đã acquire, instance A tỉnh lại và xóa lock của B.

## 5. Real production scenario

Một recurring billing job chạy trên nhiều App Service instances. Redis lease đảm bảo một leader thực hiện batch. Nhưng charge operation vẫn cần idempotency key vì process có thể mất lease sau khi charge thành công nhưng trước khi ghi progress.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng job chạy đồng thời dù có lock.

**Evidence** → execution duration đôi khi dài hơn lease TTL; GC pause/network stall xảy ra; logs cho thấy owner token đổi giữa execution.

**Hypothesis** → lease hết hạn trước khi critical section hoàn thành.

**Diagnosis** → so sánh TTL, worst-case runtime, renewal events và Redis availability.

**Fix** → renewal protocol có ownership check, bounded work chunks, idempotent side effects; nếu correctness cực nghiêm ngặt, cân nhắc fencing token/coordination system khác.

**Verification** → fault test process pause/crash/network delay và xác nhận không tạo duplicate harmful side effect.

## 7. Common mistakes

- Dùng `SETNX` không TTL rồi dead process giữ lock mãi.
- Release bằng `DEL` không owner token.
- Lease 30 giây cho job có thể chạy 10 phút.
- Nghĩ lock loại bỏ nhu cầu idempotency.
- Không định nghĩa behavior khi Redis unavailable.

## 8. Alternatives

- Database advisory/application lock.
- Queue với single active consumer/session semantics.
- Leader election platform primitive.
- Không lock, thiết kế operation idempotent và partition work.

## 9. Trade-offs

### Advantages

- Coordination tương đối đơn giản.
- Phù hợp scheduler/batch có tolerance hợp lý.

### Costs / Risks

- Lease expiry và partition tạo edge cases.
- Thêm dependency Redis vào correctness path.
- Renewal/ownership logic không đơn giản như local mutex.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu local lock không đồng bộ nhiều processes.

### Middle

Biết NX + TTL + owner-token release.

### Senior

Reasoning về lease expiry, crash, partition, idempotency và fencing.

### Technical Lead / Architect

Quyết định distributed lock có thật sự cần, hay queue/partition/idempotent design đơn giản và đáng tin hơn.

## 11. Key takeaway

- Distributed lock thường là lease, không phải guarantee tuyệt đối.
- Ownership token và expiry semantics là correctness-critical.
- Side effects quan trọng vẫn cần idempotency/fencing strategy.

# 9. OpenTelemetry trace sampling và correlation: giữ observability hữu ích ở production mà không thu thập 100% mọi request

## 1. What is it?

Distributed trace nối các spans của một request xuyên qua services và dependencies bằng trace context. Sampling quyết định trace nào được record/export để kiểm soát volume và cost.

```text
Client
  traceId=abc
    -> API span
       -> SQL span
       -> HTTP span
          -> Service B span
```

## 2. Why does it exist?

Logs rời rạc trả lời “component này log gì”; trace trả lời “một request cụ thể đã đi qua đâu và chậm ở đâu”. Nhưng hệ thống lớn có thể tạo hàng tỷ spans, nên lưu 100% thường quá đắt.

## 3. How does it work?

Trace context (`traceparent`) được propagate qua HTTP/messaging. Sampler có thể quyết định head-based ngay khi trace bắt đầu hoặc tail-based sau khi đã thấy outcome ở collector architecture phù hợp.

Parent-based sampling giữ consistency: child spans thường theo sampling decision của parent.

## 4. Practical implementation

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation()
        .SetSampler(new ParentBasedSampler(
            new TraceIdRatioBasedSampler(0.10))));
```

10% chỉ là ví dụ. Sampling rate phải dựa traffic, cost và incident requirements.

Structured logs nên chứa `TraceId` để pivot từ log sang trace.

## 5. Real production scenario

API p99 tăng nhưng average bình thường. Trace của slow requests cho thấy chỉ requests tới một region của downstream payment service có 2-second latency. Correlation giúp tránh đổ lỗi DB chỉ vì DB query xuất hiện trong cùng request.

## 6. Failure scenario & troubleshooting

**Symptom** → incident xảy ra nhưng trace của lỗi hiếm không được sample.

**Evidence** → head sampling 1% và lỗi chỉ chiếm 0.01% traffic.

**Hypothesis** → sampling strategy tối ưu cost nhưng bỏ mất high-value failures.

**Diagnosis** → kiểm tra sampler/exporter/collector và tỷ lệ error traces retained.

**Fix** → cân nhắc tail sampling giữ error/high-latency traces, hoặc adaptive policy phù hợp platform.

**Verification** → synthetic failures xuất hiện trong telemetry với acceptable ingest volume.

## 7. Common mistakes

- Sample 100% production vô thời hạn.
- Sample quá thấp mà không ưu tiên errors.
- Mất trace context khi publish message/background work.
- Gắn high-cardinality/PII attributes bừa bãi.
- Dùng tracing thay metrics cho aggregate alerting.

## 8. Alternatives

- Metrics: tốt cho aggregate health/SLO/alert.
- Logs: tốt cho rich event details.
- Traces: tốt cho causal path một request.

Ba loại telemetry bổ sung nhau, không thay thế hoàn toàn.

## 9. Trade-offs

### Advantages

- Tìm latency/failure propagation xuyên services.
- Correlation giảm thời gian điều tra incident.

### Costs / Risks

- Ingest/storage cost.
- High-cardinality attributes tăng cost.
- Sampling sai làm mất rare incidents.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace ID nối nhiều spans trong một request.

### Middle

Instrument HTTP/DB và propagate context.

### Senior

Thiết kế sampling, cardinality và correlation cho incident investigation.

### Technical Lead / Architect

Đặt telemetry budget, retention, SLO observability và data-governance boundary toàn hệ thống.

## 11. Key takeaway

- Metrics nói hệ thống có vấn đề; traces giúp thấy request bị vấn đề ở đâu.
- Sampling là cost/correctness trade-off của observability.
- Error/slow trace retention thường giá trị hơn random volume lớn.

# 10. Docker multi-stage build cho .NET: tách build-time toolchain khỏi runtime image để giảm attack surface và deployment weight

## 1. What is it?

Multi-stage build dùng nhiều stages trong Dockerfile: stage SDK restore/build/publish, rồi chỉ copy published artifacts sang runtime image nhỏ hơn.

```text
SDK image
  restore -> build -> publish
                    |
                    v
Runtime image <- published output only
```

## 2. Why does it exist?

Nếu production container dùng full .NET SDK image, nó mang theo compiler, NuGet tooling và nhiều files không cần khi chạy application. Image lớn hơn đồng nghĩa pull chậm hơn, patch surface lớn hơn và nhiều tool không cần thiết tồn tại trong runtime.

## 3. How does it work?

Docker build tạo filesystem layer cho từng stage. Final image chỉ lấy artifacts được copy từ named build stage.

Build cache hiệu quả phụ thuộc layer ordering; copy project files và restore trước khi copy toàn source giúp cache NuGet restore tốt hơn khi source code đổi nhưng dependencies không đổi.

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

COPY MyApi/MyApi.csproj MyApi/
RUN dotnet restore MyApi/MyApi.csproj

COPY . .
RUN dotnet publish MyApi/MyApi.csproj \
    -c Release \
    -o /app/publish \
    --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
WORKDIR /app
COPY --from=build /app/publish .

USER $APP_UID
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

Version thực tế cần pin theo organization policy và patch strategy.

## 5. Real production scenario

CI trước đây build image 1.4 GB vì copy cả source, `.git`, test results và SDK vào runtime. Scale-out trên Kubernetes/App Service container mất lâu do pull image. Multi-stage + `.dockerignore` giảm image đáng kể và deployment startup nhanh hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → application build thành công nhưng container runtime fail vì native dependency/timezone/certificate file thiếu.

**Evidence** → build stage có dependency, runtime stage không có; error xuất hiện chỉ sau final image start.

**Hypothesis** → runtime assumptions bị ẩn bởi SDK image.

**Diagnosis** → run final image locally/CI, inspect base distro/native libraries và container logs.

**Fix** → thêm runtime dependency tối thiểu, chọn base image phù hợp và integration-test final image.

**Verification** → health check pass trên chính immutable image sẽ deploy.

## 7. Common mistakes

- Dùng SDK image làm production runtime.
- `COPY . .` trước restore làm cache invalidation liên tục.
- Copy secrets vào build context/layer.
- Chạy container bằng root không cần thiết.
- Chỉ test `dotnet run`, không test final container image.
- Dùng `latest` tag không có patch/reproducibility strategy.

## 8. Alternatives

- Framework-dependent deployment trên VM/IIS: phù hợp môi trường Windows hosting truyền thống.
- Self-contained/native AOT image: giảm dependency framework nhưng có build/runtime trade-offs riêng.
- Buildpacks: giảm Dockerfile maintenance khi platform conventions phù hợp.

## 9. Trade-offs

### Advantages

- Runtime image nhỏ hơn.
- Attack surface và tooling dư thừa giảm.
- Build/runtime responsibilities rõ hơn.

### Costs / Risks

- Dockerfile/cache strategy cần hiểu đúng.
- Native dependency differences có thể chỉ lộ ở final stage.
- Image size nhỏ không tự động nghĩa startup nhanh nếu app initialization chậm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu build image và runtime image có trách nhiệm khác nhau.

### Middle

Viết multi-stage Dockerfile, `.dockerignore` và chạy non-root.

### Senior

Tối ưu cache, reproducibility, vulnerability patching và debug native/runtime differences.

### Technical Lead / Architect

Định nghĩa base-image policy, SBOM/scanning, patch cadence và immutable artifact promotion qua environments.

## 11. Key takeaway

- Production image chỉ nên chứa thứ cần để chạy application.
- Multi-stage build tách compile toolchain khỏi runtime artifact.
- Test chính final image sẽ deploy, không chỉ test source/build stage.
