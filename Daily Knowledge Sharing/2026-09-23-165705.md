# 1. .NET Large Object Heap: allocation lớn không chỉ là “tốn RAM hơn”

## 1. What is it?

Mental model: .NET GC chia managed heap thành các vùng/generations để tối ưu cho giả định phần lớn object sống ngắn. Các object đủ lớn được cấp phát trên Large Object Heap (LOH), nơi lifecycle và compaction behavior khác các object nhỏ.

Điểm quan trọng không phải nhớ một threshold như trivia, mà hiểu rằng allocation lớn làm tăng áp lực memory, thời gian GC và nguy cơ fragmentation theo cách khác với hàng nghìn object nhỏ.

## 2. Why does it exist?

Copy/compact object lớn thường đắt. Runtime vì vậy xử lý large allocations theo chiến lược phù hợp hơn thay vì di chuyển chúng liên tục như short-lived objects. Điều này giảm một loại chi phí nhưng tạo trade-off khác: LOH thường được thu gom cùng full GC và fragmentation có thể trở thành vấn đề.

## 3. How does it work?

```text
request
  -> allocate large byte[]
  -> LOH
  -> object dies
  -> space becomes reusable
  -> repeated uneven allocations
  -> fragmented free regions
  -> allocation pressure / full GC
```

Một service có thể còn tổng free memory nhưng không có contiguous region phù hợp cho allocation lớn tiếp theo. Đồng thời full collections đắt hơn Gen0 collections vì phạm vi lớn hơn.

## 4. Practical implementation

Đừng đọc toàn bộ file lớn vào một `byte[]` nếu có thể stream:

```csharp
app.MapGet("/exports/{id}", async (
    string id,
    IExportStore store,
    HttpResponse response,
    CancellationToken ct) =>
{
    response.ContentType = "application/octet-stream";

    await using var source = await store.OpenReadAsync(id, ct);
    await source.CopyToAsync(response.Body, ct);
});
```

Nếu workload thực sự cần reusable buffers, `ArrayPool<T>` có thể giảm allocation churn, nhưng buffer thuê phải được trả đúng lifecycle và dữ liệu nhạy cảm cần được xử lý cẩn thận.

## 5. Real production scenario

API tạo PDF export 20–80 MB bằng `MemoryStream.ToArray()` trước khi upload Blob Storage. Traffic bình thường ổn, nhưng khi nhiều exports chạy đồng thời, process memory tăng theo răng cưa, full GC xuất hiện dày hơn và p99 của endpoint khác cũng tăng. Root cause không phải Blob chậm mà là large-buffer allocation strategy.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng mạnh, GC pause/p99 tăng khi xử lý payload lớn.

**Telemetry** → runtime counters cho allocation rate, heap size, Gen2/GC behavior; profiler/dump cho thấy `byte[]`, `char[]` hoặc buffers lớn chiếm ưu thế.

**Hypothesis** → large allocations tạo LOH pressure hoặc giữ buffers quá lâu.

**Evidence** → correlate allocation type/size với request path và concurrent workload.

**Remediation** → streaming, bounded buffering, pooling khi hợp lý, giảm concurrent large work.

**Verification** → load test với payload distribution Production-like và đo memory + latency tail.

## 7. Common mistakes

Tăng container memory rồi coi là đã sửa; pool mọi buffer mà không hiểu ownership; giữ pooled buffer trong cache; chỉ nhìn managed heap mà bỏ native/process memory; tối ưu allocation trước khi profiler chứng minh bottleneck.

## 8. Alternatives

Streaming là lựa chọn tốt khi consumer không cần toàn bộ payload cùng lúc. Temporary file/object storage phù hợp khi cần materialize nhưng không muốn giữ toàn bộ trong RAM. Pooling phù hợp reusable transient buffers có lifecycle rõ.

## 9. Trade-offs

Streaming giảm peak memory nhưng code/error handling phức tạp hơn. Pooling giảm allocation nhưng tăng ownership/security complexity. Materialization đơn giản nhất và vẫn đúng với payload nhỏ, bounded.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu allocation và GC không đồng nghĩa memory được trả về OS ngay lập tức.

### Middle
Biết tránh materialize payload lớn không cần thiết và dùng profiler/counters.

### Senior
Phân tích allocation rate, LOH, Gen2 pressure, retention và concurrency cùng nhau.

### Technical Lead / Architect
Đặt payload limits, streaming conventions và workload isolation dựa trên memory budget của service.

## 11. Key takeaway

- Large allocation là performance concern về lifecycle và GC, không chỉ số MB.
- Với payload lớn, streaming thường tốt hơn materialization.
- Chỉ dùng pooling khi ownership và measurement chứng minh lợi ích.

# 2. ASP.NET Core middleware ordering: đúng middleware, sai thứ tự vẫn sai hệ thống

## 1. What is it?

Mental model: ASP.NET Core middleware tạo một chuỗi nested delegates. Request đi theo thứ tự đăng ký; response đi ngược trở lại. Vì middleware có thể short-circuit hoặc phụ thuộc context do middleware trước tạo ra, ordering là một phần của behavior và security model.

## 2. Why does it exist?

Pipeline cho phép composition: exception handling bao quanh downstream work, routing xác định endpoint, authentication tạo principal, authorization kiểm tra principal/metadata. Nếu các bước đảo vị trí, component có thể chạy khi prerequisite chưa tồn tại.

## 3. How does it work?

```text
Request
  -> Exception handler
    -> Routing
      -> Authentication
        -> Authorization
          -> Endpoint
        <-
      <-
    <-
  <-
Response
```

Một middleware gọi `await next(context)` để chuyển xuống pipeline; code sau `await next` chạy trên đường response quay lại.

## 4. Practical implementation

```csharp
var app = builder.Build();

app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();
```

Với custom middleware cần endpoint metadata, hãy đảm bảo nó chạy tại vị trí metadata đã được routing xác định theo hosting/routing model đang dùng. Đừng copy ordering từ blog cũ mà không hiểu prerequisite.

## 5. Real production scenario

Team thêm tenant authorization middleware trước authentication. Middleware đọc `context.User` nhưng principal chưa được tạo, nên authenticated users đôi lúc bị coi là anonymous hoặc custom fallback path bỏ qua policy dự kiến. Từng middleware riêng lẻ đều “đúng”; composition sai.

## 6. Failure scenario & troubleshooting

**Symptom** → 401/403 bất thường, exception không được chuẩn hóa, headers/compression/CORS khác nhau theo endpoint.

**Telemetry** → request logs cho biết middleware nào chạy, endpoint metadata và authentication state tại từng stage.

**Hypothesis** → ordering hoặc short-circuit sai.

**Evidence** → minimal integration test xác nhận pipeline sequence.

**Remediation** → xác định dependency giữa stages rồi sắp xếp theo lifecycle.

**Verification** → integration tests cho authenticated/anonymous/error/preflight paths.

## 7. Common mistakes

Đăng ký middleware nhưng quên `Use...`; đặt exception handler quá sâu; custom auth logic trước authentication; nghĩ response middleware chỉ ảnh hưởng request direction; thêm middleware global cho behavior chỉ một endpoint cần.

## 8. Alternatives

Endpoint filters, MVC filters hoặc authorization policies phù hợp behavior gắn với endpoint/application concern. Middleware phù hợp cross-cutting HTTP pipeline concern.

## 9. Trade-offs

Middleware đơn giản và composable nhưng global ordering dễ tạo coupling ẩn. Endpoint-specific mechanisms rõ scope hơn nhưng không bao phủ toàn pipeline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu request đi xuống và response đi ngược pipeline.

### Middle
Biết prerequisite của authentication, authorization, error handling và endpoint execution.

### Senior
Debug short-circuit/order bằng integration tests và telemetry.

### Technical Lead / Architect
Định nghĩa pipeline conventions và chọn đúng extension point thay vì biến mọi cross-cutting concern thành middleware.

## 11. Key takeaway

- Middleware ordering là executable architecture.
- Hãy xác định prerequisite trước khi quyết định vị trí middleware.
- Security pipeline cần integration test, không chỉ unit test từng component.

# 3. EF Core compiled queries: tối ưu query-compilation overhead đúng lúc

## 1. What is it?

EF Core phải xử lý LINQ expression thành query representation/SQL trước khi database thực thi. EF đã cache query compilation theo query shape; compiled queries cho phép application tạo delegate đã compile rõ ràng để giảm thêm overhead trên hot path phù hợp.

## 2. Why does it exist?

Với query rất thường xuyên, rất nhanh ở database và có shape ổn định, client-side query processing có thể trở thành phần đáng kể của tổng latency/CPU. Nhưng nếu SQL mất 200 ms, tiết kiệm micro/milliseconds ở compilation hiếm khi là ưu tiên đầu tiên.

## 3. How does it work?

```text
normal LINQ
 -> expression shape lookup/compile
 -> SQL command
 -> DB

compiled delegate
 -> reusable compiled query pipeline
 -> parameter values
 -> DB
```

Compiled query tối ưu phần EF-side; nó không sửa missing index, N+1, over-fetching hoặc network latency.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, long, Task<Order?>> GetOrder =
    EF.CompileAsyncQuery((AppDbContext db, long id) =>
        db.Orders
          .AsNoTracking()
          .SingleOrDefault(x => x.Id == id));

var order = await GetOrder(db, orderId);
```

Benchmark phải bao gồm realistic DbContext lifecycle và warm-up. Đừng chuyển toàn repository sang compiled queries theo mặc định.

## 5. Real production scenario

Một low-latency internal service gọi cùng lookup hàng chục nghìn lần/giây; database query đã seek rất nhanh và payload nhỏ. Profiling cho thấy EF-side overhead đáng kể. Compiled query có lợi. Ngược lại reporting query 2 giây không thay đổi đáng kể vì bottleneck nằm ở DB I/O.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled query nhưng endpoint gần như không nhanh hơn.

**Telemetry** → trace cho thấy phần lớn thời gian nằm trong database/dependency.

**Hypothesis** → tối ưu sai layer.

**Evidence** → benchmark tách client query overhead khỏi SQL duration.

**Remediation** → quay lại execution plan, projection, indexes hoặc round trips.

**Verification** → đo throughput/CPU/latency trước và sau.

## 7. Common mistakes

Compiled query quá sớm; tạo query shape động khó reuse; bỏ qua generated SQL; benchmark in-memory database rồi suy ra Production; đánh đổi readability cho optimization không đo được.

## 8. Alternatives

EF query cache mặc định thường đủ. Projection, reducing round trips, proper indexes và raw SQL cho specialized cases thường có impact lớn hơn nếu bottleneck ở database.

## 9. Trade-offs

Compiled queries có thể giảm CPU/latency trên hot path nhưng tăng code ceremony và giảm flexibility của dynamic query composition.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu LINQ phải được translate trước khi DB chạy.

### Middle
Biết xem SQL và đo query duration.

### Senior
Phân biệt EF overhead với DB execution cost bằng profiling.

### Technical Lead / Architect
Chỉ chuẩn hóa optimization khi workload evidence đủ mạnh, giữ default path đơn giản cho phần lớn code.

## 11. Key takeaway

- Compiled query tối ưu EF query pipeline, không tối ưu SQL plan.
- Hot, stable, cheap database queries là candidate tốt hơn.
- Profile trước khi tăng complexity.

# 4. SQL covering index: index phục vụ access pattern, không phục vụ cảm giác an toàn

## 1. What is it?

Một index “cover” query khi index chứa đủ dữ liệu cần để tìm/filter/order và trả kết quả mà engine không phải quay lại base table/clustered structure để lấy thêm columns. Trên SQL Server, key columns và `INCLUDE` columns thường được phối hợp cho mục tiêu này.

## 2. Why does it exist?

Nonclustered index có thể tìm rows rất nhanh nhưng nếu query cần columns không có trong index, engine có thể thực hiện nhiều Key Lookups. Với số rows nhỏ lookup rẻ; với hàng chục nghìn rows nó có thể thành random I/O đáng kể.

## 3. How does it work?

```text
Index seek -> matching index rows
       |
       +-> missing columns?
             yes -> Key Lookup x N
             no  -> return directly
```

Key order ảnh hưởng seek/sort. `INCLUDE` có thể cover output columns mà không biến chúng thành search-key ordering semantics.

## 4. Practical implementation

Query:

```sql
SELECT OrderNumber, Total, CreatedAt
FROM dbo.Orders
WHERE CustomerId = @CustomerId
ORDER BY CreatedAt DESC;
```

Một candidate access path có thể là:

```sql
CREATE INDEX IX_Orders_CustomerId_CreatedAt
ON dbo.Orders(CustomerId, CreatedAt DESC)
INCLUDE(OrderNumber, Total);
```

Đây chỉ là candidate; phải xem existing indexes, cardinality, write load và actual plan trước khi tạo.

## 5. Real production scenario

Customer order history trả 50 rows nhưng execution plan cho thấy seek rồi lookup rất nhiều vì predicate trước pagination chưa đủ selective trong một số tenant. Thiết kế index theo filter + ordering + projection giảm logical reads đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → read nhanh hơn nhưng write latency/storage tăng sau khi thêm nhiều covering indexes.

**Telemetry** → index usage cho thấy nhiều indexes ít đọc nhưng phải maintain trên mỗi write.

**Hypothesis** → over-indexing.

**Evidence** → compare read benefit với write amplification, size và overlap.

**Remediation** → consolidate/remove redundant indexes sau validation.

**Verification** → benchmark read workload lẫn write workload.

## 7. Common mistakes

Include mọi column; tạo index theo từng query riêng lẻ; bỏ qua key order; tin missing-index suggestion như quyết định cuối; không xem filtered/selective access pattern; quên index làm migrations/deploy nặng hơn.

## 8. Alternatives

Projection nhỏ hơn có thể giảm nhu cầu cover. Clustered/index design khác, materialized read model hoặc query redesign phù hợp khi workload fundamentally khác OLTP access path.

## 9. Trade-offs

Covering index giảm reads/lookups nhưng tăng storage, memory footprint và write maintenance. “Faster SELECT” không miễn phí.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu index không phải bản copy miễn phí của table.

### Middle
Đọc seek/scan/lookup và logical reads.

### Senior
Thiết kế key/include dựa trên predicate, sort, cardinality và write cost.

### Technical Lead / Architect
Quản trị index portfolio theo workload thay vì tích lũy indexes qua từng incident.

## 11. Key takeaway

- Cover query để giảm lookup chỉ khi workload đáng giá.
- Index design phải xét filter, ordering, projection và write cost cùng lúc.
- Actual plan + logical reads tốt hơn phỏng đoán.

# 5. MongoDB embedding vs referencing: document boundary là quyết định consistency và access

## 1. What is it?

Embedding lưu related data trong cùng document; referencing lưu identity/link sang document khác. Đây không phải “NoSQL thì embed tất cả”, mà là quyết định data locality dựa trên read/write pattern, cardinality, ownership và consistency boundary.

## 2. Why does it exist?

Document database tối ưu khi dữ liệu thường được đọc/cập nhật cùng nhau có thể nằm cùng aggregate-like document. Nhưng embedded collection tăng không giới hạn hoặc shared entity được copy nhiều nơi tạo write amplification và consistency complexity.

## 3. How does it work?

```text
Embedding:
Order {
  customerSnapshot,
  lines: [...]
}

Referencing:
Order { customerId }
Customer { ... }
```

Snapshot embedded có thể cố ý giữ lịch sử tại thời điểm order; đó không nhất thiết là duplicated-data bug.

## 4. Practical implementation

Một Order thường phù hợp embed line snapshot nếu lines thuộc Order lifecycle:

```json
{
  "_id": "O-1001",
  "customerId": "C-9",
  "lines": [
    { "sku": "SKU-1", "name": "Name at purchase", "price": 120 }
  ]
}
```

Product master vẫn có thể là collection riêng vì được cập nhật và truy vấn độc lập.

## 5. Real production scenario

E-commerce lưu order lines bằng references trực tiếp tới current product data. Sau khi product đổi tên/giá, historical invoice hiển thị dữ liệu mới, sai business semantics. Embedding purchase snapshot giải quyết requirement lịch sử tốt hơn “normalized” reference.

## 6. Failure scenario & troubleshooting

**Symptom** → document tăng rất lớn, updates chậm và hot document contention.

**Telemetry** → document size/cardinality tăng theo thời gian; write latency tập trung một key.

**Hypothesis** → unbounded child collection bị embed sai boundary.

**Evidence** → access pattern cho thấy children có lifecycle/query độc lập.

**Remediation** → reference/bucket/re-model theo workload.

**Verification** → test realistic cardinality và concurrent writes.

## 7. Common mistakes

Port relational schema 1:1 sang MongoDB; embed unbounded event history; reference mọi thứ vì sợ duplication; duplicate mutable data nhưng không có synchronization ownership; chọn model trước khi biết queries.

## 8. Alternatives

Referencing phù hợp shared/high-cardinality entities. Bucket pattern phù hợp time-series-like growth. Relational database có thể phù hợp hơn nếu workload cần rich joins và cross-entity transactional constraints thường xuyên.

## 9. Trade-offs

Embedding tăng locality/atomicity trong document nhưng tăng duplication/size. Referencing giảm duplication nhưng thêm queries/aggregation và consistency coordination.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu document không phải row có JSON syntax.

### Middle
Model theo reads/writes thay vì ER diagram thuần túy.

### Senior
Đánh giá growth, atomicity, hot documents và duplicated-state ownership.

### Technical Lead / Architect
Chọn storage/model dựa trên domain invariants và operational access patterns.

## 11. Key takeaway

- Embed khi dữ liệu có ownership/lifecycle và access locality phù hợp.
- Reference khi data độc lập, shared hoặc tăng trưởng không bounded.
- Duplication có thể là chủ ý, nhưng phải có semantics rõ.

# 6. Circuit Breaker: dừng gọi dependency đang thất bại để bảo vệ cả hai phía

## 1. What is it?

Circuit Breaker là resilience state machine tạm thời từ chối calls tới dependency khi failure rate vượt điều kiện, sau đó cho một số calls thử nghiệm để xem dependency đã phục hồi chưa.

Mental model: timeout giới hạn một call; retry thử lại một call; circuit breaker giới hạn việc cả hệ thống tiếp tục tạo calls khi dependency đang unhealthy.

## 2. Why does it exist?

Nếu payment provider đang timeout 10 giây, 1.000 requests có thể giữ 1.000 operations/resources chờ. Retry còn nhân tải. Breaker giúp fail fast sau khi có đủ evidence rằng dependency đang lỗi.

## 3. How does it work?

```text
CLOSED --failures threshold--> OPEN
  ^                           |
  |                           | break duration
  |                           v
  +----successes---------- HALF-OPEN
```

State thường là local theo process/pipeline; đừng mặc định coi nó là global truth về dependency.

## 4. Practical implementation

Với .NET resilience stack, policy nên được cấu hình theo dependency và operation semantics. Ví dụ conceptual configuration:

```csharp
builder.Services.AddHttpClient<PaymentClient>()
    .AddStandardResilienceHandler();
```

Production configuration cần xác định timeout, retry, breaker thresholds và jitter theo idempotency/SLO của dependency; không copy default rồi coi là hoàn tất.

## 5. Real production scenario

Review API bên thứ ba bắt đầu trả 503. Không breaker, product page threads/connections chờ và retry làm latency lan sang toàn site. Breaker mở, service trả fallback “reviews temporarily unavailable” trong khi core product data vẫn hoạt động.

## 6. Failure scenario & troubleshooting

**Symptom** → breaker liên tục open/half-open, dependency vừa hồi phục lại bị traffic đập mạnh.

**Telemetry** → breaker state transitions, downstream latency/error code, retry count.

**Hypothesis** → threshold/probe/retry composition tạo oscillation.

**Evidence** → correlate transitions với dependency health.

**Remediation** → tune sampling/break duration, giảm retries, thêm bulkhead/fallback.

**Verification** → fault-injection test outage và recovery.

## 7. Common mistakes

Breaker cho mọi exception kể cả validation 4xx; retry bên trong/ngoài nhiều layers tạo multiplicative retries; global breaker gộp unrelated endpoints; fallback trả dữ liệu sai business; không quan sát breaker state.

## 8. Alternatives

Timeout luôn cần cho bounded waiting. Retry phù hợp transient failure và idempotent operations. Bulkhead giới hạn concurrent impact. Queue phù hợp khi work có thể deferred. Các patterns thường phối hợp nhưng mỗi cái giải quyết failure mode khác nhau.

## 9. Trade-offs

Fail-fast bảo vệ capacity nhưng có thể reject calls trong lúc dependency đã bắt đầu hồi phục. Threshold quá nhạy gây false-open; quá chậm thì không bảo vệ được hệ thống.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt timeout, retry và breaker.

### Middle
Cấu hình policy theo HTTP client/dependency.

### Senior
Reason về idempotency, policy composition, recovery và telemetry.

### Technical Lead / Architect
Thiết kế degradation strategy để optional dependency không kéo sập critical user journey.

## 11. Key takeaway

- Circuit Breaker giới hạn failure propagation, không sửa dependency.
- Retry và breaker phải được thiết kế cùng nhau.
- Fallback chỉ hợp lệ khi business semantics cho phép degraded result.

# 7. Azure Key Vault + Managed Identity: application cần secret, không nhất thiết cần credential để lấy secret

## 1. What is it?

Azure Key Vault lưu secrets/keys/certificates với access control và audit. Managed Identity cung cấp identity cho Azure workload để lấy token từ Microsoft Entra ID mà không cần application lưu client secret của chính nó.

## 2. Why does it exist?

Nếu appsettings chứa database password và credential dùng để truy cập secret store, ta chỉ di chuyển bài toán secret. Managed Identity loại bỏ bootstrap secret cho workload chạy trên Azure resource hỗ trợ identity.

## 3. How does it work?

```text
App Service / VM / workload identity
        |
        | request Entra token
        v
Managed Identity
        |
        | token + Key Vault RBAC/access policy
        v
Azure Key Vault
        |
        +-> authorized secret/key operation
```

Identity và authorization là hai bước: có identity không có nghĩa tự động được đọc mọi secret.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(keyVaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("SqlPassword", cancellationToken: ct);
```

Local development có thể dùng developer identity supported bởi `DefaultAzureCredential`; Production dùng Managed Identity. Quyền phải theo least privilege.

## 5. Real production scenario

App Service trước đây có service-principal secret trong deployment variable để đọc Key Vault. Secret đó phải rotate và có thể leak qua pipeline. Chuyển sang system/user-assigned Managed Identity loại bỏ credential bootstrap khỏi deployment path.

## 6. Failure scenario & troubleshooting

**Symptom** → app startup fail với 401/403 khi đọc Key Vault.

**Telemetry** → Azure identity logs/Key Vault diagnostics phân biệt token acquisition với authorization denial/network restriction.

**Hypothesis** → identity chưa được gán quyền, sai vault URI hoặc Private Endpoint/DNS path.

**Evidence** → kiểm tra principal, role scope và network resolution.

**Remediation** → sửa đúng layer, không cấp quyền rộng để “test”.

**Verification** → deployment bằng Production identity và secret rotation test.

## 7. Common mistakes

Hard-code vault secret vào config fallback; cấp Contributor thay vì secret-specific data-plane permission; fetch secret mỗi request; log secret values; nghĩ Key Vault tự rotate mọi consumer; bỏ qua Private Endpoint/DNS design.

## 8. Alternatives

Platform configuration references có thể inject Key Vault-backed settings đơn giản hơn. Managed Identity trực tiếp tới database/storage có thể loại bỏ password hoàn toàn, tốt hơn việc chỉ cất password trong vault khi service hỗ trợ token auth.

## 9. Trade-offs

Key Vault tăng security/audit nhưng thêm network dependency, permissions và startup/runtime failure modes. Caching secret giảm calls nhưng ảnh hưởng rotation freshness.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt secret storage với identity.

### Middle
Dùng `DefaultAzureCredential` và least privilege.

### Senior
Thiết kế caching, rotation, network/private access và diagnostics.

### Technical Lead / Architect
Ưu tiên passwordless identity khi có thể và quản trị secret lifecycle như platform capability.

## 11. Key takeaway

- Managed Identity loại bỏ bootstrap credential khỏi Azure workload.
- Authentication và authorization vẫn là hai concern riêng.
- Nếu dependency hỗ trợ passwordless, cân nhắc bỏ secret thay vì chỉ lưu secret tốt hơn.

# 8. BackgroundService graceful shutdown: worker phải biết cách dừng đúng

## 1. What is it?

`BackgroundService` nhận cancellation signal khi host shutdown. Graceful shutdown nghĩa worker ngừng nhận work mới, hoàn tất hoặc abandon work đang giữ theo protocol an toàn, giải phóng resource và kết thúc trong shutdown budget.

## 2. Why does it exist?

Container restart, deployment, scale-in và node maintenance là hoạt động bình thường. Nếu worker chỉ được thiết kế cho steady state, shutdown giữa message có thể gây duplicate side effects, mất lock hoặc mất work.

## 3. How does it work?

```text
SIGTERM / host stopping
      -> stoppingToken cancelled
      -> stop fetching new work
      -> finish/settle current work OR abandon safely
      -> Dispose resources
      -> process exits before grace period
```

Cancellation là cooperative; token không “giết” method. Code phải observe và propagate token.

## 4. Practical implementation

```csharp
public sealed class InvoiceWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var job = await ReceiveAsync(stoppingToken);
            if (job is null) continue;

            await ProcessIdempotentlyAsync(job, stoppingToken);
            await CompleteAsync(job, stoppingToken);
        }
    }
}
```

Trong thực tế, settlement khi shutdown có thể cần token/budget riêng nếu host token đã cancelled; semantics phụ thuộc broker SDK. Quan trọng là không acknowledge trước khi durable side effects đạt trạng thái an toàn.

## 5. Real production scenario

Queue consumer xử lý invoice 20 giây. Kubernetes rollout gửi termination signal nhưng app không propagate cancellation tới HTTP/DB calls; pod bị kill giữa xử lý. Message được redeliver và invoice gửi email hai lần vì side effect không idempotent.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate work tăng đúng lúc deployments/scale-in.

**Telemetry** → correlate host shutdown, message lock/settlement và business idempotency key.

**Hypothesis** → shutdown vượt grace period hoặc acknowledge timing sai.

**Evidence** → structured logs theo message ID + lifecycle events.

**Remediation** → stop intake, propagate cancellation, idempotency, tune lock/shutdown budget.

**Verification** → kill/restart worker trong từng phase của processing.

## 7. Common mistakes

Nuốt `OperationCanceledException` như lỗi Production; không truyền token; dùng timer fire-and-forget; complete message trước side effect; shutdown timeout ngắn hơn legitimate operation; giả định graceful shutdown luôn được đảm bảo khi machine crash.

## 8. Alternatives

Azure Functions/managed consumers giảm một phần host lifecycle burden nhưng idempotency vẫn cần. Durable workflow engine phù hợp long-running stateful orchestration.

## 9. Trade-offs

Graceful completion giảm duplicates nhưng kéo dài deployments. Aggressive cancellation tăng rollout speed nhưng yêu cầu work dễ resume/retry hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu cancellation là cooperative.

### Middle
Propagate `CancellationToken` xuyên I/O calls.

### Senior
Thiết kế settlement, idempotency và shutdown budget.

### Technical Lead / Architect
Xem deployment/scale-in như failure scenario bắt buộc trong worker architecture.

## 11. Key takeaway

- Shutdown là normal lifecycle, không phải edge case.
- Stop intake trước, rồi xử lý in-flight work theo semantics rõ.
- Idempotency vẫn cần vì graceful shutdown không bao phủ crash đột ngột.

# 9. CDN Cache-Control: một response có nhiều cache layers

## 1. What is it?

`Cache-Control` là HTTP mechanism mô tả cacheability và freshness của response. Trong hệ thống có browser + CDN + reverse proxy, một header có thể ảnh hưởng nhiều cache layers, nhưng directives như `private`, `public`, `max-age`, `s-maxage`, `no-store` có semantics khác nhau.

## 2. Why does it exist?

Không có explicit caching contract, hệ thống hoặc không cache và lãng phí origin capacity, hoặc cache nhầm personalized/sensitive content. CDN chỉ hữu ích khi application định nghĩa được dữ liệu nào có thể reuse, trong bao lâu và ở scope nào.

## 3. How does it work?

```text
Browser
  | cache miss
  v
CDN edge
  | cache miss
  v
Origin

Cache-Control: public, max-age=60, s-maxage=300
browser freshness: 60s
shared-cache freshness: 300s
```

`Vary` làm cache key phụ thuộc request headers được chỉ định; dùng sai có thể phá hit ratio hoặc trộn variants.

## 4. Practical implementation

Static/versioned asset có thể cache dài:

```http
Cache-Control: public, max-age=31536000, immutable
```

Personal account response thường không nên shared-cache:

```http
Cache-Control: private, no-store
```

Public product content có thể dùng shared TTL phù hợp business freshness và purge strategy. Header phải xuất phát từ data semantics, không từ mong muốn “CDN nhanh hơn”.

## 5. Real production scenario

Product API được cache edge 10 phút. Giá thay đổi khẩn cấp nhưng không có purge/version strategy, khách thấy stale price. Vấn đề không phải CDN “sai”; cache freshness contract không phù hợp business requirement.

## 6. Failure scenario & troubleshooting

**Symptom** → user thấy content cũ hoặc cache hit ratio thấp.

**Telemetry** → browser DevTools, CDN cache status/age headers, origin request volume.

**Hypothesis** → TTL, cache key, `Vary`, cookie hoặc purge behavior sai.

**Evidence** → trace cùng URL qua browser/edge/origin.

**Remediation** → sửa cache policy/key/invalidation.

**Verification** → test warm hit, expiry, purge và personalized variants.

## 7. Common mistakes

Cache authenticated response ở shared edge; `Vary` theo high-cardinality header; cache-busting query string không có governance; TTL dài nhưng không có invalidation; `no-cache` và `no-store` bị hiểu như nhau; chỉ test local bỏ qua CDN.

## 8. Alternatives

Application/Redis cache giảm origin computation nhưng vẫn nhận network request. Browser cache giảm cả edge traffic. CDN phù hợp geographically distributed reusable responses/assets. Các layers giải quyết cost khác nhau.

## 9. Trade-offs

TTL dài tăng hit ratio và giảm latency/cost nhưng tăng stale window. Purge nhanh hơn tăng operational dependency vào CDN invalidation capability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu browser cache khác CDN cache.

### Middle
Đọc `Cache-Control`, `Age`, `Vary` và DevTools network.

### Senior
Thiết kế cache key, stale policy và invalidation theo business data.

### Technical Lead / Architect
Phân bổ caching responsibility xuyên browser → CDN → app → Redis → DB và định nghĩa ownership của freshness.

## 11. Key takeaway

- Cache policy là correctness contract trước khi là performance optimization.
- Shared cache không được trộn personalized/sensitive responses.
- TTL luôn phải đi cùng freshness và invalidation reasoning.

# 10. DDD Aggregate boundary: transaction mạnh chỉ nên bao quanh invariant thực sự cần cùng đúng

## 1. What is it?

Aggregate là một consistency boundary trong domain model: một cluster objects được thay đổi thông qua Aggregate Root và các invariants bên trong boundary được bảo vệ trong một transaction logic. Aggregate không đơn giản là object graph có quan hệ cha-con.

## 2. Why does it exist?

Nếu mọi related entity đều nằm trong một aggregate khổng lồ, mỗi command phải load/lock/update quá nhiều state và concurrency giảm. Nếu boundary quá nhỏ, invariant cần atomicity bị tách ra và application phải tự vá consistency.

## 3. How does it work?

```text
Command
  -> load Aggregate Root
  -> execute behavior
  -> validate invariant
  -> persist aggregate transaction
  -> publish domain/integration consequences
```

Giữa aggregates, eventual consistency thường được chấp nhận khi business invariant không yêu cầu atomic transaction.

## 4. Practical implementation

Ví dụ Order có thể sở hữu OrderLines vì total/quantity invariants cần được kiểm tra cùng Order. Customer không nhất thiết nằm trong Order aggregate chỉ vì Order có `CustomerId`.

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public void AddLine(ProductSnapshot product, int quantity)
    {
        if (quantity <= 0) throw new DomainException("Invalid quantity");
        _lines.Add(new OrderLine(product, quantity));
        RecalculateTotal();
    }
}
```

Boundary phải đến từ invariant và transaction need, không từ navigation convenience.

## 5. Real production scenario

Team model Customer là root chứa toàn bộ Orders. Updating một order cần load/customer version và tạo contention cho mọi orders của cùng customer. Thực tế invariant không yêu cầu tất cả orders atomic với customer profile. Tách Order aggregate giảm contention và ownership phức tạp.

## 6. Failure scenario & troubleshooting

**Symptom** → frequent concurrency conflicts, aggregate load rất lớn, một command chạm nhiều tables/entities không liên quan trực tiếp.

**Telemetry** → transaction duration, rows touched, conflict/deadlock patterns.

**Hypothesis** → aggregate boundary quá rộng.

**Evidence** → liệt kê invariant nào thật sự cần atomic consistency.

**Remediation** → tách boundary, dùng identity references và domain/integration events cho cross-boundary consequences.

**Verification** → concurrency tests và business-invariant tests.

## 7. Common mistakes

Aggregate = EF navigation graph; một aggregate cho cả bounded context; expose child entity để caller mutate trực tiếp; cross-aggregate transaction mặc định; dùng domain events để che boundary sai mà không xác định consistency requirement.

## 8. Alternatives

Transaction Script/Application Service phù hợp domain đơn giản. Database constraints bảo vệ invariants dữ liệu rất hiệu quả. Saga/process manager phù hợp business process kéo dài qua nhiều aggregates/services.

## 9. Trade-offs

Aggregate rõ giúp bảo vệ invariants và ownership nhưng có thể thêm domain-model ceremony. Boundary nhỏ tăng concurrency nhưng yêu cầu eventual consistency cho cross-boundary workflows.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu entity relationship không tự động quyết định aggregate.

### Middle
Đặt behavior qua root và giữ invariant trong boundary.

### Senior
Reason về transaction, concurrency và eventual consistency giữa aggregates.

### Technical Lead / Architect
Chọn aggregate boundaries dựa trên business invariants, contention và change ownership; không áp DDD tactical patterns khi domain không cần.

## 11. Key takeaway

- Aggregate là consistency/transaction boundary, không phải folder hay EF graph.
- Giữ boundary nhỏ nhất có thể nhưng đủ để bảo vệ invariant.
- Cross-aggregate workflow cần explicit consistency semantics.
