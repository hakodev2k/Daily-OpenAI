# 1. .NET ThreadPool starvation: khi async code vẫn làm server “đứng hình” vì blocking

## 1. What is it?

ThreadPool starvation xảy ra khi số worker threads khả dụng không đủ để phục vụ công việc đang chờ, thường vì nhiều thread bị block bởi synchronous I/O, `.Result`, `.Wait()`, lock dài hoặc CPU work chạy sai chỗ.

Mental model:

```text
request arrives
→ needs ThreadPool thread
→ thread blocks waiting I/O
→ more requests arrive
→ more threads block
→ queue grows
→ latency explodes
```

## 2. Why does it exist?

ASP.NET Core scale tốt nhờ asynchronous I/O: trong lúc chờ network/database, thread được trả về pool. Nếu code biến asynchronous wait thành blocking wait, lợi thế này mất đi.

## 3. How does it work?

`await` đúng cách thường giải phóng thread trong thời gian chờ I/O. Ngược lại:

```csharp
var result = httpClient.GetStringAsync(url).Result;
```

thread hiện tại bị giữ cho đến khi I/O hoàn tất. Dưới tải cao, ThreadPool phải tăng thread dần dần, nhưng tốc độ tăng có giới hạn; request queue vì thế có thể phình rất nhanh.

## 4. Practical implementation

Sai:

```csharp
public IActionResult Get()
{
    var data = service.LoadAsync().Result;
    return Ok(data);
}
```

Đúng:

```csharp
public async Task<IActionResult> Get(CancellationToken ct)
{
    var data = await service.LoadAsync(ct);
    return Ok(data);
}
```

CPU-bound work lớn không nên giả vờ là I/O async. Với workload nặng, cân nhắc queue/background processing hoặc bounded parallelism.

## 5. Real production scenario

Một API gọi ba third-party services. Developer dùng `.Result` vì muốn “code gọn”. Khi dependency chậm từ 100 ms lên 2 giây, worker threads bị giữ hàng loạt. CPU chỉ 30% nhưng p99 nhảy lên hàng chục giây.

## 6. Failure scenario & troubleshooting

**Symptom** → latency cao, request queue tăng, CPU không nhất thiết cao.

**Evidence** → ThreadPool queue length tăng, worker thread count tăng dần, stack traces cho thấy `.Wait()`/`.Result`/sync I/O.

**Hypothesis** → ThreadPool starvation.

**Diagnosis** → `dotnet-counters`, `dotnet-trace`, profiler, dump stacks.

**Fix** → async all the way, loại sync-over-async, giới hạn concurrency cho expensive work.

**Verification** → queue length giảm, p95/p99 ổn định dưới load.

## 7. Common mistakes

* Dùng `Task.Run` để “sửa” mọi blocking I/O.
* Cho rằng CPU thấp thì server không bị saturation.
* Dùng lock dài quanh I/O.
* Không propagate `CancellationToken`.

## 8. Alternatives

Với CPU-heavy work, queue worker hoặc dedicated processing service thường rõ ràng hơn việc đẩy tất cả lên ThreadPool request path.

## 9. Trade-offs

### Advantages

Async I/O đúng giúp throughput cao với ít threads.

### Costs / Risks

Async propagation làm call chain phức tạp hơn; cancellation và exception flow phải được thiết kế rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` không đơn giản là “chạy thread khác”.

### Middle

Biết tránh `.Result`/`.Wait()` trong request path.

### Senior

Nhận diện starvation từ telemetry thay vì chỉ nhìn CPU.

### Technical Lead / Architect

Thiết kế concurrency boundary và quyết định workload nào nên rời khỏi synchronous request-response path.

## 11. Key takeaway

* Blocking I/O phá mô hình scale của ASP.NET Core.
* CPU thấp không loại trừ ThreadPool starvation.
* Đo queue length, thread count và stack traces trước khi đoán.

# 2. ASP.NET Core `ProblemDetails`: thiết kế error contract ổn định thay vì trả exception text tùy tiện

## 1. What is it?

`ProblemDetails` là chuẩn hóa response lỗi HTTP theo cấu trúc machine-readable như `type`, `title`, `status`, `detail`, `instance` và các extension fields.

## 2. Why does it exist?

Nếu mỗi endpoint trả lỗi một kiểu, client phải viết logic đặc biệt cho từng API. Tệ hơn, trả raw exception message có thể leak implementation details hoặc secrets.

## 3. How does it work?

Một error contract ổn định tách hai thứ:

```text
internal exception / diagnostic detail
            ≠
public API error contract
```

Client cần mã lỗi ổn định; operations team cần trace/correlation để tìm chi tiết trong logs.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler();
```

Custom response:

```csharp
return Results.Problem(
    statusCode: StatusCodes.Status409Conflict,
    title: "Order state conflict",
    type: "https://api.example.com/problems/order-state-conflict",
    extensions: new Dictionary<string, object?>
    {
        ["code"] = "order_state_conflict",
        ["traceId"] = Activity.Current?.TraceId.ToString()
    });
```

Không expose stack trace cho public client.

## 5. Real production scenario

Frontend checkout cần phân biệt `payment_declined`, `inventory_changed`, `validation_failed`. Nếu chỉ nhận 400 với text tự do, UI phải parse string và sẽ vỡ khi message thay đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → client xử lý lỗi không nhất quán, support khó map lỗi UI sang backend trace.

**Evidence** → nhiều response shapes, message text bị dùng như code.

**Hypothesis** → thiếu error contract.

**Fix** → chuẩn hóa `ProblemDetails`, stable error code, trace ID.

**Verification** → contract tests đảm bảo shape/code không đổi ngoài ý muốn.

## 7. Common mistakes

* Dùng `detail` làm machine code.
* Trả stack trace ở Production.
* Dùng 200 cho business failure rồi nhét `success=false`.
* Mọi lỗi đều trả 500.

## 8. Alternatives

Custom envelope có thể dùng, nhưng nếu không có lý do đặc biệt, `ProblemDetails` giúp tránh phát minh format riêng.

## 9. Trade-offs

### Advantages

* Client integration ổn định hơn.
* Tách public contract khỏi diagnostic internals.

### Costs / Risks

* Cần governance cho error taxonomy.
* Versioning vẫn cần nếu semantics thay đổi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code và body lỗi là hai phần của contract.

### Middle

Biết mapping exception/business failure sang response phù hợp.

### Senior

Thiết kế stable error codes và observability correlation.

### Technical Lead / Architect

Định nghĩa error taxonomy dùng xuyên services, tránh coupling client với implementation detail.

## 11. Key takeaway

* Error response là public contract.
* Client nên phụ thuộc stable code, không phụ thuộc message text.
* Internal diagnostics thuộc logs/traces, không thuộc public response.

# 3. EF Core `SaveChanges` batching: giảm round-trip nhưng không biến ORM thành bulk engine

## 1. What is it?

EF Core có thể gom nhiều INSERT/UPDATE/DELETE commands trong một `SaveChanges` thành batches để giảm database round-trips.

## 2. Why does it exist?

Nếu 100 thay đổi đồng nghĩa 100 network round-trips thì latency tăng mạnh. Batching giảm protocol overhead và tận dụng một transaction hiệu quả hơn.

## 3. How does it work?

Flow:

```text
Change Tracker
→ detect modified entities
→ generate SQL commands
→ group commands into batches
→ send batches
→ database executes
→ affected rows validated
```

Nhưng EF vẫn track từng entity và tạo command semantics riêng; nó không phải bulk loader chuyên dụng.

## 4. Practical implementation

```csharp
foreach (var item in items)
{
    db.OrderLines.Add(new OrderLine
    {
        OrderId = orderId,
        ProductId = item.ProductId,
        Quantity = item.Quantity
    });
}

await db.SaveChangesAsync(ct);
```

Với update set-based, EF Core có thể dùng:

```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Expired)
    .ExecuteUpdateAsync(
        s => s.SetProperty(x => x.Status, OrderStatus.Archived),
        ct);
```

## 5. Real production scenario

Import 100.000 rows qua tracked entities làm memory tăng mạnh dù batching tồn tại. Bottleneck chuyển từ network sang change tracking, allocations và generated commands.

## 6. Failure scenario & troubleshooting

**Symptom** → import chậm, memory cao, GC nhiều.

**Evidence** → ChangeTracker chứa hàng chục nghìn entities; SQL round-trips không phải bottleneck duy nhất.

**Hypothesis** → ORM tracking overhead.

**Fix** → chunking, `ExecuteUpdate`, provider bulk APIs hoặc database-native bulk loading.

**Verification** → đo rows/sec, memory, round-trips trước/sau.

## 7. Common mistakes

* Nghĩ một `SaveChanges` = một SQL statement.
* Giữ một `DbContext` tracking hàng trăm nghìn entities.
* Dùng Add từng entity rồi kỳ vọng hiệu năng như `SqlBulkCopy`.
* Tối ưu batch size mà chưa đo bottleneck.

## 8. Alternatives

`SqlBulkCopy`, PostgreSQL `COPY`, bulk libraries, staging table + set-based merge.

## 9. Trade-offs

### Advantages

* Giảm round-trips với code ORM quen thuộc.
* Giữ lifecycle/change tracking semantics.

### Costs / Risks

* Tracking overhead vẫn tồn tại.
* Bulk workload rất lớn cần công cụ chuyên dụng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `SaveChanges` có thể phát nhiều SQL commands.

### Middle

Biết batching khác bulk insert.

### Senior

Đo tracking, network và database execution riêng.

### Technical Lead / Architect

Chọn ORM path hay bulk pipeline dựa trên volume, correctness và operational complexity.

## 11. Key takeaway

* Batching giảm round-trip, không xóa ORM overhead.
* Bulk workload cần đo theo rows/sec và memory.
* Set-based operations thường tốt hơn entity-by-entity cho mass update.

# 4. SQL Server isolation levels: Dirty Read, Non-repeatable Read, Phantom và lựa chọn đúng cho transaction

## 1. What is it?

Isolation level định nghĩa transaction được phép nhìn thấy thay đổi concurrent ở mức nào.

## 2. Why does it exist?

Concurrency và consistency luôn có trade-off. Isolation mạnh hơn giảm anomaly nhưng thường tăng locking/versioning overhead.

## 3. How does it work?

Các anomalies cơ bản:

```text
Dirty Read          → đọc dữ liệu chưa commit
Non-repeatable Read → cùng row đọc hai lần ra giá trị khác
Phantom             → cùng predicate đọc lại thấy thêm/bớt rows
```

`READ COMMITTED` phổ biến vì cân bằng tương đối tốt. `SNAPSHOT` dùng row versions để giảm reader/writer blocking, nhưng write conflicts vẫn tồn tại.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(
    IsolationLevel.Serializable,
    ct);

// critical read + write

await tx.CommitAsync(ct);
```

Không nâng lên `Serializable` chỉ vì “an toàn hơn”; hãy xác định invariant cần bảo vệ.

## 5. Real production scenario

Hai workers cùng đọc “còn 1 slot” rồi cùng insert booking. Nếu invariant chỉ được kiểm tra ở application với isolation không đủ mạnh và không có unique constraint, overbooking có thể xảy ra.

## 6. Failure scenario & troubleshooting

**Symptom** → blocking tăng mạnh sau khi nâng isolation.

**Evidence** → lock waits tăng, long-running transactions, throughput giảm.

**Hypothesis** → isolation mạnh hơn scope cần thiết.

**Fix** → thu nhỏ transaction, dùng constraint, optimistic concurrency hoặc snapshot semantics phù hợp.

**Verification** → concurrent tests kiểm tra invariant và lock metrics.

## 7. Common mistakes

* Dùng `NOLOCK` để chữa mọi blocking.
* Dùng `Serializable` mặc định cho mọi transaction.
* Không có DB constraint cho invariant quan trọng.
* Giữ transaction trong HTTP call.

## 8. Alternatives

Unique/check constraints, optimistic concurrency, application-level serialization, queueing cho workflow đặc thù.

## 9. Trade-offs

### Advantages

Isolation đúng bảo vệ correctness trong concurrency.

### Costs / Risks

Isolation mạnh có thể tăng blocking, deadlock hoặc version-store pressure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction concurrent có thể ảnh hưởng nhau.

### Middle

Biết anomalies cơ bản.

### Senior

Chọn isolation theo invariant và workload.

### Technical Lead / Architect

Kết hợp database constraints, transaction design và concurrency model thay vì dựa vào một setting duy nhất.

## 11. Key takeaway

* Isolation là correctness decision, không phải tuning flag.
* Stronger không luôn better.
* Invariant quan trọng nên được bảo vệ gần data source nhất có thể.

# 5. MongoDB embedding vs referencing: model theo access pattern thay vì mô phỏng relational schema

## 1. What is it?

Embedding lưu related data trong cùng document. Referencing lưu riêng documents và liên kết bằng identifier.

## 2. Why does it exist?

Document database tối ưu khi model phản ánh cách dữ liệu được đọc/ghi. Nếu copy relational normalization nguyên xi, bạn có thể tạo nhiều client-side joins và round-trips không cần thiết.

## 3. How does it work?

Embedding:

```text
Order
 ├─ CustomerSnapshot
 └─ Lines[]
```

phù hợp khi dữ liệu thường được đọc cùng nhau và lifecycle gần nhau.

Referencing phù hợp khi child có lifecycle độc lập, cardinality lớn hoặc được chia sẻ rộng.

## 4. Practical implementation

```json
{
  "_id": "order-123",
  "customer": {
    "id": "cust-9",
    "displayName": "Ha Nguyen"
  },
  "lines": [
    { "sku": "A1", "qty": 2, "price": 15.5 }
  ]
}
```

Đây là snapshot có chủ đích; không nhất thiết phải đồng bộ `displayName` mọi lúc với customer master record.

## 5. Real production scenario

Order history cần hiển thị tên khách hàng tại thời điểm mua. Embedding snapshot tránh dependency vào Customer service và giữ historical truth tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → document phình lớn, update một child array tốn kém.

**Evidence** → unbounded embedded collection.

**Hypothesis** → embedding sai lifecycle/cardinality.

**Fix** → tách collection, redesign access pattern, pagination/reference.

**Verification** → document size distribution, query count, latency và write amplification.

## 7. Common mistakes

* Normalize mọi thứ như SQL.
* Embed unbounded arrays.
* Duplicate data mà không định nghĩa ownership/freshness.
* Chọn schema trước khi biết query patterns.

## 8. Alternatives

SQL relational model nếu consistency/join-heavy workload là trọng tâm; Cosmos DB có partitioning/consistency economics khác MongoDB.

## 9. Trade-offs

### Advantages

Embedding giảm joins/round-trips và giữ aggregate gần nhau.

### Costs / Risks

Duplication, document growth, update complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu document không chỉ là row JSON hóa.

### Middle

Model theo read/write pattern.

### Senior

Đánh giá cardinality, lifecycle, consistency và document growth.

### Technical Lead / Architect

Chọn data model dựa trên domain ownership và operational workload, không theo trend SQL/NoSQL.

## 11. Key takeaway

* Document modeling bắt đầu từ access pattern.
* Embed khi lifecycle gần nhau và cardinality bounded.
* Duplication phải có semantics rõ ràng.

# 6. Timeout budget trong distributed systems: timeout cục bộ phải khớp với end-to-end latency budget

## 1. What is it?

Timeout budget là cách phân bổ tổng thời gian chấp nhận được của request cho từng dependency/hop thay vì để mỗi call tự đặt timeout tùy ý.

## 2. Why does it exist?

Nếu API có SLA 2 giây nhưng gọi ba dependency, mỗi dependency timeout 30 giây thì toàn hệ thống không có end-to-end control thực sự.

## 3. How does it work?

Ví dụ:

```text
Client budget: 2.0s
 ├─ API processing: 200ms
 ├─ Product API: 500ms
 ├─ Pricing API: 400ms
 ├─ DB: 300ms
 └─ safety margin: 600ms
```

Retry phải nằm trong cùng budget; không được cộng timeout mới vô hạn sau mỗi retry.

## 4. Practical implementation

```csharp
using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
timeoutCts.CancelAfter(TimeSpan.FromMilliseconds(500));

var response = await httpClient.GetAsync(
    requestUri,
    timeoutCts.Token);
```

Ở cấp resilience pipeline, timeout, retry và circuit breaker phải được compose theo thứ tự có chủ đích.

## 5. Real production scenario

Checkout API có p99 1.5 giây bình thường. Review service chậm 10 giây. Nếu request đợi đủ 10 giây, dependency phụ có thể phá toàn checkout SLA.

## 6. Failure scenario & troubleshooting

**Symptom** → cascading timeout, queue tăng, retry storm.

**Evidence** → downstream timeout lớn hơn upstream request timeout; retries nối tiếp.

**Hypothesis** → timeout budgets không đồng bộ.

**Fix** → end-to-end deadline, per-hop budget, bounded retry + jitter, graceful degradation.

**Verification** → dependency failure không đẩy p99 vượt budget ngoài mức thiết kế.

## 7. Common mistakes

* Timeout 100 giây cho mọi `HttpClient`.
* Retry mỗi lần với full timeout mới.
* Không distinguish optional vs critical dependency.
* Timeout nhưng không propagate cancellation xuống DB/HTTP.

## 8. Alternatives

Asynchronous messaging cho workflow không cần synchronous result; cache/fallback cho read dependencies; bulkhead để cô lập saturation.

## 9. Trade-offs

### Advantages

Giữ latency predictable và giảm failure propagation.

### Costs / Risks

Timeout quá ngắn gây false failure; quá dài gây resource retention.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout là correctness/reliability boundary, không chỉ config.

### Middle

Propagate cancellation/deadline đúng.

### Senior

Compose timeout + retry theo end-to-end budget.

### Technical Lead / Architect

Định nghĩa latency budget per dependency dựa trên business criticality và SLO.

## 11. Key takeaway

* Local timeout phải phục vụ end-to-end deadline.
* Retry tiêu tốn cùng một budget.
* Optional dependency không nên có quyền phá critical path.

# 7. Azure Blob Storage SAS: delegated access, blast radius và khi Managed Identity tốt hơn

## 1. What is it?

Shared Access Signature (SAS) cấp quyền giới hạn theo resource, operation và thời gian mà không đưa account key cho client.

## 2. Why does it exist?

Browser/mobile client đôi khi cần upload/download trực tiếp từ Blob Storage. Đưa storage account key xuống client là không chấp nhận được. SAS cho phép delegated access có thời hạn.

## 3. How does it work?

Flow upload trực tiếp:

```text
Client
→ API authenticates user
→ API authorizes upload
→ API issues short-lived SAS
→ Client uploads directly to Blob Storage
```

API không cần proxy toàn bộ file bytes.

## 4. Practical implementation

Server-side issuance cần scope hẹp: container/blob cụ thể, permission tối thiểu, expiry ngắn.

Với service-to-service, ưu tiên Managed Identity + RBAC thay vì phát SAS nếu caller là trusted Azure workload.

## 5. Real production scenario

CMS cho editor upload video 2 GB. Proxy qua web app làm tăng bandwidth, memory pressure và timeout. SAS cho phép direct upload nhưng API vẫn giữ quyền quyết định editor được upload vào path nào.

## 6. Failure scenario & troubleshooting

**Symptom** → SAS bị reuse ngoài dự kiến hoặc URL bị leak qua logs.

**Evidence** → expiry quá dài, permission rộng, token xuất hiện trong telemetry.

**Hypothesis** → delegated credential có blast radius quá lớn.

**Fix** → short expiry, blob-level scope, HTTPS only, scrub query strings khỏi logs.

**Verification** → expired token fail, wrong blob fail, write-only token không đọc được.

## 7. Common mistakes

* SAS expiry vài ngày cho upload tạm thời.
* Dùng account key ở application khi Managed Identity khả dụng.
* Log full SAS URL.
* Cấp container-wide write khi chỉ cần một blob.

## 8. Alternatives

Managed Identity cho backend workloads; API proxy cho file nhỏ/strict inspection; user delegation SAS thay vì account-key-based SAS khi phù hợp.

## 9. Trade-offs

### Advantages

Giảm load application và giữ delegated access bounded.

### Costs / Risks

SAS là bearer token: ai có token có thể dùng trong phạm vi được cấp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SAS không phải storage account key.

### Middle

Biết scope permission/expiry tối thiểu.

### Senior

Thiết kế secure upload flow và logging hygiene.

### Technical Lead / Architect

Chọn giữa SAS, Managed Identity và proxy dựa trên trust boundary, file size và compliance.

## 11. Key takeaway

* SAS là delegated credential, cần least privilege.
* Service-to-service thường nên dùng Managed Identity.
* Không log bearer credentials.

# 8. Kubernetes resource requests/limits: scheduling, throttling và vì sao CPU limit có thể làm p99 xấu đi

## 1. What is it?

`requests` mô tả lượng resource Pod cần để scheduler placement; `limits` đặt mức tối đa container được phép dùng.

## 2. Why does it exist?

Cluster cần biết Pod cần bao nhiêu CPU/memory để tránh overcommit vô kiểm soát. Nhưng config sai có thể trực tiếp tạo production latency.

## 3. How does it work?

CPU limit thường được thực thi bằng throttling. Memory limit vượt quá có thể dẫn tới OOM kill.

```text
CPU request → scheduling guarantee signal
CPU limit   → throttling ceiling
Memory limit → hard boundary, possible OOM kill
```

## 4. Practical implementation

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "1Gi"
```

Số này phải đến từ load/profile evidence, không phải copy từ template.

## 5. Real production scenario

API bình thường dùng 300m CPU nhưng lúc burst cần 1.5 core để giữ p99. Limit 500m khiến container bị throttled đúng lúc traffic tăng, dù node còn rất nhiều CPU trống.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 tăng khi traffic burst, CPU usage nhìn như “không vượt limit”.

**Evidence** → CPU throttling metrics tăng, node còn capacity.

**Hypothesis** → CPU limit quá thấp.

**Fix** → điều chỉnh requests/limits dựa trên measured workload, cân nhắc bỏ CPU limit theo platform policy nhưng giữ request phù hợp.

**Verification** → throttling giảm, p99 cải thiện, scheduler vẫn ổn định.

## 7. Common mistakes

* Requests = limits theo thói quen.
* Không set memory limit rồi để leak lan rộng.
* Tăng replicas khi bottleneck là CPU throttling.
* Copy values giữa services khác workload.

## 8. Alternatives

Vertical Pod Autoscaler hỗ trợ recommendation; HPA scale theo metrics; managed container platforms có abstraction khác nhưng bản chất capacity planning vẫn tồn tại.

## 9. Trade-offs

### Advantages

Resource controls tăng predictability và scheduling quality.

### Costs / Risks

Limit quá chặt gây throttling/OOM; request quá cao lãng phí cluster capacity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt request và limit.

### Middle

Biết đọc throttling/OOM signals.

### Senior

Capacity-plan dựa trên percentiles và burst behavior.

### Technical Lead / Architect

Định nghĩa cluster resource policy cân bằng reliability, density và cost.

## 11. Key takeaway

* CPU limit có thể làm latency xấu dù cluster còn rảnh.
* Memory limit là hard failure boundary quan trọng.
* Resource config phải dựa trên measurement.

# 9. Contract testing: bảo vệ integration boundary khi provider và consumer release độc lập

## 1. What is it?

Contract testing kiểm tra rằng provider vẫn đáp ứng shape/semantics mà consumer thực sự phụ thuộc, hoặc consumer assumptions vẫn phù hợp provider contract.

## 2. Why does it exist?

Unit tests của từng service có thể đều pass nhưng integration vẫn vỡ vì field rename, enum mới, status code thay đổi hoặc serialization semantics khác.

## 3. How does it work?

Consumer-driven contract flow:

```text
Consumer records expected interaction
→ contract artifact
→ provider verifies against contract
→ release blocked if breaking mismatch
```

Nó kiểm tra boundary, không thay thế toàn bộ E2E testing.

## 4. Practical implementation

Ví dụ đơn giản với integration test:

```csharp
var response = await client.GetAsync("/api/products/123");
response.EnsureSuccessStatusCode();

var body = await response.Content.ReadFromJsonAsync<ProductResponse>();
body.Should().NotBeNull();
body!.Id.Should().Be("123");
```

Ở quy mô nhiều teams, Pact hoặc schema-based validation có thể formalize contract lifecycle.

## 5. Real production scenario

Product API đổi `price` từ number thành object để hỗ trợ multi-currency. Backend tests pass, frontend build vẫn pass vì type generated cũ chưa update, Production fail runtime.

## 6. Failure scenario & troubleshooting

**Symptom** → integration chỉ vỡ sau deploy.

**Evidence** → provider change không được validate against real consumer expectations.

**Hypothesis** → missing boundary verification.

**Fix** → contract tests + compatibility policy + staged release.

**Verification** → provider CI chạy contracts của active consumers.

## 7. Common mistakes

* Contract test duplicate toàn business logic.
* Dùng snapshots khổng lồ khó review.
* Tin OpenAPI file tồn tại là đủ.
* Không quản version/consumer lifecycle.

## 8. Alternatives

E2E tests, shared schema validation, generated clients, backward-compatibility checks. Thường cần kết hợp chứ không chọn một tuyệt đối.

## 9. Trade-offs

### Advantages

Phát hiện breaking change sớm và nhanh hơn full E2E.

### Costs / Risks

Contract lifecycle và tooling thêm operational/process complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu integration có contract riêng ngoài code compile.

### Middle

Viết tests cho request/response assumptions quan trọng.

### Senior

Phân biệt contract, integration và E2E test responsibilities.

### Technical Lead / Architect

Thiết kế compatibility policy và release coordination giữa independently deployed systems.

## 11. Key takeaway

* Hai services test riêng đều xanh vẫn có thể tích hợp hỏng.
* Contract tests bảo vệ boundary, không thay thế E2E.
* Compatibility là release discipline, không chỉ schema format.

# 10. AI Structured Outputs: dùng schema để ép output machine-readable nhưng không nhầm với business correctness

## 1. What is it?

Structured Outputs ép model trả output theo schema xác định, giúp application parse dữ liệu đáng tin cậy hơn so với yêu cầu “hãy trả JSON” bằng prompt tự do.

## 2. Why does it exist?

LLM output tự nhiên có thể thiếu field, sai kiểu, thêm prose hoặc thay structure. Application integration cần deterministic envelope dù nội dung bên trong vẫn probabilistic.

## 3. How does it work?

Mental model:

```text
Prompt + schema
→ model generation constrained by schema
→ valid structured payload
→ deterministic application validation
→ business action
```

Schema compliance không chứng minh nội dung là đúng sự thật.

## 4. Practical implementation

Application nên validate tiếp các domain rules sau khi parse:

```csharp
public sealed record RefundDecision(
    string Decision,
    decimal Amount,
    string Reason);

if (result.Amount < 0 || result.Amount > order.PaidAmount)
{
    throw new InvalidOperationException("Invalid refund amount");
}
```

Model có thể trả đúng schema nhưng `Amount` vẫn sai business rule.

## 5. Real production scenario

AI agent triage support ticket và đề xuất refund. Structured output giúp parse `decision`, `amount`, `reason`; nhưng hệ thống tài chính vẫn phải enforce max refundable amount, currency, authorization và audit trail bằng deterministic code.

## 6. Failure scenario & troubleshooting

**Symptom** → JSON parse luôn thành công nhưng business action sai.

**Evidence** → schema valid, domain invariant violated.

**Hypothesis** → team nhầm syntax validity với semantic correctness.

**Fix** → deterministic validators, policy engine, human approval cho high-risk action.

**Verification** → adversarial/evaluation tests với edge cases và invalid business proposals.

## 7. Common mistakes

* Cho rằng schema = truthfulness.
* Để model quyết định authorization.
* Không version schema.
* Không log model/version/prompt metadata cần thiết cho evaluation.

## 8. Alternatives

Function Calling/Tool Calling khi mục tiêu là hành động; plain text khi chỉ cần human-readable answer; rules engine cho deterministic decision logic.

## 9. Trade-offs

### Advantages

* Parsing reliable hơn.
* Contract giữa model và application rõ hơn.
* Dễ test/evaluate hơn.

### Costs / Risks

* Nội dung vẫn probabilistic.
* Schema quá chặt có thể giảm flexibility.
* High-risk decisions vẫn cần deterministic guardrails.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu structured output đảm bảo shape, không đảm bảo truth.

### Middle

Biết parse + validate domain rules.

### Senior

Thiết kế evaluation, failure handling và safe tool boundaries.

### Technical Lead / Architect

Quyết định phần nào giao cho model, phần nào phải nằm trong deterministic application logic và human approval.

## 11. Key takeaway

* Structured Outputs giải quyết format reliability.
* Business correctness vẫn cần deterministic validation.
* Không giao authorization, money movement hoặc destructive action cho unconstrained model judgment.
