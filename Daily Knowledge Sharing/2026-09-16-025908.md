# 1. C# `TimeProvider`: tách business time khỏi system clock để code deterministic và testable

## 1. What is it?

`TimeProvider` là abstraction thời gian của modern .NET. Mental model quan trọng: business code không nên phụ thuộc trực tiếp vào “đồng hồ của máy đang chạy”; nó nên phụ thuộc vào một nguồn thời gian có thể thay thế.

`TimeProvider.System` cung cấp thời gian thật. Trong test, một controllable provider cho phép tiến thời gian mà không `Thread.Sleep`.

## 2. Why does it exist?

Code gọi `DateTime.UtcNow` ở nhiều nơi tạo hidden dependency. Test logic expiry, retry window, subscription renewal hoặc scheduled state transition trở nên phụ thuộc wall clock, chậm và flaky.

Abstraction này biến time thành explicit dependency, giống database hoặc HTTP client.

## 3. How does it work?

Application đọc clock thông qua provider. Production inject system provider; test inject fake provider. Business rule chỉ biết “now”, không biết đồng hồ đến từ OS hay test harness.

Quan trọng: lưu instant bằng UTC/`DateTimeOffset`; timezone conversion là concern khác. Không dùng local server time làm business truth.

## 4. Practical implementation

```csharp
builder.Services.AddSingleton(TimeProvider.System);

public sealed class TrialPolicy(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => timeProvider.GetUtcNow() >= expiresAt;
}
```

Test có thể dùng `FakeTimeProvider` từ `Microsoft.Extensions.TimeProvider.Testing` và advance clock thay vì chờ thật.

## 5. Real production scenario

Một SaaS cho phép payment authorization tồn tại 15 phút. API, background worker và test suite đều dùng cùng semantics UTC. Worker restart không làm thay đổi rule vì expiry được persist dưới dạng instant, không dựa vào process uptime.

## 6. Failure scenario & troubleshooting

**Symptom:** test expiry thỉnh thoảng fail quanh boundary. **Evidence:** code gọi `DateTime.Now` nhiều lần và CI chạy ở timezone khác. **Hypothesis:** wall-clock dependency + local timezone. **Diagnosis:** log instant và timezone, freeze test clock. **Fix:** inject `TimeProvider`, persist UTC. **Verification:** chạy test lặp lại và advance fake clock qua chính xác boundary.

## 7. Common mistakes

- Wrap `DateTime.UtcNow` bằng một interface riêng trong mọi project dù framework abstraction đã đủ.
- Trộn UTC instant với local display time.
- Dùng `Thread.Sleep` để test timeout.
- Cho domain tự đọc static clock, khiến dependency bị ẩn.

## 8. Alternatives

Một `IClock` rất nhỏ vẫn hợp lý trong legacy code hoặc khi cần domain-specific contract. `Stopwatch` phù hợp đo elapsed time, không phù hợp biểu diễn business timestamp.

## 9. Trade-offs

### Advantages

Deterministic tests, explicit dependency, dễ mô phỏng expiry/timeouts và giảm timezone bugs.

### Costs / Risks

Thêm dependency vào constructor; migration code cũ cần kỷ luật để không tiếp tục gọi static clock trực tiếp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt UTC instant, local time và elapsed duration.

### Middle

Inject clock, viết deterministic test cho expiry và boundary conditions.

### Senior

Nhận diện clock skew, DST, persistence semantics và những rule không nên dựa vào wall clock.

### Technical Lead / Architect

Chuẩn hóa time semantics xuyên service, database và event contracts; quyết định khi abstraction framework là đủ thay vì tạo thêm layer.

## 11. Key takeaway

- Time là dependency, không phải global constant.
- Persist instant bằng UTC; timezone chủ yếu là presentation/business-calendar concern.
- Test thời gian bằng controllable clock, không bằng sleep.

# 2. ASP.NET Core Endpoint Filters: cross-cutting behavior ở endpoint boundary mà không biến middleware thành nơi chứa mọi logic

## 1. What is it?

Endpoint Filter bao quanh execution của Minimal API endpoint. Nó nằm sau routing, biết endpoint arguments và có thể chạy logic trước/sau handler.

Mental model: middleware xử lý HTTP pipeline rộng; endpoint filter xử lý concern gắn với endpoint invocation.

## 2. Why does it exist?

Nếu mọi validation, audit, tenant check hoặc endpoint-specific policy đều đưa vào middleware, middleware phải tự hiểu route metadata/body/arguments và nhanh chóng trở thành god layer. Ngược lại copy logic vào từng handler tạo duplication.

## 3. How does it work?

Request đi qua middleware → routing chọn endpoint → filter chain chạy → endpoint handler. Filter có thể inspect `EndpointFilterInvocationContext`, short-circuit hoặc gọi `next`.

Authorization quan trọng vẫn nên dùng authorization system/policies thay vì tự viết security framework trong filter.

## 4. Practical implementation

```csharp
public sealed class RequirePositiveIdFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var id = context.GetArgument<int>(0);
        if (id <= 0)
            return Results.ValidationProblem(new Dictionary<string, string[]>
            {
                ["id"] = ["Id must be positive."]
            });

        return await next(context);
    }
}

app.MapGet("/orders/{id:int}", GetOrder)
   .AddEndpointFilter<RequirePositiveIdFilter>();
```

## 5. Real production scenario

Một internal API có nhóm endpoints cần tenant metadata validation và consistent audit context. Filter dùng endpoint metadata để áp dụng đúng nhóm thay vì middleware parse path thủ công.

## 6. Failure scenario & troubleshooting

**Symptom:** endpoint trả 400 trước khi telemetry business được ghi. **Evidence:** trace cho thấy filter short-circuit. **Hypothesis:** filter order sai. **Diagnosis:** inspect registered chain và structured logs ở mỗi boundary. **Fix:** sắp xếp validation/audit đúng semantics. **Verification:** integration test cả success và short-circuit paths.

## 7. Common mistakes

- Dùng filter thay middleware cho global exception handling.
- Tự implement authentication/authorization trong filter.
- Filter gọi database cho mọi endpoint dù chỉ vài route cần.
- Phụ thuộc vào argument index quá mong manh khi signature thay đổi.

## 8. Alternatives

Middleware cho concern toàn pipeline; MVC filters cho controller/action; endpoint filters phù hợp Minimal APIs; explicit handler code tốt nhất khi logic không thật sự cross-cutting.

## 9. Trade-offs

### Advantages

Context gần endpoint hơn middleware, reusable, hỗ trợ short-circuit rõ ràng.

### Costs / Risks

Thêm execution layer, ordering complexity và có thể che business rule nếu lạm dụng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu middleware và endpoint filter chạy ở hai boundary khác nhau.

### Middle

Implement validation/audit filter và integration test pipeline.

### Senior

Phân biệt transport concern, security policy và business invariant; debug ordering/short-circuit.

### Technical Lead / Architect

Quy định concern nào thuộc global pipeline, endpoint boundary hay application layer để tránh framework coupling lan vào domain.

## 11. Key takeaway

- Chọn extension point theo boundary, không theo sự tiện tay.
- Endpoint Filter không thay thế authorization system hay domain validation.
- Cross-cutting abstraction chỉ đáng có khi duplication thực sự tồn tại.

# 3. EF Core Temporal Tables: audit và point-in-time recovery ở database boundary

## 1. What is it?

SQL Server temporal table tự giữ historical row versions trong history table khi dữ liệu được update/delete. EF Core có mapping/query support để truy vấn trạng thái tại một thời điểm hoặc khoảng thời gian.

## 2. Why does it exist?

Audit history tự viết trong application dễ bị bỏ sót ở bulk SQL, admin script hoặc code path mới. Temporal tables đưa row-version history xuống database boundary.

Nó không thay thế domain audit event: temporal history trả lời “row từng có giá trị gì”, không nhất thiết trả lời “ai làm, tại sao, business intent gì”.

## 3. How does it work?

SQL Server duy trì period columns và chuyển old row vào history table khi mutation xảy ra. Current table vẫn phục vụ normal query; temporal query hợp nhất lịch sử theo system time.

Transaction boundary vẫn là database transaction của mutation.

## 4. Practical implementation

```csharp
modelBuilder.Entity<Employee>()
    .ToTable("Employees", b => b.IsTemporal());

var snapshot = await db.Employees
    .TemporalAsOf(pointInTime)
    .AsNoTracking()
    .SingleAsync(x => x.Id == employeeId);
```

Migration cần được review kỹ vì enable temporal trên bảng lớn có operational impact.

## 5. Real production scenario

HR platform cần điều tra salary grade trước một accidental bulk update. Temporal query khôi phục row state tại 09:00 mà không restore toàn database backup.

## 6. Failure scenario & troubleshooting

**Symptom:** history table tăng hàng trăm GB. **Evidence:** storage growth và update-heavy workload. **Hypothesis:** retention chưa được thiết kế. **Diagnosis:** đo history growth theo table, mutation frequency và retention requirement. **Fix:** policy retention/archive phù hợp. **Verification:** monitor storage và point-in-time queries sau cleanup.

## 7. Common mistakes

- Coi temporal table là complete audit trail.
- Không thiết kế retention.
- Query history qua tracking DbContext như current entities.
- Enable trên bảng hot/large mà không đánh giá migration và storage.

## 8. Alternatives

Application audit log cho actor/reason; CDC cho downstream change processing; event sourcing khi event là source of truth; backup/PITR cho disaster recovery rộng hơn.

## 9. Trade-offs

### Advantages

History tự động, point-in-time query mạnh, ít phụ thuộc application path.

### Costs / Risks

Storage/write overhead, retention complexity và thiếu business intent.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu current row và historical versions là hai mục đích khác nhau.

### Middle

Map temporal table, query `TemporalAsOf`, viết migration/test.

### Senior

Đánh giá storage, indexing, retention, restore workflow và audit limitations.

### Technical Lead / Architect

Chọn temporal, audit log, CDC hay event sourcing dựa trên compliance/recovery/integration requirement thay vì gom tất cả vào một cơ chế.

## 11. Key takeaway

- Temporal history là database row history, không tự động là business audit.
- Retention và storage phải được thiết kế từ đầu.
- Dùng đúng công cụ cho audit, integration và disaster recovery.

# 4. PostgreSQL `JSONB` + GIN index: linh hoạt schema nhưng vẫn phải thiết kế access pattern

## 1. What is it?

`JSONB` lưu JSON ở binary representation có thể query/index. GIN index phù hợp membership/containment operations trên nhiều keys/values.

Mental model: đây là relational database có một document-shaped column, không phải lý do để bỏ schema design.

## 2. Why does it exist?

Một số attributes biến đổi theo product type hoặc integration payload khiến hàng trăm nullable columns khó quản lý. `JSONB` cho phép giữ core relational fields ổn định và phần sparse/extensible linh hoạt.

## 3. How does it work?

Query containment như `attributes @> '{"color":"black"}'` có thể dùng GIN index. Nhưng expression, operator class và selectivity quyết định plan. Query → planner → index/heap I/O → locks/concurrency → latency vẫn là chuỗi reasoning cần kiểm tra.

## 4. Practical implementation

```sql
CREATE TABLE product (
    id bigint PRIMARY KEY,
    sku text NOT NULL UNIQUE,
    attributes jsonb NOT NULL DEFAULT '{}'::jsonb
);

CREATE INDEX ix_product_attributes_gin
ON product USING gin (attributes);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, sku
FROM product
WHERE attributes @> '{"color":"black"}'::jsonb;
```

Đừng chỉ thấy “Index Scan” rồi kết luận nhanh; đọc actual rows, buffers và latency.

## 5. Real production scenario

Marketplace có common columns `sku`, `price`, `brand`, còn category-specific attributes như RAM, engine size hoặc material nằm trong `JSONB`. Những field filter thường xuyên có thể được promote thành typed columns khi access pattern ổn định.

## 6. Failure scenario & troubleshooting

**Symptom:** product filter p95 tăng mạnh. **Evidence:** `EXPLAIN ANALYZE` cho thấy nhiều heap pages và low-selectivity predicate. **Hypothesis:** GIN index quá rộng/không phù hợp operator. **Diagnosis:** kiểm tra operator, statistics, result cardinality và buffers. **Fix:** expression index/typed column hoặc redesign query. **Verification:** so actual plan/I/O trước-sau dưới realistic data volume.

## 7. Common mistakes

- Nhét mọi column vào JSONB để “schema-less”.
- Không validate shape.
- Tạo GIN index rồi giả định mọi JSON query đều nhanh.
- Dùng JSON cho relational keys/constraints quan trọng.

## 8. Alternatives

Typed columns + normal indexes; child attribute table; dedicated document database khi aggregate/access pattern thật sự document-centric.

## 9. Trade-offs

### Advantages

Schema flexibility, containment query tốt, giữ PostgreSQL transaction/relational capabilities.

### Costs / Risks

Index size/write amplification, weaker type constraints và query/index reasoning phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu JSONB không loại bỏ nhu cầu schema.

### Middle

Viết containment query, GIN index và đọc `EXPLAIN ANALYZE` cơ bản.

### Senior

Đánh giá cardinality, buffers, write cost, validation và promote hot fields.

### Technical Lead / Architect

Quyết định relational core + JSON extension hay document store dựa trên ownership, transaction và access patterns.

## 11. Key takeaway

- JSONB là flexibility tool, không phải schema escape hatch.
- Index phải khớp operator và access pattern.
- Đo execution plan/I/O trước khi “thêm index”.

# 5. Domain Event vs Integration Event: cùng là “event” nhưng khác transaction boundary và ownership

## 1. What is it?

Domain Event mô tả điều đã xảy ra có ý nghĩa bên trong một domain/bounded context. Integration Event là contract được publish ra ngoài boundary để hệ thống khác phản ứng.

Không nên coi chúng là cùng một DTO chỉ vì tên đều kết thúc bằng `Event`.

## 2. Why does it exist?

Domain model cần phản ứng với business facts mà không coupling aggregate trực tiếp. Hệ thống phân tán cần contract ổn định để giao tiếp. Hai áp lực khác nhau tạo ra hai loại event với lifecycle khác nhau.

## 3. How does it work?

```text
Aggregate -> Domain Event -> same bounded context
                         -> application handler
                         -> Outbox record
                         -> Integration Event -> broker -> external consumer
```

Domain event có thể nằm trong transaction/application unit. Integration event vượt process/network boundary, nên phải giả định at-least-once delivery, versioning, retry và eventual consistency.

Responsibilities: domain sở hữu invariant; application chuyển business outcome thành integration contract; infrastructure publish. Data ownership không chuyển chỉ vì consumer nhận event.

## 4. Practical implementation

```csharp
public sealed record OrderPaid(Guid OrderId, decimal Amount); // domain event

public sealed record OrderPaymentConfirmedV1(
    Guid OrderId,
    decimal Amount,
    DateTimeOffset OccurredAt); // integration contract
```

Handler map domain event thành outbox message trong cùng database transaction; publisher gửi sau commit.

## 5. Real production scenario

Checkout đánh dấu order paid. Inventory và notification cần biết, nhưng không được join trực tiếp database của Checkout. Integration event cung cấp contract; duplicate consumer processing được xử lý idempotently.

## 6. Failure scenario & troubleshooting

**Symptom:** DB đã commit paid nhưng broker không có event. **Evidence:** transaction log có update, không có outbound message. **Hypothesis:** dual-write gap. **Diagnosis:** kiểm tra publish nằm ngoài transaction. **Fix:** transactional outbox. **Verification:** fault-injection giữa commit/publish và confirm eventual delivery.

## 7. Common mistakes

- Publish domain object trực tiếp ra broker.
- Integration event chứa toàn bộ internal entity.
- Consumer giả định exactly-once.
- Version contract theo implementation class thay vì consumer compatibility.

## 8. Alternatives

Synchronous REST khi cần immediate response và coupling chấp nhận được; CDC cho data-change integration; đơn giản gọi application service nội bộ nếu chưa vượt bounded context.

## 9. Trade-offs

### Advantages

Boundary rõ, giảm temporal coupling, hỗ trợ independent deployment.

### Costs / Risks

Eventual consistency, schema governance, duplicate delivery và observability phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt in-process business notification với distributed message.

### Middle

Implement handlers, outbox mapping và idempotent consumer.

### Senior

Thiết kế versioning, retries, ordering và failure recovery.

### Technical Lead / Architect

Xác định bounded context/data ownership/transaction boundary; chỉ dùng integration events khi independent boundary thực sự mang lại giá trị.

## 11. Key takeaway

- Domain Event và Integration Event có boundary/lifecycle khác nhau.
- Crossing network boundary biến failure model thành distributed systems problem.
- Không publish internal domain model như public contract.

# 6. Azure SQL Failover Groups: database failover không đồng nghĩa application tự động resilient

## 1. What is it?

Azure SQL Failover Groups cung cấp replication/failover giữa logical servers/regions và listener endpoint để application không phải hard-code từng database server khi failover.

## 2. Why does it exist?

Regional failure không thể được giải quyết chỉ bằng local database HA. Nhưng replication + DNS/listener mới chỉ giải quyết database placement; application còn connection pools, retry, transaction semantics và dependent services.

## 3. How does it work?

Primary replicate sang secondary. Khi failover, listener chuyển target. Existing connections có thể fail; client phải reconnect. Replication có thể asynchronous nên RPO không mặc định bằng zero.

Identity, firewall/private networking và DNS phải hoạt động ở cả hai region. Monitoring phải quan sát replication/failover state, không chỉ API health.

## 4. Practical implementation

```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(
        connectionString,
        sql => sql.EnableRetryOnFailure(
            maxRetryCount: 5,
            maxRetryDelay: TimeSpan.FromSeconds(10),
            errorNumbersToAdd: null)));
```

Retry chỉ dành cho transient failures. Business transaction có side effects ngoài DB cần idempotency/reconciliation, không được retry mù.

## 5. Real production scenario

SaaS chạy active/passive giữa Southeast Asia và East Asia. App region failover thành công nhưng API vẫn lỗi vì secondary region thiếu Key Vault/private DNS rule. Database HA không cứu được dependency graph chưa được diễn tập.

## 6. Failure scenario & troubleshooting

**Symptom:** sau failover, connection error tăng 5 phút. **Evidence:** database role đã đổi nhưng clients còn failed/stale connections. **Hypothesis:** reconnect/DNS/network path. **Diagnosis:** kiểm tra listener resolution, pool errors, firewall/private endpoint và retry telemetry. **Fix:** resilient reconnect + symmetric networking/configuration. **Verification:** planned failover game day đo RTO/RPO thực tế.

## 7. Common mistakes

- Gọi architecture là multi-region chỉ vì database có replica.
- Giả định zero data loss.
- Retry transaction chứa non-idempotent external call.
- Không test failback.

## 8. Alternatives

Zone-redundant/local HA cho requirement nhỏ hơn; geo-replication với custom topology; Cosmos DB cho workload cần distribution model khác. Đừng chọn cross-region nếu business RTO/RPO không justify cost.

## 9. Trade-offs

### Advantages

Managed geo failover, stable listener abstraction, giảm manual recovery.

### Costs / Risks

Cross-region cost/latency, possible replication lag, networking/config duplication và operational testing burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu failover làm existing connections fail và cần reconnect.

### Middle

Cấu hình client resiliency, health checks và connection telemetry.

### Senior

Phân tích RTO/RPO, retry safety, DNS/networking và dependency readiness.

### Technical Lead / Architect

Thiết kế whole-system regional recovery, ownership/runbook/game day và quyết định mức HA phù hợp business impact/cost.

## 11. Key takeaway

- Database failover chỉ là một phần của application resilience.
- Retry phải hiểu transaction/side-effect semantics.
- RTO/RPO phải được đo qua diễn tập, không suy ra từ sơ đồ kiến trúc.

# 7. RED + USE metrics: điều tra production từ user symptom đến resource saturation

## 1. What is it?

RED tập trung vào service behavior: Rate, Errors, Duration. USE tập trung resource: Utilization, Saturation, Errors.

Hai mental models bổ sung nhau: RED cho biết user đang chịu gì; USE giúp tìm resource nào đang nghẽn.

## 2. Why does it exist?

Dashboard chỉ có CPU/memory dễ bỏ sót dependency latency; dashboard chỉ có request count lại khó localize saturation. Incident response cần chuyển từ symptom sang evidence có cấu trúc.

## 3. How does it work?

Logs cung cấp event detail, metrics cho trend/alert, traces cho causal path, alerts kích hoạt response. Với OpenTelemetry/Application Insights, correlate request duration với dependency span và runtime metrics.

Flow: error/latency SLO alert → RED endpoint → trace dependency → USE database/thread pool/CPU → hypothesis.

## 4. Practical implementation

```csharp
builder.Services.AddOpenTelemetry()
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddRuntimeInstrumentation())
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation());
```

Alert nên ưu tiên user impact như error rate/p95/p99, sau đó dùng resource metrics để diagnose.

## 5. Real production scenario

Checkout p99 tăng từ 800 ms lên 6 s nhưng CPU chỉ 35%. Trace cho thấy SQL span chiếm 5 s; DB metrics cho thấy connection pool saturation. CPU dashboard một mình sẽ dẫn team sai hướng.

## 6. Failure scenario & troubleshooting

**Symptom:** p95 tăng. **Evidence:** RED xác nhận chỉ `/checkout`; trace chỉ DB dependency; USE cho thấy pool wait tăng. **Hypothesis:** connections giữ quá lâu. **Diagnosis:** correlate slow transactions/query duration. **Fix:** giảm transaction scope/query latency hoặc điều chỉnh pool sau khi tìm root cause. **Verification:** load test và so p95/p99 + pool wait.

## 7. Common mistakes

- Alert mọi metric threshold.
- Dùng average latency thay percentile.
- Log không correlation.
- Tăng pool size trước khi tìm vì sao connection bị giữ.

## 8. Alternatives

Golden Signals gần với RED nhưng thêm saturation; domain-specific SLI vẫn cần cho workflow quan trọng. Framework không quan trọng bằng việc telemetry trả lời được incident question.

## 9. Trade-offs

### Advantages

Điều tra có hệ thống, giảm guessing, nối user impact với infrastructure evidence.

### Costs / Risks

Telemetry cost/cardinality, dashboard sprawl và alert fatigue nếu instrumentation thiếu governance.

## 10. Junior → Middle → Senior → Technical Lead

# 8. Trunk-Based Development + Feature Flags: tách deploy khỏi release nhưng phải quản lý flag debt

## 1. What is it?

Trunk-Based Development giữ branch sống ngắn và tích hợp thường xuyên vào trunk. Feature Flag cho phép code đã deploy nhưng behavior chưa được bật cho toàn bộ user.

Deploy là đưa artifact vào environment; release là expose capability. Hai việc có thể tách nhau.

## 2. Why does it exist?

Long-lived branches tạo integration drift và merge pain. Nhưng merge incomplete feature trực tiếp vào trunk có thể expose behavior chưa sẵn sàng. Flags tạo runtime control để giữ trunk releasable.

## 3. How does it work?

Commit → build → unit/integration tests → immutable artifact → deploy → health validation → flag off → targeted enable → monitor → wider rollout → remove flag.

Rollback code vẫn cần; flag chỉ là một kill switch cho behavior phù hợp, không thay thế deployment safety.

## 4. Practical implementation

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
{
    return await newCheckout.ExecuteAsync(ct);
}

return await legacyCheckout.ExecuteAsync(ct);
```

Flag phải có owner, expiry/removal date và telemetry theo variant.

## 5. Real production scenario

Team deploy checkout algorithm mới cho 5% internal users, sau đó 10% production traffic. Error rate tăng nên disable flag trong vài giây mà không redeploy artifact.

## 6. Failure scenario & troubleshooting

**Symptom:** production behavior khác staging dù cùng commit. **Evidence:** flag configuration khác. **Hypothesis:** configuration drift. **Diagnosis:** audit flag state/version/targeting. **Fix:** environment governance + change audit. **Verification:** smoke tests cho cả flag on/off và telemetry dimension theo variant.

## 7. Common mistakes

- Flag tồn tại vĩnh viễn.
- Nested flags tạo exponential state combinations.
- Dùng flag để che database migration không backward-compatible.
- Không test old/new paths.

## 8. Alternatives

Short-lived feature branches nếu integration cadence vẫn nhanh; Blue-Green/Canary điều khiển deployment traffic thay vì application behavior. Nhiều team cần phối hợp cả hai nhưng không nên thêm machinery nếu release đơn giản.

## 9. Trade-offs

### Advantages

Small integrations, giảm merge risk, progressive release và fast kill switch.

### Costs / Risks

Runtime branching, config governance, test matrix và stale flag debt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt merge, deploy và release.

### Middle

Implement/test flag on/off và giữ commits nhỏ.

### Senior

Thiết kế backward-compatible rollout, telemetry và flag cleanup.

### Technical Lead / Architect

Thiết kế release flow end-to-end, giới hạn flag complexity và đảm bảo database/API compatibility xuyên versions.

## 11. Key takeaway

- Trunk-based cần releasable trunk, không có nghĩa mọi feature phải visible ngay.
- Feature flag là temporary release mechanism, không phải permanent architecture.
- CI/CD vẫn phải validate artifact, health, monitoring và rollback.

# 9. CSRF + `SameSite` cookies: vì sao authenticated browser request vẫn có thể bị giả mạo

## 1. What is it?

CSRF xảy ra khi browser tự động gửi credentials như cookies tới trusted site trong một request do attacker-controlled site kích hoạt. Server thấy cookie hợp lệ nhưng không biết user có chủ ý tạo request hay không.

`SameSite` là browser cookie control giúp hạn chế cross-site cookie sending; anti-forgery token cung cấp request-intent proof bổ sung.

## 2. Why does it exist?

Cookie authentication tiện vì browser tự attach cookie. Chính automation đó tạo attack surface. Authentication trả lời “credential của ai”; nó không luôn trả lời “request này có được user/site hợp lệ chủ động tạo hay không”.

## 3. How does it work?

Attacker page có thể submit form tới victim origin. Nếu browser attach auth cookie và endpoint chấp nhận request, side effect có thể xảy ra. `SameSite=Lax/Strict`, anti-forgery token, Origin/Referer validation trong một số design và correct HTTP semantics giảm risk.

CORS không phải CSRF protection tổng quát: browser có thể gửi một số cross-origin requests dù JavaScript không được phép đọc response.

## 4. Practical implementation

```csharp
builder.Services.AddAntiforgery(options =>
{
    options.HeaderName = "X-CSRF-TOKEN";
});
```

Cookie-authenticated state-changing endpoints cần anti-forgery strategy phù hợp. Bearer token trong explicit `Authorization` header có threat model khác vì browser không tự attach token như cookie.

## 5. Real production scenario

Admin portal dùng cookie auth. Endpoint `POST /users/{id}/disable` không validate anti-forgery token. Admin đang login mở malicious page; form cross-site trigger action bằng session cookie hiện tại.

## 6. Failure scenario & troubleshooting

**Symptom:** state-changing requests hợp lệ về authentication nhưng không có corresponding UI trace. **Evidence:** request Origin/Referer bất thường và thiếu anti-forgery header. **Hypothesis:** CSRF. **Diagnosis:** review cookie `SameSite`, endpoint method và anti-forgery enforcement. **Fix:** token + secure cookie policy + correct methods. **Verification:** security integration test từ cross-site context.

## 7. Common mistakes

- Nghĩ CORS block request nên không cần CSRF defense.
- Dùng GET cho state-changing operation.
- Đặt `SameSite=None` không hiểu lý do.
- Disable anti-forgery vì SPA gọi API bị 400 thay vì thiết kế token flow đúng.

## 8. Alternatives

Bearer-token APIs không dựa vào automatically attached cookie giảm classic CSRF nhưng tăng XSS/token-storage concerns. SameSite alone có thể không đủ cho mọi compatibility/integration requirement.

## 9. Trade-offs

### Advantages

Giảm unauthorized side effects trong cookie-authenticated browser flows.

### Costs / Risks

Thêm token lifecycle/client integration; strict cookie policy có thể phá legitimate cross-site SSO/payment flows.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu authentication và request intent là hai vấn đề khác nhau.

### Middle

Cấu hình anti-forgery và test state-changing endpoints.

### Senior

Phân tích cookie attributes, SPA/BFF flows, CORS misconceptions và XSS interaction.

### Technical Lead / Architect

Chọn browser auth architecture và security boundary dựa trên threat model, third-party redirects và operational constraints.

## 11. Key takeaway

- Cookie tự động được gửi là nguồn gốc classic CSRF risk.
- CORS không thay anti-forgery protection.
- Security design phải xét cả CSRF, XSS, cookie attributes và auth architecture.

# 10. Cosmos DB Change Feed: xây asynchronous projection mà không biến database thành message broker tùy tiện

## 1. What is it?

Cosmos DB Change Feed là ordered stream các changes trong logical partition, cho phép processor đọc thay đổi và xây projection/integration workflow bất đồng bộ.

Mental model: đây là change stream của data store, không phải transactional event contract tự động có đầy đủ business semantics.

## 2. Why does it exist?

Polling toàn collection để tìm record mới vừa tốn RU vừa tạo latency. Change Feed cung cấp incremental processing và checkpoint/lease coordination cho distributed consumers.

## 3. How does it work?

Writer cập nhật item → Cosmos persist → change feed expose change → processor instances chia lease ranges → handler xử lý batch → checkpoint tiến lên.

Scale-out dựa trên partition/lease distribution. Consumer phải idempotent vì retries/reprocessing có thể xảy ra. Partition key ảnh hưởng cả write distribution lẫn processing parallelism.

## 4. Practical implementation

```csharp
ChangeFeedProcessor processor = container
    .GetChangeFeedProcessorBuilder<Order>(
        "search-projection",
        async (changes, ct) =>
        {
            foreach (var order in changes)
                await projector.UpsertAsync(order, ct);
        })
    .WithInstanceName(Environment.MachineName)
    .WithLeaseContainer(leaseContainer)
    .Build();

await processor.StartAsync();
```

Projection operation nên idempotent, ví dụ upsert theo stable document/version key.

## 5. Real production scenario

Order container là source of truth. Change Feed cập nhật read model phục vụ dashboard/search. User có thể thấy order commit trước khi projection xuất hiện; UX phải chấp nhận eventual consistency hoặc đọc source-of-truth ở critical path.

## 6. Failure scenario & troubleshooting

**Symptom:** projection lag tăng liên tục. **Evidence:** processor throughput thấp, 429/RU throttling hoặc hot partition. **Hypothesis:** consumer capacity/partition imbalance. **Diagnosis:** đo RU, lease distribution, handler latency và downstream dependency. **Fix:** tăng/auto-scale RU, tối ưu handler, partitioning hoặc decouple downstream. **Verification:** lag trở về SLO sau replay/backlog drain.

## 7. Common mistakes

- Giả định global ordering.
- Handler non-idempotent.
- Đưa slow external API trực tiếp vào batch loop không timeout/bulkhead.
- Coi raw document change là stable public integration contract.

## 8. Alternatives

Transactional outbox + Service Bus khi cần explicit business event contract; Event Grid cho event routing phù hợp; scheduled polling cho workload rất nhỏ nơi simplicity thắng infrastructure complexity.

## 9. Trade-offs

### Advantages

Efficient incremental processing, managed checkpoint/lease model, phù hợp projections và data synchronization.

### Costs / Risks

Eventual consistency, partition-aware scaling, RU cost và coupling vào data shape nếu dùng trực tiếp làm integration contract.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu change feed là asynchronous stream và consumer có thể chậm hơn writer.

### Middle

Implement processor, lease container, idempotent upsert và cancellation.

### Senior

Điều tra lag/429/hot partition, thiết kế retries và downstream isolation.

### Technical Lead / Architect

Quyết định Change Feed là internal projection mechanism hay cần outbox/message broker cho stable cross-service contracts; xác định data ownership và consistency UX.

## 11. Key takeaway

- Change Feed phù hợp incremental projections nhưng không tự động là business event bus.
- Idempotency, partitioning và lag observability là production requirements.
- Chọn polling, Change Feed hay broker dựa trên semantics và operational cost, không theo độ “hiện đại”.
