# 1. C# string allocation, interning và `StringBuilder`: tối ưu text processing mà không biến code thành micro-optimization khó bảo trì

## 1. What is it?

Trong .NET, `string` là immutable reference type. Mọi thao tác có vẻ như “sửa” string thực chất tạo ra string mới nếu nội dung thay đổi.

Ví dụ:

```csharp
var full = firstName + " " + lastName;
```

Compiler có thể tối ưu một số biểu thức nối cố định, nhưng trong vòng lặp hoặc pipeline xử lý text, việc liên tục tạo string trung gian có thể tăng allocation rate đáng kể.

`StringBuilder` tồn tại để gom nhiều thay đổi trên một mutable buffer rồi materialize thành `string` ở cuối.

## 2. Why does it exist?

Text processing xuất hiện ở logging, CSV generation, email templating, serialization, SQL generation, report export và protocol handling.

Nếu workload lớn, pattern này:

```csharp
string result = "";
foreach (var item in items)
{
    result += item;
}
```

có thể tạo nhiều intermediate strings. Khi `result` dài dần, mỗi vòng lặp có thể phải cấp phát và copy dữ liệu cũ sang vùng nhớ mới.

## 3. How does it work?

`StringBuilder` giữ một mutable character buffer. Khi capacity hiện tại không đủ, nó mở rộng backing storage thay vì tạo một string hoàn chỉnh sau mỗi lần append.

```csharp
var builder = new StringBuilder(capacity: 1024);

foreach (var item in items)
{
    builder.Append(item);
    builder.AppendLine();
}

var text = builder.ToString();
```

String interning là cơ chế khác: runtime có thể chia sẻ cùng một string literal thay vì giữ nhiều bản sao giống nhau. Không nên nhầm interning với general-purpose string cache.

## 4. Practical implementation

Một report builder nên estimate capacity khi có dữ liệu đủ ổn định:

```csharp
public static string BuildCsv(IEnumerable<Product> products)
{
    var sb = new StringBuilder(4096);
    sb.AppendLine("Id,Name,Price");

    foreach (var product in products)
    {
        sb.Append(product.Id)
          .Append(',')
          .Append(product.Name)
          .Append(',')
          .Append(product.Price)
          .AppendLine();
    }

    return sb.ToString();
}
```

Nếu output rất lớn, tốt hơn có thể là stream trực tiếp ra `TextWriter` hoặc response body thay vì build toàn bộ string trong memory.

## 5. Real production scenario

Một endpoint export hàng trăm nghìn dòng CSV dùng `result += ...`. CPU không quá cao nhưng allocation rate và Gen 0 collection tăng mạnh. Sau profiling, nguyên nhân chính là intermediate strings.

Giải pháp hợp lý không phải luôn là `StringBuilder`. Nếu response có thể stream, tránh giữ cả report trong RAM thường tốt hơn cả về memory footprint lẫn time-to-first-byte.

## 6. Failure scenario & troubleshooting

**Symptom** → memory allocation rate tăng, GC chạy thường xuyên, p95 latency xấu khi report lớn.

**Evidence** → profiler cho thấy nhiều `System.String` allocations trong loop.

**Hypothesis** → text concatenation tạo nhiều intermediate objects.

**Diagnosis** → đo allocation theo request size và kiểm tra hot path.

**Fix** → dùng `StringBuilder`, `string.Create`, span-based formatting hoặc streaming tùy workload.

**Verification** → benchmark bằng dữ liệu thực tế và so sánh allocation, CPU, latency.

## 7. Common mistakes

* Dùng `StringBuilder` cho hai hoặc ba phép nối đơn giản rồi làm code khó đọc hơn.
* Dùng string concatenation trong loop lớn mà không đo allocation.
* Nghĩ string interning tự động giải quyết mọi duplicate runtime string.
* Build output hàng trăm MB trong memory dù có thể stream.
* Tối ưu string trước khi xác nhận đây là bottleneck.

## 8. Alternatives

* String interpolation: phù hợp cho biểu thức nhỏ, rõ ràng.
* `string.Concat`: hiệu quả cho số phần tử nhỏ và biết trước.
* `string.Create`: hữu ích cho formatting tối ưu allocation.
* `Span<char>` / `ArrayPool<char>`: phù hợp hot path chuyên biệt.
* Streaming qua `TextWriter`: tốt cho output lớn.

## 9. Trade-offs

### Advantages

* `StringBuilder` giảm intermediate allocations khi ghép nhiều phần.
* Có thể pre-size capacity để giảm resize.
* API dễ dùng hơn manual buffer management.

### Costs / Risks

* Không phải thread-safe cho concurrent mutation.
* Có thể giữ buffer lớn lâu hơn cần thiết.
* Không giải quyết vấn đề nếu thiết kế đúng ra nên stream.
* Có thể trở thành premature optimization nếu workload nhỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `string` là immutable và phép nối có thể tạo object mới.

### Middle

Biết khi nào loop-based concatenation nên chuyển sang `StringBuilder`.

### Senior

Đo allocation bằng profiler/benchmark, phân biệt build-in-memory với streaming.

### Technical Lead / Architect

Đặt performance budget cho export/text pipeline và chọn thiết kế dựa trên scale, không dựa trên “best practice” máy móc.

## 11. Key takeaway

* `string` immutable nên repeated mutation thực chất là allocation.
* `StringBuilder` hữu ích khi có nhiều phép append, không phải mọi nơi.
* Với output lớn, streaming thường quan trọng hơn micro-optimization.

# 2. ASP.NET Core `ProblemDetails` và exception boundary: chuẩn hóa lỗi API mà không làm rò implementation detail

## 1. What is it?

`ProblemDetails` là representation chuẩn hóa cho HTTP API errors theo problem details format. Nó giúp client nhận một contract ổn định thay vì mỗi endpoint tự trả shape lỗi khác nhau.

Một response có thể trông như:

```json
{
  "type": "https://example.com/problems/order-not-found",
  "title": "Order not found",
  "status": 404,
  "detail": "The requested order does not exist.",
  "traceId": "00-..."
}
```

## 2. Why does it exist?

Không có exception boundary rõ ràng, controller dễ chứa nhiều `try/catch`, error response thiếu nhất quán và internal exception message có thể bị lộ ra ngoài.

API cần phân biệt:

* expected business errors,
* validation errors,
* authentication/authorization failures,
* dependency failures,
* unexpected bugs.

## 3. How does it work?

Request pipeline nên có một centralized exception handler gần outer boundary. Handler map exception/domain result thành status code + public error contract.

```text
Request
  ↓
Exception middleware / handler
  ↓
Endpoint
  ↓
Application / domain
  ↓
Exception or result
  ↑
Map to ProblemDetails
```

Internal telemetry có thể giữ stack trace; public response thì không nên.

## 4. Practical implementation

Ví dụ .NET:

```csharp
builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();

var app = builder.Build();
app.UseExceptionHandler();
```

Handler:

```csharp
public sealed class GlobalExceptionHandler : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext context,
        Exception exception,
        CancellationToken cancellationToken)
    {
        var status = exception switch
        {
            KeyNotFoundException => StatusCodes.Status404NotFound,
            ArgumentException => StatusCodes.Status400BadRequest,
            _ => StatusCodes.Status500InternalServerError
        };

        await Results.Problem(
            statusCode: status,
            title: status == 500 ? "Unexpected server error" : exception.Message,
            extensions: new Dictionary<string, object?>
            {
                ["traceId"] = context.TraceIdentifier
            })
            .ExecuteAsync(context);

        return true;
    }
}
```

Trong production, không nên trả `exception.Message` cho mọi loại exception.

## 5. Real production scenario

Một API ban đầu trả `{ error: "..." }`, endpoint khác trả `{ message: "..." }`, endpoint khác dùng plain text. Frontend phải viết nhiều nhánh parsing.

Khi chuẩn hóa bằng `ProblemDetails`, client có contract thống nhất, còn backend dễ gắn `traceId` để support tra log.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận 500 nhưng không tìm được log tương ứng.

**Evidence** → response không có correlation identifier.

**Hypothesis** → exception boundary chưa propagate trace context.

**Diagnosis** → kiểm tra middleware order, logging scope và distributed trace.

**Fix** → thêm `traceId`, structured logging và map error ở một nơi duy nhất.

**Verification** → gây lỗi có chủ đích và xác nhận response trace liên kết được với telemetry.

## 7. Common mistakes

* Trả stack trace hoặc raw database exception cho client.
* Map mọi exception thành 400.
* Dùng exception cho control flow bình thường quá mức.
* Mỗi controller tự định nghĩa error shape riêng.
* Nuốt exception mà không log/trace đủ context.

## 8. Alternatives

* Domain result / `Result<T>` pattern cho expected failure.
* RFC-style error object tự định nghĩa.
* gRPC status/details nếu protocol là gRPC.
* Exception filter trong MVC, dù middleware/handler thường bao quát hơn.

## 9. Trade-offs

### Advantages

* Contract lỗi nhất quán.
* Dễ tích hợp observability và support.
* Tách public error khỏi internal implementation.

### Costs / Risks

* Mapping layer cần governance.
* Over-abstraction nếu taxonomy lỗi quá phức tạp.
* Business error và system exception cần được phân biệt rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code và error body là API contract.

### Middle

Triển khai centralized exception handling và `ProblemDetails`.

### Senior

Thiết kế error taxonomy, correlation và security boundary.

### Technical Lead / Architect

Đảm bảo error contract nhất quán giữa services, documentation và monitoring.

## 11. Key takeaway

* Exception handling là boundary concern, không nên copy khắp controller.
* Public error contract phải ổn định và không lộ internals.
* `traceId` giúp nối trải nghiệm client với production evidence.

# 3. EF Core transaction boundaries và savepoints: `SaveChanges` atomic không có nghĩa toàn bộ business workflow tự động atomic

## 1. What is it?

EF Core `SaveChanges` thường chạy các thay đổi trong transaction khi cần. Điều đó đảm bảo batch database mutation của một lần save có tính atomic tương đối với database.

Nhưng một business workflow có thể gồm nhiều `SaveChanges`, nhiều DbContext hoặc external side effects. Khi đó transaction boundary phải được thiết kế rõ ràng.

## 2. Why does it exist?

Business operation như tạo order có thể cần:

1. insert order,
2. update inventory,
3. append audit data,
4. publish event.

Nếu các bước database phải cùng thành công hoặc cùng rollback, boundary không thể phụ thuộc vào nhiều transaction rời rạc.

## 3. How does it work?

Có thể mở explicit transaction:

```csharp
await using var transaction =
    await db.Database.BeginTransactionAsync(cancellationToken);

try
{
    // mutate entities
    await db.SaveChangesAsync(cancellationToken);

    // more database work
    await db.SaveChangesAsync(cancellationToken);

    await transaction.CommitAsync(cancellationToken);
}
catch
{
    await transaction.RollbackAsync(cancellationToken);
    throw;
}
```

Khi transaction đã tồn tại, EF Core có thể tạo savepoint trước `SaveChanges` để rollback về điểm an toàn khi save thất bại.

## 4. Practical implementation

Transaction nên bao quanh đúng consistency boundary, không phải toàn bộ request một cách máy móc.

```csharp
public async Task PlaceOrderAsync(Order order, CancellationToken ct)
{
    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    _db.Orders.Add(order);
    await _db.SaveChangesAsync(ct);

    var outbox = OutboxMessage.From(order.DomainEvents);
    _db.OutboxMessages.AddRange(outbox);
    await _db.SaveChangesAsync(ct);

    await tx.CommitAsync(ct);
}
```

Event được dispatch sau commit thay vì gọi external broker trong transaction.

## 5. Real production scenario

Một checkout lưu order thành công rồi gọi payment service, sau đó update trạng thái. Nếu payment timeout, database có thể đã có order nhưng external state chưa rõ.

Cố kéo HTTP call vào database transaction chỉ làm lock tồn tại lâu hơn và vẫn không tạo atomicity thực sự giữa hai hệ thống.

## 6. Failure scenario & troubleshooting

**Symptom** → lock duration tăng, deadlock tăng sau khi thêm explicit transaction.

**Evidence** → transaction mở từ đầu request và chứa network call chậm.

**Hypothesis** → consistency boundary quá rộng.

**Diagnosis** → trace transaction duration, lock waits và dependency latency.

**Fix** → rút ngắn transaction, dùng Outbox/Saga cho cross-system workflow.

**Verification** → failure injection ở dependency và kiểm tra state transition vẫn hợp lệ.

## 7. Common mistakes

* Nghĩ một request HTTP cần đúng một database transaction dài.
* Gọi external API trong transaction rồi giữ lock hàng giây.
* Dùng nhiều `SaveChanges` nhưng tưởng chúng mặc định nằm cùng transaction.
* Không xử lý retry khi transaction gặp transient database error.
* Nhầm database atomicity với distributed atomicity.

## 8. Alternatives

* Một `SaveChanges` duy nhất nếu workflow đơn giản.
* Explicit transaction cho nhiều database changes cần chung boundary.
* Outbox cho database + messaging.
* Saga/compensation cho workflow nhiều service.

## 9. Trade-offs

### Advantages

* Transaction rõ ràng bảo vệ invariant trong relational database.
* Savepoint giúp rollback partial database work trong một số flow.

### Costs / Risks

* Transaction dài tăng lock contention.
* Cross-system calls không trở nên atomic chỉ vì đặt trong transaction.
* Retry logic phức tạp hơn nếu transaction manual.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction = all-or-nothing cho phạm vi database transaction.

### Middle

Biết dùng `BeginTransactionAsync`, commit, rollback đúng scope.

### Senior

Phân biệt database consistency với distributed workflow consistency.

### Technical Lead / Architect

Thiết kế transaction boundary dựa trên invariant, lock cost và failure model.

## 11. Key takeaway

* `SaveChanges` atomic không đồng nghĩa cả workflow atomic.
* Transaction càng dài càng có operational cost.
* Cross-system consistency thường cần messaging pattern, không phải transaction kéo dài.

# 4. Keyset pagination trong SQL: tránh chi phí tăng dần của `OFFSET` và giữ thứ tự ổn định khi dữ liệu thay đổi

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên giá trị sort key cuối cùng của trang trước, thay vì bỏ qua N dòng bằng `OFFSET`.

Thay vì:

```sql
ORDER BY CreatedAt DESC
OFFSET 100000 ROWS FETCH NEXT 50 ROWS ONLY;
```

có thể dùng:

```sql
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC
FETCH FIRST 50 ROWS ONLY;
```

## 2. Why does it exist?

`OFFSET` dễ implement và phù hợp nhiều UI nhỏ. Nhưng khi offset lớn, database vẫn phải tìm/sắp xếp/bỏ qua nhiều rows trước khi trả page hiện tại.

Ngoài ra, dữ liệu insert/delete giữa hai request có thể làm item bị lặp hoặc bị bỏ sót.

## 3. How does it work?

Keyset pagination biến “page number” thành “position in ordered set”. Cursor thường chứa các sort key cần thiết.

```text
Page 1 -> last key = (2026-09-14T10:00, 9812)
Page 2 -> WHERE key < last key
```

Sort phải deterministic. Nếu `CreatedAt` không unique, cần tie-breaker như `Id`.

## 4. Practical implementation

EF Core example:

```csharp
var query = db.Orders
    .AsNoTracking()
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id);

if (cursor is not null)
{
    query = query.Where(x =>
        x.CreatedAt < cursor.CreatedAt ||
        (x.CreatedAt == cursor.CreatedAt && x.Id < cursor.Id));
}

var items = await query
    .Take(51)
    .ToListAsync(ct);
```

Có thể lấy 51 rows để biết còn next page hay không rồi chỉ trả 50.

## 5. Real production scenario

Admin portal có bảng audit log hàng chục triệu records. Page đầu nhanh nhưng page 2,000 chậm rõ rệt với `OFFSET`.

Chuyển sang cursor/keyset giúp query tận dụng composite index theo `(CreatedAt DESC, Id DESC)` và latency ổn định hơn theo độ sâu của pagination.

## 6. Failure scenario & troubleshooting

**Symptom** → item lặp giữa hai trang.

**Evidence** → sort chỉ theo `CreatedAt`, nhiều rows cùng timestamp.

**Hypothesis** → ordering không deterministic.

**Diagnosis** → kiểm tra duplicate sort key.

**Fix** → thêm unique tie-breaker như `Id` vào order và cursor.

**Verification** → test concurrent inserts/deletes giữa page requests.

## 7. Common mistakes

* Dùng cursor nhưng sort key không unique.
* Encode cursor nhưng không validate/serialize version.
* Mong muốn “jump to page 500” dù keyset không phù hợp use case đó.
* Không có index phù hợp với order/filter.
* Dùng nullable sort key mà không định nghĩa ordering rõ ràng.

## 8. Alternatives

* Offset pagination: đơn giản, hỗ trợ page number trực tiếp.
* Seek pagination: tên khác của cùng keyset concept.
* Time-window pagination: hữu ích cho logs/events.
* Search engine cursor/search-after: tương tự trong Elasticsearch.

## 9. Trade-offs

### Advantages

* Latency ổn định hơn ở dataset lớn.
* Ít lỗi pagination khi dữ liệu thay đổi liên tục.
* Tận dụng index tốt nếu thiết kế đúng.

### Costs / Risks

* Khó jump tới arbitrary page.
* Cursor contract phức tạp hơn.
* Multi-column sorting cần cursor tương ứng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `OFFSET` là bỏ qua rows trước đó.

### Middle

Implement cursor với deterministic ordering.

### Senior

Thiết kế index theo filter/order và test concurrency behavior.

### Technical Lead / Architect

Chọn pagination model theo UX, scale và consistency semantics.

## 11. Key takeaway

* `OFFSET` không miễn phí khi offset tăng lớn.
* Keyset pagination dựa trên vị trí thật trong ordered dataset.
* Deterministic sort + supporting index là điều kiện cốt lõi.

# 5. Redis cache stampede và request coalescing: cache hết hạn đồng thời có thể biến cache thành nguyên nhân gây outage

## 1. What is it?

Cache stampede xảy ra khi nhiều request cùng thấy một cache key bị miss/expired và đồng thời gọi xuống dependency đắt tiền để rebuild cùng dữ liệu.

```text
1000 requests
      ↓
cache key expired
      ↓
1000 database queries
```

Cache vốn được thêm để giảm tải nhưng tại thời điểm expiration lại tạo spike lớn hơn bình thường.

## 2. Why does it exist?

TTL đồng bộ, hot key và burst traffic tạo điều kiện cho hàng trăm consumer cùng miss một lúc.

Đặc biệt nguy hiểm với product catalog, pricing, feature metadata hoặc expensive aggregation.

## 3. How does it work?

Một kỹ thuật là request coalescing/single-flight: chỉ một caller rebuild cache; các caller khác chờ kết quả hoặc dùng stale value.

```text
Miss
 ├─ request A -> acquires rebuild ownership -> DB
 ├─ request B -> waits
 ├─ request C -> waits
 └─ request D -> waits
```

Trong distributed system, lock cần TTL và failure handling cẩn thận.

## 4. Practical implementation

Local process có thể dùng `SemaphoreSlim` theo key. Multi-instance thường cần strategy khác: distributed lock, stale-while-revalidate, background refresh hoặc jittered TTL.

Pseudo-flow:

```csharp
var cached = await cache.GetAsync(key);
if (cached is not null)
    return cached;

await using var lease = await lockProvider.TryAcquireAsync(key, ct);

if (!lease.Acquired)
    return await WaitOrUseStaleAsync(key, ct);

cached = await cache.GetAsync(key);
if (cached is not null)
    return cached;

var fresh = await repository.LoadAsync(ct);
await cache.SetAsync(key, fresh, RandomizedTtl());
return fresh;
```

Double-check cache sau khi lấy lock là quan trọng.

## 5. Real production scenario

Một product detail endpoint cache metadata 10 phút. Hàng nghìn hot keys được warm cùng lúc sau deploy, vì vậy cũng hết hạn gần cùng lúc 10 phút sau.

Database bị spike query đột ngột. Thêm TTL jitter và background refresh làm expiration phân tán hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → database CPU spike định kỳ đúng theo TTL.

**Evidence** → Redis miss rate tăng cùng thời điểm và query rate tăng mạnh.

**Hypothesis** → synchronized expiration gây stampede.

**Diagnosis** → correlate cache hit/miss, DB QPS và key TTL distribution.

**Fix** → jitter TTL, single-flight, stale fallback hoặc proactive refresh.

**Verification** → load test quanh expiration boundary.

## 7. Common mistakes

* Đặt cùng TTL cho hàng nghìn keys hot.
* Distributed lock không có expiry.
* Lock global toàn bộ cache thay vì theo key.
* Không có fallback khi Redis unavailable.
* Cho rằng cache miss luôn là event rẻ.

## 8. Alternatives

* Stale-while-revalidate.
* Background refresh trước expiry.
* Local memory + distributed cache multi-layer.
* Rate limiting dependency.
* Không cache nếu source đủ nhanh và workload nhỏ.

## 9. Trade-offs

### Advantages

* Coalescing giảm duplicate rebuild work.
* Jitter làm traffic mượt hơn.
* Stale serving tăng resilience.

### Costs / Risks

* Distributed locking thêm failure mode.
* Stale data có consistency implication.
* Background refresh tăng complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss có thể gọi xuống database.

### Middle

Biết TTL, jitter và double-check pattern.

### Senior

Thiết kế fallback, lock semantics và stale tolerance.

### Technical Lead / Architect

Quyết định cache có thực sự giảm risk hay tạo hidden critical dependency.

## 11. Key takeaway

* Hot key expiration có thể tạo synchronized load spike.
* TTL jitter và request coalescing là công cụ quan trọng.
* Cache strategy phải bao gồm cả failure behavior, không chỉ happy path.

# 6. Outbox Pattern với relational database: commit business state và integration event mà không cần distributed transaction

## 1. What is it?

Outbox Pattern lưu business change và message cần publish vào cùng relational database transaction. Một background publisher sau đó đọc outbox và gửi message tới broker.

```text
Transaction
  ├─ Orders table
  └─ OutboxMessages table
        ↓
Background publisher
        ↓
Message broker
```

## 2. Why does it exist?

Nếu code làm:

1. save database,
2. publish event,

thì crash giữa hai bước tạo inconsistent state.

Đảo thứ tự cũng không an toàn: message có thể publish thành công nhưng database rollback.

## 3. How does it work?

Business state và serialized integration event commit cùng transaction. Sau commit, publisher gửi event rồi đánh dấu row đã processed.

Delivery thường là at-least-once, vì publisher có thể gửi thành công nhưng crash trước khi mark processed.

Do đó consumer vẫn cần idempotency.

## 4. Practical implementation

Entity:

```csharp
public sealed class OutboxMessage
{
    public Guid Id { get; init; }
    public DateTimeOffset OccurredAt { get; init; }
    public string Type { get; init; } = null!;
    public string Payload { get; init; } = null!;
    public DateTimeOffset? ProcessedAt { get; set; }
}
```

Publisher có thể lấy batch:

```csharp
var messages = await db.OutboxMessages
    .Where(x => x.ProcessedAt == null)
    .OrderBy(x => x.OccurredAt)
    .Take(100)
    .ToListAsync(ct);
```

Sau publish, update `ProcessedAt`.

## 5. Real production scenario

Order service cần publish `OrderPlaced`. Trước đây DB commit thành công nhưng Service Bus transiently unavailable, event bị mất hoàn toàn.

Outbox cho phép giữ message pending trong DB và retry về sau mà không rollback order.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng event được consumer xử lý hai lần.

**Evidence** → publisher log cho thấy message đã send trước crash nhưng row chưa mark processed.

**Hypothesis** → at-least-once redelivery.

**Diagnosis** → kiểm tra event id và consumer deduplication.

**Fix** → Inbox/idempotency key ở consumer.

**Verification** → inject crash giữa send và mark-processed.

## 7. Common mistakes

* Nghĩ Outbox tạo exactly-once delivery end-to-end.
* Không có cleanup/archive strategy cho table.
* Publish rows song song mà phá ordering requirement.
* Không có retry/backoff cho broker outage.
* Không monitor backlog age.

## 8. Alternatives

* Distributed transaction nếu hạ tầng thật sự hỗ trợ và complexity chấp nhận được.
* Change Data Capture đọc DB log.
* Broker-first workflow kết hợp compensation.
* Direct publish nếu mất message được business chấp nhận.

## 9. Trade-offs

### Advantages

* Không cần 2PC giữa DB và broker.
* Message không mất khi broker tạm unavailable.
* Dễ audit pending publication.

### Costs / Risks

* Event có delay.
* Table cần cleanup và indexing.
* Duplicate delivery vẫn tồn tại.
* Publisher trở thành production component cần observability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu vấn đề crash giữa DB commit và publish.

### Middle

Implement outbox table và background publisher.

### Senior

Thiết kế idempotency, batching, locking và retry.

### Technical Lead / Architect

Quyết định khi nào eventual consistency hợp lý và định nghĩa reliability SLO cho message publication.

## 11. Key takeaway

* Outbox giải quyết atomicity giữa DB state và intent-to-publish.
* Nó không loại bỏ duplicate delivery.
* Backlog, retry và idempotency là phần của pattern, không phải chi tiết phụ.

# 7. Azure Front Door, Application Gateway và Load Balancer: chọn đúng layer thay vì coi mọi dịch vụ routing là tương đương

## 1. What is it?

Ba dịch vụ đều liên quan tới traffic distribution nhưng hoạt động ở phạm vi và layer khác nhau.

* Azure Front Door: global HTTP(S) entry, edge routing, acceleration, WAF/CDN-oriented capabilities.
* Application Gateway: regional Layer 7 HTTP(S) load balancing, WAF, path/host routing trong Azure region/VNet context.
* Azure Load Balancer: Layer 4 TCP/UDP load balancing.

## 2. Why does it exist?

Một hệ thống có thể cần global ingress, regional routing và internal TCP balancing cùng lúc. Không có một component duy nhất tối ưu cho tất cả boundary.

## 3. How does it work?

Một architecture có thể là:

```text
Internet
  ↓
Azure Front Door
  ↓
Regional Application Gateway
  ↓
App Service / AKS / VMs
```

Trong workload khác, Front Door có thể route trực tiếp tới App Service/Container Apps mà không cần Application Gateway.

## 4. Practical implementation

Câu hỏi chọn dịch vụ:

* Cần route global multi-region? → xem Front Door.
* Cần WAF/path routing regional vào private backend? → xem Application Gateway.
* Chỉ cần TCP/UDP balancing? → Load Balancer.
* Backend đã có platform ingress đủ tốt? → tránh thêm hop không cần thiết.

Thiết kế phải kèm health probe, TLS ownership, DNS, private connectivity và failover semantics.

## 5. Real production scenario

Một team đặt cả Front Door và Application Gateway chỉ vì “production architecture nên có hai layer”. Kết quả là TLS/debugging phức tạp, chi phí tăng và khó xác định source của 502.

Nếu không có requirement regional WAF/private ingress, một layer có thể đủ.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận 502 nhưng application không có request log.

**Evidence** → Front Door health probe báo origin unhealthy.

**Hypothesis** → lỗi ở ingress chain trước application.

**Diagnosis** → kiểm tra lần lượt DNS → Front Door → Application Gateway → backend health.

**Fix** → sửa probe path, TLS/SNI, NSG/private endpoint hoặc origin configuration.

**Verification** → health state xanh và end-to-end trace xác nhận traffic đến backend.

## 7. Common mistakes

* Dùng Layer 4 load balancer khi cần HTTP path routing.
* Thêm nhiều ingress layer mà không có requirement.
* Health probe gọi endpoint phụ thuộc quá nhiều downstream services.
* Không phân biệt public edge với regional ingress.
* Không tính egress/hop latency và operational cost.

## 8. Alternatives

* App Service built-in ingress.
* Azure Container Apps ingress.
* AKS ingress controller / Gateway API.
* Third-party CDN/WAF như Akamai hoặc Cloudflare tùy tổ chức.

## 9. Trade-offs

### Advantages

* Front Door mạnh cho global HTTP routing.
* Application Gateway mạnh cho regional L7/VNet/WAF needs.
* Load Balancer đơn giản cho L4.

### Costs / Risks

* Nhiều layer làm debugging khó hơn.
* WAF/routing policy phân tán dễ drift.
* Chi phí và latency tăng theo kiến trúc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Layer 4 khác Layer 7.

### Middle

Biết use case chính của từng dịch vụ.

### Senior

Thiết kế health probe, TLS, failover và private connectivity.

### Technical Lead / Architect

Loại bỏ layer thừa và chọn ingress topology theo requirement cụ thể.

## 11. Key takeaway

* Front Door, Application Gateway và Load Balancer không interchangeable.
* Chọn service theo layer, scope và security boundary.
* Architecture tốt thường là architecture ít layer nhất nhưng đáp ứng đủ requirement.

# 8. OpenTelemetry metric cardinality: observability có thể tự gây chi phí và instability nếu label dimension không được kiểm soát

## 1. What is it?

Metric cardinality là số lượng unique time series sinh ra từ một metric và tập label/tag dimensions.

Ví dụ:

```text
http_requests_total{method="GET", status="200"}
```

cardinality thấp.

Nhưng nếu thêm `user_id`, `order_id` hoặc full URL:

```text
http_requests_total{user_id="..."}
```

số series có thể tăng gần như không giới hạn.

## 2. Why does it exist?

Labels giúp slice metric theo dimension hữu ích: status code, route, region, dependency. Nhưng mỗi combination thường tạo time series riêng ở backend metrics.

High cardinality làm storage, memory, query cost và telemetry bill tăng mạnh.

## 3. How does it work?

Nếu có:

* 10 routes,
* 5 status codes,
* 3 regions,
* 20 instances,

thì riêng combination có thể tới 3,000 series.

Thêm `customer_id` với 100,000 giá trị có thể làm explosion nhiều bậc.

## 4. Practical implementation

Metric tốt:

```csharp
requestCounter.Add(1,
    new("http.method", method),
    new("http.route", routeTemplate),
    new("http.status_code", statusCode));
```

Không nên dùng raw path nếu path chứa IDs:

```text
/orders/123
/orders/456
/orders/789
```

Nên normalize thành route template `/orders/{id}`.

High-cardinality identifiers thuộc logs/traces tốt hơn metrics.

## 5. Real production scenario

Team thêm `request_url` vào every metric. Một e-commerce site có hàng triệu product URLs, metric backend bắt đầu ingest hàng triệu series và dashboard query chậm.

Fix không phải tăng capacity trước tiên mà là giảm dimensions sai bản chất.

## 6. Failure scenario & troubleshooting

**Symptom** → telemetry cost tăng mạnh, metrics query timeout.

**Evidence** → series count tăng sau release.

**Hypothesis** → label mới có high cardinality.

**Diagnosis** → rank dimensions theo unique value count.

**Fix** → remove/normalize label, dùng logs/traces cho identifiers.

**Verification** → theo dõi active series và ingest volume sau deploy.

## 7. Common mistakes

* Đưa `userId`, `sessionId`, `orderId` vào metric labels.
* Dùng raw URL thay route template.
* Gắn exception message thành metric label.
* Instrument mọi dimension “phòng khi cần”.
* Không có telemetry budget.

## 8. Alternatives

* Structured logs cho high-cardinality event detail.
* Distributed traces cho per-request investigation.
* Exemplars để link metric với trace sample.
* Sampling ở traces/logs, nhưng metric labels vẫn cần discipline.

## 9. Trade-offs

### Advantages

* Labels đúng giúp aggregation và alerting cực mạnh.
* Metric cardinality thấp cho query nhanh và predictable cost.

### Costs / Risks

* Quá ít labels làm metric mất diagnostic value.
* Quá nhiều labels có thể tự tạo observability incident.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu tag tạo dimensions cho metric.

### Middle

Tránh identifiers không giới hạn trong labels.

### Senior

Thiết kế signal split giữa metrics, logs và traces.

### Technical Lead / Architect

Đặt telemetry conventions và cost/cardinality guardrails toàn hệ thống.

## 11. Key takeaway

* Metric label phải có bounded cardinality.
* ID cụ thể thường thuộc logs/traces, không thuộc metrics.
* Observability cũng cần capacity và cost engineering.

# 9. Vue reactivity và derived state: tránh đồng bộ thủ công nhiều nguồn state dẫn tới UI drift

## 1. What is it?

Vue reactivity theo dõi dependencies của reactive state và cập nhật computed/render effect khi dependency thay đổi.

Derived state là state có thể tính từ source-of-truth khác. Thay vì lưu cả `items` và `totalPrice` rồi tự đồng bộ, có thể tính `totalPrice` bằng `computed`.

## 2. Why does it exist?

Duplicated mutable state tạo synchronization problem.

```text
items changed
   ↓
forgot to update total
   ↓
UI inconsistent
```

Computed state biến relationship thành expression thay vì manual bookkeeping.

## 3. How does it work?

```ts
const items = ref<CartItem[]>([])

const total = computed(() =>
  items.value.reduce((sum, x) => sum + x.price * x.quantity, 0)
)
```

Vue track reactive reads bên trong computed getter. Khi `items` thay đổi, computed invalidates và recalculates khi cần.

## 4. Practical implementation

Không nên:

```ts
const items = ref<CartItem[]>([])
const total = ref(0)

watch(items, () => {
  total.value = calculateTotal(items.value)
})
```

nếu `total` hoàn toàn derived từ `items`.

`watch` hợp lý hơn cho side effects: gọi API, persist local storage, analytics hoặc imperative integration.

## 5. Real production scenario

Checkout UI giữ `subtotal`, `discount`, `tax`, `grandTotal` ở nhiều refs và update trong nhiều event handlers. Một edge case coupon removal quên update `grandTotal`.

Refactor về computed chain giảm invalid state và số nơi phải sửa.

## 6. Failure scenario & troubleshooting

**Symptom** → UI hiển thị total khác backend request payload.

**Evidence** → duplicated refs được mutate ở các handler khác nhau.

**Hypothesis** → derived state drift.

**Diagnosis** → xác định source of truth và dependency graph.

**Fix** → chuyển derived values sang `computed`, giữ mutation tại source state.

**Verification** → test các sequence add/remove/update/coupon.

## 7. Common mistakes

* Dùng `watch` để đồng bộ state hoàn toàn có thể derive.
* Mutate prop trực tiếp.
* Destructure reactive object sai cách rồi mất reactivity trong một số pattern.
* Dùng global store cho state chỉ sống trong component.
* Dùng computed cho side effect.

## 8. Alternatives

* Plain function nếu calculation không cần reactive caching.
* State management library như Pinia cho shared application state.
* Backend-authoritative calculation cho business-critical totals.

## 9. Trade-offs

### Advantages

* Ít duplicated mutable state.
* Dễ reason về UI consistency.
* Dependency tracking tự động.

### Costs / Risks

* Reactive graph quá phức tạp vẫn khó debug.
* Computed đắt tiền có thể cần decomposition/memoization strategy.
* Frontend derived state không thay thế server-side invariant.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `ref`, `reactive`, `computed` khác nhau.

### Middle

Nhận diện derived state và tránh manual synchronization.

### Senior

Thiết kế component/store boundaries và trace reactivity bug.

### Technical Lead / Architect

Quy định state ownership giữa component, store và backend contract.

## 11. Key takeaway

* Một giá trị tính được từ state khác thường không nên là mutable source riêng.
* `computed` dành cho derivation; `watch` chủ yếu dành cho side effects.
* Giảm duplicated state là cách giảm bug, không chỉ là style preference.

# 10. Git `rebase`, merge và history policy: tối ưu collaboration flow mà không biến “history đẹp” thành rủi ro rewrite branch dùng chung

## 1. What is it?

`merge` kết hợp hai histories bằng merge commit hoặc fast-forward. `rebase` lấy commits của một branch và replay chúng lên base mới, tạo commit identities mới.

```text
Before rebase:
A---B---C main
     \
      D---E feature

After rebase:
A---B---C main
         \
          D'---E'
```

## 2. Why does it exist?

Teams cần đồng bộ feature branch với main và giữ history dễ hiểu. `rebase` có thể tạo linear history; `merge` bảo toàn topology thực tế của collaboration.

Không có strategy nào luôn đúng cho mọi repository.

## 3. How does it work?

Rebase thực chất replay patch của từng commit. Vì commit content/parent thay đổi, SHA thay đổi.

Nếu branch đã được người khác base work lên, force-push sau rebase có thể làm họ phải reconcile histories.

## 4. Practical implementation

An toàn trên branch cá nhân:

```bash
git fetch origin
git rebase origin/main
```

Sau conflict:

```bash
git add <files>
git rebase --continue
```

Nếu branch chưa shared hoặc team policy cho phép, push thường cần:

```bash
git push --force-with-lease
```

`--force-with-lease` an toàn hơn `--force` vì từ chối overwrite remote changes mà local chưa biết.

## 5. Real production scenario

Hai developer cùng làm trên shared feature branch. Một người interactive rebase rồi `git push --force`, xóa khỏi remote commit mới của người kia.

Nếu buộc phải rewrite history, `--force-with-lease` và branch ownership rõ ràng giảm rủi ro.

## 6. Failure scenario & troubleshooting

**Symptom** → commits “biến mất” sau force push.

**Evidence** → remote branch history đã rewritten.

**Hypothesis** → force push overwrite shared commits.

**Diagnosis** → dùng `git reflog`, remote logs hoặc pull request activity tìm old SHA.

**Fix** → restore commit/branch, sau đó thống nhất policy.

**Verification** → diff branch và xác nhận tất cả intended commits hiện diện.

## 7. Common mistakes

* Rebase branch shared mà không phối hợp.
* Dùng `git push --force` thay vì `--force-with-lease`.
* Tưởng rebase “di chuyển” commit mà SHA không đổi.
* Squash mọi thứ làm mất các checkpoint có ý nghĩa.
* Tranh luận linear history như mục tiêu cao hơn code safety.

## 8. Alternatives

* Merge main vào feature.
* Squash merge tại pull request.
* Rebase merge do hosting platform thực hiện.
* Merge commit để giữ branch topology.

## 9. Trade-offs

### Advantages

* Rebase tạo history tuyến tính, dễ đọc/bisect trong nhiều repo.
* Merge giữ nguyên shared history và context branch.

### Costs / Risks

* Rebase rewrite commit identity.
* Merge-heavy history có thể noisy.
* Squash giảm noise nhưng mất commit granularity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác biệt giữa merge và rebase.

### Middle

Resolve conflict, dùng `--force-with-lease` đúng tình huống.

### Senior

Biết recovery qua reflog và chọn strategy theo collaboration model.

### Technical Lead / Architect

Định nghĩa repository history policy để giảm cognitive load và tránh destructive workflows.

## 11. Key takeaway

* `rebase` rewrite history; `merge` preserve topology.
* Shared branch safety quan trọng hơn history “đẹp”.
* Team policy nên tối ưu khả năng collaboration, recovery và code review.
