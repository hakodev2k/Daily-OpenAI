# 1. C# `ArrayPool<T>` + buffer ownership: giảm allocation mà không tạo use-after-return, data leakage và memory corruption logic

## 1. What is it?

`ArrayPool<T>` là cơ chế tái sử dụng arrays thay vì cấp phát array mới liên tục. Mental model đơn giản:

```text
Rent buffer
   ↓
Use buffer temporarily
   ↓
Return buffer to pool
   ↓
Another operation may receive the same array
```

Điểm quan trọng nhất không phải API `Rent`/`Return`, mà là **ownership**. Sau khi buffer đã được trả lại pool, code hiện tại không còn quyền đọc hoặc ghi buffer đó nữa.

## 2. Why does it exist?

Trong hot path như serialization, compression, protocol parsing hoặc upload processing, việc tạo nhiều arrays có thể làm allocation rate tăng mạnh và tạo GC pressure.

Nếu mỗi request tạo một `byte[128 * 1024]`, 1.000 requests đồng thời có thể tạo lượng memory transient rất lớn dù mỗi buffer chỉ sống trong thời gian ngắn.

Pooling đổi bài toán từ:

```text
allocate → use → GC reclaim
```

thành:

```text
rent → use → return → reuse
```

## 3. How does it work?

`ArrayPool<T>.Shared.Rent(minimumLength)` trả về một array có length **ít nhất** bằng yêu cầu, không đảm bảo bằng chính xác.

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
```

Buffer có thể chứa dữ liệu từ lần sử dụng trước. Khi `Return`, array trở lại pool và có thể được cấp cho operation khác ngay sau đó.

Do đó hai nguyên tắc quan trọng:

* chỉ dùng slice chứa dữ liệu hợp lệ
* không giữ reference sau khi `Return`

## 4. Practical implementation

```csharp
public async Task<int> ReadChunkAsync(
    Stream stream,
    CancellationToken cancellationToken)
{
    byte[] buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);

    try
    {
        return await stream.ReadAsync(
            buffer.AsMemory(0, 64 * 1024),
            cancellationToken);
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
    }
}
```

`clearArray: true` có thêm CPU cost nhưng hữu ích nếu buffer từng chứa secrets, tokens hoặc PII.

## 5. Real production scenario

Một API nhận file uploads nhỏ nhưng traffic rất cao. Mỗi request dùng `MemoryStream` và arrays mới để transform file trước khi đẩy Blob Storage. Allocation rate tăng, Gen 2 collections xuất hiện thường xuyên và p99 latency dao động.

Chuyển phần temporary buffers sang `ArrayPool<byte>` giảm allocation, nhưng team phải chuẩn hóa ownership: buffer chỉ sống trong một method scope và không được đưa vào background task.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu response đôi khi chứa bytes không thuộc request hiện tại.

**Evidence** → lỗi chỉ xuất hiện dưới concurrency cao; local single-user không tái hiện.

**Hypothesis** → buffer bị `Return` sớm rồi tiếp tục được dùng.

**Diagnosis** → code tạo `Task` hoặc callback giữ reference tới rented array sau `finally`.

**Fix** → copy dữ liệu nếu lifetime phải vượt khỏi rental scope, hoặc chuyển ownership rõ ràng tới component khác và chỉ một nơi chịu trách nhiệm `Return`.

**Verification** → stress test song song với payload markers khác nhau; không còn cross-request contamination.

## 7. Common mistakes

* Giả định `Rent(1024)` luôn trả array length đúng 1024.
* Đọc toàn bộ array thay vì chỉ phần dữ liệu hợp lệ.
* `Return` rồi vẫn giữ reference.
* Không clear buffer chứa dữ liệu nhạy cảm.
* Pool mọi allocation dù profiling chưa chứng minh allocation là bottleneck.

## 8. Alternatives

`new byte[]` đơn giản và an toàn hơn cho workload bình thường. `MemoryPool<T>` phù hợp khi muốn owner-based memory abstraction. `PipeReader`/`PipeWriter` phù hợp hơn cho high-throughput streaming pipelines.

`ArrayPool<T>` nên được dùng khi allocation cost đã đo được và buffer lifetime ngắn, rõ ràng.

## 9. Trade-offs

### Advantages

* Giảm allocations và GC pressure.
* Hữu ích cho hot path và large temporary buffers.
* API đơn giản hơn custom object pool.

### Costs / Risks

* Ownership phức tạp hơn.
* Có nguy cơ data leakage nếu không clear dữ liệu nhạy cảm.
* Use-after-return tạo bug concurrency rất khó tái hiện.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu rented array không thuộc riêng request mãi mãi và phải `Return` đúng lúc.

### Middle

Biết giới hạn scope, dùng `try/finally`, slice đúng length và propagate cancellation.

### Senior

Đánh giá allocation profile, security implications và lifetime hazards trước khi pooling.

### Technical Lead / Architect

Quyết định library/component nào sở hữu pooling để application code không bị lan truyền low-level memory management không cần thiết.

## 11. Key takeaway

* `ArrayPool<T>` tối ưu allocation, không tự động tối ưu toàn hệ thống.
* Ownership sau `Rent`/`Return` phải tuyệt đối rõ ràng.
* Không dùng pooling nếu profiling chưa chứng minh lợi ích đáng kể.

# 2. ASP.NET Core resource-based authorization: khi authorization phụ thuộc chính resource thay vì chỉ role/claim tĩnh

## 1. What is it?

Resource-based authorization là cách quyết định quyền dựa trên **user + action + resource cụ thể**.

Ví dụ: user có thể sửa Project A vì là owner, nhưng không thể sửa Project B dù cả hai request đều tới cùng endpoint và user có cùng claims.

```text
Identity claims
      +
Requested action
      +
Loaded resource state
      ↓
Authorization decision
```

## 2. Why does it exist?

Role-based authorization như `[Authorize(Roles = "Admin")]` chỉ phù hợp khi quyền gần như tĩnh.

Trong SaaS thực tế, quyền thường phụ thuộc dữ liệu:

* owner của document
* manager của employee
* tenant của record
* trạng thái resource
* support access window

Nếu nhét mọi rule vào role/claim, token phình to và quyền bị stale khi business state thay đổi.

## 3. How does it work?

ASP.NET Core dùng `IAuthorizationService` cùng requirements/handlers.

```text
Endpoint
  ↓ load resource
IAuthorizationService.AuthorizeAsync(user, resource, requirement)
  ↓
AuthorizationHandler
  ↓
Success / Failure
```

Handler có thể kiểm tra claim, resource owner, status hoặc policy khác.

## 4. Practical implementation

```csharp
public sealed record EditProjectRequirement : IAuthorizationRequirement;

public sealed class EditProjectHandler
    : AuthorizationHandler<EditProjectRequirement, Project>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        EditProjectRequirement requirement,
        Project resource)
    {
        var userId = context.User.FindFirst("sub")?.Value;

        if (userId == resource.OwnerUserId && !resource.IsArchived)
            context.Succeed(requirement);

        return Task.CompletedTask;
    }
}
```

Endpoint:

```csharp
var project = await db.Projects.FindAsync([id], ct);
if (project is null) return Results.NotFound();

var auth = await authorization.AuthorizeAsync(
    user,
    project,
    new EditProjectRequirement());

if (!auth.Succeeded)
    return Results.Forbid();
```

## 5. Real production scenario

Một enterprise platform cho phép managers approve timesheet của employees thuộc team họ quản lý. Claim `Manager=true` không đủ: manager A không được approve employee thuộc team B.

Authorization phải xét cả quan hệ management hiện tại trong domain data.

## 6. Failure scenario & troubleshooting

**Symptom** → user biết GUID của resource khác và sửa được record không thuộc quyền của mình.

**Evidence** → endpoint chỉ kiểm tra `IsAuthenticated` hoặc role chung, sau đó query theo `Id`.

**Hypothesis** → thiếu resource-level authorization.

**Diagnosis** → review đường đi từ route parameter tới persistence; không có ownership/tenant condition hoặc authorization handler.

**Fix** → thêm resource-based policy và defense-in-depth ở query boundary nếu phù hợp.

**Verification** → integration tests với owner, non-owner và privileged support user.

## 7. Common mistakes

* Chỉ ẩn nút trên frontend nhưng backend không authorize.
* Tin client-supplied `OwnerId`.
* Load resource rồi quên tenant boundary.
* Nhồi toàn bộ resource permissions vào JWT dài sống hàng giờ.
* Trả 403/404 thiếu nhất quán và vô tình leak resource existence.

## 8. Alternatives

Role/claim policies vẫn tốt cho coarse-grained permissions như `CanAccessAdminPortal`. Query filters phù hợp để áp tenant isolation rộng. Resource-based authorization phù hợp cho quyết định gắn với một object cụ thể.

## 9. Trade-offs

### Advantages

* Mapping sát business rule.
* Quyền phản ánh state hiện tại.
* Tách authorization logic khỏi controller branching rải rác.

### Costs / Risks

* Có thể cần load resource trước khi authorize.
* Handler quá phức tạp có thể thành hidden domain layer.
* Nếu query không tối ưu, authorization có thể thêm round trips.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt authentication với authorization và hiểu role không luôn đủ.

### Middle

Biết viết requirement/handler và integration tests cho ownership rules.

### Senior

Xem xét tenant isolation, stale claims, resource existence leakage và performance.

### Technical Lead / Architect

Định nghĩa permission model: rule nào thuộc token, rule nào thuộc resource state, rule nào cần policy engine hoặc domain service.

## 11. Key takeaway

* Authorization phải được kiểm tra ở backend và sát resource boundary.
* Claims tốt cho coarse-grained facts; dynamic ownership thường cần resource state.
* Đừng biến authorization handler thành nơi chứa toàn bộ business logic.

# 3. EF Core `SaveChanges` batching + round trips: vì sao một transaction vẫn có thể chậm dù SQL từng statement rất nhanh

## 1. What is it?

Khi `SaveChanges` chạy, EF Core detect changes, tạo commands và có thể batch nhiều commands vào ít database round trips hơn.

Mental model:

```text
Tracked changes
   ↓
DetectChanges
   ↓
Generate SQL commands
   ↓
Batch commands
   ↓
Send to database
   ↓
Apply rows + return generated values
```

Performance không chỉ phụ thuộc mỗi statement nhanh hay chậm; số round trips và số entities tracked cũng quan trọng.

## 2. Why does it exist?

Network/database round trip có latency cố định. 500 câu lệnh mỗi câu 0,2 ms nhưng gửi thành 500 round trips vẫn có thể chậm hơn nhiều so với vài batches.

Ngoài ra `SaveChanges` còn có application-side cost như change detection và relationship fixup.

## 3. How does it work?

EF Core gom insert/update/delete commands theo provider constraints và batch size. Một batch vẫn có nhiều SQL statements.

```text
App → batch 1 → DB
App ← result
App → batch 2 → DB
App ← result
```

Nếu code gọi `SaveChangesAsync` trong loop, batching bị phá vỡ:

```csharp
foreach (var item in items)
{
    db.Items.Add(item);
    await db.SaveChangesAsync(ct);
}
```

## 4. Practical implementation

Tốt hơn:

```csharp
foreach (var dto in request.Items)
{
    db.Items.Add(new Item
    {
        Id = Guid.NewGuid(),
        Name = dto.Name
    });
}

await db.SaveChangesAsync(ct);
```

Với bulk update không cần materialize entities, EF Core có `ExecuteUpdateAsync`:

```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Expired)
    .ExecuteUpdateAsync(
        setters => setters.SetProperty(
            x => x.Status,
            OrderStatus.Archived),
        ct);
```

## 5. Real production scenario

Import job ghi 20.000 records. Bản đầu gọi `SaveChanges` mỗi record; database CPU thấp nhưng job mất hàng chục phút.

Telemetry cho thấy hàng chục nghìn round trips. Sau khi batch theo chunk và dùng set-based operations cho phần phù hợp, total duration giảm mạnh mà không cần index mới.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL statements riêng lẻ đều nhanh nhưng API write endpoint mất 8 giây.

**Evidence** → dependency telemetry hiển thị hàng nghìn database calls.

**Hypothesis** → round-trip amplification hoặc `SaveChanges` trong loop.

**Diagnosis** → inspect call count, EF logs và generated SQL.

**Fix** → gom changes, dùng bounded batching hoặc `ExecuteUpdate/Delete` khi semantics cho phép.

**Verification** → so sánh database-call count và end-to-end latency trước/sau.

## 7. Common mistakes

* `SaveChanges` trong mỗi iteration.
* Giữ hàng trăm nghìn tracked entities trong một DbContext.
* Tăng batch size vô hạn mà không xét transaction/log pressure.
* Chuyển hết sang bulk library nhưng làm mất concurrency/audit/domain behavior.

## 8. Alternatives

* `ExecuteUpdateAsync`/`ExecuteDeleteAsync` cho set-based changes.
* Provider-specific bulk APIs cho data ingestion lớn.
* Raw SQL/stored procedure khi cần tối ưu đặc thù.
* Standard change tracking khi correctness/domain behavior quan trọng hơn throughput cực cao.

## 9. Trade-offs

### Advantages

* Batching giảm network round trips.
* Giữ được EF change tracking và transaction semantics trong nhiều trường hợp.

### Costs / Risks

* Batch lớn tăng transaction duration và lock footprint.
* Tracking nhiều entities tăng memory và change-detection cost.
* Bulk/set-based operations có thể bypass domain hooks.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một `SaveChanges` có thể tạo nhiều SQL commands.

### Middle

Biết tránh `SaveChanges` trong loop và đo số database calls.

### Senior

Phân biệt bottleneck ở DB execution, round trips, change tracking hay transaction footprint.

### Technical Lead / Architect

Chọn persistence path khác nhau cho OLTP write nhỏ, batch import và maintenance operations thay vì một abstraction cho mọi workload.

## 11. Key takeaway

* Database performance phải đo cả số round trips, không chỉ duration từng query.
* Batch vừa đủ thường tốt hơn “mỗi record một save” hoặc “một transaction khổng lồ”.
* Set-based operations hữu ích nhưng phải hiểu behavior bị bypass.

# 4. SQL Server covering index + Key Lookup: đọc execution plan để quyết định INCLUDE columns thay vì thêm index theo cảm tính

## 1. What is it?

Một nonclustered index có thể tìm rows rất nhanh theo key nhưng query vẫn phải quay lại clustered index/base table để lấy các columns còn thiếu. Operator đó thường xuất hiện là `Key Lookup`.

Một covering index chứa đủ dữ liệu cần cho query để tránh lookup đó.

```text
Index Seek
   ↓
Key Lookup for extra columns
   ↓
Return row
```

## 2. Why does it exist?

Index không thể chứa mọi column trong key vì write cost, storage và maintenance sẽ tăng. SQL Server phải cân bằng index nhỏ cho seek với khả năng lấy đủ projection.

`INCLUDE` columns cho phép lưu thêm non-key data ở leaf level mà không làm chúng trở thành search/sort key.

## 3. How does it work?

Query:

```sql
SELECT OrderNumber, Total, CreatedAt
FROM Orders
WHERE CustomerId = @customerId;
```

Index:

```sql
CREATE INDEX IX_Orders_CustomerId
ON Orders(CustomerId);
```

SQL Server có thể seek theo `CustomerId`, nhưng cần lookup để lấy `OrderNumber`, `Total`, `CreatedAt`.

Potential covering index:

```sql
CREATE INDEX IX_Orders_CustomerId
ON Orders(CustomerId)
INCLUDE (OrderNumber, Total, CreatedAt);
```

## 4. Practical implementation

Không thêm INCLUDE chỉ vì thấy `Key Lookup`. Trước tiên kiểm tra execution plan:

* lookup chạy bao nhiêu lần
* estimated vs actual rows
* operator cost
* query frequency
* index size hiện tại

Nếu query chỉ trả 3 rows, lookup có thể rẻ. Nếu trả 100.000 rows, repeated lookup có thể thành random I/O đáng kể.

## 5. Real production scenario

Order-history API nhanh với khách hàng bình thường nhưng chậm với enterprise customer có 80.000 orders. Plan dùng seek rồi Key Lookup hàng chục nghìn lần.

Vấn đề không phải seek sai; vấn đề là lookup amplification theo cardinality.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 query latency tăng theo số rows của một customer.

**Evidence** → actual plan cho thấy Key Lookup execution count rất cao.

**Hypothesis** → nonclustered index không cover projection và lookup dominates I/O.

**Diagnosis** → đo logical reads bằng `SET STATISTICS IO ON` và so sánh plan variants.

**Fix** → cân nhắc INCLUDE columns, giảm projection hoặc đổi access pattern/pagination.

**Verification** → logical reads và p95 giảm trong representative workload.

## 7. Common mistakes

* Thấy Key Lookup là luôn xấu.
* INCLUDE quá nhiều columns làm index khổng lồ.
* Tạo index riêng cho mọi query shape.
* Không xét write workload và storage.
* Bỏ qua cardinality estimation sai khiến optimizer chọn plan không phù hợp.

## 8. Alternatives

* Giảm columns trong `SELECT`.
* Dùng keyset pagination để giới hạn rows.
* Tạo index khác với key order phù hợp hơn.
* Chấp nhận lookup nếu row count nhỏ và query hiếm.

## 9. Trade-offs

### Advantages

* Có thể giảm random I/O đáng kể.
* Giữ key nhỏ trong khi cover projection.

### Costs / Risks

* Index lớn hơn, tốn memory/storage.
* INSERT/UPDATE chậm hơn.
* Nhiều covering indexes dẫn tới index sprawl.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index seek không có nghĩa query đã đọc đủ columns.

### Middle

Biết đọc Key Lookup và actual execution count.

### Senior

Đánh đổi read latency với write amplification, cache footprint và maintenance.

### Technical Lead / Architect

Định nghĩa indexing strategy theo workload patterns thay vì tối ưu từng query riêng lẻ không kiểm soát.

## 11. Key takeaway

* `Key Lookup` chỉ xấu khi frequency/cardinality khiến cost đáng kể.
* `INCLUDE` là công cụ covering, không phải mặc định cho mọi projection.
* Luôn đo logical reads và workload impact trước khi thêm index.

# 5. DDD Domain Event vs Integration Event: tách invariant nội bộ khỏi contract phát ra ngoài bounded context

## 1. What is it?

`Domain Event` mô tả điều có ý nghĩa vừa xảy ra **bên trong domain model/bounded context**. `Integration Event` là message contract dùng để giao tiếp với hệ thống hoặc bounded context khác.

```text
Aggregate
  ↓ Domain Event
Application boundary
  ↓ translate
Integration Event
  ↓ broker
Other system
```

Hai loại có thể mang ý nghĩa gần nhau nhưng không nên mặc định là cùng class/schema.

## 2. Why does it exist?

Domain model cần quyền tiến hóa theo business logic nội bộ. External consumers cần contract ổn định hơn và không nên phụ thuộc cấu trúc aggregate nội bộ.

Nếu publish trực tiếp domain event ra broker, internal refactoring dễ trở thành breaking integration change.

## 3. How does it work?

Ví dụ aggregate phát:

```csharp
public sealed record OrderConfirmedDomainEvent(Guid OrderId);
```

Application handler có thể tạo integration event:

```csharp
public sealed record OrderConfirmedV1(
    Guid OrderId,
    DateTimeOffset ConfirmedAt,
    string CustomerId);
```

Integration event thường đi qua Outbox để đảm bảo state change và message publication không bị lệch nhau.

## 4. Practical implementation

```csharp
public async Task Handle(
    OrderConfirmedDomainEvent evt,
    CancellationToken ct)
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleAsync(x => x.Id == evt.OrderId, ct);

    db.OutboxMessages.Add(OutboxMessage.Create(
        new OrderConfirmedV1(
            order.Id,
            order.ConfirmedAt!.Value,
            order.CustomerId)));
}
```

Domain event phục vụ orchestration nội bộ; integration event là external contract có versioning policy riêng.

## 5. Real production scenario

Order bounded context thay đổi aggregate để tách ShippingAddress thành Value Object mới. Nếu integration message serialize trực tiếp aggregate/domain event, consumers có thể vỡ dù business contract external không đổi.

Tách integration contract giúp internal model tiến hóa độc lập.

## 6. Failure scenario & troubleshooting

**Symptom** → refactor nội bộ làm downstream service deserialize lỗi.

**Evidence** → broker payload dùng namespace/class schema giống domain event.

**Hypothesis** → internal model bị leak thành public event contract.

**Diagnosis** → không có translation layer/versioned integration schema.

**Fix** → tách domain event khỏi integration event và thêm compatibility tests.

**Verification** → internal refactor không thay payload contract ngoài bounded context.

## 7. Common mistakes

* Gọi mọi message là “domain event”.
* Publish aggregate object trực tiếp.
* Domain event handler gọi remote service synchronously trong cùng transaction.
* Không version integration event.
* Dùng event để che coupling thay vì thật sự tách ownership.

## 8. Alternatives

Một modular monolith nhỏ có thể chỉ dùng in-process domain notifications mà chưa cần broker/integration event. REST API vẫn phù hợp khi consumer cần synchronous query/command semantics.

## 9. Trade-offs

### Advantages

* Tách internal evolution khỏi external compatibility.
* Contract ownership rõ hơn.
* Hỗ trợ Outbox/event-driven integration sạch hơn.

### Costs / Risks

* Thêm mapping và event versions.
* Eventual consistency xuất hiện khi đi qua broker.
* Debug end-to-end phức tạp hơn synchronous calls.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event là “điều đã xảy ra”, không phải command trá hình.

### Middle

Biết tạo domain notification và integration message riêng.

### Senior

Hiểu transaction boundary, Outbox, schema evolution và consumer compatibility.

### Technical Lead / Architect

Quyết định event nào thực sự là external contract và ai sở hữu lifecycle/versioning của contract đó.

## 11. Key takeaway

* Domain Event thuộc domain boundary; Integration Event thuộc integration boundary.
* Đừng expose internal model chỉ vì serialization thuận tiện.
* Event-driven architecture vẫn cần contract governance.

# 6. Azure Service Bus Sessions: bảo toàn ordering theo business key mà không biến toàn queue thành single-threaded bottleneck

## 1. What is it?

Azure Service Bus Sessions nhóm messages theo `SessionId`. Một receiver lock một session và xử lý messages của session đó theo thứ tự, trong khi sessions khác vẫn có thể được xử lý song song.

```text
Order A: A1 → A2 → A3  ── consumer 1
Order B: B1 → B2       ── consumer 2
Order C: C1 → C2 → C3  ── consumer 3
```

## 2. Why does it exist?

Global ordering trên toàn queue phá throughput vì mọi message phải đi qua một serialization point.

Nhiều business workflows chỉ cần ordering **theo entity/key**, ví dụ cùng `OrderId`, `AccountId` hoặc `WorkflowId`.

Sessions tạo ordered partition theo business key.

## 3. How does it work?

Producer đặt cùng `SessionId` cho các messages cần ordering tương đối.

```csharp
var message = new ServiceBusMessage(payload)
{
    SessionId = orderId.ToString()
};
```

Session-aware receiver chấp nhận session, giữ session lock và process sequence. Các sessions độc lập có thể scale qua nhiều consumers.

At-least-once delivery vẫn áp dụng: session ordering không loại duplicate delivery.

## 4. Practical implementation

```csharp
var processor = client.CreateSessionProcessor(
    queueName,
    new ServiceBusSessionProcessorOptions
    {
        MaxConcurrentSessions = 16,
        MaxConcurrentCallsPerSession = 1,
        AutoCompleteMessages = false
    });

processor.ProcessMessageAsync += async args =>
{
    await handler.HandleAsync(args.Message, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message, args.CancellationToken);
};
```

`MaxConcurrentCallsPerSession = 1` giúp giữ serialization trong một session.

## 5. Real production scenario

Order workflow có events `Created`, `Paid`, `Packed`, `Shipped`. Không thể xử lý `Shipped` trước `Paid` cho cùng order, nhưng 100.000 orders khác nhau vẫn nên chạy song song.

`SessionId = OrderId` cho phép ordering theo order mà không khóa toàn hệ thống.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog tăng dù CPU consumers còn thấp.

**Evidence** → một vài sessions có lượng messages rất lớn; `MaxConcurrentSessions` thấp hoặc một hot session chiếm lâu.

**Hypothesis** → partition key/session design tạo hot session.

**Diagnosis** → đo backlog/processing duration theo `SessionId` business category.

**Fix** → chọn key có cardinality tốt, tăng concurrent sessions, tối ưu handler; nếu một entity thực sự quá nóng thì phải xem lại workflow serialization requirement.

**Verification** → throughput tăng mà ordering trong từng business key vẫn đúng.

## 7. Common mistakes

* Nghĩ Sessions tạo exactly-once delivery.
* Dùng một constant `SessionId` cho toàn queue.
* Chọn key quá coarse, tạo hot session.
* Process song song nhiều messages trong cùng session rồi phá ordering side effects.
* Không thiết kế idempotency.

## 8. Alternatives

* Queue bình thường nếu ordering không cần thiết.
* Partitioning ở application/database nếu workflow khác.
* Event stream platforms phù hợp hơn khi cần ordered log semantics ở scale lớn.

## 9. Trade-offs

### Advantages

* Ordering theo business key.
* Parallelism giữa sessions.
* Có thể giữ session state cho workflow use cases.

### Costs / Risks

* Session-aware infrastructure phức tạp hơn.
* Hot sessions giới hạn throughput.
* Ordering yêu cầu consumers disciplined hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ordering thường chỉ cần trong một nhóm messages, không phải toàn queue.

### Middle

Biết set `SessionId` và cấu hình session processor.

### Senior

Thiết kế idempotency, lock handling, poison messages và hot-session diagnosis.

### Technical Lead / Architect

Quyết định business key nào thật sự cần serialization và liệu messaging model có phù hợp hay đang che một aggregate/workflow boundary sai.

## 11. Key takeaway

* Sessions cho ordered concurrency theo key, không phải global ordering.
* Chọn `SessionId` sai có thể biến queue thành bottleneck.
* Ordering không thay thế idempotency.

# 7. Kubernetes readiness, liveness và startup probes: health check sai có thể tự tạo outage như thế nào

## 1. What is it?

Kubernetes probes trả lời ba câu hỏi khác nhau:

* **readiness**: pod có nên nhận traffic không?
* **liveness**: process có bị kẹt và cần restart không?
* **startup**: application có còn đang khởi động hợp lệ không?

Nhầm ba khái niệm này có thể khiến orchestration tự giết application đang khỏe hoặc route traffic vào pod chưa sẵn sàng.

## 2. Why does it exist?

Process “đang chạy” không đồng nghĩa application “phục vụ được traffic”. Ngược lại, dependency tạm thời down cũng không phải lúc nào là lý do restart process.

Kubernetes cần signals khác nhau để quyết định routing và lifecycle.

## 3. How does it work?

```text
startupProbe fails → chờ startup, chưa áp liveness bình thường
readinessProbe fails → remove pod khỏi Service endpoints
livenessProbe fails repeatedly → restart container
```

Nếu readiness check SQL dependency và SQL chập chờn, pod có thể tạm ngừng nhận traffic hợp lý. Nhưng nếu liveness cũng phụ thuộc SQL, toàn bộ pods có thể restart đồng loạt khi database outage, làm sự cố tệ hơn.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy())
    .AddSqlServer(connectionString, name: "sql");

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = r => r.Name == "self"
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = _ => true
});
```

Kubernetes:

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
startupProbe:
  httpGet:
    path: /health/live
    port: 8080
  failureThreshold: 30
  periodSeconds: 5
```

## 5. Real production scenario

Database có outage 2 phút. Mọi pod dùng DB check cho liveness. Kubernetes restart toàn bộ application pods liên tục. Khi DB phục hồi, apps vẫn đang cold start và connection storms xuất hiện.

Một dependency outage nhỏ biến thành full application outage do probe semantics sai.

## 6. Failure scenario & troubleshooting

**Symptom** → pods `RESTARTS` tăng nhanh cùng lúc dependency bên ngoài gặp lỗi.

**Evidence** → events hiển thị liveness probe failures; application logs không cho thấy process deadlock.

**Hypothesis** → liveness phụ thuộc remote dependency.

**Diagnosis** → kiểm tra health endpoint composition và Kubernetes events.

**Fix** → liveness chỉ phản ánh process self-health; readiness có thể xét critical dependencies với policy thận trọng.

**Verification** → simulate dependency outage; pods ngừng nhận traffic nếu cần nhưng không restart storm.

## 7. Common mistakes

* Dùng cùng endpoint cho cả readiness/liveness mà không phân semantics.
* Liveness gọi mọi remote dependency.
* Timeout probe quá ngắn so với startup behavior.
* Readiness luôn trả healthy dù app chưa load config/migrations cần thiết.
* Health endpoint làm expensive query và tự tạo load.

## 8. Alternatives

Một ứng dụng đơn giản trên App Service/IIS có health-check model khác nhưng nguyên lý vẫn giống: routing health và process health là hai signals khác nhau.

## 9. Trade-offs

### Advantages

* Tự động loại instance chưa sẵn sàng.
* Có thể recover process thật sự stuck.
* Hỗ trợ rolling deployment an toàn hơn.

### Costs / Risks

* Probe sai tạo restart storm hoặc traffic blackhole.
* Dependency checks có thể tăng load.
* Thresholds cần phù hợp startup/runtime characteristics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Nhớ readiness = traffic, liveness = restart, startup = startup grace.

### Middle

Biết expose separate health endpoints và đọc Kubernetes events.

### Senior

Thiết kế dependency health semantics, thresholds và failure behavior.

### Technical Lead / Architect

Xác định service-level degraded mode: dependency nào làm instance unavailable, dependency nào chỉ làm một feature unavailable.

## 11. Key takeaway

* Health check là control signal cho orchestrator, không chỉ monitoring endpoint.
* Remote dependency failure hiếm khi nên trực tiếp làm liveness fail.
* Probe design sai có thể khuếch đại outage.

# 8. OpenTelemetry sampling: head sampling, tail sampling và trade-off giữa observability fidelity với telemetry cost

## 1. What is it?

Sampling quyết định trace nào được giữ lại thay vì export 100% telemetry.

* **Head sampling** quyết định sớm khi trace bắt đầu.
* **Tail sampling** quyết định sau khi đã thấy nhiều hoặc toàn bộ spans của trace.

```text
Request starts
   ↓
Head sampling? decide now

Request completes
   ↓
Tail sampling? decide using outcome/latency/errors
```

## 2. Why does it exist?

Ở traffic lớn, export mọi span làm storage, network và observability cost tăng nhanh. Nhưng drop sai traces có thể khiến incident khó điều tra.

Sampling là bài toán giữ **signal có giá trị cao** trong budget hữu hạn.

## 3. How does it work?

Head sampling có thể giữ 10% traces ngẫu nhiên. Ưu điểm: đơn giản và rẻ. Nhược điểm: tại thời điểm quyết định chưa biết request sẽ trở thành error hay p99.

Tail sampling có thể giữ:

* 100% error traces
* 100% traces > 2 giây
* 5% success traces bình thường

Nhưng collector phải buffer trace data tới khi đủ context để quyết định.

## 4. Practical implementation

Trong .NET SDK, head sampler có thể cấu hình parent-based probability:

```csharp
services.AddOpenTelemetry()
    .WithTracing(builder => builder
        .SetSampler(new ParentBasedSampler(
            new TraceIdRatioBasedSampler(0.1)))
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation());
```

Tail sampling thường triển khai ở OpenTelemetry Collector layer thay vì app process.

## 5. Real production scenario

Checkout service xử lý 5.000 requests/second. Export 100% traces làm telemetry bill tăng mạnh. Team chuyển xuống 5% random head sampling và vô tình gần như mất toàn bộ traces của lỗi hiếm 0,01%.

Giải pháp tốt hơn là tail sampling hoặc policy kết hợp error/latency signals.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard metrics cho thấy 500 errors nhưng gần như không có error traces để điều tra.

**Evidence** → sampling config dùng low-rate head sampler thuần random.

**Hypothesis** → error traces bị drop trước khi biết outcome.

**Diagnosis** → so sánh metrics error count với sampled trace count.

**Fix** → điều chỉnh sampling strategy; dùng tail sampling hoặc custom rules phù hợp.

**Verification** → synthetic errors xuất hiện với expected trace retention ratio.

## 7. Common mistakes

* Sampling traces nhưng nghĩ metrics cũng bị sampling cùng cách.
* Đặt sampling rate quá thấp mà không biết incident-detection requirements.
* Tail sampling nhưng collector thiếu memory/buffer capacity.
* Không propagate sampling decision qua distributed trace.
* Sampling theo user ID/high-cardinality rule thiếu kiểm soát.

## 8. Alternatives

* 100% tracing: đơn giản, phù hợp traffic thấp hoặc critical environment nhỏ.
* Head sampling: rẻ, dễ scale.
* Tail sampling: nhiều signal hơn nhưng collector phức tạp và tốn tài nguyên hơn.

## 9. Trade-offs

### Advantages

* Kiểm soát telemetry cost.
* Tail sampling giữ được rare/high-value traces tốt hơn.

### Costs / Risks

* Mất visibility nếu policy sai.
* Tail sampling cần stateful buffering.
* Debugging cross-service khó nếu sampling propagation không nhất quán.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace sampling nghĩa là không phải mọi request đều có trace lưu lại.

### Middle

Biết cấu hình head sampling và kiểm tra propagation.

### Senior

Thiết kế sampling theo error, latency, critical paths và volume.

### Technical Lead / Architect

Định nghĩa observability budget và evidence-retention policy thay vì chỉ tối ưu bill hoặc giữ 100% vô hạn.

## 11. Key takeaway

* Sampling là reliability/cost decision, không chỉ config observability.
* Head sampling rẻ nhưng quyết định trước outcome.
* Tail sampling giữ high-value traces tốt hơn nhưng tăng collector complexity.

# 9. Canary deployment + feature flags: giảm blast radius nhưng vẫn phải tách deployment risk khỏi release risk

## 1. What is it?

Canary deployment đưa version mới tới một tỷ lệ traffic/instances nhỏ trước khi mở rộng. Feature flag kiểm soát **behavior** độc lập với việc binary/version đã được deploy hay chưa.

```text
Deploy code v2 to 5% traffic
        ↓
Observe health
        ↓
Increase traffic

Feature flag:
code already deployed
        ↓
turn behavior on for selected users
```

## 2. Why does it exist?

Một deployment có thể fail vì runtime, config hoặc performance. Một feature có thể fail vì business logic dù binary chạy ổn.

Nếu release và deployment luôn là một hành động duy nhất, rollback thường nặng và blast radius lớn.

## 3. How does it work?

Canary thường dựa trên weighted routing hoặc subset of instances. Decision promote nên dựa vào telemetry:

* 5xx rate
* p95/p99 latency
* saturation
* dependency errors
* business KPI nếu phù hợp

Feature flag cho phép activation theo user, tenant hoặc percentage nhưng phải có lifecycle và ownership.

## 4. Practical implementation

ASP.NET Core:

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
{
    return await newCheckout.ExecuteAsync(request, ct);
}

return await legacyCheckout.ExecuteAsync(request, ct);
```

CI/CD flow:

```text
build once
→ deploy canary
→ health validation
→ expand deployment
→ enable feature for internal users
→ gradual feature rollout
```

## 5. Real production scenario

New checkout implementation deploy lên Production nhưng để flag OFF. Canary xác nhận app startup, memory và dependency behavior ổn. Sau đó flag bật cho 1% users; business error rate tăng dù infrastructure metrics bình thường.

Team tắt flag ngay mà không rollback deployment.

## 6. Failure scenario & troubleshooting

**Symptom** → canary infrastructure healthy nhưng conversion/checkout failures tăng khi rollout feature.

**Evidence** → errors correlate với flag cohort, không correlate với pod version vì tất cả pods đã có code.

**Hypothesis** → feature behavior lỗi, không phải deployment mechanics.

**Diagnosis** → log/trace phải chứa feature-flag dimension có cardinality kiểm soát.

**Fix** → disable flag, sửa logic, giữ binary nếu phần khác ổn.

**Verification** → cohort metrics trở lại baseline.

## 7. Common mistakes

* Build artifact khác nhau cho canary và full rollout.
* Không có automatic/clear rollback criteria.
* Feature flags sống mãi thành technical debt.
* Dùng flag cho schema incompatible change mà không có expand-contract.
* Chỉ nhìn CPU/5xx mà bỏ business correctness metrics.

## 8. Alternatives

* Blue-Green: cutover giữa hai environments, rollback nhanh nhưng resource cost cao.
* Rolling deployment: đơn giản hơn nhưng ít kiểm soát exposure.
* Deployment slots trên App Service: phù hợp nhiều web workloads.

## 9. Trade-offs

### Advantages

* Giảm blast radius.
* Tách code deployment khỏi feature release.
* Có rollback behavior nhanh qua flag.

### Costs / Risks

* Routing/flagging infrastructure tăng complexity.
* Test matrix tăng vì nhiều flag states.
* Flag cleanup cần governance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy code và release feature là hai việc khác nhau.

### Middle

Biết instrument rollout và rollback theo metrics.

### Senior

Thiết kế compatibility, cohort analysis, flag lifecycle và database changes an toàn.

### Technical Lead / Architect

Chọn rollout strategy theo blast radius, recovery time và operational maturity của team.

## 11. Key takeaway

* Canary giảm exposure của deployment risk; feature flags giảm exposure của behavior risk.
* Rollout chỉ an toàn khi có telemetry và stop criteria rõ.
* Feature flag không được trở thành permanent branching architecture.

# 10. RAG evaluation: đo retrieval quality bằng Recall@K, MRR và groundedness thay vì đánh giá “câu trả lời nghe có vẻ đúng”

## 1. What is it?

RAG evaluation tách hệ thống thành ít nhất hai phần cần đo riêng:

```text
Question
   ↓
Retriever → relevant chunks?
   ↓
LLM → answer grounded in retrieved evidence?
```

Nếu answer sai, cần biết lỗi nằm ở retrieval hay generation. Chỉ đọc câu trả lời và chấm “có vẻ ổn” không đủ để cải thiện hệ thống.

## 2. Why does it exist?

Một RAG system có thể hallucinate dù retrieval tốt, hoặc trả lời thiếu vì retriever không lấy đúng document. Hai failure modes cần fixes hoàn toàn khác nhau.

Without evaluation dataset, thay chunk size, embedding model hoặc prompt dễ trở thành trial-and-error không có evidence.

## 3. How does it work?

Với một golden dataset, mỗi câu hỏi có expected relevant documents/chunks và reference answer hoặc grading criteria.

Một số retrieval metrics:

* **Recall@K**: trong top K có lấy được relevant evidence hay không/bao nhiêu.
* **MRR**: relevant result đầu tiên đứng càng cao càng tốt.
* precision-like metrics: top K có bao nhiêu noise.

Generation metrics nên xem groundedness/citation support và task correctness, không chỉ lexical similarity.

## 4. Practical implementation

Một evaluation record có thể là:

```json
{
  "question": "How long is the support-access window?",
  "relevantDocumentIds": ["support-policy-v3"],
  "requiredFacts": ["24 hours default"],
  "forbiddenClaims": ["permanent access"]
}
```

Pipeline:

```text
run retriever
→ record topK IDs/scores
→ calculate retrieval metrics
→ run answer generation
→ grade groundedness/correctness
→ compare against previous baseline
```

Business-critical facts nên có deterministic assertions khi có thể.

## 5. Real production scenario

Internal knowledge assistant bắt đầu trả lời sai policy sau khi team đổi chunking strategy. LLM model và prompt không đổi.

Evaluation cho thấy Recall@5 giảm từ 94% xuống 71% vì headings bị tách khỏi policy paragraphs. Root cause nằm ở ingestion/chunking, không phải model reasoning.

## 6. Failure scenario & troubleshooting

**Symptom** → answer quality giảm sau embedding/chunking change.

**Evidence** → groundedness thấp và relevant document thường không xuất hiện trong top K.

**Hypothesis** → retrieval regression.

**Diagnosis** → so sánh Recall@K/MRR trước và sau change theo từng query category.

**Fix** → điều chỉnh chunking, metadata filters, hybrid search hoặc reranking.

**Verification** → evaluation metrics phục hồi và manual spot-check xác nhận không overfit dataset.

## 7. Common mistakes

* Chỉ chấm final answer, không đo retriever.
* Dùng vài câu hỏi demo làm benchmark.
* Dùng LLM judge mà không có deterministic checks cho critical facts.
* Đổi embedding, chunking, prompt và reranker cùng lúc nên không biết cải thiện đến từ đâu.
* Tối ưu Recall@K nhưng để context đầy noise làm generation tệ hơn.

## 8. Alternatives

Không phải mọi knowledge lookup đều cần RAG. Structured database query, search filters hoặc deterministic rules có thể chính xác và rẻ hơn cho dữ liệu có schema rõ.

Full-text/BM25 search cũng có thể đủ tốt nếu semantic mismatch không phải vấn đề chính.

## 9. Trade-offs

### Advantages

* Biến quality thành thứ có thể regression-test.
* Phân biệt retrieval failure và generation failure.
* Hỗ trợ lựa chọn chunking/embedding/reranking dựa trên evidence.

### Costs / Risks

* Golden dataset cần bảo trì.
* LLM-based grading có variance.
* Offline metrics không luôn phản ánh Production user distribution.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG có hai bước chính: tìm evidence và tạo answer từ evidence.

### Middle

Biết tạo evaluation dataset và đo Recall@K/MRR cơ bản.

### Senior

Phân tích regressions theo retrieval, reranking, context construction và generation.

### Technical Lead / Architect

Quyết định use case nào cần RAG, quality threshold nào đủ cho Production và logic nào phải giữ deterministic vì correctness/security.

## 11. Key takeaway

* Không thể cải thiện RAG nghiêm túc nếu không tách retrieval quality khỏi answer quality.
* Recall@K/MRR giúp đo liệu evidence có được tìm thấy đúng vị trí.
* Business-critical facts cần deterministic validation thay vì tin hoàn toàn vào model judge.
