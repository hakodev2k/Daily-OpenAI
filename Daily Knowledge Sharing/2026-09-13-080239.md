# 1. C# Nullable Reference Types: flow analysis, annotation context và vì sao compiler warning không thay thế runtime validation

## 1. What is it?

Nullable Reference Types (NRT) là hệ thống annotation + static flow analysis của C# giúp compiler phân biệt reference được kỳ vọng **không null** và reference **có thể null**.

Mental model:

```text
string  -> contract nói rằng value không nên null
string? -> contract nói rằng null là một trạng thái hợp lệ
```

NRT không thay CLR type system. Ở runtime, `string` và `string?` vẫn đều là reference type. Giá trị `null` vẫn có thể xuất hiện nếu đến từ reflection, serialization, legacy assembly, database mapping sai, external API hoặc code dùng null-forgiving operator `!`.

Điểm quan trọng hơn syntax `?` là **flow analysis**. Compiler theo dõi nhánh code để suy ra một value đã được kiểm tra null hay chưa.

## 2. Why does it exist?

Trước NRT, API như:

```csharp
Customer Find(string id)
```

không nói rõ method có thể trả `null` hay không. Developer phải đọc docs, implementation hoặc chờ `NullReferenceException` ở Production.

NRT biến một phần intent đó thành compile-time contract. Điều này đặc biệt có giá trị ở codebase lớn vì nullability được truyền xuyên method signature, generics, properties và external annotations.

Tuy nhiên, compiler chỉ bảo vệ những gì nó có thể suy luận trong code được annotate đúng. NRT không xác thực input bên ngoài hệ thống.

## 3. How does it work?

Compiler kết hợp annotation context với control-flow analysis:

```csharp
string? name = GetName();

if (name is null)
    return;

Console.WriteLine(name.Length); // safe theo flow analysis
```

Sau nhánh `if`, compiler biết `name` không còn null trên execution path đó.

Attributes như `NotNullWhen`, `MemberNotNull`, `AllowNull`, `DisallowNull` có thể mô tả contract phức tạp hơn khi compiler không tự suy ra đủ.

Ví dụ helper:

```csharp
public static bool HasValue(
    [System.Diagnostics.CodeAnalysis.NotNullWhen(true)] string? value)
    => !string.IsNullOrWhiteSpace(value);
```

Nếu `HasValue(value)` trả `true`, compiler hiểu `value` là non-null.

## 4. Practical implementation

Một API boundary nên kết hợp NRT với runtime validation:

```csharp
public sealed record CreateUserRequest(
    string Email,
    string? DisplayName);

app.MapPost("/users", async (
    CreateUserRequest request,
    UserService service,
    CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(request.Email))
    {
        return Results.ValidationProblem(new Dictionary<string, string[]>
        {
            ["email"] = ["Email is required."]
        });
    }

    var user = await service.CreateAsync(
        request.Email,
        request.DisplayName,
        ct);

    return Results.Created($"/users/{user.Id}", user);
});
```

`string Email` nói lên developer contract. Runtime validation vẫn bắt payload JSON thiếu field, field null hoặc empty string tùy serializer/model-binding behavior.

## 5. Real production scenario

Một service migrate từ legacy .NET Framework sang .NET 8. Project mới bật NRT nhưng shared library cũ chưa annotate. Compiler coi nhiều return values là “oblivious”, khiến cảm giác an toàn giả.

Nếu team chỉ sửa warnings bằng `!`, code compile sạch nhưng risk không giảm. Migration đúng cần phân loại:

```text
trusted internal invariant
vs
legacy unknown contract
vs
external/untrusted input
```

Với external boundary, validation vẫn bắt buộc.

## 6. Failure scenario & troubleshooting

**Symptom:** code không có nullable warning nhưng Production vẫn `NullReferenceException`.

**Evidence:** stack trace cho thấy value đến từ JSON/deserialization hoặc legacy library.

**Hypothesis:** compiler contract không phản ánh runtime reality.

**Diagnosis:** trace nguồn value; kiểm tra NRT annotation của assembly, serializer options và các `!` đã dùng.

**Fix:** thêm runtime validation tại boundary, sửa annotations đúng nghĩa và loại bỏ null-forgiving operator không có invariant chứng minh được.

**Verification:** thêm integration tests với missing/null fields và static build với nullable warnings được treat nghiêm túc.

## 7. Common mistakes

- Dùng `!` để “dọn warning” thay vì chứng minh invariant.
- Nghĩ `string` nghĩa là runtime không thể nhận null.
- Bật NRT rồi sửa hàng nghìn warnings cơ học mà không phân loại boundary.
- Trả `null` từ method annotate non-null vì “caller biết mà”.
- Dùng nullable cho mọi property để serializer dễ chạy, làm contract mất ý nghĩa.

## 8. Alternatives

- **Runtime guard clauses:** bắt buộc cho input không đáng tin; không thay compile-time contract.
- **Option/Maybe type:** explicit hơn cho domain nơi “không có value” là trạng thái business quan trọng.
- **Result type:** tốt khi cần phân biệt nhiều failure states thay vì null.

NRT phù hợp nhất để biểu diễn nullability của reference trong C# API contract, không phải mọi dạng absence/error.

## 9. Trade-offs

### Advantages

- Phát hiện nhiều null bug trước runtime.
- Signature truyền intent rõ hơn giữa teams.
- Refactoring an toàn hơn trong codebase lớn.

### Costs / Risks

- Migration codebase cũ có thể nhiều warnings.
- Annotation sai tạo false confidence.
- Interop với legacy/reflection/generated code cần judgment.
- Overuse custom attributes có thể làm contract khó đọc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `string` và `string?` là contract, không chỉ syntax.

### Middle

Biết flow analysis, guard clauses, nullable generics và xử lý warnings đúng nguyên nhân.

### Senior

Phân biệt compile-time null safety với runtime boundary validation; review `!` như một risk signal.

### Technical Lead / Architect

Đặt migration policy cho legacy code, quyết định warning severity và chuẩn hóa nullability ở public/shared contracts mà không biến migration thành churn không tạo giá trị.

## 11. Key takeaway

- NRT là compile-time contract + flow analysis, không phải runtime guarantee.
- `!` là assertion của developer, không phải fix tự động.
- External data vẫn cần runtime validation dù code compile không có warning.

# 2. ASP.NET Core `IAsyncEnumerable<T>` response streaming: giảm peak memory nhưng phải hiểu cancellation, buffering và partial response failure

## 1. What is it?

`IAsyncEnumerable<T>` cho phép producer tạo từng item asynchronously thay vì materialize toàn bộ collection trước khi caller nhận dữ liệu.

Mental model:

```text
Database/API
   -> item 1 -> response
   -> item 2 -> response
   -> item 3 -> response
```

Khác với:

```text
Database -> load 500,000 items -> List<T> -> serialize toàn bộ -> response
```

Streaming giúp giảm time-to-first-byte và peak memory trong một số workload lớn.

## 2. Why does it exist?

Một endpoint export hoặc feed có thể trả hàng trăm nghìn records. Nếu dùng `ToListAsync()`, application phải giữ toàn bộ result + serialization buffers trước hoặc trong lúc trả response.

Streaming cho phép pipeline consume dữ liệu dần dần. Nhưng đổi lại, transaction/database connection có thể bị giữ lâu hơn và sau khi response bắt đầu thì error handling bị giới hạn.

## 3. How does it work?

Một `async iterator` dùng `yield return` và có thể `await` giữa các lần yield:

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [System.Runtime.CompilerServices.EnumeratorCancellation]
    CancellationToken ct)
{
    await foreach (var order in db.Orders
        .AsNoTracking()
        .OrderBy(x => x.Id)
        .Select(x => new OrderDto(x.Id, x.Total))
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        yield return order;
    }
}
```

ASP.NET Core serializer có thể enumerate sequence trong lúc viết response. Caller disconnect nên propagate qua cancellation để database enumeration dừng sớm.

## 4. Practical implementation

Minimal API:

```csharp
app.MapGet("/orders/stream", (
    OrderStreamService service,
    HttpContext httpContext) =>
{
    return service.StreamOrdersAsync(httpContext.RequestAborted);
});
```

Với NDJSON hoặc custom streaming contract, có thể kiểm soát framing rõ hơn:

```csharp
app.MapGet("/orders.ndjson", async (
    HttpContext context,
    OrderStreamService service) =>
{
    context.Response.ContentType = "application/x-ndjson";

    await foreach (var item in service
        .StreamOrdersAsync(context.RequestAborted))
    {
        await System.Text.Json.JsonSerializer.SerializeAsync(
            context.Response.Body,
            item,
            cancellationToken: context.RequestAborted);

        await context.Response.WriteAsync("\n", context.RequestAborted);
    }
});
```

## 5. Real production scenario

Một admin portal export 300.000 audit events. Version đầu query toàn bộ vào `List<AuditEventDto>` khiến mỗi request dùng hàng trăm MB memory khi nhiều user export cùng lúc.

Streaming giảm peak memory, nhưng database connection bị giữ suốt 1–2 phút. Nếu pool chỉ có 100 connections và 50 exports chạy đồng thời, endpoint khác có thể bị starvation.

Optimization memory đã chuyển pressure sang connection pool. Senior engineer phải nhìn toàn pipeline.

## 6. Failure scenario & troubleshooting

**Symptom:** export memory tốt hơn nhưng API khác bắt đầu timeout khi nhiều export chạy.

**Evidence:** DB pool active connections tăng, export durations dài, request response đã bắt đầu.

**Hypothesis:** streaming giữ database reader/connection lâu.

**Diagnosis:** correlate export concurrency, connection pool metrics, dependency duration và request traces.

**Fix:** giới hạn concurrent exports, chunk sang durable file/background job hoặc dùng pagination/chunked data source phù hợp.

**Verification:** load test với realistic concurrency, theo dõi p95 API khác và connection pool saturation.

## 7. Common mistakes

- Nghĩ streaming luôn nhanh hơn materialization.
- Không propagate `RequestAborted`.
- Streaming từ một transaction kéo dài hàng phút.
- Sau khi đã ghi một phần response vẫn cố đổi status code sang 500.
- Dùng JSON array cực lớn nhưng không cân nhắc client parsing/buffering.

## 8. Alternatives

- **Paged API:** tốt cho interactive clients.
- **Background export + Blob Storage:** tốt cho file lớn, retry và download lại.
- **Materialize small result:** đơn giản và thường đúng khi payload nhỏ.
- **NDJSON streaming:** phù hợp consumer xử lý record-by-record.

## 9. Trade-offs

### Advantages

- Peak memory thấp hơn.
- Time-to-first-byte tốt hơn.
- Có thể xử lý datasets lớn mà không tạo list khổng lồ.

### Costs / Risks

- Giữ DB/network resource lâu hơn.
- Partial response khó rollback.
- Client cần hiểu streaming format.
- Observability/tracing phải bao được long-lived request.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu difference giữa materialize và stream.

### Middle

Implement `IAsyncEnumerable<T>`, cancellation và serialization đúng.

### Senior

Đánh giá connection lifetime, backpressure, partial failure và client behavior.

### Technical Lead / Architect

Quyết định workload nào nên synchronous stream, workload nào nên background export/durable object; đặt concurrency limit và resource budget.

## 11. Key takeaway

- Streaming giảm memory nhưng không xóa cost; nó thay đổi nơi cost xuất hiện.
- Long-lived stream phải có cancellation và capacity control.
- Với export rất lớn, background file generation thường dễ vận hành hơn request kéo dài.

# 3. EF Core `DbContext` thread safety: vì sao parallel query trên cùng context lỗi dù database hỗ trợ concurrency

## 1. What is it?

`DbContext` là unit-of-work + identity map + change tracker và **không thread-safe**. Một instance không được dùng cho nhiều operations đồng thời.

Mental model:

```text
1 DbContext
  -> 1 tracked state graph
  -> operations expected sequentially
```

Database server có thể xử lý hàng nghìn concurrent queries, nhưng điều đó không có nghĩa một `DbContext` instance có thể phát nhiều command parallel an toàn.

## 2. Why does it exist?

EF Core giữ mutable internal state: tracked entities, state manager, current transaction, connection usage và query materialization context. Cho nhiều threads mutate state đó đồng thời sẽ tạo race condition hoặc ambiguous ownership.

Vì vậy EF Core fail-fast với lỗi kiểu “A second operation was started on this context instance before a previous operation completed.”

## 3. How does it work?

Sai:

```csharp
var usersTask = db.Users.ToListAsync(ct);
var ordersTask = db.Orders.ToListAsync(ct);

await Task.WhenAll(usersTask, ordersTask);
```

Cả hai dùng cùng context đồng thời.

Đúng nếu không cần parallelism:

```csharp
var users = await db.Users.ToListAsync(ct);
var orders = await db.Orders.ToListAsync(ct);
```

Nếu thật sự cần parallel independent queries, dùng independent contexts:

```csharp
await using var db1 = await factory.CreateDbContextAsync(ct);
await using var db2 = await factory.CreateDbContextAsync(ct);

var usersTask = db1.Users.AsNoTracking().ToListAsync(ct);
var ordersTask = db2.Orders.AsNoTracking().ToListAsync(ct);

await Task.WhenAll(usersTask, ordersTask);
```

## 4. Practical implementation

Đăng ký factory khi background/concurrent workload cần tạo context theo unit-of-work:

```csharp
builder.Services.AddDbContextFactory<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Worker:

```csharp
public sealed class BatchWorker(IDbContextFactory<AppDbContext> factory)
{
    public async Task ProcessAsync(IEnumerable<long> ids, CancellationToken ct)
    {
        await Parallel.ForEachAsync(
            ids,
            new ParallelOptions
            {
                MaxDegreeOfParallelism = 8,
                CancellationToken = ct
            },
            async (id, token) =>
            {
                await using var db = await factory.CreateDbContextAsync(token);
                var entity = await db.Items.FindAsync([id], token);

                if (entity is not null)
                {
                    entity.MarkProcessed();
                    await db.SaveChangesAsync(token);
                }
            });
    }
}
```

Degree of parallelism phải dựa trên DB capacity, không phải CPU count một cách mù quáng.

## 5. Real production scenario

Một request dashboard cần 8 widgets. Developer dùng `Task.WhenAll` trên 8 repository methods nhưng tất cả repositories inject cùng scoped `DbContext`.

Local traffic thấp có thể lúc được lúc lỗi. Production bắt đầu ném “second operation” exception.

Fix không nhất thiết là tạo 8 contexts. Có thể một query/projection tốt hơn, stored read model, cache hoặc sequential calls rẻ hơn tổng complexity của parallel DB access.

## 6. Failure scenario & troubleshooting

**Symptom:** intermittent EF Core concurrency exception.

**Evidence:** cùng request trace có multiple DB operations overlap trên cùng service scope.

**Hypothesis:** scoped context bị dùng parallel qua `Task.WhenAll`, event handlers hoặc fire-and-forget task.

**Diagnosis:** inspect call graph, DI lifetime và timing spans.

**Fix:** await tuần tự, tạo independent context per operation hoặc redesign query.

**Verification:** stress test request concurrency và đảm bảo không còn overlapping operations trên cùng context instance.

## 7. Common mistakes

- Nghĩ scoped service đồng nghĩa thread-safe.
- Share context qua parallel loops.
- Cất scoped context vào singleton/background queue.
- Tạo context mới vô hạn rồi làm connection pool quá tải.
- Parallelize queries trước khi đo latency source.

## 8. Alternatives

- **Sequential queries:** đơn giản, thường đủ.
- **Single optimized projection:** thường tốt hơn nhiều queries parallel.
- **Independent contexts:** đúng khi workloads thực sự độc lập và DB chịu được concurrency.
- **Read model/cache:** phù hợp dashboard/read-heavy scenario.

## 9. Trade-offs

### Advantages

- Context per unit-of-work giữ state isolation rõ ràng.
- Factory hữu ích cho workers/blazor/background workloads.

### Costs / Risks

- Parallel contexts tăng DB connections và load.
- Nhiều unit-of-work không còn share transaction mặc định.
- Over-parallelization có thể làm latency tail tệ hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbContext` không thread-safe và phải await operation trước khi reuse.

### Middle

Biết khi nào dùng `IDbContextFactory`, scoped context và transaction riêng.

### Senior

Đánh giá parallelism theo DB capacity, query plan và pool budget thay vì “Task.WhenAll cho nhanh”.

### Technical Lead / Architect

Thiết kế read path sao cho concurrency hợp lý; quyết định khi nào cần aggregate query/read model thay vì tạo fan-out xuống database.

## 11. Key takeaway

- Database concurrency không đồng nghĩa `DbContext` concurrency.
- Parallelism cần independent context và capacity budget.
- Nhiều khi query tốt hơn quan trọng hơn chạy nhiều query cùng lúc.

# 4. PostgreSQL Partial Index: index ít dữ liệu hơn nhưng chỉ hiệu quả khi predicate thực sự khớp access pattern

## 1. What is it?

Partial index là index chỉ chứa rows thỏa một predicate.

Ví dụ hệ thống có 100 triệu orders nhưng chỉ 2% ở trạng thái `Pending`:

```sql
CREATE INDEX ix_orders_pending_created_at
ON orders (created_at, id)
WHERE status = 'Pending';
```

Index này nhỏ hơn nhiều so với index trên toàn bộ bảng nếu query thường xuyên chỉ quan tâm pending orders.

## 2. Why does it exist?

Full index có storage, write amplification, maintenance và cache cost. Nếu workload chỉ truy cập một subset ổn định của rows, indexing toàn bộ dữ liệu có thể lãng phí.

Partial index cho phép database giữ access path nhỏ và selective hơn cho query quan trọng.

## 3. How does it work?

Planner chỉ dùng partial index khi có thể chứng minh query predicate phù hợp với index predicate.

Query tốt:

```sql
SELECT id, created_at
FROM orders
WHERE status = 'Pending'
ORDER BY created_at, id
LIMIT 100;
```

Planner có thể scan partial index thay vì index/full table lớn.

Nếu query dùng predicate khác hoặc logic khó suy ra tương đương, index có thể không được chọn.

## 4. Practical implementation

Trước khi tạo index, đo dữ liệu:

```sql
SELECT status, COUNT(*)
FROM orders
GROUP BY status;
```

Sau đó kiểm tra query plan:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at
FROM orders
WHERE status = 'Pending'
ORDER BY created_at, id
LIMIT 100;
```

Không dừng ở việc thấy “Index Scan”. Xem actual rows, buffer hits/reads và latency.

## 5. Real production scenario

Approval system giữ 50 triệu workflow items, 48 triệu đã `Completed`. Dashboard mỗi phút query những item `Pending` gần nhất cho từng team.

Full composite index `(status, created_at)` vẫn lớn vì chứa mọi row. Partial index chỉ cho `Pending` giữ hot working set nhỏ hơn và giảm maintenance cho completed history.

Nhưng nếu status thay đổi liên tục, mỗi transition Pending → Completed cũng là index delete; write cost vẫn tồn tại.

## 6. Failure scenario & troubleshooting

**Symptom:** đã tạo partial index nhưng query vẫn sequential scan.

**Evidence:** `EXPLAIN ANALYZE` không dùng index; query predicate khác kiểu/cấu trúc so với index condition hoặc selectivity không tốt.

**Hypothesis:** planner không chứng minh predicate implication hoặc cost estimate cho rằng scan rẻ hơn.

**Diagnosis:** inspect exact SQL, parameters, statistics, row distribution và plan.

**Fix:** align access pattern/index predicate, update statistics, hoặc bỏ index nếu workload không phù hợp.

**Verification:** so buffer I/O, execution time và write overhead trước/sau dưới dữ liệu thật.

## 7. Common mistakes

- Tạo partial index chỉ vì bảng lớn mà không có stable subset.
- Nghĩ index nhỏ luôn được dùng.
- Không đo write amplification khi rows thường xuyên vào/ra predicate.
- Tạo quá nhiều status-specific indexes.
- Chỉ nhìn query latency mà bỏ qua storage/cache/maintenance cost.

## 8. Alternatives

- **Full composite index:** đơn giản hơn nếu nhiều statuses đều được query.
- **Covering/index INCLUDE:** hữu ích khi muốn giảm heap access.
- **Partitioning:** phù hợp data lifecycle/access boundaries lớn hơn, nhưng complexity cao hơn.
- **Archive table:** khi historical data có lifecycle hoàn toàn khác.

## 9. Trade-offs

### Advantages

- Index nhỏ hơn.
- Có thể fit cache tốt hơn.
- Giảm write/index maintenance cho rows ngoài predicate.

### Costs / Risks

- Chỉ phục vụ subset query rõ ràng.
- Planner matching có nuance.
- Nhiều partial indexes làm schema khó quản lý.
- Predicate distribution thay đổi theo thời gian có thể làm index mất giá trị.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không nhất thiết chứa mọi row.

### Middle

Biết tạo partial index và dùng `EXPLAIN ANALYZE` xác nhận.

### Senior

Đánh giá selectivity, write cost, statistics và data evolution.

### Technical Lead / Architect

Quyết định partial index là tactical optimization hay data lifecycle cần partition/archive/read model; tránh accumulating indexes không có owner.

## 11. Key takeaway

- Partial index tốt khi hot query nhắm vào một subset nhỏ, ổn định.
- Query plan phải được đo, không suy luận từ DDL.
- Index design luôn là trade-off giữa read path, write cost và operational maintenance.

# 5. Elasticsearch refresh interval và near-real-time search: document đã index chưa chắc đã search thấy ngay

## 1. What is it?

Elasticsearch là **near-real-time (NRT)** search engine. Sau khi indexing API trả thành công, document chưa nhất thiết ngay lập tức xuất hiện trong search results.

Điểm phân biệt:

```text
index request acknowledged
       !=
document visible to search immediately
```

Search visibility phụ thuộc refresh cycle.

## 2. Why does it exist?

Nếu mỗi write phải lập tức tạo search segment mới và mở searcher tương ứng, indexing throughput sẽ giảm mạnh. Elasticsearch batch công việc visibility qua refresh để cân bằng write throughput và search freshness.

Điều này phù hợp search systems vì nhiều use case chấp nhận độ trễ vài trăm ms đến vài giây giữa source-of-truth write và search visibility.

## 3. How does it work?

Simplified flow:

```text
Client -> Index API
          -> in-memory/indexing buffers
          -> refresh
          -> new segment visible to search
```

Refresh không giống durability flush/fsync concept. Đây chủ yếu là search visibility boundary.

`refresh=wait_for` cho phép caller chờ tới refresh tiếp theo thay vì force refresh ngay lập tức.

## 4. Practical implementation

Không force refresh cho mọi document trong bulk indexing.

Ví dụ .NET client logic ở application level:

```csharp
await searchClient.IndexAsync(product, options => options
    .Index("products")
    .Refresh(Refresh.WaitFor), ct);
```

`wait_for` có thể phù hợp command hiếm nơi UX yêu cầu “save xong search thấy ngay”. Với high-throughput ingestion, thường để refresh tự nhiên tốt hơn.

Bulk import có thể tạm tăng refresh interval hoặc disable refresh có kiểm soát rồi restore sau import, nhưng phải hiểu freshness impact.

## 5. Real production scenario

Admin cập nhật product title trong CMS. Primary database update ngay; event sync sang Elasticsearch trong 200 ms. Admin lập tức search và không thấy title mới trong ~1 giây.

Nếu team hiểu NRT, đây có thể là expected consistency window. Nếu product page đọc DB nhưng search đọc Elasticsearch, UX cần communicate hoặc dùng targeted read-after-write strategy.

## 6. Failure scenario & troubleshooting

**Symptom:** indexing API success nhưng search tạm thời không thấy document.

**Evidence:** GET-by-id/index metadata có write, search result xuất hiện sau refresh.

**Hypothesis:** normal refresh lag chứ không phải lost indexing.

**Diagnosis:** check refresh interval, indexing latency, sync pipeline lag và shard health.

**Fix:** chỉ dùng `refresh=wait_for` ở flow thực sự cần read-after-write; không force refresh toàn hệ thống.

**Verification:** đo end-to-end freshness percentile từ source change tới searchable state.

## 7. Common mistakes

- Gọi `_refresh` sau mọi write.
- Coi Elasticsearch như strongly consistent transactional DB.
- Không phân biệt indexing pipeline lag và refresh lag.
- Test integration bằng “sleep 1 second” cố định.
- Đặt refresh interval cực thấp mà không đo indexing CPU/I/O.

## 8. Alternatives

- **Primary DB lookup:** cho immediate read-after-write của entity cụ thể.
- **`refresh=wait_for`:** targeted consistency khi acceptable latency.
- **Poll-until-visible trong tests:** condition-based thay vì fixed sleep.
- **Dedicated read model khác:** nếu business cần consistency semantics khác search engine cung cấp.

## 9. Trade-offs

### Advantages

- Refresh batching hỗ trợ indexing throughput tốt.
- NRT là compromise hợp lý cho search workloads.

### Costs / Risks

- User có thể thấy stale search ngắn hạn.
- Force refresh quá nhiều tăng segment churn và cost.
- Tight freshness SLO làm ingestion architecture phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu “indexed” và “searchable” không luôn cùng thời điểm.

### Middle

Biết refresh interval, `wait_for` và test eventual visibility.

### Senior

Phân biệt source-to-index lag, refresh lag và query/cache issue bằng telemetry.

### Technical Lead / Architect

Định nghĩa freshness SLO cho search và quyết định UX/read path nào cần strong read-after-write thay vì ép Elasticsearch thành transactional store.

## 11. Key takeaway

- Elasticsearch search là near-real-time, không immediate consistency mặc định.
- `refresh=wait_for` nên dùng có chọn lọc.
- Freshness phải được đo end-to-end, không chỉ nhìn indexing API success.

# 6. Timeout budget và deadline propagation trong distributed systems: tránh mỗi tầng tự đặt timeout khiến request sống lâu hơn business deadline

## 1. What is it?

Timeout là giới hạn cho một operation cụ thể. **Deadline/budget** là thời điểm hoặc tổng thời lượng tối đa cho toàn bộ end-to-end request.

Ví dụ business yêu cầu API hoàn tất trong 2 giây:

```text
Client budget: 2000 ms
  API auth:       100 ms
  SQL:            300 ms
  Product API:    500 ms
  retry/backoff:  ?
  serialization:  100 ms
```

Mỗi dependency không thể tự dùng timeout 2 giây, vì tổng thời gian có thể vượt xa deadline.

## 2. Why does it exist?

Distributed request thường đi qua nhiều hops. Nếu mỗi hop có timeout riêng không liên quan upstream deadline:

```text
API timeout 5s
 -> Service A timeout 5s
    -> Service B timeout 5s
```

client có thể đã bỏ cuộc từ lâu nhưng downstream vẫn tiêu tốn CPU, connections và retries.

Deadline propagation giúp hệ thống dừng work không còn giá trị.

## 3. How does it work?

Upstream tạo deadline. Mỗi hop tính remaining budget:

```text
remaining = deadline - now
```

Dependency timeout phải nhỏ hơn remaining budget và chừa thời gian cleanup/response.

CancellationToken trong .NET là transport hữu ích trong process, nhưng deadline giữa services cần protocol/header/gRPC deadline hoặc explicit metadata tùy hệ thống.

## 4. Practical implementation

Trong ASP.NET Core, combine request abort với server-side timeout:

```csharp
using var timeoutCts = new CancellationTokenSource(
    TimeSpan.FromMilliseconds(800));

using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(
    httpContext.RequestAborted,
    timeoutCts.Token);

var result = await productClient.GetAsync(
    productId,
    linkedCts.Token);
```

Nếu còn 900 ms end-to-end, không nên dành full 900 ms cho một dependency rồi không còn thời gian serialize/return error.

Polly/resilience pipeline cần composition timeout/retry dựa trên budget, không retry mù quáng.

## 5. Real production scenario

Checkout API SLO p95 < 2s. Pricing dependency có timeout 2s và retry 2 lần. Worst case request có thể mất hơn 6s chưa tính backoff.

Client đã timeout ở 3s nhưng server vẫn tiếp tục pricing retries, giữ outbound sockets và DB transaction context. Traffic tăng làm retry amplification đẩy hệ thống xuống nhanh hơn.

## 6. Failure scenario & troubleshooting

**Symptom:** clients report 3s timeout nhưng server traces kéo dài 8–10s.

**Evidence:** child dependency spans tiếp tục sau client disconnect; multiple retries vượt request budget.

**Hypothesis:** cancellation/deadline không propagate.

**Diagnosis:** inspect distributed trace timing, retry count, timeout policies và `RequestAborted` propagation.

**Fix:** propagate deadline/cancellation; cap retry bởi remaining budget; giảm nested retries.

**Verification:** inject slow dependency và đảm bảo child work dừng gần end-to-end deadline.

## 7. Common mistakes

- Mỗi service đặt cùng một timeout độc lập.
- Timeout nhưng không cancel underlying HTTP/DB operation.
- Retry sau timeout mà không kiểm tra idempotency.
- Parent và child đều retry tạo retry multiplication.
- Dùng timeout cực dài để “giảm lỗi” và vô tình tăng resource retention.

## 8. Alternatives

- **Fail fast:** đúng khi dependency không critical hoặc fallback có sẵn.
- **Async workflow:** tốt khi business không cần response synchronously.
- **Cached/stale response:** phù hợp khi freshness có budget.
- **Circuit Breaker/Bulkhead:** bổ sung cho timeout nhưng giải quyết failure dimension khác.

## 9. Trade-offs

### Advantages

- Giảm wasted work sau khi request mất giá trị.
- Tail latency predictable hơn.
- Hạn chế retry storm/resource exhaustion.

### Costs / Risks

- Timeout quá aggressive tạo false failures.
- Deadline propagation cần cross-service convention.
- Business flows khác nhau có budget khác nhau.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không phải retry và cancellation cần propagate.

### Middle

Implement linked cancellation, HTTP timeout và bounded retries.

### Senior

Thiết kế remaining-budget logic, tránh nested retry amplification và đọc distributed traces.

### Technical Lead / Architect

Đặt latency budgets per critical path, ownership của retry policy và quyết định workflow nào không nên synchronous.

## 11. Key takeaway

- Timeout của từng dependency phải phục vụ end-to-end deadline.
- Request đã hết giá trị thì downstream work nên dừng càng sớm càng tốt.
- Retry phải nằm trong budget và chỉ dùng khi operation đủ an toàn để retry.

# 7. Azure Service Bus message lock, renewal và settlement: xử lý long-running consumer mà không tạo duplicate processing ngoài ý muốn

## 1. What is it?

Trong `PeekLock` mode, Azure Service Bus không xóa message khi consumer nhận. Broker tạm **lock** message cho consumer. Consumer sau đó settlement:

```text
Receive -> lock
   -> Complete    : thành công, remove message
   -> Abandon     : trả lại queue
   -> DeadLetter  : chuyển DLQ
   -> lock expires: message có thể được redeliver
```

Lock duration là lease tạm thời, không phải ownership vĩnh viễn.

## 2. Why does it exist?

Nếu broker xóa message ngay khi deliver và process crash giữa chừng, work bị mất. Peek-lock giữ broker ownership cho tới khi consumer xác nhận thành công.

Đổi lại, processing lâu hơn lock duration có thể dẫn đến redelivery và duplicate execution.

## 3. How does it work?

Ví dụ lock = 60 giây:

```text
00s receive
40s still processing
60s lock expires
65s broker redelivers to another consumer
80s first consumer finishes business action
```

Giờ hai consumers có thể cùng thực hiện side effect nếu không có idempotency.

SDK có auto lock renewal trong giới hạn cấu hình, nhưng renewal không phải excuse cho handler kéo dài vô hạn.

## 4. Practical implementation

Processor config:

```csharp
var options = new ServiceBusProcessorOptions
{
    AutoCompleteMessages = false,
    MaxConcurrentCalls = 8,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(5)
};

var processor = client.CreateProcessor("orders", options);

processor.ProcessMessageAsync += async args =>
{
    var messageId = args.Message.MessageId;

    if (await inbox.AlreadyProcessedAsync(messageId, args.CancellationToken))
    {
        await args.CompleteMessageAsync(args.Message, args.CancellationToken);
        return;
    }

    await handler.ProcessAsync(args.Message, args.CancellationToken);
    await inbox.MarkProcessedAsync(messageId, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message, args.CancellationToken);
};
```

Thực tế `ProcessAsync` + inbox marker cần transaction design phù hợp để tránh crash gap.

## 5. Real production scenario

Consumer tạo PDF hóa đơn mất 2–4 phút. Lock mặc định ngắn hơn processing time. Dưới load, CPU chậm hơn và auto-renew có lúc fail do network hiccup.

Message được redeliver, hai workers cùng tạo file và gửi email hai lần.

Fix tốt có thể là tách processing thành smaller durable steps, idempotency theo invoice ID và lock renewal chỉ là support mechanism.

## 6. Failure scenario & troubleshooting

**Symptom:** cùng `MessageId` xuất hiện nhiều lần, `DeliveryCount` tăng dù handler cuối cùng success.

**Evidence:** logs cho thấy `MessageLockLostException`, processing duration gần/vượt lock renewal window.

**Hypothesis:** lock expires trước settlement hoặc broker/client connectivity làm renewal thất bại.

**Diagnosis:** correlate delivery count, handler duration, lock-lost exceptions và CPU/network telemetry.

**Fix:** giảm handler duration, điều chỉnh concurrency/renewal, chia workflow hoặc tăng idempotency protection.

**Verification:** fault inject delay/network interruption và xác nhận duplicate delivery không tạo duplicate business side effect.

## 7. Common mistakes

- Nghĩ Service Bus đảm bảo exactly-once business processing.
- Complete message trước khi business state commit.
- Tăng lock renewal lên rất lớn thay vì sửa long-running handler.
- MaxConcurrentCalls quá cao làm downstream chậm, khiến lock expiry tăng.
- Không log `MessageId`, `DeliveryCount`, correlation ID.

## 8. Alternatives

- **ReceiveAndDelete:** chỉ dùng khi message loss acceptable; thường không phù hợp business-critical work.
- **Durable orchestration:** cho workflow dài nhiều bước.
- **Chunk work thành messages nhỏ:** tăng recoverability và giảm lock duration pressure.
- **Scheduled/retry queues:** cho delayed retry thay vì giữ lock lâu.

## 9. Trade-offs

### Advantages

- PeekLock hỗ trợ at-least-once reliability tốt.
- Settlement cho consumer control rõ ràng.

### Costs / Risks

- Duplicate delivery là thực tế phải xử lý.
- Long-running handlers cần renewal/idempotency.
- High concurrency có thể làm lock loss gián tiếp qua downstream saturation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu receive không đồng nghĩa message đã bị xóa.

### Middle

Biết complete/abandon/dead-letter và lock renewal.

### Senior

Thiết kế idempotent processing, settlement sau durable success và investigate lock loss bằng telemetry.

### Technical Lead / Architect

Quyết định handler granularity, concurrency budget, inbox/outbox strategy và khi nào workflow dài nên chuyển orchestration thay vì giữ một message lock.

## 11. Key takeaway

- Message lock là lease tạm, không phải exactly-once guarantee.
- Duplicate delivery phải được xem là normal failure mode.
- Long-running work nên được thiết kế để recover, không chỉ kéo dài auto-renew.

# 8. `.NET` runtime counters và production diagnosis: dùng GC, ThreadPool, exception và allocation telemetry để phân biệt symptom với root cause

## 1. What is it?

`.NET` runtime exposes metrics/counters về process behavior như:

- GC collections
- heap size
- allocation rate
- ThreadPool thread count
- ThreadPool queue length
- exception rate
- CPU usage
- working set

`dotnet-counters`, OpenTelemetry runtime instrumentation và monitoring platforms có thể đọc các signals này.

Mental model:

```text
request latency tăng
    -> runtime signal
    -> dependency signal
    -> host signal
    -> hypothesis
```

Counter là evidence, không phải diagnosis tự động.

## 2. Why does it exist?

Một API chậm có nhiều root causes:

```text
CPU saturation
GC pressure
ThreadPool starvation
SQL timeout
connection pool exhaustion
external API latency
lock contention
```

Nhìn mỗi CPU hoặc memory thường không đủ. Runtime counters giúp thu hẹp hypothesis nhanh hơn khi incident xảy ra.

## 3. How does it work?

Ví dụ ThreadPool starvation pattern:

```text
request rate stable
ThreadPool queue length ↑
Thread count ↑ dần
CPU không nhất thiết 100%
latency ↑
```

GC pressure pattern khác:

```text
allocation rate ↑
Gen 2 collections ↑
GC pause ↑
heap size oscillates/high
```

Hai incident đều “API chậm” nhưng remediation khác hoàn toàn.

## 4. Practical implementation

Local diagnosis:

```bash
dotnet-counters monitor --process-id <PID> System.Runtime
```

Trong application, export runtime metrics qua OpenTelemetry để correlate với request/dependency metrics:

```csharp
builder.Services.AddOpenTelemetry()
    .WithMetrics(metrics =>
    {
        metrics.AddAspNetCoreInstrumentation();
        metrics.AddHttpClientInstrumentation();
        metrics.AddRuntimeInstrumentation();
    });
```

Production dashboard nên kết hợp request latency/error rate với runtime saturation signals thay vì một chart riêng lẻ.

## 5. Real production scenario

Sau release, p99 API tăng từ 700 ms lên 5s. CPU chỉ 45%, nên team nghĩ database chậm. SQL spans vẫn bình thường.

Runtime metrics cho thấy ThreadPool queue length spike. Diff release phát hiện một library mới gọi synchronous `.Result` trên async HTTP path, giữ worker threads chờ I/O.

Nếu chỉ nhìn CPU, root cause dễ bị bỏ qua.

## 6. Failure scenario & troubleshooting

**Symptom:** latency tăng, CPU trung bình không cao.

**Evidence:** ThreadPool queue tăng, dependency durations bình thường, thread count tăng từ từ.

**Hypothesis:** blocking/sync-over-async.

**Diagnosis:** lấy trace/dump, xem blocking stacks, correlate deployment diff.

**Fix:** chuyển blocking I/O sang async thực sự, giới hạn concurrency hoặc sửa library usage.

**Verification:** queue length ổn định, p95/p99 giảm dưới same load.

## 7. Common mistakes

- Alert trực tiếp mọi GC collection.
- Thấy memory cao rồi kết luận leak.
- Chỉ dùng average CPU.
- Không correlate counters với deployment/request traces.
- Thu metrics nhưng không biết baseline healthy của service.
- Fix bằng tăng instance count trước khi hiểu bottleneck.

## 8. Alternatives

- **Profiler/trace:** chi tiết hơn khi cần stack/allocation evidence.
- **Memory dump:** cần cho retained-object/leak investigation.
- **APM distributed traces:** tốt cho dependency latency.
- **Load test:** dùng để reproduce và verify hypothesis.

Counters thường là first-pass localization, không thay mọi diagnostic tool.

## 9. Trade-offs

### Advantages

- Overhead thấp, dễ thu liên tục.
- Cho runtime health context nhanh.
- Hữu ích để phân biệt CPU/GC/ThreadPool patterns.

### Costs / Risks

- Aggregate metrics có thể che per-request behavior.
- Không cho call stack/root cause trực tiếp.
- Quá nhiều dashboards/counters tạo noise nếu không có diagnostic model.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết CPU, memory và GC metrics chỉ là signals.

### Middle

Dùng `dotnet-counters`, đọc ThreadPool/GC basics và correlate với request latency.

### Senior

Chuyển symptom thành hypotheses, dùng trace/profile/dump để xác nhận và tránh cargo-cult fixes.

### Technical Lead / Architect

Định nghĩa service baselines, saturation alerts và production diagnostic playbook để team xử lý incident nhất quán.

## 11. Key takeaway

- Runtime counters giúp localize vấn đề, không tự nói root cause.
- Tail latency + ThreadPool/GC/dependency evidence phải được đọc cùng nhau.
- Measure → hypothesis → evidence → fix → verify vẫn là loop cốt lõi.

# 9. Optimizely CMS content type evolution: đổi model an toàn mà không phá dữ liệu editor và deployment hiện có

## 1. What is it?

Trong Optimizely CMS, content types/page types/blocks được map giữa code model và metadata/content đã tồn tại trong CMS database.

Content model không chỉ là C# class. Nó là contract giữa:

```text
Code
Editors
Stored content
Rendering
Search/index
Integrations
```

Đổi property name/type/remove field có thể ảnh hưởng dữ liệu đã publish từ nhiều năm trước.

## 2. Why does it exist?

CMS sống lâu hơn nhiều feature release. Editors tạo hàng nghìn content items dựa trên model hiện tại. Nếu developer refactor class như refactor DTO thông thường, stored content có thể trở thành orphaned, không render hoặc mất khả năng edit.

Content type evolution cần backward compatibility và data migration thinking giống database schema evolution.

## 3. How does it work?

Ví dụ block ban đầu:

```csharp
[ContentType(DisplayName = "Hero Block")]
public class HeroBlock : BlockData
{
    public virtual string? Heading { get; set; }
}
```

Sau này business muốn rich text + subtitle. Additive change thường an toàn hơn destructive rename/remove:

```csharp
public virtual string? Heading { get; set; }
public virtual string? Subtitle { get; set; }
public virtual XhtmlString? Body { get; set; }
```

Khi cần rename semantic lớn, phải xem platform migration mechanisms/content migration script và editor rollout thay vì chỉ đổi property identifier.

## 4. Practical implementation

Một migration workflow hợp lý:

```text
1. Add new property
2. Deploy code compatible với old + new data
3. Migrate/backfill content
4. Update rendering/search mapping
5. Let editors verify
6. Remove legacy field ở release sau nếu thật sự cần
```

Rendering có thể giữ fallback tạm thời:

```csharp
var title = !string.IsNullOrWhiteSpace(model.NewHeading)
    ? model.NewHeading
    : model.LegacyHeading;
```

Fallback chỉ nên tồn tại trong migration window có owner, không trở thành permanent debt.

## 5. Real production scenario

Marketing site có 20.000 product landing pages dùng `HeroBlock`. Team rename property để “code đẹp hơn”, deploy xong staging trống heading ở content cũ vì mapping identity thay đổi.

Production rollback binary chưa chắc khôi phục mọi effect nếu metadata/content migration đã chạy. Vì vậy CMS model change cần release plan riêng.

## 6. Failure scenario & troubleshooting

**Symptom:** content mới render đúng nhưng content cũ thiếu field sau deployment.

**Evidence:** database/content metadata vẫn có old property identity; code model chỉ nhận new one.

**Hypothesis:** destructive content model change không có migration.

**Diagnosis:** compare previous content type definition, stored content và model synchronization logs.

**Fix:** restore compatibility field/mapping, migrate content có kiểm soát và test representative historical pages.

**Verification:** sample old/new content, editor UI, rendering, search indexing và publish workflow.

## 7. Common mistakes

- Rename/delete CMS property như refactor private C# field.
- Test chỉ với content mới tạo.
- Không include editors/content owners trong migration validation.
- Thay type từ string sang complex object mà không data migration.
- Deploy code và destructive content changes trong một bước không rollback plan.

## 8. Alternatives

- **Additive field + deprecate old field:** an toàn hơn nhưng có temporary duplication.
- **New content type version:** phù hợp khi semantics thay đổi lớn.
- **Migration script/job:** phù hợp khi cần chuyển nhiều existing items.
- **Leave legacy field:** đôi khi cheapest option nếu cleanup risk lớn hơn value.

## 9. Trade-offs

### Advantages

- Additive evolution giảm production/editor disruption.
- Migration có staged verification và rollback path tốt hơn.

### Costs / Risks

- Temporary duplicate fields tăng complexity.
- Large content migration có thể tốn thời gian/indexing load.
- Legacy compatibility code dễ tồn tại quá lâu nếu không có cleanup owner.

### Junior

Hiểu CMS property là persisted contract, không chỉ C# member.

### Middle

Biết additive change, fallback rendering và test old content.

### Senior

Thiết kế migration, search/cache invalidation và rollback cho content model evolution.

### Technical Lead / Architect

Quyết định khi nào deprecate, migrate, version content type hoặc giữ legacy model; cân bằng editor impact, migration risk và long-term maintainability.

## 11. Key takeaway

- CMS model changes phải được đối xử như persistent schema changes.
- Historical content là test data bắt buộc.
- Additive migration thường an toàn hơn destructive refactor trong cùng release.

# 10. CORS preflight trong ASP.NET Core: browser security boundary, cache behavior và vì sao CORS không phải authorization

## 1. What is it?

CORS (Cross-Origin Resource Sharing) là browser-enforced policy quyết định JavaScript từ một origin có được đọc/gửi một số cross-origin requests tới server hay không.

Một số request cần **preflight**:

```text
Browser -> OPTIONS /api/orders
Server  -> Access-Control-Allow-Origin / Methods / Headers
Browser -> actual POST /api/orders
```

Nếu policy không cho phép, browser chặn script access hoặc không gửi actual request tùy trường hợp.

## 2. Why does it exist?

Browser tự mang cookies/credentials và web page có thể chạy JavaScript từ nhiều origins. Nếu bất kỳ site nào cũng đọc API response của origin khác, sensitive data dễ bị exfiltrate.

CORS cho server nói origin nào được phép tương tác cross-origin ở browser context.

Nhưng non-browser clients như curl/Postman/backend service không bị CORS bảo vệ. Vì vậy CORS không phải authentication/authorization.

## 3. How does it work?

Preflight thường xảy ra khi request không thuộc “simple request” constraints, ví dụ custom headers hoặc certain methods/content types.

Browser gửi:

```http
OPTIONS /api/orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization,content-type
```

Server response:

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: authorization,content-type
```

Browser mới quyết định gửi actual request.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("frontend", policy =>
    {
        policy
            .WithOrigins("https://app.example.com")
            .WithMethods("GET", "POST", "PUT", "DELETE")
            .WithHeaders("Content-Type", "Authorization")
            .SetPreflightMaxAge(TimeSpan.FromMinutes(10));
    });
});

var app = builder.Build();

app.UseCors("frontend");
```

Nếu dùng credentials/cookies, origin policy phải được thiết kế chặt; wildcard và credentials có security constraints quan trọng.

## 5. Real production scenario

SPA chạy `https://portal.company.com`, API chạy `https://api.company.com`. Local dev dùng permissive CORS nên mọi thứ chạy. Production thêm `Authorization` header và browser bắt đầu gửi preflight. Reverse proxy không route `OPTIONS` đúng, nên UI báo “CORS error”.

Backend endpoint thật có thể hoàn toàn khỏe; failure nằm ở preflight/proxy/policy layer.

## 6. Failure scenario & troubleshooting

**Symptom:** browser báo CORS error, Postman gọi API thành công.

**Evidence:** DevTools Network cho thấy `OPTIONS` 404/403 hoặc thiếu `Access-Control-Allow-*` headers.

**Hypothesis:** preflight bị middleware/proxy/auth policy chặn.

**Diagnosis:** inspect actual preflight request/response, origin string, allowed headers/methods và middleware ordering.

**Fix:** route OPTIONS đúng, cấu hình explicit origins và đảm bảo CORS middleware chạy ở vị trí phù hợp.

**Verification:** test từ browser origin thật, không chỉ curl.

## 7. Common mistakes

- Dùng `AllowAnyOrigin` để “fix nhanh” Production.
- Nghĩ CORS chặn backend-to-backend attack.
- Đòi authentication cho preflight theo cách khiến browser không bao giờ gửi actual request.
- Không tính subdomain/scheme/port là một phần của origin.
- Cho phép credentials với policy quá rộng.
- Debug API controller trong khi preflight chưa tới controller.

## 8. Alternatives

- **Same-origin deployment/reverse proxy:** loại bỏ nhiều CORS complexity.
- **Backend-for-Frontend:** browser gọi một origin, BFF gọi downstream services.
- **Server-to-server calls:** không dựa vào CORS; dùng authentication/authorization/network controls.

## 9. Trade-offs

### Advantages

- Cho phép SPA/API tách origins có kiểm soát.
- Browser enforcement giúp giảm cross-origin data exposure.

### Costs / Risks

- Preflight thêm request/latency.
- Policy/config qua proxy/CDN dễ sai.
- Misconfiguration có thể mở dữ liệu cho origin không mong muốn.
- Không thay thế CSRF protection hoặc authorization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu origin gồm scheme + host + port và CORS do browser enforce.

### Middle

Đọc preflight trong DevTools và cấu hình ASP.NET Core policy đúng.

### Senior

Phân biệt CORS, CSRF, authentication và authorization; debug proxy/middleware/cache layers.

### Technical Lead / Architect

Quyết định topology same-origin, BFF hay cross-origin SPA; đặt policy least-privilege và tránh dùng CORS như security boundary duy nhất.

## 11. Key takeaway

- CORS là browser cross-origin policy, không phải API authorization.
- Preflight phải được debug như một request riêng biệt.
- Production policy nên explicit origins/methods/headers thay vì permissive wildcard để “cho chạy”.
