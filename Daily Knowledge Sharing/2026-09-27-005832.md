# 1. C# `Span<T>` và `Memory<T>`: giảm allocation mà vẫn giữ lifetime an toàn

## 1. What is it?

Mental model: `Span<T>` là một “cửa sổ” liên tục nhìn vào vùng memory đã tồn tại; nó không sở hữu dữ liệu. `Memory<T>` mang ý tưởng tương tự nhưng có thể sống qua asynchronous boundary. Mục tiêu không phải làm mọi code “zero allocation”, mà tránh copy/allocate ở hot path đã được đo.

`Span<T>` là `ref struct`, vì vậy CLR/compiler áp các giới hạn lifetime để nó không thoát khỏi stack context theo cách nguy hiểm.

## 2. Why does it exist?

Parsing protocol, xử lý buffer, serialization và text processing thường tạo nhiều substring/array tạm. Với throughput lớn, các allocation nhỏ cộng lại thành GC pressure. Trước khi dùng `Span<T>`, cách đơn giản thường là copy một đoạn array hoặc tạo string mới.

## 3. How does it work?

```text
byte[] buffer
    │
    ├── Span<byte> [0..32]      -> view, không copy
    └── Span<byte> [32..128]    -> view, không copy
```

`Span<T>.Slice` chỉ tạo view mới. `Memory<T>` có thể được giữ trong object hoặc đi qua `await`; khi cần truy cập synchronous, lấy `.Span`.

## 4. Practical implementation

```csharp
static bool TryReadHeader(ReadOnlySpan<byte> data, out int length)
{
    length = 0;
    if (data.Length < 4) return false;

    length = System.Buffers.Binary.BinaryPrimitives
        .ReadInt32BigEndian(data[..4]);

    return length >= 0;
}
```

Không có array 4-byte trung gian.

## 5. Real production scenario

Một API ingest hàng nghìn payload/giây phải parse header trước khi deserialize body. Profiling cho thấy allocation rate cao do `ToArray()` ở mỗi request. Chuyển phần parsing nhỏ sang `ReadOnlySpan<byte>` giảm allocation mà không thay đổi business layer.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU GC tăng dù request rate không đổi.  
**Evidence** → allocation profile cho thấy nhiều short-lived arrays/string.  
**Hypothesis** → parsing đang copy dữ liệu.  
**Diagnosis** → trace allocation tới `ToArray`, `Substring`.  
**Fix** → dùng view chỉ ở hot path phù hợp.  
**Verification** → so allocation/sec, GC count và p95 trước/sau.

## 7. Common mistakes

Dùng `Span<T>` khắp business code; tối ưu khi chưa profile; gọi `ToArray()` ngay sau khi tạo span; cố giữ `Span<T>` qua `await`; đánh đổi readability để tiết kiệm allocation không đáng kể.

## 8. Alternatives

Array/string bình thường thường đúng cho business code. `ArrayPool<T>` phù hợp buffer lớn cần reuse. `Memory<T>` phù hợp async. Pipelines phù hợp streaming protocol phức tạp.

## 9. Trade-offs

### Advantages

Giảm copy, giảm allocation, tốt cho parsing/serialization hot path.

### Costs / Risks

API phức tạp hơn, lifetime constraints khó hiểu hơn, benchmark dễ bị lạm dụng và readability giảm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu view khác ownership và slice không nhất thiết copy.

### Middle
Biết dùng `ReadOnlySpan<T>` cho parsing nhỏ và hiểu compiler lifetime rules.

### Senior
Chỉ áp dụng sau profiling; đánh giá allocation, GC và throughput cùng nhau.

### Technical Lead / Architect
Quyết định hot path nào đáng nhận thêm complexity và giữ optimization khỏi lan vào domain code.

## 11. Key takeaway

- `Span<T>` là view, không phải container sở hữu dữ liệu.
- Tối ưu allocation phải bắt đầu bằng measurement.
- `Memory<T>` phù hợp khi lifetime phải vượt asynchronous boundary.

# 2. ASP.NET Core ProblemDetails: biến lỗi API thành contract ổn định thay vì chuỗi exception

## 1. What is it?

`ProblemDetails` là representation chuẩn cho HTTP API error. Mental model: exception là implementation detail phía server; error response là public contract với client.

## 2. Why does it exist?

Nếu mỗi endpoint trả lỗi theo format riêng, frontend phải đoán `message`, `error`, `errors` hay plain text. Khi exception message bị trả thẳng, API vừa không ổn định vừa có nguy cơ leak implementation detail.

## 3. How does it work?

```text
Exception / validation failure
        ↓
Exception handler / status-code handling
        ↓
ProblemDetails mapping
        ↓
HTTP status + stable machine-readable body
```

HTTP status vẫn mang semantics; body bổ sung `type`, `title`, `status`, `detail`, `instance` và extension fields như correlation ID.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();

app.UseExceptionHandler();

app.MapGet("/orders/{id:int}", async (int id, AppDbContext db) =>
{
    var order = await db.Orders.FindAsync(id);
    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

Với domain exception, map tập trung sang status phù hợp thay vì `try/catch` ở mọi controller.

## 5. Real production scenario

Web app gọi Order API. Validation trả 400, missing resource trả 404, conflict trả 409, unexpected fault trả 500. Frontend dựa vào status và stable error code; correlation ID cho phép support nối lỗi UI với trace backend.

## 6. Failure scenario & troubleshooting

**Symptom** → client hiển thị “Unexpected token” vì endpoint lỗi trả HTML.  
**Evidence** → response `Content-Type: text/html` từ proxy/server error page.  
**Diagnosis** → error path bypass API error middleware.  
**Fix** → chuẩn hóa exception handling và kiểm tra proxy behavior.  
**Verification** → integration test cả 400/404/409/500 và content type.

## 7. Common mistakes

Luôn trả HTTP 200 kèm `success=false`; leak stack trace; dùng 500 cho lỗi business; nhét localized text làm machine-readable code; format validation và exception hoàn toàn khác nhau.

## 8. Alternatives

Custom envelope có thể cần cho legacy contract, nhưng phải duy trì lâu dài. gRPC dùng status model khác. Minimal API vẫn có thể dùng ProblemDetails.

## 9. Trade-offs

### Advantages

Contract nhất quán, client đơn giản hơn, observability tốt hơn.

### Costs / Risks

Cần governance cho error codes và mapping; thay đổi contract lỗi cũng là compatibility concern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt HTTP status với exception type.

### Middle
Implement centralized handler và integration test error contract.

### Senior
Thiết kế mapping domain/application/infrastructure error, tránh leak dữ liệu và giữ backward compatibility.

### Technical Lead / Architect
Quy định organization-wide error taxonomy vừa đủ, không biến mọi exception class thành public API.

## 11. Key takeaway

- Exception không phải API contract.
- Status code và ProblemDetails phải phản ánh semantics.
- Error path cần được test như success path.

# 3. EF Core compiled queries: hiểu query compilation trước khi tối ưu hot path

## 1. What is it?

EF Core phải biến LINQ expression thành SQL command shape. Compiled query cho phép tái sử dụng phần compilation cho một query shape ổn định. Đây là micro-optimization cho hot path, không phải giải pháp cho SQL chậm.

## 2. Why does it exist?

Ngay cả khi database query nhanh, application vẫn có overhead phân tích expression tree và chuẩn bị query pipeline. Ở endpoint cực nóng với query đơn giản, overhead này có thể đo được.

## 3. How does it work?

```text
LINQ expression
   ↓
translation / query pipeline
   ↓
SQL shape + parameterization
   ↓
database execution
```

Compiled query tối ưu phần phía application; nó không sửa execution plan, index, lock hay network round trip.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, int, Task<Order?>>
    GetOrderById = EF.CompileAsyncQuery(
        (AppDbContext db, int id) =>
            db.Orders.AsNoTracking().SingleOrDefault(x => x.Id == id));

var order = await GetOrderById(db, orderId);
```

## 5. Real production scenario

Product lookup endpoint có hàng chục nghìn calls/phút, SQL đã dưới vài ms và CPU application trở thành bottleneck. Benchmark cho thấy query pipeline overhead đáng kể; compiled query có thể hợp lý.

## 6. Failure scenario & troubleshooting

**Symptom** → team dùng compiled query nhưng p95 vẫn 800 ms.  
**Evidence** → SQL trace cho thấy database mất 760 ms.  
**Diagnosis** → bottleneck nằm ở I/O/query plan, không phải EF compilation.  
**Fix** → phân tích execution plan/access pattern.  
**Verification** → đo riêng application overhead và DB duration.

## 7. Common mistakes

Compile mọi query; dùng nó để che N+1; bỏ qua projection; tin rằng compiled query tương đương SQL Server plan cache; tối ưu benchmark nhưng không đo production.

## 8. Alternatives

Query cache mặc định của EF Core đã xử lý nhiều trường hợp. Dapper/raw SQL hữu ích khi cần kiểm soát mapping/query cụ thể nhưng tăng maintenance cost.

## 9. Trade-offs

### Advantages

Giảm overhead ở stable hot query.

### Costs / Risks

Thêm static code path, giảm flexibility, lợi ích thường nhỏ hơn tối ưu round trip và SQL.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu LINQ phải được translate trước khi DB chạy.

### Middle
Biết projection, `AsNoTracking` và đo query trước.

### Senior
Tách EF overhead khỏi DB latency bằng profiler/telemetry.

### Technical Lead / Architect
Chỉ chuẩn hóa compiled query khi workload chứng minh lợi ích; không biến nó thành coding rule.

## 11. Key takeaway

- Compiled query tối ưu translation overhead, không tối ưu SQL plan.
- Hot path phải được đo trước.
- Round trips và query design thường đáng ưu tiên hơn.

# 4. PostgreSQL transaction isolation và MVCC: consistency không đồng nghĩa với khóa mọi thứ

## 1. What is it?

MVCC cho phép nhiều transaction nhìn các phiên bản dữ liệu phù hợp với snapshot của chúng. Isolation level xác định transaction được phép quan sát thay đổi concurrent đến mức nào.

## 2. Why does it exist?

Nếu mọi reader phải khóa row chống writer, throughput sẽ giảm mạnh. MVCC tách việc đọc snapshot khỏi nhiều xung đột read/write, nhưng không xóa race condition hay write conflict.

## 3. How does it work?

Mỗi transaction quan sát visibility của row versions. `READ COMMITTED` lấy snapshot theo statement; `REPEATABLE READ` giữ view ổn định hơn trong transaction; `SERIALIZABLE` cố đảm bảo outcome tương đương serial execution và có thể abort transaction cần retry.

## 4. Practical implementation

```sql
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;

SELECT balance
FROM accounts
WHERE id = 42;

UPDATE accounts
SET balance = balance - 100
WHERE id = 42;

COMMIT;
```

Application phải sẵn sàng xử lý serialization failure nếu chọn mức mạnh.

## 5. Real production scenario

Hai approval requests cùng kiểm tra quota rồi cùng ghi. Chỉ “bọc transaction” chưa chắc bảo vệ invariant nếu isolation/access pattern không phù hợp.

## 6. Failure scenario & troubleshooting

**Symptom** → thỉnh thoảng quota bị vượt dù mỗi request đều kiểm tra trước.  
**Evidence** → concurrent traces cho thấy hai transaction cùng đọc trạng thái hợp lệ.  
**Hypothesis** → write skew/race.  
**Diagnosis** → reproduce bằng concurrent integration test.  
**Fix** → constraint/atomic update/locking hoặc isolation mạnh hơn tùy invariant.  
**Verification** → stress test concurrency và kiểm tra invariant.

## 7. Common mistakes

Tin rằng transaction tự động loại bỏ mọi race; tăng isolation lên tối đa mà không đánh giá retries; giữ transaction mở khi gọi external API; bỏ qua database constraints.

## 8. Alternatives

Atomic conditional update, explicit row locking, optimistic concurrency token hoặc queue serialization có thể đơn giản hơn tùy business invariant.

## 9. Trade-offs

### Advantages

Isolation mạnh giúp reasoning về consistency dễ hơn.

### Costs / Risks

Conflict/abort nhiều hơn, transaction dài gây pressure, retry logic phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu transaction là boundary của atomic work, không phải “khóa database”.

### Middle
Biết isolation level và reproduce concurrent behavior.

### Senior
Chọn constraint, atomic operation, optimistic/pessimistic strategy theo invariant.

### Technical Lead / Architect
Xác định consistency requirement trước khi chọn cơ chế; tránh giữ transaction qua network boundary.

## 11. Key takeaway

- MVCC giảm contention nhưng không xóa concurrency bugs.
- Isolation phải gắn với invariant.
- Database constraint thường là lớp bảo vệ cuối cùng đáng tin cậy.

# 5. Cosmos DB partition key: quyết định data locality, scalability và chi phí RU

## 1. What is it?

Partition key quyết định cách Cosmos DB phân phối items theo logical partitions. Mental model: đây là quyết định data placement và access pattern, không chỉ là một field bắt buộc.

## 2. Why does it exist?

Một distributed database phải chia dữ liệu để scale storage và throughput. Nếu key phân phối kém hoặc query không biết partition, hệ thống phải fan-out hoặc tạo hot partition.

## 3. How does it work?

```text
tenantId=A ─┐
tenantId=B ─┼─> hash/routing -> physical partitions
tenantId=C ─┘
```

Point read với `id + partition key` thường hiệu quả. Cross-partition query có thể phải truy vấn nhiều partitions và tiêu thụ RU cao hơn.

## 4. Practical implementation

```csharp
var response = await container.ReadItemAsync<Order>(
    id: orderId,
    partitionKey: new PartitionKey(tenantId),
    cancellationToken: cancellationToken);
```

Thiết kế document nên khiến request phổ biến có sẵn partition key.

## 5. Real production scenario

SaaS lưu orders theo tenant. `tenantId` cho locality tốt nếu tenant tương đối cân bằng; nhưng một mega-tenant có thể trở thành hotspot và cần hierarchical/synthetic strategy phù hợp.

## 6. Failure scenario & troubleshooting

**Symptom** → RU tăng mạnh và latency tăng khi traffic tăng nhẹ.  
**Evidence** → diagnostics cho thấy cross-partition queries và một partition chịu tải lớn.  
**Diagnosis** → access pattern không khớp partition key.  
**Fix** → sửa query/model; repartition thường là migration đáng kể.  
**Verification** → theo dõi RU/request, throttling 429 và partition distribution.

## 7. Common mistakes

Chọn key có cardinality thấp; chọn field “trông hợp domain” nhưng query không có nó; dùng Cosmos như relational DB với nhiều cross-partition joins giả lập; bỏ qua mega-tenant.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp nếu transaction relational và joins là trung tâm. MongoDB cũng cần shard-key reasoning khi scale phân tán.

## 9. Trade-offs

### Advantages

Scale-out tự nhiên khi key và workload phù hợp.

### Costs / Risks

Partition decision khó đổi, RU/cost phụ thuộc access pattern, consistency và transaction scope bị giới hạn theo boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu partition key quyết định nơi dữ liệu nằm.

### Middle
Implement point read và tránh query fan-out không cần thiết.

### Senior
Đo RU, hotspot, throttling và thiết kế theo access pattern.

### Technical Lead / Architect
Quyết định liệu workload có thực sự cần Cosmos DB và chọn partition strategy chịu được growth/tenant skew.

## 11. Key takeaway

- Partition key là architectural decision.
- Model theo access pattern, không chỉ theo entity shape.
- RU và hotspot phải được quan sát trong production.

# 6. Kubernetes readiness vs liveness probes: đừng biến health check thành restart loop

## 1. What is it?

Readiness trả lời “Pod có nên nhận traffic không?”. Liveness trả lời “process có bị kẹt đến mức cần restart không?”. Hai câu hỏi khác nhau.

## 2. Why does it exist?

Process có thể đang chạy nhưng chưa sẵn sàng phục vụ; hoặc tạm mất database nhưng process vẫn hoàn toàn khỏe và có thể hồi phục. Nếu gom mọi dependency vào liveness, một outage downstream có thể khiến toàn cluster restart đồng loạt.

## 3. How does it work?

```text
readiness fails -> Pod bị loại khỏi Service endpoints
liveness fails  -> kubelet restart container
```

Startup probe có thể bảo vệ app khởi động chậm khỏi liveness quá sớm.

## 4. Practical implementation

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 10

livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 20
```

Trong ASP.NET Core, map health checks theo tags để readiness có thể kiểm tra dependency cần thiết trong khi liveness chỉ kiểm tra process health phù hợp.

## 5. Real production scenario

API phụ thuộc SQL. SQL maintenance 2 phút. Readiness có thể ngừng route traffic tới instance không phục vụ được; liveness không nên restart vô hạn chỉ vì SQL đang down.

## 6. Failure scenario & troubleshooting

**Symptom** → outage DB kéo theo `CrashLoopBackOff`.  
**Evidence** → liveness endpoint trả unhealthy do DB check.  
**Diagnosis** → dependency failure bị hiểu nhầm thành process failure.  
**Fix** → tách health semantics, điều chỉnh timeout/threshold.  
**Verification** → chaos test dependency outage và quan sát restart count.

## 7. Common mistakes

Cùng một endpoint cho mọi probe; probe quá nặng; timeout quá ngắn; readiness luôn 200; liveness phụ thuộc external API; không có startup allowance.

## 8. Alternatives

App Service health check đơn giản hơn cho App Service workload. Kubernetes chỉ đáng nhận operational complexity khi orchestration requirement thực sự cần.

## 9. Trade-offs

### Advantages

Traffic routing và self-healing tốt khi semantics đúng.

### Costs / Risks

Probe sai tạo cascading failure; health logic trở thành production-critical code.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Nhớ readiness = nhận traffic, liveness = restart.

### Middle
Cấu hình probe và ASP.NET Core health endpoints đúng.

### Senior
Test dependency failure, startup delay và overload behavior.

### Technical Lead / Architect
Quyết định health contract nào phản ánh khả năng phục vụ mà không khuếch đại outage.

## 11. Key takeaway

- Readiness và liveness không đồng nghĩa.
- Dependency outage thường không nên kích hoạt process restart.
- Health checks phải được failure-test.

# 7. OpenTelemetry metrics và p95/p99: đo tail latency thay vì tin vào average

## 1. What is it?

Percentile latency cho biết tỷ lệ request hoàn thành dưới một ngưỡng. p95 = 95% request nhanh hơn hoặc bằng giá trị đó; p99 tập trung vào tail. OpenTelemetry cung cấp instrumentation model để metrics, traces và logs có thể liên hệ trong observability stack.

## 2. Why does it exist?

Average có thể đẹp dù một nhóm người dùng chịu latency rất tệ. Ví dụ 99 request 100 ms và một request 10 s vẫn cho average dễ che giấu tail.

## 3. How does it work?

```text
request
  ├─ metric: duration distribution
  ├─ trace: API -> SQL -> external API
  └─ logs: structured context
             ↓
dashboard / alert / investigation
```

Histogram/distribution cho phép backend observability tính percentiles phù hợp.

## 4. Practical implementation

```csharp
builder.Services.AddOpenTelemetry()
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation());
```

Custom metric chỉ nên thêm khi built-in telemetry không biểu diễn business/technical signal cần thiết.

## 5. Real production scenario

Average API latency 180 ms nhưng p99 tăng từ 600 ms lên 4 s. Trace của slow requests cho thấy một external review service timeout ở một subset request.

## 6. Failure scenario & troubleshooting

**Symptom** → support báo “thỉnh thoảng rất chậm”, dashboard average bình thường.  
**Evidence** → p99 spike, trace dependency span kéo dài.  
**Hypothesis** → tail do dependency.  
**Diagnosis** → filter traces theo duration/status.  
**Fix** → timeout/bulkhead/cache hoặc dependency remediation tùy evidence.  
**Verification** → p95/p99 trở về baseline, error rate không tăng.

## 7. Common mistakes

Chỉ alert average; tạo metric có cardinality cao như `userId`; log mọi thứ nhưng không có trace context; coi p99 của sample nhỏ như chân lý; không phân tách endpoint.

## 8. Alternatives

Application Insights có instrumentation tích hợp mạnh trong Azure. Prometheus/Grafana phổ biến cho metrics. OpenTelemetry giúp giảm coupling ở instrumentation layer nhưng backend vẫn cần lựa chọn.

## 9. Trade-offs

### Advantages

Nhìn được tail behavior và correlation xuyên dependency.

### Costs / Risks

Telemetry có storage/cost, sampling và cardinality cần governance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu average khác percentile.

### Middle
Đọc dashboard và trace một request chậm.

### Senior
Thiết kế metrics có cardinality hợp lý và điều tra tail latency bằng evidence.

### Technical Lead / Architect
Đặt SLI/SLO phản ánh user experience và cân bằng telemetry cost với diagnostic value.

## 11. Key takeaway

- Average không đại diện cho tail latency.
- Metrics cho biết “có vấn đề”; traces giúp biết “ở đâu”.
- Cardinality là chi phí kỹ thuật thực.

# 8. Playwright E2E: bảo vệ critical user journey mà không xây test suite dễ vỡ

## 1. What is it?

Playwright điều khiển browser thật để test hệ thống qua UI. E2E test bảo vệ integration của frontend, API, auth và backend theo user journey; nó không thay unit/integration tests.

## 2. Why does it exist?

Một component có thể pass unit test, API pass integration test nhưng login → create order → confirmation vẫn hỏng do routing, browser state hoặc contract mismatch.

## 3. How does it work?

```text
Browser
  ↓
Frontend
  ↓
API
  ↓
Database / dependencies
```

E2E kiểm tra chuỗi này từ ngoài vào, nên confidence cao nhưng setup và failure diagnosis đắt hơn.

## 4. Practical implementation

```typescript
test('user can create an order', async ({ page }) => {
  await page.goto('/orders/new');
  await page.getByLabel('Product').fill('SKU-42');
  await page.getByRole('button', { name: 'Create' }).click();

  await expect(page.getByText('Order created')).toBeVisible();
});
```

Ưu tiên role/label ổn định thay vì CSS selector gắn với layout.

## 5. Real production scenario

Release thay API validation contract. Backend tests pass, frontend build pass, nhưng form submit không render lỗi mới. Một E2E critical-flow test bắt regression trước deploy.

## 6. Failure scenario & troubleshooting

**Symptom** → test CI flaky nhưng local pass.  
**Evidence** → screenshot/trace cho thấy element chưa ready hoặc test data collision.  
**Diagnosis** → fixed sleep hoặc shared state.  
**Fix** → auto-wait/assertion theo state, isolated test data.  
**Verification** → chạy lặp nhiều lần/parallel không fail ngẫu nhiên.

## 7. Common mistakes

Test mọi edge case bằng E2E; `waitForTimeout`; selector theo DOM structure; dùng chung account mutable; mock quá nhiều khiến test không còn E2E; không giữ trace khi fail.

## 8. Alternatives

Unit test nhanh cho logic; API integration test tốt cho contract/persistence; contract test bảo vệ service boundary. E2E chỉ nên bao phủ critical journeys và integration risks.

## 9. Trade-offs

### Advantages

Confidence cao ở user-visible workflow.

### Costs / Risks

Chậm, đắt bảo trì, dễ flaky nếu test design kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Viết locator theo semantics và assertion theo visible outcome.

### Middle
Quản lý test data, auth setup và trace failure.

### Senior
Phân bổ risk giữa unit/integration/E2E, giảm flakiness có hệ thống.

### Technical Lead / Architect
Định nghĩa critical journeys đáng trả chi phí E2E và giữ pipeline feedback time hợp lý.

## 11. Key takeaway

- E2E bảo vệ integration risk, không phải coverage number.
- Tránh fixed sleeps và shared mutable state.
- Critical journey ít nhưng chất lượng tốt hơn hàng trăm brittle tests.

# 9. Third-party webhook security: signature, replay protection và idempotent processing

## 1. What is it?

Webhook là inbound HTTP callback từ hệ thống bên ngoài. Vì endpoint thường public, receiver phải xác minh authenticity, chống replay và xử lý duplicate delivery.

## 2. Why does it exist?

Chỉ “giấu URL” không phải security. Attacker có thể gửi payload giả; provider có thể retry cùng event; network timeout có thể khiến sender không biết receiver đã xử lý thành công hay chưa.

## 3. How does it work?

```text
Provider
  │ payload + timestamp + signature
  ▼
Webhook endpoint
  ├─ verify signature
  ├─ reject stale timestamp
  ├─ deduplicate event id
  ├─ persist/queue
  └─ return 2xx quickly
```

Signature thường là HMAC hoặc asymmetric signature trên raw request bytes; phải theo đúng canonicalization của provider.

## 4. Practical implementation

```csharp
static bool VerifyHmac(
    ReadOnlySpan<byte> body,
    ReadOnlySpan<byte> expected,
    byte[] secret)
{
    using var hmac = new System.Security.Cryptography.HMACSHA256(secret);
    var actual = hmac.ComputeHash(body.ToArray());
    return System.Security.Cryptography.CryptographicOperations
        .FixedTimeEquals(actual, expected);
}
```

Production implementation phải tuân đúng encoding/header/timestamp scheme của provider; secret lấy từ secure secret store, không hard-code.

## 5. Real production scenario

Payment provider gửi `payment.completed`. Receiver verify signature, ghi event ID vào inbox table trong transaction, queue work nội bộ rồi trả 2xx. Retry cùng event không tạo đơn hàng lần hai.

## 6. Failure scenario & troubleshooting

**Symptom** → một payment tạo hai fulfillment records.  
**Evidence** → logs có cùng provider event ID hai lần sau timeout.  
**Hypothesis** → provider retry vì response đầu không tới được.  
**Diagnosis** → handler không idempotent.  
**Fix** → unique constraint/inbox deduplication trên event ID.  
**Verification** → replay cùng payload nhiều lần chỉ tạo một side effect.

## 7. Common mistakes

Parse/re-serialize body trước verify; so signature bằng string comparison không constant-time; không kiểm tra timestamp; xử lý business work lâu trước khi 2xx; tin source IP là cơ chế duy nhất; log secret/header nhạy cảm.

## 8. Alternatives

Polling đơn giản hơn khi freshness thấp. Message broker tốt nếu hai hệ thống cùng kiểm soát infrastructure. Webhook phù hợp cross-organization integration nhưng cần public ingress.

## 9. Trade-offs

### Advantages

Near-real-time, tránh polling liên tục.

### Costs / Risks

Public attack surface, retries/duplicates, provider-specific security contract và operational monitoring.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu webhook delivery không đảm bảo exactly-once.

### Middle
Implement signature verification, fast acknowledgement và deduplication.

### Senior
Thiết kế replay window, secret rotation, retry behavior và incident telemetry.

### Technical Lead / Architect
Quyết định boundary: webhook chỉ ingress event, còn business processing chuyển sang durable internal workflow khi cần reliability.

## 11. Key takeaway

- Webhook URL không phải secret.
- Authenticity và idempotency là hai vấn đề độc lập.
- Persist/deduplicate trước side effect quan trọng.

# 10. Git bisect: tìm commit gây regression bằng evidence thay vì đọc diff theo cảm giác

## 1. What is it?

`git bisect` thực hiện binary search trên commit history giữa một commit “good” và một commit “bad” để tìm commit đầu tiên gây regression.

## 2. Why does it exist?

Khi regression xuất hiện sau hàng trăm commits, đọc từng PR hoặc revert ngẫu nhiên rất tốn thời gian. Nếu có test tái hiện được lỗi, history trở thành searchable state space.

## 3. How does it work?

```text
good ------------------------------ bad
                 ^
              test midpoint
       good? -> search right half
       bad?  -> search left half
```

Số lần kiểm tra tăng theo log2(N), nên 512 commits chỉ cần khoảng 9 bước nếu history/test phù hợp.

## 4. Practical implementation

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0

# chạy test ở commit Git checkout
git bisect good   # hoặc: git bisect bad

git bisect reset
```

Có thể tự động hóa bằng `git bisect run <script>` nếu script trả exit code ổn định.

## 5. Real production scenario

Sau release, CSV export dùng sai timezone. Release trước đúng; release hiện tại sai; 180 commits nằm giữa. Team viết regression test nhỏ rồi dùng bisect để xác định commit thay đổi date conversion.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ tới commit “không liên quan”.  
**Evidence** → test lúc pass lúc fail hoặc commit cũ không build vì external dependency thay đổi.  
**Diagnosis** → predicate good/bad không deterministic.  
**Fix** → cô lập reproduction, pin dependency/test data; dùng `git bisect skip` cho commit không test được.  
**Verification** → checkout parent pass, culprit fail với cùng test.

## 7. Common mistakes

Bisect bằng cảm nhận thủ công thay vì test; chọn “good” chưa được xác minh; quên submodule/config differences; kết luận causality chỉ từ commit location mà không reproduce.

## 8. Alternatives

Trace/APM xác định runtime root cause; `git log -S`/`-G` tốt khi biết symbol/text thay đổi; revert hữu ích để mitigate nhanh nhưng không thay root-cause analysis.

## 9. Trade-offs

### Advantages

Nhanh, deterministic khi reproduction tốt, giảm bias.

### Costs / Risks

Phụ thuộc history buildable và test phân loại ổn định; merge-heavy history có thể khó reasoning hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Biết đánh dấu good/bad và reset sau bisect.

### Middle
Viết regression test đủ deterministic để bisect.

### Senior
Kết hợp bisect với telemetry, dependency/version context và verification.

### Technical Lead / Architect
Xây engineering practice giúp regression reproducible: artifacts, tests, release tags và observability đủ tốt để điều tra nhanh.

## 11. Key takeaway

- `git bisect` biến regression search thành binary search.
- Chất lượng reproduction quyết định chất lượng kết quả.
- Tìm culprit commit là bước điều tra, không tự động là root cause cuối cùng.
