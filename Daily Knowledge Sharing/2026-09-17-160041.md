# 1. .NET `IAsyncDisposable`: asynchronous cleanup, resource lifetime và shutdown correctness

## 1. What is it?

`IAsyncDisposable` biểu diễn resource cần cleanup bằng asynchronous work. Mental model quan trọng: acquire resource có lifecycle; cleanup cũng là một phần của correctness. Nếu cleanup phải flush network buffer, commit protocol state hoặc close asynchronous resource thì `Dispose()` synchronous có thể không đủ.

## 2. Why does it exist?

`IDisposable.Dispose()` không thể `await`. Ép asynchronous cleanup thành blocking bằng `.GetAwaiter().GetResult()` có thể giữ thread, kéo dài shutdown hoặc gây deadlock trong environment có synchronization semantics đặc biệt. `IAsyncDisposable` cho phép caller chờ cleanup hoàn tất mà không biến I/O thành synchronous blocking.

## 3. How does it work?

`await using` được compiler chuyển thành `try/finally` và gọi `DisposeAsync()` khi scope kết thúc.

```text
Acquire resource
      │
      ▼
Use asynchronously
      │
      ▼
finally
      │
      ▼
await DisposeAsync()
```

Cleanup vẫn phải idempotent theo thiết kế nếu có khả năng được gọi nhiều đường; cancellation của business operation cũng không mặc định có nghĩa cleanup được phép bỏ qua.

## 4. Practical implementation

```csharp
public sealed class ExportWriter : IAsyncDisposable
{
    private readonly Stream _stream;

    public ExportWriter(Stream stream) => _stream = stream;

    public async ValueTask DisposeAsync()
    {
        await _stream.FlushAsync();
        await _stream.DisposeAsync();
    }
}

await using var writer = new ExportWriter(stream);
// write export data
```

Nếu type sở hữu cả synchronous và asynchronous resources, disposal pattern cần thể hiện ownership rõ; đừng dispose object mà type không sở hữu.

## 5. Real production scenario

Một file-processing Worker ghi output vào remote stream. Job bị cancellation khi deployment shutdown. Nếu code chỉ thoát khỏi loop mà không await cleanup, buffered bytes có thể chưa được flush, tạo file tồn tại nhưng bị truncate — lỗi khó phát hiện hơn exception rõ ràng.

## 6. Failure scenario & troubleshooting

**Symptom** → file đôi lúc thiếu phần cuối sau restart.  
**Evidence** → shutdown logs cho thấy process dừng ngay sau cancellation; không có completion log của writer.  
**Hypothesis** → asynchronous cleanup không được awaited.  
**Diagnosis** → trace ownership/lifetime và kiểm tra `DisposeAsync()` path.  
**Fix** → `await using`, bounded graceful-shutdown window, cleanup có telemetry.  
**Verification** → terminate worker có kiểm soát trong integration test và verify artifact integrity.

## 7. Common mistakes

Dùng `using` cho type cần `await using`; gọi sync-over-async trong `Dispose`; swallow cleanup exception; truyền `CancellationToken` đã canceled vào critical cleanup rồi cleanup lập tức bỏ cuộc; dispose dependency do DI container sở hữu.

## 8. Alternatives

`IDisposable` vẫn đúng cho purely synchronous cleanup như release unmanaged handle nhanh. Không nên implement `IAsyncDisposable` chỉ để API trông hiện đại hơn.

## 9. Trade-offs

### Advantages

Cleanup I/O không block thread và caller biết khi resource thực sự được giải phóng.

### Costs / Risks

Lifecycle API phức tạp hơn; shutdown cần budget; cleanup lỗi phải có policy rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu resource lifetime không kết thúc chỉ vì method return.

### Middle

Dùng `await using` đúng và xác định object ownership.

### Senior

Thiết kế cleanup chịu cancellation/shutdown, quan sát partial failure và tránh sync-over-async.

### Technical Lead / Architect

Quyết định resource nào cần graceful drain, timeout shutdown bao nhiêu và dữ liệu nào phải durable trước process termination.

## 11. Key takeaway

- Asynchronous resource cần asynchronous cleanup khi cleanup có I/O.
- Cancellation business work không đồng nghĩa được bỏ qua cleanup.
- Ownership và shutdown budget là phần của correctness.

# 2. ASP.NET Core `HttpClientFactory`: connection reuse, DNS rotation và outbound dependency policy

## 1. What is it?

`IHttpClientFactory` quản lý việc tạo `HttpClient` và lifecycle của underlying handlers. Mental model: `HttpClient` là logical client; connection pool nằm sâu hơn ở handler. Vấn đề cần quản lý là connection reuse và handler lifetime, không phải chỉ “new HttpClient có đắt không”.

## 2. Why does it exist?

Tạo/dispose `HttpClient` liên tục có thể làm connections bị churn và socket resources tích tụ. Giữ một handler vô hạn lại có thể giữ stale network assumptions. Factory cung cấp handler pooling và một nơi tập trung outbound policies/configuration.

## 3. How does it work?

```text
Application
   │ CreateClient
   ▼
HttpClientFactory
   │
   ▼
pooled HttpMessageHandler
   │
   ▼
connection pool ──► remote API
```

`HttpClient` instance có thể ngắn hạn trong factory model vì handler được reuse phía dưới.

## 4. Practical implementation

```csharp
builder.Services.AddHttpClient<CatalogClient>(client =>
{
    client.BaseAddress = new Uri("https://catalog.internal/");
    client.Timeout = TimeSpan.FromSeconds(3);
});

public sealed class CatalogClient(HttpClient http)
{
    public Task<Product?> GetAsync(string id, CancellationToken ct) =>
        http.GetFromJsonAsync<Product>($"products/{id}", ct);
}
```

Timeout/retry phải dựa vào operation semantics; không retry mọi POST một cách mù quáng.

## 5. Real production scenario

Product page gọi Reviews API và Inventory API. Typed clients giúp mỗi dependency có base address, timeout, telemetry và authentication riêng. Khi Reviews chậm, policy của Reviews không được làm Inventory requests chịu cùng timeout budget.

## 6. Failure scenario & troubleshooting

**Symptom** → outbound timeout tăng sau dependency deployment/network change.  
**Evidence** → dependency traces cho thấy connect duration hoặc DNS endpoint behavior bất thường.  
**Hypothesis** → stale connection/DNS assumptions hoặc downstream saturation.  
**Diagnosis** → phân biệt DNS/connect/TLS/server latency qua telemetry.  
**Fix** → handler/connection lifetime phù hợp, timeout budget và downstream remediation.  
**Verification** → controlled endpoint rotation/load test và dependency metrics.

## 7. Common mistakes

`new HttpClient()` per request; retry nested nhiều tầng; timeout 100 giây mặc định cho critical path; dùng một named client cho mọi dependency; retry non-idempotent operation mà không có idempotency contract.

## 8. Alternatives

Một long-lived `HttpClient` với `SocketsHttpHandler` cấu hình đúng cũng hợp lệ. Factory hữu ích nhất khi application có DI, nhiều clients và cần centralized policies/telemetry.

## 9. Trade-offs

### Advantages

Connection reuse, cấu hình theo dependency, DI integration và policy centralization.

### Costs / Risks

Policy abstraction có thể che network behavior; retry/timeout cấu hình sai tạo retry storm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP call dùng connection resources phía dưới `HttpClient`.

### Middle

Dùng typed/named clients, cancellation và timeout đúng.

### Senior

Phân tích connection pool, DNS, retries, idempotency và dependency telemetry.

### Technical Lead / Architect

Đặt outbound reliability standards và latency budget cho từng dependency thay vì global policy.

## 11. Key takeaway

- Quản lý handler/connection lifecycle quan trọng hơn lifetime bề mặt của `HttpClient`.
- Retry phải gắn với idempotency và failure semantics.
- Mỗi remote dependency cần timeout/telemetry boundary rõ.

# 3. EF Core split queries: cartesian explosion, consistency window và query-shape engineering

## 1. What is it?

Split query cho phép EF Core tải một object graph bằng nhiều SQL queries thay vì một JOIN query lớn. Mental model: đây là trade-off giữa result-set duplication và số round trips/consistency window.

## 2. Why does it exist?

Khi `Include` nhiều sibling collections, JOIN có thể nhân số rows. Một Order có 20 Lines và 10 Notes có thể tạo khoảng 200 joined rows cho cùng Order, làm network payload và materialization tăng mạnh.

## 3. How does it work?

Single query:

```text
Orders × Lines × Notes → duplicated rows
```

Split query:

```text
Query Orders
Query Lines for Orders
Query Notes for Orders
        │
        ▼
EF assembles graph
```

Nhiều queries nghĩa là database state có thể thay đổi giữa các statements tùy isolation level.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .AsNoTracking()
    .ToListAsync(ct);
```

Nếu endpoint chỉ cần summary, projection thường tốt hơn cả `Include` lẫn split query.

## 5. Real production scenario

Admin Order detail tải Lines, Payments và Audit entries. Single JOIN trả hàng chục nghìn rows cho một order lớn. Split query giảm transferred duplication đáng kể, nhưng team vẫn cần hỏi liệu UI có thực sự cần toàn bộ collections cùng lúc.

## 6. Failure scenario & troubleshooting

**Symptom** → query time/network bytes tăng đột biến khi dữ liệu con tăng.  
**Evidence** → generated SQL + execution plan cho thấy large joined result; profiler cho thấy materialization cost.  
**Hypothesis** → cartesian explosion.  
**Diagnosis** → đo row count/result bytes và từng collection cardinality.  
**Fix** → projection, pagination child collection hoặc `AsSplitQuery()`.  
**Verification** → so round trips, rows, bytes, p95 và consistency requirement.

## 7. Common mistakes

Dùng `Include` như auto-fetch; đổi sang split query mà không đo round trips; quên consistency window; load full graph chỉ để map DTO 5 fields.

## 8. Alternatives

Projection thường tối ưu cho read API. Explicit queries cho control cao hơn. Single query hợp lý khi graph nhỏ và consistency trong một statement quan trọng.

## 9. Trade-offs

### Advantages

Giảm duplicated result data và cartesian explosion.

### Costs / Risks

Nhiều database round trips và khả năng quan sát state khác nhau giữa statements.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` thay đổi SQL/data volume.

### Middle

Đọc generated SQL và chọn projection/split query theo use case.

### Senior

Đánh giá row multiplication, isolation, network payload và materialization cost.

### Technical Lead / Architect

Đặt read-model boundary: aggregate graph nào thực sự cần load và API contract nào nên tránh expose persistence graph.

## 11. Key takeaway

- `AsSplitQuery()` chữa một query shape cụ thể, không phải performance switch toàn cục.
- Projection thường là lựa chọn tốt nhất cho read endpoints.
- Đo cả round trips, bytes và consistency semantics.

# 4. PostgreSQL transaction isolation: MVCC, write skew và khi `Serializable` thực sự cần thiết

## 1. What is it?

PostgreSQL dùng MVCC để nhiều transactions đọc snapshots mà giảm read/write blocking. Isolation level quyết định anomalies nào được phép. Mental model: “không blocking” không đồng nghĩa “không có concurrency anomaly”.

## 2. Why does it exist?

Concurrency cần cân bằng throughput và correctness. Lock mọi thứ serially giữ correctness nhưng giảm concurrency; snapshot-based execution tăng concurrency nhưng business invariant có thể bị phá nếu transactions đưa quyết định dựa trên snapshots khác nhau.

## 3. How does it work?

Ví dụ invariant: phải luôn có ít nhất một bác sĩ on-call.

```text
Tx A snapshot: A + B on-call
Tx B snapshot: A + B on-call
Tx A turns A off
Tx B turns B off
Both commit → invariant broken
```

Đây là write skew: transactions update rows khác nhau nên simple row-level conflict detection có thể không bắt được ở isolation thấp hơn.

## 4. Practical implementation

```sql
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;

SELECT COUNT(*)
FROM on_call
WHERE shift_id = $1 AND active = true;

UPDATE on_call
SET active = false
WHERE shift_id = $1 AND doctor_id = $2;

COMMIT;
```

Ở `Serializable`, application phải sẵn sàng retry serialization failure với bounded policy.

## 5. Real production scenario

Approval system yêu cầu luôn còn ít nhất một approver active cho cost center. Hai admins disable hai approvers khác nhau cùng lúc. Mỗi request thấy người còn lại nên cả hai cho phép update. Database constraints đơn giản khó biểu diễn invariant xuyên nhiều rows.

## 6. Failure scenario & troubleshooting

**Symptom** → invariant hiếm khi bị phá dưới concurrent load.  
**Evidence** → audit log cho thấy hai transactions overlap và đọc snapshots hợp lệ riêng lẻ.  
**Hypothesis** → write skew.  
**Diagnosis** → model transaction interleaving, không chỉ xem từng SQL statement.  
**Fix** → stronger isolation, explicit locking hoặc redesign invariant representation.  
**Verification** → concurrency integration test chạy hàng nghìn interleavings.

## 7. Common mistakes

Cho rằng transaction = serial execution; tăng isolation toàn database mà không đo contention/retry; retry serialization failure mà operation có external side effect; dùng application lock trong một instance cho multi-instance system.

## 8. Alternatives

Explicit `SELECT ... FOR UPDATE` phù hợp khi có row rõ để serialize. Unique/check constraints tốt hơn khi invariant biểu diễn được declaratively. `Serializable` hữu ích khi anomaly phức tạp nhưng có retry cost.

## 9. Trade-offs

### Advantages

MVCC cho read concurrency tốt; stronger isolation bảo vệ invariants khó hơn.

### Costs / Risks

`Serializable` có thể abort transactions và yêu cầu retry-safe application logic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction isolation quyết định dữ liệu transaction được phép quan sát.

### Middle

Biết isolation level, locks và transaction scope cơ bản.

### Senior

Nhận diện lost update/write skew và viết concurrency tests.

### Technical Lead / Architect

Chọn nơi enforce invariant: constraint, lock, isolation hay domain redesign dựa trên contention và correctness.

## 11. Key takeaway

- MVCC giảm blocking nhưng không xóa concurrency anomalies.
- Isolation phải xuất phát từ business invariant.
- `Serializable` cần retry strategy và side-effect discipline.

# 5. CQRS với một database: separation of intent mà chưa trả distributed-data tax

## 1. What is it?

CQRS tách command (thay đổi state) khỏi query (đọc state) theo intent/model. Nó không bắt buộc hai databases, Event Sourcing hay Microservices. Mental model: separation trước hết nằm ở responsibility và model shape.

## 2. Why does it exist?

Một CRUD model duy nhất thường bị kéo theo hai hướng: write side cần invariants và transaction behavior; read side cần projections tối ưu cho UI/reporting. Tách intent giúp mỗi path đơn giản hơn mà chưa cần distributed consistency.

## 3. How does it work?

```text
POST /orders ─► Command Handler ─► Domain/EF Core ─┐
                                                   ├─ SQL Database
GET /orders  ─► Query Handler ─► Projection/SQL ──┘
```

Cả hai vẫn có thể dùng một database và cùng deployment.

## 4. Practical implementation

```csharp
public sealed record GetOrderQuery(Guid Id);

public sealed class GetOrderHandler(AppDbContext db)
{
    public Task<OrderDto?> Handle(GetOrderQuery q, CancellationToken ct) =>
        db.Orders.AsNoTracking()
          .Where(x => x.Id == q.Id)
          .Select(x => new OrderDto(x.Id, x.Status, x.Total))
          .SingleOrDefaultAsync(ct);
}
```

Write handler có thể load aggregate và enforce invariant; read handler không cần hydrate aggregate chỉ để hiển thị DTO.

## 5. Real production scenario

Timesheet system có complex approval rules nhưng dashboard chỉ cần employee, week, status và total hours. Query projection trực tiếp giúp read path rõ và hiệu quả, trong khi command path giữ domain invariants.

## 6. Failure scenario & troubleshooting

**Symptom** → project có hàng trăm handlers nhưng thay đổi đơn giản cần chạm quá nhiều files.  
**Evidence** → commands/queries chỉ wrap một dòng CRUD, không có khác biệt model/behavior.  
**Hypothesis** → ceremony vượt complexity thật.  
**Diagnosis** → xem CQRS có giải quyết read/write pressure nào không.  
**Fix** → collapse trivial paths; giữ separation nơi có giá trị.  
**Verification** → complexity giảm mà tests/business boundaries vẫn rõ.

## 7. Common mistakes

Đồng nhất CQRS với MediatR; bắt buộc một handler cho mọi method; tách database quá sớm; gọi query qua domain aggregate dù chỉ cần projection; thêm Event Sourcing vì nghĩ đó là “full CQRS”.

## 8. Alternatives

Simple application services/CRUD phù hợp domain đơn giản. Separate read store chỉ nên xuất hiện khi scale/model/latency thực sự yêu cầu.

## 9. Trade-offs

### Advantages

Read/write models rõ, projection hiệu quả, command intent dễ review/test.

### Costs / Risks

Nhiều types/files và abstraction overhead; separate stores làm consistency phức tạp hơn đáng kể.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt operation đọc và operation thay đổi state.

### Middle

Implement command/query với validation và projection phù hợp.

### Senior

Biết khi nào separation giảm coupling và khi nào chỉ tạo ceremony.

### Technical Lead / Architect

Quyết định mức CQRS cần thiết: none, logical separation, separate models hay separate stores dựa trên evidence.

## 11. Key takeaway

- CQRS không đồng nghĩa Event Sourcing hoặc hai databases.
- Bắt đầu bằng separation of intent nếu có pressure thực.
- Complexity phải tăng theo nhu cầu, không theo pattern checklist.

# 6. Azure Service Bus lock renewal: long-running consumer, redelivery và idempotency boundary

## 1. What is it?

Trong Peek-Lock processing, consumer nhận message và giữ lock tạm thời. Nếu processing chưa hoàn tất trước khi lock hết hạn, message có thể được giao lại. Lock renewal kéo dài lease; nó không biến delivery thành exactly-once.

## 2. Why does it exist?

Broker không thể khóa message vô hạn vì consumer có thể crash. Lease cho phép recovery. Long-running work cần renewal hoặc redesign để processing duration không vượt delivery assumptions.

## 3. How does it work?

```text
Receive message
   │ lock acquired
   ▼
Process ──► renew lock ──► renew lock
   │
   ├─ success ─► Complete
   └─ crash/lock lost ─► message becomes available again
```

At-least-once semantics nghĩa là duplicate processing luôn phải được xem là khả năng thực tế.

## 4. Practical implementation

```csharp
var processor = client.CreateProcessor(queueName, new ServiceBusProcessorOptions
{
    AutoCompleteMessages = false,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(10),
    MaxConcurrentCalls = 8
});

processor.ProcessMessageAsync += async args =>
{
    await handler.HandleAsync(args.Message, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message, args.CancellationToken);
};
```

Handler vẫn cần idempotency; renewal chỉ giảm accidental redelivery do processing time.

## 5. Real production scenario

File import message mất 7 phút để parse và persist. Lock mặc định ngắn hơn processing. Production thấy cùng file được xử lý hai lần và tạo duplicate rows dù consumer “không throw exception”.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate work và `MessageLockLost` xuất hiện.  
**Evidence** → processing duration vượt lock/renewal window; delivery count tăng.  
**Hypothesis** → lock expired hoặc renewal thất bại do network/process pause.  
**Diagnosis** → correlate receive, renew, complete timestamps và delivery count.  
**Fix** → idempotent inbox, phù hợp renewal duration hoặc chia work thành smaller durable stages.  
**Verification** → inject delay/crash và verify duplicate delivery không tạo duplicate business effect.

## 7. Common mistakes

Tăng lock lên rất dài thay vì redesign; complete trước business commit; assume auto-renew = exactly once; concurrency quá cao làm DB chậm và lock loss hàng loạt; không xử lý poison messages/DLQ.

## 8. Alternatives

Azure Functions Service Bus trigger đơn giản hóa host/renewal nhưng semantics duplicate vẫn còn. Với very long workflow, Durable Functions hoặc persisted workflow/state machine có thể phù hợp hơn.

## 9. Trade-offs

### Advantages

Peek-Lock cho recovery khi consumer chết và controlled settlement.

### Costs / Risks

Consumer phải chịu duplicate, lock timing và operational monitoring.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu receive không có nghĩa message đã biến mất.

### Middle

Complete/abandon đúng và viết handler idempotent.

### Senior

Tune concurrency, renewal, retries và DLQ dựa trên processing distribution.

### Technical Lead / Architect

Quyết định workload có còn phù hợp queue-message handler hay cần durable workflow decomposition.

## 11. Key takeaway

- Lock là lease, không phải ownership vĩnh viễn.
- Renewal không loại bỏ duplicate delivery.
- Long-running consumer cần idempotency và workload decomposition judgment.

# 7. Kubernetes readiness vs liveness probes: traffic safety khác process recovery

## 1. What is it?

Readiness trả lời “Pod có nên nhận traffic không?”. Liveness trả lời “process có cần restart không?”. Hai probes giải quyết hai failure actions khác nhau; dùng cùng một check cho cả hai có thể khuếch đại outage.

## 2. Why does it exist?

Process có thể đang chạy nhưng chưa ready vì startup/warm-up. Ngược lại, dependency tạm thời down không nhất thiết có nghĩa restart process sẽ giúp. Kubernetes cần signal riêng cho routing và recovery.

## 3. How does it work?

```text
Readiness false ─► remove Pod from Service endpoints
Liveness false  ─► restart container
```

Nếu liveness phụ thuộc database và DB outage, mọi pods có thể restart liên tục dù application process hoàn toàn khỏe.

## 4. Practical implementation

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<StartupReadyCheck>("ready");

app.MapHealthChecks("/health/live", new()
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new()
{
    Predicate = r => r.Name == "ready"
});
```

Liveness nên tối giản; readiness chỉ chứa dependencies thực sự bắt buộc để phục vụ traffic.

## 5. Real production scenario

ASP.NET Core API có Redis optional cache. Redis outage làm health endpoint fail. Vì endpoint đó được dùng làm liveness, Kubernetes restart toàn bộ pods, gây cold starts và tăng load lên SQL — outage nhỏ thành cascading failure.

## 6. Failure scenario & troubleshooting

**Symptom** → `CrashLoopBackOff` đồng thời khi dependency outage.  
**Evidence** → pod events cho thấy liveness failures; application logs không có fatal process error.  
**Hypothesis** → probe semantics sai.  
**Diagnosis** → xem từng health dependency và action Kubernetes thực hiện.  
**Fix** → tách live/ready/startup probes; optional dependency không làm liveness fail.  
**Verification** → chaos test dependency outage và quan sát pods không restart vô ích.

## 7. Common mistakes

Một `/health` cho mọi probe; query DB nặng mỗi vài giây; liveness fail vì third-party API; timeout probe quá ngắn; readiness luôn 200 dù startup migration chưa xong.

## 8. Alternatives

Azure App Service health checks có orchestration model khác nhưng nguyên tắc vẫn là signal phải phản ánh action mong muốn. Không phải application nào cũng cần phức tạp nhiều probes nếu failure model đơn giản.

## 9. Trade-offs

### Advantages

Tách routing khỏi restart giúp recovery chính xác hơn.

### Costs / Risks

Health model sai có thể tự gây outage; checks thêm dependency load nếu thiết kế tệ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Nhớ readiness = traffic, liveness = restart.

### Middle

Cấu hình probes và health endpoints riêng.

### Senior

Thiết kế dependency criticality và chaos-test failure actions.

### Technical Lead / Architect

Xác định degradation strategy: dependency nào làm service unready, dependency nào chỉ giảm feature, khi nào restart thực sự có ích.

## 11. Key takeaway

- Probe phải được thiết kế từ recovery action.
- Dependency outage không mặc định là process failure.
- Sai liveness check có thể biến partial failure thành total outage.

# 8. Application Insights dependency telemetry: tìm latency propagation qua critical path

## 1. What is it?

Dependency telemetry ghi nhận outbound calls như SQL, HTTP hoặc Azure services và liên kết chúng với request/trace. Mental model: request latency là tổng critical-path behavior; application log riêng lẻ không cho biết thời gian đã đi đâu.

## 2. Why does it exist?

API chậm có thể do code, SQL, Redis, HTTP hoặc queue interaction. Nếu chỉ đo request duration, ta biết symptom nhưng không biết component gây latency. Distributed tracing tạo causal context giữa spans.

## 3. How does it work?

```text
Request 1200 ms
 ├─ App code 40 ms
 ├─ SQL 80 ms
 └─ Product API 1050 ms
       └─ downstream SQL 980 ms
```

Trace/correlation context cho phép đi từ request đến dependency thay vì grep timestamps thủ công.

## 4. Practical implementation

Với OpenTelemetry trong ASP.NET Core:

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation());
```

Exporter có thể gửi telemetry tới Azure Monitor/Application Insights theo stack được chọn. Custom spans chỉ nên thêm ở meaningful business/technical boundaries.

## 5. Real production scenario

Checkout p95 tăng từ 600 ms lên 2.4 s. Request trace cho thấy app code ổn, nhưng Reviews API timeout chiếm 1.8 s dù review data không critical. Evidence dẫn tới architectural decision: giảm timeout và degrade reviews thay vì scale Checkout.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard request chậm nhưng dependency breakdown thiếu.  
**Evidence** → traces bị đứt tại custom HTTP wrapper.  
**Hypothesis** → context propagation/instrumentation bị mất.  
**Diagnosis** → kiểm tra trace headers, `Activity` context và instrumentation coverage.  
**Fix** → chuẩn hóa OpenTelemetry propagation và bỏ custom code phá context.  
**Verification** → synthetic request có end-to-end trace ID xuyên services.

## 7. Common mistakes

Log duration thủ công nhưng không correlation; custom metric có user ID gây cardinality explosion; sample mất toàn bộ error traces; coi dependency duration cao là root cause mà không drill xuống downstream.

## 8. Alternatives

Logs hữu ích cho discrete events; metrics tốt cho aggregate trends; traces tốt cho causal request path. Production observability cần phối hợp cả ba chứ không chọn một.

## 9. Trade-offs

### Advantages

Nhanh localize bottleneck và failure propagation.

### Costs / Risks

Telemetry volume/cost, sampling và sensitive attributes cần governance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request có thể chậm vì downstream dependency.

### Middle

Tìm trace và đọc dependency spans.

### Senior

Phân tích critical path, propagation, sampling và telemetry gaps.

### Technical Lead / Architect

Đặt observability standards, retention/cost budget và service-level ownership dựa trên trace boundaries.

## 11. Key takeaway

- Request latency phải được phân rã theo critical path.
- Logs + metrics + traces trả lời các câu hỏi khác nhau.
- Telemetry chỉ hữu ích khi context được propagate xuyên boundaries.

# 9. Vue.js request cancellation: stale response race và UI state correctness

## 1. What is it?

Request cancellation ở frontend dừng network operation không còn giá trị, thường qua `AbortController`. Mental model: UI state có phiên bản theo user intent; response cũ không được phép overwrite state mới chỉ vì nó về muộn.

## 2. Why does it exist?

Search-as-you-type có thể phát nhiều requests. Network không đảm bảo response order. Query `car` gửi trước có thể trả sau query `camera`, làm UI hiển thị kết quả sai dù cả hai API responses đều “đúng”.

## 3. How does it work?

```text
User: c  ─► Request A ─────────────► response late
User: ca ─► Request B ─────► response early
                              │
                              ▼
Without cancellation/versioning: A may overwrite B
```

Cancellation giảm wasted work; sequence/version check vẫn hữu ích vì cancellation có thể race với completion.

## 4. Practical implementation

```ts
let controller: AbortController | null = null;
let requestVersion = 0;

async function search(term: string) {
  controller?.abort();
  controller = new AbortController();
  const version = ++requestVersion;

  const response = await fetch(`/api/search?q=${encodeURIComponent(term)}`, {
    signal: controller.signal
  });

  const data = await response.json();
  if (version === requestVersion) {
    results.value = data;
  }
}
```

Abort không nên được hiển thị như application error cho user.

## 5. Real production scenario

Automotive marketplace filter thay đổi make/model nhanh. API cũ trả chậm do cache miss, API mới trả nhanh do cache hit. Nếu component không bảo vệ ordering, danh sách xe không khớp filter đang hiển thị.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng “nhảy ngược” về dữ liệu cũ.  
**Evidence** → DevTools Network cho thấy responses về khác thứ tự gửi.  
**Hypothesis** → stale async response overwrites current state.  
**Diagnosis** → log request version/filter snapshot.  
**Fix** → abort previous request và/hoặc version guard.  
**Verification** → Playwright route delays để cố tình đảo response order.

## 7. Common mistakes

Chỉ debounce nhưng không xử lý in-flight request; coi `AbortError` là lỗi user-facing; mutate shared state từ mọi response; backend không nhận cancellation nên expensive work vẫn chạy dù browser abort.

## 8. Alternatives

Debounce giảm số requests trước khi gửi. Data-fetching libraries có stale-query/cache semantics. Version guard đơn giản và deterministic khi cancellation support không đầy đủ.

## 9. Trade-offs

### Advantages

Giảm stale UI và unnecessary network/backend work.

### Costs / Risks

State machine phức tạp hơn; cancellation không thay thế server-side timeout/cancellation propagation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async responses có thể về không theo thứ tự.

### Middle

Dùng `AbortController`, debounce và loading/error state đúng.

### Senior

Thiết kế stale-response protection và test race conditions deterministically.

### Technical Lead / Architect

Chuẩn hóa frontend data-fetching behavior và phối hợp cancellation contract với backend APIs.

## 11. Key takeaway

- Response order không phải request order.
- Cancellation là correctness tool, không chỉ performance optimization.
- Race conditions nên được tạo lại có chủ đích trong automated tests.

# 10. AI coding agent verification pipeline: repository grounding, deterministic gates và blast-radius control

## 1. What is it?

Verification pipeline cho coding agent là chuỗi deterministic checks bao quanh probabilistic code generation: repository context → proposed change → build/test/static analysis → diff review → controlled merge/deploy. Mental model: agent tạo candidate change; pipeline quyết định candidate có đủ bằng chứng để đi tiếp hay không.

## 2. Why does it exist?

LLM có thể tạo code compile được nhưng sai requirement, dùng API version không tồn tại, làm test pass vì test sai, hoặc sửa unrelated files. “Agent tự tin” không phải quality signal. Engineering cần machine-verifiable evidence và human review ở risk boundaries.

## 3. How does it work?

```text
Repository + requirements
          │
          ▼
      Coding Agent
          │
          ▼
        Diff
          │
   ┌──────┼─────────┐
   ▼      ▼         ▼
 Build   Tests   Static/Security
   └──────┼─────────┘
          ▼
   Human/risk review
          ▼
      Merge/Deploy
```

Authorization, financial calculations và security-critical decisions phải được enforced bởi deterministic application logic/tests, không bằng prompt instruction đơn thuần.

## 4. Practical implementation

Một CI gate tối thiểu cho .NET repository:

```bash
dotnet restore --locked-mode
dotnet build --no-restore -c Release
dotnet test --no-build -c Release
dotnet format --verify-no-changes
```

Thêm integration/E2E/security checks theo blast radius. Agent prompt nên yêu cầu đọc authoritative requirements nhưng CI không được tin agent đã làm điều đó.

## 5. Real production scenario

Agent sửa authorization handler và tự tạo unit tests. Tests mock claims theo đúng implementation mới nên đều pass, nhưng integration test với real authentication pipeline phát hiện endpoint cho phép tenant A đọc tenant B. Đây là ví dụ “generated test confirms generated assumption”.

## 6. Failure scenario & troubleshooting

**Symptom** → PR xanh nhưng production behavior sai requirement.  
**Evidence** → tests chỉ kiểm tra implementation-level mocks; không có contract/integration coverage cho boundary.  
**Hypothesis** → verification oracle yếu.  
**Diagnosis** → map requirement/risk → test layer; xem diff có unrelated scope không.  
**Fix** → independent acceptance tests, real infrastructure ở critical boundaries, static/security scans và human review.  
**Verification** → reproduce failure bằng test không phụ thuộc generated implementation.

## 7. Common mistakes

Cho agent quyền merge chỉ vì unit tests pass; để agent sửa cả requirements và implementation rồi tự đánh giá; không pin package versions; tin generated tests; không giới hạn file scope; gửi secrets vào model context.

## 8. Alternatives

Human-only coding giảm automation nhưng không tự động đảm bảo correctness. Agent dùng ở analysis/review-only mode có blast radius thấp hơn. Mức autonomy nên tăng theo strength của verification environment.

## 9. Trade-offs

### Advantages

Tăng throughput cho repetitive implementation, refactoring và test scaffolding.

### Costs / Risks

Verification infrastructure, token/tool cost và false confidence nếu gates không đại diện business correctness.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Xem AI output như code của contributor khác: phải build, test và đọc diff.

### Middle

Dùng agent với scoped tasks và verify API/package assumptions.

### Senior

Thiết kế independent tests, security boundaries và failure-oriented review cho agent changes.

### Technical Lead / Architect

Quyết định autonomy theo blast radius; xác định actions nào agent không được tự quyết và evidence nào bắt buộc trước merge/deploy.

## 11. Key takeaway

- LLM output là candidate, không phải source of truth.
- Deterministic gates phải độc lập đủ để bắt generated assumptions sai.
- Agent autonomy chỉ nên tăng khi verification strength và blast-radius control tăng tương ứng.
