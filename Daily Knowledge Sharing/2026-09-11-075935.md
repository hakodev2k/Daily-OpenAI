# 1. .NET linked cancellation + timeout budget: phân biệt client cancellation, application deadline và shutdown cancellation

## 1. What is it?

Trong .NET, `CancellationToken` không phải “exception generator” mà là một tín hiệu cooperative cancellation. Một operation có thể nhận nhiều nguồn hủy khác nhau: client đóng HTTP connection, application deadline hết hạn, hoặc host đang shutdown.

`CancellationTokenSource.CreateLinkedTokenSource` cho phép gom các tín hiệu này thành một token duy nhất cho downstream operation.

Mental model:

```text
Client aborted ─┐
Timeout budget ─┼─> linked token ─> DB / HTTP / storage
Host shutdown ──┘
```

## 2. Why does it exist?

Nếu downstream không biết request đã vô nghĩa, nó vẫn tiêu tốn connection, CPU, database I/O hoặc external API quota. Ngược lại, nếu dùng một timeout cứng cho mọi layer, mỗi layer có thể tự reset timeout và tổng end-to-end latency vượt xa SLO.

Cancellation propagation giúp hệ thống ngừng work sớm khi kết quả không còn giá trị.

## 3. How does it work?

Mỗi `CancellationTokenSource` phát tín hiệu cancellation. Linked source chuyển thành canceled nếu bất kỳ source nào bị cancel.

Timeout nên được hiểu như deadline budget:

```text
Request budget: 2s
API processing: 150ms
Remaining downstream budget: ~1.85s
```

Nếu mỗi downstream lại có timeout riêng 2s, một request nhiều bước có thể kéo dài 6–10s.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:int}", async (
    int id,
    OrdersDbContext db,
    IHostApplicationLifetime lifetime,
    CancellationToken requestAborted) =>
{
    using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(2));
    using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(
        requestAborted,
        timeoutCts.Token,
        lifetime.ApplicationStopping);

    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, linkedCts.Token);

    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

## 5. Real production scenario

Một mobile request bị user đóng sau 300 ms nhưng backend đang chờ SQL query 8 giây. Nếu `RequestAborted` không được propagate, query tiếp tục giữ connection và cạnh tranh tài nguyên với các request còn sống.

Khi traffic tăng, nhiều “zombie work” có thể góp phần làm connection pool exhaustion.

## 6. Failure scenario & troubleshooting

**Symptom** → client timeout nhiều nhưng database vẫn thấy queries chạy lâu sau khi client đã rời đi.

**Evidence** → trace cho thấy HTTP span kết thúc trước dependency span; downstream API/DB call không nhận token.

**Hypothesis** → cancellation bị mất giữa các layer.

**Diagnosis** → kiểm tra method signatures và các lời gọi `HttpClient.SendAsync`, EF Core async APIs, stream APIs.

**Fix** → propagate token xuyên call chain; phân biệt cancellation do client với internal timeout khi map response/logging.

**Verification** → abort request trong load test và xác nhận dependency operation dừng sớm.

## 7. Common mistakes

* Tạo `CancellationToken.None` ở layer giữa và cắt đứt propagation.
* Catch `OperationCanceledException` rồi log `Error` cho mọi trường hợp client disconnect.
* Tạo timeout mới ở từng layer mà không nghĩ tới end-to-end budget.
* Dùng cancellation cho operation đã commit nhưng chưa hoàn thành critical cleanup, làm state khó đoán.

## 8. Alternatives

Timeout ở reverse proxy hoặc gateway vẫn cần thiết để bảo vệ edge, nhưng không thay thế cooperative cancellation bên trong application.

Resilience policies như timeout của `HttpClient` có thể bổ sung dependency-specific budget.

## 9. Trade-offs

### Advantages

Giảm wasted work, giảm resource pressure và làm latency budget rõ ràng hơn.

### Costs / Risks

Cancellation làm control flow phức tạp hơn. Một operation không được thiết kế idempotent/transaction-safe có thể để lại partial state nếu bị hủy sai thời điểm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu token là tín hiệu cooperative; code phải chủ động truyền và quan sát nó.

### Middle

Biết propagate token vào EF Core, HttpClient và background work.

### Senior

Phân biệt timeout, client abort, host shutdown; thiết kế transactional boundary để cancellation không phá correctness.

### Technical Lead / Architect

Đặt end-to-end latency budget và quyết định layer nào được quyền hủy operation, layer nào phải hoàn tất critical work.

## 11. Key takeaway

* Cancellation nên được propagate, không được “reset” tùy tiện.
* Timeout nên được quản lý như end-to-end budget.
* Không phải mọi `OperationCanceledException` đều là application error.

# 2. ASP.NET Core `ProblemDetails` + exception mapping: biến lỗi nội bộ thành error contract ổn định thay vì leak implementation details

## 1. What is it?

`ProblemDetails` là chuẩn biểu diễn lỗi HTTP theo RFC 7807/9457 style với các field như `type`, `title`, `status`, `detail`, `instance` và extensions.

Giá trị chính không nằm ở JSON shape, mà ở việc tách internal exception model khỏi public API error contract.

## 2. Why does it exist?

Nếu controller nào cũng tự trả error khác nhau, client phải xử lý nhiều shape. Nếu trả thẳng exception message, API có thể leak SQL, path, stack trace hoặc internal identifiers.

Một error contract ổn định giúp frontend, mobile và integrations dựa vào semantics thay vì implementation detail.

## 3. How does it work?

Flow:

```text
Exception / domain failure
        ↓
central exception handler
        ↓
map to stable HTTP semantics
        ↓
ProblemDetails
        ↓
client
```

Ví dụ `OrderNotFoundException` có thể map `404`; validation map `400`; concurrency conflict map `409`; unknown exception map `500` với correlation identifier thay vì stack trace.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler(exceptionHandlerApp =>
{
    exceptionHandlerApp.Run(async context =>
    {
        var exception = context.Features
            .Get<IExceptionHandlerFeature>()?.Error;

        var (status, title) = exception switch
        {
            KeyNotFoundException => (404, "Resource not found"),
            DbUpdateConcurrencyException => (409, "Concurrency conflict"),
            _ => (500, "Unexpected server error")
        };

        context.Response.StatusCode = status;

        await Results.Problem(
            statusCode: status,
            title: title,
            extensions: new Dictionary<string, object?>
            {
                ["traceId"] = context.TraceIdentifier
            })
            .ExecuteAsync(context);
    });
});
```

Production code nên dùng centralized mapper/testable handler thay vì nhồi logic lớn vào middleware.

## 5. Real production scenario

Frontend gọi `PATCH /projects/42`. Backend gặp optimistic concurrency conflict. Nếu trả 500 generic, UI chỉ hiện “Something went wrong”. Nếu contract trả `409` + machine-readable problem type, UI có thể yêu cầu user reload dữ liệu mới.

## 6. Failure scenario & troubleshooting

**Symptom** → mobile app xử lý một lỗi đúng ở dev nhưng fail ở Production vì error body khác shape.

**Evidence** → logs cho thấy các controllers/middleware trả lỗi theo nhiều format.

**Hypothesis** → không có centralized error contract.

**Diagnosis** → inventory tất cả status codes và body schemas.

**Fix** → chuẩn hóa mapping và contract tests.

**Verification** → integration tests cho 400/401/403/404/409/429/500 và schema tương ứng.

## 7. Common mistakes

* Dùng `detail = exception.Message` cho 500 Production.
* Trả `200 OK` với `{ success:false }` cho business/API errors.
* Map mọi exception thành 400.
* Dùng exception cho expected validation flow quá thường xuyên.

## 8. Alternatives

Result type/application error objects có thể biểu diễn expected failures mà không ném exception. Exception handler vẫn cần cho unexpected failures.

## 9. Trade-offs

### Advantages

Contract nhất quán, dễ observability, ít leak thông tin và client behavior rõ hơn.

### Costs / Risks

Cần governance về problem types/status codes. Over-modeling hàng trăm error codes có thể tạo maintenance burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP status và error body là một phần API contract.

### Middle

Biết centralized exception handling và `ProblemDetails`.

### Senior

Phân loại expected vs unexpected failures, security exposure và backward compatibility.

### Technical Lead / Architect

Định nghĩa cross-service error taxonomy đủ ổn định nhưng không quá phức tạp.

## 11. Key takeaway

* Public error contract không nên phản chiếu internal exception hierarchy.
* `ProblemDetails` hữu ích khi semantics được chuẩn hóa, không chỉ vì JSON đẹp.
* 500 response không nên leak stack trace hoặc infrastructure detail.

# 3. EF Core `ExecuteUpdateAsync` / `ExecuteDeleteAsync`: bulk mutation nhanh hơn nhưng bypass change tracker và domain behavior

## 1. What is it?

`ExecuteUpdateAsync` và `ExecuteDeleteAsync` cho phép EF Core phát trực tiếp SQL `UPDATE`/`DELETE` cho một query mà không materialize từng entity và không dùng change tracker cho các rows đó.

```text
Traditional:
SELECT entities → track → mutate → SaveChanges

Set-based:
UPDATE ... WHERE ...
```

## 2. Why does it exist?

Nếu cần expire 100.000 sessions, load tất cả rows vào memory chỉ để đổi một field là lãng phí I/O, allocation và round trips.

Set-based database operation tận dụng khả năng xử lý tập hợp của relational database.

## 3. How does it work?

EF dịch query predicate và update expression thành SQL trực tiếp. Operation thực thi ngay và không chờ `SaveChanges()`.

Điều quan trọng: tracked entities đã tồn tại trong `DbContext` không tự được đồng bộ giá trị mới.

## 4. Practical implementation

```csharp
var affected = await db.Sessions
    .Where(x => x.ExpiresUtc < DateTime.UtcNow && x.Status == SessionStatus.Active)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, SessionStatus.Expired)
        .SetProperty(x => x.UpdatedUtc, DateTime.UtcNow), ct);
```

Bulk delete:

```csharp
await db.AuditEntries
    .Where(x => x.CreatedUtc < cutoff)
    .ExecuteDeleteAsync(ct);
```

## 5. Real production scenario

Nightly retention job cần xóa hàng triệu telemetry staging rows. Materialize + `RemoveRange` làm process memory tăng và transaction kéo dài. `ExecuteDeleteAsync` tạo một set-based statement đơn giản hơn nhiều.

## 6. Failure scenario & troubleshooting

**Symptom** → sau `ExecuteUpdateAsync`, code đọc tracked entity trong cùng `DbContext` và thấy giá trị cũ.

**Evidence** → SQL đã update DB nhưng change tracker vẫn giữ snapshot trước đó.

**Hypothesis** → bulk operation bypass tracker.

**Diagnosis** → kiểm tra `ChangeTracker.Entries()` và lifetime của context.

**Fix** → tránh mixing tracked entity với set-based mutation trong cùng unit of work, hoặc reload/clear tracker có chủ đích.

**Verification** → integration test trạng thái DB và in-memory state.

## 7. Common mistakes

* Gọi `ExecuteUpdateAsync` rồi nghĩ `SaveChanges` mới commit mutation đó.
* Dùng bulk update cho aggregate mà domain invariant/domain event phải chạy per entity.
* Không kiểm tra số rows affected khi đó là correctness signal.
* Chạy update cực lớn trong một transaction mà không đánh giá locks/log growth.

## 8. Alternatives

Tracked updates phù hợp khi cần domain behavior, concurrency token per entity hoặc thay đổi nhỏ.

Raw SQL/stored procedure có thể tối ưu sâu hơn nhưng giảm abstraction/type safety.

## 9. Trade-offs

### Advantages

Ít round trips, ít allocations, phù hợp bulk data maintenance.

### Costs / Risks

Bypass change tracker, domain hooks và một số per-entity semantics; transaction/locking impact vẫn phải đánh giá.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu set-based update khác với load từng entity rồi save.

### Middle

Biết dùng APIs đúng và nhận biết tracker stale.

### Senior

Đánh giá locks, transaction size, business invariants và concurrency behavior.

### Technical Lead / Architect

Quyết định mutation nào thuộc domain workflow và mutation nào chỉ là data-maintenance concern.

## 11. Key takeaway

* Bulk APIs nhanh vì không materialize entities.
* Chúng bypass change tracker và domain behavior.
* Performance win không được đánh đổi correctness mù quáng.

# 4. SQL Server covering index với `INCLUDE`: giảm key lookup nhưng hiểu write cost, width và index bloat

## 1. What is it?

Covering index là index chứa đủ columns để SQL Server trả kết quả query mà không cần quay về clustered index/heap để lấy thêm dữ liệu.

`INCLUDE` cho phép thêm non-key columns vào leaf level mà không đưa chúng vào key ordering.

## 2. Why does it exist?

Một nonclustered index có thể seek đúng rows nhưng query vẫn phải thực hiện hàng nghìn key lookups để lấy columns còn thiếu. Với selective query ít rows, lookup rẻ; với nhiều rows, lookup trở thành random I/O đáng kể.

## 3. How does it work?

Query:

```sql
SELECT Id, CustomerId, TotalAmount
FROM Orders
WHERE Status = @status
ORDER BY CreatedUtc DESC;
```

Index:

```sql
CREATE INDEX IX_Orders_Status_CreatedUtc
ON Orders(Status, CreatedUtc DESC)
INCLUDE (Id, CustomerId, TotalAmount);
```

Database có thể seek/filter/order và trả projection từ chính index.

## 4. Practical implementation

Trước khi tạo index, đo actual execution plan và logical reads:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

So sánh trước/sau thay đổi và kiểm tra write workload, index size, fragmentation/maintenance impact.

## 5. Real production scenario

Order listing endpoint p95 tăng từ 100 ms lên 1.5 s khi số active orders tăng. Plan cho thấy `Index Seek` nghe có vẻ tốt nhưng theo sau là 80.000 `Key Lookup` operations.

Thêm đúng `INCLUDE` columns giảm lookup và logical reads đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → read query nhanh hơn nhưng bulk import/update chậm rõ rệt sau khi thêm nhiều indexes.

**Evidence** → index usage cho thấy một số index rất rộng, write duration và transaction log tăng.

**Hypothesis** → read optimization tạo write amplification.

**Diagnosis** → xem index usage, size, write frequency và workload mix.

**Fix** → loại index trùng lặp/ít dùng, thu hẹp includes hoặc đổi query projection.

**Verification** → benchmark cả read và write paths.

## 7. Common mistakes

* `INCLUDE` mọi column để “cover tất cả”.
* Chỉ nhìn index seek mà bỏ qua lookup count.
* Tạo index theo từng slow query riêng lẻ, gây hàng chục overlapping indexes.
* Không giảm `SELECT *` trước khi mở rộng index.

## 8. Alternatives

Có thể giảm projection, dùng clustered index phù hợp hơn hoặc thay đổi access pattern. Không phải query nào cũng cần covering index.

## 9. Trade-offs

### Advantages

Giảm random lookups và I/O cho hot read queries.

### Costs / Risks

Tốn storage, cache memory, tăng write amplification và maintenance cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index có thể chứa thêm data để tránh quay về base row.

### Middle

Biết đọc execution plan và nhận diện key lookup.

### Senior

Đánh giá selectivity, logical reads, write cost và overlapping indexes.

### Technical Lead / Architect

Thiết kế indexing theo workload toàn hệ thống thay vì tối ưu từng query cô lập.

## 11. Key takeaway

* Covering index giải quyết lookup cost, không phải mọi slow query.
* `INCLUDE` vẫn có storage/write cost.
* Đo plan + I/O trước và sau thay đổi.

# 5. MongoDB read concern + write concern: chọn durability/consistency theo business requirement thay vì dùng mặc định một cách mù quáng

## 1. What is it?

`writeConcern` mô tả mức xác nhận cần đạt trước khi MongoDB coi write thành công. `readConcern` mô tả mức isolation/consistency mà read yêu cầu.

Chúng là knobs về correctness, latency và availability chứ không chỉ driver options.

## 2. Why does it exist?

Distributed replica set phải cân bằng giữa trả response nhanh và đảm bảo dữ liệu đã được replicate đủ để sống sót qua failure.

Business data như payment state có yêu cầu khác analytics event hoặc ephemeral activity feed.

## 3. How does it work?

Ví dụ `w: "majority"` yêu cầu write được acknowledge theo majority semantics trước khi trả success.

`readConcern: "majority"` tránh đọc data chưa majority-committed.

Higher guarantees thường thêm latency hoặc giảm availability trong partition/failure scenario.

## 4. Practical implementation

C# driver:

```csharp
var collection = database
    .GetCollection<OrderDocument>("orders")
    .WithWriteConcern(WriteConcern.WMajority)
    .WithReadConcern(ReadConcern.Majority);

await collection.InsertOneAsync(order, cancellationToken: ct);
```

Không nên copy configuration này vào mọi collection mà không xét business semantics.

## 5. Real production scenario

Một notification history store chấp nhận eventual visibility vài giây. Nhưng order confirmation không nên trả “success” nếu write chỉ tồn tại trên một node dễ mất trong failover.

Hai workload có thể chọn concerns khác nhau.

## 6. Failure scenario & troubleshooting

**Symptom** → client vừa tạo record nhưng sau failover không còn thấy dữ liệu như mong đợi.

**Evidence** → driver config dùng weak acknowledgement; failover xảy ra ngay sau write.

**Hypothesis** → durability requirement và write concern không khớp.

**Diagnosis** → kiểm tra connection/client settings, replica health và timing.

**Fix** → chọn concern dựa trên business durability requirement; test failure scenario.

**Verification** → chaos/failover test với expected guarantees.

## 7. Common mistakes

* Nghĩ NoSQL luôn eventual consistency.
* Chọn strongest concern mọi nơi mà không đo latency/availability cost.
* Chọn weak settings vì benchmark nhanh hơn nhưng không document risk.
* Không xét interaction giữa retryable writes và idempotency/business keys.

## 8. Alternatives

SQL Server/PostgreSQL có consistency/transaction semantics khác. Cosmos DB cung cấp nhiều consistency levels ở distributed service model khác.

## 9. Trade-offs

### Advantages

Cho phép map durability/consistency tới từng workload thay vì một global assumption.

### Costs / Risks

Guarantee mạnh hơn có thể tăng latency và làm writes unavailable hơn trong một số failures.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu write success có nhiều mức nghĩa trong replicated database.

### Middle

Biết configure read/write concerns và test behavior.

### Senior

Hiểu failover, replication lag, retries và business correctness.

### Technical Lead / Architect

Định nghĩa consistency/durability requirement theo domain thay vì để driver default quyết định kiến trúc.

## 11. Key takeaway

* Read/write concern là business correctness knobs.
* Stronger guarantee không miễn phí.
* Chọn theo failure semantics thực tế, không theo slogan SQL vs NoSQL.

# 6. Hexagonal Architecture ports/adapters: cô lập third-party dependencies mà không biến codebase thành ceremony

## 1. What is it?

Hexagonal Architecture đặt business/application logic ở trung tâm. Các external systems đi qua ports; concrete integrations là adapters.

```text
HTTP adapter ─┐
              ▼
         Application
              │
          Port/interface
              ▼
        Payment adapter
              ▼
        External API
```

Mục tiêu là boundary và dependency direction, không phải số lượng folders.

## 2. Why does it exist?

Nếu domain/application code trực tiếp dùng SDK của payment provider, CMS hoặc search engine, external contract lan khắp codebase. Khi provider thay schema hoặc migration, change blast radius lớn.

## 3. How does it work?

Core định nghĩa capability nó cần:

```csharp
public interface IPaymentGateway
{
    Task<PaymentResult> ChargeAsync(
        PaymentRequest request,
        CancellationToken ct);
}
```

Infrastructure adapter chuyển domain/application request sang provider-specific SDK/HTTP contract.

Dependency hướng từ adapter vào port, không từ core vào SDK.

## 4. Practical implementation

```csharp
public sealed class StripePaymentGateway : IPaymentGateway
{
    private readonly HttpClient _http;

    public StripePaymentGateway(HttpClient http) => _http = http;

    public async Task<PaymentResult> ChargeAsync(
        PaymentRequest request,
        CancellationToken ct)
    {
        var providerRequest = new
        {
            amount = request.AmountMinor,
            currency = request.Currency
        };

        using var response = await _http.PostAsJsonAsync(
            "/payments", providerRequest, ct);

        response.EnsureSuccessStatusCode();
        var dto = await response.Content.ReadFromJsonAsync<ProviderPayment>(ct);

        return new PaymentResult(dto!.Id, dto.Status == "captured");
    }
}
```

## 5. Real production scenario

E-commerce platform thay review provider. Nếu controllers/domain entities chứa provider DTOs, migration chạm hàng chục files. Nếu provider nằm sau `IReviewService`, thay adapter và mapping nhỏ hơn đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → provider thêm field/status mới và business logic ở nhiều nơi xử lý sai.

**Evidence** → search code thấy SDK enums/DTOs xuất hiện trong application/domain layers.

**Hypothesis** → external model đã vượt architectural boundary.

**Diagnosis** → dependency analysis và code search.

**Fix** → tạo anti-corruption mapping/port ở đúng boundary.

**Verification** → core tests không cần provider SDK; adapter integration tests cover provider contract.

## 7. Common mistakes

* Tạo interface cho mọi class dù không có meaningful boundary.
* Đặt adapter abstraction nhưng vẫn leak provider DTO vào interface.
* Tạo generic repository chỉ để “đúng Hexagonal”.
* Có 20 layers cho CRUD app nhỏ không có change pressure.

## 8. Alternatives

Layered Architecture đơn giản hơn có thể đủ cho application nhỏ. Modular Monolith có thể kết hợp ports/adapters ở những external boundaries quan trọng.

## 9. Trade-offs

### Advantages

Giảm coupling với external systems, test core dễ hơn, migration provider dễ kiểm soát hơn.

### Costs / Risks

Mapping và abstractions tăng code. Nếu boundary không có volatility, abstraction có thể chỉ là ceremony.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu core logic không nên phụ thuộc trực tiếp mọi infrastructure detail.

### Middle

Biết thiết kế interface theo capability của application.

### Senior

Nhận diện model leakage, ownership và failure translation ở adapter boundary.

### Technical Lead / Architect

Quyết định boundary nào đáng abstraction dựa trên business volatility và integration risk.

## 11. Key takeaway

* Hexagonal Architecture là dependency/boundary discipline, không phải folder template.
* Port nên nói ngôn ngữ của application, không leak provider model.
* Không cần abstraction nếu chưa có problem thật sự cần giải quyết.

# 7. Azure Service Bus sessions: giữ message ordering theo business key trong hệ thống at-least-once

## 1. What is it?

Service Bus sessions nhóm messages theo `SessionId`. Một consumer giữ session lock và xử lý stream messages của session theo thứ tự broker cung cấp.

Ví dụ:

```text
Order-42: Created → Paid → Shipped
Order-99: Created → Cancelled
```

Hai orders có thể xử lý song song, nhưng messages trong cùng order session được serialize.

## 2. Why does it exist?

Một queue nhiều competing consumers tối ưu throughput nhưng có thể xử lý events cùng aggregate ngoài thứ tự. `Shipped` chạy trước `Paid` có thể phá business state machine.

Session cho phép ordering theo partition/business key thay vì serialize toàn bộ queue.

## 3. How does it work?

Producer đặt `SessionId = OrderId`. Broker phân phối một session cho một session receiver tại một thời điểm.

Tuy nhiên Service Bus vẫn theo at-least-once semantics: duplicate delivery vẫn có thể xảy ra. Ordering không thay thế idempotency.

## 4. Practical implementation

Producer:

```csharp
var message = new ServiceBusMessage(BinaryData.FromObjectAsJson(evt))
{
    MessageId = evt.EventId.ToString(),
    SessionId = evt.OrderId.ToString()
};

await sender.SendMessageAsync(message, ct);
```

Processor:

```csharp
var options = new ServiceBusSessionProcessorOptions
{
    MaxConcurrentSessions = 16,
    MaxConcurrentCallsPerSession = 1,
    AutoCompleteMessages = false
};
```

Consumer vẫn cần deduplication/business transition validation.

## 5. Real production scenario

Order workflow phát `PaymentCaptured` và `OrderCancelled` gần nhau. Nếu handlers chạy unordered, downstream fulfillment có thể ship order sau khi cancel.

Session theo `OrderId` giúp serialize state transitions trong cùng order.

## 6. Failure scenario & troubleshooting

**Symptom** → một session backlog lớn trong khi queue tổng thể vẫn có capacity.

**Evidence** → một `SessionId` có rất nhiều messages hoặc handler cho session đó chậm.

**Hypothesis** → hot session/business key tạo serialized bottleneck.

**Diagnosis** → metric theo session/business key, processing duration và retries.

**Fix** → tối ưu handler, tránh long-running work trong critical ordered path, xem lại session granularity.

**Verification** → backlog age giảm và ordering tests vẫn pass.

## 7. Common mistakes

* Nghĩ sessions tạo exactly-once processing.
* Dùng một `SessionId` cho toàn bộ tenant lớn khiến queue gần như single-threaded.
* Không renew lock cho long-running handlers.
* Retry non-idempotent handler và tạo duplicate side effect.

## 8. Alternatives

Nếu order không quan trọng, queue bình thường đơn giản và throughput cao hơn. Một database state machine với optimistic concurrency cũng có thể chống invalid transition mà không dựa hoàn toàn vào broker ordering.

## 9. Trade-offs

### Advantages

Ordering theo business key, concurrency giữa các keys và stateful session workflow khi cần.

### Costs / Risks

Hot sessions giới hạn throughput; lock/session operations tăng complexity; duplicates vẫn phải xử lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu message queue có thể xử lý song song và vì thế ordering không tự nhiên được đảm bảo ở mọi workflow.

### Middle

Biết set `SessionId` và cấu hình session processor.

### Senior

Thiết kế idempotency, lock renewal, poison handling và hot-session diagnosis.

### Technical Lead / Architect

Quyết định business entity nào thật sự cần ordering và liệu broker ordering hay domain concurrency control là boundary tốt hơn.

## 11. Key takeaway

* Sessions cho ordering theo key, không phải global ordering miễn phí.
* At-least-once vẫn tồn tại; consumer cần idempotency.
* Session key sai có thể biến scalability problem thành serialized bottleneck.

# 8. Immutable deployment artifact + environment promotion: build một lần, promote cùng artifact qua nhiều môi trường

## 1. What is it?

Immutable artifact strategy nghĩa là CI build một package/image duy nhất từ một commit, sau đó cùng artifact đó được promote qua Test → Staging → Production. Environment-specific configuration được inject khi deploy/runtime, không rebuild binary cho từng môi trường.

## 2. Why does it exist?

Nếu Production được rebuild riêng, code đã test không nhất thiết là code được deploy. Package restore, compiler version, generated assets hoặc dependencies có thể drift giữa builds.

Build-once giúp provenance rõ ràng hơn.

## 3. How does it work?

```text
commit
  ↓
build + test
  ↓
artifact v1.8.42
  ├─ deploy Test + Test config
  ├─ promote Staging + Staging config
  └─ promote Production + Prod config
```

Octopus Deploy, Azure DevOps hay Jenkins pipeline đều có thể áp dụng nguyên lý này.

## 4. Practical implementation

CI publish:

```bash
dotnet restore
dotnet test --configuration Release
dotnet publish src/Web/Web.csproj \
  --configuration Release \
  --no-restore \
  --output ./artifacts/web
```

Configuration như connection string/Key Vault URI không bake vào binary; nó được cấp qua environment variables/secret store/deployment variables.

## 5. Real production scenario

Team build lại package lúc Production deploy ba ngày sau Staging. Một transitive dependency floating version thay đổi. Production binary khác Staging dù source commit giống nhau.

Build-once loại lớp drift này.

## 6. Failure scenario & troubleshooting

**Symptom** → “same commit” chạy đúng Staging nhưng crash Production và checksum package khác.

**Evidence** → artifact IDs/hashes giữa environments không giống nhau.

**Hypothesis** → pipeline rebuild per environment.

**Diagnosis** → trace provenance từ commit → CI run → artifact hash → release.

**Fix** → promote immutable artifact; tách configuration khỏi build.

**Verification** → hash artifact giống nhau ở mọi environment, chỉ config khác.

## 7. Common mistakes

* Bake secrets vào `appsettings.Production.json` trong artifact.
* Rebuild frontend/backend riêng khi promote.
* Dùng mutable Docker tag như `latest` làm release identity duy nhất.
* Không lưu provenance commit/build/artifact.

## 8. Alternatives

Một số generated static sites cần environment-specific build-time variables; khi đó phải coi mỗi build là artifact khác và test đúng artifact Production sẽ dùng.

## 9. Trade-offs

### Advantages

Giảm drift, rollback rõ hơn, auditability và supply-chain provenance tốt hơn.

### Costs / Risks

Yêu cầu configuration discipline và pipeline promotion model tốt; build-time environment assumptions phải được loại bỏ hoặc quản lý rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu artifact là output build cụ thể, không phải chỉ source commit.

### Middle

Biết tách config/secrets và promote package/image.

### Senior

Thiết kế provenance, rollback, database migration compatibility và health validation.

### Technical Lead / Architect

Định nghĩa release model đảm bảo “what we tested is what we run”.

## 11. Key takeaway

* Same commit không đảm bảo same artifact nếu rebuild.
* Build once, promote many giảm deployment drift.
* Secrets/configuration nên tách khỏi immutable binary/image.

# 9. Application Insights sampling + high-cardinality telemetry: giảm cost mà không phá khả năng điều tra Production

## 1. What is it?

Sampling giảm lượng telemetry được ingest bằng cách giữ một phần representative traces/requests thay vì lưu mọi event. High-cardinality dimensions là fields có rất nhiều giá trị khác nhau như `userId`, `orderId`, URL chứa random IDs.

Hai khái niệm liên quan trực tiếp đến observability cost và query usefulness.

## 2. Why does it exist?

Một service traffic cao có thể phát hàng triệu spans/logs mỗi giờ. Lưu tất cả làm ingestion/storage cost tăng. Nhưng sampling sai có thể loại chính trace cần điều tra.

High-cardinality tags cũng làm metrics dimensions bùng nổ và query đắt.

## 3. How does it work?

Sampling thường quyết định trace nào được giữ theo probability/rate hoặc adaptive rules. Tốt nhất các spans của cùng trace giữ quyết định nhất quán.

Metrics cho aggregate signals nên dùng dimensions bounded; trace/log dùng identifiers để drill down khi cần.

```text
Metric: endpoint=/orders/{id}, status=500
Trace: order.id=8f7... khi cần investigation
```

## 4. Practical implementation

OpenTelemetry sampler example:

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .SetSampler(new ParentBasedSampler(
            new TraceIdRatioBasedSampler(0.10)))
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddOtlpExporter());
```

Không nên đưa raw `userId` thành metric dimension rộng nếu dashboard chỉ cần tenant tier/endpoint/status class.

## 5. Real production scenario

API 50k RPM ghi mọi request dependency span vào Application Insights. Cost tăng mạnh. Team bật sampling 5%, nhưng không giữ failed/slow traces hợp lý, khiến incident p99 khó điều tra.

Giải pháp tốt hơn là kết hợp metrics đầy đủ để detect issue với sampled traces được thiết kế để giữ giá trị diagnostic.

## 6. Failure scenario & troubleshooting

**Symptom** → alert báo 5xx tăng nhưng truy vấn traces gần như không thấy failures.

**Evidence** → sampling configuration loại quá nhiều error traces hoặc telemetry processors không nhất quán.

**Hypothesis** → observability pipeline tối ưu cost quá mức.

**Diagnosis** → kiểm tra sampling rate, ingestion pipeline, exception/request linkage.

**Fix** → tune sampling, ưu tiên giữ error/slow traces khi platform hỗ trợ, dùng metrics cho complete aggregate signal.

**Verification** → synthetic failures xuất hiện đủ evidence để trace root cause trong acceptable cost budget.

## 7. Common mistakes

* Log mọi request body để “debug dễ hơn”.
* Dùng unique IDs làm metric dimensions.
* Giảm sampling mà không kiểm tra incident investigation quality.
* Nghĩ logs, metrics và traces là ba bản sao tương đương.

## 8. Alternatives

Có thể tăng retention ngắn hạn trong incident hoặc route audit/security logs sang storage khác. Không phải telemetry nào cũng cần Application Insights.

## 9. Trade-offs

### Advantages

Sampling kiểm soát cost và volume; cardinality discipline làm metrics/dashboards ổn định hơn.

### Costs / Risks

Mất chi tiết nếu sampling quá mạnh; telemetry design cần governance và testing.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu không phải mọi telemetry đều cần lưu vĩnh viễn.

### Middle

Biết phân biệt metric dimensions và trace attributes.

### Senior

Thiết kế sampling để vẫn điều tra được errors/p99 incidents.

### Technical Lead / Architect

Đặt observability budget, data-retention policy, PII rules và SLO-driven telemetry strategy.

## 11. Key takeaway

* Observability volume là một resource có cost.
* High cardinality có thể phá metrics economics và usability.
* Sampling phải được đánh giá bằng khả năng điều tra incident, không chỉ tiền tiết kiệm.

# 10. AI Tool Calling với deterministic validation: model đề xuất action, application vẫn quyết định action có hợp lệ và được phép hay không

## 1. What is it?

Tool Calling cho phép LLM sinh structured request để application gọi một function/tool. Model có thể chọn tool và arguments, nhưng output đó vẫn là untrusted probabilistic input.

Mental model an toàn:

```text
User intent
  ↓
LLM proposes tool call
  ↓
Schema validation
  ↓
Authorization + business rules
  ↓
Deterministic execution
  ↓
Tool result
  ↓
LLM explanation
```

## 2. Why does it exist?

LLM rất tốt trong việc hiểu language và chọn hành động, nhưng không nên trực tiếp nắm quyền quyết định security-critical hoặc financial action. Hallucination, prompt injection hoặc ambiguous intent có thể tạo arguments sai.

## 3. How does it work?

Structured schema giới hạn shape của arguments, nhưng schema-valid không đồng nghĩa business-valid.

Ví dụ `{ "amount": 1000000, "accountId": "X" }` có thể valid JSON/schema nhưng user không có quyền transfer từ account X.

Authorization phải dùng authenticated identity và server-side policy, không dựa vào model statement.

## 4. Practical implementation

```csharp
public async Task<IResult> ExecuteTransferAsync(
    ClaimsPrincipal user,
    TransferToolArgs args,
    CancellationToken ct)
{
    if (args.Amount <= 0 || args.Amount > 10_000)
        return Results.BadRequest("Invalid amount");

    if (!await authorization.CanTransferAsync(user, args.AccountId, ct))
        return Results.Forbid();

    var command = new TransferMoneyCommand(
        args.AccountId,
        args.DestinationId,
        args.Amount);

    var result = await handler.HandleAsync(command, ct);
    return Results.Ok(result);
}
```

LLM không được truyền một boolean như `isAuthorized=true` để bypass policy.

## 5. Real production scenario

AI assistant nội bộ có tools `search_documents`, `create_ticket`, `disable_user`. Một retrieved document chứa prompt injection yêu cầu gọi `disable_user` cho admin account.

Nếu application chỉ tin model-selected tool call, indirect prompt injection trở thành privileged action. Nếu authorization/policy nằm deterministic server-side, action bị chặn.

## 6. Failure scenario & troubleshooting

**Symptom** → model tạo tool call syntactically valid nhưng action không phù hợp user intent hoặc permission.

**Evidence** → trace lưu tool proposal, authenticated actor, validation decision và execution result.

**Hypothesis** → tool layer đang coi model output như trusted command.

**Diagnosis** → review boundary giữa model runtime và domain/application services.

**Fix** → schema validation, authorization, business invariants, idempotency và confirmation policy cho high-impact actions.

**Verification** → adversarial tests/prompt injection tests phải không vượt policy boundary.

## 7. Common mistakes

* Tin Structured Output đồng nghĩa correct action.
* Cho model tự quyết định user role/permission.
* Tool function trực tiếp gọi database bằng arbitrary query từ model.
* Không log/audit action source và authorization decision.
* Retry tool call có side effect mà không idempotency.

## 8. Alternatives

Với workflow hoàn toàn deterministic, rule engine/form-based UI đơn giản hơn AI agent. LLM chỉ nên được thêm khi natural-language interpretation tạo giá trị thật.

## 9. Trade-offs

### Advantages

Tool Calling tạo UX tự nhiên và cho LLM phối hợp nhiều capabilities.

### Costs / Risks

Thêm security boundary, evaluation, audit, latency, token cost và failure modes khó đoán hơn deterministic UI/workflow.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu model output chỉ là đề xuất dữ liệu/action, không phải trusted instruction.

### Middle

Biết validate schema và gọi application service thay vì expose infrastructure trực tiếp.

### Senior

Thiết kế authz, idempotency, prompt-injection defenses, audit trail và evaluation.

### Technical Lead / Architect

Quyết định action nào AI được phép đề xuất, action nào cần confirmation, và boundary nào phải luôn deterministic.

## 11. Key takeaway

* Structured schema không thay thế authorization/business validation.
* Model không nên là security boundary.
* High-impact tool calls cần deterministic policy, audit và idempotency.
