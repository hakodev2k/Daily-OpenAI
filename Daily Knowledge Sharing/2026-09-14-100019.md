# 1. `CancellationToken` propagation trong .NET: cancellation phải đi xuyên suốt call chain

## 1. What is it?

Mental model đơn giản:

```text
Client disconnects / request timeout / shutdown
                |
                v
        CancellationToken
                |
                v
Controller -> Service -> Repository -> HTTP/DB call
```

`CancellationToken` là tín hiệu phối hợp để các operation đang chạy có thể dừng sớm khi công việc không còn cần thiết. Nó không "kill thread" và cũng không tự động hủy mọi thứ chỉ vì method có tham số token.

Điểm quan trọng là propagation: token phải được truyền tới operation thực sự có khả năng cancel như `HttpClient`, EF Core, stream I/O, delay hoặc background workflow.

## 2. Why does it exist?

Nếu client đã đóng request nhưng server vẫn tiếp tục query database, gọi API downstream hoặc serialize response, hệ thống đang tiêu CPU, connection, memory và quota cho công việc không còn giá trị.

Trong production, cancellation đặc biệt quan trọng khi:

- request có fan-out tới nhiều dependencies,
- database pool bị giới hạn,
- external API tính phí theo request,
- deployment cần graceful shutdown,
- background worker xử lý message dài.

Không propagate cancellation có thể biến một traffic spike thành resource exhaustion.

## 3. How does it work?

`CancellationTokenSource` giữ trạng thái cancellation. `CancellationToken` là lightweight value được truyền cho consumer.

Khi source gọi `Cancel()`, các API hỗ trợ token sẽ quan sát trạng thái đó và thường throw `OperationCanceledException` hoặc `TaskCanceledException`.

```text
HTTP request aborted
    -> RequestAborted token cancelled
        -> EF Core query cancelled
        -> SQL command cancelled
        -> connection được trả về pool sớm hơn
```

Cancellation là cooperative. Nếu code chạy CPU loop nhưng không kiểm tra token, nó vẫn tiếp tục chạy.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    OrderService service,
    CancellationToken cancellationToken) =>
{
    var order = await service.GetAsync(id, cancellationToken);
    return order is null ? Results.NotFound() : Results.Ok(order);
});

public sealed class OrderService
{
    private readonly AppDbContext _db;

    public OrderService(AppDbContext db) => _db = db;

    public Task<OrderDto?> GetAsync(Guid id, CancellationToken ct)
        => _db.Orders
            .Where(x => x.Id == id)
            .Select(x => new OrderDto(x.Id, x.Total))
            .SingleOrDefaultAsync(ct);
}
```

Với `HttpClient`:

```csharp
using var response = await httpClient.GetAsync(url, ct);
```

Với CPU loop dài:

```csharp
foreach (var item in items)
{
    ct.ThrowIfCancellationRequested();
    Process(item);
}
```

## 5. Real production scenario

Một API export báo cáo gọi SQL Server, Blob Storage và một service khác. User đóng tab sau 2 giây nhưng backend tiếp tục chạy 40 giây.

Nếu 100 user làm vậy cùng lúc, request đã "biến mất" ở frontend nhưng hệ thống vẫn giữ hàng chục SQL connections và outbound HTTP calls. Propagation đúng giúp từng layer dừng sớm và trả tài nguyên về pool.

## 6. Failure scenario & troubleshooting

**Symptom** → request timeout cao, SQL pool cạn dù traffic không lớn.

**Evidence** → trace cho thấy request client đã abort nhưng dependency spans vẫn tiếp tục nhiều giây.

**Hypothesis** → token bị dừng ở service layer.

**Diagnosis** → tìm các lời gọi `ToListAsync()`, `SendAsync()`, `ReadAsync()` không truyền token.

**Fix** → propagate token xuyên call chain; với library không hỗ trợ cancellation, cân nhắc timeout hoặc isolation khác.

**Verification** → abort request và kiểm tra dependency operation kết thúc sớm trong trace.

## 7. Common mistakes

- Nhận `CancellationToken` ở controller nhưng không truyền xuống dưới.
- Tạo `new CancellationTokenSource()` ở mỗi layer, làm mất cancellation gốc.
- Bắt `OperationCanceledException` rồi log như lỗi hệ thống.
- Dùng cancellation để thay thế timeout policy.
- Cancel một operation không hỗ trợ cooperative cancellation rồi giả định nó đã dừng.

## 8. Alternatives

Cancellation không thay cho:

- timeout: giới hạn thời gian tối đa,
- Circuit Breaker: ngăn dependency lỗi kéo dài,
- Bulkhead: giới hạn concurrent work,
- queue: tách request lifecycle khỏi long-running work.

Chúng giải quyết các failure mode khác nhau.

## 9. Trade-offs

### Advantages

- giải phóng tài nguyên sớm,
- cải thiện graceful shutdown,
- giảm useless work,
- giúp overload recovery tốt hơn.

### Costs / Risks

- phải propagate xuyên nhiều layer,
- partial work có thể đã xảy ra trước cancellation,
- business operation không idempotent cần thiết kế transaction boundary cẩn thận.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu token là tín hiệu cooperative cancellation, không phải thread abort.

### Middle

Biết truyền token vào EF Core, `HttpClient`, stream và background operations.

### Senior

Hiểu interaction giữa cancellation, timeout, transaction, partial side effects và shutdown.

### Technical Lead / Architect

Quyết định operation nào phải cancel theo request lifecycle, operation nào phải detach sang durable background processing để không bị user disconnect làm mất công việc quan trọng.

## 11. Key takeaway

- `CancellationToken` chỉ hữu ích nếu được propagate tới I/O thực sự.
- Cancellation giảm wasted work nhưng không thay timeout, idempotency hay transaction design.
- Long-running business work quan trọng thường nên tách khỏi request lifecycle.

# 2. ASP.NET Core `ProblemDetails`: chuẩn hóa error contract mà không làm rò rỉ implementation detail

## 1. What is it?

`ProblemDetails` là structured HTTP error representation dùng các field chuẩn như `type`, `title`, `status`, `detail`, `instance` và có thể thêm extension fields.

Mental model:

```text
Exception / validation / domain failure
                |
                v
     Error mapping boundary
                |
                v
        ProblemDetails JSON
```

Nó biến lỗi thành API contract có cấu trúc thay vì trả string tùy ý.

## 2. Why does it exist?

Client cần biết lỗi theo cách ổn định để:

- hiển thị đúng UX,
- quyết định retry hay không,
- phân biệt validation, not-found, conflict, authorization,
- correlation với telemetry.

Nếu mỗi endpoint tự tạo format riêng, frontend và integration clients phải chứa rất nhiều branch logic khó duy trì.

## 3. How does it work?

ASP.NET Core có thể map exception và status response sang `ProblemDetails`. Application nên tạo một error taxonomy ổn định:

```text
Domain validation -> 400
Resource missing  -> 404
Concurrency conflict -> 409
Unauthorized      -> 401
Forbidden         -> 403
Unexpected fault  -> 500
```

Điểm quan trọng: HTTP status phản ánh semantics; `ProblemDetails` cung cấp machine-readable context.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();

app.UseExceptionHandler(exceptionHandlerApp =>
{
    exceptionHandlerApp.Run(async context =>
    {
        var feature = context.Features.Get<IExceptionHandlerFeature>();
        var exception = feature?.Error;

        context.Response.StatusCode = exception switch
        {
            KeyNotFoundException => StatusCodes.Status404NotFound,
            ConcurrencyException => StatusCodes.Status409Conflict,
            _ => StatusCodes.Status500InternalServerError
        };

        await Results.Problem(
            statusCode: context.Response.StatusCode,
            title: "Request processing failed",
            extensions: new Dictionary<string, object?>
            {
                ["traceId"] = context.TraceIdentifier
            }).ExecuteAsync(context);
    });
});
```

Không nên đưa stack trace hoặc connection string vào response Production.

## 5. Real production scenario

Frontend checkout cần phân biệt:

- coupon không hợp lệ,
- inventory conflict,
- payment provider timeout,
- server fault.

Nếu backend luôn trả `500 { message: "Something went wrong" }`, frontend không thể đưa ra hành vi phù hợp. `ProblemDetails` cho phép client xử lý dựa trên `status` + stable error code.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend hiển thị generic error dù backend log cho thấy domain conflict.

**Evidence** → API luôn map exception thành 500.

**Hypothesis** → error mapping boundary quá thô.

**Diagnosis** → kiểm tra exception handler và domain-to-HTTP mapping.

**Fix** → tạo taxonomy rõ ràng, chỉ map known errors thành 4xx; unknown errors vẫn 500.

**Verification** → contract tests cho các lỗi quan trọng.

## 7. Common mistakes

- Dùng `200 OK` rồi đặt `success=false` trong body.
- Expose stack trace hoặc internal exception message.
- Dùng `400` cho mọi loại lỗi.
- Dùng error message text làm machine-readable contract.
- Để mỗi controller định nghĩa error schema khác nhau.

## 8. Alternatives

Có thể dùng custom error envelope, nhưng nếu không có lý do đặc biệt, `ProblemDetails` giảm chi phí thiết kế protocol riêng.

GraphQL hoặc gRPC có error semantics khác và không nên áp HTTP REST mapping một cách máy móc.

## 9. Trade-offs

### Advantages

- contract ổn định,
- hỗ trợ tooling tốt,
- dễ correlation với trace,
- giảm coupling frontend với exception internals.

### Costs / Risks

- cần taxonomy nhất quán,
- mapping domain failure sang HTTP semantics đòi hỏi judgment,
- nếu extension fields phát triển vô kiểm soát, schema vẫn có thể trở nên hỗn loạn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác nhau giữa 4xx và 5xx.

### Middle

Biết tạo centralized exception handling và validation responses.

### Senior

Thiết kế stable error codes, backward compatibility và telemetry correlation.

### Technical Lead / Architect

Định nghĩa enterprise-wide error contract vừa đủ thống nhất nhưng không ép mọi bounded context dùng cùng business error vocabulary.

## 11. Key takeaway

- Error response là API contract, không phải log message cho developer.
- `ProblemDetails` tốt nhất khi đi cùng HTTP semantics chính xác và stable error codes.
- Unknown server faults không được biến thành 4xx chỉ để "response đẹp hơn".

# 3. SQL keyset pagination: tránh chi phí và tính không ổn định của `OFFSET`

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên giá trị sort key cuối cùng của trang trước thay vì nói "bỏ qua N rows".

```text
OFFSET pagination:
ORDER BY CreatedAt DESC
OFFSET 100000 ROWS FETCH NEXT 20 ROWS

Keyset pagination:
WHERE CreatedAt < @lastCreatedAt
ORDER BY CreatedAt DESC
FETCH NEXT 20 ROWS
```

## 2. Why does it exist?

`OFFSET` phải tìm và bỏ qua nhiều row trước khi trả kết quả. Khi page sâu, database vẫn phải xử lý số lượng row lớn.

Ngoài hiệu năng, dữ liệu thay đổi giữa các request có thể làm user thấy duplicate hoặc missing row.

## 3. How does it work?

Database dùng predicate trên ordered key để seek gần trực tiếp vào vị trí tiếp theo.

Nếu sort key không unique, cần tie-breaker:

```sql
WHERE CreatedAt < @createdAt
   OR (CreatedAt = @createdAt AND Id < @id)
ORDER BY CreatedAt DESC, Id DESC
```

Index phù hợp:

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON Orders (CreatedAt DESC, Id DESC);
```

Query → index seek/range scan → ít I/O hơn page sâu kiểu `OFFSET`.

## 4. Practical implementation

```sql
SELECT TOP (@pageSize)
    Id, CreatedAt, CustomerId, Total
FROM Orders
WHERE
    CreatedAt < @cursorCreatedAt
    OR (CreatedAt = @cursorCreatedAt AND Id < @cursorId)
ORDER BY CreatedAt DESC, Id DESC;
```

API có thể encode cursor thành opaque token thay vì expose raw fields.

## 5. Real production scenario

Order history có vài chục triệu records. Page 1 nhanh, nhưng page 5000 với `OFFSET` bắt đầu mất vài giây.

Keyset pagination biến traversal thành seek-based access pattern. Nó đặc biệt phù hợp infinite scroll hoặc next/previous navigation.

## 6. Failure scenario & troubleshooting

**Symptom** → page sâu chậm, logical reads tăng mạnh.

**Evidence** → execution plan cho thấy scan/range processing lớn trước khi trả 20 rows.

**Hypothesis** → `OFFSET` cost tăng theo depth.

**Diagnosis** → kiểm tra actual plan và logical reads.

**Fix** → keyset pagination + deterministic ordering + composite index phù hợp.

**Verification** → so p95 và logical reads ở page sâu.

## 7. Common mistakes

- Chỉ dùng `CreatedAt` dù nhiều row có cùng timestamp.
- Không tạo deterministic order.
- Encode cursor nhưng không validate malformed cursor.
- Dùng keyset khi UI bắt buộc jump trực tiếp tới page 937.
- Thêm index quá rộng chỉ để cover mọi field.

## 8. Alternatives

`OFFSET` vẫn hợp lý cho dataset nhỏ hoặc admin UI cần random page access.

Search engine có `search_after` concept tương tự keyset.

Một số use case cần snapshot/export thay vì live pagination.

## 9. Trade-offs

### Advantages

- ổn định hơn khi dữ liệu thay đổi,
- hiệu năng tốt ở page sâu,
- thường giảm I/O đáng kể.

### Costs / Risks

- khó jump tới page bất kỳ,
- cursor logic phức tạp hơn,
- sort key và index phải được thiết kế cẩn thận.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `OFFSET` không miễn phí.

### Middle

Biết implement composite cursor và index phù hợp.

### Senior

Đọc execution plan, logical reads và đánh giá consistency của pagination dưới concurrent writes.

### Technical Lead / Architect

Chọn pagination model theo UX requirement, data size và query access pattern thay vì mặc định "page/pageSize".

## 11. Key takeaway

- Page sâu với `OFFSET` thường là vấn đề access pattern, không chỉ là thiếu index.
- Keyset cần deterministic ordering.
- Pagination contract nên được chọn cùng UX và data-change behavior.

# 4. MongoDB embedding vs referencing: model theo access pattern và consistency boundary

## 1. What is it?

Embedding đặt dữ liệu con trực tiếp trong document cha. Referencing lưu document riêng và liên kết bằng identifier.

```text
Embedding:
Order { items: [...] }

Referencing:
Order { customerId }
Customer { ... }
```

Đây không chỉ là câu hỏi "NoSQL có join hay không" mà là quyết định về ownership, read pattern, update pattern và consistency boundary.

## 2. Why does it exist?

Document database tối ưu mạnh cho việc đọc/ghi một aggregate-like document. Nhưng nếu embed mọi thứ, document phình to, duplication tăng và update fan-out xuất hiện.

Nếu reference mọi thứ như relational schema, application lại phải ghép nhiều documents và đánh mất lợi thế document locality.

## 3. How does it work?

Embedding phù hợp khi dữ liệu:

- được đọc cùng nhau,
- có lifecycle gần nhau,
- kích thước bị giới hạn,
- ít update độc lập.

Referencing phù hợp khi entity:

- được chia sẻ bởi nhiều aggregate,
- update độc lập thường xuyên,
- có cardinality lớn hoặc unbounded,
- cần query riêng.

## 4. Practical implementation

```json
{
  "_id": "order-123",
  "customerId": "cust-88",
  "shippingAddress": {
    "line1": "12 Main St",
    "city": "Hanoi"
  },
  "items": [
    { "sku": "A1", "name": "Keyboard", "price": 120 }
  ]
}
```

`shippingAddress` được embed như snapshot lịch sử. `customerId` reference customer master data.

Điều này tránh việc đổi địa chỉ hiện tại của customer làm thay đổi lịch sử đơn hàng.

## 5. Real production scenario

E-commerce order cần preserve product name và price tại thời điểm mua. Nếu chỉ reference product hiện tại, catalog update có thể làm historical order hiển thị sai.

Một phần duplication trong document ở đây là intentional denormalization để bảo toàn business history.

## 6. Failure scenario & troubleshooting

**Symptom** → update profile của customer cần update hàng trăm nghìn order documents.

**Evidence** → batch write lớn và write amplification cao.

**Hypothesis** → data được embed nhưng thực ra có independent lifecycle.

**Diagnosis** → xem access/update patterns và ownership semantics.

**Fix** → chỉ embed snapshot fields thực sự cần lịch sử; reference mutable shared data.

**Verification** → theo dõi write volume và query complexity sau redesign.

## 7. Common mistakes

- Embed array tăng không giới hạn.
- Reference mọi thứ vì quen relational modeling.
- Duplicate dữ liệu nhưng không xác định source of truth.
- Không tính document size limit.
- Không index fields phù hợp với query pattern.

## 8. Alternatives

Relational database có thể đơn giản hơn nếu domain phụ thuộc nhiều join và transactional constraints liên entity.

Cosmos DB cũng dùng document/partition modeling nhưng thêm partition-key và RU considerations.

## 9. Trade-offs

### Advantages của embedding

- locality tốt,
- ít round trips,
- atomic update trong document dễ hơn.

### Costs / Risks

- duplication,
- document growth,
- write amplification.

### Advantages của referencing

- shared data rõ ràng,
- update độc lập.

### Costs / Risks

- thêm queries hoặc `$lookup`,
- consistency giữa documents phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu document modeling khác table normalization.

### Middle

Biết chọn embed/reference theo read-write pattern.

### Senior

Đánh giá bounded growth, atomicity, duplication và query cost.

### Technical Lead / Architect

Quyết định database model dựa trên business consistency boundary và operational scale, không dựa trên slogan "NoSQL linh hoạt schema".

## 11. Key takeaway

- Embedding và referencing là quyết định ownership + access pattern.
- Duplication có thể đúng nếu đó là snapshot có chủ đích.
- Unbounded child collections thường là tín hiệu cần reference hoặc model khác.

# 5. Bounded Context + Anti-Corruption Layer: bảo vệ business model khỏi external model

## 1. What is it?

`Bounded Context` là ranh giới nơi một domain model và ngôn ngữ nghiệp vụ có nghĩa nhất quán.

`Anti-Corruption Layer` (ACL) là translation boundary giữa model của mình và model bên ngoài.

```text
Internal Domain
      |
      v
Anti-Corruption Layer
      |
      v
Legacy ERP / Partner API
```

## 2. Why does it exist?

External systems thường có terminology, status code và lifecycle khác hệ thống của bạn.

Nếu internal code trực tiếp dùng DTO/status từ vendor, external semantics lan khắp application. Sau đó một thay đổi ở partner API trở thành refactor toàn codebase.

## 3. How does it work?

ACL nhận external contract rồi translate thành internal concepts.

Ví dụ partner trả:

```json
{ "state": "A", "priorityCode": 7 }
```

Internal domain không cần biết `A` nghĩa gì. Adapter map nó sang `OrderStatus.Approved`.

Dependency direction nên là:

```text
Domain <- Application <- Integration Adapter -> External API
```

Domain không phụ thuộc vendor SDK.

## 4. Practical implementation

```csharp
public sealed class ErpOrderTranslator
{
    public OrderSnapshot Translate(ErpOrderDto dto)
    {
        var status = dto.State switch
        {
            "A" => OrderStatus.Approved,
            "C" => OrderStatus.Cancelled,
            _ => OrderStatus.Pending
        };

        return new OrderSnapshot(dto.OrderNumber, status, dto.TotalAmount);
    }
}
```

Application layer gọi integration client rồi nhận internal model thay vì raw ERP DTO.

## 5. Real production scenario

Một CRM gọi field `Account`, hệ thống nội bộ gọi `Customer`, billing system lại gọi `Party`.

Nếu cùng một class dùng chung mọi nơi, semantics bị trộn. ACL giúp mỗi bounded context giữ language riêng và translate ở boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → vendor đổi enum/status và hàng chục services fail compile hoặc runtime.

**Evidence** → vendor DTO xuất hiện ở domain/application methods.

**Hypothesis** → boundary bị xuyên thủng.

**Diagnosis** → dependency scan cho thấy vendor package referenced từ nhiều projects.

**Fix** → isolate integration adapter và internal contract.

**Verification** → thay fixture vendor schema, phần lớn code nội bộ không cần sửa.

## 7. Common mistakes

- Tạo "shared model" chứa union của mọi hệ thống.
- Gọi mọi mapper là ACL dù không có semantic translation.
- Đặt vendor SDK vào Domain project.
- Mirror toàn external schema dù application chỉ cần 5 fields.
- Overengineer bounded contexts cho CRUD nhỏ.

## 8. Alternatives

Với integration rất đơn giản và ổn định, adapter mỏng có thể đủ.

Không phải hệ thống nào cũng cần full DDD. Layered architecture với explicit integration boundary vẫn có thể giải quyết cùng coupling problem.

## 9. Trade-offs

### Advantages

# 6. Azure Key Vault + Managed Identity: bỏ secrets khỏi application configuration

## 1. What is it?

`Azure Key Vault` lưu secrets, keys và certificates. `Managed Identity` cho Azure workload nhận identity do platform quản lý để authenticate mà không cần lưu credential trong code/config.

```text
App Service / Function
      |
      | Managed Identity token
      v
Microsoft Entra ID
      |
      v
Azure Key Vault
```

## 2. Why does it exist?

Nếu application secret nằm trong `appsettings.json`, pipeline variables hoặc environment variables lâu dài, bạn phải giải quyết:

- ai được đọc,
- rotation,
- leakage qua logs/dumps,
- secret distribution,
- revocation.

Managed Identity loại bỏ một lớp credential bootstrap.

## 3. How does it work?

Azure resource được gán identity. Application dùng Azure Identity SDK để lấy token cho Key Vault. Key Vault kiểm tra RBAC/Access Policy rồi trả secret nếu authorized.

Application không cần password để chứng minh nó là chính nó.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("PaymentApiKey");
var apiKey = secret.Value;
```

Trong local development, `DefaultAzureCredential` có thể dùng developer identity; trong Azure, nó dùng Managed Identity.

## 5. Real production scenario

App Service gọi third-party payment API. API key được lưu trong Key Vault. App Service chỉ có quyền `secrets/get` cho đúng vault.

Khi rotate key, team cập nhật Key Vault thay vì rebuild image chứa secret mới.

## 6. Failure scenario & troubleshooting

**Symptom** → app deploy thành công nhưng startup fail với `403 Forbidden` từ Key Vault.

**Evidence** → identity token có nhưng Key Vault audit log từ chối authorization.

**Hypothesis** → RBAC chưa được cấp hoặc cấp sai principal/vault.

**Diagnosis** → xác nhận Managed Identity object ID, role assignment và network access.

**Fix** → cấp minimum required role; nếu vault dùng Private Endpoint, kiểm tra DNS/VNet path.

**Verification** → application lấy secret và audit log ghi request thành công.

## 7. Common mistakes

- Dùng Key Vault nhưng vẫn hard-code client secret để access vault.
- Cấp quyền quá rộng như Owner/Contributor.
- Fetch secret cho mọi request thay vì cache phù hợp.
- Không thiết kế rotation behavior.
- Quên network restriction khi bật Private Endpoint.

## 8. Alternatives

Kubernetes Secrets đơn giản hơn trong cluster nhưng vẫn cần bảo vệ/rotation.

Environment variables có thể đủ cho local/dev hoặc hệ thống nhỏ nếu pipeline secret management tốt.

Key Vault phù hợp khi cần centralized governance, audit và rotation.

## 9. Trade-offs

### Advantages

- giảm secret sprawl,
- audit tốt,
- rotation dễ hơn,
- least privilege rõ hơn.

### Costs / Risks

- thêm external dependency,
- startup có thể phụ thuộc network/identity,
- private networking và RBAC tăng operational complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu secret không nên nằm trong source code.

### Middle

Biết cấu hình Key Vault và Managed Identity.

### Senior

Hiểu RBAC, rotation, caching, network path và failure mode.

### Technical Lead / Architect

Quyết định secret-management boundary, fallback behavior, startup dependency và governance model cho nhiều applications/environments.

## 11. Key takeaway

- Key Vault giải quyết secret storage; Managed Identity giải quyết bootstrap credential.
- Least privilege và network path quan trọng ngang việc lưu secret an toàn.
- Secret retrieval cũng là remote dependency và cần vận hành như một dependency thật.

# 7. Chẩn đoán database connection pool exhaustion

## 1. What is it?

Connection pooling tái sử dụng physical database connections thay vì mở handshake mới cho mỗi query.

Pool exhaustion xảy ra khi application cần connection nhưng pool không còn connection available trước timeout.

```text
Request -> acquire connection -> query -> return connection
                     |
                     +-- pool empty -> wait -> timeout
```

## 2. Why does it exist?

Database connections đắt và hữu hạn. Pool giúp giảm connection setup cost, nhưng chính giới hạn này tạo backpressure khi queries quá chậm hoặc connections không được trả về đúng lúc.

## 3. How does it work?

Với EF Core, `DbContext` thường mở connection khi query/transaction cần và đóng sau khi operation hoàn tất. ADO.NET pool giữ physical connection để tái sử dụng.

Pool exhaustion thường do một trong các nhóm nguyên nhân:

- query/transaction giữ connection quá lâu,
- traffic concurrency vượt capacity,
- connection leak,
- database bị blocking,
- downstream retry storm tăng concurrent queries.

## 4. Practical implementation

Không giữ transaction qua remote call:

```csharp
await using var transaction = await db.Database.BeginTransactionAsync(ct);

await db.SaveChangesAsync(ct);
await transaction.CommitAsync(ct);
```

Tránh:

```text
Begin DB transaction
 -> call external API 5 seconds
 -> write DB
 -> commit
```

Remote call kéo dài thời gian giữ connection/locks.

## 5. Real production scenario

Sau một deployment, p95 SQL tăng từ 40 ms lên 3 s. Traffic không đổi nhưng mỗi request giữ connection lâu hơn khoảng 75 lần. Pool nhanh chóng cạn và request mới timeout khi chờ connection.

Root cause có thể là missing index hoặc bad execution plan, không phải pool size nhỏ.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout kiểu "Timeout expired prior to obtaining a connection from the pool".

**Evidence** → active connections đạt gần max pool size; query latency và blocking tăng.

**Hypothesis** → connections bị giữ quá lâu.

**Diagnosis** → correlate application traces, SQL waits, active sessions, slow queries và transaction duration.

**Fix** → sửa root cause: query, lock contention, transaction scope hoặc leak. Chỉ tăng pool size sau khi đo database capacity.

**Verification** → wait time để acquire connection giảm, pool usage ổn định, p95/p99 query cải thiện.

## 7. Common mistakes

- Tăng `Max Pool Size` ngay lập tức.
- Chỉ nhìn CPU database và bỏ qua lock waits.
- Giữ transaction quanh HTTP call.
- Retry connection timeout hàng loạt gây retry storm.
- Tạo nhiều connection strings hơi khác nhau và vô tình tạo nhiều pools.

## 8. Alternatives

Nếu workload thực sự cần concurrency cao hơn, có thể scale database, shard/partition workload hoặc chuyển một số work sang async queue.

Nhưng pool tuning không thay cho query optimization và concurrency control.

## 9. Trade-offs

### Pool lớn hơn

Tăng concurrency tiềm năng nhưng có thể đẩy database vào overload nhanh hơn.

### Pool nhỏ hơn

Tạo backpressure sớm hơn nhưng tăng khả năng request chờ connection.

Đây là capacity decision, không phải magic number.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu connection phải được trả về pool.

### Middle

Biết dùng `DbContext` lifetime đúng và tránh transaction dài.

### Senior

Phân tích pool metrics cùng query latency, locks, retries và request concurrency.

### Technical Lead / Architect

Thiết kế capacity model: maximum concurrent DB work, backpressure, timeout và overload behavior của toàn service.

## 11. Key takeaway

- Pool exhaustion thường là symptom của latency/concurrency problem phía dưới.
- Tăng pool size có thể làm database chết nhanh hơn.
- Điều tra phải nối request latency → pool wait → SQL latency/locks → root cause.

# 8. Integration testing với Testcontainers: dùng infrastructure thật có kiểm soát

## 1. What is it?

Testcontainers khởi tạo dependency thật như SQL Server, PostgreSQL, Redis hoặc message broker trong container cho test run.

```text
Test suite
  -> start container
  -> apply schema
  -> run tests
  -> destroy container
```

Nó nằm giữa unit test thuần mock và shared integration environment.

## 2. Why does it exist?

Mock repository không kiểm tra:

- LINQ có translate thật không,
- SQL constraint có hoạt động không,
- transaction/isolation behavior,
- case sensitivity/collation,
- migration compatibility.

Integration test cần dependency có behavior gần Production hơn nhưng vẫn reproducible.

## 3. How does it work?

Test fixture start container, lấy dynamic connection string, chạy migrations/seed rồi inject vào application-under-test.

Isolation có thể theo test class, test collection hoặc toàn test suite tùy cost.

## 4. Practical implementation

Ví dụ ý tưởng với .NET:

```csharp
private readonly PostgreSqlContainer _db =
    new PostgreSqlBuilder()
        .WithDatabase("app")
        .WithUsername("postgres")
        .WithPassword("postgres")
        .Build();

public async Task InitializeAsync()
{
    await _db.StartAsync();
}
```

Sau đó cấu hình `DbContext` dùng `_db.GetConnectionString()` và apply migration.

## 5. Real production scenario

Một LINQ query chạy qua mocked repository nhưng fail Production vì EF Core không translate một expression. Testcontainers integration test sẽ execute qua provider thật và bắt lỗi trước deploy.

## 6. Failure scenario & troubleshooting

**Symptom** → test suite flaky hoặc rất chậm.

**Evidence** → container start per test, shared mutable test data, port conflicts.

**Hypothesis** → test isolation strategy không phù hợp.

**Diagnosis** → đo startup cost, xác định state leakage và parallel execution behavior.

**Fix** → reuse container theo fixture scope hợp lý, reset database state deterministic, dùng random resources khi cần.

**Verification** → chạy test lặp nhiều lần và song song trong CI.

## 7. Common mistakes

- Dùng SQLite in-memory để giả SQL Server rồi tin behavior giống nhau.
- Khởi tạo container cho từng assertion nhỏ.
- Không cleanup state.
- Test quá nhiều implementation detail.
- Dùng real cloud dependency cho mọi integration test làm test chậm và tốn chi phí.

## 8. Alternatives

- mocks/fakes cho unit tests nhanh,
- LocalStack/Azurite cho một số cloud abstractions,
- dedicated shared test environment cho E2E broader flows.

Testcontainers mạnh nhất khi dependency có container image và behavior local đủ sát Production.

## 9. Trade-offs

### Advantages

- realism cao hơn mock,
- reproducible,
- cô lập khỏi shared environment,
- bắt migration/query issues tốt.

### Costs / Risks

- test chậm hơn,
- cần Docker/container runtime,
- CI resource usage cao hơn,
- vẫn không thay thế full production-like E2E.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu unit test và integration test bảo vệ các risk khác nhau.

### Middle

Biết tạo fixture, seed data và reset state.

### Senior

Chọn đúng layer để test thật, tránh over-mocking và quản lý flakiness.

### Technical Lead / Architect

Thiết kế test strategy theo business risk, CI cost và fidelity thay vì chạy mọi test ở cùng một mức realism.

## 11. Key takeaway

- Mock không mô phỏng được database semantics thật.
- Testcontainers là công cụ cân bằng realism và reproducibility.
- Test architecture tốt cần mix unit, integration, contract và E2E tests.

# 9. Expand–Migrate–Contract cho database deployment

## 1. What is it?

Đây là chiến lược thay đổi schema theo nhiều bước backward-compatible thay vì deploy một breaking schema change ngay lập tức.

```text
Expand  -> thêm schema mới nhưng giữ cũ
Migrate -> application/data chuyển dần
Contract -> xóa schema cũ sau khi không còn consumer
```

## 2. Why does it exist?

Trong rolling deployment, version cũ và mới của application có thể cùng chạy. Nếu migration rename/drop column ngay trước khi tất cả instances upgrade, version cũ sẽ fail.

Database thường là shared contract giữa nhiều deployment versions.

## 3. How does it work?

Ví dụ rename `FullName` thành `DisplayName`:

1. Add `DisplayName`, giữ `FullName`.
2. New app ghi cả hai hoặc có compatibility layer.
3. Backfill dữ liệu cũ.
4. Chuyển reads sang `DisplayName`.
5. Đảm bảo không còn old version/consumer.
6. Drop `FullName` ở release sau.

## 4. Practical implementation

Migration đầu:

```sql
ALTER TABLE Users ADD DisplayName nvarchar(200) NULL;
```

Backfill:

```sql
UPDATE Users
SET DisplayName = FullName
WHERE DisplayName IS NULL;
```

Sau khi cutover và verify:

```sql
ALTER TABLE Users ALTER COLUMN DisplayName nvarchar(200) NOT NULL;
-- drop old column chỉ ở release sau
```

## 5. Real production scenario

App Service deployment slot swap chạy version mới trong khi old slot vẫn có thể nhận traffic trong rollback window.

Nếu migration drop column cũ ngay, rollback application không còn khả năng chạy. Expand–Contract giữ rollback path.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment mới thành công nhưng rollback cũ fail ngay khi query database.

**Evidence** → migration đã drop/rename column old version còn sử dụng.

**Hypothesis** → schema change không backward-compatible.

**Diagnosis** → so EF migrations với supported deployment overlap window.

**Fix** → tách migration thành nhiều release; never contract trước khi old consumers biến mất.

**Verification** → compatibility test cả app N và N-1 với schema expanded.

## 7. Common mistakes

- Rename column trong một migration rồi deploy rolling.
- Backfill millions of rows trong blocking migration transaction.
- Add non-null column với expensive default trên bảng lớn mà không đo lock behavior.
- Xóa old schema ngay sau code merge.
- Không biết còn background job hoặc reporting consumer dùng field cũ.

## 8. Alternatives

Maintenance window + coordinated downtime có thể đơn giản hơn nếu business cho phép.

Với hệ thống nhỏ, zero-downtime ceremony có thể không đáng chi phí. Complexity phải theo availability requirement.

## 9. Trade-offs

### Advantages

- giảm deployment risk,
- hỗ trợ rolling deployment/rollback,
- tách schema risk khỏi application release.

### Costs / Risks

- tạm thời có duplicate fields/logic,
- migration kéo dài nhiều releases,
- cần tracking consumer ownership tốt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu database migration có thể break app đang chạy.

### Middle

Biết viết additive migration và backfill an toàn.

### Senior

Thiết kế compatibility window, data migration, lock impact và rollback.

### Technical Lead / Architect

Quyết định khi nào cần zero-downtime schema evolution và khi nào controlled downtime đơn giản, rẻ hơn và đáng tin hơn.

## 11. Key takeaway

- Database schema là deployment contract, không chỉ là implementation detail của version hiện tại.
- Additive change trước, destructive change sau.
- Rollback chỉ thực sự tồn tại nếu schema vẫn tương thích.

# 10. LLM Tool Calling với deterministic guardrails

## 1. What is it?

Tool Calling cho phép model đề xuất structured action như:

```json
{
  "tool": "create_invoice",
  "arguments": {
    "customerId": "C123",
    "amount": 1000
  }
}
```

Nhưng model không nên trực tiếp sở hữu security-critical hoặc financial correctness decision.

Mental model:

```text
User intent
   -> LLM proposes action
   -> deterministic validation/policy
   -> authorized tool execution
   -> result
   -> LLM explains result
```

## 2. Why does it exist?

LLM giỏi hiểu ngôn ngữ và chọn intent nhưng output có tính probabilistic. Business rules, permissions, money calculation và state transition thường yêu cầu deterministic behavior.

Tool Calling tạo ranh giới giữa reasoning linh hoạt và execution kiểm soát.

## 3. How does it work?

Application gửi schema các tools cho model. Model trả structured arguments. Application phải:

1. validate schema,
2. authenticate user,
3. authorize action,
4. re-check business invariants,
5. enforce limits,
6. execute deterministic code,
7. audit result.

Model proposal không phải authorization grant.

## 4. Practical implementation

Pseudo-realistic C# boundary:

```csharp
public async Task<InvoiceResult> CreateInvoiceAsync(
    CreateInvoiceArgs args,
    UserContext user,
    CancellationToken ct)
{
    if (!user.CanCreateInvoices)
        throw new ForbiddenException();

    if (args.Amount <= 0 || args.Amount > user.InvoiceLimit)
        throw new ValidationException("Amount outside allowed range.");

    return await invoiceService.CreateAsync(args, ct);
}
```

Model chỉ quyết định rằng user có vẻ muốn tạo invoice; code vẫn kiểm tra quyền và invariant.

## 5. Real production scenario

AI assistant nội bộ cho phép nhân viên tra customer, tạo ticket và draft refund request.

Model có thể hiểu câu "refund đơn này" nhưng actual refund cần policy engine kiểm tra amount, order state và user role trước khi gọi payment provider.

## 6. Failure scenario & troubleshooting

**Symptom** → model gọi tool nguy hiểm với argument ngoài ý định user.

**Evidence** → audit log cho thấy tool call hợp schema nhưng vi phạm business policy.

**Hypothesis** → application xem structured output như trusted command.

**Diagnosis** → tool handler thiếu authorization/invariant validation.

**Fix** → deterministic guardrails, confirmation cho high-impact action, idempotency và limits.

**Verification** → adversarial tests với prompt injection, malformed arguments và unauthorized scenarios.

## 7. Common mistakes

- Tin rằng JSON schema = business validation.
- Đưa API key/secrets vào prompt.
- Cho model quyền chọn arbitrary URL rồi fetch không kiểm soát, tạo SSRF risk.
- Không log tool execution/audit context.
- Cho model tính tiền/tax rồi ghi thẳng kết quả vào financial system.
- Không có idempotency cho tool gây side effect.

## 8. Alternatives

Với workflow deterministic rõ ràng, rules engine hoặc normal UI form có thể đơn giản hơn AI agent.

RAG phù hợp khi cần retrieve knowledge; Tool Calling phù hợp khi cần action. Hai thứ giải quyết bài toán khác nhau.

## 9. Trade-offs

### Advantages

- natural-language interface,
- flexible intent understanding,
- có thể orchestration nhiều tools.

### Costs / Risks

- nondeterminism,
- prompt injection,
- extra latency/cost,
- audit và authorization phức tạp hơn,
- tool misuse nếu boundary yếu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu model output là untrusted input.

### Middle

Biết validate structured arguments và handle retries/timeouts.

### Senior

Thiết kế authorization, idempotency, audit, prompt-injection defense và deterministic business invariants.

### Technical Lead / Architect

Quyết định workflow nào nên có LLM trong control loop và workflow nào bắt buộc giữ hoàn toàn deterministic; xác định blast radius nếu model chọn sai tool.

## 11. Key takeaway

- Tool Calling không biến LLM thành trusted backend service.
- Authentication, authorization, invariants và financial correctness phải nằm trong deterministic application logic.
- AI nên đề xuất hoặc điều phối; hệ thống vẫn phải kiểm soát execution boundary.
