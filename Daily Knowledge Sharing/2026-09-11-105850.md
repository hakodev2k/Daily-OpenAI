# 1. CLR Tiered Compilation + Dynamic PGO: vì sao cùng một method có thể được JIT nhiều lần để đổi startup speed lấy steady-state performance

## 1. What is it?

Trong .NET, source code C# được compile thành IL, sau đó CLR JIT compiler chuyển IL thành native machine code khi method được thực thi. Với Tiered Compilation, runtime không nhất thiết tối ưu method tối đa ngay lần đầu. Method có thể được compile nhanh ở tier ban đầu để giảm startup latency, rồi được recompile ở tier tối ưu hơn khi runtime xác định method đó thực sự “hot”.

Dynamic PGO (Profile-Guided Optimization) bổ sung runtime profile: branch nào thường chạy, type nào thường xuất hiện, call target nào phổ biến. JIT dùng dữ liệu thực tế đó để tạo machine code phù hợp workload hiện tại.

Mental model:

```text
IL
 -> Tier 0: compile nhanh, optimization hạn chế
 -> runtime quan sát execution
 -> hot method
 -> Tier 1 + profile data
 -> native code tối ưu hơn
```

## 2. Why does it exist?

Nếu JIT tối ưu mọi method mạnh ngay từ đầu, application startup sẽ tốn CPU và thời gian cho cả những method hiếm khi chạy. Nếu compile quá đơn giản, startup nhanh nhưng throughput dài hạn kém.

Tiered Compilation giải quyết tension giữa:

- startup latency
- JIT CPU cost
- steady-state throughput
- code quality trên hot path

Đây là ví dụ điển hình cho việc runtime tối ưu theo evidence thay vì giả định mọi code đều quan trọng như nhau.

## 3. How does it work?

Khi process khởi động, method được gọi lần đầu có thể nhận Tier 0 code. Runtime theo dõi invocation count và profile behavior. Method đủ “hot” được queue cho recompilation.

Dynamic PGO có thể cho phép JIT:

- devirtualize một call nếu runtime thấy một concrete type áp đảo
- inline branch phổ biến
- tối ưu layout của hot/cold paths
- loại bỏ một số check trong path thường gặp khi guard vẫn đảm bảo correctness

Ví dụ interface call:

```csharp
public decimal Calculate(IPricePolicy policy, Order order)
    => policy.Calculate(order);
```

Statically, JIT thấy interface dispatch. Nếu runtime profile cho thấy 99% call dùng `DefaultPricePolicy`, Dynamic PGO có thể optimize common case tốt hơn nhưng vẫn giữ fallback path cho type khác.

## 4. Practical implementation

Phần lớn application không cần code đặc biệt để “bật” Tiered Compilation. Điều quan trọng là benchmark đúng lifecycle.

Ví dụ BenchmarkDotNet:

```csharp
[MemoryDiagnoser]
public class PricingBenchmark
{
    private readonly PriceCalculator _calculator = new();
    private readonly Order _order = Order.Sample();

    [Benchmark]
    public decimal Calculate()
        => _calculator.Calculate(_order);
}
```

Không nên dùng `Stopwatch` chạy một lần rồi kết luận performance vì kết quả có thể đo cả JIT warm-up thay vì steady-state code.

Khi profiling Production, nên phân biệt:

```text
cold start latency
vs
steady-state latency
```

Hai metric có thể bị chi phối bởi hai cơ chế khác nhau.

## 5. Real production scenario

Một ASP.NET Core API deploy lên Azure App Service. Sau recycle, vài request đầu có latency cao hơn bình thường. Sau 1–2 phút, throughput ổn định và p95 giảm.

Nếu team chỉ nhìn trace lúc cold start, họ có thể nghĩ database hoặc dependency chậm. Thực tế startup còn gồm assembly loading, JIT, DI graph creation, connection establishment và cache warm-up.

Tiered Compilation giúp steady-state tốt hơn, nhưng không biến cold start thành zero-cost.

## 6. Failure scenario & troubleshooting

**Symptom** → request đầu sau deployment/recycle chậm, sau đó ổn định.

**Evidence** → database latency bình thường, CPU có burst ngắn, method-level profiler cho thấy JIT/runtime activity cao lúc đầu.

**Hypothesis** → cold-start cost gồm JIT và warm-up.

**Diagnosis** → đo riêng first-request latency, warm-up window và steady-state; dùng `dotnet-trace`, EventPipe hoặc profiler để quan sát runtime events.

**Fix** → chỉ tối ưu nếu cold-start SLA thực sự quan trọng: pre-warm deployment slot, warm critical endpoints, giảm startup work, tránh reflection/scanning quá mức, cân nhắc ReadyToRun khi phù hợp.

**Verification** → so startup p95 và steady-state p95 trước/sau thay đổi, không trộn hai phase.

## 7. Common mistakes

- Nghĩ JIT chỉ compile method đúng một lần.
- Benchmark quá ngắn rồi đo chủ yếu Tier 0/JIT warm-up.
- Cố micro-optimize code khi bottleneck thực sự là SQL hoặc network.
- Bật/tắt runtime knobs mà không có benchmark đại diện workload.
- Nhầm ReadyToRun với “không còn JIT”. Runtime vẫn có thể JIT/re-JIT để tối ưu.

## 8. Alternatives

ReadyToRun giúp giảm một phần JIT cost bằng native code được tạo trước, phù hợp khi startup quan trọng. Native AOT đi xa hơn và thay đổi deployment/runtime model đáng kể, nhưng có compatibility trade-offs với reflection/dynamic code.

Tiered JIT phù hợp general-purpose server application vì cân bằng startup và steady-state mà không đòi hỏi kiến trúc build đặc biệt.

## 9. Trade-offs

### Advantages

- startup nhanh hơn so với tối ưu mọi method tối đa ngay lập tức
- hot code nhận optimization sâu hơn
- Dynamic PGO sử dụng behavior thực tế của workload

### Costs / Risks

- performance có phase warm-up
- benchmark/debugging khó hơn nếu không hiểu tiering
- re-JIT tiêu tốn CPU ngắn hạn
- optimization runtime không cứu được architecture hoặc I/O bottleneck tệ

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu IL chưa phải machine code cuối cùng và JIT chạy trong runtime.

### Middle

Biết benchmark có warm-up, phân biệt cold-start với steady-state và tránh kết luận từ một lần chạy.

### Senior

Biết đọc runtime telemetry, xác định khi JIT/runtime thực sự là bottleneck và hiểu trade-off ReadyToRun/AOT/JIT.

### Technical Lead / Architect

Quyết định deployment model dựa trên SLA thực: startup, memory, throughput, compatibility và operational complexity; không chọn Native AOT hoặc runtime tuning chỉ vì “nghe nhanh hơn”.

## 11. Key takeaway

- JIT optimization là quá trình runtime, không phải một bước compile duy nhất.
- Cold-start và steady-state là hai performance regime khác nhau.
- Chỉ tối ưu runtime khi profiling chứng minh runtime là bottleneck.

# 2. ASP.NET Core Output Caching: cache HTTP response đúng boundary thay vì biến controller thành nơi tự quản lý cache

## 1. What is it?

Output Caching lưu response đã tạo cho một request và có thể phục vụ lại response đó cho request tương đương mà không chạy lại toàn bộ endpoint/application/database path.

Khác với cache-aside ở data layer, Output Caching đặt cache ở HTTP response boundary.

Mental model:

```text
Request
 -> Output Cache lookup
    -> HIT  -> cached HTTP response
    -> MISS -> endpoint -> services -> DB
                         -> response
                         -> cache response
```

## 2. Why does it exist?

Nhiều endpoint read-heavy có output lặp lại theo URL/query/header trong một khoảng thời gian. Nếu mỗi request đều chạy model binding, authorization-independent business logic, EF Core query và serialization, application lãng phí CPU/DB capacity.

Tự viết `IMemoryCache` trong controller có thể hoạt động, nhưng nhanh chóng phát sinh duplicate key logic, invalidation khó, response semantics không nhất quán và coupling với implementation.

Output Caching cung cấp policy ở HTTP boundary.

## 3. How does it work?

Cache key thường được xây từ request characteristics như route/query và các vary rules. Policy quyết định response nào được cache, bao lâu và request nào có thể dùng lại.

Điểm quan trọng: HTTP response caching phải xét identity và personalization. Nếu response phụ thuộc user nhưng cache key không vary theo user hoặc endpoint không nên cache, có nguy cơ data leak.

Flow:

```text
GET /catalog?page=1
 -> cache key = path + query
 -> cached 200 JSON

GET /catalog?page=2
 -> key khác
 -> execute endpoint
```

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("catalog", policy =>
        policy
            .Expire(TimeSpan.FromSeconds(30))
            .SetVaryByQuery("page", "category"));
});

var app = builder.Build();
app.UseOutputCache();

app.MapGet("/catalog", async (
    string? category,
    int page,
    CatalogDbContext db,
    CancellationToken ct) =>
{
    var items = await db.Products
        .AsNoTracking()
        .Where(x => category == null || x.Category == category)
        .OrderBy(x => x.Id)
        .Skip((page - 1) * 50)
        .Take(50)
        .Select(x => new ProductListItem(x.Id, x.Name, x.Price))
        .ToListAsync(ct);

    return Results.Ok(items);
})
.CacheOutput("catalog");
```

Nếu content thay đổi theo publish event, có thể thiết kế tag-based eviction thay vì chỉ TTL.

## 5. Real production scenario

Product listing page nhận 5.000 request/phút nhưng catalog chỉ thay đổi vài lần mỗi phút. Mỗi request hiện tại query SQL và serialize cùng một payload.

Output cache 15–30 giây có thể giảm đáng kể origin load. Nhưng product inventory realtime không nên bị cache cùng policy nếu business yêu cầu freshness cao.

Điểm Senior cần nhìn là “response nào có freshness tolerance nào?”, không phải “cache càng nhiều càng tốt”.

## 6. Failure scenario & troubleshooting

**Symptom** → user thấy dữ liệu của user khác hoặc response stale quá lâu.

**Evidence** → cache hit cao, endpoint personalized, cache key không chứa dimension cần thiết hoặc invalidation không chạy.

**Hypothesis** → cache policy sai boundary.

**Diagnosis** → inspect vary rules, authentication state, headers/query dimensions và invalidation events.

**Fix** → không cache personalized response nếu không thật sự cần; hoặc dùng policy/key đủ chặt. Tách catalog public khỏi user-specific data.

**Verification** → integration test nhiều identity/query variant và test publish/update sau cache hit.

## 7. Common mistakes

- Cache response có authorization-sensitive data mà không vary theo identity.
- Cache mọi `GET` vì nghĩ `GET = safe to cache`.
- TTL dài nhưng không có invalidation ownership.
- Cache endpoint vốn đã rẻ, trong khi cost/complexity của cache lớn hơn lợi ích.
- Đặt cache ở nhiều tầng: CDN + output cache + Redis + data cache nhưng không biết tầng nào đang giữ stale value.

## 8. Alternatives

- `IMemoryCache`: phù hợp data/object cục bộ trong một process.
- Redis: shared distributed cache cho nhiều instances.
- CDN/Akamai: cache ở edge, phù hợp public HTTP content.
- Database optimization: đôi khi query đủ nhanh, không cần cache.

Output Caching phù hợp khi HTTP response là đúng unit để reuse.

## 9. Trade-offs

### Advantages

- giảm request processing, serialization và database traffic
- policy nằm gần HTTP boundary
- dễ áp dụng nhất quán hơn cache tự viết trong từng controller

### Costs / Risks

- stale data
- invalidation complexity
- security risk nếu cache key sai
- thêm state làm incident khó debug hơn

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache hit bỏ qua phần lớn pipeline xử lý endpoint.

### Middle

Cấu hình TTL/vary policy và viết integration test cho cache behavior.

### Senior

Xác định data freshness, cache key cardinality, invalidation và security boundary.

### Technical Lead / Architect

Quyết định cache nên nằm ở CDN, app output, Redis hay không tồn tại; đồng thời quy định owner của invalidation và SLO freshness.

## 11. Key takeaway

- Cache ở đúng boundary quan trọng hơn cache ở nhiều nơi.
- Personalized/authorized response cần cực kỳ cẩn trọng.
- TTL là business consistency decision, không chỉ performance setting.

# 3. EF Core compiled query: giảm query compilation overhead nhưng chỉ hữu ích ở hot path có bằng chứng đo lường

## 1. What is it?

EF Core phải xử lý LINQ expression tree, translate sang SQL và xây query execution pipeline. EF Core đã có internal query-plan caching, nhưng explicit compiled query cho phép chuẩn bị delegate query để giảm thêm overhead ở path được gọi rất thường xuyên.

Mental model:

```text
LINQ expression
 -> query shape analysis
 -> translation
 -> SQL command pipeline
 -> execute
```

Compiled query cố định query shape và tái sử dụng phần preparation hiệu quả hơn.

## 2. Why does it exist?

Ở phần lớn business API, database/network latency lớn hơn query compilation overhead rất nhiều. Nhưng trong hot path với query rất nhanh, gọi hàng chục nghìn lần mỗi giây, CPU overhead phía application có thể trở nên đo được.

Compiled query tồn tại cho trường hợp đã tối ưu access pattern và vẫn còn bottleneck ở query preparation.

## 3. How does it work?

Ví dụ:

```csharp
private static readonly Func<AppDbContext, Guid, Order?> GetOrderById =
    EF.CompileQuery((AppDbContext db, Guid id) =>
        db.Orders
            .AsNoTracking()
            .SingleOrDefault(x => x.Id == id));
```

Delegate được tạo một lần và reuse:

```csharp
var order = GetOrderById(db, id);
```

Với async:

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<Order>> GetOrder =
    EF.CompileAsyncQuery((AppDbContext db, Guid id) =>
        db.Orders
            .AsNoTracking()
            .Where(x => x.Id == id));
```

Compiled query không thay đổi SQL semantics, index, round-trip hay database execution plan.

## 4. Practical implementation

Trước tiên đo query bình thường:

```csharp
var order = await db.Orders
    .AsNoTracking()
    .Where(x => x.Id == id)
    .Select(x => new OrderDto(x.Id, x.Status, x.Total))
    .SingleOrDefaultAsync(ct);
```

Nếu profiler cho thấy EF query compilation/preparation đáng kể trên hot path, mới thử compiled query và benchmark cả throughput lẫn allocation.

Đừng benchmark với InMemory provider vì nó không đại diện translation/database path thực.

## 5. Real production scenario

Một low-latency internal pricing service chạy query theo key trên local/network-near PostgreSQL, median DB latency rất thấp. Endpoint đạt hàng chục nghìn request/giây và CPU app trở thành bottleneck.

Sau khi projection/index/connection pool đã đúng, profiling cho thấy phần EF query overhead lặp lại đáng kể. Compiled query có thể đáng cân nhắc.

Trong CRUD backoffice 100 request/giây với SQL 40 ms, compiled query gần như không giải quyết vấn đề có ý nghĩa.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries hàng loạt nhưng latency hầu như không đổi.

**Evidence** → trace cho thấy 95% latency nằm ở database I/O; app CPU thấp.

**Hypothesis** → tối ưu sai bottleneck.

**Diagnosis** → profile request breakdown: EF CPU vs DB dependency duration vs serialization/network.

**Fix** → quay lại query plan/index/access pattern nếu DB là bottleneck; bỏ complexity compiled query không cần thiết.

**Verification** → benchmark trước/sau dưới workload đại diện, theo p95 + CPU + allocations.

## 7. Common mistakes

- Dùng compiled query như default cho mọi repository method.
- Nghĩ compiled query tạo database prepared statement “nhanh tuyệt đối”.
- Bỏ qua projection và kéo cả entity graph về memory.
- Benchmark không có database thật.
- Tạo nhiều compiled query variants làm code khó maintain hơn lợi ích.

## 8. Alternatives

- Query cache mặc định của EF Core thường đủ.
- Raw SQL/Dapper có thể phù hợp cho read hot path rất đặc thù.
- Database stored procedure phù hợp một số workload nhưng tăng coupling.
- Tối ưu index/query shape thường tạo gain lớn hơn.

## 9. Trade-offs

### Advantages

- giảm một phần EF-side CPU overhead
- phù hợp hot path ổn định, query shape cố định

### Costs / Risks

- code ít tự nhiên hơn LINQ bình thường
- lợi ích nhỏ nếu I/O chi phối
- tăng complexity và benchmark burden

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ query phải được translate trước khi database chạy SQL.

### Middle

Biết dùng projection, `AsNoTracking`, đo query duration trước khi tối ưu sâu.

### Senior

Profile EF-side overhead và quyết định compiled query chỉ khi có evidence.

### Technical Lead / Architect

Ngăn đội ngũ biến micro-optimization thành coding standard. Quy định performance work dựa trên benchmark và production telemetry.

## 11. Key takeaway

- Compiled query là optimization chuyên biệt, không phải best practice mặc định.
- Nếu database mất 100 ms, tiết kiệm vài micro/milliseconds ở EF không giải quyết root cause.
- Measure trước, tối ưu đúng layer sau.

# 4. PostgreSQL deadlock: hiểu wait-for cycle, lock order và cách phân tích thay vì chỉ tăng timeout

## 1. What is it?

Deadlock xảy ra khi hai hoặc nhiều transaction giữ lock mà transaction khác cần, đồng thời mỗi transaction lại chờ lock do transaction khác giữ. Không transaction nào tự tiến tiếp được.

Ví dụ:

```text
T1 giữ lock Row A -> chờ Row B
T2 giữ lock Row B -> chờ Row A
```

PostgreSQL phát hiện cycle và abort một transaction để phá deadlock.

## 2. Why does it exist?

Lock là cần thiết để giữ consistency khi concurrent writes. Deadlock không phải “database bị lỗi”, mà là hệ quả có thể xảy ra khi nhiều transaction acquire resources theo thứ tự không nhất quán.

Nếu database không phát hiện deadlock, các transaction có thể chờ vô hạn.

## 3. How does it work?

Transaction ví dụ:

```sql
-- T1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- giữ row lock id=1
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

Song song:

```sql
-- T2
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;
-- giữ row lock id=2
UPDATE accounts SET balance = balance + 50 WHERE id = 1;
```

Nếu timing phù hợp, tạo cycle.

Database chọn victim transaction và trả deadlock error. Application phải xem đây là transient concurrency failure có thể retry nếu operation idempotent/safe.

## 4. Practical implementation

Cách đơn giản nhất thường là enforce lock order:

```csharp
var ids = new[] { fromAccountId, toAccountId }
    .OrderBy(x => x)
    .ToArray();

var accounts = await db.Accounts
    .Where(x => ids.Contains(x.Id))
    .OrderBy(x => x.Id)
    .ToListAsync(ct);
```

Nếu cần explicit locking, SQL có thể dùng `FOR UPDATE`, nhưng transaction scope phải ngắn.

Retry policy cần bounded retry + jitter và chỉ áp dụng khi business operation an toàn:

```text
deadlock detected
 -> rollback transaction
 -> short randomized delay
 -> retry whole transaction
```

Không retry từ giữa transaction.

## 5. Real production scenario

Approval workflow cập nhật `Request` rồi `EmployeeSummary`. Job nền lại cập nhật `EmployeeSummary` trước rồi `Request`. Khi traffic tăng, hai flow thỉnh thoảng deadlock.

Mỗi flow riêng lẻ đều “đúng”, nhưng resource acquisition order khác nhau tạo cycle.

Fix bền vững thường là thống nhất transaction boundary/order, không chỉ thêm retry.

## 6. Failure scenario & troubleshooting

**Symptom** → sporadic transaction failures dưới load; retry thường thành công.

**Evidence** → PostgreSQL log có `deadlock detected`, chi tiết process nào chờ transaction/lock nào.

**Hypothesis** → lock ordering conflict.

**Diagnosis** → map SQL statements về application flows, xem `pg_stat_activity`, `pg_locks`, transaction duration và log deadlock graph.

**Fix** → consistent resource order, transaction ngắn hơn, giảm rows locked, index đúng để tránh lock footprint không cần thiết; retry transient victim.

**Verification** → concurrency stress test tái hiện trước fix và không còn deadlock hoặc deadlock rate giảm về mức chấp nhận được.

## 7. Common mistakes

- Tăng command timeout rồi nghĩ deadlock sẽ hết.
- Retry vô hạn, tạo retry storm.
- Giữ transaction mở trong lúc gọi external API.
- Update cùng resource theo order khác nhau ở các code path.
- Thiếu index khiến statement scan/update nhiều rows hơn dự kiến.

## 8. Alternatives

Optimistic concurrency phù hợp khi có thể detect conflict ở application level. Queue serialization theo business key có thể loại một số concurrent write races nhưng tăng latency/complexity. Serializable isolation giải quyết class anomaly khác nhưng không “miễn deadlock”.

## 9. Trade-offs

### Advantages

Locking cho correctness transaction mạnh và database tự phát hiện deadlock.

### Costs / Risks

Contention làm giảm throughput. Retry thêm latency. Thiết kế transaction không nhất quán tạo lỗi hiếm, khó reproduce.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deadlock là cycle chờ lock, khác với query đơn thuần chạy chậm.

### Middle

Biết giữ transaction ngắn và đọc error/log cơ bản.

### Senior

Phân tích lock order, transaction scope, query plan và thiết kế safe retry.

### Technical Lead / Architect

Chuẩn hóa ownership/order cho shared data, quyết định khi nào cần serialize workflow hoặc thay boundary để giảm contention hệ thống.

## 11. Key takeaway

- Deadlock là concurrency design problem, không phải timeout problem.
- Consistent lock/resource ordering là biện pháp mạnh và đơn giản.
- Retry là safety net, không thay thế root-cause fix.

# 5. Redis distributed lock: khi nào lock phân tán giải quyết đúng bài toán và khi nào nó chỉ che một boundary thiết kế yếu

## 1. What is it?

Distributed lock cố đảm bảo tại một thời điểm chỉ một process/instance được sở hữu một critical section liên quan shared resource.

Trong Redis, pattern cơ bản thường dựa trên atomic set-if-not-exists với expiration:

```text
SET lock:key unique-value NX PX 30000
```

Lock có TTL để tránh bị giữ mãi nếu owner crash.

## 2. Why does it exist?

Trong single process, `lock`/`SemaphoreSlim` đủ để serialize execution. Nhưng khi application scale 5 instances, mỗi process có lock riêng, nên cả 5 vẫn có thể chạy cùng job.

Distributed lock tạo coordination qua shared system.

Tuy nhiên câu hỏi đầu tiên phải là: ta có thực sự cần lock, hay có thể thiết kế operation idempotent / partition ownership / queue consumer semantics tốt hơn?

## 3. How does it work?

Acquire:

```text
Instance A -> SET job:billing tokenA NX PX 30000 -> OK
Instance B -> SET job:billing tokenB NX PX 30000 -> fail
```

Release phải chỉ xóa lock nếu token vẫn thuộc owner đó. Không được `DEL key` mù quáng vì lock có thể đã expire và được owner khác acquire.

Lua release pattern:

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

Nếu critical section dài hơn TTL, cần renewal/lease semantics rất cẩn thận.

## 4. Practical implementation

Ví dụ conceptual C# với StackExchange.Redis:

```csharp
var key = "locks:monthly-close";
var token = Guid.NewGuid().ToString("N");
var ttl = TimeSpan.FromSeconds(30);

var acquired = await database.StringSetAsync(
    key,
    token,
    ttl,
    When.NotExists);

if (!acquired)
    return;

try
{
    await RunMonthlyCloseAsync(ct);
}
finally
{
    const string script = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    else
        return 0
    end
    """;

    await database.ScriptEvaluateAsync(
        script,
        new RedisKey[] { key },
        new RedisValue[] { token });
}
```

Đây vẫn chưa giải quyết mọi failure mode như process pause dài, network partition hoặc operation tiếp tục chạy sau khi lease mất.

## 5. Real production scenario

ASP.NET Core app chạy 4 App Service instances. `BackgroundService` mỗi instance đều chạy job gửi monthly invoice. Team thêm Redis lock để chỉ một instance chạy.

Điều này có thể hợp lý nếu job nhỏ và team chấp nhận Redis coordination. Nhưng nếu invoice là financial side effect quan trọng, kiến trúc tốt hơn có thể là durable queue + idempotency + explicit scheduler ownership, vì lock loss không được phép dẫn tới duplicate charge.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng job chạy đồng thời dù có distributed lock.

**Evidence** → first owner chạy quá TTL; lock expire; second owner acquire trong khi first vẫn tiếp tục.

**Hypothesis** → lease duration/renewal không bao phủ critical section.

**Diagnosis** → compare lock acquire/renew logs với job duration và GC/network pauses.

**Fix** → renewal với ownership check, fencing token nếu resource hỗ trợ, hoặc redesign sang idempotent queue/ownership model.

**Verification** → chaos test pause process/network và chứng minh duplicate side effect không xảy ra.

## 7. Common mistakes

- Dùng `GET` rồi `SET` tách rời thay vì atomic `SET NX`.
- Release bằng `DEL` không kiểm token owner.
- TTL không có hoặc TTL quá ngắn.
- Nghĩ Redis lock cung cấp exactly-once execution.
- Dùng lock cho mọi concurrency issue thay vì sửa business invariant bằng database constraint/idempotency.

## 8. Alternatives

- SQL advisory/application lock
- database unique constraint
- queue partition/session ownership
- leader election
- idempotent processing
- scheduler platform chỉ có một logical trigger

Nhiều bài toán “không được duplicate” tốt hơn nếu biến duplicate thành harmless thay vì cố chứng minh duplicate không bao giờ xảy ra.

## 9. Trade-offs

### Advantages

- tương đối đơn giản cho cross-instance coordination
- latency thấp khi Redis đã là dependency sẵn có

### Costs / Risks

- Redis trở thành coordination dependency critical
- lease expiry tạo edge cases tinh vi
- network partition và process pause làm reasoning khó
- dễ tạo false confidence về exactly-once

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu in-process `lock` không coordination được nhiều instances.

### Middle

Biết atomic acquire, owner token và TTL.

### Senior

Hiểu lease loss, renewal, fencing và idempotency.

### Technical Lead / Architect

Quyết định có nên dùng distributed lock hay redesign workflow; đánh giá failure semantics quan trọng hơn API lock cụ thể.

## 11. Key takeaway

- Distributed lock là lease-based coordination, không phải phép màu exactly-once.
- Owner token + TTL là tối thiểu; vẫn cần suy nghĩ về lock loss.
- Nếu duplicate có hậu quả lớn, idempotency và durable workflow thường quan trọng hơn lock.

# 6. CQRS với một database: tách command/query về intent mà chưa trả giá của dual-store và eventual consistency

## 1. What is it?

CQRS (Command Query Responsibility Segregation) tách operations làm thay đổi state khỏi operations chỉ đọc state.

Điểm dễ hiểu sai: CQRS không bắt buộc hai database, Event Sourcing hoặc message broker.

Một hệ thống có thể dùng cùng SQL database nhưng có command model và query model khác nhau để phản ánh hai nhu cầu khác nhau.

## 2. Why does it exist?

Write side thường cần enforce invariant, transaction và domain behavior. Read side thường cần projection tối ưu cho UI/reporting.

Nếu ép cả hai qua một generic repository/entity model, read query có thể trở nên phức tạp và write model bị kéo theo nhu cầu presentation.

CQRS tách intent để mỗi side tối ưu đúng nhiệm vụ.

## 3. How does it work?

```text
POST /orders
 -> CreateOrderCommand
 -> Handler
 -> Domain / transaction
 -> Orders tables

GET /orders/{id}/summary
 -> query handler
 -> projection SQL/EF
 -> DTO
```

Cả hai vẫn truy cập cùng database:

```text
           +--> Command path --> Domain --> SQL
API -------|
           +--> Query path -----------> SQL --> DTO
```

Không có eventual consistency chỉ vì dùng CQRS một database; consistency phụ thuộc cách transaction/read được thiết kế.

## 4. Practical implementation

Command:

```csharp
public sealed record ApproveTimesheetCommand(Guid TimesheetId, Guid ApproverId);

public sealed class ApproveTimesheetHandler
{
    private readonly AppDbContext _db;

    public async Task Handle(
        ApproveTimesheetCommand command,
        CancellationToken ct)
    {
        var timesheet = await _db.Timesheets
            .SingleAsync(x => x.Id == command.TimesheetId, ct);

        timesheet.Approve(command.ApproverId);
        await _db.SaveChangesAsync(ct);
    }
}
```

Query:

```csharp
public async Task<TimesheetSummaryDto?> GetSummaryAsync(
    Guid id,
    CancellationToken ct)
{
    return await _db.Timesheets
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new TimesheetSummaryDto(
            x.Id,
            x.Employee.Name,
            x.TotalHours,
            x.Status))
        .SingleOrDefaultAsync(ct);
}
```

Query không cần hydrate full aggregate nếu chỉ cần DTO.

## 5. Real production scenario

Timesheet system có approval rules phức tạp nhưng dashboard chỉ cần employee name, total hours và status. Nếu dashboard luôn load aggregate + related entities, read side vừa chậm vừa coupling với domain model.

Tách query projection giúp domain tập trung invariant còn UI có shape phù hợp.

## 6. Failure scenario & troubleshooting

**Symptom** → codebase có hàng trăm command/query classes nhưng logic CRUD đơn giản, navigation trở nên khó.

**Evidence** → handler chỉ gọi một repository method, không có behavior/trade-off rõ ràng.

**Hypothesis** → CQRS ceremony được áp dụng như coding style thay vì giải quyết complexity.

**Diagnosis** → xem từng boundary có read/write pressure thực sự khác nhau không.

**Fix** → giữ separation chỉ nơi có giá trị; endpoint CRUD đơn giản có thể dùng application service trực tiếp.

**Verification** → code giảm indirection nhưng vẫn bảo toàn testability và business boundaries.

## 7. Common mistakes

- Nghĩ dùng MediatR = CQRS.
- Tách hai database quá sớm.
- Mỗi request một command class dù không có lợi ích.
- Query side vẫn dùng full domain aggregate.
- Command handler chứa mọi logic thay vì domain invariant đúng boundary.

## 8. Alternatives

Layered application service đơn giản thường đủ cho CRUD. Vertical Slice Architecture có thể tách theo feature mà không cần full CQRS semantics. Dual-store CQRS chỉ nên xuất hiện khi read/write scale, latency hoặc model requirements thực sự khác biệt.

## 9. Trade-offs

### Advantages

- command/read intent rõ hơn
- read projection hiệu quả
- write model ít bị presentation concerns làm bẩn

### Costs / Risks

- nhiều types/files hơn
- dễ overengineering
- nếu tiến lên dual-store, operational complexity tăng mạnh

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu command thay đổi state, query không thay đổi state.

### Middle

Implement handler/projection rõ và không hydrate object graph không cần thiết.

### Senior

Biết khi separation đem lại clarity/performance và khi chỉ thêm ceremony.

### Technical Lead / Architect

Quyết định CQRS level phù hợp: không CQRS, logical CQRS một DB, hay physical read/write stores. Complexity phải theo business/scale requirement.

## 11. Key takeaway

- CQRS là separation of intent, không đồng nghĩa microservices/Event Sourcing.
- Một database thường là điểm bắt đầu hợp lý.
- Read model và write model chỉ nên tách đến mức complexity thực tế yêu cầu.

# 7. Azure Service Bus dead-letter queue: biến poison message thành luồng vận hành có thể quan sát và recover

## 1. What is it?

Dead-letter queue (DLQ) là nơi Service Bus giữ các message không thể xử lý bình thường hoặc bị application explicitly dead-letter.

DLQ không phải thùng rác tự dọn. Nó là failure channel cần ownership, telemetry và recovery process.

## 2. Why does it exist?

Nếu consumer retry mãi một poison message, message đó có thể tiêu tốn throughput, tạo log noise và chặn ordered/session workflow. Nếu drop message ngay, mất dữ liệu và audit trail.

DLQ tách message lỗi khỏi main delivery path để hệ thống tiếp tục xử lý message lành mạnh trong khi team điều tra.

## 3. How does it work?

Service Bus dùng at-least-once delivery. Consumer nhận message với lock. Nếu fail/retry nhiều lần vượt `MaxDeliveryCount`, broker chuyển message sang DLQ.

```text
Queue
 -> receive
 -> handler fail
 -> abandon / lock expires
 -> retry
 -> delivery count exceeded
 -> DLQ
```

Consumer cũng có thể dead-letter chủ động với reason/description khi payload vi phạm contract không thể retry.

## 4. Practical implementation

```csharp
processor.ProcessMessageAsync += async args =>
{
    try
    {
        var command = args.Message.Body.ToObjectFromJson<ImportCommand>()
            ?? throw new InvalidOperationException("Invalid body");

        await handler.HandleAsync(command, args.CancellationToken);
        await args.CompleteMessageAsync(args.Message, args.CancellationToken);
    }
    catch (UnsupportedSchemaVersionException ex)
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            deadLetterReason: "UnsupportedSchemaVersion",
            deadLetterErrorDescription: ex.Message,
            cancellationToken: args.CancellationToken);
    }
};
```

Transient timeout không nên dead-letter ngay; invalid schema thường không nên retry hàng chục lần.

## 5. Real production scenario

Import service nhận message chứa blob URL + schema version. Một producer deploy version mới trước consumer và gửi `schemaVersion=4` trong khi consumer chỉ hỗ trợ v3.

Retry 10 lần không sửa được incompatibility. Message nên vào DLQ với reason rõ, alert được phát, sau khi consumer upgrade thì operator/recovery job resubmit message.

## 6. Failure scenario & troubleshooting

**Symptom** → business nói một số records “biến mất”, main queue không backlog.

**Evidence** → DLQ count tăng nhưng không có alert/dashboard.

**Hypothesis** → poison messages bị dead-letter âm thầm.

**Diagnosis** → inspect DLQ reason, delivery count, exception telemetry và message schema/version.

**Fix** → sửa consumer/producer compatibility; xây replay tool có validation/idempotency.

**Verification** → resubmit sample message, consumer complete thành công, DLQ age/count giảm.

## 7. Common mistakes

- Không monitor DLQ vì nghĩ broker tự xử lý.
- Replay tất cả DLQ message mù quáng sau deploy.
- Không lưu dead-letter reason có ý nghĩa.
- Retry permanent validation error như transient error.
- Recovery không idempotent, replay tạo duplicate side effect.

## 8. Alternatives

Một số hệ thống dùng quarantine queue riêng để có policy tùy chỉnh hơn. Kafka-style platforms có thể dùng dead-letter topic. Với batch import, failure table trong database đôi khi đơn giản hơn messaging DLQ.

## 9. Trade-offs

### Advantages

- main flow không bị poison message làm nghẽn
- giữ evidence để điều tra/recover
- có thể phân loại permanent vs transient failure

### Costs / Risks

- cần dashboard, alert, retention, tooling và ownership
- DLQ có thể trở thành “nghĩa địa message” nếu không có operational process
- replay có thể gây duplicate nếu consumer không idempotent

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DLQ là queue dành cho message xử lý thất bại, không phải message đã “xong”.

### Middle

Phân loại exception, complete/abandon/dead-letter đúng semantics.

### Senior

Thiết kế retry, idempotency, replay, alert và schema compatibility.

### Technical Lead / Architect

Quy định failure taxonomy, DLQ ownership, retention, recovery SLA và producer/consumer versioning strategy.

## 11. Key takeaway

- DLQ là production workflow, không phải nơi bỏ quên lỗi.
- Permanent failure và transient failure cần policy khác nhau.
- Replay chỉ an toàn khi consumer/idempotency được thiết kế trước.

# 8. IIS Application Pool recycling: vì sao process “tự restart” và cách phân biệt recycle bình thường với Production incident

## 1. What is it?

IIS Application Pool chứa một hoặc nhiều worker process (`w3wp.exe`) chạy web application. Recycling kết thúc worker process cũ và tạo process mới theo policy hoặc trigger như scheduled recycle, config change, memory limit hoặc manual action.

Recycle khác machine reboot và khác application crash, dù từ góc nhìn application đều có thể gây mất in-memory state.

## 2. Why does it exist?

Long-running process có thể tích lũy fragmentation, resource leak hoặc cần reload config/binary. IIS cung cấp lifecycle management để worker process được thay mới có kiểm soát.

Trong legacy enterprise hosting, recycle là một phần bình thường của operational model. Nhưng nếu app không designed cho restart, recycle sẽ lộ ra vấn đề như lost session, job duplicate hoặc cold-start 5xx.

## 3. How does it work?

Simplified flow:

```text
IIS receives traffic
 -> App Pool worker A

Recycle triggered
 -> worker B starts
 -> old worker A drains/terminates
 -> traffic shifts to B
```

Behavior thực tế phụ thuộc overlapped recycling, startup time, load balancer/proxy và app initialization.

State trong process như static dictionary, `IMemoryCache`, in-memory session hoặc background-job progress không bền qua recycle.

## 4. Practical implementation

ASP.NET Core hosted behind IIS nên xử lý graceful shutdown:

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var item = await ReceiveAsync(stoppingToken);
            await ProcessAsync(item, stoppingToken);
        }
    }
}
```

Không giữ critical state chỉ trong static memory:

```csharp
// Không phù hợp cho durable business state
private static readonly Dictionary<Guid, JobState> Jobs = new();
```

Durable state cần database/blob/queue tùy use case.

## 5. Real production scenario

Một .NET Framework CMS chạy trên IIS. Mỗi đêm 02:00 App Pool recycle. Team phát hiện đúng 02:00 có spike latency và thỉnh thoảng editor mất session.

Root cause không phải “server ngẫu nhiên restart”: session dùng InProc provider, cache warm-up nặng và app startup compile nhiều view.

Giải pháp phải xử lý hosting lifecycle, không chỉ tăng server CPU.

## 6. Failure scenario & troubleshooting

**Symptom** → application “restart” theo pattern thời gian, memory về thấp, startup logs xuất hiện lại.

**Evidence** → Windows Event Viewer/IIS logs cho thấy recycle trigger; process ID thay đổi.

**Hypothesis** → configured recycle hoặc memory threshold.

**Diagnosis** → inspect App Pool advanced settings, event logs, config/file changes, Rapid-Fail Protection và application crash logs.

**Fix** → loại trigger không cần thiết hoặc làm app restart-safe: out-of-process session, durable jobs, warm-up, graceful stop.

**Verification** → trigger recycle có kiểm soát trong staging và quan sát request errors/session/job behavior.

## 7. Common mistakes

- Lưu critical session/business state trong process.
- Tắt recycling hoàn toàn để “fix” leak thay vì điều tra leak.
- Không log process start/stop reason.
- Chạy scheduler trong web app mà không tính recycle/multi-instance.
- Nhầm recycle với crash và điều tra sai hướng.

## 8. Alternatives

Azure App Service quản lý process lifecycle theo platform khác nhưng application vẫn phải restart-safe. Windows Service/Worker Service phù hợp background work hơn web-hosted scheduler. Containers cũng restart thường xuyên; immutable/stateless principle tương tự.

## 9. Trade-offs

### Advantages

- lifecycle management sẵn có
- recycle có thể hạn chế ảnh hưởng của một số long-running process issues

### Costs / Risks

- cold start
- mất in-memory state
- background work bị interrupt
- recycle che memory leak nếu chỉ dùng như workaround

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu App Pool và worker process không sống mãi.

### Middle

Đọc IIS/Event Viewer logs, cấu hình App Pool và làm app handle shutdown.

### Senior

Phân biệt recycle/crash/config reload, thiết kế stateless/durable state và warm-up.

### Technical Lead / Architect

Quyết định workload nào còn phù hợp IIS web process, workload nào nên tách worker/service và đặt operational policies dựa trên availability requirement.

## 11. Key takeaway

- Process restart là normal operating condition, không phải edge case.
- In-memory state không phải durable state.
- Hãy xác định recycle reason bằng evidence trước khi thay config.

# 9. OpenTelemetry context propagation: giữ trace xuyên qua HTTP và messaging mà không biến correlation thành logging thủ công

## 1. What is it?

Context propagation truyền trace context từ component này sang component khác để spans ở nhiều service được nối thành cùng distributed trace.

W3C Trace Context thường dùng `traceparent`/`tracestate` qua HTTP. Messaging cần inject/extract context vào message properties/headers.

Mental model:

```text
Client trace
 -> API span
    -> SQL span
    -> HTTP downstream span
       -> Service B span
          -> Service Bus publish
             -> Consumer span
```

## 2. Why does it exist?

Trong distributed system, timestamp + text log không đủ để biết request nào ở Service A tương ứng operation nào ở Service B. Manually tạo “CorrelationId” có thể giúp, nhưng dễ mất context ở async/messaging boundaries và không cung cấp parent/child timing chuẩn.

OpenTelemetry chuẩn hóa trace/span propagation và export.

## 3. How does it work?

Mỗi trace có `TraceId`; mỗi operation/span có `SpanId`. Khi outbound HTTP request xảy ra, instrumentation inject parent context. Downstream extract rồi tạo child span.

Messaging phức tạp hơn vì producer và consumer không cùng call stack. Producer inject context vào application properties; consumer extract và tạo consumer span.

Baggage có thể truyền metadata business nhỏ, nhưng không nên dùng để mang sensitive/high-cardinality data tùy tiện.

## 4. Practical implementation

ASP.NET Core setup:

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation()
        .AddSource("Orders"));
```

Custom span:

```csharp
private static readonly ActivitySource ActivitySource = new("Orders");

public async Task ProcessAsync(Order order, CancellationToken ct)
{
    using var activity = ActivitySource.StartActivity("ProcessOrder");
    activity?.SetTag("order.type", order.Type);

    await _service.ProcessAsync(order, ct);
}
```

Không nên tag `customer.email`, full payload hoặc secret/token.

## 5. Real production scenario

Checkout request đi qua Web API → Product API → SQL → Service Bus → Notification Worker. User báo checkout mất 6 giây.

Distributed trace cho thấy API chỉ mất 100 ms local, nhưng Product API outbound dependency mất 4.8 giây và retry thêm một lần. Không có context propagation, team phải ghép log thủ công giữa 4 systems.

## 6. Failure scenario & troubleshooting

**Symptom** → Application Insights có nhiều trace fragments nhưng không nối thành end-to-end transaction.

**Evidence** → downstream request tạo TraceId mới; message headers thiếu trace context.

**Hypothesis** → propagation bị mất ở custom HTTP client/message serializer/consumer boundary.

**Diagnosis** → inspect outbound headers/properties và current `Activity` ở producer/consumer.

**Fix** → dùng instrumentation chuẩn hoặc inject/extract `ActivityContext` đúng cách.

**Verification** → gửi synthetic request và xác nhận toàn flow có cùng TraceId với parent-child hợp lý.

## 7. Common mistakes

- Tự tạo GUID correlation mới ở mỗi service.
- Log TraceId nhưng không propagate qua messaging.
- Đưa PII/token vào baggage/tags.
- High-cardinality tags không kiểm soát làm telemetry cost tăng.
- Sampling quá mạnh ở downstream khiến trace khó điều tra mà không hiểu sampling strategy.

## 8. Alternatives

Manual correlation ID vẫn hữu ích như business/request identifier nhưng không thay thế distributed tracing. Vendor-specific tracing như Application Insights SDK có thể hoạt động tốt, nhưng OpenTelemetry giảm coupling và chuẩn hóa instrumentation/export.

## 9. Trade-offs

### Advantages

- end-to-end causality
- latency breakdown giữa services/dependencies
- chuẩn vendor-neutral

### Costs / Risks

- telemetry volume/cost
- context propagation edge cases
- privacy/high-cardinality concerns
- instrumentation overhead dù thường nhỏ

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu TraceId nối nhiều spans thuộc cùng operation.

### Middle

Cấu hình ASP.NET Core/HttpClient/EF instrumentation và đọc trace waterfall.

### Senior

Xử lý propagation qua messaging, sampling, cardinality và custom spans.

### Technical Lead / Architect

Định nghĩa observability contract: mandatory instrumentation, sensitive-data rules, sampling, retention và SLO use cases.

## 11. Key takeaway

- Correlation tốt phải propagate tự động qua service boundaries.
- Trace context và business identifiers bổ sung cho nhau, không thay thế nhau.
- Telemetry schema/cardinality cần governance giống API/data schema.

# 10. Vue.js async race condition: ngăn response cũ ghi đè state mới trong UI khi request hoàn tất không theo thứ tự

## 1. What is it?

Async race condition ở frontend xảy ra khi nhiều request cùng liên quan một state nhưng completion order khác request order. Response cũ về muộn có thể ghi đè dữ liệu mới hơn.

Ví dụ user gõ search:

```text
request A: "ca"   -> gửi trước -> về sau
request B: "car"  -> gửi sau   -> về trước
```

Nếu cả hai đều `results.value = response`, UI cuối cùng có thể hiển thị kết quả cho `ca` dù input đang là `car`.

## 2. Why does it exist?

Network latency không deterministic. `await` chỉ giữ thứ tự bên trong một async flow, không serialize các event handler độc lập.

Frontend reactive framework cập nhật state đúng theo code, nhưng code không biết response nào còn relevant nếu không thiết kế request identity/cancellation.

## 3. How does it work?

Vue watcher có thể kích hoạt nhiều fetch:

```text
input changes
 -> request #1
input changes again
 -> request #2

#2 completes -> state = newest
#1 completes -> state = stale
```

Hai cách phổ biến:

- cancel request cũ bằng `AbortController`
- sequence/version guard: chỉ latest request được commit state

## 4. Practical implementation

Vue 3 + TypeScript:

```ts
import { ref, watch } from 'vue'

const search = ref('')
const results = ref<Product[]>([])

let controller: AbortController | null = null

watch(search, async (value) => {
  controller?.abort()
  controller = new AbortController()

  try {
    const response = await fetch(
      `/api/products?q=${encodeURIComponent(value)}`,
      { signal: controller.signal }
    )

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`)
    }

    results.value = await response.json()
  } catch (error) {
    if (error instanceof DOMException && error.name === 'AbortError') {
      return
    }

    console.error(error)
  }
})
```

Backend vẫn nên nhận cancellation khi client connection bị abort nếu stack/proxy hỗ trợ, nhưng frontend cancellation không phải guarantee rằng server side side-effect đã dừng.

## 5. Real production scenario

Automotive marketplace có autocomplete make/model. User gõ nhanh “toyota”. Request “toy” mất 800 ms, request “toyota” mất 120 ms. UI hiển thị đúng trong chốc lát rồi quay về kết quả “toy”.

Bug thường bị báo là “API trả sai”, nhưng network traces cho thấy cả hai response đều đúng; frontend commit state sai ordering.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng quay về dữ liệu cũ khi thao tác nhanh; khó reproduce trên localhost.

**Evidence** → browser DevTools Network cho thấy request order khác completion order.

**Hypothesis** → stale async response overwrite.

**Diagnosis** → thêm request sequence log, throttle network trong DevTools để reproduce.

**Fix** → cancellation/latest-request guard; debounce nếu giảm request volume có giá trị.

**Verification** → simulated slow network, gõ nhanh nhiều lần và xác nhận state luôn tương ứng latest input.

## 7. Common mistakes

- Nghĩ `await` tự đảm bảo user events chạy theo thứ tự.
- Chỉ debounce nhưng không xử lý race nếu request trước đã được gửi.
- Abort request và giả định server transaction chắc chắn rollback.
- Shared loading flag bị request cũ set `false` trong khi request mới vẫn chạy.
- Không phân biệt stale response với cache stale data.

## 8. Alternatives

Sequence token:

```ts
let requestVersion = 0

async function searchProducts(q: string) {
  const version = ++requestVersion
  const data = await fetchProducts(q)

  if (version === requestVersion) {
    results.value = data
  }
}
```

Libraries như TanStack Query có thể quản lý query identity/caching/cancellation tốt hơn cho app phức tạp. Với simple page, custom logic có thể đủ và ít dependency hơn.

## 9. Trade-offs

### Advantages

- UI state nhất quán với latest user intent
- abort có thể giảm work không còn cần thiết

### Costs / Risks

- cancellation/error state phức tạp hơn
- không phải mọi API/client đều support cancellation đầy đủ
- state machine loading/error cần thiết kế rõ nếu nhiều concurrent requests hợp lệ

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request gửi trước không đảm bảo response về trước.

### Middle

Dùng `AbortController`, sequence guard và DevTools network throttling để reproduce.

### Senior

Thiết kế state concurrency, cache/query identity và backend cancellation semantics.

### Technical Lead / Architect

Quyết định khi nào dùng library quản lý server state, chuẩn hóa frontend data-fetching patterns và tránh mỗi component tự phát minh concurrency semantics khác nhau.

## 11. Key takeaway

- Async UI có concurrency dù JavaScript execution đơn luồng.
- Latest user intent phải được encode bằng cancellation hoặc version guard.
- Network DevTools + throttling là công cụ quan trọng để debug race condition frontend.
