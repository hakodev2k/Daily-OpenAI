# 1. .NET `IAsyncDisposable`: async cleanup và resource ownership

## 1. What is it?

`IAsyncDisposable` biểu diễn cleanup có thể cần asynchronous I/O. Mental model quan trọng không phải “Dispose nhưng có await”, mà là ownership: component nào tạo/giữ resource thì component đó phải bảo đảm resource được giải phóng đúng lúc mà không block thread vô ích.

## 2. Why does it exist?

`IDisposable.Dispose()` chỉ có synchronous contract. Nếu cleanup cần flush network buffer, hoàn tất asynchronous stream hoặc đóng resource qua I/O, ép nó chạy đồng bộ có thể gây blocking hoặc sync-over-async.

## 3. How does it work?

Compiler chuyển `await using` thành `try/finally` và await `DisposeAsync()` trong cleanup path. Cleanup vẫn chạy khi scope kết thúc do return hoặc exception.

```text
Acquire resource -> use asynchronously -> scope exits
                                      -> DisposeAsync
                                      -> await cleanup
```

## 4. Practical implementation

```csharp
await using var stream = new FileStream(
    path,
    FileMode.Create,
    FileAccess.Write,
    FileShare.None,
    81920,
    useAsync: true);

await JsonSerializer.SerializeAsync(stream, payload, cancellationToken: ct);
```

Nếu class sở hữu async-disposable dependency, class đó thường cũng phải expose async disposal.

## 5. Real production scenario

Worker xử lý file lớn và mở stream cho từng message. Nếu cleanup bị bỏ qua khi exception xảy ra, file handles tích tụ; process sau đó không mở được file mới dù business logic không có lỗi rõ ràng.

## 6. Failure scenario & troubleshooting

**Symptom** → handle count tăng hoặc file vẫn bị lock.  
**Evidence** → profiler/process metrics cho thấy resource không giảm sau mỗi work item.  
**Hypothesis** → ownership/disposal path thiếu.  
**Diagnosis** → kiểm tra object lifetime và exception paths.  
**Fix** → `await using`, explicit ownership và không giữ resource vượt logical operation.  
**Verification** → handle/resource count ổn định dưới load test.

## 7. Common mistakes

Gọi `DisposeAsync().AsTask().Wait()`; dispose dependency không thuộc ownership của mình; quên cleanup khi exception; dùng finalizer thay deterministic cleanup.

## 8. Alternatives

`IDisposable` đủ nếu cleanup hoàn toàn synchronous. Factory/callback API có thể ẩn ownership khi consumer không cần giữ resource lâu.

## 9. Trade-offs

### Advantages

Cleanup không block, ownership rõ, phù hợp asynchronous resource lifecycle.

### Costs / Risks

Async disposal lan vào call chain; shutdown path cần đủ thời gian để cleanup hoàn tất.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu resource cần deterministic cleanup.

### Middle

Dùng `await using` đúng exception path.

### Senior

Reason về ownership, shutdown và sync-over-async.

### Technical Lead / Architect

Thiết kế resource lifetime theo request/work unit thay vì để cleanup phụ thuộc GC.

## 11. Key takeaway

- Disposal trước hết là ownership contract.
- Async cleanup không nên bị ép thành synchronous blocking.
- GC quản lý memory, không thay deterministic release của external resources.

# 2. ASP.NET Core graceful shutdown: drain request trước khi process chết

## 1. What is it?

Graceful shutdown cho application ngừng nhận work mới, báo cancellation cho hosted services và cho in-flight work một khoảng thời gian hoàn tất trước khi process bị terminate.

## 2. Why does it exist?

Container restart, App Service recycle và deployment là hoạt động bình thường. Nếu process chết ngay, request đang ghi database, upload hoặc consume message có thể bị cắt giữa chừng.

## 3. How does it work?

```text
Termination signal
      -> stop accepting new traffic
      -> application stopping
      -> cancel BackgroundService
      -> finish/drain in-flight work
      -> dispose resources
      -> process exits
```

Infrastructure readiness/draining và application shutdown phải phối hợp.

## 4. Practical implementation

```csharp
public sealed class Worker(ChannelReader<Job> reader) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in reader.ReadAllAsync(stoppingToken))
        {
            await ProcessAsync(job, stoppingToken);
        }
    }
}
```

Không thay `stoppingToken` bằng `CancellationToken.None` trong long-running operations.

## 5. Real production scenario

Rolling deployment có nhiều instances. Instance cũ bị remove khỏi load balancer nhưng vẫn có request upload đang chạy. Drain window cho request kết thúc trước khi instance bị terminate.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment tạo spike 499/5xx hoặc duplicate jobs.  
**Evidence** → errors trùng thời điểm restart; traces bị cắt.  
**Hypothesis** → termination grace period ngắn hoặc worker bỏ qua cancellation.  
**Diagnosis** → so shutdown timestamps với request/job duration.  
**Fix** → readiness drain, propagate cancellation, chia work dài thành resumable/idempotent units.  
**Verification** → rolling deployment dưới traffic không tăng error rate.

## 7. Common mistakes

Cho rằng shutdown luôn có vô hạn thời gian; nhận work mới sau stopping signal; swallow cancellation; dùng graceful shutdown thay idempotency.

## 8. Alternatives

Queue-based work tách long-running operation khỏi web process. Checkpoint/resume phù hợp jobs dài hơn shutdown window.

## 9. Trade-offs

### Advantages

Giảm interrupted work và deployment errors.

### Costs / Risks

Deployment chậm hơn; không bảo vệ khỏi crash/OOM/node loss.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process restart là bình thường.

### Middle

Propagate stopping token và dispose đúng.

### Senior

Thiết kế drain, idempotency và bounded shutdown.

### Technical Lead / Architect

Quyết định work nào được drain, checkpoint hoặc chuyển sang durable queue.

## 11. Key takeaway

- Graceful shutdown giảm planned interruption, không thay fault tolerance.
- Long-running work cần cancellation hoặc resumability.
- Infrastructure draining và application lifecycle phải khớp nhau.

# 3. SQL Server covering index: giảm lookup nhưng không biến index thành bản sao table

## 1. What is it?

Covering index là index chứa đủ columns để SQL Server phục vụ query mà không cần quay lại clustered index/heap lấy thêm dữ liệu. Key columns phục vụ seek/order; `INCLUDE` chứa payload cần trả về.

## 2. Why does it exist?

Một nonclustered index có thể tìm rows nhanh nhưng hàng nghìn Key Lookups làm random I/O tăng mạnh. Cover query có thể loại bỏ lookup đó.

## 3. How does it work?

```text
Predicate -> nonclustered index seek
                    |
                    +-- missing selected column -> Key Lookup x N

Covering index -> seek -> return directly
```

Index vẫn có write/storage cost.

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_Customer_CreatedAt
ON dbo.Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, TotalAmount);
```

Phải dựa trên workload và execution plan, không copy toàn bộ SELECT list một cách máy móc.

## 5. Real production scenario

Order history query lấy 50 records gần nhất của customer. Index cũ chỉ có `CustomerId`; plan thực hiện nhiều lookups để lấy status/total. Sau measurement, covering index giảm logical reads và p95.

## 6. Failure scenario & troubleshooting

**Symptom** → read nhanh hơn nhưng writes chậm và index storage tăng.  
**Evidence** → index usage/write stats cho thấy nhiều maintenance.  
**Hypothesis** → over-indexing.  
**Diagnosis** → so read benefit với update frequency và duplicate indexes.  
**Fix** → consolidate/drop index ít giá trị.  
**Verification** → đo cả read latency lẫn write throughput.

## 7. Common mistakes

`INCLUDE` mọi column; bỏ qua key order/selectivity; tạo index cho query hiếm; nhìn estimated plan mà không đo I/O thực.

## 8. Alternatives

Projection nhỏ hơn có thể loại nhu cầu cover. Clustered design khác hoặc columnstore phù hợp workload khác. Cache không sửa access pattern SQL tệ.

## 9. Trade-offs

### Advantages

Giảm lookup và I/O cho read path quan trọng.

### Costs / Risks

Tốn disk/memory, tăng write amplification và maintenance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index là cấu trúc dữ liệu phụ.

### Middle

Đọc Seek + Key Lookup trong plan.

### Senior

Cân bằng coverage với write/storage cost.

### Technical Lead / Architect

Thiết lập index strategy theo workload thay vì từng query riêng lẻ.

## 11. Key takeaway

- Covering index giải quyết lookup cost cụ thể.
- Index tốt cho read vẫn có giá ở write path.
- Đo logical reads và workload trước/sau thay đổi.

# 4. Cosmos DB partition key: scalability bắt đầu từ data distribution

## 1. What is it?

Partition key quyết định cách Cosmos DB phân phối logical items lên physical partitions. Nó ảnh hưởng trực tiếp đến scalability, query routing, transaction scope và hot partition risk.

## 2. Why does it exist?

Một node không thể scale storage/throughput vô hạn. Distributed database phải chia dữ liệu. Nếu key phân phối kém, tăng RU tổng không sửa được hotspot ở một partition.

## 3. How does it work?

```text
partition key value -> logical partition -> physical partition
```

Point read có `id + partition key` được route chính xác. Cross-partition query phải fan-out nhiều partitions và tiêu tốn RU/latency hơn.

## 4. Practical implementation

```csharp
var item = await container.ReadItemAsync<Order>(
    id,
    new PartitionKey(customerId),
    cancellationToken: ct);
```

Chọn key dựa trên cardinality, access patterns, growth và write distribution.

## 5. Real production scenario

Multi-tenant SaaS chọn `/tenantId`. Phần lớn tenants nhỏ nhưng một tenant chiếm 60% traffic. Logical model hợp lý về ownership nhưng tạo hot partition cho tenant lớn.

## 6. Failure scenario & troubleshooting

**Symptom** → throttling `429` dù tổng provisioned RU còn dư.  
**Evidence** → metrics theo partition key range cho thấy traffic lệch.  
**Hypothesis** → hot key.  
**Diagnosis** → phân tích request distribution và large tenants.  
**Fix** → synthetic/hierarchical partitioning nếu access pattern cho phép; retry chỉ giảm symptom.  
**Verification** → RU và throttling phân bố đều hơn.

## 7. Common mistakes

Chọn field ít cardinality; dùng timestamp tạo write hotspot; chọn key chỉ theo schema; assume cross-partition query miễn phí.

## 8. Alternatives

SQL database phù hợp nếu relational transactions/query flexibility quan trọng hơn horizontal distribution. MongoDB sharding có bài toán shard key tương tự.

## 9. Trade-offs

### Advantages

Partitioning tốt cho horizontal scale và targeted reads.

### Costs / Risks

Key khó đổi; access patterns tương lai bị ràng buộc; distributed queries tốn hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dữ liệu bị chia theo key.

### Middle

Dùng partition key trong reads/writes.

### Senior

Phân tích cardinality, hotspot, RU và fan-out.

### Technical Lead / Architect

Chọn data model từ access pattern và growth model trước khi chọn database.

## 11. Key takeaway

- Partition key là architectural decision, không phải field bắt buộc cho SDK.
- Tổng throughput cao không cứu hot partition.
- Thiết kế theo access pattern và distribution thực tế.

# 5. DDD Aggregate: consistency boundary chứ không phải object graph

## 1. What is it?

Aggregate là nhóm domain objects được xem như một consistency boundary; Aggregate Root là entry point cho mutations phải bảo vệ invariants bên trong boundary đó.

## 2. Why does it exist?

Business model cần biết invariant nào phải đúng ngay trong một transaction. Nếu aggregate quá lớn, contention/load tăng; nếu quá nhỏ, invariant cần atomicity bị phá.

## 3. How does it work?

```text
Command -> Aggregate Root -> enforce invariant -> state change
                              |
                              -> one transaction boundary
```

Reference sang aggregate khác thường dùng identity thay vì kéo toàn bộ object graph vào cùng transaction.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void AddLine(ProductId productId, int quantity)
    {
        if (quantity <= 0) throw new DomainException("Quantity must be positive");
        _lines.Add(new OrderLine(productId, quantity));
    }
}
```

Invariant phải được bảo vệ qua methods thay vì public setters tùy ý.

## 5. Real production scenario

Order và Inventory không nhất thiết cùng aggregate. Order cần đảm bảo line/total nội bộ; inventory reservation có ownership/lifecycle riêng và có thể consistency qua messaging.

## 6. Failure scenario & troubleshooting

**Symptom** → mỗi update Order lock/load hàng nghìn child objects.  
**Evidence** → transaction lớn, EF tracking nhiều entities, contention cao.  
**Hypothesis** → aggregate boundary quá rộng.  
**Diagnosis** → hỏi invariant nào thật sự cần atomic.  
**Fix** → tách boundary và dùng eventual consistency nơi business cho phép.  
**Verification** → invariant vẫn đúng, transaction nhỏ hơn.

## 7. Common mistakes

Aggregate = table graph; một aggregate cho toàn bounded context; repository cho mọi entity; domain model chỉ chứa getters/setters.

## 8. Alternatives

CRUD/anemic model hoàn toàn hợp lý cho domain đơn giản. Application service + transaction script thường đơn giản hơn DDD tactical patterns nếu invariants ít.

## 9. Trade-offs

### Advantages

Làm invariant và transaction ownership rõ.

### Costs / Risks

Modeling khó; boundary sai tạo coupling hoặc eventual consistency không cần thiết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Root kiểm soát mutation.

### Middle

Implement invariant trong domain methods.

### Senior

Thiết kế boundary theo consistency và contention.

### Technical Lead / Architect

Quyết định nơi DDD tạo giá trị và nơi CRUD đơn giản đủ tốt.

## 11. Key takeaway

- Aggregate là consistency boundary, không phải navigation graph.
- Boundary nên nhỏ nhất nhưng vẫn bảo vệ invariant cần atomicity.
- DDD không bắt buộc cho domain đơn giản.

# 6. Bulkhead Pattern: cô lập resource pool để dependency chậm không kéo sập toàn API

## 1. What is it?

Bulkhead cô lập capacity giữa các workloads/dependencies, tương tự khoang kín trên tàu. Một dependency chậm chỉ được chiếm resource budget riêng thay vì toàn bộ threads/connections/concurrency của service.

## 2. Why does it exist?

Timeout và Circuit Breaker giới hạn failure theo thời gian/state nhưng request vẫn có thể đồng loạt chờ dependency chậm, làm resource exhaustion lan sang endpoints khỏe mạnh.

## 3. How does it work?

```text
API
 |- Payment calls -> concurrency pool 20
 |- Search calls  -> concurrency pool 50
 `- Core DB       -> separate capacity
```

Khi payment pool đầy, requests mới fail/queue có kiểm soát thay vì ăn toàn service capacity.

## 4. Practical implementation

```csharp
private readonly SemaphoreSlim _paymentConcurrency = new(20);

public async Task<T> ExecuteAsync<T>(Func<Task<T>> action, CancellationToken ct)
{
    await _paymentConcurrency.WaitAsync(ct);
    try { return await action(); }
    finally { _paymentConcurrency.Release(); }
}
```

Production thường dùng resilience library/policy với metrics và bounded queue thay vì tự viết đầy đủ.

## 5. Real production scenario

Reviews API chậm 8 giây trên product page. Không bulkhead, hàng nghìn requests giữ outbound connection/concurrency và health endpoint cũng chậm. Bulkhead giới hạn reviews traffic; page có thể fallback không reviews.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency nhỏ gây latency toàn API.  
**Evidence** → concurrent calls/connection pool tăng và unrelated endpoints degrade.  
**Hypothesis** → shared capacity exhaustion.  
**Diagnosis** → trace resource usage theo dependency.  
**Fix** → timeout + bounded concurrency + fallback phù hợp.  
**Verification** → dependency load test không làm core endpoints vượt SLO.

## 7. Common mistakes

Bulkhead queue vô hạn; giới hạn quá thấp không dựa capacity; retry bên trong bulkhead làm amplification; fallback cho operation không thể degrade.

## 8. Alternatives

Separate service/process cho isolation mạnh hơn nhưng operational cost cao. Circuit Breaker xử lý repeated failure; Rate Limiter bảo vệ ingress. Các pattern bổ sung nhau.

## 9. Trade-offs

### Advantages

Failure isolation và predictable capacity.

### Costs / Risks

Có thể reject request sớm; tuning sai lãng phí capacity hoặc tạo bottleneck giả.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu shared resource có thể bị một dependency chiếm hết.

### Middle

Implement bounded concurrency và cancellation.

### Senior

Kết hợp timeout/retry/circuit breaker mà không amplification.

### Technical Lead / Architect

Phân bổ capacity theo business criticality và degradation strategy.

## 11. Key takeaway

- Resilience không chỉ là retry; còn là bảo vệ capacity.
- Bulkhead cần bounded queue/concurrency.
- Isolation mạnh hơn luôn đi kèm utilization/operational cost.

# 7. Azure App Service deployment slots: warm-up, swap và configuration boundary

## 1. What is it?

Deployment slot là live App Service environment riêng cho cùng app, thường dùng `staging` và `production`. Code được deploy/warm ở staging rồi swap routing/configuration theo slot semantics.

## 2. Why does it exist?

Deploy trực tiếp production có startup cold path và rollback chậm. Slot cho phép validate artifact trước khi traffic production chuyển sang nó.

## 3. How does it work?

```text
Deploy vNext -> staging -> warm/health validation
                         -> swap
Production traffic -----------------> vNext
```

Một số settings được đánh dấu deployment slot settings để không swap, đặc biệt environment-specific secrets/endpoints.

## 4. Practical implementation

Pipeline nên deploy staging, gọi health endpoint và smoke tests, sau đó mới swap. Application không nên coi “process started” là “ready”.

```csharp
builder.Services.AddHealthChecks()
    .AddDbContextCheck<AppDbContext>();
```

Health design phải tránh biến transient dependency thành deployment deadlock không cần thiết.

## 5. Real production scenario

ASP.NET Core app cần load configuration và JIT hot paths. Staging warm-up hoàn tất trước swap nên first production requests không chịu toàn bộ cold-start cost.

## 6. Failure scenario & troubleshooting

**Symptom** → swap thành công nhưng app production gọi staging database.  
**Evidence** → configuration sau swap không đúng environment.  
**Hypothesis** → setting đáng lẽ sticky nhưng không được đánh dấu slot setting.  
**Diagnosis** → compare slot configuration.  
**Fix** → phân loại code config và environment config; đánh dấu đúng slot settings.  
**Verification** → pre/post-swap smoke test kiểm tra dependency identity.

## 7. Common mistakes

Assume mọi config swap giống nhau; chạy destructive DB migration trước compatibility; health check chỉ trả 200 cố định; coi swap là rollback database.

## 8. Alternatives

Blue-Green bằng hai App Services cho isolation mạnh hơn. Container Apps/Kubernetes rolling/canary có deployment primitives khác. Direct deployment đơn giản hơn cho low-risk internal app.

## 9. Trade-offs

### Advantages

Warm-up, validation và app rollback nhanh.

### Costs / Risks

Config semantics phức tạp; database/shared dependencies vẫn là common failure boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu staging và production là hai slots.

### Middle

Deploy, smoke test, swap và cấu hình sticky settings.

### Senior

Reason về schema compatibility, health và rollback.

### Technical Lead / Architect

Chọn slot/blue-green/canary theo risk và observability maturity.

## 11. Key takeaway

- Slot swap không tự giải quyết database compatibility.
- Environment-specific settings phải có ownership rõ.
- Readiness validation trước traffic switch quan trọng hơn “deployment succeeded”.

# 8. OpenTelemetry baggage vs tags: correlation xuyên service mà không tạo telemetry debt

## 1. What is it?

Span tags/attributes mô tả một span. Baggage là key-value context có thể propagate xuyên process/service boundaries cùng distributed trace context. Vì baggage đi qua network, nó có cost và security implications khác tags.

## 2. Why does it exist?

Một số context như tenant tier hoặc workflow type hữu ích xuyên nhiều services. Nhưng copy mọi business identifier vào baggage làm header phình, rò dữ liệu và tăng cardinality khi export thành metrics/tags.

## 3. How does it work?

```text
Service A Activity + baggage
        -> HTTP propagation
Service B receives context
        -> child Activity
```

Baggage không tự động nên được export như span attribute; instrumentation phải quyết định sử dụng nó thế nào.

## 4. Practical implementation

```csharp
Activity.Current?.SetTag("checkout.step", "payment");
Baggage.SetBaggage("tenant.tier", "enterprise");
```

Không đặt access token, email hoặc payload nhạy cảm vào baggage.

## 5. Real production scenario

SaaS muốn phân tích incident theo tenant tier xuyên API → worker → payment adapter. Low-cardinality tier có thể propagate; tenant ID cụ thể nên được xử lý cẩn thận theo privacy/cardinality policy.

## 6. Failure scenario & troubleshooting

**Symptom** → telemetry bill tăng mạnh hoặc backend giới hạn dimensions.  
**Evidence** → hàng triệu unique attribute values.  
**Hypothesis** → high-cardinality identifiers bị export rộng.  
**Diagnosis** → audit semantic conventions/tags/baggage.  
**Fix** → giữ dimensions bounded, dùng logs/trace lookup cho identifiers chi tiết.  
**Verification** → cardinality/cost giảm mà incident correlation vẫn đủ.

## 7. Common mistakes

Baggage = secure context; propagate PII; dùng order ID làm metric dimension; đặt cùng attribute với tên khác ở mỗi service.

## 8. Alternatives

Structured logs phù hợp details; trace IDs dùng correlation mặc định; metrics chỉ nên giữ dimensions bounded và operationally useful.

## 9. Trade-offs

### Advantages

Context propagation giúp cross-service diagnosis.

### Costs / Risks

Header overhead, privacy risk và telemetry cardinality nếu lạm dụng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt trace context và log text.

### Middle

Gắn tags có ý nghĩa và propagate context.

### Senior

Quản lý cardinality, sampling, privacy.

### Technical Lead / Architect

Định nghĩa telemetry semantic conventions toàn platform.

## 11. Key takeaway

- Baggage được propagate nên phải coi là distributed data contract.
- High-cardinality identifiers không phù hợp metric dimensions.
- Observability tốt cần governance, không chỉ thêm nhiều fields.

# 9. Contract testing: bảo vệ integration boundary mà không cần E2E cho mọi trường hợp

## 1. What is it?

Contract testing kiểm tra producer và consumer thống nhất về interface: HTTP schema, required fields, status semantics hoặc message format. Nó tập trung vào boundary compatibility thay vì chạy toàn hệ thống end-to-end.

## 2. Why does it exist?

Unit tests không phát hiện producer đổi JSON field làm consumer hỏng. E2E phát hiện được nhưng chậm, fragile và khó bao phủ mọi consumer/version combination.

## 3. How does it work?

```text
Consumer expectation -> contract
                         |
                         v
Producer verification -> compatible / breaking
```

Contract có thể schema-first hoặc consumer-driven tùy ownership model.

## 4. Practical implementation

Một integration test có thể kiểm tra serialized contract thực:

```csharp
var response = await client.GetAsync("/api/orders/42");
response.EnsureSuccessStatusCode();

var json = await response.Content.ReadFromJsonAsync<OrderResponse>();
Assert.NotNull(json);
Assert.Equal(42, json.Id);
```

Mature setup nên verify schema/consumer expectations trong CI của producer.

## 5. Real production scenario

Orders API đổi `total` từ number sang formatted string. Producer unit tests vẫn xanh; frontend/mobile consumers fail. Contract verification chặn breaking change trước deploy.

## 6. Failure scenario & troubleshooting

**Symptom** → contract tests xanh nhưng production consumer vẫn hỏng.  
**Evidence** → test chỉ kiểm tra happy-path fields, bỏ status/error/pagination semantics.  
**Hypothesis** → contract coverage không phản ánh dependency thực.  
**Diagnosis** → map consumer assumptions.  
**Fix** → thêm meaningful interactions, không snapshot toàn payload mù.  
**Verification** → replay representative consumer cases.

## 7. Common mistakes

Snapshot mọi JSON khiến test brittle; mock producer thay vì verify real serialization; coi contract test thay integration/E2E hoàn toàn; không version contract.

## 8. Alternatives

OpenAPI schema validation phù hợp provider-defined APIs. Integration tests với real service mạnh hơn nhưng đắt. E2E giữ cho critical journeys, không cần mọi field combination.

## 9. Trade-offs

### Advantages

Feedback nhanh về breaking integration, ít fragile hơn full E2E.

### Costs / Risks

Contract governance/versioning và nguy cơ false confidence nếu expectations thiếu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu API contract không chỉ là compile-time type.

### Middle

Viết integration/contract tests cho boundary quan trọng.

### Senior

Phân biệt compatibility, semantics và consumer assumptions.

### Technical Lead / Architect

Chọn schema-first/consumer-driven và policy cho breaking changes.

## 11. Key takeaway

- Contract tests bảo vệ boundary, không thay mọi loại test.
- Test assumptions mà consumer thật sự phụ thuộc.
- Compatibility phải được kiểm tra trong CI trước production.

# 10. Third-party webhook verification: authenticity, replay protection và idempotency

## 1. What is it?

Webhook là inbound HTTP callback từ external provider. Secure webhook handling cần xác minh request thật từ provider, chống replay theo khả năng protocol và xử lý duplicate delivery idempotently.

## 2. Why does it exist?

Endpoint public có thể bị giả request. Ngay cả request hợp lệ cũng có thể được provider retry vì timeout, khiến cùng event đến nhiều lần.

## 3. How does it work?

```text
Provider -> signed payload + timestamp
             |
             v
Webhook endpoint
 -> verify signature on raw body
 -> validate timestamp/replay window
 -> deduplicate event ID
 -> enqueue/process
 -> return acknowledgement
```

Signature verification và authorization business là hai lớp khác nhau.

## 4. Practical implementation

```csharp
var expected = HMACSHA256.HashData(secretBytes, payloadBytes);
if (!CryptographicOperations.FixedTimeEquals(expected, signatureBytes))
    return Results.Unauthorized();
```

Thực tế phải dùng canonicalization/signature scheme chính thức của provider, thường ký raw request body và timestamp; không tự phát minh protocol nếu provider đã định nghĩa.

## 5. Real production scenario

Payment provider gửi `payment.succeeded`. API xử lý thành công nhưng response bị network timeout; provider retry cùng event. Nếu handler không deduplicate, order có thể phát hành invoice/notification hai lần.

## 6. Failure scenario & troubleshooting

**Symptom** → signature verification fail chỉ ở Production.  
**Evidence** → payload parsed rồi serialize lại khác raw bytes provider ký.  
**Hypothesis** → verification dùng transformed body.  
**Diagnosis** → compare raw bytes/canonical string theo provider docs.  
**Fix** → verify trước mutation/parsing, đúng encoding và timestamp.  
**Verification** → test official signed fixtures và tampered payload.

## 7. Common mistakes

Chỉ whitelist IP; compare signature bằng string thông thường; log secret/raw sensitive payload; không kiểm tra replay timestamp; assume webhook exactly-once; làm synchronous processing quá lâu trước acknowledgement.

## 8. Alternatives

Polling đơn giản hơn khi provider không có webhook nhưng tăng latency/quota cost. Queue sau verification giúp decouple acknowledgement khỏi processing. mTLS có thể bổ sung authentication nếu provider hỗ trợ.

## 9. Trade-offs

### Advantages

Webhook giảm polling và cho near-real-time integration.

### Costs / Risks

Public ingress, signature/key rotation, duplicate/reordering và operational recovery complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu webhook là untrusted inbound request cho tới khi verify.

### Middle

Implement signature verification và deduplication.

### Senior

Xử lý replay, retries, ordering, secret rotation và async processing.

### Technical Lead / Architect

Định nghĩa trust boundary, durable ingestion và reconciliation khi provider/webhook pipeline lỗi.

## 11. Key takeaway

- Verify signature trên representation mà provider thực sự ký.
- Authentic request vẫn có thể là duplicate.
- Webhook reliability cần idempotency và reconciliation, không chỉ HTTP 200.
