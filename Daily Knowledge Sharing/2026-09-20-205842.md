# 1. C# `IAsyncDisposable`: giải phóng resource bất đồng bộ mà không block ThreadPool

## 1. What is it?

`IAsyncDisposable` cho phép cleanup có I/O được `await` thông qua `DisposeAsync`. Mental model: `Dispose` phù hợp cleanup đồng bộ; nếu đóng/flush resource cần network hoặc storage I/O, ép nó chạy synchronously có thể block thread đúng lúc hệ thống đang chịu tải.

## 2. Why does it exist?

Một resource như asynchronous stream, transaction wrapper hoặc client-owned session có thể cần flush/close qua I/O. Nếu cleanup dùng `.GetAwaiter().GetResult()`, latency của dependency trở thành blocked worker thread và có thể góp phần tạo ThreadPool starvation.

## 3. How does it work?

`await using` được compiler chuyển thành `try/finally` và `await resource.DisposeAsync()` trong cleanup path. Cleanup vẫn chạy khi exception xảy ra, nhưng caller không cần block thread trong lúc chờ I/O.

```text
Acquire → use asynchronously → finally → await DisposeAsync
```

## 4. Practical implementation

```csharp
await using var stream = await OpenExportStreamAsync(ct);
await JsonSerializer.SerializeAsync(stream, report, cancellationToken: ct);
await stream.FlushAsync(ct);
```

Nếu type implement cả `IDisposable` và `IAsyncDisposable`, API consumer chọn path phù hợp lifecycle của mình; library author phải document ownership rõ ràng.

## 5. Real production scenario

Export service stream file lớn tới remote storage. Cleanup cần flush buffered data. Async disposal giúp request không giữ worker thread blocked trong lúc remote storage hoàn tất close/flush.

## 6. Failure scenario & troubleshooting

**Symptom** → request đã xử lý xong business logic nhưng latency vẫn cao và ThreadPool queue tăng. **Evidence** → trace cho thấy synchronous dispose chờ network. **Hypothesis** → sync-over-async trong cleanup. **Diagnosis** → inspect dispose path và thread stacks. **Fix** → dùng async-native cleanup nếu resource hỗ trợ. **Verification** → load test cho thấy blocked threads và tail latency giảm.

## 7. Common mistakes

Quên dispose khi exception; gọi `DisposeAsync().AsTask().Wait()`; dispose object mà caller không sở hữu; giả định mọi `IAsyncDisposable` đều cần async path trong mọi context.

## 8. Alternatives

`IDisposable` vẫn tốt cho purely synchronous cleanup như release unmanaged handle. Factory có thể che lifecycle khi ownership phức tạp. Không nên implement `IAsyncDisposable` chỉ để theo convention nếu cleanup không có asynchronous work.

## 9. Trade-offs

### Advantages

Không block thread trong I/O cleanup và giữ lifecycle rõ ràng.

### Costs / Risks

API surface phức tạp hơn, ownership cần document, cleanup failure trở thành asynchronous exception path.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu resource phải được giải phóng và `await using` là async counterpart của `using`.

### Middle

Biết chọn `IDisposable` hay `IAsyncDisposable`, propagate cancellation ở work path và test cleanup.

### Senior

Nhận diện sync-over-async, ownership ambiguity và cleanup latency dưới load.

### Technical Lead / Architect

Quyết định lifecycle contract ở library boundaries và tránh đưa asynchronous disposal vào API khi không có operational benefit.

## 11. Key takeaway

- Async cleanup hữu ích khi cleanup thật sự có I/O.
- Ownership quan trọng ngang cơ chế disposal.
- Không block async cleanup bằng `.Wait()` hoặc `.Result`.

# 2. ASP.NET Core graceful shutdown: drain request và dừng background work đúng lifecycle

## 1. What is it?

Graceful shutdown là quá trình application ngừng nhận work mới, cho in-flight work cơ hội hoàn tất trong một deadline, rồi giải phóng resource. Nó không đảm bảo mọi operation luôn hoàn thành; nó tạo một bounded shutdown protocol.

## 2. Why does it exist?

Deployment, autoscaling và host recycle là bình thường. Nếu process bị terminate ngay, request có thể bị cắt giữa transaction, message có thể chưa settle và background job có thể để lại partial state.

## 3. How does it work?

```text
Host receives stop
  → stop accepting new work
  → signal ApplicationStopping / CancellationToken
  → await hosted services
  → dispose services
  → process exits before platform deadline
```

Business operation vẫn cần idempotency vì host có thể crash hoặc deadline có thể hết trước khi drain xong.

## 4. Practical implementation

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var item = await _queue.ReceiveAsync(stoppingToken);
            await ProcessAsync(item, stoppingToken);
        }
    }
}
```

Không tạo `CancellationToken.None` ở deep calls nếu operation nên dừng cùng host.

## 5. Real production scenario

App Service deployment swap dừng instance cũ. API requests đang chạy được drain, còn Worker ngừng receive message mới và hoàn tất message đang xử lý trong shutdown budget.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment tạo spike 499/5xx và duplicate processing. **Evidence** → logs kết thúc đột ngột, hosted service không observe stopping token. **Diagnosis** → shutdown lifecycle bị bỏ qua hoặc operation vượt deadline. **Fix** → propagate token, giới hạn work unit, settle message sau commit. **Verification** → rolling deployment dưới load không tăng failed business operations.

## 7. Common mistakes

Dùng shutdown như guarantee; bắt `OperationCanceledException` rồi retry vô hạn; start fire-and-forget tasks ngoài host tracking; giữ transaction dài; không biết platform termination deadline.

## 8. Alternatives

Queue-driven Worker tách khỏi web process nếu work dài. Durable orchestration phù hợp workflow cần survive restarts. Với work cực ngắn, lifecycle mặc định có thể đủ.

## 9. Trade-offs

### Advantages

Giảm interrupted work và deployment regression.

### Costs / Risks

Shutdown lâu làm rollout chậm; vẫn cần crash-safe/idempotent design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process có lifecycle và cancellation khi host dừng.

### Middle

Propagate `CancellationToken`, dispose resource và test stop path.

### Senior

Thiết kế work unit bounded, idempotent và quan sát deployment behavior.

### Technical Lead / Architect

Quyết định workload nào nên sống cùng web app, workload nào cần worker/orchestrator riêng và shutdown budget bao nhiêu.

## 11. Key takeaway

- Graceful shutdown là bounded opportunity, không phải durability guarantee.
- Background work phải observe host cancellation.
- Idempotency vẫn cần cho crash và forced termination.

# 3. PostgreSQL composite index: thứ tự cột phải theo access pattern, không theo cảm giác

## 1. What is it?

Composite index chứa nhiều columns theo một thứ tự xác định. Mental model: index là ordered data structure; `(TenantId, CreatedAt)` và `(CreatedAt, TenantId)` phục vụ access patterns khác nhau.

## 2. Why does it exist?

Query thực tế thường filter/sort trên nhiều fields. Các single-column indexes riêng lẻ không phải lúc nào cũng thay thế được một ordered composite index có thể vừa narrow search range vừa hỗ trợ ordering.

## 3. How does it work?

Với B-tree `(tenant_id, created_at DESC)`, entries được nhóm theo `tenant_id`, rồi ordered theo `created_at`. Query một tenant và recent records có thể range scan hiệu quả.

```sql
SELECT id, status, created_at
FROM orders
WHERE tenant_id = $1
ORDER BY created_at DESC
LIMIT 50;
```

```sql
CREATE INDEX ix_orders_tenant_created
ON orders (tenant_id, created_at DESC);
```

## 4. Practical implementation

Dùng `EXPLAIN (ANALYZE, BUFFERS)` để kiểm tra actual rows, scan type và buffers thay vì chỉ nhìn estimated cost.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, status, created_at
FROM orders
WHERE tenant_id = 'acme'
ORDER BY created_at DESC
LIMIT 50;
```

## 5. Real production scenario

Multi-tenant SaaS có bảng events hàng trăm triệu rows. Mọi request UI đọc recent events theo tenant. Index bắt đầu bằng tenant giúp data access local hơn so với index chỉ theo timestamp.

## 6. Failure scenario & troubleshooting

**Symptom** → index tồn tại nhưng query vẫn scan nhiều pages. **Evidence** → plan cho thấy filter sau scan hoặc sort riêng. **Hypothesis** → column order không match predicates/order. **Diagnosis** → so sánh query shapes với index definition và selectivity. **Fix** → thiết kế index theo dominant access pattern, không thêm index mù quáng. **Verification** → buffers, execution time và write overhead đều được đo lại.

## 7. Common mistakes

Đặt cột theo schema order; tạo index cho mọi permutation; bỏ qua low-selectivity predicates; chỉ benchmark reads mà không đo write amplification; quên rằng query khác có thể cần index khác.

## 8. Alternatives

Single-column indexes có thể đủ cho simple predicates. Partial index hữu ích với subset ổn định. BRIN phù hợp một số bảng rất lớn có physical correlation. Không index cũng đúng nếu table nhỏ hoặc write-heavy.

## 9. Trade-offs

### Advantages

Giảm I/O, có thể hỗ trợ filtering và ordering cùng lúc.

### Costs / Risks

Tốn storage, tăng write cost, vacuum/maintenance overhead và có thể tối ưu quá riêng một query.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu composite index có thứ tự, không phải tập hợp columns không thứ tự.

### Middle

Đọc `EXPLAIN ANALYZE` và match index với query.

### Senior

Đánh giá selectivity, buffers, write cost và workload distribution.

### Technical Lead / Architect

Quản trị index portfolio theo production workload thay vì để từng feature thêm index không kiểm soát.

## 11. Key takeaway

- Index order phải bắt nguồn từ query pattern.
- Execution plan và I/O mới là evidence.
- Read optimization luôn có write/storage cost.

# 4. Cosmos DB partition key: scalability bắt đầu từ data distribution, không phải tăng RU/s

## 1. What is it?

Partition key quyết định cách Cosmos DB phân phối logical items lên physical partitions. Mental model: throughput có thể scale chỉ khi traffic và data có thể được phân tán; một hot key vẫn tạo bottleneck dù account có nhiều tổng RU/s.

## 2. Why does it exist?

Distributed storage cần routing key để biết item nằm ở đâu và để scale data/throughput ngang. Query không có partition key có thể fan-out nhiều partitions, tăng RU và latency.

## 3. How does it work?

```text
partition key value
      ↓ hash/routing
physical partitions
 P1   P2   P3   P4
```

Operations có exact partition key thường route trực tiếp. Cross-partition query cần coordinator fan-out rồi merge results.

## 4. Practical implementation

```csharp
var item = await container.ReadItemAsync<Order>(
    id: orderId,
    partitionKey: new PartitionKey(customerId),
    cancellationToken: ct);
```

Model nên chọn key có cardinality và traffic distribution phù hợp, đồng thời hỗ trợ dominant access paths.

## 5. Real production scenario

Telemetry platform dùng `TenantId` làm key. Một enterprise tenant tạo 60% traffic và trở thành hot partition. Tổng RU/s còn dư nhưng tenant đó vẫn bị throttling.

## 6. Failure scenario & troubleshooting

**Symptom** → `429` tập trung ở một tenant. **Evidence** → partition-level metrics cho thấy skew. **Hypothesis** → hot logical partition. **Diagnosis** → phân tích key distribution và request charge. **Fix** → redesign key như synthetic key nếu access pattern cho phép; migration phải có plan. **Verification** → throughput phân bố đều và cross-partition query cost vẫn chấp nhận được.

## 7. Common mistakes

Chọn constant/low-cardinality key; chọn key chỉ vì unique; bỏ qua future growth; query cross-partition mọi request; nghĩ tăng RU luôn chữa hot partition.

## 8. Alternatives

SQL/PostgreSQL phù hợp nếu relational constraints và joins quan trọng hơn global distribution. MongoDB sharding có bài toán shard key tương tự. Azure SQL sharding chỉ đáng khi workload thật sự cần.

## 9. Trade-offs

### Advantages

Scale-out và targeted routing tốt khi key phù hợp.

### Costs / Risks

Sai partition key rất khó sửa, ảnh hưởng query shape, transaction scope và migration cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định data placement.

### Middle

Luôn truyền key khi biết và đo Request Units.

### Senior

Phân tích cardinality, skew, hot partitions và cross-partition cost.

### Technical Lead / Architect

Chọn partition strategy từ workload forecast và migration risk; đôi khi quyết định không dùng Cosmos DB.

## 11. Key takeaway

- Distribution key là architectural decision.
- Tổng RU/s không cứu được traffic skew vô hạn.
- Model theo access pattern và growth, không chỉ current schema.

# 5. DDD Aggregate: transaction boundary bảo vệ invariant, không phải object graph khổng lồ

## 1. What is it?

Aggregate là consistency boundary trong domain; Aggregate Root là entry point để thay đổi state bên trong boundary. Entity có identity; Value Object được định nghĩa bởi value; Domain Service chứa domain behavior không thuộc tự nhiên một Entity; Application Service điều phối use case; Domain Event biểu diễn sự kiện domain; Bounded Context xác định model/language boundary.

## 2. Why does it exist?

Business invariants cần một nơi chịu trách nhiệm. Nếu mọi entity được sửa độc lập, rule xuyên các object trong cùng business transaction dễ bị phá. Ngược lại, gom cả domain vào một aggregate tạo transaction lớn và contention.

## 3. How does it work?

```text
Application Service
       ↓
Aggregate Root ── protects invariant ──> Entities / Value Objects
       ↓
transaction commit
       ↓
Domain Events (effects outside boundary)
```

Một transaction thường nên mutate một aggregate; coordination xuyên aggregate thường dùng eventual consistency khi business cho phép.

## 4. Practical implementation

```csharp
public sealed class Timesheet
{
    private readonly List<Entry> _entries = [];
    public TimesheetStatus Status { get; private set; }

    public void AddEntry(DateOnly day, decimal hours)
    {
        if (Status != TimesheetStatus.Draft)
            throw new InvalidOperationException("Only draft can change");
        if (_entries.Sum(x => x.Hours) + hours > 80)
            throw new DomainException("Period hour limit exceeded");
        _entries.Add(new Entry(day, hours));
    }
}
```

Invariant nằm trong model thay vì phụ thuộc controller nhớ validate.

## 5. Real production scenario

Timesheet và entries cần nhất quán khi submit; payroll export lại thuộc bounded context khác. Không nên load payroll history vào Timesheet aggregate chỉ vì có relation business.

## 6. Failure scenario & troubleshooting

**Symptom** → update một employee kéo theo hàng nghìn child objects và transaction lock lâu. **Evidence** → aggregate load graph rất lớn. **Hypothesis** → boundary được vẽ theo navigation graph thay vì invariant. **Diagnosis** → liệt kê rules nào thực sự cần atomicity. **Fix** → split boundaries và dùng domain events/workflow cho cross-boundary effects. **Verification** → invariants vẫn được tests bảo vệ, transaction duration giảm.

## 7. Common mistakes

DDD = repository + MediatR; aggregate = tất cả related tables; setter public phá invariant; Domain Service chứa toàn bộ logic; Domain Event dùng như integration event mà không phân biệt boundary.

## 8. Alternatives

Anemic CRUD model đủ tốt với domain đơn giản. Database constraints bảo vệ invariant dữ liệu rất hiệu quả. Application service có thể đủ khi rule ít và không cần rich domain model.

## 9. Trade-offs

### Advantages

Ownership/invariant rõ, model phản ánh business behavior.

### Costs / Risks

Modeling effort, persistence complexity và overengineering nếu domain chủ yếu CRUD.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Aggregate Root kiểm soát thay đổi trong consistency boundary.

### Middle

Implement behavior/invariants và unit tests quanh aggregate.

### Senior

Phân biệt atomic invariant với workflow/eventual consistency và tránh aggregate quá lớn.

### Technical Lead / Architect

Xác định Bounded Context, ownership, transaction boundary và liệu DDD có đáng chi phí cho domain đó hay không.

## 11. Key takeaway

- Aggregate boundary xuất phát từ invariant cần atomicity.
- Related data không tự động thuộc cùng aggregate.
- DDD không phải bộ folder/pattern bắt buộc.

# 6. Distributed timeout budget: retry đúng từng service vẫn có thể làm request tổng thể thất bại

## 1. What is it?

Timeout budget là tổng thời gian end-to-end mà request có thể tiêu trước khi caller không còn cần kết quả. Mỗi downstream call và retry phải nằm trong budget đó. Local retry policy “đúng” có thể cộng dồn thành global latency sai.

## 2. Why does it exist?

Trong service chain, A gọi B, B gọi C. Nếu mỗi layer timeout 30 giây và retry ba lần, caller có thể đã timeout từ lâu trong khi downstream vẫn tiếp tục tạo load vô ích.

## 3. How does it work?

```text
Client budget 3s
 └─ API processing 200ms
    └─ Service B budget ~2.5s
       └─ DB/external call + bounded retry
```

Deadline/cancellation nên propagate xuống chain. Retry chỉ có ích khi failure transient và còn đủ time budget.

## 4. Practical implementation

```csharp
using var budget = CancellationTokenSource.CreateLinkedTokenSource(requestAborted);
budget.CancelAfter(TimeSpan.FromSeconds(2));

using var response = await httpClient.SendAsync(request, budget.Token);
response.EnsureSuccessStatusCode();
```

Resilience pipeline nên giới hạn per-attempt timeout và total timeout; không retry non-idempotent operation mù quáng.

## 5. Real production scenario

Product page gọi reviews provider. Provider chậm 5 giây nhưng page SLO p95 là 1.5 giây. Reviews là optional; timeout ngắn và graceful fallback tốt hơn giữ toàn page chờ.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 tăng mạnh và dependency traffic tăng trong outage. **Evidence** → traces cho thấy nested retries sau khi upstream client đã disconnect. **Hypothesis** → timeout/retry budgets độc lập. **Diagnosis** → reconstruct critical path từ distributed traces. **Fix** → propagate deadline/cancellation, cap retries, degrade optional dependency. **Verification** → fault injection cho thấy latency bounded và retry volume không bùng nổ.

## 7. Common mistakes

Mọi dependency cùng timeout 30s; retry timeout ba lần không jitter; retry POST không idempotency; ignore `RequestAborted`; timeout quá thấp không dựa trên latency distribution.

## 8. Alternatives

Asynchronous messaging loại latency coupling cho workflows không cần immediate response. Cache/fallback phù hợp stale-tolerant data. Circuit Breaker giảm calls khi dependency đã unhealthy nhưng không thay timeout.

## 9. Trade-offs

### Advantages

Bounded latency, giảm wasted work và failure amplification.

### Costs / Risks

Timeout quá aggressive tạo false failures; budget allocation cần telemetry và business priority.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout là giới hạn chờ, retry tiêu thêm budget.

### Middle

Propagate cancellation và cấu hình retry theo idempotency.

### Senior

Dùng traces/p95/p99 để phân bổ budget và tránh retry storm.

### Technical Lead / Architect

Xác định SLO end-to-end, critical/optional dependencies và nơi nên chuyển synchronous flow thành asynchronous.

## 11. Key takeaway

- Tối ưu local policy không đảm bảo end-to-end reliability.
- Retry phải tiêu trong một bounded deadline.
- Optional dependency không nên quyết định availability của core response.

# 7. Azure Functions queue trigger: scale-out, duplicate execution và idempotency

## 1. What is it?

Queue-triggered Azure Function chạy handler khi message đến và có thể scale nhiều instances theo backlog. Mental model: scale-out tạo competing consumers; delivery/retry semantics có thể khiến cùng logical work xuất hiện lại, nên side effects phải idempotent.

## 2. Why does it exist?

Queue tách producer khỏi processing latency và cho compute scale theo backlog. Nhưng network/process failure khiến hệ thống không thể biết tuyệt đối handler đã commit side effect trước khi acknowledgement hay chưa.

## 3. How does it work?

```text
Producer → Queue → Function instances
                  ├─ F1
                  ├─ F2
                  └─ F3
failure → retry → poison/dead-letter path
```

Scale, retry và visibility/lock semantics phụ thuộc backing messaging service và configuration; application không nên giả định exactly-once.

## 4. Practical implementation

```csharp
[Function("ProcessInvoice")]
public async Task Run(
    [ServiceBusTrigger("invoices", Connection = "Bus")] ServiceBusReceivedMessage msg,
    CancellationToken ct)
{
    var eventId = msg.MessageId;
    if (await _inbox.ExistsAsync(eventId, ct)) return;

    await _processor.ProcessAndRecordAsync(eventId, msg.Body, ct);
}
```

Deduplication record và business state nên commit trong cùng transactional boundary khi data store cho phép.

## 5. Real production scenario

Invoice generation backlog tăng cuối tháng. Function scale-out xử lý song song. Một instance crash sau khi lưu invoice nhưng trước settlement; retry trên instance khác không được tạo invoice thứ hai.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate invoice sau transient outage. **Evidence** → cùng `MessageId` xuất hiện ở nhiều invocation IDs. **Hypothesis** → side effect không idempotent. **Diagnosis** → kiểm tra commit/settlement ordering. **Fix** → inbox/idempotency key hoặc unique database constraint. **Verification** → kill process sau commit trong integration test; retry không duplicate state.

## 7. Common mistakes

Tin vào exactly-once; dùng in-memory dedupe; scale concurrency vượt DB capacity; retry permanent validation error; không monitor poison/DLQ; function timeout ngắn hơn work unit.

## 8. Alternatives

Worker Service phù hợp khi cần process control ổn định. Container Apps jobs phù hợp containerized batch. App Service BackgroundService đơn giản nhưng scale/multi-instance scheduling cần tự quản lý.

## 9. Trade-offs

### Advantages

Elastic processing, ít server management, natural queue integration.

### Costs / Risks

Cold/startup behavior, concurrency pressure, retry semantics và observability cần thiết kế kỹ; cost tăng theo executions/resources.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue consumer có thể chạy lại message.

### Middle

Implement idempotency, cancellation và failure handling.

### Senior

Tune concurrency theo downstream capacity, monitor backlog/DLQ và test crash windows.

### Technical Lead / Architect

Chọn Functions vs Worker/Container Apps theo workload, cost, operational control và scaling characteristics.

## 11. Key takeaway

- Scale-out không thay thế idempotency.
- Consumer concurrency phải tôn trọng downstream capacity.
- Test crash giữa business commit và message acknowledgement.

# 8. Application Insights dependency tracing: tìm latency bằng critical path thay vì nhìn log rời rạc

## 1. What is it?

Dependency tracing ghi lại request và outbound dependencies như SQL/HTTP cùng trace context. Mental model: latency end-to-end là critical path qua nhiều spans; log riêng từng service không tự cho biết thời gian bị tiêu ở đâu.

## 2. Why does it exist?

Một API chậm có thể do SQL, Redis, HTTP provider hoặc queue handoff. Timestamp logs thủ công khó correlate, đặc biệt khi concurrent requests xen kẽ.

## 3. How does it work?

OpenTelemetry/SDK propagate trace context qua supported protocols. Application Insights liên kết request span với dependency spans.

```text
HTTP request 900ms
 ├─ app CPU 40ms
 ├─ SQL 120ms
 └─ Product API 690ms
      └─ downstream SQL 620ms
```

Critical path chỉ ra nơi latency thực sự nằm.

## 4. Practical implementation

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddSqlClientInstrumentation());
```

Exporter/configuration gửi telemetry tới backend như Application Insights; tránh ghi sensitive query parameters/payloads nếu không cần.

## 5. Real production scenario

Checkout p95 tăng từ 600ms lên 1.8s. API CPU bình thường. Trace cho thấy inventory dependency chiếm 1.1s và chỉ region cụ thể bị ảnh hưởng, giúp khoanh vùng thay vì optimize controller.

## 6. Failure scenario & troubleshooting

**Symptom** → traces bị đứt giữa services. **Evidence** → downstream có trace mới thay vì parent-child relation. **Hypothesis** → custom HTTP/messaging code không propagate context. **Diagnosis** → inspect `traceparent`/instrumentation. **Fix** → dùng standard instrumentation hoặc inject/extract context đúng protocol. **Verification** → synthetic request tạo một connected trace xuyên boundaries.

## 7. Common mistakes

Log mọi payload; không sampling strategy; chỉ nhìn average; custom correlation ID nhưng bỏ W3C trace context; alert trên raw exception count mà không gắn SLO.

## 8. Alternatives

Structured logs hữu ích forensic detail; metrics tốt cho trend/alert; profiler tốt cho in-process CPU. Chúng bổ sung chứ không thay traces.

## 9. Trade-offs

### Advantages

Nhanh localize dependency latency và failure propagation.

### Costs / Risks

Telemetry volume/cost, sampling bias và data privacy cần governance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt logs, metrics và traces.

### Middle

Instrument HTTP/SQL và dùng trace để debug request.

### Senior

Phân tích p95/p99, sampling và critical path; correlate deployment với regression.

### Technical Lead / Architect

Định nghĩa observability standard, retention/cost budget và telemetry ownership xuyên services.

## 11. Key takeaway

- Trace cho biết latency nằm trên dependency path nào.
- Logs + Metrics + Traces giải quyết các câu hỏi khác nhau.
- Instrumentation phải preserve context qua service boundaries.

# 9. Contract testing cho REST API: bảo vệ compatibility giữa producer và consumer

## 1. What is it?

Contract test kiểm tra assumptions ở boundary giữa API producer và consumer: route, status, schema, required fields và semantics quan trọng. Nó không thay unit/integration/E2E tests; nó tập trung vào compatibility risk.

## 2. Why does it exist?

Producer có thể pass toàn bộ unit tests nhưng đổi `status` thành `state`, làm consumer production hỏng. Full E2E giữa mọi service thường chậm và flaky; contract tests tạo feedback sớm hơn cho boundary changes.

## 3. How does it work?

```text
Consumer expectations
        ↕
HTTP contract / OpenAPI
        ↕
Producer implementation
```

Contract có thể provider-driven từ OpenAPI hoặc consumer-driven tùy organization. Quan trọng là test behavior thực tế, không chỉ validate file syntax.

## 4. Practical implementation

```csharp
[Fact]
public async Task GetOrder_keeps_public_contract()
{
    var response = await _client.GetAsync("/api/orders/42");
    response.StatusCode.Should().Be(HttpStatusCode.OK);

    using var json = JsonDocument.Parse(await response.Content.ReadAsStringAsync());
    json.RootElement.GetProperty("id").GetInt32().Should().Be(42);
    json.RootElement.GetProperty("status").ValueKind.Should().Be(JsonValueKind.String);
}
```

Chạy test trên real ASP.NET Core host và realistic serialization configuration để bắt naming/nullability behavior.

## 5. Real production scenario

Mobile client release cadence chậm hơn backend. Backend phải giữ old fields/status semantics nhiều tuần. Contract suite ngăn accidental breaking change trước deployment.

## 6. Failure scenario & troubleshooting

**Symptom** → CI xanh nhưng consumer production fail deserialize. **Evidence** → tests mock service interface thay vì HTTP wire contract. **Hypothesis** → test ở sai boundary. **Diagnosis** → compare captured response với production serializer/config. **Fix** → integration-level contract test và schema diff. **Verification** → replay representative consumer expectations.

## 7. Common mistakes

Mock producer trong “contract test”; snapshot toàn JSON làm tests brittle; chỉ kiểm schema mà bỏ status/error semantics; coi additive field luôn breaking; không version contract artifacts.

## 8. Alternatives

E2E tests bảo vệ whole journey nhưng expensive. OpenAPI lint/schema checks nhanh nhưng không chứng minh runtime behavior. Integration tests có thể cover contract nếu được thiết kế có chủ đích.

## 9. Trade-offs

### Advantages

Phát hiện breaking changes sớm và giảm cross-team integration regression.

### Costs / Risks

Contract governance/versioning, test maintenance và false confidence nếu expectations không phản ánh consumer thật.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu public API shape là contract.

### Middle

Viết integration contract tests cho success/error paths.

### Senior

Phân loại breaking/non-breaking changes, compatibility window và serializer behavior.

### Technical Lead / Architect

Định nghĩa API evolution policy, ownership và nơi contract testing mang lại value hơn full E2E.

## 11. Key takeaway

- Test contract ở wire boundary, không chỉ service interface.
- Compatibility gồm semantics, không chỉ JSON schema.
- Contract tests bổ sung, không thay integration/E2E strategy.

# 10. Git bisect: biến regression investigation từ đoán commit thành binary search

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên làm behavior chuyển từ good sang bad. Mental model: nếu có một test/reproduction deterministic, bạn có thể giảm hàng trăm commits xuống khoảng log2(N) lần kiểm tra.

## 2. Why does it exist?

Regression thường xuất hiện sau một khoảng thay đổi lớn. Đọc diff từng commit hoặc đoán “commit đáng ngờ” tốn thời gian và chịu confirmation bias.

## 3. How does it work?

```text
known good ---------------- known bad
             ↓ midpoint test
        discard half
             ↓
        repeat until culprit
```

Điều kiện quan trọng: có thể classify mỗi tested commit thành good/bad tương đối đáng tin cậy.

## 4. Practical implementation

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
# run reproduction
git bisect good   # or: git bisect bad
git bisect reset
```

Có thể automate:

```bash
git bisect run dotnet test tests/Regression.Tests --filter SlowCheckout
```

Exit code của script phải phân biệt pass/fail đúng.

## 5. Real production scenario

Sau 120 commits, checkout API tăng allocation 3×. Team có benchmark threshold reproducible. `git bisect run` tìm commit thay serializer configuration trong vài iterations thay vì review toàn bộ sprint.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit không liên quan hoặc kết quả thay đổi giữa runs. **Evidence** → reproduction flaky hoặc commit cũ không build vì external dependency. **Hypothesis** → predicate không deterministic. **Diagnosis** → chạy repeated test ở same commit. **Fix** → ổn định test, pin dependencies; dùng `git bisect skip` cho untestable commits khi cần. **Verification** → checkout culprit parent = good, culprit = bad nhiều lần.

## 7. Common mistakes

Chọn “good” chưa thật sự good; bisect flaky test; quên reset; sửa working tree trong lúc bisect; coi culprit commit là root cause mà không đọc context/diff.

## 8. Alternatives

`git log`, blame và manual diff tốt khi suspect range rất nhỏ. APM/deployment correlation giúp xác định release window trước. Revert có thể là mitigation nhanh hơn investigation trong incident.

## 9. Trade-offs

### Advantages

Giảm search space nhanh, evidence-driven và dễ automate.

### Costs / Risks

Cần reproducible predicate; historical commits có thể không build hoặc phụ thuộc environment cũ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết xác định known-good và known-bad commit.

### Middle

Dùng bisect với automated regression test.

### Senior

Ổn định reproduction, xử lý skipped commits và xác nhận causal mechanism sau khi tìm culprit.

### Technical Lead / Architect

Xây release/test practices giúp regression có thể bisect được: reproducible builds, deterministic tests và traceable deployments.

## 11. Key takeaway

- `git bisect` mạnh nhất khi reproduction deterministic.
- Nó tìm transition commit, chưa tự chứng minh root cause.
- Reproducible build/test infrastructure trực tiếp cải thiện incident investigation.
