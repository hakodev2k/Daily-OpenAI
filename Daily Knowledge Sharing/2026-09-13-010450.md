# 1. .NET GC Large Object Heap và pinned memory: hiểu fragmentation, allocation pressure và vì sao “còn RAM” không đồng nghĩa process khỏe

## 1. What is it?

Trong .NET, Garbage Collector quản lý managed heap theo generations. Những object lớn — theo ngưỡng runtime hiện hành thường khoảng 85 KB trở lên — được phân bổ vào **Large Object Heap (LOH)** thay vì đi qua Gen 0 như object nhỏ.

Mental model quan trọng:

```text
Small short-lived objects -> Gen 0 -> Gen 1 -> Gen 2
Large objects             -> LOH --------------------^
```

LOH tồn tại vì copy các object lớn qua nhiều generation rất tốn CPU và memory bandwidth. Nhưng đổi lại, workload tạo/xóa nhiều buffer lớn có thể gây fragmentation và Gen 2 collection đắt hơn.

`pinned` object là object mà GC tạm thời không được phép di chuyển, thường vì native code hoặc I/O cần địa chỉ memory ổn định. Pinning kéo dài có thể làm GC khó compact heap hiệu quả.

## 2. Why does it exist?

Nếu GC compact mọi object lớn giống object nhỏ, một request upload 20 MB hoặc serialization buffer lớn có thể khiến runtime liên tục copy hàng chục MB chỉ để thu hồi memory. LOH giảm chi phí đó bằng cách xử lý large allocation khác với short-lived allocation.

Pinning tồn tại để managed code có thể tương tác an toàn với native APIs, sockets, buffers hoặc interop cần pointer ổn định.

Vấn đề bắt đầu khi application coi large allocation là “bình thường” trong hot path: throughput giảm, GC pause tăng và process có thể chịu memory pressure dù working set chưa chạm giới hạn máy.

## 3. How does it work?

Một large object thường đi thẳng vào LOH. LOH được thu gom cùng các full/Gen 2 GC. Khi object chết, vùng memory được tái sử dụng, nhưng heap không nhất thiết luôn được compact như small-object heap.

Ví dụ:

```text
Before:
[A 10MB][B 20MB][C 10MB][D 20MB]

B và D chết:
[A 10MB][ free 20MB ][C 10MB][ free 20MB ]
```

Tổng free = 40 MB, nhưng một allocation liên tục 30 MB vẫn có thể không khớp tốt với các hole hiện có. Runtime có nhiều chiến lược quản lý heap, nhưng fragmentation vẫn là signal cần điều tra.

Pinned object tạo thêm “điểm cố định” mà compaction phải đi vòng quanh.

## 4. Practical implementation

Đừng tạo buffer lớn mới cho mỗi operation nếu có thể reuse an toàn. Với byte buffers, `ArrayPool<T>` thường là lựa chọn tốt:

```csharp
using System.Buffers;

public async Task CopyAsync(Stream input, Stream output, CancellationToken ct)
{
    byte[] buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);

    try
    {
        int read;
        while ((read = await input.ReadAsync(buffer.AsMemory(0, buffer.Length), ct)) > 0)
        {
            await output.WriteAsync(buffer.AsMemory(0, read), ct);
        }
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
    }
}
```

64 KB nằm dưới LOH threshold và buffer được tái sử dụng. Không phải lúc nào cũng nên “né LOH”; mục tiêu là tránh allocation churn không cần thiết.

Khi điều tra production, xem các counters như allocation rate, Gen 2 collections, heap size và LOH size bằng `dotnet-counters`, Application Insights hoặc OpenTelemetry runtime metrics.

## 5. Real production scenario

Một API export báo cáo lấy 100.000 rows, serialize toàn bộ thành `byte[]`, rồi trả file. Mỗi request tạo 30–100 MB buffers. Khi 20 người export cùng lúc:

```text
20 requests
  -> large result objects
  -> large serialization buffers
  -> LOH pressure
  -> more full GC
  -> longer pauses
  -> p95/p99 latency tăng
```

Giải pháp tốt hơn có thể là streaming response, chunked processing, temporary storage hoặc background export tùy business flow.

## 6. Failure scenario & troubleshooting

**Symptom:** API thỉnh thoảng latency tăng từ 300 ms lên nhiều giây, CPU không luôn 100%, memory dao động cao.

**Evidence:** Gen 2 GC tăng, LOH size lớn, allocation rate spike tương ứng endpoint export.

**Hypothesis:** large allocation churn ép full GC thường xuyên.

**Diagnosis:** profile allocation bằng `dotnet-trace`, PerfView hoặc profiler; xác định type/buffer nào chiếm LOH.

**Fix:** stream dữ liệu, pool buffer, tránh materialize toàn bộ payload, giới hạn concurrency.

**Verification:** so lại Gen 2 count, allocation rate và p95/p99 dưới cùng load test.

## 7. Common mistakes

- Thấy memory cao rồi gọi `GC.Collect()` thủ công trong request path.
- Chỉ nhìn working set mà không nhìn allocation rate và GC pauses.
- Dùng `ArrayPool<T>` nhưng quên trả buffer trong `finally`.
- Pool object chứa sensitive data nhưng không cân nhắc clearing.
- Giữ pinned buffers quá lâu.
- Tối ưu mọi allocation nhỏ trước khi đo bottleneck thật.

## 8. Alternatives

- **Streaming:** tốt nhất khi có thể xử lý dữ liệu tuần tự.
- **ArrayPool<T>:** phù hợp buffer tạm có kích thước lặp lại.
- **MemoryPool<T>:** hữu ích cho pipeline/buffer ownership phức tạp hơn.
- **Materialize toàn bộ:** vẫn hợp lý nếu payload nhỏ, code đơn giản và memory budget rõ ràng.

## 9. Trade-offs

### Advantages

- Pooling/streaming giảm allocation pressure và peak memory.
- Ít full GC hơn giúp tail latency ổn định hơn.

### Costs / Risks

- Pooling thêm ownership complexity.
- Streaming có thể làm error handling khó hơn sau khi response đã bắt đầu.
- Reused buffers có thể gây data leak nếu xử lý sensitive data sai.
- Micro-optimization khi chưa đo có thể làm code khó đọc mà không tạo giá trị.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu heap, generations và large allocation không “free” chỉ vì GC sẽ tự dọn.

### Middle

Biết profile allocation, dùng streaming/pooling đúng chỗ và tránh giữ buffers không cần thiết.

### Senior

Phân biệt memory leak, allocation churn, fragmentation và GC pressure; liên hệ chúng với p95/p99 latency.

### Technical Lead / Architect

Quyết định workload nào nên synchronous streaming, workload nào nên background export; đặt memory/concurrency budget và observability thay vì chỉ yêu cầu “optimize GC”.

## 11. Key takeaway

- LOH giải quyết chi phí copy large objects nhưng large-allocation churn vẫn có giá vận hành.
- Điều tra bằng allocation/GC evidence, không đoán từ RAM usage.
- Streaming và buffer reuse thường đáng giá hơn việc ép GC thủ công.

# 2. ASP.NET Core graceful shutdown: drain request, `ApplicationStopping` và tránh mất work khi App Service/Kubernetes thay instance

## 1. What is it?

Graceful shutdown là quá trình application **ngừng nhận work mới, cho work đang chạy cơ hội hoàn thành trong một khoảng thời gian, cleanup resource rồi mới terminate process**.

Mental model:

```text
Running
  -> stop signal
  -> stop accepting new work
  -> drain in-flight work
  -> stop background services
  -> flush/cleanup
  -> process exits
```

Trong ASP.NET Core, host phát các lifetime signals và truyền cancellation tới hosted services. Đây là protocol shutdown, không phải đảm bảo mọi request sẽ hoàn thành vô hạn.

## 2. Why does it exist?

Production instance bị restart vì deployment, autoscaling, VM maintenance, App Service recycle hoặc Kubernetes rolling update. Nếu process chết ngay:

- request đang ghi database có thể bị ngắt;
- background work có thể mất;
- message có thể chưa settle;
- telemetry/log buffer có thể chưa flush;
- caller nhận connection reset thay vì response rõ ràng.

Graceful shutdown biến “process sắp biến mất” thành một trạng thái có thể xử lý.

## 3. How does it work?

Ở mức host:

```text
SIGTERM / platform stop
        |
        v
ASP.NET Core Host
        |
        +--> ApplicationStopping
        +--> CancellationToken cho BackgroundService
        +--> server stop accepting/draining
        |
        v
Shutdown timeout
        |
        v
Process exit
```

Kubernetes còn có readiness và termination grace period. Một pod nên bị loại khỏi traffic trước khi process bị kill, nhưng cấu hình platform và application phải tương thích.

## 4. Practical implementation

Một `BackgroundService` cần tôn trọng `stoppingToken`:

```csharp
public sealed class InvoiceWorker : BackgroundService
{
    private readonly ILogger<InvoiceWorker> _logger;

    public InvoiceWorker(ILogger<InvoiceWorker> logger)
        => _logger = logger;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await ProcessNextBatchAsync(stoppingToken);
        }
    }

    public override async Task StopAsync(CancellationToken cancellationToken)
    {
        _logger.LogInformation("Invoice worker is draining");
        await base.StopAsync(cancellationToken);
    }
}
```

Không nuốt `OperationCanceledException` rồi tiếp tục loop vô hạn. Với message consumer, chỉ complete/settle message sau khi business transaction thực sự thành công.

## 5. Real production scenario

Một App Service có 4 instances đang chạy API và `BackgroundService`. Deployment slot swap hoặc scale-in loại một instance.

Nếu worker giữ 20 jobs trong memory và coi dequeue là “đã nhận trách nhiệm”, shutdown có thể làm mất jobs. Nếu queue broker vẫn sở hữu message cho tới settlement, uncompleted message có thể được redeliver sau lock expiry.

Kiến trúc đúng phụ thuộc ownership của work, không chỉ `StopAsync`.

## 6. Failure scenario & troubleshooting

**Symptom:** sau deployment có một số job thiếu hoặc message xử lý hai lần.

**Evidence:** logs có shutdown event; message lock hết hạn; instance bị terminate trước khi batch hoàn thành.

**Hypothesis:** shutdown timeout ngắn hơn processing time hoặc worker settle message quá sớm.

**Diagnosis:** correlate deployment timestamp, host lifetime logs, broker delivery count và business transaction.

**Fix:** rút ngắn batch, propagate cancellation, settle sau commit, dùng durable queue, tăng grace period khi hợp lý.

**Verification:** chạy controlled rolling deployment trong load test và xác nhận không mất work; duplicate nếu có phải được idempotent handling.

## 7. Common mistakes

- Fire-and-forget bằng `Task.Run` từ controller rồi kỳ vọng shutdown sẽ chờ.
- Ignore `CancellationToken` ở DB/HTTP calls.
- Dùng `ApplicationStopping` để thực hiện work dài hàng phút.
- Cho scheduled job chạy trong mọi replica mà không có coordination.
- Coi graceful shutdown là exactly-once guarantee.

## 8. Alternatives

- **Durable queue + Worker:** tốt hơn cho work cần đảm bảo tồn tại qua restart.
- **Azure Functions:** phù hợp event-driven/background workloads có execution model rõ.
- **In-process BackgroundService:** đơn giản cho lightweight work khi durability requirement thấp hoặc nguồn work đã durable.

## 9. Trade-offs

### Advantages

- Giảm request interruption và work loss trong deployment/scale.
- Tạo lifecycle rõ ràng cho resource cleanup.

### Costs / Risks

- Drain lâu làm deployment chậm.
- Grace period quá dài không sửa được worker thiết kế sai.
- Shutdown vẫn có thể bị hard kill; hệ thống phải chịu được interruption.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process có lifecycle và cancellation là cooperative.

### Middle

Propagate token, viết hosted service dừng đúng cách và test shutdown.

### Senior

Thiết kế idempotency/durability để hard termination không làm corrupt business state.

### Technical Lead / Architect

Chọn boundary giữa in-process work và durable asynchronous processing; đồng bộ app timeout với platform termination behavior.

## 11. Key takeaway

- Graceful shutdown là bounded coordination, không phải lời hứa process sẽ sống tới khi mọi thứ xong.
- Durable work phải có durable ownership và idempotency.
- Deployment reliability cần test cả shutdown path, không chỉ startup path.

# 3. EF Core Change Tracker, identity resolution và batch processing: tránh memory phình khi xử lý hàng trăm nghìn entities

## 1. What is it?

EF Core `ChangeTracker` giữ thông tin về entity instance mà `DbContext` đang theo dõi: state, original values, relationships và identity map.

Mental model:

```text
Database row Id=42
      |
      v
DbContext identity map
      |
      +--> một tracked object instance cho Id=42
```

Tracking rất hữu ích cho unit-of-work ngắn. Nhưng `DbContext` sống quá lâu và liên tục query/update hàng trăm nghìn records có thể tích lũy tracked entities, khiến memory và `DetectChanges` cost tăng.

## 2. Why does it exist?

ORM cần biết entity nào mới, sửa hoặc xóa để tạo SQL đúng khi `SaveChanges`. Identity resolution cũng giúp cùng một database row không xuất hiện thành nhiều object tracked khác nhau trong cùng context, giữ navigation consistency.

Nếu không tracking, developer phải tự quản original values, relationship fixup và mutation state.

## 3. How does it work?

Khi query tracking:

```text
SQL row
 -> materializer
 -> identity map lookup
 -> existing instance? reuse
 -> otherwise create + track
```

`SaveChanges` xem tracked entries để xác định `Added`, `Modified`, `Deleted`, `Unchanged`.

Một batch processor dùng cùng một context qua 10.000 iterations có thể biến context thành một cache vô tình.

## 4. Practical implementation

Với batch update, giữ unit-of-work bounded:

```csharp
const int batchSize = 500;

while (true)
{
    var orders = await db.Orders
        .Where(x => x.Status == OrderStatus.Pending)
        .OrderBy(x => x.Id)
        .Take(batchSize)
        .ToListAsync(ct);

    if (orders.Count == 0)
        break;

    foreach (var order in orders)
        order.MarkExpiredIfNeeded(clock.UtcNow);

    await db.SaveChangesAsync(ct);
    db.ChangeTracker.Clear();
}
```

Nếu operation có thể diễn đạt thành set-based update, `ExecuteUpdateAsync` có thể tốt hơn vì không cần materialize/tracking từng row. Nhưng domain logic phức tạp có thể vẫn cần entities.

## 5. Real production scenario

Nightly worker rà 2 triệu subscription để expire. Version đầu inject một scoped `DbContext` cho toàn bộ job kéo dài 40 phút. Mỗi batch query thêm entities vào tracker; memory tăng dần và `SaveChanges` ngày càng chậm.

Bằng cách chia transaction/unit-of-work theo batch, clear tracker hoặc tạo context per batch, memory trở nên bounded.

## 6. Failure scenario & troubleshooting

**Symptom:** worker bắt đầu nhanh nhưng sau 20 phút chậm dần; memory tăng tuyến tính.

**Evidence:** số `ChangeTracker.Entries()` tăng liên tục; heap profile chứa nhiều entity objects/internal tracking entries.

**Hypothesis:** long-lived context giữ toàn bộ entity graph.

**Diagnosis:** log batch duration và tracked-entry count; profile heap.

**Fix:** context per batch, `ChangeTracker.Clear()`, `AsNoTracking` cho read-only path hoặc set-based update.

**Verification:** tracked count trở về bounded range và batch latency ổn định.

## 7. Common mistakes

- Dùng singleton `DbContext`.
- Dùng `AsNoTracking` rồi kỳ vọng mutate object và `SaveChanges` tự phát hiện.
- Gọi `ChangeTracker.Clear()` trước khi transaction cần state chưa save.
- Load full entity graph cho batch chỉ để update một field.
- Cho một transaction khổng lồ bao toàn bộ job.

## 8. Alternatives

- **Tracked entities:** tốt cho rich domain mutation trong bounded unit-of-work.
- **`AsNoTracking`:** tốt cho read-only projections.
- **`AsNoTrackingWithIdentityResolution`:** read-only nhưng cần deduplicate object instances trong result graph.
- **`ExecuteUpdate/Delete`:** tốt cho set-based mutation đơn giản.
- **Raw SQL/bulk library:** có thể cần cho extreme throughput nhưng đổi lấy abstraction/consistency complexity.

## 9. Trade-offs

### Advantages

- Tracking làm CRUD/domain mutation tự nhiên và giữ relationship consistency.

### Costs / Risks

- Memory tăng theo số tracked entities.
- Long-lived context tạo stale state và khó reasoning về transaction.
- Bypass tracker bằng bulk operations bỏ qua một số in-memory domain behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbContext` là unit-of-work, không phải global database singleton.

### Middle

Chọn tracking/no-tracking, projection và batch size phù hợp.

### Senior

Nhận diện tracker overhead qua telemetry/profiling và chọn set-based vs entity-based mutation theo semantics.

### Technical Lead / Architect

Đặt transaction/unit-of-work boundary theo business invariant; không ép mọi batch workload đi qua cùng abstraction CRUD.

## 11. Key takeaway

- `ChangeTracker` mang lại correctness tiện lợi nhưng state của nó phải được bounded.
- Long-running batch cần explicit unit-of-work strategy.
- Chọn entity tracking hay set-based update dựa trên business semantics và measured cost.

# 4. SQL Server deadlock: đọc deadlock graph, phân biệt blocking với deadlock và sửa access pattern thay vì chỉ retry

## 1. What is it?

**Blocking** xảy ra khi transaction A giữ lock và transaction B phải chờ. **Deadlock** xảy ra khi có vòng chờ mà không transaction nào tự tiến tiếp được:

```text
Transaction A holds Row 1 -> waits Row 2
Transaction B holds Row 2 -> waits Row 1
```

SQL Server phát hiện cycle và chọn một transaction làm deadlock victim để rollback.

## 2. Why does it exist?

Locks bảo vệ consistency. Khi nhiều transaction đồng thời cần các resources theo thứ tự khác nhau, circular wait có thể hình thành. Deadlock detection cho database một cách thoát khỏi trạng thái đó thay vì để cả hai chờ vô hạn.

Retry có thể làm request thành công lần sau, nhưng nếu access pattern luôn đối nghịch dưới load, retry chỉ che nguyên nhân và tăng pressure.

## 3. How does it work?

Ví dụ hai code path:

```text
Path A: UPDATE Orders -> UPDATE Inventory
Path B: UPDATE Inventory -> UPDATE Orders
```

Hai transaction chạy đồng thời có thể mỗi bên giữ lock ở bảng đầu rồi chờ bảng còn lại.

Deadlock graph cho biết processes, resources, lock mode, victim và SQL statements liên quan. Đây là evidence quan trọng hơn việc đoán “database đang chậm”.

## 4. Practical implementation

Một fix phổ biến là chuẩn hóa thứ tự access:

```sql
BEGIN TRANSACTION;

-- Luôn lock Order trước
SELECT Id
FROM dbo.Orders WITH (UPDLOCK)
WHERE Id = @OrderId;

-- Sau đó mới update Inventory
UPDATE dbo.Inventory
SET Quantity = Quantity - @Quantity
WHERE ProductId = @ProductId;

UPDATE dbo.Orders
SET Status = 'Confirmed'
WHERE Id = @OrderId;

COMMIT;
```

Hint không phải default recommendation; ví dụ này minh họa explicit lock ordering. Thực tế nên xem execution plan, indexes, isolation và transaction scope trước.

Ở .NET, retry deadlock có thể hợp lý nếu operation idempotent và retry count bounded.

## 5. Real production scenario

Checkout API update `Orders` rồi `Inventory`. Một stock reconciliation worker update `Inventory` rồi ghi `Orders`. Bình thường không thấy lỗi; giờ cao điểm concurrency tăng và deadlock xuất hiện.

Sửa đúng có thể là thống nhất access ordering, giảm transaction duration, thêm index để query lock ít rows hơn, hoặc tách workflow tùy invariant.

## 6. Failure scenario & troubleshooting

**Symptom:** ngẫu nhiên có SQL exception deadlock victim dù CPU/database latency tổng thể bình thường.

**Evidence:** Extended Events deadlock graph chỉ ra hai statements và resources.

**Hypothesis:** inconsistent resource ordering hoặc range/lookup locks lớn hơn dự kiến.

**Diagnosis:** đọc deadlock XML/graph, execution plan, index usage và transaction scope.

**Fix:** consistent ordering, shorten transaction, cải thiện access path; chỉ thêm retry sau khi semantics an toàn.

**Verification:** stress test cùng concurrency và theo dõi deadlock count, transaction latency.

## 7. Common mistakes

- Gọi mọi lock wait là deadlock.
- Chỉ tăng command timeout.
- Retry vô hạn.
- Thêm `NOLOCK` để “fix deadlock”, đổi correctness lấy dirty/inconsistent reads.
- Mở transaction rồi gọi remote API trong khi giữ DB locks.
- Thêm index không dựa trên execution plan.

## 8. Alternatives

- **Consistent pessimistic locking:** phù hợp invariant cần serialization rõ.
- **Optimistic concurrency:** tốt khi conflict hiếm và retry business-level khả thi.
- **Snapshot-based isolation:** giảm reader/writer blocking trong một số workload nhưng có tempdb/versioning cost.
- **Queue/serialization theo business key:** có thể giảm concurrent writes nhưng tăng latency/architecture complexity.

## 9. Trade-offs

### Advantages

- Locking mạnh bảo vệ transactional correctness.
- Retry bounded giúp hấp thụ transient deadlock còn sót lại.

### Costs / Risks

- Lock rộng/lâu giảm concurrency.
- Snapshot isolation tăng row-version storage.
- Serialization qua queue giảm throughput per key và thêm operational component.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt blocking, timeout và deadlock.

## 11. Key takeaway

- Deadlock là cycle của lock dependencies, không phải “query chậm”.
- Deadlock graph là evidence chính để chẩn đoán.

# 5. Redis cache stampede: single-flight, TTL jitter và stale-while-revalidate để bảo vệ database khi hot key hết hạn

## 1. What is it?

Cache stampede xảy ra khi nhiều requests cùng lúc thấy một hot cache key bị miss/expire và tất cả cùng truy vấn source of truth.

```text
10,000 clients
     |
     v
Redis key expired
     |
     +--> DB
     +--> DB
     +--> DB
     ...
```

Cache vốn để giảm tải database, nhưng đúng thời điểm expiry nó có thể khuếch đại load.

## 2. Why does it exist?

TTL là cách đơn giản để giới hạn staleness. Tuy nhiên, nếu nhiều keys có cùng TTL hoặc một hot key phục vụ lượng traffic lớn, expiry tạo synchronization point. Một cache miss đơn lẻ rẻ; hàng nghìn miss đồng thời có thể làm DB chậm, khiến requests giữ connection lâu hơn và tạo cascade failure.

## 3. How does it work?

Ba kỹ thuật thường gặp:

- **Single-flight/request coalescing:** chỉ một caller refresh key; callers khác chờ/share kết quả.
- **TTL jitter:** thêm random variation để nhiều keys không expire cùng thời điểm.
- **Stale-while-revalidate:** tạm phục vụ dữ liệu cũ trong cửa sổ cho phép, đồng thời refresh nền.

Distributed system cần phân biệt single-flight **trong một process** và coordination **giữa nhiều instances**.

## 4. Practical implementation

Một local single-flight đơn giản bằng `SemaphoreSlim` per key có thể đủ trong một instance; với multi-instance cần cân nhắc distributed coordination hoặc chấp nhận mỗi instance một refresh.

TTL jitter:

```csharp
var baseTtl = TimeSpan.FromMinutes(5);
var jitter = TimeSpan.FromSeconds(Random.Shared.Next(0, 45));

await cache.SetStringAsync(
    key,
    json,
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = baseTtl + jitter
    },
    ct);
```

Không dùng một global distributed lock cho mọi cache key; lock granularity phải theo key và có timeout/failure policy rõ.

## 5. Real production scenario

Product detail page có 5.000 requests/s cho promotion key. TTL = 10 phút. Khi key hết hạn, hàng nghìn requests query SQL/API pricing cùng lúc. DB latency tăng, connection pool đầy, API bắt đầu timeout.

Một giải pháp có thể là serve stale tối đa 30 giây, một refresher per key và TTL jitter cho các related keys.

## 6. Failure scenario & troubleshooting

**Symptom:** cứ gần chu kỳ cố định, DB QPS và latency spike dù traffic người dùng gần như ổn định.

**Evidence:** Redis miss rate spike trùng TTL expiration; dependency trace cho thấy cùng query/key lặp lại hàng nghìn lần.

**Hypothesis:** synchronized cache expiry.

**Diagnosis:** correlate cache hit/miss, key TTL, DB QPS, hot keys và request concurrency.

**Fix:** coalescing, jitter, stale policy hoặc pre-refresh tùy freshness requirement.

**Verification:** load test qua nhiều TTL cycles; DB QPS không còn spike sắc.

## 7. Common mistakes

- Đặt cùng TTL cho toàn bộ keys khi warm cache hàng loạt.
- Dùng distributed lock nhưng không có lock expiry.
- Khi Redis lỗi, cho mọi request fallback thẳng DB không giới hạn.
- Cache dữ liệu authorization-sensitive bằng key thiếu tenant/user dimension.
- Cho stale data vô hạn mà không có business agreement.

## 8. Alternatives

- **No cache:** đúng nếu database đủ nhanh và scale đơn giản hơn.
- **IMemoryCache:** nhanh, đơn giản nhưng per-instance và không shared.
- **Distributed Redis:** shared state nhưng thêm network/dependency.
- **CDN/edge cache:** phù hợp HTTP content có cache semantics rõ.
- **Materialized/read model:** phù hợp khi read computation bản chất quá đắt cho request-time.

## 9. Trade-offs

### Advantages

- Stampede protection giữ dependency load bounded.
- Stale-while-revalidate cải thiện availability/tail latency.

### Costs / Risks

- Stale data là correctness decision.
- Distributed locks thêm failure mode.
- Coalescing khiến callers cùng phụ thuộc một refresh chậm.
- Cache logic phức tạp có thể khó hơn việc scale source of truth.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss và TTL không chỉ ảnh hưởng performance của Redis mà cả downstream.

### Middle

Implement cache-aside, jitter và metrics hit/miss đúng key scope.

### Senior

Thiết kế behavior khi Redis unavailable, refresh chậm và hot key expire dưới load.

### Technical Lead / Architect

Quyết định freshness budget, cache ownership, fallback capacity và khi nào nên bỏ cache để giảm operational complexity.

## 11. Key takeaway

- Cache expiry có thể tạo load spike lớn hơn traffic thực.
- Stampede protection phải xét multi-instance và downstream capacity.
- Staleness là business/correctness trade-off, không chỉ kỹ thuật performance.

# 6. Hexagonal Architecture với third-party integration: Ports & Adapters để cô lập vendor contract mà không biến hệ thống thành abstraction factory

## 1. What is it?

Hexagonal Architecture tổ chức dependency quanh application/domain boundary. **Port** mô tả capability mà core cần hoặc cung cấp; **Adapter** kết nối capability đó với HTTP, database, message broker hoặc vendor SDK.

```text
        HTTP API adapter
              |
              v
      +----------------+
      | Application    |
      |   Ports        |
      +----------------+
          ^        |
          |        v
      SQL adapter  Vendor adapter
```

Mục tiêu là cô lập thay đổi tại system boundary, không phải tạo interface cho mọi class.

## 2. Why does it exist?

Third-party APIs thay đổi schema, auth, timeout behavior và availability. Nếu vendor DTOs lan vào domain/application, việc đổi provider hoặc version có thể chạm hàng chục layers.

Port giúp application nói bằng ngôn ngữ của nó: “lấy review summary”, “reserve inventory”, “calculate shipping quote” thay vì vendor-specific endpoints.

## 3. How does it work?

Application định nghĩa contract theo use case:

```csharp
public interface IShippingQuoteProvider
{
    Task<ShippingQuote> GetQuoteAsync(
        ShipmentRequest request,
        CancellationToken ct);
}
```

Infrastructure adapter map model nội bộ sang vendor request, gọi HTTP API, validate response rồi map trở lại.

Dependency direction:

```text
Application -> port abstraction
Infrastructure adapter -> Application contract
Vendor SDK/HTTP stays outside core
```

## 4. Practical implementation

```csharp
public sealed class AcmeShippingAdapter : IShippingQuoteProvider
{
    private readonly HttpClient _http;

    public AcmeShippingAdapter(HttpClient http) => _http = http;

    public async Task<ShippingQuote> GetQuoteAsync(
        ShipmentRequest request,
        CancellationToken ct)
    {
        var vendorRequest = new AcmeQuoteRequest(
            request.PostalCode,
            request.WeightKg);

        using var response = await _http.PostAsJsonAsync(
            "/v2/quotes", vendorRequest, ct);

        response.EnsureSuccessStatusCode();

        var payload = await response.Content
            .ReadFromJsonAsync<AcmeQuoteResponse>(cancellationToken: ct)
            ?? throw new InvalidOperationException("Empty quote response");

        return new ShippingQuote(payload.Price, payload.Currency);
    }
}
```

Port nên phản ánh semantics application cần, không copy 1:1 toàn bộ vendor API.

## 5. Real production scenario

E-commerce dùng provider A cho review ratings và provider B dự phòng. UI/application chỉ cần `ReviewSummary`. Nếu domain chứa `ProviderARatingDto`, mọi consumer bị coupling vào provider A.

Adapter boundary cho phép normalize provider-specific response và fallback policy ở integration layer/application policy phù hợp.

## 6. Failure scenario & troubleshooting

**Symptom:** vendor đổi field `score` thành nullable hoặc thêm rate limit; nhiều service nội bộ cùng lỗi deserialize.

**Evidence:** vendor DTO được dùng xuyên application layers.

**Hypothesis:** external contract không được cô lập tại boundary.

**Diagnosis:** trace dependency graph và nơi vendor model xuất hiện.

**Fix:** đưa mapping vào adapter, tạo application-owned model, thêm contract/integration tests.

**Verification:** simulate vendor schema/timeout behavior và kiểm tra blast radius chỉ nằm ở adapter.

## 7. Common mistakes

- Tạo `IOrderService`, `IOrderRepository`, `IWhatever` chỉ vì “Hexagonal cần interface”.
- Port mirror toàn bộ vendor SDK nên abstraction không tạo isolation thật.
- Che mất capability quan trọng bằng lowest-common-denominator abstraction.
- Đặt retry/timeout ở nhiều layers dẫn tới retry multiplication.
- Cho adapter quyết định business rule đáng lẽ thuộc application/domain.

## 8. Alternatives

- **Simple layered architecture:** tốt khi integration đơn giản và change risk thấp.
- **Anti-Corruption Layer:** DDD-oriented boundary khi model bên ngoài khác sâu với domain.
- **Direct SDK usage:** hợp lý cho internal tool nhỏ hoặc provider rất ổn định nếu abstraction chưa mang giá trị.

## 9. Trade-offs

### Advantages

- Cô lập vendor churn.
- Test application logic dễ hơn mà không cần remote service.
- Dependency direction rõ.

### Costs / Risks

- Thêm mapping/contracts và code ceremony.
- Abstraction sai có thể che vendor features cần thiết.
- Với hệ thống nhỏ, layer thêm có thể không đáng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu boundary giữa business code và external infrastructure.

### Middle

Implement adapter, mapping, timeout/error handling và integration tests.

### Senior

Thiết kế port theo application semantics, tránh abstraction leakage và retry policy chồng chéo.

### Technical Lead / Architect

Quyết định boundary nào thực sự cần isolation dựa trên change frequency, business criticality và migration cost; không áp pattern đồng loạt.

## 11. Key takeaway

- Ports & Adapters là về dependency boundary và change isolation, không phải số lượng interfaces.
- External models nên dừng ở integration boundary khi chúng không thuộc ubiquitous language của application.
- Pattern chỉ đáng dùng khi cost của coupling thực sự lớn hơn cost của abstraction.

# 7. Azure Service Bus Dead-Letter Queue: poison message, delivery count và quy trình replay an toàn thay vì “retry mãi”

## 1. What is it?

Dead-Letter Queue (DLQ) là subqueue giữ messages không thể xử lý thành công theo policy hiện tại. Message không “biến mất”; nó được tách khỏi active queue để consumer tiếp tục xử lý healthy traffic.

```text
Queue -> Consumer -> success -> Complete
                  -> transient -> retry/redelivery
                  -> poison/max delivery -> DLQ
```

DLQ là operational workflow boundary, không phải thùng rác tự dọn.

## 2. Why does it exist?

Một malformed message hoặc business data không hợp lệ có thể fail mỗi lần delivery. Nếu retry vô hạn, poison message tiêu tốn compute, tạo log noise, tăng queue latency và có thể chặn ordered/session workloads.

DLQ cho phép quarantine lỗi cần con người hoặc remediation riêng.

## 3. How does it work?

Azure Service Bus dùng peek-lock phổ biến cho reliable processing. Consumer nhận message với lock, xử lý rồi `Complete`. Nếu abandon/lock expiry/failure lặp lại, `DeliveryCount` tăng. Khi vượt `MaxDeliveryCount`, message có thể vào DLQ.

Một số lỗi application có thể dead-letter chủ động với reason/description rõ để điều tra.

At-least-once delivery vẫn áp dụng: duplicate processing có thể xảy ra, vì vậy consumer cần idempotency.

## 4. Practical implementation

```csharp
processor.ProcessMessageAsync += async args =>
{
    try
    {
        var command = args.Message.Body.ToObjectFromJson<CreateInvoice>();
        await handler.HandleAsync(command, args.CancellationToken);
        await args.CompleteMessageAsync(args.Message, args.CancellationToken);
    }
    catch (ValidationException ex)
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            deadLetterReason: "InvalidContract",
            deadLetterErrorDescription: ex.Message,
            cancellationToken: args.CancellationToken);
    }
};
```

Không dead-letter mọi exception. Timeout transient có thể retry; schema/business-invalid message có thể không bao giờ tự lành.

## 5. Real production scenario

Order service publish event version mới nhưng một consumer cũ chưa support field/value mới. Messages liên tục fail deserialize. Nếu retry mỗi vài giây, backlog và error volume tăng mạnh.

DLQ giữ affected messages; team deploy compatible consumer, kiểm tra replay safety rồi resubmit có kiểm soát.

## 6. Failure scenario & troubleshooting

**Symptom:** active queue ổn nhưng DLQ count tăng đều sau deployment.

**Evidence:** dead-letter reason, application exception, message schema/version và deployment timestamp.

**Hypothesis:** contract incompatibility hoặc deterministic business validation failure.

**Diagnosis:** inspect representative messages, correlate producer/consumer versions, không replay ngay.

**Fix:** sửa consumer/producer contract; tạo replay tool có throttling và idempotency checks.

**Verification:** replay sample/canary trước, theo dõi DLQ/active queue/error rate rồi mới replay bulk.

## 7. Common mistakes

- Không alert DLQ count.
- Tự động replay DLQ vô hạn về main queue.
- Log full message có PII/secrets.
- Complete message trước khi DB transaction xong.
- Coi `MaxDeliveryCount` là substitute cho retry classification.
- Không lưu idempotency key nên replay tạo duplicate side effects.

## 8. Alternatives

- **Retry queue/delayed retry:** tốt cho transient lỗi cần backoff dài.
- **Topic/subscription filters:** ngăn consumer nhận message không liên quan.
- **Schema registry/contract validation:** giảm poison message trước runtime.
- **Manual remediation:** phù hợp rare/high-risk business messages.

## 9. Trade-offs

### Advantages

- Poison message không làm nghẽn healthy traffic.
- Giữ evidence để điều tra và khôi phục.

### Costs / Risks

- DLQ cần monitoring, tooling và ownership.
- Replay sai có thể tạo duplicate business effects.
- Max delivery quá thấp có thể quarantine transient failures quá sớm; quá cao gây retry storm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu complete/abandon/dead-letter và at-least-once delivery.

### Middle

Phân loại transient vs deterministic errors và ghi dead-letter reason hữu ích.

### Senior

Thiết kế idempotent consumer, replay flow, alerting và contract compatibility.

### Technical Lead / Architect

Xác định ownership của DLQ, SLO cho backlog, retention, security và operational runbook; quyết định khi nào cần retry queue riêng.

## 11. Key takeaway

- DLQ là quarantine + recovery workflow, không phải nơi “ném lỗi”.
- Retry chỉ phù hợp failure có khả năng tự hồi phục.
- Replay phải idempotent, observable và có throttling.

# 8. Zero-downtime database migration bằng Expand–Migrate–Contract: deploy schema và application độc lập mà vẫn giữ backward compatibility

## 1. What is it?

Expand–Migrate–Contract là chiến lược thay đổi database schema qua nhiều bước tương thích thay vì đổi schema và code theo kiểu “big bang”.

```text
Expand:   thêm schema mới nhưng giữ schema cũ
Migrate:  code/data chuyển dần sang schema mới
Contract: xóa schema cũ khi không consumer nào còn dùng
```

Đây là backward-compatibility strategy cho deployment, không phải tool-specific migration command.

## 2. Why does it exist?

Trong rolling deployment, version cũ và mới của application có thể chạy đồng thời. Nếu migration rename/drop column ngay, old instances vẫn query schema cũ và fail.

Rollback cũng trở nên nguy hiểm nếu database đã irreversibly thay đổi.

Expand–Contract cho phép app versions overlap an toàn.

## 3. How does it work?

Ví dụ rename `FullName` thành `DisplayName`:

1. **Expand:** thêm nullable `DisplayName`, chưa drop `FullName`.
2. Deploy code có thể đọc fallback và ghi cả hai hoặc có compatibility strategy.
3. **Migrate:** backfill dữ liệu cũ.
4. Deploy version chỉ đọc `DisplayName`.
5. Xác nhận không còn old instances/jobs/report queries.
6. **Contract:** drop `FullName` ở release sau.

Mỗi bước phải có observability và rollback plan.

## 4. Practical implementation

Migration expand:

```sql
ALTER TABLE dbo.Customers
ADD DisplayName nvarchar(200) NULL;
```

Backfill theo batch để tránh transaction/lock quá lớn:

```sql
WHILE 1 = 1
BEGIN
    UPDATE TOP (1000) dbo.Customers
    SET DisplayName = FullName
    WHERE DisplayName IS NULL;

    IF @@ROWCOUNT = 0 BREAK;
END
```

Sau khi mọi writer đã populate field mới và backfill xong, có thể enforce `NOT NULL` nếu business invariant yêu cầu.

## 5. Real production scenario

Hệ thống có API, worker, scheduled report và một legacy admin app dùng chung database. Team chỉ update API rồi drop column cũ. Worker version cũ vẫn chạy và fail sau deployment.

Một schema change an toàn phải inventory toàn bộ consumers, không chỉ service đang được deploy.

## 6. Failure scenario & troubleshooting

**Symptom:** deployment “successful” nhưng một số instances trả 500 `Invalid column name`.

**Evidence:** mixed application versions trong rolling deployment; schema migration đã drop/rename column.

**Hypothesis:** migration không backward compatible.

**Diagnosis:** map deployment timeline, active versions và SQL errors.

**Fix:** restore compatibility schema nếu có thể, roll forward code; thiết kế migration theo expand-contract ở release sau.

**Verification:** test N và N+1 versions cùng chạy với cùng schema trong staging.

## 7. Common mistakes

- Rename/drop column trong cùng release với code change.
- Backfill hàng trăm triệu rows trong một transaction.
- Thêm `NOT NULL DEFAULT` mà không hiểu lock/rewrite behavior của DB/version.
- Quên background jobs, BI/reporting hoặc integration consumers.
- Coi rollback application binary là đủ dù schema không rollback tương thích.

## 8. Alternatives

- **Maintenance window:** đơn giản và hợp lý nếu business cho phép downtime.
- **Blue-Green với shared DB:** vẫn cần schema compatibility khi hai versions overlap.
- **Versioned database/per-service storage:** giảm shared-schema coupling nhưng tăng data synchronization/operations.

## 9. Trade-offs

### Advantages

- Hỗ trợ rolling deploy và rollback an toàn hơn.
- Giảm coupling giữa app deployment và destructive schema change.

### Costs / Risks

- Migration kéo dài qua nhiều releases.
- Temporary dual fields/dual write tăng complexity.
- Backfill cần capacity planning và observability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu application version và database schema không đổi atomically trong production.

### Middle

Viết additive migration, backfill bounded và compatibility code.

### Senior

Thiết kế N/N+1 coexistence, rollback path và migration observability.

### Technical Lead / Architect

Đặt release policy cho destructive migrations, inventory consumers và quyết định khi downtime đơn giản hơn zero-downtime complexity.

## 11. Key takeaway

- Zero-downtime release yêu cầu schema tương thích với mixed application versions.
- Destructive change nên tách khỏi release giới thiệu schema mới.
- Database migration là release-engineering problem, không chỉ EF/SQL script problem.

# 9. Playwright test isolation: tránh flaky E2E do shared state, timing và selector không ổn định

## 1. What is it?

Test isolation nghĩa là mỗi test có preconditions và dữ liệu đủ độc lập để kết quả không phụ thuộc test chạy trước, thứ tự execution hoặc worker khác.

Flaky E2E test là test cùng code/build nhưng lúc pass lúc fail vì race, shared state, timing hoặc environment instability.

## 2. Why does it exist?

E2E test chạm browser, network, API, database và asynchronous UI. Nếu test dùng chung account/data hoặc `Thread.Sleep`/fixed delay, parallel execution dễ tạo race.

Một test suite flaky làm CI mất trust: team bắt đầu rerun thay vì điều tra, và signal regression bị suy yếu.

## 3. How does it work?

Playwright cung cấp auto-waiting cho locators/actions. Test nên đợi **condition có ý nghĩa**, không đợi thời gian tùy ý.

```text
Bad:  wait 3000 ms -> hy vọng UI đã xong
Good: wait until expected element/state -> assert
```

Isolation thường cần unique test data, cleanup hoặc disposable environment. Selector nên dựa trên accessible role/label/test id ổn định hơn CSS structure dễ đổi.

## 4. Practical implementation

```csharp
[Fact]
public async Task User_can_create_project()
{
    var projectName = $"e2e-{Guid.NewGuid():N}";

    await Page.GotoAsync("/projects");
    await Page.GetByRole(AriaRole.Button, new() { Name = "New project" }).ClickAsync();

    await Page.GetByLabel("Project name").FillAsync(projectName);
    await Page.GetByRole(AriaRole.Button, new() { Name = "Create" }).ClickAsync();

    await Expect(Page.GetByRole(AriaRole.Heading, new() { Name = projectName }))
        .ToBeVisibleAsync();
}
```

Tên unique giảm collision giữa parallel tests. Với setup phức tạp, dùng API fixture để seed state nhanh hơn thao tác UI mọi bước.

## 5. Real production scenario

Suite có 200 tests dùng chung `test@example.com`. Một test đổi password, test khác tạo cart, test khác logout session. Chạy local serial thì ổn; CI 8 workers thì fail ngẫu nhiên.

Sửa isolation bằng account/data per worker/test hoặc reset strategy giúp parallelism trở thành lợi ích thay vì nguồn race.

## 6. Failure scenario & troubleshooting

**Symptom:** test checkout fail 1/20 runs ở CI, rerun thường pass.

**Evidence:** trace/video cho thấy button chưa enabled hoặc shared cart chứa item từ test khác.

**Hypothesis:** timing race hoặc shared state contamination.

**Diagnosis:** dùng Playwright trace, network logs, screenshot; chạy repeated/parallel để reproduce.

**Fix:** condition-based wait, unique data, stable locator, explicit fixture ownership.

**Verification:** chạy test nhiều lần dưới parallelism giống CI; flaky rate phải về gần zero.

## 7. Common mistakes

- `Task.Delay(5000)` để “fix” flake.
- Chọn `.container > div:nth-child(3)` thay vì semantic locator.
- Test phụ thuộc thứ tự.
- Seed data thủ công lâu dài trong shared QA environment.
- Mock mọi backend trong E2E khiến test không còn kiểm tra integration thật.
- Retry test quá nhiều để che instability.

## 8. Alternatives

- **Unit tests:** nhanh, deterministic cho logic thuần.
- **Integration/API tests:** kiểm tra DB/network contract với ít UI variability.
- **Component tests:** kiểm tra frontend behavior ở scope nhỏ.
- **E2E:** dành cho critical user journeys nơi cross-system confidence đáng chi phí.

## 9. Trade-offs

### Advantages

- E2E cô lập tốt cho confidence cao ở business flow thật.
- Parallelism giảm pipeline duration.

### Costs / Risks

- Setup/cleanup data phức tạp.
- Full-stack environment đắt và chậm hơn unit/integration tests.
- Overusing E2E làm feedback loop dài.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu assertion cần chờ state, không chờ “một khoảng thời gian chắc đủ”.

### Middle

Viết stable locators, fixtures, unique test data và dùng traces để debug.

### Senior

Phân tích flakiness như concurrency/distributed-system problem giữa UI, API và data.

### Technical Lead / Architect

Thiết kế test strategy theo risk: phần nào unit, integration, contract, E2E; đặt policy không chấp nhận flaky suite kéo dài.

## 11. Key takeaway

- Flaky test là defect của test system, không phải noise bình thường.
- Condition-based waiting và data isolation quan trọng hơn tăng timeout.
- E2E nên bảo vệ critical journeys, không thay mọi tầng test khác.

# 10. RAG retrieval evaluation: đo chất lượng retrieval trước khi đổ lỗi cho LLM và giữ authorization ở deterministic boundary

## 1. What is it?

Retrieval-Augmented Generation (RAG) lấy dữ liệu liên quan từ knowledge source rồi đưa context đó vào LLM để tạo câu trả lời.

```text
User query
   -> retrieval
   -> top-k chunks
   -> prompt/context
   -> LLM
   -> answer
```

RAG có ít nhất hai hệ thống cần đánh giá riêng: **retrieval** có lấy đúng evidence không, và **generation** có dùng evidence đúng không.

## 2. Why does it exist?

LLM không tự biết dữ liệu private/current của doanh nghiệp một cách đáng tin cậy. RAG grounding model bằng tài liệu được truy xuất tại runtime mà không cần fine-tune cho mọi thay đổi nội dung.

Nhưng nếu retrieval lấy sai chunks, model không thể “reason” ra tài liệu bị thiếu. Nhiều team chỉ nhìn chất lượng answer cuối và không biết lỗi nằm ở retrieval, prompt hay model.

## 3. How does it work?

Pipeline điển hình:

```text
Documents -> chunk -> embed -> vector/index
                         ^
                         |
Query -> normalize/embed/search -> candidate chunks
                                 -> optional rerank
                                 -> LLM context
```

Evaluation retrieval có thể dùng labeled query → relevant document/chunk pairs. Metrics như recall@k, precision@k hoặc MRR giúp biết relevant evidence có xuất hiện trong candidates hay không.

Authorization phải lọc dữ liệu trước/hoặc trong retrieval query. Không được retrieve tài liệu tenant khác rồi dặn LLM “đừng tiết lộ”.

## 4. Practical implementation

Một deterministic retrieval contract:

```csharp
public async Task<IReadOnlyList<SearchChunk>> RetrieveAsync(
    string query,
    UserContext user,
    CancellationToken ct)
{
    var allowedDocumentIds = await authorization
        .GetReadableDocumentIdsAsync(user, ct);

    return await vectorStore.SearchAsync(
        query,
        topK: 8,
        filter: new SearchFilter
        {
            TenantId = user.TenantId,
            AllowedDocumentIds = allowedDocumentIds
        },
        ct);
}
```

Sau retrieval, log non-sensitive evaluation metadata như query class, retrieved document IDs, scores, latency và model/version — không log full confidential prompts mặc định.

## 5. Real production scenario

Internal HR assistant trả sai policy nghỉ phép. Team đổi model lớn hơn nhưng lỗi vẫn còn. Investigation cho thấy chunker tách heading khỏi rule và vector search đưa policy cũ lên top 5.

Fix thực sự nằm ở document lifecycle, chunking/metadata filter và retrieval ranking, không nằm ở “prompt mạnh hơn”.

## 6. Failure scenario & troubleshooting

**Symptom:** answer fluent nhưng thiếu rule quan trọng dù rule có trong knowledge base.

**Evidence:** trace cho thấy relevant chunk không nằm trong top-k.

**Hypothesis:** chunking/indexing/query formulation/retrieval filter kém.

**Diagnosis:** chạy evaluation set; đo recall@k; inspect failed queries và index freshness.

**Fix:** cải thiện chunk boundaries, metadata, hybrid search/reranking hoặc query rewrite; re-evaluate.

**Verification:** retrieval metric tăng và end-to-end grounded answer quality cải thiện trên held-out cases.

Một failure nghiêm trọng hơn là cross-tenant data leak. Với lỗi đó, fix phải nằm ở deterministic authorization/query filter, không phải system prompt.

## 7. Common mistakes

- Đánh giá chỉ bằng “trông câu trả lời có vẻ hay”.
- Tăng `topK` vô hạn làm context nhiều noise và tăng token cost.
- Không version document/index nên nội dung cũ vẫn được retrieve.
- Dùng similarity score như confidence tuyệt đối.
- Cho LLM tự quyết user được xem document nào.
- Log toàn bộ prompt chứa dữ liệu nhạy cảm.

## 8. Alternatives

- **Keyword/BM25 search:** mạnh với exact terms, IDs, product codes.
- **Hybrid search:** kết hợp lexical + vector, thường robust hơn cho enterprise search.
- **Structured SQL/API lookup:** tốt hơn khi câu hỏi thực chất cần deterministic fact query.
- **Fine-tuning:** phù hợp behavior/style/task specialization hơn là cập nhật private facts liên tục.

## 9. Trade-offs

### Advantages

- RAG cập nhật knowledge mà không retrain model.
- Có thể trace evidence và citation tốt hơn pure generation.

### Costs / Risks

- Thêm indexing, chunking, freshness và evaluation pipeline.
- Retrieval latency/token cost tăng.
- Authorization sai có thể thành security incident nghiêm trọng.
- Vector similarity không đảm bảo semantic correctness tuyệt đối.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG = retrieval + context + generation, không phải “LLM đọc database”.

### Middle

Implement indexing/search, metadata filters và basic evaluation set.

### Senior

Tách retrieval failure khỏi generation failure; đo recall/latency/cost và thiết kế secure observability.

### Technical Lead / Architect

Quyết định dữ liệu nào phù hợp RAG, dữ liệu nào phải dùng deterministic API; đặt authorization boundary, evaluation gates, data lifecycle và cost/SLO.

## 11. Key takeaway

- Muốn debug RAG phải đo retrieval riêng trước khi đổi model/prompt.
- Authorization là deterministic application responsibility.
- RAG chỉ đáng tin khi có evaluation, freshness và observability chứ không chỉ demo đẹp.
