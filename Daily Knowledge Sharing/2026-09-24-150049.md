# 1. C# `CancellationToken`: cancellation là cooperative protocol, không phải kill switch

## 1. What is it?

Mental model: `CancellationToken` là tín hiệu “operation này không còn cần thiết nữa”. Nó không cưỡng chế thread dừng; code tham gia operation phải chủ động quan sát token hoặc truyền token xuống API hỗ trợ cancellation.

Một request bị client hủy, timeout hoặc application shutdown có thể phát tín hiệu cancellation xuyên call chain.

## 2. Why does it exist?

Nếu caller đã bỏ request nhưng backend vẫn query database, gọi HTTP, deserialize payload và publish work, hệ thống đang tiêu tài nguyên cho kết quả không ai dùng. Dưới tải lớn, abandoned work có thể trở thành capacity problem.

Cưỡng chế terminate thread không an toàn vì code có thể đang giữ lock hoặc đang thay đổi state. Cooperative cancellation cho operation cơ hội dừng tại boundary an toàn.

## 3. How does it work?

```text
HTTP request aborted
   -> RequestAborted token is cancelled
      -> application service receives token
         -> EF Core / HttpClient receives token
            -> pending I/O attempts cancellation
```

Cancellation propagation không tự xảy ra nếu một layer bỏ token.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    AppDbContext db,
    CancellationToken ct) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

Trong service methods, nhận `CancellationToken` như parameter và truyền tiếp xuống asynchronous I/O.

## 5. Real production scenario

Search endpoint gọi SQL và hai downstream APIs. User đổi filter liên tục, browser hủy requests cũ. Nếu cancellation được propagate, work cũ dừng sớm; nếu không, mỗi user action để lại nhiều expensive requests chạy ngầm.

## 6. Failure scenario & troubleshooting

**Symptom** → request count phía client thấp nhưng database/downstream vẫn giữ load cao sau khi clients disconnect. **Evidence** → traces cho thấy server spans tiếp tục lâu sau HTTP cancellation. **Hypothesis** → token bị mất trong service boundary. **Diagnosis** → inspect call chain và APIs không nhận token. **Fix** → propagate token; phân biệt timeout/cancellation hợp lý. **Verification** → hủy request dưới load và xác nhận dependency operations kết thúc sớm.

## 7. Common mistakes

Tạo `new CancellationToken()` thay vì truyền token hiện có; catch `OperationCanceledException` rồi log Error; dùng cancellation để rollback business action đã commit; không đặt cancellation point trong long CPU loop; truyền `CancellationToken.None` vì tiện.

## 8. Alternatives

Timeout giới hạn duration nhưng không hoàn toàn giống caller cancellation. Durable background work thường không nên gắn lifetime trực tiếp vào HTTP request; hãy enqueue command/job rồi xử lý với lifecycle riêng.

## 9. Trade-offs

### Advantages

Giảm wasted work, cải thiện shutdown và responsiveness.

### Costs / Risks

Call chain phải thiết kế cancellation-aware; cancellation tại sai boundary có thể để operation business ở trạng thái khó hiểu nếu transaction semantics không rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu token là signal và phải được truyền xuống.

### Middle
Propagate token qua controller/service/repository/HTTP/database và test cancellation.

### Senior
Xác định operation nào cancellable trước/sau commit boundary; phân biệt timeout, cancellation và failure.

### Technical Lead / Architect
Định nghĩa cancellation policy cho HTTP, background jobs và distributed workflows; không gắn durable work vào request lifetime một cách vô thức.

## 11. Key takeaway

- Cancellation là cooperative protocol.
- Token bị mất ở một layer sẽ cắt đứt propagation.
- Không cancel mù quáng sau irreversible commit boundary.

# 2. ASP.NET Core graceful shutdown: ngừng nhận traffic trước khi kết thúc in-flight work

## 1. What is it?

Graceful shutdown là quá trình application nhận termination signal, ngừng nhận work mới, cho work đang chạy một khoảng thời gian để hoàn tất và giải phóng resources có trật tự.

## 2. Why does it exist?

Containers, App Service, Kubernetes và process managers thường restart/replace instances. Nếu process chết ngay lập tức, in-flight requests có thể bị reset, queue messages có thể bị xử lý dở và buffered telemetry có thể mất.

## 3. How does it work?

```text
termination signal
 -> instance becomes unready / traffic drains
 -> host signals ApplicationStopping
 -> requests/background workers observe cancellation
 -> cleanup/flush
 -> process exits before shutdown deadline
```

Traffic draining và process shutdown là hai lớp khác nhau; chỉ có `StopAsync` không bảo đảm load balancer đã ngừng route request mới.

## 4. Practical implementation

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await ProcessNextAsync(stoppingToken);
        }
    }
}
```

Consumer phải quyết định message settlement khi shutdown xảy ra giữa processing.

## 5. Real production scenario

Rolling deployment thay 10 pods. Readiness chuyển false trước termination, load balancer ngừng gửi traffic; mỗi pod hoàn tất requests ngắn đang chạy rồi exit. Nếu không drain, deployment tạo burst 502/connection reset dù application code không lỗi.

## 6. Failure scenario & troubleshooting

**Symptom** → error rate tăng đúng lúc deployment. **Evidence** → terminated instance vẫn nhận request hoặc requests vượt shutdown grace period. **Hypothesis** → drain/shutdown sequencing sai. **Diagnosis** → correlate deployment events, readiness, request traces và termination timestamps. **Fix** → pre-stop/draining, shutdown timeout và cancellable workers phù hợp. **Verification** → rolling deployment dưới traffic thật mô phỏng.

## 7. Common mistakes

Sleep cố định thay vì readiness/drain semantics; background worker bỏ qua stopping token; shutdown timeout quá ngắn; chờ vô hạn; bắt đầu long-running work mới sau termination signal.

## 8. Alternatives

Durable queue cho work dài giúp process replacement an toàn hơn. Blue-Green có thể giảm traffic transition risk nhưng worker shutdown vẫn cần đúng.

## 9. Trade-offs

### Advantages
Giảm request loss và duplicate/incomplete work.

### Costs / Risks
Shutdown lâu làm deployment/node drain chậm; graceful shutdown không thể cứu operation dài hơn platform deadline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu process lifecycle và cancellation.

### Middle
Implement shutdown-aware workers và health endpoints.

### Senior
Test termination giữa request/message processing và xác định safe retry semantics.

### Technical Lead / Architect
Thiết kế traffic draining, deployment strategy và durable-work boundaries cùng nhau.

## 11. Key takeaway

- Graceful shutdown bắt đầu từ traffic draining, không chỉ `Dispose()`.
- Long-running work cần durable ownership.
- Deployment phải được test như một production failure transition.

# 3. SQL Server covering index: giảm lookup nhưng không phải miễn phí

## 1. What is it?

Covering index là index chứa đủ columns để SQL Server đáp ứng query mà không cần quay lại clustered index/heap lấy thêm dữ liệu. Key columns phục vụ seek/order; `INCLUDE` columns có thể cung cấp payload.

## 2. Why does it exist?

Một nonclustered index seek có thể tìm rows nhanh nhưng nếu query cần columns không có trong index, engine phải thực hiện Key Lookup cho từng matching row. Với nhiều rows, lookup I/O trở nên đắt.

## 3. How does it work?

```text
Nonclustered seek
   -> matching index rows
      -> Key Lookup x N
```

Covering index có thể biến flow thành:

```text
Nonclustered seek/scan
   -> required columns already present
```

Nhưng index lớn hơn làm write/storage/cache cost tăng.

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_CustomerId_CreatedAt
ON dbo.Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, TotalAmount);
```

Query:

```sql
SELECT CreatedAt, Status, TotalAmount
FROM dbo.Orders
WHERE CustomerId = @customerId
ORDER BY CreatedAt DESC;
```

Xác minh bằng actual execution plan, logical reads và runtime statistics.

## 5. Real production scenario

Customer history endpoint trả 50 orders mới nhất. Existing index seek nhanh nhưng 50–500 Key Lookups/request tạo I/O đáng kể ở traffic cao. Một carefully-sized covering index giảm reads.

## 6. Failure scenario & troubleshooting

**Symptom** → reads giảm cho SELECT nhưng write latency/storage tăng. **Evidence** → index size lớn, update cost tăng, buffer cache pressure. **Hypothesis** → over-covering. **Diagnosis** → usage stats, write workload, index size và plans. **Fix** → bỏ unnecessary includes hoặc redesign query. **Verification** → đo read/write workload tổng thể.

## 7. Common mistakes

Include mọi column; tạo overlapping indexes cho từng query; không xem selectivity/order; coi “Index Seek” luôn nhanh; tối ưu query hiếm nhưng làm mọi write đắt hơn.

## 8. Alternatives

Projection nhỏ hơn, clustered/index key redesign, read model riêng hoặc caching khi semantics phù hợp.

## 9. Trade-offs

### Advantages
Giảm lookup và I/O cho hot reads.

### Costs / Risks
Storage, memory, maintenance và write amplification tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu seek và lookup là hai operations khác nhau.

### Middle
Đọc execution plan và logical reads.

### Senior
Cân read benefit với write/index portfolio cost.

### Technical Lead / Architect
Quản lý indexing theo workload toàn hệ thống thay vì từng query riêng lẻ.

## 11. Key takeaway

- Covering index là workload optimization.
- `INCLUDE` vẫn có storage/write cost.
- Đo logical reads và write impact trước/sau.

# 4. Elasticsearch alias + reindex: thay mapping mà Search API không cần biết index vật lý

## 1. What is it?

Alias là logical name trỏ tới một hoặc nhiều Elasticsearch indexes. Search application dùng alias ổn định; backend có thể tạo index version mới, reindex rồi chuyển alias.

## 2. Why does it exist?

Một số mapping/analyzer changes không thể thay đổi an toàn in-place. Nếu application hard-code `products-v17`, mỗi migration buộc deploy application hoặc gây downtime.

## 3. How does it work?

```text
Search API -> products-read -> products-v17

create products-v18
 -> reindex/backfill
 -> validate
 -> atomic alias switch

Search API -> products-read -> products-v18
```

Primary database vẫn thường là source of truth; reindex cần chiến lược bắt kịp changes xảy ra trong quá trình backfill.

## 4. Practical implementation

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v17", "alias": "products-read" }},
    { "add":    { "index": "products-v18", "alias": "products-read" }}
  ]
}
```

Switch chỉ nên xảy ra sau validation về document count, query correctness và representative relevance.

## 5. Real production scenario

E-commerce đổi analyzer cho product names. Team tạo v18, backfill từ SQL/change stream, chạy shadow queries, rồi swap alias mà Search API không đổi config.

## 6. Failure scenario & troubleshooting

**Symptom** → sau alias switch, một số products biến mất. **Evidence** → v18 document count thấp hơn và sync lag tồn tại. **Hypothesis** → backfill không capture concurrent updates. **Diagnosis** → compare source watermark/change events. **Fix** → replay delta trước switch hoặc dual-write/change-capture strategy. **Verification** → source/index reconciliation.

## 7. Common mistakes

Reindex snapshot nhưng bỏ changes phát sinh; xóa old index ngay; chỉ so document count mà không test query semantics; dùng Elasticsearch như transactional source of truth.

## 8. Alternatives

In-place changes chỉ phù hợp với settings/mappings hỗ trợ. Dual-read/shadow query hữu ích cho migration rủi ro cao.

## 9. Trade-offs

### Advantages
Zero/low-downtime migration và rollback alias nhanh.

### Costs / Risks
Tạm thời cần gấp đôi storage, synchronization logic và validation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu alias tách logical endpoint khỏi physical index.

### Middle
Thực hiện versioned index + alias switch.

### Senior
Thiết kế backfill/delta/reconciliation và rollback.

### Technical Lead / Architect
Quyết định source-of-truth và migration contract giữa database, indexing pipeline và Search API.

## 11. Key takeaway

- Alias giải deployment coupling, không giải data synchronization.
- Reindex phải xử lý concurrent changes.
- Giữ old index đủ lâu để rollback có kiểm soát.

# 5. DDD Aggregate: transaction boundary bảo vệ invariant

## 1. What is it?

Aggregate là cụm domain objects được xem như một consistency boundary. Aggregate Root là entry point mà external code dùng để thay đổi state bên trong. Mental model quan trọng: Aggregate không phải “load toàn bộ object graph liên quan”.

## 2. Why does it exist?

Business rules thường yêu cầu một nhóm state thay đổi atomically. Nếu bất kỳ code nào sửa child entities trực tiếp, invariant dễ bị phá và transaction boundary trở nên mơ hồ.

## 3. How does it work?

Ví dụ Order Aggregate bảo vệ rule: không thể thêm line sau khi order đã submitted.

```text
Application Service
   -> Order Aggregate Root
      -> validates invariant
      -> mutates OrderLine internally
   -> persistence transaction
```

Một Aggregate khác thường được tham chiếu bằng ID thay vì giữ object graph lớn.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyCollection<OrderLine> Lines => _lines;
    public OrderStatus Status { get; private set; }

    public void AddLine(ProductId productId, int quantity)
    {
        if (Status != OrderStatus.Draft)
            throw new DomainException("Submitted order cannot be changed.");

        _lines.Add(new OrderLine(productId, quantity));
    }
}
```

Application Service orchestration và domain invariant là hai trách nhiệm khác nhau.

## 5. Real production scenario

Approval workflow có `Timesheet` root và entries. Submit operation phải bảo đảm entries hợp lệ và status chuyển atomically. Employee profile không cần nằm trong cùng aggregate chỉ vì timesheet có EmployeeId.

## 6. Failure scenario & troubleshooting

**Symptom** → EF Core load graph cực lớn và concurrent updates conflict thường xuyên. **Evidence** → Aggregate chứa nhiều collections không cần atomic consistency. **Hypothesis** → boundary quá lớn. **Diagnosis** → hỏi invariant nào thật sự phải commit cùng transaction. **Fix** → tách aggregate, tham chiếu ID, dùng eventual consistency cho cross-boundary coordination. **Verification** → concurrency/load tests và invariant tests.

## 7. Common mistakes

Một database table = một Aggregate; toàn bounded context = một Aggregate; public setters cho mọi state; generic repository bỏ qua domain semantics; Domain Event dùng để che boundary chưa rõ.

## 8. Alternatives

CRUD/anemic model có thể hoàn toàn đủ cho domain đơn giản. Không cần DDD tactical patterns nếu business rules ít và chủ yếu data-entry.

## 9. Trade-offs

### Advantages
Invariant và transaction ownership rõ hơn.

### Costs / Risks
Modeling khó hơn; boundary sai tạo performance/concurrency problems; cross-aggregate workflows cần eventual consistency hoặc orchestration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt Entity, Value Object và Aggregate Root.

### Middle
Đưa invariant vào domain behavior thay vì controller.

### Senior
Thiết kế aggregate nhỏ theo consistency boundary và concurrency.

### Technical Lead / Architect
Quyết định domain nào đủ phức tạp để DDD mang lại giá trị và boundary nào nên eventual-consistent.

## 11. Key takeaway

- Aggregate là consistency/transaction boundary.
- Relationship trong database không tự động nghĩa là cùng Aggregate.
- Domain đơn giản không cần ép DDD.

# 6. Azure Service Bus PeekLock: settlement và duplicate delivery

## 1. What is it?

Ở PeekLock mode, consumer nhận message nhưng Service Bus chưa xóa nó. Broker lock message trong thời gian giới hạn; consumer xử lý rồi `Complete`, hoặc `Abandon`/dead-letter theo kết quả.

## 2. Why does it exist?

Nếu broker xóa message ngay khi giao và consumer crash giữa processing, work bị mất. PeekLock cho phép redelivery khi processing không hoàn tất.

## 3. How does it work?

```text
Receive -> lock acquired
   -> process
      -> Complete -> message removed
      -> crash/lock expires -> message visible again
```

Đây là nền tảng của at-least-once delivery: cùng message có thể được xử lý nhiều lần.

## 4. Practical implementation

```csharp
var options = new ServiceBusProcessorOptions
{
    AutoCompleteMessages = false,
    MaxConcurrentCalls = 8
};

processor.ProcessMessageAsync += async args =>
{
    await handler.HandleAsync(args.Message, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message);
};
```

Business side effect cần idempotency dựa trên stable message/business ID.

## 5. Real production scenario

Invoice consumer cập nhật SQL trong 40 giây. Process crash sau DB commit nhưng trước `Complete`. Message được giao lại; idempotent handler phát hiện invoice event đã apply và chỉ complete lần hai.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng order được xử lý hai lần hoặc lock-lost exceptions tăng. **Evidence** → delivery count > 1, processing duration gần/vượt lock duration. **Hypothesis** → redelivery hoặc lock expiry. **Diagnosis** → inspect duration, lock renewal, settlement logs và message ID. **Fix** → idempotency, bounded processing, lock renewal phù hợp. **Verification** → fault-inject crash sau business commit.

## 7. Common mistakes

Tin PeekLock tạo exactly-once; complete trước business commit; retry side effects không idempotent; concurrency cao hơn downstream capacity; DLQ nhưng không có monitoring/repair process.

## 8. Alternatives

Receive-and-delete đơn giản hơn nhưng có loss risk và hiếm phù hợp business work. Storage Queue hoặc Kafka có semantics khác; chọn theo ordering, throughput và operational model.

## 9. Trade-offs

### Advantages
Reliable redelivery và explicit settlement.

### Costs / Risks
Duplicate handling, lock management, poison messages và operational complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu receive không đồng nghĩa message đã xóa.

### Middle
Implement settlement và error handling.

### Senior
Thiết kế idempotency, concurrency, lock duration và DLQ recovery.

### Technical Lead / Architect
Định nghĩa delivery contract end-to-end và quyết định business operations nào chịu được at-least-once.

## 11. Key takeaway

- PeekLock bảo vệ khỏi message loss bằng redelivery.
- Redelivery kéo theo duplicate processing.
- Idempotency là business requirement, không phải broker checkbox.

# 7. Blue-Green deployment với database migration: application rollback dễ hơn schema rollback

## 1. What is it?

Blue-Green giữ hai application environments: version đang phục vụ và version mới. Traffic switch có thể nhanh. Nhưng nếu cả hai dùng cùng database, schema trở thành shared compatibility boundary.

## 2. Why does it exist?

Application binary có thể rollback trong vài giây; destructive database migration có thể không rollback an toàn. Nếu Green đổi schema khiến Blue không còn chạy được, lợi ích rollback của Blue-Green gần như mất.

## 3. How does it work?

Dùng expand-contract:

```text
1. Expand schema: additive/backward-compatible change
2. Deploy Green: supports old + new shape
3. Switch traffic
4. Observe
5. Later contract: remove obsolete schema after Blue is no longer needed
```

## 4. Practical implementation

Thay vì rename column trực tiếp:

```text
release A: add NewColumn, code can read/write compatibility path
release B: migrate/backfill data
release C: stop using OldColumn
later: drop OldColumn
```

Migration phải được versioned và deployment pipeline kiểm tra compatibility.

## 5. Real production scenario

Checkout Green đổi `CustomerName` thành structured fields. Nếu migration drop column trước traffic switch, Blue rollback sẽ crash. Expand-contract cho phép cả Blue và Green cùng hoạt động trong transition.

## 6. Failure scenario & troubleshooting

**Symptom** → Green health fail, switch về Blue nhưng Blue trả SQL errors. **Evidence** → migration đã drop/rename column Blue cần. **Hypothesis** → schema change không backward-compatible. **Diagnosis** → compare deployed binaries với schema migration timeline. **Fix** → restore compatibility hoặc emergency migration. **Verification** → rollback rehearsal trước production.

## 7. Common mistakes

Gắn destructive migration vào startup; cho nhiều instances cùng migrate; coi migration success là deployment success; không test rollback; giữ compatibility code mãi không cleanup.

## 8. Alternatives

Canary/rolling deployment vẫn có cùng database compatibility problem. Separate database per service giảm một số coupling nhưng migration trong service vẫn cần strategy.

## 9. Trade-offs

### Advantages
Rollback application nhanh và giảm release risk.

### Costs / Risks
Temporary schema/code duplication, backfill complexity và multi-release coordination.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu application và schema có lifecycle khác nhau.

### Middle
Viết additive migrations và deploy sequencing.

### Senior
Thiết kế expand-contract/backfill/rollback rehearsal.

### Technical Lead / Architect
Định nghĩa compatibility window và ownership giữa application release với data migration.

## 11. Key takeaway

- Database là shared compatibility boundary trong Blue-Green.
- Rollback binary không giúp nếu schema đã phá compatibility.
- Destructive changes nên là bước cuối, không phải đầu.

# 8. Application Insights dependency telemetry: tìm critical path của p95 latency

## 1. What is it?

Dependency telemetry ghi lại outbound calls như SQL, HTTP và một số Azure services cùng duration, success/failure và trace correlation. Mental model: request latency là tổng/overlap của các spans trên critical path, không phải chỉ thời gian controller.

## 2. Why does it exist?

Average request duration có thể ổn trong khi p95/p99 xấu. Nếu không biết thời gian nằm ở SQL, downstream HTTP, queue interaction hay application CPU, team dễ tối ưu sai chỗ.

## 3. How does it work?

```text
Request 2.4s
  |- SQL query 120ms
  |- Product API 2.0s  <-- critical dependency
  |- serialization 40ms
```

Distributed trace nối request với dependency spans bằng trace context.

## 4. Practical implementation

Instrument ASP.NET Core/OpenTelemetry/Application Insights và giữ operation names bounded. Khi incident xảy ra, lọc slow requests, mở representative traces, so dependency percentiles và failure rates trước/sau deployment.

## 5. Real production scenario

API p95 tăng từ 400 ms lên 2.8 s nhưng CPU/SQL bình thường. Traces cho thấy review provider p95 tăng 2.3 s. Team áp timeout/fallback cho non-critical reviews thay vì scale SQL.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard chỉ thấy request chậm nhưng không có dependency detail. **Evidence** → missing spans hoặc broken trace context. **Hypothesis** → instrumentation/propagation thiếu. **Diagnosis** → inspect trace headers, SDK setup và sampling. **Fix** → instrument dependency client và propagation. **Verification** → synthetic request phải tạo end-to-end trace.

## 7. Common mistakes

Chỉ nhìn average; metric dimension cardinality cao; log text không correlation; sampling làm mất rare errors mà không hiểu policy; alert trên từng dependency spike nhỏ không gắn SLO.

## 8. Alternatives

OpenTelemetry vendor-neutral pipeline có thể export sang nhiều backends. Structured logs vẫn hữu ích nhưng không thay latency topology của traces.

## 9. Trade-offs

### Advantages
Nhanh chóng localize latency/failure theo dependency.

### Costs / Risks
Telemetry volume/cost, sampling và privacy/cardinality governance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu request có nhiều dependency operations.

### Middle
Dùng correlation và trace để tìm slow span.

### Senior
Reason về p50/p95/p99, sampling và critical path.

### Technical Lead / Architect
Thiết kế SLI/SLO, telemetry budget và fallback policy dựa trên dependency criticality.

## 11. Key takeaway

- Percentiles quan trọng hơn average cho tail latency.
- Trace giúp localize critical path.
- Telemetry chỉ có giá trị khi dẫn tới diagnostic decision.

# 9. OAuth 2.0 / OIDC `state`, `nonce`, PKCE: đừng trộn ba cơ chế

## 1. What is it?

Trong Authorization Code flow, `state`, OIDC `nonce` và PKCE đều tăng security nhưng bảo vệ các boundary khác nhau. Mental model: chúng không phải ba phiên bản của cùng một random string.

## 2. Why does it exist?

Redirect-based authentication đi qua browser/front channel nên có rủi ro request/response substitution, login CSRF và authorization code interception. Một cơ chế đơn lẻ không giải hết.

## 3. How does it work?

- `state`: bind authorization response với client transaction và thường bảo vệ CSRF/request correlation.
- `nonce`: OIDC value được đưa vào ID Token để client xác minh token thuộc authentication request mong đợi/replay protection context.
- PKCE: client gửi challenge trước, rồi phải chứng minh `code_verifier` khi redeem authorization code.

```text
Client -> authorize(state, nonce, code_challenge)
IdP -> callback(code, state)
Client verifies state
Client -> token(code, code_verifier)
Client validates ID Token including nonce
```

## 4. Practical implementation

Ưu tiên framework/OIDC middleware chuẩn thay vì tự xây protocol. Trong ASP.NET Core, middleware quản lý correlation/state/nonce và code redemption; cấu hình HTTPS, callback URI và cookie policy đúng deployment topology.

## 5. Real production scenario

Web app dùng external Entra ID qua OIDC. Reverse proxy misconfiguration làm correlation cookie không quay lại callback; login fail dù Entra đã authenticate thành công. Trace redirect/cookie/state flow giúp phân biệt protocol failure với credential failure.

## 6. Failure scenario & troubleshooting

**Symptom** → “Correlation failed” hoặc nonce validation failure chỉ ở Production. **Evidence** → callback host/scheme/cookie khác request ban đầu. **Hypothesis** → proxy forwarded headers/SameSite/secure-cookie configuration sai. **Diagnosis** → inspect redirect URI, cookies và forwarded headers, không log token secrets. **Fix** → sửa trusted proxy/HTTPS/cookie configuration. **Verification** → full browser login flow qua production-like proxy.

## 7. Common mistakes

Tự implement OAuth; tắt validation để login “chạy”; nhầm access token với ID token; dùng `state` làm authorization; log tokens; callback wildcard rộng; không dùng PKCE khi flow/client profile yêu cầu.

## 8. Alternatives

BFF pattern có thể giữ tokens server-side cho browser apps. Cookie authentication phù hợp application session sau OIDC sign-in; nó không thay identity federation protocol.

## 9. Trade-offs

### Advantages
Chuẩn protocol cho federation và giảm nhiều front-channel attacks khi dùng đúng.

### Costs / Risks
Redirect/cookie/proxy configuration phức tạp; custom implementation cực dễ tạo security flaw.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt authentication, authorization, access token và ID token.

### Middle
Cấu hình OIDC middleware và debug redirect/cookie flow.

### Senior
Hiểu `state`, `nonce`, PKCE và token validation boundaries.

### Technical Lead / Architect
Chọn identity topology, BFF/token storage và trust boundaries; tránh protocol customization không cần thiết.

## 11. Key takeaway

- `state`, `nonce`, PKCE giải các rủi ro khác nhau.
- Dùng mature middleware thay vì tự viết OAuth/OIDC.
- Production proxy/cookie topology là một phần của authentication design.

# 10. AI RAG evaluation: retrieval đúng chưa đủ nếu answer grounding sai

## 1. What is it?

RAG evaluation đo riêng các tầng của Retrieval-Augmented Generation: query/retrieval có lấy đúng evidence không, model có dùng evidence đúng không, câu trả lời có đáp ứng task và biết từ chối khi evidence thiếu không.

## 2. Why does it exist?

Một end-to-end score duy nhất không nói lỗi nằm ở đâu. Model có thể trả lời sai vì retriever không lấy đúng document, chunking mất context, reranker xếp sai, hoặc LLM bỏ qua evidence đúng.

## 3. How does it work?

```text
Question
 -> retrieval
    -> candidate chunks
       -> rerank/context assembly
          -> LLM answer
             -> grounded answer / unsupported claim
```

Evaluation nên tách retrieval metrics khỏi generation/grounding metrics và production feedback.

## 4. Practical implementation

Tạo versioned evaluation set gồm question, expected evidence IDs, answer criteria và cases mà hệ thống phải abstain. CI có thể chạy deterministic retrieval checks trước; LLM-as-judge chỉ là một signal và cần calibration/human review cho critical cases.

Ví dụ deterministic check:

```csharp
Assert.Contains("policy-2026-17", result.RetrievedDocumentIds);
Assert.True(result.Citations.Count > 0);
```

Authorization, tenant filtering và document access phải nằm trong deterministic retrieval/application logic, không giao cho model quyết định.

## 5. Real production scenario

Internal support agent trả lời từ policy documents. Sau đổi embedding model, answer fluency vẫn đẹp nhưng relevant policy recall giảm. Retrieval evaluation phát hiện regression trước khi users báo hallucination.

## 6. Failure scenario & troubleshooting

**Symptom** → answer sai dù top retrieved chunk nhìn có vẻ đúng. **Evidence** → expected evidence có trong context nhưng output chứa unsupported claim. **Hypothesis** → generation/grounding failure thay vì retrieval failure. **Diagnosis** → inspect retrieved set, prompt/context truncation và claim-to-source mapping. **Fix** → context assembly, structured citations/refusal rules hoặc model/prompt change. **Verification** → rerun fixed eval set + adversarial no-evidence cases.

## 7. Common mistakes

Đánh giá bằng vài demo đẹp; chỉ đo cosine similarity; thay model/chunking mà không version eval; LLM judge tự chấm output của chính model family mà không calibration; cho model quyết định access control; không test “không có câu trả lời”.

## 8. Alternatives

Fine-tuning phù hợp behavioral/style patterns nhưng không thay retrieval cho frequently changing private knowledge. Search-only UX đơn giản và đáng tin hơn khi generated synthesis không tạo đủ giá trị.

## 9. Trade-offs

### Advantages
Tách được lỗi retrieval/generation và kiểm soát regressions.

### Costs / Risks
Eval set maintenance, judge variance, token cost và risk tối ưu quá mức theo benchmark nhỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu RAG gồm retrieval và generation riêng biệt.

### Middle
Xây evaluation cases, citations và retrieval assertions.

### Senior
Phân tích recall/precision, grounding, refusal và production drift.

### Technical Lead / Architect
Quyết định phần nào probabilistic, phần nào bắt buộc deterministic; đặt release gates và data/security boundaries cho AI system.

## 11. Key takeaway

- RAG quality phải được phân rã theo pipeline stage.
- Fluent answer không chứng minh grounded answer.
- Security/authorization phải deterministic, không giao cho LLM.
