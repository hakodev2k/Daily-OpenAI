# 1. .NET `ValueTask<T>`: allocation optimization và ownership contract của async result

## 1. What is it?

`ValueTask<T>` là awaitable có thể biểu diễn kết quả hoàn thành synchronously mà không nhất thiết tạo một `Task<T>` object mới. Mental model đúng: đây là **performance-oriented return contract**, không phải phiên bản “nhanh hơn” để thay `Task<T>` ở mọi API.

## 2. Why does it exist?

Một async API cực nóng có thể hoàn thành synchronously phần lớn thời gian, ví dụ đọc từ buffer/cache đã có dữ liệu. Nếu mỗi invocation đều tạo `Task<T>`, allocation nhỏ nhưng lặp hàng triệu lần có thể trở thành GC pressure đo được.

## 3. How does it work?

```text
ValueTask<T>
   ├── synchronous T
   ├── Task<T>
   └── IValueTaskSource<T>
```

Đổi lại khả năng tránh allocation, consumer phải tuân theo contract chặt hơn. Một `ValueTask<T>` nói chung nên được await trực tiếp một lần; lưu giữ, await nhiều lần hoặc gọi `.Result` rồi lại await có thể không hợp lệ với implementation dựa trên `IValueTaskSource<T>`.

## 4. Practical implementation

```csharp
public ValueTask<User?> GetCachedUserAsync(Guid id)
{
    if (_cache.TryGetValue(id, out User? user))
        return ValueTask.FromResult(user);

    return new ValueTask<User?>(LoadFromStoreAsync(id));
}
```

Nếu caller cần reuse result như `Task<T>`, có thể gọi `AsTask()`, nhưng lúc đó lợi ích allocation có thể giảm.

## 5. Real production scenario

Một high-throughput protocol parser thường tìm thấy dữ liệu trong in-memory buffer và chỉ hiếm khi cần I/O. Profiling chứng minh `Task` allocations nằm trong hot path. `ValueTask<T>` có thể hợp lý ở boundary này; business service gọi database vài trăm lần/giây thường không cần complexity đó.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi khó tái hiện hoặc result behavior bất thường khi cùng awaitable được consume nhiều lần.  
**Evidence** → caller lưu `ValueTask<T>` vào field/list rồi await ở nhiều nơi.  
**Hypothesis** → vi phạm consumption contract.  
**Diagnosis** → trace lifetime của returned value và implementation source.  
**Fix** → await trực tiếp một lần hoặc convert sang `Task<T>` khi cần multi-consumption.  
**Verification** → concurrency/stress tests và allocation benchmark.

## 7. Common mistakes

Đổi toàn bộ `Task<T>` thành `ValueTask<T>` vì nghĩ nhanh hơn; benchmark không representative; lưu `ValueTask` lâu dài; await nhiều lần; bỏ qua tăng kích thước state machine/copy cost.

## 8. Alternatives

`Task<T>` là default tốt hơn cho hầu hết application APIs: semantics đơn giản, composability tốt và runtime đã tối ưu completed tasks ở nhiều trường hợp. Synchronous API phù hợp nếu operation thực sự không asynchronous.

## 9. Trade-offs

### Advantages

Có thể giảm allocation ở synchronous-completion hot paths.

### Costs / Risks

API contract phức tạp hơn, struct lớn hơn reference, misuse dễ tạo bug và lợi ích thường nhỏ nếu operation thực sự I/O-bound.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Dùng `Task<T>` mặc định và hiểu async result lifetime.

### Middle

Biết `ValueTask<T>` có consumption restrictions.

### Senior

Chỉ áp dụng sau allocation profiling/benchmark.

### Technical Lead / Architect

Giới hạn performance-specific contracts vào hot infrastructure boundaries thay vì lan vào toàn application.

## 11. Key takeaway

- `ValueTask<T>` là optimization có contract cost.
- `Task<T>` vẫn là default cho application code.
- Measure allocation pressure trước khi đổi API.

# 2. ASP.NET Core Rate Limiting: partitioning, queueing và overload protection

## 1. What is it?

Rate limiting giới hạn lượng work được chấp nhận trong một khoảng thời gian hoặc mức concurrency. Trong ASP.NET Core, limiter có thể partition theo user, API key, tenant, IP hoặc route. Mental model: **admission control** để bảo vệ finite capacity, không phải chỉ chống abuse.

## 2. Why does it exist?

Một endpoint có database dependency chịu được 500 concurrent operations. Nếu application nhận 5.000 requests cùng lúc và để tất cả đi xuống DB, connection pool và database có thể collapse. Reject có kiểm soát thường tốt hơn timeout hàng loạt.

## 3. How does it work?

```text
Requests
   │
   ▼
Partition key (tenant/user/API)
   │
   ▼
Rate/Concurrency limiter
   ├── permit → endpoint → dependency
   └── reject/queue → 429
```

Fixed Window, Sliding Window, Token Bucket và Concurrency limiter giải quyết các dạng capacity khác nhau. Queueing không tạo capacity; queue quá dài chỉ biến overload thành latency.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddConcurrencyLimiter("db-heavy", limiter =>
    {
        limiter.PermitLimit = 100;
        limiter.QueueLimit = 20;
        limiter.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
    });

    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});

app.UseRateLimiter();

app.MapGet("/reports", HandleReport)
   .RequireRateLimiting("db-heavy");
```

Production policy nên phản ánh downstream capacity và fairness, không chọn số ngẫu nhiên.

## 5. Real production scenario

Một B2B API có một tenant gửi burst traffic lớn. Global limiter có thể làm tenant đó chiếm hết permits; partitioned limiter theo tenant giúp fairness và bảo vệ khách hàng khác.

## 6. Failure scenario & troubleshooting

**Symptom** → 429 tăng nhưng DB vẫn overload.  
**Evidence** → nhiều app instances mỗi instance có limiter riêng.  
**Hypothesis** → local limit × instance count vượt downstream capacity.  
**Diagnosis** → tính aggregate concurrency và autoscaling behavior.  
**Fix** → giảm per-instance budget, dùng gateway/distributed admission control nếu cần global guarantee.  
**Verification** → load test khi scale-out và quan sát DB connections/p95.

## 7. Common mistakes

Rate limit chỉ theo IP sau reverse proxy; queue hàng nghìn requests; trả 500 thay vì 429; không gửi retry guidance khi phù hợp; dùng limiter thay authorization; không tính autoscaling.

## 8. Alternatives

Queue-based asynchronous processing phù hợp workload có thể defer. Bulkhead giới hạn dependency concurrency bên trong service. API Gateway rate limiting phù hợp enforcement trước application.

## 9. Trade-offs

### Advantages

Bảo vệ capacity, fairness và giảm cascading failure.

### Costs / Risks

Reject legitimate traffic, distributed enforcement khó hơn, policy cần tune theo workload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 429 và finite capacity.

### Middle

Implement limiter theo endpoint/key.

### Senior

Định lượng queue/concurrency từ downstream capacity.

### Technical Lead / Architect

Thiết kế admission control xuyên gateway, services và dependencies.

## 11. Key takeaway

- Rate limiting là reliability primitive.
- Queue không làm dependency mạnh hơn.
- Partition key quyết định fairness và blast radius.

# 3. OAuth 2.0 / OpenID Connect: Access Token vs ID Token và lỗi trust-boundary phổ biến

## 1. What is it?

OAuth 2.0 là authorization framework; OpenID Connect (OIDC) thêm identity layer. `access_token` được cấp để client gọi protected resource/API. `id_token` cho client biết authentication result và thông tin về user session. Hai token có audience và purpose khác nhau.

## 2. Why does it exist?

Nếu mọi application nhận username/password của user để gọi mọi service, credentials bị lan rộng và delegation gần như không kiểm soát được. Token-based delegation tách authorization server, client và resource server.

## 3. How does it work?

```text
User → Client → Authorization Server
                │
                ├── ID Token → Client identity/session context
                └── Access Token → Resource API

Client ── Access Token ──► API
```

API phải validate issuer, audience, signature, lifetime và policy/claims phù hợp. Token “decode được” không có nghĩa token trusted.

## 4. Practical implementation

```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = configuration["Identity:Authority"];
        options.Audience = "orders-api";
    });
```

Authorization tiếp tục bằng policy/claims; authentication thành công không có nghĩa caller được phép thực hiện mọi operation.

## 5. Real production scenario

SPA đăng nhập qua OIDC nhận ID token và access token. Developer gửi ID token tới Orders API vì “nó cũng là JWT”. API chấp nhận sai audience/purpose tạo trust-boundary bug.

## 6. Failure scenario & troubleshooting

**Symptom** → token từ client app khác vẫn gọi được API.  
**Evidence** → validation bỏ qua audience hoặc issuer quá rộng.  
**Hypothesis** → API chỉ kiểm signature/lifetime.  
**Diagnosis** → inspect token `iss`, `aud`, scopes/roles và validation config.  
**Fix** → strict issuer/audience validation và authorization policy.  
**Verification** → negative tests với token đúng signature nhưng sai audience/scope.

## 7. Common mistakes

Dùng ID token làm API access token; chỉ base64-decode JWT; lưu access token trong unsafe browser storage không đánh giá XSS; dùng roles/scopes lẫn lộn; log raw token; tin claim từ unvalidated token.

## 8. Alternatives

Cookie authentication phù hợp server-rendered web apps. Managed Identity/client credentials phù hợp service-to-service tùy environment. API key đơn giản hơn cho một số machine integrations nhưng capability/rotation model khác.

## 9. Trade-offs

### Advantages

Delegated access, centralized identity, scoped authorization và interoperability.

### Costs / Risks

Protocol/config complexity, token leakage risk và trust boundaries dễ cấu hình sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt authentication và authorization.

### Middle

Validate JWT và implement policies.

### Senior

Reason về issuer/audience/scope/token lifetime và threat model.

### Technical Lead / Architect

Định nghĩa identity topology, trust boundaries và service-to-service strategy.

## 11. Key takeaway

- ID Token nói với client về authentication; Access Token dùng cho resource API.
- JWT format không tạo trust.
- Authorization phải explicit sau authentication.

# 4. EF Core `ExecuteUpdate` / `ExecuteDelete`: set-based mutation và Change Tracker boundary

## 1. What is it?

`ExecuteUpdate` và `ExecuteDelete` cho phép EF Core thực hiện set-based SQL mutation trực tiếp mà không load entities vào memory và không đi qua normal Change Tracker/`SaveChanges` pipeline.

## 2. Why does it exist?

Để deactivate 100.000 expired sessions, load từng row → track → modify → `SaveChanges` vừa tốn memory vừa tạo unnecessary data transfer. Database vốn có thể xử lý operation đó bằng một `UPDATE`.

## 3. How does it work?

```text
LINQ filter
   │
   ▼
ExecuteUpdate/Delete
   │
   ▼
Direct SQL UPDATE/DELETE
   │
   └── Change Tracker không được đồng bộ tự động
```

Đây là boundary quan trọng: tracked entity đã tồn tại trong `DbContext` có thể trở thành stale sau bulk mutation.

## 4. Practical implementation

```csharp
var affected = await db.Sessions
    .Where(x => x.ExpiresAt < now && x.IsActive)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.IsActive, false), ct);
```

Không cần gọi `SaveChangesAsync` cho operation này. Nếu cần atomicity với nhiều operations, tạo transaction explicit phù hợp.

## 5. Real production scenario

Nightly cleanup deactivate hàng triệu rows. Chuyển từ entity-by-entity update sang set-based update giảm round trips và memory đáng kể. Nhưng audit/domain-event logic từng chạy trong `SaveChanges` interceptor không còn tự động chạy.

## 6. Failure scenario & troubleshooting

**Symptom** → DB đã update nhưng code tiếp tục đọc giá trị cũ từ tracked entity.  
**Evidence** → cùng `DbContext` đã track entity trước `ExecuteUpdate`.  
**Hypothesis** → tracker stale.  
**Diagnosis** → inspect tracked entries và SQL.  
**Fix** → tránh mixing, clear/reload tracker hoặc tách context/use case.  
**Verification** → integration test cùng transaction/context boundary.

## 7. Common mistakes

Giả định interceptors/domain events giống `SaveChanges`; quên transaction boundary; bulk update aggregate state mà bỏ invariants; mix tracked entities với direct mutation; không kiểm `affected` rows khi concurrency quan trọng.

## 8. Alternatives

Normal tracked update phù hợp domain-rich mutation. Raw SQL phù hợp SQL-specific operations nhưng giảm type/query integration. Dedicated bulk libraries có capability khác và cần đánh giá riêng.

## 9. Trade-offs

### Advantages

Ít round trips, ít allocation, tận dụng set-based database engine.

### Costs / Risks

Bypass tracking hooks/invariants, stale state và transaction semantics phải explicit.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu tracked update vs direct SQL mutation.

### Middle

Dùng set-based operation cho bulk maintenance.

### Senior

Đánh giá hooks, concurrency và transaction implications.

### Technical Lead / Architect

Quy định boundary nơi bulk mutation được phép bypass domain model.

## 11. Key takeaway

- Set-based mutation là performance tool nhưng đổi semantics.
- Không giả định Change Tracker biết database vừa thay đổi.
- Domain invariants quyết định có nên bypass entity lifecycle hay không.

# 5. PostgreSQL MVCC: vì sao read không đơn giản là “không lock”

## 1. What is it?

PostgreSQL dùng Multi-Version Concurrency Control (MVCC): mỗi SQL statement nhìn thấy một snapshot dữ liệu phù hợp với transaction isolation. Update tạo row version mới thay vì overwrite đơn giản theo cách reader phải chờ writer cho mọi read.

## 2. Why does it exist?

Nếu readers và writers luôn block nhau, throughput transactional workload giảm mạnh. MVCC cho phép nhiều reads tiếp tục trên committed versions trong khi writes diễn ra.

## 3. How does it work?

```text
Row version V1 ── visible to older snapshot
      │ UPDATE
      ▼
Row version V2 ── visible to newer eligible snapshot

Old/dead tuples → VACUUM cleanup/reuse
```

MVCC không có nghĩa “PostgreSQL không lock”. Writers vẫn có row/table-level locking interactions; DDL và explicit locking vẫn có thể block.

## 4. Practical implementation

Troubleshooting bắt đầu bằng transaction state:

```sql
SELECT pid, state, xact_start, query_start, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE state <> 'idle';
```

Long-running transactions có thể giữ old snapshots và ngăn cleanup của dead tuples.

## 5. Real production scenario

Một reporting transaction mở hàng giờ trong production. OLTP updates vẫn chạy nhưng dead tuples tích tụ, table/index bloat và vacuum không reclaim được như kỳ vọng. Root cause không phải “VACUUM hỏng” mà là snapshot lifetime.

## 6. Failure scenario & troubleshooting

**Symptom** → storage/bloat tăng và query chậm dần.  
**Evidence** → long-running/idle-in-transaction sessions và dead tuples cao.  
**Hypothesis** → old snapshots cản vacuum progress.  
**Diagnosis** → `pg_stat_activity`, vacuum statistics và transaction age.  
**Fix** → giới hạn transaction lifetime, sửa app transaction boundaries, tune vacuum sau khi hiểu workload.  
**Verification** → dead tuple/bloat trend và query latency ổn định.

## 7. Common mistakes

Giữ transaction quanh user interaction; nghĩ read-only transaction vô hại; disable autovacuum để “giảm CPU”; gọi mọi blocking là MVCC issue; không monitor idle-in-transaction.

## 8. Alternatives

Lock-based engines có concurrency behavior khác. Read replicas tách reporting load nhưng replication lag/snapshot semantics lại trở thành concern mới.

## 9. Trade-offs

### Advantages

Reader/writer concurrency tốt và snapshot semantics mạnh.

### Costs / Risks

Dead tuples, vacuum requirement, storage amplification và transaction-lifetime discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu row versions và snapshots.

### Middle

Nhận diện long transaction/locking.

### Senior

Reason về vacuum, bloat và isolation behavior.

### Technical Lead / Architect

Thiết kế OLTP/reporting boundaries và operational guardrails cho transaction lifetime.

## 11. Key takeaway

- MVCC giảm reader/writer blocking nhưng không loại bỏ locking.
- Transaction lifetime ảnh hưởng storage và vacuum.
- “Idle in transaction” là production smell cần theo dõi.

# 6. Cosmos DB partition key: data distribution, RU và hot partition

## 1. What is it?

Partition key quyết định cách Cosmos DB nhóm logical items và phân phối chúng lên physical partitions. Đây là quyết định data model + scalability; không chỉ là field bắt buộc khi tạo container.

## 2. Why does it exist?

Distributed database cần chia dữ liệu và throughput. Nếu workload có thể phân bố theo key tốt, reads/writes scale horizontally. Nếu phần lớn traffic dồn vào một key/range, tổng provisioned throughput lớn vẫn không cứu được hot partition.

## 3. How does it work?

```text
Items + partition-key value
          │ hash/distribution
          ▼
Logical partitions
          │
          ▼
Physical partitions
```

Queries có partition key cụ thể thường tránh fan-out. Cross-partition query phải đọc nhiều partitions và có thể tiêu thụ RU cao hơn.

## 4. Practical implementation

Ví dụ multi-tenant container:

```json
{
  "id": "order-123",
  "tenantId": "tenant-42",
  "customerId": "customer-9",
  "status": "Paid"
}
```

Nếu access pattern chủ yếu `tenantId + orderId`, `/tenantId` có thể hợp lý; nhưng cần kiểm tenant size/traffic skew trước khi quyết định.

## 5. Real production scenario

SaaS có 50.000 tenants nhưng một enterprise tenant tạo 60% traffic. `/tenantId` nhìn có cardinality tốt nhưng runtime workload vẫn tạo hot logical partition. Data cardinality không đồng nghĩa traffic distribution tốt.

## 6. Failure scenario & troubleshooting

**Symptom** → 429 throttling dù tổng RU chưa dùng hết như kỳ vọng.  
**Evidence** → normalized RU consumption cao ở một partition key range.  
**Hypothesis** → hot partition.  
**Diagnosis** → phân tích request distribution theo key và query fan-out.  
**Fix** → redesign/hierarchical partitioning phù hợp, distribute write workload hoặc tách extreme tenant khi business cho phép.  
**Verification** → RU/latency phân bố đều hơn và 429 giảm.

## 7. Common mistakes

Chọn key chỉ vì unique; dùng timestamp gây write hotspot; chọn random key rồi mọi query cross-partition; bỏ qua logical partition limits; nghĩ autoscale giải quyết mọi hotspot.

## 8. Alternatives

SQL database phù hợp khi relational transactions/query flexibility quan trọng hơn global distribution. MongoDB sharding có shard-key trade-offs tương tự nhưng operational/model semantics khác.

## 9. Trade-offs

### Advantages

Horizontal scale, locality và efficient targeted operations khi key phù hợp.

### Costs / Risks

Partition-key decision khó đổi, access pattern bị ràng buộc và skew tạo throttling/cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định data placement.

### Middle

Thiết kế key theo query/access pattern.

### Senior

Đánh giá RU, skew, hot partitions và growth.

### Technical Lead / Architect

Chọn partition strategy từ workload forecast và tenant isolation requirements.

## 11. Key takeaway

- Partition key là architecture decision.
- Cardinality cao chưa đủ; traffic phải phân bố hợp lý.
- Query locality và write distribution cần được cân bằng.

# 7. Elasticsearch aliases: zero-downtime reindexing và consistency với primary database

## 1. What is it?

Elasticsearch alias là tên logic trỏ tới một hoặc nhiều indices. Search application gọi alias thay vì hard-code physical index name. Alias tạo indirection cần thiết để reindex/version schema rồi chuyển traffic atomically ở cluster metadata level.

## 2. Why does it exist?

Mapping/analyzer changes thường yêu cầu index mới và reindex dữ liệu. Nếu application gọi trực tiếp `products-v1`, deployment phải phối hợp chặt với migration. Alias cho phép `products-read` chuyển từ `products-v1` sang `products-v2` mà client contract không đổi.

## 3. How does it work?

```text
Search API → alias: products-read
                    │
                    ├── before → products-v1
                    └── after  → products-v2

DB → sync pipeline → new index
```

Alias switch chỉ giải quyết routing. Nó không tự bảo đảm `v2` đã đồng bộ hoàn toàn với primary database.

## 4. Practical implementation

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v1", "alias": "products-read" } },
    { "add":    { "index": "products-v2", "alias": "products-read" } }
  ]
}
```

Trước switch cần validate document count, representative queries, mappings, lag và indexing errors.

## 5. Real production scenario

E-commerce đổi analyzer cho product search. Team build `products-v2`, backfill từ DB, replay changes phát sinh trong lúc backfill, validate rồi switch alias. Nếu chỉ snapshot DB rồi reindex, updates xảy ra giữa quá trình có thể bị mất trong search index mới.

## 6. Failure scenario & troubleshooting

**Symptom** → sau alias switch, một số products biến mất hoặc stale.  
**Evidence** → reindex bắt đầu từ snapshot nhưng không replay concurrent DB changes.  
**Hypothesis** → synchronization gap.  
**Diagnosis** → compare source-of-truth versions/timestamps với indexed docs.  
**Fix** → backfill + CDC/outbox replay + reconciliation trước switch.  
**Verification** → consistency checks và shadow queries trước/after cutover.

## 7. Common mistakes

Coi `_reindex` là toàn bộ migration strategy; delete old index ngay lập tức; hard-code index names; không có rollback alias; dùng Elasticsearch làm transactional source of truth.

## 8. Alternatives

Dual-read/shadow-read có thể validate trước cutover nhưng phức tạp hơn. Database full-text search đủ cho use case đơn giản và giảm synchronization burden.

## 9. Trade-offs

### Advantages

Cutover nhanh, rollback đơn giản hơn và decouple client khỏi physical index lifecycle.

### Costs / Risks

Cần double storage trong migration, synchronization/reconciliation pipeline và operational discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt alias và physical index.

### Middle

Build/reindex/switch alias an toàn.

### Senior

Thiết kế catch-up, validation và rollback.

### Technical Lead / Architect

Định nghĩa search-index lifecycle và consistency contract với source of truth.

## 11. Key takeaway

- Alias giải quyết cutover, không giải quyết data synchronization.
- Reindex production cần backfill + catch-up + validation.
- Primary database vẫn phải sở hữu transactional truth.

# 8. Transactional Outbox: atomic business write và reliable event publication

## 1. What is it?

Transactional Outbox ghi business state và event/message record vào cùng local database transaction. Một publisher riêng đọc outbox rồi gửi message tới broker. Pattern này tránh distributed transaction giữa database và message broker.

## 2. Why does it exist?

Naive flow:

```text
1. UPDATE Order
2. Publish OrderPaid
```

Nếu process crash giữa bước 1 và 2, database đã commit nhưng event mất. Đảo thứ tự thì event có thể được publish trong khi DB transaction thất bại.

## 3. How does it work?

```text
DB transaction
 ├── update Order
 └── insert OutboxMessage
          │ commit atomically
          ▼
Outbox Publisher
          │ retry
          ▼
Message Broker
          │
          ▼
Idempotent Consumer
```

Outbox tạo reliable **at-least-once publication**, không tạo exactly-once end-to-end. Publisher có thể gửi message rồi crash trước khi mark published, dẫn tới duplicate.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

order.MarkPaid();
db.OutboxMessages.Add(new OutboxMessage(
    Guid.NewGuid(),
    "OrderPaid",
    JsonSerializer.Serialize(new { order.Id })));

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Publisher cần claim/batch/retry và cleanup strategy; consumers cần deduplication/idempotency.

## 5. Real production scenario

Checkout service commit payment/order state rồi phát event cho fulfillment. Outbox bảo đảm event không mất chỉ vì broker tạm unavailable ngay thời điểm transaction commit.

## 6. Failure scenario & troubleshooting

**Symptom** → consumer nhận cùng event hai lần.  
**Evidence** → publisher sent successfully nhưng crash trước `PublishedAt` update.  
**Hypothesis** → expected at-least-once replay.  
**Diagnosis** → correlate message ID, outbox row và broker delivery.  
**Fix** → idempotent consumer/inbox; không cố “fix” bằng assuming send+mark atomic.  
**Verification** → fault-injection crash giữa send và mark-published.

## 7. Common mistakes

Outbox insert ngoài business transaction; publisher không có retry/backoff; giữ rows mãi không cleanup; event payload chứa mutable references; consumer không idempotent; gọi pattern là exactly-once.

## 8. Alternatives

CDC có thể publish database changes mà giảm app publisher logic nhưng event semantics cần thiết kế kỹ. Distributed transaction chỉ khả thi trong giới hạn platform và thường tăng coupling/availability cost.

## 9. Trade-offs

### Advantages

Atomic local write, broker outage tolerance và clear recovery path.

### Costs / Risks

Eventual consistency, duplicate delivery, outbox table growth và publisher operations.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dual-write failure.

### Middle

Implement outbox transaction + publisher.

### Senior

Thiết kế dedup, ordering, cleanup và monitoring.

### Technical Lead / Architect

Quyết định consistency boundary và event ownership giữa services.

## 11. Key takeaway

- Outbox giải quyết atomic DB-write/event-intent, không giải quyết exactly-once.
- Duplicate delivery là expected condition.
- Fault injection là cách tốt để verify pattern.

# 9. Azure Blob Storage SAS: delegation, least privilege và upload architecture

## 1. What is it?

Shared Access Signature (SAS) cấp quyền giới hạn tới Azure Storage resource trong thời gian và phạm vi xác định mà không đưa storage account key cho client. Với Blob Storage, SAS thường dùng để client upload/download trực tiếp mà application không proxy toàn bộ bytes.

## 2. Why does it exist?

Nếu browser upload file 5 GB qua ASP.NET Core chỉ để application chuyển tiếp sang Blob Storage, app chịu bandwidth, connection lifetime và memory/streaming complexity không cần thiết. SAS cho phép control plane và data plane tách nhau.

## 3. How does it work?

```text
Client ── authenticate ──► API
                           │ authorize
                           ▼
                    issue short-lived SAS
                           │
Client ───────── direct upload ───────► Blob Storage
                           │
                           ▼
                    completion/event
```

Ưu tiên User Delegation SAS khi architecture phù hợp vì authorization dựa trên Microsoft Entra credentials thay vì account key.

## 4. Practical implementation

API nên tạo blob name server-side và scope quyền tối thiểu, ví dụ chỉ `Create/Write` vào một object cụ thể trong vài phút. Không cấp container-wide read/write SAS nếu client chỉ cần upload một file.

Pseudo-flow:

```csharp
// 1. authorize caller
// 2. create server-owned blob path
// 3. generate short-lived write-only SAS
// 4. return upload URL + required headers
```

Sau upload, backend không nên tin filename/content-type từ client như security proof; cần validation/scanning workflow phù hợp.

## 5. Real production scenario

CMS cho editors upload video lớn. API cấp 10-minute SAS cho blob path mới; browser upload trực tiếp. Background pipeline scan/transcode rồi mới mark asset publishable.

## 6. Failure scenario & troubleshooting

**Symptom** → leaked upload URL vẫn dùng được lâu hoặc ghi vào nhiều blobs.  
**Evidence** → SAS expiry dài và scope container-wide.  
**Hypothesis** → excessive delegation.  
**Diagnosis** → inspect permissions/resource scope/expiry.  
**Fix** → short TTL, object-level scope, least privilege và server-generated paths.  
**Verification** → negative tests sau expiry và với path khác.

## 7. Common mistakes

Đưa account key vào frontend; SAS sống hàng ngày/tháng; cấp delete/list không cần thiết; dùng predictable blob path gây overwrite; coi SAS là file-content validation; log full SAS URL.

## 8. Alternatives

Backend-proxied upload phù hợp file nhỏ hoặc cần synchronous inspection. Managed Identity phù hợp server-to-storage access nhưng không trực tiếp cấp browser quyền. CDN/signed delivery mechanism có mục tiêu khác cho downloads.

## 9. Trade-offs

### Advantages

Giảm app bandwidth, scale upload tốt và giữ credential chính khỏi client.

### Costs / Risks

Delegated URL là bearer capability; revocation khó hơn nếu TTL dài; client flow và post-upload validation phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Không expose account key.

### Middle

Tạo short-lived scoped SAS.

### Senior

Thiết kế upload state machine, validation và abuse controls.

### Technical Lead / Architect

Tách control plane/data plane và đặt identity/network/security boundaries.

## 11. Key takeaway

- SAS là delegated capability; ai có URL có thể dùng quyền được cấp trong lifetime của nó.
- Scope và TTL phải tối thiểu.
- Direct upload vẫn cần server-side authorization và post-upload trust validation.

# 10. SLI/SLO/Error Budget: biến reliability thành engineering decision

## 1. What is it?

SLI (Service Level Indicator) là measurement về behavior người dùng quan tâm, ví dụ successful request ratio hoặc latency. SLO (Service Level Objective) là target cho SLI trong một window. Error budget là lượng unreliability được phép trong target đó.

## 2. Why does it exist?

“Service phải luôn ổn định” không actionable. 100% availability thường cực đắt và không thực tế. SLO biến reliability thành measurable contract nội bộ để cân bằng feature velocity với risk.

## 3. How does it work?

Ví dụ availability SLO 99.9% trong 30 ngày:

```text
Allowed bad fraction = 0.1%
30 days ≈ 43,200 minutes
Error budget ≈ 43.2 minutes equivalent unavailability
```

Quan trọng hơn raw downtime là định nghĩa **good event / valid event** đúng với user experience.

## 4. Practical implementation

Một API SLI có thể là:

```text
good requests = HTTP requests hoàn thành < 500 ms và không phải 5xx
valid requests = tất cả eligible user requests
SLI = good / valid
SLO = 99.5% trong rolling 28 days
```

Không nên dùng CPU utilization làm SLI trực tiếp nếu user không quan tâm CPU; CPU là diagnostic metric.

## 5. Real production scenario

Search API có average latency 120 ms nhưng p99 thường 4 s. Average dashboard xanh trong khi một nhóm users gặp trải nghiệm tệ. Latency SLO theo request threshold/percentile làm tail problem trở nên visible và actionable.

## 6. Failure scenario & troubleshooting

**Symptom** → team “đạt SLO” nhưng customers vẫn phàn nàn.  
**Evidence** → SLI chỉ đo process uptime, bỏ dependency failures và latency.  
**Hypothesis** → indicator không phản ánh user journey.  
**Diagnosis** → map request path và customer-visible failure modes.  
**Fix** → redefine SLI ở service boundary/user outcome.  
**Verification** → incidents thực tế làm SLI degrade tương ứng.

## 7. Common mistakes

SLO = SLA; chọn 99.99% vì nghe tốt; alert trên mọi metric; không có window; loại bỏ lỗi “khó chịu” khỏi denominator; error budget tồn tại trên dashboard nhưng không ảnh hưởng release decisions.

## 8. Alternatives

SLA là external/business commitment có consequence khác. Operational thresholds vẫn hữu ích cho capacity nhưng không thay user-centric SLO. Apdex đơn giản hóa UX latency nhưng ít expressive hơn custom SLIs.

## 9. Trade-offs

### Advantages

Reliability measurable, prioritization rõ hơn, alerts gắn với user impact và release risk.

### Costs / Risks

SLI design khó; telemetry quality phải tốt; SLO quá chặt tạo operational burden, quá lỏng mất ý nghĩa.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt metric, SLI và SLO.

### Middle

Tạo dashboard từ user-facing indicators.

### Senior

Thiết kế burn-rate alerts và incident correlation.

### Technical Lead / Architect

Dùng error budget để quyết định release velocity, reliability investment và architectural risk.

## 11. Key takeaway

- SLO phải đo điều user thực sự trải nghiệm.
- Error budget biến reliability thành finite engineering resource.
- Average latency hiếm khi đủ để quản lý production reliability.

# Overall Takeaways

- Performance primitives như `ValueTask<T>` hay EF Core set-based mutation chỉ có giá trị khi hiểu semantics mà chúng bypass hoặc làm phức tạp.
- Reliability bắt đầu bằng admission và trust boundaries: rate limiter bảo vệ capacity; OAuth/OIDC validation bảo vệ identity boundary; SAS bảo vệ delegated storage access.
- Distributed data systems buộc engineer suy nghĩ theo data placement và versioning: PostgreSQL MVCC quản lý row versions, Cosmos DB partition key quản lý distribution, Elasticsearch alias quản lý index lifecycle.
- Reliable messaging không đồng nghĩa exactly-once. Transactional Outbox làm dual-write an toàn hơn nhưng consumers vẫn phải chịu duplicate delivery.
- Senior/Lead reasoning cần chuyển từ component metric sang user outcome: SLI/SLO là ví dụ điển hình của việc biến telemetry thành engineering policy.
