# 1. CLR GC generations và promotion: vì sao object sống lâu làm GC đắt hơn

## 1. What is it?

.NET Garbage Collector chia managed heap thành generations. Mental model quan trọng không phải “Gen 0 nhanh, Gen 2 chậm” đơn thuần, mà là giả định phần lớn object chết trẻ. Object sống qua collection sẽ được promote và trở nên đắt hơn để thu gom về sau.

## 2. Why does it exist?

Nếu GC phải scan toàn heap cho mọi allocation pressure, pause và CPU cost sẽ tăng mạnh. Generational GC tận dụng thực tế request-scoped temporary objects thường chết nhanh, trong khi số object sống lâu nhỏ hơn.

## 3. How does it work?

Allocation thường bắt đầu ở Gen 0. Khi Gen 0 collection chạy, object còn reachable sống sót và có thể được promote. Gen 1 đóng vai trò buffer; Gen 2 chứa long-lived objects. Large Object Heap có behavior riêng và thường liên quan allocation lớn.

```text
Allocate → Gen 0 → survive → Gen 1 → survive → Gen 2
             ↓ dead       ↓ dead       ↓ expensive collection
```

GC roots như static fields, active stack references và object graph quyết định reachability, không phải “object còn được business sử dụng hay không”.

## 4. Practical implementation

Một cache không bounded có thể vô tình giữ object graph sống lâu:

```csharp
public sealed class BadCache
{
    private readonly ConcurrentDictionary<string, byte[]> _items = new();

    public void Add(string key, byte[] value)
        => _items[key] = value;
}
```

Production cache phải có ownership, eviction/TTL và memory budget. Đừng “fix GC” trước khi sửa lifetime của object.

## 5. Real production scenario

Một API deserialize payload lớn rồi lưu DTO vào singleton dictionary để “tối ưu”. Memory tăng chậm trong nhiều giờ. Gen 2 heap tăng, full GC thường xuyên hơn, p99 latency xấu dần dù request rate không đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng và latency spike định kỳ. **Evidence** → GC metrics cho Gen 2 size/collection tăng; heap dump cho thấy dictionary giữ object graph. **Hypothesis** → unintended long-lived retention. **Diagnosis** → inspect GC roots. **Fix** → bounded cache/TTL hoặc bỏ cache. **Verification** → load soak test cho thấy heap đạt steady state và Gen 2 pressure giảm.

## 7. Common mistakes

Gọi mọi memory growth là memory leak; ép `GC.Collect()`; tối ưu allocation nhỏ trong khi singleton giữ hàng GB; giữ scoped objects qua static events; cache không eviction.

## 8. Alternatives

Pooling như `ArrayPool<T>` có thể giảm allocation cho hot buffers nhưng cũng giữ memory và tăng complexity. Streaming/batching có thể giảm peak allocation mà không cần pooling.

## 9. Trade-offs

### Advantages

Generational GC làm common short-lived allocation rất hiệu quả và giảm manual memory management.

### Costs / Risks

Long-lived graphs, LOH pressure và excessive allocation vẫn tạo CPU/pause cost; tuning GC không thay thế lifetime design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu reachability và generations thay vì nghĩ GC “xóa object sau khi method kết thúc”.

### Middle

Biết đọc basic GC counters và tránh accidental long-lived references.

### Senior

Phân tích allocation rate, Gen 2, LOH và heap roots trước khi tối ưu.

### Technical Lead / Architect

Quyết định cache/pooling có thực sự cần thiết, đặt memory budget và operational telemetry cho chúng.

## 11. Key takeaway

- GC tối ưu cho object chết trẻ; retention làm chi phí tăng.
- Memory issue cần evidence từ counters/dump/roots.
- Đừng dùng `GC.Collect()` để che lifetime design sai.

# 2. ASP.NET Core graceful shutdown: drain request và CancellationToken khi deploy

## 1. What is it?

Graceful shutdown là quá trình instance ngừng nhận work mới, cho work đang chạy cơ hội hoàn thành trong giới hạn thời gian, rồi giải phóng resources trước khi process bị terminate.

## 2. Why does it exist?

Deploy, autoscale, recycle và node maintenance đều có thể dừng process. Nếu application coi shutdown là sự kiện bất ngờ duy nhất, request đang ghi DB, upload file hoặc background processing có thể bị cắt giữa chừng.

## 3. How does it work?

Host nhận termination signal, dừng acceptance/routing tùy platform, phát cancellation tới hosted services và chờ shutdown timeout. Application phải propagate cancellation tới I/O thay vì nuốt token.

```text
Termination signal
→ stop new work
→ cancel/drain active work
→ dispose resources
→ process exits
```

## 4. Practical implementation

```csharp
public sealed class QueueWorker(ChannelReader<Job> reader) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in reader.ReadAllAsync(stoppingToken))
            await ProcessAsync(job, stoppingToken);
    }
}
```

Long-running work cần checkpoint/idempotency nếu không thể đảm bảo hoàn thành trong shutdown window.

## 5. Real production scenario

App Service slot swap hoặc Kubernetes rolling update dừng instance đang xử lý file 2 phút. Nếu shutdown window chỉ 30 giây, worker cần thiết kế resumable processing thay vì hy vọng process sống đủ lâu.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate hoặc partial jobs sau deploy. **Evidence** → logs kết thúc giữa processing, job được queue redeliver. **Hypothesis** → work không idempotent và shutdown token không được xử lý. **Fix** → idempotency/checkpoint, stop fetching new jobs khi shutdown, propagate cancellation. **Verification** → terminate instance giữa job và xác nhận replay an toàn.

## 7. Common mistakes

Nuốt `CancellationToken`; bắt `OperationCanceledException` rồi retry; bắt đầu work mới sau shutdown; giả định graceful shutdown luôn có vô hạn thời gian; background task fire-and-forget ngoài host lifecycle.

## 8. Alternatives

Short synchronous request có thể chỉ cần host defaults. Long-running work thường phù hợp queue + Worker/Functions hơn HTTP request kéo dài.

## 9. Trade-offs

### Advantages

Deploy/recycle ít gây lỗi, giảm partial work và cải thiện reliability.

### Costs / Risks

Drain window kéo dài deployment; application vẫn phải chịu hard termination và thiết kế recovery.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process có lifecycle và cancellation là cooperative.

### Middle

Propagate token qua DB/HTTP/background work.

### Senior

Thiết kế idempotency, checkpoint và shutdown tests.

### Technical Lead / Architect

Chọn workload placement và shutdown SLO; không đặt unbounded work vào lifecycle không phù hợp.

## 11. Key takeaway

- Graceful shutdown không đảm bảo mọi work sẽ hoàn thành.
- Cancellation phải được propagate, không chỉ truyền cho có.
- Long-running work cần recovery/idempotency.

# 3. EF Core optimistic concurrency: concurrency token thay vì khóa dài transaction

## 1. What is it?

Optimistic concurrency giả định conflict không thường xuyên. Application đọc entity cùng concurrency token, sau đó update chỉ khi token vẫn khớp. Nếu người khác đã sửa trước, update ảnh hưởng 0 rows và EF Core báo concurrency conflict.

## 2. Why does it exist?

Giữ database lock từ lúc user mở form tới lúc bấm Save là không thực tế: request stateless, thời gian người dùng không bounded và lock contention cao. Optimistic concurrency phát hiện stale write tại thời điểm commit.

## 3. How does it work?

Với SQL Server `rowversion`, EF tạo điều kiện tương tự:

```sql
UPDATE Employees
SET Title = @p0
WHERE Id = @id AND RowVersion = @originalRowVersion;
```

Nếu row đã đổi, predicate không match và EF ném `DbUpdateConcurrencyException`.

## 4. Practical implementation

```csharp
public class Employee
{
    public int Id { get; set; }
    public string Title { get; set; } = "";
    [Timestamp]
    public byte[] RowVersion { get; set; } = [];
}

try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    // Reload, merge, or return 409 based on business semantics.
    throw;
}
```

## 5. Real production scenario

Hai managers cùng sửa employee profile. Manager A đổi title, Manager B save stale form sau đó. Không có concurrency control, B có thể silently overwrite A.

## 6. Failure scenario & troubleshooting

**Symptom** → user thấy dữ liệu vừa sửa bị “mất”. **Evidence** → audit cho hai updates sát nhau, last-write-wins. **Hypothesis** → không có concurrency token. **Fix** → token + conflict UX/business merge policy. **Verification** → integration test hai DbContexts update cùng row và second save phải conflict.

## 7. Common mistakes

Catch exception rồi retry cùng stale values; coi mọi conflict là HTTP 500; dùng timestamp thời gian với precision không đáng tin; token không đi qua API round-trip; generic repository che mất original values.

## 8. Alternatives

Pessimistic locking phù hợp critical short transactions có contention semantics rõ. Application-level version number cũng có thể dùng. Last-write-wins hợp lệ khi business chấp nhận.

## 9. Trade-offs

### Advantages

Không giữ lock qua user think-time; scale tốt khi conflicts hiếm; phát hiện lost update.

### Costs / Risks

Cần merge/retry UX và business policy; conflict cao có thể làm workflow khó dùng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hai request có thể đọc cùng state rồi ghi đè nhau.

### Middle

Implement token và handle exception.

### Senior

Thiết kế merge/reload/reject policy theo aggregate invariant.

### Technical Lead / Architect

Quyết định nơi optimistic concurrency đủ, nơi cần serialization/locking hoặc workflow khác.

## 11. Key takeaway

- Concurrency control bảo vệ lost updates, không chỉ database errors.
- Retry mù có thể tái tạo overwrite.
- Conflict resolution là business decision.

# 4. SQL Server parameter sniffing: cùng query nhưng execution plan có thể trở thành regression

## 1. What is it?

Parameter sniffing xảy ra khi SQL Server compile plan dựa trên parameter values thấy lúc compilation và reuse plan đó cho executions sau. Đây thường là optimization tốt, nhưng data distribution skew có thể làm plan tốt cho giá trị A rất tệ cho B.

## 2. Why does it exist?

Compile execution plan có chi phí. Plan cache giúp giảm compilation và tận dụng statistics. Vấn đề xuất hiện khi một plan không phù hợp cho mọi parameter shape.

## 3. How does it work?

Query `WHERE TenantId = @tenantId` có thể có tenant 100 rows và tenant 20 triệu rows. Plan chọn từ một tenant nhỏ có thể dùng access strategy không phù hợp tenant lớn, hoặc ngược lại.

## 4. Practical implementation

```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE TenantId = @tenantId
  AND CreatedAt >= @from;
```

Investigation cần actual execution plan, Query Store, statistics, row estimates vs actual rows. Không bắt đầu bằng việc thêm index hoặc `OPTION(RECOMPILE)` cho mọi query.

## 5. Real production scenario

SaaS API chỉ chậm với enterprise tenant lớn sau deployment/recompile. Average latency vẫn bình thường vì phần lớn tenants nhỏ.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng endpoint lúc nhanh lúc chậm theo tenant. **Evidence** → Query Store có plan regression; estimated/actual cardinality khác lớn. **Hypothesis** → plan reuse + skew. **Diagnosis** → compare plans/parameters/statistics. **Fix** → có thể query rewrite, better indexing/statistics, plan forcing hoặc targeted recompilation tùy evidence. **Verification** → test representative small/large parameter sets và p95/p99.

## 7. Common mistakes

Gọi mọi slow query là parameter sniffing; xóa plan cache production; dùng `RECOMPILE` toàn hệ thống; chỉ test với một tenant; bỏ qua stale statistics.

## 8. Alternatives

Query Store plan forcing có thể ổn định regression. Dynamic SQL hoặc separate query shapes đôi khi phù hợp skew rõ. Mỗi lựa chọn có compile/maintenance cost.

## 9. Trade-offs

### Advantages

Plan reuse giảm CPU compilation và thường rất hiệu quả.

### Costs / Risks

Skew làm một cached plan không đại diện cho mọi workload; mitigation sai có thể tăng CPU hoặc khóa plan không còn tối ưu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SQL text giống nhau không đồng nghĩa runtime cost giống nhau.

### Middle

Đọc execution plan và statistics cơ bản.

### Senior

Dùng Query Store, cardinality evidence và representative workload.

### Technical Lead / Architect

Thiết kế multi-tenant data/access pattern và performance regression process thay vì chữa từng query bằng hint.

## 11. Key takeaway

- Plan cache là optimization, không phải lỗi.
- Data skew có thể làm reused plan nguy hiểm.
- Diagnose bằng plan + cardinality + representative parameters.

# 5. Elasticsearch aliases và zero-downtime reindexing

## 1. What is it?

Alias là logical name trỏ tới một hoặc nhiều Elasticsearch indexes. Nó cho phép application query tên ổn định trong khi physical index được rebuild/versioned phía sau.

## 2. Why does it exist?

Mapping/analyzer changes thường cần reindex. Nếu application hard-code index `products-v1`, migration sang `v2` đòi coordinated deploy hoặc downtime.

## 3. How does it work?

```text
Search API → products-read alias → products-v1
                         reindex ↓
                             products-v2
Atomic alias switch → products-v2
```

Primary database vẫn là source of truth; reindex cần chiến lược đồng bộ changes xảy ra trong migration window.

## 4. Practical implementation

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v1", "alias": "products-read" }},
    { "add":    { "index": "products-v2", "alias": "products-read" }}
  ]
}
```

Switch aliases trong một aliases request giúp thay đổi routing atomically ở cluster metadata level.

## 5. Real production scenario

E-commerce thay analyzer để cải thiện autocomplete. Team tạo `products-v2`, bulk reindex, catch up changes, validate search quality rồi switch alias mà Search API không đổi configuration.

## 6. Failure scenario & troubleshooting

**Symptom** → sau switch, một số sản phẩm mới biến mất. **Evidence** → v2 snapshot/reindex kết thúc nhưng changes phát sinh trong lúc rebuild không được replay. **Hypothesis** → synchronization gap. **Fix** → CDC/outbox/replay watermark hoặc controlled dual-write strategy. **Verification** → compare counts/checksums/sample business queries trước switch.

## 7. Common mistakes

Coi alias switch là toàn bộ zero-downtime solution; không xử lý writes trong reindex; xóa v1 ngay lập tức; mapping không được validation; Elasticsearch trở thành transactional truth.

## 8. Alternatives

In-place updates phù hợp changes tương thích nhỏ. Database full-text search có thể đủ nếu search requirements đơn giản và không cần Elasticsearch operational burden.

## 9. Trade-offs

### Advantages

Stable application endpoint, rollback nhanh và safer index evolution.

### Costs / Risks

Tạm thời cần gấp đôi storage, reindex load, sync complexity và validation tooling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu alias tách logical search name khỏi physical index.

### Middle

Tạo versioned index và atomic switch.

### Senior

Thiết kế catch-up, validation, rollback và capacity.

### Technical Lead / Architect

Quyết định Elasticsearch có đáng tồn tại và ai sở hữu data synchronization/recovery.

## 11. Key takeaway

- Alias giải routing/versioning, không tự giải consistency.
- Reindex phải xử lý concurrent changes.
- Giữ rollback path cho tới khi validation hoàn tất.

# 6. Bulkhead Pattern: chặn một dependency lỗi ăn hết tài nguyên hệ thống

## 1. What is it?

Bulkhead cô lập capacity giữa workloads/dependencies để failure hoặc saturation của một vùng không tiêu thụ toàn bộ shared resource như threads, connections hoặc concurrency slots.

## 2. Why does it exist?

Timeout/retry không đủ nếu 5.000 requests cùng chờ một review provider chậm. Chúng có thể chiếm connection/concurrency, làm cả endpoints không liên quan cũng chậm.

## 3. How does it work?

```text
Product requests ── capacity A ── Product DB
Review requests  ── capacity B ── Review API
```

Khi B đầy, system fail fast/degrade reviews thay vì cho B kéo A xuống.

## 4. Practical implementation

```csharp
private readonly SemaphoreSlim _reviewSlots = new(50);

public async Task<ReviewResult?> GetReviewsAsync(CancellationToken ct)
{
    if (!await _reviewSlots.WaitAsync(TimeSpan.FromMilliseconds(50), ct))
        return null; // explicit degraded behavior

    try { return await reviewClient.GetAsync(ct); }
    finally { _reviewSlots.Release(); }
}
```

Production có thể dùng resilience pipeline/library, nhưng capacity và fallback semantics vẫn phải do application quyết định.

## 5. Real production scenario

Product page gọi CMS, Product API, Reviews và Recommendations. Reviews timeout 10 giây. Không isolation, request concurrency tăng đến mức product core cũng 503. Bulkhead + short timeout cho reviews giữ page core hoạt động.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency nhỏ outage nhưng toàn API p99 tăng. **Evidence** → active requests/connections tập trung ở dependency call. **Hypothesis** → resource exhaustion propagation. **Fix** → bounded concurrency, timeout và degraded response. **Verification** → fault injection vào Reviews và core endpoint vẫn đạt SLO.

## 7. Common mistakes

Bulkhead limit tùy ý không load test; queue vô hạn trước semaphore; retry bên trong saturated bulkhead; fallback che dependency outage khỏi monitoring.

## 8. Alternatives

Circuit Breaker giảm calls khi failure rõ; rate limiting bảo vệ ingress; queue tách asynchronous workload. Chúng bổ sung chứ không đồng nghĩa Bulkhead.

## 9. Trade-offs

### Advantages

Failure isolation và predictable resource usage.

### Costs / Risks

Có thể reject work sớm; capacity tuning khó; thêm metrics/configuration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một dependency chậm có thể làm cạn shared resources.

### Middle

Implement bounded concurrency và timeout.

### Senior

Đo saturation, queueing và fallback correctness.

### Technical Lead / Architect

Xác định critical vs optional dependencies và allocate failure budgets/capacity boundaries.

## 11. Key takeaway

- Reliability cần giới hạn resource, không chỉ retries.
- Optional dependency không nên kéo core flow xuống.
- Bulkhead cần bounded queue và telemetry.

# 7. Azure Blob Storage SAS: delegated access mà không phát tán storage credentials

## 1. What is it?

Shared Access Signature cấp quyền giới hạn theo resource, action và thời gian cho Blob Storage mà không trao storage account key cho client.

## 2. Why does it exist?

Nếu browser/mobile upload file qua backend, backend phải relay bytes tốn bandwidth. Nếu trao account key cho client, blast radius quá lớn. SAS cho phép direct upload với capability giới hạn.

## 3. How does it work?

```text
Client → API (authorized request)
API → issue short-lived SAS
Client → Blob Storage directly
Blob → event/queue → processing
```

API vẫn quyết định user có quyền nhận SAS; SAS không thay application authorization.

## 4. Practical implementation

```csharp
var sas = new BlobSasBuilder
{
    BlobContainerName = container,
    BlobName = blobName,
    Resource = "b",
    ExpiresOn = DateTimeOffset.UtcNow.AddMinutes(10)
};
sas.SetPermissions(BlobSasPermissions.Create | BlobSasPermissions.Write);
```

Trong Azure, ưu tiên user delegation SAS với Microsoft Entra credentials/Managed Identity khi phù hợp thay vì account key.

## 5. Real production scenario

CMS cho editor upload video 500 MB. API xác thực editor, tạo blob name server-side và short-lived write-only SAS; browser upload trực tiếp Blob Storage.

## 6. Failure scenario & troubleshooting

**Symptom** → leaked SAS vẫn đọc được sensitive files. **Evidence** → token có read/list permissions và expiry dài. **Hypothesis** → over-privileged SAS. **Fix** → minimum permissions, short expiry, resource-specific scope, rotate/revoke mechanism phù hợp. **Verification** → security test token không thể list/read ngoài intended operation.

## 7. Common mistakes

Expiry hàng ngày/tuần; cấp container-level khi chỉ cần blob; cho read+write+delete mặc định; log full SAS URL; coi SAS như identity của user.

## 8. Alternatives

Backend proxy upload đơn giản hơn cho file nhỏ/strict inspection. Managed Identity phù hợp service-to-service. Public blob chỉ phù hợp dữ liệu thực sự public.

## 9. Trade-offs

### Advantages

Giảm backend bandwidth, scale upload tốt và giới hạn quyền tốt hơn account key.

### Costs / Risks

Bearer token có thể bị leak trong lifetime; CORS/upload lifecycle/security scanning cần thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SAS là delegated temporary capability.

### Middle

Tạo scope/expiry/permissions đúng.

### Senior

Thiết kế upload validation, malware scanning, lifecycle và audit.

### Technical Lead / Architect

Chọn direct vs proxied upload theo security, file size, cost và compliance.

## 11. Key takeaway

- SAS phải short-lived và least privilege.
- Application authorization diễn ra trước khi cấp SAS.
- Không log hoặc phát tán SAS URL như URL bình thường.

# 8. OpenTelemetry correlation: nối Logs + Metrics + Traces trong incident investigation

## 1. What is it?

Correlation là khả năng dùng cùng context như TraceId/SpanId và dimensions để chuyển từ metric symptom sang trace cụ thể rồi tới logs liên quan.

## 2. Why does it exist?

Một dashboard nói p95 tăng nhưng không cho biết request nào, dependency nào hay code path nào. Logs riêng lẻ lại thiếu hệ thống context. Kết hợp signals tạo investigation chain.

## 3. How does it work?

```text
Alert/Metric spike
→ filter route/version/region
→ representative trace
→ slow/error span
→ correlated structured logs
→ root-cause evidence
```

W3C trace context được propagate qua HTTP/messaging; logs cần capture trace identifiers tự động hoặc qua logging integration.

## 4. Practical implementation

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation());

logger.LogInformation(
    "Checkout failed for OrderId {OrderId} Provider {Provider}",
    orderId, provider);
```

Structured properties phải hữu ích nhưng không chứa secrets/PII tùy tiện.

## 5. Real production scenario

Alert báo checkout p95 tăng. Metric dimension cho thấy region West Europe. Trace cho thấy payment dependency 4 giây; correlated log chứa provider timeout category và deployment version mới.

## 6. Failure scenario & troubleshooting

**Symptom** → logs có hàng triệu lines nhưng không nối được request. **Evidence** → outbound custom client không propagate trace headers; background message mất context. **Diagnosis** → instrumentation/context propagation gap. **Fix** → standard instrumentation và message correlation conventions. **Verification** → synthetic transaction có end-to-end trace qua API → queue → worker.

## 7. Common mistakes

Log plain strings; tự tạo correlation ID nhưng không propagate; high-cardinality metric dimensions như user ID; log secrets; sampling làm mất mọi error traces.

## 8. Alternatives

Application Insights auto-instrumentation có thể giảm setup; custom telemetry cần khi domain signals đặc thù. Không có một signal nào thay thế hoàn toàn ba loại Logs/Metrics/Traces.

## 9. Trade-offs

### Advantages

Giảm mean time to diagnose và tạo evidence xuyên distributed boundaries.

### Costs / Risks

Telemetry volume/cost, cardinality, privacy và sampling complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu metric phát hiện, trace localize, log cung cấp detail.

### Middle

Instrument HTTP/dependencies và structured logging.

### Senior

Thiết kế sampling, dimensions, message propagation và incident queries.

### Technical Lead / Architect

Định nghĩa observability conventions/SLO và budget xuyên services.

## 11. Key takeaway

- Observability mạnh khi signals liên kết được với nhau.
- Structured context quan trọng hơn số lượng log lines.
- Trace propagation phải vượt HTTP và messaging boundaries.

# 9. Playwright E2E: test user journey nhưng kiểm soát flakiness và test data

## 1. What is it?

Playwright E2E test chạy browser thật/engine tương ứng để kiểm tra critical user journey xuyên frontend, API và các integration cần thiết. Giá trị của E2E là bảo vệ wiring và behavior end-to-end, không phải thay unit/integration tests.

## 2. Why does it exist?

Frontend unit tests và backend integration tests đều có thể pass nhưng login redirect, CORS, routing, deployment config hoặc API contract wiring vẫn hỏng khi ghép hệ thống.

## 3. How does it work?

Test khởi tạo deterministic state, mở browser, tương tác qua user-visible semantics, assert outcome và cleanup/isolate state. Auto-waiting giúp giảm manual sleeps nhưng không sửa test design không deterministic.

## 4. Practical implementation

```typescript
import { test, expect } from '@playwright/test';

test('manager approves timesheet', async ({ page }) => {
  await page.goto('/timesheets/42');
  await page.getByRole('button', { name: 'Approve' }).click();
  await expect(page.getByText('Approved')).toBeVisible();
});
```

Test data nên được tạo qua fixture/API/database strategy có ownership rõ, không phụ thuộc record shared cố định.

## 5. Real production scenario

Release đổi auth callback path. Unit tests xanh nhưng production login loop. Một smoke E2E trên deployed environment phát hiện redirect chain trước promotion.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail ngẫu nhiên CI nhưng rerun pass. **Evidence** → hard-coded timeout, shared test user/state, dependency bên ngoài biến động. **Hypothesis** → nondeterministic environment/test. **Fix** → isolated data, semantic locators, deterministic waits, stub only external systems không thuộc test scope. **Verification** → chạy lặp suite nhiều lần và theo dõi flake rate.

## 7. Common mistakes

`waitForTimeout(5000)`; selector dựa CSS implementation; mọi case đều E2E; dùng production-like shared account; rerun để che flake; mock cả backend rồi vẫn gọi test là end-to-end.

## 8. Alternatives

Unit tests nhanh cho pure logic; integration tests bảo vệ DB/API boundaries; contract tests bảo vệ compatibility. E2E nên tập trung critical journeys và deployment wiring.

## 9. Trade-offs

### Advantages

Bắt integration/configuration regressions mà lower-level tests bỏ sót.

### Costs / Risks

Chậm, tốn infrastructure, data management khó và dễ flaky nếu scope quá rộng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu E2E test user behavior, không test DOM internals.

### Middle

Viết stable locators/fixtures và debug traces/screenshots.

### Senior

Thiết kế test pyramid theo risk, quản lý data và flake budget.

### Technical Lead / Architect

Quyết định journeys nào đáng E2E và quality gates nào chạy PR vs post-deploy.

## 11. Key takeaway

- E2E bảo vệ critical wiring, không thay mọi test layer.
- Flaky test là defect cần xử lý, không phải noise bình thường.
- Deterministic test data quan trọng ngang test code.

# 10. Git bisect: tìm commit gây regression bằng binary search

## 1. What is it?

`git bisect` dùng binary search trên commit history giữa một commit known-good và known-bad để tìm commit đầu tiên gây regression.

## 2. Why does it exist?

Nếu regression xuất hiện trong 500 commits, checkout từng commit tuần tự rất tốn thời gian. Binary search giảm số lần kiểm tra xuống khoảng log2(N).

## 3. How does it work?

Git checkout commit giữa range. Bạn test và đánh dấu `good` hoặc `bad`; Git loại nửa range và lặp lại tới khi xác định culprit.

## 4. Practical implementation

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
# run test
git bisect good   # or bad
git bisect reset
```

Nếu có deterministic script:

```bash
git bisect run dotnet test tests/Regression.Tests
```

Exit code của script quyết định good/bad.

## 5. Real production scenario

API serialization thay đổi sau hai tuần development nhưng PR chứa nhiều unrelated commits. Một regression test tái tạo bug cho phép `git bisect run` tìm commit đổi custom converter.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit không liên quan hoặc kết quả thay đổi mỗi lần. **Evidence** → test flaky, commit trung gian không build, environment state không reset. **Hypothesis** → oracle good/bad không deterministic. **Fix** → tạo minimal deterministic reproduction; dùng `git bisect skip` khi commit không test được. **Verification** → culprit commit fail, parent pass nhiều lần.

## 7. Common mistakes

Bisect khi chưa có reproduction; đánh dấu good/bad dựa cảm giác; quên reset DB/environment; history commits quá lớn và không build độc lập; kết luận causation mà không inspect diff.

## 8. Alternatives

Query deployment telemetry khi regression map rõ release; profiler/traces khi bug không liên quan code change cụ thể; manual history inspection cho range rất nhỏ.

## 9. Trade-offs

### Advantages

Thu hẹp regression nhanh, đặc biệt khi có automated deterministic test.

### Costs / Risks

Phụ thuộc history testable và reliable oracle; merge-heavy history có thể khó diễn giải.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết good/bad boundary và binary search mental model.

### Middle

Tạo reproduction và chạy bisect thủ công/tự động.

### Senior

Kết hợp bisect với telemetry, regression tests và root-cause review.

### Technical Lead / Architect

Khuyến khích commits/release history đủ testable và incident workflow biến production bug thành permanent regression test.

## 11. Key takeaway

- `git bisect` mạnh khi có deterministic good/bad test.
- Tìm culprit commit không đồng nghĩa đã hiểu root cause.
- Production regression nên trở thành automated regression test.
