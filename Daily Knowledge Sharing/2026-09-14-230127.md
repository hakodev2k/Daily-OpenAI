# 1. C# Source Generators: chuyển một phần reflection/runtime discovery sang compile-time code generation để giảm startup cost và tăng tính kiểm tra được

## 1. What is it?

Source Generator là cơ chế trong Roslyn cho phép analyzer chạy trong quá trình compilation, đọc syntax/semantic model rồi sinh thêm source code để compiler tiếp tục compile cùng project.

Mental model:

```text
Your source code
      ↓
Roslyn compilation
      ↓
Source Generator inspects symbols
      ↓
Generated .cs files
      ↓
Final compilation
```

Nó đặc biệt hữu ích cho những việc trước đây thường cần reflection lúc runtime: serializer metadata, mapper code, strongly typed bindings hoặc registration boilerplate.

## 2. Why does it exist?

Reflection rất linh hoạt nhưng có chi phí:

* runtime discovery,
* startup overhead,
* khó trim/AOT,
* lỗi chỉ xuất hiện khi application chạy,
* hidden control flow khó trace.

Source Generator đổi một phần chi phí đó sang compile time. Nếu generator biết structure của type trước khi application chạy, code có thể được sinh tĩnh và compiler kiểm tra bình thường.

## 3. How does it work?

Incremental Source Generator thường đăng ký pipeline dựa trên syntax/attributes rồi chỉ recompute phần bị ảnh hưởng khi code thay đổi.

Ví dụ conceptual:

```csharp
[Generator]
public sealed class EndpointGenerator : IIncrementalGenerator
{
    public void Initialize(IncrementalGeneratorInitializationContext context)
    {
        var candidates = context.SyntaxProvider
            .ForAttributeWithMetadataName(
                "MyApp.GenerateEndpointAttribute",
                static (node, _) => node is ClassDeclarationSyntax,
                static (ctx, _) => (INamedTypeSymbol)ctx.TargetSymbol);

        context.RegisterSourceOutput(candidates, static (spc, symbol) =>
        {
            spc.AddSource(
                $"{symbol.Name}.g.cs",
                $$"""
                partial class {{symbol.Name}}
                {
                    public static string GeneratedName => "{{symbol.Name}}";
                }
                """);
        });
    }
}
```

Generated code là source thật trong compilation, không phải dynamic IL bí mật sau startup.

## 4. Practical implementation

Một use case thực tế là `System.Text.Json` source generation:

```csharp
[JsonSerializable(typeof(OrderDto))]
[JsonSerializable(typeof(List<OrderDto>))]
public partial class ApiJsonContext : JsonSerializerContext
{
}
```

Sau đó:

```csharp
var json = JsonSerializer.Serialize(order, ApiJsonContext.Default.OrderDto);
```

Điểm đáng giá là serializer metadata được chuẩn bị ở compile time, phù hợp hơn với Native AOT/trimming và giảm runtime reflection.

## 5. Real production scenario

Một API có nhiều DTO và cold start quan trọng vì chạy trên autoscaled container. Reflection-based metadata initialization làm startup tốn thêm CPU và gây tail latency ở instance mới.

Team chuyển serialization path sang source-generated metadata. Startup giảm và AOT compatibility tốt hơn. Nhưng họ không viết custom generator cho mọi mapping nhỏ vì maintenance cost của generator cao hơn vài dòng code thủ công.

## 6. Failure scenario & troubleshooting

**Symptom** → generated code không xuất hiện hoặc compile output thiếu type mong đợi.

**Evidence** → attribute/syntax filter không match symbol sau refactor namespace.

**Hypothesis** → generator pipeline phụ thuộc brittle string metadata name hoặc syntax shape.

**Diagnosis** → inspect generated files, analyzer diagnostics và intermediate output.

**Fix** → dùng semantic symbol matching ổn định, emit diagnostic rõ ràng, thêm tests cho generator.

**Verification** → compile clean project, inspect generated source và test AOT/trimming nếu đó là mục tiêu.

## 7. Common mistakes

* Viết generator chỉ để loại bỏ vài dòng boilerplate không đáng kể.
* Generate code khó đọc, khó debug và không emit diagnostics hữu ích.
* Dùng syntax-only reasoning khi cần semantic model.
* Tạo output không deterministic làm incremental build kém hiệu quả.
* Cho rằng compile-time generation luôn nhanh hơn runtime trong mọi workload.

## 8. Alternatives

* Reflection: linh hoạt, đơn giản hơn cho low-frequency code paths.
* T4/templates: phù hợp một số build-time generation workflow nhưng ít tích hợp semantic model hơn.
* Handwritten code: đôi khi rõ nhất và rẻ nhất.
* Expression trees/runtime compilation: phù hợp khi behavior phụ thuộc runtime metadata.

## 9. Trade-offs

### Advantages

* Compile-time validation tốt hơn.
* Giảm runtime reflection và startup work.
* Hữu ích cho trimming/Native AOT.
* Generated code có thể được inspect/debug.

### Costs / Risks

* Generator là compiler extension, độ phức tạp cao hơn application code bình thường.
* Debugging pipeline build khó hơn.
* Roslyn APIs và semantic edge cases cần expertise.
* Có thể làm build chậm nếu incremental design kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Source Generator sinh C# trước khi final compilation, không phải magic runtime.

### Middle

Biết dùng generator có sẵn như `System.Text.Json` source generation và inspect `.g.cs` khi lỗi.

### Senior

Đánh giá startup/runtime benefit, AOT requirement, build cost và maintainability trước khi tự viết generator.

### Technical Lead / Architect

Quyết định generator có giải quyết constraint thật hay chỉ chuyển complexity từ runtime sang build pipeline.

## 11. Key takeaway

* Source Generator đổi runtime discovery thành compile-time code khi metadata đã biết trước.
* Giá trị lớn nhất nằm ở performance/AOT/type safety, không phải giảm mọi boilerplate.
* Custom generator chỉ đáng dùng khi lợi ích vượt maintenance cost của compiler-level tooling.

# 2. ASP.NET Core Forwarded Headers: tin đúng reverse proxy boundary để scheme, host và client IP không bị giả mạo hoặc hiểu sai

## 1. What is it?

Trong production, ASP.NET Core thường không trực tiếp nhận request từ Internet. Request đi qua CDN, load balancer, reverse proxy hoặc ingress.

Do đó application nhìn thấy connection trực tiếp từ proxy, không nhất thiết là client thật.

Forwarded headers như:

* `X-Forwarded-For`
* `X-Forwarded-Proto`
* `X-Forwarded-Host`

cho phép proxy truyền lại thông tin upstream.

## 2. Why does it exist?

Nếu application không hiểu proxy boundary:

* `Request.Scheme` có thể thành `http` dù client dùng HTTPS,
* redirect URL có thể sai,
* secure cookie behavior có thể sai,
* audit log ghi IP của proxy thay vì client,
* rate limiting theo IP có thể vô nghĩa.

Ngược lại, nếu tin forwarded headers từ mọi nguồn, attacker có thể tự gửi header giả.

## 3. How does it work?

Flow điển hình:

```text
Client HTTPS
   ↓
Reverse Proxy
   ├─ terminates TLS
   ├─ X-Forwarded-Proto: https
   └─ X-Forwarded-For: client-ip
   ↓ HTTP/private network
ASP.NET Core
```

Application chỉ nên process forwarded headers khi request đến từ trusted proxy/network.

## 4. Practical implementation

```csharp
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders =
        ForwardedHeaders.XForwardedFor |
        ForwardedHeaders.XForwardedProto;

    options.KnownProxies.Add(IPAddress.Parse("10.0.0.10"));
});

var app = builder.Build();

app.UseForwardedHeaders();
```

Middleware phải chạy đủ sớm trước logic phụ thuộc scheme/client IP.

Nếu platform tự quản lý trusted proxy chain, configuration cần bám đúng deployment architecture, không copy một đoạn config giữa môi trường.

## 5. Real production scenario

Một ASP.NET Core app sau Application Gateway redirect login callback về `http://...` thay vì `https://...`, khiến OIDC redirect URI mismatch.

Application thực ra chạy HTTP phía sau TLS termination. `X-Forwarded-Proto` có giá trị `https`, nhưng middleware chưa được cấu hình đúng.

Sau khi trust đúng proxy và process forwarded headers, generated redirect URL phản ánh scheme của client.

## 6. Failure scenario & troubleshooting

**Symptom** → audit log cho thấy mọi request đến từ cùng một IP hoặc redirect scheme sai.

**Evidence** → raw headers có `X-Forwarded-*`, nhưng `HttpContext.Connection.RemoteIpAddress`/`Request.Scheme` không thay đổi.

**Hypothesis** → middleware thiếu, sai order hoặc proxy không nằm trong trust list.

**Diagnosis** → log direct peer IP, forwarded chain và middleware order tại một environment test.

**Fix** → cấu hình trusted proxies/networks và đặt middleware đúng vị trí.

**Verification** → kiểm tra HTTPS redirect, callback URL, IP-based policy và spoof attempt từ untrusted source.

## 7. Common mistakes

* Clear `KnownNetworks`/`KnownProxies` rồi tin mọi forwarded header.
* Dùng raw `X-Forwarded-For` trực tiếp cho authorization.
* Không hiểu nhiều proxy tạo ra một chain IP.
* Đặt middleware sau authentication/redirect logic.
* Giả định local development networking giống production ingress.

## 8. Alternatives

* PROXY protocol ở Layer 4 trong một số topology.
* Platform-specific integration middleware.
* Không dùng client IP cho security-sensitive identity nếu có lựa chọn tốt hơn.

## 9. Trade-offs

### Advantages

* Application hiểu đúng external scheme/client connection metadata.
* Logging, redirects và security behavior nhất quán với reverse proxy topology.

### Costs / Risks

* Trust boundary cấu hình sai có thể tạo spoofing vulnerability.
* Multi-proxy chains khó reason hơn.
* Infrastructure change có thể yêu cầu app config change.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu application phía sau proxy không trực tiếp nhìn thấy client connection.

### Middle

Biết dùng `UseForwardedHeaders` và kiểm tra middleware order.

### Senior

Đánh giá trusted proxy chain, spoofing risk và ảnh hưởng tới auth/rate limiting/logging.

### Technical Lead / Architect

Định nghĩa ingress trust boundary rõ ràng giữa CDN, WAF, reverse proxy và application.

## 11. Key takeaway

* Forwarded headers là trust-boundary feature, không chỉ networking convenience.
* Chỉ tin header từ proxy/network đã xác định.
* Scheme, host và client IP sai có thể kéo theo lỗi authentication, redirect và security policy.

# 3. EF Core `IDbContextFactory<TContext>`: tạo `DbContext` đúng lifetime cho parallel work, background jobs và UI/server scenarios

## 1. What is it?

`IDbContextFactory<TContext>` là factory tạo `DbContext` theo nhu cầu thay vì phụ thuộc hoàn toàn vào một scoped `DbContext` được inject sẵn.

Mental model:

```text
Factory
  ├─ Create context A → operation A → dispose
  ├─ Create context B → operation B → dispose
  └─ Create context C → operation C → dispose
```

Mỗi context có lifetime ngắn, độc lập và không được dùng concurrent.

## 2. Why does it exist?

`DbContext` không thread-safe và thường được thiết kế như unit-of-work ngắn.

Một HTTP request đơn giản dùng scoped context rất phù hợp. Nhưng các tình huống sau cần boundary khác:

* background worker,
* parallel tasks,
* Blazor Server circuit sống lâu,
* một scope cần nhiều unit-of-work độc lập.

Giữ một context quá lâu tạo stale tracking state và memory growth; dùng cùng context song song gây exception hoặc race-like behavior.

## 3. How does it work?

Registration:

```csharp
builder.Services.AddDbContextFactory<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Consumer tạo context khi cần:

```csharp
await using var db = await _factory.CreateDbContextAsync(ct);
```

Context này phải được dispose bởi caller.

## 4. Practical implementation

Background worker:

```csharp
public sealed class ReconciliationWorker(
    IDbContextFactory<AppDbContext> factory)
{
    public async Task ReconcileAsync(Guid batchId, CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);

        var batch = await db.Batches
            .SingleAsync(x => x.Id == batchId, ct);

        batch.MarkStarted();
        await db.SaveChangesAsync(ct);
    }
}
```

Nếu chạy nhiều items song song, mỗi task tạo context riêng thay vì share một context.

## 5. Real production scenario

Một worker xử lý 20 messages concurrently nhưng inject một scoped `DbContext` ở worker lifetime rồi dùng chung. Production xuất hiện:

`A second operation was started on this context instance before a previous operation completed.`

Chuyển sang factory giúp mỗi message sở hữu unit-of-work riêng và giảm coupling giữa concurrency model với DI scope.

## 6. Failure scenario & troubleshooting

**Symptom** → intermittent EF Core concurrency exception hoặc entity state bất ngờ giữa operations.

**Evidence** → cùng context instance được capture bởi nhiều task.

**Hypothesis** → lifetime boundary không khớp concurrency boundary.

**Diagnosis** → log context identity/scope, inspect worker construction và parallel loop.

**Fix** → tạo context riêng cho từng independent operation.

**Verification** → stress test với concurrency cao và assert transaction/state isolation.

## 7. Common mistakes

* Share một `DbContext` giữa `Task.WhenAll` branches.
* Dùng factory nhưng quên dispose context.
* Tạo context mới quá tùy tiện trong cùng business transaction rồi mất transaction boundary.
* Dùng long-lived context làm cache entity.
* Nghĩ factory tự động làm code thread-safe.

## 8. Alternatives

* Scoped `DbContext`: tốt nhất cho request/unit-of-work đơn giản.
* `IServiceScopeFactory`: hữu ích khi background flow cần tạo cả scope DI, không chỉ context.
* `PooledDbContextFactory`: giảm allocation trong hot path nhưng cần state hygiene nghiêm ngặt.

## 9. Trade-offs

### Advantages

* Lifetime rõ ràng theo operation.
* Hữu ích cho concurrent/background scenarios.
* Giảm stale tracking state của long-lived context.

### Costs / Risks

* Caller phải quản lý disposal.
* Dễ vô tình chia business operation thành nhiều transactions.
* Tăng số context/connection acquisitions nếu dùng quá vụn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbContext` là unit-of-work và không thread-safe.

### Middle

Biết tạo/dispose context bằng factory trong worker hoặc parallel flow.

### Senior

Thiết kế lifetime theo transaction/concurrency boundary và tránh context fragmentation.

### Technical Lead / Architect

Quy định pattern dùng scoped context, factory và pooled factory theo workload thay vì một rule chung cho toàn codebase.

## 11. Key takeaway

* `DbContext` lifetime phải khớp unit-of-work, không khớp lifetime của service một cách máy móc.
* Parallel operations cần context độc lập.
* Factory giải quyết lifetime creation, không tự giải quyết transaction design.

# 4. SQL window functions: tính ranking, running totals và top-N-per-group mà không biến query thành chuỗi self-join khó tối ưu

## 1. What is it?

Window function tính giá trị trên một tập rows liên quan nhưng không collapse rows như `GROUP BY`.

Ví dụ:

```sql
SELECT
    EmployeeId,
    DepartmentId,
    Salary,
    ROW_NUMBER() OVER (
        PARTITION BY DepartmentId
        ORDER BY Salary DESC
    ) AS SalaryRank
FROM Employees;
```

Mỗi employee vẫn tồn tại như một row, nhưng có thêm rank trong department.

## 2. Why does it exist?

Nhiều bài toán cần vừa giữ detail row vừa tính aggregate/ranking:

* top 3 sản phẩm mỗi category,
* running balance,
* previous/next event,
* percentile/rank,
* rolling metrics.

Nếu chỉ dùng subquery/self-join, query thường dài hơn, khó reason và đôi khi tạo work lớn hơn cần thiết.

## 3. How does it work?

Cú pháp chính:

```text
function() OVER (
  PARTITION BY ...
  ORDER BY ...
  ROWS/RANGE ...
)
```

`PARTITION BY` chia logical groups.

`ORDER BY` xác định thứ tự trong mỗi partition.

Window frame xác định rows nào tham gia calculation cho current row.

## 4. Practical implementation

Top 2 orders có giá trị cao nhất mỗi customer:

```sql
WITH RankedOrders AS
(
    SELECT
        Id,
        CustomerId,
        TotalAmount,
        ROW_NUMBER() OVER (
            PARTITION BY CustomerId
            ORDER BY TotalAmount DESC, Id DESC
        ) AS rn
    FROM Orders
)
SELECT Id, CustomerId, TotalAmount
FROM RankedOrders
WHERE rn <= 2;
```

Running total:

```sql
SUM(Amount) OVER (
    PARTITION BY AccountId
    ORDER BY PostedAt, Id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

Tie-breaker giúp ordering deterministic.

## 5. Real production scenario

Dashboard cần “3 tickets gần nhất của mỗi customer”. Team ban đầu query tất cả tickets rồi group trong application, kéo hàng triệu rows qua network.

Window function đẩy ranking xuống database và chỉ trả subset cần thiết, giảm network transfer và application memory.

## 6. Failure scenario & troubleshooting

**Symptom** → query window function chậm và spill ra temp storage.

**Evidence** → execution plan có large sort và memory grant không đủ.

**Hypothesis** → partition/order cần sort lượng dữ liệu lớn mà index không hỗ trợ.

**Diagnosis** → inspect plan, sort operator, cardinality, spills và predicate selectivity.

**Fix** → giảm input sớm, xem xét supporting index theo partition/order, hoặc materialize summary nếu workload phù hợp.

**Verification** → so sánh logical reads, spill warning và elapsed time.

## 7. Common mistakes

* Dùng `RANK`, `DENSE_RANK`, `ROW_NUMBER` mà không hiểu khác biệt tie behavior.
* Không thêm deterministic tie-breaker.
* Dùng window function trên toàn bảng rồi filter quá muộn.
* Giả định syntax đẹp đồng nghĩa execution rẻ.
* Không đọc execution plan cho dataset production-scale.

## 8. Alternatives

* `GROUP BY`: tốt khi thực sự cần collapse rows.
* Correlated subquery: có thể hợp lý cho một số selective query.
* Application-side aggregation: chỉ phù hợp khi dataset đã nhỏ.
* Precomputed/materialized summary: tốt cho analytics read-heavy ổn định.

## 9. Trade-offs

### Advantages

* Biểu diễn ranking/analytics rõ ràng.
* Giữ detail rows trong cùng query.
* Thường tránh round trip hoặc application processing thừa.

### Costs / Risks

* Sort/partition lớn có thể tốn memory/I/O.
* Index strategy phức tạp với nhiều window definitions.
* Không thay thế việc đọc execution plan.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu window function tính trên nhóm rows nhưng không collapse output.

### Middle

Dùng `ROW_NUMBER`, `LAG`, `SUM OVER` cho query thực tế.

### Senior

Đọc sort/spill/memory behavior trong execution plan và thiết kế index dựa trên access pattern.

### Technical Lead / Architect

Quyết định analytics nên chạy on-demand trong OLTP, precompute, hay chuyển sang reporting pipeline.

## 11. Key takeaway

* Window functions giải quyết ranking/rolling analytics rất tự nhiên.
* `PARTITION BY` và `ORDER BY` là cả semantic lẫn performance concern.
* Query đẹp vẫn cần execution evidence trên dữ liệu thật.

# 5. Redis eviction policy và memory pressure: khi cache đầy, lựa chọn key nào bị loại là một quyết định reliability chứ không chỉ configuration

## 1. What is it?

Redis có giới hạn memory. Khi đạt `maxmemory`, behavior phụ thuộc eviction policy.

Ví dụ:

* `noeviction`
* `allkeys-lru`
* `allkeys-lfu`
* `volatile-lru`
* `volatile-ttl`

Policy quyết định Redis từ chối write hay loại key nào để tạo chỗ.

## 2. Why does it exist?

Cache không được phép giả định memory vô hạn.

Nếu cache tăng đến capacity:

* process có thể chịu memory pressure,
* write có thể fail,
* useful hot keys có thể bị đẩy ra,
* miss rate tăng rồi dồn tải xuống database.

Eviction policy là cách hệ thống định nghĩa degradation behavior.

## 3. How does it work?

Mental model:

```text
SET new-key
   ↓
Memory < maxmemory ? ── yes ──> store
   │ no
   ▼
Eviction policy
   ├─ evict candidate
   └─ or reject write
```

LRU ưu tiên loại key ít dùng gần đây.

LFU ưu tiên key có frequency thấp.

`volatile-*` chỉ xem xét keys có TTL, tạo behavior rất khác nếu nhiều keys không có expiry.

## 4. Practical implementation

Application cần coi cache write failure là expected dependency behavior:

```csharp
try
{
    await cache.StringSetAsync(key, payload, TimeSpan.FromMinutes(5));
}
catch (RedisException ex)
{
    logger.LogWarning(ex, "Cache write failed for {CacheKey}", key);
    // Business request may still succeed without cache.
}
```

Đồng thời monitor:

* used memory,
* evicted keys,
* hit ratio,
* command latency,
* rejected writes,
* hot keys.

## 5. Real production scenario

Một e-commerce API dùng Redis cho product data và session-like metadata. Team thêm một dataset cache mới không TTL, memory tăng nhanh. Với `volatile-lru`, Redis chỉ có thể evict keys có TTL; cuối cùng write behavior không như team mong đợi.

Root cause không phải “Redis yếu” mà là mismatch giữa data policy và eviction policy.

## 6. Failure scenario & troubleshooting

**Symptom** → database QPS tăng mạnh dù traffic không đổi.

**Evidence** → Redis evicted keys tăng, hit ratio giảm, memory sát `maxmemory`.

**Hypothesis** → memory pressure đang đẩy hot keys khỏi cache.

**Diagnosis** → inspect keyspace size, TTL distribution, large keys và eviction counters.

**Fix** → giới hạn cached dataset, chỉnh TTL/key design/capacity và chọn policy phù hợp.

**Verification** → hit ratio ổn định, eviction rate phù hợp và database load giảm.

## 7. Common mistakes

* Chỉ monitor Redis CPU mà không monitor eviction/memory.
* Không đặt TTL cho dữ liệu cache-like nhưng dùng `volatile-*` policy.
* Cache object rất lớn mà không đo serialized size.
* Tăng Redis size trước khi hiểu key growth.
* Coi cache miss storm sau eviction là vấn đề riêng của database.

## 8. Alternatives

* `IMemoryCache` cho instance-local data.
* CDN/HTTP caching cho response phù hợp.
* Không cache nếu nguồn dữ liệu đủ nhanh.
* Tách Redis workloads nếu session/queue/cache có reliability requirement khác nhau.

## 9. Trade-offs

### Advantages

* Eviction giúp Redis degrade có kiểm soát khi memory đầy.
* LRU/LFU có thể giữ data hữu ích tốt hơn random removal.

### Costs / Risks

* Eviction tạo downstream load bất ngờ.
* Policy sai với TTL distribution gây behavior khó đoán.
* Cache capacity trở thành production capacity planning concern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Redis cache có giới hạn memory và key có thể bị loại.

### Middle

Biết TTL, `maxmemory` và eviction policy ảnh hưởng cache behavior.

### Senior

Correlate eviction với miss rate/database load và phân tích keyspace growth.

### Technical Lead / Architect

Xác định Redis có phải hidden critical dependency hay không và thiết kế degradation/fallback khi cache under pressure.

## 11. Key takeaway

* Cache full là một failure mode cần thiết kế trước.
* Eviction policy phải phù hợp TTL và workload semantics.
* Monitor `evicted_keys` + hit ratio + downstream load, không chỉ Redis uptime.

# 6. Modular Monolith với bounded modules: giữ deployment đơn giản nhưng vẫn cô lập domain boundaries, data ownership và dependency direction

## 1. What is it?

Modular Monolith là một application deploy như một unit nhưng bên trong được chia thành các modules có boundary rõ ràng.

Mental model:

```text
Single deployment
┌───────────────────────────────┐
│ Orders module                 │
│ Billing module                │
│ Inventory module              │
│ Identity module               │
└───────────────────────────────┘
```

Điểm cốt lõi không phải folder names mà là ownership và dependency constraints.

## 2. Why does it exist?

Microservices giải quyết một số vấn đề scale/ownership/deployment nhưng mang theo network failure, distributed tracing, eventual consistency, deployment orchestration và operational cost.

Một monolith không có module boundary lại dễ biến thành shared-database/shared-domain codebase nơi mọi thứ phụ thuộc mọi thứ.

Modular Monolith tìm điểm cân bằng: process đơn giản nhưng architecture bên trong có isolation.

## 3. How does it work?

Mỗi module nên sở hữu:

* application logic,
* domain model,
* persistence boundary,
* public contracts,
* integration events/internal APIs.

Một module không nên query table nội bộ của module khác chỉ vì cùng database server.

```text
Orders ──public contract/event──> Billing
  │                             │
  └ owns Orders tables          └ owns Billing tables
```

## 4. Practical implementation

Solution có thể tổ chức:

```text
Modules/
  Orders/
    Orders.Api
    Orders.Application
    Orders.Domain
    Orders.Infrastructure
  Billing/
    Billing.Api
    Billing.Application
    Billing.Domain
    Billing.Infrastructure
```

Nhưng folder layout chỉ có giá trị nếu dependency được enforce bằng project references, architecture tests hoặc visibility rules.

Ví dụ module contract:

```csharp
public interface IOrderModule
{
    Task<OrderSummary?> GetSummaryAsync(Guid orderId, CancellationToken ct);
}
```

Internal entities không được expose ra ngoài module.

## 5. Real production scenario

Một SaaS ban đầu có `Orders`, `Billing`, `Notifications`. Team cân nhắc microservices nhưng chỉ có một nhóm backend nhỏ và release cadence giống nhau.

Họ giữ single deployment nhưng tách database schemas, contracts và project references. Sau này nếu Billing thực sự cần scale/ownership độc lập, extraction boundary đã rõ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → thay đổi table Billing làm Orders build/test fail hàng loạt.

**Evidence** → Orders đọc trực tiếp Billing EF entities và DbSet.

**Hypothesis** → module boundary tồn tại trên slide nhưng không tồn tại trong dependencies.

**Diagnosis** → dependency graph + code search cross-module references.

**Fix** → tạo explicit contract/query/event, move data ownership về module sở hữu.

**Verification** → architecture tests cấm cross-internal references.

## 7. Common mistakes

* Gọi mọi folder là module nhưng dùng chung domain entities.
* Shared `Common` project chứa business logic của tất cả modules.
* Cross-module database joins trực tiếp mọi nơi.
* Dùng MediatR rồi tuyên bố đã có module boundaries.
* Chuyển sang microservices chỉ để “đúng kiến trúc”.

## 8. Alternatives

* Layered Monolith: đơn giản hơn khi business domain nhỏ.
* Microservices: hợp lý khi cần independent deployment/scale/ownership thật.
* Vertical Slice Architecture: tốt cho feature organization nhưng không tự định nghĩa bounded business modules.

## 9. Trade-offs

### Advantages

* Deployment/operations đơn giản hơn microservices.
* In-process communication nhanh, ít network failure.
* Boundary tốt giúp maintainability và future extraction.

### Costs / Risks

* Process/resource isolation vẫn dùng chung.
* Một deploy lỗi có thể ảnh hưởng toàn application.
* Boundary dễ bị phá nếu team không enforce.
* Database server chung có thể che giấu coupling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là responsibility boundary, không chỉ namespace.

### Middle

Implement code chỉ đi qua public module contract.

### Senior

Thiết kế data ownership, transactions và cross-module communication.

### Technical Lead / Architect

Quyết định modular monolith có đủ hay business/operational pressure thực sự yêu cầu service extraction.

## 11. Key takeaway

* Modular Monolith tối ưu cho boundary tốt mà chưa trả distributed-systems tax.
* Data ownership và dependency enforcement quan trọng hơn folder structure.
* Microservice extraction nên là response cho pressure thật, không phải mục tiêu mặc định.

# 7. Azure Service Bus Sessions: giữ ordering theo business key mà không ép toàn queue thành single-threaded bottleneck

## 1. What is it?

Azure Service Bus Sessions nhóm messages có cùng `SessionId` thành một ordered logical stream.

Ví dụ:

```text
Order-100: Created → Paid → Shipped
Order-200: Created → Cancelled
```

Hai order có thể xử lý song song, nhưng messages trong cùng session được consumer có session lock xử lý theo thứ tự nhận.

## 2. Why does it exist?

Một queue thông thường với nhiều competing consumers tối ưu throughput nhưng không đảm bảo business ordering toàn cục.

Nếu workflow yêu cầu message `Paid` không được xử lý trước `Created` cho cùng order, cần một coordination key.

Global single-thread processing giữ order nhưng phá scalability.

Sessions tạo ordering theo partition logic/business key.

## 3. How does it work?

Publisher đặt:

```csharp
new ServiceBusMessage(body)
{
    SessionId = orderId.ToString()
};
```

Session-aware receiver accept một session và giữ exclusive lock cho session đó trong lúc processing.

```text
Session A → Consumer 1
Session B → Consumer 2
Session C → Consumer 3
```

Ordering chỉ có ý nghĩa trong cùng session, không phải across all messages.

## 4. Practical implementation

Registration example:

```csharp
var processor = client.CreateSessionProcessor(
    queueName,
    new ServiceBusSessionProcessorOptions
    {
        MaxConcurrentSessions = 16,
        MaxConcurrentCallsPerSession = 1,
        AutoCompleteMessages = false
    });
```

Handler cần settlement rõ ràng:

```csharp
processor.ProcessMessageAsync += async args =>
{
    await HandleAsync(args.Message, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message, args.CancellationToken);
};
```

Idempotency vẫn cần vì at-least-once delivery không biến mất.

## 5. Real production scenario

Order workflow có events `Created`, `PaymentCaptured`, `Cancelled`. Không có session, hai consumers có thể xử lý `PaymentCaptured` trước `Created` khi queue load cao.

Dùng `SessionId = OrderId` giữ order trong từng aggregate mà vẫn cho hàng nghìn orders khác xử lý parallel.

## 6. Failure scenario & troubleshooting

**Symptom** → throughput thấp dù backlog lớn.

**Evidence** → phần lớn messages dùng cùng một `SessionId`.

**Hypothesis** → hot session biến workload thành single lane.

**Diagnosis** → đo distribution theo session, processing duration và active concurrent sessions.

**Fix** → chọn session key có cardinality phù hợp hoặc xem lại requirement ordering.

**Verification** → backlog drain rate tăng nhưng invariant per-business-key vẫn đúng.

## 7. Common mistakes

* Dùng một constant `SessionId` cho toàn queue.
* Nghĩ session đảm bảo exactly-once.
* Handler lâu nhưng không quan tâm session lock renewal.
* Poison message chặn cả session workflow mà không có DLQ strategy.
* Chọn session key theo technical convenience thay vì business ordering boundary.

## 8. Alternatives

* Không cần sessions nếu handler idempotent và ordering không quan trọng.
* Partitioned stream/event platform nếu throughput/order model khác.
* Application-level version checking để reject out-of-order events.
* Saga state machine xử lý transitions với explicit state validation.

## 9. Trade-offs

### Advantages

* Ordering theo business key.
* Parallelism across sessions.
* Natural fit cho workflows/aggregates.

### Costs / Risks

* Hot session giới hạn throughput.
* Session lock làm operational behavior phức tạp hơn.
* Requires session-aware consumers.
* Poison message có thể ảnh hưởng sequence phía sau.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue ordering toàn cục khác ordering theo `SessionId`.

### Middle

Publish/consume session messages và settle đúng.

### Senior

Thiết kế session key, concurrency, DLQ và idempotency.

### Technical Lead / Architect

Quyết định ordering requirement có thật sự cần infrastructure guarantee hay có thể giải bằng state/version semantics đơn giản hơn.

## 11. Key takeaway

* Sessions cho ordering theo key, không phải ordering toàn hệ thống.
* Session key sai có thể phá scalability.
* Ordering không thay thế idempotency và state validation.

# 8. .NET Large Object Heap và fragmentation: memory còn trống nhưng process vẫn có thể chịu GC pause và allocation pressure

## 1. What is it?

Large Object Heap (LOH) là vùng managed heap dành cho object lớn, điển hình các array/string lớn vượt threshold runtime.

Các object này thường được collect cùng Gen 2 và historically ít compact thường xuyên hơn small object heap vì moving large memory regions tốn chi phí.

Mental model:

```text
LOH
[large A][free][large B][free small][large C]
```

Tổng free memory có thể nhiều nhưng không nhất thiết có block contiguous đủ lớn cho allocation mới.

## 2. Why does it exist?

Copy/move object rất lớn trong mỗi GC sẽ rất đắt. Runtime đối xử khác với large objects để cân bằng throughput và compaction cost.

Nhưng application tạo/huỷ buffer lớn liên tục có thể gây:

* Gen 2 pressure,
* fragmentation,
* peak memory cao,
* long GC pauses.

## 3. How does it work?

Large arrays đi vào LOH. Nếu lifetime patterns xen kẽ size khác nhau, các holes xuất hiện sau collection.

GC có thể compact LOH trong một số tình huống/configuration, nhưng “cứ compact” không phải chiến lược performance bền vững.

Pinned objects còn có thể làm movement khó hơn; modern .NET có Pinned Object Heap cho một số pinned allocation scenarios.

## 4. Practical implementation

Tránh materialize payload lớn không cần thiết:

```csharp
await source.CopyToAsync(destination, bufferSize: 81920, cancellationToken);
```

Thay vì:

```csharp
var bytes = await File.ReadAllBytesAsync(path, cancellationToken);
await destination.WriteAsync(bytes, cancellationToken);
```

Với hot path cần buffer lớn, có thể cân nhắc `ArrayPool<byte>` nhưng phải quản lý ownership đúng.

## 5. Real production scenario

File-processing API đọc toàn bộ 20–50 MB file vào `byte[]`, sau đó tạo thêm compressed copy và base64 string.

Một request có thể tạo nhiều large objects cùng lúc. Traffic burst khiến process memory tăng nhanh, Gen 2 collections dày hơn và p99 latency xấu.

Thiết kế streaming giảm live-set size tốt hơn chỉ tinh chỉnh GC.

## 6. Failure scenario & troubleshooting

**Symptom** → memory graph dạng sawtooth lớn, Gen 2 GC tăng và request pause theo burst file upload.

**Evidence** → dump/gcdump cho thấy nhiều `byte[]` lớn và LOH size cao.

**Hypothesis** → whole-payload buffering tạo LOH churn.

**Diagnosis** → dùng `dotnet-counters`, `dotnet-gcdump`, allocation profiler và inspect object sizes.

**Fix** → stream, pool buffer có kiểm soát, giới hạn concurrency/payload size.

**Verification** → allocation rate, LOH size và p95/p99 giảm dưới cùng load test.

## 7. Common mistakes

* Gọi mọi memory growth là “memory leak”.
* Force `GC.Collect()` định kỳ thay vì sửa allocation pattern.
* Pool buffer lớn nhưng không giới hạn concurrency.
* Giữ reference lớn trong cache/static collection.
* Chỉ nhìn working set mà không inspect managed heap generations.

## 8. Alternatives

* Streaming I/O.
* `ArrayPool<T>`/`MemoryPool<T>` khi ownership rõ.
* Chunk processing.
* External/object storage flow thay vì đưa toàn payload qua application memory.

## 9. Trade-offs

### Advantages

* Large-object handling giúp runtime tránh move cost quá thường xuyên.
* Streaming/pooling có thể giảm LOH churn đáng kể.

### Costs / Risks

* Pooling tăng ownership complexity.
* Streaming code phức tạp hơn simple materialization.
* Compaction có thể tạo pause lớn nếu lạm dụng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu object rất lớn ảnh hưởng GC khác object nhỏ.

### Middle

Nhận diện code whole-buffer và chuyển sang streaming khi phù hợp.

### Senior

Dùng counters/dumps để phân biệt leak, retention và LOH churn.

### Technical Lead / Architect

Đặt payload/concurrency limits và chọn data flow tránh application trở thành memory buffer khổng lồ.

## 11. Key takeaway

* Memory pressure không chỉ là “còn bao nhiêu RAM”.
* Large-object allocation pattern có thể ảnh hưởng Gen 2, fragmentation và tail latency.
* Streaming thường là architectural fix tốt hơn GC tuning.

# 9. Integration testing với Testcontainers: kiểm thử behavior thật của SQL/Redis/broker mà không biến test suite thành phụ thuộc môi trường thủ công

## 1. What is it?

Testcontainers cho phép integration test khởi tạo dependency thật bằng container tạm thời: PostgreSQL, SQL Server, Redis, RabbitMQ và nhiều service khác.

Mental model:

```text
Test starts
   ↓
Start disposable container
   ↓
Run migration / seed
   ↓
Execute real integration test
   ↓
Dispose container
```

Mục tiêu là test protocol/driver/database behavior thật thay vì mock một dependency phức tạp.

## 2. Why does it exist?

Mock `DbContext`, Redis hoặc broker thường chỉ test assumptions của chính code mock.

Các lỗi quan trọng lại nằm ở:

* SQL translation,
* constraints,
* transaction behavior,
* serialization,
* network protocol,
* real client configuration.

Dùng shared dev database thủ công làm tests flaky và environment-dependent.

## 3. How does it work?

Test fixture start container với image/version xác định, lấy dynamic port/connection string rồi inject vào application under test.

Mỗi suite có thể dùng container riêng hoặc reuse theo controlled lifecycle tùy speed/isolation requirement.

## 4. Practical implementation

Ví dụ PostgreSQL với .NET Testcontainers:

```csharp
private readonly PostgreSqlContainer _postgres =
    new PostgreSqlBuilder()

        .WithDatabase("app_tests")
        .WithUsername("postgres")
        .WithPassword("postgres")
        .Build();

public async Task InitializeAsync()
{
    await _postgres.StartAsync();
}

public async Task DisposeAsync()
{
    await _postgres.DisposeAsync();
}
```

Sau đó dùng `_postgres.GetConnectionString()` cho test host, chạy migrations rồi gọi API thật.

## 5. Real production scenario

Repository layer có query LINQ dùng một function hoạt động với in-memory provider nhưng translate khác PostgreSQL production.

Unit test đều xanh; production lỗi SQL translation.

Integration test với PostgreSQL container bắt lỗi ngay trong CI vì provider thật được dùng.

## 6. Failure scenario & troubleshooting

**Symptom** → integration tests flaky hoặc CI quá chậm.

**Evidence** → mỗi test method start container riêng và migrations chạy lặp lại hàng trăm lần.

**Hypothesis** → isolation granularity quá nhỏ.

**Diagnosis** → đo startup/migration time và identify shared-safe fixture boundary.

**Fix** → reuse container per test collection, reset data bằng deterministic strategy.

**Verification** → test duration giảm mà parallel runs vẫn isolated.

## 7. Common mistakes

* Dùng `latest` image tag khiến test environment đổi bất ngờ.
* Shared container nhưng không reset data.
* Dùng containers để test mọi business rule, làm suite quá chậm.
* Bỏ qua readiness và bắt đầu test trước khi service sẵn sàng.
* Không chạy cùng major version với production dependency.

## 8. Alternatives

* Pure unit tests cho domain logic.
* Local emulator khi behavior đủ gần production.
* Dedicated shared test environment cho full E2E.
* SQLite/in-memory provider, nhưng chỉ khi provider differences không quan trọng.

## 9. Trade-offs

### Advantages

* Fidelity cao hơn mock.
* Reproducible dependency version.
* CI có thể self-contained hơn.

### Costs / Risks

* Cần container runtime.
* Startup chậm hơn unit tests.
* Test lifecycle/data reset cần thiết kế.
* Không thay thế production-like E2E cho networking/platform-specific behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu unit test và integration test bảo vệ các loại risk khác nhau.

### Middle

Viết fixture container, migration và cleanup deterministic.

### Senior

Thiết kế test pyramid dựa trên fidelity, speed và failure isolation.

### Technical Lead / Architect

Quyết định dependency nào đáng chạy thật trong CI và đặt version/environment strategy cho toàn team.

## 11. Key takeaway

* Mock database/broker không kiểm tra behavior thật của database/broker.
* Testcontainers tăng fidelity nhưng phải quản lý startup và isolation.
* Dùng đúng layer: unit tests cho logic, container integration tests cho infrastructure contracts.

# 10. Third-party API contract drift: chống schema change, timeout và semantic break bằng adapter boundary, tolerant parsing và contract monitoring

## 1. What is it?

Contract drift là khi external API thay đổi theo cách làm integration của bạn không còn đúng, dù endpoint vẫn “hoạt động”.

Drift có thể là:

* field đổi type,
* enum có value mới,
* field từng mandatory trở thành nullable,
* response semantics đổi,
* pagination/rate-limit behavior đổi,
* endpoint version bị deprecate.

## 2. Why does it exist?

Third-party API nằm ngoài control của team. Network success `200 OK` không đảm bảo business contract còn tương thích.

Nếu domain code phụ thuộc trực tiếp DTO của vendor, mỗi drift lan xuyên hệ thống và migration trở nên đắt.

## 3. How does it work?

Một integration boundary tốt:

```text
Domain/Application
      ↓
Internal interface
      ↓
Vendor adapter
      ↓
Vendor DTO / HTTP contract
      ↓
External API
```

Adapter chịu trách nhiệm mapping vendor semantics thành internal model ổn định.

## 4. Practical implementation

Internal abstraction:

```csharp
public interface IReviewProvider
{
    Task<ReviewSummary> GetSummaryAsync(
        string productId,
        CancellationToken cancellationToken);
}
```

Vendor DTO giữ riêng:

```csharp
internal sealed record VendorReviewResponse(
    double? Average,
    int? Count,
    string? Status);
```

Mapping xử lý unknown/missing data rõ ràng thay vì expose vendor DTO vào domain.

HTTP client cần timeout/retry hợp lý:

```csharp
services.AddHttpClient<IReviewProvider, VendorReviewProvider>(client =>
{
    client.BaseAddress = new Uri(configuration["Reviews:BaseUrl"]!);
    client.Timeout = TimeSpan.FromSeconds(3);
});
```

Retry chỉ áp dụng operation an toàn/idempotent và phải có budget.

## 5. Real production scenario

Review vendor thêm enum status `PARTIALLY_AVAILABLE`. Code dùng exhaustive `switch` nhưng default map thành failure, khiến product pages mất toàn bộ reviews dù data cơ bản vẫn hợp lệ.

Adapter layer được sửa để map unknown status thành degraded internal state, trong khi alert phát hiện contract drift.

## 6. Failure scenario & troubleshooting

**Symptom** → external API vẫn 200 nhưng tỷ lệ mapping error tăng sau một thời điểm cụ thể.

**Evidence** → logs cho thấy field mới/enum mới/schema mismatch.

**Hypothesis** → provider contract drift chứ không phải network outage.

**Diagnosis** → capture sanitized sample payload, compare schema/version/changelog và correlate deployment timeline.

**Fix** → tolerant parser + mapping update + contract test.

**Verification** → replay captured payloads và monitor mapping-error metric.

## 7. Common mistakes

* Reuse vendor DTO xuyên application/domain layers.
* Deserialize strict đến mức field additive cũng làm fail toàn response.
* Retry mọi 4xx/5xx không phân biệt semantics.
* Không version adapter behavior.
* Log full external payload chứa PII/secrets.
* Không monitor semantic error vì HTTP status vẫn 200.

## 8. Alternatives

* Vendor SDK: giảm HTTP boilerplate nhưng vẫn cần boundary vì SDK model cũng là external contract.
* Webhook/event integration: phù hợp nếu provider hỗ trợ push semantics.
* Cache last-known-good data: hữu ích khi stale data chấp nhận được.
* Manual fallback/process nếu dependency không critical realtime.

## 9. Trade-offs

### Advantages

* Adapter cô lập vendor change.
* Tolerant parsing tăng resilience với additive change.
* Internal model giữ semantics do business sở hữu.

### Costs / Risks

* Thêm mapping code và tests.
* Quá tolerant có thể che giấu breaking semantic change.
* Fallback/stale cache có freshness trade-off.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu remote API là unreliable external contract, không phải local method call.

### Middle

Implement typed client, timeout, mapping và error handling.

### Senior

Thiết kế retry/fallback, schema tolerance, observability và contract tests.

### Technical Lead / Architect

Quyết định dependency criticality, ownership boundary, fallback policy và migration strategy nếu vendor thay đổi hoặc bị thay thế.

## 11. Key takeaway

* Third-party integration thất bại không chỉ vì network; semantic contract cũng drift.
* Giữ vendor DTO sau adapter boundary để giảm blast radius.
* Monitor mapping/semantic errors, không chỉ HTTP status và latency.
