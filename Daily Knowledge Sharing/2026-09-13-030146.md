# 1. ASP.NET Core DI lifetimes và captive dependency: vì sao `Singleton` giữ `Scoped` service có thể tạo stale state, race condition và production bug khó đoán

## 1. What is it?

ASP.NET Core Dependency Injection quản lý lifetime của service bằng ba scope chính:

- `Transient`: tạo instance mới mỗi lần resolve.
- `Scoped`: thường một instance cho mỗi HTTP request scope.
- `Singleton`: một instance cho toàn bộ lifetime của application process.

**Captive dependency** xảy ra khi một service lifetime dài giữ reference đến dependency lifetime ngắn hơn, điển hình là `Singleton` phụ thuộc trực tiếp vào `Scoped` service.

Mental model:

```text
Application lifetime
└── Singleton
    └── Scoped dependency  <-- bị giữ lâu hơn thiết kế ban đầu
```

Nếu dependency chứa request-specific state như `DbContext`, tenant context hoặc user context, bug không còn chỉ là “DI configuration sai” mà trở thành state leakage và concurrency problem.

## 2. Why does it exist?

Lifetime tồn tại để model ownership và resource boundaries. `DbContext` phù hợp với unit-of-work ngắn; singleton cache hoặc coordinator lại cần tồn tại lâu.

Nếu mọi service đều singleton, mutable state dễ bị nhiều request truy cập đồng thời. Nếu mọi service đều transient, application tạo object/resource không cần thiết và có thể phá semantics của một unit-of-work.

Lifetime là engineering contract về **ai sở hữu state và state sống bao lâu**.

## 3. How does it work?

Request flow phổ biến:

```text
Request A -> Request Scope A -> Scoped Service A -> DbContext A
Request B -> Request Scope B -> Scoped Service B -> DbContext B
```

Một singleton đúng thiết kế thường chỉ phụ thuộc vào stateless singleton/transient-safe collaborators.

Nếu singleton cần thực hiện operation có scoped dependencies, nó nên tạo scope tại thời điểm operation:

```text
Singleton background coordinator
        |
        v
IServiceScopeFactory.CreateScope()
        |
        v
Scoped DbContext / tenant service
```

Scope mới tạo ra ownership boundary mới; resolve xong rồi dispose scope.

## 4. Practical implementation

Một `BackgroundService` cần `DbContext` nên tạo scope cho từng iteration:

```csharp
public sealed class InvoiceWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public InvoiceWorker(IServiceScopeFactory scopeFactory)
        => _scopeFactory = scopeFactory;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = _scopeFactory.CreateAsyncScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var processor = scope.ServiceProvider.GetRequiredService<InvoiceProcessor>();

            await processor.ProcessBatchAsync(db, stoppingToken);
            await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
        }
    }
}
```

Không inject `AppDbContext` trực tiếp vào `BackgroundService` singleton.

## 5. Real production scenario

Một multi-tenant SaaS có `TenantContext` scoped theo request. Developer inject nó vào singleton pricing service để tránh truyền tenant ID qua nhiều methods.

Dưới load, singleton giữ tenant context từ scope đầu tiên. Request của tenant B có thể đọc pricing config của tenant A. Đây vừa là correctness bug vừa có thể là security incident.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu tenant đôi lúc sai; bug chỉ xuất hiện khi concurrent traffic cao.

**Evidence** → object hash / correlation logs cho thấy cùng service instance được dùng bởi nhiều requests; tenant identifier trong singleton không đổi.

**Hypothesis** → request-scoped state bị giữ bởi singleton.

**Diagnosis** → inspect DI registration và constructor dependency graph; bật scope validation trong Development/test.

**Fix** → đổi lifetime, bỏ mutable request state khỏi singleton hoặc tạo explicit scope cho operation.

**Verification** → concurrency test nhiều tenants và trace instance/lifetime boundaries.

## 7. Common mistakes

- Inject `DbContext` trực tiếp vào singleton.
- Cho singleton giữ `HttpContext` hoặc user claims.
- Nghĩ rằng service không có field mutable thì dependency chain chắc chắn thread-safe.
- Tạo scope nhưng giữ resolved scoped service ra ngoài scope.
- Dùng Service Locator khắp nơi để né lifetime design thay vì sửa boundary.

## 8. Alternatives

- Truyền immutable request data trực tiếp vào method.
- Dùng factory để tạo dependency đúng lifetime.
- Dùng `IServiceScopeFactory` ở process/background boundary.
- Nếu service thực chất request-specific, đổi chính service đó thành scoped.

## 9. Trade-offs

### Advantages

- Lifetime đúng làm ownership, thread-safety và transaction boundary rõ ràng.
- Scoped unit-of-work tự nhiên cho web requests.

### Costs / Risks

- Quá nhiều factory/scope manual có thể che design smell.
- Singleton giảm allocation nhưng đổi lại yêu cầu thread-safety nghiêm ngặt.
- Scoped state tiện nhưng dễ bị lạm dụng thành hidden ambient context.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Transient`, `Scoped`, `Singleton` khác nhau ở lifetime chứ không phải “performance mode”.

### Middle

Biết chọn lifetime, tạo scope cho background work và tránh captive dependency.

### Senior

Đánh giá thread-safety, request state leakage và transaction/resource ownership xuyên dependency graph.

### Technical Lead / Architect

Quyết định state nào nên explicit trong API contract, state nào được ambient, và lifetime nào phản ánh đúng system boundary thay vì tối ưu object allocation sớm.

## 11. Key takeaway

- DI lifetime là ownership contract, không chỉ registration syntax.
- Singleton không được vô tình giữ request-scoped state.
- Lifetime bug thường biểu hiện thành concurrency, stale state hoặc data-leak problem.

# 2. EF Core projection và `IQueryable`: kéo đúng cột từ database thay vì materialize entity graph rồi mới lọc trong memory

## 1. What is it?

`IQueryable<T>` đại diện cho query expression mà EF Core còn có thể translate thành SQL. Projection dùng `Select` để chỉ lấy dữ liệu mà use case thật sự cần thay vì materialize full entity.

Mental model:

```text
LINQ expression
   -> EF Core translation
   -> SQL SELECT đúng columns
   -> database executes
   -> result materialization
```

Khác biệt quan trọng là **query được thực thi ở đâu**: database hay application memory.

## 2. Why does it exist?

Entity model thường chứa nhiều fields và navigation properties hơn API response cần. Nếu endpoint chỉ cần `Id`, `Name`, `Total`, việc load full entity làm tăng:

- bytes đọc từ database;
- network transfer;
- materialization cost;
- tracking cost;
- memory pressure.

Projection giữ computation gần data source khi DB xử lý hiệu quả hơn.

## 3. How does it work?

Ví dụ:

```csharp
var query = db.Orders
    .Where(x => x.Status == OrderStatus.Open)
    .Select(x => new OrderListItem(
        x.Id,
        x.Customer.Name,
        x.Total));
```

Cho tới khi gọi `ToListAsync`, query chưa chạy. EF Core inspect expression tree và translate thành SQL tương ứng.

Nếu developer gọi `ToListAsync()` quá sớm rồi `.Where(...)` tiếp, phần sau chạy trong memory:

```text
DB -> nhiều rows -> app memory -> filter
```

thay vì:

```text
DB filter -> ít rows -> app
```

## 4. Practical implementation

Tốt:

```csharp
var items = await db.Products
    .AsNoTracking()
    .Where(x => x.IsActive)
    .OrderBy(x => x.Name)
    .Select(x => new ProductDto(
        x.Id,
        x.Name,
        x.Price,
        x.Category.Name))
    .Take(100)
    .ToListAsync(ct);
```

Không cần `Include` nếu projection đã tham chiếu navigation và EF có thể translate join phù hợp.

Không tối ưu mù quáng: hãy xem generated SQL (`ToQueryString()` trong debugging) và execution plan khi query thực sự chậm.

## 5. Real production scenario

Admin screen hiển thị 50 orders nhưng code load `Order` + `OrderLines` + `Customer` + `Payments`. Response chỉ dùng 8 fields.

Under load, SQL trả hàng chục nghìn rows do join expansion. API memory tăng và latency xấu. Chuyển sang DTO projection giảm dữ liệu đọc và materialization đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint list chậm và memory cao dù chỉ trả ít fields.

**Evidence** → SQL trace cho thấy nhiều columns/rows; payload DB lớn; query có `Include` không cần thiết.

**Hypothesis** → over-fetching/materialization.

**Diagnosis** → xem LINQ chain, generated SQL, actual row count, query plan.

**Fix** → projection, pagination, bỏ Include dư, giữ filtering/sorting ở `IQueryable` trước materialization.

**Verification** → đo DB logical reads, response latency, allocations và result correctness.

## 7. Common mistakes

- Gọi `ToList()` rồi mới filter/sort.
- Trả entity trực tiếp từ API rồi phụ thuộc serializer.
- Dùng `Include` cho mọi navigation “phòng khi cần”.
- Đưa custom .NET method không translate được vào query hot path.
- Dùng `IQueryable` như abstraction leak xuyên nhiều architectural boundaries mà không kiểm soát.

## 8. Alternatives

- Full entity tracking: đúng khi cần mutation/domain behavior.
- DTO projection: tốt cho read API.
- Raw SQL/Dapper: hữu ích khi query đặc thù và cần tối ưu rất sâu.
- CQRS read model: hợp lý khi read shape khác domain model đáng kể và complexity đủ lớn.

## 9. Trade-offs

### Advantages

- Ít I/O, ít allocation và rõ API contract.
- Database thực hiện filtering/aggregation hiệu quả hơn nhiều trường hợp.

### Costs / Risks

- Projection DTO tăng mapping code.
- Complex LINQ có thể tạo SQL khó dự đoán.
- Quá nhiều specialized projections làm maintenance khó nếu thiếu naming/boundary rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deferred execution và khác biệt `IQueryable` / materialized collection.

### Middle

Viết projection, pagination, inspect SQL và tránh over-fetching.

### Senior

Đánh giá translation, query plan, round trips và khi nào ORM abstraction cần bypass.

### Technical Lead / Architect

Định nghĩa read boundary: entity model có được leak ra API không, read model có cần riêng không, và team sẽ kiểm soát query complexity bằng convention/tooling nào.

## 11. Key takeaway

- Đừng materialize trước khi database hoàn thành phần việc nó làm tốt.
- Projection là performance và contract-design tool, không chỉ DTO convenience.
- Luôn xác minh SQL thật thay vì suy luận từ LINQ nhìn “đẹp”.

# 3. SQL Server isolation levels: phân biệt `Read Committed`, `RCSI` và `Snapshot` bằng locking, row versioning và transaction semantics

## 1. What is it?

Transaction isolation level xác định transaction được phép nhìn thấy thay đổi concurrent ở mức nào và database dùng cơ chế gì để bảo vệ consistency.

Ba khái niệm dễ bị trộn:

- `READ COMMITTED`: mặc định phổ biến, thường dùng locks để tránh đọc uncommitted data.
- `READ_COMMITTED_SNAPSHOT` (RCSI): vẫn semantics Read Committed nhưng reads dùng row versions thay vì shared locks trong nhiều trường hợp.
- `SNAPSHOT`: transaction nhìn một consistent snapshot từ thời điểm transaction bắt đầu.

## 2. Why does it exist?

Concurrency cần cân bằng correctness và throughput. Lock mạnh giảm anomalies nhưng tăng blocking. Row versioning giảm reader/writer blocking nhưng cần version store và có conflict semantics riêng.

Không có isolation level “tốt nhất cho mọi hệ thống”. Business invariant quyết định mức consistency cần thiết.

## 3. How does it work?

Với locking Read Committed:

```text
Writer holds X lock
Reader needs compatible access
-> reader may wait
```

Với RCSI:

```text
Writer updates row
old committed version stored
reader sees committed version
-> thường không chờ writer
```

Với Snapshot transaction:

```text
Transaction starts at T0
all reads observe committed state as of T0
later commits by others are not visible inside same transaction
```

Write conflicts vẫn cần xử lý; row versioning không biến mọi transaction thành lock-free.

## 4. Practical implementation

Bật RCSI là database-level decision, ví dụ:

```sql
ALTER DATABASE MyAppDb
SET READ_COMMITTED_SNAPSHOT ON;
```

Trước khi làm vậy cần test application behavior, long-running transactions, tempdb/version store pressure và reporting workloads.

Với explicit snapshot:

```sql
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

SELECT Balance
FROM Accounts
WHERE Id = @AccountId;

-- other work

COMMIT;
```

Business operation vẫn cần concurrency checks nếu invariant phụ thuộc latest state.

## 5. Real production scenario

Reporting endpoint chạy aggregate query vài giây và block checkout updates. Team bật RCSI để readers dùng committed row versions thay vì shared locks.

Blocking giảm mạnh, nhưng version store tăng. Một report transaction kéo dài bất thường giữ old row versions lâu hơn, tạo tempdb pressure.

## 6. Failure scenario & troubleshooting

**Symptom** → sau chuyển sang row versioning, blocking giảm nhưng tempdb tăng nhanh.

**Evidence** → long-running transactions và version store usage cao.

**Hypothesis** → snapshot readers giữ versions lâu.

**Diagnosis** → inspect transaction duration, version store DMVs, workload timeline.

**Fix** → rút ngắn transactions, tránh user think-time trong transaction, tối ưu long-running queries.

**Verification** → theo dõi blocking, tempdb/version store và p95 latency cùng lúc.

## 7. Common mistakes

- Nghĩ RCSI và Snapshot là cùng semantics.
- Bật `NOLOCK` để “fix blocking” và chấp nhận dirty/inconsistent reads mà không hiểu hậu quả.
- Giữ transaction mở qua remote API call.
- Cho rằng row versioning loại bỏ mọi locks.
- Thay isolation level mà không test business invariant như inventory/balance.

## 8. Alternatives

- Locking Read Committed: đơn giản, phổ biến, phù hợp workload không bị blocking nghiêm trọng.
- RCSI: giảm reader/writer blocking với semantics statement-level committed view.
- Snapshot: consistent transaction-level view.
- Explicit locking/optimistic concurrency: khi business invariant cần kiểm soát cụ thể hơn.

## 9. Trade-offs

### Advantages

- Row versioning có thể tăng concurrency đáng kể cho read-heavy workloads.
- Snapshot cho repeatable transaction view dễ reasoning trong một số use cases.

### Costs / Risks

- Version store tiêu thụ tempdb/storage resources.
- Long transactions trở nên đắt hơn.
- Write conflicts/correctness rules vẫn tồn tại.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction isolation giải quyết concurrent visibility, không chỉ “bật transaction”.

### Middle

Nhận biết blocking, isolation level và row-version behavior từ query/session.

### Senior

Phân tích anomalies, lock/version evidence và business correctness trước khi đổi database setting.

### Technical Lead / Architect

Chọn default isolation dựa trên workload và invariants; xác định monitoring cho blocking, version store và long transactions.

## 11. Key takeaway

- RCSI và Snapshot đều dùng row versions nhưng không cùng semantics.
- Giảm blocking không đồng nghĩa giảm mọi concurrency risk.
- Isolation level là correctness + performance decision, không phải tuning switch độc lập.

# 4. Cosmos DB Request Units và cross-partition query: partition key sai biến query đơn giản thành fan-out đắt đỏ

## 1. What is it?

Azure Cosmos DB định giá nhiều operations theo **Request Units (RU)**, một abstraction phản ánh compute, I/O và memory cần cho operation.

Partition key quyết định cách documents được phân bố vào logical partitions. Query có exact partition key có thể route trực tiếp; query không có partition key phù hợp có thể fan-out nhiều partitions.

Mental model:

```text
Query with partition key -> 1 logical partition -> bounded work
Query without key        -> many partitions     -> fan-out cost
```

## 2. Why does it exist?

Cosmos DB scale horizontally bằng cách phân tán dữ liệu. Muốn route request hiệu quả, platform cần một key để biết data nằm ở đâu.

Nếu model chỉ dựa theo entity shape mà không theo access patterns, query production có thể đắt dù dataset chưa quá lớn.

## 3. How does it work?

Giả sử partition key là `/tenantId`:

```json
{
  "id": "order-123",
  "tenantId": "tenant-a",
  "status": "Open"
}
```

Query:

```sql
SELECT * FROM c
WHERE c.tenantId = @tenantId
  AND c.status = 'Open'
```

có thể target partition tương ứng.

Query chỉ theo `status` phải hỏi nhiều partitions rồi merge results. Càng nhiều partitions, latency/RU thường càng khó dự đoán.

## 4. Practical implementation

Trong .NET SDK, truyền partition key explicit khi biết:

```csharp
var response = await container.ReadItemAsync<OrderDocument>(
    id: orderId,
    partitionKey: new PartitionKey(tenantId),
    cancellationToken: ct);
```

Với query:

```csharp
var options = new QueryRequestOptions
{
    PartitionKey = new PartitionKey(tenantId),
    MaxItemCount = 100
};

var iterator = container.GetItemQueryIterator<OrderDocument>(
    queryDefinition,
    requestOptions: options);
```

Log RU charge ở telemetry cho important operations thay vì chỉ nhìn request count.

## 5. Real production scenario

SaaS lưu orders partition theo `country`, nhưng hầu hết requests là “orders của tenant X”. Mỗi tenant query fan-out across countries/partitions.

Khi số physical partitions tăng, cùng endpoint dần đắt hơn dù code không đổi. Đây là data-model/access-pattern mismatch.

## 6. Failure scenario & troubleshooting

**Symptom** → latency và RU/query tăng theo dataset; CPU application bình thường.

**Evidence** → request charge cao, query metrics cho fan-out, missing effective partition-key filter.

**Hypothesis** → query không align với partition strategy.

**Diagnosis** → inventory top queries, RU distribution và cardinality/hotness của partition key.

**Fix** → redesign key/container/read model, include partition key trong API boundary hoặc precompute alternative access path.

**Verification** → compare RU, p95 latency và partition distribution dưới production-like data.

## 7. Common mistakes

- Chọn partition key chỉ vì field có unique values.
- Dùng `/id` rồi mọi business query thành cross-partition.
- Chọn key có hot tenant cực lớn mà không cân nhắc distribution.
- Chỉ monitor total RU, không monitor RU per operation/query.
- Cố mô hình hóa Cosmos giống relational normalized schema.

## 8. Alternatives

- SQL Server/PostgreSQL: tốt khi relational joins/transactions chiếm ưu thế.
- MongoDB: document model tương tự về access-pattern reasoning nhưng operational model khác.
- Cosmos multiple containers/read models: đổi thêm duplication/sync complexity để tối ưu access paths.

## 9. Trade-offs

### Advantages

- Partitioning đúng cho horizontal scale và predictable routing.
- RU metric giúp nhìn thấy cost trực tiếp theo operation.

### Costs / Risks

- Partition key khó thay đổi về sau.
- Denormalization tăng synchronization complexity.
- Cross-partition analytics có thể đắt nếu chọn sai workload cho Cosmos.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định data placement và request routing.

### Middle

Viết partition-targeted query và đo RU charge.

### Senior

Đánh giá hot partition, fan-out và data model theo access pattern thật.

### Technical Lead / Architect

Quyết định Cosmos có phù hợp workload không, chọn partition strategy dựa trên scale horizon và migration cost chứ không chỉ schema hiện tại.

## 11. Key takeaway

- Cosmos modeling bắt đầu từ access patterns và partitioning, không từ class diagram.
- Cross-partition query có operational cost tăng theo scale.
- RU per operation là signal quan trọng cho cả performance lẫn cost.

# 5. Saga Pattern và compensating transaction: xử lý workflow nhiều service khi không có distributed transaction đáng tin cậy

## 1. What is it?

Saga chia một business workflow dài thành nhiều local transactions. Nếu bước sau thất bại, hệ thống chạy **compensating actions** để đảo hoặc bù business effect của các bước đã hoàn tất.

Ví dụ checkout:

```text
Create Order
 -> Reserve Inventory
 -> Charge Payment
 -> Arrange Shipment
```

Nếu payment fail sau khi inventory đã reserve, compensation có thể release inventory.

## 2. Why does it exist?

Trong microservices, mỗi service thường sở hữu database riêng. Một ACID transaction xuyên SQL + payment provider + inventory service + message broker là không thực tế hoặc tạo coupling lớn.

Saga chấp nhận eventual consistency và model failure thành business workflow explicit.

## 3. How does it work?

Hai style phổ biến:

- **Orchestration:** một coordinator quyết định bước kế tiếp và compensation.
- **Choreography:** services phản ứng events và tự phát progression.

Orchestration flow:

```text
Order Saga
  -> Inventory: Reserve
  <- Reserved
  -> Payment: Charge
  <- Failed
  -> Inventory: Release
  -> Order: MarkPaymentFailed
```

Compensation không nhất thiết là exact inverse. Ví dụ refund payment có thể mất phí hoặc cần asynchronous settlement.

## 4. Practical implementation

State machine tối giản:

```csharp
public async Task HandlePaymentFailedAsync(
    CheckoutSaga saga,
    CancellationToken ct)
{
    if (saga.InventoryReserved && !saga.InventoryReleased)
    {
        await inventory.ReleaseAsync(
            saga.OrderId,
            saga.ReservationId,
            ct);

        saga.MarkInventoryReleased();
    }

    saga.MarkFailed("PaymentFailed");
    await db.SaveChangesAsync(ct);
}
```

Mỗi command/message cần idempotency key vì duplicate delivery có thể khiến compensation chạy nhiều lần.

## 5. Real production scenario

Marketplace reserve vehicle listing, charge booking deposit, rồi gọi external inspection partner. Partner timeout sau payment thành công.

Business có thể không muốn auto-refund ngay; có thể chuyển saga sang `PendingManualReview`. Compensation là domain policy, không phải technical rollback đơn giản.

## 6. Failure scenario & troubleshooting

**Symptom** → order `Failed` nhưng inventory vẫn reserved.

**Evidence** → saga state cho thấy payment failure được ghi nhưng compensation message chưa complete; queue có retries/DLQ.

**Hypothesis** → compensation bị partial failure.

**Diagnosis** → trace correlation/saga ID qua services, inspect message delivery và local transaction states.

**Fix** → idempotent compensation, retry policy, operational repair command và reconciliation job.

**Verification** → inject failures ở từng transition và xác nhận saga luôn tiến tới recoverable terminal state.

## 7. Common mistakes

- Gọi Saga = “rollback nhiều services”.
- Không persist saga state.
- Không thiết kế idempotency cho steps/compensations.
- Choreography quá nhiều events dẫn tới workflow ownership mơ hồ.
- Dùng compensation cho business action không thể đảo thực tế.

## 8. Alternatives

- Single database transaction: đơn giản hơn nếu boundary cho phép; ưu tiên khi có thể.
- Modular Monolith: giữ transaction local nếu business chưa cần distributed deployment.
- Two-phase commit/distributed transaction: chỉ phù hợp môi trường/hạ tầng rất cụ thể và operational cost chấp nhận được.

## 9. Trade-offs

### Advantages

- Cho phép services độc lập và workflow chịu partial failure.
- Failure states trở thành explicit business state.

### Costs / Risks

- Eventual consistency phức tạp hơn ACID.
- Compensation không luôn hoàn hảo.
- Cần observability, reconciliation và support tooling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu local transaction không thể tự rollback remote service.

### Middle

Implement idempotent handlers và persist workflow state.

### Senior

Thiết kế failure matrix, compensation và reconciliation cho partial failures.

### Technical Lead / Architect

Quyết định có thật sự cần distributed workflow không; chọn orchestration/choreography và ownership phù hợp với business complexity/team structure.

## 11. Key takeaway

- Saga quản lý business consistency qua nhiều local transactions.
- Compensation là business action, không phải database rollback xuyên services.
- Idempotency và observability là yêu cầu nền tảng, không phải enhancement sau này.

# 6. Azure Functions queue-trigger concurrency: autoscale nhanh có thể làm downstream SQL/API sụp trước khi Function itself quá tải

## 1. What is it?

Queue-triggered Azure Functions có thể xử lý nhiều messages concurrent trong một instance và platform còn có thể scale thêm instances theo backlog/throughput signals.

Mental model:

```text
Queue backlog
   -> instance concurrency
   -> more instances
   -> more downstream calls
```

Autoscaling function không đồng nghĩa toàn hệ thống có infinite capacity.

## 2. Why does it exist?

Queue consumers cần tăng throughput khi backlog tăng. Serverless scaling giúp team không phải provision worker cố định.

Nhưng bottleneck thường nằm ở SQL, third-party API hoặc rate-limited dependency. Nếu Function scale nhanh hơn downstream, hệ thống có thể tạo self-inflicted outage.

## 3. How does it work?

Một instance pull nhiều messages. Nhiều instances cùng hoạt động tạo tổng concurrency:

```text
Total concurrency ≈ instances × concurrent handlers/instance
```

Nếu mỗi message mở SQL connection và gọi payment API, scale từ 5 lên 100 instances có thể tăng dependency pressure 20x trong vài phút.

Retries còn làm tải tăng thêm nếu failure là overload chứ không phải transient random error.

## 4. Practical implementation

Business handler vẫn cần bounded behavior:

```csharp
public async Task ProcessAsync(ServiceBusReceivedMessage message, CancellationToken ct)
{
    using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
    timeoutCts.CancelAfter(TimeSpan.FromSeconds(10));

    await processor.HandleAsync(
        message.Body.ToObjectFromJson<Job>(),
        timeoutCts.Token);
}
```

Ở architecture level, configure concurrency/prefetch/retry phù hợp và đặt rate limit/bulkhead trước fragile downstream.

Nếu database chỉ chịu 200 concurrent operations, autoscale policy phải tôn trọng capacity đó.

## 5. Real production scenario

Nightly import đẩy 500.000 messages. Function scale-out mạnh. Mỗi message gọi SQL stored procedure. SQL connection pool/server đạt saturation, latency tăng, Function timeout, messages retry, backlog còn tăng nhanh hơn.

Vấn đề không phải “Function thiếu scale” mà là **consumer concurrency không aligned với bottleneck capacity**.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog tăng đồng thời Function instances tăng, SQL timeouts bùng nổ.

**Evidence** → dependency p95, connection count, retry count và active executions tăng cùng nhau.

**Hypothesis** → downstream saturation + retry amplification.

**Diagnosis** → correlate queue depth, instance count, function concurrency và dependency capacity.

**Fix** → giảm concurrency, batch hợp lý, backoff, bulkhead, tối ưu downstream hoặc tăng downstream capacity có chủ đích.

**Verification** → load test với backlog lớn và xác nhận throughput ổn định thay vì oscillation/retry storm.

## 7. Common mistakes

- Coi autoscale là performance fix universal.
- Retry nhanh không jitter khi dependency đang overloaded.
- Không đặt timeout cho downstream call.
- Không monitor queue age, chỉ monitor queue length.
- Scale consumer trước khi biết downstream capacity.

## 8. Alternatives

- Worker Service/Container Apps: kiểm soát concurrency/resource rõ hơn.
- Fixed worker count: đơn giản và predictable nếu workload ổn định.
- Batch processing: giảm per-message overhead nhưng tăng transaction/failure complexity.

## 9. Trade-offs

### Advantages

- Functions xử lý burst tốt và giảm idle infrastructure.
- Queue decouples producer speed khỏi consumer speed.

### Costs / Risks

- Rapid scale-out có thể chuyển bottleneck xuống dependency.
- Serverless behavior khó predict hơn fixed workers nếu thiếu load testing.
- Retry + autoscale tạo feedback loop nguy hiểm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue consumer có concurrency và downstream vẫn hữu hạn.

### Middle

Thiết lập timeout, retry và telemetry cho handler.

### Senior

Model total concurrency, dependency capacity và retry amplification.

### Technical Lead / Architect

Đặt system-wide throughput budget và chọn compute model dựa trên workload, cost, failure behavior chứ không chỉ convenience.

## 11. Key takeaway

- Autoscaling consumer không tự scale dependency.
- Queue backlog, concurrency và retry phải được quan sát cùng nhau.
- Throughput tối đa của pipeline bằng bottleneck chậm nhất, không phải worker nhanh nhất.

# 7. Kubernetes readiness vs liveness probes: tránh restart application khỏe hoặc route traffic vào pod chưa sẵn sàng

## 1. What is it?

Hai probe giải quyết hai câu hỏi khác nhau:

- **Readiness:** pod có sẵn sàng nhận traffic lúc này không?
- **Liveness:** process có còn sống/khả năng tự phục hồi hay cần restart?

Nếu dùng cùng endpoint/check cho cả hai, failure của dependency như database có thể khiến Kubernetes restart hàng loạt pods dù application process hoàn toàn khỏe.

## 2. Why does it exist?

Một process có thể:

- sống nhưng chưa warm-up;
- sống nhưng tạm thời không thể phục vụ request;
- deadlock/hung và cần restart.

Traffic routing và process restart là hai control actions khác nhau nên cần signals khác nhau.

## 3. How does it work?

```text
Readiness false
-> pod bị loại khỏi Service endpoints
-> process vẫn chạy

Liveness false nhiều lần
-> kubelet restart container
```

Startup probe còn hữu ích cho application khởi động lâu để liveness không kill process trước khi startup hoàn tất.

## 4. Practical implementation

ASP.NET Core health checks có thể map endpoints riêng:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<SelfHealthCheck>("self", tags: new[] { "live" })
    .AddSqlServer(connectionString, tags: new[] { "ready" });

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready")
});
```

Liveness thường nên kiểm tra process-internal health tối thiểu. Readiness có thể xét dependency critical cần để phục vụ traffic.

## 5. Real production scenario

Database fail 30 giây. Cả 20 pods có liveness check gọi database. Tất cả liveness fail và containers restart đồng loạt. Khi database hồi phục, application còn đang cold start, làm outage kéo dài.

Nếu DB chỉ ảnh hưởng readiness, pods ngừng nhận traffic nhưng không tạo restart storm.

## 6. Failure scenario & troubleshooting

**Symptom** → pod restart count tăng mỗi khi SQL latency spike.

**Evidence** → `kubectl describe pod` cho liveness failures; health endpoint logs dependency timeout.

**Hypothesis** → liveness phụ thuộc remote dependency.

**Diagnosis** → inspect probe config và health-check composition.

**Fix** → tách live/ready, tune thresholds/timeouts, thêm startup probe nếu cần.

**Verification** → simulate dependency outage và xác nhận pods không restart vô ích nhưng bị removed khỏi traffic khi appropriate.

## 7. Common mistakes

- Dùng một `/health` cho cả readiness và liveness.
- Liveness gọi mọi dependency remote.
- Timeout probe dài hơn interval khiến checks overlap.
- Readiness luôn trả 200 dù app chưa load critical configuration.
- Probe quá aggressive gây false positives under temporary CPU pressure.

## 8. Alternatives

- Platform-native App Service health check cho simpler hosting.
- External synthetic checks để đo user-visible availability; không thay thế pod probes.

## 9. Trade-offs

### Advantages

- Tách routing khỏi restart giúp recovery chính xác hơn.
- Probes tốt hỗ trợ rolling deployment an toàn.

### Costs / Risks

- Health model phức tạp hơn “200 nếu process chạy”.
- Readiness quá strict có thể loại toàn bộ capacity khi dependency degraded nhưng app vẫn có fallback.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu readiness và liveness trả lời hai câu hỏi khác nhau.

### Middle

Map health endpoints và debug probe failures.

### Senior

Thiết kế dependency degradation/fallback và threshold tránh restart cascade.

### Technical Lead / Architect

Xác định service nào thực sự critical cho readiness, failure nào nên degrade thay vì remove capacity, và deployment probes gắn với SLO thế nào.

## 11. Key takeaway

- Readiness điều khiển traffic; liveness điều khiển restart.
- Remote dependency failure không mặc định nghĩa là process cần restart.
- Probe design là reliability control loop, không phải checkbox deployment.

# 8. Cookie Authentication, `SameSite` và CSRF: browser tự gửi credential nên backend phải bảo vệ state-changing requests đúng cách

## 1. What is it?

Cookie Authentication lưu session/authentication token trong browser cookie. Browser tự động gắn cookie vào requests phù hợp domain/path/policy.

Chính tính “tự gửi” này tạo điều kiện cho **Cross-Site Request Forgery (CSRF)**: trang độc hại dụ browser của user gửi request tới site đã đăng nhập.

`SameSite` là browser cookie policy giảm một phần cross-site sending, nhưng không thay thế toàn bộ CSRF design cho mọi architecture.

## 2. Why does it exist?

Cookie giúp web authentication đơn giản và browser quản lý session. Nhưng server nhìn request có valid cookie không thể tự biết user thật sự chủ động gửi request từ trusted UI hay bị cross-site form/request kích hoạt.

State-changing endpoints cần thêm proof gắn với legitimate page/session flow.

## 3. How does it work?

Ví dụ attack:

```text
User logged in to bank.example
        |
visits evil.example
        |
evil page submits POST to bank.example/transfer
        |
browser may attach bank cookie automatically
```

Anti-forgery pattern thường dùng token mà attacker origin không đọc được và request phải gửi explicit token hợp lệ.

`SameSite=Lax/Strict/None` ảnh hưởng khi cookie được gửi trong cross-site contexts; `None` yêu cầu `Secure` trên modern browsers.

## 4. Practical implementation

Với ASP.NET Core MVC/Razor state-changing forms, dùng anti-forgery mechanisms của framework. Với SPA + cookie auth, có thể expose anti-forgery token và gửi qua custom header.

Cookie config cần secure defaults:

```csharp
builder.Services.ConfigureApplicationCookie(options =>
{
    options.Cookie.HttpOnly = true;
    options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
    options.Cookie.SameSite = SameSiteMode.Lax;
});
```

`HttpOnly` giảm JavaScript access nhưng không tự chống CSRF; nó chủ yếu giúp giảm credential theft qua script khi XSS xảy ra.

## 5. Real production scenario

Internal admin portal dùng cookie auth. Endpoint `POST /users/{id}/disable` chỉ kiểm tra logged-in role. Attacker gửi link/trang HTML khiến browser admin submit request tự động.

Nếu endpoint không có anti-forgery protection phù hợp, authorization vẫn pass vì cookie là thật.

## 6. Failure scenario & troubleshooting

**Symptom** → action được thực hiện với valid authenticated user nhưng user nói không thao tác.

**Evidence** → request có cookie hợp lệ nhưng thiếu anti-forgery token/custom header; referrer/origin bất thường nếu available.

**Hypothesis** → CSRF hoặc automation misuse.

**Diagnosis** → review auth mechanism, SameSite policy, endpoint method và anti-forgery coverage.

**Fix** → anti-forgery token, secure SameSite policy, kiểm tra Origin khi appropriate, không dùng GET cho state changes.

**Verification** → cross-site test page không thể thực hiện action; legitimate client vẫn hoạt động.

## 7. Common mistakes

- Nghĩ CORS tự chống CSRF.
- Dùng `GET` để mutate state.
- Cho rằng `HttpOnly` = CSRF protection.
- Đặt `SameSite=None` toàn bộ để “fix login” mà không hiểu exposure.
- Tắt anti-forgery vì SPA request bị 400 thay vì sửa token flow.

## 8. Alternatives

- Bearer token gửi explicit trong `Authorization` header giảm classic CSRF exposure vì browser không tự attach như cookie, nhưng tăng risk nếu token lưu ở insecure JavaScript storage và bị XSS.
- BFF pattern có thể giữ token server-side và dùng cookie + anti-forgery ở browser boundary.

## 9. Trade-offs

### Advantages

- Cookie auth tích hợp tốt với browser và server-rendered apps.
- `HttpOnly`/`Secure` giảm một số credential exposure.

### Costs / Risks

- Cần CSRF controls cho state-changing requests.
- SameSite policy có thể xung đột external identity/payment flows.
- Bearer tokens đổi threat model chứ không xóa security risk.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu authentication hợp lệ không chứng minh request được user chủ động tạo.

### Middle

Cấu hình cookie flags và anti-forgery flow đúng framework.

### Senior

Phân tích XSS/CSRF/CORS threat model theo client architecture và identity flow.

### Technical Lead / Architect

Chọn cookie, BFF hay bearer-token model dựa trên browser/security boundaries, third-party flows và operational constraints.

## 11. Key takeaway

- Browser tự attach cookie nên cookie-authenticated state changes cần CSRF defense.
- `CORS`, `HttpOnly` và `SameSite` giải quyết các vấn đề khác nhau.
- Security design phải theo credential transport model, không theo framework default một cách mù quáng.

# 9. CDN/Akamai `Cache-Control`, stale content và purge: giảm origin load mà không vô tình phục vụ nội dung cũ sau release

## 1. What is it?

CDN cache giữ response gần user ở edge để giảm latency và origin traffic. `Cache-Control` mô tả freshness/caching policy giữa browser, CDN và origin.

Mental model:

```text
Browser
  -> CDN edge cache
      -> origin/reverse proxy
          -> application
```

Một response cached nhanh nhưng sai freshness semantics có thể tạo production incident khó debug vì application origin đã đúng còn user vẫn nhận bản cũ.

## 2. Why does it exist?

Static assets, images và public content có thể được phục vụ từ edge thay vì mỗi request về origin. Điều này giảm network distance và compute/database load.

Nhưng cache introduces another copy of data. Mỗi copy cần invalidation/freshness strategy.

## 3. How does it work?

Ví dụ:

```http
Cache-Control: public, max-age=300, s-maxage=3600
```

Browser có thể cache 5 phút; shared cache/CDN có thể cache 1 giờ tùy policy support.

Với versioned static assets:

```text
app.4f8c1.js
```

có thể dùng TTL rất dài vì filename đổi khi content đổi.

Dynamic HTML thường cần TTL ngắn hơn hoặc revalidation vì deploy mới có thể reference asset/version mới.

## 4. Practical implementation

ASP.NET Core cho static/versioned assets có thể set headers:

```csharp
app.UseStaticFiles(new StaticFileOptions
{
    OnPrepareResponse = ctx =>
    {
        ctx.Context.Response.Headers.CacheControl =
            "public,max-age=31536000,immutable";
    }
});
```

Chỉ dùng `immutable` khi URL thực sự content-versioned. Không áp TTL một năm cho `/index.html` nếu nội dung thay đổi tại cùng URL.

## 5. Real production scenario

Release deploy frontend mới nhưng CDN giữ `index.html` cũ 30 phút. HTML cũ reference JavaScript chunk đã bị xóa khỏi origin. User nhận 404 chunk và app trắng trang.

Root cause không nằm ở JavaScript business logic mà ở mismatch giữa deployment artifact retention và cache policy.

## 6. Failure scenario & troubleshooting

**Symptom** → chỉ một số regions/users thấy UI cũ sau deploy.

**Evidence** → origin response mới nhưng CDN response có `Age` cao/cache-hit headers; purge chưa hoàn thành.

**Hypothesis** → stale edge cache.

**Diagnosis** → compare origin vs edge headers/body, cache key, TTL, purge status.

**Fix** → purge targeted URL nếu cần, dùng content hashing cho assets, điều chỉnh HTML caching policy.

**Verification** → test nhiều PoPs/regions hoặc edge endpoints; xác nhận expected cache status và version.

## 7. Common mistakes

- Cache HTML và hashed assets cùng TTL policy.
- Purge toàn bộ site mỗi deploy dù versioned assets không cần.
- Không include query/header dimensions cần thiết trong cache key.
- Cache personalized/authenticated content như public.
- Debug application mà không inspect CDN headers.

## 8. Alternatives

- Browser cache only: đơn giản hơn nhưng không giảm origin traffic toàn cầu nhiều bằng CDN.
- Reverse-proxy cache: gần origin, hữu ích nhưng latency địa lý vẫn còn.
- No cache: đúng cho highly personalized/real-time data nếu correctness quan trọng hơn latency.

## 9. Trade-offs

### Advantages

- Giảm latency, bandwidth và origin load.
- Tăng resilience khi origin bị spike cho cacheable content.

### Costs / Risks

- Staleness và invalidation complexity.
- Cache key sai có thể gây data leakage.
- Purge dependency trở thành operational concern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser cache, CDN cache và origin là các layers khác nhau.

### Middle

Đọc `Cache-Control`, cache-hit headers và thiết kế hashed static assets.

### Senior

Debug stale-content incidents và thiết kế cache key/invalidation an toàn.

### Technical Lead / Architect

Đặt caching policy theo content class, privacy/freshness requirement và deployment model; quyết định khi nào CDN complexity thực sự đáng giá.

## 11. Key takeaway

- Cache policy phải gắn với content mutability và URL versioning.
- Origin đúng không có nghĩa edge đang phục vụ đúng version.
- CDN design là correctness + deployment concern, không chỉ performance optimization.

# 10. Git `bisect` cho deployment regression: biến việc tìm commit gây lỗi từ đoán mò thành binary search có evidence

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên biến trạng thái từ **good** sang **bad**.

Mental model:

```text
Good ----------------------------- Bad
                 ^ test midpoint
```

Mỗi lần test loại bỏ khoảng một nửa candidate commits. Với 1.024 commits, lý thuyết chỉ cần khoảng 10 bước nếu history/test rõ.

## 2. Why does it exist?

Deployment regression thường dẫn tới kiểu điều tra “commit nào nhìn đáng nghi”. Với nhiều commits, review thủ công chậm và dễ bias.

Nếu bug reproduce deterministic trên một commit, bisect biến incident investigation thành search có method.

## 3. How does it work?

Bắt đầu:

```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-commit>
```

Git checkout midpoint. Chạy test/reproduce:

```bash
git bisect good
# hoặc
git bisect bad
```

Lặp đến khi Git chỉ ra first bad commit.

Kết thúc:

```bash
git bisect reset
```

Có thể automate nếu có script trả exit code ổn định:

```bash
git bisect run ./repro.sh
```

## 4. Practical implementation

Ví dụ regression API serialization:

```bash
#!/usr/bin/env bash
set -e

dotnet test tests/Regression.Tests \
  --filter "FullyQualifiedName~CustomerSerializationRegression"
```

Nếu test pass ở good commit và fail ở bad commit, script có thể drive bisect tự động.

Cần khóa dependency/environment đủ ổn định để test result phản ánh code commit chứ không phải external drift.

## 5. Real production scenario

Sau release 60 commits, p95 của search endpoint tăng gấp đôi. Metrics cho thấy regression xuất hiện sau release trước nhưng không biết commit nào.

Team tạo benchmark/repro test với dataset cố định, bisect giữa hai release tags và tìm ra commit đổi LINQ query làm mất index-friendly predicate.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect cho kết quả khác nhau mỗi lần.

**Evidence** → same commit lúc pass lúc fail.

**Hypothesis** → reproduction flaky hoặc phụ thuộc environment/data/external service.

**Diagnosis** → isolate test, pin data/dependencies, tăng measurement sample nếu là performance regression.

**Fix** → biến symptom thành deterministic test trước khi tiếp tục bisect; dùng `git bisect skip` khi commit không build/test được.

**Verification** → checkout identified commit và parent; parent consistently good, commit consistently bad.

## 7. Common mistakes

- Bisect khi không có known-good baseline.
- Dùng manual subjective test “có vẻ nhanh”.
- History có commits không build nhưng không dùng `skip`.
- Kết luận commit là root cause chỉ vì nó first bad mà không review mechanism.
- Force-push/rewrite shared history trong lúc incident mà không cần thiết.

## 8. Alternatives

- Review diff giữa releases: nhanh nếu change set nhỏ.
- Feature flag disable: tốt để mitigate trước khi root cause xong.
- Observability/deployment markers: giúp localize release/time window.
- Revert suspected commit: mitigation, không phải luôn là diagnosis.

## 9. Trade-offs

### Advantages

- Search complexity logarithmic thay vì linear.
- Giảm human bias trong large change range.
- Có thể automate hoàn toàn với deterministic test.

### Costs / Risks

- Cần reproducible environment.
- Merge-heavy/non-linear history có thể làm reasoning khó hơn.
- Không hữu ích nếu bug phụ thuộc production-only state không reproduce được.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết `bisect` dùng good/bad boundaries để tìm regression commit.

### Middle

Tạo reproducible test/script và dùng `skip/reset` đúng cách.

### Senior

Kết hợp bisect với telemetry, deployment markers và performance measurement để localize regression có evidence.

### Technical Lead / Architect

Xây engineering system giúp bisect khả thi: reproducible builds, test fixtures, release tags và observable deployment history; đồng thời ưu tiên mitigation khi incident impact cao.

## 11. Key takeaway

- `git bisect` hiệu quả khi symptom được biến thành deterministic good/bad test.
- First bad commit là điểm bắt đầu root-cause analysis, không phải tự động là toàn bộ nguyên nhân.
- Reproducible builds/tests biến Git history thành diagnostic tool thực sự.
