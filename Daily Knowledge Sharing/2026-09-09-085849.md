# 1. C# exception filters: phân loại failure đúng chỗ mà không phá stack trace hoặc nuốt lỗi

## 1. What is it?

Exception filter là phần `when (...)` trong `catch` của C#. Nó cho phép runtime quyết định một `catch` có phù hợp với exception hiện tại hay không trước khi thực sự đi vào block xử lý.

Mental model:

```text
exception thrown
    ↓
inspect catch clauses
    ↓
filter true? ── no ──> continue searching
    ↓ yes
enter catch block
```

Khác biệt quan trọng là filter không chỉ là syntax tiện lợi. Nó giúp phân loại lỗi theo context mà không cần catch rồi rethrow chỉ để quyết định “đây có phải lỗi mình muốn xử lý không?”.

## 2. Why does it exist?

Trong production code, cùng một exception type có thể đại diện nhiều failure modes.

Ví dụ `SqlException` có thể là:

* deadlock;
* unique constraint violation;
* login failure;
* network interruption;
* timeout.

Nếu application catch tất cả `SqlException` và retry, unique constraint violation cũng bị retry vô ích. Nếu catch rồi `throw ex;`, stack trace còn có thể bị phá.

Exception filter cho phép xử lý đúng subset failure mà vẫn giữ exception propagation tự nhiên cho phần còn lại.

## 3. How does it work?

Ví dụ:

```csharp
try
{
    await db.SaveChangesAsync(cancellationToken);
}
catch (SqlException ex) when (ex.Number == 1205)
{
    // deadlock-specific handling
}
```

Filter được evaluate trong quá trình exception dispatch. Nếu filter trả `false`, CLR tiếp tục tìm `catch` khác như thể block này không tồn tại.

Một pattern hữu ích khác là phân biệt timeout với user cancellation:

```csharp
catch (OperationCanceledException)
    when (timeoutCts.IsCancellationRequested &&
          !requestAborted.IsCancellationRequested)
{
    // dependency timeout
}
```

## 4. Practical implementation

Ví dụ map một external API failure:

```csharp
public async Task<CustomerProfile> GetProfileAsync(
    Guid id,
    CancellationToken cancellationToken)
{
    try
    {
        return await _client.GetProfileAsync(id, cancellationToken);
    }
    catch (HttpRequestException ex)
        when (ex.StatusCode == HttpStatusCode.NotFound)
    {
        throw new CustomerNotFoundException(id, ex);
    }
}
```

Lỗi 404 được chuyển sang application-specific exception. Các network failure khác tiếp tục bubble lên resilience layer.

## 5. Real production scenario

Một payment worker dùng chung catch block cho `HttpRequestException` và coi mọi lỗi là retryable. Provider trả 400 vì request invalid nhưng worker retry hàng nghìn lần, làm queue backlog tăng.

Sau khi phân loại theo HTTP status, chỉ timeout/5xx/network failure được retry; validation failure được dead-letter hoặc mark permanent failure.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng một lỗi business bị retry liên tục.  
**Evidence** → telemetry cho thấy exception type giống nhau nhưng status/error code khác.  
**Hypothesis** → exception handling quá rộng.  
**Diagnosis** → kiểm tra catch boundaries và retry predicates.  
**Fix** → dùng exception filters hoặc typed result để phân loại transient/permanent failure.  
**Verification** → fault-injection nhiều error codes và xác nhận chỉ retry loại phù hợp.

## 7. Common mistakes

* Catch `Exception` rồi trả default value.
* Dùng `throw ex;` thay vì `throw;` khi muốn rethrow.
* Đặt business logic nặng trong filter.
* Retry dựa duy nhất vào exception type.
* Log cùng exception ở mọi layer, tạo duplicate noise.

## 8. Alternatives

Typed Result/Result<T> phù hợp expected business outcomes. Exception filter phù hợp exceptional failure cần phân loại theo metadata. Policy library như Polly cũng có predicates nhưng vẫn cần taxonomy failure đúng.

## 9. Trade-offs

### Advantages

* Phân loại exception chính xác hơn.
* Giữ propagation tự nhiên cho lỗi không match.
* Giảm catch/rethrow boilerplate.

### Costs / Risks

* Filter quá phức tạp khó đọc.
* Exception-code coupling có thể phụ thuộc provider/database.
* Dùng exception cho expected control flow vẫn có thể là thiết kế sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `catch` không nên đồng nghĩa “nuốt mọi lỗi”.

### Middle

Biết dùng `when`, preserve stack trace và phân biệt retryable/non-retryable failures.

### Senior

Thiết kế exception taxonomy, retry predicates và logging ownership giữa layers.

### Technical Lead / Architect

Quyết định boundary nào dùng exception, boundary nào dùng typed result và chuẩn hóa transient/permanent failure semantics toàn hệ thống.

## 11. Key takeaway

* Exception type chưa chắc đủ để quyết định cách xử lý.
* Filter giúp phân loại failure mà không cần catch rộng rồi rethrow.
* Retry policy phải dựa trên semantics, không chỉ class name.

# 2. ASP.NET Core model binding + validation boundary: vì sao input hợp JSON vẫn có thể sai nghiệp vụ

## 1. What is it?

Model binding biến HTTP input thành .NET object. Validation kiểm tra object đó có đáp ứng contract ở transport boundary hay không.

Mental model:

```text
HTTP body/query/route
      ↓
model binding
      ↓
transport validation
      ↓
application command
      ↓
domain/business validation
```

Điểm quan trọng: deserialize thành công chỉ chứng minh payload có shape phù hợp. Nó không chứng minh request hợp nghiệp vụ.

## 2. Why does it exist?

Nếu transport layer không validate shape/range/basic constraints, application phải xử lý input malformed sâu bên trong. Ngược lại, nếu nhồi mọi business rule vào DataAnnotations, validation sẽ dính vào DTO và khó tái sử dụng ở background jobs hoặc messaging.

Cần phân biệt:

* transport validity;
* application use-case validity;
* domain invariant.

## 3. How does it work?

Ví dụ request:

```csharp
public sealed record CreateLeaveRequest(
    DateOnly StartDate,
    DateOnly EndDate,
    string Reason);
```

JSON có thể deserialize tốt nhưng vẫn sai nếu `EndDate < StartDate` hoặc user không còn ngày phép.

Transport validation có thể chặn required/length/format. Business validation cần application/domain context và có thể cần database lookup.

## 4. Practical implementation

Minimal API với explicit validator:

```csharp
app.MapPost("/leave-requests", async (
    CreateLeaveRequest request,
    LeaveService service,
    CancellationToken ct) =>
{
    if (request.EndDate < request.StartDate)
    {
        return Results.ValidationProblem(new Dictionary<string, string[]>
        {
            [nameof(request.EndDate)] =
                ["EndDate must be on or after StartDate."]
        });
    }

    var result = await service.CreateAsync(request, ct);

    return result switch
    {
        LeaveResult.InsufficientBalance => Results.Conflict(),
        LeaveResult.Created created => Results.Created(
            $"/leave-requests/{created.Id}", created),
        _ => Results.Problem()
    };
});
```

## 5. Real production scenario

Timesheet API nhận `Hours = 24` vì JSON number hợp lệ và DTO dùng `decimal`. Dữ liệu chỉ bị phát hiện sai sau khi payroll report tổng hợp.

Sau khi thêm transport constraint và domain rule về working-hour policy, invalid request bị từ chối ngay tại boundary với error contract rõ ràng.

## 6. Failure scenario & troubleshooting

**Symptom** → database có record “hợp schema nhưng vô lý”.  
**Evidence** → API logs cho thấy model binding thành công; không có business validation trước save.  
**Hypothesis** → team coi DTO validity là domain validity.  
**Diagnosis** → trace request → validation → application → persistence.  
**Fix** → tách boundary validation và invariant validation.  
**Verification** → integration tests cho malformed, boundary và business-invalid payloads.

## 7. Common mistakes

* Đưa database-dependent validation vào DataAnnotations.
* Trả 500 cho validation failure.
* Tin nullable reference types là runtime input validation.
* Bind entity trực tiếp từ request, gây over-posting.
* Dùng một DTO cho create/update/read dù semantics khác nhau.

## 8. Alternatives

FluentValidation hoặc custom validator hữu ích cho transport/application rules phức tạp. Domain methods/constructors bảo vệ invariant cốt lõi. Không có một validation layer duy nhất phù hợp mọi loại rule.

## 9. Trade-offs

### Advantages

* Failure sớm và error contract rõ.
* Domain sạch hơn khỏi transport concerns.
* Test từng layer dễ hơn.

### Costs / Risks

* Rule có thể bị duplicate nếu ownership không rõ.
* Over-validation tạo nhiều round trips.
* Validation quá sâu ở controller làm application layer yếu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deserialize thành công chưa chắc request hợp lệ.

### Middle

Biết tách format/range validation khỏi business rule.

### Senior

Thiết kế validation ownership, avoid over-posting và map failure đúng HTTP semantics.

### Technical Lead / Architect

Quyết định invariant nằm ở domain, use-case rule nằm ở application và transport constraint nằm ở API boundary.

## 11. Key takeaway

* JSON hợp lệ không đồng nghĩa nghiệp vụ hợp lệ.
* Validation có nhiều tầng với responsibilities khác nhau.
* Entity không nên được bind trực tiếp từ untrusted HTTP input.

# 3. PostgreSQL MVCC + VACUUM: concurrency tốt hơn không có nghĩa storage tự dọn sạch

## 1. What is it?

MVCC — Multi-Version Concurrency Control — cho phép PostgreSQL giữ nhiều version của row để readers và writers ít block nhau hơn.

Mental model:

```text
UPDATE row
   ↓
old tuple remains visible to older transaction
new tuple becomes visible to newer transaction
   ↓
old tuple eventually becomes dead
   ↓
VACUUM reclaims reusable space / maintains visibility metadata
```

## 2. Why does it exist?

Nếu mọi read phải khóa row đang được update, concurrency của OLTP workload giảm mạnh. MVCC cho phép transaction đọc snapshot phù hợp mà không cần chờ writer trong nhiều trường hợp.

Đổi lại, update/delete không xóa vật lý ngay old row version. Hệ thống cần VACUUM để xử lý dead tuples.

## 3. How does it work?

Mỗi transaction nhìn snapshot theo isolation semantics. Tuple có metadata xác định transaction nào tạo/xóa nó.

Update thường tạo tuple mới thay vì overwrite in-place theo cách đơn giản. Old tuple trở thành dead khi không còn transaction nào cần thấy nó.

Autovacuum chạy nền để:

* đánh dấu/reclaim space có thể tái sử dụng;
* update visibility map;
* tránh transaction ID wraparound.

## 4. Practical implementation

Quan sát dead tuples:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Long-running transactions cũng cần kiểm tra vì chúng có thể giữ snapshot cũ:

```sql
SELECT pid, xact_start, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

## 5. Real production scenario

SaaS audit table có hàng triệu updates/deletes mỗi ngày. Storage tăng liên tục dù business record count gần như không đổi. Query latency cũng xấu dần.

Root cause là autovacuum không theo kịp churn và một reporting transaction giữ snapshot nhiều giờ, khiến dead tuples chưa thể reclaim đúng lúc.

## 6. Failure scenario & troubleshooting

**Symptom** → table/index size tăng nhanh, query đọc nhiều pages hơn.  
**Evidence** → `n_dead_tup` cao, autovacuum chạy chậm hoặc bị block bởi long transaction.  
**Hypothesis** → bloat do update/delete churn + vacuum lag.  
**Diagnosis** → pg stats, transaction age, vacuum logs.  
**Fix** → xử lý long transaction, tune autovacuum theo table, đôi khi `VACUUM FULL`/reindex trong maintenance window.  
**Verification** → theo dõi dead tuples, storage và query I/O sau remediation.

## 7. Common mistakes

* Nghĩ DELETE sẽ ngay lập tức giảm file size.
* Tắt autovacuum vì sợ CPU.
* Giữ transaction mở trong batch job hàng giờ.
* Chạy `VACUUM FULL` production mà không hiểu lock impact.
* Chỉ nhìn row count, bỏ qua table/index bloat.

## 8. Alternatives

SQL Server dùng MVCC-like behavior qua row versioning khi bật snapshot-based isolation nhưng storage mechanism khác. Partitioning có thể giúp churn-heavy retention workloads bằng drop partition thay vì mass delete.

## 9. Trade-offs

### Advantages

* Readers/writers ít block nhau hơn.
* Snapshot semantics mạnh cho concurrent workload.

### Costs / Risks

* Dead tuples và vacuum overhead.
* Long-running transactions gây bloat.
* Operational tuning cần dựa trên workload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu update/delete không nhất thiết xóa physical row ngay.

### Middle

Biết đọc `pg_stat_user_tables` và phát hiện long transaction.

### Senior

Phân tích bloat, vacuum lag, transaction lifetime và index impact.

### Technical Lead / Architect

Thiết kế batch/retention/transaction strategy để database maintenance phù hợp workload dài hạn.

## 11. Key takeaway

* MVCC đổi lock contention lấy version-management cost.
* Long transaction có thể làm VACUUM mất hiệu quả.
* Database maintenance là một phần của application design, không chỉ DBA concern.

# 4. Elasticsearch alias + zero-downtime reindexing: thay mapping mà không khóa Search API

## 1. What is it?

Elasticsearch alias là logical name trỏ tới một hoặc nhiều indices. Search API gọi alias thay vì hard-code physical index name.

Mental model:

```text
Search API → products-read alias → products-v3

reindex:
products-v3 → products-v4
                ↓
atomic alias switch
```

## 2. Why does it exist?

Nhiều mapping/analyzer changes không thể áp dụng in-place đơn giản cho dữ liệu đã index. Nếu application hard-code `products-v3`, việc reindex yêu cầu coordinated deployment và có thể gây downtime.

Alias tạo indirection để data migration và application deployment tách nhau.

## 3. How does it work?

Flow điển hình:

1. tạo `products-v4` với mapping mới;
2. bulk/reindex dữ liệu;
3. verify document count/search correctness;
4. sync delta phát sinh trong lúc reindex;
5. atomic alias switch;
6. giữ index cũ một thời gian rollback;
7. xóa index cũ sau validation.

## 4. Practical implementation

Atomic alias update:

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v3", "alias": "products-read" } },
    { "add":    { "index": "products-v4", "alias": "products-read" } }
  ]
}
```

Search API chỉ gọi:

```http
GET /products-read/_search
```

## 5. Real production scenario

E-commerce search cần đổi analyzer để hỗ trợ synonym và normalization mới. Reindex 40 triệu products mất hàng giờ.

Thay vì downtime, team build index mới song song, replay changes từ primary database, verify relevance metrics rồi switch alias trong một operation.

## 6. Failure scenario & troubleshooting

**Symptom** → sau alias switch, một số sản phẩm mới biến mất.  
**Evidence** → base reindex hoàn tất nhưng updates phát sinh trong thời gian reindex không được replay.  
**Hypothesis** → missing delta synchronization.  
**Diagnosis** → compare source-of-truth change log với destination index version.  
**Fix** → CDC/outbox/change timestamp replay trước cutover.  
**Verification** → document parity + representative search tests + lag metric về zero.

## 7. Common mistakes

* Reindex trực tiếp vào alias đang phục vụ traffic.
* Không có rollback index.
* Chỉ compare document count, không test relevance/mapping behavior.
* Không capture writes trong reindex window.
* Xóa old index ngay sau switch.

## 8. Alternatives

Nếu schema change backward-compatible, có thể dùng field mới và migrate dần. Blue/green application deployment không thay thế index migration; hai concerns có thể phối hợp nhưng độc lập.

## 9. Trade-offs

### Advantages

* Gần zero-downtime schema evolution.
* Rollback đơn giản hơn.
* Application tách khỏi physical index version.

### Costs / Risks

* Tạm thời cần storage gấp đôi.
* Cần delta sync chính xác.
* Operational workflow phức tạp hơn direct update.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu alias là logical pointer tới index.

### Middle

Biết create/reindex/switch và verify search.

### Senior

Thiết kế delta capture, rollback và correctness validation.

### Technical Lead / Architect

Quyết định source-of-truth → search synchronization contract và schema migration strategy không downtime.

## 11. Key takeaway

* Alias tách Search API khỏi physical index lifecycle.
* Reindex an toàn cần xử lý delta writes, không chỉ copy snapshot.
* Rollback và relevance verification phải là một phần của cutover plan.

# 5. Circuit Breaker + Bulkhead: cô lập dependency failure thay vì retry cho tới khi cả hệ thống sập

## 1. What is it?

Circuit Breaker ngừng gọi một dependency đang fail liên tục trong một khoảng thời gian. Bulkhead giới hạn lượng concurrency/resource mà dependency đó được phép chiếm.

Mental model:

```text
requests
   ↓
Bulkhead: max N concurrent calls
   ↓
Circuit Breaker: dependency healthy?
   ↓
remote service
```

Hai pattern giải quyết hai vấn đề khác nhau nhưng bổ sung cho nhau.

## 2. Why does it exist?

Retry không phải luôn cứu hệ thống. Nếu dependency chậm, retry tăng load lên đúng dependency đang gặp vấn đề. Đồng thời callers giữ thread/socket/connection lâu hơn, tạo cascading failure.

Bulkhead giới hạn blast radius. Circuit Breaker fail-fast khi evidence cho thấy dependency chưa sẵn sàng phục vụ.

## 3. How does it work?

Circuit thường có trạng thái:

* Closed: call bình thường;
* Open: fail-fast;
* Half-Open: thử một số request để đánh giá recovery.

Bulkhead dùng semaphore/concurrency limiter/queue capacity để giới hạn in-flight work.

## 4. Practical implementation

Conceptual .NET resilience pipeline:

```csharp
var pipeline = new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddConcurrencyLimiter(new ConcurrencyLimiterStrategyOptions
    {
        PermitLimit = 50,
        QueueLimit = 100
    })
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions<HttpResponseMessage>
    {
        FailureRatio = 0.5,
        MinimumThroughput = 20,
        SamplingDuration = TimeSpan.FromSeconds(30),
        BreakDuration = TimeSpan.FromSeconds(15)
    })
    .Build();
```

Policy values phải dựa trên traffic/latency/error characteristics, không copy từ sample.

## 5. Real production scenario

Review provider latency tăng từ 200 ms lên 8 giây. Product page API vẫn cho phép hàng nghìn concurrent calls. Thread/socket pressure lan sang toàn app, khiến cả endpoints không dùng review service cũng chậm.

Bulkhead giới hạn review dependency concurrency; circuit mở khi failure ratio tăng, product page degrade bằng “reviews temporarily unavailable” thay vì toàn site timeout.

## 6. Failure scenario & troubleshooting

**Symptom** → một dependency chậm làm toàn application p99 tăng.  
**Evidence** → in-flight calls và socket usage tập trung vào dependency đó.  
**Hypothesis** → không có isolation; retries đang amplify load.  
**Diagnosis** → dependency traces, concurrency, retry count, queue length.  
**Fix** → bounded concurrency + sane retry budget + breaker + fallback.  
**Verification** → chaos test dependency latency/failure và kiểm tra unrelated endpoints vẫn khỏe.

## 7. Common mistakes

* Circuit Breaker dùng để “làm dependency nhanh hơn”.
* Retry nằm ngoài breaker theo thứ tự gây số call ngoài dự kiến.
* Queue bulkhead vô hạn.
* Một global breaker cho nhiều host/use cases khác nhau.
* Không có degraded-mode UX.

## 8. Alternatives

Timeout là baseline luôn cần. Queue-based async decoupling phù hợp workflow không cần synchronous response. Cache có thể giảm dependency load nếu freshness cho phép nhưng không thay failure isolation.

## 9. Trade-offs

### Advantages

* Fail-fast và giảm cascading failure.
* Giới hạn blast radius.
* Bảo vệ resource của caller.

### Costs / Risks

* Tuning sai có thể reject traffic quá sớm.
* Thêm state/metrics phải monitor.
* Fallback có thể trả stale/incomplete data.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu remote call có thể chậm/fail và không nên retry vô hạn.

### Middle

Biết cấu hình timeout/retry/breaker/concurrency limit cơ bản.

### Senior

Phân tích policy ordering, failure amplification và degraded behavior.

### Technical Lead / Architect

Thiết kế dependency isolation theo business criticality và quyết định khi nào synchronous dependency nên được decouple hoàn toàn.

## 11. Key takeaway

* Retry không có isolation có thể làm outage nặng hơn.
* Bulkhead giới hạn blast radius; Circuit Breaker giúp fail-fast.
* Resilience policy phải đi kèm degraded-mode business behavior.

# 6. Azure Key Vault + Managed Identity + secret rotation: tách identity khỏi secret material và tránh rotation outage

## 1. What is it?

Managed Identity cho Azure resource một identity do platform quản lý. Key Vault lưu secret/key/certificate và cấp quyền truy cập qua identity đó.

Mental model:

```text
App Service / Function
      ↓ Managed Identity token
Microsoft Entra ID
      ↓
Key Vault authorization
      ↓
secret/certificate/key
```

Application không cần giữ Key Vault credential riêng trong config.

## 2. Why does it exist?

Nếu app config chứa client secret để đọc Key Vault, secret đó lại trở thành bootstrap secret cần bảo vệ và rotate.

Managed Identity loại bỏ credential tĩnh cho app-to-Azure authentication. Key Vault centralize secret lifecycle, access control, auditing và rotation support.

## 3. How does it work?

App dùng `DefaultAzureCredential` trong Azure. SDK lấy token từ Managed Identity endpoint. Entra ID xác thực identity; Key Vault kiểm tra RBAC/access policy rồi trả secret nếu được phép.

```text
code asks credential
→ token issued for managed identity
→ Key Vault validates token + role
→ secret version returned
```

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    new DefaultAzureCredential());

KeyVaultSecret secret =
    await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
```

Không hard-code version nếu application cần tự động nhận rotated current version, trừ khi rollout strategy cố ý pin version.

## 5. Real production scenario

Third-party API key rotate mỗi 90 ngày. Team cập nhật Key Vault nhưng app giữ secret trong singleton cache vô hạn. Production vẫn dùng old key cho tới khi instances restart và bắt đầu trả 401.

Secret storage đúng nhưng consumption lifecycle sai.

## 6. Failure scenario & troubleshooting

**Symptom** → secret đã rotate nhưng app vẫn dùng value cũ.  
**Evidence** → Key Vault version mới tồn tại; process không refetch.  
**Hypothesis** → application cache secret quá lâu.  
**Diagnosis** → inspect startup/config provider/caching behavior.  
**Fix** → refresh strategy hoặc dual-secret overlap window.  
**Verification** → rotate trong staging khi app đang chạy và xác nhận không downtime.

## 7. Common mistakes

* Dùng Key Vault nhưng vẫn lưu service principal secret trong app settings.
* Cấp role quá rộng như full vault admin cho runtime app.
* Log secret value khi debug.
* Rotate secret nhưng không test consumer refresh.
* Dùng một Key Vault/shared secret scope cho mọi environment không cần thiết.

## 8. Alternatives

Environment secret stores phù hợp local/simple deployment nhưng kém centralized lifecycle. Workload Identity trên Kubernetes giải quyết identity mapping trong AKS. Certificate-based auth vẫn cần lifecycle management.

## 9. Trade-offs

### Advantages

* Giảm static credentials.
* Centralized authorization/audit/rotation.
* Tích hợp Azure identity tốt.

### Costs / Risks

* Network dependency và startup behavior cần thiết kế.
* Rotation semantics vẫn thuộc application/system design.
* RBAC và vault topology cần governance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Key Vault lưu secret; Managed Identity giúp app chứng minh identity mà không giữ password.

### Middle

Implement `DefaultAzureCredential`, least privilege và config integration.

### Senior

Thiết kế secret refresh, dual-key rotation, network/private endpoint và outage behavior.

### Technical Lead / Architect

Chuẩn hóa identity-first architecture và secret ownership/rotation policy trên toàn platform.

## 11. Key takeaway

* Key Vault không tự giải quyết rotation nếu consumer cache sai.
* Managed Identity loại bỏ phần lớn bootstrap credential cho Azure workloads.
* Secret lifecycle phải được test khi application đang chạy, không chỉ lúc deploy.

# 7. IIS Application Pool recycling: process lifecycle, hidden in-memory state và production cold start

## 1. What is it?

IIS Application Pool quản lý worker process (`w3wp.exe`) chạy web application. Recycling thay worker process cũ bằng process mới theo cấu hình hoặc trigger vận hành.

Mental model:

```text
IIS App Pool
   ↓
w3wp process A
   ↓ recycle
w3wp process B starts
   ↓
application cold start / cache rebuild
```

## 2. Why does it exist?

Process có thể cần recycle vì configuration changes, scheduled policy, memory limit, deployment hoặc recovery. IIS dùng lifecycle management để giữ hosting environment ổn định.

Nhưng application không được giả định process sống vĩnh viễn.

## 3. How does it work?

Khi recycle, IIS có thể start process mới trước rồi drain process cũ trong overlapping recycle. Tuy nhiên in-memory state của process cũ không chuyển sang process mới.

Những thứ mất khi recycle:

* `IMemoryCache`;
* static mutable state;
* in-process session;
* singleton runtime state;
* background timers không externalized.

## 4. Practical implementation

Application nên externalize durable state và handle warm-up:

```csharp
builder.Services.AddDistributedMemoryCache(); // demo only
builder.Services.AddSession();
```

Trong production multi-instance, session cần distributed backing store nếu session thật sự cần tồn tại qua process/instance changes.

Health endpoint cũng nên tách liveness khỏi readiness trong startup window.

## 5. Real production scenario

Legacy ASP.NET application giữ shopping cart/session trong-process. Nightly app-pool recycle làm một nhóm users “mất đăng nhập” hoặc mất state. Team ban đầu tưởng auth provider lỗi theo lịch.

Root cause là state ownership nằm trong worker process.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi/latency spike theo thời điểm cố định mỗi ngày.  
**Evidence** → IIS logs/Event Viewer cho thấy App Pool recycle đúng thời điểm.  
**Hypothesis** → cold start hoặc in-memory state loss.  
**Diagnosis** → correlate process start time, app logs, JIT/cache initialization.  
**Fix** → externalize durable state, warm-up, bỏ scheduled recycle không cần thiết hoặc tune hợp lý.  
**Verification** → controlled recycle và quan sát session correctness + p95 startup latency.

## 7. Common mistakes

* Dùng recycle như “memory leak fix” lâu dài.
* Giữ critical scheduled job trong web process.
* Tin singleton sống suốt deployment lifetime.
* In-process session trong load-balanced environment.
* Không monitor process restart reason.

## 8. Alternatives

Modern hosting trên App Service/containers cũng có process restarts; chỉ khác orchestration. Windows Service/Worker Service phù hợp background processing hơn web process nếu lifecycle độc lập cần thiết.

## 9. Trade-offs

### Advantages

* Recovery và lifecycle management đơn giản cho enterprise hosting.
* Có thể hạn chế process degradation kéo dài.

### Costs / Risks

* Cold start.
* In-memory state loss.
* Scheduled recycle có thể che root cause memory/resource bug.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu web process có thể restart bất kỳ lúc nào.

### Middle

Biết đọc IIS/Event Viewer và phân biệt app restart với request failure.

### Senior

Phân tích cold start, session/cache/background task implications.

### Technical Lead / Architect

Thiết kế application stateless đủ mức cần thiết và tách durable/background responsibilities khỏi IIS worker lifecycle.

## 11. Key takeaway

* Process restart là normal hosting event, không phải edge case.
* Critical state không nên chỉ tồn tại trong `w3wp` memory.
* Scheduled recycle không phải giải pháp gốc cho memory leak.

# 8. Load testing p95/p99 + coordinated omission: benchmark sai có thể chứng minh hệ thống “nhanh” một cách giả tạo

## 1. What is it?

p95/p99 mô tả tail latency: 95% hoặc 99% requests hoàn thành nhanh hơn ngưỡng đó. Coordinated omission là lỗi đo khi load generator vô tình gửi ít request hơn trong lúc system chậm, nên không ghi nhận đầy đủ latency mà user thực tế sẽ chịu.

## 2. Why does it exist?

Average latency che tail. Một API average 100 ms nhưng p99 5 giây vẫn có thể gây trải nghiệm tệ cho users và timeout chain.

Tệ hơn, benchmark kiểu “gửi request mới sau khi request trước hoàn tất” tự giảm offered load khi service chậm. Kết quả nhìn đẹp hơn thực tế.

## 3. How does it work?

Closed-loop test:

```text
send request
wait 5s
send next request
```

Khi service chậm, generator cũng giảm request rate.

Open-model arrival:

```text
requests arrive theo planned rate
independent of previous response time
```

Cách thứ hai mô phỏng traffic thực tốt hơn cho nhiều web workloads.

## 4. Practical implementation

Ví dụ k6 concept:

```javascript
export const options = {
  scenarios: {
    api: {
      executor: 'constant-arrival-rate',
      rate: 500,
      timeUnit: '1s',
      duration: '5m',
      preAllocatedVUs: 200
    }
  }
};
```

Theo dõi đồng thời:

* p50/p95/p99;
* error rate;
* throughput achieved vs target;
* saturation: CPU, DB pool, ThreadPool, queue length.

## 5. Real production scenario

Staging test cho thấy checkout API p99 400 ms ở “500 users”. Production lại timeout ở sale campaign.

Review test phát hiện mỗi virtual user chờ response rồi mới gửi request tiếp. Khi API chậm, actual RPS rơi từ 800 xuống 180, nên test không giữ offered load như campaign thật.

## 6. Failure scenario & troubleshooting

**Symptom** → load test xanh nhưng production tail latency xấu hơn nhiều.  
**Evidence** → test throughput giảm đúng lúc latency tăng.  
**Hypothesis** → coordinated omission/closed-loop behavior.  
**Diagnosis** → compare target arrival rate với achieved RPS.  
**Fix** → dùng arrival-rate model phù hợp và saturation telemetry.  
**Verification** → rerun, đảm bảo offered load được giữ cho tới point of saturation.

## 7. Common mistakes

* Chỉ báo average latency.
* Không tính warm-up/cold cache.
* Test DB dataset nhỏ hơn production rất nhiều.
* Không giữ RPS target khi response chậm.
* Tăng load nhưng không monitor dependency saturation.

## 8. Alternatives

Closed-loop vẫn hữu ích cho workload thật sự user-think-time dependent. BenchmarkDotNet phù hợp microbenchmark code path, không thay system load test.

## 9. Trade-offs

### Advantages

* Tail percentiles phản ánh user impact tốt hơn average.
* Arrival-rate test expose saturation rõ hơn.

### Costs / Risks

* Cần nhiều load-generator capacity.
* Test realism đòi hỏi representative data/dependencies.
* Sai model traffic vẫn tạo kết luận sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu average không đại diện worst tail experience.

### Middle

Biết đọc p50/p95/p99 và throughput.

### Senior

Thiết kế load model, phát hiện coordinated omission và correlate saturation metrics.

### Technical Lead / Architect

Định nghĩa performance acceptance theo business traffic model và capacity margin, không theo một con số average duy nhất.

## 11. Key takeaway

* Tail latency quan trọng hơn average trong production API.
* Load generator phải giữ đúng traffic model khi system chậm.
* Benchmark chỉ có giá trị nếu offered load, data và bottleneck telemetry đáng tin.

# 9. CSRF trong cookie-authenticated web app: vì sao CORS không phải CSRF protection

## 1. What is it?

CSRF — Cross-Site Request Forgery — lợi dụng việc browser tự động gửi credential như authentication cookie tới target site, ngay cả khi request được kích hoạt từ site độc hại.

Mental model:

```text
User logged in to bank.example
      ↓ browser stores auth cookie
attacker.example triggers POST to bank.example
      ↓
browser automatically attaches cookie
```

## 2. Why does it exist?

Cookie authentication dựa trên browser tự attach cookie theo domain/path/SameSite rules. Server nhìn thấy cookie hợp lệ nhưng không biết request có thực sự được user khởi tạo từ trusted UI hay không.

CORS chủ yếu điều khiển việc browser cho JavaScript đọc/gửi cross-origin requests trong một số điều kiện; nó không phải universal CSRF defense.

## 3. How does it work?

Defense thường kết hợp:

* `SameSite` cookie phù hợp;
* anti-forgery token;
* Origin/Referer validation trong một số kiến trúc;
* không dùng state-changing GET;
* explicit custom header với SPA khi flow cho phép.

ASP.NET Core anti-forgery dùng token pair để chứng minh request đến từ page/app đã nhận token hợp lệ.

## 4. Practical implementation

MVC/Razor:

```csharp
[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> ChangeEmail(ChangeEmailRequest request)
{
    ...
}
```

Form:

```html
<form method="post">
    @Html.AntiForgeryToken()
    ...
</form>
```

Với SPA + cookie auth, cần thiết kế token issuance/header strategy rõ ràng thay vì tắt validation cho tiện.

## 5. Real production scenario

Employee portal dùng cookie auth. Endpoint `/profile/email` chấp nhận POST form-url-encoded và không có anti-forgery protection. Attacker gửi link tới page ngoài có auto-submit form, browser victim gửi auth cookie theo request.

Nếu endpoint chỉ kiểm tra “user đã login chưa”, request vẫn hợp lệ về authentication.

## 6. Failure scenario & troubleshooting

**Symptom** → user báo account setting đổi dù không thực hiện.  
**Evidence** → authenticated request có cookie hợp lệ nhưng Origin/anti-forgery evidence thiếu.  
**Hypothesis** → CSRF.  
**Diagnosis** → inspect cookie SameSite, endpoint methods/content-types và antiforgery config.  
**Fix** → anti-forgery + SameSite + request design phù hợp.  
**Verification** → browser-based security test từ malicious origin.

## 7. Common mistakes

* “Có CORS rồi nên không cần CSRF token.”
* Dùng GET để thay đổi state.
* Set `SameSite=None` toàn bộ cookie mà không hiểu impact.
* Chỉ validate token ở một số sensitive endpoints không có policy rõ.
* Confuse CSRF với XSS; hai threat khác nhau và có thể kết hợp.

## 8. Alternatives

Bearer token trong Authorization header thường không tự được browser attach như cookie, nên CSRF profile khác; nhưng XSS/token storage lại trở thành concern lớn. Không có auth mechanism nào tự loại bỏ mọi web threat.

## 9. Trade-offs

### Advantages

* Anti-forgery token chặn request không có trusted request context.
* SameSite giảm nhiều cross-site cookie scenarios.

### Costs / Risks

* SPA flow phức tạp hơn.
* Third-party/embedded scenarios có thể cần SameSite exceptions.
* XSS vẫn có thể bypass nhiều CSRF defenses nếu attacker chạy code trong origin thật.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser tự gửi cookie và authentication không chứng minh user intention.

### Middle

Biết cấu hình antiforgery/SameSite và không dùng state-changing GET.

### Senior

Đánh giá SPA, cross-site embedding, proxy và cookie policy interactions.

### Technical Lead / Architect

Chọn auth/browser security model toàn ứng dụng và chuẩn hóa CSRF/XSS/CORS responsibilities thay vì xử lý ad hoc từng endpoint.

## 11. Key takeaway

* CORS không phải CSRF protection.
* Cookie auth cần xem xét anti-forgery vì browser tự attach credential.
* Authentication chứng minh identity, không chứng minh user intention.

# 10. Architecture Decision Record (ADR): lưu reasoning và trade-off thay vì chỉ lưu kết quả cuối cùng

## 1. What is it?

ADR là tài liệu ngắn ghi lại một quyết định kiến trúc quan trọng cùng context, options, trade-offs và consequences.

Mental model:

```text
Context
  ↓
Options considered
  ↓
Decision
  ↓
Consequences / follow-up
```

ADR không phải full design document và cũng không phải meeting minutes.

## 2. Why does it exist?

Sau 6–12 tháng, code chỉ cho biết **đã làm gì**, hiếm khi cho biết **tại sao**.

Ví dụ team thấy Redis nhưng không biết:

* vì sao thêm Redis;
* dữ liệu nào được phép stale;
* tại sao không dùng IMemoryCache;
* failure mode được chấp nhận là gì;
* assumption scale lúc ra quyết định.

Không có reasoning history, team dễ “refactor ngược” về option từng bị loại vì constraint thật đã bị quên.

## 3. How does it work?

Một ADR thường gồm:

```text
Title
Status: Proposed / Accepted / Superseded
Context
Decision Drivers
Options Considered
Decision
Consequences
Follow-up / Review Trigger
```

ADR nên immutable về lịch sử: khi quyết định thay đổi, tạo ADR mới supersede ADR cũ thay vì rewrite quá khứ.

## 4. Practical implementation

Ví dụ ngắn:

```markdown
# ADR-012: Use Azure Service Bus for invoice processing

Status: Accepted

## Context
Invoice processing takes 20–90 seconds and must survive API restarts.

## Decision Drivers
- request latency must stay below 2s
- duplicate delivery is acceptable if consumer is idempotent
- operations team already supports Service Bus

## Decision
HTTP API persists request + Outbox record; worker consumes Service Bus.

## Consequences
- eventual consistency
- requires idempotent consumer
- queue backlog becomes an operational signal
```

## 5. Real production scenario

Team mới muốn chuyển modular monolith thành microservices “vì scale”. ADR cũ cho thấy system từng intentionally chọn monolith vì team nhỏ, transaction consistency quan trọng và deployment ownership chưa tách.

Decision có thể vẫn cần thay đổi, nhưng discussion bắt đầu từ constraints thật thay vì opinion.

## 6. Failure scenario & troubleshooting

**Symptom** → ADR repository đầy tài liệu nhưng không ai dùng.  
**Evidence** → ADR ghi quyết định sau khi implementation xong, không có options/consequences.  
**Hypothesis** → ADR bị biến thành compliance paperwork.  
**Diagnosis** → review timing và decision quality.  
**Fix** → chỉ ADR cho decision có lasting architectural impact; viết trước/đồng thời với decision.  
**Verification** → architecture review có thể dùng ADR để hiểu rationale mà không cần hỏi original author.

## 7. Common mistakes

* Viết ADR cho mọi coding detail nhỏ.
* Chỉ ghi “Decision: use Kafka” mà không có context.
* Không ghi rejected alternatives.
* Chỉnh ADR cũ để phù hợp hiện tại, làm mất lịch sử.
* Không có review trigger khi assumption thay đổi.

## 8. Alternatives

Full RFC phù hợp thay đổi lớn cần nhiều review. Design doc phù hợp implementation detail sâu hơn. Git commit/PR discussion hữu ích nhưng khó trở thành canonical long-term reasoning record.

## 9. Trade-offs

### Advantages

* Giữ institutional memory.
* Làm trade-offs explicit.
* Hỗ trợ onboarding và future migration.

### Costs / Risks

* Có maintenance cost.
* Dễ thành documentation bureaucracy nếu scope quá rộng.
* Decision stale nếu không có superseding discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu architecture decision có context và consequences, không chỉ “best practice”.

### Middle

Biết đọc ADR để hiểu constraints trước khi refactor.

### Senior

Viết ADR với alternatives, failure modes và operational implications.

### Technical Lead / Architect

Dùng ADR như decision-governance mechanism: lưu assumption, review trigger, ownership và migration consequence.

## 11. Key takeaway

* Code lưu implementation; ADR lưu reasoning.
* ADR tốt tập trung vào decision có long-term consequence.
* Khi context thay đổi, supersede decision thay vì rewrite lịch sử.
