# 1. `System.IO.Pipelines`: high-throughput I/O mà không biến buffer ownership thành bug

## 1. What is it?

`System.IO.Pipelines` là abstraction cho producer/consumer I/O hiệu năng cao. Thay vì liên tục allocate byte arrays rồi copy dữ liệu giữa network, parser và application, `PipeReader`/`PipeWriter` quản lý segmented buffers và cho phép đọc dữ liệu theo streaming boundary.

## 2. Why does it exist?

Network protocols thường nhận dữ liệu theo chunks không trùng message boundaries. Code dùng `Stream.ReadAsync` + array tự quản lý phải xử lý partial reads, buffer growth, compaction và allocations. Pipelines gom các vấn đề này vào một model chuẩn hơn.

## 3. How does it work?

Producer ghi vào `PipeWriter`; consumer gọi `ReadAsync` và nhận `ReadOnlySequence<byte>`. Consumer phải báo vị trí đã consume và examined bằng `AdvanceTo`. Buffer chỉ được reclaim khi ownership contract được tuân thủ.

```text
Socket -> PipeWriter -> segmented buffer -> PipeReader -> parser
```

## 4. Practical implementation

```csharp
static async Task ReadLinesAsync(PipeReader reader, CancellationToken ct)
{
    while (true)
    {
        var result = await reader.ReadAsync(ct);
        var buffer = result.Buffer;

        while (TryReadLine(ref buffer, out var line))
            Process(line);

        reader.AdvanceTo(buffer.Start, buffer.End);
        if (result.IsCompleted) break;
    }

    await reader.CompleteAsync();
}
```

Parser phải xử lý delimiter nằm giữa hai segments; không được giả định `FirstSpan` chứa toàn message.

## 5. Real production scenario

Một ingestion service nhận telemetry TCP liên tục. Array-per-message tạo allocation rate lớn và Gen 0 collections dày. Pipelines cho phép parser đọc trực tiếp từ pooled segmented buffers và giảm copying.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng dù throughput ổn. **Evidence** → retained pipe segments và consumer chậm. **Hypothesis** → `AdvanceTo` sai hoặc consumer giữ sequence quá lâu. **Diagnosis** → kiểm tra consumed/examined positions và allocation profile. **Fix** → advance chính xác, copy chỉ dữ liệu cần sống lâu. **Verification** → working set và GC rate ổn định dưới load test.

## 7. Common mistakes

Giữ `ReadOnlySequence` sau lần `AdvanceTo`; assume contiguous memory; không complete reader/writer; dùng Pipelines cho CRUD API nhỏ nơi `Stream` đã đủ; tối ưu trước khi đo.

## 8. Alternatives

`Stream` đơn giản hơn cho phần lớn application I/O. `Channel<T>` phù hợp truyền logical objects giữa producers/consumers, không thay thế byte-oriented pipelines.

## 9. Trade-offs

### Advantages

Giảm allocations/copies, hỗ trợ partial data tự nhiên và backpressure tốt hơn.

### Costs / Risks

API phức tạp hơn; ownership sai gây corruption/memory retention; lợi ích nhỏ nếu throughput thấp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu network read không đảm bảo một read bằng một message.

### Middle

Implement parser đúng với segmented buffer và cancellation.

### Senior

### Technical Lead / Architect

## 11. Key takeaway

- Pipelines tối ưu buffer flow, không thay thế business abstractions.
- `AdvanceTo` là ownership contract quan trọng.
- Chỉ dùng khi throughput/allocation thực sự là bottleneck.

# 2. ASP.NET Core idempotent API design với `ETag` và `If-Match`

## 1. What is it?

`ETag` biểu diễn version của resource. Client gửi `If-Match` khi update để server chỉ thực hiện mutation nếu version hiện tại vẫn đúng. Đây là HTTP-level optimistic concurrency.

## 2. Why does it exist?

Client thường đọc resource, chỉnh sửa rồi gửi update sau vài giây/phút. Nếu resource đã bị actor khác thay đổi, blind PUT/PATCH có thể tạo lost update.

## 3. How does it work?

Server trả `ETag: "v42"`. Client update với `If-Match: "v42"`. Server so version atomically với persisted concurrency token. Không match thì trả `412 Precondition Failed` thay vì overwrite.

## 4. Practical implementation

```csharp
app.MapPut("/orders/{id}", async (int id, UpdateOrder dto,
    HttpRequest request, AppDbContext db, CancellationToken ct) =>
{
    var order = await db.Orders.SingleOrDefaultAsync(x => x.Id == id, ct);
    if (order is null) return Results.NotFound();

    var expected = request.Headers.IfMatch.ToString().Trim('"');
    if (expected != Convert.ToBase64String(order.Version))
        return Results.StatusCode(StatusCodes.Status412PreconditionFailed);

    order.Note = dto.Note;
    await db.SaveChangesAsync(ct);
    return Results.NoContent();
});
```

Database concurrency token vẫn là enforcement cuối cùng để tránh race giữa check và commit.

## 5. Real production scenario

Hai nhân viên mở cùng approval request. Người A sửa comment; người B lưu form cũ sau đó. `If-Match` giúp B nhận conflict thay vì xóa thay đổi của A.

## 6. Failure scenario & troubleshooting

**Symptom** → update đôi khi trả 412. **Evidence** → ETag client cũ hơn row version. **Diagnosis** → conflict hợp lệ, không phải infrastructure failure. **Fix** → UI reload/merge hoặc yêu cầu user xác nhận. **Verification** → concurrent integration test không tạo lost update.

## 7. Common mistakes

Tạo ETag từ timestamp độ phân giải thấp; check version trong memory nhưng update SQL không có concurrency predicate; retry 412 tự động; nhầm idempotency của HTTP method với concurrency safety.

## 8. Alternatives

`409 Conflict` với explicit version field dễ dùng cho non-HTTP clients. Pessimistic locking phù hợp critical short transactions nhưng không phù hợp giữ lock trong thời gian user chỉnh form.

## 9. Trade-offs

### Advantages

Dùng chuẩn HTTP, giảm lost update và làm concurrency contract explicit.

### Costs / Risks

Client phải lưu version và xử lý conflict; API gateway/cache phải preserve headers đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ETag là resource version.

### Middle

Implement `If-Match` và status code đúng.

### Senior

Liên kết HTTP precondition với database atomic concurrency.

### Technical Lead / Architect

Quyết định resource nào cần optimistic concurrency và conflict UX nào phù hợp business.

## 11. Key takeaway

- `If-Match` bảo vệ update dựa trên version client đã đọc.
- Enforcement cuối phải atomic ở persistence layer.
- Conflict là business state cần xử lý, không phải lỗi để retry mù.

# 3. EF Core temporal tables: audit và point-in-time recovery ở đúng boundary

## 1. What is it?

SQL Server temporal table tự lưu historical row versions vào history table khi `UPDATE`/`DELETE`. EF Core hỗ trợ mapping và temporal queries để đọc trạng thái tại một thời điểm hoặc khoảng thời gian.

## 2. Why does it exist?

Audit bằng application code dễ bị bỏ sót khi có nhiều write paths, scripts hoặc batch jobs. Temporal tables đưa version history xuống database boundary cho row state.

## 3. How does it work?

Current table có period columns; SQL Server tự chuyển version cũ sang history table trong cùng database operation. EF Core có `TemporalAsOf`, `TemporalAll` và range queries.

## 4. Practical implementation

```csharp
modelBuilder.Entity<Employee>()
    .ToTable("Employees", b => b.IsTemporal());

var snapshot = await db.Employees
    .TemporalAsOf(instantUtc)
    .AsNoTracking()
    .SingleAsync(x => x.Id == employeeId);
```

Temporal history không tự ghi business reason hoặc actor; nếu cần, audit event riêng vẫn cần thiết.

## 5. Real production scenario

HR cần biết employee record trông như thế nào tại thời điểm payroll chạy. Temporal query cho point-in-time state mà không phải reconstruct từ application logs.

## 6. Failure scenario & troubleshooting

**Symptom** → history database tăng nhanh. **Evidence** → high-update tables tạo nhiều historical rows. **Hypothesis** → retention không được thiết kế. **Fix** → retention/archive policy theo compliance. **Verification** → storage growth và query performance nằm trong budget.

## 7. Common mistakes

Coi temporal table là full audit trail; không lưu actor/reason; dùng local time thay UTC; giữ history vô hạn; query `TemporalAll` trên bảng lớn mà không giới hạn.

## 8. Alternatives

Application audit log ghi business context tốt hơn. Event sourcing lưu domain events nhưng có complexity lớn hơn. CDC phục vụ change propagation hơn là user-facing audit.

## 9. Trade-offs

### Advantages

History nhất quán với database writes, point-in-time query thuận tiện.

### Costs / Risks

Storage tăng, retention cần quản trị, không tự giải thích ý nghĩa business của thay đổi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu current row và historical versions.

### Middle

Map temporal table và query snapshots.

### Senior

Thiết kế retention, indexing và phân biệt audit kỹ thuật/business.

### Technical Lead / Architect

Chọn temporal, audit events hoặc event sourcing dựa trên mục tiêu compliance/recovery/domain history.

## 11. Key takeaway

- Temporal tables lưu row history, không phải toàn bộ business audit semantics.
- Retention là phần của thiết kế, không phải cleanup về sau.
- Dùng UTC và kiểm soát query scope.

# 4. SQL Server lock escalation: khi nhiều row locks trở thành table-level contention

## 1. What is it?

Lock escalation là cơ chế SQL Server chuyển nhiều fine-grained locks thành lock lớn hơn, thường table lock, để giảm memory/lock-management overhead. Điều này có thể biến một batch update thành contention toàn bảng.

## 2. Why does it exist?

Hàng chục nghìn row/page locks tiêu thụ memory và CPU quản lý. Engine cần cân bằng concurrency với chi phí lock bookkeeping.

## 3. How does it work?

Một transaction chạm rất nhiều rows có thể kích hoạt escalation nếu điều kiện cho phép. Table lock sau đó block operations vốn không đụng cùng rows. Query plan, access path, transaction size và concurrent locks đều ảnh hưởng behavior.

## 4. Practical implementation

Thay vì update hàng triệu rows trong một transaction, batch có kiểm soát:

```sql
WHILE 1 = 1
BEGIN
    UPDATE TOP (2000) Orders
    SET Archived = 1
    WHERE Archived = 0 AND CreatedAt < DATEADD(year, -3, SYSUTCDATETIME());

    IF @@ROWCOUNT = 0 BREAK;
END
```

Cần index/access pattern phù hợp để mỗi batch không scan toàn bảng.

## 5. Real production scenario

Nightly archival job chạy cùng giờ với order API. Job update 500k rows trong transaction dài; table lock làm API writes chờ dù chúng thao tác orders mới.

## 6. Failure scenario & troubleshooting

**Symptom** → request latency tăng, blocking chains dài. **Evidence** → DMVs/Extended Events cho thấy blocking session và lock escalation. **Hypothesis** → batch transaction quá lớn. **Diagnosis** → inspect plan, lock footprint và transaction duration. **Fix** → batching, index/access pattern, scheduling hoặc redesign archival. **Verification** → lock waits và p95 giảm.

## 7. Common mistakes

Disable escalation như fix đầu tiên; tăng command timeout; batch nhưng predicate vẫn full scan; giữ transaction mở trong application logic dài; nhầm blocking với deadlock.

## 8. Alternatives

Partition switching có thể tốt cho lifecycle data lớn. Online/background archival theo small batches đơn giản hơn. Isolation level khác không loại bỏ write locks.

## 9. Trade-offs

### Advantages

Escalation giúp engine giới hạn lock-management overhead.

### Costs / Risks

Lock coarse-grained làm giảm concurrency mạnh trong workload đồng thời.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt row/page/table locks và blocking.

### Middle

Tìm blocking session và transaction dài.

### Senior

Liên kết plan → rows touched → locks → latency.

### Technical Lead / Architect

Thiết kế batch/data lifecycle để maintenance không cạnh tranh critical traffic.

## 11. Key takeaway

- Lock escalation thường là triệu chứng của access pattern/transaction footprint.
- Timeout dài hơn không sửa contention.
- Batch phải nhỏ cả về transaction lẫn rows thực sự được scan/touch.

# 5. Redis cache invalidation ownership: cache-aside không tự giải quyết consistency

## 1. What is it?

Cache-aside để application đọc Redis trước database và populate cache khi miss. Nhưng correctness phụ thuộc vào ai chịu trách nhiệm invalidate/update key khi source of truth thay đổi.

## 2. Why does it exist?

Cache làm dữ liệu tồn tại ở ít nhất hai nơi. TTL chỉ giới hạn stale window; nó không đảm bảo user đọc dữ liệu mới ngay sau write.

## 3. How does it work?

```text
Read: API -> Redis miss -> DB -> Redis SET
Write: API -> DB commit -> invalidate Redis
```

Race xảy ra nếu concurrent read populate cache bằng dữ liệu cũ quanh thời điểm write.

## 4. Practical implementation

```csharp
await db.SaveChangesAsync(ct);
await cache.RemoveAsync($"product:{product.Id}", ct);
```

Đây vẫn là two-system operation. Nếu invalidation thất bại sau DB commit, cần TTL, retry/outbox hoặc chấp nhận bounded staleness theo business requirement.

## 5. Real production scenario

Price update commit thành công nhưng Redis timeout lúc invalidate. Product page tiếp tục hiển thị giá cũ tới khi TTL hết; với checkout, mức stale này có thể không chấp nhận được.

## 6. Failure scenario & troubleshooting

**Symptom** → DB đúng nhưng API trả dữ liệu cũ. **Evidence** → cache entry version/timestamp cũ. **Hypothesis** → invalidation bị mất. **Diagnosis** → correlate write logs với cache dependency failures. **Fix** → reliable invalidation hoặc bỏ cache khỏi correctness-critical path. **Verification** → chaos test Redis failure sau DB commit.

## 7. Common mistakes

TTL rất dài nhưng không có invalidation; mọi service tự tạo key convention; cache financial/authorization decisions thiếu freshness rule; Redis outage làm toàn API fail dù DB còn khỏe.

## 8. Alternatives

`IMemoryCache` đơn giản cho single-instance/local data. Read-through abstraction giảm boilerplate nhưng không xóa consistency problem. Không cache là lựa chọn đúng nếu DB đáp ứng SLO.

## 9. Trade-offs

### Advantages

Giảm read latency và database load.

### Costs / Risks

Staleness, invalidation complexity, serialization/versioning và thêm critical dependency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache không phải source of truth.

### Middle

Implement cache-aside, TTL và invalidation.

### Senior

Reason về races, Redis outage và stale tolerance.

### Technical Lead / Architect

Xác định ownership, freshness SLO và liệu cache có thực sự cần tồn tại.

## 11. Key takeaway

- Cache invalidation là consistency design, không chỉ API call `Remove`.
- TTL là safety net, không phải guarantee freshness.
- Đừng cache nếu operational complexity lớn hơn lợi ích đo được.

# 6. Bounded Context integration: chọn synchronous API, events hay shared data theo ownership

## 1. What is it?

Bounded Context là boundary nơi một domain model và ngôn ngữ nghiệp vụ có nghĩa nhất quán. Integration giữa contexts cần contract rõ thay vì chia sẻ entity/database trực tiếp.

## 2. Why does it exist?

Customer trong Sales có thể khác Customer trong Billing. Shared model tạo coupling: một thay đổi schema vì Sales có thể phá Billing dù business responsibilities khác nhau.

## 3. How does it work?

Sales sở hữu sales data/transaction; Billing sở hữu billing data. Dependency direction đi qua explicit contracts. Synchronous API phù hợp khi caller cần kết quả ngay; events phù hợp propagation state không cần transaction đồng bộ.

```text
Sales Context --OrderPlaced--> Billing Context
      |                           |
   Sales DB                    Billing DB
```

Không có transaction ACID xuyên hai DB; failure propagation và eventual consistency phải explicit.

## 4. Practical implementation

Integration event chỉ expose contract cần thiết:

```csharp
public sealed record OrderPlacedV1(
    Guid OrderId,
    Guid CustomerId,
    decimal Total,
    string Currency);
```

Không serialize EF entity/domain aggregate làm public message.

## 5. Real production scenario

E-commerce Order context publish `OrderPlaced`; Loyalty context cộng điểm và Notification gửi email. Order commit không nên phụ thuộc SMTP hoặc Loyalty database availability.

## 6. Failure scenario & troubleshooting

**Symptom** → order thành công nhưng loyalty chưa cập nhật. **Evidence** → event backlog/retry. **Diagnosis** → expected eventual consistency hay delivery failure phải được phân biệt bằng SLO. **Fix** → idempotent consumer, DLQ/replay và reconciliation. **Verification** → lag trở lại budget và invariant local vẫn đúng.

## 7. Common mistakes

Shared database vì “nhanh”; event chứa internal entity graph; context boundary theo technical layer; synchronous call chain quá dài; không định nghĩa owner của data.

## 8. Alternatives

Modular Monolith với module boundaries và một database có thể đơn giản hơn khi deployment independence chưa cần. Shared schema chỉ phù hợp khi thực chất vẫn cùng ownership boundary.

## 9. Trade-offs

### Advantages

Change isolation, ownership rõ, model phù hợp từng domain.

### Costs / Risks

Contract/versioning, duplicate data, eventual consistency và operational overhead.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cùng từ có thể mang nghĩa khác theo domain.

### Middle

Implement explicit API/event contracts.

### Senior

Reason về transaction boundary, failure propagation và versioning.

### Technical Lead / Architect

Quyết định boundary dựa trên business ownership/change patterns; không tách service chỉ vì muốn microservices.

## 11. Key takeaway

- Boundary tốt bắt đầu từ business ownership, không từ folder/service count.
- Shared database tạo coupling mạnh hơn API/event contract.
- Modular Monolith thường đủ nếu chưa cần independent deployment.

# 7. Azure SQL failover: transient connectivity, retry và transaction ambiguity

## 1. What is it?

Azure SQL có high-availability/failover mechanisms có thể chuyển connection sang replica/endpoint khác khi failure. Application phải chịu được transient disconnect trong quá trình này.

## 2. Why does it exist?

Database node, maintenance hoặc regional components có thể fail. Availability ở infrastructure layer không có nghĩa connection hiện tại sống mãi; application vẫn thấy transient errors.

## 3. How does it work?

Client connection có thể bị drop; connection pool loại connection lỗi và lần open sau resolve endpoint hiện tại. Retry phù hợp operations chưa có ambiguous side effects. Với transaction, disconnect sau commit request có thể khiến client không biết commit đã xảy ra chưa.

## 4. Practical implementation

```csharp
builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(connectionString, sql =>
        sql.EnableRetryOnFailure(
            maxRetryCount: 5,
            maxRetryDelay: TimeSpan.FromSeconds(10),
            errorNumbersToAdd: null)));
```

EF execution strategy phải được hiểu cùng explicit transactions; business command cần idempotency nếu retry có thể lặp side effect.

## 5. Real production scenario

Checkout đang ghi order khi Azure SQL failover. API nhận connection error. Retry toàn command mà không idempotency có thể tạo duplicate order nếu transaction trước thực tế đã commit.

## 6. Failure scenario & troubleshooting

**Symptom** → spike SQL transient errors và request retries. **Evidence** → Azure SQL events + application dependency telemetry. **Hypothesis** → failover/maintenance. **Diagnosis** → xác định operation nào safe retry, operation nào outcome ambiguous. **Fix** → resilient connection policy + idempotent command/reconciliation. **Verification** → failover test không tạo duplicate business effects.

## 7. Common mistakes

Retry mọi exception; retry transaction chứa external HTTP side effect; connection timeout quá dài; không monitor retry count; nghĩ HA loại bỏ downtime hoàn toàn.

## 8. Alternatives

Application-level active/active data architecture có thể tăng availability nhưng complexity rất cao. Với đa số systems, Azure SQL HA + resilient application đơn giản hơn.

## 9. Trade-offs

### Advantages

Managed availability giảm operational burden và node-level failure impact.

### Costs / Risks

Transient errors vẫn tồn tại; cross-region options tăng cost/latency; retry sai gây duplicate effects.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu failover có thể làm connection hiện tại mất.

### Middle

Cấu hình retry và logging đúng.

### Senior

Phân biệt transient failure với ambiguous transaction outcome.

### Technical Lead / Architect

Chọn availability topology, RTO/RPO, region strategy và idempotency boundary theo business requirement/cost.

## 11. Key takeaway

- HA không loại bỏ transient failures khỏi application.
- Retry write command cần idempotency/transaction reasoning.
- Đo retry/failover behavior bằng production telemetry và drills.

# 8. Kubernetes graceful termination: `SIGTERM`, readiness và request draining

## 1. What is it?

Khi Pod bị terminate, Kubernetes bắt đầu shutdown lifecycle: endpoint cần ngừng nhận traffic, process nhận termination signal và có grace period để hoàn tất work trước khi bị kill.

## 2. Why does it exist?

Rolling deployment, autoscaling và node maintenance đều terminate Pods bình thường. Nếu application shutdown như crash, in-flight requests/messages bị cắt và tạo 5xx hoặc duplicate processing.

## 3. How does it work?

Pod chuyển termination; kubelet chạy lifecycle hooks nếu có, gửi `SIGTERM`, chờ `terminationGracePeriodSeconds`, rồi `SIGKILL` nếu process chưa thoát. Endpoint removal/load-balancer propagation có race, nên readiness/draining phải được thiết kế cùng application shutdown.

## 4. Practical implementation

ASP.NET Core hosted services phải tôn trọng cancellation:

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    await foreach (var item in queue.ReadAllAsync(stoppingToken))
        await ProcessAsync(item, stoppingToken);
}
```

Kubernetes manifest cần grace period phù hợp worst-case legitimate request/work unit, không tùy tiện rất dài.

## 5. Real production scenario

Deployment rollout thay 10 API Pods. Nếu old Pods bị terminate trong khi load balancer vẫn gửi requests vài giây, user thấy burst 502/connection resets dù readiness mới đều xanh.

## 6. Failure scenario & troubleshooting

**Symptom** → 5xx spike đúng lúc deploy. **Evidence** → Pod termination timestamps correlate với failed requests. **Hypothesis** → draining chưa đủ. **Diagnosis** → inspect readiness transition, ingress endpoint propagation, shutdown duration. **Fix** → graceful shutdown/readiness sequencing và grace period phù hợp. **Verification** → repeated rollout không tăng error rate.

## 7. Common mistakes

Dùng liveness để báo dependency outage; background consumer không honor cancellation; grace period ngắn hơn request timeout; `preStop sleep` như fix duy nhất mà không hiểu traffic flow.

## 8. Alternatives

App Service/IIS cũng có graceful recycle concepts nhưng lifecycle khác. Nếu workload không cần Kubernetes, managed App Service/Container Apps có thể giảm operational complexity.

## 9. Trade-offs

### Advantages

Giảm deploy-induced errors và partial work.

### Costs / Risks

Shutdown chậm kéo rollout; long-running tasks cần checkpoint/idempotency thay vì chỉ tăng grace period.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Pod termination khác process crash.

### Middle

Implement cancellation và readiness đúng.

### Senior

Điều tra ingress propagation, in-flight requests và consumer semantics.

### Technical Lead / Architect

Chọn hosting/deployment model có operational complexity phù hợp; định nghĩa shutdown SLO và work-unit boundaries.

## 11. Key takeaway

- Graceful termination là phối hợp orchestrator, network và application.
- Cancellation phải đi tới I/O/work đang chạy.
- Long work cần resumability/idempotency, không chỉ grace period lớn.

# 9. `dotnet-counters` + allocation profiling: điều tra GC pressure theo evidence

## 1. What is it?

GC pressure xảy ra khi application allocate nhanh hoặc giữ objects lâu khiến GC phải chạy thường xuyên/tốn CPU. `dotnet-counters` cho live runtime signals; allocation profiler/dump giúp xác định types/call paths tạo pressure.

## 2. Why does it exist?

Memory cao không tự động nghĩa memory leak. Một service có thể giữ working set ổn nhưng allocation rate cực lớn, gây frequent GC và p99 latency spikes.

## 3. How does it work?

Bắt đầu bằng symptom → counters: allocation rate, GC heap size, Gen 0/1/2 collections, `% Time in GC`, CPU. Sau đó profile allocation để localize hot path; hình thành hypothesis; thay đổi; load test lại cùng workload.

## 4. Practical implementation

```bash
dotnet-counters monitor --process-id <pid> System.Runtime
```

Sau khi thấy allocation rate bất thường, dùng profiler/dotnet-trace phù hợp để tìm allocation stacks. Ví dụ thường gặp: JSON intermediate objects, LINQ materialization, large strings, repeated buffers.

## 5. Real production scenario

API p99 tăng mỗi vài giây trong khi SQL/HTTP dependencies bình thường. Counters cho Gen 2 collections tăng và allocation rate cao. Profile chỉ ra endpoint export tạo nhiều large strings trước khi ghi response.

## 6. Failure scenario & troubleshooting

**Symptom** → latency spikes + CPU sawtooth. **Measure** → runtime counters. **Localize** → GC/allocation. **Hypothesis** → response construction allocate quá nhiều. **Test** → streaming/buffer reuse ở isolated benchmark. **Change** → giảm materialization. **Measure again** → allocation rate, GC pauses và p99 giảm.

## 7. Common mistakes

Thấy memory cao rồi gọi `GC.Collect`; tối ưu micro-allocation không nằm hot path; chỉ nhìn heap size; dùng object pooling cho objects rẻ khiến ownership phức tạp; benchmark khác production workload.

## 8. Alternatives

`dotnet-dump` tốt cho retained objects/leak investigation. CPU profiler tốt nếu CPU-bound. BenchmarkDotNet tốt cho isolated code nhưng không thay production telemetry/load test.

## 9. Trade-offs

### Advantages

Evidence-driven, phân biệt allocation churn với retention/leak.

### Costs / Risks

Profiling có overhead; optimization như pooling/Span có thể tăng complexity đáng kể.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu allocation và GC collections.

### Middle

Đọc runtime counters và reproduce dưới load.

### Senior

Kết nối allocation stack với latency percentiles và GC modes.

### Technical Lead / Architect

Đặt performance budget; chỉ chấp nhận complexity optimization khi evidence và SLO justify.

## 11. Key takeaway

- Memory size và allocation rate là hai tín hiệu khác nhau.
- Điều tra theo measure → localize → hypothesis → change → measure lại.
- Không dùng pooling/low-level APIs nếu bottleneck chưa được chứng minh.

# 10. Contract testing cho third-party API: bảo vệ integration trước schema drift

## 1. What is it?

Contract testing kiểm tra assumptions giữa application và remote API: endpoint, authentication, required fields, status/error semantics và schema. Mục tiêu là phát hiện contract drift trước khi production integration vỡ.

## 2. Why does it exist?

Third-party provider có deployment lifecycle riêng. Generated SDK hoặc compile-time types không đảm bảo provider production vẫn trả contract mà code kỳ vọng.

## 3. How does it work?

Application giữ explicit adapter boundary. Tests xác minh mapping với representative payloads; nếu provider có sandbox/schema/OpenAPI đáng tin cậy, scheduled/integration verification kiểm tra compatibility. Business layer không phụ thuộc trực tiếp provider DTO.

## 4. Practical implementation

```csharp
public sealed record ProviderCustomer(string Id, string? DisplayName);

public sealed class CustomerGateway(HttpClient client)
{
    public async Task<ProviderCustomer> GetAsync(string id, CancellationToken ct)
    {
        using var response = await client.GetAsync($"customers/{id}", ct);
        response.EnsureSuccessStatusCode();
        return (await response.Content.ReadFromJsonAsync<ProviderCustomer>(cancellationToken: ct))!;
    }
}
```

Test payloads nên gồm missing optional fields, unknown fields, error bodies và enum values mới.

## 5. Real production scenario

Review provider đổi field `rating` từ luôn có sang nullable khi chưa đủ reviews. Application deserialize được nhưng business mapping dùng `.Value`, gây 500 trên product pages mới.

## 6. Failure scenario & troubleshooting

**Symptom** → error rate tăng chỉ với một provider. **Evidence** → dependency success nhưng deserialization/mapping exceptions tăng. **Hypothesis** → schema drift. **Diagnosis** → capture sanitized payload/schema diff. **Fix** → tolerant reader/adapter update; fallback nếu business cho phép. **Verification** → contract suite + production canary metrics.

## 7. Common mistakes

Mock provider hoàn toàn nên tests chỉ xác nhận assumptions của chính mình; expose provider DTO xuyên domain; retry schema errors; log secrets/full PII payloads; không version adapter behavior.

## 8. Alternatives

Consumer-driven contract testing mạnh khi cả hai teams phối hợp. Sandbox smoke tests kiểm tra provider thật nhưng có reliability/rate-limit concerns. Schema validation offline rẻ hơn nhưng không kiểm tra runtime behavior.

## 9. Trade-offs

### Advantages

Phát hiện breaking changes sớm, cô lập provider model và giảm production surprises.

### Costs / Risks

Provider sandbox có thể khác production; test maintenance tăng; không thể chứng minh mọi behavioral contract.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external JSON là untrusted contract boundary.

### Middle

Test serialization, status codes và adapter mapping.

### Senior

Thiết kế tolerant parsing, timeout/fallback, observability và schema-drift handling.

### Technical Lead / Architect

Định nghĩa anti-corruption boundary, provider SLO/degradation strategy và mức contract verification đáng chi phí.

## 11. Key takeaway

- Mock-only tests không chứng minh provider contract vẫn đúng.
- Third-party DTO không nên trở thành domain model.
- Schema drift cần adapter boundary, telemetry và verification strategy.
