# 1. C# `IAsyncDisposable`: giải phóng resource khi cleanup bản thân cũng là I/O

## 1. What is it?

`IAsyncDisposable` cung cấp `DisposeAsync()` cho resource có bước cleanup cần chờ asynchronous work. Mental model: `IDisposable` phù hợp cleanup đồng bộ; `IAsyncDisposable` phù hợp khi đóng/flush resource cần I/O và việc block thread để chờ cleanup là không hợp lý.

## 2. Why does it exist?

Một resource như asynchronous stream, transaction wrapper hoặc network writer có thể cần flush dữ liệu trước khi đóng. Nếu cleanup dùng `.Wait()` hoặc `.Result`, application có thể block ThreadPool và tăng tail latency.

## 3. How does it work?

`await using` tạo `try/finally` về mặt semantics; cuối scope runtime gọi `DisposeAsync()` và await completion trước khi tiếp tục.

```text
Acquire resource -> use asynchronously -> DisposeAsync -> await cleanup -> leave scope
```

## 4. Practical implementation

```csharp
await using var stream = new FileStream(
    path, FileMode.Create, FileAccess.Write, FileShare.None,
    bufferSize: 64 * 1024, useAsync: true);

await JsonSerializer.SerializeAsync(stream, payload, cancellationToken: ct);
await stream.FlushAsync(ct);
```

Nếu tự xây type sở hữu async-disposable dependency, propagate disposal thay vì chỉ bỏ reference.

## 5. Real production scenario

Background worker xuất file lớn lên storage. Sau khi serialize, stream còn buffered data. Scope chỉ được coi là hoàn thành sau khi flush/close đúng cách; shutdown giữa chừng phải phối hợp với `CancellationToken` và cleanup.

## 6. Failure scenario & troubleshooting

**Symptom** → memory/file handles tăng dần hoặc shutdown kéo dài. **Evidence** → profiler cho thấy resource không được dispose; logs thiếu completion của cleanup. **Diagnosis** → object async-disposable được tạo nhưng dùng `using` sai contract hoặc không dispose. **Fix** → `await using`, ownership rõ ràng và bounded shutdown timeout. **Verification** → soak test cho thấy handle count ổn định.

## 7. Common mistakes

Implement cả hai interfaces nhưng semantics mâu thuẫn; sync-over-async trong `Dispose`; swallow cleanup exception; dispose object không thuộc ownership; giữ resource quá lâu.

## 8. Alternatives

`IDisposable` đơn giản hơn nếu cleanup hoàn toàn local/synchronous. Factory callback có thể quản lý lifetime tập trung. Không nên thêm async disposal chỉ vì method khác trong class là async.

## 9. Trade-offs

### Advantages

Không block thread khi cleanup cần I/O; lifetime rõ ràng qua `await using`.

### Costs / Risks

Control flow phức tạp hơn, shutdown có thể kéo dài, exception trong cleanup cần policy rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu resource lifetime và khác biệt `using`/`await using`.

### Middle

Implement và consume `IAsyncDisposable` đúng ownership.

### Senior

Phân tích shutdown, cancellation, exception và resource leak.

### Technical Lead / Architect

Quyết định boundary nào sở hữu resource và cleanup latency có ảnh hưởng lifecycle toàn service hay không.

## 11. Key takeaway

- Async method không tự động cần async disposal.
- Cleanup có I/O mới là lý do chính cho `IAsyncDisposable`.
- Resource ownership phải rõ trước khi nói về disposal syntax.

# 2. ASP.NET Core `ProblemDetails`: biến lỗi API thành contract ổn định thay vì leak exception

## 1. What is it?

`ProblemDetails` là representation chuẩn hóa cho HTTP API errors với các field như `type`, `title`, `status`, `detail`, `instance` và extensions. Nó tách internal exception model khỏi public API error contract.

## 2. Why does it exist?

Nếu mỗi endpoint trả lỗi theo một shape khác nhau, frontend và integrations phải viết logic đặc biệt. Trả raw exception còn leak stack trace, SQL, path hoặc implementation detail.

## 3. How does it work?

```text
Exception / validation failure
        -> centralized handler
        -> map to public error category
        -> ProblemDetails + HTTP status
        -> correlation identifier
```

Internal logs giữ exception đầy đủ; response chỉ chứa thông tin client cần.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();
var app = builder.Build();

app.UseExceptionHandler();

app.MapGet("/orders/{id:int}", async (int id, AppDbContext db, CancellationToken ct) =>
{
    var order = await db.Orders.FindAsync([id], ct);
    return order is null
        ? Results.Problem(statusCode: 404, title: "Order not found")
        : Results.Ok(order);
});
```

Domain exceptions nên được map tập trung sang status/error code ổn định.

## 5. Real production scenario

Vue frontend gọi Order API. Validation, authorization và business conflict đều trả cùng envelope semantics, cho phép UI hiển thị message phù hợp và telemetry correlate bằng request ID.

## 6. Failure scenario & troubleshooting

**Symptom** → Production response chứa connection string trong `detail`. **Evidence** → handler copy `exception.Message`. **Diagnosis** → internal diagnostic data bị dùng làm public contract. **Fix** → map exception sang safe error code/title; log full exception server-side. **Verification** → security integration tests kiểm tra response không chứa stack trace/secrets.

## 7. Common mistakes

Luôn trả HTTP 200 kèm `success=false`; expose exception message; tạo error shape riêng cho từng controller; đổi error code tùy tiện; thiếu correlation ID.

## 8. Alternatives

Custom error envelope hợp khi organization đã có contract lâu dài. gRPC dùng status/details khác. Quan trọng là consistency và separation giữa diagnostic detail với client contract.

## 9. Trade-offs

### Advantages

Client handling nhất quán, observability tốt hơn, giảm information leakage.

### Costs / Risks

Cần taxonomy/error mapping governance và backward compatibility cho error codes.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt HTTP status với exception.

### Middle

Map validation/not-found/conflict thành response đúng semantics.

### Senior

Thiết kế safe diagnostics, correlation và compatibility.

### Technical Lead / Architect

Định nghĩa organization-wide error contract đủ ổn định nhưng không biến mọi domain error thành shared coupling.

## 11. Key takeaway

- Exception là implementation detail; API error là contract.
- Client cần actionable error, không cần stack trace.
- Error contracts cũng cần versioning discipline.

# 3. EF Core optimistic concurrency: phát hiện lost update bằng concurrency token

## 1. What is it?

Optimistic concurrency cho phép nhiều request đọc cùng entity nhưng phát hiện khi một request update trên dữ liệu đã bị request khác thay đổi. EF Core thực hiện bằng concurrency token như SQL Server `rowversion` hoặc application-managed version.

## 2. Why does it exist?

Flow read-modify-write kéo dài qua HTTP request không thể giữ database lock suốt thời gian user chỉnh form. Nếu không phát hiện version thay đổi, người lưu sau có thể âm thầm ghi đè người lưu trước.

## 3. How does it work?

EF Core đưa original concurrency token vào `WHERE` của `UPDATE`.

```sql
UPDATE Orders
SET Status = @status
WHERE Id = @id AND RowVersion = @originalVersion;
```

Affected rows = 0 nghĩa là entity đã thay đổi/xóa; EF Core ném `DbUpdateConcurrencyException`.

## 4. Practical implementation

```csharp
public sealed class Order
{
    public int Id { get; set; }
    public string Status { get; set; } = default!;

    [Timestamp]
    public byte[] RowVersion { get; set; } = default!;
}

try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new { code = "order_changed" });
}
```

API phải round-trip version từ read response sang update command.

## 5. Real production scenario

Hai managers mở cùng approval request. A approves; B vẫn nhìn state cũ và reject. Concurrency token ngăn B ghi đè im lặng; UI có thể reload và yêu cầu quyết định lại trên state mới.

## 6. Failure scenario & troubleshooting

**Symptom** → `DbUpdateConcurrencyException` tăng sau rollout. **Evidence** → nhiều users update cùng aggregate hoặc version mapping sai. **Diagnosis** → phân biệt contention hợp lệ với bug DTO không round-trip token. **Fix** → conflict UX, retry chỉ khi operation thật sự merge-safe. **Verification** → integration test hai contexts update cùng row.

## 7. Common mistakes

Catch rồi retry vô hạn; không trả token cho client; dùng last-write-wins cho dữ liệu nhạy cảm; coi concurrency exception là infrastructure outage; token quá rộng khiến thay đổi không liên quan cũng conflict.

## 8. Alternatives

Pessimistic locking phù hợp critical short transaction nhưng tăng blocking/deadlock risk. Domain-specific compare-and-set có thể rõ hơn cho state transition. Event sourcing có concurrency trên stream version nhưng complexity cao hơn.

## 9. Trade-offs

### Advantages

Không giữ long-lived locks, phát hiện lost update, phù hợp stateless HTTP.

### Costs / Risks

Conflict phải được giải quyết ở application/UX; retry không phải lúc nào đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hai users có thể sửa cùng dữ liệu.

### Middle

Map concurrency token và xử lý conflict.

### Senior

Phân biệt retry-safe với business conflict cần user decision.

### Technical Lead / Architect

Chọn consistency policy theo invariant và user workflow, không áp một chiến lược cho mọi table.

## 11. Key takeaway

- Optimistic concurrency phát hiện conflict; nó không tự giải quyết conflict.
- Blind retry có thể tái tạo lost update ở tầng business.
- Version phải đi xuyên API contract nếu update dựa trên state đã đọc.

# 4. Redis hot key: một key nổi tiếng có thể phá scalability của distributed cache

## 1. What is it?

Hot key là cache key nhận lượng traffic bất cân xứng so với phần còn lại. Dù Redis cluster có nhiều nodes, một key cụ thể thường thuộc một shard; tải của key đó không tự phân tán theo số nodes.

## 2. Why does it exist?

Caching thường được thêm để giảm database load, nhưng access pattern skewed có thể biến Redis thành bottleneck mới. Một homepage configuration hoặc viral product có thể nhận hàng chục nghìn reads/second trên cùng key.

## 3. How does it work?

```text
10,000 clients -> GET product:42 -> one hash slot -> one Redis shard
```

Scale cluster không giúp nhiều nếu traffic vẫn hội tụ vào một slot.

## 4. Practical implementation

Với dữ liệu cho phép stale ngắn, thêm local L1 cache trước Redis:

```csharp
if (memoryCache.TryGetValue(key, out ProductDto? value))
    return value;

value = await redisCache.GetAsync<ProductDto>(key, ct);
if (value is not null)
    memoryCache.Set(key, value, TimeSpan.FromSeconds(5));

return value;
```

TTL ngắn ở L1 có thể cắt mạnh read pressure nhưng cần chấp nhận freshness window.

## 5. Real production scenario

E-commerce campaign đẩy một SKU lên homepage. Database ổn nhưng Redis node CPU/network tăng 95%, p99 của mọi keys cùng shard tăng theo.

## 6. Failure scenario & troubleshooting

**Symptom** → cache hit rate cao nhưng latency vẫn tăng. **Evidence** → per-key traffic cho thấy một key áp đảo; một shard CPU/network cao. **Diagnosis** → hot key. **Fix** → L1 cache, request coalescing, precomputed response hoặc key replication có kiểm soát. **Verification** → load test theo realistic skew, không chỉ uniform keys.

## 7. Common mistakes

Chỉ nhìn global hit rate; tăng cluster nodes mà không xem slot distribution; randomize keys làm invalidation khó; cache object cực lớn; không đặt memory budget cho L1.

## 8. Alternatives

CDN phù hợp public HTTP responses; `IMemoryCache` phù hợp per-instance data nhỏ; application-level precomputation phù hợp derived data. Có lúc không cache và query database đã tối ưu lại đơn giản hơn.

## 9. Trade-offs

### Advantages

Redis giảm DB load và chia sẻ cache xuyên instances.

### Costs / Risks

Hot keys, stale data, network dependency, eviction và operational burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache hit cao không đồng nghĩa cache khỏe.

### Middle

Đo per-key latency/traffic và thiết kế TTL.

### Senior

Phân tích skew, shard saturation, fallback và stampede.

### Technical Lead / Architect

Quyết định dữ liệu nên cache ở browser/CDN/L1/Redis hay không cache, dựa trên consistency và load shape.

## 11. Key takeaway

- Distributed cache không tự phân tán một hot key.
- Load distribution quan trọng hơn average hit rate.
- Multi-level caching chỉ hợp khi freshness contract rõ.

# 5. Circuit Breaker: ngăn dependency failure lan thành retry storm

## 1. What is it?

Circuit Breaker tạm ngừng gọi một dependency đang có failure rate cao, fail fast trong một khoảng thời gian rồi cho một số probe kiểm tra recovery. Nó bảo vệ caller khỏi tiêu tốn threads/connections/timeouts vào dependency đang hỏng.

## 2. Why does it exist?

Timeout 10 giây nhân hàng nghìn requests có thể làm caller cạn connection/ThreadPool trước cả dependency. Retry còn khuếch đại traffic đúng lúc downstream yếu nhất.

## 3. How does it work?

```text
Closed --failures exceed threshold--> Open
Open --break duration--> Half-Open
Half-Open --probe succeeds--> Closed
Half-Open --probe fails--> Open
```

Circuit state phải dựa trên meaningful failures, không phải mọi HTTP status.

## 4. Practical implementation

```csharp
builder.Services.AddHttpClient<ReviewClient>()
    .AddStandardResilienceHandler(options =>
    {
        options.AttemptTimeout.Timeout = TimeSpan.FromSeconds(2);
        options.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(30);
        options.CircuitBreaker.BreakDuration = TimeSpan.FromSeconds(15);
    });
```

Policy phải phối hợp timeout, retry và circuit breaker; không stack retries tùy tiện ở nhiều layers.

## 5. Real production scenario

Product page gọi Reviews API. Reviews down không nên kéo toàn product page down. Circuit mở, application trả product data cùng trạng thái “reviews temporarily unavailable”.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency đã recover nhưng traffic vẫn thất bại lâu. **Evidence** → circuit open duration quá dài hoặc probe bị policy khác chặn. **Diagnosis** → resilience policies tương tác sai. **Fix** → tune threshold/window từ telemetry, xác định fallback rõ. **Verification** → chaos test dependency fail/recover và đo recovery time.

## 7. Common mistakes

Circuit breaker thay cho timeout; retry cả non-transient 4xx; fallback dữ liệu sai business; mỗi layer retry riêng tạo multiplicative attempts; không emit metrics về circuit state.

## 8. Alternatives

Fail fast đơn giản đủ cho dependency không critical. Queue phù hợp work có thể asynchronous. Bulkhead giới hạn concurrency nhưng giải quyết vấn đề khác; thường bổ sung chứ không thay circuit breaker.

## 9. Trade-offs

### Advantages

Giảm failure amplification, bảo vệ resources, recovery có kiểm soát.

### Costs / Risks

Có thể reject requests khi dependency vừa recover; tuning và fallback semantics tăng complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry không luôn tốt.

### Middle

Cấu hình timeout/retry/circuit breaker và logging.

### Senior

Phân loại transient failures, đo failure amplification và recovery.

### Technical Lead / Architect

Xác định dependency nào có thể degrade, dependency nào bắt buộc fail request, và resilience budget xuyên call chain.

## 11. Key takeaway

- Circuit Breaker bảo vệ caller, không sửa downstream.
- Retry và breaker phải được thiết kế cùng nhau.
- Fallback chỉ đúng nếu business chấp nhận degraded result.

# 6. Azure Service Bus dead-letter queue: quarantine failure thay vì retry vô hạn

## 1. What is it?

Dead-letter queue (DLQ) giữ messages không thể xử lý bình thường sau policy nhất định. Nó tách poison messages khỏi main queue để consumer tiếp tục xử lý traffic khỏe.

## 2. Why does it exist?

Một message luôn throw nếu được retry vô hạn sẽ chiếm compute, tăng delivery count, noise và backlog. Xóa message lại mất evidence/business work. DLQ tạo nơi quarantine có thể quan sát và xử lý có chủ đích.

## 3. How does it work?

```text
Queue -> Consumer
          ├─ success -> Complete
          ├─ transient -> Abandon/retry
          └─ poison / max delivery -> DLQ
                                      -> inspect/fix/replay
```

Service Bus sử dụng at-least-once semantics; replay vẫn đòi hỏi idempotent consumer.

## 4. Practical implementation

```csharp
try
{
    await handler.ProcessAsync(message, ct);
    await args.CompleteMessageAsync(message, ct);
}
catch (InvalidMessageSchemaException ex)
{
    await args.DeadLetterMessageAsync(
        message,
        deadLetterReason: "InvalidSchema",
        deadLetterErrorDescription: ex.Message,
        cancellationToken: ct);
}
```

Không đưa sensitive payload vào error description nếu telemetry/operators không cần.

## 5. Real production scenario

Order event từ producer cũ thiếu field bắt buộc sau schema migration. Consumer dead-letter với reason cụ thể; alert tăng; team xác định producer version và quyết định transform/replay.

## 6. Failure scenario & troubleshooting

**Symptom** → main queue ổn nhưng DLQ tăng liên tục. **Evidence** → reason tập trung vào deserialization. **Hypothesis** → contract incompatibility. **Diagnosis** → correlate producer version/deployment với first failure. **Fix** → backward-compatible consumer hoặc producer rollback; replay sau fix. **Verification** → DLQ drain có kiểm soát và không tạo duplicate side effects.

## 7. Common mistakes

Không monitor DLQ; auto-replay vô hạn; dead-letter mọi transient timeout; sửa payload thủ công không audit; consumer không idempotent; không lưu reason/correlation.

## 8. Alternatives

Retry queue với delayed backoff phù hợp transient failures. Quarantine database có thể cần khi business workflow yêu cầu richer operations. DLQ vẫn là native failure boundary tốt cho Service Bus.

## 9. Trade-offs

### Advantages

Giữ main queue tiến lên, bảo tồn failed work, hỗ trợ diagnosis/replay.

### Costs / Risks

DLQ trở thành “nghĩa địa” nếu không có ownership, alert và remediation runbook.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt retryable failure và poison message.

### Middle

Settle/dead-letter message đúng semantics.

### Senior

Thiết kế replay, idempotency, schema compatibility và alerting.

### Technical Lead / Architect

Định nghĩa ownership/SLO của DLQ và quy trình recovery như một phần architecture, không phải việc vận hành phụ.

## 11. Key takeaway

- DLQ không phải nơi “ném lỗi rồi quên”.
- Replay phải an toàn với duplicate delivery.
- DLQ growth là production signal cần owner.

# 7. Blue-Green deployment: zero-downtime chỉ đúng khi database và contract tương thích

## 1. What is it?

Blue-Green duy trì hai production-capable environments: Blue đang phục vụ traffic, Green chạy version mới. Sau validation, router chuyển traffic sang Green; Blue giữ làm rollback target trong khoảng thời gian xác định.

## 2. Why does it exist?

In-place deployment có thể tạo downtime và rollback chậm. Blue-Green tách “deploy bits” khỏi “expose traffic”, cho phép smoke test version mới trước cutover.

## 3. How does it work?

```text
             ┌-> Blue v1
Client -> Router
             └-> Green v2

Deploy v2 -> health/smoke -> switch traffic -> observe -> retire Blue
```

Database thường vẫn shared; đây là nơi “zero downtime” dễ vỡ nhất.

## 4. Practical implementation

Migration theo Expand/Contract:

```sql
-- Expand: safe while v1 and v2 coexist
ALTER TABLE Customers ADD PreferredName nvarchar(200) NULL;

-- Deploy v2 and backfill separately.
-- Contract/drop old column only after v1 can no longer receive traffic.
```

## 5. Real production scenario

App Service slots đóng vai Blue/Green. Green v2 được warm up và health-check. Traffic swap chỉ xảy ra sau smoke tests; old slot vẫn chạy để rollback nếu error rate tăng.

## 6. Failure scenario & troubleshooting

**Symptom** → rollback application thành công nhưng v1 crash với schema mới. **Evidence** → migration đã rename/drop column trước cutover. **Diagnosis** → deployment artifact rollbackable nhưng database không backward-compatible. **Fix** → Expand/Contract, decouple destructive migration. **Verification** → chạy compatibility tests với v1 và v2 trên expanded schema.

## 7. Common mistakes

Gọi deployment là zero-downtime nhưng không warm cache; destructive migration cùng release; sessions chỉ nằm memory; health check quá nông; rollback chưa được test.

## 8. Alternatives

Rolling deployment dùng ít duplicate capacity hơn. Canary giảm blast radius bằng gradual traffic. Feature flags tách code deployment khỏi feature release. Chọn theo risk/cost chứ không theo tên pattern.

## 9. Trade-offs

### Advantages

Cutover nhanh, rollback application nhanh, pre-production validation trên environment gần production.

### Costs / Risks

Double environment cost, shared-state compatibility, cache/session concerns và operational orchestration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy và release là hai bước khác nhau.

### Middle

Build health/smoke checks và rollback procedure.

### Senior

Thiết kế backward-compatible DB/API changes.

### Technical Lead / Architect

Quyết định strategy theo blast radius, state, capacity cost và recovery objective; “zero downtime” phải được chứng minh end-to-end.

## 11. Key takeaway

- Blue-Green không làm database tự rollbackable.
- Compatibility window là điều kiện cốt lõi.
- Health validation và rollback rehearsal quan trọng như deployment automation.

# 8. OpenTelemetry distributed tracing: tìm latency xuyên nhiều dependency bằng context propagation

## 1. What is it?

Distributed tracing biểu diễn một request end-to-end thành trace gồm nhiều spans. OpenTelemetry chuẩn hóa instrumentation và propagation để HTTP request, SQL call, messaging và external dependency có thể được nối vào cùng causal chain.

## 2. Why does it exist?

Trong distributed system, log “request took 4s” không cho biết 4s nằm ở API, SQL, Redis hay downstream. Correlation ID giúp tìm logs; trace còn mô tả timing và parent-child relationship.

## 3. How does it work?

```text
Trace
└─ API span 1200ms
   ├─ SQL span 40ms
   ├─ Redis span 5ms
   └─ Reviews HTTP span 1100ms
```

W3C trace context được propagate qua headers/message metadata. Sampling quyết định trace nào được export.

## 4. Practical implementation

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddSource("Orders.Application"));

private static readonly ActivitySource Source = new("Orders.Application");

using var activity = Source.StartActivity("ApproveOrder");
activity?.SetTag("order.operation", "approve");
```

Không đưa PII/high-cardinality payload tùy tiện vào tags.

## 5. Real production scenario

API p95 tăng từ 300ms lên 1.8s. Trace cho thấy SQL vẫn 40ms nhưng external Reviews API chiếm 1.4s. Team sửa timeout/fallback đúng dependency thay vì “optimize database” theo phỏng đoán.

## 6. Failure scenario & troubleshooting

**Symptom** → trace bị chia thành nhiều roots. **Evidence** → downstream span có trace ID khác. **Hypothesis** → context propagation bị mất qua queue/custom client. **Diagnosis** → kiểm tra headers/message properties và instrumentation. **Fix** → inject/extract context đúng chuẩn. **Verification** → test request xuyên HTTP + messaging hiển thị một causal trace.

## 7. Common mistakes

Sample 100% ở scale lớn; tag user IDs/payload nhạy cảm; coi trace thay thế metrics/logs; custom spans quá chi tiết; không propagate qua background messages.

## 8. Alternatives

Structured logs tốt cho event detail; metrics tốt cho aggregate trends/alerts. Application Insights có auto-instrumentation trong Azure. Thực tế Logs + Metrics + Traces bổ sung nhau.

## 9. Trade-offs

### Advantages

Localize latency/failure xuyên services, hiểu dependency chain và critical path.

### Costs / Risks

Telemetry cost, sampling loss, cardinality/privacy risk và instrumentation overhead.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace/span và correlation.

### Middle

Instrument HTTP/SQL/custom operations.

### Senior

Thiết kế sampling, attributes, propagation và incident workflow.

### Technical Lead / Architect

Đặt observability conventions/SLOs đủ nhất quán xuyên teams mà không tạo telemetry bill không kiểm soát.

## 11. Key takeaway

- Trace trả lời “thời gian đi đâu” tốt hơn một log đơn lẻ.
- Context propagation là nền tảng của distributed tracing.
- Traces không thay metrics và logs.

# 9. Optimizely CMS content modeling: thiết kế theo editorial intent thay vì page layout hiện tại

## 1. What is it?

Content modeling định nghĩa semantic content types, properties, blocks và relationships mà editors quản lý. Trong Optimizely CMS, model tốt phản ánh ý nghĩa nội dung và reuse boundary, không chỉ mirror HTML sections của một thiết kế Figma hiện tại.

## 2. Why does it exist?

Nếu content type được đặt tên `LeftColumnBlock`, redesign sang mobile/card layout khiến model trở nên vô nghĩa. Nếu model quá generic, editor lại không biết field dùng để làm gì. Cần cân bằng semantic intent, validation và presentation flexibility.

## 3. How does it work?

```text
Editorial intent
   -> Content Type
      -> validated properties
      -> reusable Blocks where ownership makes sense
   -> Rendering component
   -> CDN/cache/browser
```

Content model là contract giữa editors, application và delivery layer.

## 4. Practical implementation

```csharp
[ContentType(DisplayName = "Promotion Card", GUID = "11111111-2222-3333-4444-555555555555")]
public class PromotionCardBlock : BlockData
{
    [Display(Name = "Heading", Order = 10)]
    public virtual string Heading { get; set; } = string.Empty;

    [Display(Name = "Destination", Order = 20)]
    public virtual Url? Destination { get; set; }
}
```

Tên type/property mô tả business/editorial meaning; CSS layout thuộc rendering layer.

## 5. Real production scenario

Marketing cần cùng promotion card ở homepage, category page và campaign landing page. Reusable block hợp lý nếu lifecycle/reuse thật sự chung; nếu content chỉ có nghĩa trong một parent aggregate, embedded/local block có thể đơn giản hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → redesign yêu cầu migration hàng nghìn content items. **Evidence** → properties tên theo layout cũ (`DesktopLeftImage`, `RightText`). **Diagnosis** → presentation bị đóng cứng vào content schema. **Fix** → semantic model + rendering variants; migration có version/backward compatibility. **Verification** → render cùng content qua layouts mới mà không sửa editorial data không cần thiết.

## 7. Common mistakes

Một mega-block với hàng chục nullable fields; block hóa mọi thứ; hard-code layout vào schema; không validate required/editor constraints; đổi property/GUID phá persisted content; quên cache invalidation khi publish.

## 8. Alternatives

Headless CMS tách delivery mạnh hơn nhưng không tự sửa model xấu. Hard-coded application content đơn giản hơn cho nội dung không cần editorial workflow. Composable architecture chỉ đáng giá nếu organizational needs biện minh integration cost.

## 9. Trade-offs

### Advantages

Semantic model tăng reuse, editor clarity và khả năng redesign.

### Costs / Risks

Abstraction quá generic làm editing khó; reusable content tăng dependency/caching complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt content data với rendering layout.

### Middle

Tạo content types/blocks có validation và editor-friendly naming.

### Senior

Thiết kế reuse boundary, migration, caching và backward compatibility.

### Technical Lead / Architect

Quyết định traditional/headless/composable boundary dựa trên editorial workflow, delivery channels và operational cost.

## 11. Key takeaway

- Model editorial meaning, không model pixel layout.
- Reuse chỉ có giá trị khi lifecycle/ownership thực sự phù hợp.
- CMS schema là persisted contract cần migration discipline.

# 10. Git `bisect`: biến regression investigation từ đoán commit thành binary search

## 1. What is it?

`git bisect` tìm commit đầu tiên gây regression bằng binary search giữa một commit known-good và một commit known-bad. Thay vì kiểm tra tuần tự hàng trăm commits, mỗi bước loại khoảng một nửa search space.

## 2. Why does it exist?

Production regression thường xuất hiện sau nhiều merges. Đọc diff lớn hoặc đoán “commit đáng ngờ” dễ bias và tốn thời gian. Nếu có deterministic test, commit history trở thành searchable evidence.

## 3. How does it work?

```text
Good ------------------------------ Bad
                 ^ test midpoint
Good ------------ Bad
          ^ test midpoint
...
first bad commit
```

Với 1,024 commits, lý tưởng chỉ cần khoảng 10 evaluations.

## 4. Practical implementation

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0

# At each checked-out commit:
dotnet test tests/Regression.Tests
# then mark:
git bisect good   # or git bisect bad

# Finish:
git bisect reset
```

Có thể automate bằng `git bisect run` nếu script trả exit code đáng tin cậy.

## 5. Real production scenario

Memory usage tăng sau hai tuần development với 180 commits. Team tạo regression test/benchmark tái hiện leak, rồi bisect để tìm commit thay đổi caching lifetime thay vì review thủ công toàn bộ history.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit không liên quan hoặc kết quả thay đổi mỗi run. **Evidence** → test flaky hoặc historical commits không build vì external dependency. **Diagnosis** → oracle “good/bad” không deterministic. **Fix** → stabilize reproduction, pin dependencies, dùng `git bisect skip` cho commits không test được. **Verification** → checkout candidate parent/candidate và reproduce boundary nhiều lần.

## 7. Common mistakes

Bisect trước khi có reliable reproduction; chọn good commit thực ra đã lỗi; dùng manual subjective testing; quên submodules/config; coi first bad commit là root cause mà không đọc diff/context.

## 8. Alternatives

`git log`, `git blame` và PR search tốt khi biết file/line. APM deployment markers có thể thu hẹp window trước. Bisect mạnh nhất khi regression có binary/deterministic signal.

## 9. Trade-offs

### Advantages

Giảm search space nhanh, evidence-driven, automate được.

### Costs / Risks

Historical builds có thể khó chạy; flaky tests làm thuật toán mất giá trị; merge-heavy history cần interpretation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết tạo good/bad boundary và reset bisect.

### Middle

Viết deterministic regression test để automate search.

### Senior

Kết hợp telemetry/deployment history để thu hẹp range và xác minh root cause.

### Technical Lead / Architect

Xây release/observability/test discipline để regression có thể truy vết nhanh; tool chỉ hiệu quả khi history và reproduction đủ tốt.

## 11. Key takeaway

- `git bisect` là binary search trên lịch sử code.
- Chất lượng good/bad test quyết định chất lượng kết quả.
- First bad commit là điểm bắt đầu root-cause analysis, không phải kết luận cuối cùng.
