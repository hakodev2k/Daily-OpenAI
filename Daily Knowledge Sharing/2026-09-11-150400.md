# 1. C# `SemaphoreSlim` như bounded concurrency gate: giới hạn số I/O operation đồng thời thay vì bắn hàng nghìn task cùng lúc

## 1. What is it?

`SemaphoreSlim` là một synchronization primitive cho phép tối đa N caller cùng đi vào một vùng xử lý. Trong backend .NET, một use case rất thực tế là **bounded concurrency**: cho phép chạy song song đủ để tận dụng I/O, nhưng không để application đồng thời tạo hàng nghìn request tới SQL, HTTP API, Blob Storage hoặc một service bên ngoài.

Mental model:

```text
1000 items cần xử lý
        |
        v
SemaphoreSlim(20)
        |
        +--> tối đa 20 operation đang chạy
        +--> phần còn lại chờ asynchronous
```

Nó không phải distributed lock và cũng không phải queue bền vững. Nó chỉ là concurrency gate trong process.

## 2. Why does it exist?

Một lỗi phổ biến là thấy I/O async rồi tạo task cho toàn bộ input:

```csharp
await Task.WhenAll(items.Select(ProcessAsync));
```

Nếu `items` có 50 record thì có thể ổn. Nếu có 50.000 record, application có thể đồng thời tạo hàng nghìn HTTP request, thuê hàng nghìn database connection logical operation hoặc dồn áp lực vào downstream.

`async` giúp không giữ thread trong lúc chờ I/O, nhưng **không giới hạn resource consumption**. Bounded concurrency tồn tại để bảo vệ cả application lẫn dependency.

## 3. How does it work?

`SemaphoreSlim` giữ một counter.

- `WaitAsync` giảm counter khi còn slot.
- Khi counter = 0, caller chờ asynchronously.
- `Release` trả slot lại.

Flow:

```text
Item 1 ─┐
Item 2 ─┼─> WaitAsync() ─> slot available ─> Process ─> Release()
...
Item N ─┘               └> no slot        ─> async wait
```

Điểm quan trọng là `Release()` phải nằm trong `finally`. Nếu exception làm mất một permit, gate có thể dần bị “rò slot” và cuối cùng mọi work đứng chờ.

## 4. Practical implementation

```csharp
public async Task ProcessBatchAsync(
    IReadOnlyCollection<Guid> ids,
    CancellationToken cancellationToken)
{
    using var gate = new SemaphoreSlim(initialCount: 20);

    var tasks = ids.Select(async id =>
    {
        await gate.WaitAsync(cancellationToken);

        try
        {
            await ProcessOneAsync(id, cancellationToken);
        }
        finally
        {
            gate.Release();
        }
    });

    await Task.WhenAll(tasks);
}
```

Với batch rất lớn, vẫn nên tránh materialize hàng trăm nghìn task cùng lúc. Khi đó `Channel<T>`, `Parallel.ForEachAsync` hoặc queue consumer thường kiểm soát memory tốt hơn.

`Parallel.ForEachAsync` cho trường hợp đơn giản:

```csharp
await Parallel.ForEachAsync(
    ids,
    new ParallelOptions
    {
        MaxDegreeOfParallelism = 20,
        CancellationToken = cancellationToken
    },
    async (id, ct) =>
    {
        await ProcessOneAsync(id, ct);
    });
```

## 5. Real production scenario

Một background job đọc 30.000 customer record rồi gọi third-party CRM API để đồng bộ. Ban đầu developer dùng `Task.WhenAll` cho toàn bộ collection.

Kết quả:

- outbound connection tăng đột biến,
- CRM trả `429 Too Many Requests`,
- retry policy tiếp tục tạo thêm traffic,
- memory tăng vì quá nhiều task sống cùng lúc,
- toàn job chậm hơn dù “parallel” nhiều hơn.

Giới hạn concurrency xuống 10–20 request đồng thời thường cho throughput ổn định hơn và giảm retry storm.

## 6. Failure scenario & troubleshooting

**Symptom** → latency downstream tăng, 429/503 xuất hiện, memory và số active connection tăng mạnh khi batch lớn.

**Evidence** → dependency telemetry cho thấy concurrency spike; request count tăng nhanh hơn throughput hoàn thành.

**Hypothesis** → application không có backpressure / concurrency limit.

**Diagnosis** → đo số in-flight operation, HTTP connection usage, DB pool usage và task count.

**Fix** → giới hạn concurrency, thêm rate-limit-aware retry, cân nhắc `Channel<T>` hoặc queue.

**Verification** → load test với batch lớn; throughput ổn định, dependency error giảm và memory không tăng tuyến tính theo batch size.

## 7. Common mistakes

- Nghĩ rằng `async` tự động kiểm soát concurrency.
- `WaitAsync()` nhưng quên `Release()` trong `finally`.
- Chọn `MaxDegreeOfParallelism` theo số CPU cho I/O-bound workload một cách máy móc.
- Giới hạn concurrency trong mỗi instance nhưng quên rằng Production có 20 replicas, tổng concurrency thành 20 × N.
- Dùng `SemaphoreSlim` để giải quyết distributed coordination giữa nhiều process.

## 8. Alternatives

- `Parallel.ForEachAsync`: tốt cho bounded parallelism đơn giản.
- `Channel<T>`: tốt khi cần producer/consumer, backpressure và pipeline dài sống trong process.
- Azure Service Bus / queue: phù hợp khi cần durability, retry độc lập và scale nhiều instances.
- Rate limiter: phù hợp khi giới hạn theo requests/second hoặc quota thay vì số operation đồng thời.

## 9. Trade-offs

### Advantages

- Đơn giản, nhẹ và asynchronous.
- Bảo vệ dependency khỏi traffic burst.
- Cho phép tune throughput thay vì “parallel tối đa”.

### Costs / Risks

- Chỉ giới hạn trong process.
- Chọn concurrency sai có thể giảm throughput hoặc vẫn overload downstream.
- Không tự cung cấp durability, retry, fairness hay observability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu concurrency khác parallelism và `async` không đồng nghĩa “bao nhiêu task cũng được”.

### Middle

Implement `SemaphoreSlim` đúng `try/finally`, propagate `CancellationToken` và benchmark mức concurrency khác nhau.

### Senior

Quan sát downstream capacity, connection pools, 429/503, retry behavior và xác định bottleneck thực sự trước khi tăng concurrency.

### Technical Lead / Architect

Quyết định concurrency control nằm trong process, distributed queue hay API gateway/rate limiter; đồng thời tính tổng concurrency toàn hệ thống khi autoscale.

## 11. Key takeaway

- Async giải phóng thread, không giới hạn số I/O đang diễn ra.
- Bounded concurrency thường nhanh và ổn định hơn uncontrolled fan-out.
- `SemaphoreSlim` phù hợp local coordination, không thay thế distributed queue/lock.

# 2. ASP.NET Core model binding + validation boundary: tách transport validation khỏi business invariant để API contract rõ và domain không bị rò logic

## 1. What is it?

Model binding là quá trình ASP.NET Core đọc route, query string, headers hoặc request body rồi tạo object .NET cho endpoint. Validation ở transport boundary kiểm tra request có đúng hình dạng và constraint cơ bản hay không trước khi business logic chạy.

Mental model nên tách ba tầng:

```text
HTTP payload
  -> transport validation
  -> application command
  -> domain invariant
```

`Email` thiếu, JSON sai type hoặc `pageSize = -10` là transport/input problem. “Không thể approve timesheet đã đóng kỳ lương” là business invariant và không nên bị nhét vào DTO attribute.

## 2. Why does it exist?

Nếu không có validation boundary, business layer phải xử lý cả lỗi protocol lẫn business rule. Code nhanh chóng trở thành chuỗi `if` khó phân biệt:

```text
field thiếu?
format sai?
user không có quyền?
state transition không hợp lệ?
entity không tồn tại?
```

API cần trả lỗi ổn định cho client, còn domain cần giữ invariant độc lập với HTTP.

## 3. How does it work?

Request lifecycle đơn giản:

```text
Client
 -> JSON parse
 -> model binding
 -> validation
 -> endpoint/application
 -> domain rules
 -> persistence
 -> response
```

Với controller có `[ApiController]`, invalid model state có thể được chuyển thành HTTP 400 trước khi action chạy. Với Minimal API, validation strategy cần explicit hơn tùy stack/framework version và library sử dụng.

## 4. Practical implementation

DTO chỉ giữ transport constraint:

```csharp
public sealed record CreateEmployeeRequest(
    string Email,
    string DisplayName,
    DateOnly StartDate);
```

Endpoint có thể validate rõ ràng:

```csharp
app.MapPost("/employees", async (
    CreateEmployeeRequest request,
    EmployeeService service,
    CancellationToken ct) =>
{
    var errors = new Dictionary<string, string[]>();

    if (string.IsNullOrWhiteSpace(request.Email))
        errors["email"] = ["Email is required."];

    if (!EmailAddress.TryParse(request.Email, out var email))
        errors["email"] = ["Email format is invalid."];

    if (errors.Count > 0)
        return Results.ValidationProblem(errors);

    var result = await service.CreateAsync(
        email!,
        request.DisplayName,
        request.StartDate,
        ct);

    return Results.Created($"/employees/{result.Id}", result);
});
```

Business invariant vẫn nằm trong domain/application:

```csharp
public void Terminate(DateOnly date)
{
    if (Status == EmployeeStatus.Terminated)
        throw new DomainRuleViolation("Employee is already terminated.");

    if (date < StartDate)
        throw new DomainRuleViolation(
            "Termination date cannot be before start date.");

    Status = EmployeeStatus.Terminated;
}
```

## 5. Real production scenario

Một HR API có endpoint approve leave request. Frontend gửi `approverId`, `leaveId` và comment.

Transport layer cần kiểm tra:

- UUID hợp lệ,
- comment không vượt limit,
- required field tồn tại.

Nhưng các rule như:

- approver phải quản lý nhân viên,
- leave phải ở trạng thái `Pending`,
- không được approve request đã bị payroll lock,

phải nằm ở application/domain logic, vì chúng vẫn đúng nếu operation sau này được gọi từ message consumer hoặc batch process chứ không chỉ HTTP.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng một business operation trả lỗi khác nhau tùy gọi từ API, background job hay unit test.

**Evidence** → rule nằm trong controller hoặc validator chỉ chạy ở HTTP path.

**Hypothesis** → business invariant bị đặt nhầm tại transport boundary.

**Diagnosis** → trace call path và tìm rule nào chỉ tồn tại trong API layer.

**Fix** → giữ shape/format validation ở boundary, chuyển invariant vào domain/application service.

**Verification** → cùng invariant phải được enforce từ API, integration test và non-HTTP caller.

## 7. Common mistakes

- Nhét database query và business workflow vào validation attribute.
- Dùng HTTP DTO làm domain entity.
- Trả mọi lỗi thành `400 Bad Request`, kể cả `404`, `409` hoặc `403`.
- Tin rằng client-side validation đủ nên server không cần validate.
- Validation quá sâu làm endpoint gọi database nhiều lần trước khi business operation thật sự bắt đầu.

## 8. Alternatives

FluentValidation hoặc custom pipeline behavior hữu ích nếu hệ thống có nhiều request model và cần reusable rules. Với API nhỏ, explicit validation trong endpoint có thể đơn giản hơn. Domain invariant vẫn phải tồn tại độc lập dù dùng library nào.

## 9. Trade-offs

### Advantages

- API contract rõ.
- Domain không phụ thuộc HTTP.
- Test dễ phân loại input error và business conflict.

### Costs / Risks

- Có thể tạo duplication nếu cùng rule bị viết ở nhiều layer mà không xác định ownership.
- Validation framework quá phức tạp dễ biến thành một “business layer thứ hai”.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt JSON/model invalid với business operation không hợp lệ.

### Middle

Thiết kế request DTO, validation response và status code hợp lý.

### Senior

Nhận diện rule ownership, tránh duplicate database lookup và giữ error contract backward compatible.

### Technical Lead / Architect

Xác định validation boundary chung cho API, messaging và background workflow; quyết định rule nào thuộc transport, application hay domain.

## 11. Key takeaway

- Validation không phải một khối duy nhất; input rule và business invariant có ownership khác nhau.
- Domain rule không nên chỉ tồn tại trong controller/validator.
- Error contract tốt giúp client phân biệt malformed input, conflict, authorization và missing resource.

# 3. EF Core raw SQL parameterization + composability: dùng SQL thủ công khi cần nhưng không đánh đổi security, maintainability và query composition

## 1. What is it?

EF Core hỗ trợ chạy raw SQL khi LINQ không diễn đạt tốt query, cần gọi database feature đặc thù hoặc muốn kiểm soát SQL chính xác hơn.

Điểm quan trọng: raw SQL không có nghĩa là bỏ toàn bộ EF Core. Có thể dùng SQL thủ công cho một query cụ thể nhưng vẫn tận dụng mapping, connection management, transaction và materialization của `DbContext`.

## 2. Why does it exist?

LINQ là abstraction rất mạnh nhưng không phải mọi query đều tự nhiên. Một số trường hợp:

- query dùng CTE phức tạp,
- window function/database-specific function,
- stored procedure,
- migration từ code SQL có sẵn,
- query cần shape tối ưu mà LINQ provider khó biểu diễn.

Nếu ép mọi thứ qua LINQ chỉ vì “chuẩn EF”, code có thể khó hiểu hơn SQL gốc.

## 3. How does it work?

EF Core có API phân biệt interpolated SQL được parameterize và raw string thực sự.

Ví dụ an toàn:

```csharp
var status = OrderStatus.Pending;

var orders = await db.Orders
    .FromSqlInterpolated($"""
        SELECT *
        FROM Orders
        WHERE Status = {status}
        """)
    .AsNoTracking()
    .ToListAsync(ct);
```

`{status}` trở thành database parameter, không được nối trực tiếp vào SQL text.

Ngược lại, code như sau nguy hiểm:

```csharp
var sql = $"SELECT * FROM Orders WHERE CustomerName = '{name}'";
```

Nếu `name` đến từ user input, đây là SQL injection boundary.

## 4. Practical implementation

Query với explicit parameter:

```csharp
var customerId = new SqlParameter("@customerId", request.CustomerId);

var orders = await db.Orders
    .FromSqlRaw("""
        SELECT Id, CustomerId, Status, CreatedAt
        FROM Orders
        WHERE CustomerId = @customerId
        """, customerId)
    .AsNoTracking()
    .ToListAsync(ct);
```

Raw SQL có thể composable nếu SQL nguồn là một subquery hợp lệ:

```csharp
var query = db.Orders
    .FromSqlInterpolated($"""
        SELECT *
        FROM Orders
        WHERE CreatedAt >= {fromDate}
        """)
    .Where(x => x.Status == OrderStatus.Pending)
    .OrderByDescending(x => x.CreatedAt);
```

EF Core sẽ bọc source SQL và compose thêm SQL ngoài nó khi provider hỗ trợ.

## 5. Real production scenario

Một reporting endpoint cần “latest order per customer” kết hợp window function và filter phức tạp. LINQ hiện tại tạo SQL khó đọc và execution plan không ổn định.

Team chuyển query này sang một raw SQL projection có test integration, parameter đầy đủ và performance benchmark. Phần còn lại của application vẫn dùng LINQ.

Đây là lựa chọn pragmatic: không cần tạo repository mới chỉ vì một query đặc biệt.

## 6. Failure scenario & troubleshooting

**Symptom** → query trả lỗi syntax sau khi thêm `.Where()` hoặc performance tệ hơn mong đợi.

**Evidence** → generated SQL cho thấy EF bọc raw SQL thành subquery rồi compose thêm filter.

**Hypothesis** → raw SQL không composable hoặc query shape khiến optimizer khó tối ưu.

**Diagnosis** → bật SQL logging, xem generated command và execution plan.

**Fix** → chuyển toàn bộ filter cần thiết vào SQL, dùng keyless projection hoặc tách query thành stored object nếu hợp lý.

**Verification** → integration test trên database thật và đo logical reads/latency.

## 7. Common mistakes

- Nối string từ user input vào SQL.
- Dùng raw SQL như default vì “nhanh hơn LINQ” mà không đo.
- Trả entity tracked từ complex query rồi vô tình `SaveChanges` với state không mong muốn.
- Không test provider-specific SQL trong integration test.
- Che raw SQL sau generic repository khiến query semantics và tuning trở nên khó thấy hơn.

## 8. Alternatives

- LINQ: ưu tiên khi expression rõ, provider translate tốt và maintainability cao.
- Database view: phù hợp với reusable read model.
- Stored procedure: hữu ích khi organization/database ownership yêu cầu hoặc operation phức tạp có lifecycle riêng.
- Dapper: phù hợp nếu workload read-heavy cần explicit SQL mapping rộng hơn EF Core.

## 9. Trade-offs

### Advantages

- Kiểm soát SQL tốt hơn.
- Có thể tận dụng feature đặc thù database.
- Không cần bỏ toàn bộ EF Core.

### Costs / Risks

- Tăng coupling với database dialect.
- Refactor entity/schema ít được compiler hỗ trợ.
- Security phụ thuộc parameterization đúng.
- Test unit mock không đủ; cần database integration test.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu raw SQL phải parameterize và không nối user input.

### Middle

Biết `FromSqlInterpolated`, `FromSqlRaw`, tracking behavior và cách xem generated SQL.

### Senior

Đánh giá execution plan, composition boundary, provider portability và khi nào SQL rõ hơn LINQ.

### Technical Lead / Architect

Quyết định tiêu chuẩn sử dụng raw SQL/Dapper/stored procedure, test strategy và ownership để tránh codebase biến thành hỗn hợp query không kiểm soát.

## 11. Key takeaway

- Raw SQL là escape hatch hợp lệ, không phải thất bại của architecture.
- Parameterization là bắt buộc ở security boundary.
- Chọn LINQ hay SQL theo clarity, correctness và measured behavior.

# 4. SQL Server blocking chain: phân tích lock wait và transaction scope thay vì nhầm mọi request chậm thành deadlock

## 1. What is it?

Blocking xảy ra khi một transaction giữ lock mà transaction khác cần, khiến transaction sau phải chờ. Deadlock là trường hợp đặc biệt có cycle; blocking thông thường có thể kéo dài nhưng không có cycle.

Mental model:

```text
Session A giữ lock X trên Row 1
        |
        v
Session B cần Row 1 -> WAIT
        |
        v
Session C chờ resource do B đang giữ -> WAIT
```

Đây là blocking chain.

## 2. Why does it exist?

Lock là một phần của cơ chế bảo đảm isolation/correctness. Nếu database cho mọi transaction đọc/ghi cùng dữ liệu mà không coordination, race condition và inconsistent state xuất hiện.

Vấn đề không phải “lock tồn tại”, mà là lock giữ quá rộng hoặc quá lâu so với business operation.

## 3. How does it work?

Một update có thể giữ exclusive lock đến khi transaction commit:

```sql
BEGIN TRANSACTION;

UPDATE Orders
SET Status = 'Approved'
WHERE Id = @id;

-- transaction chưa commit
```

Session khác:

```sql
SELECT *
FROM Orders
WHERE Id = @id;
```

Tùy isolation/versioning configuration, query sau có thể phải chờ.

Blocking time phụ thuộc:

```text
query duration
+ transaction scope
+ lock footprint
+ access order
+ isolation level
```

## 4. Practical implementation

Một anti-pattern trong application:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

var order = await db.Orders.SingleAsync(x => x.Id == id, ct);
order.MarkProcessing();
await db.SaveChangesAsync(ct);

// Remote call trong transaction DB
await paymentClient.CaptureAsync(order.PaymentId, ct);

order.MarkPaid();
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Remote HTTP call có thể mất vài giây và transaction giữ lock suốt khoảng đó.

Tốt hơn là thu hẹp transaction boundary và thiết kế workflow distributed rõ ràng, ví dụ state transition + Outbox thay vì giữ SQL transaction xuyên network call.

## 5. Real production scenario

Approval API bình thường chạy 100 ms. Sau một release, p95 tăng lên 8 giây vào giờ cao điểm. SQL CPU vẫn thấp.

Investigation cho thấy một batch job mở transaction, update hàng nghìn row rồi gọi external API trước khi commit. Các request khác chờ lock trên cùng bảng.

CPU thấp nhưng latency cao vì workload **waiting**, không phải computing.

## 6. Failure scenario & troubleshooting

**Symptom** → request chậm theo burst, SQL CPU không nhất thiết cao.

**Evidence** → sessions có wait type liên quan lock; nhiều session cùng chờ một blocker.

**Hypothesis** → long-running transaction hoặc scan/update footprint lớn.

**Diagnosis** → xác định head blocker, transaction start time, query đang chạy, execution plan và code path mở transaction.

**Fix** → thu hẹp transaction, giảm batch size, thêm index nếu access pattern gây scan không cần thiết, tránh network I/O trong transaction.

**Verification** → blocking duration giảm, p95/p99 phục hồi và transaction lifetime metric ngắn hơn.

## 7. Common mistakes

- Gọi mọi blocking là deadlock.
- Kill session bị block thay vì tìm head blocker.
- Tăng command timeout để “fix” lock wait.
- Thêm index mà không xem transaction scope.
- Giữ transaction mở qua user interaction hoặc remote API call.

## 8. Alternatives

Snapshot-based isolation có thể giảm reader/writer blocking nhưng chuyển chi phí sang row versioning và không loại bỏ write/write contention. Optimistic concurrency giúp xử lý lost update nhưng cũng không thay thế việc thiết kế transaction ngắn.

## 9. Trade-offs

### Advantages

Lock-based consistency dễ reason trong nhiều operation và bảo vệ write correctness.

### Costs / Risks

Transaction dài làm tăng blocking, log growth và blast radius. Isolation mạnh hơn có thể giảm anomaly nhưng tăng contention.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt slow CPU query với query đang chờ lock.

### Middle

Biết transaction bắt đầu/kết thúc ở đâu và tránh giữ transaction qua remote call.

### Senior

Đọc blocking chain, execution plan, wait evidence và xác định head blocker/root cause.

### Technical Lead / Architect

Thiết kế transaction boundary theo consistency requirement; quyết định workflow nào cần local ACID, workflow nào cần asynchronous/eventual consistency.

## 11. Key takeaway

- Blocking không phải deadlock; deadlock chỉ là một cycle đặc biệt.
- SQL CPU thấp không có nghĩa database không phải bottleneck.
- Transaction scope thường quan trọng ngang query text khi điều tra lock wait.

# 5. Cosmos DB Request Units + partition-aware query design: hiểu query cost để tránh cross-partition scan biến thành hóa đơn và latency khó kiểm soát

## 1. What is it?

Cosmos DB dùng Request Units (RU) như abstraction cho compute/I/O cost của operation. Một point read theo `id + partition key` rất rẻ và predictable; query quét nhiều partition hoặc nhiều document có thể tốn RU lớn hơn rất nhiều.

Mental model:

```text
Access pattern
   -> partition routing
   -> documents/index work
   -> RU charge
   -> latency + cost + throttling risk
```

## 2. Why does it exist?

Cosmos DB là distributed database. Chi phí query không chỉ phụ thuộc câu query “ngắn hay dài” mà còn phụ thuộc data distribution và số partition phải chạm tới.

Nếu application không cung cấp partition key phù hợp, coordinator có thể fan-out query tới nhiều physical partition, tổng hợp kết quả rồi trả về.

## 3. How does it work?

Point read:

```text
(id, partitionKey)
    -> route trực tiếp partition
    -> fetch item
```

Cross-partition query:

```text
query không đủ partition key
    -> fan-out partition A
    -> fan-out partition B
    -> fan-out partition C
    -> merge result
```

RU bị ảnh hưởng bởi:

- số document/index entry phải đọc,
- số partition,
- result size,
- indexing policy,
- consistency và operation type.

## 4. Practical implementation

Point read trong .NET SDK:

```csharp
var response = await container.ReadItemAsync<OrderDocument>(
    id: orderId.ToString(),
    partitionKey: new PartitionKey(customerId.ToString()),
    cancellationToken: ct);

var ru = response.RequestCharge;
```

Query có partition key rõ:

```csharp
var query = new QueryDefinition("""
    SELECT *
    FROM c
    WHERE c.customerId = @customerId
      AND c.status = @status
    """)
    .WithParameter("@customerId", customerId)
    .WithParameter("@status", "Pending");

using var iterator = container.GetItemQueryIterator<OrderDocument>(
    query,
    requestOptions: new QueryRequestOptions
    {
        PartitionKey = new PartitionKey(customerId)
    });
```

Nên log/metric `RequestCharge` cho hot operation thay vì chỉ nhìn average account RU.

## 5. Real production scenario

Một SaaS multi-tenant dùng `tenantId` làm partition key. API “list recent invoices của tenant” chạy tốt vì luôn route theo tenant.

Sau đó team thêm admin endpoint search invoice toàn hệ thống theo `status`. Query không có partition key và chạy trên hàng trăm tenant partition. Khi usage tăng:

- RU spike,
- 429 tăng,
- latency admin API tăng,
- các tenant API khác cũng bị ảnh hưởng vì chia sẻ throughput.

Vấn đề là access pattern mới không khớp data model cũ.

## 6. Failure scenario & troubleshooting

**Symptom** → Cosmos trả 429 dù số request không tăng nhiều; latency query admin tăng.

**Evidence** → request charge per query tăng cao, diagnostics cho thấy cross-partition execution.

**Hypothesis** → access pattern fan-out quá rộng hoặc indexing/query shape không phù hợp.

**Diagnosis** → xem partition key, query metrics, RU/request và cardinality của filter.

**Fix** → đưa partition key vào request, tạo read model riêng, denormalize theo access pattern hoặc tách workload throughput nếu cần.

**Verification** → RU/query giảm, 429 giảm và p95 ổn định ở production-like dataset.

## 7. Common mistakes

- Chọn partition key chỉ vì field có vẻ “unique”.
- Dùng cross-partition query như default vì SDK vẫn trả kết quả đúng.
- Chỉ monitor total RU mà không theo operation/query.
- Dùng Cosmos DB như SQL database rồi kỳ vọng join/filter tùy ý với cùng cost model.
- Tăng provisioned RU để che data model/access pattern kém.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp hơn nếu workload cần relational join/ad-hoc query mạnh. Elasticsearch phù hợp search/filter full-text. Một read model riêng trong Cosmos hoặc search index có thể phục vụ cross-tenant analytics mà không phá transactional path.

## 9. Trade-offs

### Advantages

- Scale phân tán tốt khi partition key khớp workload.
- Point read predictable và latency thấp.
- Managed replication/availability mạnh.

### Costs / Risks

- Data modeling bị chi phối bởi access pattern.
- Cross-partition query có cost khó chịu khi scale.
- Denormalization tăng complexity consistency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định dữ liệu nằm/được route như thế nào.

### Middle

Đọc `RequestCharge`, truyền partition key và test query trên dataset đủ lớn.

### Senior

Phân tích hot partition, cross-partition fan-out và lựa chọn denormalized/read model.

### Technical Lead / Architect

Quyết định Cosmos có phù hợp workload không, partition key có sống được khi scale không và operation nào cần data store khác.

## 11. Key takeaway

- RU là tín hiệu trực tiếp về cost của access pattern.
- Partition key là quyết định architecture, không chỉ schema field.
- Query đúng kết quả nhưng cross-partition vẫn có thể là thiết kế sai ở quy mô lớn.

# 6. Dependency Inversion ở architecture boundary: đặt abstraction tại nơi có volatility thay vì tạo interface cho mọi class

## 1. What is it?

Dependency Inversion Principle nói high-level policy không nên phụ thuộc trực tiếp vào low-level detail; cả hai nên phụ thuộc abstraction phù hợp.

Nhưng trong codebase thực tế, điều này **không** có nghĩa mọi service đều phải có interface một-một.

Mental model tốt hơn:

```text
Business policy
     |
     v
Port / abstraction
     ^
     |
Infrastructure adapter
```

Abstraction có giá trị khi nó bảo vệ một boundary có khả năng thay đổi hoặc cần test/replace độc lập.

## 2. Why does it exist?

Nếu application service trực tiếp new SDK/client cụ thể:

```text
OrderApplication
  -> StripeClient
  -> AzureBlobClient
  -> SmtpClient
```

business workflow bị buộc với implementation detail. Thay provider, test failure mode hoặc chạy offline trở nên khó.

Ngược lại, tạo `IFooService` cho mọi `FooService` dù không có boundary thật chỉ thêm ceremony.

## 3. How does it work?

Boundary abstraction nên nói bằng language của consumer:

```csharp
public interface IPaymentGateway
{
    Task<PaymentResult> CaptureAsync(
        Money amount,
        PaymentReference reference,
        CancellationToken ct);
}
```

Adapter cụ thể:

```csharp
public sealed class StripePaymentGateway : IPaymentGateway
{
    private readonly StripeClient _client;

    public async Task<PaymentResult> CaptureAsync(
        Money amount,
        PaymentReference reference,
        CancellationToken ct)
    {
        // Translate domain/application request -> provider request
        // Call provider
        // Translate provider response -> application result
        throw new NotImplementedException();
    }
}
```

Application phụ thuộc `IPaymentGateway`, không phụ thuộc provider-specific DTO.

## 4. Practical implementation

DI registration:

```csharp
builder.Services.AddScoped<IPaymentGateway, StripePaymentGateway>();
```

Application service:

```csharp
public sealed class CheckoutService(IPaymentGateway payments)
{
    public async Task CompleteAsync(
        Order order,
        CancellationToken ct)
    {
        var result = await payments.CaptureAsync(
            order.Total,
            new PaymentReference(order.Id.ToString()),
            ct);

        order.RecordPayment(result.TransactionId);
    }
}
```

Interface ownership nên nằm gần application/domain boundary, không nhất thiết nằm trong infrastructure project chỉ vì implementation ở đó.

## 5. Real production scenario

E-commerce ban đầu dùng một review provider và SDK model của provider bị lan ra controller, domain và database projection. Hai năm sau business đổi provider.

Nếu provider contract đã leak sâu, migration không còn là “thay adapter”; nó trở thành rewrite nhiều layer.

Một anti-corruption/port boundary nhỏ từ đầu có thể giới hạn thay đổi vào integration layer.

## 6. Failure scenario & troubleshooting

**Symptom** → đổi third-party SDK version kéo theo sửa hàng chục project/file không liên quan.

**Evidence** → provider namespace xuất hiện trong application/domain layer.

**Hypothesis** → dependency detail xuyên boundary.

**Diagnosis** → dependency graph và namespace usage.

**Fix** → định nghĩa consumer-oriented port, map provider model tại adapter và migrate theo slice.

**Verification** → application tests chạy với fake adapter; đổi provider SDK không làm domain compile fail.

## 7. Common mistakes

- `IFooService` cho mọi `FooService` dù chỉ có một implementation và không có boundary meaningful.
- Interface copy nguyên method của SDK/provider nên abstraction không thực sự abstract.
- Domain object chứa Azure/HTTP/EF type.
- Dùng abstraction để che mọi code khiến debugging khó hơn.
- Tưởng dependency inversion đồng nghĩa phải có Clean Architecture đầy đủ folder/project.

## 8. Alternatives

Với code nội bộ đơn giản, concrete class + DI trực tiếp thường đủ. Function/delegate abstraction có thể phù hợp với behavior nhỏ. Adapter pattern chỉ cần khi volatility/testing/ownership thực sự justify.

## 9. Trade-offs

### Advantages

- Giảm coupling tới infrastructure/vendor.
- Test failure path dễ hơn.
- Thay implementation tại boundary rõ.

### Costs / Risks

- Thêm type/mapping.
- Abstraction sai có thể trở thành leaky abstraction.
- Over-abstraction làm onboarding/debugging khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu interface không chỉ phục vụ mocking; nó có thể định nghĩa boundary.

### Middle

Thiết kế port theo nhu cầu của consumer và map provider DTO tại adapter.

### Senior

Nhận diện volatility, leaky abstraction và chi phí abstraction.

### Technical Lead / Architect

Quyết định boundary nào đáng bảo vệ và boundary nào nên giữ concrete để hệ thống đơn giản; dependency direction phải phản ánh ownership/change isolation.

## 11. Key takeaway

- Dependency inversion là về direction và boundary, không phải số lượng interface.
- Abstraction nên thuộc language của consumer, không copy vendor API.
- Nếu không có volatility/boundary thật, concrete dependency có thể là lựa chọn tốt hơn.

# 7. Azure Private Endpoint + Private DNS: đưa PaaS traffic vào private network mà không tự tạo outage vì DNS resolution sai

## 1. What is it?

Azure Private Endpoint tạo một network interface với private IP trong Virtual Network và ánh xạ nó tới một Azure PaaS resource như Storage Account, Key Vault, SQL hoặc Cosmos DB.

Application vẫn gọi hostname dịch vụ, nhưng DNS phải resolve hostname đó về private IP phù hợp.

Mental model:

```text
App trong VNet
   -> DNS lookup service.azure...
   -> Private DNS zone
   -> private IP
   -> Private Endpoint
   -> Azure PaaS service
```

## 2. Why does it exist?

Nhiều enterprise system không muốn traffic tới database/storage/secrets đi qua public endpoint dù có TLS và firewall. Private Endpoint đưa data-plane connectivity vào private address space và cho phép disable/restrict public network access.

Nhưng private connectivity không chỉ là “bật một checkbox”. DNS trở thành critical dependency.

## 3. How does it work?

Azure thường dùng DNS indirection:

```text
myvault.vault.azure.net
   -> CNAME private-link name
   -> private DNS zone
   -> 10.x.x.x
```

Nếu workload dùng custom DNS server, on-prem DNS hoặc hybrid network, cần conditional forwarding/resolution đúng. Sai DNS có thể khiến hostname vẫn resolve public IP dù Private Endpoint đã tồn tại.

## 4. Practical implementation

Trong application code, thường **không đổi URL**:

```csharp
var client = new SecretClient(
    new Uri("https://myvault.vault.azure.net/"),
    new DefaultAzureCredential());
```

Network/DNS layer quyết định endpoint thực sự.

Troubleshooting từ host/container:

```bash
nslookup myvault.vault.azure.net
```

hoặc Linux:

```bash
dig myvault.vault.azure.net
```

Sau đó kiểm tra route/connectivity tới private IP.

## 5. Real production scenario

Team tạo Private Endpoint cho Key Vault và disable public access. App Service đã VNet-integrated nhưng deployment lập tức trả 500 khi lấy secret.

RBAC hoàn toàn đúng. Root cause: custom DNS server không forward zone `privatelink.vaultcore.azure.net` về Azure DNS. Hostname resolve sai và application cố đi public path đã bị chặn.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout hoặc network error sau khi bật Private Endpoint; application credential vẫn hợp lệ.

**Evidence** → DNS resolve về public IP hoặc không resolve; TCP connection tới private IP không thành công.

**Hypothesis** → Private DNS/route/VNet integration sai, không phải authentication.

**Diagnosis** → kiểm tra DNS chain, Private DNS zone link, VNet integration, NSG/route và endpoint approval state.

**Fix** → sửa zone link/conditional forwarding/routing.

**Verification** → từ chính workload runtime, hostname resolve private IP và request thành công khi public access vẫn disabled.

## 7. Common mistakes

- Hard-code private IP trong application config.
- Tạo Private Endpoint nhưng quên Private DNS zone.
- Test từ laptop rồi kết luận Production network hoạt động.
- Nhầm Managed Identity/RBAC issue với connectivity issue.
- Tạo quá nhiều private endpoint mà không có naming/DNS/network ownership rõ.

## 8. Alternatives

Service Endpoint có mô hình khác và không tạo private IP cho resource. Public endpoint + firewall có thể đủ cho workload ít nhạy cảm. Với AKS/multi-region/hybrid network, architecture có thể cần hub-spoke DNS resolver thay vì zone link đơn giản.

## 9. Trade-offs

### Advantages

- Private data-plane access.
- Giảm exposure public network.
- Phù hợp enterprise network control/compliance.

### Costs / Risks

- Tăng DNS/network complexity.
- Cross-region/hybrid troubleshooting khó hơn.
- Thêm endpoint cost và operational ownership.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hostname vẫn giữ nguyên nhưng DNS có thể đưa traffic vào private IP.

### Middle

Biết kiểm tra DNS resolution, VNet integration và endpoint state.

### Senior

Debug hybrid DNS, routing và phân biệt identity vs network failure.

### Technical Lead / Architect

Quyết định service nào thực sự cần private connectivity, thiết kế DNS ownership toàn tổ chức và tránh tạo network architecture phức tạp hơn risk cần giải quyết.

## 11. Key takeaway

- Private Endpoint là network + DNS design, không chỉ Azure resource setting.
- Application thường không nên hard-code private endpoint address.
- Luôn verify DNS từ chính runtime environment.

# 8. Docker writable layer + volumes: hiểu container lifecycle để dữ liệu không biến mất sau restart/redeploy và image không trở thành storage

## 1. What is it?

Một container chạy từ image read-only layers và có thêm writable layer tạm thời cho thay đổi filesystem trong lifetime container.

Volume hoặc bind mount cung cấp storage nằm ngoài writable layer đó.

Mental model:

```text
Image layers (read-only)
        +
Container writable layer (ephemeral)
        +
Volume / bind mount (external persistence)
```

## 2. Why does it exist?

Container được thiết kế disposable: có thể stop, remove và recreate từ image. Nếu application lưu dữ liệu quan trọng vào filesystem nội bộ container, dữ liệu gắn với instance thay vì workload lifecycle.

Điều này đối nghịch với immutable deployment và horizontal scaling.

## 3. How does it work?

Khi container ghi file vào path không mount volume, file nằm trong writable layer. `docker restart` cùng container thường vẫn thấy file, nhưng remove/recreate container có thể làm dữ liệu biến mất.

Volume có lifecycle tách khỏi container:

```text
Container A --mount--> Volume X
Container A removed
Container B --mount--> Volume X
```

Trong orchestrator/cloud, persistent storage semantics lại phụ thuộc storage driver/platform.

## 4. Practical implementation

Docker Compose:

```yaml
services:
  app:
    image: my-api:1.0
    volumes:
      - app-data:/app/data

volumes:
  app-data:
```

Trong ASP.NET Core, cần xác định rõ dữ liệu nào thực sự nên ở local filesystem. Ví dụ user upload trong multi-instance web app thường nên đi Blob Storage/object storage thay vì local volume.

## 5. Real production scenario

Một API container lưu generated PDF vào `/app/files`. Local Docker chạy ổn. Khi Production deploy phiên bản mới, platform recreate container và file biến mất.

Sau đó app scale thành 3 replicas: request upload vào instance A, request download được route vào instance B nên trả 404.

Root cause không phải Docker “mất file”; storage ownership sai.

## 6. Failure scenario & troubleshooting

**Symptom** → file tồn tại sau upload nhưng mất sau deploy hoặc chỉ một số request đọc được.

**Evidence** → file chỉ có trong filesystem của một container instance.

**Hypothesis** → application dùng local ephemeral storage cho shared/persistent data.

**Diagnosis** → inspect mounts, container recreation history và request routing.

**Fix** → chuyển shared durable data sang Blob/object storage hoặc persistent volume phù hợp.

**Verification** → recreate container/scale replicas và xác nhận dữ liệu vẫn truy cập nhất quán.

## 7. Common mistakes

- Dùng container filesystem như database/file server.
- Nghĩ `docker restart` giữ file nên production recreate cũng chắc chắn giữ.
- Mount source code/config writable vào Production không kiểm soát.
- Lưu secrets vào image layer rồi xóa ở layer sau; secret vẫn có thể tồn tại trong image history.
- Dùng volume cho dữ liệu đáng lẽ nên là external object storage trong multi-instance system.

## 8. Alternatives

- Azure Blob Storage/S3-style object storage cho file shared/durable.
- Database cho structured transactional data.
- Managed disk/persistent volume cho workload thực sự cần filesystem semantics.
- Ephemeral storage vẫn phù hợp cho temp files/cache có thể rebuild.

## 9. Trade-offs

### Advantages

Container writable layer đơn giản và nhanh cho temporary state. Volume tách persistence khỏi image/container lifecycle.

### Costs / Risks

Persistent volume thêm backup, replication, mount và scheduling concern. Shared filesystem có thể trở thành bottleneck; object storage thường scale tốt hơn cho upload/download pattern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu image, container writable layer và volume là ba thứ khác nhau.

### Middle

Cấu hình mount, permissions và test recreate container.

### Senior

Nhận diện state ownership, multi-replica behavior, backup và failure semantics.

### Technical Lead / Architect

Quyết định dữ liệu nào nên stateless, object storage, database hay persistent filesystem; tránh biến container platform thành storage architecture ngẫu nhiên.

## 11. Key takeaway

- Container nên được xem là disposable.
- “File tồn tại trong container” không đồng nghĩa dữ liệu durable/shared.
- Chọn storage theo ownership và access pattern, không theo path dễ ghi nhất.

# 9. SonarQube Quality Gates: dùng static analysis như engineering signal thay vì biến coverage/code smell thành KPI mù quáng

## 1. What is it?

SonarQube phân tích source code để phát hiện bug pattern, vulnerability, code smell, duplication, complexity và coverage data. Quality Gate là tập điều kiện quyết định một change có vượt tiêu chuẩn chất lượng đã đặt hay không.

Nó là **signal tự động**, không phải bằng chứng tuyệt đối rằng code tốt hay xấu.

## 2. Why does it exist?

Human code review giỏi ở context, design và business reasoning nhưng không nên lãng phí thời gian lặp lại các check cơ học:

- obvious nullability issue,
- duplicate block,
- known insecure API,
- uncovered changed code,
- complexity tăng mạnh.

Static analysis giúp automation các check có thể máy hóa.

## 3. How does it work?

CI pipeline điển hình:

```text
commit
 -> build
 -> unit/integration tests
 -> coverage report
 -> Sonar analysis
 -> Quality Gate
 -> deploy eligibility
```

Một rule có thể đánh dấu code smell dựa trên heuristic. Vì vậy developer phải hiểu rule, không sửa máy móc để “green dashboard”.

## 4. Practical implementation

Ví dụ pipeline command ở mức khái niệm:

```bash
dotnet sonarscanner begin \
  /k:"employee-api" \
  /d:sonar.cs.opencover.reportsPaths="**/coverage.opencover.xml"

dotnet build

dotnet test \
  /p:CollectCoverage=true \
  /p:CoverletOutputFormat=opencover

dotnet sonarscanner end
```

Quality Gate hợp lý thường tập trung mạnh vào **new code** thay vì bắt legacy codebase phải đạt trạng thái lý tưởng ngay lập tức.

Ví dụ policy:

```text
New critical vulnerabilities = 0
New blocker bugs = 0
Coverage on new code >= agreed threshold
Duplicated lines on new code < threshold
```

## 5. Real production scenario

Một legacy application có coverage toàn hệ thống 28%. Nếu team đặt gate “overall coverage >= 80%”, mọi PR đều fail và developer bắt đầu viết test vô nghĩa chỉ để tăng số.

Nếu gate tập trung new/changed code, team có thể dần nâng chất lượng mà không cần rewrite hoặc test toàn bộ legacy system trước khi ship feature.

## 6. Failure scenario & troubleshooting

**Symptom** → PR bị block bởi hàng trăm issue không liên quan change hiện tại hoặc team mass-suppress warning.

**Evidence** → Quality Gate đánh overall legacy debt thay vì new code; rule profile không khớp stack/risk.

**Hypothesis** → quality policy không phản ánh engineering objective.

**Diagnosis** → xem rule severity, issue age, changed lines và false-positive rate.

**Fix** → dùng quality profile phù hợp, baseline legacy debt, gate new code và document suppression rationale.

**Verification** → PR signal tập trung issue actionable; số suppression giảm và review time không bị static-noise chiếm hết.

## 7. Common mistakes

- Đồng nhất coverage cao với test chất lượng cao.
- Fix code smell máy móc làm code khó đọc hơn.
- Block release bởi metric không liên quan business risk.
- Ignore toàn bộ tool vì từng gặp false positive.
- Cho developer quyền suppress mọi rule mà không cần rationale/review.

## 8. Alternatives

Roslyn analyzers, StyleCop, CodeQL, Semgrep và compiler warnings có thể cover một phần khác nhau. SonarQube mạnh ở centralized quality dashboard/history nhưng không thay thế security review, runtime test hay architecture review.

## 9. Trade-offs

### Advantages

- Feedback sớm và repeatable.
- Giảm manual review cho issue cơ học.
- Theo dõi technical debt trend.

### Costs / Risks

- False positive và metric gaming.
- Operational cost của server/configuration.
- Rule không hiểu đầy đủ business semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu issue từ tool là tín hiệu cần xem xét, không phải mệnh lệnh tuyệt đối.

### Middle

Fix/suppress có rationale và viết test bảo vệ behavior quan trọng.

### Senior

Đánh giá rule profile, noise, coverage quality và effect lên developer workflow.

### Technical Lead / Architect

Thiết kế Quality Gate theo risk, new-code policy và legacy strategy; không biến metric thành mục tiêu thay thế chất lượng thực.

## 11. Key takeaway

- Static analysis tốt nhất khi automation signal cơ học, không thay engineering judgment.
- Coverage đo code được chạy bởi test, không đo test có giá trị hay không.
- Quality Gate nên giảm risk của change mới thay vì biến legacy debt thành blocker vô hạn.

# 10. Webhook signature verification + replay protection: tin payload chỉ sau khi xác minh authenticity, freshness và idempotency

## 1. What is it?

Webhook là inbound HTTP callback từ hệ thống bên ngoài. Vì endpoint thường public, application không được tin payload chỉ vì request “trông giống provider”.

Một secure webhook flow thường cần ba lớp:

```text
authenticity -> freshness -> idempotency
```

- Signature xác minh request được tạo bởi bên giữ secret/private key.
- Timestamp/nonce giúp chống replay.
- Event ID/idempotency giúp xử lý duplicate delivery an toàn.

## 2. Why does it exist?

Nếu endpoint `/webhooks/payment` chỉ parse JSON rồi update order, attacker có thể tự gửi payload giả “payment succeeded”.

Ngay cả request signature hợp lệ cũng có thể bị capture rồi replay nếu application không kiểm tra freshness/duplicate event.

## 3. How does it work?

HMAC pattern điển hình:

```text
provider:
  signature = HMAC(secret, timestamp + "." + rawBody)

consumer:
  read raw body
  recompute HMAC
  constant-time compare
  validate timestamp window
  check event id
  process once
```

Quan trọng: verify trên **raw request bytes** theo đúng canonicalization provider quy định. Deserialize rồi serialize lại có thể thay whitespace/property order và làm signature khác.

## 4. Practical implementation

Ví dụ simplified ASP.NET Core HMAC verification:

```csharp
static bool VerifySignature(
    string rawBody,
    string timestamp,
    string providedSignature,
    string secret)
{
    var payload = Encoding.UTF8.GetBytes($"{timestamp}.{rawBody}");
    var key = Encoding.UTF8.GetBytes(secret);

    using var hmac = new HMACSHA256(key);
    var expected = hmac.ComputeHash(payload);

    var provided = Convert.FromHexString(providedSignature);

    return CryptographicOperations.FixedTimeEquals(
        expected,
        provided);
}
```

Endpoint cần thêm timestamp tolerance:

```csharp
var eventTime = DateTimeOffset.FromUnixTimeSeconds(timestampSeconds);
if (DateTimeOffset.UtcNow - eventTime > TimeSpan.FromMinutes(5))
    return Results.Unauthorized();
```

Và event store/Inbox có unique constraint trên provider event ID.

## 5. Real production scenario

Payment provider gửi webhook `payment.succeeded`. Network timeout xảy ra sau khi application commit nhưng trước khi provider nhận HTTP 200, nên provider retry cùng event ba lần.

Nếu handler chỉ “update rồi gửi email”, user có thể nhận ba email hoặc downstream side effect bị lặp.

Nếu có unique event ID + transaction/inbox, lần retry được acknowledge nhưng business side effect chỉ thực hiện một lần.

## 6. Failure scenario & troubleshooting

**Symptom** → webhook Production liên tục trả 401 dù secret đúng.

**Evidence** → signature mismatch chỉ xảy ra sau khi middleware parse/transform body.

**Hypothesis** → application verify body đã bị thay đổi hoặc canonicalization sai.

**Diagnosis** → capture exact raw bytes, header format, timestamp và provider specification.

**Fix** → enable/request buffering đúng chỗ, verify raw payload trước deserialize và dùng fixed-time compare.

**Verification** → replay official signed fixture/request và test payload bị sửa một byte phải fail.

Một failure khác:

**Symptom** → duplicate notification/order transition.

**Evidence** → cùng provider event ID xuất hiện nhiều lần.

**Fix** → unique event record + idempotent processing.

## 7. Common mistakes

- Chỉ kiểm tra secret trong query string.
- So signature bằng string equality thông thường khi provider yêu cầu cryptographic comparison.
- Verify object đã deserialize thay vì raw body.
- Không validate timestamp/replay window.
- Trả 500 cho duplicate event đã xử lý, khiến provider retry mãi.
- Cho webhook trực tiếp mutate nhiều hệ thống trong cùng request mà không có recovery strategy.

## 8. Alternatives

mTLS có thể tăng trust ở transport layer nhưng thường không thay application-level event verification/idempotency. OAuth client authentication phù hợp một số callback protocol, nhưng webhook provider phổ biến vẫn dùng HMAC/asymmetric signature.

Với workload nặng, endpoint nên verify + persist event nhanh rồi đẩy processing sang queue/worker.

## 9. Trade-offs

### Advantages

- Ngăn forged event.
- Replay/duplicate behavior rõ ràng.
- Tách inbound trust boundary khỏi business logic.

### Costs / Risks

- Secret/key rotation cần coordination.
- Raw body buffering và canonicalization tăng implementation detail.
- Idempotency storage cần retention/cleanup policy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu webhook là public inbound request và không được tin payload mặc định.

### Middle

Implement signature verification, timestamp check và duplicate event handling.

### Senior

Thiết kế key rotation, raw-body handling, retry semantics, Inbox/idempotency và observability.

### Technical Lead / Architect

Xác định trust boundary, event retention, asynchronous processing, blast radius và behavior khi provider gửi sai/retry storm.

## 11. Key takeaway

- Signature xác minh nguồn; timestamp chống replay; idempotency xử lý duplicate — cần cả ba khi risk phù hợp.
- Verify raw payload trước khi business logic chạy.
- Webhook delivery nên được xem là at-least-once, không phải exactly-once.
