# 1. C# nullable reference types như một compile-time contract: giảm null bugs nhưng không biến runtime thành null-safe

## 1. What is it?

Nullable Reference Types (NRT) là cơ chế phân tích tĩnh của C# để biểu diễn intent: một reference được mong đợi là non-null hay có thể null.

Mental model:

```text
string   → contract: nên có value
string?  → contract: có thể null
```

NRT không thay đổi CLR type system theo cách làm `string` không thể nhận `null` ở runtime. Nó chủ yếu cung cấp compiler warnings và metadata annotation để tooling hiểu nullability contract.

## 2. Why does it exist?

Trong codebase lớn, phần lớn null bugs không đến từ syntax mà từ contract mơ hồ giữa layers:

```text
Repository trả null?
Service có check không?
DTO field có bắt buộc không?
External API có thể thiếu property không?
```

Trước NRT, developer phải tự nhớ hoặc dựa vào documentation. NRT đưa assumption đó vào type annotation và compiler flow analysis.

## 3. How does it work?

Compiler theo dõi null-state của variable qua control flow:

```csharp
string? name = GetName();

if (name is not null)
{
    Console.WriteLine(name.Length); // safe theo flow analysis
}
```

Nếu code dereference một `string?` mà chưa chứng minh non-null, compiler cảnh báo.

`!` null-forgiving operator chỉ tắt warning:

```csharp
Console.WriteLine(name!.Length);
```

Nó không thêm runtime check. Nếu `name` thật sự null, vẫn có `NullReferenceException`.

## 4. Practical implementation

DTO input:

```csharp
public sealed record CreateCustomerRequest(
    string Name,
    string? MiddleName,
    string Email);
```

Application service nên validate runtime input riêng:

```csharp
if (string.IsNullOrWhiteSpace(request.Name))
{
    return Results.ValidationProblem(new Dictionary<string, string[]>
    {
        ["name"] = ["Name is required."]
    });
}
```

NRT mô tả compile-time contract; model validation/business validation vẫn xử lý dữ liệu runtime.

## 5. Real production scenario

Một legacy API trả `Customer.Email` đôi khi null nhưng C# model khai báo `string`. Team bật NRT rồi dùng `!` hàng loạt để dọn warnings nhanh.

Code compile sạch, nhưng production vẫn gặp `NullReferenceException` khi downstream gọi `Email.ToLowerInvariant()`.

Bài học: warning suppression không sửa data contract.

## 6. Failure scenario & troubleshooting

**Symptom** → production vẫn có null exception dù project bật `<Nullable>enable</Nullable>`.

**Evidence** → stack trace đi qua property được annotate non-null nhưng deserialize từ external/legacy data.

**Hypothesis** → compile-time annotation không khớp runtime reality.

**Diagnosis** → kiểm tra serializer, database nullability, external contract và chỗ dùng `!`.

**Fix** → sửa model thành nullable nơi dữ liệu thật sự nullable, thêm validation ở boundary, migrate dữ liệu nếu business rule yêu cầu non-null.

**Verification** → thêm integration tests với null payload/data row thực tế.

## 7. Common mistakes

* Dùng `!` như một cách “fix null”.
* Nghĩ `string` không bao giờ nhận null ở runtime.
* Annotate mọi thứ `string?` để hết warnings, làm contract mất giá trị.
* Không align database schema, JSON contract và C# nullability.

## 8. Alternatives

Guard clauses, validation libraries và Option/Maybe abstractions vẫn hữu ích cho runtime/business semantics. NRT không thay thế chúng.

Trong domain model phức tạp, Value Object hoặc factory method có thể đảm bảo invariant mạnh hơn chỉ nullability annotation.

## 9. Trade-offs

### Advantages

* Bắt nhiều lỗi sớm ở compile time.
* Làm API contract rõ hơn.
* Hỗ trợ refactoring và tooling tốt hơn.

### Costs / Risks

* Migration legacy code có nhiều warnings.
* Annotation sai tạo false confidence.
* External data vẫn có thể vi phạm contract runtime.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác biệt giữa `string` và `string?` như intent của contract.

### Middle

Biết dùng flow analysis, guard clause và tránh abuse `!`.

### Senior

Biết align nullability giữa API, domain, persistence và external integrations.

### Technical Lead / Architect

Quyết định migration strategy cho legacy code, nơi nào compiler contract đủ và nơi nào cần stronger invariant/runtime validation.

## 11. Key takeaway

* NRT là compile-time safety net, không phải runtime guarantee.
* `!` tắt cảnh báo chứ không loại null.
* Nullability có giá trị nhất khi phản ánh đúng contract xuyên các layers.

# 2. ASP.NET Core Rate Limiting: bảo vệ dependency và fairness thay vì chỉ chặn request theo số lượng

## 1. What is it?

Rate limiting kiểm soát lượng work một client, user, tenant hoặc endpoint được phép tạo trong một khoảng thời gian hay tại một thời điểm.

Mental model đúng không phải chỉ là:

```text
100 requests/minute
```

mà là:

```text
incoming demand
      ↓
rate/concurrency policy
      ↓
capacity system có thể xử lý an toàn
```

## 2. Why does it exist?

Không có limiter, một tenant lỗi hoặc bot có thể tiêu thụ connection pool, CPU, external API quota hoặc database throughput và kéo mọi tenant khác xuống.

Autoscaling không giải quyết mọi trường hợp, đặc biệt khi bottleneck nằm ở database hoặc third-party dependency có quota cố định.

## 3. How does it work?

ASP.NET Core hỗ trợ nhiều limiter concepts như fixed window, sliding window, token bucket và concurrency limiter.

Ví dụ token bucket phù hợp khi muốn cho phép burst nhỏ nhưng kiểm soát sustained rate.

```text
Tokens refill theo thời gian
Request cần token
Có token  → đi tiếp
Hết token → reject/queue
```

Partitioned limiter có thể tạo bucket riêng theo user/tenant thay vì một global bucket.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("per-user", context =>
    {
        var userId = context.User.Identity?.Name ?? "anonymous";

        return RateLimitPartition.GetTokenBucketLimiter(
            userId,
            _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 20,
                TokensPerPeriod = 10,
                ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                AutoReplenishment = true,
                QueueLimit = 0
            });
    });

    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});

app.UseRateLimiter();
```

Endpoint:

```csharp
app.MapPost("/api/search", HandleSearch)
   .RequireRateLimiting("per-user");
```

## 5. Real production scenario

Search API gọi Elasticsearch và một enrichment API tính phí theo request. Một customer import script vô tình gửi 2,000 requests/second.

API instances vẫn còn CPU nhưng Elasticsearch thread pool queue tăng và external quota bị cạn. Per-tenant limiter giữ tenant lỗi trong budget mà không chặn toàn hệ thống.

## 6. Failure scenario & troubleshooting

**Symptom** → toàn bộ users nhận p99 cao trong khi traffic spike đến chủ yếu từ một tenant.

**Evidence** → request metrics theo tenant cho thấy skew lớn; downstream saturation trùng thời gian.

**Hypothesis** → thiếu fairness/capacity control.

**Diagnosis** → xác định bottleneck thật: CPU, SQL, Elasticsearch, external quota hay concurrent connections.

**Fix** → chọn limiter theo resource cần bảo vệ, partition theo identity phù hợp.

**Verification** → load test với noisy tenant; healthy tenants vẫn giữ SLO.

## 7. Common mistakes

* Rate limit theo IP khi traffic đi qua proxy/NAT mà không hiểu forwarded headers.
* Dùng một global limit khiến một tenant làm mọi tenant khác bị 429.
* Chọn con số tùy ý không liên hệ với downstream capacity.
* Queue quá nhiều requests trong limiter, chỉ đổi overload thành latency backlog.

## 8. Alternatives

API Gateway, Azure Front Door, reverse proxy hoặc external API management layer có thể rate limit trước application.

Concurrency limiter thường hợp lý hơn request-rate limiter khi resource bottleneck là số operations đồng thời.

## 9. Trade-offs

### Advantages

* Bảo vệ downstream dependencies.
* Tạo fairness giữa clients/tenants.
* Giảm blast radius của buggy clients.

### Costs / Risks

* Policy sai có thể chặn legitimate traffic.
* Distributed deployments cần hiểu limiter state scope.
* Rate limiting thêm contract 429/retry behavior cho clients.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 429 nghĩa là request bị giới hạn bởi policy capacity, không phải generic server error.

### Middle

Biết configure limiter, partition key và response behavior.

### Senior

Biết chọn algorithm dựa trên burst, concurrency và downstream saturation.

### Technical Lead / Architect

Định nghĩa capacity budget xuyên edge, API, database và external dependencies; quyết định limiter nằm ở đâu để blast radius nhỏ nhất.

## 11. Key takeaway

* Rate limiting là capacity-control mechanism.
* Partition key quan trọng ngang con số limit.
* Đừng queue overload vô hạn; overload cần bị shed có chủ đích.

# 3. EF Core split queries: tránh cartesian explosion khi `Include` nhiều collection nhưng không đánh đổi consistency một cách vô thức

## 1. What is it?

Split query cho phép EF Core load một object graph bằng nhiều SQL queries thay vì một query join khổng lồ.

Ví dụ:

```csharp
var orders = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .ToListAsync(ct);
```

Mental model:

```text
Single query:
Orders × Items × Payments

Split query:
Orders
Items for Orders
Payments for Orders
```

## 2. Why does it exist?

Khi include nhiều sibling collections, relational join có thể tạo cartesian multiplication.

Một order có 20 items và 10 payments có thể tạo 200 joined rows chỉ để materialize một aggregate graph. Nếu có thêm collection khác, row count tăng rất nhanh.

## 3. How does it work?

Single-query mode gửi một SQL statement với joins. EF Core deduplicate entities trong materialization.

Split-query mode gửi query root trước, sau đó query từng collection liên quan và ghép object graph phía client.

Đổi lại, multiple round trips và consistency window xuất hiện: data có thể thay đổi giữa query 1 và query 2 nếu không dùng transaction isolation phù hợp.

## 4. Practical implementation

```csharp
var result = await db.Projects
    .AsNoTracking()
    .Where(x => x.Status == ProjectStatus.Active)
    .Include(x => x.Tasks)
    .Include(x => x.Tags)
    .AsSplitQuery()
    .ToListAsync(ct);
```

Trước khi dùng `Include`, hãy hỏi liệu projection có tốt hơn:

```csharp
var result = await db.Projects
    .Where(x => x.Status == ProjectStatus.Active)
    .Select(x => new ProjectSummary(
        x.Id,
        x.Title,
        x.Tasks.Count,
        x.Tags.Select(t => t.Name).ToArray()))
    .ToListAsync(ct);
```

## 5. Real production scenario

Admin endpoint load 200 projects, mỗi project có tasks, tags và members. Một single join trả hơn 100,000 rows, network payload tăng mạnh, EF materialization tốn CPU và memory.

`AsSplitQuery()` giảm duplication đáng kể. Sau đó team còn tối ưu thêm bằng projection vì UI thực tế không cần full entity graph.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL duration vừa phải nhưng API memory và response latency cao.

**Evidence** → generated SQL có nhiều collection joins; row count lớn hơn entity count hàng trăm lần.

**Hypothesis** → cartesian explosion/materialization overhead.

**Diagnosis** → inspect SQL, result rows và allocation profile.

**Fix** → projection hoặc split query tùy use case.

**Verification** → so logical reads, rows transferred, allocations và p95 latency.

## 7. Common mistakes

* Dùng `AsSplitQuery()` như universal performance fix.
* Quên rằng nhiều queries có consistency window.
* Load full graph chỉ vì navigation tồn tại.
* Đo query time nhưng không đo network/materialization cost.

## 8. Alternatives

Projection thường là lựa chọn tốt nhất cho read API vì chỉ lấy fields cần thiết.

Explicit loading phù hợp khi application chỉ cần related data trong một số branch cụ thể.

## 9. Trade-offs

### Advantages

* Tránh duplicate rows do multiple collection joins.
* Có thể giảm memory và materialization overhead mạnh.

### Costs / Risks

* Tăng số round trips.
* Snapshot giữa queries có thể không hoàn toàn đồng nhất.
* Với latency network cao, split quá nhiều query có thể chậm hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` không miễn phí và có thể tạo nhiều SQL rows hơn số entities nhìn thấy.

### Middle

Biết đọc generated SQL, dùng projection và `AsSplitQuery()` có chủ đích.

### Senior

Đánh giá round trips, isolation, materialization và data shape.

### Technical Lead / Architect

Đặt read-model strategy rõ ràng thay vì để entity graph quyết định API query shape.

## 11. Key takeaway

* Multiple `Include` collections có thể tạo cartesian explosion.
* Split query đổi duplication lấy round trips và consistency considerations.
* Projection vẫn thường là baseline tốt cho read endpoints.

# 4. PostgreSQL MVCC và VACUUM: vì sao reader ít block writer nhưng dead tuples vẫn có chi phí thật

## 1. What is it?

PostgreSQL dùng Multi-Version Concurrency Control (MVCC) để nhiều transactions nhìn các versions khác nhau của một row tùy snapshot.

Một `UPDATE` thường không overwrite tuple tại chỗ theo mental model đơn giản; nó tạo row version mới và version cũ trở thành dead tuple khi không transaction nào còn cần nó.

## 2. Why does it exist?

Nếu readers và writers luôn khóa lẫn nhau, concurrency của OLTP workload sẽ giảm mạnh.

MVCC cho phép reader tiếp tục đọc snapshot phù hợp trong khi writer tạo version mới, giảm nhiều dạng reader-writer blocking.

## 3. How does it work?

Simplified flow:

```text
Row v1
Transaction A đọc v1
Transaction B UPDATE → tạo v2
A vẫn thấy v1 theo snapshot
Transaction mới thấy v2
```

Khi v1 không còn visible với transaction nào, VACUUM có thể reclaim space metadata/tuple để PostgreSQL tái sử dụng.

Autovacuum là operational component rất quan trọng, không phải housekeeping tùy chọn.

## 4. Practical implementation

Theo dõi dead tuples:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Query dài giữ old snapshot có thể làm cleanup chậm. Cần kiểm tra long-running transactions:

```sql
SELECT pid, xact_start, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

## 5. Real production scenario

Một SaaS audit table nhận hàng triệu updates. Autovacuum không theo kịp vì table rất write-heavy và một reporting transaction giữ snapshot lâu.

Table/index bloat tăng, I/O tăng và queries dần chậm dù application code không thay đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → database size và read I/O tăng, query latency xấu dần.

**Evidence** → `n_dead_tup` cao, autovacuum delay, long-running transaction tồn tại hàng giờ.

**Hypothesis** → dead tuple accumulation/bloat.

**Diagnosis** → kiểm tra vacuum stats, transaction age, table/index size và execution plans.

**Fix** → xử lý long transaction, tune autovacuum theo workload, maintenance khi cần.

**Verification** → dead tuples giảm, I/O/latency trở lại baseline.

## 7. Common mistakes

* Nghĩ MVCC nghĩa là “không có locks”. Writers vẫn có thể block writers và DDL vẫn có locking implications.
* Disable autovacuum để giảm background load.
* Giữ transaction mở quanh user interaction hoặc network calls.
* Chỉ nhìn CPU mà bỏ qua bloat/I/O.

## 8. Alternatives

SQL Server dùng locking-based `READ COMMITTED` mặc định hoặc row-versioning variants như RCSI/Snapshot Isolation. Cơ chế khác nhau nhưng cùng trade-off giữa concurrency, version storage và cleanup.

## 9. Trade-offs

### Advantages

* Read concurrency tốt.
* Ít reader-writer blocking hơn nhiều mô hình locking trực tiếp.

### Costs / Risks

* Row versions tạo storage/maintenance overhead.
* VACUUM và transaction age trở thành operational concerns.
* Bloat có thể âm thầm làm performance xấu dần.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một row có thể tồn tại nhiều versions theo transaction visibility.

### Middle

Biết đọc `pg_stat_user_tables` và tránh transaction mở quá lâu.

### Senior

Điều tra bloat, autovacuum pressure và lock/transaction interactions.

### Technical Lead / Architect

Thiết kế workload, retention, reporting boundaries và database operating model phù hợp với write volume.

## 11. Key takeaway

* MVCC giảm blocking nhưng không loại concurrency cost.
* Dead tuples cần được vacuum.
* Long-running transactions có thể trở thành production performance problem dù không dùng nhiều CPU.

# 5. Modular Monolith boundaries: giữ deployment đơn giản mà vẫn cô lập domain ownership và dependency direction

## 1. What is it?

Modular Monolith là một application deploy như một unit nhưng nội bộ chia thành các modules có boundaries rõ ràng theo business capability.

```text
Single deployment
┌────────────────────────────┐
│ Orders │ Billing │ Catalog │
└────────────────────────────┘
```

Điểm cốt lõi là ownership, dependency và data boundary — không phải chỉ tạo nhiều folders/projects.

## 2. Why does it exist?

Một monolith không có boundary thường biến thành shared database + shared services + cross-module calls tùy ý. Thay đổi một feature có blast radius khó đoán.

Microservices giải quyết một số isolation problems nhưng thêm network, deployment, observability, eventual consistency và operational complexity.

Modular Monolith giữ runtime đơn giản khi team/scale chưa cần independent deployment.

## 3. How does it work?

Mỗi module nên expose contract rõ ràng:

```text
Orders
 ├─ Application
 ├─ Domain
 ├─ Infrastructure
 └─ Public Contracts

Billing không truy cập Orders tables/classes nội bộ trực tiếp.
```

Cross-module interaction có thể qua in-process application contracts hoặc domain/integration events, tùy coupling cần thiết.

Data có thể cùng physical database nhưng ownership schema/table vẫn phải rõ.

## 4. Practical implementation

Ví dụ solution:

```text
src/
  Host/
  Modules/
    Orders/
      Orders.Application/
      Orders.Domain/
      Orders.Infrastructure/
      Orders.Contracts/
    Billing/
      Billing.Application/
      Billing.Domain/
      Billing.Infrastructure/
      Billing.Contracts/
```

Billing reference `Orders.Contracts`, không reference `Orders.Infrastructure`.

Architecture test có thể enforce dependency:

```csharp
var result = Types.InAssembly(typeof(BillingModule).Assembly)
    .ShouldNot()
    .HaveDependencyOn("Orders.Infrastructure")
    .GetResult();
```

## 5. Real production scenario

Một SaaS có Tasks, Documents, Notifications và Finance. Ban đầu chỉ 6 developers và một deployment pipeline.

Tách thành microservices ngay sẽ tạo 4 pipelines, messaging, tracing, retries và distributed data consistency trước khi có nhu cầu scale độc lập.

Modular Monolith cho phép team giữ một deployable nhưng ngăn Finance query trực tiếp tables của Tasks.

## 6. Failure scenario & troubleshooting

**Symptom** → thay đổi schema Orders làm Billing test fail dù hai modules không có business coupling rõ.

**Evidence** → Billing query trực tiếp Orders tables hoặc reference internal entity classes.

**Hypothesis** → module boundary bị xuyên thủng.

**Diagnosis** → dependency graph + SQL access ownership review.

**Fix** → expose explicit contract/read API nội bộ hoặc event/read model phù hợp.

**Verification** → architecture tests và module-level integration tests.

## 7. Common mistakes

* Gọi codebase là Modular Monolith chỉ vì có folders modules.
* Dùng một generic repository/shared service cho mọi module, tạo coupling trung tâm.
* Cho mọi module sở hữu chung tables không rõ ownership.
* Tạo event-driven internal architecture quá phức tạp dù direct in-process call là đủ.

## 8. Alternatives

Layered monolith phù hợp hơn cho domain nhỏ, ít boundary và team nhỏ.

Microservices đáng cân nhắc khi cần independent deployment, scale, ownership hoặc failure isolation thực sự.

## 9. Trade-offs

### Advantages

* Một deployment, debugging và transaction model đơn giản.
* Boundaries tốt hơn monolith tùy ý.
* Có đường tiến hóa sang services nếu cần.

### Costs / Risks

* Boundary phải được enforce bằng code review/tests.
* Process crash vẫn ảnh hưởng toàn application.
* Independent scaling/deployment chưa có.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business boundary, không chỉ folder.

### Middle

Biết giữ dependency đúng chiều và dùng public contract.

### Senior

Thiết kế data ownership, transaction boundary và cross-module communication.

### Technical Lead / Architect

Quyết định khi nào một module nên vẫn in-process và khi nào operational pressure đủ lớn để tách service.

## 11. Key takeaway

* Modular Monolith tối ưu simplicity mà vẫn giữ boundaries.
* Shared process không đồng nghĩa shared ownership.
* Chỉ tách microservice khi independent operation mang giá trị thật.

# 6. Azure Blob Storage SAS: cấp quyền truy cập giới hạn mà không biến storage account key thành shared secret toàn hệ thống

## 1. What is it?

Shared Access Signature (SAS) là token ủy quyền giới hạn cho Azure Storage, có thể scope theo resource, permissions và thời gian.

Thay vì đưa storage account key cho client, backend có thể cấp quyền upload một blob cụ thể trong vài phút.

## 2. Why does it exist?

Nếu browser upload file qua API server, application phải proxy toàn bộ bytes:

```text
Browser → API → Blob Storage
```

Điều này tăng bandwidth, memory/streaming complexity và scale cost ở application.

Direct upload:

```text
Browser → Blob Storage
```

hiệu quả hơn, nhưng client cần authorization giới hạn. SAS giải quyết boundary đó.

## 3. How does it work?

Backend authenticate user, authorize business action, rồi tạo SAS chỉ cho blob path được phép:

```text
User
 ↓ authenticated request
API
 ↓ generate short-lived SAS
Client
 ↓ PUT blob using SAS
Blob Storage
```

SAS không thay business authorization; nó là delegated storage permission sau khi application đã quyết định user được phép làm gì.

## 4. Practical implementation

Preferred architecture trên Azure là backend dùng Managed Identity/User Delegation SAS thay vì account key khi phù hợp.

Conceptual C# flow:

```csharp
var blobClient = containerClient.GetBlobClient(blobName);

// Application first validates tenant/user ownership.
// Then create a short-lived scoped SAS for write only.
```

SAS nên giới hạn:

```text
resource = one blob
permission = write/create
expiry = short
protocol = HTTPS
```

## 5. Real production scenario

Document SaaS cho user upload 500 MB video attachment. Proxy qua App Service làm instances chịu outbound/inbound bandwidth lớn và request duration dài.

Backend chuyển sang issue upload SAS 10 phút. Browser upload trực tiếp Blob Storage; API chỉ lưu metadata sau khi xác nhận upload hoàn tất.

## 6. Failure scenario & troubleshooting

**Symptom** → file upload bị 403 dù user đã login.

**Evidence** → Blob response cho biết SAS expired hoặc permission/resource mismatch.

**Hypothesis** → SAS scope/time skew không đúng.

**Diagnosis** → kiểm tra expiry/start time, blob path, permission, clock và storage logs.

**Fix** → tạo token với scope chính xác và time window có tolerance hợp lý.

**Verification** → upload đúng blob thành công; thử blob khác phải fail.

## 7. Common mistakes

* Gửi storage account key xuống frontend.
* SAS có expiry hàng ngày/tháng dù chỉ dùng cho một upload.
* Scope cả container với write/delete khi chỉ cần create một blob.
* Tin file chỉ vì upload thành công; vẫn cần content validation/malware workflow khi domain yêu cầu.

## 8. Alternatives

Proxy upload qua API đơn giản hơn cho file nhỏ hoặc cần synchronous inspection.

Backend worker có thể nhận file qua controlled ingestion pipeline khi compliance yêu cầu scan trước khi lưu final location.

## 9. Trade-offs

### Advantages

* Giảm load application server.
* Permission có thể scope nhỏ và time-bound.
* Scale file transfer tốt hơn.

### Costs / Risks

* Client flow phức tạp hơn.
* Cần lifecycle cho incomplete uploads.
* Leaked SAS vẫn usable cho tới expiry trong scope của nó.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SAS là quyền tạm thời giới hạn, không phải account credential đầy đủ.

### Middle

Biết issue short-lived blob-scoped SAS và xử lý upload flow.

### Senior

Thiết kế Managed Identity, validation, lifecycle và audit.

### Technical Lead / Architect

Quyết định direct-vs-proxy upload dựa trên security, compliance, file size, cost và ownership.

## 11. Key takeaway

* Không chia sẻ account key cho clients.
* SAS nên least-privilege và short-lived.
* Storage authorization không thay business authorization.

# 7. Docker multi-stage build cho .NET: giảm image surface, size và supply-chain exposure trong production

## 1. What is it?

Multi-stage build dùng một image để compile/publish application và một image khác nhỏ hơn để chạy artifact production.

```text
SDK image → restore/build/publish
                 ↓
runtime image ← published output only
```

Production image không cần compiler, NuGet cache hay source code.

## 2. Why does it exist?

Nếu deploy nguyên SDK image, image lớn hơn và chứa nhiều tools/packages không cần runtime. Điều này tăng download time, patch surface và số thành phần có thể bị khai thác.

Build environment và runtime environment có mục đích khác nhau nên nên tách.

## 3. How does it work?

Docker tạo layers theo stage. Final stage chỉ copy output từ build stage:

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish MyApi.csproj -c Release -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

Chỉ `final` stage trở thành deployable image mặc định.

## 4. Practical implementation

Tối ưu cache bằng cách copy project files trước source files:

```dockerfile
COPY MyApi.csproj ./
RUN dotnet restore MyApi.csproj
COPY . .
RUN dotnet publish MyApi.csproj -c Release -o /app/publish --no-restore
```

Khi source thay đổi nhưng dependencies không đổi, restore layer có thể được reuse.

## 5. Real production scenario

CI build 40 services. Mỗi SDK-based image gần 1 GB. Cluster rolling deployment phải pull nhiều GB mỗi release.

Chuyển sang runtime-only final images giảm đáng kể image size, rollout nhanh hơn và vulnerability scanner bớt findings từ build-only tooling.

## 6. Failure scenario & troubleshooting

**Symptom** → container chạy local SDK image được nhưng runtime image crash vì thiếu native library/timezone package.

**Evidence** → startup log có missing shared library.

**Hypothesis** → application có runtime OS dependency không tồn tại trong base image final.

**Diagnosis** → inspect image, native dependencies và base distro.

**Fix** → chọn compatible runtime image hoặc cài đúng runtime package tối thiểu.

**Verification** → container smoke/integration test trên exact final image.

## 7. Common mistakes

* Copy toàn repository trước `dotnet restore`, làm cache invalidation liên tục.
* Dùng `latest` tag cho base image production mà không có update governance.
* Chạy container root khi không cần.
* Build/test một image nhưng deploy image khác chưa được kiểm chứng.

## 8. Alternatives

Framework-dependent deployment trên VM/IIS có thể đơn giản hơn khi platform không dùng containers.

Native AOT/self-contained có trade-offs khác về image/runtime dependency và compatibility.

## 9. Trade-offs

### Advantages

* Smaller image.
* Giảm attack surface.
* Tách build tools khỏi runtime.

### Costs / Risks

* Dockerfile phức tạp hơn.
* Base-image compatibility cần quản trị.
* Supply-chain scanning vẫn cần; image nhỏ không tự động an toàn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SDK image để build, runtime image để chạy.

### Middle

Biết viết multi-stage Dockerfile và tận dụng layer cache.

### Senior

Đánh giá native deps, non-root runtime, image scanning và reproducibility.

### Technical Lead / Architect

Chuẩn hóa base images, patch cadence, artifact provenance và deployment validation cho nhiều services.

## 11. Key takeaway

* Production image chỉ nên chứa những gì cần để chạy.
* Multi-stage build giảm size và attack surface nhưng không thay supply-chain governance.
* Test đúng final image sẽ deploy.

# 8. Testcontainers cho integration testing: dùng infrastructure thật có vòng đời kiểm soát thay vì mock database behavior

## 1. What is it?

Testcontainers khởi động Docker containers tạm thời cho dependency thật như PostgreSQL, SQL Server, Redis hoặc message broker trong integration tests.

Mental model:

```text
Test process
   ↓ start isolated container
Real database/broker
   ↓ execute test
Dispose container
```

## 2. Why does it exist?

Mocking repository không chứng minh LINQ translate đúng SQL, migration chạy được, transaction behavior đúng hay database constraint tồn tại.

Shared developer database thì dễ flaky vì state bị chia sẻ giữa tests/users.

Testcontainers tạo môi trường thật nhưng disposable và reproducible hơn.

## 3. How does it work?

Test fixture khởi động container, lấy dynamic connection string, configure application test host rồi chạy integration test.

Sau suite, container được dispose.

Isolation có thể ở mức container per suite, database per test class hoặc schema/transaction per test tùy cost và correctness.

## 4. Practical implementation

Ví dụ với PostgreSQL:

```csharp
public sealed class DatabaseFixture : IAsyncLifetime
{
    private readonly PostgreSqlContainer _postgres =
        new PostgreSqlBuilder()
            .WithImage("postgres:16")
            .Build();

    public string ConnectionString => _postgres.GetConnectionString();

    public Task InitializeAsync() => _postgres.StartAsync();
    public Task DisposeAsync() => _postgres.DisposeAsync().AsTask();
}
```

Sau đó chạy migrations trước tests và inject connection string vào `WebApplicationFactory`.

## 5. Real production scenario

Unit tests mock `IOrderRepository` đều pass, nhưng production deployment fail vì EF migration tạo unique index không hợp dữ liệu cũ.

Integration test chạy against real database image có thể phát hiện migration/constraint behavior trước release.

## 6. Failure scenario & troubleshooting

**Symptom** → tests flaky hoặc chậm bất thường trên CI.

**Evidence** → mỗi test start một database container, startup chiếm phần lớn duration.

**Hypothesis** → isolation strategy quá đắt.

**Diagnosis** → profile suite time và state dependencies.

**Fix** → reuse container theo test collection/suite nhưng reset state deterministic giữa tests.

**Verification** → repeated CI runs ổn định và duration giảm.

## 7. Common mistakes

* Biến mọi unit test thành container test.
* Reuse database state nhưng không reset, tạo order-dependent tests.
* Dùng database version khác production.
* Không test migrations, chỉ `EnsureCreated()`.

## 8. Alternatives

SQLite in-memory nhanh nhưng semantics có thể khác SQL Server/PostgreSQL.

Local shared database phù hợp cho manual development nhưng kém reproducible trong CI.

Pure mocks phù hợp cho domain/application behavior không phụ thuộc infrastructure semantics.

## 9. Trade-offs

### Advantages

* Fidelity cao hơn mocks.
* Reproducible infrastructure lifecycle.
* Phát hiện SQL/migration/serialization/network behavior thật.

### Costs / Risks

* Test chậm hơn unit tests.
* CI cần container runtime.
* Cần chiến lược seed/reset data rõ ràng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu unit test và integration test bảo vệ các loại rủi ro khác nhau.

### Middle

Biết dựng container fixture và test API/database thật.

### Senior

Thiết kế isolation, deterministic data và CI performance.

### Technical Lead / Architect

Xây test strategy theo risk: phần nào mock, phần nào cần real infrastructure, đâu là contract/E2E boundary.

## 11. Key takeaway

* Mock không chứng minh database thật hoạt động đúng.
* Real infrastructure tests cần isolation và lifecycle tốt.
* Dùng integration tests để bảo vệ integration risk, không thay toàn bộ unit tests.

# 9. Optimizely CMS content caching: cache đúng content boundary mà không làm editor publish xong nhưng user vẫn thấy nội dung cũ

## 1. What is it?

CMS caching lưu content hoặc rendered output để giảm số lần resolve content tree, repository access, personalization logic hoặc rendering work.

Trong Optimizely CMS, platform có caching behavior cho content, nhưng application vẫn phải hiểu boundary giữa content cache, output cache và CDN cache.

## 2. Why does it exist?

Marketing website thường có read-heavy workload: cùng Home Page được đọc hàng nghìn lần nhưng editor chỉ publish vài lần mỗi ngày.

Không cache, application lặp lại content lookup/rendering dù dữ liệu ít thay đổi.

Nhưng CMS có yêu cầu freshness cao sau publish, nên invalidation quan trọng hơn chỉ TTL.

## 3. How does it work?

Typical layers:

```text
Browser cache
   ↓
CDN / Akamai
   ↓
ASP.NET output cache
   ↓
Optimizely content cache
   ↓
Content store
```

Khi editor publish, content cache nội bộ có thể invalidate đúng content/version. Nhưng output/CDN caches ngoài CMS cần key/invalidation policy riêng.

## 4. Practical implementation

Không cache personalized response bằng key chỉ theo URL:

```text
/insights/article-a
```

nếu response phụ thuộc locale, authentication hoặc segment.

Cache key cần phản ánh variation thực sự, ví dụ:

```text
path + language + published-version + audience-variant
```

Với static/public pages, response caching/CDN có thể dùng `Cache-Control` phù hợp. Với editor preview, thường phải bypass public caching.

## 5. Real production scenario

Editor publish legal disclaimer mới. Optimizely content view trong CMS đã đúng nhưng public site qua CDN vẫn hiển thị bản cũ 30 phút.

Team ban đầu debug content repository nhưng root cause nằm ở edge cache TTL không được purge khi publish.

## 6. Failure scenario & troubleshooting

**Symptom** → editor thấy content mới, một số users vẫn thấy content cũ.

**Evidence** → origin trả bản mới nhưng CDN response có `Age` cao/cache hit.

**Hypothesis** → stale edge/output cache, không phải CMS database inconsistency.

**Diagnosis** → request trực tiếp origin, inspect cache headers, compare locale/auth variants.

**Fix** → purge/invalidate đúng layer hoặc thiết kế short TTL + versioned cache key.

**Verification** → publish test content và đo propagation đến origin/CDN/public clients.

## 7. Common mistakes

* Nói chung chung “Optimizely cache sai” mà không xác định layer.
* Cache preview/editor responses như public content.
* Cache personalized page theo URL duy nhất.
* Dùng TTL dài mà không có publish invalidation strategy.

## 8. Alternatives

Không cache application output nếu traffic nhỏ và CMS content cache đã đủ.

CDN-only caching có thể phù hợp cho site public/static-heavy. Output caching hữu ích khi origin rendering là bottleneck thật.

## 9. Trade-offs

### Advantages

* Giảm origin load và latency.
* Tăng khả năng chịu traffic spike.

### Costs / Risks

* Invalidation complexity.
* Risk stale hoặc cross-user content leakage nếu key sai.
* Nhiều cache layers làm troubleshooting khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CMS cache, output cache và CDN cache là các layers khác nhau.

### Middle

Biết inspect cache headers và bypass cache để localize stale layer.

### Senior

Thiết kế cache key theo locale/user/content version và publish invalidation.

### Technical Lead / Architect

Quyết định cache layer nào thực sự cần, freshness SLA và ownership giữa CMS/platform/CDN teams.

## 11. Key takeaway

* Stale content phải được localize theo cache layer.
* CMS publish không tự động đảm bảo mọi external cache đã invalidated.
* Cache key sai có thể là correctness/security bug, không chỉ performance bug.

# 10. Third-party webhook verification: xác thực nguồn, chống replay và thiết kế consumer idempotent khi external provider gửi lại event

## 1. What is it?

Webhook là HTTP callback từ external provider đến application khi event xảy ra. Vì endpoint thường public internet, application phải xác minh request thật sự đến từ provider và payload không bị sửa.

Phổ biến nhất là HMAC signature trên raw request body kèm timestamp.

## 2. Why does it exist?

Nếu endpoint chỉ tin JSON payload:

```json
{ "paymentId": "123", "status": "paid" }
```

attacker có thể tự POST payload giả và kích hoạt business side effect.

Ngoài authenticity, provider thường retry khi không nhận 2xx, nên duplicate delivery là behavior bình thường.

## 3. How does it work?

Flow:

```text
Provider
  ↓ payload + timestamp + signature
API
  ↓ verify HMAC using shared secret/public key
check timestamp tolerance
  ↓
deduplicate event id
  ↓
process business action
```

HMAC thường dạng:

```text
signature = HMAC(secret, timestamp + "." + raw_body)
```

Server tính lại signature và compare constant-time.

## 4. Practical implementation

Conceptual C#:

```csharp
var payload = await new StreamReader(request.Body).ReadToEndAsync();
var signed = $"{timestamp}.{payload}";

using var hmac = new HMACSHA256(secretBytes);
var expected = hmac.ComputeHash(Encoding.UTF8.GetBytes(signed));
var supplied = Convert.FromHexString(signatureHeader);

if (!CryptographicOperations.FixedTimeEquals(expected, supplied))
    return Results.Unauthorized();
```

Sau verification, persist provider event ID với unique constraint trước hoặc cùng business handling phù hợp để chống duplicate side effect.

## 5. Real production scenario

Payment provider gửi `payment.succeeded`. Application xử lý xong nhưng response 200 bị network timeout. Provider retry cùng event ID ba lần.

Nếu consumer không idempotent, hệ thống có thể cộng balance hoặc gửi fulfillment nhiều lần.

Signature verification chứng minh nguồn; idempotency xử lý duplicate delivery. Hai concern khác nhau.

## 6. Failure scenario & troubleshooting

**Symptom** → signature verification fail chỉ ở Production.

**Evidence** → provider dashboard cho thấy payload đúng nhưng server hash khác.

**Hypothesis** → middleware/parser đã normalize/deserialize body trước khi verify, hoặc secret/env sai.

**Diagnosis** → compare raw bytes, timestamp, header format và secret version.

**Fix** → verify đúng raw request representation theo provider spec; rotate/configure secret chính xác.

**Verification** → replay provider test fixture và invalid-signature tests.

## 7. Common mistakes

* Verify trên JSON re-serialized thay vì raw body nếu provider ký raw bytes.
* Chỉ kiểm signature nhưng không check timestamp, cho phép replay cũ nếu request bị lộ.
* Trust IP allowlist như authentication duy nhất.
* Process duplicate event nhiều lần.
* Trả 500 cho permanent validation errors khiến provider retry storm.

## 8. Alternatives

Một số providers dùng asymmetric signatures/public keys thay vì shared-secret HMAC.

Polling API có thể đơn giản hơn trong use case low-frequency nhưng tăng latency/quota usage và không loại nhu cầu authentication.

## 9. Trade-offs

### Advantages

* Xác minh authenticity/integrity của webhook.
* Timestamp giúp giảm replay window.
* Idempotency làm retry an toàn.

### Costs / Risks

* Secret rotation và signature-version compatibility cần quản trị.
* Raw-body handling có thể conflict với middleware nếu thiết kế kém.
* Cần event retention/deduplication policy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu webhook endpoint là public input và không được tin payload mặc định.

### Middle

Biết verify signature/timestamp và deduplicate event IDs.

### Senior

Thiết kế secret rotation, replay protection, retry classification và observability.

### Technical Lead / Architect

Định nghĩa integration contract: security boundary, idempotency semantics, failure recovery, reconciliation và ownership khi provider degraded.

## 11. Key takeaway

* Signature verification và idempotency giải quyết hai vấn đề khác nhau.
* Verify theo raw payload đúng provider contract.
* External provider retry phải được coi là normal system behavior.
