# 1. C# `Span<T>` và `Memory<T>`: giảm allocation trong hot path mà không phá safety boundary của managed memory

## 1. What is it?

`Span<T>` là một stack-only view trên một vùng memory liên tục. Nó không sở hữu dữ liệu; nó chỉ trỏ tới một slice của array, string, stack buffer hoặc unmanaged memory trong lifetime hợp lệ.

`Memory<T>` cũng biểu diễn một vùng memory nhưng có thể tồn tại qua asynchronous boundary vì nó là regular managed type, không phải `ref struct`.

Mental model:

```text
byte[] buffer
┌───────────────────────────────┐
│ header │ payload │ checksum   │
└───────────────────────────────┘
    ↑          ↑
  Span       Span
```

Bạn có thể parse từng phần mà không tạo `Substring`, `byte[]` mới hoặc intermediate object.

## 2. Why does it exist?

Code dễ viết thường tạo nhiều temporary allocation:

```csharp
var pieces = input.Split(':');
var id = pieces[0];
var value = pieces[1];
```

Trong request path ít traffic, chi phí này thường không đáng lo. Nhưng với parser, serializer, networking hoặc file-processing hot path, hàng triệu temporary allocations sẽ tăng GC pressure.

`Span<T>` tồn tại để xử lý dữ liệu theo view/slice thay vì copy.

## 3. How does it work?

`Span<T>` giữ reference tới vùng memory và length. Slice mới thường chỉ tạo một view mới:

```csharp
ReadOnlySpan<char> input = "12345:ACTIVE";
var separator = input.IndexOf(':');
var idPart = input[..separator];
var statusPart = input[(separator + 1)..];
```

Không có substring allocation ở đây.

Vì `Span<T>` có thể trỏ tới stack memory, compiler không cho phép nó escape scope, bị box, capture vào lambda hoặc sống qua `await`.

## 4. Practical implementation

```csharp
public static bool TryParseHeader(
    ReadOnlySpan<char> input,
    out int id,
    out ReadOnlySpan<char> status)
{
    var separator = input.IndexOf(':');
    if (separator <= 0)
    {
        id = default;
        status = default;
        return false;
    }

    if (!int.TryParse(input[..separator], out id))
    {
        status = default;
        return false;
    }

    status = input[(separator + 1)..];
    return true;
}
```

Nếu data cần đi qua asynchronous API, chuyển sang `ReadOnlyMemory<T>`:

```csharp
public async Task<int> SendAsync(
    ReadOnlyMemory<byte> payload,
    CancellationToken ct)
{
    await _stream.WriteAsync(payload, ct);
    return payload.Length;
}
```

## 5. Real production scenario

Một ingestion service parse hàng trăm nghìn telemetry records mỗi phút. Phiên bản đầu dùng `Split`, `Substring` và array copy ở nhiều bước. CPU chưa quá cao nhưng Gen 0 collection diễn ra liên tục và p99 latency tăng khi load burst.

Sau khi profile cho thấy allocation tập trung ở parser, team chuyển hot parsing path sang `ReadOnlySpan<char>`. Throughput tăng và GC pause giảm mà không cần scale thêm instances.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU và GC activity cao bất thường dù business logic đơn giản.

**Evidence** → allocation profile cho thấy nhiều short-lived strings/arrays từ parsing.

**Hypothesis** → excessive copying trong hot path.

**Diagnosis** → benchmark riêng parser, đo allocations/op trước và sau.

**Fix** → dùng span/slice có chọn lọc ở đoạn đã được chứng minh là bottleneck.

**Verification** → allocation rate và GC frequency giảm; throughput/latency được đo lại.

## 7. Common mistakes

* Dùng `Span<T>` mọi nơi chỉ vì “nhanh hơn”, làm code khó đọc mà không có số đo.
* Cố giữ `Span<T>` qua `await` và chống lại restriction của compiler.
* Chuyển mọi API sang `Memory<T>` dù không có performance reason.
* Bỏ qua lifetime/ownership khi buffer đến từ pool.

## 8. Alternatives

`string`, arrays và normal collections vẫn là lựa chọn đúng cho phần lớn application code. `ArrayPool<T>` hữu ích khi cần reusable large buffers. `SequenceReader<T>`/`ReadOnlySequence<T>` phù hợp hơn khi data không contiguous, ví dụ high-performance pipelines.

## 9. Trade-offs

### Advantages

Giảm copies, giảm allocation và GC pressure trong hot path; vẫn giữ nhiều safety guarantees của managed runtime.

### Costs / Risks

API khó đọc hơn, lifetime constraints phức tạp hơn và dễ tối ưu premature nếu không benchmark.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slice có thể chỉ là view chứ không phải copy dữ liệu.

### Middle

Biết dùng `ReadOnlySpan<T>` cho synchronous parsing và `ReadOnlyMemory<T>` cho async APIs.

### Senior

Biết profile allocation, hiểu ownership/lifetime và chỉ tối ưu đoạn có evidence.

### Technical Lead / Architect

Quyết định performance-sensitive boundary nào đáng dùng specialized memory APIs mà vẫn giữ maintainability cho toàn team.

## 11. Key takeaway

* `Span<T>` chủ yếu giải quyết copy/allocation trong hot path.
* `Memory<T>` dùng được qua async boundary; `Span<T>` thì không.
* Measure trước, tối ưu sau.

# 2. ASP.NET Core `ProblemDetails`: biến lỗi API thành contract ổn định thay vì rải `try/catch` và message tùy hứng

## 1. What is it?

`ProblemDetails` là representation chuẩn hóa cho HTTP API errors theo RFC 7807/9457-style problem detail semantics. Mental model không phải “object đẹp hơn cho exception”, mà là **error contract** giữa server và client.

Ví dụ:

```json
{
  "type": "https://api.example.com/problems/order-not-found",
  "title": "Order not found",
  "status": 404,
  "detail": "Order 123 does not exist.",
  "instance": "/orders/123"
}
```

## 2. Why does it exist?

Không có error contract, mỗi endpoint có thể trả khác nhau:

```json
{ "message": "Not found" }
```

hoặc:

```json
{ "error": true, "code": 12 }
```

hoặc plain string.

Client phải special-case từng endpoint. Logging, observability và backward compatibility cũng khó kiểm soát.

## 3. How does it work?

ASP.NET Core có thể centralize exception handling và map exception/domain error sang HTTP semantics:

```text
Domain/Application error
        ↓
Exception/Error mapping
        ↓
ProblemDetails
        ↓
HTTP 4xx/5xx
```

Điểm quan trọng là status code phải phản ánh semantics thật: validation thường `400`, unauthenticated `401`, forbidden `403`, resource missing `404`, conflict `409`, unexpected server error `500`.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();

app.UseExceptionHandler();
```

Custom mapping:

```csharp
public sealed class OrderNotFoundException(int id)
    : Exception($"Order {id} was not found");
```

Trong centralized handler:

```csharp
return Results.Problem(
    statusCode: StatusCodes.Status404NotFound,
    title: "Order not found",
    type: "https://api.example.com/problems/order-not-found",
    extensions: new Dictionary<string, object?>
    {
        ["code"] = "ORDER_NOT_FOUND"
    });
```

`detail` không nên chứa stack trace hoặc sensitive internals ở Production.

## 5. Real production scenario

Mobile app và web app dùng chung backend. Trước đây mobile parse `message` text để biết lỗi business. Một developer đổi wording tiếng Anh, mobile flow hỏng.

Sau khi API dùng stable machine-readable `code` và `type`, human-readable title/detail có thể thay đổi mà client vẫn xử lý đúng.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận 500 cho validation hoặc business conflict.

**Evidence** → trace cho thấy expected domain exception bị generic handler map hết thành 500.

**Hypothesis** → exception classification thiếu.

**Diagnosis** → kiểm tra mapping table và endpoint-specific `try/catch` đang bypass global handler.

**Fix** → centralize expected error mapping, giữ unexpected error ở 500.

**Verification** → contract tests cho status, `type`, `code` và schema.

## 7. Common mistakes

* Trả `200 OK` với `{ success:false }` cho mọi lỗi.
* Dùng exception text như machine-readable contract.
* Leak SQL, connection string, stack trace vào `detail`.
* Tạo hàng chục format error khác nhau vì mỗi team tự định nghĩa.

## 8. Alternatives

Một custom envelope có thể hợp lý nếu hệ thống legacy đã có contract ổn định. Nhưng custom format phải giải quyết cùng các vấn đề: status semantics, machine-readable code, validation errors, compatibility và observability.

## 9. Trade-offs

### Advantages

Contract nhất quán, dễ client integration, dễ documentation và test.

### Costs / Risks

Cần governance cho error taxonomy. Nếu biến mọi internal exception thành một `type` public, API có thể expose implementation detail và tạo compatibility burden không cần thiết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code và body cùng tạo nên error semantics.

### Middle

Biết centralize handling và trả `ProblemDetails` nhất quán.

### Senior

Thiết kế error taxonomy, security boundary và backward-compatible machine codes.

### Technical Lead / Architect

Xác định organization-wide API error contract và phân biệt public contract với internal diagnostic detail.

## 11. Key takeaway

* Error format là API contract, không chỉ coding style.
* Client không nên parse human-readable message để ra quyết định.
* Unexpected diagnostic detail phải ở telemetry, không ở response public.

# 3. EF Core execution strategy + explicit transaction: retry transient failure mà không vô tình chạy business transaction hai lần

## 1. What is it?

EF Core execution strategy có thể retry database operations khi gặp transient failure như network hiccup hoặc temporary unavailability. Nhưng khi developer tự mở explicit transaction, retry semantics cần được xem xét như một **đơn vị replay** chứ không chỉ retry từng SQL statement.

## 2. Why does it exist?

Cloud databases và network không đảm bảo mọi connection luôn thành công. Một lỗi transient không nhất thiết nghĩa operation phải fail vĩnh viễn.

Nhưng retry sai boundary tạo rủi ro:

```text
DB commit đã thành công
↓
network lỗi trước khi client nhận ACK
↓
application tưởng transaction fail
↓
retry toàn bộ business operation
```

Nếu operation không idempotent, duplicate side effect có thể xảy ra.

## 3. How does it work?

Khi bật retry provider-specific strategy, EF Core có thể replay operation được xem là retriable. Nếu dùng explicit transaction, toàn bộ transaction cần chạy bên trong execution strategy callback để EF có thể replay đúng scope.

```text
ExecutionStrategy.ExecuteAsync
    ↓
BeginTransaction
    ↓
DB operations
    ↓
Commit
```

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var transaction =
        await db.Database.BeginTransactionAsync(ct);

    var invoice = new Invoice(customerId, amount);
    db.Invoices.Add(invoice);

    db.OutboxMessages.Add(OutboxMessage.For(invoice));

    await db.SaveChangesAsync(ct);
    await transaction.CommitAsync(ct);
});
```

Không nên wrap một arbitrary business workflow có external HTTP call trong database retry callback nếu call đó không idempotent.

## 5. Real production scenario

Order API ghi order vào SQL và trong cùng application method gọi payment provider. Developer bọc toàn method bằng retry vì thỉnh thoảng SQL timeout.

Lần đầu payment thành công, sau đó SQL/network lỗi. Retry gọi payment lần hai. Database reliability fix biến thành financial correctness bug.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate external operations chỉ xảy ra trong thời điểm database/network instability.

**Evidence** → logs cho thấy cùng request correlation chạy handler nhiều lần từ retry policy.

**Hypothesis** → retry scope rộng hơn transaction-safe boundary.

**Diagnosis** → kiểm tra Polly/EF execution strategy nesting và external side effects bên trong callback.

**Fix** → thu hẹp retry vào database operation; dùng idempotency key/Outbox cho external side effect.

**Verification** → fault-injection test ở trước/sau commit và bảo đảm business effect không duplicate.

## 7. Common mistakes

* Nghĩ retry luôn an toàn vì exception là transient.
* Retry cả transaction có gửi email/payment/webhook trực tiếp.
* Nest nhiều retry layers tạo retry amplification.
* Không giới hạn attempts/backoff.

## 8. Alternatives

Nếu transaction chỉ có một `SaveChanges`, implicit transaction của EF Core thường đủ đơn giản. Với workflow cần external side effect, Outbox Pattern thường phù hợp hơn dual-write + retry.

## 9. Trade-offs

### Advantages

Tăng resilience trước transient database failure và giảm user-visible lỗi ngắn hạn.

### Costs / Risks

Replay làm semantics phức tạp; retry tăng latency và load khi dependency đang suy giảm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transient error khác permanent error.

### Middle

Biết dùng execution strategy theo provider và explicit transaction đúng pattern.

### Senior

Hiểu ambiguous commit, retry scope và idempotency.

### Technical Lead / Architect

Đặt retry policy theo boundary, tránh layered retry storm và tách transactional state khỏi remote side effect.

## 11. Key takeaway

* Retry là replay; replay phải có correctness semantics.
* Explicit transaction cần nằm trong execution strategy đúng cách.
* Không đặt non-idempotent remote side effects trong database retry scope.

# 4. Cosmos DB partition key + hot partition: scalability bắt đầu từ data distribution chứ không phải tăng Request Units vô hạn

## 1. What is it?

Partition key quyết định cách Cosmos DB phân phối items theo logical partitions và cuối cùng lên physical partitions. Nó ảnh hưởng trực tiếp tới scalability, query cost, transactional boundary và hot-spot risk.

Mental model:

```text
Partition key = TenantId

Tenant A ─┐
Tenant B ─┼─> distributed partitions
Tenant C ─┘
```

Nếu một giá trị key nhận phần lớn traffic, hệ thống có hot partition dù tổng RU/s còn cao.

## 2. Why does it exist?

Distributed database phải chia data và workload ra nhiều machines. Partition key là thông tin application cung cấp để database biết cách colocate và phân phối dữ liệu.

Một key “đúng về schema” nhưng sai về workload có thể phá scalability.

## 3. How does it work?

Queries có exact partition key thường được route trực tiếp tới partition phù hợp. Cross-partition queries phải fan out.

Transactions trong Cosmos DB bị giới hạn trong logical partition boundary. Vì vậy key vừa là distribution key vừa ảnh hưởng consistency/transaction design.

## 4. Practical implementation

Ví dụ multi-tenant SaaS:

```json
{
  "id": "task-123",
  "tenantId": "tenant-42",
  "projectId": "p-9",
  "title": "Prepare release"
}
```

Container dùng `/tenantId` nếu phần lớn access pattern là theo tenant và tenant distribution đủ cân bằng.

Repository/query nên luôn truyền partition key khi biết:

```csharp
var response = await container.ReadItemAsync<TaskDocument>(
    id,
    new PartitionKey(tenantId),
    cancellationToken: ct);
```

## 5. Real production scenario

Notification platform dùng `/status` làm partition key với giá trị `Pending`, `Sent`, `Failed`. Hầu hết write mới đều vào `Pending`, tạo một hot logical partition.

Team tăng provisioned RU/s nhưng vẫn thấy throttling ở cùng partition. Root cause là skewed distribution, không phải thiếu tổng throughput.

## 6. Failure scenario & troubleshooting

**Symptom** → `429 Too Many Requests` tăng dù overall RU utilization không chạm 100%.

**Evidence** → metrics cho thấy một partition/key range tiêu thụ phần lớn throughput.

**Hypothesis** → hot partition.

**Diagnosis** → phân tích cardinality, traffic distribution và top partition keys.

**Fix** → redesign key hoặc introduce hierarchical/composite distribution strategy phù hợp access pattern; migration cần kế hoạch vì partition key không phải field dễ đổi tại chỗ.

**Verification** → RU distribution cân bằng hơn, 429 giảm, cross-partition query cost không tăng bất ngờ.

## 7. Common mistakes

* Chọn low-cardinality key như `status`, `country` hoặc boolean.
* Chỉ nhìn data size mà bỏ qua write/read rate per key.
* Dùng random GUID để phân phối hoàn hảo nhưng phá query/transaction access pattern.
* Nghĩ autoscale sẽ sửa được hot key.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp hơn nếu workload phụ thuộc relational joins/transactions mạnh và scale requirements chưa buộc distributed storage.

MongoDB cũng có sharding key trade-offs tương tự ở mức kiến trúc.

## 9. Trade-offs

### Advantages

Partition key tốt cho phép horizontal scale, efficient routing và predictable transactional boundary.

### Costs / Risks

Key là quyết định khó thay đổi; tối ưu distribution có thể làm query phức tạp hoặc tăng duplication.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định data được nhóm/phân phối ở đâu.

### Middle

Biết truyền partition key trong point reads và tránh cross-partition query không cần thiết.

### Senior

Phân tích cardinality, skew, RU cost và transaction boundary.

### Technical Lead / Architect

Chọn key dựa trên workload thực, growth model và migration cost chứ không dựa trên field “trông hợp lý”.

## 11. Key takeaway

* Partition key là architecture decision, không phải mapping detail.
* Hot partition không được giải quyết chỉ bằng tăng RU.
* Distribution, query routing và transaction boundary phải được cân nhắc cùng nhau.

# 5. Hexagonal Architecture ports/adapters: cô lập domain khỏi framework và external systems mà không biến solution thành mê cung abstraction

## 1. What is it?

Hexagonal Architecture tổ chức hệ thống quanh business core. Core định nghĩa **ports** — interfaces/contract mà nó cần hoặc cung cấp. External technologies trở thành **adapters** thực thi các ports đó.

```text
          HTTP Adapter
              ↓
        Application Port
              ↓
           Domain
              ↑
      Persistence Port
              ↑
        EF Core Adapter
```

Architecture không phải folder naming. Mục tiêu là dependency direction và change isolation.

## 2. Why does it exist?

Nếu domain/application logic trực tiếp phụ thuộc EF Core, HTTP SDK, queue client và vendor-specific DTO, mỗi thay đổi infrastructure lan vào business logic.

Ports/adapters cho phép domain nói bằng language của business thay vì language của framework.

## 3. How does it work?

Core sở hữu abstraction mà nó cần:

```csharp
public interface IExchangeRateProvider
{
    Task<decimal> GetRateAsync(
        string from,
        string to,
        CancellationToken ct);
}
```

Infrastructure adapter implement bằng external API. Dependency trỏ vào core contract, không ngược lại.

Data ownership và transaction boundary vẫn phải rõ; interface không tự tạo architecture tốt.

## 4. Practical implementation

Application service:

```csharp
public sealed class PriceCalculator(IExchangeRateProvider rates)
{
    public async Task<Money> ConvertAsync(
        Money source,
        string targetCurrency,
        CancellationToken ct)
    {
        var rate = await rates.GetRateAsync(
            source.Currency,
            targetCurrency,
            ct);

        return new Money(source.Amount * rate, targetCurrency);
    }
}
```

Infrastructure:

```csharp
public sealed class HttpExchangeRateProvider(HttpClient http)
    : IExchangeRateProvider
{
    public async Task<decimal> GetRateAsync(
        string from,
        string to,
        CancellationToken ct)
    {
        var dto = await http.GetFromJsonAsync<RateDto>(
            $"rates/{from}/{to}", ct);

        return dto!.Rate;
    }
}
```

## 5. Real production scenario

Commerce system ban đầu dùng Provider A cho reviews. Sau hai năm chuyển Provider B. Nếu domain model, controllers và business rules dùng trực tiếp Provider A DTO ở mọi nơi, migration thành cross-cutting rewrite.

Nếu integration được đặt sau một domain/application port, thay đổi chủ yếu nằm ở adapter và anti-corruption mapping.

## 6. Failure scenario & troubleshooting

**Symptom** → thay một third-party SDK kéo theo sửa hàng chục business classes.

**Evidence** → vendor types xuất hiện trong domain/application projects.

**Hypothesis** → dependency boundary bị xuyên thủng.

**Diagnosis** → dependency graph và namespace references.

**Fix** → tạo business-facing contract ở boundary có giá trị thật; map vendor DTO tại adapter.

**Verification** → core compile/test mà không reference vendor package.

## 7. Common mistakes

* Tạo interface cho mọi class kể cả khi không có boundary/change reason.
* Generic repository chỉ để “đúng Hexagonal”.
* Biến ports thành mirror 1:1 của vendor API, nên vẫn coupled semantics.
* Quá nhiều layers cho CRUD app rất đơn giản.

## 8. Alternatives

Layered Architecture đơn giản thường đủ cho nhỏ/medium CRUD systems. Modular Monolith có thể kết hợp với Hexagonal boundaries ở các modules phức tạp thay vì áp toàn solution đồng đều.

## 9. Trade-offs

### Advantages

Giảm framework/vendor coupling, dễ test business behavior và thay external technology.

### Costs / Risks

Thêm interfaces, mapping và cognitive overhead. Nếu boundary không có volatility hoặc business meaning, abstraction trở thành ceremony.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu business logic không nhất thiết phải biết EF Core/HTTP vendor types.

### Middle

Biết đặt interface ở layer sở hữu use case và implement adapter ngoài core.

### Senior

Phân biệt useful boundary với abstraction vô nghĩa; quản lý transaction/data ownership.

### Technical Lead / Architect

Quyết định chỗ nào cần ports/adapters dựa trên change frequency, integration risk và domain complexity.

## 11. Key takeaway

* Hexagonal Architecture là dependency boundary, không phải folder template.
* Core nên nói bằng business contract, không phải vendor DTO.
* Không phải mọi CRUD service đều cần đầy đủ ports/adapters ceremony.

# 6. Timeout budget propagation trong distributed systems: tránh mỗi layer tự chờ 30 giây rồi cộng dồn thành outage

## 1. What is it?

Timeout budget là tổng thời gian một request/workflow được phép tiêu thụ. Thay vì mỗi dependency tự có timeout độc lập không liên quan, downstream calls phải tôn trọng remaining budget của upstream request.

```text
Client budget: 2s
API processing: 100ms
DB: 300ms
External API: còn ~1.6s
```

## 2. Why does it exist?

Naive setup:

```text
Gateway timeout 30s
API A timeout tới B 30s
B timeout tới C 30s
```

Khi C treo, work có thể tích tụ sâu trong system. Requests mà client đã bỏ cuộc vẫn chiếm threads, connections và queue slots.

## 3. How does it work?

Budget bắt đầu ở ingress. Mỗi layer tiêu thụ một phần và propagate cancellation/deadline xuống dưới.

Timeout phải phối hợp với retries: nếu total budget 2 giây, ba retries mỗi lần timeout 2 giây là logic sai.

## 4. Practical implementation

ASP.NET Core:

```csharp
public async Task<IResult> GetQuote(
    CancellationToken requestAborted)
{
    using var budget = CancellationTokenSource
        .CreateLinkedTokenSource(requestAborted);

    budget.CancelAfter(TimeSpan.FromSeconds(2));

    var quote = await _quotes.GetAsync(budget.Token);
    return Results.Ok(quote);
}
```

HttpClient:

```csharp
using var request = new HttpRequestMessage(
    HttpMethod.Get,
    "/pricing/current");

using var response = await _http.SendAsync(
    request,
    HttpCompletionOption.ResponseHeadersRead,
    ct);
```

Tránh vừa có `HttpClient.Timeout` rất lớn vừa bỏ qua request cancellation.

## 5. Real production scenario

Checkout gọi inventory, promotion và tax APIs. Tax provider chậm 15 giây. Front Door/client timeout ở 5 giây nhưng backend vẫn giữ hàng nghìn in-flight calls thêm 10 giây.

Connection pool cạn và requests khỏe cũng bắt đầu fail. Một dependency chậm lan thành full-system outage.

## 6. Failure scenario & troubleshooting

**Symptom** → downstream connection count tăng sau khi client timeout; latency tail kéo dài.

**Evidence** → traces cho thấy child spans sống lâu hơn parent request.

**Hypothesis** → cancellation/deadline không propagate.

**Diagnosis** → kiểm tra `CancellationToken.None`, SDK timeout và retry duration.

**Fix** → linked token/deadline propagation, per-call budget và retry policy nằm trong total budget.

**Verification** → fault injection dependency latency; child operations phải dừng khi parent budget hết.

## 7. Common mistakes

* Set timeout giống nhau cho mọi dependency.
* Retry sau timeout mà không xét remaining budget.
* Catch `OperationCanceledException` rồi retry như transient failure bình thường.
* Không phân biệt client cancellation và server-side timeout trong telemetry.

## 8. Alternatives

Asynchronous messaging phù hợp hơn nếu business operation không cần synchronous completion. Queue chuyển latency coupling thành eventual completion, nhưng thêm consistency/operational complexity.

## 9. Trade-offs

### Advantages

Giới hạn resource occupancy, giảm failure propagation và làm latency behavior predictable hơn.

### Costs / Risks

Timeout quá ngắn tạo false failures. Budget cần dựa trên SLO và dependency latency thực tế, không phải con số tùy ý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout là giới hạn thời gian, không phải “fix network”.

### Middle

Biết propagate `CancellationToken` xuyên application và HTTP/database calls.

### Senior

Thiết kế retry + timeout + circuit breaker trong cùng latency budget.

### Technical Lead / Architect

Đặt end-to-end latency objective và quyết định synchronous boundary nào nên được thay bằng messaging.

## 11. Key takeaway

* Timeout phải là end-to-end budget, không phải các con số độc lập.
* Retry phải nằm trong remaining budget.
* Cancellation propagation bảo vệ tài nguyên khi caller đã bỏ cuộc.

# 7. Azure Blob Storage large-file streaming: upload/download file lớn mà không giữ toàn bộ payload trong process memory

## 1. What is it?

Streaming xử lý file theo luồng/chunks thay vì đọc toàn bộ file vào `byte[]` hoặc `MemoryStream`. Với Azure Blob Storage, application có thể stream request body trực tiếp tới blob client hoặc stream blob về response.

## 2. Why does it exist?

Naive implementation:

```csharp
using var ms = new MemoryStream();
await file.CopyToAsync(ms);
var bytes = ms.ToArray();
await blob.UploadAsync(new BinaryData(bytes));
```

File 500 MB + nhiều concurrent uploads có thể làm process memory tăng hàng GB, tạo LOH pressure hoặc OOM.

## 3. How does it work?

```text
Client stream
   ↓
ASP.NET Core request body
   ↓
Blob SDK
   ↓
Azure Storage
```

Data đi qua bounded buffers. Application không cần sở hữu toàn payload cùng lúc.

## 4. Practical implementation

```csharp
app.MapPost("/files/{name}", async (
    string name,
    HttpRequest request,
    BlobContainerClient container,
    CancellationToken ct) =>
{
    var blob = container.GetBlobClient(name);

    await blob.UploadAsync(
        request.Body,
        overwrite: true,
        cancellationToken: ct);

    return Results.Accepted();
});
```

Download:

```csharp
var stream = await blob.OpenReadAsync(
    cancellationToken: ct);

return Results.Stream(
    stream,
    contentType: "application/octet-stream");
```

Trong production cần validate size, content type, authorization, naming và malware scanning strategy.

## 5. Real production scenario

CMS cho phép editor upload videos vài trăm MB. App chạy 4 instances, mỗi instance memory limit 1 GB. Cách buffer toàn file chỉ cần 2–3 concurrent uploads là process recycling/OOM.

Streaming làm memory footprint gần như độc lập với file size và ổn định hơn theo concurrency.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng theo kích thước file và concurrent uploads; GC/LOH spikes.

**Evidence** → heap dump có large `byte[]`/`MemoryStream`.

**Hypothesis** → full buffering.

**Diagnosis** → trace upload pipeline và allocation profile.

**Fix** → streaming, request limits, cancellation; với cực lớn có thể dùng direct-to-Blob SAS upload.

**Verification** → load test nhiều large files và theo dõi working set/GC.

## 7. Common mistakes

* `ToArray()` sau khi đã stream vào `MemoryStream`.
* Cho public client upload qua web server dù có thể upload trực tiếp bằng scoped SAS.
* Không giới hạn file size.
* Tin `Content-Type`/extension do client gửi là trustworthy.

## 8. Alternatives

Direct browser/mobile → Blob bằng short-lived SAS giảm load web app mạnh hơn. Web app chỉ cấp authorization token/SAS và nhận metadata callback.

Server-proxy streaming vẫn phù hợp nếu cần inline validation/transformation bắt buộc.

## 9. Trade-offs

### Advantages

Memory ổn định, hỗ trợ large file tốt hơn và giảm GC pressure.

### Costs / Risks

Streaming làm validation/retry phức tạp hơn; direct SAS upload cần security policy và cleanup cho abandoned blobs.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu stream xử lý dần thay vì giữ toàn file trong memory.

### Middle

Biết dùng Blob SDK với request/response streams và cancellation.

### Senior

Thiết kế size limits, retry, integrity, malware scanning và direct upload.

### Technical Lead / Architect

Chọn app-proxy hay direct-to-storage dựa trên security, bandwidth, transformation và operational cost.

## 11. Key takeaway

* File lớn không nên mặc định biến thành `byte[]` trong application memory.
* Direct-to-Blob SAS có thể loại web app khỏi data path.
* Streaming vẫn cần security và lifecycle controls.

# 8. SLI/SLO + error budget: biến observability thành quyết định reliability thay vì chỉ có dashboard đẹp

## 1. What is it?

SLI (Service Level Indicator) là phép đo reliability thực tế, ví dụ tỷ lệ request thành công hoặc p95 latency.

SLO (Service Level Objective) là mục tiêu cho SLI trong một cửa sổ thời gian, ví dụ 99.9% requests thành công trong 30 ngày.

Error budget là phần failure được phép:

```text
100% - 99.9% = 0.1% budget
```

## 2. Why does it exist?

“System phải luôn ổn định” không phải objective đo được. 100% reliability thường cực đắt hoặc bất khả thi.

SLO tạo ngôn ngữ chung giữa engineering và product: reliability cần bao nhiêu, và khi nào team nên ưu tiên stability hơn feature velocity.

## 3. How does it work?

Ví dụ availability SLI:

```text
successful eligible requests / total eligible requests
```

Không nhất thiết mọi `5xx` đều giống nhau và không phải mọi request đều nằm trong SLI. Health probes, synthetic traffic hoặc client cancellations có thể cần classification riêng.

Burn rate cho biết budget đang bị tiêu nhanh đến đâu. Một spike ngắn có thể cần alert khác với slow degradation kéo dài.

## 4. Practical implementation

Application Insights/Kusto conceptual query:

```kusto
requests
| where timestamp > ago(30d)
| summarize
    total=count(),
    successful=countif(success == true)
| extend availability = 100.0 * successful / total
```

Latency SLI có thể theo p95/p99:

```kusto
requests
| summarize p95=percentile(duration, 95),
            p99=percentile(duration, 99)
```

Metric tốt phải phản ánh user experience, không chỉ resource health.

## 5. Real production scenario

SaaS có dashboard CPU xanh và database CPU chỉ 30%, nhưng users phàn nàn login hay timeout. Team trước đây không có SLO.

Khi định nghĩa login success SLI và p95 latency, họ phát hiện external identity dependency làm 2% login requests vượt 5 giây. Infrastructure metrics trước đó không cho thấy trực tiếp user impact.

## 6. Failure scenario & troubleshooting

**Symptom** → alert noise rất nhiều nhưng incident thật đôi khi không alert.

**Evidence** → alerts dựa trên CPU/memory threshold chứ không gắn với user-facing failure.

**Hypothesis** → monitoring không SLO-driven.

**Diagnosis** → map user journey → critical SLIs → telemetry gaps.

**Fix** → định nghĩa SLI/SLO, error-budget alerts và dependency metrics bổ trợ.

**Verification** → replay historical incidents xem alert mới có bắt đúng signal sớm hơn không.

## 7. Common mistakes

* Dùng SLA contract với khách hàng thay cho engineering SLO.
* Chọn SLI dễ đo nhưng không phản ánh user experience.
* Đặt 99.999% vì “nghe chuyên nghiệp” mà không tính cost.
* Alert mỗi lần SLI lệch nhẹ thay vì nhìn burn rate/window.

## 8. Alternatives

Traditional threshold monitoring vẫn cần cho capacity/resource failure. SLO không thay thế logs, traces hay infrastructure alerts; nó cung cấp top-level reliability objective để ưu tiên chúng.

## 9. Trade-offs

### Advantages

Reliability đo được, ưu tiên incident/technical debt rõ hơn và giảm tranh luận cảm tính.

### Costs / Risks

Cần telemetry quality, agreement về user journey và maintenance. SLO sai có thể tối ưu nhầm thứ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu metric khác objective.

### Middle

Biết tạo query/dashboard cho success rate và percentile latency.

### Senior

Thiết kế SLI phản ánh user impact, burn-rate alert và incident analysis.

### Technical Lead / Architect

Thương lượng reliability target với business, cân bằng cost/complexity và dùng error budget để quyết định engineering priorities.

## 11. Key takeaway

* SLI đo; SLO đặt mục tiêu; error budget biểu diễn failure allowance.
* Resource health không đồng nghĩa user experience khỏe.
* SLO nên điều khiển engineering decisions, không chỉ dashboard.

# 9. Git rebase vs merge: giữ lịch sử hữu ích mà không hy sinh khả năng truy vết production change

## 1. What is it?

`merge` kết hợp hai histories bằng một merge commit khi cần. `rebase` replay commits của branch lên một base mới, tạo commit IDs mới và lịch sử tuyến tính hơn.

```text
Merge:
A---B---C main
     \   \
      D---E---M

Rebase:
A---B---C---D'---E'
```

## 2. Why does it exist?

Teams cần vừa tích hợp concurrent work vừa giữ history đủ rõ để review, bisect, rollback và audit.

Không có một strategy đúng cho mọi team. Vấn đề là hiểu semantics thay vì chọn vì lịch sử “đẹp”.

## 3. How does it work?

`git rebase main` lấy commits riêng của branch, tạm bỏ chúng, move branch tới `main`, rồi replay từng commit.

Commit mới có parent mới nên SHA thay đổi.

Merge giữ original commits và thêm node kết hợp histories.

## 4. Practical implementation

Feature branch cá nhân trước PR:

```bash
git fetch origin
git rebase origin/main
```

Resolve conflicts:

```bash
git add <files>
git rebase --continue
```

Nếu branch đã public/shared, rewrite history cần thận trọng. Khi buộc force push:

```bash
git push --force-with-lease
```

`--force-with-lease` an toàn hơn `--force` vì tránh ghi đè remote changes ngoài dự kiến.

## 5. Real production scenario

Incident xảy ra sau release gồm 20 PRs. Team cần tìm commit gây regression bằng `git bisect` và correlate deployment artifact.

History với meaningful commits/PR merge giúp truy vết. History bị squash/rebase tùy tiện sau khi release hoặc chứa hàng trăm “fix typo/fix again” commits làm investigation khó hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → developer mất commits đồng đội sau force push.

**Evidence** → reflog/local branches cho thấy remote history bị rewrite.

**Hypothesis** → rebase trên shared branch rồi `--force`.

**Diagnosis** → compare SHAs và reflog.

**Fix** → recover commit từ reflog, restore branch, dùng `--force-with-lease` và branch policy.

**Verification** → PR history khớp expected commits; protected branches chặn unsafe force push.

## 7. Common mistakes

* Rebase `main`/shared branch đã có nhiều consumers.
* Đồng nhất “linear history” với “good history”.
* Squash mọi thứ làm mất useful logical commits cần cho bisect.
* Merge liên tục main vào feature mỗi vài phút tạo noise.

## 8. Alternatives

Squash merge tạo một commit per PR, phù hợp khi PR là unit of change quan trọng hơn internal commits. Merge commit giữ complete branch context. Rebase-and-merge tạo linear history nhưng rewrite feature commit IDs.

## 9. Trade-offs

### Advantages

Rebase có thể làm local feature history sạch, merge giữ integration history và tránh rewrite.

### Costs / Risks

Rebase trên shared history nguy hiểm; merge quá nhiều có thể tạo graph noise. Squash đơn giản hóa history nhưng giảm granularity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu merge giữ lịch sử, rebase replay và đổi SHA.

### Middle

Biết resolve conflicts, dùng `--force-with-lease` và tránh rewrite shared branch.

### Senior

Chọn strategy hỗ trợ review, rollback, bisect và release traceability.

### Technical Lead / Architect

Định nghĩa branch/merge policy dựa trên deployment model và incident workflow, không dựa trên sở thích đồ thị Git.

## 11. Key takeaway

* Rebase rewrite commit identity; merge thì không.
* Shared history không nên bị rewrite tùy tiện.
* Git history tốt là history giúp review và production troubleshooting.

# 10. Frontend async race condition với `AbortController`: response cũ ghi đè state mới dù API hoàn toàn đúng

## 1. What is it?

Async race ở frontend xảy ra khi nhiều requests cho các user actions khác nhau chạy đồng thời và hoàn thành không theo thứ tự gửi.

Ví dụ search-as-you-type:

```text
Request A: "car"   → mất 800 ms
Request B: "cargo" → mất 200 ms

B trả trước → UI hiển thị cargo
A trả sau   → UI bị ghi ngược về car
```

Backend có thể hoàn toàn đúng; bug nằm ở state coordination phía client.

## 2. Why does it exist?

Network latency không deterministic. User có thể đổi filter, route hoặc component state trước khi request cũ hoàn tất.

Promise ordering không tự động gắn với “latest user intent”.

## 3. How does it work?

Mỗi request cần lifecycle gắn với current intent. Có hai pattern phổ biến:

* cancel request cũ bằng `AbortController`
* giữ request/version ID và chỉ apply response mới nhất

Cancellation tốt khi request không còn giá trị; version check vẫn cần trong một số libraries/workflows.

## 4. Practical implementation

TypeScript:

```typescript
let currentController: AbortController | null = null;

async function search(query: string) {
  currentController?.abort();
  currentController = new AbortController();

  try {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(query)}`,
      { signal: currentController.signal }
    );

    const data = await response.json();
    renderResults(data);
  } catch (error) {
    if (error instanceof DOMException && error.name === "AbortError") {
      return;
    }

    showError(error);
  }
}
```

Ở React/Vue, cancellation phải gắn với component/effect lifecycle.

## 5. Real production scenario

Automotive marketplace có filters Brand → Model → Year. User đổi Brand từ Toyota sang BMW nhanh. Request lấy Toyota models chậm hơn request BMW.

Nếu response Toyota về sau và overwrite store, UI hiển thị Toyota models dưới BMW selection. Người dùng nghĩ backend trả sai dữ liệu.

## 6. Failure scenario & troubleshooting

**Symptom** → bug chỉ xảy ra khi click/type nhanh hoặc network chậm.

**Evidence** → browser Network tab cho thấy responses hoàn thành out-of-order.

**Hypothesis** → stale response update state.

**Diagnosis** → thêm request sequence/correlation log ở client; throttle network trong DevTools.

**Fix** → abort stale requests hoặc guard state update bằng latest request ID.

**Verification** → automated test với delayed responses đảo thứ tự hoàn thành.

## 7. Common mistakes

* Cho rằng request gửi trước sẽ về trước.
* Abort request nhưng catch block vẫn hiện “Something went wrong”.
* Chỉ debounce input nhưng không cancel request đã bắt đầu.
* Component unmount nhưng async callback vẫn update state/store không phù hợp.

## 8. Alternatives

Debounce giảm số requests nhưng không hoàn toàn loại race. Server-side request versioning hiếm khi cần cho simple search nhưng hữu ích trong stateful mutation flows.

Libraries như React Query/TanStack Query cung cấp cache/request lifecycle abstractions, nhưng developer vẫn phải hiểu stale data semantics.

## 9. Trade-offs

### Advantages

Cancellation giảm wasted work và stale UI updates; user intent được phản ánh chính xác hơn.

### Costs / Risks

Tăng lifecycle logic và error classification. Abort phía browser không đảm bảo downstream server operation luôn dừng nếu cancellation không propagate tới backend.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async responses có thể về sai thứ tự.

### Middle

Biết dùng `AbortController`, debounce và cleanup lifecycle.

### Senior

Phân biệt stale response, cache freshness và mutation race; thiết kế test deterministic cho timing bugs.

### Technical Lead / Architect

Định nghĩa frontend data-fetching strategy, cancellation semantics và API behavior để tránh duplicated custom state machinery giữa teams.

## 11. Key takeaway

* Network completion order không đại diện cho latest user intent.
* Debounce và cancellation giải quyết hai vấn đề khác nhau.
* Race conditions cần được test bằng deliberate delay/reordering, không chỉ happy-path tests.
