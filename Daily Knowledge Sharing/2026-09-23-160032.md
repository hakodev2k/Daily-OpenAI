# 1. .NET GC Server vs Workstation: throughput, pause time và container memory budget

## 1. What is it?

Mental model: Garbage Collector không chỉ là cơ chế “xóa object không dùng nữa”; nó là bộ quản lý heap phải cân bằng **allocation throughput, CPU, memory footprint và pause time**. .NET có các GC modes khác nhau, trong đó Server GC được tối ưu cho server throughput và thường sử dụng nhiều heap/GC threads hơn, còn Workstation GC thiên về footprint và responsiveness của process nhỏ hơn.

Điều quan trọng trong backend không phải thuộc tên mode, mà là hiểu GC mode thay đổi cách application tiêu thụ CPU và memory dưới load.

## 2. Why does it exist?

Một desktop process và một API chạy trên máy nhiều cores có workload khác nhau. Server workload thường có nhiều concurrent allocations và cần tận dụng nhiều cores để collect song song. Nhưng tăng throughput bằng nhiều heaps cũng có memory cost. Trong container có memory limit chặt, lựa chọn/runtime configuration không thể tách khỏi resource budget.

## 3. How does it work?

Simplified flow:

```text
Requests -> allocations -> managed heaps
                         -> Gen 0 / Gen 1 collections
                         -> survivors promoted
                         -> Gen 2 / LOH pressure

Server GC:
multiple heaps + dedicated GC workers
        -> higher parallel collection capability
        -> potentially larger memory footprint
```

GC quyết định collection dựa trên allocation rate, generations, heap budget và memory pressure. Vì vậy cùng code nhưng concurrency/resource limit khác nhau có thể cho behavior khác hẳn.

## 4. Practical implementation

Đừng “tune GC” trước khi đo. Với production investigation, bắt đầu bằng runtime counters:

```bash
dotnet-counters monitor \
  --process-id <PID> \
  System.Runtime
```

Theo dõi allocation rate, heap size, Gen 0/1/2 collections, time in GC và working set. Trong container, đối chiếu thêm memory limit/throttling của platform.

Một optimization có giá trị thường là giảm allocation ở hot path trước khi đổi GC knobs:

```csharp
// Tránh tạo intermediate collection nếu không cần.
var total = orders
    .Where(x => x.IsActive)
    .Sum(x => x.Total);
```

## 5. Real production scenario

Một ASP.NET Core service chạy ổn trên VM 8 GB nhưng sau khi chuyển sang containers giới hạn 512 MB, pod thường xuyên tăng memory rồi bị restart. Team nhìn heap snapshot thấy không có leak rõ ràng. Vấn đề thực tế là allocation rate cao, concurrent traffic lớn và runtime/container memory budget không phù hợp; native/runtime overhead cộng managed heap vượt cgroup limit.

## 6. Failure scenario & troubleshooting

**Symptom** → latency p99 tăng theo chu kỳ, memory saw-tooth lớn hoặc container OOMKilled.

**Evidence** → GC counters cho thấy Gen 2/time-in-GC tăng; container metrics cho thấy memory tiến sát limit.

**Hypothesis** → allocation pressure + heap budget không phù hợp workload/resource limit.

**Diagnosis** → correlate allocation rate, GC pauses, request throughput và container memory.

**Fix** → giảm allocations/buffering trước; điều chỉnh resource requests/limits hoặc GC configuration chỉ khi evidence hỗ trợ.

**Verification** → chạy load test với cùng container limits như Production và so p95/p99, allocation rate, GC time, peak memory.

## 7. Common mistakes

Coi mọi memory growth là leak; chỉ nhìn managed heap mà bỏ native memory; tăng container memory mà không tìm allocation source; bật/tắt GC option theo blog benchmark khác workload; benchmark single request thay vì sustained concurrency.

## 8. Alternatives

Không có “alternative GC” thực tế cho normal .NET application; lựa chọn chính là giảm allocation, pooling có kiểm soát, streaming thay buffering và điều chỉnh hosting/resource model.

## 9. Trade-offs

### Advantages

Server-oriented GC có thể tăng throughput trên multicore workloads.

### Costs / Risks

Nhiều heap/resources hơn có thể tăng footprint; tuning sai dễ che application allocation problem.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu managed object có lifecycle và GC không miễn phí.

### Middle

Đọc runtime counters và tránh allocation không cần thiết.

### Senior

Phân biệt leak, allocation pressure, GC pause và container memory pressure bằng evidence.

### Technical Lead / Architect

Thiết kế resource budget, concurrency và workload isolation sao cho runtime behavior phù hợp deployment platform.

## 11. Key takeaway

- GC behavior là một phần của performance model, không phải background magic.
- Container memory limit phải tính cả managed lẫn native/runtime overhead.
- Giảm allocation có bằng chứng thường tốt hơn tuning GC theo cảm tính.

# 2. ASP.NET Core Output Caching: cache HTTP response đúng semantics

## 1. What is it?

Output Caching lưu response đã tạo của endpoint và tái sử dụng cho request tương thích. Mental model: đây là **response reuse policy ở application boundary**, khác với việc cache một repository result hoặc để browser/CDN cache bằng HTTP headers.

## 2. Why does it exist?

Một endpoint GET có thể tốn CPU, database I/O và serialization dù cùng response được yêu cầu hàng nghìn lần. Application-level output cache có thể tránh chạy lại toàn pipeline phía sau endpoint cho request đủ điều kiện.

Nhưng response phụ thuộc user, query string, locale hoặc authorization thì cache key/policy sai có thể trở thành correctness hoặc security bug.

## 3. How does it work?

```text
Request
  -> Output Cache lookup
       -> hit  -> cached response
       -> miss -> endpoint -> DB/API -> response
                            -> store by cache policy/key
```

Policy quyết định request nào cache được, duration, variation dimensions và invalidation/tag behavior.

## 4. Practical implementation

```csharp
builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("catalog", policy =>
        policy.Expire(TimeSpan.FromSeconds(30))
              .SetVaryByQuery("category", "page"));
});

app.UseOutputCache();

app.MapGet("/catalog", GetCatalog)
   .CacheOutput("catalog");
```

Nếu response thay đổi theo tenant/user, đừng cache cho đến khi variation/isolation semantics được định nghĩa chính xác.

## 5. Real production scenario

Homepage catalog endpoint được gọi 2.000 lần/phút nhưng dữ liệu chỉ đổi vài lần mỗi phút. Cache response 20–30 giây giảm SQL/serialization load đáng kể. Tuy nhiên endpoint `/me/orders` không được dùng chung response giữa users dù URL shape giống nhau.

## 6. Failure scenario & troubleshooting

**Symptom** → user thấy dữ liệu của context khác hoặc dữ liệu quá stale.

**Evidence** → cache hit nhưng request dimensions cần thiết không nằm trong key/policy.

**Hypothesis** → variation/invalidation contract sai.

**Diagnosis** → liệt kê mọi input làm response thay đổi: path, query, header, identity, tenant, feature flag, locale.

**Fix** → bổ sung variation, tag invalidation hoặc không output-cache endpoint đó.

**Verification** → integration tests với nhiều users/tenants/query combinations và cache hit/miss telemetry.

## 7. Common mistakes

Cache authenticated personalized response như public data; cache POST side effect; TTL dài để “tăng performance”; không có invalidation ownership; nhầm Output Caching với HTTP Response Caching/CDN caching.

## 8. Alternatives

`IMemoryCache`/Redis cache domain/read-model data; CDN cache ở edge; database/read model optimization nếu response không phù hợp cache.

## 9. Trade-offs

### Advantages

Giảm cả endpoint computation, downstream calls và serialization khi hit.

### Costs / Risks

Freshness, invalidation, memory/distributed cache cost và nguy cơ data isolation nếu key sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache hit/miss/TTL.

### Middle

Cấu hình policy và variation đúng endpoint.

### Senior

Đánh giá identity, invalidation, stampede và multi-instance behavior.

### Technical Lead / Architect

Quyết định cache nên nằm ở browser, CDN, application response, data layer hay không nên tồn tại.

## 11. Key takeaway

- Output cache là correctness policy trước khi là performance feature.
- Cache key phải đại diện mọi input ảnh hưởng response.
- Chọn cache layer dựa trên ownership và freshness semantics.

# 3. EF Core execution strategy + transaction: retry transient failure đúng boundary

## 1. What is it?

EF Core execution strategy có thể retry database operations khi gặp lỗi được phân loại là transient. Mental model: retry chỉ an toàn khi **toàn bộ đơn vị công việc có thể được replay theo boundary đã biết**.

Một user-created transaction gồm nhiều operations không thể được retry từng command độc lập mà vẫn giữ semantics ban đầu.

## 2. Why does it exist?

Cloud databases có transient failures: connection reset, failover hoặc temporary throttling. Không retry có thể biến sự cố ngắn thành user-visible failure. Nhưng retry sai boundary có thể chạy một phần transaction nhiều lần hoặc gặp trạng thái không xác định khi commit outcome không rõ.

## 3. How does it work?

```text
Execution strategy
  -> execute unit
      -> begin transaction
      -> command A
      -> command B
      -> commit
  -> transient failure?
      -> replay whole unit when safe
```

Điểm quan trọng là delegate của execution strategy phải bao phủ transaction cần replay.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    order.MarkPaid();
    await db.SaveChangesAsync(ct);

    db.OutboxMessages.Add(OutboxMessage.From(order));
    await db.SaveChangesAsync(ct);

    await tx.CommitAsync(ct);
});
```

Business side effects ngoài database không nên nằm tùy tiện trong replayable delegate.

## 5. Real production scenario

Checkout ghi Order và Outbox trong một SQL transaction. SQL failover xảy ra giữa workload. Nếu retry chỉ `SaveChanges` thứ hai, state reasoning trở nên khó. Replay transaction unit giúp giữ atomic database intent, trong khi message publishing được xử lý sau qua Outbox.

## 6. Failure scenario & troubleshooting

**Symptom** → exception nói execution strategy không hỗ trợ user-initiated transaction theo cách hiện tại, hoặc duplicate external side effect sau retry.

**Evidence** → transaction được tạo ngoài execution-strategy delegate; HTTP call nằm trong retry scope.

**Hypothesis** → retry boundary lớn/sai loại side effect.

**Diagnosis** → map từng operation và tính replayability/idempotency.

**Fix** → đặt DB unit trong execution strategy; tách external side effects bằng Outbox/idempotency.

**Verification** → fault-injection transient failure ở các điểm trước/sau `SaveChanges` và commit.

## 7. Common mistakes

Retry mọi exception; retry transaction nhưng gọi payment API bên trong; không giới hạn attempts/backoff; coi commit timeout là chắc chắn rollback; thêm Polly retry bên ngoài EF retry mà không hiểu retry multiplication.

## 8. Alternatives

Application-level retry có thể phù hợp khi cần orchestration rộng hơn; queue-based processing phù hợp work có thể deferred; không retry nếu operation không replay-safe.

## 9. Trade-offs

### Advantages

Tăng resilience trước transient database faults.

### Costs / Risks

Tăng latency, database load và complexity; retry sai có thể duplicate effects.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt transient và permanent failure.

### Middle

Dùng execution strategy đúng transaction boundary.

### Senior

Reason về unknown commit outcome, idempotency và nested retry layers.

### Technical Lead / Architect

Định nghĩa consistency/retry strategy xuyên database, messaging và external APIs.

## 11. Key takeaway

- Retry phải replay một unit có semantics rõ.
- Transaction + external side effect cần boundary khác database transaction.
- Resilience không đồng nghĩa “retry nhiều hơn”.

# 4. SQL SARGability: predicate quyết định optimizer có thể seek hay không

## 1. What is it?

SARGable predicate là điều kiện tìm kiếm có hình thức cho phép database dùng index access path hiệu quả, thường bằng cách so sánh indexed column trực tiếp với giá trị/range. Mental model: index tồn tại chưa đủ; query phải cho optimizer cách **định vị range** trong index.

## 2. Why does it exist?

Nếu function được áp lên từng row của indexed column, engine có thể phải tính function rồi mới kiểm tra predicate. Điều đó thường làm mất khả năng seek trực tiếp và tăng logical reads.

## 3. How does it work?

Kém:

```sql
WHERE CAST(CreatedAt AS date) = @Date
```

Tốt hơn:

```sql
WHERE CreatedAt >= @Date
  AND CreatedAt < DATEADD(day, 1, @Date)
```

Predicate thứ hai mô tả một range trên `CreatedAt`, phù hợp B-tree navigation hơn.

## 4. Practical implementation

EF Core cũng cần giữ shape có thể translate thành predicate tốt:

```csharp
var from = date.Date;
var to = from.AddDays(1);

var rows = await db.Orders
    .Where(x => x.CreatedAt >= from && x.CreatedAt < to)
    .Select(x => new { x.Id, x.Total })
    .ToListAsync(ct);
```

Xác minh bằng generated SQL + actual execution plan + logical reads.

## 5. Real production scenario

Order report có index trên `(CreatedAt, Status)` nhưng query vẫn scan hàng chục triệu rows. Root cause không phải “SQL Server không dùng index” mà predicate wrap `CreatedAt` bằng conversion/function. Viết lại range predicate giảm reads mạnh mà không thêm index mới.

## 6. Failure scenario & troubleshooting

**Symptom** → query chậm dù indexed column xuất hiện trong WHERE.

**Evidence** → plan có scan/residual predicate; logical reads cao.

**Hypothesis** → non-SARGable expression, implicit conversion hoặc index order/selectivity không phù hợp.

**Diagnosis** → xem plan warnings, data types, predicate và estimates.

**Fix** → viết lại predicate/data type hoặc thiết kế computed/indexed strategy khi business expression bắt buộc.

**Verification** → so actual plan, reads, CPU, duration trên representative data.

## 7. Common mistakes

Thêm index mới mà giữ predicate xấu; function trên column; implicit conversion do parameter type khác column; `%term%` rồi kỳ vọng B-tree seek; chỉ nhìn elapsed time trên dev database nhỏ.

## 8. Alternatives

Computed persisted column + index cho expression quan trọng; full-text search cho text search; Elasticsearch khi requirement thực sự là search/relevance chứ không phải relational filtering.

## 9. Trade-offs

### Advantages

Predicate tốt có thể tận dụng index hiện có và giảm I/O lớn.

### Costs / Risks

Rewrite phải giữ đúng semantics, đặc biệt date/time zone/collation; thêm computed index tăng write/storage cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không tự động làm mọi WHERE nhanh.

### Middle

Viết range predicates và đọc seek/scan cơ bản.

### Senior

Phân tích residual predicates, conversions, cardinality và I/O.

### Technical Lead / Architect

Thiết kế query/API access patterns phù hợp data model thay vì chữa từng query bằng index.

## 11. Key takeaway

- Index usability phụ thuộc query shape.
- Đo logical reads và execution plan, không chỉ duration.
- SARGability là access-path reasoning, không phải syntax trick.

# 5. MongoDB embedding vs referencing: model theo access pattern và atomicity boundary

## 1. What is it?

Embedding lưu related data trong cùng document; referencing lưu documents riêng và liên kết bằng identifier. Mental model: đây là quyết định **data locality + ownership + update boundary**, không phải bản sao của SQL join-vs-no-join.

## 2. Why does it exist?

Document database tối ưu khi dữ liệu thường được đọc/ghi cùng nhau có thể nằm cùng document. Nhưng embedded collection tăng không giới hạn, independent lifecycle hoặc nhiều writers có thể biến document thành hotspot và khó quản lý.

## 3. How does it work?

```text
Embedded Order
{
  _id,
  customerSnapshot,
  lines: [ ... ]
}

Referenced model
Order { _id, customerId }
Customer { _id, ... }
```

Embedding cho locality và single-document atomic update. Referencing cho independent ownership/lifecycle nhưng cần thêm queries/aggregation/application joins tùy use case.

## 4. Practical implementation

Ví dụ order line thường thuộc vòng đời Order:

```json
{
  "_id": "order-42",
  "status": "Paid",
  "lines": [
    { "sku": "A-10", "quantity": 2, "unitPrice": 19.5 }
  ]
}
```

Giá tại thời điểm mua là snapshot hợp lý; không nhất thiết reference Product hiện tại rồi tính lại lịch sử.

## 5. Real production scenario

E-commerce Order cần hiển thị nhanh invoice lịch sử. Embed line snapshot giúp một read lấy đủ dữ liệu và bảo toàn giá/tên sản phẩm lúc mua. Product catalog vẫn là collection riêng vì product thay đổi độc lập và được nhiều orders tham chiếu logic.

## 6. Failure scenario & troubleshooting

**Symptom** → document tăng liên tục, update chậm và contention tập trung.

**Evidence** → embedded array tăng không bounded; nhiều writers update cùng parent document.

**Hypothesis** → embedding vượt ownership/cardinality phù hợp.

**Diagnosis** → đo document growth, write frequency và read patterns.

**Fix** → tách unbounded child stream/reference hoặc remodel aggregate.

**Verification** → benchmark realistic cardinality và concurrent writes.

## 7. Common mistakes

Thiết kế MongoDB như normalized SQL schema; embed mọi thứ vì “NoSQL”; duplicate mutable data mà không có ownership/synchronization policy; dùng `$lookup` khắp nơi rồi mất lợi ích locality.

## 8. Alternatives

Relational model phù hợp khi joins/ad-hoc relational queries/invariants xuyên entities là trung tâm. Cosmos DB có document modeling tương tự nhưng partitioning/RU model thêm constraints khác.

## 9. Trade-offs

### Advantages

Embedding giảm round trips và tạo atomic/local aggregate.

### Costs / Risks

Duplication, document growth, write contention và synchronization nếu duplicated data cần cập nhật.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu document là modeling boundary, không chỉ JSON row.

### Middle

Chọn embed/reference theo read/write pattern.

### Senior

Reason về cardinality, atomicity, duplication và hot documents.

### Technical Lead / Architect

Chọn data store/model dựa trên invariants và access patterns thay vì xu hướng SQL/NoSQL.

## 11. Key takeaway

- Embed khi data có cùng ownership/lifecycle và bounded growth.
- Reference khi lifecycle/writes độc lập hoặc relationship tăng không bounded.
- Data modeling bắt đầu từ access pattern và invariant.

# 6. Circuit Breaker: ngăn dependency failure tiêu thụ hết capacity caller

## 1. What is it?

Circuit Breaker theo dõi failures của remote dependency và tạm thời ngừng gửi requests khi failure threshold/policy cho thấy dependency đang unhealthy. Mental model: nó không “sửa” dependency; nó **giới hạn thời gian/capacity bị lãng phí vào dependency đã có bằng chứng đang fail**.

## 2. Why does it exist?

Nếu downstream mất 10 giây rồi timeout, 500 concurrent requests có thể giữ sockets, request slots và memory trong lúc chờ. Retry còn có thể nhân traffic. Fail fast trong khoảng thời gian hợp lý giúp caller giữ capacity cho work khác.

## 3. How does it work?

```text
Closed -> requests flow
  failures exceed policy
Open -> fail fast
  break duration passes
Half-open -> probe limited requests
  success -> Closed
  failure -> Open
```

## 4. Practical implementation

Trong modern .NET resilience stack, policy nên kết hợp timeout/retry/circuit breaker có chủ đích. Conceptual ordering:

```text
request
 -> overall timeout budget
 -> retry (bounded, transient only)
 -> circuit breaker
 -> HTTP attempt
```

Exact ordering phụ thuộc library/policy semantics; phải test behavior thay vì suy luận từ tên middleware.

## 5. Real production scenario

Review provider trả 503 trong 15 phút. Product page trước đây chờ provider 5 giây, khiến page latency và thread/socket pressure tăng. Circuit mở sau failure evidence; page trả review fallback ngay trong khi probes kiểm tra recovery.

## 6. Failure scenario & troubleshooting

**Symptom** → circuit liên tục open/close hoặc fail-fast quá nhiều dù dependency ổn.

**Evidence** → breaker metrics và downstream status không khớp.

**Hypothesis** → threshold/window không phù hợp traffic hoặc business errors bị tính như transient failures.

**Diagnosis** → phân loại status/exception và traffic volume.

**Fix** → tune sampling/threshold, chỉ handle failures phù hợp, thiết kế fallback.

**Verification** → chaos/fault injection với partial outage và recovery.

## 7. Common mistakes

Circuit breaker thay timeout; breaker global cho dependencies/tenants khác nhau; retry bên trong/outside tạo storm; coi HTTP 4xx business validation là dependency outage; không có telemetry state transition.

## 8. Alternatives

Timeout là bắt buộc dù có breaker; bulkhead/concurrency limiter bảo vệ capacity; queue decouples work; fallback/cache có thể duy trì degraded service.

## 9. Trade-offs

### Advantages

Fail fast, giảm cascading failure và bảo vệ caller capacity.

### Costs / Risks

Có thể reject request trong lúc downstream vừa recovery; thêm state/policy tuning và observability burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout khác retry khác breaker.

### Middle

Cấu hình breaker cho HTTP client và quan sát state.

### Senior

Thiết kế failure classification, timeout budget, retry interaction và fallback.

### Technical Lead / Architect

Quyết định dependency nào critical, degradable hay cần asynchronous isolation.

## 11. Key takeaway

- Circuit breaker bảo vệ caller, không chữa downstream.
- Phải đi cùng timeout và retry policy có giới hạn.
- Failure classification quan trọng hơn threshold đẹp.

# 7. Azure Blob Storage large-file streaming: đừng biến file thành RAM requirement

## 1. What is it?

Streaming xử lý dữ liệu file theo dòng/chunks thay vì đọc toàn bộ file vào `byte[]` hoặc `MemoryStream`. Với Azure Blob Storage, mental model là application chuyển dữ liệu giữa streams/storage transport với bounded memory, không materialize toàn payload.

## 2. Why does it exist?

Một API cho upload 500 MB mà buffer toàn file có thể tiêu thụ hàng trăm MB mỗi request. Chỉ vài uploads đồng thời đủ gây GC/LOH pressure hoặc OOM. File size nên ảnh hưởng transfer duration/network, không tuyến tính biến thành process memory footprint.

## 3. How does it work?

```text
Client stream
   -> ASP.NET Core request body
   -> Blob SDK upload stream
   -> Azure Blob Storage
```

Hoặc tốt hơn trong nhiều kiến trúc:

```text
Client -> SAS-authorized direct upload -> Blob Storage
API    -> issues constrained access / records metadata
```

## 4. Practical implementation

Server-side streaming:

```csharp
app.MapPost("/files", async (
    HttpRequest request,
    BlobContainerClient container,
    CancellationToken ct) =>
{
    var blob = container.GetBlobClient($"uploads/{Guid.NewGuid():N}");
    await blob.UploadAsync(request.Body, overwrite: false, ct);
    return Results.Accepted();
});
```

Production cần thêm content-length policy, content-type handling, authorization, malware scanning workflow và timeout/cancellation.

## 5. Real production scenario

CMS cho editor upload video 1 GB. Proxying qua web app làm App Service bandwidth, request duration và memory trở thành bottleneck. Chuyển sang short-lived SAS cho direct upload giảm data-plane load trên API; API chỉ quản lý authorization và metadata lifecycle.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng theo file size hoặc upload timeout giữa chừng.

**Evidence** → heap có large `byte[]`; traces cho thấy request đi qua API toàn bộ duration.

**Hypothesis** → buffering hoặc architecture đặt API trong data path không cần thiết.

**Diagnosis** → inspect request pipeline, multipart buffering, SDK upload mode và proxy limits.

**Fix** → streaming/chunked/direct upload; resumable strategy khi cần.

**Verification** → concurrent large-file load test và theo dõi memory/network/timeout.

## 7. Common mistakes

`ReadToEndAsync` cho binary payload; SAS quá rộng/quá lâu; tin content type/filename từ client; không giới hạn size; public container vô tình; upload thành công nhưng metadata DB thất bại mà không có cleanup reconciliation.

## 8. Alternatives

Server proxy phù hợp khi phải inspect/transform synchronously; direct SAS upload tốt cho large payload; background ingestion phù hợp scanning/transcoding.

## 9. Trade-offs

### Advantages

Streaming/direct upload giảm memory và application bandwidth bottleneck.

### Costs / Risks

Direct upload cần delegated authorization, lifecycle cleanup, validation và eventual workflow rõ hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu stream khác byte array.

### Middle

Implement bounded streaming và cancellation.

### Senior

Thiết kế SAS scope, scanning, retries, orphan cleanup và observability.

### Technical Lead / Architect

Quyết định control plane/data plane: API có thực sự cần đứng giữa client và object storage hay không.

## 11. Key takeaway

- Large file không nên đồng nghĩa large process memory.
- Direct-to-Blob thường giảm operational load đáng kể.
- Security/lifecycle phải được thiết kế cùng transfer path.

# 8. OpenTelemetry sampling: kiểm soát telemetry cost mà vẫn giữ diagnostic value

## 1. What is it?

Sampling quyết định traces nào được record/export thay vì lưu 100% traffic. Mental model: telemetry cũng là một workload có **CPU, network, storage và query cost**; sampling là data-retention decision, không chỉ cost switch.

## 2. Why does it exist?

Service 20.000 requests/second có thể tạo lượng spans rất lớn. Export tất cả có thể đắt và gây backpressure. Nhưng random drop không có strategy có thể xóa chính traces hiếm của lỗi p99.

## 3. How does it work?

Head sampling quyết định sớm khi trace bắt đầu; tail sampling có thể quan sát trace rồi quyết định dựa trên outcome/latency nhưng cần collector state/resources.

```text
Request -> trace
           |
Head: decide early --------> export/drop

Tail:
spans -> collector buffer -> evaluate error/latency -> export/drop
```

Trace context cần giữ sampling decision nhất quán xuyên services để tránh trace bị thủng tùy tiện.

## 4. Practical implementation

Ví dụ head sampling cơ bản:

```csharp
services.AddOpenTelemetry()
    .WithTracing(builder => builder
        .SetSampler(new ParentBasedSampler(
            new TraceIdRatioBasedSampler(0.10)))
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation());
```

Tỷ lệ 10% chỉ là ví dụ; production policy phải dựa traffic, incident needs và backend cost.

## 5. Real production scenario

Checkout service export 100% traces và observability bill tăng nhanh. Giảm xuống 5% random làm cost tốt hơn nhưng incident hiếm 500 response khó tìm. Team chuyển policy: baseline sample thấp, giữ errors/high-latency traces qua collector tail-sampling strategy.

## 6. Failure scenario & troubleshooting

**Symptom** → logs có error nhưng trace tương ứng không tồn tại.

**Evidence** → sampling policy drop trace trước khi biết outcome hoặc propagation bị mất.

**Hypothesis** → sampling/collector design không giữ diagnostic classes quan trọng.

**Diagnosis** → kiểm tra sampler, trace flags, collector pipeline và dropped-span metrics.

**Fix** → parent-aware policy, tail sampling hoặc targeted higher sampling cho critical routes.

**Verification** → synthetic errors/slow requests và xác nhận trace retention end-to-end.

## 7. Common mistakes

Sample metrics như traces; high-cardinality attributes vẫn gây cost dù sample; mỗi service tự quyết định không theo parent; collector buffer không đủ cho tail sampling; sampling quá thấp trước khi biết baseline incident rate.

## 8. Alternatives

100% tracing phù hợp low-volume critical system; adaptive/dynamic policies phù hợp workload biến động; logs/metrics bổ sung nhưng không thay distributed trace causality.

## 9. Trade-offs

### Advantages

Giảm telemetry cost và processing load.

### Costs / Risks

Mất visibility nếu policy sai; tail sampling tăng collector complexity/memory/latency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu log/metric/trace khác nhau.

### Middle

Cấu hình sampler và propagation.

### Senior

Thiết kế sampling giữ errors/tail latency và quan sát dropped telemetry.

### Technical Lead / Architect

Đặt observability budget theo SLO, incident requirements, compliance và cost.

## 11. Key takeaway

- Sampling là observability design, không chỉ cost reduction.
- Rare errors và p99 traces thường có giá trị cao hơn random success trace.
- Luôn quan sát chính telemetry pipeline.

# 9. React stale closure: callback có thể nhìn thấy state của render cũ

## 1. What is it?

JavaScript closure giữ references tới lexical environment tại thời điểm function được tạo. Trong React function components, mỗi render tạo một snapshot của props/state cho closures của render đó. Mental model: callback không “đọc state mới nhất toàn cục”; nó có thể đang chạy với snapshot từ render trước.

## 2. Why does it exist?

React render model dựa trên pure-ish render snapshots. Điều này làm reasoning và scheduling khả thi, nhưng timers, async callbacks và effects có thể sống lâu hơn render đã tạo chúng.

## 3. How does it work?

```text
Render #1: count = 0 -> callback captures 0
Render #2: count = 1
later callback from #1 runs -> still sees 0
```

Đây là JavaScript closure semantics tương tác với React lifecycle, không phải state “tự quay về giá trị cũ”.

## 4. Practical implementation

Nếu update dựa trên previous state, dùng functional update:

```tsx
const [count, setCount] = useState(0);

function incrementLater() {
  setTimeout(() => {
    setCount(current => current + 1);
  }, 500);
}
```

Với `useEffect`, dependency list phải phản ánh values effect sử dụng; đừng xóa dependency chỉ để làm lint warning biến mất.

## 5. Real production scenario

Search UI debounce request theo query. Callback cũ hoàn tất sau callback mới và update results theo query trước. User thấy list “nhảy ngược”. Đây vừa có stale closure/state issue vừa có request race; giải pháp thường gồm correct dependencies + cancellation/request identity.

## 6. Failure scenario & troubleshooting

**Symptom** → callback log state cũ hoặc response cũ ghi đè UI mới.

**Evidence** → DevTools/logging theo render/request ID cho thấy callback thuộc render/request trước.

**Hypothesis** → stale closure hoặc out-of-order async completion.

**Diagnosis** → trace creation time của callback, effect dependencies và request lifecycle.

**Fix** → functional state update, dependencies đúng, AbortController hoặc request sequence guard tùy case.

**Verification** → test rapid input/navigation và intentionally delayed responses.

## 7. Common mistakes

Thêm mọi thứ vào `useRef` để né render; disable exhaustive-deps; nghĩ `setState` synchronous; không cancel obsolete request; memoize callback nhưng dependency sai.

## 8. Alternatives

State machine/store có thể làm complex async flows rõ hơn; server-state libraries quản lý request freshness/cancellation/cache tốt hơn cho data fetching phức tạp.

## 9. Trade-offs

### Advantages

React snapshot model làm render behavior nhất quán và hỗ trợ scheduling.

### Costs / Risks

Async callbacks yêu cầu hiểu closure/dependency semantics; workaround bằng refs có thể giảm transparency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu closure và render snapshot.

### Middle

Sửa dependencies, functional updates và cancellation.

### Senior

Phân biệt stale closure với network race/server-state problem.

### Technical Lead / Architect

Đặt frontend async/data-fetching conventions để tránh mỗi component tự phát minh concurrency semantics.

## 11. Key takeaway

- Mỗi render tạo một state snapshot cho closures của nó.
- Async completion order không đảm bảo request creation order.
- Fix đúng layer: closure, effect dependency hay request concurrency.

# 10. Expand-and-contract database migration: schema change không cần đồng bộ deploy tuyệt đối

## 1. What is it?

Expand-and-contract là migration strategy thay đổi schema qua nhiều bước backward-compatible. Mental model: trong rolling/blue-green deployment, **old code và new code có thể chạy đồng thời**, nên database schema phải hỗ trợ overlap period.

## 2. Why does it exist?

Rename/drop column trực tiếp có thể làm old instances crash ngay khi migration chạy, dù deployment mới chưa hoàn tất. Database thường là shared dependency không rollback đơn giản cùng application binary.

## 3. How does it work?

Ví dụ đổi `FullName` thành `DisplayName`:

```text
Phase 1 EXPAND
add DisplayName nullable
old app still reads/writes FullName
new app can dual-write/backfill

Phase 2 MIGRATE
backfill DisplayName
verify consistency
switch reads to DisplayName

Phase 3 CONTRACT
after all old versions gone
stop dual-write
remove FullName in later release
```

Mỗi phase có deployment và verification riêng.

## 4. Practical implementation

Migration đầu tiên chỉ additive:

```sql
ALTER TABLE Customers
ADD DisplayName nvarchar(200) NULL;
```

Backfill nên được batch nếu table lớn thay vì một transaction khổng lồ:

```sql
UPDATE TOP (5000) Customers
SET DisplayName = FullName
WHERE DisplayName IS NULL;
```

Lặp bằng controlled job, đo locks/log growth và tiến độ.

## 5. Real production scenario

App Service dùng deployment slot. New version cần tách một column nhưng Production vẫn có old instances trong swap/rollback window. Additive migration cho phép cả hai versions chạy. Destructive cleanup chỉ xảy ra sau khi rollback window đóng và telemetry xác nhận không còn code đọc old column.

## 6. Failure scenario & troubleshooting

**Symptom** → deploy mới thành công nhưng old pods bắt đầu lỗi SQL “invalid column” hoặc write path mất dữ liệu.

**Evidence** → migration rename/drop chạy trước khi toàn fleet chuyển version; mixed-version traffic tồn tại.

**Hypothesis** → schema change không backward-compatible.

**Diagnosis** → map application versions với schema assumptions và rollout timeline.

**Fix** → restore compatible schema hoặc rollback application theo runbook; thiết kế lại thành expand/migrate/contract.

**Verification** → integration test old + new binaries trên expanded schema và rehearsal rollback.

## 7. Common mistakes

Rename/drop trong cùng release; backfill hàng triệu rows trong startup migration; thêm `NOT NULL` ngay khi chưa backfill; dual-write nhưng không monitor divergence; xóa old column vì “deploy đã xanh” mà rollback window vẫn mở.

## 8. Alternatives

Maintenance-window migration có thể đủ cho internal system chấp nhận downtime; versioned new table/read model phù hợp redesign lớn; database view/compatibility layer có thể hỗ trợ legacy consumers.

## 9. Trade-offs

### Advantages

Cho phép zero/low-downtime rollout, rollback an toàn hơn và mixed-version operation.

### Costs / Risks

Nhiều releases, temporary duplication, dual-write complexity và cleanup discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu migration ảnh hưởng running code, không chỉ schema file.

### Middle

Viết additive migration và test backward compatibility.

### Senior

Thiết kế backfill, dual-read/write, rollout/rollback và lock/log impact.

### Technical Lead / Architect

Định nghĩa database evolution protocol cho nhiều services/versions và quyết định khi nào downtime đơn giản hơn distributed migration complexity.

## 11. Key takeaway

- Database migration là release-engineering problem, không chỉ DDL.
- Mixed-version window yêu cầu backward compatibility.
- Destructive change nên là bước cuối sau verification và rollback window.
