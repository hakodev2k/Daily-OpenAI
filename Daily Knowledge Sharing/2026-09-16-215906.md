# 1. .NET `ArrayPool<T>`: giảm allocation nhưng thêm ownership và data-leak risk

## 1. What is it?

`ArrayPool<T>` là cơ chế thuê và trả lại array để tái sử dụng buffer thay vì allocate array mới cho mỗi operation. Mental model đúng là **shared buffer ownership**, không phải “array miễn phí”. Buffer được thuê có capacity ít nhất bằng yêu cầu, có thể lớn hơn, và sau `Return` caller không còn quyền sử dụng nó.

## 2. Why does it exist?

Các hot path như serialization, compression, parsing hoặc network processing có thể tạo rất nhiều temporary arrays. Allocation rate cao làm GC chạy thường xuyên; buffer lớn còn có thể đi vào LOH. Pooling giảm allocation pressure khi profiling chứng minh buffer churn là bottleneck.

## 3. How does it work?

```text
Rent(size)
   |
   v
shared pool -> reusable array
   |
 application owns temporarily
   |
Return(array)
   v
shared pool
```

Pool không bảo đảm array được zero trước khi giao cho caller mới. `Rent(4096)` cũng không bảo đảm `Length == 4096`.

## 4. Practical implementation

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(16 * 1024);

try
{
    var read = await stream.ReadAsync(
        buffer.AsMemory(0, 16 * 1024), cancellationToken);

    await ProcessAsync(buffer.AsMemory(0, read), cancellationToken);
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

Chỉ truyền slice chứa dữ liệu hợp lệ; không truyền toàn bộ rented array cho serializer hoặc downstream API.

## 5. Real production scenario

File-processing API đọc hàng nghìn ảnh nhỏ mỗi phút. Profiling cho thấy temporary `byte[]` chiếm phần lớn allocation rate. Pooling buffer đọc file giảm GC pressure đáng kể mà không cần thay architecture.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu request A đôi khi xuất hiện trong output request B hoặc corruption xảy ra ngẫu nhiên.  
**Evidence** → code giữ reference sau `Return`, hoặc consumer dùng toàn bộ `buffer.Length`.  
**Hypothesis** → ownership violation / stale bytes.  
**Diagnosis** → trace lifecycle `Rent` → use → `Return`, kiểm tra async callbacks giữ buffer.  
**Fix** → không dùng buffer sau return; truyền exact `Memory<T>` slice; `clearArray: true` nếu dữ liệu nhạy cảm và threat model yêu cầu.  
**Verification** → stress test concurrent operations và kiểm tra allocation profile.

## 7. Common mistakes

Pooling mọi array dù allocation không đáng kể; quên `Return`; double-return; dùng buffer sau return; assume buffer được zero; giữ rented buffer lâu làm pool kém hiệu quả; tối ưu trước khi đo.

## 8. Alternatives

Array allocation bình thường đơn giản và thường đủ tốt. `MemoryPool<T>` hữu ích khi cần memory-owner abstraction. `Span<T>` giúp tránh copy nhưng không tự pooling storage.

## 9. Trade-offs

### Advantages

Giảm allocation rate, GC pressure và LOH churn trong hot path.

### Costs / Risks

Ownership phức tạp hơn, có nguy cơ data leakage/corruption và code khó review hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Rent`/`Return` và không dùng buffer sau return.

### Middle

Dùng `try/finally`, slice đúng length và benchmark allocation.

### Senior

Đánh giá lifetime, concurrency, sensitive-data clearing và GC evidence.

### Technical Lead / Architect

Quyết định pooling có đáng complexity hay không dựa trên profiling và SLO, thay vì biến nó thành coding convention.

## 11. Key takeaway

- Pooling đổi allocation cost lấy ownership complexity.
- Rented buffer có thể lớn hơn yêu cầu và chứa dữ liệu cũ.
- Chỉ dùng `ArrayPool<T>` khi measurement chứng minh allocation là vấn đề.

# 2. ASP.NET Core streaming response: backpressure, cancellation và memory profile

## 1. What is it?

Streaming response gửi dữ liệu dần xuống client thay vì materialize toàn bộ payload trong memory trước khi response bắt đầu. Nó đặc biệt hữu ích với file lớn, export hoặc sequence dài.

## 2. Why does it exist?

Nếu API tạo file 500 MB trong `MemoryStream` rồi mới gửi, mỗi request có thể giữ hàng trăm MB managed memory. Nhiều request đồng thời biến memory thành capacity bottleneck dù network và storage vẫn ổn.

## 3. How does it work?

```text
Storage -> application buffer -> response pipe -> network -> client
                     ^
                     |
                backpressure
```

Khi client/network đọc chậm, write async có thể chậm theo. Application phải tôn trọng backpressure và `RequestAborted`, thay vì tiếp tục producer không giới hạn.

## 4. Practical implementation

```csharp
app.MapGet("/exports/{name}", async (
    string name,
    HttpContext context,
    BlobService blobService) =>
{
    await using var source = await blobService.OpenReadAsync(
        name, context.RequestAborted);

    context.Response.ContentType = "application/octet-stream";
    await source.CopyToAsync(
        context.Response.Body,
        64 * 1024,
        context.RequestAborted);
});
```

Nếu biết length/type, set headers phù hợp. Không buffer lại toàn file ở application chỉ để “stream”.

## 5. Real production scenario

Reporting endpoint export CSV hàng triệu rows. Thay vì `ToListAsync()` rồi build một string lớn, application đọc theo batch/stream và flush dần, giữ memory tương đối ổn định.

## 6. Failure scenario & troubleshooting

**Symptom** → memory vẫn tăng dù endpoint được gọi là streaming.  
**Evidence** → heap profile thấy `List<T>`, `MemoryStream` hoặc giant strings trước response write.  
**Hypothesis** → upstream vẫn materialize toàn bộ dữ liệu.  
**Diagnosis** → theo data flow từ DB/storage tới response.  
**Fix** → stream/batch từ source; propagate cancellation; tránh unbounded producer.  
**Verification** → load test concurrent downloads và quan sát working set, GC, throughput.

## 7. Common mistakes

Streaming ở HTTP layer nhưng `ToListAsync()` ở repository; bỏ `CancellationToken`; write từng byte/chunk quá nhỏ; không kiểm soát compression CPU; assume streaming luôn nhanh hơn.

## 8. Alternatives

Buffered response đơn giản hơn cho payload nhỏ. Direct-to-Blob download bằng SAS có thể bỏ application khỏi data path. Background export + object storage phù hợp report rất lớn hoặc generation lâu.

## 9. Trade-offs

### Advantages

Memory ổn định hơn, time-to-first-byte tốt hơn, xử lý payload lớn.

### Costs / Risks

Error handling sau khi headers đã gửi khó hơn; connection sống lâu; slow clients tiêu thụ concurrency; observability cần đo duration và bytes.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu streaming khác buffering.

### Middle

Implement async copy và cancellation.

### Senior

Reason về backpressure, source materialization, connection lifetime và load profile.

### Technical Lead / Architect

Quyết định application có nên nằm trong data path hay nên dùng object storage/direct download.

## 11. Key takeaway

- Streaming chỉ có ý nghĩa nếu upstream cũng không materialize toàn payload.
- Slow client tạo backpressure và giữ resource lâu.
- Với file lớn, direct object-storage delivery thường đơn giản hơn.

# 3. EF Core split queries: tránh cartesian explosion nhưng chấp nhận nhiều round trips

## 1. What is it?

`AsSplitQuery()` yêu cầu EF Core tải graph có nhiều collection bằng nhiều SQL queries thay vì một JOIN query khổng lồ. Nó giải quyết cartesian explosion/data duplication, không phải universal performance switch.

## 2. Why does it exist?

Một `Order` có `Items` và `Payments`. JOIN cả hai collections có thể nhân rows: 20 items × 5 payments = 100 rows cho một order. Parent columns bị lặp lại và network/materialization cost tăng mạnh.

## 3. How does it work?

Single query:

```text
Orders JOIN Items JOIN Payments -> row multiplication
```

Split query:

```text
Query Orders
Query Items for selected Orders
Query Payments for selected Orders
EF Core assembles graph
```

Đổi lại, application có nhiều database commands và consistency window giữa các queries.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Include(x => x.Items)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .AsNoTracking()
    .ToListAsync(cancellationToken);
```

Trước khi dùng `Include`, hỏi liệu API thực sự cần entity graph hay projection DTO sẽ tốt hơn.

## 5. Real production scenario

Admin order-details page include nhiều collections. Single SQL trả hàng chục nghìn rows dù chỉ có vài chục entities thực. Split query giảm bytes transferred và materialization CPU.

## 6. Failure scenario & troubleshooting

**Symptom** → sau chuyển sang split query, latency tăng ở environment database xa application.  
**Evidence** → trace cho thấy nhiều SQL round trips, mỗi round trip có network latency đáng kể.  
**Hypothesis** → giảm row duplication nhưng tăng network cost.  
**Diagnosis** → so actual rows, bytes và dependency spans single vs split.  
**Fix** → projection, giảm collections, hoặc single query nếu dataset nhỏ.  
**Verification** → benchmark production-like cardinality/network latency.

## 7. Common mistakes

Bật split query global không đo; dùng `Include` để phục vụ DTO đơn giản; bỏ qua consistency giữa queries; nghĩ nhiều SQL luôn là N+1; chỉ nhìn query duration mà không nhìn transferred rows.

## 8. Alternatives

Projection thường tốt nhất cho read API. Single query tốt khi graph nhỏ. Explicit queries cho phép kiểm soát sâu hơn nhưng tăng code.

## 9. Trade-offs

### Advantages

Giảm cartesian explosion, duplicate data và materialization pressure.

### Costs / Risks

Nhiều round trips, consistency window, query orchestration phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` tạo JOIN/data loading.

### Middle

Nhận diện cartesian explosion và thử `AsSplitQuery`.

### Senior

So row cardinality, network latency, consistency và projection alternatives.

### Technical Lead / Architect

Đặt guideline read-model: entity graph chỉ khi thực sự cần, projection cho contract-oriented APIs.

## 11. Key takeaway

- Split query đổi row explosion lấy round trips.
- Projection thường tránh được cả hai cực đoan.
- Đo với cardinality và network giống Production.

# 4. Redis hot key: khi distributed cache vẫn có single-point bottleneck

## 1. What is it?

Hot key là key nhận lượng traffic vượt trội so với phần còn lại. Dù Redis cluster phân phối keys, một key cụ thể thường vẫn được phục vụ bởi một shard/node chính, nên traffic không tự chia đều.

## 2. Why does it exist?

Caching thường được thêm để giảm database load. Nhưng nếu mọi request homepage đều đọc cùng một giant key, bottleneck chỉ chuyển từ database sang Redis/network/serialization.

## 3. How does it work?

```text
100 app instances
      |
      +------> product:homepage  ----> one owning shard
      |
      +------> product:homepage
```

Hash distribution cân bằng nhiều keys; nó không phân tán một key đơn lẻ thành nhiều independent reads.

## 4. Practical implementation

Có thể thêm L1 local cache ngắn trước distributed cache khi staleness cho phép:

```csharp
if (memory.TryGetValue(key, out ProductPage? page))
    return page!;

page = await redis.GetAsync<ProductPage>(key, ct);
memory.Set(key, page, TimeSpan.FromSeconds(5));
return page;
```

Đây chỉ là một lựa chọn; phải xác định invalidation/freshness semantics.

## 5. Real production scenario

Flash sale làm một catalog key nhận hàng chục nghìn reads/s. Database load thấp nhưng Redis node CPU/network tăng và API p99 xấu đi.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis latency tăng nhưng tổng key count/cluster capacity nhìn vẫn dư.  
**Evidence** → command/key sampling cho thấy traffic tập trung vào một key.  
**Hypothesis** → hot key.  
**Diagnosis** → correlate Redis node metrics, key access và payload size.  
**Fix** → local caching, split payload/access pattern, replication/read strategy hoặc bỏ cache nếu computation rẻ.  
**Verification** → load phân tán hơn và p95/p99 giảm.

## 7. Common mistakes

Assume cluster giải quyết hot key; cache object quá lớn; TTL đồng loạt gây stampede; thêm distributed lock vào read path mà không hiểu contention; không có fallback khi Redis chậm.

## 8. Alternatives

`IMemoryCache` rất nhanh nhưng per-instance và stale independently. CDN/edge cache phù hợp public HTTP content. Database/read replica có thể đủ nếu query rẻ và cache complexity không đáng.

## 9. Trade-offs

### Advantages

Distributed cache giảm source load và chia sẻ state giữa instances.

### Costs / Risks

Hot keys tạo hidden central dependency; local cache giảm load nhưng tăng staleness/invalidation complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu distributed cache không có nghĩa mỗi key được phân tán.

### Middle

Đo key traffic, TTL và payload.

### Senior

Thiết kế multi-level caching/fallback theo freshness requirement.

### Technical Lead / Architect

Quyết định liệu cache có thực sự cần tồn tại và ai sở hữu invalidation/operational SLO.

## 11. Key takeaway

- Cluster cân bằng keys, không tự cân bằng một hot key.
- Cache có thể trở thành bottleneck mới.
- Freshness requirement quyết định có thể dùng L1/edge cache hay không.

# 5. CQRS với một database: separation of intent trước khi tách storage

## 1. What is it?

CQRS tách command (thay đổi state) khỏi query (đọc state) ở mức intent/model. CQRS không bắt buộc hai databases, Event Sourcing hoặc microservices.

## 2. Why does it exist?

Read và write thường có nhu cầu khác nhau. Write cần enforce invariant; read cần projection phù hợp UI. Ép cùng một domain entity/repository phục vụ cả hai có thể tạo abstraction khó hiểu và query kém hiệu quả.

## 3. How does it work?

```text
HTTP POST -> Command -> Handler -> Domain/EF -> same SQL DB
HTTP GET  -> Query   -> Handler -> Projection -> same SQL DB
```

Boundary nằm ở model/intent; transaction vẫn đơn giản trong một database.

## 4. Practical implementation

```csharp
public sealed record GetOrderQuery(Guid Id);
public sealed record ApproveOrderCommand(Guid Id, byte[] Version);
```

Query handler có thể projection trực tiếp:

```csharp
return await db.Orders
    .AsNoTracking()
    .Where(x => x.Id == query.Id)
    .Select(x => new OrderDto(x.Id, x.Status, x.Total))
    .SingleAsync(ct);
```

Không cần tạo read database chỉ vì đã có `Command`/`Query` classes.

## 5. Real production scenario

Approval workflow có write rules phức tạp nhưng dashboard cần aggregate nhanh. Command dùng domain logic; query dùng SQL/EF projection tối ưu, cùng một SQL Server.

## 6. Failure scenario & troubleshooting

**Symptom** → codebase có hàng trăm handlers nhưng logic vẫn CRUD đơn giản, navigation khó hơn trước.  
**Evidence** → mỗi handler chỉ gọi generic repository một dòng.  
**Hypothesis** → CQRS ceremony không giải quyết complexity thật.  
**Diagnosis** → xem business invariants/read-model divergence có tồn tại không.  
**Fix** → đơn giản hóa hoặc chỉ áp dụng ở module cần separation.  
**Verification** → change flow dễ hiểu hơn mà không mất testability.

## 7. Common mistakes

Đồng nhất CQRS với MediatR; tách database quá sớm; bắt mọi CRUD đi qua command/query ceremony; gọi read model là eventual consistency dù dùng cùng transaction store.

## 8. Alternatives

Layered application service đơn giản hơn cho CRUD. Separate read store hữu ích khi scale/query model thực sự khác. Event Sourcing là quyết định độc lập với chi phí lớn hơn nhiều.

## 9. Trade-offs

### Advantages

Intent rõ, read projection tự do, write invariant tập trung.

### Costs / Risks

Nhiều types/handlers, navigation overhead, dễ overengineering.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt read intent và state-changing intent.

### Middle

Implement command/query handlers và projection.

### Senior

Biết khi separation giúp domain/read performance và khi chỉ tạo ceremony.

### Technical Lead / Architect

Quyết định CQRS ở boundary nào; không mặc định tách storage khi business chưa cần.

## 11. Key takeaway

- CQRS trước hết là separation of intent/model.
- Một database vẫn là CQRS hợp lệ.
- Tách read/write stores chỉ khi scale, model hoặc operational requirement biện minh.

# 6. Azure Functions concurrency: scale-out không đồng nghĩa downstream chịu được tải

## 1. What is it?

Azure Functions có thể xử lý nhiều executions đồng thời trên một instance và scale ra nhiều instances. Effective concurrency của toàn hệ thống là concurrency mỗi instance × số instances, nên downstream capacity phải được tính cùng.

## 2. Why does it exist?

Serverless scale giúp hấp thụ workload nhanh, nhưng database, third-party API hoặc legacy service không tự scale theo. Một consumer scale quá mạnh có thể biến queue backlog thành dependency outage.

## 3. How does it work?

```text
Service Bus backlog
       |
       v
Functions instances x concurrency
       |
       v
SQL / external API capacity
```

Trigger settings, runtime scaling và hosting plan cùng ảnh hưởng throughput. Message delivery vẫn cần idempotency vì retry/duplicate có thể xảy ra.

## 4. Practical implementation

Application-level bounded concurrency có thể bảo vệ dependency trong một process:

```csharp
private static readonly SemaphoreSlim Gate = new(20);

await Gate.WaitAsync(ct);
try
{
    await downstream.ProcessAsync(item, ct);
}
finally
{
    Gate.Release();
}
```

Nhưng semaphore per-instance không tạo global limit; scale-out vẫn nhân tổng concurrency.

## 5. Real production scenario

Queue import có 100k messages. Functions scale từ 2 lên 30 instances; mỗi instance mở nhiều SQL operations. SQL connection/CPU saturation làm execution chậm, lock duration tăng và retries tạo thêm load.

## 6. Failure scenario & troubleshooting

**Symptom** → scale-out tăng nhưng throughput giảm, queue backlog tiếp tục tăng.  
**Evidence** → SQL latency/connection pressure tăng cùng instance count; retry count tăng.  
**Hypothesis** → downstream saturation.  
**Diagnosis** → tính arrival rate, service rate và effective concurrency.  
**Fix** → giới hạn concurrency/scale, batch hợp lý, tăng downstream capacity hoặc redesign workload.  
**Verification** → throughput ổn định và dependency latency không vượt SLO.

## 7. Common mistakes

Chỉ nhìn Function CPU; assume autoscale luôn cải thiện throughput; retry aggressive; không có idempotency; dùng per-instance semaphore rồi nghĩ đã có global throttle.

## 8. Alternatives

Worker Service/Container Apps cho control concurrency rõ hơn. Queue vẫn hữu ích để absorb burst. Logic Apps phù hợp orchestration low-code nhưng không thay capacity planning.

## 9. Trade-offs

### Advantages

Elastic scale, operational simplicity cho event-driven workloads.

### Costs / Risks

Scale có thể khuếch đại downstream pressure và cloud cost; concurrency behavior cần được đo end-to-end.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu scale-out tạo thêm consumers.

### Middle

Cấu hình/test concurrency và idempotency.

### Senior

Reason về queue rate, downstream capacity, retries và lock duration.

### Technical Lead / Architect

Đặt system-level concurrency budget thay vì tối ưu riêng Function.

## 11. Key takeaway

- Consumer scale phải bị giới hạn bởi slowest sustainable dependency.
- Per-instance concurrency không phải global concurrency.
- Queue hấp thụ burst nhưng không tạo downstream capacity.

# 7. Kubernetes resource requests/limits: scheduling, throttling và OOMKilled

## 1. What is it?

`requests` mô tả resource scheduler dùng để đặt Pod; `limits` đặt upper bound runtime cho container. CPU vượt limit thường bị throttled; memory vượt limit có thể dẫn tới OOM kill.

## 2. Why does it exist?

Cluster cần biết workload cần bao nhiêu capacity và cần cô lập noisy neighbors. Không có requests hợp lý, scheduler có thể overpack node; limits sai lại có thể bóp nghẹt ứng dụng.

## 3. How does it work?

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
```

Scheduler chủ yếu dùng requests để placement. Runtime/cgroup enforce limits. .NET process thấy memory pressure thực tế trong container, không nên được capacity-plan như VM không giới hạn.

## 4. Practical implementation

Load test để lấy working set/CPU percentiles, sau đó đặt requests gần sustainable baseline và memory limit có headroom hợp lý. Theo dõi `container_cpu_cfs_throttled_*`, working set, restart reason và application latency.

## 5. Real production scenario

API bình thường dùng 300 MiB nhưng startup/load spike lên 480 MiB. Memory limit 400 MiB khiến pod restart trong rollout; readiness chưa kịp pass và deployment mất capacity.

## 6. Failure scenario & troubleshooting

**Symptom** → Pod restart với `OOMKilled` hoặc latency tăng dù node CPU còn dư.  
**Evidence** → `kubectl describe pod`, container metrics, throttling counters.  
**Hypothesis** → memory limit quá thấp hoặc CPU throttling.  
**Diagnosis** → correlate resource metrics với GC/requests.  
**Fix** → sửa leak/allocation hoặc tune request/limit dựa trên measurement.  
**Verification** → rollout/load test không restart và p95 ổn định.

## 7. Common mistakes

Copy resource values giữa services; đặt request = limit cực cao để “an toàn”; bỏ limits hoàn toàn mà không hiểu tenancy; tăng memory limit thay vì điều tra leak; chỉ nhìn average CPU.

## 8. Alternatives

VM/App Service giảm Kubernetes tuning burden. Vertical/Horizontal Pod Autoscaler hỗ trợ điều chỉnh nhưng vẫn cần hiểu workload và dependency constraints.

## 9. Trade-offs

### Advantages

Scheduling predictable hơn, isolation tốt hơn, capacity planning rõ hơn.

### Costs / Risks

Sai số tạo wasted capacity, throttling hoặc OOM; tuning cần production-like measurements.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt requests và limits.

### Middle

Đọc Pod status/metrics và nhận diện OOM/throttling.

### Senior

Liên hệ GC, workload burst, autoscaling và resource envelopes.

### Technical Lead / Architect

Đánh giá Kubernetes complexity có đáng hay managed platform đơn giản hơn đủ dùng.

## 11. Key takeaway

- Requests phục vụ scheduling; limits phục vụ enforcement.
- CPU limit và memory limit thất bại theo cách khác nhau.
- Resource values phải đến từ measurement, không phải template copy-paste.

# 8. SQL Server connection pool exhaustion: phân biệt pool pressure với database CPU

## 1. What is it?

ADO.NET connection pooling giữ physical connections để tái sử dụng. Pool exhaustion xảy ra khi callers chờ connection vì pool đã đạt capacity hoặc connections bị giữ quá lâu; database CPU có thể vẫn chưa cao.

## 2. Why does it exist?

Mở physical DB connection có chi phí. Pooling giảm handshake/authentication overhead. Nhưng pool là bounded resource; slow queries, transactions dài hoặc leaked connections biến nó thành queue trước database.

## 3. How does it work?

```text
Requests -> connection pool -> SQL Server
              | all busy
              v
           wait/timeout
```

Pool được phân chia theo connection string/credential identity. `DbConnection.Close/Dispose` thường trả connection về pool chứ không đóng physical connection ngay.

## 4. Practical implementation

Với EF Core, giữ `DbContext` theo unit of work ngắn và tránh transaction bao quanh remote calls:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);
await ApplyDatabaseChangesAsync(db, ct);
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Không gọi external HTTP chậm bên trong transaction nếu không có lý do business mạnh.

## 5. Real production scenario

API p95 tăng đột ngột; SQL CPU chỉ 35%. Trace cho thấy request mất nhiều giây trước SQL dependency span. Một transaction giữ connection trong lúc chờ payment API 8 giây.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout “prior to obtaining a connection from the pool”.  
**Evidence** → active connection count cao, DB CPU bình thường, transaction/request duration dài.  
**Hypothesis** → connections bị giữ lâu hoặc leak.  
**Diagnosis** → correlate pool counters, traces, slow transactions và code ownership.  
**Fix** → rút ngắn DB scope/transaction, dispose đúng; chỉ tăng pool sau khi hiểu capacity.  
**Verification** → connection wait giảm và throughput tăng mà DB không saturation.

## 7. Common mistakes

Tăng `Max Pool Size` như fix đầu tiên; giữ transaction qua HTTP call; tạo nhiều connection strings gần giống nhau làm phân mảnh pools; singleton `DbContext`; không propagate cancellation.

## 8. Alternatives

Tăng pool có thể phù hợp nếu DB thực sự chịu được thêm concurrency. Queue/background processing có thể làm phẳng burst. Query optimization giảm hold time nếu query là nguyên nhân.

## 9. Trade-offs

### Advantages

Pooling giảm connection setup cost và tăng throughput.

### Costs / Risks

Pool che giấu bounded-resource contention; tăng pool quá mức có thể chuyển saturation sang database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dispose trả connection về pool.

### Middle

Giữ context/transaction ngắn và đọc timeout evidence.

### Senior

Phân biệt pool wait, slow SQL, locks và DB CPU saturation.

### Technical Lead / Architect

Đặt concurrency budget từ application tới database, không tune pool độc lập.

## 11. Key takeaway

- Connection pool exhaustion có thể xảy ra khi DB CPU còn thấp.
- Connection hold time quan trọng không kém pool size.
- Tăng pool chỉ chuyển bottleneck nếu database không có capacity.

# 9. Git `bisect`: tìm deployment regression bằng binary search thay vì đọc commit history

## 1. What is it?

`git bisect` dùng binary search trên commit graph giữa một commit “good” và một commit “bad” để tìm commit đầu tiên gây regression.

## 2. Why does it exist?

Nếu release có 200 commits và bug chỉ xuất hiện sau release, đọc từng diff hoặc revert ngẫu nhiên tốn thời gian. Binary search giảm số lần kiểm tra xuống khoảng `log2(N)` khi có test/reproduction đáng tin cậy.

## 3. How does it work?

```text
good --------------------------- bad
                  ^ test midpoint
          good <--|--> bad
                     ^ next midpoint
```

Mỗi lần đánh dấu `good`/`bad`, Git thu hẹp phạm vi commit.

## 4. Practical implementation

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.8.0

# chạy reproduction/test
git bisect good   # hoặc bad

# khi xong
git bisect reset
```

Có thể automate:

```bash
git bisect run dotnet test tests/Regression.Tests
```

Exit code của script phải phản ánh good/bad đúng.

## 5. Real production scenario

Sau deployment, CSV export bắt đầu encode sai ký tự. Có 120 commits từ release trước. Một deterministic regression test cho phép `bisect run` tìm commit gây lỗi trong vài lần build/test.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit không liên quan hoặc kết quả thay đổi giữa runs.  
**Evidence** → reproduction flaky hoặc intermediate commits không build.  
**Hypothesis** → test oracle không deterministic.  
**Diagnosis** → chạy test nhiều lần, kiểm tra environment/data dependency.  
**Fix** → ổn định reproduction; dùng `git bisect skip` khi commit không test được.  
**Verification** → culprit commit tái tạo regression và parent không tái tạo.

## 7. Common mistakes

Chọn “good” commit chưa thực sự verified; dùng flaky E2E; quên reset; kết luận commit là root cause chỉ vì bisect chỉ tới nó mà không đọc diff/reproduce parent-child.

## 8. Alternatives

Logs/traces xác định symptom runtime; `git log`/PR review tốt khi phạm vi nhỏ; feature flags giúp isolate behavior. Bisect mạnh khi regression deterministic và commit range lớn.

## 9. Trade-offs

### Advantages

Thu hẹp regression rất nhanh và evidence-driven.

### Costs / Risks

Build/test intermediate commits tốn thời gian; merge history và flaky tests làm kết quả khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết good/bad commit concept.

### Middle

Chạy manual bisect và xác minh culprit.

### Senior

Automate reproduction, xử lý skipped commits và phân biệt culprit với systemic root cause.

### Technical Lead / Architect

Đầu tư deterministic regression tests và release traceability để incident investigation nhanh hơn.

## 11. Key takeaway

- `git bisect` biến regression search thành binary search.
- Chất lượng kết quả phụ thuộc test oracle deterministic.
- Sau bisect vẫn phải phân tích vì sao commit gây failure.

# 10. React stale closure: async UI state và API correctness cho full-stack engineer

## 1. What is it?

Trong React functional components, callback/async operation capture values từ render nơi nó được tạo. Stale closure xảy ra khi callback chạy sau nhưng vẫn thấy state/props cũ, dẫn tới UI hoặc API request dùng dữ liệu lỗi thời.

## 2. Why does it exist?

JavaScript closure giữ lexical bindings; React render tạo snapshot logic mới. Async work, timers và effects sống qua nhiều renders, nên “state hiện tại” không tự động thay thế giá trị đã capture trong callback cũ.

## 3. How does it work?

```text
Render A: query = "car"
  -> async callback captures "car"
Render B: query = "cars"
  -> newer request starts
Old request finishes later
  -> callback from Render A may update UI with old result
```

Đây còn là race condition giữa requests, không chỉ dependency-array issue.

## 4. Practical implementation

Hủy request cũ khi input đổi:

```tsx
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(query)}`,
      { signal: controller.signal });
    const data = await response.json();
    setResults(data);
  }

  void load();
  return () => controller.abort();
}, [query]);
```

Backend cũng nên propagate disconnect/cancellation nếu request bị abort.

## 5. Real production scenario

Autocomplete gửi request cho `ca`, `car`, `cars`. Response `ca` chậm nhất và về cuối, ghi đè result mới. User thấy kết quả không khớp input dù backend trả đúng từng request.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị dữ liệu cũ khi thao tác nhanh.  
**Evidence** → browser Network cho thấy responses hoàn thành khác thứ tự gửi.  
**Hypothesis** → stale async result/race.  
**Diagnosis** → log request sequence/query và component render.  
**Fix** → abort previous request hoặc sequence/version guard; dependencies đúng.  
**Verification** → throttle network trong DevTools và thao tác nhanh lặp lại.

## 7. Common mistakes

Thêm mọi thứ vào dependency array mà không hiểu lifecycle; bỏ dependency để “ngăn effect chạy”; assume response order = request order; backend không hỗ trợ cancellation; dùng global mutable variable để vá race.

## 8. Alternatives

Data-fetching libraries có cancellation/deduplication/cache semantics tốt hơn cho ứng dụng lớn. Server-driven rendering có thể giảm một số client races nhưng không loại bỏ async UI state.

## 9. Trade-offs

### Advantages

Functional rendering giúp state flow rõ khi lifecycle được hiểu đúng.

### Costs / Risks

Async closures và effect lifecycle dễ tạo race tinh vi; abstraction library thêm dependency/learning cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mỗi render có snapshot state riêng.

### Middle

Quản lý effect dependencies và abort fetch cũ.

### Senior

Phân biệt stale closure với request-order race, cache race và backend consistency.

### Technical Lead / Architect

Chuẩn hóa data-fetching/cancellation pattern giữa frontend và API để tránh mỗi component tự phát minh lifecycle riêng.

## 11. Key takeaway

- Async callback có thể giữ state từ render cũ.
- Request gửi trước không bảo đảm response về trước.
- Frontend cancellation nên nối với backend cancellation để giảm cả correctness bug lẫn wasted work.
