# 1. .NET `IAsyncEnumerable<T>`: streaming, cancellation và backpressure boundary

## 1. What is it?

`IAsyncEnumerable<T>` biểu diễn một chuỗi dữ liệu được tạo bất đồng bộ theo thời gian. Mental model: consumer không cần đợi toàn bộ collection hoàn tất trước khi xử lý phần tử đầu tiên; mỗi bước enumeration có thể `await` I/O.

## 2. Why does it exist?

`Task<List<T>>` buộc producer materialize toàn bộ kết quả trước khi trả. Với dataset lớn hoặc nguồn dữ liệu chậm, điều đó tăng time-to-first-byte và memory. Async streaming cho phép pipeline xử lý dần, nhưng không tự động giải quyết downstream chậm.

## 3. How does it work?

Compiler biến async iterator thành state machine. Consumer gọi `MoveNextAsync()` qua `await foreach`; producer chỉ tiến tiếp khi consumer yêu cầu phần tử kế tiếp.

```text
DB/API → async iterator → consumer → response
           one item        one item
```

## 4. Practical implementation

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct)
{
    await foreach (var order in _db.Orders
        .AsNoTracking()
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        yield return new OrderDto(order.Id, order.Total);
    }
}
```

Consumer phải truyền cancellation và tránh buffer lại toàn bộ bằng `ToListAsync()` nếu mục tiêu là streaming.

## 5. Real production scenario

Export API trả hàng trăm nghìn rows. Streaming cho phép bắt đầu gửi dữ liệu sớm và giữ memory ổn định hơn so với tạo một `List` khổng lồ.

## 6. Failure scenario & troubleshooting

**Symptom** → memory vẫn tăng dù dùng `IAsyncEnumerable`. **Evidence** → profiler cho thấy consumer tích lũy objects. **Hypothesis** → downstream buffer lại hoặc serialization layer chưa thực sự stream. **Diagnosis** → trace allocation và response buffering. **Fix** → streaming end-to-end, cancellation, giới hạn payload. **Verification** → load test theo memory + time-to-first-byte.

## 7. Common mistakes

Dùng async iterator nhưng materialize ở tầng kế tiếp; bỏ cancellation; giữ `DbContext`/connection rất lâu; coi streaming là vô hạn mà không có pagination hoặc resource budget.

## 8. Alternatives

Pagination đơn giản hơn cho request/response thông thường. `Channel<T>` phù hợp producer/consumer concurrent trong process. Messaging phù hợp workload dài và durable.

## 9. Trade-offs

### Advantages

Giảm buffering, cải thiện time-to-first-item và phù hợp dữ liệu được tạo dần.

### Costs / Risks

Resource lifetime dài hơn; lỗi có thể xảy ra sau khi response đã bắt đầu; observability và retry phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async stream khác `Task<List<T>>` ở thời điểm dữ liệu được tạo và tiêu thụ.

### Middle

Implement iterator, cancellation và tránh accidental buffering.

### Senior

Phân tích connection lifetime, serialization, slow consumer và failure giữa stream.

### Technical Lead / Architect

Quyết định streaming, pagination hay asynchronous export dựa trên payload, SLA và operational cost.

## 11. Key takeaway

- Streaming phải end-to-end mới giảm buffering thật.
- Cancellation và resource lifetime là phần của thiết kế.
- Không dùng streaming chỉ vì dataset “có vẻ lớn”.

# 2. EF Core `DbContext` pooling: giảm allocation nhưng state leakage có thể phá correctness

## 1. What is it?

`AddDbContextPool` tái sử dụng `DbContext` instances thay vì tạo mới hoàn toàn cho mỗi scope. Đây là object pooling, không phải database connection pooling.

## 2. Why does it exist?

Khởi tạo context và internal services có overhead. Trong high-throughput workload, pooling có thể giảm allocation và initialization cost khi profiling chứng minh đây là bottleneck.

## 3. How does it work?

Context được lấy từ pool, dùng trong scope, reset rồi trả lại pool. Database connection vẫn do ADO.NET pool quản lý riêng.

## 4. Practical implementation

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Không nên giữ mutable request-specific state trong context, ví dụ tự gán `TenantId` rồi giả định instance sẽ bị hủy sau request.

## 5. Real production scenario

Multi-tenant API dùng global query filter phụ thuộc tenant. Nếu tenant state được lưu sai trên pooled context, request sau có thể inherit state không mong muốn và tạo data-isolation bug.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu tenant sai xuất hiện hiếm dưới load. **Evidence** → context instance reuse + mutable tenant field. **Diagnosis** → state không reset đúng. **Fix** → đưa request state ra scoped service hoặc dùng factory pattern phù hợp. **Verification** → concurrent integration test nhiều tenant.

## 7. Common mistakes

Nhầm DbContext pooling với connection pooling; bật pooling trước khi benchmark; lưu mutable request state; giữ context ngoài scope.

## 8. Alternatives

`AddDbContext` thông thường đơn giản và an toàn hơn cho đa số ứng dụng. `IDbContextFactory<T>` hữu ích khi lifetime không khớp request scope.

## 9. Trade-offs

### Advantages

Giảm allocation/init overhead trong workload phù hợp.

### Costs / Risks

Stateful customization khó hơn và correctness risk tăng nếu context chứa request-specific state.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt context pool và DB connection pool.

### Middle

Cấu hình và benchmark đúng.

### Senior

Review state leakage, tenant boundary và concurrency assumptions.

### Technical Lead / Architect

Chỉ đưa pooling vào khi measurement chứng minh lợi ích lớn hơn complexity.

## 11. Key takeaway

- Pooling là optimization, không phải default architecture requirement.
- Pooled context phải được coi như reusable object.
- Correctness quan trọng hơn vài allocation tiết kiệm được.

# 3. PostgreSQL JSONB + GIN: linh hoạt schema nhưng vẫn phải thiết kế access pattern

## 1. What is it?

`jsonb` lưu JSON ở dạng binary representation có thể query/index. GIN index hỗ trợ tra cứu các keys/values theo operator phù hợp.

## 2. Why does it exist?

Một số attributes biến đổi theo loại entity khiến việc thêm hàng chục nullable columns không hợp lý. `jsonb` cho phép giữ phần linh hoạt trong relational database mà chưa cần thêm document database.

## 3. How does it work?

PostgreSQL parse JSONB và GIN index nhiều tokens/paths. Query operator phải tương thích index; không phải mọi expression trên JSON đều tự động nhanh.

## 4. Practical implementation

```sql
CREATE INDEX ix_products_attributes_gin
ON products USING GIN (attributes);

SELECT id, name
FROM products
WHERE attributes @> '{"color":"black"}';
```

Đo bằng `EXPLAIN (ANALYZE, BUFFERS)` thay vì chỉ nhìn index tồn tại.

## 5. Real production scenario

Marketplace có attributes khác nhau cho car, motorcycle và accessories. Core fields vẫn relational; category-specific attributes nằm JSONB.

## 6. Failure scenario & troubleshooting

**Symptom** → filter JSON chậm khi data tăng. **Evidence** → plan dùng sequential scan, buffer reads cao. **Diagnosis** → operator/expression không match GIN index hoặc selectivity thấp. **Fix** → index strategy theo query thật, có thể expression index cho hot fields. **Verification** → so plan/I/O trước và sau.

## 7. Common mistakes

Đẩy toàn bộ schema vào JSONB; bỏ constraints cho dữ liệu quan trọng; tạo GIN index lớn nhưng ít query; assume JSONB = MongoDB trong PostgreSQL.

## 8. Alternatives

Normalized tables tốt hơn cho relational invariants và joins. MongoDB phù hợp nếu document access pattern chi phối toàn hệ thống.

## 9. Trade-offs

### Advantages

Schema flexibility trong cùng transaction/database; query JSON mạnh.

### Costs / Risks

Index lớn, validation khó hơn, analytics/query evolution có thể phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu JSONB không thay thế mọi column.

### Middle

Viết query/index và đọc execution plan.

### Senior

Đánh giá selectivity, index size, constraints và migration path.

### Technical Lead / Architect

Quyết định boundary giữa relational model và flexible attributes theo business invariants.

## 11. Key takeaway

- JSONB hữu ích cho phần schema thực sự linh hoạt.
- Index phải xuất phát từ access pattern.
- Luôn kiểm tra plan và I/O.

# 4. Redis hot keys: khi distributed cache bị nghẽn ở một key thay vì thiếu tổng capacity

## 1. What is it?

Hot key là key nhận lượng traffic bất cân xứng so với phần còn lại. Trong distributed cache, tổng cluster còn capacity nhưng một shard/node có thể trở thành bottleneck vì key đó.

## 2. Why does it exist?

Load distribution chỉ tốt nếu access phân tán. Homepage, global configuration hoặc flash-sale product có thể tập trung hàng chục nghìn reads lên một key.

## 3. How does it work?

Hashing route một key tới một partition. Tăng số nodes không tự chia một key thành nhiều keys.

## 4. Practical implementation

Giảm repeated remote reads bằng near-cache có TTL rất ngắn cho immutable/tolerably-stale data:

```csharp
var value = await memoryCache.GetOrCreateAsync(key, async entry =>
{
    entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromSeconds(2);
    return await redis.StringGetAsync(key);
});
```

Chỉ áp dụng khi freshness requirement cho phép.

## 5. Real production scenario

Flash sale product metadata được mọi request đọc từ cùng Redis key. Redis CPU của một shard tăng mạnh trong khi shard khác nhàn.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis latency tăng nhưng overall memory thấp. **Evidence** → command/key frequency cho thấy skew. **Diagnosis** → hot key. **Fix** → local caching, request coalescing, data replication/sharding strategy hoặc loại cache call khỏi hot path. **Verification** → latency per shard và request distribution.

## 7. Common mistakes

Scale cluster mà không đo key distribution; cache object cực lớn; local cache không có invalidation/freshness policy; dùng Redis cho dữ liệu có thể nằm trong process.

## 8. Alternatives

`IMemoryCache` tốt cho per-instance data có thể stale. CDN phù hợp public HTTP content. Database có thể đủ nhanh nếu query/index tốt và cache chỉ thêm complexity.

## 9. Trade-offs

### Advantages

Redis giảm load nguồn dữ liệu và chia sẻ cache giữa instances.

### Costs / Risks

Hot key biến Redis thành centralized bottleneck; multi-layer cache làm invalidation khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu distributed cache không đảm bảo traffic tự cân bằng.

### Middle

Đo key usage, TTL và latency.

### Senior

Thiết kế mitigation theo freshness/correctness requirement.

### Technical Lead / Architect

Quyết định dữ liệu nào đáng trở thành shared dependency và failure mode khi Redis degrade.

## 11. Key takeaway

- Capacity tổng không phản ánh hotspot.
- Hot-key mitigation phải dựa trên freshness semantics.
- Đừng thêm cache layer nếu nguồn dữ liệu đã đáp ứng SLA.

# 5. Anti-Corruption Layer: bảo vệ domain khỏi model của hệ thống bên ngoài

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary dịch model/protocol của external hoặc legacy system sang model của bounded context nội bộ. Nó bảo vệ domain language khỏi coupling trực tiếp.

## 2. Why does it exist?

External CRM có thể gọi `Customer` theo nghĩa khác hệ thống Commerce. Nếu import trực tiếp DTO và semantics của CRM vào domain, thay đổi external contract sẽ lan khắp business logic.

## 3. How does it work?

```text
Commerce Domain ← internal model ← ACL ← CRM API/model
```

ACL chịu mapping, protocol adaptation và semantic translation. Domain không phụ thuộc external SDK.

## 4. Practical implementation

```csharp
public sealed class CrmCustomerGateway : ICustomerProfileSource
{
    public async Task<CustomerProfile> GetAsync(CustomerId id, CancellationToken ct)
    {
        var dto = await _crm.GetCustomerAsync(id.Value, ct);
        return new CustomerProfile(id, dto.DisplayName, MapTier(dto.SegmentCode));
    }
}
```

## 5. Real production scenario

Legacy ERP dùng status codes `A`, `H`, `D`; commerce domain dùng explicit `AccountState`. ACL centralizes translation thay vì rải `if (code == "A")` khắp application.

## 6. Failure scenario & troubleshooting

**Symptom** → external provider thêm status mới và domain xử lý sai. **Evidence** → mapping fallback im lặng. **Diagnosis** → ACL không fail/observe unknown semantic values. **Fix** → explicit mapping, telemetry và contract tests. **Verification** → test known + unknown provider values.

## 7. Common mistakes

ACL chỉ copy DTO 1:1; tạo generic integration layer biết mọi system; leak provider enums vào domain; không có ownership cho mapping.

## 8. Alternatives

Direct integration hợp lý với small/simple stable dependency. Event-driven integration giảm runtime coupling nhưng thêm eventual consistency và messaging complexity.

## 9. Trade-offs

### Advantages

Change isolation, domain language sạch và testability tốt.

### Costs / Risks

Thêm mapping/code và có thể overengineer nếu external contract đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không mặc định là domain entity.

### Middle

Implement adapters/mappers có tests.

### Senior

Thiết kế semantic translation, failure handling và ownership.

### Technical Lead / Architect

Quyết định boundary, data ownership, transaction boundary, sync/async communication và deployment coupling. Nếu chỉ có một integration nhỏ, adapter đơn giản có thể đủ thay vì cả subsystem ACL.

## 11. Key takeaway

- ACL bảo vệ semantics, không chỉ đổi tên fields.
- External model không nên sở hữu domain language nội bộ.
- Chỉ thêm boundary complexity khi coupling risk thực sự tồn tại.

# 6. Timeout budget và deadline propagation: ngăn retry biến partial failure thành outage

## 1. What is it?

Timeout budget là tổng thời gian request được phép tiêu thụ; deadline propagation đảm bảo downstream calls biết phần budget còn lại thay vì mỗi tầng tự đặt timeout độc lập.

## 2. Why does it exist?

Nếu API có SLA 2 giây nhưng gọi ba dependencies mỗi cái timeout 5 giây, request có thể sống lâu hơn giá trị business. Retry còn nhân thời gian và tài nguyên.

## 3. How does it work?

```text
Client deadline 2s
  └─ API remaining 1.8s
      ├─ DB 300ms budget
      └─ Pricing API 800ms budget
```

Mỗi hop phải bounded; retry chỉ dùng phần budget còn lại.

## 4. Practical implementation

```csharp
using var timeout = CancellationTokenSource.CreateLinkedTokenSource(requestCt);
timeout.CancelAfter(TimeSpan.FromMilliseconds(800));

var response = await httpClient.GetAsync("/price", timeout.Token);
```

Trong hệ thống lớn, propagate deadline metadata và convert thành cancellation ở service boundary.

## 5. Real production scenario

Product page gọi pricing và reviews. Reviews chậm 4 giây nhưng page SLA 1.5 giây. Nếu reviews là optional, budget ngắn + fallback tốt hơn giữ toàn page chờ.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency outage kéo toàn API vào thread/connection exhaustion. **Evidence** → trace spans dài, retry count tăng. **Diagnosis** → timeout mỗi layer quá lớn và retry không biết deadline. **Fix** → end-to-end budget, bounded retry, bulkhead/fallback. **Verification** → chaos test dependency latency và quan sát p99/resource usage.

## 7. Common mistakes

Timeout bằng nhau ở mọi tầng; retry sau timeout mà không kiểm tra idempotency; timeout quá ngắn dựa trên average thay vì percentile; bỏ cancellation xuống DB.

## 8. Alternatives

Async messaging loại dependency khỏi synchronous critical path khi business flow cho phép. Cache/stale response có thể là fallback cho read-only data.

## 9. Trade-offs

### Advantages

Giới hạn resource retention và failure propagation.

### Costs / Risks

Budget quá aggressive tạo false timeout; fallback có thể làm dữ liệu stale.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout là correctness/reliability boundary, không chỉ config.

### Middle

Truyền cancellation và đặt timeout cho remote calls.

### Senior

Thiết kế retry trong remaining budget và phân tích trace percentiles.

### Technical Lead / Architect

Phân bổ latency budget theo criticality, ownership và user SLA; quyết định dependency nào không nên nằm synchronous path.

## 11. Key takeaway

- Timeout phải bắt đầu từ end-to-end SLA.
- Retry tiêu thụ cùng một budget, không tạo thêm thời gian miễn phí.
- Optional dependency không nên kéo sập critical path.

# 7. Azure Functions cold start: latency, scaling và lựa chọn hosting đúng workload

## 1. What is it?

Cold start là latency khi platform cần tạo/warm một Functions instance trước khi xử lý request. Nó gồm host startup, runtime initialization, dependency loading và application initialization.

## 2. Why does it exist?

Serverless tối ưu resource bằng elastic/on-demand compute. Khi không giữ instance warm liên tục, lần invocation đầu có thể trả startup cost.

## 3. How does it work?

```text
Event → no warm instance → allocate/start host → load app → execute
```

Scale-out có thể tạo nhiều cold instances khi burst lớn.

## 4. Practical implementation

Giữ startup path nhẹ, tránh network calls/migrations trong initialization và dùng dependency injection có chủ đích. Đo invocation latency tách startup khỏi business execution.

## 5. Real production scenario

HTTP Function cho synchronous checkout callback có strict latency SLA. Sau idle period, cold start làm p99 vượt SLA dù business code chỉ chạy 80 ms.

## 6. Failure scenario & troubleshooting

**Symptom** → first requests chậm, subsequent requests nhanh. **Evidence** → Application Insights trace startup/invocation pattern. **Diagnosis** → cold start hoặc heavy initialization. **Fix** → hosting plan phù hợp, warm capacity nếu cần, giảm startup work. **Verification** → test sau idle và trong scale-out burst.

## 7. Common mistakes

Chọn Functions cho mọi API vì “serverless”; chạy EF migrations khi startup; không phân biệt cold-start latency với downstream latency; bỏ qua cost của always-ready capacity.

## 8. Alternatives

App Service phù hợp long-running web API ổn định. Worker Service/Container Apps phù hợp background consumer cần process control. Logic Apps phù hợp orchestration integration low-code.

## 9. Trade-offs

### Advantages

Elastic scaling, event integration và giảm server management.

### Costs / Risks

Cold start, execution constraints, platform semantics và cost có thể khó dự đoán ở workload liên tục.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu serverless vẫn chạy trên process phải khởi động.

### Middle

Viết stateless Function, đo latency và startup.

### Senior

Phân tích scaling, retries, idempotency, networking, Managed Identity và monitoring.

### Technical Lead / Architect

Chọn Functions khi event-driven elasticity tạo giá trị; không dùng nếu always-on low-latency API đơn giản hơn trên App Service.

## 11. Key takeaway

- Cold start là hệ quả của compute elasticity.
- Đo p95/p99 sau idle và scale-out, không chỉ warm benchmark.
- Hosting model phải theo workload, SLA và cost.

# 8. `dotnet-dump` memory investigation: từ memory growth đến retention root cause

## 1. What is it?

`dotnet-dump` cho phép thu và phân tích managed process dump để xem heap, object roots và retention chains. Nó giúp trả lời “object nào đang sống và vì sao GC không thu được?”.

## 2. Why does it exist?

Memory growth không đồng nghĩa memory leak. Cache hợp lệ, LOH fragmentation, native memory hoặc workload spike đều có thể tăng RSS. Cần evidence từ heap/root thay vì đoán.

## 3. How does it work?

```text
Symptom → counters → dump → heap statistics → suspicious type → gcroot → owner
```

GC chỉ thu object không còn reachable; `gcroot` giúp tìm reference chain giữ object sống.

## 4. Practical implementation

```bash
dotnet-counters monitor --process-id 1234 System.Runtime
dotnet-dump collect --process-id 1234
dotnet-dump analyze core_*.dmp
```

Trong analyzer:

```text
dumpheap -stat
dumpheap -type MyLargeObject
gcroot <address>
```

## 5. Real production scenario

API memory tăng 200 MB mỗi giờ. `dumpheap -stat` cho thấy hàng trăm nghìn response DTO được giữ bởi static dictionary cache không có eviction.

## 6. Failure scenario & troubleshooting

**Symptom** → container OOMKilled. **Evidence** → GC heap tăng liên tục sau full collections. **Hypothesis** → managed retention. **Diagnosis** → compare dumps theo thời gian, tìm growing types và roots. **Fix** → bounded cache/unsubscribe event/dispose owner. **Verification** → soak test, heap stabilizes sau GC.

## 7. Common mistakes

Thu một dump rồi kết luận leak; chỉ nhìn RSS; dump production không cân nhắc size/sensitive data; “fix” bằng tăng memory limit.

## 8. Alternatives

`dotnet-gcdump` nhẹ hơn cho heap snapshot; PerfView/Visual Studio profiler phù hợp lab; `dotnet-trace` tốt cho runtime events.

## 9. Trade-offs

### Advantages

Có evidence sâu về managed heap và roots.

### Costs / Risks

Dump lớn, có thể chứa sensitive memory và việc collect/analyze có operational impact.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt allocation với retained memory.

### Middle

Dùng counters và heap statistics.

### Senior

So sánh dumps, đọc root chain và liên hệ ownership/lifetime.

### Technical Lead / Architect

Thiết kế diagnostic playbook, retention policy và safe production dump handling.

## 11. Key takeaway

- Memory growth phải được đo trước khi gọi là leak.
- `gcroot` trả lời vì sao object còn sống.
- Soak test sau fix quan trọng như dump analysis.

# 9. CORS: browser trust boundary, không phải cơ chế authentication

## 1. What is it?

CORS là browser-enforced policy cho phép server khai báo origins nào được JavaScript đọc response cross-origin. Nó không xác thực caller và không chặn non-browser clients.

## 2. Why does it exist?

Same-Origin Policy bảo vệ user khỏi website độc hại đọc dữ liệu từ origin khác bằng browser credentials. CORS tạo cơ chế opt-in có kiểm soát cho legitimate cross-origin frontend.

## 3. How does it work?

Browser có thể gửi preflight `OPTIONS`, server trả `Access-Control-Allow-*`, sau đó browser quyết định JavaScript có được truy cập response hay không.

## 4. Practical implementation

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("frontend", policy =>
        policy.WithOrigins("https://app.example.com")
              .AllowAnyHeader()
              .AllowAnyMethod());
});

app.UseCors("frontend");
```

Không dùng `AllowAnyOrigin` cùng credential semantics một cách tùy tiện.

## 5. Real production scenario

Vue SPA ở `app.example.com` gọi API ở `api.example.com`. API hoạt động qua Postman nhưng browser fail preflight. Đây là CORS/configuration issue, không phải API route hỏng.

## 6. Failure scenario & troubleshooting

**Symptom** → browser báo CORS nhưng server logs có request. **Evidence** → DevTools Network cho thấy preflight thiếu allow header hoặc origin mismatch. **Diagnosis** → middleware ordering/policy/proxy headers. **Fix** → explicit allowed origins/methods/headers. **Verification** → browser test từ allowed và disallowed origins.

## 7. Common mistakes

Dùng CORS thay authorization; `AllowAnyOrigin` để “fix”; quên credentials/cookies; debug bằng Postman rồi kết luận browser sai.

## 8. Alternatives

Same-origin deployment qua reverse proxy loại nhu cầu CORS ở nhiều hệ thống. Backend-for-Frontend có thể đơn giản hóa browser security boundary nhưng thêm component.

## 9. Trade-offs

### Advantages

Cho phép controlled browser cross-origin integration.

### Costs / Risks

Configuration phức tạp với credentials và nhiều environments; policy rộng tạo exposure không cần thiết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CORS do browser enforce.

### Middle

Debug preflight và cấu hình explicit origins.

### Senior

Phân biệt CORS, CSRF, authentication và authorization.

### Technical Lead / Architect

Quyết định origin topology, cookie/token strategy và liệu same-origin/BFF có giảm complexity không.

## 11. Key takeaway

- CORS không phải authentication.
- Postman success không chứng minh browser sẽ success.
- Policy nên explicit và tối thiểu cần thiết.

# 10. ADR: lưu engineering decision và trade-off thay vì chỉ lưu kết quả cuối

## 1. What is it?

Architecture Decision Record (ADR) là tài liệu ngắn ghi context, decision, alternatives và consequences của một quyết định kỹ thuật quan trọng.

## 2. Why does it exist?

Code cho biết hệ thống đang làm gì nhưng hiếm khi cho biết tại sao. Sau vài tháng, team dễ lặp lại tranh luận hoặc “simplify” một constraint có lý do lịch sử hợp lệ.

## 3. How does it work?

Một ADR thường có: Context → Decision → Alternatives → Consequences → Status. ADR mới có thể supersede ADR cũ; lịch sử quyết định được giữ lại.

## 4. Practical implementation

```markdown
# ADR-014: Use PostgreSQL for Order Service
Status: Accepted

## Context
Need relational transactions and reporting queries.

## Decision
Use PostgreSQL.

## Alternatives
Cosmos DB; SQL Server.

## Consequences
Team owns migrations, HA configuration and query tuning.
```

## 5. Real production scenario

Team hỏi vì sao không tách Inventory thành microservice. ADR cũ ghi rõ traffic thấp, team nhỏ và transaction coupling cao; extraction chỉ được reconsider khi independent scaling/ownership xuất hiện.

## 6. Failure scenario & troubleshooting

**Symptom** → ADR repository đầy documents nhưng decisions thực tế khác. **Evidence** → PR/code contradict accepted ADR. **Diagnosis** → ADR không nằm trong design/review flow. **Fix** → update/supersede ADR khi decision thay đổi, link ADR từ PR/design. **Verification** → architecture review dùng ADR làm decision history chứ không phải compliance theater.

## 7. Common mistakes

Viết ADR dài như specification; ghi quyết định nhỏ không đáng lưu; sửa lịch sử ADR cũ thay vì supersede; chỉ ghi “chọn X” mà không ghi constraint/trade-off.

## 8. Alternatives

README/design doc phù hợp mô tả hệ thống hiện tại. RFC phù hợp proposal cần discussion lớn. Issue/PR discussion hữu ích nhưng thường khó tìm lại như durable decision record.

## 9. Trade-offs

### Advantages

Giữ context, giảm repeated debate, hỗ trợ onboarding và architecture evolution.

### Costs / Risks

Documentation debt nếu không maintain; quá nhiều ADR tạo noise.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Đọc ADR để hiểu tại sao architecture tồn tại.

### Middle

Đóng góp evidence và alternatives trong design discussion.

### Senior

Viết ADR tập trung vào constraints/trade-offs và migration consequences.

### Technical Lead / Architect

Xác định decision nào cần record, ai sở hữu, khi nào revisit và cách supersede khi context thay đổi.

## 11. Key takeaway

- ADR lưu lý do và trade-off, không chỉ kết quả.
- Quyết định tốt luôn gắn với context tại thời điểm ra quyết định.
- ADR phải sống cùng engineering workflow, không phải kho tài liệu tĩnh.
