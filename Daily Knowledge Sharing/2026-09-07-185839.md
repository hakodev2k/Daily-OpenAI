# 1. `IAsyncDisposable` và asynchronous cleanup

## 1. What is it?
`IDisposable` giải phóng resource theo synchronous path; `IAsyncDisposable` cung cấp `DisposeAsync()` khi cleanup cần I/O như flush stream hoặc đóng protocol bất đồng bộ. GC quản lý managed memory, nhưng không thay thế deterministic cleanup của file handle, stream hay socket.

## 2. Why does it exist?
Nếu cleanup có I/O mà chỉ dùng synchronous `Dispose()`, thread có thể bị block. Với ASP.NET Core hoặc Worker Service dưới load, blocking cleanup lặp lại có thể làm throughput giảm.

## 3. How does it work?

```csharp
await using var stream = await store.OpenWriteAsync(path, ct);
await stream.WriteAsync(payload, ct);
```

Compiler bảo đảm `DisposeAsync()` được gọi khi scope kết thúc, kể cả exception path.

## 4. Practical implementation
Một abstraction chỉ nên implement `IAsyncDisposable` nếu nó thực sự sở hữu resource cần async cleanup. Nếu cleanup hoàn toàn synchronous, `IDisposable` đơn giản hơn.

## 5. Real production scenario
Export worker ghi file lớn lên remote storage. Flush cuối cùng cần network I/O. `await using` giữ lifecycle non-blocking thay vì giữ ThreadPool thread trong synchronous wait.

## 6. Failure scenario & troubleshooting
**Symptom:** file đôi lúc truncate hoặc shutdown kéo dài.  
**Evidence:** stream không được dispose trong exception path.  
**Hypothesis:** lifecycle resource không deterministic.  
**Fix:** chuẩn hóa ownership, `await using`, graceful shutdown và test exception path.

## 7. Common mistakes
* Nghĩ GC tự giải phóng mọi external resource đúng thời điểm.
* Dispose resource do caller sở hữu.
* Viết `DisposeAsync()` nhưng bên trong lại block bằng `.Wait()`.

## 8. Alternatives
`IDisposable` vẫn đúng cho synchronous cleanup. Không cần biến mọi class thành `IAsyncDisposable`.

## 9. Trade-offs
Async cleanup tránh blocking nhưng tăng API ceremony và yêu cầu caller dùng đúng lifecycle.

## 10. Junior → Middle → Senior → Technical Lead
Junior hiểu cleanup khác GC; Middle dùng `using`/`await using`; Senior debug lifecycle qua exception/cancellation; Lead định nghĩa ownership contract cho disposable infrastructure.

## 11. Key takeaway
Deterministic cleanup là resource-management concern; async resource nên được cleanup theo async path nếu cleanup thực sự có I/O.

# 2. ASP.NET Core output caching vs response caching

## 1. What is it?
Response caching dựa vào HTTP cache semantics và headers; output caching lưu response ở server theo policy của application. Điểm khác biệt chính là layer nào sở hữu quyết định reuse response.

## 2. Why does it exist?
Endpoint đọc CMS/config/database nhưng dữ liệu thay đổi ít có thể bị gọi hàng nghìn lần. Cache output hoàn chỉnh giúp bỏ qua nhiều bước application work.

## 3. How does it work?

```text
Request -> cache policy/key -> HIT -> cached response
                         \-> MISS -> endpoint -> response -> cache
```

Key có thể vary theo path, query hoặc metadata khác.

## 4. Practical implementation

```csharp
builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("catalog", p =>
        p.Expire(TimeSpan.FromSeconds(30))
         .SetVaryByQuery("page", "category"));
});
```

## 5. Real production scenario
Catalog public có thể cache 30 giây. Pricing theo customer contract không nên reuse cùng output cache entry giữa users.

## 6. Failure scenario & troubleshooting
**Symptom:** user thấy dữ liệu tenant khác.  
**Evidence:** cache key chỉ theo URL.  
**Root cause:** personalized response bị cache như public data.  
**Fix:** bỏ output cache hoặc vary theo đúng business/security boundary.

## 7. Common mistakes
* Cache endpoint authenticated mặc định.
* Không nghĩ tới invalidation khi content publish.
* Chồng CDN, output cache và Redis mà không rõ ownership.

## 8. Alternatives
`IMemoryCache`, Redis hoặc CDN có thể phù hợp hơn tùy dữ liệu và vị trí reuse.

## 9. Trade-offs
Output cache giảm backend work nhưng tăng stale-data và invalidation complexity.

## 10. Junior → Middle → Senior → Technical Lead
Junior hiểu hit/miss/TTL; Middle cấu hình policy; Senior đánh giá personalization và invalidation; Lead phân lớp cache giữa browser, CDN, app và Redis.

## 11. Key takeaway
Cache key là một phần của correctness model, không chỉ performance configuration.

# 3. JWT validation: signature, issuer, audience và lifetime

## 1. What is it?
JWT thường là dữ liệu Base64Url-encoded có chữ ký. Payload đọc được không có nghĩa token đáng tin. Resource Server phải validate chữ ký và các claims trust-critical.

## 2. Why does it exist?
Access token cho phép Authorization Server phát credential để API xác thực caller mà không cần session state truyền thống cho từng request.

## 3. How does it work?

```text
Token -> signature -> issuer -> audience -> expiry/not-before -> trusted ClaimsPrincipal
```

Sau đó authorization policy mới quyết định caller được phép làm gì.

## 4. Practical implementation

```csharp
builder.Services.AddAuthentication("Bearer")
    .AddJwtBearer("Bearer", options =>
    {
        options.Authority = configuration["Identity:Authority"];
        options.Audience = "employee-api";
    });
```

## 5. Real production scenario
Frontend login thành công nhưng API trả 401 vì token có `aud` dành cho resource khác. Tắt audience validation sẽ che lỗi cấu hình và làm trust boundary yếu đi.

## 6. Failure scenario & troubleshooting
**Symptom:** token hợp lệ ở một API nhưng fail ở API khác.  
**Evidence:** issuer/signature đúng nhưng audience không khớp.  
**Fix:** sửa token issuance hoặc API configuration; không tắt validation để “cho chạy”.

## 7. Common mistakes
* Decode = validate.
* Dùng ID token gọi API thay vì access token.
* Log raw token.
* Bỏ lifetime validation.

## 8. Alternatives
Opaque/reference tokens hoặc cookie authentication phù hợp trong một số architecture, nhưng có trade-off khác về state và network dependency.

## 9. Trade-offs
JWT validation local scale tốt; revocation tức thời khó hơn và token contract phải được governance rõ.

## 10. Junior → Middle → Senior → Technical Lead
Junior phân biệt encode/sign/encrypt; Middle configure JwtBearer; Senior xử lý key rotation/multi-tenant claims; Lead thiết kế token lifetime, scopes và service trust.

## 11. Key takeaway
JWT chỉ đáng tin sau validation đầy đủ; authentication và authorization vẫn là hai bước khác nhau.

# 4. EF Core compiled queries: khi nào optimization này đáng dùng

## 1. What is it?
EF Core phải phân tích expression tree và translate LINQ sang SQL. Compiled query precompile một query delegate để giảm một phần runtime overhead trên hot path.

## 2. Why does it exist?
Nếu query cực nhanh ở database nhưng được gọi hàng chục nghìn lần/giây, EF query-pipeline overhead có thể measurable. Với query database mất hàng trăm ms, optimization này thường không đáng kể.

## 3. How does it work?

```csharp
private static readonly Func<AppDbContext, Guid, Task<Employee?>> ById =
    EF.CompileAsyncQuery(
        (AppDbContext db, Guid id) =>
            db.Employees.AsNoTracking().FirstOrDefault(x => x.Id == id));
```

## 4. Practical implementation
Benchmark normal LINQ trước. Nếu profiler cho thấy query translation/lookup overhead đáng kể mới cân nhắc compiled query.

## 5. Real production scenario
Lookup theo primary key ở 20k RPS có thể benefit. Endpoint 50 RPS thường không justify thêm complexity.

## 6. Failure scenario & troubleshooting
**Symptom:** compiled query không cải thiện latency.  
**Evidence:** execution plan vẫn scan 300 ms.  
**Root cause:** bottleneck nằm ở database I/O.  
**Fix:** index/projection/query design trước.

## 7. Common mistakes
* Compiled query mọi nơi.
* Nghĩ nó tối ưu SQL execution plan.
* Bỏ qua projection và `AsNoTracking`.

## 8. Alternatives
Normal LINQ + EF internal cache thường đủ. Raw SQL chỉ hợp lý khi cần control/query shape đặc thù.

## 9. Trade-offs
Giảm một phần CPU overhead nhưng tăng code ceremony và giảm flexibility.

## 10. Junior → Middle → Senior → Technical Lead
Junior hiểu LINQ cần translation; Middle đo DB duration; Senior benchmark đúng bottleneck; Lead ngăn premature optimization thành convention.

## 11. Key takeaway
Compiled query tối ưu EF pipeline, không sửa slow SQL.

# 5. SQL composite indexes: column order, covering và execution plan

## 1. What is it?
Composite index chứa nhiều columns theo thứ tự xác định. `(TenantId, Status, CreatedAt)` không tương đương `(CreatedAt, Status, TenantId)`.

## 2. Why does it exist?
Production query thường filter nhiều dimensions. Một composite index aligned với access pattern có thể giảm logical reads nhiều hơn nhiều single-column indexes riêng lẻ.

## 3. How does it work?

```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE TenantId = @tenantId
  AND Status = @status
  AND CreatedAt < @cursor
ORDER BY CreatedAt DESC;
```

Candidate index:

```sql
CREATE INDEX IX_Orders_Tenant_Status_CreatedAt
ON Orders (TenantId, Status, CreatedAt DESC)
INCLUDE (Total);
```

## 4. Practical implementation
Quy trình: slow query → actual plan → actual rows → logical reads → seek/scan/lookups → candidate index → benchmark read/write impact.

## 5. Real production scenario
Orders table lớn luôn scope theo tenant. Index chỉ trên `CreatedAt` vẫn đọc quá nhiều rows; tenant-first composite index giúp thu hẹp search space sớm.

## 6. Failure scenario & troubleshooting
**Symptom:** thêm index nhưng query vẫn chậm.  
**Evidence:** leading columns không khớp predicate thực tế hoặc key lookup quá nhiều.  
**Fix:** điều chỉnh key order/INCLUDE hoặc rewrite query.

## 7. Common mistakes
* “Column selectivity cao nhất luôn đặt đầu”.
* Index mọi filter column.
* INCLUDE quá rộng.
* Không tính write amplification.

## 8. Alternatives
Filtered/partial index, query redesign hoặc denormalization có thể phù hợp hơn tùy workload.

## 9. Trade-offs
Index tăng read speed nhưng tốn storage, cache memory và write maintenance.

## 10. Junior → Middle → Senior → Technical Lead
Junior hiểu index là access path; Middle đọc seek/scan; Senior thiết kế composite index theo query family; Lead quản trị indexing strategy theo workload toàn hệ thống.

## 11. Key takeaway
Column order là semantics. Actual plan và I/O metrics quan trọng hơn lời khuyên “thêm index”.

# 6. DDD Aggregate: consistency boundary và invariant

## 1. What is it?
Aggregate là một consistency boundary trong Domain-Driven Design. Aggregate Root là entry point để thay đổi state bên trong boundary đó.

## 2. Why does it exist?
Nếu mọi entity có public mutation từ mọi nơi, invariant dễ bị phá. Nếu aggregate quá lớn, transaction lại giữ quá nhiều data và tăng concurrency conflict.

## 3. How does it work?

```csharp
public void AddItem(ProductId productId, int quantity, Money price)
{
    if (quantity <= 0)
        throw new DomainException("Quantity must be positive.");

    _items.Add(new OrderItem(productId, quantity, price));
}
```

Invariant được bảo vệ qua root thay vì public setters rải rác.

## 4. Practical implementation
Hỏi trước: dữ liệu nào bắt buộc nhất quán trong cùng transaction? Chỉ đưa phần đó vào aggregate boundary.

## 5. Real production scenario
`Customer` aggregate chứa Orders, Addresses, Preferences, Payments làm update nhỏ kéo cả graph lớn. Tách boundary giảm tracking, locking và conflict.

## 6. Failure scenario & troubleshooting
**Symptom:** update nhỏ gây nhiều rows tracked và concurrency conflicts.  
**Evidence:** aggregate phản ánh navigation graph hơn là consistency requirement.  
**Fix:** tách aggregates, dùng IDs/domain events giữa boundaries.

## 7. Common mistakes
* Aggregate = toàn bộ object graph.
* Repository cho từng child rồi bypass root.
* Dùng DDD cho CRUD đơn giản không có domain complexity.

## 8. Alternatives
Transaction Script/Application Service thường đơn giản hơn cho business logic CRUD nhẹ.

## 9. Trade-offs
Aggregate tăng encapsulation nhưng có modeling cost; boundary nhỏ hơn thường chấp nhận eventual consistency giữa aggregates.

## 10. Junior → Middle → Senior → Technical Lead
Junior hiểu Entity/Value Object; Middle bảo vệ invariant bằng methods; Senior thiết kế transaction boundary; Lead cân bằng domain model với scalability và operational complexity.

## 11. Key takeaway
Aggregate là consistency boundary trước khi là class structure.

# 7. Distributed timeouts: timeout budget, retries và deadline propagation

## 1. What is it?
Timeout giới hạn thời gian caller sẵn sàng chờ dependency. Deadline propagation mang remaining time budget xuyên qua service chain thay vì mỗi hop reset timeout mới.

## 2. Why does it exist?
Network failure thường biểu hiện bằng chậm. Không có timeout, threads/connections bị giữ quá lâu; timeout sai cộng retries lại có thể tạo retry storm.

## 3. How does it work?

```text
Client budget 2s
 -> API dùng 200ms, còn 1.8s
 -> Service B dùng 500ms, còn 1.3s
 -> downstream chỉ được dùng phần còn lại
```

## 4. Practical implementation

```csharp
using var cts = CancellationTokenSource.CreateLinkedTokenSource(requestAborted);
cts.CancelAfter(TimeSpan.FromSeconds(2));
await client.SendAsync(request, cts.Token);
```

## 5. Real production scenario
A retry B 3 lần; B retry database 3 lần. Một user request có thể tạo tới 9 attempts downstream khi hệ thống đang degraded.

## 6. Failure scenario & troubleshooting
**Symptom:** dependency chậm nhẹ nhưng internal traffic tăng mạnh.  
**Evidence:** distributed traces có nhiều retry spans.  
**Fix:** bounded retries, backoff+jitter, deadline propagation, circuit breaker/bulkhead khi phù hợp.

## 7. Common mistakes
* Retry ở mọi layer.
* Timeout mỗi hop lớn hơn end-to-end SLA.
* Không propagate cancellation.
* Retry non-idempotent operation mù quáng.

## 8. Alternatives
Asynchronous messaging phù hợp khi caller không cần synchronous result.

## 9. Trade-offs
Timeout nhanh bảo vệ capacity nhưng có thể giảm success rate; retry tăng resilience với transient failure nhưng khuếch đại load.

## 10. Junior → Middle → Senior → Technical Lead
Junior biết mọi network call cần timeout; Middle dùng cancellation; Senior thiết kế retry budget; Lead phân bổ latency budget và sync/async boundaries.

## 11. Key takeaway
Timeout là capacity-protection mechanism; retry phải tiêu thụ cùng một budget có giới hạn.

# 8. Azure Blob Storage upload architecture cho file lớn

## 1. What is it?
Azure Blob Storage là object storage. Upload có thể đi qua web application hoặc đi trực tiếp từ client tới Blob với permission ngắn hạn do backend cấp.

## 2. Why does it exist?
Nếu browser upload file 2 GB qua ASP.NET Core rồi app forward lên Blob, application trở thành bandwidth/request-duration bottleneck không cần thiết.

## 3. How does it work?

```text
Server-mediated: Client -> App -> Blob
Direct upload:   Client -> API xin quyền ngắn hạn -> Blob trực tiếp
```

Backend vẫn sở hữu authorization và metadata workflow.

## 4. Practical implementation
Nếu upload qua server, stream request thẳng tới Blob thay vì đọc toàn file vào `byte[]`. Khi backend truy cập Azure resources, Managed Identity giảm nhu cầu quản lý static credentials.

## 5. Real production scenario
Recruitment portal upload video lớn qua App Service gây timeout và memory pressure. Direct-to-Blob giúp app chỉ xử lý control plane thay vì data plane.

## 6. Failure scenario & troubleshooting
**Symptom:** file lớn hay timeout dù Blob khỏe.  
**Evidence:** reverse-proxy limit, request duration và app resource usage tăng.  
**Fix:** direct upload hoặc true streaming/chunking; post-processing chạy background.

## 7. Common mistakes
* `ReadToEndAsync()` toàn file vào memory.
* Permission upload quá rộng hoặc quá lâu.
* Tin file extension/content-type từ client.
* Chạy heavy scanning inline trong request dài.

## 8. Alternatives
Server-mediated upload vẫn phù hợp file nhỏ hoặc workflow cần server kiểm soát byte stream trực tiếp.

## 9. Trade-offs
Direct upload giảm app bandwidth nhưng tăng client/storage integration và post-upload validation complexity.

## 10. Junior → Middle → Senior → Technical Lead
Junior hiểu object storage; Middle implement streaming; Senior xử lý chunk/retry/validation; Lead chọn data path, retention và security workflow.

## 11. Key takeaway
File lớn không nên mặc định đi xuyên application server.

# 9. Playwright + Testcontainers cho integration/E2E testing

## 1. What is it?
Playwright chạy browser workflow thực. Testcontainers khởi tạo database/cache/broker tạm thời cho test run. Kết hợp hai lớp giúp test protocol và infrastructure behavior gần Production hơn mocks.

## 2. Why does it exist?
Mock-heavy tests có thể pass dù migration, serialization hoặc browser behavior thật đã hỏng. Shared staging lại dễ flaky vì state không deterministic.

## 3. How does it work?

```text
CI -> start containers -> run migrations -> seed data -> start app -> Playwright -> assertions -> cleanup
```

## 4. Practical implementation
Playwright nên chờ semantic condition:

```ts
await page.getByRole('button', { name: 'Save' }).click();
await expect(page.getByText('Saved successfully')).toBeVisible();
```

Tránh fixed sleep như `waitForTimeout(3000)` nếu không có lý do đặc biệt.

## 5. Real production scenario
Unit tests mock database nên không phát hiện migration mới thiếu default cho non-null column. Containerized DB chạy migration thật sẽ fail ngay trong CI.

## 6. Failure scenario & troubleshooting
**Symptom:** E2E flaky.  
**Evidence:** fixed sleeps, shared data, async background work chưa hoàn thành.  
**Fix:** semantic waits, unique test data, deterministic seed và trace diagnostics.

## 7. Common mistakes
* E2E test mọi branch logic.
* Shared mutable DB giữa tests parallel.
* Container image `latest` làm environment thay đổi bất ngờ.
* Rerun flaky test thay vì sửa root cause.

## 8. Alternatives
Unit tests cho domain logic, integration tests cho boundaries, contract tests cho service contracts. E2E chỉ nên cover critical user journeys.

## 9. Trade-offs
Real dependencies tăng confidence nhưng làm CI chậm và phức tạp hơn mocks.

## 10. Junior → Middle → Senior → Technical Lead
Junior viết deterministic assertions; Middle phân biệt test levels; Senior thiết kế isolated infrastructure; Lead phân bổ coverage theo risk và feedback time.

## 11. Key takeaway
Test gần Production không đồng nghĩa dùng shared staging; determinism vẫn là yêu cầu số một.

# 10. p50 / p95 / p99 latency và tail-latency engineering

## 1. What is it?
Percentile latency mô tả distribution: `p50` là median, `p95` là ngưỡng 95% requests, `p99` tập trung vào tail latency. Average có thể che một nhóm requests cực chậm.

## 2. Why does it exist?
Nếu 99 requests mất 100 ms và 1 request mất 10 giây, average vẫn có thể trông “không quá tệ”, nhưng 1% users chịu trải nghiệm rất xấu.

## 3. How does it work?
Tail latency thường đến từ queueing, GC pause, lock contention, cold cache, slow dependency, connection-pool wait hoặc retries.

## 4. Practical implementation
Dashboard nên theo dõi request rate, error rate, p50/p95/p99, dependency latency và saturation metrics như queue/pool usage.

## 5. Real production scenario
Sau deployment average tăng 120 → 130 ms, nhưng p99 tăng 600 ms → 4.5 s vì cache-miss path giữ database connection lâu.

## 6. Failure scenario & troubleshooting
**Symptom:** support nói “thỉnh thoảng rất chậm” nhưng average xanh.  
**Evidence:** p99 spike tương quan DB pool wait.  
**Fix:** trace slowest requests, phân segment endpoint/tenant và xử lý saturation source.

## 7. Common mistakes
* Chỉ nhìn average.
* Gộp mọi endpoint thành một percentile.
* Tối ưu p50 khi incident nằm ở p99.
* Không xem sample size và traffic volume.

## 8. Alternatives
Histogram/latency distribution đầy đủ thường cho insight tốt hơn chỉ vài percentile; Apdex hữu ích cho experience target nhưng không thay raw latency.

## 9. Trade-offs
p99 phản ánh tail nhưng noisy hơn p50 và cần đủ traffic. Percentile aggregation sai giữa instances cũng có thể gây hiểu nhầm.

## 10. Junior → Middle → Senior → Technical Lead
Junior hiểu median khác average; Middle dùng p95/p99 khi debug; Senior correlate tail với queueing/saturation; Lead đặt SLO và capacity plan dựa trên user-impacting percentiles.

## 11. Key takeaway
Performance engineering phải nhìn distribution + saturation, không chỉ một con số trung bình.
