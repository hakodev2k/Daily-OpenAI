# 1. C# `ArrayPool<T>`: giảm allocation cho buffer ngắn hạn mà không tạo retention và data-leak bug

## 1. What is it?

`ArrayPool<T>` là cơ chế cho phép thuê (`Rent`) và trả (`Return`) các array có thể tái sử dụng thay vì tạo array mới liên tục.

Mental model:

```text
request
  ↓
Rent buffer
  ↓
use buffer
  ↓
Return buffer
  ↓
pool reuses it later
```

Nó đặc biệt hữu ích với buffer lớn hoặc hot path có allocation lặp lại, ví dụ parsing, compression, serialization hoặc file/network processing.

## 2. Why does it exist?

Một đoạn code tạo `byte[64 * 1024]` cho mọi request có thể gây allocation rate cao. Với throughput lớn, nhiều arrays chuyển nhanh qua Gen 0/Gen 1; arrays đủ lớn còn có thể đi vào LOH và làm GC pressure tăng.

Pooling đổi chi phí từ “allocate mỗi lần” sang “reuse memory đã có”.

## 3. How does it work?

`ArrayPool<T>.Shared.Rent(size)` trả về array có độ dài **ít nhất** bằng `size`, không bảo đảm đúng bằng `size`.

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    // use only the intended range
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);
}
```

Pool không bảo đảm buffer đã được zero hóa. Nội dung từ lần sử dụng trước có thể vẫn còn.

## 4. Practical implementation

Ví dụ đọc stream theo chunk:

```csharp
public static async Task<long> CopyAndCountAsync(
    Stream source,
    Stream destination,
    CancellationToken cancellationToken)
{
    var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
    long total = 0;

    try
    {
        int read;
        while ((read = await source.ReadAsync(
            buffer.AsMemory(0, 64 * 1024),
            cancellationToken)) > 0)
        {
            await destination.WriteAsync(
                buffer.AsMemory(0, read),
                cancellationToken);

            total += read;
        }

        return total;
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
    }
}
```

Nếu buffer chứa secret material, cân nhắc `clearArray: true` hoặc clear phần đã dùng trước khi return.

## 5. Real production scenario

Một image-processing API nhận hàng nghìn uploads/phút. Mỗi stage tạo arrays 128–512 KB cho decode/transform. Memory allocation rate tăng mạnh dù working set logic không lớn.

Sau profiling, team dùng `ArrayPool<byte>` cho các transient buffers lớn. Gen 0/LOH allocation giảm và p99 latency ổn định hơn khi traffic tăng.

## 6. Failure scenario & troubleshooting

**Symptom** → memory không giảm sau khi traffic spike hoặc dữ liệu cũ xuất hiện trong buffer.

**Evidence** → profiler cho thấy pooled arrays retained lâu; code giữ reference sau khi `Return`.

**Hypothesis** → lifecycle sai hoặc code giả định buffer mới luôn zeroed.

**Diagnosis** → tìm các đường code không `finally`, object giữ pooled array sau method, hoặc xử lý quá phạm vi dữ liệu thực.

**Fix** → ownership rõ ràng, luôn `Return` trong `finally`, không expose pooled array ra ngoài lifetime, clear dữ liệu nhạy cảm khi cần.

**Verification** → chạy allocation benchmark và memory stress test; kiểm tra cả correctness khi pool tái sử dụng buffer.

## 7. Common mistakes

* Giả định `Rent(1000)` trả array đúng 1000 phần tử.
* Quên `Return`.
* Return rồi vẫn tiếp tục dùng buffer.
* Cache pooled array trong singleton mà không có ownership model.
* Không clear secret bytes.
* Dùng pooling cho object nhỏ, allocation rẻ, khiến code khó hiểu mà không có lợi ích đo được.

## 8. Alternatives

`Memory<T>` / `Span<T>` giúp slice dữ liệu nhưng không tự giảm allocation. `MemoryPool<T>` phù hợp khi cần `IMemoryOwner<T>`. Array allocation thông thường vẫn đơn giản hơn cho phần lớn business code.

## 9. Trade-offs

### Advantages

* Giảm allocation rate.
* Giảm GC pressure trên hot path.
* Hữu ích cho large temporary buffers.

### Costs / Risks

* Ownership phức tạp hơn.
* Có nguy cơ use-after-return.
* Buffer có thể chứa dữ liệu cũ.
* Pool giữ memory để reuse nên working set không nhất thiết giảm ngay.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu pooling là reuse memory, không phải “array đặc biệt”.

### Middle

Biết dùng `Rent`/`Return`, `try/finally` và chỉ xử lý đúng valid range.

### Senior

Đo allocation bằng profiler/benchmark, hiểu LOH, retention và sensitive-data risk.

### Technical Lead / Architect

Quyết định nơi pooling đáng giá dựa trên throughput, buffer size, GC evidence và độ phức tạp ownership.

## 11. Key takeaway

* `ArrayPool<T>` là performance optimization dựa trên reuse.
* Chỉ dùng khi allocation thực sự là bottleneck.
* Ownership và dữ liệu còn sót lại là hai rủi ro lớn nhất.

# 2. ASP.NET Core `ProblemDetails`: biến failure thành API contract ổn định thay vì trả exception tùy hứng

## 1. What is it?

`ProblemDetails` là representation chuẩn hóa cho HTTP API errors dựa trên RFC problem details semantics. Nó giúp client nhận error contract nhất quán thay vì mỗi endpoint trả một shape khác.

Mental model:

```text
Exception / validation / business conflict
              ↓
        error mapping layer
              ↓
         ProblemDetails
              ↓
            client
```

## 2. Why does it exist?

Nếu endpoint A trả:

```json
{ "message": "Not found" }
```

endpoint B trả:

```json
{ "error": "invalid_state", "details": "..." }
```

và endpoint C để raw exception middleware trả HTML/stack trace, client phải viết logic riêng cho từng nơi.

Một contract ổn định giúp frontend, mobile client, monitoring và integration consumers xử lý lỗi predictably.

## 3. How does it work?

ASP.NET Core có thể map exceptions và status codes sang `ProblemDetails`. Các field thường gồm:

* `type`
* `title`
* `status`
* `detail`
* `instance`
* custom extensions, ví dụ `code`, `traceId`

Không nên expose stack trace hoặc internal implementation detail cho public client.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

builder.Services.AddExceptionHandler<DomainExceptionHandler>();

app.UseExceptionHandler();

public sealed class DomainExceptionHandler(
    IProblemDetailsService problemDetailsService)
    : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext context,
        Exception exception,
        CancellationToken cancellationToken)
    {
        if (exception is not OrderAlreadyClosedException)
            return false;

        context.Response.StatusCode = StatusCodes.Status409Conflict;

        await problemDetailsService.WriteAsync(new()
        {
            HttpContext = context,
            ProblemDetails = new ProblemDetails
            {
                Status = 409,
                Title = "Order conflict",
                Detail = "The order is already closed.",
                Extensions = { ["code"] = "order_already_closed" }
            }
        });

        return true;
    }
}
```

Client nên dựa chủ yếu vào machine-readable `code`, không parse `detail`.

## 5. Real production scenario

Một Vue.js frontend xử lý 20 APIs. Trước chuẩn hóa, team phải inspect `response.data.message`, `error`, `errors[]` tùy endpoint. Sau khi dùng consistent `ProblemDetails`, frontend có một error adapter chung và chỉ có mapping đặc biệt cho một số business codes.

## 6. Failure scenario & troubleshooting

**Symptom** → production trả `500` nhưng client nhận body trống hoặc HTML.

**Evidence** → reverse proxy/app middleware path khác nhau; exception xảy ra sau response đã bắt đầu.

**Hypothesis** → exception handler không còn quyền thay response hoặc pipeline ordering sai.

**Diagnosis** → kiểm tra `Response.HasStarted`, middleware order, logs và trace.

**Fix** → centralize exception mapping sớm trong pipeline; tránh viết response trước khi operation có thể fail; đối với streaming response phải chấp nhận rằng error contract sau khi headers/body bắt đầu có giới hạn.

**Verification** → integration-test các nhóm `400`, `401`, `403`, `404`, `409`, `429`, `500`.

## 7. Common mistakes

* Trả `200 OK` rồi đặt `{ success:false }`.
* Expose stack trace hoặc SQL message.
* Dùng `500` cho validation/business conflict.
* Cho mỗi controller tự tạo error shape.
* Dùng human-readable `detail` như machine contract.
* Gộp authentication và authorization thành cùng một lỗi.

## 8. Alternatives

Custom error envelope có thể hợp lý nếu organization đã có contract lâu đời. gRPC có status/trailer semantics khác. GraphQL cũng có error model riêng. Với HTTP REST APIs mới, chuẩn problem details thường giảm custom convention.

## 9. Trade-offs

### Advantages

* Error contract nhất quán.
* Dễ observability và client integration.
* Phân biệt transport/business failure rõ hơn.

### Costs / Risks

* Cần taxonomy cho error codes.
* Mapping quá generic có thể che mất business semantics.
* Legacy clients có thể cần migration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP status code và error body là hai phần của cùng contract.

### Middle

Implement centralized mapping và validation errors.

### Senior

Thiết kế stable machine-readable codes, security boundary và backward compatibility.

### Technical Lead / Architect

Chuẩn hóa error contract toàn platform, versioning policy và observability correlation.

## 11. Key takeaway

* Error cũng là API contract.
* `ProblemDetails` giúp chuẩn hóa transport semantics nhưng business code vẫn cần thiết kế tốt.
* Không leak implementation detail qua error response.

# 3. EF Core compiled queries: giảm query-compilation overhead đúng hot path thay vì tối ưu mù

## 1. What is it?

EF Core phải biến LINQ expression thành database query plan representation trước khi gửi SQL. EF đã có query compilation cache nội bộ, nhưng explicit compiled queries cho phép precompile một query shape và gọi lại với parameters.

Mental model:

```text
LINQ expression
   ↓
translation / compilation
   ↓
cached query delegate
   ↓
parameter values
   ↓
SQL execution
```

## 2. Why does it exist?

Trong phần lớn APIs, database I/O chiếm thời gian lớn hơn EF query compilation. Nhưng ở high-throughput hot paths với query nhỏ và lặp lại hàng triệu lần, compilation/cache lookup overhead có thể trở thành measurable cost.

Compiled queries tồn tại cho trường hợp optimization có evidence này.

## 3. How does it work?

```csharp
private static readonly Func<AppDbContext, Guid, Task<Customer?>>
    GetCustomerById =
        EF.CompileAsyncQuery(
            (AppDbContext db, Guid id) =>
                db.Customers
                    .AsNoTracking()
                    .FirstOrDefault(x => x.Id == id));
```

Sau đó gọi delegate với `DbContext` và parameter. Query shape phải ổn định.

## 4. Practical implementation

```csharp
public sealed class CustomerReader(AppDbContext db)
{
    private static readonly Func<AppDbContext, string, IAsyncEnumerable<CustomerDto>>
        ByCountry =
            EF.CompileAsyncQuery(
                (AppDbContext context, string country) =>
                    context.Customers
                        .AsNoTracking()
                        .Where(x => x.Country == country)
                        .OrderBy(x => x.Id)
                        .Select(x => new CustomerDto(x.Id, x.Name)));

    public IAsyncEnumerable<CustomerDto> GetByCountry(string country)
        => ByCountry(db, country);
}
```

Benchmark compiled vs normal query với realistic DB latency trước khi adopt.

## 5. Real production scenario

Một pricing service phục vụ hàng chục nghìn requests/giây, query một row nhỏ từ local-region SQL với rất thấp latency. Profiling cho thấy EF query pipeline overhead đáng kể trong CPU profile. Một vài hot queries được compiled và CPU/request giảm measurable.

Không có lý do đổi hàng trăm queries khác không nằm trên hot path.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries nhưng latency gần như không thay đổi.

**Evidence** → trace cho thấy 95% thời gian nằm ở SQL execution/network.

**Hypothesis** → tối ưu nhầm layer.

**Diagnosis** → đo EF client-side duration, server execution, round trip, connection wait.

**Fix** → tập trung vào query shape/index/data access nếu database mới là bottleneck.

**Verification** → benchmark trước/sau với production-like latency, không chỉ microbenchmark in-memory.

## 7. Common mistakes

* Compiled mọi query vì nghĩ “compiled = nhanh”.
* Dùng nó che một slow query.
* Tạo quá nhiều query variants khiến maintenance tăng.
* Bỏ `AsNoTracking`/projection và chỉ tối ưu compilation.
* Không benchmark end-to-end.

## 8. Alternatives

EF query cache mặc định đủ cho đa số cases. Dapper/raw ADO.NET có thể giảm abstraction overhead hơn nữa nhưng tăng code và mapping responsibility. Caching result giải quyết vấn đề khác: tránh database call, không chỉ query compilation.

## 9. Trade-offs

### Advantages

* Giảm overhead của repeated query compilation path.
* Predictable cho hot query shapes.

### Costs / Risks

* Boilerplate và discoverability kém hơn.
* Lợi ích nhỏ nếu DB I/O dominates.
* Có thể làm code tối ưu hóa sớm khó bảo trì.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ không “chạy trực tiếp”; EF phải translate query.

### Middle

Biết đo generated SQL và query performance.

### Senior

Phân biệt client-side EF overhead với server-side database bottleneck.

### Technical Lead / Architect

Đặt performance discipline: compiled queries chỉ xuất hiện ở evidence-backed hot paths.

## 11. Key takeaway

* Compiled query là micro-optimization có use case thật nhưng hẹp.
* Đo database, network và EF overhead riêng biệt.
* Query shape và I/O thường quan trọng hơn compilation.

# 4. PostgreSQL connection pooling với Npgsql: pool saturation, transaction leakage và timeout dưới tải

## 1. What is it?

Npgsql connection pooling giữ các physical PostgreSQL connections để các logical `OpenAsync()` calls có thể reuse connection thay vì tạo TCP/TLS/database session mới mỗi lần.

Mental model:

```text
request
  ↓
OpenAsync
  ↓
pool
 ├─ available connection → reuse
 └─ none available → wait
```

## 2. Why does it exist?

Tạo database connection mới có chi phí network handshake, TLS, authentication và server backend process/session. Pooling giảm latency và load.

Nhưng pool là tài nguyên hữu hạn. Khi app giữ connections quá lâu, request mới phải chờ pool dù database vẫn còn CPU.

## 3. How does it work?

Connection string có các pool settings như `Maximum Pool Size` và timeout. `Dispose`/`Close` thường trả connection về pool, không đóng physical connection ngay.

Một transaction hoặc reader giữ connection lâu cũng giữ slot trong pool.

## 4. Practical implementation

```csharp
await using var connection = new NpgsqlConnection(connectionString);
await connection.OpenAsync(ct);

await using var command = new NpgsqlCommand(
    "select id, name from customer where id = @id",
    connection);

command.Parameters.AddWithValue("id", id);

await using var reader = await command.ExecuteReaderAsync(ct);

if (await reader.ReadAsync(ct))
{
    // map and return quickly
}
```

Đặt scope connection ngắn, không giữ qua remote HTTP call.

Với EF Core/Npgsql, `DbContext` lifetime cũng phải ngắn theo request/unit of work.

## 5. Real production scenario

API bình thường chạy 200 RPS ổn. Sau release, một handler bắt đầu mở transaction rồi gọi external payment API trước khi commit. Payment latency 2–5 giây khiến hàng chục connections bị giữ. Pool đạt max và request khác timeout dù PostgreSQL CPU chỉ 30%.

## 6. Failure scenario & troubleshooting

**Symptom** → `Timeout while getting a connection from pool`.

**Evidence** → active connection count chạm max; DB query durations không cao tương ứng.

**Hypothesis** → connection được giữ lâu hoặc leak.

**Diagnosis** → trace duration từ `Open` đến `Dispose`, inspect long transactions, active readers, external calls nằm trong transaction.

**Fix** → rút ngắn connection/transaction scope; không tăng pool size trước khi hiểu nguyên nhân.

**Verification** → load test và theo dõi pool wait time, active/idle connections, DB saturation.

## 7. Common mistakes

* Giữ connection trong singleton.
* Transaction bao trùm HTTP call.
* Không dispose reader/command đúng cách.
* Tăng `Maximum Pool Size` vô hạn.
* Mở quá nhiều app instances làm tổng connections vượt khả năng DB.
* Nhầm pool timeout với slow SQL timeout.

## 8. Alternatives

PgBouncer có thể thêm external pooling, đặc biệt khi số app instances lớn. Nhưng nó có transaction/session pooling semantics riêng. Direct connections đơn giản hơn khi workload nhỏ.

## 9. Trade-offs

### Advantages

* Giảm connect latency.
* Giảm auth/TLS overhead.
* Tăng throughput.

### Costs / Risks

* Saturation tạo queueing trong app.
* Pool size mỗi instance nhân với số replicas.
* Session state/transactions dài làm reuse kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Dispose` thường trả connection về pool.

### Middle

Biết giữ scope ngắn và phân biệt command timeout với pool wait.

### Senior

Đọc pool/DB telemetry, tìm transaction leakage và capacity mismatch.

### Technical Lead / Architect

Tính tổng connection budget theo replicas, autoscaling và DB limits; quyết định khi cần PgBouncer.

## 11. Key takeaway

* Pooling tăng hiệu năng nhưng tạo một finite concurrency boundary.
* Connection lifetime dài thường nguy hiểm hơn pool size nhỏ.
* Capacity phải tính ở toàn deployment, không chỉ từng process.

# 5. Redis cache penetration: negative caching, Bloom-filter concepts và cách bảo vệ database khỏi miss lặp vô hạn

## 1. What is it?

Cache penetration xảy ra khi requests liên tục hỏi các keys **không tồn tại**, nên cache luôn miss và mọi request đi xuống database.

```text
GET product:does-not-exist
  ↓ miss
DB lookup
  ↓ not found
repeat forever
```

Đây khác cache stampede: stampede thường là key có tồn tại nhưng hết hạn cùng lúc.

## 2. Why does it exist?

Cache-aside thường chỉ cache data tồn tại. Vì vậy bot, typo, crawler hoặc client bug truy vấn ID không tồn tại có thể bypass cache hoàn toàn và biến database thành lớp “xác nhận 404” đắt đỏ.

## 3. How does it work?

Hai biện pháp phổ biến:

1. **Negative caching**: cache “not found” trong TTL ngắn.
2. **Bloom filter**: cấu trúc xác suất trả lời “key chắc chắn không tồn tại” hoặc “có thể tồn tại”.

Bloom filter có false positive nhưng không có false negative nếu được duy trì đúng; vì vậy request “có thể tồn tại” vẫn cần DB/cache lookup.

## 4. Practical implementation

Negative cache đơn giản:

```csharp
var key = $"product:{id}";

var cached = await redis.StringGetAsync(key);

if (cached == "__NULL__")
    return null;

if (cached.HasValue)
    return JsonSerializer.Deserialize<ProductDto>(cached!);

var product = await db.Products
    .AsNoTracking()
    .Where(x => x.Id == id)
    .Select(x => new ProductDto(x.Id, x.Name))
    .SingleOrDefaultAsync(ct);

if (product is null)
{
    await redis.StringSetAsync(
        key,
        "__NULL__",
        TimeSpan.FromSeconds(30));

    return null;
}
```

Production code nên dùng typed envelope thay vì magic string nếu value domain có thể trùng.

## 5. Real production scenario

Search engine crawler tạo URLs với stale product IDs. 40% product-detail requests là IDs đã xóa. Vì 404 không được cache, SQL nhận hàng nghìn point queries/giây. Negative caching 30–60 giây giảm đáng kể repeated misses.

## 6. Failure scenario & troubleshooting

**Symptom** → sản phẩm vừa được tạo nhưng API vẫn trả 404 trong vài chục giây.

**Evidence** → negative cache entry tồn tại.

**Hypothesis** → negative TTL quá dài hoặc create flow không invalidate cache.

**Diagnosis** → inspect key, TTL và write workflow.

**Fix** → TTL ngắn, invalidate negative key khi create/import, hoặc không negative-cache những namespace có rapid creation.

**Verification** → test create-after-miss path.

## 7. Common mistakes

* Negative TTL bằng positive TTL rất dài.
* Không phân biệt cache penetration với stampede.
* Bloom filter không được update khi data thay đổi.
* Cho Redis outage biến thành total API outage.
* Cache error `500` như “not found”.
* Không rate-limit abusive keyspace scans.

## 8. Alternatives

Rate limiting giảm abuse. Database index có thể làm miss rẻ hơn nhưng không loại repeated work. CDN negative caching phù hợp public HTTP 404 trong một số workload. Bloom filter hợp với keyspace cực lớn nhưng tăng operational complexity.

## 9. Trade-offs

### Advantages

* Bảo vệ database khỏi repeated misses.
* Giảm latency cho known-missing keys.

### Costs / Risks

* Có stale-negative window.
* Invalidation thêm complexity.
* Bloom filter cần lifecycle/rebuild strategy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss không đồng nghĩa data tồn tại ở DB.

### Middle

Implement negative caching với TTL ngắn.

### Senior

Phân tích abuse, stale-negative, invalidation và Redis failure.

### Technical Lead / Architect

Quyết định negative cache, edge cache, Bloom filter hay rate limiting dựa trên keyspace và threat/workload model.

## 11. Key takeaway

* 404 cũng có thể trở thành hot path.
* Negative caching là giải pháp đơn giản nhưng phải quản lý freshness.
* Bloom filter chỉ đáng giá khi scale/keyspace thật sự yêu cầu.

# 6. DDD Domain Event vs Integration Event: phân biệt business fact nội bộ với contract xuyên bounded context

## 1. What is it?

**Domain Event** diễn tả một business fact xảy ra trong domain model, ví dụ `OrderConfirmed`.

**Integration Event** là message contract dùng để giao tiếp qua boundary giữa bounded contexts/services, ví dụ `OrderConfirmedV1`.

Hai khái niệm có thể liên quan nhưng không nên mặc định là cùng một object.

## 2. Why does it exist?

Domain model muốn diễn đạt nghiệp vụ theo ngôn ngữ nội bộ và có thể thay đổi khi business model evolves. External consumers lại cần stable contract, versioning và backward compatibility.

Nếu publish domain object trực tiếp ra message bus, internal refactoring có thể vô tình trở thành breaking integration change.

## 3. How does it work?

Flow thường là:

```text
Aggregate
  ↓ raises
Domain Event
  ↓ handled inside application boundary
Outbox mapping
  ↓
Integration Event
  ↓
Message Bus
  ↓
Other bounded contexts
```

Domain event có thể trigger local side effects trong cùng process/transaction scope; integration event thường publish sau durable commit thông qua Outbox.

## 4. Practical implementation

```csharp
public sealed record OrderConfirmed(Guid OrderId, DateTimeOffset ConfirmedAt)
    : IDomainEvent;

public sealed record OrderConfirmedV1(
    Guid OrderId,
    DateTimeOffset ConfirmedAtUtc,
    string Currency);

public sealed class OrderConfirmedIntegrationMapper
{
    public OrderConfirmedV1 Map(
        OrderConfirmed domainEvent,
        Order order)
        => new(
            domainEvent.OrderId,
            domainEvent.ConfirmedAt,
            order.Currency);
}
```

Outbox record nên chứa versioned contract hoặc serialized payload rõ ràng.

## 5. Real production scenario

Ordering domain đổi internal entity từ `CustomerId` sang `BuyerAccount`. Nếu internal domain event được publish trực tiếp cho Billing và Analytics, rename/refactor có thể phá consumers.

Tách integration contract cho phép domain model thay đổi mà external schema vẫn giữ tương thích.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment của một service làm consumer khác deserialize fail.

**Evidence** → message schema đổi cùng refactor domain model.

**Hypothesis** → internal domain type bị dùng như external contract.

**Diagnosis** → inspect publisher serializer, contract package/version và consumer assumptions.

**Fix** → tách integration schema, thêm versioning/backward compatibility, publish bằng outbox.

**Verification** → contract tests với consumer versions cũ.

## 7. Common mistakes

* Gọi mọi message là “domain event”.
* Publish EF entity trực tiếp.
* Domain event chứa infrastructure concern như queue name.
* Integration event chứa quá nhiều internal fields.
* Không version external schema.
* Raise integration event trước DB commit rồi publish dữ liệu chưa durable.

## 8. Alternatives

Một modular monolith có thể chỉ cần in-process domain events. Với ít integration, direct application service call có thể đơn giản hơn messaging. Event sourcing là kiến trúc khác; domain/integration events không tự động nghĩa event sourcing.

## 9. Trade-offs

### Advantages

* Bảo vệ bounded-context boundary.
* Cho phép domain model evolve độc lập.
* Contract versioning rõ hơn.

### Costs / Risks

* Mapping code và outbox complexity.
* Event taxonomy cần governance.
* Eventual consistency giữa contexts.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event là fact đã xảy ra, khác command là yêu cầu làm gì đó.

### Middle

Biết raise domain event và map sang integration event.

### Senior

Thiết kế versioning, outbox và consumer compatibility.

### Technical Lead / Architect

Xác định bounded context, ownership và nơi messaging thực sự tạo giá trị thay vì biến monolith thành distributed system vô lý.

## 11. Key takeaway

* Domain Event tối ưu cho model nội bộ; Integration Event tối ưu cho boundary ổn định.
* Không publish domain entity/type trực tiếp chỉ vì tiện.
* External contracts cần versioning và durable publication.

# 7. Azure Functions + Service Bus trigger concurrency: scale nhanh nhưng không được đánh đổi ordering, idempotency và downstream capacity

## 1. What is it?

Azure Functions Service Bus trigger có thể chạy nhiều message handlers đồng thời và scale-out nhiều function instances khi backlog tăng.

Mental model:

```text
Service Bus queue
   ↓
instance A: msg1 msg2 msg3 ...
instance B: msg4 msg5 msg6 ...
instance C: ...
```

Concurrency giúp throughput tăng, nhưng đồng thời tăng pressure lên database/API phía sau.

## 2. Why does it exist?

Nếu chỉ xử lý một message mỗi lần, queue backlog có thể tăng nhanh khi workload burst. Serverless runtime cho phép tăng concurrent processing và instance count mà không quản lý worker hosts thủ công.

## 3. How does it work?

Concurrency chịu ảnh hưởng bởi host/runtime configuration, trigger extension, sessions và workload. Scale controller quan sát queue pressure và quyết định thêm instances.

Với non-session queue, message order giữa handlers không được đảm bảo. Với session-enabled entity, ordering scope theo `SessionId`.

At-least-once delivery vẫn có nghĩa handler phải idempotent.

## 4. Practical implementation

```csharp
public sealed class ProcessOrderFunction
{
    [Function("ProcessOrder")]
    public async Task Run(
        [ServiceBusTrigger("orders", Connection = "ServiceBus")]
        ServiceBusReceivedMessage message,
        ServiceBusMessageActions actions,
        CancellationToken ct)
    {
        var orderId = message.ApplicationProperties["orderId"]?.ToString()
            ?? throw new InvalidOperationException("Missing orderId");

        if (await _inbox.AlreadyProcessedAsync(message.MessageId, ct))
        {
            await actions.CompleteMessageAsync(message, ct);
            return;
        }

        await _processor.ProcessAsync(orderId, ct);
        await _inbox.MarkProcessedAsync(message.MessageId, ct);

        await actions.CompleteMessageAsync(message, ct);
    }
}
```

Inbox write và business state update cần transaction/consistency design phù hợp.

## 5. Real production scenario

Queue backlog tăng sau campaign. Functions scale từ 2 lên 20 instances. Queue giảm nhanh nhưng SQL connection pool và third-party API rate limit bị bão hòa. Error rate tăng và messages retry, khiến tải còn lớn hơn.

Đây là failure amplification do consumer scale vượt downstream capacity.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog tăng dù function instances tăng.

**Evidence** → dependency latency/429/SQL pool waits tăng, retry count tăng.

**Hypothesis** → bottleneck nằm ở downstream, không phải số consumer.

**Diagnosis** → correlate queue age, concurrency, dependency latency, DB connections và retry/dead-letter metrics.

**Fix** → cap concurrency, batch hợp lý, backoff, bulkhead, optimize downstream hoặc scale downstream trước.

**Verification** → load test với production rate limit/capacity.

## 7. Common mistakes

* Coi serverless scale là vô hạn.
* Không idempotency.
* Retry ngay lập tức trên `429`.
* Không có DLQ process.
* Giả định queue order là business order.
* Cho mọi message fan-out thêm nhiều remote calls không bounded.

## 8. Alternatives

Worker Service/Container Apps cho kiểm soát concurrency chi tiết hơn. AKS consumer phù hợp workload có custom runtime/operational needs. Service Bus sessions phù hợp per-key ordering.

## 9. Trade-offs

### Advantages

* Scale nhanh theo backlog.
* Giảm ops burden cho worker host.
* Tích hợp tốt với Service Bus.

### Costs / Risks

* Scale có thể phá downstream.
* At-least-once đòi idempotency.
* Cost tăng theo executions và dependencies.
* Tuning concurrency cần workload-specific evidence.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một queue có thể được nhiều handlers xử lý song song.

### Middle

Implement idempotency, retry và settlement đúng.

### Senior

Tuning concurrency dựa trên downstream capacity và backlog age.

### Technical Lead / Architect

Thiết kế end-to-end capacity model: queue, Functions, DB, APIs, DLQ và cost.

## 11. Key takeaway

* Consumer scale chỉ có ích khi downstream chịu được.
* At-least-once delivery bắt buộc idempotency.
* Queue backlog phải được nhìn cùng dependency saturation, không riêng metric queue length.

# 8. OpenTelemetry attributes, baggage và cardinality: telemetry hữu ích hay hóa đơn monitoring tăng vô hạn

## 1. What is it?

OpenTelemetry span attributes là key/value metadata gắn vào trace/span để query và phân tích. Baggage là context có thể propagate qua service boundaries và được downstream code đọc.

Ví dụ attributes:

```text
http.request.method = GET
order.region = APAC
db.system = postgresql
```

Cardinality là số lượng distinct values của một dimension.

## 2. Why does it exist?

Trace chỉ có duration và service name thường không đủ để điều tra. Attributes cho phép hỏi:

* lỗi tập trung ở region nào?
* endpoint nào chậm?
* dependency nào gây bottleneck?

Nhưng nếu gắn `userId`, raw URL, GUID hay search query tự do vào metric dimensions, cardinality có thể bùng nổ.

## 3. How does it work?

Span attributes thường đi cùng trace data. Metrics backends thường rất nhạy với high-cardinality dimensions vì mỗi unique combination có thể tạo time series mới.

Baggage còn nguy hiểm hơn nếu lạm dụng vì nó được propagate qua request headers/context, tăng payload và có nguy cơ leak dữ liệu.

## 4. Practical implementation

```csharp
using var activity = ActivitySource.StartActivity("ProcessOrder");

activity?.SetTag("order.channel", order.Channel);
activity?.SetTag("order.region", order.Region);
activity?.SetTag("retry.count", retryCount);
```

Không nên:

```csharp
activity?.SetTag("customer.email", customer.Email);
activity?.SetTag("full.request.body", json);
```

Dùng low-cardinality business dimensions có chủ đích.

## 5. Real production scenario

Team thêm `customerId` và raw request path vào custom metric labels để “debug dễ hơn”. Sau vài tuần, monitoring backend chứa hàng triệu series, ingestion cost tăng mạnh và dashboard query chậm.

Trace logs có thể phù hợp cho entity-specific investigation; metric dimensions thì không.

## 6. Failure scenario & troubleshooting

**Symptom** → telemetry cost tăng 5x nhưng request volume chỉ tăng 10%.

**Evidence** → distinct dimension count tăng mạnh.

**Hypothesis** → high-cardinality attributes được export thành metric labels hoặc baggage quá nhiều.

**Diagnosis** → audit top dimensions, unique value counts, payload size và exporter mapping.

**Fix** → whitelist low-cardinality labels, move IDs sang traces/logs có sampling, redact sensitive data.

**Verification** → theo dõi series count, ingest volume và dashboard latency.

## 7. Common mistakes

* Gắn GUID/userId vào metrics.
* Propagate secrets/PII qua baggage.
* Log full headers/body.
* Mọi field đều thành attribute.
* Không có semantic-convention/governance.
* Sampling traces nhưng không hiểu metrics vẫn có cardinality explosion riêng.

## 8. Alternatives

Structured logs tốt cho detailed event lookup. Traces tốt cho request journey. Metrics tốt cho aggregated trend/alerting. Không một signal nào thay thế ba loại còn lại.

## 9. Trade-offs

### Advantages

* Debugging và correlation mạnh.
* Cho phép slicing theo business/technical dimensions.

### Costs / Risks

* Cost và storage tăng.
* PII/security risk.
* Query performance giảm khi cardinality quá cao.
* Baggage propagation tăng coupling/context size.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu logs, metrics, traces phục vụ mục đích khác nhau.

### Middle

Biết thêm low-cardinality tags có ý nghĩa.

### Senior

Phân tích sampling, cardinality, PII và exporter behavior.

### Technical Lead / Architect

Đặt telemetry schema, retention, cost guardrails và sensitive-data policy toàn platform.

## 11. Key takeaway

* Telemetry càng nhiều không tự động càng tốt.
* High-cardinality dimensions là vấn đề cả chi phí lẫn vận hành.
* IDs chi tiết thường phù hợp trace/log hơn metric label.

# 9. Playwright test isolation + auto-waiting: giảm flaky E2E bằng state control thay vì thêm `Task.Delay`

## 1. What is it?

Playwright có auto-waiting: trước khi action như click, framework chờ element đạt điều kiện actionability thích hợp. Test isolation nghĩa mỗi test có state độc lập, không dựa vào test trước.

Mental model:

```text
Arrange isolated state
  ↓
navigate
  ↓
locator waits for usable element
  ↓
act
  ↓
assert observable result
```

## 2. Why does it exist?

E2E tests chạy qua browser, network, frontend rendering và backend. Timing biến động làm test dễ flaky nếu dùng sleep cố định:

```csharp
await Task.Delay(3000);
```

Delay 3 giây vừa chậm, vừa không bảo đảm đủ khi CI load cao.

## 3. How does it work?

Playwright locators được resolve lazily và actions/assertions tự retry trong timeout. Test context/browser context có thể tách cookies/storage để giảm shared state.

```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();

await Expect(page.GetByText("Saved"))
    .ToBeVisibleAsync();
```

## 4. Practical implementation

```csharp
[Fact]
public async Task User_can_create_project()
{
    await SeedUserAndEmptyWorkspaceAsync();

    await Page.GotoAsync("/projects");

    await Page.GetByRole(AriaRole.Button, new() { Name = "New project" })
        .ClickAsync();

    await Page.GetByLabel("Title").FillAsync("Migration");

    await Page.GetByRole(AriaRole.Button, new() { Name = "Create" })
        .ClickAsync();

    await Expect(Page.GetByText("Migration")).ToBeVisibleAsync();
}
```

Test data setup nên deterministic và cleanup độc lập.

## 5. Real production scenario

Suite 400 tests có 8–12% flaky failures. Team ban đầu tăng sleeps lên 5 giây. Runtime suite gấp đôi nhưng flakiness vẫn tồn tại.

Root cause gồm shared account, test A tạo dữ liệu mà test B phụ thuộc, locator theo CSS brittle và network response race.

Sau khi isolate data/account, dùng role/label locators và assertion auto-wait, failure rate giảm mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → test pass local nhưng fail CI ngẫu nhiên.

**Evidence** → screenshot cho thấy element chưa xuất hiện hoặc state từ test khác.

**Hypothesis** → timing assumption hoặc shared state.

**Diagnosis** → inspect trace/video/network logs, chạy test lặp nhiều lần và song song.

**Fix** → bỏ arbitrary sleeps, chờ observable condition, isolate data, reset storage, dùng stable locators.

**Verification** → repeat test 50–100 lần và chạy parallel CI.

## 7. Common mistakes

* `Task.Delay` như synchronization primitive.
* Tests phụ thuộc thứ tự.
* Dùng shared user với mutable data.
* Locator theo generated CSS classes.
* Chỉ assert “page loaded”.
* Mock quá nhiều tới mức không còn test integration thật.

## 8. Alternatives

Integration tests nhanh hơn và ổn định hơn cho backend contracts. Unit tests tốt cho business logic. E2E chỉ nên bảo vệ critical user journeys, không thay toàn bộ test pyramid.

## 9. Trade-offs

### Advantages

* Confidence cao cho real browser flow.
* Bắt lỗi integration/frontend/backend.
* Auto-wait giảm manual timing logic.

### Costs / Risks

* Chậm và tốn infrastructure hơn.
* Debug failure phức tạp.
* State isolation cần đầu tư test environment/data APIs.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu test phải chờ condition, không chờ thời gian cố định.

### Middle

Viết stable locators, isolated setup và meaningful assertions.

### Senior

Phân tích trace, parallelism, data races và flaky patterns.

### Technical Lead / Architect

Quyết định journey nào cần E2E, budget runtime, isolation strategy và CI signal quality.

## 11. Key takeaway

* Flaky E2E thường là state/timing design problem.
* Auto-waiting tốt hơn arbitrary sleep.
* Isolation quan trọng hơn tăng timeout.

# 10. Modernization `.NET Framework` → modern .NET bằng Strangler Pattern: giảm migration risk thay vì rewrite toàn hệ thống

## 1. What is it?

Strangler Pattern là cách modernize hệ thống từng phần: giữ legacy application hoạt động, rồi dần route từng capability sang implementation mới cho đến khi phần cũ có thể retire.

Mental model:

```text
Client
  ↓
Routing / facade
  ├─ legacy module (.NET Framework)
  └─ new module (modern .NET)
```

## 2. Why does it exist?

Rewrite toàn bộ enterprise application thường kéo dài nhiều tháng/năm. Trong thời gian đó business vẫn thay đổi, production vẫn cần fixes, và “big bang” cutover tạo risk lớn.

Incremental modernization cho phép deliver giá trị từng slice và rollback từng bước.

## 3. How does it work?

Chọn seam rõ ràng:

* endpoint nhóm `/reports/*`
* background job cụ thể
* module document export
* authentication adapter
* integration client

Sau đó:

1. Baseline behavior bằng tests/telemetry.
2. Xây implementation mới.
3. Route một phần traffic/capability.
4. So sánh kết quả.
5. Migrate data/contract nếu cần.
6. Retire legacy slice.

## 4. Practical implementation

Ví dụ reverse proxy/YARP route một capability:

```csharp
builder.Services.AddReverseProxy()
    .LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"));

app.MapReverseProxy();
```

Config có thể route `/api/reports/*` sang modern service trong khi phần còn lại vẫn tới legacy app.

Database sharing nên được xem là transitional coupling, không phải trạng thái lý tưởng kéo dài vô hạn.

## 5. Real production scenario

Một .NET Framework MVC application có 200 endpoints và nhiều third-party dependencies. Team chọn migrate reporting/export trước vì boundary rõ, ít writes và có test datasets.

Sau vài releases, report traffic chạy ở .NET 8 service. Legacy app vẫn phục vụ core workflows. Nếu lỗi, route có thể rollback về implementation cũ trong thời gian chuyển đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng một user thấy behavior khác giữa legacy và new endpoint.

**Evidence** → authentication claims, timezone, validation hoặc serialization defaults khác nhau.

**Hypothesis** → contract compatibility chưa được baseline đầy đủ.

**Diagnosis** → compare request/response, headers, culture, auth claims, database side effects và edge cases.

**Fix** → contract tests, compatibility adapter và canary traffic.

**Verification** → shadow/dual-run ở read-only paths khi phù hợp, plus regression suite trước route cutover.

## 7. Common mistakes

* “Strangler” nhưng new system vẫn gọi ngược legacy internals everywhere.
* Migrate theo technical layer thay vì business slice.
* Shared database trở thành permanent dependency.
* Không có rollback.
* Vừa migrate framework vừa redesign toàn domain cùng lúc.
* Không đo usage nên migrate feature gần như không ai dùng.

## 8. Alternatives

In-place upgrade phù hợp codebase nhỏ và dependencies tương thích. Big-bang rewrite chỉ hợp khi system nhỏ hoặc business cho phép freeze/cutover rõ. Modular monolith extraction có thể đơn giản hơn tạo microservice mới.

## 9. Trade-offs

### Advantages

* Giảm blast radius.
* Deliver incremental value.
* Có rollback/canary.
* Cho phép học từ từng migration slice.

### Costs / Risks

* Tạm thời vận hành hai stacks.
* Routing, auth và data consistency phức tạp.
* Transitional architecture dễ trở thành permanent nếu không có exit criteria.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu modernization không đồng nghĩa rewrite.

### Middle

Migrate một endpoint/module với tests và compatibility.

### Senior

Quản lý dual-stack auth, data, routing và rollback.

### Technical Lead / Architect

Chọn migration seams, sequencing, exit criteria và quyết định phần legacy nào nên giữ thay vì migrate.

## 11. Key takeaway

* Incremental migration thường an toàn hơn big-bang rewrite.
* Boundary tốt quan trọng hơn framework version.
* Transitional coupling phải có kế hoạch kết thúc rõ ràng.
