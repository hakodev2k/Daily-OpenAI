# 1. C# `ValueTask`: giảm allocation trong hot path nhưng tăng complexity contract

## 1. What is it?

Mental model: `Task<T>` là một object đại diện cho kết quả bất đồng bộ; `ValueTask<T>` là value type có thể đại diện cho kết quả đã có sẵn hoặc một asynchronous operation. Nó hữu ích khi operation **rất thường xuyên hoàn tất synchronously** và allocation của `Task` thực sự đáng kể.

## 2. Why does it exist?

Một API cache có thể trả kết quả ngay trong phần lớn calls. Nếu mỗi hit đều tạo `Task<T>`, hot path tạo allocation không cần thiết. `ValueTask<T>` cho phép fast path trả value trực tiếp. Nhưng optimization này đổi simplicity lấy contract phức tạp hơn.

## 3. How does it work?

```text
Call
 ├─ result đã có -> ValueTask chứa T
 └─ phải async   -> ValueTask bọc Task/IValueTaskSource
```

Không nên mặc định await một `ValueTask` nhiều lần hoặc dùng nó như reusable `Task`; backing source có thể chỉ hỗ trợ consumption một lần.

## 4. Practical implementation

```csharp
public ValueTask<User?> FindAsync(Guid id, CancellationToken ct)
{
    if (_cache.TryGetValue(id, out var user))
        return ValueTask.FromResult<User?>(user);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id, ct));
}
```

Nếu caller cần giữ/reuse operation, chuyển bằng `.AsTask()` với cost tương ứng.

## 5. Real production scenario

Một in-memory metadata resolver chạy hàng trăm nghìn lần/phút và >95% hit cache. Profiling cho thấy `Task` allocation đáng kể. Sau measurement, `ValueTask` giảm allocation. Với API chỉ gọi database, lợi ích gần như không đáng kể vì operation vốn asynchronous.

## 6. Failure scenario & troubleshooting

**Symptom** → behavior lạ khi consumer await cùng `ValueTask` nhiều lần. **Evidence** → API trả `IValueTaskSource`-backed result. **Hypothesis** → caller vi phạm consumption contract. **Diagnosis** → inspect call sites. **Fix** → await một lần hoặc dùng `Task` nếu semantics cần reuse. **Verification** → tests + allocation benchmark.

## 7. Common mistakes

Đổi mọi `Task` thành `ValueTask`; optimize không profiling; lưu `ValueTask` lâu dài; gọi `.Result`; tăng API complexity cho path không hot.

## 8. Alternatives

`Task<T>` nên là default vì semantics đơn giản, tooling tốt và dễ compose. Caching completed `Task` đôi khi đủ.

## 9. Trade-offs

### Advantages
Giảm allocation khi synchronous completion rất phổ biến.

### Costs / Risks
Contract khó dùng hơn, struct lớn hơn reference, composition/debugging phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `Task` không phải thread.
### Middle
Dùng `Task` mặc định và await đúng.
### Senior
Chỉ chọn `ValueTask` sau profiling và hiểu consumption semantics.
### Technical Lead / Architect
Quyết định API contract có đáng đổi simplicity lấy allocation reduction hay không.

## 11. Key takeaway

- `Task` là default; `ValueTask` là optimization có điều kiện.
- Chỉ tối ưu khi synchronous completion + allocation thực sự đáng kể.
- API simplicity cũng là performance của đội ngũ.

# 2. ASP.NET Core Options validation: fail fast configuration

## 1. What is it?

Options Pattern bind configuration thành typed object. Validation biến configuration từ “dictionary strings” thành startup/runtime contract có thể kiểm chứng.

## 2. Why does it exist?

Sai endpoint, missing secret name hoặc timeout âm thường chỉ lộ khi endpoint đầu tiên được gọi. Production deployment có thể báo healthy rồi vài phút sau mới 500. Fail-fast đưa lỗi về deployment boundary.

## 3. How does it work?

`IOptions<T>` thường resolve singleton-like configuration; `IOptionsSnapshot<T>` hỗ trợ scoped snapshot; `IOptionsMonitor<T>` theo dõi changes. `ValidateOnStart()` buộc validation khi application startup thay vì lần đầu options được resolve.

## 4. Practical implementation

```csharp
builder.Services
    .AddOptions<PaymentOptions>()
    .BindConfiguration("Payment")
    .Validate(o => Uri.TryCreate(o.BaseUrl, UriKind.Absolute, out _),
        "Payment:BaseUrl must be an absolute URI")
    .Validate(o => o.TimeoutSeconds is > 0 and <= 30,
        "TimeoutSeconds must be 1..30")
    .ValidateOnStart();
```

Không log secret value khi validation fail.

## 5. Real production scenario

Slot mới thiếu `Payment:BaseUrl`. Không validation, health endpoint vẫn xanh và swap đưa traffic vào slot lỗi. Với startup validation, instance không trở thành healthy candidate.

## 6. Failure scenario & troubleshooting

**Symptom** → startup fail với `OptionsValidationException`. **Evidence** → validation failures chỉ rõ key/invariant. **Hypothesis** → environment config drift. **Diagnosis** → compare configuration sources, Key Vault references và environment variables. **Fix** → sửa deployment configuration. **Verification** → restart + readiness check.

## 7. Common mistakes

Validate chỉ `NotNull`; inject raw `IConfiguration` khắp code; reload setting nhưng service cache value cũ; đưa secrets vào exception; dùng `IOptionsSnapshot` trong singleton.

## 8. Alternatives

Custom configuration service hữu ích khi config động/phức tạp; schema validation ở CI/CD bổ sung nhưng không thay runtime validation.

## 9. Trade-offs

### Advantages
Typed contract, fail fast, testable invariants.
### Costs / Risks
Startup có thể fail vì dependency/config tạm thời nếu validation thực hiện network I/O không phù hợp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Bind config thành typed options.
### Middle
Validate required fields và ranges.
### Senior
Hiểu lifetime/reload semantics và secret handling.
### Technical Lead / Architect
Quyết định config nào phải fail deployment, config nào có safe fallback.

## 11. Key takeaway

- Configuration là runtime contract.
- Validate deterministic invariants tại startup.
- Đừng biến startup validation thành remote dependency health check.

# 3. SQL Server isolation levels: consistency đổi lấy concurrency

## 1. What is it?

Isolation level định nghĩa transaction được phép quan sát thay đổi concurrent đến mức nào. Nó không chỉ là “mức khóa”; với row versioning, SQL Server có thể cung cấp consistent reads mà giảm reader/writer blocking.

## 2. Why does it exist?

Nếu mọi transaction serialize hoàn toàn, correctness dễ reasoning nhưng throughput thấp. Nếu đọc tự do, dirty/non-repeatable/phantom observations có thể phá business invariant. Isolation là lựa chọn giữa các guarantees và concurrency cost.

## 3. How does it work?

`READ COMMITTED` mặc định ngăn dirty read nhưng statement sau có thể thấy dữ liệu mới. `SNAPSHOT` dùng row versions để transaction đọc snapshot nhất quán. `SERIALIZABLE` mạnh hơn nhưng có thể giữ range locks và tăng blocking/deadlock.

## 4. Practical implementation

```sql
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

SELECT Balance FROM Accounts WHERE Id = @id;
-- business work
UPDATE Accounts SET Balance = Balance - @amount WHERE Id = @id;

COMMIT;
```

Isolation không thay business concurrency control; update invariants vẫn cần predicate/token phù hợp.

## 5. Real production scenario

Reporting query dài block order writes dưới locking read strategy. Row-versioned reads giảm contention, nhưng tempdb/version-store pressure phải được theo dõi và long-running transactions vẫn gây retention.

## 6. Failure scenario & troubleshooting

**Symptom** → blocking giảm nhưng tempdb/version store tăng. **Evidence** → long-running snapshot transactions giữ old row versions. **Hypothesis** → transaction lifetime quá dài. **Diagnosis** → active transaction + version-store telemetry. **Fix** → rút ngắn transaction/batch report. **Verification** → load test reads+writes.

## 7. Common mistakes

Dùng `NOLOCK` để “fix blocking”; chọn `SERIALIZABLE` toàn hệ thống; transaction bao quanh HTTP call; nghĩ snapshot loại mọi write conflict; không đo tempdb.

## 8. Alternatives

Optimistic concurrency token xử lý lost update ở application; explicit locking phù hợp critical invariant ngắn; read replica phù hợp reporting nhưng có replication lag.

## 9. Trade-offs

### Advantages
Isolation mạnh hơn đơn giản hóa một số consistency reasoning.
### Costs / Risks
Locking, version storage, retries hoặc reduced concurrency tùy mode.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu transaction không chỉ là commit/rollback.
### Middle
Biết blocking và isolation hiện tại.
### Senior
Đọc locks/versioning/conflicts từ evidence.
### Technical Lead / Architect
Chọn consistency guarantee theo invariant thay vì global preference.

## 11. Key takeaway

- Isolation là business-correctness + concurrency decision.
- `NOLOCK` không phải performance switch miễn phí.
- Transaction càng dài, operational cost càng lớn.

# 4. Redis cache penetration: request cho dữ liệu không tồn tại vẫn có thể phá database

## 1. What is it?

Cache penetration xảy ra khi requests liên tục hỏi keys không tồn tại; cache luôn miss nên mỗi request xuyên xuống database.

## 2. Why does it exist?

Cache-aside chỉ bảo vệ dữ liệu đã cache. Bot, malformed IDs hoặc traffic hợp lệ tới missing records có thể tạo origin load lớn mà hit rate nhìn tổng thể vẫn có vẻ tốt.

## 3. How does it work?

```text
GET product:missing -> miss -> DB: not found
GET product:missing -> miss -> DB: not found
... lặp lại vì "not found" không được cache
```

Negative caching lưu sentinel “không tồn tại” trong TTL ngắn. Bloom filter có thể loại nhiều impossible IDs trước origin nhưng có false positives.

## 4. Practical implementation

```csharp
var cached = await cache.GetStringAsync(key, ct);
if (cached == "__missing__") return null;
if (cached is not null) return JsonSerializer.Deserialize<Product>(cached);

var product = await db.Products.FindAsync([id], ct);
await cache.SetStringAsync(
    key,
    product is null ? "__missing__" : JsonSerializer.Serialize(product),
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = product is null
            ? TimeSpan.FromSeconds(20)
            : TimeSpan.FromMinutes(5)
    }, ct);
return product;
```

## 5. Real production scenario

Crawler thử hàng triệu product IDs. Existing products hit Redis; missing IDs mỗi lần query SQL. Negative cache + input/rate controls giảm DB QPS đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → cache hit rate ổn nhưng DB point-lookups tăng. **Evidence** → repeated misses cho cùng nonexistent keys. **Hypothesis** → penetration. **Diagnosis** → sample miss keys/status. **Fix** → negative cache, validation, rate limit. **Verification** → replay missing-key workload.

## 7. Common mistakes

Negative TTL quá dài làm newly-created entity vẫn “missing”; cache user-specific authorization result sai key; dùng Bloom filter nhưng không có update strategy.

## 8. Alternatives

Input validation, edge rate limiting, Bloom filter, API semantics không cho arbitrary IDs.

## 9. Trade-offs

### Advantages
Giảm repeated origin reads.
### Costs / Risks
Temporary staleness và thêm invalidation semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu cache miss vẫn có cost.
### Middle
Implement negative caching an toàn.
### Senior
Phân biệt penetration, stampede và hot key.
### Technical Lead / Architect
Thiết kế cache policy cùng abuse protection và freshness requirement.

## 11. Key takeaway

- “Không tồn tại” cũng là kết quả có thể cache.
- TTL negative cache nên ngắn và có chủ đích.
- Cache design phải xét adversarial/malformed traffic.

# 5. Modular Monolith dependency rules: boundary phải được enforce

## 1. What is it?

Modular Monolith là một deployable application chứa nhiều business modules có boundary rõ về code, data ownership và interaction. Module không chỉ là folder; nó phải giới hạn dependency và mutation paths.

## 2. Why does it exist?

Một monolith không boundary dần thành shared database + shared services, nơi thay đổi Orders làm vỡ Billing. Microservices có thể cô lập hơn nhưng thêm network, deployment và consistency cost. Modular Monolith giữ process đơn nhưng luyện discipline về ownership.

## 3. How does it work?

```text
Host
 ├─ Orders  -> public contract
 ├─ Billing -> public contract
 └─ Catalog -> public contract

Orders --X--> Billing internal DbContext/entity
Orders -----> Billing API/application contract
```

Module có thể dùng schema/table ownership riêng dù cùng physical database.

## 4. Practical implementation

Trong .NET, tách assemblies và chỉ expose contract assembly/public facade. Architecture tests có thể assert namespace/assembly dependencies để CI bắt violation.

```csharp
// Orders chỉ biết abstraction công khai
public interface IBillingGateway
{
    Task<PaymentStatus> GetStatusAsync(Guid orderId, CancellationToken ct);
}
```

## 5. Real production scenario

E-commerce monolith có Catalog, Orders, Payments. Trước boundary, Orders query thẳng Payments tables. Một migration Payments đổi schema làm Orders fail. Sau khi ownership được enforce, schema nội bộ thay đổi không lan sang consumer.

## 6. Failure scenario & troubleshooting

**Symptom** → thay đổi một module yêu cầu sửa nhiều modules. **Evidence** → cross-module entity references/direct SQL. **Hypothesis** → boundary chỉ tồn tại trên diagram. **Diagnosis** → dependency graph + DB access map. **Fix** → facade/contracts, data ownership, architecture tests. **Verification** → build/test module dependency rules.

## 7. Common mistakes

Shared `Common` chứa domain logic; mọi module dùng cùng entities; internal event biến thành hidden synchronous coupling; chia module theo technical layer thay vì business capability.

## 8. Alternatives

Layered monolith đơn giản hơn cho domain nhỏ. Microservices phù hợp khi cần independent deployment/scale/ownership đủ mạnh để trả operational cost.

## 9. Trade-offs

### Advantages
Change isolation tốt hơn mà không có distributed-system tax đầy đủ.
### Costs / Risks
Cần discipline và tooling; process/database vẫn là shared failure/deployment boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Không bypass public module API.
### Middle
Giữ contracts và tests.
### Senior
Thiết kế ownership/transaction boundaries.
### Technical Lead / Architect
Quyết định module nào đủ business autonomy để sau này tách service nếu cần.

## 11. Key takeaway

- Folder không tạo boundary; dependency rules mới tạo boundary.
- Data ownership quan trọng ngang code ownership.
- Modular Monolith thường là bước đơn giản hơn Microservices.

# 6. Azure Service Bus PeekLock: xử lý message dài và duplicate delivery

## 1. What is it?

Ở PeekLock mode, consumer nhận message nhưng broker chưa xóa nó. Message bị lock tạm thời; consumer phải `Complete`, `Abandon`, `DeadLetter` hoặc để lock hết hạn.

## 2. Why does it exist?

Nếu broker xóa ngay khi deliver, process crash giữa chừng sẽ mất message. PeekLock hỗ trợ at-least-once delivery: message chỉ hoàn tất sau successful processing.

## 3. How does it work?

```text
Receive -> lock
  -> success -> Complete
  -> transient fail -> Abandon / retry
  -> poison -> DeadLetter
  -> crash/lock expiry -> message visible again
```

Long handler có thể cần automatic lock renewal, nhưng renewal không biến processing thành exactly-once.

## 4. Practical implementation

```csharp
var options = new ServiceBusProcessorOptions
{
    AutoCompleteMessages = false,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(10),
    MaxConcurrentCalls = 8
};

processor.ProcessMessageAsync += async args =>
{
    await handler.HandleAsync(args.Message, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message, args.CancellationToken);
};
```

Side effects phải idempotent theo `MessageId`/business operation ID.

## 5. Real production scenario

Image processing mất 3–8 phút. Lock 1 phút hết hạn giữa work; message được consumer khác nhận và cả hai ghi kết quả. Renewal giảm premature redelivery, idempotency ngăn duplicate side effect.

## 6. Failure scenario & troubleshooting

**Symptom** → `MessageLockLostException`, duplicate processing. **Evidence** → processing duration > lock/renewal hoặc network pause. **Hypothesis** → handler quá dài/blocked. **Diagnosis** → trace receive-to-settlement duration. **Fix** → renewal, chia nhỏ work, idempotency. **Verification** → inject slow processing/process crash.

## 7. Common mistakes

Complete trước side effect; retry poison message vô hạn; concurrency quá cao làm downstream saturation; coi lock là distributed transaction.

## 8. Alternatives

Receive-and-delete chỉ phù hợp khi loss chấp nhận được. Durable workflow/queue chaining phù hợp work rất dài nhiều bước.

## 9. Trade-offs

### Advantages
Giảm message loss khi consumer crash.
### Costs / Risks
Duplicate delivery, lock management và idempotency complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu settlement.
### Middle
Handle complete/abandon/dead-letter.
### Senior
Thiết kế idempotency và tune concurrency/lock renewal.
### Technical Lead / Architect
Quyết định work granularity và delivery semantics toàn flow.

## 11. Key takeaway

- PeekLock cho at-least-once, không exactly-once.
- Lock duration phải phù hợp processing behavior.
- Idempotency vẫn là requirement cốt lõi.

# 7. Azure App Service deployment slots: swap không tự động làm release an toàn

## 1. What is it?

Deployment slot là live App Service environment riêng trong cùng app, thường `staging` và `production`. Ta deploy/warm staging rồi swap routing/configuration semantics sang production.

## 2. Why does it exist?

Deploy trực tiếp có thể đưa cold startup, missing dependency hoặc broken artifact vào traffic ngay. Slot tạo nơi chạy artifact gần production trước cutover.

## 3. How does it work?

```text
Build artifact -> Staging slot -> warm/health validation
                              -> swap
Client traffic ----------------> Production target
```

Slot settings có thể “sticky”; không phải mọi configuration đều swap giống nhau.

## 4. Practical implementation

Pipeline nên: deploy artifact → warm endpoint → readiness/smoke tests → swap → post-swap health validation → rollback swap nếu cần. Database migration phải backward-compatible với cả old/new app trong transition.

## 5. Real production scenario

Code mới deploy staging khỏe nhưng migration đã drop column mà production version cũ còn đọc. Swap chưa xảy ra mà production đã lỗi. Slot isolation không tạo database isolation.

## 6. Failure scenario & troubleshooting

**Symptom** → app fail ngay sau swap dù staging health pass. **Evidence** → production-only hostname/config/traffic behavior khác. **Hypothesis** → slot settings hoặc shared dependency mismatch. **Diagnosis** → compare settings, dependency telemetry, startup logs. **Fix** → sticky-setting discipline + production-like smoke checks. **Verification** → swap rehearsal.

## 7. Common mistakes

Coi slot là full environment; migration destructive trước compatibility window; health check chỉ trả 200 hardcoded; không warm dependencies; secrets/config slot mismatch.

## 8. Alternatives

Blue-green ở separate apps/clusters tăng isolation; canary giảm blast radius; rolling deployment đơn giản hơn nhưng rollback semantics khác.

## 9. Trade-offs

### Advantages
Warm-up và fast traffic switch/rollback.
### Costs / Risks
Shared resources/config complexity; không bảo vệ khỏi incompatible DB/schema/external contract.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu staging vs production slot.
### Middle
Automate health/smoke checks.
### Senior
Thiết kế backward-compatible migration và rollback.
### Technical Lead / Architect
Chọn deployment strategy theo blast radius, stateful dependencies và SLO.

## 11. Key takeaway

- Slot swap chỉ giải quyết một phần release risk.
- Shared database vẫn là compatibility boundary.
- Rollback phải được thiết kế, không chỉ có nút Swap.

# 8. Playwright E2E: bảo vệ critical flow mà không tạo flaky suite

## 1. What is it?

Playwright điều khiển browser thật để kiểm thử hệ thống qua UI/network như user. E2E mạnh vì bao phủ nhiều integration boundary cùng lúc, nhưng chính vì thế failure signal khó localize hơn unit/integration tests.

## 2. Why does it exist?

Controller tests không chứng minh login redirect, JavaScript, API, cookie và DOM cùng hoạt động. Critical user journey cần một lớp test xuyên hệ thống.

## 3. How does it work?

```text
Browser -> UI -> API -> Auth -> DB
   ^                         |
   +------- assertion -------+
```

Playwright auto-wait theo actionable state; test nên chờ condition business/UI thay vì arbitrary sleep.

## 4. Practical implementation

```typescript
test('user can submit timesheet', async ({ page }) => {
  await page.goto('/timesheets/new');
  await page.getByLabel('Hours').fill('8');
  await page.getByRole('button', { name: 'Submit' }).click();
  await expect(page.getByText('Submitted')).toBeVisible();
});
```

Dùng stable semantic locators (`role`, `label`) và deterministic test data.

## 5. Real production scenario

API tests đều pass nhưng CSP change làm frontend auth callback script fail. Một E2E login→submit flow bắt regression trước release.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail ngẫu nhiên CI. **Evidence** → trace/video cho thấy fixed timeout hoặc shared data collision. **Hypothesis** → nondeterministic state/timing. **Diagnosis** → Playwright trace + server logs/correlation ID. **Fix** → isolate data, condition-based waits, remove cross-test dependency. **Verification** → repeated CI runs.

## 7. Common mistakes

`waitForTimeout(5000)`; test mọi permutation qua UI; shared user state; selector theo fragile CSS; retry che flaky root cause.

## 8. Alternatives

Unit tests cho logic; integration/API tests cho DB/contracts; contract tests cho service boundary. E2E chỉ giữ journeys có business value cao.

## 9. Trade-offs

### Advantages
Confidence cao cho integrated user flow.
### Costs / Risks
Chậm, expensive, khó diagnose, dễ flaky nếu environment không deterministic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Viết stable locator/assertion.
### Middle
Quản lý fixtures/test data.
### Senior
Debug flakiness bằng trace và phân tầng test.
### Technical Lead / Architect
Xác định risk nào đáng trả cost E2E.

## 11. Key takeaway

- E2E bảo vệ journey, không thay toàn bộ test pyramid.
- Flakiness thường là state/timing design problem.
- Trace + deterministic data quan trọng hơn retry count.

# 9. Vue/JavaScript event loop: microtask, rendering và stale UI

## 1. What is it?

JavaScript trên browser thường chạy application code trên một main thread theo event loop. Promise continuations chạy qua microtask queue; browser rendering xảy ra giữa các turns phù hợp. Vue batching state updates dựa trên scheduling thay vì render DOM ngay sau từng assignment.

## 2. Why does it exist?

Nếu DOM render sau mọi state mutation, UI work rất đắt. Batching tăng efficiency, nhưng developer dễ giả định DOM đã cập nhật ngay sau `state.value = ...`.

## 3. How does it work?

```text
Task: click handler
 -> mutate reactive state
 -> schedule Vue update
 -> Promise/microtasks
 -> flush update
 -> browser render
 -> next task
```

`nextTick()` chờ Vue hoàn tất DOM update đã schedule; nó không phải general-purpose delay.

## 4. Practical implementation

```ts
const open = ref(false)

async function showDialog() {
  open.value = true
  await nextTick()
  inputRef.value?.focus()
}
```

Với API races, dùng request identity/cancellation; event loop ordering không đảm bảo response cũ về trước response mới.

## 5. Real production scenario

Search-as-you-type gửi request A rồi B. B trả trước và render đúng; A trả sau ghi đè kết quả mới. Bug nhìn như Vue reactivity nhưng root cause là async race.

## 6. Failure scenario & troubleshooting

**Symptom** → UI đôi lúc quay về dữ liệu cũ. **Evidence** → network timeline cho response ordering đảo. **Hypothesis** → stale async completion. **Diagnosis** → request IDs/DevTools timing. **Fix** → AbortController hoặc latest-request guard. **Verification** → inject variable latency.

## 7. Common mistakes

Dùng `setTimeout` để “đợi Vue”; block main thread bằng computation; không cancel stale fetch; assume state mutation = DOM mutation ngay lập tức.

## 8. Alternatives

Web Worker cho CPU-heavy browser work; server-side filtering giảm client work; state library không tự loại race conditions.

## 9. Trade-offs

### Advantages
Batching/reactivity giảm manual DOM work.
### Costs / Risks
Scheduling semantics tạo timing bugs nếu mental model sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu Promise/event loop cơ bản.
### Middle
Dùng `nextTick` và cancellation đúng.
### Senior
Phân tích network/UI races và main-thread bottleneck.
### Technical Lead / Architect
Đặt frontend concurrency/data-fetching conventions.

## 11. Key takeaway

- Reactive state update không đồng nghĩa DOM update synchronous.
- Async response ordering phải được kiểm soát.
- DevTools timeline là evidence tốt hơn thêm delay.

# 10. LLM Tool Calling: model chọn intent, application giữ quyền thực thi

## 1. What is it?

Tool Calling cho phép model tạo structured request để application gọi function/API bên ngoài. Model không trực tiếp “có quyền” trên hệ thống; application nhận tool call, validate và quyết định có thực thi hay không.

## 2. Why does it exist?

LLM chỉ sinh output xác suất và knowledge có giới hạn. Muốn đọc order hiện tại, tạo ticket hoặc query database, nó cần deterministic integration boundary thay vì hallucinate kết quả.

## 3. How does it work?

```text
User -> LLM
LLM -> tool_call(name,args)
App -> authorize + validate
App -> deterministic tool/API
Tool -> result
App -> LLM -> final response
```

Security boundary nằm ở application/tool executor, không ở prompt “hãy chỉ làm điều an toàn”.

## 4. Practical implementation

```csharp
public sealed record GetOrderArgs(Guid OrderId);

async Task<OrderDto?> GetOrderAsync(
    GetOrderArgs args,
    ClaimsPrincipal user,
    CancellationToken ct)
{
    if (!authorization.CanReadOrder(user, args.OrderId))
        throw new UnauthorizedAccessException();

    return await orders.FindAsync(args.OrderId, ct);
}
```

Schema validation, authorization, timeout, audit và idempotency phải nằm ngoài model.

## 5. Real production scenario

Support assistant có tool `refund_order`. User prompt cố yêu cầu refund order của account khác. Nếu executor tin model-provided `customerId`, authorization bị bypass. Correct design lấy identity từ trusted session và kiểm tra order ownership server-side.

## 6. Failure scenario & troubleshooting

**Symptom** → tool được gọi với arguments hợp schema nhưng sai business intent. **Evidence** → audit log cho model/tool arguments và authenticated principal. **Hypothesis** → authorization bị delegate cho model. **Diagnosis** → inspect executor boundary. **Fix** → deterministic policy checks + least-privilege tools + confirmation cho high-impact actions. **Verification** → adversarial evals và authorization integration tests.

## 7. Common mistakes

Tool quá rộng như `execute_sql`; đưa secret vào context; tin model validation; retry side-effecting tool không idempotency; không giới hạn timeout/rate; log sensitive prompts/results.

## 8. Alternatives

Structured Outputs chỉ tạo data shape, không thực thi action. Workflow deterministic phù hợp process cố định; RAG phù hợp retrieval nhưng không thay transactional tools.

## 9. Trade-offs

### Advantages
Kết nối natural-language reasoning với live systems và deterministic operations.
### Costs / Risks
Tăng attack surface, authorization complexity, latency, token/tool cost và observability requirement.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu model output không phải trusted command.
### Middle
Implement schema validation/tool dispatcher.
### Senior
Thiết kế authorization, idempotency, timeout và audit.
### Technical Lead / Architect
Quyết định tool granularity, trust boundary và actions nào không nên trao cho agent tự động.

## 11. Key takeaway

- Model đề xuất tool call; application quyết định và thực thi.
- Authorization phải dựa trên trusted identity/context.
- High-impact actions cần deterministic controls, audit và bounded capability.
