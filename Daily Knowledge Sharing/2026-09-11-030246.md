# 1. C# `ValueTask`: tối ưu allocation có điều kiện và vì sao dùng sai còn tệ hơn `Task`

## 1. What is it?

`ValueTask<T>` là awaitable type trong .NET có thể biểu diễn một asynchronous result mà không nhất thiết phải allocate một `Task<T>` object cho mỗi invocation.

Mental model:

```text
Task<T>
  → thường là một reference object đại diện cho operation

ValueTask<T>
  → có thể chứa trực tiếp kết quả đã có
  → hoặc wrap một Task<T>
  → hoặc wrap IValueTaskSource<T>
```

Điểm quan trọng là `ValueTask<T>` không phải phiên bản “nhanh hơn” của `Task<T>`. Nó là một optimization tool dành cho hot path nơi operation rất thường xuyên hoàn thành synchronously và allocation của `Task<T>` đã được chứng minh là đáng kể.

## 2. Why does it exist?

Một API async có thể phần lớn trả kết quả ngay từ memory/cache nhưng thỉnh thoảng mới cần I/O.

Ví dụ một parser hoặc pooled transport:

```text
95% call → dữ liệu đã sẵn sàng
5% call  → cần await I/O
```

Nếu luôn trả `Task<T>`, hot path có thể tạo lượng lớn allocation không cần thiết. `ValueTask<T>` cho phép trả kết quả trực tiếp mà vẫn giữ cùng async calling model.

Tuy nhiên optimization này đổi lại API semantics phức tạp hơn.

## 3. How does it work?

Một `ValueTask<T>` là struct. Nó có thể chứa:

* một `T` đã hoàn thành
* một `Task<T>`
* một nguồn implement `IValueTaskSource<T>` cùng token versioning

Điều này cho phép runtime tránh một heap allocation trong synchronous-completion path.

Nhưng vì có thể wrap reusable `IValueTaskSource<T>`, caller không được giả định `ValueTask<T>` có semantics giống `Task<T>` hoàn toàn.

Đặc biệt, một `ValueTask<T>` nói chung chỉ nên được `await` một lần trừ khi API documentation bảo đảm điều khác.

## 4. Practical implementation

Một cache đơn giản:

```csharp
public sealed class ProductLookup
{
    private readonly Dictionary<int, Product> _cache = new();
    private readonly ProductRepository _repository;

    public ProductLookup(ProductRepository repository)
    {
        _repository = repository;
    }

    public ValueTask<Product?> GetAsync(
        int id,
        CancellationToken cancellationToken)
    {
        if (_cache.TryGetValue(id, out var product))
        {
            return ValueTask.FromResult<Product?>(product);
        }

        return new ValueTask<Product?>(LoadAsync(id, cancellationToken));
    }

    private async Task<Product?> LoadAsync(
        int id,
        CancellationToken cancellationToken)
    {
        var product = await _repository.GetAsync(id, cancellationToken);

        if (product is not null)
        {
            _cache[id] = product;
        }

        return product;
    }
}
```

Nhưng nếu API hầu như luôn thực hiện I/O, `Task<T>` thường đơn giản và đủ tốt.

## 5. Real production scenario

Một high-throughput protocol handler gọi hàng triệu lần mỗi phút vào method đọc metadata. Khoảng 99% metadata đã nằm trong local cache.

Profiler cho thấy `Task<T>` allocation ở method này đóng góp đáng kể vào Gen 0 allocation rate và GC frequency.

Sau benchmark có kiểm soát, team chuyển hot method sang `ValueTask<T>` và giảm allocation rõ rệt.

Ở một CRUD API chỉ vài trăm requests/second, cùng thay đổi có thể gần như không tạo khác biệt nhưng lại làm API khó sử dụng hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → behavior khó đoán khi cùng một `ValueTask<T>` được await nhiều lần hoặc convert/reuse sai.

**Evidence** → exception từ underlying `IValueTaskSource<T>` hoặc kết quả không còn hợp lệ theo lifecycle source.

**Hypothesis** → caller đang dùng `ValueTask<T>` như một reusable `Task<T>`.

**Diagnosis** → tìm code lưu `ValueTask<T>` vào field, await nhiều lần hoặc gọi `.AsTask()` không cần thiết trong hot loop.

**Fix** → await trực tiếp một lần; nếu cần cache/reuse operation, materialize thành `Task<T>` hoặc thiết kế API trả `Task<T>` ngay từ đầu.

**Verification** → benchmark allocation, thêm concurrency tests và kiểm tra semantics của underlying source.

## 7. Common mistakes

* Thay toàn bộ `Task<T>` bằng `ValueTask<T>` vì nghĩ struct luôn nhanh hơn.
* Dùng `ValueTask<T>` khi method gần như luôn asynchronous.
* Await cùng instance nhiều lần.
* Lưu `ValueTask<T>` lâu dài như state.
* Tối ưu trước khi đo allocation bằng profiler hoặc benchmark.

## 8. Alternatives

`Task<T>` là default tốt cho hầu hết application code vì semantics đơn giản, composable và dễ cache/reuse.

Nếu synchronous path thật sự phổ biến nhưng performance chưa phải bottleneck, vẫn có thể giữ `Task<T>` để tối ưu maintainability.

## 9. Trade-offs

### Advantages

* Có thể giảm allocation trên hot path synchronous-completion.
* Hữu ích cho low-level libraries, parsers, pipelines và pooled infrastructure.

### Costs / Risks

* API semantics phức tạp hơn.
* Struct lớn hơn reference và có copying cost riêng.
* Dùng sai có thể làm code khó hiểu hoặc thậm chí chậm hơn.
* Lợi ích thường không đáng kể trong business CRUD path thông thường.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task<T>` là lựa chọn mặc định; `ValueTask<T>` không phải “Task nhanh hơn”.

### Middle

Biết đọc và sử dụng API trả `ValueTask<T>` đúng cách, đặc biệt await một lần.

### Senior

Biết profile allocation, đánh giá synchronous-completion ratio và benchmark trước khi thay public API.

### Technical Lead / Architect

Quyết định optimization có đáng đánh đổi API complexity hay không và giữ low-level optimization không lan sang business layer vô lý.

## 11. Key takeaway

* `ValueTask<T>` là optimization có điều kiện, không phải default async return type.
* Chỉ dùng khi synchronous completion phổ biến và allocation thực sự đáng quan tâm.
* `Task<T>` thường thắng về simplicity và correctness trong application code.

# 2. ASP.NET Core graceful shutdown: dừng nhận request, hoàn tất in-flight work và không làm mất background work khi instance bị terminate

## 1. What is it?

Graceful shutdown là quá trình application nhận tín hiệu terminate nhưng không thoát process ngay. Nó ngừng nhận work mới, cho work đang chạy một khoảng thời gian để kết thúc, propagate cancellation và giải phóng resource theo thứ tự có kiểm soát.

Mental model:

```text
SIGTERM / App Service stop / container termination
                 ↓
         Host begins shutdown
                 ↓
      stop accepting new work
                 ↓
 cancel BackgroundService token
                 ↓
   finish / checkpoint in-flight work
                 ↓
         dispose resources
                 ↓
             process exit
```

## 2. Why does it exist?

Production process luôn có thể restart do deployment, autoscaling, node maintenance, recycle hoặc crash recovery.

Nếu application coi shutdown là sự kiện hiếm và cứ giữ request/job cho tới khi process bị kill cưỡng bức, consequences gồm:

* HTTP request bị cắt giữa chừng
* message lock hết hạn và message được xử lý lại
* file chỉ ghi một phần
* transaction chưa commit
* background job bị mất progress

Graceful shutdown làm termination trở thành một phần của normal operational lifecycle.

## 3. How does it work?

ASP.NET Core Generic Host theo dõi lifetime signal. Khi shutdown bắt đầu, host phát cancellation tới hosted services và chờ tới shutdown timeout.

Với `BackgroundService`, token trong `ExecuteAsync` là contract quan trọng:

```text
host stopping
  ↓
stoppingToken.Cancel()
  ↓
consumer loop phải quan sát token
  ↓
method trả về
```

Nếu code ignore token hoặc giữ blocking call lâu hơn grace period, platform vẫn có thể kill process.

## 4. Practical implementation

```csharp
public sealed class InvoiceWorker : BackgroundService
{
    private readonly ChannelReader<InvoiceJob> _reader;
    private readonly ILogger<InvoiceWorker> _logger;

    public InvoiceWorker(
        ChannelReader<InvoiceJob> reader,
        ILogger<InvoiceWorker> logger)
    {
        _reader = reader;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in _reader.ReadAllAsync(stoppingToken))
        {
            try
            {
                await ProcessAsync(job, stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                _logger.LogInformation("Worker is shutting down");
                break;
            }
        }
    }
}
```

Configure timeout đủ cho workload nhưng không vô hạn:

```csharp
builder.Services.Configure<HostOptions>(options =>
{
    options.ShutdownTimeout = TimeSpan.FromSeconds(30);
});
```

## 5. Real production scenario

Một App Service scale-in một instance đang xử lý batch export 20 giây. Platform phát stop signal.

Nếu worker quan sát cancellation và checkpoint đúng cách, nó dừng nhận batch mới, hoàn tất hoặc persist progress của batch hiện tại rồi exit.

Nếu worker dùng loop không token và blocking filesystem call 2 phút, process bị terminate giữa file generation. User nhận file corrupted hoặc job stuck ở trạng thái `Processing`.

## 6. Failure scenario & troubleshooting

**Symptom** → chỉ khi deployment hoặc scale-in mới xuất hiện duplicate jobs, truncated files hoặc request reset.

**Evidence** → logs dừng đột ngột sau shutdown signal; telemetry cho thấy operation chưa hoàn thành trước process exit.

**Hypothesis** → application không honor cancellation hoặc grace period quá ngắn so với work unit.

**Diagnosis** → trace hosted-service lifecycle, kiểm tra `CancellationToken`, blocking calls và platform termination timeout.

**Fix** → làm work unit nhỏ hơn, checkpoint, propagate token, tránh bắt đầu long work khi host đã stopping.

**Verification** → chaos test bằng cách terminate instance giữa workload và xác nhận recovery/idempotency đúng.

## 7. Common mistakes

* Catch `OperationCanceledException` rồi log Error như production failure.
* Ignore `stoppingToken` trong network/database call.
* Nghĩ shutdown timeout bảo đảm work chắc chắn hoàn tất.
* Giữ một job không checkpoint hàng chục phút trong web process.
* Dựa vào graceful shutdown thay cho idempotency.

## 8. Alternatives

Long-running durable work có thể phù hợp hơn với queue + Worker Service, Azure Functions hoặc orchestration system thay vì nằm trong web request lifecycle.

Một job cực ngắn có thể xử lý trực tiếp trong request nếu business semantics cho phép.

## 9. Trade-offs

### Advantages

* Giảm partial work và noisy deployment failures.
* Cho lifecycle rõ ràng hơn với autoscaling/container platforms.

### Costs / Risks

* Cần thiết kế cancellation, checkpoint và idempotency.
* Grace period dài làm deployment/scale-in chậm hơn.
* Không loại bỏ hard kill hoặc process crash.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process có thể bị stop bất kỳ lúc nào và `CancellationToken` là lifecycle signal.

### Middle

Biết propagate token, xử lý `OperationCanceledException` đúng và cleanup resource.

### Senior

Thiết kế work unit có thể retry/checkpoint, test shutdown và phân biệt graceful termination với crash.

### Technical Lead / Architect

Quyết định loại workload nào được chạy trong web host, loại nào cần durable execution và reliability contract khi deployment/scale xảy ra.

## 11. Key takeaway

* Shutdown là normal production event, không phải edge case.
* Graceful shutdown cần cancellation-aware code và bounded work units.
* Idempotency vẫn cần thiết vì graceful shutdown không bao giờ là bảo đảm tuyệt đối.

# 3. EF Core `IQueryable` boundary: khi một lời gọi `ToListAsync` quá sớm biến query database thành xử lý in-memory đắt đỏ

## 1. What is it?

`IQueryable<T>` biểu diễn một query expression chưa được thực thi. EF Core có thể dịch expression tree đó thành SQL và đẩy filtering, sorting, projection xuống database.

Khi query được materialize bằng `ToListAsync`, `FirstAsync`, `CountAsync` hoặc tương tự, database execution xảy ra và phần code sau đó không còn được translate xuống SQL.

Mental model:

```text
IQueryable
  → build expression
  → translate SQL
  → execute in DB
  → materialize objects
  → IEnumerable/List processing in memory
```

## 2. Why does it exist?

Database engine được tối ưu để filter, join, aggregate và project gần dữ liệu.

Nếu application materialize quá sớm, nó có thể kéo hàng trăm nghìn rows qua network chỉ để filter xuống vài chục rows trong process memory.

Deferred execution cho phép compose query trước khi thực thi.

## 3. How does it work?

Code này giữ filtering ở database:

```csharp
var query = db.Orders
    .Where(x => x.TenantId == tenantId)
    .Where(x => x.Status == OrderStatus.Open)
    .OrderByDescending(x => x.CreatedUtc)
    .Select(x => new OrderDto(x.Id, x.Total));

var page = await query.Take(50).ToListAsync(ct);
```

Nhưng code này materialize quá sớm:

```csharp
var orders = await db.Orders.ToListAsync(ct);

var page = orders
    .Where(x => x.TenantId == tenantId)
    .Where(x => x.Status == OrderStatus.Open)
    .Take(50)
    .ToList();
```

Hai đoạn có thể cho cùng functional result trên dev database nhỏ nhưng production cost rất khác.

## 4. Practical implementation

Giữ composition ở query layer tới khi cần dữ liệu:

```csharp
public Task<List<OrderListItem>> GetOpenOrdersAsync(
    Guid tenantId,
    CancellationToken ct)
{
    return _db.Orders
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId && x.Status == OrderStatus.Open)
        .OrderByDescending(x => x.CreatedUtc)
        .Select(x => new OrderListItem(
            x.Id,
            x.Number,
            x.Total,
            x.CreatedUtc))
        .Take(100)
        .ToListAsync(ct);
}
```

Nếu cần custom C# function không translate được, hãy cố thu hẹp dataset trước rồi mới chuyển sang in-memory processing có chủ đích.

## 5. Real production scenario

Một reporting endpoint chạy tốt với 3,000 rows ở staging. Developer thêm reusable method trả `Task<List<Order>>`, sau đó caller filter theo tenant và date.

Production table có 8 triệu rows. Endpoint bắt đầu consume nhiều memory, network throughput tăng và SQL query trả dataset khổng lồ.

Root cause không phải “EF Core chậm”, mà là query boundary bị đặt sai.

## 6. Failure scenario & troubleshooting

**Symptom** → API memory tăng, response chậm, SQL duration có thể không quá cao nhưng result-set rất lớn.

**Evidence** → generated SQL thiếu `WHERE`/`TOP` dự kiến; rows returned lớn bất thường.

**Hypothesis** → materialization xảy ra trước filtering/projection.

**Diagnosis** → xem query logs, `ToQueryString()`, profiler và code path nơi `ToListAsync`/`AsEnumerable` xuất hiện.

**Fix** → expose composable query hoặc chuyển filter/projection vào repository/query service trước materialization.

**Verification** → generated SQL chứa predicate phù hợp; rows read/network payload giảm.

## 7. Common mistakes

* Gọi `ToListAsync` “cho dễ debug” trong reusable data method.
* Dùng `AsEnumerable()` giữa query rồi tiếp tục tưởng LINQ vẫn chạy ở SQL.
* Trả `IQueryable` xuyên quá nhiều architectural layers khiến persistence details leak.
* Dùng client-side filtering cho authorization boundary.
* Load full entity khi chỉ cần DTO projection.

## 8. Alternatives

Một query service có methods rõ ràng thường tốt hơn việc expose `IQueryable` ra toàn application.

Specification Pattern có thể hữu ích khi filter composition thực sự phức tạp, nhưng không cần đưa pattern vào chỉ để tránh vài `Where` clauses.

## 9. Trade-offs

### Advantages

Giữ work gần database, giảm network, memory và materialization cost.

### Costs / Risks

Query composition quá tự do có thể làm boundary kiến trúc mơ hồ. Không phải mọi C# expression đều translate sang SQL.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ trên `IQueryable` chưa nhất thiết chạy ngay.

### Middle

Biết vị trí materialization và kiểm tra generated SQL.

### Senior

Biết cân bằng composability, query translation, projection, authorization và performance.

### Technical Lead / Architect

Định nghĩa data-access boundary: ai được compose query, ai sở hữu persistence concern và cách tránh cả over-fetching lẫn leaking `IQueryable` toàn hệ thống.

## 11. Key takeaway

* `ToListAsync` là một execution boundary, không chỉ là method đổi collection type.
* Filter/project trước materialization khi có thể.
* Luôn kiểm tra SQL thật và rows thật khi performance có vấn đề.

# 4. SQL Server parameter sniffing: cùng một query, cùng code nhưng execution plan tốt cho user này lại rất tệ cho user khác

## 1. What is it?

Parameter sniffing là behavior khi SQL Server compile một parameterized query và sử dụng parameter values tại thời điểm compile để estimate cardinality rồi chọn execution plan. Plan đó có thể được cache và reuse cho những parameter values sau.

Mental model:

```text
first execution parameter
        ↓
cardinality estimate
        ↓
execution plan compiled
        ↓
plan cache
        ↓
reused cho parameter khác
```

Behavior này thường có lợi vì plan reuse giảm compilation cost. Vấn đề xuất hiện khi data distribution lệch mạnh.

## 2. Why does it exist?

SQL Server cần chọn giữa nhiều strategies:

* index seek + key lookup
* scan
* nested loops
* hash join
* memory grant khác nhau

Một parameter đại diện vài rows cần plan khác parameter đại diện hàng triệu rows.

Reuse một plan là trade-off giữa compile overhead và per-execution optimality.

## 3. How does it work?

Giả sử table Orders có:

```text
Tenant A → 100 rows
Tenant B → 8,000,000 rows
```

Stored procedure:

```sql
SELECT Id, CreatedUtc, Total
FROM Orders
WHERE TenantId = @TenantId;
```

Nếu first compile dùng Tenant A, optimizer có thể chọn index seek + lookup rất hiệu quả cho 100 rows. Khi cùng plan dùng cho Tenant B, hàng triệu lookups có thể cực đắt.

Ngược lại, plan scan tối ưu cho Tenant B lại lãng phí cho Tenant A.

## 4. Practical implementation

Bước đầu không phải ngay lập tức thêm `OPTION (RECOMPILE)`.

Đầu tiên đo:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

So sánh execution plans cho parameter nhỏ/lớn và kiểm tra actual vs estimated rows.

Một lựa chọn có chủ đích:

```sql
SELECT Id, CreatedUtc, Total
FROM Orders
WHERE TenantId = @TenantId
OPTION (RECOMPILE);
```

Điều này compile theo parameter hiện tại mỗi execution, nhưng tăng CPU compilation.

Một số workload phù hợp với query branching, filtered index, statistics improvement hoặc plan hints mới hơn tùy SQL Server version.

## 5. Real production scenario

Một multi-tenant SaaS có 98% tenants dưới 10,000 orders và một enterprise tenant có 50 triệu orders.

Sau application restart, first request tình cờ đến từ small tenant. Plan cache chứa seek-oriented plan. Khi enterprise tenant mở dashboard, query chạy 40 giây thay vì 400 ms với plan phù hợp.

Incident có thể “tự hết” sau recompile hoặc plan eviction, khiến lỗi khó tái hiện nếu không lưu plan evidence.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng query lúc nhanh lúc chậm theo parameter; app code không đổi.

**Evidence** → Query Store cho thấy nhiều runtime distributions hoặc plan regression; actual/estimated rows chênh lớn.

**Hypothesis** → cached plan không phù hợp cho skewed parameter.

**Diagnosis** → so plans, parameters, statistics, row distribution và logical reads.

**Fix** → chọn mitigation dựa trên data shape: recompile có chọn lọc, optimize strategy, query split hoặc indexing/statistics changes.

**Verification** → test representative parameter classes, không chỉ một sample value.

## 7. Common mistakes

* Clear toàn bộ plan cache trong Production như một “fix”.
* Dùng `RECOMPILE` mọi nơi và chuyển vấn đề thành CPU compilation pressure.
* Đổ lỗi parameter sniffing cho mọi slow query mà không kiểm tra plan/evidence.
* Test performance chỉ với một tenant/data distribution.

## 8. Alternatives

Có thể dùng query-specific plan forcing/Query Store trong một số incident response scenario, nhưng phải hiểu đó là operational control chứ không thay thế root-cause analysis.

Schema/data partitioning có thể thay đổi problem shape nhưng là architectural decision lớn hơn.

## 9. Trade-offs

### Advantages

Plan caching thường giảm CPU và cải thiện throughput đáng kể.

### Costs / Risks

Data skew làm một cached plan khó tối ưu cho mọi parameter. Mitigation như recompilation đổi latency predictability lấy CPU compile cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu parameterized query có thể reuse execution plan.

### Middle

Biết đọc actual/estimated rows, logical reads và Query Store cơ bản.

### Senior

Phân biệt data skew, stale statistics và plan regression; chọn mitigation theo evidence.

### Technical Lead / Architect

Nhận ra multi-tenant data distribution là capacity/design concern; performance testing phải bao gồm representative tenant sizes.

## 11. Key takeaway

* Parameter sniffing là optimization bình thường có thể trở thành vấn đề khi data skew lớn.
* Điều tra bằng plans, parameters và cardinality evidence.
* Không có một hint duy nhất đúng cho mọi workload.

# 5. Redis cache penetration + negative caching: bảo vệ database khỏi các key không tồn tại bị hỏi lặp lại

## 1. What is it?

Cache penetration xảy ra khi requests liên tục hỏi những keys không tồn tại. Vì cache chỉ chứa dữ liệu có thật, mỗi request trở thành cache miss và đi xuống database.

Mental model:

```text
GET product:99999999
        ↓
Redis MISS
        ↓
Database MISS
        ↓
next request repeats everything
```

Negative caching lưu tạm thời kết quả “không tồn tại” để tránh lặp lại expensive miss.

## 2. Why does it exist?

Cache-aside bảo vệ database tốt khi hot data tồn tại. Nhưng nó không tự bảo vệ các lookups invalid.

Nguồn invalid key có thể là:

* bot/crawler
* stale links
* client bug
* brute-force enumeration
* deleted entities

Nếu một invalid ID bị request hàng nghìn lần/second, database vẫn chịu toàn bộ load.

## 3. How does it work?

Flow với negative cache:

```text
Request
  ↓
Redis
  ├─ value → return value
  ├─ negative marker → return 404
  └─ miss → query DB
               ├─ found → cache value
               └─ not found → cache short-lived negative marker
```

Negative TTL thường ngắn hơn normal object TTL vì “không tồn tại” có thể thay đổi khi entity được tạo sau đó.

## 4. Practical implementation

```csharp
private const string MissingMarker = "__missing__";

public async Task<ProductDto?> GetProductAsync(int id, CancellationToken ct)
{
    var key = $"product:{id}";
    var cached = await _redis.StringGetAsync(key);

    if (cached == MissingMarker)
        return null;

    if (cached.HasValue)
        return JsonSerializer.Deserialize<ProductDto>(cached!);

    var product = await _db.Products
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new ProductDto(x.Id, x.Name, x.Price))
        .SingleOrDefaultAsync(ct);

    if (product is null)
    {
        await _redis.StringSetAsync(
            key,
            MissingMarker,
            TimeSpan.FromSeconds(20));

        return null;
    }

    await _redis.StringSetAsync(
        key,
        JsonSerializer.Serialize(product),
        TimeSpan.FromMinutes(5));

    return product;
}
```

## 5. Real production scenario

Một product URL bị bot crawl với millions of random numeric IDs. Valid product hit rate chỉ 0.1%.

Redis hit rate nhìn rất thấp và SQL Server nhận khối lượng point lookups lớn dù mỗi query riêng lẻ nhanh.

Negative caching 10–30 giây cho repeated invalid IDs làm giảm duplicate DB work đáng kể, kết hợp rate limiting để xử lý random-key attack rộng hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis miss rate cao, database QPS cao nhưng phần lớn query trả 0 rows.

**Evidence** → application metrics phân loại cache miss cho not-found; access logs có repeated invalid IDs.

**Hypothesis** → cache penetration.

**Diagnosis** → đo cardinality invalid keys, repetition frequency và nguồn traffic.

**Fix** → negative caching cho repeated misses, validation/rate limiting, có thể Bloom filter ở scale đặc biệt lớn.

**Verification** → DB QPS cho missing lookups giảm; 404 latency và Redis behavior ổn định.

## 7. Common mistakes

* Cache negative result quá lâu và làm newly-created entity tiếp tục trả 404.
* Dùng negative caching như defense duy nhất trước random-key attack với mỗi key chỉ xuất hiện một lần.
* Không validate input range/format trước cache/database.
* Cache exception/timeout như “not found”.

## 8. Alternatives

Bloom filter có thể chặn nhanh keys chắc chắn không tồn tại nhưng có false positives và cần lifecycle/rebuild strategy.

Rate limiting xử lý abusive traffic theo caller/IP/keyspace nhưng không loại database miss cho legitimate repeated invalid requests.

## 9. Trade-offs

### Advantages

* Giảm repeated database misses.
* Giảm latency cho repeated 404 lookups.

### Costs / Risks

* Staleness cho newly-created entities.
* Thêm cache key/state semantics.
* Không hiệu quả nếu attack tạo key mới mỗi request.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss không có nghĩa database chắc chắn có dữ liệu.

### Middle

Biết implement negative marker với TTL ngắn và phân biệt not-found với error.

### Senior

Phân tích traffic shape, invalid-key cardinality và kết hợp negative caching với rate limiting/validation.

### Technical Lead / Architect

Quyết định cache có thật sự là đúng layer để xử lý vấn đề hay upstream contract/security controls nên loại traffic sớm hơn.

## 11. Key takeaway

* Cache-aside không tự bảo vệ database khỏi repeated missing keys.
* Negative caching chỉ nên cache “không tồn tại”, không cache transient failure như 404.
* TTL phải phản ánh khả năng entity xuất hiện sau đó.

# 6. Domain Events vs Integration Events: tách invariant nội bộ khỏi contract giữa bounded contexts

## 1. What is it?

Domain Event biểu diễn một fact có ý nghĩa trong domain model, thường trong cùng bounded context: `OrderConfirmed`, `EmployeeApproved`, `InvoiceIssued`.

Integration Event là contract được publish qua boundary để hệ thống/bounded context khác phản ứng.

Hai loại có thể cùng xuất phát từ một business occurrence nhưng không nên bị coi là cùng object chỉ vì tên giống nhau.

## 2. Why does it exist?

Nếu domain model publish thẳng internal entity/event schema ra Service Bus, internal refactoring trở thành external breaking change.

Ngược lại, nếu mọi internal domain reaction đều phải qua remote message broker, local invariant/workflow bị biến thành distributed system không cần thiết.

Tách hai concepts giúp giữ boundary:

```text
Domain truth nội bộ
        ↓
Application mapping
        ↓
Stable external contract
```

## 3. How does it work?

Ví dụ:

```text
Order Aggregate
  emits OrderConfirmedDomainEvent
            ↓
Application handler
  updates local projection / schedules work
            ↓
creates OrderConfirmedIntegrationEvent
            ↓
Outbox
            ↓
Service Bus
            ↓
Inventory bounded context
```

Domain event có thể chứa domain-rich object/reference phù hợp nội bộ. Integration event nên là explicit versioned DTO với ownership rõ ràng.

## 4. Practical implementation

Domain event:

```csharp
public sealed record OrderConfirmedDomainEvent(
    Guid OrderId,
    DateTime ConfirmedUtc) : IDomainEvent;
```

Integration contract:

```csharp
public sealed record OrderConfirmedV1(
    Guid OrderId,
    string CustomerReference,
    IReadOnlyList<OrderLineV1> Lines,
    DateTime ConfirmedUtc);
```

Application mapping:

```csharp
public async Task Handle(
    OrderConfirmedDomainEvent domainEvent,
    CancellationToken ct)
{
    var order = await _orders.GetAsync(domainEvent.OrderId, ct);

    var integrationEvent = new OrderConfirmedV1(
        order.Id,
        order.CustomerReference,
        order.Lines.Select(x => new OrderLineV1(x.Sku, x.Quantity)).ToArray(),
        domainEvent.ConfirmedUtc);

    _outbox.Add(integrationEvent);
}
```

## 5. Real production scenario

Commerce team đổi internal aggregate từ `CustomerId` sang richer `CustomerAccount` model. Nếu Service Bus payload serialize trực tiếp aggregate/domain event, consumers có thể break.

Nếu integration contract riêng, domain model có thể evolve miễn mapping vẫn tạo `OrderConfirmedV1` đúng contract hoặc giới thiệu `V2` có migration strategy.

## 6. Failure scenario & troubleshooting

**Symptom** → một refactor nội bộ bất ngờ làm downstream deserialization fail.

**Evidence** → message payload shape thay đổi cùng deployment producer dù consumer contract không được coordinated.

**Hypothesis** → internal domain type đã bị dùng trực tiếp làm integration contract.

**Diagnosis** → inspect producer serialization path và package sharing giữa services.

**Fix** → introduce explicit integration DTO/versioning; map ở boundary; consumer tolerant với compatible changes khi phù hợp.

**Verification** → contract tests giữa published schema và consumers.

## 7. Common mistakes

* Coi MediatR notification = distributed event architecture.
* Serialize EF entity trực tiếp thành broker message.
* Share một “Common.Events” assembly chứa toàn bộ internal models giữa services.
* Bắt local invariant phải chờ remote consumer.
* Gắn versioning vào class name nhưng không có compatibility policy.

## 8. Alternatives

Một simple application service call tốt hơn domain events nếu reaction chỉ có một nơi và event abstraction không tạo giá trị.

Synchronous REST có thể phù hợp cho query/immediate response requirement; messaging phù hợp khi decoupling và eventual consistency đáng giá.

## 9. Trade-offs

### Advantages

* Cô lập domain evolution khỏi external contracts.
* Làm ownership và compatibility rõ ràng.
* Hỗ trợ Outbox/eventual consistency có kiểm soát.

### Costs / Risks

* Thêm mapping, schema/version governance và observability.
* Event-driven design dễ overengineer nếu system nhỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event biểu diễn fact đã xảy ra, không phải command trá hình.

### Middle

Biết tách domain event nội bộ và DTO integration event.

### Senior

Thiết kế transaction boundary, Outbox, schema compatibility, retries và idempotent consumers.

### Technical Lead / Architect

Quyết định bounded-context ownership, sự kiện nào xứng đáng trở thành public contract và nơi synchronous coupling đơn giản hơn messaging.

## 11. Key takeaway

* Internal domain model và external integration contract có lifecycle khác nhau.
* Đừng publish domain object trực tiếp chỉ vì tiện.
* Event boundary tốt giúp domain evolve mà không kéo toàn hệ thống thay đổi theo.

# 7. Azure Service Bus Sessions: giữ ordering theo business key mà không biến toàn queue thành single-threaded pipeline

## 1. What is it?

Azure Service Bus Sessions nhóm messages có cùng `SessionId` thành một ordered logical stream. Một receiver giữ exclusive session lock và xử lý messages của session theo thứ tự broker cung cấp.

Mental model:

```text
Queue
 ├─ Session Order-1001: M1 → M2 → M3
 ├─ Session Order-1002: M1 → M2
 └─ Session Order-1003: M1 → M2 → M3 → M4

Nhiều sessions có thể xử lý song song,
nhưng mỗi session giữ sequencing riêng.
```

## 2. Why does it exist?

Global ordering trên toàn queue thường làm throughput sụt mạnh vì mọi message phải đi qua một sequence duy nhất.

Business thường chỉ cần ordering theo entity/workflow key:

* events của cùng Order
* commands của cùng Account
* state transitions của cùng ImportJob

Sessions cho phép partition ordering theo business key.

## 3. How does it work?

Producer đặt `SessionId`, ví dụ `OrderId`.

Broker giữ messages cùng session trong ordered stream. Consumer accept session và có lock. Trong thời gian lock, instance khác không xử lý cùng session.

At-least-once delivery vẫn tồn tại. Session ordering không loại duplicate delivery và không tự bảo đảm business state transition hợp lệ.

## 4. Practical implementation

Producer:

```csharp
var message = new ServiceBusMessage(BinaryData.FromObjectAsJson(evt))
{
    MessageId = evt.EventId.ToString(),
    SessionId = evt.OrderId.ToString()
};

await sender.SendMessageAsync(message, ct);
```

Processor:

```csharp
var options = new ServiceBusSessionProcessorOptions
{
    MaxConcurrentSessions = 16,
    MaxConcurrentCallsPerSession = 1,
    AutoCompleteMessages = false
};

await using var processor = client.CreateSessionProcessor(
    "order-events",
    options);
```

Consumer vẫn nên deduplicate bằng `MessageId` hoặc Inbox table khi side effects cần correctness.

## 5. Real production scenario

Order workflow nhận:

```text
OrderCreated
PaymentAuthorized
OrderCancelled
```

Nếu events của cùng order chạy song song trên nhiều consumers, `OrderCancelled` có thể commit trước `PaymentAuthorized`, làm state machine khó kiểm soát.

Đặt `SessionId = OrderId` serialize processing trong từng order nhưng vẫn cho hàng nghìn orders khác chạy song song.

## 6. Failure scenario & troubleshooting

**Symptom** → một subset messages bị backlog lâu trong khi queue tổng thể vẫn có consumers rảnh.

**Evidence** → backlog tập trung vào một hot session ID.

**Hypothesis** → session key distribution lệch; một business entity phát quá nhiều messages.

**Diagnosis** → metric messages/session, processing duration và session-lock renewals.

**Fix** → giảm work trong session handler, xem lại session granularity hoặc redesign hot aggregate/workflow.

**Verification** → session latency giảm, concurrency giữa session tăng mà ordering requirement vẫn đúng.

## 7. Common mistakes

* Dùng cùng một `SessionId` cho toàn tenant lớn và vô tình single-thread cả workload.
* Nghĩ session = exactly-once delivery.
* Cho handler gọi external API chậm nhiều phút dưới session lock.
* Không monitor hot sessions.
* Chọn random SessionId mỗi message nên ordering không còn ý nghĩa.

## 8. Alternatives

Nếu không cần ordering, queue bình thường đơn giản và throughput cao hơn.

Nếu cần complex long-running workflow state, Durable Functions hoặc dedicated workflow engine có thể phù hợp hơn.

Partitioned data store + optimistic concurrency cũng có thể bảo vệ state mà không serialize broker processing hoàn toàn.

## 9. Trade-offs

### Advantages

* Ordering theo business key.
* Parallelism giữa independent sessions.
* Simplify một số state-machine workflows.

### Costs / Risks

* Hot session trở thành throughput bottleneck.
* Session lock/lifecycle tăng operational complexity.
* Không giải quyết duplicate delivery hoặc downstream idempotency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ordering thường cần theo key, không nhất thiết toàn queue.

### Middle

Biết set `SessionId`, configure processor và settle messages.

### Senior

Biết capacity-plan session distribution, idempotency, lock behavior và poison-message handling.

### Technical Lead / Architect

Quyết định business invariant có thực sự cần serialized message processing hay consistency nên được bảo vệ ở domain/database layer.

## 11. Key takeaway

* Sessions cung cấp ordered streams theo key, không phải global ordering miễn phí.
* Chọn `SessionId` là quyết định partitioning và throughput.
* Session ordering không thay thế idempotency.

# 8. Azure App Service Deployment Slots: deploy, warm-up và swap mà không nhầm deployment safety với database compatibility

## 1. What is it?

Deployment Slot là một live deployment environment trong cùng App Service, thường có `production` và `staging`. Code mới được deploy vào staging, warm-up/validate rồi traffic routing được swap sang production.

Mental model:

```text
Before swap:
production → v1
staging    → v2

After swap:
production → v2
staging    → v1
```

Slot giúp giảm downtime ở application deployment, nhưng không tự giải quyết schema migration hoặc external side effects.

## 2. Why does it exist?

Deploy trực tiếp vào production instance có thể gây:

* cold startup
* JIT/loading delay
* missing configuration chỉ phát hiện khi user traffic đến
* restart window

Slot cho phép validate build trong production-like environment trước khi nhận production traffic.

## 3. How does it work?

Deploy v2 vào staging slot. App khởi động, health/warm-up chạy, dependencies được validate. Khi swap, platform chuyển routing/configuration theo slot rules.

Một số settings có thể được đánh dấu slot-specific để credential/endpoint không swap nhầm.

Nhưng database thường là shared dependency:

```text
production v1 ─┐
               ├─ shared database
staging v2 ────┘
```

Do đó v2 migration phải tương thích với v1 trong thời gian coexist.

## 4. Practical implementation

Một release flow an toàn hơn:

```text
1. Build immutable artifact
2. Apply backward-compatible Expand migration
3. Deploy v2 to staging slot
4. Warm up + health validation
5. Run smoke tests
6. Swap staging → production
7. Observe metrics
8. Later run Contract migration after old code is gone
```

Health endpoint nên kiểm tra readiness cần thiết nhưng tránh biến mọi optional dependency thành hard failure.

## 5. Real production scenario

Version v2 rename column `CustomerName` thành `DisplayName` bằng destructive migration trước swap.

Staging v2 chạy được, nhưng production v1 vẫn đang live và bắt đầu fail query vì column cũ biến mất.

Team có deployment slot nhưng vẫn outage vì database compatibility bị phá trước traffic swap.

Đúng approach là Expand-Contract: thêm column mới, dual-read/write hoặc backfill, deploy compatible code, rồi remove old schema sau.

## 6. Failure scenario & troubleshooting

**Symptom** → staging health pass, nhưng production lỗi ngay khi migration chạy hoặc sau swap.

**Evidence** → SQL errors/5xx correlate với schema migration, không phải slot routing.

**Hypothesis** → application versions cùng tồn tại nhưng schema chỉ tương thích một version.

**Diagnosis** → map deployment timeline, migration order và compatibility matrix v1/v2.

**Fix** → rollback application nếu schema còn compatible; nếu không, forward-fix schema bằng additive compatibility change.

**Verification** → run both versions against transitional schema trong pre-production tests.

## 7. Common mistakes

* Nghĩ slot swap = full zero-downtime release.
* Run destructive migration trước khi old version hết traffic.
* Không đánh dấu secrets/endpoints là slot settings đúng cách.
* Warm-up chỉ gọi `/` nhưng critical startup path khác chưa được exercised.
* Không monitor sau swap vì “swap đã thành công”.

## 8. Alternatives

Blue-Green trên separate infrastructure cho isolation mạnh hơn nhưng cost/complexity cao hơn.

Canary deployment giảm blast radius bằng partial traffic nhưng cần routing và observability tốt.

Rolling deployment đơn giản cho stateless containers nhưng cũng yêu cầu backward compatibility giữa versions.

## 9. Trade-offs

### Advantages

* Giảm cold-start exposure.
* Cho smoke test trên near-production deployment.
* Swap/rollback application nhanh hơn.

### Costs / Risks

* Slot không cô lập shared database/external dependencies.
* Có additional config management và compute considerations.
* Rollback code không cứu được destructive data migration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu staging slot là environment live để chuẩn bị version mới trước production traffic.

### Middle

Biết deploy, configure slot settings, health check và swap.

### Senior

Thiết kế release với backward-compatible schema, smoke tests và post-swap telemetry.

### Technical Lead / Architect

Định nghĩa deployment compatibility contract xuyên app/database/message schema và chọn Blue-Green/Canary/slots dựa trên blast radius, cost và rollback requirements.

## 11. Key takeaway

* Slot giảm application deployment risk nhưng không loại database migration risk.
* Zero-downtime cần version compatibility trong toàn dependency graph.
* Rollback chỉ đáng tin nếu data/schema vẫn backward compatible.

# 9. Playwright E2E test isolation: selector bền, dữ liệu độc lập và vì sao flaky test thường là symptom của shared state

## 1. What is it?

E2E test chạy ứng dụng qua browser như user thật: UI, frontend logic, API, authentication và thường cả database/infrastructure thật.

Playwright cung cấp browser automation, auto-waiting, locators và tracing. Nhưng chất lượng E2E suite phụ thuộc nhiều hơn vào isolation và deterministic state chứ không chỉ API của tool.

## 2. Why does it exist?

Unit test bảo vệ local logic. Integration test bảo vệ subsystem boundary. Nhưng vẫn có failures chỉ xuất hiện khi toàn flow nối lại:

```text
Browser
  → frontend
  → auth
  → API
  → database
  → rendered result
```

E2E test bảo vệ critical user journeys nơi integration giữa layers mới là rủi ro chính.

## 3. How does it work?

Một test tốt cần:

* unique test data
* predictable starting state
* semantic selectors
* wait theo observable condition thay vì fixed delay
* cleanup hoặc disposable environment

Playwright locator như `getByRole` thường bền hơn CSS chain dựa vào layout internals.

Auto-wait giúp tránh nhiều timing races nhưng không sửa được shared-state races giữa tests.

## 4. Practical implementation

```typescript
import { test, expect } from '@playwright/test';

test('user can create a project', async ({ page }) => {
  const projectName = `e2e-${crypto.randomUUID()}`;

  await page.goto('/projects');
  await page.getByRole('button', { name: 'New project' }).click();
  await page.getByLabel('Title').fill(projectName);
  await page.getByRole('button', { name: 'Create' }).click();

  await expect(
    page.getByRole('heading', { name: projectName })
  ).toBeVisible();
});
```

Tránh:

```typescript
await page.waitForTimeout(3000);
await page.locator('div:nth-child(4) > button:nth-child(2)').click();
```

## 5. Real production scenario

CI chạy 12 E2E tests parallel. Tất cả dùng account `test@example.com` và project tên `Test Project`.

Một test delete project trong lúc test khác đang edit. Failures xuất hiện ngẫu nhiên và team bắt đầu rerun CI cho tới khi xanh.

Root cause không phải browser “không ổn định”, mà là test data collision và shared state.

## 6. Failure scenario & troubleshooting

**Symptom** → test pass local, fail ngẫu nhiên trên CI, rerun lại pass.

**Evidence** → Playwright trace cho thấy element/state bị test khác thay đổi; logs có cùng entity IDs giữa parallel workers.

**Hypothesis** → shared fixture/data hoặc timing dependency.

**Diagnosis** → inspect trace/video/network, chạy test repeat/parallel và kiểm tra data ownership.

**Fix** → unique per-test data, isolated users/tenants, deterministic seed/cleanup, semantic waits.

**Verification** → chạy suite nhiều vòng parallel; flake rate phải giảm về gần 0 thay vì chỉ một lần pass.

## 7. Common mistakes

* Dùng `waitForTimeout` thay cho condition-based wait.
* Selector dựa vào generated CSS classes/DOM position.
* Một shared admin account cho toàn suite parallel.
* Test quá nhiều implementation details thay vì user outcome.
* Cho phép automatic rerun che flaky tests mãi mãi.

## 8. Alternatives

Integration/API tests nhanh hơn và nên cover phần lớn business paths không cần browser.

Component tests hữu ích để test frontend behavior sâu hơn mà không cần full backend.

E2E nên tập trung vào critical cross-system journeys thay vì duplicate mọi unit case.

## 9. Trade-offs

### Advantages

* Bảo vệ integration thực tế xuyên UI/backend.
* Catch routing/auth/browser issues mà lower-level tests bỏ sót.

### Costs / Risks

* Chậm hơn, đắt hơn và dễ flaky nếu environment/state không kiểm soát.
* Debug failure phức tạp hơn.
* Suite quá lớn làm feedback loop chậm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu E2E test xác minh user flow xuyên nhiều layers.

### Middle

Biết dùng semantic locators, assertions và deterministic data.

### Senior

Thiết kế isolation, parallelism, tracing và phân lớp test để flake rate thấp.

### Technical Lead / Architect

Định nghĩa test strategy theo risk: cái gì cần unit, integration, contract hay E2E; không dùng browser test như universal solution.

## 11. Key takeaway

* Flaky E2E thường là engineering signal về state/timing, không phải thứ phải “chấp nhận”.
* Unique data và semantic waits quan trọng hơn sleep dài hơn.
* E2E bảo vệ critical integration journeys, không nên thay thế test pyramid.

# 10. CDN `Cache-Control`, `stale-while-revalidate` và origin shielding: giảm latency mà vẫn kiểm soát freshness và failure behavior

## 1. What is it?

CDN cache lưu response gần user tại edge để giảm round trip tới origin. `Cache-Control` mô tả cacheability/freshness contract giữa browser, CDN và origin.

`stale-while-revalidate` cho phép cache tạm phục vụ response đã stale trong một khoảng thời gian trong khi revalidate ở background.

Origin shielding là kiến trúc đưa một lớp cache trung gian tập trung trước origin để nhiều edge misses không đồng thời đánh trực tiếp backend.

## 2. Why does it exist?

Không có CDN cache:

```text
100,000 users
   ↓
origin API/CMS
   ↓
database
```

Với edge cache:

```text
Users → nearby edge cache
               ↓ occasional miss/revalidate
           shield/origin
```

Mục tiêu không chỉ latency. CDN còn giảm origin load và blast radius khi traffic spike.

Nhưng cache sai có thể trả stale hoặc private content cho sai user.

## 3. How does it work?

Ví dụ header:

```http
Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=30
```

Tùy CDN/browser support và configuration:

* browser có thể coi fresh 60 giây
* shared cache có thể dùng `s-maxage=300`
* sau đó có thể serve stale tối đa 30 giây trong lúc revalidate

Cache key có thể gồm URL, query, headers hoặc rules khác. Sai cache key là correctness bug, không chỉ performance bug.

## 4. Practical implementation

ASP.NET Core response cho public catalog data:

```csharp
app.MapGet("/catalog/{slug}", async (
    string slug,
    CatalogService service,
    HttpContext http,
    CancellationToken ct) =>
{
    var page = await service.GetAsync(slug, ct);

    if (page is null)
        return Results.NotFound();

    http.Response.Headers.CacheControl =
        "public, max-age=60, s-maxage=300, stale-while-revalidate=30";

    return Results.Ok(page);
});
```

Không làm vậy cho personalized response nếu cache key không partition theo authorization/user state.

## 5. Real production scenario

Marketing site dùng Optimizely CMS và Akamai. Homepage có 50,000 requests/minute khi campaign launch.

Với 5-minute edge TTL, phần lớn requests được trả từ edge. Khi content expires, origin shielding giúp nhiều POPs không đồng thời revalidate trực tiếp vào CMS origin.

Nếu editor publish update quan trọng, purge/invalidation policy quyết định user thấy nội dung mới nhanh tới đâu.

## 6. Failure scenario & troubleshooting

**Symptom** → một số regions vẫn thấy banner cũ sau publish hoặc origin spike mỗi khi TTL hết.

**Evidence** → response headers cho thấy `Age`, cache HIT/MISS pattern và simultaneous revalidation waves.

**Hypothesis** → invalidation chưa tới edge hoặc TTL expiry gây synchronized misses.

**Diagnosis** → inspect CDN cache key, purge status, origin request rate và headers từ từng layer.

**Fix** → tune TTL, invalidation, `stale-while-revalidate`, shielding và cache-key policy.

**Verification** → publish test content, đo propagation/freshness SLA và origin request reduction.

## 7. Common mistakes

* Cache authenticated response với `public` mà không hiểu key variation.
* Dùng TTL cực dài rồi kỳ vọng purge luôn hoàn hảo.
* Dùng query string làm cache busting nhưng CDN config ignore query params.
* Không phân biệt browser cache và shared CDN cache.
* Chỉ nhìn backend logs nên không biết response thực tế được phục vụ từ edge.

## 8. Alternatives

Browser cache đủ cho static assets ít traffic nhưng không giảm first-user origin load toàn cầu như CDN.

Application/Redis cache giảm backend computation nhưng request vẫn phải tới origin region.

Không cache là lựa chọn đúng cho dữ liệu security-sensitive hoặc freshness tuyệt đối khi complexity cache không đáng giá.

## 9. Trade-offs

### Advantages

* Giảm latency và origin bandwidth/load.
* Hấp thụ traffic spikes.
* Có thể giữ availability tốt hơn khi origin degraded bằng controlled stale serving.

### Costs / Risks

* Freshness chậm hơn.
* Invalidation và cache-key correctness phức tạp.
* Debug nhiều caching layers khó hơn.
* Sai policy có thể thành security incident.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser, CDN và origin là các cache layers khác nhau.

### Middle

Biết đọc `Cache-Control`, `Age`, HIT/MISS headers và kiểm tra cache behavior.

### Senior

Thiết kế cache key, TTL, stale policy, purge và troubleshoot regional inconsistency.

### Technical Lead / Architect

Quyết định freshness SLA theo content type, boundary nào được cache, failure behavior khi origin down và operational ownership giữa application/CDN teams.

## 11. Key takeaway

* CDN caching là freshness/correctness contract, không chỉ performance switch.
* `stale-while-revalidate` có thể giảm revalidation spikes và latency nhưng phải phù hợp freshness requirement.
* Không cache personalized/private response ở shared edge nếu authorization-aware cache boundary chưa rõ.
