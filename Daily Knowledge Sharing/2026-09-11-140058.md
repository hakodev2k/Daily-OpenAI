# 1. C# `record`, equality semantics và immutable data: dùng value-oriented model đúng boundary thay vì biến mọi DTO thành domain object

## 1. What is it?

`record` trong C# là một type được tối ưu cho mô hình dữ liệu có **value-based equality**. Với class thông thường, hai object khác reference thường không bằng nhau nếu không override equality. Với `record`, compiler sinh equality theo các thành phần dữ liệu.

Mental model:

```text
class  -> identity-oriented object
record -> value-oriented object
```

Điểm quan trọng không phải cú pháp ngắn hơn, mà là semantics. Nếu hai instance có cùng dữ liệu và domain coi chúng là cùng một giá trị, `record` thường tự nhiên hơn. Nếu object có lifecycle, identity riêng và state thay đổi theo thời gian, entity class thường hợp lý hơn.

## 2. Why does it exist?

Trong nhiều hệ thống, developer phải viết lặp lại:

- constructor;
- read-only properties;
- `Equals`;
- `GetHashCode`;
- copy logic;
- deconstruction.

Điều này tạo boilerplate và dễ khiến equality sai. `record` cho phép biểu diễn intent rõ hơn: object này được so sánh theo giá trị.

Nếu không phân biệt identity với value, domain model dễ xuất hiện bug subtle, ví dụ hai `Money` cùng amount/currency bị coi là khác nhau chỉ vì khác reference.

## 3. How does it work?

Ví dụ:

```csharp
public record Money(decimal Amount, string Currency);
```

Hai object:

```csharp
var a = new Money(100, "USD");
var b = new Money(100, "USD");

Console.WriteLine(a == b); // true
```

Compiler tạo equality members phù hợp. `with` expression tạo object mới dựa trên object cũ:

```csharp
var updated = a with { Amount = 120 };
```

Tuy nhiên `record` không tự động làm toàn bộ object graph immutable. Nếu property bên trong là mutable collection, collection vẫn có thể bị thay đổi.

## 4. Practical implementation

Một Value Object cho địa chỉ email:

```csharp
public sealed record EmailAddress
{
    public string Value { get; }

    private EmailAddress(string value)
    {
        Value = value;
    }

    public static EmailAddress Create(string value)
    {
        if (string.IsNullOrWhiteSpace(value))
            throw new ArgumentException("Email is required.");

        var normalized = value.Trim().ToLowerInvariant();

        if (!normalized.Contains('@'))
            throw new ArgumentException("Invalid email format.");

        return new EmailAddress(normalized);
    }
}
```

Domain code dùng:

```csharp
customer.ChangeEmail(EmailAddress.Create(request.Email));
```

Thay vì truyền `string` xuyên toàn hệ thống, type này mang invariant và normalization rule.

## 5. Real production scenario

Một CRM dùng `string` cho email ở hàng chục service. Chỗ trim, chỗ không trim; chỗ lowercase, chỗ giữ nguyên; chỗ validate regex, chỗ không validate. Kết quả là duplicate customer và lookup không ổn định.

Khi đóng gói email thành Value Object, application có một nơi duy nhất định nghĩa normalization và equality. Nhưng DTO public vẫn có thể dùng `string`; mapping vào domain xảy ra tại application boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → dictionary/set chứa duplicate object tưởng như giống nhau hoặc equality thay đổi bất ngờ.

**Evidence** → record chứa `List<T>` mutable hoặc equality dựa trên reference của collection.

**Hypothesis** → developer giả định “record = deep immutable/value equality”.

**Diagnosis** → kiểm tra các member tham gia equality và mutable nested state.

**Fix** → dùng immutable collection, giới hạn component tham gia equality hoặc tự định nghĩa Value Object rõ ràng.

**Verification** → unit test equality, hash code và behavior trong `HashSet<T>` / dictionary.

## 7. Common mistakes

- Dùng `record` cho entity có identity riêng như `Order` chỉ vì syntax ngắn.
- Nghĩ `init` hoặc `record` đảm bảo deep immutability.
- Đưa mutable collection vào record rồi dùng làm dictionary key.
- Dùng raw primitive khắp domain dù invariant lặp lại.
- Biến mọi DTO thành Value Object dù chúng chỉ là transport model.

## 8. Alternatives

Class thông thường phù hợp cho entity/lifecycle object. `readonly record struct` phù hợp cho value nhỏ, ngắn sống và cần tránh heap allocation, nhưng phải cân nhắc copying cost. Struct thường chỉ nên dùng khi semantics thực sự phù hợp.

## 9. Trade-offs

### Advantages

- Intent value-oriented rõ.
- Equality và copy syntax tiện.
- Hữu ích cho immutable message, DTO và Value Object.

### Costs / Risks

- Dễ dùng sai cho entity.
- Không có deep immutability mặc định.
- Equality trên object graph lớn có thể tốn chi phí.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác nhau giữa object identity và value equality.

### Middle

Biết chọn `record`, class hoặc struct theo semantics, và test equality behavior.

### Senior

Nhìn ra boundary nào nên dùng Value Object, tránh primitive obsession và hiểu mutation/equality pitfalls.

### Technical Lead / Architect

Quyết định domain model cần value semantics ở đâu, mapping boundary giữa transport/persistence/domain ra sao và tránh biến syntax feature thành architectural rule.

## 11. Key takeaway

- `record` là lựa chọn về semantics, không chỉ syntax.
- Value equality phù hợp cho Value Object và immutable messages hơn entity có identity.
- `record` không đồng nghĩa với deep immutable.

# 2. ASP.NET Core API versioning + backward compatibility: thay đổi contract mà không ép toàn bộ client nâng cấp cùng lúc

## 1. What is it?

API versioning là cách quản lý nhiều contract khác nhau của cùng capability khi client không thể đồng loạt nâng cấp. Mục tiêu thực tế là kiểm soát **breaking changes**, không phải thêm `v1`, `v2` vào URL cho đẹp.

Backward compatibility nghĩa là client đang dùng contract cũ tiếp tục hoạt động khi server được deploy version mới.

## 2. Why does it exist?

API enterprise thường có mobile app, web app, partner integration và batch jobs với release cycle khác nhau. Nếu server đổi field bắt buộc, enum semantics hoặc response shape ngay lập tức, client cũ có thể hỏng dù server deploy thành công.

Không có strategy versioning, team buộc phải phối hợp release đồng thời giữa nhiều hệ thống — điều gần như không bền vững khi quy mô tăng.

## 3. How does it work?

Một contract có thể được version bằng:

```text
URL:        /api/v2/orders
Header:     Api-Version: 2.0
Query:      ?api-version=2.0
Media type: application/vnd.company.orders-v2+json
```

Versioning chỉ là routing surface. Phần khó hơn là policy:

```text
introduce new contract
-> hỗ trợ song song
-> telemetry usage version cũ
-> announce deprecation
-> migrate clients
-> retire version cũ
```

## 4. Practical implementation

Ví dụ route version đơn giản:

```csharp
app.MapGet("/api/v1/orders/{id:guid}", async (
    Guid id,
    AppDbContext db,
    CancellationToken ct) =>
{
    var order = await db.Orders.FindAsync([id], ct);
    return order is null
        ? Results.NotFound()
        : Results.Ok(new
        {
            order.Id,
            order.Total
        });
});

app.MapGet("/api/v2/orders/{id:guid}", async (
    Guid id,
    AppDbContext db,
    CancellationToken ct) =>
{
    var order = await db.Orders.FindAsync([id], ct);
    return order is null
        ? Results.NotFound()
        : Results.Ok(new
        {
            order.Id,
            total = new
            {
                amount = order.Total,
                currency = order.Currency
            }
        });
});
```

Version 2 thay đổi `Total` primitive thành object có currency — một breaking contract change hợp lý để version.

## 5. Real production scenario

Mobile app v1 dùng response:

```json
{ "total": 100 }
```

Backend muốn hỗ trợ multi-currency và đổi thành:

```json
{
  "total": {
    "amount": 100,
    "currency": "USD"
  }
}
```

Nếu overwrite contract cũ, user chưa update mobile app bị lỗi deserialize. Server cần hỗ trợ v1 đủ lâu hoặc giữ field cũ trong transitional period.

## 6. Failure scenario & troubleshooting

**Symptom** → sau release backend, một nhóm client tăng 4xx/5xx hoặc deserialize error.

**Evidence** → telemetry cho thấy lỗi tập trung ở app version cũ / API version cũ.

**Hypothesis** → breaking contract change không được version hoặc compatibility assumption sai.

**Diagnosis** → diff OpenAPI schema, kiểm tra request/response payload của client cũ và contract tests.

**Fix** → restore contract cũ, introduce version mới hoặc thêm compatibility adapter.

**Verification** → replay contract tests cho cả current và previous supported versions.

## 7. Common mistakes

- Version mọi thay đổi, kể cả additive optional field.
- Nghĩ URL `/v2` tự giải quyết migration.
- Xóa version cũ mà không có usage telemetry.
- Reuse cùng DTO class cho nhiều version rồi thay đổi một version làm hỏng version khác.
- Thay enum semantics mà coi là non-breaking vì JSON shape không đổi.

## 8. Alternatives

Nếu change additive và optional, thường không cần version mới. GraphQL hoặc tolerant-reader contract có thể giảm một số breaking changes nhưng không loại bỏ evolution problem. Event/message contracts cũng cần versioning riêng.

## 9. Trade-offs

### Advantages

- Client release độc lập hơn.
- Rollout migration có kiểm soát.
- Giảm blast radius của breaking change.

### Costs / Risks

- Nhiều code path phải maintain.
- Test matrix tăng.
- Có nguy cơ version cũ tồn tại quá lâu và trở thành technical debt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết additive change và breaking change khác nhau.

### Middle

Implement route/version contract, OpenAPI và regression tests cho version cũ.

### Senior

Thiết kế deprecation policy, compatibility adapter và telemetry usage.

### Technical Lead / Architect

Quyết định versioning strategy toàn platform, support window, ownership migration và tiêu chí retire contract cũ.

## 11. Key takeaway

- API versioning là bài toán contract lifecycle, không chỉ routing.
- Không phải mọi thay đổi đều cần version mới.
- Usage telemetry và deprecation policy quan trọng ngang implementation.

# 3. EF Core Change Tracker + identity map: hiểu vì sao cùng một entity key chỉ nên có một tracked instance trong một `DbContext`

## 1. What is it?

EF Core Change Tracker theo dõi entity instance và trạng thái của chúng như `Unchanged`, `Modified`, `Added`, `Deleted`. Identity map là hành vi đảm bảo trong một `DbContext`, một database identity thường tương ứng với một tracked object instance.

Mental model:

```text
DbContext
  -> Entity key 42
      -> tracked instance A
```

Nếu cố attach instance B cũng có key 42, EF Core không thể biết instance nào là source of truth.

## 2. Why does it exist?

ORM cần biết object nào đã thay đổi để tạo SQL `UPDATE`, đồng thời duy trì relationship fix-up và consistency trong unit of work.

Nếu cùng một row được đại diện bởi nhiều tracked object với state khác nhau, SaveChanges có thể trở nên mơ hồ hoặc tạo overwrite không dự đoán được.

## 3. How does it work?

Khi query tracking:

```csharp
var order = await db.Orders.SingleAsync(x => x.Id == id, ct);
```

EF Core lưu metadata:

```text
Order Id=42
OriginalValues
CurrentValues
State=Unchanged
```

Sau:

```csharp
order.Status = OrderStatus.Approved;
```

Change detection xác định property thay đổi và phát SQL update phù hợp.

Nếu query lại cùng key trong cùng context, EF có thể trả tracked instance hiện có thay vì tạo một identity cạnh tranh.

## 4. Practical implementation

Một anti-pattern phổ biến:

```csharp
var existing = await db.Orders.FindAsync([request.Id], ct);

var mapped = new Order
{
    Id = request.Id,
    Status = request.Status
};

db.Update(mapped); // có thể conflict với existing đã tracked
```

Tốt hơn:

```csharp
var order = await db.Orders.SingleAsync(
    x => x.Id == request.Id,
    ct);

order.ChangeStatus(request.Status);

await db.SaveChangesAsync(ct);
```

Hoặc với disconnected update, attach duy nhất một instance và set rõ property cần modified.

## 5. Real production scenario

Một API dùng AutoMapper tạo entity mới từ request DTO, trong khi repository đã load entity cũ để validate. Cả hai cùng key được đưa vào `DbContext`. Production bắt đầu ném:

```text
The instance of entity type 'Order' cannot be tracked because another instance with the same key value is already being tracked.
```

Root cause không phải EF “khó tính”, mà là unit of work đang có hai object cạnh tranh cùng identity.

## 6. Failure scenario & troubleshooting

**Symptom** → tracking exception hoặc SaveChanges ghi đè field không mong muốn.

**Evidence** → `ChangeTracker.Entries()` cho thấy entity state bất thường; mapping layer tạo entity mới.

**Hypothesis** → duplicate tracked instance hoặc blanket `Update()`.

**Diagnosis** → inspect tracked entries theo key, theo dõi lifecycle `DbContext` và mapping flow.

**Fix** → load-and-mutate tracked entity hoặc attach một instance duy nhất với explicit modified properties.

**Verification** → integration test kiểm tra generated SQL chỉ update field dự kiến.

## 7. Common mistakes

- Giữ `DbContext` quá lâu như Singleton.
- Map DTO thành entity mới rồi gọi `Update()` sau khi entity cũ đã tracked.
- Dùng `Update()` cho partial PATCH và vô tình mark mọi property modified.
- Nhầm `AsNoTracking()` với “không cần quan tâm identity”.
- Dùng tracking query cho read-only list lớn, tăng memory không cần thiết.

## 8. Alternatives

`AsNoTracking()` phù hợp read-only query. `AsNoTrackingWithIdentityResolution()` hữu ích khi muốn không tracking nhưng vẫn tránh duplicate object instance trong materialized graph. Raw SQL/Dapper phù hợp khi không cần unit-of-work/change tracking behavior.

## 9. Trade-offs

### Advantages

- Unit of work rõ.
- Relationship fix-up thuận tiện.
- EF tự tạo update dựa trên state.

### Costs / Risks

- Tracking tốn memory.
- Long-lived context dễ stale state.
- Disconnected web update cần discipline rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbContext` không chỉ là database connection; nó giữ state của entity.

### Middle

Biết chọn tracking/no-tracking và xử lý update không tạo duplicate instance.

### Senior

Debug `ChangeTracker`, disconnected graph, partial update và generated SQL.

### Technical Lead / Architect

Quyết định transaction/unit-of-work boundary, nơi mapping DTO vào domain entity và khi nào EF tracking phù hợp hoặc quá nặng.

## 11. Key takeaway

- Một `DbContext` nên có một tracked instance cho mỗi entity identity.
- Load-and-mutate thường an toàn hơn map-to-new-entity rồi `Update()`.
- Tracking là capability có cost; read-only path nên cân nhắc no-tracking.

# 4. SQL window functions: giải quyết ranking, running total và latest-per-group mà không tự tạo N+1 query hoặc correlated subquery đắt đỏ

## 1. What is it?

Window function tính toán trên một “cửa sổ” rows liên quan mà không collapse chúng thành một row như `GROUP BY`.

Ví dụ phổ biến:

- `ROW_NUMBER()`;
- `RANK()`;
- `LAG()` / `LEAD()`;
- `SUM(...) OVER (...)`.

Mental model:

```text
GROUP BY      -> nhiều rows thành ít rows
window        -> giữ từng row, thêm context từ nhóm
```

## 2. Why does it exist?

Nhiều bài toán như “đơn hàng mới nhất của mỗi customer” hoặc “running total theo tháng” thường bị implement bằng loop ứng dụng, N+1 query hoặc self join phức tạp.

Window function cho phép database xử lý set-based, tận dụng optimizer và giảm round trip.

## 3. How does it work?

Lấy order mới nhất của mỗi customer:

```sql
WITH RankedOrders AS
(
    SELECT
        Id,
        CustomerId,
        CreatedAt,
        Total,
        ROW_NUMBER() OVER (
            PARTITION BY CustomerId
            ORDER BY CreatedAt DESC, Id DESC
        ) AS rn
    FROM Orders
)
SELECT Id, CustomerId, CreatedAt, Total
FROM RankedOrders
WHERE rn = 1;
```

`PARTITION BY` tạo nhóm logic; `ORDER BY` xác định thứ tự bên trong từng nhóm.

## 4. Practical implementation

Running total:

```sql
SELECT
    AccountId,
    TransactionDate,
    Amount,
    SUM(Amount) OVER (
        PARTITION BY AccountId
        ORDER BY TransactionDate, Id
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS RunningBalance
FROM Transactions;
```

Khi dùng qua EF Core, nếu LINQ translation không hỗ trợ cleanly cho case cụ thể, raw SQL projection có thể tốt hơn việc kéo toàn bộ rows về memory.

## 5. Real production scenario

Dashboard cần hiển thị trạng thái approval mới nhất cho 50.000 employees. Implementation ban đầu query employee list rồi mỗi employee query một approval mới nhất — hàng chục nghìn round trips.

Một query với `ROW_NUMBER()` giải quyết toàn bộ set và giảm latency từ nhiều giây xuống mức database có thể xử lý ổn định.

## 6. Failure scenario & troubleshooting

**Symptom** → query dùng window function vẫn chậm và tempdb/sort cost cao.

**Evidence** → execution plan có large sort, spill hoặc scan lớn.

**Hypothesis** → index không hỗ trợ partition/order hoặc dataset filter quá rộng.

**Diagnosis** → xem actual execution plan, memory grant, sort spill, logical reads.

**Fix** → filter sớm, thiết kế index theo access pattern, giảm selected columns hoặc materialize intermediate result khi justified.

**Verification** → so actual reads, elapsed time và spill warnings trước/sau.

## 7. Common mistakes

- Dùng window function nhưng không có deterministic tiebreaker.
- Nhầm `RANK()` với `ROW_NUMBER()` khi có ties.
- Kéo data về C# rồi group/sort cho bài toán database làm tốt hơn.
- Chọn quá nhiều columns làm sort rộng.
- Thấy query chậm rồi “thêm index” mà không đọc plan.

## 8. Alternatives

`GROUP BY` phù hợp khi chỉ cần aggregate một row mỗi group. `CROSS APPLY TOP (1)` có thể rất hiệu quả cho latest-per-group nếu index phù hợp. Precomputed aggregate/materialized view phù hợp dashboard rất nặng và freshness requirement cho phép.

## 9. Trade-offs

### Advantages

- Set-based.
- Giảm round trip.
- Diễn đạt ranking/sequence rõ.

### Costs / Risks

- Sort có thể đắt.
- Execution plan khó đọc hơn query đơn giản.
- Không phải ORM nào translate mọi window function tốt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `PARTITION BY` và `ORDER BY` trong window khác `GROUP BY`.

### Middle

Viết `ROW_NUMBER`, `LAG`, running total cho use case thực tế.

### Senior

Đọc sort/spill/index behavior và so sánh với `APPLY`, aggregate hoặc precomputation.

### Technical Lead / Architect

Quyết định computation nên xảy ra tại transactional DB, read model hay analytics layer dựa trên load và freshness.

## 11. Key takeaway

- Window function giải nhiều bài toán sequence/ranking mà không mất row-level detail.
- Set-based query thường tốt hơn N+1 application loop.
- Performance vẫn phải kiểm chứng bằng execution plan và I/O.

# 5. Cosmos DB consistency levels: chọn Strong, Session hay Eventual dựa trên business semantics thay vì mặc định “càng mạnh càng tốt”

## 1. What is it?

Consistency level xác định mức đảm bảo client nhận dữ liệu mới đến đâu khi dữ liệu được replicate phân tán.

Trong Cosmos DB, các mức quan trọng gồm:

- Strong;
- Bounded Staleness;
- Session;
- Consistent Prefix;
- Eventual.

Mental model: consistency mạnh hơn thường đổi lại bằng latency, availability hoặc throughput/cost behavior.

## 2. Why does it exist?

Trong distributed storage, replicas không thể luôn cập nhật cùng thời điểm mà không trả giá coordination. Một hệ thống shopping cart có thể chỉ cần user đọc thấy chính write của mình, trong khi ledger tài chính có requirement mạnh hơn.

Một policy duy nhất cho mọi workload thường lãng phí hoặc không đủ đúng.

## 3. How does it work?

Với Session consistency:

```text
Client session
  -> write document version 42
  -> nhận session token
  -> subsequent read với token
  -> đảm bảo không quay về version cũ hơn trong session đó
```

Điều này phù hợp nhiều web applications: user thấy write của chính mình mà không cần global Strong consistency cho mọi reader.

Eventual consistency cho phép replica trả dữ liệu cũ tạm thời nhưng convergence về sau.

## 4. Practical implementation

Với Azure Cosmos DB SDK, consistency có thể đặt ở client/account level. Ví dụ:

```csharp
var client = new CosmosClient(
    connectionString,
    new CosmosClientOptions
    {
        ConsistencyLevel = ConsistencyLevel.Session
    });
```

Application vẫn phải thiết kế business semantics: nếu write một order rồi immediately redirect sang read endpoint qua session khác, session token propagation có thể ảnh hưởng read-your-own-write expectation.

## 5. Real production scenario

Một global product catalog có replicas nhiều region. Giá/description update không cần mọi user toàn cầu thấy trong cùng millisecond; eventual/session có thể chấp nhận. Nhưng checkout validation không nên dựa mù quáng vào stale catalog cache cho inventory-critical decision.

Kiến trúc có thể dùng Cosmos cho read model nhưng giữ authoritative inventory check tại service có consistency mạnh hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → user update profile xong refresh và thấy dữ liệu cũ.

**Evidence** → read đi qua session khác hoặc request không giữ session token; multi-region read trả replica chưa catch up.

**Hypothesis** → consistency expectation không khớp cấu hình/runtime session behavior.

**Diagnosis** → log region, session token, write/read timeline và consistency config.

**Fix** → Session consistency đúng boundary, token propagation hoặc route read-after-write qua authoritative path.

**Verification** → integration test multi-request read-after-write và chaos/failover scenario.

## 7. Common mistakes

- Chọn Strong cho mọi thứ vì nghe “an toàn hơn”.
- Chọn Eventual nhưng UI/business lại assume immediate visibility.
- Không phân biệt consistency của database với cache/search read model.
- Không log region/session context khi debug stale read.
- Dùng stale read cho decision có hậu quả tài chính/inventory mà không revalidate.

## 8. Alternatives

SQL database single-region có thể cho transaction semantics đơn giản hơn. Redis/search index thường có consistency yếu hơn và nên được xem là read optimization. Nếu business requirement cần strongly consistent cross-entity transaction, Cosmos có thể không phải lựa chọn đơn giản nhất.

## 9. Trade-offs

### Advantages

Consistency tunable cho phép cân bằng latency, scale và correctness theo workload.

### Costs / Risks

Semantics phức tạp hơn developer intuition. Multi-region behavior và failover cần test thực tế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu “replicated” không có nghĩa mọi replica cập nhật đồng thời.

### Middle

Biết Session/Eventual khác nhau và test read-after-write.

### Senior

Map consistency requirement vào business operation, region topology và failure mode.

### Technical Lead / Architect

Quyết định source of truth, consistency SLA từng bounded context và nơi nào phải revalidate trước action quan trọng.

## 11. Key takeaway

- Consistency là business requirement được ánh xạ vào storage behavior.
- Strong không miễn phí và không phải default tốt cho mọi workload.
- Session consistency thường là điểm cân bằng tốt cho nhiều user-centric flows.

# 6. DDD Value Object: đóng gói invariant và equality theo giá trị mà không biến domain model thành lớp dữ liệu thụ động

## 1. What is it?

Value Object trong DDD là object không có identity độc lập; nó được định nghĩa bởi giá trị và invariant.

Ví dụ:

- Money;
- DateRange;
- EmailAddress;
- Address;
- Percentage.

Hai Value Object có cùng giá trị được coi là tương đương về domain meaning.

## 2. Why does it exist?

Primitive như `decimal`, `string`, `DateTime` không diễn đạt business rule. Một `decimal` có thể là tiền, phần trăm, khối lượng hoặc số lượng.

Nếu invariant nằm rải rác trong controller/service, hệ thống dần xuất hiện invalid states. Value Object đưa rule vào ngay type đại diện cho khái niệm.

## 3. How does it work?

Ví dụ `DateRange`:

```csharp
public sealed record DateRange
{
    public DateOnly Start { get; }
    public DateOnly End { get; }

    private DateRange(DateOnly start, DateOnly end)
    {
        Start = start;
        End = end;
    }

    public static DateRange Create(DateOnly start, DateOnly end)
    {
        if (end < start)
            throw new ArgumentException("End must be on or after Start.");

        return new DateRange(start, end);
    }
}
```

Object không cần `Id`. Equality dựa trên `Start` và `End`.

## 4. Practical implementation

Domain entity:

```csharp
public sealed class LeaveRequest
{
    public Guid Id { get; private set; }
    public DateRange Period { get; private set; }

    public LeaveRequest(Guid id, DateRange period)
    {
        Id = id;
        Period = period;
    }

    public void Reschedule(DateRange newPeriod)
    {
        Period = newPeriod;
    }
}
```

EF Core có thể map Value Object bằng owned/complex type tùy version/modeling approach.

## 5. Real production scenario

Timesheet system truyền `startDate` và `endDate` riêng qua nhiều method. Một code path quên validate `endDate >= startDate`, tạo request âm ngày. Sau đó reporting và approval logic phải defensive everywhere.

Khi `DateRange` chỉ có thể được tạo qua factory hợp lệ, invalid state bị chặn sớm.

## 6. Failure scenario & troubleshooting

**Symptom** → domain object vẫn có invalid combinations dù đã có Value Object.

**Evidence** → ORM/deserializer có thể bypass constructor/factory hoặc setters public.

**Hypothesis** → invariant boundary bị phá bởi persistence/serialization design.

**Diagnosis** → kiểm tra constructors, materialization behavior và mutation paths.

**Fix** → encapsulation tốt hơn, integration tests persistence round-trip và validation tại external boundary.

**Verification** → không thể tạo invalid object qua public API và persisted state round-trip giữ invariant.

## 7. Common mistakes

- Cho Value Object một `Id` vô nghĩa.
- Dùng Value Object cho mọi primitive, tạo ceremony lớn.
- Để property mutable public làm equality/hash behavior không ổn định.
- Nhầm Value Object với DTO.
- Đặt business process orchestration vào Value Object.

## 8. Alternatives

Primitive + validation service đủ cho domain đơn giản. Strongly typed ID có thể dùng cho identity semantics nhưng không phải Value Object business concept đầy đủ. Entity phù hợp khi object có lifecycle/identity riêng.

## 9. Trade-offs

### Advantages

- Invariant tập trung.
- Domain language rõ.
- Giảm primitive obsession.

### Costs / Risks

- Mapping/persistence phức tạp hơn.
- Overuse tạo nhiều tiny types khó đọc.
- Team cần thống nhất semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt Entity có identity với Value Object theo giá trị.

### Middle

Tạo Value Object immutable và enforce invariant.

### Senior

Chọn boundary phù hợp, tránh over-modeling và xử lý persistence mapping.

### Technical Lead / Architect

Quyết định domain complexity có đủ để justify rich model hay layered CRUD đơn giản hiệu quả hơn.

## 11. Key takeaway

- Value Object dùng để diễn đạt domain meaning và invariant, không phải để tăng số class.
- Không có identity độc lập; equality theo giá trị.
- Chỉ tạo khi khái niệm thực sự có business rule hoặc meaning riêng.

# 7. Azure App Service autoscale: scale compute nhưng không vô tình nhân áp lực lên SQL, Redis hoặc third-party API

## 1. What is it?

Autoscale tăng/giảm số App Service instances theo metric hoặc schedule. Nó giải quyết capacity của web compute layer, nhưng không tự động scale mọi dependency phía sau.

Mental model:

```text
10 App instances
   -> 10x potential concurrency
   -> SQL / Redis / external API vẫn có giới hạn riêng
```

Scale-out có thể cải thiện throughput hoặc làm outage downstream nhanh hơn nếu concurrency không được kiểm soát.

## 2. Why does it exist?

Traffic thay đổi theo giờ hoặc campaign. Provision peak capacity 24/7 lãng phí; provision average capacity gây overload giờ cao điểm. Autoscale giúp capacity theo nhu cầu.

Nhưng CPU-based autoscale chỉ quan sát một layer. Hệ thống distributed cần capacity planning end-to-end.

## 3. How does it work?

Một rule đơn giản:

```text
CPU > 70% trong 10 phút
-> add instance

CPU < 30% trong 20 phút
-> remove instance
```

Ngoài CPU có thể scale theo queue length hoặc custom metrics. Scale-out tạo process mới, cold start, connection pools mới và background services mới.

## 4. Practical implementation

Application phải giới hạn downstream concurrency. Ví dụ dùng `SemaphoreSlim` cho một third-party API có quota thấp:

```csharp
private readonly SemaphoreSlim _gate = new(20);

public async Task<T> CallPartnerAsync<T>(
    Func<Task<T>> action,
    CancellationToken ct)
{
    await _gate.WaitAsync(ct);
    try
    {
        return await action();
    }
    finally
    {
        _gate.Release();
    }
}
```

Lưu ý limiter per-instance vẫn nhân theo số instances. Nếu quota global, cần architecture khác hoặc phân bổ limit phù hợp.

## 5. Real production scenario

Marketing campaign tăng traffic 5 lần. Autoscale web từ 4 lên 16 instances. Mỗi instance mở SQL connection pool tối đa 100 connections. Database đột ngột chịu khả năng 1600 connections, vượt capacity, latency tăng rồi web tiếp tục scale vì request chậm.

Một feedback loop xấu xuất hiện: scale web → overload DB → request chậm → metric xấu → scale thêm.

## 6. Failure scenario & troubleshooting

**Symptom** → instance count tăng nhưng throughput không tăng; SQL timeout tăng.

**Evidence** → database connections/CPU/IO saturate trong khi web CPU giảm.

**Hypothesis** → bottleneck chuyển sang dependency.

**Diagnosis** → correlate App Service instance count, request rate, SQL metrics, connection pool và dependency p95.

**Fix** → cap scale, optimize access pattern, bounded concurrency, cache hợp lý hoặc scale database nếu justified.

**Verification** → load test theo full architecture, không chỉ web tier.

## 7. Common mistakes

- Chỉ autoscale theo CPU.
- Không tính connection pool nhân theo replicas.
- Background job chạy trên mỗi instance sau scale-out.
- Scale-in quá nhanh làm request/background work bị gián đoạn.
- Dùng autoscale để che memory leak hoặc slow query.

## 8. Alternatives

Queue-based architecture phù hợp workload bursty vì consumer concurrency dễ điều tiết hơn. Azure Functions/Container Apps có model scaling khác nhưng vẫn phải bảo vệ downstream. Fixed capacity có thể tốt hơn workload ổn định và latency-sensitive.

## 9. Trade-offs

### Advantages

- Elastic capacity.
- Giảm chi phí ngoài peak.
- Tăng resilience trước traffic burst nếu dependency đủ sức.

### Costs / Risks

- Cold start/warm-up.
- Downstream pressure tăng.
- Capacity/debugging phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu scale-out = thêm process instances, không phải “server mạnh hơn”.

### Middle

Cấu hình rule, health check và quan sát instance metrics.

### Senior

Phân tích bottleneck end-to-end, pool multiplication, warm-up và bounded concurrency.

### Technical Lead / Architect

Đặt scaling policy dựa trên system capacity, cost, dependency limits và business SLO chứ không theo một metric đơn lẻ.

## 11. Key takeaway

- Autoscale web tier không tự scale dependency.
- Replica count nhân concurrency, connection pools và background execution.
- Scale policy phải dựa trên bottleneck thật của toàn hệ thống.

# 8. Canary deployment + feature flags: tách rủi ro deployment khỏi rủi ro feature rollout để rollback có kiểm soát

## 1. What is it?

Canary deployment gửi một phần nhỏ traffic tới version mới trước khi mở rộng rollout. Feature flag cho phép bật/tắt behavior runtime độc lập với việc deploy binary.

Hai kỹ thuật giải quyết hai loại rủi ro khác nhau:

```text
Canary      -> binary/runtime/infrastructure risk
Feature flag -> product/business behavior risk
```

Kết hợp đúng giúp giảm blast radius.

## 2. Why does it exist?

Test staging không tái hiện hoàn toàn Production data, traffic và dependency behavior. Deploy 100% có thể biến bug nhỏ thành incident toàn hệ thống.

Feature cũng có thể đúng về kỹ thuật nhưng sai business behavior. Có khả năng tắt feature mà không rollback toàn application là một control hữu ích.

## 3. How does it work?

Canary flow:

```text
Deploy v2
-> 5% traffic
-> observe error/latency/business metrics
-> 25%
-> 50%
-> 100%
```

Feature flag flow:

```text
code exists in v2
-> flag off
-> enable internal users
-> 5% users
-> wider audience
```

Database change vẫn phải backward-compatible vì v1 và v2 có thể cùng chạy.

## 4. Practical implementation

Một abstraction đơn giản:

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
{
    return await newCheckout.ExecuteAsync(request, ct);
}

return await legacyCheckout.ExecuteAsync(request, ct);
```

Flag evaluation cần deterministic enough cho user/session nếu flow nhiều bước. Không nên để user bước 1 vào old flow và bước 2 bất ngờ sang new flow nếu state incompatible.

## 5. Real production scenario

Checkout v2 deploy thành công, health check xanh. Khi 5% traffic thật đi qua, p99 tăng mạnh vì một SQL query chỉ chậm với large carts. Canary metric phát hiện trước khi rollout toàn bộ.

Sau khi fix performance, feature flag vẫn cho phép rollout business behavior dần theo customer cohort.

## 6. Failure scenario & troubleshooting

**Symptom** → metrics toàn platform tốt nhưng canary user lỗi cao.

**Evidence** → dimensions theo deployment version cho thấy v2 error rate cao.

**Hypothesis** → regression chỉ trong new version.

**Diagnosis** → compare traces v1/v2, config, SQL plans và dependency calls.

**Fix** → stop rollout/route traffic về v1; nếu code ổn nhưng feature lỗi, disable flag.

**Verification** → canary metrics trở lại baseline trước tăng rollout.

## 7. Common mistakes

- Không tag telemetry theo version/flag cohort.
- Canary 5% nhưng traffic low đến mức không đủ signal.
- Feature flag tồn tại vĩnh viễn, code path cũ không bao giờ xóa.
- Database migration phá backward compatibility giữa v1/v2.
- Dùng flag cho security authorization thay vì policy deterministic.

## 8. Alternatives

Blue-Green deployment phù hợp cutover nhanh giữa hai môi trường. Rolling deployment đơn giản hơn nhưng ít kiểm soát cohort. Deployment slot trên App Service hữu ích cho warm-up/swap nhưng không thay thế business feature rollout.

## 9. Trade-offs

### Advantages

- Giảm blast radius.
- Rollback nhanh.
- Tách release kỹ thuật khỏi rollout business.

### Costs / Risks

- Telemetry và routing phức tạp hơn.
- Nhiều code path tạm thời.
- Flag debt nếu không cleanup.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy code và enable feature là hai hành động có thể tách nhau.

### Middle

Implement flag, version telemetry và rollback path.

### Senior

Thiết kế cohort stability, backward-compatible schema và rollout guardrails.

### Technical Lead / Architect

Định nghĩa release policy: metric nào block rollout, ai có quyền flip flag, cleanup deadline và strategy cho high-risk changes.

## 11. Key takeaway

- Canary giảm risk của version mới; feature flag giảm risk của behavior mới.
- Không có telemetry theo cohort thì canary mất nhiều giá trị.
- Database compatibility là điều kiện bắt buộc khi nhiều version chạy song song.

# 9. p50 / p95 / p99 latency: dùng percentile để nhìn tail latency và user impact thay vì bị average che khuất

## 1. What is it?

Percentile latency trả lời “bao nhiêu phần trăm request nhanh hơn ngưỡng này”.

Ví dụ:

```text
p50 = 120 ms
p95 = 800 ms
p99 = 4.5 s
```

50% request dưới 120 ms, 95% dưới 800 ms và 1% chậm hơn 4.5 giây.

Average có thể vẫn 200 ms và che toàn bộ tail latency.

## 2. Why does it exist?

User experience thường bị quyết định bởi request chậm, không phải request trung bình. Trong distributed request gọi nhiều dependency, tail latency dễ cộng dồn.

Nếu chỉ alert average, một minority requests có thể timeout nghiêm trọng mà dashboard vẫn “xanh”.

## 3. How does it work?

Với 10.000 request, sort latency và lấy vị trí tương ứng percentile. Monitoring system thường dùng histogram/sketch để aggregate hiệu quả thay vì giữ từng sample.

Quan hệ nên hiểu:

```text
p50 -> experience phổ biến
p95 -> tail đáng kể
p99 -> rare-but-impactful tail
```

Không có percentile nào “tốt nhất”; chọn dựa trên SLO và traffic volume.

## 4. Practical implementation

Trong OpenTelemetry, nên record request duration thành histogram thay vì log từng latency như text.

Ví dụ custom metric concept:

```csharp
private static readonly Histogram<double> Duration =
    Meter.CreateHistogram<double>("order.processing.duration", "ms");

var sw = Stopwatch.StartNew();
try
{
    await ProcessAsync(ct);
}
finally
{
    Duration.Record(sw.Elapsed.TotalMilliseconds);
}
```

Backend metrics tính percentile từ distribution.

## 5. Real production scenario

API có average 180 ms, team kết luận healthy. Nhưng customer lớn có query pattern khiến 2% request mất 8 giây. Vì traffic cao, 2% tương đương hàng nghìn request mỗi giờ.

p99 và trace dimension theo tenant/query type cho thấy tail tập trung ở một SQL path.

## 6. Failure scenario & troubleshooting

**Symptom** → user report timeout nhưng average latency gần như không đổi.

**Evidence** → p99 tăng từ 1 s lên 10 s; p50 giữ 150 ms.

**Hypothesis** → một subset workload/dependency path bị chậm.

**Diagnosis** → slice metric theo endpoint, tenant, dependency, version; inspect traces của slow percentile.

**Fix** → xử lý bottleneck cụ thể thay vì optimize toàn hệ thống.

**Verification** → p95/p99 quay về baseline và error/timeout rate giảm.

## 7. Common mistakes

- Chỉ dùng average.
- Nhìn p99 của sample quá nhỏ và kết luận quá mạnh.
- Aggregate percentile từ percentile của nhiều node một cách sai toán học.
- Không phân tách cold start, endpoint hoặc tenant dimensions.
- Tối ưu p50 trong khi SLO fail ở p95.

## 8. Alternatives

Apdex có thể tóm tắt satisfaction nhưng mất chi tiết distribution. Histograms đầy đủ hữu ích hơn khi cần phân tích. Max latency thường quá noisy để làm metric chính.

## 9. Trade-offs

### Advantages

- Thể hiện tail behavior.
- Gắn tốt với SLO.
- Giúp ưu tiên user impact thật.

### Costs / Risks

- Cần hiểu sample size và aggregation.
- High-cardinality dimensions có cost.
- Percentile một mình vẫn không chỉ ra root cause.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu p95 không phải “95% chậm”, mà 95% nhanh hơn hoặc bằng ngưỡng đó.

### Middle

Biết đọc p50/p95/p99 và correlate với endpoint/dependency.

### Senior

Hiểu histogram aggregation, sampling, tail amplification và SLO interpretation.

### Technical Lead / Architect

Chọn SLI/SLO percentile phù hợp business, traffic và cost quan sát; tránh dashboard vanity metrics.

## 11. Key takeaway

- Average có thể che tail latency nghiêm trọng.
- p95/p99 cần được đọc cùng traffic volume và dimensions.
- Percentile cho biết “có vấn đề ở đâu trong distribution”, không tự nói root cause.

# 10. Linux `systemd` + graceful shutdown cho .NET Worker: hiểu process lifecycle, signal và restart policy khi chạy ngoài container

## 1. What is it?

`systemd` là service manager phổ biến trên Linux. Nó quản lý process lifecycle: start, stop, restart, dependency và log integration.

Với .NET Worker, graceful shutdown nghĩa là khi service nhận tín hiệu stop như `SIGTERM`, host truyền cancellation để background loop kết thúc có kiểm soát trước khi process bị kill.

## 2. Why does it exist?

Chạy `dotnet Worker.dll` trong SSH session không phải production service management. Process có thể chết khi session đóng, không tự restart, không có startup order và khó quản lý log.

`systemd` cung cấp operational contract rõ cho OS-level service.

## 3. How does it work?

Lifecycle đơn giản:

```text
systemctl start
-> systemd launch dotnet process
-> Worker executes

systemctl stop
-> SIGTERM
-> .NET HostApplicationLifetime stopping
-> CancellationToken cancelled
-> worker cleanup
-> process exits
```

Nếu process không thoát trước timeout, systemd có thể gửi kill signal mạnh hơn.

## 4. Practical implementation

Worker:

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await ProcessNextMessageAsync(stoppingToken);
        }
    }
}
```

Service unit ví dụ:

```ini
[Unit]
Description=Order Worker
After=network.target

[Service]
WorkingDirectory=/opt/order-worker
ExecStart=/usr/bin/dotnet /opt/order-worker/Order.Worker.dll
Restart=on-failure
RestartSec=5
User=orderworker
Environment=DOTNET_ENVIRONMENT=Production

[Install]
WantedBy=multi-user.target
```

Sau đó:

```bash
sudo systemctl daemon-reload
sudo systemctl enable order-worker
sudo systemctl start order-worker
sudo systemctl status order-worker
```

## 5. Real production scenario

Một legacy integration worker chạy trên Linux VM đọc SFTP và ghi SQL. Deployment script kill process rồi start lại. Khi kill xảy ra giữa file processing, record bị xử lý nửa chừng và file marker chưa update.

Khi Worker propagate `CancellationToken` và hoàn thành/rollback current unit trước exit, shutdown predictable hơn. Idempotency vẫn cần vì hard kill/power loss luôn có thể xảy ra.

## 6. Failure scenario & troubleshooting

**Symptom** → service liên tục restart hoặc stop mất rất lâu.

**Evidence** → `systemctl status`, `journalctl -u order-worker` cho thấy exit code hoặc timeout stop.

**Hypothesis** → unhandled exception, config sai hoặc worker bỏ qua cancellation.

**Diagnosis** → xem journal, process exit code, startup exception và stack/traces.

**Fix** → handle lifecycle đúng, validate config startup, propagate stopping token và tránh blocking call không cancel được.

**Verification** → `systemctl stop` phải kết thúc trong expected grace period, không để lại partial work.

## 7. Common mistakes

- Dùng `Restart=always` che application crash loop.
- Không set working directory/environment rõ.
- Chạy service bằng root dù không cần.
- Ignore `CancellationToken` trong long-running I/O.
- Giả định graceful shutdown luôn xảy ra nên bỏ idempotency/recovery.

## 8. Alternatives

Docker/Kubernetes cung cấp lifecycle abstraction khác nhưng cũng dùng signal/grace period concept. Windows Service phù hợp Windows Server. Azure Functions/Worker trên managed platform giảm OS management nếu workload phù hợp.

## 9. Trade-offs

### Advantages

- Process supervision rõ.
- Automatic startup/restart.
- Tích hợp log và OS lifecycle.

### Costs / Risks

- Team phải vận hành VM/OS.
- Deployment/configuration drift có thể xảy ra.
- Restart policy sai có thể tạo crash loop hoặc che root cause.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết service manager khác với chạy process thủ công.

### Middle

Viết unit file, đọc `journalctl`, propagate shutdown token.

### Senior

Thiết kế graceful shutdown, idempotent work, restart/backoff và production diagnostics.

### Technical Lead / Architect

Quyết định VM service còn hợp lý hay nên chuyển sang container/managed compute dựa trên operational cost, dependency và migration risk.

## 11. Key takeaway

- `systemd` quản lý process; application vẫn phải quản lý work lifecycle.
- `SIGTERM` nên dẫn tới cooperative cancellation và bounded graceful shutdown.
- Graceful shutdown không thay thế idempotency và crash recovery.
