# 1. C# `CancellationToken`: propagation, linked deadlines và cancellation semantics

## 1. What is it?

`CancellationToken` là cooperative cancellation mechanism của .NET. Nó không kill thread và không tự rollback side effect. Nó chỉ truyền tín hiệu rằng caller không còn cần operation tiếp tục; từng layer phải chủ động dừng tại điểm an toàn.

```text
Client disconnect / timeout
        ↓
RequestAborted
        ↓
API → application → EF Core / HttpClient
        ↓
cooperative stop
```

## 2. Why does it exist?

Nếu gateway timeout sau 5 giây nhưng backend vẫn chạy SQL thêm 20 giây, hệ thống tiếp tục giữ connections và downstream capacity cho request không còn người nhận. Khi tải tăng, orphan work này làm overload trầm trọng hơn.

## 3. How does it work?

Token được phát bởi `CancellationTokenSource`. Deadline cục bộ có thể liên kết với request token:

```csharp
using var timeout = new CancellationTokenSource(TimeSpan.FromSeconds(2));
using var linked = CancellationTokenSource.CreateLinkedTokenSource(
    requestToken, timeout.Token);

await dependency.CallAsync(linked.Token);
```

## 4. Practical implementation

```csharp
public Task<Order?> GetAsync(
    Guid id,
    CancellationToken cancellationToken) =>
    _db.Orders
       .AsNoTracking()
       .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);
```

Controller/Minimal API phải truyền token xuyên xuống service, repository, HTTP SDK và loops thay vì tạo `CancellationToken.None` ở giữa.

## 5. Real production scenario

Pricing API có gateway timeout 5 giây. Một repository không truyền token vào EF Core nên query tiếp tục 25 giây. Dưới traffic cao, DB pool cạn dù client đã bỏ request.

## 6. Failure scenario & troubleshooting

**Symptom** → parent request đã timeout nhưng dependency spans vẫn chạy.  
**Evidence** → traces cho thấy child operations dài hơn request lifetime.  
**Hypothesis** → token propagation bị đứt.  
**Diagnosis** → kiểm tra overload không token, `CancellationToken.None`, loops không check token.  
**Fix** → propagate end-to-end và đặt dependency deadline riêng.  
**Verification** → abort request trong integration test và xác nhận downstream work dừng.

## 7. Common mistakes

* Catch `OperationCanceledException` rồi log như 500.
* Tin cancellation undo payment/message đã gửi.
* Dùng cùng timeout cho mọi dependency.
* Tạo token mới và bỏ token của caller.

## 8. Alternatives

Gateway timeout, Polly timeout và SDK timeout bổ sung deadline nhưng không thay cancellation propagation. Idempotency vẫn cần cho side effects.

## 9. Trade-offs

### Advantages

* Giảm wasted work.
* Giải phóng resource sớm.
* Hỗ trợ graceful shutdown.

### Costs / Risks

* Contract xuyên nhiều layer.
* Side-effect semantics phức tạp.
* Telemetry phải phân biệt cancellation và failure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu token là cooperative signal.

### Middle
Propagate token qua EF Core, `HttpClient` và async loops.

### Senior
Thiết kế latency budget, timeout taxonomy và side-effect safety.

### Technical Lead / Architect
Chuẩn hóa end-to-end deadline/cancellation policy cho service graph.

## 11. Key takeaway

* Cancellation chỉ có giá trị khi propagate end-to-end.
* Gateway timeout không tự dừng backend work.
* Cancel không đồng nghĩa rollback.

# 2. ASP.NET Core `ProblemDetails`: error contract ổn định

## 1. What is it?

`ProblemDetails` là standardized HTTP error representation với các field như `type`, `title`, `status`, `detail`, `instance` và extensions.

## 2. Why does it exist?

Client không nên parse exception message. Error response là public API contract và cần stable machine-readable identifiers.

## 3. How does it work?

```text
Domain/Application outcome
        ↓
HTTP mapping
        ↓
status + stable problem type
        ↓
ProblemDetails
```

Internal exception type không nên leak trực tiếp ra transport contract.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails(options =>
{
    options.CustomizeProblemDetails = ctx =>
    {
        ctx.ProblemDetails.Extensions["traceId"] =
            Activity.Current?.TraceId.ToString()
            ?? ctx.HttpContext.TraceIdentifier;
    };
});

app.UseExceptionHandler();
```

Business conflict:

```csharp
return Results.Problem(
    statusCode: 409,
    title: "Order state conflict",
    type: "https://errors.example.com/order-state-conflict");
```

## 5. Real production scenario

Web, mobile và partner clients từng nhận ba error shapes khác nhau. Sau khi chuẩn hóa, clients có generic handling cho validation, not-found, conflict và transient failures.

## 6. Failure scenario & troubleshooting

**Symptom** → partner integration fail dù status code vẫn 409.  
**Evidence** → `type`/error code bị đổi.  
**Hypothesis** → team coi error identifier là implementation detail.  
**Diagnosis** → compare OpenAPI/contract tests.  
**Fix** → version/stabilize machine-readable codes.  
**Verification** → contract tests cho representative failures.

## 7. Common mistakes

* Trả raw stack trace.
* HTTP 200 cho mọi lỗi.
* Dùng .NET exception class làm public error code.
* Đưa PII/SQL text vào `detail`.

## 8. Alternatives

Custom envelope hợp lý khi organization đã có mature standard; gRPC và GraphQL có semantics khác. Dù dùng format nào vẫn cần stable contract.

## 9. Trade-offs

### Advantages
* Consistency cho clients.
* Dễ document/test.
* Gắn correlation tốt.

### Costs / Risks
* Cần taxonomy governance.
* Public codes trở thành compatibility commitment.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu error body cũng là contract.

### Middle
Map validation/not-found/conflict đúng semantics.

### Senior
Thiết kế stable taxonomy và contract tests.

### Technical Lead / Architect
Chuẩn hóa error standard và deprecation lifecycle.

## 11. Key takeaway

* Error payload không phải log message.
* Stable identifiers quan trọng hơn wording.
* Internal diagnostics thuộc telemetry.

# 3. EF Core optimistic concurrency với `rowversion`

## 1. What is it?

Optimistic concurrency phát hiện stale update mà không giữ DB lock trong suốt user think-time. SQL Server `rowversion` thay đổi khi row được update và có thể dùng làm concurrency token.

## 2. Why does it exist?

```text
A reads version 10
B reads version 10
A saves → 11
B saves stale 10 → lost update
```

Web UI không thể giữ lock vài phút trong khi user chỉnh form.

## 3. How does it work?

EF thêm original token vào update predicate:

```sql
UPDATE Orders
SET Status = @status
WHERE Id = @id
  AND RowVersion = @originalVersion;
```

0 affected rows → `DbUpdateConcurrencyException`.

## 4. Practical implementation

```csharp
public sealed class Order
{
    public Guid Id { get; set; }
    public string Status { get; set; } = null!;

    [Timestamp]
    public byte[] RowVersion { get; set; } = null!;
}
```

API nên round-trip token, thường encode Base64, rồi trả 409 nếu stale.

## 5. Real production scenario

Hai support agents mở cùng order. Một người cập nhật payment status, người kia save stale form. Không concurrency control sẽ silently overwrite dữ liệu mới.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu “quay lại” giá trị cũ.  
**Evidence** → UPDATE không có version predicate.  
**Hypothesis** → last-write-wins.  
**Diagnosis** → reproduce hai sessions đọc cùng version.  
**Fix** → concurrency token + conflict workflow.  
**Verification** → stale update phải fail mà không overwrite.

## 7. Common mistakes

* Retry stale values tự động.
* Không round-trip token.
* Nhầm `rowversion` với datetime.
* Trả 500 cho expected conflict.

## 8. Alternatives

HTTP ETag + `If-Match`, pessimistic locking cho short critical sections, domain-specific merge khi các fields có thể hợp nhất.

## 9. Trade-offs

### Advantages
* Không giữ long lock.
* Detect lost update rõ.

### Costs / Risks
* Client phải handle conflict.
* Merge semantics có thể phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu last-write-wins có thể mất dữ liệu.

### Middle
Cấu hình token và xử lý concurrency exception.

### Senior
Thiết kế merge/retry semantics.

### Technical Lead / Architect
Quyết định aggregate nào cần concurrency protection.

## 11. Key takeaway

* Optimistic concurrency phát hiện stale write, không tự merge.
* Retry chỉ đúng khi business semantics cho phép.
* Conflict là expected domain outcome, không mặc định là 500.

# 4. SQL Server covering index và Key Lookup

## 1. What is it?

Nonclustered index có thể seek đúng rows nhưng thiếu columns query cần. SQL Server khi đó thực hiện `Key Lookup` về clustered/base row. Covering index chứa đủ dữ liệu để tránh lookup.

## 2. Why does it exist?

Một lookup rất rẻ; 200.000 lookups thì không. Vì vậy execution plan có “Index Seek” vẫn có thể rất chậm.

## 3. How does it work?

```sql
CREATE INDEX IX_Orders_CustomerId
ON Orders(CustomerId);
```

Query cần thêm fields:

```sql
SELECT Id, CreatedAt, Total, Status
FROM Orders
WHERE CustomerId = @CustomerId;
```

Covering index:

```sql
CREATE INDEX IX_Orders_CustomerId_Covering
ON Orders(CustomerId)
INCLUDE (CreatedAt, Total, Status);
```

## 4. Practical implementation

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

Đọc Actual Execution Plan, Key Lookup execution count, logical reads, estimated vs actual rows và write overhead trước khi sửa.

## 5. Real production scenario

Customer dashboard nhanh với khách nhỏ nhưng 4 giây với enterprise tenant. Plan có Index Seek nhưng Key Lookup lặp 200.000 lần.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 cao dù có seek.  
**Evidence** → lookup count lớn, logical reads cao.  
**Hypothesis** → lookup amplification.  
**Diagnosis** → actual plan + `STATISTICS IO`.  
**Fix** → projection gọn hoặc include columns có chọn lọc.  
**Verification** → đo cả read benefit và write cost.

## 7. Common mistakes

* Thấy seek là kết luận query tối ưu.
* Include gần toàn table.
* Tạo index cho từng endpoint.
* Dùng `SELECT *`.

## 8. Alternatives

Filtered index, columnstore, read model riêng hoặc cache tùy access pattern.

## 9. Trade-offs

### Advantages
* Giảm logical reads.
* Tăng read throughput.

### Costs / Risks
* Index rộng tốn storage/memory.
* Writes phải maintain thêm data.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu seek không đồng nghĩa rẻ.

### Middle
Đọc Key Lookup và logical reads.

### Senior
Cân bằng read/write/index overlap.

### Technical Lead / Architect
Thiết kế indexing theo workload classes.

## 11. Key takeaway

* Key Lookup cost tăng theo matching cardinality.
* Phải đọc complete plan, không nhìn một operator.
* Cover có chủ đích.

# 5. Distributed lease + fencing token

## 1. What is it?

Distributed lease là quyền sở hữu có thời hạn. Owner có thể mất lease nhưng vẫn chạy nếu process bị pause. Fencing token là sequence tăng đơn điệu để downstream reject stale owner.

## 2. Why does it exist?

```text
A gets lease #41
A pauses
lease expires
B gets #42
A resumes
```

Nếu A và B cùng ghi dữ liệu, lock TTL đơn giản không đảm bảo single-writer correctness.

## 3. How does it work?

```text
B writes token 42 → accepted
storage remembers 42
A writes token 41 → rejected
```

Downstream resource phải enforce token.

## 4. Practical implementation

```csharp
var lease = await coordinator.AcquireAsync("invoice-batch", ct);
if (lease is null) return;

await processor.RunAsync(
    lease.Sequence,
    lease.LostToken);
```

```sql
UPDATE BatchState
SET Payload = @Payload,
    LastFence = @Fence
WHERE Id = @Id
  AND LastFence < @Fence;
```

## 5. Real production scenario

Worker A có Redis lease 60 giây nhưng VM pause 90 giây. Worker B lấy lease mới. A resume và chạy tiếp settlement. Nếu không fenced/idempotent, side effect có thể chạy hai lần.

## 6. Failure scenario & troubleshooting

**Symptom** → hai workers cùng xử lý.  
**Evidence** → old worker pause vượt TTL.  
**Hypothesis** → stale owner.  
**Diagnosis** → correlate lease sequence với writes.  
**Fix** → lost-lease cancellation + fencing/idempotency.  
**Verification** → chaos test pause worker lâu hơn TTL.

## 7. Common mistakes

* Nghĩ distributed lock là mutex tuyệt đối.
* Ignore renewal failure.
* Generate fence nhưng downstream không check.
* Dùng wall clock làm sequence không đáng tin.
* Dùng lock thay vì thiết kế idempotent.

## 8. Alternatives

Leader election, queue partition ownership, DB advisory locks, unique job claims hoặc single-writer architecture.

## 9. Trade-offs

### Advantages
* Lease tránh dead owner.
* Fencing chặn stale write.

### Costs / Risks
* Cần monotonic sequence.
* Downstream phải enforce.
* Complexity tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu distributed lock có failure semantics khác local lock.

### Middle
Biết TTL/renewal/lost lease.

### Senior
Thiết kế fencing và idempotency.

### Technical Lead / Architect
Chọn lease hay queue/single-writer dựa trên failure model.

## 11. Key takeaway

* Lease expiry có thể tạo hai active owners.
* Fencing bảo vệ resource thật.
* Idempotency vẫn cần.

# 6. Azure Blob Storage cho file lớn: streaming, Managed Identity và SAS

## 1. What is it?

Blob Storage là object storage. Với file lớn, kiến trúc phải quyết định data path, authentication, upload lifecycle, retries và integrity.

## 2. Why does it exist?

Nếu app proxy 5 GB uploads, app tier có thể scale theo bandwidth thay vì business workload. Nếu SAS quá rộng, security blast radius lại tăng.

## 3. How does it work?

```text
Client → App → Blob
```

hoặc:

```text
Client → Blob directly
          ↑
    short-lived SAS
```

App-to-Azure nên ưu tiên Managed Identity.

## 4. Practical implementation

```csharp
var service = new BlobServiceClient(
    new Uri("https://myaccount.blob.core.windows.net"),
    new DefaultAzureCredential());

var blob = service
    .GetBlobContainerClient("uploads")
    .GetBlobClient(blobName);

await blob.UploadAsync(
    request.Body,
    overwrite: false,
    cancellationToken);
```

Sau upload nên verify size/checksum/ETag trước khi workflow complete.

## 5. Real production scenario

CMS upload video 4K. Chuyển direct-to-Blob giúp app chỉ authorize/orchestrate, còn antivirus/transcoding chạy bất đồng bộ.

## 6. Failure scenario & troubleshooting

**Symptom** → upload success nhưng file corrupt.  
**Evidence** → checksum/size mismatch.  
**Hypothesis** → partial upload được mark complete.  
**Diagnosis** → inspect block commit, ETag, completion event.  
**Fix** → explicit completion + integrity check.  
**Verification** → test disconnect/retry/duplicate callback.

## 7. Common mistakes

* Storage account key trong config.
* SAS sống quá lâu/quyền quá rộng.
* Proxy file lớn qua app không cần thiết.
* Không cleanup abandoned uploads.

## 8. Alternatives

Azure Files, Data Lake hoặc app-proxied upload cho file nhỏ/inline inspection.

## 9. Trade-offs

### Advantages
* Scale tốt.
* Direct upload giảm app pressure.
* Managed Identity giảm secrets.

### Costs / Risks
* SAS lifecycle phức tạp.
* Processing chuyển sang async.
* Integrity/scanning phải explicit.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Biết file lớn nên stream.

### Middle
Dùng Blob SDK, MI và scoped SAS.

### Senior
Thiết kế retry/integrity/resumable workflow.

### Technical Lead / Architect
Chọn data path và trust boundary.

## 11. Key takeaway

* Large-file upload là architecture problem.
* Identity-first cho app; short-lived scoped SAS cho client.
* Upload complete cần integrity semantics.

# 7. Kubernetes startup/readiness/liveness probes

## 1. What is it?

* startup: app đã khởi động xong?
* readiness: Pod có nên nhận traffic?
* liveness: process có cần restart?

Ba câu hỏi này không giống nhau.

## 2. Why does it exist?

Nếu liveness check phụ thuộc DB, DB slowdown có thể khiến toàn bộ Pods restart và tạo restart storm, làm incident nặng hơn.

## 3. How does it work?

Readiness failure loại Pod khỏi service endpoints. Liveness failure restart container. Startup probe bảo vệ slow-start process khỏi bị kill quá sớm.

## 4. Practical implementation

```csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy())
    .AddSqlServer(connectionString, name: "sql");

app.MapHealthChecks("/health/live",
    new HealthCheckOptions
    {
        Predicate = x => x.Name == "self"
    });

app.MapHealthChecks("/health/ready",
    new HealthCheckOptions
    {
        Predicate = _ => true
    });
```

## 5. Real production scenario

DB latency spike 20 giây. Liveness gọi DB nên tất cả replicas restart, tạo cold connections và làm DB càng quá tải.

## 6. Failure scenario & troubleshooting

**Symptom** → Pod restarts hàng loạt.  
**Evidence** → liveness timeout ở downstream.  
**Hypothesis** → probe semantics sai.  
**Diagnosis** → `kubectl describe pod`, endpoint dependencies, thresholds.  
**Fix** → external dependency thường chỉ ảnh hưởng readiness.  
**Verification** → inject DB outage và xác nhận không restart loop.

## 7. Common mistakes

* Liveness gọi DB/Redis/external APIs.
* Probe timeout quá aggressive.
* Health endpoint chạy expensive query.
* Ready trước khi initialization complete.

## 8. Alternatives

TCP/exec probes cho use case phù hợp; sidecar aggregation chỉ khi complexity được justify.

## 9. Trade-offs

### Advantages
* Self-healing.
* Automated routing.

### Costs / Risks
* Sai semantics tự tạo outage.
* Threshold cần tuning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt ready và alive.

### Middle
Implement lightweight health endpoints.

### Senior
Debug restart storm và startup behavior.

### Technical Lead / Architect
Chuẩn hóa probe policy và chaos testing.

## 11. Key takeaway

* Readiness quyết định traffic; liveness quyết định restart.
* External dependency outage thường không phải liveness failure.
* Probe config là resilience logic.

# 8. OpenTelemetry metric cardinality

## 1. What is it?

Metric cardinality là số unique time series tạo bởi metric name + attribute combinations.

## 2. Why does it exist?

Metrics hoạt động tốt với bounded dimensions. `user_id`, `order_id`, raw URL hoặc exception message có thể tạo hàng trăm nghìn series và làm collector/backend quá tải.

## 3. How does it work?

20 routes × 6 statuses × 4 regions = 480 series. Thêm 100.000 users có thể đẩy theoretical combination count lên hàng chục triệu.

## 4. Practical implementation

```csharp
private static readonly Meter Meter = new("Checkout");
private static readonly Counter<long> Requests =
    Meter.CreateCounter<long>("checkout.requests");

Requests.Add(1,
    new("result", result),
    new("region", region));
```

Không dùng request ID/user ID làm metric labels.

## 5. Real production scenario

Team thêm `customerId` vào latency histogram. Series count và observability bill tăng mạnh; dashboard query chậm.

## 6. Failure scenario & troubleshooting

**Symptom** → collector memory tăng, metrics bị drop.  
**Evidence** → active-series count spike sau deploy.  
**Hypothesis** → high-cardinality attribute.  
**Diagnosis** → inspect unique values/instrumentation diff.  
**Fix** → normalize/drop dimension, đưa identity sang logs/traces.  
**Verification** → theo dõi series count và ingestion cost.

## 7. Common mistakes

* GUID/request IDs trong labels.
* Raw exception messages.
* Raw URLs thay route templates.
* Copy mọi trace attributes sang metrics.

## 8. Alternatives

Logs cho detail, traces cho request correlation, exemplars để link metrics với representative traces.

## 9. Trade-offs

### Advantages
* Metrics tốt cho aggregation/SLO/alerting.

### Costs / Risks
* High cardinality gây cost explosion.
* Quá ít dimensions lại khó actionable.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu labels tạo series.

### Middle
Chọn bounded dimensions.

### Senior
Thiết kế metric taxonomy/cardinality monitoring.

### Technical Lead / Architect
Đặt observability budget và instrumentation governance.

## 11. Key takeaway

* Metric labels phải bounded.
* Identity chi tiết thuộc logs/traces.
* Observability cũng cần capacity engineering.

# 9. Consumer-driven contract testing

## 1. What is it?

Consumer-driven contracts mô tả interactions consumers thật sự phụ thuộc, rồi provider verify các contracts đó trong CI.

## 2. Why does it exist?

Unit test producer không chứng minh clients còn tương thích. Full E2E chậm và flaky. Contract tests tạo feedback nhanh ở service boundary.

## 3. How does it work?

```text
Consumer expectation
      ↓
published contract
      ↓
Provider verification
      ↓
breaking change caught before deploy
```

Consumer chỉ nên assert fields/semantics nó thực sự dùng.

## 4. Practical implementation

Pact-style concept:

```csharp
await pact
    .UponReceiving("an existing paid order")
    .WithRequest(HttpMethod.Get, "/orders/123")
    .WillRespond()
    .WithStatus(HttpStatusCode.OK)
    .WithJsonBody(new
    {
        id = Match.Type("123"),
        status = Match.Type("Paid"),
        total = Match.Decimal(125.50m)
    });
```

## 5. Real production scenario

Orders API đổi `total` từ number thành object. Producer tests xanh nhưng mobile client cũ vẫn cần number. Provider verification fail trước release.

## 6. Failure scenario & troubleshooting

**Symptom** → thêm optional field cũng làm contracts fail.  
**Evidence** → consumers snapshot toàn payload.  
**Hypothesis** → contract mô tả implementation chứ không phải dependency.  
**Diagnosis** → review fields consumer thật sự đọc.  
**Fix** → tolerant matching.  
**Verification** → additive changes không làm fail.

## 7. Common mistakes

* Thay mọi integration tests bằng contracts.
* Assert quá nhiều fields.
* Verify với fake serializer.
* Không version contracts.
* Không có breaking-change workflow.

## 8. Alternatives

OpenAPI compatibility checks, real integration tests và một số E2E critical journeys.

## 9. Trade-offs

### Advantages
* Bắt breaking changes sớm.
* Feedback nhanh.

### Costs / Risks
* Contract matrix tăng.
* Cần broker/versioning discipline.
* Không bắt mọi infrastructure issue.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu mock của consumer không chứng minh provider thật tương thích.

### Middle
Viết contract đúng dependency.

### Senior
Quản lý provider states và evolution.

### Technical Lead / Architect
Thiết kế testing pyramid cho service ecosystem.

## 11. Key takeaway

* Contract tests bảo vệ boundary nhanh hơn E2E.
* Chỉ assert dependency thật.
* Vẫn cần real integration tests.

# 10. LLM Structured Outputs + deterministic tool validation

## 1. What is it?

Structured Outputs ép model trả dữ liệu theo schema. Nhưng schema chỉ đảm bảo shape, không đảm bảo authorization, ownership hay business correctness.

```text
LLM structured proposal
       ↓
schema validation
       ↓
authorization + business validation
       ↓
tool execution
```

Model output phải được coi là untrusted input.

## 2. Why does it exist?

Parse prose bằng regex rất fragile. Structured outputs giảm ambiguity, nhưng JSON hợp lệ vẫn có thể chứa wrong tenant, excessive amount hoặc dangerous action.

## 3. How does it work?

Model có thể đề xuất:

```json
{
  "action": "refund_invoice",
  "invoiceId": "INV-123",
  "amount": 50
}
```

Application vẫn phải kiểm tra resource ownership, user permission, refundable balance, idempotency và approval.

## 4. Practical implementation

```csharp
public sealed record RefundCommand(
    string InvoiceId,
    decimal Amount,
    string Reason);

public async Task<RefundResult> ExecuteAsync(
    RefundCommand command,
    ClaimsPrincipal user,
    CancellationToken ct)
{
    if (command.Amount <= 0)
        return RefundResult.Invalid();

    var invoice = await repository.GetAsync(command.InvoiceId, ct);
    if (invoice is null)
        return RefundResult.NotFound();

    if (!authorization.CanRefund(user, invoice))
        return RefundResult.Forbidden();

    if (command.Amount > invoice.RefundableAmount)
        return RefundResult.Invalid();

    return await paymentGateway.RefundAsync(command, ct);
}
```

## 5. Real production scenario

Customer note chứa prompt injection yêu cầu refund full amount. Model có thể sinh tool call hợp schema. Deterministic authorization/invariants phải chặn action không hợp lệ.

## 6. Failure scenario & troubleshooting

**Symptom** → JSON parse thành công nhưng action sai tenant.  
**Evidence** → executor tin `tenantId` do model cung cấp.  
**Hypothesis** → structured output bị coi là trusted.  
**Diagnosis** → trace identity → proposal → validation → tool.  
**Fix** → derive identity từ authenticated context và enforce ownership.  
**Verification** → adversarial tests với prompt injection/unauthorized IDs/duplicates.

## 7. Common mistakes

* Tin schema = business validation.
* Cho model chọn tenant identity.
* Expose generic `execute_sql`.
* Không idempotency.
* Đưa secrets vào model context.
* Không audit tool outcome.

## 8. Alternatives

Read-only assistant cho use case không cần actions; deterministic rules engine khi không cần LLM; human approval cho high-impact actions.

## 9. Trade-offs

### Advantages
* Typed boundary dễ validate/test.
* Tool calls audit rõ.
* Giảm parsing fragility.

### Costs / Risks
* Model vẫn có thể semantic error.
* Schema cần versioning.
* High-impact actions cần approval/deterministic controls.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu JSON valid chưa chắc business-valid.

### Middle
Map output sang typed DTO và validate.

### Senior
Thiết kế least-privilege tools, idempotency và prompt-injection defenses.

### Technical Lead / Architect
Xác định AI trust model và approval boundaries.

## 11. Key takeaway

* Structured Outputs giải quyết shape, không giải quyết trust.
* Authorization/business invariants phải deterministic.
* Tool càng narrow và least-privilege, blast radius càng nhỏ.
