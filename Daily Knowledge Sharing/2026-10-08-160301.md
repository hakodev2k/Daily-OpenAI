# 1. .NET Garbage Collector: Large Object Heap, allocation pressure và ArrayPool<T>

## 1. What is it?

GC quản lý vòng đời managed objects, nhưng không có nghĩa allocation là miễn phí. Object lớn (thường từ khoảng 85.000 bytes) đi vào Large Object Heap (LOH); LOH được thu gom cùng Gen 2. Allocation rate, object lifetime và fragmentation quyết định tác động lên latency, không chỉ tổng RAM đang sử dụng. `ArrayPool<T>` cho phép tái sử dụng buffer để tránh cấp phát lặp lại, nhưng chuyển một phần trách nhiệm quản lý vòng đời về code.

## 2. Why does it exist?

Một API upload hoặc export xử lý hàng nghìn payload 200 KB mỗi giây sẽ tạo lượng allocation đáng kể nếu mỗi request gọi `new byte[]`. Khi Gen 2 collection xuất hiện thường xuyên, pause và CPU có thể tăng dù không có memory leak. Pooling giải quyết churn của buffer tạm; nó không giải quyết việc giữ reference quá lâu hoặc thiết kế đọc toàn bộ file vào RAM.

## 3. How does it work?

GC xác định object còn reachable từ roots. Object sống qua nhiều collection có thể được promote. LOH thông thường không được compact trong mọi lần collection; fragmentation có thể khiến footprint tăng. `ArrayPool<byte>.Shared.Rent(n)` trả buffer có độ dài **ít nhất** n, không cam kết đúng n hay dữ liệu sạch. Buffer được thuê phải trả về pool sau khi không còn ai sử dụng.

## 4. Practical implementation

```csharp
using System.Buffers;

static async Task<int> CopyChunkAsync(
    Stream source, Stream destination, CancellationToken ct)
{
    const int requested = 128 * 1024;
    byte[] buffer = ArrayPool<byte>.Shared.Rent(requested);
    try
    {
        int read = await source.ReadAsync(
            buffer.AsMemory(0, requested), ct);
        if (read > 0)
            await destination.WriteAsync(buffer.AsMemory(0, read), ct);
        return read;
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
    }
}
```

Đây là ví dụ một chunk, không phải hàm copy toàn bộ stream. Với pipeline dài, cân nhắc `Stream.CopyToAsync` hoặc `System.IO.Pipelines` trước khi tự viết buffering.

## 5. Real production scenario

Dịch vụ tạo báo cáo Excel tải dữ liệu từ SQL, serialize rồi gửi Blob Storage. Đội ngũ nhận thấy p99 tăng mỗi khi nhiều báo cáo chạy song song. Profiling cho thấy hàng nghìn buffer trung gian lớn bị cấp phát, cùng lúc worker giữ toàn bộ file trong `MemoryStream`. Sửa theo hướng streaming và reuse buffer giảm peak working set rõ rệt hơn việc chỉ tăng RAM container.

## 6. Failure scenario & troubleshooting

**Symptom:** memory tăng và request latency có spike. **Evidence:** `dotnet-counters monitor System.Runtime` cho thấy allocation rate và Gen 2 GC tăng; `dotnet-gcdump` hoặc profiler cho thấy `byte[]` lớn. **Hypothesis:** buffer churn hoặc retained buffers. **Diagnosis:** đối chiếu allocation stack, live objects và concurrent requests. **Fix:** stream dữ liệu, giới hạn concurrency, dùng pooling có kiểm soát. **Verification:** đo lại p95/p99, allocation bytes/request, GC pause và memory sau tải kéo dài. Không suy luận “memory leak” chỉ từ đồ thị RSS.

## 7. Common mistakes

Trả buffer về pool khi async consumer vẫn đang đọc; dùng toàn bộ `buffer.Length` thay vì số byte thực tế; quên `finally`; đưa buffer chứa secrets về pool mà không xóa; pool mọi object dù allocation nhỏ và ít; gọi `GC.Collect()` như cách chữa latency.

## 8. Alternatives

`stackalloc`/`Span<T>` phù hợp vùng nhớ nhỏ, sống ngắn; `MemoryPool<T>` hỗ trợ ownership qua `IMemoryOwner<T>`; `Pipelines` hữu ích cho stream protocol. Đối với request ít và payload nhỏ, allocation thông thường có thể đơn giản, an toàn và đủ nhanh.

## 9. Trade-offs

### Advantages

Giảm allocation churn, Gen 2 pressure và biến động latency khi buffer có thể tái sử dụng.

### Costs / Risks

Buffer ownership phức tạp, nguy cơ data leak và use-after-return; pool không giới hạn tổng concurrency hay khắc phục giữ object lâu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt object unreachable với object đã được thu gom; hiểu `Rent`/`Return` là một cặp bắt buộc.

### Middle

Đo allocations, dùng `try/finally` và xác định chính xác vùng byte hợp lệ.

### Senior

Đọc GC counters, phân biệt fragmentation với leak, benchmark theo throughput và tail latency.

### Technical Lead / Architect

Quyết định nên streaming, pooling hay giới hạn workload; thiết lập memory budget theo replica và quy tắc ownership cho toàn nhóm.

## 11. Key takeaway

- GC tự động không đồng nghĩa allocation không có chi phí.
- Ưu tiên giảm buffering không cần thiết trước khi tối ưu pool.
- Pooling chỉ an toàn khi ownership và cleanup rõ ràng.

# 2. ASP.NET Core ProblemDetails: thiết kế error contract ổn định

## 1. What is it?

`ProblemDetails` là định dạng JSON chuẩn hóa thông tin lỗi HTTP theo RFC 9457. Đây là **contract với client**, không chỉ cách serialize exception. Một response lỗi hữu ích cần status, type, title, detail phù hợp và correlation identifier; không nên phơi stack trace hay tên bảng database.

## 2. Why does it exist?

Nếu từng controller trả `{ message }`, `{ errorCode }` hoặc HTML error page, frontend phải xử lý nhiều schema và không phân biệt lỗi validation, conflict, unauthorized hay dependency failure. Chuẩn hóa giúp client đưa ra hành vi đúng và hỗ trợ điều tra production mà không rò thông tin nội bộ.

## 3. How does it work?

Request đi qua middleware; exception chưa được xử lý được `UseExceptionHandler` bắt và chuyển thành response. `IExceptionHandler` có thể map domain exception sang HTTP status; `AddProblemDetails` hỗ trợ tạo payload nhất quán. Chỉ map lỗi đã hiểu rõ; lỗi bất ngờ là 500. Validation failure và business conflict là hai trường hợp khác nhau.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler<ApiExceptionHandler>();

var app = builder.Build();
app.UseExceptionHandler();

sealed class ApiExceptionHandler : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext context, Exception error, CancellationToken ct)
    {
        if (error is not OrderConflictException) return false;
        context.Response.StatusCode = StatusCodes.Status409Conflict;
        await Results.Problem(
            statusCode: 409,
            title: "Order state conflict",
            type: "https://httpstatuses.com/409",
            extensions: new Dictionary<string, object?>
            {
                ["traceId"] = context.TraceIdentifier,
                ["code"] = "ORDER_CONFLICT"
            }).ExecuteAsync(context);
        return true;
    }
}
```

`OrderConflictException` là domain exception của ứng dụng. Với 500, để handler mặc định xử lý và cấu hình logging/ProblemDetails phù hợp; đừng trả `error.Message` trực tiếp.

## 5. Real production scenario

Ứng dụng timesheet có nút Approve. Hai quản lý thao tác đồng thời; backend phát hiện version conflict và trả 409 kèm code ổn định. Frontend hiển thị “Dữ liệu đã thay đổi, hãy tải lại” thay vì retry mù quáng. `traceId` giúp support đối chiếu logs và trace của request.

## 6. Failure scenario & troubleshooting

**Symptom:** frontend nhận 200 với body báo lỗi hoặc 500 cho mọi lỗi nghiệp vụ. **Evidence:** Network tab cho thấy status không nhất quán, metrics 5xx tăng. **Hypothesis:** controller swallow exception hoặc mapping quá rộng. **Diagnosis:** integration test từng loại exception và inspect middleware order. **Fix:** mapping có chủ đích, giữ HTTP semantics. **Verification:** test 400/401/403/404/409/429/500 và bảo đảm response không chứa secrets.

## 7. Common mistakes

Dùng 200 cho lỗi; trả 401 khi user đã authenticated nhưng không có quyền (thường là 403); log cùng exception nhiều lần; lộ SQL exception; đưa dynamic message vào `code` khiến client không thể xử lý ổn định; thay đổi schema mà không kiểm tra client cũ.

## 8. Alternatives

Custom error envelope có thể phù hợp hệ thống legacy đã có contract lâu dài; gRPC dùng status và trailers; GraphQL có error model riêng. Không nên ép một định dạng HTTP vào transport khác mà bỏ qua semantics của nó.

## 9. Trade-offs

### Advantages

Client integration nhất quán, dễ instrument và test, giảm coupling với message tự do.

### Costs / Risks

Cần governance về error codes, migration cho client cũ, và phân loại domain exceptions chính xác.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code mô tả kết quả HTTP, còn ProblemDetails bổ sung thông tin.

### Middle

Cấu hình middleware, viết mapping và integration tests.

### Senior

Thiết kế error taxonomy, phân biệt transient với permanent errors và kiểm soát information disclosure.

### Technical Lead / Architect

Đặt quy tắc contract/versioning dùng chung cho các API, nhưng tránh tạo shared package buộc mọi service triển khai đồng thời.

## 11. Key takeaway

- Error response là API contract có vòng đời riêng.
- Không biến domain conflict thành 500 hoặc thành “success” giả.
- Correlation và security phải được thiết kế ngay từ đầu.

# 3. EF Core LINQ translation: giữ filtering tại database

## 1. What is it?

`IQueryable<T>` mô tả một expression tree có thể được EF Core provider dịch sang SQL; `IEnumerable<T>` là abstraction của enumeration trong .NET. Ranh giới giữa chúng quyết định query chạy ở database hay dữ liệu được kéo về application rồi mới xử lý.

## 2. Why does it exist?

Viết LINQ trông giống nhau nhưng chi phí rất khác. `ToListAsync()` quá sớm biến filter trên hàng triệu orders thành filter in-memory. EF Core giúp compose query an toàn, nhưng developer vẫn phải hiểu translation, round trips và materialization.

## 3. How does it work?

Provider phân tích expression tree, tạo SQL, bind parameters, execute và materialize kết quả. Trong EF Core hiện đại, biểu thức không dịch được ở phần predicate thường gây exception thay vì tự động client-evaluate; một số xử lý client ở top-level projection vẫn được phép. `AsEnumerable()` hoặc `ToList()` là ranh giới chủ động chuyển sang client-side.

## 4. Practical implementation

```csharp
IQueryable<Order> query = db.Orders.AsNoTracking()
    .Where(o => o.TenantId == tenantId && o.CreatedAt >= from);

var page = await query
    .OrderByDescending(o => o.CreatedAt)
    .ThenByDescending(o => o.Id)
    .Select(o => new OrderSummary(o.Id, o.Total))
    .Take(50)
    .ToListAsync(ct);

string sql = query.ToQueryString(); // inspect trong môi trường debug
```

Ở production, luôn áp dụng authorization/tenant predicate trước pagination. `Take(50)` không tự giải quyết vấn đề nếu thiếu index tương ứng với filter và sort.

## 5. Real production scenario

Trang dashboard CRM chỉ hiển thị 50 khách hàng mới, nhưng endpoint gọi `ToListAsync` trước khi filter và sort. Khi dữ liệu tăng từ 10 nghìn lên 3 triệu rows, latency và RAM tăng mạnh. Đưa predicate/projection/pagination vào SQL giảm network transfer và số entity được materialize.

## 6. Failure scenario & troubleshooting

**Symptom:** endpoint chậm nhưng SQL Server CPU không cao. **Evidence:** trace có lượng dữ liệu trả về lớn; memory allocation cao; SQL thiếu `WHERE` hoặc `TOP`. **Hypothesis:** materialization sớm. **Diagnosis:** kiểm tra `ToQueryString()`, EF command logs và actual execution plan. **Fix:** compose trên `IQueryable` đến lúc execute, tránh custom C# methods trong predicate. **Verification:** đo rows read, bytes transferred, duration và allocations/request.

## 7. Common mistakes

Gọi `AsEnumerable` để né translation error rồi lọc toàn bộ ở RAM; trả `IQueryable` qua layer boundary khiến query bị sửa ngoài kiểm soát; log raw SQL chứa PII; dùng `Include` khi chỉ cần projection; quên deterministic ordering khi phân trang.

## 8. Alternatives

Raw SQL hoặc Dapper phù hợp hot path cần kiểm soát SQL chặt; stored procedure hữu ích khi logic gần dữ liệu và được vận hành tốt. EF Core vẫn thường đủ hiệu quả nếu SQL sinh ra đúng và được đo.

## 9. Trade-offs

### Advantages

Type-safe composition, parameterization và tích hợp unit-of-work.

### Costs / Risks

Provider-specific translation, abstraction có thể che SQL cost; LINQ dễ tạo cảm giác query rẻ dù thực tế tốn I/O.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deferred execution và khác biệt `IQueryable`/`IEnumerable`.

### Middle

Viết query có filter, projection, pagination; inspect SQL.

### Senior

Phân tích execution plan, index, round trips và query shape theo workload.

### Technical Lead / Architect

Quy định query ownership, giới hạn abstraction không cần thiết và tiêu chuẩn đo query regressions.

## 11. Key takeaway

- Vị trí materialization là một quyết định performance.
- Kiểm tra SQL thực tế, không đoán từ vẻ đẹp của LINQ.
- Chỉ chuyển sang client-side khi tập dữ liệu đã được giới hạn rõ ràng.

# 4. SQL Server deadlock: phân tích wait-for graph và retry đúng boundary

## 1. What is it?

Deadlock xảy ra khi các transactions giữ resources mà transaction khác cần, tạo vòng chờ không thể tự tiến triển. SQL Server chọn một victim và rollback transaction đó, thường trả error 1205. Deadlock khác blocking thông thường: blocking có thể tự kết thúc, còn deadlock cần phá vòng.

## 2. Why does it exist?

Transactions bảo vệ consistency bằng locks. Khi hai workflows cập nhật cùng tập records nhưng theo thứ tự khác nhau, lock acquisition có thể tạo vòng. Hệ thống càng concurrent, xác suất va chạm càng cao; tăng timeout không giải quyết được deadlock cycle.

## 3. How does it work?

Transaction A giữ X lock trên row 10 rồi đợi row 20. Transaction B giữ X lock row 20 rồi đợi row 10. Deadlock monitor phát hiện cycle và chọn victim dựa trên deadlock priority/cost. Sau rollback, application phải quyết định có retry **toàn bộ transaction** hay không.

## 4. Practical implementation

```sql
BEGIN TRAN;
UPDATE dbo.Inventory SET Reserved = Reserved + 1 WHERE ProductId = 10;
UPDATE dbo.Inventory SET Reserved = Reserved + 1 WHERE ProductId = 20;
COMMIT;
```

Mọi code path cập nhật cùng hai products nên dùng thứ tự khóa nhất quán, ví dụ ProductId tăng dần. Trong .NET, chỉ retry khi bắt đúng `SqlException.Number == 1205`, với số lần giới hạn, jitter và transaction/DbContext state được tạo lại phù hợp.

## 5. Real production scenario

Checkout đặt trước tồn kho của nhiều products; một workflow xử lý theo thứ tự cart, workflow khác theo thứ tự ưu tiên warehouse. Các cart có thứ tự đảo nhau gây deadlock sporadic. Chuẩn hóa thứ tự cập nhật và giảm thời gian giữ transaction giúp giảm số deadlocks mà không cần tăng database tier.

## 6. Failure scenario & troubleshooting

**Symptom:** vài request thất bại ngẫu nhiên với 1205. **Evidence:** Extended Events `xml_deadlock_report` (thường có trong `system_health`) cho biết processes, resources, statements và victim. **Hypothesis:** lock order không nhất quán. **Diagnosis:** dựng wait-for graph, đối chiếu execution plans và transaction duration. **Fix:** thống nhất ordering, index phù hợp để giảm scan/lock footprint, tách transaction quá dài. **Verification:** so deadlocks/min, lock waits và throughput dưới concurrency test.

## 7. Common mistakes

Retry từng SQL statement sau khi transaction đã rollback; retry không giới hạn; thực hiện HTTP call bên trong transaction; coi `NOLOCK` là giải pháp an toàn; nghĩ Snapshot Isolation sẽ loại bỏ mọi write-write conflict.

## 8. Alternatives

Optimistic concurrency phù hợp cập nhật entity độc lập; queue serialize operations theo key khi business cho phép; `sp_getapplock` có thể giúp khóa logic nhưng tăng coupling và contention. Không có một chiến lược áp dụng cho mọi workload.

## 9. Trade-offs

### Advantages

Locking transactions duy trì invariants mạnh và dễ lập luận khi phạm vi nhỏ.

### Costs / Risks

Contention, deadlock, retry amplification; chuẩn hóa lock order đòi hỏi hiểu tất cả writers của dữ liệu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt blocking, timeout và deadlock.

### Middle

Đọc error 1205, giữ transaction ngắn, thực hiện retry có giới hạn.

### Senior

Đọc deadlock XML và execution plan, tìm lock acquisition order thực tế.

### Technical Lead / Architect

Quyết định transaction boundary, data ownership và khi nào nên serialize writes ở application layer.

## 11. Key takeaway

- Deadlock là vòng chờ, không chỉ là “query chậm”.
- Đọc deadlock graph trước khi đổi isolation hoặc thêm index.
- Retry toàn transaction có kiểm soát; ưu tiên giảm nguyên nhân gốc.

# 5. Redis cache stampede: single-flight, TTL jitter và stale data

## 1. What is it?

Cache stampede xảy ra khi nhiều requests đồng thời thấy cùng một hot key bị miss/expire rồi cùng đánh vào database. Cache giúp giảm tải khi hit, nhưng có thể **khuếch đại tải** đúng thời điểm key hết hạn. Single-flight cho một producer tính lại giá trị; TTL jitter làm các keys không đồng loạt expire.

## 2. Why does it exist?

Một trang sản phẩm có 10.000 requests/phút, dữ liệu được cache 60 giây. Nếu hot key expire và hàng trăm requests cùng query SQL, connection pool có thể cạn trước khi cache được làm đầy. Đặt TTL dài hơn chỉ dời thời điểm xảy ra vấn đề.

## 3. How does it work?

Flow: request → cache GET → miss → acquire per-key coordination → recheck cache → load source → cache SET → release. `SemaphoreSlim` chỉ điều phối trong một process; nhiều replicas cần cơ chế phối hợp cross-instance hoặc chấp nhận một mức duplicate recomputation. Stale-while-revalidate có thể trả dữ liệu cũ trong khoảng cho phép khi một worker refresh.

## 4. Practical implementation

```csharp
private static readonly SemaphoreSlim ProductGate = new(1, 1);

async Task<ProductDto> GetHotProductAsync(int id, CancellationToken ct)
{
    var key = $"product:{id}";
    var cached = await cache.GetStringAsync(key, ct);
    if (cached is not null) return JsonSerializer.Deserialize<ProductDto>(cached)!;

    await ProductGate.WaitAsync(ct);
    try
    {
        cached = await cache.GetStringAsync(key, ct); // double-check
        if (cached is not null) return JsonSerializer.Deserialize<ProductDto>(cached)!;

        var product = await database.LoadProductAsync(id, ct);
        var ttl = TimeSpan.FromSeconds(50 + Random.Shared.Next(0, 21));
        await cache.SetStringAsync(key, JsonSerializer.Serialize(product),
            new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = ttl }, ct);
        return product;
    }
    finally { ProductGate.Release(); }
}
```

Đây là bản demo single-flight **trong một instance**, dùng một global gate nên giảm parallelism giữa các products. Production nên dùng per-key gates có cleanup, hoặc distributed strategy khi cần.

## 5. Real production scenario

Flash sale làm hàng nghìn người mở cùng product page. Cache vừa bị invalidate sau cập nhật giá; DB spikes, API p99 tăng và autoscaling làm thêm replicas cùng recompute. Giải pháp kết hợp request coalescing, bounded concurrency và stale product description; **giá cuối cùng** vẫn được xác nhận tại checkout.

## 6. Failure scenario & troubleshooting

**Symptom:** Redis hit rate giảm đột ngột, DB QPS tăng, nhiều request cùng query. **Evidence:** cache miss rate, key expiry histogram, traces và SQL connection waits. **Hypothesis:** synchronized expiration. **Diagnosis:** correlate timestamp expire với DB spike. **Fix:** TTL jitter, per-key coordination, pre-warming cho hot keys và graceful stale policy. **Verification:** load test đúng thời điểm expiry, đo concurrent source loads/key.

## 7. Common mistakes

Dùng distributed lock không có lease/timeout; giữ lock khi gọi dependency không giới hạn; trả stale inventory như dữ liệu authoritative; không double-check cache sau khi lấy lock; cache null mãi mãi; dùng một semaphore toàn hệ thống gây bottleneck.

## 8. Alternatives

`IMemoryCache` và `HybridCache` có thể hỗ trợ coalescing trong một process; precompute/materialized views phù hợp dữ liệu tổng hợp; không cache khi source query đủ rẻ và traffic thấp. Distributed lock chỉ đáng thêm khi chi phí recomputation lớn.

## 9. Trade-offs

### Advantages

Bảo vệ database, ổn định tail latency và giảm tải đột biến.

### Costs / Risks

Coordination latency, stale data, lock failure và thêm operational complexity. Freshness và correctness phải được quyết định theo loại dữ liệu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss và expiry không giống nhau về tải.

### Middle

Implement double-check, TTL jitter và metric hit/miss.

### Senior

Thiết kế stampede protection across replicas, fallback và concurrency budgets.

### Technical Lead / Architect

Quy định dữ liệu nào được stale, ai sở hữu invalidation và khi nào không nên thêm Redis.

## 11. Key takeaway

- Cache có thể làm backend quá tải khi nhiều miss đồng thời.
- Single-flight local không đồng nghĩa coordination toàn cluster.
- Stale policy phải dựa trên business correctness.

# 6. Modular Monolith: module ownership và dependency boundaries

## 1. What is it?

Modular Monolith là một deployable application với nhiều modules có trách nhiệm và boundaries rõ ràng. “Modular” không đến từ folder names mà từ quyền sở hữu domain rules, data và public contracts. Một module không được tùy tiện truy cập internal entity hay bảng của module khác.

## 2. Why does it exist?

Monolith tăng tốc phát triển và transaction đơn giản, nhưng khi mọi feature đọc/ghi chung tables và gọi chéo internals, thay đổi nhỏ tạo regression diện rộng. Microservices tách deployment nhưng thêm network failure và operational cost. Modular Monolith cho phép xây boundaries trước khi cần distributed deployment.

## 3. How does it work?

Mỗi module có application services, domain model và persistence riêng. Module A tương tác với B qua public interface hoặc integration event nội bộ. Có thể dùng cùng SQL database nhưng ownership của schema/tables phải rõ. Transaction cross-module cần xem xét kỹ; không mặc nhiên tạo một giant Unit of Work.

## 4. Practical implementation

```csharp
// Public contract của Inventory module
public interface IInventoryReservations
{
    Task<ReservationResult> ReserveAsync(
        Guid orderId, IReadOnlyList<ReservationLine> lines,
        CancellationToken ct);
}

// Ordering module chỉ phụ thuộc public contract:
public sealed class PlaceOrder(IInventoryReservations inventory)
{
    public Task<ReservationResult> ReserveAsync(
        Guid orderId, IReadOnlyList<ReservationLine> lines,
        CancellationToken ct)
        => inventory.ReserveAsync(orderId, lines, ct);
}
```

Đây là interface boundary, chưa phải một workflow checkout hoàn chỉnh. Tổ chức assemblies và architecture tests để Ordering không reference `Inventory.Infrastructure` hoặc query trực tiếp bảng Inventory.

## 5. Real production scenario

Nền tảng e-commerce có Catalog, Ordering, Inventory, Reviews. Catalog đổi schema giá hiển thị; Ordering không bị ảnh hưởng vì dùng published contract thay vì join thẳng bảng Catalog. Cả hệ thống vẫn deploy một artifact, dùng một pipeline và ít overhead hơn microservices.

## 6. Failure scenario & troubleshooting

**Symptom:** thay đổi Inventory làm build hoặc test của mọi module fail. **Evidence:** dependency graph có circular references; SQL logs cho thấy Ordering truy cập Inventory tables. **Hypothesis:** boundary chỉ tồn tại trên sơ đồ. **Diagnosis:** map assemblies, database ownership và call paths. **Fix:** expose use-case API, chuyển query cross-module sang read model hoặc contract có versioning. **Verification:** architecture tests chặn dependency trái chiều và change-impact tests.

## 7. Common mistakes

Một `SharedKernel` chứa toàn bộ entities; mỗi module có generic repository nhưng cùng sửa một bảng; gọi mọi thứ qua event dù cần immediate consistency; tạo interface cho mọi class thay vì cho business boundary; nhầm module với deployable service.

## 8. Alternatives

Layered Monolith phù hợp sản phẩm nhỏ ít domain complexity; Microservices có ích khi cần independent scaling/deployment và team ownership thực sự. Một monolith được thiết kế tốt thường là bước tiến an toàn hơn phân tán sớm.

## 9. Trade-offs

### Advantages

Refactoring thuận lợi, dễ debug và transaction local; tách responsibilities mà chưa gánh network operations.

### Costs / Risks

Cần discipline và enforcement; một process vẫn có shared resource contention, một deployment vẫn ảnh hưởng toàn ứng dụng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module cung cấp capability, không chỉ namespace.

### Middle

Triển khai public interfaces và giữ internal types private.

### Senior

Thiết kế invariants, transaction boundaries và test chống dependency erosion.

### Technical Lead / Architect

Chọn ranh giới theo business ownership, cân nhắc chi phí tách service trong tương lai và tránh distributed architecture khi chưa có nhu cầu.

## 11. Key takeaway

- Boundary là quyền sở hữu dữ liệu và dependency direction.
- Một deployable artifact vẫn có thể có kiến trúc module tốt.
- Tách service chỉ khi lợi ích vận hành vượt chi phí phân tán.

# 7. Azure Managed Identity + Key Vault: identity, permissions và secret rotation

## 1. What is it?

Managed Identity cấp identity cho Azure workload để gọi dịch vụ hỗ trợ Microsoft Entra ID mà không lưu credential của chính workload trong config. Azure Key Vault quản lý secrets/keys/certificates và phân quyền truy cập. Managed Identity **không** tự động cấp quyền vào mọi vault.

## 2. Why does it exist?

Lưu connection password hoặc client secret trong `appsettings.json`, pipeline variables hoặc container image tạo rủi ro leak và rotation khó. Identity-based access giảm long-lived credentials, nhưng secret của third-party API vẫn có thể cần lưu trong vault và xoay vòng theo policy.

## 3. How does it work?

App Service/Container Apps/VM được gắn system-assigned hoặc user-assigned identity. SDK dùng token credential để lấy access token cho Key Vault; Key Vault kiểm tra RBAC/data-plane permissions và network policy. Token có cache/lifetime; secret value do ứng dụng fetch có thể cũng được cache, vì vậy secret rotation không nhất thiết có hiệu lực ngay.

## 4. Practical implementation

```csharp
using Azure.Identity;
using Azure.Security.KeyVault.Secrets;

var client = new SecretClient(
    new Uri(configuration["KeyVaultUri"]!),
    new DefaultAzureCredential());

KeyVaultSecret secret =
    await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);

string paymentApiKey = secret.Value;
```

Trong production, cấp quyền tối thiểu `Key Vault Secrets User` cho identity cần đọc secret (và scope phù hợp); cấu hình network access/Private Endpoint nếu cần. `DefaultAzureCredential` thuận tiện dev/prod nhưng nên kiểm soát credential chain trong production theo yêu cầu bảo mật.

## 5. Real production scenario

Một API xử lý thanh toán trên App Service cần gọi payment provider. App dùng Managed Identity đọc `PaymentApiKey` từ vault lúc startup hoặc qua cache có TTL. Khi provider rotate key, đội vận hành cập nhật secret version và đảm bảo ứng dụng refresh theo quy trình trước khi revoke key cũ.

## 6. Failure scenario & troubleshooting

**Symptom:** chạy local được nhưng production nhận 403 từ Key Vault. **Evidence:** Key Vault diagnostic logs, identity object ID, RBAC assignment và network rules. **Hypothesis:** gán role sai identity hoặc token chưa phản ánh permission mới. **Diagnosis:** kiểm tra identity thực tế của workload, role scope, propagation delay và firewall/Private Endpoint DNS. **Fix:** gán đúng data-plane role và sửa network route; không cấp `Owner` để “chữa nhanh”. **Verification:** test secret read từ đúng deployment environment và theo dõi access-denied metrics.

## 7. Common mistakes

Nhầm Azure RBAC management role với secret data-plane permission; log secret values; fetch Key Vault trên mọi request; coi rotation chỉ là cập nhật vault mà quên consumer cache; dùng cùng identity/quyền cho tất cả environments.

## 8. Alternatives

Environment variables từ secret store/pipeline có thể đủ cho ứng dụng nhỏ nhưng cần bảo vệ deployment logs và rotation. Direct Managed Identity tới Azure SQL/Storage còn tốt hơn khi service hỗ trợ token auth, vì có thể không cần secret trung gian.

## 9. Trade-offs

### Advantages

Giảm credential sprawl, audit rõ identity, quyền và truy cập secrets tập trung.

### Costs / Risks

Phụ thuộc Entra/Key Vault/network, phát sinh latency và chi phí operations, cần rotation plan và fallback behavior khi vault unavailable.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt authentication identity với authorization permission.

### Middle

Cấu hình SDK, identity, RBAC và diagnostics.

### Senior

Thiết kế caching/rotation, kiểm soát network và xử lý dependency outage.

### Technical Lead / Architect

Xác định trust boundary, tách quyền theo workload/environment và ưu tiên passwordless connections khi khả thi.

## 11. Key takeaway

- Managed Identity loại bỏ nhu cầu lưu credential của workload, không loại bỏ mọi secret.
- 403 cần kiểm tra cả identity, RBAC và network.
- Secret rotation phải bao gồm behavior của consumers.

# 8. Queue backlog observability: queue age, throughput và capacity

## 1. What is it?

Queue backlog là lượng công việc chưa được xử lý. Nhưng số messages đợi không đủ mô tả user impact: 10.000 messages có thể bình thường nếu consumers xử lý 20.000/phút, hoặc là sự cố nếu throughput chỉ 100/phút. **Age of oldest work** và processing latency thường gần SLO hơn queue length đơn thuần.

## 2. Why does it exist?

Autoscaling chỉ theo CPU bỏ sót consumer đang chờ downstream I/O hoặc bị rate limit. Khi arrival rate lớn hơn completion rate, backlog tích lũy dù CPU thấp. Quan sát queue cần nối ingestion, processing, retry, DLQ và business latency.

## 3. How does it work?

Theo dõi `arrival_rate`, `completion_rate`, `active_messages`, `dead_letter_count`, `processing_duration` và `message_age_at_start`. Gần đúng: backlog change ≈ arrivals − completions (cần tính cả retry/deferral). Đối với Azure Service Bus, `EnqueuedTime` trên message hỗ trợ đo thời gian đợi khi consumer bắt đầu; metric này phản ánh **processed-message wait**, không tự động đo oldest message đang còn nằm trong queue.

## 4. Practical implementation

```csharp
using System.Diagnostics.Metrics;

static readonly Meter Meter = new("OrderWorkers");
static readonly Histogram<double> WaitSeconds =
    Meter.CreateHistogram<double>("queue_wait_seconds");

async Task HandleAsync(ServiceBusReceivedMessage message, CancellationToken ct)
{
    double wait = Math.Max(0,
        (DateTimeOffset.UtcNow - message.EnqueuedTime).TotalSeconds);
    WaitSeconds.Record(wait);
    await ProcessOrderAsync(message, ct);
}
```

Instrument thêm success/failure/retry counts và queue depth từ broker metrics. Đặt tag có cardinality thấp như `queue` và `outcome`; không tag `messageId` hoặc `userId`.

## 5. Real production scenario

Ứng dụng gửi hóa đơn qua queue. Traffic cuối tháng tăng 4 lần; active message count tăng nhưng không có error. SLO “95% invoices sent within 5 minutes” bị vi phạm khi queue wait p95 lên 12 phút. Đội vận hành tăng consumers có giới hạn, sau đó phát hiện SMTP provider throttle nên điều chỉnh concurrency và retry budget thay vì scale vô hạn.

## 6. Failure scenario & troubleshooting

**Symptom:** queue length tăng và khách hàng nhận email chậm. **Evidence:** arrival rate vượt completion rate; p95 wait tăng; 429 từ provider. **Hypothesis:** downstream capacity thấp hơn demand. **Diagnosis:** phân tách wait time, handler duration, retry delays và lock renewals. **Fix:** throttle ingress hoặc batch, tăng throughput nơi thực sự có headroom, xử lý poison messages. **Verification:** backlog drain rate dương, p95 end-to-end latency hồi phục và DLQ không tăng.

## 7. Common mistakes

Alert chỉ dựa trên queue depth; đo duration handler mà bỏ queue wait; tăng replica khiến provider bị 429 nhiều hơn; quên DLQ; log mỗi messageId thành metric tag; dùng `CompleteMessageAsync` trước khi side effect được bảo đảm.

## 8. Alternatives

Azure Monitor broker metrics cho cái nhìn hạ tầng; OpenTelemetry application metrics cho business latency; Application Insights traces cho từng execution. Dashboard tốt kết hợp cả ba, không thay thế lẫn nhau.

## 9. Trade-offs

### Advantages

Nhận diện backlog trước khi khách hàng phàn nàn; scale theo demand/capacity thực tế.

### Costs / Risks

Metric collection và alerting có chi phí; queue age quan sát từ consumers bị lệch khi consumer ngừng hoàn toàn, cần broker-level signal bổ sung.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue depth khác queue wait time.

### Middle

Instrument wait, duration, outcome và DLQ.

### Senior

Phân tích arrival/completion rates, retry amplification và downstream limits.

### Technical Lead / Architect

Định nghĩa SLO theo thời gian hoàn thành business workflow và capacity plan theo peak traffic.

## 11. Key takeaway

- Backlog count thiếu ngữ cảnh throughput và age.
- Scale consumers không giúp nếu downstream là bottleneck.
- Queue observability phải nối broker metrics với business SLO.

# 9. CMS content model evolution: Optimizely schema và editorial compatibility

## 1. What is it?

Content model là contract giữa editors, CMS database, rendering và content delivery. Trong Optimizely CMS, `PageData`, `BlockData`, `ContentArea` và content type definitions quyết định dữ liệu nào editor có thể nhập và frontend sử dụng. Thay đổi model là **data migration**, không chỉ refactor C#.

## 2. Why does it exist?

Một website marketing sống nhiều năm với hàng nghìn pages. Đổi tên property hoặc xóa block type có thể khiến nội dung cũ không còn render được, dù project compile và deploy thành công. CMS cần thiết kế để hỗ trợ editorial workflow và content evolution an toàn.

## 3. How does it work?

CMS lưu content instances và property values dựa trên definitions/metadata. Template/controller/rendering đọc những values đó. Deploy code mới có thể làm model schema thay đổi; dữ liệu đã publish vẫn tồn tại theo cấu trúc cũ. Đặc biệt phải xem xét content versions, drafts, languages và scheduled publishing khi migrate.

## 4. Practical implementation

```csharp
[ContentType(
    GUID = "9f8c9b7e-1b62-49dd-b85f-447bc8794c13",
    DisplayName = "Product landing page")]
public class ProductLandingPage : PageData
{
    [Display(Name = "Main content", Order = 100)]
    public virtual ContentArea? MainContent { get; set; }

    [Display(Name = "SEO summary", Order = 200)]

```

Khi thay `SeoSummary` bằng structured SEO block, nên giữ property cũ trong giai đoạn chuyển tiếp, viết migration/backfill có kiểm tra và cập nhật templates đọc được cả dữ liệu cũ/mới. Các attributes/namespaces phụ thuộc version Optimizely CMS đang sử dụng.

## 5. Real production scenario

## 6. Failure scenario & troubleshooting

**Symptom:** trang render 200 nhưng thiếu content sau release. **Evidence:** CMS content versions vẫn có data; template mới chỉ đọc property mới. **Hypothesis:** breaking content model change. **Diagnosis:** so sánh content definitions, property data, publish status và renderer mapping. **Fix:** compatibility reader hoặc migration với backup; kiểm tra drafts và localized content. **Verification:** snapshot pages quan trọng, editorial smoke test và content coverage report trước/sau.

## 7. Common mistakes

Đổi GUID content type tùy tiện; xóa property trước khi migrate; test chỉ với content mới; không backup CMS database; migration chỉ cho default language; quên cache/CDN purge khi output đổi; để business logic phụ thuộc trực tiếp editor-facing content type.

## 8. Alternatives

Headless CMS có thể tách delivery và presentation nhưng vẫn phải version schema; composable blocks tăng reuse nhưng dễ làm editorial UI phức tạp. Đôi khi một page type đơn giản tốt hơn cây nested blocks sâu.

### Costs / Risks

Schema coupling với nội dung lịch sử, migration khó rollback, cache/search synchronization và editorial training.

# 10. Expand–Contract database migrations: zero-downtime deployment

## 1. What is it?

Expand–Contract là chiến lược thay đổi database schema theo nhiều bước tương thích: **expand** schema để cả code cũ và mới hoạt động; migrate/backfill dữ liệu; chuyển consumers; cuối cùng **contract** phần cũ. Nó đặc biệt quan trọng khi rolling deployment có nhiều versions chạy đồng thời.

## 2. Why does it exist?

Deploy code và database không diễn ra atomically. Nếu rename/drop column ngay, pod cũ vẫn xử lý requests có thể crash; rollback application cũng không sửa được schema đã bị xóa. Database change phải được thiết kế cho giai đoạn mixed versions, không chỉ trạng thái cuối.

## 3. How does it work?

Ví dụ chuyển `Orders.LegacyRef` sang `Orders.ExternalReference`: (1) add nullable column; (2) deploy code dual-write và fallback-read; (3) backfill theo batches; (4) đo data parity; (5) switch reads; (6) ngừng ghi old column; (7) sau khi mọi consumers đã chuyển, drop old column trong release riêng. Backfill cần tính locks, transaction log và replication lag.

## 4. Practical implementation

```sql
-- Release A: additive schema change
ALTER TABLE dbo.Orders
ADD ExternalReference nvarchar(64) NULL;

-- Backfill theo batch, chạy lặp đến khi @@ROWCOUNT = 0
UPDATE TOP (1000) dbo.Orders
SET ExternalReference = LegacyRef
WHERE ExternalReference IS NULL AND LegacyRef IS NOT NULL;
```

Ứng dụng trong giai đoạn chuyển tiếp đọc `ExternalReference ?? LegacyRef` và ghi cả hai khi có thể. Trước khi thêm `NOT NULL` hoặc drop `LegacyRef`, xác nhận dữ liệu, traffic và các consumers ngoài ứng dụng (reports, ETL, jobs).

## 5. Real production scenario

Hệ thống timesheet có 8 App Service instances và worker background cùng dùng bảng Approval. Một schema migration destructive chạy trước rolling deploy khiến các instances chưa update trả 500. Với Expand–Contract, schema additive đi trước, code chạy được cả hai versions, contract chỉ thực hiện sau khi fleet và jobs đã chuyển.

## 6. Failure scenario & troubleshooting

**Symptom:** sau release, một phần requests 500 với “Invalid column name” hoặc “column not found”. **Evidence:** deployment timeline, app version labels, SQL errors và migration history. **Hypothesis:** migration/code version mismatch. **Diagnosis:** đối chiếu compatibility matrix của code N/N−1 với schema S/S+1. **Fix:** khôi phục compatibility bằng additive change hoặc rollback code nếu schema còn tương thích; tránh rollback database destructive trong panic. **Verification:** smoke test cả old/new app versions, batch backfill metrics và query error rates.

## 7. Common mistakes

Drop column trong cùng release đổi reader; backfill một transaction khổng lồ; áp dụng NOT NULL trước khi tất cả writers đã cập nhật; không biết các ETL/reporting consumers; cho mọi pod tự chạy migration đồng thời; cho rằng rollback app đồng nghĩa rollback data.

## 8. Alternatives

Maintenance window có thể hợp lý cho hệ thống nhỏ có downtime được chấp nhận. Blue-Green database phức tạp hơn và có vấn đề data synchronization. Expand–Contract thường là mặc định thực tế cho online schema evolution, không phải công thức miễn phí.

## 9. Trade-offs

### Advantages

Cho phép rolling deployments, rollback code an toàn hơn và kiểm soát data migration.

### Costs / Risks

Nhiều releases, dual-write complexity, temporary storage overhead và yêu cầu observability về data parity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu vì sao code cũ và code mới có thể cùng tồn tại sau deploy.

### Middle

Viết additive migrations và backfill idempotent, test compatibility.

### Senior

Phân tích locks, log growth, mixed-version behavior và rollback path.

### Technical Lead / Architect

Quy định release sequencing, schema ownership, migration approval và điều kiện contract có thể thực hiện an toàn.

## 11. Key takeaway

- Database schema là contract giữa nhiều application versions và consumers.
- Expand trước, backfill/verify, rồi mới contract.
- Rollback phải được thiết kế từ đầu, không giả định migration nào cũng đảo ngược được.
