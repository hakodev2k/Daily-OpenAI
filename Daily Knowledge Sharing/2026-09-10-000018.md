# 1. C# `IAsyncDisposable` + `await using`: giải phóng async resource đúng cách mà không block thread trong cleanup

## 1. What is it?

`IAsyncDisposable` là contract dành cho resource cần cleanup bằng asynchronous I/O. Thay vì chỉ có:

```csharp
void Dispose();
```

object có thể cung cấp:

```csharp
ValueTask DisposeAsync();
```

Consumer dùng `await using` để compiler bảo đảm `DisposeAsync()` được gọi khi scope kết thúc, kể cả khi có exception.

Mental model:

```text
Acquire resource
      ↓
use asynchronously
      ↓
await cleanup I/O
      ↓
leave scope
```

Điểm quan trọng là cleanup itself có thể cần flush network buffer, complete protocol handshake hoặc asynchronously close underlying resource.

## 2. Why does it exist?

Một số resource không thể cleanup hiệu quả bằng synchronous API. Ví dụ stream có buffered data cần flush tới storage, async transaction cần rollback/close qua network, hoặc writer cần complete asynchronous pipeline.

Nếu ép asynchronous cleanup vào `Dispose()` bằng `.Wait()` hoặc `.GetAwaiter().GetResult()`, application có thể block thread, tăng thread-pool starvation và trong một số synchronization context cũ còn có nguy cơ deadlock.

## 3. How does it work?

Class có thể implement `IAsyncDisposable`:

```csharp
public sealed class AuditBatchWriter : IAsyncDisposable
{
    private readonly Stream _stream;

    public AuditBatchWriter(Stream stream) => _stream = stream;

    public async ValueTask DisposeAsync()
    {
        await _stream.FlushAsync();
        await _stream.DisposeAsync();
    }
}
```

Consumer:

```csharp
await using var writer = new AuditBatchWriter(stream);
await WriteAuditEventsAsync(writer, ct);
```

Compiler đặt cleanup vào logic tương đương `finally` và await nó trước khi method thực sự rời scope.

## 4. Practical implementation

Nếu class sở hữu cả synchronous và asynchronous resources, pattern cần rõ ownership:

```csharp
public sealed class ExportSession : IDisposable, IAsyncDisposable
{
    private readonly Stream _stream;
    private bool _disposed;

    public ExportSession(Stream stream) => _stream = stream;

    public void Dispose()
    {
        if (_disposed) return;
        _stream.Dispose();
        _disposed = true;
    }

    public async ValueTask DisposeAsync()
    {
        if (_disposed) return;
        await _stream.DisposeAsync();
        _disposed = true;
        GC.SuppressFinalize(this);
    }
}
```

Không phải object nào implement cả hai interfaces cũng có semantics giống nhau. Caller nên dùng async path khi đang ở async workflow và resource có async cleanup thực sự.

## 5. Real production scenario

Một service export dữ liệu lớn ra encrypted cloud stream. Code cũ dùng `using`, khiến final flush chạy synchronously và giữ request thread trong nhiều trăm milliseconds khi storage latency tăng. Dưới concurrent exports, worker threads bị giữ trong cleanup thay vì phục vụ requests khác.

Chuyển sang end-to-end async write + `await using` giúp cleanup không block thread trong thời gian chờ I/O.

## 6. Failure scenario & troubleshooting

**Symptom** → request latency tăng mạnh ở cuối request dù business processing đã hoàn tất.

**Evidence** → trace/profiler cho thấy nhiều threads đứng ở `Dispose()` hoặc synchronous flush/close.

**Hypothesis** → asynchronous resource đang bị cleanup theo synchronous path.

**Diagnosis** → kiểm tra object ownership, `using` vs `await using`, `.Wait()`, `.Result`, `.GetAwaiter().GetResult()` và resource implementation.

**Fix** → propagate async cleanup đến caller; dùng `await using`; tránh sync-over-async.

**Verification** → load test với artificial storage/network latency và theo dõi thread-pool queue length, request p95/p99 và cleanup span duration.

## 7. Common mistakes

* Implement `DisposeAsync()` nhưng bên trong vẫn gọi blocking I/O.
* Gọi cả `Dispose()` rồi `DisposeAsync()` cho cùng resource mà không hiểu idempotency.
* Dùng `await using` cho object không thực sự cần async cleanup rồi kỳ vọng performance tự tốt hơn.
* Quên ownership: dispose resource được DI container hoặc caller sở hữu.
* Nuốt exception trong cleanup khiến dữ liệu chưa flush bị coi như thành công.

## 8. Alternatives

`IDisposable` vẫn đúng cho memory/native handles hoặc cleanup không cần asynchronous I/O. Explicit `CompleteAsync()` có thể phù hợp nếu “complete business operation” khác với “release resource”; không nên nhét domain success semantics vào `DisposeAsync()`.

## 9. Trade-offs

### Advantages

* Không block thread trong I/O-bound cleanup.
* Scope ownership rõ với `await using`.
* Tích hợp tự nhiên với async pipeline.

### Costs / Risks

* Async cleanup lan lên call stack.
* Exception trong dispose làm control flow phức tạp hơn.
* Dual `IDisposable`/`IAsyncDisposable` implementation cần semantics nhất quán.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết `using` và `await using` phục vụ hai cleanup models khác nhau.

### Middle

Propagate async disposal đúng ownership boundary.

### Senior

Phân tích sync-over-async, thread-pool impact và exception semantics trong cleanup.

### Technical Lead / Architect

Đặt guideline resource lifecycle cho DB, stream, messaging và SDK wrappers để team không vô tình block request threads trong cleanup.

## 11. Key takeaway

* Async workflow có thể cần async cleanup.
* `await using` hữu ích khi release resource thực sự chờ I/O.
* Không dùng sync-over-async để “giấu” asynchronous disposal.

# 2. ASP.NET Core Partitioned Rate Limiting: giới hạn traffic theo user/API key thay vì throttle toàn hệ thống như nhau

## 1. What is it?

Rate limiting kiểm soát số request được phép đi qua trong một khoảng thời gian hoặc theo lượng concurrency. ASP.NET Core cung cấp rate-limiting middleware với các thuật toán như fixed window, sliding window, token bucket và concurrency limiter.

Partitioned rate limiting thêm một ý quan trọng: quota được tách theo key, ví dụ:

```text
user:42      → quota riêng
api-key:abc  → quota riêng
anonymous-ip → quota riêng
```

Như vậy một noisy client không tiêu hết capacity của mọi client khác.

## 2. Why does it exist?

Global limiter kiểu “1000 requests/second cho cả API” có thể bảo vệ process nhưng không đảm bảo fairness. Một integration lỗi có thể bắn 900 RPS và khiến hàng trăm users bình thường tranh nhau 100 RPS còn lại.

Partitioning cho phép align quota với tenant, subscription plan, endpoint cost hoặc security identity.

## 3. How does it work?

Ví dụ limiter theo authenticated user:

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(ctx =>
    {
        var key = ctx.User.Identity?.IsAuthenticated == true
            ? ctx.User.FindFirst("sub")?.Value ?? "authenticated"
            : ctx.Connection.RemoteIpAddress?.ToString() ?? "anonymous";

        return RateLimitPartition.GetTokenBucketLimiter(
            key,
            _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 20,
                ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                QueueLimit = 0,
                AutoReplenishment = true
            });
    });
});
```

Middleware:

```csharp
app.UseRateLimiter();
```

Partition key là một phần của security/resource model, không chỉ là string để group metrics.

## 4. Practical implementation

Một API public có thể cần nhiều policies:

```text
Login endpoint       → strict limiter theo IP + account dimension
Read API             → token bucket theo API key
Expensive export     → concurrency limiter theo tenant
Internal callback    → policy riêng dựa trên trusted identity
```

Response khi reject nên dùng `429 Too Many Requests` và có metadata hợp lý như `Retry-After` nếu policy có thể tính được.

Rate limiting phải nằm sau bước đủ sớm để xác định identity, nhưng không nên để attacker buộc hệ thống làm quá nhiều expensive work trước khi limiter chạy.

## 5. Real production scenario

Một SaaS có endpoint search đắt. Một enterprise integration vô tình bỏ debounce và gửi request mỗi keystroke từ hàng nghìn browser sessions. Database CPU tăng, latency của tenants khác vượt SLO.

Per-tenant token bucket giữ integration lỗi trong quota của chính tenant đó, trong khi global infrastructure limiter vẫn đóng vai trò “last line of defense”.

## 6. Failure scenario & troubleshooting

**Symptom** → users hợp lệ nhận `429` dù traffic cá nhân thấp.

**Evidence** → telemetry cho thấy nhiều users bị map vào cùng partition key như `authenticated` hoặc một proxy IP.

**Hypothesis** → key extraction bị fallback quá rộng.

**Diagnosis** → log hashed/opaque partition identifier, auth state, endpoint và limiter decision; kiểm tra reverse-proxy forwarding setup.

**Fix** → dùng stable identity claim/API key ID; chỉ dùng source IP khi topology và trust boundaries rõ.

**Verification** → load test nhiều tenants: một tenant vượt quota không được làm tăng reject rate của tenants khác.

## 7. Common mistakes

* Rate-limit theo raw IP sau reverse proxy mà chưa cấu hình trusted forwarded headers.
* Dùng user-supplied header làm partition key mà không authenticate.
* Một policy giống nhau cho cheap GET và expensive report generation.
* Queue quá dài trong limiter, biến overload thành latency explosion.
* Xem rate limiting là thay thế cho authorization hoặc WAF.

## 8. Alternatives

API gateway/Azure API Management có thể enforce quotas trước application. Reverse proxy/CDN phù hợp coarse traffic protection. Application-level limiter vẫn hữu ích khi quota cần hiểu user, tenant hoặc business cost.

## 9. Trade-offs

### Advantages

* Fairness tốt hơn global throttling.
* Cô lập noisy tenant/client.
* Policy có thể phản ánh subscription/business model.

### Costs / Risks

* Partition cardinality có thể lớn.
* In-memory limiter trên nhiều replicas không tự tạo cluster-wide quota tuyệt đối.
* Identity/key selection sai có thể gây bypass hoặc false throttling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `429` và các limiter algorithms cơ bản.

### Middle

Biết tạo named/partitioned policies và chọn key hợp lý.

### Senior

Phân tích fairness, distributed replicas, proxy identity và overload behavior.

### Technical Lead / Architect

Thiết kế quota model xuyên edge gateway → application → downstream capacity với SLO và commercial plan rõ ràng.

## 11. Key takeaway

* Rate limit nên bám theo resource ownership, không chỉ tổng RPS.
* Partition key là trust decision.
* Application limiter không tự trở thành distributed global quota khi scale nhiều replicas.

# 3. EF Core Single Query vs Split Query: tránh Cartesian explosion mà vẫn kiểm soát consistency và round-trip

## 1. What is it?

Khi `Include` nhiều collection navigations, EF Core có thể load object graph bằng một SQL query lớn hoặc chia thành nhiều SQL queries.

Single query:

```text
Parent JOIN ChildrenA JOIN ChildrenB
```

Split query:

```text
Query Parents
Query ChildrenA
Query ChildrenB
```

EF Core hỗ trợ `AsSplitQuery()` và `AsSingleQuery()` để kiểm soát strategy.

## 2. Why does it exist?

Hai collections 1:N khi join cùng lúc có thể tạo Cartesian multiplication. Một parent có 20 items và 30 comments có thể tạo tới 600 joined rows cho chỉ một parent, lặp lại columns của parent rất nhiều lần.

Split query giảm duplication nhưng đổi lại thêm database round-trips và có consistency considerations giữa các queries.

## 3. How does it work?

Ví dụ:

```csharp
var orders = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Events)
    .AsSplitQuery()
    .Where(x => x.CustomerId == customerId)
    .ToListAsync(ct);
```

EF chạy query principal trước, sau đó query dependent collections và fix-up relations trong memory.

Với single query, database trả joined result lớn rồi EF materialize/deduplicate entities.

## 4. Practical implementation

Không chọn global default chỉ dựa trên slogan. Đo query shape:

```csharp
var query = db.Orders
    .AsNoTracking()
    .Where(x => x.CreatedAt >= from)
    .Select(x => new OrderSummaryDto
    {
        Id = x.Id,
        ItemCount = x.Items.Count,
        LatestEvent = x.Events
            .OrderByDescending(e => e.CreatedAt)
            .Select(e => e.Type)
            .FirstOrDefault()
    });
```

Projection thường tốt hơn load cả aggregate khi screen chỉ cần summary.

Nếu thật sự cần graph lớn, benchmark `AsSingleQuery()` và `AsSplitQuery()` trên production-like cardinality.

## 5. Real production scenario

Admin order-detail page include Items, Payments, AuditEntries và Attachments. Test data mỗi collection chỉ có 1–2 row nên single query nhanh. Production orders có hàng trăm audit entries và hàng chục items; payload SQL bùng nổ, memory allocation tăng và timeout xuất hiện.

Split query giảm rows truyền qua network rất mạnh. Sau đó team còn cải thiện thêm bằng cách tách audit history thành endpoint paginated thay vì load toàn bộ graph.

## 6. Failure scenario & troubleshooting

**Symptom** → query dùng `Include` nhìn đơn giản nhưng network bytes và materialization time rất cao.

**Evidence** → generated SQL có nhiều sibling collection joins; actual result rows lớn hơn entity count nhiều lần.

**Hypothesis** → Cartesian explosion.

**Diagnosis** → inspect `ToQueryString()`, SQL execution plan, row counts và profiler allocations.

**Fix** → projection, pagination, `AsSplitQuery()` hoặc redesign query boundary.

**Verification** → so sánh DB reads, transferred rows/bytes, application allocations và p95 latency.

## 7. Common mistakes

* Dùng `Include` như “eager load mọi thứ cho chắc”.
* Chuyển tất cả queries sang split mà không đo round-trip impact.
* Bỏ qua consistency nếu data có thể đổi giữa các split queries.
* Load collection lớn chỉ để lấy `Count`.
* Benchmark với seed data quá nhỏ.

## 8. Alternatives

Projection DTO là lựa chọn mạnh nhất cho read models. Explicit loading phù hợp conditional branches. CQRS/read-optimized queries có thể tránh aggregate-loading hoàn toàn cho reporting screens.

## 9. Trade-offs

### Single query

* Ít round-trip hơn.
* Snapshot trong một SQL statement.
* Có nguy cơ row multiplication lớn.

### Split query

* Giảm duplication với nhiều collections.
* Nhiều SQL round-trips hơn.
* Có thể thấy state thay đổi giữa statements nếu không dùng isolation phù hợp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết `Include` tạo SQL thực, không phải free navigation loading.

### Middle

Biết `AsSplitQuery`, projection và đọc generated SQL.

### Senior

Phân tích cardinality, consistency, network payload và materialization cost.

### Technical Lead / Architect

Đặt read-model conventions để UI không mặc định load aggregate graph khổng lồ qua ORM.

## 11. Key takeaway

* Nhiều sibling collections có thể làm single query phình theo cấp số nhân của cardinality.
* Split query là trade-off, không phải universal fix.
* Projection đúng use case thường tốt hơn tranh luận single vs split.

# 4. SQL Server Query Store: bắt plan regression bằng evidence thay vì chữa slow query theo cảm tính

## 1. What is it?

Query Store lưu lịch sử query text, execution plans và runtime statistics theo thời gian. Nó giúp trả lời các câu hỏi như:

```text
Query nào vừa chậm đi?
Plan hiện tại khác plan tuần trước thế nào?
Regression xảy ra từ lúc nào?
Plan nào từng tốt hơn?
```

Nó biến performance troubleshooting từ snapshot hiện tại thành historical analysis.

## 2. Why does it exist?

Một query có thể chạy tốt nhiều tháng rồi đột nhiên chậm sau statistics update, schema/index change, data skew hoặc plan recompilation. Khi DBA/developer vào kiểm tra vài giờ sau, bad plan có thể đã biến mất khỏi plan cache.

Query Store giữ lịch sử để điều tra regression sau sự kiện.

## 3. How does it work?

Query Store capture normalized query, plans và runtime metrics theo intervals. Có thể tìm top regressions và trong trường hợp phù hợp force một known-good plan trong khi điều tra root cause.

Conceptually:

```text
Query Q
 ├─ Plan A → avg 20 ms
 └─ Plan B → avg 1.8 s  ← regression
```

Plan forcing là mitigation, không tự giải thích vì sao optimizer chọn plan xấu.

## 4. Practical implementation

Workflow thực tế:

1. Xác định time window sự cố.
2. Tìm queries có duration/CPU/read regression.
3. So sánh old/new plan.
4. Kiểm tra estimated vs actual rows, indexes, parameter values, stats.
5. Force known-good plan nếu cần giảm impact tức thời.
6. Sửa root cause và theo dõi lại.

Ví dụ root cause có thể là parameter-sensitive workload, stale statistics hoặc index bị drop.

## 5. Real production scenario

Endpoint invoice search từ 80 ms tăng lên 4 giây sau nightly load. Không có code deploy. Query Store cho thấy lúc 02:10 plan chuyển từ seek + nested loops sang scan + hash path do row estimates thay đổi mạnh. Team tạm force plan cũ để phục hồi SLO rồi sửa statistics/index strategy phù hợp với distribution mới.

## 6. Failure scenario & troubleshooting

**Symptom** → production chậm nhưng local/staging query vẫn nhanh.

**Evidence** → Query Store có nhiều plans với runtime profile khác hẳn nhau.

**Hypothesis** → plan regression hoặc parameter-sensitive behavior.

**Diagnosis** → so sánh plans, compile/runtime parameters, waits, row estimates và Query Store intervals.

**Fix** → address stats/index/query/parameterization root cause; dùng plan forcing như controlled mitigation nếu cần.

**Verification** → bỏ forcing khi phù hợp và xác nhận optimizer chọn plan ổn định trên representative parameters.

## 7. Common mistakes

* Force plan rồi coi incident đã “fix xong”.
* Chỉ nhìn average duration, bỏ p95/p99 hoặc workload mix.
* Không kiểm soát Query Store storage/retention.
* Thấy plan khác là kết luận ngay plan regression mà không xem data volume.
* Tuning trên query text copy từ log nhưng không dùng production parameters.

## 8. Alternatives

Extended Events phù hợp low-level event capture. DMVs cho snapshot hiện tại. Application tracing cung cấp request context. Query Store đặc biệt mạnh khi cần historical plan/runtime comparison ngay trong SQL Server.

## 9. Trade-offs

### Advantages

* Lịch sử plan và runtime metrics.
* Hữu ích khi sự cố đã qua.
* Có controlled mitigation qua plan forcing.

### Costs / Risks

* Có storage/write overhead.
* Retention/configuration cần quản lý.
* Force plan lâu dài có thể trở thành technical debt khi data distribution thay đổi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết execution plan có thể thay đổi dù code SQL không đổi.

### Middle

Dùng Query Store để xác định regression window và plans.

### Senior

Kết hợp plan history với statistics, parameter sensitivity và workload evidence.

### Technical Lead / Architect

Chuẩn hóa database performance incident workflow thay vì để team “thêm index cho tới khi nhanh”.

## 11. Key takeaway

* Query Store cung cấp timeline của performance, không chỉ snapshot.
* Plan forcing là mitigation có kiểm soát, không phải root-cause fix.
* Tuning tốt bắt đầu bằng evidence của plan + workload thực tế.

# 5. Elasticsearch Point in Time + `search_after`: deep pagination ổn định mà không trả giá bằng `from + size`

## 1. What is it?

Pagination phổ biến bằng `from` + `size` yêu cầu Elasticsearch thu thập và sort đủ kết quả trước offset. Với page rất sâu, chi phí tăng mạnh.

`search_after` dùng sort values của item cuối page trước làm cursor. Point in Time (PIT) giữ một consistent search view đủ lâu để nhiều page không bị thay đổi thứ tự khi index tiếp tục nhận writes.

```text
Page 1 → last sort = [2026-09-10T00:00:00Z, "id-123"]
Page 2 → search_after same values
```

## 2. Why does it exist?

Nếu user export 500.000 search hits bằng page size 1000, `from=499000&size=1000` rất tốn memory/CPU trên shards vì hệ thống phải xem xét lượng kết quả lớn trước khi bỏ 499.000 entries.

Ngoài ra, nếu documents được insert/update giữa các pages, offset pagination có thể duplicate hoặc skip items.

## 3. How does it work?

Mở PIT:

```json
POST /products/_pit?keep_alive=2m
```

Sau đó search với stable sort:

```json
{
  "size": 1000,
  "pit": {
    "id": "PIT_ID",
    "keep_alive": "2m"
  },
  "sort": [
    { "updatedAt": "asc" },
    { "_shard_doc": "asc" }
  ]
}
```

Page sau gửi `search_after` từ sort values cuối page trước.

## 4. Practical implementation

Cursor nên là opaque token do backend encode thay vì để client tự sửa sort values.

Backend cần:

```text
query hash / filters
sort definition
PIT id hoặc session state
last sort values
expiry
```

Nếu cursor được reuse với filter khác, semantics có thể sai; vì vậy bind cursor vào query context hoặc ký token.

## 5. Real production scenario

Một compliance export search qua 3 triệu audit documents. Offset pagination khiến coordinator heap tăng và export càng về cuối càng chậm. Chuyển sang PIT + `search_after` giúp cost mỗi page ổn định hơn và tránh missing/duplicate results trong lúc index vẫn ingest events mới.

## 6. Failure scenario & troubleshooting

**Symptom** → pagination thỉnh thoảng duplicate/missing documents hoặc cursor trả lỗi sau vài phút.

**Evidence** → không dùng PIT hoặc PIT hết `keep_alive`; sort field không unique/stable.

**Hypothesis** → search view thay đổi hoặc cursor thiếu deterministic tie-breaker.

**Diagnosis** → kiểm tra sort definition, PIT lifecycle, query mutation và returned sort values.

**Fix** → dùng PIT, stable multi-field sort, refresh `keep_alive` phù hợp và cursor validation.

**Verification** → concurrent indexing trong lúc paginate toàn result set; kiểm tra IDs không duplicate/missing trong snapshot.

## 7. Common mistakes

* Dùng `from + size` cho arbitrary deep export.
* `search_after` chỉ sort theo timestamp có nhiều duplicate values mà không tie-break.
* Giữ PIT quá lâu không cần thiết.
* Cho client đổi filter nhưng reuse cursor cũ.
* Dùng pagination search như job export nhiều giờ thay vì asynchronous export pipeline khi scale quá lớn.

## 8. Alternatives

Offset pagination vẫn phù hợp shallow UI pages. Scroll API từng dùng nhiều cho bulk extraction nhưng `search_after` + PIT thường phù hợp hơn cho modern pagination. Với long-running exports, background job + object storage có thể tốt hơn interactive API.

## 9. Trade-offs

### Advantages

* Deep-page cost ổn định hơn offset.
* Snapshot consistency tốt hơn với PIT.
* Cursor model phù hợp large result sets.

### Costs / Risks

* Không jump trực tiếp tới page 5000 dễ dàng.
* Cursor lifecycle phức tạp hơn.
* PIT giữ search context/resources trong cluster.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu offset pagination không scale vô hạn.

### Middle

Biết `search_after`, stable sort và PIT lifecycle.

### Senior

Thiết kế opaque cursor, snapshot consistency và export boundaries.

### Technical Lead / Architect

Chọn search pagination contract dựa trên UX, dataset size và cluster resource budget thay vì copy relational paging semantics.

## 11. Key takeaway

* `search_after` là cursor traversal, không phải offset khác tên.
* PIT giúp nhiều page nhìn cùng một logical snapshot.
* Stable sort và tie-breaker là điều kiện correctness, không chỉ performance optimization.

# 6. Azure Blob Storage ETag + conditional writes: optimistic concurrency cho object storage và tránh lost update

## 1. What is it?

Blob Storage trả ETag đại diện cho version hiện tại của object. Client có thể gửi conditional operation như `If-Match` để update chỉ khi ETag vẫn giống lúc client đọc.

Mental model:

```text
Read blob → ETag = "v7"
Client A writes If-Match "v7" → success, new ETag "v8"
Client B writes If-Match "v7" → precondition failed
```

Đây là optimistic concurrency cho object storage.

## 2. Why does it exist?

Nếu hai workers cùng đọc JSON config blob rồi cả hai update, last write wins có thể âm thầm làm mất thay đổi của worker trước.

Object storage không phải relational row nhưng lost update vẫn là concurrency bug.

## 3. How does it work?

Azure SDK cho phép set access conditions:

```csharp
var download = await blob.DownloadContentAsync(cancellationToken: ct);
var etag = download.Value.Details.ETag;

var updated = Transform(download.Value.Content);

await blob.UploadAsync(
    BinaryData.FromObjectAsJson(updated),
    new BlobUploadOptions
    {
        Conditions = new BlobRequestConditions
        {
            IfMatch = etag
        }
    },
    ct);
```

Nếu blob đã đổi, service trả precondition failure thay vì overwrite.

## 4. Practical implementation

Conflict handler cần business policy:

```text
412 Precondition Failed
   ↓
reload latest blob
   ↓
re-evaluate intended change
   ↓
merge/retry only if still valid
```

Không nên auto retry bằng cách re-upload cùng payload cũ, vì payload đó được tính từ stale state.

Với create-if-not-exists, `If-None-Match: *` giúp biến “check rồi create” thành atomic conditional write.

## 5. Real production scenario

Hai scheduler instances cập nhật checkpoint blob chứa processed offsets. Không có ETag condition, instance chậm ghi state cũ sau instance nhanh và làm checkpoint lùi lại. Job sau restart xử lý lại lượng dữ liệu lớn.

Conditional write biến race thành explicit conflict để worker reload và merge progress theo monotonic rule.

## 6. Failure scenario & troubleshooting

**Symptom** → blob đôi lúc “quay lại” state cũ dù logs đều báo upload thành công.

**Evidence** → multiple writers, không có conditional headers, timestamps cho thấy stale writer commit sau.

**Hypothesis** → lost update do last-write-wins.

**Diagnosis** → log ETag before/after, writer identity và operation intent.

**Fix** → `IfMatch`, immutable object naming, lease hoặc single-writer design tùy use case.

**Verification** → concurrency test nhiều writers với injected delay; stale writer phải fail thay vì overwrite.

## 7. Common mistakes

* Dùng `ExistsAsync()` rồi `UploadAsync()` và nghĩ đó là atomic.
* Catch 412 rồi retry payload stale.
* Xem ETag là business version có format tự kiểm soát.
* Dùng blob lease cho mọi conflict dù optimistic condition đủ dùng.
* Không thiết kế idempotency cho side effects xung quanh blob write.

## 8. Alternatives

Blob lease phù hợp exclusive writer trong một khoảng thời gian. Immutable/versioned object names loại bỏ overwrite hoàn toàn. Database phù hợp hơn nếu cần multi-record transaction/query semantics.

## 9. Trade-offs

### Advantages

* Lightweight concurrency control ngay tại storage service.
* Không cần distributed lock cho nhiều read-modify-write workflows.
* Conflict được phát hiện rõ.

### Costs / Risks

* Caller phải resolve conflict.
* ETag chỉ bảo vệ object/version scope tương ứng.
* Multi-object atomicity vẫn không có.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu last-write-wins có thể làm mất dữ liệu.

### Middle

Dùng ETag và conditional request đúng SDK semantics.

### Senior

Thiết kế merge/idempotency và chọn optimistic vs lease.

### Technical Lead / Architect

Định nghĩa consistency strategy cho object-based state, checkpoints, manifests và generated artifacts.

## 11. Key takeaway

* ETag biến overwrite race thành explicit conflict.
* Conditional writes mạnh hơn “check rồi write”.
* Retry concurrency conflict phải re-evaluate state, không chỉ gửi lại stale payload.

# 7. Docker BuildKit: layer cache, cache mount và secret mount để build nhanh mà không nhét credential vào image

## 1. What is it?

BuildKit là modern Docker build engine cung cấp dependency-aware build graph, improved caching và specialized mounts cho cache/secrets/SSH.

Ba concepts dễ nhầm:

```text
Layer cache   → reuse Dockerfile step output
Cache mount   → reuse mutable build cache giữa builds
Secret mount  → expose secret tạm thời cho một RUN, không bake vào layer
```

## 2. Why does it exist?

CI build .NET/Node thường chậm vì mỗi run tải toàn bộ NuGet/npm packages. Team đôi khi giải quyết bằng cách copy token vào build arg hoặc config file, vô tình để credential xuất hiện trong image history/layers.

BuildKit giúp vừa tăng cache efficiency vừa tách secret khỏi artifact.

## 3. How does it work?

Dockerfile nên copy dependency manifests trước source để giữ restore layer cache:

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

COPY MyApp.csproj ./
RUN dotnet restore

COPY . .
RUN dotnet publish -c Release -o /app/publish --no-restore
```

Cache mount có thể giữ NuGet packages:

```dockerfile
RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet restore
```

Secret mount:

```dockerfile
RUN --mount=type=secret,id=nuget_config,target=/root/.nuget/NuGet.Config \
    dotnet restore
```

Secret chỉ tồn tại trong step thay vì trở thành file của final layer.

## 4. Practical implementation

Multi-stage build giảm final image surface:

```dockerfile
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApp.dll"]
```

CI nên dùng external cache exporter/importer khi runners ephemeral; local cache mount không giúp nếu mỗi build chạy trên máy sạch và không persist cache backend.

Build context cũng cần `.dockerignore` để tránh invalidate cache vì files không liên quan.

## 5. Real production scenario

Pipeline monorepo mất 12 phút vì `COPY . .` nằm trước `dotnet restore`; bất kỳ README/frontend change nào cũng invalidates restore layer. Team reorder manifests, dùng cache mount và remote build cache, giảm build xuống vài phút. Đồng thời token private feed được chuyển từ `ARG` sang BuildKit secret.

## 6. Failure scenario & troubleshooting

**Symptom** → build cache gần như không hit dù dependency files không đổi.

**Evidence** → Docker build output cho thấy restore step luôn rerun.

**Hypothesis** → layer trước restore bị invalidated bởi broad `COPY` hoặc changing build args.

**Diagnosis** → inspect Dockerfile order, build context, cache source và CI runner lifecycle.

**Fix** → copy manifests trước, source sau; dùng `.dockerignore`; configure cache import/export; dùng dedicated cache mounts.

**Verification** → chạy clean build rồi no-code/dependency-unchanged build; restore/download steps phải reuse cache như mong đợi.

## 7. Common mistakes

* `COPY . .` quá sớm.
* Dùng `ARG NUGET_TOKEN` rồi ghi token vào config trong layer.
* Copy SDK/build tools sang runtime image.
* Cache package folder nhưng quên lockfile/version determinism.
* Assume CI ephemeral runner tự có local Docker cache giữa runs.

## 8. Alternatives

CI-native dependency cache có thể cache NuGet/npm ngoài Docker. Prebuilt builder images hữu ích với toolchains ổn định. Không phải project nào cũng cần BuildKit-specific optimization nếu build vốn đã ngắn.

## 9. Trade-offs

### Advantages

* Build nhanh hơn nhờ caching tốt.
* Secret handling an toàn hơn build args/files.
* Final image nhỏ hơn qua multi-stage build.

### Costs / Risks

* Dockerfile/CI cache topology phức tạp hơn.
* Remote cache tốn storage/network.
* Cache không đúng key có thể tạo surprising stale behavior nếu build không deterministic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu layer cache và multi-stage build.

### Middle

Sắp xếp Dockerfile để restore cache hiệu quả và dùng `.dockerignore`.

### Senior

Thiết kế BuildKit cache/secret strategy cho CI runners và private feeds.

### Technical Lead / Architect

Chuẩn hóa secure reproducible builds, SBOM/signing pipeline và artifact provenance thay vì chỉ tối ưu build time.

## 11. Key takeaway

* Docker cache hiệu quả phụ thuộc thứ tự inputs, không phải magic của Docker daemon.
* Build secret không được bake vào layer/history.
* Tối ưu build phải đi cùng reproducibility và supply-chain security.

# 8. Kubernetes HPA: resource requests, stabilization window và vì sao autoscaling có thể tự tạo oscillation

## 1. What is it?

Horizontal Pod Autoscaler (HPA) điều chỉnh số replicas dựa trên metrics như CPU, memory hoặc custom/external metrics.

Với CPU utilization, HPA không chỉ nhìn raw CPU usage; nó so usage với requested CPU của pods.

Ví dụ:

```text
request = 500m CPU
actual  = 400m CPU
utilization ≈ 80%
```

Nếu target là 60%, HPA có thể scale out.

## 2. Why does it exist?

Traffic thay đổi theo thời gian. Fix 20 replicas cho peak traffic lãng phí resource; fix 3 replicas cho average traffic có thể overload khi spike.

Autoscaling điều chỉnh capacity theo demand, nhưng chỉ tốt khi metric phản ánh load và application có thể scale theo metric đó.

## 3. How does it work?

Simplified ratio:

```text
desired replicas ≈ current replicas × current metric / target metric
```

HPA còn có tolerance, scale policies và stabilization windows để tránh thay đổi replicas quá nhanh.

Ví dụ behavior:

```yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300
  scaleUp:
    policies:
      - type: Percent
        value: 100
        periodSeconds: 60
```

## 4. Practical implementation

Resource requests phải realistic:

```yaml
resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: 1000m
    memory: 512Mi
```

Nếu request CPU đặt cực thấp, moderate usage nhìn thành utilization cực cao và HPA scale quá mức. Nếu request quá cao, HPA có thể không scale khi pod thực tế đã bottleneck ở dependency khác.

Đối với queue workers, queue depth hoặc message age thường là metric tốt hơn CPU.

## 5. Real production scenario

API target CPU 60%, nhưng mỗi pod startup mất 90 giây để warm caches. Traffic spike khiến HPA scale up; khi pods mới ready thì spike đã giảm. Ngay sau đó HPA scale down, rồi cache cold làm CPU tăng lại và hệ thống oscillate.

Team thêm startup/readiness đúng, scale-down stabilization và chọn metric gần workload hơn, giảm replica thrashing.

## 6. Failure scenario & troubleshooting

**Symptom** → replicas lên xuống liên tục nhưng latency không cải thiện.

**Evidence** → CPU target chạm liên tục; downstream DB đã saturation; pods mới chỉ làm tăng concurrent pressure.

**Hypothesis** → bottleneck không nằm ở compute capacity của pods hoặc scaling signal sai.

**Diagnosis** → correlate HPA events với request rate, p95 latency, DB connection saturation, queue depth và pod startup time.

**Fix** → chọn metric phù hợp, cap max replicas theo downstream budget, stabilization policies và capacity planning downstream.

**Verification** → load test ramp/spike/decay, không chỉ steady-state throughput.

## 7. Common mistakes

* Không set resource requests rồi kỳ vọng CPU utilization HPA hoạt động đúng.
* Autoscale API vô hạn trong khi DB connection pool có hard cap.
* Scale theo memory cho workload mà memory không giảm sau request.
* Không tính startup latency.
* Scale-down quá nhanh gây cache churn và connection churn.

## 8. Alternatives

KEDA phù hợp event/queue-driven scaling. Vertical Pod Autoscaler giải quyết resource sizing khác với replica count. Scheduled scaling hữu ích workload rất predictable. Manual fixed replicas có thể đơn giản hơn cho low-variance services.

## 9. Trade-offs

### Advantages

* Capacity thích nghi demand.
* Giảm idle cost.
* Có thể hấp thụ traffic growth/spikes tốt hơn fixed replicas.

### Costs / Risks

* Feedback loop có thể oscillate.
* Downstream services không tự scale cùng.
* Metrics pipeline/staleness trở thành dependency của scaling decisions.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu requests/limits và HPA target.

### Middle

Cấu hình HPA behavior và đọc scaling events.

### Senior

Phân tích control-loop behavior, startup delay, metric choice và downstream saturation.

### Technical Lead / Architect

Thiết kế autoscaling cùng capacity model toàn dependency chain, SLO và cost guardrails.

## 11. Key takeaway

* HPA là feedback control loop, không phải nút “auto scale”.
* Resource requests ảnh hưởng trực tiếp CPU utilization math.
* Scale application không giúp nếu bottleneck thực nằm ở downstream shared resource.

# 9. React stale closure: khi callback nhìn thấy state cũ và vì sao dependency array không phải checklist máy móc

## 1. What is it?

JavaScript closure giữ references/values theo lexical environment của lần render tạo ra function. Trong React functional components, mỗi render tạo một snapshot logic mới. Callback được giữ lại bởi timer, event listener hoặc async operation có thể tiếp tục nhìn thấy state/props từ render cũ.

Ví dụ:

```jsx
const [count, setCount] = useState(0);

useEffect(() => {
  const id = setInterval(() => {
    console.log(count);
  }, 1000);

  return () => clearInterval(id);
}, []);
```

Callback trên capture `count` từ render đầu tiên.

## 2. Why does it exist?

React không mutate một biến state duy nhất xuyên thời gian. Mỗi render tính UI từ snapshot state tại thời điểm đó. Đây là cơ sở cho predictable rendering, nhưng async callbacks sống lâu hơn render tạo ra chúng cần strategy rõ để đọc state mới.

## 3. How does it work?

Có nhiều fixes tùy intent.

Nếu update dựa trên previous state:

```jsx
setCount(current => current + 1);
```

Nếu effect phải phản ứng khi dependency đổi:

```jsx
useEffect(() => {
  doSomething(query);
}, [query]);
```

Nếu callback lifecycle phải stable nhưng cần latest mutable value, `useRef` có thể phù hợp:

```jsx
const latestValue = useRef(value);
latestValue.current = value;
```

Không nên thêm dependency chỉ để linter im nếu điều đó làm lifecycle semantics sai.

## 4. Practical implementation

Async search thường còn có race condition:

```jsx
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    const response = await fetch(`/api/search?q=${encodeURIComponent(query)}`, {
      signal: controller.signal
    });
    const data = await response.json();
    setResults(data);
  }

  load();
  return () => controller.abort();
}, [query]);
```

Dependency bảo đảm effect chạy theo `query`; abort cleanup ngăn request cũ update UI sau request mới.

## 5. Real production scenario

Dashboard có WebSocket reconnect handler được tạo khi user đang ở tenant A. Sau đó user switch tenant B nhưng handler cũ vẫn capture tenant A ID và ghi incoming events vào wrong state slice. Bug chỉ xuất hiện sau navigation/reconnect nên rất khó tái hiện.

Fix đúng không chỉ là “thêm tenantId dependency”; team còn phải teardown old subscription và tạo subscription mới theo tenant lifecycle.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng dùng value cũ dù DevTools cho thấy state hiện tại đã đổi.

**Evidence** → callback/timer/listener được đăng ký ở render trước và không recreate/cleanup.

**Hypothesis** → stale closure.

**Diagnosis** → log render version, dependency values lúc register callback và lúc callback fire.

**Fix** → functional state update, correct effect dependency, cleanup/re-subscribe hoặc ref tùy semantics.

**Verification** → test rapid state changes/navigation trước khi timer/request/event hoàn thành.

## 7. Common mistakes

* Tắt `exhaustive-deps` cho toàn project.
* Thêm mọi variable vào dependency array mà không hiểu effect lifecycle.
* Dùng `useRef` để né rerender cho dữ liệu thực sự phải render.
* Không cleanup event listener/subscription.
* Chỉ fix stale closure nhưng bỏ qua out-of-order async response.

## 8. Alternatives

State machines/reducers làm complex async states explicit hơn. Data-fetching libraries có request cancellation/cache semantics sẵn. External stores có subscription model riêng nhưng không loại bỏ stale callback logic tự viết.

## 9. Trade-offs

### Advantages của explicit effect lifecycle

* Dễ reason hơn về subscription/resource ownership.
* Ít hidden race hơn.
* Tests có thể mô phỏng transitions rõ.

### Costs / Risks

* Dependency changes có thể recreate expensive subscriptions.
* Ref-based latest-value pattern giảm reactivity nếu lạm dụng.
* Async UI cần xử lý cả stale closure lẫn stale response.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu closure và mỗi render là một snapshot.

### Middle

Dùng dependency arrays, cleanup và functional updates đúng intent.

### Senior

Phân biệt stale closure, race condition, subscription lifecycle và cancellation.

### Technical Lead / Architect

Chuẩn hóa async state/data-fetching patterns để team không tự xây effect orchestration khác nhau trên từng component.

## 11. Key takeaway

* Callback không tự “nhìn state mới nhất” chỉ vì component đã rerender.
* Dependency array mô tả lifecycle dependencies, không phải danh sách để làm linter im.
* Async correctness cần cả snapshot semantics, cleanup và cancellation.

# 10. SLO burn-rate alerting: cảnh báo theo tốc độ đốt error budget thay vì spam alert theo CPU threshold

## 1. What is it?

Service Level Objective (SLO) định nghĩa mức reliability mục tiêu, ví dụ 99.9% successful requests trong 30 ngày. Phần failure được phép là error budget.

Với SLO 99.9%:

```text
allowed bad fraction = 0.1%
```

Burn rate đo tốc độ tiêu error budget so với tốc độ “được phép” nếu budget trải đều cả window.

```text
Burn rate = 1   → tiêu budget đúng tốc độ kế hoạch
Burn rate = 10  → tiêu nhanh gấp 10 lần
```

## 2. Why does it exist?

Alert `CPU > 80%` có thể fire dù users không bị ảnh hưởng. Ngược lại, payment requests có thể fail 5% do dependency lỗi dù CPU chỉ 20%.

SLO alerting bám vào user-visible reliability: availability, latency hoặc correctness indicators.

## 3. How does it work?

Giả sử availability SLI:

```text
successful requests / eligible requests
```

Error rate hiện tại chia cho allowed error rate sẽ cho burn rate gần đúng.

Với SLO 99.9%, allowed error rate = 0.001. Nếu 1% requests đang fail:

```text
0.01 / 0.001 = 10x burn
```

Nếu kéo dài, budget 30 ngày sẽ hết rất nhanh.

## 4. Practical implementation

Multi-window alerting giúp vừa bắt severe incident nhanh vừa tránh noise:

```text
Fast burn:
  high burn rate trong 5m
  AND vẫn high trong 1h

Slow burn:
  moderate burn trong 30m
  AND vẫn moderate trong 6h
```

Exact thresholds phụ thuộc SLO/window và incident policy; điểm chính là kết hợp short + long window để xác nhận vấn đề vừa nghiêm trọng vừa sustained.

Metrics phải loại các requests không thuộc SLI denominator nếu business contract quy định, ví dụ client-side invalid requests có thể không được tính là service failure.

## 5. Real production scenario

Search service CPU thường xuyên chạm 85% trong peak hour nhưng latency và errors vẫn đạt SLO; CPU alert đánh thức on-call vô ích. Một lần khác upstream authorization lỗi làm 2% requests bị 5xx trong khi CPU bình thường. Burn-rate alert phát hiện ngay vì user-visible error budget đang bị đốt nhanh.

Team giữ CPU saturation như diagnostic signal/dashboard, còn paging alert dựa trên SLO impact.

## 6. Failure scenario & troubleshooting

**Symptom** → burn-rate alerts fire quá nhiều nhưng incidents không có impact thực.

**Evidence** → SLI denominator chứa health checks, bots, canceled requests hoặc expected 4xx không thuộc service responsibility.

**Hypothesis** → SLI definition không phản ánh user journey/SLO contract.

**Diagnosis** → sample requests bị đánh dấu bad, phân loại status/endpoint/tenant và so với business semantics.

**Fix** → sửa SLI eligibility, tách critical/noncritical endpoints hoặc định nghĩa latency SLI phù hợp.

**Verification** → replay historical incidents và normal peaks; alert phải bắt incidents quan trọng nhưng không page cho healthy high-utilization periods.

## 7. Common mistakes

* Gọi uptime dashboard là SLO nhưng không định nghĩa denominator rõ.
* Page trực tiếp trên mọi infrastructure threshold.
* Một SLO chung cho endpoints có criticality rất khác nhau.
* Không account maintenance/exclusions theo policy.
* Error budget chỉ làm slide, không ảnh hưởng release/incident decisions.

## 8. Alternatives

Static metric thresholds vẫn cần cho imminent resource exhaustion như disk full. Anomaly detection hữu ích với unknown patterns nhưng khó explain hơn. SLO burn alert tốt nhất cho user-impact paging; diagnostic alerts có thể tồn tại ở severity thấp hơn.

## 9. Trade-offs

### Advantages

* Alert bám user-visible reliability.
* Giảm noise từ healthy infrastructure variation.
* Kết nối incident urgency với error-budget impact.

### Costs / Risks

* SLI/SLO definition cần product + engineering alignment.
* Metrics quality phải cao.
* Một số catastrophic infrastructure signals cần alert riêng trước khi SLO bị ảnh hưởng đủ lâu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt metric, SLI, SLO và SLA.

### Middle

Tính error rate/burn rate và xây basic dashboards.

### Senior

Thiết kế multi-window alerts, denominator và incident validation.

### Technical Lead / Architect

Dùng error budget để cân bằng reliability, release velocity và operational investment ở cấp hệ thống.

## 11. Key takeaway

* Alert tốt nên phản ánh tốc độ mất reliability budget, không chỉ resource utilization.
* SLI definition sai tạo alert chính xác về toán nhưng sai về business.
* Infrastructure metrics rất quan trọng để chẩn đoán; chúng không nhất thiết là pager criteria.
