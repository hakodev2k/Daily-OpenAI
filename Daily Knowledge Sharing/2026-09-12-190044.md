# 1. C# covariance và contravariance trong generics: variance là type-safety rule, không phải mẹo syntax

## 1. What is it?

Variance mô tả quan hệ giữa generic types khi type argument có quan hệ kế thừa.

Nếu `Dog : Animal`, câu hỏi là:

```text
IEnumerable<Dog> có dùng như IEnumerable<Animal> được không?
Action<Animal> có dùng như Action<Dog> được không?
```

Trong C#:

- covariance dùng `out T`;
- contravariance dùng `in T`;
- invariant không cho phép conversion theo inheritance direction.

Mental model:

```text
Producer<T>  -> covariance  -> chỉ “đưa T ra”
Consumer<T>  -> contravariance -> chỉ “nhận T vào”
```

## 2. Why does it exist?

Nếu generic abstraction chỉ sản xuất `T`, việc dùng producer của subtype ở nơi cần producer của base type là type-safe.

Ví dụ `IEnumerable<Dog>` có thể cung cấp mọi phần tử dưới dạng `Animal`.

Ngược lại, một consumer chấp nhận mọi `Animal` chắc chắn chấp nhận được `Dog`, nên `Action<Animal>` có thể dùng ở nơi cần `Action<Dog>`.

Variance tồn tại để compiler cho phép các conversion an toàn này mà không cần cast thủ công.

## 3. How does it work?

Covariance:

```csharp
public interface IProducer<out T>
{
    T Get();
}
```

`T` chỉ được xuất hiện ở output position phù hợp.

Contravariance:

```csharp
public interface IConsumer<in T>
{
    void Handle(T value);
}
```

Compiler ngăn interface variance dùng `T` ở position phá type safety.

Ví dụ nếu `IProducer<out T>` cho phép `void Set(T value)`, một `IProducer<Dog>` có thể bị truyền một `Cat` thông qua reference `IProducer<Animal>` — không an toàn.

## 4. Practical implementation

Một event pipeline:

```csharp
public interface IEventHandler<in TEvent>
{
    Task HandleAsync(TEvent evt, CancellationToken ct);
}

public sealed class AuditHandler : IEventHandler<DomainEvent>
{
    public Task HandleAsync(DomainEvent evt, CancellationToken ct)
    {
        // audit every domain event
        return Task.CompletedTask;
    }
}
```

Vì handler consume `TEvent`, `in TEvent` cho phép handler cấp base type được dùng cho event subtype khi contract phù hợp.

## 5. Real production scenario

Một domain event bus có hàng chục event types. Team muốn một audit handler nhận tất cả `DomainEvent` và specific handlers nhận từng subtype.

Không hiểu variance, developer có thể tạo reflection/casts phức tạp hoặc duplicate registration logic. Hiểu producer/consumer direction giúp contract đơn giản hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → compiler báo generic conversion không hợp lệ dù types có inheritance relation.

**Evidence** → generic interface invariant hoặc dùng type parameter ở cả input/output positions.

**Hypothesis** → abstraction không thật sự chỉ producer hoặc chỉ consumer.

**Diagnosis** → đánh dấu từng method parameter/return position của `T`.

**Fix** → chỉ thêm `in`/`out` khi contract thực sự bảo toàn type safety; nếu type vừa đọc vừa ghi thì giữ invariant.

**Verification** → compile-time tests/usages cho base/subtype conversion.

## 7. Common mistakes

- Nghĩ `out` trong generic variance giống `out` method parameter.
- Cố làm variance cho mutable collection như `List<T>`.
- Cast để ép compiler thay vì kiểm tra semantics.
- Thiết kế interface quá rộng khiến `T` vừa input vừa output.
- Dùng variance như optimization performance.

## 8. Alternatives

Invariant generic thường rõ ràng hơn khi object vừa consume vừa produce cùng `T`. Non-generic abstraction hoặc explicit adapter phù hợp nếu type relationship không map sạch vào variance.

## 9. Trade-offs

### Advantages

- API linh hoạt hơn mà vẫn compile-time safe.
- Giảm cast và adapter thừa.
- Diễn đạt producer/consumer intent rõ.

### Costs / Risks

- Khó hiểu nếu team không nắm type theory cơ bản.
- Có thể ép abstraction vào `in/out` chỉ để đạt conversion mong muốn.
- Không áp dụng cho mọi generic type.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu covariance theo hướng “producer trả subtype có thể xem như base type”.

### Middle

Thiết kế interface chỉ consume hoặc produce khi phù hợp.

### Senior

Nhận diện khi variance giúp giảm coupling và khi invariant mới phản ánh đúng mutable semantics.

### Technical Lead / Architect

Đánh giá generic abstraction ở shared libraries để API dễ dùng nhưng không che ownership/mutability bằng type tricks.

## 11. Key takeaway

- `out T` phù hợp producer; `in T` phù hợp consumer.
- Variance là rule đảm bảo type safety, không phải cast tự động tùy ý.
- Mutable generic abstraction thường phải invariant.

# 2. ASP.NET Core `ProblemDetails`: thiết kế error contract ổn định thay vì trả exception message tùy hứng

## 1. What is it?

`ProblemDetails` là cấu trúc chuẩn hóa response lỗi HTTP với fields như `type`, `title`, `status`, `detail`, `instance` và extensions.

Mental model:

```text
Exception/domain failure
   -> boundary mapping
   -> stable HTTP error contract
   -> client handles by status/code
```

Nó không phải chỉ là “JSON đẹp hơn”; nó là contract giữa server và clients.

## 2. Why does it exist?

Nếu mỗi endpoint trả lỗi khác nhau:

```json
{ "error": "bad request" }
```

hoặc:

```json
{ "message": "Object reference not set..." }
```

frontend/mobile/partner phải viết parsing logic riêng và có nguy cơ phụ thuộc exception text.

Một error contract ổn định giúp client xử lý deterministic hơn và tránh leak implementation detail.

## 3. How does it work?

Error pipeline nên phân loại failure:

```text
Validation failure -> 400
Authentication failure -> 401
Authorization failure -> 403
Resource missing -> 404
Concurrency conflict -> 409
Unexpected exception -> 500
```

Domain/infrastructure exception không nên tự quyết định HTTP status sâu trong domain layer; HTTP boundary chịu trách nhiệm mapping.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();
app.UseExceptionHandler();
```

Custom exception handler:

```csharp
public sealed class ApiExceptionHandler : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext context,
        Exception exception,
        CancellationToken ct)
    {
        var (status, code, title) = exception switch
        {
            CustomerNotFoundException =>
                (404, "customer_not_found", "Customer not found"),

            ConcurrencyConflictException =>
                (409, "concurrency_conflict", "Resource changed"),

            _ =>
                (500, "internal_error", "Unexpected server error")
        };

        var problem = new ProblemDetails
        {
            Status = status,
            Title = title,
            Extensions = { ["code"] = code }
        };

        await context.Response.WriteAsJsonAsync(problem, ct);
        return true;
    }
}
```

## 5. Real production scenario

Mobile app cần phân biệt “order đã bị user khác sửa” với generic server error. Nếu app parse chuỗi `"The record has changed"`, chỉ cần backend đổi wording là client hỏng.

Ổn định hơn:

```json
{
  "status": 409,
  "title": "Resource changed",
  "code": "concurrency_conflict"
}
```

Client xử lý theo `code`.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend hiển thị generic error hoặc behavior khác giữa endpoints.

**Evidence** → response bodies không cùng schema; một số endpoint leak stack trace.

**Hypothesis** → error mapping phân tán.

**Diagnosis** → inventory status codes/error payloads; contract tests.

**Fix** → centralized mapping; stable machine-readable error code; validation/errors dùng cùng convention.

**Verification** → integration tests cho 400/401/403/404/409/500.

## 7. Common mistakes

- Trả `200 OK` với `{ success: false }` cho lỗi HTTP rõ ràng.
- Dùng exception message làm API contract.
- Trả stack trace ở Production.
- Mapping mọi exception thành `400`.
- Domain layer phụ thuộc ASP.NET types chỉ để tạo `ProblemDetails`.

## 8. Alternatives

Custom envelope có thể dùng nếu ecosystem đã chuẩn hóa, nhưng phải có lý do rõ. gRPC dùng status/error model khác. Internal service protocol có thể không cần HTTP-oriented structure.

## 9. Trade-offs

### Advantages

- Client contract nhất quán.
- Dễ observability và contract testing.
- Giảm leakage implementation detail.

### Costs / Risks

- Cần taxonomy error code và ownership.
- Mapping quá generic có thể mất useful diagnostics.
- Client vẫn cần backward-compatible handling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP status và error body có vai trò riêng.

### Middle

Implement centralized error mapping và integration tests.

### Senior

Thiết kế stable machine-readable codes, privacy boundary và compatibility.

### Technical Lead / Architect

Định nghĩa error contract toàn API estate và ownership giữa domain, application, transport layers.

## 11. Key takeaway

- Error response là API contract, không phải chỗ dump exception.
- Client nên dựa vào stable status/code, không dựa vào message text.
- HTTP mapping thuộc transport boundary.

# 3. EF Core split queries: tránh cartesian explosion nhưng không vô tình đổi consistency và round-trip behavior

## 1. What is it?

Khi query nhiều collection navigation bằng `Include`, EF Core có thể tạo một SQL query join lớn. Nếu nhiều collections cùng được join, số rows trung gian có thể tăng theo tích số phần tử — cartesian explosion.

`AsSplitQuery()` tách graph load thành nhiều SQL queries thay vì một join khổng lồ.

## 2. Why does it exist?

Ví dụ một `Order` có 20 `Items` và 10 `Notes`.

Một join có thể materialize khoảng:

```text
20 × 10 = 200 rows
```

cho chỉ một order, dù business graph chỉ có 30 child objects.

Split query giảm data duplication/network payload và materialization overhead.

## 3. How does it work?

Single query:

```text
Orders
 JOIN Items
 JOIN Notes
 -> one result set lớn
```

Split query:

```text
Query 1 -> Orders
Query 2 -> Items for selected Orders
Query 3 -> Notes for selected Orders
```

EF Core sau đó fix-up relationships trong memory.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Include(x => x.Items)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .AsNoTracking()
    .ToListAsync(ct);
```

Tuy nhiên nếu API chỉ cần DTO summary, projection thường tốt hơn:

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummaryDto(
        x.Id,
        x.Items.Count,
        x.Notes.Count))
    .ToListAsync(ct);
```

## 5. Real production scenario

Order details endpoint load `Items`, `Discounts`, `Notes`, `Attachments`. SQL query trả hàng chục nghìn rows cho một order lớn. Database execution chưa quá chậm nhưng network bytes và EF materialization làm API p95 tăng mạnh.

Split query giảm row multiplication đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → generated SQL cực lớn, response nhỏ nhưng dependency bytes/CPU cao.

**Evidence** → execution plan và row count lớn; profiler cho thấy materialization nhiều.

**Hypothesis** → multiple collection `Include` gây cartesian explosion.

**Diagnosis** → inspect generated SQL (`ToQueryString()`), số rows thực tế, graph cardinality.

**Fix** → projection, split query hoặc tách endpoint/read model.

**Verification** → so logical reads, bytes transferred, materialization time và total latency.

Consistency caveat: nhiều queries có thể quan sát dữ liệu thay đổi giữa các query nếu isolation không đảm bảo snapshot consistency.

## 7. Common mistakes

- Dùng `Include` như mặc định cho mọi navigation.
- Chuyển sang split query mà không đo thêm round trips.
- Load toàn entity graph rồi chỉ dùng vài fields.
- Nghĩ split query luôn nhanh hơn.
- Bỏ qua consistency requirement giữa các result sets.

## 8. Alternatives

Projection là lựa chọn tốt nhất cho read API cụ thể. Explicit separate queries có thể rõ hơn khi child data có paging riêng. Single query vẫn tốt khi graph nhỏ và round-trip latency cao.

## 9. Trade-offs

### Advantages

- Giảm row multiplication.
- Giảm network/materialization overhead cho nhiều collections.
- Query SQL dễ kiểm soát hơn.

### Costs / Risks

- Nhiều database round trips.
- Consistency giữa queries cần cân nhắc.
- Có thể chậm hơn nếu latency DB network cao và graph nhỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` biến thành database query, không phải free navigation loading.

### Middle

Đọc generated SQL và biết projection/split query.

### Senior

Đo row explosion, round-trip latency và isolation semantics.

### Technical Lead / Architect

Thiết kế read model/API boundary để không cần load aggregate graph khổng lồ chỉ vì entity relationships tồn tại.

## 11. Key takeaway

- Multiple collection `Include` có thể nhân rows rất mạnh.
- `AsSplitQuery()` đổi row explosion lấy nhiều round trips.
- Projection thường tốt hơn nếu endpoint không cần full entity graph.

# 4. SQL Server lock escalation: vì sao một transaction “bình thường” có thể chặn cả bảng dưới tải lớn

## 1. What is it?

SQL Server lock rows/pages/resources để bảo vệ consistency. Khi một statement/transaction giữ rất nhiều fine-grained locks, engine có thể cố gắng lock escalation lên mức rộng hơn, thường là table lock, nhằm giảm memory overhead quản lý lock.

Mental model:

```text
nhiều row/page locks
   -> lock manager pressure
   -> escalation attempt
   -> broader lock
   -> blocking blast radius lớn hơn
```

## 2. Why does it exist?

Mỗi lock có memory/management cost. Giữ hàng trăm nghìn row locks có thể đắt hơn một table lock.

Lock escalation là cơ chế engine cân bằng concurrency với lock-manager overhead.

## 3. How does it work?

Một batch update lớn:

```sql
UPDATE Orders
SET Archived = 1
WHERE CreatedAt < @Cutoff;
```

Nếu update chạm rất nhiều rows trong một transaction, SQL Server có thể giữ nhiều locks và escalation.

Nếu table lock xung đột với active readers/writers, hàng loạt sessions bắt đầu wait.

## 4. Practical implementation

Thay vì một transaction cực lớn, batch có kiểm soát:

```sql
WHILE 1 = 1
BEGIN
    UPDATE TOP (1000) Orders
    SET Archived = 1
    WHERE CreatedAt < @Cutoff
      AND Archived = 0;

    IF @@ROWCOUNT = 0 BREAK;
END
```

Nhưng batching cũng cần index phù hợp, nếu mỗi batch scan toàn table thì vẫn tệ.

Theo dõi blocking bằng DMVs/Query Store/Extended Events tùy incident.

## 5. Real production scenario

Nightly cleanup job update vài triệu records lúc traffic vẫn còn cao. Job “chỉ chạy một câu UPDATE”, nhưng API checkout bắt đầu timeout vì lock wait tăng.

Team ban đầu tăng API timeout, làm request pile-up nặng hơn. Root cause là transaction/batch design.

## 6. Failure scenario & troubleshooting

**Symptom** → p95/p99 tăng đột biến, DB CPU chưa chắc cao, sessions chờ lock.

**Evidence** → wait types liên quan lock, blocking chain, long-running transaction.

**Hypothesis** → batch DML giữ lock quá rộng/quá lâu hoặc escalation.

**Diagnosis** → identify head blocker, transaction duration, rows affected, access path/index.

**Fix** → batch nhỏ, commit thường xuyên, index đúng predicate, schedule workload hoặc redesign maintenance process.

**Verification** → chạy production-like data volume và theo dõi lock waits/API latency.

## 7. Common mistakes

- Chỉ nhìn CPU mà bỏ qua waits.
- Tăng timeout client thay vì xử lý blocker.
- Batch nhưng không có index nên scan lặp lại.
- Transaction bao cả external I/O.
- Dùng `NOLOCK` như universal fix cho blocking.

## 8. Alternatives

Snapshot-based isolation có thể giảm reader/writer blocking nhưng thêm version-store cost và không giải quyết mọi writer contention. Partitioning/data lifecycle strategy có thể tốt hơn cho archive/delete khối lượng lớn.

## 9. Trade-offs

### Advantages

Lock escalation giảm overhead khi transaction thật sự cần chạm nhiều rows.

### Costs / Risks

Concurrency giảm mạnh; một maintenance operation có thể ảnh hưởng toàn application.

Batching giảm lock footprint nhưng tăng số transactions và orchestration complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slow request có thể do chờ lock chứ không phải query tự nó tốn CPU.

### Middle

Biết tìm blocking session và transaction dài.

### Senior

Phân tích lock granularity, access path, batching, isolation và workload interaction.

### Technical Lead / Architect

Thiết kế data maintenance, retention và transaction boundaries để operational jobs không cạnh tranh trực tiếp với critical traffic.

## 11. Key takeaway

- Database performance = execution + waits + concurrency, không chỉ CPU.
- Transaction lớn có thể mở rộng lock blast radius.
- Fix blocking bằng evidence và workload design, không bằng tăng timeout.

# 5. MongoDB compound index và ESR rule: thiết kế index theo Equality → Sort → Range thay vì cộng column ngẫu nhiên

## 1. What is it?

Compound index chứa nhiều fields theo thứ tự xác định. Thứ tự này ảnh hưởng query engine có thể dùng index để filter/sort/range hiệu quả như thế nào.

Một heuristic phổ biến là ESR:

```text
Equality -> Sort -> Range
```

Không phải luật tuyệt đối, nhưng là mental model tốt để bắt đầu thiết kế index theo access pattern.

## 2. Why does it exist?

B-tree-like ordered index có prefix semantics. Index:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

không tương đương:

```javascript
{ createdAt: -1, tenantId: 1, status: 1 }
```

Dù chứa cùng fields, traversal/search space khác nhau.

## 3. How does it work?

Query:

```javascript
db.orders.find({
  tenantId: "t1",
  status: "Open",
  createdAt: { $gte: ISODate("2026-09-01") }
}).sort({ createdAt: -1 })
```

Index candidate:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

Equality fields thu hẹp prefix trước; sort field tiếp theo giữ order; range áp trên phần còn lại.

## 4. Practical implementation

Tạo index:

```javascript
db.orders.createIndex({
  tenantId: 1,
  status: 1,
  createdAt: -1
})
```

Kiểm tra bằng:

```javascript
db.orders.find({
  tenantId: "t1",
  status: "Open"
}).sort({ createdAt: -1 }).explain("executionStats")
```

Quan sát keys examined, docs examined và sort stage.

## 5. Real production scenario

SaaS order API query theo tenant + status và sort newest first. Team có ba single-field indexes nhưng query vẫn scan nhiều và sort in-memory.

Một compound index đúng access pattern giảm examined documents và tránh sort stage tốn memory.

## 6. Failure scenario & troubleshooting

**Symptom** → query chậm khi data tăng, dù “đã có index cho từng field”.

**Evidence** → explain plan đọc nhiều docs/keys, có blocking sort.

**Hypothesis** → indexes không match compound filter/sort access pattern.

**Diagnosis** → inspect actual queries, selectivity và index prefixes.

**Fix** → tạo compound index có thứ tự phù hợp; loại redundant indexes khi an toàn.

**Verification** → so executionStats và latency với production-like cardinality.

## 7. Common mistakes

- Một index cho mỗi field rồi kỳ vọng query kết hợp tối ưu.
- Tạo index theo schema order thay vì query pattern.
- Thêm quá nhiều indexes làm write chậm và tốn memory/storage.
- Không xem sort direction/prefix.
- Dùng ESR như luật tuyệt đối mà không đo selectivity.

## 8. Alternatives

Nếu query patterns quá đa dạng, read model riêng hoặc Elasticsearch có thể phù hợp hơn cho search/filter phức tạp. Nhưng thêm search engine chỉ vì vài queries chưa tối ưu là overengineering.

## 9. Trade-offs

### Advantages

- Query/filter/sort hiệu quả hơn.
- Giảm documents scanned.
- Có thể loại sort in-memory.

### Costs / Risks

- Mỗi index tăng write amplification và storage.
- Index set phình to nếu support mọi query permutation.
- Cardinality/access pattern thay đổi có thể làm index cũ kém giá trị.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu compound index có thứ tự, không phải một “set columns”.

### Middle

Dùng `explain("executionStats")` và thiết kế index theo query thực tế.

### Senior

Cân bằng read gain với write/storage cost và selectivity.

### Technical Lead / Architect

Quyết định query nào đáng được first-class index support, query nào cần read model khác, và index budget của collection.

## 11. Key takeaway

- Index order phải phản ánh access pattern.
- Equality/Sort/Range là heuristic tốt nhưng cần verify bằng execution stats.
- Nhiều index không đồng nghĩa query nhanh hơn.

# 6. DDD Aggregate boundary: bảo vệ invariant và transaction boundary thay vì gom entity theo quan hệ dữ liệu

## 1. What is it?

Aggregate là một consistency boundary trong domain model. Aggregate Root là entry point kiểm soát các thay đổi bên trong boundary.

Nó không đơn giản là “parent entity có children”.

Mental model:

```text
Aggregate
  -> invariants phải đúng khi transaction commit
  -> mutations đi qua Aggregate Root
  -> external aggregate reference thường qua identity
```

## 2. Why does it exist?

Business rule thường cần consistency mạnh trong một phạm vi hữu hạn.

Ví dụ `Order` phải đảm bảo:

- không approve order không có line;
- total khớp các lines;
- cancelled order không thể add line.

Nếu mọi entity mutate tự do từ mọi service, invariant bị phân tán và khó đảm bảo transactionally.

## 3. How does it work?

Ví dụ:

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public OrderStatus Status { get; private set; }
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void AddLine(ProductId productId, int quantity, Money price)
    {
        if (Status != OrderStatus.Draft)
            throw new DomainException("Only draft orders can change.");

        if (quantity <= 0)
            throw new DomainException("Quantity must be positive.");

        _lines.Add(new OrderLine(productId, quantity, price));
    }
}
```

Application Service orchestration không nên bypass invariant bằng setter public.

## 4. Practical implementation

Transaction boundary thường theo aggregate:

```csharp
var order = await db.Orders
    .Include(x => x.Lines)
    .SingleAsync(x => x.Id == command.OrderId, ct);

order.AddLine(command.ProductId, command.Quantity, command.Price);

await db.SaveChangesAsync(ct);
```

Nếu operation cần update `Order`, `Inventory`, `Customer`, `Payment` trong một aggregate khổng lồ, có thể boundary đang sai hoặc workflow nên eventual consistency.

## 5. Real production scenario

Team tạo `Customer` aggregate chứa Orders, Addresses, Payments, Preferences, Notifications vì “tất cả thuộc customer”. Mỗi update profile load graph lớn và conflict concurrency tăng.

Business invariants thực tế giữa các phần này rất ít. Tách aggregates nhỏ hơn giảm contention và load.

## 6. Failure scenario & troubleshooting

**Symptom** → update một field nhỏ phải load graph khổng lồ; concurrency conflict liên tục.

**Evidence** → aggregate có hàng nghìn child entities, transaction dài, nhiều unrelated invariants.

**Hypothesis** → boundary được thiết kế theo ownership/data relationship thay vì consistency requirement.

**Diagnosis** → hỏi: invariant nào thật sự cần atomic transaction?

**Fix** → tách aggregates, reference bằng ID, dùng domain events/workflow khi consistency có thể eventual.

**Verification** → business invariant tests + concurrency/load tests.

## 7. Common mistakes

- Aggregate = database table group.
- Aggregate Root = entity có nhiều children.
- Mọi relationship phải nằm cùng aggregate.
- Setter public rồi “validate ở service”.
- Aggregate quá lớn vì muốn một transaction cho tất cả.

## 8. Alternatives

Anemic CRUD model hoàn toàn hợp lý nếu domain đơn giản và invariant ít. DDD aggregate chỉ đáng dùng khi business rules đủ phức tạp để cần behavior-rich model.

## 9. Trade-offs

### Advantages

- Invariants tập trung.
- Transaction boundary rõ.
- Giảm accidental mutation.

### Costs / Risks

- Rich domain model tăng conceptual overhead.
- Boundary sai tạo contention/load hoặc eventual consistency không cần thiết.
- Mapping ORM có thể phức tạp hơn CRUD entity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Aggregate Root là gatekeeper cho consistency, không phải naming convention.

### Middle

Implement behavior methods và invariant tests.

### Senior

Thiết kế aggregate size theo transaction/concurrency/access patterns.

### Technical Lead / Architect

Quyết định nơi cần strong consistency, nơi chấp nhận eventual consistency, và liệu DDD complexity có thực sự justified.

## 11. Key takeaway

- Aggregate là consistency boundary.
- Boundary nên theo invariant/transaction, không theo “có foreign key”.
- Domain đơn giản có thể không cần DDD aggregate phức tạp.

# 7. Azure Key Vault + Managed Identity: secret rotation chỉ an toàn khi application lifecycle và cache behavior được thiết kế đúng

## 1. What is it?

Azure Key Vault lưu secrets/keys/certificates ngoài application configuration. Managed Identity cho App Service/Function/Container workload authenticate với Key Vault mà không cần embedded client secret.

Mental model:

```text
Application identity
   -> Entra ID token
   -> Key Vault authorization
   -> secret/certificate
```

## 2. Why does it exist?

Secret trong source code, pipeline variable hoặc `appsettings.json` dễ leak và khó rotate.

Key Vault centralize secret lifecycle, access policy/RBAC, auditing và rotation workflow.

Nhưng đưa secret vào vault không tự động làm application “rotation-safe”.

## 3. How does it work?

Application có thể đọc secret lúc startup hoặc runtime. Nếu secret được cache trong process mãi, vault value đổi nhưng app vẫn dùng old value cho đến restart/reload.

Do đó phải phân biệt:

```text
rotation in vault
vs
application observes new secret
vs
upstream accepts both during transition
```

## 4. Practical implementation

Credential:

```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);

KeyVaultSecret secret = await client.GetSecretAsync(
    "ExternalApiKey",
    cancellationToken: ct);
```

Không gọi Key Vault cho mỗi HTTP request. Có thể cache có TTL phù hợp hoặc dùng provider/configuration integration tùy secret semantics.

## 5. Real production scenario

Third-party API key rotate lúc 10:00. Key Vault đã chứa key mới, nhưng 20 App Service instances load key lúc startup và cache singleton. 8 giờ sau vẫn có requests dùng key cũ và bắt đầu `401` khi provider revoke old key.

Root cause không phải Key Vault availability mà là rotation propagation design.

## 6. Failure scenario & troubleshooting

**Symptom** → một số instances authenticate được, một số `401` sau rotation.

**Evidence** → instance age khác nhau; secret version telemetry khác nhau.

**Hypothesis** → stale in-process secret cache.

**Diagnosis** → kiểm tra secret version đang dùng theo instance, rotation timeline, provider overlap window.

**Fix** → controlled refresh strategy, dual-key overlap khi provider hỗ trợ, rolling restart hoặc dynamic reload có kiểm soát.

**Verification** → rehearsed rotation trong staging và production runbook.

## 7. Common mistakes

- Dùng Managed Identity nhưng vẫn giữ storage/API keys vô hạn.
- Fetch vault mỗi request gây latency/throttling dependency.
- Rotation không có overlap/recovery plan.
- App có quyền đọc toàn vault thay vì least privilege.
- Log secret value trong exception/debug output.

## 8. Alternatives

Managed Identity trực tiếp tới Azure service tốt hơn secret khi service hỗ trợ Entra auth. Certificate có thể phù hợp service-to-service trust. Environment secret injection đơn giản hơn nhưng rotation/audit thường kém hơn.

## 9. Trade-offs

### Advantages

- Giảm secret nằm trong code/config.
- Audit và access control tập trung.
- Managed Identity loại bỏ credential bootstrap cho Azure workload.

### Costs / Risks

- Key Vault trở thành dependency/control-plane component.
- Cache/refresh logic cần thiết kế.
- Rotation coordination vẫn là distributed rollout problem.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu vault lưu secret không đồng nghĩa app tự động dùng version mới ngay.

### Middle

Dùng `DefaultAzureCredential`, RBAC và không hardcode secret.

### Senior

Thiết kế caching, rotation, retry và incident telemetry.

### Technical Lead / Architect

Ưu tiên secretless auth khi có thể; với secrets bắt buộc, định nghĩa rotation SLA, overlap, ownership và rollback.

## 11. Key takeaway

- Key Vault giải quyết storage/access lifecycle, không tự giải quyết application refresh.
- Managed Identity nên được ưu tiên cho Azure-to-Azure auth.
- Rotation phải được test như một production deployment scenario.

# 8. Git bisect trong production regression: tìm commit gây lỗi bằng evidence thay vì đọc hàng trăm PR thủ công

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên gây regression.

Bạn đánh dấu:

```text
good commit
bad commit
```

Git checkout commit giữa khoảng. Mỗi lần bạn xác định good/bad, search space giảm khoảng một nửa.

## 2. Why does it exist?

Nếu 256 commits nằm giữa release tốt và release lỗi, đọc từng commit/PR thủ công rất tốn thời gian.

Binary search lý thuyết chỉ cần khoảng:

```text
log2(256) = 8 checks
```

nếu có test/reproduction deterministic.

## 3. How does it work?

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.3
```

Sau mỗi checkout:

```bash
git bisect good
# hoặc
git bisect bad
```

Kết thúc:

```bash
git bisect reset
```

Có thể automate bằng test command:

```bash
git bisect run dotnet test tests/Regression.Tests/Regression.Tests.csproj
```

## 4. Practical implementation

Một API serialization regression có deterministic test:

```csharp
[Fact]
public async Task Legacy_client_contract_remains_compatible()
{
    var response = await _client.GetAsync("/api/v1/orders/123");
    var json = await response.Content.ReadAsStringAsync();

    Assert.Contains("customerName", json);
}
```

Nếu test exit code phản ánh good/bad, `git bisect run` tự tìm commit.

## 5. Real production scenario

Sau hai tuần development, release mới làm một legacy integration fail. 180 commits đã merge. Logs xác định behavior từng hoạt động ở release trước.

Thay vì “PR nào có vẻ liên quan?”, team tạo regression test và bisect để xác định commit thay DTO serializer config.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect cho kết quả không ổn định hoặc commit giữa history không build được.

**Evidence** → test flaky; historical commits phụ thuộc unavailable artifact/config.

**Hypothesis** → good/bad oracle không deterministic hoặc history có untestable points.

**Diagnosis** → chạy reproduction nhiều lần; dùng `git bisect skip` cho commit không test được.

**Fix** → tạo minimal deterministic test; pin environment/dependencies khi có thể.

**Verification** → checkout culprit parent và culprit commit, xác nhận test đổi từ pass sang fail.

## 7. Common mistakes

- Bisect bằng cảm giác thay vì reproducible test.
- Chọn “good” commit chưa thực sự verify.
- Regression phụ thuộc data/environment nhưng test local không tái tạo.
- Kết luận commit culprit = developer culprit; commit chỉ là technical change point.
- Không thêm regression test sau incident.

## 8. Alternatives

`git log`, `git blame`, PR search phù hợp khi phạm vi thay đổi đã rất nhỏ. Feature flags/telemetry có thể identify behavior rollout nhanh hơn. Bisect mạnh nhất khi có deterministic reproduction và khoảng commit lớn.

## 9. Trade-offs

### Advantages

- Thu hẹp search space rất nhanh.
- Evidence-driven.
- Có thể automate hoàn toàn.

### Costs / Risks

- Cần historical builds reproducible.
- Flaky tests phá binary-search assumption.
- Merge histories phức tạp có thể khó reasoning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết dùng `good`/`bad` để thu hẹp commit range.

### Middle

Tạo regression test và automate `git bisect run`.

### Senior

Xử lý flaky/environment-dependent reproduction và verify causal change.

### Technical Lead / Architect

Đảm bảo build/test reproducibility đủ tốt để incident investigation không phụ thuộc trí nhớ con người.

## 11. Key takeaway

- `git bisect` biến regression search thành binary search.
- Giá trị phụ thuộc vào deterministic good/bad test.
- Sau khi tìm culprit, giữ regression test để lỗi không quay lại.

# 9. ADO.NET connection pool exhaustion: API timeout dù database vẫn khỏe vì connection không quay về pool đúng lúc

## 1. What is it?

ADO.NET connection pooling tái sử dụng physical database connections. `SqlConnection.OpenAsync()` thường mượn connection từ pool thay vì tạo TCP/login mới mỗi lần.

Pool exhaustion xảy ra khi mọi connection khả dụng đang bận và requests mới phải chờ connection được trả về.

Mental model:

```text
Request
 -> Open connection
 -> pool has free connection? yes -> execute
                           no  -> wait
```

## 2. Why does it exist?

Tạo physical DB connection đắt: network handshake, authentication, session setup. Pooling giảm cost này.

Nhưng pool hữu hạn cũng là concurrency boundary. Nếu application giữ connection quá lâu, throughput bị giới hạn dù SQL Server CPU thấp.

## 3. How does it work?

Connection được trả về pool khi `Dispose`/`Close` đúng cách và connection không bị invalid.

EF Core thường quản lý connection lifetime cho query ngắn. Nhưng transaction dài, streaming reader, manual connection hoặc sync blocking có thể giữ connection lâu.

Little’s Law mental model:

```text
concurrency ≈ throughput × hold time
```

Nếu hold time tăng 10×, số connections cần để giữ cùng throughput cũng tăng gần tương ứng.

## 4. Practical implementation

Manual ADO.NET phải dispose:

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(ct);

await using var command = connection.CreateCommand();
command.CommandText = "SELECT ...";

await using var reader = await command.ExecuteReaderAsync(ct);
```

Không giữ connection trong singleton/service field.

Với EF Core, transaction scope phải ngắn:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

// DB work only
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Không gọi external HTTP API trong transaction nếu có thể tránh.

## 5. Real production scenario

Checkout API mở transaction, update DB, rồi gọi payment provider 12 giây trước commit. Mỗi request giữ SQL connection trong suốt external call.

Chỉ cần vài chục concurrent checkouts là pool cạn. Requests khác timeout “while obtaining a connection from the pool”, dù database chỉ 25% CPU.

## 6. Failure scenario & troubleshooting

**Symptom** → request timeout, message liên quan pool timeout; DB CPU/IO không tương ứng mức lỗi.

**Evidence** → active connections gần pool limit, transaction duration cao, traces cho thấy gap dài giữa DB commands.

**Hypothesis** → connection hold time quá dài/leak/disposal sai.

**Diagnosis** → inspect connection metrics, dependency traces, transaction scopes, manual `SqlConnection` usages.

**Fix** → dispose đúng, rút ngắn transaction, tách external I/O, giảm streaming hold time; tăng pool size chỉ sau khi hiểu capacity.

**Verification** → load test và theo dõi wait-for-connection duration.

## 7. Common mistakes

- Tăng `Max Pool Size` như fix đầu tiên.
- Giữ transaction xuyên HTTP call.
- Không dispose `DbDataReader`/connection.
- Singleton `DbContext`.
- Nghĩ async tự động giải phóng DB connection trong lúc reader/transaction còn active.

## 8. Alternatives

Scale database không giải quyết connection leak. Queue/asynchronous workflow có thể giảm synchronous concurrency cho expensive workflow. Connection multiplexing/proxy concepts phụ thuộc database/provider nhưng không thay application transaction discipline.

## 9. Trade-offs

### Advantages

Pooling làm DB access nhanh và hiệu quả hơn rất nhiều.

### Costs / Risks

Pool là finite shared resource. Hold-time tăng có thể tạo queueing/cascading latency trước khi database bản thân overload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Open()` thường mượn pooled connection và `Dispose` rất quan trọng.

### Middle

Biết scope `DbContext`/transaction đúng và tìm pool timeout.

### Senior

Liên hệ throughput, hold time, pool capacity và external dependency latency.

### Technical Lead / Architect

Thiết kế workflow để scarce resources không bị giữ xuyên slow remote operations; đặt telemetry/capacity guardrails.

## 11. Key takeaway

- Connection pool exhaustion có thể xảy ra khi DB vẫn khỏe.
- Connection hold time quan trọng ngang số request.
- Tăng pool size không sửa transaction/lifetime design sai.

# 10. Structured Outputs cho AI integration: schema giúp format deterministic hơn nhưng business correctness vẫn phải do code kiểm soát

## 1. What is it?

Structured Outputs là pattern/API capability yêu cầu model trả output theo một schema xác định, ví dụ JSON object với fields/types bắt buộc.

Mental model:

```text
Natural-language reasoning
   -> constrained structured response
   -> application validation
   -> deterministic business logic
```

Schema cải thiện shape correctness, không biến model thành deterministic rule engine.

## 2. Why does it exist?

Parsing free-form text như:

```text
Approved because risk seems low.
```

rất brittle. Application cần data như:

```json
{
  "category": "low_risk",
  "confidence": 0.82,
  "explanation": "..."
}
```

Structured response giúp integration ổn định hơn, giảm regex/manual parsing và invalid JSON.

## 3. How does it work?

Application định nghĩa schema. Model generation bị constrain để tạo output phù hợp shape đó.

Tuy nhiên field value vẫn có thể sai về facts/business meaning.

Ví dụ model có thể hợp lệ schema nhưng trả:

```json
{
  "invoiceTotal": 999999,
  "currency": "USD"
}
```

trong khi source invoice là 99.99 EUR.

Schema validation pass nhưng semantic correctness fail.

## 4. Practical implementation

C# contract:

```csharp
public sealed record TicketClassification(
    string Category,
    double Confidence,
    string Summary);
```

Sau model response, application vẫn validate whitelist/business boundaries:

```csharp
if (!AllowedCategories.Contains(result.Category))
    throw new InvalidOperationException("Unsupported category.");

if (result.Confidence is < 0 or > 1)
    throw new InvalidOperationException("Invalid confidence.");
```

Nếu model đề xuất financial action:

```text
model -> recommendation
code  -> authorization + amount validation + policy checks
```

Không để model output trực tiếp commit transaction.

## 5. Real production scenario

Support system dùng model classify tickets và chọn queue. Structured output đảm bảo `category` luôn là field machine-readable.

Nhưng nếu model hallucinate customer tier, routing có thể sai. Vì vậy customer tier phải lấy từ deterministic CRM data, không để model tự suy luận từ email text.

## 6. Failure scenario & troubleshooting

**Symptom** → JSON luôn parse được nhưng business actions vẫn sai.

**Evidence** → schema-valid response chứa values không grounded vào source data.

**Hypothesis** → team nhầm structural validity với semantic correctness.

**Diagnosis** → trace prompt/context/source grounding; compare model fields với deterministic source.

**Fix** → move authoritative fields về code/tool lookup; add validation/evaluation; giới hạn model role vào classification/extraction nơi acceptable.

**Verification** → eval dataset gồm adversarial/ambiguous cases và assertion business guardrails luôn enforce.

## 7. Common mistakes

- Nghĩ JSON schema = hallucination solved.
- Cho model quyết định authorization/financial correctness.
- Không version schema.
- Không log model/version/schema/context metadata cho debugging.
- Retry model vô hạn khi semantic output không đạt.

## 8. Alternatives

Deterministic parser/rules tốt hơn khi input format ổn định. Function Calling/Tool Calling phù hợp khi model cần đề xuất action nhưng application vẫn kiểm soát execution. RAG giúp grounding nhưng không đảm bảo correctness tuyệt đối.

## 9. Trade-offs

### Advantages

- Integration contract rõ.
- Giảm parse failures.
- Dễ validation, telemetry và downstream processing.

### Costs / Risks

- Model values vẫn probabilistic.
- Schema evolution cần compatibility strategy.
- Constrained output có thể tăng complexity/token cost tùy use case.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu structured output đảm bảo shape tốt hơn, không đảm bảo nội dung đúng.

### Middle

Implement typed DTO, schema validation và error handling.

### Senior

Thiết kế evaluation, grounding, retries và deterministic guardrails.

### Technical Lead / Architect

Quyết định field nào model được phép suy luận và field nào bắt buộc đến từ authoritative deterministic systems; giới hạn blast radius của model error.

## 11. Key takeaway

- Structured Outputs giải quyết contract shape, không giải quyết truth.
- Security/authorization/financial correctness phải nằm trong deterministic code.
- AI integration tốt cần schema + validation + grounding + evaluation + observability.
