# 1. C# `Span<T>` và `Memory<T>`: zero-copy đúng lifetime mà không mang stack-only data qua async boundary

## 1. What is it?

`Span<T>` là một `ref struct` biểu diễn một vùng nhớ liên tiếp mà không cần tạo một array/string mới. Nó có thể trỏ vào array, stack memory hoặc unmanaged memory. `Memory<T>` có mục tiêu gần giống nhưng có lifetime linh hoạt hơn và có thể đi qua async boundary.

Mental model:

```text
byte[] buffer
┌──────────────────────────────┐
│ header │ payload │ checksum  │
└──────────────────────────────┘
    ↑         ↑
 Span<byte>  Span<byte>
```

Thay vì copy từng phần sang array mới, code chỉ tạo view lên cùng vùng nhớ.

## 2. Why does it exist?

Parsing protocol, serialization, compression và text processing thường tạo nhiều temporary allocations. Ví dụ:

```csharp
var prefix = input.Substring(0, 8);
var payload = input.Substring(8, 64);
```

Mỗi `Substring` hiện đại tạo string mới. Trên hot path, hàng triệu temporary objects làm tăng Gen 0 GC và memory bandwidth. `Span<T>` cho phép slicing mà không copy dữ liệu.

## 3. How does it work?

`Span<T>` chứa reference tới vùng nhớ và length. Vì có thể trỏ vào stack memory, compiler cấm nó escape ra heap hoặc tồn tại qua `await`/`yield`.

```csharp
ReadOnlySpan<char> span = input.AsSpan();
var prefix = span[..8];
var body = span.Slice(8, 64);
```

`Memory<T>` thì có thể được giữ trong object hoặc qua async operation:

```csharp
Memory<byte> memory = buffer.AsMemory(0, count);
await stream.WriteAsync(memory, cancellationToken);
```

Khi cần synchronous parsing, có thể lấy `memory.Span` trong phạm vi ngắn.

## 4. Practical implementation

Ví dụ parse header không allocation:

```csharp
public static bool TryParseFrame(
    ReadOnlySpan<byte> frame,
    out ushort type,
    out ReadOnlySpan<byte> payload)
{
    type = 0;
    payload = default;

    if (frame.Length < 4)
        return false;

    type = BinaryPrimitives.ReadUInt16BigEndian(frame[..2]);
    var length = BinaryPrimitives.ReadUInt16BigEndian(frame.Slice(2, 2));

    if (frame.Length < 4 + length)
        return false;

    payload = frame.Slice(4, length);
    return true;
}
```

Nếu sau đó phải gọi asynchronous API, hãy chuyển boundary về `ReadOnlyMemory<byte>` hoặc giữ original buffer sống đủ lâu thay vì cố giữ `Span<T>`.

## 5. Real production scenario

Một ingestion service nhận hàng chục nghìn binary messages mỗi giây. Phiên bản ban đầu dùng `byte[].Skip(...).Take(...).ToArray()` cho từng field, tạo lượng lớn short-lived arrays. CPU profile cho thấy GC chiếm phần đáng kể latency.

Refactor sang `ReadOnlySpan<byte>` cho parsing synchronous và `ReadOnlyMemory<byte>` cho asynchronous write giảm allocation rõ rệt mà không thay đổi protocol semantics.

## 6. Failure scenario & troubleshooting

**Symptom** → developer không thể compile code vì `Span<T>` “cannot be preserved across await boundary”, hoặc refactor sang unsafe workaround gây corrupted data.

**Evidence** → method đang giữ span rồi gọi `await` trong cùng scope.

**Hypothesis** → lifetime của stack-only view vượt quá phạm vi an toàn.

**Diagnosis** → xác định dữ liệu thực sự cần tồn tại qua async operation hay chỉ cần parse trước `await`.

**Fix** → hoàn tất xử lý span trước `await`; hoặc dùng `Memory<T>`/owner object có lifetime rõ ràng.

**Verification** → stress test với concurrent requests và buffer reuse; dùng tests để bảo đảm consumer không đọc buffer sau khi buffer đã được trả về pool.

## 7. Common mistakes

* Dùng `Span<T>` mọi nơi dù workload không allocation-sensitive.
* Trả span trỏ vào vùng nhớ có lifetime ngắn không hợp lệ.
* Dùng pooled buffer rồi giữ `Memory<T>` sau khi buffer đã `Return`.
* Benchmark micro-operation nhưng bỏ qua complexity của toàn pipeline.
* Nhầm zero-copy với zero-cost; bounds checks, parsing và memory bandwidth vẫn tồn tại.

## 8. Alternatives

Array/string bình thường đơn giản hơn cho code không nằm trên hot path. `ArraySegment<T>` phù hợp API cũ. `ReadOnlySequence<T>` phù hợp dữ liệu segmented như `System.IO.Pipelines` khi payload không nằm trong một buffer liên tục.

## 9. Trade-offs

### Advantages

* Giảm temporary allocation và copy.
* Tốt cho parsing/serialization hot path.
* Cho phép API biểu diễn slice rõ ràng.

### Costs / Risks

* Lifetime rules khó hơn.
* Không phải mọi API đều hỗ trợ span/memory.
* Buffer pooling kết hợp sai có thể tạo data leak hoặc use-after-return logic bug.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slicing không nhất thiết phải copy dữ liệu.

### Middle

Biết chọn `Span<T>` cho synchronous code và `Memory<T>` cho async-compatible lifetime.

### Senior

Kết hợp spans, pooled buffers, `ReadOnlySequence<T>` và profiling để tối ưu đúng bottleneck.

### Technical Lead / Architect

Chỉ đưa low-allocation APIs vào boundary nơi throughput/GC metrics chứng minh giá trị; giữ application/business code đơn giản ở phần còn lại.

## 11. Key takeaway

* `Span<T>` là view stack-only, `Memory<T>` có lifetime linh hoạt hơn.
* Zero-copy chỉ an toàn khi ownership và lifetime được hiểu rõ.
* Tối ưu allocation phải bắt đầu từ profiler, không từ sở thích syntax.

# 2. ASP.NET Core Endpoint Filters: đặt cross-cutting logic sát Minimal API mà không biến pipeline thành middleware hỗn loạn

## 1. What is it?

Endpoint Filter là cơ chế của ASP.NET Core Minimal APIs cho phép chạy logic trước và sau một endpoint handler cụ thể hoặc nhóm endpoints. Nó tương tự một pipeline nhỏ ở endpoint layer.

```text
Request
  ↓
Global middleware
  ↓
Endpoint filter 1
  ↓
Endpoint filter 2
  ↓
Handler
```

Nó hữu ích cho validation, logging có context endpoint, policy checks hoặc transformation ở phạm vi hẹp.

## 2. Why does it exist?

Middleware phù hợp cross-cutting concern toàn application, nhưng nếu một rule chỉ áp dụng cho nhóm endpoints, middleware có thể phải chứa nhiều `Path`/metadata checks. Ngược lại, copy validation/authorization boilerplate vào từng handler làm logic phân tán.

Endpoint Filters tạo scope ở giữa: reusable nhưng gắn gần endpoint.

## 3. How does it work?

Filter nhận `EndpointFilterInvocationContext` và delegate tới bước tiếp theo:

```csharp
public async ValueTask<object?> InvokeAsync(
    EndpointFilterInvocationContext context,
    EndpointFilterDelegate next)
{
    // before
    var result = await next(context);
    // after
    return result;
}
```

Order filter có ý nghĩa. Nếu filter A gọi B, execution trở thành nested pipeline giống middleware.

## 4. Practical implementation

Ví dụ validation filter cho request implementing contract:

```csharp
public sealed class ValidationFilter<T> : IEndpointFilter
{
    private readonly IValidator<T> _validator;

    public ValidationFilter(IValidator<T> validator)
        => _validator = validator;

    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var model = context.Arguments.OfType<T>().FirstOrDefault();
        if (model is null)
            return Results.BadRequest();

        var validation = await _validator.ValidateAsync(model);
        if (!validation.IsValid)
            return Results.ValidationProblem(validation.ToDictionary());

        return await next(context);
    }
}
```

Đăng ký ở endpoint group giúp policy rõ phạm vi:

```csharp
var orders = app.MapGroup("/orders");
orders.MapPost("/", CreateOrder)
      .AddEndpointFilter<ValidationFilter<CreateOrderRequest>>();
```

## 5. Real production scenario

Một API có 40 Minimal API endpoints. Team ban đầu đặt tenant validation trong từng handler, dẫn đến vài endpoints quên check tenant scope. Sau đó họ chuyển rule sang filter gắn ở `MapGroup("/tenant/{tenantId}")`, giúp boundary nhất quán và giảm boilerplate.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint trả `403` trước khi validation hoặc telemetry mong muốn chạy; log order khó hiểu.

**Evidence** → nhiều filters cùng xử lý auth, validation, exception mapping và metrics.

**Hypothesis** → pipeline order hoặc responsibility overlap không rõ.

**Diagnosis** → trace thứ tự filters và middleware; xác định concern nào phải chạy global, concern nào endpoint-specific.

**Fix** → đưa exception handling/correlation toàn cục về middleware; giữ filter cho concern phụ thuộc endpoint arguments/metadata.

**Verification** → integration tests assert cả status code lẫn việc handler có/không được gọi cho từng failure path.

## 7. Common mistakes

* Dùng filter thay cho mọi middleware.
* Đặt business rule quan trọng vào generic infrastructure filter.
* Filter tự mở transaction rồi downstream handler cũng mở transaction khác.
* Không document execution order.
* Filter đọc body thủ công trong khi model binding đã làm việc đó.

## 8. Alternatives

Middleware phù hợp concern toàn application. MVC action filters phù hợp controller-based application. Decorator ở application layer tốt hơn nếu concern gắn với use case chứ không phải HTTP endpoint.

## 9. Trade-offs

### Advantages

* Reuse logic theo endpoint/group.
* Có access tới bound arguments.
* Giảm handler boilerplate.

### Costs / Risks

* Pipeline nhiều lớp có thể khó debug.
* Dễ đẩy business logic xuống HTTP layer.
* Order dependence tạo hidden behavior nếu governance kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu filter chạy quanh handler và khác middleware global.

### Middle

Biết dùng filters cho validation/policy scoped theo endpoint.

### Senior

Thiết kế ownership giữa middleware, filters và application decorators.

### Technical Lead / Architect

Đặt convention để pipeline có ít lớp, order deterministic và business invariants không bị giấu trong infrastructure.

## 11. Key takeaway

* Endpoint Filters tốt cho cross-cutting logic cần endpoint context.
* Middleware vẫn là lựa chọn đúng cho concern toàn request pipeline.
* Boundary tốt quan trọng hơn việc tận dụng mọi extension point framework cung cấp.

# 3. EF Core `DbContext` pooling: giảm allocation đúng workload nhưng tránh state leakage giữa requests

## 1. What is it?

`DbContext` pooling tái sử dụng instances của `DbContext` thay vì tạo object graph mới cho mỗi scope. Khi context được trả về pool, EF Core reset internal state để instance có thể được dùng lại.

```text
Request A → rent DbContext → use → return
Request B → rent same instance → use → return
```

Nó khác connection pooling: `DbContext` pool tái sử dụng EF object; ADO.NET connection pool tái sử dụng database connections.

## 2. Why does it exist?

Khởi tạo `DbContext` gồm services, change tracker và metadata wiring. Trong high-throughput APIs có hàng chục nghìn scopes mỗi giây, allocation/initialization này có thể đáng kể dù query latency thấp.

Pooling giảm overhead này, nhưng chỉ đáng làm khi profiling cho thấy context creation nằm trên hot path.

## 3. How does it work?

Đăng ký:

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

EF Core lấy context từ pool, dùng trong DI scope, sau đó reset state và trả về pool. Vì instance được reuse, mutable state do application thêm vào context có thể trở thành vấn đề.

## 4. Practical implementation

Tránh lưu tenant/user-specific state trực tiếp trên pooled context:

```csharp
public sealed class AppDbContext : DbContext
{
    // Bad for pooled context if mutated per request:
    // public Guid CurrentTenantId { get; set; }
}
```

Nếu global query filter cần tenant, cân nhắc factory/wrapper có lifecycle rõ hoặc truyền tenant condition ở repository/specification layer. Nếu buộc dùng stateful context, phải bảo đảm state được set lại an toàn trên mỗi lease — nhưng đó là complexity cần evidence.

## 5. Real production scenario

Một multi-tenant SaaS bật `AddDbContextPool`. `CurrentTenantId` được set ở middleware và query filter dùng property đó. Một code path quên set tenant sau khi context được reuse, khiến query dùng tenant cũ — một lỗi isolation nghiêm trọng.

Root cause không nằm ở EF query translation mà ở mutable request state trên pooled object.

## 6. Failure scenario & troubleshooting

**Symptom** → rất hiếm khi request đọc dữ liệu sai tenant hoặc interceptor thấy state từ request trước.

**Evidence** → lỗi chỉ xuất hiện khi pooling bật và dưới concurrency.

**Hypothesis** → mutable custom state không được reset cùng EF internal state.

**Diagnosis** → inspect fields/properties, interceptors và custom services gắn vào context; chạy stress test với alternating tenant IDs.

**Fix** → loại per-request mutable state khỏi pooled context hoặc bỏ pooling nếu design không tương thích.

**Verification** → concurrency isolation test với hàng nghìn requests, assert tenant boundary ở database result.

## 7. Common mistakes

* Nhầm context pooling với connection pooling.
* Bật pooling trước khi đo performance.
* Lưu user/tenant/request metadata trên context instance.
* Giả định pooling cho phép dùng một context concurrently.
* Giữ context ngoài DI scope hoặc cache context thủ công.

## 8. Alternatives

`AddDbContext` thường đủ tốt và đơn giản hơn. `IDbContextFactory<T>` phù hợp background work hoặc UI lifecycle đặc biệt. ADO.NET/Dapper có thể phù hợp hot query cực hẹp nếu EF overhead thực sự là bottleneck.

## 9. Trade-offs

### Advantages

* Giảm allocation và initialization overhead.
* Có thể cải thiện throughput cho short, frequent DB operations.

### Costs / Risks

* Mutable state cần kiểm soát nghiêm ngặt.
* Lợi ích nhỏ nếu query/network chiếm phần lớn latency.
* Debugging state leakage khó vì lỗi có tính probabilistic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbContext` là scoped unit-of-work và không thread-safe.

### Middle

Phân biệt context pooling với database connection pooling.

### Senior

Đánh giá tenant state, interceptors, factory lifecycle và benchmark trước/sau.

### Technical Lead / Architect

Chỉ chuẩn hóa pooling khi coding conventions bảo đảm context stateless theo request và performance evidence đủ mạnh.

## 11. Key takeaway

* `DbContext` pooling tối ưu object lifecycle, không tối ưu query xấu.
* Pooled object phải được coi gần như stateless ngoài state EF quản lý.
* Data-isolation correctness luôn quan trọng hơn vài microseconds context creation.

# 4. PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)`: phân biệt query chậm vì I/O, CPU hay cardinality estimate sai

## 1. What is it?

`EXPLAIN` cho thấy execution plan mà PostgreSQL chọn. `ANALYZE` chạy query thật và bổ sung actual timing/rows. `BUFFERS` cho thấy số shared/local/temp blocks được hit/read/dirtied/written.

Nó biến câu hỏi “query chậm vì sao?” thành evidence về plan behavior.

## 2. Why does it exist?

Execution time đơn thuần không nói query chậm do disk read, bad join order, sort spill, row estimate sai hay CPU-heavy expression. Hai queries cùng mất 2 giây có root cause hoàn toàn khác.

## 3. How does it work?

Ví dụ:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.total
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE c.region = 'APAC'
ORDER BY o.created_at DESC
LIMIT 100;
```

Quan sát các cặp:

```text
estimated rows vs actual rows
shared hit vs shared read
temp read/write
loops
actual time
```

Estimate sai lớn thường kéo theo join strategy hoặc memory decision không phù hợp.

## 4. Practical implementation

Checklist đọc plan từ ngoài vào trong:

1. Tìm node tốn thời gian nhất.
2. So sánh estimated vs actual rows.
3. Xem loops — một node rẻ nhưng chạy 100.000 lần vẫn đắt.
4. Kiểm tra `shared read` cao → I/O lạnh hoặc working set không cache.
5. Kiểm tra `temp read/write` → sort/hash spill.
6. Xem filter rows removed và index condition.

Đừng chỉ thấy `Seq Scan` rồi kết luận phải thêm index; sequential scan có thể đúng nếu query đọc phần lớn bảng.

## 5. Real production scenario

Một report query mất 8 giây. Team định thêm index mới vì thấy `Seq Scan`. `EXPLAIN (ANALYZE, BUFFERS)` cho thấy scan chỉ mất 300 ms; phần lớn thời gian nằm ở nested loop chạy inner lookup hàng triệu lần vì optimizer estimate outer rows là vài trăm.

Sau khi cập nhật statistics và sửa data correlation/index design, planner chọn join phù hợp hơn và latency giảm mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → query nhanh trong staging nhưng chậm production dù schema giống nhau.

**Evidence** → production plan có row estimates lệch lớn và buffer reads cao hơn nhiều.

**Hypothesis** → data distribution, table size, cache state hoặc statistics khác nhau.

**Diagnosis** → lấy actual plan production an toàn, so sánh statistics freshness, row counts, parameter values và indexes.

**Fix** → giải quyết root cause như statistics, index, query shape hoặc memory/work_mem phù hợp; tránh copy plan hint-style workaround không hiểu nguyên nhân.

**Verification** → chạy với representative parameter distribution, không chỉ một “fast value”.

## 7. Common mistakes

* Chạy `EXPLAIN ANALYZE` cho destructive query trên production mà quên nó thực thi thật.
* Chỉ nhìn total time, không nhìn loops và row estimates.
* Coi mọi sequential scan là lỗi.
* Tuning bằng dữ liệu staging nhỏ hơn nhiều production.
* Bật `work_mem` cực lớn global chỉ để cứu một sort.

## 8. Alternatives

`pg_stat_statements` giúp tìm queries tốn tổng thời gian nhất. Auto-explain có thể capture slow plans. Application tracing cho context request. Database monitoring tool giúp trend lâu dài nhưng actual plan vẫn là evidence quan trọng.

## 9. Trade-offs

### Advantages

* Evidence rất gần execution engine.
* Phân biệt I/O, cardinality, loop amplification và spill.
* Hỗ trợ tuning có hệ thống.

### Costs / Risks

* `ANALYZE` chạy query thật và có thể tốn tài nguyên.
* Plan đọc khó với queries lớn.
* Một plan sample không đại diện mọi parameter/data state.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết lấy plan và phân biệt estimated vs actual rows.

### Middle

Đọc scans, joins, loops và buffer hits/reads.

### Senior

Kết nối plan với statistics, data skew, memory và parameter distribution.

### Technical Lead / Architect

Xây performance workflow từ query telemetry → representative plan → controlled fix → regression benchmark.

## 11. Key takeaway

* Query tuning bắt đầu từ actual evidence, không từ “thêm index thử xem”.
* Estimated/actual row mismatch là tín hiệu cực quan trọng.
* `BUFFERS` giúp phân biệt query đắt vì I/O hay vì cách plan xử lý dữ liệu.

# 5. MongoDB Change Streams: phản ứng với thay đổi dữ liệu mà không polling và không giả định event delivery là exactly-once

## 1. What is it?

MongoDB Change Streams cho phép application subscribe các thay đổi xảy ra trên collection/database/deployment, dựa trên oplog replication mechanism.

Consumer có thể nhận events như insert, update, replace, delete mà không phải query polling liên tục.

## 2. Why does it exist?

Polling kiểu:

```text
SELECT/Find records WHERE updatedAt > lastSeen
sleep 5s
repeat
```

tạo load định kỳ, có latency tối thiểu và khó xử lý race quanh timestamp. Change Streams cung cấp stream thay đổi gần real-time hơn và có resume token để tiếp tục sau disconnect.

## 3. How does it work?

Consumer mở stream:

```csharp
using var cursor = await collection.WatchAsync(
    cancellationToken: cancellationToken);

await cursor.ForEachAsync(change =>
{
    // process change
}, cancellationToken);
```

Mỗi event có resume token. Consumer có thể persist token và resume sau restart nếu oplog history vẫn còn đủ để token hợp lệ.

## 4. Practical implementation

Production consumer cần durable checkpoint:

```text
receive event
  ↓
process idempotently
  ↓
persist side effect + checkpoint strategy
  ↓
advance
```

Không nên chỉ lưu resume token trong memory. Nếu process crash sau side effect nhưng trước checkpoint, event có thể được xử lý lại. Handler phải idempotent hoặc có inbox/deduplication strategy.

## 5. Real production scenario

Product catalog dùng MongoDB và Search index dùng Elasticsearch. Thay vì application code ở mọi write path phải update Elasticsearch trực tiếp, indexer subscribe Change Stream và cập nhật projection.

Khi Elasticsearch outage 10 phút, indexer reconnect/resume và catch up thay vì làm request write chính thất bại theo downstream search availability.

## 6. Failure scenario & troubleshooting

**Symptom** → sau consumer downtime dài, resume thất bại hoặc search projection thiếu updates.

**Evidence** → persisted resume token cũ hơn oplog retention window hoặc token không còn resumable.

**Hypothesis** → recovery assumption vượt quá retention của underlying replication history.

**Diagnosis** → kiểm tra oplog window, downtime duration, last checkpoint và consumer lag.

**Fix** → thiết kế full resync/rebuild path; tăng operational alerting trước khi lag vượt retention; không coi resume token là archive vô hạn.

**Verification** → chaos test consumer dừng, duplicate delivery, network partition và full rebuild.

## 7. Common mistakes

* Giả định Change Stream exactly-once.
* Không persist resume token.
* Side effect không idempotent.
* Không có rebuild path khi token hết hiệu lực.
* Watch toàn database dù chỉ cần một collection, tăng noise và processing cost.

## 8. Alternatives

Transactional Outbox phù hợp khi business events cần explicit semantic contract thay vì raw data changes. CDC platform như Debezium phù hợp ecosystem đa database. Polling vẫn hợp với workload nhỏ, latency không quan trọng và complexity budget thấp.

## 9. Trade-offs

### Advantages

* Gần real-time mà không polling liên tục.
* Có resume mechanism.
* Tốt cho projections/cache invalidation/integration adapters.

### Costs / Risks

* Event là data-change semantics, không nhất thiết business-event semantics.
* Recovery phụ thuộc oplog retention.
* Idempotency và checkpointing vẫn bắt buộc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu stream thay đổi khác polling.

### Middle

Biết watch, filter và lưu resume token.

### Senior

Thiết kế idempotency, lag monitoring, rebuild và failure recovery.

### Technical Lead / Architect

Quyết định khi nào dùng CDC/change stream và khi nào domain cần explicit integration events/outbox.

## 11. Key takeaway

* Change Streams giải quyết observation của data changes, không tự giải quyết business messaging.
* Resume token giúp recovery nhưng không thay thế durable design.
* Projection consumer phải chịu được duplicate và có rebuild path.

# 6. Redis distributed lock với fencing token: vì sao TTL lock đơn thuần chưa đủ bảo vệ resource quan trọng

## 1. What is it?

Distributed lock thường dùng Redis `SET key value NX PX ttl` để một worker giành quyền xử lý resource trong thời gian hữu hạn. Fencing token bổ sung một sequence tăng dần cho mỗi lần lock được cấp, để downstream resource có thể từ chối writer cũ.

Mental model:

```text
Worker A gets lock, token 41
A pauses 20s
lock expires
Worker B gets lock, token 42
B writes with 42
A wakes up and tries write with 41 → reject
```

## 2. Why does it exist?

TTL chỉ nói lock entry hết hạn. Nó không thể ép process cũ ngừng chạy. GC pause, network partition hoặc CPU stall có thể khiến worker giữ “niềm tin” rằng nó vẫn sở hữu lock sau khi lease đã hết và worker khác đã tiếp quản.

Nếu cả hai cùng ghi side effect, lock đã không bảo vệ correctness.

## 3. How does it work?

Lock acquisition cấp token đơn điệu tăng. Resource cuối cùng — database row, storage service hoặc coordinator — nhớ token cao nhất đã chấp nhận và reject request có token thấp hơn.

```text
acceptedToken = 42
request token 41 → stale → reject
request token 43 → accept, advance
```

Điểm cốt lõi: fencing phải được enforce ở nơi side effect xảy ra. Token chỉ nằm trong Redis mà downstream không kiểm tra thì không có tác dụng.

## 4. Practical implementation

Pseudo flow:

```csharp
var lease = await lockService.TryAcquireAsync(resourceId, ct);
if (lease is null)
    return;

await storage.UpdateAsync(
    resourceId,
    fencingToken: lease.Token,
    cancellationToken: ct);
```

Downstream SQL có thể dùng version/token condition:

```sql
UPDATE resource
SET value = @value,
    fencing_token = @token
WHERE id = @id
  AND fencing_token < @token;
```

Nếu affected rows = 0, writer có thể đã stale.

## 5. Real production scenario

Hai workers generate monthly invoice cho cùng customer. Worker A có Redis lease nhưng bị long GC pause. Lease hết hạn, Worker B acquire và tạo invoice. A tiếp tục rồi cũng tạo invoice thứ hai.

TTL lock giảm probability nhưng không bảo đảm correctness. Fencing token hoặc database uniqueness/idempotency constraint mới chặn stale writer/duplicate side effect.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate processing vẫn xảy ra dù logs chứng minh tại mỗi thời điểm Redis chỉ có một lock owner.

**Evidence** → worker cũ hoàn tất side effect sau thời điểm lease hết hạn.

**Hypothesis** → lease expiration không đồng nghĩa worker execution bị hủy.

**Diagnosis** → correlate lock acquisition/expiry/token với side-effect timestamp.

**Fix** → thêm idempotency/unique constraint hoặc fencing token được enforce downstream; dùng cancellation chỉ như best-effort optimization.

**Verification** → inject process pause dài hơn TTL và xác nhận stale worker không thể commit side effect.

## 7. Common mistakes

* Nghĩ lock TTL = mutual exclusion tuyệt đối.
* Renew lease nhưng không xử lý network partition.
* Release lock bằng `DEL` mà không kiểm tra owner token/value.
* Dùng distributed lock cho vấn đề database có thể giải bằng unique constraint/atomic update đơn giản hơn.
* Không test pause vượt TTL.

## 8. Alternatives

Database advisory locks/row locks phù hợp nếu resource nằm cùng database. Unique constraints + idempotency thường tốt hơn cho duplicate creation. Queue partition/session có thể serialize work theo key. Single-writer architecture loại bỏ nhu cầu lock trong một số domain.

## 9. Trade-offs

### Advantages

* Lease giúp điều phối workers phân tán.
* Fencing bảo vệ khỏi stale holder tốt hơn TTL-only design.

### Costs / Risks

* Downstream phải hiểu token.
* Sequence generation và persistence tăng complexity.
* Lock service vẫn là dependency operational.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu lock có timeout và owner identity.

### Middle

Biết atomic acquire/release và lease renewal.

### Senior

Hiểu stale holder, fencing, idempotency và failure under pauses/partitions.

### Technical Lead / Architect

Ưu tiên invariant ở system of record; chỉ dùng distributed lock khi simpler serialization/constraint không đáp ứng được.

## 11. Key takeaway

* TTL lock không thể dừng process cũ sau expiry.
* Fencing token biến quyền sở hữu thành thứ tự mà downstream có thể enforce.
* Database constraint/idempotency thường là lớp correctness cuối cùng đáng tin cậy hơn lock đơn thuần.

# 7. Azure App Configuration + feature flags: rollout runtime an toàn mà không biến config refresh thành trạng thái khó kiểm soát

## 1. What is it?

Azure App Configuration là service quản lý application settings và feature flags tập trung. Application có thể load configuration lúc startup và refresh theo runtime policy thay vì phải redeploy chỉ để đổi flag/config.

Feature flag tách “code deployed” khỏi “feature exposed”.

## 2. Why does it exist?

Một release lớn có thể cần deploy code trước rồi bật dần cho internal users, 5%, 25%, 100% traffic. Nếu enablement gắn cứng vào deployment, rollback exposure đồng nghĩa rollback artifact — chậm và rủi ro hơn.

Central configuration cũng giúp tránh mỗi instance có file config thủ công khác nhau.

## 3. How does it work?

Application provider đọc key-values từ App Configuration. Refresh có thể dựa trên sentinel/key registration và khoảng thời gian tối thiểu. Feature Management layer đánh giá flag theo conditions như percentage, time window hoặc custom filter.

Điểm quan trọng: refresh thường eventual, không phải mọi instance đổi trạng thái đúng cùng một nanosecond.

## 4. Practical implementation

Ví dụ đăng ký provider và feature management cần có refresh policy bounded. Business code kiểm tra flag ở boundary rõ:

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
{
    return await newCheckout.ExecuteAsync(request, ct);
}

return await legacyCheckout.ExecuteAsync(request, ct);
```

Đừng rải `IsEnabledAsync()` hàng chục nơi cho cùng một feature; hãy đặt ở orchestration boundary để behavior dễ reason/test.

## 5. Real production scenario

Team deploy checkout engine mới nhưng để flag off. Sau smoke test production, bật 5% rồi 25%. Metrics cho thấy payment timeout tăng ở 25%, nên team tắt flag ngay mà không rollback deployment. Code vẫn ở production để investigation tiếp tục.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng thời điểm một số instances chạy feature mới, số khác vẫn chạy cũ lâu hơn dự kiến.

**Evidence** → App Configuration đã đổi nhưng refresh timestamp khác nhau giữa instances.

**Hypothesis** → refresh interval/cache behavior bị hiểu như strong consistency.

**Diagnosis** → log flag evaluation version/timestamp với low-cardinality metadata; kiểm tra provider refresh configuration và network access.

**Fix** → thiết kế rollout chịu được mixed-version/mixed-flag window; nếu operation cần atomic global switch, feature flag eventual refresh có thể không phải primitive phù hợp.

**Verification** → multi-instance test và đo propagation window thực tế.

## 7. Common mistakes

* Dùng feature flag như permanent business configuration không có lifecycle.
* Không xóa flags đã rollout xong, tạo “flag debt”.
* Rải branch khắp domain code.
* Cho flag thay đổi invariant giữa hai services mà không tính propagation lag.
* Đưa secrets vào App Configuration thay vì Key Vault/reference phù hợp.

## 8. Alternatives

Environment variables tốt cho immutable deployment config. Database-admin configuration phù hợp business settings cần transaction/audit riêng. Deployment slots/canary infrastructure phù hợp rollout cả artifact/network path chứ không chỉ code branch.

## 9. Trade-offs

### Advantages

* Tách deploy khỏi release exposure.
* Rollback feature nhanh.
* Central management và targeting.

### Costs / Risks

* Runtime behavior trở thành dynamic state.
* Mixed evaluations trong refresh window.
* Flag debt làm code khó hiểu lâu dài.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu flag cho phép code tồn tại nhưng chưa bật.

### Middle

Biết refresh, targeting và fallback behavior.

### Senior

Thiết kế mixed-state tolerance, telemetry và flag cleanup lifecycle.

### Technical Lead / Architect

Đặt governance: owner, expiry date, rollout metrics, kill switch semantics và khi nào config không được phép dynamic.

## 11. Key takeaway

* Feature flag là release-control mechanism, không phải nơi chứa mọi business rule.
* Runtime refresh có consistency semantics cần được thiết kế rõ.
* Mỗi flag nên có owner và ngày xóa, nếu không codebase sẽ tích lũy trạng thái khó reason.

# 8. Kubernetes PodDisruptionBudget + topology spread: giữ availability khi node maintenance, rollout và zone failure xảy ra

## 1. What is it?

PodDisruptionBudget (PDB) giới hạn số replicas có thể bị voluntary disruption cùng lúc. Topology spread constraints hướng scheduler phân bố pods qua node/zone để replicas không dồn vào cùng failure domain.

Hai cơ chế giải hai phần khác nhau của availability:

```text
PDB → bao nhiêu pod có thể bị chủ động evict?
Topology spread → các pod nằm ở đâu?
```

## 2. Why does it exist?

Có 6 replicas không có nghĩa high availability nếu cả 6 nằm trên cùng node hoặc cùng zone. Tương tự, cluster maintenance có thể evict nhiều pods cùng lúc nếu không có policy bảo vệ capacity tối thiểu.

## 3. How does it work?

Ví dụ PDB:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: orders-api
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app: orders-api
```

Topology spread có thể yêu cầu scheduler cân bằng theo `topology.kubernetes.io/zone` với `maxSkew` phù hợp.

PDB chỉ áp dụng voluntary disruptions như drain/eviction; nó không ngăn node crash, OOM hay zone outage.

## 4. Practical implementation

Thiết kế từ SLO và capacity:

```text
replicas = 6
minimum serving capacity = 4
zones = 3
```

Có thể đặt PDB giữ tối thiểu 4, và topology spread phân tán 2/2/2 nếu cluster capacity cho phép. Nhưng constraints quá cứng có thể khiến pods Pending khi một zone thiếu capacity.

## 5. Real production scenario

Một service có 8 replicas nhưng scheduler đặt 6 replicas trên một node pool nhỏ do resource fit. Node upgrade drain cùng lúc làm service mất phần lớn capacity, p99 tăng mạnh dù “replica count = 8”.

Sau khi thêm topology policy và PDB phù hợp, maintenance chỉ giảm capacity có kiểm soát và replicas được phân bố tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → node drain bị treo vì eviction không tiến; hoặc deployment không schedule đủ replicas.

**Evidence** → events báo PDB prevents eviction hoặc topology constraints unsatisfiable.

**Hypothesis** → availability policy không tương thích cluster capacity/current replica count.

**Diagnosis** → kiểm tra desired/ready replicas, PDB status, zones/nodes khả dụng, resource requests và scheduler events.

**Fix** → điều chỉnh replica count/capacity/PDB/constraint dựa trên minimum serving capacity; không “fix” bằng xóa PDB ngay trong production mà không đánh giá impact.

**Verification** → controlled node drain và zone-capacity simulation.

## 7. Common mistakes

* Nghĩ PDB bảo vệ khỏi mọi outage.
* `minAvailable` bằng 100%, khiến maintenance không thể tiến.
* Topology constraint cứng nhưng cluster chỉ có một zone thực tế có capacity.
* Không tính autoscaler interaction.
* Replica count cao nhưng tất cả pods dùng cùng downstream bottleneck nên service vẫn không resilient.

## 8. Alternatives

Pod anti-affinity có thể phân tán pods nhưng thường cứng/đắt scheduler hơn. Multi-cluster/multi-region cần cho failure domain lớn hơn. Infrastructure canary/rolling strategy giải deployment sequencing nhưng không thay topology resilience.

## 9. Trade-offs

### Advantages

* Bảo vệ serving capacity trong voluntary maintenance.
* Giảm correlated failure do co-location.

### Costs / Risks

* Scheduling khó hơn.
* Cần dư capacity để constraints có thể thỏa.
* PDB quá nghiêm làm maintenance/upgrade bị block.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu replicas cần được phân bố, không chỉ đếm số lượng.

### Middle

Biết PDB, node drain và topology keys.

### Senior

Kết hợp scheduler, autoscaler, resource requests và failure-domain testing.

### Technical Lead / Architect

Chuyển availability SLO thành replica/capacity/disruption policy có thể kiểm chứng bằng game day.

## 11. Key takeaway

* Replica count không tự động tạo fault isolation.
* PDB kiểm soát voluntary disruption; topology spread kiểm soát placement.
* Availability policy phải phù hợp capacity thật, nếu không nó chỉ chuyển outage thành scheduling deadlock.

# 9. OAuth 2.0 Authorization Code + PKCE: bảo vệ browser/mobile login flow mà không nhầm OAuth với authentication

## 1. What is it?

OAuth 2.0 là authorization framework để client nhận access token truy cập protected resource. Authorization Code flow dùng một short-lived authorization code đổi lấy token. PKCE (`Proof Key for Code Exchange`) ràng buộc code với client instance đã khởi tạo flow.

OIDC bổ sung identity layer lên OAuth để cung cấp authentication semantics và ID Token.

## 2. Why does it exist?

Public clients như SPA/mobile không thể giữ client secret an toàn. Nếu attacker intercept authorization code, họ có thể cố đổi code lấy token. PKCE thêm verifier/challenge để authorization code bị đánh cắp một mình không đủ.

## 3. How does it work?

Client tạo random `code_verifier`, derive `code_challenge` và gửi challenge ở authorization request:

```text
Client → /authorize?code_challenge=...
      ← authorization code
Client → /token { code, code_verifier }
```

Authorization server kiểm tra verifier khớp challenge trước khi cấp token.

Nếu ứng dụng cần biết user identity, dùng OIDC scopes/ID Token đúng validation; không suy diễn identity tùy tiện từ access token dành cho API khác.

## 4. Practical implementation

Trong ASP.NET Core, ưu tiên standards-based authentication libraries/middleware thay vì tự ghép protocol requests. Validation cần kiểm tra issuer, audience, signature, expiry, nonce/state theo flow và key rotation.

Với BFF, browser có thể giữ session cookie HTTP-only còn backend xử lý token exchange/server-side token storage, giảm token exposure trong JavaScript.

## 5. Real production scenario

Một SPA cũ dùng implicit-style token handling và lưu access token dài hạn trong `localStorage`. XSS nhỏ biến thành token theft. Modernization chuyển sang Authorization Code + PKCE và BFF/session cookie, giảm giá trị token trực tiếp nằm trong browser runtime.

## 6. Failure scenario & troubleshooting

**Symptom** → login redirect thành công nhưng callback báo `invalid_grant` khi đổi code.

**Evidence** → code chưa expired nhưng `code_verifier` khác/verifier bị mất giữa redirect.

**Hypothesis** → PKCE state không được persist/correlate đúng hoặc callback bị replay.

**Diagnosis** → trace correlation ID, state, challenge method và token endpoint error mà không log raw tokens/secrets.

**Fix** → dùng library chuẩn, bảo đảm state/verifier lifecycle đúng và một code chỉ được redeem một lần.

**Verification** → security tests cho replay, wrong verifier, expired code, wrong issuer/audience và key rotation.

## 7. Common mistakes

* Gọi OAuth là “login protocol” mà không phân biệt OIDC.
* Tự parse JWT rồi bỏ signature/audience validation.
* Log access/refresh token.
* Dùng access token của API A để xác thực API B.
* Nghĩ PKCE thay thế `state`, CSRF protection hoặc secure redirect URI validation.

## 8. Alternatives

Server-rendered app truyền thống có thể dùng confidential-client code flow với server-side session. mTLS/private-key JWT phù hợp machine-to-machine ở maturity cao hơn. API keys chỉ hợp use case đơn giản không cần delegated user authorization.

## 9. Trade-offs

### Advantages

* Standards-based delegated authorization.
* PKCE bảo vệ code interception tốt hơn cho public clients.
* Ecosystem/library support mạnh.

### Costs / Risks

* Protocol có nhiều moving parts.
* Token/session lifecycle, revocation và key rotation cần vận hành đúng.
* Sai validation tạo security bug nghiêm trọng dù flow nhìn “chạy được”.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt access token, ID token và refresh token.

### Middle

Hiểu Authorization Code + PKCE, state, redirect URI và token validation.

### Senior

Thiết kế browser/BFF boundaries, rotation, logout và downstream token propagation.

### Technical Lead / Architect

Chuẩn hóa identity architecture, tránh custom protocol code và threat-model token exposure xuyên frontend/backend/services.

## 11. Key takeaway

* OAuth giải authorization; OIDC thêm authentication/identity.
* PKCE ràng buộc authorization code với client flow đã khởi tạo.
* Security nằm ở validation và token lifecycle đầy đủ, không chỉ ở việc nhận được JWT.

# 10. Optimizely CMS content model evolution: đổi property/type an toàn mà không phá published content và editor workflow

## 1. What is it?

Optimizely content types được định nghĩa qua code model và metadata. Khi code thay đổi property name/type, hệ thống phải reconcile model mới với content definitions và dữ liệu đã tồn tại.

Đây là schema evolution của CMS, không chỉ là refactor C# class.

## 2. Why does it exist?

Production CMS có hàng nghìn published pages/blocks. Rename property bằng IDE có thể compile thành công nhưng CMS lại coi property cũ bị xóa và property mới được tạo, làm existing editor data không còn map như mong đợi.

Vì content sống lâu hơn một deployment, model changes cần migration semantics rõ.

## 3. How does it work?

Content model chứa stable identifiers/metadata mà CMS dùng để đồng bộ code model với definitions. Các thay đổi an toàn phụ thuộc loại change:

```text
add optional property        → thường backward-compatible
rename property              → cần migration/metadata-aware strategy
change primitive type        → cần convert/validate existing values
split one block into two     → cần content migration
remove property              → cần xác nhận data không còn dùng
```

Một rollout an toàn thường theo expand-and-contract:

1. Thêm property/model mới nhưng vẫn đọc cũ.
2. Migrate existing content có kiểm soát.
3. Deploy rendering hỗ trợ cả old/new shape nếu cần mixed window.
4. Verify published pages, preview, language branches.
5. Chỉ sau đó xóa property cũ.

Migration nên idempotent và có dry-run/report trước khi write hàng loạt.

Team tạo property mới, migration map URL sang media item, báo các URL không resolve được, update rendering để fallback cũ trong một release rồi mới retire field cũ.

## 6. Failure scenario & troubleshooting

**Symptom** → sau deploy, editor thấy field mới rỗng trong khi site trước đó có dữ liệu.

**Evidence** → content versions vẫn chứa value theo old property definition hoặc migration chưa chạy/không match language/version.

**Hypothesis** → code refactor đã thay identity/type mà không có content migration path.

**Diagnosis** → inspect content type synchronization, existing versions, language branches và migration logs; không sửa trực tiếp DB tùy tiện.

**Fix** → restore compatibility model, chạy migration qua supported APIs và verify content trước khi remove old definition.

**Verification** → snapshot representative pages/blocks, preview + published rendering, multi-language and rollback test.

## 7. Common mistakes

* Rename property như refactor C# thuần túy.
* Đổi type destructive trên production content mà không inventory existing values.
* Migration chỉ xử lý current language/current version.
* Script không idempotent, retry tạo duplicate content.
* Xóa property cũ cùng release thêm property mới, không có rollback window.

## 8. Alternatives

Giữ legacy property nếu migration cost lớn hơn giá trị thay đổi. Adapter/view-model mapping có thể che old shape khỏi rendering layer mà không migrate ngay. Với redesign lớn, tạo block/content type mới rồi migrate dần thường an toàn hơn biến đổi type cũ tại chỗ.

## 9. Trade-offs

### Advantages của staged evolution

* Giảm risk mất content.
* Có rollback window.
* Editor workflow ít gián đoạn hơn.

### Costs / Risks

* Tạm thời phải hỗ trợ hai schemas.
* Migration tooling/testing tốn công.
* Cleanup bị trì hoãn có thể để lại legacy fields lâu dài.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu content model là persistent schema, không chỉ C# class.

### Middle

Biết add/rename/type-change có mức độ rủi ro khác nhau và test editor/rendering.

### Senior

Thiết kế idempotent migration, fallback, version/language coverage và rollback.

### Technical Lead / Architect

Đặt CMS schema-change process: inventory → expand → migrate → verify → contract, kèm backup/observability và ownership rõ.

## 11. Key takeaway

* CMS model refactor có thể là data migration dù compiler không báo lỗi.
* Expand-and-contract an toàn hơn destructive one-step change.
* Luôn bảo vệ existing published content và editor workflow trước sự tiện lợi của code refactor.
