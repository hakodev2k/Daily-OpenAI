# 1. C# `Channel<T>` + bounded producer/consumer: tạo backpressure cho background pipelines thay vì để queue trong memory tăng vô hạn

## 1. What is it?

`Channel<T>` là abstraction producer/consumer trong .NET cho phép một hoặc nhiều producer ghi work items và một hoặc nhiều consumer đọc chúng bất đồng bộ.

Mental model:

```text
Producer(s)
    ↓
Bounded Channel<T>
    ↓
Consumer(s)
```

Điểm quan trọng không phải chỉ là “queue thread-safe”. Với bounded channel, capacity trở thành một phần của flow control. Khi channel đầy, producer có thể phải `await` thay vì tiếp tục đẩy dữ liệu vào memory vô hạn.

## 2. Why does it exist?

Một background pipeline ngây thơ thường dùng `ConcurrentQueue<T>` hoặc `List<Task>` rồi enqueue nhanh hơn consumer xử lý.

Khi downstream chậm:

* queue length tăng liên tục
* memory tăng
* latency của work item tăng
* process có thể OOM trước khi downstream hồi phục

Bounded `Channel<T>` tạo backpressure để producer cảm nhận được khả năng xử lý thực tế của hệ thống.

## 3. How does it work?

Channel có writer và reader:

```text
ChannelWriter<T> → buffer → ChannelReader<T>
```

Với bounded channel:

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait
});
```

Khi có 100 items chưa xử lý, `WriteAsync` chờ cho tới khi consumer đọc bớt.

Đó chính là backpressure: downstream capacity kiểm soát upstream throughput.

## 4. Practical implementation

```csharp
public sealed class JobQueue
{
    private readonly Channel<Job> _channel =
        Channel.CreateBounded<Job>(new BoundedChannelOptions(100)
        {
            FullMode = BoundedChannelFullMode.Wait,
            SingleReader = false,
            SingleWriter = false
        });

    public ValueTask EnqueueAsync(Job job, CancellationToken ct) =>
        _channel.Writer.WriteAsync(job, ct);

    public IAsyncEnumerable<Job> ReadAllAsync(CancellationToken ct) =>
        _channel.Reader.ReadAllAsync(ct);
}
```

Consumer:

```csharp
public sealed class JobWorker(JobQueue queue) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in queue.ReadAllAsync(stoppingToken))
        {
            await ProcessAsync(job, stoppingToken);
        }
    }
}
```

## 5. Real production scenario

Một API nhận requests tạo thumbnail. Producer có thể nhận 1.000 requests/giây nhưng image processor chỉ xử lý 100 jobs/giây.

Nếu dùng unbounded queue, backlog tăng 900 jobs mỗi giây. Sau vài phút, memory tăng mạnh và pod bị restart.

Bounded channel buộc API hoặc upstream workflow phải chậm lại, reject, hoặc chuyển sang durable queue như Azure Service Bus.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng đều dù CPU không cao.

**Evidence** → queue depth trong process tăng liên tục; consumer throughput thấp hơn producer rate.

**Hypothesis** → unbounded buffering.

**Diagnosis** → đo enqueue rate, dequeue rate và queue depth.

**Fix** → bounded channel, explicit capacity, hoặc chuyển sang durable broker.

**Verification** → dưới load vượt capacity, memory giữ ổn định và producer latency/rejection phản ánh overload thay vì OOM.

## 7. Common mistakes

* Dùng unbounded channel mặc định cho workload có thể burst lớn.
* Chọn capacity tùy ý không dựa trên latency/resource budget.
* Swallow exception trong consumer khiến item biến mất.
* Dùng in-memory channel cho work bắt buộc phải survive process restart.
* Không hoàn tất writer hoặc xử lý graceful shutdown.

## 8. Alternatives

* `ConcurrentQueue<T>`: đơn giản nhưng không có async waiting/backpressure tích hợp.
* `BlockingCollection<T>`: phù hợp synchronous/legacy scenarios hơn.
* Azure Service Bus / RabbitMQ: phù hợp khi cần durability, distributed consumers và retry semantics.

## 9. Trade-offs

### Advantages

* Backpressure rõ ràng.
* Async-friendly.
* Rất nhẹ cho in-process pipelines.

### Costs / Risks

* Không durable.
* Capacity và overflow policy phải thiết kế.
* Process crash làm mất items chưa persist.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu producer nhanh hơn consumer sẽ tạo backlog.

### Middle

Biết dùng bounded channel, cancellation và background consumer.

### Senior

Đánh giá capacity, failure semantics, retry, shutdown và memory behavior.

### Technical Lead / Architect

Quyết định boundary nào nên dùng in-process queue và khi nào durability/scale yêu cầu external broker.

## 11. Key takeaway

* Queue không giới hạn là hidden memory risk.
* Backpressure phải là phần của thiết kế, không phải hậu quả tình cờ.
* `Channel<T>` phù hợp in-process; durable work nên dùng durable messaging.

# 2. ASP.NET Core API Versioning + backward compatibility: thay đổi contract mà không phá client đang chạy Production

## 1. What is it?

API versioning là cách cho phép nhiều phiên bản contract cùng tồn tại trong một giai đoạn migration.

Mental model:

```text
Client v1 ──> /api/v1/orders
Client v2 ──> /api/v2/orders
```

Nhưng versioning chỉ là cơ chế routing/contract selection. Vấn đề lớn hơn là backward compatibility: thay đổi nào client cũ vẫn chịu được, thay đổi nào là breaking change.

## 2. Why does it exist?

Production clients không deploy đồng thời với server. Mobile app, partner integration hoặc frontend cached bundle có thể còn dùng contract cũ nhiều tuần hoặc nhiều tháng.

Nếu đổi response field, semantics hoặc validation ngay lập tức, server có thể deploy thành công nhưng client đang chạy bị phá.

## 3. How does it work?

Một change thường thuộc hai nhóm:

**Backward-compatible**:

* thêm optional response field
* thêm optional request field
* thêm endpoint mới

**Potentially breaking**:

* rename/remove field
* thay type
* đổi status code semantics
* biến optional thành required
* thay interpretation của giá trị hiện có

Versioning cho phép contract cũ và mới cùng tồn tại trong transition window.

## 4. Practical implementation

Một approach URL-based rõ ràng:

```csharp
app.MapGet("/api/v1/orders/{id:guid}", async (Guid id, OrderService service, CancellationToken ct) =>
{
    var order = await service.GetAsync(id, ct);
    return order is null
        ? Results.NotFound()
        : Results.Ok(new OrderV1(order.Id, order.Total));
});

app.MapGet("/api/v2/orders/{id:guid}", async (Guid id, OrderService service, CancellationToken ct) =>
{
    var order = await service.GetAsync(id, ct);
    return order is null
        ? Results.NotFound()
        : Results.Ok(new OrderV2(order.Id, order.Total, order.Currency));
});
```

Domain/application logic có thể reuse; DTO contract được version độc lập.

## 5. Real production scenario

Một mobile app v1 hiểu `total` là số tiền theo default currency. Backend cần hỗ trợ multi-currency.

Thêm `currency` có thể backward-compatible nếu semantics cũ vẫn đúng. Nhưng đổi `total` thành object `{ amount, currency }` sẽ phá parser cũ.

Version v2 cho phép thiết kế contract sạch hơn trong khi v1 vẫn hoạt động đến khi adoption đủ cao.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment backend thành công nhưng mobile crash rate tăng.

**Evidence** → errors parse JSON xuất hiện trên app versions cũ.

**Hypothesis** → breaking contract change.

**Diagnosis** → compare OpenAPI/schema trước và sau release; kiểm tra telemetry theo client version.

**Fix** → restore contract cũ hoặc phục vụ version riêng.

**Verification** → contract tests và telemetry theo version phải ổn định.

## 7. Common mistakes

* Version mọi thay đổi nhỏ dù không breaking.
* Dùng cùng DTO cho domain, persistence và external contract.
* Remove field vì “frontend mới không dùng nữa”.
* Không có deprecation policy.
* Nghĩ OpenAPI diff thay thế hoàn toàn consumer contract tests.

## 8. Alternatives

* Additive evolution không cần version mới khi change thật sự compatible.
* Header/query-string versioning giảm URL churn nhưng visibility thấp hơn.
* Consumer-driven contract tests giúp phát hiện incompatibility trước deploy.

## 9. Trade-offs

### Advantages

* Giảm blast radius khi contract thay đổi.
* Cho phép client migration dần.

### Costs / Risks

* Multiple versions tăng maintenance cost.
* Business logic có thể phân nhánh phức tạp.
* Deprecated versions dễ sống quá lâu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu server và client không deploy cùng lúc.

### Middle

Biết nhận diện breaking changes và giữ DTO contract riêng.

### Senior

Thiết kế migration/deprecation, telemetry và contract tests.

### Technical Lead / Architect

Quyết định versioning strategy, support window và ownership của compatibility guarantees.

## 11. Key takeaway

* Versioning là migration tool, không phải mục tiêu.
* Backward compatibility nên được ưu tiên trước khi tạo version mới.
* External contract phải có lifecycle riêng với domain model.

# 3. EF Core compiled queries: giảm query-compilation overhead khi query shape nóng và ổn định

## 1. What is it?

EF Core phải biến LINQ expression tree thành query model và SQL trước khi database thực thi. EF Core có query caching nội bộ, nhưng compiled query cho phép precompile một query shape để giảm overhead ở hot path.

Mental model:

```text
LINQ expression
   ↓ compile/translate
SQL command
   ↓
Database
```

Compiled query tối ưu phần trước khi database execution; nó không làm slow SQL trở thành fast SQL.

## 2. Why does it exist?

Trong hầu hết business APIs, database/network latency lớn hơn query compilation nhiều lần. Nhưng với endpoint cực nóng, query đơn giản, cache hit cao và latency budget rất thấp, overhead ở application layer có thể trở nên đáng kể.

## 3. How does it work?

Một compiled query giữ query shape đã được biên dịch để tái sử dụng với parameters khác nhau.

```csharp
private static readonly Func<AppDbContext, Guid, Order?> GetOrder =
    EF.CompileQuery((AppDbContext db, Guid id) =>
        db.Orders
            .AsNoTracking()
            .SingleOrDefault(x => x.Id == id));
```

Mỗi call dùng cùng expression shape nhưng parameter khác.

## 4. Practical implementation

Async variant:

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<OrderDto>> Query =
    EF.CompileAsyncQuery((AppDbContext db, Guid customerId) =>
        db.Orders
            .AsNoTracking()
            .Where(x => x.CustomerId == customerId)
            .OrderByDescending(x => x.CreatedAt)
            .Take(20)
            .Select(x => new OrderDto(x.Id, x.Number, x.Total)));
```

Consumer:

```csharp
await foreach (var order in Query(db, customerId).WithCancellation(ct))
{
    // consume result
}
```

Chỉ nên dùng sau measurement.

## 5. Real production scenario

Một endpoint authorization lookup chạy hàng chục nghìn lần/giây. Query chỉ đọc một row theo indexed key và database latency rất thấp.

Profiling cho thấy EF query pipeline chiếm tỷ lệ đáng kể CPU. Compiled query có thể giảm overhead hữu ích.

Ngược lại, query report mất 800 ms vì scan hàng triệu rows sẽ không được cứu bằng compiled query.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries nhưng p95 gần như không đổi.

**Evidence** → trace cho thấy 95% thời gian ở SQL dependency.

**Hypothesis** → bottleneck bị xác định sai.

**Diagnosis** → breakdown app CPU vs database latency.

**Fix** → tối ưu query/index/access pattern thay vì EF compilation.

**Verification** → benchmark trước/sau và production telemetry.

## 7. Common mistakes

* Dùng compiled query như default cho mọi repository method.
* Tối ưu application overhead trước slow SQL.
* Tạo dynamic query shapes rồi cố compile từng biến thể.
* Bỏ qua `AsNoTracking`/projection trong read path.

## 8. Alternatives

* Dùng EF Core query cache mặc định: đủ cho phần lớn ứng dụng.
* Raw SQL/Dapper: hữu ích khi cần control SQL hoặc giảm abstraction overhead sâu hơn.
* Tối ưu database: thường mang lại tác động lớn hơn.

## 9. Trade-offs

### Advantages

* Giảm query pipeline overhead ở hot path.
* Predictable query shape.

### Costs / Risks

* Code khó đọc hơn.
* Lợi ích thường nhỏ nếu database là bottleneck.
* Dynamic queries ít phù hợp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ không đi thẳng tới database; có translation pipeline.

### Middle

Biết dùng projection, `AsNoTracking` và đo query timing.

### Senior

Biết khi nào compilation overhead thực sự đáng tối ưu.

### Technical Lead / Architect

Giữ performance discipline: chỉ đưa compiled queries vào hot paths có evidence và benchmark.

## 11. Key takeaway

* Compiled query tối ưu EF overhead, không tối ưu execution plan.
* Đo bottleneck trước.
* Với phần lớn CRUD, query cache mặc định đã đủ.

# 4. SQL Server Read Committed Snapshot Isolation: giảm reader-writer blocking bằng row versioning nhưng không loại bỏ mọi concurrency problem

## 1. What is it?

Read Committed Snapshot Isolation (RCSI) thay cách `READ COMMITTED` xử lý reads: thay vì reader phải chờ writer release lock trong nhiều tình huống, reader có thể đọc committed row version từ version store.

Mental model:

```text
Writer updates row
   ↓
old committed version retained
   ↓
reader sees old committed version
```

## 2. Why does it exist?

Trong workload OLTP, reader-writer blocking có thể tạo latency chain:

```text
long UPDATE
  ↓ blocks
SELECT
  ↓ blocks request threads
API p95/p99 tăng
```

RCSI giảm contention bằng MVCC-style row versioning cho reads.

## 3. How does it work?

Khi RCSI bật, SQL Server lưu row versions cần thiết trong version store. Query ở `READ COMMITTED` lấy committed snapshot phù hợp ở statement level thay vì đợi nhiều write locks.

Điều này không có nghĩa “không còn locks”. Writers vẫn lock khi ghi và writer-writer conflicts vẫn tồn tại.

## 4. Practical implementation

Enable ở database level cần kế hoạch deployment:

```sql
ALTER DATABASE MyDb
SET READ_COMMITTED_SNAPSHOT ON;
```

Sau đó code EF Core thường không cần đổi để queries ở default isolation hưởng behavior mới.

Trước khi bật cần kiểm tra transaction semantics hiện tại, tempdb/version-store pressure và các đoạn code dựa ngầm vào blocking behavior.

## 5. Real production scenario

Một order-processing transaction update nhiều rows trong 2 giây. Dashboard SELECT cùng tables bị block, kéo request latency lên 8–10 giây khi traffic cao.

Sau khi xác nhận reads chấp nhận statement-level committed snapshot, RCSI giảm reader-writer blocking đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → blocking giảm nhưng tempdb usage tăng mạnh.

**Evidence** → version store growth correlates với long-running transactions.

**Hypothesis** → old versions bị giữ lâu.

**Diagnosis** → kiểm tra transaction duration và version-store metrics.

**Fix** → rút ngắn transactions; capacity-plan tempdb; loại bỏ transactions mở không cần thiết.

**Verification** → blocking giảm mà version-store growth ổn định.

## 7. Common mistakes

* Nghĩ RCSI giải quyết deadlocks hoàn toàn.
* Bật Production mà không hiểu semantics thay đổi.
* Để transactions dài vì nghĩ MVCC “không block”.
* Dùng `NOLOCK` như giải pháp thay thế cho concurrency design.

## 8. Alternatives

* Default locking `READ COMMITTED`: đơn giản nhưng có reader-writer blocking.
* Snapshot Isolation: transaction-level snapshot rõ hơn nhưng semantics khác và cần explicit use.
* Query/index/transaction redesign: nhiều blocking vấn đề nên xử lý ở root cause.

## 9. Trade-offs

### Advantages

* Giảm reader-writer blocking.
* Cải thiện concurrency cho read-heavy OLTP.

### Costs / Risks

* Version-store overhead.
* Semantics reads thay đổi.
* Không loại bỏ writer-writer conflict.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu isolation level ảnh hưởng cách transactions nhìn dữ liệu và chờ nhau.

### Middle

Biết nhận diện blocking qua DMVs/telemetry.

### Senior

Đánh giá transaction duration, tempdb pressure và consistency semantics.

### Technical Lead / Architect

Quyết định isolation policy ở database level dựa trên workload, correctness và operational capacity.

## 11. Key takeaway

* RCSI giảm blocking bằng versioning, không làm concurrency biến mất.
* Transaction dài vẫn nguy hiểm.
* Isolation level là correctness decision trước khi là performance tweak.

# 5. Redis cache stampede + single-flight: ngăn hàng nghìn requests cùng đánh database khi một hot key hết TTL

## 1. What is it?

Cache stampede xảy ra khi nhiều requests cùng miss một hot key và đồng thời tải lại dữ liệu từ source-of-truth.

```text
Hot key expires
      ↓
1000 requests miss
      ↓
1000 DB queries
```

Single-flight là chiến lược cho phép chỉ một operation refresh dữ liệu, các requests khác chờ cùng result hoặc dùng fallback.

## 2. Why does it exist?

Cache thường che database khỏi read load. Khi hot key hết TTL đúng lúc traffic cao, toàn bộ load bị chuyển đột ngột về database.

Đây là failure amplification: cache được tạo để giảm tải nhưng expiration đồng bộ lại tạo spike lớn hơn bình thường.

## 3. How does it work?

Một process có thể dùng keyed lock/semaphore để chỉ một caller refresh:

```text
miss
 ↓
acquire key lock
 ↓
check cache again
 ↓
load DB once
 ↓
set cache
 ↓
release
```

Trong multi-instance system, local single-flight chỉ deduplicate trong từng instance. Distributed lock có thể giảm toàn cluster nhưng tăng complexity và failure modes.

## 4. Practical implementation

Simplified in-process single-flight:

```csharp
private readonly ConcurrentDictionary<string, SemaphoreSlim> _locks = new();

public async Task<ProductDto> GetAsync(string key, CancellationToken ct)
{
    var cached = await cache.GetStringAsync(key, ct);
    if (cached is not null)
        return JsonSerializer.Deserialize<ProductDto>(cached)!;

    var gate = _locks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
    await gate.WaitAsync(ct);

    try
    {
        cached = await cache.GetStringAsync(key, ct);
        if (cached is not null)
            return JsonSerializer.Deserialize<ProductDto>(cached)!;

        var product = await repository.LoadAsync(key, ct);
        await cache.SetStringAsync(key, JsonSerializer.Serialize(product), ct);
        return product;
    }
    finally
    {
        gate.Release();
    }
}
```

Production implementation cần lifecycle/cleanup cho keyed locks.

## 5. Real production scenario

Homepage cache chứa promotion configuration, TTL 5 phút. Hàng chục app instances cùng hết TTL gần một thời điểm.

Mỗi instance nhận hàng nghìn requests và cùng query SQL. Database CPU nhảy từ 20% lên 95%, làm cả endpoints không liên quan chậm theo.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL QPS spike theo chu kỳ đúng TTL.

**Evidence** → Redis miss rate tăng đồng thời; nhiều identical SQL queries.

**Hypothesis** → stampede.

**Diagnosis** → correlate cache expiration, miss count và database load.

**Fix** → single-flight, TTL jitter, stale-while-revalidate hoặc proactive refresh.

**Verification** → khi hot key expire, source-of-truth refresh count giữ gần 1 thay vì hàng nghìn.

## 7. Common mistakes

* Cho mọi key cùng TTL cố định và expire đồng loạt.
* Dùng distributed lock cho mọi cache miss dù không cần.
* Không re-check cache sau khi acquire lock.
* Giữ lock nếu source call bị treo mà không timeout/cancellation.
* Cache dữ liệu correctness-critical nhưng không có invalidation contract.

## 8. Alternatives

* TTL jitter: giảm synchronized expiration.
* Stale-while-revalidate: ưu tiên availability/freshness trade-off.
* Proactive refresh: phù hợp hot predictable keys.
* Không cache: đúng khi source đủ nhanh và load nhỏ.

## 9. Trade-offs

### Advantages

* Bảo vệ database khỏi burst.
* Giảm duplicate work.

### Costs / Risks

* Locking logic phức tạp.
* Distributed single-flight tăng dependency/failure modes.
* Waiting callers có thể tăng latency khi refresh chậm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss đồng thời có thể tạo spike.

### Middle

Biết double-check sau lock và thêm TTL jitter.

### Senior

Đánh giá stale tolerance, timeout, lock scope và multi-instance behavior.

### Technical Lead / Architect

Quyết định cache strategy theo business freshness, source capacity và failure behavior.

## 11. Key takeaway

* Cache expiration là production event cần thiết kế.
* Single-flight giảm duplicate refresh nhưng không phải lúc nào cũng cần distributed lock.
* TTL jitter và stale strategies thường đơn giản hơn architecture phức tạp.

# 6. CQRS với một database: tách command/query intent mà chưa cần tách storage hay Event Sourcing

## 1. What is it?

CQRS — Command Query Responsibility Segregation — tách intent ghi và đọc ở application level.

```text
Command → handler → write model
Query   → handler → read projection
```

CQRS không đồng nghĩa với hai databases, messaging hay Event Sourcing.

## 2. Why does it exist?

Read và write thường có nhu cầu khác nhau:

* write cần enforce invariants
* read cần projection nhanh và DTO phù hợp UI

Nếu ép cả hai qua cùng generic service/repository model, code dễ trở thành abstraction chung quá mức và query path phải hydrate domain graph không cần thiết.

## 3. How does it work?

Với một database:

```text
POST /orders
  ↓
CreateOrderCommand
  ↓
Domain logic
  ↓
SQL Database

GET /orders/{id}
  ↓
GetOrderQuery
  ↓
Projection
  ↓
Same SQL Database
```

Transaction model vẫn đơn giản vì chỉ một source-of-truth.

## 4. Practical implementation

Command:

```csharp
public sealed record ApproveTimesheetCommand(Guid TimesheetId, Guid ApproverId);

public sealed class ApproveTimesheetHandler(AppDbContext db)
{
    public async Task HandleAsync(ApproveTimesheetCommand command, CancellationToken ct)
    {
        var timesheet = await db.Timesheets
            .SingleAsync(x => x.Id == command.TimesheetId, ct);

        timesheet.Approve(command.ApproverId);
        await db.SaveChangesAsync(ct);
    }
}
```

Query:

```csharp
public Task<TimesheetDto?> GetAsync(Guid id, CancellationToken ct) =>
    db.Timesheets
      .AsNoTracking()
      .Where(x => x.Id == id)
      .Select(x => new TimesheetDto(x.Id, x.Status, x.TotalHours))
      .SingleOrDefaultAsync(ct);
```

## 5. Real production scenario

Approval system có write rules phức tạp nhưng dashboards cần nhiều projections và filters.

CQRS một database cho phép write path giữ domain invariants trong khi read path query thẳng DTO hiệu quả, chưa cần event-driven replication.

## 6. Failure scenario & troubleshooting

**Symptom** → project nói dùng CQRS nhưng mỗi feature có hàng chục handlers chỉ wrap một dòng CRUD và complexity tăng mạnh.

**Evidence** → không có khác biệt thực tế giữa read/write concerns.

**Hypothesis** → pattern được áp dụng vì template thay vì pressure thực.

**Diagnosis** → review coupling, domain complexity và query needs.

**Fix** → simplify feature; giữ segregation nơi nó tạo value.

**Verification** → code path rõ intent hơn mà không tăng ceremony vô ích.

## 7. Common mistakes

* Đồng nhất CQRS với MediatR.
* Cho rằng CQRS bắt buộc Event Sourcing.
* Tách databases quá sớm.
* Tạo command/query class cho mọi getter/setter dù application nhỏ.
* Dùng read model làm write entity.

## 8. Alternatives

* Simple application service: tốt cho CRUD đơn giản.
* CQRS one database: tốt khi read/write concerns khác nhau nhưng consistency cần đơn giản.
* Separate read/write stores: chỉ đáng cân nhắc khi scale, model hoặc latency requirements thực sự khác biệt.

## 9. Trade-offs

### Advantages

* Intent rõ ràng.
* Read path tối ưu độc lập.
* Vẫn giữ transaction đơn giản.

### Costs / Risks

* Nhiều types/handlers hơn.
* Có thể thành ceremony.
* Team dễ overengineer thành distributed CQRS quá sớm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu command thay đổi state, query chỉ đọc state.

### Middle

Biết implement handlers và projections riêng.

### Senior

Nhận diện khi separation tạo value và khi chỉ thêm boilerplate.

### Technical Lead / Architect

Quyết định mức độ CQRS dựa trên complexity, scale và operational cost; không gắn CQRS mặc định với Event Sourcing.

## 11. Key takeaway

* CQRS bắt đầu từ separation of intent.
* Một database thường là đủ.
* Tách storage chỉ khi có pressure rõ ràng.

# 7. Azure Key Vault + Managed Identity + secret rotation: loại secret khỏi application config mà vẫn giữ ownership và rotation rõ ràng

## 1. What is it?

Azure Key Vault lưu secrets/keys/certificates ngoài application deployment. Managed Identity cho workload Azure có identity riêng để authenticate tới Key Vault mà không cần lưu client secret trong app.

```text
App Service / Function
      ↓ Managed Identity
Azure AD / Entra ID
      ↓ token
Key Vault
      ↓ secret
Application
```

## 2. Why does it exist?

Nếu connection strings hoặc API keys nằm trong source code, CI variables hoặc config files lâu dài, rotation và access control trở nên khó quản lý.

Managed Identity loại credential dùng để lấy credential khác.

## 3. How does it work?

Azure workload được gán identity. Runtime lấy token từ Azure identity endpoint. Token được dùng để gọi Key Vault theo RBAC/access policy.

Application chỉ cần biết vault URI và secret name, không cần biết password để authenticate với vault.

## 4. Practical implementation

```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri(configuration["KeyVaultUri"]!),
    credential);

KeyVaultSecret secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
var apiKey = secret.Value;
```

Production nên cache secret hợp lý thay vì gọi Key Vault trên mỗi request.

## 5. Real production scenario

Payment provider key cần rotate mỗi 90 ngày. Nếu key nằm trong App Service configuration, rotation yêu cầu update config và có thể restart/redeploy.

Với Key Vault, secret version mới có thể publish tập trung. Application strategy cần quyết định khi nào refresh version mới.

## 6. Failure scenario & troubleshooting

**Symptom** → app deploy thành công nhưng startup trả 403 khi đọc Key Vault.

**Evidence** → Managed Identity tồn tại nhưng không có role phù hợp trên vault.

**Hypothesis** → authorization misconfiguration, không phải secret name sai.

**Diagnosis** → kiểm tra principal ID, RBAC role, vault networking/private endpoint và audit logs.

**Fix** → cấp least-privilege role hoặc sửa network path.

**Verification** → identity đúng đọc được đúng secret, identity khác không đọc được.

## 7. Common mistakes

* Dùng client secret để truy cập Key Vault dù Managed Identity khả dụng.
* Cho app quyền `Owner`/broad access thay vì secret-level need.
* Gọi vault trên mỗi HTTP request.
* Rotate secret nhưng app cache vô thời hạn.
* Log secret value trong troubleshooting.

## 8. Alternatives

* App configuration secret: đơn giản hơn cho local/internal small systems nhưng rotation/audit yếu hơn.
* Environment variables: tốt cho injection nhưng vẫn cần secret store upstream.
* Kubernetes Secrets: không thay thế external secret management nếu threat model yêu cầu mạnh hơn.

## 9. Trade-offs

### Advantages

* Centralized secret management.
* Audit/access control tốt hơn.
* Loại static credential cho Azure workload.

### Costs / Risks

* Thêm runtime dependency.
* Networking/RBAC complexity.
* Rotation strategy vẫn phải thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu secret không nên nằm trong source code.

### Middle

Biết dùng `DefaultAzureCredential` và Managed Identity.

### Senior

Thiết kế caching, rotation, RBAC, networking và failure fallback.

### Technical Lead / Architect

Định nghĩa secret ownership, rotation SLA và blast radius của mỗi identity.

## 11. Key takeaway

* Key Vault không tự động giải quyết rotation; nó tạo nền tảng để rotation có thể quản lý.
* Managed Identity loại static app credential.
* Least privilege và networking vẫn là phần bắt buộc của design.

# 8. Kubernetes readiness vs liveness probes: phân biệt “pod chưa sẵn sàng nhận traffic” với “process cần restart” để tránh self-inflicted outage

## 1. What is it?

Readiness probe trả lời: **pod có nên nhận traffic lúc này không?**

Liveness probe trả lời: **process có bị kẹt tới mức cần restart không?**

Hai câu hỏi này khác nhau về semantics và action.

```text
Readiness fail → remove from Service endpoints
Liveness fail  → restart container
```

## 2. Why does it exist?

Một app có thể sống nhưng chưa sẵn sàng: đang warm cache, migration, dependency degraded.

Ngược lại process có thể thực sự deadlocked/hung và cần restart.

Nếu dùng cùng check cho cả hai, transient downstream failure có thể khiến Kubernetes restart toàn bộ pods liên tục.

## 3. How does it work?

Kubernetes định kỳ gọi probe endpoint/command.

Ví dụ:

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5

livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10
```

Readiness nên phản ánh khả năng phục vụ traffic. Liveness thường nên kiểm tra process health tối thiểu, không phụ thuộc mọi external service.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, name: "sql", tags: new[] { "ready" });

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

`/health/live` ở đây chỉ chứng minh process pipeline phản hồi; readiness mới kiểm tra SQL.

## 5. Real production scenario

SQL có outage 2 phút. Nếu liveness check phụ thuộc SQL, tất cả pods fail liveness và restart đồng loạt. Startup lại vẫn cần SQL và pods vào CrashLoopBackOff.

Trong khi đó root cause ban đầu chỉ là database outage.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment có pod restarts hàng loạt khi dependency chậm.

**Evidence** → kube events cho thấy liveness probe timeout; dependency telemetry cho thấy SQL timeout.

**Hypothesis** → liveness quá sâu.

**Diagnosis** → inspect probe endpoint dependencies.

**Fix** → đưa external dependency check sang readiness; giữ liveness tối giản.

**Verification** → khi SQL bị simulated outage, pods không restart storm nhưng được remove khỏi traffic nếu cần.

## 7. Common mistakes

* Dùng cùng endpoint cho readiness và liveness.
* Cho liveness check mọi dependency.
* Probe timeout quá ngắn so với startup behavior.
* Không có `startupProbe` cho app khởi động chậm.
* Health endpoint trả 200 dù critical readiness condition fail.

## 8. Alternatives

* `startupProbe`: phù hợp app startup lâu, tránh liveness giết app quá sớm.
* Application-level circuit breaker: xử lý dependency failure trong request path, không thay probe semantics.

## 9. Trade-offs

### Advantages

* Routing traffic chính xác hơn.
* Restart chỉ khi thật sự cần.

### Costs / Risks

* Health semantics cần thiết kế cẩn thận.
* Readiness quá strict có thể remove toàn fleet.
* Liveness quá aggressive tạo restart storm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu readiness và liveness dẫn đến action khác nhau.

### Middle

Biết cấu hình ASP.NET Core health checks và Kubernetes probes.

### Senior

Thiết kế probe theo dependency criticality và failure modes.

### Technical Lead / Architect

Định nghĩa fleet-level behavior khi dependency outage để tránh health checks tự khuếch đại sự cố.

## 11. Key takeaway

* Readiness quyết định traffic; liveness quyết định restart.
* External dependency failure thường không nên trực tiếp làm fail liveness.
* Health checks là control-plane behavior, không chỉ endpoint monitoring.

# 9. Application Insights dependency telemetry + p95/p99: xác định latency nằm ở application, SQL hay external API thay vì nhìn average

## 1. What is it?

Application Insights thu thập request, dependency, exception, trace và metric telemetry. Dependency telemetry cho biết thời gian application chờ SQL, HTTP, Service Bus hoặc services khác.

Percentiles như p95/p99 mô tả tail latency tốt hơn average.

```text
Request 900 ms
 ├─ app CPU 50 ms
 ├─ SQL 700 ms
 └─ HTTP 120 ms
```

## 2. Why does it exist?

Average latency có thể che user pain.

Ví dụ:

* 95 requests = 100 ms
* 5 requests = 5 s

Average vẫn có thể trông chấp nhận được nhưng 5% users chịu trải nghiệm rất xấu.

p95/p99 giúp nhìn tail behavior.

## 3. How does it work?

Distributed tracing liên kết request span với dependency spans. Ta có thể query latency distribution theo endpoint, dependency, status code, deployment version hoặc region.

Một investigation nên tách:

```text
request duration
  ↓
self time vs dependency time
  ↓
which dependency
  ↓
why that dependency is slow
```

## 4. Practical implementation

Kusto example:

```kusto
requests
| where timestamp > ago(1h)
| summarize
    p50 = percentile(duration, 50),
    p95 = percentile(duration, 95),
    p99 = percentile(duration, 99)
  by name
| order by p95 desc
```

Dependencies:

```kusto
dependencies
| where timestamp > ago(1h)
| summarize
    count(),
    p95 = percentile(duration, 95)
  by type, target, name
| order by p95 desc
```

## 5. Real production scenario

Checkout API average latency tăng từ 220 ms lên 300 ms — nhìn không quá nghiêm trọng. Nhưng p99 tăng từ 700 ms lên 8 giây.

Trace breakdown cho thấy 2% requests gọi tax provider timeout và retry, kéo tail latency cực mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → users báo checkout “thỉnh thoảng rất chậm” nhưng dashboard average bình thường.

**Evidence** → p99 spike; dependency spans cho external Tax API kéo dài.

**Hypothesis** → tail latency do dependency retries/timeouts.

**Diagnosis** → correlate slow traces với dependency target và retry count.

**Fix** → timeout budget, circuit breaker, fallback hoặc provider escalation.

**Verification** → p95/p99 giảm sau change; không chỉ average.

## 7. Common mistakes

* Chỉ theo dõi average.
* Log request duration nhưng không instrument dependencies.
* Không có correlation/trace context.
* Alert trên CPU dù user-facing latency mới là SLI quan trọng.
* Sampling quá mạnh mà không hiểu impact lên rare slow traces.

## 8. Alternatives

* OpenTelemetry + Grafana/Tempo/Prometheus: vendor-neutral hơn.
* Elasticsearch/Kibana: mạnh cho log analytics nhưng tracing cần instrumentation phù hợp.
* Custom metrics: hữu ích cho business-specific SLI.

## 9. Trade-offs

### Advantages

* Tách bottleneck theo dependency.
* Tail latency phản ánh user pain tốt hơn average.

### Costs / Risks

* Telemetry volume/cost.
* Sampling có thể mất rare events.
* Instrumentation sai tạo kết luận sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu p95 nghĩa là 95% requests nhanh hơn hoặc bằng giá trị đó.

### Middle

Biết đọc request/dependency traces và KQL cơ bản.

### Senior

Phân biệt self time, downstream latency, retry amplification và sampling bias.

### Technical Lead / Architect

Định nghĩa SLI/SLO dựa trên user-visible latency và telemetry đủ để điều tra root cause.

## 11. Key takeaway

* Average latency thường che tail problems.
* Dependency telemetry biến “API chậm” thành câu hỏi có thể định vị.
* Quan sát p95/p99 cùng traces mới đủ để điều tra production latency.

# 10. Git bisect: cô lập commit gây regression bằng binary search thay vì đọc lịch sử thủ công

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên gây regression.

Mental model:

```text
good ---------------------- bad
            ↓ midpoint
         test result
            ↓
      halve search space
```

Thay vì kiểm tra từng commit tuần tự, mỗi bước loại bỏ khoảng một nửa candidates.

## 2. Why does it exist?

Một regression được phát hiện hôm nay nhưng last-known-good build từ 3 tuần trước. Có thể có hàng trăm commits giữa hai điểm.

Đọc PR titles hoặc đoán commit đáng ngờ không đáng tin bằng executable evidence.

## 3. How does it work?

Bắt đầu:

```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-commit>
```

Git checkout midpoint. Sau mỗi test:

```bash
git bisect good
```

hoặc:

```bash
git bisect bad
```

Cuối cùng Git xác định first bad commit.

## 4. Practical implementation

Nếu có automated regression test:

```bash
git bisect start HEAD v1.4.0
git bisect run dotnet test tests/Regression.Tests/Regression.Tests.csproj --filter FullyQualifiedName~CheckoutLatencyRegression
```

Exit code `0` = good; non-zero = bad theo script design.

Sau khi xong:

```bash
git bisect reset
```

## 5. Real production scenario

API serialization thay đổi khiến một response field biến mất. Regression chỉ được phát hiện sau nhiều merges.

Team viết một focused test tái hiện bug, dùng `git bisect run`, và tìm commit gây lỗi trong vài bước thay vì review hàng chục PR thủ công.

## 6. Failure scenario & troubleshooting

**Symptom** → `git bisect` đưa ra commit không liên quan hoặc results không ổn định.

**Evidence** → cùng commit lúc test pass lúc fail.

**Hypothesis** → test không deterministic hoặc environment dependency thay đổi.

**Diagnosis** → rerun test nhiều lần tại cùng SHA.

**Fix** → ổn định fixture, pin dependency/version hoặc dùng skip cho commit không test được.

**Verification** → rerun bisect với deterministic test và confirm first bad commit manually.

## 7. Common mistakes

* Chọn “good” commit chưa thật sự xác nhận tốt.
* Dùng flaky test.
* Quên reset sau bisect.
* Kết luận commit gây bug chỉ vì bisect chỉ tới đó mà không đọc diff/context.
* Không thêm regression test sau khi fix.

## 8. Alternatives

* Manual history review: phù hợp khi change set rất nhỏ.
* `git log -S` / `-G`: tốt khi biết symbol/text thay đổi.
* Observability + deployment correlation: tốt khi regression gắn rõ release.

## 9. Trade-offs

### Advantages

* Tìm regression source rất nhanh với history lớn.
* Evidence-driven.
* Tự động hóa được.

### Costs / Risks

* Cần reproducible test.
* Một số historical commits có thể không build.
* Không giải thích root cause; chỉ thu hẹp commit.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu binary search giúp giảm số commits phải kiểm tra.

### Middle

Biết chạy bisect thủ công và reset repository.

### Senior

Biết tạo deterministic reproducer và dùng `git bisect run`.

### Technical Lead / Architect

Xây engineering workflow trong đó regressions có executable tests và release history đủ sạch để diagnosis nhanh.

## 11. Key takeaway

* `git bisect` biến lịch sử commit thành search space có thể kiểm chứng.
* Giá trị của bisect phụ thuộc chất lượng reproducer.
* Sau khi tìm được commit, vẫn phải phân tích root cause và thêm regression test.
