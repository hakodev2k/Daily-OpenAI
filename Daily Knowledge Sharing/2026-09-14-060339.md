# 1. C# `IAsyncDisposable`: cleanup tài nguyên bất đồng bộ mà không biến shutdown thành blocking path

## 1. What is it?

Mental model của `IAsyncDisposable` là: object đang giữ một tài nguyên mà việc giải phóng tài nguyên đó có thể cần asynchronous I/O, vì vậy cleanup cũng phải được `await` thay vì ép chạy đồng bộ.

```text
acquire resource
      |
      v
use resource
      |
      v
await DisposeAsync()
      |
      +--> flush async
      +--> close network session
      +--> release remote resource
```

`IDisposable.Dispose()` phù hợp khi cleanup là synchronous. `IAsyncDisposable.DisposeAsync()` tồn tại cho trường hợp cleanup thực sự cần asynchronous operation.

## 2. Why does it exist?

Một số resource không thể cleanup tốt chỉ bằng synchronous API. Ví dụ buffered stream có thể cần flush xuống remote storage, database transaction wrapper có thể cần async rollback hoặc component có network session cần đóng có kiểm soát.

Nếu ép cleanup async thành sync bằng `.GetAwaiter().GetResult()` hoặc `.Wait()`, ứng dụng có thể block ThreadPool, tăng shutdown latency hoặc tạo deadlock trong môi trường có synchronization context.

## 3. How does it work?

Type implement:

```csharp
public interface IAsyncDisposable
{
    ValueTask DisposeAsync();
}
```

Caller dùng `await using`:

```csharp
await using var resource = await OpenResourceAsync(ct);
await resource.ProcessAsync(ct);
```

Compiler tạo logic gần tương đương `try/finally`, trong đó `DisposeAsync()` được await ở `finally`.

Nếu type quản lý cả synchronous và asynchronous resources, nó có thể implement cả `IDisposable` và `IAsyncDisposable`, nhưng hai paths cần ownership semantics rõ ràng để không double-dispose hoặc bỏ cleanup.

## 4. Practical implementation

Ví dụ một buffered writer cần flush bất đồng bộ:

```csharp
public sealed class AsyncReportWriter : IAsyncDisposable
{
    private readonly Stream _stream;
    private bool _disposed;

    public AsyncReportWriter(Stream stream)
    {
        _stream = stream;
    }

    public async Task WriteAsync(
        ReadOnlyMemory<byte> data,
        CancellationToken ct)
    {
        ObjectDisposedException.ThrowIf(_disposed, this);
        await _stream.WriteAsync(data, ct);
    }

    public async ValueTask DisposeAsync()
    {
        if (_disposed)
            return;

        _disposed = true;
        await _stream.FlushAsync();
        await _stream.DisposeAsync();
    }
}
```

Caller:

```csharp
await using var writer = new AsyncReportWriter(stream);
await writer.WriteAsync(payload, ct);
```

Cleanup không nên phụ thuộc mù quáng vào request cancellation token vì request đã bị hủy nhưng resource vẫn có thể cần được giải phóng hoàn chỉnh.

## 5. Real production scenario

Một background export job ghi dữ liệu lớn vào remote object storage qua stream. Sau khi ghi xong, client library phải flush buffers và finalize upload asynchronously.

Team ban đầu wrap cleanup trong synchronous `Dispose()`. Khi nhiều jobs kết thúc cùng lúc, worker threads bị block trong flush network I/O và graceful shutdown vượt timeout của container platform.

Chuyển lifecycle sang `await using` giúp cleanup nhường thread trong lúc chờ I/O và shutdown behavior dễ dự đoán hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → application shutdown lâu, nhiều worker threads đứng ở `.Wait()`/`.GetResult()` trong cleanup hoặc uploaded objects đôi lúc thiếu final bytes.

**Evidence** → trace cho thấy synchronous blocking quanh flush/dispose; logs thiếu completion event của remote stream.

**Hypothesis** → asynchronous cleanup đang bị ép thành sync hoặc không được await.

**Diagnosis** → kiểm tra object ownership, call sites có `await using` hay không và disposal path có I/O hay không.

**Fix** → implement/consume `IAsyncDisposable` đúng boundary; không fire-and-forget `DisposeAsync()`.

**Verification** → integration test shutdown giữa load, xác nhận resources được finalize và worker không giữ threads trong blocking waits.

## 7. Common mistakes

- Implement `IAsyncDisposable` cho object chỉ có synchronous cleanup.
- Gọi `DisposeAsync()` nhưng không await.
- Dùng `.AsTask().Wait()` trong shutdown path.
- Dùng request cancellation token để hủy cleanup bắt buộc giữa chừng.
- Không xác định rõ ai sở hữu nested disposable resource.
- Implement cả `Dispose` và `DisposeAsync` nhưng hai path cleanup khác nhau về correctness.

## 8. Alternatives

- `IDisposable`: tốt hơn nếu cleanup hoàn toàn synchronous.
- Explicit `CloseAsync`/`CompleteAsync`: đôi khi hợp lý nếu “complete protocol” khác với disposal semantics.
- Background finalization: chỉ phù hợp khi resource protocol hỗ trợ durable handoff; không nên dùng để che lifecycle không rõ ràng.

## 9. Trade-offs

### Advantages

- Không block thread trong asynchronous cleanup.
- Lifecycle rõ ràng qua `await using`.
- Phù hợp network/remote resource cleanup.

### Costs / Risks

- API và call chain phức tạp hơn synchronous disposal.
- Cleanup failure giờ là asynchronous exception cần xử lý đúng.
- Có thể kéo dài operation completion nếu cleanup thực sự đắt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Dispose` giải phóng resource và `await using` dùng khi cleanup cần asynchronous work.

### Middle

Biết implement/consume `IAsyncDisposable`, tránh fire-and-forget và sync-over-async.

### Senior

Phân biệt business cancellation với mandatory cleanup, hiểu ownership và graceful-shutdown implications.

### Technical Lead / Architect

Quyết định resource lifecycle contract ở component boundaries và tránh để async cleanup lan rộng nơi không có giá trị thực tế.

## 11. Key takeaway

- Chỉ dùng `IAsyncDisposable` khi cleanup thực sự có asynchronous work.
- `await using` giúp cleanup I/O không giữ ThreadPool thread.
- Cancellation của business operation không đồng nghĩa cleanup được phép bỏ dở.

# 2. ASP.NET Core `ProblemDetails`: biến error response thành API contract ổn định thay vì trả exception/string tùy tiện

## 1. What is it?

`ProblemDetails` là chuẩn representation cho HTTP API errors theo RFC 7807/9457-style problem details. Mental model:

```text
exception / validation / domain failure
              |
              v
      error translation boundary
              |
              v
        ProblemDetails
              |
              v
stable HTTP error contract
```

Nó không phải logging format và cũng không phải nơi dump exception stack trace cho client.

## 2. Why does it exist?

Nếu mỗi endpoint trả lỗi khác nhau:

```json
"not found"
```

hoặc:

```json
{ "error": "missing" }
```

hoặc thậm chí raw exception, client phải viết parsing logic rời rạc. Khi backend thay đổi implementation, frontend/integration dễ vỡ dù HTTP status vẫn giống nhau.

Một error contract chuẩn giúp clients xử lý machine-readable errors ổn định và tách internal diagnostics khỏi public API surface.

## 3. How does it work?

ASP.NET Core có `AddProblemDetails()` và exception handling middleware. Flow hợp lý:

```text
request
  |
endpoint/application
  |
known domain exception / validation failure
  |
exception/error mapper
  |
status + type + title + detail + extensions
  |
client
```

`status` thể hiện HTTP semantics. `type` hoặc custom error `code` giúp machine identify category. `detail` nên an toàn để expose.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();

app.UseExceptionHandler();

app.MapGet("/orders/{id:guid}", async (
    Guid id,
    AppDbContext db,
    CancellationToken ct) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    return order is null
        ? Results.Problem(
            statusCode: StatusCodes.Status404NotFound,
            title: "Order not found",
            extensions: new Dictionary<string, object?>
            {
                ["code"] = "order_not_found"
            })
        : Results.Ok(order);
});
```

Một central mapper nên translate known domain/application exceptions sang stable codes. Unknown exceptions nên trả generic `500` và correlation/trace identifier, trong khi chi tiết thật nằm ở server logs/traces.

## 5. Real production scenario

Một mobile client tích hợp order API. Backend từng trả `400` với message tiếng Anh và mobile app kiểm tra substring `"already paid"` để quyết định UI.

Sau khi backend đổi wording, app không nhận diện được lỗi dù behavior business không đổi.

Một stable error code như `order_already_paid` tách machine contract khỏi human-readable message.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend hiển thị generic error hoặc branch sai sau backend release dù status codes không thay đổi.

**Evidence** → clients parse `detail`/message text; cùng failure type có nhiều payload shapes.

**Hypothesis** → error representation chưa được coi là API contract.

**Diagnosis** → inventory status codes, payloads, client parsing logic và exception mapping.

**Fix** → chuẩn hóa ProblemDetails + stable error codes; version/deprecate behavior nếu clients đang phụ thuộc contract cũ.

**Verification** → contract/integration tests assert status + machine-readable error code, không assert toàn bộ message wording.

## 7. Common mistakes

- Trả raw exception message/stack trace cho client.
- Dùng `200 OK` cho business failure rồi nhét `success=false` vào body.
- Dùng một status code `400` cho mọi failure kể cả authentication, authorization, not-found và conflict.
- Để client parse localized human message.
- Log cùng exception ở nhiều layers tạo duplicate noise.
- Dùng ProblemDetails nhưng mỗi endpoint tự đặt schema/extensions khác nhau.

## 8. Alternatives

- Custom error envelope có thể hợp lệ nếu organization đã có contract mạnh và consistent.
- gRPC dùng status/trailers thay vì HTTP ProblemDetails body.
- GraphQL có error model riêng.

Điểm quan trọng không phải tên chuẩn mà là contract nhất quán và semantics rõ ràng.

## 9. Trade-offs

### Advantages

- Error contract thống nhất.
- Dễ document bằng OpenAPI.
- Tách diagnostics nội bộ khỏi client-safe details.

### Costs / Risks

- Cần governance cho error codes.
- Mapping domain failures sang HTTP semantics cần judgment.
- Thay đổi error contract cũng là breaking change nếu client phụ thuộc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP status và error body là hai phần của API response.

### Middle

Biết dùng ProblemDetails, validation errors và exception middleware.

### Senior

Thiết kế stable error taxonomy, không leak internals và phân biệt 400/401/403/404/409/429/5xx đúng semantics.

### Technical Lead / Architect

Chuẩn hóa error contract xuyên services, versioning/deprecation policy và observability correlation giữa client error với server trace.

## 11. Key takeaway

- Error payload là public API contract, không phải chỗ dump exception.
- Stable machine-readable error code quan trọng hơn wording của message.
- Unknown internal failures nên được log/trace đầy đủ nhưng expose tối thiểu cho client.

# 3. EF Core single query vs split query: tránh Cartesian explosion nhưng không đánh đổi consistency một cách vô thức

## 1. What is it?

Khi query một root entity với nhiều collection navigations, EF Core có thể load graph bằng một SQL query lớn hoặc nhiều SQL queries tách biệt.

Mental model:

```text
Single query
Parent JOIN ChildrenA JOIN ChildrenB
        -> repeated parent/child rows

Split query
Query Parents
Query ChildrenA
Query ChildrenB
        -> EF fix-up graph
```

`AsSplitQuery()` không phải performance switch luôn tốt; nó đổi cả round trips lẫn consistency characteristics.

## 2. Why does it exist?

Giả sử một Order có 20 Items và 10 Notes. Join cả hai collections có thể tạo gần 200 result rows cho một Order vì cross product giữa collections.

Nhiều Orders sẽ làm payload phình rất nhanh, tăng database I/O, network transfer và materialization cost.

Split query giảm duplication bằng cách lấy từng collection riêng.

## 3. How does it work?

Single query:

```csharp
var orders = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Notes)
    .ToListAsync(ct);
```

Có thể sinh SQL với joins lớn.

Split query:

```csharp
var orders = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .ToListAsync(ct);
```

EF chạy nhiều statements và correlate rows vào tracked/materialized entities.

Điểm quan trọng: giữa các SQL statements, data có thể thay đổi nếu transaction/isolation không cung cấp snapshot phù hợp.

## 4. Practical implementation

Đừng mặc định `Include` toàn graph. Với read API, projection thường hiệu quả hơn:

```csharp
var result = await db.Orders
    .AsNoTracking()
    .Where(x => x.Id == id)
    .Select(x => new OrderDetailsDto
    {
        Id = x.Id,
        Number = x.Number,
        Items = x.Items
            .Select(i => new OrderItemDto
            {
                ProductId = i.ProductId,
                Quantity = i.Quantity
            })
            .ToList()
    })
    .SingleOrDefaultAsync(ct);
```

Nếu cần multiple collections và single query tạo Cartesian explosion, benchmark `AsSplitQuery()` với production-like cardinality.

## 5. Real production scenario

Một CRM endpoint load Customer cùng Contacts, Orders, Notes và Tags. Dev environment có mỗi collection vài rows nên query chạy nhanh.

Production customers lớn có hàng trăm Orders và Notes. SQL result chứa hàng chục nghìn duplicate combinations cho một customer, p95 tăng mạnh và memory allocation trên API tăng.

Chuyển sang projection hoặc split query giảm payload đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint trả ít entities nhưng SQL rows/network bytes rất lớn.

**Evidence** → generated SQL có nhiều sibling collection joins; execution plan và row count cao bất thường.

**Hypothesis** → Cartesian explosion do eager-loading graph rộng.

**Diagnosis** → inspect generated SQL, actual result-row counts, entity cardinalities và allocation profile.

**Fix** → projection, reduce graph, hoặc `AsSplitQuery()` khi appropriate.

**Verification** → benchmark database duration, transferred rows/bytes, allocations và consistency behavior.

## 7. Common mistakes

- Dùng `Include` như cách mặc định để “lấy đủ dữ liệu”.
- Bật global split query mà không hiểu workload.
- Quên rằng split query tăng database round trips.
- Cho rằng split query luôn thấy một snapshot nhất quán qua mọi statements.
- Load full entities khi API chỉ cần vài columns.
- Fix Cartesian explosion bằng lazy loading rồi tạo N+1.

## 8. Alternatives

- DTO projection: thường tốt nhất cho read-specific API.
- Single query: tốt khi graph nhỏ và round-trip latency quan trọng.
- Explicit loading: hữu ích khi conditional loading thực sự cần thiết.
- Separate read model/CQRS projection: phù hợp khi read shape rất khác domain model.

## 9. Trade-offs

### Advantages

- Split query giảm duplicated result rows khi nhiều collections.
- Projection giảm cả columns lẫn entity-tracking overhead.

### Costs / Risks

- Split query tăng round trips.
- Data có thể thay đổi giữa statements tùy isolation.
- Projection tạo read-model code riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` tạo SQL joins và có cost.

### Middle

Biết inspect generated SQL, dùng projection và `AsSplitQuery()` có chủ đích.

### Senior

Đánh giá cardinality, network payload, consistency và isolation trade-offs.

### Technical Lead / Architect

Quyết định khi entity graph còn phù hợp với read path hay nên tạo read model riêng.

## 11. Key takeaway

- Nhiều sibling collection `Include` có thể tạo Cartesian explosion.
- `AsSplitQuery()` đổi duplication lấy thêm round trips và consistency considerations.
- Read API thường nên bắt đầu từ projection thay vì load cả object graph.

# 4. PostgreSQL keyset pagination: phân trang ổn định ở dataset lớn thay vì trả giá O(n) cho `OFFSET`

## 1. What is it?

Keyset pagination lấy page tiếp theo dựa trên giá trị sort key cuối cùng của page trước, thay vì yêu cầu database bỏ qua N rows.

Mental model:

```text
OFFSET pagination
ORDER BY CreatedAt DESC
OFFSET 100000 LIMIT 50
-> DB phải đi qua rất nhiều rows trước khi trả 50 rows

Keyset pagination
WHERE (CreatedAt, Id) < (@lastCreatedAt, @lastId)
ORDER BY CreatedAt DESC, Id DESC
LIMIT 50
-> bắt đầu từ vị trí index gần cursor
```

## 2. Why does it exist?

`OFFSET` rất tiện cho page nhỏ. Nhưng page số 10,000 nghĩa là database vẫn phải locate/skip một lượng lớn rows trước khi trả page nhỏ tiếp theo.

Ngoài performance, concurrent inserts/deletes còn làm offset-based pages dễ duplicate hoặc skip items giữa hai requests.

## 3. How does it work?

Cần deterministic ordering. Một field như `CreatedAt` thường không unique, nên thêm tie-breaker `Id`.

PostgreSQL hỗ trợ row-value comparison:

```sql
SELECT id, created_at, total
FROM orders
WHERE (created_at, id) < (@last_created_at, @last_id)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Index nên align với ordering/access pattern:

```sql
CREATE INDEX ix_orders_created_id
ON orders (created_at DESC, id DESC);
```

Cursor gửi cho client có thể encode hai values thay vì expose raw implementation details.

## 4. Practical implementation

API request:

```text
GET /orders?limit=50&cursor=eyJjcmVhdGVkQXQiOi...
```

Server decode cursor thành `(CreatedAt, Id)` rồi query:

```csharp
var query = db.Orders
    .AsNoTracking()
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id);

if (cursor is not null)
{
    query = query.Where(x =>
        x.CreatedAt < cursor.CreatedAt ||
        (x.CreatedAt == cursor.CreatedAt && x.Id.CompareTo(cursor.Id) < 0));
}

var page = await query.Take(limit + 1).ToListAsync(ct);
```

Với EF/provider, cần xác nhận generated SQL và index usage.

## 5. Real production scenario

Một audit-log API có 200 triệu rows. UI dùng infinite scroll nhưng backend implement `OFFSET page * size`.

Các page đầu nhanh; sau vài nghìn pages, query latency tăng từ vài chục ms lên vài giây và database I/O tăng mạnh.

Keyset pagination giúp latency gần ổn định vì query tiếp tục từ index position thay vì skip toàn bộ lịch sử trước đó.

## 6. Failure scenario & troubleshooting

**Symptom** → page sâu chậm hơn tuyến tính; users đôi lúc thấy duplicate/missing rows khi dữ liệu được insert đồng thời.

**Evidence** → execution plan cho thấy nhiều rows scanned/discarded do offset; sort key không deterministic.

**Hypothesis** → offset pagination không phù hợp dataset/access pattern.

**Diagnosis** → đo latency theo page depth, inspect plan và index order.

**Fix** → chuyển infinite-scroll/next-page flow sang keyset cursor; thêm stable tie-breaker.

**Verification** → benchmark page đầu và page rất sâu; insert concurrent rows để kiểm tra duplicate/skip semantics.

## 7. Common mistakes

- Dùng chỉ `CreatedAt` làm cursor dù nhiều rows cùng timestamp.
- Encode cursor nhưng vẫn dùng `OFFSET` phía sau.
- Không align index với filter/order.
- Kỳ vọng keyset hỗ trợ nhảy trực tiếp đến page 843 như offset.
- Cho cursor chứa mutable sort field khiến row có thể di chuyển giữa pages.
- Không giới hạn page size.

## 8. Alternatives

- `OFFSET/LIMIT`: đơn giản và phù hợp admin UI nhỏ hoặc page shallow.
- Materialized/search index: phù hợp complex search/sort workloads.
- Snapshot/export job: phù hợp large sequential exports hơn interactive pagination.

## 9. Trade-offs

### Advantages

- Performance ổn định hơn ở deep pagination.
- Ít duplicate/skip hơn dưới concurrent inserts khi ordering đúng.
- Tận dụng ordered index tốt.

### Costs / Risks

- Không nhảy arbitrary page dễ dàng.
- Cursor contract phức tạp hơn page number.
- Sort options động có thể cần index/cursor strategies khác nhau.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `OFFSET` không làm database “teleport” đến row thứ N.

### Middle

Biết tạo deterministic sort và cursor.

### Senior

Đánh giá index shape, mutable keys, concurrent writes và API compatibility.

### Technical Lead / Architect

Chọn pagination contract theo UX và scale thay vì mặc định page-number cho mọi API.

## 11. Key takeaway

- Deep `OFFSET` thường trả giá bằng scan/skip work ngày càng lớn.
- Keyset pagination cần deterministic ordering và index phù hợp.
- Nếu UX chỉ cần “next page”, cursor thường tốt hơn page number ở dataset lớn.

# 5. MongoDB compound indexes: thứ tự field trong index phải đi theo access pattern, không theo thứ tự property trong model

## 1. What is it?

Compound index chứa nhiều fields trong một ordered index structure.

Mental model:

```text
index: { tenantId: 1, status: 1, createdAt: -1 }

ordered first by tenantId
then by status
then by createdAt within those prefixes
```

Index field order quyết định queries nào tận dụng prefix và sort hiệu quả.

## 2. Why does it exist?

Production queries thường filter nhiều dimensions và sort. Separate single-field indexes không phải lúc nào cũng tương đương một compound index phù hợp.

Ví dụ SaaS query gần như luôn scope theo `tenantId`, filter `status`, rồi sort newest first. Index phải phản ánh access pattern đó.

## 3. How does it work?

Query:

```javascript
db.orders.find({
  tenantId: "t1",
  status: "Pending"
}).sort({ createdAt: -1 }).limit(50)
```

Một index hợp lý:

```javascript
db.orders.createIndex({
  tenantId: 1,
  status: 1,
  createdAt: -1
})
```

Equality predicates thường đứng trước sort/range fields. Nhưng không nên biến rule-of-thumb thành luật tuyệt đối; phải inspect workload và `explain()`.

## 4. Practical implementation

Trong MongoDB .NET Driver:

```csharp
var keys = Builders<Order>.IndexKeys
    .Ascending(x => x.TenantId)
    .Ascending(x => x.Status)
    .Descending(x => x.CreatedAt);

await collection.Indexes.CreateOneAsync(
    new CreateIndexModel<Order>(keys),
    cancellationToken: ct);
```

Sau đó kiểm tra execution stats thay vì kết luận từ tên index:

```javascript
db.orders.find({ tenantId: "t1", status: "Pending" })
  .sort({ createdAt: -1 })
  .explain("executionStats")
```

Quan tâm `keysExamined`, `docsExamined`, returned count và sort stage.

## 5. Real production scenario

Một marketplace collection có hàng trăm triệu listings. API query theo region + status rồi sort `publishedAt`.

Team thêm ba single-field indexes vì thấy từng field xuất hiện trong filter. MongoDB vẫn phải scan nhiều candidates và in-memory sort ở một số query shapes.

Một compound index dựa trên actual access pattern giảm scanned keys và loại sort stage tốn kém.

## 6. Failure scenario & troubleshooting

**Symptom** → query có index nhưng vẫn chậm và CPU/storage I/O cao.

**Evidence** → `explain()` cho thấy `keysExamined` lớn hơn nhiều `nReturned`, hoặc có blocking sort.

**Hypothesis** → index tồn tại nhưng field order/selectivity không match query shape.

**Diagnosis** → inspect representative filters, sort, cardinality và index prefixes.

**Fix** → thiết kế compound index cho dominant access pattern; xóa redundant indexes sau khi xác minh usage.

**Verification** → compare execution stats và production query latency trước/sau.

## 7. Common mistakes

- Tạo index cho mọi field độc lập.
- Chọn field order theo model/class property order.
- Chỉ nhìn query có `IXSCAN` rồi kết luận tối ưu.
- Bỏ qua sort requirement.
- Tạo quá nhiều indexes làm write amplification và RAM pressure.
- Không tính multi-tenant prefix vào index strategy.

## 8. Alternatives

- Separate indexes + index intersection có thể phù hợp một số cases nhưng không mặc định thay compound index.
- Denormalized/materialized read collection cho query rất đặc thù.
- Search engine nếu requirement chuyển thành full-text/relevance/search facets phức tạp.

## 9. Trade-offs

### Advantages

- Giảm examined keys/documents cho targeted workloads.
- Có thể đáp ứng filter + sort trực tiếp từ index.

### Costs / Risks

- Mỗi index tăng storage, memory footprint và write cost.
- Index tối ưu query A có thể không giúp query B.
- Schema/access-pattern evolution đòi hỏi index lifecycle management.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index là ordered structure, không chỉ boolean “field này được index”.

### Middle

Biết dùng compound indexes và `explain()`.

### Senior

Đánh giá selectivity, sort, examined/returned ratio và write amplification.

### Technical Lead / Architect

Định nghĩa access patterns trước schema/index strategy và kiểm soát index sprawl ở scale lớn.

## 11. Key takeaway

- Compound-index field order phải phục vụ query shape thực tế.
- `IXSCAN` chưa đủ để chứng minh query hiệu quả; xem `keysExamined`/`docsExamined`.
- Thêm index luôn có write/storage/operational cost.

# 6. CQRS với một database vs separate read/write stores: tách intent trước, tách storage chỉ khi complexity thực sự đòi hỏi

## 1. What is it?

CQRS — Command Query Responsibility Segregation — trước hết là tách operations thay đổi state khỏi operations đọc state.

Mental model cơ bản:

```text
Command -> validate intent -> mutate state
Query   -> read/projection -> return data
```

Điều này không bắt buộc hai databases.

Có ba mức thường bị trộn lẫn:

```text
1. CQRS logic separation, same model/database
2. Separate read/write models, same database
3. Separate read/write stores + synchronization
```

## 2. Why does it exist?

Một model tối ưu cho invariants/write consistency thường không tối ưu cho complex read screens. Nếu ép cùng DTO/entity/service đáp ứng cả hai, code dễ thành CRUD-centric object graph với nhiều condition và accidental coupling.

CQRS cho phép command model tập trung correctness, còn query model tập trung read shape.

## 3. How does it work?

Simple CQRS:

```text
POST /orders
  -> CreateOrderCommandHandler
  -> DbContext

GET /orders/{id}
  -> OrderDetailsQueryHandler
  -> same DbContext/database
  -> projection DTO
```

Advanced CQRS:

```text
write store
   |
Outbox/Event
   |
projector
   v
read store
```

Mức advanced đổi synchronous consistency lấy independent scaling/read optimization và thêm failure/recovery complexity.

## 4. Practical implementation

Không cần framework để làm CQRS:

```csharp
public sealed record CreateOrderCommand(Guid CustomerId);

public sealed class CreateOrderHandler(AppDbContext db)
{
    public async Task<Guid> HandleAsync(
        CreateOrderCommand command,
        CancellationToken ct)
    {
        var order = Order.Create(command.CustomerId);
        db.Orders.Add(order);
        await db.SaveChangesAsync(ct);
        return order.Id;
    }
}
```

Query:

```csharp
public sealed class OrderQueries(AppDbContext db)
{
    public Task<OrderDetailsDto?> GetAsync(Guid id, CancellationToken ct) =>
        db.Orders
          .AsNoTracking()
          .Where(x => x.Id == id)
          .Select(x => new OrderDetailsDto(x.Id, x.Status, x.Total))
          .SingleOrDefaultAsync(ct);
}
```

Đây đã là separation of command/query intent dù cùng database.

## 5. Real production scenario

Một e-commerce admin dashboard có read queries join nhiều reporting dimensions, trong khi checkout write path cần transaction/invariants chặt.

Ban đầu team dùng same SQL database nhưng tách command handlers và query projections. Chỉ khi dashboard traffic/reporting load thực sự cạnh tranh với transactional workload, team mới thêm read replica hoặc separate projection store.

## 6. Failure scenario & troubleshooting

**Symptom** → team giới thiệu message broker, read database và projector ngay từ MVP, rồi mất nhiều thời gian xử lý projection lag, replay và schema evolution.

**Evidence** → actual read scale thấp, same database đáp ứng latency, nhưng architecture đã có nhiều moving parts.

**Hypothesis** → CQRS bị hiểu thành “phải tách database/event-driven”.

**Diagnosis** → tách business need thật: code separation, read performance hay independent scaling?

**Fix** → chọn mức CQRS nhỏ nhất giải quyết constraint; chỉ tách store khi metrics/requirements chứng minh.

**Verification** → architecture review đo complexity giảm/tăng, operational components, latency và consistency expectations.

## 7. Common mistakes

- Đồng nhất CQRS với MediatR.
- Đồng nhất CQRS với Event Sourcing.
- Tạo command/query class cho mọi trivial CRUD mà không tăng clarity.
- Tách read store nhưng không thiết kế replay/rebuild.
- Không thông báo user về eventual consistency sau write.
- Dùng separate stores chỉ vì “microservice architecture nên thế”.

## 8. Alternatives

- Layered CRUD service: đủ tốt cho domain đơn giản.
- Domain service + direct queries: cân bằng khi writes có logic nhưng reads đơn giản.
- Event Sourcing: giải quyết history/state reconstruction problems khác, không phải requirement mặc định của CQRS.

## 9. Trade-offs

### Advantages

- Command và query có thể evolve độc lập hơn.
- Read shape không cần ép theo domain entities.
- Có đường nâng cấp tới independent scaling khi thật sự cần.

### Costs / Risks

- Tăng số types/handlers.
- Separate stores thêm eventual consistency, sync/replay/monitoring burden.
- Overengineering rất dễ xảy ra ở domain CRUD đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu command thay đổi state, query chỉ đọc state.

### Middle

Tách write behavior và read projection mà không cần framework ceremony quá mức.

### Senior

Biết khi nào same-database CQRS đủ và khi nào separate read model đáng giá.

### Technical Lead / Architect

Quyết định mức segregation dựa trên domain complexity, scale và consistency requirement, không dựa trên pattern fashion.

## 11. Key takeaway

- CQRS trước hết là tách intent, không phải tách database.
- Separate read/write stores tạo operational complexity thật và eventual consistency.
- Bắt đầu với mức đơn giản nhất rồi nâng cấp khi constraints chứng minh cần thiết.

# 7. Azure Private Endpoint + Private DNS: private connectivity chỉ đúng khi cả routing lẫn name resolution cùng đúng

## 1. What is it?

Azure Private Endpoint tạo một private IP trong Virtual Network để truy cập một PaaS resource như Storage, SQL hoặc Key Vault qua private network path.

Mental model:

```text
App in VNet
   |
DNS: service.azure... -> private IP
   |
Private Endpoint NIC
   |
Azure PaaS resource
```

Điểm thường bị bỏ sót: network path đúng nhưng DNS resolve public IP thì application vẫn không đi qua private endpoint.

## 2. Why does it exist?

Public endpoint có thể được firewall/identity bảo vệ, nhưng một số organizations cần giảm public exposure và giữ service traffic trong private networking boundary.

Private Endpoint giải quyết connectivity path. Nó không thay thế authentication/authorization.

## 3. How does it work?

Khi private endpoint được tạo, Azure thường kết hợp private DNS zone cho service domain tương ứng.

Ví dụ conceptual flow:

```text
myvault.vault.azure.net
        |
public CNAME/private DNS integration
        |
resolve -> 10.20.1.7
        |
VNet routing
        |
Private Endpoint
```

On-premises hoặc custom DNS environments phải forward/resolve private zones đúng cách. Chỉ tạo endpoint mà không thiết kế DNS là chưa hoàn tất.

## 4. Practical implementation

Một App Service dùng VNet Integration để gọi Key Vault qua private endpoint cần kiểm tra ít nhất:

- outbound path từ App Service vào VNet;
- private endpoint subnet;
- private DNS zone link với VNet;
- name resolution từ workload;
- Key Vault public network access/firewall policy;
- Managed Identity/RBAC.

Debug từ workload environment nên bắt đầu bằng DNS lookup và connection test, không chỉ xem Azure Portal resource tồn tại.

## 5. Real production scenario

Team bật “Disable public access” cho Azure SQL sau khi tạo Private Endpoint. Portal nhìn mọi thứ healthy nhưng application production mất connection.

Nguyên nhân: corporate DNS vẫn resolve SQL hostname về public endpoint. Route private tồn tại nhưng application chưa bao giờ dùng nó.

Sau khi sửa DNS forwarding/private zone linkage, connection hoạt động mà không cần đổi connection string hostname.

## 6. Failure scenario & troubleshooting

**Symptom** → `timeout`, connection refused hoặc firewall error sau khi tắt public access.

**Evidence** → `nslookup`/DNS diagnostic từ workload trả public IP thay vì private IP; hoặc private IP đúng nhưng route/NSG/network path bị chặn.

**Hypothesis** → private DNS hoặc routing chưa đúng.

**Diagnosis** → kiểm tra theo thứ tự: DNS result → route/path → TCP reachability → TLS/hostname → identity/RBAC.

**Fix** → sửa private DNS zone/link/forwarding hoặc networking rule tương ứng.

**Verification** → từ chính workload, hostname resolve private IP và connection thành công khi public access bị disabled.

## 7. Common mistakes

- Nghĩ tạo Private Endpoint là đủ.
- Hard-code private IP thay vì dùng service hostname.
- Quên hybrid/on-prem DNS forwarding.
- Dùng private networking như thay thế cho Managed Identity/RBAC.
- Test từ laptop public rồi kết luận production route đúng.
- Tạo quá nhiều private endpoints/zones mà không có naming/network ownership rõ ràng.

## 8. Alternatives

- Public endpoint + firewall/service restrictions: đơn giản hơn khi threat/compliance model cho phép.
- Service Endpoint: mô hình khác, không cấp private IP cho resource theo cùng cách.
- VNet-injected service/private architecture khác tùy Azure service.

## 9. Trade-offs

### Advantages

- Giảm public network exposure.
- Cho phép private IP-based connectivity và centralized network controls.
- Phù hợp enterprise/hybrid security requirements.

### Costs / Risks

- DNS trở thành critical infrastructure.
- Tăng network topology và troubleshooting complexity.
- Private endpoints/DNS zones có cost và governance burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu private endpoint là private network path tới PaaS service.

### Middle

Biết kiểm tra DNS resolution và connectivity từ workload.

### Senior

Chẩn đoán hybrid DNS, routing, TLS, identity và firewall theo từng layer.

### Technical Lead / Architect

Quyết định service nào thực sự cần private connectivity và chuẩn hóa DNS/network ownership để tránh platform sprawl.

## 11. Key takeaway

- Private Endpoint chỉ hữu ích khi DNS resolve workload tới private IP đúng.
- Networking và identity là hai security layers riêng.
- Debug private connectivity theo thứ tự DNS → route → transport → auth.

# 8. SLI, SLO và burn-rate alerting: cảnh báo theo reliability budget thay vì page đội vận hành vì từng spike nhỏ

## 1. What is it?

SLI là measurement của service behavior; SLO là target; error budget là phần unreliability được phép trong một window.

Ví dụ:

```text
SLI: tỷ lệ requests thành công và < 500 ms
SLO: 99.9% trong 30 ngày
Error budget: 0.1% requests có thể vi phạm
```

Burn rate mô tả tốc độ service đang tiêu error budget so với tốc độ cho phép.

## 2. Why does it exist?

Alert trực tiếp kiểu “error rate > 1% trong 1 phút” dễ page vì transient spike không ảnh hưởng meaningful reliability. Ngược lại, một degradation 0.3% kéo dài nhiều giờ có thể bào mòn SLO nghiêm trọng nhưng không vượt threshold cứng.

SLO-based alerting tập trung vào user-visible reliability và mức độ nhanh service đang phá budget.

## 3. How does it work?

Nếu SLO cho phép 0.1% failures, error rate 1% nghĩa là đang burn budget khoảng 10x tốc độ cho phép.

Một strategy thường dùng multi-window burn-rate:

```text
fast burn:
  high burn rate trong short window
  + xác nhận trong longer window

slow burn:
  lower burn rate
  + tồn tại trong long window
```

Điều này giảm false positives nhưng vẫn bắt incidents nghiêm trọng sớm.

## 4. Practical implementation

Trong OpenTelemetry/Application Insights pipeline, tạo metric từ requests:

```text
good = status < 500 AND duration < 500ms
valid = requests thuộc SLI population
SLI = good / valid
```

Loại health probes/internal endpoints nếu chúng không đại diện user journey.

Alert nên link tới dashboard gồm error rate, latency percentiles, dependency failures, deployment markers và trace samples.

## 5. Real production scenario

Một checkout API có occasional 30-second deployment spike mỗi tuần. Threshold-based alert page on-call mỗi lần dù error budget tháng gần như không ảnh hưởng.

Trong incident khác, 0.4% payment timeout kéo dài 8 giờ lại không trigger threshold 1%, nhưng tiêu phần lớn monthly error budget.

Burn-rate alerts ưu tiên incident thứ hai đúng mức hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → alert fatigue cao hoặc incident user-visible lớn nhưng không page.

**Evidence** → alert thresholds không liên hệ SLO; health/internal traffic làm denominator sai; “success” chỉ dựa status mà bỏ latency.

**Hypothesis** → SLI chưa phản ánh user experience hoặc alert logic không dựa budget consumption.

**Diagnosis** → audit SLI population, good-event definition, time windows và alert history.

**Fix** → định nghĩa SLI theo critical user journey và áp multi-window burn-rate alerts.

**Verification** → replay historical incidents để xem alerts mới có bắt đúng severe/slow-burn cases và giảm noise không.

## 7. Common mistakes

- Chọn SLO 99.999% theo cảm giác mà không xét architecture/cost.
- Dùng infrastructure uptime làm proxy duy nhất cho user reliability.
- Tính tất cả requests kể cả bots/health probes vào SLI.
- Page trên mọi metric spike.
- Tạo SLO nhưng release process không bao giờ dùng error budget để quyết định risk.
- Dùng average latency thay vì threshold success hoặc percentiles phù hợp.

## 8. Alternatives

- Static metric thresholds: vẫn hữu ích cho resource exhaustion hoặc invariant rất cụ thể.
- Anomaly detection: hỗ trợ phát hiện behavior lạ nhưng không thay reliability target.
- Synthetic monitoring: tốt cho critical journeys từ outside-in perspective.

## 9. Trade-offs

### Advantages

- Alerts gắn với user-visible reliability.
- Giảm noise từ short harmless spikes.
- Tạo ngôn ngữ chung giữa reliability và release risk.

### Costs / Risks

- SLI design sai sẽ tạo confidence giả.
- Cần metrics aggregation chất lượng.
- SLO governance có thể biến thành process ceremony nếu không gắn quyết định thật.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SLI là measurement, SLO là target, SLA là external/business commitment khác.

### Middle

Biết instrument good/total events và đọc error-budget consumption.

### Senior

Thiết kế burn-rate alerts, validate denominator và correlate với traces/dependencies.

### Technical Lead / Architect

Chọn SLO phản ánh business-critical journeys và dùng error budget để cân bằng reliability với delivery speed.

## 11. Key takeaway

- Alert tốt nên phản ánh tốc độ mất reliability, không chỉ một metric vượt threshold tức thời.
- SLI phải đo điều user thực sự cảm nhận.
- Error budget chỉ có giá trị khi ảnh hưởng operational/release decisions.

# 9. Playwright flaky tests: làm E2E deterministic bằng control state, selectors và network assumptions

## 1. What is it?

Flaky E2E test là test có thể pass/fail dù application code không thay đổi. Mental model:

```text
test code
 + browser timing
 + network timing
 + async UI state
 + shared test data
 + selector stability
 + environment state
 = observed result
```

E2E test càng phụ thuộc uncontrolled factors, xác suất flake càng cao.

## 2. Why does it exist?

Browser UI là concurrent system: DOM render, API calls, animations, async state updates và background requests xảy ra theo thời gian.

Test kiểu `sleep 2 seconds` giả định timing cố định. Nó có thể pass local nhưng fail CI khi machine/network chậm hơn.

## 3. How does it work?

Playwright có auto-wait cho actionability: element visible, enabled, stable và actionable. Locator-based assertions cũng retry cho tới timeout.

Thay vì:

```ts
await page.waitForTimeout(2000);
expect(await page.textContent('#status')).toBe('Saved');
```

nên:

```ts
await expect(page.getByTestId('status')).toHaveText('Saved');
```

Test nên chờ observable state, không chờ thời gian giả định.

## 4. Practical implementation

Tạo unique test data:

```ts
const email = `e2e-${crypto.randomUUID()}@example.test`;
```

Dùng semantic/stable locator:

```ts
await page.getByRole('button', { name: 'Create account' }).click();
await expect(page.getByRole('heading', { name: 'Welcome' })).toBeVisible();
```

Nếu flow phụ thuộc API response cụ thể:

```ts
const responsePromise = page.waitForResponse(r =>
  r.url().includes('/api/orders') && r.request().method() === 'POST');

await page.getByRole('button', { name: 'Place order' }).click();
const response = await responsePromise;
expect(response.ok()).toBeTruthy();
```

Không cần wait network nếu UI state đã là business signal đủ tốt; tránh over-synchronization.

## 5. Real production scenario

Checkout E2E suite có 8% flake rate. Team rerun failed tests tự động đến khi xanh, khiến CI “pass” nhưng che real regressions.

Điều tra cho thấy tests dùng shared customer/cart data và CSS selectors phụ thuộc DOM layout. Parallel runs ghi đè cart của nhau.

Tách test data per worker + semantic locators giảm flake đáng kể mà không tăng timeout.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng commit, cùng test lúc pass lúc fail; rerun thường xanh.

**Evidence** → trace/video cho thấy wrong shared state, detached element, pending request hoặc timing assumptions.

**Hypothesis** → nondeterministic test/environment dependency, không phải product bug thuần túy.

**Diagnosis** → dùng Playwright trace, screenshots, network logs; chạy test lặp lại/parallel để tái hiện.

**Fix** → isolate data, remove sleeps, dùng locator/assertion auto-wait, control external dependencies khi phù hợp.

**Verification** → chạy hàng chục/hàng trăm iterations và parallel CI; theo dõi flake rate theo test.

## 7. Common mistakes

- Dùng `waitForTimeout` như synchronization mechanism.
- Selector theo `.container > div:nth-child(3)`.
- Shared account/database state giữa parallel tests.
- Retry nhiều lần rồi coi suite khỏe.
- Mock mọi backend call đến mức E2E không còn kiểm tra integration thật.
- Dùng một giant E2E test cover cả hệ thống, khó biết failure boundary.

## 8. Alternatives

- Integration/API tests cho business flows không cần browser.
- Component tests cho UI behavior cô lập.
- Contract tests cho frontend-backend schema/semantics.

E2E nên tập trung critical journeys nơi browser + backend integration thực sự là risk.

## 9. Trade-offs

### Advantages

- Kiểm tra user journey qua nhiều layers.
- Bắt routing/auth/browser integration bugs mà unit test không thấy.

### Costs / Risks

- Chậm và đắt hơn lower-level tests.
- Environment/data dependencies dễ tạo flakiness.
- Failure diagnosis phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu E2E test nên chờ state, không ngủ theo thời gian cố định.

### Middle

Biết selectors ổn định, isolated test data và trace debugging.

### Senior

Phân loại product failure vs test failure, quản lý parallelism/dependencies và giảm flake bằng evidence.

### Technical Lead / Architect

Thiết kế test strategy theo risk: phần nào unit, integration, contract và E2E; đặt flake budget thay vì chấp nhận rerun vô hạn.

## 11. Key takeaway

- Flakiness thường đến từ uncontrolled state/timing, không phải “CI chậm”.
- Chờ observable condition và isolate test data thay vì sleep/retry mù.
- E2E tests nên bảo vệ critical journeys, không thay toàn bộ test pyramid.

# 10. AI Structured Outputs: schema-valid JSON vẫn chưa phải business-valid quyết định

## 1. What is it?

Structured Outputs buộc model response tuân theo một schema đã định, ví dụ object có các fields/types cụ thể.

Mental model:

```text
LLM output
   |
constrained by schema
   |
syntactically/structurally valid object
   |
application validation
   |
business-authorized action
```

Schema correctness không đồng nghĩa factual correctness, authorization correctness hay business-rule correctness.

## 2. Why does it exist?

Parsing natural-language model responses bằng regex/string heuristics rất brittle. Structured output giúp application có deterministic shape để deserialize và tiếp tục workflow.

Nhưng model vẫn probabilistic ở việc chọn values. Vì vậy schema chỉ giải quyết representation boundary, không giải quyết trust boundary.

## 3. How does it work?

Ví dụ model trả:

```json
{
  "customerId": "C123",
  "refundAmount": 500,
  "reason": "duplicate charge"
}
```

Schema có thể bảo đảm `refundAmount` là number và `customerId` là string.

Nó không thể tự bảo đảm:

- customer tồn tại;
- order thuộc customer;
- refundable balance >= 500;
- caller có permission refund;
- transaction chưa được refund trước đó.

Các checks này phải nằm trong deterministic application logic.

## 4. Practical implementation

Model có thể đề xuất intent:

```csharp
public sealed record RefundProposal(
    string OrderId,
    decimal Amount,
    string Reason);
```

Sau deserialize, application validate:

```csharp
var order = await db.Orders
    .SingleOrDefaultAsync(x => x.Id == proposal.OrderId, ct);

if (order is null)
    return Result.Fail("order_not_found");

if (!authorization.CanRefund(user, order))
    return Result.Fail("forbidden");

if (proposal.Amount <= 0 || proposal.Amount > order.RefundableAmount)
    return Result.Fail("invalid_refund_amount");

await paymentGateway.RefundAsync(order.PaymentId, proposal.Amount, ct);
```

Model giúp interpret user intent; application giữ policy và side-effect authority.

## 5. Real production scenario

Support assistant đọc chat và đề xuất refund reason/amount. Model output luôn đúng JSON schema nên team ban đầu cho workflow gọi payment API trực tiếp.

Một prompt injection trong customer message khiến model đề xuất refund lớn hơn order value. Schema vẫn valid hoàn toàn.

Sau redesign, model chỉ tạo proposal; backend re-check ownership, amount, policy và operator authorization trước side effect.

## 6. Failure scenario & troubleshooting

**Symptom** → không có parsing errors nhưng business actions sai hoặc không authorized.

**Evidence** → logs cho thấy model response schema-valid nhưng values vi phạm domain rules.

**Hypothesis** → team đã nhầm structural validation với semantic/security validation.

**Diagnosis** → trace workflow từ model output tới side effect; xác định checks nào đang bị delegate cho model.

**Fix** → đưa authorization, limits, existence checks, idempotency và financial invariants về deterministic code.

**Verification** → adversarial tests với prompt injection, impossible IDs, excessive amounts và repeated tool calls.

## 7. Common mistakes

- Coi schema-valid output là trusted data.
- Cho model quyết định authorization.
- Cho model tự chọn unrestricted tool parameters.
- Không validate IDs/ownership sau model output.
- Retry tool side effects mà không có idempotency.
- Log sensitive prompts/tool arguments không có redaction policy.
- Không có evaluation set cho failure/adversarial scenarios.

## 8. Alternatives

- Deterministic form/workflow: tốt hơn nếu intent đã cấu trúc và không cần language understanding.
- Tool Calling: cung cấp action interface rõ hơn, nhưng vẫn cần server-side validation/authorization.
- Human approval: hợp lý cho high-impact/irreversible actions.

## 9. Trade-offs

### Advantages

- Giảm brittle parsing.
- Hợp nhất tốt với typed application code.
- Dễ validate và test contract hơn free-form text.

### Costs / Risks

- Có thể tạo false sense of safety.
- Model values vẫn có thể hallucinate hoặc bị prompt injection ảnh hưởng.
- Schema phức tạp quá mức làm model/workflow khó evolve.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Structured Outputs đảm bảo shape chứ không đảm bảo truth.

### Middle

Biết deserialize, validate và reject invalid domain values.

### Senior

Thiết kế trust boundary, tool authorization, idempotency và adversarial evaluations.

### Technical Lead / Architect

Quyết định phần nào giao cho probabilistic reasoning và phần nào bắt buộc deterministic, audit-able, policy-enforced code.

## 11. Key takeaway

- Structured Outputs giải quyết format, không giải quyết trust.
- Authorization, financial invariants và side-effect safety phải nằm trong deterministic application logic.
- Model nên đề xuất intent; backend phải kiểm chứng trước khi hành động.
