# 1. .NET Large Object Heap: allocation lớn, GC pressure và object pooling có điều kiện

## 1. What is it?

Mental model: CLR quản lý object lớn khác object nhỏ vì việc copy/compact chúng đắt. Các allocation lớn được đưa vào Large Object Heap (LOH). Vấn đề thực tế không phải “LOH xấu”, mà là tốc độ allocation, lifetime và fragmentation của các buffer lớn.

## 2. Why does it exist?

Generational GC tối ưu cho giả định phần lớn object nhỏ chết nhanh. Copy một buffer hàng MB mỗi lần collection lại rất tốn CPU và memory bandwidth, nên runtime cần chiến lược khác cho large objects.

## 3. How does it work?

Object lớn đi vào LOH; LOH được thu gom cùng full collections và thường ít compact hơn small-object generations. Nếu application liên tục tạo byte arrays lớn, allocation rate có thể kéo theo Gen 2/full GC và tăng pause time.

## 4. Practical implementation

Đừng pool trước khi đo. Với transient buffers có kích thước phù hợp, `ArrayPool<byte>` có thể giảm allocation:

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(128 * 1024);
try
{
    await stream.ReadExactlyAsync(buffer.AsMemory(0, 128 * 1024), ct);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}
```

Không giữ rented buffer sau khi return và không giả định kích thước array trả về bằng chính xác kích thước yêu cầu.

## 5. Real production scenario

API import file đọc mỗi chunk bằng `new byte[4_000_000]`. Khi nhiều uploads chạy song song, memory allocation tăng mạnh và full GC xuất hiện. Chuyển sang streaming với bounded buffers giảm peak memory đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 tăng theo chu kỳ, memory saw-tooth lớn. **Evidence** → allocation profile có large arrays; Gen 2/LOH collections tăng. **Hypothesis** → large transient allocations. **Diagnosis** → `dotnet-counters`, GC events và allocation profiler. **Fix** → streaming, giảm buffer size hoặc pooling có giới hạn. **Verification** → load test cùng file size/concurrency và so GC pause/allocation rate.

## 7. Common mistakes

Pool mọi object; giữ pooled buffer quá lâu; quên return khi exception; cache byte arrays lớn vô hạn; chỉ nhìn managed heap size mà không nhìn allocation rate.

## 8. Alternatives

Streaming trực tiếp thường đơn giản hơn pooling. `MemoryPool<T>` hữu ích khi ownership/lifetime cần rõ hơn. Với workload nhỏ, allocation bình thường có thể là lựa chọn tốt nhất.

## 9. Trade-offs

### Advantages
Giảm allocation và GC pressure ở measured hot paths.

### Costs / Risks
Pooling thêm ownership complexity, giữ memory resident và có nguy cơ data leakage nếu tái sử dụng buffer sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

### Middle
Biết stream dữ liệu và dùng pool đúng lifetime.

### Senior

### Technical Lead / Architect
Quyết định memory budget/concurrency limit cho file, serialization và batch workloads thay vì tối ưu từng allocation rời rạc.

## 11. Key takeaway

- LOH là runtime mechanism, không phải bug.
- Đo allocation rate và GC pauses trước khi pool.
- Streaming/bounded memory thường quan trọng hơn micro-optimization.

# 2. ASP.NET Core API backward compatibility: versioning không cứu được contract thay đổi tùy tiện

## 1. What is it?

Backward compatibility nghĩa là client đang hoạt động với contract cũ tiếp tục hoạt động sau khi server được deploy. API versioning chỉ là một công cụ quản lý nhiều contracts; nó không tự tạo compatibility.

## 2. Why does it exist?

Client và server hiếm khi deploy atomically. Mobile apps, partners hoặc frontend cached có thể chạy phiên bản cũ hàng tuần. Một field rename đơn giản có thể trở thành production outage phía client.

## 3. How does it work?

Contract gồm nhiều thứ hơn URL: method, status code, JSON shape, nullability, enum values, pagination semantics và error contract. Compatible evolution thường ưu tiên additive changes và tolerant readers.

## 4. Practical implementation

Thay vì đổi:

```json
{"name":"Ha"}
```

thành:

```json
{"displayName":"Ha"}
```

ngay lập tức, có thể giữ `name`, thêm `displayName`, migrate consumers rồi deprecate theo policy. OpenAPI diff trong CI giúp phát hiện breaking changes trước deploy.

## 5. Real production scenario

Backend đổi enum `Pending` thành `AwaitingApproval`. Một partner deserialize bằng strict enum và fail toàn bộ response. HTTP vẫn 200 nhưng integration bị gãy.

## 6. Failure scenario & troubleshooting

**Symptom** → error tăng chỉ ở một nhóm clients sau release. **Evidence** → client version correlation và schema diff. **Hypothesis** → breaking contract. **Diagnosis** → replay payload cũ/mới. **Fix** → restore compatible representation hoặc route version cũ. **Verification** → consumer contract tests cho supported versions.

## 7. Common mistakes

Version mọi endpoint ngay từ đầu; nghĩ optional field luôn vô hại; thay status codes/error shape không báo; xóa field vì “frontend hiện không dùng”; version URL nhưng dùng chung DTO rồi thay DTO toàn cục.

## 8. Alternatives

Additive evolution không cần version mới cho nhiều thay đổi. Version mới phù hợp khi semantics thực sự không thể tương thích. GraphQL cũng có deprecation nhưng vẫn cần schema discipline.

## 9. Trade-offs

### Advantages
Giảm coordinated deployment và integration outages.

### Costs / Risks
Nhiều versions tăng test/support burden; compatibility kéo dài có thể giữ technical debt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu JSON/status code là public contract.

### Middle
Thiết kế additive changes và integration tests.

### Senior
Đánh giá semantic breaking changes, rollout/deprecation và telemetry theo client version.

### Technical Lead / Architect
Đặt compatibility window, ownership và retirement policy thay vì để versions sống vô hạn.

## 11. Key takeaway

- Compatibility là deployment property, không chỉ routing feature.
- Additive evolution thường rẻ hơn tạo version mới.
- Contract cần được test như code.

# 3. SQL keyset pagination: ổn định hơn OFFSET khi dữ liệu lớn và liên tục thay đổi

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên giá trị sort key cuối cùng của trang trước, thay vì yêu cầu database bỏ qua N rows bằng `OFFSET`.

## 2. Why does it exist?

`OFFSET 500000` vẫn buộc engine tìm/đi qua lượng rows lớn trước khi trả vài chục rows. Đồng thời inserts/deletes giữa hai requests có thể làm user thấy duplicate hoặc missing items.

## 3. How does it work?

Với ordering `(CreatedAt DESC, Id DESC)`, cursor chứa cặp giá trị cuối:

```sql
WHERE CreatedAt < @lastCreatedAt
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC
FETCH FIRST 50 ROWS ONLY;
```

Composite index phải phù hợp access pattern.

## 4. Practical implementation

Cursor nên encode opaque values thay vì expose offset. Sort cần deterministic tie-breaker như unique `Id`.

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON Orders (CreatedAt DESC, Id DESC);
```

Đọc execution plan để xác nhận seek/range access và số rows đọc.

## 5. Real production scenario

Order history có hàng chục triệu rows. Page 1 nhanh nhưng page 10.000 với OFFSET chậm nhiều giây. Keyset giữ latency gần ổn định theo depth.

## 6. Failure scenario & troubleshooting

**Symptom** → records lặp/mất giữa pages. **Evidence** → ordering chỉ theo non-unique `CreatedAt`. **Hypothesis** → cursor không xác định total order. **Diagnosis** → kiểm tra duplicate sort values. **Fix** → thêm unique tie-breaker. **Verification** → concurrent insert test trong khi paginate.

## 7. Common mistakes

Cursor chỉ chứa một non-unique field; cho phép arbitrary sort nhưng không có indexes; encode cursor nhưng không validate; vẫn chạy `COUNT(*)` đắt cho mọi page.

## 8. Alternatives

OFFSET phù hợp cho datasets nhỏ hoặc UI cần jump-to-page. Snapshot/materialized result phù hợp export/reporting cần view ổn định.

## 9. Trade-offs

### Advantages
Latency ổn định hơn, ít duplicate/missing hơn dưới mutation.

### Costs / Risks
Không thuận tiện jump tới page N; cursor logic/index design phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu pagination vẫn là database query problem.

### Middle
Implement cursor với deterministic order.

### Senior
Reason từ execution plan, indexes và concurrent mutations.

### Technical Lead / Architect
Chọn pagination contract theo UX, scale và consistency requirement.

## 11. Key takeaway

- Deep OFFSET có cost tăng theo vị trí.
- Keyset cần total ordering ổn định.
- API cursor và database index phải được thiết kế cùng nhau.

# 4. Elasticsearch aliases: zero-downtime reindex và rollback search schema

## 1. What is it?

Alias là logical name trỏ tới một hoặc nhiều Elasticsearch indices. Application query alias thay vì physical index name, cho phép đổi index implementation mà không đổi client contract.

## 2. Why does it exist?

Mapping/analyzer changes thường cần reindex toàn bộ data. Nếu application trỏ trực tiếp `products-v17`, rollout schema mới sẽ coupling deployment với physical index lifecycle.

## 3. How does it work?

```text
products-search -> products-v17
reindex -> products-v18
validate v18
atomic alias switch
products-search -> products-v18
```

Alias switch giúp cutover nhanh; source-of-truth synchronization vẫn phải xử lý changes phát sinh trong quá trình reindex.

## 4. Practical implementation

Tạo index mới, bulk backfill, replay/catch up changes, validate document counts/search behavior rồi dùng aliases API để remove old/add new trong một operation.

## 5. Real production scenario

Search team đổi analyzer để autocomplete tốt hơn. `products-v18` được build song song; shadow queries so kết quả; alias đổi sau validation mà web application không redeploy.

## 6. Failure scenario & troubleshooting

**Symptom** → sau switch, sản phẩm mới vài phút gần đây biến mất. **Evidence** → backfill snapshot hoàn thành nhưng delta events chưa replay đủ. **Hypothesis** → synchronization gap. **Diagnosis** → compare primary DB change sequence với indexed checkpoint. **Fix** → catch-up protocol/checkpoint trước cutover. **Verification** → reconcile IDs/version watermark.

## 7. Common mistakes

Reindex rồi switch mà không xử lý concurrent writes; xóa old index ngay; không version index names; coi document count bằng nhau là đủ validation.

## 8. Alternatives

In-place mapping additions phù hợp compatible changes. Database full-text search có thể đủ cho workload đơn giản và giảm operational components.

## 9. Trade-offs

### Advantages
Deployment độc lập hơn, rollback nhanh, schema evolution an toàn hơn.

### Costs / Risks
Cần temporary duplicate storage, synchronization logic và validation tooling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu alias tách logical endpoint khỏi physical index.

### Middle
Thực hiện create/reindex/switch.

### Senior
Thiết kế delta synchronization, validation và rollback.

### Technical Lead / Architect
Quyết định search index lifecycle và ownership; đảm bảo Elasticsearch không biến thành transactional source of truth.

## 11. Key takeaway

- Alias giải deployment indirection, không giải data synchronization.
- Reindex cần backfill + catch-up + validation.
- Giữ rollback window thay vì xóa old index ngay.

# 5. Modular Monolith: boundary theo business capability thay vì layer dùng chung toàn hệ thống

## 1. What is it?

Modular Monolith là một deployable application nhưng code/data ownership được chia thành modules có boundary rõ theo business capability. Nó không phải “monolith với nhiều folders”.

## 2. Why does it exist?

Layered monolith lớn dễ trở thành graph phụ thuộc nơi mọi feature truy cập mọi repository/table. Microservices tạo network/operations complexity. Modular Monolith tìm cách giữ deployment đơn giản nhưng tăng change isolation.

## 3. How does it work?

```text
Host
 ├─ Orders Module
 ├─ Catalog Module
 └─ Billing Module

Orders -> published Billing contract
Orders -X-> Billing internal DbContext/entities
```

Boundary nằm ở dependency, ownership và contract; không chỉ project names.

## 4. Practical implementation

Mỗi module có application/domain/infrastructure nội bộ khi complexity cần, expose một nhỏ public API. Architecture tests có thể cấm references vào internal namespaces/modules.

## 5. Real production scenario

E-commerce team cần thay pricing rules. Nếu Catalog, Checkout và CMS cùng dùng `ProductRepository`, thay đổi lan rộng. Tách Pricing capability với explicit contract giúp isolate change dù vẫn deploy cùng process.

## 6. Failure scenario & troubleshooting

**Symptom** → modules tồn tại trên diagram nhưng một feature sửa 6 modules/tables trực tiếp. **Evidence** → cross-module entity references và shared database access. **Hypothesis** → boundary chỉ mang tính folder. **Diagnosis** → dependency graph/change history. **Fix** → define ownership/contracts và remove shared internals. **Verification** → architecture tests + review cross-module changes.

## 7. Common mistakes

Shared `Common` project chứa domain logic; module nào cũng query tables của module khác; event bus nội bộ cho mọi method call; ép DDD layers vào module rất đơn giản.

## 8. Alternatives

Simple layered monolith tốt hơn cho hệ thống nhỏ. Microservices hợp lý khi independent deployment/scaling/ownership thực sự cần.

## 9. Trade-offs

### Advantages
Operational simplicity của monolith với boundary tốt hơn.

### Costs / Risks
Boundary discipline phải được enforce; database vẫn có thể trở thành coupling point.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu module đại diện capability, không phải technical layer.

### Middle
Tuân thủ public contracts và ownership.

### Senior
Phát hiện coupling qua code, schema và transactions.

### Technical Lead / Architect
Quyết định module boundaries, transaction boundaries và liệu module nào thật sự cần tách thành service sau này.

## 11. Key takeaway

- Một process không đồng nghĩa một boundary.
- Module tốt cô lập thay đổi và ownership.
- Đừng trả distributed-systems tax khi chưa cần independent services.

# 6. Azure Managed Identity + Key Vault: bỏ application secrets khỏi deployment pipeline

## 1. What is it?

Managed Identity cung cấp identity cho Azure workload; Key Vault lưu secrets/keys/certificates. Application dùng identity để xin token và truy cập vault thay vì giữ client secret trong config.

## 2. Why does it exist?

Secrets trong environment variables/pipeline variables vẫn phải được tạo, phân phối và rotate. Managed Identity loại bỏ credential bootstrap cho Azure-hosted workload.

## 3. How does it work?

```text
App Service/Function
   -> Managed Identity token
   -> Microsoft Entra ID
   -> Key Vault authorization
   -> secret/key operation
```

Identity và authorization là hai bước: có identity không có nghĩa tự động có quyền vault.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(vaultUrl),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("PartnerApiKey", cancellationToken: ct);
```

Production dùng Managed Identity; local development có thể dùng developer credential chain phù hợp.

## 5. Real production scenario

App Service cần third-party API key. Pipeline không còn inject secret value; app identity chỉ có quyền đọc đúng vault/secrets cần thiết.

## 6. Failure scenario & troubleshooting

**Symptom** → local chạy nhưng production 403 từ Key Vault. **Evidence** → authentication thành công nhưng authorization denied. **Hypothesis** → RBAC/access policy thiếu hoặc wrong identity. **Diagnosis** → kiểm tra principal ID, role assignment, vault networking. **Fix** → least-privilege role/network path. **Verification** → app đọc được secret nhưng operation ngoài quyền vẫn fail.

## 7. Common mistakes

Gán quyền rộng cho subscription; cache secret vô hạn rồi quên rotation; log secret value; nhầm network 403/timeout với identity; dùng client secret để truy cập Key Vault rồi coi như đã “bỏ secrets”.

## 8. Alternatives

Workload identity phù hợp Kubernetes/AKS scenarios. Config không nhạy cảm nên ở configuration service/settings, không cần Key Vault.

## 9. Trade-offs

### Advantages
Giảm secret distribution, hỗ trợ rotation và least privilege.

### Costs / Risks
Thêm dependency vào identity/vault/network; startup strategy và caching cần thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt identity, secret và authorization.

### Middle
Cấu hình Managed Identity/Key Vault và local credential flow.

### Senior
Troubleshoot RBAC/network/rotation và degraded startup.

### Technical Lead / Architect
Thiết kế secret ownership, blast radius và platform-wide identity policy.

## 11. Key takeaway

- Managed Identity loại bỏ credential bootstrap cho Azure workload.
- Key Vault không thay thế authorization design.
- Secret rotation phải được tính vào runtime behavior.

# 7. BackgroundService graceful shutdown: CancellationToken, in-flight work và delivery semantics

## 1. What is it?

Graceful shutdown cho background worker cơ hội ngừng nhận work mới, hoàn tất hoặc safely abandon in-flight work và giải phóng resources trước khi process kết thúc.

## 2. Why does it exist?

Containers, App Service và deployments đều có thể terminate instance. Nếu worker coi shutdown là trường hợp hiếm, message có thể bị mất hoặc side effect dở dang.

## 3. How does it work?

`BackgroundService.ExecuteAsync` nhận stopping token. Khi host shutdown, token được cancel; worker phải propagate token và tuân theo broker/database semantics.

## 4. Practical implementation

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        var message = await _queue.ReceiveAsync(stoppingToken);
        await ProcessAsync(message, stoppingToken);
        await _queue.CompleteAsync(message, stoppingToken);
    }
}
```

Nếu broker dùng lock/visibility timeout, completion chỉ nên xảy ra sau khi business effect thành công.

## 5. Real production scenario

Worker xử lý invoice 40 giây; rolling deployment bắt đầu. Instance ngừng nhận message mới, cố hoàn tất invoice trong shutdown budget. Nếu không kịp, message lock hết hạn và instance khác xử lý lại—do đó handler phải idempotent.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate processing tăng đúng lúc deployments. **Evidence** → shutdown logs trùng message redelivery. **Hypothesis** → in-flight message không hoàn tất trước termination. **Diagnosis** → compare processing duration, host shutdown timeout và broker lock. **Fix** → idempotency, bounded work duration, lock renewal hoặc shutdown budget phù hợp. **Verification** → terminate worker giữa processing.

## 7. Common mistakes

Ignore stopping token; dequeue hàng trăm messages trước; complete message trước business commit; infinite retry trong shutdown; giả định graceful shutdown luôn được cấp đủ thời gian.

## 8. Alternatives

Azure Functions/managed consumers giảm lifecycle code nhưng vẫn có retry/idempotency semantics. Durable workflow engine phù hợp long-running stateful processes.

## 9. Trade-offs

### Advantages
Deployments ít disruptive và state transitions rõ hơn.

### Costs / Risks
Shutdown không thể bảo đảm trước crash/kill; correctness vẫn cần replay-safe processing.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Propagate `CancellationToken`.

### Middle
Thiết kế receive/process/complete đúng thứ tự.

### Senior
Reason về lock duration, redelivery và idempotency khi termination.

### Technical Lead / Architect
Chọn execution platform và delivery semantics theo workload duration/reliability.

## 11. Key takeaway

- Cancellation là cooperative protocol.
- Graceful shutdown không thay idempotency.
- Test termination giữa side effects, không chỉ happy path.

# 8. Akamai/CDN Cache-Control: browser cache, shared cache và stale response là ba bài toán khác nhau

## 1. What is it?

`Cache-Control` mô tả caching semantics cho user agents và shared caches như CDN. Mental model: response có thể tồn tại ở nhiều cache layers với ownership và freshness khác nhau.

## 2. Why does it exist?

Nếu mọi request về origin, latency và origin load tăng. Nhưng cache sai dynamic/private content có thể trả stale hoặc thậm chí dữ liệu của user khác.

## 3. How does it work?

```text
Browser -> Akamai edge -> reverse proxy -> application -> database
```

`max-age` thường điều khiển freshness ở browser/shared cache; `s-maxage` có thể đặt freshness riêng cho shared cache. `private` ngăn shared caching; `no-store` yêu cầu không lưu response.

## 4. Practical implementation

Static versioned asset:

```http
Cache-Control: public, max-age=31536000, immutable
```

Personalized account response thường không nên shared-cache. Với HTML/content, TTL và purge strategy phải đi cùng nhau.

## 5. Real production scenario

CMS publish campaign lúc 10:00 nhưng edge TTL 30 phút. Origin đã có content mới, một số regions vẫn trả bản cũ. Đây là cache invalidation/TTL behavior, không phải database replication issue.

## 6. Failure scenario & troubleshooting

**Symptom** → chỉ một số users thấy nội dung cũ. **Evidence** → response headers/edge cache status cho thấy HIT với object cũ. **Hypothesis** → stale edge object hoặc cache key thiếu dimension. **Diagnosis** → compare browser/edge/origin response và cache key. **Fix** → purge/version key/header policy. **Verification** → kiểm tra nhiều POPs và cold/warm requests.

## 7. Common mistakes

Dùng `no-cache` như đồng nghĩa `no-store`; cache personalized HTML; purge path nhưng quên query variants; TTL dài cho unversioned assets; debug origin mà không inspect CDN headers.

## 8. Alternatives

Browser-only caching đơn giản hơn nếu CDN không cần cache dynamic content. Versioned URLs giảm phụ thuộc purge cho static assets.

## 9. Trade-offs

### Advantages
Giảm latency, bandwidth và origin load.

### Costs / Risks
Freshness, invalidation, cache-key complexity và security risk nếu private data bị shared-cache.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

### Middle

### Senior

## 11. Key takeaway

- Debug theo từng layer: browser → edge → origin.

# 9. OAuth 2.0 Authorization Code + PKCE: bảo vệ authorization code trong public clients

## 1. What is it?

PKCE bổ sung proof vào Authorization Code flow. Client tạo random `code_verifier`, gửi derived `code_challenge` khi bắt đầu authorization và phải trình verifier khi đổi code lấy tokens.

## 2. Why does it exist?

Public clients như SPA/native app không thể giữ client secret đáng tin cậy. Nếu attacker chặn authorization code, PKCE khiến code đó không đủ để đổi token nếu attacker không có verifier.

## 3. How does it work?

```text
Client creates verifier
 -> challenge = transform(verifier)
 -> authorize request includes challenge
Authorization Server returns code
 -> token request includes code + verifier
Server verifies verifier matches original challenge
```

PKCE không thay redirect URI validation, state/nonce hay token validation.

## 4. Practical implementation

Với ASP.NET Core/OIDC libraries, ưu tiên protocol implementation chuẩn thay vì tự viết crypto/redirect flow. Kiểm tra provider/client configuration yêu cầu Authorization Code + PKCE và tránh implicit flow cho modern applications.

## 5. Real production scenario

Desktop app mở system browser để login. Custom URI scheme nhận authorization code. Một malicious app cố intercept redirect nhưng không có verifier của legitimate client nên token exchange thất bại.

## 6. Failure scenario & troubleshooting

**Symptom** → token endpoint trả `invalid_grant`. **Evidence** → authorize request có challenge nhưng token request dùng verifier khác/mất state. **Hypothesis** → verifier lifecycle sai. **Diagnosis** → trace protocol metadata không log secrets/tokens. **Fix** → lưu verifier đúng transaction/session. **Verification** → successful flow và deliberate wrong-verifier test.

## 7. Common mistakes

Coi PKCE là authentication của user; hard-code client secret trong SPA; bỏ `state`; validate JWT chỉ bằng decode; log authorization code/verifier/token; tự implement protocol khi library đã hỗ trợ.

## 8. Alternatives

Confidential server-side web app có thể dùng client authentication cùng Authorization Code; PKCE vẫn thường được khuyến nghị. BFF pattern giữ tokens khỏi browser JavaScript khi threat model yêu cầu.

## 9. Trade-offs

### Advantages
Giảm rủi ro authorization-code interception mà không cần public client secret.

### Costs / Risks
Thêm protocol state; không bảo vệ khỏi XSS/token theft sau khi token đã vào compromised client.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt authorization code và access token.

### Middle
Cấu hình OIDC/OAuth library đúng flow.

### Senior
Threat-model redirect, token storage, nonce/state và validation.

### Technical Lead / Architect
Chọn SPA direct OAuth, BFF hay server-side flow dựa trên threat model và operational complexity.

## 11. Key takeaway

- Public client secret không phải secret.
- PKCE binds code exchange vào client đã bắt đầu flow.
- PKCE chỉ là một lớp trong toàn bộ OAuth/OIDC security design.

# 10. Contract testing: bảo vệ service boundary mà không biến toàn bộ integration thành E2E

## 1. What is it?

Contract testing xác minh producer và consumer đồng ý về interface: request/response schema, status, events hoặc message shape. Nó nằm giữa isolated unit tests và full E2E.

## 2. Why does it exist?

Hai services có thể pass unit tests riêng nhưng integration fail vì field, enum hoặc endpoint semantics thay đổi. E2E phát hiện được nhưng thường chậm, fragile và khó bao phủ mọi consumer expectation.

## 3. How does it work?

Consumer expectation được biểu diễn thành contract; producer CI xác minh implementation vẫn đáp ứng contract trước release.

```text
Consumer expectation -> contract artifact -> Producer verification
```

Contract không nên encode implementation details không thuộc public boundary.

## 4. Practical implementation

Ví dụ consumer cần:

```json
{
  "id": "123",
  "status": "Approved"
}
```

Producer verification seed deterministic state rồi gọi real HTTP endpoint và xác minh response semantics. Database có thể là test infrastructure thật thay vì mock controller internals.

## 5. Real production scenario

Payroll service consume Employee API. Employee team muốn đổi nullable field thành required semantics. Contract verification fail trong PR trước khi breaking change tới shared environment.

## 6. Failure scenario & troubleshooting

**Symptom** → hàng trăm contract tests khó maintain và mọi internal refactor đều fail. **Evidence** → contracts assert headers/order/fields consumer không dùng. **Hypothesis** → over-specified contracts. **Diagnosis** → map assertions về actual consumer dependency. **Fix** → giữ contract ở observable boundary và meaningful semantics. **Verification** → internal refactor không phá tests nhưng real breaking change vẫn fail.

## 7. Common mistakes

Contract test thay mọi integration test; mock producer thay vì verify real endpoint; không version contract artifacts; consumers không publish actual expectations; assert toàn response snapshot vô điều kiện.

## 8. Alternatives

OpenAPI schema validation tốt cho provider-driven contracts. Integration tests tốt cho component + real infrastructure. E2E vẫn cần cho vài cross-system critical journeys.

## 9. Trade-offs

### Advantages
Feedback sớm, xác định consumer impact rõ và ít environment coupling hơn E2E.

### Costs / Risks
Contract infrastructure/governance; consumer contracts quá chi tiết tạo coupling mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu service boundary là testable contract.

### Middle
Viết producer/consumer verification cho meaningful fields.

### Senior
Phân biệt schema compatibility với semantic compatibility và tránh brittle contracts.

### Technical Lead / Architect
Thiết kế test portfolio và ownership để contract tests bổ sung, không thay thế, integration/E2E tests.

## 11. Key takeaway

- Contract tests bắt breaking boundary changes sớm.
- Chỉ assert những gì consumer thực sự phụ thuộc.
- Unit + integration + contract + E2E bảo vệ các loại risk khác nhau.
