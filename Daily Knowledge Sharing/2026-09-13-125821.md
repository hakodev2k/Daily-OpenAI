# 1. .NET Dependency Injection lifetimes và captive dependency: `Singleton`, `Scoped`, `Transient` không chỉ là syntax registration

## 1. What is it?

Dependency Injection lifetime mô tả **một instance được tạo khi nào và được chia sẻ trong phạm vi nào**.

Mental model:

```text
Singleton -> một instance cho application lifetime
Scoped    -> một instance cho một scope, thường là một HTTP request
Transient -> tạo instance mới mỗi lần resolve
```

Điểm quan trọng không nằm ở ba method `AddSingleton`, `AddScoped`, `AddTransient`, mà ở dependency graph hình thành từ chúng.

Một **captive dependency** xảy ra khi object sống lâu giữ reference tới object lẽ ra phải sống ngắn hơn, ví dụ Singleton giữ Scoped service.

## 2. Why does it exist?

Object có state, resource và lifecycle khác nhau.

`DbContext` nên gắn với business/request unit-of-work, trong khi stateless formatter có thể sống lâu hơn. Nếu mọi dependency đều Singleton, state dễ bị share sai. Nếu mọi thứ đều Transient, application có thể tạo quá nhiều objects/resources và việc quản lý disposal trở nên khó đoán.

Lifetime giúp DI container quản lý ownership và disposal đúng boundary.

## 3. How does it work?

ASP.NET Core thường tạo một service scope cho mỗi request:

```text
Root container
   |
   +-- Singleton A
   |
   +-- Request scope #1
   |      +-- Scoped DbContext #1
   |
   +-- Request scope #2
          +-- Scoped DbContext #2
```

Nếu `SingletonReportService` inject trực tiếp `AppDbContext`, context bị capture bởi root lifetime. Đây vừa là correctness bug vừa có thể gây concurrent access vào `DbContext`, vốn không thread-safe.

## 4. Practical implementation

Sai:

```csharp
builder.Services.AddSingleton<ReportScheduler>();
builder.Services.AddScoped<AppDbContext>();

public sealed class ReportScheduler(AppDbContext db)
{
    public Task RunAsync(CancellationToken ct)
        => db.Reports.CountAsync(ct);
}
```

Đúng hơn với background singleton:

```csharp
public sealed class ReportScheduler(IServiceScopeFactory scopeFactory)
{
    public async Task RunAsync(CancellationToken ct)
    {
        await using var scope = scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        var count = await db.Reports.CountAsync(ct);
    }
}
```

Scope được tạo đúng lúc work bắt đầu và dispose sau khi work kết thúc.

## 5. Real production scenario

Một `BackgroundService` chạy mỗi phút và sử dụng một scoped repository bị capture lúc application startup. Sau vài giờ, ChangeTracker giữ ngày càng nhiều entities, memory tăng và job đôi lúc ném concurrency exception vì nhiều execution chạm cùng context.

Root cause không phải EF Core “memory leak”, mà là lifetime mismatch.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng, `DbContext` concurrency exception, state cũ xuất hiện giữa requests.

**Evidence** → dependency graph có Singleton → Scoped; object dispose muộn bất thường; same instance IDs xuất hiện qua nhiều requests.

**Hypothesis** → captive dependency hoặc scope bị giữ quá lâu.

**Diagnosis** → bật scope validation ở Development, log instance identity khi cần, inspect constructor graph.

**Fix** → đổi lifetime, tách stateless service khỏi stateful dependency, hoặc tạo explicit scope tại execution boundary.

**Verification** → mỗi request/job nhận đúng scoped instance và disposal xảy ra sau scope.

## 7. Common mistakes

- Chọn Singleton chỉ vì “nhanh hơn”.
- Inject Scoped service vào Singleton.
- Service giữ mutable request state trong field.
- Dùng Service Locator khắp code để né lifetime design.
- Tạo scope rồi giữ service sau khi scope đã dispose.
- Quên rằng `HttpClient` lifecycle được quản lý khác khi dùng `IHttpClientFactory`.

## 8. Alternatives

- Constructor injection với lifetime đúng: default tốt nhất.
- Factory abstraction: hữu ích khi object cần tạo theo runtime input.
- Explicit scope: phù hợp background/scheduled processing.
- Manual new: hợp lý cho pure objects không cần container-managed dependencies.

## 9. Trade-offs

### Advantages

- Ownership và disposal rõ hơn.
- Giảm accidental shared mutable state.
- Request/business boundaries dễ reasoning hơn.

### Costs / Risks

- Lifetime graph phức tạp ở hệ thống lớn.
- Factory/scope có thể che dependency nếu lạm dụng.
- Singleton sai có blast radius rất lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ba lifetime và một request thường là một scope.

### Middle

Biết phát hiện captive dependency, dùng `IServiceScopeFactory` trong background work và hiểu disposal.

### Senior

Reasoning về thread safety, ownership, mutable state và resource lifetime xuyên dependency graph.

### Technical Lead / Architect

Đặt conventions cho service lifetimes, review background-processing boundaries và loại bỏ hidden global state khỏi application architecture.

## 11. Key takeaway

- Lifetime là ownership contract, không phải performance switch.
- Long-lived object không nên capture short-lived mutable dependency.
- Scope phải bám execution/business boundary thực tế.

# 2. ASP.NET Core `IAsyncEnumerable<T>` response streaming: giảm buffering nhưng phải hiểu cancellation, serialization và backpressure

## 1. What is it?

`IAsyncEnumerable<T>` cho phép producer tạo dữ liệu theo từng phần bất đồng bộ thay vì materialize toàn bộ collection trước khi trả response.

Mental model:

```text
DB/read source
   -> item 1 -> serialize -> client
   -> item 2 -> serialize -> client
   -> item 3 -> serialize -> client
```

Thay vì:

```text
load 100k rows
-> giữ toàn bộ trong memory
-> serialize toàn bộ
-> gửi response
```

## 2. Why does it exist?

Large result sets làm tăng memory pressure và time-to-first-byte nếu API luôn `ToListAsync()` trước khi trả data.

Streaming giúp:

- client nhận dữ liệu sớm hơn;
- server không nhất thiết giữ toàn bộ dataset trong memory;
- producer có thể đọc từng phần từ upstream source.

Nhưng streaming không tự động giải quyết pagination, slow client hoặc transaction duration.

## 3. How does it work?

`await foreach` gọi asynchronous enumerator từng bước. ASP.NET Core serializer có thể serialize item khi chúng được enumerate.

```text
Enumerator.MoveNextAsync()
  -> await source
  -> current item
  -> serializer writes bytes
  -> next item
```

Nếu client đọc chậm, network write có thể chậm theo. Đây là dạng backpressure tự nhiên ở I/O boundary, nhưng upstream query/resource vẫn có thể bị giữ lâu.

## 4. Practical implementation

```csharp
app.MapGet("/events/stream", (
    EventDbContext db,
    CancellationToken ct) =>
{
    return db.Events
        .AsNoTracking()
        .OrderBy(x => x.Id)
        .Select(x => new EventDto(x.Id, x.Name, x.StartAtUtc))
        .AsAsyncEnumerable()
        .WithCancellation(ct);
});
```

Với custom producer:

```csharp
static async IAsyncEnumerable<LogEntry> ReadLogsAsync(
    [EnumeratorCancellation] CancellationToken ct)
{
    while (!ct.IsCancellationRequested)
    {
        var entry = await ReadNextAsync(ct);
        yield return entry;
    }
}
```

Cancellation phải propagate khi client disconnect.

## 5. Real production scenario

Một export endpoint trả vài trăm nghìn rows. Phiên bản cũ `ToListAsync` dùng hàng trăm MB memory và TTFB cao. Streaming giảm peak memory và client bắt đầu download sớm hơn.

Tuy nhiên nếu export mất 20 phút, giữ DB reader/connection suốt 20 phút có thể gây connection pressure. Khi đó batch/chunk hoặc background export file có thể tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → API memory giảm nhưng DB connections lại bị giữ rất lâu.

**Evidence** → request duration cao, active DB readers kéo dài, client bandwidth thấp.

**Hypothesis** → streaming giữ source resource mở theo tốc độ client.

**Diagnosis** → trace request duration, SQL connection lifetime và response throughput.

**Fix** → keyset batch, materialize từng chunk nhỏ, hoặc chuyển long export sang background job + Blob Storage.

**Verification** → connection hold time giảm trong khi memory vẫn ở mức kiểm soát.

## 7. Common mistakes

- Stream vô hạn từ transactional query mà không cancellation.
- Dùng streaming cho endpoint cần random access/sorting phía client toàn dataset.
- Nghĩ streaming thay pagination.
- Giữ transaction mở trong suốt response.
- Không test client disconnect.
- Return lazy query rồi dispose context trước khi enumeration thực sự diễn ra.

## 8. Alternatives

- Pagination: tốt cho interactive APIs.
- Chunked export: cân bằng memory và resource duration.
- Background export + Blob Storage: phù hợp file rất lớn.
- Full buffering: vẫn đúng cho result nhỏ và đơn giản.

## 9. Trade-offs

### Advantages

- Giảm peak memory.
- TTFB tốt hơn.
- Hợp với large sequential datasets.

### Costs / Risks

- Resource lifetime dài hơn.
- Failure giữa stream tạo partial response khó retry.
- Slow client có thể kéo dài server-side work.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu streaming là xử lý từng phần thay vì load toàn bộ.

### Middle

Biết dùng `IAsyncEnumerable<T>`, cancellation và `AsNoTracking` phù hợp.

### Senior

Đánh giá DB connection lifetime, partial failure, slow client và batching strategy.

### Technical Lead / Architect

Quyết định endpoint nào stream trực tiếp, endpoint nào nên pagination hoặc async export pipeline.

## 11. Key takeaway

- Streaming đổi memory pressure thành lifecycle/resource-management problem.
- Luôn propagate cancellation và đo connection duration.
- Large export thường cần kiến trúc khác interactive API.

# 3. EF Core `DbContext` pooling và tenant state leakage: tối ưu allocation chỉ an toàn khi context thực sự có thể tái sử dụng

## 1. What is it?

`AddDbContextPool<TContext>` cho phép EF Core tái sử dụng các `DbContext` instances sau khi reset internal state, thay vì tạo mới hoàn toàn mỗi scope.

Mental model:

```text
Request A -> rent context #7 -> use -> return pool
Request B -> rent context #7 -> use -> return pool
```

Pooling khác connection pooling. `DbContext` pool quản lý context object; ADO.NET connection pool quản lý physical database connections.

## 2. Why does it exist?

Tạo `DbContext` không phải operation đắt nhất trong phần lớn APIs, nhưng high-throughput services có thể hưởng lợi từ việc giảm initialization/allocation overhead.

Vấn đề xuất hiện khi developers coi context như request state container. Pooled context được tái sử dụng, nên custom mutable state có thể rò sang request sau nếu không được thiết kế đúng.

## 3. How does it work?

Khi scope kết thúc, pooled context được reset và trả về pool. EF reset ChangeTracker/internal services mà framework quản lý, nhưng application-specific state không tự động trở thành an toàn.

Ví dụ `TenantId` set trong constructor không phù hợp nếu constructor chỉ chạy khi context được tạo lần đầu, trong khi context có thể phục vụ tenant khác ở lần reuse sau.

## 4. Practical implementation

Registration:

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Không nên:

```csharp
public sealed class AppDbContext : DbContext
{
    public Guid TenantId { get; set; }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Order>()
            .HasQueryFilter(x => x.TenantId == TenantId);
    }
}
```

nếu `TenantId` được gắn tùy tiện và có nguy cơ giữ value cũ.

Một hướng an toàn hơn là inject tenant context qua factory/boundary rõ ràng, hoặc không pool nếu custom state phức tạp hơn lợi ích đo được.

## 5. Real production scenario

Multi-tenant SaaS bật pooling để giảm allocations. Sau deploy, hiếm khi user tenant A thấy empty result hoặc dữ liệu tenant B bị filter sai. Bug chỉ xuất hiện dưới concurrency vì pooled context được reuse với tenant state cũ.

Đây là correctness/security incident, không phải performance regression đơn thuần.

## 6. Failure scenario & troubleshooting

**Symptom** → query filter sử dụng tenant/user state không ổn định giữa requests.

**Evidence** → same context instance phục vụ nhiều scopes; custom fields giữ giá trị không mong đợi.

**Hypothesis** → mutable per-request state nằm trong pooled context.

**Diagnosis** → log context ID, tenant ID và request correlation trong test concurrency.

**Fix** → bỏ custom mutable state khỏi context, dùng safe factory pattern, hoặc tắt pooling.

**Verification** → concurrency/integration tests nhiều tenants không còn cross-request leakage.

## 7. Common mistakes

- Nhầm `DbContext` pooling với SQL connection pooling.
- Bật pooling trước khi benchmark.
- Đặt tenant/user/request state trong context.
- Giữ references tới tracked entities sau khi scope kết thúc.
- Tưởng pooling cho phép dùng cùng context đồng thời nhiều threads.

## 8. Alternatives

- `AddDbContext`: default đơn giản và an toàn hơn.
- `IDbContextFactory<T>`: phù hợp explicit context lifetime, background hoặc UI scenarios.
- Connection pooling riêng của provider: giải quyết physical connection reuse.

## 9. Trade-offs

### Advantages

- Giảm một phần allocation/setup overhead.
- Có lợi ở high-throughput hot paths nếu đo được.

### Costs / Risks

- Lifetime reasoning khó hơn.
- Custom state có thể leak.
- Performance gain thường nhỏ hơn query/index/network improvements.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbContext` vẫn là unit-of-work và không thread-safe.

### Middle

Phân biệt context pooling với connection pooling.

### Senior

Biết benchmark và audit mutable state trước khi bật pooling.

### Technical Lead / Architect

Quyết định optimization này có đáng complexity/correctness risk hay không, đặc biệt ở multi-tenant systems.

## 11. Key takeaway

- Pooling tái sử dụng `DbContext` object, không biến nó thành Singleton.
- Per-request mutable state và pooling là tổ hợp nguy hiểm.
- Chỉ bật khi benchmark chứng minh lợi ích có ý nghĩa.

# 4. SQL Server connection pool exhaustion: vì sao “database timeout” đôi khi không phải query chậm

## 1. What is it?

ADO.NET connection pooling giữ các physical database connections đã mở để request sau có thể reuse thay vì thực hiện handshake mới.

Connection pool exhaustion xảy ra khi application cần connection nhưng pool không còn connection khả dụng trước timeout.

Mental model:

```text
App requests connection
   -> pool has free connection -> rent immediately
   -> pool empty -> wait
        -> connection returned -> continue
        -> wait too long -> timeout
```

## 2. Why does it exist?

Mở database connection vật lý liên tục rất đắt. Pooling giảm latency và resource cost.

Nhưng pool hữu hạn. Nếu code giữ connection lâu, transactions dài, queries treo hoặc connection không dispose đúng, throughput application có thể bị giới hạn bởi pool trước cả khi SQL Server CPU cao.

## 3. How does it work?

`SqlConnection.OpenAsync()` thường lấy connection từ pool theo connection string. Connection được trả về pool khi dispose/close, không nhất thiết đóng physical TCP connection.

Các connection strings khác nhau có thể tạo pools khác nhau. Vì vậy một thay đổi nhỏ trong connection string cũng có thể phân mảnh pool.

## 4. Practical implementation

Pattern đúng:

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(ct);

await using var command = connection.CreateCommand();
command.CommandText = "SELECT ...";

await using var reader = await command.ExecuteReaderAsync(ct);
```

Với EF Core, dispose `DbContext` đúng scope thường trả underlying connection đúng cách.

Quan trọng hơn syntax là đo thời gian:

```text
time waiting for connection
vs
SQL execution time
vs
transaction duration
```

## 5. Real production scenario

API bắt đầu trả lỗi timeout sau deployment. SQL CPU chỉ 35%. Investigation cho thấy một endpoint gọi downstream HTTP trong khi transaction DB vẫn mở. Mỗi request giữ một connection thêm 4–8 giây. Traffic tăng nhẹ là pool 100 connections bị chiếm hết.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout khi mở connection, latency spike nhưng database CPU không tương ứng.

**Evidence** → active requests chờ pool, transaction duration cao, connection usage đạt ceiling.

**Hypothesis** → connection hold time quá dài hoặc leak/lifetime sai.

**Diagnosis** → correlate application traces, transaction spans, SQL waits và pool/runtime counters.

**Fix** → rút ngắn transaction/query, dispose đúng, bỏ remote I/O khỏi DB transaction, sau đó mới cân nhắc tăng pool size.

**Verification** → connection wait giảm và peak concurrency không chạm pool ceiling.

## 7. Common mistakes

- Tăng `Max Pool Size` ngay mà không tìm root cause.
- Mở connection quá sớm.
- Giữ `DbDataReader` trong long-running stream không có chủ đích.
- Transaction bao quanh HTTP call.
- Dùng nhiều connection strings gần giống nhau gây pool fragmentation.
- Kết luận mọi DB timeout là slow SQL.

## 8. Alternatives

- Tăng pool size: chỉ khi DB chịu được thêm concurrency và hold time là hợp lý.
- Queue/backpressure: giới hạn concurrent DB work.
- Read replica: giải quyết workload read scale, không sửa connection leak.
- Query optimization: cần khi connection bị giữ vì query thực sự chậm.

## 9. Trade-offs

### Advantages

- Pooling giảm handshake cost đáng kể.
- Cho phép throughput cao với số physical connections hữu hạn.

### Costs / Risks

- Pool có thể trở thành bottleneck ẩn.
- Tăng pool quá mức có thể đẩy overload xuống database.
- Long-lived work giữ scarce resource lâu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Open` thường thuê connection từ pool và `Dispose` trả nó về.

### Middle

Biết đo query/transaction duration và đảm bảo disposal.

### Senior

Phân biệt pool wait, SQL latency và lock wait bằng telemetry.

### Technical Lead / Architect

Đặt concurrency budget giữa app tier và database, thay vì scale application vô hạn nhưng giữ database connection model cũ.

## 11. Key takeaway

- Connection timeout không đồng nghĩa query timeout.
- Connection hold time là metric production quan trọng.
- Tăng pool size chỉ hợp lý sau khi hiểu bottleneck thật.

# 5. Azure Cosmos DB consistency levels và session consistency: chọn consistency theo business invariant thay vì chọn mức mạnh nhất theo cảm giác

## 1. What is it?

Cosmos DB cung cấp nhiều consistency levels để cân bằng freshness, latency, availability và distributed replication behavior.

Các mức phổ biến theo hướng mạnh → yếu hơn gồm:

```text
Strong
Bounded Staleness
Session
Consistent Prefix
Eventual
```

`Session` thường cung cấp read-your-writes trong cùng client session thông qua session token mà không yêu cầu global strong consistency.

## 2. Why does it exist?

Trong distributed database, replicas ở nhiều regions không thể luôn vừa đồng bộ tuyệt đối, vừa latency thấp và availability tối đa trong mọi failure scenario.

Consistency level là business/architecture choice về **người đọc được phép thấy dữ liệu cũ đến mức nào**.

## 3. How does it work?

Write được replicate. Tùy consistency contract, read có thể cần chờ quorum/replication nhiều hơn hoặc có thể đọc replica chưa mới nhất.

Session token giúp client thể hiện logical version đã quan sát. Các reads tiếp theo trong session có thể tránh quay ngược về state cũ hơn state client vừa ghi.

## 4. Practical implementation

Ví dụ một user cập nhật profile rồi đọc lại ngay trong cùng application session. `Session` consistency thường phù hợp hơn việc chọn `Strong` toàn account chỉ vì muốn read-your-writes.

```csharp
var client = new CosmosClient(
    connectionString,
    new CosmosClientOptions
    {
        ConsistencyLevel = ConsistencyLevel.Session
    });
```

Không nên chọn level chỉ từ code sample. Cần map từng workload: cart, analytics, catalog, billing, inventory reservation.

## 5. Real production scenario

E-commerce catalog replicated nhiều regions có thể chấp nhận vài giây stale data. Nhưng inventory reservation không thể chỉ dựa vào eventually consistent read rồi decrement ở application layer.

Ở đây vấn đề không đơn giản là tăng consistency toàn database; thường cần conditional write/ETag, partition-local atomicity hoặc transactional design phù hợp invariant.

## 6. Failure scenario & troubleshooting

**Symptom** → user update data rồi request kế tiếp đôi khi thấy giá trị cũ khi request đi qua service instance khác.

**Evidence** → session token không được propagate đúng, client instances/lifetime không phù hợp hoặc consistency expectation vượt contract.

**Hypothesis** → application giả định read-your-writes nhưng implementation làm mất session context.

**Diagnosis** → trace region, client/session token behavior và request path.

**Fix** → reuse `CosmosClient` đúng lifetime, propagate session token khi kiến trúc yêu cầu, hoặc thay consistency strategy cho business flow đó.

**Verification** → deterministic tests qua multi-instance path và regional test setup phù hợp.

## 7. Common mistakes

- Chọn Strong vì “an toàn nhất”.
- Dùng Eventual cho invariant tài chính chỉ để giảm latency.
- Nhầm consistency với transaction.
- Tạo `CosmosClient` mỗi request.
- Không hiểu partition boundary và nghĩ global consistency sửa mọi race condition.

## 8. Alternatives

- SQL database khi workload yêu cầu relational transaction phức tạp.
- MongoDB/other stores tùy access pattern.
- Application-level version/ETag + conditional writes.
- Eventual consistency + reconciliation khi business cho phép.

## 9. Trade-offs

### Advantages

- Cho phép chọn consistency phù hợp workload.
- Session thường cân bằng tốt cho user-centric applications.

### Costs / Risks

- Mô hình consistency làm application reasoning khó hơn.
- Stronger consistency có latency/availability/cost implications.
- Weaker consistency yêu cầu UI/business xử lý staleness rõ ràng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu distributed replicas có thể không thấy cùng state cùng lúc.

### Middle

Biết các consistency levels và khi nào cần ETag/conditional write.

### Senior

Map business invariant sang consistency + partition + write strategy.

### Technical Lead / Architect

Quyết định consistency per workload và tránh dùng một account-wide setting để che thiếu domain reasoning.

## 11. Key takeaway

- Consistency là business contract, không phải checkbox hạ tầng.
- Session consistency thường giải quyết read-your-writes hiệu quả.
- Invariant quan trọng vẫn cần atomic write/concurrency design phù hợp.

# 6. Anti-Corruption Layer cho third-party integration: cô lập external model để vendor change không lan vào domain

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary dịch giữa model của hệ thống bên ngoài và model của domain nội bộ.

Mental model:

```text
Domain
  |
  | internal concepts
  v
Anti-Corruption Layer
  |
  | external DTO/protocol
  v
Vendor API
```

Mục tiêu là ngăn terminology, quirks và data shape của vendor trở thành model cốt lõi của application.

## 2. Why does it exist?

Third-party APIs thay đổi version, enum, auth scheme, field meaning và failure behavior. Nếu domain services dùng trực tiếp vendor DTOs, mỗi thay đổi bên ngoài lan sâu vào business code.

ACL giúp localize translation và cho domain nói bằng ngôn ngữ của business nội bộ.

## 3. How does it work?

Boundary thường gồm:

- client giao tiếp protocol;
- external DTOs;
- mapper/translator;
- domain-facing interface;
- error normalization.

Dependency direction nên để domain/application phụ thuộc vào internal contract, còn infrastructure adapter phụ thuộc vendor SDK/API.

```text
Application -> IShippingRateProvider
Infrastructure -> VendorShippingClient
Infrastructure maps VendorRate -> ShippingQuote
```

## 4. Practical implementation

```csharp
public interface IShippingRateProvider
{
    Task<ShippingQuote> GetQuoteAsync(
        Shipment shipment,
        CancellationToken ct);
}

public sealed class VendorShippingRateProvider(
    VendorClient client) : IShippingRateProvider
{
    public async Task<ShippingQuote> GetQuoteAsync(
        Shipment shipment,
        CancellationToken ct)
    {
        var response = await client.GetRatesAsync(
            VendorRequestMapper.Map(shipment), ct);

        return new ShippingQuote(
            response.TotalAmount,
            response.Currency,
            MapServiceLevel(response.ServiceCode));
    }
}
```

Vendor DTO không đi qua application boundary.

## 5. Real production scenario

Review provider đổi `rating` từ số 1–5 sang string category và deprecate field cũ. Nếu UI/domain phụ thuộc trực tiếp vendor JSON, thay đổi lan qua nhiều projects. Với ACL, adapter map format mới về internal `ReviewScore`, phần còn lại gần như không đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → vendor thêm enum value mới làm deserialization hoặc domain switch fail.

**Evidence** → raw response chứa value chưa biết; adapter mapping throw exception.

**Hypothesis** → external contract evolved ngoài assumptions.

**Diagnosis** → capture sanitized payload/schema version, compare contract docs và telemetry.

**Fix** → tolerant external parsing, explicit unknown mapping, contract tests và alert.

**Verification** → replay captured payload qua adapter tests.

## 7. Common mistakes

- Copy vendor DTO làm domain entity.
- Đặt business rules trong HTTP client.
- Catch mọi vendor error và trả `null`.
- Expose vendor status codes trực tiếp ra public API nội bộ.
- Tạo abstraction quá generic kiểu `IExternalService<T>` không có domain meaning.

## 8. Alternatives

- Direct client usage: đủ tốt cho integration nhỏ, low-risk, replaceability không quan trọng.
- Generated client + thin mapper: thường là practical default.
- Event-based integration: phù hợp asynchronous ownership boundary.

## 9. Trade-offs

### Advantages

- Cô lập vendor change.
- Domain model rõ và ổn định hơn.
- Testing failure/translation dễ hơn.

### Costs / Risks

- Thêm mapping code.
- Có thể overengineer wrapper nếu vendor API rất đơn giản.
- Translation layer phải được maintain cùng contract evolution.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain model.

### Middle

Viết typed adapter, mapping và normalized errors.

### Senior

Thiết kế boundary theo business capability, timeout/retry/fallback và contract evolution.

### Technical Lead / Architect

Quyết định integration nào cần ACL thực sự và giữ dependency direction để vendor không định hình core domain.

## 11. Key takeaway

- ACL bảo vệ domain khỏi external vocabulary và change rate.
- Boundary tốt thường nhỏ, domain-specific và testable.
- Không cần wrapper phức tạp nếu integration đơn giản và ít rủi ro.

# 7. Azure App Service autoscale: scale-out chỉ hiệu quả khi application không phụ thuộc hidden in-memory state

## 1. What is it?

Autoscale tăng hoặc giảm số App Service instances dựa trên metric/rule như CPU, memory, queue length hoặc schedule.

```text
1 instance
   -> load tăng
   -> scale rule
   -> 4 instances
   -> load balancer phân phối requests
```

Scale-out tăng số process độc lập; nó không biến nhiều process thành một shared-memory application.

## 2. Why does it exist?

Traffic thay đổi theo giờ/campaign. Provision fixed peak capacity gây lãng phí, trong khi fixed low capacity gây overload.

Autoscale cho phép capacity phản ứng theo demand, nhưng chỉ khi application có thể chạy trên nhiều instances một cách đúng đắn.

## 3. How does it work?

Mỗi instance có process, memory, local filesystem semantics và lifecycle riêng. Requests có thể đến instance khác nhau.

Nếu state quan trọng chỉ lưu `IMemoryCache`, static dictionary hoặc local file, behavior sau scale-out trở nên không nhất quán.

Scheduled jobs chạy trong web app cũng có thể chạy trên mọi instance nếu không có coordination.

## 4. Practical implementation

Scale-safe application thường:

```text
session/state -> external/shared store when required
files         -> Blob Storage
cache         -> Redis when cross-instance sharing needed
jobs          -> queue/Function/worker with ownership semantics
secrets       -> Key Vault / configuration provider
```

Autoscale rules nên dùng metric phản ánh saturation/workload thật. CPU 70% có thể hữu ích cho CPU-bound service; queue depth thường tốt hơn cho worker workload.

## 5. Real production scenario

Campaign làm traffic tăng 5x. App scale từ 2 lên 8 instances. Users bắt đầu mất cart vì cart được giữ trong static memory. Đồng thời scheduled cleanup job chạy 8 lần.

Infrastructure scale thành công; application semantics thất bại.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi chỉ xuất hiện khi có nhiều instances; user state không ổn định hoặc duplicate jobs.

**Evidence** → correlation logs cho thấy request của cùng user đi qua instance IDs khác nhau; state nằm local memory.

**Hypothesis** → hidden single-instance assumption.

**Diagnosis** → inventory in-memory state, local disk usage, singleton schedulers và cache ownership.

**Fix** → externalize state cần share, thiết kế idempotent jobs, dùng queue/distributed coordination hoặc tách worker.

**Verification** → load test với >=2 instances và deliberate restarts.

## 7. Common mistakes

- Bật autoscale rồi giả định application tự scale-safe.
- Dùng sticky sessions để che design issue dài hạn.
- Scale theo CPU cho I/O-bound bottleneck ở database.
- Không đặt max instance/cost guard.
- Scale web tier trong khi database đã saturated.
- Lưu upload trên local disk rồi mong instance khác nhìn thấy.

## 8. Alternatives

- Vertical scale-up: đơn giản nhưng có ceiling và vẫn single-instance assumptions.
- Container Apps/AKS: nhiều control hơn nhưng operational complexity cao hơn.
- Queue-based worker scaling: phù hợp background workload.
- Fixed capacity: đúng cho low/steady traffic.

## 9. Trade-offs

### Advantages

- Elastic capacity.
- Có thể giảm manual intervention và cost so với peak provisioning cố định.

### Costs / Risks

- Multi-instance correctness requirement.
- Warm-up/cold-start behavior.
- Downstream database/API có thể trở thành bottleneck.
- Cost tăng nhanh nếu rule sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mỗi instance là process riêng với memory riêng.

### Middle

Biết externalize shared state và đọc instance/correlation telemetry.

### Senior

Thiết kế scale signal, downstream capacity và fault behavior.

### Technical Lead / Architect

Quyết định scaling model toàn hệ thống thay vì chỉ web tier, gồm database, cache, queue, cost và operational limits.

## 11. Key takeaway

- Scale-out phơi bày mọi hidden single-instance assumption.
- Autoscale phải đi cùng statelessness/idempotency phù hợp.
- Scale bottleneck, không chỉ scale layer dễ cấu hình nhất.

# 8. Git bisect cho deployment regression: biến “commit nào làm hỏng production?” thành tìm kiếm có bằng chứng

## 1. What is it?

`git bisect` dùng binary search để tìm commit đầu tiên gây regression giữa một commit known-good và known-bad.

```text
Good -------------------------- Bad
             test midpoint
                   |
          good? -> search right half
          bad?  -> search left half
```

Thay vì test tuần tự 100 commits, binary search cần khoảng `log2(100)` lần kiểm tra.

## 2. Why does it exist?

Production regression thường xuất hiện sau nhiều commits được release cùng nhau. Blame theo cảm giác hoặc “commit cuối cùng chắc là lỗi” dễ sai.

Bisect biến investigation thành process có hypothesis test lặp lại.

## 3. How does it work?

```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-sha>
```

Git checkout midpoint. Bạn chạy reproduction test rồi đánh dấu:

```bash
git bisect good
# hoặc
git bisect bad
```

Cuối cùng Git xác định first bad commit.

Có thể automation bằng:

```bash
git bisect run ./scripts/regression-test.sh
```

Exit code 0 = good, non-zero theo semantics script.

## 4. Practical implementation

Một latency regression có thể được biến thành deterministic test:

```bash
#!/usr/bin/env bash
set -e

dotnet test tests/RegressionTests \
  --filter FullyQualifiedName~ProductSearchRegression
```

Nếu test tái hiện đúng issue, `git bisect run` giúp tìm commit gây thay đổi behavior.

Quan trọng: test phải đủ deterministic để classification good/bad đáng tin.

## 5. Real production scenario

Sau weekly release, product search trả sai filter cho một edge case. Release chứa 70 commits. Team tạo integration test từ production payload đã sanitize, xác nhận commit trước release pass, HEAD fail, rồi dùng bisect tìm commit thay đổi query composition.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect trả commit “thủ phạm” nhưng checkout commit đó không build độc lập.

**Evidence** → historical commits phụ thuộc migration/tooling state hoặc test flaky.

**Hypothesis** → predicate good/bad không deterministic hoặc history không buildable.

**Diagnosis** → chạy reproduction nhiều lần, dùng `git bisect skip` cho commit không test được.

**Fix** → làm test hermetic hơn, pin dependencies, chọn phạm vi history phù hợp.

**Verification** → cherry-pick/revert suspected commit làm regression biến mất hoặc test pass.

## 7. Common mistakes

- Dùng bisect khi chưa có reproducible signal.
- Đánh dấu good/bad dựa manual cảm giác.
- Không reset sau khi xong: `git bisect reset`.
- Kết luận commit đầu tiên gây test fail chắc chắn là root cause cuối cùng mà không đọc diff.
- Không xét config/database migration ngoài Git history.

## 8. Alternatives

- `git log`/`git blame`: tốt khi phạm vi nhỏ/rõ.
- Revert recent commit: phù hợp incident cần restore service ngay.
- Feature flags: giảm blast radius và giúp isolate behavior.
- Deployment comparison/observability: cần khi lỗi đến từ config/infrastructure hơn source commit.

## 9. Trade-offs

### Advantages

- Thu hẹp regression rất nhanh.
- Dựa trên executable evidence.
- Dễ automate.

### Costs / Risks

- Cần reproducible test.
- Historical commits có thể không build.
- Không tìm được config/environment regression nằm ngoài Git source.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu good/bad commit và binary search.

### Middle

Dùng bisect với unit/integration test deterministic.

### Senior

Biến production symptom thành minimal executable regression test và xác minh causality.

### Technical Lead / Architect

Xây release/observability/testability sao cho regressions có thể được isolate nhanh, thay vì phụ thuộc tribal knowledge.

## 11. Key takeaway

- `git bisect` chỉ mạnh khi good/bad signal đáng tin.
- Reproduction test là tài sản quan trọng hơn command Git.
- Source regression và environment regression phải được phân biệt.

# 9. Optimizely CMS content modeling và cache invalidation: page, block, content area và freshness contract trong production

## 1. What is it?

Trong CMS, content model xác định cách editors tạo và tái sử dụng nội dung. Với Optimizely CMS, các khái niệm như Page, Block và ContentArea biểu diễn các cấp composition khác nhau.

Mental model:

```text
Page
 ├─ Hero Block
 ├─ ContentArea
 │   ├─ Promo Block
 │   └─ Product Teaser Block
 └─ SEO metadata
```

Caching phải tôn trọng dependency giữa các content items này.

## 2. Why does it exist?

Nếu mọi trang là một object khổng lồ, editor khó tái sử dụng và development khó evolve. Nếu chia thành quá nhiều blocks nhỏ, editorial workflow lại phức tạp.

Content modeling cân bằng reuse, ownership, editorial usability và rendering performance.

Caching tồn tại vì CMS pages thường read-heavy, nhưng cache sai invalidation khiến nội dung publish rồi người dùng vẫn thấy bản cũ.

## 3. How does it work?

Một rendered page có thể phụ thuộc nhiều content references. Khi block dùng chung được publish lại, mọi page dùng block đó có thể cần fresh rendering/data.

Cache strategy có thể nằm nhiều layer:

```text
Browser
 -> CDN
 -> ASP.NET/output cache
 -> CMS object cache
 -> content repository
```

Mỗi layer có TTL/invalidation semantics khác nhau.

## 4. Practical implementation

Content model nên theo editorial concept:

```csharp
[ContentType(DisplayName = "Promo Block")]
public class PromoBlock : BlockData
{
    public virtual string Heading { get; set; } = string.Empty;
    public virtual Url? Link { get; set; }
}
```

Không nên biến block thành service locator chứa query logic lớn. Rendering component/service lấy content model rồi gọi application services cần thiết qua boundary rõ.

Khi cache rendered fragments, key nên bao gồm content version/culture và invalidation phải gắn publication events hoặc short TTL phù hợp business.

## 5. Real production scenario

Marketing publish một global promo block dùng trên 200 pages. CMS repository đã có version mới nhưng CDN/output cache vẫn giữ HTML cũ 30 phút. Editors nghĩ publish hỏng và republish nhiều lần.

Root cause nằm ở multi-layer cache ownership không rõ.

## 6. Failure scenario & troubleshooting

**Symptom** → backend preview đúng nhưng public site vẫn hiện content cũ.

**Evidence** → response headers cho thấy CDN HIT, age cao; origin response đã mới.

**Hypothesis** → stale ở edge/output cache, không phải CMS persistence.

**Diagnosis** → kiểm tra từng layer: CMS version → app response → reverse proxy/CDN → browser.

**Fix** → purge/tag invalidation đúng layer hoặc điều chỉnh TTL/cache-key contract.

**Verification** → publish test content, trace freshness end-to-end và xác nhận cache observability.

## 7. Common mistakes

- Dùng block cho mọi field nhỏ.
- Gắn business logic nặng trực tiếp vào content model.
- Cache mà không định nghĩa invalidation owner.
- Quên culture/visitor-group/version trong cache key khi relevant.
- Đổ lỗi CMS khi stale nằm ở CDN/browser.
- Dùng preview behavior để suy ra production caching behavior.

## 8. Alternatives

- Page-centric model đơn giản: tốt cho site ít reuse.
- Headless CMS: hợp khi nhiều channels cần cùng content API.
- Traditional server-rendered Optimizely: đơn giản hơn cho web-centric editorial flow.
- Composable architecture: linh hoạt hơn nhưng tăng integration/operational complexity.

## 9. Trade-offs

### Advantages

- Blocks cho phép reuse và editorial composition.
- Cache nhiều layer có thể giảm origin load mạnh.

### Costs / Risks

- Reuse tăng dependency graph.
- Invalidation khó hơn khi một block xuất hiện nhiều pages.
- Composable/headless tăng số network boundaries.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Page, Block và ContentArea phục vụ mục đích editorial khác nhau.

### Middle

Implement content types, rendering và cache-aware behavior.

### Senior

Reasoning về cache dependency, publication freshness, culture/version và performance.

### Technical Lead / Architect

Thiết kế content model theo editorial workflow và ownership, đồng thời định nghĩa cache/freshness contract xuyên CMS–app–CDN.

## 11. Key takeaway

- Content modeling là business/editorial architecture, không chỉ class hierarchy.
- Cache freshness phải được reasoning xuyên nhiều layers.
- Reuse tốt nhưng dependency graph và invalidation phải được kiểm soát.

# 10. Contract Testing cho APIs và integrations: bảo vệ boundary quan trọng mà không biến test suite thành hàng nghìn mocks giả tạo

## 1. What is it?

Contract Testing kiểm tra hai systems có đồng ý về interface boundary hay không: request shape, response shape, status codes, headers, schema, semantics quan trọng.

Mental model:

```text
Consumer expectation
       ↕
    Contract
       ↕
Provider implementation
```

Nó không thay unit test hay end-to-end test; nó tập trung vào compatibility giữa producer và consumer.

## 2. Why does it exist?

Microservices/third-party integrations thường fail không phải vì code từng service sai nội bộ, mà vì hai bên hiểu contract khác nhau.

Ví dụ provider rename field, đổi nullable semantics hoặc trả status code mới. Unit tests ở cả hai repos vẫn xanh nếu chúng chỉ mock đối phương.

## 3. How does it work?

Contract test có thể là:

- consumer-driven contract;
- schema/OpenAPI compatibility test;
- provider integration test với recorded fixtures;
- executable contract trong shared compatibility pipeline.

Điểm cốt lõi là test một **boundary thật**, không phải mock interface nội bộ rồi tự chứng minh mock của mình đúng.

## 4. Practical implementation

Ví dụ ASP.NET Core integration test kiểm tra public contract:

```csharp
[Fact]
public async Task GetOrder_ReturnsCompatibleContract()
{
    var response = await client.GetAsync("/api/orders/123");

    response.StatusCode.Should().Be(HttpStatusCode.OK);

    var json = await response.Content.ReadFromJsonAsync<JsonElement>();
    json.GetProperty("id").GetString().Should().NotBeNullOrWhiteSpace();
    json.GetProperty("status").GetString().Should().NotBeNullOrWhiteSpace();
}
```

Ở mức mạnh hơn, CI có thể diff OpenAPI schema và fail khi có breaking change không được version hóa.

## 5. Real production scenario

Order service đổi `total` từ number sang string để giữ formatting. Frontend TypeScript client và billing integration vẫn expect number. Unit tests backend đều pass; production consumers fail.

Contract compatibility check ở CI có thể chặn change trước deploy.

## 6. Failure scenario & troubleshooting

**Symptom** → provider tests xanh nhưng consumer fail sau release.

**Evidence** → mocks không khớp payload thật hoặc OpenAPI schema đã breaking change.

**Hypothesis** → test suite kiểm tra implementation isolation nhưng không kiểm tra integration contract.

**Diagnosis** → compare request/response thực tế với consumer expectations và historical schema.

**Fix** → thêm executable compatibility test, schema diff, versioning hoặc additive migration path.

**Verification** → provider mới chạy against known consumer contracts trước promotion.

## 7. Common mistakes

- Mock provider ở mọi test rồi gọi đó là integration coverage.
- Contract test mọi internal implementation detail.
- Snapshot toàn JSON khổng lồ gây brittle tests.
- Không phân biệt additive change với breaking change.
- Dùng shared DTO package khiến services coupled compile-time và tưởng đó là contract governance.
- Không có deprecation/version policy.

## 8. Alternatives

- Full E2E tests: coverage rộng nhưng chậm và flaky hơn.
- Integration tests với real dependency: tốt nhưng cần environment/data management.
- OpenAPI schema diff: nhẹ và hữu ích cho HTTP shape compatibility.
- Manual coordination: đủ cho hệ thống nhỏ ít consumers nhưng không scale tốt.

## 9. Trade-offs

### Advantages

- Phát hiện breaking integration sớm.
- Giảm dependency vào fragile end-to-end suites.
- Khuyến khích explicit API evolution.

### Costs / Risks

- Contract artifacts cần ownership/versioning.
- Consumer-driven contracts có thể proliferate nếu governance kém.
- Không chứng minh business flow end-to-end hoạt động hoàn chỉnh.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu unit test của một service không bảo đảm hai services tương thích.

### Middle

Viết API integration/contract tests và kiểm tra schema/status code semantics.

### Senior

Phân loại breaking/additive changes, thiết kế backward-compatible rollout và contract pipeline.

### Technical Lead / Architect

Quyết định boundary nào cần contract testing, ai sở hữu compatibility policy và khi nào versioning/deprecation là cần thiết.

## 11. Key takeaway

- Contract Testing bảo vệ boundary giữa systems, không thay mọi loại test khác.
