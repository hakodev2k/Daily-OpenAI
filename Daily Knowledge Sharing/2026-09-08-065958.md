# 1. C# Source Generators: compile-time code generation, reflection avoidance và maintenance trade-offs

## 1. What is it?

Source Generator là compiler extension chạy trong quá trình build và tạo thêm C# source code trước khi compilation hoàn tất.

Mental model:

```text
Your source
   ↓
Roslyn compilation
   ↓
Source Generator inspects symbols
   ↓
Generated .cs code
   ↓
Final compilation
```

Khác với runtime reflection, generator chuyển một phần discovery/boilerplate sang compile time.

## 2. Why does it exist?

Nhiều framework historically dựa vào reflection để tìm types, attributes, serializers hoặc mappings. Reflection linh hoạt nhưng có thể tăng startup cost, làm Native AOT khó hơn và đẩy một số lỗi sang runtime.

Source Generators giúp tạo code strongly typed, giảm runtime discovery và đưa lỗi sớm hơn về build time.

## 3. How does it work?

Generator đọc syntax/symbol model từ Roslyn, tìm pattern hoặc attribute cần xử lý, rồi emit source.

Ví dụ serializer source generation có thể tạo code đọc/ghi property trực tiếp thay vì dùng reflection để enumerate metadata mỗi lần.

Điểm quan trọng: generated source trở thành một phần compilation; nó không phải magic runtime layer.

## 4. Practical implementation

Ví dụ `System.Text.Json` source generation:

```csharp
[JsonSerializable(typeof(OrderDto))]
[JsonSerializable(typeof(List<OrderDto>))]
internal partial class AppJsonContext : JsonSerializerContext
{
}
```

Sử dụng:

```csharp
var json = JsonSerializer.Serialize(order, AppJsonContext.Default.OrderDto);
```

Trong ASP.NET Core có thể register generated metadata thay vì mặc định reflection-based serialization cho hot paths hoặc AOT-oriented apps.

## 5. Real production scenario

Một API serverless hoặc container scale-to-zero cần cold start nhanh. Runtime reflection để discover serializer metadata, mapping hoặc DI registration có thể góp phần tăng startup path.

Source generation giảm một phần runtime discovery, đặc biệt hữu ích khi startup latency hoặc Native AOT là requirement thật.

## 6. Failure scenario & troubleshooting

**Symptom** → build chậm bất thường hoặc generated code gây compile error khó đọc.

**Evidence** → compiler trace cho thấy generator chạy lâu; generated files quá lớn; incremental generator invalidation xảy ra thường xuyên.

**Hypothesis** → generator scan quá rộng hoặc không tận dụng incremental model.

**Diagnosis** → inspect generated output, build timing và phạm vi syntax/symbol được đọc.

**Fix** → dùng Incremental Generator, filter sớm, tránh scan toàn compilation nếu không cần.

**Verification** → đo build time trước/sau và kiểm tra generated source nhỏ, deterministic.

## 7. Common mistakes

* Dùng generator chỉ để “tránh viết code”, dù runtime reflection hoàn toàn đủ.
* Generator đọc toàn solution cho một feature nhỏ.
* Emit source không deterministic.
* Không expose generated files cho debugging.
* Dùng generator để nhúng business logic khó review.

## 8. Alternatives

Reflection đơn giản hơn và đủ tốt cho nhiều application. Runtime code generation bằng Expression Trees có thể phù hợp khi metadata chỉ biết lúc runtime. T4 hoặc external codegen phù hợp khi generation nằm ngoài compiler pipeline.

## 9. Trade-offs

### Advantages

* Giảm runtime reflection.
* Compile-time validation tốt hơn.
* Hỗ trợ Native AOT tốt hơn trong nhiều trường hợp.

### Costs / Risks

* Build pipeline phức tạp hơn.
* Debug generated code khó hơn.
* Generator design kém có thể làm incremental build chậm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu generator tạo source trước compile, không phải runtime magic.

### Middle

Biết đọc generated code và debug compilation errors.

### Senior

Đánh giá startup/runtime benefit so với build complexity.

### Technical Lead / Architect

Chỉ chấp nhận source generation khi nó giải quyết measurable constraint: AOT, startup, type safety hoặc repetitive metadata có giá trị rõ.

## 11. Key takeaway

* Source Generators chuyển một số work từ runtime sang compile time.
* Chúng hữu ích nhất khi reflection/startup/AOT thực sự là constraint.
* Generator kém có thể đổi runtime problem thành build-system problem.

# 2. ASP.NET Core request-body buffering & streaming: memory pressure, retry semantics và large payload safety

## 1. What is it?

HTTP request body trong ASP.NET Core mặc định là stream forward-only. Một middleware hoặc endpoint đọc body rồi thì downstream không thể tự động đọc lại trừ khi buffering được bật.

Mental model:

```text
Client body → Kestrel stream → middleware → model binding / endpoint
```

Buffering tạo khả năng rewind; streaming xử lý dữ liệu dần thay vì materialize toàn payload.

## 2. Why does it exist?

Logging, signature verification hoặc request replay đôi khi cần đọc body nhiều lần. Nhưng copy toàn payload vào memory cho mọi request dễ tạo memory pressure, đặc biệt với upload lớn.

Do đó hệ thống phải quyết định rõ: body nào cần buffer, body nào phải stream.

## 3. How does it work?

`EnableBuffering()` cho phép request body được đọc lại. Payload nhỏ có thể nằm memory; lớn hơn threshold có thể spill ra temporary storage tùy implementation.

Streaming giữ peak memory thấp hơn nhưng yêu cầu consumer xử lý dữ liệu tuần tự và không phụ thuộc full-body random access.

## 4. Practical implementation

Middleware cần đọc body có kiểm soát:

```csharp
app.Use(async (context, next) =>
{
    context.Request.EnableBuffering(bufferThreshold: 30 * 1024, bufferLimit: 1024 * 1024);

    using var reader = new StreamReader(
        context.Request.Body,
        leaveOpen: true);

    var body = await reader.ReadToEndAsync(context.RequestAborted);
    context.Request.Body.Position = 0;

    await next();
});
```

Không nên dùng pattern này cho file upload hàng trăm MB.

## 5. Real production scenario

Webhook endpoint cần verify HMAC signature trên raw body rồi model-bind JSON. Nếu middleware đọc stream nhưng quên rewind, endpoint nhận empty body và trả 400.

Ngược lại, nếu bật buffering không giới hạn cho public upload endpoint, attacker có thể tạo disk/memory pressure.

## 6. Failure scenario & troubleshooting

**Symptom** → model binding thỉnh thoảng nhận body rỗng hoặc memory tăng khi upload traffic cao.

**Evidence** → middleware đã đọc `Request.Body`; buffering không giới hạn; large payloads tăng đồng thời.

**Hypothesis** → stream consumption hoặc buffering policy sai.

**Diagnosis** → trace middleware order, payload size distribution, memory/temp-file usage.

**Fix** → rewind đúng, giới hạn request size, stream large payload, chỉ buffer endpoint thực sự cần.

**Verification** → integration test raw-body verification + model binding; load test large payload.

## 7. Common mistakes

* Log toàn raw body chứa secrets/PII.
* Buffer mọi request chỉ để debug.
* Không giới hạn upload size.
* Đọc stream ở middleware rồi không reset position.
* Dùng `ReadToEndAsync()` cho multi-GB payload.

## 8. Alternatives

Streaming trực tiếp vào Blob Storage cho file lớn. Reverse proxy/CDN có thể enforce body-size limit sớm hơn. Với webhook, chỉ buffer payload nhỏ cần signature verification.

## 9. Trade-offs

### Advantages của buffering

* Có thể đọc body nhiều lần.
* Thuận tiện cho signature verification và diagnostics.

### Costs / Risks

* Memory/disk pressure.
* Tăng latency do copy dữ liệu.
* Security risk nếu logging raw payload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request body là stream, không phải string có thể đọc vô hạn lần.

### Middle

Biết khi nào dùng `EnableBuffering` và reset position.

### Senior

Thiết kế size limits, streaming và sensitive-data handling.

### Technical Lead / Architect

Xác định boundary: payload lớn nên đi qua application, direct-to-storage hay dedicated ingestion service.

## 11. Key takeaway

* Body stream có ownership/lifecycle rõ.
* Buffering là capability có chi phí, không phải default an toàn.
* Large payload nên được stream và giới hạn từ edge tới application.

# 3. SQL Server parameter sniffing: execution-plan reuse, skewed data và plan instability

## 1. What is it?

Parameter sniffing xảy ra khi SQL Server compile query plan dựa trên parameter values nhìn thấy tại thời điểm compilation, sau đó reuse plan đó cho executions khác.

Plan reuse thường tốt; vấn đề xuất hiện khi data distribution rất skewed và một plan không phù hợp cho mọi parameter.

## 2. Why does it exist?

Compilation tốn CPU. SQL Server cache plan để tránh compile lại mỗi execution. Optimizer cần cardinality estimate để chọn join strategy, index access và memory grant, nên parameter value ban đầu ảnh hưởng plan.

## 3. How does it work?

Ví dụ:

```sql
SELECT *
FROM Orders
WHERE CustomerId = @CustomerId;
```

Một customer có 2 orders, customer khác có 2 triệu orders. Plan tối ưu cho customer nhỏ có thể dùng nested loops + seek; plan đó reuse cho whale customer có thể cực chậm.

## 4. Practical implementation

Đầu tiên đo plan và runtime evidence:

```sql
SET STATISTICS IO, TIME ON;
EXEC dbo.GetOrders @CustomerId = 42;
EXEC dbo.GetOrders @CustomerId = 999999;
```

Sau đó so sánh actual execution plans, row estimates, reads và memory grant.

Các options có thể gồm query rewrite, better indexes, `OPTION (RECOMPILE)` cho query phù hợp hoặc Query Store plan management. Không chọn hint trước khi có evidence.

## 5. Real production scenario

API `/customers/{id}/orders` p95 ổn nhiều giờ rồi đột nhiên chậm sau deployment/restart. First execution sau cache clear thuộc một whale customer, tạo plan phù hợp whale nhưng tệ cho phần lớn traffic — hoặc ngược lại.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng query text lúc nhanh lúc chậm sau plan cache change.

**Evidence** → Query Store có nhiều plan hoặc performance change theo compile time/parameter; estimates lệch lớn.

**Hypothesis** → plan reuse không phù hợp data skew.

**Diagnosis** → Query Store, actual plan, parameter distribution, statistics freshness.

**Fix** → address skew/access pattern, statistics/index/query design; dùng recompile/hint có chủ đích khi justified.

**Verification** → test representative parameter classes và p95/p99 ổn định sau plan changes.

## 7. Common mistakes

* Xóa plan cache production như permanent fix.
* Dùng `OPTION (RECOMPILE)` cho mọi query.
* Chỉ nhìn estimated plan.
* Đổ lỗi parameter sniffing cho mọi slow query.
* Không kiểm tra data skew và statistics.

## 8. Alternatives

Separate query paths cho fundamentally different parameter classes. Dynamic SQL parameterized có thể tạo plan shape phù hợp hơn. Query Store hints giúp operational control nhưng vẫn cần root-cause understanding.

## 9. Trade-offs

### Advantages của plan reuse

* Giảm compile CPU.
* Throughput tốt cho stable workloads.

### Costs / Risks

* Một plan có thể không tối ưu cho skewed distributions.
* Recompile tăng CPU và latency compilation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu database không “chạy SQL từ đầu” giống nhau mỗi lần; execution plan được cache.

### Middle

Biết đọc actual plan và IO stats.

### Senior

Phân biệt skew, stale statistics, index issue và true parameter-sniffing symptoms.

### Technical Lead / Architect

Thiết kế access pattern và operational tooling để plan instability không biến thành production surprise.

## 11. Key takeaway

* Parameter sniffing là side effect của plan reuse, không phải bug mặc định.
* Data skew mới là yếu tố thường làm vấn đề bộc lộ.
* Chẩn đoán bằng Query Store + actual plans, không bằng guess.

# 4. Cosmos DB cross-partition query: fan-out, RU cost và thiết kế access pattern

## 1. What is it?

Cross-partition query là query không xác định được một partition key cụ thể, nên Cosmos DB phải fan-out request tới nhiều physical/logical partitions liên quan rồi merge kết quả.

## 2. Why does it exist?

Cosmos DB scale bằng partitioning. Partition key tốt giúp point reads và targeted queries rẻ/predictable. Nhưng application đôi khi cần query theo field không chứa partition key.

Fan-out tồn tại để vẫn query được, nhưng chi phí và latency tăng theo data distribution.

## 3. How does it work?

```text
Query without partition key
        ↓
Coordinator
  ├─ Partition A
  ├─ Partition B
  ├─ Partition C
  └─ Partition N
        ↓
Merge results
```

Mỗi partition tiêu thụ work/RUs. Index giúp giảm scan trong từng partition nhưng không loại bỏ fan-out nếu partition pruning không thể xảy ra.

## 4. Practical implementation

Targeted query:

```csharp
var query = new QueryDefinition(
    "SELECT * FROM c WHERE c.tenantId = @tenantId AND c.status = @status")
    .WithParameter("@tenantId", tenantId)
    .WithParameter("@status", "Active");

var options = new QueryRequestOptions
{
    PartitionKey = new PartitionKey(tenantId)
};
```

Nếu access pattern thường xuyên là “find by email across all tenants”, có thể cần lookup container/materialized projection thay vì chấp nhận cross-partition query trên dataset lớn.

## 5. Real production scenario

SaaS dùng `tenantId` làm partition key. Admin search toàn hệ thống theo `externalReference` chạy tốt khi có 50k documents nhưng RU và latency tăng mạnh khi có hàng trăm triệu documents.

Problem không nằm ở SDK; access pattern không align partition model.

## 6. Failure scenario & troubleshooting

**Symptom** → RU/query tăng theo data volume dù result chỉ vài records.

**Evidence** → query metrics cho thấy fan-out nhiều partitions; no partition key supplied.

**Hypothesis** → access pattern không partition-aware.

**Diagnosis** → inspect query metrics, continuation behavior, partition count, RU charge.

**Fix** → target partition, projection/index container, change access path hoặc reconsider partition key nếu workload fundamentally khác.

**Verification** → RU và latency ổn định khi dataset scale.

## 7. Common mistakes

* Nghĩ index sẽ loại bỏ cross-partition cost.
* Chọn partition key chỉ theo uniqueness.
* Dùng synthetic partition key mà không dựa trên queries.
* Không log `RequestCharge`.
* Đánh giá Cosmos DB chỉ bằng functional correctness.

## 8. Alternatives

SQL database cho workload cần ad-hoc joins/queries rộng. Elasticsearch cho search use cases. Secondary lookup container hoặc materialized projection cho specific global lookup.

## 9. Trade-offs

### Advantages

* Cross-partition query giữ tính linh hoạt.
* Không cần duplicate data ngay từ đầu.

### Costs / Risks

* RU/latency tăng khi fan-out lớn.
* Cost khó predict nếu query pattern không bounded.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định data placement.

### Middle

Biết supply `PartitionKey` khi query có thể target một tenant.

### Senior

Đọc RU/query metrics và model access patterns.

### Technical Lead / Architect

Thiết kế partitioning dựa trên workload thật, scale horizon và global-query requirements.

## 11. Key takeaway

* Partition key là query-routing decision, không chỉ schema field.
* Cross-partition query hợp lệ nhưng có cost model khác.
* Nếu global lookup là critical path, hãy thiết kế nó explicit.

# 5. DDD Aggregate boundary: invariant, transaction boundary và tránh giant aggregate

## 1. What is it?

Aggregate là nhóm domain objects được coi như một consistency boundary. Aggregate Root là entry point để thay đổi state và bảo vệ invariants của aggregate.

Mental model:

```text
Command
  ↓
Aggregate Root
  ↓
Validate invariant
  ↓
State change inside one consistency boundary
```

## 2. Why does it exist?

Nếu mọi entity có thể bị sửa tùy ý từ mọi nơi, business invariants phân tán và transaction boundary không rõ. Aggregate gom những rules bắt buộc phải consistent ngay lập tức.

## 3. How does it work?

Ví dụ Order cần invariant: không được confirm nếu không có line items. `Order.Confirm()` kiểm tra invariant thay vì application service set `Status = Confirmed` trực tiếp.

Không phải mọi dữ liệu liên quan đến Order đều phải nằm trong cùng aggregate. Payment, Inventory hoặc Shipment có thể là boundaries khác với eventual consistency.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public OrderStatus Status { get; private set; }
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void Confirm()
    {
        if (_lines.Count == 0)
            throw new DomainException("Cannot confirm an empty order.");

        if (Status != OrderStatus.Draft)
            throw new DomainException("Only draft orders can be confirmed.");

        Status = OrderStatus.Confirmed;
    }
}
```

Application service orchestrates loading/saving; invariant lives trong domain model.

## 5. Real production scenario

Team modeling Customer → Orders → Payments → Shipments → Reviews thành một giant aggregate. Mỗi update phải load graph lớn, concurrency conflict tăng và transaction kéo dài.

Boundary đúng thường nhỏ hơn: chỉ những state cần strong consistency ngay lập tức mới ở chung aggregate.

## 6. Failure scenario & troubleshooting

**Symptom** → frequent optimistic concurrency conflicts và SaveChanges chậm.

**Evidence** → aggregate graph rất lớn; nhiều workflows độc lập cùng update root.

**Hypothesis** → aggregate boundary quá rộng.

**Diagnosis** → map invariants: rule nào thực sự cần atomic consistency, rule nào có thể eventual.

**Fix** → split aggregates, dùng domain events/workflow cho cross-boundary coordination.

**Verification** → smaller transaction, reduced contention, invariants vẫn được enforce.

## 7. Common mistakes

* Aggregate = toàn bộ object graph có foreign keys.
* Mọi child entity đều được expose setter public.
* Dùng domain event để thay mọi method call trong cùng aggregate.
* Tạo aggregate theo table boundaries thay vì invariants.
* Giant aggregate vì “DDD phải consistency mạnh”.

## 8. Alternatives

Anemic model + application services đủ tốt cho CRUD domain đơn giản. Transaction script thường dễ hiểu hơn nếu business rules ít. DDD aggregate nên dùng khi invariants/business behavior thực sự có độ phức tạp.

## 9. Trade-offs

### Advantages

* Business invariants có owner rõ.
* Transaction boundary rõ.
* Encapsulation tốt hơn.

### Costs / Risks

* Modeling effort cao hơn.
* Boundary sai gây contention hoặc eventual-consistency complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu entity không chỉ là table row có getters/setters.

### Middle

Biết đặt business rules vào aggregate methods.

### Senior

Phân biệt invariant cần atomic consistency với cross-aggregate workflow.

### Technical Lead / Architect

Chọn aggregate boundaries dựa trên invariants, contention và business ownership — không dựa trên ER diagram.

## 11. Key takeaway

* Aggregate là consistency boundary.
* Boundary quá lớn làm concurrency và performance tệ.
* DDD chỉ có giá trị khi nó bảo vệ business complexity thật.

# 6. Azure Service Bus Sessions: ordering theo business key mà không serialize toàn hệ thống

## 1. What is it?

Service Bus Sessions cho phép group messages có cùng `SessionId` và đảm bảo một receiver giữ exclusive lock trên session trong khi xử lý. Nó hỗ trợ ordered processing theo một business key mà vẫn cho nhiều sessions chạy song song.

## 2. Why does it exist?

Một queue global FIFO serialize toàn workload và giảm throughput. Nhưng nhiều domain chỉ cần ordering per entity, ví dụ events của cùng `OrderId` phải theo thứ tự, còn orders khác có thể xử lý đồng thời.

Sessions giải quyết đúng boundary đó.

## 3. How does it work?

```text
Session Order-1: M1 → M2 → M3   handled sequentially
Session Order-2: M1 → M2        handled sequentially
Session Order-3: M1 → M2 → M3   handled sequentially

Different sessions can run concurrently.
```

Receiver accept một session, giữ session lock và xử lý messages của session đó.

## 4. Practical implementation

Producer:

```csharp
var message = new ServiceBusMessage(payload)
{
    MessageId = eventId,
    SessionId = orderId.ToString()
};

await sender.SendMessageAsync(message, ct);
```

Consumer vẫn cần idempotency; session ordering không loại bỏ duplicate delivery.

## 5. Real production scenario

Order lifecycle events: `OrderCreated`, `PaymentCaptured`, `OrderShipped`. Nếu các event cùng order được xử lý out of order, downstream projection có thể thấy `OrderShipped` trước `OrderCreated`.

Dùng `SessionId = OrderId` bảo vệ ordering per order trong khi hệ thống vẫn xử lý hàng nghìn orders song song.

## 6. Failure scenario & troubleshooting

**Symptom** → một subset messages backlog trong khi queue tổng thể vẫn có consumers rảnh.

**Evidence** → một hot session có rất nhiều messages hoặc handler session bị chậm.

**Hypothesis** → per-session serialization tạo hot key.

**Diagnosis** → metrics theo session/message age, processing duration, session lock failures.

**Fix** → giảm work per message, tránh session key quá coarse, tách workflow khi ordering requirement không thật sự cần toàn chuỗi.

**Verification** → throughput tăng mà per-key order vẫn đúng.

## 7. Common mistakes

* SessionId = tenantId cho tenant cực lớn → serialize toàn tenant.
* Nghĩ session = exactly-once.
* Không xử lý lock renewal.
* Một message poison block progress của session lâu.
* Dùng sessions dù messages độc lập.

## 8. Alternatives

Partitioned Kafka topic cho ordering by key. Application-level sequencing bằng version number. Không dùng ordering nếu consumer có thể thiết kế commutative/idempotent behavior.

## 9. Trade-offs

### Advantages

* Ordering per business key.
* Parallelism giữa keys.

### Costs / Risks

* Hot session giới hạn throughput.
* Lock/session lifecycle phức tạp hơn queue thường.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ordering thường cần theo key, không phải toàn queue.

### Middle

Biết set `SessionId` và xử lý session-enabled queue.

### Senior

Thiết kế idempotency, poison handling và hot-session mitigation.

### Technical Lead / Architect

Xác định business entity nào thực sự yêu cầu ordering và throughput ceiling chấp nhận được.

## 11. Key takeaway

* Sessions cho FIFO theo key, không phải global FIFO.
* Ordering luôn đổi lấy một mức serialization.
* Session key là architecture decision, không chỉ message metadata.

# 7. SLO & Error Budget: biến reliability thành engineering constraint có thể đo lường

## 1. What is it?

SLI là metric đo service behavior. SLO là target cho SLI trong một khoảng thời gian. Error budget là phần failure còn được phép trước khi vi phạm SLO.

Ví dụ: availability SLO 99.9% trong 30 ngày tương đương khoảng 0.1% request budget cho failure theo định nghĩa SLI.

## 2. Why does it exist?

Nếu target chỉ là “hệ thống phải ổn định”, team không biết khi nào reliability đủ tốt hoặc khi nào nên ưu tiên feature vs hardening.

SLO tạo một measurable contract nội bộ giữa product velocity và reliability.

## 3. How does it work?

Ví dụ request-based SLI:

```text
good_requests / valid_requests
```

SLO:

```text
>= 99.9% trong rolling 30 days
```

Error budget:

```text
1 - 0.999 = 0.001
```

Burn rate cho biết budget bị tiêu thụ nhanh tới mức nào.

## 4. Practical implementation

Trong Application Insights/OpenTelemetry pipeline, định nghĩa “good request” rõ ràng: status nào là server failure, latency threshold nào vượt SLO, health probes có loại ra không.

Một KQL-style query conceptual:

```text
Good = requests where success == true and duration < 500ms
Total = valid production requests
SLI = Good / Total
```

Alert nên dựa trên burn rate, không chỉ một spike ngắn.

## 5. Real production scenario

API có average availability 99.95% nhưng mỗi deployment gây 10 phút lỗi concentrated đúng giờ business. Monthly average nhìn vẫn đẹp nhưng UX tệ.

SLO window + burn-rate alert giúp phát hiện budget đang cháy nhanh thay vì chỉ nhìn monthly summary.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard báo SLO tốt nhưng users vẫn complain.

**Evidence** → SLI loại nhầm critical endpoint hoặc aggregate toàn requests làm high-volume health traffic che business failures.

**Hypothesis** → SLI không đại diện user experience.

**Diagnosis** → map critical journeys, request classes, latency percentiles.

**Fix** → redesign SLI theo user-facing outcome, tách critical services/endpoints.

**Verification** → incident thật phải phản ánh rõ trong SLO/burn-rate dashboard.

## 7. Common mistakes

* SLO = SLA copy-paste.
* Chọn 99.99% vì “nghe enterprise”.
* Dùng average latency làm SLI duy nhất.
* Health-check traffic làm đẹp availability.
* Có SLO nhưng không có action policy khi budget gần hết.

## 8. Alternatives

Simple operational thresholds đủ cho system nhỏ. SLA là external/business commitment; SLO thường là engineering target nội bộ và có thể chặt hơn SLA.

## 9. Trade-offs

### Advantages

* Reliability có language định lượng.
* Giúp ưu tiên engineering work.
* Alerting gắn với user impact hơn.

### Costs / Risks

* SLI sai tạo false confidence.
* SLO quá cao tăng cost/complexity không cần thiết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu logs/metrics không chỉ để debug mà còn đo reliability.

### Middle

Biết xây dashboard cho SLI.

### Senior

Thiết kế burn-rate alerts và tránh misleading metrics.

### Technical Lead / Architect

Chọn SLO theo business criticality, architecture cost và recovery capability.

## 11. Key takeaway

* SLO tốt phải phản ánh user outcome.
* Error budget biến reliability thành trade-off có thể quản lý.
* 99.99% không miễn phí; mỗi “9” thêm đều có architectural cost.

# 8. JWT validation + JWKS key rotation: vì sao “decode được token” không đồng nghĩa authentication an toàn

## 1. What is it?

JWT validation là quá trình xác minh token thực sự do trusted issuer phát hành và phù hợp audience, lifetime, signing algorithm/key cùng các policy khác.

JWKS (JSON Web Key Set) cung cấp public keys để resource server validate signatures và hỗ trợ key rotation.

## 2. Why does it exist?

JWT payload chỉ base64url-encoded, không phải encrypted. Bất kỳ ai cũng có thể decode claims. Security đến từ signature validation và semantic checks.

Nếu application chỉ đọc `sub`, `role` rồi tin claims, attacker có thể tự tạo token giả.

## 3. How does it work?

```text
JWT header contains kid
      ↓
Resource server obtains issuer JWKS
      ↓
Find matching public key
      ↓
Verify signature
      ↓
Validate iss / aud / exp / nbf / algorithm
      ↓
Build authenticated principal
```

Khi identity provider rotate signing keys, JWKS publish key mới và giữ overlap đủ để active tokens cũ vẫn validate.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = "https://login.example.com/tenant";
        options.Audience = "orders-api";
        options.RequireHttpsMetadata = true;
    });
```

Middleware sẽ dùng metadata/JWKS discovery từ trusted authority thay vì hard-code một signing key vĩnh viễn.

## 5. Real production scenario

Identity provider rotate key. Một service hard-code public key cũ bắt đầu reject tất cả token mới, gây outage sau rotation.

Ngược lại, service tự fetch arbitrary `jku` từ token header có thể tạo SSRF/trust-boundary vulnerability.

## 6. Failure scenario & troubleshooting

**Symptom** → 401 tăng đột ngột sau IdP key rotation.

**Evidence** → token `kid` mới không có trong local cache/hard-coded key.

**Hypothesis** → signing-key refresh failure.

**Diagnosis** → inspect metadata endpoint/JWKS reachability, cache refresh logs, issuer/audience config.

**Fix** → use trusted authority metadata, resilient refresh, network access đúng.

**Verification** → validate tokens signed bằng old/new overlapping keys trong rotation window.

## 7. Common mistakes

* Decode JWT rồi coi là validated.
* Bỏ audience validation.
* Accept issuer wildcard.
* Cho token tự chỉ định arbitrary JWKS URL.
* Hard-code một signing key không rotation.
* Log full access token.

## 8. Alternatives

Opaque tokens + introspection phù hợp khi central validation/revocation requirements cao. Cookie authentication phù hợp traditional web app. JWT không phải default tốt cho mọi session model.

## 9. Trade-offs

### Advantages

* Local signature validation giảm dependency call per request.
* Scales tốt cho distributed APIs.

### Costs / Risks

* Revocation khó hơn.
* Key rotation/cache/trust configuration phải đúng.
* Claims có thể stale đến khi token expire.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu decode ≠ verify.

### Middle

Biết configure issuer/audience/lifetime validation.

### Senior

Hiểu JWKS caching, key rotation và failure modes.

### Technical Lead / Architect

Chọn token/session strategy dựa trên revocation, trust boundaries, latency và operational complexity.

## 11. Key takeaway

* JWT security nằm ở validation, không ở encoding.
* Key rotation là normal lifecycle, phải được thiết kế trước.
* Trusted metadata endpoint là trust boundary quan trọng.

# 9. Vue reactivity: `computed`, `watch`, `watchEffect` và race condition trong async UI

## 1. What is it?

Vue reactivity track dependencies giữa reactive state và effects. `computed` dành cho derived state, `watch` cho side effects dựa trên nguồn cụ thể, còn `watchEffect` tự track dependencies được đọc trong effect.

## 2. Why does it exist?

UI state thay đổi liên tục. Nếu developer tự sync nhiều derived fields bằng imperative code, state dễ lệch. Reactivity giúp dependency graph tự propagate changes.

Nhưng async effects vẫn có race conditions nếu request cũ hoàn tất sau request mới.

## 3. How does it work?

```text
reactive state changes
      ↓
dependency invalidated
      ↓
computed recomputes / watcher runs
      ↓
UI or side effect updates
```

`computed` nên pure. `watch` phù hợp cho API call, persistence hoặc imperative side effect.

## 4. Practical implementation

```ts
const search = ref('');
const normalized = computed(() => search.value.trim().toLowerCase());

watch(search, async (value, _, onCleanup) => {
  const controller = new AbortController();
  onCleanup(() => controller.abort());

  const response = await fetch(
    `/api/products?q=${encodeURIComponent(value)}`,
    { signal: controller.signal }
  );

  results.value = await response.json();
});
```

Cleanup hủy stale request khi search term thay đổi nhanh.

## 5. Real production scenario

User gõ `car`, rồi nhanh chóng đổi thành `cargo`. Request `cargo` hoàn tất trước, sau đó request `car` chậm hơn trả về và overwrite results mới.

UI hiển thị kết quả sai dù mỗi request riêng lẻ đều thành công.

## 6. Failure scenario & troubleshooting

**Symptom** → UI đôi lúc hiển thị stale data khi input thay đổi nhanh.

**Evidence** → network waterfall cho thấy responses hoàn tất out of order.

**Hypothesis** → async watcher race.

**Diagnosis** → correlate request parameters với completion order.

**Fix** → abort stale requests, sequence token hoặc server-state library có stale request handling.

**Verification** → automated test rapid input changes và delayed responses.

## 7. Common mistakes

* Dùng `watch` để tạo derived state nên có thể dùng `computed`.
* Side effects trong `computed`.
* `watchEffect` đọc quá nhiều dependencies ngoài ý muốn.
* Không cleanup timers/requests.
* Deep watch giant object gây unnecessary work.

## 8. Alternatives

TanStack Query/Vue Query cho server-state caching, cancellation và stale handling. Explicit event handlers đơn giản hơn watcher khi side effect chỉ xảy ra từ một user action cụ thể.

## 9. Trade-offs

### Advantages

* Derived state declarative.
* Dependency tracking giảm manual synchronization.

### Costs / Risks

* Hidden dependencies trong `watchEffect` khó reasoning.
* Async effects cần lifecycle/race handling riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `computed` là derived value.

### Middle

Biết chọn `watch` cho side effects và cleanup async work.

### Senior

Thiết kế server-state flow tránh stale race và duplicate requests.

### Technical Lead / Architect

Đặt boundary rõ giữa local UI state, derived state và server state; tránh watcher trở thành implicit orchestration layer toàn app.

## 11. Key takeaway

* `computed` cho derived state; `watch` cho side effects.
* Async reactivity không tự giải quyết race condition.
* Cleanup/cancellation là phần của frontend correctness.

# 10. Consumer-Driven Contract Testing: phát hiện breaking integration trước khi deploy

## 1. What is it?

Consumer-Driven Contract Testing (CDC) cho phép consumer mô tả interaction mà nó thực sự cần từ provider; contract được verify phía provider để phát hiện breaking change sớm.

Mental model:

```text
Consumer expectation
      ↓
Contract artifact
      ↓
Provider verification
      ↓
Compatibility evidence
```

## 2. Why does it exist?

Unit tests của provider có thể pass nhưng vẫn break consumer vì đổi field, status code hoặc semantics. End-to-end tests bắt được một phần nhưng thường chậm, brittle và cần nhiều environments.

CDC tập trung vào integration contract ở boundary.

## 3. How does it work?

Consumer test tạo contract cho request/response thật sự cần. Provider CI chạy verification against current implementation.

Điểm quan trọng: contract không nên encode toàn response schema nếu consumer chỉ dùng một subset; nếu quá chặt, tests trở thành coupling mới.

## 4. Practical implementation

Ví dụ contract concept cho consumer:

```json
{
  "request": {
    "method": "GET",
    "path": "/api/orders/123"
  },
  "response": {
    "status": 200,
    "body": {
      "id": "123",
      "status": "Confirmed"
    }
  }
}
```

Provider verification trong CI đảm bảo endpoint vẫn đáp ứng interaction này trước khi release.

## 5. Real production scenario

Orders API đổi `status` từ string sang nested object để “clean model”. Provider tests pass vì API behavior mới hợp spec nội bộ. Mobile app cũ deserialize fail ngay sau deployment.

CDC có thể fail trong provider CI trước khi breaking change tới production.

## 6. Failure scenario & troubleshooting

**Symptom** → CDC suite có hàng trăm failures sau harmless provider change.

**Evidence** → contracts assert toàn payload kể cả fields consumer không dùng.

**Hypothesis** → over-specified contracts.

**Diagnosis** → compare consumer code với contract assertions.

**Fix** → assert only required semantics, version/break contract intentionally khi cần.

**Verification** → provider refactor không break irrelevant contracts; real breaking change vẫn bị bắt.

## 7. Common mistakes

* Dùng CDC thay thế mọi integration/E2E test.
* Consumer publish contract nhưng provider không verify trong CI.
* Assert timestamps/irrelevant fields exact match.
* Không manage contract versions/deploy compatibility.
* Treat schema compatibility như business-semantic compatibility đầy đủ.

## 8. Alternatives

OpenAPI schema validation tốt cho structural contract. Integration tests against real provider tốt cho broader behavior. E2E tests cần thiết cho critical journeys. CDC bổ sung chứ không thay thế toàn bộ pyramid.

## 9. Trade-offs

### Advantages

* Feedback sớm hơn E2E production-like tests.
* Provider biết consumer nào có thể bị break.
* Hỗ trợ independent deployment an toàn hơn.

### Costs / Risks

* Contract lifecycle/broker/tooling thêm complexity.
* Over-specification tạo coupling giả.
* Không chứng minh toàn distributed workflow hoạt động.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu API compatibility không chỉ là compile pass.

### Middle

Viết consumer interaction test focused.

### Senior

Thiết kế contract boundaries và compatibility strategy.

### Technical Lead / Architect

Quyết định nơi CDC có ROI: nhiều independently deployed consumers/providers với breaking-change risk đáng kể.

## 11. Key takeaway

* CDC kiểm tra contract consumer thực sự phụ thuộc.
* Contract quá rộng sẽ tạo coupling mới.
* CDC mạnh nhất khi provider verification nằm trong CI/release gate.
