# 1. C# boxing/unboxing trong generic code: allocation ẩn, interface dispatch và khi nào value type thực sự giúp performance

## 1. What is it?

Boxing là quá trình CLR đặt một value type như `int`, `DateTime` hoặc `struct` vào một object trên managed heap để nó có thể được xử lý như `object` hoặc một interface reference.

Mental model:

```text
int value = 42
   ↓ boxing
object reference
   ↓
heap object chứa copy của 42
```

Unboxing là lấy value type trở lại từ boxed object. Điều đáng quan tâm trong production không phải bản thân cú pháp, mà là allocation, copy và dispatch ẩn có thể xuất hiện trong hot path.

## 2. Why does it exist?

.NET cần một unified object model: value type vẫn có thể đi qua API nhận `object`, implement interface hoặc tham gia một số non-generic abstractions.

Trước generics, collections như `ArrayList` buộc value type phải boxing. Generics tồn tại một phần để giữ type information xuyên runtime và tránh boxing không cần thiết.

## 3. How does it work?

Ví dụ:

```csharp
int x = 42;
object boxed = x;
int y = (int)boxed;
```

`boxed` không trỏ vào stack slot của `x`; CLR tạo object mới chứa một copy.

Generic code thường tránh boxing:

```csharp
static bool AreEqual<T>(T a, T b)
    where T : IEquatable<T>
    => a.Equals(b);
```

Trong khi API dựa vào `object` có thể tạo boxing:

```csharp
static bool AreEqual(object a, object b)
    => a.Equals(b);
```

Một subtle case là gọi interface method trên struct. JIT có thể tối ưu một số trường hợp bằng constrained call, nhưng nếu value đã bị convert thành interface reference thì boxing có thể xảy ra.

## 4. Practical implementation

Không nên dùng `object` chỉ để tạo API “generic”:

```csharp
public static object Max(object left, object right)
{
    var a = (int)left;
    var b = (int)right;
    return Math.Max(a, b);
}
```

Thay bằng generic constraint:

```csharp
public static T Max<T>(T left, T right)
    where T : IComparable<T>
{
    return left.CompareTo(right) >= 0 ? left : right;
}
```

Khi code thực sự nằm trong hot path, dùng BenchmarkDotNet hoặc profiler để xác nhận allocations thay vì tối ưu bằng trực giác.

## 5. Real production scenario

Một telemetry pipeline format hàng triệu numeric measurements mỗi phút. Developer dùng `params object[]` cho mọi log helper. Mỗi số nguyên, enum và `DateTime` có thể bị boxing trước khi logger xử lý.

Ở traffic thấp không đáng kể. Ở production throughput lớn, Gen0 allocation rate tăng mạnh, GC chạy thường xuyên hơn và CPU dành nhiều thời gian thu gom short-lived objects.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU tăng, Gen0 collections dày, allocation rate cao nhưng object lifetime rất ngắn.

**Evidence** → allocation profiler chỉ ra nhiều boxed value types hoặc `object[]` từ logging/formatting path.

**Hypothesis** → abstraction dùng `object` tạo allocation ẩn trong hot path.

**Diagnosis** → profile allocation stack và benchmark đoạn code cụ thể.

**Fix** → chuyển sang generic/typed API, source-generated logging hoặc overload typed khi đáng giá.

**Verification** → allocation bytes/op và GC frequency giảm sau benchmark/load test.

## 7. Common mistakes

* Cho rằng mọi struct đều “không allocate”. Struct vẫn có thể bị boxing.
* Viết custom struct lớn rồi truyền/copy khắp nơi để tránh heap, cuối cùng tốn copy cost hơn.
* Tối ưu boxing trong path chạy vài lần/ngày trong khi bottleneck thật nằm ở database.
* Dùng `object` vì muốn API linh hoạt nhưng không đánh giá allocation impact.

## 8. Alternatives

Reference types có thể phù hợp hơn khi object lớn, identity quan trọng hoặc lifetime dài.

`record struct`, generic constraints và typed logging APIs giúp giữ value semantics mà giảm boxing trong các path phù hợp.

## 9. Trade-offs

### Advantages

Value types có thể giảm heap allocation và cải thiện locality khi nhỏ, immutable và được dùng đúng context.

### Costs / Risks

Struct lớn gây copy cost; boxing có thể xuất hiện qua interface/object boundaries; generic specialization có thể tăng code size.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu value type và reference type có runtime behavior khác nhau; boxing tạo object.

### Middle

Nhận diện `object`, non-generic APIs và interface conversions có thể gây boxing.

### Senior

Đo allocation bằng profiler/benchmark, cân bằng allocation, copy cost, JIT behavior và readability.

### Technical Lead / Architect

Không biến micro-optimization thành coding standard toàn hệ thống; chỉ áp dụng khi workload và measurements chứng minh lợi ích.

## 11. Key takeaway

* Boxing là allocation/copy boundary ẩn giữa value type và object/interface abstractions.
* Generics thường giúp giữ type information và tránh boxing.
* Chỉ tối ưu khi allocation profile chứng minh đây là bottleneck thật.

# 2. ASP.NET Core middleware ordering: vì sao thứ tự Authentication, Authorization, exception handling và endpoint routing thay đổi behavior toàn request pipeline

## 1. What is it?

ASP.NET Core middleware pipeline là chuỗi components xử lý request theo thứ tự đăng ký và response theo chiều ngược lại.

Mental model:

```text
Request
  ↓
Middleware A
  ↓
Middleware B
  ↓
Endpoint
  ↑
Middleware B
  ↑
Middleware A
```

Thứ tự không phải style preference. Nó quyết định component nào nhìn thấy route metadata, user identity, exception hoặc response đã được tạo.

## 2. Why does it exist?

Cross-cutting concerns như exception handling, authentication, authorization, CORS, compression và logging cần chạy quanh business endpoint mà không lặp code trong từng controller.

Pipeline cho phép composition rõ ràng, nhưng cái giá là behavior phụ thuộc thứ tự.

## 3. How does it work?

Ví dụ điển hình:

```csharp
app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
```

Authentication phải chạy trước Authorization để `HttpContext.User` được thiết lập trước khi policy được đánh giá.

Exception handler phải nằm đủ sớm để catch exception phát sinh downstream.

Routing cần hoàn tất trước middleware nào cần đọc endpoint metadata.

## 4. Practical implementation

Có thể thêm diagnostic middleware để hiểu pipeline:

```csharp
app.Use(async (context, next) =>
{
    var endpointBefore = context.GetEndpoint();
    await next();
    var endpointAfter = context.GetEndpoint();

    app.Logger.LogDebug(
        "Endpoint before: {Before}; after: {After}",
        endpointBefore?.DisplayName,
        endpointAfter?.DisplayName);
});
```

Trong production, không nên log quá nhiều per-request details ở hot path, nhưng kỹ thuật này hữu ích để hiểu ordering trong môi trường test.

## 5. Real production scenario

API có policy `[Authorize(Policy = "AdminOnly")]`. Sau refactor startup, `UseAuthorization()` bị đặt trước `UseAuthentication()`.

Token hợp lệ nhưng authorization chạy khi `HttpContext.User` chưa có authenticated principal. Production bắt đầu trả 401/403 cho user hợp lệ dù JWT validation code không thay đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint trả 401/403 sau deployment, local unit tests vẫn pass.

**Evidence** → request trace cho thấy auth handler chưa chạy trước authorization; user identity rỗng tại policy evaluation.

**Hypothesis** → middleware ordering regression.

**Diagnosis** → inspect startup pipeline, endpoint metadata và logs quanh Authentication/Authorization.

**Fix** → đặt middleware theo lifecycle dependency đúng.

**Verification** → integration test toàn HTTP pipeline bằng `WebApplicationFactory`, không chỉ unit-test handler riêng.

## 7. Common mistakes

* Nghĩ `UseAuthentication()` và `UseAuthorization()` có thể đảo thứ tự.
* Đặt custom exception middleware sau endpoint mapping nên không bắt được exception cần thiết.
* Custom middleware gọi `next()` hai lần hoặc quên gọi `next()` mà không chủ ý short-circuit.
* Dựa vào unit tests và không có integration test cho pipeline behavior.

## 8. Alternatives

Một số cross-cutting concerns có thể đặt ở filters, endpoint filters hoặc delegating handlers. Boundary đúng phụ thuộc concern nằm ở HTTP pipeline, endpoint invocation hay outbound dependency.

## 9. Trade-offs

### Advantages

Middleware tách cross-cutting concerns khỏi business code và áp dụng nhất quán toàn application.

### Costs / Risks

Global ordering tạo implicit dependency. Pipeline dài làm behavior khó reason và mỗi middleware đều thêm overhead.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu middleware là chain xử lý request/response.

### Middle

Biết ordering cơ bản cho routing, authentication, authorization và exception handling.

### Senior

Debug pipeline bằng endpoint metadata, integration tests và request traces; tránh custom middleware khi concern thuộc layer khác.

### Technical Lead / Architect

Giữ pipeline nhỏ, có ownership rõ và documented ordering constraints để giảm hidden coupling.

## 11. Key takeaway

* Middleware order là runtime behavior, không phải formatting.
* Cross-cutting component chỉ hoạt động đúng khi dữ liệu nó phụ thuộc đã được tạo trước đó.
* Integration tests nên bảo vệ pipeline-level contracts.

# 3. EF Core `ExecutionStrategy` + explicit transaction: retry transient failure mà không vô tình chạy business transaction hai lần

## 1. What is it?

EF Core execution strategy là cơ chế retry transient database failures, ví dụ một số connection/network faults trong cloud database.

Điểm khó xuất hiện khi application tự mở explicit transaction. Nếu mỗi database operation có retry riêng nhưng transaction do application kiểm soát, EF Core không thể tự replay toàn bộ transaction như một unit.

## 2. Why does it exist?

Distributed infrastructure tạo transient failures: connection reset, failover, throttling hoặc short network interruption.

Retry một operation đọc thường đơn giản. Retry một transaction nhiều bước nguy hiểm hơn vì application cần biết toàn bộ unit có thể được replay an toàn hay không.

## 3. How does it work?

Pattern đúng là để execution strategy execute toàn transaction delegate:

```text
ExecutionStrategy
   ↓ execute/retry whole delegate
Begin transaction
   ↓
Step A
   ↓
Step B
   ↓
Commit
```

Nếu transient failure xảy ra trước commit và state xác định được, strategy có thể replay delegate. Nhưng nếu connection mất ngay sau commit, application có thể không biết commit đã thành công hay chưa: commit ambiguity.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var transaction =
        await db.Database.BeginTransactionAsync(ct);

    var order = Order.Create(customerId);
    db.Orders.Add(order);

    db.AuditEntries.Add(new AuditEntry
    {
        Action = "OrderCreated",
        EntityId = order.Id
    });

    await db.SaveChangesAsync(ct);
    await transaction.CommitAsync(ct);
});
```

Nếu transaction bao gồm external API call, retry toàn delegate có thể gọi external side effect nhiều lần. Vì vậy transaction delegate nên chỉ chứa operations có replay semantics được hiểu rõ.

## 5. Real production scenario

Azure SQL failover ngắn trong lúc Order API ghi order và audit row. Team bật retry globally nhưng code tự mở transaction sai cách. Khi lỗi transient xảy ra, một operation được retry ngoài transaction context mong đợi và request thất bại với exception về execution strategy không hỗ trợ user-initiated transaction theo cách đó.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi chỉ xuất hiện khi database transient fault/failover; normal load không tái hiện.

**Evidence** → exception liên quan execution strategy và user-initiated transaction hoặc duplicate external side effect sau retry.

**Hypothesis** → retry boundary không trùng transaction boundary.

**Diagnosis** → inspect transaction scope, external calls và EF retry configuration.

**Fix** → execute toàn DB transaction qua strategy; tách non-idempotent external side effects sang Outbox/workflow phù hợp.

**Verification** → fault-injection test transient database error và kiểm tra final state không duplicate.

## 7. Common mistakes

* Nghĩ “retry database” luôn an toàn.
* Đặt payment/API call bên trong delegate có thể replay.
* Retry `SaveChanges` sau unknown commit result mà không có idempotent business key.
* Bật retry nhưng không test failover path.

## 8. Alternatives

Nếu operation rất đơn giản, implicit transaction của `SaveChanges` có thể đủ và execution strategy xử lý dễ hơn.

Với workflow nhiều hệ thống, Outbox/Saga thường phù hợp hơn việc cố biến mọi thứ thành một transaction có retry.

## 9. Trade-offs

### Advantages

Tăng resilience trước transient database failures và giữ retry boundary rõ.

### Costs / Risks

Replay làm correctness phức tạp; retry kéo dài latency và có thể nhân load khi database đang suy yếu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry chỉ dành cho lỗi có khả năng tạm thời.

### Middle

Biết dùng execution strategy với explicit transaction đúng pattern.

### Senior

Hiểu commit ambiguity, idempotency và interaction giữa retries với side effects.

### Technical Lead / Architect

Định nghĩa resilience boundary: cái gì retry được, cái gì phải deduplicate, cái gì cần Outbox thay vì transaction mở rộng.

## 11. Key takeaway

* Retry boundary phải bao quanh đúng transaction unit.
* Không đưa non-idempotent remote side effect vào transaction delegate có thể replay.
* Transient-fault resilience là correctness problem, không chỉ availability feature.

# 4. SQL Server covering index với `INCLUDE`: giảm key lookup nhưng không biến mọi query thành một index riêng

## 1. What is it?

Covering index là index chứa đủ columns để SQL Server trả kết quả query mà không phải quay lại clustered index/heap để lấy thêm dữ liệu.

Key columns quyết định ordering/searchability; `INCLUDE` columns được lưu ở leaf level để cover projection mà không tham gia key ordering.

## 2. Why does it exist?

Query có thể dùng nonclustered index để tìm rows nhanh nhưng sau đó phải thực hiện Key Lookup cho từng match để lấy columns còn thiếu.

Với vài rows, lookup rẻ. Với hàng chục nghìn rows, random lookups có thể trở thành phần lớn I/O cost.

## 3. How does it work?

Query:

```sql
SELECT Id, CustomerId, Status, TotalAmount
FROM Orders
WHERE CustomerId = @customerId
  AND Status = @status;
```

Index ban đầu:

```sql
CREATE INDEX IX_Orders_Customer_Status
ON Orders(CustomerId, Status);
```

Nếu `TotalAmount` không có trong index, SQL Server có thể lookup base table.

Covering version:

```sql
CREATE INDEX IX_Orders_Customer_Status
ON Orders(CustomerId, Status)
INCLUDE (TotalAmount);
```

Nếu clustered key `Id` đã implicit có trong nonclustered index, query có thể được cover hoàn toàn tùy schema.

## 4. Practical implementation

Không thêm `INCLUDE` chỉ từ code review. Trước tiên đo plan và I/O:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

So sánh logical reads, execution plan và row counts trước/sau index change.

Với EF Core, projection nên chỉ lấy fields cần thiết để index có cơ hội cover query:

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId && x.Status == status)
    .Select(x => new OrderSummary(
        x.Id,
        x.CustomerId,
        x.Status,
        x.TotalAmount))
    .ToListAsync(ct);
```

## 5. Real production scenario

Customer portal load 200 orders gần nhất. Index giúp seek theo `CustomerId`, nhưng execution plan cho thấy hàng nghìn Key Lookups vì query projection lấy thêm 6 columns.

Sau khi xác định hot query và thêm một số `INCLUDE` columns cần thiết, logical reads giảm mạnh và p95 giảm mà không thay business code.

## 6. Failure scenario & troubleshooting

**Symptom** → query dùng Index Seek nhưng vẫn chậm ở data volume lớn.

**Evidence** → execution plan có Key Lookup cost cao; actual rows lớn hơn dự kiến.

**Hypothesis** → lookup amplification.

**Diagnosis** → xem actual execution plan, logical reads và selected columns.

**Fix** → giảm projection hoặc thêm selective included columns nếu workload justify.

**Verification** → plan mới bỏ lookup hoặc giảm lookup đáng kể; reads/latency giảm.

## 7. Common mistakes

* Thấy Key Lookup là xóa ngay, dù lookup chỉ 3 rows.
* Include hàng chục wide columns, làm index phình lớn.
* Tạo index riêng cho từng query variation.
* Bỏ qua write amplification: insert/update phải maintain thêm index.

## 8. Alternatives

Có thể thay query projection, composite key order hoặc data model. Đôi khi query cần lookup nhưng vẫn đủ nhanh; không cần thay gì.

## 9. Trade-offs

### Advantages

Giảm base-table lookups và I/O cho hot read paths.

### Costs / Risks

Tăng storage, memory footprint, index maintenance, write latency và migration complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index có thể tìm row nhưng chưa chắc chứa đủ dữ liệu cần trả.

### Middle

Biết đọc Key Lookup trong execution plan và dùng `INCLUDE`.

### Senior

Cân bằng read gain với write/storage cost dựa trên measured workload.

### Technical Lead / Architect

Đặt indexing strategy theo critical access patterns, không chạy theo từng query riêng lẻ.

## 11. Key takeaway

* Covering index tối ưu projection cụ thể, không phải universal index.
* Key Lookup chỉ là vấn đề khi volume/cost thực sự đáng kể.
* Mỗi index thêm vào đều có write và operational cost.

# 5. Redis eviction + memory pressure: khi cache đầy thì dữ liệu nào biến mất và vì sao TTL không phải memory-management strategy hoàn chỉnh

## 1. What is it?

Redis giữ dữ liệu trong memory. Khi memory chạm `maxmemory`, eviction policy quyết định Redis sẽ từ chối writes hay loại bỏ keys để giải phóng memory.

TTL quyết định key hết hạn khi nào về mặt business/cache semantics. Eviction quyết định key nào bị xóa sớm vì memory pressure. Hai cơ chế khác nhau.

## 2. Why does it exist?

Memory hữu hạn. Cache workload có thể tăng vì traffic, key cardinality, payload size hoặc TTL quá dài.

Nếu Redis không có policy rõ, memory exhaustion có thể biến thành write failures hoặc process/host instability tùy deployment.

## 3. How does it work?

Các policy phổ biến gồm ý tưởng như:

```text
noeviction
allkeys-lru
allkeys-lfu
volatile-lru
volatile-ttl
```

Ví dụ `allkeys-lru` cho phép loại keys ít được dùng gần đây khi cần memory. `noeviction` giữ data nhưng write command cần thêm memory có thể fail.

Trong managed Redis, policy và memory metrics vẫn phải được quan sát; cloud không làm capacity planning biến mất.

## 4. Practical implementation

Application không nên giả định cache hit:

```csharp
var cached = await cache.GetStringAsync(key, ct);
if (cached is not null)
    return JsonSerializer.Deserialize<ProductDto>(cached)!;

var product = await repository.GetAsync(id, ct);

if (product is not null)
{
    await cache.SetStringAsync(
        key,
        JsonSerializer.Serialize(product),
        new DistributedCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
        },
        ct);
}

return product;
```

Cache miss phải luôn là supported behavior, kể cả miss do eviction chứ không phải TTL expiry.

## 5. Real production scenario

Product cache bình thường hit rate 92%. Một release thêm key theo `userId + productId` thay vì chỉ `productId`, làm cardinality tăng hàng trăm lần.

Redis memory tiến sát max. Evictions tăng mạnh, hit rate tụt, database traffic tăng, database chậm, request latency tăng. Team ban đầu tưởng “Redis vẫn up nên cache không có vấn đề”.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis availability bình thường nhưng DB load và API latency tăng.

**Evidence** → eviction count tăng, used memory sát limit, cache hit rate giảm.

**Hypothesis** → memory pressure tạo eviction churn.

**Diagnosis** → inspect key cardinality, payload size, TTL distribution và top memory consumers.

**Fix** → sửa key design, giảm payload/TTL, tăng capacity nếu justified, chọn eviction policy đúng semantics.

**Verification** → eviction rate về mức kỳ vọng, hit rate hồi phục, DB load giảm.

## 7. Common mistakes

* Nghĩ TTL ngắn tự động bảo đảm Redis không đầy.
* Cache per-user dữ liệu có cardinality rất cao mà không estimate memory.
* Chọn `allkeys-lru` cho dữ liệu thực ra không được phép mất.
* Biến Redis thành database nhưng vẫn cấu hình như disposable cache.

## 8. Alternatives

`IMemoryCache` phù hợp cho single-instance/local optimization nhưng không shared giữa instances.

Nếu data cần durability và không được phép evict, database hoặc durable key-value store đúng semantics thường phù hợp hơn Redis cache.

## 9. Trade-offs

### Advantages

Eviction giúp cache tiếp tục hoạt động dưới memory pressure thay vì fail toàn bộ writes trong một số workload.

### Costs / Risks

Eviction giảm hit rate, tạo load downstream và có thể gây cascading failure nếu database không có headroom.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss có thể xảy ra dù key chưa hết TTL.

### Middle

Biết quan sát memory, evictions, hit rate và thiết kế TTL/key hợp lý.

### Senior

Liên kết cache churn với database load, latency và cascading failure.

### Technical Lead / Architect

Xác định Redis là cache hay source-of-truth-like component, rồi chọn durability/capacity/failure semantics tương ứng.

## 11. Key takeaway

* TTL và eviction giải quyết hai vấn đề khác nhau.
* Redis “up” không có nghĩa cache đang khỏe.
* Cache capacity phải được thiết kế cùng downstream headroom.

# 6. Retry, Circuit Breaker và Bulkhead: ba resilience patterns giải quyết ba failure modes khác nhau

## 1. What is it?

Ba patterns thường bị gom chung dưới chữ “resilience”, nhưng chúng có mục tiêu khác nhau:

```text
Retry         → thử lại transient failure
CircuitBreaker→ ngừng gọi dependency đang fail liên tục
Bulkhead      → giới hạn blast radius / concurrency của dependency
```

Chúng có thể phối hợp, nhưng không pattern nào thay thế pattern còn lại.

## 2. Why does it exist?

Remote dependency sẽ có latency, timeout và partial failure. Nếu caller phản ứng sai, một lỗi nhỏ có thể trở thành retry storm hoặc resource exhaustion.

Resilience patterns tồn tại để caller có behavior có kiểm soát khi dependency không khỏe.

## 3. How does it work?

Một flow hợp lý:

```text
Request
  ↓
Bulkhead capacity check
  ↓
Circuit state check
  ↓
Attempt
  ├─ transient failure → bounded retry + backoff/jitter
  └─ repeated failures → circuit opens
```

Bulkhead giới hạn số concurrent calls. Circuit Breaker giảm calls khi failure rate cao. Retry xử lý lỗi ngắn hạn.

## 4. Practical implementation

Với modern .NET resilience APIs/Polly-style concepts, policy nên có budget rõ:

```csharp
var retryDelays = new[]
{
    TimeSpan.FromMilliseconds(100),
    TimeSpan.FromMilliseconds(300),
    TimeSpan.FromMilliseconds(800)
};
```

Quan trọng hơn syntax là rule:

* chỉ retry operation an toàn/idempotent
* total timeout phải bao toàn retry budget
* concurrency phải bounded
* log/metric từng final outcome thay vì spam từng attempt ở Error level

## 5. Real production scenario

Checkout API gọi Review Service không critical. Review Service timeout 5 giây. Caller retry 3 lần, mỗi retry 5 giây, không có total timeout và không có bulkhead.

Khi Review Service outage, checkout threads/connections bị giữ lâu, retry traffic nhân lên, p99 tăng hàng chục giây dù review data có thể bỏ qua.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency outage kéo theo caller latency và resource usage tăng mạnh.

**Evidence** → outbound attempts/request tăng gấp nhiều lần, timeout dồn dập, connection/concurrency saturated.

**Hypothesis** → unsafe retry amplification và thiếu isolation.

**Diagnosis** → inspect retry count, timeout layers, concurrency và circuit state telemetry.

**Fix** → bounded retries, jitter, total timeout, bulkhead, fallback nếu business cho phép.

**Verification** → chaos/fault test; dependency fail nhưng caller vẫn giữ SLO chấp nhận được hoặc degrade có kiểm soát.

## 7. Common mistakes

* Retry mọi 500 response.
* Retry POST tạo side effect không có idempotency.
* Layer nào cũng retry: SDK retry + HttpClient retry + application retry + gateway retry.
* Circuit Breaker mở nhưng fallback vẫn gọi chính dependency đó qua path khác.

## 8. Alternatives

Asynchronous messaging có thể loại synchronous dependency khỏi critical path nếu business không cần immediate response.

Cache/stale response có thể là fallback cho read-only data nếu freshness requirements cho phép.

## 9. Trade-offs

### Advantages

Giảm impact của transient failures và ngăn dependency failure lan toàn hệ thống.

### Costs / Risks

Policies thêm state, latency và operational tuning. Sai cấu hình có thể làm outage nặng hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt retry, circuit breaker và concurrency limit.

### Middle

Implement timeout/retry có giới hạn và idempotency-aware.

### Senior

Tính retry amplification, total latency budget và failure propagation.

### Technical Lead / Architect

Quyết định dependency nào critical, degradation semantics nào chấp nhận được và resilience ownership nằm ở layer nào.

## 11. Key takeaway

* Retry xử lý transient failure; Circuit Breaker xử lý sustained failure; Bulkhead xử lý resource isolation.
* Retry không có budget dễ trở thành traffic amplifier.
* Resilience phải dựa trên business criticality và idempotency.

# 7. Azure Functions scale-out + idempotent processing: serverless scale không loại bỏ duplicate execution

## 1. What is it?

Azure Functions có thể scale nhiều instances dựa trên trigger/load. Với queue/message-triggered workloads, cùng logical message có thể được delivery lại nếu processing thất bại, lock hết hạn hoặc acknowledgement không hoàn tất.

Serverless giảm server management; nó không tạo exactly-once business semantics.

## 2. Why does it exist?

At-least-once delivery ưu tiên không mất work. Nếu platform không chắc một invocation đã hoàn tất, retry là lựa chọn an toàn hơn về delivery nhưng đẩy duplicate-handling responsibility về application.

## 3. How does it work?

```text
Message M
  ↓
Function Instance A
  ↓ processing hoàn tất DB
  ↓
ack/complete thất bại
  ↓
Message M được deliver lại
  ↓
Function Instance B
```

Nếu handler tạo invoice mỗi lần chạy, duplicate invoice xuất hiện dù function code “không lỗi business”.

## 4. Practical implementation

Dùng Inbox/deduplication key:

```csharp
public async Task ProcessAsync(ServiceBusReceivedMessage message, CancellationToken ct)
{
    var messageId = message.MessageId;

    await using var tx = await db.Database.BeginTransactionAsync(ct);

    var processed = await db.ProcessedMessages
        .AnyAsync(x => x.MessageId == messageId, ct);

    if (processed)
        return;

    await HandleBusinessOperationAsync(message, ct);

    db.ProcessedMessages.Add(new ProcessedMessage
    {
        MessageId = messageId,
        ProcessedUtc = DateTime.UtcNow
    });

    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
```

Unique constraint trên `MessageId` bảo vệ race giữa concurrent deliveries.

## 5. Real production scenario

Function xử lý `EmployeeApproved` rồi gửi onboarding email và tạo account record. Sau database commit, invocation mất connection tới broker trước khi completion được ghi nhận.

Message quay lại. Nếu email gửi trực tiếp và không idempotent, user nhận hai email. Nếu account insert có unique business key, DB có thể block duplicate nhưng email side effect vẫn duplicate.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate notifications hoặc duplicate external actions dù queue chỉ có một logical event.

**Evidence** → cùng `MessageId` xuất hiện nhiều invocation logs.

**Hypothesis** → redelivery sau lock/ack failure.

**Diagnosis** → correlate Function invocation, Service Bus delivery count và message settlement telemetry.

**Fix** → idempotent consumer, unique business keys, Outbox cho outbound side effects.

**Verification** → intentionally redeliver cùng message và kiểm tra final business state chỉ áp dụng một lần.

## 7. Common mistakes

* Tin rằng Azure Functions trigger bảo đảm exactly-once.
* Dùng timestamp làm deduplication key.
* Mark processed trước business transaction.
* Gọi remote side effect trước khi durable idempotency state được ghi.

## 8. Alternatives

Worker Service/Container Apps cũng cần idempotency nếu broker là at-least-once. Hosting model không thay message semantics.

Nếu workflow thật sự synchronous và low-scale, direct API call có thể đơn giản hơn messaging.

## 9. Trade-offs

### Advantages

Functions giảm infrastructure management và scale thuận tiện cho event-driven workload.

### Costs / Risks

Cold start, retry semantics, concurrency, observability và duplicate processing vẫn cần application design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một message có thể trigger code nhiều hơn một lần.

### Middle

Biết dùng stable message ID + unique constraint để deduplicate.

### Senior

Thiết kế idempotency xuyên database và external side effects, hiểu lock duration/retry behavior.

### Technical Lead / Architect

Đánh giá Functions vs Worker/Container Apps dựa trên workload, latency, scaling, cost và operational ownership chứ không dựa vào “serverless = tự động đúng”.

## 11. Key takeaway

* Scale-out và at-least-once delivery làm duplicate execution trở thành normal case cần thiết kế.
* Unique business/idempotency keys quan trọng hơn hosting model.
* External side effects thường cần Outbox hoặc provider-level idempotency.

# 8. Backward-compatible CI/CD với feature flags: deploy code trước, activate behavior sau mà không trộn deployment với release

## 1. What is it?

Deployment là đưa code/artifact mới vào environment. Release là cho user thực sự sử dụng behavior mới.

Feature flag tách hai việc này:

```text
Deploy code with flag OFF
        ↓
validate production health
        ↓
turn flag ON for cohort
        ↓
expand rollout
```

Nó hữu ích nhất khi code mới vẫn backward-compatible với data/contracts hiện tại.

## 2. Why does it exist?

Nếu deployment và release luôn cùng thời điểm, rollback behavior thường đồng nghĩa rollback binary. Điều đó chậm và nguy hiểm hơn khi database migration hoặc multi-service rollout đang diễn ra.

Feature flags cho phép kiểm soát exposure mà không redeploy.

## 3. How does it work?

Pipeline vẫn cần:

```text
commit
→ build
→ tests
→ artifact
→ deploy
→ health validation
→ flag rollout
→ monitor
```

Flag không thay CI/CD. Nó thêm runtime decision layer.

Database evolution nên theo Expand-Contract khi old/new application versions cùng tồn tại.

## 4. Practical implementation

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
{
    return await newCheckout.ExecuteAsync(request, ct);
}

return await legacyCheckout.ExecuteAsync(request, ct);
```

Flag evaluation không nên nằm sâu ở hàng chục domain methods. Boundary thường tốt hơn ở application orchestration/entry point để tránh hai behavior path đan xen khắp codebase.

## 5. Real production scenario

Team deploy checkout engine mới lúc 10:00 nhưng giữ flag OFF. Health metrics ổn. Sau đó bật cho internal users, rồi 5%, 25%, 100% traffic.

Ở 25%, p95 payment latency tăng. Team tắt flag trong vài giây mà không rollback artifact, giữ investigation evidence trong production deployment hiện tại.

## 6. Failure scenario & troubleshooting

**Symptom** → behavior khác nhau giữa users hoặc instances ngoài dự kiến.

**Evidence** → flag evaluation logs/config inconsistent, stale cache hoặc targeting rule sai.

**Hypothesis** → feature-management control plane/config propagation issue.

**Diagnosis** → inspect evaluated flag state theo request/cohort và configuration version.

**Fix** → simplify rules, ensure deterministic targeting, restore known-safe flag state.

**Verification** → synthetic checks cho cả OFF/ON paths và cohort distribution.

## 7. Common mistakes

* Dùng flag làm permanent configuration rồi không cleanup.
* Flag ở quá nhiều low-level code paths tạo combinatorial states khó test.
* Bật feature mới nhưng schema migration không backward-compatible.
* Không test OFF path sau nhiều tuần vì mọi developer chỉ dùng ON locally.

## 8. Alternatives

Blue-Green/Canary deployment kiểm soát traffic theo deployment version thay vì runtime feature. Hai kỹ thuật có thể kết hợp nhưng solve boundary khác nhau.

Với thay đổi nhỏ, rollback deployment bình thường có thể đơn giản hơn feature flag.

## 9. Trade-offs

### Advantages

Giảm blast radius, rollout theo cohort và rollback behavior nhanh.

### Costs / Risks

Tăng state space, configuration dependency, testing burden và technical debt nếu flags không được retire.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy và release không nhất thiết là cùng một hành động.

### Middle

Implement flag ở boundary rõ và test cả hai paths.

### Senior

Thiết kế rollout metrics, backward compatibility và cleanup lifecycle.

### Technical Lead / Architect

Quyết định change nào đáng feature flag, change nào chỉ cần normal deployment, và governance để tránh flag debt.

## 11. Key takeaway

* Feature flag tách code deployment khỏi user exposure.
* Flag không cứu được schema/API breaking change.
* Mỗi flag cần owner, rollout criteria và removal date.

# 9. Production profiling với `dotnet-counters` và allocation rate: điều tra memory/GC pressure bằng evidence thay vì đoán memory leak

## 1. What is it?

`dotnet-counters` cho phép quan sát runtime counters của .NET process như GC heap size, allocation rate, GC collections, exception rate, ThreadPool behavior và CPU usage.

Nó là tool triage: giúp xác định “hệ thống đang làm gì” trước khi lấy dump/profile sâu hơn.

## 2. Why does it exist?

Memory tăng không đồng nghĩa memory leak. Có thể là:

* allocation rate tăng nhưng GC vẫn thu hồi
* cache giữ dữ liệu theo design
* LOH growth
* native/unmanaged memory
* traffic tăng
* object retention thật sự

Nếu nhảy thẳng vào code và đoán leak, team dễ sửa sai chỗ.

## 3. How does it work?

Runtime expose counters. Tool đọc counters theo thời gian:

```bash
dotnet-counters monitor --process-id <PID> System.Runtime
```

Các signals nên nhìn cùng nhau:

```text
Allocation Rate
GC Heap Size
Gen0/Gen1/Gen2 collections
Time in GC
Working Set
CPU
ThreadPool Queue Length
```

Một signal đơn lẻ hiếm khi đủ kết luận.

## 4. Practical implementation

Ví dụ triage:

```bash
dotnet-counters ps

dotnet-counters monitor \
  --process-id 1234 \
  System.Runtime
```

Nếu allocation rate rất cao nhưng heap size dao động ổn định, đây có thể là allocation churn chứ không phải retained-memory leak.

Nếu heap size và working set cùng tăng lâu dài qua nhiều full GC, cần chuyển sang heap dump/profile để tìm retention roots.

## 5. Real production scenario

API memory tăng từ 700 MB lên 1.3 GB sau release. Team nghi static dictionary leak.

Counters cho thấy allocation rate tăng gấp 6 lần và Gen0/Gen1 collections tăng, nhưng Gen2 heap tương đối ổn định. Root cause là JSON serialization path tạo large temporary buffers do response shape mới, không phải static retention.

## 6. Failure scenario & troubleshooting

**Symptom** → memory/CPU tăng sau deployment.

**Evidence** → allocation rate cao, time in GC tăng, p95 latency tăng cùng request volume.

**Hypothesis** → allocation churn gây GC pressure.

**Diagnosis** → counters trước, sau đó allocation profiler/dump để tìm types và call stacks.

**Fix** → giảm allocations ở measured hot path, streaming/buffering hợp lý, reuse buffer khi justified.

**Verification** → cùng load profile: allocation rate và GC time giảm, latency cải thiện.

## 7. Common mistakes

* Thấy working set cao là kết luận leak.
* Force `GC.Collect()` như production fix.
* Tối ưu mọi allocation nhỏ mà chưa profile.
* Chụp một metric snapshot thay vì xem trend theo traffic/deployment timeline.

## 8. Alternatives

Application Insights/Azure Monitor cung cấp historical production metrics. `dotnet-trace`, `dotnet-dump` và profiler cho phân tích sâu hơn khi counters đã localize vấn đề.

## 9. Trade-offs

### Advantages

Low-friction triage, runtime-specific signals và rất hữu ích để chọn bước điều tra tiếp theo.

### Costs / Risks

Counters không chỉ ra object nào giữ memory; cần tool sâu hơn cho root cause. Quan sát sai signal có thể dẫn đến kết luận sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu heap size, allocation rate và working set không phải cùng một khái niệm.

### Middle

Biết dùng `dotnet-counters` để triage process.

### Senior

Xây hypothesis từ nhiều counters, correlate với traffic/deploy và chọn profiler/dump tiếp theo.

### Technical Lead / Architect

Thiết lập production observability đủ để phân biệt capacity issue, GC pressure, leak và workload shift trước khi incident trở nên nghiêm trọng.

## 11. Key takeaway

* Memory tăng không tự động nghĩa memory leak.
* Allocation rate + GC behavior + heap trend phải được đọc cùng nhau.
* Counters dùng để localize; profiler/dump dùng để chứng minh root cause sâu hơn.

# 10. AI coding agent repository changes: phân biệt “code nhìn hợp lý” với “change đã được chứng minh đúng” bằng deterministic verification gates

## 1. What is it?

AI coding agent có thể đọc repository, sửa nhiều files, chạy tests và đề xuất PR. Nhưng model output vẫn probabilistic: một patch có thể compile-looking, stylistically đúng và vẫn vi phạm hidden invariant hoặc dùng API không tồn tại.

Mental model phù hợp:

```text
LLM proposes change
      ↓
deterministic tools verify
      ↓
human/engineering review judges intent & trade-offs
```

AI nên tăng tốc implementation, không trở thành nguồn sự thật cho correctness.

## 2. Why does it exist?

Repository-level tasks có quá nhiều context: build configuration, package versions, conventions, tests, schema, generated code và deployment assumptions.

LLM có thể suy luận tốt nhưng không có guarantee. Deterministic gates biến “có vẻ đúng” thành evidence có thể kiểm tra.

## 3. How does it work?

Verification pipeline:

```text
Repository grounding
  ↓
Patch generation
  ↓
format/lint
  ↓
build
  ↓
unit tests
  ↓
integration/contract tests
  ↓
security/static analysis
  ↓
diff review
```

Mỗi gate bắt một class failure khác nhau. Build không chứng minh business correctness; unit test không chứng minh migration an toàn; static analyzer không hiểu đầy đủ requirement.

## 4. Practical implementation

Một agent workflow cho .NET repository nên tối thiểu chạy:

```bash
dotnet restore
dotnet build --no-restore
dotnet test --no-build
```

Nếu repository có formatter/analyzer:

```bash
dotnet format --verify-no-changes
```

Nếu thay API contract, chạy integration/contract tests. Nếu thay migration, kiểm tra generated SQL/deployment compatibility.

Agent cần báo rõ test nào đã chạy và test nào không thể chạy, thay vì nói chung chung “implementation complete”.

## 5. Real production scenario

Agent refactor `DateTime` handling và đổi từ local time sang UTC. Build pass, unit tests pass. Nhưng một downstream report phụ thuộc legacy local-time semantics và không có contract test.

Patch technically clean nhưng business behavior sai. Human review + regression test trên representative data mới phát hiện.

## 6. Failure scenario & troubleshooting

**Symptom** → AI-generated PR pass compile nhưng fail CI hoặc gây regression sau merge.

**Evidence** → package/API mismatch, missing integration tests, changed contract hoặc hidden side effect trong diff.

**Hypothesis** → generation được chấp nhận mà không có đủ verification layers.

**Diagnosis** → map failure về gate đã thiếu: build, test, contract, migration, security hay requirement review.

**Fix** → thêm deterministic validation và repository-specific instructions; không chỉ prompt agent “hãy cẩn thận hơn”.

**Verification** → reproduce original regression bằng test tự động rồi rerun full relevant pipeline.

## 7. Common mistakes

* Tin generated test chỉ vì test pass; model có thể viết test phù hợp implementation sai.
* Cho agent update package version mà không đọc lockfile/project constraints.
* Chỉ review final code, không review deleted behavior và migration impact.
* Để agent tự quyết security/authorization business rules không có deterministic policy checks.

## 8. Alternatives

AI có thể chỉ dùng ở mode advisory: phân tích/draft patch để developer áp dụng thủ công.

Với repetitive mechanical migration, deterministic codemod/source generator đôi khi an toàn và reproducible hơn LLM.

## 9. Trade-offs

### Advantages

Agent giảm thời gian đọc repository, boilerplate, refactor và test scaffolding.

### Costs / Risks

Có thể tạo plausible-but-wrong changes nhanh hơn con người kịp review; verification compute và review discipline trở nên quan trọng hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu AI suggestion cần compile/test và không nên copy blindly.

### Middle

Biết yêu cầu agent ground vào repository và chạy relevant tests.

### Senior

Đánh giá semantic diff, missing tests, migration/security risks và failure classes mà CI chưa cover.

### Technical Lead / Architect

Thiết kế agent permissions, required gates, protected branches, approval boundaries và auditability cho AI-assisted workflow.

## 11. Key takeaway

* LLM tạo hypothesis/patch; deterministic tools tạo evidence.
* “Build passed” chỉ bảo vệ một phần correctness.
* Agent càng tự động, verification gates và permission boundaries càng phải mạnh.
