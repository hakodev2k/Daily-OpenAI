# 1. C# `ArrayPool<T>` và buffer ownership: tái sử dụng memory mà không tạo data leak hoặc giữ buffer quá lâu

## 1. What is it?

`ArrayPool<T>` là pool dùng để **rent** và **return** arrays thay vì tạo array mới liên tục.

Mental model:

```text
new byte[64KB]
-> allocation mới
-> GC phải quản lý lifetime

ArrayPool<byte>.Shared.Rent(64KB)
-> lấy buffer đã có
-> dùng
-> Return(buffer)
-> buffer có thể được tái sử dụng
```

Pool không đảm bảo array trả về có đúng length yêu cầu; thường length thực tế >= requested length.

## 2. Why does it exist?

Hot path xử lý file, serialization, network frames hoặc compression có thể liên tục tạo temporary arrays lớn. Allocation rate cao làm GC chạy thường xuyên; nếu buffer đủ lớn còn có thể tác động tới LOH.

Pooling đổi allocation pressure lấy **lifetime/ownership complexity**.

## 3. How does it work?

Pool giữ các buckets theo kích thước. `Rent` trả một array có thể đã từng chứa dữ liệu của operation khác. `Return` đưa array lại pool để request tương lai tái sử dụng.

Vì vậy buffer ownership phải rõ:

```text
Rent
  -> caller owns buffer
  -> no one may retain it after Return
Return
  -> caller loses ownership
```

Sau `Return`, bất kỳ code nào vẫn giữ reference đều có thể đọc dữ liệu đã bị consumer khác ghi đè.

## 4. Practical implementation

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(64 * 1024);

try
{
    var bytesRead = await stream.ReadAsync(
        buffer.AsMemory(0, 64 * 1024), ct);

    await ProcessAsync(buffer.AsMemory(0, bytesRead), ct);
}
finally
{
    pool.Return(buffer, clearArray: true);
}
```

`clearArray: true` có thêm CPU cost nhưng phù hợp nếu buffer chứa secret, token hoặc dữ liệu nhạy cảm.

## 5. Real production scenario

Một file-processing API đọc hàng nghìn ảnh mỗi phút. Mỗi request trước đây tạo nhiều `byte[]` 128–512 KB. Allocation rate và Gen2/LOH pressure tăng đáng kể.

Chuyển buffer tạm thời sang `ArrayPool<byte>` giảm allocation, nhưng chỉ ở layer parser/streaming có ownership rõ ràng.

## 6. Failure scenario & troubleshooting

**Symptom** → payload đôi lúc bị corrupt hoặc request A thấy bytes từ request B.

**Evidence** → code return buffer trước khi async consumer hoàn thành; buffer được lưu vào field/cache.

**Hypothesis** → use-after-return.

**Diagnosis** → trace lifetime của buffer từ `Rent` tới `Return`, đặc biệt qua async boundaries.

**Fix** → chỉ return sau khi consumer cuối cùng hoàn thành; copy dữ liệu nếu ownership phải chuyển sang lifetime dài hơn.

**Verification** → concurrency/load test với checksum và profiler xác nhận allocation giảm mà data corruption không còn.

## 7. Common mistakes

- Tưởng `Rent(1000)` luôn trả array length = 1000.
- Return buffer trong khi async work vẫn đang dùng.
- Không clear buffer chứa secret.
- Giữ pooled array trong singleton/cache.
- Dùng pooling cho small allocations không tạo áp lực đáng kể.

## 8. Alternatives

- `new T[]`: đơn giản và thường đúng mặc định.
- `MemoryPool<T>`: hữu ích khi cần owner object/lifetime abstraction rõ hơn.
- `Span<T>`: giảm copy nhưng không tự giải quyết buffer allocation source.

## 9. Trade-offs

### Advantages

- Giảm allocation và GC pressure ở hot path.
- Tốt cho buffer lớn/tần suất cao.

### Costs / Risks

- Ownership complexity tăng.
- Data leakage/corruption nếu return sai thời điểm.
- Clear buffer có CPU cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu pool là tái sử dụng array, không phải “memory miễn phí”.

### Middle

Biết `try/finally`, slice đúng length và không dùng buffer sau `Return`.

### Senior

Đo allocation trước khi áp dụng, xác định security/lifetime risk và benchmark dưới concurrency.

### Technical Lead / Architect

Chỉ cho phép pooling ở performance-critical boundaries có ownership conventions rõ thay vì biến nó thành coding style toàn hệ thống.

## 11. Key takeaway

- `ArrayPool<T>` giảm allocation bằng cách tăng trách nhiệm ownership.
- Sau `Return`, buffer không còn thuộc caller.
- Chỉ pool khi profiler chứng minh allocation đáng tối ưu.

# 2. ASP.NET Core Endpoint Filters và validation boundary: đặt cross-cutting logic gần endpoint nhưng không biến API layer thành nơi chứa business rules

## 1. What is it?

Endpoint Filter là cơ chế cho Minimal APIs cho phép chạy logic trước/sau endpoint handler tương tự một lightweight invocation pipeline.

```text
Request
 -> middleware
 -> endpoint filter 1
 -> endpoint filter 2
 -> handler
 -> response
```

Filter phù hợp cho concern gắn với một nhóm endpoints như request validation, logging metadata hoặc small policy checks.

## 2. Why does it exist?

Middleware thường quá global; business service thì quá sâu. Một số logic cần nằm gần endpoint invocation nhưng không nên copy vào từng handler.

Ví dụ: kiểm tra command contract hợp lệ trước khi gọi application service.

## 3. How does it work?

Filter nhận `EndpointFilterInvocationContext` và delegate tới filter tiếp theo:

```csharp
public async ValueTask<object?> InvokeAsync(
    EndpointFilterInvocationContext context,
    EndpointFilterDelegate next)
{
    // before
    var result = await next(context);
    // after
    return result;
}
```

Điểm quan trọng: endpoint validation không thay domain invariant.

```text
API validation
-> shape/range/required fields

Domain validation
-> business state/invariant
```

## 4. Practical implementation

```csharp
public sealed class CreateOrderValidationFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var request = context.GetArgument<CreateOrderRequest>(0);

        if (request.Items.Count == 0)
        {
            return Results.ValidationProblem(new Dictionary<string, string[]>
            {
                ["items"] = ["At least one item is required."]
            });
        }

        return await next(context);
    }
}
```

Domain vẫn phải tự bảo vệ invariant như “order đã Cancelled không thể Approve”.

## 5. Real production scenario

Một API có 30 Minimal API endpoints. Mỗi handler tự validate basic request fields, dẫn tới response format không nhất quán.

Filter chuẩn hóa contract validation, trong khi authorization vẫn dùng policy và business invariant vẫn thuộc application/domain.

## 6. Failure scenario & troubleshooting

**Symptom** → request hợp lệ ở HTTP layer nhưng domain state sai vẫn được chấp nhận.

**Evidence** → critical rule chỉ nằm trong filter; background job gọi application service trực tiếp bỏ qua filter.

**Hypothesis** → business rule bị đặt sai boundary.

**Diagnosis** → kiểm tra rule có phải đúng cho mọi entry point hay chỉ cho HTTP contract.

**Fix** → giữ transport validation ở filter; đưa invariant vào domain/application layer.

**Verification** → unit/integration tests qua cả HTTP và non-HTTP entry point.

## 7. Common mistakes

- Nhét database query/business workflow vào filter.
- Dùng filter thay middleware cho global concern.
- Duplicate authorization logic thay vì policy-based authorization.
- Trả error contract không thống nhất.
- Không hiểu execution order khi nhiều filters compose.

## 8. Alternatives

- Middleware: global/protocol-level concern.
- MVC filters: MVC action lifecycle.
- FluentValidation/manual validation trong application boundary.
- Domain invariant trong aggregate/domain service.

## 9. Trade-offs

### Advantages

- Reuse logic gần endpoint.
- Minimal API handler gọn hơn.
- Dễ scope theo endpoint/group.

### Costs / Risks

- Dễ biến thành hidden application layer.
- Filter chain dài làm flow khó theo dõi.
- Rule đặt sai boundary tạo inconsistency giữa entry points.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu filter wrap endpoint invocation.

### Middle

Biết implement validation/logging filter và test execution order.

### Senior

Phân biệt transport concern, application concern và domain invariant.

### Technical Lead / Architect

Đặt convention rõ: concern nào dùng middleware, endpoint filter, application behavior hay domain rule.

## 11. Key takeaway

- Endpoint Filter tốt cho concern scoped quanh endpoint invocation.
- Validation contract không thay business invariant.
- Boundary đúng quan trọng hơn giảm vài dòng handler code.

# 3. EF Core raw SQL, parameterization và composability: dùng SQL thủ công đúng chỗ mà không mở cửa cho SQL injection hoặc phá query pipeline

## 1. What is it?

EF Core cho phép chạy raw SQL khi LINQ khó biểu diễn hoặc cần tận dụng database-specific feature.

Raw SQL không có nghĩa bỏ toàn bộ EF Core. Nó có thể vẫn materialize entities/keyless types và đôi khi compose thêm LINQ phía trên.

## 2. Why does it exist?

LINQ rất mạnh nhưng không bao phủ mọi SQL feature tối ưu: complex CTE, specialized hints, provider-specific functions hoặc query đã được DBA tối ưu sẵn.

Nếu ép mọi thứ qua abstraction chỉ để “không viết SQL”, code có thể khó hiểu và query kém hơn.

## 3. How does it work?

Điểm security quan trọng nhất là parameterization.

An toàn:

```csharp
var rows = await db.Orders
    .FromSql($"SELECT * FROM Orders WHERE CustomerId = {customerId}")
    .ToListAsync(ct);
```

EF Core biến interpolated value thành parameter.

Nguy hiểm khi tự concatenate:

```csharp
var sql = "SELECT * FROM Orders WHERE Name = '" + input + "'";
```

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .FromSql($"""
        SELECT *
        FROM Orders
        WHERE CustomerId = {customerId}
          AND CreatedAt >= {fromUtc}
        """)
    .AsNoTracking()
    .ToListAsync(ct);
```

Nếu dùng `FromSqlRaw`, parameter phải được truyền rõ bằng `DbParameter`/arguments thay vì concatenate untrusted input.

## 5. Real production scenario

Reporting endpoint cần recursive CTE và windowing mà LINQ translation trở nên khó đọc. Team dùng raw SQL, giữ mapping qua keyless entity và vẫn dùng cùng connection/observability stack.

## 6. Failure scenario & troubleshooting

**Symptom** → security scan phát hiện SQL injection path hoặc query chỉ fail khi compose thêm LINQ.

**Evidence** → dynamic column/order string được concatenate; SQL có trailing semicolon/stored-procedure shape không composable.

**Hypothesis** → raw SQL boundary đang nhận structural input không được whitelist hoặc query shape không hỗ trợ composition.

**Diagnosis** → inspect generated command text/parameters và provider rules.

**Fix** → parameterize values, whitelist identifiers, tách query nếu SQL không composable.

**Verification** → injection tests + integration tests trên provider thật.

## 7. Common mistakes

- Tin rằng string interpolation luôn nguy hiểm dù dùng API parameterized đúng.
- Dùng `FromSqlRaw` với direct user input.
- Dynamic `ORDER BY` từ request mà không whitelist.
- Raw SQL trả entity thiếu required columns.
- Bỏ qua query plan chỉ vì SQL được viết thủ công.

## 8. Alternatives

- LINQ: default tốt vì composable/type-safe.
- Stored procedure: phù hợp một số enterprise governance/performance boundaries.
- Dapper: lightweight mapping khi query-centric workload chiếm ưu thế.

## 9. Trade-offs

### Advantages

- Truy cập đầy đủ database capability.
- Có thể rõ hơn LINQ cho query đặc thù.

### Costs / Risks

- Portability giảm.
- SQL injection risk nếu parameterization sai.
- Mapping/schema coupling tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu value phải parameterized, không concatenate SQL.

### Middle

Biết chọn LINQ vs raw SQL và integration-test query thật.

### Senior

Đọc plan, kiểm soát composability, mapping và structural input.

### Technical Lead / Architect

Cho phép raw SQL như một explicit escape hatch với review/security conventions, không cấm tuyệt đối cũng không thả tự do.

## 11. Key takeaway

- Raw SQL là công cụ hợp lệ khi abstraction không còn phù hợp.
- Parameterization là security boundary.
- Query thủ công vẫn phải được đo và review như mọi production query khác.

# 4. SQL Server blocking chain và lock escalation: điều tra query “treo” bằng wait evidence thay vì chỉ nhìn CPU

## 1. What is it?

Blocking xảy ra khi session A giữ lock mà session B cần. Blocking chain là chuỗi nhiều sessions chờ nhau theo một hướng.

```text
Session 51 holds X lock
   |
Session 72 waits
   |
Session 88 waits behind 72
```

Lock escalation là khi SQL Server có thể chuyển nhiều fine-grained locks thành table-level lock để giảm lock-management overhead.

## 2. Why does it exist?

Lock bảo vệ transactional consistency. Vấn đề không phải “lock tồn tại”, mà là lock sống quá lâu hoặc access pattern khiến nhiều work tranh cùng resource.

CPU có thể chỉ 20% nhưng API vẫn timeout vì sessions đang chờ lock.

## 3. How does it work?

Một transaction update row rồi chưa commit:

```sql
BEGIN TRAN;
UPDATE Orders SET Status = 'Processing' WHERE Id = 42;
-- transaction still open
```

Session khác cần incompatible lock trên row/key đó sẽ chờ.

Large modification có thể giữ rất nhiều locks; engine có thể xem xét escalation tùy điều kiện/resource pressure.

## 4. Practical implementation

Khi incident xảy ra, thu evidence:

```sql
SELECT
    r.session_id,
    r.blocking_session_id,
    r.wait_type,
    r.wait_time,
    r.command
FROM sys.dm_exec_requests r
WHERE r.blocking_session_id <> 0;
```

Kết hợp query text, transaction age và lock DMV/monitoring tool để tìm **root blocker**, không chỉ session bị timeout cuối chuỗi.

## 5. Real production scenario

Một background batch update 100k rows trong một transaction vào giờ cao điểm. API update từng order bắt đầu timeout. CPU và memory bình thường.

Root cause là transaction batch giữ locks lâu, tạo blocking chain lớn.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 DB latency tăng mạnh; CPU thấp; request timeout hàng loạt.

**Evidence** → `LCK_M_*` waits, blocking_session_id, transaction age cao.

**Hypothesis** → long-running transaction hoặc batch quá lớn.

**Diagnosis** → tìm root blocker và business operation tạo nó.

**Fix** → transaction ngắn hơn, batch nhỏ, index đúng để giảm rows locked, thay workflow nếu cần.

**Verification** → lock waits/blocking duration giảm trong load window tương tự.

## 7. Common mistakes

- Kill random blocked session thay vì root blocker.
- Thêm `NOLOCK` như universal fix.
- Giữ transaction trong lúc gọi external API.
- Update batch quá lớn trong peak traffic.
- Chỉ xem slow query duration mà không xem wait type.

## 8. Alternatives

- Snapshot-based isolation cho một số read blocking scenarios.
- Optimistic concurrency ở application layer.
- Queue/batch scheduling ngoài peak.

Không alternative nào loại bỏ nhu cầu transaction design đúng.

## 9. Trade-offs

### Advantages

- Locks cung cấp consistency mạnh và semantics rõ.

### Costs / Risks

- Long transactions tăng contention.
- Snapshot isolation chuyển một phần cost sang version store/tempdb.
- Batching nhỏ giảm lock duration nhưng tăng round trips.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu query có thể chậm vì chờ, không phải vì tính toán.

### Middle

Biết đọc blocking session/wait type và tìm transaction chưa commit.

### Senior

Phân tích lock footprint, access path và transaction design.

### Technical Lead / Architect

Thiết kế workload/batch/isolation strategy để contention không trở thành systemic outage.

## 11. Key takeaway

- Blocking là wait problem; CPU thấp không loại trừ database bottleneck.
- Tìm root blocker, không chỉ victim.
- Transaction duration và number of touched rows là yếu tố thiết kế quan trọng.

# 5. Redis eviction, memory pressure và hot keys: cache có thể làm hệ thống chậm hơn khi memory policy và traffic distribution bị hiểu sai

## 1. What is it?

Redis giữ data trong memory. Khi đạt `maxmemory`, eviction policy quyết định key nào có thể bị loại để nhường chỗ.

Hot key là một key nhận lượng traffic bất thường lớn so với các keys khác.

## 2. Why does it exist?

Memory là hữu hạn. Cache không thể tăng vô hạn. Nếu không có capacity/eviction strategy, Redis có thể reject writes hoặc gây churn liên tục.

Hot key lại tạo một bottleneck khác: hệ thống tưởng traffic đã phân tán nhưng phần lớn operations dồn vào một key/node.

## 3. How does it work?

Policy có thể dựa LRU/LFU/TTL tùy cấu hình.

```text
memory full
  -> choose eviction candidate
  -> remove key
  -> admit new data
```

Nếu working set lớn hơn capacity quá nhiều, cache liên tục evict rồi miss rồi refill: hit ratio giảm và origin load tăng.

## 4. Practical implementation

Theo dõi ít nhất:

- memory used / maxmemory;
- evicted keys;
- hit/miss ratio;
- ops/sec theo command/key pattern;
- latency;
- origin fallback load.

Cache key nên có TTL phù hợp và tránh một giant object duy nhất cho dataset rất lớn.

## 5. Real production scenario

Product API cache mỗi product riêng nhưng homepage dùng một key `homepage:all-products` rất lớn, được đọc ở gần như mọi request. Key này trở thành hot key, serialization payload lớn và network throughput tăng mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis latency tăng, hit ratio giảm, database CPU tăng cùng lúc.

**Evidence** → evictions tăng nhanh, memory luôn sát limit, miss rate tăng.

**Hypothesis** → cache churn do working set vượt capacity hoặc TTL/key strategy sai.

**Diagnosis** → phân tích key sizes, eviction rate, top access patterns và origin fallback.

**Fix** → điều chỉnh dataset, TTL, capacity, partition hot content hoặc bỏ cache ít giá trị.

**Verification** → hit ratio ổn định, eviction phù hợp và origin load giảm.

## 7. Common mistakes

- Cache mọi thứ vì “Redis nhanh”.
- Không đặt TTL cho cache data.
- Giant key chứa collection khổng lồ.
- Không monitor eviction.
- Redis fail thì mọi request đồng loạt đánh DB.

## 8. Alternatives

- `IMemoryCache` cho instance-local low-value data.
- CDN/output cache cho public HTTP representation.
- Không cache nếu query đã đủ nhanh và invalidation cost cao.

## 9. Trade-offs

### Advantages

- Latency thấp, giảm origin load.
- Shared cache giữa instances.

### Costs / Risks

- Memory cost và eviction complexity.
- Hot key/churn có thể tạo hidden bottleneck.
- Fallback path phải chịu được cache outage.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache hit/miss và TTL.

### Middle

Theo dõi hit ratio, memory và eviction.

### Senior

Thiết kế key distribution, fallback và capacity theo workload.

### Technical Lead / Architect

Quyết định data nào xứng đáng ở Redis và đảm bảo Redis không trở thành single hidden critical dependency.

## 11. Key takeaway

- Redis memory phải có capacity/eviction strategy.
- Hit ratio cao không đủ nếu hot key vẫn bottleneck.
- Cache failure mode phải được thiết kế cùng cache happy path.

# 6. Bulkhead Pattern: cô lập failure của dependency để một downstream chậm không chiếm hết concurrency budget của application

## 1. What is it?

Bulkhead Pattern chia concurrency/resources thành các ngăn độc lập để failure ở một dependency không tiêu thụ toàn bộ threads/connections/work slots.

Tên gọi đến từ khoang kín trên tàu: một khoang ngập nước không làm toàn tàu chìm.

## 2. Why does it exist?

Giả sử API gọi review service chậm. Nếu 5,000 requests đều được phép chờ review service đồng thời, sockets, memory và downstream connections có thể bị chiếm hết; endpoints không liên quan cũng bị ảnh hưởng.

Timeout giới hạn thời gian. Bulkhead giới hạn **số work đồng thời**.

## 3. How does it work?

```text
Main API concurrency
   |
   +--> Payment bulkhead: 50
   +--> Reviews bulkhead: 20
   +--> Search bulkhead: 100
```

Khi Reviews đạt 20 active calls, request mới fail/queue theo policy thay vì chiếm tài nguyên vô hạn.

## 4. Practical implementation

Một implementation đơn giản có thể dùng `SemaphoreSlim` quanh dependency adapter:

```csharp
public sealed class ReviewClient
{
    private readonly SemaphoreSlim _gate = new(20);

    public async Task<ReviewSummary?> GetAsync(string productId, CancellationToken ct)
    {
        if (!await _gate.WaitAsync(TimeSpan.FromMilliseconds(50), ct))
            return null;

        try
        {
            return await CallReviewsAsync(productId, ct);
        }
        finally
        {
            _gate.Release();
        }
    }
}
```

Production có thể dùng resilience library/policy với metrics rõ ràng.

## 5. Real production scenario

E-commerce product page gọi CMS, pricing, reviews và recommendations. Reviews provider degraded. Bulkhead giới hạn review calls; page vẫn trả product/price với fallback “reviews unavailable”.

## 6. Failure scenario & troubleshooting

**Symptom** → một dependency latency spike làm toàn API p99 tăng.

**Evidence** → concurrent calls tới dependency tăng, connection pool/thread queue pressure xuất hiện.

**Hypothesis** → không có concurrency isolation.

**Diagnosis** → dependency spans + active request metrics + pool metrics.

**Fix** → bounded concurrency, timeout, fallback và circuit breaker phù hợp.

**Verification** → chaos/load test dependency chậm nhưng unrelated endpoints vẫn giữ SLO.

## 7. Common mistakes

- Chỉ thêm retry, làm dependency càng quá tải.
- Bulkhead limit đặt theo cảm giác, không dựa capacity.
- Queue vô hạn phía trước bulkhead.
- Không expose rejection/saturation metrics.
- Fallback vẫn gọi dependency khác tốn kém tương đương.

## 8. Alternatives

- Circuit Breaker: ngừng gọi khi failure threshold vượt ngưỡng.
- Timeout: giới hạn thời gian một call.
- Queue: chuyển work khỏi synchronous request path.

Thường cần composition, nhưng mỗi pattern giải quyết pressure khác nhau.

## 9. Trade-offs

### Advantages

- Giới hạn blast radius.
- Bảo vệ resource budget.

### Costs / Risks

- Có thể reject request sớm hơn.
- Cần tuning limit và fallback semantics.
- Thêm operational metrics/policy complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một dependency chậm có thể kéo cả process xuống.

### Middle

Implement bounded concurrency và cancellation đúng.

### Senior

Tuning limit dựa downstream capacity và load, kết hợp timeout/circuit breaker.

### Technical Lead / Architect

Phân loại dependency nào cần isolation và business feature nào có thể degrade gracefully.

## 11. Key takeaway

- Timeout giới hạn thời gian; bulkhead giới hạn concurrency.
- Isolation giảm blast radius của partial failure.
- Retry không có concurrency budget có thể biến degradation thành outage.

# 7. Azure Monitor alert design: từ metric/log signal đến actionable alert thay vì biến production thành một hệ thống báo động giả

## 1. What is it?

Alert là rule biến telemetry thành hành động khi signal vượt điều kiện có ý nghĩa.

Mental model:

```text
Telemetry
 -> metric/log query
 -> threshold/window
 -> alert state
 -> action group
 -> human/automation response
```

Mục tiêu không phải “alert mọi lỗi”, mà là phát hiện condition cần hành động.

## 2. Why does it exist?

Dashboard chỉ hữu ích khi ai đó đang nhìn. Production cần proactive detection.

Nhưng quá nhiều alert tạo alert fatigue: team bắt đầu ignore cả critical signals.

## 3. How does it work?

Metric alert phù hợp signal số học liên tục như error rate, CPU, queue depth. Log alert phù hợp condition cần truy vấn dữ liệu sự kiện.

Alert nên có:

- signal;
- threshold;
- evaluation window;
- severity;
- owner;
- runbook/context.

## 4. Practical implementation

Thay vì alert “có một request 500”, dùng điều kiện như:

```text
5xx rate > 5%
AND request count > minimum traffic
FOR 5 minutes
```

Queue consumer có thể alert theo **oldest message age** thay vì chỉ queue length, vì 10k messages có thể bình thường ở peak nếu drain nhanh.

## 5. Real production scenario

App Service có occasional 500 do client disconnect nhưng SLO vẫn tốt. Alert từng exception khiến on-call bị spam. Chuyển sang error-rate + burn-rate style condition làm alert hiếm hơn nhưng có ý nghĩa hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → hàng chục alerts mỗi ngày nhưng không alert nào dẫn tới action.

**Evidence** → repeated auto-resolve, thresholds không gắn SLO, cùng incident tạo nhiều alerts.

**Hypothesis** → alert design dựa raw telemetry thay vì service symptom.

**Diagnosis** → review historical alerts: bao nhiêu % actionable?

**Fix** → deduplicate, tune window, alert symptom trước cause và gắn runbook/owner.

**Verification** → giảm noise trong khi synthetic/known incidents vẫn trigger đúng.

## 7. Common mistakes

- Alert CPU > 80% mà không biết đó có thực sự là user impact.
- Alert từng exception.
- Không có minimum traffic guard.
- Không có owner/runbook.
- Một incident tạo 10 alerts từ 10 components.

## 8. Alternatives

- Dashboard: exploration/manual observation.
- SLO/error-budget alerting: tốt cho user-impact oriented operations.
- Synthetic tests: phát hiện end-to-end availability từ client perspective.

## 9. Trade-offs

### Advantages

- Phát hiện incident sớm.
- Chuẩn hóa operational response.

### Costs / Risks

- Noise tạo alert fatigue.
- Threshold cố định có thể không hợp traffic biến động.
- Monitoring cost tăng theo query/telemetry volume.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu alert phải dựa telemetry có ý nghĩa.

### Middle

Biết tạo metric/log alert và action group cơ bản.

### Senior

Tune signal/window theo SLO, traffic và incident history.

### Technical Lead / Architect

Thiết kế alert taxonomy, ownership và escalation để operations scale theo team/system.

## 11. Key takeaway

- Alert phải yêu cầu hành động, không chỉ báo “có dữ liệu bất thường”.
- Alert symptom gần user impact thường giá trị hơn raw component noise.
- Review alert quality giống review code quality.

# 8. NuGet supply-chain security và dependency pinning: package restore cũng là một phần của security boundary

## 1. What is it?

Software supply chain gồm dependencies, package feeds, build tooling và artifacts đi vào binary cuối cùng.

NuGet restore không chỉ là build convenience; nó quyết định code bên thứ ba nào được đưa vào application.

## 2. Why does it exist?

Một package compromised có thể chạy trong application với cùng quyền như code của bạn. Version drift hoặc feed ambiguity cũng có thể làm build hôm nay khác build tuần sau.

Security phải bao phủ dependency provenance và reproducibility.

## 3. How does it work?

Các controls thường gồm:

- trusted package sources;
- version strategy;
- lock file khi phù hợp;
- vulnerability scanning;
- transitive dependency review;
- artifact/SBOM generation;
- controlled update process.

`packages.lock.json` có thể giúp restore dependency graph đã resolve ổn định khi dùng locked mode.

## 4. Practical implementation

Trong CI:

```bash
dotnet restore --locked-mode
dotnet list package --vulnerable --include-transitive
dotnet build --no-restore
dotnet test --no-build
```

Repository nên có `nuget.config` kiểm soát sources thay vì silently dùng feed developer-local không tồn tại trong CI.

## 5. Real production scenario

Một transitive package có CVE nghiêm trọng. Team chỉ nhìn top-level package list nên không phát hiện. Vulnerability scan có `--include-transitive` giúp tìm dependency thật sự nằm trong resolved graph.

## 6. Failure scenario & troubleshooting

**Symptom** → clean CI restore ra version khác local hoặc package từ feed không mong muốn.

**Evidence** → nhiều sources, floating versions, lock file không được enforce.

**Hypothesis** → dependency resolution không reproducible.

**Diagnosis** → inspect assets/lock file và source mapping.

**Fix** → pin/lock policy, package source mapping, controlled feeds và update process.

**Verification** → clean builds ở multiple agents resolve cùng graph/hash expectation.

## 7. Common mistakes

- Chỉ scan direct dependencies.
- Auto-upgrade production dependency không có tests.
- Dùng wildcard/floating version cho critical package.
- Public + private feeds cấu hình mơ hồ.
- Commit secret credentials vào `nuget.config`.

## 8. Alternatives

- Internal artifact repository/proxy.
- Dependabot/Renovate-style controlled update workflow.
- Vendoring hiếm khi phù hợp .NET enterprise package ecosystem nhưng có thể dùng trong special high-assurance cases.

## 9. Trade-offs

### Advantages

- Reproducible build tốt hơn.
- Giảm dependency confusion/version drift risk.
- Vulnerability visibility tốt hơn.

### Costs / Risks

- Updates cần governance.
- Pinning quá cứng có thể làm security patch chậm nếu process kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transitive dependency cũng chạy trong application.

### Middle

Biết inspect vulnerable/outdated packages và NuGet sources.

### Senior

Thiết kế reproducible restore, feed policy và controlled update pipeline.

### Technical Lead / Architect

Định nghĩa supply-chain controls, SBOM/scanning requirements và ownership của dependency risk.

## 11. Key takeaway

- Dependency restore là security-sensitive build step.
- Transitive packages phải được scan và quản lý.
- Reproducibility + update discipline quan trọng hơn chỉ “pin mọi version”.

# 9. TypeScript discriminated unions cho API state: model trạng thái frontend để compiler chặn impossible UI states

## 1. What is it?

Discriminated union là union các object types dùng một field chung như `status` để phân biệt state.

```typescript
type LoadState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: string };
```

Nó thay nhiều booleans độc lập bằng một state model có tính loại trừ.

## 2. Why does it exist?

Model kiểu này dễ tạo impossible state:

```typescript
isLoading = true
hasError = true
data != null
```

UI không biết phải render gì. Union buộc state chỉ thuộc một case hợp lệ tại một thời điểm.

## 3. How does it work?

TypeScript narrow type theo discriminator:

```typescript
if (state.status === 'success') {
  console.log(state.data); // data guaranteed here
}
```

Compiler có thể kiểm tra exhaustive handling bằng `never` pattern.

## 4. Practical implementation

```typescript
function render<T>(state: LoadState<T>) {
  switch (state.status) {
    case 'idle':
      return 'Idle';
    case 'loading':
      return 'Loading...';
    case 'success':
      return JSON.stringify(state.data);
    case 'error':
      return state.error;
    default: {
      const exhaustive: never = state;
      return exhaustive;
    }
  }
}
```

Khi thêm `status: 'refreshing'`, compiler chỉ ra các switch chưa xử lý.

## 5. Real production scenario

React/Vue screen có initial load, retry, success và error. Trước đây state gồm `loading`, `error`, `data`, `isRetrying`; bug hiển thị stale data cùng error banner sai ngữ cảnh.

Union làm lifecycle explicit.

## 6. Failure scenario & troubleshooting

**Symptom** → UI render trạng thái mâu thuẫn sau race condition.

**Evidence** → nhiều booleans được set ở các async callbacks khác nhau.

**Hypothesis** → state model cho phép impossible combinations.

**Diagnosis** → liệt kê valid states và transitions.

**Fix** → encode valid states bằng discriminated union/reducer/state machine phù hợp.

**Verification** → compiler + tests cho transitions và stale response handling.

## 7. Common mistakes

- Dùng `string` status rộng thay vì literal union.
- Thêm optional fields vào một giant interface.
- Cast `as` để né compiler.
- Model every tiny UI detail thành state machine quá phức tạp.

## 8. Alternatives

- Simple nullable data + loading boolean cho trivial flow.
- Reducer/state machine library cho workflow phức tạp.
- Server state library cho caching/retry/refetch lifecycle.

## 9. Trade-offs

### Advantages

- Impossible states giảm.
- Refactor an toàn hơn.
- UI branches rõ ràng.

### Costs / Risks

- Type definitions dài hơn.
- Có thể over-model simple component.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu literal union và type narrowing.

### Middle

Model API lifecycle bằng discriminated union.

### Senior

Phân biệt local UI state, server state và domain workflow; tránh overengineering.

### Technical Lead / Architect

Định nghĩa frontend state conventions giúp nhiều teams giữ predictable behavior và API error handling nhất quán.

## 11. Key takeaway

- Model valid states thay vì ghép nhiều booleans độc lập.
- Compiler có thể trở thành correctness guard cho UI flow.
- Chỉ dùng độ phức tạp tương xứng workflow.

# 10. Blue-Green deployment trên App Service/IIS: tách deployment khỏi traffic switching để rollback nhanh và giảm release risk

## 1. What is it?

Blue-Green deployment duy trì hai environments/revisions tương đương:

```text
Blue  = đang nhận production traffic
Green = version mới đã deploy và validate
```

Sau validation, traffic được switch từ Blue sang Green. Nếu có regression, switch lại nhanh hơn rollback binary tại chỗ.

## 2. Why does it exist?

In-place deployment thay files/process trên environment đang phục vụ user. Nếu startup, config hoặc dependency compatibility lỗi, production ngay lập tức chịu impact.

Blue-Green tạo một pre-production runtime gần production ngay trong release path.

## 3. How does it work?

Trên Azure App Service, deployment slots là một implementation phổ biến. Trên IIS/on-prem có thể dùng hai sites/server pools phía sau load balancer/reverse proxy.

Flow:

```text
commit
 -> build
 -> test
 -> immutable artifact
 -> deploy Green
 -> warm-up / health validation
 -> switch traffic
 -> monitor
 -> rollback traffic if needed
```

Database vẫn là challenge vì Blue và Green có thể cùng tồn tại trong transition.

## 4. Practical implementation

Database migration phải backward-compatible trong window cả hai versions cùng chạy.

Ví dụ Expand–Migrate–Contract:

```text
1. Add nullable NewColumn
2. Deploy code hiểu old + new schema
3. Backfill
4. Switch traffic
5. Sau khi old version hết tồn tại mới remove OldColumn
```

Không deploy migration phá schema trước khi Green được validate nếu Blue vẫn phụ thuộc schema cũ.

## 5. Real production scenario

ASP.NET Core application trên App Service deploy version mới sang staging slot. Health checks, smoke tests và dependency tests pass; sau đó swap traffic.

5 phút sau error rate tăng do production-only config. Team swap lại slot nhanh trong khi điều tra.

## 6. Failure scenario & troubleshooting

**Symptom** → Green health pass nhưng sau switch request fail do config/identity/network khác Blue.

**Evidence** → slot settings hoặc Managed Identity/network rules khác nhau.

**Hypothesis** → environments không thực sự equivalent hoặc health check quá nông.

**Diagnosis** → compare effective config, identity, private endpoint/DNS, dependency reachability.

**Fix** → define slot-sticky settings rõ, synthetic validation qua critical dependencies và infrastructure-as-code parity.

**Verification** → pre-switch checks phát hiện condition tương tự trước traffic cutover.

## 7. Common mistakes

- Health check chỉ trả 200 hardcoded.
- Schema migration không backward-compatible.
- Green dùng config khác không được quản lý.
- Rollback traffic nhưng database đã destructive migration.
- Build lại artifact giữa environments thay vì promote cùng artifact.

## 8. Alternatives

- Rolling deployment: tiết kiệm capacity hơn nhưng versions coexist theo từng instance.
- Canary: chuyển một phần traffic trước, tốt cho risk-based rollout.
- In-place deployment: đơn giản hơn cho low-risk/internal systems.

## 9. Trade-offs

### Advantages

- Rollback traffic nhanh.
- Validate version mới trước full cutover.
- Giảm downtime risk.

### Costs / Risks

- Gần như cần double environment capacity trong window.
- Database compatibility phức tạp hơn.
- Environment drift có thể làm validation giả tạo.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy artifact và switch traffic là hai bước khác nhau.

### Middle

Biết health validation, slot settings và rollback flow.

### Senior

Thiết kế backward-compatible DB/config/dependency rollout và production verification.

### Technical Lead / Architect

Chọn Blue-Green, Canary hay Rolling dựa risk, capacity, rollback requirements và data migration constraints.

## 11. Key takeaway

- Blue-Green giảm release risk bằng cách tách deployment khỏi traffic cutover.
- Database compatibility thường là phần khó nhất của rollback.
- Promote cùng artifact và validate production-like dependencies trước switch.
