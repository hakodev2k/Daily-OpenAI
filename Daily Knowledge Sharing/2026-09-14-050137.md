# 1. .NET Large Object Heap (LOH): vì sao vài allocation lớn có thể làm GC pauses và memory footprint tăng khó đoán

## 1. What is it?

Mental model:

```text
Managed Heap
├─ Gen 0
├─ Gen 1
├─ Gen 2
└─ Large Object Heap (LOH)
```

Trong .NET, object đủ lớn được cấp phát trên Large Object Heap. Ngưỡng phổ biến là khoảng 85 KB cho object allocation. LOH được quản lý cùng với Gen 2 và có lifecycle khác các small objects ngắn hạn.

Điểm quan trọng: object lớn không nhất thiết sống lâu về business meaning, nhưng runtime vẫn xử lý chúng như large allocations có chi phí memory và collection đáng kể.

## 2. Why does it exist?

Copy/compact object rất lớn liên tục sẽ tốn CPU đáng kể. Vì vậy runtime tách large objects để giảm chi phí di chuyển thường xuyên.

Điều này hợp lý cho workloads như:

- large byte buffers;
- image processing;
- JSON payload lớn;
- file buffering;
- serialization buffers;
- large arrays.

Nhưng nếu application liên tục tạo rồi bỏ các buffer lớn, LOH có thể trở thành nguồn GC pressure và fragmentation.

## 3. How does it work?

Ví dụ:

```csharp
var buffer = new byte[200_000];
```

Allocation này có khả năng đi vào LOH.

Nếu request path làm việc như sau:

```text
request
  -> allocate 2 MB byte[]
  -> serialize
  -> discard
```

và có hàng trăm requests đồng thời, heap có thể tăng rất nhanh trước khi GC reclaim memory.

LOH collection thường xảy ra khi Gen 2 collection xảy ra, vì vậy large short-lived allocations không được thu gom nhanh như Gen 0 objects.

## 4. Practical implementation

Một pattern tốt khi buffer có thể tái sử dụng là `ArrayPool<T>`:

```csharp
var pool = ArrayPool<byte>.Shared;
byte[] buffer = pool.Rent(256 * 1024);

try
{
    var read = await stream.ReadAsync(buffer, ct);
    // process buffer
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

Nhưng pooling không miễn phí. Buffer được rent có thể lớn hơn requested size và không được giữ reference lâu dài.

Streaming thường còn tốt hơn nếu không cần toàn bộ payload cùng lúc:

```text
input stream
   -> chunk
   -> process
   -> output
```

thay vì:

```text
input
 -> MemoryStream toàn bộ
 -> byte[] toàn bộ
 -> output
```

## 5. Real production scenario

Một ASP.NET Core API generate PDF report. Implementation ban đầu tạo `MemoryStream`, render toàn bộ PDF 20–50 MB vào RAM, gọi `ToArray()`, rồi mới upload Blob Storage.

Mỗi report gần như giữ hai copies lớn cùng lúc:

```text
MemoryStream internal buffer
+ byte[] từ ToArray()
```

Khi 30 reports chạy song song, memory tăng hàng GB dù CPU không quá cao. Container bị OOM kill trước khi GC kịp reclaim ổn định.

Chuyển sang streaming trực tiếp sang Blob output hoặc temporary file đã giảm peak memory đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng theo traffic burst, GC pauses dài hơn, container restart/OOM dù không thấy obvious memory leak.

**Evidence** → allocation profile có nhiều `byte[]`, `char[]`, `MemoryStream`; GC counters cho thấy Gen 2 collections tăng và LOH size lớn.

**Hypothesis** → application đang tạo large transient allocations thay vì true long-lived leak.

**Diagnosis** → dùng `dotnet-counters`, `dotnet-gcdump`, profiler hoặc memory dump để xem allocation size/type và retaining paths.

**Fix** → stream, pool buffers, tránh duplicate copies, giới hạn concurrency, giảm payload size.

**Verification** → load test cùng workload và so sánh peak RSS, LOH size, Gen 2 collections, pause duration.

## 7. Common mistakes

- Gọi mọi memory growth là “memory leak”.
- Dùng `MemoryStream.ToArray()` trên payload rất lớn mà không nghĩ đến duplicate copy.
- Pool buffer nhưng quên return.
- Return buffer trong khi code khác vẫn dùng reference đó.
- Dùng pooling cho mọi allocation nhỏ dù complexity tăng mà lợi ích không đáng kể.
- Chỉ nhìn managed heap mà bỏ qua native memory/container RSS.

## 8. Alternatives

- Streaming I/O.
- Temporary file cho payload quá lớn.
- `ArrayPool<T>` cho reusable buffers.
- Chunked processing.
- Giảm concurrency thay vì cố giữ mọi work trong RAM.

## 9. Trade-offs

### Advantages

- Giảm large allocation giúp ổn định memory và GC behavior.
- Streaming giảm peak working set.

### Costs / Risks

- Pooling tạo lifetime complexity.
- Streaming APIs phức tạp hơn “load all then process”.
- Temporary storage thêm I/O và cleanup responsibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu object lớn có allocation cost khác object nhỏ.

### Middle

Biết nhận diện large arrays/`MemoryStream` trong hot path và dùng streaming khi phù hợp.

### Senior

Đọc GC metrics, phân biệt leak với allocation pressure và chọn pooling/chunking/concurrency limits.

### Technical Lead / Architect

Đặt memory budget cho workloads lớn, quyết định process nào nên stream, batch hoặc chạy background thay vì giữ trong request path.

## 11. Key takeaway

- Large transient allocations có thể phá memory stability dù không có leak.
- Streaming thường tốt hơn materialize toàn bộ payload.
- Đo LOH, Gen 2 GC và retaining paths trước khi tối ưu.

# 2. ASP.NET Core Rate Limiting: bảo vệ capacity bằng policy đúng thay vì chỉ trả `429` theo số request thô

## 1. What is it?

Rate limiting giới hạn lượng work client được phép tạo trong một khoảng thời gian hoặc theo concurrency budget.

Mental model:

```text
Client
  |
  v
Rate Limiter
  |
allowed? ---- no ---> 429 / retry information
  |
 yes
  v
Application capacity
```

Rate limiting không chỉ là chống abuse. Nó còn là cơ chế bảo vệ finite capacity của application và downstream dependencies.

## 2. Why does it exist?

Một API có thể chạy tốt ở 1,000 requests/s nhưng database chỉ chịu được 150 expensive report queries cùng lúc.

Nếu limiter chỉ đếm tổng requests, cheap health checks và expensive exports được coi như nhau. Policy tốt phải phản ánh cost hoặc resource boundary thực tế.

## 3. How does it work?

ASP.NET Core hỗ trợ nhiều limiter models:

- fixed window;
- sliding window;
- token bucket;
- concurrency limiter.

Ví dụ concurrency limiter phù hợp endpoint giữ DB connection lâu:

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddConcurrencyLimiter("reports", limiter =>
    {
        limiter.PermitLimit = 20;
        limiter.QueueLimit = 10;
    });
});
```

Endpoint:

```csharp
app.MapGet("/reports/{id}", Handler)
   .RequireRateLimiting("reports");
```

## 4. Practical implementation

Partition limiter theo tenant/user/API key khi fairness quan trọng:

```text
Tenant A -> own limiter partition
Tenant B -> own limiter partition
Tenant C -> own limiter partition
```

Nếu chỉ dùng global limiter, một noisy tenant có thể làm mọi tenant khác bị throttled.

Policy có thể khác nhau:

```text
/login             -> anti-abuse rate
/search            -> request rate
/report/export     -> concurrency budget
/webhook endpoint  -> burst-aware token bucket
```

## 5. Real production scenario

Một e-commerce search endpoint bình thường mất 80 ms. Sau marketing campaign, bot traffic tăng mạnh. API CPU vẫn còn nhưng Elasticsearch concurrency tăng đến mức queue và latency bùng nổ.

Global rate limit theo RPS không đủ vì traffic từ internal mobile app và bots bị trộn chung. Team chuyển sang partition theo client key và đặt concurrency ceiling cho search dependency.

## 6. Failure scenario & troubleshooting

**Symptom** → downstream timeout tăng dù application vẫn còn CPU.

**Evidence** → dependency concurrency tăng, queue length tăng, rate limiter chưa giới hạn theo expensive operation.

**Hypothesis** → limiter đang bảo vệ wrong dimension.

**Diagnosis** → xác định bottleneck thật: RPS, concurrent requests, DB connections, third-party quota hay CPU.

**Fix** → đổi limiter strategy và partition key phù hợp resource boundary.

**Verification** → load test burst + noisy-neighbor scenario; kiểm tra protected dependency giữ trong safe concurrency.

## 7. Common mistakes

- Dùng một fixed-window limit cho toàn API.
- Chỉ rate-limit theo IP phía sau proxy mà không xử lý forwarded headers đúng.
- Không phân biệt authenticated tenant với anonymous traffic.
- Queue quá lớn khiến client chờ lâu thay vì fail fast.
- Trả `429` nhưng không cung cấp retry semantics hợp lý.
- Xem limiter như security control duy nhất.

## 8. Alternatives

- Queue/buffer work nếu operation có thể asynchronous.
- Bulkhead/concurrency isolation ở outbound dependency.
- Autoscaling nếu bottleneck thực sự scale horizontally được.
- CDN/WAF rate controls cho edge abuse.

## 9. Trade-offs

### Advantages

- Bảo vệ capacity và giảm cascading failure.
- Tạo fairness giữa consumers.

### Costs / Risks

- Policy sai có thể reject legitimate traffic.
- Distributed/global limits cần shared coordination hoặc edge support.
- Quá nhiều partitions tăng state/complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `429 Too Many Requests` và mục đích giới hạn traffic.

### Middle

Biết fixed/sliding/token/concurrency limiter khác nhau.

### Senior

Chọn limiter theo bottleneck và partition theo tenant/client.

### Technical Lead / Architect

Định nghĩa capacity budget xuyên API, database và external dependencies, đồng thời quyết định limiter nào nằm ở edge hay application.

## 11. Key takeaway

- Rate limiting phải bảo vệ resource thật, không chỉ đếm request.
- Expensive endpoint thường cần concurrency control hơn simple RPS limit.
- Partitioning giúp tránh noisy-neighbor failure.

# 3. CSRF trong ứng dụng web: vì sao cookie authentication cần anti-forgery còn bearer token thường có threat model khác

## 1. What is it?

Cross-Site Request Forgery (CSRF) lợi dụng việc browser tự động gửi credential, thường là authentication cookie, tới target site.

Mental model:

```text
User logged in to bank.example
Browser stores auth cookie

attacker.example
   |
   +--> POST bank.example/transfer
            |
Browser automatically attaches bank cookie
```

Server có thể tưởng request đến từ legitimate user session dù user không chủ động tạo request đó.

## 2. Why does it exist?

Cookie có behavior đặc biệt: browser quản lý và tự động attach theo domain/path/SameSite rules.

Do đó attacker không cần đọc cookie để gây CSRF. Họ chỉ cần khiến browser gửi request có credential.

Bearer token lưu trong JavaScript memory và phải explicit attach trong `Authorization` header thường không bị browser tự động gửi cross-site theo cùng cơ chế, nên CSRF threat model khác. Tuy nhiên bearer token lại có rủi ro XSS/token theft lớn hơn nếu lưu không an toàn.

## 3. How does it work?

Anti-forgery thường dùng một secret/token mà attacker site không thể biết hoặc đọc, rồi server yêu cầu nó đi cùng state-changing request.

ASP.NET Core có anti-forgery support. Với server-rendered forms:

```html
<form method="post">
    @Html.AntiForgeryToken()
</form>
```

MVC action có thể validate token theo convention/configuration phù hợp.

## 4. Practical implementation

Security decision tree:

```text
Cookie auth?
  |
  +-- yes --> evaluate CSRF protection + SameSite + origin rules
  |
  +-- no --> bearer token?
               |
               +--> focus on XSS, token storage, CORS, scopes
```

`SameSite=Lax/Strict` giúp giảm CSRF nhưng không nên luôn được coi là thay thế hoàn toàn anti-forgery cho mọi workflow, đặc biệt khi cross-site identity/payment flows cần `SameSite=None`.

## 5. Real production scenario

Internal admin portal dùng cookie auth. Endpoint `POST /users/{id}/disable` chỉ kiểm tra authenticated role. Attacker gửi email chứa page tự submit form tới endpoint. Admin đang đăng nhập mở page đó, browser gửi cookie và account bị disable.

Không có XSS và attacker cũng không biết cookie. Đây vẫn là CSRF.

## 6. Failure scenario & troubleshooting

**Symptom** → state-changing action xảy ra từ browser session nhưng user phủ nhận đã thực hiện.

**Evidence** → valid auth cookie, cross-origin navigation/form source, không có anti-forgery token/origin validation.

**Hypothesis** → endpoint cookie-authenticated nhưng thiếu CSRF protection.

**Diagnosis** → inventory state-changing endpoints, credential transport và SameSite/CORS behavior.

**Fix** → anti-forgery token, safe cookie settings, avoid state changes via GET, enforce origin where appropriate.

**Verification** → security test cross-site form/fetch scenarios và expected rejection.

## 7. Common mistakes

- Nghĩ CORS tự động ngăn CSRF.
- Dùng GET để mutate state.
- Nghĩ HTTPS ngăn CSRF.
- Bật `SameSite=None` mà không hiểu cross-site consequences.
- Lưu bearer token trong `localStorage` rồi tuyên bố “không có security issue” vì CSRF thấp hơn.
- Áp anti-forgery mù cho machine-to-machine API dùng bearer token.

## 8. Alternatives

- Bearer token auth cho APIs nếu architecture phù hợp.
- BFF pattern để giữ tokens server-side nhưng vẫn cần xử lý cookie CSRF.
- Origin/Referer validation như defense-in-depth ở một số scenarios.

## 9. Trade-offs

### Advantages

- Anti-forgery token bảo vệ cookie-authenticated state changes hiệu quả.
- `SameSite` thêm browser-level protection.

### Costs / Risks

- SPA/BFF flows cần token plumbing.
- Cross-site integrations có thể cần exceptions.
- Chọn bearer token để né CSRF có thể đổi rủi ro sang XSS/token theft.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CSRF xảy ra vì browser tự gửi credential.

### Middle

Biết anti-forgery, `SameSite`, CORS và bearer token khác nhau.

### Senior

Threat-model authentication transport và frontend architecture thay vì áp checklist.

### Technical Lead / Architect

Chọn cookie/BFF/bearer model dựa trên threat model, UX, token exposure và cross-domain requirements.

## 11. Key takeaway

- CSRF chủ yếu liên quan automatic credential sending, đặc biệt cookies.
- CORS không phải CSRF protection đầy đủ.
- Security model phải xét CSRF và XSS cùng nhau, không tối ưu một phía rồi bỏ phía còn lại.

# 4. EF Core compiled queries: giảm query compilation overhead nhưng chỉ đáng dùng khi profiling chứng minh hot path

## 1. What is it?

EF Core phải xử lý LINQ expression thành executable query plan ở client side trước khi database nhận SQL.

Mental model:

```text
LINQ expression
   |
query translation / compilation
   |
SQL + parameter mapping
   |
database execution
```

EF Core có query caching nội bộ, nhưng compiled query cho phép application precompile query delegate và tái sử dụng trực tiếp cho hot path.

## 2. Why does it exist?

Trong đa số business APIs, database/network latency lớn hơn query-compilation overhead. Nhưng với extremely hot low-latency query chạy hàng trăm nghìn lần, phần overhead nhỏ này có thể trở nên đáng đo.

Compiled query tồn tại để tối ưu micro-overhead ở query shape ổn định.

## 3. How does it work?

Ví dụ:

```csharp
private static readonly Func<AppDbContext, int, Product?> GetProduct =
    EF.CompileQuery(
        (AppDbContext db, int id) =>
            db.Products
              .AsNoTracking()
              .SingleOrDefault(x => x.Id == id));
```

Call:

```csharp
var product = GetProduct(db, id);
```

Async variant dùng `EF.CompileAsyncQuery`.

## 4. Practical implementation

Chỉ cân nhắc khi:

- query shape cố định;
- được gọi cực thường xuyên;
- database query vốn rất nhanh;
- profiler cho thấy client-side query compilation có tỷ trọng đáng kể.

Không nên thay toàn bộ repository methods bằng compiled queries như coding standard.

## 5. Real production scenario

Một pricing service có point lookup trên local low-latency database. Query chỉ mất ~0.5–1 ms và chạy hàng chục nghìn lần/s. Profiling cho thấy EF query pipeline overhead bắt đầu đáng kể.

Compiled query cho hot lookup giảm CPU một phần nhỏ nhưng measurable. Team chỉ áp dụng cho 2 queries thay vì 300 queries khác.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU application cao dù DB latency thấp; profile cho thấy query compilation/expression processing lặp lại trên hot path.

**Evidence** → same query shape chạy cực nhiều; DB execution không phải bottleneck.

**Hypothesis** → ORM client-side overhead có ý nghĩa ở workload này.

**Diagnosis** → benchmark representative query với/không compiled query; tránh microbenchmark không có database reality.

**Fix** → compiled query cho targeted paths nếu benefit rõ.

**Verification** → measure CPU/request, throughput và p95 dưới production-like concurrency.

## 7. Common mistakes

- Dùng compiled query trước khi tối ưu SQL/index/round trips.
- Nghĩ compiled query làm database execution plan tốt hơn.
- Dùng cho query shape động phức tạp.
- Tạo abstraction khó maintain chỉ để tiết kiệm microseconds không đáng kể.
- Benchmark với in-memory fake rồi kết luận production benefit.

## 8. Alternatives

- Projection để giảm data transfer.
- `AsNoTracking` cho read-only query.
- Index/query-plan tuning.
- Cache nếu data semantics cho phép.
- Raw SQL cho cases ORM translation không phù hợp.

## 9. Trade-offs

### Advantages

- Giảm một phần CPU/translation overhead ở hot path.
- Predictable query shape.

### Costs / Risks

- Code verbose hơn.
- Ít linh hoạt với dynamic query composition.
- Dễ trở thành premature optimization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ không trực tiếp “chạy trong database”; nó phải được translate.

### Middle

Tối ưu query shape, projection và tracking trước.

### Senior

Dùng profiling để xác định khi ORM overhead thật sự đáng kể.

### Technical Lead / Architect

Ngăn micro-optimization lan thành framework convention khi không có evidence.

## 11. Key takeaway

- Compiled query là optimization cho hot query, không phải default pattern.
- Database I/O, index và round trips thường đáng tối ưu trước.
- Chỉ giữ optimization nếu benchmark production-like chứng minh benefit.

# 5. SQL Server deadlocks: đọc wait graph để tìm cycle thật thay vì tăng timeout hoặc retry mù

## 1. What is it?

Deadlock xảy ra khi nhiều transactions giữ resources mà transaction khác cần và tạo thành cycle không thể tự tiến tiếp.

Mental model:

```text
Transaction A holds Row X
Transaction B holds Row Y

A waits for Y
B waits for X

A <---- wait ---- B
|                 |
+------ cycle ----+
```

SQL Server phát hiện cycle và chọn một transaction làm deadlock victim để rollback.

## 2. Why does it exist?

Locking là cần thiết để bảo vệ transactional consistency. Deadlock là hệ quả có thể xảy ra khi transactions acquire resources theo thứ tự khác nhau hoặc giữ locks quá lâu.

Deadlock khác blocking:

```text
blocking -> có thể tự resolve khi holder commit

deadlock -> cycle, cần một participant bị abort
```

## 3. How does it work?

Ví dụ:

Transaction A:

```sql
UPDATE Accounts SET Balance = Balance - 10 WHERE Id = 1;
UPDATE Accounts SET Balance = Balance + 10 WHERE Id = 2;
```

Transaction B:

```sql
UPDATE Accounts SET Balance = Balance - 5 WHERE Id = 2;
UPDATE Accounts SET Balance = Balance + 5 WHERE Id = 1;
```

Nếu hai transactions xen kẽ đúng thời điểm, mỗi transaction giữ một row và chờ row kia.

## 4. Practical implementation

Nguyên tắc quan trọng: access resources theo cùng order.

Ví dụ chuyển tiền luôn lock account theo ascending ID:

```text
min(accountA, accountB) first
max(accountA, accountB) second
```

Giữ transaction ngắn:

```text
BAD:
BEGIN TRAN
  update DB
  call external API 3s
  update DB
COMMIT
```

External network call không nên nằm trong DB transaction nếu không thật sự cần.

## 5. Real production scenario

Order service update `Orders` rồi `Inventory`; worker khác update `Inventory` rồi `Orders`. Under low traffic không sao. Sale event tăng concurrency và deadlocks xuất hiện hàng phút.

Team ban đầu tăng command timeout nhưng deadlock vẫn xảy ra vì timeout không phá cycle logic. Deadlock graph cho thấy resource acquisition order ngược nhau.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL error 1205, transaction was deadlocked and chosen as victim.

**Evidence** → Extended Events/deadlock graph cho thấy participants, lock modes, objects và statements.

**Hypothesis** → conflicting transactions lock resources theo order khác nhau hoặc scan quá rộng.

**Diagnosis** → đọc deadlock graph, execution plans và transaction boundaries.

**Fix** → consistent access order, better indexes để giảm lock footprint, shorter transactions; retry targeted nếu operation idempotent/safe.

**Verification** → concurrency load test và monitor deadlock event rate.

## 7. Common mistakes

- Tăng timeout để chữa deadlock.
- Retry vô hạn mọi database exception.
- Bật `NOLOCK` như universal fix.
- Giữ transaction mở khi gọi HTTP.
- Chỉ nhìn application stack trace mà không capture deadlock graph.
- Thêm index mà không biết lock path/execution plan.

## 8. Alternatives

- Snapshot-based isolation để giảm reader-writer blocking trong phù hợp scenarios.
- Optimistic concurrency cho application-level conflicts.
- Queue serialization cho một số highly contended workflows.

## 9. Trade-offs

### Advantages

- Consistent resource ordering thường là simple và robust fix.
- Targeted retry giúp recover rare unavoidable deadlocks.

### Costs / Risks

- Isolation changes có storage/semantic impact.
- Retry tăng latency và có thể duplicate side effects nếu transaction boundary không rõ.
- Serialization giảm throughput.

## 10. Junior → Middle → Senior → Technical Lead

Phân biệt blocking và deadlock.

### Middle

### Senior

Đọc deadlock graph và execution plan để tìm cycle/root cause.

### Technical Lead / Architect

Định nghĩa transactional boundaries, retry policy và lock-order conventions cho critical workflows.

## 11. Key takeaway

- Deadlock là cycle, không phải đơn giản “query chậm”.
- Deadlock graph là evidence quan trọng nhất.
- Fix root cause trước; retry chỉ là resilience layer bổ sung.

# 6. Elasticsearch analyzers: `text`, `keyword`, tokenizer và normalization quyết định search behavior trước cả scoring

**Diagnosis** → inspect mapping, `_analyze`, query DSL và indexed terms.

**Fix** → mapping/analyzer đúng semantics; reindex qua new index + alias switch.

**Verification** → relevance regression tests với representative queries và edge cases.

## 7. Common mistakes

- Dùng `text` cho IDs/codes.
- Dùng `keyword` cho natural-language fields rồi kỳ vọng full-text relevance.
- Thay analyzer trên existing index mà quên cần reindex.
- Custom analyzer quá sớm.
- Debug scoring trước khi kiểm tra tokenization.
- Không có search relevance regression corpus.

## 8. Alternatives

- SQL exact search cho identifiers/structured filtering.
- Database full-text features khi search requirements đơn giản.
- Search SaaS nếu operational burden Elasticsearch quá cao.

## 9. Trade-offs

### Advantages

- Analyzer đúng giúp relevance tốt và behavior predictable.
- Multi-fields cho phép vừa full-text vừa exact/sort.

# 7. Modular Monolith: giữ deployment đơn giản nhưng vẫn tạo boundaries đủ mạnh để tránh “big ball of mud”

## 1. What is it?

Modular Monolith là một application deployable unit nhưng được chia thành modules có boundaries rõ ràng về domain, dependencies và data ownership.

Mental model:

```text
One deployment

+---------------------------+
| Module Orders             |
| Module Catalog            |
| Module Identity           |
| Module Payments           |
+---------------------------+

Boundaries strong in code/design
Deployment remains one unit
```

Nó không đơn giản là “monolith có nhiều folders”.

## 2. Why does it exist?

Microservices giải quyết independent deployment/scaling/ownership nhưng mang theo network failure, distributed transactions, observability và deployment complexity.

Nhiều teams chưa cần operational complexity đó nhưng vẫn cần domain boundaries để codebase không thành tightly coupled monolith.

## 3. How does it work?

Mỗi module nên có:

- public contract rõ;
- internal implementation ẩn;
- dependency direction kiểm soát;
- data ownership rõ;
- tests ở module boundary.

Ví dụ:

```text
Orders
  -> references Payments.Contracts
  X does not reference Payments.Infrastructure
```

Cross-module communication có thể synchronous in-process hoặc domain/integration-style events nội bộ tùy nhu cầu.

## 4. Practical implementation

Trong .NET solution:

```text
src/
  Modules/
    Orders/
      Orders.Contracts
      Orders.Application
      Orders.Infrastructure
    Catalog/
      Catalog.Contracts
      Catalog.Application
      Catalog.Infrastructure
```

Không nhất thiết mỗi layer/module đều cần project riêng. Project boundaries chỉ đáng dùng khi thực sự enforce dependency tốt hơn.

Architecture tests có thể kiểm tra forbidden references.

## 5. Real production scenario

Startup có 8 developers nhưng chọn microservices từ ngày đầu. Mỗi feature phải update 4 repos, CI/CD pipelines, service discovery, distributed tracing và test environments.

Team chưa có organizational ownership độc lập nên microservices tạo coordination cost mà không đem independent delivery thực tế.

Một modular monolith có thể phù hợp hơn: domain boundaries vẫn rõ nhưng local development và deployment đơn giản.

## 6. Failure scenario & troubleshooting

**Symptom** → monolith có modules trên diagram nhưng bất kỳ module nào cũng query trực tiếp tables/services của module khác.

**Evidence** → circular project references, shared database tables không có owner, internal classes được dùng xuyên module.

**Hypothesis** → boundary chỉ mang tính naming, không enforce.

**Diagnosis** → dependency graph, database ownership, public APIs và change-impact analysis.

**Fix** → narrow contracts, internal visibility, architecture tests, ownership rules, refactor cross-module DB access.

**Verification** → thay implementation một module không kéo cascade changes không liên quan.

## 7. Common mistakes

- Gọi bất kỳ monolith nào có folders là modular monolith.
- Tạo 100 projects để “enforce architecture”.
- Shared `Common` project chứa toàn business logic.
- Cho module khác query tables trực tiếp vì “cùng database mà”.
- Dùng internal event bus phức tạp như Kafka giả lập dù không cần.
- Xây modular monolith chỉ để “sau này chắc chắn tách microservice”.

## 8. Alternatives

- Layered monolith cho domain đơn giản.
- Microservices khi independent deployment/scaling/ownership có business value rõ.
- Vertical slices trong single application khi module boundaries chưa cần mạnh.

## 9. Trade-offs

### Advantages

- Deployment/local development đơn giản hơn distributed system.
- Giữ domain boundaries và change isolation tốt hơn unstructured monolith.
- Có thể evolve dần.

### Costs / Risks

- Runtime/resource scaling vẫn theo whole application.
- Database coupling dễ quay lại nếu discipline yếu.
- In-process calls có thể che coupling mà network boundary sẽ lộ rõ hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là boundary business, không chỉ folder.

### Middle

Tôn trọng public contracts và data ownership.

### Senior

Thiết kế dependency graph, module APIs và transactional boundaries.

### Technical Lead / Architect

Chọn modular monolith vs microservices dựa trên organizational, scaling và deployment needs thay vì trend.

## 11. Key takeaway

- Modular Monolith tối ưu cho strong boundaries + simple deployment.
- Boundary phải được enforce bằng dependency/data ownership, không chỉ naming.
- Microservices chỉ đáng giá khi independent operation thật sự cần thiết.

# 8. Azure Service Bus Dead-Letter Queue: DLQ là operational workflow, không phải thùng rác cho message lỗi

## 1. What is it?

Dead-Letter Queue (DLQ) chứa messages không thể được xử lý thành công trong normal delivery path.

Mental model:

```text
Queue / Subscription
      |
consumer receives
      |
 success -> Complete
 failure -> Abandon / retry
      |
exceeds delivery / explicit dead-letter
      |
      v
     DLQ
```

Message trong DLQ vẫn là production data cần ownership và remediation.

## 2. Why does it exist?

Nếu poison message cứ retry mãi:

- throughput bị chiếm;
- logs bị flood;
- downstream bị gọi lặp;
- queue backlog tăng;
- cost và incident severity tăng.

DLQ cách ly message không tiến triển khỏi healthy traffic.

## 3. How does it work?

Message có delivery count. Consumer có thể:

- `Complete` khi xử lý xong;
- `Abandon` để delivery lại;
- `DeadLetter` khi biết message không thể xử lý tự động;
- defer trong một số advanced workflow.

Khi max delivery count vượt ngưỡng, Service Bus có thể đưa message vào DLQ.

## 4. Practical implementation

Consumer phải phân loại lỗi:

```text
Transient error
 -> retry/backoff

Permanent validation error
 -> dead-letter immediately

Unknown dependency outage
 -> limited retries, then DLQ or defer policy
```

Dead-letter reason/description nên structured đủ để triage, không chứa secrets.

Ví dụ:

```csharp
await args.DeadLetterMessageAsync(
    args.Message,
    deadLetterReason: "UnsupportedSchemaVersion",
    deadLetterErrorDescription: "Expected v2 or v3",
    cancellationToken: ct);
```

## 5. Real production scenario

Producer deploy schema v3 trước consumer. Consumer cũ deserialize fail và abandon. Message retry hàng chục lần rồi DLQ.

Nếu không có dashboard/alert DLQ, business orders bị “mất khỏi flow” nhiều giờ dù queue chính trông khỏe.

DLQ visibility phải là part of service SLO/operations.

## 6. Failure scenario & troubleshooting

**Symptom** → queue input/output có vẻ bình thường nhưng users báo một số transactions không hoàn tất.

**Evidence** → DLQ message count tăng; reasons tập trung vào schema/validation/dependency type.

**Hypothesis** → poison/permanent failures bị tách khỏi main queue nhưng không có remediation loop.

**Diagnosis** → inspect DLQ metadata, correlation IDs và producer/consumer versions.

**Fix** → sửa consumer/data, replay có kiểm soát sau khi root cause resolved.

**Verification** → DLQ drains, replay không tạo duplicate side effects, business state đúng.

## 7. Common mistakes

- Không monitor DLQ.
- Tự động replay mọi message liên tục.
- Delete DLQ để “clear alarm”.
- Retry validation errors như transient errors.
- Replay message non-idempotent mà không kiểm tra side effects trước đó.
- Đặt max delivery count quá cao để trì hoãn vấn đề.

## 8. Alternatives

- Quarantine database/table nếu cần richer remediation UI/workflow.
- Separate invalid-message topic cho domain-specific rejection.
- Manual intervention khi business operation có high financial risk.

## 9. Trade-offs

### Advantages

- Healthy messages tiếp tục xử lý.
- Giữ failed payload để investigation/recovery.

### Costs / Risks

- DLQ tạo operational backlog cần owner.
- Replay có thể duplicate side effects.
- Sensitive payload retention cần security/compliance consideration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DLQ là nơi message fail được cách ly.

### Middle

Phân biệt transient/permanent failure và settlement actions.

### Senior

Thiết kế idempotent replay, DLQ telemetry và incident workflow.

### Technical Lead / Architect

Định nghĩa ownership, retention, alert thresholds và replay governance cho messaging platform.

## 11. Key takeaway

- DLQ không phải nơi lỗi “biến mất”; nó là production recovery queue.
- Permanent errors và transient errors cần policy khác nhau.
- Replay chỉ an toàn khi side effects/idempotency được hiểu rõ.

# 9. OpenTelemetry trace context: nối request, database, message và downstream calls thành một causal chain có thể điều tra

API span

Một baseline .NET setup gồm:

```text
ASP.NET Core instrumentation
HttpClient instrumentation
database instrumentation
custom business spans where useful
exporter -> Azure Monitor / OTLP backend
```

## 5. Real production scenario

Checkout API p95 tăng từ 800 ms lên 4 s. Logs của checkout không có error. Trace cho thấy 3.1 s nằm ở inventory downstream call, và inventory trace tiếp tục cho thấy SQL lock wait.

**Symptom** → traces bị đứt giữa Service A và Service B hoặc message consumer tạo trace mới không liên quan.

**Evidence** → trace IDs khác nhau qua boundary dù cùng logical operation.

**Hypothesis** → context propagation bị mất hoặc custom client/message layer không inject headers.

**Diagnosis** → inspect outgoing headers/message metadata và instrumentation configuration.

**Fix** → propagate W3C context đúng boundary; không tự tạo random correlation scheme nếu standard support đã có.

**Verification** → synthetic transaction phải hiển thị end-to-end single trace.

## 7. Common mistakes

- Ghi mọi data vào span attributes.
- Dùng user ID/order ID uncontrolled làm metric label high-cardinality.
- Sample 100% traffic ở scale lớn mà không tính cost.
- Có tracing nhưng không propagate qua queues.
- Tạo custom spans cho từng trivial method làm trace noise.
- Dùng trace thay hoàn toàn logs/metrics.

## 8. Alternatives

- Correlation ID trong logs cho hệ thống nhỏ.
- Vendor-specific APM auto-instrumentation.
- Metrics để detect aggregate symptoms; traces để investigate request path.

## 9. Trade-offs

### Advantages

- Nối dependency latency xuyên services.
- Hỗ trợ root-cause analysis và service ownership.

### Costs / Risks

- Telemetry volume/cost có thể lớn.
- Sampling có thể bỏ rare traces.
- Sensitive-data governance cần rõ ràng.

### Senior

Thiết kế propagation, sampling và useful custom spans.

### Technical Lead / Architect

Chuẩn hóa telemetry schema, privacy, backend cost và incident workflows xuyên tổ chức.

## 11. Key takeaway

- Trace context biến nhiều service calls thành một causal chain.
- Tracing hữu ích nhất khi propagation xuyên mọi boundary.

# 10. CDN `Cache-Control` và invalidation: performance ở edge chỉ an toàn khi ownership của freshness được thiết kế rõ

## 1. What is it?

CDN cache giữ response gần user tại edge để giảm origin latency và load.

Mental model:

```text
Browser
   |
   v
CDN Edge Cache
   | hit -> return
   |
 miss
   v
Origin / App
```

`Cache-Control` xác định ai có thể cache, trong bao lâu và dưới điều kiện nào.

## 2. Why does it exist?

Static content như images, JS bundles và public product data có thể được phục vụ từ edge nhanh hơn rất nhiều so với gọi origin mỗi request.

Nhưng caching tạo consistency problem: dữ liệu đã update ở origin không đồng nghĩa edge copy biến mất ngay.

## 3. How does it work?

Ví dụ immutable versioned asset:

```http
Cache-Control: public, max-age=31536000, immutable
```

Tên file chứa content hash:

```text
app.a81f3c.js
```

Khi content đổi, URL đổi, nên cache cũ không gây stale behavior cho version mới.

Dynamic content có thể dùng shorter TTL hoặc `s-maxage` cho shared cache tùy policy.

## 4. Practical implementation

Phân loại content:

```text
Hashed static assets
 -> very long TTL

Public catalog page/data
 -> moderate TTL + purge/revalidation

Personalized/account data
 -> usually private/no shared caching

Sensitive responses
 -> explicit no-store/private as appropriate
```

Đừng chỉ dựa vào default headers của framework/CDN.

## 5. Real production scenario

Product price update trong database đúng ngay, app origin cũng trả giá mới, nhưng users ở một region vẫn thấy giá cũ 20 phút.

Root cause: CDN cached HTML/API response với TTL 30 phút. Team deploy application nhiều lần nhưng không thay đổi gì vì stale content nằm ở edge.

Correct remediation là inspect cache headers/key/purge path, không restart origin.

## 6. Failure scenario & troubleshooting

**Symptom** → một số users/regions thấy content cũ; direct origin request trả content mới.

**Evidence** → response headers cho thấy cache hit/age; edge cache key chưa invalidated.

**Hypothesis** → freshness policy hoặc purge failed.

**Diagnosis** → compare browser/CDN/origin responses, `Age`, cache-control, vary/cache key behavior và purge status.

**Fix** → targeted purge, shorter TTL hoặc versioned URLs; sửa ownership của invalidation workflow.

**Verification** → requests qua multiple edge locations trả expected version và cache headers.

## 7. Common mistakes

- Cache personalized response ở shared CDN.
- Dùng long TTL cho mutable URL nhưng không có purge/versioning.
- Purge toàn CDN quá thường xuyên, làm mất cache efficiency.
- Không đưa query parameters/headers cần thiết vào cache key.
- Đổi backend data rồi mặc định edge thấy ngay.
- Debug app origin trước khi kiểm tra `Age`/cache status headers.

## 8. Alternatives

- Browser-only caching cho content không phù hợp shared cache.
- Application Redis cache cho server-side reusable data.
- No-cache/revalidation semantics khi freshness quan trọng hơn hit ratio.

## 9. Trade-offs

### Advantages

- Giảm latency và origin load đáng kể.
- Tăng resilience trước traffic spikes cho cacheable content.

### Costs / Risks

- Stale content và invalidation complexity.
- Cache key mistakes có thể thành security incident.
- Purge operations có propagation delay/cost tùy provider.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser cache khác CDN/shared cache.

### Middle

Biết `Cache-Control`, TTL, `Age`, immutable assets và purge.

### Senior

Thiết kế cache keys/freshness cho dynamic/public content và troubleshoot edge-vs-origin mismatch.

### Technical Lead / Architect

Định nghĩa ownership của freshness, invalidation SLA, personalized-content boundaries và CDN failure strategy.

## 11. Key takeaway

- CDN performance luôn đổi lấy freshness complexity.
- Versioned immutable assets là pattern đơn giản và mạnh nhất cho static content.
- Khi origin đúng nhưng user thấy sai, kiểm tra edge cache trước khi restart application.
