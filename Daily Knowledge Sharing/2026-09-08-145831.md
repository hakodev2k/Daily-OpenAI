# 1. `async` / `await` state machine trong .NET: vì sao sync-over-async có thể phá throughput dù code nhìn rất “bình thường”

## 1. What is it?

`async` / `await` trong C# là syntax giúp viết asynchronous control flow theo dạng tuần tự, nhưng compiler không “biến thread thành async”. Nó chuyển method thành một state machine quản lý continuation quanh các điểm `await`.

Mental model đúng:

```text
Call async method
   ↓
Run synchronously until incomplete await
   ↓
Return Task to caller
   ↓
I/O completes later
   ↓
Schedule continuation
   ↓
Resume state machine
```

Điểm quan trọng nhất: một method async vẫn chạy synchronous cho đến khi gặp một awaitable chưa hoàn thành. `await` không tạo thread mới. Với I/O-bound work, thread được trả về ThreadPool trong lúc chờ network, database hoặc file I/O.

## 2. Why does it exist?

Trước `async` / `await`, asynchronous programming thường dựa vào callback, events hoặc continuation chain. Logic error handling và sequencing rất khó đọc.

Trong server, asynchronous I/O cho phép một lượng thread hữu hạn phục vụ số lượng request lớn hơn. Nếu một request chờ SQL Server 100 ms, thread không cần ngồi blocked 100 ms.

Nếu code chuyển lại sang blocking bằng `.Result`, `.Wait()` hoặc `.GetAwaiter().GetResult()`, lợi ích này biến mất và có thể tạo ThreadPool starvation.

## 3. How does it work?

Compiler sinh một struct/class state machine chứa:

* state hiện tại;
* local variables cần sống qua `await`;
* awaiter;
* builder cho `Task`/`ValueTask`.

Ví dụ:

```csharp
public async Task<int> LoadAsync(CancellationToken ct)
{
    var value = await _client.GetStringAsync("value", ct);
    return int.Parse(value);
}
```

Conceptually gần với:

```text
state 0: call GetStringAsync
         if completed → continue immediately
         else save state and return Task

state 1: I/O completed
         restore locals
         parse value
         complete Task
```

Trong ASP.NET Core hiện đại thường không có request-scoped `SynchronizationContext` kiểu ASP.NET cũ. Vì vậy deadlock cổ điển do context capture ít phổ biến hơn, nhưng sync-over-async vẫn nguy hiểm vì blocking ThreadPool workers.

## 4. Practical implementation

Sai:

```csharp
public OrderDto GetOrder(Guid id)
{
    return _repository.GetOrderAsync(id).Result;
}
```

Đúng hơn:

```csharp
public Task<OrderDto?> GetOrderAsync(
    Guid id,
    CancellationToken cancellationToken)
{
    return _repository.GetOrderAsync(id, cancellationToken);
}
```

Nếu endpoint:

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    OrderService service,
    CancellationToken cancellationToken) =>
{
    var result = await service.GetOrderAsync(id, cancellationToken);
    return result is null ? Results.NotFound() : Results.Ok(result);
});
```

Không thêm `Task.Run()` quanh I/O-bound work chỉ để “làm async”:

```csharp
// Không nên
await Task.Run(() => httpClient.GetStringAsync(url));
```

`HttpClient` đã asynchronous rồi.

## 5. Real production scenario

Một ASP.NET Core API có 500 concurrent requests. Mỗi request gọi database mất 200 ms. Phiên bản async thuần giữ ít ThreadPool workers active trong thời gian chờ I/O.

Một developer thêm `.Result` tại service layer vì một interface cũ là synchronous. Requests bắt đầu giữ worker thread suốt 200 ms. Khi traffic tăng, queue length của ThreadPool tăng, request mới phải chờ worker được inject thêm. CPU có thể chưa đạt 100% nhưng p99 latency tăng rất mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU trung bình không quá cao nhưng request latency tăng, timeout hàng loạt dưới tải.

**Evidence** → thread count tăng, ThreadPool queue tăng, traces cho thấy request “đứng” trước hoặc quanh dependency call.

**Hypothesis** → sync-over-async hoặc blocking I/O gây ThreadPool starvation.

**Diagnosis** → tìm `.Result`, `.Wait()`, synchronous DB/HTTP calls, `Thread.Sleep`, lock giữ lâu. Dùng `dotnet-counters`, Application Insights dependency spans hoặc profiler để xem ThreadPool queue/thread growth.

**Fix** → async xuyên call chain; bỏ blocking call; chỉ dùng CPU parallelism khi thực sự CPU-bound.

**Verification** → load test cùng concurrency; so sánh p95/p99, ThreadPool queue length và throughput.

## 7. Common mistakes

* Nghĩ `async` có nghĩa “chạy trên thread khác”.
* Dùng `Task.Run()` cho I/O-bound work trong ASP.NET Core.
* Chuyển một layer sang async nhưng layer trên gọi `.Result`.
* `async void` ngoài event handler.
* Không truyền `CancellationToken`.
* Tối ưu `ValueTask` trước khi giải quyết blocking thực sự.

## 8. Alternatives

* Synchronous code vẫn hợp lý cho CPU work rất ngắn hoặc API không có async equivalent.
* Background queue phù hợp cho work dài không cần hoàn thành trong request.
* Parallelism (`Parallel.ForEachAsync`, workers) khác asynchronous I/O và chỉ nên dùng theo workload.

## 9. Trade-offs

### Advantages

* Tăng scalability cho I/O-bound workload.
* Giảm số thread bị blocked.
* Control flow dễ đọc hơn callback-based async.

### Costs / Risks

* Async contract lan qua nhiều layer.
* State machine có overhead nhỏ.
* Debugging continuation có thể khó hơn synchronous code.
* Sai blocking usage có thể phá lợi ích toàn pipeline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` không tạo thread; nó cho phép trả thread khi I/O chưa xong.

### Middle

Biết viết async end-to-end, tránh `.Result`/`.Wait()`, propagate cancellation và phân biệt CPU-bound với I/O-bound.

### Senior

Biết đọc ThreadPool starvation signals, hiểu state machine/continuation và đánh giá hot path có thực sự cần micro-optimization không.

### Technical Lead / Architect

Đặt async conventions ở boundary, hiện đại hóa synchronous legacy interface từng bước và review design để một adapter cũ không kéo cả request pipeline về blocking.

## 11. Key takeaway

* `await` là scheduling/control-flow abstraction, không phải thread creation.
* Async chỉ mang lại scalability nếu call chain không quay lại blocking.
* ThreadPool starvation có thể xảy ra khi CPU chưa hề đầy.

# 2. ASP.NET Core DI lifetimes và captive dependency: khi `Singleton` vô tình giữ `Scoped` state lâu hơn request

## 1. What is it?

ASP.NET Core DI có ba lifetime phổ biến:

* `Transient`: tạo instance theo lần resolve.
* `Scoped`: một instance trong scope, thường là một HTTP request.
* `Singleton`: một instance cho toàn application lifetime.

Captive dependency xảy ra khi component sống lâu giữ reference tới dependency có lifetime ngắn hơn, đặc biệt `Singleton → Scoped`.

Mental model:

```text
Application lifetime
└── Singleton
    └── Scoped service  ← nguy hiểm nếu bị giữ vượt request

Request A scope → DbContext A
Request B scope → DbContext B
```

## 2. Why does it exist?

Lifetime biểu diễn ownership và state boundary. `DbContext` là ví dụ điển hình: nó giữ change tracker và connection-related state, nên thường thuộc request/unit-of-work scope.

Nếu một singleton giữ `DbContext`, context đó có thể bị nhiều request dùng đồng thời, giữ entity tracking quá lâu hoặc trở thành disposed reference tùy cách resolve.

## 3. How does it work?

ASP.NET Core tạo root service provider khi startup. Mỗi request tạo một child scope. `Scoped` services được cache trong child scope và dispose khi scope kết thúc.

Sai:

```csharp
services.AddSingleton<ReportCache>();
services.AddScoped<AppDbContext>();
```

Nếu `ReportCache` constructor nhận `AppDbContext`, DI validation thường phát hiện khi scope validation bật. Nhưng captive lifetime cũng có thể xuất hiện gián tiếp qua factory/service locator.

## 4. Practical implementation

Nếu singleton cần thực hiện một unit of work định kỳ, inject `IServiceScopeFactory` thay vì giữ scoped service:

```csharp
public sealed class ReportWarmupService : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public ReportWarmupService(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = _scopeFactory.CreateAsyncScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            await db.Reports
                .AsNoTracking()
                .Take(100)
                .ToListAsync(stoppingToken);

            await Task.Delay(TimeSpan.FromMinutes(5), stoppingToken);
        }
    }
}
```

Tốt hơn nữa, nếu service chỉ cần một stateless abstraction, thiết kế singleton phụ thuộc vào thread-safe singleton/transient dependencies thay vì service locator rộng.

## 5. Real production scenario

Một singleton pricing cache được viết để giảm database calls. Developer inject repository scoped vào cache singleton. Dưới tải cao, cùng repository/DbContext bị nhiều request sử dụng đồng thời.

Kết quả có thể là exception “A second operation was started on this context before a previous operation completed”, stale tracked entities hoặc race condition khó tái hiện local.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi concurrency trên `DbContext`, memory tăng dần hoặc data request này xuất hiện trong request khác.

**Evidence** → object instance ID của service/DbContext lặp lại giữa nhiều request scope.

**Hypothesis** → lifetime mismatch/captive dependency.

**Diagnosis** → inspect registrations, constructor graph, factories và root provider resolutions. Bật scope validation ở Development/test.

**Fix** → sửa lifetime, tạo scope tại unit-of-work boundary hoặc đổi abstraction để singleton không giữ scoped state.

**Verification** → concurrent integration test và logging instance identifiers theo request.

## 7. Common mistakes

* Cho rằng `Singleton` luôn nhanh hơn vì ít allocation.
* Inject `DbContext` vào singleton/background service trực tiếp.
* Resolve scoped service từ root `IServiceProvider`.
* Dùng singleton cho object có mutable request/user state.
* Thay DI lifetime để “fix disposed object” mà không hiểu ownership.

## 8. Alternatives

* `Scoped` service là default tốt cho request-centric application services.
* `Transient` phù hợp stateless lightweight components.
* `IDbContextFactory<T>` hữu ích khi cần tạo context ngoài request scope hoặc nhiều unit-of-work độc lập.

## 9. Trade-offs

### Advantages

Correct lifetime làm ownership, disposal và concurrency boundary rõ ràng.

### Costs / Risks

Quá nhiều scopes/factories có thể làm flow khó theo dõi. Singleton có thể tiết kiệm allocation nhưng yêu cầu thread safety nghiêm ngặt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết ba lifetime và hiểu scoped thường gắn với request.

### Middle

Biết register service đúng lifetime, tạo scope trong `BackgroundService` và tránh mutable singleton state.

### Senior

Phân tích dependency graph, disposal, thread safety và hidden captive dependency qua factories.

### Technical Lead / Architect

Định nghĩa service ownership conventions và quyết định boundary nào thực sự cần long-lived process versus request-scoped unit of work.

## 11. Key takeaway

* DI lifetime là ownership/concurrency contract, không phải tuning option.
* `Singleton → Scoped` là red flag cần lý do rất rõ.
* `DbContext` lifetime sai thường tạo lỗi production khó tái hiện.

# 3. EF Core `IQueryable` execution boundary: khi một dòng `ToListAsync()` quyết định SQL, round-trip và memory footprint

## 1. What is it?

`IQueryable<T>` biểu diễn một query chưa thực thi. EF Core giữ expression tree và dịch nó thành SQL khi gặp terminal operation như `ToListAsync`, `SingleAsync`, `CountAsync` hoặc khi enumeration bắt đầu.

Mental model:

```text
LINQ composition
   ↓
Expression tree
   ↓ terminal operator
EF Core translation
   ↓
SQL execution
   ↓
Materialization
```

Đây là execution boundary: trước boundary là query definition; sau boundary là in-memory objects.

## 2. Why does it exist?

Deferred execution cho phép compose filter/sort/projection trước khi database round-trip xảy ra. Nhưng nó cũng dễ tạo bug nếu developer không để ý nơi query chuyển từ server-side sang client-side.

Một `ToListAsync()` đặt quá sớm có thể kéo hàng trăm nghìn rows về memory rồi mới filter.

## 3. How does it work?

Ví dụ tốt:

```csharp
var query = db.Orders.AsNoTracking();

if (status is not null)
    query = query.Where(x => x.Status == status);

var result = await query
    .OrderByDescending(x => x.CreatedAt)
    .Select(x => new OrderDto(x.Id, x.Number, x.Total))
    .Take(100)
    .ToListAsync(cancellationToken);
```

Filter, sort, projection và `TOP` được đẩy xuống SQL nếu provider dịch được.

Ví dụ xấu:

```csharp
var orders = await db.Orders.ToListAsync(cancellationToken);
var active = orders.Where(x => x.Status == OrderStatus.Active).Take(100);
```

Ở đây database đã trả toàn bộ bảng trước filter.

## 4. Practical implementation

Một repository/application query nên tránh trả `IQueryable` ra khỏi persistence boundary nếu caller có thể compose query tùy ý và vô tình phụ thuộc EF implementation. Nhưng cũng không nên ép mọi query qua generic repository đầy abstraction.

Một domain-specific query service có thể giữ execution boundary rõ:

```csharp
public Task<List<OrderListItem>> SearchAsync(
    OrderSearch filter,
    CancellationToken ct)
{
    return _db.Orders
        .AsNoTracking()
        .Where(x => filter.Status == null || x.Status == filter.Status)
        .Where(x => filter.From == null || x.CreatedAt >= filter.From)
        .OrderByDescending(x => x.CreatedAt)
        .Select(x => new OrderListItem(x.Id, x.Number, x.Total))
        .Take(filter.Limit)
        .ToListAsync(ct);
}
```

## 5. Real production scenario

Một API search employee records chạy tốt với 5.000 rows. Sau hai năm có 2 triệu rows, latency tăng lên 8 giây và instance memory spike.

Code review phát hiện `ToListAsync()` được gọi trước filtering vì developer cần dùng một helper C# không translate được. SQL chỉ là `SELECT * FROM Employees`.

Fix bằng cách đẩy filter có thể translate xuống SQL trước, sau đó chỉ chạy helper trên result set nhỏ.

## 6. Failure scenario & troubleshooting

**Symptom** → database network bytes và application memory tăng mạnh nhưng SQL syntax nhìn đơn giản.

**Evidence** → generated SQL không có expected `WHERE`/`TOP`; trace cho thấy số rows returned cực lớn.

**Hypothesis** → execution boundary đặt quá sớm.

**Diagnosis** → dùng `ToQueryString()`, query logging, profiler và inspect LINQ chain.

**Fix** → compose server-translatable predicates/projection trước materialization. Nếu logic không translate được, thu nhỏ candidate set trước.

**Verification** → so logical reads, returned row count, allocations và p95 latency.

## 7. Common mistakes

* `ToListAsync()` sớm rồi mới filter/sort.
* Chuyển sang `AsEnumerable()` để “fix translation error” mà không đo data volume.
* Trả entity đầy đủ khi API chỉ cần 5 columns.
* Gọi query nhiều lần do enumerate `IQueryable` nhiều lần.
* Trả `IQueryable` qua nhiều architectural layer làm persistence details leak.

## 8. Alternatives

* Direct `DbContext` + projection: đơn giản và rõ cho nhiều application.
* Domain-specific repository/query object: hữu ích khi query semantics cần encapsulation.
* Dapper/raw SQL: hợp lý cho read query cực phức tạp hoặc cần kiểm soát SQL tuyệt đối.

## 9. Trade-offs

### Advantages

Deferred execution giúp compose query linh hoạt và đẩy work xuống database.

### Costs / Risks

Execution boundary không rõ có thể gây accidental full-table reads, multiple execution hoặc persistence leakage.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết LINQ trên `IQueryable` chưa chắc đã chạy ngay.

### Middle

Biết xem generated SQL, projection và đặt terminal operator đúng chỗ.

### Senior

Đánh giá translation, round-trip, materialization, index interaction và client/server execution boundary.

### Technical Lead / Architect

Quyết định query abstraction đủ đơn giản nhưng vẫn giữ ownership rõ; không dùng generic repository chỉ để che `DbContext` theo thói quen.

## 11. Key takeaway

* `ToListAsync()` là architectural/performance boundary, không chỉ là syntax.
* Hãy nhìn SQL thực tế và số rows thực tế.
* Projection + late materialization thường là default tốt cho read API.

# 4. SQL Server deadlocks: đọc wait-for cycle, chuẩn hóa lock order và retry đúng chỗ

## 1. What is it?

Deadlock xảy ra khi hai hoặc nhiều transactions giữ lock mà transaction kia cần, tạo thành vòng chờ không thể tự giải quyết.

Mental model:

```text
Transaction A: holds Row 1 → waits Row 2
Transaction B: holds Row 2 → waits Row 1

A waits B
↑       ↓
└───────┘
```

SQL Server deadlock monitor chọn một victim, rollback transaction đó và trả error 1205 để phá vòng.

## 2. Why does it exist?

Locking bảo vệ consistency. Khi transactions truy cập resources theo thứ tự khác nhau, concurrency có thể tạo cycle.

Không có deadlock detection, transactions có thể chờ vô hạn. Deadlock victim selection là cơ chế phục hồi, không phải dấu hiệu database “bị hỏng”.

## 3. How does it work?

Ví dụ:

Transaction A:

```sql
BEGIN TRAN;
UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1;
UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 2;
COMMIT;
```

Transaction B đồng thời update Id 2 rồi Id 1. Nếu timing phù hợp, hai transaction khóa chéo.

Deadlock graph cho biết:

* processes;
* resources;
* lock mode;
* owner;
* waiter;
* victim.

Senior engineer đọc graph thay vì đoán “thêm index là xong”.

## 4. Practical implementation

Chuẩn hóa lock order:

```csharp
var orderedIds = new[] { fromAccountId, toAccountId }
    .OrderBy(x => x)
    .ToArray();

await using var tx = await db.Database.BeginTransactionAsync(ct);

var accounts = await db.Accounts
    .Where(x => orderedIds.Contains(x.Id))
    .OrderBy(x => x.Id)
    .ToListAsync(ct);

// apply deterministic updates
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Retry có thể phù hợp với deadlock victim nếu transaction idempotent/re-executable:

```text
1205 → short randomized backoff → retry whole transaction
```

Không retry từng SQL statement trong một transaction đã rollback context/state mơ hồ.

## 5. Real production scenario

Order approval flow update `Orders` rồi `Inventory`. Reconciliation worker lại update `Inventory` rồi `Orders`. Dưới load cuối tháng, deadlock tăng mạnh.

Root cause không phải “SQL Server yếu” mà là inconsistent resource access order giữa hai workflows.

## 6. Failure scenario & troubleshooting

**Symptom** → sporadic error 1205, thường chỉ xuất hiện khi traffic cao.

**Evidence** → Extended Events deadlock graph cho thấy hai statements và lock cycle.

**Hypothesis** → transactions chạm cùng resources theo thứ tự khác nhau hoặc range lock rộng.

**Diagnosis** → đọc graph, execution plans, transaction duration và indexes. Xác định resource thật: key/page/index/range.

**Fix** → canonical lock order, thu nhỏ transaction, cải thiện access path/index nếu scan mở rộng lock footprint, retry victim an toàn.

**Verification** → concurrency test + monitor deadlocks/hour và transaction latency.

## 7. Common mistakes

* Chỉ tăng command timeout.
* `WITH (NOLOCK)` như “fix deadlock”.
* Retry vô hạn không jitter.
* Giữ transaction qua external API call.
* Update cùng entities theo random order từ dictionary/list.
* Không capture deadlock graph.

## 8. Alternatives

* Optimistic concurrency giảm một số lock contention nhưng giải bài toán khác.
* Snapshot-based isolation có thể giảm reader/writer blocking nhưng không xóa mọi writer deadlock.
* Queue/serialization theo aggregate key có thể phù hợp khi business chấp nhận giảm concurrency.

## 9. Trade-offs

### Advantages

Locking cung cấp strong transactional consistency.

### Costs / Risks

Transactions dài, access order không thống nhất và scan lớn làm contention/deadlock probability tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deadlock là vòng chờ, khác query timeout thông thường.

### Middle

Biết thu thập deadlock graph và nhận diện victim/resources.

### Senior

Thiết kế lock order, transaction boundary và retry strategy dựa trên idempotency.

### Technical Lead / Architect

Xem deadlock như feedback về workflow/data ownership; quyết định khi nào cần serialize work, đổi transaction boundary hoặc thay interaction pattern.

## 11. Key takeaway

* Đừng đoán deadlock: đọc deadlock graph.
* Canonical access order thường hiệu quả hơn tăng timeout.
* Retry chỉ an toàn khi retry toàn business transaction với semantics rõ.

# 5. Redis eviction dưới memory pressure: cache miss storm, hot key và khi Redis trở thành dependency critical ngoài ý muốn

## 1. What is it?

Redis giữ dữ liệu trong memory. Khi chạm `maxmemory`, behavior phụ thuộc eviction policy: Redis có thể từ chối write hoặc evict keys theo policy như LRU/LFU/TTL-related variants.

Mental model:

```text
Memory grows
   ↓ reaches maxmemory
Eviction policy
   ├─ remove keys
   └─ reject write
        ↓
Cache hit ratio changes
        ↓
Origin DB/API load changes
```

Eviction không chỉ là “Redis tự dọn memory”; nó có thể thay đổi load profile toàn hệ thống.

## 2. Why does it exist?

Memory hữu hạn. Cache cần policy quyết định dữ liệu nào hy sinh khi capacity hết.

Nếu không hiểu policy, team có thể thấy database bỗng tăng CPU dù deploy application không thay đổi: Redis đang evict hot data, tạo cache misses và origin load.

## 3. How does it work?

Các policy thường gặp conceptually:

* `noeviction`: write mới fail khi vượt memory.
* LRU-like: ưu tiên evict key ít dùng gần đây.
* LFU-like: ưu tiên key ít thường xuyên.
* TTL-based: chỉ/ưu tiên keys có expiration tùy policy.

Redis implementation dùng sampling/approximation cho efficiency, không phải exact global LRU queue.

Hot key còn có thể tạo bottleneck dù tổng memory ổn: một key được đọc hàng chục nghìn lần/giây tập trung workload vào một shard/node.

## 4. Practical implementation

Cache-aside cần failure path rõ:

```csharp
public async Task<ProductDto?> GetAsync(Guid id, CancellationToken ct)
{
    var key = $"product:{id}";

    try
    {
        var cached = await _cache.GetStringAsync(key, ct);
        if (cached is not null)
            return JsonSerializer.Deserialize<ProductDto>(cached);
    }
    catch (RedisException ex)
    {
        _logger.LogWarning(ex, "Redis read failed for {CacheKey}", key);
    }

    var product = await LoadFromDatabaseAsync(id, ct);

    if (product is not null)
    {
        try
        {
            await _cache.SetStringAsync(
                key,
                JsonSerializer.Serialize(product),
                new DistributedCacheEntryOptions
                {
                    AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
                },
                ct);
        }
        catch (RedisException ex)
        {
            _logger.LogWarning(ex, "Redis write failed for {CacheKey}", key);
        }
    }

    return product;
}
```

Nhưng fallback-to-DB chỉ an toàn nếu DB có capacity chịu cache outage. Nếu không, “graceful fallback” có thể làm DB sập.

## 5. Real production scenario

Product catalog dùng Redis với 20 GB maxmemory. Một release tăng serialized product size 3 lần vì thêm nested fields. Redis memory chạm limit, eviction rate tăng, hit ratio giảm từ 95% xuống 55%.

Database nhận gần gấp 9 lần số reads trước đó và p99 tăng mạnh. Root cause nhìn bên SQL nhưng bắt đầu từ cache object size và eviction.

## 6. Failure scenario & troubleshooting

**Symptom** → database CPU tăng, Redis latency vẫn “khá bình thường”.

**Evidence** → Redis `evicted_keys` tăng, hit ratio giảm, memory sát max, payload size tăng sau deploy.

**Hypothesis** → eviction-induced cache miss storm.

**Diagnosis** → correlate Redis memory/evictions/hit ratio với DB QPS và deploy timeline. Kiểm tra largest keys và serialization changes.

**Fix** → giảm payload, điều chỉnh TTL/policy/capacity, phân tách cache workload hoặc bỏ cache những object giá trị thấp.

**Verification** → eviction rate ổn định, hit ratio phục hồi, origin QPS trở lại baseline.

## 7. Common mistakes

* Chỉ monitor Redis CPU/latency mà không monitor hit ratio và evictions.
* Cache object quá lớn “vì memory rẻ”.
* Dùng cùng Redis cho session critical và best-effort cache mà không boundary rõ.
* TTL tất cả keys cùng thời điểm gây expiration wave.
* Fallback trực tiếp về DB không có capacity protection.

## 8. Alternatives

* `IMemoryCache`: đơn giản và nhanh nhưng không shared giữa instances.
* CDN/edge caching: phù hợp HTTP/public content.
* Không cache: đôi khi tốt hơn nếu origin đã đủ nhanh và consistency quan trọng.
* Dedicated Redis instances cho workloads có criticality khác nhau.

## 9. Trade-offs

### Advantages

* Giảm latency và origin load.
* Hỗ trợ distributed applications.

### Costs / Risks

* Invalidation/freshness complexity.
* Hidden capacity dependency.
* Eviction có thể chuyển load đột ngột xuống origin.
* Redis outage trở thành cascading failure nếu design sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết cache có capacity và keys có thể biến mất.

### Middle

Biết TTL, cache-aside, fallback và basic Redis metrics.

### Senior

Đánh giá eviction, hit ratio, payload size, hot keys và origin capacity.

### Technical Lead / Architect

Quyết định workload nào nên cache, cache nào critical, failure mode khi Redis mất hoàn toàn và liệu complexity có đáng với latency benefit không.

## 11. Key takeaway

* Eviction là system-level load redistribution event.
* Cache hit ratio quan trọng không kém Redis latency.
* Một cache chỉ “optional” nếu origin thật sự chịu được khi cache biến mất.

# 6. Hexagonal Architecture: Ports & Adapters để cô lập thay đổi, không phải để tạo thêm folder và interface

## 1. What is it?

Hexagonal Architecture tổ chức hệ thống quanh application/domain core và các **ports** mô tả cách core giao tiếp với bên ngoài. **Adapters** triển khai ports cho HTTP, database, messaging, file system hoặc third-party APIs.

Mental model:

```text
            HTTP Adapter
                 ↓
        [ Inbound Port ]
                 ↓
          Application Core
                 ↓
        [ Outbound Port ]
          ↙            ↘
   SQL Adapter      Vendor API Adapter
```

Mục tiêu là dependency direction và change isolation, không phải hình lục giác hay folder names.

## 2. Why does it exist?

Enterprise systems thay đổi infrastructure thường xuyên hơn business rules: SQL provider đổi, third-party API đổi, HTTP transport thêm queue consumer, test cần fake external service.

Nếu domain/application logic trực tiếp gọi SDK cụ thể ở khắp nơi, thay đổi infrastructure xuyên qua nhiều layers.

Ports tạo boundary nơi application nói bằng ngôn ngữ của use case, adapter chịu trách nhiệm dịch sang technology contract.

## 3. How does it work?

Ví dụ outbound port:

```csharp
public interface IPaymentGateway
{
    Task<PaymentResult> ChargeAsync(
        PaymentRequest request,
        CancellationToken cancellationToken);
}
```

Application phụ thuộc interface này. Stripe/Adyen adapter triển khai nó.

Dependency direction:

```text
Web API ───────► Application ◄────── Infrastructure implementation
                       │
                       ▼
                     Domain
```

Infrastructure phụ thuộc application contract, không để application phụ thuộc SDK vendor trực tiếp.

## 4. Practical implementation

```csharp
public sealed class CheckoutService
{
    private readonly IPaymentGateway _payments;
    private readonly IOrderRepository _orders;

    public CheckoutService(
        IPaymentGateway payments,
        IOrderRepository orders)
    {
        _payments = payments;
        _orders = orders;
    }

    public async Task CheckoutAsync(OrderId orderId, CancellationToken ct)
    {
        var order = await _orders.GetAsync(orderId, ct)
            ?? throw new InvalidOperationException("Order not found");

        order.ValidateReadyForPayment();

        var result = await _payments.ChargeAsync(
            new PaymentRequest(order.Id.Value, order.Total), ct);

        order.RecordPayment(result.Reference);
        await _orders.SaveAsync(order, ct);
    }
}
```

Adapter:

```csharp
public sealed class VendorPaymentGateway : IPaymentGateway
{
    private readonly VendorClient _client;

    public async Task<PaymentResult> ChargeAsync(
        PaymentRequest request,
        CancellationToken ct)
    {
        var response = await _client.CreateChargeAsync(..., ct);
        return new PaymentResult(response.Id);
    }
}
```

## 5. Real production scenario

Một automotive marketplace dùng một reviews provider. Sau hai năm vendor tăng giá và API contract đổi. Nếu `ReviewSdkClient` xuất hiện trong controllers, services, background jobs và domain code, migration rất rộng.

Nếu application có port `IReviewProvider`, adapter mới có thể được thay dần trong boundary đó. Tuy nhiên nếu abstraction chỉ mirror 1:1 toàn vendor API, lợi ích change isolation vẫn thấp.

## 6. Failure scenario & troubleshooting

**Symptom** → project có hàng trăm interfaces nhưng thay vendor vẫn sửa khắp hệ thống.

**Evidence** → port methods/DTOs mang nguyên tên field/status của vendor.

**Hypothesis** → abstraction là forwarding wrapper, không phải application boundary.

**Diagnosis** → xem domain/application có hiểu vendor-specific error codes, pagination token hoặc SDK types không.

**Fix** → thiết kế port theo business capability; mapping vendor-specific semantics trong adapter.

**Verification** → prototype adapter thứ hai; đo số file core phải thay.

## 7. Common mistakes

* Mọi class đều có interface dù không có boundary/change pressure.
* Repository interface chỉ mirror `DbSet` generic CRUD.
* Infrastructure DTO leak vào domain.
* Tạo 5 projects chỉ để thể hiện “clean architecture”.
* Domain event, MediatR và repository được dùng như checklist thay vì giải bài toán.

## 8. Alternatives

* Simple layered architecture tốt cho CRUD app nhỏ.
* Modular Monolith phù hợp khi cần business boundaries lớn hơn nhưng chưa cần independent deployment.
* Direct SDK usage có thể hợp lý trong một isolated adapter/service nhỏ nếu migration risk thấp.

## 9. Trade-offs

### Advantages

* Change isolation.
* Testability ở boundary.
* Domain/application ít phụ thuộc technology/vendor.

### Costs / Risks

* Thêm mapping và abstraction.
* Overengineering nếu domain đơn giản.
* Wrong abstraction có thể tệ hơn direct dependency vì che giấu semantics quan trọng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu port là contract của core; adapter là implementation cho technology bên ngoài.

### Middle

Biết đặt dependency direction và mapping DTO/vendor types tại adapter boundary.

### Senior

Đánh giá abstraction quality, transaction boundary, failure semantics và test strategy.

### Technical Lead / Architect

Quyết định boundary nào đáng bảo vệ khỏi change. Một quyết định senior hợp lệ là **không tạo port** nếu dependency nhỏ, ổn định và abstraction không mang giá trị.

## 11. Key takeaway

* Hexagonal Architecture nói về dependency direction và change isolation.
* Port nên diễn đạt capability của application, không mirror vendor SDK.
* Abstraction chỉ đáng tồn tại khi nó giảm coupling thực tế.

# 7. Saga Pattern: consistency giữa nhiều service bằng local transaction + compensation thay vì distributed transaction

## 1. What is it?

Saga là chuỗi local transactions trên nhiều service/bounded contexts. Mỗi bước commit độc lập. Nếu bước sau thất bại, hệ thống chạy compensating actions để đưa business state về trạng thái chấp nhận được.

Mental model:

```text
Create Order
   ↓
Reserve Inventory
   ↓
Authorize Payment
   ↓
Confirm Order

Nếu Payment fail:
Release Inventory
Cancel Order
```

Saga không cung cấp ACID transaction xuyên toàn hệ thống. Nó quản lý **eventual consistency + business compensation**.

## 2. Why does it exist?

Trong microservices, mỗi service sở hữu database riêng. Distributed transaction/2PC thường khó hoặc không được hỗ trợ bởi cloud messaging/datastores, đồng thời làm availability/coupling xấu hơn.

Business vẫn cần workflow nhiều bước. Saga chấp nhận intermediate states và định nghĩa cách phục hồi.

## 3. How does it work?

Có hai coordination style:

**Orchestration**

```text
Saga Orchestrator
 → Inventory Reserve
 → Payment Authorize
 → Order Confirm
```

Orchestrator giữ workflow state và quyết định next/compensation step.

**Choreography**

```text
OrderCreated event
 → Inventory reacts
 → InventoryReserved event
 → Payment reacts
 → PaymentAuthorized event
```

Choreography giảm central coordinator nhưng dễ tạo implicit workflow khó quan sát khi chain dài.

Mỗi consumer phải idempotent vì message delivery thường at-least-once.

## 4. Practical implementation

Một saga state đơn giản:

```csharp
public sealed record CheckoutSagaState(
    Guid OrderId,
    bool InventoryReserved,
    bool PaymentAuthorized,
    CheckoutStatus Status);
```

Pseudo-near-production orchestration handler:

```csharp
try
{
    await inventory.ReserveAsync(orderId, ct);
    state.InventoryReserved = true;

    await payment.AuthorizeAsync(orderId, ct);
    state.PaymentAuthorized = true;

    await orders.ConfirmAsync(orderId, ct);
}
catch
{
    if (state.PaymentAuthorized)
        await payment.VoidAsync(orderId, ct);

    if (state.InventoryReserved)
        await inventory.ReleaseAsync(orderId, ct);

    await orders.CancelAsync(orderId, ct);
    throw;
}
```

Thực tế state phải persisted, steps idempotent, retries durable và crash recovery được xử lý qua message infrastructure/workflow engine chứ không chỉ `try/catch` trong một process.

## 5. Real production scenario

Checkout cần Order, Inventory, Payment. Payment provider timeout sau khi đã authorize nhưng trước khi caller nhận response.

Nếu application đơn giản retry authorize, customer có thể bị charge hai lần. Saga cần idempotency key ở payment boundary và reconciliation state để xác định payment đã xảy ra chưa trước compensation/retry.

## 6. Failure scenario & troubleshooting

**Symptom** → order ở trạng thái `PendingPayment` hàng giờ; inventory vẫn reserved.

**Evidence** → traces/message logs cho thấy PaymentAuthorized event có nhưng saga state chưa advance vì consumer crash.

**Hypothesis** → durable coordination/idempotent resume thiếu.

**Diagnosis** → inspect saga state, inbox/outbox records, message delivery attempts và correlation ID.

**Fix** → persist workflow state, idempotent step handlers, retry policy và manual reconciliation path cho stuck saga.

**Verification** → kill process giữa từng step trong integration test và xác nhận saga resume/compensate đúng.

## 7. Common mistakes

* Gọi nhiều service bằng HTTP trong một DB transaction và nghĩ đó là atomic.
* Compensation được hiểu là “rollback kỹ thuật”; thực tế có thể là refund, release, cancel.
* Không thiết kế intermediate states trong domain/UI.
* Không có idempotency.
* Choreography quá dài làm business flow bị ẩn trong hàng chục consumers.

## 8. Alternatives

* Single database transaction: tốt nhất khi boundaries thực sự thuộc một service/module.
* Modular Monolith: thường đơn giản hơn microservices + saga nếu independent deployment chưa cần.
* 2PC/distributed transaction: có niche cases nhưng tăng coupling/availability constraints.

## 9. Trade-offs

### Advantages

* Không cần global ACID transaction.
* Cho phép independent service/data ownership.
* Resilient hơn với partial failure nếu thiết kế đúng.

### Costs / Risks

* Eventual consistency.
* Compensation phức tạp.
* Debug/reconciliation khó.
* Nhiều intermediate states và operational tooling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu saga là nhiều local transactions + compensation.

### Middle

Biết correlation, idempotent handlers, retries và persisted workflow state.

### Senior

Thiết kế compensation semantics, crash recovery, observability và stuck-state reconciliation.

### Technical Lead / Architect

Trước khi chọn Saga, hỏi liệu các operations có thật sự cần nằm ở các services riêng. Nếu một transaction local giải quyết được, microservice split có thể chưa đáng complexity.

## 11. Key takeaway

* Saga không tạo ACID xuyên services; nó quản lý eventual consistency.
* Compensation là business action, không phải database rollback.
* Durable state + idempotency + observability là bắt buộc cho production saga.

# 8. Azure Functions queue-trigger processing: scale-out, retry, poison message và idempotency trong thực tế

## 1. What is it?

Azure Functions queue-trigger model cho phép function instances nhận messages/events và scale processing theo backlog/load. Developer viết handler; platform quản lý host lifecycle và scale ở mức lớn.

Mental model:

```text
Producer → Queue → Function instances
                   ├─ message A
                   ├─ message B
                   └─ message C
                         ↓
                    dependency/DB
```

Đây không phải “exactly once background job”. Duplicate delivery, retry và partial failure phải được coi là bình thường.

## 2. Why does it exist?

Background work như image processing, notifications, imports hoặc integrations không nên giữ HTTP request mở. Queue decouples producer khỏi processing latency và cho phép consumers scale độc lập.

Azure Functions giảm operational burden so với tự quản lý worker hosts trong nhiều workload bursty.

## 3. How does it work?

Flow điển hình:

1. producer enqueue message;
2. Function host nhận/lock message;
3. handler chạy;
4. success → message được settle/delete;
5. failure → message retry;
6. quá số attempts → poison/dead-letter path tùy queue technology/configuration.

Scale-out nghĩa nhiều instances có thể chạy đồng thời. Ordering không mặc định được đảm bảo cho mọi loại queue/workload.

## 4. Practical implementation

Ví dụ idempotent consumer bằng processed-message table:

```csharp
public async Task HandleAsync(OrderCreated message, CancellationToken ct)
{
    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    var exists = await _db.ProcessedMessages
        .AnyAsync(x => x.MessageId == message.MessageId, ct);

    if (exists)
        return;

    await _notificationSender.SendOrderConfirmationAsync(
        message.OrderId,
        ct);

    _db.ProcessedMessages.Add(new ProcessedMessage
    {
        MessageId = message.MessageId,
        ProcessedAt = DateTimeOffset.UtcNow
    });

    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
```

Cần lưu ý: nếu `SendOrderConfirmationAsync` là external side effect rồi DB commit fail, duplicate vẫn có thể xảy ra. Với side effect quan trọng, cần provider idempotency key hoặc Outbox/Inbox workflow phù hợp.

## 5. Real production scenario

Marketplace nhận 500.000 product-image jobs sau nightly import. Queue backlog tăng, Functions scale từ 2 lên 40 instances.

Storage và downstream image API không chịu được 40× concurrency, bắt đầu throttle. Nếu retry ngay lập tức, retry storm làm tình hình tệ hơn.

Scale consumer phải gắn với downstream capacity, không chỉ queue depth.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog không giảm dù instance count tăng; dependency 429/timeout tăng.

**Evidence** → retries/message age tăng, dependency throttle metrics tăng theo scale-out.

**Hypothesis** → consumer scale vượt downstream capacity.

**Diagnosis** → correlate function concurrency, processing duration, dependency limits, retry count và oldest message age.

**Fix** → giới hạn concurrency, exponential backoff + jitter, batch size phù hợp, downstream quota/capacity planning, dead-letter poison payloads.

**Verification** → backlog drain rate ổn định mà dependency error rate không tăng.

## 7. Common mistakes

* Nghĩ queue trigger là exactly-once.
* Handler không idempotent.
* Retry mọi exception giống nhau, kể cả validation error vĩnh viễn.
* Không có poison/dead-letter workflow.
* Scale theo backlog mà không nhìn dependency capacity/cost.
* Timer-trigger cho work cần queue semantics và retry durability.

## 8. Alternatives

* Worker Service/Container Apps: phù hợp khi cần process control, long-running workers hoặc stable throughput.
* Azure Service Bus + dedicated worker: nhiều control hơn về sessions, settlement, ordering.
* Logic Apps: phù hợp integration workflow low-code, không phải compute-heavy processing.

## 9. Trade-offs

### Advantages

* Elastic scale.
* Operational setup nhẹ cho event-driven work.
* Tốt cho bursty workloads.

### Costs / Risks

* Retry/duplicate semantics cần thiết kế.
* Cold start/runtime constraints tùy hosting plan.
* Scale có thể khuếch đại downstream overload và cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue decouples producer/consumer và message có thể retry.

### Middle

Biết idempotent handler, cancellation, poison message và logging correlation.

### Senior

Đánh giá concurrency, retry storm, dependency quotas, message age và cost.

### Technical Lead / Architect

Chọn Functions hay Worker/Container Apps dựa trên workload shape, runtime control, throughput, failure semantics và operational ownership.

## 11. Key takeaway

* Queue-trigger processing phải giả định duplicate delivery.
* Scale-out không có nghĩa downstream cũng scale được.
* Retry, poison handling và idempotency là phần của business reliability design.

# 9. Blue-Green deployment + database expand-contract: deploy không downtime chỉ khi schema tương thích hai chiều trong rollout window

## 1. What is it?

Blue-Green deployment duy trì hai application environments/versions: một đang phục vụ traffic và một chứa version mới. Sau validation, traffic được switch sang version mới.

Nhưng database thường được share. Vì vậy zero-downtime application switch chỉ an toàn nếu cả old và new version tương thích với schema trong rollout window.

Mental model:

```text
Blue v1 ─┐
         ├── Shared DB schema compatible with v1 + v2
Green v2 ┘

After Green stable:
contract old schema later
```

## 2. Why does it exist?

Nếu deploy in-place, lỗi startup hoặc regression có thể tạo downtime. Blue-Green cho pre-warm, health validation và fast traffic rollback.

Nhưng nhiều team nhầm rằng có deployment slot là đủ. Một migration `DROP COLUMN` trước khi traffic switch có thể làm Blue v1 crash ngay, phá rollback.

## 3. How does it work?

Expand-contract chia schema migration thành phases.

**Expand**

* thêm nullable/new column/table/index;
* deploy code có thể làm việc với old + new shape;
* backfill nếu cần.

**Transition**

* deploy new version;
* có thể dual-read/dual-write trong window ngắn;
* validate data.

**Contract**

* khi không còn old version consumer, remove old column/constraint/code path.

## 4. Practical implementation

Giả sử đổi `FullName` thành `FirstName` + `LastName`.

Không nên:

```sql
ALTER TABLE Customers DROP COLUMN FullName;
ALTER TABLE Customers ADD FirstName nvarchar(100) NOT NULL;
ALTER TABLE Customers ADD LastName nvarchar(100) NOT NULL;
```

Trong một release duy nhất.

Expand:

```sql
ALTER TABLE Customers ADD FirstName nvarchar(100) NULL;
ALTER TABLE Customers ADD LastName nvarchar(100) NULL;
```

Deploy v2 hỗ trợ fallback:

```csharp
var displayName = !string.IsNullOrWhiteSpace(customer.FirstName)
    ? $"{customer.FirstName} {customer.LastName}".Trim()
    : customer.FullName;
```

Backfill và chỉ drop `FullName` ở release sau khi metrics chứng minh v1 không còn chạy.

## 5. Real production scenario

App Service dùng deployment slots. Green deploy pass health check. Migration đã rename column trực tiếp. Blue đang phục vụ request trong lúc migration chạy và bắt đầu lỗi SQL “invalid column name”.

Traffic chưa hề swap nhưng production đã outage. Root cause là database migration không backward-compatible.

## 6. Failure scenario & troubleshooting

**Symptom** → rollback application version xong nhưng lỗi vẫn tiếp tục.

**Evidence** → schema đã destructive change; old binary không tương thích.

**Hypothesis** → rollback path chỉ tính application artifact, bỏ qua database.

**Diagnosis** → compare migration history, old/new ORM models và schema contract.

**Fix** → restore compatibility bằng additive migration; áp dụng expand-contract trong future releases.

**Verification** → staging test chạy v1 và v2 đồng thời trên expanded schema, rồi test rollback traffic.

## 7. Common mistakes

* Rename/drop column trong cùng release với code change.
* Auto-run destructive migration khi app startup trên nhiều instances.
* Blue-Green nhưng cả hai versions không cùng tương thích schema.
* Không test rollback sau migration.
* Giữ dual-write mãi mãi, tạo permanent complexity.

## 8. Alternatives

* Rolling deployment vẫn cần backward compatibility tương tự vì old/new pods cùng tồn tại.
* Canary deployment cần compatibility còn rõ hơn do traffic split kéo dài.
* Maintenance window có thể đơn giản hơn cho internal system nhỏ nếu downtime được business chấp nhận.

## 9. Trade-offs

### Advantages

* Fast traffic rollback.
* Pre-deployment validation.
* Giảm downtime risk.

### Costs / Risks

* Tốn duplicate environment/capacity.
* Database migration phức tạp hơn.
* Temporary compatibility code và backfill cần quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Blue và Green là hai app versions, nhưng database có thể vẫn là shared dependency.

### Middle

Biết additive migration, health check và rollback traffic.

### Senior

Thiết kế expand-contract, backfill, compatibility window và migration observability.

### Technical Lead / Architect

Quyết định release strategy theo business downtime tolerance, schema change risk và operational maturity. Zero downtime không phải mục tiêu miễn phí.

## 11. Key takeaway

* Blue-Green không bảo vệ bạn khỏi destructive DB migration.
* Schema phải tương thích với old và new binaries trong rollout window.
* Rollback plan phải bao gồm data/schema state, không chỉ application artifact.

# 10. SSRF trong URL-fetching API: validation URL chưa đủ nếu application có thể chạm vào network nội bộ

## 1. What is it?

SSRF — Server-Side Request Forgery — xảy ra khi attacker khiến server thực hiện network request tới destination mà attacker không được phép truy cập trực tiếp.

Ví dụ endpoint:

```http
POST /api/import-image
{
  "url": "https://example.com/image.jpg"
}
```

Nếu server fetch URL tùy ý, attacker có thể thử internal services, loopback, private IP, cloud metadata endpoint hoặc redirect chain.

Mental model:

```text
Attacker
   ↓ supplies URL
Public API
   ↓ server-side HTTP request
Internal network / metadata / admin service
```

## 2. Why does it exist?

Server thường có network privilege lớn hơn client: private DNS, VNet access, Managed Identity environment và internal APIs.

Một chức năng tưởng đơn giản như “import image by URL”, “generate preview”, “webhook tester” hoặc “PDF from URL” vô tình trở thành network proxy với trust level của server.

## 3. How does it work?

Validation chỉ kiểm tra string như `StartsWith("https://")` là không đủ.

Attack paths gồm:

* hostname resolve thành private IP;
* DNS rebinding;
* redirects từ public host sang private target;
* IPv6/alternative IP representations;
* credentials hoặc unusual schemes nếu client hỗ trợ;
* access tới internal HTTP services không có auth vì dựa vào network trust.

Defense cần nhiều lớp: destination policy, DNS/IP validation, redirect control, network egress restriction và timeout/size limits.

## 4. Practical implementation

Application-level allowlist nếu business có tập domains xác định:

```csharp
private static readonly HashSet<string> AllowedHosts =
    new(StringComparer.OrdinalIgnoreCase)
    {
        "images.partner-a.com",
        "cdn.partner-b.com"
    };

public static Uri ValidateExternalUrl(string input)
{
    if (!Uri.TryCreate(input, UriKind.Absolute, out var uri))
        throw new ValidationException("Invalid URL");

    if (uri.Scheme != Uri.UriSchemeHttps)
        throw new ValidationException("HTTPS required");

    if (!AllowedHosts.Contains(uri.Host))
        throw new ValidationException("Host is not allowed");

    return uri;
}
```

Ngoài code, production nên kiểm soát egress ở network layer nếu threat model yêu cầu: proxy/Firewall rules, deny private address ranges hoặc dedicated fetch service với quyền tối thiểu.

`HttpClient` cũng cần:

* timeout;
* response size limit;
* content-type validation;
* redirect policy;
* cancellation.

## 5. Real production scenario

CMS cho editor nhập URL để tải image từ website bên ngoài. Endpoint chạy trong App Service có VNet integration và truy cập internal admin APIs.

Attacker chiếm account editor thấp quyền và nhập URL trỏ tới internal service. Nếu internal service dựa vào private-network trust, attacker có thể đọc dữ liệu mà browser bên ngoài không chạm tới.

## 6. Failure scenario & troubleshooting

**Symptom** → logs cho thấy image-import endpoint gọi IP nội bộ hoặc metadata-like destinations.

**Evidence** → request URL ban đầu là domain public nhưng final redirect destination là private IP.

**Hypothesis** → validation chỉ chạy trước redirect hoặc chỉ kiểm hostname string.

**Diagnosis** → trace DNS resolution, redirect chain, final destination và network flow logs.

**Fix** → allowlist host, disable/validate redirects, reject private/link-local/loopback resolutions, giới hạn egress network và isolate fetcher.

**Verification** → security tests với localhost, RFC1918 ranges, IPv6 loopback, redirect-to-private và DNS rebinding scenarios.

## 7. Common mistakes

* Chỉ kiểm `https://`.
* Block literal `127.0.0.1` nhưng cho hostname resolve về loopback.
* Cho automatic redirects mà không re-validate destination.
* Tin rằng internal service không cần authentication vì “chỉ VNet truy cập được”.
* Fetch response không giới hạn size, tạo memory/bandwidth DoS.
* Log full URL chứa secrets/query tokens.

## 8. Alternatives

* Chỉ cho upload file trực tiếp thay vì URL fetch.
* Predefined partner integrations thay vì arbitrary URLs.
* Dedicated network-isolated fetch service/proxy.
* Object-storage presigned upload flow nếu mục tiêu chỉ là nhận file từ client.

## 9. Trade-offs

### Advantages

URL-fetching tạo UX tiện và giảm client upload burden.

### Costs / Risks

Nó mở network capability của server cho untrusted input, tăng attack surface, egress cost và DoS risk.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu input URL có thể khiến server truy cập nơi client không truy cập được.

### Middle

Biết validate scheme/host, timeout, size, redirects và content type.

### Senior

Xử lý DNS/IP resolution, redirect chain, egress policy, cloud metadata/internal API threat model.

### Technical Lead / Architect

Quyết định có nên cho arbitrary URL fetch hay không. Với hệ thống nhạy cảm, một dedicated low-privilege fetch boundary có thể an toàn hơn nhiều so với thêm validation vào main application.

## 11. Key takeaway

* SSRF là vấn đề network trust, không chỉ URL parsing.
* Allowlist + redirect validation + egress control mạnh hơn blacklist string.
* Internal services vẫn cần authentication/authorization; private network không phải security boundary duy nhất.
