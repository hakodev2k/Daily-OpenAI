# 1. C# `Span<T>` và `Memory<T>`: giảm allocation mà không phá lifetime safety

## 1. What is it?

Mental model: `Span<T>` là một view liên tục lên vùng memory đã tồn tại; nó không sở hữu dữ liệu. Nó có thể trỏ vào array, stack memory hoặc slice của buffer mà không cần tạo array/string mới. Vì `Span<T>` là `ref struct`, compiler/CLR giới hạn lifetime để nó không thoát sang heap theo cách có thể tham chiếu memory đã hết hạn. `Memory<T>` là counterpart có thể sống trên heap và đi qua async boundary.

## 2. Why does it exist?

Parsing protocol, serialization và text processing thường tạo nhiều temporary arrays/strings chỉ để đọc một đoạn dữ liệu. Allocation tăng GC pressure. Copy cũng tốn CPU/memory bandwidth. View cho phép xử lý trực tiếp buffer gốc.

## 3. How does it work?

```text
byte[] buffer
[0 1 2 3 4 5 6 7]
     |-----|
       Span slice
```

Slice giữ reference + offset/length, không copy payload. `ReadOnlySpan<T>` biểu diễn read-only view. `Memory<T>` có thể được lưu và dùng với async APIs; khi cần synchronous processing có thể lấy `.Span`.

## 4. Practical implementation

```csharp
static bool TryReadHeader(ReadOnlySpan<byte> data, out ushort type)
{
    if (data.Length < 2)
    {
        type = 0;
        return false;
    }

    type = System.Buffers.Binary.BinaryPrimitives.ReadUInt16BigEndian(data);
    return true;
}
```

Không cần `data.Take(2).ToArray()`. Với async I/O, nhận `Memory<byte>`:

```csharp
var buffer = new byte[4096];
var read = await stream.ReadAsync(buffer.AsMemory(), ct);
Process(buffer.AsSpan(0, read));
```

## 5. Real production scenario

Gateway parse hàng chục nghìn payload/giây. Implementation cũ dùng `Substring`/`ToArray` cho từng field, tạo Gen0 allocation lớn. Chuyển hot parsing path sang spans giảm temporary allocations mà không thay business semantics.

## 6. Failure scenario & troubleshooting

**Symptom** → optimization compile không được qua `await`, hoặc code trở nên phức tạp nhưng allocation không giảm đáng kể. **Evidence** → compiler báo ref-struct lifetime violation; profiler cho thấy allocations nằm ở JSON/domain mapping chứ không ở slicing. **Hypothesis** → chọn sai hot path. **Diagnosis** → đo allocation profile trước. **Fix** → dùng `Memory<T>` qua async boundary hoặc giữ code đơn giản nếu allocation không đáng kể. **Verification** → benchmark + allocation counters.

## 7. Common mistakes

Dùng Span ở mọi nơi vì “nhanh”; cố giữ `Span<T>` trong field của class; benchmark micro-operation nhưng bỏ qua end-to-end cost; dùng `stackalloc` kích thước không kiểm soát; tối ưu trước khi profiler chỉ ra allocation bottleneck.

## 8. Alternatives

Array/string bình thường thường rõ ràng hơn và đủ nhanh. `ArrayPool<T>` phù hợp khi cần reusable owned buffer lớn. `Memory<T>` phù hợp lifetime dài/async.

## 9. Trade-offs

### Advantages
Giảm allocation/copy ở hot path, hỗ trợ high-performance APIs.

### Costs / Risks
Lifetime rules phức tạp hơn, code dễ khó đọc và lợi ích nhỏ nếu workload không allocation-sensitive.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu view khác copy và object ownership.
### Middle
Dùng `ReadOnlySpan<T>` cho parsing có benchmark.
### Senior
Đọc allocation profile, hiểu lifetime/ref-safety và pool interactions.
### Technical Lead / Architect
Quyết định nơi performance complexity đáng chi phí maintainability.

## 11. Key takeaway

- `Span<T>` là view, không phải owner.
- Dùng `Memory<T>` khi cần vượt async/heap boundary.
- Chỉ đưa complexity này vào nơi measurement chứng minh allocation/copy là bottleneck.

# 2. ASP.NET Core graceful shutdown: hoàn tất in-flight work

## 1. What is it?

Graceful shutdown là quá trình instance ngừng nhận work mới, cho work đang chạy thời gian hoàn tất, rồi dispose resources và dừng process. Nó đặc biệt quan trọng khi deploy, autoscale hoặc orchestrator terminate container.

## 2. Why does it exist?

Process termination không phải sự kiện hiếm: rolling deployment, node maintenance, App Service recycle và Kubernetes rescheduling đều có thể dừng instance. Nếu process bị cắt ngay, request đang commit payment hoặc consumer đang xử lý message có thể bị bỏ giữa chừng.

## 3. How does it work?

```text
termination signal
 -> stop accepting new work
 -> ApplicationStopping cancellation
 -> drain in-flight requests/background loops
 -> dispose resources
 -> process exits
```

Grace period hữu hạn; shutdown không đảm bảo mọi operation sẽ hoàn thành.

## 4. Practical implementation

Background worker phải tôn trọng cancellation:

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        var item = await queue.ReceiveAsync(stoppingToken);
        await ProcessAsync(item, stoppingToken);
    }
}
```

Không bắt `OperationCanceledException` rồi tiếp tục loop vô hạn. Với message broker, settlement chỉ xảy ra sau khi side effect an toàn.

## 5. Real production scenario

Rolling deployment thay 10 API pods. Một pod đang upload metadata và ghi DB. Readiness được hạ trước termination nên traffic mới đi sang pods khác; request hiện tại có cửa sổ hoàn tất trước khi process exit.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment tạo burst 499/5xx hoặc duplicate message. **Evidence** → failures trùng pod termination; traces kết thúc đột ngột. **Hypothesis** → grace period nhỏ hoặc app không propagate cancellation/drain. **Diagnosis** → timeline ingress/readiness/process logs. **Fix** → shutdown coordination, bounded operation, idempotency. **Verification** → load test trong rolling restart.

## 7. Common mistakes

Readiness vẫn true đến giây cuối; background task bỏ qua cancellation; operation dài hơn termination grace period; coi graceful shutdown là exactly-once guarantee; bắt cancellation như application error.

## 8. Alternatives

Durable queue phù hợp long-running work. Request path nên enqueue nếu operation không thể hoàn thành trong bounded HTTP lifecycle.

## 9. Trade-offs

### Advantages
Giảm dropped work và deployment disruption.
### Costs / Risks
Deploy chậm hơn; vẫn cần idempotency vì hard termination luôn có thể xảy ra.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu process lifecycle và cancellation.
### Middle
Propagate `CancellationToken`.
### Senior
Thiết kế drain, timeout và message settlement.
### Technical Lead / Architect
Đặt workload đúng execution model và xác định termination semantics toàn platform.

## 11. Key takeaway

- Shutdown là production path bình thường.
- Graceful không đồng nghĩa guaranteed completion.
- Durable/idempotent design vẫn cần cho critical work.

# 3. PostgreSQL MVCC và VACUUM: concurrency cao đổi lấy version cleanup

## 1. What is it?

MVCC (Multi-Version Concurrency Control) cho phép PostgreSQL giữ nhiều row versions để readers và writers ít block nhau hơn. UPDATE thường tạo tuple version mới; version cũ trở thành dead tuple khi không transaction nào còn cần nhìn thấy nó. VACUUM thu hồi khả năng tái sử dụng space và duy trì metadata cần thiết.

## 2. Why does it exist?

Nếu reader luôn khóa writer hoặc writer luôn khóa reader, concurrency giảm mạnh. Snapshot visibility cho mỗi transaction thấy phiên bản phù hợp isolation semantics mà không cần serialize mọi access.

## 3. How does it work?

```text
Row v1 -- UPDATE --> Row v2
  |                    |
old snapshot sees v1   new snapshot sees v2

khi v1 không còn visible với transaction nào
 -> VACUUM có thể đánh dấu space reusable
```

Long-running transactions giữ old snapshots và có thể ngăn cleanup hiệu quả.

## 4. Practical implementation

Investigation nên xem dead tuples, autovacuum activity và transaction age thay vì chỉ tăng storage:

```sql
SELECT relname, n_live_tup, n_dead_tup,
       last_autovacuum, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Tìm transactions sống bất thường trong `pg_stat_activity` trước khi tùy tiện chạy maintenance nặng.

## 5. Real production scenario

SaaS audit table bị update/delete lớn. Một reporting transaction chạy hàng giờ giữ snapshot cũ. Dead tuples tích tụ, table/index bloat và I/O tăng dù số business rows không tăng tương ứng.

## 6. Failure scenario & troubleshooting

**Symptom** → storage/I/O tăng, query scan chậm dần. **Evidence** → dead tuples cao, long transaction, autovacuum không theo kịp. **Hypothesis** → churn + cleanup bị cản. **Diagnosis** → transaction age, table stats, vacuum logs. **Fix** → xử lý long transaction, tune workload-specific autovacuum khi có evidence. **Verification** → dead tuple trend và query I/O giảm.

## 7. Common mistakes

Nghĩ DELETE lập tức trả file space về OS; disable autovacuum; giữ transaction mở trong UI/job; chạy `VACUUM FULL` như routine fix mà không xét lock/rewrite cost.

## 8. Alternatives

Partitioning có thể giúp lifecycle của append/time-based data; archival/drop partition đôi khi tốt hơn mass delete. Không thay thế hiểu MVCC.

## 9. Trade-offs

### Advantages
Reader/writer concurrency tốt.
### Costs / Risks
Version churn, vacuum overhead, bloat và transaction-age operational discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu snapshot và row version.
### Middle
Đọc table/activity statistics.
### Senior
Liên hệ transaction lifetime, bloat, vacuum và execution I/O.
### Technical Lead / Architect
Thiết kế retention/write patterns phù hợp storage engine.

## 11. Key takeaway

- MVCC chuyển một phần locking pressure thành version-management cost.
- Long transaction có hậu quả ngoài chính query đó.
- Diagnose bằng visibility/transaction/vacuum evidence.

# 4. Elasticsearch aliases: reindex production không buộc client đổi tên index

## 1. What is it?

Alias là tên logic trỏ tới một hoặc nhiều Elasticsearch indices. Application query alias ổn định, trong khi operations có thể tạo index version mới và atomically chuyển alias.

## 2. Why does it exist?

Một số mapping changes cần reindex. Nếu application hard-code `products-v17`, mỗi reindex kéo theo config/deploy coupling. Alias tách logical search contract khỏi physical index generation.

## 3. How does it work?

```text
Search API -> products-read -> products-v17

reindex -> products-v18
alias switch:
products-read -----------> products-v18
```

Alias update có thể remove old/add new trong một aliases operation.

## 4. Practical implementation

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v17", "alias": "products-read" }},
    { "add":    { "index": "products-v18", "alias": "products-read" }}
  ]
}
```

Trước switch, validate document count, representative queries, mapping/analyzer behavior và indexing lag.

## 5. Real production scenario

E-commerce thay analyzer cho product name. Team tạo `products-v18`, bulk reindex từ source of truth/change stream, chạy shadow validation rồi chuyển alias. Search API không cần release chỉ để biết physical index mới.

## 6. Failure scenario & troubleshooting

**Symptom** → sau alias switch, search thiếu recent products. **Evidence** → bulk snapshot hoàn tất nhưng incremental changes trong lúc reindex chưa catch up. **Hypothesis** → cutover không có synchronization barrier. **Diagnosis** → compare source watermark/index watermark. **Fix** → replay deltas đến safe checkpoint rồi switch. **Verification** → consistency sampling sau cutover.

## 7. Common mistakes

Reindex từ index cũ khi source of truth là DB nhưng data đã drift; switch trước validation; xóa old index ngay; write alias không xác định write index; nghĩ alias giải quyết synchronization.

## 8. Alternatives

In-place mapping additions phù hợp compatible change. Data streams phù hợp time-series lifecycle. Alias-based blue/green index hữu ích schema/analyzer migration.

## 9. Trade-offs

### Advantages
Cutover nhanh, rollback dễ, application decoupled khỏi index version.
### Costs / Risks
Cần temporary double storage, sync/cutover protocol và operational tooling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu logical vs physical index.
### Middle
Thực hiện reindex + alias switch.
### Senior
Thiết kế delta synchronization và validation.
### Technical Lead / Architect
Định nghĩa source-of-truth, migration và rollback strategy.

## 11. Key takeaway

- Alias giải quyết indirection/cutover, không giải quyết data correctness tự động.
- Reindex production cần snapshot + delta strategy.
- Giữ rollback window cho index cũ.

# 5. Saga và compensating transaction: consistency vượt khỏi một database

## 1. What is it?

Saga chia business transaction dài thành nhiều local transactions. Mỗi step commit độc lập; nếu step sau thất bại, hệ thống thực hiện compensating actions cho các effects trước đó khi business cho phép.

## 2. Why does it exist?

Order, payment, inventory có thể thuộc các services/databases khác nhau. ACID transaction xuyên tất cả thường không khả dụng hoặc tạo coupling/availability cost lớn. Distributed workflow phải chấp nhận partial progress.

## 3. How does it work?

```text
Create Order -> Reserve Inventory -> Authorize Payment
                    |
                 failure
                    v
Cancel Order <- Release Inventory
```

Compensation không phải database rollback: external effect có thể đã được nhìn thấy và compensation là business operation mới.

## 4. Practical implementation

Persist workflow state:

```csharp
public enum CheckoutState
{
    Started,
    InventoryReserved,
    PaymentAuthorized,
    Completed,
    Compensating,
    Failed
}
```

Mỗi command/message có idempotency key. State transition và outgoing message nên dùng transactional outbox nếu cùng DB boundary.

## 5. Real production scenario

Marketplace reserve inventory thành công nhưng payment provider timeout. Không biết request payment đã thực thi hay chưa. Workflow không đơn giản “catch rồi rollback”; nó cần reconcile provider status, rồi capture hoặc release inventory theo state thực tế.

## 6. Failure scenario & troubleshooting

**Symptom** → order stuck `Compensating`. **Evidence** → compensation message retry liên tục do inventory API unavailable. **Hypothesis** → partial failure trong recovery path. **Diagnosis** → workflow state + message history + external idempotency records. **Fix** → bounded retry, DLQ/manual reconciliation. **Verification** → fault-injection ở từng transition.

## 7. Common mistakes

Gọi compensation là rollback; không persist saga state; non-idempotent handlers; retry payment blindly sau timeout; orchestration service trở thành domain god-object; không có manual recovery.

## 8. Alternatives

Single database transaction là tốt hơn khi boundary có thể giữ chung. Choreography giảm central coordinator nhưng khó nhìn flow. Orchestration rõ state hơn nhưng thêm component/workflow coupling.

## 9. Trade-offs

### Advantages
Cho phép multi-service workflow chịu partial failure.
### Costs / Risks
Eventual consistency, nhiều intermediate states, compensation complexity và observability burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu local transaction vs distributed workflow.
### Middle
Implement idempotent steps.
### Senior
Thiết kế compensation/reconciliation và failure state.
### Technical Lead / Architect
Quyết định có thực sự cần split service/data ownership hay single transaction đơn giản hơn.

## 11. Key takeaway

- Saga tồn tại vì partial failure là bình thường trong distributed systems.
- Compensation là business action, không time travel.
- Nếu một DB transaction đủ, đừng tự tạo distributed transaction problem.

# 6. Azure Managed Identity + Key Vault: bỏ credential tĩnh khỏi application

## 1. What is it?

Managed Identity cung cấp identity do Azure quản lý cho workload. Application dùng identity đó lấy token từ Microsoft Entra ID và truy cập resource như Key Vault theo authorization policy, thay vì lưu client secret/password trong config.

## 2. Why does it exist?

Static secrets phải được tạo, phân phối, lưu, rotate và revoke. Mỗi bản copy là một leak surface. Workload identity chuyển authentication sang short-lived token issuance.

## 3. How does it work?

```text
App Service / VM / Container
       |
 Managed Identity
       v
Microsoft Entra ID -> access token
       |
       v
Key Vault -> authorized secret/key/certificate
```

Key Vault vẫn có authorization boundary; Managed Identity không tự động được quyền đọc mọi secret.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(configuration["KeyVaultUri"]!),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("PartnerApiKey", cancellationToken: ct);
```

`DefaultAzureCredential` hỗ trợ local developer identity và Managed Identity trên Azure, nhưng production authorization vẫn phải least privilege.

## 5. Real production scenario

API trước đây chứa SQL password trong deployment variable. Chuyển Azure SQL sang Entra/Managed Identity loại password khỏi app. Với third-party API vẫn cần secret, Key Vault lưu secret và workload identity chỉ có quyền đọc secret cụ thể cần thiết.

## 6. Failure scenario & troubleshooting

**Symptom** → local chạy nhưng Azure trả 403 từ Key Vault. **Evidence** → token acquisition thành công nhưng authorization denied. **Hypothesis** → identity đúng nhưng role/access policy thiếu hoặc scope sai. **Diagnosis** → xác định principal ID, token audience và Key Vault authorization model. **Fix** → grant tối thiểu đúng scope. **Verification** → truy cập từ workload identity thực.

## 7. Common mistakes

Cho `Key Vault Administrator` vì nhanh; cache secret mãi và bỏ rotation semantics; log secret khi debug; nhầm authentication với authorization; giữ fallback client secret trong production config.

## 8. Alternatives

Workload identity/federation phù hợp CI/Kubernetes scenarios. Environment secret đơn giản hơn local nhỏ nhưng tăng rotation/leak risk. Không phải mọi config value đều là secret.

## 9. Trade-offs

### Advantages
Giảm static credential lifecycle, centralized authorization/audit.
### Costs / Risks
Phụ thuộc identity/control plane configuration, RBAC complexity và Key Vault availability/cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt identity, token, permission.
### Middle
Cấu hình SDK + RBAC.
### Senior
Thiết kế rotation/cache/failure behavior.
### Technical Lead / Architect
Đặt workload identity và secret governance toàn platform.

## 11. Key takeaway

- Secret manager tốt không bằng loại bỏ secret khi workload identity dùng được.
- Managed Identity giải quyết credential issuance; RBAC vẫn quyết định quyền.
- Production cần least privilege và audit.

# 7. Kubernetes resource requests/limits: scheduling, throttling và OOMKill

## 1. What is it?

`requests` mô tả resource scheduler dùng để placement pod; `limits` đặt ceiling runtime cho container. CPU và memory có behavior khác: CPU thường bị throttled khi vượt limit; memory vượt giới hạn có thể dẫn tới OOM kill.

## 2. Why does it exist?

Cluster chia sẻ finite CPU/RAM. Không có resource contracts, một workload có thể noisy-neighbor workloads khác và scheduler không biết node nào thực sự đủ capacity.

## 3. How does it work?

```text
Pod request: 500m CPU, 512Mi memory
Scheduler: tìm node có allocatable capacity cho request
Runtime:
 CPU > limit -> throttling
 Memory > limit -> OOM risk/kill
```

Request quá cao lãng phí schedulable capacity; quá thấp dễ overcommit node.

## 4. Practical implementation

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"
```

Đặt từ observed working set/CPU profile dưới representative load, có headroom cho startup/GC/burst.

## 5. Real production scenario

.NET API có memory limit 256Mi nhưng heap + native memory + runtime overhead vượt mức khi traffic burst. Pod bị OOMKilled, restart làm warm-up và traffic dồn sang pods còn lại, tạo cascade.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng dù node CPU chưa 100%, hoặc pod restart `OOMKilled`. **Evidence** → CPU throttling metrics/container termination reason/memory working set. **Hypothesis** → limits không phù hợp workload. **Diagnosis** → correlate request latency, GC, throttling, RSS. **Fix** → tune resource profile hoặc giảm allocation/workload. **Verification** → load test với same cgroup constraints.

## 7. Common mistakes

Copy resource values giữa services; chỉ nhìn managed heap; CPU limit quá thấp cho startup/JIT; request bằng peak cho mọi pod; sửa OOM chỉ bằng tăng limit mà không điều tra leak.

## 8. Alternatives

Vertical Pod Autoscaler có thể hỗ trợ recommendations; HPA scale replicas theo signals; cả hai không thay profiling/capacity model.

## 9. Trade-offs

### Advantages
Isolation và predictable scheduling.
### Costs / Risks
Sai sizing gây waste, throttling hoặc eviction/OOM behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu request khác limit.
### Middle
Đọc pod metrics/events.
### Senior
Liên hệ .NET GC/cgroup/load profile.
### Technical Lead / Architect
Thiết kế capacity, autoscaling và cost model.

## 11. Key takeaway

- Request chủ yếu ảnh hưởng scheduling; limit ảnh hưởng runtime enforcement.
- CPU throttling và memory OOM là failure modes khác nhau.
- Resource values phải dựa trên workload evidence.

# 8. SLI/SLO và error budget: reliability thành quyết định đo được

## 1. What is it?

SLI là chỉ số đo trải nghiệm/reliability, ví dụ tỷ lệ request hợp lệ hoàn thành dưới 500 ms. SLO là target cho SLI trong window, ví dụ 99.9% successful requests trong 30 ngày. Error budget là phần failure được phép trong target đó.

## 2. Why does it exist?

“System phải luôn ổn định” không actionable. 100% availability thường không thực tế và có thể làm delivery cực chậm. SLO tạo ngôn ngữ chung giữa reliability và tốc độ thay đổi.

## 3. How does it work?

Nếu SLO availability 99.9%, error budget là 0.1% eligible events trong measurement window. Burn rate cho biết budget đang bị tiêu nhanh đến đâu.

```text
requests -> classify good/total -> SLI
SLI vs objective -> remaining budget
budget burn -> alert/release decision input
```

## 4. Practical implementation

Ví dụ SLI:

```text
good = HTTP requests status < 500 AND duration < 750ms
total = eligible HTTP requests
SLI = good / total
```

Phải định nghĩa exclusions rõ: health probes? client cancellations? expected 4xx? Không thay denominator sau incident để làm số đẹp.

## 5. Real production scenario

Checkout có average latency tốt nhưng p99 và timeout tăng ở peak. SLO dựa trên “successful under latency threshold” phản ánh user impact tốt hơn CPU alert đơn thuần. Release mới burn budget nhanh nên team ưu tiên remediation trước rollout tiếp.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard xanh nhưng users báo lỗi. **Evidence** → SLI chỉ đo 5xx, bỏ latency/critical dependency hoặc đo ở sai boundary. **Hypothesis** → indicator không đại diện user journey. **Diagnosis** → map user-visible outcome tới telemetry. **Fix** → sửa SLI definition/version governance. **Verification** → replay known incidents xem SLI có phản ánh impact.

## 7. Common mistakes

SLO = SLA; chọn target theo cảm giác; alert mọi single failure; dùng infrastructure metric làm user SLI; target 100%; không phân biệt critical endpoints.

## 8. Alternatives

Simple operational thresholds đủ cho hệ thống nhỏ, nhưng khi reliability trade-off trở nên quan trọng, SLO cung cấp framework nhất quán hơn.

## 9. Trade-offs

### Advantages
Reliability có objective, alerting gắn user impact, hỗ trợ ưu tiên engineering.
### Costs / Risks
Sai SLI tạo false confidence; telemetry/window governance cần đầu tư.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu availability/latency metrics.
### Middle
Instrument và query SLI.
### Senior
Thiết kế burn-rate alert và incident analysis.
### Technical Lead / Architect
Đặt SLO theo business criticality và dùng budget làm decision input, không máy móc.

## 11. Key takeaway

- SLI phải gần user outcome.
- SLO không phải lời hứa 100%.
- Error budget giúp thảo luận reliability bằng dữ liệu.

# 9. Contract testing: bảo vệ API integration mà không biến mọi test thành E2E

## 1. What is it?

Contract testing xác minh producer và consumer đồng ý về interaction contract: request shape, response fields, status/semantics quan trọng. Nó nằm giữa unit test cô lập và full E2E xuyên nhiều deployed systems.

## 2. Why does it exist?

Producer có thể pass toàn bộ unit tests nhưng đổi field/status làm consumer vỡ. Full E2E phát hiện được nhưng chậm, flaky và cần nhiều environments. Contract test tập trung vào integration boundary.

## 3. How does it work?

```text
Consumer expectation
 -> contract artifact/spec
 -> provider verification
 -> incompatible change fails CI
```

OpenAPI schema validation là một phần; consumer-driven contracts có thể mô tả interactions thực tế sâu hơn.

## 4. Practical implementation

Ví dụ integration contract cần bảo vệ:

```http
GET /api/orders/42
Accept: application/json
```

```json
{
  "id": 42,
  "status": "Paid",
  "total": 125.50
}
```

Provider test nên chạy against real ASP.NET Core pipeline khi contract phụ thuộc routing/serialization/model binding, không mock controller internals.

## 5. Real production scenario

Order API đổi `status` từ string thành nested object. Producer tests vẫn xanh; frontend/mobile client cũ crash parsing. Contract verification trong CI sẽ đánh dấu breaking change trước deploy.

## 6. Failure scenario & troubleshooting

**Symptom** → contract suite xanh nhưng Production consumer vẫn lỗi. **Evidence** → test chỉ kiểm schema, nhưng semantic behavior/status/header khác. **Hypothesis** → contract quá nông hoặc consumer expectation không được publish/update. **Diagnosis** → compare actual failed interaction. **Fix** → contract hóa behavior có giá trị, không snapshot mọi byte. **Verification** → reproduce regression bằng provider verification.

## 7. Common mistakes

Contract test duplicate toàn bộ E2E; mock provider trong provider verification; contract quá strict với irrelevant fields; không version contract; tin schema compatibility đồng nghĩa business compatibility.

## 8. Alternatives

Integration tests trong monolith đơn giản hơn nếu components deploy cùng nhau. E2E vẫn cần cho vài critical journeys. Static OpenAPI diff hữu ích API governance nhưng không thay runtime semantics.

## 9. Trade-offs

### Advantages
Feedback nhanh cho integration compatibility, ít environment coupling hơn E2E.
### Costs / Risks
Contract lifecycle/tooling và nguy cơ false confidence nếu expectations không đại diện consumers.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu unit/integration/E2E boundaries.
### Middle
Viết provider integration tests cho API contract.
### Senior
Chọn interaction nào đáng contract hóa và compatibility policy.
### Technical Lead / Architect
Thiết kế ownership/versioning giữa independently deployed components.

## 11. Key takeaway

- Contract tests bảo vệ boundary, không thay mọi test layer.
- Test behavior consumers phụ thuộc, không snapshot noise.
- Deployment independence càng cao, compatibility discipline càng quan trọng.

# 10. Optimizely CMS content modeling: thiết kế content boundary

## 1. What is it?

Content modeling xác định các content types, properties, reusable blocks và relationships mà editors dùng để tạo trải nghiệm. Trong Optimizely CMS, page/block types không chỉ là C# classes; chúng tạo editor contract và ảnh hưởng rendering, reuse, migration và governance.

## 2. Why does it exist?

Nếu CMS chỉ có một “Generic Page” với hàng chục optional fields, editors khó hiểu và code chứa nhiều condition. Ngược lại, tạo type cho từng pixel variation làm model bùng nổ. Mục tiêu là model theo semantic content và editorial workflow.

## 3. How does it work?

```text
Editor
  -> ProductLandingPage
       -> HeroBlock
       -> PromoGridBlock
       -> RichTextBlock
  -> published content
  -> rendering/API
  -> CDN/browser
```

Page thường định nghĩa route/context; block encapsulate reusable content composition. Content references tạo graph cần cân nhắc lifecycle/caching.

## 4. Practical implementation

```csharp
[ContentType(DisplayName = "Promo Card")]
public class PromoCardBlock : BlockData
{
    [CultureSpecific]
    public virtual string Heading { get; set; } = string.Empty;

    public virtual ContentReference Image { get; set; }

    public virtual Url Link { get; set; } = new();
}
```

Property nên phản ánh intent (`Heading`, `Image`, `Link`) hơn presentation implementation như `LeftColumnPixelWidth` trừ khi requirement thật sự cần control đó.

## 5. Real production scenario

Marketing website có campaign pages. Team ban đầu hard-code hero/banner fields vào mọi page type. Sau vài quý, cùng component cần reuse ở product/category pages và localization trở nên khó. Reusable semantic blocks giảm duplication và cho editor workflow nhất quán.

## 6. Failure scenario & troubleshooting

**Symptom** → editor phải hỏi developer field nào dùng được; publish page gây layout lỗi; migration khó. **Evidence** → quá nhiều optional fields, presentation-specific model, blocks có dependencies ngầm. **Hypothesis** → content boundary phản ánh UI hiện tại thay vì editorial semantics. **Diagnosis** → review editor tasks + content reuse + rendering contracts. **Fix** → refactor model có migration/backward compatibility plan. **Verification** → editor usability test + rendering regression test.

## 7. Common mistakes

Biến CMS thành relational database cho transactional data; page type quá generic; block quá nhỏ đến mức editor phải lắp hàng chục primitives; business logic critical nằm trong rendering; xóa/đổi property mà không migration existing content.

## 8. Alternatives

Headless CMS tách delivery/UI mạnh hơn nhưng vẫn cần content modeling tốt. Hard-coded application config phù hợp dữ liệu không do editors sở hữu. Product/catalog transactional data thường nên có source chuyên biệt rồi reference/integrate vào CMS.

## 9. Trade-offs

### Advantages
Semantic model cải thiện editor experience, reuse và maintainability.
### Costs / Risks
Model evolution cần migration; quá nhiều abstraction làm authoring phức tạp; reusable blocks tạo dependency graph/cache invalidation considerations.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu page/block/property và publish lifecycle.
### Middle
Implement types/rendering và validation.
### Senior
Thiết kế reuse, localization, caching và migrations.
### Technical Lead / Architect
Xác định data ownership giữa CMS, commerce/search/application systems và giữ editorial model không bị UI/DB concerns làm méo.

## 11. Key takeaway

- Content model là editor/domain contract, không chỉ class hierarchy.
- Model semantic intent trước presentation details.
- CMS không nên trở thành source of truth cho mọi loại business data.
