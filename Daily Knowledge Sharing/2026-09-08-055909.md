# 1. `Task` vs `ValueTask`: allocation, single-consumption semantics và khi optimization phản tác dụng

## 1. What is it?

Mental model: `Task` là một object đại diện cho một asynchronous operation có thể được await, lưu giữ, truyền đi và await nhiều lần. `ValueTask` là một value type wrapper cho phép operation đôi khi hoàn tất đồng bộ mà không cần cấp phát một `Task` mới.

`ValueTask<T>` hữu ích khi method được gọi cực thường xuyên và phần lớn invocation hoàn tất synchronously, ví dụ đọc từ buffer/cache nội bộ trước khi phải I/O.

## 2. Why does it exist?

Một API async luôn trả `Task<T>` có thể tạo allocation cho mỗi call nếu operation không tận dụng cached task. Trong hot path hàng triệu calls, allocation nhỏ có thể trở thành GC pressure đáng kể.

`ValueTask<T>` cho phép fast path trả value trực tiếp và slow path wrap `Task<T>`.

Nhưng lợi ích này chỉ đáng giá khi profiling chứng minh allocation thực sự là bottleneck.

## 3. How does it work?

Conceptually:

```text
Call method
  ├─ data already available → ValueTask<T> chứa T trực tiếp
  └─ needs async work       → ValueTask<T> wrap Task<T>
```

Không nên coi `ValueTask` như `Task` nhỏ hơn. Một `ValueTask` có thể dựa trên `IValueTaskSource`, và một số implementation chỉ hỗ trợ consumption một lần.

Do đó pattern an toàn nhất thường là:

```csharp
var result = await operationAsync();
```

thay vì cache `ValueTask` để await nhiều lần.

## 4. Practical implementation

Một in-memory cache abstraction:

```csharp
public sealed class ProductCache
{
    private readonly ConcurrentDictionary<Guid, ProductDto> _cache = new();
    private readonly IProductRepository _repository;

    public ProductCache(IProductRepository repository)
        => _repository = repository;

    public ValueTask<ProductDto?> GetAsync(Guid id, CancellationToken ct)
    {
        if (_cache.TryGetValue(id, out var cached))
            return ValueTask.FromResult<ProductDto?>(cached);

        return new ValueTask<ProductDto?>(LoadAsync(id, ct));
    }

    private async Task<ProductDto?> LoadAsync(Guid id, CancellationToken ct)
    {
        var product = await _repository.GetAsync(id, ct);
        if (product is not null)
            _cache[id] = product;

        return product;
    }
}
```

Nếu cache hit rate thấp, complexity này gần như không mang lại lợi ích.

## 5. Real production scenario

Một serializer pipeline gọi accessor async hàng chục triệu lần/ngày. 99% dữ liệu đã nằm trong memory. Profiling cho thấy nhiều short-lived `Task` allocations góp phần đáng kể vào Gen 0 GC.

Chuyển đúng hot method sang `ValueTask<T>` giảm allocation. Nhưng chuyển toàn bộ service layer sang `ValueTask` chỉ làm API khó dùng hơn mà không tạo khác biệt đo được.

## 6. Failure scenario & troubleshooting

**Symptom** → code async khó debug hoặc lỗi do await cùng `ValueTask` nhiều lần.

**Evidence** → `ValueTask` bị lưu vào field, truyền qua nhiều layer hoặc convert qua lại liên tục.

**Hypothesis** → optimization đã làm lifecycle semantics phức tạp hơn giá trị nhận được.

**Diagnosis** → benchmark allocation, inspect call graph, xác định sync-completion ratio.

**Fix** → quay lại `Task` nếu không có evidence; chỉ giữ `ValueTask` ở hot boundary đã đo.

**Verification** → BenchmarkDotNet + allocation metrics trước/sau.

## 7. Common mistakes

* Dùng `ValueTask` chỉ vì “nhanh hơn”.
* Await cùng một instance nhiều lần khi source không hỗ trợ.
* Gọi `.AsTask()` khắp nơi, làm mất lợi ích allocation.
* Expose `ValueTask` trên public API không có lý do đo được.
* Tối ưu allocation trước khi xác nhận bottleneck.

## 8. Alternatives

`Task` nên là mặc định cho phần lớn application code. Cached/completed `Task` cũng đủ cho nhiều trường hợp. `ValueTask` hợp lý ở runtime/library/high-throughput internals với sync-completion rate cao.

## 9. Trade-offs

### Advantages

* Có thể giảm allocation trong hot path.
* Hữu ích khi operation thường hoàn tất synchronously.

### Costs / Risks

* Semantics phức tạp hơn.
* Dễ misuse hơn `Task`.
* Performance gain nhỏ hoặc bằng 0 nếu slow path chiếm đa số.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task` là abstraction cho công việc async, không phải thread.

### Middle

Biết khi nào `ValueTask` có sync fast path và cách await đúng.

### Senior

Đòi profiling evidence trước khi đổi API vì allocation optimization.

### Technical Lead / Architect

Giữ API đơn giản mặc định; chỉ cho phép optimization complexity ở bottleneck đã đo và có benchmark regression guard.

## 11. Key takeaway

* `Task` là lựa chọn mặc định.
* `ValueTask` là optimization có điều kiện, không phải “Task nhanh hơn”.
* Chỉ dùng khi sync-completion rate và allocation cost đã được đo.

# 2. `IHttpClientFactory`: connection pooling, DNS refresh, handler lifetime và resilience cho outbound HTTP

## 1. What is it?

`IHttpClientFactory` quản lý việc tạo `HttpClient` và reuse underlying `HttpMessageHandler` theo lifecycle hợp lý.

Mental model quan trọng: vấn đề không phải `HttpClient` “cần dispose mỗi request”, mà là lifecycle của connection pool bên dưới.

## 2. Why does it exist?

Tạo/Dispose `HttpClient` liên tục có thể tạo nhiều TCP connections và góp phần vào socket exhaustion. Ngược lại, giữ một `HttpClient` với handler sống vô hạn có thể giữ DNS resolution cũ quá lâu trong một số môi trường.

Factory giúp quản lý handler pooling và cung cấp một composition point cho logging, authentication và resilience.

## 3. How does it work?

```text
Application
   ↓ CreateClient
HttpClient (lightweight logical client)
   ↓
pooled HttpMessageHandler
   ↓
connection pool
   ↓
DNS / TCP / TLS / remote service
```

Handler có thể được recycle theo `HandlerLifetime`. Với `SocketsHttpHandler`, `PooledConnectionLifetime` còn cho phép connection được refresh sau một khoảng thời gian để nhận DNS changes.

## 4. Practical implementation

```csharp
builder.Services.AddHttpClient<ProductApiClient>(client =>
{
    client.BaseAddress = new Uri(configuration["ProductApi:BaseUrl"]!);
    client.Timeout = TimeSpan.FromSeconds(5);
})
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(5),
    MaxConnectionsPerServer = 100
});
```

Typed client:

```csharp
public sealed class ProductApiClient(HttpClient http)
{
    public async Task<ProductDto?> GetAsync(Guid id, CancellationToken ct)
    {
        using var response = await http.GetAsync($"products/{id}", ct);

        if (response.StatusCode == HttpStatusCode.NotFound)
            return null;

        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<ProductDto>(cancellationToken: ct);
    }
}
```

## 5. Real production scenario

Một e-commerce web app gọi Pricing API. Pricing được scale và IP thay đổi qua service discovery/DNS. Nếu connections sống quá lâu, một số instances tiếp tục gọi endpoint cũ. Nếu connections được tạo quá nhiều, ephemeral ports hoặc upstream connection limit bị pressure.

## 6. Failure scenario & troubleshooting

**Symptom** → outbound timeout tăng, socket/connection count cao hoặc chỉ một số instances gọi endpoint cũ.

**Evidence** → dependency telemetry, connection metrics, DNS resolution, handler configuration.

**Hypothesis** → connection pool lifecycle hoặc timeout policy không phù hợp.

**Diagnosis** → kiểm tra `PooledConnectionLifetime`, max connections, DNS TTL, dependency latency.

**Fix** → lifecycle phù hợp, bounded timeout, retry chỉ cho failure transient và idempotent operations.

**Verification** → connection count ổn định, dependency p95 giảm, endpoint rotation hoạt động.

## 7. Common mistakes

* `new HttpClient()` cho từng request.
* Dùng retry cho mọi POST không có idempotency.
* Timeout 100 giây mặc định cho critical user path.
* Retry timeout 5 lần rồi tạo latency 25+ giây.
* Đặt auth token mutable vào shared default headers sai cách.
* Không propagate `CancellationToken`.

## 8. Alternatives

Một singleton `HttpClient` với `SocketsHttpHandler` cấu hình đúng cũng có thể tốt. `IHttpClientFactory` hữu ích hơn khi có nhiều named/typed clients, policies, logging và dependency-specific configuration.

## 9. Trade-offs

### Advantages

* Handler/connection lifecycle có quản lý.
* Centralize dependency configuration.
* Dễ thêm logging/resilience handlers.

### Costs / Risks

* Policy layering có thể bị overengineer.
* Retry/timeout composition sai tạo retry storm.
* Factory không tự giải quyết DNS, capacity hay downstream design nếu cấu hình sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `HttpClient` dùng connection pool bên dưới.

### Middle

Biết typed client, timeout, cancellation và error handling.

### Senior

Điều tra socket exhaustion, stale DNS và retry amplification.

### Technical Lead / Architect

Định nghĩa outbound dependency policy theo criticality: timeout budget, retry, circuit breaker, observability và fallback.

## 11. Key takeaway

* Quản lifecycle của connection pool quan trọng hơn lifecycle của wrapper `HttpClient`.
* Retry phải kết hợp timeout budget và idempotency.
* Mỗi remote dependency cần policy riêng, không dùng một cấu hình chung cho tất cả.

# 3. EF Core `ExecuteUpdate` / `ExecuteDelete`: set-based mutation và ranh giới với Change Tracker

## 1. What is it?

`ExecuteUpdateAsync` và `ExecuteDeleteAsync` cho phép EF Core gửi set-based `UPDATE`/`DELETE` trực tiếp tới database từ LINQ query mà không load entities vào Change Tracker.

Mental model:

```text
LINQ predicate
→ translated SQL UPDATE/DELETE
→ database mutates matching rows
```

khác với:

```text
query entities
→ materialize
→ track
→ modify objects
→ SaveChanges
```

## 2. Why does it exist?

Nếu cần expire 500.000 records, load từng entity chỉ để đổi một cột là tốn memory, network và Change Tracker overhead.

Database đã có set-based execution model; API này cho phép tận dụng nó từ EF Core.

## 3. How does it work?

Ví dụ:

```csharp
await db.Sessions
    .Where(x => x.ExpiresAt < now)
    .ExecuteDeleteAsync(ct);
```

EF Core tạo `DELETE ... WHERE ...` trực tiếp. Change Tracker không được cập nhật để phản ánh mutation đó.

Đây là điểm quan trọng nhất: bulk mutation bypass normal tracked-entity lifecycle.

## 4. Practical implementation

```csharp
var affected = await db.Products
    .Where(p => p.CategoryId == categoryId && p.IsActive)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(p => p.IsActive, false)
        .SetProperty(p => p.UpdatedAt, now), ct);
```

Nếu trong cùng `DbContext` đã track các `Product` đó, tracked object có thể vẫn giữ giá trị cũ.

Một boundary an toàn là dùng bulk mutation trong operation riêng, không trộn với tracked aggregate manipulation trong cùng context lifetime.

## 5. Real production scenario

Background job archive millions of audit rows. Cách cũ load batch entities rồi `RemoveRange`, làm memory spike và job kéo dài. `ExecuteDeleteAsync` giảm round trips và không cần materialization.

## 6. Failure scenario & troubleshooting

**Symptom** → sau bulk update, code tiếp tục đọc tracked entity và thấy dữ liệu cũ.

**Evidence** → same `DbContext` đã track entity trước `ExecuteUpdate`.

**Hypothesis** → Change Tracker stale.

**Diagnosis** → inspect tracked entries và generated SQL.

**Fix** → tách context/operation, clear tracker khi phù hợp hoặc reload entity.

**Verification** → integration test trong cùng transaction/context boundary.

## 7. Common mistakes

* Giả định domain events/interceptors per entity vẫn chạy như `SaveChanges`.
* Bulk delete mà không validate predicate kỹ.
* Trộn tracked state và direct mutation.
* Dùng bulk operation cho aggregate invariant phức tạp mà business logic nằm trong entity methods.
* Không log affected row count cho operation quan trọng.

## 8. Alternatives

Tracked entity update phù hợp khi cần domain behavior, validation per entity và Change Tracker. Raw SQL/stored procedure vẫn hữu ích cho SQL phức tạp hoặc tuned operations. Dedicated bulk libraries có thêm features nhưng tăng dependency.

## 9. Trade-offs

### Advantages

* Ít round trips và allocation.
* Tận dụng database set-based execution.
* Rất hiệu quả cho maintenance jobs.

### Costs / Risks

* Bypass tracked lifecycle.
* Dễ bỏ qua domain invariants.
* Predicate sai có blast radius lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu sự khác nhau giữa object mutation và SQL set-based mutation.

### Middle

Biết dùng `ExecuteUpdate/Delete` và kiểm tra generated SQL.

### Senior

Hiểu stale tracker, transaction và invariant implications.

### Technical Lead / Architect

Quyết định boundary nào là domain operation, boundary nào chỉ là data maintenance và có thể bypass aggregate behavior.

## 11. Key takeaway

* Bulk mutation không đi qua Change Tracker như `SaveChanges`.
* Hiệu năng tốt hơn đổi lại ít domain/lifecycle hooks hơn.
* Dùng cho đúng boundary, không chỉ vì SQL ngắn hơn.

# 4. PostgreSQL MVCC + VACUUM: vì sao UPDATE tạo dead tuples và database cần housekeeping

## 1. What is it?

PostgreSQL dùng MVCC (Multi-Version Concurrency Control) để cho readers thấy snapshot phù hợp mà không phải block writers theo cách đơn giản nhất.

Một `UPDATE` thường không overwrite tuple tại chỗ theo mental model application. Nó tạo version mới; version cũ trở thành dead tuple khi không transaction nào còn cần nó.

`VACUUM` reclaim/reuse space và duy trì metadata cần thiết cho MVCC.

## 2. Why does it exist?

Readers và writers cần concurrency cao mà vẫn giữ transaction isolation. MVCC cho phép transaction đọc snapshot nhất quán trong khi row đang được update bởi transaction khác.

Cái giá là version churn và housekeeping.

## 3. How does it work?

```text
row version V1 visible to old snapshot
        ↓ UPDATE
new row version V2 created
        ↓
old transactions finish
        ↓
V1 becomes dead tuple
        ↓
VACUUM marks space reusable
```

Autovacuum chạy nền dựa trên thresholds. Long-running transactions có thể giữ old snapshots, ngăn cleanup hiệu quả.

## 4. Practical implementation

Investigation query cơ bản:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Tìm long-running transactions:

```sql
SELECT pid, now() - xact_start AS age, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Không nên bắt đầu bằng `VACUUM FULL` trong production; nó có locking/storage implications lớn.

## 5. Real production scenario

Một table session/update-heavy có millions updates mỗi giờ. Autovacuum không theo kịp, table/index bloat tăng, query I/O tăng dù số live rows không đổi nhiều.

Root cause có thể là scale factor không phù hợp, long transaction hoặc write pattern quá churn-heavy.

## 6. Failure scenario & troubleshooting

**Symptom** → table size tăng, query chậm dần, disk I/O cao.

**Evidence** → `n_dead_tup` cao, autovacuum lag, long transaction tồn tại.

**Hypothesis** → dead tuple accumulation/bloat.

**Diagnosis** → stats + transaction age + autovacuum logs/settings.

**Fix** → xử lý long transaction, tune per-table autovacuum nếu cần, điều chỉnh write pattern.

**Verification** → dead tuples và I/O giảm, latency ổn định qua thời gian.

## 7. Common mistakes

* Nghĩ `UPDATE` luôn overwrite in-place.
* Disable autovacuum vì “ăn CPU”.
* Dùng transaction kéo dài hàng giờ cho batch job.
* Chạy `VACUUM FULL` như routine fix mà không hiểu lock.
* Chỉ nhìn row count mà không nhìn dead tuples/bloat.

## 8. Alternatives

SQL Server có MVCC/snapshot implementation khác. Với append-only workload, churn ít hơn. Partitioning có thể giảm maintenance blast radius cho time-series/history data nhưng tăng schema/operational complexity.

## 9. Trade-offs

### Advantages

* Reader/writer concurrency tốt.
* Snapshot semantics mạnh.

### Costs / Risks

* Dead tuple cleanup cần vận hành đúng.
* Write-heavy tables có thể bloat.
* Long transaction gây hậu quả hệ thống ngoài chính transaction đó.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu row có thể có nhiều versions vật lý.

### Middle

Biết xem table stats và transaction age.

### Senior

Phân tích autovacuum, bloat và write amplification.

### Technical Lead / Architect

Thiết kế data lifecycle/batch jobs để tránh transaction lâu và chọn storage model phù hợp workload.

## 11. Key takeaway

* MVCC đổi blocking lấy version management.
* Autovacuum là correctness/performance mechanism, không chỉ housekeeping phụ.
* Long-running transaction có thể làm cleanup toàn table kém hiệu quả.

# 5. MongoDB embedding vs referencing: thiết kế document theo access pattern thay vì theo ER diagram

## 1. What is it?

Embedding lưu related data bên trong cùng document. Referencing lưu identifier trỏ sang document khác.

Mental model của document database không phải “table nhưng không schema”; model nên phản ánh cách application đọc/ghi dữ liệu.

## 2. Why does it exist?

Nếu dữ liệu luôn được đọc cùng nhau và có lifecycle chung, embedding có thể giảm round trips và giúp atomic update trong một document.

Nếu dữ liệu tăng không giới hạn, được chia sẻ bởi nhiều aggregate hoặc có lifecycle riêng, embedding có thể gây document growth và write amplification.

## 3. How does it work?

Embedding:

```json
{
  "orderId": "...",
  "customer": { "name": "..." },
  "items": [ ... ]
}
```

Reference:

```json
{
  "orderId": "...",
  "customerId": "..."
}
```

MongoDB atomicity mạnh nhất trong single-document mutation. Vì vậy boundary document thường gần aggregate boundary hơn normalized relational model.

## 4. Practical implementation

C# model:

```csharp
public sealed class OrderDocument
{
    public ObjectId Id { get; set; }
    public Guid OrderId { get; set; }
    public CustomerSnapshot Customer { get; set; } = null!;
    public List<OrderItemDocument> Items { get; set; } = [];
    public DateTime CreatedAt { get; set; }
}
```

Snapshot customer name/address trong order có thể đúng business semantics nếu order phải giữ dữ liệu tại thời điểm purchase.

Đó không phải “duplicate data sai”; đó là deliberate denormalization.

## 5. Real production scenario

Order history page luôn cần order + item + customer snapshot. Nếu mọi field được normalize/reference như SQL, API cần nhiều queries/lookups. Embedding snapshot giúp read đơn giản và preserve history.

Ngược lại, embedding toàn bộ product review history vào Product document sẽ tăng không giới hạn và trở thành design lỗi.

## 6. Failure scenario & troubleshooting

**Symptom** → document size tăng mạnh, update chậm, network payload lớn.

**Evidence** → unbounded arrays embedded; product/customer shared data được copy ở hàng triệu documents nhưng business lại yêu cầu cập nhật đồng bộ.

**Hypothesis** → document boundary không khớp lifecycle/access pattern.

**Diagnosis** → review top queries, update frequency, document growth và ownership.

**Fix** → reference unbounded/shared data; embed bounded snapshot/co-owned data.

**Verification** → query count, payload size, update cost và document size distribution.

## 7. Common mistakes

* Normalize MongoDB giống SQL theo phản xạ.
* Embed collection không giới hạn.
* Duplicate mutable shared data mà không có consistency strategy.
* Reference mọi thứ rồi tạo client-side joins thủ công.
* Chọn model trước khi biết access patterns.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp khi relational constraints/joins/transact across many entities là trung tâm. Cosmos DB cũng document-oriented nhưng partitioning/RU model thay đổi nhiều quyết định thiết kế.

## 9. Trade-offs

### Advantages của embedding

* Ít round trips.
* Atomic single-document update.
* Read model tự chứa.

### Costs / Risks

* Duplication.
* Document growth.
* Synchronization khó nếu embedded data thực tế là shared mutable truth.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu embedding không chỉ là nested JSON cho đẹp.

### Middle

Model theo read/write access patterns.

### Senior

Đánh giá growth, atomicity, duplication và consistency.

### Technical Lead / Architect

Chọn document boundary dựa trên ownership/lifecycle và workload thay vì chuyển ER diagram 1:1 sang MongoDB.

## 11. Key takeaway

* Document model phải bắt đầu từ access pattern.
* Embed bounded, co-owned data; reference shared/unbounded data.
* Denormalization có thể là thiết kế đúng khi semantics và consistency rõ.

# 6. Bulkhead Pattern: cô lập saturation để một dependency chậm không kéo sập toàn service

## 1. What is it?

Bulkhead Pattern chia capacity thành các vùng cô lập, giống khoang kín trên tàu: một vùng bị ngập không làm toàn tàu chìm.

Trong software, bulkhead có thể là concurrency limit, dedicated connection pool, queue hoặc worker pool cho một dependency/workload.

## 2. Why does it exist?

Nếu mọi outbound dependency dùng chung ThreadPool/concurrency/connection capacity không kiểm soát, một service chậm có thể làm requests pile up, giữ resources và khiến các endpoint không liên quan cũng timeout.

Bulkhead giới hạn blast radius.

## 3. How does it work?

```text
Incoming requests
    ├─ Pricing calls → max 20 concurrent
    ├─ Reviews calls → max 10 concurrent
    └─ Search calls  → max 50 concurrent
```

Khi Pricing saturation, request Pricing mới bị reject/queue có giới hạn thay vì chiếm toàn capacity.

Bulkhead không làm dependency nhanh hơn; nó bảo vệ phần còn lại của hệ thống.

## 4. Practical implementation

Một lightweight concurrency guard:

```csharp
public sealed class DependencyBulkhead
{
    private readonly SemaphoreSlim _gate = new(20, 20);

    public async Task<T> ExecuteAsync<T>(
        Func<CancellationToken, Task<T>> action,
        CancellationToken ct)
    {
        if (!await _gate.WaitAsync(TimeSpan.FromMilliseconds(100), ct))
            throw new DependencySaturatedException();

        try
        {
            return await action(ct);
        }
        finally
        {
            _gate.Release();
        }
    }
}
```

Production implementation cần metrics cho active, rejected, queued và dependency latency.

## 5. Real production scenario

Product page gọi Reviews API. Reviews outage làm call treo gần timeout. Nếu không bulkhead, hàng nghìn requests cùng giữ outbound connections và request resources; Search/Product API paths cũng chậm.

Giới hạn Reviews concurrency và graceful degradation (“reviews temporarily unavailable”) giữ core product page hoạt động.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency nhỏ bị chậm nhưng toàn application p99 tăng.

**Evidence** → active outbound calls tới một dependency tăng, request queue và connection usage tăng.

**Hypothesis** → shared capacity exhaustion.

**Diagnosis** → traces + concurrency metrics + pool utilization.

**Fix** → bulkhead per dependency/workload, bounded queue, shorter timeout, fallback phù hợp.

**Verification** → làm dependency A chậm trong chaos/load test; endpoint B vẫn đạt SLO.

## 7. Common mistakes

* Queue vô hạn phía sau bulkhead.
* Set concurrency limit theo cảm tính không load test.
* Bulkhead nhưng retry phía ngoài tạo thêm áp lực.
* Fallback trả dữ liệu sai business meaning.
* Một global semaphore cho tất cả dependencies.

## 8. Alternatives

Circuit Breaker ngừng call khi failure rate cao; Rate Limiting kiểm soát ingress/admission; timeout giới hạn thời gian một call. Các pattern này giải quyết vấn đề khác nhau và thường được phối hợp.

## 9. Trade-offs

### Advantages

* Giảm failure propagation.
* Capacity predictable hơn.
* Cho phép graceful degradation.

### Costs / Risks

* Có intentional rejection.
* Cần tuning concurrency.
* Quá nhiều pools/limits làm vận hành phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một dependency chậm có thể chiếm resource của request khác.

### Middle

Biết dùng bounded concurrency và timeout.

### Senior

Đo saturation, rejection và tune capacity dựa trên SLO/downstream limits.

### Technical Lead / Architect

Xác định dependency nào critical, dependency nào degradable và cách phân bổ resource isolation theo business priority.

## 11. Key takeaway

* Bulkhead giới hạn blast radius, không chữa dependency.
* Queue phải bounded.
* Resilience tốt là timeout + admission + isolation + fallback có semantics rõ.

# 7. Azure Front Door vs Application Gateway: global edge routing, regional ingress và failure boundary

## 1. What is it?

Azure Front Door là global Layer 7 edge service dùng Microsoft global network để route HTTP(S) traffic tới origins theo health, latency và routing rules.

Application Gateway là regional Layer 7 load balancer/reverse proxy, thường đứng trước workloads trong một Azure region/VNet và có WAF capability.

Mental model:

```text
Internet
  ↓
Azure Front Door (global edge)
  ↓
Region A / Region B
  ↓
Application Gateway (regional ingress, optional)
  ↓
App Service / AKS / VMs
```

## 2. Why does it exist?

Global application có hai bài toán khác nhau:

1. Chọn region/origin gần và khỏe nhất.
2. Route traffic bên trong một region tới private workloads và áp dụng regional ingress policy.

Dùng một service cho mọi boundary có thể không phù hợp.

## 3. How does it work?

Front Door health-probe origins và route traffic tại edge. Application Gateway quản regional backend pools, routing rules, TLS/WAF và có thể tích hợp private networking.

Không phải hệ thống nào cũng cần cả hai.

## 4. Practical implementation

Một architecture phổ biến:

```text
Client
→ Front Door + WAF
→ Private Link / regional origin
→ App Service / Container Apps
```

Nếu workload AKS/private VNet cần ingress control phức tạp:

```text
Client
→ Front Door
→ Application Gateway
→ AKS ingress/services
```

Configuration phải xác định rõ health endpoint nào đại diện cho readiness thực, không chỉ process alive.

## 5. Real production scenario

SaaS chạy West Europe và Southeast Asia. Front Door route users tới healthy region và failover nếu một region unavailable. Application Gateway trong region bảo vệ/private-route AKS backend.

Nếu region A database chết nhưng health probe chỉ check `/health` trả 200 vì process sống, Front Door vẫn route traffic vào một origin thực tế không usable.

## 6. Failure scenario & troubleshooting

**Symptom** → global failover không xảy ra dù backend region đang lỗi.

**Evidence** → Front Door origin health vẫn healthy; application logs cho thấy DB dependency unavailable.

**Hypothesis** → health probe không phản ánh serving capability.

**Diagnosis** → review health contract, origin status, dependency telemetry.

**Fix** → readiness health phù hợp; tránh probe quá nặng gây self-DDoS.

**Verification** → regional failure drill và quan sát traffic shift.

## 7. Common mistakes

* Dùng Front Door và Application Gateway cùng lúc mà không có lý do boundary rõ.
* Health check chỉ trả 200 unconditional.
* Expose origin công khai khiến traffic bypass edge/WAF.
* TLS/certificate ownership không rõ.
* Không capacity-plan surviving region khi failover.

## 8. Alternatives

Azure Load Balancer là Layer 4 regional. Azure Traffic Manager là DNS-based routing. CDN-focused setup có thể đủ cho static content. Nhiều App Service applications chỉ cần Front Door mà không cần Application Gateway.

## 9. Trade-offs

### Advantages

* Front Door: global routing, edge presence, WAF/CDN features.
* Application Gateway: regional Layer 7 ingress, VNet integration.

### Costs / Risks

* Hai layers tăng latency, config và cost.
* Health/failover semantics phức tạp hơn.
* Origin security sai làm edge controls bị bypass.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt global edge với regional ingress.

### Middle

Hiểu health probes, routing và backend pools.

### Senior

Thiết kế failover drill, origin security và observability.

### Technical Lead / Architect

Chọn ít layers nhất vẫn đáp ứng global routing, private networking, WAF và availability requirements.

## 11. Key takeaway

* Front Door và Application Gateway giải quyết boundary khác nhau.
* Không phải multi-region nào cũng cần cả hai.
* Failover chỉ đáng tin nếu health semantics và surviving-region capacity đúng.

# 8. Playwright test reliability: auto-waiting, locator semantics và loại bỏ flaky timing assumptions

## 1. What is it?

Playwright locators và web-first assertions tự chờ các điều kiện cần thiết thay vì yêu cầu test dùng fixed sleep.

Mental model đúng:

```text
act on semantic locator
→ Playwright waits for actionable state
→ assert observable UI state
```

không phải:

```text
click
→ sleep 2 seconds
→ hope UI finished
```

## 2. Why does it exist?

Modern UI có async rendering, network calls, transitions và hydration. Fixed delay phụ thuộc timing môi trường nên test có thể pass local nhưng fail CI.

Reliable E2E tests nên synchronize với observable state, không synchronize với đồng hồ.

## 3. How does it work?

Locator được evaluate khi action/assertion chạy, không nhất thiết snapshot element một lần. Assertions như `toBeVisible()` retry trong timeout cho đến khi điều kiện đạt hoặc timeout.

Role/text/test-id locator cũng giảm coupling với DOM structure hơn selector kiểu `.container > div:nth-child(3)`.

## 4. Practical implementation

Bad:

```ts
await page.click('#save');
await page.waitForTimeout(2000);
expect(await page.textContent('.toast')).toContain('Saved');
```

Better:

```ts
await page.getByRole('button', { name: 'Save' }).click();
await expect(page.getByRole('status')).toHaveText('Saved');
```

Nếu cần chờ API response thật sự là contract quan trọng:

```ts
const responsePromise = page.waitForResponse(r =>
  r.url().includes('/api/orders') && r.request().method() === 'POST');

await page.getByRole('button', { name: 'Submit order' }).click();
const response = await responsePromise;
expect(response.ok()).toBeTruthy();
```

## 5. Real production scenario

CI runners chậm hơn laptop. Test checkout dùng `waitForTimeout(1000)`; local pass 100%, CI fail 8%. Tăng sleep lên 5 giây chỉ làm suite chậm và vẫn không chứng minh correctness.

Đổi sang locator/assertion based synchronization loại race và giảm test duration trung bình.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail ngẫu nhiên với “element not found” hoặc assertion stale.

**Evidence** → fixed sleeps, CSS selectors brittle, shared test state.

**Hypothesis** → timing/selector coupling.

**Diagnosis** → trace viewer, screenshots, network timeline, retries chỉ để thu evidence.

**Fix** → semantic locator, web-first assertions, deterministic test data, isolate state.

**Verification** → chạy test lặp nhiều lần và trên CI parallelism thực tế.

## 7. Common mistakes

* `waitForTimeout` như synchronization chính.
* Dùng retry để che flaky root cause.
* Chia sẻ user/cart state giữa tests.
* Selector phụ thuộc DOM layout.
* Mock toàn backend rồi gọi đó là E2E.
* Assert implementation detail thay vì user-visible behavior.

## 8. Alternatives

Unit/component tests nhanh hơn cho logic nhỏ. Integration tests phù hợp API/data boundary. E2E nên dành cho critical workflows nơi browser + backend integration mang risk thực.

## 9. Trade-offs

### Advantages

* E2E bắt integration/browser regressions thật.
* Playwright có tooling tốt cho traces và auto-waiting.

### Costs / Risks

* Chậm và đắt hơn unit tests.
* Test data/environment complexity cao.
* Flakiness nếu synchronization/state design kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu đừng sleep theo thời gian nếu có thể chờ state.

### Middle

Dùng locators, assertions, traces và test isolation.

### Senior

Phân tích flakiness theo timing, data, environment và dependency boundary.

### Technical Lead / Architect

Thiết kế test pyramid theo risk và giữ E2E suite nhỏ, deterministic, tập trung critical paths.

## 11. Key takeaway

* Synchronize với state, không với clock.
* Retry không phải fix cho flaky test.
* E2E reliability phụ thuộc test data và boundary design nhiều như selector syntax.

# 9. CMS content-model evolution: thay đổi page/block schema mà không phá content đang publish

## 1. What is it?

CMS content model là contract giữa editors, stored content, rendering code và delivery APIs. Khi page type/block type thay đổi, dữ liệu cũ vẫn tồn tại và phải tiếp tục render hoặc được migrate an toàn.

Đây là schema evolution problem, không chỉ là đổi C# class.

## 2. Why does it exist?

Production CMS có hàng nghìn content items được tạo nhiều năm. Rename/remove property, đổi type hoặc thay block structure có thể làm content cũ mất dữ liệu hoặc renderer lỗi.

CMS deployment vì thế cần backward compatibility và migration strategy giống database/API evolution.

## 3. How does it work?

Ví dụ Optimizely-like model:

```csharp
[ContentType(DisplayName = "Hero Block", GUID = "...")]
public class HeroBlock : BlockData
{
    public virtual string? Heading { get; set; }
    public virtual ContentReference? Image { get; set; }
}
```

Nếu `Heading` đổi thành complex object hoặc property bị remove, stored content version cũ không tự hiểu business intent mới.

Safe evolution thường đi qua additive change → migration/backfill → renderer compatibility → cleanup sau.

## 4. Practical implementation

Một migration-friendly approach:

```csharp
public class HeroBlock : BlockData
{
    [Obsolete("Use HeadingText for new content")]
    public virtual string? Heading { get; set; }

    public virtual string? HeadingText { get; set; }
}
```

Renderer transition:

```csharp
var heading = model.HeadingText ?? model.Heading;
```

Sau khi content migration và verification hoàn tất mới remove legacy property ở release sau.

## 5. Real production scenario

Marketing site có 30.000 Hero blocks. Team rename property và deploy code mới. Editor UI ổn với content mới nhưng pages cũ render heading trống vì stored values nằm ở property cũ.

Nếu không có content inventory/migration, bug có thể chỉ xuất hiện ở long-tail pages ít traffic.

## 6. Failure scenario & troubleshooting

**Symptom** → chỉ một số old pages mất field sau deployment.

**Evidence** → affected content versions được tạo trước schema change; storage vẫn có legacy property.

**Hypothesis** → incompatible content model change.

**Diagnosis** → inspect content versions/schema metadata/render fallback.

**Fix** → restore compatibility, migrate content, publish carefully.

**Verification** → content query/report số items còn legacy state = 0 trước cleanup.

## 7. Common mistakes

* Rename property như rename local variable.
* Delete content type/property cùng release với migration.
* Không test old published content.
* Migration script không idempotent.
* Không backup/export hoặc rollback plan.
* Chỉ test editor create-new flow.

## 8. Alternatives

Headless CMS vẫn có schema evolution problem, chỉ chuyển failure sang API consumers. Strongly versioned content APIs có thể giảm coupling nhưng tăng compatibility burden.

## 9. Trade-offs

### Advantages của additive migration

* Rollout an toàn hơn.
* Cho phép rollback.
* Old/new content cùng tồn tại trong transition.

### Costs / Risks

* Temporary duplication.
* Renderer phức tạp trong migration window.
* Cleanup cần kỷ luật sau khi migration hoàn tất.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CMS field là persisted data contract.

### Middle

Biết test old content và migration scripts.

### Senior

Thiết kế additive/backward-compatible rollout, rollback và data verification.

### Technical Lead / Architect

Xác định content ownership, versioning policy và migration governance giữa dev/editorial teams.

## 11. Key takeaway

* CMS model change là data migration, không chỉ code refactor.
* Additive transition giúp rollback và compatibility.
* Luôn verify old published content, không chỉ content mới tạo.

# 10. OpenAI Structured Outputs: đưa LLM output vào deterministic application boundary an toàn hơn

## 1. What is it?

Structured Outputs cho phép application yêu cầu model trả dữ liệu theo schema xác định thay vì parse prose tự do.

Mental model đúng:

```text
Probabilistic model reasoning
→ constrained structured response
→ schema validation
→ deterministic application logic
```

Structured output giảm ambiguity của integration boundary nhưng không biến nội dung model thành fact đúng tuyệt đối.

## 2. Why does it exist?

Nếu backend trích JSON từ prose bằng regex hoặc prompt “please return valid JSON”, production sẽ gặp malformed output, missing fields, enum lạ và retry logic khó kiểm soát.

Schema constraint giúp application có contract rõ hơn.

## 3. How does it work?

Application định nghĩa schema, model sinh output phù hợp shape đó, sau đó code deserialize/validate và quyết định bước tiếp theo.

Ví dụ result cho ticket triage:

```json
{
  "category": "billing",
  "priority": "medium",
  "summary": "Customer cannot download invoice"
}
```

Dù schema valid, `priority` vẫn có thể sai business meaning. Validation cấu trúc không thay thế business verification.

## 4. Practical implementation

C# contract:

```csharp
public sealed record TicketClassification(
    string Category,
    string Priority,
    string Summary);
```

Sau khi nhận structured response:

```csharp
var result = JsonSerializer.Deserialize<TicketClassification>(json)
             ?? throw new InvalidOperationException("Missing model result");

if (!allowedCategories.Contains(result.Category))
    throw new ValidationException("Unsupported category");

if (result.Priority is not ("low" or "medium" or "high"))
    throw new ValidationException("Unsupported priority");
```

Security-critical action vẫn cần deterministic authorization:

```csharp
if (!user.CanRefund)
    return Results.Forbid();
```

Không bao giờ dùng model output như `"authorized": true` để thay permission check.

## 5. Real production scenario

Support platform dùng LLM classify tickets rồi route queue. Trước đây prose parser đôi lúc fail vì model thêm explanation. Structured contract làm parsing ổn định hơn và telemetry theo category dễ hơn.

Nhưng auto-refund vẫn không được giao cho model; model chỉ đề xuất action, deterministic policy engine quyết định có được execute hay không.

## 6. Failure scenario & troubleshooting

**Symptom** → schema hợp lệ nhưng routing business sai.

**Evidence** → JSON parse 100% thành công nhưng evaluation accuracy thấp ở một category.

**Hypothesis** → semantic/model quality issue, không phải serialization issue.

**Diagnosis** → labeled evaluation dataset, confusion matrix, prompt/context inspection.

**Fix** → improve examples/context/model selection, add deterministic rules cho cases rõ ràng, human review cho low confidence/high risk.

**Verification** → offline eval + production shadow metrics trước auto-execution.

## 7. Common mistakes

* Đồng nhất “schema valid” với “fact correct”.
* Cho model quyết định authorization/financial correctness trực tiếp.
* Retry vô hạn khi output không đạt business validation.
* Không version schema.
* Không log model/version/prompt metadata cần cho observability.
* Đưa untrusted retrieved text vào tool instruction mà không có trust boundary.

## 8. Alternatives

Function/Tool Calling phù hợp khi model cần chọn hành động/tool. Plain JSON mode chỉ đảm bảo JSON syntax ở mức nào đó nhưng contract yếu hơn schema-constrained output. Deterministic parser/rules nên được ưu tiên khi problem vốn deterministic.

## 9. Trade-offs

### Advantages

* Stable application contract.
* Giảm parsing failures.
* Dễ validate, test và observe hơn prose output.

### Costs / Risks

* Model vẫn probabilistic về meaning.
* Schema evolution cần versioning.
* Quá rigid schema có thể làm prompt/workflow khó mở rộng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu model output cần deserialize/validate như external API data.

### Middle

Thiết kế schema, validation và retry bounded.

### Senior

Tách structural correctness, semantic accuracy và authorization correctness.

### Technical Lead / Architect

Xác định boundary rõ giữa probabilistic recommendation và deterministic execution; high-risk actions cần policy/human approval phù hợp.

## 11. Key takeaway

* Structured Outputs làm contract ổn định hơn, không làm model trở thành deterministic.
* Schema validation và business validation là hai lớp khác nhau.
* Security/authorization/financial correctness phải nằm trong deterministic application logic.
