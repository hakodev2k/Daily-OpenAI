# 1. C# `async` state machine: `await` không giữ thread nhưng continuation vẫn có chi phí

## 1. What is it?

Một method C# có `async`/`await` thường được compiler biến thành state machine. Mental model đúng không phải “`await` tạo thread mới”, mà là: method chạy đồng bộ cho tới khi gặp awaitable chưa hoàn tất, lưu state cần thiết, trả quyền điều khiển cho caller và đăng ký continuation để tiếp tục khi operation hoàn thành.

## 2. Why does it exist?

I/O có thể mất hàng chục hoặc hàng trăm milliseconds. Nếu mỗi request giữ một OS thread chỉ để chờ network hoặc database, throughput server bị giới hạn bởi thread count. Async I/O cho phép thread quay lại ThreadPool phục vụ work khác trong lúc kernel/runtime chờ I/O.

## 3. How does it work?

```text
Request thread
    │
    ├─ execute method
    │
    ├─ await DB I/O ───────────────┐
    │                              │
    └─ return thread to pool       │
                                   │ I/O completes
ThreadPool thread <─ continuation ─┘
    │
    └─ continue method
```

Locals cần tồn tại qua `await` trở thành state của generated state machine. Nếu awaited operation đã hoàn tất, fast path có thể tiếp tục synchronously.

## 4. Practical implementation

```csharp
public async Task<OrderDto?> GetOrderAsync(
    Guid id,
    CancellationToken cancellationToken)
{
    var order = await db.Orders
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new OrderDto(x.Id, x.Status, x.Total))
        .SingleOrDefaultAsync(cancellationToken);

    return order;
}
```

Không cần `Task.Run` quanh EF Core I/O. Database provider đã cung cấp asynchronous I/O path.

## 5. Real production scenario

Một ASP.NET Core API có 500 concurrent requests đang chờ SQL và HTTP dependencies. Với async I/O, các request không cần giữ 500 threads trong toàn bộ thời gian chờ. ThreadPool chủ yếu chạy continuation và CPU work thực tế.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 tăng mạnh, CPU chưa cao nhưng ThreadPool queue tăng. **Evidence** → traces cho thấy code gọi `.Result`, `.Wait()` hoặc synchronous HTTP/database API trong async request path. **Hypothesis** → sync-over-async/blocking làm worker threads bị giữ. **Diagnosis** → kiểm tra ThreadPool counters, stacks và dependency spans. **Fix** → async all the way, loại blocking wait, propagate `CancellationToken`. **Verification** → load test lại; queue length và latency giảm mà không cần tăng threads tùy tiện.

## 7. Common mistakes

Cho rằng `async` luôn chạy song song; dùng `Task.Run` cho I/O; thêm `async` nhưng vẫn gọi blocking API; tạo nhiều concurrent operations không giới hạn; quên cancellation; tối ưu state-machine allocation trước khi profiling.

## 8. Alternatives

Synchronous code vẫn hợp với short CPU work hoặc tooling đơn giản. `Task.Run` hữu ích để offload CPU-bound work trong một số client scenarios nhưng không biến CPU work thành scalable I/O. Queue/Worker Service phù hợp khi work không cần hoàn thành trong request.

## 9. Trade-offs

### Advantages

Tăng khả năng sử dụng threads hiệu quả cho I/O-bound workloads và giúp server chịu concurrency cao hơn.

### Costs / Risks

State machine, continuation, execution context và coordination vẫn có overhead; concurrency quá cao vẫn có thể phá downstream dependencies.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` không đồng nghĩa tạo thread mới.

### Middle

Viết async end-to-end, propagate cancellation và tránh `.Result`/`.Wait()`.

### Senior

Phân biệt I/O-bound với CPU-bound, đọc ThreadPool/runtime metrics và kiểm soát concurrency.

### Technical Lead / Architect

Thiết kế concurrency budget từ API tới database/external services; async chỉ giải phóng thread, không tạo capacity vô hạn cho downstream.

## 11. Key takeaway

- `await` là suspension/continuation mechanism, không phải thread creation mechanism.
- Async scalability phụ thuộc việc không block threads trong I/O path.
- Async không thay thế backpressure và downstream capacity planning.

# 2. EF Core optimistic concurrency: bảo vệ lost update bằng concurrency token

## 1. What is it?

Optimistic concurrency giả định conflict tương đối hiếm và không khóa row trong toàn bộ thời gian user chỉnh sửa. EF Core dùng concurrency token để đảm bảo `UPDATE` chỉ thành công nếu version đọc trước đó vẫn còn đúng.

## 2. Why does it exist?

Hai users có thể đọc cùng một order, sau đó lần lượt update. Nếu update thứ hai ghi đè update thứ nhất mà không biết, hệ thống gặp lost update. Giữ database lock từ lúc UI load tới lúc user bấm Save là không thực tế.

## 3. How does it work?

Với SQL Server `rowversion`, EF Core phát sinh logic tương tự:

```sql
UPDATE Orders
SET Status = @status
WHERE Id = @id
  AND RowVersion = @originalRowVersion;
```

Nếu affected rows = 0, EF Core ném `DbUpdateConcurrencyException`. Application phải quyết định retry, merge hay báo conflict.

## 4. Practical implementation

```csharp
public sealed class Order
{
    public Guid Id { get; set; }
    public string Status { get; set; } = default!;

    [Timestamp]
    public byte[] RowVersion { get; set; } = default!;
}
```

```csharp
try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new ProblemDetails
    {
        Title = "Order was modified by another operation"
    });
}
```

Production API nên gửi version/ETag về client và nhận lại version khi update.

## 5. Real production scenario

Nhân viên A approve timesheet trong khi nhân viên B sửa cùng record từ màn hình cũ. Concurrency token ngăn update B âm thầm ghi đè trạng thái approval mới.

## 6. Failure scenario & troubleshooting

**Symptom** → users nhận nhiều `409 Conflict`. **Evidence** → telemetry cho thấy cùng aggregate bị update bởi background job và UI. **Hypothesis** → conflict là thật, không phải lỗi EF. **Diagnosis** → log entity key, operation type và version metadata nhưng không log sensitive payload. **Fix** → thu hẹp write boundary, thiết kế merge/reload UX hoặc serialize business operation nếu invariant yêu cầu. **Verification** → concurrency tests chứng minh không lost update.

## 7. Common mistakes

Catch exception rồi retry vô hạn; reload và overwrite dữ liệu mới; không đưa version tới disconnected client; dùng timestamp thời gian có precision không đủ; nhầm optimistic concurrency với transaction isolation.

## 8. Alternatives

Pessimistic locking phù hợp critical short-lived workflows nhưng tăng blocking/deadlock risk. Serializable isolation mạnh hơn cho transaction invariants nhưng không giải quyết long-lived UI editing. Domain command có thể tránh generic “edit whole entity”.

## 9. Trade-offs

### Advantages

Không giữ long-running locks, phát hiện lost update rõ ràng, phù hợp web applications.

### Costs / Risks

Application phải có conflict semantics; high-contention aggregate có thể tạo retry/conflict storm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hai users có thể update cùng dữ liệu và overwrite nhau.

### Middle

Cấu hình concurrency token và xử lý `DbUpdateConcurrencyException`.

### Senior

Thiết kế API/ETag, merge strategy và phân biệt concurrency conflict với transient failure.

### Technical Lead / Architect

Xác định aggregate nào cần optimistic concurrency, khi nào contention báo hiệu boundary/business workflow cần đổi.

## 11. Key takeaway

- Concurrency token biến lost update thành conflict có thể quan sát.
- Retry không phải câu trả lời mặc định cho business conflict.
- Conflict handling là product/business semantics, không chỉ EF Core plumbing.

# 3. SQL Server deadlock: đọc wait-for graph thay vì chỉ retry lỗi 1205

## 1. What is it?

Deadlock xảy ra khi nhiều transactions giữ resources mà transaction khác cần và tạo vòng chờ. SQL Server deadlock detector chọn một victim, rollback transaction đó và trả lỗi 1205 để phá vòng.

## 2. Why does it exist?

Locking bảo vệ consistency. Khi transactions lấy locks theo thứ tự khác nhau, tính đúng đắn của từng transaction riêng lẻ vẫn có thể tạo circular wait ở mức hệ thống.

## 3. How does it work?

```text
Tx A: holds Order 1 -> waits Customer 7
Tx B: holds Customer 7 -> waits Order 1

A ─waits→ B
↑         │
└─waits───┘
```

Deadlock khác blocking: blocking có thể tự hết khi holder commit; deadlock cần một participant bị rollback.

## 4. Practical implementation

Giảm risk bằng consistent access order và transaction ngắn:

```sql
BEGIN TRANSACTION;

UPDATE Customers
SET Balance = Balance - @amount
WHERE Id = @customerId;

UPDATE Orders
SET Paid = 1
WHERE Id = @orderId;

COMMIT;
```

Mọi competing code path nên cố truy cập resources theo cùng logical order. Dùng Extended Events/deadlock graph để xác định locks, statements và indexes liên quan.

## 5. Real production scenario

Checkout update `Orders` rồi `Customers`, trong khi reconciliation job update `Customers` rồi `Orders`. Under load, hai paths giao nhau và tạo deadlock dù staging gần như không tái hiện.

## 6. Failure scenario & troubleshooting

**Symptom** → intermittent SQL error 1205. **Evidence** → deadlock graph chỉ ra processes/resources và victim. **Hypothesis** → inconsistent lock acquisition order hoặc scan giữ quá nhiều locks. **Diagnosis** → map statements về application traces, xem execution plans và transaction boundaries. **Fix** → thống nhất access order, giảm transaction duration, cải thiện access path nếu scan là nguyên nhân. **Verification** → stress test cùng concurrency pattern và theo dõi deadlock rate.

## 7. Common mistakes

Chỉ bật retry rồi bỏ qua root cause; nhầm timeout với deadlock; thêm `NOLOCK`; tăng timeout; giữ transaction qua remote API call; tạo index mà không đọc execution plan.

## 8. Alternatives

Optimistic concurrency giải quyết lost update ở application level nhưng không loại mọi database deadlock. Snapshot-based isolation có thể giảm reader/writer blocking nhưng writer conflicts vẫn tồn tại và có tempdb/version-store costs.

## 9. Trade-offs

### Advantages

Locking cung cấp transactional consistency; deadlock victim mechanism giúp database tự thoát vòng chờ.

### Costs / Risks

Concurrency cao làm lock ordering và access paths trở thành production concern; retry tăng load nếu root cause còn đó.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt blocking và deadlock.

### Middle

Giữ transaction ngắn và biết lỗi 1205 có thể retry có kiểm soát.

### Senior

Đọc deadlock graph, execution plan và correlation với application operation.

### Technical Lead / Architect

Thiết kế transaction boundaries và concurrency model để contention có giới hạn, thay vì coi database như black box.

## 11. Key takeaway

- Deadlock là circular wait, không chỉ “query chậm”.
- Deadlock graph là evidence chính.
- Retry là resilience layer; root cause vẫn cần được xử lý.

# 4. Redis hot key: một key có thể phá throughput dù cluster còn nhiều capacity

## 1. What is it?

Hot key là key nhận lượng traffic vượt trội so với các keys khác. Trong distributed Redis topology, một key thường thuộc một shard/partition cụ thể; traffic không tự chia đều chỉ vì cluster có nhiều nodes.

## 2. Why does it exist?

Caching thường được thêm để giảm database load. Nhưng nếu millions requests cùng đọc hoặc ghi một key như `homepage:global`, bottleneck chuyển từ database sang một Redis shard, network path hoặc serialization path.

## 3. How does it work?

```text
Clients ───────┐
Clients ───────┼──> key K -> shard 2 (hot)
Clients ───────┘

shard 1: idle
shard 2: saturated
shard 3: idle
```

Cluster capacity tổng không phản ánh capacity của hottest shard/key.

## 4. Practical implementation

Với read-mostly data chấp nhận stale ngắn, có thể thêm L1 cache per instance:

```csharp
public async Task<HomePage?> GetAsync(CancellationToken ct)
{
    if (memoryCache.TryGetValue("home", out HomePage? cached))
        return cached;

    var value = await distributedCache.GetStringAsync("home:v3", ct);
    var model = value is null ? null : JsonSerializer.Deserialize<HomePage>(value);

    memoryCache.Set("home", model, TimeSpan.FromSeconds(10));
    return model;
}
```

Đây chỉ phù hợp nếu 10 giây stale data được chấp nhận.

## 5. Real production scenario

E-commerce homepage dùng một cache key chung cho campaign config. Marketing event tạo traffic spike; Redis CPU trên một shard đạt giới hạn trong khi các shards khác thấp. API latency tăng dù cache hit rate gần 100%.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis latency tăng nhưng aggregate memory/capacity trông bình thường. **Evidence** → command/key sampling cho thấy một key chiếm phần lớn operations. **Hypothesis** → hot key. **Diagnosis** → kiểm tra per-shard CPU/network/latency và request distribution. **Fix** → local cache, replication/read strategy, key sharding nếu semantics cho phép, hoặc redesign data. **Verification** → load test và per-shard metrics cân bằng hơn.

## 7. Common mistakes

Chỉ nhìn hit rate; tăng cluster size nhưng key vẫn map một shard; shard key ngẫu nhiên làm invalidation khó; cache mutable critical state không có consistency strategy; để Redis thành hard dependency không fallback.

## 8. Alternatives

`IMemoryCache` phù hợp per-instance, non-authoritative data. CDN phù hợp public/cacheable responses. Database có thể đủ nếu workload nhỏ. Không cache cũng là lựa chọn đúng khi invalidation/operational cost lớn hơn lợi ích.

## 9. Trade-offs

### Advantages

Redis giảm latency và database load cho shared cached data.

### Costs / Risks

Hot keys, stale data, invalidation complexity và một dependency vận hành mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache hit không đảm bảo cache khỏe.

### Middle

Thiết kế TTL/key và theo dõi latency.

### Senior

Phân tích per-shard load, hot keys, stale tolerance và fallback.

### Technical Lead / Architect

Quyết định có nên cache, ở layer nào, và liệu Redis đang trở thành hidden critical dependency.

## 11. Key takeaway

- Capacity phải được nhìn theo hottest partition, không chỉ tổng cluster.
- Cache hit rate cao vẫn có thể đi cùng outage.
- Local cache/CDN đôi khi giảm hot-key pressure tốt hơn scale Redis mù quáng.

# 5. CQRS với một database: tách intent mà chưa cần distributed architecture

## 1. What is it?

CQRS tách command (thay đổi state) khỏi query (đọc state). CQRS không bắt buộc hai databases, Event Sourcing hay microservices. Một application có thể dùng cùng SQL database nhưng command/query models và code paths khác nhau.

## 2. Why does it exist?

Read và write thường có nhu cầu khác: write cần enforce invariants; read cần projection tối ưu cho UI. Ép cả hai qua cùng generic entity/repository model có thể tạo abstraction cồng kềnh.

## 3. How does it work?

```text
HTTP Command -> Handler -> Domain/EF Core -> SQL
                                      ▲
HTTP Query   -> Query Handler -> projection/read SQL
```

Data ownership và transaction boundary vẫn là một database; separation ở intent/model, chưa phải infrastructure split.

## 4. Practical implementation

```csharp
public sealed record GetOrderQuery(Guid Id);

public async Task<OrderView?> Handle(GetOrderQuery query, CancellationToken ct)
{
    return await db.Orders
        .AsNoTracking()
        .Where(x => x.Id == query.Id)
        .Select(x => new OrderView(x.Id, x.Status, x.Total))
        .SingleOrDefaultAsync(ct);
}
```

Command handler có thể load aggregate tracking và enforce business invariant; query không cần hydrate toàn domain model.

## 5. Real production scenario

Approval workflow có commands `ApproveTimesheet`, `RejectTimesheet`, còn dashboard cần query tổng hợp theo employee/month. Tách models giúp write side rõ business rules trong khi read side dùng projection phù hợp UI.

## 6. Failure scenario & troubleshooting

**Symptom** → solution có hàng trăm handlers một dòng và khó navigate hơn trước. **Evidence** → CRUD đơn giản bị tách thành ceremony nhưng không có read/write pressure khác nhau. **Diagnosis** → áp CQRS theo pattern purity. **Fix** → gom simple use cases hoặc dùng application service trực tiếp; giữ CQRS ở areas có giá trị. **Verification** → code ownership và change path đơn giản hơn mà tests vẫn bảo vệ behavior.

## 7. Common mistakes

Đồng nhất CQRS với MediatR; nghĩ phải có hai databases; thêm event bus ngay lập tức; duplicate models không có mục đích; tách command/query nhưng vẫn expose EF entities ra API.

## 8. Alternatives

Layered application service đủ cho CRUD đơn giản. Vertical Slice Architecture có thể tổ chức theo use case mà không cần strict CQRS. Separate read store chỉ đáng dùng khi scale/latency/modeling thực sự yêu cầu.

## 9. Trade-offs

### Advantages

Read/write intent rõ, query projection tự do hơn, business command dễ review/test.

### Costs / Risks

Thêm types/handlers, navigation overhead và nguy cơ ceremony nếu domain đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu command thay đổi state, query chỉ đọc.

### Middle

Tạo focused handlers và projections mà không overabstract.

### Senior

Nhận ra khi separation giúp maintainability và khi chỉ thêm boilerplate.

### Technical Lead / Architect

Quyết định mức CQRS phù hợp từng bounded context; không nâng lên separate stores nếu chưa có pressure thực tế.

## 11. Key takeaway

- CQRS là separation of intent trước khi là infrastructure topology.
- Một database vẫn là CQRS hợp lệ.
- Pattern chỉ đáng giữ khi giảm coupling hoặc phục vụ read/write needs khác nhau.

# 6. Azure Service Bus lock duration: xử lý lâu, lock renewal và duplicate delivery

## 1. What is it?

Trong Peek-Lock mode, consumer nhận message với một lock tạm thời. Message chưa bị xóa cho tới khi consumer `Complete`. Nếu lock hết hạn trước completion, message có thể được delivery lại.

## 2. Why does it exist?

Broker không thể tin consumer sống mãi sau khi nhận message. Temporary lock cho phép message quay lại queue nếu consumer crash, network partition hoặc không hoàn tất xử lý.

## 3. How does it work?

```text
Receive -> lock acquired -> process -> Complete
              │
              └─ lock expires before Complete
                     -> message visible again
                     -> possible duplicate delivery
```

Auto lock renewal kéo dài lock trong giới hạn cấu hình nhưng không biến delivery thành exactly-once.

## 4. Practical implementation

```csharp
var processor = client.CreateProcessor(queueName, new ServiceBusProcessorOptions
{
    AutoCompleteMessages = false,
    MaxConcurrentCalls = 8,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(10)
});

processor.ProcessMessageAsync += async args =>
{
    await handler.HandleAsync(args.Message, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message, args.CancellationToken);
};
```

Handler vẫn phải idempotent vì duplicate có thể xảy ra ngoài lock-expiry scenario.

## 5. Real production scenario

Worker xử lý PDF mất 7 phút nhưng queue lock mặc định ngắn hơn. Nếu auto renewal bị giới hạn hoặc process pause, message có thể được worker khác nhận trong khi worker đầu vẫn hoàn tất side effect.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng document được xử lý hai lần, log có `MessageLockLost`. **Evidence** → processing duration vượt lock/renewal window. **Hypothesis** → work quá dài cho lock assumptions. **Diagnosis** → correlate message ID, delivery count và processing spans. **Fix** → idempotent result storage, điều chỉnh renewal hợp lý, chia work nhỏ hoặc chuyển long-running orchestration. **Verification** → inject delay vượt lock và chứng minh duplicate không tạo side effect thứ hai.

## 7. Common mistakes

Coi Peek-Lock là exactly-once; `Complete` trước business commit; tăng lock vô hạn; không xử lý cancellation; không monitor delivery count/DLQ; concurrency cao hơn downstream capacity.

## 8. Alternatives

Azure Functions Service Bus trigger đơn giản hóa hosting nhưng semantics delivery vẫn tương tự. Durable Functions phù hợp orchestration dài. Queue Storage đơn giản/rẻ hơn cho use case ít messaging features.

## 9. Trade-offs

### Advantages

Reliable redelivery khi consumer fail, decoupling producer/consumer, controlled concurrency.

### Costs / Risks

Duplicate processing, lock management, DLQ/replay và operational tuning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu receive chưa đồng nghĩa message đã bị xóa.

### Middle

Biết settlement, delivery count và lock renewal.

### Senior

Thiết kế idempotency, concurrency, poison-message handling và telemetry.

### Technical Lead / Architect

Quyết định message granularity và workload placement; long-running task có thể cần orchestration khác thay vì chỉ kéo dài lock.

## 11. Key takeaway

- Lock là lease tạm thời, không phải ownership vĩnh viễn.
- Duplicate delivery là normal failure mode.
- Idempotency quan trọng hơn cố cấu hình lock để “không bao giờ hết hạn”.

# 7. Azure Blob Storage streaming: upload file lớn mà không giữ toàn bộ payload trong memory

## 1. What is it?

Streaming upload chuyển bytes từ request/source tới Blob Storage theo stream/chunks thay vì đọc toàn bộ file vào `byte[]` hoặc `MemoryStream`. Mental model: file size không nên trực tiếp trở thành application memory footprint.

## 2. Why does it exist?

Một API nhận 100 MB file và buffer toàn bộ cho 50 concurrent uploads có thể tạo nhiều GB memory pressure, LOH allocations và GC pauses trước cả khi upload tới storage.

## 3. How does it work?

```text
Client request stream
       │ bounded buffers
       ▼
ASP.NET Core
       │ streaming
       ▼
Azure Blob Storage
```

Blob SDK có thể upload stream và quản lý block transfer; application cần giới hạn request size, concurrency và timeout.

## 4. Practical implementation

```csharp
app.MapPost("/files", async (
    HttpRequest request,
    BlobContainerClient container,
    CancellationToken ct) =>
{
    var blob = container.GetBlobClient($"uploads/{Guid.NewGuid():N}");

    await blob.UploadAsync(
        request.Body,
        overwrite: false,
        cancellationToken: ct);

    return Results.Accepted();
});
```

Production cần content-type policy, authorization, malware workflow và size limits; không tin filename/path từ client.

## 5. Real production scenario

CMS cho editors upload video/assets. Streaming giữ API memory gần với buffer/concurrency thay vì tổng file sizes. Với uploads rất lớn, client-to-Blob bằng scoped SAS có thể bỏ API khỏi data path hoàn toàn.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng theo số concurrent uploads và pods recycle. **Evidence** → heap dump có nhiều large `byte[]`/`MemoryStream`. **Hypothesis** → request buffering. **Diagnosis** → inspect upload code và ASP.NET buffering configuration. **Fix** → stream/chunk, giới hạn concurrency hoặc direct upload bằng SAS. **Verification** → load test với nhiều large files; working set không tăng tuyến tính theo file size.

## 7. Common mistakes

`CopyToAsync(new MemoryStream())` trước upload; tin `Content-Type`; dùng user filename làm blob path; SAS quá rộng/quá lâu; không cleanup abandoned uploads; scan malware synchronously trong request dài.

## 8. Alternatives

Direct-to-Blob SAS giảm application bandwidth và scale cost. Background processing phù hợp virus scan/transcoding. Local filesystem chỉ hợp temporary/local scenarios và không phù hợp multi-instance persistence.

## 9. Trade-offs

### Advantages

Giảm memory pressure, hỗ trợ file lớn, scale application tốt hơn.

### Costs / Risks

Streaming error handling, partial uploads, security validation và lifecycle management phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Không đọc file lớn toàn bộ vào memory nếu không cần.

### Middle

Implement streaming, cancellation và size/content validation.

### Senior

Thiết kế concurrency limits, retry/resume, scanning và telemetry.

### Technical Lead / Architect

Quyết định API-proxy upload hay direct-to-Blob dựa trên security, bandwidth, cost và ownership.

## 11. Key takeaway

- File size không nên bằng memory allocation của API.
- Với large uploads, data path architecture quan trọng hơn một API call.
- Direct upload bằng narrowly scoped SAS thường giảm application burden đáng kể.

# 8. OpenTelemetry trace context: correlation xuyên services nhưng baggage/cardinality cần kỷ luật

## 1. What is it?

Distributed trace nối spans từ một request xuyên API, database, messaging và downstream services bằng trace context. OpenTelemetry chuẩn hóa instrumentation/export. Baggage là key-value context có thể propagate cùng request nhưng không nên biến thành nơi nhét mọi business data.

## 2. Why does it exist?

Trong distributed system, log của từng service riêng lẻ không đủ trả lời “request này chậm ở đâu?”. Trace cho phép nhìn critical path và dependency latency xuyên boundaries.

## 3. How does it work?

```text
Client
  └─ trace abc / span 1
       API
        ├─ span 2: SQL
        └─ span 3: HTTP -> Inventory
                         └─ span 4: Redis
```

W3C `traceparent` truyền trace/span identity. Metrics labels và span attributes cần kiểm soát cardinality; user ID/order ID không nên trở thành metric dimension tùy tiện.

## 4. Practical implementation

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation());
```

Custom activity chỉ nên thêm attributes hữu ích và không chứa secrets/PII.

## 5. Real production scenario

Checkout p95 tăng từ 400 ms lên 1.8 s. Trace breakdown cho thấy API code chỉ 40 ms, Inventory HTTP span mất 1.2 s và SQL 300 ms. Team tập trung đúng dependency thay vì tối ưu controller vô ích.

## 6. Failure scenario & troubleshooting

**Symptom** → telemetry bill tăng mạnh và backend observability chậm. **Evidence** → hàng triệu unique attribute values hoặc sampling quá cao. **Hypothesis** → high-cardinality dimensions/baggage bị lạm dụng. **Diagnosis** → inspect attribute keys, sampling và exporter volume. **Fix** → bỏ IDs khỏi metric labels, dùng trace attributes/log fields phù hợp, sampling strategy. **Verification** → telemetry volume giảm nhưng incident queries cốt lõi vẫn hoạt động.

## 7. Common mistakes

Log trace ID nhưng không propagate; đưa secrets vào baggage; dùng user/order ID làm metric label; sample 100% production traffic vô thời hạn; instrumentation mọi thứ nhưng không có SLO/dashboard/use case.

## 8. Alternatives

Correlation ID thủ công đơn giản hơn cho monolith nhưng thiếu span timing chuẩn. Application Insights native instrumentation có thể đủ; OpenTelemetry hữu ích khi muốn vendor-neutral instrumentation/export pipeline.

## 9. Trade-offs

### Advantages

End-to-end latency visibility, dependency correlation và chuẩn instrumentation chung.

### Costs / Risks

Telemetry volume/cost, sampling complexity, sensitive-data risk và cardinality explosion.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace là chuỗi spans của cùng operation.

### Middle

Instrument HTTP/DB và propagate context đúng.

### Senior

Thiết kế sampling, attributes, cardinality và incident queries.

### Technical Lead / Architect

Định nghĩa observability contract/SLO để telemetry phục vụ decisions, không chỉ thu thập dữ liệu vì có thể.

## 11. Key takeaway

- Trace trả lời request đã đi đâu và mất thời gian ở đâu.
- Context propagation phải xuyên service/messaging boundaries.
- Cardinality và sensitive data là architectural constraints của observability.

# 9. IIS Application Pool recycle: process restart, in-memory state và graceful recovery

## 1. What is it?

IIS Application Pool quản lý worker process (`w3wp.exe`) cho hosted application. Recycle thay worker process theo configuration/health/deployment conditions. Application phải giả định process có thể bị thay thế; process memory không phải durable storage.

## 2. Why does it exist?

Long-running processes có thể cần recovery, configuration/deployment activation hoặc isolation. IIS dùng process lifecycle management để giữ hosting environment vận hành được mà không yêu cầu machine restart.

## 3. How does it work?

```text
IIS
 ├─ old w3wp -> draining requests
 └─ new w3wp -> startup -> receive traffic
```

Behavior thực tế phụ thuộc recycle/overlapped recycle và application startup. In-memory cache/session/background work của process cũ không tự migrate sang process mới.

## 4. Practical implementation

ASP.NET Core background work phải respect shutdown:

```csharp
public sealed class CleanupWorker(ILogger<CleanupWorker> logger)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await RunOneBatchAsync(stoppingToken);
            await Task.Delay(TimeSpan.FromMinutes(1), stoppingToken);
        }
    }
}
```

Critical jobs cần durable queue/checkpoint thay vì tin worker process sống mãi.

## 5. Real production scenario

Legacy enterprise app chạy IIS và giữ shopping/session state trong process memory. Sau recycle, users mất state. Scale-out sang hai servers còn làm vấn đề rõ hơn vì request có thể sang process khác.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi tăng theo chu kỳ, background jobs bị cắt giữa chừng. **Evidence** → IIS event logs trùng thời điểm recycle; application startup/shutdown logs xác nhận process change. **Hypothesis** → lifecycle assumption sai. **Diagnosis** → kiểm tra recycle settings, memory thresholds, deployments và process IDs. **Fix** → externalize durable state, graceful cancellation, idempotent/restartable jobs. **Verification** → force recycle trong test environment và xác nhận requests/jobs recover đúng.

## 7. Common mistakes

Dùng static/in-memory state như durable data; schedule critical job trong web process không checkpoint; tắt recycle để che memory leak; không log process start/stop; lưu files cần persistence trong deployment directory.

## 8. Alternatives

Azure App Service cũng có process restarts nên nguyên tắc tương tự. Windows Service/Worker Service phù hợp background workloads nhưng vẫn phải chịu restart. Durable queue/scheduler giải quyết ownership tốt hơn critical jobs.

## 9. Trade-offs

### Advantages

Process isolation và recovery giúp hosting ổn định, deployment/lifecycle dễ quản lý.

### Costs / Risks

Cold start, lost volatile state và interrupted in-process work nếu application không restart-safe.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process memory biến mất khi process restart.

### Middle

Biết đọc IIS logs, App Pool settings và implement graceful shutdown.

### Senior

Thiết kế restart-safe state/jobs và điều tra recycle do memory/deployment/configuration.

### Technical Lead / Architect

Loại critical durability khỏi web process lifecycle và lập modernization path thay vì chỉ tinh chỉnh IIS settings.

## 11. Key takeaway

- Process restart là normal hosting event, không phải edge case.
- In-memory state không durable.
- Critical background work phải restartable/idempotent hoặc được chuyển sang durable execution model.

# 10. AI Tool Calling: model đề xuất action, application vẫn phải validate và authorize

## 1. What is it?

Tool Calling cho phép LLM tạo structured request để application gọi function/API/tool. Model không trực tiếp có quyền; nó đề xuất tool name và arguments, còn deterministic application code quyết định có thực thi hay không.

## 2. Why does it exist?

LLM giỏi diễn giải natural language nhưng không nên tự giả lập database/API result. Tool Calling nối probabilistic reasoning với deterministic systems: model chọn intent, application thực thi real operation và trả result lại model.

## 3. How does it work?

```text
User
  │
  ▼
LLM -> proposed tool + JSON args
              │
              ▼
      validation + authorization
              │
              ▼
          real service/API
              │
              ▼
           tool result
              │
              ▼
             LLM
```

Tool schema cải thiện structure nhưng không chứng minh arguments đúng hoặc caller được phép.

## 4. Practical implementation

```csharp
public sealed record GetOrderArgs(Guid OrderId);

public async Task<OrderDto> ExecuteAsync(
    GetOrderArgs args,
    ClaimsPrincipal user,
    CancellationToken ct)
{
    if (!await authorization.CanReadOrderAsync(user, args.OrderId, ct))
        throw new UnauthorizedAccessException();

    return await orders.GetAsync(args.OrderId, ct)
        ?? throw new KeyNotFoundException();
}
```

Model không được truyền `CustomerId` rồi mặc nhiên coi đó là authorization proof.

## 5. Real production scenario

Support agent hỏi AI “show order 123”. Model chọn `get_order`. Application kiểm tra operator có quyền truy cập tenant/order trước khi gọi backend. Nếu user yêu cầu “refund order 123”, write tool có thể cần policy chặt hơn hoặc human confirmation.

## 6. Failure scenario & troubleshooting

**Symptom** → model gọi tool đúng schema nhưng resource không thuộc tenant hiện tại. **Evidence** → tool arguments syntactically valid, authorization context không được enforce. **Hypothesis** → team nhầm structured output với trusted output. **Diagnosis** → review tool gateway và audit logs. **Fix** → server-side authorization, allowlist tools, argument validation, least privilege và approval cho high-impact actions. **Verification** → adversarial tests thử cross-tenant IDs và unauthorized actions đều bị deterministic layer chặn.

## 7. Common mistakes

Cho model raw SQL/shell tool; tin schema validation là security; nhét API keys vào prompt; để model quyết định authorization; không timeout/retry policy; không audit tool calls; tool quá generic có blast radius lớn.

## 8. Alternatives

Structured Output không tool phù hợp extraction/classification. Deterministic UI/workflow tốt hơn nếu intent hữu hạn và correctness cao. RAG phù hợp read-only knowledge retrieval; không cần agent nếu không có action loop.

## 9. Trade-offs

### Advantages

Natural-language orchestration, reusable business capabilities, model có thể grounding bằng real system results.

### Costs / Risks

Probabilistic tool selection, latency/token cost, security surface, retry/idempotency và observability complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu model đề xuất action; application mới là nơi thực thi.

### Middle

Implement typed schemas, validation, timeout và error handling.

### Senior

Thiết kế authorization, idempotency, audit, prompt-injection defenses và evaluations.

### Technical Lead / Architect

Quyết định tool granularity/blast radius và action nào phải deterministic hoặc human-approved; không dùng agent chỉ vì có thể.

## 11. Key takeaway

- Structured tool arguments không phải trusted arguments.
- Authorization và business invariants phải nằm ngoài LLM.
- Tool càng mạnh/generic, blast radius càng lớn và policy càng khó chứng minh.
