# 1. C# ThreadPool starvation: vì sao code “async” vẫn có thể làm cả service nghẽn khi block thread

## 1. What is it?

ThreadPool starvation xảy ra khi application có nhiều work cần ThreadPool thread hơn số thread khả dụng trong thời điểm đó, trong khi các thread hiện tại lại bị giữ bởi blocking work.

Mental model:

```text
incoming requests
      |
      v
ThreadPool queue
      |
+-----+-----+-----+
|     |     |     |
T1    T2    T3    ...
|     |     |
.blocking waits.

new continuation/request
        |
        v
   phải chờ thread
```

Điểm quan trọng: `async` chỉ giúp giải phóng thread khi code thực sự await asynchronous I/O. `Task.Result`, `.Wait()`, synchronous I/O hoặc lock dài có thể biến một async call chain thành blocking system.

## 2. Why does it exist?

Server .NET dùng ThreadPool để chạy request continuations, timers và nhiều background callbacks. Nếu 300 request cùng gọi một downstream API nhưng code dùng `.Result`, 300 threads có thể bị giữ để chờ network. ThreadPool có thể inject thêm threads, nhưng quá trình ramp-up không tức thời và càng nhiều threads càng tăng scheduling/context-switch cost.

Kết quả thường không phải CPU 100%. Service có thể CPU thấp nhưng latency tăng mạnh vì work nằm trong queue chờ thread.

## 3. How does it work?

Code tốt:

```csharp
var response = await httpClient.GetAsync(url, ct);
```

Khi network chưa trả về, thread được trả lại pool. Sau khi I/O hoàn tất, continuation được queue lại.

Code blocking:

```csharp
var response = httpClient.GetAsync(url, ct).Result;
```

Thread đang xử lý request bị giữ cho đến khi task hoàn tất.

Ở ASP.NET Core không còn classic `SynchronizationContext` như ASP.NET cũ, nên deadlock kiểu UI-context ít phổ biến hơn, nhưng sync-over-async vẫn gây starvation và throughput collapse.

## 4. Practical implementation

Giữ call chain async từ endpoint xuống dependency:

```csharp
app.MapGet("/products/{id:int}", async (
    int id,
    ProductService service,
    CancellationToken ct) =>
{
    var product = await service.GetAsync(id, ct);
    return product is null ? Results.NotFound() : Results.Ok(product);
});
```

Service:

```csharp
public async Task<Product?> GetAsync(int id, CancellationToken ct)
{
    return await _db.Products
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);
}
```

CPU-bound work không tự nhiên trở thành tốt hơn khi bọc trong `Task.Run` ở request path. Nếu CPU work nặng và dài, cần capacity control hoặc chuyển sang background processing.

## 5. Real production scenario

Một API aggregator gọi ba external APIs. Team dùng `.Result` vì method cấp trên chưa được chuyển sang async. Traffic bình thường không thấy vấn đề. Khi downstream chậm từ 100 ms lên 3 giây, số blocked threads tăng nhanh, request queue dài ra và health endpoint cũng bắt đầu timeout.

Root cause không phải downstream duy nhất; sync-over-async đã khuếch đại latency thành ThreadPool starvation.

## 6. Failure scenario & troubleshooting

**Symptom** → p95/p99 tăng mạnh, request queue tăng, CPU chưa chắc cao.

**Evidence** → runtime counters cho thấy ThreadPool queue length tăng, thread count tăng dần; dump/trace có nhiều stacks ở `.Wait()`, `.Result`, synchronous socket/file/database calls.

**Hypothesis** → blocking work đang giữ worker threads trong thời gian dài.

**Diagnosis** → dùng `dotnet-counters`, trace hoặc profiler; tìm sync-over-async, lock contention và synchronous I/O trong hot path.

**Fix** → async end-to-end, giới hạn concurrency ở dependency chậm, tách CPU-heavy work khỏi HTTP request path khi cần.

**Verification** → load test với downstream latency injection và kiểm tra queue length, thread count, throughput, p95/p99.

## 7. Common mistakes

- Nghĩ `async` keyword tự động giải quyết blocking.
- Gọi `.Result` trong service hoặc middleware.
- Dùng `Task.Run` để “async hóa” database/network I/O.
- Chỉ tăng ThreadPool minimum threads để che root cause.
- Không đặt concurrency limit khi downstream chậm.
- Chỉ nhìn CPU và bỏ qua ThreadPool queue.

## 8. Alternatives

- Async I/O end-to-end là default cho I/O-bound work.
- `Channel<T>` hoặc queue/background worker phù hợp khi request không cần chờ công việc dài.
- Bounded concurrency phù hợp khi dependency chỉ chịu được số calls hữu hạn.

## 9. Trade-offs

### Advantages

- Async I/O tăng khả năng phục vụ nhiều concurrent requests với ít threads hơn.
- Giảm wasted blocking time.

### Costs / Risks

- Async propagation làm nhiều signatures trở thành `Task`/`ValueTask`.
- Concurrency quá cao vẫn có thể làm downstream overload dù ThreadPool khỏe.
- CPU-bound work vẫn cần capacity planning riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết `await` I/O thay vì `.Result`/`.Wait()`.

### Middle

Hiểu thread được trả về pool trong asynchronous wait và biết nhận diện sync-over-async.

### Senior

Chẩn đoán starvation bằng runtime counters/traces và phân biệt CPU saturation, lock contention, downstream latency với ThreadPool starvation.

### Technical Lead / Architect

Đặt concurrency budget cho dependencies, quy chuẩn async call chain và thiết kế degradation khi downstream chậm.

## 11. Key takeaway

- Async chỉ giúp khi work thực sự không block thread.
- `.Result`/`.Wait()` có thể biến downstream latency thành toàn-service latency.
- Khi latency tăng nhưng CPU không cao, hãy kiểm tra ThreadPool queue và blocking stacks.

# 2. ASP.NET Core DI lifetimes: tránh captive dependency khi Singleton giữ Scoped service

## 1. What is it?

ASP.NET Core DI có ba lifetimes chính:

```text
Transient -> instance mới mỗi resolve
Scoped    -> một instance trong mỗi scope, thường là mỗi HTTP request
Singleton -> một instance cho toàn application lifetime
```

Captive dependency xảy ra khi object sống lâu giữ reference tới dependency có lifetime ngắn hơn, đặc biệt Singleton giữ Scoped service.

## 2. Why does it exist?

Lifetime thể hiện ownership và state boundary. `DbContext` thường Scoped vì nó đại diện unit-of-work theo request/operation. Nếu Singleton giữ một `DbContext`, context có thể sống qua nhiều requests, giữ Change Tracker ngày càng lớn, chia sẻ state không thread-safe và sử dụng connection/transaction sai boundary.

## 3. How does it work?

Sai:

```csharp
public sealed class ReportCache
{
    private readonly AppDbContext _db;

    public ReportCache(AppDbContext db) => _db = db;
}

services.AddSingleton<ReportCache>();
```

Container có thể phát hiện một số lifetime violations khi scope validation bật. Nhưng nhiều lỗi xuất hiện qua factory/service locator hoặc background service tạo dependency không đúng scope.

## 4. Practical implementation

Background singleton cần scoped work nên tạo scope cho mỗi operation:

```csharp
public sealed class CleanupWorker(
    IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = scopeFactory.CreateAsyncScope();
            var service = scope.ServiceProvider
                .GetRequiredService<CleanupService>();

            await service.RunAsync(stoppingToken);
            await Task.Delay(TimeSpan.FromMinutes(5), stoppingToken);
        }
    }
}
```

Scope phải nhỏ và gắn với một logical unit-of-work, không phải tạo một scope rồi giữ suốt lifetime của worker.

## 5. Real production scenario

Một hosted service inject repository Scoped thông qua custom factory và giữ repository trong field. Sau vài ngày, DbContext tracked hàng chục nghìn entities, memory tăng và đôi lúc ném concurrency exception khi timer callbacks overlap.

Fix không phải chỉ `AsNoTracking`; lifecycle của unit-of-work mới là vấn đề gốc.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng, data stale, `DbContext` concurrency errors hoặc state giữa requests bị “rò”.

**Evidence** → dependency graph có Singleton → Scoped; object IDs của scoped service không đổi qua nhiều operations.

**Hypothesis** → service ngắn hạn đang bị giữ bởi owner dài hạn.

**Diagnosis** → kiểm tra registrations, constructor graph, factories và code tạo scope.

**Fix** → align lifetime hoặc tạo scope cho từng operation; tránh service locator tràn lan.

**Verification** → integration test nhiều requests/worker iterations và xác nhận scoped instances thay đổi đúng boundary.

## 7. Common mistakes

- Chọn Singleton chỉ vì “nhanh hơn”.
- Inject `DbContext` trực tiếp vào `BackgroundService`.
- Tạo scope một lần trong constructor rồi dùng mãi.
- Đưa mutable request/user state vào Singleton.
- Dùng `IServiceProvider` khắp nơi để né dependency graph rõ ràng.

## 8. Alternatives

- Stateless Singleton cho thread-safe shared services.
- Scoped application service cho request unit-of-work.
- `IDbContextFactory<TContext>` phù hợp một số background/parallel operation cần explicit context creation.

## 9. Trade-offs

### Advantages

- Lifetime đúng giúp ownership, disposal và thread-safety rõ ràng.
- Scoped boundary phù hợp database transaction/unit-of-work.

### Costs / Risks

- Tạo scope thủ công làm code lifecycle phức tạp hơn.
- Quá nhiều Transient heavy objects có allocation/setup cost.
- Singleton mutable state đòi hỏi synchronization cẩn thận.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết ba lifetimes và dùng Scoped cho request-oriented state.

### Middle

Nhận ra Singleton không được giữ Scoped dependency.

### Senior

Thiết kế scope cho hosted services, factories và multi-tenant/request state.

### Technical Lead / Architect

Đặt conventions về lifetime, state ownership và background unit-of-work để dependency graph không tạo hidden concurrency bugs.

## 11. Key takeaway

- DI lifetime là state/ownership contract, không chỉ container configuration.
- Singleton giữ Scoped dependency là một architectural smell nghiêm trọng.
- Background work cần explicit operation scope khi dùng scoped services.

# 3. JWT validation: token decode được không có nghĩa token hợp lệ hoặc được phép truy cập

## 1. What is it?

JWT là một token format gồm header, payload và signature. Base64URL decode chỉ đọc payload; validation mới xác minh token có đáng tin hay không.

Mental model:

```text
JWT received
   |
   +-> parse/decode
   |
   +-> verify signature
   +-> issuer
   +-> audience
   +-> lifetime
   +-> algorithm/key
   |
   v
authenticated identity
   |
   v
authorization policy
```

Authentication và Authorization là hai bước khác nhau.

## 2. Why does it exist?

Nếu API chỉ decode claims rồi tin `role=admin`, attacker có thể tự tạo payload. Ngay cả token có signature hợp lệ cũng có thể dành cho service khác, hết hạn hoặc phát hành bởi issuer không được chấp nhận.

## 3. How does it work?

ASP.NET Core JWT bearer middleware thường validate signature bằng signing keys từ authority metadata/JWKS, sau đó kiểm tra `iss`, `aud`, `exp` và các token validation parameters.

Sau authentication, authorization policy quyết định request cụ thể có được phép không:

```csharp
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("orders.write", policy =>
        policy.RequireClaim("scope", "orders.write"));
});
```

## 4. Practical implementation

```csharp
builder.Services
    .AddAuthentication("Bearer")
    .AddJwtBearer("Bearer", options =>
    {
        options.Authority = "https://identity.example.com";
        options.Audience = "orders-api";
        options.RequireHttpsMetadata = true;
    });

app.MapPost("/orders", Handler)
   .RequireAuthorization("orders.write");
```

Không hard-code custom token parsing trong controller nếu chuẩn middleware đã giải quyết validation.

## 5. Real production scenario

Một company có `billing-api` và `profile-api`. Cả hai dùng cùng identity provider. `profile-api` chỉ kiểm tra signature nhưng không kiểm tra audience. Token được cấp cho `billing-api` vô tình được chấp nhận ở `profile-api`.

Signature hợp lệ nhưng security boundary sai vì recipient không được validate.

## 6. Failure scenario & troubleshooting

**Symptom** → token hoạt động local nhưng production trả 401, hoặc token của service khác được chấp nhận bất ngờ.

**Evidence** → claims cho thấy `iss`/`aud` khác expected; signing key rotation hoặc clock skew khác môi trường.

**Hypothesis** → validation parameters hoặc authority metadata không đúng.

**Diagnosis** → inspect token metadata an toàn, không log raw token; kiểm tra issuer, audience, expiration, key ID và discovery/JWKS endpoint.

**Fix** → strict validation + policy authorization; đồng bộ identity configuration giữa environments.

**Verification** → negative tests với wrong audience, expired token, invalid signature và missing scope.

## 7. Common mistakes

- Dùng jwt.io/decode thành công rồi kết luận token valid.
- Chỉ check role trong controller nhưng không validate signature/audience.
- Log access token nguyên văn.
- Dùng quá nhiều long-lived bearer tokens.
- Nhầm 401 với 403.
- Dựa vào frontend để enforce permission.

## 8. Alternatives

- Cookie authentication cho browser-centric server apps.
- Opaque/reference tokens khi muốn server-side introspection/revocation model.
- mTLS hoặc workload identity cho một số service-to-service scenarios.

## 9. Trade-offs

### Advantages

- JWT có thể validate locally, giảm identity-provider round trip.
- Claims hỗ trợ distributed authorization context.

### Costs / Risks

- Revocation khó hơn với long-lived self-contained tokens.
- Key rotation, audience design và scope design cần governance.
- Token leakage có thể trao bearer access cho attacker.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt decode và validate.

### Middle

Hiểu issuer, audience, expiry, signature và policy authorization.

### Senior

Thiết kế scope/claim boundaries, key rotation và negative security tests.

### Technical Lead / Architect

Chuẩn hóa token audience, service identities, least privilege và credential/token lifecycle toàn hệ thống.

## 11. Key takeaway

- Decode JWT không tạo trust.
- Signature hợp lệ vẫn chưa đủ: issuer, audience, lifetime và authorization policy đều quan trọng.
- Không log raw bearer tokens và không giao authorization cho frontend.

# 4. EF Core optimistic concurrency với `rowversion`: phát hiện lost update mà không khóa pessimistic toàn transaction

## 1. What is it?

Optimistic concurrency cho phép nhiều users/processes đọc cùng row và chỉ phát hiện conflict khi update.

Mental model:

```text
A reads version 10
B reads version 10
B updates -> version 11
A updates WHERE Version = 10
           -> 0 rows affected
           -> concurrency conflict
```

SQL Server `rowversion` là một concurrency token phù hợp để EF Core biết row đã thay đổi kể từ lúc được đọc.

## 2. Why does it exist?

Không có concurrency control, hai users sửa cùng record có thể tạo lost update: người save sau âm thầm ghi đè thay đổi của người trước.

Giữ database lock từ lúc user mở form đến lúc nhấn Save là không thực tế. Optimistic concurrency giả định conflict hiếm và xử lý khi xảy ra.

## 3. How does it work?

Entity:

```csharp
public sealed class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }

    [Timestamp]
    public byte[] Version { get; set; } = [];
}
```

EF tạo update gần như:

```sql
UPDATE Products
SET Price = @price
WHERE Id = @id AND Version = @originalVersion;
```

Nếu zero rows affected, EF ném `DbUpdateConcurrencyException`.

## 4. Practical implementation

API nên round-trip version/ETag thay vì che conflict:

```csharp
try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new
    {
        code = "concurrency_conflict",
        message = "The resource changed. Reload before saving."
    });
}
```

Với HTTP API, có thể map version sang ETag/`If-Match` để contract rõ hơn.

## 5. Real production scenario

Hai customer-service agents mở cùng order. Agent A sửa shipping address; Agent B thay status. Nếu UI gửi full object và backend overwrite toàn row, save của B có thể ghi địa chỉ cũ trở lại.

Concurrency token phát hiện record đã đổi và buộc hệ thống chọn policy: reject, merge hoặc retry có kiểm soát.

## 6. Failure scenario & troubleshooting

**Symptom** → user báo dữ liệu “tự quay về giá trị cũ” dù cả hai saves đều 200 OK.

**Evidence** → audit log cho thấy overlapping updates trên cùng row; API không có version condition.

**Hypothesis** → last-write-wins đang che lost update.

**Diagnosis** → inspect generated SQL và update DTO semantics.

**Fix** → thêm concurrency token và explicit conflict handling.

**Verification** → integration test hai contexts đọc cùng version rồi save xen kẽ; lần save thứ hai phải conflict theo policy.

## 7. Common mistakes

- Catch `DbUpdateConcurrencyException` rồi retry vô hạn.
- Retry bằng cách overwrite database values mà không hiểu business conflict.
- Dùng timestamp business (`UpdatedAt`) với precision không đảm bảo như concurrency token.
- Trả generic 500 cho conflict có thể dự đoán.
- Dùng full-entity PUT làm ghi đè fields client chưa thực sự chỉnh sửa.

## 8. Alternatives

- Pessimistic locking cho critical short transactions có conflict cao.
- Application version number khi database không có native `rowversion`.
- Event-sourced/versioned aggregate cho domain cần explicit expected version.

## 9. Trade-offs

### Advantages

- Không giữ long-lived locks.
- Phát hiện lost update rõ ràng.
- Phù hợp web/distributed systems.

### Costs / Risks

- Client phải hiểu conflict semantics.
- Merge logic có thể phức tạp.
- Retry tự động không phải lúc nào an toàn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hai users có thể update cùng record.

### Middle

Biết dùng concurrency token và xử lý `DbUpdateConcurrencyException`.

### Senior

Chọn reject/merge/retry dựa trên business semantics và API contract.

### Technical Lead / Architect

Định nghĩa concurrency strategy xuyên UI, API, persistence và auditability.

## 11. Key takeaway

- Optimistic concurrency biến silent overwrite thành explicit conflict.
- Conflict handling là business decision, không chỉ exception handling.
- Retry mù có thể phá ý nghĩa của concurrency protection.

# 5. SQL Server parameter sniffing: cùng một query có thể rất nhanh với parameter này nhưng rất chậm với parameter khác

## 1. What is it?

Parameter sniffing là behavior trong đó SQL Server compile query plan dựa trên parameter values tại thời điểm compilation và có thể reuse plan đó cho các values sau.

Mental model:

```text
first execution: CustomerId = rare customer
        |
compile plan optimized for few rows
        |
plan cached
        |
next execution: CustomerId = huge customer
        |
reuse same plan -> potentially bad
```

Bản thân parameter sniffing không phải bug; plan reuse thường tốt. Vấn đề xuất hiện khi data distribution skew lớn và một plan không phù hợp mọi parameter.

## 2. Why does it exist?

Compile query plan có cost. SQL Server cache/reuse plans để giảm compilation overhead. Nhưng optimizer phải ước lượng cardinality. Giá trị parameter đầu tiên hoặc representative estimate ảnh hưởng join type, index access và memory grant.

## 3. How does it work?

Ví dụ:

```sql
SELECT Id, Total, CreatedAt
FROM Orders
WHERE CustomerId = @CustomerId;
```

Customer A có 5 orders, Customer B có 5 triệu orders. Plan dùng nested loops + index seek có thể tuyệt vời cho A nhưng tệ cho B.

Không nên mặc định chữa bằng `OPTION (RECOMPILE)` cho mọi query vì compilation cost và plan cache behavior cũng quan trọng.

## 4. Practical implementation

Workflow xử lý:

1. xác nhận query text/plan thực tế;
2. so sánh estimated vs actual rows;
3. kiểm tra data distribution/statistics;
4. xem Query Store có plan regression hay nhiều plans khác nhau;
5. chọn mitigation nhỏ nhất phù hợp.

Mitigations có thể gồm index/schema cải thiện, query shape khác, `OPTION (RECOMPILE)` cho query hiếm nhưng skew mạnh, hoặc các SQL Server plan features phù hợp version đang dùng.

## 5. Real production scenario

Report endpoint chạy dưới 100 ms ở staging nhưng production đôi lúc mất 20 giây. Production có một enterprise tenant chiếm 40% rows. Plan được compile từ tenant nhỏ sau deploy và sau đó reused cho enterprise tenant.

Scale/data distribution khác nhau làm bug không thể tái hiện bằng staging dataset đồng đều.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng stored procedure/query lúc nhanh lúc chậm theo parameter; restart/recompile tạm thời đổi behavior.

**Evidence** → Query Store cho thấy execution duration phụ thuộc plan/parameter; actual row counts lệch xa estimates.

**Hypothesis** → plan reuse không phù hợp skewed cardinality.

**Diagnosis** → capture actual plans cho representative small/large parameters; inspect statistics và indexes.

**Fix** → chọn targeted plan/query/index strategy, không dùng global hack trước khi hiểu workload.

**Verification** → benchmark nhiều parameter buckets và theo dõi regression trong Query Store.

## 7. Common mistakes

- Restart SQL Server để “fix performance”.
- Thêm index ngẫu nhiên theo missing-index suggestion.
- Dùng `RECOMPILE` ở mọi query.
- Test chỉ một tenant/data size.
- Nhìn duration mà không xem plan/cardinality estimates.
- Đổ lỗi ORM trước khi inspect generated SQL và execution plan.

## 8. Alternatives

- Query specialization cho genuinely different workloads.
- Pre-aggregated/read models cho heavy reporting.
- Partitioning hoặc tenant isolation khi skew phản ánh architectural scale boundary.

## 9. Trade-offs

### Advantages

- Plan cache giảm compilation cost đáng kể.
- Targeted tuning giữ được benefits của reuse.

### Costs / Risks

- Workload skew làm performance khó dự đoán.
- Query hints có thể trở thành technical debt khi data thay đổi.
- Recompile tăng CPU compilation cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết query plan ảnh hưởng performance, không chỉ SQL text.

### Middle

Biết đọc estimated/actual rows và kiểm tra indexes/statistics.

### Senior

Nhận diện parameter-sensitive workload bằng Query Store và production-like datasets.

### Technical Lead / Architect

Đảm bảo performance testing phản ánh tenant/data skew và tránh institutionalize query hints như giải pháp mặc định.

## 11. Key takeaway

- Một SQL text có thể cần các execution strategies khác nhau tùy data distribution.
- Chẩn đoán bằng plan + cardinality + Query Store, không đoán.
- Mitigation phải targeted; đừng chữa plan problem bằng global hacks.

# 6. MongoDB embedding vs references: chọn document boundary theo access pattern thay vì mô phỏng relational schema

## 1. What is it?

MongoDB cho phép model related data bằng hai hướng chính:

```text
Embedding
Order document
  + customer snapshot
  + items[]
  + shipping address

References
Order { customerId }
Customer { _id, ... }
```

Document boundary nên phản ánh dữ liệu thường được đọc/ghi cùng nhau và consistency boundary, không phải chỉ quan hệ conceptual giữa entities.

## 2. Why does it exist?

Nếu chuyển schema relational sang MongoDB bằng cách tạo collection cho mọi entity và reference mọi thứ, application dễ tạo nhiều round trips/`$lookup` và mất lợi thế document locality.

Ngược lại, embed dữ liệu không giới hạn có thể làm document phình lớn, update contention và vượt document-size constraints.

## 3. How does it work?

Embedding phù hợp khi child data:

- bounded;
- được đọc cùng parent;
- có lifecycle gắn với parent;
- cần atomic update cùng document.

References phù hợp khi data:

- được chia sẻ bởi nhiều aggregates/documents;
- tăng trưởng không giới hạn;
- được truy cập độc lập;
- có lifecycle riêng.

## 4. Practical implementation

Order thường có thể embed immutable snapshot của item pricing:

```json
{
  "_id": "order-123",
  "customerId": "customer-9",
  "items": [
    {
      "productId": "p-1",
      "name": "Keyboard",
      "unitPrice": 120,
      "quantity": 2
    }
  ],
  "total": 240
}
```

Không nhất thiết lookup current product price khi hiển thị historical order; snapshot có business meaning riêng.

## 5. Real production scenario

Một activity stream embed toàn bộ comments trong cùng document. Ban đầu mỗi activity có vài comments. Sau khi product tăng trưởng, một số posts có hàng trăm nghìn comments; document updates trở nên nóng và payload đọc quá lớn.

Boundary ban đầu không còn phù hợp growth pattern.

## 6. Failure scenario & troubleshooting

**Symptom** → document size tăng nhanh, updates chậm, nhiều payload thừa hoặc query phải `$lookup` liên tục.

**Evidence** → access patterns cho thấy embedded array unbounded hoặc reference graph tạo nhiều server/client joins.

**Hypothesis** → schema được model theo entity relationship thay vì workload.

**Diagnosis** → inventory top reads/writes, cardinality, growth bounds và atomicity requirements.

**Fix** → redesign boundary; có thể embed snapshots/bounded children và reference unbounded/shared data.

**Verification** → load test representative document sizes và query patterns, không chỉ small fixtures.

## 7. Common mistakes

- Dùng MongoDB như SQL nhưng bỏ foreign keys.
- Embed unbounded arrays.
- Duplicate data mà không xác định source of truth.
- Normalize mọi thứ vì sợ duplication.
- Thiết kế schema trước khi biết access patterns.
- Dùng `$lookup` như mặc định cho mọi relation.

## 8. Alternatives

- Relational database nếu workload chủ yếu cần joins/constraints phức tạp.
- Separate read model nếu UI cần denormalized shape nhưng write model cần normalized consistency.
- Event-driven projection cho derived documents ở scale lớn.

## 9. Trade-offs

### Advantages

- Embedding giảm round trips và hỗ trợ atomic document updates.
- Denormalized shape có thể khớp trực tiếp read model.

### Costs / Risks

- Duplication tạo synchronization responsibility.
- Document growth cần giới hạn.
- Reference model có thể tăng query complexity/round trips.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu document không phải row và collection không phải table theo nghĩa 1:1.

### Middle

Chọn embed/reference dựa trên boundedness và access patterns.

### Senior

Đánh giá growth, consistency, duplication và hot-document contention.

### Technical Lead / Architect

Định nghĩa document boundaries dựa trên workload thực tế và migration strategy khi scale assumptions thay đổi.

## 11. Key takeaway

- MongoDB schema design bắt đầu từ access pattern.
- Embed bounded data được dùng cùng nhau; reference shared/unbounded data khi hợp lý.
- Denormalization đổi join cost thành synchronization cost — cần chọn có chủ đích.

# 7. Redis cache stampede: ngăn hàng nghìn request cùng xuyên cache khi một hot key hết hạn

## 1. What is it?

Cache stampede xảy ra khi một hot cache entry hết hạn và nhiều requests đồng thời đều thấy cache miss, sau đó cùng truy vấn database/downstream để rebuild cùng một value.

Mental model:

```text
hot key expires
     |
1000 requests -> MISS
     |
1000 DB queries
     |
DB overload
```

Cache vốn để giảm tải có thể tạo load spike đúng thời điểm entry mất hiệu lực.

## 2. Why does it exist?

TTL thường đồng bộ requests quanh cùng expiration boundary. Với expensive query hoặc hot key, một cache miss không đáng ngại; 5,000 concurrent misses mới nguy hiểm.

## 3. How does it work?

Một mitigation phổ biến là single-flight/per-key locking:

```text
MISS
 |
acquire key-specific lock
 |
re-check cache
 |
one caller computes
 |
cache set
 |
others read cached value
```

Re-check sau khi lấy lock rất quan trọng vì một request khác có thể đã populate cache trong lúc caller chờ.

## 4. Practical implementation

Trong một process, `SemaphoreSlim` per key có thể đủ. Trong multi-instance system, có thể dùng distributed coordination nếu thực sự cần, nhưng phải cân nhắc complexity.

Pseudo-flow:

```csharp
var cached = await cache.GetAsync(key, ct);
if (cached is not null)
    return cached;

await using var lease = await locker.AcquireAsync(key, ct);

cached = await cache.GetAsync(key, ct);
if (cached is not null)
    return cached;

var fresh = await repository.LoadAsync(id, ct);
await cache.SetAsync(key, fresh, ttl, ct);
return fresh;
```

Thêm TTL jitter giúp nhiều keys không hết hạn cùng một giây.

## 5. Real production scenario

Homepage có config object được đọc hàng nghìn lần mỗi giây, TTL 10 phút. Mỗi 10 phút database CPU spike vì tất cả app instances cùng miss key và query config table.

Thêm jitter + single-flight theo instance giảm spike; vì query đủ rẻ, team không thêm distributed lock để tránh operational complexity không cần thiết.

## 6. Failure scenario & troubleshooting

**Symptom** → database QPS có spike định kỳ đúng TTL boundaries.

**Evidence** → Redis miss rate tăng đột ngột, cùng query/key được load hàng trăm lần đồng thời.

**Hypothesis** → synchronized expiration + no request coalescing.

**Diagnosis** → correlate cache hit ratio, key TTLs và downstream QPS.

**Fix** → jitter, single-flight, stale-while-revalidate hoặc proactive refresh tùy consistency requirement.

**Verification** → force hot key expiration dưới load và kiểm tra số downstream calls thực tế.

## 7. Common mistakes

- Thêm Redis rồi mặc định database sẽ luôn nhẹ hơn.
- Dùng distributed lock cho mọi cache miss dù local coalescing đủ tốt.
- Quên double-check cache sau khi acquire lock.
- TTL giống hệt cho hàng triệu keys.
- Không có fallback khi Redis unavailable.
- Cache null/error response không có policy rõ ràng.

## 8. Alternatives

- Stale-while-revalidate khi chấp nhận dữ liệu hơi cũ.
- Background refresh trước expiration.
- Local in-memory cache tầng 1 + Redis tầng 2.
- Không cache nếu source query vốn đủ rẻ và traffic thấp.

## 9. Trade-offs

### Advantages

- Request coalescing bảo vệ database/downstream khi hot key miss.
- TTL jitter đơn giản nhưng giảm synchronized spikes hiệu quả.

### Costs / Risks

- Locking thêm latency cho miss path.
- Distributed coordination có failure modes riêng.
- Serving stale data phải có business agreement.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss có thể đi xuống database.

### Middle

Biết TTL, jitter và double-check locking.

### Senior

Chọn single-flight, stale serving hoặc refresh dựa trên consistency/load profile.

### Technical Lead / Architect

Quyết định cache failure behavior và liệu distributed lock có đáng operational cost hay không.

## 11. Key takeaway

- Cache expiration là một concurrency event, không chỉ data freshness event.
- Jitter + request coalescing thường giải quyết phần lớn stampede risk.
- Đừng thêm distributed coordination nếu simpler local strategy đã đủ bảo vệ dependency.

# 8. Azure Key Vault + Managed Identity: bỏ secrets khỏi source code và giảm vòng đời credential thủ công

## 1. What is it?

Managed Identity cho Azure resource một workload identity do platform quản lý. Key Vault lưu secrets/keys/certificates và cấp quyền theo identity thay vì application phải giữ client secret dài hạn.

Mental model:

```text
App Service / VM / Function
        |
Managed Identity
        |
Microsoft Entra token
        |
        v
    Key Vault
        |
 authorized secret/key access
```

## 2. Why does it exist?

Nếu application cần một client secret để lấy secret khác từ vault, team vẫn phải phân phối và rotate bootstrap credential. Managed Identity loại bỏ phần lớn secret bootstrap trong Azure-hosted workloads.

## 3. How does it work?

Application dùng Azure Identity credential chain. Ở local, developer có thể authenticate bằng developer identity phù hợp; ở Azure, SDK dùng Managed Identity.

```csharp
var client = new SecretClient(
    new Uri(vaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("PaymentsApiKey");
```

Access vẫn phải được giới hạn bằng RBAC/access policy phù hợp least privilege.

## 4. Practical implementation

Production application nên:

- enable system-assigned hoặc user-assigned Managed Identity;
- grant chỉ permissions cần thiết;
- reference vault URI qua configuration, không phải secret;
- cache secret hợp lý nếu request volume cao;
- có rotation process cho actual third-party secret trong vault.

Không gọi Key Vault cho cùng secret trên mọi HTTP request nếu không cần.

## 5. Real production scenario

Một App Service có database password trong pipeline variable, copied sang app settings. Password bị rotate nhưng một environment deployment variable chưa update nên production outage.

Chuyển database access sang Entra/Managed Identity nơi supported giúp loại password hoàn toàn; các third-party API keys còn lại được giữ trong Key Vault với centralized rotation.

## 6. Failure scenario & troubleshooting

**Symptom** → local chạy được nhưng Azure trả 403 khi đọc vault.

**Evidence** → token acquisition thành công nhưng Key Vault authorization denied.

**Hypothesis** → identity đúng nhưng RBAC scope/role assignment thiếu hoặc application đang dùng identity khác expected.

**Diagnosis** → xác định principal/object ID thực tế, vault permissions, tenant và network restrictions.

**Fix** → cấp least-privilege role đúng scope; sửa credential selection/configuration.

**Verification** → application chỉ đọc được secrets cần thiết và bị deny với secrets ngoài scope.

## 7. Common mistakes

- Đưa Key Vault secret vào source rồi gọi đó là “vault integration”.
- Cho app quyền Owner/Contributor thay vì secret-specific data-plane access.
- Fetch vault mỗi request.
- Log secret values khi startup diagnostics.
- Nghĩ Key Vault tự rotate mọi third-party credential.
- Không phân biệt identity/authentication issue với vault network issue.

## 8. Alternatives

- Environment/app settings cho non-secret configuration.
- Kubernetes workload identity + external secret integration trong container platform.
- HSM/key-management services khi cần cryptographic key operations thay vì generic secrets.

## 9. Trade-offs

### Advantages

- Giảm static credentials trong deployment pipeline/configuration.
- Centralize secret access control và auditing.
- Managed Identity giảm manual credential rotation cho workload identity.

### Costs / Risks

- Azure identity/RBAC/network configuration có learning curve.
- Vault dependency cần caching/resilience hợp lý.
- Third-party secrets vẫn cần lifecycle/rotation process.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Không commit secrets và hiểu vault là secret store, không phải config store cho mọi thứ.

### Middle

Dùng `DefaultAzureCredential`, Managed Identity và least-privilege access.

### Senior

Thiết kế secret caching, rotation, failure behavior và network/RBAC troubleshooting.

### Technical Lead / Architect

Ưu tiên passwordless/workload identity nơi khả thi và chuẩn hóa secret ownership/audit/rotation toàn platform.

## 11. Key takeaway

- Tốt nhất không phải “giấu secret tốt hơn” mà là loại static secret nơi có thể.
- Managed Identity giải quyết workload authentication; Key Vault giải quyết secret/key storage và access control.
- Least privilege, rotation và observability vẫn cần thiết.

# 9. Consumer-driven contract testing: bắt API breaking change trước khi deploy mà không cần full E2E environment

## 1. What is it?

Consumer-driven contract testing kiểm tra rằng provider API vẫn đáp ứng những interactions mà consumers thực sự phụ thuộc.

Mental model:

```text
Consumer expectations
       |
       v
contract artifact
       |
       v
Provider verification
       |
breaking change detected in CI
```

Nó nằm giữa unit/integration tests và full end-to-end tests.

## 2. Why does it exist?

Microservices/distributed systems thường có independent deployment. Provider có thể đổi field, status code hoặc nullable semantics mà unit tests của provider vẫn xanh. Full E2E environment lại chậm, brittle và khó cover mọi consumer version.

Contract tests bảo vệ interface compatibility cụ thể.

## 3. How does it work?

Consumer tạo contract từ expected interaction, ví dụ:

```text
GET /customers/123
-> 200
-> body contains:
   id: string
   displayName: string
```

Provider CI chạy verification trên current implementation. Nếu đổi `displayName` thành `name` mà consumer chưa migrate, provider build fail trước deploy.

## 4. Practical implementation

Contract nên kiểm tra behavior consumer thực sự dùng, không snapshot toàn payload vô nghĩa.

Ví dụ consumer chỉ cần:

```json
{
  "id": "123",
  "displayName": "Ha"
}
```

Nếu provider thêm field `avatarUrl`, contract không nên fail. Nếu provider xóa `displayName`, phải fail.

Kết hợp provider states/test fixtures để tái tạo deterministic scenarios như customer exists/not found.

## 5. Real production scenario

Team A đổi API từ `404` sang `200 { data: null }` vì frontend mới chấp nhận. Một background service cũ của Team B dựa vào 404 để phân biệt missing customer và transient empty response.

Provider unit tests pass, frontend E2E pass, nhưng background service production behavior sai. Contract test của Team B có thể bắt semantic break này.

## 6. Failure scenario & troubleshooting

**Symptom** → provider deploy thành công nhưng một consumer cũ lỗi parsing hoặc branch sai theo status code.

**Evidence** → API schema có vẻ tương thích nhưng actual consumer expectation khác.

**Hypothesis** → compatibility được đánh giá từ provider perspective thay vì consumer usage.

**Diagnosis** → inventory deployed consumer versions và interactions thực tế.

**Fix** → contract verification + backward-compatible migration/deprecation plan.

**Verification** → provider candidate build verify với contracts của active consumers trước release.

## 7. Common mistakes

- Snapshot toàn JSON response làm contract quá brittle.
- Dùng contract tests thay cho provider integration tests.
- Chỉ test schema type mà bỏ status codes/headers/behavior.
- Không biết consumer versions nào còn production.
- Cho contract broker trở thành mandatory complexity khi hệ thống chỉ có một client đơn giản.

## 8. Alternatives

- OpenAPI schema compatibility checks cho broad structural contracts.
- Integration tests giữa hai services khi topology đơn giản.
- Full E2E cho critical user journeys xuyên nhiều components.

## 9. Trade-offs

### Advantages

- Feedback nhanh cho breaking changes.
- Không cần deploy toàn hệ thống để verify basic compatibility.
- Capture consumer-relevant behavior.

### Costs / Risks

- Contract lifecycle/versioning cần governance.
- Provider states/test data có thể phức tạp.
- Không thay thế network, auth, deployment và true E2E validation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu API compatibility không chỉ là code compile.

### Middle

Viết contract cho behavior consumer thực sự dùng.

### Senior

Phân tầng unit/integration/contract/E2E tests theo risk và failure boundary.

### Technical Lead / Architect

Quyết định khi contract-testing infrastructure đáng giá và gắn nó với API deprecation/version strategy.

## 11. Key takeaway

- Contract tests bảo vệ compatibility giữa independently deployed components.
- Test consumer-relevant behavior, không snapshot mọi byte.
- Contract tests bổ sung chứ không thay thế integration và E2E tests.

# 10. Docker multi-stage builds: tách build environment khỏi runtime image để giảm image size và attack surface

## 1. What is it?

Multi-stage Docker build dùng nhiều `FROM` stages: một stage chứa SDK/build tools, stage cuối chỉ chứa runtime artifacts cần để chạy application.

Mental model:

```text
SDK image
  |
restore -> build -> publish
  |
  v
/publish output
  |
COPY
  v
runtime image
```

Final image không cần compiler, source code hay package-manager caches.

## 2. Why does it exist?

Nếu deploy nguyên SDK image, container lớn hơn, pull/start chậm hơn và chứa nhiều binaries/packages không cần ở runtime. Mỗi tool dư thừa cũng mở rộng attack surface và patching burden.

## 3. How does it work?

Ví dụ .NET:

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet restore
RUN dotnet publish -c Release -o /out --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /out .
ENTRYPOINT ["dotnet", "MyApp.dll"]
```

Build stage bị bỏ khỏi final filesystem; chỉ artifacts được copy sang runtime stage.

## 4. Practical implementation

Tối ưu build cache bằng cách copy project/lock files trước source files khi cấu trúc repo cho phép:

```dockerfile
COPY MyApp.csproj ./
RUN dotnet restore
COPY . ./
RUN dotnet publish -c Release -o /out --no-restore
```

Thêm `.dockerignore` để loại `.git`, local artifacts, secrets và directories không cần vào build context.

Runtime nên chạy non-root khi image/application requirements cho phép.

## 5. Real production scenario

CI build image từ SDK base nặng hơn 1 GB vì team deploy cùng stage dùng để compile. Cluster node pull image lâu khi scale-out, registry transfer tăng và vulnerability scan trả nhiều CVEs từ build tooling không hề cần ở production.

Chuyển multi-stage build giảm đáng kể runtime image và số packages phải patch.

## 6. Failure scenario & troubleshooting

**Symptom** → image rất lớn, cold deployment chậm hoặc runtime container chứa `dotnet` SDK/tools không cần thiết.

**Evidence** → `docker history` cho thấy build caches/source/packages nằm trong final layers.

**Hypothesis** → build và runtime concerns chưa được tách.

**Diagnosis** → inspect Dockerfile stages, image layers và build context.

**Fix** → multi-stage build, copy chỉ publish output, `.dockerignore`, chọn runtime base phù hợp.

**Verification** → so sánh image size, package inventory, pull/start time và vulnerability scan trước/sau.

## 7. Common mistakes

- Copy toàn repo vào runtime image.
- Đưa `.env`/secrets vào image layer rồi xóa ở layer sau; secret vẫn có thể tồn tại trong history/layer.
- Dùng SDK image production chỉ vì dễ debug.
- Gộp restore/build steps khiến cache invalidated liên tục.
- Pin `latest` vô điều kiện và mất reproducibility.
- Chạy root mặc định mà không có lý do.

## 8. Alternatives

- Native/AOT hoặc distroless/chiseled images khi workload và operational tooling phù hợp.
- Buildpacks khi muốn standardize build without handwritten Dockerfile.
- Không containerize nếu deployment target hiện tại (ví dụ IIS/App Service code deploy) đơn giản hơn và container không giải quyết vấn đề thực tế.

## 9. Trade-offs

### Advantages

- Runtime image nhỏ hơn.
- Ít packages/tools hơn, giảm attack surface.
- Tách rõ build dependencies khỏi runtime dependencies.

### Costs / Risks

- Dockerfile/build caching cần hiểu đúng để CI nhanh.
- Minimal images có thể thiếu shell/debug tools khi incident.
- Base image strategy và patch cadence vẫn cần quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu image là immutable filesystem layers và build stage khác runtime stage.

### Middle

Viết multi-stage Dockerfile, `.dockerignore` và tận dụng cache hợp lý.

### Senior

Tối ưu reproducibility, non-root runtime, image scanning và cold-start/pull behavior.

### Technical Lead / Architect

Định nghĩa golden base images, patch policy, registry strategy và quyết định khi containerization thực sự mang lại giá trị.

## 11. Key takeaway

- Production image chỉ nên chứa những gì application cần để chạy.
- Multi-stage build giảm size và attack surface bằng cách bỏ build toolchain khỏi runtime.
- Containerization là deployment choice; đừng thêm nó nếu operational complexity vượt giá trị mang lại.
