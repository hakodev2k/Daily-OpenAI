# 1. .NET `System.IO.Pipelines`: xử lý streaming buffer hiệu quả mà không tự viết một hệ thống buffer ownership khó kiểm soát

## 1. What is it?

`System.IO.Pipelines` là abstraction của .NET cho producer/consumer streaming I/O dựa trên buffer. Mental model quan trọng không phải “một Stream khác”, mà là một pipeline trong đó producer ghi bytes vào `PipeWriter`, consumer đọc các segments qua `PipeReader`, và hai phía phối hợp ownership/backpressure mà không cần liên tục `new byte[]`, copy và compact buffer thủ công.

```text
Socket / Stream
      |
      v
 PipeWriter
      |
  buffered data
      |
      v
 PipeReader
      |
      v
 parser / protocol handler
```

Nó đặc biệt hữu ích khi dữ liệu đến theo chunk nhưng logical message không trùng với chunk boundary.

## 2. Why does it exist?

Network code viết trực tiếp trên `Stream.ReadAsync` thường nhanh chóng phải tự giải quyết:

- một message có thể bị chia thành nhiều reads;
- một read có thể chứa nhiều messages;
- partial message phải giữ lại cho lần sau;
- buffer phải resize/compact;
- allocation và copy tăng khi throughput cao;
- consumer chậm hơn producer cần backpressure.

Một implementation thủ công dễ đúng ở happy path nhưng sai ở partial read, cancellation hoặc memory ownership. `Pipelines` chuẩn hóa các vấn đề này.

## 3. How does it work?

`PipeReader.ReadAsync` trả `ReadResult` chứa `ReadOnlySequence<byte>`. Sequence có thể gồm nhiều memory segments, nên parser không nên giả định toàn bộ payload nằm trong một contiguous array.

Sau khi inspect data, consumer gọi:

```csharp
reader.AdvanceTo(consumed, examined);
```

Hai vị trí này có semantics khác nhau:

- `consumed`: bytes đã xử lý xong và có thể reclaim;
- `examined`: bytes đã xem xét đến đâu.

Nếu dùng sai, pipeline có thể giữ memory quá lâu hoặc loop liên tục mà không chờ thêm dữ liệu.

Backpressure xuất hiện khi writer flush nhưng lượng buffered data vượt thresholds, khiến producer phải chờ consumer tiến lên.

## 4. Practical implementation

Ví dụ đọc protocol line-delimited:

```csharp
static async Task ReadLinesAsync(
    PipeReader reader,
    CancellationToken ct)
{
    while (true)
    {
        ReadResult result = await reader.ReadAsync(ct);
        ReadOnlySequence<byte> buffer = result.Buffer;

        while (TryReadLine(ref buffer, out var line))
        {
            Process(line);
        }

        reader.AdvanceTo(buffer.Start, buffer.End);

        if (result.IsCompleted)
            break;
    }

    await reader.CompleteAsync();
}

static bool TryReadLine(
    ref ReadOnlySequence<byte> buffer,
    out ReadOnlySequence<byte> line)
{
    var position = buffer.PositionOf((byte)'\n');
    if (position is null)
    {
        line = default;
        return false;
    }

    line = buffer.Slice(0, position.Value);
    buffer = buffer.Slice(buffer.GetPosition(1, position.Value));
    return true;
}
```

Điểm đáng chú ý: parser hoạt động trên sequence thay vì copy thành array/string trước khi biết có cần copy hay không.

## 5. Real production scenario

Một service nhận telemetry qua TCP. Mỗi connection gửi hàng nghìn records/second. Version cũ đọc vào array, ghép phần dư sang array mới, rồi `Encoding.UTF8.GetString` cho toàn frame trước khi parse.

Profiler cho thấy allocation rate cao và CPU dành đáng kể cho copying/GC. Chuyển framing layer sang `Pipelines` giúp giữ bytes trong pooled buffers, parse boundary trực tiếp trên `ReadOnlySequence<byte>`, và chỉ materialize fields thực sự cần.

Business logic phía trên không cần biết về `PipeReader`; complexity được giữ ở transport boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng dần dù throughput ổn; hoặc consumer loop CPU cao khi input dừng giữa một frame.

**Evidence** → buffered bytes tăng; traces cho thấy `ReadAsync` hoàn thành liên tục; code gọi `AdvanceTo` với positions sai hoặc không consume dữ liệu đã xử lý.

**Hypothesis** → pipeline không reclaim buffer hoặc `examined` semantics khiến reader tin consumer vẫn cần được gọi ngay.

**Diagnosis** → log size của unread sequence, consumed/examined progress và message boundaries; tạo tests với payload bị chia ở mọi vị trí có thể.

**Fix** → đảm bảo mỗi iteration hoặc consume data, hoặc đánh dấu examined tới cuối buffer để chờ thêm bytes; giới hạn frame size để tránh attacker giữ buffer vô hạn.

**Verification** → soak test với fragmented frames, slow producer, slow consumer và malformed oversized message; memory phải ổn định.

## 7. Common mistakes

- Giả định `ReadOnlySequence<byte>` luôn có một segment rồi gọi `.FirstSpan` như toàn payload.
- Copy sang array ngay lập tức, làm mất phần lớn lợi ích của pipeline.
- Không giới hạn maximum frame/message size.
- Dùng `AdvanceTo` sai khiến memory retention hoặc busy loop.
- Đưa `Pipelines` vào business layer dù vấn đề chỉ nằm ở transport parser.
- Tối ưu low-level I/O khi bottleneck thực tế là SQL/downstream API.

## 8. Alternatives

- `Stream`: đơn giản và hoàn toàn phù hợp cho nhiều workload không cần complex framing.
- `SequenceReader<T>` trên `ReadOnlySequence<T>`: hỗ trợ parser structured data trên sequence.
- High-level protocol libraries như HTTP/gRPC: nên dùng nếu protocol đã được giải quyết sẵn, thay vì tự xây transport.

## 9. Trade-offs

### Advantages

- Giảm allocation/copy trong streaming hot path.
- Xử lý partial reads và multi-segment buffers tốt.
- Có backpressure và buffer lifecycle rõ hơn hand-written loop.

### Costs / Risks

- API phức tạp hơn `Stream`.
- `consumed`/`examined` semantics dễ dùng sai.
- Low-level optimization tăng cognitive load nếu workload không cần.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu network read boundary không phải message boundary và buffer có thể chứa partial/multiple messages.

### Middle

Biết đọc `PipeReader`, parse `ReadOnlySequence<byte>`, xử lý cancellation/completion và viết fragmentation tests.

### Senior

Biết điều tra allocation, memory retention, backpressure và framing attacks; chỉ dùng Pipelines khi evidence cho thấy transport layer cần nó.

### Technical Lead / Architect

Quyết định low-level pipeline nên nằm ở boundary nào, library nào có thể thay thế custom protocol code, và complexity có được justified bởi throughput/latency requirements hay không.

## 11. Key takeaway

- `Pipelines` giải quyết streaming buffer lifecycle và partial-read complexity, không chỉ là API đọc bytes nhanh hơn.
- `AdvanceTo(consumed, examined)` là correctness-critical.
- Giữ optimization ở transport hot path; không lan low-level abstraction vào business code nếu không cần.

# 2. EF Core `SaveChangesInterceptor`: audit, persistence hooks và vì sao interceptor không nên trở thành nơi giấu business logic

## 1. What is it?

`SaveChangesInterceptor` là extension point cho phép code quan sát hoặc can thiệp vào lifecycle của `DbContext.SaveChanges` / `SaveChangesAsync`.

Mental model:

```text
Application changes entities
        |
        v
ChangeTracker
        |
        v
SavingChanges interceptor
        |
        v
SQL commands / transaction
        |
   success / failure
        |
        v
SavedChanges / SaveChangesFailed
```

Interceptor phù hợp với cross-cutting persistence concerns như audit metadata, diagnostics hoặc capture domain events. Nó không phải một “hidden service layer”.

## 2. Why does it exist?

Nếu mọi service phải nhớ set `UpdatedAtUtc`, `UpdatedBy`, emit audit record hoặc log persistence timing, logic sẽ lặp và dễ bị bỏ sót.

Interceptor tạo một centralized hook ở persistence boundary. Nhưng vì hook chạy implicit, business rule quan trọng bị giấu ở đây sẽ làm flow khó reasoning và test.

Một rule như “order trên 100 triệu phải được manager approve” không nên chỉ tồn tại trong `SaveChangesInterceptor`.

## 3. How does it work?

EF Core gọi interceptor trước/sau save và khi save thất bại. Interceptor có access tới `DbContext` và `ChangeTracker`, nên có thể inspect `EntityEntry` states.

Ví dụ audit timestamps:

```text
Added    -> CreatedAtUtc + UpdatedAtUtc
Modified -> UpdatedAtUtc
Deleted  -> maybe audit record, not silently convert unless policy says so
```

Thứ tự quan trọng nếu nhiều interceptors cùng mutate state. Interceptor cũng phải tôn trọng async path nếu nó cần I/O.

## 4. Practical implementation

```csharp
public sealed class AuditTimestampInterceptor : SaveChangesInterceptor
{
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData,
        InterceptionResult<int> result,
        CancellationToken ct = default)
    {
        var db = eventData.Context;
        if (db is null)
            return base.SavingChangesAsync(eventData, result, ct);

        var now = DateTimeOffset.UtcNow;

        foreach (var entry in db.ChangeTracker.Entries<IAuditable>())
        {
            if (entry.State == EntityState.Added)
                entry.Entity.CreatedAtUtc = now;

            if (entry.State is EntityState.Added or EntityState.Modified)
                entry.Entity.UpdatedAtUtc = now;
        }

        return base.SavingChangesAsync(eventData, result, ct);
    }
}
```

Registration:

```csharp
builder.Services.AddSingleton<AuditTimestampInterceptor>();

builder.Services.AddDbContext<AppDbContext>((sp, options) =>
{
    options.UseSqlServer(connectionString);
    options.AddInterceptors(
        sp.GetRequiredService<AuditTimestampInterceptor>());
});
```

Nếu interceptor cần request/user state, lifetime phải được thiết kế cẩn thận thay vì mặc định singleton.

## 5. Real production scenario

Enterprise platform cần mọi mutable entity có audit timestamps và actor identifier. Trước đây mỗi handler tự set fields; một batch import path quên làm, khiến audit trail thiếu dữ liệu.

Một interceptor đảm bảo technical audit metadata được áp dụng thống nhất. Business audit event như “SalaryChanged” vẫn được tạo explicit từ application/domain workflow vì nó có semantics nghiệp vụ khác timestamp kỹ thuật.

## 6. Failure scenario & troubleshooting

**Symptom** → một save đơn giản bất ngờ thực hiện thêm queries hoặc chậm vài trăm milliseconds.

**Evidence** → trace cho thấy interceptor gọi external user service/database lookup trong `SavingChangesAsync` cho mỗi entity.

**Hypothesis** → cross-cutting hook đang thực hiện hidden I/O/N+1 work.

**Diagnosis** → instrument duration của interceptor, inspect SQL/dependency spans và số entries được scan.

**Fix** → đưa required actor/context vào request scope trước save; tránh external lookup trong interceptor; precompute metadata hoặc dùng local context abstraction.

**Verification** → `SaveChanges` latency trở lại baseline và audit correctness vẫn được giữ.

## 7. Common mistakes

- Đưa business validation quan trọng vào interceptor để “khỏi quên gọi”.
- Thực hiện network I/O trong mỗi save.
- Publish integration event trực tiếp trước transaction commit rồi tưởng event và DB atomic.
- Mutate mọi Modified entry mà không hiểu owned entities/change detection.
- Inject scoped dependency vào singleton interceptor.
- Catch `SaveChangesFailed` rồi nuốt exception.

## 8. Alternatives

- Override `DbContext.SaveChanges`: đơn giản hơn cho local context-specific behavior.
- Application/domain layer explicit logic: tốt hơn cho business semantics cần nhìn thấy trong use case.
- Database trigger: mạnh khi nhiều applications ghi cùng DB nhưng khó test/version/debug từ application.
- Outbox + explicit domain event collection: tốt cho reliable integration event publication.

## 9. Trade-offs

### Advantages

- Centralize persistence cross-cutting concerns.
- Giảm duplicated technical code.
- Có hook cho success/failure diagnostics.

### Costs / Risks

- Behavior implicit, khó phát hiện khi đọc application handler.
- Có thể thêm hidden latency hoặc side effects.
- Lifetime/order giữa interceptors cần quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu interceptor chạy quanh persistence operation và không thay thế service/domain layer.

### Middle

Biết implement audit interceptor, inspect `ChangeTracker` và test Added/Modified/Delete paths.

### Senior

Phân biệt technical persistence concern với business invariant; tránh hidden I/O và thiết kế lifetime/transaction semantics đúng.

### Technical Lead / Architect

Quyết định concerns nào được phép implicit ở persistence boundary, đặt conventions về interceptor ownership và đảm bảo integration side effects vẫn có reliable delivery architecture.

## 11. Key takeaway

- `SaveChangesInterceptor` phù hợp cho cross-cutting persistence behavior, không phải nơi giấu business workflow.
- Hidden I/O trong interceptor có thể biến mọi save thành production bottleneck.
- Transaction và event publication semantics phải được thiết kế explicit.

# 3. SQL Server `tempdb` và version store: vì sao query bình thường vẫn có thể gây contention, disk growth và production slowdown

## 1. What is it?

`tempdb` là shared system database SQL Server dùng cho nhiều loại temporary/internal work: temporary tables, table variables, sorts, hashes, row versioning, spill operations và một số engine internals.

Mental model:

```text
User databases
   |       |       |
   +-------+-------+
           |
           v
        tempdb
   temporary/shared work area
```

Version store trong `tempdb` giữ older row versions cho các isolation features như `READ_COMMITTED_SNAPSHOT` hoặc Snapshot Isolation.

## 2. Why does it exist?

Database engine cần working space ngoài memory để thực hiện operations vượt memory grant hoặc giữ historical versions phục vụ concurrent readers.

Một query không hề tạo `#temp` vẫn có thể dùng `tempdb` nếu sort/hash spill. Một transaction đọc theo snapshot không viết `tempdb` trực tiếp nhưng long-running transaction có thể ngăn row versions được cleanup.

Vì `tempdb` là shared resource, một workload xấu có thể ảnh hưởng nhiều databases trên cùng instance.

## 3. How does it work?

Hai pressure modes thường gặp:

```text
Large sort/hash + insufficient memory grant
        -> spill to tempdb

Long-running snapshot transaction
        -> old row versions retained
        -> version store grows
```

Engine cleanup version store chỉ khi không còn transaction nào cần các versions cũ. Vì vậy một report transaction mở hàng giờ có thể giữ rất nhiều version data dù chính report không update rows.

## 4. Practical implementation

Khi điều tra, bắt đầu từ evidence thay vì tăng disk ngay:

```sql
SELECT
    SUM(user_object_reserved_page_count) * 8 / 1024.0 AS UserObjectsMB,
    SUM(internal_object_reserved_page_count) * 8 / 1024.0 AS InternalObjectsMB,
    SUM(version_store_reserved_page_count) * 8 / 1024.0 AS VersionStoreMB
FROM sys.dm_db_file_space_usage;
```

Tìm long-running transactions và query plans có spills. Execution plan warnings như sort/hash spill là dấu hiệu memory grant/query shape cần xem xét.

Pre-size `tempdb` phù hợp và cấu hình files theo guidance của version SQL Server đang vận hành, nhưng configuration không thay thế root-cause analysis.

## 5. Real production scenario

Một reporting query được deploy và chạy mỗi 5 phút. Query sort hàng chục triệu rows, estimate sai khiến memory grant nhỏ và spill mạnh sang `tempdb`. Đồng thời hệ thống dùng `READ_COMMITTED_SNAPSHOT`.

Khi report kéo dài, write-heavy OLTP tạo row versions nhanh hơn cleanup. `tempdb` disk tăng, I/O latency cao và unrelated order APIs bắt đầu chậm.

Incident nhìn ban đầu giống “SQL Server toàn hệ thống tự nhiên chậm”, nhưng shared pressure nằm ở `tempdb`.

## 6. Failure scenario & troubleshooting

**Symptom** → database latency tăng đồng loạt; `tempdb` file growth; storage latency hoặc space alert.

**Evidence** → version store/internal object usage tăng; long-running transactions; execution plans có spill warnings.

**Hypothesis** → một workload giữ row versions hoặc tạo excessive worktable/spill.

**Diagnosis** → correlate growth timeline với active requests/jobs, transaction age, waits và query plans.

**Fix** → kết thúc/fix long-running transaction, cải thiện query/index/statistics để giảm spill, batch workload lớn, đảm bảo `tempdb` capacity phù hợp.

**Verification** → version store/internal usage trở về baseline, disk latency và p95 query latency phục hồi.

## 7. Common mistakes

- Chỉ tăng `tempdb` size mà không tìm workload gây growth.
- Cho rằng `tempdb` chỉ liên quan `#temp` tables.
- Giữ transaction mở quanh report/user think time.
- Bỏ qua spill warnings vì query vẫn “chạy xong”.
- Shrink `tempdb` thường xuyên như maintenance routine.
- Thay đổi file count theo một con số truyền miệng mà không xét SQL Server version/CPU/workload.

## 8. Alternatives

Không có “database khác thay `tempdb`” trong cùng SQL Server instance; alternatives nằm ở workload design:

- tối ưu query/index/statistics;
- batch large operations;
- tách heavy analytics khỏi OLTP instance;
- dùng read replica/reporting store khi business workload phù hợp.

## 9. Trade-offs

### Advantages

- Row versioning giảm reader/writer blocking trong nhiều workload.
- Shared temporary workspace cho phép engine thực hiện complex operations linh hoạt.

### Costs / Risks

- Shared resource tạo blast radius lớn.
- Snapshot semantics cần storage cho versions.
- Spill có thể chuyển memory-estimation problem thành disk-I/O problem.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `tempdb` là shared working database của SQL Server, không chỉ nơi chứa temporary tables.

### Middle

Biết đọc `sys.dm_db_file_space_usage`, nhận diện spill warning và transaction kéo dài.

### Senior

Correlate version store, memory grants, query plans, waits và I/O để tìm root cause thay vì chỉ mở rộng disk.

### Technical Lead / Architect

Quyết định workload nào nên ở OLTP instance, capacity/monitoring cho `tempdb`, và khi nào reporting/analytics cần tách architecture.

## 11. Key takeaway

- `tempdb` pressure có thể đến từ row versioning và query spills dù application không tạo temp table.
- Long-running transactions có thể giữ version store rất lâu.
- Điều tra workload + plan + transaction age trước khi coi thêm disk là “fix”.

# 4. PostgreSQL `JSONB` + GIN index: giữ schema linh hoạt nhưng vẫn phải thiết kế query/index như một database có cấu trúc

## 1. What is it?

`JSONB` lưu JSON ở binary representation cho phép PostgreSQL query operators và indexing hiệu quả hơn plain JSON text. GIN (Generalized Inverted Index) có thể index nhiều keys/values bên trong documents để hỗ trợ containment/existence queries.

Mental model:

```text
Relational columns -> stable, typed, frequently constrained fields
JSONB              -> flexible attributes with queryable structure
GIN index          -> inverted lookup into JSONB content
```

`JSONB` không có nghĩa là “không cần schema”. Schema chỉ chuyển một phần responsibility từ DDL sang application/data contracts.

## 2. Why does it exist?

Một product catalog có core fields ổn định (`Id`, `Sku`, `Price`) nhưng attributes thay đổi theo category: laptop có RAM/CPU, clothing có size/material.

Tạo hàng trăm nullable columns hoặc EAV model có thể phức tạp. `JSONB` cho phép giữ flexible attributes trong cùng row, vẫn query được khi cần.

## 3. How does it work?

Ví dụ:

```sql
CREATE TABLE products (
    id bigint PRIMARY KEY,
    sku text NOT NULL,
    price numeric(18,2) NOT NULL,
    attributes jsonb NOT NULL
);
```

Query containment:

```sql
SELECT id, sku
FROM products
WHERE attributes @> '{"brand":"Contoso"}';
```

GIN index:

```sql
CREATE INDEX ix_products_attributes_gin
ON products
USING gin (attributes);
```

Operator class (`jsonb_ops` vs `jsonb_path_ops`) ảnh hưởng operators được hỗ trợ, index size và performance profile.

## 4. Practical implementation

Nếu một attribute trở thành first-class query/sort/filter field rất thường xuyên, cân nhắc promoted generated/real column thay vì mãi giữ trong generic JSONB.

Ví dụ expression index cho một path cụ thể:

```sql
CREATE INDEX ix_products_brand
ON products ((attributes ->> 'brand'));
```

Sau đó query đúng expression:

```sql
SELECT id, sku
FROM products
WHERE attributes ->> 'brand' = 'Contoso';
```

Luôn kiểm tra `EXPLAIN (ANALYZE, BUFFERS)` với workload/cardinality thật.

## 5. Real production scenario

Marketplace có hàng triệu listings và mỗi category mang custom specifications. Ban đầu team tạo GIN index trên toàn `attributes`, giúp flexible filtering nhanh.

Sau vài tháng, `brand`, `condition` và `year` trở thành filters gần như mọi request. Generic GIN index phình lớn, write cost tăng. Team promote các fields nóng thành typed columns/index riêng, giữ long-tail attributes trong JSONB.

Đây là evolution theo access pattern, không phải thất bại của JSONB.

## 6. Failure scenario & troubleshooting

**Symptom** → insert/update chậm dần, index storage lớn, một số JSON filters vẫn scan nhiều rows.

**Evidence** → GIN index size lớn; `EXPLAIN` cho selectivity thấp hoặc operator/query shape không dùng index mong muốn.

**Hypothesis** → generic JSONB index đang index quá nhiều data hoặc query không match operator class/expression.

**Diagnosis** → inspect index usage, query operators, cardinality, `BUFFERS`, write workload.

**Fix** → expression index cho hot path, chọn operator class phù hợp, promote stable fields, loại index không tạo giá trị.

**Verification** → compare read latency, buffer reads, index size và write throughput trước/sau.

## 7. Common mistakes

- Đưa tất cả columns vào JSONB để “schema flexible”.
- Không validate document shape ở application boundary.
- Tạo một giant GIN index rồi kỳ vọng mọi JSON expression đều nhanh.
- Sort numeric value bằng text extraction khiến semantics sai.
- Dùng JSONB cho relational relationships cần FK/integrity rõ.
- Không theo dõi write amplification/index size.

## 8. Alternatives

- Typed relational columns: tốt nhất cho stable fields, constraints, joins và frequent filtering.
- Separate attribute table/EAV: đôi khi phù hợp nhưng query/integrity phức tạp.
- Document database: hợp nếu aggregate/document access pattern chiếm ưu thế toàn hệ thống.
- Hybrid relational + JSONB: thường là lựa chọn thực tế cho flexible metadata.

## 9. Trade-offs

### Advantages

- Flexible shape trong relational database.
- Queryable và indexable.
- Tránh schema explosion cho long-tail attributes.

### Costs / Risks

- Type/data-quality constraints yếu hơn nếu không bổ sung validation.
- GIN index có storage/write cost đáng kể.
- Query semantics/indexing phức tạp hơn typed columns.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu JSONB vẫn là structured data và query operator phải đúng semantics.

### Middle

Biết tạo GIN/expression index và dùng `EXPLAIN ANALYZE` để xác minh.

### Senior

Thiết kế hybrid schema dựa selectivity, write cost và field evolution; biết khi nào promote field thành column.

### Technical Lead / Architect

Quyết định flexible data boundary, governance/validation và liệu PostgreSQL hybrid model có đơn giản hơn đưa thêm document database vào hệ thống hay không.

## 11. Key takeaway

- JSONB mang flexibility, không loại bỏ nhu cầu schema thinking.
- Generic GIN index có cost; hot fields thường cần index/model chuyên biệt.
- Thiết kế theo access pattern và đo cả read lẫn write workload.

# 5. Domain Events vs Integration Events: tách business reaction trong boundary khỏi contract giao tiếp ra bên ngoài

## 1. What is it?

Domain Event biểu diễn một business fact đã xảy ra trong domain/bounded context, ví dụ `OrderApproved`. Integration Event là contract được publish ra ngoài boundary để systems khác phản ứng, ví dụ `OrderApprovedV2` trên message broker.

Chúng có thể mang ý nghĩa gần nhau nhưng không nên mặc định là cùng object/class.

```text
Domain model
   |
   | Domain Event
   v
Application handlers
   |
   | translate / decide publication
   v
Integration Event
   |
   v
Broker -> external consumers
```

## 2. Why does it exist?

Domain model cần vocabulary tối ưu cho business invariants nội bộ. External consumers cần stable contract, compatibility và ownership rõ.

Nếu publish thẳng domain object ra broker, mỗi refactor nội bộ có thể trở thành breaking integration change. Ngược lại, nếu domain layer phụ thuộc broker DTO, external contract kéo infrastructure concern vào business core.

Tách hai khái niệm giúp giảm accidental coupling.

## 3. How does it work?

Flow điển hình:

```text
Command
 -> Aggregate changes state
 -> records Domain Event
 -> application handles local reactions
 -> transaction commits
 -> outbox stores Integration Event
 -> publisher sends to broker
```

Một Domain Event có thể:

- chỉ gây local reaction;
- map thành một Integration Event;
- hoặc không publish gì ra ngoài.

Một Integration Event cũng có thể tổng hợp data từ nhiều domain facts để tạo contract hữu ích cho consumer.

## 4. Practical implementation

Domain event:

```csharp
public sealed record OrderApproved(
    Guid OrderId,
    DateTimeOffset ApprovedAtUtc) : IDomainEvent;
```

Integration contract:

```csharp
public sealed record OrderApprovedV1(
    Guid OrderId,
    string CustomerReference,
    decimal Total,
    DateTimeOffset OccurredAtUtc);
```

Application handler map explicit và ghi integration event vào outbox cùng transaction thay vì gọi broker trực tiếp từ entity.

## 5. Real production scenario

Trong commerce platform, khi Order được approve:

- domain handler cập nhật local eligibility state;
- application tạo audit entry;
- fulfillment service cần Integration Event;
- analytics có thể consume cùng public event hoặc một event riêng tối ưu cho reporting.

Sau này domain refactor `CustomerReference` thành Value Object không buộc external consumers thay contract nếu mapping boundary vẫn giữ compatibility.

## 6. Failure scenario & troubleshooting

**Symptom** → một thay đổi nhỏ trong domain model làm nhiều consumers fail deserialize.

**Evidence** → broker payload chính là serialized domain entity/event type; không có versioning/mapping boundary.

**Hypothesis** → internal model bị dùng như public integration contract.

**Diagnosis** → map ownership của event schemas và consumers; inspect change history.

**Fix** → tạo explicit integration contract, compatibility policy và translation layer; dùng outbox để publish sau persistence boundary đáng tin cậy.

**Verification** → domain refactor không đổi wire contract; consumer contract tests vẫn pass.

## 7. Common mistakes

- Gọi mọi message là Domain Event.
- Publish domain entity nguyên object ra broker.
- Cho domain project reference Service Bus/Kafka client.
- Dùng synchronous domain event handler để gọi external API trong transaction.
- Không version integration schema.
- Tạo event cho mọi setter dù không có business meaning.

## 8. Alternatives

- Direct synchronous application call trong cùng module: đơn giản hơn nếu không cần decoupling.
- Database transaction + explicit service orchestration: đủ cho use case local.
- Integration event qua broker: phù hợp cross-service asynchronous boundary.

Không phải mọi local reaction cần event; method call rõ ràng đôi khi maintainable hơn.

## 9. Trade-offs

### Advantages

- Domain model không bị khóa bởi public wire contract.
- External contract có lifecycle/versioning riêng.
- Bounded context ownership rõ hơn.

### Costs / Risks

- Thêm mapping và event lifecycle concepts.
- Eventual consistency xuất hiện khi publish cross-boundary.
- Overuse events có thể làm control flow khó theo dõi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event là fact đã xảy ra, khác command là yêu cầu thực hiện điều gì đó.

### Middle

Biết tạo domain event, handler và map integration DTO rõ ràng.

### Senior

Reasoning về transaction boundary, outbox, contract versioning và event ownership.

### Technical Lead / Architect

Quyết định boundary nào thực sự cần asynchronous integration event, event contract thuộc team nào và khi nào direct call đơn giản hơn event-driven architecture.

## 11. Key takeaway

- Domain Event phục vụ model/boundary nội bộ; Integration Event phục vụ contract bên ngoài.
- Không serialize domain model thành public API chỉ để tiết kiệm mapping.
- Events tăng decoupling nhưng cũng tăng flow/operational complexity; dùng khi boundary thật sự cần.

# 6. Inbox Pattern và idempotent consumer: xử lý message at-least-once mà không tạo duplicate side effects

## 1. What is it?

Inbox Pattern lưu identifier/trạng thái của message đã xử lý ở phía consumer để cùng message được deliver lại không thực hiện business side effect lần nữa.

Mental model:

```text
Broker may deliver MessageId=123 more than once

Consumer transaction:
  check Inbox(123)
  if exists -> no-op / acknowledge
  else
     apply business change
     insert Inbox(123)
  commit
```

Đây là cách biến at-least-once delivery thành effectively-once business effect trong một consistency boundary cụ thể.

## 2. Why does it exist?

Messaging systems thường không thể bảo đảm end-to-end exactly-once cho business side effects. Failure window phổ biến:

```text
consumer commits DB change
process crashes before ACK
broker redelivers
```

Nếu handler charge payment hoặc create shipment lần nữa, duplicate delivery trở thành business incident.

Retry là cần cho reliability, nên consumer phải chịu được replay.

## 3. How does it work?

Inbox cần stable idempotency key, thường là `MessageId` do producer tạo. Consumer check/insert inbox trong cùng local transaction với business state nếu muốn atomicity.

Unique constraint là guard cuối cùng chống race:

```sql
CREATE TABLE InboxMessages (
    ConsumerName nvarchar(100) NOT NULL,
    MessageId uniqueidentifier NOT NULL,
    ProcessedAtUtc datetime2 NOT NULL,
    CONSTRAINT PK_InboxMessages
        PRIMARY KEY (ConsumerName, MessageId)
);
```

`ConsumerName` hữu ích nếu nhiều handlers independently consume cùng message identity.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

var exists = await db.InboxMessages.AnyAsync(
    x => x.ConsumerName == "Fulfillment" &&
         x.MessageId == message.Id,
    ct);

if (!exists)
{
    await fulfillment.ApplyAsync(message, ct);

    db.InboxMessages.Add(new InboxMessage
    {
        ConsumerName = "Fulfillment",
        MessageId = message.Id,
        ProcessedAtUtc = DateTimeOffset.UtcNow
    });

    await db.SaveChangesAsync(ct);
}

await tx.CommitAsync(ct);
```

Trong high-concurrency scenario, rely vào unique key + handling duplicate-key race thay vì coi `AnyAsync` là synchronization guarantee.

## 5. Real production scenario

Service Bus consumer nhận `OrderPaid`. Handler tạo shipment. Production restart xảy ra sau khi shipment row commit nhưng trước message complete. Message được redeliver.

Không inbox: tạo hai shipments.

Có inbox trong cùng DB transaction: lần hai thấy/đụng unique inbox key và không tạo side effect mới. Message có thể complete an toàn.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate business rows xuất hiện dù broker config “duplicate detection” đã bật.

**Evidence** → cùng semantic event được redeliver/re-published với IDs khác, hoặc dedupe window của broker đã hết; consumer không có business-level idempotency.

**Hypothesis** → system dựa quá nhiều vào transport deduplication.

**Diagnosis** → correlate message IDs, producer retries, broker delivery count và database commits.

**Fix** → xác định stable business/idempotency key, inbox/unique constraint tại consumer; producer cũng phải giữ message identity đúng khi retry publication.

**Verification** → fault-inject crash sau DB commit trước ACK và confirm chỉ một business effect tồn tại.

## 7. Common mistakes

- Đánh dấu inbox processed trước business transaction rồi crash giữa chừng.
- Dùng in-memory `HashSet` làm dedupe trong multi-instance service.
- Không có unique constraint, tạo race giữa hai concurrent deliveries.
- Xóa inbox quá sớm hơn khả năng replay thực tế.
- Nghĩ broker “exactly once” loại bỏ nhu cầu idempotent business logic.
- Dùng random new ID mỗi lần producer retry cùng logical event.

## 8. Alternatives

- Natural idempotency bằng business unique constraint (`OrderId` chỉ có một Shipment).
- Broker duplicate detection: hữu ích nhưng thường có window và transport-specific semantics.
- Conditional update/state machine: xử lý event chỉ khi entity đang ở expected state.
- Inbox table: generic khi business model không tự cung cấp idempotency guard đủ mạnh.

## 9. Trade-offs

### Advantages

- Cho phép safe retry/redelivery.
- Dễ audit message đã xử lý.
- Kết hợp tốt với local DB transaction.

### Costs / Risks

- Thêm write/storage và cleanup policy.
- Idempotency scope/key phải thiết kế đúng.
- External side effects ngoài DB vẫn cần idempotency key tương ứng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu message có thể đến nhiều lần và handler không được giả định exactly-once.

### Middle

Implement inbox + unique constraint + transaction với business update.

### Senior

Thiết kế idempotency key, retention, concurrency race và side effects đi qua external APIs.

### Technical Lead / Architect

Quyết định nơi natural idempotency đủ, nơi cần Inbox, và đặt organization-wide message identity/replay conventions.

## 11. Key takeaway

- At-least-once delivery buộc consumer phải chịu duplicate.
- Inbox chỉ mạnh khi marker và business change nằm trong cùng consistency boundary.
- Transport dedupe là lớp hỗ trợ; business idempotency mới là correctness boundary cuối.

# 7. Azure App Configuration và Feature Flags: thay đổi runtime behavior có kiểm soát mà không biến configuration thành hidden control plane

## 1. What is it?

Azure App Configuration là managed service lưu application configuration và feature flags tách khỏi deployment artifact. Feature flag cho phép bật/tắt behavior mà không build/deploy code mới.

Mental model:

```text
Application binary
      +
App Configuration values / feature flags
      |
      v
runtime behavior
```

Điểm quan trọng: externalized configuration là một **control plane** có khả năng thay đổi production behavior, nên cần ownership, refresh semantics và audit như deployment.

## 2. Why does it exist?

Khi config chỉ nằm trong `appsettings.json`, thay một value có thể yêu cầu deploy. Environment variables giải quyết một phần nhưng quản lý nhiều applications/environments trở nên khó.

Feature flags còn hỗ trợ progressive rollout, kill switch hoặc tách deploy khỏi release.

Nhưng nếu hàng trăm flags sống vô thời hạn, codebase trở thành ma trận behavior khó test.

## 3. How does it work?

Application load keys từ Azure App Configuration, thường dùng Managed Identity. Runtime refresh không nhất thiết polling mọi key mỗi request; provider có refresh registration/interval và có thể dùng sentinel key để biểu diễn một batch config version.

```text
request
 -> config provider checks refresh eligibility
 -> if refresh needed, fetch changed state
 -> application reads updated option/flag
```

Feature flag evaluation có thể dựa percentage, time window hoặc targeting tùy library/requirements.

## 4. Practical implementation

Registration concept:

```csharp
builder.Configuration.AddAzureAppConfiguration(options =>
{
    options.Connect(new Uri(endpoint), new DefaultAzureCredential())
        .Select("MyApi:*")
        .ConfigureRefresh(refresh =>
        {
            refresh.Register("MyApi:Sentinel", refreshAll: true)
                   .SetRefreshInterval(TimeSpan.FromSeconds(30));
        });
});

builder.Services.AddAzureAppConfiguration();
```

Pipeline:

```csharp
app.UseAzureAppConfiguration();
```

Critical values như connection topology hoặc DI graph có thể vẫn nên restart-required thay vì hot reload.

## 5. Real production scenario

Team deploy code cho checkout algorithm mới nhưng flag mặc định off. Sau deploy health ổn, team bật cho internal users, rồi 5%, 25%, 100% traffic. Nếu error rate tăng, flag là kill switch nhanh hơn rollback image.

Sau migration hoàn tất, team xóa flag và dead code. Flag có owner + expiry date từ lúc tạo.

## 6. Failure scenario & troubleshooting

**Symptom** → một số instances dùng config mới, một số vẫn dùng cũ trong nhiều phút.

**Evidence** → refresh middleware không chạy ở execution path, refresh interval/sentinel không được update, hoặc process cache semantics khác expectation.

**Hypothesis** → team tưởng App Configuration là push-based instant consistency trong khi provider refresh là cached/pull lifecycle.

**Diagnosis** → log configuration version/sentinel (không log secret), compare instance state và provider refresh telemetry.

**Fix** → thiết kế refresh trigger/interval rõ, dùng sentinel cho coordinated update, restart nếu config không an toàn để hot reload.

**Verification** → controlled config change propagate trong documented SLA và instances converge.

## 7. Common mistakes

- Lưu secrets trực tiếp như normal config thay vì Key Vault reference/secret store phù hợp.
- Không định nghĩa refresh semantics nhưng kỳ vọng instant update.
- Feature flag tồn tại nhiều năm.
- Flag name gắn implementation detail khó hiểu.
- Bật flag 100% mà không telemetry/rollback condition.
- Cho quá nhiều người quyền thay production config mà không audit/governance.

## 8. Alternatives

- Environment variables: đơn giản, tốt khi restart/deploy để đổi config là chấp nhận được.
- Key Vault: dành cho secrets, không thay feature-management system.
- Database/custom admin config: linh hoạt nhưng tự chịu availability, audit, caching và security.
- Deployment slot/canary: rollout artifact/version thay vì logic branch trong cùng binary.

## 9. Trade-offs

### Advantages

- Tách deploy khỏi release.
- Centralized configuration và managed identity integration.
- Có thể làm progressive rollout/kill switch.

### Costs / Risks

- Thêm runtime dependency/control plane.
- Stale config và multi-instance convergence cần reasoning.
- Flag debt làm code/test matrix tăng nhanh.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu config external không đồng nghĩa mọi thay đổi áp dụng tức thời.

### Middle

Biết integrate provider, options/feature flags và test on/off behavior.

### Senior

Thiết kế refresh, failure fallback, telemetry, rollout và flag cleanup.

### Technical Lead / Architect

Định nghĩa governance: config nào hot reload, config nào restart-required, ai được thay production state, audit/approval ra sao và feature flag lifecycle bao lâu.

## 11. Key takeaway

- External config là production control plane, không chỉ nơi để key/value.
- Refresh semantics phải được document/test như caching semantics.
- Feature flag cần owner, rollout metric và ngày xóa.

# 8. Azure Blob Storage conditional writes với `ETag`: ngăn lost update trên object storage bằng optimistic concurrency

## 1. What is it?

Mỗi Blob có `ETag` đại diện cho version hiện tại của resource. Conditional request dùng HTTP preconditions như `If-Match` để chỉ update/delete khi blob vẫn đúng version client đã đọc.

Mental model:

```text
Client A reads ETag "v1"
Client B reads ETag "v1"

B updates -> ETag becomes "v2"
A writes with If-Match "v1"
          -> 412 Precondition Failed
```

Đây là optimistic concurrency trên object storage.

## 2. Why does it exist?

Nếu hai workers đọc cùng metadata blob, modify rồi upload lại mà không condition, writer sau có thể silently overwrite writer trước. Blob Storage không tự biết hai uploads thuộc cùng logical read-modify-write workflow.

Conditional writes cho phép phát hiện stale writer mà không cần distributed lock cho mọi update.

## 3. How does it work?

Azure Storage evaluates access condition atomically ở service boundary. `If-Match` yêu cầu current ETag match expected value; nếu không, operation fail với HTTP 412.

Các preconditions khác như `If-None-Match` có thể hỗ trợ create-if-not-exists semantics.

ETag nên được coi opaque token, không parse thành version number.

## 4. Practical implementation

```csharp
BlobClient blob = container.GetBlobClient("settings/catalog.json");

BlobDownloadResult current = await blob.DownloadContentAsync(ct);
ETag etag = current.Details.ETag;

var updated = UpdateCatalog(current.Content);

try
{
    await blob.UploadAsync(
        BinaryData.FromObjectAsJson(updated),
        new BlobUploadOptions
        {
            Conditions = new BlobRequestConditions
            {
                IfMatch = etag
            }
        },
        ct);
}
catch (RequestFailedException ex) when (ex.Status == 412)
{
    // Reload, merge/re-evaluate business operation, then retry if appropriate.
    throw new ConcurrencyException("Blob changed concurrently", ex);
}
```

Không blind retry cùng stale payload; phải re-read và decide merge/recompute.

## 5. Real production scenario

Hai background jobs update manifest JSON của media processing pipeline. Job A thêm asset X; Job B thêm asset Y. Không `ETag`, upload cuối làm mất entry của job kia.

Conditional write biến lost update thành explicit 412. Worker reload manifest, merge change của mình với version mới rồi thử lại theo bounded policy.

## 6. Failure scenario & troubleshooting

**Symptom** → 412 rate tăng mạnh sau scale-out.

**Evidence** → nhiều instances update cùng blob; each operation thực hiện read-modify-write trên shared document.

**Hypothesis** → hotspot/concurrency model không scale, chứ không phải Storage “unstable”.

**Diagnosis** → correlate blob path, writer count, update frequency và conflict rate.

**Fix** → partition state thành nhiều blobs, chuyển high-contention metadata sang database/queue-owned state, hoặc serialize writer nếu business thật sự yêu cầu single owner.

**Verification** → conflict rate giảm và no-lost-update tests pass dưới concurrency.

## 7. Common mistakes

- Upload overwrite không `If-Match` sau read-modify-write.
- Catch 412 rồi retry cùng body vô hạn.
- Parse ETag và tự tăng version.
- Dùng distributed lock dù conditional write đã đủ cho invariant.
- Lưu high-contention mutable coordination state trong một giant blob.
- Không phân biệt create-only với overwrite semantics.

## 8. Alternatives

- Blob lease: phù hợp khi cần exclusive access trong khoảng thời gian, nhưng có lease lifecycle/failure complexity.
- SQL/Cosmos optimistic concurrency: phù hợp richer structured state/query requirements.
- Single-writer queue/actor model: tốt khi updates cần ordered serialization.
- Append Blob/event log: phù hợp append-only workflows thay vì rewrite whole document.

## 9. Trade-offs

### Advantages

- Không cần central lock cho common optimistic concurrency case.
- Service-side atomic condition.
- Phát hiện lost update rõ ràng.

### Costs / Risks

- Conflict handling thuộc application.
- Hot blob gây nhiều retries.
- Large read-modify-write object có bandwidth/latency cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ETag là opaque version token và 412 nghĩa resource đã thay đổi.

### Middle

Biết dùng `BlobRequestConditions.IfMatch` và implement bounded reload/retry.

### Senior

Phân biệt conflict bình thường với hotspot architecture; thiết kế merge/idempotency đúng.

### Technical Lead / Architect

Quyết định Blob có phù hợp làm mutable shared state hay workload đã cần database/single-writer architecture.

## 11. Key takeaway

- `ETag` + `If-Match` biến silent overwrite thành explicit concurrency conflict.
- Retry conflict phải re-read/re-evaluate, không blind replay stale data.
- Conflict rate cao thường là signal về state ownership/partitioning.

# 9. Testcontainers cho integration testing .NET: test với dependency thật nhưng vẫn giữ môi trường reproducible và cô lập

## 1. What is it?

Testcontainers là cách khởi động disposable Docker containers từ test code để integration tests chạy với real dependency như PostgreSQL, SQL Server, Redis hoặc message broker thay vì mock behavior của chúng.

Mental model:

```text
Test suite
   |
   +--> start isolated DB container
   +--> run migrations/seed
   +--> start System Under Test
   +--> execute test
   +--> dispose container
```

Mục tiêu là tăng fidelity mà vẫn giữ environment tạo lại được tự động.

## 2. Why does it exist?

Mock repository không bắt được:

- SQL translation lỗi;
- collation/case semantics;
- transaction/isolation behavior;
- migrations sai;
- unique/FK constraints;
- Redis serialization/TTL behavior;
- broker redelivery semantics.

Shared integration database ngược lại thường tạo flaky tests vì state giữa developers/CI runs va chạm nhau.

Disposable containers cân bằng real dependency và isolation.

## 3. How does it work?

Test fixture tạo container từ pinned image, chờ readiness, lấy dynamic port/connection string rồi configure application dưới test.

Lifecycle có thể là:

- container per test: isolation cao, chậm;
- container per test class/collection: nhanh hơn, cần reset data;
- container per suite: nhanh nhất nhưng state isolation phải rất kỷ luật.

Test phải reset **data**, không nhất thiết restart container mỗi case.

## 4. Practical implementation

Ví dụ PostgreSQL:

```csharp
public sealed class PostgresFixture : IAsyncLifetime
{
    private readonly PostgreSqlContainer _db =
        new PostgreSqlBuilder()
            .WithImage("postgres:16")
            .WithDatabase("app_test")
            .WithUsername("test")
            .WithPassword("test")
            .Build();

    public string ConnectionString => _db.GetConnectionString();

    public Task InitializeAsync() => _db.StartAsync();
    public Task DisposeAsync() => _db.DisposeAsync().AsTask();
}
```

Application factory override connection string, chạy migrations và test HTTP endpoint end-to-end qua real EF provider.

CI runner cần Docker/container runtime phù hợp.

## 5. Real production scenario

Team dùng EF Core InMemory provider cho tests. Query dùng method mà SQL Server provider không translate được, nhưng tests xanh vì LINQ chạy in-memory. Production endpoint mới ném exception khi traffic thật đến.

Chuyển critical repository/API tests sang SQL Server/PostgreSQL Testcontainer bắt translation và migration lỗi trước merge.

Unit tests vẫn được giữ cho pure domain logic; không biến toàn suite thành integration tests.

## 6. Failure scenario & troubleshooting

**Symptom** → CI integration suite chậm/flaky hơn local.

**Evidence** → pull image mỗi run, startup readiness race, parallel tests cùng mutate shared rows, cleanup không deterministic.

**Hypothesis** → container lifecycle/data-isolation strategy chưa được thiết kế.

**Diagnosis** → đo startup vs test time, inspect resource limits, identify cross-test state dependencies.

**Fix** → pin/cache images, reuse container theo collection khi phù hợp, reset DB bằng deterministic strategy, randomize unique test data, giới hạn parallelism chỉ nơi resource contention thật.

**Verification** → chạy suite lặp nhiều lần/parallel trong CI và theo dõi flaky rate + duration.

## 7. Common mistakes

- Test mọi method bằng container, làm feedback loop quá chậm.
- Dùng `latest` image khiến CI không reproducible.
- Không wait readiness đúng cách, chỉ `Task.Delay(5000)`.
- Dùng SQLite thay SQL Server/PostgreSQL rồi tưởng semantics giống nhau hoàn toàn.
- Shared static test data gây collisions.
- Không cleanup containers/resources khi test crash.

## 8. Alternatives

- Unit tests/mocks: nhanh cho pure business logic và edge cases.
- LocalDB/embedded DB: tiện nhưng có thể khác production engine.
- Shared staging DB: realistic nhưng isolation/reproducibility kém.
- Full ephemeral environment: fidelity cao cho system tests nhưng cost/thời gian lớn hơn.

## 9. Trade-offs

### Advantages

- High fidelity với real dependency.
- Reproducible trên local/CI.
- Bắt migration/provider/protocol issues mocks bỏ qua.

### Costs / Risks

- Test startup/resource cost cao hơn unit tests.
- Cần Docker-compatible CI environment.
- Data/lifecycle isolation phải được thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu integration test xác minh interaction với real dependency chứ không thay unit test.

### Middle

Biết dựng fixture, migrations, seed/reset và application factory.

### Senior

Thiết kế test pyramid theo risk, tối ưu lifecycle/parallelism và chống flaky state.

### Technical Lead / Architect

Quyết định boundary nào cần real dependency fidelity trong CI, budget thời gian suite và standard reusable test infrastructure cho nhiều teams.

## 11. Key takeaway

- Testcontainers giúp test đúng database/broker semantics thay vì mock tưởng tượng.
- Không cần container cho mọi test; dùng ở integration boundaries có risk thật.
- Reproducibility phụ thuộc image pinning, readiness và data isolation.

# 10. Production diagnostics escalation với `dotnet-counters`, `dotnet-trace`, `dotnet-dump`: chọn đúng mức bằng chứng trước khi đoán root cause

## 1. What is it?

.NET diagnostics có nhiều mức quan sát với cost và độ chi tiết khác nhau. Một workflow hữu ích là escalation:

```text
Metrics/counters
   -> xác định loại saturation/anomaly
Trace
   -> xem timeline, CPU samples, runtime events
Dump
   -> inspect process memory/stacks/state tại một thời điểm
```

Không phải incident nào cũng bắt đầu bằng memory dump. Công cụ phải match câu hỏi đang cần trả lời.

## 2. Why does it exist?

Production symptom thường mơ hồ:

- API chậm;
- CPU cao;
- memory tăng;
- ThreadPool queue tăng;
- exceptions tăng.

Nếu developer nhảy ngay tới một giả thuyết như “GC leak” hoặc “SQL chậm”, thời gian xử lý incident bị tiêu vào trial-and-error.

Diagnostics escalation xây evidence từng bước, từ low-overhead signal tới deep inspection.

## 3. How does it work?

`dotnet-counters` xem runtime/process counters gần realtime, ví dụ CPU, GC heap size, allocation rate, exception count, ThreadPool queue/thread count.

`dotnet-trace` collect EventPipe trace để phân tích CPU stacks, GC/runtime events và providers được chọn.

`dotnet-dump` capture memory dump để inspect managed stacks/heap bằng SOS commands.

Mỗi tool trả lời câu hỏi khác nhau:

```text
CPU thật sự cao?              -> counters
CPU đang chạy code nào?       -> trace
Threads đang block ở đâu?     -> trace/dump
Object nào giữ memory?        -> dump/gcdump
```

## 4. Practical implementation

Bắt đầu nhẹ:

```bash
dotnet-counters monitor \
  --process-id <PID> \
  System.Runtime
```

Nếu CPU cao cần sampling:

```bash
dotnet-trace collect \
  --process-id <PID> \
  --profile cpu-sampling
```

Nếu cần process snapshot:

```bash
dotnet-dump collect \
  --process-id <PID> \
  --type Heap
```

Sau đó:

```bash
dotnet-dump analyze <dump-file>
```

Production phải có runbook về quyền truy cập, file size, PII/secrets và nơi lưu diagnostic artifacts an toàn.

## 5. Real production scenario

API p99 tăng gấp 5 nhưng CPU chỉ 35%. Team ban đầu định scale CPU.

`dotnet-counters` cho thấy ThreadPool queue tăng và thread count climb. `dotnet-trace` chỉ ra nhiều synchronous waits quanh legacy HTTP client wrapper. Root cause là blocking I/O gây ThreadPool starvation, không phải thiếu CPU.

Fix async boundary và concurrency control giải quyết latency; scale CPU sẽ chỉ che symptom tạm thời.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng 200 MB/hour; team capture một dump rồi kết luận “cache leak”.

**Evidence** → chỉ có một snapshot, không có baseline/growth comparison; large objects có thể là legitimate working set.

**Hypothesis** → conclusion thiếu temporal evidence.

**Diagnosis** → trước hết xem heap size/allocation/GC trend; capture snapshots ở nhiều thời điểm nếu cần; compare object counts/retention paths.

**Fix** → xác định type tăng theo thời gian và GC roots giữ chúng; sửa ownership/cache eviction/subscription lifecycle tương ứng.

**Verification** → soak test và production counters cho thấy heap plateau thay vì tăng liên tục.

## 7. Common mistakes

- Bắt dump ngay trong peak production mà không hiểu disk/I/O/privacy impact.
- Dùng CPU profiler để tìm network latency.
- Nhìn một counter riêng lẻ và kết luận root cause.
- Không correlate application metrics với dependency/SQL telemetry.
- Capture artifact nhưng không ghi thời điểm, deployment version, workload.
- Upload dump chứa sensitive memory vào nơi không được kiểm soát.

## 8. Alternatives

- Application Insights/OpenTelemetry/APM: first-line continuous observability.
- `dotnet-gcdump`: focused managed heap insight với artifact nhỏ hơn full dump trong một số scenarios.
- OS/container metrics: cần để phân biệt process problem với host/cgroup pressure.
- Native profilers: khi issue nằm ở native/runtime boundary sâu hơn.

## 9. Trade-offs

### Advantages

- Evidence-driven incident diagnosis.
- Escalation từ low overhead tới deep state.
- Có thể phân biệt CPU, GC, ThreadPool, blocking và memory ownership problems.

### Costs / Risks

- Trace/dump có runtime/storage overhead tùy cấu hình.
- Dump có thể chứa credentials/PII/plaintext payloads.
- Deep diagnostics cần kỹ năng phân tích, không chỉ command execution.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết khác nhau giữa CPU, memory, allocation, ThreadPool và dependency latency ở mức mental model.

### Middle

Biết dùng counters/trace cơ bản, gắn timestamp/deployment context và reproduce dưới load test.

### Senior

Chọn đúng diagnostic artifact cho hypothesis, đọc stacks/GC evidence và tránh correlation-causation trap.

### Technical Lead / Architect

Xây production diagnostic runbook: access control, safe collection, retention, incident evidence checklist và observability đủ tốt để không cần dump cho mọi outage.

## 11. Key takeaway

- Bắt đầu bằng signal rẻ nhất có thể bác bỏ/xác nhận hypothesis.
- Counters → trace → dump là escalation, không phải checklist phải chạy đủ mọi lần.
- Diagnostic artifacts là sensitive production data và cần governance như dữ liệu thật.
