## 1. C# / .NET — `ValueTask<T>` là optimization contract, không phải phiên bản “nhanh hơn” của `Task<T>`

### Concept / Problem
`ValueTask<T>` có thể tránh allocation của `Task<T>` khi operation thường hoàn tất synchronously, nhưng đổi lại consumer phải tuân theo contract chặt hơn. Một `ValueTask<T>` không nên mặc định được await nhiều lần, lưu giữ lâu, hoặc dùng giống một `Task<T>` thông thường.

```csharp
public ValueTask<User?> GetCachedUserAsync(int id, CancellationToken ct)
{
    if (_cache.TryGetValue(id, out User? user))
        return ValueTask.FromResult<User?>(user);

    return new ValueTask<User?>(LoadUserAsync(id, ct));
}
```

### Why it matters
Trong hot path có tỷ lệ synchronous completion cao, allocation reduction có thể đáng kể. Nhưng trong application code bình thường, complexity tăng thêm thường không đáng so với lợi ích chưa đo được.

### Senior-level insight
API return type là một performance contract. Chỉ chọn `ValueTask<T>` sau profiling khi allocation của `Task<T>` thực sự nằm trên critical path. Nếu caller cần await nhiều lần hoặc compose linh hoạt, chuyển bằng `.AsTask()` sẽ lại tạo/đòi hỏi `Task`, làm mất một phần lợi ích.

### Trade-offs
`Task<T>` đơn giản, composable và an toàn hơn. `ValueTask<T>` có thể giảm allocation nhưng làm API khó dùng đúng hơn và struct lớn hơn một reference đơn giản.

### Common mistakes
- Đổi hàng loạt `Task<T>` thành `ValueTask<T>` mà không benchmark.
- Await cùng một `ValueTask<T>` nhiều lần.
- Gọi `.Result` hoặc mix sync-over-async.
- Dùng nó cho operation gần như luôn asynchronous.

### Practical checklist
1. Profile allocation trước.
2. Xác nhận synchronous completion rate cao.
3. Giữ consumer usage đơn giản: await trực tiếp một lần.
4. Benchmark end-to-end, không chỉ microbenchmark method.

## 2. C# / .NET — `ConfigureAwait(false)` trong ASP.NET Core khác với ASP.NET cổ điển

### Concept / Problem
Trong ASP.NET Core mặc định không có request `SynchronizationContext` kiểu ASP.NET classic. Vì vậy việc thêm `.ConfigureAwait(false)` vào mọi `await` trong application code thường không tạo ra thay đổi hành vi đáng kể như nhiều guideline cũ mô tả.

```csharp
var result = await repository.GetAsync(id, ct);
```

Trong reusable library, `ConfigureAwait(false)` vẫn có thể là lựa chọn có chủ đích vì library không nên giả định context của caller:

```csharp
var data = await stream.ReadAsync(buffer, ct).ConfigureAwait(false);
```

### Why it matters
Copy guideline từ .NET Framework sang modern .NET dễ tạo ceremony mà team không hiểu lý do. Quan trọng hơn là hiểu context model của runtime đang chạy.

### Senior-level insight
Không nên áp dụng concurrency folklore xuyên thế hệ framework. Hãy phân biệt application code với general-purpose library code. Trong ASP.NET Core, vấn đề phổ biến hơn là blocking `.Result`/`.Wait()`, thread-pool starvation và sync I/O, không phải deadlock do request SynchronizationContext như ASP.NET cũ.

### Trade-offs
Dùng nhất quán trong library có thể làm intent rõ; dùng tràn lan trong application code làm code noisy mà lợi ích nhỏ. Một convention chỉ có giá trị khi team hiểu failure mode nó ngăn chặn.

### Common mistakes
- Tin rằng thiếu `ConfigureAwait(false)` chắc chắn gây deadlock trong ASP.NET Core.
- Dùng `.Result` rồi cố “sửa” bằng `ConfigureAwait(false)`.
- Áp analyzer rule cứng cho mọi project type.

### Practical checklist
- Xác định project là app hay reusable library.
- Tránh sync-over-async.
- Đo thread-pool starvation khi có latency bất thường.
- Document convention theo runtime hiện tại.

## 3. ASP.NET Core / Web API — `HttpClientFactory` giải quyết handler lifetime, nhưng resilience policy sai vẫn có thể gây outage

### Concept / Problem
Tạo `new HttpClient()` liên tục có thể gây connection churn; giữ một handler sai cách có thể làm DNS refresh không phù hợp. `IHttpClientFactory` quản lý handler lifetime và cấu hình client tập trung.

```csharp
services.AddHttpClient<InventoryClient>(client =>
{
    client.BaseAddress = new Uri(configuration["Inventory:BaseUrl"]!);
    client.Timeout = TimeSpan.FromSeconds(2);
});
```

### Why it matters
Outbound HTTP là dependency boundary quan trọng. Một service khỏe có thể tự làm mình quá tải nếu timeout/retry/concurrency không được thiết kế cùng nhau.

### Senior-level insight
Retry chỉ phù hợp với transient failure và operation có thể retry an toàn. Ba retry ở mỗi service qua chuỗi A → B → C có thể khuếch đại một request thành nhiều lần gọi downstream. Resilience cần budget tổng thể, jitter, circuit breaking/rate limiting khi phù hợp và observability.

### Trade-offs
Retry cải thiện success rate cho transient fault nhưng tăng tail latency và load đúng lúc dependency đang yếu. Fail-fast bảo vệ capacity nhưng có thể làm lỗi nhìn thấy nhiều hơn trong spike ngắn.

### Common mistakes
- Retry mọi `5xx` một cách mù quáng.
- Retry POST có side effect mà không có idempotency.
- Timeout từng attempt dài hơn end-to-end SLO.
- Không log attempt count và final outcome.

### Practical checklist
- Phân loại transient/permanent failures.
- Đặt timeout theo latency budget.
- Retry có backoff + jitter.
- Bảo đảm idempotency trước retry side-effecting operation.
- Theo dõi downstream latency/error/saturation.

## 4. ASP.NET Core / Web API — Validation nên bảo vệ contract; business invariant phải sống gần domain logic

### Concept / Problem
Có hai loại rule thường bị trộn vào controller validation:

```text
Contract validation:
- Quantity > 0
- Email đúng format
- Required field có giá trị

Business invariant:
- Không thể ship order đã cancelled
- Credit limit không được vượt quá policy
- Một booking không thể overlap theo rule nghiệp vụ
```

### Why it matters
Nếu business rule chỉ nằm trong HTTP validator, cùng use case được gọi từ queue consumer, background job hoặc gRPC có thể bypass rule.

### Senior-level insight
Boundary validation trả feedback sớm và đẹp cho client; domain/application invariant bảo vệ correctness bất kể entry point. Có thể có duplication nhỏ có chủ đích: boundary check cho UX, authoritative rule ở domain/application layer.

### Trade-offs
Đẩy mọi validation vào domain làm error mapping/UX phức tạp. Đẩy mọi thứ ra controller làm domain dễ bị invalid state. Boundary đúng phụ thuộc loại rule và ownership.

### Common mistakes
- Controller chứa toàn bộ business logic.
- Validator query database hàng loạt mà không kiểm soát race condition.
- Tin rằng pre-check `ExistsAsync` thay thế được unique constraint.
- Return cùng một 400 cho validation, conflict và authorization.

### Practical checklist
- Tách shape/format validation khỏi invariant.
- Enforce invariant tại nơi mọi entry point đều đi qua.
- Dùng database constraint cho invariant cần atomicity.
- Map lỗi thành status/code có semantics rõ.

## 5. EF Core / SQL — Optimistic concurrency bảo vệ lost update, nhưng phải thiết kế conflict UX

### Concept / Problem
Hai request đọc cùng một row, cùng sửa và lần save sau ghi đè lần trước là lost update. Với SQL Server, EF Core có thể dùng `rowversion`:

```csharp
public class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }

    [Timestamp]
    public byte[] Version { get; set; } = [];
}
```

EF Core thêm concurrency token vào `WHERE` của `UPDATE`; nếu không row nào match, nó ném `DbUpdateConcurrencyException`.

### Why it matters
Concurrency conflict là normal distributed behavior, không phải exceptional bug hiếm gặp. Admin UI, inventory, profile editing và workflow state đều có thể gặp.

### Senior-level insight
Phát hiện conflict mới là nửa bài toán. Hệ thống phải quyết định semantics: client wins, store wins, merge, retry hay trả `409 Conflict` để người dùng refresh. Auto-retry update mù quáng có thể tái tạo chính lost update mà concurrency token vừa phát hiện.

### Trade-offs
Optimistic concurrency hiệu quả khi conflict hiếm. Pessimistic locking có thể phù hợp cho critical short transaction nhưng làm giảm concurrency và tăng deadlock/blocking risk.

### Common mistakes
- Catch `DbUpdateConcurrencyException` rồi retry cùng state vô hạn.
- Không đưa version/ETag tới client khi client cần round-trip version.
- Dùng timestamp thời gian làm token nhưng precision/clock semantics không đủ.

### Practical checklist
- Xác định entity nào cần lost-update protection.
- Chọn concurrency token đáng tin cậy.
- Thiết kế conflict response/UX.
- Test hai writer concurrent.
- Quan sát conflict rate production.

## 6. EF Core / SQL — Unique constraint là correctness mechanism; pre-check chỉ là UX optimization

### Concept / Problem
Code sau có race condition:

```csharp
if (!await db.Users.AnyAsync(x => x.Email == email, ct))
{
    db.Users.Add(new User { Email = email });
    await db.SaveChangesAsync(ct);
}
```

Hai request có thể cùng thấy `false` rồi cùng insert. Correctness phải được bảo vệ bằng unique index/constraint:

```csharp
modelBuilder.Entity<User>()
    .HasIndex(x => x.NormalizedEmail)
    .IsUnique();
```

### Why it matters
Application check và write là hai operations riêng. Isolation mặc định không biến chúng thành atomic “check-and-insert”. Database constraint là arbiter cuối cùng cho uniqueness.

### Senior-level insight
Pre-check vẫn hữu ích để trả lỗi thân thiện trong common case, nhưng code phải xử lý constraint violation vì race vẫn tồn tại. Đây là pattern tổng quát: validation cải thiện UX; constraint bảo vệ invariant.

### Trade-offs
Chỉ dựa constraint có thể làm mapping database exception phức tạp. Pre-check + constraint thêm một query nhưng UX tốt hơn. Với high-throughput path, có thể bỏ pre-check và map violation trực tiếp.

### Common mistakes
- Không normalize email/key trước uniqueness.
- Parse error message text phụ thuộc database/localization.
- Unique index sai scope, ví dụ quên `TenantId`.
- Unit test mock repository nhưng không test constraint thật.

### Practical checklist
- Định nghĩa exact uniqueness scope.
- Enforce bằng DB constraint.
- Map known violation thành domain/API conflict.
- Integration test concurrent inserts.

## 7. MongoDB — Index compound phải theo query shape; thứ tự field không phải chi tiết trang trí

### Concept / Problem
Giả sử query phổ biến:

```javascript
db.orders.find({ tenantId: 42, status: "Open" })
         .sort({ createdAt: -1 })
```

Một compound index hợp lý có thể là:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

Index `{ createdAt: -1, tenantId: 1, status: 1 }` không tương đương về khả năng phục vụ query này.

### Why it matters
MongoDB index design cần xuất phát từ workload. Compound index tốt có thể vừa lọc vừa hỗ trợ sort, giảm documents examined và tránh blocking sort.

### Senior-level insight
Một heuristic hữu ích là equality fields trước, sau đó sort/range tùy query shape, nhưng đừng biến heuristic thành luật tuyệt đối. Hãy kiểm chứng bằng `explain()` với cardinality gần production. Selectivity, prefix reuse và nhiều query competing cho index budget đều ảnh hưởng thiết kế.

### Trade-offs
Mỗi index tăng storage, RAM pressure và write amplification. “Index mọi query” có thể làm write-heavy collection chậm đáng kể.

### Common mistakes
- Chỉ nhìn `executionTimeMillis` trên dataset nhỏ.
- Tạo nhiều index gần giống nhau.
- Không xem `totalKeysExamined`/`totalDocsExamined`.
- Quên rằng index prefix quyết định query nào reuse được.

### Practical checklist
- Inventory top query shapes.
- Dùng `explain("executionStats")`.
- So sánh keys/docs examined với rows returned.
- Loại index redundant/unused có dữ liệu quan sát đủ lâu.

## 8. Software Design — Cache invalidation nên bắt đầu từ consistency requirement, không phải từ Redis

### Concept / Problem
Trước khi chọn cache-aside hay distributed cache, cần hỏi dữ liệu được phép stale bao lâu và hậu quả của stale read là gì.

Cache-aside cơ bản:

```text
Read:
1. GET cache
2. miss -> read DB
3. SET cache with TTL

Write:
1. update DB
2. invalidate/update cache
```

Khoảng thời gian giữa các bước tạo consistency windows.

### Why it matters
Cache là một bản sao dữ liệu. Ngay khi có bản sao, hệ thống có consistency problem. Product catalog stale 30 giây có thể chấp nhận; permission/revocation hoặc financial balance có thể không.

### Senior-level insight
TTL không phải consistency guarantee; nó chỉ giới hạn một số dạng staleness. Race `read DB → concurrent write → set stale value into cache` vẫn có thể tồn tại. Versioned keys, event-driven invalidation, short TTL, single-flight và bypass cache cho critical reads là các công cụ khác nhau cho các invariant khác nhau.

### Trade-offs
Cache tăng throughput và giảm latency nhưng tăng state, failure modes và observability burden. Nếu database đã đáp ứng SLO với headroom tốt, không cache thường là thiết kế đơn giản hơn.

### Common mistakes
- Cache trước khi đo bottleneck.
- Dùng cùng TTL cho mọi loại dữ liệu.
- Cache authorization data lâu mà không có revocation strategy.
- Cache stampede khi hot key hết hạn.

### Practical checklist
- Định nghĩa acceptable staleness.
- Định nghĩa source of truth.
- Chọn invalidation strategy theo invariant.
- Bảo vệ hot-key stampede.
- Đo hit rate và latency thực, không chỉ cache size.

## 9. Testing / QA / Debugging — Property-based testing tìm class of bugs mà example-based tests dễ bỏ sót

### Concept / Problem
Example-based test kiểm tra vài input cụ thể. Property-based test mô tả invariant phải đúng cho nhiều input được sinh tự động.

Ví dụ với normalization function, property có thể là idempotence:

```text
Normalize(Normalize(x)) == Normalize(x)
```

Với serializer round-trip:

```text
Deserialize(Serialize(x)) == x
```

### Why it matters
Boundary values, empty collections, Unicode, duplicate items và tổ hợp input lạ thường không được developer nghĩ ra hết bằng tay. Generator mở rộng search space; shrinking giúp thu nhỏ failing input thành case dễ debug.

### Senior-level insight
Property-based testing không thay thế example tests. Examples diễn tả business scenario rõ; properties kiểm chứng invariant rộng. Giá trị lớn nhất xuất hiện ở pure/domain logic, parser, transformation, ordering, money/calculation và state-machine transitions.

### Trade-offs
Property tốt khó thiết kế hơn test example. Property quá yếu chỉ tạo cảm giác coverage; property quá tổng quát có thể khó debug nếu generator/model không được kiểm soát.

### Common mistakes
- Chỉ generate random data mà không có invariant rõ.
- Reimplement production algorithm trong assertion.
- Không lưu seed/counterexample khi fail.
- Dùng cho integration flow đắt tiền mà không giới hạn cases.

### Practical checklist
- Liệt kê algebraic/domain invariants.
- Giữ oracle độc lập với implementation.
- Include boundary-biased generators.
- Persist minimal failing case vào regression suite.

## 10. Git / Tooling / Engineering Workflow — `git bisect` biến lịch sử sạch thành công cụ tìm regression theo logarithmic search

### Concept / Problem
Khi biết commit hiện tại lỗi và một commit cũ tốt, `git bisect` chọn commit giữa khoảng để test:

```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-sha>
```

Sau mỗi test:

```bash
git bisect good
# hoặc
git bisect bad
```

Có thể tự động hóa nếu có test command đáng tin cậy:

```bash
git bisect run dotnet test tests/MyProject.Tests/MyProject.Tests.csproj
```

### Why it matters
Với hàng trăm commit, binary search giảm mạnh số điểm phải kiểm tra. Nhưng hiệu quả phụ thuộc vào lịch sử có thể build/test và commit boundary đủ coherent.

### Senior-level insight
Test automation và Git hygiene bổ trợ trực tiếp cho incident debugging. Một regression test có exit code ổn định biến `bisect` thành automated fault localization. Ngược lại, flaky tests hoặc commit không build được phá vỡ search signal.

### Trade-offs
Giữ commit buildable cần discipline. Một số refactor lớn khó tách thành mọi commit đều production-ready; khi đó có thể dùng `git bisect skip`, nhưng càng nhiều skip thì khả năng định vị càng kém.

### Common mistakes
- Bisect bằng test flaky.
- Chọn “good” commit chưa thực sự được xác nhận.
- Quên reset sau khi hoàn tất.
- Lịch sử chứa mega-commit làm kết quả chỉ khoanh vùng được một diff khổng lồ.

### Practical checklist
- Xác nhận known-good và known-bad.
- Ưu tiên deterministic regression test.
- Dùng `git bisect run` khi có thể.
- Sau khi tìm commit, viết regression test trước/sát với fix.
- Kết thúc bằng `git bisect reset`.
