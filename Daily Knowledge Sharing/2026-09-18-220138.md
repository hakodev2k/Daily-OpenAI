# 1. C# `async`/`await` state machine: continuation, allocation và sync-over-async failure

## 1. What is it?

Mental model quan trọng: `async` không tạo ra một thread riêng. Compiler biến method thành một state machine có thể tạm dừng tại `await`, trả control cho caller, rồi tiếp tục khi awaitable hoàn tất. `Task` đại diện cho completion của operation, không đại diện cho một thread.

## 2. Why does it exist?

I/O như HTTP, database và file thường dành phần lớn thời gian để chờ bên ngoài process. Nếu một server thread bị block trong toàn bộ thời gian đó, throughput giảm và ThreadPool có thể bị starvation dưới tải. `await` cho phép thread quay lại pool trong lúc I/O chưa hoàn tất.

## 3. How does it work?

```text
Request thread
   │ call async method
   ▼
Start operation ──► await incomplete
   │                    │
   │ return Task        └── I/O completes
   ▼                           │
Thread returns to pool         ▼
                        continuation scheduled
                               │
                               ▼
                        state machine resumes
```

Nếu awaitable đã complete synchronously, state machine có thể tiếp tục ngay. Vì vậy async path không phải lúc nào cũng có context switch.

## 4. Practical implementation

```csharp
public async Task<OrderDto?> GetOrderAsync(Guid id, CancellationToken ct)
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    return order is null
        ? null
        : new OrderDto(order.Id, order.Total);
}
```

Tránh:

```csharp
var order = GetOrderAsync(id, ct).Result;
```

Trong ASP.NET Core, `.Result`/`.Wait()` vẫn có thể gây ThreadPool starvation dù không còn classic ASP.NET `SynchronizationContext` deadlock như trước.

## 5. Real production scenario

Một API gọi ba remote services. Code chuyển từ `await` sang `.Result` để “đơn giản hóa”. Load test cho thấy CPU chưa cao nhưng p99 tăng mạnh, request queue dài và ThreadPool phải inject thêm threads. Bottleneck là blocked workers, không phải raw CPU.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng mạnh khi concurrency tăng nhưng dependency latency tương đối ổn định.  
**Evidence** → nhiều blocked threads, ThreadPool queue tăng, traces có gaps ở sync waits.  
**Hypothesis** → sync-over-async.  
**Diagnosis** → tìm `.Result`, `.Wait()`, blocking locks quanh async calls; dùng `dotnet-counters`/trace.  
**Fix** → async all the way và propagate `CancellationToken`.  
**Verification** → load test lại, theo dõi ThreadPool queue và p95/p99.

## 7. Common mistakes

Cho rằng `async` luôn chạy parallel; dùng `Task.Run` cho database I/O; bỏ `CancellationToken`; tạo async method nhưng block ở caller; tối ưu allocation của state machine trước khi đo.

## 8. Alternatives

Synchronous code vẫn hợp lý cho CPU work ngắn hoặc API hoàn toàn synchronous. `Task.Run` phù hợp để offload CPU work trong một số client scenarios, nhưng không biến synchronous server I/O thành scalable I/O.

## 9. Trade-offs

### Advantages

Giải phóng worker threads khi chờ I/O, cải thiện scalability và composition.

### Costs / Risks

Control flow phức tạp hơn khi debugging; có state-machine/task overhead; cancellation và exception propagation phải được hiểu đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task` không phải thread và `await` là suspension point.

### Middle

Viết async all the way, cancellation và exception handling đúng.

### Senior

Chẩn đoán starvation, allocation và concurrency behavior bằng telemetry.

### Technical Lead / Architect

Quyết định async boundaries theo workload, không ép async như style rule ở mọi layer.

## 11. Key takeaway

- `await` chủ yếu giải phóng thread trong I/O wait; nó không tự tạo parallelism.
- Sync-over-async có thể phá throughput mà CPU vẫn chưa bão hòa.
- Đo ThreadPool và tail latency trước khi kết luận bottleneck.

# 2. ASP.NET Core response streaming: buffering, backpressure và client disconnect

## 1. What is it?

Response streaming gửi dữ liệu dần tới client thay vì materialize toàn bộ payload trong memory rồi mới trả. Mental model: đây là một pipeline có producer và network consumer; tốc độ consumer ảnh hưởng producer thông qua backpressure.

## 2. Why does it exist?

Export hàng trăm MB hoặc AI/token stream không nên giữ toàn bộ response trong RAM. Buffering lớn làm tăng memory pressure và time-to-first-byte.

## 3. How does it work?

```text
Database/File → Application producer → HTTP response buffer → Network → Client
                                      ▲
                                      └── slow client creates backpressure
```

Streaming không loại bỏ buffering hoàn toàn: Kestrel, proxy, compression middleware và CDN có thể có buffers riêng.

## 4. Practical implementation

```csharp
app.MapGet("/export", async (HttpResponse response, AppDbContext db, CancellationToken ct) =>
{
    response.ContentType = "application/x-ndjson";

    await foreach (var row in db.Orders
        .AsNoTracking()
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        await response.WriteAsJsonAsync(row, cancellationToken: ct);
        await response.WriteAsync("\n", ct);
        await response.Body.FlushAsync(ct);
    }
});
```

Production code cần kiểm tra format, query lifetime và flush frequency; flush từng record có thể làm network overhead tăng.

## 5. Real production scenario

Admin export 2 triệu rows. Implementation cũ gọi `ToListAsync()` rồi serialize, làm pod vượt memory limit. Streaming giảm peak memory nhưng giữ DB reader/connection lâu hơn, nên vấn đề chuyển từ memory sang connection lifetime.

## 6. Failure scenario & troubleshooting

**Symptom** → memory ổn nhưng DB connection pool cạn khi nhiều exports đồng thời.  
**Evidence** → mỗi streaming request giữ connection nhiều phút.  
**Hypothesis** → long-lived streaming query chiếm scarce DB connections.  
**Diagnosis** → correlate active exports, connection duration và pool wait.  
**Fix** → concurrency limit, chunking/background export hoặc pre-generated Blob.  
**Verification** → concurrent export không làm interactive APIs mất connection.

## 7. Common mistakes

Cho rằng streaming luôn tốt hơn; flush quá thường xuyên; không handle client disconnect; stream qua proxy đang buffer toàn response; giữ transaction mở suốt download.

## 8. Alternatives

Background job tạo file rồi trả SAS URL thường tốt hơn cho export lớn. Pagination phù hợp interactive data. Buffering phù hợp payload nhỏ và đơn giản.

## 9. Trade-offs

### Advantages

Peak memory thấp hơn và time-to-first-byte tốt hơn.

### Costs / Risks

Giữ resource lâu, xử lý partial response khó, proxy behavior phức tạp và retry không đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu streaming khác materialization.

### Middle

Implement cancellation và bounded buffering.

### Senior

Reason về slow clients, DB connections, proxy buffering và partial failures.

### Technical Lead / Architect

Chọn synchronous streaming hay asynchronous file-generation dựa trên size, duration và resource budget.

## 11. Key takeaway

- Streaming giảm memory nhưng có thể kéo dài lifetime của DB/network resources.
- Backpressure và disconnect là một phần của contract.
- Export rất lớn thường nên chuyển sang background workflow.

# 3. EF Core savepoints: partial transaction recovery và retry boundary

## 1. What is it?

Savepoint là checkpoint bên trong một database transaction. EF Core có thể tạo savepoint trước `SaveChanges` khi transaction đã tồn tại, cho phép rollback phần thay đổi sau checkpoint mà không nhất thiết hủy toàn transaction.

## 2. Why does it exist?

Một transaction có thể chứa nhiều logical steps. Nếu step sau gặp optimistic concurrency conflict, rollback toàn bộ work trước đó đôi khi không cần thiết. Savepoint cho phép recovery có kiểm soát.

## 3. How does it work?

```text
BEGIN TRANSACTION
  Step A
  SAVEPOINT S1
  Step B / SaveChanges
       │ fail
       ▼
  ROLLBACK TO S1
  retry/repair Step B
COMMIT
```

Savepoint không biến mọi error thành retry-safe. External side effects và transaction state vẫn phải được reason riêng.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

await UpdateHeaderAsync(db, ct);
await db.SaveChangesAsync(ct);

await tx.CreateSavepointAsync("BeforeLines", ct);
try
{
    await UpdateLinesAsync(db, ct);
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
catch
{
    await tx.RollbackToSavepointAsync("BeforeLines", ct);
    throw;
}
```

## 5. Real production scenario

Import workflow ghi batch header và nhiều detail rows. Một subset vi phạm business/database constraint. Savepoint có thể hỗ trợ recovery trong transaction, nhưng nếu batch rất lớn thì transaction dài vẫn gây lock/log pressure.

## 6. Failure scenario & troubleshooting

**Symptom** → retry sau `SaveChanges` failure nhưng transaction vẫn unusable hoặc data state khó hiểu.  
**Evidence** → error type không retryable, transaction đã có external effects hoặc provider behavior khác kỳ vọng.  
**Hypothesis** → savepoint bị dùng như generic retry mechanism.  
**Diagnosis** → phân loại error, inspect transaction scope và generated SQL.  
**Fix** → retry chỉ lỗi phù hợp; thu nhỏ transaction; tách external effects.  
**Verification** → fault-injection test tại từng step.

## 7. Common mistakes

Transaction quá dài; giữ HTTP call trong DB transaction; retry mọi exception; nhầm savepoint với nested transaction; không test provider-specific behavior.

## 8. Alternatives

Nhiều transaction nhỏ thường đơn giản hơn nếu invariant cho phép. Outbox xử lý external messaging sau business transaction. Saga phù hợp cross-service workflows, không phải savepoint.

## 9. Trade-offs

### Advantages

Fine-grained rollback trong một transaction và hỗ trợ recovery scenarios.

### Costs / Risks

Transaction vẫn giữ locks/resources; logic recovery phức tạp; không giải quyết distributed side effects.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction và rollback.

### Middle

Biết khi nào EF Core `SaveChanges` nằm trong explicit transaction.

### Senior

Phân loại retryable failures và transaction state.

### Technical Lead / Architect

Quyết định invariant nào thực sự cần một transaction dài và khi nào nên redesign workflow.

## 11. Key takeaway

- Savepoint là checkpoint trong transaction, không phải distributed rollback.
- Recovery chỉ an toàn khi failure semantics được hiểu rõ.
- Transaction càng dài, operational cost càng lớn.

# 4. SQL covering indexes: Key Lookup, write amplification và index design theo workload

## 1. What is it?

Covering index chứa đủ columns để query được phục vụ từ index mà không cần quay lại base table/clustered index cho các columns còn thiếu. Mental model: giảm random lookups bằng cách đổi thêm storage và write cost.

## 2. Why does it exist?

Một selective nonclustered index tìm đúng rows nhanh, nhưng nếu query cần thêm columns không có trong index, SQL Server có thể thực hiện Key Lookup cho từng row. Với cardinality lớn, lookup cost tăng mạnh.

## 3. How does it work?

```text
Nonclustered seek
      │ 10 rows   → lookup cost nhỏ
      │ 100k rows → 100k lookups có thể rất đắt
      ▼
Clustered index / base row
```

`INCLUDE` cho phép thêm output columns vào leaf level mà không biến chúng thành key columns.

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_Customer_CreatedAt
ON dbo.Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, Total);

SELECT CreatedAt, Status, Total
FROM dbo.Orders
WHERE CustomerId = @CustomerId
ORDER BY CreatedAt DESC;
```

Đánh giá bằng actual execution plan, logical reads và write workload; không chỉ nhìn query duration một lần.

## 5. Real production scenario

Order-history endpoint nhanh với khách hàng nhỏ nhưng chậm với khách hàng có hàng chục nghìn orders. Plan cho thấy seek + rất nhiều Key Lookups. Covering index giảm reads, nhưng bảng có write rate cao nên index width phải được kiểm soát.

## 6. Failure scenario & troubleshooting

**Symptom** → read nhanh hơn sau thêm index nhưng write latency và storage tăng.  
**Evidence** → nhiều overlapping indexes, page writes và maintenance tăng.  
**Hypothesis** → over-indexing.  
**Diagnosis** → usage stats, query plans, index size và write metrics.  
**Fix** → consolidate/remove redundant indexes, giữ coverage cho critical workload.  
**Verification** → đo cả read lẫn write p95 sau thay đổi.

## 7. Common mistakes

`INCLUDE` mọi column; tạo index theo từng query riêng lẻ; bỏ qua selectivity/order; chỉ dựa missing-index hint; không tính update cost.

## 8. Alternatives

Projection/query redesign có thể giảm columns cần đọc. Columnstore phù hợp analytical workload khác. Key Lookup hoàn toàn chấp nhận được khi số rows nhỏ.

## 9. Trade-offs

### Advantages

Giảm I/O và lookup cho read-heavy hot queries.

### Costs / Risks

Storage lớn hơn, insert/update/delete tốn hơn, index maintenance tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu seek và lookup.

### Middle

Đọc actual plan và logical reads.

### Senior

Cân bằng covering width với write amplification.

### Technical Lead / Architect

Quản lý index portfolio theo workload tổng thể thay vì tối ưu endpoint cô lập.

## 11. Key takeaway

- Key Lookup không tự động là xấu; cardinality quyết định cost.
- Covering index đổi write/storage lấy read efficiency.
- Index design phải dựa trên workload, không dựa trên checklist.

# 5. Elasticsearch refresh: near-real-time search và read-after-write expectation

## 1. What is it?

Elasticsearch search là near-real-time: document được index thành công không nhất thiết lập tức xuất hiện trong search result cho đến khi refresh làm segment mới searchable. Mental model: indexing acknowledgment và search visibility là hai mốc khác nhau.

## 2. Why does it exist?

Refresh mỗi write sẽ làm segment churn và giảm indexing throughput. Elasticsearch batch hóa visibility để cân bằng throughput với freshness.

## 3. How does it work?

```text
Index request → in-memory indexing buffer
                     │
                  refresh
                     ▼
              searchable segment
```

Realtime GET theo document ID và search query có visibility semantics khác nhau; application không nên tự giả định read-after-write giống relational transaction.

## 4. Practical implementation

Trong test hoặc workflow đặc biệt có thể yêu cầu refresh behavior, nhưng không nên ép refresh mỗi production write:

```http
POST /products/_doc/42?refresh=wait_for
{
  "name": "Mechanical Keyboard",
  "status": "active"
}
```

`refresh=wait_for` chờ refresh làm change visible thay vì force refresh ngay lập tức, nhưng vẫn tăng request latency.

## 5. Real production scenario

CMS editor publish page rồi lập tức search trong admin UI. Primary database đã commit nhưng search chưa thấy document trong một khoảng ngắn. Đây có thể là expected eventual visibility, không phải lost write.

## 6. Failure scenario & troubleshooting

**Symptom** → “save thành công nhưng search không thấy”.  
**Evidence** → document xuất hiện sau refresh interval; indexing pipeline không báo lỗi.  
**Hypothesis** → freshness expectation mismatch.  
**Diagnosis** → kiểm tra index response, refresh timing, sync lag và search filters.  
**Fix** → UX acknowledgement, `wait_for` ở workflow cần thiết hoặc đọc primary store cho immediate confirmation.  
**Verification** → đo publish-to-search-visible latency như một SLI.

## 7. Common mistakes

Force refresh mỗi document; dùng Elasticsearch như transactional source of truth; nhầm indexing success với search visibility; không monitor sync lag.

## 8. Alternatives

SQL full-text/search có thể đủ cho nhu cầu đơn giản. Primary database nên phục vụ authoritative read khi immediate consistency là invariant.

## 9. Trade-offs

### Advantages

Batch refresh hỗ trợ indexing throughput tốt và search near-real-time.

### Costs / Risks

Có freshness window; UX và integration phải chấp nhận eventual visibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu near-real-time không phải instant search visibility.

### Middle

Debug indexing vs search visibility.

### Senior

Đo sync lag và chọn refresh strategy theo workflow.

### Technical Lead / Architect

Quyết định đâu là source of truth và business flow nào thực sự cần immediate consistency.

## 11. Key takeaway

- Index success và search visibility là hai sự kiện khác nhau.
- Force refresh có throughput cost.
- Freshness expectation phải là explicit product/system contract.

# 6. Anti-Corruption Layer: bảo vệ domain khỏi third-party model drift

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary dịch model/protocol của external system sang model mà domain nội bộ hiểu. Nó không chỉ là một DTO mapper; mục tiêu là ngăn semantics của dependency bên ngoài lan vào core model.

## 2. Why does it exist?

Third-party API có naming, status codes, lifecycle và business concepts khác hệ thống nội bộ. Nếu domain dùng trực tiếp external DTO, vendor changes trở thành domain changes.

## 3. How does it work?

```text
Domain/Application
       │ internal concepts
       ▼
Anti-Corruption Layer
       │ translation / normalization
       ▼
Third-party API / legacy system
```

ACL sở hữu mapping, error translation và compatibility policy tại integration boundary.

## 4. Practical implementation

```csharp
public sealed class ReviewGateway(ExternalReviewClient client)
{
    public async Task<ProductRating> GetRatingAsync(string sku, CancellationToken ct)
    {
        var dto = await client.GetAsync(sku, ct);
        return new ProductRating(
            Average: decimal.Parse(dto.Score, CultureInfo.InvariantCulture),
            Count: dto.TotalReviews);
    }
}
```

Domain không cần biết external API dùng string cho score hay tên field `TotalReviews`.

## 5. Real production scenario

E-commerce tích hợp review provider. Provider đổi status từ `APPROVED` sang nhiều moderation states. Nếu trạng thái vendor đã leak khắp codebase, migration chạm hàng chục modules. Với ACL, thay đổi tập trung tại integration boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → vendor schema change làm business logic lỗi ở nhiều nơi.  
**Evidence** → external DTO types xuất hiện trong domain/application APIs.  
**Hypothesis** → integration model đã trở thành internal model.  
**Diagnosis** → dependency search từ vendor package/types.  
**Fix** → introduce internal contract và translation boundary dần dần.  
**Verification** → contract tests chứng minh vendor variations được normalize.

## 7. Common mistakes

Tạo wrapper một-một không thêm semantic isolation; đặt ACL nhưng domain vẫn reference vendor enums; over-map mọi field dù không dùng; swallow external errors.

## 8. Alternatives

Direct integration hợp lý khi API nhỏ, stable và blast radius thấp. ACL đáng giá khi dependency quan trọng, semantics khác biệt hoặc migration/vendor replacement có khả năng xảy ra.

## 9. Trade-offs

### Advantages

Giảm coupling, cô lập schema drift và giữ ubiquitous language nội bộ sạch.

### Costs / Risks

Thêm mapping code, tests và một abstraction cần ownership.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain entity.

### Middle

Implement mapping và error translation.

### Senior

Thiết kế semantic boundary và contract tests.

### Technical Lead / Architect

Quyết định integration nào đủ rủi ro để justify ACL và tránh abstraction ceremony vô ích.

## 11. Key takeaway

- ACL bảo vệ semantics, không chỉ đổi tên fields.
- External model càng lan rộng, migration cost càng cao.
- Boundary chỉ đáng tồn tại khi nó thực sự cô lập thay đổi.

# 7. Azure Front Door: global ingress, health probing và origin failure isolation

## 1. What is it?

Azure Front Door là global Layer-7 entry point cho HTTP(S), cung cấp routing, acceleration, health-based origin selection và có thể kết hợp WAF/caching. Mental model: một global traffic boundary đứng trước regional origins.

## 2. Why does it exist?

Khi application có users toàn cầu hoặc nhiều origins/regions, DNS-only failover và từng app tự xử lý ingress tạo operational complexity. Front Door tập trung routing và health decisions ở edge.

## 3. How does it work?

```text
Users
  │
  ▼
Azure Front Door edge
  ├── healthy origin A
  └── healthy origin B
          │
          ▼
      App Service / AKS
```

Health probe chỉ phản ánh endpoint được probe. Một `/health` luôn trả 200 dù database chết có thể khiến Front Door tiếp tục route traffic vào origin không phục vụ được business requests.

## 4. Practical implementation

Thiết kế health endpoint theo dependency criticality:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, name: "sql", tags: ["ready"]);

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready")
});
```

Không đưa mọi optional dependency vào readiness nếu việc đó khiến toàn region bị loại khỏi rotation không cần thiết.

## 5. Real production scenario

E-commerce chạy West Europe và Southeast Asia. Một regional App Service bị lỗi deployment. Front Door health probe loại origin đó và route users sang region còn lại, nhưng capacity region còn lại phải đủ chịu failover load.

## 6. Failure scenario & troubleshooting

**Symptom** → origin A lỗi nhưng vẫn nhận traffic.  
**Evidence** → probe endpoint vẫn 200 trong khi business endpoint 5xx.  
**Hypothesis** → health check không đại diện service readiness.  
**Diagnosis** → compare probe telemetry với dependency/request telemetry.  
**Fix** → thiết kế readiness signal đúng và test regional failure.  
**Verification** → fault injection làm unhealthy origin bị loại trong expected interval.

## 7. Common mistakes

Coi multi-region là tự động HA; không capacity-plan failover; cache personalized responses; health probe quá shallow hoặc quá strict; quên origin security để bypass Front Door.

## 8. Alternatives

Application Gateway phù hợp regional ingress/use cases. Traffic Manager là DNS-based routing. CDN đơn thuần phù hợp static acceleration nhưng không thay toàn bộ global application routing requirements.

## 9. Trade-offs

### Advantages

Global entry point, edge routing, health-based failover và security integration.

### Costs / Risks

# 8. Git `bisect`: biến regression investigation thành binary search có bằng chứng

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên gây regression, dựa trên việc phân loại revisions thành `good` hoặc `bad`.

## 2. Why does it exist?

Nếu regression xuất hiện trong 500 commits, đọc diff tuần tự hoặc đoán theo tác giả/file rất chậm và dễ bias. Binary search giảm số revisions cần kiểm tra xuống khoảng logarithmic.

## 3. How does it work?

```text
known good -------------------------- known bad
                    ▲ test midpoint
          good -----┘
                       ▲ test next midpoint
```

Với history tuyến tính đủ testable, 512 candidate commits chỉ cần khoảng 9 bước phân loại.

## 4. Practical implementation

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0

# chạy test tại revision Git chọn
git bisect good   # hoặc bad

# khi hoàn tất
git bisect reset
```

Có thể automate nếu có deterministic regression test:

```bash
git bisect run dotnet test tests/Regression.Tests
```

## 5. Real production scenario

Sau hai tuần releases, API serialization thay đổi khiến một legacy client fail. Team có regression test tái hiện được. `git bisect run` xác định commit đổi serializer options thay vì manually review hàng trăm commits.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit “vô lý”.  
**Evidence** → test flaky hoặc old commits không build với current environment.  
**Hypothesis** → good/bad oracle không deterministic.  
**Diagnosis** → rerun test nhiều lần, kiểm tra environment/toolchain.  
**Fix** → stabilize reproduction, dùng `git bisect skip` cho untestable revisions.  
**Verification** → checkout parent/candidate và chứng minh behavior chuyển good → bad.

## 7. Common mistakes

Bắt đầu khi chưa có reliable reproduction; đánh dấu bad chỉ vì build environment hỏng; quên reset; coi bisect result là root cause mà không inspect diff.

## 8. Alternatives

Logs/traces tốt hơn nếu regression phụ thuộc production data. `git blame` tìm origin của line nhưng không chứng minh regression. Manual diff phù hợp change set rất nhỏ.

## 9. Trade-offs

### Advantages

Nhanh, evidence-driven và đặc biệt mạnh khi có automated regression test.

### Costs / Risks

Phụ thuộc history testable và deterministic oracle; merge-heavy history có thể phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu good/bad revision.

### Middle

Dùng bisect với reproducible test.

### Senior

Automate oracle và xử lý untestable commits.

### Technical Lead / Architect

Đầu tư regression tests/toolchain reproducibility để incident investigation có thể tự động hóa.

## 11. Key takeaway

- `git bisect` thay guessing bằng binary search.
- Chất lượng result phụ thuộc quality của reproduction test.
- Commit tìm được là điểm bắt đầu root-cause analysis, không phải kết luận cuối.

# 9. IIS Application Pool recycling: process lifetime, in-memory state và deployment surprises

## 1. What is it?

Application Pool quản lý một hoặc nhiều IIS worker processes (`w3wp.exe`). Recycling thay worker process theo policy/configuration hoặc operational event. Mental model: web process là disposable; application không được giả định process sống mãi.

## 2. Why does it exist?

IIS cần isolation, lifecycle management và khả năng thay process khi config/deployment thay đổi hoặc theo policy. Recycling cũng từng được dùng để giảm tác động của long-lived process problems, nhưng không nên là “fix memory leak” chính.

## 3. How does it work?

```text
IIS App Pool
   │
   ├── old w3wp ── draining/termination
   └── new w3wp ── startup/warm-up
```

Process-local memory, static caches và background timers không sống qua recycle. In-flight behavior phụ thuộc shutdown/startup configuration và application design.

## 4. Practical implementation

ASP.NET Core application nên coi shutdown là expected lifecycle event:

```csharp
public sealed class CleanupWorker(ILogger<CleanupWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await DoWorkAsync(stoppingToken);
        }

        log.LogInformation("Worker stopping gracefully");
    }
}
```

Business-critical scheduled state không nên chỉ nằm trong memory của IIS-hosted process.

## 5. Real production scenario

Legacy enterprise site giữ user workflow state trong static dictionary. App Pool recycle ban đêm làm users mất workflow. Team ban đầu nghĩ database bị mất dữ liệu, nhưng state chưa từng được persist.

## 6. Failure scenario & troubleshooting

**Symptom** → session/cache/background job “reset ngẫu nhiên”.  
**Evidence** → IIS event logs cho thấy recycle trùng thời điểm.  
**Hypothesis** → process-local state bị xem như durable state.  
**Diagnosis** → kiểm tra recycle settings, deployment events, process start time và storage ownership.  
**Fix** → externalize durable/shared state; make startup/shutdown safe.  
**Verification** → recycle có chủ đích không làm mất business state.

## 7. Common mistakes

Tắt recycle để che leak; lưu critical state trong static memory; chạy scheduler quan trọng trong mỗi web instance; không log startup/shutdown; nhầm App Pool restart với server restart.

## 8. Alternatives

App Service/container cũng có disposable process semantics. Worker Service/queue-based job phù hợp background workload hơn khi cần lifecycle độc lập với web hosting.

## 9. Trade-offs

### Advantages

Isolation và lifecycle control cho IIS-hosted applications.

### Costs / Risks

Cold start, mất in-memory state và duplicate/background execution nếu application không thiết kế cho restart.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu App Pool và worker process.

### Middle

Troubleshoot recycle/startup logs và graceful shutdown.

### Senior

Phân biệt ephemeral process state với durable/shared state.

### Technical Lead / Architect

Thiết kế application restart-safe và tách background responsibilities khỏi web process khi cần.

## 11. Key takeaway

- Web process phải được xem là disposable.
- Recycling không được làm mất business-critical state.
- Restart-safe design là yêu cầu production, không phải edge case.

# 10. Production metrics cardinality: khi observability tự trở thành sự cố

## 1. What is it?

Cardinality là số lượng combinations khác nhau của metric label dimensions. Một metric `http_requests_total{method,status}` có cardinality nhỏ; thêm `user_id`, raw URL hoặc request ID có thể tạo hàng triệu time series.

## 2. Why does it exist?

Labels giúp slice metrics theo dimensions hữu ích. Nhưng metrics systems tối ưu cho bounded dimensions, không phải arbitrary identifiers. Unbounded labels làm memory/storage/query cost tăng nhanh.

## 3. How does it work?

```text
metric × labels

method: 5
status: 10
region: 4
=> tối đa ~200 combinations

+ user_id: 1,000,000
=> cardinality có thể bùng nổ
```

Cardinality cost nhân qua dimensions; không thể đánh giá từng label độc lập.

## 4. Practical implementation

Tốt:

```csharp
requestCounter.Add(1,
    new KeyValuePair<string, object?>("method", request.Method),
    new KeyValuePair<string, object?>("route", endpointRoute),
    new KeyValuePair<string, object?>("status_class", "2xx"));
```

Tránh label bằng raw path như `/orders/8f5...` hoặc `customerId`. Những identifiers đó phù hợp hơn với trace/log có sampling/retention thích hợp.

## 5. Real production scenario

Team thêm `tenant_id` vào mọi request metric để debug một customer. Telemetry backend tăng số series hàng trăm lần, dashboard chậm và ingestion cost tăng mạnh. Một debugging convenience đã trở thành platform incident.

## 6. Failure scenario & troubleshooting

**Symptom** → telemetry ingestion/storage tăng đột biến sau deployment.  
**Evidence** → active time-series count tăng cùng label mới.  
**Hypothesis** → high-cardinality dimension.  
**Diagnosis** → inspect top metric names/labels và unique-value counts.  
**Fix** → remove/aggregate unbounded labels; chuyển correlation sang traces/logs.  
**Verification** → series count và ingestion cost giảm sau retention window.

## 7. Common mistakes

Dùng request ID làm metric label; raw URL thay route template; customer/email làm dimension; tạo histogram buckets quá chi tiết mà không có SLO use case; không có telemetry budget.

## 8. Alternatives

Logs lưu discrete high-cardinality events tốt hơn. Traces giữ request-specific causal context. Metrics nên dùng cho aggregate health, SLI và bounded operational dimensions.

## 9. Trade-offs

### Advantages

Labels đúng giúp slicing nhanh và alert/SLO analysis hiệu quả.

### Costs / Risks

High cardinality làm backend đắt, chậm hoặc mất ổn định; còn có privacy risk nếu labels chứa identifiers.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu metric labels tạo time series.

### Middle

Chọn bounded labels và route templates.

### Senior

Theo dõi series cardinality, ingestion cost và query performance.

### Technical Lead / Architect

Định nghĩa telemetry semantic conventions, budgets và review guardrails toàn hệ thống.

## 11. Key takeaway

- Metrics dành cho bounded aggregation, không phải request-level identity.
- Cardinality tăng theo combinations của labels.
- Chọn Logs, Metrics và Traces theo loại câu hỏi cần trả lời.
