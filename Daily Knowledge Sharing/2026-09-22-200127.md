# 1. `Span<T>` / `Memory<T>`: giảm allocation mà không phá lifetime safety

## 1. What is it?

Mental model: `Span<T>` là một **view** lên một vùng memory liên tục, không sở hữu vùng memory đó. Nó có thể trỏ vào array, stack memory hoặc một phần buffer mà không cần copy. `Memory<T>` có mục tiêu tương tự nhưng có thể tồn tại qua asynchronous boundary vì nó không phải `ref struct`.

`Span<T>` được runtime/compiler áp các lifetime restriction mạnh để reference không sống lâu hơn memory mà nó trỏ tới.

## 2. Why does it exist?

Code xử lý protocol, parsing, serialization thường cắt string/array thành nhiều phần. Cách đơn giản như `Substring`, `ToArray()` có thể tạo object mới liên tục. Ở hot path, allocation rate cao dẫn tới GC pressure dù từng allocation nhỏ.

`Span<T>` cho phép thao tác trên slice mà không copy.

## 3. How does it work?

```text
byte[] buffer
┌───────────────────────────────┐
│ header │ payload │ checksum   │
└───────────────────────────────┘
   ▲          ▲
 Span #1    Span #2
```

Slice chỉ thay đổi start/length của view. Dữ liệu nền không được copy.

Vì `Span<T>` có thể trỏ stack memory, compiler không cho capture nó vào lambda, box thành `object`, lưu vào heap field thông thường hoặc giữ qua `await`.

## 4. Practical implementation

```csharp
static bool TryReadHeader(ReadOnlySpan<byte> packet, out ushort length)
{
    length = 0;
    if (packet.Length < 2)
        return false;

    length = System.Buffers.Binary.BinaryPrimitives
        .ReadUInt16BigEndian(packet[..2]);

    return packet.Length >= 2 + length;
}
```

Nếu buffer cần sống qua `await`, dùng `ReadOnlyMemory<byte>` và lấy `.Span` sau asynchronous boundary khi cần xử lý đồng bộ.

## 5. Real production scenario

Một API ingest file CSV lớn. Parser cũ tạo hàng triệu substring. CPU chưa bão hòa nhưng allocation rate rất cao và Gen0 collections liên tục. Chuyển parser hot path sang `ReadOnlySpan<char>` giảm intermediate strings mà không thay đổi API business layer.

## 6. Failure scenario & troubleshooting

**Symptom** → tối ưu sang Span nhưng latency gần như không đổi.

**Evidence** → profiler cho thấy bottleneck thực tế nằm ở SQL/network, allocation của parser chỉ chiếm phần nhỏ.

**Hypothesis** → micro-optimization sai tầng.

**Diagnosis** → so sánh allocation profile, CPU samples và end-to-end trace.

**Fix** → chỉ giữ optimization nếu nó đơn giản hoặc có measured benefit; ưu tiên bottleneck thật.

**Verification** → benchmark allocation bytes/op và production p95/p99.

## 7. Common mistakes

Dùng `Span<T>` ở mọi method vì nghĩ luôn nhanh hơn; gọi `ToArray()` ngay sau khi slice; cố giữ Span qua `await`; pool buffer nhưng trả pool trước khi consumer dùng xong; làm API public khó dùng chỉ để tiết kiệm allocation chưa đo.

## 8. Alternatives

Array/string bình thường là default tốt cho phần lớn business code. `ArrayPool<T>` hữu ích khi cần reusable owned buffer. `Memory<T>` phù hợp asynchronous APIs. Streaming có thể tốt hơn việc materialize buffer lớn rồi tối ưu slice.

## 9. Trade-offs

### Advantages

Giảm copy và allocation trong parsing/serialization hot path; biểu diễn slice rõ ràng.

### Costs / Risks

Lifetime semantics phức tạp hơn; code khó compose hơn; lợi ích nhỏ nếu bottleneck là I/O.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Span là view, không phải container sở hữu dữ liệu.

### Middle

Dùng slice/parsing an toàn và biết khi nào cần `Memory<T>`.

### Senior

Đọc profiler, hiểu lifetime, pooling và async boundary.

### Technical Lead / Architect

Giữ low-level optimization ở boundary/hot path phù hợp, không lan complexity vào domain code nếu không có performance budget chứng minh.

## 11. Key takeaway

- `Span<T>` tối ưu data access, không phải universal replacement cho array/string.
- Lifetime safety là lý do các restriction tồn tại.
- Đo allocation trước và sau; không tối ưu theo trực giác.

# 2. REST API idempotency key: chống duplicate side effect khi client retry

## 1. What is it?

Idempotency key là identifier do client gửi cùng một logical operation để server nhận ra retry của operation đã xử lý. Mục tiêu không phải ngăn mọi duplicate request; mục tiêu là làm nhiều lần gửi cùng intent tạo ra **một business effect**.

## 2. Why does it exist?

Client có thể timeout sau khi server đã commit nhưng trước khi response tới client. Client không biết operation thành công hay thất bại. Nếu retry `POST /payments` mù quáng, hệ thống có thể charge hai lần.

## 3. How does it work?

```text
Client ─ POST key=abc ─> API ─> commit Order #123
Client <── network timeout ─X
Client ─ POST key=abc ─> API ─> lookup abc ─> return previous result
```

Key phải được scope đúng, ví dụ theo tenant/user + operation, và lưu cùng trạng thái đủ để phân biệt pending/completed/conflicting payload.

## 4. Practical implementation

Một bảng SQL đơn giản:

```sql
CREATE TABLE IdempotencyKeys (
    TenantId uniqueidentifier NOT NULL,
    [Key] nvarchar(100) NOT NULL,
    RequestHash varbinary(32) NOT NULL,
    ResourceId uniqueidentifier NULL,
    Status varchar(20) NOT NULL,
    CreatedAt datetime2 NOT NULL,
    CONSTRAINT PK_IdempotencyKeys PRIMARY KEY (TenantId, [Key])
);
```

API phải reject nếu cùng key được reuse với payload khác thay vì âm thầm trả kết quả cũ.

## 5. Real production scenario

Mobile checkout gửi order creation qua mạng yếu. Server tạo order nhưng response mất. App retry cùng key; API trả lại order đã tạo thay vì tạo order thứ hai.

## 6. Failure scenario & troubleshooting

**Symptom** → vẫn có duplicate orders dù client gửi idempotency key.

**Evidence** → log cho thấy hai instances đồng thời kiểm tra “key chưa tồn tại”, sau đó cùng thực hiện side effect.

**Hypothesis** → check-then-act không atomic.

**Diagnosis** → idempotency record không có unique constraint hoặc không cùng consistency boundary với operation.

**Fix** → enforce uniqueness/transactional claim; thiết kế trạng thái pending/completed.

**Verification** → concurrency test gửi hàng chục request cùng key vào nhiều instances.

## 7. Common mistakes

Chỉ cache key trong memory; không scope theo tenant; reuse key cho payload khác; TTL ngắn hơn retry window; đánh dấu completed trước business commit; nghĩ HTTP `POST` tự nhiên không thể idempotent.

## 8. Alternatives

Business-natural unique key như `ExternalOrderId` thường đơn giản hơn generic idempotency store. Queue + deduplication phù hợp asynchronous workflow nhưng consumer vẫn cần idempotency.

## 9. Trade-offs

### Advantages

Retry an toàn hơn và UX tốt hơn trong network failure.

### Costs / Risks

Thêm storage, cleanup, concurrency semantics và response replay policy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không chứng minh server chưa xử lý.

### Middle

Implement key validation, unique constraint và conflict response.

### Senior

Thiết kế atomicity, retry window, payload hash và multi-instance races.

### Technical Lead / Architect

Xác định operation nào cần idempotency, boundary nào sở hữu key và business uniqueness có thể thay abstraction generic hay không.

## 11. Key takeaway

- Retry safety phải được thiết kế từ business effect.
- Idempotency check phải atomic dưới concurrency.
- Cùng key nhưng payload khác phải là conflict, không phải cache hit.

# 3. EF Core transaction savepoint: partial recovery bên trong một transaction

## 1. What is it?

Savepoint là checkpoint bên trong database transaction. Có thể rollback tới savepoint mà không rollback toàn bộ transaction. EF Core có thể tạo savepoint trước `SaveChanges` khi transaction đã tồn tại, giúp xử lý một số failure mà vẫn giữ transaction ngoài.

## 2. Why does it exist?

Một transaction có nhiều bước đôi khi cần retry hoặc sửa một bước mà không bỏ toàn bộ work đã làm. Nhưng retry cả transaction có thể đắt hoặc phá application workflow.

## 3. How does it work?

```text
BEGIN
  step A
  SAVEPOINT S1
  step B ── failure
  ROLLBACK TO S1
  corrected step B
COMMIT
```

Savepoint không commit độc lập. Nếu outer transaction rollback, mọi bước vẫn mất.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

await SaveHeaderAsync(db, ct);
await tx.CreateSavepointAsync("BeforeLines", ct);

try
{
    await SaveLinesAsync(db, ct);
}
catch (DbUpdateException)
{
    await tx.RollbackToSavepointAsync("BeforeLines", ct);
    // resolve only if the failure is understood and safely recoverable
    await SaveCorrectedLinesAsync(db, ct);
}

await tx.CommitAsync(ct);
```

Không nên catch mọi exception rồi retry cùng transaction một cách vô điều kiện.

## 5. Real production scenario

Import workflow ghi batch header rồi nhiều detail rows. Một subset vi phạm business constraint có thể được normalize và thử lại mà không cần rebuild toàn bộ transaction state.

## 6. Failure scenario & troubleshooting

**Symptom** → sau DB error, transaction tiếp tục nhưng commit thất bại hoặc state khó đoán.

**Evidence** → exception loại không recoverable, connection/transaction đã invalid hoặc application state không đồng bộ với DB.

**Diagnosis** → savepoint bị coi như universal retry mechanism.

**Fix** → chỉ recover lỗi có semantics rõ; với transient connection failure, retry toàn unit-of-work bằng execution strategy phù hợp.

**Verification** → integration test với database thật, không mock transaction semantics.

## 7. Common mistakes

Nhầm savepoint với nested transaction; giữ transaction mở trong lúc gọi remote API; retry deadlock/connection failure ở sai scope; DbContext state không được reconcile sau rollback.

## 8. Alternatives

Transaction ngắn, đơn giản thường tốt hơn. Chia workflow thành idempotent steps hoặc Saga nếu boundary vượt database. Execution strategy phù hợp transient database failure.

## 9. Trade-offs

### Advantages

Có partial recovery trong một atomic transaction.

### Costs / Risks

Tăng state complexity, lock duration và khả năng developer hiểu sai transaction state.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu savepoint vẫn nằm trong outer transaction.

### Middle

Dùng transaction API và integration test rollback.

### Senior

Phân biệt recoverable business/database conflict với transient infrastructure failure.

### Technical Lead / Architect

Ưu tiên transaction boundary ngắn; chỉ dùng savepoint khi workflow thực sự cần partial recovery.

## 11. Key takeaway

- Savepoint không phải nested commit.
- Recovery phải dựa trên loại failure cụ thể.
- Transaction dài thường là design smell cần xem lại boundary.

# 4. PostgreSQL MVCC và VACUUM: vì sao UPDATE tạo version mới thay vì sửa row tại chỗ

## 1. What is it?

MVCC (Multi-Version Concurrency Control) cho phép nhiều transaction nhìn các version dữ liệu phù hợp snapshot của chúng. Trong PostgreSQL, `UPDATE` về bản chất tạo tuple version mới và để version cũ trở thành dead tuple khi không transaction nào còn cần nó.

## 2. Why does it exist?

Nếu reader và writer luôn khóa chặn nhau, throughput concurrent workload giảm mạnh. MVCC cho reader thấy snapshot ổn định trong khi writer tạo version mới.

## 3. How does it work?

```text
Row v1 [visible to old snapshot]
   │ UPDATE
   ▼
Row v2 [visible to newer transaction]

v1 eventually no longer needed
   ↓
VACUUM reclaims reusable space
```

Visibility dựa transaction metadata. VACUUM không phải “optional cleanup job”; nó là phần thiết yếu của storage lifecycle.

## 4. Practical implementation

Điều tra table bloat/autovacuum thay vì chạy `VACUUM FULL` theo phản xạ:

```sql
SELECT relname, n_live_tup, n_dead_tup,
       last_autovacuum, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Sau đó correlate với update/delete rate, long-running transactions và autovacuum configuration.

## 5. Real production scenario

Audit-heavy SaaS table bị update trạng thái liên tục. Long-running reporting transaction giữ snapshot cũ nhiều giờ, khiến dead tuples chưa thể reclaim sớm và table/index bloat tăng.

## 6. Failure scenario & troubleshooting

**Symptom** → table size tăng mạnh dù row count gần như không đổi.

**Evidence** → dead tuples cao, autovacuum chạy nhưng không reclaim như kỳ vọng; có long-running transaction.

**Hypothesis** → old snapshot giữ tuple versions.

**Diagnosis** → kiểm tra `pg_stat_activity`, dead tuples và vacuum logs.

**Fix** → xử lý transaction dài, tune autovacuum theo workload; chỉ chọn aggressive maintenance khi có evidence.

**Verification** → dead tuple trend và query I/O giảm.

## 7. Common mistakes

Giữ transaction mở quanh user interaction; disable autovacuum; coi `VACUUM FULL` là routine fix; chỉ nhìn logical row count mà bỏ qua physical storage.

## 8. Alternatives

SQL Server cũng có row-versioning mechanisms nhưng storage/concurrency implementation khác. Không nên copy operational tuning giữa database engines chỉ vì cùng dùng MVCC terminology.

## 9. Trade-offs

### Advantages

Reader/writer concurrency tốt và snapshot semantics mạnh.

### Costs / Risks

Version cleanup, bloat, vacuum I/O và transaction-age management trở thành operational concern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu UPDATE có thể tạo row version mới.

### Middle

Đọc PostgreSQL activity/statistics và giữ transaction ngắn.

### Senior

Phân tích vacuum, bloat, snapshots và write-heavy workload.

### Technical Lead / Architect

Đưa maintenance characteristics vào capacity model thay vì chỉ benchmark query happy path.

## 11. Key takeaway

- MVCC đổi blocking pressure lấy version-management cost.
- Long-running transaction có hậu quả storage ngoài lock semantics.
- VACUUM là runtime maintenance mechanism, không phải housekeeping tùy chọn.

# 5. Redis cache stampede: khi cache miss biến thành database outage

## 1. What is it?

Cache stampede xảy ra khi nhiều request cùng lúc thấy một hot key bị miss/expire rồi đồng loạt truy cập source of truth để rebuild cùng dữ liệu.

## 2. Why does it exist?

Cache giảm downstream load khi hit. Nhưng TTL đồng bộ có thể tạo load spike cực lớn đúng lúc entry biến mất. Một key có 10.000 requests/s có thể biến một miss thành 10.000 database queries.

## 3. How does it work?

```text
Hot key expires
   ├─ request 1 ─┐
   ├─ request 2 ─┼─> DB
   ├─ request 3 ─┤
   └─ ... ───────┘
```

Single-flight/request coalescing cho một worker rebuild trong khi others chờ hoặc nhận stale value có kiểm soát.

## 4. Practical implementation

Trong một process có thể dùng keyed lock; distributed fleet cần strategy phù hợp hơn. Một lựa chọn là stale-while-revalidate semantics: giữ value cũ trong soft TTL và chỉ một actor refresh. Hard TTL là giới hạn không được phục vụ quá stale.

Pseudo-state:

```text
fresh       -> return
soft-expired-> return stale + one refresh
hard-expired-> block/fallback according to policy
```

## 5. Real production scenario

Product detail cache của campaign hết hạn cùng lúc sau 5 phút. SQL CPU tăng 20% lên 100% trong vài giây, API timeout và retries làm sự cố nặng hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → DB spike theo chu kỳ đúng TTL.

**Evidence** → cache miss burst, cùng key, dependency calls tăng đột biến.

**Hypothesis** → synchronized expiration/stampede.

**Diagnosis** → correlate cache hit ratio, key expiry và SQL traces.

**Fix** → jitter TTL, request coalescing, stale serving hoặc proactive refresh.

**Verification** → load test expiration event, không chỉ steady-state cache hit.

## 7. Common mistakes

Chỉ tăng TTL; distributed lock không có timeout/fencing; mọi instance tự refresh; cache miss fallback không có concurrency limit; Redis outage khiến toàn traffic lập tức đổ vào DB.

## 8. Alternatives

Local near-cache giảm Redis traffic nhưng tăng invalidation complexity. Output/CDN cache có thể hấp thụ request trước application. Đôi khi query đủ nhanh và cache không đáng tồn tại.

## 9. Trade-offs

### Advantages

Stampede protection làm cache failure/expiry ít biến thành downstream outage.

### Costs / Risks

Stale data và coordination complexity; distributed locking có failure modes riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss có cost ở source of truth.

### Middle

Implement TTL jitter và metrics hit/miss.

### Senior

Thiết kế stale policy, coalescing và fallback under outage.

### Technical Lead / Architect

Xác định cache có thực sự cần thiết và downstream capacity khi cache hoàn toàn unavailable.

## 11. Key takeaway

- Test cache expiration như một failure event.
- TTL jitter giảm synchronization nhưng không thay capacity planning.
- Cache outage path phải có bounded load xuống database.

# 6. DDD Aggregate boundary: consistency boundary chứ không phải object graph

## 1. What is it?

Aggregate là nhóm domain objects được thay đổi như một consistency boundary, được truy cập mutation qua Aggregate Root. Nó không có nghĩa “load toàn bộ object graph có quan hệ”. Boundary nên phản ánh invariant cần atomic consistency.

## 2. Why does it exist?

Nếu mọi entity liên quan đều nằm trong một aggregate lớn, transaction, locking và loading cost phình to. Nếu boundary quá nhỏ, invariant business cần atomicity lại bị chia cắt.

## 3. How does it work?

Ví dụ `Order` có invariant tổng tiền phải bằng tổng lines. `Order` và `OrderLine` có thể cùng aggregate. Nhưng `Customer` không cần nằm trong Order aggregate chỉ vì Order có CustomerId.

```text
Order Aggregate
┌────────────────────┐
│ Order (Root)       │
│ ├─ OrderLine       │
│ └─ ShippingAddress │
└────────────────────┘
        │ CustomerId
        ▼
Customer Aggregate
```

Cross-aggregate coordination thường dùng ID, application workflow hoặc domain events thay vì object reference mutable trực tiếp.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void AddLine(ProductId productId, int quantity, Money price)
    {
        if (quantity <= 0) throw new DomainException("Quantity must be positive");
        _lines.Add(new OrderLine(productId, quantity, price));
        RecalculateTotal();
    }
}
```

Mutation đi qua root để invariant không bị bypass.

## 5. Real production scenario

E-commerce Order trước đây chứa Customer, Product, Inventory, Promotion graph. Mỗi update order kéo theo huge EF graph và contention. Tách boundaries giúp order transaction chỉ sở hữu state cần atomicity; inventory reservation trở thành workflow riêng.

## 6. Failure scenario & troubleshooting

**Symptom** → một command cần lock/load hàng nghìn child records hoặc nhiều aggregate tables không liên quan trực tiếp.

**Evidence** → transaction dài, conflicts cao, aggregate serialized payload lớn.

**Hypothesis** → aggregate boundary quá rộng.

**Diagnosis** → liệt kê invariants nào thực sự phải atomic.

**Fix** → split boundary và chấp nhận explicit eventual consistency nơi business cho phép.

**Verification** → invariant tests + concurrency/load tests.

## 7. Common mistakes

Aggregate = EF navigation graph; mỗi table = aggregate; repository cho mọi entity; cross-aggregate transaction mặc định; domain events dùng để né việc định nghĩa invariant rõ ràng.

## 8. Alternatives

CRUD/application service đơn giản phù hợp domain ít business rules. Không cần DDD tactical patterns nếu complexity không đủ biện minh.

## 9. Trade-offs

### Advantages

Boundary rõ cho invariant, transaction và ownership.

### Costs / Risks

Đòi hỏi domain analysis; split boundaries có thể đưa eventual consistency vào workflow.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Aggregate Root bảo vệ invariant.

### Middle

Implement mutation qua root và persistence boundary.

### Senior

Thiết kế boundary dựa consistency/contention, không dựa table relationship.

### Technical Lead / Architect

Quyết định nơi cần strong consistency và nơi business chấp nhận asynchronous coordination.

## 11. Key takeaway

- Aggregate là consistency boundary.
- Boundary càng lớn không đồng nghĩa domain model càng “đúng DDD”.
- Chỉ giữ cùng aggregate những state cần thay đổi atomic để bảo vệ invariant.

# 7. Azure Functions concurrency: scale-out không đồng nghĩa throughput tăng vô hạn

## 1. What is it?

Azure Functions có concurrency ở mỗi host instance và scale-out bằng nhiều instances tùy hosting plan/trigger. Throughput thực tế bị giới hạn bởi downstream capacity, trigger semantics, execution duration và concurrency configuration.

## 2. Why does it exist?

Serverless giúp tăng workers mà không tự quản VM, nhưng nếu mỗi invocation dùng SQL connection hoặc gọi API có quota, scale nhanh hơn có thể làm downstream collapse thay vì tăng throughput.

## 3. How does it work?

```text
Queue backlog
   ↓
Function instances: F1 F2 F3 F4 ...
   ↓        ↓       ↓
      shared SQL / API
          hard limit
```

Scale controller nhìn trigger/load signals; application vẫn phải có backpressure/idempotency và downstream capacity model.

## 4. Practical implementation

Với Service Bus trigger, tune concurrency có chủ ý thay vì max mặc định theo cảm tính. Handler dùng async I/O, bounded external calls và idempotent processing. Metrics cần gồm invocation concurrency, queue age, dependency latency, SQL pool usage và throttling.

## 5. Real production scenario

Import queue tăng từ 1k lên 200k messages. Functions scale out mạnh; SQL connection pool/database worker saturation tăng, processing time dài hơn và message lock renewals nhiều hơn. Thêm instances làm throughput giảm.

## 6. Failure scenario & troubleshooting

**Symptom** → instance count tăng nhưng queue age vẫn tăng.

**Evidence** → dependency p95 tăng, SQL throttling/connection waits tăng.

**Hypothesis** → downstream saturation.

**Diagnosis** → compare throughput với concurrency, dependency latency và capacity.

**Fix** → bound concurrency, batch hợp lý, optimize DB hoặc decouple stage.

**Verification** → load test tìm throughput knee thay vì chỉ “max instances”.

## 7. Common mistakes

Scale-out như universal fix; synchronous blocking; shared static mutable state; không idempotent; không xem lock duration; retry storm khi dependency throttles.

## 8. Alternatives

Worker Service/Container Apps cho workload cần kiểm soát process/concurrency rõ hơn. App Service background worker phù hợp một số hệ thống nhỏ nhưng coupling deployment/runtime cao hơn.

## 9. Trade-offs

### Advantages

Elasticity và managed trigger integration.

### Costs / Risks

Concurrency khó thấy, downstream overload, cold start/plan behavior và cost theo workload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một Function app có thể chạy nhiều invocations song song.

### Middle

Implement idempotent async handler và telemetry.

### Senior

Tune concurrency dựa downstream capacity và queue age.

### Technical Lead / Architect

Chọn compute model theo workload shape, SLO, cost và operational control thay vì “serverless = auto scale”.

## 11. Key takeaway

- Scale controller không biết toàn bộ downstream limits của bạn.
- Throughput có điểm bão hòa; concurrency vượt điểm đó làm latency xấu hơn.
- Queue age + dependency saturation quan trọng hơn instance count riêng lẻ.

# 8. IIS Application Pool recycling: process restart “đúng thiết kế” vẫn có thể làm mất in-memory state

## 1. What is it?

IIS Application Pool chứa worker process (`w3wp.exe`) chạy ứng dụng. Recycling thay worker process theo configuration/health/administrative action. Với ASP.NET Core behind IIS, hosting model khác nhau nhưng process lifecycle vẫn là operational boundary cần hiểu.

## 2. Why does it exist?

Long-running process có thể cần restart vì deployment, configuration, health hoặc operational policy. IIS cung cấp lifecycle management thay vì coi process chạy vĩnh viễn.

## 3. How does it work?

Trong overlapped recycle, worker mới có thể khởi động trước khi worker cũ dừng. Điều này giảm downtime nhưng trong một khoảng ngắn hai process có thể cùng tồn tại.

```text
old w3wp ─────── draining ──X
          new w3wp ─────────────>
```

In-memory cache, singleton state và timer job thuộc process, không phải application identity toàn cluster.

## 4. Practical implementation

Application phải xử lý graceful shutdown bằng `IHostApplicationLifetime`/`CancellationToken`; durable work không chỉ nằm trong memory. Session quan trọng nên dùng distributed store khi nhiều process/instances cần share.

```csharp
public sealed class Worker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
            await ProcessNextAsync(stoppingToken);
    }
}
```

## 5. Real production scenario

Legacy enterprise app có timer gửi invoice trong singleton. App Pool recycle đúng lúc timer chạy; job bị ngắt giữa chừng. Sau restart, không có durable checkpoint nên invoice bị bỏ hoặc gửi lại.

## 6. Failure scenario & troubleshooting

**Symptom** → user session mất hoặc background job “randomly” dừng mỗi ngày.

**Evidence** → IIS event logs/process start time trùng thời điểm lỗi.

**Hypothesis** → recycle/lifecycle dependency.

**Diagnosis** → inspect App Pool recycling settings, deployment logs và application shutdown logs.

**Fix** → externalize durable state/job scheduling; graceful cancellation.

**Verification** → chủ động recycle dưới load và quan sát request/job behavior.

## 7. Common mistakes

Lưu business state trong static; coi singleton là cluster singleton; disable recycle để che bug; background thread không observe shutdown; không warm up app mới.

## 8. Alternatives

Azure App Service/container orchestration cũng có process restart semantics, chỉ khác control plane. Durable job nên dùng scheduler/queue/worker architecture thay vì dựa process lifetime.

## 9. Trade-offs

### Advantages

Managed lifecycle, isolation và recovery cho hosted apps.

### Costs / Risks

In-memory assumptions dễ vỡ; recycle có thể lộ startup cost và non-durable work.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu web process không sống vĩnh viễn.

### Middle

Đọc IIS logs và implement graceful shutdown.

### Senior

Thiết kế state/job không phụ thuộc worker lifetime.

### Technical Lead / Architect

Xác định state nào process-local được phép mất và state nào phải durable/distributed.

## 11. Key takeaway

- Process restart là normal operating condition.
- Singleton chỉ singleton trong process/container scope.
- Test recycle/restart như một failure mode thật.

# 9. Contract testing: bảo vệ integration boundary mà không cần E2E cho mọi case

## 1. What is it?

Contract test kiểm tra producer và consumer đồng ý về interface observable: HTTP schema/status, event shape, required fields hoặc compatibility rules. Nó tập trung boundary giữa components thay vì toàn user journey.

## 2. Why does it exist?

Unit tests không phát hiện producer đổi JSON field mà consumer phụ thuộc. Full E2E có thể phát hiện nhưng thường chậm, flaky và khó chạy cho mọi integration combination.

## 3. How does it work?

Consumer expectations được biểu diễn thành executable contract hoặc producer schema test. CI xác minh thay đổi producer không phá contract đã hỗ trợ.

```text
Consumer expectation
        ↓
     Contract
        ↓ verify
     Provider API
```

Contract không chứng minh business workflow end-to-end hoạt động; nó bảo vệ compatibility boundary.

## 4. Practical implementation

Với ASP.NET Core, integration test có thể boot app bằng `WebApplicationFactory` và assert status + JSON contract/OpenAPI compatibility. Event contracts nên version/schema-check và test backward-compatible deserialization bằng payload cũ.

```csharp
var response = await client.GetAsync("/api/products/42");
response.EnsureSuccessStatusCode();
var dto = await response.Content.ReadFromJsonAsync<ProductDto>();
Assert.NotNull(dto?.Name);
```

Test thực tế cần assert semantics quan trọng hơn chỉ “deserialization không ném lỗi”.

## 5. Real production scenario

Product API đổi `price` từ number thành nested object. Frontend và mobile app deploy độc lập. Provider contract test chặn breaking change trước khi release.

## 6. Failure scenario & troubleshooting

**Symptom** → contract suite xanh nhưng production vẫn lỗi.

**Evidence** → schema đúng nhưng semantics thay đổi, ví dụ currency unit đổi hoặc field nullable thực tế.

**Hypothesis** → contract chỉ kiểm shape, không kiểm business semantics.

**Diagnosis** → compare real payload và assumptions của consumer.

**Fix** → thêm semantic invariants/example compatibility; giữ một số E2E cho critical journey.

**Verification** → replay representative payloads và deploy pipeline gate.

## 7. Common mistakes

Snapshot toàn JSON khiến test brittle; mock provider rồi gọi đó là contract test; không version event; test implementation detail; nghĩ contract tests thay thế integration/E2E hoàn toàn.

## 8. Alternatives

OpenAPI diff/static compatibility checks rẻ hơn nhưng không chứng minh runtime behavior. E2E bảo vệ journey rộng hơn nhưng cost cao. Integration tests với real dependency bảo vệ behavior sâu hơn ở một boundary.

## 9. Trade-offs

### Advantages

Feedback nhanh cho independently deployed components, giảm reliance vào flaky E2E.

### Costs / Risks

Contract governance/versioning cần discipline; semantic mismatch vẫn có thể lọt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu API schema là compatibility surface.

### Middle

Viết integration/contract assertions cho status, fields và errors.

### Senior

Thiết kế backward compatibility, versioning và semantic contracts.

### Technical Lead / Architect

Phân bổ test layer theo risk: unit, integration, contract và ít critical E2E thay vì ép mọi thứ vào một tầng.

## 11. Key takeaway

- Contract tests bảo vệ boundary, không bảo vệ toàn hệ thống.
- Schema compatibility chưa đủ nếu semantics thay đổi.
- Test strategy tốt phân tầng risk thay vì chạy E2E cho mọi case.

# 10. AI Structured Outputs: schema-constrained output vẫn không biến model thành deterministic business logic

## 1. What is it?

Structured Outputs buộc model tạo output theo schema được hỗ trợ, giúp application parse dữ liệu đáng tin cậy hơn về **shape**. Nó không đảm bảo các giá trị bên trong là factually correct hoặc business-valid.

## 2. Why does it exist?

Parsing free-form text bằng regex hoặc “hãy trả JSON” dễ lỗi: thiếu field, sai type, thêm prose. Schema constraint giảm một lớp integration failure giữa probabilistic model và deterministic code.

## 3. How does it work?

```text
User/context
    ↓
   LLM
    ↓ constrained by schema
Structured candidate
    ↓
Deterministic validation / authorization / business rules
    ↓
Application action
```

Schema là transport contract. Authorization, pricing, permission và invariant vẫn thuộc deterministic application.

## 4. Practical implementation

Ví dụ application muốn model phân loại support ticket:

```csharp
public sealed record TicketClassification(
    string Category,
    int Priority,
    string[] SuggestedActions);
```

Sau khi deserialize, application vẫn validate `Category` theo allowlist, clamp/reject priority ngoài business rule và không tự động thực thi `SuggestedActions` nếu chúng gọi privileged tools.

## 5. Real production scenario

AI agent đọc email support và đề xuất refund action. Model trả JSON hoàn toàn đúng schema nhưng hallucinate order ID hoặc refund amount. Workflow an toàn phải lookup order thật, authorize actor, validate amount và yêu cầu deterministic policy/human approval nếu cần.

## 6. Failure scenario & troubleshooting

**Symptom** → không còn JSON parse errors nhưng business incidents vẫn xảy ra.

**Evidence** → output hợp schema nhưng chứa identifier/value không tồn tại.

**Hypothesis** → team nhầm structural validity với semantic correctness.

**Diagnosis** → trace prompt/context/model output/tool inputs và validation path.

**Fix** → deterministic validation, source grounding, constrained tool arguments, approval boundary và evals.

**Verification** → adversarial evals với missing context, prompt injection và conflicting data.

## 7. Common mistakes

Schema-valid = true; cho model quyết định authorization; model tự tạo database ID; tool call không revalidate server-side; log prompt chứa secrets/PII; retry model vô hạn khi validation fail.

## 8. Alternatives

Function/Tool Calling phù hợp khi model chọn action từ tool set; deterministic parser/rules tốt hơn khi problem thực chất là fixed business logic; human review phù hợp high-impact ambiguous decision.

## 9. Trade-offs

### Advantages

Giảm parsing failures, contract rõ hơn, dễ test integration.

### Costs / Risks

Không loại hallucination, prompt injection hay semantic error; schema phức tạp tăng token/maintenance cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt valid JSON với correct answer.

### Middle

Deserialize, validate và handle refusal/error path.

### Senior

Thiết kế grounding, tool boundary, evals, timeout/retry và observability.

### Technical Lead / Architect

Quyết định logic nào model được đề xuất và logic nào bắt buộc deterministic; đặt trust boundary trước privileged side effects.

## 11. Key takeaway

- Structured output đảm bảo shape tốt hơn, không đảm bảo truth.
- Security/business invariants phải được enforce ngoài model.
- AI output nên đi qua validation và trust boundary trước side effect.
