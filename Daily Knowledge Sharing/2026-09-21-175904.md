## 1. C# / .NET Runtime — `IDisposable` không phải cơ chế giải phóng memory

### Mental model
Garbage Collector quản lý **managed memory**; `IDisposable` quản lý **lifetime của resource cần release có tính xác định** như database connection, stream, socket, timer hoặc wrapper quanh native handle. Hai cơ chế liên quan nhưng không thay thế nhau.

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(cancellationToken);
// use connection
```

Khi ra khỏi scope, `DisposeAsync` trả connection về pool. GC có thể chưa chạy trong một thời gian dài, vì vậy chờ GC để “dọn connection” là sai ownership model.

### Điều gì thực sự xảy ra
Object managed trở thành eligible for collection khi không còn reachable. Nhưng resource bên ngoài CLR có lifetime riêng. Finalizer chỉ là safety net cho một số type sở hữu unmanaged resource; nó không đảm bảo release ngay lập tức và làm object cần thêm ít nhất một GC cycle trước khi reclaim hoàn toàn.

### Production failure
Một endpoint quên dispose stream/connection có thể vẫn có memory bình thường nhưng dần cạn connection pool hoặc file handle. Triệu chứng thường là latency tăng, timeout và request queueing thay vì `OutOfMemoryException`.

### Engineering judgment
- Dùng `using` / `await using` khi scope ownership rõ ràng.
- Không implement finalizer nếu class chỉ sở hữu managed disposable object; dispose object đó là đủ.
- `IAsyncDisposable` hữu ích khi cleanup cần asynchronous I/O, nhưng không nên thêm chỉ để “hiện đại”.
- DI container thường dispose service mà nó tạo; đừng tự dispose dependency injected service nếu bạn không sở hữu lifetime của nó.

### Debug checklist
Theo dõi connection-pool exhaustion, open handles, socket count, stream lifetime và disposal path. Câu hỏi quan trọng nhất là: **ai tạo resource và ai chịu trách nhiệm kết thúc lifetime của nó?**

## 2. ASP.NET Core — DI lifetime là correctness boundary, không chỉ configuration

### Mental model
Ba lifetime phổ biến:

- `Singleton`: một instance cho application lifetime.
- `Scoped`: thường một instance cho mỗi HTTP request.
- `Transient`: instance mới mỗi lần resolve.

Sai lifetime có thể biến thành race condition hoặc giữ state lâu hơn dự kiến.

```csharp
builder.Services.AddDbContext<AppDbContext>(); // scoped
builder.Services.AddScoped<OrderService>();
builder.Services.AddSingleton<ProductCatalogCache>();
```

### Captive dependency
Một `Singleton` không nên giữ trực tiếp `Scoped` dependency. Nếu singleton giữ `DbContext`, request boundary biến mất: context sống quá lâu, change tracker tăng, thread-safety bị phá và dữ liệu tracked có thể stale.

Background worker là trường hợp thường gặp. `BackgroundService` là singleton; muốn dùng scoped service, hãy tạo scope cho mỗi unit of work:

```csharp
public sealed class OrderWorker(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = scopeFactory.CreateAsyncScope();
            var processor = scope.ServiceProvider.GetRequiredService<OrderProcessor>();
            await processor.ProcessNextAsync(stoppingToken);
        }
    }
}
```

### Production implications
Lifetime sai có thể gây memory retention, cross-request state leak, concurrency bug hoặc disposed-object error. Đây là lý do lifetime phải được review như một phần của architecture, không phải “đăng ký sao cho resolve được”.

### Engineering judgment
Singleton phù hợp khi service stateless/thread-safe hoặc sở hữu cache/process-wide state có kiểm soát. Scoped phù hợp cho request/unit-of-work state. Transient phù hợp với lightweight stateless component nhưng có thể tạo allocation lớn nếu bị resolve quá nhiều.

## 3. EF Core — Optimistic concurrency bảo vệ lost update, nhưng application phải định nghĩa conflict semantics

### Problem
Hai người cùng đọc Order version 5. A cập nhật status; B cập nhật address. Nếu B ghi sau A mà không có concurrency control, update của A có thể bị overwrite tùy cách update được thực hiện.

SQL Server `rowversion` là một lựa chọn:

```csharp
public sealed class Order
{
    public int Id { get; set; }
    public string Status { get; set; } = default!;

    [Timestamp]
    public byte[] Version { get; set; } = default!;
}
```

EF Core đưa concurrency token vào `WHERE` của `UPDATE`. Nếu row đã thay đổi, affected rows = 0 và `DbUpdateConcurrencyException` được ném.

### Điều quan trọng hơn exception
Framework chỉ phát hiện conflict. Business phải quyết định:

1. Reject và yêu cầu client reload.
2. Client-wins.
3. Store-wins.
4. Merge nếu hai thay đổi độc lập và business cho phép.

Không có chiến lược universal.

### API contract
Có thể expose version dưới dạng ETag và yêu cầu `If-Match`, để optimistic concurrency trở thành contract HTTP thay vì chi tiết persistence.

### Common mistakes
- Catch `DbUpdateConcurrencyException` rồi retry cùng state một cách mù quáng.
- Dùng retry policy cho concurrency conflict như transient network error.
- Update detached entity bằng cách mark toàn entity `Modified`, làm conflict surface rộng và dễ overwrite field không liên quan.
- Không test hai writers thật sự concurrent.

### Engineering judgment
Concurrency control phải bám theo invariant. Nếu operation là `increment inventory reservation`, model command/domain operation thường an toàn hơn generic “update object”.

## 4. SQL — Isolation level là lựa chọn giữa anomaly, blocking và versioning cost

### Mental model
Transaction isolation không đơn giản là “cao hơn thì tốt hơn”. Nó kiểm soát những hiện tượng transaction có thể quan sát và cách database phối hợp concurrent access.

Ví dụ inventory:

```text
T1: read stock = 1
T2: read stock = 1
T1: reserve 1
T2: reserve 1
```

Nếu business invariant là stock không âm, chỉ bọc code trong transaction chưa chắc đủ. Cần hiểu statement semantics, lock/version behavior và update condition.

Một cách thường an toàn hơn là atomic conditional update:

```sql
UPDATE Inventory
SET Available = Available - @quantity
WHERE ProductId = @productId
  AND Available >= @quantity;
```

Sau đó kiểm tra affected rows.

### SQL Server perspective
`READ COMMITTED` có thể dùng locks hoặc row versioning tùy database configuration. Snapshot-based isolation giảm reader/writer blocking nhưng tạo version-store cost và không tự giải quyết mọi write conflict.

### Production trade-off
Isolation mạnh hơn có thể giảm anomaly nhưng tăng blocking/deadlock hoặc serialization failure. Isolation yếu hơn tăng concurrency nhưng đẩy responsibility về application/invariant design.

### Debugging
Khi thấy latency spike, đừng chỉ nhìn query duration. Kiểm tra wait type, blocking chain, lock footprint, transaction duration và execution plan. Query nhanh khi chạy một mình vẫn có thể chậm dưới contention.

## 5. Redis — Cache stampede là concurrency problem, không phải TTL problem

### Scenario
Một product key rất nóng hết hạn lúc 10:00:00. Hàng trăm request cùng thấy cache miss và cùng query database. Cache được tạo để giảm DB load nhưng đúng lúc expiry lại tạo load spike.

Cache-aside cơ bản:

```csharp
var value = await cache.GetStringAsync(key, ct);
if (value is null)
{
    value = await repository.LoadAsync(id, ct);
    await cache.SetStringAsync(key, Serialize(value), options, ct);
}
```

Đoạn này đúng về functional behavior nhưng không có request coalescing.

### Mitigation
Tùy scale có thể dùng:

- per-key in-process lock cho single instance;
- distributed coordination khi thật sự cần;
- stale-while-revalidate;
- probabilistic/early refresh;
- TTL jitter để nhiều key không expire đồng loạt;
- background refresh cho hot data.

### Failure reasoning
Distributed lock không phải miễn phí. Nếu Redis chính là dependency đang lỗi, dựa thêm vào Redis lock có thể làm failure path tệ hơn. Đôi khi stale cache có giới hạn tốt hơn việc cố giữ strong freshness.

### Architecture question
Trước khi cache, phải định nghĩa:

- source of truth là gì;
- stale bao lâu chấp nhận được;
- ai invalidate;
- cache unavailable thì fail-open hay fail-closed;
- database có chịu được fallback load không.

Cache là performance optimization nhưng khi application không có degradation strategy, nó có thể trở thành critical dependency.

## 6. Azure Service Bus — `PeekLock` tạo at-least-once processing; handler phải chịu được duplicate

### Mental model
Với `PeekLock`, consumer nhận message nhưng message chưa bị xóa. Consumer xử lý rồi `Complete`. Nếu process crash sau khi side effect đã commit nhưng trước `Complete`, lock hết hạn và message được delivery lại.

```text
Receive message
→ update database successfully
→ process crashes
→ message lock expires
→ broker redelivers
```

Đây không phải broker bug; đây là failure window tự nhiên của distributed processing.

### Idempotent consumer
Một chiến lược là lưu `MessageId` đã xử lý cùng transaction với business change. Duplicate sau đó được nhận diện và bỏ qua an toàn.

### Lock duration
Nếu processing lâu hơn lock duration, cần lock renewal hoặc thiết kế work nhỏ hơn. Nhưng automatic renewal không sửa được handler bị treo vô hạn; vẫn cần timeout/cancellation và observability.

### Dead-letter queue
Poison message không nên retry mãi. Cần phân biệt:

- transient failure → retry/backoff;
- permanent validation/business failure → dead-letter hoặc explicit handling;
- infrastructure outage → controlled retry để tránh retry storm.

### Metrics cần xem
Active message count, dead-letter count, oldest-message age, delivery count, processing latency, lock-lost rate và handler failure rate thường hữu ích hơn chỉ đếm throughput.

## 7. OpenTelemetry — Trace giúp nối latency xuyên service, nhưng metric mới phù hợp để phát hiện xu hướng

### Three signals
- **Logs**: chi tiết discrete events.
- **Metrics**: số liệu aggregate theo thời gian, tốt cho alert/SLO.
- **Traces**: causal path của một request xuyên components/services.

Một request có thể đi:

```text
API
 ├─ SQL query: 18 ms
 ├─ Redis GET: 3 ms
 └─ Product API: 640 ms
      └─ downstream call: 590 ms
```

Trace giúp trả lời “request này chậm ở đâu?”. Metric giúp trả lời “tỷ lệ request chậm có đang tăng trên toàn hệ thống không?”.

### Instrumentation
Trong .NET, `ActivitySource` là primitive quan trọng cho custom tracing:

```csharp
private static readonly ActivitySource Source = new("Orders.Application");

using var activity = Source.StartActivity("CreateOrder");
activity?.SetTag("order.channel", channel);
```

### Cardinality trap
Không đưa `userId`, `orderId`, raw URL có ID động vào metric labels nếu cardinality lớn. Cardinality explosion làm telemetry đắt và query chậm. High-cardinality identifiers phù hợp hơn trong trace/log context có kiểm soát.

### Engineering judgment
Observability phải xuất phát từ câu hỏi vận hành: latency đến từ đâu, dependency nào lỗi, backlog đang tăng không, deployment nào gây regression? “Có log” không đồng nghĩa hệ thống observable.

## 8. Security — SSRF xảy ra khi server trở thành HTTP client thay cho attacker

### Scenario
API nhận URL từ user để tải ảnh:

```csharp
var bytes = await httpClient.GetByteArrayAsync(request.Url, ct);
```

Nếu không kiểm soát destination, attacker có thể yêu cầu server gọi internal endpoint, metadata service hoặc private network mà attacker không truy cập trực tiếp được.

### Tại sao validate URL string chưa đủ
Các bypass có thể liên quan đến redirects, DNS resolution, alternative IP representation, IPv6, hostname thay đổi resolution hoặc URL parsing differences. Allowlist domain đơn giản nhưng follow redirect sang destination khác vẫn có thể phá policy nếu redirect không được validate.

### Defense layers
- Prefer identifier thay vì arbitrary URL nếu business cho phép.
- Allowlist scheme/host/port.
- Chặn private/link-local/loopback destinations theo network policy phù hợp.
- Revalidate redirect destinations hoặc disable automatic redirect.
- Dùng outbound proxy/egress firewall để enforce ở infrastructure layer.
- Đặt timeout, response-size limit và content validation.
- Không gửi internal credentials tới arbitrary destination.

### Architect-level point
Input validation trong application không nên là defense duy nhất. Egress control tạo boundary độc lập nếu application validation có bug. Security mạnh thường đến từ nhiều lớp có failure mode khác nhau.

## 9. Architecture — Modular Monolith thường là bước trưởng thành trước Microservices

### Problem framing
Microservices giải quyết organizational và operational boundaries ở scale nhất định, nhưng đổi lại mang distributed failure, deployment coordination, observability, network security, data consistency và platform overhead.

Nếu một team nhỏ có domain chưa ổn định, tách service sớm thường biến refactor nội bộ thành network contract migration.

### Modular Monolith
Một process/deployment vẫn có thể có boundary nghiêm túc:

```text
Application
├── Orders
│   ├── Domain
│   ├── Application
│   └── Infrastructure
├── Catalog
└── Payments
```

Module không nên tùy tiện truy cập table/internal type của module khác. Interaction có thể qua public module API hoặc internal events tùy nhu cầu.

### Điều cần tránh
Chỉ chia folder không tạo architecture. Nếu mọi module reference mọi module, dùng chung entity model và query trực tiếp schema của nhau, đó vẫn là tightly coupled monolith.

### Khi nào service extraction có giá trị
- independent scaling thực sự cần;
- ownership/team boundary rõ;
- security/compliance isolation;
- deployment cadence độc lập có giá trị;
- failure isolation cần thiết;
- technology/runtime boundary có business justification.

### Engineering judgment
Thiết kế module tốt tạo **optionality**: có thể giữ monolith nếu đủ tốt hoặc tách một boundary sau này với chi phí thấp hơn. Architecture tốt không tối đa hóa số service; nó tối ưu cost of change và operational fit.

## 10. Performance Engineering — ThreadPool starvation khác CPU saturation

### Symptom
ASP.NET Core latency tăng mạnh, request queueing tăng, nhưng CPU chỉ 40–60%. Một nguyên nhân có thể là ThreadPool starvation do blocking work.

Ví dụ nguy hiểm:

```csharp
public IActionResult Get()
{
    var result = service.GetAsync().Result; // sync-over-async
    return Ok(result);
}
```

Request thread bị block trong lúc chờ asynchronous operation. Dưới tải cao, nhiều worker cùng block; ThreadPool phải inject thread mới dần dần, tạo latency và context-switch overhead.

### CPU saturation
CPU saturation là workload thực sự dùng hết compute capacity, ví dụ serialization lớn, compression, crypto hoặc algorithm CPU-heavy. Thêm async không làm CPU-bound work rẻ hơn.

### Investigation loop
**Symptom:** p99 tăng, throughput giảm.  
**Telemetry:** CPU chưa đầy, ThreadPool queue length tăng, thread count tăng, request duration tăng.  
**Hypothesis:** blocking/sync-over-async.  
**Evidence:** stack trace/profile cho thấy `.Result`, `.Wait()`, synchronous I/O hoặc lock contention.  
**Remediation:** async all the way, loại blocking path, bounded concurrency nếu cần.  
**Verification:** load test lại và so p50/p95/p99, throughput, queue length.

### Senior-level judgment
Đừng tăng ThreadPool minimum như remediation đầu tiên. Nó có thể che triệu chứng và tăng pressure lên database/downstream. Trước tiên phải xác định tại sao threads bị giữ lâu. Capacity tuning chỉ có ý nghĩa sau khi hiểu bottleneck.
