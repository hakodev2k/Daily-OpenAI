# 1. .NET Channels: bounded producer/consumer và backpressure thay vì tạo Task vô hạn

## 1. What is it?

`System.Threading.Channels` cung cấp asynchronous queue giữa producer và consumer trong cùng process. Mental model quan trọng không phải “queue nhanh”, mà là **ranh giới điều tiết tốc độ**: producer có thể tạo work nhanh hơn consumer xử lý, nên hệ thống cần giới hạn lượng work đang chờ.

## 2. Why does it exist?

Nếu mỗi request tạo một `Task.Run` hoặc đẩy item vào unbounded collection, burst traffic có thể biến thành hàng trăm nghìn pending operations. Memory tăng, ThreadPool bị áp lực và downstream bị flood. Bounded channel cho phép hệ thống thể hiện capacity hữu hạn.

## 3. How does it work?

```text
Producer(s)
    |
    v
Bounded Channel --capacity=N--> Consumer(s)
    |
    +-- full -> producer waits / drops according to policy
```

`ChannelWriter.WriteAsync` có thể chờ khi buffer đầy. Đó là backpressure: overload được phản hồi về phía producer thay vì bị giấu trong RAM.

## 4. Practical implementation

```csharp
var channel = Channel.CreateBounded<Job>(
    new BoundedChannelOptions(500)
    {
        FullMode = BoundedChannelFullMode.Wait,
        SingleReader = false,
        SingleWriter = false
    });

await channel.Writer.WriteAsync(job, ct);

await foreach (var item in channel.Reader.ReadAllAsync(stoppingToken))
{
    await ProcessAsync(item, stoppingToken);
}
```

Nếu work phải sống qua process restart, Channel không phải durable queue.

## 5. Real production scenario

API nhận image-processing requests. Version cũ gọi `Task.Run` cho mỗi upload; traffic burst làm memory tăng và dependency bị gọi đồng thời quá mức. Bounded Channel giới hạn backlog và worker concurrency.

## 6. Failure scenario & troubleshooting

**Symptom** → request latency tăng khi channel đầy. **Evidence** → queue depth sát capacity, consumer duration tăng. **Hypothesis** → downstream chậm hơn arrival rate. **Diagnosis** → đo enqueue wait, queue depth, processing rate. **Fix** → giảm producer rate, tăng consumer có kiểm soát hoặc chuyển sang durable broker. **Verification** → load test vượt expected peak và kiểm tra memory vẫn bounded.

## 7. Common mistakes

Dùng unbounded channel mặc định; không propagate cancellation; coi Channel là durable messaging; tăng consumer count mà không kiểm tra database/API capacity; không có metric queue depth.

## 8. Alternatives

`ConcurrentQueue` đơn giản nhưng không có async backpressure. Azure Service Bus phù hợp khi cần durability, cross-process delivery và retry/DLQ.

## 9. Trade-offs

### Advantages

Memory bounded, async coordination rõ ràng, throughput tốt.

### Costs / Risks

Chỉ in-process, mất work khi process chết nếu chưa persist, overload policy phải được thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu producer có thể nhanh hơn consumer.

### Middle

Implement bounded Channel với cancellation.

### Senior

Đo capacity, backpressure và downstream saturation.

### Technical Lead / Architect

Quyết định khi nào in-process queue đủ và khi nào cần durable broker.

## 11. Key takeaway

- Queue không giới hạn chỉ trì hoãn overload.
- Bounded capacity biến overload thành hành vi có thể kiểm soát.
- Durability là boundary quyết định Channel hay message broker.

# 2. REST API Idempotency-Key: chống duplicate command khi client retry

## 1. What is it?

Idempotency key là client-generated identifier đại diện cho một logical command. Server ghi nhận key và kết quả để cùng command retry không tạo side effect lần hai.

## 2. Why does it exist?

Network timeout không cho client biết request đã thất bại hay server đã commit nhưng response bị mất. Nếu client retry `POST /payments`, hệ thống có thể charge hai lần.

## 3. How does it work?

```text
Client -> POST + Idempotency-Key=abc
API -> reserve abc
API -> execute command
API -> store outcome for abc
response lost
Client retries abc
API -> return stored outcome
```

Key cần scope, expiration và request fingerprint để tránh cùng key được dùng cho payload khác.

## 4. Practical implementation

```csharp
app.MapPost("/orders", async (
    CreateOrder request,
    HttpRequest http,
    IdempotencyStore store,
    OrderService service,
    CancellationToken ct) =>
{
    var key = http.Headers["Idempotency-Key"].ToString();
    if (string.IsNullOrWhiteSpace(key))
        return Results.BadRequest();

    return await store.ExecuteOnceAsync(
        key,
        request,
        () => service.CreateAsync(request, ct),
        ct);
});
```

Production implementation phải đảm bảo atomic reservation/result persistence.

## 5. Real production scenario

Mobile app mất mạng ngay sau khi checkout được commit. User bấm lại. Cùng idempotency key trả về order đã tạo thay vì tạo order thứ hai.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate orders dù client gửi cùng key. **Evidence** → hai instances đồng thời không thấy key. **Hypothesis** → check-then-insert không atomic. **Diagnosis** → trace requests và unique constraint/storage transaction. **Fix** → atomic insert/unique key và deterministic conflict handling. **Verification** → gửi concurrent identical requests.

## 7. Common mistakes

Chỉ cache key trong memory; không bind key với payload; TTL quá ngắn; dùng idempotency key thay cho business uniqueness; retry non-idempotent operation không có server support.

## 8. Alternatives

Natural business key/unique constraint có thể đủ. PUT với resource identifier tự nhiên có idempotent semantics tốt hơn trong một số API.

## 9. Trade-offs

### Advantages

Retry an toàn hơn và UX tốt hơn khi network không chắc chắn.

### Costs / Risks

Storage, TTL, atomicity và response replay complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không đồng nghĩa server chưa xử lý.

### Middle

Implement key validation và persistence.

### Senior

Thiết kế race handling, request fingerprint và ambiguous outcomes.

### Technical Lead / Architect

Xác định command nào cần idempotency contract và ownership của deduplication.

## 11. Key takeaway

- Retry an toàn là API contract.
- Idempotency cần atomicity, không chỉ một dictionary.
- Business uniqueness và request idempotency là hai vấn đề khác nhau.

# 3. EF Core projection: giảm data transfer, tracking và materialization cost

## 1. What is it?

Projection dùng `Select` để yêu cầu database trả đúng shape cần dùng thay vì materialize full entity graph.

## 2. Why does it exist?

API list thường chỉ cần vài columns. Load full entity + `Include` có thể tăng network I/O, allocations và change-tracking cost mà không tạo business value.

## 3. How does it work?

LINQ expression được EF Core translate thành SQL projection. Query:

```csharp
db.Orders.Select(x => new OrderListItem(x.Id, x.Number, x.Total))
```

thường trở thành `SELECT Id, Number, Total ...`, thay vì lấy mọi column rồi map trong memory.

## 4. Practical implementation

```csharp
var page = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .OrderByDescending(x => x.CreatedAt)
    .Select(x => new OrderListItem(
        x.Id,
        x.Number,
        x.Total,
        x.Items.Count))
    .Take(50)
    .ToListAsync(ct);
```

Inspect generated SQL khi query phức tạp.

## 5. Real production scenario

Order history endpoint load entity, customer, items và product chỉ để trả 5 fields. Projection giảm payload DB và allocation đáng kể, đồng thời tránh accidental lazy loading.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint vẫn chậm sau projection. **Evidence** → execution plan cho thấy scan lớn hoặc correlated subquery đắt. **Hypothesis** → bottleneck ở access pattern/index, không phải materialization. **Diagnosis** → generated SQL + actual execution plan. **Fix** → sửa query/index/pagination dựa trên evidence. **Verification** → logical reads và p95 giảm.

## 7. Common mistakes

Gọi `ToListAsync` rồi mới `Select`; projection chứa method không translate được; tạo generic repository che mất `IQueryable`; coi `AsNoTracking` là đủ dù vẫn fetch quá nhiều data.

## 8. Alternatives

Full entity phù hợp command/update workflow cần domain behavior. Raw SQL/Dapper hợp với read hot path đặc biệt nhưng tăng maintenance.

## 9. Trade-offs

### Advantages

Ít data transfer, ít allocations, read model rõ.

### Costs / Risks

Nhiều DTO shapes và coupling query với use case.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu entity model không phải response model.

### Middle

Viết projection và inspect SQL.

### Senior

Reason về translation, execution plan và materialization cost.

### Technical Lead / Architect

Cho phép use-case-specific read models thay vì ép mọi read qua generic abstraction.

## 11. Key takeaway

- Fetch đúng data cần dùng.
- Projection không thay thế execution-plan analysis.
- Read model và write model có thể có shape khác nhau.

# 4. SQL Server Snapshot Isolation: giảm reader/writer blocking nhưng không loại bỏ conflict

## 1. What is it?

Snapshot-based isolation cho reader thấy version dữ liệu nhất quán thay vì luôn chờ writer release lock. SQL Server lưu row versions trong version store.

## 2. Why does it exist?

Read-heavy system có thể gặp blocking chain khi long write transaction giữ locks. Row versioning giảm một lớp contention nhưng đổi lấy storage/cleanup cost và semantics khác.

## 3. How does it work?

```text
T1 starts snapshot -> sees version V1
T2 updates row -> V2 and commits
T1 continues seeing V1
new transaction sees V2
```

Snapshot không có nghĩa mọi write conflict biến mất; concurrent writers vẫn cần correctness rules.

## 4. Practical implementation

Trước khi bật isolation, đo blocking và hiểu workload. Application transaction vẫn phải ngắn:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(
    IsolationLevel.Snapshot, ct);

var order = await db.Orders.SingleAsync(x => x.Id == id, ct);
order.Approve();
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

## 5. Real production scenario

Reporting queries block order updates trong giờ cao điểm. Team xác nhận reader/writer contention là root cause, đánh giá tempdb/version-store capacity rồi áp dụng row-versioning strategy thay vì tăng timeout.

## 6. Failure scenario & troubleshooting

**Symptom** → tempdb/version store tăng mạnh. **Evidence** → long transactions giữ old versions. **Hypothesis** → snapshot readers sống quá lâu. **Diagnosis** → transaction duration + version-store metrics. **Fix** → rút ngắn transaction/query, capacity planning. **Verification** → blocking giảm mà version-store growth ổn định.

## 7. Common mistakes

Bật snapshot như “performance switch”; transaction kéo dài; nhầm snapshot với optimistic concurrency token; bỏ qua write-write conflict.

## 8. Alternatives

READ COMMITTED locking đơn giản hơn; Read Committed Snapshot có semantics khác; read replica phù hợp reporting isolation lớn hơn.

## 9. Trade-offs

### Advantages

Giảm reader/writer blocking, snapshot consistency tốt.

### Costs / Risks

Version-store overhead, semantics phức tạp hơn và long transaction trở nên đắt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu isolation quyết định transaction nhìn dữ liệu nào.

### Middle

Nhận diện blocking và transaction scope.

### Senior

Đánh giá locks, version store và anomalies.

### Technical Lead / Architect

Chọn isolation dựa trên correctness + workload, không chỉ latency.

## 11. Key takeaway

- Isolation level là correctness decision trước khi là tuning decision.
- Snapshot giảm một loại blocking nhưng tạo versioning cost.
- Long transaction vẫn là vấn đề.

# 5. MongoDB embedding vs referencing: thiết kế document theo access pattern và growth boundary

## 1. What is it?

Embedding lưu related data trong cùng document; referencing lưu identifier tới document khác. Mental model: MongoDB modeling tối ưu theo **aggregate/access pattern**, không phải sao chép relational normalization máy móc.

## 2. Why does it exist?

Document database cho phép đọc một aggregate trong một operation, nhưng document có growth/lifecycle khác nhau có thể trở thành quá lớn hoặc gây write contention.

## 3. How does it work?

Embedding phù hợp khi child data nhỏ, bounded và thường đọc cùng parent. Referencing phù hợp khi child có lifecycle riêng, cardinality lớn hoặc được truy cập độc lập.

## 4. Practical implementation

```javascript
{
  _id: ObjectId("..."),
  orderNumber: "O-1001",
  shippingAddress: {
    city: "Hanoi",
    country: "VN"
  },
  itemIds: [ObjectId("..."), ObjectId("...")]
}
```

Address snapshot có thể embed vì thuộc order history; product catalog thường reference vì lifecycle độc lập.

## 5. Real production scenario

CMS page embed toàn bộ revision history. Sau vài năm document lớn và mỗi publish rewrite payload lớn. Tách revisions thành collection riêng giải growth boundary trong khi metadata hiện tại vẫn embed.

## 6. Failure scenario & troubleshooting

**Symptom** → writes chậm và document size tăng liên tục. **Evidence** → document growth/cardinality không bounded. **Hypothesis** → embedded collection sai boundary. **Diagnosis** → size distribution + access pattern. **Fix** → reference/archive/bucket strategy. **Verification** → write latency và document growth ổn định.

## 7. Common mistakes

Embed “vì MongoDB là NoSQL”; reference mọi thứ như SQL; duplicate data không có ownership/invalidation rule; index không phù hợp access pattern.

## 8. Alternatives

Relational database phù hợp khi joins/invariants xuyên entities là trung tâm. Cosmos DB có partitioning/cost model khác dù cũng document-oriented.

## 9. Trade-offs

### Advantages

Embedding giảm round trips và có atomicity trong document.

### Costs / Risks

Duplication, growth và update amplification.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu document boundary.

### Middle

Model theo read/write patterns.

### Senior

Đánh giá cardinality, growth, indexes và consistency.

### Technical Lead / Architect

Chọn storage model dựa trên invariants và operational workload, không theo xu hướng.

## 11. Key takeaway

- Embedding là boundary decision.
- Data growth phải được dự đoán.
- Access pattern quan trọng hơn “SQL vs NoSQL” slogan.

# 6. Azure Functions concurrency & scale-out: throughput phải tôn trọng downstream capacity

## 1. What is it?

Azure Functions có thể xử lý nhiều executions đồng thời và scale ra nhiều instances. Tổng concurrency là tích của concurrency mỗi instance và số instances.

## 2. Why does it exist?

Serverless cần hấp thụ workload biến động. Nhưng autoscale không biết database hay third-party API của bạn chịu được bao nhiêu concurrent calls.

## 3. How does it work?

```text
Queue backlog
   -> Function instances scale out
   -> each instance runs concurrent handlers
   -> downstream SQL/API
```

Nếu downstream capacity thấp hơn tổng fan-out, scale-out có thể làm latency/error tăng thay vì giảm backlog.

## 4. Practical implementation

Handler cần cancellation, idempotency và bounded dependency usage:

```csharp
[Function("ProcessOrder")]
public async Task Run(
    [ServiceBusTrigger("orders")] ServiceBusReceivedMessage message,
    CancellationToken ct)
{
    await processor.ProcessIdempotentlyAsync(message, ct);
}
```

Concurrency settings phải được load-test cùng dependency limits.

## 5. Real production scenario

Queue backlog tăng, Functions scale từ 5 lên 40 instances. SQL connection pool/database đạt saturation; retries tăng và backlog còn lớn hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → scale-out tăng cùng lúc DB timeout tăng. **Evidence** → function concurrency, SQL connections, queue age và retry count tương quan. **Hypothesis** → downstream saturation. **Diagnosis** → end-to-end metrics. **Fix** → cap concurrency, optimize dependency, batch hoặc redesign flow. **Verification** → throughput tăng mà dependency latency ổn định.

## 7. Common mistakes

Tin autoscale tự tối ưu toàn hệ thống; retry vô hạn; không idempotent; mỗi invocation mở quá nhiều connections; chỉ monitor invocation count.

## 8. Alternatives

Worker Service/Container Apps cho concurrency control rõ hơn; Service Bus consumers dedicated phù hợp workload ổn định.

## 9. Trade-offs

### Advantages

Elasticity và operational convenience.

### Costs / Risks

Scale amplification, cold-start/cost variability và dependency pressure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu scale-out = nhiều executions hơn.

### Middle

Viết stateless/idempotent handler.

### Senior

Tính total concurrency và dependency budget.

### Technical Lead / Architect

Đặt throughput boundary theo toàn system, không riêng compute tier.

## 11. Key takeaway

- Autoscale không tạo downstream capacity.
- Concurrency là system-wide budget.
- Queue age + dependency saturation quan trọng hơn instance count.

# 7. CQRS trong một database: tách intent mà chưa cần distributed architecture

## 1. What is it?

CQRS tách command (thay đổi state) khỏi query (đọc state). Nó không bắt buộc hai database, Event Sourcing hay Microservices.

## 2. Why does it exist?

Một model chung cho cả writes có business rules và reads có projection phức tạp dễ tạo abstraction khó dùng. Tách intent giúp mỗi side tối ưu theo trách nhiệm.

## 3. How does it work?

```text
POST /orders -> Command -> Handler -> Domain/DbContext
GET /orders  -> Query   -> Handler -> Projection/DbContext
                         ________ same database ________/
```

Transaction boundary vẫn đơn giản vì một database.

## 4. Practical implementation

```csharp
public sealed record GetOrderQuery(Guid Id);

public async Task<OrderDto?> Handle(
    GetOrderQuery query,
    CancellationToken ct) =>
    await db.Orders
        .Where(x => x.Id == query.Id)
        .Select(x => new OrderDto(x.Id, x.Status, x.Total))
        .SingleOrDefaultAsync(ct);
```

MediatR là optional dispatch mechanism, không phải CQRS itself.

## 5. Real production scenario

Approval system có command rules phức tạp nhưng dashboard cần joins/projections khác. CQRS một DB tách code paths mà không thêm synchronization infrastructure.

## 6. Failure scenario & troubleshooting

**Symptom** → hàng trăm handler một dòng, tracing khó, development chậm. **Evidence** → mọi CRUD operation bị ép qua layers không mang value. **Hypothesis** → pattern ceremony vượt complexity thật. **Diagnosis** → review boundaries và change frequency. **Fix** → đơn giản hóa trivial flows. **Verification** → maintainability tốt hơn mà invariants vẫn rõ.

## 7. Common mistakes

CQRS = MediatR; CQRS = two databases; tạo event bus cho CRUD đơn giản; command trả giant read model; generic handlers che business intent.

## 8. Alternatives

Layered application service đơn giản hơn cho CRUD-centric system. Separate read store chỉ đáng khi scale/query requirements thực sự cần.

## 9. Trade-offs

### Advantages

Intent rõ, read/write optimization độc lập trong code.

### Costs / Risks

Nhiều types/handlers và architectural ceremony.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt read intent và state-changing intent.

### Middle

Implement command/query handlers rõ boundary.

### Senior

Nhận biết khi CQRS tạo value hoặc chỉ thêm ceremony.

### Technical Lead / Architect

Chọn mức CQRS tối thiểu cần thiết và chỉ tách stores khi có business/scale justification.

## 11. Key takeaway

- CQRS không đồng nghĩa Event Sourcing.
- Một database thường là bước khởi đầu hợp lý.
- Architecture phải trả tiền cho complexity bằng value thật.

# 8. Akamai/CDN Cache-Control: browser cache, edge cache và invalidation ownership

## 1. What is it?

CDN cache giữ response gần user. Nhưng có ít nhất hai cache boundaries khác nhau: browser và edge. HTTP caching headers định nghĩa freshness/revalidation contract.

## 2. Why does it exist?

Static assets đi từ origin cho mọi request gây latency và origin load. CDN giảm distance và repeated work, nhưng stale content trở thành correctness problem nếu cache policy sai.

## 3. How does it work?

```text
Browser cache
   |
   v
Akamai edge cache
   |
   v
Origin / ASP.NET Core
```

`Cache-Control: public, max-age=300` cho phép freshness 5 phút. Versioned assets có thể dùng TTL dài vì URL đổi khi content đổi.

## 4. Practical implementation

```csharp
app.MapGet("/assets/{hash}/app.js", async context =>
{
    context.Response.Headers.CacheControl =
        "public,max-age=31536000,immutable";
    await ServeAssetAsync(context);
});
```

Dynamic personalized responses cần policy khác và thường không nên public-cache.

## 5. Real production scenario

Marketing site deploy CSS mới nhưng HTML vẫn tham chiếu cùng URL. Edge/browser giữ CSS cũ và layout hỏng. Content-hashed asset URLs loại bỏ nhu cầu purge thường xuyên.

## 6. Failure scenario & troubleshooting

**Symptom** → một vùng/user thấy content cũ. **Evidence** → response `Age`, cache headers, edge status. **Hypothesis** → stale edge/browser layer. **Diagnosis** → compare origin vs edge response và cache key. **Fix** → correct TTL/versioning/purge. **Verification** → request qua affected edge và browser clean/profile.

## 7. Common mistakes

Purge CDN nhưng quên browser cache; cache personalized response; cache key bỏ query/header quan trọng; TTL zero cho mọi thứ; dùng purge như deployment mechanism chính.

## 8. Alternatives

Origin-only đơn giản cho low traffic. Reverse-proxy cache có thể đủ trong private systems. Browser caching vẫn hữu ích dù không dùng CDN.

## 9. Trade-offs

### Advantages

Latency thấp, origin load giảm, global delivery tốt.

### Costs / Risks

Staleness, invalidation complexity và debugging nhiều layers.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser và CDN là hai cache khác nhau.

### Middle

Thiết kế Cache-Control cho static assets.

### Senior

Debug cache key, freshness và stale incidents.

### Technical Lead / Architect

Định nghĩa ownership: ai quyết TTL, versioning, purge và personalized-cache policy.

## 11. Key takeaway

- Cache policy là data-freshness contract.
- Versioned immutable assets đơn giản hơn purge.
- Debug CDN phải xác định chính xác layer đang trả response.

# 9. SonarQube/static analysis: quản lý risk thay vì chạy theo score

## 1. What is it?

Static analysis kiểm tra source/code model mà không cần chạy application để phát hiện bug patterns, vulnerabilities, maintainability issues và duplication.

## 2. Why does it exist?

Code review bằng người không ổn định với repetitive rules. Tool tự động hóa checks để reviewer tập trung vào design, correctness và business behavior.

## 3. How does it work?

```text
commit -> build/analyze -> rules -> issues/quality gate
                         -> developer feedback
```

Signal có giá trị khi rule phù hợp codebase và gate tập trung vào new code/risk, không phải legacy debt vô hạn.

## 4. Practical implementation

CI nên fail vì policy rõ ràng, không vì arbitrary metric. Ví dụ team có thể block new critical security issues và coverage regression trên changed code, đồng thời quản lý legacy findings theo backlog.

## 5. Real production scenario

Legacy solution có hàng nghìn existing smells. Nếu gate yêu cầu “zero issues toàn repo”, team hoặc không thể merge hoặc suppress hàng loạt. New-code policy ngăn debt mới trong khi remediation cũ diễn ra có ưu tiên.

## 6. Failure scenario & troubleshooting

**Symptom** → developers thêm suppressions vô tội vạ. **Evidence** → false positives/noisy rules và gate không phản ánh incident risk. **Hypothesis** → governance sai. **Diagnosis** → sample findings + defect history. **Fix** → tune profile, severity và ownership. **Verification** → critical findings được xử lý, noise giảm.

## 7. Common mistakes

Coverage = quality; cyclomatic complexity threshold áp máy móc; sửa code chỉ để qua score; bỏ qua analyzer vì có false positive; gate legacy debt toàn bộ ngay lập tức.

## 8. Alternatives

Compiler analyzers/Roslyn, security scanners, linters và manual review bổ sung nhau; không tool nào thay thế test/runtime observability.

## 9. Trade-offs

### Advantages

Feedback sớm, consistency và automation.

### Costs / Risks

False positives, metric gaming và CI friction.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu warning là signal cần reasoning.

### Middle

Fix hoặc justify finding bằng evidence.

### Senior

Phân biệt design smell, correctness bug và acceptable exception.

### Technical Lead / Architect

Thiết kế quality gate theo risk và team capacity.

## 11. Key takeaway

- Static analysis hỗ trợ judgment, không thay thế judgment.
- New-code quality thường actionable hơn “clean toàn legacy”.
- Metric bị biến thành target dễ bị game.

# 10. Third-party API resilience: timeout, Circuit Breaker, Bulkhead và retry budget

## 1. What is it?

Resilience policy kiểm soát cách application phản ứng khi external dependency chậm hoặc lỗi. Timeout giới hạn thời gian; retry thử lại lỗi transient; Circuit Breaker ngừng gọi dependency đang fail; Bulkhead giới hạn resource/concurrency bị dependency chiếm.

## 2. Why does it exist?

Một external API chậm có thể giữ request threads/connections, làm pool cạn và biến dependency incident thành outage của chính hệ thống.

## 3. How does it work?

```text
request
 -> total timeout budget
 -> bulkhead/concurrency limit
 -> attempt
    -> transient failure -> bounded retry + jitter
 -> repeated failures -> circuit opens
 -> fallback/fail fast
```

Policies phải phối hợp; retry vô hạn bên trong timeout dài chỉ khuếch đại failure.

## 4. Practical implementation

Với modern .NET resilience handlers, policy nên có budget rõ:

```csharp
builder.Services.AddHttpClient("reviews", client =>
{
    client.BaseAddress = new Uri(config["Reviews:BaseUrl"]!);
})
.AddStandardResilienceHandler();
```

Sau đó tune timeout/retry/circuit thresholds theo API semantics và SLO; không giữ default mà không đo.

## 5. Real production scenario

Product page gọi review provider. Provider p99 tăng từ 300 ms lên 12 s. Nếu mỗi request retry 3 lần, traffic tới provider tăng đúng lúc provider yếu nhất. Bounded timeout + circuit + degraded “reviews unavailable” giữ product page hoạt động.

## 6. Failure scenario & troubleshooting

**Symptom** → local API p99 tăng, connection pool/active requests tăng. **Evidence** → dependency traces chiếm latency, retry count tăng. **Hypothesis** → retry amplification. **Diagnosis** → correlate request traces, attempt count, circuit state. **Fix** → giảm attempts, jitter, timeout budget, bulkhead/fallback. **Verification** → chaos test dependency latency/error.

## 7. Common mistakes

Retry mọi 4xx; retry POST không idempotent; nested retries ở SDK + application; timeout mỗi attempt nhưng không có total budget; circuit breaker dùng như retry mechanism; fallback trả stale/wrong data mà không đánh dấu.

## 8. Alternatives

Async messaging loại dependency khỏi synchronous request path khi business flow cho phép. Cached/stale data phù hợp với non-critical reads. Không gọi dependency cũng là lựa chọn kiến trúc hợp lệ.

## 9. Trade-offs

### Advantages

Failure isolation, predictable latency và graceful degradation.

### Costs / Risks

Policy interaction phức tạp, retries tăng load/cost, fallback có consistency implications.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu network call luôn có thể fail hoặc chậm.

### Middle

Set timeout, cancellation và bounded retry.

### Senior

Thiết kế retry safety, circuit/bulkhead metrics và fallback semantics.

### Technical Lead / Architect

Quyết định dependency có nên nằm trên critical synchronous path và đặt end-to-end latency budget.

## 11. Key takeaway

- Retry tiêu thụ capacity; nó không miễn phí.
- Timeout phải thuộc end-to-end budget.
- Resilience tốt nhất đôi khi là loại dependency khỏi critical path.
