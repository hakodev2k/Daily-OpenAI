# 1. .NET `FrozenDictionary` / `FrozenSet`: tối ưu read-heavy lookup sau giai đoạn build

## 1. What is it?

`FrozenDictionary<TKey,TValue>` và `FrozenSet<T>` là immutable, read-optimized collections trong modern .NET. Mental model quan trọng: trả thêm chi phí ở giai đoạn tạo collection để runtime có thể chọn representation tối ưu cho lookup về sau. Chúng phù hợp khi dữ liệu được xây một lần rồi đọc rất nhiều lần.

## 2. Why does it exist?

`Dictionary` là lựa chọn tổng quát tốt nhưng phải hỗ trợ mutation. Với bảng routing, metadata, mapping hoặc policy được load lúc startup rồi không đổi, khả năng mutation không mang lại giá trị nhưng representation chuyên cho read có thể cải thiện throughput và locality.

## 3. How does it work?

Khi gọi `ToFrozenDictionary()` hoặc `ToFrozenSet()`, collection phân tích keys/comparer và xây cấu trúc nội bộ phục vụ lookup. Vì freeze có cost, lợi ích chỉ xuất hiện nếu số lần lookup đủ lớn để amortize chi phí build.

## 4. Practical implementation

```csharp
using System.Collections.Frozen;

var handlers = new Dictionary<string, Func<Request, Task<Response>>>(
    StringComparer.OrdinalIgnoreCase)
{
    ["create"] = HandleCreateAsync,
    ["cancel"] = HandleCancelAsync
}.ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);

if (handlers.TryGetValue(command, out var handler))
    return await handler(request);
```

Đừng freeze collection mỗi request; hãy freeze tại startup hoặc khi tạo immutable snapshot mới.

## 5. Real production scenario

Một API gateway nội bộ có vài trăm operation mappings được load từ configuration khi startup. Mỗi request thực hiện nhiều lookup nhưng mappings chỉ thay khi deploy. Đây là read-heavy lifecycle phù hợp hơn một dictionary mutable chia sẻ toàn process.

## 6. Failure scenario & troubleshooting

**Symptom:** sau khi chuyển sang Frozen collection, startup chậm hơn nhưng throughput không thay đổi. **Evidence:** collection chỉ có vài entries và lookup không nằm trong hot path. **Hypothesis:** optimization không amortize build cost. **Diagnosis:** benchmark startup và request CPU/allocation. **Fix:** quay lại `Dictionary` nếu đơn giản hơn. **Verification:** benchmark representative workload, không microbenchmark lookup cô lập khỏi lifecycle thật.

## 7. Common mistakes

Freeze collection trong request path; dùng vì tên “Frozen” nghe nhanh hơn; bỏ qua comparer semantics; dùng cho dữ liệu cần mutation liên tục; tối ưu lookup trong khi bottleneck thật là SQL/network.

## 8. Alternatives

`Dictionary` phù hợp general-purpose mutable lookup. `ImmutableDictionary` phù hợp immutable semantics với update tạo version mới. Array/switch có thể đơn giản hơn cho tập nhỏ, cố định.

## 9. Trade-offs

### Advantages

Read path có thể nhanh hơn; immutable state giảm accidental mutation; phù hợp snapshot/configuration lookup.

### Costs / Risks

Build cost cao hơn, update cần rebuild snapshot, lợi ích nhỏ nếu collection ít hoặc lookup không nóng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu collection choice phụ thuộc lifecycle đọc/ghi.

### Middle

Biết build một lần, reuse nhiều lần và giữ comparer đúng.

### Senior

Benchmark end-to-end, xem CPU profile và amortization thay vì chọn theo API name.

### Technical Lead / Architect

Quyết định có cần optimization này hay `Dictionary` đơn giản đã đủ; tránh đưa specialized structure vào public abstraction nếu không có evidence.

## 11. Key takeaway

- Frozen collections phù hợp build-once/read-many.
- Tối ưu collection chỉ đáng giá khi lookup thực sự là hot path.
- Đo lifecycle đầy đủ, không chỉ benchmark một operation.

# 2. ASP.NET Core Endpoint Filters: cross-cutting logic ở endpoint boundary mà không biến middleware thành “god layer”

## 1. What is it?

Endpoint Filter là interception boundary quanh Minimal API handler. Nó cho phép logic như validation, auditing hoặc endpoint-specific policy chạy trước/sau handler mà không áp lên toàn request pipeline.

## 2. Why does it exist?

Middleware rất tốt cho concern toàn ứng dụng như correlation, exception handling hoặc authentication pipeline. Nhưng nếu middleware phải biết DTO/endpoint semantics để validate một nhóm endpoint, boundary đã sai. Filter đưa concern gần endpoint metadata và arguments hơn.

## 3. How does it work?

Request đi qua middleware trước, routing chọn endpoint, sau đó filter chain bao quanh endpoint handler. Filter có thể đọc invocation arguments, short-circuit response hoặc gọi `next`.

## 4. Practical implementation

```csharp
public sealed class ValidateOrderFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var request = context.GetArgument<CreateOrderRequest>(0);
        if (request.Lines.Count == 0)
            return Results.ValidationProblem(new Dictionary<string, string[]>
            {
                ["lines"] = ["At least one line is required."]
            });

        return await next(context);
    }
}

app.MapPost("/orders", CreateOrder)
   .AddEndpointFilter<ValidateOrderFilter>();
```

## 5. Real production scenario

Một nhóm import endpoints cần validate tenant header và payload size semantics riêng. Đưa logic vào global middleware khiến mọi request phải đi qua branch không liên quan; endpoint filter giữ policy gần boundary thực tế.

## 6. Failure scenario & troubleshooting

**Symptom:** cùng validation chạy hai lần và error contract khác nhau. **Evidence:** middleware, filter và application handler đều validate cùng rule. **Hypothesis:** ownership không rõ. **Diagnosis:** trace pipeline và review boundary. **Fix:** transport validation ở endpoint, business invariant ở application/domain. **Verification:** integration tests kiểm tra mỗi failure được map một lần sang `ProblemDetails`/validation response.

## 7. Common mistakes

Đưa business logic vào filter; dùng filter thay authentication/authorization framework; tạo filter global cho concern thực ra thuộc middleware; swallow exception; phụ thuộc argument position mong manh mà không test.

## 8. Alternatives

Middleware cho concern toàn pipeline. MVC filters phù hợp controller stack. Application pipeline behaviors phù hợp use-case boundary. Đôi khi gọi validator trực tiếp trong handler là lựa chọn đơn giản nhất.

## 9. Trade-offs

### Advantages

Scope chính xác hơn middleware, composable và truy cập endpoint arguments/metadata.

### Costs / Risks

Thêm interception layer, execution order cần hiểu rõ và có thể phân tán validation nếu team thiếu convention.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu middleware và endpoint filter chạy ở boundaries khác nhau.

### Middle

Implement filter và integration test short-circuit behavior.

### Senior

Phân loại transport validation, authorization và business invariant đúng layer.

### Technical Lead / Architect

Định nghĩa cross-cutting policy nào thuộc middleware, endpoint, application hoặc domain; ưu tiên direct code khi abstraction không đem lại reuse thực.

## 11. Key takeaway

- Filter hữu ích khi concern cần endpoint context.
- Không dùng filter để giấu business logic.
- Boundary ownership quan trọng hơn việc giảm vài dòng code handler.

# 3. SQL SARGability: khi predicate đúng về logic nhưng phá khả năng index seek

## 1. What is it?

SARGable predicate là điều kiện mà optimizer có thể dùng để tìm range/key trong index hiệu quả. Khi bọc indexed column trong function hoặc implicit conversion, query vẫn đúng về kết quả nhưng có thể buộc engine scan nhiều dữ liệu hơn.

## 2. Why does it exist?

Index được tổ chức theo giá trị key. Nếu query yêu cầu tính `YEAR(CreatedAt)` cho từng row rồi mới so sánh, engine thường không thể trực tiếp seek range của `CreatedAt` như khi dùng boundary timestamps.

## 3. How does it work?

```sql
-- Khó tận dụng index seek hiệu quả
WHERE YEAR(CreatedAt) = 2026

-- SARGable range
WHERE CreatedAt >= '20260101'
  AND CreatedAt <  '20270101'
```

Flow cần reasoning: predicate → execution plan → rows read → I/O → locks/concurrency → latency.

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_CreatedAt ON Orders(CreatedAt);

SELECT Id, CustomerId, Total
FROM Orders
WHERE CreatedAt >= @from
  AND CreatedAt < @to;
```

Với EF Core, inspect generated SQL để bảo đảm LINQ không vô tình tạo function trên column hoặc conversion sai type.

## 5. Real production scenario

Dashboard chạy tốt với 100k orders nhưng chậm khi bảng lên 80 triệu rows. Index đã tồn tại, nên team ban đầu “thêm index” không giúp. Actual plan cho thấy scan vì predicate `CONVERT(date, CreatedAt) = @date`.

## 6. Failure scenario & troubleshooting

**Symptom:** p95 query tăng và logical reads rất lớn. **Evidence:** execution plan cho Index Scan/Table Scan, actual rows read vượt xa rows returned. **Hypothesis:** non-SARGable predicate. **Diagnosis:** inspect predicate, implicit conversions, plan warnings. **Fix:** rewrite thành range hoặc tạo computed/indexed strategy khi business query thực sự cần expression. **Verification:** compare plan, logical reads và duration dưới cùng parameters.

## 7. Common mistakes

Cho rằng “có index” nghĩa query sẽ dùng tốt; function trên indexed column; mismatch `nvarchar`/`varchar`; wildcard prefix `%term`; sửa bằng hint trước khi hiểu access pattern.

## 8. Alternatives

Computed persisted column + index phù hợp expression truy vấn thường xuyên. Full-text search phù hợp text search. Scan có thể đúng nếu query trả phần lớn table.

## 9. Trade-offs

### Advantages

SARGable access thường giảm I/O, CPU và thời gian giữ locks.

### Costs / Risks

Rewrite có thể phức tạp; thêm computed/indexed data tăng write/storage cost; seek không luôn tốt hơn scan nếu selectivity thấp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không phải magic lookup cho mọi predicate.

### Middle

Đọc basic execution plan và viết range predicates.

### Senior

Phân tích cardinality, implicit conversion, logical reads, locking và parameter behavior.

### Technical Lead / Architect

Thiết kế access patterns/index budget theo workload tổng thể, không tối ưu một query bằng cách làm write path đắt vô hạn.

## 11. Key takeaway

- Query đúng logic vẫn có thể sai về access pattern.
- Đọc plan và I/O trước khi thêm index.
- SARGability là interaction giữa predicate và index structure.

# 4. MongoDB Change Streams: CDC-style reaction, resume token và failure recovery

## 1. What is it?

Change Streams cho application subscribe thay đổi trên MongoDB collection/database/cluster dựa trên replication oplog. Consumer nhận change events thay vì polling liên tục.

## 2. Why does it exist?

Search indexing, notifications hoặc projections thường cần phản ứng khi document thay đổi. Polling theo timestamp tạo latency, duplicate windows và query load; Change Streams cung cấp ordered change feed trong phạm vi semantics của MongoDB.

## 3. How does it work?

MongoDB ghi replicated operations; Change Stream cursor chuyển các thay đổi phù hợp pipeline thành events. Mỗi event có resume token để consumer có thể tiếp tục sau disconnect thay vì bắt đầu lại mù quáng.

## 4. Practical implementation

```csharp
var pipeline = new EmptyPipelineDefinition<ChangeStreamDocument<Order>>()
    .Match(x => x.OperationType == ChangeStreamOperationType.Insert ||
                x.OperationType == ChangeStreamOperationType.Update);

using var cursor = await collection.WatchAsync(pipeline, cancellationToken: ct);
await cursor.ForEachAsync(change =>
{
    // persist projection + checkpoint/resume strategy
    Console.WriteLine(change.DocumentKey);
}, ct);
```

Production code cần durable checkpoint/resume-token policy và idempotent side effects.

## 5. Real production scenario

Product catalog ở MongoDB cần đồng bộ projection sang Elasticsearch. Change Stream consumer nhận product changes và update search index. Search là eventual projection, MongoDB vẫn là source of truth.

## 6. Failure scenario & troubleshooting

**Symptom:** search index thiếu updates sau consumer outage dài. **Evidence:** stored resume token không còn usable hoặc checkpoint chỉ nằm trong memory. **Hypothesis:** recovery design không bền vững. **Diagnosis:** kiểm tra oplog retention, token persistence và processing logs. **Fix:** durable checkpoint, idempotent replay và full rebuild fallback. **Verification:** kill consumer, giữ outage qua test window, restart và reconcile source-vs-projection counts/checksums.

## 7. Common mistakes

Không persist resume token; coi delivery là exactly-once; side effect không idempotent; dùng Change Stream thay business event khi consumer cần business intent chứ không phải storage mutation.

## 8. Alternatives

Polling đơn giản hơn ở scale nhỏ. Application-level Outbox/Event Bus diễn đạt business intent rõ hơn. Batch rebuild phù hợp projection có thể tái tạo hoàn toàn.

## 9. Trade-offs

### Advantages

Latency thấp hơn polling, giảm query load và thuận lợi cho projections.

### Costs / Risks

Coupling với storage changes, resume/recovery complexity, oplog retention constraints và eventual consistency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu change feed khác query snapshot.

### Middle

Consume stream, filter events và handle cancellation.

### Senior

Thiết kế durable resume, idempotency, reconciliation và rebuild.

### Technical Lead / Architect

Quyết định consumer cần database change hay business event; xác định source of truth, recovery objective và operational ownership.

## 11. Key takeaway

- Resume token là phần của recovery design, không phải implementation detail.
- Projection consumer phải chịu replay/duplicate.
- Storage change không luôn tương đương business event.

# 5. Bulkhead Pattern: cô lập concurrency để một dependency chậm không kéo sập toàn service

## 1. What is it?

Bulkhead giới hạn tài nguyên/concurrency dành cho một workload hoặc dependency. Mental model lấy từ khoang tàu: một khoang ngập không làm toàn tàu chìm. Trong service, dependency A chậm không nên chiếm hết request slots/connections khiến endpoint không liên quan cũng chết.

## 2. Why does it exist?

Timeout và retry không ngăn hàng nghìn request đồng thời chờ một downstream chậm. Khi shared ThreadPool, connection pool hoặc memory queue bị chiếm hết, partial dependency failure lan thành service-wide failure.

## 3. How does it work?

Mỗi dependency/workload có bounded concurrency/queue. Khi capacity hết, hệ thống reject/degrade sớm thay vì chờ vô hạn. Bulkhead thường phối hợp timeout, Circuit Breaker và rate limiting nhưng mỗi pattern giải failure khác nhau.

## 4. Practical implementation

```csharp
private readonly SemaphoreSlim _inventorySlots = new(50, 50);

public async Task<Inventory> GetInventoryAsync(string sku, CancellationToken ct)
{
    if (!await _inventorySlots.WaitAsync(TimeSpan.FromMilliseconds(50), ct))
        throw new DependencyOverloadedException("Inventory capacity exhausted");

    try { return await inventoryClient.GetAsync(sku, ct); }
    finally { _inventorySlots.Release(); }
}
```

Production nên dùng resilience library/policy có metrics thay vì tự viết mọi primitive.

## 5. Real production scenario

Review service timeout 8 giây trên product page. Không có isolation, requests chờ review chiếm concurrency và làm Product API core data chậm. Bulkhead + fallback cho phép bỏ reviews nhưng vẫn trả product.

## 6. Failure scenario & troubleshooting

**Symptom:** dependency A chậm nhưng toàn API p99 tăng. **Evidence:** traces cho nhiều spans chờ A, connection/concurrency queue tăng. **Hypothesis:** shared resource exhaustion. **Diagnosis:** dependency latency + queue depth + pool metrics. **Fix:** bounded concurrency, timeout budget và graceful fallback. **Verification:** inject latency vào A; endpoint B/core flow vẫn giữ SLO.

## 7. Common mistakes

Queue vô hạn; bulkhead limit không dựa capacity; retry bên trong bulkhead làm slot bị giữ lâu; mọi dependency dùng cùng limit; reject nhưng không có telemetry.

## 8. Alternatives

Circuit Breaker dừng calls khi failure threshold đạt; rate limiter kiểm soát admission; separate service/process tạo isolation mạnh hơn nhưng operational cost cao hơn.

## 9. Trade-offs

### Advantages

Giảm blast radius, bounded resource use và predictable degradation.

### Costs / Risks

Capacity tuning, early rejection và nhiều policies cần monitoring; limit quá thấp tự tạo bottleneck.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slow dependency có thể gây resource exhaustion dù chưa throw error.

### Middle

Implement bounded concurrency và timeout.

### Senior

Đo queue/pool saturation, thiết kế fallback và load-test failure.

### Technical Lead / Architect

Xác định isolation boundaries theo business criticality và quyết định khi process/service separation đáng operational cost.

## 11. Key takeaway

- Bulkhead bảo vệ capacity, không thay timeout/Circuit Breaker.
- Queue vô hạn chỉ trì hoãn failure.
- Test degraded dependency, không chỉ happy-path load.

# 6. Azure Private Endpoint + Private DNS: private connectivity và lỗi DNS khó thấy trong production

## 1. What is it?

Private Endpoint đưa một Azure PaaS resource như Storage/SQL/Key Vault vào VNet thông qua private IP. Private DNS giúp hostname chuẩn của service resolve về private endpoint từ network phù hợp.

## 2. Why does it exist?

Doanh nghiệp muốn traffic tới PaaS không đi qua public endpoint và cần network isolation/egress control. Nhưng private IP không đủ: application thường kết nối bằng hostname, nên DNS trở thành phần của connectivity architecture.

## 3. How does it work?

Client trong VNet query DNS; Private DNS zone/link trả private IP; route đi tới Private Endpoint; service vẫn áp identity/authentication riêng. Network reachability không thay authorization.

## 4. Practical implementation

Ví dụ Storage thường cần private DNS zone tương ứng và VNet link. Trong application, vẫn dùng normal service hostname/SDK và Managed Identity; không hard-code private IP vì TLS/service routing dựa hostname.

```csharp
var credential = new DefaultAzureCredential();
var client = new BlobServiceClient(
    new Uri("https://myaccount.blob.core.windows.net"), credential);
```

## 5. Real production scenario

App Service VNet integration truy cập Key Vault Private Endpoint. Local developer truy cập được public endpoint, nhưng Production timeout vì DNS zone không link đúng VNet. Code và credentials đều đúng; name resolution sai.

## 6. Failure scenario & troubleshooting

**Symptom:** timeout chỉ trong Production. **Evidence:** `nslookup`/DNS diagnostics trả public IP hoặc không resolve; identity logs không có request. **Hypothesis:** traffic chưa tới service. **Diagnosis:** kiểm tra Private DNS zone, VNet link, custom DNS forwarder, routes/NSG. **Fix:** sửa DNS linkage/forwarding. **Verification:** hostname resolve private IP và dependency telemetry xác nhận request thành công.

## 7. Common mistakes

Hard-code private IP; nghĩ Private Endpoint tự cấu hình mọi DNS scenario; bỏ qua on-prem/custom DNS; cho rằng private network thay thế Managed Identity/RBAC; tạo nhiều zones trùng namespace không có governance.

## 8. Alternatives

Public endpoint + firewall/service restrictions đơn giản hơn. Service Endpoints có model khác và không tạo private IP cho resource. Chọn theo security/network requirements thực tế.

## 9. Trade-offs

### Advantages

Private network path, giảm public exposure và phù hợp enterprise network controls.

### Costs / Risks

DNS/network complexity, per-endpoint cost, troubleshooting khó và dependency vào network topology.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hostname phải resolve tới đúng network destination.

### Middle

Biết kiểm tra DNS, connectivity và identity riêng biệt.

### Senior

Troubleshoot VNet integration, custom DNS, routes và platform telemetry.

### Technical Lead / Architect

Quyết định private connectivity có được security requirement biện minh; thiết kế shared DNS ownership và tránh topology không team nào vận hành được.

## 11. Key takeaway

- Private Endpoint là network path; identity vẫn là security boundary riêng.
- DNS là thành phần kiến trúc, không phải chi tiết phụ.
- Troubleshoot theo thứ tự resolution → route → TLS → identity → application.

# 7. Canary Deployment: giảm blast radius bằng progressive delivery và measurable gates

## 1. What is it?

Canary deployment đưa version mới tới một phần nhỏ traffic/instances trước, đo health và business signals rồi tăng dần tỷ lệ nếu ổn. Nó là risk-control strategy, không chỉ là “deploy 10%”.

## 2. Why does it exist?

Tests không mô phỏng hoàn toàn production traffic, data distribution và dependency behavior. Full rollout biến regression nhỏ thành outage toàn user base. Canary giảm blast radius và tạo evidence trước khi mở rộng.

## 3. How does it work?

`commit → build → test → artifact → deploy canary → health validation → observe → promote/rollback`. Gates nên dựa error rate, p95/p99, saturation và business metrics phù hợp, không chỉ process health.

## 4. Practical implementation

Pipeline có thể deploy cùng immutable artifact sang canary slot/ring, route 5%, quan sát 10–20 phút, sau đó tăng 25% → 50% → 100%. Database schema phải backward-compatible trong toàn transition window.

## 5. Real production scenario

Checkout release mới gây timeout chỉ với một payment provider chiếm 8% traffic. Canary 5% cho thấy dependency p99/error tăng trước khi full rollout, giới hạn số user bị ảnh hưởng.

## 6. Failure scenario & troubleshooting

**Symptom:** canary “green” nhưng full rollout fail. **Evidence:** canary volume quá thấp để gặp rare path hoặc metric aggregate che segment lỗi. **Hypothesis:** gate thiếu statistical/business coverage. **Diagnosis:** segment telemetry theo version/provider/tenant. **Fix:** tăng observation window/traffic và thêm targeted synthetic/business metrics. **Verification:** replay representative traffic và validate automated rollback signal.

## 7. Common mistakes

Build artifact mới giữa stages; canary nhưng DB migration breaking; chỉ nhìn average latency; manual promotion không có criteria; rollback code nhưng schema không rollback-compatible.

## 8. Alternatives

Blue-Green đơn giản hơn khi cần switch nhanh; rolling deployment giảm capacity disruption nhưng không tự tạo risk gate; feature flags tách deploy khỏi feature activation.

## 9. Trade-offs

### Advantages

Giảm blast radius, production evidence sớm và rollback trước widespread impact.

### Costs / Risks

Routing/telemetry/pipeline phức tạp, coexistence nhiều versions và cần backward compatibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy success khác production correctness.

### Middle

Thiết lập health checks và version-tagged telemetry.

### Senior

# 8. .NET allocation profiling: từ GC pressure đến bằng chứng trước khi tối ưu memory

## 1. What is it?

Allocation profiling xác định object nào được cấp phát, ở call path nào và với tốc độ bao nhiêu. Mục tiêu không phải “zero allocation”, mà tìm allocation gây GC pressure/latency/cost đáng kể.

## 2. Why does it exist?

Memory tăng có thể là allocation rate cao nhưng objects chết nhanh, retained objects/leak, cache growth hoặc LOH pressure. Nhìn working set một mình không phân biệt được các cơ chế này.

## 3. How does it work?

Bắt đầu bằng metrics: allocation rate, GC heap size, Gen0/1/2 frequency, pause time. Sau đó dùng trace/profiler để tìm allocation stacks/types. Cuối cùng thay đổi code và đo lại cùng workload.

## 4. Practical implementation

```bash
dotnet-counters monitor --process-id 1234 System.Runtime
dotnet-trace collect --process-id 1234
```

Trong code hot path, các nguồn phổ biến gồm LINQ intermediates, string formatting, serialization buffers và materializing collections không cần thiết.

## 5. Real production scenario

API throughput tăng nhưng CPU cũng tăng mạnh dù SQL ổn. Counters cho allocation rate hàng GB/phút và Gen0 rất thường xuyên. Profile chỉ ra logging enrichment tạo dictionaries/strings cho mọi successful request.

## 6. Failure scenario & troubleshooting

**Symptom** → p99 spikes định kỳ. **Measure** → GC pause/allocation correlate spikes. **Localize** → allocation profile. **Hypothesis** → hot logging/serialization path. **Test** → giảm allocation trong branch đó. **Change** → structured source-generated logging/buffer strategy phù hợp. **Measure again** → allocation và p99 giảm dưới cùng load.

## 7. Common mistakes

Tối ưu object nhỏ không nằm hot path; pool object phức tạp gây bugs; gọi mọi memory growth là leak; benchmark Debug build; bỏ qua retained heap.

## 8. Alternatives

Memory dump phù hợp retained-object/leak investigation. CPU profiler phù hợp compute bottleneck. BenchmarkDotNet phù hợp isolated code comparison nhưng không thay production profiling.

## 9. Trade-offs

### Advantages

Evidence-driven optimization và giảm GC/CPU khi allocation thực sự đáng kể.

### Costs / Risks

Profiling overhead, specialized code khó maintain và nguy cơ premature optimization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu allocation và retained memory khác nhau.

### Middle

Đọc counters và basic profiles.

### Senior

Correlate GC, allocation stacks và latency; validate bằng controlled load.

### Technical Lead / Architect

Đặt performance budget và chỉ chấp nhận complexity optimization khi SLO/cost evidence biện minh.

## 11. Key takeaway

- Memory symptom cần phân loại trước khi sửa.
- Allocation rate, retention và LOH là các vấn đề khác nhau.
- Measure → hypothesis → change → measure again.

# 9. CORS trust model: browser enforcement không phải API authorization

## 1. What is it?

CORS là browser security mechanism kiểm soát JavaScript origin nào được phép đọc response cross-origin. Nó không phải cơ chế xác thực hoặc authorization cho API.

## 2. Why does it exist?

Same-Origin Policy ngăn website tùy ý đọc dữ liệu từ origin khác. CORS cho server chủ động nới policy cho trusted web origins trong browser context.

## 3. How does it work?

Browser có thể gửi preflight `OPTIONS` với requested method/headers. Server trả `Access-Control-Allow-*`; browser quyết định có cho JavaScript đọc/gửi request theo policy. Non-browser client không bị CORS ngăn.

## 4. Practical implementation

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("frontend", p => p
        .WithOrigins("https://app.example.com")
        .WithMethods("GET", "POST")
        .WithHeaders("content-type", "authorization"));
});

app.UseCors("frontend");
```

API vẫn phải validate token và authorization policy cho mọi request.

## 5. Real production scenario

SPA ở `app.example.com` gọi API ở `api.example.com`. CORS cho SPA origin nhưng attacker vẫn có thể gọi API bằng curl/server code; access token/RBAC mới quyết định quyền.

## 6. Failure scenario & troubleshooting

**Symptom:** browser báo CORS nhưng API logs cho thấy request 401/500. **Evidence:** DevTools Network và server logs. **Hypothesis:** CORS message chỉ là biểu hiện vì error response thiếu headers hoặc pipeline order sai. **Diagnosis:** inspect preflight, response status và middleware order. **Fix:** sửa auth/error/CORS configuration đúng nguyên nhân. **Verification:** test preflight và actual request từ allowed/disallowed origins.

## 7. Common mistakes

`AllowAnyOrigin` để “fix nhanh”; kết hợp credentials với trust quá rộng; nghĩ CORS chặn Postman/curl; dùng CORS thay authorization; wildcard subdomain không đánh giá takeover risk.

## 8. Alternatives

Same-origin hosting tránh CORS cho SPA/API cùng origin. Reverse proxy/BFF có thể đơn giản hóa browser boundary nhưng vẫn cần authentication/authorization.

## 9. Trade-offs

### Advantages

Cho phép controlled cross-origin browser integration.

### Costs / Risks

Configuration dễ hiểu sai, preflight latency và policy quá rộng tăng browser data-exposure surface.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CORS là browser rule, không phải API security wall.

### Middle

Configure explicit origins và debug preflight.

### Senior

Phân tích credentials, cookies, CSRF interaction và middleware ordering.

### Technical Lead / Architect

Chọn SPA direct API, same-origin reverse proxy hay BFF dựa trust boundary; giữ authorization độc lập với CORS.

## 11. Key takeaway

- CORS không thay authentication/authorization.
- Debug status/preflight/server logs trước khi “mở CORS”.
- Allow-list phải phản ánh browser trust boundary thực.

# 10. React render/memoization: hiểu re-render trước khi rải `useMemo` và `React.memo`

## 1. What is it?

React re-render nghĩa component function được evaluate lại để tạo UI description mới; không đồng nghĩa toàn DOM bị viết lại. Memoization có thể bỏ qua một số computations/renders khi inputs giữ identity phù hợp.

## 2. Why does it exist?

UI tree lớn hoặc computation nặng có thể làm interaction chậm. Nhưng memoization cũng có comparison/cache cost và tăng cognitive complexity; dùng khắp nơi có thể không cải thiện gì.

## 3. How does it work?

State/props/context changes kích hoạt render. React reconcile output mới với trước đó rồi commit thay đổi DOM cần thiết. `React.memo`, `useMemo`, `useCallback` tác động identity/recomputation nhưng không sửa data-flow design xấu.

## 4. Practical implementation

```tsx
const visibleOrders = useMemo(
  () => expensiveFilter(orders, filter),
  [orders, filter]
);

const OrderList = memo(function OrderList({ orders }: Props) {
  return orders.map(x => <OrderRow key={x.id} order={x} />);
});
```

Chỉ thêm memoization sau React Profiler/evidence cho thấy render/computation này đáng kể.

## 5. Real production scenario

Admin dashboard nhận polling data mỗi vài giây. Parent tạo object/callback mới mỗi render khiến expensive child render lại. Profiler xác nhận child chiếm phần lớn commit time; stabilizing props + memoization giảm latency interaction.

## 6. Failure scenario & troubleshooting

**Symptom:** thêm `React.memo` nhưng render count không giảm. **Evidence:** Profiler cho props luôn có new object/function identity. **Hypothesis:** memo boundary bị phá bởi unstable props. **Diagnosis:** inspect prop changes. **Fix:** simplify state/props hoặc stabilize đúng value; không memo mọi thứ. **Verification:** Profiler trước/sau với cùng interaction.

## 7. Common mistakes

Đồng nhất render với DOM mutation; `useMemo` mọi expression; dependency array sai tạo stale value; dùng memo để che global state quá rộng; tối ưu trước khi profile.

## 8. Alternatives

Tách state gần nơi sử dụng, virtualization cho large lists, server pagination và giảm network payload có thể đem lợi ích lớn hơn memoization.

## 9. Trade-offs

### Advantages

Giảm expensive recomputation/render khi boundary ổn định.

### Costs / Risks

Comparison/cache overhead, stale dependency bugs và code khó đọc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu render, reconcile và DOM commit khác nhau.

### Middle

Dùng Profiler và dependency arrays đúng.

### Senior

Tối ưu state boundaries, list rendering và network/data flow trước micro-optimization.

### Technical Lead / Architect

Giữ frontend performance strategy dựa measurement; tránh convention “memo mọi component” tạo complexity không có evidence.

## 11. Key takeaway

- Re-render không đồng nghĩa DOM rewrite.
- Memoization là optimization có cost.
- Profile trước; sửa data-flow/state boundary trước khi rải cache.
