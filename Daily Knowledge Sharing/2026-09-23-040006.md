# 1. .NET `CancellationToken`: cancellation propagation là cooperative contract, không phải kill thread

## 1. What is it?

`CancellationToken` là tín hiệu cooperative cancellation. Caller yêu cầu dừng; code ở downstream quyết định quan sát token và kết thúc ở safe point. Nó không cưỡng bức terminate thread.

## 2. Why does it exist?

Khi client disconnect hoặc request timeout, tiếp tục query database, gọi external API hay xử lý file có thể lãng phí capacity. Cancellation cho phép toàn bộ call chain ngừng công việc không còn giá trị.

## 3. How does it work?

```text
Client disconnect
      |
RequestAborted
      v
Controller -> Service -> EF Core / HttpClient
                  token propagated
```

Token mang trạng thái cancellation và callbacks. API hỗ trợ token thường kiểm tra trạng thái trong quá trình chờ hoặc trước operation tiếp theo và ném `OperationCanceledException`.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    AppDbContext db,
    CancellationToken cancellationToken) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

Trong application service, tiếp tục truyền cùng token xuống EF Core, `HttpClient.SendAsync` và các operation hỗ trợ cancellation.

## 5. Real production scenario

Search endpoint mất 8 giây khi database bận. User đóng tab sau 1 giây. Nếu token không được propagate, SQL query vẫn chạy thêm 7 giây và cạnh tranh connection/CPU với request còn sống.

## 6. Failure scenario & troubleshooting

**Symptom** → request count giảm nhưng database vẫn giữ nhiều queries dài.

**Evidence** → traces kết thúc ở ingress nhưng dependency calls tiếp tục; service methods dùng `CancellationToken.None`.

**Diagnosis** → cancellation chain bị cắt.

**Fix** → propagate token end-to-end; phân biệt timeout token và host shutdown token khi cần.

**Verification** → cancel request trong load test và kiểm tra dependency duration/connection utilization giảm.

## 7. Common mistakes

Tạo token parameter nhưng không truyền tiếp; bắt `Exception` rồi log cancellation như lỗi 500; dùng cancellation sau khi irreversible side effect đã commit mà không hiểu semantics; giả định cancellation chắc chắn dừng ngay lập tức.

## 8. Alternatives

Timeout đặt giới hạn thời gian; cancellation truyền intent. Thực tế thường cần cả hai. Queue-based work phù hợp khi công việc phải hoàn thành dù HTTP client biến mất.

## 9. Trade-offs

### Advantages

Giảm wasted work và cải thiện shutdown/resource utilization.

### Costs / Risks

Cần propagation discipline; partial work phải có semantics rõ; library không hỗ trợ token có thể làm chain mất hiệu lực.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cancellation là cooperative signal.

### Middle

Propagate token qua async call chain và xử lý `OperationCanceledException` đúng ngữ cảnh.

### Senior

Phân biệt client cancellation, timeout, shutdown và irreversible side effects.

### Technical Lead / Architect

Quyết định operation nào gắn lifetime với request và operation nào phải chuyển sang durable background workflow.

## 11. Key takeaway

- Cancellation hiệu quả chỉ khi được propagate end-to-end.
- Cancellation không rollback business side effect đã commit.
- Durable work không nên phụ thuộc lifetime của HTTP request.

# 2. ASP.NET Core rate limiting: bảo vệ capacity thay vì chỉ chặn “user xấu”

## 1. What is it?

Rate limiting giới hạn lượng work được chấp nhận theo một partition như user, tenant, API key hoặc endpoint. Mục tiêu chính là bảo vệ finite capacity và fairness.

## 2. Why does it exist?

Một client hợp lệ cũng có thể tạo burst đủ lớn để làm connection pool, downstream API hoặc CPU saturation. Autoscaling phản ứng chậm và không tạo capacity vô hạn.

## 3. How does it work?

```text
Client -> Rate limiter -> ASP.NET Core -> SQL
             |
          reject 429
```

Algorithms như fixed window, sliding window, token bucket và concurrency limiter kiểm soát các dạng pressure khác nhau.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddFixedWindowLimiter("write-api", o =>
    {
        o.PermitLimit = 100;
        o.Window = TimeSpan.FromMinutes(1);
        o.QueueLimit = 0;
    });
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});

app.UseRateLimiter();
```

Production policy thường partition theo tenant/API identity thay vì một global bucket duy nhất.

## 5. Real production scenario

Bulk integration gửi 20.000 write requests trong vài giây. API pods còn CPU nhưng SQL connection pool cạn. Rate limit ở API boundary giữ admission rate gần capacity downstream.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều 429 dù tổng traffic không cao.

**Evidence** → một enterprise tenant chiếm phần lớn quota global.

**Diagnosis** → partition strategy không phản ánh fairness requirement.

**Fix** → per-tenant limiter, endpoint-specific budgets và response `Retry-After` khi phù hợp.

**Verification** → load test nhiều tenants, quan sát accepted rate và downstream saturation.

## 7. Common mistakes

Dùng IP cho authenticated users sau proxy; coi limiter là DDoS solution hoàn chỉnh; queue quá dài khiến request timeout thay vì reject sớm; đặt limit tùy ý không dựa capacity measurement.

## 8. Alternatives

API gateway/CDN có thể rate-limit trước application. Queue phù hợp với workload có thể xử lý asynchronous. Concurrency limiter tốt hơn request-rate limiter khi cost mỗi request biến thiên lớn.

## 9. Trade-offs

### Advantages

Failure có kiểm soát, fairness tốt hơn, bảo vệ dependencies.

### Costs / Risks

Reject legitimate bursts; distributed limit phức tạp hơn; policy sai gây self-inflicted outage.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 429 và admission control.

### Middle

Cấu hình policy theo endpoint/identity.

### Senior

Chọn algorithm dựa workload và downstream bottleneck.

### Technical Lead / Architect

Định nghĩa capacity budget, fairness và layer chịu trách nhiệm rate limiting.

## 11. Key takeaway

- Rate limiting là capacity-control mechanism.
- Partition key quan trọng ngang limit value.
- Limit phải dựa measurement và downstream capacity.

# 3. EF Core optimistic concurrency: phát hiện lost update bằng concurrency token

## 1. What is it?

Optimistic concurrency cho phép nhiều readers làm việc đồng thời và chỉ phát hiện conflict lúc update. EF Core đưa concurrency token vào `WHERE` của `UPDATE`; nếu không row nào match, nó ném `DbUpdateConcurrencyException`.

## 2. Why does it exist?

Nếu hai users đọc cùng version của record rồi cùng ghi, update sau có thể âm thầm đè update trước: lost update. Giữ database lock suốt thời gian user chỉnh form là không thực tế.

## 3. How does it work?

```text
A reads Version=7
B reads Version=7
A UPDATE ... WHERE Version=7 -> success, Version=8
B UPDATE ... WHERE Version=7 -> 0 rows -> conflict
```

## 4. Practical implementation

```csharp
public class Employee
{
    public int Id { get; set; }
    public string Name { get; set; } = null!;

    [Timestamp]
    public byte[] RowVersion { get; set; } = null!;
}
```

Khi save, client phải gửi version mà nó đã đọc; API không nên query version mới rồi gắn vào entity trước update vì như vậy vô hiệu hóa conflict detection.

## 5. Real production scenario

Manager A sửa department, HR B sửa title trên cùng employee. Business có thể cho phép merge field-level hoặc yêu cầu user reload; điều quan trọng là conflict phải được phát hiện thay vì silently overwrite.

## 6. Failure scenario & troubleshooting

**Symptom** → `DbUpdateConcurrencyException` tăng sau khi UI thêm autosave.

**Evidence** → cùng record bị update từ nhiều requests gần nhau.

**Diagnosis** → conflict thật, không phải transient database error.

**Fix** → xác định policy: client-wins, store-wins, merge hoặc trả HTTP 409 cùng current representation.

**Verification** → integration test hai contexts cùng update một entity.

## 7. Common mistakes

Retry conflict mù quáng; không expose version trong API contract; dùng concurrency token nhưng mapping DTO làm mất token; nhầm optimistic concurrency với database deadlock.

## 8. Alternatives

Pessimistic locking phù hợp với transaction ngắn cần exclusive access. Domain command có thể tránh generic entity update và giảm conflict bằng business-specific operations.

## 9. Trade-offs

### Advantages

Không giữ long-lived locks, phát hiện lost update rõ ràng.

### Costs / Risks

Application phải có conflict resolution semantics; high-contention record có thể retry/conflict nhiều.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hai users có thể ghi đè nhau.

### Middle

Implement `rowversion` và xử lý exception.

### Senior

Thiết kế HTTP 409/merge semantics và test concurrency.

### Technical Lead / Architect

Chọn concurrency strategy theo business invariant và contention pattern.

## 11. Key takeaway

- Concurrency token phát hiện conflict; nó không tự quyết định cách resolve.
- Retry không phải câu trả lời mặc định cho business conflict.
- API contract phải giữ version từ read đến write.

# 4. SQL Server covering index: giảm lookup nhưng không biến mọi query thành “index-only” miễn phí

## 1. What is it?

Covering index là index chứa đủ columns để engine phục vụ query mà không cần lookup thêm vào clustered index/heap. Key columns phục vụ seek/order; `INCLUDE` columns bổ sung dữ liệu output mà không mở rộng key semantics.

## 2. Why does it exist?

Một nonclustered index có thể tìm đúng rows nhanh nhưng phải thực hiện hàng nghìn key lookups để lấy columns còn thiếu. Khi cardinality lớn, random I/O này trở thành bottleneck.

## 3. How does it work?

```text
Query -> Nonclustered Index Seek
                |
         columns đủ? ---- yes -> return
                |
               no
                v
          Key Lookup x N
```

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_Customer_CreatedAt
ON dbo.Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, Total);
```

Cho query lọc `CustomerId`, order `CreatedAt` và select `Status, Total`, index này có thể tránh lookup. Phải xác nhận bằng actual execution plan và logical reads.

## 5. Real production scenario

Order-history API trả 50 rows nhưng optimizer dự đoán/đọc nhiều rows và thực hiện lookup lớn. Sau khi đo plan, include hai output columns giảm logical reads đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → reads giảm nhưng write latency và database size tăng.

**Evidence** → bảng có nhiều wide covering indexes gần giống nhau.

**Diagnosis** → read optimization tạo write amplification.

**Fix** → consolidate indexes, chỉ cover hot queries có evidence, loại unused/redundant indexes.

**Verification** → đo cả read latency lẫn insert/update cost.

## 7. Common mistakes

Include mọi column; bỏ qua key order/selectivity; tạo index cho từng slow query; chỉ nhìn estimated plan; quên index maintenance/storage cost.

## 8. Alternatives

Projection nhỏ hơn có thể loại nhu cầu cover. Query rewrite, keyset pagination hoặc schema/read model riêng đôi khi tốt hơn thêm index.

## 9. Trade-offs

### Advantages

Giảm lookup và I/O cho read path quan trọng.

### Costs / Risks

Storage, write amplification, maintenance và optimizer complexity tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không chỉ giúp `WHERE` mà còn có thể chứa output columns.

### Middle

Đọc plan để thấy Seek + Lookup.

### Senior

Đánh giá logical reads, cardinality và write cost.

### Technical Lead / Architect

Cân bằng workload read/write và tránh index proliferation.

## 11. Key takeaway

- Covering index là workload-specific optimization.
- `INCLUDE` không miễn phí.
- Đo execution plan, I/O và write impact trước/sau thay đổi.

# 5. Redis hot key: một key có thể phá scale-out của distributed cache

## 1. What is it?

Hot key là key nhận lượng request không cân xứng so với phần còn lại. Trong Redis cluster, một key thuộc một hash slot/node, nên thêm nodes không tự chia tải của chính key đó.

## 2. Why does it exist?

Distributed cache scale tốt khi workload phân bố. Nhưng homepage config, global product catalog key hoặc celebrity profile có thể tập trung hàng chục nghìn requests/second vào một node.

## 3. How does it work?

```text
App instances ----+
                  +--> GET global:catalog --> Redis node A
App instances ----+                       node B idle
                                          node C idle
```

Cluster partitions keys, không partition một value của một key.

## 4. Practical implementation

Một giải pháp đơn giản cho data chấp nhận stale ngắn là two-level cache:

```csharp
if (memoryCache.TryGetValue(key, out ProductCatalog? local))
    return local!;

var value = await distributedCache.GetStringAsync(key, cancellationToken);
memoryCache.Set(key, value, TimeSpan.FromSeconds(10));
return value;
```

Local cache giảm fan-in tới Redis nhưng thêm freshness semantics cần kiểm soát.

## 5. Real production scenario

Campaign homepage đọc cùng một navigation/config key ở mọi request. App scale từ 10 lên 80 instances nhưng Redis CPU node chứa key đạt 100%; application scaling làm Redis pressure tệ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis latency tăng dù total key count và memory ổn.

**Evidence** → command/key sampling cho thấy một key chiếm phần lớn operations; một shard CPU cao.

**Diagnosis** → hot-key concentration.

**Fix** → local caching, request coalescing, redesign granularity hoặc replicate/read strategy phù hợp.

**Verification** → đo per-node ops/CPU và cache latency sau change.

## 7. Common mistakes

Chỉ tăng Redis tier; shard key bằng random suffix nhưng làm invalidation khó; cache huge object thành một global key; TTL đồng loạt gây stampede.

## 8. Alternatives

`IMemoryCache` cho data nhỏ/stale-tolerant; CDN cho public HTTP content; database/read replica nếu caching không tạo đủ giá trị.

## 9. Trade-offs

### Advantages

Mitigation đúng có thể giảm network/cache pressure mạnh.

### Costs / Risks

Multi-level cache tăng stale-data và invalidation complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu distributed cache không đồng nghĩa mọi key được phân tán.

### Middle

Đo key access và dùng TTL/local cache hợp lý.

### Senior

Phân tích hot-key, stampede và shard behavior.

### Technical Lead / Architect

Quyết định liệu Redis có nên nằm trên hot path và freshness SLA nào chấp nhận được.

## 11. Key takeaway

- Scale-out Redis không tự chia tải của một hot key.
- Application scale-out có thể tăng pressure lên shared cache.
- Giải pháp phải cân bằng load với freshness/invalidation.

# 6. Saga và compensating transaction: consistency khi business transaction vượt service boundary

## 1. What is it?

Saga biểu diễn business workflow dài thành chuỗi local transactions. Khi bước sau thất bại, hệ thống thực hiện compensating actions cho các bước trước thay vì rollback ACID xuyên nhiều services.

Compensation là business operation mới, không phải database undo thần kỳ.

## 2. Why does it exist?

Giữ distributed transaction qua Order, Payment, Inventory và Shipping làm coupling và availability kém. Network có partial failure nên “tất cả commit cùng lúc” không thực tế trong nhiều architectures.

## 3. How does it work?

```text
Create Order -> Reserve Inventory -> Capture Payment
                      |                  |
                      | success          | fail
                      v                  v
                 Reserved        Release Inventory
                                  Cancel Order
```

State machine/orchestrator hoặc choreography theo events theo dõi progress. Mỗi command/event handler phải tính đến duplicate delivery.

## 4. Practical implementation

```csharp
public enum CheckoutState
{
    Started,
    InventoryReserved,
    PaymentCaptured,
    Completed,
    Compensating,
    Failed
}
```

Persist state cùng correlation ID; transition phải idempotent. Không chỉ giữ state trong memory của worker.

## 5. Real production scenario

Inventory reserve thành công nhưng payment provider timeout. Hệ thống chưa biết payment thực sự failed hay response bị mất. Saga phải query/reconcile payment bằng idempotency key trước khi quyết định release inventory.

## 6. Failure scenario & troubleshooting

**Symptom** → inventory bị release nhưng payment thực tế đã capture.

**Evidence** → HTTP timeout xảy ra sau provider processed request.

**Diagnosis** → application coi timeout là definitive failure.

**Fix** → idempotency key + provider status reconciliation; compensation dựa known state.

**Verification** → chaos test response-loss scenario.

## 7. Common mistakes

Compensation như inverse SQL; không persist workflow state; không idempotent; giả định message ordering tuyệt đối; không có manual recovery path.

## 8. Alternatives

Một local database transaction đơn giản hơn nếu operations có thể nằm cùng consistency boundary. Modular Monolith đôi khi tránh nhu cầu Saga hoàn toàn.

## 9. Trade-offs

### Advantages

Không cần global lock, service autonomy tốt hơn, chịu partial failure tốt hơn nếu thiết kế đúng.

### Costs / Risks

Eventual consistency, state-machine complexity, compensation/reconciliation và observability khó.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu distributed workflow không rollback như một SQL transaction.

### Middle

Implement idempotent steps và persisted state.

### Senior

Xử lý unknown outcome, retries, compensation và reconciliation.

### Technical Lead / Architect

Quyết định business boundary nào thực sự cần distribution; nếu local transaction đủ thì không đưa Saga vào.

## 11. Key takeaway

- Compensation là business action, không phải rollback vật lý.
- Timeout có thể tạo unknown outcome.
- Saga chỉ đáng giá khi transaction thật sự vượt consistency/deployment boundary.

# 7. Azure Managed Identity + Key Vault: bỏ secret khỏi application configuration

## 1. What is it?

Managed Identity cung cấp identity do Azure quản lý cho compute resource. Application dùng identity đó lấy access token từ Microsoft Entra ID rồi truy cập Key Vault hoặc dịch vụ Azure được cấp quyền, thay vì lưu client secret trong config.

## 2. Why does it exist?

Secret trong environment variable vẫn phải được tạo, phân phối, rotate và có nguy cơ leak qua pipeline/log/support dump. Managed Identity loại bỏ credential dài hạn do application sở hữu.

## 3. How does it work?

```text
App Service
   |
   | identity token request
   v
Microsoft Entra ID
   |
   | access token
   v
Key Vault
```

Key Vault authorization vẫn dựa RBAC/access policy; có identity không đồng nghĩa có quyền.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(vaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync(
    "ExternalApiKey",
    cancellationToken: cancellationToken);
```

`DefaultAzureCredential` hỗ trợ developer credential local và Managed Identity trên Azure mà không hard-code secret.

## 5. Real production scenario

App Service cần database credential của legacy vendor và Blob access. Blob dùng Managed Identity trực tiếp; vendor secret còn lại nằm Key Vault. Application identity chỉ có `get` trên secrets cần thiết.

## 6. Failure scenario & troubleshooting

**Symptom** → local chạy được nhưng Production trả 403 từ Key Vault.

**Evidence** → authentication thành công nhưng authorization denied.

**Diagnosis** → Managed Identity chưa được cấp đúng RBAC role/scope hoặc network path bị chặn.

**Fix** → xác minh principal ID, role assignment, vault firewall/private endpoint và token audience.

**Verification** → test từ chính production network/identity.

## 7. Common mistakes

Gán role quá rộng; nhầm authentication với authorization; vẫn copy secret từ Key Vault vào log/config file; gọi Key Vault mỗi request; không thiết kế secret rotation.

## 8. Alternatives

Workload identity trong Kubernetes; service principal + certificate khi Managed Identity không khả dụng; application configuration secret chỉ nên là fallback có kiểm soát.

## 9. Trade-offs

### Advantages

Giảm credential lifecycle, least privilege tốt hơn, audit access tập trung.

### Costs / Risks

Phụ thuộc identity/network configuration; local-vs-cloud behavior cần hiểu; Key Vault không nên trở thành per-request hot dependency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu identity khác secret.

### Middle

Dùng `DefaultAzureCredential`, RBAC và Key Vault SDK.

### Senior

Debug token/RBAC/network và thiết kế caching/rotation.

### Technical Lead / Architect

Chuẩn hóa workload identity, least privilege và secret ownership toàn hệ thống.

## 11. Key takeaway

- Managed Identity loại bỏ application-managed Azure credential.
- Có token không có nghĩa có authorization.
- Key Vault là secret authority, không nên bị gọi như database mỗi request.

# 8. BackgroundService graceful shutdown: drain work đúng cách khi deploy/restart

## 1. What is it?

`BackgroundService` chạy long-lived work trong .NET host. Khi host shutdown, cancellation token báo worker dừng nhận work mới và hoàn tất/abandon work đang xử lý theo bounded shutdown budget.

## 2. Why does it exist?

Deploy, autoscale, VM restart và container termination là bình thường. Nếu process chết giữa message mà settlement/state semantics không rõ, có thể mất hoặc xử lý trùng work.

## 3. How does it work?

```text
Running -> SIGTERM/host stop
             |
             v
Cancellation requested
   | stop intake
   | finish/checkpoint current work
   v
Host exits within shutdown timeout
```

## 4. Practical implementation

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    await foreach (var item in channel.Reader.ReadAllAsync(stoppingToken))
    {
        await ProcessAsync(item, stoppingToken);
    }
}
```

Với durable broker, chỉ complete message sau khi side effect thành công; nếu shutdown trước complete, broker có thể redeliver nên handler cần idempotent.

## 5. Real production scenario

Worker xử lý file 3 phút nhưng container termination grace period 30 giây. Deploy cắt process giữa file. Nếu job state chỉ ở memory, file bị bỏ dở không có recovery.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate jobs tăng ngay sau deployment.

**Evidence** → message lock mất trước completion; shutdown logs cho thấy processing bị cancel.

**Diagnosis** → expected redelivery nhưng handler không idempotent/checkpointed.

**Fix** → stop intake, checkpoint durable progress, tune shutdown/lock renewal và idempotency.

**Verification** → deploy/terminate worker giữa processing trong integration test.

## 7. Common mistakes

Ignore `stoppingToken`; bắt cancellation rồi tiếp tục loop; dùng in-memory queue cho work phải durable; shutdown timeout vô hạn; complete broker message trước business commit.

## 8. Alternatives

Azure Functions phù hợp event-driven workload có managed execution semantics. Durable queue + short handlers thường dễ vận hành hơn giant long-running job.

## 9. Trade-offs

### Advantages

Worker Service cho control tốt và hosting đơn giản.

### Costs / Risks

Team chịu trách nhiệm lifecycle, durability, retries và shutdown behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process restart là normal event.

### Middle

Quan sát cancellation và cleanup đúng.

### Senior

Thiết kế idempotency, checkpoint, broker settlement và termination budget.

### Technical Lead / Architect

Chọn hosting model theo durability/runtime requirements thay vì mặc định `BackgroundService`.

## 11. Key takeaway

- Graceful shutdown phải được thiết kế và test.
- Redelivery sau shutdown có thể là đúng thiết kế.
- Durable work cần durable state, không chỉ memory.

# 9. Playwright E2E: bảo vệ critical user journey mà không biến test suite thành bottleneck

## 1. What is it?

Playwright E2E test điều khiển browser thật để kiểm tra system qua UI, network và backend integration. Giá trị lớn nhất là bảo vệ một số critical journeys mà unit/integration tests riêng lẻ không chứng minh được.

## 2. Why does it exist?

Login component, routing, API auth và backend có thể pass test riêng nhưng kết hợp sai vẫn làm user không checkout được. E2E kiểm tra assembled system.

## 3. How does it work?

```text
Browser -> Frontend -> API -> Database
   ^                         |
   +------ assertions -------+
```

Playwright auto-wait theo actionable state tốt hơn fixed sleep, nhưng test data/environment vẫn phải deterministic.

## 4. Practical implementation

```typescript
test('employee can submit timesheet', async ({ page }) => {
  await page.goto('/timesheets/current');
  await page.getByLabel('Hours').fill('8');
  await page.getByRole('button', { name: 'Submit' }).click();
  await expect(page.getByText('Submitted')).toBeVisible();
});
```

Selector theo role/label vừa ổn định hơn CSS internals vừa khuyến khích accessibility.

## 5. Real production scenario

Backend đổi 401 handling, frontend interceptor redirect loop. Unit tests hai phía đều xanh; E2E login + protected navigation bắt regression trước release.

## 6. Failure scenario & troubleshooting

**Symptom** → CI đỏ ngẫu nhiên, rerun lại xanh.

**Evidence** → tests dùng shared account/data và `waitForTimeout(2000)`.

**Diagnosis** → race + test isolation kém.

**Fix** → deterministic fixtures, unique data, condition-based waits, trace/video chỉ khi failure cần điều tra.

**Verification** → chạy suite lặp nhiều lần/parallel và đo flaky rate.

## 7. Common mistakes

E2E mọi edge case; phụ thuộc shared Production-like data; fixed sleeps; selector theo fragile CSS; mock toàn bộ backend rồi vẫn gọi đó là full E2E.

## 8. Alternatives

Unit tests nhanh cho logic; integration tests tốt cho API/database boundary; contract tests cho service contracts. E2E chỉ nên phủ journeys có business risk cao.

## 9. Trade-offs

### Advantages

Bảo vệ assembled user flow, bắt integration/configuration regressions.

### Costs / Risks

Chậm, flaky nếu data/environment kém, failure localization khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Viết stable selectors/assertions.

### Middle

Quản lý fixtures và debug traces.

### Senior

Chọn coverage theo risk, giảm flakiness và cân bằng test pyramid.

### Technical Lead / Architect

Định nghĩa release gates: journey nào bắt buộc E2E và failure nào block deployment.

## 11. Key takeaway

- E2E bảo vệ journeys, không thay thế unit/integration tests.
- Deterministic data quan trọng hơn thêm retry.
- Coverage nên dựa business risk, không dựa số lượng test.

# 10. RAG retrieval boundary: grounding LLM bằng evidence nhưng vẫn giữ authorization deterministic

## 1. What is it?

Retrieval-Augmented Generation (RAG) lấy các tài liệu/chunks liên quan rồi đưa chúng vào model context để câu trả lời được grounded vào dữ liệu hệ thống. Retrieval cải thiện evidence availability; nó không biến model thành database transaction engine hay authorization authority.

## 2. Why does it exist?

Model không biết private/current enterprise data và có thể hallucinate. Fine-tuning không phải cơ chế phù hợp để cập nhật knowledge liên tục hoặc enforce per-user document access.

## 3. How does it work?

```text
User query
   |
Authorization filter
   |
Embedding / search
   v
Allowed documents
   |
Context assembly
   v
LLM -> structured/cited answer
```

Security boundary phải nằm trước hoặc trong retrieval query. Không retrieve toàn bộ rồi yêu cầu prompt “đừng tiết lộ tài liệu user không được xem”.

## 4. Practical implementation

```csharp
var allowedTenantId = user.TenantId;

var hits = await vectorStore.SearchAsync(
    embedding,
    filter: new SearchFilter
    {
        TenantId = allowedTenantId,
        IsDeleted = false
    },
    cancellationToken);

var answer = await llm.GenerateAsync(
    BuildGroundedPrompt(question, hits),
    cancellationToken);
```

Authorization filter phải xuất phát từ trusted identity/context, không lấy tenant ID do model tự suy luận.

## 5. Real production scenario

Internal assistant trả lời từ HR policies và project docs. Employee A không được phép xem compensation document của department B. Vector similarity có thể xếp tài liệu B rất cao, nên ACL/tenant filtering phải xảy ra ở retrieval layer.

## 6. Failure scenario & troubleshooting

**Symptom** → answer chứa thông tin từ tài liệu ngoài quyền user.

**Evidence** → trace retrieval cho thấy unauthorized chunk đã vào context.

**Diagnosis** → authorization được đặt trong system prompt thay vì search filter/data boundary.

**Fix** → enforce ACL before context construction, test adversarial queries và log document IDs an toàn để audit.

**Verification** → security tests với users/tenants khác nhau phải chứng minh unauthorized docs không bao giờ được retrieved.

## 7. Common mistakes

Coi vector similarity là truth; không filter tenant/ACL; chunk chứa stale/deleted content; prompt injection trong retrieved document; cho model tự quyết định quyền truy cập; không đo retrieval quality riêng khỏi generation quality.

## 8. Alternatives

Keyword/BM25 search tốt cho exact identifiers; hybrid search kết hợp lexical + vector; tool calling trực tiếp vào deterministic API tốt hơn RAG khi cần current transactional facts.

## 9. Trade-offs

### Advantages

Grounding trên enterprise knowledge, cập nhật corpus độc lập model, có thể cung cấp evidence/citations.

### Costs / Risks

Index freshness, retrieval errors, token cost, prompt injection và authorization complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retrieval tìm evidence trước khi model trả lời.

### Middle

Implement chunking/search/context và đánh giá basic relevance.

### Senior

Tách retrieval evaluation khỏi generation evaluation; xử lý ACL, stale index và injection.

### Technical Lead / Architect

Quyết định dữ liệu nào phù hợp RAG, trust boundary ở đâu, logic nào bắt buộc deterministic và auditability cần mức nào.

## 11. Key takeaway

- RAG grounding không thay thế authorization.
- Unauthorized document không được phép vào model context ngay từ đầu.
- Transactional/security-critical logic phải ở deterministic application boundary.
