# 1. .NET `TimeProvider`: làm time-dependent code deterministic và testable

## 1. What is it?

`TimeProvider` là abstraction của .NET cho current time, timestamp và timer. Mental model: business code không nên coi `DateTime.UtcNow` là global dependency vô hình nếu correctness phụ thuộc vào thời gian.

## 2. Why does it exist?

Code kiểm tra expiration, retry window, SLA hoặc scheduled transition thường khó test nếu đọc clock thật. Test phải sleep hoặc phụ thuộc thời điểm chạy, dẫn tới flaky tests.

## 3. How does it work?

Production inject `TimeProvider.System`; test inject fake clock có thể advance có kiểm soát. Dependency vào clock trở nên explicit như database hay HTTP client.

## 4. Practical implementation

```csharp
public sealed class TokenPolicy(TimeProvider clock)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => clock.GetUtcNow() >= expiresAt;
}

builder.Services.AddSingleton(TimeProvider.System);
```

Test có thể dùng fake provider từ testing package phù hợp thay vì `Thread.Sleep`.

## 5. Real production scenario

Approval link hết hạn sau 24 giờ. Test cần kiểm tra boundary 23:59:59 và 24:00:00 mà không chờ thực tế một ngày.

## 6. Failure scenario & troubleshooting

**Symptom** → test expiration thỉnh thoảng fail trên CI. **Evidence** → assertion nằm sát clock boundary. **Diagnosis** → production code đọc clock nhiều lần. **Fix** → inject clock và capture một `now` cho operation. **Verification** → advance fake time deterministic qua boundary.

## 7. Common mistakes

Trộn `DateTime.Now` và UTC; mock static clock bằng wrapper tự chế khắp solution; gọi clock nhiều lần trong cùng business decision; dùng local time làm persistence timestamp.

## 8. Alternatives

Một `IClock` custom vẫn hợp lý ở legacy code, nhưng `TimeProvider` giảm custom abstraction và hỗ trợ timer semantics.

## 9. Trade-offs

### Advantages

Deterministic tests, explicit dependency, ít sleep-based testing.

### Costs / Risks

Thêm dependency vào constructors; abstraction không sửa được domain rule sai về timezone/calendar.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt UTC instant với local presentation time.

### Middle

Inject clock và viết boundary tests không phụ thuộc thời gian thật.

### Senior

Thiết kế expiration/idempotency windows với một captured timestamp và timezone semantics rõ.

### Technical Lead / Architect

Chuẩn hóa time policy giữa services, persistence và tests; quyết định nơi business calendar cần abstraction riêng.

## 11. Key takeaway

- Clock là dependency khi business logic phụ thuộc thời gian.
- Capture time một lần cho một decision quan trọng.
- Test thời gian bằng điều khiển clock, không bằng sleep.

# 2. ASP.NET Core Request Timeouts: deadline boundary thay vì để request treo vô hạn

## 1. What is it?

Request timeout đặt upper bound cho thời gian server dành cho một HTTP request. Nó là deadline policy ở ingress, không phải cơ chế làm downstream nhanh hơn.

## 2. Why does it exist?

Request treo lâu giữ connection, memory và downstream resources. Dưới partial failure, hàng nghìn request chậm có thể tích tụ và gây cascading failure.

## 3. How does it work?

Timeout signal phải propagate qua `CancellationToken` xuống EF Core, `HttpClient` và application services. Nếu code bỏ token, timeout ở middleware chỉ ngừng chờ response chứ work phía dưới vẫn chạy.

## 4. Practical implementation

```csharp
builder.Services.AddRequestTimeouts(o =>
{
    o.AddPolicy("api", TimeSpan.FromSeconds(5));
});

app.UseRequestTimeouts();
app.MapGet("/catalog", Handler).WithRequestTimeout("api");
```

Handler tiếp tục truyền cancellation token xuống dependencies.

## 5. Real production scenario

Product API có SLO 2 giây nhưng review provider đôi lúc treo 30 giây. Request timeout 3 giây cùng dependency timeout ngắn hơn bảo vệ capacity và cho phép fallback.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận timeout nhưng DB query vẫn xuất hiện sau đó. **Evidence** → trace span downstream sống lâu hơn server span. **Diagnosis** → token không propagate. **Fix** → truyền cancellation và đặt dependency deadlines nhỏ hơn overall budget. **Verification** → trace cho thấy child work dừng đúng deadline.

## 7. Common mistakes

Một timeout giống nhau cho mọi endpoint; timeout server ngắn hơn proxy không được thiết kế; retry request timeout không kiểm tra idempotency; không budget thời gian cho downstream.

## 8. Alternatives

Background job + `202 Accepted` phù hợp cho work dài. Streaming phù hợp khi client cần incremental results nhưng vẫn cần cancellation.

## 9. Trade-offs

### Advantages

Bounded resource usage và predictable failure behavior.

### Costs / Risks

Deadline quá ngắn gây false failures; cancellation không rollback external side effects đã commit.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout khác cancellation và khác retry.

### Middle

Cấu hình policy, propagate token, map timeout response hợp lý.

### Senior

Thiết kế end-to-end timeout budget và idempotent retry semantics.

### Technical Lead / Architect

Quyết định synchronous SLA nào hợp lý và workload nào phải chuyển asynchronous.

## 11. Key takeaway

- Timeout là capacity boundary.
- Deadline phải propagate xuống dependency.
- Long-running work thường cần async architecture thay vì timeout cực lớn.

# 3. EF Core `AsNoTrackingWithIdentityResolution`: cân bằng read performance và object identity

## 1. What is it?

`AsNoTrackingWithIdentityResolution` không đưa entities vào `DbContext` change tracker lâu dài nhưng vẫn đảm bảo cùng database identity trong một result materialization được represented bởi cùng object instance.

## 2. Why does it exist?

`AsNoTracking` tốt cho read-only queries, nhưng joins/includes có thể materialize duplicate entity instances. Một số read models cần reference identity nhất quán mà không cần update tracking.

## 3. How does it work?

EF dùng temporary identity map trong lúc enumerate result, rồi bỏ map sau khi query hoàn tất. Nó nằm giữa full tracking và pure no-tracking.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .AsNoTrackingWithIdentityResolution()
    .Include(x => x.Customer)
    .Include(x => x.Lines)
    .Where(x => x.Status == OrderStatus.Open)
    .ToListAsync(ct);
```

Nếu API chỉ cần DTO, projection thường vẫn tốt hơn materialize entity graph.

## 5. Real production scenario

Admin screen tải orders cùng customer references. Pure no-tracking tạo nhiều `Customer` objects giống ID; identity resolution giảm duplication trong graph mà không cần update entities.

## 6. Failure scenario & troubleshooting

**Symptom** → memory vẫn cao dù đã bỏ tracking. **Evidence** → profiler cho thấy graph lớn và Includes nhiều. **Diagnosis** → vấn đề là over-fetching, không phải change tracker. **Fix** → projection, pagination hoặc query shape nhỏ hơn. **Verification** → đo allocations và SQL result rows.

## 7. Common mistakes

Dùng option này như performance magic; trả EF entities trực tiếp qua API; Include toàn graph; nhầm identity resolution với database deduplication.

## 8. Alternatives

`AsTracking` khi cần update; `AsNoTracking` cho simple reads; DTO projection cho API/read model thường rõ và tiết kiệm nhất.

## 9. Trade-offs

### Advantages

Không giữ tracking state nhưng tránh duplicate object identities trong result.

### Costs / Risks

Temporary identity map vẫn có CPU/memory cost; không thay thế query-shape optimization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu tracking phục vụ change detection.

### Middle

Chọn tracking mode theo use case.

### Senior

Đo allocations/result cardinality trước khi tối ưu.

### Technical Lead / Architect

Chuẩn hóa read-model strategy và tránh entity graph trở thành API contract.

## 11. Key takeaway

- Tracking mode phải phản ánh intent.
- Identity resolution giải object duplication, không giải over-fetching.
- Projection thường là baseline tốt cho read APIs.

# 4. PostgreSQL sargability: khi query đúng logic nhưng index không thể giúp

## 1. What is it?

Sargability mô tả khả năng predicate được database dùng để tìm range/index entries hiệu quả thay vì xử lý function trên từng row.

## 2. Why does it exist?

Index tồn tại nhưng query vẫn sequential scan nếu predicate biến indexed column thành expression mà planner không thể map trực tiếp vào index access condition.

## 3. How does it work?

`WHERE created_at >= ... AND created_at < ...` có thể dùng B-tree range scan; `WHERE DATE(created_at)=...` thường buộc evaluate function trên rows trừ khi có matching expression index.

## 4. Practical implementation

Kém:

```sql
SELECT id, total
FROM orders
WHERE DATE(created_at) = DATE '2026-09-17';
```

Tốt hơn:

```sql
SELECT id, total
FROM orders
WHERE created_at >= TIMESTAMP '2026-09-17 00:00:00'
  AND created_at <  TIMESTAMP '2026-09-18 00:00:00';
```

Dùng `EXPLAIN (ANALYZE, BUFFERS)` để kiểm chứng plan và I/O.

## 5. Real production scenario

Dashboard orders theo ngày chạy tốt ở 100k rows nhưng chậm ở 80 triệu rows. Index `created_at` có sẵn nhưng function predicate khiến scan nhiều pages.

## 6. Failure scenario & troubleshooting

**Symptom** → latency và buffer reads tăng theo table size. **Evidence** → execution plan cho Seq Scan. **Hypothesis** → non-sargable predicate. **Fix** → range predicate hoặc expression index nếu semantics bắt buộc. **Verification** → compare actual rows, buffers, execution time.

## 7. Common mistakes

Thêm index mới mà không đọc plan; cast indexed column; wildcard `%term` rồi kỳ vọng B-tree; chỉ nhìn estimated cost mà không chạy representative data.

## 8. Alternatives

Expression index hợp lý khi function predicate là access pattern ổn định. Materialized derived column có thể dùng khi computation phức tạp và write cost chấp nhận được.

## 9. Trade-offs

### Advantages

Sargable queries tận dụng index tốt, giảm I/O và latency.

### Costs / Risks

Rewrite predicate phải giữ đúng timezone/collation semantics; thêm expression index tăng write/storage cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết index không tự động được dùng chỉ vì column đã indexed.

### Middle

Đọc basic plan và viết range predicates.

### Senior

Liên hệ query shape → plan → buffers → locks/latency.

### Technical Lead / Architect

Thiết kế access patterns/schema/index budget dựa trên workload thay vì từng query riêng lẻ.

## 11. Key takeaway

- Có index không đồng nghĩa query dùng được index.
- Đo bằng actual plan và buffers.
- Tối ưu predicate trước khi thêm index mù.

# 5. Domain Event vs Integration Event: cùng là event nhưng khác transaction và ownership boundary

## 1. What is it?

Domain Event biểu diễn điều đã xảy ra có ý nghĩa bên trong domain/bounded context. Integration Event là contract được publish ra ngoài boundary để hệ thống/module khác phản ứng.

## 2. Why does it exist?

Nếu internal domain model trở thành public message contract, thay đổi domain sẽ coupling consumers bên ngoài. Hai loại event tách internal business collaboration khỏi distributed integration contract.

## 3. How does it work?

```text
Order Aggregate
   │ Domain Event
   ▼
Application handlers
   │ transaction boundary
   ▼
Outbox
   │ Integration Event
   ▼
Message Broker → external consumers
```

Domain owns invariants/data. Integration contract phải versionable và chịu duplicate/delay.

## 4. Practical implementation

```csharp
public sealed record OrderConfirmed(Guid OrderId); // domain event
public sealed record OrderConfirmedV1(Guid OrderId, DateTimeOffset OccurredAt); // integration contract
```

Application layer map domain event sang outbox message sau khi transaction state hợp lệ.

## 5. Real production scenario

Orders xác nhận đơn; nội bộ cập nhật loyalty rule bằng domain event. Shipping service cần notification qua broker bằng integration event ổn định, không cần biết entity internals.

## 6. Failure scenario & troubleshooting

**Symptom** → rename domain property phá consumer khác. **Evidence** → broker schema serialize trực tiếp domain entity. **Diagnosis** → boundary leakage. **Fix** → explicit integration DTO/versioning + outbox. **Verification** → contract tests với consumer expectations.

## 7. Common mistakes

Gọi mọi notification là domain event; publish broker message trước DB commit; serialize aggregate; assume event delivery exactly once.

## 8. Alternatives

Direct application-service call đơn giản hơn trong cùng module khi decoupling không có giá trị. REST synchronous phù hợp khi caller cần immediate response.

## 9. Trade-offs

### Advantages

Boundary rõ, internal model tiến hóa độc lập hơn, integration contract có ownership.

### Costs / Risks

Mapping/versioning/outbox tăng code và operational components.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt internal event với external message.

### Middle

Implement handlers và contracts không leak entities.

### Senior

Thiết kế transaction, outbox, versioning, idempotency.

### Technical Lead / Architect

Quyết định bounded-context communication và nơi event-driven complexity thực sự cần thiết.

## 11. Key takeaway

- Domain Event và Integration Event có boundary khác nhau.
- External contract không nên là domain entity serialized.
- Cross-process event cần failure/idempotency/versioning design.

# 6. Bulkhead Pattern: giới hạn blast radius khi một dependency chậm

## 1. What is it?

Bulkhead chia capacity thành các giới hạn độc lập để một workload/dependency không tiêu thụ toàn bộ shared resource. Tên gọi từ vách ngăn tàu: một khoang ngập không làm chìm cả tàu.

## 2. Why does it exist?

Timeout và circuit breaker không ngăn 500 concurrent calls cùng chiếm sockets/threads/connections trước khi timeout. Concurrency limit bảo vệ phần còn lại của hệ thống.

## 3. How does it work?

```text
Requests ─┬─ Reviews dependency [max 20]
          ├─ Pricing dependency [max 50]
          └─ Core DB             [separate pool/budget]
```

Khi Reviews đầy, request liên quan fail/fallback sớm thay vì lấy capacity của Pricing.

## 4. Practical implementation

```csharp
private readonly SemaphoreSlim _gate = new(20);

public async Task<Review?> GetAsync(CancellationToken ct)
{
    if (!await _gate.WaitAsync(TimeSpan.FromMilliseconds(50), ct))
        return null;
    try { return await CallProviderAsync(ct); }
    finally { _gate.Release(); }
}
```

Production nên dùng resilience pipeline/concurrency limiter có telemetry thay vì custom primitive nếu requirements lớn.

## 5. Real production scenario

Review provider chậm 10 giây. Không bulkhead, requests chờ hàng loạt và exhaust outbound capacity. Với limit + fallback, product page vẫn trả core product data.

## 6. Failure scenario & troubleshooting

**Symptom** → bulkhead rejection tăng. **Evidence** → dependency latency tăng trước rejection. **Diagnosis** → downstream saturation. **Fix** → tune capacity theo measured downstream limit, fallback, circuit breaker. **Verification** → core endpoints giữ p95 ổn trong chaos test.

## 7. Common mistakes

Set limit bằng traffic peak thay vì dependency capacity; queue vô hạn trước bulkhead; không metric rejection; share một limiter cho unrelated dependencies.

## 8. Alternatives

Queue-based async processing cho work không cần synchronous response. Rate limiting kiểm soát arrival rate; bulkhead kiểm soát concurrent in-flight capacity.

## 9. Trade-offs

### Advantages

Failure isolation và predictable resource ceiling.

### Costs / Risks

Reject work sớm; cần sizing, fallback và observability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu giới hạn concurrency khác timeout.

### Middle

Implement bounded concurrency và cancellation.

### Senior

Tune bằng latency/capacity evidence và thiết kế fallback.

### Technical Lead / Architect

Phân bổ resource budgets theo criticality và dependency ownership.

## 11. Key takeaway

- Bulkhead bảo vệ capacity trước cascading failure.
- Queue vô hạn không phải resilience.
- Limit phải dựa trên downstream capacity và business priority.

# 7. Azure Event Grid delivery: event notification, retry và idempotent consumer

## 1. What is it?

Azure Event Grid là event-routing service cho notification-style events từ publishers tới subscribers. Nó phù hợp cho “something happened” fan-out, không phải mặc định thay Azure Service Bus cho mọi messaging workflow.

## 2. Why does it exist?

Publishers không nên biết mọi subscriber endpoint. Event Grid cung cấp routing/filtering và managed delivery, giảm point-to-point integration.

## 3. How does it work?

```text
Blob/CMS/App → Event Grid Topic → filters → Webhook/Function/Service
```

Delivery có retry và consumer phải chịu duplicate. Failure lâu có thể đi tới dead-letter destination khi cấu hình.

## 4. Practical implementation

Consumer phải dedupe theo event ID:

```csharp
if (await inbox.ExistsAsync(evt.Id, ct)) return;
await inbox.StoreAsync(evt.Id, ct);
await handler.HandleAsync(evt, ct);
```

Identity nên dùng Managed Identity khi subscriber/publisher path hỗ trợ; private networking và monitoring phải được thiết kế theo architecture thực tế.

## 5. Real production scenario

Blob upload hoàn tất phát event để Azure Function tạo thumbnail và metadata. Upload API không cần synchronous chờ image processing.

## 6. Failure scenario & troubleshooting

**Symptom** → thumbnail tạo hai lần. **Evidence** → cùng event ID được delivery nhiều lần. **Diagnosis** → consumer không idempotent. **Fix** → durable dedupe/business idempotency. **Verification** → replay event và assert một logical result; monitor delivery failures/dead-letter.

## 7. Common mistakes

Assume exactly-once; dùng Event Grid cho ordered command workflow; không dead-letter; không monitor subscriber latency; event schema không version.

## 8. Alternatives

Azure Service Bus phù hợp commands, queueing, sessions/order và richer broker semantics. Storage Queue đơn giản/rẻ cho basic work queue. Direct HTTP đơn giản nếu chỉ một synchronous consumer.

## 9. Trade-offs

### Advantages

Managed fan-out, filtering, Azure event integration, giảm publisher coupling.

### Costs / Risks

Eventual delivery, duplicate handling, schema governance và operational monitoring vẫn cần.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event notification khác command queue.

### Middle

Tạo subscriber idempotent và xử lý retry.

### Senior

Thiết kế dead-letter, schema evolution, observability, identity/networking.

### Technical Lead / Architect

Chọn Event Grid vs Service Bus dựa trên semantics, không dựa trên việc cả hai đều “gửi message”.

## 11. Key takeaway

- Event Grid mạnh cho event routing/fan-out.
- Consumer vẫn phải idempotent.
- Chọn messaging service theo delivery semantics và workflow needs.

# 8. `dotnet-counters`: điều tra CPU, GC, ThreadPool bằng runtime metrics trước khi đoán

## 1. What is it?

`dotnet-counters` là diagnostic tool đọc runtime/application counters từ process .NET đang chạy. Nó cho quick evidence về CPU, allocations, GC, exception rate và ThreadPool behavior.

## 2. Why does it exist?

Production incident thường bắt đầu bằng triệu chứng mơ hồ: CPU cao, latency tăng, memory tăng. Full dump/profiler có cost; counters là bước triage nhẹ hơn để chọn hypothesis đúng.

## 3. How does it work?

Runtime phát counters; tool subscribe và hiển thị theo thời gian. Counter không cho stack trace/root cause trực tiếp nhưng giúp localize subsystem cần điều tra sâu.

## 4. Practical implementation

```bash
dotnet-counters monitor --process-id 1234 System.Runtime
```

Quan sát CPU Usage, GC Heap Size, Allocation Rate, Gen collections, ThreadPool Thread Count/Queue Length và exception count theo phiên bản runtime/tool.

## 5. Real production scenario

API p99 tăng sau deployment. CPU 40%, ThreadPool queue tăng liên tục và thread count ramp-up: evidence hướng investigation vào blocking/starvation thay vì SQL index tuning.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng. **Measure** → heap size + allocation rate. **Localize** → heap tăng sau GC hay chỉ allocation burst? **Hypothesis** → retention nếu live heap tăng. **Test** → capture dump. **Change** → fix owner/reference. **Measure again** → compare same load profile.

## 7. Common mistakes

Đọc một snapshot; coi correlation là causation; chạy profiler nặng ngay; không correlate counters với traffic/deployment; nhìn average latency thay p95/p99.

## 8. Alternatives

Application Insights/Azure Monitor cho historical production metrics; `dotnet-trace` cho event traces; `dotnet-dump` cho heap; profiler cho CPU/allocation stacks.

## 9. Trade-offs

### Advantages

Nhanh, tương đối nhẹ, tốt cho triage.

### Costs / Risks

Không cung cấp root cause stack trực tiếp; cần baseline và context để diễn giải.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết CPU/memory/thread là signals khác nhau.

### Middle

Capture counters và correlate với incident timeline.

### Senior

Chuyển signal thành hypothesis rồi chọn trace/dump/profiler đúng.

### Technical Lead / Architect

Chuẩn hóa production diagnostic playbook và telemetry baseline trước incident.

## 11. Key takeaway

- Measure trước khi sửa.
- Counters giúp chọn hướng điều tra, không tự nói root cause.
- So sánh với baseline và cùng workload.

# 9. React stale closure: async UI state và bug từ snapshot semantics

## 1. What is it?

Function component render tạo một snapshot của props/state. Callback closure giữ values từ render nơi nó được tạo. Stale closure xảy ra khi async callback sau đó dùng snapshot cũ trong khi UI đã render state mới.

## 2. Why does it exist?

JavaScript closures là lexical; React không mutate local variable của render cũ. Mental model này giúp component predictable nhưng async timers/events dễ giữ state lỗi thời.

## 3. How does it work?

Render A tạo callback với `count=1`; state update tạo Render B với `count=2`; callback từ A vẫn thấy `1` nếu nó chạy sau đó.

## 4. Practical implementation

Dễ lỗi:

```tsx
setTimeout(() => setCount(count + 1), 1000);
```

An toàn hơn khi update phụ thuộc previous state:

```tsx
setTimeout(() => setCount(c => c + 1), 1000);
```

Effects cần dependency list đúng; `useRef` chỉ nên dùng khi cần mutable value không trigger render.

## 5. Real production scenario

Search UI debounce request. User đổi filter nhanh; callback cũ dùng filter snapshot trước và overwrite result mới, tạo UI “nhảy ngược”.

## 6. Failure scenario & troubleshooting

**Symptom** → UI chỉ sai khi thao tác nhanh. **Evidence** → React DevTools/network timeline cho thấy callbacks từ render cũ. **Diagnosis** → stale closure/race. **Fix** → functional update, correct dependencies, AbortController/request identity. **Verification** → deterministic rapid-interaction test.

## 7. Common mistakes

Tắt exhaustive-deps lint để hết warning; dùng ref cho mọi state; assume `setState` mutate variable hiện tại; không cancel stale network requests.

## 8. Alternatives

State machine/store có thể làm complex async flows explicit hơn nhưng không cần cho component đơn giản. Server-state libraries giúp request caching/races nhưng vẫn cần hiểu React semantics.

## 9. Trade-offs

### Advantages

Snapshot model giúp render reasoning rõ và tránh hidden mutation.

### Costs / Risks

Async callbacks đòi hỏi dependency/cancellation discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mỗi render có state snapshot riêng.

### Middle

Dùng functional updates, effect dependencies và cancellation.

### Senior

Phân biệt stale closure với request race/cache issue và thiết kế async state rõ.

### Technical Lead / Architect

Chọn state-management complexity theo application needs, không che mental model bằng library.

## 11. Key takeaway

- Closure giữ snapshot của render tạo ra nó.
- Functional updates giải dependency vào previous state.
- Async requests cần cancellation/ordering strategy.

# 10. Mutation Testing: đo khả năng test suite phát hiện lỗi thay vì chỉ đo coverage

## 1. What is it?

Mutation testing cố tình thay đổi code nhỏ — đảo điều kiện, đổi toán tử, bỏ statement — rồi chạy tests. Nếu tests vẫn xanh, mutant “survives”, cho thấy test suite có thể execute code nhưng không bảo vệ behavior đó.

## 2. Why does it exist?

Line coverage trả lời “dòng này đã chạy chưa?”, không trả lời “test có fail nếu logic sai không?”. Mutation testing đánh giá sensitivity của tests với realistic code changes.

## 3. How does it work?

```text
Production code
   │ mutate
   ├─ `>` → `>=`
   ├─ `true` → `false`
   └─ remove call
        │
        ▼
Run tests → killed / survived
```

Survived mutant là signal để xem test thiếu assertion hay mutation tương đương về semantics.

## 4. Practical implementation

Ví dụ rule:

```csharp
public bool CanApprove(decimal amount) => amount <= 10_000m;
```

Nếu mutation `<=` thành `<` vẫn pass, test suite thiếu boundary case `10_000`.

Trong .NET có thể dùng mutation-testing tooling phù hợp trong CI theo scope; không nhất thiết chạy toàn solution ở mọi commit.

## 5. Real production scenario

Payroll approval service có 92% coverage nhưng bug boundary amount lọt production. Mutation testing trên domain rules phát hiện nhiều survived mutants ở comparison boundaries dù coverage rất cao.

## 6. Failure scenario & troubleshooting

**Symptom** → mutation job quá chậm và team bỏ dùng. **Evidence** → hàng nghìn mutants ở generated/trivial code. **Diagnosis** → scope sai. **Fix** → tập trung critical domain modules, incremental/nightly strategy. **Verification** → runtime phù hợp và surviving mutants tạo actionable tests.

## 7. Common mistakes

Chạy mutation score như KPI; cố kill mọi equivalent mutant; dùng nó thay integration/E2E tests; test implementation details chỉ để tăng score.

## 8. Alternatives

Coverage vẫn hữu ích để tìm unexecuted areas. Property-based testing mạnh cho invariant/input spaces. Integration tests bảo vệ wiring/infrastructure mà unit mutation testing không thấy.

## 9. Trade-offs

### Advantages

Đánh giá test effectiveness sâu hơn coverage và lộ weak assertions/boundary gaps.

### Costs / Risks

Compute time cao, noise nếu scope kém, dễ bị game hóa thành metric.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu test phải fail khi behavior quan trọng bị phá.

### Middle

Viết boundary/assertion tests để kill meaningful mutants.

### Senior

Phân tích surviving mutants theo risk, không theo score tuyệt đối.

### Technical Lead / Architect

Áp dụng mutation testing cho critical business logic với CI strategy có cost hợp lý; không biến metric thành mục tiêu.

## 11. Key takeaway

- Coverage đo execution; mutation testing đo khả năng phát hiện thay đổi sai.
- Dùng theo risk, không chạy mù toàn codebase.
- Survived mutant là câu hỏi về test quality, không tự động là bug.
