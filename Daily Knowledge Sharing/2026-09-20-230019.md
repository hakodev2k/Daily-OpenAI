# 1. C# `Channel<T>`: bounded backpressure thay vì để producer phá memory

## 1. What is it?

`Channel<T>` là abstraction producer-consumer bất đồng bộ trong .NET. Mental model quan trọng không phải “queue nhanh”, mà là một boundary giữa tốc độ tạo công việc và tốc độ xử lý công việc. Với bounded channel, capacity trở thành cơ chế backpressure: producer phải chờ, bỏ item hoặc áp policy khi consumer không theo kịp.

## 2. Why does it exist?

Một `ConcurrentQueue<T>` cho phép enqueue rất nhanh nhưng không tự giải quyết câu hỏi “nếu producer tạo 50.000 items/giây còn consumer xử lý 5.000 thì sao?”. Queue tăng vô hạn cho tới khi GC pressure và memory trở thành bottleneck. `Channel<T>` cung cấp asynchronous waiting và bounded capacity để biến overload thành behavior có kiểm soát.

## 3. How does it work?

```text
Producer(s)
    │ WriteAsync
    ▼
Bounded Channel [ capacity = 1000 ]
    │ ReadAllAsync
    ▼
Consumer(s)
```

Khi buffer đầy, `BoundedChannelFullMode.Wait` làm `WriteAsync` chờ cho tới khi có chỗ. Điều này truyền áp lực ngược về producer thay vì âm thầm tích backlog trong RAM.

## 4. Practical implementation

```csharp
var channel = Channel.CreateBounded<WorkItem>(new BoundedChannelOptions(1000)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = false
});

async Task ProduceAsync(WorkItem item, CancellationToken ct)
{
    await channel.Writer.WriteAsync(item, ct);
}

async Task ConsumeAsync(CancellationToken ct)
{
    await foreach (var item in channel.Reader.ReadAllAsync(ct))
    {
        await ProcessAsync(item, ct);
    }
}
```

Nếu work không được phép mất khi process restart, in-memory channel không đủ; cần durable queue như Azure Service Bus.

## 5. Real production scenario

Một API nhận yêu cầu resize ảnh. Nếu request handler đẩy mọi ảnh vào unbounded in-memory queue rồi trả `202`, traffic spike có thể giữ hàng GB buffers. Bounded channel giới hạn số work items trong process; API có thể chờ ngắn, reject với `429/503`, hoặc chuyển sang durable broker tùy reliability requirement.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng liên tục, GC frequency tăng, latency consumer kéo dài. **Evidence** → queue depth tăng nhanh hơn throughput, producer rate cao hơn consumer rate. **Hypothesis** → không có backpressure. **Diagnosis** → đo arrival rate, processing rate, queue depth và item memory footprint. **Fix** → bounded capacity, concurrency hợp lý hoặc durable broker. **Verification** → load test vượt capacity; memory phải ổn định và overload behavior phải predictable.

## 7. Common mistakes

Dùng unbounded channel cho workload không giới hạn; coi channel là durable queue; tăng số consumer vô hạn rồi làm nghẽn database; không complete writer khi shutdown; bỏ qua cancellation; chọn `DropOldest`/`DropWrite` mà business không chấp nhận mất dữ liệu.

## 8. Alternatives

`ConcurrentQueue<T>` phù hợp khi tự quản signaling/capacity. `BlockingCollection<T>` hữu ích cho synchronous producer-consumer cũ. Azure Service Bus, RabbitMQ hoặc Kafka phù hợp khi cần durability, cross-process delivery và recovery.

## 9. Trade-offs

### Advantages

API async tự nhiên, backpressure rõ, throughput cao và tránh polling.

### Costs / Risks

In-memory state mất khi process chết; capacity/concurrency cần tuning; overload policy trở thành business decision.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu producer và consumer có thể chạy khác tốc độ, queue không thể tăng vô hạn miễn phí.

### Middle

Implement bounded channel, cancellation và graceful completion.

### Senior

Đo throughput, memory footprint, downstream capacity và chọn overload policy đúng.

### Technical Lead / Architect

Quyết định in-memory channel có đủ reliability hay cần durable messaging; xác định ai chịu backpressure và điều gì xảy ra khi hệ thống overload.

## 11. Key takeaway

- Queue không giới hạn chỉ trì hoãn overload thành memory failure.
- Bounded capacity là một reliability control, không chỉ optimization.
- Nếu work phải sống qua process restart, dùng durable broker.

# 2. ASP.NET Core middleware ordering: security và error handling phụ thuộc vị trí trong pipeline

## 1. What is it?

ASP.NET Core middleware tạo pipeline tuần tự cho mỗi HTTP request. Mỗi middleware có thể xử lý request trước `next()`, gọi middleware tiếp theo, rồi xử lý response khi stack unwind. Thứ tự đăng ký vì vậy là runtime behavior, không phải formatting preference.

## 2. Why does it exist?

Cross-cutting concerns như exception handling, forwarded headers, authentication, authorization, CORS và rate limiting cần áp dụng ở những boundary khác nhau. Nếu order sai, middleware có thể không thấy endpoint metadata, không thấy authenticated principal hoặc không bắt được exception phía sau.

## 3. How does it work?

```text
Request
  ↓
Exception Handler
  ↓
Routing
  ↓
Authentication
  ↓
Authorization
  ↓
Endpoint
  ↑
Response unwinds through pipeline
```

Một middleware chỉ bắt được exception phát sinh sau khi nó gọi `next()`. Authorization phải chạy sau khi routing đã xác định endpoint metadata và sau authentication đã tạo `User`.

## 4. Practical implementation

```csharp
var app = builder.Build();

app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();
app.Run();
```

Order cụ thể còn phụ thuộc middleware đang dùng; không copy pipeline từ project khác mà không hiểu dependency giữa stages.

## 5. Real production scenario

Một API dùng policy-based authorization theo endpoint. Sau refactor, `UseAuthorization()` được đặt trước authentication. Request có valid JWT vẫn bị `401/403` vì authorization chạy khi `HttpContext.User` chưa được populate đúng như dự kiến.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint hoạt động local nhưng Production redirect sai scheme hoặc auth thất bại sau reverse proxy. **Evidence** → request headers cho thấy proxy gửi `X-Forwarded-Proto`, nhưng application xử lý HTTPS redirect trước forwarded headers. **Hypothesis** → pipeline order sai. **Diagnosis** → trace middleware stages và inspect effective scheme/user/endpoint. **Fix** → đặt forwarded-header processing đúng boundary và giới hạn trusted proxies. **Verification** → integration test qua proxy-like headers và auth flows.

## 7. Common mistakes

Đăng ký exception handler quá muộn; authorization trước authentication; custom middleware đọc endpoint metadata trước routing; CORS order sai; middleware tự swallow exception; tin forwarded headers từ mọi source.

## 8. Alternatives

Endpoint filters hoặc MVC filters phù hợp concern chỉ thuộc endpoint/MVC. Middleware phù hợp concern ở HTTP pipeline rộng hơn. Không nên biến mọi logic thành middleware.

## 9. Trade-offs

### Advantages

Composable, centralized cross-cutting behavior và request lifecycle rõ.

### Costs / Risks

Order-sensitive; middleware global có blast radius lớn; custom middleware khó test nếu chứa business logic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu pipeline chạy theo thứ tự đăng ký và response đi ngược lại.

### Middle

Biết đặt authentication/authorization/error handling đúng vị trí và viết integration tests.

### Senior

Debug proxy, security và endpoint metadata issues bằng request lifecycle thay vì thử đổi order ngẫu nhiên.

### Technical Lead / Architect

Quy định pipeline conventions, trust boundaries và nơi cross-cutting concern nên sống: middleware, filter hay application layer.

## 11. Key takeaway

- Middleware order là executable architecture.
- Authentication và authorization là hai stages khác nhau.
- Test pipeline bằng integration tests, đặc biệt khi có reverse proxy.

# 3. EF Core projection: giảm data transfer và tracking thay vì `Include` cả object graph

## 1. What is it?

Projection là việc dùng `Select` để yêu cầu EF Core chỉ materialize shape cần cho use case thay vì load full entities. Mental model: query model nên phản ánh dữ liệu consumer cần, không phản ánh toàn bộ domain object graph.

## 2. Why does it exist?

`Include` thuận tiện nhưng dễ lấy quá nhiều columns/rows, tạo entity tracking không cần thiết và nhân dữ liệu khi join nhiều collections. Read endpoint thường chỉ cần DTO nhỏ.

## 3. How does it work?

LINQ expression được EF Core translate thành SQL projection. Nếu chỉ chọn `Id`, `Name` và aggregate, SQL có thể chỉ lấy những fields đó thay vì materialize entity + navigation collections.

```text
LINQ Select
   ↓ translation
SELECT Id, Name, COUNT(...)
   ↓
DTO materialization
```

## 4. Practical implementation

```csharp
var products = await db.Products
    .AsNoTracking()
    .Where(p => p.IsActive)
    .OrderBy(p => p.Name)
    .Select(p => new ProductListItem(
        p.Id,
        p.Name,
        p.Reviews.Count(r => r.IsPublished)))
    .Take(50)
    .ToListAsync(ct);
```

Inspect generated SQL bằng logging hoặc `ToQueryString()` trong debugging để xác nhận translation.

## 5. Real production scenario

Product listing chỉ hiển thị tên, thumbnail URL và review count. Implementation cũ `Include(p => p.Reviews).Include(p => p.Images)` rồi map in-memory. Projection giảm network payload từ database, allocations và tracking overhead.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint list có latency và allocation cao. **Evidence** → SQL trả hàng chục columns và nhiều joined rows cho mỗi product. **Hypothesis** → over-fetching/object graph materialization. **Diagnosis** → compare generated SQL, row count, logical reads và allocation profile. **Fix** → projection theo response shape. **Verification** → đo lại SQL duration, transferred rows và API p95.

## 7. Common mistakes

`ToListAsync()` trước rồi `Select` in-memory; projection gọi method không translate được; trả entity trực tiếp từ API; thêm `Include` dù projection đã navigation đúng; dùng `AsNoTracking` nhưng vẫn over-fetch rất nhiều dữ liệu.

## 8. Alternatives

Full entity loading đúng khi use case cần mutate aggregate. Raw SQL/Dapper hữu ích cho read query cực tối ưu hoặc SQL phức tạp. `Include` vẫn phù hợp khi thực sự cần related entities.

## 9. Trade-offs

### Advantages

Ít I/O, ít allocation, DTO contract rõ và tránh accidental tracking.

### Costs / Risks

Nhiều query-specific projections; thay đổi response shape có thể cần sửa query; expression phức tạp có thể tạo SQL khó đọc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu query không cần load toàn entity nếu chỉ đọc vài fields.

### Middle

Viết projection DTO và kiểm tra generated SQL.

### Senior

Đánh giá SQL shape, row multiplication, I/O và materialization cost.

### Technical Lead / Architect

Chọn read model strategy phù hợp thay vì ép domain entity phục vụ mọi API query.

## 11. Key takeaway

- Read endpoint nên query đúng shape nó cần.
- `AsNoTracking` không chữa over-fetching.
- Generated SQL và measurements mới xác nhận optimization thực sự.

# 4. Elasticsearch synchronization lag: search index là read model eventual-consistent, không phải source of truth

## 1. What is it?

Trong kiến trúc phổ biến, SQL/MongoDB giữ transactional truth còn Elasticsearch giữ search-optimized copy. Synchronization lag là khoảng thời gian giữa lúc source thay đổi và lúc search index phản ánh thay đổi đó.

## 2. Why does it exist?

Elasticsearch tối ưu full-text search, scoring và aggregations nhưng không nên gánh transactional invariants của order/payment. Khi tách source of truth và search read model, consistency tức thời bị đổi lấy search capability và scale độc lập.

## 3. How does it work?

```text
Primary DB
   │ commit
   ▼
Outbox / CDC / Event
   ▼
Indexer
   ▼
Elasticsearch
   ▼ refresh
Search API
```

Lag có thể xuất hiện ở event publishing, queue backlog, indexing failure hoặc Elasticsearch refresh/cluster pressure.

## 4. Practical implementation

Một event nên mang stable entity ID và version. Indexer upsert theo ID; version giúp bỏ event cũ đến muộn.

```csharp
if (message.Version <= currentIndexedVersion)
    return;

await elastic.IndexAsync(new ProductSearchDocument
{
    Id = message.ProductId,
    Version = message.Version,
    Name = message.Name,
    IsActive = message.IsActive
}, x => x.Index("products-read"), ct);
```

Production cần idempotency, retry và DLQ/replay strategy.

## 5. Real production scenario

Editor publish product mới trong CMS/commerce database. Product detail theo ID có thể thấy ngay từ source, nhưng search results xuất hiện sau vài giây. UX phải xác định freshness expectation thay vì giả vờ strong consistency.

## 6. Failure scenario & troubleshooting

**Symptom** → product đã update 30 phút nhưng search vẫn cũ. **Evidence** → DB version mới, queue backlog tăng, indexed version cũ. **Hypothesis** → indexer stalled hoặc poison message. **Diagnosis** → trace entity ID xuyên outbox, broker, consumer và index. **Fix** → phục hồi consumer, replay idempotently, xử lý mapping/schema failure. **Verification** → lag metric trở lại SLO và version index khớp source.

## 7. Common mistakes

Dual-write DB + Elasticsearch trực tiếp trong request; không có replay path; không đo indexing lag; dùng search index làm authority cho authorization/inventory; event không có version; mapping breaking change update trực tiếp production index.

## 8. Alternatives

Database full-text search đủ cho workload đơn giản. CDC giảm application publishing logic nhưng tăng infra complexity. Scheduled bulk sync đơn giản hơn nếu freshness theo phút/giờ là chấp nhận được.

## 9. Trade-offs

### Advantages

Search capability mạnh, read scale độc lập, query model tối ưu riêng.

### Costs / Risks

Eventual consistency, duplicate storage, synchronization pipeline và operational burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Elasticsearch thường là copy phục vụ search, không phải transactional truth.

### Middle

Implement idempotent indexing và basic retry/replay.

### Senior

Theo dõi lag, ordering/versioning, mapping failures và zero-downtime reindex.

### Technical Lead / Architect

Xác định freshness SLO, source ownership và liệu nhu cầu search có đủ để biện minh thêm distributed component hay không.

## 11. Key takeaway

- Search freshness phải được định nghĩa và đo.
- Đồng bộ search là distributed-systems problem.
- Authorization, payment và inventory correctness không nên dựa vào stale search index.

# 5. Hexagonal Architecture: bảo vệ business boundary mà không biến solution thành ceremony

## 1. What is it?

Hexagonal Architecture tổ chức hệ thống quanh application/domain core và các ports mô tả capability mà core cần hoặc cung cấp. Adapters kết nối ports với HTTP, SQL, Azure Service Bus hoặc third-party APIs. Mục tiêu là dependency direction và change isolation, không phải số lượng projects.

## 2. Why does it exist?

Nếu business logic gọi trực tiếp EF, HTTP SDK, queue SDK và framework types ở mọi nơi, thay đổi infrastructure lan xuyên codebase và tests khó cô lập. Ports tạo boundary tại nơi volatility hoặc business ownership thực sự cần tách.

## 3. How does it work?

```text
HTTP Adapter ──> Application Core ──> IInventoryPort
                       ▲                    │
                       │                    ▼
                 Domain Rules        Commerce API Adapter

SQL Adapter implements persistence port
```

Core định nghĩa abstraction cần thiết; infrastructure phụ thuộc vào core để implement nó. Data ownership và transaction boundary vẫn phải explicit.

## 4. Practical implementation

```csharp
public interface IInventoryGateway
{
    Task<Availability> GetAsync(string sku, CancellationToken ct);
}

public sealed class ReserveProductHandler(IInventoryGateway inventory)
{
    public async Task<Result> Handle(string sku, CancellationToken ct)
    {
        var availability = await inventory.GetAsync(sku, ct);
        return availability.InStock ? Result.Ok() : Result.Conflict();
    }
}
```

Adapter có thể dùng typed `HttpClient`; domain/application không cần biết SDK cụ thể.

## 5. Real production scenario

E-commerce platform đổi review provider. Nếu provider SDK nằm sau domain-specific `IReviewReader`, thay đổi chủ yếu ở adapter. Nếu abstraction chỉ mirror toàn bộ SDK cũ, boundary không tạo giá trị.

## 6. Failure scenario & troubleshooting

**Symptom** → một feature đơn giản cần sửa 8 projects và 12 interfaces. **Evidence** → mỗi class đều có interface dù không có boundary/alternative. **Hypothesis** → architecture biến thành ceremony. **Diagnosis** → trace dependency và change frequency. **Fix** → giữ ports ở meaningful external/domain boundaries, collapse trivial layers. **Verification** → feature flow ngắn hơn nhưng core vẫn không phụ thuộc volatile infrastructure.

## 7. Common mistakes

Một interface cho mọi class; repository generic che mất EF capabilities; domain model anemic; coi folder layout là architecture; mapping DTO qua quá nhiều layers; không xác định transaction/data ownership.

## 8. Alternatives

Layered Architecture đơn giản hơn cho CRUD app. Modular Monolith tập trung module boundaries. Vertical Slice Architecture tối ưu feature cohesion. Các approach có thể kết hợp có chọn lọc.

## 9. Trade-offs

### Advantages

Dependency isolation, testability và replaceable external adapters ở meaningful boundaries.

### Costs / Risks

Nhiều abstractions/mapping; onboarding cost; overengineering nếu domain đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu business logic không nên phụ thuộc tùy tiện vào mọi infrastructure detail.

### Middle

Implement port/adapter tại external boundary và tests cho application behavior.

### Senior

Phân biệt useful abstraction với pass-through interface, đồng thời giữ transaction semantics rõ.

### Technical Lead / Architect

Quyết định boundary dựa trên business complexity, volatility và team ownership; có thể chọn architecture đơn giản hơn nếu không có pressure.

## 11. Key takeaway

- Hexagonal Architecture là dependency discipline, không phải project template.
- Port nên diễn đạt domain capability, không mirror vendor SDK.
- Abstraction không có change boundary thường chỉ tăng cognitive load.

# 6. Background jobs trên nhiều instance: duplicate execution, idempotency và ownership

## 1. What is it?

Khi ASP.NET Core/App Service scale thành nhiều instances, mỗi instance chạy cùng `BackgroundService`. Một timer “mỗi 5 phút” vì vậy có thể chạy N lần song song. Đây không phải bug của framework mà là hệ quả của replicated process model.

## 2. Why does it exist?

Horizontal scaling nhân application process để tăng availability/capacity. In-process scheduler không tự biết rằng business muốn singleton execution toàn cluster.

## 3. How does it work?

```text
App instance A ─ timer ─┐
App instance B ─ timer ─┼─> same business job
App instance C ─ timer ─┘
```

Có ba hướng chính: làm operation idempotent để duplicate vô hại; dùng distributed coordination/lock; hoặc chuyển scheduling sang service có ownership rõ như Azure Functions/queue-based worker.

## 4. Practical implementation

Một pattern mạnh hơn lock đơn thuần là claim work atomically:

```sql
UPDATE JobItems
SET Status = 'Processing', WorkerId = @worker
OUTPUT inserted.*
WHERE Id = (
    SELECT TOP (1) Id
    FROM JobItems WITH (UPDLOCK, READPAST, ROWLOCK)
    WHERE Status = 'Pending'
    ORDER BY CreatedAt
);
```

Cần thiết kế lease/recovery nếu worker chết sau khi claim.

## 5. Real production scenario

Scheduled invoice reminder chạy trên 4 App Service instances. Nếu mỗi instance query “reminders due” và gửi email, customer nhận 4 emails. Unique business key + atomic claim/idempotency record ngăn duplicate side effect.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate notifications chỉ xuất hiện sau scale-out. **Evidence** → logs cùng job timestamp nhưng khác instance ID. **Hypothesis** → in-process scheduler chạy trên mọi replica. **Diagnosis** → correlate execution ID, instance ID và side-effect key. **Fix** → idempotent processing + centralized scheduling/claim. **Verification** → scale lên nhiều replicas và chạy concurrency test; mỗi business key chỉ có một committed effect.

## 7. Common mistakes

Giả định timer là singleton; distributed lock không có expiry; lock hết hạn khi job vẫn chạy; side effect không idempotent; không xử lý process crash; giữ job dài trong web process dù deployment/recycle thường xuyên.

## 8. Alternatives

Azure Functions Timer Trigger phù hợp scheduled cloud work nhưng vẫn cần hiểu retries/duplicates. Service Bus queue tốt cho distributed work. Dedicated Worker Service cho ownership rõ. Database scheduler có thể đủ với enterprise legacy system.

## 9. Trade-offs

### Advantages

In-process background work rất đơn giản cho best-effort/local tasks.

### Costs / Risks

Scale-out, restart và deployment làm lifecycle khó dự đoán; singleton coordination thêm distributed-state complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mỗi application instance có background service riêng.

### Middle

Implement cancellation, graceful shutdown và idempotency key.

### Senior

Thiết kế claim/lease/recovery, duplicate handling và telemetry.

### Technical Lead / Architect

Quyết định scheduler ownership và liệu job có nên sống trong web app hay tách thành durable worker/service.

## 11. Key takeaway

- Horizontal scale nhân timer cùng với process.
- Idempotency bảo vệ side effect tốt hơn niềm tin vào “exactly once”.
- Job quan trọng cần explicit ownership, recovery và observability.

# 7. Azure Front Door: global edge routing, health probing và failure boundary trước origin

## 1. What is it?

Azure Front Door là global Layer-7 edge service đặt trước web origins để route HTTP(S), terminate TLS, health-probe origins và có thể kết hợp caching/WAF tùy cấu hình. Mental model: nó là edge entry point và traffic-management boundary, không phải application server.

## 2. Why does it exist?

Một global application có users ở nhiều regions và nhiều origins. Client không nên tự biết region nào healthy. Edge layer cung cấp stable hostname, routing policy và failover trước application infrastructure.

## 3. How does it work?

```text
Client
  ↓ HTTPS
Azure Front Door edge
  ├─ health/routing ─> Origin A
  └─ failover ───────> Origin B
                         ↓
                    ASP.NET Core
```

Health probe chỉ phản ánh signal bạn expose. Nếu probe quá nông, traffic vẫn đi vào origin không phục vụ được; nếu probe phụ thuộc mọi downstream service, transient dependency failure có thể loại toàn bộ origins.

## 4. Practical implementation

ASP.NET Core nên hiểu forwarded scheme/host theo trusted proxy configuration và có readiness endpoint nhẹ:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<CoreReadinessCheck>("core-ready");

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = x => x.Name == "core-ready"
});
```

Front Door origin probe trỏ vào endpoint có semantics phù hợp. Identity/secrets nên dùng Managed Identity/Key Vault ở origin khi applicable; edge không thay thế application authorization.

## 5. Real production scenario

Marketing/e-commerce site chạy West Europe và Southeast Asia. Front Door route users tới healthy origin gần/ưu tiên hơn. Khi một region deploy lỗi và readiness fail, traffic chuyển sang region còn lại nếu data/session architecture cho phép.

## 6. Failure scenario & troubleshooting

**Symptom** → origin trực tiếp healthy nhưng users nhận `503` từ edge. **Evidence** → Front Door health reports origin unhealthy; probe path trả `401` hoặc host-header mismatch. **Hypothesis** → probe configuration sai. **Diagnosis** → kiểm tra origin health, DNS, TLS certificate, host header và probe response. **Fix** → sửa health endpoint/routing configuration. **Verification** → origin chuyển healthy và synthetic request qua public hostname thành công.

## 7. Common mistakes

Coi Front Door là magic multi-region HA dù database chỉ có single-region dependency; cache dynamic/private response sai; health probe quá sâu; không giới hạn direct-origin access khi threat model yêu cầu; quên WAF/routing logs.

## 8. Alternatives

Application Gateway tập trung regional Layer-7 routing. Load Balancer là Layer-4. CDN-only service phù hợp static acceleration. Không cần Front Door nếu application single-region nhỏ và global routing không mang giá trị.

## 9. Trade-offs

### Advantages

Global entry point, failover/routing, edge security/caching capabilities và giảm coupling client với origins.

### Costs / Risks

Thêm configuration/cost/observability layer; failover chỉ hiệu quả nếu downstream state cũng resilient; caching/routing sai có blast radius lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Front Door nằm trước origin và route HTTP traffic.

### Middle

Configure health endpoint, headers và test public route.

### Senior

Debug TLS/DNS/probe/caching failures và thiết kế origin protection.

### Technical Lead / Architect

Đánh giá end-to-end multi-region architecture, data consistency, failover objective và operational cost thay vì chỉ thêm edge service.

## 11. Key takeaway

- Edge HA không thể bù cho stateful dependency single point of failure.
- Health probe semantics quyết định routing behavior.
- Luôn troubleshoot từ client → edge → origin → dependencies.

# 8. SLO và error budget: biến reliability thành quyết định engineering có thể đo

## 1. What is it?

SLI là measurement về service behavior; SLO là target cho SLI trong một window; error budget là phần failure được phép trong target đó. Ví dụ availability SLO 99.9% nghĩa là 0.1% request/window có thể nằm ngoài objective theo định nghĩa cụ thể.

## 2. Why does it exist?

“Service phải luôn ổn định” không phải requirement có thể engineering. Không có target, team tranh luận reliability bằng cảm giác và có xu hướng hoặc under-invest hoặc over-engineer.

## 3. How does it work?

Ví dụ SLI request-based:

```text
good requests / eligible requests
```

Nếu SLO = 99.9% trong 30 ngày, error budget = 0.1%. Burn rate cho biết budget đang bị tiêu nhanh đến mức nào. p95 latency có thể là SLI khác nhưng phải định nghĩa threshold/user journey phù hợp.

## 4. Practical implementation

Với OpenTelemetry/Application Insights, emit request outcome và duration; dashboard tính tỷ lệ request đạt contract. Ví dụ business API có thể định nghĩa good request là server responses không phải 5xx và latency dưới threshold, nhưng phải cẩn thận không tính client `4xx` do invalid input thành service outage.

```csharp
var sw = Stopwatch.StartNew();
try
{
    await next(context);
}
finally
{
    requestDuration.Record(sw.Elapsed.TotalMilliseconds,
        new("route", routeTemplate),
        new("status_class", $"{context.Response.StatusCode / 100}xx"));
}
```

Tránh high-cardinality labels như raw URL/user ID.

## 5. Real production scenario

Checkout API có SLO nghiêm hơn internal reporting API. Khi checkout burn rate tăng sau release, team freeze risky rollout và ưu tiên remediation; reporting có thể chấp nhận degradation dài hơn. Reliability investment theo business criticality.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard báo 99.99% nhưng users vẫn phàn nàn checkout chậm. **Evidence** → SLI chỉ đo HTTP 5xx, không đo latency hoặc critical dependency/business success. **Hypothesis** → metric không đại diện user experience. **Diagnosis** → map critical journey và telemetry gaps. **Fix** → bổ sung latency/business-success SLI. **Verification** → synthetic/real-user symptoms correlate tốt hơn với SLO alerts.

## 7. Common mistakes

Đồng nhất SLA với SLO; dùng average latency; alert mọi exception; SLO quá cao không dựa business; label cardinality bùng nổ; metric đẹp nhưng bỏ critical user journey.

## 8. Alternatives

Simple threshold alerts đủ cho service nhỏ ở giai đoạn đầu. SLA là external/business commitment, không thay thế internal engineering objective. Error-budget discipline chỉ hữu ích khi team thực sự dùng nó để quyết định.

## 9. Trade-offs

### Advantages

Reliability measurable, prioritization rõ và giảm tranh luận cảm tính.

### Costs / Risks

Cần telemetry tốt, governance và đúng SLI; target sai tạo false confidence hoặc engineering cost không cần thiết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt logs, metrics và reliability target.

### Middle

Instrument request metrics và xây dashboard/alerts có bounded cardinality.

### Senior

Thiết kế SLI phản ánh user experience, burn-rate alerts và incident verification.

### Technical Lead / Architect

Chọn SLO theo business criticality và dùng error budget để cân bằng feature velocity với reliability work.

## 11. Key takeaway

- SLO tốt bắt đầu từ user-visible behavior, không từ metric dễ thu thập nhất.
- Average latency che tail latency; p95/p99 thường quan trọng hơn.
- Reliability target phải ảnh hưởng engineering decisions mới có giá trị.

# 9. SSRF trong backend integrations: outbound HTTP cũng là security boundary

## 1. What is it?

Server-Side Request Forgery (SSRF) xảy ra khi attacker ảnh hưởng URL/host mà backend request tới, khiến server truy cập internal network, metadata endpoints hoặc services mà attacker không thể truy cập trực tiếp. Mental model: outbound HTTP từ trusted backend không tự động là trusted operation.

## 2. Why does it exist?

Backend thường có network privileges lớn hơn browser/client. Features như “import image from URL”, webhook tester hoặc PDF renderer có thể trở thành proxy vào private infrastructure nếu URL không được kiểm soát.

## 3. How does it work?

```text
Attacker input URL
      ↓
Backend fetcher
      ├─ public allowed host  ✓
      └─ 127.0.0.1 / private IP / metadata / redirected host  ✗
```

Validation phải xét scheme, hostname, DNS resolution, redirect behavior và egress policy; string-prefix checks không đủ.

## 4. Practical implementation

Prefer allowlist cho known integrations:

```csharp
static readonly HashSet<string> AllowedHosts =
    new(StringComparer.OrdinalIgnoreCase)
    {
        "images.partner.example",
        "api.partner.example"
    };

if (!Uri.TryCreate(input, UriKind.Absolute, out var uri) ||
    uri.Scheme != Uri.UriSchemeHttps ||
    !AllowedHosts.Contains(uri.Host))
{
    return Results.BadRequest("Unsupported remote host");
}
```

Production defense nên kết hợp DNS/IP validation, redirect policy, network egress controls, timeouts và response-size limits. Không tự viết “URL sanitizer” rồi coi là hoàn chỉnh.

## 5. Real production scenario

CMS cho editor nhập image URL để backend download và optimize. Nếu endpoint chấp nhận URL tùy ý, compromised editor account có thể probe internal admin services. Allowlist + isolated fetcher + egress restriction giảm blast radius.

## 6. Failure scenario & troubleshooting

**Symptom** → outbound logs cho thấy requests tới private address từ public import endpoint. **Evidence** → user-supplied URL redirect từ allowed-looking host sang internal IP. **Hypothesis** → validation chỉ chạy trước redirect. **Diagnosis** → inspect redirect chain/DNS resolution. **Fix** → disable automatic redirects hoặc revalidate mỗi hop; enforce network egress. **Verification** → security tests với loopback, RFC1918, IPv6 local và redirect cases.

## 7. Common mistakes

Chặn chuỗi `localhost` nhưng bỏ IP forms; chỉ validate initial URL; cho mọi scheme; không limit body size; leak fetched response/errors; tin DNS một lần trong môi trường có rebinding risk; backend có egress quá rộng.

## 8. Alternatives

Không hỗ trợ arbitrary URL nếu business không cần. Client upload trực tiếp file có validation riêng. Dedicated media ingestion service với network isolation phù hợp workload rủi ro cao.

## 9. Trade-offs

### Advantages

Remote-fetch feature tiện lợi và giảm client upload steps.

### Costs / Risks

Tạo server-side network attack surface, bandwidth abuse và dependency risk; defense cần application + network layers.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu user-controlled URL là untrusted input.

### Middle

Implement allowlist, HTTPS-only, timeout và size limits.

### Senior

Threat-model redirects, DNS/IP resolution, cloud metadata và egress boundaries.

### Technical Lead / Architect

Quyết định có cần feature remote fetch hay nên cô lập thành service riêng với least-privilege network access.

## 11. Key takeaway

- Outbound request cũng cần authorization/trust policy.
- URL string validation một mình không đủ chống SSRF.
- Network egress restriction là defense-in-depth quan trọng.

# 10. LLM Structured Outputs: schema-constrained output vẫn không biến probabilistic reasoning thành business truth

## 1. What is it?

Structured Outputs buộc model trả dữ liệu theo schema đã định nghĩa, ví dụ JSON object với fields/types cụ thể. Nó giải quyết shape/parseability của response; nó không đảm bảo facts, business correctness hay authorization decisions đúng.

## 2. Why does it exist?

Parsing free-form text bằng regex hoặc “hãy trả JSON” rất brittle. Application cần deterministic envelope để validate và tiếp tục workflow. Schema constraint giảm một class integration failures nhưng không loại bỏ semantic uncertainty.

## 3. How does it work?

```text
Application
   ↓ prompt + schema
LLM
   ↓ schema-constrained response
Parser / validator
   ↓
Deterministic business validation
   ↓
Allowed action / rejection / human review
```

Model có thể trả `{ "risk": "low" }` đúng schema nhưng đánh giá sai. Shape correctness khác semantic correctness.

## 4. Practical implementation

Giữ deterministic validation sau model:

```csharp
public sealed record ExpenseExtraction(
    string Vendor,
    decimal Amount,
    string Currency,
    DateOnly InvoiceDate);

ExpenseExtraction extracted = await llm.ExtractAsync(document, ct);

if (extracted.Amount <= 0 || !AllowedCurrencies.Contains(extracted.Currency))
    return Result.Invalid("Model output failed business validation");

// Never let model decide whether the caller is authorized to approve it.
await authorization.EnsureCanSubmitAsync(userId, ct);
```

Financial totals, permissions và invariant checks vẫn do deterministic code/data sources kiểm soát.

## 5. Real production scenario

AI đọc invoice và trả structured vendor/amount/currency/date. Schema giúp backend parse ổn định, nhưng invoice approval vẫn kiểm tra purchase order, duplicate invoice, currency rules và user authorization bằng application/database logic.

## 6. Failure scenario & troubleshooting

**Symptom** → JSON luôn valid nhưng một số invoices có amount sai. **Evidence** → schema validation 100% pass, evaluation dataset cho semantic accuracy thấp ở scanned documents. **Hypothesis** → team nhầm parse reliability với extraction accuracy. **Diagnosis** → compare model output với labeled ground truth theo document class. **Fix** → improve context/OCR pipeline, confidence/review policy và deterministic reconciliation. **Verification** → rerun eval set, track field-level accuracy và business error rate.

## 7. Common mistakes

Coi valid schema là valid fact; cho model tự authorize tool call; không version schema; retry mọi semantic error vô hạn; không lưu model/version/evaluation metadata; đưa sensitive context quá rộng; không chống prompt injection từ retrieved/user documents.

## 8. Alternatives

Deterministic parser phù hợp fixed document formats. Rules engine phù hợp policy logic. Human review cần thiết cho high-impact uncertain cases. Function/Tool Calling hữu ích khi model chọn capability, nhưng tool implementation vẫn phải enforce authorization và validation.

## 9. Trade-offs

### Advantages

Integration contract ổn định hơn, giảm parsing failures, dễ validate và compose workflow.

### Costs / Risks

Semantic hallucination vẫn tồn tại; schema evolution, token cost, latency, evaluation và security vẫn cần quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu structured JSON không đồng nghĩa nội dung đúng.

### Middle

Implement typed parsing, schema validation, timeout/retry và business validation.

### Senior

Xây eval dataset, quan sát semantic failure, prompt injection và cost/latency.

### Technical Lead / Architect

Xác định boundary giữa probabilistic reasoning và deterministic authority; security-critical, authorization-critical và financial correctness không được giao cho unconstrained model output.

## 11. Key takeaway

- Structured Outputs đảm bảo shape tốt hơn, không đảm bảo truth.
- Business invariants và authorization phải ở deterministic code.
- AI feature production cần evaluation, observability và failure policy như mọi external dependency khác.
