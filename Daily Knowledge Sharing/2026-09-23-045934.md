# 1. .NET `ArrayPool<T>`: reuse buffer để giảm allocation nhưng phải quản lý ownership

## 1. What is it?

`ArrayPool<T>` là pool các array có thể thuê (`Rent`) và trả lại (`Return`) để tái sử dụng buffer thay vì allocation array mới cho mỗi operation. Mental model quan trọng: buffer thuê **không thuộc sở hữu vĩnh viễn của caller**; caller chỉ mượn nó trong một lifetime rõ ràng.

## 2. Why does it exist?

Các hot path như parsing, compression, serialization hoặc file/network processing có thể tạo rất nhiều temporary arrays. Allocation rate cao làm GC chạy thường xuyên; buffer lớn còn có thể đi vào LOH. Pooling giảm allocation pressure khi profiling chứng minh buffer churn là bottleneck.

## 3. How does it work?

```text
ArrayPool.Shared
   | Rent(4096)
   v
[ reusable buffer ] --> application uses slice
   |
   | Return(buffer)
   v
pool bucket
```

`Rent(4096)` có thể trả array lớn hơn 4096. Nội dung cũ có thể vẫn còn. Sau `Return`, application không được tiếp tục sử dụng reference vì buffer có thể được giao cho operation khác.

## 4. Practical implementation

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(
        buffer.AsMemory(0, 64 * 1024), cancellationToken);

    Process(buffer.AsSpan(0, read));
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}
```

Với dữ liệu nhạy cảm, cân nhắc `clearArray: true` hoặc tự clear vùng đã dùng trước khi trả pool.

## 5. Real production scenario

Một service xử lý hàng nghìn file chunks mỗi phút, mỗi chunk allocation 64 KB. Allocation profile cho thấy GC pressure đáng kể dù CPU business logic thấp. Pooling buffer ở I/O hot path giảm allocation rate và tail latency.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu request A đôi lúc xuất hiện trong request B.

**Evidence** → code giữ reference tới pooled array sau khi `Return` hoặc đọc toàn bộ `buffer.Length` thay vì phần dữ liệu hợp lệ.

**Hypothesis** → lifetime/ownership violation.

**Diagnosis** → trace buffer lifecycle và kiểm tra slice length.

**Fix** → giới hạn ownership bằng `try/finally`, không expose pooled array ra ngoài scope, copy nếu consumer cần lifetime dài hơn.

**Verification** → concurrency tests + memory diagnostics dưới load.

## 7. Common mistakes

Giữ buffer sau `Return`; giả định array được zero; dùng toàn bộ rented length; quên trả buffer khi exception; pooling mọi array dù allocation không phải bottleneck.

## 8. Alternatives

Array allocation thông thường đơn giản hơn và thường đủ tốt. `MemoryPool<T>` phù hợp với ownership model khác; `Span<T>` giảm copy nhưng không tự pool storage.

## 9. Trade-offs

### Advantages

Giảm allocation/GC pressure và hữu ích cho high-throughput buffer workloads.

### Costs / Risks

Ownership phức tạp hơn, nguy cơ data leakage/use-after-return và code khó review hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Rent/Return và buffer có thể lớn hơn kích thước yêu cầu.

### Middle

Quản lý lifetime bằng `try/finally`, chỉ dùng valid slice.

### Senior

Đo allocation/GC trước tối ưu và đánh giá sensitive-data risk.

### Technical Lead / Architect

Quyết định pooling có đáng complexity trong hot path hay allocation bình thường đã đủ.

## 11. Key takeaway

- Pooling tối ưu allocation, không tối ưu mọi workload.
- Buffer ownership/lifetime phải rõ tuyệt đối.
- Không giả định pooled memory sạch hoặc thuộc riêng một request.

# 2. ASP.NET Core graceful API versioning: backward compatibility là contract, không chỉ route `/v2`

## 1. What is it?

API versioning là chiến lược quản lý evolution của public contract khi consumers không thể nâng cấp đồng thời. Version có thể biểu diễn qua URL, header hoặc media type, nhưng phần khó thực sự là compatibility policy và migration lifecycle.

## 2. Why does it exist?

Một mobile app cũ, partner integration hoặc frontend cached lâu có thể tiếp tục gọi contract cũ sau khi backend deploy. Thay đổi field semantics, enum hoặc validation trực tiếp có thể phá consumers dù endpoint vẫn trả HTTP 200.

## 3. How does it work?

```text
Client v1 ---> Contract v1 ----+
                               +--> Application capability
Client v2 ---> Contract v2 ----+
```

Version boundary nên nằm ở transport contract. Application/domain không nhất thiết duplicate toàn bộ logic theo version.

## 4. Practical implementation

Ví dụ giữ DTO mới tách khỏi domain:

```csharp
public sealed record CreateOrderV2Request(
    Guid CustomerId,
    IReadOnlyList<OrderLineV2> Lines,
    string Currency);

public static CreateOrderCommand ToCommand(CreateOrderV2Request request) =>
    new(request.CustomerId,
        request.Lines.Select(x => new OrderLineInput(x.Sku, x.Quantity)).ToList(),
        request.Currency);
```

Versioned endpoint map request vào application command ổn định thay vì clone toàn bộ service.

## 5. Real production scenario

V1 coi `price` là currency mặc định; V2 bắt buộc `currency`. Mobile clients có rollout kéo dài nhiều tuần. Backend phục vụ cả hai contract trong deprecation window rồi đo traffic v1 trước khi retire.

## 6. Failure scenario & troubleshooting

**Symptom** → release không đổi route nhưng clients cũ bắt đầu fail validation.

**Evidence** → telemetry cho thấy v1 requests thiếu field vừa chuyển thành required.

**Diagnosis** → breaking semantic change được deploy vào contract hiện hữu.

**Fix** → restore compatible behavior hoặc tạo version mới; thêm contract tests.

**Verification** → chạy consumer fixtures của v1/v2 và theo dõi version-specific error rate.

## 7. Common mistakes

Version mọi thay đổi kể cả additive safe change; duplicate toàn bộ business logic; bỏ version cũ mà không đo usage; coi enum thêm value luôn safe với generated clients; thay error contract mà không coi đó là API contract.

## 8. Alternatives

Additive evolution trong cùng version đơn giản hơn khi compatibility được đảm bảo. Feature negotiation có thể phù hợp một số internal APIs nhưng tăng protocol complexity.

## 9. Trade-offs

### Advantages

Cho consumers migration window, giảm coordinated deployment.

### Costs / Risks

Nhiều contract phải test/support, deprecation kéo dài tạo maintenance burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu breaking vs non-breaking change.

### Middle

Implement versioned DTO/endpoints và contract tests.

### Senior

Đánh giá semantic compatibility, telemetry và deprecation strategy.

### Technical Lead / Architect

Định nghĩa compatibility policy, support window và ownership cho consumer migration.

## 11. Key takeaway

- API versioning là lifecycle của contract, không phải naming convention.
- Version transport contract nhưng tránh duplicate domain logic vô ích.
- Retire version dựa trên telemetry và consumer agreement.

# 3. EF Core split query: tránh cartesian explosion nhưng chấp nhận nhiều round trips

## 1. What is it?

Khi query nhiều collection navigations bằng `Include`, single SQL query có thể tạo cartesian multiplication. `AsSplitQuery()` cho phép EF Core tải graph bằng nhiều SQL queries thay vì một JOIN khổng lồ.

## 2. Why does it exist?

Một Order có 20 Lines và 10 Notes. JOIN cả hai collections có thể tạo 200 result rows cho một Order, lặp lại columns của parent và tăng network/materialization cost.

## 3. How does it work?

```text
Single query:
Orders JOIN Lines JOIN Notes
        -> row multiplication

Split query:
SELECT Orders
SELECT Lines for Orders
SELECT Notes for Orders
```

EF Core fix-up các results thành object graph.

## 4. Practical implementation

```csharp
var order = await db.Orders
    .AsNoTracking()
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .SingleAsync(x => x.Id == id, cancellationToken);
```

Nếu endpoint chỉ cần read model nhỏ, projection thường tốt hơn cả `Include` single lẫn split.

## 5. Real production scenario

Order detail endpoint có parent rộng, Lines, Notes và Attachments. Một JOIN tạo hàng nghìn rows và payload SQL lớn. Split query giảm duplicated bytes đáng kể dù tăng số commands.

## 6. Failure scenario & troubleshooting

**Symptom** → chuyển sang split query nhưng latency tăng ở môi trường database có network RTT cao.

**Evidence** → payload giảm nhưng trace cho thấy nhiều sequential DB round trips.

**Diagnosis** → trade-off chuyển từ row explosion sang round-trip cost.

**Fix** → projection, giảm navigations, benchmark single vs split với production-like cardinality/latency.

**Verification** → so sánh generated SQL, rows, bytes, duration và p95.

## 7. Common mistakes

Dùng `Include` để lấy cả aggregate dù response chỉ cần vài fields; bật split query toàn hệ thống mà không đo; không hiểu consistency giữa nhiều queries khi concurrent updates xảy ra.

## 8. Alternatives

Projection DTO thường tối ưu nhất cho read API. Explicit queries cho control cao hơn. Single query phù hợp khi cardinality nhỏ và round-trip cost đáng kể.

## 9. Trade-offs

### Advantages

Giảm cartesian explosion và duplicated payload.

### Costs / Risks

Nhiều commands/round trips; consistency window giữa queries; không thay thế query modeling tốt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` có thể tạo JOIN lớn.

### Middle

Biết dùng `AsSplitQuery()` và projection.

### Senior

Đo cardinality, network RTT và consistency implications.

### Technical Lead / Architect

Đặt guideline read-model design thay vì mặc định load entity graph.

## 11. Key takeaway

- Split query đổi row multiplication lấy nhiều database commands.
- Projection thường là lựa chọn tốt hơn cho API read model.
- Benchmark bằng cardinality thực tế, không chọn theo rule tuyệt đối.

# 4. Cosmos DB partition key: quyết định data locality, RU cost và scalability từ lúc modeling

## 1. What is it?

Partition key xác định cách Cosmos DB phân phối logical items vào logical partitions và từ đó physical partitions. Nó là quyết định data distribution/access pattern, không chỉ một field bắt buộc khi insert.

## 2. Why does it exist?

Distributed database phải chia dữ liệu để scale storage/throughput. Query có partition key có thể route trực tiếp; query không biết partition thường phải fan-out qua nhiều partitions.

## 3. How does it work?

```text
tenantId=A --> partition range --> physical partition 1
 tenantId=B --> partition range --> physical partition 2
 tenantId=C --> partition range --> physical partition 3
```

Distribution thực tế phụ thuộc hash/ranges và service internals, nhưng mental model là key ảnh hưởng locality, transaction scope và load distribution.

## 4. Practical implementation

```csharp
var response = await container.ReadItemAsync<OrderDocument>(
    id: orderId,
    partitionKey: new PartitionKey(tenantId),
    cancellationToken: cancellationToken);
```

Point read với `id + partition key` thường hiệu quả hơn query tìm ID xuyên partitions.

## 5. Real production scenario

Multi-tenant SaaS dùng `tenantId` làm partition key vì hầu hết operations nằm trong tenant. Một enterprise tenant cực lớn sau đó tạo hot partition; team phải đánh giá hierarchical/synthetic partitioning hoặc workload isolation tùy requirement.

## 6. Failure scenario & troubleshooting

**Symptom** → RU throttling 429 dù tổng provisioned throughput nhìn còn đủ.

**Evidence** → metrics cho thấy một partition/key range nóng bất cân xứng.

**Diagnosis** → low-cardinality/skewed partition key hoặc một tenant/key có traffic vượt partition capacity.

**Fix** → giảm hot-key workload, redesign key khi cần, phân tán write pattern; retry 429 theo SDK policy nhưng không coi retry là root-cause fix.

**Verification** → theo dõi normalized RU consumption và throttling theo partition.

## 7. Common mistakes

Chọn key có cardinality thấp; chọn ngẫu nhiên chỉ để phân tán rồi khiến mọi business query fan-out; bỏ qua transaction boundary; nghĩ tăng tổng RU luôn chữa hot partition.

## 8. Alternatives

SQL database phù hợp hơn nếu workload cần relational joins/transactions rộng. MongoDB có sharding model khác nhưng vẫn đòi hỏi shard-key reasoning tương tự.

## 9. Trade-offs

### Advantages

Scale-out lớn, locality tốt khi key khớp access pattern.

### Costs / Risks

Key khó thay đổi về sau, cross-partition query tốn RU, skew gây hotspot.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định nơi dữ liệu được phân phối.

### Middle

Luôn truyền key cho point reads và đo RU.

### Senior

Phân tích cardinality, skew, hot partition và transaction scope.

### Technical Lead / Architect

Chọn partition strategy từ access patterns, growth model và tenant isolation requirement.

## 11. Key takeaway

- Partition key là architectural decision về distribution.
- Access pattern quan trọng hơn tên field đẹp.
- Retry 429 không sửa một partition strategy sai.

# 5. Circuit Breaker: ngăn dependency failure lan thành resource exhaustion

## 1. What is it?

Circuit Breaker tạm thời ngừng gọi một dependency đang fail mạnh. Thay vì mỗi request tiếp tục timeout, circuit chuyển trạng thái để fail fast trong một khoảng thời gian rồi thử phục hồi có kiểm soát.

## 2. Why does it exist?

Timeout 5 giây tới dependency đang chết có thể giữ connection, request slots và memory cho hàng nghìn calls. Retry còn khuếch đại traffic. Partial failure biến thành cascading failure ở caller.

## 3. How does it work?

```text
Closed -- failures exceed threshold --> Open
  ^                                    |
  |                                    | break duration
  +--------- successful probe <-- Half-Open
```

Circuit cần signal đủ tốt: failure ratio, minimum throughput và sampling window, không chỉ một exception đơn lẻ.

## 4. Practical implementation

Với .NET resilience pipeline, conceptually:

```csharp
services.AddHttpClient<InventoryClient>()
    .AddStandardResilienceHandler();
```

Production configuration cần timeout/retry/circuit policies phù hợp idempotency và SLA của dependency; không copy threshold tùy ý từ sample.

## 5. Real production scenario

Reviews API outage. Product API trước đây retry 3 lần x 3 giây, khiến thread/request pressure và p99 tăng mạnh. Circuit breaker mở sau failure threshold, Product API trả degraded response không có reviews thay vì kéo cả page xuống.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency đã phục hồi nhưng caller vẫn trả fail-fast lâu.

**Evidence** → circuit state Open/Half-Open, break duration hoặc probe traffic không phù hợp.

**Diagnosis** → policy quá aggressive hoặc health recovery logic sai.

**Fix** → tune bằng observed failure/latency distribution và business fallback.

**Verification** → chaos test dependency outage/recovery và quan sát circuit transitions.

## 7. Common mistakes

Circuit breaker không có fallback nhưng vẫn kỳ vọng UX tốt; retry trước circuit với số lần quá lớn; dùng cho local deterministic validation errors; một circuit dùng chung cho unrelated endpoints/tenants khiến blast radius rộng.

## 8. Alternatives

Timeout là baseline bắt buộc. Bulkhead/concurrency limit bảo vệ capacity. Queue phù hợp khi operation không cần synchronous response. Circuit breaker thường kết hợp chứ không thay các cơ chế này.

## 9. Trade-offs

### Advantages

Fail fast, giảm pressure lên dependency và caller, hạn chế cascading failure.

### Costs / Risks

State/tuning phức tạp, có thể reject request khi dependency vừa hồi phục, cần fallback semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Open circuit nghĩa là chủ động không gọi dependency.

### Middle

Kết hợp timeout và resilience handler đúng loại exception/status.

### Senior

Tune threshold, retry order, fallback và telemetry.

### Technical Lead / Architect

Xác định dependency criticality, degradation mode và blast-radius boundary.

## 11. Key takeaway

- Circuit breaker bảo vệ capacity, không chữa dependency.
- Retry + timeout + circuit phải được thiết kế cùng nhau.
- Fallback chỉ hợp lệ nếu business chấp nhận degraded behavior.

# 6. CQRS với một database: tách intent mà chưa cần distributed read/write stores

## 1. What is it?

CQRS tách command (thay đổi state) khỏi query (đọc state) ở model/intent. Nó **không bắt buộc** hai databases, Event Sourcing hay message broker.

## 2. Why does it exist?

Read và write thường có concerns khác nhau. Write cần invariants/transaction; read cần projection/filtering hiệu quả. Ép một entity model phục vụ cả hai có thể tạo abstraction khó dùng.

## 3. How does it work?

```text
HTTP Command --> Handler --> Domain/EF Core --> same DB
HTTP Query   --> Query Handler --> Projection ----^ 
```

Cùng database vẫn có thể dùng transaction consistency đơn giản trong khi code paths tách rõ intent.

## 4. Practical implementation

```csharp
public sealed record GetOrderQuery(Guid Id);

public async Task<OrderDto?> Handle(
    GetOrderQuery query,
    CancellationToken ct) =>
    await db.Orders.AsNoTracking()
        .Where(x => x.Id == query.Id)
        .Select(x => new OrderDto(x.Id, x.Status, x.Total))
        .SingleOrDefaultAsync(ct);
```

Write handler có thể load aggregate và enforce invariant; read handler projection trực tiếp.

## 5. Real production scenario

Approval system có complex write rules nhưng dashboards cần joins/projections khác. CQRS logical separation làm write model sạch hơn mà chưa cần operational cost của replicated read store.

## 6. Failure scenario & troubleshooting

**Symptom** → team có hàng trăm handler một dòng, navigation khó hơn nhưng business complexity không giảm.

**Evidence** → mỗi CRUD operation bị ceremony hóa, không có khác biệt meaningful giữa read/write model.

**Diagnosis** → pattern được áp dụng vì architecture fashion.

**Fix** → giảm abstraction ở modules đơn giản; dùng CQRS nơi separation tạo giá trị.

**Verification** → code path dễ hiểu hơn, tests bám behavior/risk thay vì framework ceremony.

## 7. Common mistakes

Đồng nhất CQRS với MediatR; bắt buộc Event Sourcing; tách databases quá sớm; tạo command/query cho mọi getter/setter; để handler chỉ forward qua nhiều layers vô nghĩa.

## 8. Alternatives

Application services CRUD đơn giản phù hợp domain nhỏ. Separate read store chỉ đáng cân nhắc khi scale/query requirements biện minh cho eventual consistency và synchronization cost.

## 9. Trade-offs

### Advantages

Intent rõ, read projection linh hoạt, write model tập trung invariants.

### Costs / Risks

Nhiều types/files hơn, dễ overengineering; physical separation thêm consistency complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt command và query.

### Middle

Implement read projection/write transaction riêng.

### Senior

Nhận ra khi CQRS giảm coupling và khi chỉ thêm ceremony.

### Technical Lead / Architect

Quyết định logical CQRS có đủ hay cần physical separation dựa trên evidence.

## 11. Key takeaway

- CQRS không đồng nghĩa two databases.
- Tách intent trước; chỉ tách infrastructure khi có lý do.
- Pattern phải giảm business/technical friction, không tăng ceremony vô ích.

# 7. Azure App Service deployment slots: release validation, warm-up và rollback không đồng nghĩa zero-risk

## 1. What is it?

Deployment slot là một live App Service environment riêng trong cùng app, thường dùng `staging` và `production`. Code mới deploy vào staging, warm/validate rồi swap routing/configuration sang production.

## 2. Why does it exist?

Deploy trực tiếp có thể khiến users chịu startup/JIT/configuration errors. Slot cho phép kiểm tra build trong Azure environment trước cutover và rollback bằng swap nhanh hơn redeploy artifact.

## 3. How does it work?

```text
Artifact --> Staging slot --> warm-up/health
                              |
                              | swap
                              v
Users --------------------> Production
```

Slot settings quyết định configuration nào “stick” với slot thay vì swap theo code.

## 4. Practical implementation

Pipeline nên theo flow:

```text
build -> test -> deploy staging -> health/smoke test
      -> swap -> production validation -> monitor
```

Connection strings/secrets/environment-specific settings phải được phân loại rõ trước swap.

## 5. Real production scenario

API .NET deploy version mới có startup migration check. Staging slot phát hiện missing Key Vault permission trước khi users bị ảnh hưởng. Team sửa identity/config rồi mới swap.

## 6. Failure scenario & troubleshooting

**Symptom** → swap thành công nhưng production requests lỗi database schema.

**Evidence** → application healthy ở staging với backward-compatible traffic test, nhưng schema migration đã phá old/new compatibility.

**Diagnosis** → slot swap chỉ đổi application routing; database vẫn là shared external state.

**Fix** → expand/contract migration, backward-compatible release sequence.

**Verification** → test old + new app versions cùng schema trong deployment window.

## 7. Common mistakes

Coi slot là full environment isolation; staging dùng database khác nên không phát hiện production schema issue; secret settings swap nhầm; không warm-up; swap xong không monitor.

## 8. Alternatives

Blue-Green với separate infrastructure cho isolation mạnh hơn nhưng tốn cost. Rolling/Canary giúp gradual exposure. Direct deployment đơn giản hơn cho low-risk internal apps.

## 9. Trade-offs

### Advantages

Warm-up, pre-production validation và rollback application nhanh.

### Costs / Risks

Shared dependencies vẫn có blast radius; slot/config complexity; không giải quyết destructive DB migrations.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu staging slot là runtime riêng trước swap.

### Middle

Deploy, health test, swap và validate.

### Senior

Quản lý slot settings, schema compatibility và rollback semantics.

### Technical Lead / Architect

Chọn slot/Blue-Green/Canary theo risk, traffic và stateful dependency constraints.

## 11. Key takeaway

- Slot giảm release risk nhưng không cô lập database/external dependencies.
- Database compatibility quyết định rollback có thực sự khả thi hay không.
- Swap phải đi cùng health validation và post-release monitoring.

# 8. SQL connection pool exhaustion: latency có thể đến từ chờ connection chứ không phải query chậm

## 1. What is it?

ADO.NET connection pooling giữ các physical database connections để tái sử dụng. `OpenAsync` thường lấy connection từ pool; khi pool hết available connections, caller phải chờ connection được trả lại hoặc timeout.

## 2. Why does it exist?

Tạo database connection mới có chi phí network/authentication. Pooling giảm overhead, nhưng đồng thời tạo một bounded shared resource mà application phải quản lý lifetime tốt.

## 3. How does it work?

```text
Requests --> [ Connection Pool ] --> SQL Server
                | | | | |
                leased connections

pool full + long holders
        -> new callers wait
```

Pool thường được phân tách theo connection string/identity, nên thay đổi nhỏ trong connection string có thể tạo pools riêng.

## 4. Practical implementation

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(cancellationToken);

await using var command = connection.CreateCommand();
command.CommandText = "SELECT ...";
// execute promptly; dispose returns connection to pool
```

EF Core `DbContext` scoped đúng cách thường quản lý connection lifecycle; không giữ context/transaction lâu qua remote calls.

## 5. Real production scenario

External API latency tăng. Code mở transaction/connection trước khi gọi external API, nên hàng trăm connections bị giữ trong lúc chờ network. SQL query metrics không chậm nhưng API bắt đầu timeout khi lấy connection.

## 6. Failure scenario & troubleshooting

**Symptom** → `Timeout expired prior to obtaining a connection from the pool` hoặc request latency tăng trước khi SQL command xuất hiện.

**Evidence** → pool wait metrics, active connections cao, traces có gap ở `OpenAsync`.

**Hypothesis** → connection leak hoặc transaction/lifetime quá dài.

**Diagnosis** → inspect disposal paths, DbContext lifetime, transactions và concurrent DB operations.

**Fix** → dispose đúng, rút ngắn transaction, không giữ connection qua remote I/O; chỉ tăng pool size sau khi hiểu capacity database.

**Verification** → load test và theo dõi wait time, active connections, SQL CPU/concurrency.

## 7. Common mistakes

Tăng `Max Pool Size` ngay lập tức; singleton `DbContext`; quên dispose manual connection; transaction bao cả HTTP call; tạo nhiều pools do connection strings khác nhau.

## 8. Alternatives

Không pooling thường kém hiệu quả cho web workloads. Queue/concurrency limit có thể bảo vệ database nếu application fan-out vượt DB capacity.

## 9. Trade-offs

### Advantages

Reuse connection nhanh, giảm handshake overhead.

### Costs / Risks

Pool trở thành capacity boundary; tăng pool size có thể chỉ chuyển bottleneck sang database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dispose thường trả connection về pool, không nhất thiết đóng physical socket.

### Middle

Quản lý lifetime và cancellation đúng.

### Senior

Phân tích pool wait vs query latency và concurrency pressure.

### Technical Lead / Architect

Thiết kế DB concurrency budget theo application instances và database capacity.

## 11. Key takeaway

- Slow database access không luôn là slow SQL.
- Connection lifetime phải ngắn và predictable.
- Pool size là capacity control, không phải nút “tăng performance” miễn phí.

# 9. Akamai/CDN `Cache-Control`: browser, edge và origin có các freshness boundary khác nhau

## 1. What is it?

HTTP caching cho phép browser/CDN reuse response dựa trên freshness metadata như `Cache-Control`. Trong architecture có Akamai, response có thể được cache ở browser và edge trước khi request chạm origin.

## 2. Why does it exist?

Static/content-heavy sites không nên đưa mọi request về application. Edge caching giảm latency, origin load và network distance, nhưng freshness trở thành distributed state problem.

## 3. How does it work?

```text
Browser cache
     |
     v
Akamai edge cache
     |
     v
Origin / ASP.NET Core / CMS
```

`max-age` thường định nghĩa browser/shared freshness theo directive; `s-maxage` có thể áp riêng cho shared caches. Chính xác behavior còn phụ thuộc CDN property/configuration.

## 4. Practical implementation

Ví dụ public asset/versioned response:

```http
Cache-Control: public, max-age=300, s-maxage=3600
ETag: "content-v42"
```

Không áp policy này cho personalized/authenticated content nếu cache key/vary semantics chưa được thiết kế an toàn.

## 5. Real production scenario

CMS publish campaign mới. Origin trả nội dung mới nhưng Akamai edge còn object cũ theo TTL. Team purge origin cache nhưng users vẫn thấy stale content vì edge cache là layer khác.

## 6. Failure scenario & troubleshooting

**Symptom** → một số geography thấy nội dung cũ, direct-origin request đúng.

**Evidence** → CDN headers/cache status cho thấy edge HIT với object cũ.

**Diagnosis** → stale edge object hoặc cache key/purge mismatch.

**Fix** → purge đúng key/property, điều chỉnh TTL/versioned URLs và invalidation workflow.

**Verification** → kiểm tra nhiều edge locations và response headers.

## 7. Common mistakes

Cache personalized HTML public; purge application cache rồi tưởng CDN cũng sạch; TTL cực ngắn làm mất lợi ích CDN; TTL cực dài nhưng asset URL không version; bỏ qua `Vary`/cache key dimensions.

## 8. Alternatives

Browser-only cache đơn giản hơn nhưng không giảm origin traffic từ first visits. Reverse-proxy cache gần origin giảm load nhưng không có geographic edge latency benefit.

## 9. Trade-offs

### Advantages

Latency thấp, giảm origin load, tăng resilience cho cacheable content.

### Costs / Risks

Staleness, invalidation complexity, cache-key security và khó debug nhiều layers.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser/edge/origin là ba cache boundaries khác nhau.

### Middle

Đọc response cache headers và CDN cache status.

### Senior

Thiết kế cache keys, TTL, purge và personalized-content safety.

### Technical Lead / Architect

Định nghĩa freshness SLA và ownership giữa CMS, application và CDN configuration.

## 11. Key takeaway

- Cache invalidation phải xác định đúng layer.
- CDN chỉ an toàn khi cache key và data visibility đúng.
- Versioned assets thường đơn giản hơn aggressive purge cho static content.

# 10. SonarQube/code coverage: quality gate là risk signal, không phải bằng chứng correctness

## 1. What is it?

Code coverage đo phần code được tests thực thi theo metric như line/branch coverage. SonarQube kết hợp coverage với static-analysis findings, duplication, complexity và maintainability/security rules để tạo quality signals.

## 2. Why does it exist?

Team cần automated feedback trước merge/release. Nhưng một số metric dễ đo không đồng nghĩa behavior đúng. 100% line coverage có thể đạt bằng tests không assert gì có ý nghĩa.

## 3. How does it work?

```text
commit
  -> build
  -> tests + coverage report
  -> static analysis
  -> quality gate
  -> PR decision + human review
```

Quality gate nên tập trung new code/risk phù hợp thay vì biến legacy baseline thành blocker không thể xử lý.

## 4. Practical implementation

Test tốt bảo vệ behavior:

```csharp
[Fact]
public async Task Approve_WhenAlreadyRejected_MustFail()
{
    var request = RejectedRequest();

    var act = () => request.Approve(UserId.New());

    act.Should().Throw<InvalidOperationException>();
}
```

Giá trị nằm ở invariant được bảo vệ, không phải dòng code được “chạm”.

## 5. Real production scenario

Service có 90% coverage nhưng production bug xảy ra ở transaction rollback khi Service Bus publish fail. Unit tests mock cả database/message publisher nên không bao giờ kiểm tra integration boundary. Coverage cao che một risk gap thực tế.

## 6. Failure scenario & troubleshooting

**Symptom** → quality gate xanh nhưng regression vẫn lọt production.

**Evidence** → covered lines cao, nhưng thiếu integration/E2E test cho critical failure path.

**Diagnosis** → test strategy tối ưu metric thay vì risk.

**Fix** → map tests theo failure boundaries: unit cho invariants, integration cho persistence/contracts, E2E cho critical journeys.

**Verification** → reproduce production bug bằng test trước fix và giữ regression test sau fix.

## 7. Common mistakes

Đặt target 100% cho mọi project; test getters/DTOs để tăng số; mock mọi dependency; bỏ qua flaky tests; coi static analyzer finding là absolute truth mà không review context.

## 8. Alternatives

Mutation testing có thể đánh giá assertion strength nhưng tốn compute. Architecture tests bảo vệ dependency rules. Manual review vẫn cần cho semantics/design mà static tools không hiểu đầy đủ.

## 9. Trade-offs

### Advantages

Fast automated feedback, phát hiện regression/code smells sớm, tạo baseline nhất quán.

### Costs / Risks

Metric gaming, false positives, pipeline time và cảm giác an toàn giả nếu coverage bị hiểu sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu coverage chỉ cho biết code đã chạy trong test.

### Middle

Viết assertions bảo vệ behavior và chọn test level phù hợp.

### Senior

Review test gaps theo failure mode/integration boundary, không theo percentage đơn thuần.

### Technical Lead / Architect

Thiết kế quality gate và test strategy theo business/technical risk, build time và legacy constraints.

## 11. Key takeaway

- Coverage là signal về test execution, không phải proof of correctness.
- Test strategy phải bám risk và failure boundaries.
- Quality gate hỗ trợ engineering judgment, không thay thế nó.
