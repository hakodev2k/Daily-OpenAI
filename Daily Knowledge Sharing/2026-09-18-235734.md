# 1. .NET `IAsyncDisposable`: async cleanup và resource lifetime

## 1. What is it?

`IAsyncDisposable` là contract cho resource cần cleanup có asynchronous work. Mental model: acquisition và release đều là một phần của resource lifetime; nếu release phải flush network/file state thì synchronous `Dispose()` có thể không phù hợp.

## 2. Why does it exist?

Một resource có thể cần gửi bytes cuối, flush buffer hoặc đóng protocol asynchronously. Chặn thread để cleanup làm giảm scalability và dễ tạo sync-over-async.

## 3. How does it work?

`await using` gọi `DisposeAsync()` khi scope kết thúc, kể cả khi exception xảy ra.

```text
Acquire → use → exception/success → DisposeAsync → resource released
```

## 4. Practical implementation

```csharp
await using var stream = new FileStream(
    path, FileMode.Create, FileAccess.Write,
    FileShare.None, 81920, useAsync: true);

await stream.WriteAsync(payload, ct);
```

Custom type:

```csharp
public async ValueTask DisposeAsync()
{
    await FlushAsync(CancellationToken.None);
    _connection.Dispose();
}
```

Cleanup thường không nên phụ thuộc request cancellation token đã bị cancel.

## 5. Real production scenario

File-processing worker upload buffered output. Handler hoàn tất business logic nhưng nếu process trả message trước khi async flush xong, output có thể incomplete.

## 6. Failure scenario & troubleshooting

**Symptom** → file truncated hoặc connection count tăng. **Evidence** → resource không được async-dispose trên exception path. **Hypothesis** → lifetime leak. **Diagnosis** → inspect ownership và disposal path. **Fix** → `await using`, một owner rõ ràng. **Verification** → fault-injection test và resource counters ổn định.

## 7. Common mistakes

Gọi `DisposeAsync().AsTask().Wait()`; nhiều objects cùng nghĩ mình sở hữu resource; truyền cancelled token vào cleanup; bỏ qua disposal vì GC “sẽ dọn”.

## 8. Alternatives

`IDisposable` đúng khi cleanup thuần synchronous. Factory/callback scope có thể encapsulate ownership nếu caller không nên quản lý resource trực tiếp.

## 9. Trade-offs

### Advantages

Cleanup non-blocking, lifetime explicit, exception-safe với `await using`.

### Costs / Risks

API phức tạp hơn và ownership sai vẫn gây double-dispose/leak.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu dispose là deterministic cleanup.

### Middle
Dùng `await using` đúng scope.

### Senior
Reason về cleanup khi cancellation/failure xảy ra.

### Technical Lead / Architect
Định nghĩa ownership contract để resource không vượt boundary không cần thiết.

## 11. Key takeaway

- Cleanup là một phần của correctness.
- Async resource nên được async-dispose.
- Ownership phải rõ hơn cả API syntax.

# 2. ASP.NET Core `ProblemDetails`: error contract ổn định thay vì exception leakage

## 1. What is it?

`ProblemDetails` là representation chuẩn hóa cho HTTP API errors. Mental model: exception là implementation detail; HTTP error response là public contract.

## 2. Why does it exist?

Nếu mỗi endpoint trả lỗi theo shape khác nhau, clients phải đoán. Nếu serialize exception trực tiếp, API có thể leak stack trace, SQL hoặc internal names.

## 3. How does it work?

```text
Exception / validation failure
        ↓
central error mapping
        ↓
HTTP status + ProblemDetails
        ↓
client handles stable contract
```

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();
app.UseExceptionHandler();

return Results.Problem(
    statusCode: StatusCodes.Status409Conflict,
    title: "Order state conflict",
    detail: "The order can no longer be modified.");
```

Domain/application errors nên map có chủ đích sang HTTP semantics.

## 5. Real production scenario

Approval API có web và mobile clients. Stable `type`, `status`, error code extension giúp clients xử lý conflict mà không parse human-readable message.

## 6. Failure scenario & troubleshooting

**Symptom** → client retry 400/409 như 500. **Evidence** → error mapping không nhất quán. **Hypothesis** → transport contract không phản ánh failure semantics. **Diagnosis** → inventory status codes và client retry logic. **Fix** → centralized mapping. **Verification** → contract tests cho representative failures.

## 7. Common mistakes

Mọi exception thành 500; trả 200 với `{success:false}`; leak stack trace; dùng `detail` như machine code; thay đổi error shape không versioning.

## 8. Alternatives

Custom envelope có thể cần cho legacy contract nhưng nên giữ HTTP status semantics. gRPC dùng status model khác.

## 9. Trade-offs

### Advantages

Client integration rõ, observability tốt, giảm information leakage.

### Costs / Risks

Cần taxonomy lỗi và backward-compatibility discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt exception và HTTP response.

### Middle
Map validation/not-found/conflict đúng status.

### Senior
Thiết kế retryable vs non-retryable error semantics.

### Technical Lead / Architect
Chuẩn hóa error contract xuyên APIs mà không leak domain internals.

## 11. Key takeaway

- Error response là API contract.
- HTTP status phải phản ánh semantics.
- Internal exception không nên đi thẳng ra client.

# 3. EF Core optimistic concurrency: `rowversion`, lost update và retry đúng nghĩa

## 1. What is it?

Optimistic concurrency giả định conflict hiếm và phát hiện conflict khi write thay vì lock record suốt thời gian user chỉnh sửa. `rowversion` của SQL Server thường được dùng làm concurrency token.

## 2. Why does it exist?

Hai users đọc cùng version. Nếu cả hai update unconditional, writer sau ghi đè writer trước mà không biết.

## 3. How does it work?

```text
Read Version=7
UPDATE ... WHERE Id=42 AND Version=7
              ↓
0 rows → conflict
1 row  → success, new version
```

EF Core kiểm tra affected rows và ném `DbUpdateConcurrencyException` khi token không còn khớp.

## 4. Practical implementation

```csharp
public class Order
{
    public int Id { get; set; }
    [Timestamp]
    public byte[] Version { get; set; } = [];
}

try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new { code = "order_changed" });
}
```

## 5. Real production scenario

Hai operators sửa customer configuration. Operator B phải thấy conflict thay vì vô tình xóa thay đổi vừa được A lưu.

## 6. Failure scenario & troubleshooting

**Symptom** → lost updates vẫn xảy ra. **Evidence** → generated `UPDATE` không có version predicate. **Hypothesis** → token chưa configured hoặc raw SQL bypass tracker. **Diagnosis** → inspect model metadata/generated SQL. **Fix** → concurrency token xuyên persistence path. **Verification** → parallel integration test chỉ một stale writer thành công.

## 7. Common mistakes

Blind retry bằng cách reload rồi overwrite; catch exception và trả success; dùng timestamp ứng dụng thiếu precision; nghĩ transaction tự ngăn lost update.

## 8. Alternatives

Pessimistic locking phù hợp critical short-lived contention nhưng khó với stateless web interactions. ETag có thể đưa version contract lên HTTP boundary.

## 9. Trade-offs

### Advantages

Không giữ lock dài, conflict explicit.

### Costs / Risks

Client/user phải có merge/retry strategy; high-contention workloads có thể retry nhiều.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu lost update.

### Middle
Configure token và handle exception.

### Senior
Quyết định merge/reject/retry theo business invariant.

### Technical Lead / Architect
Nối concurrency semantics từ API tới database thay vì giải quyết từng layer riêng.

## 11. Key takeaway

- Concurrency conflict là business event, không chỉ exception kỹ thuật.
- Retry không được biến thành silent overwrite.
- Verify bằng concurrent integration tests.

# 4. PostgreSQL keyset pagination: ổn định latency khi dataset lớn

## 1. What is it?

Keyset pagination lấy trang kế tiếp dựa trên giá trị sort cuối cùng thay vì `OFFSET N`. Mental model: tiếp tục từ cursor trong ordered index thay vì đếm và bỏ qua hàng loạt rows.

## 2. Why does it exist?

`OFFSET 500000 LIMIT 50` vẫn buộc database đi qua lượng lớn rows trước khi trả 50 rows cần thiết. Dataset càng lớn, deep page càng đắt.

## 3. How does it work?

```sql
SELECT id, created_at, total
FROM orders
WHERE (created_at, id) < (@createdAt, @id)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Composite ordering cần deterministic tie-breaker như `id`.

## 4. Practical implementation

Tạo index phù hợp access pattern:

```sql
CREATE INDEX ix_orders_created_id
ON orders (created_at DESC, id DESC);
```

Cursor API encode các sort values, không phải arbitrary page number.

## 5. Real production scenario

Audit timeline có hàng chục triệu records. Users chủ yếu “load more”; keyset giữ query cost tương đối ổn định ở page sâu.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate/missing rows giữa pages. **Evidence** → sort chỉ bằng non-unique `created_at`. **Hypothesis** → cursor ordering không deterministic. **Diagnosis** → tìm ties và concurrent inserts. **Fix** → stable composite order. **Verification** → pagination test với duplicate timestamps và concurrent writes.

## 7. Common mistakes

Cursor không chứa mọi sort key; sort direction và predicate không khớp; vẫn expose random page jump dù backend keyset; thêm index mà không xem plan.

## 8. Alternatives

Offset pagination đơn giản và phù hợp dataset nhỏ/random page navigation. Search engine `search_after` có mental model tương tự cho search results.

## 9. Trade-offs

### Advantages

Deep-page latency ổn định hơn, ít wasted I/O.

### Costs / Risks

Không tiện jump-to-page, cursor contract phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `LIMIT/OFFSET`.

### Middle
Implement stable cursor.

### Senior
Đọc execution plan và index alignment.

### Technical Lead / Architect
Chọn pagination semantics dựa UX/access pattern thay vì mặc định page-number API.

## 11. Key takeaway

- Pagination là database access pattern.
- Stable ordering là correctness requirement.
- Keyset phù hợp feed/timeline lớn hơn random page navigation.

# 5. Elasticsearch refresh: near-real-time search và read-after-write expectation

## 1. What is it?

Elasticsearch search là near-real-time: document indexed không nhất thiết searchable ngay lập tức. Refresh tạo search-visible segments; nó khác durability flush và transaction commit của relational database.

## 2. Why does it exist?

Refresh mỗi write sẽ tăng I/O và segment overhead. Elasticsearch batch visibility để cân bằng indexing throughput và search freshness.

## 3. How does it work?

```text
Primary DB write → sync/index request → ES indexing buffer
                                      ↓ refresh
                               searchable segment
```

## 4. Practical implementation

Với workflow hiếm cần chờ visibility có thể dùng refresh behavior có chủ đích; không ép refresh trên mọi write. UI vừa tạo entity thường nên đọc transactional source cho confirmation thay vì search ngay.

## 5. Real production scenario

Admin publish product rồi lập tức search và không thấy trong vài giây. Đây có thể là expected NRT behavior, không phải lost data.

## 6. Failure scenario & troubleshooting

**Symptom** → search stale lâu bất thường. **Evidence** → indexing succeeded nhưng sync lag/refresh metrics tăng. **Hypothesis** → pipeline backlog hoặc cluster pressure. **Diagnosis** → kiểm tra bulk failures, refresh/indexing latency, queue lag. **Fix** → xử lý pipeline/cluster bottleneck. **Verification** → đo end-to-end DB-change-to-search-visible latency.

## 7. Common mistakes

`refresh=true` cho mọi write; coi Elasticsearch là transactional source; không monitor sync lag; user workflow đòi read-after-write nhưng chỉ đọc search index.

## 8. Alternatives

SQL full-text có consistency/scale trade-off khác. Dedicated search vẫn hợp lý khi relevance, analyzers và aggregations là yêu cầu chính.

## 9. Trade-offs

### Advantages

High search throughput và rich retrieval capabilities.

### Costs / Risks

Eventual visibility và synchronization complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu index không luôn searchable tức thì.

### Middle
Debug indexing vs refresh vs sync lag.

### Senior
Định nghĩa freshness SLI.

### Technical Lead / Architect
Thiết kế UX và source-of-truth boundary phù hợp eventual consistency.

## 11. Key takeaway

- Indexed không đồng nghĩa immediately searchable.
- Freshness phải được đo end-to-end.
- Đừng đổi throughput lấy synchronous refresh nếu business không cần.

# 6. Bulkhead Pattern: cô lập resource để một dependency không làm sập toàn service

## 1. What is it?

Bulkhead chia resource capacity thành các vùng cô lập để saturation ở một workload/dependency không tiêu thụ toàn bộ service capacity.

## 2. Why does it exist?

Nếu mọi outbound call dùng cùng concurrency budget, một slow dependency có thể giữ hết sockets/tasks và làm endpoints không liên quan cũng chậm.

## 3. How does it work?

```text
API
├─ Payment calls → concurrency pool A
├─ Review calls  → concurrency pool B
└─ Search calls  → concurrency pool C
```

Isolation có thể ở semaphore, connection pool, queue, worker pool hoặc process/service boundary.

## 4. Practical implementation

```csharp
private readonly SemaphoreSlim _reviewSlots = new(20);

await _reviewSlots.WaitAsync(ct);
try
{
    return await reviewClient.GetAsync(id, ct);
}
finally
{
    _reviewSlots.Release();
}
```

Production cần bounded wait/timeout; semaphore không nên biến thành unbounded queue.

## 5. Real production scenario

Third-party reviews API treo 20 giây. Không bulkhead, product page requests giữ capacity cho reviews và checkout cũng suy giảm.

## 6. Failure scenario & troubleshooting

**Symptom** → unrelated endpoints latency tăng cùng dependency outage. **Evidence** → shared pool/concurrency saturation. **Hypothesis** → failure propagation qua shared resource. **Diagnosis** → dependency traces + pool/queue metrics. **Fix** → isolation, timeout, fallback. **Verification** → fault test dependency A trong khi SLO của path B vẫn giữ.

## 7. Common mistakes

Chỉ thêm Circuit Breaker nhưng không giới hạn concurrency; bulkhead quá nhỏ; queue vô hạn; không có fallback semantics.

## 8. Alternatives

Process/service isolation mạnh hơn nhưng operational cost lớn. Rate limiting bảo vệ ingress; bulkhead bảo vệ internal capacity.

## 9. Trade-offs

### Advantages

Giảm blast radius và cascading saturation.

### Costs / Risks

Capacity fragmentation, tuning và metrics phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu shared resource saturation.

### Middle
Implement bounded concurrency.

### Senior
Đo queue time, saturation và fallback behavior.

### Technical Lead / Architect
Quyết định isolation boundary theo business criticality và blast radius.

## 11. Key takeaway

- Reliability cần resource isolation, không chỉ retry.
- Queue phải bounded.
- Bulkhead boundary nên phản ánh failure domain.

# 7. Azure Service Bus lock & settlement: duplicate delivery là normal condition

## 1. What is it?

Trong Peek-Lock mode, receiver lock message tạm thời, xử lý rồi `Complete`. Nếu lock hết hạn hoặc settlement thất bại, message có thể được deliver lại. At-least-once nghĩa duplicate là điều phải thiết kế cho.

## 2. Why does it exist?

Broker không thể atomically biết business side effect của consumer đã commit hay chưa khi network/process fail.

## 3. How does it work?

```text
Receive + lock → business work → Complete
                    │ crash
                    ↓
             lock expires → redelivery
```

## 4. Practical implementation

```csharp
processor.ProcessMessageAsync += async args =>
{
    var messageId = args.Message.MessageId;
    if (await inbox.AlreadyProcessedAsync(messageId, args.CancellationToken))
    {
        await args.CompleteMessageAsync(args.Message);
        return;
    }

    await handler.HandleAsync(args.Message, args.CancellationToken);
    await inbox.MarkProcessedAsync(messageId, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message);
};
```

Inbox/business atomicity cần thiết kế kỹ; snippet chỉ minh họa boundary.

## 5. Real production scenario

Worker tạo invoice thành công rồi process crash trước `Complete`. Message quay lại. Nếu handler không idempotent, invoice thứ hai được tạo.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate side effects. **Evidence** → cùng `MessageId` có nhiều deliveries. **Hypothesis** → handler giả định exactly-once. **Diagnosis** → correlate delivery count, business IDs và settlement logs. **Fix** → idempotent operation/inbox/deduplication. **Verification** → kill worker sau commit nhưng trước complete.

## 7. Common mistakes

Complete trước business commit; dùng delivery count như unique identity; retry poison message mãi; lock duration quá ngắn cho handler.

## 8. Alternatives

Receive-and-delete giảm broker redelivery nhưng chấp nhận mất message khi consumer crash. Thường không phù hợp critical workflows.

## 9. Trade-offs

### Advantages

Reliable redelivery khi consumer fail.

### Costs / Risks

Duplicate processing, lock renewal và DLQ operations.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu Peek-Lock lifecycle.

### Middle
Handle complete/abandon/dead-letter.

### Senior
Thiết kế idempotency và crash-window tests.

### Technical Lead / Architect
Đặt delivery guarantee và business deduplication contract xuyên producers/consumers.

## 11. Key takeaway

- At-least-once yêu cầu duplicate-safe consumer.
- Settlement không phải business transaction.
- Test crash windows có giá trị hơn happy-path test.

# 8. Kubernetes resource requests/limits: scheduling, throttling và OOMKilled

## 1. What is it?

`requests` mô tả resource scheduler dùng để đặt Pod; `limits` đặt upper bound runtime. CPU và memory có failure behavior khác nhau: CPU có thể throttle, memory vượt limit có thể dẫn tới OOM kill.

## 2. Why does it exist?

Cluster nhiều workloads cần capacity accounting và isolation. Không khai báo hợp lý, noisy neighbor hoặc overcommit có thể làm latency và availability khó đoán.

## 3. How does it work?

```text
requests → scheduler placement/capacity
limits   → runtime enforcement
CPU over → throttling
Memory over → OOMKilled/restart
```

## 4. Practical implementation

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
```

Giá trị phải dựa profiling/load test, không copy từ template.

## 5. Real production scenario

.NET API có memory limit 256Mi nhưng peak GC working set vượt ngưỡng khi traffic burst. Pod restart liên tục dù node còn RAM trống.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng hoặc Pod restart. **Evidence** → CPU throttling metrics hoặc `OOMKilled`. **Hypothesis** → resource envelope không khớp workload. **Diagnosis** → correlate utilization, GC, limits và request rate. **Fix** → tối ưu workload hoặc chỉnh envelope/capacity. **Verification** → load test với production-like concurrency.

## 7. Common mistakes

Requests=limits tùy tiện; memory limit quá sát average; chỉ nhìn node CPU; tăng limits mà không tìm allocation leak; autoscale theo metric không phản ánh bottleneck.

## 8. Alternatives

VM/App Service abstract nhiều scheduler details nhưng capacity vẫn tồn tại. Container Apps cung cấp abstraction cao hơn Kubernetes trực tiếp.

## 9. Trade-offs

### Advantages

Predictable scheduling, isolation và capacity planning.

### Costs / Risks

Sai sizing gây waste, throttling hoặc restarts.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu requests khác limits.

### Middle
Debug throttling/OOMKilled.

### Senior
Kết nối GC, concurrency và resource metrics.

### Technical Lead / Architect
Thiết kế capacity/autoscaling dựa workload SLO và cost.

## 11. Key takeaway

- Requests là scheduling contract; limits là enforcement boundary.
- CPU pressure và memory pressure fail khác nhau.
- Sizing phải dựa measurement.

# 9. Application Insights dependency telemetry: điều tra latency theo critical path

## 1. What is it?

Dependency telemetry ghi outbound operations như HTTP hoặc database calls và liên kết chúng với request trace. Mental model: endpoint latency là tổng/overlap của work trên critical path, không chỉ thời gian trong controller.

## 2. Why does it exist?

Log “request took 2.4s” không cho biết 2.4s nằm ở SQL, Redis, external API hay application CPU.

## 3. How does it work?

```text
Request 2.4s
├─ SQL 120ms
├─ Redis 8ms
└─ Reviews API 2.1s  ← dominant dependency
```

Distributed trace/correlation giúp nối parent request và child dependencies.

## 4. Practical implementation

```csharp
builder.Services.AddApplicationInsightsTelemetry();
```

Kết hợp OpenTelemetry instrumentation khi architecture cần vendor-neutral telemetry. Custom spans chỉ nên thêm cho meaningful operations.

## 5. Real production scenario

Product API p95 tăng từ 400ms lên 2.5s. CPU và SQL bình thường; dependency duration cho review provider tăng mạnh sau 14:00.

## 6. Failure scenario & troubleshooting

**Symptom** → request latency tăng. **Evidence** → dependency p95 tăng ở một target. **Hypothesis** → remote dependency regression. **Diagnosis** → trace samples, status codes, network timing, deployment timeline. **Fix** → timeout/fallback/cache hoặc provider remediation. **Verification** → request p95 và dependency p95 hồi phục.

## 7. Common mistakes

Chỉ query exceptions; không có operation correlation; log full sensitive URLs; custom telemetry cardinality cao; nhìn average thay p95/p99.

## 8. Alternatives

OpenTelemetry + collector/exporter cho portability. Logs vẫn hữu ích cho events; metrics cho aggregate health; traces cho causal path.

## 9. Trade-offs

### Advantages

Localize bottleneck nhanh và hỗ trợ distributed RCA.

### Costs / Risks

Telemetry volume/cost, sampling và privacy governance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu request/dependency telemetry.

### Middle
Đi từ slow request tới child dependency.

### Senior
Correlate traces, metrics và deployment changes.

### Technical Lead / Architect
Định nghĩa telemetry conventions/SLOs để incident investigation không phụ thuộc tribal knowledge.

## 11. Key takeaway

- Latency phải được phân rã theo critical path.
- Logs, metrics và traces bổ sung nhau.
- Telemetry cần correlation và bounded cardinality.

# 10. Contract Testing: bảo vệ integration boundary mà không cần E2E khổng lồ

## 1. What is it?

Contract testing xác minh consumer và provider đồng ý về interface: endpoint, schema, required fields, status/error semantics. Mental model: test boundary assumptions thay vì dựng toàn bộ system cho mọi case.

## 2. Why does it exist?

Unit tests có thể xanh ở cả hai services nhưng integration vẫn vỡ vì provider rename field hoặc thay nullable semantics. Full E2E phát hiện được nhưng chậm, brittle và khó cover mọi consumer expectation.

## 3. How does it work?

```text
Consumer expectation
        ↓ contract
Provider verification
        ↓
compatible release? yes/no
```

Contract không thay thế business integration test; nó tập trung compatibility boundary.

## 4. Practical implementation

Ví dụ consumer phụ thuộc response:

```json
{
  "id": "ORD-42",
  "status": "approved"
}
```

Provider verification phải chứng minh endpoint vẫn cung cấp fields/types/status semantics consumer cần. OpenAPI schema validation hoặc consumer-driven contract tooling có thể automate phần này.

## 5. Real production scenario

Order API đổi `status` từ string sang nested object. Provider unit tests xanh; mobile/backend consumer fail production. Contract gate có thể chặn breaking release trước deployment.

## 6. Failure scenario & troubleshooting

**Symptom** → contract tests xanh nhưng production integration fail. **Evidence** → failure nằm ở authentication, network policy hoặc behavioral sequence không nằm trong contract. **Hypothesis** → contract scope quá hẹp. **Diagnosis** → xác định assumption bị thiếu. **Fix** → bổ sung integration test đúng layer, không biến contract suite thành full E2E. **Verification** → regression tái hiện đúng failure.

## 7. Common mistakes

Snapshot toàn response khiến test brittle; provider tự viết cả expectation nên bỏ sót consumer reality; contract chứa implementation details; nghĩ contract tests thay thế integration/E2E.

## 8. Alternatives

Integration tests với real provider phù hợp ít dependencies. E2E cần cho critical journeys. OpenAPI compatibility checks tốt cho schema-level backward compatibility.

## 9. Trade-offs

### Advantages

Feedback nhanh về breaking changes và ownership rõ giữa teams.

### Costs / Risks

Contract lifecycle/tooling, false confidence nếu behavior ngoài schema không được test.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu API schema là shared contract.

### Middle
Viết tests cho required consumer assumptions.

### Senior
Phân biệt schema, behavioral integration và E2E risks.

### Technical Lead / Architect
Thiết kế compatibility gates phù hợp deployment independence và team ownership.

## 11. Key takeaway

- Contract tests bảo vệ integration assumptions, không phải toàn hệ thống.
- Test đúng boundary giúp giảm E2E brittleness.
- Compatibility phải được kiểm tra trước release, không đợi production.
