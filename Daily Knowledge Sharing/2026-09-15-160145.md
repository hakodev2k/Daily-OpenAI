# 1. C# `Span<T>` và `Memory<T>`: giảm allocation trên hot path nhưng không biến mọi code thành low-level code

## 1. What is it?

`Span<T>` là view liên tục trên một vùng memory mà không cần copy dữ liệu. Nó có thể trỏ vào array, stack memory hoặc một slice của buffer. Vì là `ref struct`, `Span<T>` bị giới hạn để không sống lâu hơn vùng memory mà nó tham chiếu. `Memory<T>` có mental model tương tự nhưng có thể sống trên heap và đi qua asynchronous boundary.

## 2. Why does it exist?

Các thao tác parsing thường tạo nhiều substring/temporary arrays. Trên hot path, allocation nhỏ nhưng lặp hàng triệu lần tạo GC pressure. `Span<T>` cho phép xử lý slice của dữ liệu gốc mà không copy.

## 3. How does it work?

```text
Original buffer: [A][B][C][D][E][F]
                    └──── Span ────┘
```

Slice chỉ mang reference + offset/length. Nó không tạo một buffer mới.

## 4. Practical implementation

```csharp
static bool TryParsePair(ReadOnlySpan<char> input, out int left, out int right)
{
    var separator = input.IndexOf(':');
    if (separator < 0)
    {
        left = right = 0;
        return false;
    }

    return int.TryParse(input[..separator], out left)
        && int.TryParse(input[(separator + 1)..], out right);
}
```

Không cần `Substring` cho hai phần.

## 5. Real production scenario

Một ingestion service parse hàng trăm nghìn records/second. Profiling cho thấy phần đáng kể allocation đến từ slicing strings và byte arrays. Sau khi chuyển đúng hot parser sang span-based APIs, allocation rate giảm và Gen0 GC ít hơn. Team không rewrite business services vì chúng không nằm trên bottleneck.

## 6. Failure scenario & troubleshooting

**Symptom** → code phức tạp hơn nhưng latency gần như không đổi. **Evidence** → profiler cho thấy parser chỉ chiếm 1% request time. **Diagnosis** → tối ưu sai bottleneck. **Fix** → quay lại measure CPU/allocation profile và chỉ dùng low-allocation APIs nơi có bằng chứng. **Verification** → benchmark end-to-end, không chỉ microbenchmark.

## 7. Common mistakes

* Dùng `Span<T>` ở mọi nơi vì nghĩ allocation luôn là vấn đề lớn.
* Cố giữ `Span<T>` qua `await`.
* Benchmark Debug build.
* Giảm allocation nhưng tăng CPU do parsing phức tạp hơn.

## 8. Alternatives

String/array APIs thường rõ hơn và hoàn toàn đủ cho normal business code. `ArrayPool<T>` phù hợp buffer lớn cần reuse; `Memory<T>` phù hợp asynchronous APIs.

## 9. Trade-offs

### Advantages

Giảm copying và allocations; phù hợp parser, serializer, protocol handling.

### Costs / Risks

API khó đọc hơn, lifetime rules chặt hơn và dễ tạo premature optimization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu slice khác copy.
### Middle
Biết dùng `ReadOnlySpan<T>` với parsing APIs.
### Senior
Dùng profiler/BenchmarkDotNet để chứng minh benefit và hiểu lifetime constraints.
### Technical Lead / Architect
Giữ low-level optimization trong boundary hẹp, không để performance technique làm giảm maintainability toàn codebase.

## 11. Key takeaway

* `Span<T>` có giá trị khi copying/allocation thật sự là bottleneck.
* `Memory<T>` phù hợp lifetime dài/asynchronous hơn.
* Measure trước khi đổi readability lấy micro-optimization.

# 2. ASP.NET Core graceful shutdown: drain request, propagate cancellation và tránh mất work khi instance bị terminate

## 1. What is it?

Graceful shutdown là quá trình application ngừng nhận work mới, cho work đang chạy cơ hội hoàn tất trong một khoảng giới hạn rồi đóng resources có kiểm soát.

## 2. Why does it exist?

Container restart, App Service recycle và rolling deployment là behavior bình thường. Nếu process bị kill giữa transaction, upload hoặc message handling, user có thể thấy request reset và work có thể bị xử lý dở dang.

## 3. How does it work?

```text
Termination signal
  ↓
Host stopping token cancelled
  ↓
Stop accepting/drain traffic
  ↓
In-flight work finishes or observes cancellation
  ↓
Hosted services stop
  ↓
Process exits
```

Graceful không có nghĩa chờ vô hạn. Platform luôn có termination deadline.

## 4. Practical implementation

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var item = await ReceiveAsync(stoppingToken);
            await ProcessAsync(item, stoppingToken);
        }
    }
}
```

Request handlers cũng phải propagate `CancellationToken` xuống EF Core/HttpClient khi cancellation thực sự có ý nghĩa.

## 5. Real production scenario

Một rolling deployment thay 10 API instances. Nếu readiness bị remove trước khi termination và request có vài giây để hoàn tất, phần lớn traffic không nhận ra deployment. Nếu instance vẫn nhận request tới sát lúc kill, tail requests dễ reset.

## 6. Failure scenario & troubleshooting

**Symptom** → 499/502 spike đúng lúc deploy. **Evidence** → timestamps trùng pod/App Service recycle; request duration vượt shutdown window. **Hypothesis** → drain không đủ hoặc downstream call không cancellable. **Fix** → align platform termination grace period, readiness removal, server shutdown timeout và operation design. **Verification** → controlled rolling deployment dưới load.

## 7. Common mistakes

* Nuốt `OperationCanceledException` rồi retry vô hạn khi host đang shutdown.
* Bắt đầu long-running background work từ HTTP request mà không durable queue.
* Giả định platform chờ process mãi.
* Cancellation xảy ra sau DB commit nhưng code coi toàn operation như chưa chạy.

## 8. Alternatives

Durable queue phù hợp work cần sống qua process lifetime. Short synchronous request có thể chỉ cần standard host shutdown behavior.

## 9. Trade-offs

### Advantages
Giảm request loss và deployment disruption.
### Costs / Risks
Shutdown chậm làm rollout chậm; cancellation semantics phức tạp với side effects.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu process có thể dừng bất cứ lúc nào.
### Middle
Propagate cancellation và dispose resources đúng.
### Senior
Thiết kế idempotency cho work có thể bị cắt giữa chừng.
### Technical Lead / Architect
Đồng bộ application lifecycle với load balancer, orchestrator, durable messaging và deployment policy.

## 11. Key takeaway

* Restart là normal production event.
* Graceful shutdown cần cả traffic draining và cancellation-aware code.
* Work quan trọng dài hạn nên durable, không phụ thuộc process sống mãi.

# 3. EF Core split query: kiểm soát Cartesian explosion khi load nhiều collection navigation

## 1. What is it?

Split query cho phép EF Core load một object graph bằng nhiều SQL queries thay vì một JOIN query khổng lồ khi có nhiều collection `Include`.

## 2. Why does it exist?

Nếu `Order` có 20 Lines và 10 Notes, join cả hai collections có thể tạo khoảng 200 result rows cho một Order. Parent columns bị lặp lại, network payload tăng và materialization tốn memory.

## 3. How does it work?

Single query:

```text
Orders JOIN Lines JOIN Notes
→ cross multiplication
```

Split query:

```text
Query Orders
Query Lines for selected Orders
Query Notes for selected Orders
→ EF fixes relationships in memory
```

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .AsNoTracking()
    .ToListAsync(cancellationToken);
```

Nếu API chỉ cần summary, projection thường tốt hơn cả hai:

```csharp
var result = await db.Orders.Select(x => new
{
    x.Id,
    LineCount = x.Lines.Count,
    x.Total
}).ToListAsync(cancellationToken);
```

## 5. Real production scenario

Order details endpoint thêm promotions và audit entries. Sau release, response chậm dù indexes không đổi. Generated SQL có nhiều sibling collection joins và trả hàng chục nghìn rows để tạo vài chục entities.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL duration vừa phải nhưng network bytes/materialization CPU lớn. **Evidence** → result row count vượt xa entity count. **Diagnosis** → Cartesian explosion. **Fix** → projection hoặc `AsSplitQuery`. **Verification** → đo SQL rows, bytes, application allocation và end-to-end latency.

## 7. Common mistakes

* Dùng `Include` như mặc định cho mọi navigation.
* Chuyển sang split query mà không cân nhắc extra round trips.
* Load full graph cho list endpoint chỉ cần 5 fields.

## 8. Alternatives

Projection là lựa chọn tốt nhất cho read DTO; explicit loading phù hợp conditional detail; single query vẫn tốt cho graph nhỏ.

## 9. Trade-offs

### Advantages
Giảm row multiplication và duplicated payload.
### Costs / Risks
Nhiều database round trips hơn; consistency giữa queries cần được hiểu nếu concurrent writes xảy ra.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `Include` biến thành database access thật.
### Middle
Inspect generated SQL và dùng projection/split query.
### Senior
Đánh giá round trips, consistency và materialization cost.
### Technical Lead / Architect
Thiết kế read model/API contract để tránh object graph vô hạn trở thành persistence contract.

## 11. Key takeaway

* Nhiều sibling collection joins có thể nhân result set.
* `AsSplitQuery` là tool, không phải default universal.
* Projection thường rõ và rẻ nhất cho read APIs.

# 4. SQL Server isolation levels: consistency, blocking và versioning dưới concurrent workload

## 1. What is it?

Isolation level quy định transaction được phép quan sát thay đổi concurrent ở mức nào và database dùng locking/versioning ra sao để duy trì contract đó.

## 2. Why does it exist?

Concurrency tạo tension giữa consistency và throughput. Nếu mọi transaction serialize hoàn toàn, correctness dễ reasoning nhưng blocking cao. Nếu đọc quá tự do, application có thể thấy dữ liệu chưa commit hoặc không ổn định.

## 3. How does it work?

`READ COMMITTED` thường ngăn dirty read. `REPEATABLE READ` giữ read locks lâu hơn. `SERIALIZABLE` bảo vệ cả key ranges. `SNAPSHOT` đọc row versions để giảm reader/writer blocking nhưng có version-store cost và write-conflict semantics riêng.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(
    System.Data.IsolationLevel.Serializable,
    cancellationToken);

// Critical invariant check + write
await tx.CommitAsync(cancellationToken);
```

Không nên nâng isolation chỉ vì gặp một bug concurrency mà chưa hiểu invariant.

## 5. Real production scenario

Hai requests cùng kiểm tra “còn 1 slot” rồi insert reservation. Ở isolation không phù hợp, cả hai có thể vượt invariant nếu check và write không được bảo vệ bằng constraint/transaction strategy thích hợp.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng và deadlocks sau khi đổi isolation. **Evidence** → blocking chains/range locks dài. **Hypothesis** → transaction scope quá lớn. **Diagnosis** → execution plans, lock waits, deadlock graph. **Fix** → rút ngắn transaction, index access path, dùng constraint/optimistic strategy hoặc versioning phù hợp. **Verification** → concurrent load test.

## 7. Common mistakes

* Dùng `NOLOCK` như performance switch.
* Transaction bao gồm HTTP call.
* Chọn `SERIALIZABLE` toàn hệ thống để “an toàn”.
* Không dùng database constraint cho invariant có thể enforce trực tiếp.

## 8. Alternatives

Optimistic concurrency phù hợp user edits; unique/check constraints tốt cho invariants đơn giản; application serialization/queue phù hợp một số hot workflow.

## 9. Trade-offs

### Advantages
Isolation mạnh giúp reasoning consistency tốt hơn.
### Costs / Risks
Locks/version storage, blocking, deadlock và throughput cost tăng tùy strategy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu transaction không chỉ là commit/rollback.
### Middle
Biết isolation ảnh hưởng reads/writes concurrent.
### Senior
Đọc lock waits/deadlock graph và chọn boundary theo invariant.
### Technical Lead / Architect
Quyết định consistency requirement theo business, không theo thói quen database.

## 11. Key takeaway

* Isolation là business-correctness/performance trade-off.
* Transaction scope càng dài càng tăng contention.
* Constraint đúng thường đáng tin hơn application check đơn lẻ.

# 5. Elasticsearch alias + reindex: thay mapping/index mà không buộc Search API downtime

## 1. What is it?

Alias là tên logic trỏ tới một hoặc nhiều Elasticsearch indices. Application query alias thay vì hard-code physical index name. Điều này cho phép tạo index version mới, reindex dữ liệu rồi atomically đổi alias.

## 2. Why does it exist?

Một số mapping changes không thể áp dụng in-place an toàn. Nếu application phụ thuộc trực tiếp `products-v1`, migration buộc coordinated code/config change và có thể downtime.

## 3. How does it work?

```text
Search API → products-read → products-v1
                         reindex ↓
                              products-v2
Alias switch: products-read → products-v2
```

Primary database vẫn là source of truth; synchronization mechanism phải xử lý writes xảy ra trong thời gian reindex.

## 4. Practical implementation

Tạo `products-v2` với mapping mới, bulk index/backfill, validate counts/query quality, sau đó đổi alias bằng một aliases operation. Search API không cần biết physical index đổi tên.

## 5. Real production scenario

Product search cần analyzer mới cho multilingual fields. Team build v2 song song, backfill từ SQL và replay changes từ event stream trước khi switch alias. Nếu relevance regression xuất hiện, alias có thể chuyển lại v1 miễn data synchronization vẫn được duy trì.

## 6. Failure scenario & troubleshooting

**Symptom** → sau switch, một số sản phẩm mới biến mất. **Evidence** → backfill snapshot kết thúc nhưng writes phát sinh trong migration chưa vào v2. **Hypothesis** → synchronization gap. **Fix** → dual-write/change stream/replay cursor có checkpoint rõ ràng. **Verification** → compare IDs/version watermark giữa primary DB và new index.

## 7. Common mistakes

* Chỉ so document count, không test search semantics.
* Xóa v1 ngay sau switch.
* Không có strategy cho concurrent writes.
* Dùng Elasticsearch như transactional source of truth.

## 8. Alternatives

In-place update phù hợp setting/mapping change được hỗ trợ; blue-green index phù hợp breaking mapping; managed search platforms có deployment abstractions khác nhưng consistency problem vẫn tồn tại.

## 9. Trade-offs

### Advantages
Migration/rollback ít downtime, application decoupled khỏi physical index.
### Costs / Risks
Tạm thời cần double storage và synchronization phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu alias là logical indirection.
### Middle
Biết create/reindex/switch và validate.
### Senior
Thiết kế catch-up strategy và rollback.
### Technical Lead / Architect
Quyết định source of truth, ownership và migration protocol cho search platform.

## 11. Key takeaway

* Alias giải coupling giữa API và physical index.
* Reindex correctness phụ thuộc xử lý concurrent changes.
* Search migration cần validate relevance, không chỉ row count.

# 6. Hexagonal Architecture và anti-corruption boundary: cô lập third-party integration khỏi domain model

## 1. What is it?

Hexagonal Architecture tổ chức system quanh application/domain core và các ports mô tả capability cần thiết. Adapters triển khai ports để nói chuyện với HTTP, SQL, broker hoặc vendor APIs. Anti-corruption layer dịch external model sang internal model thay vì để vendor semantics lan vào domain.

## 2. Why does it exist?

Third-party contracts thay đổi theo ownership khác. Nếu `VendorCustomerDto`, status code và SDK types xuất hiện khắp domain, một vendor migration trở thành codebase-wide rewrite.

## 3. How does it work?

```text
Domain/Application
      ↓ port
IReviewProvider
      ↑
VendorReviewAdapter
      ↓
External Review API
```

Dependency hướng vào abstraction do application sở hữu; adapter chịu trách nhiệm mapping, timeout, retry và vendor-specific behavior.

## 4. Practical implementation

```csharp
public interface IReviewProvider
{
    Task<ProductRating?> GetRatingAsync(
        string productId,
        CancellationToken cancellationToken);
}

public sealed class VendorReviewAdapter(HttpClient client) : IReviewProvider
{
    public async Task<ProductRating?> GetRatingAsync(
        string productId,
        CancellationToken ct)
    {
        var dto = await client.GetFromJsonAsync<VendorRatingDto>(
            $"ratings/{productId}", ct);

        return dto is null ? null : new ProductRating(dto.Score, dto.Count);
    }
}
```

## 5. Real production scenario

E-commerce site thay review provider. Với adapter boundary, domain/product page logic vẫn dùng `ProductRating`; chỉ integration adapter và mapping thay đổi. Nếu vendor-specific concepts đã nằm trong core entities, migration đắt hơn nhiều.

## 6. Failure scenario & troubleshooting

**Symptom** → vendor thêm status mới làm domain throw exception. **Evidence** → switch expression trên external enum nằm trong domain. **Diagnosis** → boundary leakage. **Fix** → mapping unknown/external states trong adapter thành internal semantics có chủ đích. **Verification** → contract tests với unknown/new fields.

## 7. Common mistakes

* Tạo interface cho mọi class dù không có boundary thật.
* Domain reference vendor SDK package.
* Adapter chỉ proxy 1:1 nên không tạo isolation giá trị.
* Che mất useful vendor capabilities vì abstraction quá generic.

## 8. Alternatives

Simple layered architecture đủ cho CRUD nhỏ; direct SDK usage hợp lý nếu integration nhỏ và replacement risk thấp; ACL đáng giá khi external semantics khác domain đáng kể.

## 9. Trade-offs

### Advantages
Change isolation, testability, vendor migration dễ hơn.
### Costs / Risks
Mapping code và abstraction overhead; abstraction kém có thể thành lowest-common-denominator.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu domain không nên biết mọi vendor detail.
### Middle
Implement adapter và mapping rõ ràng.
### Senior
Thiết kế port theo business capability thay vì SDK methods.
### Technical Lead / Architect
Quyết định boundary nào đáng trả abstraction cost và ownership của failure policy.

## 11. Key takeaway

* Architecture boundary bảo vệ change, không phải folder convention.
* Port nên nói ngôn ngữ application/domain.
* Không cần abstraction nếu dependency nhỏ và change risk thấp.

# 7. Azure Blob Storage large-file upload: streaming, SAS và lifecycle thay vì đưa toàn file qua application memory

## 1. What is it?

Azure Blob Storage là object storage phù hợp file lớn, media, exports và documents. Large-file architecture cần quyết định data path: client upload qua API hay trực tiếp tới Blob bằng scoped SAS.

## 2. Why does it exist?

Nếu 500 MB upload đi `Client → API memory → Blob`, application chịu bandwidth, connection duration và memory/buffer pressure dù nó không cần inspect bytes.

## 3. How does it work?

Direct upload pattern:

```text
Client → API: request upload authorization
API → Client: short-lived scoped SAS
Client → Blob Storage: upload bytes
Client/API → finalize metadata
```

Managed Identity nên dùng cho server-side Blob access; SAS dành quyền hạn hẹp cho client trong thời gian ngắn.

## 4. Practical implementation

Server-side streaming khi bắt buộc inspect content:

```csharp
await blobClient.UploadAsync(
    request.Body,
    overwrite: false,
    cancellationToken);
```

Không `CopyToAsync(new MemoryStream())` toàn file trước khi upload nếu không cần random access.

## 5. Real production scenario

CMS cho editor upload video lớn. API instances bị memory spike vì buffering multipart file. Team chuyển video path sang direct-to-Blob SAS, còn API chỉ cấp authorization và lưu metadata sau finalize.

## 6. Failure scenario & troubleshooting

**Symptom** → orphan blobs tồn tại khi client upload xong nhưng không finalize metadata. **Evidence** → blobs không có DB record. **Diagnosis** → two-step workflow có partial failure. **Fix** → upload vào temporary prefix/container, lifecycle cleanup và idempotent finalize. **Verification** → simulate client crash giữa upload/finalize.

## 7. Common mistakes

* SAS lifetime quá dài/quyền quá rộng.
* Public container cho private documents.
* Load toàn file vào RAM.
* Không có cleanup incomplete/orphan uploads.

## 8. Alternatives

API proxy phù hợp file nhỏ hoặc cần synchronous validation; direct Blob phù hợp file lớn; background scanning phù hợp malware/content validation sau upload.

## 9. Trade-offs

### Advantages
Giảm app bandwidth/memory, tận dụng storage scalability.
### Costs / Risks
Workflow nhiều bước, SAS security và orphan cleanup cần thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu object storage khác database blob column.
### Middle
Stream file và cấu hình content type/metadata.
### Senior
Thiết kế SAS scope, retry, block upload và cleanup.
### Technical Lead / Architect
Chọn data path dựa trên security, size, compliance, scanning và cost.

## 11. Key takeaway

* Large files không nên mặc định đi qua application memory.
* SAS phải short-lived và least privilege.
* Partial upload/finalize failure là workflow cần xử lý chủ động.

# 8. Kubernetes readiness vs liveness probe: tránh biến dependency outage thành restart storm

## 1. What is it?

Readiness trả lời: pod hiện có nên nhận traffic không? Liveness trả lời: process có bị kẹt đến mức restart là cách recovery đúng không?

Hai câu hỏi khác nhau và không nên dùng cùng một dependency check một cách máy móc.

## 2. Why does it exist?

Một process có thể đang sống nhưng chưa ready vì startup/warmup. Ngược lại, database outage không nhất thiết có nghĩa restart mọi API pods sẽ sửa được database.

## 3. How does it work?

```text
Readiness fail → remove pod from Service endpoints
Liveness fail  → kubelet restarts container
```

Startup probe có thể bảo vệ app khởi động chậm khỏi bị liveness kill quá sớm.

## 4. Practical implementation

ASP.NET Core có thể tách health checks bằng tags:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<SelfHealthCheck>("self", tags: ["live"])
    .AddSqlServer(connectionString, tags: ["ready"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = x => x.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = x => x.Tags.Contains("ready")
});
```

## 5. Real production scenario

SQL outage kéo dài 5 phút. Nếu liveness endpoint check SQL, mọi pods liên tục restart. Startup cost, log noise và reconnect storm làm recovery khó hơn. Nếu SQL chỉ ảnh hưởng readiness theo policy phù hợp, pods có thể ngừng nhận traffic nhưng process không bị restart vô ích.

## 6. Failure scenario & troubleshooting

**Symptom** → `CrashLoopBackOff` trong dependency outage. **Evidence** → liveness failures trùng SQL timeout. **Diagnosis** → liveness phụ thuộc external service. **Fix** → liveness chỉ kiểm tra process self-health; readiness phản ánh serving capability. **Verification** → simulate dependency outage và quan sát pod không restart storm.

## 7. Common mistakes

* Cùng endpoint cho live/ready.
* Probe timeout quá ngắn so với startup behavior.
* Health check tạo expensive DB query.
* Readiness fail vì optional dependency dù API vẫn có fallback.

## 8. Alternatives

App Service health checks có semantics platform khác; VM/process supervisors chỉ restart process nhưng không có Service endpoint routing giống Kubernetes.

## 9. Trade-offs

### Advantages
Tự động traffic isolation và recovery tốt hơn.
### Costs / Risks
Probe sai nguy hiểm hơn không probe: có thể tự tạo outage/restart storm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt alive và ready.
### Middle
Tạo endpoints/probes riêng.
### Senior
Phân loại critical vs optional dependencies và tune thresholds.
### Technical Lead / Architect
Định nghĩa health semantics phù hợp degradation strategy và orchestrator behavior.

## 11. Key takeaway

* Liveness không phải dependency monitor.
* Readiness là quyết định routing traffic.
* Probe design là reliability logic.

# 9. Playwright E2E testing: bảo vệ critical user journey mà không xây test suite chậm và flaky

## 1. What is it?

Playwright điều khiển browser thật để kiểm tra behavior end-to-end: rendering, JavaScript, network, authentication và user interaction. E2E test bảo vệ integration giữa nhiều layers mà unit test không nhìn thấy.

## 2. Why does it exist?

Unit tests có thể pass trong khi login redirect sai, API CORS fail, button không bind event hoặc frontend/backend contract mismatch. E2E test kiểm tra journey gần với user thật.

## 3. How does it work?

```text
Test runner → Browser → Frontend → API → DB/test environment
```

Do nhiều components tham gia, test chậm và dễ nondeterministic hơn unit/integration tests. Vì vậy số lượng cần chọn theo risk.

## 4. Practical implementation

```typescript
import { test, expect } from '@playwright/test';

test('user can submit timesheet', async ({ page }) => {
  await page.goto('/timesheets/new');
  await page.getByLabel('Hours').fill('8');
  await page.getByRole('button', { name: 'Submit' }).click();
  await expect(page.getByText('Submitted')).toBeVisible();
});
```

Ưu tiên role/label selectors thay vì brittle CSS hierarchy.

## 5. Real production scenario

Release thay authentication callback route. Backend integration tests vẫn pass nhưng browser redirect loop. Một E2E smoke test cho login + critical action bắt regression trước production.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail ngẫu nhiên CI nhưng pass local. **Evidence** → fixed `waitForTimeout(3000)` và shared test data. **Hypothesis** → timing/data race. **Fix** → await observable UI/network state, isolate data, capture trace/video/screenshot khi fail. **Verification** → chạy repeated CI executions.

## 7. Common mistakes

* Test mọi validation branch bằng E2E.
* Fixed sleeps.
* Shared account/state giữa parallel tests.
* Mock mọi API khiến test không còn end-to-end.

## 8. Alternatives

Unit tests bảo vệ logic nhanh; integration tests bảo vệ API/database contracts; contract tests bảo vệ service boundaries. E2E dành cho critical cross-layer journeys.

## 9. Trade-offs

### Advantages
Confidence cao cho user flow thực.
### Costs / Risks
Chậm, infrastructure-heavy và dễ flaky nếu thiết kế kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu E2E không thay unit test.
### Middle
Viết stable selectors và deterministic setup.
### Senior
Thiết kế test pyramid theo risk và debug flakiness bằng trace evidence.
### Technical Lead / Architect
Chọn critical journeys, execution gates và ownership để CI feedback vẫn nhanh.

## 11. Key takeaway

* E2E có giá trị cao nhưng cost cao.
* Stable synchronization/data isolation quan trọng hơn thêm retries.
* Test đúng critical journeys thay vì duplicate mọi lower-level test.

# 10. Production SLO và error budget: biến reliability thành constraint kỹ thuật có thể đo thay vì cảm giác “hệ thống khá ổn”

## 1. What is it?

SLI là chỉ số đo reliability thực tế, ví dụ tỷ lệ successful requests dưới một latency threshold. SLO là target cho SLI trong một window. Error budget là phần failure được phép trước khi vi phạm SLO.

Ví dụ: SLO 99.9% availability trong 30 ngày cho phép khoảng 0.1% unsuccessful service time/requests theo cách đo đã định nghĩa.

## 2. Why does it exist?

Nếu target chỉ là “100% uptime”, team dễ overengineer hoặc không có cách cân bằng feature velocity với reliability. SLO tạo một contract kỹ thuật đủ cụ thể để alert và ra quyết định.

## 3. How does it work?

```text
User expectation
   ↓
SLI definition
   ↓
SLO target/window
   ↓
Error budget
   ↓
Alerts + release/reliability decisions
```

Một useful SLI phải gần user experience. CPU < 80% là infrastructure metric, không trực tiếp là availability SLI.

## 4. Practical implementation

Ví dụ SLI cho API:

```text
Good event:
HTTP response is 2xx/3xx AND duration < 750 ms

Eligible event:
All non-health-check API requests

SLO:
99.5% good events over rolling 28 days
```

Application Insights/OpenTelemetry metrics có thể aggregate request count, failures và latency distribution để tính burn rate.

## 5. Real production scenario

Team có nhiều alerts CPU/memory nhưng user phàn nàn checkout chậm mà không alert. Sau khi định nghĩa checkout SLI theo successful requests dưới 2 giây, alert bám trực tiếp vào user-visible reliability. Một CPU spike không ảnh hưởng SLO có thể điều tra với priority thấp hơn; dependency latency làm burn budget nhanh được ưu tiên ngay.

## 6. Failure scenario & troubleshooting

**Symptom** → SLO dashboard xanh nhưng khách hàng vẫn báo lỗi. **Evidence** → SLI loại trừ timeout ở CDN/gateway vì chỉ đo request vào application. **Hypothesis** → measurement boundary sai. **Diagnosis** → so client/edge telemetry với server telemetry. **Fix** → định nghĩa eligible events tại boundary gần user hơn. **Verification** → replay known incident và kiểm tra SLI phản ánh degradation.

## 7. Common mistakes

* Dùng infrastructure utilization làm SLO.
* Chọn 99.99% vì “nghe tốt” mà không tính architecture/cost.
* Alert trên mọi single failure thay vì burn rate.
* SLO không phân biệt critical và non-critical journeys.

## 8. Alternatives

SLA là external/business commitment và thường khác SLO nội bộ. Traditional threshold alerts vẫn cần cho component diagnostics nhưng không thay user-centric SLO.

## 9. Trade-offs

### Advantages
Reliability measurable, prioritization rõ và alert gần user impact hơn.
### Costs / Risks
SLI design sai tạo false confidence; telemetry/storage và governance có cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt metric, SLI, SLO và SLA.
### Middle
Instrument request success/latency đúng.
### Senior
Thiết kế burn-rate alerts và correlate logs/metrics/traces trong incident.
### Technical Lead / Architect
Chọn SLO theo business criticality, architecture capability và cost; dùng error budget để cân bằng release với reliability work.

## 11. Key takeaway

* SLO phải đo điều user thực sự cảm nhận.
* Error budget biến reliability thành trade-off có thể quản lý.
* Observability tốt cần logs + metrics + traces, nhưng SLO cung cấp mục tiêu để biết tín hiệu nào quan trọng.
