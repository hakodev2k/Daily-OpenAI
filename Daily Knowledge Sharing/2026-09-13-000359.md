# 1. C# `System.Threading.Channels`: bounded queue, backpressure và vì sao producer nhanh hơn consumer là reliability problem

## 1. What is it?

`System.Threading.Channels` cung cấp asynchronous producer/consumer queue trong .NET. Mental model quan trọng không phải “một collection thread-safe”, mà là một **buffer nằm giữa hai tốc độ xử lý khác nhau**:

```text
Producer(s) -> Channel -> Consumer(s)
     500/s       ?          120/s
```

Nếu channel unbounded, producer có thể tiếp tục ghi nhanh hơn consumer và memory tăng không giới hạn. Với bounded channel, hệ thống phải quyết định điều gì xảy ra khi buffer đầy: chờ, drop hoặc reject.

## 2. Why does it exist?

Producer và consumer hiếm khi có throughput giống nhau. Nếu request thread trực tiếp làm mọi công việc phụ, latency tăng. Nếu chỉ `Task.Run` fire-and-forget, application mất ownership của work. Channel cho phép tách intake và processing trong cùng process nhưng vẫn có một coordination primitive rõ ràng.

Backpressure tồn tại để nói với upstream rằng downstream đã đạt capacity. Không có backpressure, overload thường chỉ bị trì hoãn cho tới khi memory, ThreadPool hoặc dependency sụp đổ.

## 3. How does it work?

Bounded channel có capacity hữu hạn:

```text
write -> [1][2][3][4][5] -> read
           capacity = 5
```

Khi đầy, `BoundedChannelFullMode.Wait` khiến `WriteAsync` chờ space. Các mode khác có thể drop newest/oldest/write. Đây là business/reliability decision, không chỉ configuration.

`ChannelReader<T>` và `ChannelWriter<T>` tách trách nhiệm đọc/ghi. `ReadAllAsync(stoppingToken)` rất phù hợp với `BackgroundService`.

## 4. Practical implementation

```csharp
builder.Services.AddSingleton(_ =>
    Channel.CreateBounded<EmailJob>(
        new BoundedChannelOptions(500)
        {
            FullMode = BoundedChannelFullMode.Wait,
            SingleReader = false,
            SingleWriter = false
        }));

public sealed class EmailWorker(
    Channel<EmailJob> channel,
    IEmailSender sender) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        await foreach (var job in channel.Reader.ReadAllAsync(ct))
        {
            await sender.SendAsync(job, ct);
        }
    }
}
```

Producer phải dùng `WriteAsync`, không nên `TryWrite` rồi bỏ qua `false` nếu work không được phép mất.

## 5. Real production scenario

API import CSV nhận 20.000 records và enqueue validation work. Bình thường consumer xử lý 300 records/s. Khi database latency tăng, consumer giảm còn 40/s. Unbounded queue khiến memory từ 400 MB lên nhiều GB. Bounded channel capacity 1.000 khiến producer chậm lại và API có thể chuyển sang durable job model thay vì giả vờ hệ thống vẫn khỏe.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng, GC nhiều, request vẫn accept nhưng processing lag hàng phút.

**Evidence** → queue depth tăng liên tục; producer rate > consumer rate; dependency latency tăng.

**Hypothesis** → hệ thống không có effective backpressure.

**Diagnosis** → đo queue depth, enqueue wait time, throughput từng consumer và downstream latency.

**Fix** → bound capacity, giới hạn concurrency, reject/defer workload khi cần; nếu work phải sống qua restart, chuyển sang Azure Service Bus hoặc durable queue.

**Verification** → load test với downstream chậm hơn producer và xác nhận memory bounded, latency/rejection predictable.

## 7. Common mistakes

- Dùng unbounded channel mặc định cho workload không giới hạn.
- Drop message mà không metric/log.
- Tăng số consumer vượt quá database connection capacity.
- Xem in-memory channel như durable queue.
- Không hoàn tất writer hoặc handle shutdown.

## 8. Alternatives

`ConcurrentQueue<T>` đơn giản hơn nhưng thiếu async waiting/backpressure semantics. Azure Service Bus phù hợp khi cần durability, multi-instance processing và recovery sau restart. `BackgroundService` + Channel phù hợp cho transient in-process work có thể mất hoặc tái tạo.

## 9. Trade-offs

### Advantages

- Async producer/consumer hiệu quả.
- Backpressure explicit.
- Ít infrastructure hơn external broker.

### Costs / Risks

- Không durable.
- Capacity/concurrency phải tune.
- Scale nhiều application instances tạo nhiều independent queues.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue không làm workload biến mất; nó chỉ dời thời điểm xử lý.

### Middle

Implement bounded channel, cancellation và worker lifecycle đúng.

### Senior

Đo producer/consumer rate, queue depth và downstream saturation; chọn full mode theo semantics.

### Technical Lead / Architect

Quyết định khi nào in-process buffering đủ và khi nào business durability buộc phải dùng external messaging.

## 11. Key takeaway

- Queue depth là dấu hiệu chênh lệch throughput, không phải capacity miễn phí.
- Bounded channel buộc overload trở thành một behavior có kiểm soát.
- Work cần survive restart không nên chỉ nằm trong memory.

# 2. ASP.NET Core Rate Limiting: reject, queue và partition request theo client thay vì chỉ “giới hạn requests/second”

## 1. What is it?

Rate limiting kiểm soát lượng work được phép đi qua một boundary trong một khoảng thời gian hoặc tại cùng một thời điểm. ASP.NET Core có middleware hỗ trợ fixed window, sliding window, token bucket và concurrency limiter.

Mental model đúng là **protect scarce capacity**, không phải chỉ chống bot.

## 2. Why does it exist?

Một API có thể xử lý 2.000 lightweight requests/s nhưng chỉ 50 concurrent report queries trước khi SQL pool bị bão hòa. Nếu tất cả client share cùng limit, một tenant noisy có thể ảnh hưởng mọi tenant. Vì vậy limiter thường cần partition theo user, API key, tenant hoặc route.

## 3. How does it work?

Request đi qua limiter trước expensive work:

```text
Client -> RateLimiter -> Endpoint -> DB/API
             |
          reject 429
```

Token bucket cho phép burst nhỏ nhưng giới hạn average rate. Concurrency limiter bảo vệ số operation đồng thời. Queue limit cho phép chờ một lượng nhỏ; queue quá lớn chỉ biến rejection thành latency.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("tenant-api", httpContext =>
    {
        var tenantId = httpContext.User.FindFirst("tenant_id")?.Value
            ?? "anonymous";

        return RateLimitPartition.GetTokenBucketLimiter(
            tenantId,
            _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 50,
                ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                QueueLimit = 20,
                AutoReplenishment = true
            });
    });

    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});
```

Endpoint:

```csharp
app.MapGet("/api/search", SearchAsync)
   .RequireRateLimiting("tenant-api");
```

## 5. Real production scenario

Một partner sync catalog tạo burst 5.000 requests sau mỗi deployment. Không có partitioning, SQL CPU lên 100% và người dùng web cũng timeout. Per-partner token bucket + global concurrency guard giữ database trong safe operating range.

## 6. Failure scenario & troubleshooting

**Symptom** → 429 tăng dù backend còn capacity, hoặc backend vẫn overload dù đã “có rate limit”.

**Evidence** → limiter metrics, queue wait, endpoint latency, SQL connections, traffic distribution theo tenant.

**Hypothesis** → key partition sai hoặc limiter bảo vệ metric không liên quan bottleneck.

**Diagnosis** → map resource saturation với route/client; kiểm tra NAT/proxy có khiến nhiều user cùng IP key hay không.

**Fix** → partition theo authenticated identity/tenant, dùng concurrency limiter cho expensive work, điều chỉnh queue nhỏ và trả `Retry-After` khi phù hợp.

**Verification** → burst test nhiều tenants và xác nhận noisy client không kéo p95 của tenant khác lên.

## 7. Common mistakes

- Rate limit chỉ theo IP sau reverse proxy.
- Queue hàng nghìn requests rồi nghĩ đó là resilience.
- Một global limit cho endpoint có cost rất khác nhau.
- Retry 429 ngay lập tức ở client gây retry storm.
- Không quan sát rejected/queued requests.

## 8. Alternatives

API Gateway/Azure Front Door/API Management có thể rate limit trước application. Application-level limiter hiểu business identity tốt hơn. Hai lớp có thể cùng tồn tại nếu responsibility rõ.

## 9. Trade-offs

### Advantages

- Bảo vệ dependencies và fairness.
- Failure mode predictable hơn timeout cascade.

### Costs / Risks

- Legitimate burst có thể bị reject.
- Distributed limit across instances phức tạp hơn local limiter.
- Policy sai tạo false throttling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 429 là capacity policy chứ không nhất thiết application error.

### Middle

Cấu hình limiter và partition key đúng authentication context.

### Senior

Liên kết limiter với bottleneck thật, retry behavior và multi-instance semantics.

### Technical Lead / Architect

Định nghĩa fairness/SLO và quyết định limit ở edge, app hay dependency boundary.

## 11. Key takeaway

- Rate limiting nên bảo vệ resource cụ thể.
- Partitioning quyết định fairness.
- Queue quá lớn thường chỉ đổi overload thành timeout chậm hơn.

# 3. EF Core execution strategy và transaction: retry transient failure mà không vô tình chạy business side effect hai lần

## 1. What is it?

EF Core execution strategy có thể retry database operations khi gặp transient faults như temporary network issue hoặc Azure SQL failover. Khi explicit transaction được dùng, toàn bộ transactional unit phải chạy bên trong execution strategy để retry đúng scope.

## 2. Why does it exist?

Cloud database không hứa network connection không bao giờ đứt. Một operation có thể fail tạm thời và thành công khi retry. Nhưng retry chỉ an toàn nếu operation có semantics phù hợp.

Nguy hiểm nhất là transaction chứa side effect ngoài database như gửi email hoặc publish HTTP call.

## 3. How does it work?

```text
ExecutionStrategy.ExecuteAsync
  -> begin transaction
  -> DB changes
  -> commit
  -> success

transient failure
  -> rerun whole delegate
```

Nếu external payment call nằm bên trong delegate, retry có thể charge hai lần nếu external API không idempotent.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    order.MarkConfirmed();
    db.OutboxMessages.Add(OutboxMessage.ForOrderConfirmed(order.Id));

    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
});
```

External publication để outbox worker thực hiện sau commit thay vì gọi trực tiếp trong retriable transaction.

## 5. Real production scenario

Checkout cập nhật order rồi gọi email provider trước commit. Azure SQL transient disconnect làm EF retry block; user nhận hai email. Nếu payment API cũng nằm trong block và không có idempotency key, hậu quả nghiêm trọng hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate side effects xuất hiện đúng lúc database transient errors/failover.

**Evidence** → execution strategy retry logs + hai external calls cùng correlation/business ID.

**Hypothesis** → non-idempotent side effect nằm trong retriable scope.

**Diagnosis** → trace transaction boundary và external calls; xác định operation nào có thể được replay.

**Fix** → giữ retriable block database-only; dùng Outbox hoặc idempotency key cho remote call.

**Verification** → inject transient DB failure và xác nhận business effect chỉ xảy ra một lần logically.

## 7. Common mistakes

- Bật retry rồi giả định mọi operation an toàn.
- Explicit transaction ngoài execution strategy delegate.
- Gửi message/email trong DB transaction.
- Retry unique constraint/business conflict như transient error.
- Không phân biệt unknown commit outcome.

## 8. Alternatives

Không retry tự động nếu workload yêu cầu manual reconciliation. Với distributed side effects, Outbox/Saga thường rõ semantics hơn distributed transaction.

## 9. Trade-offs

### Advantages

- Tăng resilience với transient DB faults.
- Cloud failover ít lộ thành user-visible error hơn.

### Costs / Risks

- Replay semantics làm side effect phức tạp.
- Retry tăng latency và load trong outage.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry nghĩa là code có thể chạy lại.

### Middle

Cấu hình execution strategy và transaction đúng scope.

### Senior

Phân loại transient/business failure và audit side effects.

### Technical Lead / Architect

Thiết kế idempotency/outbox để retry là property của system chứ không phải một decorator mù quáng.

## 11. Key takeaway

- Retriable scope phải được xem như có thể replay.
- External side effects không nên nằm tùy tiện trong EF retry transaction.
- Outbox giúp tách database atomicity khỏi message publication.

# 4. PostgreSQL keyset pagination với composite sort: tránh `OFFSET` ngày càng chậm và dữ liệu nhảy trang khi concurrent writes

## 1. What is it?

Keyset pagination lấy trang kế tiếp dựa trên giá trị sort cuối cùng của trang hiện tại thay vì `OFFSET N`.

Ví dụ sort ổn định:

```sql
ORDER BY created_at DESC, id DESC
```

Cursor chứa `(created_at, id)` cuối trang.

## 2. Why does it exist?

`OFFSET 100000` không có nghĩa database nhảy thẳng tới row 100001; engine thường vẫn phải scan/skip nhiều rows. Concurrent insert cũng làm vị trí rows dịch chuyển, gây duplicate hoặc missing records giữa các page.

## 3. How does it work?

Trang đầu:

```sql
SELECT id, created_at, total
FROM orders
WHERE tenant_id = $1
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Trang sau:

```sql
SELECT id, created_at, total
FROM orders
WHERE tenant_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Composite index phù hợp:

```sql
CREATE INDEX ix_orders_tenant_created_id
ON orders (tenant_id, created_at DESC, id DESC);
```

`id` là tie-breaker để ordering deterministic.

## 4. Practical implementation

API không cần expose raw values trực tiếp; encode cursor opaque Base64/JSON có version, rồi validate khi decode.

```csharp
public sealed record OrderCursor(DateTimeOffset CreatedAt, Guid Id);
```

Cursor không nên chứa trust-sensitive filter authorization; server vẫn phải áp tenant/user policy độc lập.

## 5. Real production scenario

Admin portal có 8 triệu audit events. Page 1 nhanh 40 ms, page 3.000 bằng OFFSET mất vài giây. Sau khi đổi sang keyset + composite index, latency của page sâu gần ổn định vì database seek từ cursor boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → item trùng/mất giữa page hoặc query page sâu chậm.

**Evidence** → sort column không unique; execution plan scan nhiều rows; concurrent inserts xảy ra.

**Hypothesis** → OFFSET hoặc non-deterministic ordering.

**Diagnosis** → inspect plan, rows scanned, index order và cursor predicates.

**Fix** → thêm unique tie-breaker, composite index match filter/order, keyset cursor.

**Verification** → paginate trong lúc concurrent inserts và check no duplicate IDs.

## 7. Common mistakes

- Sort chỉ `created_at` dù nhiều rows cùng timestamp.
- Index columns sai order.
- Cursor có thể bị client sửa để vượt authorization.
- Dùng keyset nhưng UI vẫn yêu cầu jump trực tiếp page 10.000.
- Encode cursor nhưng không version schema.

## 8. Alternatives

OFFSET phù hợp dataset nhỏ hoặc UI cần random page navigation. Keyset tốt cho feeds, infinite scroll và deep pagination. Search engines có cơ chế cursor/search-after tương tự.

## 9. Trade-offs

### Advantages

- Latency ổn định hơn ở page sâu.
- Ít duplicate/missing do insert mới.

### Costs / Risks

- Không thuận tiện jump arbitrary page.
- Cursor logic/index design phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu pagination là database access pattern, không chỉ API DTO.

### Middle

Viết deterministic ordering và cursor predicate.

### Senior

Đọc plan/index, xử lý concurrency và cursor validation.

### Technical Lead / Architect

Chọn UX/API pagination model phù hợp data volume thay vì giữ page-number contract bằng mọi giá.

## 11. Key takeaway

- Deep OFFSET thường scale kém.
- Keyset cần stable unique ordering.
- Index phải phù hợp filter + sort, không chỉ tồn tại “một index nào đó”.

# 5. MongoDB embedding vs referencing: thiết kế document theo access pattern, atomicity và document growth thay vì theo object model

## 1. What is it?

Embedding lưu related data trong cùng document; referencing lưu ID để liên kết document khác.

```json
{
  "orderId": "O1",
  "items": [
    { "sku": "A", "quantity": 2, "unitPrice": 10 }
  ]
}
```

Đây không phải quyết định “NoSQL thì embed”. Boundary nên dựa trên dữ liệu nào được đọc/ghi cùng nhau, ownership và growth.

## 2. Why does it exist?

Document database tối ưu mạnh khi một aggregate có thể đọc bằng một document fetch và update atomically. Nhưng embed collection tăng vô hạn có thể tạo document lớn, write amplification và contention.

## 3. How does it work?

Embed phù hợp khi child:

- thuộc owner rõ ràng;
- được đọc cùng parent;
- bounded cardinality;
- cần atomic update cùng parent.

Reference phù hợp khi data được share độc lập, grow lớn hoặc có lifecycle riêng.

## 4. Practical implementation

Order item thường snapshot product data thay vì reference live product price:

```csharp
public sealed class OrderDocument
{
    public string Id { get; init; } = default!;
    public List<OrderItem> Items { get; init; } = [];
}

public sealed record OrderItem(
    string Sku,
    string ProductName,
    decimal UnitPrice,
    int Quantity);
```

Snapshot này giữ lịch sử order đúng dù product catalog thay đổi.

## 5. Real production scenario

Team embed toàn bộ comments vào article. Một viral article có hàng trăm nghìn comments, document growth và write contention trở thành bottleneck. Comments có unbounded cardinality và query lifecycle riêng nên collection riêng hợp lý hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → update một document ngày càng chậm, document size tăng mạnh, hot document contention.

**Evidence** → profiler/metrics cho document size, array length, update latency.

**Hypothesis** → embedding vượt quá bounded aggregate assumption.

**Diagnosis** → map access patterns và growth distribution.

**Fix** → tách unbounded child collection, denormalize chỉ fields cần đọc nhanh, thêm indexes theo query pattern.

**Verification** → test với percentile lớn nhất của child count, không chỉ average.

## 7. Common mistakes

- Copy relational schema sang MongoDB bằng references mọi nơi.
- Embed unbounded arrays.
- Denormalize nhưng không có ownership/update strategy.
- Reference product price làm historical order tự thay đổi semantics.
- Chọn schema trước khi biết query patterns.

## 8. Alternatives

PostgreSQL/SQL Server phù hợp khi joins/ad-hoc relational consistency là trung tâm. MongoDB mạnh khi document aggregate và access pattern ổn định phù hợp model.

## 9. Trade-offs

### Advantages

Embedding giảm round trips và có atomicity trong document.

### Costs / Risks

Denormalization tạo duplication; document growth và synchronization cần quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu document model không phải relational tables viết bằng JSON.

### Middle

Model theo read/write pattern và bounded child collections.

### Senior

Đánh giá growth, hot documents, indexes và consistency.

### Technical Lead / Architect

Quyết định datastore/model dựa trên workload thay vì ép mọi domain vào cùng một persistence style.

## 11. Key takeaway

- Embed theo ownership + bounded access pattern.
- Reference khi lifecycle/growth độc lập.
- Historical snapshot đôi khi đúng hơn “normalized reference”.

# 6. Transactional Outbox Pattern: nối database transaction với message publishing mà không cần distributed transaction

## 1. What is it?

Outbox Pattern lưu business change và “message cần publish” trong cùng local database transaction. Một worker sau đó đọc outbox và publish sang broker.

```text
API transaction
  -> Orders table
  -> Outbox table
       commit
         |
         v
Outbox Worker -> Service Bus -> Consumers
```

## 2. Why does it exist?

Nếu code commit database rồi publish message, process có thể crash giữa hai bước. Database đã đổi nhưng event mất. Nếu publish trước rồi DB commit fail, event lại nói điều chưa xảy ra.

Distributed transaction thường không khả dụng hoặc quá đắt giữa SQL và cloud broker.

## 3. How does it work?

Business operation thêm outbox row cùng transaction. Publisher poll/claim rows, gửi message, đánh dấu processed. Publish có thể xảy ra hơn một lần nếu crash sau send nhưng trước mark processed, nên consumer vẫn cần idempotency/Inbox.

Outbox đạt atomic capture of intent, không tạo “exactly once delivery”.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

order.Confirm();

db.OutboxMessages.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    Type = "OrderConfirmed",
    Payload = JsonSerializer.Serialize(new { order.Id }),
    OccurredAtUtc = DateTimeOffset.UtcNow
});

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Publisher phải có batching, retry, claim/locking strategy và cleanup/retention.

## 5. Real production scenario

Order service commit status `Confirmed`; inventory service chỉ reserve khi nhận event. Trước Outbox, thỉnh thoảng production crash sau commit khiến order confirmed nhưng inventory không reserve. Outbox biến gap đó thành recoverable backlog.

## 6. Failure scenario & troubleshooting

**Symptom** → outbox backlog tăng hoặc duplicate downstream effects.

**Evidence** → oldest unprocessed age tăng, broker publish errors, same message ID processed nhiều lần.

**Hypothesis** → publisher stalled hoặc consumer không idempotent.

**Diagnosis** → metrics: backlog count/age, publish latency, retry count, duplicate detection.

**Fix** → restore publisher, backoff đúng, Inbox/dedup theo message ID, scale worker có controlled claiming.

**Verification** → kill publisher ở các điểm trước/sau send và xác nhận eventual delivery không gây duplicate business effect.

## 7. Common mistakes

- Gọi Outbox là exactly-once.
- Không monitor backlog age.
- Serialize internal EF entity thành integration event.
- Không có schema/version strategy.
- Outbox table tăng vô hạn.

## 8. Alternatives

Synchronous API call đơn giản hơn nếu strong immediate coordination thật sự cần và failure coupling chấp nhận được. Broker transaction có thể giải quyết một số scope nhưng không thay thế DB atomicity cross-system.

## 9. Trade-offs

### Advantages

- Không mất publish intent sau DB commit.
- Tách transaction local khỏi broker availability.

### Costs / Risks

- Eventual consistency.
- Worker, backlog, retention và dedup tăng operational complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DB commit và message publish là hai failure boundaries.

### Middle

Implement outbox row cùng transaction.

### Senior

Thiết kế claiming, retry, idempotency, ordering và observability.

### Technical Lead / Architect

Chỉ dùng Outbox khi cross-boundary reliability đáng complexity; đừng thêm messaging nếu một local transaction/module call đủ.

## 11. Key takeaway

- Outbox atomically lưu business change + publish intent.
- Delivery vẫn có thể duplicate.
- Backlog age là production signal quan trọng.

# 7. Azure Blob Storage direct upload bằng User Delegation SAS: giảm tải API mà vẫn giữ authorization boundary

## 1. What is it?

Thay vì client upload file qua ASP.NET Core rồi API stream tiếp sang Blob Storage, backend có thể authorize operation và phát short-lived SAS cho client upload trực tiếp.

```text
Client -> API: xin upload permission
API -> Entra/Blob: tạo User Delegation SAS
API -> Client: signed URL
Client -> Blob Storage: upload trực tiếp
```

## 2. Why does it exist?

Proxy file qua application làm app chịu bandwidth, connection duration, memory/buffer và scale cost dù nó không cần đọc nội dung. Direct upload tách data plane khỏi application compute.

## 3. How does it work?

Backend dùng Managed Identity để lấy user delegation key, tạo SAS giới hạn:

- container/blob cụ thể;
- permission cần thiết (`Create`/`Write`);
- expiry ngắn;
- HTTPS only.

SAS là capability token: ai có URL có quyền trong scope đó tới khi hết hạn, nên không được log/leak.

## 4. Practical implementation

Conceptual C#:

```csharp
var service = new BlobServiceClient(
    new Uri(storageUri),
    new DefaultAzureCredential());

var delegationKey = await service.GetUserDelegationKeyAsync(
    startsOn: DateTimeOffset.UtcNow.AddMinutes(-5),
    expiresOn: DateTimeOffset.UtcNow.AddMinutes(15),
    cancellationToken: ct);
```

Sau đó build `BlobSasBuilder` chỉ cho blob path server cấp, không nhận tùy ý container/path từ client.

## 5. Real production scenario

CMS cho editor upload video 2 GB. Upload qua App Service giữ request lâu, tăng egress/compute pressure và restart dễ cắt stream. Direct-to-Blob làm API chỉ cấp quyền và ghi metadata; Blob Storage xử lý transfer.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận 403 khi upload hoặc SAS bị dùng upload sai path.

**Evidence** → Storage diagnostic logs, SAS expiry/permissions/resource path, clock skew.

**Hypothesis** → scope/signature sai hoặc backend cho client ảnh hưởng quá nhiều vào SAS target.

**Diagnosis** → kiểm tra canonical blob path, permission, expiry, HTTPS và identity RBAC.

**Fix** → server-generated object name, short expiry, minimum permission, CORS chính xác, validation hậu upload.

**Verification** → SAS phải upload đúng blob, không list/delete container và hết hiệu lực sau expiry.

## 7. Common mistakes

- Dùng account key lâu dài trong app settings.
- SAS cho cả container với quyền quá rộng.
- Log full SAS URL.
- Cho file upload xong là “trusted” mà không scan/validate metadata/content.
- Expiry quá dài.

## 8. Alternatives

Proxy upload qua API hợp lý cho file nhỏ hoặc khi server bắt buộc transform/inspect streaming inline. Direct upload tốt cho large objects và scale.

## 9. Trade-offs

### Advantages

- Giảm app bandwidth/connection pressure.
- Blob Storage scale data transfer trực tiếp.

### Costs / Risks

- Client flow phức tạp hơn.
- Authorization chuyển thành signed capability cần quản trị cẩn thận.
- Cần lifecycle xử lý abandoned uploads.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu API có thể authorize mà không proxy toàn bộ bytes.

### Middle

Tạo short-lived least-privilege SAS và handle CORS.

### Senior

Thiết kế upload lifecycle, security scanning, orphan cleanup và observability.

### Technical Lead / Architect

Chọn control-plane/data-plane boundary và đánh giá threat model trước khi cấp direct storage access.

## 11. Key takeaway

- SAS nên ngắn hạn và scope tối thiểu.
- Managed Identity tốt hơn storage account key trong application.
- Direct upload giảm tải app nhưng không loại bỏ validation/security lifecycle.

# 8. Kubernetes CPU requests/limits và memory limits: hiểu throttling, scheduling và `OOMKilled` trước khi “tăng resource”

## 1. What is it?

Kubernetes `requests` mô tả resource scheduler dùng để đặt Pod lên node; `limits` đặt upper bound runtime.

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"
```

CPU và memory failure semantics khác nhau: CPU thường bị throttled; vượt memory limit có thể khiến container bị OOM kill.

## 2. Why does it exist?

Cluster chia tài nguyên hữu hạn giữa workloads. Không có requests đúng, scheduler có thể pack quá nhiều workload. Không có limits/guardrails, một process runaway có thể gây node pressure và ảnh hưởng workload khác.

## 3. How does it work?

CPU request ảnh hưởng scheduling và CPU shares dưới contention. CPU limit dùng cgroup quota, có thể throttle. Memory không thể “throttle” theo cách tương tự; khi vượt limit, process có thể bị kill.

Với .NET, container memory limit cũng ảnh hưởng GC/runtime decisions; cần đo working set, heap và native memory.

## 4. Practical implementation

Đừng copy con số từ môi trường khác. Load test và xem:

- CPU usage/throttling;
- working set/RSS;
- managed heap;
- GC pause/allocation;
- p95/p99 latency.

Readiness/liveness không nên restart app chỉ vì dependency ngoài tạm thời chậm.

## 5. Real production scenario

API có CPU limit `500m`. Dashboard CPU chỉ “500m” nhưng p99 tăng mạnh khi JSON serialization burst. Container không crash; nó bị CPU throttling. Team scale database vô ích vì bottleneck thực tế ở cgroup quota.

Một worker khác vượt 512 MiB do large buffers và xuất hiện `OOMKilled`, restart loop làm message redelivery tăng.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng mà CPU graph dừng đúng limit, hoặc Pod restart với exit reason `OOMKilled`.

**Evidence** → `kubectl describe pod`, container restart count, cgroup/Kubernetes CPU throttling metrics, memory working set.

**Hypothesis** → resource limits không phù hợp workload.

**Diagnosis** → correlate throttle/OOM timestamps với traffic, GC, allocations và request latency.

**Fix** → giảm allocation/concurrency trước; điều chỉnh requests/limits dựa measurement; scale replicas nếu workload parallelizable.

**Verification** → load test tại expected peak và failover capacity.

## 7. Common mistakes

- Requests = limits cực thấp “để tiết kiệm”.
- Chỉ tăng memory mà không tìm leak/buffer growth.
- Không set request rồi autoscaling/scheduling trở nên khó đoán.
- Nhìn average CPU thay vì throttling + tail latency.
- Liveness probe kill app khi dependency ngoài down.

## 8. Alternatives

Azure App Service/Container Apps có thể giảm Kubernetes operational burden nếu không cần cluster-level control. Kubernetes đáng dùng khi orchestration requirements đủ lớn.

## 9. Trade-offs

### Advantages

- Resource isolation và scheduling predictable hơn.
- Capacity planning/autoscaling có signal tốt hơn.

### Costs / Risks

- Tune sai gây throttle/OOM dù node còn tài nguyên.
- Cần observability ở container/runtime/application layers.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt request và limit.

### Middle

Đọc Pod reason/metrics khi throttle hoặc OOM.

### Senior

Liên kết .NET GC/allocation với container constraints và tail latency.

### Technical Lead / Architect

Quyết định SLO/capacity headroom và liệu Kubernetes có thật sự đáng operational cost cho team.

## 11. Key takeaway

- CPU limit thường degrade bằng throttling; memory limit có thể kill process.
- Resource numbers phải đến từ measurement.
- “Tăng limit” không thay thế bottleneck analysis.

# 9. OpenTelemetry sampling: giảm telemetry cost mà không làm mất đúng trace cần để điều tra production incident

## 1. What is it?

Sampling quyết định trace nào được record/export khi traffic quá lớn để giữ 100%. Head sampling quyết định sớm lúc trace bắt đầu; tail sampling quyết định sau khi đã thấy nhiều spans và kết quả trace.

## 2. Why does it exist?

Một hệ thống 20.000 requests/s có thể tạo hàng tỷ spans. Thu thập toàn bộ làm storage/ingestion cost tăng và observability backend quá tải. Nhưng sampling ngây thơ 1% có thể bỏ mất rare 500 errors hoặc p99 traces.

## 3. How does it work?

Head sampling:

```text
request starts -> sample? yes/no -> spans follow decision
```

Nhanh và rẻ nhưng chưa biết request sẽ error hay chậm.

Tail sampling:

```text
collect spans temporarily -> trace completes
 -> keep errors/slow/interesting traces
 -> drop majority normal traces
```

Tail sampling cần collector state/memory và thêm complexity.

## 4. Practical implementation

Trong OpenTelemetry Collector, policy conceptually có thể giữ:

- tất cả traces có status error;
- traces > 2s;
- 5% normal traffic.

Application vẫn nên emit low-cardinality metrics riêng; không dùng traces sampling để thay metric/SLO measurement.

## 5. Real production scenario

Payment API sample ngẫu nhiên 1%. Một race condition gây 0.05% request fail. Incident có metrics báo error spike nhưng không có trace lỗi vì toàn bộ sample bị bỏ. Tail policy “keep error traces” làm investigation có evidence mà không cần giữ 100% normal traces.

## 6. Failure scenario & troubleshooting

**Symptom** → metrics thấy 5xx nhưng trace search gần như không có failed requests.

**Evidence** → sampler configuration, sampled flag, collector drop metrics.

**Hypothesis** → sampling policy bỏ đúng rare failures.

**Diagnosis** → trace sampling decision path, collector capacity và propagation.

**Fix** → error/latency-aware sampling, reserve capacity, propagate trace context đúng.

**Verification** → synthetic error traffic phải luôn/đủ xác suất xuất hiện theo policy.

## 7. Common mistakes

- Dùng 1% random sampling rồi tưởng traces đại diện mọi rare failure.
- Sampling metrics giống traces.
- Collector tail sampling thiếu memory capacity.
- High-cardinality attributes ở mọi span làm cost tăng dù sample rate thấp.
- Không monitor collector dropped spans.

## 8. Alternatives

100% tracing phù hợp traffic nhỏ/critical temporary diagnostics. Head sampling đơn giản và rẻ. Tail sampling phù hợp khi cần giữ traces theo outcome nhưng thêm infrastructure.

## 9. Trade-offs

### Advantages

- Kiểm soát telemetry cost.
- Tail policy giữ high-value failure traces.

### Costs / Risks

- Có thể mất evidence.
- Tail sampling cần buffering/state và collector capacity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace search không nhất thiết chứa mọi request.

### Middle

Biết propagate trace context và đọc sampling flag.

### Senior

Thiết kế sampling theo error/latency, monitor collector drops.

### Technical Lead / Architect

Cân bằng observability cost với incident diagnosability và compliance/data-retention requirements.

## 11. Key takeaway

- Sampling là loss policy có chủ đích.
- Metrics và traces phục vụ mục đích khác nhau.
- Rare failures cần policy giữ evidence, không chỉ random sample.

# 10. REST API backward compatibility: evolve contract mà không phá mobile client, partner integration và deployment độc lập

## 1. What is it?

Backward compatibility nghĩa là client đã hoạt động với contract cũ tiếp tục hoạt động sau khi server evolve trong phạm vi cam kết. Contract không chỉ là URL; nó gồm status codes, fields, nullability, enum values, validation, ordering assumptions và error shape.

## 2. Why does it exist?

Backend có thể deploy hàng ngày nhưng mobile app cũ tồn tại hàng tháng, partner integration có release cycle riêng. Nếu server đổi field/semantics tùy tiện, independent deployment biến thành coordinated release bắt buộc.

## 3. How does it work?

Thay đổi additive thường an toàn hơn destructive:

```json
// old
{ "id": 1, "name": "A" }

// evolved
{ "id": 1, "name": "A", "displayName": "A" }
```

Nhưng thêm enum value có thể vẫn phá client nếu client deserialize strict switch. Vì vậy compatibility phải dựa vào actual consumer behavior, không chỉ OpenAPI diff.

## 4. Practical implementation

Dùng DTO contracts thay vì expose EF entities:

```csharp
public sealed record OrderResponse(
    Guid Id,
    string Status,
    decimal Total,
    DateTimeOffset CreatedAt);
```

Deprecation nên có lifecycle rõ. Contract tests có thể chạy producer/consumer expectations. Khi breaking change thật sự cần, version endpoint/media type theo strategy nhất quán.

## 5. Real production scenario

Backend đổi `status: "in_progress"` thành `"processing"`. Web frontend deploy cùng lúc nên ổn, nhưng mobile v3.2 có exhaustive switch và crash UI. Một “string change nhỏ” trở thành production incident do consumer lifecycle khác nhau.

## 6. Failure scenario & troubleshooting

**Symptom** → chỉ client version cũ/partner cụ thể fail sau backend deployment.

**Evidence** → API diff, client logs, contract tests, telemetry grouped by client version.

**Hypothesis** → breaking semantic/schema change.

**Diagnosis** → compare request/response/error contract trước/sau; replay old client fixture.

**Fix** → restore old behavior, additive migration, dual-read/write hoặc versioned contract; deprecate sau adoption window.

**Verification** → regression tests cho supported client versions và partner contracts.

## 7. Common mistakes

- Nghĩ thêm field/enum luôn non-breaking.
- Đổi `400` thành `404` mà không coi status code là contract.
- Expose database entity trực tiếp.
- Version API mỗi thay đổi nhỏ.
- Không biết consumer nào đang dùng endpoint cũ.

## 8. Alternatives

Additive evolution là mặc định tốt khi semantics tương thích. Explicit API versioning phù hợp breaking contract cần sống song song. Backend-for-Frontend có thể isolate mobile/web lifecycles nhưng thêm service ownership.

## 9. Trade-offs

### Advantages

- Client/server deploy độc lập.
- Giảm coordinated release risk.

### Costs / Risks

- Compatibility code và deprecation window tăng maintenance.
- Nhiều versions kéo dài tạo technical debt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu JSON field/status code cũng là public contract.

### Middle

Thiết kế DTO, validation và error response ổn định.

### Senior

Đánh giá semantic breaking changes, contract tests và migration strategy.

### Technical Lead / Architect

Định nghĩa compatibility policy, supported client window và khi nào complexity giữ backward compatibility lớn hơn lợi ích của version mới.

## 11. Key takeaway

- API contract rộng hơn schema.
- Independent deployment yêu cầu compatibility discipline.
- Prefer additive evolution; version khi breaking change thật sự cần sống song song.
