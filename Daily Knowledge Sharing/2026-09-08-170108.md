# 1. `Span<T>` và `Memory<T>` trong .NET: tối ưu allocation mà không biến code thành unsafe optimization

## 1. What is it?

`Span<T>` là một stack-only view lên vùng memory liên tục. Nó có thể trỏ vào array, stack memory hoặc một đoạn của buffer mà không cần copy dữ liệu. `Memory<T>` cung cấp ý tưởng tương tự nhưng có thể tồn tại qua async boundary và được lưu trên heap.

Mental model:

```text
Underlying buffer
[0][1][2][3][4][5][6][7]
       └──── Span slice ────┘
```

Điểm quan trọng: `Span<T>` không sở hữu memory. Nó chỉ là một view.

## 2. Why does it exist?

Các API truyền thống thường tạo substring, temporary array hoặc copy buffer chỉ để xử lý một đoạn dữ liệu. Trong hot path, các allocation nhỏ nhưng dày đặc sẽ tạo GC pressure.

`Span<T>` cho phép xử lý dữ liệu theo slice mà không tạo object mới.

## 3. How does it work?

`Span<T>` là `ref struct`, vì vậy compiler ngăn nó escape ra heap. Điều này khiến nó không thể dùng làm field của class hoặc sống qua `await`.

`Memory<T>` có thể được lưu và truyền qua async code, sau đó truy cập `.Span` khi xử lý đồng bộ.

```text
Array/Memory owner
      ↓
Memory<T>
      ↓ async boundary allowed
Span<T>
      ↓ synchronous processing only
```

## 4. Practical implementation

Ví dụ parse header dạng `key:value` mà không tạo substring trung gian:

```csharp
public static bool TrySplitHeader(
    ReadOnlySpan<char> input,
    out ReadOnlySpan<char> key,
    out ReadOnlySpan<char> value)
{
    var separator = input.IndexOf(':');
    if (separator <= 0)
    {
        key = default;
        value = default;
        return false;
    }

    key = input[..separator].Trim();
    value = input[(separator + 1)..].Trim();
    return true;
}
```

Với async I/O, thường nhận `Memory<byte>`:

```csharp
var buffer = new byte[8192];
var read = await stream.ReadAsync(buffer.AsMemory(), cancellationToken);
Process(buffer.AsSpan(0, read));
```

## 5. Real production scenario

Một gateway parse hàng triệu header/token nhỏ mỗi phút. Profiling cho thấy nhiều allocation đến từ slicing string và temporary buffer. Chuyển đúng hot path sang `ReadOnlySpan<char>` giảm allocation rate và GC frequency.

Không nên áp dụng vào business code hiếm khi chạy chỉ để “code nhanh hơn”.

## 6. Failure scenario & troubleshooting

**Symptom** → code phức tạp hơn đáng kể nhưng throughput không cải thiện.

**Evidence** → profiler cho thấy bottleneck chính là SQL/network, không phải allocation.

**Hypothesis** → tối ưu sai layer.

**Diagnosis** → so allocation profile, GC pause, CPU sample trước/sau.

**Fix** → rollback abstraction phức tạp nếu lợi ích không đủ lớn.

**Verification** → benchmark production-like workload.

## 7. Common mistakes

* Dùng `Span<T>` trong code không có allocation problem.
* Cố giữ `Span<T>` qua `await`.
* Nhầm view với ownership của buffer.
* Trả buffer về `ArrayPool<T>` trong khi còn reference đang dùng.
* Benchmark micro-method nhưng bỏ qua end-to-end latency.

## 8. Alternatives

* String/array thông thường: đơn giản, phù hợp đa số business code.
* `ArraySegment<T>`: cũ hơn, ít ergonomic hơn.
* `Memory<T>`: phù hợp khi cần async/lifetime dài hơn.
* `ArrayPool<T>`: giảm allocation buffer lớn nhưng phải quản lý ownership rõ ràng.

## 9. Trade-offs

### Advantages

* Giảm allocation/copy.
* Tốt cho parsing và high-throughput processing.
* Có thể giảm GC pressure.

### Costs / Risks

* API/lifetime phức tạp hơn.
* Dễ tạo ownership bug với pooled memory.
* Lợi ích nhỏ nếu bottleneck không nằm ở memory allocation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Span<T>` là view, không phải container sở hữu dữ liệu.

### Middle

Biết dùng slicing, `ReadOnlySpan<T>`, `Memory<T>` đúng async boundary.

### Senior

Biết profiling allocation, buffer ownership và GC impact trước khi tối ưu.

### Technical Lead / Architect

Quyết định hot path nào xứng đáng nhận thêm complexity và thiết lập convention cho pooled memory/lifetime safety.

## 11. Key takeaway

* `Span<T>` là công cụ tối ưu hot path, không phải default abstraction.
* Tối ưu allocation chỉ có giá trị khi profiling chứng minh allocation là vấn đề.
* Lifetime và ownership quan trọng hơn syntax.

# 2. ASP.NET Core middleware ordering

## 1. What is it?

ASP.NET Core xử lý request qua một chuỗi middleware. Thứ tự đăng ký quyết định thứ tự xử lý request đi vào và response đi ra.

Mental model:

```text
Request
  ↓
Exception Handler
  ↓
Routing
  ↓
Authentication
  ↓
Authorization
  ↓
Endpoint
  ↑
Response unwinds backward
```

## 2. Why does it exist?

Middleware cho phép ghép các cross-cutting concerns như error handling, security, logging, compression và routing. Nhưng vì pipeline có tính tuần tự, một middleware đặt sai chỗ có thể làm feature “có cấu hình nhưng không hoạt động đúng”.

## 3. How does it work?

Mỗi middleware có thể làm việc trước và sau `next()`.

```csharp
app.Use(async (context, next) =>
{
    // before downstream
    await next();
    // after downstream
});
```

Authentication phải chạy trước Authorization để principal được thiết lập. Exception handler phải bao ngoài phần pipeline muốn bắt exception.

## 4. Practical implementation

```csharp
var app = builder.Build();

app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();
```

Nếu dùng custom correlation middleware:

```csharp
app.Use(async (context, next) =>
{
    var correlationId = context.Request.Headers["X-Correlation-Id"].FirstOrDefault()
        ?? Guid.NewGuid().ToString("N");

    using (logger.BeginScope(new Dictionary<string, object>
    {
        ["CorrelationId"] = correlationId
    }))
    {
        await next();
    }
});
```

Nó nên nằm đủ sớm để mọi downstream log có correlation.

## 5. Real production scenario

Một API có JWT authentication và policy authorization. Sau refactor, `UseAuthorization()` được đặt trước `UseAuthentication()`. Endpoint bắt đầu trả 403 dù token hợp lệ.

Code policy không sai; pipeline order sai.

## 6. Failure scenario & troubleshooting

**Symptom** → authenticated endpoint trả 401/403 bất thường.

**Evidence** → trong authorization middleware, `HttpContext.User.Identity.IsAuthenticated == false`.

**Hypothesis** → authentication chưa chạy.

**Diagnosis** → xem thứ tự middleware và endpoint metadata.

**Fix** → đặt Authentication trước Authorization.

**Verification** → integration test full request pipeline với token thật/test identity.

## 7. Common mistakes

* Chỉ đọc middleware docs riêng lẻ mà không nhìn pipeline tổng thể.
* Đặt exception handler sau middleware có thể throw.
* CORS/routing/security middleware sai thứ tự.
* Log request body trước khi nghĩ tới sensitive data.
* Custom middleware short-circuit request ngoài ý muốn.

## 8. Alternatives

Filters phù hợp concern ở MVC/action boundary. Endpoint filters phù hợp Minimal APIs. Middleware phù hợp concern xuyên toàn HTTP pipeline.

## 9. Trade-offs

### Advantages

* Composition rõ ràng.
* Cross-cutting concern tách khỏi business code.

### Costs / Risks

* Order tạo hidden dependency.
* Custom middleware quá nhiều làm pipeline khó reasoning.
* Một middleware chậm ảnh hưởng mọi request phía sau.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request đi qua pipeline theo thứ tự.

### Middle

Biết đặt Authentication, Authorization, exception handling, routing đúng vị trí.

### Senior

Debug short-circuit, response started, latency và security consequence do middleware order.

### Technical Lead / Architect

Chuẩn hóa pipeline, ownership và integration tests để tránh configuration drift giữa services.

## 11. Key takeaway

* Middleware order là behavior, không phải style preference.
* Authentication phải hoàn thành trước Authorization.
* Test pipeline thực tế, không chỉ unit-test từng middleware.

# 3. EF Core compiled queries

## 1. What is it?

EF Core compiled query cho phép cache trước query translation pipeline cho một query shape cố định, giảm chi phí expression processing và query compilation ở các hot call lặp lại.

## 2. Why does it exist?

EF Core đã cache query plan nội bộ theo query shape. Tuy nhiên với cực kỳ hot query, lookup/compilation overhead vẫn có thể đáng kể. `EF.CompileQuery` hoặc `EF.CompileAsyncQuery` giảm thêm overhead đó.

Điểm quan trọng: compiled query không làm SQL query tự nhiên nhanh hơn.

## 3. How does it work?

```text
Normal query
LINQ expression → shape lookup/compile → SQL → DB

Compiled query
precompiled delegate → SQL execution → DB
```

Nếu database mất 80 ms và EF compile overhead là 50 microseconds, tối ưu compiled query gần như không đáng kể.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<OrderDto>>
    GetOrderByCustomer = EF.CompileAsyncQuery(
        (AppDbContext db, Guid customerId) =>
            db.Orders
                .AsNoTracking()
                .Where(x => x.CustomerId == customerId)
                .OrderByDescending(x => x.CreatedAt)
                .Take(20)
                .Select(x => new OrderDto(x.Id, x.Number, x.Total)));
```

Sử dụng:

```csharp
await foreach (var item in GetOrderByCustomer(db, customerId)
    .WithCancellation(cancellationToken))
{
    results.Add(item);
}
```

## 5. Real production scenario

Một lookup endpoint nhận hàng chục nghìn request/second, query rất đơn giản, DB ở cùng region và latency thấp. Profiling cho thấy EF query pipeline chiếm tỷ lệ CPU đáng kể. Đây là tình huống compiled query có thể hợp lý.

## 6. Failure scenario & troubleshooting

**Symptom** → chuyển sang compiled query nhưng p95 không đổi.

**Evidence** → trace cho thấy DB I/O vẫn chiếm 98% duration.

**Hypothesis** → query compilation không phải bottleneck.

**Diagnosis** → đo EF CPU, DB duration, logical reads, network latency.

**Fix** → tối ưu access pattern/index/projection thay vì query compilation.

**Verification** → benchmark end-to-end.

## 7. Common mistakes

* Dùng compiled query cho mọi repository method.
* Nghĩ compiled query thay execution plan tuning.
* Query shape quá dynamic nên compiled abstraction khó dùng.
* Tối ưu ORM trước khi kiểm tra SQL.

## 8. Alternatives

* Query bình thường + EF internal cache: đủ cho đa số workload.
* Raw SQL/Dapper: giảm ORM overhead hơn nhưng tăng maintenance cost.
* Stored procedure: phù hợp một số database-centric workload.

## 9. Trade-offs

### Advantages

* Giảm CPU overhead ở hot query shape.
* Predictable query path.

### Costs / Risks

* Tăng code ceremony.
* Ít linh hoạt với dynamic query.
* Dễ tối ưu nhầm layer.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ phải được translate thành SQL.

### Middle

Biết xem generated SQL và đo query duration.

### Senior

Phân biệt ORM CPU overhead với DB latency/I/O.

### Technical Lead / Architect

Chỉ áp dụng compiled query khi profiling chứng minh giá trị và team chấp nhận complexity.

## 11. Key takeaway

* Compiled query tối ưu query pipeline, không tối ưu SQL execution.
* EF query optimization phải bắt đầu bằng đo end-to-end.
* Đa số app không cần compiled query ở mọi nơi.

# 4. PostgreSQL MVCC và autovacuum

## 1. What is it?

MVCC — Multi-Version Concurrency Control — cho phép nhiều transaction đọc/ghi đồng thời bằng cách giữ nhiều version của row thay vì khóa mọi reader khi writer update.

Trong PostgreSQL, UPDATE thường tạo một row version mới; row cũ trở thành dead tuple khi không transaction nào cần thấy nó nữa.

## 2. Why does it exist?

Nếu mọi write khóa reader, throughput concurrency sẽ giảm mạnh. MVCC cho phép reader nhìn snapshot nhất quán trong khi writer vẫn tiến hành thay đổi.

Nhưng đổi lại, row version cũ phải được cleanup.

## 3. How does it work?

```text
Transaction A reads snapshot
        ↓
Transaction B UPDATE row
        ↓
new tuple created
old tuple retained temporarily
        ↓
VACUUM later reclaims dead tuple space
```

Autovacuum theo dõi lượng dead tuples và chạy vacuum/analyze dựa trên threshold/configuration.

## 4. Practical implementation

Theo dõi table bloat/dead tuples:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum,
    last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Long-running transaction cũng đáng kiểm tra:

```sql
SELECT pid, xact_start, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

## 5. Real production scenario

Một audit/event table có update rate cao. Disk usage tăng liên tục dù row count gần như ổn định. Query bắt đầu chậm vì dead tuples và statistics không còn phản ánh tốt distribution.

Root cause không phải “PostgreSQL tự phình vô lý” mà là vacuum không theo kịp workload và có long-running transaction giữ old versions sống lâu.

## 6. Failure scenario & troubleshooting

**Symptom** → table size tăng, query latency tăng.

**Evidence** → `n_dead_tup` cao, autovacuum chạy ít hoặc không reclaim được.

**Hypothesis** → vacuum lag hoặc transaction quá dài.

**Diagnosis** → xem autovacuum stats, active transactions, table churn.

**Fix** → xử lý transaction lifetime, tuning autovacuum theo table, giảm update churn nếu có thể.

**Verification** → dead tuple trend giảm, execution plan/logical reads cải thiện.

## 7. Common mistakes

* Nghĩ DELETE/UPDATE ngay lập tức trả disk space về OS.
* Tắt autovacuum vì sợ CPU.
* Giữ transaction mở trong request dài.
* Chỉ tăng hardware mà không xem bloat/churn pattern.
* Dùng `VACUUM FULL` tùy tiện trong production vì lock impact.

## 8. Alternatives

SQL Server cũng có concurrency/versioning cơ chế khác như row versioning under snapshot isolation. Không nên map trực tiếp operational behavior giữa hai engine.

## 9. Trade-offs

### Advantages

* Reader/writer concurrency tốt.
* Snapshot semantics mạnh.

### Costs / Risks

* Dead tuples cần maintenance.
* Autovacuum tuning có thể cần theo workload.
* Long-running transaction gây operational side effects lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu UPDATE không nhất thiết ghi đè row tại chỗ.

### Middle

Biết đọc `pg_stat_user_tables` và nhận biết vacuum lag.

### Senior

Liên hệ MVCC, transaction lifetime, bloat, statistics và query latency.

### Technical Lead / Architect

Thiết kế workload và maintenance policy theo write rate, retention, transaction profile và storage budget.

## 11. Key takeaway

* MVCC mua concurrency bằng row-version lifecycle.
* Autovacuum là cơ chế vận hành cốt lõi, không phải housekeeping tùy chọn.
* Long-running transaction có thể gây bloat dù business code “không lỗi”.

# 5. CQRS với một database

## 1. What is it?

CQRS tách intent của **Command** và **Query**. Nó không bắt buộc phải có hai database, Event Sourcing hay microservices.

Mental model:

```text
Command → validate intent → mutate state
Query   → read optimized projection → no domain mutation
```

## 2. Why does it exist?

Một model dùng cho cả write invariants và read presentation thường trở nên khó hiểu khi system lớn dần. Command cần bảo vệ business rules; Query cần trả data đúng shape và nhanh.

Tách intent giúp code dễ reasoning hơn trước cả khi scale architecture.

## 3. How does it work?

CQRS mức đơn giản:

```text
API
 ├─ Commands → application handler → EF Core write model
 └─ Queries  → query handler       → same SQL database
```

Không có eventual consistency nếu cùng transaction/store và read query trực tiếp dữ liệu đã commit.

## 4. Practical implementation

```csharp
public sealed record ApproveTimesheetCommand(Guid TimesheetId, Guid ApproverId);

public sealed class ApproveTimesheetHandler
{
    private readonly AppDbContext _db;

    public async Task Handle(
        ApproveTimesheetCommand command,
        CancellationToken cancellationToken)
    {
        var timesheet = await _db.Timesheets
            .SingleAsync(x => x.Id == command.TimesheetId, cancellationToken);

        timesheet.Approve(command.ApproverId);
        await _db.SaveChangesAsync(cancellationToken);
    }
}
```

Query riêng:

```csharp
public Task<TimesheetSummary?> GetSummaryAsync(
    Guid id,
    CancellationToken ct) =>
    _db.Timesheets
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new TimesheetSummary(x.Id, x.Status, x.TotalHours))
        .SingleOrDefaultAsync(ct);
```

## 5. Real production scenario

Một approval platform ban đầu dùng entity trực tiếp cho mọi API. Sau vài năm, write rules phức tạp nhưng read dashboard cần nhiều projection. CQRS một DB giúp tách domain mutation khỏi reporting read path mà chưa cần thêm operational components.

## 6. Failure scenario & troubleshooting

**Symptom** → team áp dụng CQRS nhưng mỗi command/query chỉ là pass-through class, số file tăng gấp ba mà behavior không rõ hơn.

**Evidence** → không có khác biệt về intent, boundary hay complexity.

**Hypothesis** → pattern được áp dụng theo ceremony.

**Diagnosis** → kiểm tra command có business invariant không, query có projection/use-case riêng không.

**Fix** → giữ pattern chỉ nơi separation tạo giá trị; không ép mọi CRUD endpoint.

**Verification** → code review tập trung change isolation, không đếm số handler.

## 7. Common mistakes

* CQRS = MediatR.
* CQRS = hai database.
* CQRS = Event Sourcing.
* Tách lớp nhưng không tách intent.
* Tạo read model phức tạp cho CRUD đơn giản.

## 8. Alternatives

* Layered CRUD/service architecture: đơn giản hơn cho domain ít complexity.
* CQRS một DB: tách intent với operational cost thấp.
* Separate read/write stores: dùng khi scale/query shape thực sự cần.

## 9. Trade-offs

### Advantages

* Intent rõ.
* Read projection linh hoạt.
* Domain write path dễ bảo vệ hơn.

### Costs / Risks

* Tăng abstraction/code volume.
* Có thể thành ceremony.
* Nếu tách stores, consistency và deployment complexity tăng mạnh.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Command thay đổi state, Query đọc state.

### Middle

Biết implement handlers và projections rõ use case.

### Senior

Biết khi nào CQRS mang giá trị và khi nào CRUD đơn giản hơn.

### Technical Lead / Architect

Quyết định separation level dựa trên business complexity, scale, consistency và team capability.

## 11. Key takeaway

* CQRS bắt đầu từ separation of intent.
* Một database vẫn hoàn toàn là CQRS hợp lệ.
* Đừng trả operational complexity nếu problem chưa cần.

# 6. Idempotent consumer + Inbox Pattern

## 1. What is it?

Trong hệ thống message broker dùng at-least-once delivery, cùng một message có thể được giao nhiều lần. Idempotent consumer đảm bảo xử lý duplicate không tạo side effect lặp.

Inbox Pattern lưu dấu message đã xử lý trong storage transactional với business update.

## 2. Why does it exist?

Broker retry khi consumer crash, timeout hoặc không settle message kịp. Không thể giả định “mỗi message chỉ đến một lần”.

Nếu `OrderPaid` được xử lý hai lần, hệ thống có thể gửi hai email, cộng điểm hai lần hoặc tạo shipment hai lần.

## 3. How does it work?

```text
Receive message M123
      ↓
Begin DB transaction
      ↓
Check Inbox(M123)
  ├─ exists → skip side effect
  └─ absent → apply business change + insert Inbox row
      ↓
Commit
      ↓
Complete broker message
```

Điểm quan trọng là business change và Inbox marker cùng transaction.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

var alreadyProcessed = await db.InboxMessages
    .AnyAsync(x => x.MessageId == message.Id, ct);

if (!alreadyProcessed)
{
    var order = await db.Orders
        .SingleAsync(x => x.Id == message.OrderId, ct);

    order.MarkPaid(message.PaidAt);

    db.InboxMessages.Add(new InboxMessage
    {
        MessageId = message.Id,
        ProcessedAt = DateTimeOffset.UtcNow
    });

    await db.SaveChangesAsync(ct);
}

await tx.CommitAsync(ct);
```

Database nên có unique constraint trên `MessageId` để chống race.

## 5. Real production scenario

Azure Service Bus consumer xử lý payment events. Instance crash sau khi commit DB nhưng trước khi complete message. Broker redeliver message. Inbox marker khiến lần thứ hai trở thành no-op thay vì charge/ship lại.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate shipment dù broker configuration “normal”.

**Evidence** → cùng `MessageId` xuất hiện hai lần trong logs.

**Hypothesis** → consumer không idempotent.

**Diagnosis** → kiểm tra transaction boundary giữa business write và dedupe record.

**Fix** → Inbox + unique constraint hoặc business-level idempotency key.

**Verification** → cố ý crash consumer sau DB commit nhưng trước broker settlement.

## 7. Common mistakes

* Tin rằng broker guarantee exactly-once end-to-end.
* Dedupe chỉ trong memory cache.
* Insert inbox sau business commit ở transaction khác.
* Không có retention strategy cho Inbox table.
* Dedupe theo payload hash thay vì stable message ID khi semantics không phù hợp.

## 8. Alternatives

* Business idempotency key trên aggregate.
* Upsert/unique constraints cho side effect cụ thể.
* Exactly-once feature của một platform vẫn không tự giải quyết mọi external side effect.

## 9. Trade-offs

### Advantages

* Chịu duplicate delivery an toàn hơn.
* Failure recovery rõ ràng.

### Costs / Risks

* Thêm storage/write mỗi message.
* Cần cleanup/retention.
* Cross-database side effects vẫn cần thiết kế riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu message có thể được giao lại.

### Middle

Biết dùng unique key và transaction để dedupe.

### Senior

Reason về crash windows, settlement, retries và external side effects.

### Technical Lead / Architect

Chuẩn hóa message identity, Inbox retention, retry policy và observability toàn platform.

## 11. Key takeaway

* At-least-once delivery đồng nghĩa duplicate là normal condition.
* Idempotency phải nằm ở business/storage boundary, không chỉ broker config.
* Hãy test crash window thật.

# 7. Azure Front Door vs Application Gateway

## 1. What is it?

Azure Front Door là global edge service cho HTTP(S) routing, acceleration, WAF và multi-region entry point. Application Gateway là regional Layer 7 load balancer/reverse proxy trong Azure region/VNet context.

## 2. Why does it exist?

Hai service giải quyết boundary khác nhau.

```text
Internet users globally
        ↓
Azure Front Door
        ↓
Region A / Region B
        ↓
Application Gateway or app ingress
        ↓
Private workloads
```

Không nên chọn chỉ vì cả hai đều “load balance HTTP”.

## 3. How does it work?

Front Door dùng global edge network để nhận traffic gần client và route tới origin dựa trên health/latency/rules.

Application Gateway hoạt động trong region và có thể tích hợp VNet/private backend, TLS termination, path routing và WAF.

## 4. Practical implementation

Một architecture phổ biến:

```text
Client
  ↓
Front Door + WAF
  ↓
Private Link / regional origin
  ↓
App Service / Application Gateway / AKS ingress
```

Application nên trust forwarded headers từ proxy boundary được cấu hình rõ ràng; không lấy `X-Forwarded-For` từ arbitrary client một cách mù quáng.

## 5. Real production scenario

SaaS có users ở APAC và Europe, deploy hai regions. Front Door route global traffic và failover region. Mỗi region có Application Gateway trước private AKS workload.

Nếu chỉ có một App Service public trong một region, thêm cả hai layer có thể là overengineering.

## 6. Failure scenario & troubleshooting

**Symptom** → Front Door health probe đánh origin unhealthy dù app endpoint dùng browser vẫn mở được.

**Evidence** → probe path trả 401 hoặc phụ thuộc database đang degraded.

**Hypothesis** → health endpoint không phù hợp routing semantics.

**Diagnosis** → xem probe status, origin response, dependency health.

**Fix** → thiết kế readiness endpoint đúng: đủ để nhận traffic nhưng không biến transient downstream issue thành global failover storm.

**Verification** → chaos test origin failure/failover.

## 7. Common mistakes

* Dùng Front Door và App Gateway mà không xác định boundary.
* Health probe phụ thuộc quá nhiều downstream services.
* Public origin bỏ qua Front Door/WAF path.
* Tin forwarded headers từ mọi source.
* Không tính cross-region egress và WAF cost.

## 8. Alternatives

* Azure Load Balancer: Layer 4 regional networking.
* App Service built-in routing: đủ cho architecture đơn giản.
* CDN-only solution: phù hợp static/cache-centric workload.
* AKS ingress controller: xử lý cluster ingress nhưng không thay global edge.

## 9. Trade-offs

### Advantages

* Front Door: global routing/failover/edge security.
* App Gateway: regional L7 + private network integration.

### Costs / Risks

* Thêm hop, config và cost.
* Failure diagnosis phức tạp hơn.
* Misconfigured health/routing có thể tự tạo outage.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu global edge khác regional gateway.

### Middle

Biết path routing, WAF, health probes và forwarded headers.

### Senior

Đánh giá failover semantics, private networking, observability và latency/cost.

### Technical Lead / Architect

Quyết định cần một hay nhiều ingress layers dựa trên regions, security boundary, network topology và operational maturity.

## 11. Key takeaway

* Front Door và Application Gateway không phải hai tên cho cùng một vấn đề.
* Thiết kế health probe quyết định failure routing behavior.
* Không thêm ingress layer nếu architecture chưa cần.

# 8. OpenTelemetry trace context và baggage

## 1. What is it?

Trace context mang identity của distributed trace — thường gồm TraceId, SpanId và flags — qua service boundaries. Baggage là key/value context có thể propagate cùng request để enrich telemetry hoặc routing logic hạn chế.

## 2. Why does it exist?

Một user request có thể đi qua API, queue, worker, database và external service. Nếu mỗi component có log riêng mà không correlation, production investigation trở thành manual timestamp matching.

## 3. How does it work?

W3C Trace Context thường propagate qua headers như `traceparent`.

```text
Client → API span A
          ↓ trace context
        Service B span B
          ↓
        DB span C
```

Baggage có thể propagate metadata, nhưng vì nó có thể đi qua nhiều service, không nên chứa secret/PII tùy tiện.

## 4. Practical implementation

```csharp
using var activity = ActivitySource.StartActivity("ProcessOrder");
activity?.SetTag("order.operation", "approve");
activity?.SetTag("tenant.tier", tenantTier);

await handler.HandleAsync(cancellationToken);
```

Custom baggage chỉ dùng khi có lý do propagation thực sự:

```csharp
Baggage.SetBaggage("experiment.version", "v2");
```

Không đặt email, token, card number hoặc secret vào baggage.

## 5. Real production scenario

API p95 tăng. Trace cho thấy chỉ requests qua một downstream inventory service bị chậm. TraceId cho phép nối request log, dependency span và SQL span trong cùng causal chain.

## 6. Failure scenario & troubleshooting

**Symptom** → traces bị tách thành nhiều root spans.

**Evidence** → outbound/inbound service không preserve `traceparent` hoặc custom HTTP client thay headers sai.

**Hypothesis** → propagation bị mất.

**Diagnosis** → inspect headers và OpenTelemetry instrumentation config.

**Fix** → dùng standard instrumentation/propagator; tránh tự generate correlation ID thay trace context.

**Verification** → integration test multi-service trace continuity.

## 7. Common mistakes

* Dùng correlation ID custom nhưng bỏ distributed trace standard.
* Baggage chứa PII/secret.
* High-cardinality tag vô hạn gây telemetry cost explosion.
* Log mọi payload để “debug dễ hơn”.
* Sampling mà không hiểu ảnh hưởng tới incident evidence.

## 8. Alternatives

Correlation ID đơn giản đủ cho monolith nhỏ. OpenTelemetry cần thiết hơn khi có distributed calls và cần logs + metrics + traces theo standard.

## 9. Trade-offs

### Advantages

* Causal investigation xuyên service.
* Vendor-neutral telemetry model.

### Costs / Risks

* Telemetry volume/cost.
* Sampling complexity.
* Data governance risk từ tags/baggage.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu TraceId nối các spans của cùng request.

### Middle

Biết instrument custom activity và preserve propagation.

### Senior

Thiết kế tags, sampling và investigate broken traces.

### Technical Lead / Architect

Định nghĩa telemetry schema, PII policy, retention, sampling và vendor/export strategy.

## 11. Key takeaway

* Trace context giải quyết causal correlation, không chỉ log decoration.
* Baggage là propagated data nên phải kiểm soát như network-visible metadata.
* Observability tốt cần schema discipline và cost discipline.

# 9. Playwright E2E testing

## 1. What is it?

Playwright chạy browser automation để kiểm tra user flow thật qua UI, network và backend. E2E test bảo vệ integration behavior nhưng không nên thay unit/integration tests.

## 2. Why does it exist?

Một feature có thể pass unit test ở frontend và backend nhưng fail khi ghép routing, auth cookie, API contract, browser rendering và asynchronous UI state.

E2E test bắt các lỗi boundary đó.

## 3. How does it work?

```text
Test runner
  ↓
Browser
  ↓
Frontend
  ↓
API
  ↓
Database / dependencies
```

Test deterministic cần kiểm soát data, environment và synchronization với UI state.

## 4. Practical implementation

```ts
import { test, expect } from '@playwright/test';

test('manager approves timesheet', async ({ page }) => {
  await page.goto('/timesheets/123');

  await page.getByRole('button', { name: 'Approve' }).click();

  await expect(page.getByText('Approved')).toBeVisible();
  await expect(page.getByRole('button', { name: 'Approve' })).toBeHidden();
});
```

Ưu tiên semantic locator (`getByRole`, `getByLabel`) hơn CSS selector dễ vỡ.

## 5. Real production scenario

Sau frontend refactor, API vẫn trả đúng JSON nhưng button approve không update vì client state mutation sai. Backend integration tests pass; Playwright flow bắt regression.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail ngẫu nhiên 1/20 lần.

**Evidence** → screenshot/video cho thấy click xảy ra trước data load hoàn tất.

**Hypothesis** → test dựa trên timing thay vì state.

**Diagnosis** → tìm `waitForTimeout`, shared test data, race network.

**Fix** → chờ observable UI state, tạo isolated test data, tránh fixed sleep.

**Verification** → chạy lặp nhiều lần và parallel.

## 7. Common mistakes

* Dùng `waitForTimeout(5000)` để chữa flaky test.
* Một account/data set dùng chung cho parallel tests.
* Test mọi permutation bằng E2E.
* CSS selector phụ thuộc implementation detail.
* Retry quá nhiều làm ẩn bug thật.

## 8. Alternatives

* Unit tests: nhanh, tốt cho pure logic.
* Integration/API tests: tốt cho service/database boundary.
* Component tests: kiểm tra UI component cô lập hơn.
* E2E: dùng cho critical journeys và integration risk cao.

## 9. Trade-offs

### Advantages

* Bảo vệ user flow thực tế.
* Bắt cross-layer regression.

### Costs / Risks

* Chậm hơn.
* Environment/data dependency cao.
* Flakiness nếu thiết kế tệ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu E2E kiểm tra user flow xuyên nhiều layers.

### Middle

Biết locator ổn định, test isolation và state-based waits.

### Senior

Điều tra flakiness, test pyramid và CI parallelism.

### Technical Lead / Architect

Xác định critical journeys nào xứng đáng E2E và governance để suite không trở thành bottleneck CI.

## 11. Key takeaway

* Flaky test thường là design signal, không phải lý do tăng retry.
* Chờ state, không chờ thời gian.
* E2E nên bảo vệ critical flow, không thay toàn bộ test strategy.

# 10. RAG evaluation: đo retrieval quality trước khi đổ lỗi cho LLM

## 1. What is it?

RAG — Retrieval-Augmented Generation — đưa external knowledge vào context của LLM. Chất lượng cuối cùng phụ thuộc ít nhất hai lớp:

```text
Question
  ↓
Retrieval quality
  ↓
Context quality
  ↓
Generation quality
```

Nếu retrieval sai, model không thể “reason” ra facts không có trong context một cách đáng tin cậy.

## 2. Why does it exist?

LLM không phải database và knowledge cutoff/training data không phù hợp private enterprise data. RAG cho phép lấy tài liệu runtime từ source có kiểm soát.

Nhưng nhiều team chỉ đánh giá câu trả lời cuối cùng, không đo retrieval nên không biết lỗi nằm ở embedding, chunking, metadata filter hay generation.

## 3. How does it work?

Một pipeline thường gồm:

```text
Documents → chunk → embeddings/index
Question → retrieval → reranking/filter
         → selected context
         → LLM generation
```

Evaluation nên tách:

* Recall@K: relevant evidence có được retrieve không?
* Precision/relevance: top chunks có thực sự hữu ích không?
* Groundedness: answer có bám context không?
* Answer correctness: output cuối có đúng business expectation không?

## 4. Practical implementation

Một evaluation record có thể deterministic ở retrieval layer:

```json
{
  "question": "How long is support access valid?",
  "expected_document_ids": ["security-policy-v4"],
  "expected_facts": ["24 hours default"]
}
```

Test pipeline:

```csharp
var results = await retriever.SearchAsync(question, topK: 5, ct);
var recallHit = results.Any(x => expectedDocumentIds.Contains(x.DocumentId));
```

Sau đó mới đánh giá model answer trên context retrieved.

## 5. Real production scenario

Internal knowledge assistant trả policy cũ. Team đổi model nhưng lỗi vẫn còn. Investigation cho thấy vector search luôn retrieve document archived vì metadata filter không loại `Status = Archived`.

Root cause là retrieval governance, không phải model intelligence.

## 6. Failure scenario & troubleshooting

**Symptom** → answer hallucinate hoặc dùng policy lỗi thời.

**Evidence** → retrieved chunks không chứa current policy.

**Hypothesis** → retrieval failure.

**Diagnosis** → inspect query, chunk, similarity score, metadata filter, index freshness.

**Fix** → sửa ingestion/filter/ranking trước khi đổi prompt/model.

**Verification** → rerun golden evaluation set và theo dõi Recall@K + grounded answer score.

## 7. Common mistakes

* Chỉ chấm answer cuối.
* Không version corpus/index.
* Chunk theo số token cứng mà bỏ document structure.
* Không filter quyền truy cập trước retrieval.
* Đưa retrieved content trực tiếp vào tool/action logic như trusted instruction.
* Không phân biệt prompt injection trong document với legitimate knowledge.

## 8. Alternatives

* Direct database/API lookup: tốt hơn khi dữ liệu có schema rõ và cần deterministic correctness.
* Full-text search: có thể tốt hơn embeddings cho exact identifiers/technical terms.
* Hybrid search: kết hợp lexical + vector retrieval.

## 9. Trade-offs

### Advantages

* Kết nối LLM với private/current knowledge.
* Có thể cải thiện groundedness đáng kể.

### Costs / Risks

* Ingestion/index freshness complexity.
* Retrieval evaluation cần dataset.
* Security boundary phức tạp.
* Token/cost tăng theo context.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG = retrieve context rồi mới generate.

### Middle

Biết chunk/index/query và inspect retrieved evidence.

### Senior

Tách lỗi retrieval khỏi lỗi generation, thiết kế evaluation và security filter.

### Technical Lead / Architect

Quyết định khi nào RAG phù hợp, dữ liệu nào phải deterministic lookup, quyền truy cập nằm ở đâu và observability/evaluation vận hành thế nào.

## 11. Key takeaway

* Không thể đánh giá RAG chỉ bằng nhìn câu trả lời cuối.
* Retrieval quality phải được đo độc lập.
* Authorization và business correctness phải nằm ở deterministic application layer, không giao cho model quyết định.
