# 1. CLR Tiered Compilation + Dynamic PGO

## 1. What is it?

Tiered Compilation cho phép CLR compile cùng một method theo nhiều mức tối ưu. Ban đầu runtime ưu tiên compile nhanh để giảm startup cost; khi method trở thành hot path, JIT có thể recompile ở tier cao hơn. Dynamic PGO bổ sung runtime profile để JIT tối ưu theo branch/type thực sự xuất hiện.

Mental model:

```text
first execution → Tier 0 → runtime profiling → hot method → Tier 1 + PGO
```

## 2. Why does it exist?

Nếu tối ưu mạnh mọi method từ đầu, startup chậm. Nếu chỉ compile nhanh, throughput dài hạn kém. Tiering cân bằng cold-start và steady-state performance.

## 3. How does it work?

JIT quan sát execution frequency và profile. Một interface call có nhiều implementation trên lý thuyết nhưng nếu production gần như luôn dùng một type, optimized tier có thể tạo machine code tốt hơn cho path đó.

## 4. Practical implementation

Đừng “tối ưu JIT” trước. Hãy benchmark đúng bằng BenchmarkDotNet:

```csharp
[MemoryDiagnoser]
public class PricingBenchmarks
{
    private readonly IPricePolicy _policy = new DefaultPricePolicy();
    private readonly Order _order = Order.CreateSample();

    [Benchmark]
    public decimal Calculate() => _policy.Calculate(_order);
}
```

Warmup rất quan trọng vì cold execution và steady state khác nhau.

## 5. Real production scenario

Một ASP.NET Core API mới scale-out có CPU và p95 cao trong vài chục giây đầu, sau đó ổn định dù traffic không đổi. JIT, cache warming và connection setup đều có thể góp phần.

## 6. Failure scenario & troubleshooting

**Symptom** → instance mới chậm hơn instance cũ.  
**Evidence** → DB latency ổn, CPU giảm dần theo tuổi instance.  
**Hypothesis** → warmup/JIT thay vì regression business logic.  
**Diagnosis** → profiler, `dotnet-trace`, so sánh cold/warm runs.  
**Fix** → readiness/pre-warm/capacity headroom.  
**Verification** → đo riêng cold p95 và warm p95.

## 7. Common mistakes

* Benchmark bằng một `Stopwatch` run.
* So sánh Debug với Release.
* Dùng request đầu tiên để capacity-plan.
* Tối ưu CPU khi bottleneck thật nằm ở I/O.

## 8. Alternatives

ReadyToRun giảm một phần JIT cost. Native AOT giảm startup/memory trong một số workload nhưng hạn chế dynamic features. JIT vẫn rất phù hợp cho long-running services.

## 9. Trade-offs

### Advantages
* Startup và steady-state được cân bằng.
* Hot paths có thể được tối ưu sâu.

### Costs / Risks
* Performance thay đổi sau warmup.
* Benchmark methodology sai dễ dẫn tới kết luận sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu IL được JIT thành machine code.

### Middle
Phân biệt cold-start và steady state.

### Senior
Dùng profiling để xác định hot path thay vì đoán.

## 11. Key takeaway

* JIT optimization là động.
* Warmup ảnh hưởng benchmark và production.
* Tối ưu chỉ sau khi có profiling evidence.

# 2. ASP.NET Core Partitioned Rate Limiting

## 1. What is it?

Partitioned rate limiting tạo limiter riêng theo tenant, user, API key hoặc IP thay vì một global bucket duy nhất.

## 2. Why does it exist?

Global limit có thể để một noisy tenant chiếm toàn capacity. Partitioning cung cấp fairness và admission control trước khi CPU, DB pool hoặc downstream quota bị saturation.

## 3. How does it work?

```text
request → resolve identity → partition key → limiter → allow / 429
```

Token Bucket phù hợp burst có kiểm soát; Concurrency Limiter phù hợp expensive operations giữ resource lâu.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.GlobalLimiter =
        PartitionedRateLimiter.Create<HttpContext, string>(context =>
        {
            var tenant = context.User.FindFirst("tenant_id")?.Value ?? "anonymous";

            return RateLimitPartition.GetTokenBucketLimiter(
                tenant,
                _ => new TokenBucketRateLimiterOptions
                {
                    TokenLimit = 100,
                    TokensPerPeriod = 50,
                    ReplenishmentPeriod = TimeSpan.FromSeconds(10),
                    AutoReplenishment = true,
                    QueueLimit = 0
                });
        });

    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});
```

## 5. Real production scenario

Export report chỉ 20 RPS nhưng mỗi request giữ DB connection 10 giây. Requests/minute không bảo vệ đúng bottleneck; concurrency limit 5 exports/tenant hợp lý hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → pool exhaustion dù rate limit tồn tại.  
**Evidence** → active long-running requests cao.  
**Hypothesis** → limiter đo sai scarce resource.  
**Fix** → concurrency limiter, timeout, queue long-running work.  
**Verification** → active requests và DB pool ổn định.

## 7. Common mistakes

* Tin raw IP sau reverse proxy.
* Dùng user-controlled header làm trusted key.
* Queue quá lớn trong limiter.
* Nghĩ in-memory limiter là distributed limit.

## 8. Alternatives

Azure API Management, edge/reverse-proxy limit, Redis distributed counters, queue-based load leveling.

## 9. Trade-offs

### Advantages
* Fairness tốt hơn.
* Protect capacity trước saturation.

### Costs / Risks
* Distributed semantics khó hơn khi scale-out.
* Policy sai có thể reject legitimate users.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu 429 khác 500.

### Middle
Biết cấu hình limiter và client backoff.

### Senior
Chọn limiter dựa trên resource cost.

### Technical Lead / Architect
Quyết định limit ở edge, gateway hay application.

## 11. Key takeaway

* Rate limiting là capacity protection.
* Partition theo business identity thường tốt hơn global limit.
* Multi-instance làm in-memory limit thành per-instance limit.

# 3. EF Core optimistic concurrency với `rowversion`

## 1. What is it?

Optimistic concurrency cho phép nhiều users đọc cùng record mà không giữ lock dài; lúc update, application kiểm tra record vẫn ở version cũ.

## 2. Why does it exist?

Không kiểm tra version có thể gây lost update: A và B cùng đọc version 10, A save version 11, B sau đó silently overwrite từ snapshot cũ.

## 3. How does it work?

EF Core tạo update tương tự:

```sql
UPDATE Orders
SET Status = @status
WHERE Id = @id
  AND RowVersion = @originalVersion;
```

0 rows affected → `DbUpdateConcurrencyException`.

## 4. Practical implementation

```csharp
public sealed class Order
{
    public Guid Id { get; set; }
    public string Status { get; set; } = null!;

    [Timestamp]
    public byte[] RowVersion { get; set; } = null!;
}
```

```csharp
try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new
    {
        code = "order_concurrency_conflict"
    });
}
```

## 5. Real production scenario

CS agent sửa Order cùng lúc payment webhook cập nhật trạng thái. Giant PUT entity dễ overwrite field không liên quan; concurrency token kết hợp command hẹp sẽ an toàn hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → user save thành công nhưng dữ liệu người khác biến mất.  
**Evidence** → update không có version predicate.  
**Hypothesis** → lost update.  
**Fix** → concurrency token + narrow commands + conflict contract.  
**Verification** → integration test hai DbContext cùng đọc một version.

## 7. Common mistakes

* Auto-retry conflict vô điều kiện.
* Reload rồi overwrite lại và gọi đó là “merge”.
* Nhầm `rowversion` với timestamp thời gian.
* Không gửi version tới disconnected client.

## 8. Alternatives

Application-managed version, HTTP `ETag` + `If-Match`, pessimistic locking cho short critical sections.

## 9. Trade-offs

### Advantages
* Không giữ long lock.
* Detect lost update rõ.

### Costs / Risks
* Conflict resolution chuyển lên application/UI.
* Conflict nhiều nếu aggregate quá lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu stale write.

### Middle
Biết cấu hình concurrency token.

### Senior
Phân biệt retry kỹ thuật và business merge.

### Technical Lead / Architect
Thiết kế write boundary để giảm contention.

## 11. Key takeaway

* Optimistic concurrency phát hiện stale write.
* Nó không tự quyết định ai đúng.
* Write semantics quan trọng hơn chỉ thêm attribute.

# 4. SQL Server deadlock và transaction design

## 1. What is it?

Deadlock là cycle chờ locks:

```text
T1 giữ Order, chờ Payment
T2 giữ Payment, chờ Order
```

SQL Server phát hiện cycle và rollback một victim.

## 2. Why does it exist?

Isolation cần locks; concurrent transaction paths lấy resource khác thứ tự có thể tạo cycle.

## 3. How does it work?

Database xây wait graph. Khi phát hiện cycle, một transaction bị chọn làm victim dựa trên priority/cost và application nhận error 1205.

## 4. Practical implementation

Giữ resource order nhất quán:

```text
Flow A: Orders → Payments
Flow B: Orders → Payments
```

Và transaction ngắn:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

var order = await db.Orders.SingleAsync(x => x.Id == orderId, ct);
order.Status = OrderStatus.Paid;

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

## 5. Real production scenario

Checkout update Orders rồi Inventory; reconciliation update Inventory rồi Orders. Under load, deadlock tăng mạnh dù từng query riêng lẻ khá nhanh.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL error 1205 tăng theo traffic.  
**Evidence** → deadlock graph cho thấy access order trái ngược.  
**Hypothesis** → cyclic lock acquisition.  
**Fix** → consistent order, shorter transaction, better access path/indexes.  
**Verification** → load test và theo dõi deadlock events.

## 7. Common mistakes

* Tăng timeout để “fix”.
* Thêm `NOLOCK` khắp nơi.
* Retry vô hạn.
* Giữ transaction trong network call.

## 8. Alternatives

Optimistic concurrency, snapshot isolation trong trường hợp phù hợp, queue serialize một số workflow.

## 9. Trade-offs

### Advantages
* Locking bảo vệ consistency.

### Costs / Risks
* Contention tăng theo concurrency.
* Transaction dài tăng blast radius.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu deadlock là cycle.

### Middle
Biết xem victim/error.

### Senior
Đọc deadlock graph và lock order.

### Technical Lead / Architect
Thiết kế transaction boundary ngắn và predictable.

## 11. Key takeaway

* Deadlock phải phân tích toàn cycle.
* Retry không thay thế root-cause fix.
* Consistent order + short transaction là nền tảng.

# 5. Redis cache stampede và TTL jitter

## 1. What is it?

Cache stampede xảy ra khi hot key expire và nhiều requests cùng miss, rồi cùng query origin/database.

## 2. Why does it exist?

Expiration tạo burst: trước TTL tất cả hit, sau TTL tất cả miss. Với hot key, một expiration có thể thành production incident.

## 3. How does it work?

```text
N requests → expired key → N misses → N DB queries
```

Single-flight chỉ cho một loader rebuild; TTL jitter tránh nhiều keys expire cùng thời điểm.

## 4. Practical implementation

```csharp
var ttl = TimeSpan.FromMinutes(5)
          + TimeSpan.FromSeconds(Random.Shared.Next(0, 30));

await cache.SetStringAsync(
    key,
    json,
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = ttl
    },
    ct);
```

Với cực hot keys, thêm local single-flight hoặc stale-while-revalidate.

## 5. Real production scenario

20 sản phẩm hot được warm cùng lúc sau deploy, tất cả TTL 5 phút. Năm phút sau DB QPS spike vì keys expire đồng bộ.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis hit rate giảm ngắn, DB QPS tăng theo chu kỳ.  
**Evidence** → spike lặp đúng expiration interval.  
**Hypothesis** → stampede.  
**Fix** → jitter, single-flight, refresh-ahead.  
**Verification** → DB load không còn sawtooth.

## 7. Common mistakes

* Mọi key TTL đúng 300 giây.
* Distributed lock cho mọi miss.
* Redis down thì retry liên tục.
* Cache null quá lâu.
* Coi cache là source of truth.

## 8. Alternatives

CDN cho public content, IMemoryCache, background refresh, materialized view.

## 9. Trade-offs

### Advantages
* Giảm origin burst.
* Ổn định tail latency.

### Costs / Risks
* Stale data nếu dùng stale-while-revalidate.
* Distributed coordination thêm complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu một miss có thể gây nhiều downstream queries.

### Middle
Biết TTL và cache-aside.

### Senior
Nhận diện stampede từ telemetry.

### Technical Lead / Architect
Xác định stale tolerance và fallback khi Redis unavailable.

## 11. Key takeaway

* Expiry là một load event.
* TTL jitter rẻ nhưng hiệu quả.
* Hot key cần chiến lược hơn “miss rồi query DB”.

# 6. Azure Service Bus PeekLock và idempotent consumer

## 1. What is it?

Ở `PeekLock`, message được giao nhưng chưa xóa. Consumer xử lý rồi `Complete`; nếu crash hoặc lock expire, message có thể được giao lại.

## 2. Why does it exist?

Receive-and-delete có nguy cơ mất message nếu process crash ngay sau receive. PeekLock đổi silent loss thành possible duplicate delivery.

## 3. How does it work?

```text
receive → temporary lock
  ├─ success → Complete
  ├─ transient fail → Abandon/retry
  ├─ poison → DeadLetter
  └─ crash/lock expiry → redelivery
```

## 4. Practical implementation

```csharp
var processor = client.CreateProcessor(queueName, new ServiceBusProcessorOptions
{
    AutoCompleteMessages = false,
    MaxConcurrentCalls = 8,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(10)
});

processor.ProcessMessageAsync += async args =>
{
    var id = args.Message.MessageId;

    if (await inbox.ExistsAsync(id, args.CancellationToken))
    {
        await args.CompleteMessageAsync(args.Message);
        return;
    }

    await handler.HandleAsync(args.Message, args.CancellationToken);
    await inbox.MarkProcessedAsync(id, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message);
};
```

## 5. Real production scenario

Payment handler charge thành công nhưng process crash trước `Complete`. Message redeliver. Nếu downstream charge không idempotent, customer có thể bị double charge.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng MessageId xuất hiện nhiều lần.  
**Evidence** → lock lost, process restart hoặc settlement fail.  
**Hypothesis** → normal at-least-once redelivery.  
**Fix** → inbox/idempotency, đúng lock duration, DLQ policy.  
**Verification** → replay message nhưng business effect chỉ xảy ra một lần.

## 7. Common mistakes

* Nghĩ PeekLock là exactly-once.
* `Complete` trước business commit.
* Poison message retry vô hạn.
* Tăng concurrency không kiểm tra downstream capacity.

## 8. Alternatives

Receive-and-delete khi loss chấp nhận được, natural idempotency key, durable workflow cho long-running operations.

## 9. Trade-offs

### Advantages
* Crash safety tốt.
* Retry/DLQ tích hợp.

### Costs / Risks
* Duplicate delivery là bình thường.
* Idempotency phải nằm ở application.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `Complete` là acknowledge.

### Middle
Biết settlement, retry, DLQ.

### Senior
Thiết kế idempotent consumer.

### Technical Lead / Architect
Định nghĩa delivery semantics end-to-end.

## 11. Key takeaway

* At-least-once nghĩa duplicate là expected.
* Exactly-once business effect không tự đến từ broker.
* Idempotency phải bảo vệ side effect thật.

# 7. Kubernetes graceful shutdown

## 1. What is it?

Khi Pod terminate, Kubernetes thường gửi `SIGTERM`, cho application một grace period, rồi mới `SIGKILL` nếu process chưa exit.

## 2. Why does it exist?

Kill ngay có thể cắt HTTP requests, làm message lock expire, bỏ dở telemetry flush hoặc transaction.

## 3. How does it work?

```text
termination requested
→ readiness drain
→ SIGTERM
→ stop receiving new work
→ finish in-flight work
→ exit before grace period
```

## 4. Practical implementation

```csharp
public sealed class Worker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var item = await queue.ReceiveAsync(stoppingToken);
            await ProcessAsync(item, stoppingToken);
        }
    }
}
```

```yaml
spec:
  terminationGracePeriodSeconds: 60
```

## 5. Real production scenario

Rolling deployment tạo 502 chỉ trong lúc old Pods terminate vì process exit trước khi load balancer ngừng route traffic.

## 6. Failure scenario & troubleshooting

**Symptom** → 499/502 spike lúc deploy.  
**Evidence** → request traces trùng Pod termination.  
**Hypothesis** → routing/shutdown race.  
**Fix** → readiness drain, grace period, cancellation-aware handlers.  
**Verification** → load test xuyên suốt rollout.

## 7. Common mistakes

* Liveness và readiness giống nhau.
* `preStop sleep` theo cargo cult.
* Grace period ngắn hơn valid processing.
* Worker vẫn nhận message mới khi stopping.

## 8. Alternatives

App Service/Container Apps có lifecycle riêng; queue consumer có thể stop receive rồi drain; long workflow nên checkpoint.

## 9. Trade-offs

### Advantages
* Giảm deployment-induced errors.
* Cho in-flight work hoàn tất.

### Costs / Risks
* Grace period dài làm rollout chậm.
* Streaming/long requests khó drain.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu Pod là disposable instance.

### Middle
Propagate `CancellationToken`.

### Senior
Debug deployment/shutdown failures.

### Technical Lead / Architect
Thiết kế termination như normal lifecycle event.

## 11. Key takeaway

* Rolling deployment không tự động zero downtime.
* Routing và process shutdown phải phối hợp.
* Luôn test rollout dưới load.

# 8. OpenTelemetry metrics cardinality

## 1. What is it?

Metric cardinality là số distinct time series do tổ hợp labels/attributes tạo ra.

```text
http_requests_total{method, route, status}
```

Nếu route dùng template `/orders/{id}`, cardinality bounded. Nếu dùng raw path `/orders/12345`, mỗi order có thể tạo series mới.

## 2. Why does it exist?

Metrics aggregate rất hiệu quả chỉ khi dimensions bounded. `user_id`, `request_id`, `order_id`, raw URL hoặc exception message có thể làm backend lưu hàng triệu series.

## 3. How does it work?

Cardinality nhân theo dimensions. 10 endpoints × 5 statuses × 3 regions × 50 tenants = tối đa khoảng 7.500 combinations. Thêm 500.000 user IDs làm scale thay đổi hoàn toàn.

## 4. Practical implementation

```csharp
private static readonly Meter Meter = new("Checkout.Api");
private static readonly Counter<long> Orders =
    Meter.CreateCounter<long>("checkout.orders");

Orders.Add(1,
    new("result", result),
    new("region", region));
```

Không gắn `order_id` hoặc `request_id` vào metric mặc định; context đó phù hợp logs/traces hơn.

## 5. Real production scenario

CMS thêm raw request path vào metric. Hàng trăm nghìn dynamic slugs làm active series tăng mạnh, dashboard chậm và monitoring bill tăng.

## 6. Failure scenario & troubleshooting

**Symptom** → metrics ingestion/cost/query latency spike.  
**Evidence** → một label có cardinality gần bằng request/user count.  
**Hypothesis** → unbounded dimension.  
**Fix** → route templates, remove high-cardinality labels, chuyển detail sang traces/logs.  
**Verification** → active series giảm.

## 7. Common mistakes

* Correlation ID trong metric.
* Exception message làm label.
* Raw URL.
* Tenant dimension cực lớn không capacity-plan.

## 8. Alternatives

Logs cho event detail, traces cho causal chain, metrics cho aggregate signal, exemplars để liên kết metric với trace.

## 9. Trade-offs

### Advantages
* Low-cardinality metrics nhanh và predictable.

### Costs / Risks
* Không chứa mọi request-specific context.
* Cần logs/traces để drill-down.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu mỗi label combination tạo series.

### Middle
Biết dữ liệu nào thuộc metric/log/trace.

### Senior
Review cardinality budget.

### Technical Lead / Architect
Đặt telemetry governance và cost controls.

## 11. Key takeaway

* Metric không phải log có labels.
* Cardinality tăng theo tổ hợp dimensions.
* Identity chi tiết nên nằm ở traces/logs.

# 9. TypeScript discriminated unions cho API state

## 1. What is it?

Discriminated union mô hình hóa finite states bằng một discriminator:

```ts
type LoadState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error };
```

## 2. Why does it exist?

Nhiều booleans tạo impossible states: `isLoading=true`, `hasError=true`, đồng thời vẫn có data. Union biến state machine thành type contract.

## 3. How does it work?

TypeScript narrowing theo `status`, nên branch `success` chắc chắn có `data`, branch `error` chắc chắn có `error`.

## 4. Practical implementation

```ts
const state = ref<LoadState<Product>>({ status: 'idle' });

async function load(id: string) {
  state.value = { status: 'loading' };

  try {
    const { data } = await api.get<Product>(`/products/${id}`);
    state.value = { status: 'success', data };
  } catch (e) {
    state.value = {
      status: 'error',
      error: e instanceof Error ? e : new Error('Unknown error')
    };
  }
}
```

## 5. Real production scenario

Checkout có initial, validating, submitting, requires-3ds, succeeded, failed. Boolean soup dễ bật sai button hoặc hiện nhiều trạng thái cùng lúc.

## 6. Failure scenario & troubleshooting

**Symptom** → spinner và error cùng hiển thị.  
**Evidence** → nhiều boolean update độc lập.  
**Hypothesis** → impossible/interleaved state.  
**Fix** → finite union, atomic transition.  
**Verification** → tests theo từng state/transition.

## 7. Common mistakes

* Dùng `status: string`.
* Data optional ở mọi state.
* Giant union cho toàn app.
* Không model stale request/race.

## 8. Alternatives

XState cho workflow phức tạp, TanStack Query cho server state, boolean đơn giản cho hai trạng thái thực sự độc lập.

## 9. Trade-offs

### Advantages
* Impossible states bị loại ở compile time.
* Refactor/test dễ hơn.

### Costs / Risks
* Verbose hơn cho trivial UI.
* Workflow lớn vẫn cần state-machine design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu union là “một trong các shapes”.

### Middle
Dùng narrowing đúng.

### Senior
Model async race/error states.

### Technical Lead / Architect
Tách server state, URL state, local UI state và workflow state.

## 11. Key takeaway

* Boolean soup thường là dấu hiệu state model yếu.
* Type system có thể loại impossible states.
* State modeling là design problem.

# 10. Modular Monolith database ownership

## 1. What is it?

Modular Monolith là một deployable application nhưng chia thành modules có business boundary, contract và data ownership rõ.

Folder đẹp chưa đủ. Nếu mọi module cùng đọc/ghi mọi tables và reference internals của nhau, hệ thống vẫn tightly coupled.

## 2. Why does it exist?

Microservices mang network failure, distributed tracing, messaging, eventual consistency và deployment complexity. Nhiều hệ thống cần domain boundaries nhưng chưa cần independent deployment.

## 3. How does it work?

```text
Orders Module
  owns orders.* data
  exposes contracts/events
        ↓
Billing Module
  owns billing.* data
  consumes explicit contracts
```

Cùng một physical SQL Server vẫn có thể có logical ownership rõ.

## 4. Practical implementation

```text
Modules/
  Orders/
    Orders.Application/
    Orders.Domain/
    Orders.Infrastructure/
  Billing/
    Billing.Application/
    Billing.Domain/
    Billing.Infrastructure/
```

Schemas:

```sql
orders.Orders
orders.OrderLines
billing.Payments
billing.Refunds
```

Contract:

```csharp
public interface IOrdersQuery
{
    Task<OrderSummary?> GetSummaryAsync(
        Guid orderId,
        CancellationToken ct);
}
```

Billing dùng contract thay vì inject `OrdersDbContext`.

## 5. Real production scenario

Sau hai năm, Billing cần tách riêng vì compliance. Nếu data ownership rõ, local contract có thể được thay bằng network/message boundary. Nếu Billing JOIN trực tiếp 14 tables module khác, extraction trở thành database surgery.

## 6. Failure scenario & troubleshooting

**Symptom** → đổi schema Catalog làm nhiều modules fail.  
**Evidence** → cross-module table writes, shared entities, circular references.  
**Hypothesis** → boundary chỉ tồn tại ở folder.  
**Fix** → define owners, contracts, read models/events, cấm direct writes sang data module khác.  
**Verification** → architecture tests và dependency review.

## 7. Common mistakes

* Giant `Shared` project chứa mọi domain entity.
* Một `AppDbContext` dùng tự do ở mọi module.
* Tạo internal HTTP chỉ để “giống microservices”.
* Chia module theo technical layer thay vì business capability.

## 8. Alternatives

Layered Monolith cho domain nhỏ, Clean Architecture một boundary, Microservices khi independent deployment/scaling/ownership thật sự justify operational cost.

## 9. Trade-offs

### Advantages
* Boundary rõ nhưng vẫn giữ local-call simplicity.
* Transaction local dễ hơn distributed system.
* Tạo optionality cho future extraction.

### Costs / Risks
* Cần discipline để enforce.
* Cross-module reporting có thể cần read model.
* Có thể over-modularize domain nhỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu module sở hữu business capability.

### Middle
Không reference entity/DbContext của module khác tùy tiện.

### Senior
Thiết kế contract, data ownership và communication.

### Technical Lead / Architect
Chọn boundaries theo invariants, rate of change, ownership và future extraction pressure.

## 11. Key takeaway

* Modularity thật nằm ở ownership và dependency direction.
* Shared database không bắt buộc shared ownership.
* Modular Monolith thường là lựa chọn tốt trước khi microservices có business justification.
