# 1. C# `IAsyncEnumerable<T>`: stream dữ liệu theo nhịp consumer thay vì buffer toàn bộ kết quả trong memory

## 1. What is it?

`IAsyncEnumerable<T>` biểu diễn một chuỗi phần tử được tạo ra **bất đồng bộ theo thời gian**. Mental model quan trọng là: consumer không cần chờ producer tạo xong toàn bộ collection rồi mới bắt đầu xử lý.

```text
Producer
  ├─ item 1 ─────► Consumer xử lý
  ├─ item 2 ─────► Consumer xử lý
  ├─ item 3 ─────► Consumer xử lý
  └─ ...
```

Khác với `Task<List<T>>`, nơi toàn bộ dữ liệu thường phải được materialize trước khi trả về, `IAsyncEnumerable<T>` cho phép pull từng phần tử qua `await foreach`.

## 2. Why does it exist?

Nhiều workload tạo dữ liệu từng phần:

* đọc database theo stream,
* xử lý file lớn,
* đọc paginated external API,
* consume message-like sequence,
* stream response về client.

Nếu luôn gom toàn bộ vào `List<T>`, memory usage tăng theo kích thước dữ liệu và time-to-first-item bị trì hoãn.

## 3. How does it work?

Compiler biến async iterator thành state machine. Mỗi lần consumer yêu cầu phần tử tiếp theo, `MoveNextAsync()` tiến state machine cho tới khi có `yield return`, hoàn tất hoặc bị cancel.

```csharp
public async IAsyncEnumerable<Order> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken cancellationToken = default)
{
    await foreach (var order in _repository.StreamAsync(cancellationToken))
    {
        yield return order;
    }
}
```

`await foreach` tạo consumption loop bất đồng bộ. Cancellation cần được propagate rõ ràng, đặc biệt khi iterator gọi database hoặc network.

## 4. Practical implementation

Ví dụ xử lý nhiều records mà không materialize tất cả:

```csharp
await foreach (var order in service.StreamOrdersAsync(ct))
{
    await processor.ProcessAsync(order, ct);
}
```

Với EF Core:

```csharp
await foreach (var order in db.Orders
    .AsNoTracking()
    .OrderBy(x => x.Id)
    .AsAsyncEnumerable()
    .WithCancellation(ct))
{
    await WriteToExportAsync(order, ct);
}
```

Điểm quan trọng: streaming database query thường giữ connection/data reader mở lâu hơn. Memory giảm nhưng connection lifetime có thể tăng.

## 5. Real production scenario

Một service export 500.000 order trước đây gọi `ToListAsync()` rồi mới ghi CSV. Memory tăng hàng trăm MB và request chỉ bắt đầu trả dữ liệu sau khi query hoàn tất.

Chuyển sang `IAsyncEnumerable<T>` giúp xử lý từng row và stream output sớm hơn. Nhưng team cũng phải kiểm soát tốc độ consumer để tránh giữ SQL connection quá lâu trong request chậm.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL connection pool cạn dù memory đã giảm mạnh.

**Evidence** → mỗi export giữ data reader/connection trong thời gian dài; client download chậm.

**Hypothesis** → database streaming bị coupling trực tiếp với tốc độ network của client.

**Diagnosis** → đo query duration, connection lifetime và response throughput.

**Fix** → tách producer/consumer bằng bounded buffer, batch theo page, hoặc materialize từng chunk thay vì giữ connection xuyên suốt toàn bộ response.

**Verification** → load test nhiều client chậm và theo dõi active DB connections.

## 7. Common mistakes

* Nghĩ `IAsyncEnumerable<T>` tự động tạo backpressure hoàn hảo cho mọi dependency.
* Bỏ qua `CancellationToken`.
* Stream trực tiếp database tới slow client mà không tính connection lifetime.
* Dùng async iterator cho dataset nhỏ rồi tăng complexity không cần thiết.
* Gọi `.ToListAsync()` ngay sau `AsAsyncEnumerable()` rồi mất toàn bộ lợi ích streaming.

## 8. Alternatives

* `Task<List<T>>`: đơn giản, phù hợp dataset nhỏ.
* Keyset pagination: tốt khi muốn chunk rõ ràng và giải phóng DB connection giữa các page.
* `Channel<T>`: phù hợp producer/consumer concurrent với bounded capacity.
* `PipeReader/PipeWriter`: tốt cho byte-oriented high-performance streaming.

## 9. Trade-offs

### Advantages

* Giảm peak memory.
* Có thể cải thiện time-to-first-item.
* Tự nhiên cho dữ liệu sinh ra theo thời gian.

### Costs / Risks

* Lifetime của dependency có thể kéo dài.
* Error có thể xảy ra giữa stream sau khi client đã nhận một phần dữ liệu.
* Debugging cancellation và partial results phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác biệt giữa “trả cả collection” và “yield từng item”.

### Middle

Biết implement async iterator, cancellation và `await foreach`.

### Senior

Đánh giá connection lifetime, partial failure, buffering và backpressure.

### Technical Lead / Architect

Quyết định khi nào streaming thực sự giảm cost và khi nào chunking/pagination đơn giản hơn.

## 11. Key takeaway

* `IAsyncEnumerable<T>` tối ưu **flow**, không chỉ syntax.
* Streaming giảm memory nhưng có thể kéo dài dependency lifetime.
* Đừng nối trực tiếp slow consumer với scarce resource nếu không có buffering strategy.

# 2. ASP.NET Core Rate Limiting theo partition: bảo vệ capacity mà không để một tenant hoặc API key chiếm hết quota của hệ thống

## 1. What is it?

Rate limiting kiểm soát số request được phép đi qua trong một khoảng thời gian hoặc theo số request đang thực thi đồng thời.

Partitioned rate limiting chia quota theo một key như:

* tenant,
* API key,
* user,
* client application,
* endpoint group.

Mental model:

```text
Tenant A ─► limiter A
Tenant B ─► limiter B
Tenant C ─► limiter C
```

thay vì tất cả client tranh chung một bucket.

## 2. Why does it exist?

Nếu chỉ có global limiter, một tenant noisy có thể sử dụng gần hết quota và làm tenant khác bị từ chối dù họ không tạo tải bất thường.

Ngược lại, không rate limit thì burst traffic, retry storm hoặc abusive client có thể làm application, database hoặc external dependencies cạn capacity.

## 3. How does it work?

ASP.NET Core Rate Limiting middleware có thể chọn limiter dựa trên request context.

Các thuật toán phổ biến:

* Fixed Window,
* Sliding Window,
* Token Bucket,
* Concurrency Limiter.

Partition key nên đại diện cho entity mà business muốn áp quota.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(context =>
    {
        var tenant = context.User.FindFirst("tenant_id")?.Value ?? "anonymous";

        return RateLimitPartition.GetTokenBucketLimiter(
            tenant,
            _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 50,
                ReplenishmentPeriod = TimeSpan.FromSeconds(10),
                QueueLimit = 20,
                AutoReplenishment = true
            });
    });

    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});
```

Response nên trả `429` và nếu phù hợp có `Retry-After`.

## 5. Real production scenario

Một SaaS API có một integration client gửi batch hàng chục nghìn request sau reconnect. Nếu không partition, các customer khác thấy latency tăng và 5xx do DB pool bị bão hòa.

Partition theo tenant giúp cô lập fairness, trong khi global concurrency guard vẫn có thể bảo vệ hard capacity của service.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều người dùng hợp lệ bị 429 cùng lúc.

**Evidence** → limiter partition key đang lấy client IP từ reverse proxy, nhưng tất cả request đều thấy cùng IP của proxy.

**Hypothesis** → partition key không phản ánh client thật.

**Diagnosis** → kiểm tra forwarded headers, authentication claims và limiter metrics.

**Fix** → dùng trusted forwarded-header configuration hoặc quota key ở application layer như tenant/API key.

**Verification** → test qua production-like proxy path với nhiều tenants.

## 7. Common mistakes

* Dùng IP làm identity duy nhất trong hệ thống sau NAT/proxy.
* Chỉ rate limit ở application sau khi request đã tiêu tốn nhiều resource.
* Retry 429 ngay lập tức mà không backoff.
* Không monitor rejected requests và queue depth.
* Dùng một quota chung cho endpoint rẻ và endpoint cực đắt.

## 8. Alternatives

* API Management / gateway rate limiting.
* CDN/WAF edge throttling cho traffic internet.
* Concurrency limiting cho resource-bound endpoint.
* Queue-based admission control cho workload có thể async.

## 9. Trade-offs

### Advantages

* Bảo vệ downstream capacity.
* Tăng fairness giữa tenants.
* Hạn chế blast radius của buggy client.

### Costs / Risks

* Quota policy là business decision, không chỉ technical setting.
* Distributed instances có thể cần centralized/gateway enforcement nếu quota phải toàn cục.
* Queueing sai có thể chỉ chuyển failure từ reject sang latency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `429 Too Many Requests` và quota cơ bản.

### Middle

Implement limiter theo user/tenant và trả response đúng.

### Senior

Phân biệt rate, concurrency, fairness và downstream capacity.

### Technical Lead / Architect

Quyết định enforcement boundary: edge, gateway, service hay kết hợp nhiều tầng.

## 11. Key takeaway

* Rate limiting là capacity protection và fairness control.
* Partition key sai có thể tạo unfairness lớn hơn không limit.
* Global capacity và per-tenant quota thường là hai concern khác nhau.

# 3. SQL deadlock: đọc wait-for graph và sửa thứ tự truy cập thay vì tăng timeout hoặc retry mù quáng

## 1. What is it?

Deadlock xảy ra khi hai hoặc nhiều transaction giữ resource mà transaction khác cần và tạo vòng chờ không thể tự giải phóng.

```text
Tx A giữ Row 1 → chờ Row 2
Tx B giữ Row 2 → chờ Row 1
```

Database phát hiện cycle và chọn một transaction làm victim để rollback.

## 2. Why does it exist?

Locking bảo vệ consistency, nhưng nhiều transaction đồng thời có thể truy cập resource theo thứ tự khác nhau.

Không có deadlock detection, các transaction có thể chờ vô hạn. Database vì vậy phải phá vòng chờ bằng cách hủy một transaction.

## 3. How does it work?

Wait-for graph mô hình hóa dependency:

```text
Tx A ─ waits for ─► resource held by Tx B
Tx B ─ waits for ─► resource held by Tx A
```

Khi có cycle, deadlock tồn tại.

Index, access path và isolation level ảnh hưởng resource nào bị lock và trong bao lâu.

## 4. Practical implementation

Ví dụ nguy hiểm:

Transaction A:

```sql
UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1;
UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 2;
```

Transaction B:

```sql
UPDATE Accounts SET Balance = Balance - 50 WHERE Id = 2;
UPDATE Accounts SET Balance = Balance + 50 WHERE Id = 1;
```

Một cách giảm deadlock là luôn lock/update account theo thứ tự deterministic, ví dụ `ORDER BY Id` logic ở application.

## 5. Real production scenario

Một payment service cập nhật `Orders` rồi `Payments`; job reconciliation lại cập nhật `Payments` rồi `Orders`. Hai flow chạy đồng thời tạo deadlock ngẫu nhiên dưới tải cao.

Sửa đúng là thống nhất thứ tự truy cập và rút ngắn transaction, không phải chỉ tăng command timeout.

## 6. Failure scenario & troubleshooting

**Symptom** → application thỉnh thoảng nhận deadlock victim error.

**Evidence** → database deadlock graph cho thấy hai statements giữ lock chéo.

**Hypothesis** → transaction access cùng resource theo thứ tự khác nhau.

**Diagnosis** → đọc deadlock graph, object/index involved, lock mode và statements.

**Fix** → thống nhất access order, tối ưu query/index để giảm lock footprint, giảm transaction duration.

**Verification** → concurrency stress test và theo dõi deadlock count.

## 7. Common mistakes

* Tăng timeout dù deadlock không phải timeout problem.
* Retry vô hạn mà không sửa root cause.
* Giữ transaction mở qua network call.
* Query scan nhiều rows hơn cần thiết làm lock footprint lớn.
* Cho rằng deadlock chỉ xảy ra khi code “sai logic”.

## 8. Alternatives

* Optimistic concurrency cho một số workflow.
* Snapshot/row-versioned isolation để giảm read/write blocking trong trường hợp phù hợp.
* Queue/serialization một số critical operation nếu business throughput cho phép.

## 9. Trade-offs

### Advantages

* Locking cho consistency mạnh trong transaction.
* Retry nhỏ, bounded có thể xử lý deadlock hiếm sau khi root cause đã được giảm thiểu.

### Costs / Risks

* Retry tăng latency và load nếu deadlock thường xuyên.
* Isolation thấp hơn có thể tạo anomaly khác.
* Serialize workload giảm deadlock nhưng giảm throughput.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deadlock là vòng chờ, không chỉ là query chạy chậm.

### Middle

Biết giảm transaction scope và giữ access order nhất quán.

### Senior

Đọc deadlock graph và liên hệ với execution plan/index/lock behavior.

### Technical Lead / Architect

Thiết kế transaction boundaries và concurrency model để deadlock trở thành rare recoverable event thay vì trạng thái thường xuyên.

## 11. Key takeaway

* Deadlock phải được phân tích từ wait-for cycle.
* Retry chỉ là safety net, không phải root-cause fix.
* Thứ tự access và transaction duration thường quan trọng hơn timeout setting.

# 4. MongoDB embedding vs referencing: thiết kế document model từ access pattern và consistency boundary

## 1. What is it?

Trong MongoDB, data liên quan có thể được:

* **embed** trong cùng document,
* hoặc **reference** bằng identifier sang document khác.

Không nên chọn chỉ dựa trên quan hệ “1-n” như relational modeling. Quyết định phải dựa trên cách dữ liệu được đọc, cập nhật, tăng trưởng và sở hữu.

## 2. Why does it exist?

Document database tối ưu cho việc đọc một aggregate-like document trong ít round trip. Embedding giúp locality tốt, nhưng document có thể phình lớn và duplicate data.

Referencing giảm duplication và tách lifecycle, nhưng có thể cần nhiều query hoặc `$lookup`.

## 3. How does it work?

Embedding phù hợp khi child data:

* thuộc cùng lifecycle,
* thường được đọc cùng parent,
* số lượng bounded,
* cần atomic update trong một document.

Referencing phù hợp hơn khi:

* child có lifecycle riêng,
* cardinality rất lớn,
* được truy cập độc lập,
* nhiều parent cùng tham chiếu.

## 4. Practical implementation

Embedded order snapshot:

```json
{
  "_id": "order-123",
  "customerId": "customer-9",
  "items": [
    {
      "productId": "p-10",
      "name": "Keyboard",
      "unitPrice": 120,
      "quantity": 2
    }
  ]
}
```

Việc duplicate `name` và `unitPrice` có thể là chủ ý: order cần snapshot tại thời điểm mua, không nhất thiết phản ánh product hiện tại.

## 5. Real production scenario

Một CMS lưu page cùng blocks nhỏ, bounded và luôn render cùng page. Embedding có thể rất tự nhiên.

Ngược lại, nếu page có hàng trăm nghìn interaction records, embed toàn bộ sẽ tạo document tăng không giới hạn và contention khi update.

## 6. Failure scenario & troubleshooting

**Symptom** → document update ngày càng chậm, document size tăng mạnh.

**Evidence** → embedded array tăng không giới hạn theo thời gian.

**Hypothesis** → data có lifecycle/cardinality riêng nhưng bị model như child embedded.

**Diagnosis** → đo document size distribution, update pattern và read pattern.

**Fix** → tách collection, reference theo parent ID, hoặc archive/window dữ liệu.

**Verification** → benchmark read/write path thật sau migration.

## 7. Common mistakes

* Dịch nguyên schema SQL sang MongoDB với reference cho mọi relation.
* Embed array unbounded.
* Duplicate data nhưng không định nghĩa source of truth.
* Dùng `$lookup` khắp nơi rồi vô tình tái tạo relational joins không kiểm soát.
* Chọn schema trước khi hiểu access pattern.

## 8. Alternatives

* PostgreSQL/SQL Server nếu workload cần relational joins và constraints mạnh.
* Hybrid model: embed snapshot + reference canonical entity.
* CQRS/read model riêng nếu query shape khác write model đáng kể.

## 9. Trade-offs

### Advantages

* Embedding giảm round trip và tăng read locality.
* Referencing kiểm soát growth và tách ownership.

### Costs / Risks

* Embedding gây duplication và update fan-out nếu dữ liệu phải đồng bộ.
* Referencing tăng query complexity và consistency coordination.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu embed và reference là hai cách model relationship.

### Middle

Biết chọn dựa trên read/write pattern và cardinality.

### Senior

Phân tích consistency, growth, indexing và migration consequences.

### Technical Lead / Architect

Xác định aggregate/data ownership boundary và quyết định liệu MongoDB có thật sự phù hợp workload.

## 11. Key takeaway

* MongoDB schema nên đi từ access pattern, không từ ERD copy-paste.
* Embed khi dữ liệu cùng lifecycle và bounded.
* Reference khi lifecycle độc lập hoặc cardinality/growth lớn.

# 5. Anti-Corruption Layer: cô lập mô hình nội bộ khỏi contract kỳ quặc hoặc thay đổi liên tục của hệ thống bên ngoài

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary chuyển đổi giữa domain model nội bộ và model/protocol của external system hoặc bounded context khác.

```text
Internal Domain
      │
      ▼
Anti-Corruption Layer
      │ translate
      ▼
External API / Legacy System
```

Mục tiêu không phải “bọc API cho đẹp”, mà là ngăn semantic model bên ngoài rò vào core domain.

## 2. Why does it exist?

External system có thể dùng:

* naming khác,
* status code kỳ lạ,
* data shape legacy,
* null semantics không nhất quán,
* business concept khác nội bộ.

Nếu application dùng trực tiếp external DTO khắp nơi, thay đổi từ vendor lan xuyên codebase.

## 3. How does it work?

ACL thường gồm:

* client adapter,
* external DTO,
* mapping/translation,
* error normalization,
* resilience policy,
* contract tests.

Domain chỉ nhìn thấy interface theo ngôn ngữ nội bộ.

## 4. Practical implementation

```csharp
public interface IShippingQuoteService
{
    Task<ShippingQuote> GetQuoteAsync(
        Shipment shipment,
        CancellationToken cancellationToken);
}

public sealed class VendorShippingAdapter : IShippingQuoteService
{
    private readonly VendorClient _client;

    public async Task<ShippingQuote> GetQuoteAsync(
        Shipment shipment,
        CancellationToken ct)
    {
        var response = await _client.GetPriceAsync(
            VendorMapper.ToRequest(shipment), ct);

        return VendorMapper.ToDomain(response);
    }
}
```

`VendorQuoteResponse` không cần xuất hiện trong domain layer.

## 5. Real production scenario

Một e-commerce platform tích hợp carrier API trả trạng thái `A1`, `A2`, `R7`. Nếu những code này lan tới order domain, UI và reporting, thay đổi vendor trở thành migration toàn hệ thống.

ACL map chúng thành `ShipmentStatus` nội bộ và giữ vendor semantics ở integration boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → vendor đổi một enum value và nhiều module nội bộ crash/deserialization fail.

**Evidence** → external DTO được dùng trực tiếp qua nhiều layers.

**Hypothesis** → integration boundary bị leak.

**Diagnosis** → trace dependency từ vendor package/DTO vào application/domain.

**Fix** → gom translation vào adapter, version contract và map unknown values an toàn.

**Verification** → contract test với old/new vendor payload.

## 7. Common mistakes

* Tạo wrapper chỉ forward 1:1 method mà không translate semantics.
* Copy toàn bộ vendor SDK type vào domain API.
* Biến ACL thành “god integration service”.
* Bỏ qua idempotency, timeout và retry vì nghĩ ACL chỉ là mapping layer.
* Dùng domain model để deserialize trực tiếp external payload.

## 8. Alternatives

* Direct integration nếu dependency đơn giản, ổn định và blast radius nhỏ.
* Shared contract giữa bounded contexts nếu thật sự có shared language.
* Event-driven translation layer cho asynchronous integration.

## 9. Trade-offs

### Advantages

* Giảm coupling với external contract.
* Domain language sạch và ổn định hơn.
* Dễ thay vendor hoặc hỗ trợ nhiều provider.

### Costs / Risks

* Thêm mapping code và test surface.
* Có thể overengineer integration rất nhỏ.
* Translation semantics sai có thể che mất business nuance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain model.

### Middle

Implement adapter và mapping rõ ràng.

### Senior

Thiết kế error translation, resilience và contract testing.

### Technical Lead / Architect

Quyết định boundary nào cần ACL và đâu chỉ cần integration đơn giản.

## 11. Key takeaway

* ACL bảo vệ domain semantics, không chỉ che SDK.
* External contract nên dừng ở integration boundary.
* Complexity của ACL chỉ đáng giá khi change isolation thật sự cần thiết.

# 6. Circuit Breaker và Bulkhead: ngăn dependency failure lan rộng thành resource exhaustion toàn hệ thống

## 1. What is it?

Circuit Breaker tạm ngừng gọi dependency đang lỗi nhiều để tránh tiếp tục tạo request vô ích.

Bulkhead giới hạn lượng resource một dependency/workload có thể chiếm, để failure ở một khu vực không làm cạn capacity của toàn process.

```text
API
 ├─ Inventory client ─► bulkhead 20 ─► Inventory
 └─ Review client    ─► bulkhead 10 ─► Reviews
```

## 2. Why does it exist?

Remote dependency failure hiếm khi chỉ tạo một exception. Nếu timeout dài và traffic cao, request chờ sẽ chiếm:

* sockets,
* memory,
* task continuations,
* connection pool,
* thread capacity ở downstream sync code.

Retry có thể làm tình hình tệ hơn.

## 3. How does it work?

Circuit breaker thường có states:

```text
Closed → Open → Half-Open → Closed/Open
```

* Closed: request đi qua.
* Open: fail fast trong khoảng break duration.
* Half-Open: cho một số probe request thử dependency.

Bulkhead giới hạn concurrent executions/queue depth.

## 4. Practical implementation

Với resilience pipeline, tư duy nên là:

```text
Timeout budget
  ↓
Bulkhead / concurrency limit
  ↓
Circuit breaker
  ↓
Retry chỉ cho lỗi phù hợp
  ↓
Remote dependency
```

Không phải mọi dependency đều dùng cùng thresholds. Payment và recommendation có criticality khác nhau.

## 5. Real production scenario

Review provider của product page bắt đầu timeout 8 giây. Nếu API chờ toàn bộ dependency, request queue tăng và product page chính cũng chậm dù product data vẫn khỏe.

Bulkhead giới hạn số call review concurrent; circuit breaker mở và UI nhận fallback “reviews temporarily unavailable”. Core product flow vẫn chạy.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency đã phục hồi nhưng circuit vẫn mở liên tục.

**Evidence** → half-open probes vẫn thất bại do timeout budget quá thấp hoặc probe volume không hợp lý.

**Hypothesis** → resilience policy itself đang giữ dependency ở degraded loop.

**Diagnosis** → xem breaker state transitions, failure ratio và dependency latency.

**Fix** → điều chỉnh thresholds theo SLO thực tế, tách lỗi retryable/non-retryable, kiểm tra timeout layering.

**Verification** → chaos test outage rồi recovery.

## 7. Common mistakes

* Circuit breaker dùng chung global cho unrelated dependencies.
* Retry bên trong retry nhiều tầng tạo request amplification.
* Circuit breaker mở nhưng caller vẫn retry ngay.
* Không có fallback semantics rõ ràng.
* Bulkhead queue quá lớn nên chỉ biến reject thành latency.

## 8. Alternatives

* Fail-fast timeout đơn giản cho dependency ít quan trọng.
* Queue-based decoupling cho workload không cần synchronous response.
* Cached/stale fallback.
* Shed load ở gateway hoặc application boundary.

## 9. Trade-offs

### Advantages

* Failure isolation tốt hơn.
* Giảm resource exhaustion.
* Dependency lỗi có thể degrade một phần thay vì sập toàn hệ thống.

### Costs / Risks

* Policy tuning phức tạp.
* Fail-fast có thể giảm success rate ngắn hạn.
* Fallback có thể tạo stale/incomplete experience.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout khác retry và circuit breaker.

### Middle

Cấu hình breaker/bulkhead theo một dependency cụ thể.

### Senior

Phân tích retry amplification, queueing và recovery behavior.

### Technical Lead / Architect

Xác định failure boundaries và dependency criticality toàn hệ thống.

## 11. Key takeaway

* Circuit Breaker bảo vệ khỏi dependency failure kéo dài.
* Bulkhead bảo vệ resource capacity khỏi failure propagation.
* Resilience policy phải được load/chaos test như production code.

# 7. Azure App Service Deployment Slots: swap release an toàn nhưng phải hiểu warm-up, sticky settings và database compatibility

## 1. What is it?

Deployment Slot là một deployment environment riêng trong cùng App Service, ví dụ `staging` và `production`.

Code mới có thể deploy vào staging, warm-up và validate trước khi swap vào production.

```text
Build artifact
    ↓
Staging slot
    ↓ validate/warm-up
Swap
    ↓
Production traffic
```

## 2. Why does it exist?

Deploy trực tiếp vào production có thể gây cold start, config mistake hoặc startup failure ngay trên live traffic.

Slot cho phép kiểm tra artifact trong platform gần production hơn và giảm downtime khi release.

## 3. How does it work?

Swap trao đổi slot content/config theo semantics của App Service. Một số settings có thể được đánh dấu slot-sticky để không đổi theo swap.

Warm-up cho phép target slot khởi động application trước khi nhận production traffic.

Nhưng database thường không “swap” theo slot; cả hai slot có thể trỏ cùng production DB nếu config như vậy.

## 4. Practical implementation

Release flow:

```text
Commit
→ CI build/test
→ artifact
→ deploy staging slot
→ health check
→ smoke test
→ swap
→ monitor
→ swap back nếu cần
```

Connection strings, secrets hoặc feature flags cần xác định rõ cái nào sticky.

Database migration phải backward-compatible với cả old và new application trong giai đoạn swap.

## 5. Real production scenario

Version mới rename một column và migration chạy trước swap. Production slot cũ vẫn đang nhận traffic nhưng code cũ cần column cũ, dẫn tới 500 trước cả khi swap hoàn tất.

Giải pháp đúng là expand/contract migration:

1. thêm schema mới tương thích,
2. deploy code hỗ trợ cả hai,
3. migrate data,
4. bỏ schema cũ ở release sau.

## 6. Failure scenario & troubleshooting

**Symptom** → staging health check pass nhưng sau swap production lỗi authentication.

**Evidence** → auth secret/issuer setting không được đánh dấu sticky đúng cách.

**Hypothesis** → slot-specific configuration bị swap ngoài ý muốn.

**Diagnosis** → so sánh slot configuration trước/sau swap và inspect effective environment variables.

**Fix** → phân loại rõ deployment config vs environment-specific config.

**Verification** → rehearsal swap trong non-prod với production-like settings.

## 7. Common mistakes

* Nghĩ slot swap bao gồm database rollback.
* Chạy destructive migration trước khi code mới fully active.
* Không warm-up endpoint quan trọng.
* Health check chỉ trả 200 hardcoded.
* Không biết setting nào sticky.
* Deploy different artifact build giữa staging và production thay vì promote cùng artifact.

## 8. Alternatives

* Blue-Green qua hai App Services riêng.
* Canary routing.
* Container platform rolling deployment.
* Direct deployment cho low-risk internal service rất nhỏ.

## 9. Trade-offs

### Advantages

* Giảm downtime/cold-start exposure.
* Rollback app version nhanh bằng swap back.
* Tốt cho smoke test trước live traffic.

### Costs / Risks

* Database changes vẫn cần compatibility discipline.
* Config semantics phức tạp hơn.
* Slot có cost/operational overhead.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu staging slot khác local/staging environment độc lập.

### Middle

Deploy, validate và swap đúng flow.

### Senior

Thiết kế warm-up, health check và backward-compatible migration.

### Technical Lead / Architect

Chọn release strategy dựa trên rollback requirement, state compatibility và blast radius.

## 11. Key takeaway

* Deployment Slot giảm deployment risk nhưng không giải quyết database compatibility tự động.
* Cùng artifact nên được promote xuyên environments.
* Rollback strategy phải bao gồm schema/config, không chỉ application binary.

# 8. OpenTelemetry trace sampling: giảm telemetry cost mà vẫn giữ đủ evidence để điều tra tail latency và lỗi hiếm

## 1. What is it?

Trace sampling quyết định request/trace nào được ghi lại đầy đủ trong distributed tracing.

Nếu traffic rất lớn, lưu 100% traces có thể tốn storage, network và ingest cost đáng kể.

Sampling giúp giữ một phần traces đại diện hoặc ưu tiên traces quan trọng.

## 2. Why does it exist?

Metrics rẻ và aggregate tốt nhưng không cho biết toàn bộ path của một request cụ thể. Traces rất giàu context nhưng đắt hơn.

Hệ thống cần cân bằng observability fidelity và telemetry budget.

## 3. How does it work?

Hai mô hình chính:

* **Head sampling**: quyết định ngay khi trace bắt đầu.
* **Tail sampling**: quyết định sau khi đã thấy kết quả/latency của trace.

Head sampling đơn giản và rẻ hơn. Tail sampling có thể ưu tiên giữ:

* traces lỗi,
* traces p99,
* traces có dependency timeout,
* traces từ tenant quan trọng.

## 4. Practical implementation

Một policy thực tế có thể là:

```text
Keep 100% errors
Keep 100% traces > 2s
Keep 10% normal traces
Drop health-check noise
```

Trong OpenTelemetry Collector, tail sampling thường được thực hiện ở collector layer để có visibility toàn trace trước khi quyết định.

## 5. Real production scenario

Một API xử lý 20.000 request/giây. 100% trace retention làm telemetry bill tăng mạnh, nhưng giảm xuống 1% head sampling lại bỏ lỡ incident hiếm chỉ xảy ra ở p99.99.

Tail sampling cho phép giữ toàn bộ lỗi/slow traces nhưng sample mạnh happy path.

## 6. Failure scenario & troubleshooting

**Symptom** → metrics báo error spike nhưng gần như không có trace lỗi để điều tra.

**Evidence** → head sampling rate quá thấp và sampler không ưu tiên error outcome.

**Hypothesis** → sampling decision diễn ra trước khi biết trace sẽ fail.

**Diagnosis** → kiểm tra sampler config, propagation và collector pipeline.

**Fix** → tail-based policy hoặc increase targeted sampling cho risky endpoints.

**Verification** → inject test failures và xác nhận trace được retained.

## 7. Common mistakes

* Sample từng service độc lập làm trace bị đứt.
* Giảm sampling mà không kiểm tra impact tới incident response.
* Giữ health checks/noisy endpoints 100%.
* Dùng high-cardinality attributes vô kiểm soát dù đã sampling.
* Cho rằng traces thay thế metrics/logs.

## 8. Alternatives

* 100% tracing cho low-volume critical service.
* Head sampling với adaptive rate.
* Logs + correlation ID nếu distributed tracing chưa cần thiết.
* Exemplars nối metric spike tới trace cụ thể.

## 9. Trade-offs

### Advantages

* Giảm ingest/storage cost.
* Tail sampling giữ được evidence giá trị cao.
* Có thể tune theo risk và endpoint.

### Costs / Risks

* Tail sampling cần collector capacity và buffering.
* Sampling làm một số statistical analysis kém trực quan.
* Configuration sai có thể xóa evidence đúng lúc cần nhất.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace là một request path xuyên services.

### Middle

Biết sampling ảnh hưởng dữ liệu observability thế nào.

### Senior

Thiết kế policy giữ errors/slow traces và kiểm tra propagation.

### Technical Lead / Architect

Định nghĩa telemetry budget, retention và evidence requirements cho incident response.

## 11. Key takeaway

* Sampling là engineering decision về cost và diagnostic fidelity.
* Head sampling đơn giản; tail sampling giữ rare failures tốt hơn.
* Luôn test rằng traces cần cho incident thực sự được giữ lại.

# 9. Playwright test determinism: loại bỏ flaky E2E bằng cách kiểm soát state, network và synchronization thay vì tăng timeout

## 1. What is it?

Deterministic test cho cùng initial state và cùng behavior hệ thống sẽ cho cùng kết quả một cách ổn định.

Flaky E2E test thường không phải vì browser automation “không đáng tin”, mà vì test phụ thuộc vào timing, shared data hoặc environment state không kiểm soát.

## 2. Why does it exist?

E2E test đi qua nhiều layers:

```text
Browser
→ Frontend
→ API
→ Database
→ External dependencies
```

Mỗi layer thêm source of nondeterminism. Nếu test chỉ “sleep 2 giây rồi click”, timing variance sẽ biến thành flaky failure.

## 3. How does it work?

Playwright có auto-wait cho element actionability và assertions. Test nên chờ **condition có nghĩa**, không chờ thời gian cố định.

Sai:

```ts
await page.waitForTimeout(3000)
```

Tốt hơn:

```ts
await expect(page.getByRole('heading', { name: 'Order confirmed' }))
  .toBeVisible()
```

## 4. Practical implementation

Tạo data riêng cho test:

```ts
test('user can approve timesheet', async ({ page, request }) => {
  const employee = await createEmployeeFixture(request)
  const timesheet = await createTimesheetFixture(request, employee.id)

  await page.goto(`/timesheets/${timesheet.id}`)
  await page.getByRole('button', { name: 'Approve' }).click()

  await expect(page.getByText('Approved')).toBeVisible()
})
```

Fixture/API setup thường ổn định và nhanh hơn tạo mọi prerequisite qua UI.

## 5. Real production scenario

Suite chạy tốt local nhưng CI fail 5–10% ở test “submit order”. Team tăng timeout từ 5s lên 30s, suite chậm hơn nhưng vẫn flaky.

Root cause là test dùng shared customer account; một test khác đồng thời xóa cart. Fix là isolated test data, không phải timeout lớn hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail ngẫu nhiên ở CI nhưng rerun pass.

**Evidence** → screenshot/video cho thấy element chưa xuất hiện hoặc data đã bị thay đổi bởi test khác.

**Hypothesis** → shared state hoặc race condition.

**Diagnosis** → inspect trace viewer, network log, fixture lifecycle và parallelism.

**Fix** → unique test data, semantic waits, deterministic cleanup, mock only unstable third-party boundary khi phù hợp.

**Verification** → chạy test lặp nhiều lần và parallel trên CI-like environment.

## 7. Common mistakes

* Dùng `waitForTimeout` để chữa race.
* Test phụ thuộc thứ tự chạy.
* Shared username/cart/order giữa tests.
* Mock mọi backend khiến E2E không còn test integration thật.
* Assertion quá generic như tìm text xuất hiện ở nhiều nơi.
* Retry flaky test vô hạn rồi gọi đó là “stability”.

## 8. Alternatives

* Integration/API test cho business flow không cần browser.
* Component test cho UI behavior cục bộ.
* Contract test cho frontend-backend schema.
* Manual exploratory test cho scenario khó tự động hóa nhưng low-frequency.

## 9. Trade-offs

### Advantages

* E2E test bảo vệ critical user journeys xuyên nhiều layers.
* Playwright trace giúp debug failure tốt.

### Costs / Risks

* Chậm và đắt hơn unit/integration tests.
* Dễ flaky nếu environment/data không deterministic.
* Maintenance cao nếu selector và UI thay đổi liên tục.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết dùng semantic locator và assertion.

### Middle

Thiết kế fixture, cleanup và tránh fixed sleeps.

### Senior

Phân loại flaky root cause giữa test, environment và product race condition.

### Technical Lead / Architect

Quyết định journey nào xứng đáng E2E và phần nào nên được bảo vệ bằng test rẻ hơn.

## 11. Key takeaway

* Flaky test là reliability bug của test system.
* Chờ condition có nghĩa tốt hơn tăng timeout.
* Test pyramid nên dùng E2E cho critical flows, không cho mọi permutation.

# 10. Modernize .NET Framework theo Strangler pattern: chuyển dần sang modern .NET mà không biến modernization thành big-bang rewrite

## 1. What is it?

Strangler pattern hiện đại hóa hệ thống bằng cách đưa các capability mới hoặc được tách dần sang application/service mới, trong khi legacy system vẫn tiếp tục chạy cho phần chưa migration.

```text
Client
  ↓
Routing / Facade
  ├─ old capability ─► .NET Framework app
  └─ migrated capability ─► modern .NET app
```

Theo thời gian, phạm vi legacy giảm dần.

## 2. Why does it exist?

Big-bang rewrite có rủi ro lớn:

* mất nhiều tháng/năm trước khi tạo business value,
* behavior legacy không được document đầy đủ,
* migration data phức tạp,
* scope creep,
* rollback gần như all-or-nothing.

Incremental modernization giảm blast radius và cho phép học từ từng slice.

## 3. How does it work?

Chọn boundary có thể tách:

* endpoint group,
* background job,
* reporting,
* file processing,
* integration adapter,
* bounded context tương đối độc lập.

Sau đó định nghĩa routing và data ownership trong giai đoạn coexistence.

Quan trọng nhất không phải code migration, mà là tránh tạo **hai source of truth** không kiểm soát.

## 4. Practical implementation

Một migration path thực tế:

```text
1. Characterize legacy behavior bằng tests
2. Tách contract/API boundary
3. Route một capability sang ASP.NET Core
4. Dùng shared DB tạm thời nếu cần, nhưng hạn chế write ownership
5. Tách schema/data ownership ở bước sau
6. Monitor và rollback theo capability
```

Nếu shared database là bước chuyển tiếp, cần document table ownership và tránh hai codebase cùng thay đổi cùng invariant mà không coordination.

## 5. Real production scenario

Một .NET Framework monolith chạy IIS chứa authentication, timesheet, reporting và file export.

Team bắt đầu bằng file export vì dependency ít. API mới trên .NET 8 nhận request và xử lý export, còn monolith redirect/forward capability đó. Sau khi ổn định, reporting được tách tiếp.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng một business rule cho kết quả khác giữa endpoint cũ và mới.

**Evidence** → logic đã duplicate trong hai codebases và drift qua nhiều release.

**Hypothesis** → migration slice không có clear ownership/cutover rule.

**Diagnosis** → compare behavior tests, feature routing và write paths.

**Fix** → single owner cho capability, compatibility tests và decommission path rõ ràng.

**Verification** → shadow comparison hoặc dual-read validation trước cutover hoàn toàn.

## 7. Common mistakes

* Gọi mọi rewrite là Strangler dù không có incremental routing/cutover.
* Tách theo technical layers thay vì business capability.
* Shared database vĩnh viễn nhưng không định nghĩa ownership.
* Modernize framework đồng thời redesign toàn domain và đổi database một lần.
* Không có characterization tests cho legacy behavior.
* Không có tiêu chí decommission legacy code.

## 8. Alternatives

* In-place upgrade nếu codebase tương đối sạch và dependencies hỗ trợ.
* Big-bang rewrite khi system nhỏ, behavior đơn giản và downtime/risk chấp nhận được.
* Extract library/module trước khi extract service.
* Containerize legacy first để chuẩn hóa deployment nhưng chưa thay runtime.

## 9. Trade-offs

### Advantages

* Giảm migration risk theo từng slice.
* Có thể tạo business value sớm.
* Rollback theo capability dễ hơn.

### Costs / Risks

* Coexistence làm architecture tạm thời phức tạp.
* Duplicate infrastructure/monitoring trong giai đoạn chuyển đổi.
* Nếu không có decommission pressure, “temporary bridge” có thể sống nhiều năm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu modernization không nhất thiết là rewrite toàn hệ thống.

### Middle

Migration một capability với tests và backward-compatible contract.

### Senior

Quản lý data ownership, routing, observability và rollback trong giai đoạn coexistence.

### Technical Lead / Architect

Chọn migration sequence dựa trên business value, coupling, risk và khả năng decommission thực tế.

## 11. Key takeaway

* Incremental modernization thường an toàn hơn big-bang rewrite.
* Boundary và data ownership quan trọng hơn việc “đổi framework”.
* Mọi bridge tạm thời cần exit criteria để không trở thành kiến trúc vĩnh viễn.
