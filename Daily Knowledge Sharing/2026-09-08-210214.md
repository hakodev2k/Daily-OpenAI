# 1. `ArrayPool<T>` và `Span<T>` trong .NET: giảm allocation ở hot path nhưng phải quản lý lifetime và dữ liệu cũ

## 1. What is it?

`ArrayPool<T>` là cơ chế tái sử dụng array thay vì tạo array mới cho mỗi operation. `Span<T>` là view lightweight trên một vùng memory liên tục mà không cần copy dữ liệu.

Mental model:

```text
allocate byte[64 KB] mỗi request
        ↓
GC pressure tăng

ArrayPool<byte>.Shared.Rent(...)
        ↓
reuse buffer đã có
        ↓
Span<byte> chỉ nhìn vào slice cần dùng
```

`ArrayPool<T>` tối ưu ownership của buffer; `Span<T>` tối ưu cách thao tác trên buffer đó.

## 2. Why does it exist?

Một API parse file, serialize payload hoặc xử lý compression hàng nghìn lần mỗi giây có thể tạo rất nhiều temporary arrays. Allocation ngắn hạn không miễn phí: GC phải theo dõi, scan và thu hồi chúng.

Với buffer lớn, allocation còn có thể đẩy object vào Large Object Heap. Nếu workload là hot path có pattern buffer lặp lại, tái sử dụng memory giúp giảm allocation rate và GC pressure.

## 3. How does it work?

`Rent(n)` trả về một array có **ít nhất** `n` phần tử; length có thể lớn hơn. Caller sở hữu tạm buffer đó cho tới khi `Return()`.

`Span<T>` có thể tạo từ array:

```csharp
var span = buffer.AsSpan(0, bytesRead);
```

`Span<T>` là `ref struct`, nên không thể sống tự do trên heap hoặc đi qua mọi async boundary như object thông thường. Điều này cố ý giới hạn lifetime để tránh tham chiếu memory không còn hợp lệ.

## 4. Practical implementation

```csharp
public static async Task<int> CopyPrefixAsync(
    Stream input,
    Stream output,
    int maxBytes,
    CancellationToken cancellationToken)
{
    var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);

    try
    {
        var total = 0;

        while (total < maxBytes)
        {
            var remaining = Math.Min(buffer.Length, maxBytes - total);
            var read = await input.ReadAsync(
                buffer.AsMemory(0, remaining),
                cancellationToken);

            if (read == 0)
                break;

            await output.WriteAsync(
                buffer.AsMemory(0, read),
                cancellationToken);

            total += read;
        }

        return total;
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
    }
}
```

Nếu buffer chứa secret hoặc dữ liệu nhạy cảm, cân nhắc `clearArray: true` hoặc clear đúng vùng đã dùng trước khi return.

## 5. Real production scenario

Một image-processing API đọc 128 KB header + metadata từ hàng chục nghìn file mỗi phút. Version đầu tạo `byte[]` mới cho từng request. Allocation profiler cho thấy phần lớn Gen 0 traffic đến từ temporary buffers.

Sau khi dùng pool cho đúng hot path, allocation rate giảm đáng kể mà business logic không thay đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → thỉnh thoảng response chứa byte “rác” ở cuối payload.

**Evidence** → code dùng toàn bộ `buffer.Length` thay vì số byte thực tế đã đọc.

**Hypothesis** → rented buffer chứa dữ liệu từ user trước.

**Diagnosis** → kiểm tra mọi `ReadAsync` và slice truyền sang parser/writer.

**Fix** → luôn dùng `buffer.AsSpan(0, bytesRead)` hoặc `AsMemory(0, bytesRead)`.

**Verification** → fuzz test với buffer size khác nhau và payload ngắn/dài.

## 7. Common mistakes

* Quên `Return()` trong exception path.
* Giữ reference tới rented array sau khi đã return.
* Giả định array được zero-out khi rent.
* Dùng pool ở code không phải hot path, làm tăng complexity mà không có lợi ích đo được.
* Return buffer quá sớm trong khi async consumer vẫn đang dùng nó.

## 8. Alternatives

* `new byte[]`: đơn giản nhất, phù hợp phần lớn code.
* `MemoryPool<T>`: hữu ích khi cần ownership abstraction phức tạp hơn.
* `stackalloc` + `Span<T>`: tốt cho buffer nhỏ, lifetime rất ngắn và size có giới hạn hợp lý.

## 9. Trade-offs

### Advantages

* Giảm allocation và GC pressure.
* Có thể cải thiện throughput ở hot path.
* Tốt cho reusable temporary buffers.

### Costs / Risks

* Lifetime management phức tạp hơn.
* Có nguy cơ data leakage nếu xử lý dữ liệu nhạy cảm sai.
* Bug use-after-return rất khó debug.
* Không đáng dùng nếu profiler không chỉ ra bottleneck memory/allocation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu pool là tái sử dụng buffer, không phải memory “miễn phí”.

### Middle

Biết `Rent`, slice đúng vùng dữ liệu và `Return` trong `finally`.

### Senior

Đánh giá allocation profile, LOH, data sensitivity và lifetime across async calls.

### Technical Lead / Architect

Quyết định hot path nào đủ quan trọng để chấp nhận complexity; đặt coding convention để tránh use-after-return và leakage.

## 11. Key takeaway

* `ArrayPool<T>` chỉ đáng dùng khi allocation thực sự là bottleneck.
* Rented array có thể chứa dữ liệu cũ và có length lớn hơn yêu cầu.
* Ownership/lifetime đúng quan trọng hơn vài microseconds tiết kiệm được.

# 2. ASP.NET Core middleware ordering: authentication, authorization và exception handling phụ thuộc thứ tự pipeline như thế nào

## 1. What is it?

ASP.NET Core middleware pipeline là chuỗi component xử lý request theo thứ tự đăng ký và response theo chiều ngược lại.

Mental model:

```text
Request
  ↓
Exception Handler
  ↓
Routing
  ↓
Authentication
  ↓
Authorization
  ↓
Endpoint
  ↑
Response quay ngược pipeline
```

Thứ tự không phải style preference. Nó quyết định middleware nào có đủ context để làm việc và middleware nào có thể bắt lỗi từ component phía sau.

## 2. Why does it exist?

Mỗi concern cần đứng ở đúng boundary:

* exception handler phải bọc code có thể throw;
* routing phải chọn endpoint trước khi authorization đọc metadata của endpoint;
* authentication phải xác lập `User` trước authorization;
* static files có thể short-circuit request trước MVC/API.

Sai thứ tự có thể khiến app compile, start bình thường nhưng security hoặc error behavior sai trong runtime.

## 3. How does it work?

Mỗi middleware thường nhận `RequestDelegate next`.

```csharp
await BeforeAsync();
await next(context);
await AfterAsync();
```

Do đó request đi “xuôi”, response đi “ngược”. Middleware có thể short-circuit bằng cách không gọi `next`.

## 4. Practical implementation

```csharp
var app = builder.Build();

app.UseExceptionHandler();
app.UseHttpsRedirection();

app.UseRouting();

app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();

app.Run();
```

Một custom correlation middleware nên chạy đủ sớm để correlation ID xuất hiện trong logs của toàn pipeline:

```csharp
app.Use(async (context, next) =>
{
    var correlationId = context.Request.Headers["X-Correlation-Id"]
        .FirstOrDefault() ?? Guid.NewGuid().ToString("N");

    context.Response.Headers["X-Correlation-Id"] = correlationId;

    using (logger.BeginScope(new Dictionary<string, object>
    {
        ["CorrelationId"] = correlationId
    }))
    {
        await next(context);
    }
});
```

## 5. Real production scenario

Một API dùng policy-based authorization dựa trên endpoint metadata. Sau refactor, team đặt `UseAuthorization()` trước routing. Một số endpoint bắt đầu có behavior không nhất quán vì authorization không thấy endpoint metadata đúng thời điểm.

Root cause không nằm ở policy code mà ở pipeline topology.

## 6. Failure scenario & troubleshooting

**Symptom** → exception từ controller không được chuyển thành `ProblemDetails`; client nhận connection reset hoặc raw error.

**Evidence** → exception handler middleware được đăng ký sau endpoint execution path.

**Hypothesis** → middleware không bao bọc code throw exception.

**Diagnosis** → log pipeline order hoặc tạo minimal reproduction với middleware trace.

**Fix** → đưa global error middleware lên trước các component cần được bao bọc.

**Verification** → integration test cho 401, 403, 404, 500 và exception từ dependency.

## 7. Common mistakes

* Nghĩ thứ tự `UseAuthentication`/`UseAuthorization` không quan trọng.
* Custom middleware short-circuit nhưng quên set status code/body phù hợp.
* Ghi response rồi mới gọi `next`, dẫn tới response đã started.
* Dùng middleware cho logic chỉ thuộc một endpoint/domain use case.
* Catch mọi exception trong controller khiến global handler mất context.

## 8. Alternatives

* Endpoint filters: phù hợp concern cấp endpoint/Minimal API.
* MVC filters: phù hợp MVC-specific behavior.
* Domain/application decorator: phù hợp cross-cutting concern không thuộc HTTP layer.

## 9. Trade-offs

### Advantages

* Cross-cutting concern được centralize.
* Pipeline rõ ràng, composable.
* Có thể short-circuit sớm.

### Costs / Risks

* Sai ordering gây bug khó thấy.
* Global behavior dễ trở thành hidden coupling.
* Middleware quá nhiều làm debugging request flow khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request đi qua pipeline theo thứ tự đăng ký.

### Middle

Biết đặt exception, routing, authn, authz đúng vị trí và viết integration tests.

### Senior

Debug short-circuit, response-started issues và security implications của ordering.

### Technical Lead / Architect

Quyết định concern nào thuộc middleware, filter hay application layer; giữ pipeline tối giản và observable.

## 11. Key takeaway

* Middleware order là runtime behavior, không phải formatting.
* Authentication phải thiết lập identity trước authorization.
* Exception handler chỉ bắt được exception từ code nằm “phía trong” nó.

# 3. EF Core compiled queries: giảm query-compilation overhead ở hot path nhưng không sửa được SQL kém

## 1. What is it?

EF Core phải chuyển LINQ expression thành SQL command shape. EF đã cache query compilation theo expression shape, nhưng compiled query cho phép developer tạo delegate được compile trước cho một hot query cụ thể.

Mental model:

```text
LINQ expression
   ↓ query translation/compilation
SQL command shape
   ↓ execute repeatedly
```

Compiled query tối ưu phần **query preparation**, không làm database execution nhanh hơn nếu SQL hoặc index access path vốn đã tệ.

## 2. Why does it exist?

Trong phần lớn API, network + database I/O lớn hơn query-compilation cost. Nhưng ở endpoint cực nóng, query rất nhỏ, DB ở gần và được gọi hàng chục nghìn lần mỗi giây, overhead phía client ORM có thể trở nên đo được.

## 3. How does it work?

EF compile expression một lần thành delegate nhận `DbContext` và parameters.

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<ProductDto>>
    GetProductById = EF.CompileAsyncQuery(
        (AppDbContext db, Guid id) =>
            db.Products
                .AsNoTracking()
                .Where(x => x.Id == id)
                .Select(x => new ProductDto(x.Id, x.Name, x.Price)));
```

Caller reuse delegate thay vì đưa expression mới vào pipeline mỗi lần.

## 4. Practical implementation

```csharp
public async Task<ProductDto?> GetAsync(
    Guid id,
    CancellationToken cancellationToken)
{
    await foreach (var item in GetProductById(_db, id)
        .WithCancellation(cancellationToken))
    {
        return item;
    }

    return null;
}
```

Trước khi dùng, benchmark query path thật bằng BenchmarkDotNet hoặc production profiling.

## 5. Real production scenario

Một read-mostly pricing endpoint query theo primary key, DB response chỉ vài trăm microseconds trong cùng region, cache disabled vì yêu cầu freshness. Profiling cho thấy EF query pipeline chiếm tỷ lệ CPU đáng kể.

Compiled query có thể hợp lý ở đây. Với report query mất 300 ms ở SQL Server, compiled query gần như không giải quyết vấn đề.

## 6. Failure scenario & troubleshooting

**Symptom** → sau khi thêm compiled queries, p95 không thay đổi.

**Evidence** → traces cho thấy SQL vẫn chiếm 95% duration.

**Hypothesis** → bottleneck nằm ở DB I/O/execution plan.

**Diagnosis** → so client-side CPU với SQL duration và logical reads.

**Fix** → quay lại execution plan/access pattern; bỏ optimization không mang giá trị nếu nó làm code khó đọc.

**Verification** → benchmark before/after trên workload đại diện.

## 7. Common mistakes

* Compile mọi query “cho nhanh”.
* Nghĩ compiled query tương đương stored procedure.
* Dùng expression shape quá động khiến abstraction không còn phù hợp.
* Tối ưu query compilation trước khi sửa N+1 hoặc thiếu projection.

## 8. Alternatives

* EF query cache mặc định: đủ cho đa số workload.
* Raw SQL/Dapper: kiểm soát mapping/query path sâu hơn.
* Cache dữ liệu: chỉ khi freshness semantics cho phép.

## 9. Trade-offs

### Advantages

* Giảm repeated client-side query compilation overhead.
* Có giá trị ở extremely hot/simple queries.

### Costs / Risks

* Tăng code ceremony.
* Lợi ích thường nhỏ so với DB latency.
* Dynamic queries khó áp dụng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ phải được translate trước khi DB execute.

### Middle

Biết đọc generated SQL và benchmark query.

### Senior

Phân biệt client ORM overhead với database execution bottleneck.

### Technical Lead / Architect

Chỉ chuẩn hóa compiled query nếu workload/profiling chứng minh ROI; không biến nó thành project-wide rule.

## 11. Key takeaway

* Compiled query tối ưu EF client pipeline, không tối ưu SQL Server.
* Chỉ dùng cho measured hot path.
* Query shape và access pattern vẫn quan trọng hơn micro-optimization.

# 4. SQL Server connection pooling: vì sao “mở connection” thường không mở TCP connection mới và pool exhaustion xảy ra thế nào

## 1. What is it?

ADO.NET connection pooling giữ các physical database connections để tái sử dụng. `SqlConnection.OpenAsync()` thường lấy connection sẵn từ pool thay vì tạo TCP/TLS/login session mới.

Mental model:

```text
application code
Open SqlConnection
     ↓
connection pool
   ├─ idle physical connection → reuse
   └─ none available → create or wait
```

`Dispose`/`Close` thường trả physical connection về pool, không đóng socket thật ngay.

## 2. Why does it exist?

Thiết lập DB connection mới tốn network handshake, TLS, authentication và server session setup. Nếu mỗi HTTP request tạo physical connection thật, throughput sẽ rất tệ.

Pooling cho phép pattern đúng trong .NET là **open late, close early** ở code level, trong khi physical connection vẫn được reuse.

## 3. How does it work?

Pool thường được phân tách theo connection string/identity. Mỗi checkout lấy một physical connection; khi code dispose, connection trở lại pool nếu vẫn usable.

Nếu mọi connection đều đang bận và pool đạt `Max Pool Size`, caller phải chờ tới timeout.

## 4. Practical implementation

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(cancellationToken);

await using var command = new SqlCommand(
    "SELECT Id, Number FROM Orders WHERE Id = @id",
    connection);

command.Parameters.AddWithValue("@id", id);

await using var reader = await command.ExecuteReaderAsync(cancellationToken);
```

Điều đúng là dispose nhanh sau operation, không giữ connection trong singleton/service dài hạn.

Với EF Core, `DbContext` quản lý connection lifecycle cho từng operation thông thường.

## 5. Real production scenario

API có `Max Pool Size=100`. Một external API call được thực hiện **bên trong** transaction sau khi DB connection đã mở. External dependency chậm 5 giây. Chỉ 100 concurrent requests đã có thể chiếm hết pool, khiến request mới timeout dù SQL Server CPU thấp.

Vấn đề không phải “DB thiếu capacity”, mà connection bị giữ quá lâu ở application layer.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi timeout “prior to obtaining a connection from the pool”, DB CPU chỉ 20%.

**Evidence** → active DB sessions gần max pool; traces cho thấy transaction duration dài.

**Hypothesis** → connections bị giữ trong lúc chờ network hoặc code path không dispose.

**Diagnosis** → xem dependency traces, transaction scope, active connection metrics và thread dumps nếu cần.

**Fix** → rút ngắn DB critical section, không gọi remote dependency khi đang giữ transaction nếu không bắt buộc, dispose đúng lifecycle.

**Verification** → load test; pool wait time và timeout phải giảm.

## 7. Common mistakes

* Giữ `SqlConnection` singleton.
* Tăng `Max Pool Size` trước khi tìm nguyên nhân connection giữ lâu.
* Mở transaction rồi gọi external API.
* Tạo nhiều connection strings khác nhau vô tình chia nhỏ pools.
* Nhầm `DbContext pooling` với database connection pooling.

## 8. Alternatives

Không có “thay thế” trực tiếp cho pooling trong app server truyền thống, nhưng có thể giảm pressure bằng cache, read replica, async messaging hoặc tối ưu transaction scope.

## 9. Trade-offs

### Advantages

* Giảm connection setup overhead.
* Tăng throughput.
* Cho phép connection lifecycle ngắn ở application code.

### Costs / Risks

* Pool là finite shared resource.
* Leak/long hold time gây failure toàn service.
* Tăng pool vô hạn chỉ chuyển pressure sang database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Open()` không nhất thiết tạo socket mới.

### Middle

Biết scope connection/DbContext ngắn và dispose đúng.

### Senior

Debug pool exhaustion bằng telemetry, transaction lifetime và dependency duration.

### Technical Lead / Architect

Thiết kế concurrency budget giữa app instances, pool size và database capacity; tránh scale-out app vượt khả năng DB.

## 11. Key takeaway

* Connection pooling biến DB connection thành finite reusable resource.
* Pool exhaustion thường là lifecycle/concurrency problem, không chỉ DB performance problem.
* Đừng tăng pool size trước khi đo vì sao connections bị giữ lâu.

# 5. Redis cache invalidation ownership: TTL không thay thế consistency contract giữa write path và cache

## 1. What is it?

Cache invalidation ownership trả lời câu hỏi: **component nào chịu trách nhiệm làm cache không còn sai sau khi source of truth thay đổi?**

TTL chỉ giới hạn thời gian dữ liệu có thể stale; nó không đảm bảo client nhìn thấy thay đổi ngay sau write.

## 2. Why does it exist?

Cache-aside rất dễ viết:

```text
GET cache
miss → DB → SET cache
```

Nhưng write path mới là phần khó:

```text
UPDATE DB
then what?
DELETE cache?
UPDATE cache?
Publish invalidation event?
Wait for TTL?
```

Nếu ownership không rõ, cache stale trở thành bug “ngẫu nhiên”.

## 3. How does it work?

Một strategy phổ biến:

```text
Command API
  ↓ transaction
Primary DB updated
  ↓ after commit
Delete cache key
```

Delete thường an toàn hơn “update cache” vì next read sẽ reconstruct từ source of truth. Trong distributed system, nếu invalidation event được publish async, consistency trở thành eventual và phải được chấp nhận rõ ràng.

## 4. Practical implementation

```csharp
public async Task UpdateProductAsync(
    Product product,
    CancellationToken cancellationToken)
{
    _db.Products.Update(product);
    await _db.SaveChangesAsync(cancellationToken);

    await _cache.RemoveAsync(
        $"product:{product.Id}",
        cancellationToken);
}
```

Nhưng đoạn trên còn failure window: DB commit thành công, Redis delete thất bại. Với requirement mạnh hơn, có thể dùng Outbox để publish invalidation event sau commit đáng tin cậy.

## 5. Real production scenario

Pricing admin cập nhật giá. DB đã là 120 USD nhưng product API vẫn trả 100 USD vì key có TTL 30 phút. Team nói “cache eventually đúng”, nhưng business yêu cầu giá mới xuất hiện trong 10 giây.

TTL 30 phút vi phạm consistency requirement ngay cả khi technical implementation “hoạt động”.

## 6. Failure scenario & troubleshooting

**Symptom** → user thấy giá cũ sau update.

**Evidence** → DB có version mới, Redis key có timestamp cũ và TTL còn 20 phút.

**Hypothesis** → invalidation không chạy hoặc chạy thất bại.

**Diagnosis** → trace command path, cache operation, Outbox/event lag nếu có.

**Fix** → xác định owner; delete/update cache sau commit; thêm retry/event delivery phù hợp.

**Verification** → test write rồi immediate read, Redis outage và delayed event.

## 7. Common mistakes

* Dùng TTL như giải pháp duy nhất dù business cần freshness nhanh.
* Hai service cùng sở hữu một cache key nhưng không có contract.
* Delete cache trước DB commit rồi transaction rollback.
* Không version cache key khi schema serialization thay đổi.
* Redis outage làm write API fail dù cache chỉ nên là optimization.

## 8. Alternatives

* Không cache: tốt nhất nếu DB đủ nhanh và scale phù hợp.
* `IMemoryCache`: đơn giản nhưng mỗi instance có state riêng.
* Write-through cache: consistency path rõ hơn nhưng coupling mạnh hơn.
* Event-driven invalidation: scale tốt hơn nhưng eventual consistency và operational complexity tăng.

## 9. Trade-offs

### Advantages

* Cache-aside + invalidation rõ ownership khá đơn giản.
* Giảm stale window.

### Costs / Risks

* Dual-write failure giữa DB và cache.
* Event-based invalidation thêm queue/consumer.
* Strict freshness giảm lợi ích cache.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache có thể stale và TTL chỉ là expiration policy.

### Middle

Biết thiết kế cache key, invalidation và fallback khi Redis down.

### Senior

Phân tích DB/cache dual-write failure và freshness SLA.

### Technical Lead / Architect

Quyết định cache có nên tồn tại, ai sở hữu invalidation, stale data tối đa bao lâu và Redis có được phép trở thành critical dependency hay không.

## 11. Key takeaway

* TTL không phải consistency contract.
* Cache invalidation phải có owner rõ ràng.
* Nếu DB đủ nhanh, “không cache” đôi khi là lựa chọn Senior tốt hơn.

# 6. Anti-Corruption Layer trong architecture: cô lập external model để integration không làm nhiễm domain model

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary chuyển đổi giữa model của hệ thống bên ngoài và model của domain nội bộ.

Mental model:

```text
External CRM model
       ↓
Anti-Corruption Layer
       ↓
Internal Customer domain model
```

Tên “anti-corruption” không nói external system xấu; nó nói rằng semantic model bên ngoài không nên tự động trở thành language/model của domain bên trong.

## 2. Why does it exist?

External API thường có naming, status codes, lifecycle và data shape khác domain nội bộ. Nếu business code dùng trực tiếp DTO của vendor, vendor contract lan khắp system.

Sau này đổi provider hoặc vendor đổi schema, blast radius rất lớn.

## 3. How does it work?

ACL thường gồm:

* external client;
* DTO theo vendor contract;
* mapper/translator;
* internal abstraction hoặc application service contract;
* error translation.

Dependency direction:

```text
Domain/Application
      ↑
Internal interface
      ↑
Infrastructure adapter / ACL
      ↓
External API
```

Domain không phụ thuộc vendor SDK.

## 4. Practical implementation

```csharp
public interface ICustomerRiskService
{
    Task<RiskAssessment> AssessAsync(
        CustomerId customerId,
        CancellationToken cancellationToken);
}

public sealed class VendorRiskAdapter : ICustomerRiskService
{
    private readonly VendorRiskClient _client;

    public async Task<RiskAssessment> AssessAsync(
        CustomerId customerId,
        CancellationToken cancellationToken)
    {
        var response = await _client.GetRiskAsync(
            customerId.Value,
            cancellationToken);

        return response.Code switch
        {
            "L" => RiskAssessment.Low,
            "M" => RiskAssessment.Medium,
            "H" => RiskAssessment.High,
            _ => throw new InvalidOperationException(
                $"Unsupported vendor risk code: {response.Code}")
        };
    }
}
```

Internal domain không biết `"L"`, `"M"`, `"H"`.

## 5. Real production scenario

Một automotive marketplace tích hợp provider A cho vehicle history. Provider dùng field `damage_flag = 0/1/9`, trong đó `9 = unknown`. Nếu DTO provider đi thẳng vào domain, business rules bắt đầu chứa magic values.

ACL chuyển nó thành `DamageStatus.None`, `Reported`, `Unknown` ngay tại boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → provider thêm code `"P"` và production bắt đầu trả 500.

**Evidence** → adapter throw vì unknown code.

**Hypothesis** → external contract evolved.

**Diagnosis** → inspect raw provider response, schema/version docs và logs đã redacted.

**Fix** → quyết định semantic mapping có chủ đích; update contract tests.

**Verification** → replay captured fixtures và integration tests.

## 7. Common mistakes

* Tạo ACL chỉ là pass-through wrapper, không thực sự translate semantics.
* Domain reference vendor SDK types.
* Che mọi external error thành generic `Exception` làm mất troubleshootability.
* Overabstract một internal API ổn định mà không có semantic mismatch.

## 8. Alternatives

* Direct client usage: hợp lý với integration nhỏ, low-risk, không đi sâu vào domain.
* Generic repository/service wrapper: thường không giải quyết semantic translation.
* Event ingestion normalization: phù hợp khi external data được ingest async.

## 9. Trade-offs

### Advantages

* Cô lập vendor coupling.
* Domain language sạch hơn.
* Migration provider dễ hơn.

### Costs / Risks

* Thêm mapping code và tests.
* Có thể overengineer nếu integration rất đơn giản.
* Translation có thể làm mất vendor-specific information nếu model quá nghèo.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không mặc định là domain model.

### Middle

Biết map contract và translate errors.

### Senior

Thiết kế boundary theo semantics, failure modes và migration risk.

### Technical Lead / Architect

Quyết định integration nào cần ACL và boundary nên nằm ở bounded context nào; tránh tạo layer chỉ để “đẹp architecture”.

## 11. Key takeaway

* ACL bảo vệ domain language khỏi external semantics.
* Giá trị chính là change isolation, không phải thêm một folder Adapter.
* Chỉ dùng khi coupling thực sự đáng cô lập.

# 7. Azure Service Bus sessions: ordering có điều kiện, competing consumers và chi phí của ordered processing

## 1. What is it?

Azure Service Bus sessions nhóm messages có cùng `SessionId` thành một ordered stream được một consumer giữ session lock tại một thời điểm.

Mental model:

```text
Order-123 events → SessionId = Order-123
PaymentCreated
ItemReserved
OrderConfirmed
        ↓
one-at-a-time session ownership
```

Sessions không tạo global ordering cho cả queue. Ordering chỉ có ý nghĩa **trong cùng session**.

## 2. Why does it exist?

Competing consumers tăng throughput nhưng có thể xử lý messages cùng entity theo thứ tự khác nhau. Một số workflow cần sequence theo customer/order/device, nhưng không muốn serialize toàn bộ queue.

Session cho phép partition ordering theo business key.

## 3. How does it work?

Producer đặt `SessionId`. Consumer accept session, nhận lock rồi xử lý messages thuộc session đó. Session A và B có thể được xử lý song song; messages trong A được xử lý tuần tự theo delivery order.

Service Bus vẫn có at-least-once semantics. Duplicate delivery vẫn có thể xảy ra, nên ordered không có nghĩa exactly-once.

## 4. Practical implementation

Producer:

```csharp
var message = new ServiceBusMessage(BinaryData.FromObjectAsJson(evt))
{
    SessionId = evt.OrderId.ToString(),
    MessageId = evt.EventId.ToString()
};

await sender.SendMessageAsync(message, cancellationToken);
```

Processor:

```csharp
var options = new ServiceBusSessionProcessorOptions
{
    MaxConcurrentSessions = 16,
    MaxConcurrentCallsPerSession = 1,
    AutoCompleteMessages = false
};

var processor = client.CreateSessionProcessor(queueName, options);
```

Consumer vẫn phải idempotent theo `MessageId` hoặc business operation key.

## 5. Real production scenario

Order workflow có `OrderCreated`, `PaymentAuthorized`, `OrderCancelled`. Không muốn `OrderCancelled` được apply trước khi state machine biết order tồn tại.

Dùng `SessionId = OrderId` cho phép hàng nghìn orders xử lý song song nhưng sequence của từng order được serialize.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog tăng dù tổng message count không quá lớn.

**Evidence** → một session có hàng trăm nghìn messages, các session khác rất nhỏ.

**Hypothesis** → hot session giới hạn throughput vì chỉ một consumer xử lý stream đó.

**Diagnosis** → metric theo session key/business partition và processing duration.

**Fix** → xem lại partition key; giảm work trong critical session; tách workload không cần ordering khỏi session stream.

**Verification** → backlog drain rate và session processing latency cải thiện.

## 7. Common mistakes

* Nghĩ sessions bảo đảm exactly-once.
* Dùng một `SessionId` cho toàn hệ thống, vô tình serialize mọi message.
* Không thiết kế idempotency.
* Handler chạy lâu hơn lock/renew behavior và bị redelivery.
* Dùng ordering khi business thực ra có thể xử lý commutative/idempotent events.

## 8. Alternatives

* Queue không session: throughput đơn giản hơn nếu ordering không cần.
* Partition-specific worker: tự quản lý routing/ordering nhưng operational burden lớn hơn.
* State machine chịu out-of-order events: phức tạp domain hơn nhưng có thể scale tốt hơn.

## 9. Trade-offs

### Advantages

* Ordered processing theo business key.
* Parallelism giữa sessions.
* Hữu ích cho stateful workflows.

### Costs / Risks

* Hot session giới hạn throughput.
* Lock/session lifecycle phức tạp.
* Idempotency vẫn bắt buộc.
* Ordering tạo coupling theo sequence.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ordering chỉ trong cùng `SessionId`.

### Middle

Biết producer/processor configuration và message settlement.

### Senior

Đánh giá hot session, lock duration, duplicate delivery và idempotency.

### Technical Lead / Architect

Quyết định entity nào thật sự cần serialized processing; chọn session key theo scalability boundary.

## 11. Key takeaway

* Sessions cho per-key ordering, không phải global ordering.
* Ordered delivery không đồng nghĩa exactly-once processing.
* Session key sai có thể biến distributed queue thành single-thread bottleneck.

# 8. Application Insights + OpenTelemetry sampling: giảm telemetry cost mà không làm mất traces quan trọng

## 1. What is it?

Sampling quyết định chỉ thu hoặc export một phần telemetry thay vì 100% mọi request/span/log.

Mental model:

```text
1,000,000 requests
     ↓ sampling policy
100,000 representative traces
     ↓
observability backend
```

Mục tiêu là kiểm soát storage/ingestion cost và overhead mà vẫn giữ dữ liệu đủ để điều tra production.

## 2. Why does it exist?

Ở traffic lớn, export mọi span có thể tốn chi phí đáng kể. Một request có thể sinh hàng chục spans và logs. Nhưng sampling ngây thơ cũng nguy hiểm: nếu random sample 1%, error hiếm có thể bị bỏ hết.

## 3. How does it work?

Hai mô hình phổ biến:

* head sampling: quyết định ở đầu trace; rẻ nhưng chưa biết request cuối cùng có lỗi hay chậm;
* tail sampling: quyết định sau khi thấy toàn trace; có thể giữ errors/slow traces nhưng cần collector giữ state tạm thời.

OpenTelemetry Collector có thể áp dụng tail-sampling policy trước khi gửi Application Insights/backend khác.

## 4. Practical implementation

Head sampling đơn giản:

```csharp
services.AddOpenTelemetry()
    .WithTracing(tracing =>
    {
        tracing
            .SetSampler(new ParentBasedSampler(
                new TraceIdRatioBasedSampler(0.10)))
            .AddAspNetCoreInstrumentation()
            .AddHttpClientInstrumentation();
    });
```

Production cần bảo đảm child spans tôn trọng parent sampling decision để trace không bị rách.

## 5. Real production scenario

SaaS API xử lý 50 triệu requests/ngày. 100% tracing làm ingestion cost tăng mạnh. Team cần giữ 100% errors và requests >2 giây, nhưng chỉ 5–10% normal fast traffic.

Tail sampling tại collector phù hợp hơn random head sampling thuần túy.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard metrics báo error spike nhưng engineer không tìm thấy trace lỗi tương ứng.

**Evidence** → sampling config random-drop cả failed requests.

**Hypothesis** → policy tối ưu cost nhưng làm mất diagnostic evidence.

**Diagnosis** → kiểm tra sampler, collector policy và correlation giữa metrics/traces.

**Fix** → luôn giữ error/slow traces; sample normal success traffic nhiều hơn.

**Verification** → fault injection và xác nhận 100% test failures xuất hiện end-to-end.

## 7. Common mistakes

* Sample logs, metrics và traces độc lập làm correlation mất.
* High-cardinality tags tăng cost dù đã sample.
* Head sample quá thấp cho low-volume critical endpoints.
* Không biết Application Insights SDK và OTel collector đang cùng sampling, dẫn tới double sampling.

## 8. Alternatives

* 100% telemetry: đơn giản, tốt với traffic nhỏ.
* Head sampling: rẻ, dễ triển khai.
* Tail sampling: richer decision nhưng collector complex/cost hơn.

## 9. Trade-offs

### Advantages

* Kiểm soát ingestion cost.
* Giảm telemetry overhead.
* Tail sampling giữ được diagnostic traces quan trọng.

### Costs / Risks

* Có thể mất evidence nếu policy sai.
* Tail sampling cần state/memory ở collector.
* Sampling làm thống kê raw trace count không còn trực tiếp đại diện traffic nếu không hiểu weighting.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu telemetry không nhất thiết thu 100%.

### Middle

Biết head sampling và correlation.

### Senior

Thiết kế policy giữ errors/slow traces và kiểm soát cardinality.

### Technical Lead / Architect

Đặt observability budget, retention và sampling strategy theo SLO/incident requirements, không chỉ theo chi phí.

## 11. Key takeaway

* Sampling là trade-off cost vs diagnostic fidelity.
* Error và slow trace thường cần policy ưu tiên giữ lại.
* Double sampling và high cardinality có thể phá cả cost lẫn troubleshooting.

public sealed class SqlServerFixture : IAsyncLifetime

# 10. RAG chunking và retrieval boundary: chunk size, overlap và metadata ảnh hưởng trực tiếp chất lượng context như thế nào

## 1. What is it?

Trong Retrieval-Augmented Generation (RAG), chunking chia tài liệu lớn thành các đơn vị nhỏ để tạo embeddings, index và retrieve vào LLM context.

Mental model:

```text
Document
  ↓ split
Chunks
  ↓ embed/index
Vector/Search store
  ↓ retrieve top-k
Relevant context
  ↓
LLM response
```

Chunk không chỉ là technical preprocessing detail. Nó là **retrieval boundary** quyết định model nhìn thấy context nào.

## 2. Why does it exist?

Embedding cả tài liệu 100 trang thành một vector làm semantic representation quá coarse. Chia mỗi câu riêng lại mất context và tăng số records/cost.

Chunking cân bằng:

* semantic coherence;
* retrieval precision;
* context completeness;
* token cost;
* indexing/storage cost.

## 3. How does it work?

Một pipeline thường:

1. parse document structure;
2. split theo headings/paragraphs/token budget;
3. thêm overlap nếu boundary có thể cắt concept;
4. gắn metadata: document ID, section, permissions, version;
5. create embeddings;
6. retrieve candidate chunks;
7. optional rerank;
8. build prompt context.

Không có chunk size tối ưu universal. Source code, legal docs và FAQ có structure khác nhau.

## 4. Practical implementation

Một splitter đơn giản nên ưu tiên semantic boundary thay vì cắt mỗi N ký tự:

```csharp
public sealed record Chunk(
    string DocumentId,
    string Section,
    string Text,
    int Sequence);

public static IEnumerable<Chunk> ChunkSections(Document doc, int maxChars)
{
    var sequence = 0;

    foreach (var section in doc.Sections)
    {
        foreach (var text in SplitPreservingParagraphs(section.Text, maxChars))
        {
            yield return new Chunk(
                doc.Id,
                section.Title,
                text,
                sequence++);
        }
    }
}
```

Production implementation nên đo theo token count/model tokenizer và giữ metadata cho authorization/filtering.

## 5. Real production scenario

Internal engineering assistant index architecture documents. Chunk 200 tokens cho kết quả rất precise nhưng thường thiếu phần “Constraints” nằm ngay dưới “Decision”. Chunk 1500 tokens đủ context nhưng retrieval đưa nhiều text không liên quan và tốn token.

Team thử structure-aware chunks theo ADR sections + parent heading metadata, rồi đánh giá bằng grounded QA dataset.

## 6. Failure scenario & troubleshooting

**Symptom** → model hallucinate dù câu trả lời rõ ràng có trong document.

**Evidence** → retrieved chunks không chứa đoạn answer; embedding search trả chunk cùng keyword nhưng sai section.

**Hypothesis** → chunk boundary/retrieval strategy làm mất semantic context.

**Diagnosis** → inspect top-k chunks trước khi nhìn model output; đo recall@k trên evaluation set.

**Fix** → điều chỉnh chunking, metadata filters, hybrid search hoặc reranking.

**Verification** → chạy evaluation suite và so grounded answer rate/token cost trước-sau.

## 7. Common mistakes

* Tối ưu prompt khi retrieval đã sai.
* Chunk fixed-size không quan tâm headings/code blocks/tables.
* Overlap quá lớn tạo duplicate results.
* Không lưu document version, khiến old chunks còn trong index.
* Không apply authorization filter trước khi đưa context cho model.
* Để LLM quyết định access control dựa trên prompt.

## 8. Alternatives

* Full-document context: tốt nếu corpus nhỏ và context window đủ.
* Keyword/BM25 search: mạnh với exact terms.
* Hybrid search: kết hợp lexical + vector.
* Hierarchical retrieval: retrieve section/document trước rồi chunk con.

## 9. Trade-offs

### Advantages

* Chunk nhỏ tăng retrieval precision.
* Structure-aware chunking giữ semantic boundary tốt hơn.
* Metadata giúp filtering, ACL và provenance.

### Costs / Risks

* Chunk quá nhỏ mất context.
* Chunk quá lớn tăng token cost và noise.
* Overlap tăng index/storage cost.
* Pipeline phải reindex khi chunking strategy đổi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG chỉ tốt khi retrieve đúng context.

### Middle

Biết chunk theo structure, metadata và token budget.

### Senior

Đo retrieval recall, reranking, authorization và versioning; phân biệt retrieval failure với generation failure.

### Technical Lead / Architect

Thiết kế deterministic security boundary, evaluation framework và reindex strategy; quyết định RAG có cần thiết hay simpler search/full-context đủ dùng.

## 11. Key takeaway

* Chunking là retrieval design, không phải preprocessing phụ.
* Khi answer sai, inspect retrieved context trước khi chỉnh prompt.
* Authorization và document version phải deterministic bên ngoài LLM.
