# 1. C# nullable reference types: biến nullability thành compile-time contract thay vì chờ `NullReferenceException` ở production

## 1. What is it?

Nullable reference types (NRT) cho compiler biết reference nào được kỳ vọng không-null và reference nào có thể null. `string` và `string?` vẫn cùng runtime type; khác biệt nằm ở static analysis và contract mà code thể hiện.

Mental model: nullability annotation không “chặn null ở runtime”; nó làm cho khả năng null trở thành thông tin compiler có thể theo dõi qua control flow.

## 2. Why does it exist?

Trước NRT, mọi reference về lý thuyết đều có thể null nhưng signature không nói điều đó. Caller phải đọc implementation, documentation hoặc đoán. Sai assumption chỉ lộ ra bằng `NullReferenceException`.

NRT đưa một phần correctness này về compile time, đặc biệt hữu ích trong API contracts, DTO mapping và domain code lớn.

## 3. How does it work?

Compiler thực hiện flow analysis:

```csharp
string? name = FindName();

if (name is not null)
{
    Console.WriteLine(name.Length); // known non-null here
}
```

Annotation như `?`, null checks và attributes trong `System.Diagnostics.CodeAnalysis` giúp compiler suy luận state.

`!` chỉ suppress warning:

```csharp
return value!;
```

Nó không tạo runtime guard.

## 4. Practical implementation

Giữ contract rõ ở boundary:

```csharp
public sealed record CreateCustomerRequest(string Name, string? MiddleName);

public Customer Create(CreateCustomerRequest request)
{
    ArgumentException.ThrowIfNullOrWhiteSpace(request.Name);
    return new Customer(request.Name, request.MiddleName);
}
```

Với EF Core, nullability cũng nên phản ánh schema:

```csharp
public string Email { get; private set; } = null!;
public string? PhoneNumber { get; private set; }
```

`null!` ở entity có thể hợp lý khi framework materialization đảm bảo field được set, nhưng phải là deliberate boundary chứ không phải cách tắt warning hàng loạt.

## 5. Real production scenario

Một integration đổi field `customer.phone` thành optional. DTO nội bộ vẫn khai báo non-null và code gọi `.Trim()`. Deserializer tạo null, production bắt đầu 500.

Nếu contract được model bằng `string?`, compiler ép các call sites xử lý missing value từ trước.

## 6. Failure scenario & troubleshooting

**Symptom** → project bật NRT và xuất hiện hàng nghìn warnings.

**Evidence** → legacy models dùng annotations không nhất quán, nhiều `!` được thêm để build xanh.

**Hypothesis** → migration đang suppress uncertainty thay vì mô hình hóa contract.

**Diagnosis** → ưu tiên public boundaries, database models và hot paths; phân loại warning thật với framework initialization.

**Fix** → migrate theo module, thêm guards và annotations đúng; chỉ dùng suppression khi invariant được framework/application đảm bảo.

**Verification** → warning count giảm mà không tăng `!` tùy tiện; integration tests cover null inputs.

## 7. Common mistakes

* Nghĩ `string` không thể nhận null ở runtime.
* Dùng `!` để tắt mọi warning.
* Annotation DTO khác thực tế external contract.
* Bật NRT toàn solution legacy rồi sửa warning cơ học.

## 8. Alternatives

Runtime guard clauses vẫn cần ở untrusted boundaries. Option/Maybe types có thể biểu diễn absence rõ hơn trong domain phức tạp nhưng tăng abstraction cost.

## 9. Trade-offs

### Advantages

* Contract rõ hơn.
* Phát hiện nhiều null bugs ở compile time.
* Refactoring an toàn hơn.

### Costs / Risks

* Legacy migration tốn công.
* Annotation sai tạo false confidence.
* Interop với reflection/framework code có thể cần suppression có kiểm soát.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `T?` biểu thị khả năng null và compiler flow analysis.

### Middle

Thiết kế DTO/service signatures đúng và xử lý warning thay vì suppress.

### Senior

Phân biệt trusted invariants với untrusted boundaries, thiết kế migration strategy cho codebase cũ.

### Technical Lead / Architect

Quyết định nullability policy toàn solution, enforcement trong CI và boundary conventions giữa domain, persistence và integrations.

## 11. Key takeaway

* NRT là compile-time contract, không phải runtime enforcement.
* `!` che warning chứ không loại null.
* Giá trị lớn nhất đến từ annotations phản ánh đúng boundary thực tế.

# 2. ASP.NET Core idempotency key cho POST: retry an toàn mà không tạo duplicate business side effect

## 1. What is it?

Idempotency key là client-generated identifier đại diện cho một logical operation. Khi client retry cùng operation, server nhận cùng key và trả lại kết quả đã ghi nhận thay vì thực thi business side effect lần nữa.

## 2. Why does it exist?

Network timeout tạo ambiguity: client không biết request chưa tới server hay server đã commit nhưng response bị mất.

Với `POST /payments`, retry mù có thể charge hai lần. “Không retry” lại làm reliability kém khi lỗi chỉ là transient network failure.

## 3. How does it work?

Flow:

```text
POST + Idempotency-Key
       ↓
lookup key
 ┌─────┴─────┐
 exists     new
   ↓          ↓
return      execute
stored      transaction
result        ↓
           store key + outcome
```

Key phải gắn với caller/tenant và request semantics. Nếu cùng key nhưng payload khác, server nên reject thay vì silently reuse result.

## 4. Practical implementation

Schema đơn giản:

```sql
CREATE TABLE IdempotencyRecords (
    TenantId uniqueidentifier NOT NULL,
    IdempotencyKey nvarchar(100) NOT NULL,
    RequestHash varbinary(32) NOT NULL,
    StatusCode int NULL,
    ResponseBody nvarchar(max) NULL,
    CreatedAtUtc datetime2 NOT NULL,
    CONSTRAINT PK_IdempotencyRecords PRIMARY KEY (TenantId, IdempotencyKey)
);
```

Trong ASP.NET Core, middleware/filter có thể đọc `Idempotency-Key`, nhưng business transaction cần đảm bảo unique constraint và side effect được phối hợp đúng. Với payment provider, nên propagate provider-specific idempotency key nếu họ hỗ trợ.

## 5. Real production scenario

Mobile app gửi order, server commit thành công nhưng connection rớt trước response. App retry sau 3 giây.

Không có idempotency, hai orders được tạo. Có key, unique constraint khiến second request nhận cùng logical result.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate order vẫn xuất hiện dù API yêu cầu idempotency key.

**Evidence** → application dùng “check then insert” ngoài transaction trên nhiều instances.

**Hypothesis** → race giữa hai requests cùng key.

**Diagnosis** → inspect concurrent traces và database uniqueness.

**Fix** → enforce unique constraint tại durable store; xử lý unique violation như concurrent duplicate; gắn record với transaction/business outcome phù hợp.

**Verification** → gửi hàng chục concurrent requests cùng key và xác nhận chỉ một side effect.

## 7. Common mistakes

* Chỉ cache key trong memory một instance.
* Không bind key với tenant.
* Reuse cùng key cho payload khác.
* TTL quá ngắn so với retry window.
* Nghĩ HTTP method `POST` tự nhiên idempotent.

## 8. Alternatives

`PUT` với client-chosen resource ID tự nhiên idempotent trong nhiều resource-creation scenarios. Message consumers có thể dùng Inbox/deduplication thay vì HTTP idempotency record.

## 9. Trade-offs

### Advantages

* Retry an toàn hơn.
* Giảm duplicate financial/business effects.
* Cải thiện reliability trên mobile/network không ổn định.

### Costs / Risks

* Cần durable state và cleanup.
* Response replay semantics cần thiết kế.
* Không giải quyết side effect bên ngoài nếu external provider không idempotent.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry có thể tạo duplicate.

### Middle

Implement key validation, uniqueness và response reuse.

### Senior

Thiết kế atomicity giữa key record, DB write và external side effect.

### Technical Lead / Architect

Xác định operation nào cần idempotency, retention bao lâu và contract xuyên service/provider như thế nào.

## 11. Key takeaway

* Timeout không cho biết server đã commit hay chưa.
* Idempotency phải dựa trên durable uniqueness, không phải check-in-memory.
* External side effects cũng cần idempotency boundary tương ứng.

# 3. EF Core migration bundles: tách schema deployment khỏi application startup và kiểm soát release database có chủ đích

## 1. What is it?

Migration bundle đóng gói EF Core migrations thành executable có thể chạy trong deployment pipeline mà không cần application tự gọi `Database.Migrate()` khi startup.

## 2. Why does it exist?

Auto-migrate khi nhiều app instances khởi động tạo coupling giữa application availability và schema mutation. Migration dài hoặc destructive có thể khiến startup timeout, race hoặc rollout khó kiểm soát.

Release engineering cần biết migration chạy khi nào, bằng identity nào và thất bại thì dừng ở đâu.

## 3. How does it work?

Bundle chứa migration metadata và logic apply pending migrations tới target database. Pipeline có thể chạy:

```text
commit → build → test → artifact
                  ↓
             migration bundle
                  ↓
          controlled DB step
                  ↓
             deploy app
```

Migration history table vẫn theo dõi những migration đã apply.

## 4. Practical implementation

Build:

```bash
dotnet ef migrations bundle --self-contained -r linux-x64
```

Pipeline chạy bundle với connection string được cấp qua secret mechanism:

```bash
./efbundle --connection "$APP_DB_CONNECTION"
```

Migration nên backward-compatible khi old/new application versions có thể coexist.

## 5. Real production scenario

App Service scale 8 instances. Version mới gọi `Database.Migrate()` ở startup. Deployment restart đồng thời, nhiều instances tranh nhau startup trong lúc migration tạo index lớn.

Tách migration thành pipeline step giúp chỉ một controlled actor thay đổi schema trước rollout.

## 6. Failure scenario & troubleshooting

**Symptom** → migration step chạy hàng chục phút và release bị treo.

**Evidence** → migration tạo index/blocking operation trên bảng lớn.

**Hypothesis** → schema change được test functional nhưng không test production data volume.

**Diagnosis** → inspect SQL, locks, execution duration trên production-like dataset.

**Fix** → tách migration, dùng online/concurrent technique khi DB hỗ trợ, backfill theo batch và expand-contract.

**Verification** → rehearsal với realistic data size và rollback/roll-forward plan.

## 7. Common mistakes

* Xem migration generated code là an toàn mặc định.
* Cho application runtime identity quyền DDL không cần thiết.
* Deploy destructive migration trước khi old app ngừng chạy.
* Không backup/recovery rehearsal cho high-risk change.

## 8. Alternatives

SQL migration scripts reviewed thủ công cho phép DBA control sâu hơn. Dedicated tools như Flyway/Liquibase phù hợp polyglot environments. Auto-migrate có thể đủ cho local/dev hoặc service rất nhỏ.

## 9. Trade-offs

### Advantages

* Release step rõ ràng, auditable.
* Runtime app có thể chạy với least-privilege DML permissions.
* Giảm startup coupling.

### Costs / Risks

* Pipeline phức tạp hơn.
* Schema/app compatibility phải được quản lý có chủ đích.
* Bundle không tự biến migration nguy hiểm thành an toàn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu migration thay đổi schema và migration history.

### Middle

Build/run bundle, quản lý connection configuration và test migration.

### Senior

Review locking, data volume, compatibility và recovery.

### Technical Lead / Architect

Định nghĩa database release policy, permission boundary và expand-contract lifecycle.

## 11. Key takeaway

* Schema deployment là release operation riêng, không nên vô thức gắn vào startup.
* Bundle cải thiện control nhưng không thay thế migration review.
* Backward compatibility quyết định zero-downtime rollout.

# 4. PostgreSQL advisory locks: coordination theo business key mà không cần giữ row lock giả tạo

## 1. What is it?

Advisory lock là application-defined lock do PostgreSQL quản lý. Thay vì khóa một row cụ thể, application đưa vào một numeric key đại diện cho logical resource như `tenant + job type`.

## 2. Why does it exist?

Một số coordination problem không có row tự nhiên để khóa. Ví dụ chỉ một instance được generate monthly invoice cho tenant X.

Tạo “dummy lock row” chỉ để `SELECT ... FOR UPDATE` có thể làm persistence model méo mó.

## 3. How does it work?

PostgreSQL cung cấp session-level và transaction-level advisory locks. Transaction-level lock tự release khi transaction kết thúc.

```sql
SELECT pg_try_advisory_xact_lock(@lock_key);
```

Nếu trả `true`, transaction sở hữu lock. `false` nghĩa actor khác đang giữ.

## 4. Practical implementation

Với Npgsql:

```csharp
await using var tx = await connection.BeginTransactionAsync(ct);
await using var cmd = new NpgsqlCommand(
    "SELECT pg_try_advisory_xact_lock(@key)", connection, tx);
cmd.Parameters.AddWithValue("key", lockKey);

var acquired = (bool)(await cmd.ExecuteScalarAsync(ct))!;
if (!acquired)
    return;

await GenerateInvoicesAsync(ct);
await tx.CommitAsync(ct);
```

Hash/business-key mapping phải deterministic và collision risk phải được hiểu.

## 5. Real production scenario

Worker chạy trên 6 replicas, mỗi phút scan tenant cần settlement. Hai replicas chọn cùng tenant. Advisory lock theo tenant đảm bảo chỉ một transaction thực thi critical section.

## 6. Failure scenario & troubleshooting

**Symptom** → jobs chờ lock lâu, DB transactions mở dài.

**Evidence** → critical section chứa external HTTP call 30 giây.

**Hypothesis** → lock scope bao quanh I/O không thuộc database transaction.

**Diagnosis** → inspect transaction duration và lock holders.

**Fix** → thu nhỏ critical section hoặc chuyển sang lease/queue ownership phù hợp hơn.

**Verification** → đo lock wait và transaction duration sau refactor.

## 7. Common mistakes

* Dùng advisory lock như distributed workflow engine.
* Giữ transaction mở qua remote calls.
* Key mapping không documented.
* Quên session-level lock có lifecycle khác transaction-level lock.

## 8. Alternatives

Unique constraints đôi khi giải quyết race đơn giản hơn. Queue partitioning, Redis lease hoặc dedicated scheduler phù hợp coordination xuyên storage/service boundary.

## 9. Trade-offs

### Advantages

* Không cần dummy rows.
* Coordination nằm gần transactional data.
* Transaction-level cleanup rõ ràng.

### Costs / Risks

* PostgreSQL-specific.
* Lock contention có thể làm DB thành coordination bottleneck.
* Không tự cung cấp fencing cho actor đã mất ownership bên ngoài DB transaction.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu advisory lock khóa logical key.

### Middle

Dùng try-lock và transaction lifecycle đúng.

### Senior

Đánh giá contention, failure và lock scope.

### Technical Lead / Architect

Quyết định coordination nên ở database, queue hay distributed lease dựa trên ownership boundary.

## 11. Key takeaway

* Advisory lock phù hợp logical resource không có row tự nhiên.
* Critical section phải ngắn.
* Đừng biến database thành generic distributed coordinator nếu bài toán vượt transaction boundary.

# 5. Elasticsearch shard sizing: scale search bằng phân vùng hợp lý thay vì tăng shard count vô hạn

## 1. What is it?

Shard là đơn vị phân vùng Lucene index mà Elasticsearch phân phối trên nodes. Primary shard chứa một phần dữ liệu; replica shard cung cấp redundancy và read capacity.

## 2. Why does it exist?

Một index quá lớn không thể scale chỉ trên một node. Sharding cho phép phân phối storage và query/indexing work.

Nhưng mỗi shard có metadata, segments, file handles, heap và coordination overhead. Nhiều shard nhỏ không đồng nghĩa scale tốt.

## 3. How does it work?

Search request thường fan-out tới relevant shards, mỗi shard execute query rồi coordinating node merge kết quả.

```text
Search API
   ↓
coordinating node
 ├─ shard 0
 ├─ shard 1
 └─ shard 2
   ↓
merge top hits
```

Shard count vì vậy ảnh hưởng parallelism lẫn fan-out cost.

## 4. Practical implementation

Khi tạo index, chọn primary shard count dựa trên expected data volume, growth và node topology thay vì default mù:

```json
{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1
  }
}
```

Theo dõi shard size, segment count, heap, query latency và recovery time. Dùng rollover/ILM cho time-based data thay vì một index tăng vô hạn.

## 5. Real production scenario

Một platform tạo index riêng cho từng tenant nhỏ. Sau vài nghìn tenants, cluster có hàng chục nghìn tiny shards dù tổng data chưa lớn. Master/heap pressure tăng và cluster state operations chậm.

Gộp tenants vào shared index với routing hợp lý giảm shard overhead đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → search latency tăng dù CPU/data volume không tăng tương ứng.

**Evidence** → shard count rất cao, nhiều shard vài MB, heap pressure và GC tăng.

**Hypothesis** → oversharding.

**Diagnosis** → inspect `_cat/shards`, shard sizes, cluster stats, query fan-out.

**Fix** → rollover/reindex vào topology mới, consolidate tiny indices, dùng routing khi phù hợp.

**Verification** → so sánh heap, search p95 và cluster recovery behavior.

## 7. Common mistakes

* Một tenant = một index bất kể kích thước.
* Tăng shards để “query nhanh hơn” mà không benchmark.
* Quên shard count khó thay đổi trực tiếp sau index creation.
* Replica count cao hơn availability/read requirement.

## 8. Alternatives

Shared index + tenant field/routing thường đơn giản hơn per-tenant index. Dedicated cluster/index có thể hợp lý cho tenant rất lớn hoặc isolation requirement đặc biệt.

## 9. Trade-offs

### Advantages

* Sharding đúng cho phép scale storage và throughput.
* Replicas tăng resilience/read capacity.

### Costs / Risks

* Oversharding gây heap/coordination overhead.
* Undersharding tạo hot large shards và recovery chậm.
* Re-sharding thường cần reindex/operational work.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index gồm primary/replica shards.

### Middle

Theo dõi shard allocation và basic cluster health.

### Senior

Thiết kế shard topology theo data growth, query pattern và recovery target.

### Technical Lead / Architect

Quyết định tenant isolation, lifecycle và cluster capacity thay vì để index model tự phát triển.

## 11. Key takeaway

* Shard là resource có cost, không phải free parallelism.
* Oversharding có thể giết cluster trước khi storage đầy.
* Topology phải dựa trên workload và growth evidence.

# 6. Fencing token cho distributed lease: ngăn owner cũ tiếp tục ghi sau khi lease đã hết hạn

## 1. What is it?

Fencing token là monotonically increasing number cấp mỗi lần một actor nhận distributed lease. Downstream resource chỉ chấp nhận write có token mới hơn hoặc bằng token cuối đã thấy.

## 2. Why does it exist?

Lease có timeout nhưng process có thể pause vì GC, network partition hoặc scheduler. Actor A giữ lease, bị pause; lease hết hạn và B nhận lease mới. A tỉnh lại và tưởng mình vẫn có quyền ghi.

Distributed lock đơn thuần không thể thu hồi CPU đã chạy ở actor cũ.

## 3. How does it work?

```text
A gets lease token 41
A pauses
lease expires
B gets lease token 42
B writes with 42 -> accepted
A resumes, writes with 41 -> rejected
```

Correctness nằm ở downstream resource enforcing token order, không chỉ lock service.

## 4. Practical implementation

Một durable coordinator cấp increasing `LeaseVersion`. Write command mang version:

```csharp
public sealed record UpdateProjection(
    Guid ProjectionId,
    long FencingToken,
    string Payload);
```

Database update:

```sql
UPDATE Projection
SET Payload = @payload,
    LastFencingToken = @token
WHERE Id = @id
  AND LastFencingToken < @token;
```

0 affected rows nghĩa actor stale.

## 5. Real production scenario

Hai workers rebuild cùng search projection. Redis lease của worker A hết hạn trong một long GC pause. B nhận lease và ghi projection mới. A resume và overwrite bằng dữ liệu cũ.

Fencing token khiến stale write của A bị database từ chối.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate workers hiếm nhưng dữ liệu đôi khi quay về version cũ.

**Evidence** → lease logs cho thấy ownership chuyển, nhưng stale owner vẫn hoàn thành work.

**Hypothesis** → lock có expiry nhưng downstream không fence stale owner.

**Diagnosis** → correlate lease generation với write timestamps.

**Fix** → cấp monotonic token và enforce tại write boundary.

**Verification** → inject pause dài hơn lease TTL rồi xác nhận old owner bị reject.

## 7. Common mistakes

* Tin rằng TTL lock đảm bảo mutual exclusion tuyệt đối.
* Generate random token thay vì monotonic ordering.
* Có token nhưng downstream không validate.
* Giữ lease quá lâu để “tránh hết hạn” thay vì thiết kế correctness.

## 8. Alternatives

Single-consumer queue partition có thể tránh concurrent ownership. Database transaction/row lock tốt hơn nếu toàn critical work nằm trong một DB transaction ngắn.

## 9. Trade-offs

### Advantages

* Bảo vệ khỏi stale owner.
* Làm lease-based coordination mạnh hơn về correctness.

### Costs / Risks

* Downstream phải hỗ trợ token validation.
* Cần monotonic durable generation.
* Tăng protocol complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu lease expiry không thể “dừng” process cũ.

### Middle

Propagate token cùng operation.

### Senior

Thiết kế stale-write rejection và failure injection.

### Technical Lead / Architect

Quyết định có cần distributed lease hay queue/database ownership đơn giản hơn.

## 11. Key takeaway

* Distributed lock hết hạn không bảo đảm owner cũ đã ngừng chạy.
* Fencing phải được enforce ở resource nhận write.
* Nếu coordination đơn giản hơn giải quyết được bài toán, đừng thêm lease protocol.

# 7. Azure App Service autoscale: scale theo evidence và downstream capacity thay vì chỉ nhìn CPU

## 1. What is it?

Autoscale điều chỉnh số App Service instances theo metrics/rules để đáp ứng workload. Scale-out tăng instances; scale-in giảm instances.

## 2. Why does it exist?

Traffic thay đổi theo giờ, campaign hoặc batch workload. Provision peak capacity 24/7 lãng phí; provision average capacity gây overload lúc peak.

Nhưng scale app không tự scale SQL, Redis hay third-party quota.

## 3. How does it work?

Platform quan sát metric trong time window, áp threshold/cooldown rồi thay đổi instance count. New instance cần startup, load configuration và warm dependencies trước khi phục vụ ổn định.

CPU chỉ là một signal. Request queue, latency, memory hoặc application metric đôi khi phản ánh saturation tốt hơn.

## 4. Practical implementation

Một policy có thể đặt min 2, max 10, scale out khi CPU > 70% đủ lâu và scale in chậm hơn. Application phải stateless hoặc externalize session/state để requests có thể đi tới bất kỳ instance nào.

Theo dõi cùng lúc:

* instance count,
* request rate,
* p95 latency,
* HTTP 5xx,
* SQL connection utilization,
* dependency throttling.

## 5. Real production scenario

Campaign tăng traffic 4x. Autoscale từ 3 lên 9 instances. API CPU giảm nhưng SQL connection count tăng gấp ba và database bắt đầu throttle. Overall latency còn tệ hơn.

Scale policy đúng phải xem toàn capacity chain, không chỉ compute tier.

## 6. Failure scenario & troubleshooting

**Symptom** → instance count tăng nhưng p95 vẫn tăng.

**Evidence** → dependency latency/429 tăng cùng scale-out.

**Hypothesis** → bottleneck downstream.

**Diagnosis** → traces và dependency metrics cho thấy SQL/API quota saturation.

**Fix** → giới hạn app concurrency, tối ưu dependency, tăng downstream capacity hoặc queue work phù hợp.

**Verification** → load test toàn chain và xác nhận throughput tăng mà dependency error không tăng.

## 7. Common mistakes

* Scale chỉ theo CPU.
* Min instance quá thấp gây cold capacity.
* Scale-in quá aggressive gây oscillation.
* Lưu session/in-memory coordination giả định single instance.

## 8. Alternatives

Azure Container Apps/KEDA phù hợp event-driven scaling. Fixed capacity đơn giản hơn cho stable low-volume workloads. Queue load leveling phù hợp work có thể asynchronous.

## 9. Trade-offs

### Advantages

* Match capacity với demand.
* Tăng resilience trước traffic variation.

### Costs / Risks

* Cost tăng nhanh nếu rule sai.
* Downstream bottleneck có thể bị khuếch đại.
* Scale không tức thời.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu scale-up khác scale-out.

### Middle

Cấu hình rule và quan sát instance metrics.

### Senior

Thiết kế metric/cooldown dựa trên saturation và downstream behavior.

### Technical Lead / Architect

Xây capacity model end-to-end, cost guardrail và load-test strategy trước peak event.

## 11. Key takeaway

* Autoscale app không tự động tăng capacity toàn hệ thống.
* Metric phải đại diện saturation thực.
* Scale policy cần cost, cooldown và downstream guardrails.

# 8. `dotnet-counters` và EventCounters: điều tra CPU, GC, ThreadPool và exception pressure trước khi lấy memory dump

## 1. What is it?

`dotnet-counters` là diagnostic tool đọc runtime/application counters từ process .NET đang chạy. Nó cung cấp low-overhead telemetry tức thời về CPU, GC, allocations, ThreadPool, exceptions và nhiều provider khác.

## 2. Why does it exist?

Khi production “chậm”, lấy dump ngay thường quá nặng và chưa biết cần tìm gì. Counters giúp phân loại symptom trước: CPU-bound, allocation pressure, ThreadPool starvation hay exception storm.

## 3. How does it work?

Runtime phát diagnostic counters định kỳ. Tool subscribe qua diagnostics IPC và hiển thị rate/gauge.

Investigation loop:

```text
symptom → counters → classify → hypothesis → deeper trace/dump → fix → counters again
```

## 4. Practical implementation

Liệt kê process:

```bash
dotnet-counters ps
```

Monitor runtime:

```bash
dotnet-counters monitor --process-id 1234 System.Runtime
```

Quan sát các tín hiệu như CPU usage, allocation rate, GC heap size, Gen 2 collections, ThreadPool queue length và exception count.

## 5. Real production scenario

API p99 tăng nhưng CPU chỉ 35%. `dotnet-counters` cho thấy ThreadPool queue length tăng và worker thread count liên tục được bổ sung. Stack trace sau đó tìm ra blocking `.Result` trong request path.

Counters giúp chọn đúng hướng trước khi thu trace sâu.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng liên tục.

**Evidence** → allocation rate cao nhưng heap size sau GC ổn định.

**Hypothesis** → allocation-heavy workload, chưa chắc memory leak.

**Diagnosis** → phân biệt retained heap growth với temporary allocation; nếu heap sau Gen2 vẫn tăng mới lấy dump để inspect roots.

**Fix** → tùy evidence: giảm allocations hoặc tìm retained references.

**Verification** → chạy cùng workload và so allocation rate/heap trend.

## 7. Common mistakes

* Thấy GC cao rồi tăng memory ngay.
* Gọi mọi memory growth là leak.
* Chỉ nhìn CPU average.
* Thu dump production liên tục mà không có hypothesis.

## 8. Alternatives

Application Insights/Azure Monitor tốt cho historical telemetry. `dotnet-trace`, PerfView hoặc profiler cung cấp detail sâu hơn nhưng overhead/analysis cost cao hơn.

## 9. Trade-offs

### Advantages

* Low-overhead triage.
* Runtime signals trực tiếp.
* Hữu ích trước trace/dump.

### Costs / Risks

* Counter chỉ cho symptom, không luôn chỉ code line.
* Snapshot ngắn có thể bỏ lỡ intermittent incident.
* Cần correlate với request/dependency telemetry.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết CPU, heap, GC, ThreadPool là các resource signals khác nhau.

### Middle

Dùng tool và đọc basic counters.

### Senior

Từ counter pattern tạo hypothesis và chọn trace/dump phù hợp.

### Technical Lead / Architect

Chuẩn hóa production diagnostics/runbook và quyền truy cập tooling an toàn.

## 11. Key takeaway

* Counters là bước triage, không phải root cause tự động.
* Allocation cao khác retained-memory leak.
* Đo trước rồi mới chọn diagnostic tool nặng hơn.

# 9. React stale closures: async callback có thể đọc state cũ dù UI đã render state mới

## 1. What is it?

Mỗi React render tạo một lexical snapshot của props/state. Callback được tạo trong render đó đóng (close over) snapshot ấy. Nếu callback chạy sau, nó vẫn có thể nhìn giá trị cũ dù component đã render lại.

## 2. Why does it exist?

JavaScript closures giữ bindings từ lexical scope. React functional components dựa trên immutable render snapshots. Hai cơ chế kết hợp tạo behavior đúng về ngôn ngữ nhưng dễ bất ngờ với timers, promises và subscriptions.

## 3. How does it work?

```tsx
const [count, setCount] = useState(0);

useEffect(() => {
  const id = setInterval(() => {
    console.log(count);
  }, 1000);

  return () => clearInterval(id);
}, []);
```

Effect chạy từ render đầu và closure giữ `count = 0`.

## 4. Practical implementation

Nếu update dựa trên state trước đó, dùng functional update:

```tsx
setCount(current => current + 1);
```

Nếu subscription cần latest value mà không muốn resubscribe, `useRef` có thể giữ mutable current value có chủ đích. Nếu effect thực sự phụ thuộc state, khai báo dependency đúng.

## 5. Real production scenario

Search component gửi request async. User đổi filter nhanh. Callback của request cũ dùng filter snapshot cũ và overwrite result mới khi response đến muộn.

Giải pháp thường kết hợp `AbortController`, request identity hoặc state management bảo đảm stale response không thắng.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị dữ liệu của filter trước.

**Evidence** → network waterfall cho thấy request cũ hoàn thành sau request mới.

**Hypothesis** → stale closure/race giữa async responses.

**Diagnosis** → log request ID + filter snapshot.

**Fix** → cancel request cũ hoặc chỉ commit response của latest request.

**Verification** → throttle network và đổi filter liên tục.

## 7. Common mistakes

* Tắt exhaustive-deps warning mà không hiểu dependency.
* Thêm mọi thứ vào dependency array gây resubscribe loop.
* Dùng `useRef` để né reactivity cho mọi state.
* Không cancel obsolete HTTP requests.

## 8. Alternatives

State libraries/query libraries có thể quản lý request identity/cache. Vue có reactivity model khác nhưng async race vẫn tồn tại và cần cancellation/versioning.

## 9. Trade-offs

### Advantages

Render snapshot làm component behavior dễ reasoning khi hiểu đúng.

### Costs / Risks

Async callbacks có thể giữ stale values; effect lifecycle đòi discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu closure giữ state của render tạo callback.

### Middle

Dùng dependencies, functional update và cleanup đúng.

### Senior

Xử lý request races, cancellation và stale result protection.

### Technical Lead / Architect

Đặt conventions cho server-state fetching, cancellation và frontend observability thay vì mỗi component tự phát minh pattern.

## 11. Key takeaway

* Mỗi render là một state snapshot.
* Async completion order không đảm bảo request order.
* Cancellation/version checks quan trọng hơn chỉ sửa dependency array.

# 10. ADR trong technical leadership: ghi lại context, decision và consequences để kiến trúc không trở thành tribal knowledge

## 1. What is it?

Architecture Decision Record (ADR) là tài liệu ngắn ghi một quyết định kỹ thuật quan trọng: context, constraints, options, decision và consequences.

ADR không phải full architecture specification. Nó trả lời “vì sao chúng ta chọn cách này tại thời điểm đó?”.

## 2. Why does it exist?

Sau vài tháng, code chỉ cho biết system đang làm gì, không cho biết tại sao. Người mới dễ “sửa” một quyết định mà không biết constraint cũ, hoặc giữ legacy choice dù constraint đã biến mất.

## 3. How does it work?

Một ADR hữu ích thường có:

```text
Status
Context
Decision drivers
Options considered
Decision
Consequences
Follow-up / revisit trigger
```

Decision nên có scope rõ. ADR được version-control cùng engineering documentation và thay đổi trạng thái bằng ADR mới thay vì rewrite lịch sử.

## 4. Practical implementation

Ví dụ:

```markdown
# ADR-014: Use Modular Monolith for Release 1

Status: Accepted

Context:
Team 5 engineers, one deployment unit, domains still evolving.

Decision:
Use bounded modules in one deployable application.

Consequences:
+ simpler operations
+ transaction consistency where needed
- module boundaries require code-level enforcement

Revisit when:
Independent scaling/deployment becomes a measured constraint.
```

## 5. Real production scenario

Một developer đề xuất tách service vì module search “trông giống microservice”. ADR cũ cho thấy team đã chọn modular monolith vì operational capacity và transaction needs. Thảo luận chuyển từ preference sang việc constraint hiện tại có thay đổi hay chưa.

## 6. Failure scenario & troubleshooting

**Symptom** → repository có hàng chục ADR nhưng không ai tin chúng.

**Evidence** → status không cập nhật, decisions mới chỉ tồn tại trong Slack/PR.

**Hypothesis** → ADR là documentation ceremony, không nằm trong decision workflow.

**Diagnosis** → chọn vài architecture decisions gần đây và xem có trace tới ADR không.

**Fix** → chỉ yêu cầu ADR cho consequential decisions; link từ PR/design review; supersede rõ khi thay đổi.

**Verification** → người mới có thể giải thích decision drivers từ repository mà không cần hỏi tác giả cũ.

## 7. Common mistakes

* Viết ADR cho mọi library nhỏ.
* Ghi decision nhưng không ghi alternatives/consequences.
* Rewrite ADR cũ khiến mất historical reasoning.
* Dùng ADR để hợp thức hóa quyết định đã chốt mà không phân tích options.

## 8. Alternatives

Design docs phù hợp thay đổi lớn cần nhiều detail. README phù hợp current-state guidance. PR description tốt cho implementation-specific reasoning. ADR tốt nhất cho durable architectural decisions.

## 9. Trade-offs

### Advantages

* Giữ decision context lâu dài.
* Hỗ trợ onboarding và architecture review.
* Giảm tribal knowledge.

### Costs / Risks

* Documentation overhead nếu lạm dụng.
* Stale ADR gây hiểu sai nếu status không được quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết đọc ADR để hiểu context trước khi refactor.

### Middle

Ghi options và consequences cho quyết định module-level quan trọng.

### Senior

Phân tích decision drivers, operational impact và revisit triggers.

### Technical Lead / Architect

Xây lightweight decision process: cái gì cần ADR, ai review, khi nào supersede và cách liên kết với implementation.

## 11. Key takeaway

* ADR lưu reasoning, không chỉ kết quả.
* Chỉ document decisions có consequence đáng kể.
* Một ADR tốt phải cho biết khi nào quyết định nên được xem xét lại.
