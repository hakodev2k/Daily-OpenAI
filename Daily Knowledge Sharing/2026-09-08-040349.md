# 1. `CancellationToken` ownership: cancellation, timeout và shutdown trong .NET

## 1. What is it?

`CancellationToken` là cơ chế cooperative cancellation của .NET. Nó không dừng thread một cách cưỡng bức. Nó chỉ truyền tín hiệu để code ở các layer chủ động dừng tại safe point.

Mental model:

```text
Caller không còn cần kết quả
        ↓
Token được signal
        ↓
Callee quan sát token
        ↓
Dừng ở điểm an toàn
```

## 2. Why does it exist?

Nếu HTTP client đã rời đi nhưng server vẫn query database, gọi downstream API và serialize response, hệ thống đang tiêu tốn capacity cho work không còn giá trị.

Cancellation cũng cần cho graceful shutdown của background workers.

## 3. How does it work?

ASP.NET Core expose `RequestAborted`. Token này có thể được propagate xuống EF Core, `HttpClient`, file I/O và background APIs.

Timeout khác cancellation về meaning. Timeout nói operation vượt quá time budget; cancellation nói caller không còn muốn tiếp tục.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    OrdersDbContext db,
    CancellationToken ct) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    return order is null
        ? Results.NotFound()
        : Results.Ok(order);
});
```

Khi có downstream timeout riêng:

```csharp
using var timeout = new CancellationTokenSource(TimeSpan.FromSeconds(2));
using var linked = CancellationTokenSource.CreateLinkedTokenSource(ct, timeout.Token);
```

## 5. Real production scenario

Search API fan-out sang nhiều dependencies. User đổi màn hình giữa chừng và request bị abort. Nếu token không được propagate, abandoned work vẫn chạy và làm tăng connection usage dưới load.

## 6. Failure scenario & troubleshooting

**Symptom** → backend load vẫn cao sau nhiều client timeouts.  
**Evidence** → downstream spans tiếp tục chạy sau request abort.  
**Hypothesis** → cancellation signal bị mất qua một layer.  
**Diagnosis** → trace từ HTTP boundary xuống I/O calls.  
**Fix** → propagate token đúng chỗ.  
**Verification** → abort integration test và xác nhận downstream work dừng sớm.

## 7. Common mistakes

* Tạo CTS ở mọi method mà không có ownership rõ.
* Log mọi `OperationCanceledException` như Error.
* Dùng request token cho critical completion step không nên bị bỏ dở.
* Nghĩ cancellation tự rollback external side effects.

## 8. Alternatives

Work cần sống độc lập với request nên được đưa vào queue/background processing thay vì cố giữ request mở.

## 9. Trade-offs

### Advantages

* Giảm wasted work.
* Shutdown sạch hơn.
* Giải phóng resource sớm.

### Costs / Risks

* Token phải đi xuyên nhiều layers.
* Cancel sai boundary có thể tạo partial work.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cancellation là cooperative signal.

### Middle

Biết propagate token vào I/O APIs.

### Senior

Phân biệt request cancellation, timeout và critical completion.

### Technical Lead / Architect

Thiết kế cancellation boundary theo business semantics và recovery path.

## 11. Key takeaway

* `CancellationToken` là lifecycle contract.
* Timeout và cancellation dùng cùng mechanism nhưng khác meaning.
* Không phải mọi operation đều nên dừng chỉ vì client disconnect.

# 2. ASP.NET Core middleware ordering: khi đúng middleware nhưng sai thứ tự vẫn tạo bug

## 1. What is it?

ASP.NET Core middleware pipeline xử lý request theo thứ tự đăng ký. Mỗi middleware có thể làm việc trước và sau `next()`.

```text
Request
 → A before
   → B before
     → Endpoint
   ← B after
 ← A after
Response
```

Order là một phần của behavior.

## 2. Why does it exist?

Exception handling, forwarded headers, CORS, authentication và authorization phụ thuộc vào context đã được chuẩn bị từ middleware trước đó.

## 3. How does it work?

Một pipeline điển hình:

```text
Forwarded Headers
→ Exception Handling
→ Routing
→ CORS
→ Authentication
→ Authorization
→ Endpoint
```

Một số middleware có thể short-circuit và không gọi `next()`.

## 4. Practical implementation

```csharp
app.UseForwardedHeaders();
app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseRouting();
app.UseCors("frontend");
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
```

Thứ tự thực tế phải phù hợp hosting topology và middleware cụ thể.

## 5. Real production scenario

App chạy sau reverse proxy. Nếu forwarded headers được xử lý quá muộn, application có thể hiểu request là HTTP dù client dùng HTTPS, dẫn tới redirect loop hoặc ghi sai client IP.

## 6. Failure scenario & troubleshooting

**Symptom** → redirect loop, 401/403 bất thường, CORS preflight fail.  
**Evidence** → identity/scheme chưa tồn tại khi middleware sau cần dùng.  
**Hypothesis** → ordering issue.  
**Diagnosis** → log state ở từng pipeline boundary.  
**Fix** → sắp xếp theo dependency flow.  
**Verification** → integration test qua proxy/auth scenarios.

## 7. Common mistakes

* Copy pipeline từ project khác.
* Đặt exception handler quá muộn.
* Nghĩ authentication tự động enforce authorization.
* Trust forwarded headers không có boundary rõ.

## 8. Alternatives

Một số concerns có thể đặt ở gateway/edge. Endpoint filters phù hợp concern gắn gần endpoint hơn.

## 9. Trade-offs

### Advantages

* Composition đơn giản.
* Cross-cutting behavior tập trung.

### Costs / Risks

* Ordering dependency dễ bị ẩn.
* Sai một middleware có blast radius toàn app.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request đi qua middleware theo thứ tự.

### Middle

Biết auth/CORS/error handling cần đúng vị trí.

### Senior

Debug short-circuit và reverse-proxy behavior.

### Technical Lead / Architect

Document pipeline invariants và phân chia concern giữa edge/gateway/app.

## 11. Key takeaway

* Middleware đúng nhưng đặt sai chỗ vẫn là bug.
* Ordering phải phản ánh dependency giữa concerns.
* Proxy topology ảnh hưởng trực tiếp tới pipeline design.

# 3. EF Core query compilation và compiled query: tối ưu đúng hot path

## 1. What is it?

EF Core phải phân tích LINQ expression, xác định query shape, translate sang SQL và thực thi với parameters. EF Core đã có query cache nội bộ. `EF.CompileQuery` / `EF.CompileAsyncQuery` cho phép precompile query delegate cho hot paths ổn định.

## 2. Why does it exist?

Trong đa số API, database I/O lớn hơn application-side query processing. Nhưng ở high-RPS path có query rất nhanh, query compilation overhead có thể trở nên measurable.

## 3. How does it work?

```text
LINQ
→ query shape
→ cache lookup / translation
→ SQL
→ database
```

Nếu query shape ổn định, caching hiệu quả. Dynamic expression thay đổi shape liên tục có thể làm cache kém hơn.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, Guid, Task<ProductDto?>> GetProduct =
    EF.CompileAsyncQuery(
        (AppDbContext db, Guid id) =>
            db.Products
              .AsNoTracking()
              .Where(x => x.Id == id)
              .Select(x => new ProductDto(x.Id, x.Name, x.Price))
              .SingleOrDefault());
```

Chỉ dùng sau khi benchmark cho thấy overhead có ý nghĩa.

## 5. Real production scenario

Catalog API có primary-key lookup dưới 1 ms nhưng chạy hàng chục nghìn RPS. Profiler cho thấy EF query processing chiếm CPU đáng kể. Đây là trường hợp compiled query có thể hợp lý.

## 6. Failure scenario & troubleshooting

**Symptom** → app CPU cao dù SQL rất nhanh.  
**Evidence** → profiler chỉ ra query processing overhead.  
**Hypothesis** → hot query chịu application-side compilation/cache cost.  
**Diagnosis** → benchmark normal vs compiled query.  
**Fix** → stabilize query shape hoặc compiled query.  
**Verification** → đo CPU/request và throughput trước/sau.

## 7. Common mistakes

* Dùng compiled query cho mọi repository method.
* Tối ưu compilation trước N+1 hoặc round trips.
* Dynamic LINQ tạo query shape mới liên tục.
* Không benchmark production-like workload.

## 8. Alternatives

Projection, `AsNoTracking`, giảm round trips, index/query-plan optimization và caching thường đáng xem trước.

## 9. Trade-offs

### Advantages

* Giảm repeated query processing overhead.

### Costs / Risks

* Code kém flexible hơn.
* Benefit nhỏ nếu DB I/O dominates.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ cần được translate trước khi DB chạy.

### Middle

Biết query shape và parameterization.

### Senior

Chỉ dùng compiled query sau profiling.

### Technical Lead / Architect

Không biến micro-optimization thành global convention thiếu evidence.

## 11. Key takeaway

* EF Core đã có query cache.
* Compiled query dành cho proven hot path.
* Database work thường đáng ưu tiên hơn microseconds ở app layer.

# 4. SQL Server isolation levels: Read Committed, RCSI và Snapshot

## 1. What is it?

Transaction isolation quyết định transaction nhìn thấy thay đổi concurrent như thế nào.

* Read Committed: thường dựa trên locks cho reads.
* RCSI: giữ Read Committed semantics nhưng dùng row versions cho reads.
* Snapshot Isolation: transaction nhìn một snapshot nhất quán theo thời điểm transaction bắt đầu.

## 2. Why does it exist?

Concurrency cần cân bằng consistency và blocking. Lock-based reads có thể block writers; row-versioned reads giảm blocking nhưng thêm version-store cost.

## 3. How does it work?

```text
Read Committed:
Reader lock ↔ Writer lock
```

```text
RCSI:
Writer tạo row version
Reader đọc committed version phù hợp statement
```

Snapshot Isolation là transaction-level snapshot, khác RCSI là statement-level committed snapshot.

## 4. Practical implementation

```sql
ALTER DATABASE CommerceDb
SET READ_COMMITTED_SNAPSHOT ON;
```

```sql
ALTER DATABASE CommerceDb
SET ALLOW_SNAPSHOT_ISOLATION ON;
```

```csharp
await using var tx = await db.Database.BeginTransactionAsync(
    IsolationLevel.Snapshot,
    ct);
```

## 5. Real production scenario

Reporting query chạy vài giây trên Orders trong lúc checkout liên tục update rows. RCSI có thể giảm reader/writer blocking, nhưng không loại bỏ write/write contention.

## 6. Failure scenario & troubleshooting

**Symptom** → blocking giảm nhưng tempdb/version-store tăng.  
**Evidence** → long transactions giữ versions lâu.  
**Hypothesis** → row-version lifetime quá dài.  
**Diagnosis** → inspect active transactions và version store.  
**Fix** → shorten transactions, optimize long queries, capacity-plan tempdb.  
**Verification** → đo blocking, p95/p99 và tempdb usage.

## 7. Common mistakes

* Dùng `NOLOCK` như giải pháp mặc định.
* Nghĩ RCSI = Snapshot Isolation.
* Nghĩ row versioning loại bỏ deadlock.
* Bật production setting mà không đo version-store impact.

## 8. Alternatives

Optimize query/index, reporting replica, application-level optimistic concurrency, materialized read model.

## 9. Trade-offs

### Advantages

* Giảm reader/writer blocking.

### Costs / Risks

* Version-store pressure.
* Long transactions giữ versions lâu.
* Không loại bỏ write contention.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu isolation ảnh hưởng dữ liệu transaction thấy.

### Middle

Phân biệt locking và row versioning.

### Senior

Đọc blocking/version-store evidence.

### Technical Lead / Architect

Chọn isolation theo consistency, workload và operational cost.

## 11. Key takeaway

* Isolation là concurrency design decision.
* RCSI và Snapshot không giống nhau.
* Giảm blocking phải đo cùng version-store cost.

# 5. Elasticsearch analyzer, `text`, `keyword` và multi-fields

## 1. What is it?

Elasticsearch mapping quyết định string được index thế nào.

* `text`: analyzed thành tokens cho full-text search.
* `keyword`: giữ giá trị gần nguyên vẹn cho exact match/filter/sort/aggregation.
* multi-fields: index cùng logical value theo nhiều representations.

## 2. Why does it exist?

User có thể muốn full-text search theo product name nhưng vẫn cần exact sort/filter. Một representation không phục vụ tốt cả hai access patterns.

## 3. How does it work?

```text
"Men's Running Shoes"
→ tokenizer
→ lowercase/filter
→ tokens
→ inverted index
```

`keyword` giữ value để exact operations.

## 4. Practical implementation

```json
{
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "fields": {
          "keyword": { "type": "keyword" }
        }
      },
      "sku": { "type": "keyword" }
    }
  }
}
```

Full-text query:

```json
{ "query": { "match": { "name": "running shoes" } } }
```

Exact query:

```json
{ "query": { "term": { "sku": "MEN-001-BLACK" } } }
```

## 5. Real production scenario

SKU bị map thành `text`. Search vẫn có vẻ hoạt động nhưng exact filtering trở nên khó dự đoán. Sửa mapping thường yêu cầu index mới + reindex + alias swap.

## 6. Failure scenario & troubleshooting

**Symptom** → exact filters miss hoặc aggregation lạ.  
**Evidence** → field mapping không phù hợp use case.  
**Hypothesis** → query/index representation mismatch.  
**Diagnosis** → inspect mapping và analyzer tokens.  
**Fix** → correct mapping, reindex.  
**Verification** → relevance + exact filter tests.

## 7. Common mistakes

* Dùng `text` cho ID/SKU.
* Dùng `keyword` cho long natural-language search.
* Dùng `term` trên analyzed text.
* Thay analyzer mà không có reindex strategy.

## 8. Alternatives

SQL full-text search có thể đủ cho use case đơn giản. Elasticsearch chỉ đáng vận hành khi search capability thực sự cần.

## 9. Trade-offs

### Advantages

* Mapping linh hoạt theo search behavior.

### Costs / Risks

* Sai mapping khó sửa in-place.
* Multi-fields tăng index size.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `text` khác `keyword`.

### Middle

Biết chọn query theo mapping.

### Senior

Dùng analyzer inspection và relevance tests.

### Technical Lead / Architect

Thiết kế search schema theo access patterns và migration cost.

## 11. Key takeaway

* Search schema là product behavior.
* `text` và `keyword` phục vụ hai mục đích khác nhau.
* Mapping sai thường dẫn tới reindex.

# 6. Saga Pattern + compensating transaction trong distributed workflow

## 1. What is it?

Saga là một business workflow gồm nhiều local transactions. Khi bước sau fail, hệ thống thực hiện compensating actions cho các bước trước nếu business cho phép.

```text
Reserve Inventory
→ Authorize Payment
→ Create Shipment fails
→ Cancel Authorization
→ Release Inventory
```

## 2. Why does it exist?

Distributed workflow thường không thể giữ một ACID transaction xuyên database, payment provider và shipping provider.

## 3. How does it work?

Hai style phổ biến:

* Orchestration: coordinator điều khiển steps.
* Choreography: services phản ứng qua events.

Compensation là business operation mới, không phải database rollback.

## 4. Practical implementation

```csharp
public sealed class OrderSaga
{
    public Guid OrderId { get; init; }
    public bool InventoryReserved { get; set; }
    public bool PaymentAuthorized { get; set; }
    public string Status { get; set; } = "Pending";
}
```

```csharp
if (!shipmentResult.Success)
{
    if (saga.PaymentAuthorized)
        await payments.CancelAuthorizationAsync(orderId, ct);

    if (saga.InventoryReserved)
        await inventory.ReleaseAsync(orderId, ct);
}
```

## 5. Real production scenario

Checkout reserve hàng và authorize payment thành công nhưng shipping provider timeout. Không thể rollback hai external effects như một SQL transaction.

## 6. Failure scenario & troubleshooting

**Symptom** → order stuck ở pending.  
**Evidence** → saga state dừng giữa steps.  
**Hypothesis** → partial failure.  
**Diagnosis** → inspect timeline, message IDs, downstream status.  
**Fix** → bounded retry, reconciliation, compensation hoặc manual recovery.  
**Verification** → integration tests cho crash sau từng step.

## 7. Common mistakes

* Gọi compensation là rollback hoàn hảo.
* Compensation không idempotent.
* Không persist saga state.
* Không có manual recovery.

## 8. Alternatives

Local ACID transaction đơn giản hơn nếu invariant nằm trong một database. Durable workflow engine hữu ích khi orchestration dài và cần checkpoint.

## 9. Trade-offs

### Advantages

* Hỗ trợ long-running distributed workflows.

### Costs / Risks

* Eventual consistency.
* Compensation cũng có thể fail.
* Debugging phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu distributed work không rollback như local DB transaction.

### Middle

Biết model steps và compensation.

### Senior

Thiết kế idempotency và recovery.

### Technical Lead / Architect

Xác định Saga có thật sự cần hay boundary đang bị chia quá sớm.

## 11. Key takeaway

* Saga là business recovery.
* Compensation cũng là distributed operation.
* Nếu local transaction đủ, đừng thêm Saga.

# 7. Azure Functions queue trigger: autoscaling, concurrency và downstream saturation

## 1. What is it?

Queue-triggered Azure Function xử lý messages theo event-driven model. Platform có thể scale instances khi backlog tăng.

```text
Queue backlog
→ scale-out
→ nhiều Functions xử lý song song
→ downstream nhận load lớn hơn
```

## 2. Why does it exist?

Queue hấp thụ burst và tách producer khỏi consumer. Functions giảm operational burden cho trigger/scale/retry.

## 3. How does it work?

Consumer concurrency là tích của số instances và concurrency trên mỗi instance. Vì vậy function layer có thể scale nhanh hơn database hoặc third-party API phía sau.

## 4. Practical implementation

```csharp
public sealed class ProcessOrderFunction
{
    [Function("ProcessOrder")]
    public async Task Run(
        [QueueTrigger("orders", Connection = "StorageConnection")] string message,
        CancellationToken ct)
    {
        var order = JsonSerializer.Deserialize<OrderMessage>(message)
                    ?? throw new InvalidOperationException("Invalid message");

        await processor.ProcessAsync(order, ct);
    }
}
```

Handler cần idempotent vì retries/duplicate delivery vẫn có thể xảy ra.

## 5. Real production scenario

Queue nhận 500.000 notification jobs. Functions scale nhanh nhưng CRM API phía sau có quota thấp hơn. 429 tăng, retries tăng thêm load và queue drain chậm.

## 6. Failure scenario & troubleshooting

**Symptom** → queue age tăng cùng dependency 429/timeouts.  
**Evidence** → function concurrency tăng nhanh hơn downstream capacity.  
**Hypothesis** → consumer scale vượt downstream limit.  
**Diagnosis** → correlate queue age, concurrency, dependency RPS.  
**Fix** → cap concurrency, bounded backoff, quota-aware design.  
**Verification** → burst test với dependency errors ổn định.

## 7. Common mistakes

* Nghĩ autoscaling luôn tốt hơn.
* Không idempotency.
* Retry poison messages không giới hạn.
* Chỉ monitor queue length, không monitor queue age.

## 8. Alternatives

Worker Service/Container Apps cho control sâu hơn. Durable Functions cho orchestration dài. Service Bus cho richer messaging semantics.

## 9. Trade-offs

### Advantages

* Burst handling tốt.
* Event-driven scale đơn giản.

### Costs / Risks

* Downstream overload.
* Retry/concurrency semantics cần hiểu kỹ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue tách producer và consumer.

### Middle

Biết trigger/retry/idempotency.

### Senior

Đo queue age và dependency saturation.

### Technical Lead / Architect

Thiết kế capacity end-to-end, không chỉ Function layer.

## 11. Key takeaway

* Queue hấp thụ burst nhưng không tạo thêm downstream capacity.
* Autoscaling cần backpressure.
* Queue age là signal quan trọng của user impact.

# 8. OAuth 2.0 Authorization Code + PKCE cho SPA

## 1. What is it?

Authorization Code Flow cho phép user đăng nhập ở Authorization Server rồi application đổi authorization code lấy token. PKCE thêm một verifier tạm thời cho mỗi authorization request.

## 2. Why does it exist?

SPA chạy trong browser nên không thể giữ confidential client secret. PKCE bảo vệ authorization code bằng một verifier chỉ client instance ban đầu biết.

## 3. How does it work?

```text
SPA tạo code_verifier
→ derive code_challenge
→ /authorize
→ receive code
→ /token + code_verifier
→ server verify
→ token
```

`state`, redirect URI validation và các OIDC controls khác vẫn có vai trò riêng.

## 4. Practical implementation

Trong production nên dùng maintained auth library thay vì tự viết protocol.

Conceptual TypeScript:

```ts
const verifier = generateVerifier();
const challenge = await createChallenge(verifier);

sessionStorage.setItem('pkce_verifier', verifier);
redirectToAuthorizationEndpoint({
  response_type: 'code',
  code_challenge: challenge,
  code_challenge_method: 'S256'
});
```

## 5. Real production scenario

Team migrate SPA từ legacy flow sang Authorization Code + PKCE. Một confidential secret không nên được đặt trong browser bundle vì client-side code không phải secret storage.

## 6. Failure scenario & troubleshooting

**Symptom** → token exchange `invalid_grant`.  
**Evidence** → verifier bị mất hoặc challenge mismatch.  
**Hypothesis** → protocol state không được preserve đúng.  
**Diagnosis** → inspect request metadata mà không log raw token.  
**Fix** → dùng maintained library và exact redirect configuration.  
**Verification** → integration tests login/logout/expired flows.

## 7. Common mistakes

* Tự implement toàn bộ OAuth flow.
* Không validate request correlation state.
* Log tokens.
* Nhầm authentication với authorization.

## 8. Alternatives

BFF pattern giữ token server-side. Client Credentials dành cho service-to-service, không đại diện interactive user.

## 9. Trade-offs

### Advantages

* Phù hợp public clients.
* Không dựa vào browser-held confidential secret.

### Costs / Risks

* Browser token handling vẫn cần threat model.
* Flow phức tạp hơn simple redirect.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SPA không phải secure secret store.

### Middle

Biết Authorization Code + PKCE flow.

### Senior

Đánh giá token lifecycle và browser security boundary.

### Technical Lead / Architect

Chọn direct SPA auth hay BFF theo threat model và operational needs.

## 11. Key takeaway

* PKCE bind authorization code với client request ban đầu.
* Browser không phải nơi giữ confidential secret.
* Dùng standards-compliant auth library.

# 9. CI/CD immutable artifact promotion: build once, deploy many

## 1. What is it?

Immutable artifact promotion nghĩa là source được build một lần thành artifact có identity cố định, rồi artifact đó được promote qua các environments.

```text
Commit SHA
→ Build once
→ Artifact digest X
  ├→ Dev
  ├→ Test
  ├→ Staging
  └→ Production
```

## 2. Why does it exist?

Rebuild ở mỗi environment có thể tạo binary drift do dependency resolution, base image hoặc toolchain thay đổi.

## 3. How does it work?

Build stage tạo package/image cùng metadata như source SHA và artifact hash. Deployment stage lấy đúng artifact đó và chỉ thay environment configuration.

## 4. Practical implementation

```yaml
steps:
  - run: dotnet restore --locked-mode
  - run: dotnet publish -c Release -o out
  - uses: actions/upload-artifact@v4
    with:
      name: app-${{ github.sha }}
      path: out
```

Các deployment stages download artifact thay vì rebuild.

## 5. Real production scenario

Staging pass tests. Production rebuild từ cùng commit nhưng dependency/base image đã đổi, nên executable khác staging dù source SHA giống nhau.

## 6. Failure scenario & troubleshooting

**Symptom** → production khác staging với cùng commit.  
**Evidence** → artifact hashes khác.  
**Hypothesis** → environment-specific rebuild.  
**Diagnosis** → compare digest/build metadata.  
**Fix** → promote exact artifact.  
**Verification** → assert digest giống nhau ở mọi environment.

## 7. Common mistakes

* Dùng mutable tag như `latest`.
* Rebuild ở production stage.
* Bake environment secret vào artifact.
* Rollback bằng rebuild commit cũ thay vì redeploy known-good artifact.

## 8. Alternatives

Reproducible builds hữu ích nhưng promote exact bytes vẫn cho deployment confidence cao hơn.

## 9. Trade-offs

### Advantages

* Test và production dùng cùng binary.
* Rollback deterministic hơn.
* Audit/provenance rõ.

### Costs / Risks

* Cần artifact registry và retention policy.
* Environment config phải được tách đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu source commit khác executable artifact.

### Middle

Biết version/store/deploy artifact.

### Senior

Verify digest, provenance và rollback path.

### Technical Lead / Architect

Thiết kế promotion + retention + configuration boundaries.

## 11. Key takeaway

* Same commit chưa chắc same artifact nếu rebuild nhiều lần.
* Build once giúp test evidence có giá trị.
* Artifact digest là deployment identity tốt hơn mutable tag.

# 10. Architecture Decision Record (ADR): lưu lại lý do của quyết định kiến trúc

## 1. What is it?

ADR là tài liệu ngắn ghi lại một architecture decision cùng context, alternatives, decision và consequences.

Nó trả lời:

```text
Vấn đề là gì?
Constraints là gì?
Đã cân nhắc lựa chọn nào?
Tại sao chọn phương án hiện tại?
Hệ quả nào được chấp nhận?
Khi nào cần review lại?
```

## 2. Why does it exist?

Team thường nhớ “đang dùng gì” nhưng quên “tại sao dùng”. Khi rationale biến mất, cùng một debate lặp lại hoặc người mới thay đổi architecture mà không hiểu constraints cũ.

## 3. How does it work?

```text
Question
→ collect constraints/evidence
→ compare options
→ decision
→ ADR accepted
→ implementation
→ later superseded if context changes
```

Thay vì rewrite lịch sử, ADR mới có thể supersede ADR cũ.

## 4. Practical implementation

```markdown
# ADR-014: Use transactional outbox for order events

## Status
Accepted

## Context
DB commit và message publish không atomic với nhau.

## Decision
Persist outbox record trong cùng SQL transaction.

## Alternatives
- Publish directly after SaveChanges
- Distributed transaction

## Consequences
- Eventual delivery
- Additional worker/table/cleanup
- Consumers cần idempotency
```

## 5. Real production scenario

Team muốn chuyển Modular Monolith sang microservices. ADR buộc discussion dựa trên independent deployment, ownership, transaction boundaries, NFRs và operational cost thay vì chỉ nói “microservices scale tốt hơn”.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng architecture debate lặp lại.  
**Evidence** → chỉ có wiki mô tả current state, không có rationale.  
**Hypothesis** → decision knowledge bị mất.  
**Diagnosis** → trace major changes và tìm rationale.  
**Fix** → ADR cho significant decisions.  
**Verification** → người mới có thể giải thích why/alternatives/review trigger từ ADR.

## 7. Common mistakes

* Viết ADR sau khi quyết định chỉ để hợp thức hóa.
* ADR dài như design document lớn.
* Không ghi alternatives.
* Rewrite ADR cũ và mất history.
* Tạo ADR cho mọi tiny coding choice.

## 8. Alternatives

RFC/design doc phù hợp exploration lớn. PR description phù hợp local implementation. ADR phù hợp decision cần sống lâu hơn một PR.

## 9. Trade-offs

### Advantages

* Decision rationale discoverable.
* Giảm repeated debates.
* Hỗ trợ onboarding và architecture evolution.

### Costs / Risks

* Cần discipline duy trì status.
* Quá nhiều ADR nhỏ tạo noise.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết tìm ADR trước khi thay đổi component lớn.

### Middle

Ghi context và consequences.

### Senior

So sánh alternatives bằng evidence và NFRs.

### Technical Lead / Architect

Dùng ADR như lightweight governance, không biến thành bureaucracy.

## 11. Key takeaway

* Architecture cần lưu cả **why**, không chỉ **what**.
* ADR tốt ghi context, alternatives, decision và consequences.
* Khi context đổi, supersede quyết định bằng evidence mới.
