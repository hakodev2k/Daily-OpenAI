## 1. C# / .NET — `ConfigureAwait(false)` không phải performance switch; hãy hiểu `SynchronizationContext` trước khi dùng

### Mental model
Khi `await` một incomplete task, continuation có thể capture execution context phù hợp với môi trường hiện tại. Trong UI frameworks có `SynchronizationContext`, việc quay lại UI thread thường cần thiết. Trong ASP.NET Core hiện đại, request processing không có custom `SynchronizationContext` kiểu ASP.NET cũ, nên `ConfigureAwait(false)` thường không tạo ra thay đổi hành vi đáng kể trong application code.

```csharp
public async Task<OrderDto?> GetAsync(int id, CancellationToken ct)
{
    var order = await repository.FindAsync(id, ct);
    return order is null ? null : Map(order);
}
```

Trong reusable library code, `ConfigureAwait(false)` vẫn có thể hợp lý khi library không cần caller context:

```csharp
var payload = await stream.ReadAsync(buffer, cancellationToken)
    .ConfigureAwait(false);
```

### Tại sao chủ đề này dễ bị dùng sai
Nhiều codebase áp dụng `.ConfigureAwait(false)` cơ học vì kinh nghiệm từ ASP.NET Framework hoặc desktop UI rồi coi nó là optimization bắt buộc. Kết quả là code noise tăng nhưng developer không còn hiểu continuation semantics thực tế.

### Senior-level insight
Phân biệt ba thứ: `SynchronizationContext`, `TaskScheduler` và `ExecutionContext`. `ConfigureAwait(false)` chủ yếu tác động việc capture context phục vụ continuation; nó không có nghĩa toàn bộ execution context như `AsyncLocal` tự động biến mất. Nếu correlation/tenant context dùng `AsyncLocal`, đừng giả định `ConfigureAwait(false)` sẽ loại bỏ nó.

### Trade-off
Library code tránh phụ thuộc caller context giúp composability tốt hơn. Application code nên ưu tiên readability nếu runtime model không cần explicit configuration. Đừng thêm API ceremony nếu không có correctness/performance reason đo được.

### Review checklist
- Code đang chạy trong ASP.NET Core, UI app hay reusable library?
- Continuation có cần thread/context cụ thể không?
- Có đang dùng `ConfigureAwait(false)` vì hiểu runtime hay vì convention cũ?
- Có nhầm nó với suppression của `ExecutionContext` không?

## 2. ASP.NET Core — Middleware ordering là một phần của security và behavior contract

### Problem
ASP.NET Core middleware pipeline chạy theo thứ tự đăng ký ở chiều request và unwind ngược lại ở chiều response. Vì vậy hai middleware đúng riêng lẻ vẫn có thể tạo hệ thống sai nếu đặt sai vị trí.

```csharp
app.UseExceptionHandler("/error");
app.UseHttpsRedirection();
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
```

Authentication phải thiết lập principal trước khi authorization đánh giá policy. Exception handling cần đủ sớm để bao phủ phần pipeline mà ta muốn chuyển lỗi thành response có kiểm soát.

### Production failure
Một custom tenant middleware đọc `User` trước authentication có thể kết luận request anonymous. Một request logging middleware đặt sai chỗ có thể không thấy exception hoặc ghi status code trước khi response hoàn tất. CORS, static files, rate limiting và endpoint routing cũng có ordering semantics riêng.

### Senior-level insight
Review pipeline như một call stack, không như danh sách extension methods. Với mỗi middleware, hỏi:

```text
Nó cần state nào đã tồn tại trước khi chạy?
Nó tạo state nào cho middleware phía sau?
Nó có short-circuit không?
Nó cần quan sát response/exception ở chiều unwind không?
```

### Debugging technique
Khi behavior khó hiểu, thêm temporary structured log trước/sau `await next(context)` trong custom middleware. Điều này giúp thấy request order và response unwind order thay vì suy luận từ source bằng mắt.

### Review checklist
- Authentication trước authorization.
- Middleware phụ thuộc endpoint metadata phải chạy sau routing phù hợp.
- Exception handling bao phủ vùng cần thiết.
- Short-circuit có bỏ qua telemetry/security middleware quan trọng không?
- Integration test pipeline behavior, không chỉ unit test từng middleware.

## 3. EF Core — `DbContext` là Unit of Work ngắn hạn; reuse quá lâu làm Change Tracker trở thành hidden state

### Mental model
`DbContext` được thiết kế cho một unit of work: query/track entities, thay đổi, `SaveChanges`, rồi dispose. Nó không thread-safe và không nên trở thành application-wide object.

```csharp
await using var db = await dbContextFactory.CreateDbContextAsync(ct);
var order = await db.Orders.SingleAsync(x => x.Id == id, ct);
order.MarkPaid();
await db.SaveChangesAsync(ct);
```

### Vì sao long-lived context nguy hiểm
Change Tracker giữ reference tới tracked entities. Context sống quá lâu có thể:

- tăng memory retention;
- trả entity đã tracked thay vì state mới từ database trong một số flow;
- tạo accidental update khi `SaveChanges` commit nhiều thay đổi hơn dự kiến;
- làm concurrency reasoning khó hơn;
- bị dùng đồng thời từ nhiều operation và phát sinh lỗi.

### Background processing
`BackgroundService` có lifetime singleton. Không inject một scoped `DbContext` trực tiếp rồi dùng mãi. Tạo scope hoặc dùng `IDbContextFactory<TContext>` cho từng unit of work.

### Senior-level insight
`DbContext` không chỉ là database connection wrapper. Connection thường được mở/đóng theo operation; thứ đáng chú ý là identity map + change tracking + unit-of-work state. Vì vậy “giữ context để khỏi tạo connection nhiều lần” là mental model sai.

### Trade-off
Context ngắn hạn làm state ownership rõ và giảm tracking accumulation. Context quá ngắn nếu chia một business transaction thành nhiều context không chủ đích lại có thể làm mất atomicity. Boundary phải bám theo business unit of work.

### Review checklist
- Context lifetime có khớp unit of work không?
- Có parallel operation trên cùng context không?
- Background job có tạo scope riêng không?
- Query read-only lớn có tracking không cần thiết không?
- `SaveChanges` có thể commit hidden tracked changes nào khác không?

## 4. SQL — Parameter sniffing không phải lý do để thêm `OPTION (RECOMPILE)` khắp nơi

### Problem framing
Một parameterized query có thể có data distribution rất lệch. Ví dụ tenant nhỏ có 100 orders, tenant lớn có 20 triệu orders. Execution plan tối ưu cho một parameter có thể kém cho parameter khác.

```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE TenantId = @TenantId
  AND Status = @Status
ORDER BY CreatedAt DESC;
```

Nếu optimizer reuse plan được compile từ cardinality rất khác workload hiện tại, latency có thể dao động mạnh.

### Chẩn đoán trước khi sửa
Không nên thấy query chậm rồi kết luận ngay “parameter sniffing”. Hãy kiểm tra:

- actual vs estimated rows;
- plan history/query store;
- data skew;
- index statistics;
- parameter values của fast/slow executions;
- memory grant, join strategy và access path.

### Các hướng xử lý
Tùy engine/version/workload, lựa chọn có thể gồm cải thiện index/statistics, tách query shape cho các workload khác nhau, query hints có chủ đích hoặc recompilation ở điểm thật sự cần. `OPTION (RECOMPILE)` có thể cho plan phù hợp mỗi lần nhưng đổi lại CPU compilation và mất lợi ích plan reuse.

### Senior-level insight
Đây là vấn đề **plan stability vs plan specialization**. Một plan dùng chung rẻ về compilation nhưng có thể không phù hợp cho skew lớn. Một plan chuyên biệt tốt cho từng case nhưng có operational cost khác. Quyết định phải dựa trên execution evidence.

### Review checklist
- Có bằng chứng cùng query hash nhưng latency/plan khác nhau không?
- Statistics có đủ mới không?
- Distribution có skew theo tenant/status/date không?
- Fix có làm CPU compilation tăng mạnh không?
- Có thể tách workload semantically thay vì ép một query phục vụ mọi cardinality không?

## 5. MongoDB — Optimistic concurrency có thể dùng version field + conditional update thay vì distributed lock

### Scenario
Hai worker cùng đọc document version 7 rồi cùng tính state mới. Nếu cả hai `replaceOne({_id})`, writer sau có thể overwrite writer trước.

Thêm version vào predicate:

```javascript
db.orders.updateOne(
  { _id: orderId, version: 7 },
  {
    $set: { status: "Paid" },
    $inc: { version: 1 }
  }
)
```

Nếu `matchedCount == 0`, state đã thay đổi hoặc document không tồn tại. Application phải quyết định reload/reject/recompute.

### Why it matters
Correctness được enforce tại source of truth bằng atomic conditional write. Điều này thường đơn giản và mạnh hơn việc lấy distributed lock chỉ để bảo vệ một document update.

### Senior-level insight
Version check chỉ hữu ích nếu **mọi writer cần bảo vệ invariant đều tham gia protocol**. Một code path update document mà bỏ qua version có thể phá guarantee. Đây là lý do concurrency strategy phải là repository/application convention có test, không phải trick cục bộ.

### Trade-off
Optimistic concurrency phù hợp khi conflict hiếm. Nếu hàng trăm writer tranh cùng document liên tục, retry/recompute có thể tốn kém; lúc đó data model hoặc serialization strategy cần được xem lại.

### Practical checklist
- Predicate chứa `_id` + expected version.
- Update version atomically cùng business change.
- Kiểm tra `matchedCount`.
- Không retry mù quáng nếu command không còn hợp lệ trên state mới.
- Test concurrent writers thực tế.

## 6. REST API Design — `PUT`, `PATCH` và domain command không nên bị chọn chỉ theo CRUD convention

### Mental model
`PUT /users/42` thường biểu diễn replacement/update của resource representation theo contract. `PATCH` biểu diễn partial modification. Nhưng nhiều business operation không phải generic field update:

```http
POST /orders/42/cancel
POST /invoices/42/approve
```

Các operation này có preconditions, authorization và state transition semantics riêng.

### Vì sao generic PATCH dễ nguy hiểm
Một request kiểu:

```json
{ "status": "Cancelled" }
```

có thể bypass domain rules: order đã shipped có được cancel không, ai có quyền cancel, có cần refund/reservation release không? Nếu transport layer map field trực tiếp vào entity, business transition bị hạ thành property assignment.

### Senior-level insight
HTTP resource design và domain model không cần đối đầu nhau. Resource-oriented API vẫn có thể expose subresource/action semantics rõ ràng khi operation mang business meaning. Điều quan trọng là contract nói được intent và cho phép enforce invariant ở một nơi.

### Trade-off
Generic CRUD API ít endpoint hơn nhưng business semantics dễ mơ hồ. Explicit commands tăng surface area nhưng giúp authorization, idempotency, audit và validation rõ hơn.

### Review checklist
- Operation là representation update hay business command?
- State transition có invariant riêng không?
- Authorization có phụ thuộc operation không?
- Retry/idempotency semantics có rõ không?
- Audit log có cần biết intent thay vì chỉ biết field changed không?

## 7. Security — Secret rotation chỉ thực sự an toàn khi application chịu được khoảng thời gian hai credential cùng hợp lệ

### Problem
Nhiều hệ thống nói “secret có thể rotate” nhưng deployment vẫn giả định chỉ tồn tại một credential. Khi secret cũ bị revoke trước khi mọi instance nhận secret mới, request bắt đầu fail. Nếu secret mới được deploy trước nhưng dependency chưa chấp nhận nó, lỗi cũng xảy ra.

### Rotation model
Một flow zero/low-downtime thường cần overlap:

```text
1. Tạo credential mới.
2. Dependency chấp nhận credential mới và cũ.
3. Roll application sang credential mới.
4. Xác minh toàn bộ instances/workers đã chuyển.
5. Revoke credential cũ.
```

### Application concern
Configuration reload không phải lúc nào cũng đồng nghĩa dependency client tự rebuild. Nếu credential được capture khi singleton client được tạo, secret provider cập nhật giá trị nhưng connection/client cũ vẫn có thể dùng credential cũ.

### Senior-level insight
Secret rotation là distributed rollout problem. Hãy review credential consumer lifetime, cache, connection pooling, deployment duration và rollback path. “Secret nằm trong vault” chỉ giải quyết storage/distribution, không tự giải quyết runtime adoption.

### Failure testing
- Rotate khi application đang có traffic.
- Giữ một instance cũ lâu hơn rollout bình thường.
- Test worker/background service, không chỉ web request path.
- Theo dõi authentication failures theo credential generation nếu platform hỗ trợ.
- Có emergency revoke procedure cho compromised secret.

## 8. Architecture — Transaction boundary nên đi theo invariant, không đi theo repository method

### Anti-pattern
Một application service gọi nhiều repository, mỗi repository tự `SaveChanges`:

```text
CreateOrder()  -> commit
ReserveStock() -> commit
WriteAudit()   -> fail
```

Nếu business requirement là order và reservation phải cùng thành công hoặc cùng thất bại trong một database, việc commit theo repository đã chia sai transaction boundary.

### Better mental model
Repository encapsulates persistence access; transaction/unit of work quyết định atomic boundary. Với cùng relational database, application layer có thể orchestration nhiều aggregate/repository trong một transaction nếu invariant yêu cầu.

### Khi boundary vượt nhiều systems
Nếu order nằm SQL nhưng inventory là service khác, ACID transaction chung thường không còn phù hợp. Lúc đó phải thiết kế workflow với idempotency, durable messaging, compensation hoặc state machine thay vì giả vờ nhiều network call là một transaction.

### Senior-level insight
Hỏi **“điều gì tuyệt đối không được quan sát ở trạng thái nửa vời?”**. Câu trả lời giúp tìm invariant và transaction boundary. Đừng bắt đầu từ “mỗi repository có `SaveAsync`” rồi để persistence abstraction quyết định business consistency.

### Trade-off
Transaction lớn tăng lock duration/contention. Transaction quá nhỏ tạo partial state. Boundary đúng là tối thiểu nhưng đủ để bảo vệ invariant cần strong consistency.

### Review checklist
- Ai gọi `SaveChanges` và tại sao ở đó?
- Hai writes có cần atomicity thật không?
- Transaction có chứa network I/O không?
- Failure giữa các bước để lại state nào?
- Nếu distributed, recovery/compensation có durable không?

## 9. Testing / QA — Contract tests bảo vệ integration boundary tốt hơn việc mock lại assumption của chính consumer

### Problem
Consumer mock một external API như sau:

```csharp
mock.Setup(x => x.GetProductAsync("A1", It.IsAny<CancellationToken>()))
    .ReturnsAsync(new Product("A1", "Keyboard"));
```

Test này chỉ chứng minh code chạy với **mock mà chính team đã tưởng tượng**. Nó không chứng minh provider thật vẫn trả field, status code hoặc semantics tương thích.

### Contract-oriented testing
Ở HTTP boundary, contract có thể kiểm tra schema, required fields, status semantics, enum evolution và compatibility rules. Consumer-driven contract còn có thể biểu diễn những interaction consumer thực sự phụ thuộc để provider xác minh trước khi release.

### Không thay thế integration/E2E
Contract test không chứng minh DNS, TLS, auth configuration, network policy hoặc production data behavior. Nó thu hẹp một failure class: **interface compatibility**. Integration smoke test vẫn cần cho wiring thật.

### Senior-level insight
Test layer nên bám theo loại uncertainty:

```text
Domain logic uncertainty       -> unit/property tests
Persistence/framework behavior -> integration tests
Service compatibility          -> contract tests
Critical user journey          -> E2E tests
```

Một test suite tốt không tối đa số test; nó phân bổ confidence đúng boundary.

### Review checklist
- Mock có copy assumption từ production code không?
- Provider thay đổi enum/nullable field có bị phát hiện không?
- Contract có versioning/backward compatibility rule không?
- Có test negative/error response không?
- E2E chỉ giữ cho critical journeys thay vì duplicate mọi case không?

## 10. Performance / Debugging — Thread Pool starvation khác CPU saturation và cần cách chẩn đoán khác

### Symptom
Service có latency tăng mạnh nhưng CPU chỉ 30–40%. Request queue tăng, task completion chậm và throughput tụt. Một nguyên nhân có thể là Thread Pool starvation do nhiều worker thread bị block.

Các pattern đáng nghi:

```csharp
// sync-over-async
var result = SomeAsync().Result;

// blocking wait
SomeAsync().Wait();

// I/O synchronous trên hot request path
var text = File.ReadAllText(path);
```

### Vì sao CPU có thể thấp
Blocked thread không tiêu thụ CPU đáng kể nhưng vẫn chiếm worker. Thread Pool có thể inject thêm threads, song quá trình thích nghi không tức thời; under burst load, queueing latency có thể tăng trước khi pool bắt kịp.

### Phân biệt với CPU saturation
CPU saturation thường cần tìm hot code, allocation/GC pressure, expensive serialization/query computation. Starvation cần tìm blocking stacks, sync-over-async, lock contention hoặc synchronous I/O. Hai vấn đề có thể cùng tồn tại nhưng remediation khác nhau.

### Diagnostic workflow
Trong .NET production troubleshooting, hãy correlate:

- request rate và latency;
- CPU;
- Thread Pool thread count/queue length;
- GC metrics;
- lock/contention data;
- traces/stacks tại thời điểm incident.

Đừng chỉ thấy thread count cao rồi kết luận starvation; thread count tăng có thể là **response** của runtime với blocking.

### Senior-level insight
Async không tự làm hệ thống scalable nếu call graph cuối cùng vẫn block. Một `.Result` ở shared library có thể phá lợi ích async của toàn endpoint. Review từ request boundary xuống dependency boundary, đặc biệt ở adapters cũ.

### Practical checklist
- Tìm `.Result`, `.Wait()`, synchronous I/O trên hot path.
- Không dùng `Task.Run` để che synchronous server I/O như một fix mặc định.
- Capture runtime counters + trace/stacks dưới load.
- Load test với concurrency thực tế, không chỉ single-user benchmark.
- Sửa blocking root cause trước khi tăng Thread Pool minimum như một workaround.
