# 1. .NET Dependency Injection lifetimes và captive dependency: vì sao code resolve được vẫn có thể sai lifetime, giữ state quá lâu hoặc dùng `DbContext` sai cách

## 1. What is it?

ASP.NET Core DI container quản lý vòng đời của object theo ba lifetime phổ biến:

```text
Transient -> tạo instance mỗi lần resolve
Scoped    -> một instance trong một scope, thường là một HTTP request
Singleton -> một instance cho toàn application lifetime
```

Mental model quan trọng: lifetime không chỉ là tối ưu allocation. Nó mô tả **state ownership và thời gian object được phép sống**.

`Captive dependency` xảy ra khi object sống lâu giữ reference tới dependency đáng lẽ phải sống ngắn hơn.

```text
Singleton
   |
   +--> Scoped service
           |
           +--> DbContext
```

Graph này nguy hiểm vì singleton có thể giữ scoped state vượt qua request boundary.

## 2. Why does it exist?

Object khác nhau có lifecycle khác nhau:

- stateless formatter có thể transient;
- request context thường scoped;
- shared configuration cache có thể singleton;
- `DbContext` thường scoped vì giữ change tracker và unit-of-work state.

Nếu mọi object đều singleton, request-specific state dễ bị dùng chéo giữa users. Nếu mọi object đều transient, resource ownership và expensive initialization có thể trở nên khó kiểm soát.

Lifetime là cách container giúp application biểu diễn lifecycle rõ ràng.

## 3. How does it work?

ASP.NET Core tạo root service provider khi startup. Với mỗi HTTP request, framework tạo một child scope.

```text
Root Provider
  |- Singleton A
  |- Singleton B
  |
  +-- Request Scope #1
  |     |- Scoped C
  |     `- DbContext #1
  |
  +-- Request Scope #2
        |- Scoped C
        `- DbContext #2
```

Transient được tạo mỗi lần resolve nhưng nếu singleton giữ transient đó trong field, transient thực tế cũng sống lâu như singleton.

Vì vậy effective lifetime có thể dài hơn registration lifetime.

## 4. Practical implementation

Đăng ký điển hình:

```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString));

builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddSingleton<ISystemClock, SystemClock>();
builder.Services.AddTransient<IEmailFormatter, EmailFormatter>();
```

Sai:

```csharp
public sealed class ReportCache
{
    private readonly AppDbContext _db;

    public ReportCache(AppDbContext db)
    {
        _db = db;
    }
}

builder.Services.AddSingleton<ReportCache>();
```

Nếu background singleton cần dùng scoped service, tạo scope rõ ràng:

```csharp
public sealed class ReportWorker(
    IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await using var scope = scopeFactory.CreateAsyncScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            await RunBatchAsync(db, ct);
            await Task.Delay(TimeSpan.FromMinutes(1), ct);
        }
    }
}
```

Scope nên gắn với một logical unit of work, không tạo một scope sống suốt process.

## 5. Real production scenario

Một singleton background scheduler inject trực tiếp repository scoped dùng `DbContext`. Ở môi trường single-instance, lỗi có thể chưa rõ. Khi worker chạy lâu:

- change tracker giữ ngày càng nhiều entities;
- stale tracked state xuất hiện;
- operation concurrent có thể truy cập cùng `DbContext`;
- memory tăng và exception kiểu “A second operation was started on this context” xuất hiện.

Root cause không nằm ở EF query, mà ở lifetime boundary.

## 6. Failure scenario & troubleshooting

**Symptom**
→ dữ liệu stale, memory tăng, `DbContext` concurrency exception hoặc request state bị dùng chéo.

**Evidence**
→ service graph có singleton giữ scoped dependency; dump cho thấy scoped object sống lâu bất thường.

**Hypothesis**
→ captive dependency làm effective lifetime sai.

**Diagnosis**
→ kiểm tra registrations, constructor graph, background services và scope creation.

**Fix**
→ align lifetime theo ownership; singleton chỉ resolve scoped dependency bên trong explicit scope khi thật sự cần.

**Verification**
→ load test nhiều requests/batches, theo dõi object lifetime, memory và DB behavior.

## 7. Common mistakes

- Nghĩ `Transient` luôn được dispose ngay sau khi method kết thúc.
- Inject `DbContext` vào singleton/background service.
- Tạo `IServiceScope` một lần rồi giữ suốt lifetime worker.
- Đưa mutable per-user state vào singleton cache/service.
- Dùng service locator ở mọi nơi để “né” lifetime issue.
- Thay mọi registration thành scoped mà không hiểu ownership.

## 8. Alternatives

- Explicit object construction khi dependency graph nhỏ.
- Factory như `IDbContextFactory<TContext>` cho scenario tạo context ngoài request scope.
- Scoped application service cho request-driven unit of work.

Không cần abstraction factory nếu standard request scope đã đáp ứng đúng lifecycle.

## 9. Trade-offs

### Advantages

- Lifecycle và disposal được quản lý tập trung.
- Scoped unit of work phù hợp HTTP request.
- Dễ thay implementation và test dependency boundary.

### Costs / Risks

- Lifetime bug có thể compile và startup bình thường.
- Dependency graph lớn làm ownership khó nhìn thấy.
- Lạm dụng DI biến simple object creation thành hidden framework behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác nhau giữa transient, scoped và singleton.

### Middle

Biết chọn lifetime cho application service, `DbContext`, cache và background worker; biết tạo explicit scope đúng lúc.

### Senior

Debug captive dependency, disposal, thread safety và stale state theo object graph.

### Technical Lead / Architect

Đặt convention lifetime cho toàn codebase, giới hạn singleton mutable state và quyết định nơi factory/scope boundary thực sự cần thiết.

## 11. Key takeaway

- DI lifetime là state ownership, không chỉ object allocation.
- Dependency không nên sống lâu hơn lifecycle logic mà nó đại diện.
- `DbContext` và request-specific state cần boundary rõ ràng.

# 2. ASP.NET Core API Versioning và backward compatibility: tiến hóa contract mà không buộc toàn bộ clients nâng cấp đồng thời

## 1. What is it?

API versioning là cơ chế cho phép nhiều contract versions tồn tại trong một giai đoạn để clients cũ và mới không phải nâng cấp đồng thời.

Mental model:

```text
Mobile v1 ----> API v1
Web v2 ------> API v2
Partner v1 --> API v1
```

Versioning không phải chỉ thêm `/v2/` vào URL. Vấn đề cốt lõi là **contract evolution**: request/response shape, semantics, validation và error behavior thay đổi thế nào mà không phá clients.

## 2. Why does it exist?

Server deploy trong vài phút, nhưng mobile app, partner integration hoặc desktop client có thể mất tuần/tháng mới nâng cấp.

Nếu backend đổi:

```json
{ "name": "A" }
```

thành:

```json
{ "displayName": "A" }
```

mà client cũ phụ thuộc `name`, deployment backend có thể trở thành production outage dù server hoàn toàn healthy.

## 3. How does it work?

Có nhiều versioning strategy:

```text
URL:       /api/v2/orders
Query:     /api/orders?api-version=2
Header:    X-Api-Version: 2
MediaType: application/vnd.company.order.v2+json
```

Điểm quan trọng hơn location là routing và contract ownership rõ ràng.

Backward-compatible changes thường gồm:

- thêm optional response field;
- thêm optional request field với default rõ;
- thêm endpoint mới.

Breaking changes thường gồm:

- xóa/đổi tên field;
- đổi meaning của field;
- optional thành required;
- đổi status code/error contract khiến client logic khác.

## 4. Practical implementation

Ví dụ versioned controllers:

```csharp
[ApiController]
[ApiVersion("1.0")]
[Route("api/v{version:apiVersion}/orders")]
public sealed class OrdersV1Controller : ControllerBase
{
    [HttpGet("{id:guid}")]
    public ActionResult<OrderV1> Get(Guid id) => Ok(...);
}

[ApiController]
[ApiVersion("2.0")]
[Route("api/v{version:apiVersion}/orders")]
public sealed class OrdersV2Controller : ControllerBase
{
    [HttpGet("{id:guid}")]
    public ActionResult<OrderV2> Get(Guid id) => Ok(...);
}
```

Không nên duplicate toàn business logic. Version-specific mapping và HTTP contract nên tách khỏi shared application/domain behavior khi semantics business vẫn giống nhau.

## 5. Real production scenario

Partner API v1 trả `decimal Total`. Version mới cần thêm currency và đổi sang Money representation.

Thay vì âm thầm đổi JSON shape, hệ thống giữ v1 trong deprecation window và đưa v2:

```json
{
  "total": {
    "amount": 120.50,
    "currency": "USD"
  }
}
```

Telemetry theo version giúp biết partner nào vẫn dùng v1 trước khi sunset.

## 6. Failure scenario & troubleshooting

**Symptom**
→ deployment backend thành công nhưng một nhóm clients bắt đầu deserialize fail hoặc gửi request 400.

**Evidence**
→ lỗi tập trung vào client/app version cũ; schema diff cho thấy field became required/renamed.

**Hypothesis**
→ breaking contract change được release trong same API version.

**Diagnosis**
→ so sánh OpenAPI/schema cũ mới, replay request cũ, kiểm tra client telemetry.

**Fix**
→ restore compatibility hoặc phát hành version mới; thêm contract regression test.

**Verification**
→ chạy test suite cho v1/v2 và theo dõi error rate theo API version.

## 7. Common mistakes

- Version mọi thay đổi dù thực tế backward compatible.
- Tạo v2 controller rồi copy toàn service/domain logic.
- Xóa v1 chỉ vì traffic thấp mà không biết owner của clients.
- Nghĩ thêm field luôn an toàn dù client dùng strict deserializer.
- Không version error contract.
- Không có deprecation/sunset policy.

## 8. Alternatives

- Backward-compatible evolution trong cùng version khi thay đổi additive.
- Feature negotiation cho capability cụ thể.
- Separate endpoint/resource khi behavior mới thực chất là use case khác, không phải “version mới”.

## 9. Trade-offs

### Advantages

- Giảm coupling giữa deployment cadence của server và clients.
- Cho migration window rõ ràng.

### Costs / Risks

- Nhiều contracts phải test và support.
- Mapping/version-specific code tăng maintenance cost.
- Version tồn tại vĩnh viễn nếu không có retirement discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu API contract là thứ clients compile/runtime phụ thuộc.

### Middle

Biết implement version routing, DTO mapping và regression tests.

### Senior

Phân biệt additive vs breaking change, thiết kế deprecation và compatibility telemetry.

### Technical Lead / Architect

Quyết định versioning strategy toàn platform, support window, sunset ownership và contract governance.

## 11. Key takeaway

- API versioning giải quyết independent deployment, không chỉ URL naming.
- Ưu tiên backward-compatible evolution khi có thể.
- Breaking change cần version mới, telemetry và migration plan.

# 3. SQL keyset pagination: tránh `OFFSET` càng đi sâu càng chậm bằng continuation key ổn định và index phù hợp

## 1. What is it?

Keyset pagination lấy page tiếp theo dựa trên giá trị sort cuối cùng của page trước thay vì bỏ qua N rows bằng `OFFSET`.

Offset pagination:

```sql
ORDER BY CreatedAt DESC
OFFSET 200000 ROWS FETCH NEXT 50 ROWS ONLY;
```

Keyset pagination:

```sql
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC
FETCH NEXT 50 ROWS ONLY;
```

## 2. Why does it exist?

`OFFSET` dễ dùng nhưng database vẫn phải locate/scan qua nhiều rows trước khi bỏ chúng đi. Page 2 có thể nhanh, page 10,000 có thể rất chậm.

Ngoài performance, offset còn dễ tạo duplicate/missing rows khi data được insert/delete giữa hai requests.

Keyset dùng ordered boundary cụ thể nên ổn định hơn cho feed/history lớn.

## 3. How does it work?

Giả sử index:

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON Orders(CreatedAt DESC, Id DESC);
```

Page đầu:

```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
ORDER BY CreatedAt DESC, Id DESC;
```

Client nhận continuation token chứa `(CreatedAt, Id)` cuối page.

Page tiếp:

```text
seek from last tuple
-> read next 50 ordered rows
```

Tiebreaker `Id` cần thiết vì `CreatedAt` có thể trùng.

## 4. Practical implementation

EF Core:

```csharp
var query = db.Orders.AsNoTracking();

if (cursor is not null)
{
    query = query.Where(x =>
        x.CreatedAt < cursor.CreatedAt ||
        (x.CreatedAt == cursor.CreatedAt && x.Id.CompareTo(cursor.Id) < 0));
}

var items = await query
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id)
    .Take(51)
    .Select(x => new OrderListItem(x.Id, x.CreatedAt, x.Total))
    .ToListAsync(ct);
```

Lấy 51 items để biết `HasMore`, trả 50 và encode cursor opaque cho client.

## 5. Real production scenario

Audit log có 80 triệu rows. UI chủ yếu cần “next page”, không cần nhảy trực tiếp tới page 937.

Offset query tăng từ 50 ms ở đầu dataset lên vài giây ở deep page. Keyset pagination với composite index giữ latency ổn định hơn vì query seek từ boundary gần vị trí cần đọc.

## 6. Failure scenario & troubleshooting

**Symptom**
→ duplicate/missing items hoặc pagination sai khi nhiều rows cùng timestamp.

**Evidence**
→ sort chỉ theo `CreatedAt`, không có unique tiebreaker.

**Hypothesis**
→ ordering không total/deterministic.

**Diagnosis**
→ tìm rows có cùng sort value và replay cursor.

**Fix**
→ thêm stable unique tiebreaker vào cả `ORDER BY`, predicate và index.

**Verification**
→ concurrent insert test xác nhận không skip/duplicate theo contract mong muốn.

## 7. Common mistakes

- Dùng keyset nhưng vẫn cho user nhảy arbitrary page number.
- Sort theo column không stable.
- Không có composite index cùng thứ tự.
- Encode cursor chứa raw internal data dễ bị sửa mà không validate.
- Dùng `Id > lastId` dù sort chính là field khác.

## 8. Alternatives

- Offset pagination: tốt cho dataset nhỏ hoặc UI cần page number/random access.
- Search engine `search_after`: khái niệm tương tự keyset cho Elasticsearch.
- Snapshot/export job: phù hợp reporting cần consistency toàn tập dữ liệu.

## 9. Trade-offs

### Advantages

- Deep-page performance ổn định hơn.
- Hợp feed, audit log, transaction history.
- Ít nhạy hơn với concurrent inserts so với offset.

### Costs / Risks

- Không nhảy page tùy ý dễ dàng.
- Cursor format và ordering phức tạp hơn.
- Sort requirements ảnh hưởng index design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu offset bỏ qua rows, keyset tiếp tục từ last known row.

### Middle

Implement cursor với unique tiebreaker và matching index.

### Senior

Đọc plan/I/O, đánh giá consistency dưới concurrent writes và bảo vệ cursor contract.

### Technical Lead / Architect

Chọn pagination model theo UX + data scale, không áp một pattern cho mọi endpoint.

## 11. Key takeaway

- Keyset pagination phù hợp large ordered datasets và “next page” navigation.
- Ordering phải deterministic.
- Cursor predicate và index phải được thiết kế cùng nhau.

# 4. Azure Cosmos DB partition key và hot partition: throughput cao hay thấp thường được quyết định từ data distribution trước khi tối ưu query

## 1. What is it?

Cosmos DB phân phối data theo logical partition key. Các logical partitions được map lên physical partitions để scale storage và throughput.

Mental model:

```text
Tenant A ---> partition-key hash ----\
Tenant B ---> partition-key hash -----+--> physical partitions
Tenant C ---> partition-key hash ----/
```

Partition key ảnh hưởng trực tiếp đến:

- data locality;
- query fan-out;
- throughput distribution;
- hot partition risk;
- transaction scope.

## 2. Why does it exist?

Một machine không thể scale storage/throughput vô hạn. Distributed database phải shard data.

Nếu partition key phân phối traffic không đều, tổng RU/s account có thể còn dư nhưng một physical partition vẫn bị throttled.

Vì vậy “tăng RU” không luôn giải quyết được root cause.

## 3. How does it work?

Request có partition key cụ thể thường route tới đúng partition.

```text
GET item + PartitionKey=tenant-42
       -> targeted partition
```

Query không có partition constraint có thể fan-out:

```text
Query
  -> partition 1
  -> partition 2
  -> partition 3
  -> merge results
```

Một key như `/country` có cardinality thấp dễ tạo skew. Một key như `/tenantId` thường tốt hơn nếu tenant distribution phù hợp, nhưng một “mega tenant” vẫn có thể trở thành hotspot.

## 4. Practical implementation

Model:

```json
{
  "id": "order-123",
  "tenantId": "tenant-42",
  "customerId": "customer-9",
  "status": "Open"
}
```

Container chọn `/tenantId` khi phần lớn operations scoped theo tenant.

SDK call nên truyền partition key:

```csharp
var response = await container.ReadItemAsync<Order>(
    id: orderId,
    partitionKey: new PartitionKey(tenantId),
    cancellationToken: ct);
```

Khi workload không thể phân phối tốt bằng một key đơn giản, hierarchical partition keys hoặc data model khác có thể phù hợp hơn tùy scenario.

## 5. Real production scenario

SaaS có 20,000 tenants, nhưng một enterprise tenant phát sinh 45% writes vào giờ cao điểm. `/tenantId` nhìn chung hợp lý nhưng enterprise tenant tạo hot partition.

Giải pháp có thể là composite/hierarchical partitioning theo tenant + bucket phù hợp access pattern, thay vì chỉ tăng provisioned throughput vô hạn.

## 6. Failure scenario & troubleshooting

**Symptom**
→ nhiều HTTP 429 dù tổng throughput metrics trông chưa bão hòa.

**Evidence**
→ throttling tập trung vào một partition key range; một tenant/key có request rate vượt trội.

**Hypothesis**
→ hot partition.

**Diagnosis**
→ xem normalized RU consumption, partition key metrics, request distribution và query fan-out.

**Fix**
→ điều chỉnh access pattern/data distribution, bucket hóa khi hợp lý, hoặc isolate heavy tenant/workload.

**Verification**
→ load test với realistic skew, không chỉ uniform synthetic traffic.

## 7. Common mistakes

- Chọn partition key theo field “có vẻ business-important” thay vì access pattern.
- Chọn key cardinality thấp.
- Tin rằng autoscale tự sửa hot partition.
- Query cross-partition rồi bất ngờ vì RU cao.
- Thiết kế partition key sau khi production data đã rất lớn.
- Dùng Cosmos DB như relational database rồi join/filter fan-out liên tục.

## 8. Alternatives

- SQL Server/PostgreSQL nếu relational transaction/query là workload chính.
- MongoDB với shard strategy khác nếu operational ecosystem phù hợp.
- Separate containers theo workload/tenant tier khi isolation quan trọng hơn simplicity.

## 9. Trade-offs

### Advantages

- Scale distribution tốt khi partition key phù hợp.
- Low-latency targeted operations.
- Transactional batch trong logical partition.

### Costs / Risks

- Partition decision khó đổi sau này.
- Skew/hot key có thể giới hạn throughput.
- Cross-partition query tăng RU và latency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định data nằm và được route thế nào.

### Middle

Biết truyền partition key, đo RU và tránh cross-partition query không cần thiết.

### Senior

Phân tích traffic skew, hot partitions, consistency và transaction boundary.

### Technical Lead / Architect

Quyết định partition strategy từ business access patterns, growth model và tenant isolation trước khi schema được khóa bởi production scale.

## 11. Key takeaway

- Cosmos DB performance bắt đầu từ partition design.
- Tổng RU còn dư không có nghĩa mọi partition đều khỏe.
- Thiết kế với traffic skew thực tế, không chỉ cardinality lý thuyết.

# 5. Anti-Corruption Layer cho third-party integration: ngăn external model, lỗi và lifecycle lan thẳng vào domain của hệ thống

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary dịch giữa external model và internal domain model.

```text
Domain
  |
  v
Internal Port
  |
  v
ACL / Adapter
  |
  v
Third-party API
```

Tên “anti-corruption” không có nghĩa external system xấu. Nó nghĩa model bên ngoài không nên tự động định nghĩa terminology, state machine và constraints bên trong domain của ta.

## 2. Why does it exist?

External CRM có thể gọi customer là `Account`, status dùng code `A`, `S`, `X`, error trả 200 với field `success=false`.

Nếu application đưa những chi tiết đó vào toàn domain:

```text
CRM terminology
-> service layer
-> entities
-> UI
-> reporting
```

thì đổi vendor hoặc contract external trở thành refactor toàn hệ thống.

## 3. How does it work?

Internal application phụ thuộc interface theo business language của mình:

```csharp
public interface ICustomerCreditGateway
{
    Task<CreditDecision> EvaluateAsync(
        CustomerId customerId,
        Money amount,
        CancellationToken ct);
}
```

Adapter gọi vendor:

```text
CustomerId -> vendor account code
Money      -> vendor request DTO
vendor X   -> internal Declined
vendor 429 -> transient dependency failure
```

Mapping tập trung ở integration boundary.

## 4. Practical implementation

```csharp
public sealed class VendorCreditGateway(HttpClient httpClient)
    : ICustomerCreditGateway
{
    public async Task<CreditDecision> EvaluateAsync(
        CustomerId customerId,
        Money amount,
        CancellationToken ct)
    {
        var request = VendorCreditRequest.From(customerId, amount);
        using var response = await httpClient.PostAsJsonAsync(
            "/credit/check", request, ct);

        if (response.StatusCode == HttpStatusCode.TooManyRequests)
            throw new TransientCreditDependencyException();

        response.EnsureSuccessStatusCode();

        var dto = await response.Content
            .ReadFromJsonAsync<VendorCreditResponse>(cancellationToken: ct)
            ?? throw new InvalidOperationException("Missing vendor response");

        return dto.Status switch
        {
            "A" => CreditDecision.Approved(),
            "D" => CreditDecision.Declined(dto.Reason),
            _ => throw new InvalidOperationException("Unknown vendor status")
        };
    }
}
```

Domain không cần biết status code `A`/`D`.

## 5. Real production scenario

E-commerce tích hợp review vendor. Vendor đổi pagination, rating scale từ 0–100 sang 1–5 và đổi auth mechanism.

Nếu UI/domain dùng trực tiếp vendor DTO, thay đổi lan rộng. Với ACL, chỉ adapter + mapping + integration tests thay đổi, internal `ProductRating` contract có thể giữ ổn định.

## 6. Failure scenario & troubleshooting

**Symptom**
→ vendor deploy contract mới làm business service bắt đầu throw parsing errors khắp nơi.

**Evidence**
→ external DTO được dùng trực tiếp trong application/domain layers.

**Hypothesis**
→ integration boundary bị xuyên thủng.

**Diagnosis**
→ tìm type references từ vendor SDK/DTO đi sâu vào domain.

**Fix**
→ tạo internal port + adapter, normalize error/status/data shape tại boundary.

**Verification**
→ contract tests của adapter fail khi vendor schema đổi, domain tests không cần vendor types.

## 7. Common mistakes

- Tạo ACL nhưng chỉ rename DTO 1:1, không normalize semantics.
- Bọc vendor SDK bằng interface y hệt SDK nên coupling vẫn còn.
- Nuốt lỗi external và trả default business value sai.
- Đưa retry/caching vào domain entity.
- Overengineer ACL cho một internal stable library không có meaningful boundary.

## 8. Alternatives

- Direct integration khi API nhỏ, stable và coupling chấp nhận được.
- BFF/integration service riêng nếu nhiều products dùng cùng vendor và cần ownership độc lập.
- Event ingestion nếu vendor cung cấp event/webhook phù hợp hơn synchronous dependency.

## 9. Trade-offs

### Advantages

- Giảm vendor coupling.
- Internal language ổn định hơn.
- Dễ test failure mapping và migration vendor.

### Costs / Risks

- Thêm mapping code.
- Có thể che mất capability vendor nếu internal abstraction quá nghèo.
- Cần owner cập nhật adapter khi contract external thay đổi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu không nên dùng external DTO như domain model mặc định.

### Middle

Implement adapter, mapping và error normalization.

### Senior

Thiết kế boundary chống schema drift, latency, retry và partial failure.

### Technical Lead / Architect

Quyết định integration nào đáng có ACL riêng, service riêng hoặc vẫn direct để tránh abstraction thừa.

## 11. Key takeaway

- External contract không nên trở thành internal domain vocabulary mặc định.
- ACL bảo vệ semantic boundary, không chỉ đổi tên DTO.
- Abstraction chỉ đáng có khi giảm coupling thực tế.

# 6. Timeout, Retry và Circuit Breaker cho `HttpClient`: resilience chỉ hiệu quả khi retry budget, idempotency và failure classification được thiết kế đúng

## 1. What is it?

Ba mechanism giải quyết ba vấn đề khác nhau:

```text
Timeout         -> giới hạn thời gian chờ một attempt
Retry           -> thử lại một số transient failures
Circuit Breaker -> ngừng gọi dependency đang lỗi để tránh tiếp tục gây áp lực
```

Chúng không phải một “resilience package” cứ bật mặc định là hệ thống an toàn hơn.

## 2. Why does it exist?

Remote dependency chắc chắn có lúc:

- latency tăng;
- reset connection;
- trả 429/503;
- deploy lỗi;
- unavailable một phần.

Không timeout, request có thể treo quá lâu. Không retry, transient glitch làm request fail không cần thiết. Retry vô hạn lại gây retry storm.

Circuit breaker tạo breathing room khi failure liên tục.

## 3. How does it work?

Một request có total latency budget 2 giây:

```text
Attempt 1: timeout 500 ms
Backoff:   100 ms
Attempt 2: timeout 500 ms
Backoff:   200 ms
Attempt 3: timeout 500 ms
------------------------
~1.8s + overhead
```

Nếu upstream timeout chỉ 1 giây nhưng downstream policy có thể retry 3 x 1 giây, upstream đã bỏ cuộc trước khi downstream logic kết thúc.

Circuit breaker quan sát failure rate/consecutive failures và chuyển state:

```text
Closed -> Open -> Half-Open -> Closed
```

## 4. Practical implementation

Với modern .NET resilience handlers:

```csharp
builder.Services
    .AddHttpClient<InventoryClient>(client =>
    {
        client.BaseAddress = new Uri(inventoryBaseUrl);
    })
    .AddStandardResilienceHandler(options =>
    {
        options.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(2);
        options.AttemptTimeout.Timeout = TimeSpan.FromMilliseconds(700);
        options.Retry.MaxRetryAttempts = 2;
    });
```

Policy thực tế phải được điều chỉnh theo downstream SLA, method semantics và workload.

Không retry `POST /payments` mù quáng nếu endpoint không hỗ trợ idempotency key.

## 5. Real production scenario

Product page gọi review API. Review provider bắt đầu trả 503.

Nếu mỗi web request retry 5 lần, traffic tới provider có thể tăng gấp 5 đúng lúc provider đang yếu. Thread/connections của application cũng bị giữ lâu hơn, làm failure lan sang catalog endpoint vốn không lỗi.

Better design:

- short timeout;
- bounded retry có jitter;
- circuit breaker;
- fallback “reviews unavailable” nếu business chấp nhận.

## 6. Failure scenario & troubleshooting

**Symptom**
→ downstream outage làm outbound request count tăng mạnh thay vì giảm.

**Evidence**
→ dependency calls/request tăng 4–5 lần; retry logs dày; queue/thread/connections tăng.

**Hypothesis**
→ retry amplification.

**Diagnosis**
→ trace retries theo request, timeout budgets, status classification và call graph nhiều layers.

**Fix**
→ chỉ retry transient errors, giới hạn attempts, thêm jitter, tránh nested retries ở nhiều layers, dùng breaker/bulkhead/fallback khi phù hợp.

**Verification**
→ chaos test dependency 503/timeout và đo total outbound attempts + p99.

## 7. Common mistakes

- Retry 400/401/403 như transient failure.
- Retry unsafe side effect không có idempotency.
- Mỗi layer đều retry riêng gây exponential amplification.
- Timeout bằng nhau cho mọi dependency.
- Circuit breaker mở nhưng fallback vẫn gọi cùng dependency theo đường khác.
- Chỉ log final failure, mất visibility từng attempt.

## 8. Alternatives

- Queue/background processing khi operation không cần synchronous response.
- Cached/stale response khi freshness có thể relax.
- Fail fast nếu dependency optional và UX có degradation path.

## 9. Trade-offs

### Advantages

- Giảm impact transient failure.
- Bảo vệ latency budget và dependency capacity.
- Circuit breaker giảm futile calls trong outage.

### Costs / Risks

- Sai policy có thể tăng load và latency.
- Retry làm duplicate side effect nếu semantics không idempotent.
- Fallback có thể che outage nếu monitoring kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout, retry, circuit breaker giải quyết vấn đề khác nhau.

### Middle

Config `HttpClient` resilience và propagate cancellation.

### Senior

Thiết kế retry budget, idempotency, jitter, error classification và failure telemetry.

### Technical Lead / Architect

Quyết định synchronous dependency có nên tồn tại trên critical path hay cần cache/queue/degradation boundary.

## 11. Key takeaway

- Retry là load multiplier nếu dùng sai.
- Total latency budget phải tính cả attempts và backoff.
- Resilience bắt đầu từ failure semantics, không từ bật một library policy.

# 7. Azure Blob Storage SAS: trao quyền truy cập giới hạn mà không phát tán storage account key

## 1. What is it?

Shared Access Signature (SAS) là token cho phép truy cập giới hạn tới Azure Storage resource theo:

- resource scope;
- permissions;
- start/expiry time;
- protocol/IP restrictions khi dùng;
- signing mechanism.

Mental model:

```text
Backend owns broad storage identity
      |
      +--> issues narrow temporary capability
                |
                v
          Client uploads blob
```

## 2. Why does it exist?

Nếu browser/mobile upload file qua API server:

```text
Client -> API -> Blob Storage
```

API phải nhận rồi forward toàn file, tốn bandwidth/memory/connections.

Cho client storage account key lại quá nguy hiểm vì key có quyền rất rộng và khó thu hồi theo từng user/request.

SAS cho phép direct upload với capability giới hạn.

## 3. How does it work?

Backend xác thực user và authorize business action trước. Sau đó backend phát SAS cho một blob/container path cụ thể trong vài phút.

```text
1. Client -> API: request upload permission
2. API -> authorize user/file metadata
3. API -> SAS for blob path, write-only, short expiry
4. Client -> Blob Storage direct upload
5. Client/API -> finalize metadata/workflow
```

User delegation SAS dùng Microsoft Entra credentials và thường tốt hơn account-key-signed SAS vì giảm phụ thuộc vào long-lived account key.

## 4. Practical implementation

Ví dụ generate user delegation SAS về mặt flow:

```csharp
var blobClient = container.GetBlobClient(blobName);

var delegationKey = await blobServiceClient.GetUserDelegationKeyAsync(
    startsOn: DateTimeOffset.UtcNow.AddMinutes(-5),
    expiresOn: DateTimeOffset.UtcNow.AddMinutes(15),
    cancellationToken: ct);

var sasBuilder = new BlobSasBuilder
{
    BlobContainerName = container.Name,
    BlobName = blobName,
    Resource = "b",
    StartsOn = DateTimeOffset.UtcNow.AddMinutes(-5),
    ExpiresOn = DateTimeOffset.UtcNow.AddMinutes(10)
};

sasBuilder.SetPermissions(BlobSasPermissions.Create | BlobSasPermissions.Write);
```

Backend identity nên dùng Managed Identity để lấy delegation key thay vì lưu account key trong config.

## 5. Real production scenario

CMS cho editor upload video 500 MB. Proxy qua ASP.NET Core làm request timeout và App Service outbound/inbound resource bị giữ lâu.

Direct-to-Blob upload với short-lived SAS giảm load web tier. Sau upload, background process scan malware/transcode rồi mới publish asset.

## 6. Failure scenario & troubleshooting

**Symptom**
→ SAS URL bị share ngoài ý muốn và người khác vẫn upload được.

**Evidence**
→ SAS có expiry 7 ngày, permission `rwdl`, scope container-wide.

**Hypothesis**
→ capability rộng hơn business need.

**Diagnosis**
→ inspect SAS permissions, resource scope, expiry và issue logs.

**Fix**
→ blob-specific, short-lived, minimum permissions; rotate/revoke supporting key/policy nếu cần; ưu tiên user delegation SAS.

**Verification**
→ security test token hết hạn, path khác và forbidden operation đều fail.

## 7. Common mistakes

- Đưa storage account key cho frontend.
- SAS sống nhiều ngày cho one-time upload.
- Cấp Read + Write + Delete dù chỉ cần Create.
- Tin SAS tự thay thế business authorization.
- Public publish blob ngay trước malware/content validation.
- Log full SAS URL chứa credential-bearing query string.

## 8. Alternatives

- Backend proxy upload cho files nhỏ hoặc cần synchronous inspection.
- Private backend-only storage nếu client direct access không cần thiết.
- Managed Identity cho service-to-service access không cần SAS.

## 9. Trade-offs

### Advantages

- Offload file bandwidth khỏi app server.
- Least-privilege temporary access.
- Scale tốt cho large upload/download.

### Costs / Risks

- SAS là bearer capability; lộ token là lộ quyền trong thời gian còn hiệu lực.
- Client workflow phức tạp hơn.
- Cần finalize/validation process rõ ràng sau direct upload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SAS là temporary scoped permission, không phải storage password.

### Middle

Tạo SAS hẹp, short-lived và direct upload flow.

### Senior

Thiết kế malware scanning, finalize state, token leakage protection và observability.

### Technical Lead / Architect

Quyết định direct-client storage pattern, identity model, retention và security boundaries cho toàn file platform.

## 11. Key takeaway

- SAS nên ngắn hạn, scope nhỏ và permission tối thiểu.
- Business authorization phải xảy ra trước khi phát SAS.
- Managed Identity + user delegation SAS giảm phụ thuộc vào long-lived account keys.

# 8. SLI, SLO và error budget: biến reliability từ cảm giác thành contract có thể đo và dùng để quyết định release

## 1. What is it?

Ba khái niệm:

```text
SLI = measurement
SLO = target cho measurement
SLA = external/business commitment, thường có consequence
```

Ví dụ:

```text
SLI: tỷ lệ successful checkout requests
SLO: 99.9% successful trong 30 ngày
```

Error budget là phần failure được phép trong SLO window.

99.9% success nghĩa error budget khoảng 0.1% requests trong window, không phải “không bao giờ được lỗi”.

## 2. Why does it exist?

Nếu team chỉ nói “service phải ổn định”, không ai biết:

- ổn định bao nhiêu là đủ;
- latency nào được chấp nhận;
- khi nào phải dừng feature work để sửa reliability;
- alert nào thực sự actionable.

SLO tạo shared engineering target giữa product và operations.

## 3. How does it work?

Availability SLI có thể là:

```text
Good requests / Eligible requests
```

Latency SLI có thể là:

```text
% requests completed < 500ms
```

Không nên dùng average latency làm SLI duy nhất.

Burn rate đo error budget đang bị tiêu nhanh cỡ nào.

```text
budget burn 1x -> đúng tốc độ cho phép
budget burn 10x -> nếu kéo dài sẽ vi phạm SLO nhanh
```

## 4. Practical implementation

Ví dụ query/metric logic conceptual:

```text
good = requests where status < 500 and duration < 1000ms
total = eligible requests excluding health probes
SLI = good / total
```

ASP.NET Core/OpenTelemetry có thể export request count, status và latency histogram. Azure Monitor/Application Insights dashboard hiển thị rolling 30-day SLO và burn rate.

Alert nên dựa burn rate hoặc user-impacting signal, không alert mọi exception riêng lẻ.

## 5. Real production scenario

API có 99.99% uptime nhưng checkout p99 tăng từ 700 ms lên 7 giây trong peak hour. Availability dashboard xanh nhưng user abandon tăng mạnh.

Nếu SLO chỉ đo uptime thì reliability contract sai. Cần latency SLO cho critical path.

## 6. Failure scenario & troubleshooting

**Symptom**
→ đội nhận hàng trăm alerts nhưng incident thực sự vẫn bị phát hiện muộn.

**Evidence**
→ alerts dựa CPU, từng exception và dependency spikes không gắn SLO/user impact.

**Hypothesis**
→ monitoring có nhiều signals nhưng không có reliability objective.

**Diagnosis**
→ map alerts về SLI/SLO và kiểm tra signal nào dự đoán user impact.

**Fix**
→ chọn vài SLIs critical, xây burn-rate alerts và dùng low-level metrics để diagnosis sau khi alert fire.

**Verification**
→ game day/incident review xác nhận alert trigger nhanh, ít noise và chỉ ra impacted SLO.

## 7. Common mistakes

- Dùng SLA như internal alert threshold.
- Đặt SLO 100% cho mọi service.
- Chọn metric dễ đo thay vì user-important.
- Không loại health checks/bot traffic khỏi eligible requests khi cần.
- Có SLO nhưng không có decision policy khi budget cạn.
- Alert CPU 80% dù users hoàn toàn khỏe.

## 8. Alternatives

Không có thay thế trực tiếp cho reliability objective, nhưng KPI/product metrics bổ sung business impact. Technical component metrics vẫn cần để root-cause, chỉ không nên thay SLO.

## 9. Trade-offs

### Advantages

- Reliability trở thành measurable target.
- Alerting tập trung user impact.
- Error budget giúp cân bằng release speed và stability.

### Costs / Risks

- Chọn SLI sai tạo false confidence.
- Instrumentation/cardinality có cost.
- SLO quá strict có thể chặn delivery vô lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt metric với target.

### Middle

Build dashboards cho success rate/latency và hiểu p95/p99.

### Senior

Thiết kế SLI, burn-rate alert và incident analysis theo user impact.

### Technical Lead / Architect

Thống nhất SLO với Product/Operations và đặt error-budget policy ảnh hưởng release decisions.

## 11. Key takeaway

- SLI đo, SLO đặt target, SLA là commitment khác về bản chất.
- Reliability nên phản ánh user experience, không chỉ infrastructure health.
- Error budget biến stability vs delivery thành decision có dữ liệu.

# 9. Contract Testing cho API integration: phát hiện breaking change giữa consumer và provider trước khi production mới là mục tiêu, không phải test thêm cho đủ coverage

## 1. What is it?

Contract test xác minh consumer và provider thống nhất về interaction contract: endpoint, request, response shape, status semantics hoặc message schema.

Mental model:

```text
Consumer expectation
       |
       v
Contract
       |
       v
Provider verification
```

Nó nằm giữa unit test và full end-to-end test: tập trung boundary giữa systems.

## 2. Why does it exist?

Provider unit tests có thể xanh nhưng vẫn break consumer vì provider không biết assumptions của consumer.

E2E test có thể phát hiện breaking change nhưng thường:

- chậm;
- flaky;
- cần nhiều environments;
- failure khó localize.

Contract test đưa compatibility check gần CI hơn.

## 3. How does it work?

Consumer-driven contract flow:

```text
Consumer test
  -> record expected interaction
  -> publish contract artifact
Provider CI
  -> replay contract against provider
  -> fail build if incompatible
```

Schema-based contract có thể dùng OpenAPI diff hoặc JSON schema, nhưng semantic compatibility vẫn cần test behavior quan trọng.

## 4. Practical implementation

Ví dụ consumer mong:

```json
GET /customers/42
200
{
  "id": 42,
  "name": "Alice"
}
```

Provider refactor `name` thành `displayName`. Unit tests provider có thể pass, nhưng contract verification fail trước release.

Trong .NET, có thể dùng Pact hoặc custom integration tests dựa OpenAPI/schema tùy complexity. Điều quan trọng là CI workflow và ownership, không phải library cụ thể.

## 5. Real production scenario

Mobile backend consume pricing API. Pricing team đổi `decimal price` sang string-formatted price để “UI dùng tiện hơn”.

Provider tests pass. Mobile app cũ deserialize fail ở production.

Consumer contract test sẽ chặn provider release vì contract mà consumer đang dùng không còn được đáp ứng.

## 6. Failure scenario & troubleshooting

**Symptom**
→ contract test suite tồn tại nhưng không bắt breaking changes thực tế.

**Evidence**
→ contracts assert toàn response snapshot hoặc quá generic như “status 200”.

**Hypothesis**
→ contract không phản ánh consumer-relevant behavior.

**Diagnosis**
→ review fields/semantics consumer thực sự sử dụng.

**Fix**
→ assert minimal meaningful contract, version interactions, chạy provider verification trong CI.

**Verification**
→ intentionally introduce breaking change và xác nhận pipeline fail đúng nơi.

## 7. Common mistakes

- Snapshot toàn payload làm contract quá brittle.
- Contract test business logic nội bộ thay vì boundary.
- Publish contract nhưng provider CI không verify.
- Tin OpenAPI schema alone bắt mọi semantic breaking change.
- Dùng mocks generated từ stale contract rồi tự xác nhận chính mock đó.

## 8. Alternatives

- Integration test trực tiếp provider.
- E2E test cho vài critical journeys.
- OpenAPI breaking-change analysis cho structural contract.

Một mature strategy thường dùng kết hợp, không thay toàn bộ test pyramid bằng contract tests.

## 9. Trade-offs

### Advantages

- Phát hiện integration break sớm.
- Test nhanh hơn full E2E.
- Làm consumer assumptions explicit.

### Costs / Risks

- Contract artifacts/versioning cần governance.
- Quá nhiều low-value interactions tạo maintenance burden.
- Không kiểm chứng network/config/runtime environment như E2E.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu unit test provider không đảm bảo consumer compatibility.

### Middle

Viết contract test cho fields/status consumer thật sự dùng.

### Senior

Thiết kế provider verification pipeline, compatibility policy và tránh brittle snapshots.

### Technical Lead / Architect

Chọn integration nào cần contract testing dựa deployment independence và blast radius, không bắt mọi internal call dùng cùng pattern.

## 11. Key takeaway

- Contract testing bảo vệ compatibility boundary giữa deployable systems.
- Contract nên tối thiểu nhưng meaningful.
- Giá trị thật đến từ provider verification trong CI trước release.

# 10. Optimizely CMS content modeling và cache invalidation: mô hình nội dung tốt phải phục vụ editor, rendering, delivery API và cache lifecycle cùng lúc

## 1. What is it?

Content modeling trong CMS định nghĩa cấu trúc business/editorial của content: Page Types, Blocks, properties, references và composition rules.

Trong Optimizely CMS, developer thường tạo content types bằng C# models/attributes, nhưng architecture vấn đề rộng hơn API syntax.

Mental model:

```text
Editor intent
   -> Content model
      -> CMS repository
         -> rendering / Delivery API
            -> cache/CDN
```

## 2. Why does it exist?

Nếu content model bám sát một page design cụ thể, mỗi redesign lại yêu cầu migration content. Nếu model quá generic kiểu `JsonBlob`, editor mất guidance, validation và reuse.

Content model tốt cân bằng:

- editorial usability;
- reuse;
- semantic stability;
- rendering flexibility;
- performance/cache behavior.

## 3. How does it work?

Ví dụ:

```text
ProductLandingPage
  |- Heading
  |- Intro
  `- MainContentArea
        |- HeroBlock
        |- RichTextBlock
        `- ProductGridBlock
```

Page đại diện context/navigation; Block đại diện reusable content component.

Publish content tạo new version và cache invalidation cần lan tới output/edge entries phụ thuộc content đó.

Một block được reuse ở 30 pages nghĩa publish block có thể làm 30 rendered pages stale nếu invalidation graph không được hiểu đúng.

## 4. Practical implementation

Optimizely model đơn giản:

```csharp
[ContentType(
    DisplayName = "Hero Block",
    GUID = "11111111-1111-1111-1111-111111111111")]
public class HeroBlock : BlockData
{
    [Display(Order = 10)]
    public virtual string Heading { get; set; } = string.Empty;

    [Display(Order = 20)]
    public virtual ContentReference? Image { get; set; }

    [Display(Order = 30)]
    public virtual Url? CallToActionUrl { get; set; }
}
```

Không nên thêm property chỉ vì current frontend có một CSS field cụ thể như `marginTopPixels`. Ưu tiên semantic intent như `Theme`, `Emphasis`, `LayoutVariant` nếu editor thực sự cần control đó.

## 5. Real production scenario

Marketing site dùng HeroBlock trên hàng trăm pages và CDN cache 10 phút. Editor publish sửa legal disclaimer trong shared block.

CMS repository đã có content mới nhưng edge vẫn trả HTML cũ. User thấy inconsistency giữa pages tùy cache hit.

Đây không chỉ là “CMS bug”; đây là cache dependency/invalidation problem xuyên nhiều layers.

## 6. Failure scenario & troubleshooting

**Symptom**
→ editor thấy Published nhưng public site vẫn hiển thị content cũ.

**Evidence**
→ CMS preview đúng; origin có response mới; CDN/HTML output cache trả age cũ.

**Hypothesis**
→ invalidation không propagate tới cache layer chứa composed page.

**Diagnosis**
→ trace:

```text
CMS version
-> application cache
-> output cache
-> CDN cache
-> browser cache
```

Kiểm tra cache key/tag/surrogate key/TTL/purge event ở từng layer.

**Fix**
→ định nghĩa dependency-aware invalidation hoặc chấp nhận TTL có SLA freshness rõ.

**Verification**
→ publish shared block trong staging và đo thời gian mọi dependent surfaces phản ánh content mới.

## 7. Common mistakes

- Model theo pixel/layout hiện tại thay vì content semantics.
- Một “MegaBlock” chứa hàng chục optional properties cho mọi use case.
- Tạo block quá nhỏ khiến editor phải compose 20 phần cho một section đơn giản.
- Dùng CMS như transactional product database.
- Không tính cache invalidation khi reuse content.
- Coupling frontend trực tiếp vào internal CMS property names mà không có delivery contract ổn định.

## 8. Alternatives

- Headless CMS khi nhiều channels cần cùng content qua API.
- Traditional CMS rendering khi editorial preview/server rendering là ưu tiên.
- Product/PIM system cho product data transactional/structured chuyên biệt thay vì nhét vào CMS.

## 9. Trade-offs

### Advantages

- Structured content giúp reuse, validation và editorial consistency.
- Blocks/page types tạo composition rõ.
- CMS workflow tách content release khỏi code release.

### Costs / Risks

- Content model sai rất khó migrate khi data đã lớn.
- Reuse làm cache dependency phức tạp hơn.
- Quá generic hoặc quá specific đều làm editor experience xấu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Page Type, Block và content property đại diện semantic content.

### Middle

Implement content types, validation, rendering và basic caching.

### Senior

Thiết kế reusable model, migration, delivery contract và debug multi-layer stale content.

### Technical Lead / Architect

Quyết định boundary giữa CMS, PIM/product API, search và frontend; đặt content governance + caching strategy để editor autonomy không phá performance/correctness.

## 11. Key takeaway

- Content model nên bám editorial/business meaning hơn current UI pixels.
- Reusable content kéo theo dependency-aware cache invalidation.
- CMS không nên trở thành transactional source of truth cho mọi loại dữ liệu.
