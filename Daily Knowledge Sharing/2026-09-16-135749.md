# 1. `IAsyncEnumerable<T>`: streaming dữ liệu với cancellation và backpressure thực dụng

## 1. What is it?

`IAsyncEnumerable<T>` biểu diễn một chuỗi phần tử được tạo bất đồng bộ theo thời gian. Thay vì chờ toàn bộ collection được tải vào memory rồi trả về, consumer có thể `await foreach` từng phần tử khi producer cung cấp chúng.

Mental model quan trọng là **pull-based asynchronous streaming**: consumer yêu cầu phần tử tiếp theo; producer thực hiện I/O cần thiết rồi trả phần tử đó. Đây không phải message queue và cũng không tự tạo parallelism.

## 2. Why does it exist?

Một API export 500.000 rows nếu gọi `ToListAsync()` trước khi xử lý sẽ giữ toàn bộ result trong memory, tăng allocation và làm time-to-first-result dài. Streaming cho phép bắt đầu xử lý sớm và giới hạn working set.

Tuy nhiên streaming không loại bỏ mọi buffer. Database provider, reverse proxy, serializer hoặc client vẫn có thể buffer ở layer khác.

## 3. How does it work?

Compiler biến async iterator thành state machine. Mỗi `MoveNextAsync()` tiến state machine tới `yield return` tiếp theo.

```text
Consumer MoveNextAsync()
        |
        v
Async iterator -> DB/network I/O
        |
        v
    yield item
        |
        v
Consumer processes item
```

Tốc độ consumer tự nhiên giới hạn tốc độ producer ở mô hình pull này. Cancellation phải được truyền xuống iterator và I/O bên dưới.

## 4. Practical implementation

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [System.Runtime.CompilerServices.EnumeratorCancellation]
    CancellationToken cancellationToken = default)
{
    await foreach (var order in db.Orders
        .AsNoTracking()
        .OrderBy(x => x.Id)
        .AsAsyncEnumerable()
        .WithCancellation(cancellationToken))
    {
        yield return new OrderDto(order.Id, order.Total);
    }
}
```

Consumer:

```csharp
await foreach (var order in service.StreamOrdersAsync(ct))
{
    await writer.WriteLineAsync($"{order.Id},{order.Total}");
}
```

Giữ `DbContext` và connection sống trong suốt enumeration; đây là operational consequence cần tính trước.

## 5. Real production scenario

Một background export tạo CSV từ hàng triệu transactions. Streaming giảm peak memory đáng kể và bắt đầu ghi file sớm. Nhưng query chạy 15 phút cũng giữ database connection 15 phút. Nếu 50 exports chạy đồng thời, connection pool có thể trở thành bottleneck dù memory ổn.

## 6. Failure scenario & troubleshooting

**Symptom** → memory thấp hơn nhưng database connections bị giữ lâu và API khác bắt đầu timeout.  
**Evidence** → connection-pool metrics cho thấy active connections tăng theo số stream; traces có SQL span rất dài.  
**Hypothesis** → streaming kéo dài resource lifetime.  
**Diagnosis** → kiểm tra thời gian enumeration và concurrency của exports.  
**Fix** → giới hạn concurrent exports, chunk theo keyset, chuyển heavy export sang background job hoặc materialize theo bounded batches.  
**Verification** → connection utilization và p95 của API bình thường trở lại.

## 7. Common mistakes

- Cho rằng streaming luôn nhanh hơn batching.
- Quên cancellation nên client disconnect nhưng query vẫn chạy.
- Enumerate cùng stream nhiều lần như một in-memory collection.
- Thực hiện slow remote call cho từng item, biến stream thành N+1 network calls.
- Không hiểu serializer/proxy có thể buffer response.

## 8. Alternatives

`ToListAsync()` đơn giản hơn cho result nhỏ. Bounded batching phù hợp khi muốn giải phóng DB connection giữa batches. `Channel<T>` phù hợp producer/consumer concurrency trong process. Message broker phù hợp durable asynchronous work xuyên process.

## 9. Trade-offs

### Advantages

Giảm peak memory, cải thiện time-to-first-item, phù hợp pipelines lớn.

### Costs / Risks

Resource lifetime dài, error có thể xảy ra giữa stream sau khi response bắt đầu, retry khó hơn và end-to-end buffering cần được hiểu rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await foreach` nhận item dần thay vì chờ toàn bộ collection.

### Middle

Implement iterator có cancellation và tránh per-item N+1 I/O.

### Senior

Đánh giá connection lifetime, response buffering, partial failure và concurrency limits.

### Technical Lead / Architect

Quyết định streaming, batching hay asynchronous export dựa trên dataset, SLA, resource budget và failure semantics.

## 11. Key takeaway

- Streaming tối ưu working set nhưng có thể kéo dài resource lifetime.
- `IAsyncEnumerable<T>` không tự tạo parallelism hay durability.
- Đo cả memory, connection usage và end-to-end buffering.

# 2. EF Core `DbContext` pooling: giảm allocation nhưng không được rò state giữa requests

## 1. What is it?

`AddDbContextPool<TContext>` tái sử dụng các `DbContext` instances thay vì tạo instance mới cho mỗi scope. EF Core reset internal state trước khi context quay lại pool.

Nó khác database connection pooling: connection pooling nằm ở ADO.NET provider; `DbContext` pooling tái sử dụng object graph của EF Core.

## 2. Why does it exist?

Khởi tạo `DbContext` có allocation và setup cost. Trong high-throughput service với context sống rất ngắn, pooling có thể giảm allocation và latency. Nhưng với phần lớn ứng dụng, database I/O thường lớn hơn context-construction cost nên phải benchmark trước.

## 3. How does it work?

```text
Request A -> rent DbContext -> use -> reset -> return pool
Request B -> rent same instance --------------------^
```

EF reset Change Tracker và internal EF state, nhưng state tùy chỉnh mà application gắn vào context không tự nhiên trở thành request-safe.

## 4. Practical implementation

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Tránh kiểu stateful context:

```csharp
public sealed class AppDbContext : DbContext
{
    // Nguy hiểm nếu giá trị này được set theo request và context được pooled.
    public Guid TenantId { get; set; }
}
```

Multi-tenancy nên đưa tenant predicate/state qua boundary được thiết kế rõ, không giả định constructor chạy mỗi request trên pooled instance.

## 5. Real production scenario

Một SaaS API thêm `TenantId` mutable vào pooled context. Request tenant A trả context về pool; request tenant B nhận lại instance và một code path quên overwrite tenant state. Kết quả có nguy cơ query sai tenant — correctness/security incident nghiêm trọng.

## 6. Failure scenario & troubleshooting

**Symptom** → hiếm khi dữ liệu tenant sai hoặc interceptor dùng request metadata cũ.  
**Evidence** → lỗi chỉ xuất hiện dưới concurrency/load; instance identity cho thấy context được reuse.  
**Hypothesis** → mutable per-request state sống trong pooled object.  
**Diagnosis** → audit custom fields, interceptors và services được context giữ.  
**Fix** → loại state request-specific khỏi pooled context hoặc dùng scoped factory/wrapper an toàn.  
**Verification** → concurrency test nhiều tenants và invariant tests không còn cross-request leakage.

## 7. Common mistakes

Nhầm context pooling với connection pooling; bật pooling mà không benchmark; lưu tenant/user/request state trong context; giả định `OnConfiguring` chạy cho mỗi request; dùng pooling để chữa slow SQL.

## 8. Alternatives

`AddDbContext` thông thường đơn giản và an toàn hơn khi context construction không phải bottleneck. `IDbContextFactory<TContext>` phù hợp explicit lifetime hoặc nhiều unit-of-work trong cùng scope.

## 9. Trade-offs

### Advantages

Giảm allocation/setup overhead trong workload phù hợp.

### Costs / Risks

Object reuse làm state ownership khó hơn; lợi ích nhỏ nếu bottleneck là database; multi-tenancy cần đặc biệt cẩn thận.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt `DbContext` pooling và DB connection pooling.

### Middle

Cấu hình pooling và giữ context stateless ngoài EF-managed state.

### Senior

Benchmark allocation/latency và audit tenant/request state.

### Technical Lead / Architect

Chỉ chấp nhận pooling khi evidence cho thấy giá trị và team hiểu lifecycle constraints.

## 11. Key takeaway

- Pooling là optimization, không phải default correctness pattern.
- Không đặt mutable request-specific state vào pooled context.
- Slow query không được chữa bằng `DbContext` pooling.

# 3. SQL SARGability: viết predicate để optimizer có thể dùng index hiệu quả

## 1. What is it?

SARGable predicate là điều kiện mà database optimizer có thể biến thành efficient search argument trên index, ví dụ range seek. Khi bọc indexed column trong function hoặc implicit conversion không phù hợp, engine có thể phải scan nhiều rows hơn.

## 2. Why does it exist?

Index chỉ hữu ích khi query shape cho phép engine thu hẹp key range. Query đúng về logic vẫn có thể gây I/O rất lớn nếu predicate che mất quan hệ trực tiếp với indexed key.

## 3. How does it work?

Giả sử index trên `CreatedAt`:

```sql
-- Kém SARGable
WHERE CAST(CreatedAt AS date) = @date

-- SARGable
WHERE CreatedAt >= @date
  AND CreatedAt < DATEADD(day, 1, @date)
```

Query thứ hai mô tả một contiguous key range, cho phép optimizer cân nhắc index seek.

Chuỗi reasoning cần là:

**query → execution plan → estimated/actual rows → logical reads → locks → latency**.

## 4. Practical implementation

```sql
SET STATISTICS IO, TIME ON;

SELECT Id, CustomerId, CreatedAt
FROM Orders
WHERE CustomerId = @customerId
  AND CreatedAt >= @from
  AND CreatedAt < @to;
```

So sánh execution plan và logical reads trước/sau khi rewrite. Không kết luận chỉ dựa vào chữ `Index Seek`; seek vẫn có thể đọc rất nhiều rows nếu selectivity thấp.

## 5. Real production scenario

Reporting API filter theo ngày dùng `CONVERT(date, CreatedAt)`. Khi bảng tăng từ 2 triệu lên 80 triệu rows, CPU/reads tăng mạnh. Rewrite thành half-open range giảm I/O mà không cần thêm index mới.

## 6. Failure scenario & troubleshooting

**Symptom** → query latency tăng theo table size.  
**Evidence** → plan có scan và logical reads rất cao.  
**Hypothesis** → predicate không SARGable hoặc implicit conversion.  
**Diagnosis** → inspect plan predicates, data types và parameter types.  
**Fix** → rewrite predicate, align types; chỉ thay index nếu access pattern thực sự yêu cầu.  
**Verification** → compare plan, reads, CPU và p95.

## 7. Common mistakes

- Bọc column trong `LOWER`, `CAST`, arithmetic mà không hiểu consequence.
- So sánh mismatched data types gây implicit conversion.
- Thấy scan là lập tức thêm index.
- Chỉ nhìn execution time trên dev dataset nhỏ.
- Không tính write/storage cost của index mới.

## 8. Alternatives

Computed/indexed expression có thể phù hợp khi business query thực sự cần transformed value. Full-text search phù hợp text-search semantics. Rewrite predicate thường đơn giản nhất nếu giữ nguyên meaning.

## 9. Trade-offs

### Advantages

Có thể giảm I/O lớn mà không thêm infrastructure hoặc index.

### Costs / Risks

Rewrite phải giữ đúng semantics, đặc biệt timezone, collation và nullable behavior; optimizer vẫn quyết định scan nếu scan rẻ hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không tự động làm mọi filter nhanh.

### Middle

Nhận diện common non-SARGable predicates và đọc plan cơ bản.

### Senior

Reason về selectivity, implicit conversion, I/O và plan choices.

### Technical Lead / Architect

Đưa query-shape review và production measurements vào performance practice thay vì index-by-instinct.

## 11. Key takeaway

- Viết predicate để optimizer nhìn thấy key range.
- Đo logical reads và plan, không chỉ elapsed time.
- `Index Seek` không tự động đồng nghĩa query tốt.

# 4. Redis hot key: khi distributed cache biến thành bottleneck tập trung

## 1. What is it?

Hot key là cache key nhận lượng traffic không cân xứng so với phần còn lại. Dù Redis cluster phân phối nhiều keys qua shards, một key cụ thể thường thuộc một shard và có thể tập trung CPU/network load vào node đó.

## 2. Why does it exist?

Caching thường được thêm để giảm database load. Nhưng popularity distribution không đều: homepage config, global catalog metadata hoặc flash-sale product có thể nhận hàng chục nghìn reads/second. Distributed cache không có nghĩa một key được tự động phân tán trên mọi node.

## 3. How does it work?

```text
App instances ---- thousands RPS ----> key:product:flash-sale
                                      |
                                      v
                                one Redis shard
```

Nếu key hết hạn đồng thời với traffic peak, hot key còn kết hợp với stampede và tạo burst về origin.

## 4. Practical implementation

Một mitigation đơn giản cho immutable/read-mostly data là L1 + L2 cache:

```csharp
if (memoryCache.TryGetValue(key, out ProductDto? local))
    return local!;

var distributed = await redis.GetAsync(key, ct);
if (distributed is not null)
{
    var value = Deserialize(distributed);
    memoryCache.Set(key, value, TimeSpan.FromSeconds(10));
    return value;
}
```

L1 TTL ngắn giảm request fan-in tới Redis nhưng chấp nhận bounded staleness.

## 5. Real production scenario

Flash sale page đọc cùng promotion configuration trên mọi request. Database load thấp nhưng một Redis shard đạt network/CPU saturation; API p99 tăng. Scale thêm app instances làm Redis pressure tệ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis latency tăng dù tổng cache dataset nhỏ.  
**Evidence** → command/key sampling và per-node metrics cho thấy traffic tập trung.  
**Hypothesis** → hot key.  
**Diagnosis** → correlate key access frequency với shard CPU/network.  
**Fix** → local cache, precompute, request coalescing hoặc redesign access pattern; replication/read scaling tùy topology.  
**Verification** → per-node load cân bằng hơn và Redis p99 giảm.

## 7. Common mistakes

Tăng cluster nodes và giả định hot key tự chia; TTL tất cả instances giống nhau; cache giant object rồi transfer liên tục; không có fallback khi Redis chậm; dùng distributed lock trên chính hot path mà không đo contention.

## 8. Alternatives

`IMemoryCache` phù hợp data có thể stale nhẹ và mỗi instance giữ copy. CDN phù hợp HTTP-cacheable public content. Database/read replica có thể đủ nếu workload không cần Redis. Precomputed static artifact đôi khi đơn giản nhất.

## 9. Trade-offs

### Advantages

Redis vẫn rất hiệu quả cho shared low-latency cache và atomic primitives.

### Costs / Risks

Hotspot, network hop, serialization và operational dependency có thể biến cache thành critical bottleneck.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu distributed cache không đồng nghĩa mỗi key được phân tán.

### Middle

Đo hit rate, latency, TTL và key access patterns.

### Senior

Phân tích shard hotspot, stampede và stale-data tolerance.

### Technical Lead / Architect

Quyết định data nên ở CDN, L1, Redis hay origin và ai sở hữu invalidation.

## 11. Key takeaway

- Scale-out Redis không tự chữa một hot key.
- Cache design phải xét popularity distribution, không chỉ hit rate.
- L1 cache có thể giảm hotspot nếu business chấp nhận bounded staleness.

# 5. Anti-Corruption Layer: bảo vệ domain boundary trước model của hệ thống bên ngoài

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary dịch model/protocol của external hoặc legacy system sang language/model của bounded context nội bộ. Nó ngăn external concepts lan trực tiếp vào domain.

## 2. Why does it exist?

External API thường có naming, lifecycle và semantics khác business model nội bộ. Nếu domain entities phụ thuộc trực tiếp DTO của vendor, vendor schema changes sẽ lan qua application và business logic.

ACL đáng dùng khi semantic mismatch có thật; một wrapper một-dòng quanh API ổn định không tự nhiên trở thành kiến trúc tốt hơn.

## 3. How does it work?

```text
Our Domain <- internal port <- ACL adapter <- Vendor API
```

Responsibilities: adapter authentication/transport, translator mapping semantics, application service orchestration. Domain không biết vendor DTO.

Data ownership vẫn thuộc từng system; ACL không tạo distributed transaction. Failure của vendor phải được translate thành failure contract nội bộ có ý nghĩa.

## 4. Practical implementation

```csharp
public interface ICustomerRiskService
{
    Task<RiskAssessment> AssessAsync(Customer customer, CancellationToken ct);
}

internal sealed class VendorRiskAdapter(HttpClient http) : ICustomerRiskService
{
    public async Task<RiskAssessment> AssessAsync(Customer customer, CancellationToken ct)
    {
        var dto = await http.GetFromJsonAsync<VendorRiskDto>(
            $"risk/{customer.ExternalReference}", ct)
            ?? throw new InvalidOperationException("Missing vendor response");

        return dto.Code switch
        {
            "G" => RiskAssessment.Low,
            "A" => RiskAssessment.High,
            _ => RiskAssessment.Unknown
        };
    }
}
```

## 5. Real production scenario

CRM gọi legacy ERP nơi “customer status” gồm codes `01`, `02`, `99`. Domain CRM cần concepts `Active`, `Suspended`, `Closed`. ACL sở hữu mapping và xử lý unknown code thay vì để magic codes xuất hiện khắp domain.

## 6. Failure scenario & troubleshooting

**Symptom** → vendor thêm status mới và business flow bắt đầu xử lý sai.  
**Evidence** → telemetry cho unknown external code tăng.  
**Hypothesis** → contract drift.  
**Diagnosis** → compare vendor contract với translation rules.  
**Fix** → explicit unknown behavior, contract test và mapping update.  
**Verification** → replay representative payloads và domain invariants vẫn đúng.

## 7. Common mistakes

Copy toàn bộ vendor model vào domain; ACL chứa business rules thuộc domain; che mọi vendor failure thành generic exception; xây abstraction lớn dù chỉ có một stable endpoint; không version contract tests.

## 8. Alternatives

Direct integration đơn giản hơn khi semantics gần nhau và coupling chấp nhận được. Shared canonical model có thể hữu ích trong controlled ecosystem nhưng dễ thành enterprise-wide coupling. Event translation phù hợp asynchronous integration.

## 9. Trade-offs

### Advantages

Change isolation, domain language sạch, vendor replacement/migration dễ hơn.

### Costs / Risks

Thêm mapping code, tests và ownership; có thể overengineering nếu integration rất nhỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DTO ngoài không nhất thiết là domain model.

### Middle

Implement adapter và mapping có tests.

### Senior

Xác định semantic mismatch, failure translation và contract drift.

### Technical Lead / Architect

Quyết định boundary, ownership, transaction limits, sync/async communication và deployment coupling; chọn direct integration nếu đơn giản đã đủ.

## 11. Key takeaway

- ACL bảo vệ semantics, không chỉ che HTTP client.
- Boundary đáng tồn tại khi external model có khả năng làm ô nhiễm domain.
- Đừng thêm ACL chỉ để có thêm layer.

# 6. Event schema evolution: thay đổi integration event mà không phá consumers

## 1. What is it?

Event schema evolution là cách thay đổi contract của integration events khi producers và consumers deploy độc lập. Event đã publish có thể còn nằm trong queue, DLQ hoặc audit store lâu hơn một release.

## 2. Why does it exist?

REST có caller/server interaction tại thời điểm request; messaging có temporal decoupling. Consumer cũ có thể nhận event mới, và consumer mới có thể replay event cũ. Breaking schema change vì vậy nguy hiểm hơn việc compile cùng solution.

## 3. How does it work?

Prefer additive changes: thêm optional field, giữ meaning cũ. Breaking semantic change có thể cần event type/version mới.

```json
{
  "eventType": "OrderPlaced",
  "schemaVersion": 2,
  "orderId": "...",
  "total": 125.40,
  "currency": "USD"
}
```

Producer sở hữu event contract; consumer phải tolerant với fields không dùng. Event là integration contract, không nên serialize domain entity trực tiếp.

## 4. Practical implementation

```csharp
public sealed record OrderPlacedV2(
    Guid OrderId,
    decimal Total,
    string Currency,
    DateTimeOffset OccurredAt);
```

Contract tests cần deserialize representative old/new payloads. Nếu dùng schema registry, compatibility rules nên được enforce trong CI.

## 5. Real production scenario

Order service thêm multi-currency. Consumer accounting cũ giả định mọi total là USD. Chỉ thêm `Currency` optional không đủ nếu semantic meaning của `Total` thay đổi. Đây là semantic breaking change dù JSON vẫn deserialize.

## 6. Failure scenario & troubleshooting

**Symptom** → consumer không crash nhưng tính báo cáo sai.  
**Evidence** → payload hợp lệ về schema nhưng consumer assumption cũ không còn đúng.  
**Hypothesis** → semantic compatibility bị phá.  
**Diagnosis** → review contract meaning, không chỉ serializer errors.  
**Fix** → version event/consumer migration và explicit currency handling.  
**Verification** → replay historical + new events qua contract/integration tests.

## 7. Common mistakes

Serialize EF/domain entity thành event; rename/remove field ngay; cho rằng optional field luôn backward-compatible; không giữ samples; dùng retry để xử lý poison event vĩnh viễn; không có DLQ ownership.

## 8. Alternatives

Command API đồng bộ phù hợp khi caller cần immediate result. Database sharing tránh event mapping nhưng tạo ownership coupling lớn. CDC có thể phát hiện changes nhưng raw table changes không tự nhiên là business events.

## 9. Trade-offs

### Advantages

Cho phép independent deployment và gradual evolution.

### Costs / Risks

Contract governance, multiple versions, replay testing và observability tăng complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

# 7. Azure Functions cold start: latency, scaling và lựa chọn hosting phù hợp

## 1. What is it?

Cold start là latency phát sinh khi Azure Functions cần tạo/khởi động worker instance trước khi xử lý invocation. Nó gồm platform allocation, process/runtime startup, application initialization và dependency setup.

## 2. Why does it exist?

Serverless elasticity cho phép scale down khi không có traffic và scale out theo demand. Đổi lại, capacity không luôn warm. Workload sporadic hưởng lợi về cost nhưng latency-sensitive synchronous endpoint có thể chịu tail latency khó đoán.

## 3. How does it work?

```text
Trigger -> scale controller -> new instance
                         -> runtime start
                         -> app initialization
                         -> invocation
```

Hosting plan và configuration ảnh hưởng khả năng giữ warm instances. Networking như VNet/private dependencies cũng có thể thêm startup/connection complexity.

## 4. Practical implementation

Giữ startup nhẹ và reuse clients:

```csharp
builder.Services.AddHttpClient<InventoryClient>();
builder.Services.AddSingleton<ExpensiveMetadataCache>();
```

Không tải hàng trăm MB reference data trong startup nếu invocation không luôn cần. Instrument startup/invocation separately để biết latency nằm ở đâu.

## 5. Real production scenario

Webhook endpoint nhận traffic vài lần mỗi giờ. Sau idle period, first request có p99 cao hơn bình thường. Business provider timeout nhanh và retry, tạo duplicate delivery. Idempotency trở thành bắt buộc dù root cause ban đầu là cold latency.

## 6. Failure scenario & troubleshooting

**Symptom** → request đầu sau idle chậm, các request sau nhanh.  
**Evidence** → instance/startup telemetry correlate với latency spike.  
**Hypothesis** → cold start hoặc initialization path.  
**Diagnosis** → tách platform startup, app startup và dependency latency.  
**Fix** → tối ưu initialization, chọn hosting có warm capacity nếu SLA cần, hoặc chuyển synchronous latency-sensitive API sang App Service/Container Apps.  
**Verification** → load test gồm idle-to-first-request, không chỉ steady state.

## 7. Common mistakes

Benchmark chỉ warm traffic; static initialization nặng; tạo client/connection mỗi invocation; chọn Functions vì “serverless” dù workload constant; không tính retry/idempotency; bỏ qua networking/private endpoint startup behavior.

## 8. Alternatives

App Service phù hợp always-on HTTP workload. Worker Service/Container Apps phù hợp long-running workers. Logic Apps phù hợp workflow integration. Functions mạnh với event-driven, bursty, short-lived work.

## 9. Trade-offs

### Advantages

Elastic scaling, event integrations tốt, giảm infrastructure management cho workload phù hợp.

### Costs / Risks

Cold latency, execution/hosting constraints, observability và cost có thể kém trực quan ở high sustained load.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu scale-to-zero/warm instance và cold start.

### Middle

Giữ startup nhẹ, reuse clients và đo invocation latency.

### Senior

Phân tích trigger scaling, idempotency, networking và p99.

### Technical Lead / Architect

Chọn Functions/App Service/Container Apps dựa trên workload shape, SLA, reliability, identity, networking, monitoring và cost — không dựa trên trend.

## 11. Key takeaway

- Cold start là trade-off của elasticity, không chỉ lỗi code.
- Test idle-to-first-request nếu SLA quan tâm tail latency.
- Hosting model phải khớp workload shape.

# 8. Canary deployment: giảm blast radius nhưng cần health signals và rollback rõ ràng

## 1. What is it?

Canary deployment đưa version mới tới một phần nhỏ traffic/instances trước khi mở rộng rollout. Mục tiêu là giới hạn blast radius và dùng production signals để kiểm chứng release.

## 2. Why does it exist?

CI tests không mô phỏng đầy đủ production traffic, data distribution và dependencies. Deploy 100% ngay lập tức biến một regression nhỏ thành incident toàn bộ user base.

## 3. How does it work?

```text
commit -> build -> test -> immutable artifact
                         |
                         v
                    canary 5%
                         |
                 health/SLO gate
                    /         \
                promote     rollback
```

Canary chỉ có giá trị nếu traffic routing và telemetry phân biệt version. Database changes phải backward-compatible vì old/new versions cùng chạy.

## 4. Practical implementation

Pipeline gate nên kiểm tra signals như:

```text
error_rate(version=new) <= threshold
p95_latency(version=new) <= baseline + budget
health_check == healthy
critical_business_metric has no regression
```

Artifact phải là cùng một artifact được promote; không rebuild giữa canary và production.

## 5. Real production scenario

Checkout release mới có bug chỉ xảy ra với một payment method hiếm. Canary 5% cho thấy payment failure rate của new version tăng rõ dù global error rate chỉ tăng nhẹ. Rollout dừng trước khi 100% traffic bị ảnh hưởng.

## 6. Failure scenario & troubleshooting

**Symptom** → canary “healthy” nhưng full rollout thất bại.  
**Evidence** → canary sample không chứa workload quan trọng hoặc gate chỉ check `/health`.  
**Hypothesis** → health signal không đại diện business behavior.  
**Diagnosis** → compare traffic cohorts và business KPIs.  
**Fix** → thêm representative routing/gates và minimum observation window.  
**Verification** → game-day/release simulation xác nhận gate bắt được regression.

## 7. Common mistakes

Chỉ check process alive; canary quá nhỏ để có statistical signal; rebuild artifact khi promote; migration breaking; không tag telemetry theo version; rollback procedure chưa test; feature flag và deployment state bị trộn lẫn.

## 8. Alternatives

Blue-Green cho cutover/rollback nhanh nhưng thường đổi traffic theo khối lớn hơn. Rolling deployment đơn giản hơn nhưng ít controlled exposure. Feature flags tách feature exposure khỏi binary deployment nhưng tạo flag lifecycle debt.

## 9. Trade-offs

### Advantages

Giảm blast radius, production validation có kiểm soát, hỗ trợ progressive delivery.

### Costs / Risks

Routing, observability, automation và schema compatibility phức tạp hơn; false confidence nếu signals yếu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu canary là progressive traffic exposure.

### Middle

Theo dõi version-tagged health/error/latency.

### Senior

Thiết kế rollback, observation window và backward-compatible migrations.

### Technical Lead / Architect

Quyết định release strategy theo risk; bảo đảm flow đầy đủ **commit → build → test → artifact → deploy → health validation → monitor → rollback**.

## 11. Key takeaway

- Canary không tốt hơn full rollout nếu không có signal đáng tin.
- Promote cùng immutable artifact đã được test.
- Database compatibility là một phần của progressive delivery.

# 9. .NET memory leak investigation với `dotnet-counters` và `dotnet-dump`

## 1. What is it?

Trong managed .NET, “memory leak” thường không phải memory bị mất khỏi allocator mà là objects vẫn reachable nên Garbage Collector không thể reclaim. Investigation cần phân biệt allocation rate cao, GC pressure, LOH growth, native memory và managed retention.

## 2. Why does it exist?

Restart process chữa symptom nhưng không giải thích root cause. Memory tăng có thể do cache không bounded, event subscriptions, static collections, long-lived tasks hoặc object graph bị singleton giữ.

## 3. How does it work?

Investigation loop:

**symptom → metrics → classify memory → capture dump → inspect heap/roots → hypothesis → fix → measure again**.

`dotnet-counters` cho runtime trends; `dotnet-dump` cho heap snapshot và retention evidence.

## 4. Practical implementation

Quan sát process:

```bash
dotnet-counters monitor --process-id <PID> System.Runtime
```

Capture dump khi memory cao:

```bash
dotnet-dump collect --process-id <PID>
dotnet-dump analyze <dump-file>
```

Trong analyzer:

```text
> dumpheap -stat
> dumpheap -type MyNamespace.CachedItem
> gcroot <object-address>
```

`gcroot` trả lời câu hỏi quan trọng: object nào đang giữ object này sống?

## 5. Real production scenario

API memory tăng 200 MB mỗi giờ. Gen 2 heap tăng đều; request rate ổn. Dump cho thấy millions of DTOs reachable từ singleton dictionary không có eviction. Root cause không phải GC “không chạy”, mà ownership policy của cache sai.

## 6. Failure scenario & troubleshooting

**Symptom** → working set tăng tới container limit rồi OOM/restart.  
**Measure** → Gen 2/LOH size và GC counters tăng theo thời gian.  
**Localize** → managed heap chiếm phần lớn growth.  
**Hypothesis** → long-lived collection giữ objects.  
**Test** → compare two dumps và inspect dominant types/roots.  
**Change** → bounded cache/eviction và ownership fix.  
**Measure again** → heap đạt plateau dưới sustained load.

## 7. Common mistakes

Gọi `GC.Collect()` như fix; chỉ nhìn working set; capture một dump nhưng không có baseline; không kiểm tra native memory; dump production chứa sensitive data nhưng xử lý như file log bình thường; tối ưu allocations nhỏ trước khi tìm dominant retained graph.

## 8. Alternatives

`dotnet-gcdump` nhẹ hơn cho managed heap analysis trong một số tình huống. PerfView/Visual Studio profiler phù hợp deeper allocation analysis. Container/platform metrics cho system view nhưng không chỉ ra object roots.

## 9. Trade-offs

### Advantages

Evidence trực tiếp về heap và retention roots; tránh đoán mò.

### Costs / Risks

Dump lớn, capture có operational impact và chứa dữ liệu nhạy cảm; analysis cần hiểu GC/object graph.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu reachable object không bị GC thu hồi.

### Middle

Đọc runtime counters và heap statistics.

### Senior

Phân biệt allocation pressure, retention leak, LOH và native growth; dùng roots để chứng minh hypothesis.

### Technical Lead / Architect

Thiết kế memory budgets, safe dump procedure, alerting và load verification; tránh restart-only operations.

## 11. Key takeaway

- Managed leak thường là retention bug, không phải GC quên free.
- Tìm root giữ object sống trước khi sửa.
- Fix phải được xác nhận bằng sustained-load measurements.

# 10. CSRF + `SameSite`: bảo vệ cookie-authenticated ASP.NET Core applications

## 1. What is it?

Cross-Site Request Forgery (CSRF) lợi dụng việc browser tự động gửi authentication cookie tới target site khi request được khởi tạo từ site khác. Attacker không cần đọc cookie; họ cần khiến browser của victim gửi state-changing request đã authenticated.

`SameSite` là cookie control giúp giới hạn cross-site cookie sending, nhưng không nên được hiểu như toàn bộ CSRF strategy trong mọi topology.

## 2. Why does it exist?

Cookie authentication có ambient authority: browser tự attach credential. Nếu endpoint thay đổi state chỉ dựa trên cookie và không xác minh request intent, malicious page có thể trigger action bằng credential của victim.

Bearer token trong explicit `Authorization` header có threat model khác vì third-party page không tự có token, nhưng XSS/token storage risks vẫn tồn tại.

## 3. How does it work?

```text
Victim logged into app -> auth cookie stored
Victim visits attacker site
Attacker causes POST -> target app
Browser may attach cookie
Target sees authenticated request
```

Anti-forgery token yêu cầu một giá trị attacker không thể chỉ khiến browser tự attach theo cách cookie được attach. Server validate token + cookie/session relationship.

## 4. Practical implementation

Với ASP.NET Core form/MVC flows, dùng antiforgery support của framework. Với custom endpoints, configure explicit strategy thay vì tắt validation để “fix 400”.

Cookie policy cần cân nhắc deployment:

```csharp
builder.Services.ConfigureApplicationCookie(options =>
{
    options.Cookie.HttpOnly = true;
    options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
    options.Cookie.SameSite = SameSiteMode.Lax;
});
```

`SameSite=None` yêu cầu `Secure` và thường xuất hiện ở cross-site identity/integration flows; thay đổi nó cần test authentication redirects thực tế.

## 5. Real production scenario

Admin portal dùng cookie auth. Endpoint `POST /users/{id}/disable` chỉ check role. Nếu CSRF protection thiếu, admin đang login có thể bị dụ mở malicious page gửi form tới endpoint và browser attach cookie.

## 6. Failure scenario & troubleshooting

**Symptom** → security test chứng minh cross-site form có thể thay đổi state; hoặc sau khi siết `SameSite`, external login callback bị loop.  
**Evidence** → browser DevTools cho biết cookie có/không được gửi và `Sec-Fetch-*`/origin context.  
**Hypothesis** → cookie policy hoặc antiforgery boundary sai.  
**Diagnosis** → map auth flow, same-site/cross-site transitions và state-changing endpoints.  
**Fix** → antiforgery validation + phù hợp `SameSite`/Secure policy; không dùng GET cho mutation.  
**Verification** → legitimate login/action vẫn chạy, cross-site forged request bị reject.

## 7. Common mistakes

Cho rằng CORS chặn CSRF; dùng GET để mutate; set `SameSite=None` toàn bộ cookies cho tiện; tắt antiforgery khi SPA gặp lỗi; nhầm `HttpOnly` là CSRF protection; log antiforgery token/cookie nhạy cảm.

## 8. Alternatives

Bearer-token API không có cùng ambient-cookie CSRF mechanism nhưng cần chống XSS/token leakage. SameSite giúp giảm attack surface; anti-forgery token cho explicit request-intent validation. Origin/Fetch Metadata checks có thể là defense-in-depth.

## 9. Trade-offs

### Advantages

Framework antiforgery + cookie policy phù hợp bảo vệ state-changing cookie-authenticated actions hiệu quả.

### Costs / Risks

Cross-site SSO/embedded scenarios phức tạp hơn; SPA/API integration cần contract rõ; policy quá chặt có thể phá legitimate flows.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser tự gửi cookie là điều tạo CSRF risk.

### Middle

Dùng antiforgery framework support, `Secure`, `HttpOnly`, `SameSite` đúng context.

### Senior

Phân biệt CSRF, CORS và XSS; troubleshoot browser cookie behavior và external identity flows.

### Technical Lead / Architect

Chọn authentication model và trust boundary cho web/API; chuẩn hóa security controls thay vì để từng endpoint tự quyết.

## 11. Key takeaway

- CORS không phải CSRF protection.
- `SameSite` hữu ích nhưng phải phù hợp authentication topology.
- State-changing cookie-authenticated requests cần explicit CSRF defense.
