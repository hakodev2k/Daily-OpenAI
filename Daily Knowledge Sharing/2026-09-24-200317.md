# 1. .NET `Channel<T>`: bounded producer–consumer pipelines và backpressure

## 1. What is it?

`Channel<T>` là asynchronous producer–consumer primitive trong .NET. Mental model: producer ghi work vào một queue có contract rõ ràng; consumer đọc độc lập. Với bounded channel, queue còn là cơ chế backpressure: hệ thống không nhận work vô hạn nhanh hơn khả năng xử lý.

## 2. Why does it exist?

Một `ConcurrentQueue<T>` chỉ giải thread safety; nó không tự cung cấp asynchronous waiting, completion hay capacity control. Nếu producer nhận 50.000 items/s nhưng consumer chỉ xử lý 5.000, unbounded queue biến overload thành memory growth.

## 3. How does it work?

```text
Producer -> [ bounded Channel ] -> Consumer(s)
                 full
                  |
             wait / reject
```

`ChannelWriter<T>` và `ChannelReader<T>` tách hai phía. `BoundedChannelFullMode` quyết định wait/drop behavior.

## 4. Practical implementation

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = false
});

await channel.Writer.WriteAsync(job, ct);

await foreach (var item in channel.Reader.ReadAllAsync(stoppingToken))
    await ProcessAsync(item, stoppingToken);
```

Capacity phải dựa trên acceptable queueing delay và memory footprint, không chọn tùy ý.

## 5. Real production scenario

Một Worker nhận file metadata rồi gọi antivirus/scanner. Blob events đến burst 10x trong vài phút. Bounded channel giữ số work đang chờ trong process hữu hạn thay vì làm pod OOM.

## 6. Failure scenario & troubleshooting

**Symptom** → request producer chậm dần. **Evidence** → channel thường xuyên full, consumer throughput thấp. **Hypothesis** → downstream bottleneck chứ không phải channel bug. **Diagnosis** → đo enqueue wait, queue depth, processing duration. **Fix** → tăng consumer capacity nếu dependency chịu được, scale out hoặc chuyển durable queue. **Verification** → burst load test và dependency saturation test.

## 7. Common mistakes

Dùng unbounded channel cho external traffic; không gọi `Complete`; swallow consumer exception; tăng consumers vô hạn; coi in-memory channel là durable messaging.

## 8. Alternatives

`BackgroundService` + `Channel<T>` phù hợp process-local work. Azure Service Bus phù hợp khi cần durability, cross-instance distribution và recovery sau process crash.

## 9. Trade-offs

### Advantages
Low overhead, async-native, backpressure rõ ràng.

### Costs / Risks
Không durable; process chết thì queued work mất; capacity tuning và shutdown cần thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu producer và consumer có tốc độ khác nhau.

### Middle
Implement bounded channel, cancellation và graceful completion.

### Senior
Đo queueing delay, memory và downstream capacity.

### Technical Lead / Architect
Quyết định process-local pipeline hay durable broker dựa trên loss tolerance và ownership.

## 11. Key takeaway

- Queue thread-safe chưa chắc có backpressure.
- Bounded capacity biến overload thành behavior có kiểm soát.
- `Channel<T>` không thay durable message broker.

# 2. SQL keyset pagination: ổn định latency khi dataset tăng lớn

## 1. What is it?

Keyset pagination lấy trang kế tiếp dựa trên giá trị sort key cuối cùng của trang trước thay vì `OFFSET N`.

## 2. Why does it exist?

`OFFSET 500000` vẫn buộc database tìm/sắp xếp/bỏ qua lượng lớn rows. Cost tăng theo page depth. Với feed hoặc API lớn, user thường chỉ cần next/previous chứ không cần nhảy chính xác tới page 50.001.

## 3. How does it work?

Với sort `(CreatedAt DESC, Id DESC)`, cursor chứa cặp cuối cùng. Query kế tiếp dùng predicate nhỏ hơn cặp đó và `TOP/LIMIT`.

## 4. Practical implementation

```sql
SELECT TOP (50) Id, CreatedAt, Title
FROM Articles
WHERE CreatedAt < @CreatedAt
   OR (CreatedAt = @CreatedAt AND Id < @Id)
ORDER BY CreatedAt DESC, Id DESC;
```

Index phù hợp cần bắt đầu theo sort/access pattern, ví dụ `(CreatedAt DESC, Id DESC)` với includes nếu justified.

## 5. Real production scenario

Audit log có 200 triệu rows. Offset pagination p95 tăng mạnh ở deep pages; cursor pagination giữ seek range nhỏ và latency tương đối ổn định.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate/missing rows giữa pages. **Evidence** → sort chỉ theo non-unique `CreatedAt`. **Hypothesis** → cursor không tạo total deterministic order. **Diagnosis** → tìm timestamps trùng. **Fix** → thêm stable tie-breaker như `Id`. **Verification** → concurrent inserts + pagination integration tests.

## 7. Common mistakes

Cursor chỉ chứa một non-unique field; encode cursor nhưng không validate; dùng keyset cho UI bắt buộc nhảy page number; index không khớp order.

## 8. Alternatives

Offset pagination đơn giản và phù hợp dataset nhỏ/admin UI. Snapshot/export jobs có thể dùng batch ranges riêng.

## 9. Trade-offs

### Advantages
Deep-page performance ổn định hơn; ít scan/skip work.

### Costs / Risks
Không tự nhiên cho random page jumps; cursor contract phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `OFFSET` không miễn phí.

### Middle
Implement deterministic cursor.

### Senior
Đọc execution plan và thiết kế composite index.

### Technical Lead / Architect
Chọn pagination semantics theo product UX và scale thay vì mặc định page number.

## 11. Key takeaway

- Keyset pagination tối ưu access pattern, không chỉ syntax.
- Sort phải deterministic.
- Cursor API là một phần contract cần versioning/validation.

# 3. Elasticsearch aliases: zero-downtime reindexing và schema evolution

## 1. What is it?

Alias là tên logic trỏ tới một hoặc nhiều Elasticsearch indices. Application query alias thay vì hard-code physical index version.

## 2. Why does it exist?

Một số mapping/analyzer changes không thể sửa an toàn in-place. Cần tạo index mới, reindex dữ liệu rồi chuyển traffic mà không downtime.

## 3. How does it work?

```text
search-products -> products-v12
reindex DB/v12 -> products-v13
atomic alias switch
search-products -> products-v13
```

Alias switch có thể thực hiện atomically qua aliases API.

## 4. Practical implementation

Application chỉ biết `products-read`. Deployment pipeline tạo `products-v13`, apply mapping, bulk reindex, validate document counts/query samples rồi swap alias.

## 5. Real production scenario

E-commerce đổi analyzer cho product-name autocomplete. Rebuilding index mất 40 phút nhưng search vẫn phục vụ từ v12; sau validation alias chuyển sang v13.

## 6. Failure scenario & troubleshooting

**Symptom** → sau switch search thiếu products mới. **Evidence** → writes trong reindex window chỉ vào old index. **Hypothesis** → cutover không xử lý delta changes. **Diagnosis** → compare source DB/version timestamps và index counts. **Fix** → CDC/outbox replay hoặc controlled dual-write strategy. **Verification** → reconciliation trước/sau cutover.

## 7. Common mistakes

Chỉ so document count; không test analyzer/query behavior; dual-write không idempotent; xóa old index ngay lập tức; application hard-code versioned index.

## 8. Alternatives

In-place compatible mapping additions đơn giản hơn. Full rebuild từ source of truth thường an toàn hơn biến Elasticsearch thành transactional authority.

## 9. Trade-offs

### Advantages
Rollback/cutover nhanh, schema evolution ít downtime.

### Costs / Risks
Tạm thời cần gấp đôi storage, synchronization complexity và operational tooling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu alias tách logical name khỏi physical index.

### Middle
Thực hiện reindex và alias switch.

### Senior
Thiết kế delta synchronization, validation và rollback.

### Technical Lead / Architect
Xác định source of truth, index lifecycle và ownership của search consistency.

## 11. Key takeaway

- Alias giải deployment indirection, không giải data synchronization.
- Reindex cần validation về semantics, không chỉ row count.
- Giữ rollback window trước khi xóa old index.

# 4. Saga Pattern: business transaction xuyên nhiều service bằng compensation

## 1. What is it?

Saga là chuỗi local transactions giữa nhiều services, với compensating actions khi business flow không thể hoàn tất. Nó không biến distributed operations thành ACID transaction.

## 2. Why does it exist?

Checkout có thể cần Order, Payment, Inventory và Shipping. Giữ distributed lock/transaction xuyên các services làm coupling và availability rất tệ; nhiều external systems cũng không tham gia transaction coordinator.

## 3. How does it work?

```text
Create Order -> Reserve Inventory -> Authorize Payment
                     |
                   fail
                     v
             Cancel Order / release prior work
```

Compensation là business action, không phải byte-level rollback.

## 4. Practical implementation

Persist saga state (`Pending`, `InventoryReserved`, `PaymentAuthorized`, `Failed`) cùng message IDs. Handlers phải idempotent vì messages/retries có thể lặp.

## 5. Real production scenario

Order reserve inventory thành công nhưng payment bị decline. Saga phát `ReleaseInventory` và chuyển order sang `PaymentFailed`; user thấy trạng thái business rõ ràng thay vì half-completed hidden state.

## 6. Failure scenario & troubleshooting

**Symptom** → order kẹt `Pending` hàng giờ. **Evidence** → event đã publish nhưng compensation không hoàn thành. **Hypothesis** → saga state machine thiếu timeout/recovery path. **Diagnosis** → trace correlation + saga state + broker DLQ. **Fix** → timeout transition, retry policy, manual repair tooling. **Verification** → fault injection ở từng step.

## 7. Common mistakes

Gọi compensation là rollback; giả định reverse action luôn thành công; không persist state; không có idempotency; orchestration service trở thành god service.

## 8. Alternatives

Một local database transaction tốt hơn nếu boundary có thể nằm trong một service. Choreography giảm central coordinator nhưng flow khó quan sát khi nhiều steps.

## 9. Trade-offs

### Advantages
Cho phép multi-service business flow chịu partial failure.

### Costs / Risks
Eventual consistency, state-machine complexity, compensation semantics và support tooling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu distributed failure có thể xảy ra giữa bất kỳ hai steps.

### Middle
Implement idempotent handlers/state transitions.

### Senior
Thiết kế compensation, timeout và observability.

### Technical Lead / Architect
Hỏi trước tiên liệu service boundaries có đang làm một transaction đơn giản trở thành distributed transaction không.

## 11. Key takeaway

- Saga quản lý business consistency, không tạo distributed ACID.
- Compensation cũng có thể fail.
- Nếu một DB transaction đủ dùng, Saga là complexity không cần thiết.

# 5. Azure Managed Identity: bỏ credentials khỏi application configuration

## 1. What is it?

Managed Identity cung cấp identity do Azure quản lý cho workload, cho phép lấy Microsoft Entra tokens mà không lưu client secret trong application.

## 2. Why does it exist?

Secrets trong config/CI/CD phải được tạo, phân phối, rotate và có nguy cơ leak. Workload identity chuyển vấn đề từ “giữ password” sang “cấp đúng permission cho identity”.

## 3. How does it work?

```text
App Service / Function / VM
 -> Managed Identity credential
 -> Entra token
 -> Key Vault / Storage / SQL / supported service
```

Authentication không đồng nghĩa authorization; identity vẫn cần RBAC/data-plane permissions phù hợp.

## 4. Practical implementation

```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(new Uri(vaultUri), credential);
```

Local development có thể dùng developer credential; production resolve Managed Identity. Không fallback sang embedded secret âm thầm.

## 5. Real production scenario

App Service đọc Key Vault và Blob Storage. Deployment không còn mang storage key/client secret; RBAC cấp read-only đúng resources cần thiết.

## 6. Failure scenario & troubleshooting

**Symptom** → production nhận 403 dù token lấy được. **Evidence** → authentication success, authorization denied. **Hypothesis** → RBAC scope/role sai. **Diagnosis** → kiểm tra identity object, role assignment, control-plane vs data-plane permission. **Fix** → least-privilege role đúng scope. **Verification** → allowed action pass, disallowed action vẫn fail.

## 7. Common mistakes

Cấp Contributor khi chỉ cần data reader; nhầm system-assigned/user-assigned identity; log access token; nghĩ Managed Identity tự cấp quyền; giữ secret fallback vĩnh viễn.

## 8. Alternatives

Workload identity federation phù hợp CI/CD/Kubernetes scenarios. Client secret/certificate vẫn có use cases nhưng tăng lifecycle burden.

## 9. Trade-offs

### Advantages
Giảm secret distribution/rotation, audit identity rõ hơn.

### Costs / Risks
Cloud dependency, RBAC complexity và local/prod credential differences.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt identity và permission.

### Middle
Dùng `DefaultAzureCredential` và RBAC đúng service.

### Senior
Troubleshoot token audience/scope/RBAC và least privilege.

### Technical Lead / Architect
Chuẩn hóa workload identity và loại long-lived secrets khỏi platform khi khả thi.

## 11. Key takeaway

- Managed Identity loại secret, không loại authorization design.
- 401 và 403 chỉ tới các lớp lỗi khác nhau.
- Least privilege vẫn là yêu cầu cốt lõi.

# 6. Blue-Green deployment với database migration: backward compatibility mới là phần khó

## 1. What is it?

Blue-Green giữ hai application versions/environments để chuyển traffic nhanh. Nhưng nếu cả hai versions chia sẻ database, schema trở thành compatibility boundary.

## 2. Why does it exist?

Switch application traffic có thể vài giây; database migration thường không rollback dễ. Nếu Green đổi schema khiến Blue không chạy được, “instant rollback” chỉ là ảo tưởng.

## 3. How does it work?

Dùng expand/contract:

```text
1. Expand schema: add compatible column/table
2. Deploy code supporting old + new
3. Backfill/migrate data
4. Switch traffic
5. Observe
6. Contract old schema in later release
```

## 4. Practical implementation

Thay vì rename column trực tiếp, thêm column mới nullable, deploy dual-read/write có kiểm soát, backfill, chuyển reads, rồi xóa old column sau khi rollback window đóng.

## 5. Real production scenario

Green đổi `Customer.Name` thành `DisplayName`. Direct rename làm Blue fail ngay khi rollback. Expand/contract cho phép cả hai binaries cùng tồn tại trong deployment window.

## 6. Failure scenario & troubleshooting

**Symptom** → rollback application thành công nhưng API 500. **Evidence** → old binary query column đã bị drop. **Hypothesis** → destructive migration phá backward compatibility. **Diagnosis** → compare binary expectations với live schema. **Fix** → restore compatible schema/data hoặc forward-fix. **Verification** → compatibility test cả N và N-1 against expanded schema.

## 7. Common mistakes

Chạy destructive migration trước traffic switch; coi ORM migration rollback là production recovery plan; không tính long-running backfill; deploy app và schema như một atomic artifact tưởng tượng.

## 8. Alternatives

Rolling/Canary cũng cần schema compatibility khi versions overlap. Maintenance window có thể đơn giản hơn cho low-availability internal systems.

## 9. Trade-offs

### Advantages
Rollback application nhanh và giảm release risk.

### Costs / Risks
Temporary schema duplication, migration choreography và cleanup discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu app version và schema version có lifecycle khác nhau.

### Middle
Viết additive migrations.

### Senior
Thiết kế N/N-1 compatibility và backfill.

### Technical Lead / Architect
Định nghĩa release protocol, rollback boundary và thời điểm destructive changes được phép.

## 11. Key takeaway

- Blue-Green không tự làm database rollback-safe.
- Expand/contract là compatibility strategy, không chỉ migration trick.
- Test rollback với schema thật của release mới.

# 7. Akamai/CDN stale content: `Cache-Control`, purge và ownership của freshness

## 1. What is it?

CDN edge cache giữ response gần users. Stale content xuất hiện khi edge representation cũ hơn freshness mà business chấp nhận.

## 2. Why does it exist?

Caching đổi freshness lấy latency/origin protection. Nếu không định nghĩa ai quyết định TTL, cache key và invalidation, cùng URL có thể phục vụ dữ liệu cũ lâu hơn dự kiến.

## 3. How does it work?

```text
Browser -> Akamai edge -> Origin/App -> CMS/API
             |
           cached object
```

`Cache-Control`, surrogate/edge rules, query-string handling và purge cùng quyết định lifecycle.

## 4. Practical implementation

Static versioned assets có thể dùng long TTL + immutable naming. HTML/content động nên dùng TTL phù hợp business freshness và explicit purge khi publish nếu cần near-immediate update.

## 5. Real production scenario

CMS editor publish legal banner mới nhưng một region vẫn thấy bản cũ. Origin trả đúng content; Akamai edge vẫn giữ object vì TTL/cache key policy.

## 6. Failure scenario & troubleshooting

**Symptom** → chỉ một số users/regions thấy stale page. **Evidence** → origin fresh, edge headers cho thấy cache hit/age cao. **Hypothesis** → edge cache chưa invalidated hoặc key mismatch. **Diagnosis** → inspect response headers, cache key variables và purge status. **Fix** → purge đúng object/policy, sau đó sửa ownership rule. **Verification** → requests qua nhiều POPs và browser-cache bypass.

## 7. Common mistakes

Purge toàn site cho một item; cache personalized response; bỏ qua browser cache; query parameter làm fragment cache key; TTL dài nhưng không có invalidation workflow.

## 8. Alternatives

Versioned URLs tránh purge cho static assets. Short TTL đơn giản hơn nhưng tăng origin load. `stale-while-revalidate` hữu ích khi freshness budget cho phép.

## 9. Trade-offs

### Advantages
Latency thấp, origin shielding, global scale.

### Costs / Risks
Freshness complexity, purge dependency và debugging nhiều cache layers.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt browser cache, CDN cache và origin.

### Middle
Đọc caching headers và reproduce edge behavior.

### Senior
Thiết kế cache key/TTL/invalidation theo content semantics.

### Technical Lead / Architect
Định nghĩa freshness SLO và ownership giữa CMS, app và CDN teams.

## 11. Key takeaway

- Cache invalidation là product correctness concern khi content có freshness requirement.
- Diagnose từng cache layer, không đoán.
- Versioned assets và explicit content invalidation giải các bài toán khác nhau.

# 8. JWT signing-key rotation: validation phải chịu được key overlap

## 1. What is it?

Signing-key rotation thay cryptographic key dùng để ký tokens. Validators thường lấy public keys qua JWKS/discovery và chọn key theo `kid`.

## 2. Why does it exist?

Keys không nên tồn tại vô hạn. Rotation hỗ trợ hygiene, certificate expiry và incident response. Nhưng access tokens ký bằng key cũ vẫn hợp lệ tới khi hết hạn.

## 3. How does it work?

```text
Issuer publishes K1 + K2
new tokens -> signed K2
old valid tokens -> still verify with K1
TTL passes
issuer removes K1
```

Overlap window phải lớn đủ cho token lifetime/cache propagation.

## 4. Practical implementation

ASP.NET Core `JwtBearer` nên dùng issuer metadata/authority đúng thay vì hard-code một signing key. Cache refresh cần xử lý unknown `kid` an toàn và không disable signature validation.

## 5. Real production scenario

Identity provider rotate certificate. Một API instance có stale JWKS cache và bắt đầu trả 401 cho tokens ký K2 trong khi instance khác hoạt động.

## 6. Failure scenario & troubleshooting

**Symptom** → 401 tăng đột ngột chỉ với tokens mới. **Evidence** → token `kid` không tồn tại trong validator cache. **Hypothesis** → key rotation/cache refresh. **Diagnosis** → compare token header, issuer JWKS và metadata cache. **Fix** → refresh metadata theo supported mechanism, kiểm tra network/issuer config. **Verification** → validate cả token K1 còn sống và K2 mới.

## 7. Common mistakes

Hard-code certificate; remove old key ngay khi new key active; log raw JWT; tắt signature validation để “fix”; nhầm `aud`, `iss`, expiry errors với key issue.

## 8. Alternatives

Opaque/reference tokens chuyển validation về authorization server nhưng thêm network/cache dependency. JWT vẫn phù hợp khi local validation là yêu cầu.

## 9. Trade-offs

### Advantages
Rotation giảm long-lived key risk.

### Costs / Risks
Metadata caching, overlap và incident choreography phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu JWT phải verify signature/issuer/audience/expiry.

### Middle
Cấu hình authority và đọc `kid`/JWKS.

### Senior
Troubleshoot rotation/cache và token lifetime interactions.

### Technical Lead / Architect
Định nghĩa key lifecycle, emergency rotation và dependency resilience cho identity platform.

## 11. Key takeaway

- Rotation cần overlap với token lifetime.
- Unknown `kid` là diagnostic signal, không phải lý do bỏ validation.
- Identity metadata availability là production dependency.

# 9. Vue/TypeScript request cancellation: ngăn stale response ghi đè state mới

## 1. What is it?

Request cancellation dùng `AbortController` để hủy HTTP request không còn relevant. Mental model: UI intent thay đổi nhanh hơn network; response cũ không được phép thắng state mới.

## 2. Why does it exist?

Search-as-you-type có thể gửi `q=a`, `q=ab`, `q=abc`. Network không đảm bảo response về cùng thứ tự. `a` về cuối có thể overwrite kết quả `abc`.

## 3. How does it work?

```text
input abc -> abort previous controller
          -> fetch abc with new signal
old request -> AbortError / ignored
```

Cancellation giảm wasted work phía client/network; server chỉ dừng được nếu cancellation thực sự propagate và operation hỗ trợ.

## 4. Practical implementation

```typescript
let controller: AbortController | undefined;

async function search(q: string) {
  controller?.abort();
  controller = new AbortController();

  try {
    results.value = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
      signal: controller.signal
    }).then(r => r.json());
  } catch (e) {
    if (!(e instanceof DOMException && e.name === 'AbortError')) throw e;
  }
}
```

Debounce và cancellation có thể dùng cùng nhau nhưng giải hai vấn đề khác nhau.

## 5. Real production scenario

Automotive marketplace filter model/year liên tục. Request cũ chậm do cache miss và về sau request mới; cancellation/sequence guard ngăn UI hiển thị inventory sai filter.

## 6. Failure scenario & troubleshooting

**Symptom** → UI “nhảy ngược” về dữ liệu cũ. **Evidence** → Network tab cho thấy response completion out of order. **Hypothesis** → race giữa requests. **Diagnosis** → log request sequence/filter state. **Fix** → abort previous request hoặc chỉ commit latest sequence. **Verification** → throttle network trong DevTools và thay filter nhanh.

## 7. Common mistakes

Coi AbortError là application error; debounce nhưng vẫn để old in-flight response commit; không cancel khi component unmount; server thực hiện expensive work dù client disconnect mà không propagate cancellation.

## 8. Alternatives

Sequence/version guard hữu ích khi transport không cancel được. Data-fetching libraries có request lifecycle abstractions nhưng vẫn cần hiểu stale-state semantics.

## 9. Trade-offs

### Advantages
UI correctness tốt hơn, giảm unnecessary traffic/work.

### Costs / Risks
Lifecycle complexity và cần phân biệt cancel với genuine failure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu responses có thể về sai thứ tự.

### Middle
Implement abort + loading/error state đúng.

### Senior
Kết nối frontend cancellation với API cancellation và observability.

### Technical Lead / Architect
Chuẩn hóa async-state patterns để tránh race bugs xuyên frontend codebase.

## 11. Key takeaway

- Request order không phải response order.
- Debounce giảm số calls; cancellation xử lý obsolete in-flight calls.
- UI chỉ nên commit dữ liệu còn relevant với current intent.

# 10. RAG evaluation: đo retrieval và answer quality thay vì “demo trông có vẻ đúng”

## 1. What is it?

RAG evaluation tách chất lượng hệ thống thành ít nhất hai lớp: retrieval có lấy đúng evidence không, và model có tạo answer grounded/correct từ evidence đó không.

## 2. Why does it exist?

Nếu answer sai, chỉ nhìn final text không biết lỗi nằm ở chunking/index/query, ranking hay generation. Tuning prompt không sửa được missing evidence.

## 3. How does it work?

```text
Question
 -> Retriever -> ranked chunks
      |             |
 retrieval metrics  v
                LLM answer
                    |
          groundedness/correctness
```

Evaluation set nên chứa representative questions, expected evidence và acceptance criteria.

## 4. Practical implementation

Lưu cho mỗi test case: question, source document IDs/chunks kỳ vọng, reference facts và constraints. Đo retrieval recall@k/precision-like signals, sau đó đánh giá answer correctness, citation support và refusal khi evidence thiếu.

Deterministic checks nên kiểm tra schema, required citations, forbidden unsupported claims. Model-as-judge có thể bổ sung nhưng không phải source of truth duy nhất.

## 5. Real production scenario

Internal engineering assistant trả lời sai package version. Investigation cho thấy correct document chưa bao giờ vào top-10 retrieval; đổi system prompt không giúp. Sau khi sửa metadata filtering/ranking, grounded answer cải thiện.

## 6. Failure scenario & troubleshooting

**Symptom** → offline score cao nhưng users vẫn phàn nàn. **Evidence** → evaluation set chỉ có câu hỏi dễ/giống demo. **Hypothesis** → benchmark không đại diện production distribution. **Diagnosis** → sample failed real queries, classify retrieval/generation errors. **Fix** → mở rộng dataset và segment metrics theo query type. **Verification** → regression suite + controlled production evaluation.

## 7. Common mistakes

Chỉ đo “LLM answer similarity”; không version dataset/index/prompt/model; judge chính model đang được test; không test no-answer cases; thay nhiều variables cùng lúc.

## 8. Alternatives

Search-only systems cần relevance evaluation mà không có generation layer. Fine-tuning giải behavior/style khác với retrieval freshness và không thay RAG khi knowledge thay đổi thường xuyên.

## 9. Trade-offs

### Advantages
Biến RAG tuning thành engineering loop có evidence và regression protection.

### Costs / Risks
Dataset curation tốn công; subjective criteria; model judge có bias/cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu retrieval failure khác hallucination sau retrieval.

### Middle
Tạo evaluation cases và log retrieved context.

### Senior
Phân rã metrics, segment failures và chạy regression experiments.

### Technical Lead / Architect
Định nghĩa quality gates, deterministic boundaries, data governance và acceptable failure modes trước production rollout.

## 11. Key takeaway

- Đánh giá retrieval và generation riêng.
- Production failures phải quay lại evaluation set.
- Prompt tuning không thể bù cho evidence không được retrieve.
