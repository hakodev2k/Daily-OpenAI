# 1. C# `TimeProvider`: làm time-dependent logic testable thay vì gọi `DateTime.UtcNow` khắp nơi

## 1. What is it?

`TimeProvider` là abstraction thời gian trong modern .NET. Mental model: business logic không nên phụ thuộc trực tiếp vào wall clock toàn cục; nó nên nhận một nguồn thời gian có thể kiểm soát. `TimeProvider.System` dùng clock thật, còn tests có thể cung cấp fake time.

## 2. Why does it exist?

Logic như token expiry, SLA deadline, cache TTL hay scheduled eligibility thường khó test nếu gọi `DateTime.UtcNow` trực tiếp. Test phải chờ thời gian thật hoặc thao tác dữ liệu bằng các timestamp mong manh. Abstraction cho phép thời gian trở thành dependency rõ ràng.

## 3. How does it work?

Application inject `TimeProvider`; production đăng ký `TimeProvider.System`. Code lấy `GetUtcNow()` hoặc dùng APIs hỗ trợ provider. Test kiểm soát provider và dịch clock theo ý muốn. Boundary quan trọng là phân biệt wall-clock time với elapsed time; đo duration nên dùng timestamp/monotonic semantics thay vì trừ local `DateTime` tùy tiện.

## 4. Practical implementation

```csharp
public sealed class ApprovalPolicy(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset submittedAt, TimeSpan ttl)
        => timeProvider.GetUtcNow() >= submittedAt + ttl;
}

builder.Services.AddSingleton(TimeProvider.System);
```

Test có thể truyền fake implementation cố định tại một instant và advance clock mà không `Task.Delay`.

## 5. Real production scenario

Approval request hết hạn sau 48 giờ. Service chạy ở nhiều regions và containers. Lưu instant dưới dạng UTC/`DateTimeOffset`, dùng một clock abstraction cho policy, còn UI chuyển sang local timezone khi hiển thị.

## 6. Failure scenario & troubleshooting

**Symptom** → test expiry thỉnh thoảng fail gần boundary. **Evidence** → expected timestamp được tạo trước khi method gọi `UtcNow` lần nữa. **Hypothesis** → test phụ thuộc clock thật. **Diagnosis** → trace hai timestamps chênh milliseconds. **Fix** → inject `TimeProvider` và freeze time. **Verification** → chạy test lặp nhiều lần, kể cả đúng boundary, kết quả deterministic.

## 7. Common mistakes

Dùng local time cho persistence; gọi `DateTime.Now` ở domain code; tạo custom `IClock` dù platform abstraction đã đủ; dùng wall clock để benchmark duration; mock static clock bằng framework phức tạp.

## 8. Alternatives

Một custom `IClock` nhỏ vẫn hợp với legacy .NET hoặc khi domain cần API cực hẹp. `Stopwatch` phù hợp đo elapsed duration. Database/server timestamps phù hợp khi database phải là authority của một transaction-specific fact.

## 9. Trade-offs

### Advantages

Deterministic tests, dependency rõ ràng, giảm timezone/clock coupling.

### Costs / Risks

Thêm dependency vào constructors; abstraction bị lạm dụng nếu mọi lớp đều tự xử lý time semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt UTC instant, local display time và elapsed duration.

### Middle

Inject `TimeProvider` cho expiry/deadline logic và viết boundary tests.

### Senior

Xác định clock authority, persistence format và semantics khi hệ thống phân tán.

### Technical Lead / Architect

Chuẩn hóa time policy toàn hệ thống: UTC storage, conversion boundary, test strategy và nơi cần external authority.

## 11. Key takeaway

- Time là dependency khi nó ảnh hưởng business decision.
- Dùng UTC/`DateTimeOffset` cho instants; local timezone thuộc presentation/business rule cụ thể.
- Test time-dependent logic bằng controllable clock, không bằng sleep.

# 2. ASP.NET Core Request Timeouts: deadline là capacity boundary, không chỉ UX timeout

## 1. What is it?

Request timeout đặt deadline cho thời gian một HTTP request được phép chiếm application resources. Trong ASP.NET Core, timeout hữu ích nhất khi cancellation được propagate xuyên application, database và outbound HTTP calls.

## 2. Why does it exist?

Một request client đã bỏ cuộc nhưng backend vẫn chạy 60 giây tiếp tục giữ connection, memory và concurrency slot là wasted work. Khi dependency chậm, hàng nghìn request kiểu này có thể tạo cascading failure.

## 3. How does it work?

```text
Client deadline
  -> reverse proxy timeout
    -> ASP.NET request timeout
      -> CancellationToken
        -> EF Core / HttpClient / downstream
```

Timeout ở mỗi layer phải có budget hợp lý. Layer phía trong nên kết thúc trước layer phía ngoài để còn thời gian tạo controlled response/telemetry.

## 4. Practical implementation

```csharp
builder.Services.AddRequestTimeouts(options =>
{
    options.AddPolicy("api", TimeSpan.FromSeconds(5));
});

app.UseRequestTimeouts();

app.MapGet("/orders/{id:int}", async (
    int id, AppDbContext db, CancellationToken ct) =>
    await db.Orders.AsNoTracking().SingleOrDefaultAsync(x => x.Id == id, ct))
   .WithRequestTimeout("api");
```

Outbound `HttpClient` và repository methods cũng phải nhận cancellation/deadline phù hợp.

## 5. Real production scenario

Product API có SLO p95 800 ms và gọi reviews service. Reviews service treo 20 giây. Request budget 2 giây cho phép API fallback phần reviews thay vì giữ worker resources đến proxy timeout 30 giây.

## 6. Failure scenario & troubleshooting

**Symptom** → gateway trả 504 nhưng backend vẫn có queries chạy lâu sau đó. **Evidence** → traces kéo dài vượt gateway timeout. **Hypothesis** → cancellation không propagate. **Diagnosis** → repository dùng `CancellationToken.None` và outbound client có timeout dài. **Fix** → propagate token/deadline và định nghĩa dependency budgets. **Verification** → fault injection cho downstream latency; spans kết thúc gần deadline và resource usage ổn định.

## 7. Common mistakes

Đặt timeout nhưng bỏ token; retry sau timeout mà không còn budget; mọi endpoint dùng cùng deadline; timeout quá thấp cho upload/export; nhầm timeout với circuit breaker.

## 8. Alternatives

Long-running work nên chuyển sang queue + job status thay vì giữ HTTP request. Streaming phù hợp khi client cần incremental results. Circuit Breaker xử lý dependency health ở nhiều requests, không thay per-request deadline.

## 9. Trade-offs

### Advantages

Giới hạn wasted work, bảo vệ capacity và làm latency contract rõ hơn.

### Costs / Risks

Deadline sai có thể hủy valid work; cancellation propagation cần toàn call chain hợp tác.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không tự động kill mọi downstream operation.

### Middle

Propagate `CancellationToken` xuyên EF Core và HTTP calls.

### Senior

Thiết kế timeout budget, retry budget và fallback dựa trên traces/SLO.

### Technical Lead / Architect

Quyết định endpoint nào synchronous, endpoint nào phải asynchronous workflow và budget giữa gateway/services/databases.

## 11. Key takeaway

- Deadline là reliability/capacity control.
- Timeout chỉ hiệu quả khi cancellation được propagate.
- Không retry nếu deadline budget đã hết.

# 3. EF Core `AsNoTrackingWithIdentityResolution`: read model lớn giữa tracking cost và duplicate objects

## 1. What is it?

`AsNoTrackingWithIdentityResolution()` không đưa entities vào `DbContext` change tracker lâu dài nhưng vẫn bảo đảm cùng primary key trong một query được materialize thành cùng object instance. Nó nằm giữa full tracking và plain `AsNoTracking()`.

## 2. Why does it exist?

Read-only query có joins/includes có thể trả cùng entity nhiều lần. Plain no-tracking giảm tracking overhead nhưng có thể tạo duplicate object instances. Full tracking giải quyết identity nhưng mang state-management cost không cần thiết cho read path.

## 3. How does it work?

EF Core dùng một temporary identity map trong lúc materialization. Khi query hoàn tất, map đó không trở thành tracked state của context. Database I/O không tự giảm; lợi ích nằm ở object graph materialization semantics.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .AsNoTrackingWithIdentityResolution()
    .Include(x => x.Customer)
    .Include(x => x.Items)
    .Where(x => x.CreatedAt >= from)
    .ToListAsync(ct);
```

Nếu endpoint chỉ cần DTO, projection thường còn tốt hơn vì giảm columns và graph materialization.

## 5. Real production scenario

Admin report tải orders cùng customer references. Nhiều orders thuộc cùng customer. Identity resolution tránh tạo hàng nghìn duplicate `Customer` instances nhưng endpoint không cần update entities.

## 6. Failure scenario & troubleshooting

**Symptom** → memory vẫn cao dù chuyển từ tracking sang identity-resolution no-tracking. **Evidence** → SQL trả object graph cực lớn và nhiều columns. **Hypothesis** → vấn đề là result cardinality, không phải tracker. **Diagnosis** → đo generated SQL, row count và allocations. **Fix** → projection, pagination hoặc split query phù hợp. **Verification** → benchmark allocation và DB payload trước/sau.

## 7. Common mistakes

Coi no-tracking là query optimization toàn diện; dùng entities cho API DTO; `Include` graph không giới hạn; chọn identity resolution khi không có duplicates; cố attach graph trở lại để update.

## 8. Alternatives

`AsNoTracking()` đơn giản nhất cho read-only projections/entities không cần identity semantics. Full tracking cho update workflow. DTO projection thường tối ưu nhất cho API read models.

## 9. Trade-offs

### Advantages

Không giữ tracking state lâu dài nhưng giảm duplicate object instances trong query graph.

### Costs / Risks

Temporary identity map vẫn có CPU/memory cost; không giảm SQL payload; có thể che việc read model đang quá rộng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu tracking phục vụ update, không phải mọi read.

### Middle

Chọn tracking mode và projection theo endpoint.

### Senior

Đo materialization, row multiplication và memory thay vì chỉ nhìn SQL duration.

### Technical Lead / Architect

Thiết kế read models explicit thay vì để persistence entity graph trở thành API contract.

## 11. Key takeaway

- Tracking mode và query shape là hai vấn đề khác nhau.
- Identity resolution hữu ích khi duplicate entities thực sự xuất hiện.
- Projection thường là lựa chọn tốt nhất cho read API có contract rõ.

# 4. PostgreSQL JSONB + GIN index: schema flexibility vẫn cần access-pattern discipline

## 1. What is it?

`jsonb` lưu JSON ở dạng binary normalized cho query/indexing. GIN index có thể index các keys/values hoặc paths phù hợp để containment queries tránh full table scan. Nó cho phép một phần schema linh hoạt trong relational database.

## 2. Why does it exist?

Một số attributes thay đổi theo product/category hoặc integration payload không đáng tạo hàng trăm nullable columns. Nhưng đưa toàn entity vào JSON làm mất nhiều lợi ích relational như constraints, joins và typed schema.

## 3. How does it work?

Query `metadata @> '{"color":"black"}'` có thể dùng GIN index nếu operator/index class phù hợp. Planner vẫn dựa trên selectivity/statistics/cost; index không đảm bảo luôn được chọn.

## 4. Practical implementation

```sql
CREATE TABLE products (
    id bigint PRIMARY KEY,
    sku text NOT NULL UNIQUE,
    name text NOT NULL,
    metadata jsonb NOT NULL DEFAULT '{}'
);

CREATE INDEX ix_products_metadata_gin
ON products USING gin (metadata jsonb_path_ops);

SELECT id, sku, name
FROM products
WHERE metadata @> '{"color":"black"}';
```

Core invariants như `sku`, price ownership hay foreign keys vẫn nên là typed columns/tables.

## 5. Real production scenario

Automotive marketplace có attributes khác nhau theo vehicle category. Stable searchable fields nằm ở relational columns; sparse category-specific attributes nằm trong JSONB và chỉ các access patterns quan trọng mới được index.

## 6. Failure scenario & troubleshooting

**Symptom** → write latency tăng và index phình lớn. **Evidence** → một generic GIN index chứa huge metadata documents, nhiều keys không bao giờ query. **Hypothesis** → indexing quá rộng. **Diagnosis** → inspect index size, query plans và workload. **Fix** → expression/partial indexes cho paths thực sự dùng hoặc đưa hot fields thành columns. **Verification** → đo write cost, index size và query p95.

## 7. Common mistakes

Dùng JSONB để né schema design; không validate shape; index toàn document mặc dù chỉ query một field; kỳ vọng foreign-key semantics bên trong JSON; dùng dynamic paths khiến query khó tối ưu.

## 8. Alternatives

Typed columns tốt cho stable schema và constraints. Child tables/EAV có trade-offs riêng. MongoDB phù hợp nếu document model là primary access model chứ không chỉ vài flexible attributes.

## 9. Trade-offs

### Advantages

Schema flexibility, atomic storage cùng row, powerful containment/path queries.

### Costs / Risks

Weaker constraints bên trong JSON, index/storage overhead, query complexity và dễ biến database thành schema-less dumping ground.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

JSONB không có nghĩa là không cần schema.

### Middle

Viết containment query và kiểm tra `EXPLAIN`.

### Senior

Đo selectivity, index size, write amplification và data validation.

### Technical Lead / Architect

Quyết định boundary giữa relational core và flexible attributes dựa trên invariants/access patterns.

## 11. Key takeaway

- JSONB là hybrid modeling tool, không phải escape hatch khỏi schema design.
- Index theo workload thực tế.
- Stable business invariants vẫn hưởng lợi từ relational schema.

# 5. Event schema evolution: thay đổi integration event mà không phá consumers đang chạy

## 1. What is it?

Event schema evolution là kỷ luật thay đổi message contract khi producers và consumers được deploy độc lập. Mental model: một event đã publish là external contract theo thời gian; producer mới phải coexist với consumers cũ trong một khoảng deployment window.

## 2. Why does it exist?

Distributed deployment không atomic. Nếu producer rename/remove field ngay lập tức, consumer cũ có thể fail và đưa messages vào DLQ. Event history/replay còn kéo dài compatibility window hơn REST request thông thường.

## 3. How does it work?

Ưu tiên additive changes: thêm optional field, consumer tolerant với fields chưa biết. Breaking semantic change có thể cần event version mới. Producer ownership không đồng nghĩa producer được tự do thay contract mà không migration plan.

## 4. Practical implementation

```csharp
public sealed record OrderPlacedV2(
    Guid OrderId,
    decimal Total,
    string Currency,
    string? SalesChannel); // additive, optional for transition
```

Consumer không nên deserialize theo strict assumption rằng mọi producer version đều có `SalesChannel` ngay lập tức.

## 5. Real production scenario

Order service thêm `SalesChannel`. Analytics consumer nâng cấp sau hai ngày. Additive optional field cho phép old consumer tiếp tục xử lý; sau migration window, downstream mới bắt đầu dựa vào field.

## 6. Failure scenario & troubleshooting

**Symptom** → DLQ tăng ngay sau producer deployment. **Evidence** → deserialization exceptions “required property missing”. **Hypothesis** → breaking contract. **Diagnosis** → compare payload versions và consumer deployment. **Fix** → rollback producer hoặc publish compatible/versioned event; replay DLQ sau khi consumer sửa. **Verification** → contract tests chạy producer schema với supported consumer versions.

## 7. Common mistakes

Rename field như refactor nội bộ; reuse cùng event name cho semantic khác; publish persistence entity trực tiếp; không lưu schema/version metadata; cho consumer phụ thuộc fields không thuộc contract.

## 8. Alternatives

Synchronous REST cũng cần version compatibility nhưng messages có replay/retention làm temporal coupling dài hơn. Schema registry hữu ích ở ecosystem lớn; simple JSON contracts + disciplined contract tests đủ cho hệ thống nhỏ.

## 9. Trade-offs

### Advantages

Independent deployment, safer rollout, replayability và giảm coordinated releases.

### Costs / Risks

Contract governance, duplicated versions, migration windows và test matrix tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Event là public contract, không phải DTO nội bộ.

### Middle

Thực hiện additive change và tolerant consumer.

### Senior

Thiết kế versioning, replay và contract tests.

### Technical Lead / Architect

Định nghĩa ownership, compatibility policy, retention và deprecation process cho event ecosystem.

## 11. Key takeaway

- Distributed deployment biến schema evolution thành architecture concern.
- Additive changes thường an toàn hơn rename/remove.
- Contract tests phải bảo vệ compatibility, không chỉ current producer/current consumer.

# 6. Azure Monitor alert design: cảnh báo theo user impact thay vì mọi metric spike

## 1. What is it?

Alert design biến telemetry thành actionable operational signal. Một alert tốt nói rằng service có khả năng vi phạm reliability objective và cần hành động; nó không đơn giản là “CPU vượt 70%”.

## 2. Why does it exist?

Nếu mọi anomaly đều page team, alert fatigue làm engineer bỏ qua cả incident thật. Ngược lại, chỉ nhìn infrastructure metrics có thể bỏ lỡ lỗi user-facing khi CPU vẫn bình thường.

## 3. How does it work?

```text
Application Insights / Azure resources
 -> metrics + logs + traces
 -> alert rule
 -> action group
 -> responder
 -> runbook / diagnosis
```

Ưu tiên symptoms như error rate, p95 latency, failed dependency rate, queue age và SLO burn; resource signals hỗ trợ diagnosis/capacity alerts.

## 4. Practical implementation

Ví dụ policy: page khi `5xx rate > 5%` trong 10 phút với đủ request volume; warning khi queue oldest-message age vượt processing SLO. Alert payload phải có environment, service, dashboard/runbook và correlation context.

```text
Signal: requests/failed ÷ requests/count
Window: 10m
Condition: > 5%
Scope: production checkout API
Action: on-call action group
```

## 5. Real production scenario

CPU tăng 85% trong batch window nhưng p95 và error rate vẫn đạt SLO: không cần page. Payment dependency error tăng 20% trong khi CPU 30%: phải alert vì user impact rõ ràng.

## 6. Failure scenario & troubleshooting

**Symptom** → on-call nhận hàng trăm alerts cho cùng incident. **Evidence** → CPU, memory, pod count, dependency timeout và 5xx đều page riêng. **Hypothesis** → alerts theo component symptoms không có hierarchy. **Diagnosis** → map alerts về một failure chain. **Fix** → page theo service/user impact; resource alerts downgrade hoặc correlate. **Verification** → game day tạo dependency outage và kiểm tra số actionable pages.

## 7. Common mistakes

Static threshold không baseline; không có minimum traffic; alert trên averages; không link runbook; alert tự resolve/re-fire liên tục; page cho dev/test; metric cardinality vô kiểm soát.

## 8. Alternatives

Log query alerts tốt cho semantic events; metric alerts nhanh/rẻ cho numeric signals; SLO burn-rate alerts phù hợp reliability management trưởng thành. Không phải mọi dashboard chart cần alert.

## 9. Trade-offs

### Advantages

Phát hiện incident sớm, giảm MTTR, operational ownership rõ.

### Costs / Risks

Rules cần tuning; telemetry/retention có cost; alert noise làm giảm reliability của chính response process.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt telemetry với alert.

### Middle

Tạo alert có scope/window/action rõ và link dashboard.

### Senior

Thiết kế symptom-based alerts, burn rate và dependency correlation.

### Technical Lead / Architect

Định nghĩa SLO, paging policy, ownership và telemetry cost như một phần architecture.

## 11. Key takeaway

- Page theo user impact/reliability risk, không theo mọi spike.
- Alert phải dẫn tới hành động cụ thể.
- Logs + metrics + traces hỗ trợ diagnosis; alert là decision layer.

# 7. Canary deployment: giảm blast radius nhưng không thay thế backward compatibility

## 1. What is it?

Canary deployment đưa version mới tới một phần nhỏ traffic/instances trước khi mở rộng. Mục tiêu là quan sát production behavior với blast radius hạn chế.

## 2. Why does it exist?

Tests/staging không mô phỏng hoàn toàn production traffic, data distribution và dependencies. Deploy 100% ngay lập tức biến regression thành full outage.

## 3. How does it work?

```text
commit -> build -> test -> immutable artifact
                       -> canary 5%
                       -> health/SLO validation
                       -> 25% -> 100%
                       -> rollback/roll-forward on regression
```

Artifact phải giống nhau giữa stages; chỉ traffic share thay đổi. Database contract phải tương thích khi old/new versions cùng chạy.

## 4. Practical implementation

Trong Azure/App Service hoặc ingress platform, route một tỷ lệ traffic tới deployment slot/version mới. Validation nên kiểm tra 5xx, p95/p99, dependency failures và business KPIs, không chỉ `/health` trả 200.

```text
Gate: error_rate < 1%
Gate: p95 < 800ms
Gate: checkout_success_rate within baseline
Observation: 15 minutes
```

## 5. Real production scenario

Checkout vNext rollout 5%. Một serialization change chỉ lỗi với payment method hiếm. Canary telemetry phát hiện error-rate riêng cohort trước khi 95% users bị ảnh hưởng.

## 6. Failure scenario & troubleshooting

**Symptom** → canary tốt ở 5% nhưng rollout 100% làm database quá tải. **Evidence** → per-request cost tăng nhẹ, chỉ vượt DB capacity ở full traffic. **Hypothesis** → canary không test capacity effect. **Diagnosis** → compare query rate/I/O per request. **Fix** → capacity gate/load testing hoặc gradual steps lớn hơn với DB telemetry. **Verification** → rollout lại theo stages và đo shared dependency saturation.

## 7. Common mistakes

Canary nhưng dùng database migration breaking; sample quá nhỏ; chỉ xem app CPU; artifact khác giữa stages; không có automated rollback criteria; sticky traffic làm sample biased mà không biết.

## 8. Alternatives

Blue-Green chuyển traffic nhanh giữa hai environments; rolling deployment đơn giản hơn; feature flags tách code deployment khỏi feature exposure. Có thể kết hợp các kỹ thuật.

## 9. Trade-offs

### Advantages

Giảm blast radius, production validation sớm, hỗ trợ progressive delivery.

### Costs / Risks

Hai versions coexist, telemetry/cohort complexity, database compatibility và routing operational cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy không đồng nghĩa expose 100% ngay.

### Middle

Xây pipeline artifact → deploy → health gate → promote.

### Senior

Định nghĩa canary metrics, rollback criteria và compatibility tests.

### Technical Lead / Architect

Quyết định khi progressive delivery đáng complexity và thiết kế schema/API để multiple versions coexist.

## 11. Key takeaway

- Canary giảm blast radius, không chứng minh full-capacity safety.
- Old/new versions phải tương thích trong rollout window.
- Promotion dựa trên telemetry và business signals, không chỉ health endpoint.

# 8. GC Server mode và allocation rate: hiểu pause, throughput và memory footprint trước khi “tune GC”

## 1. What is it?

.NET GC thu hồi managed objects không còn reachable. Server GC tối ưu throughput cho server workloads bằng heaps/GC threads phù hợp multi-core, thường đổi lại memory footprint lớn hơn. Vấn đề thực tế thường là allocation rate/object lifetime trước khi là “GC setting”.

## 2. Why does it exist?

Managed allocation nhanh nhưng collection vẫn tiêu CPU và có pauses. High-throughput API tạo nhiều temporary objects có thể dành phần đáng kể CPU cho GC. Tuning mode mà không hiểu allocation source dễ chữa symptom sai chỗ.

## 3. How does it work?

Objects mới thường vào Gen0; survivors được promote. Large objects đi vào LOH theo runtime rules. Khi allocation rate tăng, collections thường xuyên hơn; long-lived retention tăng heap size. Server GC parallelizes collection work để ưu tiên throughput.

## 4. Practical implementation

Đo trước bằng runtime counters:

```bash
dotnet-counters monitor -p <PID> System.Runtime
```

Quan sát `alloc-rate`, `gc-heap-size`, Gen collections, CPU và pause/time-in-GC. Sau đó dùng profiler/dump để tìm allocation hot path thay vì đoán.

```xml
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
</PropertyGroup>
```

Không đổi setting chỉ vì thấy memory process cao.

## 5. Real production scenario

JSON endpoint p99 tăng khi traffic gấp đôi. CPU 80%, allocation rate tăng mạnh do materialize object graph rồi serialize. Projection trực tiếp DTO và giảm temporary strings hạ allocation; GC time giảm mà không cần exotic GC tuning.

## 6. Failure scenario & troubleshooting

**Symptom** → memory cao nên team ép full GC định kỳ; latency trở nên saw-tooth. **Evidence** → forced collections trùng p99 spikes. **Hypothesis** → manual GC gây pauses nhưng retention root chưa sửa. **Diagnosis** → counters + dump retention paths. **Fix** → bỏ forced GC, sửa retention/allocation source. **Verification** → load test so sánh heap, GC time và p99.

## 7. Common mistakes

Gọi `GC.Collect()` định kỳ; coi process memory cao là leak; tối ưu allocations chưa đo; giữ large buffers vô hạn; chuyển sang pooling nhưng không có ownership discipline.

## 8. Alternatives

Workstation GC phù hợp workloads khác; object pooling/`ArrayPool<T>` chỉ nên dùng khi allocation hot path được chứng minh; scale-out có thể tăng capacity nhưng không sửa allocation inefficiency.

## 9. Trade-offs

### Advantages

Server GC ưu tiên throughput tốt cho nhiều server workloads; managed memory giảm manual lifetime bugs.

### Costs / Risks

Memory footprint, pauses và CPU GC vẫn phụ thuộc workload; pooling/tuning làm code phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu GC thu hồi unreachable objects, không phải “memory về 0”.

### Middle

Đọc runtime counters và tránh forced GC.

### Senior

Phân biệt allocation pressure, retention/leak và LOH behavior bằng evidence.

### Technical Lead / Architect

Đặt performance budget và chỉ chấp nhận complexity như pooling khi profiling chứng minh ROI.

## 11. Key takeaway

- Đo allocation/retention trước khi tune GC.
- High memory không tự động là leak.
- Performance fix tốt thường nằm ở object lifetime/query/serialization shape.

# 9. Optimizely CMS cache invalidation: content publish phải hội tụ đúng trên nhiều instances

## 1. What is it?

CMS caching giữ content/model/rendered data gần application để giảm repository/database work. Trong multi-instance deployment, publish/invalidate phải khiến mọi instances cuối cùng ngừng phục vụ version cũ theo freshness contract.

## 2. Why does it exist?

CMS read-heavy nên cache mang lại hiệu quả lớn. Nhưng editor kỳ vọng content publish xuất hiện đúng thời gian. Local in-memory cache trên từng node tạo nguy cơ node A mới, node B cũ nếu invalidation không được phân phối.

## 3. How does it work?

```text
Editor -> Publish
          |
          v
    Content store
          |
    invalidation signal
      /          \
 App A cache   App B cache
      \          /
        CDN/edge
```

Có nhiều cache layers: CMS object cache, application cache, output/CDN/browser cache. Mỗi layer có key, TTL và invalidation ownership khác nhau.

## 4. Practical implementation

Ở application code, cache key phải gắn với stable content identity/version/language khi phù hợp và invalidation phải đi theo content events thay vì chỉ TTL ngẫu nhiên.

```csharp
public string ProductPageKey(ContentReference content, string language)
    => $"product-page:{content.ID}:{language}";
```

Với Optimizely, ưu tiên platform cache/event mechanisms thay vì tự tạo một parallel invalidation system nếu built-in semantics đã đáp ứng.

## 5. Real production scenario

Marketing publish legal disclaimer. App instances nhận content invalidation nhưng Akamai vẫn giữ HTML 30 phút. Backend đã đúng nhưng user vẫn thấy stale content. Freshness contract phải bao gồm cả edge cache.

## 6. Failure scenario & troubleshooting

**Symptom** → refresh lúc thấy content mới, lúc thấy cũ. **Evidence** → response headers/node correlation cho thấy chỉ một instance stale. **Hypothesis** → distributed invalidation không tới node đó. **Diagnosis** → kiểm tra publish event, cache key, instance logs và CDN layer. **Fix** → sửa invalidation propagation/keying; purge edge khi business requirement cần. **Verification** → publish test content và request qua nhiều instances/edge POPs.

## 7. Common mistakes

Chỉ xóa local cache; cache theo content ID nhưng quên language/version; purge toàn cache mỗi publish; TTL quá dài cho legal content; không phân biệt preview/published state; tự cache ngoài platform mà không nối invalidation.

## 8. Alternatives

Không cache cho low-traffic admin path; TTL-only đơn giản nhưng freshness yếu; versioned immutable keys tránh invalidation cho assets; headless architecture chuyển một phần cache responsibility sang delivery API/CDN.

## 9. Trade-offs

### Advantages

Giảm CMS/database load và cải thiện response latency.

### Costs / Risks

Stale content, multi-layer invalidation complexity và khó debug khi ownership không rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache có freshness cost.

### Middle

Thiết kế key theo content/language và trace cache hit/miss.

### Senior

Debug invalidation xuyên nodes, CMS và CDN.

### Technical Lead / Architect

Định nghĩa freshness SLA theo content type và ownership của từng cache layer; không cache chỉ vì “CMS nên cache”.

## 11. Key takeaway

- Multi-instance CMS cần distributed invalidation semantics.
- Freshness phải xét toàn đường CMS → app → CDN → browser.
- Cache key/invalidation ownership quan trọng hơn chỉ chọn TTL.

# 10. React render boundaries: `memo` không sửa được state ownership và unstable dependencies

## 1. What is it?

React re-render là việc component function chạy lại để tạo UI description mới khi state/context/parent render thay đổi. `React.memo`, `useMemo` và `useCallback` có thể giảm một số repeated work, nhưng chúng không thay thế việc đặt state đúng boundary và giữ data flow rõ.

## 2. Why does it exist?

Frontend enterprise có forms, tables và dashboards lớn. Một state đặt quá cao có thể làm subtree rộng re-render cho mỗi keystroke. Developer thường thêm memoization khắp nơi trước khi đo, làm dependency arrays phức tạp mà performance không cải thiện.

## 3. How does it work?

Parent render thường tạo lại object/function references. Memoized child chỉ skip khi props comparison cho thấy không đổi. Nếu prop luôn là object mới, `memo` không giúp. Context update cũng có thể re-render consumers độc lập với prop memoization.

## 4. Practical implementation

```tsx
const OrderRow = React.memo(function OrderRow({ order }: { order: Order }) {
  return <tr><td>{order.id}</td><td>{order.status}</td></tr>;
});

function SearchBox() {
  const [query, setQuery] = React.useState('');
  return <input value={query} onChange={e => setQuery(e.target.value)} />;
}
```

Giữ transient search-input state gần `SearchBox` có thể tránh render cả page tốt hơn việc memo mọi child.

## 5. Real production scenario

Admin page có 2.000 rows. Typing vào filter field làm cả table render lại vì input state nằm ở page root và expensive derived list chạy mỗi keypress. Profiling chỉ ra render cost; debounce/server filtering, virtualization hoặc state boundary phù hợp giải quyết đúng bottleneck.

## 6. Failure scenario & troubleshooting

**Symptom** → thêm `memo` nhưng UI vẫn lag. **Evidence** → React Profiler cho thấy context provider value là object mới mỗi render. **Hypothesis** → unstable provider value invalidates consumers. **Diagnosis** → inspect render reasons. **Fix** → split context/state ownership hoặc stabilize value khi có ý nghĩa. **Verification** → profiler commit duration/render count giảm.

## 7. Common mistakes

Memo mọi component; dependency array sai gây stale closure; tạo object/function mới rồi kỳ vọng shallow compare skip; dùng client render cho dataset khổng lồ; tối ưu trước khi React Profiler chứng minh bottleneck.

## 8. Alternatives

Component/state decomposition thường đơn giản hơn memoization. Virtualization giải quyết large lists. Server-side filtering/pagination giảm cả network và render load. Vue có reactivity model khác nhưng vẫn cần state/data-flow boundaries hợp lý.

## 9. Trade-offs

### Advantages

Memoization đúng chỗ giảm expensive recomputation/render và cải thiện interaction latency.

### Costs / Risks

Code/dependency complexity, stale closures, memory overhead và false confidence nếu bottleneck nằm ở network/layout/large DOM.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu state change có thể dẫn tới render; render không đồng nghĩa DOM luôn bị thay toàn bộ.

### Middle

Dùng React Profiler và đặt state gần nơi sở hữu nó.

### Senior

Phân biệt render CPU, network, DOM/layout và data-volume bottlenecks trước khi tối ưu.

### Technical Lead / Architect

Đặt frontend performance budgets và API pagination/data-shape contracts thay vì để UI bù cho backend payload quá lớn.

## 11. Key takeaway

- Đo render cost trước khi memoize.
- State ownership tốt thường có giá trị hơn memoization dày đặc.
- Frontend performance là vấn đề xuyên API, data volume, render và browser.
