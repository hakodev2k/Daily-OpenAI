# 1. .NET `ArrayPool<T>`: buffer reuse, ownership và dữ liệu nhạy cảm còn sót lại

## 1. What is it?

`ArrayPool<T>` là pool các array có thể tái sử dụng. Thay vì liên tục `new byte[]` cho buffer tạm thời, code `Rent()` một array và `Return()` khi xong. Mental model quan trọng: caller **mượn capacity**, không sở hữu array vĩnh viễn; kích thước nhận được có thể lớn hơn kích thước yêu cầu.

## 2. Why does it exist?

Các hot path như serialization, compression, stream processing hoặc protocol parsing có thể tạo lượng lớn temporary arrays. Allocation rate cao làm GC chạy thường xuyên; buffer lớn còn có thể tác động LOH. Reuse giảm allocation pressure khi profiler chứng minh buffer churn là bottleneck.

## 3. How does it work?

```text
Pool buckets
   |
Rent(32 KB)
   v
caller uses buffer
   |
Return(buffer)
   v
buffer available for another caller
```

Pool không đảm bảo array được zero trước khi cho thuê lại. Vì vậy lifetime và data hygiene là trách nhiệm của caller.

## 4. Practical implementation

```csharp
var pool = ArrayPool<byte>.Shared;
byte[] buffer = pool.Rent(32 * 1024);

try
{
    int read = await stream.ReadAsync(
        buffer.AsMemory(0, 32 * 1024), cancellationToken);

    await ProcessAsync(buffer.AsMemory(0, read), cancellationToken);
}
finally
{
    pool.Return(buffer, clearArray: true);
}
```

`clearArray: true` đáng cân nhắc khi buffer có secrets/PII; nó có CPU cost nên không nên bật mù quáng cho mọi buffer.

## 5. Real production scenario

File-processing API xử lý hàng trăm uploads song song. Profiler cho thấy phần lớn allocation đến từ repeated 64 KB arrays. Pooling buffer giảm allocation rate và GC pauses mà không thay đổi business logic.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu từ request trước xuất hiện trong bytes chưa được ghi của request sau.

**Evidence** → code xử lý toàn bộ `buffer.Length` thay vì số bytes thực tế; pooled array không được zero.

**Diagnosis** → ownership/range bug, không phải corruption của runtime.

**Fix** → luôn truyền valid length/slice; clear khi dữ liệu nhạy cảm; `Return` trong `finally`.

**Verification** → stress test reuse và kiểm tra chỉ valid range được đọc.

## 7. Common mistakes

Giả định rented length bằng requested length; giữ reference sau `Return`; return cùng array hai lần; quên return khi exception; pool mọi allocation nhỏ dù chưa đo; để secrets trong buffer rồi return không clear.

## 8. Alternatives

`new byte[]` đơn giản và thường đúng cho non-hot path. `MemoryPool<T>` phù hợp với ownership model khác; streaming giảm nhu cầu buffer lớn ngay từ đầu.

## 9. Trade-offs

### Advantages

Giảm allocation/GC pressure và reuse memory hiệu quả trong hot path.

### Costs / Risks

Ownership phức tạp hơn, stale data risk, retained pool memory và bug lifetime khó phát hiện.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `Rent/Return` và valid length.

### Middle
Dùng `try/finally`, slices và benchmark đúng workload.

### Senior
Đánh giá GC evidence, sensitive-data handling và concurrency safety.

### Technical Lead / Architect
Quyết định liệu pooling có đáng complexity hay streaming/simple allocation đã đủ.

## 11. Key takeaway

- Pooling là optimization dựa trên measurement.
- Rented array là tài nguyên mượn, không phải owned object.
- Security và lifetime correctness quan trọng hơn vài allocation tiết kiệm được.

# 2. ASP.NET Core rate limiting: bảo vệ capacity thay vì chỉ “chặn spam”

## 1. What is it?

Rate limiting giới hạn số request/concurrent operations mà một identity, tenant, route hoặc hệ thống được phép tiêu thụ trong một khoảng điều kiện. Nó là capacity-control mechanism, không chỉ anti-bot feature.

## 2. Why does it exist?

Một endpoint đắt có thể làm cạn DB connections, downstream quota hoặc CPU dù mọi request đều hợp lệ. Nếu không có admission control, overload làm latency tăng, timeout tạo retry và hệ thống có thể tự khuếch đại failure.

## 3. How does it work?

```text
Client -> limiter -> admitted -> endpoint -> dependency
              |
              +-> rejected 429
```

Algorithms như fixed window, sliding window, token bucket và concurrency limiter kiểm soát những dimension khác nhau.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddFixedWindowLimiter("expensive", o =>
    {
        o.PermitLimit = 100;
        o.Window = TimeSpan.FromSeconds(10);
        o.QueueLimit = 20;
    });
});

app.UseRateLimiter();

app.MapPost("/reports", GenerateReport)
   .RequireRateLimiting("expensive");
```

Production thường partition theo tenant/API key/user thay vì một global bucket duy nhất.

## 5. Real production scenario

Reporting endpoint chạy SQL aggregation nặng. Một enterprise tenant gửi burst 5.000 requests sau reconnect. Rate limit theo tenant ngăn một tenant chiếm hết DB capacity trong khi các tenant khác vẫn hoạt động.

## 6. Failure scenario & troubleshooting

**Symptom** → thêm limiter nhưng 429 tăng mà DB vẫn quá tải.

**Evidence** → mỗi request được phép chạy vẫn fan-out 20 SQL queries.

**Diagnosis** → limit request count không phản ánh resource cost.

**Fix** → giảm fan-out, dùng concurrency limit cho expensive path, cache/precompute nếu phù hợp và align quota với downstream capacity.

**Verification** → load test burst; theo dõi admitted requests, DB pool, p95 và 429.

## 7. Common mistakes

Global limit làm noisy tenant ảnh hưởng tất cả; retry 429 ngay lập tức; không trả `Retry-After` khi phù hợp; coi limiter là authorization; đặt limit không dựa trên capacity measurement.

## 8. Alternatives

Queue phù hợp khi work có thể xử lý bất đồng bộ. Autoscaling tăng capacity nhưng không bảo vệ finite downstream resources. API gateway/CDN limiter có thể chặn sớm hơn nhưng application vẫn cần domain-aware protection ở một số route.

## 9. Trade-offs

### Advantages

Giữ hệ thống trong operating envelope và tạo fairness.

### Costs / Risks

Reject legitimate traffic, state/partition complexity và UX cần xử lý backoff.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu 429 và mục tiêu bảo vệ resource.

### Middle
Cấu hình policy theo endpoint/identity và test burst.

### Senior
Chọn algorithm theo resource bottleneck và thiết kế client backoff.

### Technical Lead / Architect
Xác định capacity budget, fairness model và limiter nằm ở edge, app hay cả hai.

## 11. Key takeaway

- Rate limit là admission control cho finite capacity.
- Request count không phải lúc nào cũng tương đương resource cost.
- Limiter tốt phải gắn với downstream bottleneck và client retry behavior.

# 3. EF Core optimistic concurrency: phát hiện lost update bằng concurrency token

## 1. What is it?

Optimistic concurrency giả định conflict hiếm và không giữ lock dài trong lúc user/application suy nghĩ. Khi update, EF Core kiểm tra concurrency token để đảm bảo row vẫn là version mà caller đã đọc.

## 2. Why does it exist?

Hai users cùng mở Order. User A sửa address; user B sửa status dựa trên dữ liệu cũ. Nếu `UPDATE` cuối cùng ghi đè vô điều kiện, thay đổi trước có thể bị mất mà không ai biết.

## 3. How does it work?

Với SQL Server `rowversion`:

```sql
UPDATE Orders
SET Status = @p0
WHERE Id = @id AND Version = @originalVersion;
```

Nếu row đã đổi, affected rows = 0 và EF Core ném `DbUpdateConcurrencyException`.

## 4. Practical implementation

```csharp
public class Order
{
    public Guid Id { get; set; }
    public string Status { get; set; } = default!;
    [Timestamp]
    public byte[] Version { get; set; } = default!;
}
```

Handler phải quyết định reload, merge, reject hoặc yêu cầu user retry; exception không tự định nghĩa business policy.

## 5. Real production scenario

Approval workflow cho phép manager và finance cùng thao tác. Finance submit trên version cũ sau khi manager đã reject. Concurrency token ngăn finance vô tình đưa record trở lại trạng thái không hợp lệ.

## 6. Failure scenario & troubleshooting

**Symptom** → intermittent `DbUpdateConcurrencyException` dưới real traffic.

**Evidence** → token database khác original token.

**Diagnosis** → genuine concurrent modification hoặc application attach entity với token sai.

**Fix** → xác định conflict policy; reload current values; chỉ merge fields nếu business invariant cho phép.

**Verification** → integration test hai DbContexts đọc cùng version rồi update cạnh tranh.

## 7. Common mistakes

Catch exception rồi retry update mù quáng; dùng timestamp business time có precision không phù hợp; merge toàn entity; coi concurrency conflict là infrastructure error thay vì business event có thể dự đoán.

## 8. Alternatives

Pessimistic locking phù hợp critical short transaction nhưng giảm concurrency. Domain-specific conditional update có thể rõ hơn cho state transition đơn giản.

## 9. Trade-offs

### Advantages

Không giữ lock qua user think time; phát hiện lost update rõ ràng.

### Costs / Risks

Conflict resolution phức tạp; caller cần version contract; retry sai có thể phá invariant.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu hai writers có thể ghi đè nhau.

### Middle
Implement token và handle exception.

### Senior
Thiết kế merge/reject policy theo aggregate invariant.

### Technical Lead / Architect
Quyết định optimistic hay pessimistic concurrency dựa trên contention và correctness.

## 11. Key takeaway

- Concurrency token phát hiện stale write, không tự giải quyết conflict.
- Retry mù quáng có thể biến detection thành lost update lần nữa.
- Conflict policy thuộc business boundary.

# 4. SQL covering index: giảm lookup nhưng trả giá bằng write amplification

## 1. What is it?

Covering index chứa đủ columns để database đáp ứng query từ index mà không cần lookup về base row/clustered index. Key columns phục vụ seek/order; included columns bổ sung output mà không nhất thiết tham gia search key.

## 2. Why does it exist?

Một selective index có thể tìm IDs nhanh nhưng query vẫn phải thực hiện hàng nghìn key lookups để lấy columns còn thiếu. Khi lookup I/O trở thành phần lớn cost, covering index có thể giảm reads.

## 3. How does it work?

```text
Query predicate
   -> nonclustered index seek
       -> INCLUDE columns đủ output
           -> return
```

Không covering:

```text
index seek -> key lookup -> base row
             x N rows
```

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_Customer_CreatedAt
ON dbo.Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, Total);
```

Phải đối chiếu actual execution plan và workload; không copy index chỉ vì query “có vẻ cần”.

## 5. Real production scenario

Order history API query 50 recent orders/customer. Existing index tìm rows tốt nhưng lookup `Status` và `Total` cho mỗi row. Include hai columns giảm logical reads đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → read endpoint nhanh hơn nhưng bulk import chậm và database size tăng.

**Evidence** → index usage stats cho thấy nhiều writes; storage/index maintenance tăng.

**Diagnosis** → over-indexing/write amplification.

**Fix** → đánh giá read benefit so với write cost; xóa redundant indexes hoặc thu hẹp INCLUDE.

**Verification** → đo cả read latency/logical reads lẫn write throughput.

## 7. Common mistakes

Include mọi selected column; duplicate indexes với prefix giống nhau; bỏ qua column width; đánh giá bằng estimated plan duy nhất; không xét write-heavy workload.

## 8. Alternatives

Projection nhỏ hơn; clustered design khác; materialized/read model cho workload đặc biệt; query rewrite. Không phải mọi lookup đều cần loại bỏ.

## 9. Trade-offs

### Advantages

Giảm I/O và lookup cho read path cụ thể.

### Costs / Risks

Tăng storage, write cost, memory footprint và maintenance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu index có thể chứa dữ liệu query cần.

### Middle
Đọc execution plan và logical reads.

### Senior
Đánh giá selectivity, lookup count, write amplification và redundant indexes.

### Technical Lead / Architect
Quản lý index như workload-level design chứ không per-query patch.

## 11. Key takeaway

- Covering index tối ưu một access pattern, không miễn phí.
- Đo lookup/I/O trước khi thêm INCLUDE.
- Index strategy phải cân bằng reads và writes.

# 5. Saga + compensating transaction: consistency khi một ACID transaction không thể bao trùm nhiều service

## 1. What is it?

Saga là chuỗi local transactions giữa nhiều service, với compensating actions để xử lý khi bước sau thất bại. Nó không tạo atomicity giống một database transaction; nó quản lý **business consistency theo thời gian**.

## 2. Why does it exist?

Order, Payment và Inventory có database riêng. Giữ một distributed ACID transaction qua tất cả services thường không khả dụng hoặc tạo coupling/availability cost lớn.

## 3. How does it work?

```text
Create Order
   -> Reserve Inventory
      -> Authorize Payment
          -> Confirm Order

Payment fails
   <- Release Inventory
   <- Cancel Order
```

Compensation là business operation mới; nó không “rewind time”.

## 4. Practical implementation

Một orchestrator có thể persist saga state:

```csharp
public record CheckoutSaga(
    Guid OrderId,
    bool InventoryReserved,
    bool PaymentAuthorized,
    string State);
```

Mỗi command cần idempotency key; state transition phải được persisted trước/đồng bộ với outgoing messages bằng Outbox khi cần.

## 5. Real production scenario

Checkout reserve stock thành công nhưng payment provider timeout. Hệ thống chưa biết payment thật sự fail hay response bị mất. Saga không được lập tức charge lại vô hạn; cần query/reconciliation hoặc idempotent payment operation trước khi compensation.

## 6. Failure scenario & troubleshooting

**Symptom** → inventory bị giữ nhưng order đã cancel.

**Evidence** → compensation message chưa xử lý hoặc dead-letter.

**Diagnosis** → saga ở intermediate state.

**Fix** → durable state, retry idempotent compensation, operational reconciliation.

**Verification** → fault-injection ở từng transition và assert eventual terminal state.

## 7. Common mistakes

Gọi compensation là rollback; không persist saga state; assume message exactly-once; compensation không idempotent; không có timeout/reconciliation cho “unknown outcome”.

## 8. Alternatives

Một database transaction đơn giản hơn nếu boundaries cho phép. Modular Monolith có thể giữ local ACID. Two-phase commit chỉ phù hợp môi trường đặc biệt và có availability/operational costs.

## 9. Trade-offs

### Advantages

Cho phép autonomous services phối hợp mà không giữ distributed lock dài.

### Costs / Risks

Intermediate states, complex recovery, eventual consistency và observability burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu compensation khác rollback.

### Middle
Implement idempotent steps và state transitions.

### Senior
Xử lý unknown outcome, duplicate messages và reconciliation.

### Technical Lead / Architect
Quyết định có thực sự cần distributed boundary hay local transaction đơn giản hơn.

## 11. Key takeaway

- Saga quản lý business consistency, không tái tạo ACID toàn cục.
- Compensation cũng có thể fail và phải được vận hành như production workflow.
- Nếu một local transaction đủ, đừng đưa Saga vào hệ thống.

# 6. Azure Managed Identity + Key Vault: loại bỏ application credential khỏi deployment

## 1. What is it?

Managed Identity cung cấp identity cho Azure resource mà application không phải lưu client secret. Azure Key Vault quản lý secrets/keys/certificates và access được kiểm soát qua identity/RBAC.

## 2. Why does it exist?

Secret trong appsettings, pipeline variable hoặc container environment vẫn phải được tạo, phân phối và rotate. Managed Identity loại bỏ credential bootstrap cho Azure-to-Azure authentication.

## 3. How does it work?

```text
App Service / Container App
      |
 Managed Identity
      |
 Entra token
      v
 Key Vault / SQL / Storage
```

Application yêu cầu token cho target resource; Azure identity platform cấp token dựa trên managed identity của workload.

## 4. Practical implementation

```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri(configuration["KeyVaultUri"]!), credential);

KeyVaultSecret secret = await client.GetSecretAsync(
    "ExternalApiKey", cancellationToken: cancellationToken);
```

Local development có thể dùng developer credential chain; Production dùng Managed Identity mà code không cần chứa secret identity.

## 5. Real production scenario

App Service cần secret của legacy vendor API và access Blob Storage. Managed Identity được cấp `Key Vault Secrets User` cho vault và data role phù hợp cho storage. Deployment artifact không chứa Azure client secret.

## 6. Failure scenario & troubleshooting

**Symptom** → chạy local được nhưng Production trả 403 từ Key Vault.

**Evidence** → authentication thành công nhưng authorization denied.

**Diagnosis** → identity đúng nhưng thiếu role/scope hoặc network path bị Private Endpoint/firewall chặn.

**Fix** → xác minh principal ID, RBAC scope và networking; không tạo secret mới để “fix nhanh”.

**Verification** → test từ production network với đúng identity và audit logs.

## 7. Common mistakes

Nhầm authentication với authorization; cấp Contributor thay vì data-plane role tối thiểu; gọi Key Vault mỗi request; log secret; giữ fallback client secret lâu dài.

## 8. Alternatives

Workload identity trong Kubernetes; service principal khi workload không hỗ trợ Managed Identity. Secret store khác có thể phù hợp multi-cloud.

## 9. Trade-offs

### Advantages

Giảm secret distribution/rotation burden, identity lifecycle gắn với resource.

### Costs / Risks

Azure coupling, RBAC/network debugging và dependency vào identity service.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu app dùng identity thay vì hard-coded credential.

### Middle
Cấu hình role và `DefaultAzureCredential` đúng môi trường.

### Senior
Debug token/RBAC/network và thiết kế caching/rotation.

### Technical Lead / Architect
Định nghĩa least-privilege identity model và secret ownership toàn platform.

## 11. Key takeaway

- Managed Identity loại bỏ nhiều credential, không loại bỏ authorization design.
- Key Vault access cần xem cả identity, RBAC và network.
- Không fetch secret từ vault trên mọi request nếu không cần.

# 7. Connection pool exhaustion: khi database còn khỏe nhưng API vẫn timeout

## 1. What is it?

ADO.NET connection pooling tái sử dụng physical database connections. Pool exhaustion xảy ra khi mọi pooled connection đang được giữ và request mới phải chờ connection trở lại hoặc timeout.

## 2. Why does it exist?

Mở TCP/database session mới cho mỗi query rất đắt. Pooling amortize setup cost, nhưng pool là finite resource nên connection lifetime sai có thể trở thành bottleneck.

## 3. How does it work?

```text
Requests
  -> connection pool [busy busy busy ... max]
          |
          +-> SQL Server

new request -> waits for free pooled connection
```

`Close/Dispose` thường trả connection về pool, không đóng physical connection ngay.

## 4. Practical implementation

Với EF Core, `DbContext` scoped và operation ngắn:

```csharp
await using var transaction =
    await db.Database.BeginTransactionAsync(cancellationToken);

// only database work required for this transaction
await db.SaveChangesAsync(cancellationToken);
await transaction.CommitAsync(cancellationToken);
```

Không gọi remote HTTP trong transaction trong khi connection bị giữ nếu không có lý do consistency rất cụ thể.

## 5. Real production scenario

API mở transaction, update row, gọi payment API 8 giây rồi commit. 100 concurrent requests giữ 100 connections trong lúc chờ network. SQL CPU thấp nhưng pool hết và endpoint khác cũng timeout.

## 6. Failure scenario & troubleshooting

**Symptom** → timeout “prior to obtaining a connection from the pool”, SQL CPU thấp.

**Evidence** → active connections gần pool max; traces cho thấy connection/transaction duration dài.

**Diagnosis** → application giữ connections quá lâu hoặc leak/dispose sai.

**Fix** → rút transaction boundary, dispose đúng, giảm long-running DB work; chỉ tăng pool size sau capacity analysis.

**Verification** → load test và đo pool wait, active connections, DB sessions, p95.

## 7. Common mistakes

Tăng `Max Pool Size` ngay lập tức; tạo nhiều connection strings khác nhau làm phân mảnh pools; giữ transaction qua external calls; không dispose raw connection; query streaming rất lâu mà không hiểu connection lifetime.

## 8. Alternatives

Queue/batch cho long work; read replica giảm workload nhưng không sửa leak; pool size lớn hơn chỉ phù hợp nếu database thực sự chịu được thêm concurrency.

## 9. Trade-offs

### Advantages

Pooling giảm connection setup latency và bảo vệ DB khỏi unlimited sessions.

### Costs / Risks

Finite capacity tạo queue; bad transaction boundaries làm pool thành shared failure point.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu connection được reuse và phải dispose.

### Middle
Giữ DbContext/transaction lifetime ngắn.

### Senior
Correlate pool metrics với traces và downstream latency.

### Technical Lead / Architect
Định nghĩa concurrency budget giữa app instances, pool size và DB capacity.

## 11. Key takeaway

- SQL CPU thấp không chứng minh database path khỏe.
- Connection lifetime thường quan trọng hơn việc tăng pool size.
- Remote call bên trong DB transaction là dấu hiệu cần review nghiêm túc.

# 8. Playwright E2E: test user journey ở đúng boundary mà không biến suite thành flaky bottleneck

## 1. What is it?

Playwright điều khiển browser thật để kiểm tra user journey xuyên UI, network và backend. E2E test bảo vệ integration behavior mà unit test không thấy, nhưng đắt và dễ flaky hơn tests ở tầng thấp.

## 2. Why does it exist?

Frontend component, API và auth có thể pass riêng nhưng wiring sai khi deploy. Một số critical flow cần evidence rằng user thực sự hoàn thành hành động qua browser.

## 3. How does it work?

```text
Playwright -> Browser -> Frontend -> API -> Test DB
```

Test nên quan sát user-visible contract thay vì implementation detail.

## 4. Practical implementation

```typescript
test('manager approves timesheet', async ({ page }) => {
  await page.goto('/timesheets/42');
  await page.getByRole('button', { name: 'Approve' }).click();
  await expect(page.getByText('Approved')).toBeVisible();
});
```

Prefer semantic locators (`role`, label, stable test id khi cần), không dựa vào brittle CSS hierarchy.

## 5. Real production scenario

Backend đổi error response, frontend interceptor xử lý sai và spinner không bao giờ dừng. Unit tests hai phía đều pass; E2E critical approval flow bắt regression.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail 1/20 runs trên CI.

**Evidence** → hard-coded `waitForTimeout(2000)` và shared test data.

**Diagnosis** → timing/data race, không phải product regression.

**Fix** → wait theo observable state, isolate data, trace/video khi failure, kiểm soát parallelism.

**Verification** → chạy repeated CI executions và theo dõi flaky rate.

## 7. Common mistakes

E2E mọi edge case; sleep cố định; selectors theo DOM structure; shared mutable account; mock toàn backend khiến test không còn E2E; bỏ qua traces/artifacts.

## 8. Alternatives

Unit tests nhanh cho logic; integration/API tests tốt cho persistence/contracts; component tests cho UI behavior. E2E nên tập trung critical journeys và deployment wiring.

## 9. Trade-offs

### Advantages

Confidence cao cho user-facing integration và regression quan trọng.

### Costs / Risks

Chậm, infrastructure-heavy, flaky nếu design kém và diagnosis tốn thời gian.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Viết stable locator và assertion theo UI state.

### Middle
Quản lý test data, auth setup và CI artifacts.

### Senior
Phân bổ risk giữa unit/integration/E2E và triage flakiness.

### Technical Lead / Architect
Thiết kế test strategy để release confidence tăng mà pipeline không bị E2E bottleneck.

## 11. Key takeaway

- E2E bảo vệ journeys, không phải thay thế mọi test tầng thấp.
- Flakiness thường là test-design defect cần xử lý.
- Test theo observable contract, không theo timing giả định.

# 9. Akamai/CDN `Cache-Control`: ai thực sự quyết định freshness giữa browser, edge và origin

## 1. What is it?

HTTP caching là chuỗi quyết định giữa origin, shared caches/CDN và browser. `Cache-Control` mô tả cacheability/freshness; CDN như Akamai có thể thêm policy riêng nhưng origin headers vẫn là phần contract quan trọng.

## 2. Why does it exist?

Serving static/public content từ edge giảm latency và origin load. Nhưng cache sai có thể trả stale content hoặc, nghiêm trọng hơn, cache personalized response cho user khác.

## 3. How does it work?

```text
Browser cache
    |
Akamai edge cache
    |
Origin / ASP.NET Core
```

Ví dụ:

```http
Cache-Control: public, max-age=60, s-maxage=300
```

Browser có thể coi fresh 60 giây; shared cache có thể dùng 300 giây tùy policy/support.

## 4. Practical implementation

```csharp
context.Response.Headers.CacheControl =
    "public, max-age=60, s-maxage=300";
```

Chỉ áp dụng cho response thực sự public. Authenticated/personalized response cần policy khác, thường `private` hoặc `no-store` tùy sensitivity.

## 5. Real production scenario

Product detail public có traffic lớn. Edge cache 5 phút giảm origin traffic mạnh. Price update cần freshness dưới 1 phút nên team tách price API khỏi long-lived page cache hoặc dùng purge/version strategy.

## 6. Failure scenario & troubleshooting

**Symptom** → editor publish mới nhưng một số users vẫn thấy content cũ.

**Evidence** → response có `Age`, cache-status/header của CDN; origin trả mới.

**Diagnosis** → stale edge/browser layer chứ không phải CMS database.

**Fix** → kiểm tra TTL, cache key, purge và browser directives.

**Verification** → compare origin bypass với edge responses từ nhiều requests/locations.

## 7. Common mistakes

Cache response có user data; nghĩ purge edge cũng xóa browser cache; TTL dài nhưng không có invalidation; cache key bỏ query/language dimension cần thiết; `no-cache` và `no-store` bị hiểu là một.

## 8. Alternatives

No cache cho highly dynamic/sensitive content; application/Redis cache giảm backend compute nhưng không giảm network distance như CDN; versioned immutable assets phù hợp static files.

## 9. Trade-offs

### Advantages

Latency thấp, giảm origin load và tăng resilience cho public reads.

### Costs / Risks

Staleness, invalidation complexity, cache-key correctness và privacy risk.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu browser, CDN và origin là các cache layers khác nhau.

### Middle
Đọc headers, `Age`, TTL và test cache behavior.

### Senior
Thiết kế cache key/invalidation và debug stale response xuyên layers.

### Technical Lead / Architect
Định nghĩa freshness SLA theo content type và quyết định layer nào sở hữu caching.

## 11. Key takeaway

- CDN caching là HTTP/data-consistency design, không chỉ cấu hình performance.
- Purge edge không đồng nghĩa purge browser.
- Personalized response phải được review cacheability đặc biệt cẩn thận.

# 10. AI RAG retrieval boundary: grounding tốt vẫn cần authorization trước retrieval

## 1. What is it?

RAG lấy documents/chunks liên quan rồi đưa vào LLM context để model trả lời dựa trên nguồn. Retrieval cải thiện grounding nhưng **không phải authorization mechanism**.

## 2. Why does it exist?

Enterprise assistant cần kiến thức nội bộ vượt training data. Tuy nhiên vector similarity có thể tìm document mà user không được phép đọc nếu access control không được áp ở retrieval boundary.

## 3. How does it work?

Sai:

```text
User -> vector search toàn corpus -> LLM -> “hãy đừng tiết lộ nếu user không có quyền”
```

Đúng hơn:

```text
User identity
   -> authorization scope/filter
   -> retrieval trong allowed corpus
   -> context
   -> LLM
   -> output controls/audit
```

Deterministic authorization phải xảy ra trước khi sensitive content được đưa vào model context.

## 4. Practical implementation

```csharp
var allowedTenantId = currentUser.TenantId;
var allowedGroups = await accessService.GetGroupsAsync(currentUser.Id, ct);

var results = await vectorStore.SearchAsync(
    embedding,
    filter: new RetrievalFilter(
        TenantId: allowedTenantId,
        AllowedGroups: allowedGroups),
    cancellationToken: ct);
```

Filter phải được enforce bởi trusted application/storage layer; không dựa vào prompt kiểu “chỉ dùng documents user được phép xem”.

## 5. Real production scenario

Company assistant index HR, engineering và finance docs chung vector store. User engineering hỏi về “salary forecast”. Similarity search trả finance chunk rất liên quan. Nếu chunk đã vào prompt, system đã có data exposure dù model cuối cùng không hiển thị nguyên văn.

## 6. Failure scenario & troubleshooting

**Symptom** → red-team user suy ra nội dung restricted qua câu trả lời gián tiếp.

**Evidence** → retrieval trace cho thấy unauthorized document IDs trong context.

**Diagnosis** → authorization áp sau retrieval hoặc chỉ bằng prompt instruction.

**Fix** → ACL-aware indexing/filtering, tenant partition, deterministic access check trước context assembly; audit retrieved IDs.

**Verification** → adversarial tests giữa tenants/groups và assert restricted IDs không bao giờ vào model context.

## 7. Common mistakes

Dùng prompt làm ACL; metadata filter do model tự sinh; index nhiều tenants nhưng quên tenant predicate; log full retrieved sensitive chunks; cho tool gọi arbitrary document ID không re-authorize.

## 8. Alternatives

Separate index per tenant/security domain tạo isolation mạnh hơn nhưng tăng operational cost. Shared index + trusted metadata filter linh hoạt hơn nhưng filter correctness trở thành security-critical.

## 9. Trade-offs

### Advantages

RAG tăng grounding, freshness và khả năng dùng enterprise knowledge.

### Costs / Risks

Retrieval quality, token/cost, stale index và security boundary phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu RAG = retrieve context + model generation, không phải model “biết quyền”.

### Middle
Implement metadata filtering và source citations/audit IDs.

### Senior
Threat-model cross-tenant leakage, prompt injection và tool/retrieval authorization.

### Technical Lead / Architect
Quyết định physical/logical isolation, ACL ownership, auditability và dữ liệu nào không nên đưa vào LLM pipeline.

## 11. Key takeaway

- Grounding và authorization là hai vấn đề khác nhau.
- Sensitive document không được phép vào context ngay từ đầu.
- Security-critical access decisions phải deterministic và nằm ngoài model.
