# 1. C# Nullable Reference Types: compile-time contract và ranh giới với dữ liệu runtime

## 1. What is it?

Nullable Reference Types (NRT) là hệ thống annotation + static flow analysis của C# giúp compiler phân biệt reference dự kiến không được `null` với reference có thể `null`. Mental model quan trọng: NRT là **compile-time contract**, không phải runtime guard.

`string` và `string?` vẫn là cùng một CLR reference type ở runtime. Khác biệt nằm ở metadata/annotations và compiler analysis. Vì vậy một property khai báo `string Name` vẫn có thể nhận `null` từ reflection, deserialization, legacy assembly, database mapping hoặc code đã tắt nullable analysis.

## 2. Why does it exist?

Trước NRT, `null` thường chỉ được phát hiện khi execution đi tới dereference và ném `NullReferenceException`. Contract như “field này bắt buộc có” chủ yếu nằm trong convention, documentation hoặc developer memory.

NRT đưa phần contract này vào compiler để lỗi được phát hiện sớm hơn. Nhưng straightforward approach kiểu “bật `<Nullable>enable</Nullable>` rồi sửa hết warning bằng `!`” không giải quyết vấn đề; nó chỉ làm compiler im lặng và có thể che mất boundary không đáng tin cậy.

## 3. How does it work?

Compiler theo dõi null-state qua control flow:

```csharp
string? displayName = GetDisplayName();

if (displayName is not null)
{
    Console.WriteLine(displayName.Length); // compiler biết non-null ở branch này
}
```

Luồng thực tế nên được hiểu như:

```text
Untrusted runtime data
        |
        v
Validation / parsing boundary
        |
        v
Non-null domain/application model
        |
        v
Compiler-assisted flow analysis
```

NRT hiệu quả nhất khi nullable data được thu hẹp ở boundary thay vì lan `string?` khắp application.

## 4. Practical implementation

Ví dụ DTO nhận dữ liệu HTTP:

```csharp
public sealed record CreateEmployeeRequest(
    string? FirstName,
    string? LastName,
    string? Email);

public sealed record EmployeeName(string FirstName, string LastName);

public static EmployeeName ParseName(CreateEmployeeRequest request)
{
    if (string.IsNullOrWhiteSpace(request.FirstName))
        throw new ArgumentException("FirstName is required");

    if (string.IsNullOrWhiteSpace(request.LastName))
        throw new ArgumentException("LastName is required");

    return new EmployeeName(request.FirstName, request.LastName);
}
```

DTO phản ánh dữ liệu bên ngoài có thể thiếu; domain/application object sau validation có invariant mạnh hơn.

## 5. Real production scenario

Một integration nhận JSON từ hệ thống HR bên thứ ba. Contract tài liệu nói `employeeCode` luôn có, nên model C# khai báo `string EmployeeCode`. Một release phía provider bắt đầu gửi `null` cho employee chưa hoàn tất onboarding.

Deserializer vẫn có thể tạo object có `EmployeeCode == null`. Code downstream gọi `.Trim()` và lỗi chỉ xuất hiện trong Production. Nếu integration DTO được coi là nullable/untrusted và validate ngay sau deserialization, lỗi sẽ trở thành integration-contract failure có telemetry rõ ràng thay vì `NullReferenceException` sâu trong business flow.

## 6. Failure scenario & troubleshooting

**Symptom** → `NullReferenceException` xuất hiện dù compiler không có nullable warning.

**Evidence** → Stack trace cho thấy object đến từ JSON/reflection/legacy library; serialized payload chứa `null` ở field được khai báo non-null.

**Hypothesis** → Compile-time contract không được enforce tại runtime boundary.

**Diagnosis** → Trace object creation path, inspect payload/schema, tìm `!`, reflection mapping hoặc `default!` trong model initialization.

**Fix** → Validate tại boundary; dùng nullable DTO nếu input có thể thiếu; chỉ chuyển sang non-null model sau parsing/validation.

**Verification** → Contract test với payload null/missing, integration test deserialization và telemetry cho validation failure.

## 7. Common mistakes

* Dùng null-forgiving operator `!` để xóa warning mà không chứng minh invariant.
* Khai báo mọi property là nullable “cho dễ compile”.
* Nghĩ `string` sẽ tự động reject `null` khi deserialize.
* Đưa nullable state từ external DTO xuyên suốt domain model.
* Bật NRT trên legacy solution một lần rồi tạo hàng nghìn warning không có migration strategy.

## 8. Alternatives

* Runtime guards (`ArgumentNullException.ThrowIfNull`) bảo vệ runtime invariant nhưng không thay thế static analysis.
* Validation libraries giúp kiểm tra input contract nhưng không theo dõi null-state trong toàn control flow.
* Option/Maybe types có thể biểu diễn optionality rõ hơn trong một số domain, nhưng thêm abstraction và ecosystem friction trong C# enterprise code.

## 9. Trade-offs

### Advantages

* Phát hiện nhiều lỗi null trước runtime.
* Làm API contract rõ hơn.
* Refactoring an toàn hơn khi compiler tham gia kiểm tra flow.

### Costs / Risks

* Migration legacy code có thể noisy.
* False confidence nếu runtime boundaries không validate.
* Overuse `!` biến warning system thành decoration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `string?` nghĩa là caller phải xử lý khả năng `null`; `string` là contract mong muốn non-null chứ không phải runtime magic.

### Middle

Biết bật NRT, xử lý compiler warnings đúng cách và validate DTO ở HTTP/database/integration boundaries.

### Senior

Nhận biết annotation drift giữa runtime data và C# model; review `!`, reflection/deserialization path và thiết kế boundary để nullability không lan rộng.

### Technical Lead / Architect

Quyết định migration strategy cho legacy solution, coding conventions cho DTO/domain model và nơi invariant phải được enforce bằng runtime validation.

## 11. Key takeaway

* NRT là compiler contract, không phải runtime validation.
* External data luôn phải được coi là untrusted cho tới khi validate.
* `!` chỉ hợp lệ khi invariant đã được chứng minh, không phải công cụ “sửa warning”.

# 2. ASP.NET Core model binding + validation: từ HTTP payload đến application boundary

## 1. What is it?

Model binding là cơ chế ASP.NET Core biến dữ liệu HTTP từ route, query string, headers, form hoặc request body thành parameters/objects của endpoint. Validation kiểm tra object đã bind có thỏa contract đầu vào hay không.

Mental model: model binding không phải business logic. Nó nằm ở transport boundary:

```text
HTTP bytes
   -> parse/bind
   -> transport validation
   -> application command/query
   -> domain logic
```

## 2. Why does it exist?

Nếu mỗi controller tự đọc raw body, parse JSON, convert GUID/date, kiểm tra field bắt buộc và tạo error response, code bị lặp và error semantics không đồng nhất.

Framework cung cấp binding/validation để transport concerns được xử lý nhất quán. Nhưng nếu đưa mọi business rule vào Data Annotations thì transport model lại trở thành domain model, làm boundary bị mờ.

## 3. How does it work?

Với `[ApiController]`, ASP.NET Core có thể tự động trả `400 Bad Request` khi model state invalid. Flow điển hình:

```text
Client
  |
  v
Routing
  |
  v
Model Binding
  |
  v
Validation
  | invalid -> 400 / ProblemDetails
  v
Controller / Endpoint
  |
  v
Application
```

Binding source cũng quan trọng. Một `id` từ route và một JSON body không nên được hiểu mơ hồ nếu endpoint contract cần rõ ràng.

## 4. Practical implementation

```csharp
[ApiController]
[Route("api/employees")]
public sealed class EmployeesController : ControllerBase
{
    [HttpPut("{id:guid}")]
    public async Task<IActionResult> Update(
        [FromRoute] Guid id,
        [FromBody] UpdateEmployeeRequest request,
        CancellationToken ct)
    {
        var command = new UpdateEmployeeCommand(
            id,
            request.DisplayName.Trim(),
            request.DepartmentId);

        await handler.HandleAsync(command, ct);
        return NoContent();
    }
}

public sealed class UpdateEmployeeRequest
{
    [Required]
    [StringLength(200)]
    public string DisplayName { get; init; } = string.Empty;

    [Required]
    public Guid? DepartmentId { get; init; }
}
```

Data Annotations ở đây bảo vệ shape/basic transport constraints. Rule “employee chỉ được chuyển department khi không có timesheet đang pending approval” thuộc application/domain layer.

## 5. Real production scenario

Một CRM API có 12 controllers, mỗi controller tự trả error JSON khác nhau. Frontend phải viết nhiều branches để đọc lỗi validation. Sau khi chuẩn hóa `[ApiController]`, `ProblemDetails` và application-level error mapping, client có một error contract ổn định hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → Endpoint trả `400` trước khi breakpoint trong controller được hit.

**Evidence** → Response chứa model-state errors; request Content-Type hoặc JSON field type không khớp.

**Hypothesis** → Failure xảy ra trong binding/validation pipeline, không phải business handler.

**Diagnosis** → Inspect HTTP request thực tế, route template, Content-Type, JSON payload và model-state logging an toàn.

**Fix** → Sửa contract/client payload hoặc custom binder/converter nếu type semantics đặc biệt.

**Verification** → API integration tests cho missing field, malformed JSON, invalid GUID và valid request.

## 7. Common mistakes

* Đưa database query vào custom validation attribute.
* Dùng cùng một entity EF Core làm request model.
* Không phân biệt transport validation và business invariant.
* Tự return error format khác nhau giữa endpoints.
* Bind quá nhiều dữ liệu vào entity rồi vô tình tạo over-posting vulnerability.

## 8. Alternatives

* FluentValidation hoặc custom validators hữu ích khi request validation phức tạp hơn Data Annotations.
* Minimal API endpoint filters có thể xử lý cross-cutting validation trong Minimal APIs.
* Manual parsing chỉ hợp lý cho protocol/payload đặc biệt nơi framework binding không đủ rõ hoặc không đủ hiệu quả.

## 9. Trade-offs

### Advantages

* Ít boilerplate.
* Error handling nhất quán hơn.
* Transport contract rõ và dễ test.

### Costs / Risks

* Framework conventions có thể khiến developer khó biết request fail ở bước nào.
* Validation đặt sai layer tạo coupling transport ↔ domain/database.
* Automatic 400 cần được chuẩn hóa nếu organization có error contract riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu route/query/body được bind thành C# objects trước khi controller chạy.

### Middle

Thiết kế request DTO, validation và integration tests; phân biệt 400 transport failure với business conflict.

### Senior

Review over-posting, error contract, custom binding và performance/security của large payloads.

### Technical Lead / Architect

Quy định transport model không trở thành domain model; chuẩn hóa validation + ProblemDetails contract giữa APIs.

## 11. Key takeaway

* Model binding là transport concern, không phải domain logic.
* Validate shape ở API boundary; enforce business invariant trong application/domain boundary.
* Khi controller không được hit, kiểm tra pipeline trước khi debug handler.

# 3. EF Core optimistic concurrency: concurrency token, `rowversion` và conflict resolution

## 1. What is it?

Optimistic concurrency giả định conflict giữa concurrent writers là tương đối hiếm. Thay vì lock row từ lúc đọc đến lúc update, application phát hiện dữ liệu đã thay đổi tại thời điểm ghi.

Trong EF Core, một property có thể được cấu hình làm concurrency token. Với SQL Server, `rowversion` là lựa chọn phổ biến vì database tự đổi giá trị mỗi lần row được update.

## 2. Why does it exist?

Flow read-modify-write có race condition:

```text
User A reads version 10
User B reads version 10
User A updates -> version 11
User B updates stale version 10
```

Nếu B update mà không kiểm tra version, thay đổi của A có thể bị ghi đè im lặng — lost update.

Pessimistic locking có thể ngăn điều này nhưng giữ locks lâu, không phù hợp với web request nơi user có thể giữ form mở vài phút.

## 3. How does it work?

EF Core tạo UPDATE có điều kiện:

```sql
UPDATE Employees
SET DisplayName = @p0
WHERE Id = @id AND RowVersion = @originalRowVersion;
```

Nếu affected rows = 0, EF Core hiểu rằng row đã bị thay đổi hoặc xóa và ném `DbUpdateConcurrencyException`.

```text
Read row + version
      |
      v
Edit in application
      |
      v
UPDATE ... WHERE Version = oldVersion
      |
      +--> 1 row: success
      |
      +--> 0 rows: concurrency conflict
```

## 4. Practical implementation

Entity:

```csharp
public sealed class Employee
{
    public Guid Id { get; set; }
    public string DisplayName { get; set; } = string.Empty;

    [Timestamp]
    public byte[] RowVersion { get; set; } = Array.Empty<byte>();
}
```

Handler:

```csharp
try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    throw new ConflictException(
        "Employee was changed by another user. Reload and retry.");
}
```

API nên gửi version cho client, ví dụ Base64 string hoặc ETag, rồi nhận lại khi update.

## 5. Real production scenario

Hai managers cùng chỉnh một employee profile. Manager A đổi manager assignment; manager B mở từ trước và đổi display name. Nếu B submit full entity snapshot mà không concurrency check, manager assignment mới có thể bị ghi đè bởi giá trị cũ trong form B.

Optimistic concurrency biến silent data loss thành explicit conflict mà UI có thể yêu cầu reload/merge.

## 6. Failure scenario & troubleshooting

**Symptom** → `DbUpdateConcurrencyException` tăng sau khi release UI mới.

**Evidence** → Nhiều users update cùng aggregate; payload chứa stale version; client retry tự động bằng cùng stale token.

**Hypothesis** → Conflict hợp lệ nhưng retry strategy sai hoặc update granularity quá rộng.

**Diagnosis** → Log entity key + version metadata an toàn, xem affected operation và frequency; không log sensitive row content.

**Fix** → Reload-and-merge, narrow update scope, hoặc thiết kế UX conflict resolution. Không blind retry cùng original version.

**Verification** → Concurrent integration test tạo hai DbContexts, update cùng row và đảm bảo một writer nhận conflict thay vì lost update.

## 7. Common mistakes

* Catch `DbUpdateConcurrencyException` rồi retry vô hạn.
* Dùng timestamp thời gian ứng dụng làm version mà precision/clock semantics không đủ.
* Gửi full entity từ client rồi overwrite toàn row.
* Nhầm optimistic concurrency với transaction isolation.
* Không có UX/API semantics cho `409 Conflict`.

## 8. Alternatives

* Pessimistic locking phù hợp cho critical short transaction cần exclusive access, nhưng lock contention cao hơn.
* Domain-specific version number hữu ích nếu version semantics cần độc lập với database feature.
* ETag + `If-Match` đưa concurrency semantics lên HTTP contract, thường rất phù hợp REST APIs.

## 9. Trade-offs

### Advantages

* Không giữ long-lived locks trong user interaction.
* Ngăn silent lost update.
* Scale tốt khi conflict rate thấp.

### Costs / Risks

* Conflict phải được application/UX xử lý.
* High-contention entities có thể tạo nhiều retries/rejections.
* Version field phải đi xuyên đúng request/response boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hai người có thể đọc cùng dữ liệu rồi ghi đè nhau.

### Middle

Cấu hình concurrency token, catch conflict và viết concurrent integration test.

### Senior

Thiết kế merge/retry semantics, HTTP `409`/ETag và phân biệt conflict với transient database failure.

### Technical Lead / Architect

Xác định aggregate nào cần concurrency protection và liệu data model có đang tạo quá nhiều contention tại một aggregate root.

## 11. Key takeaway

* Optimistic concurrency biến lost update thành explicit conflict.
* `DbUpdateConcurrencyException` không nên được blind retry.
* Concurrency policy là business/data-consistency decision, không chỉ EF Core configuration.

# 4. SQL window functions: analytics trên cùng result set mà không tự tạo N+1 ở database

## 1. What is it?

Window function tính toán trên một “window” các rows liên quan nhưng vẫn giữ mỗi row trong result set, khác với `GROUP BY` thường collapse nhiều rows thành một row mỗi group.

Các function phổ biến gồm `ROW_NUMBER()`, `RANK()`, `LAG()`, `LEAD()`, `SUM() OVER(...)`.

## 2. Why does it exist?

Nhiều yêu cầu như “xếp hạng employee theo hours trong department”, “so sánh current order với previous order”, “running total” thường bị implement bằng nhiều subqueries, loops hoặc nhiều database calls.

Window functions cho database thực hiện set-based computation trong một query, thường rõ hơn và hiệu quả hơn application-side loops tải quá nhiều dữ liệu.

## 3. How does it work?

Ví dụ ranking theo department:

```sql
SELECT
    DepartmentId,
    EmployeeId,
    TotalHours,
    RANK() OVER (
        PARTITION BY DepartmentId
        ORDER BY TotalHours DESC
    ) AS DepartmentRank
FROM MonthlyHours;
```

`PARTITION BY` tạo logical partitions; `ORDER BY` trong `OVER` xác định thứ tự trong mỗi partition.

```text
Rows
 -> partition by Department
 -> order within partition
 -> compute rank/window value
 -> preserve rows
```

## 4. Practical implementation

Tìm lần order trước của customer:

```sql
SELECT
    CustomerId,
    OrderId,
    OrderedAt,
    TotalAmount,
    LAG(TotalAmount) OVER (
        PARTITION BY CustomerId
        ORDER BY OrderedAt
    ) AS PreviousOrderAmount
FROM Orders
WHERE OrderedAt >= @FromDate;
```

Điều này tránh việc application query previous order riêng cho từng order.

## 5. Real production scenario

Dashboard timesheet cần hiển thị mỗi employee, tổng hours và rank trong team. Một implementation đầu tiên query employees rồi chạy query tổng hours cho từng employee. 500 employees tạo hàng trăm round trips.

Một set-based query với aggregation + window ranking giảm round trips và đưa calculation về nơi database optimizer có thể lập execution plan tổng thể.

## 6. Failure scenario & troubleshooting

**Symptom** → Query window function chậm sau khi dataset tăng lớn.

**Evidence** → Execution plan có expensive sort/spill to tempdb; memory grant lớn; filter không đủ selective.

**Hypothesis** → Partition/order cần sort lượng dữ liệu lớn, không phải window function tự thân “chậm”.

**Diagnosis** → Xem actual execution plan, rows, sort operator, spills, I/O và index order.

**Fix** → Giảm rows trước window khi semantics cho phép, cải thiện index phù hợp access pattern, pre-aggregate nếu business query lặp lại rất lớn.

**Verification** → So sánh logical reads, execution time, spill warnings và p95 query latency.

## 7. Common mistakes

* Dùng window function khi một `GROUP BY` đơn giản đủ.
* Không hiểu khác biệt giữa `ORDER BY` trong `OVER` và final result ordering.
* Tạo partition quá lớn dẫn tới sort/memory cost cao.
* Kéo dữ liệu về C# để ranking chỉ vì LINQ dễ viết hơn.
* Thêm index mù quáng mà không xem plan.

## 8. Alternatives

* `GROUP BY`: phù hợp khi cần aggregate và collapse rows.
* Correlated subquery: có thể rõ cho query nhỏ nhưng dễ đắt nếu optimizer không transform tốt.
* Precomputed summary table/materialized view: hợp lý cho analytics nặng, đổi freshness lấy read performance.

## 9. Trade-offs

### Advantages

* Set-based, expressive.
* Giảm database round trips.
* Rất phù hợp ranking/running totals/previous-next row analytics.

### Costs / Risks

* Sorting/partitioning có thể cần memory lớn.
* Query khó đọc với team chưa quen SQL analytics.
* Không thay thế data warehouse khi analytics workload thực sự lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt `GROUP BY` collapse rows với window function giữ rows.

### Middle

Viết `ROW_NUMBER`, `RANK`, `LAG`, running total và đọc result đúng semantics.

### Senior

Đọc execution plan, sort/spill/memory grant và chọn index/filter strategy dựa trên evidence.

### Technical Lead / Architect

Quyết định calculation nên nằm trong OLTP query, summary projection hay analytics platform riêng.

## 11. Key takeaway

* Window functions giải quyết nhiều analytics problems trong một set-based query.
* Performance phụ thuộc rows, sort, partition và plan — không chỉ syntax.
* Đừng biến một set-based problem thành hàng trăm application round trips.

# 5. Redis cache penetration: negative caching, input validation và bảo vệ database khỏi miss traffic

## 1. What is it?

Cache penetration xảy ra khi requests liên tục hỏi các keys không tồn tại trong cache **và** cũng không tồn tại trong source database. Vì không có dữ liệu để cache theo cách thông thường, mỗi request xuyên qua Redis xuống database.

Đây khác cache stampede: stampede thường là nhiều requests cùng miss một key **có tồn tại** sau expiry; penetration tập trung vào non-existent keys.

## 2. Why does it exist?

Cache-aside flow cơ bản:

```text
GET cache
 -> miss
 -> query database
 -> if found: cache result
```

Nếu “not found” không được cache, random IDs hoặc bot traffic có thể khiến database nhận mọi miss. Redis vẫn khỏe nhưng database bị tấn công gián tiếp qua application.

## 3. How does it work?

```text
Request nonexistent ID
       |
       v
Redis MISS
       |
       v
Database MISS
       |
       v
Nothing cached
       |
       +---- next identical request repeats
```

Negative caching lưu một marker “không tồn tại” trong TTL ngắn:

```text
Redis key -> __NOT_FOUND__ (TTL 30s)
```

Như vậy repeated misses không xuống database liên tục.

## 4. Practical implementation

```csharp
private const string NotFoundMarker = "__NOT_FOUND__";

public async Task<ProductDto?> GetProductAsync(Guid id, CancellationToken ct)
{
    var key = $"product:v1:{id:N}";
    var value = await redis.StringGetAsync(key);

    if (value == NotFoundMarker)
        return null;

    if (value.HasValue)
        return JsonSerializer.Deserialize<ProductDto>(value!)!;

    var product = await db.Products
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new ProductDto(x.Id, x.Name))
        .SingleOrDefaultAsync(ct);

    if (product is null)
    {
        await redis.StringSetAsync(key, NotFoundMarker, TimeSpan.FromSeconds(30));
        return null;
    }

    await redis.StringSetAsync(
        key,
        JsonSerializer.Serialize(product),
        TimeSpan.FromMinutes(5));

    return product;
}
```

TTL negative nên ngắn hơn positive cache vì resource có thể được tạo sau đó.

## 5. Real production scenario

Public product endpoint nhận UUID. Một crawler lỗi generate hàng trăm nghìn UUID ngẫu nhiên. Redis hit ratio giảm, SQL QPS tăng mạnh dù traffic hợp lệ không tăng.

Negative caching + rate limiting + validation giúp loại bỏ repeated misses; nếu IDs có predictable format/range, validation còn chặn request trước cache/database.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL read QPS tăng nhưng Redis CPU thấp và phần lớn queries trả zero rows.

**Evidence** → High cache miss ratio trên keys không tồn tại; request distribution có nhiều IDs lặp lại hoặc random.

**Hypothesis** → Cache penetration.

**Diagnosis** → Correlate endpoint requests, cache misses và DB result count; phân biệt với stampede bằng việc kiểm tra resource có tồn tại hay không.

**Fix** → Input validation, negative caching, rate limiting và nếu cần edge protection.

**Verification** → DB QPS cho misses giảm, latency ổn định, newly-created resource vẫn trở nên visible trong accepted freshness window.

## 7. Common mistakes

* Negative cache với TTL quá dài làm resource mới bị “ẩn”.
* Cache mọi 404 vô thời hạn.
* Dùng Redis như security layer duy nhất thay rate limiting/auth.
* Không phân biệt malformed ID với valid-but-not-found ID.
* Tạo một global not-found key thay vì key theo resource identity.

## 8. Alternatives

* Input validation có thể loại bỏ impossible keys trước Redis.
* Rate limiting kiểm soát abusive request volume.
* Bloom filter có thể hữu ích ở scale rất lớn để test membership probabilistically, nhưng thêm complexity/false positives và thường không cần cho enterprise CRUD thông thường.

## 9. Trade-offs

### Advantages

* Giảm repeated database misses.
* Implementation đơn giản với TTL ngắn.
* Bảo vệ downstream capacity tốt hơn cache-aside thuần túy.

### Costs / Risks

* Tạm thời stale-negative sau khi resource được tạo.
* Thêm một cache semantic cần quan sát/invalidate.
* Không thay thế abuse protection.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss không phải lúc nào cũng dẫn tới dữ liệu có thể cache.

### Middle

Implement negative marker + TTL và test not-found path.

### Senior

Phân biệt penetration/stampede/hot key, đo miss traffic và phối hợp rate limiting.

### Technical Lead / Architect

Quyết định liệu negative caching có cần thiết dựa trên DB cost, public exposure, data creation semantics và acceptable stale window.

## 11. Key takeaway

* “Không tồn tại” cũng có thể là thông tin đáng cache trong thời gian ngắn.
* Negative caching bảo vệ database nhưng phải cân bằng với freshness.
* Validation + rate limiting thường là phần còn lại của giải pháp, không chỉ Redis.

# 6. Modular Monolith: module boundary, data ownership và khi nào chưa cần Microservices

## 1. What is it?

Modular Monolith là một application deployable unit nhưng được chia thành các modules có boundary rõ về business responsibility, dependencies và data ownership.

Mental model: “monolith” mô tả deployment topology; “modular” mô tả internal boundaries. Nó không đồng nghĩa một solution có nhiều folders/projects là đã modular.

## 2. Why does it exist?

Một monolith không có boundaries dễ trở thành shared-everything system: mọi module query bảng của nhau, gọi service internals của nhau và dùng chung domain objects. Mỗi change có blast radius lớn.

Microservices có thể tạo isolation mạnh hơn nhưng mang network failure, distributed tracing, messaging, deployment coordination và data consistency complexity. Modular Monolith giữ process/deployment đơn giản trong khi buộc team luyện đúng boundaries trước.

## 3. How does it work?

Ví dụ business modules:

```text
                ┌────────────────────┐
                │    Web/API Host    │
                └─────────┬──────────┘
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
    Timesheets         Payroll        Employees
      Module            Module          Module
        │                 │               │
        ▼                 ▼               ▼
   Own schema/data    Own schema/data  Own schema/data
```

Các modules giao tiếp qua explicit contracts/application interfaces hoặc internal events, không bằng cách truy cập thẳng entity/repository của module khác.

## 4. Practical implementation

Một public module contract:

```csharp
public interface IEmployeeDirectory
{
    Task<EmployeeSummary?> FindAsync(Guid employeeId, CancellationToken ct);
}
```

Timesheets module phụ thuộc contract này, không phụ thuộc `EmployeeDbContext` hay `Employee` entity nội bộ.

Composition root có thể wire implementation trong cùng process:

```csharp
services.AddScoped<IEmployeeDirectory, EmployeeDirectory>();
```

Không cần HTTP chỉ để hai modules trong cùng process nói chuyện.

## 5. Real production scenario

Employee platform có Employees, Timesheets, Leave, Payroll. Team định tách thành Microservices ngay, nhưng chỉ có 6 developers và một release train chung. Operational burden của 4 databases, Service Bus, tracing, retry và independent deployments lớn hơn business benefit.

Modular Monolith cho phép mỗi module sở hữu schema/tables và contracts rõ. Nếu Payroll sau này có scaling/compliance/team ownership khác biệt, boundary đã rõ để extract thành service.

## 6. Failure scenario & troubleshooting

**Symptom** → “Modular Monolith” nhưng change ở Timesheets vẫn phải sửa Payroll internals.

**Evidence** → Cross-module project references, shared EF entities, direct SQL joins vào tables module khác.

**Hypothesis** → Boundary chỉ tồn tại trong folders, không tồn tại trong dependency/data ownership.

**Diagnosis** → Vẽ dependency graph, search cross-module DbContext/table access và shared domain types.

**Fix** → Tạo explicit module APIs/contracts, move ownership về module, dùng integration event khi coupling thời gian không cần synchronous.

**Verification** → Architecture tests/project references và code review đảm bảo forbidden dependencies không quay lại.

## 7. Common mistakes

* Mỗi module là một folder nhưng share toàn bộ database model.
* Dùng MediatR xuyên modules và coi đó là boundary.
* Tạo internal HTTP giữa modules cùng process mà không có lý do.
* Tách module theo technical layer thay vì business capability.
* Chọn Microservices vì “Senior architecture phải scale”.

## 8. Alternatives

* Simple Layered Monolith phù hợp hệ thống nhỏ, business complexity thấp.
* Modular Monolith phù hợp khi cần boundary nhưng chưa cần distributed deployment.
* Microservices hợp lý khi có nhu cầu thực về independent deployment/scaling/team ownership/failure isolation và organization đủ khả năng vận hành.

## 9. Trade-offs

### Advantages

* Deployment/operations đơn giản hơn Microservices.
* Transaction trong process/database dễ hơn.
* Boundary tốt tạo đường migration sau này.

### Costs / Risks

* Runtime failure vẫn có thể ảnh hưởng toàn process.
* Discipline cần mạnh vì compiler/database không tự ngăn mọi cross-module shortcut.
* Independent scaling theo module chưa có nếu vẫn một deployment.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business boundary chứ không chỉ namespace.

### Middle

Implement module contracts và tránh direct cross-module persistence access.

### Senior

Thiết kế data ownership, synchronous/internal events và architecture tests.

### Technical Lead / Architect

Quyết định liệu Microservices có giải quyết constraint thực hay chỉ chuyển code coupling thành distributed-system coupling; xác định extraction seams nếu tương lai cần tách.

## 11. Key takeaway

* Modular Monolith có thể là architecture đích, không chỉ bước tạm.
* Boundary thật nằm ở dependencies + data ownership + contracts.
* Không trả network/distributed-systems tax trước khi business/scale/team ownership yêu cầu.

# 7. Azure Service Bus Sessions: ordering, competing consumers và bottleneck theo session key

## 1. What is it?

Azure Service Bus Sessions cho phép group messages bằng `SessionId` để xử lý tuần tự theo session và giữ state/session lock semantics. Đây là công cụ để đạt ordered processing **trong một logical stream**, không phải global ordering cho toàn queue.

Ví dụ mọi events của một `OrderId` dùng cùng SessionId để tránh `OrderShipped` được xử lý trước `OrderPaid` trong consumer workflow yêu cầu order.

## 2. Why does it exist?

Queue với competing consumers tăng throughput nhưng messages có thể được xử lý song song và completion order không đảm bảo. Nếu business invariant phụ thuộc sequence theo entity, concurrency tự do có thể phá state machine.

Global serialization toàn queue giữ order nhưng làm throughput sụp. Sessions tạo compromise: serial trong mỗi key, parallel giữa keys.

## 3. How does it work?

```text
Session A: A1 -> A2 -> A3   (serial)
Session B: B1 -> B2         (serial)
Session C: C1 -> C2 -> C3   (serial)

A, B, C có thể được consumers xử lý song song.
```

Receiver accept một session và giữ session lock. Messages cùng session được nhận theo sequence semantics của Service Bus trong phạm vi đó, nhưng application vẫn phải xử lý retries/duplicates.

## 4. Practical implementation

Sender:

```csharp
var message = new ServiceBusMessage(BinaryData.FromObjectAsJson(evt))
{
    MessageId = evt.EventId.ToString("N"),
    SessionId = evt.OrderId.ToString("N")
};

await sender.SendMessageAsync(message, ct);
```

Processor:

```csharp
var options = new ServiceBusSessionProcessorOptions
{
    AutoCompleteMessages = false,
    MaxConcurrentSessions = 16,
    MaxConcurrentCallsPerSession = 1
};

await using var processor = client.CreateSessionProcessor(
    queueName,
    options);
```

Business handler vẫn nên idempotent vì lock expiration/redelivery vẫn có thể tạo duplicate processing.

## 5. Real production scenario

Order workflow phát `OrderCreated`, `PaymentConfirmed`, `OrderCancelled`. Nếu cùng order được xử lý bởi nhiều consumers song song, cancellation có thể commit trước payment update và state transition conflict.

Session theo `OrderId` giữ sequence per order trong khi hàng nghìn orders khác vẫn chạy parallel.

## 6. Failure scenario & troubleshooting

**Symptom** → Queue backlog lớn dù CPU consumers thấp.

**Evidence** → Một SessionId có hàng chục nghìn messages; `MaxConcurrentSessions` cao nhưng hot session chỉ có một processing lane.

**Hypothesis** → Session key tạo hot partition/serialization bottleneck.

**Diagnosis** → Measure backlog theo session/business key, handler duration và session lock renewals.

**Fix** → Chọn granularity SessionId tốt hơn nếu business semantics cho phép; tối ưu handler; tránh một tenant/global ID làm single session cho toàn traffic.

**Verification** → Throughput tăng giữa sessions, ordering tests vẫn đúng cho entity cần sequence.

## 7. Common mistakes

* Nghĩ Sessions tạo exactly-once processing.
* Dùng một SessionId cho toàn queue để “đảm bảo order”.
* Không set `MessageId`/idempotency strategy.
* Handler chạy lâu hơn lock mà không hiểu auto lock renewal.
* Retry non-idempotent side effect.

## 8. Alternatives

* Không dùng ordering nếu business operation thực sự commutative/idempotent.
* Optimistic version check ở consumer có thể reject stale event mà không serialize mọi processing.
* Partitioned event streaming platforms phù hợp workloads streaming lớn, nhưng mang operational/model complexity khác.

## 9. Trade-offs

### Advantages

* Ordered processing theo business key.
* Parallelism giữa independent sessions.
* Hữu ích cho workflow/state machine.

### Costs / Risks

* Hot session giới hạn throughput.
* Session-aware client/processor phức tạp hơn queue thường.
* Vẫn phải xử lý duplicate, poison message và lock failure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu queue consumers có thể chạy song song và order không mặc định theo business entity.

### Middle

Set SessionId, cấu hình session processor và handle settlement/DLQ.

### Senior

Thiết kế idempotency, lock duration, hot session diagnosis và state versioning.

### Technical Lead / Architect

Quyết định liệu ordering có thật sự là invariant hay system có thể thiết kế operations commutative hơn để giữ throughput cao.

## 11. Key takeaway

* Sessions cung cấp order theo key, không phải global order miễn phí.
* Một bad SessionId có thể biến queue scale-out thành single-thread bottleneck.
* Ordering không loại bỏ nhu cầu idempotency và duplicate handling.

# 8. IIS Application Pool recycling: process lifecycle, cold start và failure mode trong enterprise hosting

## 1. What is it?

IIS Application Pool cô lập một hoặc nhiều web applications trong worker process (`w3wp.exe`). Recycling là việc IIS thay worker process bằng process mới theo config hoặc trigger như scheduled recycle, memory threshold, config change hoặc administrative action.

Mental model: application hosted trên IIS **không phải một process sống mãi**. In-memory state, background loops và caches có thể biến mất khi process recycle.

## 2. Why does it exist?

Process isolation và recycling giúp IIS quản lý reliability, configuration changes và long-running process issues. Legacy .NET Framework applications đặc biệt thường dựa vào App Pool lifecycle để recover process hoặc apply deployment/configuration.

Nhưng nếu application giả định process lifetime ổn định, recycle trở thành hidden production failure mode.

## 3. How does it work?

Simplified flow:

```text
IIS
 |
 +--> App Pool
        |
        +--> w3wp old process
        |
        | recycle trigger
        v
        +--> w3wp new process
              |
              -> application startup / warmup
```

Trong overlapped recycling, IIS có thể start process mới trước khi process cũ dừng để giảm downtime, nhưng startup dependencies và long-running requests vẫn cần được hiểu.

## 4. Practical implementation

ASP.NET Core behind IIS nên giữ state ngoài process nếu state cần survive recycle. Health/startup endpoint có thể kiểm tra application đã sẵn sàng phục vụ traffic:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, name: "sql");

app.MapHealthChecks("/health/ready");
```

Không dùng `static Dictionary` làm durable session/job state. Với legacy ASP.NET, cần kiểm tra App Pool settings, preload/warmup và deployment process.

## 5. Real production scenario

Một legacy CMS lưu cache content lớn trong process. App Pool recycle lúc 02:00. Sau recycle, hàng nghìn requests đầu cùng miss cache và query SQL/Search backend, tạo latency spike 5–10 phút dù application không có code deployment nào.

Vấn đề không phải “IIS restart ngẫu nhiên”; nó là cache warmup + dependency capacity problem gắn với known process lifecycle.

## 6. Failure scenario & troubleshooting

**Symptom** → 5xx/latency spike gần cùng giờ mỗi ngày.

**Evidence** → Windows Event Logs/IIS logs cho thấy worker process PID thay đổi; application startup logs trùng thời điểm; cache hit ratio tụt.

**Hypothesis** → Scheduled App Pool recycling gây cold start hoặc startup dependency failure.

**Diagnosis** → Correlate process start timestamps, recycle config, deployment events, memory/private bytes và dependency telemetry.

**Fix** → Điều chỉnh recycle policy dựa trên lý do thực, preload/warmup, externalize critical state, giảm startup coupling.

**Verification** → Theo dõi recycle kế tiếp: readiness, error rate, p95/p99 và dependency load không spike ngoài SLO.

## 7. Common mistakes

* Tắt recycling hoàn toàn để che memory leak.
* Lưu scheduled-job state trong memory rồi giả định không mất.
* Không log process instance/PID/start time.
* Deploy file trực tiếp vào live directory mà không hiểu file lock/restart behavior.
* Coi App Pool recycle là “hạ tầng lo”, không đưa vào reliability design.

## 8. Alternatives

* Azure App Service vẫn có process restart/recycle semantics, chỉ khác operational interface.
* Windows Service/Worker Service phù hợp một số background workloads nhưng cũng phải handle restart.
* Containers/Kubernetes thay process lifecycle bằng pod/container lifecycle; không loại bỏ ephemeral-process assumption.

## 9. Trade-offs

### Advantages

* Isolation giữa applications.
* Operational recovery/configuration model quen thuộc trong enterprise Windows hosting.
* Overlapped recycle có thể giảm downtime.

### Costs / Risks

* Cold start và in-memory state loss.
* Legacy configuration nhiều knobs khó quan sát.
* Scheduled recycle có thể che memory/resource leak thay vì sửa root cause.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu IIS app không chạy mãi trong cùng `w3wp.exe`.

### Middle

Biết đọc IIS logs/Event Viewer, App Pool config và troubleshoot startup/recycle.

### Senior

Correlate lifecycle với cache, session, background work, deployment và dependency load.

### Technical Lead / Architect

Thiết kế application để process restart là normal event; quyết định khi nào legacy IIS hosting vẫn đủ và khi nào modernization mang value thật.

## 11. Key takeaway

* Process restart/recycle là expected lifecycle event, không phải exception hiếm.
* Critical state không nên phụ thuộc lifetime của `w3wp.exe`.
* Recycle spike phải được điều tra bằng process + application + dependency telemetry cùng lúc.

# 9. SSRF trong third-party integrations: outbound request cũng là security boundary

## 1. What is it?

Server-Side Request Forgery (SSRF) xảy ra khi attacker ảnh hưởng được URL/host mà server gọi outbound, khiến server truy cập tài nguyên attacker không trực tiếp truy cập được: internal services, metadata endpoints, loopback hoặc private network.

Mental model: outbound HTTP không tự động an toàn chỉ vì request đi **từ server ra ngoài**. Nếu user-controlled input quyết định destination, đó là security boundary.

## 2. Why does it exist?

Các feature như “import image from URL”, webhook testing, PDF from URL, URL preview, third-party callback validation đều cần server fetch remote content.

Naive implementation:

```csharp
await httpClient.GetStringAsync(userProvidedUrl);
```

biến application server thành network proxy có quyền truy cập lớn hơn attacker.

## 3. How does it work?

```text
Attacker
   |
   | supplies URL
   v
Public API
   |
   v
Server-side HttpClient
   |
   +--> expected public host
   |
   +--> 127.0.0.1 / private IP / metadata service / internal DNS
```

Redirects và DNS resolution làm defense khó hơn: URL ban đầu có thể hợp lệ nhưng redirect tới forbidden network; DNS có thể resolve khác theo thời điểm.

## 4. Practical implementation

An toàn nhất là allowlist destinations khi integration domain đã biết:

```csharp
private static readonly HashSet<string> AllowedHosts =
    new(StringComparer.OrdinalIgnoreCase)
    {
        "api.partner.example",
        "cdn.partner.example"
    };

public static Uri ValidatePartnerUri(string raw)
{
    if (!Uri.TryCreate(raw, UriKind.Absolute, out var uri))
        throw new ValidationException("Invalid URL");

    if (uri.Scheme != Uri.UriSchemeHttps)
        throw new ValidationException("HTTPS required");

    if (!AllowedHosts.Contains(uri.Host))
        throw new ValidationException("Host is not allowed");

    return uri;
}
```

Với arbitrary public URL feature, cần defense sâu hơn: resolve DNS, reject loopback/private/link-local ranges, control redirects, enforce timeout/size/content type và egress network policy.

## 5. Real production scenario

Marketing CMS có feature “preview remote image”. Editor paste URL; endpoint fetch ảnh để tạo thumbnail. Attacker có editor credential thấp quyền nhưng nhập URL tới internal admin endpoint. Server có network access nên response internal bị fetch thành thumbnail/error metadata.

Một feature tưởng chỉ là image utility đã trở thành lateral-movement path.

## 6. Failure scenario & troubleshooting

**Symptom** → Outbound logs xuất hiện requests tới private IP/localhost hoặc cloud metadata-style addresses.

**Evidence** → Request input chứa unusual URL/redirect; DNS resolution hoặc redirect chain đi vào internal range.

**Hypothesis** → SSRF attempt hoặc insufficient destination validation.

**Diagnosis** → Preserve security telemetry: normalized host, resolved destination class, redirect chain, caller identity; không log secrets/query tokens không cần thiết.

**Fix** → Allowlist khi có thể; block private/link-local/loopback after resolution; disable or validate redirects; apply egress firewall/private network controls.

**Verification** → Security tests với localhost, IPv6 loopback, private RFC1918 ranges, encoded IP forms, redirect-to-private và DNS edge cases.

## 7. Common mistakes

* Chặn chuỗi `localhost` nhưng cho phép `127.0.0.1`, IPv6 hoặc integer IP representation.
* Validate URL trước redirect nhưng không validate destination sau redirect.
* Chỉ regex URL string mà không parse/resolve.
* Dùng shared HttpClient có privileged internal headers cho arbitrary destinations.
* Cho response unlimited size, tạo thêm memory/DoS risk.

## 8. Alternatives

* Client-side fetch không phải lúc nào khả thi do CORS/credentials nhưng giảm server network privilege trong một số feature.
* Dedicated fetch proxy/sandbox với restricted egress giảm blast radius cho arbitrary URL ingestion.
* Pre-signed upload để user upload asset trực tiếp có thể loại bỏ nhu cầu server fetch remote URL.

## 9. Trade-offs

### Advantages

Server-side integrations cần thiết cho nhiều workflows và giữ credentials khỏi browser.

### Costs / Risks

* Server network position tạo privilege.
* Arbitrary destination validation phức tạp hơn vẻ ngoài.
* Strict allowlist giảm flexibility nhưng tăng security đáng kể.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu user-controlled URL không được truyền thẳng vào `HttpClient`.

### Middle

Parse/validate URI, timeout, content size và implement allowlist cho known integrations.

### Senior

Xử lý redirects, DNS resolution, IP ranges, credential leakage và egress controls; threat-model toàn fetch flow.

### Technical Lead / Architect

Quyết định arbitrary URL fetching có thật sự cần không; nếu có, đặt nó trong network/security boundary với least privilege và observable egress.

## 11. Key takeaway

* Outbound requests là security-sensitive khi destination chịu ảnh hưởng từ user input.
* Allowlist known partners đơn giản và mạnh hơn blacklist URL tricks.
* Application validation + network egress policy tạo defense-in-depth tốt hơn một lớp code duy nhất.

# 10. RAG evaluation: đo retrieval, grounding và answer quality thay vì chỉ “prompt thấy ổn”

## 1. What is it?

RAG (Retrieval-Augmented Generation) kết hợp retrieval từ knowledge source với LLM generation. Evaluation của RAG phải tách ít nhất hai failure domains:

1. **Retrieval quality** — hệ thống có lấy đúng evidence không?
2. **Generation/grounding quality** — model có trả lời đúng dựa trên evidence đó không?

Mental model quan trọng: một answer sai không mặc định là “model hallucination”; có thể retriever đã đưa sai/chưa đủ context.

## 2. Why does it exist?

Demo RAG thường được đánh giá bằng vài câu hỏi developer tự thử và cảm thấy câu trả lời “có vẻ đúng”. Cách này không phát hiện regression khi đổi embedding model, chunk size, top-k, reranker, prompt hoặc source documents.

Một production AI system cần test set + measurable criteria giống software/data system khác, dù output có probabilistic behavior.

## 3. How does it work?

Evaluation pipeline:

```text
Question set
    |
    v
Retriever
    |
    +--> Retrieval metrics / evidence inspection
    v
Retrieved context
    |
    v
LLM
    |
    +--> correctness
    +--> groundedness
    +--> citation/evidence support
    +--> refusal when evidence missing
```

Một useful dataset chứa question, expected evidence/source và expected answer characteristics, không nhất thiết chỉ một exact string.

## 4. Practical implementation

Ví dụ test case schema trong C#:

```csharp
public sealed record RagEvalCase(
    string Id,
    string Question,
    IReadOnlyList<string> ExpectedDocumentIds,
    string ExpectedFact);

public sealed record RagEvalResult(
    string CaseId,
    IReadOnlyList<string> RetrievedDocumentIds,
    string Answer,
    bool ExpectedEvidenceRetrieved,
    bool ExpectedFactPresent);
```

Một deterministic first layer có thể kiểm tra expected document ID xuất hiện trong top-k. Sau đó LLM-as-judge có thể bổ sung semantic grading, nhưng không nên là metric duy nhất và judge prompt/model phải versioned.

## 5. Real production scenario

Internal engineering assistant trả lời deployment runbook. Team đổi chunk size từ 1.500 xuống 300 tokens để “retrieval chính xác hơn”. Search score nhìn tốt hơn nhưng procedure nhiều bước bị tách thành chunks rời, model bỏ mất rollback prerequisite.

Nếu eval set có câu hỏi yêu cầu full deployment sequence và expected evidence IDs, regression được phát hiện trước release.

## 6. Failure scenario & troubleshooting

**Symptom** → User báo answer sai sau khi đổi embedding/retrieval config.

**Evidence** → Trace cho thấy expected document không nằm trong top-k; model trả lời hợp lý theo context nhưng context thiếu.

**Hypothesis** → Retrieval regression, không phải generation regression.

**Diagnosis** → Replay exact question với versioned corpus/index, inspect retrieved chunks/scores/filters; sau đó chạy generation trên known-good evidence để isolate layer.

**Fix** → Điều chỉnh chunking/query transformation/filter/reranking hoặc corpus quality; không bắt đầu bằng prompt engineering nếu evidence chưa vào context.

**Verification** → Run offline eval suite, compare baseline metrics và canary production feedback before full rollout.

## 7. Common mistakes

* Chỉ đo answer fluency.
* Không version corpus/index/prompt/model trong traces.
* Dùng LLM-as-judge như oracle duy nhất.
* Test chỉ happy-path questions có câu trả lời rõ.
* Không test “evidence không tồn tại” và refusal behavior.
* Tăng top-k vô hạn để “chắc có context”, làm tăng token cost/noise.

## 8. Alternatives

* Fine-tuning có thể phù hợp behavior/style/specialized task nhưng không giải quyết dynamic knowledge retrieval giống RAG.
* Plain search + deterministic UI tốt hơn RAG nếu users cần exact documents hơn synthesized answer.
* Tool Calling tới authoritative API tốt hơn embeddings cho live structured facts như order status hoặc account balance.

## 9. Trade-offs

### Advantages

* RAG có thể ground answer vào private/current corpus mà không retrain model.
* Evaluation tách retrieval/generation giúp debug có hệ thống.

### Costs / Risks

* Nhiều moving parts: corpus, chunks, embeddings, filters, reranking, prompt, model.
* Offline metrics không phản ánh toàn bộ production user behavior.
* Judge models thêm cost và probabilistic variance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG gồm retrieval trước, generation sau; answer quality phụ thuộc cả hai.

### Middle

Build eval dataset, log retrieved evidence và test expected document retrieval.

### Senior

Thiết kế retrieval/generation metrics, regression gates, versioning và failure isolation bằng traces.

### Technical Lead / Architect

Quyết định use case nào cần RAG, use case nào nên dùng deterministic search/API; đặt quality, latency, cost và data-security SLO cho AI feature.

## 11. Key takeaway

* Khi RAG sai, hãy hỏi trước: “evidence đúng có được retrieve không?”
* Eval phải versioned và chạy lại khi đổi corpus, chunking, embeddings, prompt hoặc model.
* Deterministic checks + human review + model-based grading bổ sung nhau; không lớp nào nên là oracle duy nhất.
