# 1. .NET `IAsyncDisposable`: async cleanup, ownership và shutdown correctness

## 1. What is it?

`IAsyncDisposable` biểu diễn resource có quá trình cleanup cần asynchronous I/O. Mental model không phải “`IDisposable` nhưng có `await`”, mà là **ownership contract**: code nào sở hữu resource phải bảo đảm quá trình release hoàn tất mà không block thread.

## 2. Why does it exist?

Một số cleanup cần flush network stream, hoàn tất transaction hoặc đóng resource qua I/O. Ép quá trình đó vào `Dispose()` thường dẫn tới sync-over-async, bỏ qua lỗi cleanup hoặc đóng resource trước khi dữ liệu được flush.

## 3. How does it work?

`await using` được compiler hạ thành `try/finally`; trong `finally`, runtime gọi `DisposeAsync()` và await `ValueTask` trả về. Scope vì vậy vẫn deterministic, nhưng cleanup có thể nhường thread trong lúc chờ I/O.

## 4. Practical implementation

```csharp
await using var stream = new FileStream(
    path,
    FileMode.Create,
    FileAccess.Write,
    FileShare.None,
    64 * 1024,
    FileOptions.Asynchronous);

await JsonSerializer.SerializeAsync(stream, payload, cancellationToken);
await stream.FlushAsync(cancellationToken);
```

Nếu class sở hữu một async-disposable dependency, chính class đó phải propagate lifecycle thay vì trông chờ GC.

## 5. Real production scenario

Worker xuất báo cáo lớn lên storage. Nếu process nhận shutdown signal, resource cần được flush/close đúng thứ tự trước khi pod bị terminate. Cleanup không hoàn tất có thể để file thiếu dữ liệu dù business log đã ghi “completed”.

## 6. Failure scenario & troubleshooting

**Symptom** → file đôi khi bị truncate khi deploy.  
**Evidence** → lỗi tập trung quanh thời điểm shutdown; trace kết thúc trước operation flush.  
**Hypothesis** → resource bị dispose không đúng lifecycle.  
**Diagnosis** → fire-and-forget cleanup và host dừng trước khi await hoàn tất.  
**Fix** → ownership rõ ràng, `await using`, propagate cancellation hợp lý và đủ shutdown grace period.  
**Verification** → rolling deployment trong lúc xử lý file không tạo artifact hỏng.

## 7. Common mistakes

Gọi `.DisposeAsync().AsTask().Wait()`; dispose dependency mà object không sở hữu; vừa đăng ký resource trong DI vừa tự dispose; dùng finalizer như cơ chế cleanup chính.

## 8. Alternatives

`IDisposable` phù hợp khi cleanup hoàn toàn synchronous. Host-managed DI lifecycle phù hợp cho singleton/scoped service do container sở hữu. Không cần `IAsyncDisposable` nếu cleanup không thực hiện asynchronous work thực sự.

## 9. Trade-offs

### Advantages

Cleanup deterministic mà không block thread; biểu đạt ownership rõ hơn cho async resource.

### Costs / Risks

Lifecycle phức tạp hơn; shutdown cần thời gian; exception trong cleanup phải được quan sát; ownership sai có thể gây double-dispose.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `using` quản lý lifetime và `await using` dùng cho async cleanup.

### Middle

Implement `IAsyncDisposable`, propagate cancellation và test cleanup path.

### Senior

### Technical Lead / Architect

Quyết định resource nào thuộc application, host hay request scope; thiết kế shutdown budget và recovery khi cleanup không hoàn tất.

## 11. Key takeaway

- Async cleanup vẫn là một phần của correctness.
- Ownership quan trọng hơn bản thân API `DisposeAsync`.
- Không block async cleanup bằng `.Wait()` hoặc `.Result`.

# 2. ASP.NET Core rate limiting: bảo vệ capacity thay vì chỉ chặn traffic

## 1. What is it?

Rate limiting giới hạn tốc độ hoặc concurrency mà một caller được phép đưa vào một resource. Mental model: đây là **capacity protection boundary**, không chỉ là chống bot.

## 2. Why does it exist?

Nếu API nhận traffic nhanh hơn tốc độ database/downstream có thể xử lý, queue nội bộ tăng, latency tăng và cuối cùng toàn hệ thống timeout. Reject sớm một phần request có thể giữ phần còn lại khỏe.

## 3. How does it work?

ASP.NET Core có fixed window, sliding window, token bucket và concurrency limiter. Request đi qua middleware, partition key được xác định, limiter cấp permit hoặc trả rejection. Chọn key theo user/API key/tenant thường hữu ích hơn chỉ theo IP.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddTokenBucketLimiter("write-api", o =>
    {
        o.TokenLimit = 100;
        o.TokensPerPeriod = 50;
        o.ReplenishmentPeriod = TimeSpan.FromSeconds(1);
        o.QueueLimit = 20;
        o.AutoReplenishment = true;
    });

    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});

app.UseRateLimiter();
```

Endpoint write có thể gắn policy riêng thay vì áp một quota giống nhau cho mọi route.

## 5. Real production scenario

Tenant import hàng nghìn request cập nhật sản phẩm. Không có limiter, SQL connection pool bị chiếm hết và cả request đọc của tenant khác timeout.

## 6. Failure scenario & troubleshooting

**Symptom** → 429 tăng mạnh hoặc API vẫn collapse dù đã bật limiter.  
**Evidence** → permit rejection, queue length, DB latency và downstream saturation.  
**Hypothesis** → policy không phản ánh bottleneck thực hoặc partition key quá thô.  
**Diagnosis** → limiter 1.000 RPS trong khi DB chỉ chịu 200 concurrent writes.  
**Fix** → đo capacity, dùng concurrency limit cho scarce resource, quota theo tenant và trả `Retry-After` phù hợp.  
**Verification** → load test cho thấy p99 của accepted traffic ổn định khi overload.

## 7. Common mistakes

Dùng IP khi traffic đi qua proxy mà chưa xử lý forwarded headers; quota toàn cục làm tenant noisy ảnh hưởng tenant khác; queue quá dài biến limiter thành nơi tích latency; retry 429 ngay lập tức.

## 8. Alternatives

API Gateway/Front Door có thể enforce policy ở edge; queue phù hợp nếu work có thể xử lý bất đồng bộ; autoscaling hữu ích nếu bottleneck thực sự scale ngang được.

## 9. Trade-offs

### Advantages

Fail fast, bảo vệ dependency và tạo fairness.

### Costs / Risks

Có intentional rejection; distributed quota cần coordination; policy sai có thể throttle khách hàng hợp lệ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 429 và vì sao overload không nên luôn được queue.

### Middle

Cấu hình policy, partition key và test rejection.

### Senior

Liên hệ limiter với downstream capacity, retries và tail latency.

### Technical Lead / Architect

Xác định boundary nào cần admission control, fairness giữa tenant và capacity budget end-to-end.

## 11. Key takeaway

- Rate limit nên bảo vệ bottleneck thật.
- Queue vô hạn không tạo thêm capacity.
- Policy cần được kiểm chứng bằng load test và telemetry.

# 3. EF Core optimistic concurrency: phát hiện lost update bằng concurrency token

## 1. What is it?

Optimistic concurrency giả định conflict hiếm, cho phép nhiều request đọc cùng dữ liệu nhưng kiểm tra dữ liệu có thay đổi trước khi ghi. Nó bảo vệ khỏi **lost update**, không khóa row trong toàn bộ thời gian người dùng suy nghĩ.

## 2. Why does it exist?

Hai nhân viên mở cùng một đơn hàng. A sửa địa chỉ, B sửa trạng thái dựa trên version cũ. Nếu mỗi `UPDATE` chỉ dùng primary key, người ghi sau có thể âm thầm ghi đè thay đổi trước.

## 3. How does it work?

Với SQL Server `rowversion`, EF Core đưa token vào `WHERE`:

```sql
UPDATE Orders
SET Status = @status
WHERE Id = @id AND RowVersion = @originalRowVersion;
```

Nếu affected rows = 0, EF Core ném `DbUpdateConcurrencyException`.

## 4. Practical implementation

```csharp
public sealed class Order
{
    public int Id { get; set; }
    public string Status { get; set; } = "";
    [Timestamp]
    public byte[] RowVersion { get; set; } = [];
}

try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new ProblemDetails
    {
        Title = "Order was modified by another operation."
    });
}
```

Client cần nhận version và gửi lại khi update nếu workflow trải qua HTTP round trip.

## 5. Real production scenario

Approval workflow có manager và background reconciliation cùng cập nhật record. Conflict phải được phát hiện và business logic quyết định retry, merge hay yêu cầu reload.

## 6. Failure scenario & troubleshooting

**Symptom** → người dùng thấy dữ liệu vừa lưu bị “quay lại” giá trị khác.  
**Evidence** → audit log có hai update gần nhau.  
**Hypothesis** → lost update.  
**Diagnosis** → update chỉ predicate theo ID, không có version.  
**Fix** → concurrency token + explicit conflict handling.  
**Verification** → integration test chạy hai `DbContext` trên cùng version; write thứ hai nhận conflict.

## 7. Common mistakes

Catch exception rồi retry mù quáng với cùng stale state; không trả version qua API; dùng optimistic concurrency nhưng business operation lại cần serialize tuyệt đối; nhầm concurrency token với transaction.

## 8. Alternatives

Pessimistic locking phù hợp critical section ngắn cần khóa; ETag/`If-Match` đưa concurrency contract lên HTTP; domain-specific compare-and-set có thể kiểm tra đúng field quan trọng.

## 9. Trade-offs

### Advantages

Không giữ lock dài; scale tốt khi conflict hiếm.

### Costs / Risks

Caller phải xử lý conflict; merge phức tạp; conflict cao có thể gây retry churn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu lost update và version token.

### Middle

Implement token, HTTP contract và integration test.

### Senior

Chọn retry/merge/reject theo invariant nghiệp vụ.

### Technical Lead / Architect

Quyết định consistency model theo aggregate, conflict frequency và UX.

## 11. Key takeaway

- Optimistic concurrency phát hiện stale write, không tự giải quyết conflict.
- Conflict handling là business decision.
- Test bằng nhiều context/transaction thực thay vì mock.

# 4. SQL Server keyset pagination: ổn định latency khi dataset tăng lớn

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên key cuối cùng đã thấy thay vì bỏ qua N row bằng `OFFSET`. Mental model: “tiếp tục từ vị trí này” thay vì “đếm lại từ đầu rồi bỏ đi”.

## 2. Why does it exist?

`OFFSET 500000 ROWS` vẫn buộc database xử lý lượng row lớn trước khi trả vài chục row. Khi page sâu, I/O và CPU tăng dù response size không đổi.

## 3. How does it work?

Với thứ tự `CreatedAt DESC, Id DESC`, cursor chứa cả hai giá trị để tạo ordering deterministic:

```sql
SELECT TOP (50) Id, CreatedAt, Status
FROM Orders
WHERE CreatedAt < @lastCreatedAt
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index phù hợp với access pattern giúp seek tới vùng cần đọc thay vì scan/skip.

## 4. Practical implementation

EF Core có thể biểu diễn cùng predicate và `Take(50)`. Cursor nên encode opaque token chứa sort keys, được validate server-side.

## 5. Real production scenario

Trang audit log có hàng chục triệu record. Page 1 nhanh nhưng page 10.000 với offset mất vài giây. Keyset giữ latency gần ổn định khi người dùng duyệt tuần tự.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 endpoint tăng theo page number.  
**Evidence** → execution plan và logical reads tăng ở deep page.  
**Hypothesis** → offset scan.  
**Diagnosis** → `OFFSET/FETCH` trên tập lớn.  
**Fix** → stable ordering + keyset predicate + supporting index.  
**Verification** → so sánh logical reads và duration ở đầu/cuối dataset.

## 7. Common mistakes

Sort bằng cột không unique nhưng cursor chỉ giữ một field; index order không khớp; cho phép “jump tới page 973” nhưng lại dùng keyset; expose cursor dễ bị sửa mà không validate.

## 8. Alternatives

Offset pagination đơn giản và phù hợp dataset nhỏ hoặc UI cần page number. Search engine có cursor/search-after cho search workload. Snapshot/export job phù hợp báo cáo lớn.

## 9. Trade-offs

### Advantages

Latency ổn định hơn, ít work dư, chịu concurrent insert tốt hơn.

### Costs / Risks

Không tiện random page; cursor contract phức tạp; sort tùy ý cần nhiều index/access path.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác biệt skip N với seek sau key.

### Middle

Implement deterministic sort và cursor.

### Senior

Đọc execution plan, logical reads và thiết kế composite index.

### Technical Lead / Architect

Chọn pagination contract dựa trên UX, scale, consistency và query flexibility.

## 11. Key takeaway

- Pagination là database access pattern, không chỉ API DTO.
- Keyset cần ordering deterministic.
- Đo logical reads thay vì chỉ nhìn thời gian trên máy local.

# 5. Redis cache stampede: request coalescing, TTL jitter và stale fallback

## 1. What is it?

Cache stampede xảy ra khi nhiều request cùng thấy một hot key hết hạn/missing rồi đồng thời đánh vào source of truth. Cache miss đơn lẻ biến thành burst lên database/API.

## 2. Why does it exist?

TTL làm nhiều caller cùng chuyển trạng thái hit → miss tại một thời điểm. Nếu recompute đắt, 1.000 request có thể tạo 1.000 query giống nhau.

## 3. How does it work?

Flow xấu:

```text
Hot key expires
  -> N requests miss
  -> N database queries
  -> database slows
  -> requests overlap longer
  -> more pressure
```

Mitigation thường kết hợp single-flight/request coalescing, TTL jitter, stale-while-revalidate hoặc background refresh.

## 4. Practical implementation

Trong một instance, có thể coalesce bằng `SemaphoreSlim` theo key; trong distributed system cần cân nhắc distributed coordination hoặc chấp nhận một số duplicate refresh. TTL nên có jitter để nhiều key không hết hạn cùng giây.

## 5. Real production scenario

Product-detail cache có campaign traffic lớn. Sau deploy, cache cold và hàng nghìn SKU đồng thời miss; SQL CPU tăng 95% dù Redis vẫn healthy.

## 6. Failure scenario & troubleshooting

**Symptom** → DB spike định kỳ theo TTL.  
**Evidence** → cache miss ratio tăng theo nhịp, query giống nhau bùng lên.  
**Hypothesis** → synchronized expiration/stampede.  
**Diagnosis** → hot key TTL cố định, không coalescing.  
**Fix** → jitter, single-flight, prewarm hot keys hoặc stale fallback nếu business cho phép.  
**Verification** → source request count không tăng tuyến tính với client miss burst.

## 7. Common mistakes

Dùng distributed lock không timeout; lock Redis trở thành dependency còn nguy hiểm hơn query gốc; cache mọi thứ; TTL giống nhau cho toàn bộ key; không định nghĩa stale tolerance.

## 8. Alternatives

Không cache nếu DB đã đủ nhanh; local cache L1 giảm round trip nhưng tăng consistency complexity; materialized read model hữu ích nếu computation thực sự là projection lâu dài.

## 9. Trade-offs

### Advantages

Giảm burst và bảo vệ source of truth.

### Costs / Risks

Stale data, coordination complexity, memory và observability burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss không phải lúc nào cũng vô hại.

### Middle

Implement TTL/jitter và metrics hit/miss.

### Senior

Thiết kế coalescing, stale policy và failure fallback.

### Technical Lead / Architect

Quyết định liệu cache có đáng tồn tại và ai sở hữu invalidation/freshness SLO.

## 11. Key takeaway

- Cache có thể khuếch đại failure nếu miss đồng loạt.
- TTL là consistency và load-control decision.
- Không thêm distributed lock nếu chi phí coordination vượt lợi ích.

# 6. Azure Service Bus lock renewal: long-running consumer và duplicate delivery

## 1. What is it?

Trong Peek-Lock mode, consumer nhận message với một lock tạm thời. Message chưa bị xóa cho tới khi consumer `Complete`. Lock renewal kéo dài quyền xử lý khi operation lâu hơn lock duration.

## 2. Why does it exist?

Broker cần recover message nếu consumer chết. Vì vậy lock không thể vĩnh viễn. Nhưng work thực tế như tạo PDF hoặc gọi external system có thể lâu hơn lock ban đầu.

## 3. How does it work?

Consumer nhận message → broker đặt lock → handler xử lý → complete. Nếu lock hết trước complete, message có thể được delivery lại. Auto lock renewal chỉ giảm xác suất; nó không biến Service Bus thành exactly-once.

## 4. Practical implementation

```csharp
var processor = client.CreateProcessor(queueName, new ServiceBusProcessorOptions
{
    MaxConcurrentCalls = 8,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(10)
});

processor.ProcessMessageAsync += async args =>
{
    await handler.HandleAsync(args.Message, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message, args.CancellationToken);
};
```

Side effect quan trọng vẫn cần idempotency key/message ID ở persistence boundary.

## 5. Real production scenario

Consumer xử lý invoice mất 3–7 phút. Một dependency chậm khiến handler vượt renewal budget; cùng invoice được xử lý lần hai và email gửi trùng.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate side effect, `MessageLockLostException`.  
**Evidence** → delivery count > 1, handler duration gần/vượt lock budget.  
**Hypothesis** → lock expired hoặc process restart.  
**Diagnosis** → trace cho thấy work quá dài.  
**Fix** → idempotent consumer, chia nhỏ work, điều chỉnh concurrency/renewal và DLQ policy.  
**Verification** → intentionally kill consumer giữa handler; redelivery không tạo side effect lần hai.

## 7. Common mistakes

Coi auto-renew là exactly-once; complete trước khi side effect durable; retry non-idempotent external call; tăng lock duration thay cho sửa handler quá dài.

## 8. Alternatives

Queue Storage đơn giản hơn cho workload ít feature; Durable Functions phù hợp orchestration dài; chia job thành nhiều message nhỏ có thể giảm lock pressure.

## 9. Trade-offs

### Advantages

Peek-Lock hỗ trợ recover work khi consumer chết.

### Costs / Risks

Duplicate delivery là thực tế; renewal tốn coordination; handler dài khó deploy/shutdown.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu receive không đồng nghĩa message đã biến mất.

### Middle

Configure processor, settlement, retry và DLQ.

### Senior

Thiết kế idempotency và test crash/redelivery.

### Technical Lead / Architect

Quyết định granularity message, processing SLA và transaction boundary giữa broker với side effects.

## 11. Key takeaway

- Lock renewal không đảm bảo exactly-once.
- Consumer phải an toàn trước redelivery.
- Work quá dài thường là tín hiệu cần xem lại granularity.

# 7. Kubernetes readiness probe: traffic admission khác process liveness

## 1. What is it?

Readiness probe trả lời: “Pod này **có nên nhận traffic ngay bây giờ không?**” Liveness trả lời: “Process này có cần restart không?” Hai câu hỏi khác nhau và không nên dùng chung một health condition máy móc.

## 2. Why does it exist?

Application có thể đang chạy nhưng chưa warm-up, đang drain, mất dependency thiết yếu hoặc chưa load configuration. Gửi traffic lúc đó tạo 5xx dù process vẫn sống.

## 3. How does it work?

Kubelet chạy probe. Pod failing readiness bị loại khỏi Service endpoints nhưng không nhất thiết restart. Failing liveness đủ ngưỡng có thể khiến container restart.

## 4. Practical implementation

ASP.NET Core tách tag:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<StartupReadyCheck>("ready", tags: ["ready"])
    .AddCheck<SelfHealthCheck>("live", tags: ["live"]);

app.MapHealthChecks("/health/ready",
    new HealthCheckOptions { Predicate = x => x.Tags.Contains("ready") });

app.MapHealthChecks("/health/live",
    new HealthCheckOptions { Predicate = x => x.Tags.Contains("live") });
```

## 5. Real production scenario

Pod mới cần 20 giây warm cache/config. Nếu readiness báo healthy ngay khi process bind port, rolling deployment đưa traffic vào quá sớm và p99 tăng mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → pod restart loop khi database tạm mất.  
**Evidence** → liveness endpoint kiểm tra DB và fail.  
**Hypothesis** → dependency health bị dùng sai cho process liveness.  
**Diagnosis** → kubelet restart app khỏe về mặt process, làm outage nặng hơn.  
**Fix** → liveness chỉ kiểm tra khả năng process tự tiến triển; dependency gating đặt ở readiness khi thực sự cần.  
**Verification** → mô phỏng DB outage: pod không restart storm, readiness behavior đúng thiết kế.

## 7. Common mistakes

Probe quá nặng; liveness gọi mọi dependency; timeout quá ngắn; không có startup probe cho app khởi động lâu; readiness healthy trước migration/warm-up.

## 8. Alternatives

App Service health check có mục tiêu tương tự ở hosting khác. Load balancer health probes đơn giản hơn nhưng ít hiểu lifecycle của pod.

## 9. Trade-offs

### Advantages

Traffic routing phản ánh trạng thái runtime và hỗ trợ rolling deployment an toàn.

### Costs / Risks

Probe sai có thể tự gây outage; dependency checks tạo thêm traffic; health semantics cần ownership rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt alive với ready.

### Middle

Expose health endpoints và cấu hình probe.

### Senior

Thiết kế semantics, threshold và behavior khi dependency fail.

### Technical Lead / Architect

Quyết định dependency nào thực sự chặn readiness và cách deployment/failover hoạt động khi degraded.

## 11. Key takeaway

- Readiness điều khiển traffic; liveness điều khiển restart.
- Dependency outage không mặc định đồng nghĩa process phải chết.
- Health check là control-plane contract, không chỉ endpoint 200.

# 8. OpenTelemetry metrics: histogram, p95/p99 và cardinality discipline

## 1. What is it?

Metrics mô tả hành vi hệ thống dưới dạng số liệu tổng hợp theo thời gian. Histogram đặc biệt phù hợp latency vì giữ phân phối đủ để backend tính percentile thay vì chỉ average.

## 2. Why does it exist?

Average 100 ms có thể che 1% request mất 8 giây. Production reliability thường bị quyết định bởi tail latency và error/saturation, không phải mean.

## 3. How does it work?

Instrumentation ghi duration vào histogram với attributes. Collector/backend aggregate thành bucket/distribution và tính p50/p95/p99. Attributes tạo time series mới; cardinality quá cao làm chi phí và query complexity bùng nổ.

## 4. Practical implementation

```csharp
private static readonly Meter Meter = new("Orders.Api");
private static readonly Histogram<double> Duration =
    Meter.CreateHistogram<double>("orders.process.duration", "ms");

var sw = Stopwatch.StartNew();
try
{
    await ProcessAsync(ct);
}
finally
{
    Duration.Record(sw.Elapsed.TotalMilliseconds,
        new KeyValuePair<string, object?>("operation", "approve"));
}
```

Không gắn `userId`, raw URL chứa ID hoặc correlation ID vào metric labels.

## 5. Real production scenario

API average vẫn 180 ms sau release nhưng p99 tăng từ 900 ms lên 6 giây. Trace exemplars cho thấy tail tập trung vào SQL query của một operation.

## 6. Failure scenario & troubleshooting

**Symptom** → observability bill tăng và dashboard query chậm.  
**Evidence** → số time series tăng theo user/request.  
**Hypothesis** → high-cardinality labels.  
**Diagnosis** → metric gắn `customerId` và `requestId`.  
**Fix** → giữ dimensions bounded; dùng trace/log để drill-down identity.  
**Verification** → active series giảm trong khi SLI vẫn đủ phân tích.

## 7. Common mistakes

Dùng average làm latency SLI duy nhất; biến log field thành metric label tùy tiện; tạo metric cho dữ liệu business có cardinality vô hạn; đo quá nhiều nhưng không có alert/action.

## 8. Alternatives

Logs tốt cho event chi tiết; traces tốt cho causal path; metrics tốt cho trend/aggregation. Ba tín hiệu bổ sung nhau, không thay thế nhau.

## 9. Trade-offs

### Advantages

Rẻ hơn trace toàn bộ request cho aggregate monitoring; tốt cho SLO và alert.

### Costs / Risks

Mất chi tiết từng request; cardinality sai gây chi phí lớn; histogram boundaries/aggregation cần thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu counter, gauge, histogram và percentile.

### Middle

Instrument bounded dimensions và dashboard.

### Senior

Thiết kế SLI, correlate metrics với traces và kiểm soát cardinality.

### Technical Lead / Architect

Chuẩn hóa telemetry contract, retention, sampling và cost budget toàn platform.

## 11. Key takeaway

- Tail latency cần percentile, không chỉ average.
- Metric labels phải bounded.
- Metrics chỉ hữu ích khi nối được tới investigation/action.

# 9. React/Vue frontend cancellation: stale response và race condition khi gọi API

## 1. What is it?

Frontend cancellation hủy request không còn giá trị khi state/navigation thay đổi. Mental model quan trọng hơn: UI phải ngăn **stale async result** ghi đè state mới.

## 2. Why does it exist?

Người dùng gõ “car”, request A chạy; sau đó gõ “cargo”, request B chạy. Nếu B trả trước rồi A trả sau, UI có thể hiển thị kết quả cũ dù network đều “thành công”.

## 3. How does it work?

Browser `AbortController` phát signal tới `fetch`. Component cleanup abort request cũ. Backend ASP.NET Core nhận client disconnect qua `HttpContext.RequestAborted`; nếu propagate token xuống EF Core/HTTP dependency, work vô ích có thể dừng sớm.

## 4. Practical implementation

```ts
let controller: AbortController | undefined;

async function search(term: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(
    `/api/search?q=${encodeURIComponent(term)}`,
    { signal: controller.signal }
  );

  return await response.json();
}
```

Trong React dùng cleanup của effect; trong Vue dùng `onWatcherCleanup`/lifecycle phù hợp.

## 5. Real production scenario

Autocomplete gọi search API mỗi keystroke. Không cancellation/debounce, browser tạo burst request; Elasticsearch chịu load dư và UI đôi lúc nhảy về kết quả cũ.

## 6. Failure scenario & troubleshooting

**Symptom** → UI hiển thị result không khớp input hiện tại.  
**Evidence** → DevTools cho thấy request cũ hoàn tất sau request mới.  
**Hypothesis** → async race.  
**Diagnosis** → mọi response đều update cùng state.  
**Fix** → abort stale request, debounce khi phù hợp và/hoặc compare request generation trước state update.  
**Verification** → throttle network trong DevTools; kết quả luôn khớp query mới nhất.

## 7. Common mistakes

Coi abort là error cần toast; chỉ debounce nhưng không xử lý request đang chạy; backend bỏ qua cancellation; cancellation cho mutation non-idempotent rồi giả định server chắc chắn chưa thực thi.

## 8. Alternatives

Request generation/version check ngăn stale commit dù abort không kịp; data libraries như TanStack Query quản lý lifecycle/cache; server-side streaming phù hợp một số search UX khác.

## 9. Trade-offs

### Advantages

Giảm wasted work, tránh stale UI, cải thiện perceived performance.

### Costs / Risks

Lifecycle logic phức tạp hơn; cancellation không rollback side effect server; cần phân biệt abort với failure thật.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu promise completion order không đảm bảo request order.

### Middle

Implement abort/cleanup và loading/error state.

### Senior

Propagate cancellation end-to-end, xử lý mutation semantics và race.

### Technical Lead / Architect

Thiết kế API/UX để cancellation, debounce, caching và idempotency phối hợp đúng.

## 11. Key takeaway

- Async response có thể hoàn tất sai thứ tự.
- Abort giúp giảm work nhưng không phải transaction rollback.
- Cancellation nên được propagate xuyên frontend → API → dependency khi an toàn.

# 10. AI Tool Calling: ranh giới giữa model decision và deterministic authorization

## 1. What is it?

Tool Calling cho phép model đề xuất gọi function/tool với structured arguments. Model là **planner/proposer**, còn application phải là **policy enforcement point**. Model không nên tự quyết định quyền truy cập chỉ vì nó tạo được tool call hợp lệ.

## 2. Why does it exist?

LLM mạnh ở diễn giải intent và chọn action linh hoạt, nhưng output vẫn probabilistic và chịu prompt injection. Các hành động như hoàn tiền, đọc hồ sơ khách hàng hoặc gửi email cần authorization và invariant deterministic.

## 3. How does it work?

```text
User
  -> Application
  -> Model proposes tool + arguments
  -> Validate schema
  -> Authenticate/Authorize
  -> Apply business policy
  -> Execute tool
  -> Return bounded result
  -> Model formats response
```

Tool boundary phải coi model output như untrusted input.

## 4. Practical implementation

```csharp
public async Task<OrderDto> GetOrderAsync(
    ClaimsPrincipal user,
    Guid orderId,
    CancellationToken ct)
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == orderId, ct)
        ?? throw new NotFoundException();

    if (order.TenantId != user.GetTenantId())
        throw new ForbiddenException();

    return mapper.Map<OrderDto>(order);
}
```

Không truyền “`isAdmin=true`” từ model rồi tin nó. Identity phải đến từ authenticated execution context.

## 5. Real production scenario

AI assistant cho CRM có tool `GetCustomer`, `CreateRefund`, `SendEmail`. Một customer note chứa prompt injection yêu cầu model đọc record tenant khác. Tool layer vẫn phải từ chối vì tenant boundary không phụ thuộc prompt.

## 6. Failure scenario & troubleshooting

**Symptom** → model gọi tool đúng schema nhưng truy cập dữ liệu không đúng scope.  
**Evidence** → tool audit log cho thấy ID ngoài tenant của caller.  
**Hypothesis** → authorization bị delegate cho prompt/model.  
**Diagnosis** → tool chỉ validate JSON, không enforce resource-level permission.  
**Fix** → authenticated context, allowlist tool, resource authorization, amount limits, confirmation cho destructive action và audit.  
**Verification** → adversarial eval/prompt injection test vẫn nhận forbidden ở tool layer.

## 7. Common mistakes

Coi Structured Outputs là security boundary; đưa secret vào prompt; cho model tự chọn tenant/user ID; tool quá rộng kiểu `ExecuteSql`; retry destructive tool không có idempotency; log toàn bộ sensitive prompt/tool output.

## 8. Alternatives

Deterministic workflow phù hợp quy trình cố định; rules engine phù hợp policy; agent chỉ nên được thêm khi natural-language planning thực sự mang giá trị. Có thể kết hợp: model chọn intent, workflow deterministic thực thi.

## 9. Trade-offs

### Advantages

Tạo UX linh hoạt và kết nối nhiều capability mà không hard-code mọi câu lệnh ngôn ngữ tự nhiên.

### Costs / Risks

Prompt injection, nondeterminism, latency, token cost, audit complexity và blast radius của tool permissions.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu model output không đáng tin hơn input từ client.

### Middle

Validate schema, timeout, cancellation và error handling cho tool.

### Senior

Thiết kế authorization, idempotency, audit, eval và least privilege.

### Technical Lead / Architect

Quyết định logic nào được phép probabilistic, tool boundary ở đâu, blast radius chấp nhận được và liệu agent có cần tồn tại hay workflow deterministic đơn giản hơn.

## 11. Key takeaway

- Model có thể đề xuất action; application phải quyết định action có được phép hay không.
- Structured output giải quyết shape, không giải quyết authorization.
- Tool nên nhỏ, least-privilege, auditable và idempotent khi có side effect.
