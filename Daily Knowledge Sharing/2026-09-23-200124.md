# 1. .NET `ArrayPool<T>`: tái sử dụng buffer để giảm allocation nhưng phải quản lý ownership chặt chẽ

## 1. What is it?

Mental model: `ArrayPool<T>` là một **buffer rental system**. Thay vì mỗi operation tạo một array mới rồi chờ GC thu gom, code có thể `Rent` một buffer đã tồn tại, dùng trong một scope ngắn và `Return` lại pool.

Nó không làm dữ liệu biến mất và cũng không biến allocation thành miễn phí. Nó đổi bài toán từ **allocate/collect liên tục** thành **borrow/use/return**, vì vậy correctness phụ thuộc mạnh vào ownership và lifetime.

## 2. Why does it exist?

Hot path xử lý serialization, compression, protocol parsing hoặc file/network buffering có thể tạo rất nhiều temporary arrays. Với throughput cao, allocation rate tăng kéo theo Gen 0/Gen 1 collections; buffer lớn còn có thể gây áp lực lên Large Object Heap.

Nếu profiling chứng minh temporary buffers là nguồn allocation đáng kể, tái sử dụng chúng có thể giảm GC pressure. Nhưng nếu endpoint chỉ chạy vài lần mỗi phút, pool thường chỉ tăng complexity mà không tạo giá trị thực tế.

## 3. How does it work?

```text
Request
  |
  +--> ArrayPool<byte>.Shared.Rent(16 KB)
  |        |
  |        +--> trả array có Length >= requested size
  |
  +--> sử dụng một slice hợp lệ
  |
  +--> Return(buffer)
           |
           +--> buffer có thể được cấp cho caller khác
```

Pool không đảm bảo array trả về có đúng requested length. Nội dung cũ cũng có thể vẫn còn nếu caller không yêu cầu clear.

## 4. Practical implementation

```csharp
using System.Buffers;

static async Task<int> ReadChunkAsync(
    Stream stream,
    CancellationToken cancellationToken)
{
    byte[] buffer = ArrayPool<byte>.Shared.Rent(16 * 1024);

    try
    {
        int read = await stream.ReadAsync(
            buffer.AsMemory(0, 16 * 1024),
            cancellationToken);

        return read;
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
    }
}
```

Nếu buffer từng chứa secret hoặc dữ liệu nhạy cảm, cần đánh giá `clearArray: true` hoặc chủ động clear vùng đã dùng. Không giữ `Memory<T>`/reference vào buffer sau khi `Return`.

## 5. Real production scenario

Một API import file xử lý hàng nghìn chunks mỗi giây. Profiler cho thấy phần lớn allocation đến từ `new byte[64 * 1024]` trong parser. Sau khi xác minh parser có lifetime rõ, team chuyển temporary buffer sang `ArrayPool<byte>`, giảm allocation rate và GC pauses mà không thay đổi protocol.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu hiếm khi bị corrupt dưới concurrency dù unit test tuần tự đều pass.

**Evidence** → buffer đã được `Return` nhưng một asynchronous operation vẫn giữ reference và tiếp tục đọc/ghi.

**Hypothesis** → use-after-return.

**Diagnosis** → trace ownership từ `Rent` đến `Return`, kiểm tra mọi `await` và object giữ `Memory<T>`.

**Fix** → kéo `Return` về đúng lifetime, copy dữ liệu nếu consumer cần sở hữu lâu hơn.

**Verification** → stress test concurrent operations và bật assertions quanh valid length/lifetime.

## 7. Common mistakes

- Giả định `Rent(1024)` luôn trả array dài đúng 1024.
- `Return` trước khi asynchronous consumer hoàn tất.
- Quên `Return` khi exception xảy ra.
- Đọc phần array ngoài vùng dữ liệu thực tế.
- Pool dữ liệu nhạy cảm nhưng không cân nhắc clearing.
- Dùng pooling trước khi profiler chứng minh allocation là bottleneck.

## 8. Alternatives

`new byte[]` đơn giản và đúng cho phần lớn code. `stackalloc` phù hợp buffer nhỏ với lifetime stack rõ. `MemoryPool<T>` hữu ích khi cần ownership abstraction (`IMemoryOwner<T>`). `PipeReader`/`System.IO.Pipelines` phù hợp streaming protocol phức tạp hơn.

## 9. Trade-offs

### Advantages

Giảm temporary allocations và GC pressure trong hot path; đặc biệt hữu ích cho reusable medium/large buffers.

### Costs / Risks

Ownership phức tạp hơn, có nguy cơ data corruption hoặc data leakage, và pool giữ memory để tái sử dụng thay vì lập tức trả về OS.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu pool là thuê buffer, không phải tạo array mới; buffer phải được trả lại.

### Middle

Dùng `try/finally`, quản lý valid slice và không giữ reference sau `Return`.

### Senior

Dùng allocation profiling để chứng minh lợi ích, đánh giá async lifetime, LOH và sensitive-data risk.

### Technical Lead / Architect

Quyết định pooling có đáng complexity hay không và giới hạn nó trong infrastructure/hot paths thay vì lan khắp business code.

## 11. Key takeaway

- `ArrayPool<T>` là optimization dựa trên ownership, không phải replacement mặc định cho arrays.
- Chỉ tối ưu sau khi đo allocation/GC pressure.
- Sau `Return`, caller phải xem buffer như không còn thuộc quyền sở hữu của mình.

# 2. ASP.NET Core `ProblemDetails`: error contract là một phần của API contract

## 1. What is it?

Mental model: `ProblemDetails` chuẩn hóa **shape của HTTP error response** để client không phải đoán mỗi endpoint sẽ trả `{ error }`, string, stack trace hay object khác nhau.

Trong ASP.NET Core, nó phù hợp để tách internal exception model khỏi public API error contract.

## 2. Why does it exist?

Một API lớn thường có validation errors, authentication/authorization failures, not-found, conflicts, dependency failures và unexpected exceptions. Nếu mỗi controller tự tạo response, contract nhanh chóng phân mảnh và client phải viết logic đặc thù cho từng endpoint.

Error contract ổn định cũng giúp observability: response có thể chứa safe error code/correlation identifier trong khi chi tiết nội bộ chỉ nằm trong telemetry.

## 3. How does it work?

```text
Exception / domain failure
        |
        v
Exception handler / endpoint mapping
        |
        +--> status
        +--> type/title/detail
        +--> stable application error code
        +--> trace/correlation id
        v
application/problem+json
```

HTTP status vẫn mang semantics chính. `ProblemDetails` bổ sung machine-readable context, không thay thế status code.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();
app.UseExceptionHandler();

app.MapGet("/orders/{id:long}", async (
    long id,
    AppDbContext db,
    CancellationToken ct) =>
{
    var order = await db.Orders.FindAsync([id], ct);

    return order is null
        ? Results.Problem(
            statusCode: StatusCodes.Status404NotFound,
            title: "Order not found",
            extensions: new Dictionary<string, object?>
            {
                ["code"] = "ORDER_NOT_FOUND"
            })
        : Results.Ok(order);
});
```

Không trả stack trace, SQL text hoặc dependency secret trong `detail` ở Production.

## 5. Real production scenario

Mobile app gọi hàng chục endpoints. Trước đây mỗi team trả lỗi khác nhau nên client có nhiều `if` theo response shape. Sau khi API platform chuẩn hóa status + `ProblemDetails` + stable `code`, client xử lý lỗi nhất quán và server vẫn có thể thay internal exception types.

## 6. Failure scenario & troubleshooting

**Symptom** → client hiển thị “Unknown error” sau deployment dù HTTP status đúng.

**Evidence** → server đổi application error code hoặc response shape mà không version/coordinate contract.

**Hypothesis** → error contract bị xem như implementation detail.

**Diagnosis** → so response trước/sau release và client mapping.

**Fix** → khôi phục stable code, thêm contract test và policy compatibility.

**Verification** → integration/contract tests cho success và representative failure paths.

## 7. Common mistakes

Trả HTTP 200 với `{ success:false }`; expose exception message trực tiếp; dùng 500 cho mọi lỗi; dùng `ProblemDetails` nhưng mỗi endpoint invent extension names khác nhau; đưa localization text vào machine-readable code.

## 8. Alternatives

Custom error envelope có thể hợp lý nếu ecosystem đã có contract ổn định, nhưng phải tự định nghĩa semantics. gRPC dùng status/trailers khác HTTP REST. Dù format nào, nguyên tắc stable public contract vẫn giữ nguyên.

## 9. Trade-offs

### Advantages

Client đơn giản hơn, error semantics nhất quán, giảm coupling với exception implementation.

### Costs / Risks

Cần governance cho error codes và compatibility; quá nhiều custom extensions có thể tạo một “standard” riêng khó duy trì.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP status và error body có vai trò khác nhau.

### Middle

Map validation/not-found/conflict/unexpected failures đúng semantics.

### Senior

Thiết kế stable error taxonomy, security-safe details và correlation với telemetry.

### Technical Lead / Architect

Đặt API-wide error contract, compatibility policy và ownership cho error codes.

## 11. Key takeaway

- Error response là API contract, không phải log message gửi cho client.
- HTTP status + stable machine-readable code nên có semantics rõ.
- Internal diagnostics thuộc telemetry; public response phải tối thiểu và an toàn.

# 3. EF Core execution strategy và transaction: retry transient failure mà không replay transaction sai cách

## 1. What is it?

EF Core execution strategy có thể retry database operations khi gặp transient failures. Mental model quan trọng: retry không chỉ là “chạy lại query”; với transaction, **toàn bộ unit cần retry phải được replay như một đơn vị**.

## 2. Why does it exist?

Cloud database connections có thể gặp transient network error, failover hoặc throttling. Một retry ngắn có thể phục hồi mà caller không cần thất bại. Nhưng manual transaction tạo stateful sequence; retry riêng statement thứ hai có thể phá assumptions của transaction.

## 3. How does it work?

```text
ExecutionStrategy.ExecuteAsync
  |
  +--> create transaction
  +--> operation A
  +--> operation B
  +--> commit
  |
 transient failure
  |
  +--> replay WHOLE delegate with a new transaction
```

Retry boundary phải bao trọn transaction boundary.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var transaction =
        await db.Database.BeginTransactionAsync(ct);

    order.MarkPaid();
    await db.SaveChangesAsync(ct);

    db.OutboxMessages.Add(OutboxMessage.From(order));
    await db.SaveChangesAsync(ct);

    await transaction.CommitAsync(ct);
});
```

Operation trong delegate phải được thiết kế để replay an toàn. External side effect như gọi payment provider không nên nằm tùy tiện trong retried DB delegate.

## 5. Real production scenario

Checkout ghi Order và Outbox trong cùng SQL transaction. Sau database failover, transient exception xuất hiện. Execution strategy replay transaction mới; vì cả hai writes cùng transaction và identifiers được quản lý ổn định, state cuối vẫn consistent.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate external notification/payment sau transient DB incident.

**Evidence** → external API call nằm trong delegate bị execution strategy retry.

**Hypothesis** → retry boundary bao gồm non-idempotent side effect ngoài database transaction.

**Diagnosis** → trace attempt number và external correlation/idempotency key.

**Fix** → chuyển side effect sang Outbox/consumer hoặc làm external operation idempotent.

**Verification** → fault-injection test tại các điểm trước/sau commit.

## 7. Common mistakes

Manual transaction ngoài execution strategy; retry mọi exception; đặt HTTP call trong DB transaction; không hiểu commit outcome có thể ambiguous khi connection rớt đúng lúc commit; retry mà không có idempotency.

## 8. Alternatives

Không retry và fail fast phù hợp một số internal tools. Application-level resilience có thể wrap broader workflow nhưng cần semantics rõ. Outbox tách durable DB state khỏi external message delivery.

## 9. Trade-offs

### Advantages

Tăng resilience trước transient database faults và giảm user-visible failures ngắn hạn.

### Costs / Risks

Retry tăng latency/load trong incident và có thể duplicate side effects nếu boundary sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt transient với permanent error.

### Middle

Cấu hình execution strategy và transaction đúng scope.

### Senior

Reason về replay safety, ambiguous commit và idempotency.

### Technical Lead / Architect

Xác định transaction/retry boundary giữa database, broker và third-party systems.

## 11. Key takeaway

- Retry phải bảo toàn transaction semantics.
- Không đặt non-idempotent external side effect vào retried DB delegate.
- Fault injection là cách tốt để kiểm tra assumptions về replay.

# 4. SQL Server covering index: giảm lookup nhưng không biến mọi query thành một index khổng lồ

## 1. What is it?

Một index “cover” query khi index chứa đủ columns để SQL Server trả kết quả mà không phải quay lại clustered index/heap để lấy columns còn thiếu. Key columns phục vụ seek/order; `INCLUDE` columns có thể phục vụ output mà không tham gia key ordering.

## 2. Why does it exist?

Nonclustered index hẹp giúp tìm rows nhanh, nhưng nếu query cần thêm columns, engine có thể thực hiện Key Lookup cho từng matching row. Với ít rows, lookup rất rẻ. Với hàng chục nghìn rows, random I/O/CPU có thể trở thành phần lớn cost.

## 3. How does it work?

```text
Nonclustered Index Seek
        |
        +--> 20 rows  -> Key Lookup x20   : thường ổn
        |
        +--> 100,000 rows -> Lookup x100k : có thể rất đắt

Covering index
        |
        +--> required columns đã có trong index leaf
```

Covering không có nghĩa index phải chứa mọi column của table.

## 4. Practical implementation

Query:

```sql
SELECT OrderNumber, Total, CreatedAt
FROM dbo.Orders
WHERE CustomerId = @CustomerId
  AND Status = @Status
ORDER BY CreatedAt DESC;
```

Một candidate index có thể là:

```sql
CREATE INDEX IX_Orders_Customer_Status_CreatedAt
ON dbo.Orders(CustomerId, Status, CreatedAt DESC)
INCLUDE (OrderNumber, Total);
```

Phải kiểm tra actual execution plan, logical reads, write workload và existing indexes trước khi tạo.

## 5. Real production scenario

Order-history endpoint trả 50 rows nhưng table có hàng chục triệu records. Existing index tìm đúng Customer/Status nhưng lookup thêm `OrderNumber` và `Total`. Sau khi đo, INCLUDE hai fields giảm reads đáng kể mà không cần tạo index chứa toàn bộ entity.

## 6. Failure scenario & troubleshooting

**Symptom** → read query nhanh hơn nhưng write latency và storage tăng sau nhiều index additions.

**Evidence** → table có nhiều overlapping wide indexes; INSERT/UPDATE phải maintain tất cả.

**Hypothesis** → team tối ưu từng query độc lập và tích lũy redundant indexes.

**Diagnosis** → inventory index usage, size, overlap và write cost.

**Fix** → consolidate/drop indexes có bằng chứng không cần thiết, thiết kế theo workload.

**Verification** → benchmark cả read và representative writes.

## 7. Common mistakes

Thêm mọi SELECT column vào key thay vì `INCLUDE`; tin cost percentage trong plan là benchmark; bỏ qua selectivity/order; tạo duplicate indexes; tối ưu query hiếm nhưng làm chậm hot writes.

## 8. Alternatives

Projection giảm columns cần cover. Clustered index design có thể thay access path. Columnstore phù hợp analytics hơn OLTP lookup. Read model/materialized view phù hợp workload báo cáo đặc thù.

## 9. Trade-offs

### Advantages

Giảm lookup và I/O cho targeted read workloads.

### Costs / Risks

Tăng storage, memory footprint và write amplification; index rộng có thể giảm cache efficiency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index seek và lookup là hai bước khác nhau.

### Middle

Đọc actual plan và phân biệt key với INCLUDE columns.

### Senior

Đánh giá cardinality, logical reads, index overlap và write amplification.

### Technical Lead / Architect

Quản lý index portfolio theo workload toàn hệ thống, không tối ưu endpoint trong isolation.

## 11. Key takeaway

- Covering index giải quyết lookup cost cho query cụ thể.
- “Cover everything” thường chuyển read optimization thành write/storage problem.
- Luôn đo cả query và workload trước/sau thay đổi.

# 5. Redis outage strategy: cache failure không được biến thành database outage dây chuyền

## 1. What is it?

Cache-aside thường coi Redis là acceleration layer: app đọc cache, miss thì đọc database rồi populate cache. Nhưng khi Redis unavailable, behavior fallback quyết định hệ thống **degrade gracefully hay tạo cascading failure**.

## 2. Why does it exist?

Nếu 90% traffic thường được Redis hấp thụ, database có thể chưa được provision để nhận 100% traffic tức thời. Redis outage khiến mọi request trở thành miss; nếu tất cả cùng fallback, database pool/CPU có thể bão hòa trong vài giây.

## 3. How does it work?

```text
Normal:
API -> Redis hit -> response

Redis outage naive fallback:
API x N -> Redis timeout -> SQL x N -> saturation

Controlled degradation:
API -> short cache timeout
    -> concurrency/rate budget
    -> SQL fallback for allowed requests
    -> stale/local fallback where acceptable
```

Cache resilience phải được thiết kế cùng origin capacity.

## 4. Practical implementation

Một pattern đơn giản là giới hạn thời gian và fallback có kiểm soát; không retry Redis nhiều lần trong request path.

```csharp
public async Task<Product?> GetAsync(long id, CancellationToken ct)
{
    try
    {
        var cached = await cache.GetStringAsync($"product:{id}", ct);
        if (cached is not null)
            return JsonSerializer.Deserialize<Product>(cached);
    }
    catch (RedisConnectionException ex)
    {
        logger.LogWarning(ex, "Redis unavailable");
    }

    return await database.Products
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);
}
```

Production-grade design cần origin concurrency budget/circuit behavior thay vì cho mọi caller fallback vô hạn.

## 5. Real production scenario

Catalog API có 95% cache hit. Redis cluster maintenance gây 30 giây unavailable. Version cũ fallback toàn bộ traffic sang SQL và làm connection pool cạn; outage kéo dài dù Redis đã phục hồi. Version sau dùng short timeout, request coalescing, bounded origin fallback và stale L1 cho read-only catalog.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis errors xuất hiện trước, vài giây sau SQL latency/timeout tăng mạnh.

**Evidence** → cache hit rate rơi về 0, SQL QPS tăng tương ứng, pool saturation.

**Hypothesis** → fallback amplification.

**Diagnosis** → correlate Redis availability, origin QPS, connection pool và request concurrency.

**Fix** → giảm retry/timeouts, bound fallback, coalesce hot keys, stale data nếu business cho phép.

**Verification** → chaos test Redis unavailable dưới production-like load.

## 7. Common mistakes

Retry Redis 3–5 lần rồi mới query DB; circuit-break Redis nhưng không limit DB fallback; assume cache là optional chỉ vì data vẫn nằm trong SQL; health check restart pods khi Redis down; không load-test cache-off mode.

## 8. Alternatives

`IMemoryCache` có thể làm L1 cho mỗi instance; CDN phù hợp public HTTP content; read replica/materialized read model tăng origin capacity. Đôi khi bỏ cache và tối ưu query đơn giản hơn nếu load thực tế thấp.

## 9. Trade-offs

### Advantages

Cache giảm latency và origin load trong normal operation.

### Costs / Risks

Tạo dependency và traffic cliff khi failure; stale-data semantics và invalidation tăng complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss cuối cùng vẫn tạo origin load.

### Middle

Implement timeout/fallback và telemetry cho hit/miss/error.

### Senior

Load-test cache outage, thiết kế bounded fallback và stale policy.

### Technical Lead / Architect

Quyết định cache có phải critical dependency, origin cần headroom bao nhiêu và degradation contract với business là gì.

## 11. Key takeaway

- “Cache optional” chỉ đúng nếu origin chịu được cache-off traffic.
- Retry/fallback không giới hạn có thể khuếch đại outage.
- Test failure mode của cache dưới load, không chỉ test cache hit.

# 6. DDD Aggregate boundary: bảo vệ invariant mà không tạo object graph khổng lồ

## 1. What is it?

Mental model: Aggregate là **consistency boundary** trong domain model. Aggregate Root là entry point mà bên ngoài dùng để thay đổi state bên trong boundary. Các invariants cần atomically consistent nên nằm trong cùng aggregate; mọi thứ có relation không nhất thiết thuộc cùng aggregate.

## 2. Why does it exist?

Nếu bất kỳ code nào cũng sửa bất kỳ entity nào trực tiếp, business invariants bị phân tán. Ngược lại, nếu gom cả domain thành một aggregate lớn, mỗi command phải load/lock quá nhiều data và concurrency giảm mạnh.

Aggregate giúp cân bằng encapsulation và transactional scope.

## 3. How does it work?

```text
Command
  |
  v
Order (Aggregate Root)
  +--> OrderLine
  +--> OrderLine
  |
  +--> invariant: Total / state transition

Payment Aggregate ---- referenced by ID / domain process ---->
```

Một transaction thường thay đổi một aggregate. Coordination giữa aggregates thường cần application workflow/domain events/eventual consistency tùy invariant.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyCollection<OrderLine> Lines => _lines;
    public OrderStatus Status { get; private set; }

    public void AddLine(ProductId productId, int quantity, Money price)
    {
        if (Status != OrderStatus.Draft)
            throw new DomainException("Only draft orders can change.");

        if (quantity <= 0)
            throw new DomainException("Quantity must be positive.");

        _lines.Add(new OrderLine(productId, quantity, price));
    }
}
```

Application service gọi behavior trên root thay vì set properties tùy ý.

## 5. Real production scenario

Approval system ban đầu tạo `Employee` aggregate chứa profile, timesheets, leave requests và approvals. Load một employee kéo theo object graph lớn và mọi update tranh chấp cùng version. Team tách Timesheet và LeaveRequest thành aggregates riêng vì chúng có lifecycle/invariants độc lập.

## 6. Failure scenario & troubleshooting

**Symptom** → concurrency conflicts thường xuyên và command load hàng nghìn child records.

**Evidence** → aggregate root sở hữu collections không cần thiết cho invariant của command.

**Hypothesis** → boundary dựa trên database relationship thay vì consistency requirement.

**Diagnosis** → liệt kê invariants cần atomicity và commands thay đổi state nào.

**Fix** → thu nhỏ aggregate, reference aggregate khác bằng identity và dùng workflow phù hợp.

**Verification** → domain tests cho invariants + integration tests cho cross-aggregate process.

## 7. Common mistakes

Aggregate = table graph; repository cho mọi child entity; public setters phá encapsulation; aggregate quá lớn vì “transaction cho dễ”; dùng domain event cho mọi method dù không có business meaning.

## 8. Alternatives

Transaction Script phù hợp domain CRUD đơn giản. Application service orchestration có thể đủ khi business rules ít. Rich domain model chỉ đáng chi phí khi invariants/behavior đủ phức tạp.

## 9. Trade-offs

### Advantages

Business invariants tập trung, transaction boundary rõ và model giảm accidental mutation.

### Costs / Risks

Modeling khó hơn CRUD; cross-aggregate consistency có thể cần workflow/eventual consistency; sai boundary gây performance/concurrency issues.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt Entity, Aggregate và Aggregate Root.

### Middle

Đặt behavior trên root và bảo vệ invariant bằng methods.

### Senior

Thiết kế boundary theo transaction/concurrency và tránh aggregate quá lớn.

### Technical Lead / Architect

Quyết định nơi cần strong consistency, nơi chấp nhận eventual consistency và liệu DDD có đáng complexity cho bounded context đó không.

## 11. Key takeaway

- Aggregate là consistency boundary, không phải bản sao foreign-key graph.
- Boundary nhỏ thường cải thiện concurrency nhưng có thể tăng coordination.
- Chỉ dùng rich domain modeling nơi business complexity thực sự cần nó.

# 7. Azure Functions scale-out và idempotency: một event có thể được xử lý nhiều hơn một lần

## 1. What is it?

Azure Functions có thể scale nhiều instances để xử lý event/queue workload. Mental model an toàn: **handler có thể chạy lại**, vì message delivery, lock expiry, retry hoặc crash có thể khiến cùng logical event được xử lý nhiều lần.

## 2. Why does it exist?

Distributed processing ưu tiên durability: nếu worker chết trước khi broker chắc chắn completion, hệ thống phải redeliver thay vì mất message. Điều đó tạo at-least-once-like behavior ở nhiều trigger scenarios và buộc side effects phải chịu duplicate.

## 3. How does it work?

```text
Message M
  |
  +--> Function instance A
          |
          +--> writes DB
          +--> crash before completion acknowledgement

Broker/trigger retries M
  |
  +--> Function instance B
          |
          +--> same logical work again
```

Scale-out cũng có nghĩa in-memory lock/static state không phải coordination mechanism toàn hệ thống.

## 4. Practical implementation

Dùng stable event ID và durable deduplication/business uniqueness:

```csharp
public async Task HandleAsync(OrderPaid message, CancellationToken ct)
{
    if (await db.ProcessedMessages.AnyAsync(
        x => x.MessageId == message.MessageId, ct))
        return;

    await using var tx = await db.Database.BeginTransactionAsync(ct);

    db.ProcessedMessages.Add(new ProcessedMessage(message.MessageId));
    await ApplyBusinessChange(message, ct);
    await db.SaveChangesAsync(ct);

    await tx.CommitAsync(ct);
}
```

Database unique constraint trên `MessageId` cần là final guard cho race; check-then-insert một mình không đủ.

## 5. Real production scenario

Function gửi invoice sau `OrderPaid`. Một invocation ghi invoice thành công nhưng host restart trước completion. Message được deliver lại và version cũ tạo invoice thứ hai. Sau đó team dùng business idempotency key + unique constraint và tách email notification thành downstream idempotent step.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate records xuất hiện chủ yếu quanh restart/timeout.

**Evidence** → cùng message/event ID có nhiều invocation IDs.

**Hypothesis** → handler giả định exactly-once execution.

**Diagnosis** → correlate trigger delivery count, host logs và DB writes.

**Fix** → durable idempotency, unique constraints và side-effect-specific dedupe.

**Verification** → intentionally kill host sau DB write trước acknowledgement và replay message.

## 7. Common mistakes

Dùng static `HashSet` để dedupe; tin một Function invocation chỉ chạy một lần; giữ distributed lock thay cho idempotent state transition; gửi email/payment trước durable state mà không có idempotency key; không theo dõi poison/dead-letter behavior.

## 8. Alternatives

Worker Service + Service Bus cho control processing chi tiết hơn; Container Apps jobs cho workload khác; synchronous API phù hợp immediate request/response. Không alternative nào tự loại duplicate delivery trong distributed failure.

## 9. Trade-offs

### Advantages

Scale-out và managed triggers giảm operational work, tăng throughput và recovery.

### Costs / Risks

Concurrency, duplicate execution và retry semantics trở thành application concern; debugging phân tán hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu scale-out nghĩa nhiều process/instances.

### Middle

Viết handler có stable message ID và retry-safe operations.

### Senior

Thiết kế durable dedupe, transaction boundary và fault-injection tests.

### Technical Lead / Architect

Chọn compute/messaging model dựa trên delivery semantics, throughput, cost và operational ownership.

## 11. Key takeaway

- Distributed event handler phải giả định duplicate execution.
- In-memory state không bảo vệ giữa Function instances.
- Idempotency phải gắn với durable business state và unique constraints.

# 8. Docker image layers: reproducible build, cache hiệu quả và attack surface nhỏ hơn

## 1. What is it?

Docker image được tạo từ immutable filesystem layers. Mỗi Dockerfile instruction thường tạo layer mới; build cache có thể reuse layers nếu inputs không đổi. Runtime container thêm writable layer phía trên image.

## 2. Why does it exist?

Layering giúp distribution và build reuse hiệu quả. Nhưng Dockerfile ordering sai có thể invalidate cache liên tục, image chứa build tools/secrets hoặc tạo artifact khác nhau giữa environments.

## 3. How does it work?

```text
base runtime layer
      + app dependencies
      + published application
      = runtime image

build stage: SDK + compiler + source
runtime stage: runtime + published output only
```

Multi-stage build tách build environment khỏi runtime artifact.

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY MyApi.csproj ./
RUN dotnet restore MyApi.csproj
COPY . .
RUN dotnet publish MyApi.csproj -c Release -o /app/publish --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

Copy project/restore trước source giúp source-only changes reuse restore layer khi dependency manifest không đổi.

## 5. Real production scenario

CI ban đầu copy toàn repo trước `dotnet restore`; mỗi code change làm restore chạy lại. Image cuối dùng SDK image 1+ GB. Multi-stage build + cache-friendly ordering giảm build time và runtime image/attack surface.

## 6. Failure scenario & troubleshooting

**Symptom** → local image chạy nhưng CI/Production image chứa config/file không mong muốn hoặc build cache không ổn định.

**Evidence** → `docker history`, build logs và image inspection cho thấy broad `COPY . .`, generated files hoặc secret material.

**Hypothesis** → build context/layer boundaries không được kiểm soát.

**Diagnosis** → kiểm tra `.dockerignore`, Dockerfile và stage outputs.

**Fix** → giảm build context, multi-stage, explicit artifacts và secret mounts của build system khi cần.

**Verification** → rebuild clean, scan image và chạy integration test từ chính immutable artifact.

## 7. Common mistakes

Dùng `latest` cho base image mà không có update policy; copy `.git`, test outputs hoặc secrets; chạy process root không cần thiết; install debugging tools vào runtime image; build lại artifact khác cho mỗi environment.

## 8. Alternatives

Framework-dependent deployment trực tiếp lên App Service/IIS đơn giản hơn nếu container không giải quyết requirement thật. Buildpacks có thể giảm Dockerfile maintenance nhưng ít control hơn.

## 9. Trade-offs

### Advantages

Artifact portable, dependency boundary rõ, reproducible promotion và deployment consistency tốt hơn.

### Costs / Risks

Image patching/scanning, registry, base-image lifecycle và container operations tạo thêm supply-chain/operational responsibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu image khác container và layer khác writable runtime state.

### Middle

Viết multi-stage Dockerfile, `.dockerignore` và cache-friendly build.

### Senior

Quản lý reproducibility, vulnerabilities, non-root runtime và artifact promotion.

### Technical Lead / Architect

Quyết định containerization có tạo deployment value hay chỉ thêm platform complexity.

## 11. Key takeaway

- Layer ordering ảnh hưởng build cache và artifact contents.
- Runtime image không nên mang cả build toolchain.
- Container là deployment boundary; vẫn cần patching, scanning và operational ownership.

# 9. OpenTelemetry metrics cardinality: một label sai có thể làm observability trở thành bottleneck

## 1. What is it?

Metric cardinality là số lượng unique time series sinh ra từ tổ hợp metric name + attribute values. Một metric `http_requests` với `method` và `status_code` có cardinality hữu hạn; thêm `user_id` có thể tạo hàng triệu series.

## 2. Why does it exist?

Metrics tối ưu cho aggregation nhanh theo dimensions có cardinality được kiểm soát. Unique identifiers phù hợp logs/traces hơn. Nếu mọi request tạo series riêng, storage, memory, query latency và telemetry bill tăng mạnh.

## 3. How does it work?

```text
requests{method=GET,status=200}       -> 1 series
requests{method=POST,status=200}      -> 1 series

requests{user_id=1}                   -> series 1
requests{user_id=2}                   -> series 2
...
requests{user_id=10,000,000}          -> explosion
```

Cardinality nhân theo dimensions, không chỉ cộng.

## 4. Practical implementation

```csharp
private static readonly Meter Meter = new("Checkout.Api");
private static readonly Counter<long> Orders =
    Meter.CreateCounter<long>("orders.processed");

Orders.Add(1,
    new KeyValuePair<string, object?>("result", "success"),
    new KeyValuePair<string, object?>("channel", "web"));
```

Không dùng `order.id`, raw URL, email hoặc exception message làm metric attributes. Route template `/orders/{id}` tốt hơn path `/orders/123456`.

## 5. Real production scenario

Team thêm `customer_id` vào request metric để “filter dễ”. Telemetry backend bắt đầu ingest hàng triệu series, dashboard chậm và cost tăng. Customer-specific debugging sau đó được chuyển sang traces/logs; metrics chỉ giữ bounded dimensions như endpoint, status class và region.

## 6. Failure scenario & troubleshooting

**Symptom** → telemetry cost/memory tăng đột biến, metric queries chậm.

**Evidence** → số unique attribute values tăng theo traffic/users.

**Hypothesis** → high-cardinality label mới được deploy.

**Diagnosis** → inventory metric dimensions và top unique counts.

**Fix** → remove/bucket dimension, normalize routes, dùng trace/log cho identifiers.

**Verification** → theo dõi active series và ingestion sau deployment.

## 7. Common mistakes

Metric label chứa request ID; exception message làm dimension; raw URL có query string; tenant ID không có cardinality budget; copy mọi log property sang metric attribute.

## 8. Alternatives

Logs phù hợp rich event detail; traces phù hợp request-specific causal debugging; exemplars có thể liên kết aggregate metric với representative trace mà không biến trace ID thành metric dimension.

## 9. Trade-offs

### Advantages

Metrics cardinality thấp cho aggregation, alerting và long-term trends rất hiệu quả.

### Costs / Risks

Giảm dimensions làm ad-hoc drilldown ít chi tiết hơn; cần kết hợp traces/logs thay vì bắt metrics làm mọi việc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu metric dimension tạo nhiều time series.

### Middle

Chọn bounded labels và normalize route/status.

### Senior

Thiết kế logs-metrics-traces theo mục đích và kiểm soát telemetry cost.

### Technical Lead / Architect

Đặt observability schema, cardinality budget và review policy trước khi instrumentation lan rộng.

## 11. Key takeaway

- Metrics dành cho bounded aggregation, không phải per-request identity.
- Cardinality thường nhân rất nhanh khi thêm dimensions.
- Dùng traces/logs cho identifiers và chi tiết điều tra.

# 10. REST API idempotency key: làm retry an toàn cho create/payment-like operations

## 1. What is it?

Idempotency key là client-generated stable identifier đại diện cho **một logical operation**. Nếu client retry cùng operation do timeout, server nhận cùng key và trả lại kết quả đã ghi nhận thay vì thực hiện side effect lần nữa.

## 2. Why does it exist?

HTTP client có thể timeout sau khi server đã commit nhưng trước khi response đến client. Client không biết operation thành công hay chưa. Retry `POST /payments` naïvely có thể tạo payment thứ hai.

Network ambiguity không thể giải quyết bằng “đừng retry”; production systems cần semantics cho replay.

## 3. How does it work?

```text
Client POST + Idempotency-Key: abc
        |
Server reserves abc
        |
execute operation -> persist result
        |
response lost

Client retries same key abc
        |
Server finds completed abc
        |
return same logical result, no second side effect
```

Key phải scoped hợp lý, thường theo caller/operation, và request fingerprint có thể được lưu để phát hiện cùng key nhưng payload khác.

## 4. Practical implementation

Một schema đơn giản:

```sql
CREATE TABLE ApiIdempotency (
    ClientId        nvarchar(100) NOT NULL,
    IdempotencyKey  nvarchar(100) NOT NULL,
    RequestHash     varbinary(32) NOT NULL,
    Status          varchar(20) NOT NULL,
    ResourceId      bigint NULL,
    CreatedAt       datetime2 NOT NULL,
    CONSTRAINT PK_ApiIdempotency
        PRIMARY KEY (ClientId, IdempotencyKey)
);
```

Trong transaction, reserve key bằng unique constraint rồi tạo business resource. Nếu key tồn tại, validate request hash và return stored/current result theo contract.

## 5. Real production scenario

Mobile app submit order trên mạng chập chờn. Server commit Order nhưng response mất. App retry sau 3 giây. Không có idempotency key, hai orders được tạo. Với key ổn định cho thao tác checkout, retry trả Order ban đầu.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate resources dù client “chỉ bấm một lần”.

**Evidence** → nhiều POST requests gần nhau có cùng business intent nhưng server không có durable dedupe identity.

**Hypothesis** → client/network retry sau ambiguous outcome.

**Diagnosis** → correlate client request ID, gateway logs và DB creation timestamps.

**Fix** → idempotency contract + durable unique constraint + request fingerprint.

**Verification** → inject timeout sau commit trước response rồi retry cùng key.

## 7. Common mistakes

Lưu idempotency key chỉ trong memory; check rồi insert không có unique constraint; cho cùng key dùng payload khác; giữ records mãi không có retention policy; coi `POST` tự nhiên idempotent; tạo random key mới cho mỗi retry.

## 8. Alternatives

Natural business key/unique constraint có thể đủ nếu domain đã có stable unique identity. `PUT /resource/{client-generated-id}` có idempotent semantics tự nhiên hơn trong một số APIs. Message consumers dùng inbox/deduplication pattern tương tự.

## 9. Trade-offs

### Advantages

Cho phép retry an toàn trước timeout/network ambiguity và giảm duplicate business side effects.

### Costs / Risks

Cần storage, retention, concurrency handling, payload matching và rõ semantics khi operation đang `in-progress`.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không chứng minh server chưa xử lý request.

### Middle

Implement idempotency key + unique constraint và integration tests.

### Senior

Xử lý concurrent retries, request fingerprint, in-progress/failed states và retention.

### Technical Lead / Architect

Quyết định endpoint nào cần idempotency contract, key scope/TTL và cách nối semantics đó với payment, messaging và database transactions.

## 11. Key takeaway

- Timeout tạo ambiguous outcome; retry có thể duplicate side effect.
- Idempotency cần durable uniqueness, không chỉ application-level `if`.
- Test bằng cách làm mất response sau commit rồi replay cùng logical request.
