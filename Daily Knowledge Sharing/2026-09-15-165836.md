# 1. C# `ArrayPool<T>` và buffer ownership: giảm allocation mà không tạo data leak hoặc use-after-return logic

## 1. What is it?

`ArrayPool<T>` là pool các array có thể thuê (`Rent`) rồi trả lại (`Return`) để tái sử dụng buffer thay vì liên tục allocate array mới. Mental model quan trọng không phải “array miễn phí”, mà là **temporary ownership**: caller mượn một vùng memory trong một khoảng thời gian và phải trả lại đúng lifecycle.

## 2. Why does it exist?

Các hot path như serialization, compression, parsing hoặc stream copy có thể tạo hàng nghìn temporary buffers. Allocation liên tục tăng GC pressure; buffer lớn còn có thể đi vào Large Object Heap. Pooling đổi allocation churn thành reuse, nhưng đổi lại application phải quản lý ownership rõ ràng.

## 3. How does it work?

```text
ArrayPool
   ↓ Rent(4096)
Caller owns buffer temporarily
   ↓ use only requested logical length
   ↓ Return(buffer)
ArrayPool
```

`Rent(4096)` có thể trả array lớn hơn 4096. Nội dung cũ cũng có thể còn tồn tại. Sau `Return`, caller không còn quyền dùng buffer vì một operation khác có thể thuê lại ngay.

## 4. Practical implementation

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(16 * 1024);

try
{
    var read = await stream.ReadAsync(
        buffer.AsMemory(0, 16 * 1024), cancellationToken);

    await destination.WriteAsync(
        buffer.AsMemory(0, read), cancellationToken);
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

Nếu buffer chứa secrets, credentials hoặc dữ liệu nhạy cảm, cân nhắc `clearArray: true` hoặc tự clear phần đã dùng trước khi trả.

## 5. Real production scenario

Một file-processing API tạo `byte[128KB]` cho mỗi chunk. Dưới tải đồng thời, allocation rate và GC pause tăng đáng kể. Chuyển temporary buffers sang `ArrayPool<byte>` giảm allocation, nhưng team phải đảm bảo buffer không bị giữ trong object sống lâu hoặc dùng sau `Return`.

## 6. Failure scenario & troubleshooting

**Symptom** → response thỉnh thoảng chứa bytes từ request khác.

**Evidence** → code return buffer rồi asynchronous work vẫn giữ reference tới buffer.

**Hypothesis** → ownership violation/use-after-return.

**Diagnosis** → trace buffer lifecycle, kiểm tra mọi continuation và object capture.

**Fix** → chỉ return sau operation cuối cùng; copy dữ liệu nếu lifetime phải vượt pool lease.

**Verification** → stress test concurrent requests và kiểm tra payload isolation.

## 7. Common mistakes

* Giả định rented array có đúng requested length.
* Giả định array mới được zeroed.
* Return buffer trước khi async consumer hoàn tất.
* Pool mọi allocation nhỏ dù profiler chưa chứng minh vấn đề.
* Giữ pooled buffer trong cache hoặc singleton.

## 8. Alternatives

`new byte[]` đơn giản và an toàn hơn cho low-frequency path. `MemoryPool<T>` phù hợp khi cần memory-owner abstraction. `stackalloc` hữu ích cho buffer rất nhỏ với lifetime ngắn và synchronous scope.

## 9. Trade-offs

### Advantages

* Giảm allocation rate và GC pressure.
* Hữu ích cho high-throughput buffer-heavy paths.

### Costs / Risks

* Ownership phức tạp hơn.
* Có nguy cơ data leakage nếu reuse sai.
* Pooling không giúp nếu bottleneck thực tế là I/O hoặc database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Rent`/`Return` là mượn buffer, không phải sở hữu vĩnh viễn.

### Middle

Dùng `try/finally`, giới hạn logical length và xử lý sensitive data.

### Senior

Đo allocation trước/sau, kiểm soát lifetime qua async boundaries và phát hiện ownership bugs.

### Technical Lead / Architect

Quyết định hot path nào đáng trả complexity cost của pooling thay vì áp dụng như coding convention toàn hệ thống.

## 11. Key takeaway

* `ArrayPool<T>` tối ưu allocation bằng reuse, không loại bỏ ownership cost.
* Không dùng buffer sau `Return`.
* Chỉ pooling khi measurement chứng minh allocation là bottleneck đáng xử lý.

# 2. ASP.NET Core `ProblemDetails`: biến error contract thành API boundary ổn định thay vì trả exception text tùy tiện

## 1. What is it?

`ProblemDetails` là structured HTTP error representation giúp API trả lỗi theo contract nhất quán: status, title, detail, type và extensions. Nó tách **internal exception model** khỏi **public API error contract**.

## 2. Why does it exist?

Nếu mỗi endpoint tự trả một shape khác nhau, frontend phải viết nhiều parsing branches. Tệ hơn, serialize exception trực tiếp có thể leak stack trace, SQL, file path hoặc internal identifiers.

Error response là một phần của API contract giống success response.

## 3. How does it work?

```text
Exception / validation failure
        ↓
Central error mapping
        ↓
HTTP status + ProblemDetails
        ↓
Stable client contract
```

Internal logs giữ exception detail; client chỉ nhận thông tin cần thiết và correlation identifier.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();
app.UseExceptionHandler();

app.MapGet("/orders/{id:guid}", async (Guid id, AppDbContext db) =>
{
    var order = await db.Orders.FindAsync(id);
    return order is null
        ? Results.Problem(
            statusCode: StatusCodes.Status404NotFound,
            title: "Order not found",
            extensions: new Dictionary<string, object?>
            {
                ["code"] = "order_not_found"
            })
        : Results.Ok(order);
});
```

Domain/application exceptions nên được map tập trung sang status/code có semantics rõ ràng.

## 5. Real production scenario

Mobile app phụ thuộc error code để hiển thị flow phù hợp. Backend trước đây trả message string tiếng Anh. Một developer đổi wording và mobile logic bị hỏng. Stable machine-readable code trong `ProblemDetails.extensions` loại coupling vào human-readable text.

## 6. Failure scenario & troubleshooting

**Symptom** → Production response lộ stack trace và SQL exception.

**Evidence** → middleware gắn `exception.ToString()` vào `detail`.

**Hypothesis** → public error contract đang dùng diagnostic detail.

**Diagnosis** → inspect response và centralized exception mapping.

**Fix** → log exception server-side với trace ID; trả sanitized problem type/code cho client.

**Verification** → integration test đảm bảo production error không chứa stack/file/database details.

## 7. Common mistakes

* Trả HTTP 200 kèm `{ success:false }` cho mọi lỗi.
* Dùng exception message làm stable client code.
* Map mọi exception thành 500.
* Leak internal detail.
* Không document validation/error codes trong API contract.

## 8. Alternatives

Custom error envelope có thể phù hợp legacy contract, nhưng cần giữ HTTP semantics. gRPC có status/detail model riêng. GraphQL thường dùng error envelope theo protocol của nó.

## 9. Trade-offs

### Advantages

* Error contract nhất quán.
* Client integration dễ hơn.
* Tách diagnostics khỏi public surface.

### Costs / Risks

* Cần taxonomy error code có governance.
* Over-abstraction nếu mọi domain error đều biến thành hierarchy phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code và error body có hai vai trò khác nhau.

### Middle

Implement centralized mapping và integration tests.

### Senior

Thiết kế stable error taxonomy, security sanitization và backward compatibility.

### Technical Lead / Architect

Định nghĩa organization-wide API error contract đủ ổn định nhưng không ép mọi service dùng domain taxonomy giống hệt nhau.

## 11. Key takeaway

* Error response là API contract.
* Internal exception detail không phải client-facing detail.
* Stable machine-readable code tốt hơn parsing message text.

# 3. EF Core execution strategy và transaction retry: transient retry chỉ an toàn khi transaction unit có thể replay

## 1. What is it?

EF Core execution strategy có thể retry database operation khi gặp transient failure như temporary connectivity issue. Nhưng khi application tự mở transaction, toàn transaction phải được execution strategy thực thi như một replayable unit.

## 2. Why does it exist?

Cloud database connections có thể fail tạm thời. Retry một query độc lập thường an toàn. Nhưng transaction nhiều bước có state: nếu retry sai boundary, application có thể replay một phần operation hoặc không biết commit trước đó đã thành công chưa.

## 3. How does it work?

```text
Execution strategy
   ↓
Begin transaction
   ↓
Step A
   ↓
Step B
   ↓
Commit

Transient failure → replay whole delegate when safe
```

Execution strategy phải kiểm soát transaction lifecycle để retry toàn unit.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var transaction =
        await db.Database.BeginTransactionAsync(cancellationToken);

    order.MarkProcessed();
    db.AuditEntries.Add(new AuditEntry(order.Id, "Processed"));

    await db.SaveChangesAsync(cancellationToken);
    await transaction.CommitAsync(cancellationToken);
});
```

Nếu transaction còn gọi external HTTP API, replay trở nên nguy hiểm vì external side effect có thể đã xảy ra.

## 5. Real production scenario

Order transaction update database rồi gọi payment API trước commit. SQL connection transiently fail và execution strategy replay delegate. Payment bị charge lần hai vì external call không idempotent.

Retry policy database đã biến transient database fault thành business correctness incident.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate external side effect sau SQL transient error.

**Evidence** → same business operation ID xuất hiện trong hai outbound calls.

**Hypothesis** → retry boundary chứa non-idempotent remote side effect.

**Diagnosis** → correlate execution strategy retries với HTTP telemetry.

**Fix** → giữ DB transaction local; dùng Outbox cho integration event hoặc idempotency key ở remote call.

**Verification** → fault-injection test tại commit/query boundary.

## 7. Common mistakes

* Retry mọi exception.
* Tự mở transaction bên ngoài execution strategy.
* Đưa email/payment/API call vào replayable transaction delegate.
* Nghĩ retry đồng nghĩa exactly-once.

## 8. Alternatives

Application-level retry phù hợp khi cần domain-aware policy. Outbox tách durable database commit khỏi external delivery. Không retry cũng đúng với permanent constraint/validation errors.

## 9. Trade-offs

### Advantages

* Tăng resilience trước transient database faults.
* Giảm failure do network hiccup ngắn.

### Costs / Risks

* Replay semantics phức tạp.
* Có thể tăng load khi database đang degraded.
* Side effects ngoài database cần idempotency riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transient error khác permanent error.

### Middle

Cấu hình execution strategy và transaction boundary đúng.

### Senior

Phân tích replay safety, ambiguous commit và idempotency.

### Technical Lead / Architect

Định nghĩa retry policy theo dependency và đảm bảo transaction không vô tình bao external side effects.

## 11. Key takeaway

* Retry chỉ đúng khi operation có thể replay an toàn.
* Database transaction không làm remote side effect atomic.
* Retry policy là correctness decision, không chỉ resilience switch.

# 4. PostgreSQL MVCC và vacuum: vì sao reader không block writer nhưng dead tuples vẫn có operational cost

## 1. What is it?

PostgreSQL dùng Multi-Version Concurrency Control (MVCC): update thường tạo row version mới thay vì sửa tuple tại chỗ theo cách khiến reader phải chờ writer. Transaction nhìn snapshot phù hợp với visibility rules.

## 2. Why does it exist?

Concurrency cao cần giảm reader/writer blocking. MVCC cho phép transaction đọc consistent snapshot trong khi transaction khác update dữ liệu. Cái giá là old row versions phải được cleanup sau khi không transaction nào còn cần chúng.

## 3. How does it work?

```text
Tuple v1 visible to old snapshot
   ↓ UPDATE
Tuple v2 visible to newer snapshot

Later: v1 no longer visible to anyone
   ↓
VACUUM can reclaim space
```

Long-running transactions giữ old snapshot và có thể ngăn cleanup nhiều dead tuples.

## 4. Practical implementation

Operational query đơn giản để tìm tables có dead tuples cao:

```sql
SELECT relname,
       n_live_tup,
       n_dead_tup,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;
```

Tìm long-running transactions:

```sql
SELECT pid, xact_start, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Không nên “VACUUM thường xuyên hơn” trước khi hiểu write rate, table size và transaction behavior.

## 5. Real production scenario

Một reporting job mở transaction rồi stream dữ liệu hàng giờ. Trong lúc đó, transactional table nhận update liên tục. Autovacuum không reclaim được nhiều old versions; table/index bloat tăng và I/O latency dần xấu đi.

## 6. Failure scenario & troubleshooting

**Symptom** → database storage và query I/O tăng dù row count gần như không đổi.

**Evidence** → `n_dead_tup` cao, old transaction tồn tại lâu, autovacuum không theo kịp.

**Hypothesis** → MVCC cleanup bị giữ bởi long-lived snapshot hoặc vacuum tuning không phù hợp.

**Diagnosis** → inspect `pg_stat_activity`, `pg_stat_user_tables`, vacuum logs và table growth.

**Fix** → rút ngắn transaction; tune autovacuum cho hot table khi cần; xử lý bloat theo evidence.

**Verification** → dead tuple trend giảm và query I/O/size ổn định lại.

## 7. Common mistakes

* Giữ transaction mở quanh user interaction.
* Nhầm connection mở lâu với transaction mở lâu.
* Tắt autovacuum để “giảm CPU”.
* Chỉ nhìn row count mà bỏ qua dead tuples/bloat.

## 8. Alternatives

SQL Server cũng có row-versioning isolation options nhưng storage/cleanup mechanism khác. Pessimistic locking đơn giản về version lifecycle nhưng tăng blocking.

## 9. Trade-offs

### Advantages

* Reader/writer concurrency tốt.
* Snapshot semantics mạnh.

### Costs / Risks

* Old versions cần cleanup.
* Long transactions có hidden system-wide cost.
* Vacuum là operational subsystem phải theo dõi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu update có thể tạo nhiều row versions.

### Middle

Biết transaction lifetime ảnh hưởng cleanup.

### Senior

Chẩn đoán bloat, autovacuum lag và long-running snapshots.

### Technical Lead / Architect

Thiết kế reporting/batch workload để không giữ transaction snapshot lâu trên OLTP database.

## 11. Key takeaway

* MVCC giảm blocking bằng versioning, không làm concurrency miễn phí.
* Long transactions có thể gây storage/I/O cost ngoài transaction đó.
* Vacuum health là phần của production database engineering.

# 5. MongoDB embedding vs referencing: document boundary phải theo access pattern và atomicity, không theo object graph

## 1. What is it?

Embedding lưu related data trong cùng document; referencing lưu identifier trỏ sang document khác. Đây là quyết định data modeling dựa trên cách dữ liệu được đọc, cập nhật, tăng trưởng và cần atomicity.

## 2. Why does it exist?

Document database không nên được model như relational schema rồi thay JOIN bằng manual lookup. Đồng thời cũng không nên nhét mọi thứ vào một document chỉ vì MongoDB cho phép nested JSON.

## 3. How does it work?

Embedding phù hợp khi child data:

* thường đọc cùng parent,
* có bounded size,
* cùng lifecycle,
* cần update atomically với parent.

Referencing phù hợp khi data:

* tăng trưởng không giới hạn,
* được truy cập độc lập,
* shared giữa nhiều aggregates,
* có lifecycle riêng.

## 4. Practical implementation

Order snapshot có thể embed line items:

```json
{
  "_id": "order-123",
  "customerId": "customer-7",
  "items": [
    { "sku": "A1", "name": "Keyboard", "price": 80, "qty": 1 }
  ],
  "total": 80
}
```

`name` và `price` ở đây có thể là snapshot tại thời điểm mua, không cần reference product hiện tại.

Ngược lại, hàng triệu audit events không nên embed mãi vào customer document.

## 5. Real production scenario

Team embed toàn bộ notification history vào user document. Sau nhiều năm, document tăng lớn, update array tốn nhiều I/O và cuối cùng chạm giới hạn document size. Root cause là unbounded collection bị đặt sai aggregate/document boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → update user document ngày càng chậm và document size tăng liên tục.

**Evidence** → nested history array có hàng chục nghìn entries.

**Hypothesis** → unbounded one-to-many relationship bị embed.

**Diagnosis** → inspect document size distribution và access pattern.

**Fix** → tách history thành collection riêng, index theo `userId` + time; giữ summary nhỏ trong parent nếu cần.

**Verification** → latency và document growth ổn định.

## 7. Common mistakes

* Port normalized SQL schema 1:1 sang MongoDB.
* Embed unbounded arrays.
* Reference mọi thứ rồi tạo nhiều round trips.
* Không model theo query/access pattern.

## 8. Alternatives

Relational database phù hợp khi cross-entity constraints và ad-hoc joins là core requirement. Cosmos DB cũng dùng document modeling nhưng partition-key/cost model tạo thêm constraints riêng.

## 9. Trade-offs

### Advantages

Embedding giảm round trips và hỗ trợ atomic document update. Referencing giữ independent lifecycle và tránh document growth.

### Costs / Risks

Embedding tạo duplication/staleness. Referencing tăng query complexity và consistency coordination.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu embed không đồng nghĩa “NoSQL tốt hơn”.

### Middle

Model document theo common read/write operations.

### Senior

Đánh giá growth, atomicity, duplication và index/query cost.

### Technical Lead / Architect

Quyết định liệu document database có phù hợp workload trước khi tối ưu schema bên trong nó.

## 11. Key takeaway

* Document boundary nên theo access pattern và lifecycle.
* Unbounded child collections thường không nên embed.
* Denormalization là intentional trade-off, không phải bỏ qua consistency.

# 6. Saga + compensating transaction: quản lý business workflow nhiều service khi distributed ACID transaction không thực tế

## 1. What is it?

Saga chia một business transaction dài thành chuỗi local transactions. Nếu bước sau thất bại, system chạy compensating actions cho các bước trước khi business semantics cho phép.

Compensation không phải database rollback xuyên service; nó là **business action mới** nhằm đảo hoặc bù tác động trước đó.

## 2. Why does it exist?

Checkout có thể liên quan Order, Payment, Inventory và Shipping. Giữ distributed ACID transaction qua tất cả services làm coupling, latency và availability xấu, đồng thời nhiều cloud APIs không tham gia 2PC.

## 3. How does it work?

```text
Create Order
   ↓
Reserve Inventory
   ↓
Authorize Payment
   ↓
Create Shipment

Failure at Payment
   ↓
Release Inventory
   ↓
Cancel Order
```

Saga có thể orchestration (central coordinator) hoặc choreography (services react to events).

## 4. Practical implementation

Một orchestrator lưu state:

```csharp
public enum CheckoutState
{
    Started,
    InventoryReserved,
    PaymentAuthorized,
    Completed,
    Compensating,
    Failed
}
```

Mỗi command/event cần stable operation ID để retry và deduplicate. State phải durable; không chỉ giữ trong memory của worker.

## 5. Real production scenario

Inventory đã reserve nhưng payment provider timeout. Timeout không chứng minh payment thất bại; request có thể đã được xử lý. Orchestrator cần query/reconcile payment bằng idempotency key trước khi quyết định compensation.

## 6. Failure scenario & troubleshooting

**Symptom** → inventory được release nhưng payment thực tế đã authorized.

**Evidence** → payment request timeout, compensation chạy ngay mà không reconcile remote state.

**Hypothesis** → ambiguous remote outcome bị coi là definite failure.

**Diagnosis** → inspect payment operation ID/provider status.

**Fix** → thiết kế intermediate state như `PaymentUnknown`; reconcile trước compensation.

**Verification** → fault-injection tại network response boundary.

## 7. Common mistakes

* Gọi compensation là rollback.
* Không làm compensation idempotent.
* Không lưu saga state durable.
* Choreography quá nhiều events khiến workflow khó quan sát.
* Assume timeout = operation không xảy ra.

## 8. Alternatives

Một local database transaction tốt hơn nếu workflow nằm trong một service/database. Modular Monolith có thể tránh distributed Saga nếu business boundary chưa cần tách deployment. 2PC chỉ phù hợp trong môi trường hỗ trợ và chấp nhận coupling/cost.

## 9. Trade-offs

### Advantages

* Cho phép workflow xuyên autonomous services.
* Không cần global lock/transaction.

### Costs / Risks

* Eventual consistency.
* Compensation có thể không đảo hoàn toàn side effect.
* State machine và observability phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mỗi service commit local transaction riêng.

### Middle

Implement idempotent step và durable saga state.

### Senior

Xử lý ambiguous outcomes, compensation failures và retries.

### Technical Lead / Architect

Trước hết phải hỏi liệu workflow có thực sự cần phân tán hay một transaction boundary đơn giản hơn tốt hơn.

## 11. Key takeaway

* Saga quản lý business consistency, không tạo distributed rollback.
* Timeout tạo unknown state, không nhất thiết failure.
* Compensation và orchestration đều cần idempotency + observability.

# 7. Azure Functions idempotency: retries và duplicate execution là behavior phải thiết kế, không phải edge case

## 1. What is it?

Một Azure Function xử lý event/message có thể chạy nhiều lần cho cùng logical input do retry, lock expiry, host restart hoặc delivery semantics của trigger. Idempotency nghĩa là repeated execution không tạo repeated business effect ngoài ý muốn.

## 2. Why does it exist?

Distributed execution không thể dựa vào giả định “handler chỉ chạy đúng một lần”. Nếu Function gửi invoice, charge payment hoặc insert order mỗi retry, transient failure trở thành duplicate business action.

## 3. How does it work?

```text
Message M
  ↓
Function executes
  ↓ side effect succeeds
Host crashes before settlement
  ↓
Message M delivered again
  ↓
Function executes again
```

Broker/runtime không thể biết side effect của application đã commit hay chưa. Application cần stable idempotency key và durable record/business uniqueness constraint.

## 4. Practical implementation

Ví dụ dùng database unique key:

```csharp
public async Task HandleAsync(
    InvoiceRequested message,
    CancellationToken cancellationToken)
{
    if (await db.ProcessedMessages.AnyAsync(
        x => x.MessageId == message.MessageId, cancellationToken))
        return;

    db.Invoices.Add(new Invoice(message.InvoiceId, message.CustomerId));
    db.ProcessedMessages.Add(new ProcessedMessage(message.MessageId));

    await db.SaveChangesAsync(cancellationToken);
}
```

Trong production cần unique constraint trên `MessageId`; check-then-insert đơn thuần vẫn có race condition nếu concurrent duplicate chạy.

## 5. Real production scenario

Service Bus triggered Function tạo loyalty points. Database insert thành công nhưng host recycle trước message completion. Message được redeliver và user nhận điểm lần hai. Unique business operation ID ngăn duplicate credit.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate records xuất hiện quanh thời điểm host restart.

**Evidence** → cùng message ID có nhiều execution logs.

**Hypothesis** → handler không idempotent.

**Diagnosis** → correlate Function invocation IDs với broker message ID và DB writes.

**Fix** → durable deduplication/unique constraint; thiết kế side effect theo operation ID.

**Verification** → intentionally redeliver same message và xác nhận business state chỉ thay đổi một lần.

## 7. Common mistakes

* Dùng invocation ID làm idempotency key thay vì logical message ID.
* Lưu dedupe state trong memory.
* Check existence nhưng không có database uniqueness.
* Retry non-idempotent third-party API không có idempotency key.

## 8. Alternatives

Worker Service + Service Bus vẫn có cùng delivery problem. Durable Functions hỗ trợ workflow state nhưng activity side effects vẫn cần idempotency. Queue choice không loại bỏ application correctness requirement.

## 9. Trade-offs

### Advantages

* Cho phép retry an toàn hơn.
* Tăng reliability dưới host/network failure.

### Costs / Risks

* Cần durable dedupe state hoặc domain uniqueness.
* Retention của idempotency records phải được quản lý.
* Một số external APIs không hỗ trợ idempotency tự nhiên.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry có thể chạy cùng work lần nữa.

### Middle

Dùng stable message ID và unique constraint.

### Senior

Thiết kế idempotency xuyên DB + external dependencies và retention strategy.

### Technical Lead / Architect

Định nghĩa delivery semantics của platform và business operations nào bắt buộc có idempotency contract.

## 11. Key takeaway

* Duplicate execution là normal distributed behavior.
* Idempotency phải dựa trên logical operation identity.
* Database constraint thường là lớp bảo vệ cuối cùng quan trọng.

# 8. IIS Application Pool recycling: process lifecycle, in-memory state và startup failure trong enterprise hosting

## 1. What is it?

IIS Application Pool cô lập một hoặc nhiều web applications trong worker process (`w3wp.exe`). Recycling thay worker process bằng process mới theo configuration, health condition, deployment hoặc administrative action.

## 2. Why does it exist?

Process cần lifecycle management: recover crash, apply configuration/code, giới hạn runaway behavior và isolate applications. Nhưng application phải được thiết kế để process có thể biến mất bất kỳ lúc nào mà không làm mất durable business state.

## 3. How does it work?

```text
IIS
 ↓
Application Pool
 ↓
w3wp old
 ↓ recycle
w3wp new starts
 ↓
application startup
 ↓
traffic transitions
```

In-memory cache, static variables, background threads và session InProc gắn với worker process cũ.

## 4. Practical implementation

ASP.NET Core hosted behind IIS nên giữ durable state ngoài process và implement graceful cancellation cho background work. Diagnostic commands có thể gồm:

```powershell
%windir%\system32\inetsrv\appcmd list apppool
%windir%\system32\inetsrv\appcmd list wp
```

Kiểm tra Windows Event Viewer, IIS logs và application stdout/startup logs khi process không lên.

## 5. Real production scenario

Legacy application dùng InProc session. Scheduled recycle lúc đêm khiến active users mất session. Team tưởng authentication provider lỗi nhưng root cause là session state nằm trong worker process.

## 6. Failure scenario & troubleshooting

**Symptom** → sau deployment IIS trả 502.5/500.30 hoặc application không start.

**Evidence** → worker process spawn rồi exit; Event Viewer có startup exception.

**Hypothesis** → missing runtime/config/permission hoặc application startup failure.

**Diagnosis** → kiểm tra hosting bundle/runtime, event logs, filesystem permissions, environment configuration và startup logs.

**Fix** → sửa dependency/config thay vì tăng recycle attempts.

**Verification** → recycle pool chủ động và xác nhận app warm/start/health bình thường.

## 7. Common mistakes

* Dùng process memory làm durable state.
* Chạy critical scheduler bên trong web app mà không nghĩ tới multiple workers/recycle.
* Recycle để “fix memory leak” thay vì tìm root cause.
* Không có health/startup telemetry.

## 8. Alternatives

Azure App Service quản lý hosting lifecycle cao hơn nhưng instance restart vẫn tồn tại. Windows Service/Worker Service phù hợp background process. Containers thay process model nhưng cũng yêu cầu stateless/restart-safe design.

## 9. Trade-offs

### Advantages

* Mature Windows hosting/isolation.
* Operational tooling quen thuộc trong enterprise.

### Costs / Risks

* Process lifecycle có thể ẩn với developer chỉ test Kestrel local.
* In-process state dễ mất khi recycle.
* Legacy configuration complexity đáng kể.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu IIS app không sống vĩnh viễn; worker process có thể restart.

### Middle

Biết đọc IIS/Event Viewer logs và cấu hình app pool cơ bản.

### Senior

Thiết kế restart-safe state/background work và điều tra startup/recycle incidents.

### Technical Lead / Architect

Quyết định workload nào còn phù hợp IIS và modernization nào thực sự giảm operational risk.

## 11. Key takeaway

* Process restart là normal hosting event.
* Durable state không nên phụ thuộc `w3wp.exe` lifetime.
* Recycling không phải remediation cho root cause chưa hiểu.

# 9. Vue/TypeScript frontend authentication: access token lifecycle, 401 handling và tránh biến browser storage thành security boundary

## 1. What is it?

Frontend authentication là orchestration giữa browser, identity provider và backend APIs. Frontend có thể giữ short-lived access token để gọi API, nhưng authorization thật phải luôn được enforce ở server.

## 2. Why does it exist?

SPA cần xử lý login redirect, token expiry, concurrent API calls và 401. Nếu mỗi component tự xử lý token, logic phân tán, race condition tăng và security assumptions dễ sai.

## 3. How does it work?

```text
Browser → Identity Provider
   ↓ authenticated session
Browser obtains/uses access token
   ↓
API validates token
   ↓
API enforces authorization
```

Token trong browser là bearer credential: ai lấy được token có thể dùng nó trong lifetime còn hiệu lực. XSS vì vậy đặc biệt nguy hiểm.

## 4. Practical implementation

Một API client tập trung:

```ts
export async function apiFetch(
  input: RequestInfo,
  init: RequestInit = {}
): Promise<Response> {
  const token = await auth.getAccessToken();

  const headers = new Headers(init.headers);
  headers.set("Authorization", `Bearer ${token}`);

  const response = await fetch(input, { ...init, headers });

  if (response.status === 401) {
    await auth.handleUnauthorized();
  }

  return response;
}
```

Không nên để mỗi Vue component tự đọc `localStorage` và tự refresh token.

## 5. Real production scenario

Mười API requests chạy đồng thời đúng lúc token hết hạn. Mỗi interceptor tự trigger refresh, tạo mười refresh calls và một số request dùng token cũ. Single-flight refresh/coordinated auth client giúp serialize refresh workflow.

## 6. Failure scenario & troubleshooting

**Symptom** → user bị logout ngẫu nhiên khi nhiều requests cùng chạy.

**Evidence** → nhiều refresh operations concurrent và token state bị overwrite.

**Hypothesis** → refresh race condition.

**Diagnosis** → browser Network panel + auth client logs theo request correlation.

**Fix** → centralize refresh; share one in-flight refresh promise; retry request có giới hạn.

**Verification** → test token expiry với concurrent API requests.

## 7. Common mistakes

* Coi hidden button/menu là authorization.
* Lưu long-lived sensitive token tùy tiện trong `localStorage` mà không đánh giá XSS threat model.
* Infinite retry khi 401.
* Log token vào console/telemetry.
* Frontend decode claims rồi tin rằng API cũng sẽ chấp nhận.

## 8. Alternatives

Backend-for-Frontend với secure HttpOnly cookie có thể giảm token exposure cho browser JavaScript. Server-rendered app dùng cookie authentication thường đơn giản hơn SPA token orchestration.

## 9. Trade-offs

### Advantages

* SPA có thể gọi APIs linh hoạt.
* Central auth client giảm duplicated logic.

### Costs / Risks

* Token lifecycle và XSS surface phức tạp.
* Browser không phải trusted authorization boundary.
* Refresh/revocation behavior cần thiết kế rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu frontend authentication UX khác backend authorization enforcement.

### Middle

Centralize API/auth client và xử lý expiry/401 đúng.

### Senior

Đánh giá token storage, XSS, refresh race và BFF alternative.

### Technical Lead / Architect

Chọn SPA token flow hay BFF/cookie dựa trên threat model, platform constraints và operational complexity.

## 11. Key takeaway

* Browser token là credential, không phải authorization engine.
* 401/refresh cần coordinated lifecycle.
* Backend luôn phải enforce authorization độc lập với UI state.

# 10. AI coding agent verification: repository grounding, test evidence và static analysis trước khi chấp nhận generated change

## 1. What is it?

AI coding agent có thể đọc repository, sửa nhiều files và chạy tools. Nhưng output của agent vẫn là untrusted engineering proposal cho tới khi được kiểm chứng bằng repository evidence, compiler, tests, static analysis và review.

## 2. Why does it exist?

LLM có thể tạo API không tồn tại, dùng package version sai, hiểu nhầm architecture boundary hoặc viết test chỉ xác nhận implementation của chính nó. Tốc độ generation cao làm blast radius của assumption sai lớn hơn manual coding.

## 3. How does it work?

Một verification loop tốt:

```text
Requirement
   ↓
Repository-grounded plan
   ↓
Generated change
   ↓
Build / type check
   ↓
Unit + integration + E2E where relevant
   ↓
Static/security analysis
   ↓
Diff review against requirement
   ↓
Accept or revise
```

Deterministic tools kiểm tra những thứ model không nên tự “tin”.

## 4. Practical implementation

Ví dụ acceptance pipeline cho .NET repository:

```bash
dotnet restore
dotnet build --no-restore
dotnet test --no-build
```

Sau đó chạy repository-specific lint/static analysis và Playwright nếu change ảnh hưởng critical UI flow.

Reviewer cần kiểm tra cả **missing tests**: test suite pass không chứng minh requirement đã được cover nếu agent không viết test cho edge case quan trọng.

## 5. Real production scenario

Agent refactor authorization handler và tất cả generated unit tests pass. Nhưng tests mock `ClaimsPrincipal` theo assumption sai và không có integration test qua real ASP.NET Core authentication pipeline. Production users có claim mapping khác nên authorization fail.

Repository-grounded integration test sẽ bắt gap mà self-consistent unit tests bỏ qua.

## 6. Failure scenario & troubleshooting

**Symptom** → PR trông sạch, tests xanh nhưng behavior production sai.

**Evidence** → generated tests mirror implementation; không có test tại system boundary.

**Hypothesis** → verification thiếu independent oracle.

**Diagnosis** → trace requirement → code → tests; tìm acceptance criterion không có evidence.

**Fix** → thêm integration/contract/E2E test dựa trên external behavior, không dựa trên implementation detail.

**Verification** → cố tình revert/fault implementation và xác nhận test thật sự fail.

## 7. Common mistakes

* Chấp nhận code vì agent nói “tests pass” mà không xem tool evidence.
* Cho agent tự invent package/API thay vì kiểm tra project references/docs.
* Generated test mock quá sâu.
* Review chỉ diff syntax, không đối chiếu requirements/architecture.
* Cho model quyết định security-critical logic mà không deterministic validation.

## 8. Alternatives

AI autocomplete có blast radius nhỏ hơn repository agent. Manual implementation có tốc độ thấp hơn nhưng vẫn cần tests/review. Agent không thay thế CI; giá trị tốt nhất là tăng tốc vòng engineering đã có guardrails.

## 9. Trade-offs

### Advantages

* Tăng tốc repository analysis, repetitive changes và test scaffolding.
* Có thể thực hiện multi-file refactor nhanh.

### Costs / Risks

* Sai assumption có thể lan qua nhiều layers.
* Generated tests có thể tạo false confidence.
* Tool permissions và secret exposure cần kiểm soát.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Không coi generated code là source of truth; luôn build/test/read diff.

### Middle

Dùng agent với bounded task và kiểm tra compiler/tests.

### Senior

Thiết kế independent verification, review architecture/security và phát hiện misleading tests.

### Technical Lead / Architect

Định nghĩa agent permissions, required CI gates, human approval boundary và loại quyết định không được giao cho probabilistic model.

## 11. Key takeaway

* AI generation nhanh hơn không làm verification ít quan trọng hơn; ngược lại blast radius lớn hơn.
* Tests chỉ là evidence nếu chúng kiểm tra requirement độc lập với implementation assumption.
* Security, authorization và financial correctness phải có deterministic guardrails và human/accountable review.
