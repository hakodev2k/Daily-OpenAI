# 1. C# `Span<T>` và `Memory<T>`: zero-copy processing, lifetime rules và khi allocation optimization thực sự đáng giá

## 1. What is it?

`Span<T>` là một view liên tục lên vùng memory mà không nhất thiết sở hữu vùng memory đó. Nó có thể trỏ vào array, stack memory hoặc một phần buffer. `Memory<T>` có mental model tương tự nhưng có thể sống qua asynchronous boundary vì không bị giới hạn như `ref struct`.

Mental model:

```text
Owner: byte[] / pooled buffer / native memory
                ↓
          Span<T> / Memory<T>
                ↓
       view over a slice, not a copy
```

Điểm quan trọng: `Span<T>` tối ưu việc **tránh copy và allocation**, không phải một collection mới thay thế `List<T>`.

## 2. Why does it exist?

Các parser, serializer và protocol handlers thường cắt substring hoặc tạo temporary arrays. Mỗi copy nhỏ có vẻ rẻ, nhưng ở hot path hàng chục nghìn request/giây, chúng tạo allocation rate cao và tăng GC pressure.

`Span<T>` cho phép xử lý slice của buffer gốc mà không tạo object mới.

## 3. How does it work?

Ví dụ:

```csharp
ReadOnlySpan<char> input = "tenant:12345";
var separator = input.IndexOf(':');

ReadOnlySpan<char> kind = input[..separator];
ReadOnlySpan<char> id = input[(separator + 1)..];
```

`kind` và `id` chỉ là views lên string memory, không tạo hai substring mới.

`Span<T>` là `ref struct`, vì vậy compiler ngăn nó escape tới heap, field bình thường hoặc sống qua `await`. `Memory<T>` được dùng khi buffer view cần tồn tại qua async flow.

## 4. Practical implementation

Parsing request identifier mà không tạo nhiều strings:

```csharp
public static bool TryParseOrderKey(
    ReadOnlySpan<char> value,
    out Guid orderId)
{
    const string prefix = "order:";

    if (!value.StartsWith(prefix, StringComparison.OrdinalIgnoreCase))
    {
        orderId = default;
        return false;
    }

    return Guid.TryParse(value[prefix.Length..], out orderId);
}
```

Nếu cần async I/O, giữ owner dưới dạng `Memory<byte>`:

```csharp
Memory<byte> buffer = new byte[8192];
var read = await stream.ReadAsync(buffer, cancellationToken);
Process(buffer.Span[..read]);
```

## 5. Real production scenario

Một ingestion API parse hàng triệu CSV fields mỗi phút. Profiler cho thấy allocation lớn đến từ `Substring`, `Split` và temporary arrays. CPU chưa phải bottleneck chính; GC pause và allocation throughput mới là vấn đề.

Team thay parser hot path bằng `ReadOnlySpan<char>`, giảm allocation đáng kể. Họ không áp dụng Span vào business services thông thường vì readability cost không đem lại lợi ích đo được.

## 6. Failure scenario & troubleshooting

**Symptom** → optimization làm code phức tạp nhưng latency gần như không đổi.

**Evidence** → profiler cho thấy bottleneck thật nằm ở SQL I/O, allocation từ parser chỉ chiếm tỷ lệ nhỏ.

**Hypothesis** → team tối ưu sai layer.

**Diagnosis** → so sánh allocation profile, CPU samples và request trace trước/sau.

**Fix** → rollback complexity không cần thiết, tập trung bottleneck thật.

**Verification** → benchmark end-to-end thay vì chỉ microbenchmark parser.

## 7. Common mistakes

* Dùng `Span<T>` ở mọi nơi vì nghĩ nó luôn nhanh hơn.
* Cố giữ Span qua `await` thay vì dùng `Memory<T>`.
* Quên lifetime/ownership của pooled buffer bên dưới.
* Benchmark Debug build hoặc workload không đại diện production.
* Đổi readable code thành low-level slicing trước khi đo allocation.

## 8. Alternatives

* `string`/array bình thường: đơn giản và đủ tốt cho đa số business code.
* `ArrayPool<T>`: giảm allocations bằng buffer reuse nhưng thêm ownership complexity.
* `PipeReader`/`System.IO.Pipelines`: phù hợp streaming protocol parsing phức tạp.

## 9. Trade-offs

### Advantages

* Giảm copy và temporary allocation.
* Hữu ích cho parser, serializer, networking hot paths.
* Có thể giảm GC pressure đáng kể.

### Costs / Risks

* Lifetime rules khó hơn.
* API design có thể kém quen thuộc.
* Micro-optimization dễ làm code khó bảo trì nếu bottleneck không đáng kể.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Span là view lên memory, không sở hữu dữ liệu.

### Middle

Biết slicing, `ReadOnlySpan<T>`, và khi phải dùng `Memory<T>` qua async boundary.

### Senior

Dùng profiler/BenchmarkDotNet để chứng minh allocation hot spot trước khi tối ưu.

### Technical Lead / Architect

Quyết định low-level optimization có thuộc đúng boundary hay đang lan complexity vào business code.

## 11. Key takeaway

* `Span<T>` chủ yếu giải quyết copy/allocation trên hot path.
* `Memory<T>` phù hợp lifetime dài hơn và async flow.
* Đo trước; readability thường đáng giá hơn zero-copy nếu allocation không phải bottleneck.

# 2. ASP.NET Core graceful shutdown: request draining, `CancellationToken` và vì sao SIGTERM không đồng nghĩa process được phép chết ngay

## 1. What is it?

Graceful shutdown là quá trình application ngừng nhận work mới, cho work đang chạy cơ hội hoàn tất hoặc hủy có kiểm soát, giải phóng resources rồi mới exit.

Trong container/App Service/Kubernetes, process thường nhận termination signal trước khi infrastructure kill cưỡng bức.

## 2. Why does it exist?

Nếu process chết ngay khi deployment hoặc scale-in:

* HTTP request đang xử lý bị reset,
* background job có thể dừng giữa side effect,
* message lock có thể hết hạn rồi bị xử lý lại,
* buffer/log chưa flush,
* transaction chưa hoàn tất.

Graceful shutdown biến process lifecycle thành một phần reliability design.

## 3. How does it work?

```text
Platform requests termination
          ↓
Host signals ApplicationStopping
          ↓
Stop accepting new work
          ↓
Cancel/drain in-flight operations
          ↓
StopAsync / DisposeAsync
          ↓
Process exits before hard timeout
```

ASP.NET Core host cung cấp cancellation token cho shutdown. Background services nhận token trong `ExecuteAsync` và `StopAsync`.

## 4. Practical implementation

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var item = await queue.ReceiveAsync(stoppingToken);

            try
            {
                await ProcessAsync(item, stoppingToken);
                await queue.CompleteAsync(item, stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                // Leave message unsettled so it can be retried safely.
                break;
            }
        }
    }
}
```

Các dependency calls cũng phải nhận token; nếu inner call bỏ qua cancellation thì outer shutdown token gần như vô nghĩa.

## 5. Real production scenario

Deployment rolling restart một Worker Service đang resize images. Mỗi file mất 40 giây. Platform chỉ cho 30 giây shutdown grace period.

Worker bắt đầu file mới ngay trước SIGTERM và không observe cancellation. Process bị kill giữa upload, để lại partial side effect. Sau restart, message được delivery lại và tạo duplicate output.

Giải pháp không chỉ tăng timeout: worker phải ngừng nhận work mới, cancellation-aware, và processing phải idempotent.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment tạo spike 499/502 hoặc duplicate jobs.

**Evidence** → timestamp trùng termination/restart; logs không có completion/settlement.

**Hypothesis** → in-flight work bị hard kill trước graceful completion.

**Diagnosis** → kiểm tra platform termination grace period, host shutdown timeout, cancellation propagation và job duration.

**Fix** → drain sớm, propagate token, chia nhỏ long-running work hoặc checkpoint/idempotency.

**Verification** → terminate instance trong load test và theo dõi request/job outcomes.

## 7. Common mistakes

* Catch `OperationCanceledException` rồi log như production error.
* Không propagate `CancellationToken` xuống EF Core/HttpClient.
* `StopAsync` thực hiện cleanup không bounded và vượt hard timeout.
* Assume deployment platform chờ vô hạn.
* Background worker tiếp tục nhận work mới sau shutdown signal.

## 8. Alternatives

* Queue-triggered Azure Functions xử lý lifecycle phần lớn qua platform nhưng handler vẫn cần idempotency.
* External job orchestrator phù hợp long-running workflow cần durable checkpoints.
* Synchronous shutdown không thể đảm bảo hoàn tất mọi work; đôi khi recovery/retry mới là mechanism đúng.

## 9. Trade-offs

### Advantages

* Giảm dropped requests và partial work.
* Deployment/scale-in an toàn hơn.
* Resource cleanup rõ ràng.

### Costs / Risks

* Shutdown kéo dài deployment.
* Long-running work vẫn có thể vượt deadline.
* Cần idempotency vì graceful shutdown không bao giờ được đảm bảo tuyệt đối.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process có lifecycle và cancellation là cooperative.

### Middle

Propagate token, implement BackgroundService đúng và cleanup bounded.

### Senior

Thiết kế draining, idempotency, lock/message semantics và hard-timeout recovery.

### Technical Lead / Architect

Quyết định workload nào có thể chạy trong web process, workload nào cần durable worker/orchestrator riêng.

## 11. Key takeaway

* Graceful shutdown là bounded opportunity, không phải guarantee.
* Cancellation phải propagate end-to-end.
* Durable/idempotent recovery vẫn cần vì process có thể chết không báo trước.

# 3. EF Core split query vs single query: tránh cartesian explosion nhưng không vô tình tăng round trips và consistency risk

## 1. What is it?

Khi `Include` nhiều collection navigations, EF Core có thể tải graph bằng một SQL query lớn hoặc split thành nhiều queries.

Single query ưu tiên một round trip nhưng JOIN có thể nhân số rows. Split query giảm row duplication bằng cách query root và collections riêng.

## 2. Why does it exist?

Giả sử một Order có 20 Items và 10 Notes. JOIN cả hai collections có thể tạo 200 result rows cho chỉ một Order. Thêm collection thứ ba làm explosion lớn hơn.

Payload, SQL processing và materialization cost tăng dù domain objects thực tế ít hơn nhiều.

## 3. How does it work?

Single query:

```text
Orders
 JOIN Items
 JOIN Notes
      ↓
cartesian multiplication
```

Split query:

```text
Query Orders
Query Items for selected Orders
Query Notes for selected Orders
      ↓
EF fixes relationships in memory
```

`AsSplitQuery()` yêu cầu EF Core thực hiện nhiều SQL commands thay vì một JOIN graph lớn.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Include(x => x.Items)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .Take(50)
    .ToListAsync(cancellationToken);
```

Tốt hơn nữa, nếu API chỉ cần read model nhỏ, projection thường tránh cả hai vấn đề:

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummary(
        x.Id,
        x.Items.Count,
        x.Total))
    .Take(50)
    .ToListAsync(cancellationToken);
```

## 5. Real production scenario

Admin page load Orders + Items + Payments + Notes. Query SQL duy nhất trả hàng trăm nghìn rows cho 100 orders và p95 tăng lên 4 giây.

`AsSplitQuery` giảm payload mạnh. Sau đó team nhận ra UI chỉ cần counts và latest note, nên projection read model còn tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → chuyển sang split query giảm DB CPU nhưng latency lại tăng ở region có network latency cao.

**Evidence** → số round trips tăng từ 1 lên 4.

**Hypothesis** → cartesian cost đã giảm nhưng network round-trip cost chiếm ưu thế.

**Diagnosis** → inspect generated SQL, dependency telemetry và row counts.

**Fix** → projection, reshape query hoặc cân nhắc single query cho graph nhỏ.

**Verification** → đo cả rows transferred, DB duration và total request latency.

## 7. Common mistakes

* `Include` toàn graph chỉ vì entity có navigation.
* Bật split query global mà không hiểu workload.
* Không xét consistency giữa nhiều queries nếu data thay đổi giữa chúng.
* Fix N+1 bằng một mega-join tạo cartesian explosion.

## 8. Alternatives

* Projection DTO/read model thường là lựa chọn tốt nhất cho API reads.
* Explicit loading hữu ích khi decision phụ thuộc runtime nhưng dễ thành N+1.
* Raw SQL/Dapper phù hợp query đặc biệt cần kiểm soát shape sâu hơn.

## 9. Trade-offs

### Advantages

* Split query giảm duplicate rows cho nhiều collections.
* Single query giảm round trips và có snapshot-like result trong một statement.

### Costs / Risks

* Split query tăng round trips và có consistency window giữa queries.
* Single query có thể tạo huge intermediate result.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` không miễn phí.

### Middle

Inspect generated SQL và dùng projection/`AsSplitQuery` phù hợp.

### Senior

Đánh giá row multiplication, network latency, consistency và materialization cost.

### Technical Lead / Architect

Đặt read-model strategy thay vì để API layer mặc định serialize entity graph.

## 11. Key takeaway

* Single vs split là trade-off round trips với row explosion.
* Projection thường tốt hơn tải entity graph dư thừa.
* Luôn đo generated SQL và payload thực tế.

# 4. SQL Server parameter sniffing: cùng một query, cùng index nhưng execution plan có thể tốt cho tenant này và tệ cho tenant khác

## 1. What is it?

Parameter sniffing xảy ra khi SQL Server compile query plan dựa trên parameter values quan sát lúc compilation, rồi cache plan đó để tái sử dụng cho các values khác.

Plan reuse thường tốt. Vấn đề xuất hiện khi data distribution lệch mạnh và một plan không phù hợp mọi parameter.

## 2. Why does it exist?

Compile execution plan có cost. SQL Server cache plan để giảm CPU và tăng throughput. Optimizer cần cardinality estimate, nên parameter value ban đầu cung cấp thông tin hữu ích.

Nhưng multi-tenant database có thể có tenant 100 rows và tenant 20 triệu rows. Seek + nested loops tốt cho tenant nhỏ nhưng tệ cho tenant lớn; scan/hash join có thể ngược lại.

## 3. How does it work?

```sql
SELECT Id, Status, CreatedAt
FROM Orders
WHERE TenantId = @TenantId
  AND Status = @Status;
```

Nếu lần compile đầu dùng tenant nhỏ, optimizer có thể chọn plan tối ưu cho few rows. Plan được cache và tenant lớn dùng lại.

Pipeline reasoning:

```text
parameter values
→ cardinality estimate
→ join/access strategy
→ cached plan
→ reused under different distribution
```

## 4. Practical implementation

Trước khi “fix”, lấy actual execution plan và Query Store evidence. Các option có thể gồm query rewrite, statistics/index changes, plan forcing trong trường hợp kiểm soát tốt, hoặc `OPTION (RECOMPILE)` cho query hiếm nhưng distribution cực lệch.

Ví dụ targeted:

```sql
SELECT Id, Status, CreatedAt
FROM Orders
WHERE TenantId = @TenantId
  AND Status = @Status
OPTION (RECOMPILE);
```

Không nên thêm `RECOMPILE` đại trà vì compilation CPU cũng có giá.

## 5. Real production scenario

SaaS API cùng endpoint nhanh 50 ms cho hầu hết tenants nhưng 8 giây cho enterprise tenant. Index tồn tại và query text giống nhau.

Query Store cho thấy plan regression sau restart: plan compile bằng small tenant rồi reused cho large tenant. Đây là lý do “query hôm qua nhanh, hôm nay chậm” không nhất thiết code thay đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → latency phụ thuộc parameter, đôi khi biến mất sau plan cache clear rồi quay lại.

**Evidence** → same query hash có plan behavior/cardinality mismatch lớn.

**Hypothesis** → cached plan không phù hợp skewed distribution.

**Diagnosis** → Query Store, actual plan, estimated vs actual rows, statistics histogram.

**Fix** → chọn mitigation nhỏ nhất dựa trên evidence; có thể schema/index/query design quan trọng hơn hint.

**Verification** → test representative small/medium/large tenants và theo dõi plan stability.

## 7. Common mistakes

* Clear toàn plan cache như permanent fix.
* Thêm index mới mà không xem cardinality.
* Dùng `RECOMPILE` mọi query.
* Chỉ test query với một tenant dev nhỏ.
* Gọi mọi plan regression là parameter sniffing.

## 8. Alternatives

* Query Store plan forcing cho known stable plan.
* Separate query shapes cho materially different workload classes.
* Partition/data isolation cho extreme tenant skew nếu business scale biện minh.

## 9. Trade-offs

### Advantages

* Plan reuse giảm compilation cost.
* Sniffed value thường giúp optimizer chọn plan tốt.

### Costs / Risks

* Skewed data làm one-plan-fits-all không hiệu quả.
* Hints có thể khóa system vào assumptions cũ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu query performance phụ thuộc data distribution, không chỉ syntax/index.

### Middle

Đọc estimated vs actual rows và Query Store basics.

### Senior

Phân biệt statistics issue, plan regression và parameter sensitivity.

### Technical Lead / Architect

Đánh giá multi-tenant data model có đang tạo operational hotspot cần boundary lớn hơn query tuning hay không.

## 11. Key takeaway

* Cached plan là optimization có trade-off.
* Parameter skew có thể làm cùng query có latency rất khác nhau.
* Chẩn đoán bằng plan/cardinality evidence, không bằng cache-clearing ritual.

# 5. Elasticsearch reindex với alias: thay đổi mapping không downtime nhưng phải kiểm soát dual-write, lag và cutover correctness

## 1. What is it?

Nhiều Elasticsearch mapping changes không thể sửa trực tiếp trên field đã index. Reindex tạo index version mới, copy/rebuild documents, rồi chuyển alias từ old index sang new index.

```text
products-read → products-v1
                  ↓ reindex
               products-v2
                  ↑
             alias cutover
```

## 2. Why does it exist?

Analyzer, tokenizer hoặc field type quyết định cách dữ liệu được index. Thay `text` analyzer hoặc `keyword` strategy không thể magically reinterpret inverted index cũ.

Versioned index + alias cho phép rebuild song song mà client vẫn query một logical name ổn định.

## 3. How does it work?

Flow an toàn:

1. Create `products-v2` với mapping mới.
2. Backfill dữ liệu từ source of truth hoặc reindex old index.
3. Đồng bộ changes phát sinh trong thời gian backfill.
4. Validate counts/search semantics.
5. Atomically switch alias.
6. Giữ v1 một thời gian rollback.

Nếu primary database là source of truth, rebuild từ DB/event stream thường đáng tin hơn coi old index là canonical data.

## 4. Practical implementation

Alias switch có thể atomic:

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v1", "alias": "products-read" }},
    { "add":    { "index": "products-v2", "alias": "products-read" }}
  ]
}
```

Application chỉ query `products-read`.

Trong .NET, index name nên nằm sau search abstraction/config thay vì hard-code `products-v1` ở nhiều services.

## 5. Real production scenario

E-commerce search cần đổi analyzer để xử lý SKU và Vietnamese product names tốt hơn. Reindex mất 3 giờ. Trong 3 giờ đó, giá và inventory metadata vẫn thay đổi.

Nếu team chỉ snapshot v1 rồi switch, v2 thiếu updates mới. Họ cần replay change stream/outbox sequence tới watermark trước cutover.

## 6. Failure scenario & troubleshooting

**Symptom** → sau alias switch, search trả stale price hoặc thiếu products mới.

**Evidence** → document count gần đúng nhưng synchronization lag chưa về zero.

**Hypothesis** → backfill hoàn tất nhưng delta changes chưa catch up.

**Diagnosis** → compare source-of-truth version/timestamp với indexed document version.

**Fix** → replay missing changes, validate watermark rồi switch lại.

**Verification** → sampled consistency checks và search acceptance tests trước/after alias change.

## 7. Common mistakes

* Coi Elasticsearch là transactional source of truth.
* Switch alias chỉ dựa vào document count.
* Không version document/change event.
* Xóa old index ngay, mất rollback path.
* Dual-write trực tiếp từ request path mà không xử lý partial failure.

## 8. Alternatives

* Runtime fields phù hợp một số computed use case nhưng không thay analyzer rebuild.
* New field mapping song song có thể tránh full index migration trong thay đổi nhỏ.
* Database full-text search có thể đủ cho hệ thống đơn giản, giảm operational component.

## 9. Trade-offs

### Advantages

* Mapping evolution không downtime.
* Alias che physical index version khỏi application.
* Rollback nhanh nếu old index còn giữ.

### Costs / Risks

* Temporary storage gần gấp đôi.
* Synchronization/replay phức tạp.
* Cutover correctness cần validation ngoài count.

### Junior

Hiểu mapping ảnh hưởng index-time behavior.

### Middle

Tạo versioned index, reindex và alias switch.

### Senior

Thiết kế delta synchronization, validation và rollback.

### Technical Lead / Architect

Quyết định search index lifecycle, source-of-truth boundary và operational ownership.

## 11. Key takeaway

* Mapping migration thường là data migration.
* Alias làm cutover atomic nhưng không tự đảm bảo dữ liệu đúng.
* Source-of-truth + replay strategy quyết định recovery quality.

# 6. Hexagonal Architecture và anti-corruption boundary: cô lập third-party API volatility mà không tạo abstraction ceremony khắp codebase

## 1. What is it?

Hexagonal Architecture tổ chức dependency quanh application/domain core và các ports/adapters. Core định nghĩa capability nó cần; infrastructure adapter triển khai capability bằng SQL, HTTP, queue hoặc vendor SDK.

```text
          Payment Provider
                │
           Adapter
                │
API ─────── Application Core ─────── Database Adapter
                │
              Port
```

Anti-corruption layer (ACL) dịch external model sang language của domain để vendor concepts không lan khắp system.

## 2. Why does it exist?

Third-party APIs thay đổi schema, naming, auth và error semantics. Nếu business code trực tiếp phụ thuộc vendor DTOs, SDK exceptions và status codes, vendor trở thành implicit domain model.

Boundary tồn tại để isolate change và giữ business rules diễn đạt bằng language của chính hệ thống.

## 3. How does it work?

Application định nghĩa port theo nhu cầu business:

```csharp
public interface IPaymentGateway
{
    Task<PaymentResult> AuthorizeAsync(
        PaymentRequest request,
        CancellationToken cancellationToken);
}
```

Vendor adapter map request/response:

```csharp
public sealed class AcmePaymentGateway(HttpClient client) : IPaymentGateway
{
    public async Task<PaymentResult> AuthorizeAsync(
        PaymentRequest request,
        CancellationToken cancellationToken)
    {
        var response = await client.PostAsJsonAsync(
            "/charges",
            new AcmeChargeRequest(request.Amount, request.Currency),
            cancellationToken);

        return await MapAsync(response, cancellationToken);
    }
}
```

Domain/application không biết `AcmeChargeRequest`.

## 4. Practical implementation

Không cần tạo interface cho mọi class. Boundary có giá trị khi dependency có volatility, external ownership hoặc test/replacement need rõ ràng.

Một simple internal helper không cần `IHelperPort` + `HelperAdapter` chỉ để “đúng Hexagonal”.

## 5. Real production scenario

Review provider đổi API v2: rating field đổi scale, pagination contract đổi và một status mới xuất hiện.

Nếu controller/domain dùng vendor DTO trực tiếp, change lan nhiều modules. Với ACL, phần lớn migration nằm trong adapter; domain vẫn dùng `ReviewRating` và `PagedReviews` ổn định.

## 6. Failure scenario & troubleshooting

**Symptom** → provider trả status mới, adapter map thành generic failure và checkout bị reject.

**Evidence** → raw external response khác known mapping.

**Hypothesis** → ACL contract chưa tolerant với provider evolution.

**Diagnosis** → compare provider contract/version, adapter logs và mapping tests.

**Fix** → update adapter mapping, preserve unknown-value strategy nếu phù hợp.

**Verification** → contract tests với representative provider payloads.

## 7. Common mistakes

* Interface cho mọi class dù không có boundary thật.
* Domain model mirror 1:1 vendor schema.
* Adapter leak vendor exception ra application.
* Hide HTTP status/retry semantics quá sâu khiến troubleshooting khó.
* Dùng architecture để tăng folders thay vì isolate change.

## 8. Alternatives

* Direct SDK usage hợp lý cho small app hoặc low-risk dependency.
* Layered architecture đơn giản đủ cho CRUD system ít external volatility.
* Separate integration service chỉ đáng dùng khi ownership/deployment/scaling thực sự khác.

## 9. Trade-offs

### Advantages

* Change isolation tốt.
* Domain language độc lập vendor.
* Testing integration mapping rõ ràng.

### Costs / Risks

* Thêm mapping và abstractions.
* Có thể che mất useful provider semantics.
* Overengineering nếu dependency đơn giản và ổn định.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu adapter dịch external dependency sang application contract.

### Middle

Implement port/adapter và mapping tests.

### Senior

Chọn đúng abstraction boundary, preserve diagnostics và failure semantics.

### Technical Lead / Architect

Quyết định vendor volatility có đáng isolation cost hay direct integration đơn giản hơn.

## 11. Key takeaway

* Architecture boundary phải isolate change, không phải tạo ceremony.
* External DTO không nên tự động trở thành domain model.
* Một abstraction chỉ có giá trị khi nó bảo vệ một dependency boundary thật.

# 7. Azure Blob Storage large-file streaming và SAS: upload/download lớn mà không buffer toàn file hoặc phát tán storage credentials

## 1. What is it?

Azure Blob Storage lưu object lớn ngoài web server filesystem. Streaming xử lý file theo chunks/stream thay vì load toàn file vào RAM. SAS cấp quyền hạn chế theo resource, permission và thời gian thay vì chia sẻ account key.

## 2. Why does it exist?

Một API nhận file 2 GB mà gọi `ReadToEnd` hoặc copy vào `byte[]` sẽ tạo memory pressure cực lớn. Nhiều upload đồng thời có thể OOM process.

Nếu client có thể upload trực tiếp Blob Storage bằng short-lived SAS, application không cần trở thành data pipe cho toàn bộ bytes.

## 3. How does it work?

Recommended flow cho large client upload:

```text
Client → API: request upload authorization
API → Client: short-lived SAS for one blob
Client → Blob Storage: upload directly
Client/API → finalize metadata
```

Với Managed Identity, backend có thể tạo user delegation SAS mà không giữ storage account key.

## 4. Practical implementation

Backend streaming upload khi direct upload không phù hợp:

```csharp
public async Task UploadAsync(
    Stream input,
    BlobClient blob,
    CancellationToken cancellationToken)
{
    await blob.UploadAsync(
        input,
        overwrite: false,
        cancellationToken);
}
```

Không làm:

```csharp
using var ms = new MemoryStream();
await input.CopyToAsync(ms);
await blob.UploadAsync(new BinaryData(ms.ToArray()));
```

với file lớn.

## 5. Real production scenario

CMS cho editors upload video 1.5 GB. Web App trước đây proxy toàn upload và memory tăng theo concurrent uploads. Scale-out chỉ làm tăng cost.

Team chuyển sang direct-to-Blob SAS. API chỉ authorize file name/type/size, tạo upload intent và finalize metadata sau khi blob tồn tại.

## 6. Failure scenario & troubleshooting

**Symptom** → client upload được vào path ngoài tenant của mình.

**Evidence** → SAS scope cấp ở container level với write permission quá rộng.

**Hypothesis** → authorization boundary nằm sai ở storage token.

**Diagnosis** → inspect SAS resource scope, permissions và expiry.

**Fix** → SAS cho exact blob/path, short expiry, server-side authorization trước issuance.

**Verification** → negative tests thử upload sang tenant/path khác.

## 7. Common mistakes

* Dùng account key trong app settings khi Managed Identity khả dụng.
* SAS expiry quá dài.
* Buffer toàn file trong memory.
* Tin content type/file extension từ client.
* Không có cleanup cho abandoned uploads.

## 8. Alternatives

* API streaming phù hợp khi server phải inspect/transform bytes inline.
* Azure Files phù hợp filesystem semantics khác object storage.
* CDN trước Blob phù hợp download public/static content quy mô lớn.

## 9. Trade-offs

### Advantages

* Giảm web-app bandwidth/memory.
* Blob Storage scale tốt cho object data.
* SAS giới hạn quyền tốt hơn shared account key.

### Costs / Risks

* Upload workflow nhiều bước hơn.
* Direct upload cần finalize/validation/cleanup logic.
* SAS leak vẫn có giá trị tới expiry.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu stream khác load toàn file vào RAM.

### Middle

Implement Blob SDK, cancellation và SAS scope đúng.

### Senior

Thiết kế direct upload, malware/content validation, retries và abandoned-file lifecycle.

### Technical Lead / Architect

Quyết định data plane có nên đi qua application hay client-to-storage trực tiếp dựa trên security, transformation và cost.

## 11. Key takeaway

* Large-file path phải được thiết kế theo streaming.
* SAS là delegated capability; scope và lifetime phải tối thiểu.
* Managed Identity giảm secret management nhưng không thay authorization design.

# 8. Kubernetes readiness vs liveness probes: một probe sai có thể biến dependency chậm thành restart storm

## 1. What is it?

Readiness trả lời: **Pod có sẵn sàng nhận traffic không?**

Liveness trả lời: **Process có cần restart vì không thể tự hồi phục không?**

Hai câu hỏi khác nhau nhưng thường bị cấu hình thành cùng một endpoint.

## 2. Why does it exist?

Một process có thể đang sống nhưng chưa ready: startup warming, migration dependency, cache bootstrap. Ngược lại, process có thể deadlocked và cần restart.

Nếu liveness phụ thuộc trực tiếp SQL/Redis, một database outage có thể khiến mọi pods restart dù application process hoàn toàn khỏe.

## 3. How does it work?

```text
Readiness fail
→ Pod removed from Service endpoints
→ process remains running

Liveness fail repeatedly
→ kubelet restarts container
```

ASP.NET Core health checks có thể tách tags:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, tags: ["ready"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

## 4. Practical implementation

Kubernetes:

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5

livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10
  failureThreshold: 3
```

Startup-heavy applications có thể cần `startupProbe` để liveness không kill chúng trong legitimate initialization.

## 5. Real production scenario

Redis outage kéo dài 2 phút. Liveness endpoint kiểm Redis nên tất cả 20 pods fail cùng lúc và restart liên tục. Startup lại cần Redis, tạo CrashLoopBackOff.

Nếu Redis chỉ ảnh hưởng một feature degradable, process đáng lẽ vẫn live; readiness hoặc application fallback mới là nơi phản ánh dependency state.

## 6. Failure scenario & troubleshooting

**Symptom** → pods restart hàng loạt đúng lúc dependency outage.

**Evidence** → `kubectl describe pod` cho thấy liveness probe failed trước restart.

**Hypothesis** → liveness kiểm external dependency.

**Diagnosis** → inspect health endpoint implementation và restart events.

**Fix** → liveness chỉ kiểm unrecoverable process health; dependency checks chuyển readiness hoặc degraded telemetry phù hợp.

**Verification** → simulate Redis/SQL outage và xác nhận pods không restart storm.

## 7. Common mistakes

* Cùng endpoint cho readiness/liveness.
* Probe timeout quá ngắn so với normal startup/load behavior.
* Health endpoint thực hiện expensive queries.
* Readiness fail toàn service khi dependency optional bị lỗi.
* Không có startup probe cho slow-start app.

## 8. Alternatives

* Platform-specific App Service health check có semantics đơn giản hơn nhưng vẫn cần endpoint design tốt.
* External synthetic monitoring kiểm user journey; không thay liveness.

## 9. Trade-offs

### Advantages

* Tự động traffic removal/recovery.
* Rolling deployment an toàn hơn.

### Costs / Risks

* Probe sai có thể khuếch đại outage.
* Dependency graph phức tạp khiến “healthy” không phải boolean đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt ready và alive.

### Middle

Cấu hình health endpoints/probes và đọc pod events.

### Senior

Thiết kế dependency-aware health semantics, thresholds và startup behavior.

### Technical Lead / Architect

Định nghĩa service degradation model: dependency nào bắt buộc, dependency nào optional và khi nào restart thực sự giúp.

## 11. Key takeaway

* Readiness điều khiển traffic; liveness điều khiển restart.
* External dependency failure thường không phải lý do restart process.
* Health checks sai có thể trở thành failure amplifier.

# 9. Playwright E2E test reliability: auto-wait, deterministic test data và vì sao `Thread.Sleep` chỉ che race condition

## 1. What is it?

E2E test kiểm tra user flow qua browser, frontend, API và backend dependencies. Playwright cung cấp locator-based auto-wait và web-first assertions để đồng bộ theo observable UI state thay vì arbitrary delay.

## 2. Why does it exist?

Browser UI là asynchronous system: network, rendering, JavaScript promises và animations chạy ở thời điểm khác nhau. Test dùng fixed sleeps vừa chậm vừa flaky vì CI machine/load khác local.

Reliable E2E test phải chờ **condition**, không chờ **thời gian đoán**.

## 3. How does it work?

Bad:

```csharp
await page.ClickAsync("#save");
await Task.Delay(3000);
var text = await page.TextContentAsync("#status");
```

Better:

```csharp
await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();
await Expect(page.GetByTestId("status"))
    .ToHaveTextAsync("Saved");
```

Assertion retry tới timeout khi DOM state chưa đạt điều kiện.

## 4. Practical implementation

Test data nên unique và API-seeded khi có thể:

```csharp
var email = $"e2e-{Guid.NewGuid():N}@example.test";
await api.CreateUserAsync(email);

await page.GotoAsync("/users");
await page.GetByPlaceholder("Search").FillAsync(email);
await Expect(page.GetByText(email)).ToBeVisibleAsync();
```

Cleanup phải idempotent hoặc environment có disposable data lifecycle.

## 5. Real production scenario

Checkout E2E pass local nhưng fail 8% CI. Team tăng sleeps từ 1 lên 5 giây, suite tăng lên 40 phút mà vẫn flaky.

Trace viewer cho thấy test click trước khi button thực sự enabled sau inventory request. Chuyển sang semantic locator + assertion trên enabled/visible state loại race thay vì che nó.

## 6. Failure scenario & troubleshooting

**Symptom** → intermittent timeout chỉ trên CI.

**Evidence** → Playwright trace cho thấy API response chậm và element state thay đổi sau click attempt.

**Hypothesis** → test synchronization hoặc shared test data race.

**Diagnosis** → inspect trace, screenshots, network, console logs và parallel worker collisions.

**Fix** → condition-based waits, isolated data, stable selectors; không tăng global timeout trước khi biết root cause.

**Verification** → repeat test hàng chục/hàng trăm lần parallel trong CI.

## 7. Common mistakes

* `Thread.Sleep`/`Task.Delay` làm synchronization.
* CSS selectors gắn chặt DOM implementation.
* Tests share một account mutable.
* E2E cover mọi branch mà unit/integration test rẻ hơn có thể bảo vệ.
* Retry flaky test rồi coi build xanh là solved.

## 8. Alternatives

* Unit tests cho pure logic.
* Integration/API tests cho backend contracts nhanh và ổn định hơn.
* Component tests cho UI behavior không cần full system.

## 9. Trade-offs

### Advantages

* Bảo vệ critical user journeys xuyên stack.
* Bắt integration/configuration issues mà unit test không thấy.

### Costs / Risks

* Chậm và nhạy môi trường hơn.
* Test data/identity/dependency setup phức tạp.
* Failure localization khó hơn lower-level tests.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu E2E test user-visible behavior, không implementation details.

### Middle

Dùng locators, web-first assertions, trace và isolated data.

### Senior

Phân loại flaky root cause, xây test pyramid theo risk và CI parallelism.

### Technical Lead / Architect

Quyết định critical journeys nào xứng đáng E2E coverage và quality gate nào không làm pipeline quá chậm.

## 11. Key takeaway

* Chờ condition, không chờ số giây đoán.
* Flakiness thường là signal của race/data coupling.
* E2E nên ít nhưng bảo vệ workflow có business risk cao.

# 10. Akamai/CDN cache invalidation: TTL, purge và cache key design quyết định stale-content incident nhiều hơn việc “CDN có nhanh không”

## 1. What is it?

CDN cache response gần user tại edge. Cache key quyết định requests nào dùng chung object; TTL quyết định object có thể sống bao lâu; purge/invalidation yêu cầu edge loại hoặc refresh cached object trước TTL tự hết.

## 2. Why does it exist?

CDN giảm latency và origin load, nhưng đổi lại origin không còn kiểm soát trực tiếp mọi response sau khi object đã cache.

Một content update ở CMS không có nghĩa edge lập tức biết dữ liệu đã đổi.

## 3. How does it work?

```text
Browser
  ↓
Akamai Edge
  ├─ HIT  → return cached response
  └─ MISS → Origin → cache response → return
```

`Cache-Control` có thể định nghĩa freshness:

```http
Cache-Control: public, max-age=60, s-maxage=600
```

Cache key thường gồm host/path/query theo policy. Nếu key bỏ sót dimension quan trọng như language hoặc tenant, user có thể nhận response của context khác.

## 4. Practical implementation

ASP.NET Core response cho public catalog metadata:

```csharp
context.Response.Headers.CacheControl =
    "public, max-age=60, s-maxage=600";
```

Không cache personalized response chỉ vì endpoint là GET. Với CMS publish, có thể trigger Akamai purge theo URL/tag strategy nếu freshness requirement thấp hơn TTL.

## 5. Real production scenario

Marketing publish giá promotion mới nhưng edge giữ product page 30 phút. Origin và CMS đều đúng; chỉ một số regions stale vì edge objects có tuổi khác nhau.

Team ban đầu restart application nhưng không thay đổi gì. Root cause nằm ở CDN cache lifecycle, không phải app process.

## 6. Failure scenario & troubleshooting

**Symptom** → user region A thấy content cũ, region B thấy mới; origin direct luôn đúng.

**Evidence** → response headers cho thấy CDN HIT và object age cao.

**Hypothesis** → stale edge cache hoặc purge chưa propagate.

**Diagnosis** → compare cache key dimensions, Age/cache headers, purge status và origin response.

**Fix** → purge đúng object; sửa TTL/cache-key policy nếu incident có tính hệ thống.

**Verification** → request từ representative edges và kiểm cache headers/content version.

## 7. Common mistakes

* Cache personalized/authenticated response như public.
* Cache key bỏ language/currency dimension.
* TTL dài nhưng không có purge workflow.
* Purge toàn site cho mọi content update, làm origin spike.
* Debug CDN incident bằng restart application.

## 8. Alternatives

* Browser caching giảm client requests nhưng không chia sẻ cache giữa users.
* Redis/application cache gần origin, không giảm WAN latency như edge CDN.
* Versioned immutable asset URLs loại nhu cầu purge cho static assets.

## 9. Trade-offs

### Advantages

* Giảm latency toàn cầu.
* Giảm origin bandwidth/compute.
* Hấp thụ traffic burst tốt.

### Costs / Risks

* Freshness và invalidation phức tạp.
* Cache-key bug có thể thành data-isolation/security incident.
* Purge strategy sai có thể gây origin thundering herd.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HIT/MISS, TTL và origin.

### Middle

Đọc cache headers và cấu hình cacheability cơ bản.

### Senior

Thiết kế cache key, purge, stale tolerance và origin protection.

### Technical Lead / Architect

Quyết định content classes nào cache được, freshness SLO, invalidation ownership và security boundaries.

## 11. Key takeaway

* CDN performance luôn đi cùng freshness semantics.
* Cache key là correctness/security boundary.
* Purge là operational mechanism; immutable versioned assets thường đơn giản hơn invalidation.
