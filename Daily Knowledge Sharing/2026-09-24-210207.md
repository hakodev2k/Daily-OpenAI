# 1. C# `IAsyncEnumerable<T>`: streaming có backpressure tự nhiên nhưng giữ resource lâu hơn

## 1. What is it?

Mental model: `IAsyncEnumerable<T>` là một sequence mà mỗi phần tử có thể cần asynchronous work để xuất hiện. Consumer dùng `await foreach`; producer không cần materialize toàn bộ collection trước khi trả dữ liệu.

Khác `Task<List<T>>`, kết quả được giao từng phần tử. Điều này đặc biệt hữu ích khi source lớn, chậm hoặc bản chất đã streaming.

## 2. Why does it exist?

Nếu query trả 500.000 rows rồi `ToListAsync()`, application phải chờ toàn bộ query/materialization và giữ toàn bộ objects trong memory trước khi xử lý. Streaming cho phép xử lý sớm hơn và giảm peak memory.

Nhưng “ít memory hơn” không có nghĩa “luôn tốt hơn”: connection, reader hoặc HTTP response có thể sống lâu hơn.

## 3. How does it work?

```text
Consumer requests next item
        ↓
Async iterator resumes
        ↓
await I/O if necessary
        ↓
yield return item
        ↓
Consumer processes item
        ↓
request next item
```

Consumer pace tự nhiên giới hạn tốc độ producer tiến tới phần tử tiếp theo.

## 4. Practical implementation

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    await foreach (var order in _db.Orders
        .AsNoTracking()
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        yield return new OrderDto(order.Id, order.Total);
    }
}
```

Cancellation phải propagate vì stream có thể kéo dài đáng kể.

## 5. Real production scenario

Một export worker đọc hàng triệu records và ghi từng batch sang Blob Storage. Materialize toàn bộ dataset tạo LOH/GC pressure; async streaming giữ memory bounded theo batch size.

## 6. Failure scenario & troubleshooting

**Symptom** → database connection pool exhaustion dù memory giảm. **Evidence** → nhiều streaming operations sống hàng chục giây và giữ active readers. **Hypothesis** → resource lifetime kéo dài. **Diagnosis** → trace query duration, active connections và consumer throughput. **Fix** → batch/keyset pagination hoặc giới hạn concurrent streams. **Verification** → load test đồng thời và quan sát pool utilization.

## 7. Common mistakes

Trả `IAsyncEnumerable<T>` rồi enumerate hai lần; không cancel khi client disconnect; làm expensive work giữa các rows khiến DB reader mở lâu; tưởng streaming đồng nghĩa pagination; serialize stream nhưng middleware lại buffer response.

## 8. Alternatives

`Task<List<T>>` đơn giản hơn cho tập nhỏ. Keyset pagination phù hợp public API cần page semantics. `Channel<T>` phù hợp producer/consumer decoupling khi producer cần chạy độc lập.

## 9. Trade-offs

### Advantages

Giảm peak memory, time-to-first-item thấp, xử lý dataset lớn tự nhiên.

### Costs / Risks

Resource lifetime dài, partial failure giữa stream, retry khó hơn và transaction consistency cần cân nhắc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu sequence được tạo dần thay vì có sẵn toàn bộ.

### Middle
Implement cancellation và disposal đúng.

### Senior
Đo connection lifetime, serialization buffering và failure giữa stream.

### Technical Lead / Architect
Quyết định streaming, batching hay pagination dựa trên resource ownership và client contract.

## 11. Key takeaway

- Streaming đổi memory pressure lấy resource lifetime dài hơn.
- Cancellation là bắt buộc cho long-lived streams.
- Đo connection concurrency, không chỉ allocation.

# 2. ASP.NET Core `ProblemDetails`: error contract ổn định thay vì exception text rò ra API

## 1. What is it?

`ProblemDetails` là structured HTTP error representation. Mental model: exception là implementation detail bên trong; API error response là public contract bên ngoài.

## 2. Why does it exist?

Nếu mỗi endpoint trả một shape khác nhau hoặc gửi `ex.Message`, clients phải đoán cách parse lỗi và server có thể leak stack/database/internal details.

## 3. How does it work?

```text
Exception/domain failure
        ↓
central exception mapping
        ↓
HTTP status + ProblemDetails
        ↓
stable client-visible error contract
```

`type`, `title`, `status`, `detail`, `instance` và extensions có thể mô tả lỗi theo machine-readable contract.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();
app.UseExceptionHandler();

return Results.Problem(
    statusCode: StatusCodes.Status409Conflict,
    title: "Order cannot be modified",
    extensions: new Dictionary<string, object?>
    {
        ["code"] = "ORDER_ALREADY_SHIPPED"
    });
```

Client logic nên dựa vào stable error code/status, không parse English message.

## 5. Real production scenario

Mobile app và web app cùng gọi Order API. Backend refactor exception classes nhưng giữ `409 + ORDER_ALREADY_SHIPPED`; clients không cần release đồng thời.

## 6. Failure scenario & troubleshooting

**Symptom** → production response lộ SQL/server path. **Evidence** → `detail` chứa raw exception. **Hypothesis** → exception mapper serialize internal message. **Diagnosis** → inspect response/log policy. **Fix** → generic public detail + correlation ID; full exception chỉ ở protected telemetry. **Verification** → integration tests cho known/unknown exceptions.

## 7. Common mistakes

Mọi lỗi đều 500; mọi lỗi đều 400; trả stack trace; dùng localized message làm machine code; domain validation và infrastructure failure chung một contract mơ hồ.

## 8. Alternatives

Custom error envelope có thể hợp lệ nếu hệ thống đã có contract ổn định. `ProblemDetails` có lợi vì theo HTTP standard và tooling hỗ trợ tốt.

## 9. Trade-offs

### Advantages

Consistency, security, client compatibility và observability tốt hơn.

### Costs / Risks

Cần governance cho error codes và mapping; abstraction quá chung có thể mất domain semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt HTTP status và exception.

### Middle
Map validation/not-found/conflict đúng semantics.

### Senior
Thiết kế stable error taxonomy, correlation và security boundaries.

### Technical Lead / Architect
Quản lý error contract như versioned API surface.

## 11. Key takeaway

- Exception type không phải API contract.
- Public errors phải ổn định và không leak internals.
- Clients cần machine-readable semantics.

# 3. PostgreSQL MVCC và vacuum: vì sao UPDATE tạo dead tuples

## 1. What is it?

PostgreSQL dùng MVCC để nhiều transactions đọc/ghi đồng thời mà readers thường không block writers. Mental model quan trọng: `UPDATE` thường tạo row version mới; version cũ chưa thể biến mất ngay vì transaction khác có thể vẫn cần nhìn thấy nó.

## 2. Why does it exist?

Nếu mỗi read phải lock row chống update, concurrency giảm mạnh. MVCC cho mỗi transaction một visibility view dựa trên row versions.

## 3. How does it work?

```text
Row v1 visible to old snapshot
UPDATE
   ↓
Row v2 becomes current for new snapshot
v1 becomes dead only when no active snapshot needs it
   ↓
VACUUM can reclaim/reuse space
```

Autovacuum giữ dead tuples và transaction ID lifecycle trong kiểm soát.

## 4. Practical implementation

Theo dõi tables có update/delete nhiều:

```sql
SELECT relname, n_live_tup, n_dead_tup,
       last_autovacuum, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Đừng chỉ chạy `VACUUM FULL` theo phản xạ; nó có locking/storage implications mạnh hơn normal vacuum.

## 5. Real production scenario

Một job update trạng thái hàng triệu queue rows mỗi ngày. Table logical row count ổn định nhưng disk/index size tăng. Dead tuples sinh nhanh hơn autovacuum có thể xử lý.

## 6. Failure scenario & troubleshooting

**Symptom** → query I/O tăng và table bloat. **Evidence** → `n_dead_tup` cao, autovacuum chậm/không bắt kịp. **Hypothesis** → update churn hoặc long-running transaction ngăn cleanup. **Diagnosis** → inspect active transactions, vacuum stats, table/index growth. **Fix** → xử lý long transaction, tune autovacuum theo table và giảm unnecessary updates. **Verification** → dead tuple trend và latency ổn định lại.

## 7. Common mistakes

Tưởng DELETE trả disk ngay cho OS; disable autovacuum; transaction mở hàng giờ; update column dù value không đổi; chỉ nhìn table size mà bỏ index bloat.

## 8. Alternatives

Không có replacement đơn giản cho MVCC trong PostgreSQL. Data lifecycle có thể dùng partitioning để drop partitions hiệu quả hơn cho time-series/retention workloads.

## 9. Trade-offs

### Advantages

Read/write concurrency mạnh và snapshot semantics rõ.

### Costs / Risks

Version churn, vacuum overhead, bloat và operational tuning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu UPDATE không nhất thiết sửa row tại chỗ.

### Middle
Đọc vacuum/dead tuple statistics.

### Senior
Liên hệ long transactions, bloat, indexes và I/O.

### Technical Lead / Architect
Thiết kế retention/update patterns phù hợp MVCC thay vì chống lại storage engine.

## 11. Key takeaway

- MVCC tạo row-version lifecycle.
- Autovacuum là core database mechanism, không phải housekeeping tùy chọn.
- Long-running transactions có thể gây hậu quả ngoài transaction đó.

# 4. Cosmos DB partition key: quyết định scalability, transaction boundary và RU distribution

## 1. What is it?

Partition key là giá trị Cosmos DB dùng để phân phối items vào logical partitions và sau đó physical partitions. Mental model: chọn partition key là chọn cách data và traffic được chia trên distributed storage.

## 2. Why does it exist?

Một machine/storage partition không thể scale vô hạn. Cosmos DB cần key để route requests và phân phối capacity. Key kém có thể tạo hot partition dù tổng database còn nhiều capacity.

## 3. How does it work?

```text
Request + partition key
        ↓
route to logical partition
        ↓
physical partition hosting it
```

Operations có partition key cụ thể thường route hiệu quả hơn cross-partition queries. Transactional batch bị giới hạn trong cùng logical partition key.

## 4. Practical implementation

Trong multi-tenant workload, `/tenantId` có thể tốt nếu tenant distribution đủ đều và transaction/query boundaries chủ yếu theo tenant. Nhưng một “mega tenant” có thể phá giả định đó.

Đánh giá cardinality, storage growth, request distribution và dominant access patterns trước khi tạo container.

## 5. Real production scenario

Event SaaS chọn `/country` làm key. 70% traffic đến Việt Nam trong campaign, tạo hot partition. Chuyển sang key có cardinality/distribution phù hợp hơn cần migration container, không phải một index change đơn giản.

## 6. Failure scenario & troubleshooting

**Symptom** → 429 throttling dù overall RU chưa dùng hết. **Evidence** → một partition key range có normalized RU cao. **Hypothesis** → hot partition. **Diagnosis** → inspect per-partition metrics và top keys. **Fix** → workload/data redesign, key strategy hoặc synthetic/hierarchical strategy phù hợp. **Verification** → distribution dưới production load.

## 7. Common mistakes

Key có cardinality thấp; chọn key chỉ theo entity identity mà bỏ query patterns; nghĩ provision thêm RU luôn sửa hot partition; cross-partition scan thường xuyên; không tính transaction boundary.

## 8. Alternatives

SQL/PostgreSQL phù hợp khi relational transactions/query flexibility quan trọng hơn horizontal partition model. MongoDB có sharding model khác nhưng vẫn yêu cầu shard-key reasoning tương tự.

## 9. Trade-offs

### Advantages

Horizontal scale và efficient routing khi model đúng.

### Costs / Risks

Partition key khó đổi, ảnh hưởng query cost, transactions và hotspot behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu key quyết định data placement.

### Middle
Viết point reads/queries có partition key.

### Senior
Phân tích RU, skew, hot partitions và transaction boundaries.

### Technical Lead / Architect
Chọn data model dựa trên future scale/access patterns và migration cost.

## 11. Key takeaway

- Partition key là architecture decision, không phải field annotation nhỏ.
- Cardinality và traffic distribution đều quan trọng.
- Thiết kế sai thường đắt để sửa sau production.

# 5. Hexagonal Architecture: ports/adapters để cô lập thay đổi

## 1. What is it?

Hexagonal Architecture đặt application/domain logic ở trung tâm và giao tiếp với thế giới ngoài qua ports; adapters implement các ports cho HTTP, database, messaging hoặc third-party systems.

Mental model: boundary theo responsibility/change pressure, không theo số project.

## 2. Why does it exist?

Business logic thường bị trộn với EF Core, HTTP SDK hoặc vendor APIs. Khi integration thay đổi, core behavior bị kéo theo và testing khó vì phải dựng infrastructure.

## 3. How does it work?

```text
        HTTP Adapter
             ↓
        Input Port
             ↓
      Application Core
             ↓
        Output Port
        ↙         ↘
 SQL Adapter   Vendor Adapter
```

Dependencies từ adapters hướng vào contracts/core; core không cần biết SQL Server hay vendor SDK cụ thể.

## 4. Practical implementation

```csharp
public interface IPaymentGateway
{
    Task<PaymentResult> ChargeAsync(Money amount, CancellationToken ct);
}

public sealed class CheckoutService(IPaymentGateway gateway)
{
    public Task<PaymentResult> PayAsync(Money amount, CancellationToken ct)
        => gateway.ChargeAsync(amount, ct);
}
```

Interface có giá trị khi đại diện meaningful boundary, không phải vì mọi class cần interface.

## 5. Real production scenario

E-commerce chuyển payment provider. Domain/application flow giữ nguyên; adapter mới map provider contract, errors và idempotency semantics.

## 6. Failure scenario & troubleshooting

**Symptom** → architecture có 12 projects nhưng đổi vendor vẫn sửa khắp domain. **Evidence** → vendor DTO/types leak vào application contracts. **Hypothesis** → folder/project separation nhưng boundary không thật. **Diagnosis** → dependency graph và type leakage. **Fix** → define domain-owned port/translation adapter. **Verification** → replace adapter trong integration tests mà core không đổi.

## 7. Common mistakes

Interface cho mọi class; generic repository chỉ để “hexagonal”; core biết EF attributes/vendor DTO; mapping layers không có change-isolation value; architecture ceremony cho CRUD nhỏ.

## 8. Alternatives

Layered Architecture đơn giản hơn cho straightforward applications. Modular Monolith giải module ownership ở mức lớn hơn và có thể dùng hexagonal boundaries bên trong module quan trọng.

## 9. Trade-offs

### Advantages

Change isolation, testability và ownership rõ hơn ở volatile integrations.

### Costs / Risks

More contracts/mapping, cognitive overhead và nguy cơ over-abstraction.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu core logic không nên phụ thuộc trực tiếp mọi external detail.

### Middle
Implement adapter và integration tests.

### Senior
Nhận biết boundary nào đáng abstraction dựa trên volatility/business semantics.

### Technical Lead / Architect
Quyết định nơi ports/adapters giảm coupling và nơi direct dependency đơn giản hơn.

## 11. Key takeaway

- Architecture là dependency/change boundary, không phải folder layout.
- Port nên do core use case sở hữu semantics.
- Không abstraction khi không có pressure thực tế.

# 6. Azure Service Bus dead-letter queue: poison message là operational workflow

## 1. What is it?

Dead-letter queue (DLQ) giữ messages không thể tiếp tục xử lý bình thường. Nó không phải nơi “ném lỗi rồi quên”; nó là quarantine boundary cần telemetry, triage và replay policy.

## 2. Why does it exist?

Một poison message retry vô hạn có thể tốn compute, khóa throughput và tạo retry storm. Sau số delivery attempts hoặc explicit dead-letter, message cần rời active queue.

## 3. How does it work?

```text
Queue -> Consumer
          ↓ failure
       abandon/retry
          ↓ repeated
      MaxDeliveryCount
          ↓
         DLQ
          ↓
 triage / fix / replay / discard
```

DLQ giữ payload và dead-letter metadata để điều tra.

## 4. Practical implementation

Consumer nên phân biệt transient và permanent failures. Validation/schema violation thường không nên retry như timeout.

```csharp
if (!IsValid(message))
{
    await receiver.DeadLetterMessageAsync(
        message,
        "InvalidContract",
        "Required field customerId is missing",
        ct);
}
```

## 5. Real production scenario

Producer deploy schema mới nhưng một consumer cũ không hiểu enum mới. Messages vào DLQ thay vì retry hàng nghìn lần. Alert dựa trên DLQ count dẫn engineer tới compatibility regression.

## 6. Failure scenario & troubleshooting

**Symptom** → queue chính trông khỏe nhưng orders không hoàn thành. **Evidence** → DLQ count tăng. **Hypothesis** → permanent processing failure bị quarantine. **Diagnosis** → group dead-letter reasons, inspect representative payload/correlation. **Fix** → sửa consumer/contract rồi replay có kiểm soát. **Verification** → replay sample và theo dõi business outcome/idempotency.

## 7. Common mistakes

Không monitor DLQ; auto-replay liên tục; log sensitive payload; replay sau fix nhưng consumer không idempotent; chỉ tăng `MaxDeliveryCount` để “giải quyết” lỗi.

## 8. Alternatives

Quarantine database/storage có thể phù hợp khi cần richer workflow. Nhưng nếu Service Bus đã là transport, native DLQ thường là boundary đơn giản nhất.

## 9. Trade-offs

### Advantages

Bảo vệ active queue và giữ evidence để recovery.

### Costs / Risks

Cần ownership, alerting, retention và replay tooling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu retry không phải lúc nào cũng đúng.

### Middle
Phân loại transient/permanent và dead-letter metadata.

### Senior
Thiết kế triage/replay/idempotency và alerts.

### Technical Lead / Architect
Định nghĩa ownership/SLO cho poison messages và contract compatibility.

## 11. Key takeaway

- DLQ là production workflow, không phải trash folder.
- Permanent failure cần khác transient retry.
- Replay phải được thiết kế cùng idempotency.

# 7. Azure App Service deployment slots: swap an toàn cần hơn một nút bấm

## 1. What is it?

Deployment slots là live application environments trong cùng App Service cho phép deploy/warm một version trước khi swap routing/configuration sang production.

## 2. Why does it exist?

Deploy trực tiếp có thể đưa cold-start hoặc broken artifact vào production ngay. Slot tạo pre-production runtime gần production để health validation trước cutover.

## 3. How does it work?

```text
Production slot -> v1
Staging slot    -> deploy v2 -> warm/validate
                       ↓
                     swap
                       ↓
Production slot -> v2
Staging slot    -> v1
```

Một số settings có thể được đánh dấu slot-specific và không swap.

## 4. Practical implementation

Secrets/endpoints môi trường phải được phân loại rõ: setting nào đi cùng code, setting nào “sticky” với slot. Health/warm-up endpoint không nên chỉ trả 200 nếu dependencies/configuration thiết yếu chưa usable.

## 5. Real production scenario

v2 deploy staging, load assemblies và warm caches trước. Synthetic request xác minh critical endpoint; swap giảm cold-start impact so với direct deploy.

## 6. Failure scenario & troubleshooting

**Symptom** → staging pass nhưng production sau swap ghi dữ liệu vào sandbox dependency. **Evidence** → connection/API setting bị swap không đúng expectation. **Hypothesis** → slot setting classification sai. **Diagnosis** → compare slot configuration và deployment logs. **Fix** → mark environment-bound settings sticky, validate external endpoints trước swap. **Verification** → rehearsal với production-like slot.

## 7. Common mistakes

Cho rằng swap rollback luôn hoàn tác DB migration; staging gọi production side effects trong warm-up; health check quá nông; slot config drift; không tính background jobs chạy ở cả hai slots.

## 8. Alternatives

Blue-Green ở infrastructure level, containers/AKS rolling/canary, direct deployment cho low-risk internal apps.

## 9. Trade-offs

### Advantages

Warm-up, validation và application rollback nhanh.

### Costs / Risks

Configuration complexity, extra cost và external/database side effects không tự rollback.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu staging và production là runtime riêng.

### Middle
Deploy/swap và quản lý slot settings.

### Senior
Thiết kế health validation, job behavior và migration compatibility.

### Technical Lead / Architect
Chọn slot/blue-green/canary theo risk và đảm bảo rollback toàn hệ thống chứ không chỉ web binary.

## 11. Key takeaway

- Slot swap không phải transaction cho toàn architecture.
- Configuration và background side effects cần explicit design.
- Database compatibility vẫn là deployment constraint lớn.

# 8. SLO và error budget: reliability thành engineering decision

## 1. What is it?

SLI là measured reliability signal; SLO là target cho signal đó; error budget là phần unreliability được chấp nhận trong window.

Ví dụ: 99.9% successful requests trong 30 ngày cho phép khoảng 0.1% request failures theo định nghĩa SLI.

## 2. Why does it exist?

“Zero downtime” thường không thực tế và “hệ thống có vẻ ổn” không giúp quyết định nên release nhanh hay đầu tư reliability. SLO tạo shared quantitative target.

## 3. How does it work?

```text
User expectation
      ↓
SLI definition
      ↓
SLO target
      ↓
Allowed failure = error budget
      ↓
Release / reliability decisions
```

SLI phải đo user-visible outcome, không chỉ server CPU.

## 4. Practical implementation

Cho API checkout:

```text
SLI = successful eligible checkout requests / eligible checkout requests
SLO = 99.95% over rolling 30 days
```

Dashboard cần burn rate, không chỉ current availability. Fast burn báo outage lớn sớm; slow burn phát hiện degradation kéo dài.

## 5. Real production scenario

Team có feature deadline nhưng error budget tháng gần cạn do dependency incidents. Quyết định tạm giảm risky releases và xử lý timeout/fallback có căn cứ thay vì tranh luận cảm tính.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard báo 99.99% nhưng users vẫn phàn nàn. **Evidence** → SLI tính health endpoint/internal traffic, bỏ checkout failures. **Hypothesis** → metric không đại diện user journey. **Diagnosis** → audit eligibility/success definition. **Fix** → redefine SLI theo meaningful outcome. **Verification** → correlate SLI với incidents/support signals.

## 7. Common mistakes

SLO = SLA; chọn 100%; đo average latency thay tail; mọi endpoint chung một SLO; alert từng error thay burn rate; target không gắn product expectation.

## 8. Alternatives

Traditional threshold alerts vẫn cần cho resource symptoms nhưng không thay user-centered reliability target.

## 9. Trade-offs

### Advantages

Prioritization rõ, reliability measurable, alerting có context.

### Costs / Risks

SLI design sai tạo false confidence; telemetry/data pipeline cần đầu tư.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu uptime không phải metric duy nhất.

### Middle
Instrument success/latency metrics đúng.

### Senior
Thiết kế SLI, burn-rate alerts và incident correlation.

### Technical Lead / Architect
Dùng error budget cân release velocity, architecture investment và operational risk.

## 11. Key takeaway

- SLO phải phản ánh user-visible reliability.
- Error budget biến reliability thành trade-off định lượng.
- Metric sai còn nguy hiểm hơn không có metric.

# 9. SSRF trong backend integrations: URL do user kiểm soát có thể biến server thành network proxy

## 1. What is it?

Server-Side Request Forgery xảy ra khi attacker khiến backend gửi request tới destination mà attacker lựa chọn hoặc ảnh hưởng đáng kể. Backend có network identity/access mà browser attacker không có.

## 2. Why does it exist?

Các tính năng như “fetch image from URL”, webhook tester, PDF renderer hoặc URL preview cần server gọi URL bên ngoài. Nếu destination validation yếu, attacker có thể hướng request tới localhost, private network hoặc cloud metadata/internal services.

## 3. How does it work?

```text
Attacker input URL
      ↓
Backend HTTP client
      ↓
internal/private destination
      ↓
response/timing/side effect leaks capability
```

Redirects và DNS resolution làm validation phức tạp hơn string-prefix checks.

## 4. Practical implementation

Ưu tiên allowlist destinations khi business domain cho phép. Tách outbound network policy, chặn private/link-local ranges, giới hạn redirects, timeout, response size và protocols. Không dựa vào `StartsWith("https://trusted.com")`.

## 5. Real production scenario

CMS có “import image by URL”. Endpoint production chạy trong VNet và truy cập internal admin service. Attacker/editor account gửi crafted URL tới private endpoint và dùng CMS server làm proxy.

## 6. Failure scenario & troubleshooting

**Symptom** → outbound logs có requests tới RFC1918/link-local addresses từ image importer. **Evidence** → destination bắt nguồn từ user URL. **Hypothesis** → SSRF. **Diagnosis** → trace input, DNS/redirect chain và egress logs. **Fix** → strict destination policy + network egress controls. **Verification** → security tests với localhost/private IP/redirect/DNS cases.

## 7. Common mistakes

Chỉ validate scheme; block literal `127.0.0.1` nhưng bỏ hostname/DNS; validate trước redirect nhưng không validate destination sau redirect; cho unlimited download; HTTP client có credentials mặc định tới internal resources.

## 8. Alternatives

Nếu chỉ cần known providers, provider-specific API/adapters an toàn và observable hơn generic URL fetcher. Isolated fetch service giảm blast radius cho use case bắt buộc fetch arbitrary internet content.

## 9. Trade-offs

### Advantages

Generic URL fetching linh hoạt.

### Costs / Risks

Mở network attack surface khó kiểm soát; validation application nên kết hợp egress/network boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu server có network privileges khác client.

### Middle
Validate destination và set HTTP limits.

### Senior
Threat-model DNS, redirects, private ranges và cloud networking.

### Technical Lead / Architect
Quyết định có cần arbitrary fetch hay nên giới hạn providers/isolate component.

## 11. Key takeaway

- User-controlled URL là security-sensitive input.
- String validation đơn thuần không đủ cho SSRF.
- Network egress policy là defense-in-depth quan trọng.

# 10. React stale closure: async callback có thể đọc state cũ

## 1. What is it?

JavaScript closure giữ bindings từ render mà callback được tạo. Trong React function components, mỗi render có một snapshot state/props riêng. Async callback từ render cũ có thể tiếp tục chạy sau render mới.

## 2. Why does it exist?

React rendering dựa trên immutable render snapshots giúp reasoning predictable, nhưng async timers/network/event handlers có lifetime vượt qua render đã tạo chúng.

## 3. How does it work?

```text
Render A: query = "car"
 -> start request A
Render B: query = "cars"
 -> start request B
request B returns -> state = cars result
request A returns later -> stale callback overwrites state
```

Đây vừa là closure issue vừa là request race.

## 4. Practical implementation

Cancel obsolete requests:

```tsx
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${encodeURIComponent(query)}`, {
    signal: controller.signal
  })
    .then(r => r.json())
    .then(setResults)
    .catch(e => {
      if (e.name !== 'AbortError') throw e;
    });

  return () => controller.abort();
}, [query]);
```

Khi update dựa trên previous state, dùng functional update: `setCount(c => c + 1)`.

## 5. Real production scenario

Autocomplete: user gõ nhanh `c` → `ca` → `car`. Request `c` chậm nhất và về cuối, ghi đè kết quả `car`, khiến UI hiển thị dữ liệu không khớp input hiện tại.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng quay lại dữ liệu cũ. **Evidence** → network waterfall cho response cũ hoàn thành sau response mới. **Hypothesis** → stale async completion. **Diagnosis** → log request sequence/query snapshot. **Fix** → cancellation hoặc sequence/version guard. **Verification** → throttle network và nhập nhanh lặp lại.

## 7. Common mistakes

Thiếu dependency trong `useEffect`; dùng `setCount(count + 1)` trong delayed callbacks; ignore race vì local network quá nhanh; mutate shared state để “né closure”.

## 8. Alternatives

Data-fetching libraries có cancellation/cache/request identity semantics giúp giảm boilerplate. Nhưng engineer vẫn phải hiểu race để cấu hình đúng.

## 9. Trade-offs

### Advantages

Render snapshots giúp component logic predictable.

### Costs / Risks

Async work cần explicit lifecycle/cancellation; dependencies sai gây subtle bugs.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu mỗi render nhìn state snapshot riêng.

### Middle
Dùng dependencies, cleanup và functional updates đúng.

### Senior
Điều tra request races, cancellation và cache interactions.

### Technical Lead / Architect
Chuẩn hóa frontend data-fetching/lifecycle patterns để race handling không bị viết lại tùy tiện.

## 11. Key takeaway

- Async completion order không đảm bảo giống request order.
- Cleanup/cancellation là correctness, không chỉ performance.
- Stale closure bugs cần hiểu render snapshot, không chữa bằng arbitrary delay.
