# 1. C# `async`/`await` state machine: synchronous completion, continuation và vì sao sync-over-async có thể gây ThreadPool starvation

## 1. What is it?

`async`/`await` trong C# là cú pháp để compiler biến một method bất đồng bộ thành một **state machine**. Mental model quan trọng: `await` không có nghĩa là tạo thread mới. Nó cho phép method tạm dừng khi operation chưa hoàn thành, trả control cho caller, rồi tiếp tục khi awaitable hoàn tất.

Một method:

```csharp
public async Task<string> LoadAsync(CancellationToken ct)
{
    var data = await httpClient.GetStringAsync("/api/data", ct);
    return data.ToUpperInvariant();
}
```

được compiler chuyển thành logic gần với:

```text
State 0: gọi GetStringAsync
  -> nếu đã hoàn thành: tiếp tục ngay
  -> nếu chưa: đăng ký continuation và return

State 1: continuation được chạy
  -> lấy result
  -> transform
  -> complete Task
```

## 2. Why does it exist?

I/O như HTTP, database, file hoặc network thường dành phần lớn thời gian để **chờ** external system. Nếu một thread bị block toàn bộ thời gian đó, server phải giữ nhiều threads chỉ để chờ.

Asynchronous I/O cho phép thread quay về ThreadPool phục vụ work khác. Điều này đặc biệt quan trọng với ASP.NET Core, nơi throughput phụ thuộc vào việc không chiếm worker thread vô ích.

## 3. How does it work?

Khi awaitable chưa complete:

```text
Request thread
   |
   v
Start SQL query
   |
   +----> I/O pending
   |
   +----> thread returns to pool

Database responds
   |
   v
continuation scheduled
   |
   v
another pool thread resumes method
```

Nếu operation đã complete synchronously, state machine có thể tiếp tục ngay mà không cần schedule continuation. Đây là lý do hot-path APIs đôi khi quan tâm tới synchronous completion và allocation.

ASP.NET Core không sử dụng request `SynchronizationContext` theo kiểu ASP.NET cũ, nên continuation thường không cần quay lại đúng original thread. Nhưng blocking `.Result` / `.Wait()` vẫn nguy hiểm vì chiếm ThreadPool worker trong lúc awaited I/O cần worker để tiếp tục pipeline.

## 4. Practical implementation

Đúng:

```csharp
public async Task<OrderDto?> GetOrderAsync(
    Guid id,
    CancellationToken ct)
{
    return await db.Orders
        .Where(x => x.Id == id)
        .Select(x => new OrderDto(x.Id, x.Status))
        .SingleOrDefaultAsync(ct);
}
```

Không nên:

```csharp
public OrderDto? GetOrder(Guid id)
{
    return GetOrderAsync(id, CancellationToken.None).Result;
}
```

Nếu API boundary phải synchronous vì framework cũ, cần reasoning rõ về dedicated worker, queue hoặc migration boundary thay vì rải `.Result` khắp codebase.

## 5. Real production scenario

Một API gọi ba downstream HTTP services. Developer dùng `.Result` trong service layer vì muốn giữ interface synchronous.

Ở traffic thấp hệ thống chạy bình thường. Khi load tăng:

```text
requests tăng
-> nhiều ThreadPool threads block
-> continuation chờ thread rảnh
-> queue length tăng
-> p95/p99 tăng
-> timeout lan sang upstream
```

CPU có thể chưa 100%, nhưng server vẫn “kẹt” vì thread availability chứ không phải compute saturation.

## 6. Failure scenario & troubleshooting

**Symptom**
→ latency tăng mạnh khi concurrency tăng, CPU vừa phải.

**Evidence**
→ ThreadPool queue length tăng, worker threads tăng dần, trace có `.Result`, `.Wait()`, synchronous HTTP/DB calls.

**Hypothesis**
→ sync-over-async gây ThreadPool starvation.

**Diagnosis**
→ dùng `dotnet-counters`, runtime metrics, dump/trace để xem ThreadPool và blocked stacks.

**Fix**
→ propagate async “all the way”, loại blocking waits, giới hạn concurrency với downstream nếu cần.

**Verification**
→ load test lại; theo dõi ThreadPool queue, p95/p99 và dependency latency.

## 7. Common mistakes

- Nghĩ `async` tự động làm CPU-bound work chạy song song.
- Dùng `Task.Run` cho database/HTTP I/O trong ASP.NET Core.
- Gọi `.Result` vì “operation này chắc nhanh”.
- Quên propagate `CancellationToken`.
- Dùng `async void` ngoài event handler.
- Tối ưu `ValueTask` trước khi đo allocation thực tế.

## 8. Alternatives

- **Synchronous code:** vẫn hợp lý cho CPU/local operations rất ngắn.
- **Dedicated worker/queue:** phù hợp long-running hoặc workload cần durability.
- **Parallelism:** dùng cho CPU-bound hoặc independent work có giới hạn, không đồng nghĩa với async I/O.

## 9. Trade-offs

### Advantages

- Tăng scalability cho I/O-bound workloads.
- Giảm số thread bị block vô ích.
- Cancellation/timeout composable tốt hơn.

### Costs / Risks

- Stack trace/debugging phức tạp hơn synchronous flow.
- Unbounded fan-out vẫn có thể overload downstream.
- Async không cứu được slow database hoặc bad architecture.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` là suspension chứ không phải tạo thread mới.

### Middle

Viết async end-to-end, propagate cancellation và tránh `.Result` / `.Wait()`.

### Senior

Phân biệt ThreadPool starvation, CPU saturation và downstream latency bằng telemetry.

### Technical Lead / Architect

Quyết định concurrency budget, synchronous/asynchronous boundaries và nơi cần queue thay vì chỉ thêm `async` vào signatures.

## 11. Key takeaway

- `async`/`await` chủ yếu giải phóng thread trong thời gian chờ I/O.
- Sync-over-async có thể biến thành production scalability failure.
- Điều tra bằng ThreadPool + latency evidence, không chỉ CPU.

# 2. ASP.NET Core middleware ordering: routing, authentication, authorization và exception handling phụ thuộc thứ tự pipeline như thế nào

## 1. What is it?

ASP.NET Core middleware pipeline là chuỗi components xử lý request theo thứ tự đăng ký. Mỗi middleware có thể xử lý request trước khi gọi `next`, rồi xử lý response khi control quay ngược lại.

Mental model:

```text
Request
  -> Exception Handling
  -> Routing
  -> Authentication
  -> Authorization
  -> Endpoint
Response
  <-
```

Thứ tự là semantics, không phải style.

## 2. Why does it exist?

Cross-cutting concerns như error handling, security, logging, routing, compression hay CORS cần chạy quanh endpoint logic. Pipeline cho phép compose các concerns này mà không nhúng chúng vào từng controller.

Nhưng middleware phía sau chỉ nhận được context mà middleware phía trước đã chuẩn bị. Authorization không thể authorize endpoint metadata nếu routing chưa xác định endpoint phù hợp.

## 3. How does it work?

Middleware dạng:

```csharp
app.Use(async (context, next) =>
{
    // before next
    await next(context);
    // after next
});
```

Call stack hình thành như nested functions:

```text
M1 before
  M2 before
    M3 before
      endpoint
    M3 after
  M2 after
M1 after
```

Exception middleware phải nằm đủ sớm để catch exception phát sinh phía sau. Authentication phải populate `HttpContext.User` trước authorization.

## 4. Practical implementation

Một pipeline điển hình:

```csharp
var app = builder.Build();

app.UseExceptionHandler();
app.UseHttpsRedirection();

app.UseRouting();

app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();

app.Run();
```

Với CORS, rate limiting hoặc response compression, vị trí phụ thuộc behavior mong muốn. Không copy thứ tự từ blog mà không hiểu component cần context gì và cần wrap component nào.

## 5. Real production scenario

API có `[Authorize]`, nhưng một refactor đặt middleware custom đọc `User.Claims` trước `UseAuthentication`. Local test endpoint public vẫn pass, còn production audit logging ghi user là anonymous cho request authenticated.

Một case khác: exception handler đặt sau endpoint mapping nên exception ở authentication middleware không được chuẩn hóa thành `ProblemDetails` như mong đợi.

## 6. Failure scenario & troubleshooting

**Symptom**
→ endpoint authenticated nhưng custom middleware thấy user anonymous; hoặc lỗi trả HTML/default body thay vì expected error contract.

**Evidence**
→ pipeline order trong `Program.cs`, logs từng middleware, endpoint metadata.

**Hypothesis**
→ middleware chạy trước prerequisite hoặc exception wrapper không bao quanh failure source.

**Diagnosis**
→ trace request lifecycle và kiểm tra `HttpContext.GetEndpoint()`, `User.Identity.IsAuthenticated` tại từng stage.

**Fix**
→ reorder pipeline theo dependency semantics.

**Verification**
→ integration tests cho 401, 403, exception, CORS và endpoint metadata.

## 7. Common mistakes

- Nghĩ `MapControllers()` chỉ là “route config” không ảnh hưởng pipeline terminal behavior.
- Đặt authorization trước authentication.
- Custom middleware gọi `next()` hai lần hoặc quên gọi khi cần.
- Viết response rồi vẫn gọi downstream middleware.
- Catch exception rồi trả 200.
- Dùng middleware cho concern thực sự thuộc endpoint filter/domain layer.

## 8. Alternatives

- **Endpoint filters:** phù hợp logic gần Minimal API endpoints.
- **MVC filters:** phù hợp concern gắn với MVC action lifecycle.
- **Middleware:** phù hợp concern cần bao phủ toàn pipeline/protocol-level behavior.

## 9. Trade-offs

### Advantages

- Centralize cross-cutting concerns.
- Composition rõ nếu pipeline nhỏ và có thứ tự được test.

### Costs / Risks

- Order coupling dễ tạo bug “code đúng nhưng đứng sai chỗ”.
- Middleware quá nhiều làm request flow khó reasoning.
- Global component có blast radius lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu middleware chạy theo chain và response quay ngược chain.

### Middle

Biết placement của routing/auth/error handling và viết integration tests.

### Senior

Phân biệt concern nào thuộc middleware, filter hay application layer; debug pipeline bằng evidence.

### Technical Lead / Architect

Giữ cross-cutting architecture đơn giản, đặt conventions và regression tests cho security/error behavior toàn hệ thống.

## 11. Key takeaway

- Middleware order là runtime behavior.
- Authentication, authorization, routing và exception handling có dependency rõ ràng.
- Test pipeline bằng integration tests, không chỉ đọc `Program.cs`.

# 3. EF Core optimistic concurrency với `rowversion`: phát hiện lost update mà không khóa row suốt thời gian người dùng chỉnh sửa

## 1. What is it?

Optimistic concurrency giả định conflict hiếm, nên không giữ database lock trong suốt business interaction. Thay vào đó, khi update, application kiểm tra record có thay đổi kể từ lúc đọc hay không.

SQL Server `rowversion` là một concurrency token tự thay đổi khi row được update.

Mental model:

```text
User A reads row version 10
User B reads row version 10
User A updates -> version 11
User B updates WHERE version = 10 -> 0 rows affected
```

EF Core diễn giải “0 rows affected khi expected row/version phải tồn tại” thành `DbUpdateConcurrencyException`.

## 2. Why does it exist?

Web request thường stateless và user có thể mở form nhiều phút. Giữ transaction/lock từ lúc GET tới lúc user bấm Save là không thực tế.

Không có concurrency check, request đến sau có thể silently overwrite thay đổi trước — **lost update**.

## 3. How does it work?

Entity:

```csharp
public sealed class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }

    [Timestamp]
    public byte[] Version { get; set; } = [];
}
```

EF Core tạo update gần như:

```sql
UPDATE Products
SET Price = @price
WHERE Id = @id
  AND Version = @originalVersion;
```

Nếu database row đã có version khác, affected rows = 0.

## 4. Practical implementation

API nên mang version qua contract, ví dụ Base64 hoặc ETag:

```csharp
try
{
    product.Price = request.Price;
    db.Entry(product).Property(x => x.Version)
        .OriginalValue = Convert.FromBase64String(request.Version);

    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new
    {
        code = "product_changed",
        message = "Product was modified by another user. Reload and retry."
    });
}
```

Không tự động retry blind mutation nếu business semantics cần user quyết định merge.

## 5. Real production scenario

Hai merchandisers chỉnh cùng product. Người A đổi price, người B đổi description dựa trên snapshot cũ. Nếu API nhận toàn object và overwrite tất cả columns, B có thể vô tình đưa price cũ trở lại.

Concurrency token phát hiện snapshot stale và cho phép UI reload/merge.

## 6. Failure scenario & troubleshooting

**Symptom**
→ dữ liệu “tự quay lại giá trị cũ” hoặc users ghi đè nhau.

**Evidence**
→ update contracts không có version; audit trail cho thấy writes gần nhau.

**Hypothesis**
→ lost update.

**Diagnosis**
→ reproduce hai concurrent edit sessions; inspect generated SQL.

**Fix**
→ concurrency token + conflict handling + narrow update semantics.

**Verification**
→ integration test hai contexts đọc cùng version rồi update cạnh tranh; request thứ hai phải conflict.

## 7. Common mistakes

- Catch `DbUpdateConcurrencyException` rồi retry vô hạn.
- Gửi `rowversion` nhưng không set original value đúng.
- Dùng timestamp thời gian ứng dụng thay concurrency token mà precision/clock semantics không phù hợp.
- Trả generic 500 thay vì conflict contract.
- Dùng pessimistic lock cho form người dùng dài nhiều phút.

## 8. Alternatives

- **Application-managed version number/GUID:** portable và kiểm soát khi nào version đổi.
- **HTTP ETag / `If-Match`:** tốt để biểu diễn optimistic concurrency ở REST boundary.
- **Pessimistic locking:** phù hợp short transaction nơi conflict rất đắt và lock duration bounded.

## 9. Trade-offs

### Advantages

- Không giữ lock lâu.
- Phát hiện overwrite race rõ ràng.
- Scale tốt khi conflict hiếm.

### Costs / Risks

- Application phải xử lý conflict UX/business logic.
- Retry/merge có thể phức tạp.
- Token bảo vệ row-level snapshot, không tự bảo vệ multi-row business invariant.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu lost update và concurrency token.

### Middle

Implement `rowversion`, conflict response và tests.

### Senior

Phân biệt row concurrency với transaction invariant; chọn retry hay user merge theo semantics.

### Technical Lead / Architect

Xác định aggregate/invariant boundaries và concurrency contract giữa UI/API/database.

## 11. Key takeaway

- Optimistic concurrency phát hiện stale writes mà không giữ lock lâu.
- `DbUpdateConcurrencyException` là business concurrency signal, không chỉ technical exception.
- Không phải conflict nào cũng nên auto-retry.

# 4. PostgreSQL transaction isolation: `Read Committed`, `Repeatable Read`, `Serializable` và cách reasoning về anomaly thay vì chỉ chọn mức cao nhất

## 1. What is it?

Transaction isolation định nghĩa transaction được phép quan sát thay đổi đồng thời như thế nào. PostgreSQL dùng MVCC để readers thường không block writers theo cách lock-based đơn giản.

Ba mức quan trọng:

- `Read Committed`: mỗi statement thấy snapshot mới tại đầu statement.
- `Repeatable Read`: transaction dùng snapshot ổn định hơn trong suốt transaction.
- `Serializable`: PostgreSQL phát hiện các execution có thể tạo kết quả không tương đương serial execution và abort một transaction khi cần.

## 2. Why does it exist?

Concurrency tăng throughput nhưng tạo anomaly. Ví dụ hai doctors cùng thấy “vẫn còn một doctor on-call” rồi cả hai cùng off-call. Mỗi row update riêng lẻ hợp lệ, nhưng invariant toàn hệ thống bị phá.

Isolation level là công cụ kiểm soát loại anomaly nào được chấp nhận.

## 3. How does it work?

`Read Committed`:

```text
T1 SELECT balance -> 100
T2 UPDATE balance -> 50 COMMIT
T1 SELECT balance -> 50
```

Hai SELECT trong cùng transaction có thể thấy kết quả khác.

`Repeatable Read` giữ snapshot cũ, nhưng business anomaly liên quan nhiều rows vẫn cần reasoning.

`Serializable` có thể abort với serialization failure để application retry toàn transaction.

## 4. Practical implementation

Npgsql/EF Core:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(
    System.Data.IsolationLevel.Serializable,
    ct);

var seatsLeft = await db.Seats
    .CountAsync(x => x.EventId == eventId && !x.Reserved, ct);

if (seatsLeft <= 0)
    throw new InvalidOperationException("Sold out");

// reserve...
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Serializable transaction cần bounded retry cho serialization failures. Không retry side effect ngoài DB nằm trong transaction một cách mù quáng.

## 5. Real production scenario

Hai requests approve expense đồng thời. Rule: tổng approved budget không vượt 100 triệu. Mỗi request đọc current total 90 triệu rồi approve thêm 8 triệu. Nếu cả hai cùng commit, total = 106 triệu.

Đây không chỉ là row conflict; invariant dựa trên tập rows. Có thể giải bằng locking, materialized aggregate row, serializable isolation hoặc thiết kế command serialization.

## 6. Failure scenario & troubleshooting

**Symptom**
→ invariant thỉnh thoảng bị phá dù mỗi transaction riêng lẻ “check trước khi update”.

**Evidence**
→ concurrent traces cho thấy cả hai read cùng state rồi commit.

**Hypothesis**
→ write skew / check-then-act race.

**Diagnosis**
→ reproduce concurrency, xác định predicate/invariant và current isolation.

**Fix**
→ chọn isolation/locking/data model phù hợp.

**Verification**
→ stress test concurrent transactions và assert invariant sau mỗi run.

## 7. Common mistakes

- Chọn `Serializable` cho toàn hệ thống vì “an toàn nhất”.
- Nghĩ transaction tự động làm mọi business flow thread-safe.
- Retry serialization failure nhưng operation đã gửi email/payment bên ngoài.
- Giữ transaction mở trong lúc gọi remote API.
- Không quan sát abort/retry rate sau khi tăng isolation.

## 8. Alternatives

- **Explicit row locks:** tốt khi resource set rõ và nhỏ.
- **Optimistic versioning:** phù hợp conflict trên known records.
- **Single aggregate row/counter:** đôi khi đơn giản hóa invariant.
- **Queue theo business key:** serialize commands nhưng tăng latency/operations.

## 9. Trade-offs

### Advantages

- Isolation mạnh hơn giảm anomaly khó thấy.
- MVCC giữ read concurrency tốt trong nhiều workload.

### Costs / Risks

- Serializable có thể tăng abort/retry dưới contention.
- Long transactions giữ old versions lâu và tăng vacuum pressure.
- Isolation mạnh không thay thế data modeling tốt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction không đồng nghĩa “không ai khác thay đổi dữ liệu”.

### Middle

Biết chọn isolation theo operation và xử lý retry bounded.

### Senior

Reasoning bằng anomaly/invariant thay vì thuộc tên isolation levels.

### Technical Lead / Architect

Thiết kế data ownership và transaction boundary sao cho correctness đạt được với complexity tối thiểu.

## 11. Key takeaway

- Chọn isolation theo anomaly cần ngăn, không theo khẩu hiệu “cao hơn tốt hơn”.
- Serializable có thể abort; application phải sẵn sàng retry an toàn.
- Business invariant nhiều rows cần explicit concurrency design.

# 5. Elasticsearch analyzers và mapping evolution: `text` vs `keyword`, tokenization và vì sao đổi mapping thường cần reindex

## 1. What is it?

Elasticsearch mapping định nghĩa cách field được index. Hai kiểu thường bị nhầm:

- `text`: được analyzer tokenize/normalize để full-text search.
- `keyword`: giữ giá trị gần như nguyên khối cho exact match, sort, aggregation.

Ví dụ `"Ford Mustang GT"` với `text` analyzer có thể thành tokens:

```text
ford
mustang
gt
```

Trong khi `keyword` giữ `Ford Mustang GT` như một term.

## 2. Why does it exist?

Search engine không chỉ lưu string; nó xây inverted index. Cách tokenize quyết định query nào match.

Nếu field dùng sai mapping, hệ thống có thể:

- search tên sản phẩm không ra;
- aggregation tạo bucket kỳ lạ;
- sort fail hoặc tiêu tốn memory;
- exact filter match không như mong đợi.

## 3. How does it work?

Pipeline:

```text
Document field
   -> analyzer
   -> tokenizer
   -> token filters
   -> terms
   -> inverted index
```

Query full-text cũng được analyze theo search analyzer trước khi lookup terms.

Một field thường dùng multi-field:

```json
"name": {
  "type": "text",
  "fields": {
    "keyword": { "type": "keyword" }
  }
}
```

`name` cho full-text, `name.keyword` cho exact sort/aggregation.

## 4. Practical implementation

Mapping:

```json
PUT products-v2
{
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "fields": {
          "raw": { "type": "keyword", "ignore_above": 256 }
        }
      },
      "sku": { "type": "keyword" }
    }
  }
}
```

Nếu cần đổi analyzer của field đã index, thường tạo index mới, reindex dữ liệu rồi swap alias.

## 5. Real production scenario

Search sản phẩm cần autocomplete, full-text và filter exact theo brand. Team ban đầu index mọi field là `text`. Sau đó aggregation brand cho kết quả sai/khó dùng và SKU search tokenized không phù hợp.

Giải pháp không phải thêm query hacks mãi; mapping phải phản ánh search semantics.

## 6. Failure scenario & troubleshooting

**Symptom**
→ query “ABC-123” không match đúng SKU hoặc aggregation brand lỗi.

**Evidence**
→ inspect mapping và `_analyze` output; thấy tokenizer chia term ngoài mong đợi.

**Hypothesis**
→ analyzer/mapping không phù hợp access pattern.

**Diagnosis**
→ dùng `_analyze`, sample documents và query explain/profile khi cần.

**Fix**
→ thiết kế mapping mới, reindex, alias swap.

**Verification**
→ relevance regression tests và representative search cases trước/ sau cutover.

## 7. Common mistakes

- Dùng `text` cho IDs/SKU/email cần exact match.
- Dùng `keyword` cho nội dung full-text dài.
- Bật dynamic mapping rồi để schema tăng không kiểm soát.
- Đổi analyzer nhưng quên dữ liệu cũ đã index bằng analyzer trước.
- Dùng Elasticsearch làm transactional source of truth.

## 8. Alternatives

- **SQL full-text search:** đủ cho một số hệ thống đơn giản hơn.
- **PostgreSQL `tsvector`:** phù hợp khi search requirement vừa phải và muốn giảm component.
- **Dedicated Elasticsearch/OpenSearch:** đáng giá khi relevance, scale, aggregations và search features thực sự cần.

## 9. Trade-offs

### Advantages

- Analyzer tùy biến cho relevance/search UX tốt.
- Multi-fields hỗ trợ nhiều access patterns trên cùng logical field.

### Costs / Risks

- Mapping evolution có reindex cost.
- Search cluster là operational component riêng.
- Analyzer phức tạp khó debug nếu không có relevance tests.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `text` là analyzed còn `keyword` là exact-term oriented.

### Middle

Thiết kế mapping cơ bản, dùng `_analyze`, filters và aggregations đúng field.

### Senior

Quản lý schema evolution, reindex, aliases và relevance regression.

### Technical Lead / Architect

Quyết định khi nào Elasticsearch đáng giá so với search trong relational database và ai sở hữu consistency pipeline.

## 11. Key takeaway

- Mapping quyết định search behavior từ lúc index, không chỉ lúc query.
- `text` và `keyword` phục vụ semantics khác nhau.
- Analyzer change thường là data migration/reindex problem.

# 6. Saga Pattern: orchestration, choreography và compensating transaction khi một business transaction đi qua nhiều services

## 1. What is it?

Saga là cách quản lý một business workflow gồm nhiều local transactions ở các services khác nhau mà không dùng một distributed ACID transaction xuyên toàn hệ thống.

Ví dụ đặt hàng:

```text
Order created
 -> Reserve inventory
 -> Authorize payment
 -> Create shipment
```

Nếu bước sau fail, Saga kích hoạt **compensating actions** cho các bước đã hoàn thành khi business cho phép.

## 2. Why does it exist?

Microservices thường sở hữu database riêng. Một transaction SQL không thể đơn giản wrap database của Order, Inventory và Payment qua network mà vẫn giữ availability/operability tốt.

Saga chấp nhận eventual consistency và explicit failure handling.

## 3. How does it work?

Hai style chính:

### Orchestration

```text
Saga Orchestrator
 -> Inventory: Reserve
 <- Success
 -> Payment: Authorize
 <- Failure
 -> Inventory: Release
```

Một coordinator giữ workflow state.

### Choreography

```text
OrderCreated event
 -> Inventory service publishes InventoryReserved
 -> Payment service publishes PaymentFailed
 -> Inventory reacts and releases
```

Không có central coordinator nhưng dependencies giữa events có thể khó nhìn khi flow lớn.

## 4. Practical implementation

Pseudo-near-production state model:

```csharp
public sealed class CheckoutSaga
{
    public Guid OrderId { get; init; }
    public SagaState State { get; private set; }

    public void InventoryReserved() => State = SagaState.InventoryReserved;
    public void PaymentAuthorized() => State = SagaState.Completed;
    public void PaymentFailed() => State = SagaState.CompensationRequired;
}
```

Message handlers cần idempotent. Saga state và outgoing message thường kết hợp Outbox Pattern để tránh “state committed nhưng message không publish”.

## 5. Real production scenario

Inventory reservation thành công, payment authorization timeout. Không biết payment thực sự fail hay provider đã charge nhưng response bị mất.

Compensation không đơn giản là “undo”. Hệ thống cần query payment status/idempotency key trước khi release inventory hoặc retry charge.

## 6. Failure scenario & troubleshooting

**Symptom**
→ order stuck ở `PaymentPending` hàng giờ.

**Evidence**
→ saga state, message history, payment provider correlation ID, retry count.

**Hypothesis**
→ message thất lạc, consumer fail hoặc ambiguous remote outcome.

**Diagnosis**
→ reconstruct timeline từ durable state + traces/messages.

**Fix**
→ reconcile remote status, perform safe retry/compensation, repair workflow state.

**Verification**
→ chaos/integration tests cho timeout tại từng transition.

## 7. Common mistakes

- Gọi compensation là rollback ACID.
- Không persist saga state.
- Không thiết kế idempotency cho commands/events.
- Choreography với hàng chục implicit event dependencies.
- Cho compensation tự động khi business action không thực sự reversible.
- Không có timeout/reconciliation path cho “unknown outcome”.

## 8. Alternatives

- **Single database transaction:** đơn giản hơn nếu boundaries chưa cần tách services.
- **Modular Monolith:** thường giảm nhu cầu Saga đáng kể.
- **Distributed transaction/2PC:** hiếm khi phù hợp cloud services vì availability/operational constraints.

## 9. Trade-offs

### Advantages

- Cho phép workflow cross-service mà mỗi service giữ local transaction ownership.
- Failure handling explicit.

### Costs / Risks

- Eventual consistency và state machine complexity.
- Compensation có thể không hoàn hảo.
- Debugging cần observability xuyên services.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Saga là chuỗi local transactions + failure handling, không phải một DB transaction lớn.

### Middle

Implement idempotent handlers và persisted workflow state.

### Senior

Thiết kế compensation, timeout, replay và unknown-outcome handling.

### Technical Lead / Architect

Hỏi trước: hệ thống có thực sự cần distributed service boundary không, hay một local transaction trong Modular Monolith đơn giản hơn?

## 11. Key takeaway

- Saga đổi atomic consistency lấy explicit workflow + compensation.
- Compensation là business operation, không phải mechanical rollback.
- Nếu Saga quá phức tạp, hãy xem lại service boundaries trước.

# 7. Azure Functions scale-out và idempotency: một event có thể chạy nhiều lần dù function code chỉ được viết một lần

## 1. What is it?

Azure Functions là serverless compute model nơi platform có thể tạo nhiều instances để xử lý events song song. Với trigger như queue/service bus/event source, delivery thường có semantics gần **at-least-once**, nghĩa là cùng logical event có thể được xử lý lại.

Idempotency nghĩa là xử lý cùng command/event nhiều lần nhưng business effect cuối cùng không bị nhân đôi ngoài ý muốn.

## 2. Why does it exist?

Distributed execution có failure windows:

```text
Function updates DB successfully
-> process crashes before trigger checkpoint/settlement
-> message delivered again
```

Platform không thể biết external side effect đã hoàn tất chỉ từ việc worker biến mất. Redelivery bảo vệ reliability, nhưng application phải xử lý duplicate.

## 3. How does it work?

Scale-out:

```text
Queue backlog grows
   -> Function instance A
   -> Function instance B
   -> Function instance C
```

Nhiều workers cạnh tranh messages. Retry/lock expiry/restart có thể làm duplicate delivery.

Idempotency thường dùng business key/message ID + durable record:

```text
if messageId already processed:
    no-op
else:
    execute effect + persist processed marker atomically when possible
```

## 4. Practical implementation

Ví dụ SQL uniqueness bảo vệ invoice creation:

```csharp
public async Task HandleAsync(CreateInvoiceMessage message, CancellationToken ct)
{
    var exists = await db.ProcessedMessages
        .AnyAsync(x => x.MessageId == message.MessageId, ct);

    if (exists)
        return;

    db.Invoices.Add(new Invoice
    {
        OrderId = message.OrderId,
        Amount = message.Amount
    });

    db.ProcessedMessages.Add(new ProcessedMessage
    {
        MessageId = message.MessageId
    });

    await db.SaveChangesAsync(ct);
}
```

Tốt hơn nữa, đặt unique constraint trên `MessageId`/business key để race giữa multiple instances vẫn được database enforce.

## 5. Real production scenario

Function gửi email receipt và cập nhật DB. DB update thành công nhưng host restart trước khi message complete. Message chạy lại và customer nhận hai email.

Nếu email provider hỗ trợ idempotency key, dùng key theo order/message. Nếu không, cần persistent send-state/outbox để giảm duplicate side effect.

## 6. Failure scenario & troubleshooting

**Symptom**
→ duplicate invoice/email sau scale event hoặc transient outage.

**Evidence**
→ cùng message ID có multiple invocation IDs; delivery count > 1.

**Hypothesis**
→ handler không idempotent.

**Diagnosis**
→ trace trigger delivery, DB commits và external calls.

**Fix**
→ unique business key, Inbox/dedup store, provider idempotency key hoặc workflow redesign.

**Verification**
→ intentionally redeliver same message concurrently và assert một business effect.

## 7. Common mistakes

- Tin rằng queue/function chỉ chạy một lần.
- Check “exists” mà không có unique constraint nên race vẫn tạo duplicate.
- Dùng in-memory dedup trong multi-instance environment.
- Retry non-idempotent payment/email call vô điều kiện.
- Thiết kế timer function như singleton mà không hiểu scale/host behavior.

## 8. Alternatives

- **Worker Service + queue:** nhiều control hơn, nhưng vẫn cần idempotency.
- **Container Apps jobs:** phù hợp một số scheduled/batch workloads.
- **App Service BackgroundService:** đơn giản hơn cho low-scale work nhưng durability/scaling khác.

## 9. Trade-offs

### Advantages

- Scale theo workload, giảm server management.
- Trigger integration thuận tiện.

### Costs / Risks

- Execution ownership/platform behavior ít trực quan hơn dedicated process.
- Cold start, concurrency và retries cần hiểu kỹ.
- Exactly-once business effect phải do application/data layer thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu serverless không đồng nghĩa single-instance hay exactly-once.

### Middle

Viết idempotent handler, unique constraints và retry-safe operations.

### Senior

Reasoning về failure window giữa external effect, DB commit và message settlement.

### Technical Lead / Architect

Chọn Functions khi execution model phù hợp, đặt concurrency/idempotency/observability policy và đánh giá cost ở sustained load.

## 11. Key takeaway

- Scale-out và retry biến duplicate execution thành normal condition.
- Idempotency cần durable enforcement, không chỉ `if` trong memory.
- Exactly-once business effect là design problem, không phải checkbox của platform.

# 8. Akamai / CDN cache-control: browser cache, edge cache, `s-maxage`, purge và nguyên nhân nội dung cũ vẫn xuất hiện sau deploy

## 1. What is it?

CDN như Akamai đặt edge servers gần users để cache content và giảm latency/origin load.

Có ít nhất hai cache layers cần phân biệt:

```text
Browser cache
    |
    v
Akamai edge cache
    |
    v
Origin / reverse proxy / app
```

`Cache-Control` quyết định ai được cache và trong bao lâu.

## 2. Why does it exist?

Static assets, product images, JS/CSS và một số public API/content có thể được phục vụ từ edge thay vì request về origin mỗi lần.

Điều này giảm:

- network latency;
- origin CPU/bandwidth;
- dependency pressure;
- blast radius khi traffic spike.

Nhưng caching tạo vấn đề freshness và invalidation.

## 3. How does it work?

Ví dụ:

```http
Cache-Control: public, max-age=60, s-maxage=600
```

- Browser có thể cache 60 giây.
- Shared cache/CDN có thể cache 600 giây.

Nếu edge có fresh object, origin không thấy request. Purge có thể invalidate edge object, nhưng browser đã cache object vẫn có thể tiếp tục dùng local copy.

Versioned assets giải quyết nhiều vấn đề:

```text
/app.abc123.js
/app.def456.js
```

URL mới tạo cache key mới, không cần ép mọi browser purge.

## 4. Practical implementation

ASP.NET Core cho immutable fingerprinted assets có thể trả:

```http
Cache-Control: public, max-age=31536000, immutable
```

HTML shell nên ngắn hơn nếu nó tham chiếu asset version mới:

```http
Cache-Control: public, max-age=60, s-maxage=300
```

Không dùng long-lived cache cho user-specific response nếu cache key/vary rules không bảo vệ đúng identity/tenant.

## 5. Real production scenario

Team deploy JS bundle mới nhưng giữ filename `app.js`, TTL edge 1 giờ và browser 1 ngày. Purge Akamai xong, một số users vẫn chạy bundle cũ từ browser cache và gọi API contract không còn tương thích.

Root cause là asset versioning/backward compatibility, không chỉ “Akamai purge chậm”.

## 6. Failure scenario & troubleshooting

**Symptom**
→ một số regions/users thấy nội dung cũ, origin đã deploy bản mới.

**Evidence**
→ response headers `Age`, `Cache-Control`, `ETag`, CDN cache status; DevTools cho thấy request served from memory/disk cache.

**Hypothesis**
→ stale ở browser hoặc edge layer.

**Diagnosis**
→ kiểm tra từng layer; request bypass cache có control; so cache key/query/header variation.

**Fix**
→ correct TTL, purge khi cần, fingerprint assets, giữ API backward compatible.

**Verification**
→ test cold/warm browser và multiple edge locations; inspect headers.

## 7. Common mistakes

- Nghĩ CDN purge cũng xóa browser cache.
- Cache HTML/user-specific content quá lâu.
- Dùng query string tùy tiện nhưng cache key không include đúng parameter.
- Deploy frontend/API breaking change cùng lúc không compatibility window.
- `no-cache` và `no-store` bị hiểu như nhau.

## 8. Alternatives

- **Browser cache only:** đơn giản, không giảm origin traffic toàn cầu bằng edge.
- **Reverse proxy cache:** gần origin hơn, ít global benefit.
- **No cache:** đúng cho highly dynamic/sensitive responses nếu freshness/correctness quan trọng hơn latency.

## 9. Trade-offs

### Advantages

- Latency thấp và origin protection tốt.
- Static asset delivery hiệu quả.

### Costs / Risks

- Invalidation/freshness phức tạp.
- Sai cache key có thể thành data leak.
- CDN configuration trở thành production-critical infrastructure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser cache và CDN edge là hai layers khác nhau.

### Middle

Đọc cache headers, dùng fingerprinted assets và debug DevTools/CDN headers.

### Senior

Thiết kế cache key, TTL, invalidation và API compatibility trong deployment.

### Technical Lead / Architect

Quyết định content nào đáng edge-cache, ownership của purge/config và security review cho personalized content.

## 11. Key takeaway

- Stale content phải được định vị theo layer: browser, edge hay origin.
- Versioned asset URLs tốt hơn phụ thuộc vào purge cho mọi deploy.
- Cache policy là correctness + security decision, không chỉ performance.

# 9. Kubernetes readiness, liveness và startup probes: phân biệt “process sống”, “đã sẵn sàng nhận traffic” và “cần restart”

## 1. What is it?

Kubernetes probes trả lời ba câu hỏi khác nhau:

- **Readiness:** Pod có sẵn sàng nhận traffic không?
- **Liveness:** process có đang ở trạng thái cần restart không?
- **Startup:** application đã hoàn tất startup chưa, trước khi áp liveness bình thường?

Gộp cả ba thành `/health` duy nhất mà semantics không rõ dễ tạo cascade failure.

## 2. Why does it exist?

Một process có thể:

- đang chạy nhưng chưa warm-up;
- sống nhưng dependency tạm thời lỗi;
- deadlock/hung và cần restart;
- đang shutdown và không nên nhận request mới.

Kubernetes cần signal khác nhau để routing và restart đúng hành động.

## 3. How does it work?

```text
Readiness fails
 -> Pod stays running
 -> removed from Service endpoints

Liveness fails repeatedly
 -> kubelet restarts container

Startup probe active
 -> liveness/readiness behavior waits for slow startup window
```

Đây là operational control loop. Probe sai có thể tự gây outage.

## 4. Practical implementation

ASP.NET Core Health Checks:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<StartupHealthCheck>("startup", tags: ["ready"])
    .AddSqlServer(connectionString, tags: ["ready"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready")
});
```

Liveness thường không nên phụ thuộc tất cả remote dependencies. Nếu database down và mọi pods fail liveness, cluster restart loop không sửa được database nhưng làm outage tệ hơn.

## 5. Real production scenario

Database latency spike 30 giây. Liveness endpoint kiểm tra DB và fail trên tất cả pods. Kubernetes restart toàn bộ deployment. Startup cùng lúc tạo connection storm, làm database càng quá tải.

Nếu DB issue chỉ nên ảnh hưởng readiness, pods có thể tạm rời traffic mà không churn process liên tục.

## 6. Failure scenario & troubleshooting

**Symptom**
→ `CrashLoopBackOff` trong khi application logs chỉ có dependency timeout.

**Evidence**
→ events cho thấy liveness failures trước restart; DB incident trùng thời điểm.

**Hypothesis**
→ liveness phụ thuộc external dependency.

**Diagnosis**
→ inspect probe config, endpoint dependencies, restart count và Kubernetes events.

**Fix**
→ tách liveness/readiness/startup semantics; tune timeout/failure thresholds.

**Verification**
→ simulate dependency outage và confirm pods không restart vô ích.

## 7. Common mistakes

- Liveness gọi database, Redis, Elasticsearch, third-party API cùng lúc.
- Readiness luôn trả 200 dù app chưa initialize.
- Probe interval quá gắt khiến transient latency thành restart storm.
- Endpoint health check thực hiện query nặng.
- Không có startup probe cho app cold start dài.

## 8. Alternatives

- **App Service Health Check:** cùng mục tiêu routing instance nhưng platform semantics khác.
- **External synthetic monitoring:** kiểm tra end-to-end user path; không thay liveness probe.
- **Load balancer health check:** thường đơn giản hơn Kubernetes multi-probe model.

## 9. Trade-offs

### Advantages

- Tách traffic management khỏi process restart.
- Hỗ trợ rolling deployment và self-healing tốt.

### Costs / Risks

- Probe misconfiguration có thể tạo outage lớn hơn failure gốc.
- Health endpoint cần được maintain như production API.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Nhớ: readiness = traffic, liveness = restart, startup = initial boot.

### Middle

Implement health endpoints và đọc Kubernetes events.

### Senior

Thiết kế probe dependency semantics, thresholds và behavior dưới partial outage.

### Technical Lead / Architect

Định nghĩa platform health policy, SLO và failure containment để self-healing không trở thành self-destruction.

## 11. Key takeaway

- Không dùng một health signal cho ba quyết định khác nhau.
- Remote dependency failure thường không phải lý do restart process.
- Probe phải được chaos-tested dưới real failure modes.

# 10. OAuth 2.0 refresh token rotation: giảm blast radius khi token bị đánh cắp và phát hiện reuse thay vì coi refresh token là mật khẩu vĩnh viễn

## 1. What is it?

Access token thường ngắn hạn. Refresh token cho phép client lấy access token mới mà không bắt user login lại.

**Refresh token rotation** nghĩa là mỗi lần refresh thành công, authorization server phát refresh token mới và token cũ bị vô hiệu hóa hoặc đánh dấu đã dùng.

```text
RT1 -> refresh -> AT2 + RT2
RT1 now invalid/reused
RT2 -> refresh -> AT3 + RT3
```

## 2. Why does it exist?

Refresh token có lifetime dài hơn access token nên nếu bị đánh cắp, attacker có thể duy trì session lâu.

Rotation giảm cửa sổ sử dụng token cũ và tạo signal **reuse detection**: nếu RT1 đã được dùng hợp lệ rồi xuất hiện lần nữa, có khả năng token family bị compromise.

## 3. How does it work?

Authorization server duy trì token family/state hoặc cơ chế tương đương:

```text
Family F
 RT1 used -> RT2 active
 RT2 used -> RT3 active
```

Nếu RT1 xuất hiện sau khi đã rotate:

```text
possible theft/replay
 -> revoke token family/session
 -> require reauthentication
```

Exact behavior phụ thuộc identity provider. Application không nên tự invent refresh-token crypto protocol nếu Entra ID/B2C/IdP đã cung cấp chuẩn phù hợp.

## 4. Practical implementation

Backend-for-Frontend có thể giữ refresh token server-side thay vì browser JavaScript trực tiếp sở hữu long-lived token.

Cookie/session cần:

```text
Secure
HttpOnly
SameSite phù hợp flow
CSRF protection nếu cookie auth
```

Với SPA/OIDC, dùng Authorization Code + PKCE theo provider guidance. Token storage và rotation strategy phải dựa vào threat model, không copy localStorage pattern cũ.

## 5. Real production scenario

User login trên laptop. Malware hoặc XSS lấy refresh token. Nếu token cố định 30 ngày, attacker refresh access tokens liên tục ngay cả khi access token 5 phút.

Với rotation/reuse detection, legitimate client dùng RT1 rồi nhận RT2. Attacker dùng lại RT1 và IdP có thể revoke family, buộc re-login.

## 6. Failure scenario & troubleshooting

**Symptom**
→ users bị logout ngẫu nhiên hoặc refresh requests đồng thời làm token family bị revoke.

**Evidence**
→ multiple concurrent refreshes cùng token; provider logs báo reuse/invalid_grant.

**Hypothesis**
→ client có refresh race hoặc token persistence không atomic.

**Diagnosis**
→ correlate session ID, token family metadata và refresh timing; tuyệt đối không log raw tokens.

**Fix**
→ single-flight refresh per session, atomic token replacement, đúng provider SDK flow.

**Verification**
→ concurrency tests với expired access token và nhiều requests cùng lúc.

## 7. Common mistakes

- Log access/refresh token đầy đủ.
- Lưu refresh token dài hạn trong insecure browser storage mà không threat-model XSS.
- Tự decode JWT rồi bỏ qua signature/issuer/audience validation.
- Multiple parallel requests cùng refresh một token cũ.
- Nghĩ refresh token rotation thay thế MFA/session revocation/device controls.

## 8. Alternatives

- **Short session + re-login:** đơn giản, security mạnh hơn nhưng UX kém.
- **BFF/session cookie:** giữ OAuth tokens khỏi JavaScript và centralize session handling.
- **Provider-managed SDK/session:** thường nên ưu tiên thay vì tự xây token lifecycle.

## 9. Trade-offs

### Advantages

- Giảm giá trị của stolen refresh token cũ.
- Reuse detection cung cấp compromise signal.
- Cho access token lifetime ngắn mà UX vẫn tốt.

### Costs / Risks

- Token state/concurrency phức tạp hơn.
- False-looking reuse có thể do client race/bug.
- Session revocation có UX impact.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu access token và refresh token có purpose/lifetime khác nhau.

### Middle

Dùng chuẩn OIDC/OAuth flow, provider SDK và secure storage đúng platform.

### Senior

Thiết kế refresh concurrency, rotation/revocation và troubleshoot `invalid_grant` mà không leak token.

### Technical Lead / Architect

Chọn BFF vs SPA token model, threat-model XSS/session theft và giao token lifecycle cho trusted IdP khi có thể.

## 11. Key takeaway

- Refresh token là credential dài hạn, cần bảo vệ mạnh hơn access token ngắn hạn.
- Rotation + reuse detection giảm blast radius nhưng yêu cầu concurrency handling đúng.
- Authorization-critical logic phải dựa trên chuẩn/provider, không tự chế token protocol.
