# 1. C# `Span<T>` + `stackalloc`: xử lý buffer ngắn hạn với allocation thấp mà không để `ref struct` vượt sai lifetime

## 1. What is it?

`Span<T>` là một `ref struct` đại diện cho một vùng nhớ liên tiếp. Nó có thể trỏ tới array, stack memory, native memory hoặc một slice của buffer mà không cần copy dữ liệu.

Mental model:

```text
Underlying memory
[0][1][2][3][4][5][6][7]
       └──── Span<T> ────┘
```

`stackalloc` cho phép cấp phát một vùng nhớ nhỏ trên stack:

```csharp
Span<byte> buffer = stackalloc byte[64];
```

Điểm quan trọng không phải “stack nhanh hơn heap” theo nghĩa đơn giản, mà là tránh heap allocation cho dữ liệu ngắn hạn với lifetime rất rõ.

## 2. Why does it exist?

Nhiều hot paths chỉ cần temporary buffer rất nhỏ: parse header, encode identifier, transform bytes hoặc format dữ liệu.

Nếu mỗi operation tạo array mới:

```csharp
var buffer = new byte[64];
```

application tạo nhiều short-lived allocations. Ở throughput cao, những allocations nhỏ này cộng lại thành GC pressure.

`Span<T>` còn cho phép slice mà không copy:

```csharp
var payload = buffer.AsSpan(offset, length);
```

trong khi approach cũ dễ tạo array phụ cho mỗi slice.

## 3. How does it work?

`Span<T>` chứa reference tới vùng nhớ và length. Vì có thể trỏ vào stack memory, runtime/compiler phải đảm bảo reference đó không thoát khỏi scope hợp lệ.

Do đó `Span<T>` là `ref struct` và bị hạn chế:

* không thể box
* không thể lưu như field trong class thông thường
* không thể sống qua `await` nếu scope khiến reference vượt lifetime

Ví dụ không hợp lệ về mặt lifetime:

```csharp
public Span<byte> CreateBuffer()
{
    Span<byte> buffer = stackalloc byte[32];
    return buffer;
}
```

Stack frame kết thúc thì vùng nhớ không còn hợp lệ.

## 4. Practical implementation

Ví dụ parse một protocol header ngắn:

```csharp
public static bool TryReadHeader(
    ReadOnlySpan<byte> input,
    out ushort version,
    out uint payloadLength)
{
    version = 0;
    payloadLength = 0;

    if (input.Length < 6)
        return false;

    version = BinaryPrimitives.ReadUInt16BigEndian(input[..2]);
    payloadLength = BinaryPrimitives.ReadUInt32BigEndian(input.Slice(2, 4));

    return true;
}
```

Không có array copy cho từng field.

Với formatting tạm thời:

```csharp
Span<char> chars = stackalloc char[32];
if (orderId.TryFormat(chars, out var written))
{
    var text = chars[..written].ToString();
}
```

## 5. Real production scenario

Một gateway .NET parse hàng chục nghìn protocol messages mỗi giây. Bản đầu dùng `Substring`, `byte[]` slicing và helper methods trả array mới.

Profiler cho thấy allocation rate cao dù business logic rất nhẹ. Chuyển hot parsing path sang `ReadOnlySpan<byte>` và bounded `stackalloc` giảm allocation đáng kể mà không đổi semantics.

## 6. Failure scenario & troubleshooting

**Symptom** → sau optimization, stack overflow xuất hiện dưới input lớn.

**Evidence** → code dùng `stackalloc byte[inputLength]` với input do client kiểm soát.

**Hypothesis** → allocation trên stack không có upper bound.

**Diagnosis** → xem input size distribution và call depth.

**Fix** → chỉ `stackalloc` dưới threshold nhỏ; với buffer lớn dùng `ArrayPool<T>` hoặc heap allocation.

**Verification** → fuzz/load test với payload lớn; stack usage ổn định và allocation profile vẫn đạt mục tiêu.

## 7. Common mistakes

* Dùng `stackalloc` cho buffer lớn hoặc size do external input kiểm soát.
* Tối ưu mọi code sang `Span<T>` dù profiler chưa cho thấy allocation problem.
* Cố giữ `Span<T>` trong object sống lâu.
* Nhầm slice với copy; thay đổi underlying buffer có thể phản ánh vào span.
* Chuyển `Span<T>` sang array ngay lập tức rồi mất lợi ích.

## 8. Alternatives

* `byte[]`: đơn giản nhất, phù hợp phần lớn business code.
* `ArrayPool<T>`: phù hợp temporary buffer lớn hơn hoặc cần sống qua async boundary.
* `Memory<T>`: có thể lưu trên heap và truyền qua async boundary.

## 9. Trade-offs

### Advantages

* Giảm allocation và copying.
* Tốt cho parsing/serialization hot paths.
* Slice rất rẻ.

### Costs / Risks

* Lifetime rules phức tạp hơn.
* Dễ tạo code low-level khó maintain.
* `stackalloc` sai kích thước có thể gây stack pressure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Span<T>` là view trên memory chứ không nhất thiết sở hữu memory.

### Middle

Biết slice, parse và chọn giữa `Span<T>`, `Memory<T>` và array.

### Senior

Đánh giá lifetime, allocation profile và stack safety trước khi áp dụng.

### Technical Lead / Architect

Giữ low-level optimization trong component/library phù hợp thay vì làm toàn codebase khó đọc chỉ để giảm vài allocation không đáng kể.

## 11. Key takeaway

* `Span<T>` hữu ích khi tránh allocation/copy trên hot path đã đo được.
* `stackalloc` chỉ nên dùng cho buffer nhỏ, bounded và lifetime rất ngắn.
* Performance optimization không nên làm API/business code phức tạp hơn nếu lợi ích không measurable.

# 2. ASP.NET Core `ProblemDetails`: biến lỗi thành API contract ổn định thay vì rải `try/catch` và chuỗi lỗi tùy ý

## 1. What is it?

`ProblemDetails` là representation chuẩn hóa cho HTTP API errors theo cấu trúc có semantic fields như `type`, `title`, `status`, `detail`, `instance` và extensions.

Mental model:

```text
Exception / validation failure
        ↓
Central error mapping
        ↓
ProblemDetails contract
        ↓
Client handles predictable shape
```

Mục tiêu không chỉ là JSON đẹp hơn, mà là tách internal exception model khỏi public API error contract.

## 2. Why does it exist?

API lớn thường trượt thành nhiều kiểu lỗi:

```json
{ "error": "Not found" }
```

```json
{ "message": "Invalid request" }
```

```json
{ "errors": [ ... ] }
```

Client phải viết logic đặc biệt cho từng endpoint. Tệ hơn, developer đôi khi trả nguyên `Exception.Message`, làm lộ internal detail.

Một error contract thống nhất giúp client, observability và backward compatibility tốt hơn.

## 3. How does it work?

ASP.NET Core có built-in Problem Details services và exception handling integration.

Flow:

```text
Request
  ↓
Endpoint/Application
  ↓ exception/domain failure
Exception handler
  ↓ map semantic category
ProblemDetails
  ↓
HTTP response
```

Ví dụ mapping:

* resource không tồn tại → 404
* validation → 400
* concurrency conflict → 409
* authorization → 403
* unexpected exception → 500

Không nên map mọi exception thành 500 một cách mù quáng.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();

app.UseExceptionHandler(exceptionHandlerApp =>
{
    exceptionHandlerApp.Run(async context =>
    {
        var exception = context.Features
            .Get<IExceptionHandlerFeature>()?.Error;

        var (status, title) = exception switch
        {
            OrderNotFoundException => (404, "Order not found"),
            ConcurrencyException => (409, "Concurrency conflict"),
            _ => (500, "Unexpected server error")
        };

        await Results.Problem(
            statusCode: status,
            title: title,
            extensions: new Dictionary<string, object?>
            {
                ["traceId"] = context.TraceIdentifier
            })
            .ExecuteAsync(context);
    });
});
```

Production response không nên chứa stack trace hoặc connection string.

## 5. Real production scenario

Mobile app gọi 30 endpoints của backend. Trước đây mỗi team trả error shape khác nhau. Mobile client có hàng chục branches chỉ để parse lỗi.

Sau khi chuẩn hóa `ProblemDetails`, client dùng status + machine-readable error code extension để quyết định UX, trong khi `traceId` giúp support correlate tới logs.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận 500 cho lỗi business đã biết, support khó phân biệt retryable và non-retryable failures.

**Evidence** → exception handler chỉ có catch-all 500.

**Hypothesis** → exception taxonomy không được map thành HTTP semantics.

**Diagnosis** → kiểm tra domain/application failures và public API contract.

**Fix** → tạo mapping rõ ràng; unexpected exceptions vẫn 500 nhưng known conflicts/validation được map đúng.

**Verification** → contract tests cho từng error category và schema.

## 7. Common mistakes

* Trả raw `Exception.Message` ra client.
* Dùng HTTP 200 rồi nhét `success=false` vào body cho mọi lỗi.
* Tạo custom error shape khác nhau cho từng team.
* Cho client phụ thuộc vào human-readable `detail` thay vì stable code/status.
* Log cùng exception ở nhiều layer tạo duplicate telemetry.

## 8. Alternatives

Custom error envelope vẫn có thể hợp lệ nếu organization đã có contract mature. `ProblemDetails` có lợi thế là semantics quen thuộc và hỗ trợ tốt trong ASP.NET Core.

## 9. Trade-offs

### Advantages

* Error contract nhất quán.
* Tách internal implementation khỏi external response.
* Tốt cho client handling và observability.

### Costs / Risks

* Cần error taxonomy rõ ràng.
* Mapping sai có thể che bug thật thành business error.
* Stable extensions trở thành API contract cần versioning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code và error body là hai phần của cùng API contract.

### Middle

Biết centralize exception mapping và không leak internal details.

### Senior

Phân biệt validation, concurrency, dependency failure, authorization và unexpected bug.

### Technical Lead / Architect

Định nghĩa error contract xuyên services để retry, client UX và support workflow cùng hiểu một semantic model.

## 11. Key takeaway

* Error handling là API design, không chỉ exception handling.
* `ProblemDetails` giúp chuẩn hóa public error semantics.
* Human-readable message không nên là machine contract.

# 3. EF Core `ExecuteUpdateAsync` / `ExecuteDeleteAsync`: bulk operation trực tiếp và nguy cơ lệch state với Change Tracker

## 1. What is it?

`ExecuteUpdateAsync` và `ExecuteDeleteAsync` cho phép EF Core phát trực tiếp SQL `UPDATE`/`DELETE` từ LINQ predicate mà không materialize từng entity vào Change Tracker.

Mental model:

```text
Traditional:
SELECT rows → track entities → modify → SaveChanges → UPDATE rows

ExecuteUpdate:
LINQ predicate → UPDATE directly in database
```

## 2. Why does it exist?

Nếu cần archive 100.000 rows, load tất cả entities chỉ để đổi một field là rất lãng phí:

* network payload lớn
* memory lớn
* Change Tracker overhead
* nhiều commands hoặc batches

Set-based operation để database làm đúng việc mà relational engine mạnh nhất.

## 3. How does it work?

Ví dụ:

```csharp
await db.Orders
    .Where(x => x.ExpiresAt < cutoff && x.Status == OrderStatus.Pending)
    .ExecuteUpdateAsync(
        setters => setters
            .SetProperty(x => x.Status, OrderStatus.Expired)
            .SetProperty(x => x.UpdatedAt, DateTimeOffset.UtcNow),
        ct);
```

EF Core translate thành set-based `UPDATE`.

Quan trọng: Change Tracker không tự đồng bộ các tracked entities đã được load trước đó.

## 4. Practical implementation

Nguy cơ:

```csharp
var order = await db.Orders.SingleAsync(x => x.Id == id, ct);

await db.Orders
    .Where(x => x.Id == id)
    .ExecuteUpdateAsync(
        s => s.SetProperty(x => x.Status, OrderStatus.Expired),
        ct);

// order.Status có thể vẫn là giá trị cũ trong memory
```

Nếu cần state mới:

```csharp
await db.Entry(order).ReloadAsync(ct);
```

Hoặc tránh mix tracked state và direct bulk operation trong cùng unit of work.

## 5. Real production scenario

Nightly job archive hàng triệu expired sessions. Bản cũ load entity batches rồi gọi `SaveChanges`. Job mất hàng chục phút và tạo memory pressure.

Set-based `ExecuteDeleteAsync` giảm round trips đáng kể. Tuy nhiên application phải đảm bảo job không chạy trong cùng DbContext giữ cached tracked sessions.

## 6. Failure scenario & troubleshooting

**Symptom** → database row đã đổi nhưng code sau đó vẫn đọc giá trị cũ từ entity đang tracked.

**Evidence** → SQL profiler thấy update thành công; debugger cho thấy tracked object không đổi.

**Hypothesis** → direct update bypass Change Tracker.

**Diagnosis** → kiểm tra cùng DbContext có entity được load trước bulk operation không.

**Fix** → reload/clear tracker hoặc chia operation boundary rõ ràng.

**Verification** → integration test cùng DbContext và database state sau operation.

## 7. Common mistakes

* Nghĩ `ExecuteUpdateAsync` tương đương modify entities + `SaveChanges` về lifecycle semantics.
* Mix bulk operations với tracked entities rồi dùng stale state.
* Quên concurrency/business invariant vốn nằm trong entity method.
* Dùng bulk delete cho domain data cần audit/events nhưng không phát side effects cần thiết.

## 8. Alternatives

* Tracked update + `SaveChanges`: phù hợp khi cần domain behavior, concurrency token và per-entity validation.
* Raw SQL/stored procedure: nhiều control hơn nhưng giảm LINQ integration.
* Bulk library: hữu ích cho import/export phức tạp, nhưng thêm dependency.

## 9. Trade-offs

### Advantages

* Ít round trips và memory hơn.
* Tận dụng set-based database execution.
* Code ngắn gọn cho maintenance operations.

### Costs / Risks

* Bypass Change Tracker state.
* Có thể bypass domain invariants/events.
* Audit/concurrency semantics phải được thiết kế lại nếu cần.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu direct bulk operation không cần load entities.

### Middle

Biết khi nào dùng và tránh stale tracked state.

### Senior

Đánh giá invariant, audit, concurrency và transaction implications.

### Technical Lead / Architect

Quyết định operation nào là domain command cần aggregate behavior và operation nào thực sự chỉ là set-based maintenance/data lifecycle work.

## 11. Key takeaway

* `ExecuteUpdateAsync` nhanh vì bỏ qua materialization/tracking, và chính điều đó tạo semantic khác biệt.
* Không trộn direct bulk mutation với tracked state mà không hiểu hậu quả.
* Performance optimization không được vô tình bỏ qua business invariants.

# 4. SQL Server deadlock graph: đọc wait cycle để sửa transaction ordering thay vì tăng timeout hoặc retry mù quáng

## 1. What is it?

Deadlock xảy ra khi hai hoặc nhiều transactions giữ resources mà transaction khác cần và tạo vòng chờ không thể tự giải phóng.

```text
T1 giữ Row A → chờ Row B
T2 giữ Row B → chờ Row A
```

SQL Server phát hiện cycle và chọn một victim để rollback.

## 2. Why does it exist?

Locking bảo vệ consistency. Deadlock là hệ quả của concurrent transactions lấy locks theo thứ tự khác nhau hoặc giữ lock quá rộng/lâu.

Không thể “tắt locking” mà vẫn giữ correctness. Cần sửa access pattern.

## 3. How does it work?

Deadlock monitor phát hiện wait-for cycle. Deadlock graph cho biết:

* sessions/processes
* resources/keys/pages
* lock modes
* statements
* victim

Ví dụ pattern:

```text
Transaction A:
UPDATE Accounts WHERE Id = 1
UPDATE Accounts WHERE Id = 2

Transaction B:
UPDATE Accounts WHERE Id = 2
UPDATE Accounts WHERE Id = 1
```

Thứ tự khác nhau tạo cycle.

## 4. Practical implementation

Sửa bằng ordering nhất quán:

```csharp
var ids = new[] { fromAccountId, toAccountId }
    .OrderBy(x => x)
    .ToArray();

var accounts = await db.Accounts
    .Where(x => ids.Contains(x.Id))
    .OrderBy(x => x.Id)
    .ToListAsync(ct);
```

Mục tiêu là transactions cạnh tranh resources theo cùng deterministic order.

Extended Events/deadlock reports nên được dùng để xem graph thật thay vì đoán.

## 5. Real production scenario

Transfer service cập nhật source account và destination account. Hai transfers chạy đồng thời theo hướng ngược nhau.

Traffic thấp không thấy lỗi. Khi peak traffic, deadlock frequency tăng và một số requests nhận error 1205.

## 6. Failure scenario & troubleshooting

**Symptom** → intermittent SQL error 1205 dưới concurrency cao.

**Evidence** → deadlock graph cho thấy hai `UPDATE Accounts` chờ key locks chéo nhau.

**Hypothesis** → inconsistent lock acquisition order.

**Diagnosis** → so sánh transaction sequences ở hai code paths.

**Fix** → standardize ordering, rút ngắn transaction, thêm index nếu query đang khóa nhiều rows hơn cần thiết.

**Verification** → concurrency load test và monitor deadlock events sau deploy.

## 7. Common mistakes

* Tăng command timeout — deadlock không phải timeout problem.
* Retry vô hạn — có thể che design issue và khuếch đại tải.
* Thêm `NOLOCK` để “hết deadlock” nhưng chấp nhận dirty/incorrect reads.
* Giữ transaction mở qua external HTTP call.
* Chỉ xem query text mà không xem lock resource/plan.

## 8. Alternatives

Snapshot-based isolation có thể giảm reader-writer blocking trong một số cases, nhưng writer-writer conflicts vẫn tồn tại. Application retry có thể hợp lý sau khi transaction được thiết kế đúng và operation idempotent.

## 9. Trade-offs

### Advantages

* Locking giữ transactional correctness.
* Deadlock detector giúp hệ thống tự thoát cycle.

### Costs / Risks

* Victim bị rollback.
* Retry tạo thêm tải.
* Transaction design sai chỉ lộ dưới concurrency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deadlock là vòng chờ locks, không phải query đơn thuần “chậm”.

### Middle

Biết đọc deadlock graph cơ bản và transaction order.

### Senior

Kết nối execution plan, lock footprint, transaction duration và retry semantics.

### Technical Lead / Architect

Chuẩn hóa transaction boundaries/access ordering cho các workflow tài chính hoặc high-contention thay vì xử lý từng incident riêng lẻ.

## 11. Key takeaway

* Deadlock phải được điều tra bằng wait cycle evidence.
* Consistent resource ordering thường mạnh hơn việc tăng timeout.
* Retry chỉ là lớp resilience sau khi root cause concurrency đã được hiểu.

# 5. Redis cache stampede + single-flight: một key hết hạn có thể biến cache thành bộ khuếch đại tải lên database như thế nào

## 1. What is it?

Cache stampede xảy ra khi một hot key hết hạn và nhiều requests đồng thời đều thấy cache miss, sau đó cùng đổ xuống database/downstream dependency.

```text
1000 requests
      ↓
Redis miss cùng lúc
      ↓
1000 database queries
```

Single-flight là kỹ thuật để chỉ một request thực hiện expensive refresh trong khi các requests khác chờ hoặc dùng stale data.

## 2. Why does it exist?

Cache được thêm để giảm tải origin. Nhưng synchronized expiration có thể đảo ngược lợi ích và tạo load spike đúng lúc cache không còn bảo vệ hệ thống.

Một key homepage/catalog rất nóng có thể gây outage origin dù Redis vẫn hoạt động bình thường.

## 3. How does it work?

Một process-local single-flight cơ bản:

```text
Request A miss → acquire refresh gate → load DB → set cache
Request B miss → wait gate → recheck cache → use refreshed value
Request C miss → wait gate → recheck cache → use refreshed value
```

Trong multi-instance application, local lock chỉ bảo vệ từng instance; distributed coordination hoặc stale strategy có thể cần thiết.

## 4. Practical implementation

Ví dụ đơn giản với `SemaphoreSlim`:

```csharp
private readonly SemaphoreSlim _gate = new(1, 1);

public async Task<ProductDto> GetFeaturedAsync(CancellationToken ct)
{
    const string key = "featured-products";

    var cached = await cache.GetStringAsync(key, ct);
    if (cached is not null)
        return JsonSerializer.Deserialize<ProductDto>(cached)!;

    await _gate.WaitAsync(ct);
    try
    {
        cached = await cache.GetStringAsync(key, ct);
        if (cached is not null)
            return JsonSerializer.Deserialize<ProductDto>(cached)!;

        var value = await repository.LoadFeaturedAsync(ct);
        await cache.SetStringAsync(
            key,
            JsonSerializer.Serialize(value),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
            },
            ct);

        return value;
    }
    finally
    {
        _gate.Release();
    }
}
```

Recheck sau lock là bắt buộc.

## 5. Real production scenario

Product detail page có 20.000 requests/phút cho một promotion. TTL đúng 10 phút trên mọi instance. Khi key hết hạn, hàng trăm requests đồng thời query pricing database.

Database CPU tăng, latency tăng, requests retry và vấn đề khuếch đại.

## 6. Failure scenario & troubleshooting

**Symptom** → DB QPS spike theo chu kỳ đúng TTL của cache.

**Evidence** → Redis miss rate tăng đột ngột đúng mỗi 10 phút.

**Hypothesis** → synchronized expiration/cache stampede.

**Diagnosis** → correlate key TTL, miss rate và DB dependency telemetry.

**Fix** → jitter TTL, single-flight, stale-while-revalidate hoặc proactive refresh.

**Verification** → miss events không còn tạo origin QPS spike.

## 7. Common mistakes

* Đặt cùng TTL chính xác cho hàng nghìn keys.
* Distributed lock quá lâu rồi biến Redis thành bottleneck mới.
* Không recheck cache sau khi acquire lock.
* Chờ refresh vô hạn thay vì có timeout/fallback.
* Cache dữ liệu không đáng cache chỉ vì origin chậm.

## 8. Alternatives

* TTL jitter: giảm synchronized expiration.
* Stale-while-revalidate: phục vụ stale data trong lúc một worker refresh.
* Background warming: tốt cho predictable hot keys.
* Không cache: hợp lý nếu origin đã đủ nhanh và complexity không đáng.

## 9. Trade-offs

### Advantages

* Bảo vệ origin trong cache-miss bursts.
* Giảm duplicate refresh work.

### Costs / Risks

* Coordination complexity.
* Waiters có thể tăng latency.
* Stale strategy đổi freshness semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss đồng thời có thể tạo tải lớn hơn bình thường.

### Middle

Biết dùng recheck-after-lock, jitter và timeout.

### Senior

Đánh giá multi-instance behavior, stale tolerance và fallback khi Redis/origin lỗi.

### Technical Lead / Architect

Quyết định freshness SLA và ownership của cache refresh thay vì để mỗi endpoint tự tạo strategy khác nhau.

## 11. Key takeaway

* Cache có thể khuếch đại failure nếu expiration được thiết kế kém.
* Single-flight chỉ là một strategy; stale/jitter thường cần phối hợp.
* Hãy theo dõi miss rate và origin QPS cùng nhau.

# 6. Saga + compensating transaction: xử lý workflow nhiều service khi không thể giữ một ACID transaction xuyên hệ thống

## 1. What is it?

Saga chia một business workflow dài thành nhiều local transactions. Nếu bước sau thất bại, hệ thống chạy compensating actions để đảo hoặc trung hòa các bước đã hoàn tất trước đó.

```text
Create Order
   ↓
Reserve Inventory
   ↓
Charge Payment
   ↓ failure
Release Inventory
   ↓
Cancel Order
```

Compensation không nhất thiết là “rollback byte-for-byte”; nó là một business action để đưa hệ thống về trạng thái chấp nhận được.

## 2. Why does it exist?

Trong Microservices/distributed systems, mỗi service thường sở hữu database riêng. Một ACID transaction xuyên SQL, payment provider và inventory service thường không khả thi hoặc tạo coupling/availability rất xấu.

Saga chấp nhận eventual consistency và xử lý failure bằng workflow semantics.

## 3. How does it work?

Hai style chính:

* Orchestration: một coordinator quyết định bước tiếp theo và compensation.
* Choreography: services phản ứng events và workflow nổi lên từ event chain.

Orchestration dễ nhìn state machine hơn; choreography giảm central coordinator nhưng có thể khó theo dõi khi workflow lớn.

## 4. Practical implementation

State machine đơn giản:

```csharp
public enum OrderSagaState
{
    Created,
    InventoryReserved,
    PaymentCaptured,
    Completed,
    Compensating,
    Failed
}
```

Coordinator phải persist state trước/đồng thời với outgoing commands bằng Outbox Pattern để không mất transition khi process crash.

Pseudo-near-production flow:

```csharp
await sagaStore.MarkInventoryReservedAsync(sagaId, ct);
await outbox.EnqueueAsync(new CapturePayment(orderId), ct);
```

Hai writes nên cùng transaction nếu cùng store.

## 5. Real production scenario

Checkout gồm inventory, payment và shipping reservation. Payment thành công nhưng shipping provider timeout.

Không thể database rollback payment provider. Compensation có thể là refund hoặc void authorization, đồng thời release inventory.

## 6. Failure scenario & troubleshooting

**Symptom** → một số orders bị stuck ở `InventoryReserved` hàng giờ.

**Evidence** → saga state tồn tại nhưng không có outgoing payment command sau process crash.

**Hypothesis** → state update và message publish không atomic.

**Diagnosis** → transaction commit thành công trước khi broker publish xảy ra.

**Fix** → Outbox + reliable dispatcher; watchdog cho stuck sagas.

**Verification** → kill process giữa commit/publish trong chaos test; workflow vẫn tiếp tục sau restart.

## 7. Common mistakes

* Gọi compensation là technical rollback mà không hỏi business semantics.
* Choreography cho workflow lớn dẫn tới event spaghetti.
* Không idempotent các steps/compensations.
* Không lưu saga state.
* Không có timeout cho bước external dependency.

## 8. Alternatives

* Single database transaction: đơn giản hơn nếu workflow vẫn nằm trong một bounded system.
* Two-phase commit: hiếm phù hợp với cloud services/external providers do availability và complexity.
* Manual reconciliation: đôi khi hợp lý cho rare high-value exceptions.

## 9. Trade-offs

### Advantages

* Không cần distributed ACID transaction.
* Cho phép service autonomy.
* Failure semantics được biểu diễn rõ.

### Costs / Risks

* Eventual consistency.
* Compensation có thể thất bại.
* Workflow state/observability phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu local transaction chỉ bảo vệ một service/store.

### Middle

Biết idempotency, Outbox và compensation basics.

### Senior

Thiết kế retry, timeout, stuck-state recovery và compensation failure.

### Technical Lead / Architect

Quyết định có cần Saga hay nên giữ workflow trong một transactional boundary đơn giản hơn. Không phân tán hệ thống nếu business chưa cần.

## 11. Key takeaway

* Saga là business workflow consistency model, không phải distributed rollback trick.
* Compensation phải được thiết kế như first-class business action.
* Outbox, idempotency và observability gần như bắt buộc cho Saga đáng tin cậy.

# 7. Azure App Service deployment slots: warm-up, slot settings và cách giảm deployment blast radius mà không nhầm swap với rollback tuyệt đối

## 1. What is it?

Deployment slot là một live App Service environment khác ngoài Production, ví dụ `staging`, chạy cùng application với hostname riêng và có thể swap vào Production.

```text
Deploy → Staging Slot → Warm/Validate → Swap → Production traffic
```

Mục tiêu là tách **deploy artifact** khỏi **expose artifact cho production traffic**.

## 2. Why does it exist?

Deploy trực tiếp lên Production có thể tạo:

* cold start
* startup failure
* config error
* assembly load issue
* dependency initialization delay

Slot cho phép application boot và được validate trước khi nhận production traffic.

## 3. How does it work?

Một số settings có thể đánh dấu là slot settings, nghĩa là chúng “stick” với slot thay vì swap.

Ví dụ connection string hoặc environment-specific setting cần xem xét kỹ.

Swap không chỉ đổi URL label; platform routing/config semantics phải được hiểu để tránh staging bất ngờ dùng production dependency hoặc ngược lại.

## 4. Practical implementation

Pipeline:

```text
Build immutable artifact
   ↓
Deploy to staging
   ↓
Health/readiness validation
   ↓
Smoke tests
   ↓
Swap staging → production
   ↓
Observe metrics
```

Health endpoint nên kiểm tra startup readiness thực tế nhưng không phụ thuộc quá sâu vào mọi optional downstream service.

## 5. Real production scenario

ASP.NET Core application cần 40 giây để warm caches/JIT/load CMS metadata. Direct deploy gây 5xx spike mỗi release.

Staging slot warm-up cho phép startup hoàn tất trước swap, giảm user-visible cold start.

## 6. Failure scenario & troubleshooting

**Symptom** → staging test pass nhưng sau swap Production kết nối nhầm test database.

**Evidence** → connection string không được đánh dấu slot-specific đúng cách.

**Hypothesis** → configuration swap semantics sai.

**Diagnosis** → audit app settings/slot settings và actual environment variables ở cả hai slots.

**Fix** → phân loại config nào đi cùng artifact, config nào phải stick với environment.

**Verification** → pre-swap checklist và automated config assertions.

## 7. Common mistakes

* Nghĩ slot swap tự động là zero-risk deployment.
* Không warm/health-check trước swap.
* Để database migration destructive chạy trước khi old version ngừng tồn tại.
* Nhầm slot rollback với rollback database/schema.
* Không theo dõi telemetry sau swap.

## 8. Alternatives

* Blue-Green trên Container Apps/Kubernetes.
* Canary routing nếu cần expose traffic dần.
* Direct deployment cho internal/low-risk app đơn giản.

## 9. Trade-offs

### Advantages

* Giảm cold-start exposure.
* Có pre-production environment gần Production.
* Swap nhanh hơn redeploy artifact.

### Costs / Risks

* Tốn thêm compute/resources tùy plan.
* Config semantics phức tạp hơn.
* Database change vẫn cần backward compatibility riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slot là live environment độc lập trước Production.

### Middle

Biết deploy, warm-up, health-check và phân biệt slot settings.

### Technical Lead / Architect

Thiết kế release strategy bao gồm artifact, config, database và feature rollout — không coi App Service swap là toàn bộ deployment architecture.

## 11. Key takeaway

* Slot giảm deployment risk nhưng không giải quyết database compatibility tự động.
* Config ownership giữa slot và environment phải rõ.
* Swap xong vẫn cần Production verification và rollback plan.

# 8. IIS Application Pool recycling: vì sao recycle có thể tạo cold start, mất in-memory state và request disruption trong ứng dụng enterprise

## 1. What is it?

IIS Application Pool quản lý worker process (`w3wp.exe`) chạy web application. Recycling tạo worker process mới và kết thúc process cũ theo lifecycle của IIS.

Mental model:

```text
App Pool
  ↓
w3wp old ── recycle ──> w3wp new
```

Recycle có thể được kích hoạt bởi schedule, memory limits, config changes, deployment hoặc manual action.

## 2. Why does it exist?

Worker process cần lifecycle management để:

* áp config mới
* recover từ process degradation
* giới hạn một số resource conditions
* hỗ trợ deployment/maintenance

Nhưng recycle không phải “memory leak fix strategy” lâu dài.

## 3. How does it work?

Trong overlapped recycling, IIS có thể start worker mới trước khi worker cũ dừng, giảm downtime.

Tuy nhiên application startup vẫn có thể chậm do:

* JIT
* dependency initialization
* CMS cache loading
* DB connection warm-up

In-memory state ở process cũ không tự chuyển sang process mới.

## 4. Practical implementation

ASP.NET Core hosted behind IIS nên lưu durable/session-critical state ngoài process nếu cần survive recycle.

Không nên:

```csharp
public static Dictionary<Guid, Cart> Carts = new();
```

cho dữ liệu phải sống xuyên process lifecycle.

Thay vào đó dùng Redis/database tùy consistency requirement.

## 5. Real production scenario

Legacy enterprise portal dùng in-process session. App Pool recycle theo schedule lúc 2:00 AM tưởng là low-risk, nhưng users ở timezone khác vẫn đang hoạt động và bị mất session.

Một CMS khác recycle làm first request mất 15 giây vì cache warm-up.

## 6. Failure scenario & troubleshooting

**Symptom** → request latency spike đúng một số thời điểm cố định mỗi ngày.

**Evidence** → IIS event logs cho thấy App Pool recycle trùng thời gian; application startup logs xuất hiện lại.

**Hypothesis** → cold start do recycle.

**Diagnosis** → correlate process ID, startup timestamp và request latency.

**Fix** → review recycle policy, warm-up, preload và externalize critical state.

**Verification** → controlled recycle trong staging/load test; latency và session behavior đạt yêu cầu.

## 7. Common mistakes

* Recycle định kỳ để che memory leak.
* Dùng in-memory cache/session cho state cần durability.
* Không log process start/instance ID.
* Deploy bằng cách kill process mà không hiểu graceful shutdown.
* Không preload/warm ứng dụng nặng.

## 8. Alternatives

App Service/container platforms cũng có process restart lifecycle; khác công cụ nhưng cùng nguyên tắc: process là ephemeral. Windows Service/Kestrel direct hosting vẫn cần lifecycle design tương tự.

## 9. Trade-offs

### Advantages

* Process recovery/config application rõ ràng.
* IIS quản lý worker lifecycle tốt cho enterprise hosting.

### Costs / Risks

* Cold start.
* In-memory state loss.
* Background work bị gián đoạn nếu không shutdown đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu web app process có thể restart dù server không reboot.

### Middle

Biết xem App Pool settings, event logs và startup behavior.

### Senior

Thiết kế app stateless hơn, externalize critical state và xử lý graceful shutdown.

### Technical Lead / Architect

Không để hosting lifecycle trở thành hidden correctness dependency; process restart phải là normal operating condition.

## 11. Key takeaway

* App Pool recycle là lifecycle event bình thường, không nên làm mất business-critical state.
* Cold start phải được đo và warm-up nếu cần.
* Restart định kỳ không thay thế root-cause analysis cho memory/resource leaks.

SonarQube phân tích source code để phát hiện bugs patterns, vulnerabilities, code smells, duplication, complexity và quality-gate conditions.

# 10. Webhook signature verification: bảo vệ third-party callback trước spoofing, replay và secret leakage

## 1. What is it?

Webhook là HTTP callback từ external provider tới application của bạn. Signature verification dùng shared secret hoặc asymmetric signature để kiểm tra request thực sự do provider tạo và payload không bị sửa.

Mental model:

```text
Provider payload + secret
       ↓ HMAC/signature
HTTP request + signature header
       ↓
Your API recomputes/verifies
       ↓
Accept or reject
```

Authentication này khác với việc “URL webhook khó đoán”.

## 2. Why does it exist?

Webhook endpoint thường public trên Internet. Nếu chỉ tin request body:

* attacker có thể fake `payment.succeeded`
* replay request cũ
* spam endpoint
* trigger expensive downstream work

HTTPS bảo vệ transport, nhưng không chứng minh ai đã gửi request.

## 3. How does it work?

Với HMAC SHA-256, provider ký raw payload cùng secret. Receiver tính lại signature và so sánh bằng constant-time comparison.

Timestamp thường được ký cùng payload để giới hạn replay window.

Quan trọng: verify trên **raw request bytes**, không phải object đã deserialize rồi serialize lại, vì whitespace/order có thể khác.

## 4. Practical implementation

```csharp
public static bool VerifyWebhook(
    ReadOnlySpan<byte> body,
    string signatureHex,
    byte[] secret)
{
    using var hmac = new HMACSHA256(secret);
    var computed = hmac.ComputeHash(body.ToArray());

    Span<byte> provided = stackalloc byte[computed.Length];
    if (!Convert.TryFromHexString(signatureHex, provided, out var written) ||
        written != computed.Length)
    {
        return false;
    }

    return CryptographicOperations.FixedTimeEquals(
        computed,
        provided[..written]);
}
```

Production implementation nên theo exact provider specification, bao gồm timestamp/versioned signing scheme.

## 5. Real production scenario

Payment provider gửi `payment.completed`. Endpoint update Order và enqueue fulfillment.

Nếu attacker spoof được callback, họ có thể làm order được fulfillment dù payment chưa tồn tại. Signature verification là boundary security bắt buộc.

## 6. Failure scenario & troubleshooting

**Symptom** → signature luôn fail ở Production nhưng local pass.

**Evidence** → middleware/model binding đọc và transform request body trước verification.

**Hypothesis** → verify trên payload không còn đúng raw bytes.

**Diagnosis** → capture body hash trước/after parsing trong safe test environment.

**Fix** → enable buffering/read raw body trước deserialization hoặc dùng provider SDK đúng cách.

**Verification** → test official sample vectors và real signed events ở sandbox.

Replay case:

**Symptom** → cùng event được xử lý nhiều lần dù signature hợp lệ.

**Fix** → timestamp tolerance + event ID deduplication/idempotent handler.

## 7. Common mistakes

* Tin IP allowlist là đủ.
* So sánh signature bằng string equality thông thường.
* Log full webhook secret hoặc sensitive payload.
* Verify sau khi deserialize/normalize body.
* Không deduplicate event ID.
* Retry side effects không idempotent.

## 8. Alternatives

* mTLS: mạnh nhưng provider support không phổ biến.
* OAuth/client auth: không phải webhook providers nào cũng hỗ trợ.
* IP allowlist: hữu ích defense-in-depth nhưng không nên là proof duy nhất.

## 9. Trade-offs

### Advantages

* Xác thực sender/payload integrity.
* Dễ triển khai với HMAC.
* Kết hợp tốt với idempotency/replay protection.

### Costs / Risks

* Secret rotation cần thiết kế.
* Raw-body handling phức tạp hơn.
* Clock skew ảnh hưởng timestamp validation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTPS không chứng minh request đến từ provider hợp lệ.

### Middle

Biết verify signature, timestamp và raw body.

### Senior

Thiết kế replay protection, secret rotation và idempotent processing.

### Technical Lead / Architect

Chuẩn hóa third-party integration boundary: authentication, rate limiting, deduplication, observability, retry và secret ownership phải được thiết kế cùng nhau.

## 11. Key takeaway

* Public webhook endpoint phải xác minh authenticity và integrity.
* Signature hợp lệ chưa đủ — vẫn cần replay protection và idempotency.
* Verify đúng raw payload theo provider contract, không tự chế signing protocol nếu provider đã có chuẩn.
