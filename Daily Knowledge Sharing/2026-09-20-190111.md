# 1. C# `IAsyncEnumerable<T>`: streaming, cancellation và backpressure boundary

## 1. What is it?

`IAsyncEnumerable<T>` biểu diễn một sequence mà từng phần tử có thể được tạo bất đồng bộ. Mental model: thay vì chờ toàn bộ collection hoàn tất rồi mới trả về, consumer kéo từng item bằng `await foreach`. Nó phù hợp với dữ liệu lớn hoặc nguồn I/O tạo kết quả dần dần.

## 2. Why does it exist?

`Task<List<T>>` buộc producer materialize toàn bộ dữ liệu trước khi consumer xử lý. Với export hàng trăm nghìn records, điều đó tăng memory, time-to-first-item và có thể giữ database/resource lâu không cần thiết. Async streaming cho phép pipeline bắt đầu xử lý sớm hơn.

## 3. How does it work?

Compiler biến async iterator thành state machine. Mỗi lần `MoveNextAsync` yêu cầu phần tử tiếp theo. Consumer tạo nhịp tiêu thụ tự nhiên, nhưng điều đó không tự tạo bounded buffering nếu producer phía dưới đã preload dữ liệu.

```text
Data source -> MoveNextAsync -> item -> consumer
                    ^                    |
                    +---- next demand ---+
```

Cancellation phải đi xuyên iterator để ngừng database/network work khi client bỏ request.

## 4. Practical implementation

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    await foreach (var order in _db.Orders
        .AsNoTracking()
        .OrderBy(x => x.Id)
        .AsAsyncEnumerable()
        .WithCancellation(ct))
    {
        yield return new OrderDto(order.Id, order.Status);
    }
}
```

Nếu expose qua HTTP, cần hiểu serializer và reverse proxy có buffer response hay không; “async iterator” không đảm bảo end-to-end streaming.

## 5. Real production scenario

Reporting API export orders lớn. Thay vì tạo `List<OrderDto>` 500 MB rồi serialize, application đọc và ghi từng record. Time-to-first-byte giảm và peak managed memory thấp hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → client cancel nhưng SQL vẫn chạy lâu. **Evidence** → trace cho thấy request aborted nhưng database command tiếp tục. **Hypothesis** → `CancellationToken` không được propagate. **Diagnosis** → kiểm tra iterator, EF query và response pipeline. **Fix** → dùng `[EnumeratorCancellation]`, `WithCancellation(ct)` và truyền token tới I/O. **Verification** → cancel load test và quan sát command duration/resource release.

## 7. Common mistakes

Gọi `ToListAsync` trước khi stream; giữ transaction suốt một stream rất dài; assume streaming tự giải quyết backpressure ở mọi layer; bỏ cancellation; lazy enumeration sau khi `DbContext` đã dispose.

## 8. Alternatives

`Task<List<T>>` đơn giản hơn cho tập dữ liệu nhỏ. Pagination phù hợp client-driven navigation. `Channel<T>` phù hợp producer/consumer nội bộ cần bounded buffer rõ ràng.

## 9. Trade-offs

### Advantages

Giảm peak memory, cải thiện time-to-first-item và hỗ trợ incremental processing.

### Costs / Risks

Resource lifetime dài hơn, error có thể xảy ra sau khi response đã bắt đầu, testing và retry phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await foreach` lấy dữ liệu dần thay vì materialize toàn bộ.

### Middle

Implement iterator, cancellation và dispose đúng lifecycle.

### Senior

Đánh giá buffering, transaction/resource lifetime, partial response và end-to-end backpressure.

### Technical Lead / Architect

Quyết định streaming, pagination hay batch dựa trên workload, failure semantics và infrastructure; không chọn streaming chỉ vì dataset “lớn”.

## 11. Key takeaway

- `IAsyncEnumerable<T>` tối ưu flow và memory, không tự bảo đảm end-to-end streaming.
- Cancellation phải propagate tới nguồn I/O.
- Resource lifetime và partial-failure semantics quan trọng hơn syntax `await foreach`.

# 2. EF Core interceptors: cross-cutting behavior mà không che khuất database semantics

## 1. What is it?

EF Core interceptors cho phép quan sát hoặc can thiệp các operations như command execution và `SaveChanges`. Mental model: đây là hook ở infrastructure boundary, phù hợp cross-cutting concerns có semantics rõ ràng; không phải nơi giấu business logic.

## 2. Why does it exist?

Một số concern như auditing metadata, command diagnostics hoặc policy enforcement cần áp dụng nhất quán trên nhiều `DbContext` operations. Copy logic vào từng repository/service gây duplication và dễ bỏ sót.

## 3. How does it work?

Interceptor được đăng ký trong EF pipeline. Ví dụ `SaveChangesInterceptor` chạy trước/sau `SaveChanges`; `DbCommandInterceptor` quan sát SQL command. Nó nằm giữa application call và provider, nhưng transaction/database vẫn giữ semantics thật.

## 4. Practical implementation

```csharp
public sealed class AuditInterceptor : SaveChangesInterceptor
{
    public override InterceptionResult<int> SavingChanges(
        DbContextEventData eventData,
        InterceptionResult<int> result)
    {
        var now = DateTimeOffset.UtcNow;
        foreach (var entry in eventData.Context!.ChangeTracker
                     .Entries<IAuditable>()
                     .Where(x => x.State is EntityState.Added or EntityState.Modified))
        {
            entry.Entity.UpdatedAt = now;
        }
        return result;
    }
}
```

Interceptor nên deterministic, nhanh và không gọi remote service trong transaction path.

## 5. Real production scenario

Enterprise API cần thống nhất `UpdatedAt` cho nhiều aggregates. Interceptor áp dụng technical audit field mà không yêu cầu mọi handler nhớ set thủ công.

## 6. Failure scenario & troubleshooting

**Symptom** → `SaveChanges` latency tăng đột ngột. **Evidence** → trace cho thấy interceptor gọi HTTP audit service. **Diagnosis** → cross-cutting hook đã kéo remote I/O vào transaction path. **Fix** → ghi audit/outbox local trong transaction rồi publish async. **Verification** → transaction duration và p95 trở lại baseline.

## 7. Common mistakes

Nhét authorization/business rule vào interceptor; mutate entities không minh bạch; query database trong vòng lặp change tracker; swallow exceptions; tạo hidden behavior khiến tests khó hiểu.

## 8. Alternatives

Override `SaveChanges` đơn giản hơn nếu chỉ một context. Domain/application logic rõ hơn cho business invariants. Decorator phù hợp cross-cutting behavior ở service boundary.

## 9. Trade-offs

### Advantages

Centralized infrastructure behavior và giảm duplication.

### Costs / Risks

Hidden control flow, debugging khó hơn và dễ vô tình tăng transaction duration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu interceptor là infrastructure hook, không phải business service.

### Middle

Implement audit/diagnostic interceptor và test behavior.

### Senior

Nhận biết transaction impact, ordering và hidden side effects.

### Technical Lead / Architect

Định nghĩa concern nào đủ cross-cutting để dùng interceptor và concern nào phải explicit trong application/domain flow.

## 11. Key takeaway

- Interceptor phù hợp technical cross-cutting concerns có semantics ổn định.
- Không giấu remote I/O hoặc business invariant trong EF hooks.
- Hidden behavior phải được bù bằng tests và observability rõ ràng.

# 3. PostgreSQL JSONB + GIN: linh hoạt schema nhưng vẫn phải thiết kế access pattern

## 1. What is it?

`jsonb` lưu JSON ở dạng binary normalized; GIN index hỗ trợ tra cứu containment/key-oriented hiệu quả. Mental model: đây là relational database có một vùng semi-structured mạnh, không phải lý do để bỏ schema design.

## 2. Why does it exist?

Một số attributes thay đổi theo loại sản phẩm hoặc integration payload và không đáng tạo hàng trăm nullable columns. `jsonb` cho phép linh hoạt trong cùng transactional database, nhưng query patterns vẫn quyết định index và modeling.

## 3. How does it work?

```sql
CREATE TABLE products (
  id bigint PRIMARY KEY,
  name text NOT NULL,
  attributes jsonb NOT NULL
);

CREATE INDEX ix_products_attributes_gin
ON products USING gin (attributes);
```

Query containment như `attributes @> '{"color":"black"}'` có thể dùng GIN. Expression index có thể tốt hơn nếu thường xuyên query một scalar cụ thể.

## 4. Practical implementation

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name
FROM products
WHERE attributes @> '{"brand":"Contoso"}'
LIMIT 50;
```

Đọc actual plan và buffers trước/sau index; không giả định GIN luôn được chọn.

## 5. Real production scenario

Marketplace có common fields như SKU/name/price ở columns, còn category-specific attributes nằm trong `jsonb`. Search/filter phổ biến được index có chủ đích thay vì tạo GIN cho mọi payload theo phản xạ.

## 6. Failure scenario & troubleshooting

**Symptom** → write latency và storage tăng sau khi thêm GIN. **Evidence** → index size lớn, update-heavy workload, query hiếm dùng index. **Hypothesis** → index cost vượt read benefit. **Diagnosis** → `pg_stat_user_indexes`, plans và write metrics. **Fix** → expression/partial index hoặc bỏ index không hữu ích. **Verification** → compare read p95 và write cost.

## 7. Common mistakes

Đẩy core relational constraints vào JSON; không validate shape; index toàn bộ JSON dù chỉ query một field; dùng cast/function làm predicate khó tận dụng index; không theo dõi index bloat/cost.

## 8. Alternatives

Columns chuẩn tốt hơn cho stable, constrained fields. Child tables tốt hơn cho relational cardinality. MongoDB phù hợp nếu document access pattern chi phối toàn domain; Elasticsearch phù hợp full-text/faceted search chuyên sâu.

## 9. Trade-offs

### Advantages

Schema linh hoạt trong cùng ACID boundary và query operators mạnh.

### Costs / Risks

Validation yếu hơn nếu không bổ sung, index lớn và query/index design phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `jsonb` không có nghĩa “không schema”.

### Middle

Viết containment queries và kiểm tra execution plan.

### Senior

Thiết kế GIN/expression indexes theo workload và đo write amplification.

### Technical Lead / Architect

Quyết định phần nào thuộc relational schema, JSON extension hay một datastore khác dựa trên ownership/access patterns.

## 11. Key takeaway

- `jsonb` bổ sung flexibility, không thay thế relational modeling.
- Index phải xuất phát từ query workload.
- Đo cả read benefit lẫn write/storage cost.

# 4. Redis hot keys: khi distributed cache bị nghẽn bởi một key quá nổi tiếng

## 1. What is it?

Hot key là key nhận lượng request vượt trội so với phần còn lại, khiến một Redis node/CPU/network path trở thành bottleneck dù tổng dataset được phân tán tốt.

## 2. Why does it exist?

Partitioning phân phối theo key, không chia một key đơn lẻ ra nhiều shards. Một homepage config hoặc flash-sale product có thể nhận hàng chục nghìn reads/giây trên đúng node sở hữu key đó.

## 3. How does it work?

```text
Clients ---> key:product:42 ---> Redis shard B
           key:a -----------> shard A
           key:z -----------> shard C
```

Traffic skew, không phải memory size, tạo hotspot. Local caching hoặc replication/read architecture có thể giảm fan-in tùy consistency tolerance.

## 4. Practical implementation

```csharp
var local = memoryCache.Get<ProductDto>(key);
if (local is not null) return local;

var value = await redis.StringGetAsync(key);
if (value.HasValue)
{
    var dto = JsonSerializer.Deserialize<ProductDto>(value!)!;
    memoryCache.Set(key, dto, TimeSpan.FromSeconds(5));
    return dto;
}
```

Tiny per-instance cache có thể hấp thụ cực nhiều reads của immutable/briefly-stale data, nhưng phải chấp nhận freshness window.

## 5. Real production scenario

Flash sale làm product 42 trở thành 70% cache traffic. Redis overall memory còn dư nhưng shard chứa key đó đạt CPU/network ceiling và p99 tăng mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis latency cao nhưng chỉ một node bận. **Evidence** → key access distribution và per-node CPU/network. **Hypothesis** → hot key. **Diagnosis** → sampling/slowlog/telemetry an toàn. **Fix** → local cache, request coalescing, data partitioning nếu semantics cho phép hoặc scale topology. **Verification** → traffic distribution và p99 cải thiện.

## 7. Common mistakes

Chỉ nhìn aggregate Redis metrics; shard một logical value tùy tiện rồi tăng client complexity; local-cache dữ liệu cần strict freshness; tăng cluster size nhưng hot key vẫn ở một shard.

## 8. Alternatives

`IMemoryCache` cho per-instance data; CDN cho public cacheable content; database read replica nếu cache không đúng abstraction. Không cache cũng có thể đúng nếu backend đủ capacity.

## 9. Trade-offs

### Advantages

Mitigation đúng giúp giảm bottleneck rất lớn với thay đổi nhỏ.

### Costs / Risks

Multi-layer cache làm invalidation/freshness phức tạp và tăng observability burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu distributed cache không đảm bảo traffic tự cân bằng.

### Middle

Đo key distribution và implement local cache có TTL hợp lý.

### Senior

Phân tích skew, consistency tolerance và failure fallback.

### Technical Lead / Architect

Quyết định có nên thêm cache layer/topology hay sửa access pattern; xác định owner của invalidation và stale-data policy.

## 11. Key takeaway

- Cluster scaling không tự chữa một hot key.
- Quan sát per-node và per-key traffic, không chỉ aggregate metrics.
- Mitigation phải giữ freshness/consistency contract rõ ràng.

# 5. Domain Events vs Integration Events: tách transaction boundary khỏi distributed contract

## 1. What is it?

Domain Event biểu diễn điều đã xảy ra có ý nghĩa bên trong domain/bounded context. Integration Event là contract được publish ra ngoài process/service để hệ khác phản ứng. Hai khái niệm có thể liên quan nhưng có ownership, compatibility và failure semantics khác nhau.

## 2. Why does it exist?

Nếu domain object publish trực tiếp external message, business model bị coupling với broker/schema bên ngoài và transaction dễ rơi vào dual-write. Tách hai boundary cho phép domain diễn đạt business fact, application/infrastructure quyết định khi nào và bằng contract nào nó rời service.

## 3. How does it work?

```text
Aggregate
  -> Domain Event
  -> Application handler
  -> DB transaction + Outbox Integration Event
  -> publisher
  -> broker
  -> external consumers
```

Data ownership vẫn ở bounded context. Transaction kết thúc ở local database; external delivery là eventual và phải chịu duplicate/partial failure.

## 4. Practical implementation

```csharp
public sealed record OrderPaidDomainEvent(Guid OrderId, decimal Amount);
public sealed record OrderPaidV1(Guid OrderId, decimal Amount, DateTimeOffset PaidAt);

// In the same DB transaction as the aggregate change:
outbox.Add(new OutboxMessage(
    "order.paid.v1",
    JsonSerializer.Serialize(new OrderPaidV1(order.Id, order.Total, clock.UtcNow))));
```

Không cần expose toàn bộ domain object làm event payload.

## 5. Real production scenario

Order bounded context chuyển trạng thái Paid. Domain logic tạo `OrderPaidDomainEvent`; application tạo integration event ổn định cho fulfillment và analytics. Refactor internal aggregate không bắt consumers đổi theo.

## 6. Failure scenario & troubleshooting

**Symptom** → order commit thành công nhưng event không tới broker. **Evidence** → publish trực tiếp sau `SaveChanges` và process crash giữa hai bước. **Diagnosis** → dual-write gap. **Fix** → transactional outbox. **Verification** → kill-process test sau commit; outbox publisher vẫn phát event sau restart.

## 7. Common mistakes

Dùng cùng class cho domain và integration contract; publish trước transaction commit; đưa entity graph vào payload; không version event; giả định broker delivery exactly-once.

## 8. Alternatives

Synchronous API phù hợp khi caller cần immediate result. Database CDC có thể tạo integration stream nhưng ownership/transformation vẫn cần thiết kế. Với monolith đơn giản, in-process event có thể đủ và broker là overengineering.

## 9. Trade-offs

### Advantages

Giảm coupling, bảo vệ domain model và làm failure boundary explicit.

### Costs / Risks

Thêm mapping, outbox, schema governance và eventual consistency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt internal business notification với external distributed contract.

### Middle

Implement handlers và mapping rõ ràng.

### Senior

Thiết kế transaction/outbox, idempotency và event versioning.

### Technical Lead / Architect

Xác định bounded-context ownership, communication pattern, deployment compatibility và khi nào messaging là không cần thiết.

## 11. Key takeaway

- Domain Event và Integration Event có boundary khác nhau.
- External event là public contract cần versioning.
- Local transaction + Outbox rõ ràng hơn cố tạo distributed ACID.

# 6. Azure Private Endpoint + DNS: private connectivity thường hỏng ở name resolution

## 1. What is it?

Azure Private Endpoint đưa một Azure service vào VNet thông qua private IP. DNS quyết định hostname của service resolve về private IP đó. Mental model: network path chỉ private khi name resolution, routing và access policy cùng đúng.

## 2. Why does it exist?

Backend có thể cần truy cập Storage, SQL hoặc Key Vault mà không đi qua public endpoint. Private Endpoint giảm public exposure và hỗ trợ network isolation/compliance.

## 3. How does it work?

```text
App in VNet
   -> DNS query
   -> private DNS zone
   -> private IP
   -> Private Endpoint
   -> Azure PaaS service
```

Managed Identity xử lý identity; Private Endpoint xử lý network reachability. Hai cơ chế không thay thế nhau.

## 4. Practical implementation

Trong incident, kiểm tra resolution từ đúng runtime environment:

```bash
nslookup myvault.vault.azure.net
```

Sau đó kiểm tra private DNS zone link, custom DNS forwarder, VNet integration và service firewall. Application vẫn dùng hostname chuẩn; tránh hard-code private IP vì TLS/DNS/service lifecycle.

## 5. Real production scenario

App Service dùng VNet integration để gọi Key Vault qua Private Endpoint. Deployment mới vào subnet khác khiến DNS zone không link đúng; code và Managed Identity vẫn đúng nhưng connection timeout.

## 6. Failure scenario & troubleshooting

**Symptom** → Production timeout, local/public access hoạt động. **Evidence** → hostname trong app resolve public IP hoặc không resolve. **Hypothesis** → private DNS path sai. **Diagnosis** → kiểm tra resolution, zone links, DNS forwarding, NSG/routing. **Fix** → sửa DNS/VNet config. **Verification** → hostname resolve private IP và dependency telemetry thành công.

## 7. Common mistakes

Hard-code private IP; nghĩ Managed Identity tạo private network; disable public access trước khi kiểm chứng DNS; chỉ test từ laptop; quên custom DNS forwarding giữa on-prem/VNet.

## 8. Alternatives

Service Endpoint đơn giản hơn cho một số services nhưng không cung cấp private IP semantics giống Private Endpoint. Public endpoint + firewall/identity có thể đủ với threat model ít nghiêm ngặt hơn.

## 9. Trade-offs

### Advantages

Giảm public exposure và tạo private network boundary cho PaaS.

### Costs / Risks

DNS/routing complexity, thêm operational cost và troubleshooting cross-team.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt identity với network connectivity.

### Middle

Kiểm tra DNS, VNet integration và service firewall.

### Senior

Debug hybrid DNS/routing và thiết kế observability cho dependency failures.

### Technical Lead / Architect

Quyết định Private Endpoint có cần thiết theo threat/compliance model và bảo đảm team sở hữu DNS/network operational burden.

## 11. Key takeaway

- Private Endpoint không hoàn chỉnh nếu DNS sai.
- Identity và network security là hai lớp độc lập.
- Troubleshoot từ đúng runtime network, không từ máy developer.

# 7. Canary deployment: giảm blast radius nhưng cần telemetry và rollback discipline

## 1. What is it?

Canary deployment đưa version mới tới một phần nhỏ traffic/instances trước khi mở rộng. Mental model: canary là controlled experiment trên production traffic với explicit success/failure criteria.

## 2. Why does it exist?

Test suite và staging không tái tạo hoàn toàn production workload. Deploy 100% ngay lập tức làm regression ảnh hưởng toàn user base. Canary giới hạn blast radius và tạo thời gian quan sát.

## 3. How does it work?

```text
commit -> build -> test -> artifact
                       -> deploy canary 5%
                       -> health + SLI compare
                       -> 25% -> 50% -> 100%
                       -> rollback/stop nếu guardrail fail
```

Cùng artifact phải được promote; không rebuild giữa stages.

## 4. Practical implementation

Pipeline nên gate theo metrics như error rate, p95 latency và business success rate, không chỉ process health. Feature flag có thể tách code deployment khỏi feature exposure.

```text
Guardrail example:
5xx < 1%
p95 regression < 15%
checkout success không giảm > 2%
```

Threshold thực tế phải dựa baseline/SLO của hệ thống.

## 5. Real production scenario

API release mới thay serializer. 5% canary cho thấy p99 tăng và CPU cao dù health endpoint xanh. Pipeline dừng rollout trước khi toàn fleet bị ảnh hưởng.

## 6. Failure scenario & troubleshooting

**Symptom** → canary “pass” nhưng full rollout fail. **Evidence** → canary volume quá nhỏ để kích hoạt connection-pool/contention issue. **Diagnosis** → test không đại diện load-sensitive failure. **Fix** → tăng stage/observation window và kết hợp load testing/capacity signals. **Verification** → staged rollout tái hiện threshold trước full exposure.

## 7. Common mistakes

Chỉ check `/health`; rebuild artifact mỗi environment; database migration breaking backward compatibility; không có automated stop; canary cohort không đại diện traffic; rollback app nhưng schema không rollback-safe.

## 8. Alternatives

Blue-Green đơn giản cho instant switch nhưng blast radius sau switch có thể lớn. Rolling deployment ít infrastructure hơn. Feature flags tốt cho behavioral exposure nhưng không thay deployment health strategy.

## 9. Trade-offs

### Advantages

Giảm blast radius và dùng production evidence để quyết định rollout.

### Costs / Risks

Pipeline/routing/telemetry phức tạp, cần backward compatibility và observation discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu canary là gradual traffic exposure.

### Middle

Thiết lập deployment stages và health validation.

### Senior

Chọn guardrails, observation windows và schema compatibility strategy.

### Technical Lead / Architect

Thiết kế release architecture từ commit → artifact → staged deploy → monitor → rollback/roll-forward, cân bằng reliability với delivery speed.

## 11. Key takeaway

- Canary không chỉ là “deploy 5%”; nó cần measurable decision criteria.
- Một artifact phải được promote xuyên pipeline.
- Database/API compatibility quyết định khả năng rollback thực tế.

# 8. CPU profiling với flame graph: tìm hot path bằng evidence thay vì đoán

## 1. What is it?

CPU profiler lấy samples hoặc instrumentation để xác định code paths tiêu thụ CPU. Flame graph biểu diễn call stacks theo chiều rộng tương ứng lượng samples. Mental model: tìm nơi CPU thực sự dành thời gian, không tối ưu method trông “có vẻ nặng”.

## 2. Why does it exist?

CPU spike có thể đến từ serialization, regex, JSON mapping, lock contention spin, logging hoặc business algorithm. Source review đơn thuần không cho biết contribution dưới production workload.

## 3. How does it work?

Sampling profiler định kỳ ghi stack. Nhiều samples ở frame/path nghĩa là CPU time tập trung ở đó. Phải phân biệt inclusive time với self time và correlate với request/traffic change.

## 4. Practical implementation

Trên .NET có thể bắt đầu bằng metrics rồi profile có mục tiêu:

```bash
dotnet-counters monitor --process-id <pid> System.Runtime

dotnet-trace collect --process-id <pid> --duration 00:00:30
```

Phân tích trace bằng PerfView, Visual Studio hoặc công cụ tương thích. Production capture phải giới hạn duration/overhead và tuân policy dữ liệu.

## 5. Real production scenario

Sau release, CPU tăng từ 45% lên 85% nhưng request rate không đổi. Flame graph cho thấy phần lớn samples nằm ở custom JSON normalization mới, không phải SQL. Team tối ưu đúng code path thay vì scale database.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU cao. **Measure** → runtime/process metrics. **Localize** → profiler trace. **Hypothesis** → serializer hot path. **Test** → benchmark/canary revert. **Change** → giảm allocations/work. **Measure again** → CPU và p95 trở baseline. Nếu profile không đại diện traffic spike, capture lại đúng window.

## 7. Common mistakes

Profile dev workload khác production; nhìn self time mà bỏ inclusive path; tối ưu code hiếm chạy; capture quá lâu gây overhead; không so sánh trước/sau deployment.

## 8. Alternatives

BenchmarkDotNet tốt cho microbenchmark sau khi đã localize. `dotnet-counters` rẻ hơn để triage. APM traces giúp xác định request/dependency path nhưng không luôn đủ chi tiết CPU stack.

## 9. Trade-offs

### Advantages

Biến performance tuning thành evidence-driven process và tránh premature optimization.

### Costs / Risks

Profiling có overhead, dữ liệu lớn và cần kỹ năng diễn giải đúng workload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CPU cao cần measurement trước khi sửa code.

### Middle

Thu thập metrics/trace và đọc basic hot path.

### Senior

Phân biệt symptom, inclusive/self cost, allocation/CPU interaction và kiểm chứng thay đổi.

### Technical Lead / Architect

Thiết lập safe profiling/runbook và capacity/performance regression gates thay vì dựa vào heroic debugging.

## 11. Key takeaway

- Profile workload thật trước khi tối ưu.
- Flame graph chỉ có ý nghĩa trong context của traffic và time window.
- Mọi optimization phải được đo lại sau thay đổi.

# 9. CSRF + SameSite: cookie authentication cần browser-aware threat model

## 1. What is it?

CSRF là việc attacker khiến browser của victim gửi request tới site đã authenticated vì browser tự động đính kèm credentials như cookies. `SameSite` giới hạn một phần cross-site cookie sending nhưng không thay thế toàn bộ anti-forgery design.

## 2. Why does it exist?

Cookie authentication tiện vì browser tự gửi cookie. Chính tính tự động đó tạo risk: server có thể nhận valid session cookie trên request mà user không chủ ý tạo.

## 3. How does it work?

```text
Victim logged in -> auth cookie stored
Attacker page -> cross-site POST -> browser may attach cookie
Server sees authenticated request
```

Anti-forgery token yêu cầu một giá trị attacker site không thể tự tạo/đọc theo same-origin controls. `SameSite=Lax/Strict` giảm nhiều cross-site scenarios nhưng behavior phụ thuộc navigation/method/browser architecture.

## 4. Practical implementation

Với ASP.NET Core cookie-authenticated form/API, dùng built-in antiforgery theo application model và cookie policy phù hợp. State-changing endpoints không nên dùng `GET`.

```csharp
builder.Services.AddAntiforgery(o =>
{
    o.HeaderName = "X-CSRF-TOKEN";
});
```

SPA pattern cần endpoint/token flow được thiết kế rõ; đừng copy một header convention mà không hiểu framework validation.

## 5. Real production scenario

Internal admin portal dùng cookie auth. Một state-changing endpoint chấp nhận POST nhưng không validate antiforgery. User đang login có thể bị dẫn tới malicious page gửi form cross-site.

## 6. Failure scenario & troubleshooting

**Symptom** → Production trả 400 antiforgery nhưng local hoạt động. **Evidence** → cookie attributes/domain/HTTPS proxy khác nhau. **Hypothesis** → `Secure`, `SameSite`, forwarded scheme hoặc SPA token flow sai. **Diagnosis** → browser DevTools + server logs, kiểm tra cookie/header thực tế. **Fix** → sửa cookie/proxy/antiforgery configuration. **Verification** → valid same-site request pass, crafted cross-site request fail.

## 7. Common mistakes

Nghĩ CORS ngăn CSRF; dùng `SameSite=None` không `Secure`; state change bằng GET; disable antiforgery để “fix” 400; dùng bearer token trong cookie nhưng cho rằng nó tự hết CSRF risk.

## 8. Alternatives

Bearer token được client explicit attach trong `Authorization` header có threat model khác, nhưng XSS/token storage trở thành concern. SameSite strict có thể đủ cho một số flows nhưng có UX/integration consequences.

## 9. Trade-offs

### Advantages

Anti-forgery + cookie policy giảm unauthorized cross-site actions đáng kể.

### Costs / Risks

Thêm client/server coordination và dễ lỗi với cross-domain SSO/proxy nếu cấu hình thiếu hiểu biết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu authentication cookie hợp lệ không chứng minh user chủ ý gửi request.

### Middle

Implement antiforgery và debug cookie/header bằng browser tools.

### Senior

Phân tích SameSite, CORS, XSS và auth mechanism như các security controls khác nhau.

### Technical Lead / Architect

Chọn browser authentication architecture theo threat model, domain topology và SSO requirements; chuẩn hóa secure defaults cho teams.

## 11. Key takeaway

- CORS không phải CSRF protection.
- Cookie auto-attachment là nguồn gốc chính của CSRF threat.
- `SameSite` hữu ích nhưng phải nằm trong defense-in-depth design.

# 10. ADR: lưu architectural decision cùng context, alternatives và consequences

## 1. What is it?

Architecture Decision Record (ADR) là tài liệu ngắn ghi một quyết định kỹ thuật quan trọng, context tại thời điểm quyết định, alternatives và consequences. Mental model: ADR lưu “vì sao”, không thay thế source code hoặc full architecture document.

## 2. Why does it exist?

Sau sáu tháng, team thường biết hệ thống dùng Redis/Service Bus/CQRS nhưng không biết constraint nào dẫn tới lựa chọn đó. Khi context mất, người mới hoặc AI agent dễ “simplify” một quyết định từng bảo vệ requirement thật.

## 3. How does it work?

Một ADR thường có status, context, decision, alternatives và consequences. Nó immutable theo lịch sử: quyết định mới supersede ADR cũ thay vì rewrite quá khứ.

```text
Context -> Decision -> Consequences
             |
             +-> alternatives rejected + reasons
```

## 4. Practical implementation

```markdown
# ADR-014: Use transactional outbox for order events
Status: Accepted

## Context
Order commit and broker publish cannot be one local transaction.

## Decision
Persist integration events in SQL with the order transaction.

## Alternatives
- Direct publish after commit: dual-write gap.
- Distributed transaction: unsupported/operationally expensive.

## Consequences
Eventual publication, duplicate delivery, outbox cleanup/monitoring required.
```

ADR nên nằm gần repository/documentation workflow và được review cùng thay đổi kiến trúc.

## 5. Real production scenario

Team cân nhắc bỏ Redis vì “thêm complexity”. ADR cũ cho thấy Redis được thêm sau capacity incident với measured DB load và stale-data tolerance. Team có context để benchmark lại thay vì tranh luận theo ký ức.

## 6. Failure scenario & troubleshooting

**Symptom** → ADR repository đầy tài liệu nhưng không ai tin. **Evidence** → decisions không update status, không link implementation, template dài như design doc. **Diagnosis** → process tạo ceremony thay vì decision memory. **Fix** → chỉ record consequential decisions, giữ ngắn và supersede rõ. **Verification** → architecture review thực sự tham chiếu ADR khi thay đổi boundary.

## 7. Common mistakes

Ghi mọi code choice thành ADR; chỉ ghi quyết định mà không ghi alternatives; sửa ADR cũ để khớp hiện tại; không nêu operational consequences; biến ADR thành approval bureaucracy.

## 8. Alternatives

README/design doc phù hợp current architecture overview. PR discussion hữu ích cho implementation detail nhưng khó tìm lâu dài. Wiki có thể phù hợp cross-repo decisions nếu ownership/search tốt.

## 9. Trade-offs

### Advantages

Giữ institutional memory, làm trade-off explicit và hỗ trợ future review/migration.

### Costs / Risks

Documentation debt nếu quá nhiều, stale hoặc không gắn workflow.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Đọc ADR để hiểu lý do đằng sau architecture hiện tại.

### Middle

Đóng góp context/evidence và consequences cho decision.

### Senior

Viết ADR cho lựa chọn có trade-off thật và kiểm tra assumptions theo thời gian.

### Technical Lead / Architect

Quyết định cái gì đáng record, bảo đảm alternatives/operational burden/migration implications được nêu rõ và supersede decisions khi context đổi.

## 11. Key takeaway

- ADR lưu reasoning và trade-offs, không chỉ kết luận.
- Chỉ record decisions đủ consequential để future team cần context.
- Decision history nên được supersede, không rewrite để xóa context cũ.
