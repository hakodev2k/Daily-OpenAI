# 1. .NET ThreadPool starvation: phân biệt thiếu threads, sync-over-async và CPU saturation trong production

## 1. What is it?

ThreadPool starvation xảy ra khi application có nhiều work cần ThreadPool threads hơn số threads sẵn sàng xử lý trong một khoảng thời gian đủ dài, làm work mới phải xếp hàng dù process vẫn còn sống.

Mental model:

```text
Request arrives
   ↓
needs ThreadPool thread
   ↓
thread đang bị block / bận CPU
   ↓
request nằm trong queue
   ↓
latency tăng trước khi business code thực sự chạy
```

Starvation khác CPU saturation. CPU saturation nghĩa CPU thực sự đang làm quá nhiều work. Starvation thường xuất hiện khi threads bị giữ nhưng không làm việc hữu ích, ví dụ chờ I/O synchronously.

## 2. Why does it exist?

ASP.NET Core dựa mạnh vào asynchronous I/O để một số lượng threads hữu hạn phục vụ rất nhiều concurrent requests. Nếu code biến async operation thành blocking wait:

```csharp
var result = client.GetAsync(url).Result;
```

thread hiện tại bị giữ trong khi network I/O chưa hoàn tất. Khi traffic tăng, nhiều threads cùng bị block và request queue tăng nhanh.

ThreadPool có cơ chế tăng số threads theo thời gian, nhưng tốc độ tăng không tức thời và không thể sửa một workload fundamentally blocking.

## 3. How does it work?

Một flow tốt:

```text
Thread A starts I/O
   ↓
await releases Thread A
   ↓
I/O completes
   ↓
continuation được schedule trên một ThreadPool thread khác
```

Một flow xấu:

```text
Thread A starts I/O
   ↓
.Result waits synchronously
   ↓
Thread A bị giữ
   ↓
1000 requests => nhiều threads cùng bị giữ
```

ThreadPool starvation thường thể hiện bằng queue length tăng, request latency tăng và ThreadPool thread count tăng dần trong khi CPU có thể chưa chạm 100%.

## 4. Practical implementation

Giữ async xuyên call chain:

```csharp
public async Task<ProductDto?> GetProductAsync(
    Guid id,
    CancellationToken cancellationToken)
{
    using var response = await _httpClient.GetAsync(
        $"products/{id}",
        cancellationToken);

    response.EnsureSuccessStatusCode();

    return await response.Content.ReadFromJsonAsync<ProductDto>(
        cancellationToken: cancellationToken);
}
```

Tránh:

```csharp
var product = service.GetProductAsync(id, ct).Result;
```

Nếu có CPU-bound work thực sự lớn, không giả vờ giải quyết bằng `Task.Run()` cho mọi request. CPU-bound work cần throughput budget riêng, queueing hoặc background processing nếu phù hợp.

## 5. Real production scenario

Một API e-commerce gọi 3 downstream services. Một helper legacy dùng `.GetAwaiter().GetResult()` để gọi HTTP synchronously. Local test ổn. Khi production đạt vài trăm concurrent requests, p95 latency tăng từ 300 ms lên 8 giây dù SQL và downstream services vẫn healthy.

Root cause là request threads bị block chờ outbound I/O; ThreadPool phải tăng threads dần, tạo queue và context-switch overhead.

## 6. Failure scenario & troubleshooting

**Symptom** → p95/p99 tăng mạnh, request queue tăng, CPU chỉ 40–60%.

**Evidence** → runtime counters cho thấy ThreadPool queue length tăng, thread count tăng, nhiều stacks dừng ở `.Result`, `.Wait()` hoặc blocking I/O.

**Hypothesis** → sync-over-async hoặc blocking work đang giữ ThreadPool threads.

**Diagnosis** → lấy traces/thread dumps, tìm blocking call sites, so sánh ThreadPool counters với CPU và dependency latency.

**Fix** → async all the way, giới hạn blocking dependencies, tách CPU-heavy work khỏi request path.

**Verification** → load test cùng concurrency; queue length phải ổn định và latency không tăng theo kiểu stair-step.

## 7. Common mistakes

* Thấy starvation rồi tăng `MinThreads` ngay lập tức mà không tìm blocking source.
* Bọc synchronous I/O bằng `Task.Run()` trong web request và gọi đó là async.
* Chỉ nhìn CPU rồi kết luận application không có capacity issue.
* Không propagate `CancellationToken`, khiến abandoned work tiếp tục giữ resources.
* Dùng lock dài quanh I/O.

## 8. Alternatives

Nếu library bắt buộc synchronous, có thể cô lập nó bằng bounded worker pool. Với CPU-heavy workload, queue/background worker hoặc dedicated compute service có thể hợp lý hơn. Nếu bottleneck là downstream connection pool, ThreadPool tuning không giải quyết được.

## 9. Trade-offs

### Advantages

Async I/O cho phép throughput cao với ít threads hơn và giảm queueing.

### Costs / Risks

Async call chain phức tạp hơn nếu codebase legacy. Bounded concurrency cần thiết để tránh biến async thành unbounded fan-out. Tăng ThreadPool threads có thể giảm symptom ngắn hạn nhưng làm context switching và downstream pressure lớn hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` không có nghĩa tạo thread mới và `.Result` có thể block thread.

### Middle

Biết giữ async xuyên controller/service/repository/integration path và đọc runtime counters cơ bản.

### Senior

Phân biệt starvation, CPU saturation, lock contention, connection-pool exhaustion và downstream latency.

### Technical Lead / Architect

Thiết kế concurrency budgets, isolate blocking dependencies và quyết định khi nào workload phải rời request path.

## 11. Key takeaway

* ThreadPool starvation thường là queueing problem do threads bị giữ sai cách.
* CPU thấp không chứng minh application còn nhiều capacity.
* Sửa root cause bằng async I/O, bounded concurrency và đúng workload boundary trước khi tuning ThreadPool.

# 2. ASP.NET Core rate limiting: partitioned policies, queueing và cách tránh biến limiter thành nguồn latency mới

## 1. What is it?

Rate limiting kiểm soát số requests được phép đi qua trong một đơn vị thời gian hoặc số concurrent operations tại một thời điểm.

Mental model:

```text
Incoming requests
      ↓
partition key: user / API key / IP / tenant
      ↓
rate limiter policy
      ↓
Permit | Queue | Reject
```

Limiter không chỉ bảo vệ server khỏi traffic xấu. Nó còn bảo vệ downstream systems khỏi load vượt khả năng xử lý.

## 2. Why does it exist?

Nếu một tenant gửi 10.000 requests/second vào API chỉ chịu được 2.000, toàn hệ thống có thể degrade cho tất cả users. Không có admission control, request queue chỉ chuyển overload từ edge vào ThreadPool, SQL hoặc downstream APIs.

## 3. How does it work?

ASP.NET Core có thể áp dụng fixed window, sliding window, token bucket hoặc concurrency limiting. Partitioning cho phép mỗi key có bucket riêng thay vì một global limit duy nhất.

Ví dụ với API key:

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(
        context =>
        {
            var key = context.Request.Headers["X-Api-Key"].ToString();

            return RateLimitPartition.GetTokenBucketLimiter(
                partitionKey: string.IsNullOrWhiteSpace(key) ? "anonymous" : key,
                factory: _ => new TokenBucketRateLimiterOptions
                {
                    TokenLimit = 100,
                    TokensPerPeriod = 50,
                    ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                    QueueLimit = 20,
                    AutoReplenishment = true
                });
        });
});
```

## 4. Practical implementation

Một production policy cần định nghĩa:

```text
who is limited?
what unit is protected?
how much burst is allowed?
queue or reject?
what status code and headers are returned?
what telemetry is emitted?
```

Rejection thường dùng `429 Too Many Requests`. Khi có retry guidance hợp lý, trả `Retry-After`.

Queue chỉ nên ngắn. Queue dài biến overload thành latency spike và có thể làm request hết timeout trước khi được xử lý.

## 5. Real production scenario

Một partner integration poll inventory API quá nhanh. Không có limiter, SQL CPU tăng và latency tăng cho website chính. Sau khi limit theo partner API key, website giữ được SLO trong khi partner nhận `429` và phải back off.

## 6. Failure scenario & troubleshooting

**Symptom** → error rate thấp nhưng p99 latency tăng cực cao khi traffic spike.

**Evidence** → nhiều requests nằm trong limiter queue; downstream metrics vẫn chưa overload.

**Hypothesis** → queue limit hoặc queue wait time quá lớn.

**Diagnosis** → đo accepted/rejected/queued requests, queue duration, request timeout và per-partition traffic.

**Fix** → giảm queue, reject sớm hơn, điều chỉnh burst budget theo downstream capacity.

**Verification** → load test overload case; latency của accepted requests phải bounded và rejected requests phải fail fast.

## 7. Common mistakes

* Limit theo IP cho authenticated SaaS users phía sau NAT rồi vô tình gom nhiều users vào một bucket.
* Global limit làm tenant lớn ảnh hưởng tenant nhỏ.
* Queue hàng nghìn requests vì muốn “không reject ai”.
* Retry client ngay lập tức không jitter.
* Không rate-limit expensive endpoints riêng.

## 8. Alternatives

Rate limiting ở API gateway/CDN giảm load trước khi vào app. Concurrency limiter phù hợp operation đắt theo thời lượng. Queue-based load leveling tốt cho asynchronous work. Circuit Breaker giải quyết downstream failure, không thay thế admission control.

## 9. Trade-offs

### Advantages

* Bảo vệ capacity và downstream dependencies.
* Tạo fairness giữa tenants/clients.
* Giúp overload behavior predictable.

### Costs / Risks

* Chọn key và quota sai gây false throttling.
* Distributed rate limiting cần shared state hoặc gateway support.
* Queueing có thể che overload bằng latency thay vì error.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `429` và mục đích của rate limiting.

### Middle

Cấu hình policy theo endpoint/client và thêm telemetry.

### Senior

Tính burst, queue, retry behavior và ảnh hưởng lên downstream capacity.

### Technical Lead / Architect

Quyết định enforcement layer: CDN, gateway, application hay nhiều lớp; gắn quota với business/SLO thay vì số ngẫu nhiên.

## 11. Key takeaway

* Rate limiting là admission control, không chỉ anti-abuse.
* Partition key quyết định fairness.
* Queue ngắn và rejection rõ ràng thường tốt hơn overload âm thầm bằng latency.

# 3. EF Core single query vs split query: Cartesian explosion, round trips và cách chọn chiến lược loading theo shape dữ liệu

## 1. What is it?

Khi `Include` nhiều collection navigations, EF Core có thể load graph bằng một SQL query lớn hoặc split thành nhiều queries.

Mental model:

```text
Single query
Parent JOIN ChildrenA JOIN ChildrenB

Split query
Parent
ChildrenA
ChildrenB
```

Single query giảm round trips nhưng có thể nhân số rows. Split query giảm row duplication nhưng thực hiện nhiều database commands.

## 2. Why does it exist?

Giả sử một Order có 20 Lines và 10 Notes. Join cả hai collections có thể tạo tới 200 result rows cho một Order trước khi EF materialize lại object graph. Payload và database work tăng dù logical data ít hơn nhiều.

## 3. How does it work?

Single query:

```csharp
var order = await db.Orders
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .SingleAsync(x => x.Id == id, ct);
```

Split query:

```csharp
var order = await db.Orders
    .AsSplitQuery()
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .SingleAsync(x => x.Id == id, ct);
```

EF Core fix-up kết hợp kết quả thành graph cuối cùng.

## 4. Practical implementation

Trước hết hỏi liệu có thật sự cần full entity graph không. Với read-only endpoint, projection thường tốt hơn:

```csharp
var dto = await db.Orders
    .Where(x => x.Id == id)
    .Select(x => new OrderDetailsDto(
        x.Id,
        x.Number,
        x.Lines.Select(l => new OrderLineDto(l.Id, l.Quantity)).ToList(),
        x.Notes.Select(n => n.Text).ToList()))
    .SingleAsync(ct);
```

Nếu vẫn cần graph, đo generated SQL, row counts và round trips trước khi chọn split/single.

## 5. Real production scenario

Một back-office screen load Project + Tasks + Comments + Attachments. Single query tạo hàng chục nghìn rows cho một project lớn và payload DB vượt nhiều MB. Chuyển sang split query giảm data duplication đáng kể nhưng tăng số commands. Sau đó team dùng projection cho screen cụ thể và đạt kết quả tốt hơn cả hai.

## 6. Failure scenario & troubleshooting

**Symptom** → query chỉ load vài entities nhưng database trả hàng chục nghìn rows.

**Evidence** → SQL có nhiều sibling collection joins và actual row count lớn.

**Hypothesis** → Cartesian explosion.

**Diagnosis** → xem generated SQL, execution plan, result-set size và materialization cost.

**Fix** → projection, split query hoặc tách use case; không load graph mặc định.

**Verification** → so sánh DB reads, bytes transferred, query count và end-to-end latency.

## 7. Common mistakes

* Dùng `Include` như checkbox cho mọi navigation.
* Chọn `AsSplitQuery()` mặc định mà không tính round trips.
* Load entities chỉ để map ra DTO.
* Bỏ qua consistency giữa nhiều split queries nếu dữ liệu thay đổi đồng thời.
* Benchmark trên dataset nhỏ.

## 8. Alternatives

Projection là lựa chọn tốt cho read models. Explicit queries phù hợp complex use case cần kiểm soát data shape. Dapper/raw SQL hữu ích khi cần SQL shape cực cụ thể, nhưng đổi lấy abstraction thấp hơn.

## 9. Trade-offs

### Advantages

Single query: ít round trips.

Split query: ít duplication hơn cho nhiều collections.

Projection: data shape nhỏ và rõ nhất khi endpoint chỉ cần DTO.

### Costs / Risks

Single query có Cartesian explosion. Split query tăng commands và có consistency considerations. Projection cần mapping theo use case.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` làm SQL và payload lớn hơn.

### Middle

Biết đọc generated SQL, dùng `AsSplitQuery()` và projection.

### Senior

Đánh giá query shape, round trips, consistency và materialization overhead.

### Technical Lead / Architect

Đặt guideline: entity graph cho command/domain use cases, read-model projection cho query-heavy API khi phù hợp.

## 11. Key takeaway

* Loading strategy phụ thuộc data shape, không có lựa chọn tốt cho mọi query.
* Nhiều sibling collections là tín hiệu cần kiểm tra Cartesian explosion.
* Projection thường là bước đầu tiên cho read-only API.

# 4. SQL Server keyset pagination: tại sao `OFFSET/FETCH` chậm dần và cách giữ latency ổn định trên bảng lớn

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên giá trị cuối cùng của trang trước thay vì “bỏ qua N rows”.

Offset:

```sql
ORDER BY CreatedAt, Id
OFFSET 500000 ROWS FETCH NEXT 50 ROWS ONLY;
```

Keyset:

```sql
WHERE CreatedAt > @lastCreatedAt
   OR (CreatedAt = @lastCreatedAt AND Id > @lastId)
ORDER BY CreatedAt, Id
FETCH NEXT 50 ROWS ONLY;
```

## 2. Why does it exist?

Với offset pagination, database vẫn phải locate/scan qua phần dữ liệu bị bỏ qua. Khi page number tăng rất lớn, cost thường tăng theo offset.

Keyset cho phép seek từ bookmark gần vị trí cần đọc nếu index phù hợp.

## 3. How does it work?

Một index phù hợp:

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON Orders (CreatedAt, Id)
INCLUDE (Number, Status, Total);
```

Query có thể seek theo `(CreatedAt, Id)` thay vì skip hàng trăm nghìn rows.

Tie-breaker `Id` rất quan trọng vì `CreatedAt` có thể trùng nhau.

## 4. Practical implementation

API cursor có thể encode last sort values:

```json
{
  "createdAt": "2026-09-09T09:30:00Z",
  "id": 182734
}
```

Server validate cursor và query:

```sql
SELECT TOP (@pageSize)
    Id, Number, Status, Total, CreatedAt
FROM Orders
WHERE CreatedAt > @createdAt
   OR (CreatedAt = @createdAt AND Id > @id)
ORDER BY CreatedAt, Id;
```

Cursor có thể ký/encode opaque để client không phụ thuộc internal sorting details.

## 5. Real production scenario

Một audit table có 80 triệu rows. UI cho phép browse lịch sử. Page 1 nhanh, page 5000 mất nhiều giây với `OFFSET`. Chuyển sang cursor/keyset giữ latency gần ổn định vì query seek từ last key.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng tuyến tính theo page number.

**Evidence** → execution plan đọc rất nhiều rows rồi bỏ chúng.

**Hypothesis** → large offset pagination.

**Diagnosis** → đo logical reads giữa page đầu và page sâu, xem seek/scan behavior.

**Fix** → keyset pagination với stable sort key và matching index.

**Verification** → benchmark page đầu, giữa và rất sâu trên production-like data.

## 7. Common mistakes

* Keyset bằng `CreatedAt` nhưng không có tie-breaker.
* Sort direction không match cursor predicate.
* Cho arbitrary sort columns nhưng chỉ có một index.
* Cần jump trực tiếp tới page 10.000 nhưng vẫn kỳ vọng keyset hoạt động như offset.
* Cursor chứa mutable field khiến thứ tự thay đổi trong khi user paging.

## 8. Alternatives

Offset pagination đơn giản và hợp lý cho dataset nhỏ hoặc admin UI ít page. Search engines có search-after semantics tương tự keyset. Snapshot/export tốt hơn nếu user cần duyệt toàn bộ dataset ổn định.

## 9. Trade-offs

### Advantages

* Latency ổn định hơn ở deep pages.
* Ít logical reads nếu index phù hợp.
* Tốt cho infinite scroll/feed.

### Costs / Risks

* Không thuận tiện cho random page jump.
* Cursor design phức tạp hơn.
* Sort key phải stable và deterministic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `OFFSET` không miễn phí.

### Middle

Implement cursor theo stable sort key và index tương ứng.

### Senior

Đánh giá consistency khi rows được insert/update trong lúc paging.

### Technical Lead / Architect

Chọn pagination contract theo user experience và data size thay vì expose page number theo thói quen.

## 11. Key takeaway

* Deep offset thường tạo work tỷ lệ với số rows bỏ qua.
* Keyset pagination biến “skip N” thành index seek từ bookmark.
* Stable ordering và matching index là điều kiện bắt buộc.

# 5. Transactional Outbox với EF Core + messaging: đóng khoảng trống giữa database commit và message publish

## 1. What is it?

Transactional Outbox lưu business data và event/message cần publish trong cùng một local database transaction. Một background dispatcher sau đó đọc Outbox và gửi message ra broker.

Mental model:

```text
Business transaction
 ├─ UPDATE Order
 └─ INSERT OutboxMessage
        ↓ same DB transaction
commit
        ↓
Dispatcher
        ↓
Service Bus / broker
```

## 2. Why does it exist?

Anti-pattern:

```text
Save DB
then Publish message
```

Nếu process crash sau DB commit nhưng trước publish, state đã thay đổi nhưng event bị mất.

Đảo lại:

```text
Publish
then Save DB
```

cũng có thể gửi event dù DB transaction sau đó fail.

Không có distributed transaction đáng tin cậy giữa arbitrary database và broker trong nhiều kiến trúc hiện đại, nên Outbox giải quyết bằng durable local state + eventual publish.

## 3. How does it work?

Trong transaction:

```csharp
order.MarkPaid();

db.OutboxMessages.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    Type = "OrderPaid",
    Payload = JsonSerializer.Serialize(new OrderPaid(order.Id)),
    OccurredAtUtc = DateTime.UtcNow
});

await db.SaveChangesAsync(ct);
```

Dispatcher:

```csharp
var batch = await db.OutboxMessages
    .Where(x => x.ProcessedAtUtc == null)
    .OrderBy(x => x.OccurredAtUtc)
    .Take(100)
    .ToListAsync(ct);
```

Sau publish thành công, mark processed.

## 4. Practical implementation

Production implementation cần thêm:

* idempotent consumer
* retry/backoff
* poison message handling
* lock/claim mechanism để nhiều dispatcher không xử lý cùng row vô hạn
* observability cho oldest pending message
* retention/cleanup

Outbox không tạo exactly-once delivery. Crash sau broker publish nhưng trước mark processed có thể publish duplicate.

## 5. Real production scenario

Order API ghi `PaymentCaptured` vào DB rồi publish `OrderPaid`. Một deployment restart đúng giữa hai bước. Trước Outbox, fulfillment không nhận event và order bị kẹt. Với Outbox, message vẫn còn trong DB và dispatcher gửi lại sau restart.

## 6. Failure scenario & troubleshooting

**Symptom** → business state đúng nhưng downstream không cập nhật.

**Evidence** → Outbox backlog tăng, oldest pending age lớn.

**Hypothesis** → dispatcher hoặc broker publish đang fail.

**Diagnosis** → kiểm tra outbox pending count, dispatcher logs/traces, Service Bus errors và retry state.

**Fix** → khôi phục dispatcher, xử lý poison payload, tránh xóa outbox trước ack thành công.

**Verification** → simulate crash ở từng boundary: trước commit, sau commit, sau publish, trước mark processed.

## 7. Common mistakes

* Nghĩ Outbox cho exactly-once.
* Không làm consumer idempotent.
* Dispatcher query toàn table không index.
* Không cleanup processed rows.
* Serialize domain object trực tiếp khiến schema coupling lớn.
* Không monitor backlog age.

## 8. Alternatives

Nếu chỉ một database, local transaction đơn giản hơn. Change Data Capture có thể tạo integration stream từ DB nhưng operational model khác. Workflow engine có thể durable hơn cho long-running orchestration. Broker transaction chỉ hữu ích nếu tất cả operations nằm trong cùng transaction boundary được hỗ trợ.

## 9. Trade-offs

### Advantages

* Không mất message giữa DB commit và publish.
* Recovery tự nhiên sau process restart.
* Không cần distributed transaction toàn cục.

### Costs / Risks

* Eventual consistency.
* Duplicate delivery vẫn có thể xảy ra.
* Thêm dispatcher, storage, cleanup và monitoring.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu failure window của `SaveChanges` rồi `Publish`.

### Middle

Implement outbox table + dispatcher + retry.

### Senior

Thiết kế idempotency, concurrency claim, poison handling và schema versioning.

### Technical Lead / Architect

Quyết định khi nào business flow thực sự cần messaging; đánh giá operational cost của Outbox thay vì dùng mặc định.

## 11. Key takeaway

* Outbox đóng khoảng trống giữa local DB transaction và external broker.
* At-least-once publish nghĩa consumer vẫn phải idempotent.
* Backlog age là production signal quan trọng hơn chỉ “dispatcher process đang chạy”.

# 6. Azure Blob Storage upload architecture: SAS, Managed Identity, large-file streaming và failure recovery

## 1. What is it?

Azure Blob Storage là object storage cho files/blobs. Trong web architecture, một quyết định quan trọng là file đi qua application server hay client upload trực tiếp tới Blob Storage bằng scoped SAS.

Mental model trực tiếp:

```text
Browser
  ↓ request upload authorization
API
  ↓ generates scoped permission
Browser ─────────────→ Blob Storage
```

## 2. Why does it exist?

Nếu user upload file 5 GB qua ASP.NET Core rồi API forward sang Blob Storage, application trở thành data pipe: tốn bandwidth, memory/buffer, connection duration và scale unit không cần thiết.

Direct-to-Blob upload giảm load trên app nhưng phải kiểm soát authorization và file lifecycle.

## 3. How does it work?

Backend có thể authenticate user rồi tạo short-lived SAS chỉ cho blob/container path cụ thể. Trong Azure-hosted backend, ưu tiên Managed Identity để backend truy cập Storage thay vì lưu account key.

Pseudo flow:

```text
1. User authenticated to API
2. API validates "user may upload document X"
3. API issues short-lived scoped SAS
4. Browser uploads blocks directly
5. Browser/API confirms completion
6. Background validation/scanning marks file usable
```

## 4. Practical implementation

Backend không nên cấp SAS rộng kiểu full container write/delete trong nhiều giờ. Scope nên tối thiểu về resource, permissions và expiry.

Large file nên dùng block blob/chunking để retry từng block thay vì restart toàn upload. Metadata DB nên phân biệt:

```text
PendingUpload
Uploaded
Scanning
Ready
Rejected
```

để không coi object vừa xuất hiện là business-valid ngay lập tức.

## 5. Real production scenario

Một document portal cho upload videos 2–10 GB. Version đầu proxy toàn file qua App Service khiến instances giữ request hàng chục phút và scale-out mạnh. Chuyển sang direct SAS upload giảm app bandwidth đáng kể; API chỉ quản lý permission và metadata.

## 6. Failure scenario & troubleshooting

**Symptom** → DB ghi file `Ready` nhưng blob không tồn tại hoặc upload chưa hoàn tất.

**Evidence** → metadata transaction và blob upload không atomic.

**Hypothesis** → business state được commit trước khi storage operation xác nhận.

**Diagnosis** → correlate upload ID, blob path, status transitions và storage request IDs.

**Fix** → state machine `Pending → Uploaded → Validated/Ready`, cleanup abandoned uploads và idempotent completion endpoint.

**Verification** → test browser disconnect, expired SAS, partial upload, duplicate completion request và storage timeout.

## 7. Common mistakes

* Cấp account key cho application/client khi Managed Identity/SAS phù hợp hơn.
* SAS expiry quá dài hoặc permissions quá rộng.
* Đọc toàn file vào memory trước khi upload.
* Tin content type/file extension từ client.
* Không virus/malware scan cho file không tin cậy.
* Không cleanup orphan blobs.

## 8. Alternatives

API-proxied upload vẫn hợp lý cho files nhỏ hoặc khi application bắt buộc transform stream inline. Azure Files phù hợp filesystem semantics hơn object storage. CDN/Front Door hỗ trợ delivery nhưng không thay authorization/upload workflow.

## 9. Trade-offs

### Advantages

* Direct upload giảm app bandwidth và request duration.
* Blob Storage scale tốt cho large objects.
* Managed Identity giảm secret management.

### Costs / Risks

* Upload workflow trở thành multi-step distributed state.
* Cần cleanup, validation và eventual consistency giữa DB với Blob.
* SAS policy sai có thể thành security exposure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Blob khác filesystem local và SAS là scoped permission.

### Middle

Implement chunked upload, metadata status và cancellation/retry.

### Senior

Thiết kế security scope, orphan cleanup, scanning và failure recovery.

### Technical Lead / Architect

Quyết định data path: browser→Blob hay browser→API→Blob dựa trên file size, security, transformation và operational cost.

## 11. Key takeaway

* Large-file architecture nên tránh biến web server thành byte relay nếu không cần.
* SAS phải ngắn hạn và least-privilege.
* File existence không đồng nghĩa business-valid; cần lifecycle state rõ ràng.

# 7. OpenTelemetry context propagation: TraceId, SpanId, Baggage và cách correlation bị vỡ qua HTTP/message boundaries

## 1. What is it?

Distributed tracing nối nhiều operations trong một request/workflow bằng trace context. `TraceId` đại diện cho toàn trace, `SpanId` cho từng operation. Context propagation truyền các identifiers qua process/service boundaries.

Mental model:

```text
Client request
TraceId = A
  API span = 1
    SQL span = 2
    HTTP span = 3
      downstream span = 4
```

Nếu propagation bị mất, downstream tạo TraceId mới và incident investigation bị chia thành nhiều traces rời rạc.

## 2. Why does it exist?

Trong distributed system, timestamp gần nhau không đủ để biết request nào gây query hay message nào. Correlation cần được truyền có cấu trúc và theo standard.

## 3. How does it work?

W3C Trace Context dùng headers như `traceparent`. Instrumentation libraries inject/extract context qua HTTP automatically khi hỗ trợ.

Messaging cần inject context vào message properties/headers rồi extract ở consumer.

`Baggage` mang contextual key/value xuyên trace, nhưng không nên chứa secrets hoặc PII vì nó có thể truyền qua nhiều services.

## 4. Practical implementation

Trong .NET, dùng `ActivitySource` cho custom spans:

```csharp
private static readonly ActivitySource ActivitySource =
    new("Orders.Application");

public async Task ProcessAsync(Guid orderId, CancellationToken ct)
{
    using var activity = ActivitySource.StartActivity("ProcessOrder");
    activity?.SetTag("order.id", orderId);

    await _repository.LoadAsync(orderId, ct);
}
```

Đừng tự tạo correlation header riêng nếu standard propagation đã giải quyết được.

## 5. Real production scenario

Order API gọi Pricing, Inventory và Payment rồi publish message. HTTP traces liên kết đúng nhưng message consumer tạo trace mới vì producer không inject context vào Service Bus properties. Incident timeline bị chia đôi giữa synchronous request và async fulfillment.

## 6. Failure scenario & troubleshooting

**Symptom** → trace dừng ở producer; consumer có trace mới không liên kết.

**Evidence** → message properties không có propagated trace context hoặc consumer instrumentation không extract.

**Hypothesis** → context mất qua messaging boundary.

**Diagnosis** → inspect message metadata, instrumentation versions và exporter pipeline.

**Fix** → dùng supported propagation/instrumentation; nếu custom transport, inject/extract standard context đúng cách.

**Verification** → end-to-end test HTTP → broker → consumer và kiểm tra cùng TraceId/linked trace semantics theo thiết kế.

## 7. Common mistakes

* Tạo `CorrelationId` custom nhưng không nối với tracing system.
* Đưa email/token/user secret vào Baggage.
* Tạo quá nhiều spans cho trivial operations làm telemetry cost tăng.
* Không propagate qua background queue.
* Log TraceId nhưng logs/traces dùng timestamp/timezone khác khó correlate.

## 8. Alternatives

Correlation ID đơn giản có thể đủ cho monolith hoặc integration nhỏ. Structured logs hữu ích nhưng không thay span timing/dependency graph. Metrics cho aggregate health, traces cho request-level causality.

## 9. Trade-offs

### Advantages

* End-to-end causality rõ hơn.
* Tìm latency và failure propagation nhanh hơn.
* Standard W3C tránh proprietary correlation format.

### Costs / Risks

* Telemetry volume/cost.
* Context propagation cần support ở mọi transport.
* Baggage misuse có privacy/security risk.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu TraceId và SpanId khác nhau.

### Middle

Thêm instrumentation và custom tags/spans hợp lý.

### Senior

Debug context loss qua HTTP, messaging và background processing.

### Technical Lead / Architect

Đặt telemetry conventions, sampling, privacy boundaries và ownership cho cross-service observability.

## 11. Key takeaway

* Distributed tracing chỉ hữu ích nếu context sống xuyên mọi boundary quan trọng.
* `Baggage` là propagation mechanism, không phải nơi chứa sensitive data.
* Logs, metrics và traces bổ sung cho nhau chứ không thay thế nhau.

# 8. Expand-and-contract database migration: deploy schema thay đổi mà không khóa release pipeline hoặc phá version cũ

## 1. What is it?

Expand-and-contract là chiến lược thay đổi schema theo nhiều bước backward-compatible thay vì deploy application và destructive schema change trong một lần.

Mental model:

```text
Expand: add new schema compatible with old app
   ↓
Migrate/dual-read or dual-write as needed
   ↓
Deploy new app version
   ↓
Contract: remove old schema after no consumers remain
```

## 2. Why does it exist?

Trong rolling/blue-green deployment, version cũ và mới có thể chạy đồng thời. Nếu migration rename/drop column trước khi version cũ dừng, old instances có thể crash ngay lập tức.

Database thường là shared state nên deployment compatibility cần được thiết kế như API compatibility.

## 3. How does it work?

Ví dụ muốn rename `CustomerName` thành `DisplayName`.

Sai:

```sql
EXEC sp_rename 'Customers.CustomerName', 'DisplayName', 'COLUMN';
```

ngay trước rolling deploy.

Expand-and-contract:

```text
1. Add DisplayName nullable
2. New app writes both fields / reads fallback
3. Backfill existing rows
4. Deploy all consumers to DisplayName
5. Stop dual-write
6. Drop CustomerName later
```

## 4. Practical implementation

Migration 1:

```sql
ALTER TABLE Customers
ADD DisplayName nvarchar(200) NULL;
```

Backfill in bounded batches để tránh long locks/log growth:

```sql
UPDATE TOP (5000) Customers
SET DisplayName = CustomerName
WHERE DisplayName IS NULL;
```

Application compatibility window phải được document và monitor.

## 5. Real production scenario

Một SaaS rolling deploy 10 instances. Team drop column cũ trong migration chạy ở instance đầu tiên. 9 old instances tiếp tục query column đó và trả 500 cho tới khi deployment hoàn tất. Với expand-contract, cả hai versions sống an toàn trong rollout window.

## 6. Failure scenario & troubleshooting

**Symptom** → deploy mới thành công một phần nhưng old instances bắt đầu SQL errors.

**Evidence** → schema không còn field old version cần.

**Hypothesis** → destructive migration chạy trước khi compatibility window kết thúc.

**Diagnosis** → compare schema migration order với application rollout order.

**Fix** → restore compatible schema hoặc rollback application; chuyển migration thành additive steps.

**Verification** → test old+new versions song song trên schema expand state trước production.

## 7. Common mistakes

* Rename/drop column trong cùng release với code đổi.
* Backfill hàng trăm triệu rows trong một transaction.
* Dual-write nhưng không monitor divergence.
* Giữ compatibility code vĩnh viễn không contract.
* Cho mỗi app instance tự chạy heavy migration khi startup.

## 8. Alternatives

Maintenance window + coordinated downtime có thể đơn giản hơn nếu business cho phép. New database/versioned store phù hợp major redesign nhưng operational cost cao. Feature flag hỗ trợ rollout logic nhưng không tự giải quyết schema compatibility.

## 9. Trade-offs

### Advantages

* Giảm coupling giữa schema deploy và app rollout.
* Hỗ trợ rolling/blue-green/canary an toàn hơn.
* Rollback application dễ hơn.

### Costs / Risks

* Nhiều deployment steps.
* Temporary duplicate fields/logic.
* Backfill và cleanup cần ownership rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu migration có thể phá version đang chạy.

### Middle

Viết additive migration và batch backfill.

### Senior

Thiết kế compatibility window, dual-write/read và rollback path.

### Technical Lead / Architect

Đặt deployment contract giữa schema, app versions và dependent services; chọn downtime nếu nó đơn giản và business chấp nhận được.

## 11. Key takeaway

* Database schema cũng cần backward compatibility trong zero/low-downtime deployment.
* Add → migrate → switch → remove an toàn hơn destructive one-shot change.
* Cleanup là một phase thật sự, không phải việc “để sau”.

# 9. Frontend authentication token storage: cookie, `localStorage`, XSS, CSRF và boundary đúng giữa browser với backend

## 1. What is it?

Browser authentication thường cần lưu credential/session material giữa requests. Hai lựa chọn hay gặp là cookie hoặc browser storage như `localStorage`.

Không có câu trả lời “cookie luôn an toàn” hay “JWT trong localStorage luôn đúng”. Security phụ thuộc threat model và cách token được gửi.

## 2. Why does it exist?

Browser phải chứng minh identity ở các requests sau login. Nhưng nơi lưu credential quyết định attack surface:

```text
localStorage token
  → JavaScript đọc được
  → XSS có thể lấy token

HttpOnly cookie
  → JavaScript không đọc được
  → browser tự gửi cookie
  → phải xử lý CSRF nếu authentication dựa trên cookie
```

## 3. How does it work?

HttpOnly/Secure/SameSite cookie giảm khả năng JavaScript đọc session token trực tiếp. Nhưng browser tự attach cookie vào request theo scope, vì vậy CSRF protections vẫn quan trọng tùy `SameSite` và cross-site flows.

`localStorage` không tự attach vào request; app thêm bearer token vào `Authorization`. Điều đó giảm classic cookie-CSRF surface nhưng token có thể bị exfiltrate nếu XSS chạy trong origin.

## 4. Practical implementation

Một BFF-style architecture có thể giữ OAuth/OIDC tokens server-side và browser chỉ giữ secure session cookie:

```text
Browser
  ↓ HttpOnly session cookie
BFF / ASP.NET Core
  ↓ access token server-side
Downstream API
```

Điều này giảm token exposure trong JavaScript, nhưng BFF trở thành security-critical component và cần CSRF protection cho unsafe cookie-authenticated operations.

## 5. Real production scenario

SPA lưu refresh token trong `localStorage`. Một XSS từ third-party script compromise origin và lấy token, attacker dùng refresh token ngoài browser trong thời gian dài. Team chuyển sang BFF + HttpOnly cookie và giảm lifetime/scope của tokens.

## 6. Failure scenario & troubleshooting

**Symptom** → authenticated state-changing request có thể bị trigger từ malicious site.

**Evidence** → cookie tự gửi cross-site và endpoint không có anti-CSRF strategy phù hợp.

**Hypothesis** → hệ thống coi CORS là CSRF protection.

**Diagnosis** → kiểm tra cookie `SameSite`, request method, anti-forgery token/origin checks và CORS config.

**Fix** → dùng SameSite phù hợp, CSRF token/origin validation cho unsafe requests và không dựa vào CORS một mình.

**Verification** → security test cross-site form/fetch scenarios và XSS assumptions riêng biệt.

## 7. Common mistakes

* Lưu long-lived refresh token trong `localStorage` mà không đánh giá XSS risk.
* Nghĩ `HttpOnly` cookie tự động giải quyết CSRF.
* Nghĩ CORS chặn browser gửi mọi cross-site request.
* Access token quá dài hạn và scope quá rộng.
* Log token trong frontend error telemetry.

## 8. Alternatives

Pure SPA + Authorization Code with PKCE có thể phù hợp khi không dùng BFF, nhưng cần token-lifetime và storage strategy cẩn thận. Server-rendered app với session cookie đơn giản hơn cho nhiều enterprise apps. BFF tăng backend complexity nhưng giảm token exposure ở browser.

## 9. Trade-offs

### Advantages

BFF/HttpOnly cookie giảm JavaScript access tới tokens. Bearer token trong SPA có API decoupling tốt hơn.

### Costs / Risks

Cookie auth cần CSRF reasoning. SPA token storage cần XSS hardening mạnh. BFF thêm infrastructure và session state/scale considerations.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu XSS và CSRF là hai threat khác nhau.

### Middle

Cấu hình cookie flags, authorization header và token lifetime đúng.

### Senior

Đánh giá browser storage, refresh token theft, CSRF, XSS và third-party scripts.

### Technical Lead / Architect

Chọn SPA/BFF/session architecture dựa trên threat model, deployment topology và identity provider constraints.

## 11. Key takeaway

* Nơi lưu token quyết định attack surface khác nhau.
* `HttpOnly` giảm XSS token theft nhưng không thay CSRF defense.
* BFF là architectural trade-off, không phải security magic.

# 10. AI Tool Calling trong backend: tách model reasoning khỏi deterministic validation, authorization và business rules

## 1. What is it?

Tool Calling cho phép LLM chọn một tool/function và sinh arguments có cấu trúc để application thực thi. Model đề xuất hành động; application quyết định hành động đó có hợp lệ và được phép hay không.

Mental model đúng:

```text
User intent
   ↓
LLM chooses tool + arguments
   ↓
Application validates
   ↓
Authorization/business rules
   ↓
Tool executes
   ↓
Result returned to model/user
```

Không nên coi model output là trusted command.

## 2. Why does it exist?

LLM mạnh ở interpretation và natural-language reasoning nhưng probabilistic. Business systems cần deterministic enforcement cho permission, money, inventory, deletion hoặc secrets.

Tool Calling tạo boundary rõ giữa probabilistic intent resolution và deterministic execution.

## 3. How does it work?

Tool schema mô tả arguments:

```json
{
  "name": "create_refund",
  "parameters": {
    "type": "object",
    "properties": {
      "orderId": { "type": "string" },
      "amount": { "type": "number" }
    },
    "required": ["orderId", "amount"]
  }
}
```

Nhưng schema validation chỉ chứng minh shape đúng. Nó không chứng minh user được refund order đó hoặc amount không vượt payment captured.

## 4. Practical implementation

Backend phải revalidate:

```csharp
public async Task<RefundResult> ExecuteAsync(
    RefundToolArgs args,
    ClaimsPrincipal user,
    CancellationToken ct)
{
    var order = await _orders.GetAsync(args.OrderId, ct)
        ?? throw new NotFoundException();

    if (!await _authorization.CanRefundAsync(user, order, ct))
        throw new ForbiddenException();

    if (args.Amount <= 0 || args.Amount > order.RefundableAmount)
        throw new ValidationException("Invalid refund amount.");

    return await _payments.RefundAsync(
        order.PaymentId,
        args.Amount,
        idempotencyKey: $"refund:{order.Id}:{args.Amount}",
        ct);
}
```

LLM có thể chọn tool, nhưng application owns authorization và invariants.

## 5. Real production scenario

Customer support assistant nhận câu: “Hoàn tiền toàn bộ đơn này giúp tôi.” Model chọn `create_refund`. Nếu backend chỉ trust `amount` do model tạo, hallucination hoặc prompt injection có thể gửi amount sai. Correct design load order state và tính/validate refundable amount deterministically.

## 6. Failure scenario & troubleshooting

**Symptom** → tool calls hợp schema nhưng business action sai hoặc unauthorized.

**Evidence** → executor chỉ validate JSON schema, không re-check current domain state/identity.

**Hypothesis** → model output đang được coi là trusted application command.

**Diagnosis** → trace tool selection, arguments, authenticated principal, validation decisions và downstream result.

**Fix** → enforce authorization/invariants server-side, use allowlist tools, constrain side effects, require confirmation cho high-impact actions khi product cần.

**Verification** → adversarial tests với prompt injection, malformed intent, stale state và cross-tenant resource IDs.

## 7. Common mistakes

* Tool schema = authorization.
* Cho model tự quyết định tenant/user ID thay vì derive từ authenticated context.
* Expose generic SQL/file/system tool quá mạnh.
* Không đặt timeout/retry/idempotency cho side-effect tools.
* Log prompt/tool arguments có secrets/PII không kiểm soát.
* Không có evaluation set cho tool-selection accuracy.

## 8. Alternatives

Structured Output phù hợp extraction/classification không cần side effects. Deterministic UI/workflow tốt hơn khi task có rules rõ và ít ambiguity. Human approval phù hợp high-impact, low-frequency operations. RAG hỗ trợ knowledge retrieval nhưng không thay execution boundary.

## 9. Trade-offs

### Advantages

* Natural-language interface tới deterministic capabilities.
* Tool schemas tạo contract rõ hơn free-form text parsing.
* Có thể mở rộng workflow mà không đưa business logic vào prompt.

### Costs / Risks

* Model vẫn có thể chọn sai tool/arguments.
* Prompt injection và data leakage cần defense-in-depth.
* Observability/evaluation phức tạp hơn normal API flow.
* Token/latency/cost tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu model output là untrusted input.

### Middle

Implement typed tool schemas, validation, timeout và error handling.

### Senior

Thiết kế idempotency, authorization, prompt-injection boundaries và evaluation.

### Technical Lead / Architect

Quyết định phần nào dùng LLM reasoning và phần nào bắt buộc deterministic; giới hạn tool capability theo least privilege và business risk.

## 11. Key takeaway

* Tool Calling nối probabilistic reasoning với deterministic systems; boundary giữa hai phần phải rõ.
* Schema correctness không thay authorization hay domain validation.
* Security-critical và financial correctness phải được application enforcement, không giao cho model tự quyết.
