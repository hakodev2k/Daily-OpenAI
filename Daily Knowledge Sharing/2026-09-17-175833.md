# 1. .NET `ArrayPool<T>`: buffer reuse, ownership và dữ liệu nhạy cảm còn sót lại

## 1. What is it?

`ArrayPool<T>` là pool các array có thể thuê và trả lại để giảm allocation cho buffer tạm thời. Mental model đúng là **borrowed mutable memory**: caller không sở hữu array vĩnh viễn và phải trả nó đúng lifecycle.

## 2. Why does it exist?

Các request xử lý JSON, compression, file chunk hoặc protocol buffers có thể liên tục tạo array lớn. Allocation rate cao làm tăng GC pressure; reuse buffer có thể giảm allocation và Gen 2/LOH pressure.

## 3. How does it work?

```text
Rent(size) -> pooled array
     |
     v
 use only required range
     |
     v
Return(array) -> reusable by another caller
```

Array nhận được có thể lớn hơn requested size và chứa dữ liệu từ lần sử dụng trước.

## 4. Practical implementation

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
    await destination.WriteAsync(buffer.AsMemory(0, read), ct);
}
finally
{
    pool.Return(buffer, clearArray: true);
}
```

`clearArray: true` có chi phí CPU nhưng đáng cân nhắc khi buffer từng chứa secrets hoặc dữ liệu nhạy cảm.

## 5. Real production scenario

File-processing API nhận hàng trăm upload đồng thời. Mỗi request trước đây tạo nhiều `byte[]` lớn; allocation rate và Gen 2 GC tăng. Pooling buffer giảm pressure mà không cần cache toàn file.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu request trước xuất hiện trong log/output hoặc memory tăng bất thường. **Evidence** → code đọc quá `read` length hoặc có đường exception không `Return`. **Diagnosis** → sai ownership/range. **Fix** → `try/finally`, chỉ dùng valid slice, clear dữ liệu nhạy cảm. **Verification** → stress test và allocation profiling.

## 7. Common mistakes

Giữ pooled array trong object lâu dài; return rồi vẫn tiếp tục dùng; giả định array được zero; serialize toàn `buffer.Length` thay vì valid length; pool mọi allocation nhỏ dù không có evidence về GC pressure.

## 8. Alternatives

Allocation bình thường đơn giản hơn và thường đủ tốt. `MemoryPool<T>` phù hợp khi cần owner abstraction; streaming có thể loại bỏ nhu cầu buffer lớn.

## 9. Trade-offs

### Advantages

Giảm allocation rate và GC pressure cho hot paths có buffer lớn/lặp lại.

### Costs / Risks

Ownership phức tạp, nguy cơ data leakage và use-after-return ở mức logic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu rent/use/return và valid range.

### Middle
Dùng `try/finally`, cancellation và không giữ reference sau `Return`.

### Senior
Đo allocation trước/sau, đánh giá security clearing và contention.

### Technical Lead / Architect
Quyết định pooling có đáng complexity hay streaming/simple allocation đã đủ.

## 11. Key takeaway

- Pooling là optimization dựa trên measurement.
- Pooled memory có ownership và confidentiality boundary.
- Không bao giờ giả định rented buffer sạch hoặc đúng requested length.

# 2. ASP.NET Core graceful shutdown: request draining, `CancellationToken` và deploy an toàn

## 1. What is it?

Graceful shutdown là quá trình application ngừng nhận work mới, cho work đang chạy cơ hội hoàn tất trong bounded window rồi terminate. Đây là lifecycle protocol, không phải chỉ gọi `StopAsync`.

## 2. Why does it exist?

Deploy, scale-in, recycle và node maintenance đều có thể dừng process. Nếu process bị kill giữa transaction, upload hoặc message handling, user thấy lỗi và work có thể bị duplicate khi retry.

## 3. How does it work?

```text
SIGTERM / host stop
       |
       v
stop new traffic -> drain in-flight work
       |
       v
CancellationToken signaled
       |
       v
bounded cleanup -> process exit
```

Reverse proxy/orchestrator và application phải phối hợp; application không thể tự drain traffic nếu load balancer vẫn route request mới.

## 4. Practical implementation

```csharp
public sealed class Worker(ChannelReader<Job> jobs) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in jobs.ReadAllAsync(stoppingToken))
            await ProcessAsync(job, stoppingToken);
    }
}
```

Long-running operations phải quan sát token nhưng cần thiết kế checkpoint/idempotency để cancellation không làm state nửa vời.

## 5. Real production scenario

App Service deploy version mới khi API đang xử lý file import 40 giây. Nếu shutdown timeout ngắn hơn import và operation không resumable, request bị cắt; client retry tạo duplicate import.

## 6. Failure scenario & troubleshooting

**Symptom** → spike 499/5xx đúng thời điểm deploy. **Evidence** → shutdown logs trùng failed requests. **Hypothesis** → drain window hoặc readiness routing sai. **Diagnosis** → trace request lifetime và host termination. **Fix** → bounded work, idempotency, readiness/draining đúng, tách job dài sang queue. **Verification** → deploy dưới synthetic load.

## 7. Common mistakes

Nuốt `OperationCanceledException` như lỗi production; bắt đầu work dài trong shutdown; không truyền token xuống DB/HTTP; kỳ vọng graceful shutdown bảo đảm mọi work hoàn tất.

## 8. Alternatives

Work dài nên được durable queue + Worker Service xử lý. Request ngắn có thể chỉ cần host lifecycle mặc định nếu SLO cho phép.

## 9. Trade-offs

### Advantages
Giảm deployment-induced errors và corrupted partial work.

### Costs / Risks
Drain quá dài làm rollout chậm; cancellation-safe business flow phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu process có thể bị dừng bất kỳ lúc nào.

### Middle
Propagate cancellation và cleanup resource đúng.

### Senior
Thiết kế idempotent/resumable operations và correlate deploy với telemetry.

### Technical Lead / Architect
Quyết định workload nào thuộc request path và workload nào phải durable async.

## 11. Key takeaway

- Graceful shutdown là bounded cooperation, không phải guarantee.
- Long-running work cần durability/idempotency.
- Release engineering phải test cả shutdown path.

# 3. EF Core split queries: Cartesian explosion, round trips và consistency window

## 1. What is it?

Split query cho phép EF Core load một object graph bằng nhiều SQL queries thay vì một JOIN lớn. Nó đổi **row duplication** lấy **nhiều round trips và consistency considerations**.

## 2. Why does it exist?

Nhiều collection `Include` cùng cấp có thể tạo Cartesian explosion. Một Order có 20 Lines và 10 Events có thể tạo 200 rows cho một root, lặp lại columns của Order.

## 3. How does it work?

```text
Single query: Orders JOIN Lines JOIN Events -> duplicated rows
Split query:  Orders -> Lines -> Events -> EF assembles graph
```

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .Include(x => x.Lines)
    .Include(x => x.Events)
    .AsSplitQuery()
    .Where(x => x.CustomerId == customerId)
    .ToListAsync(ct);
```

Đo generated SQL và payload trước khi chọn strategy.

## 5. Real production scenario

Admin order page thêm `Lines`, `Payments` và `AuditEntries`. Sau release response latency tăng dù database CPU không cao; network payload từ JOIN tăng hàng chục lần.

## 6. Failure scenario & troubleshooting

**Symptom** → query trả nhanh trong SSMS với ít data nhưng API chậm trên production orders lớn. **Evidence** → trace cho thấy row count/network bytes lớn. **Diagnosis** → Cartesian explosion. **Fix** → projection hoặc split query. **Verification** → so logical reads, rows, payload và p95.

Split query cũng có consistency window: dữ liệu có thể thay đổi giữa các query nếu không dùng transaction/isolation phù hợp.

## 7. Common mistakes

`Include` toàn graph theo thói quen; chuyển sang split query mà không đo round trips; trả EF entities trực tiếp cho API; dùng transaction mạnh chỉ để che read-model design yếu.

## 8. Alternatives

Projection DTO thường tốt nhất cho read API. Explicit queries phù hợp khi các collection có lifecycle khác nhau.

## 9. Trade-offs

### Advantages
Giảm row duplication và memory/network amplification.

### Costs / Risks
Nhiều DB commands, latency tăng trên network xa, có thể đọc snapshot không đồng nhất.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `Include` thay đổi SQL/data shape.

### Middle
Đọc generated SQL và dùng projection/split query đúng chỗ.

### Senior
Đánh giá round trips, isolation và payload.

### Technical Lead / Architect
Quyết định read model/API contract thay vì để ORM graph quyết định data access.

## 11. Key takeaway

- `AsSplitQuery` không phải performance switch mặc định.
- Đo row multiplication lẫn round trips.
- Projection thường rõ boundary hơn load toàn entity graph.

# 4. PostgreSQL MVCC: dead tuples, VACUUM và vì sao “không blocking reader” vẫn có chi phí

## 1. What is it?

MVCC giữ nhiều row versions để transaction đọc snapshot phù hợp mà không buộc reader và writer luôn block nhau. Version cũ trở thành dead tuples khi không còn transaction nào cần chúng.

## 2. Why does it exist?

Concurrency cao cần giảm read/write contention nhưng vẫn giữ transactional consistency. Copy-on-write row versions là một cách đạt mục tiêu đó.

## 3. How does it work?

```text
UPDATE row
old tuple ---- visible to older snapshot
new tuple ---- visible to newer snapshot
       |
       v
VACUUM eventually reclaims dead tuple space
```

Long-running transaction có thể giữ old snapshot và ngăn cleanup hiệu quả.

## 4. Practical implementation

```sql
SELECT relname, n_live_tup, n_dead_tup
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Khi điều tra bloat, cần xem workload, autovacuum progress và long transactions thay vì chỉ chạy `VACUUM` thủ công.

## 5. Real production scenario

CRM table bị update liên tục bởi sync worker. Một reporting transaction chạy hàng giờ giữ snapshot cũ; dead tuples tăng, index/table bloat và query I/O tăng dần.

## 6. Failure scenario & troubleshooting

**Symptom** → latency và storage tăng dù row count gần như không đổi. **Evidence** → `n_dead_tup` cao, long transaction tồn tại. **Diagnosis** → cleanup bị trì hoãn. **Fix** → rút ngắn transaction, tune autovacuum theo table/workload, xử lý bloat có kế hoạch. **Verification** → theo dõi dead tuples, I/O và query latency.

## 7. Common mistakes

Giữ transaction mở khi user “think time”; disable autovacuum; coi MVCC là free concurrency; VACUUM FULL production mà không hiểu locking impact.

## 8. Alternatives

SQL Server row versioning có implementation/operations khác. Pessimistic locking phù hợp một số critical sections nhưng tăng blocking.

## 9. Trade-offs

### Advantages
Reader/writer concurrency tốt và snapshot semantics mạnh.

### Costs / Risks
Storage churn, vacuum overhead, bloat và operational tuning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu update có thể tạo row version mới.

### Middle
Không giữ transaction dài vô lý và biết đọc basic stats.

### Senior
Liên hệ snapshots, dead tuples, autovacuum, indexes và latency.

### Technical Lead / Architect
Thiết kế reporting/batch workload không phá OLTP lifecycle.

## 11. Key takeaway

- MVCC chuyển một phần locking cost thành version-management cost.
- Long transaction có tác động hệ thống dù không chạy query liên tục.
- VACUUM là thành phần correctness/operations bình thường của PostgreSQL.

# 5. DDD Aggregate boundary: invariant, transaction boundary và tránh aggregate khổng lồ

## 1. What is it?

Aggregate là consistency boundary gồm Aggregate Root và các entities/value objects phải thay đổi cùng nhau để bảo vệ invariant. Nó không phải object graph được load toàn bộ vì quan hệ database.

## 2. Why does it exist?

Business rules cần nơi sở hữu mutation. Nếu bất kỳ service nào cũng sửa trực tiếp mọi entity, invariant bị phân tán và transaction boundary trở nên mơ hồ.

## 3. How does it work?

```text
Application Service
      |
      v
Aggregate Root -> validates invariant -> state change
      |
      v
single transactional boundary
```

Cross-aggregate coordination thường không nên ép thành một giant ACID transaction nếu business chấp nhận eventual consistency.

## 4. Practical implementation

```csharp
public sealed class Timesheet
{
    private readonly List<Entry> _entries = [];
    public IReadOnlyCollection<Entry> Entries => _entries;
    public bool Submitted { get; private set; }

    public void AddEntry(DateOnly day, decimal hours)
    {
        if (Submitted) throw new InvalidOperationException("Submitted timesheet is immutable.");
        if (hours <= 0 || hours > 24) throw new ArgumentOutOfRangeException(nameof(hours));
        _entries.Add(new Entry(day, hours));
    }
}
```

Invariant nằm trong model thay vì controller.

## 5. Real production scenario

Timesheet phải bảo đảm sau submit không được sửa entry. Nếu API update trực tiếp `TimesheetEntry` repository, rule có thể bị bypass bởi batch job hoặc endpoint mới.

## 6. Failure scenario & troubleshooting

**Symptom** → production có submitted timesheet vẫn bị thay đổi. **Evidence** → nhiều code paths update child entity trực tiếp. **Diagnosis** → aggregate boundary bị bypass. **Fix** → mutation qua root/application use case, DB constraint khi phù hợp, tests cho invariant. **Verification** → architecture/search tests đảm bảo forbidden update path biến mất.

## 7. Common mistakes

Aggregate = toàn bộ navigation graph; mỗi table là aggregate; repository cho mọi entity; giant aggregate gây contention; dùng Domain Event để né transaction dù invariant cần atomicity.

## 8. Alternatives

CRUD/anemic model đủ cho domain đơn giản. Database constraints phù hợp invariant dữ liệu cơ bản. DDD chỉ đáng chi phí khi business behavior thực sự phức tạp.

## 9. Trade-offs

### Advantages
Ownership và invariant rõ, mutation dễ reasoning/test.

### Costs / Risks
Boundary sai tạo contention hoặc eventual-consistency complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt Entity, Value Object và Aggregate Root.

### Middle
Đặt behavior/invariant đúng model và transaction.

### Senior
Thiết kế aggregate nhỏ theo consistency requirement, không theo FK graph.

### Technical Lead / Architect
Quyết định invariant nào cần atomicity và boundary nào có thể eventual.

## 11. Key takeaway

- Aggregate là consistency boundary.
- Database relationship không tự động quyết định aggregate.
- DDD không cần thiết nếu business chỉ là CRUD đơn giản.

# 6. Azure Service Bus dead-letter queue: poison message, retry budget và recovery workflow

## 1. What is it?

Dead-letter queue (DLQ) là nơi giữ message không thể hoàn tất normal processing. Nó là **recovery boundary**, không phải thùng rác tự động.

## 2. Why does it exist?

At-least-once delivery và transient retries không thể giải quyết permanent schema/data/business failures. Retry vô hạn biến poison message thành resource drain.

## 3. How does it work?

```text
Queue -> Consumer -> retry/redelivery
                    |
              max delivery exceeded
                    v
                   DLQ
                    |
          inspect / repair / replay
```

Duplicate delivery vẫn có thể xảy ra; DLQ không thay thế idempotency.

## 4. Practical implementation

```csharp
processor.ProcessMessageAsync += async args =>
{
    try
    {
        await handler.HandleAsync(args.Message, args.CancellationToken);
        await args.CompleteMessageAsync(args.Message, args.CancellationToken);
    }
    catch (UnsupportedSchemaException ex)
    {
        await args.DeadLetterMessageAsync(args.Message,
            "UnsupportedSchema", ex.Message, args.CancellationToken);
    }
};
```

Transient dependency failure nên abandon/retry theo policy; permanent validation failure nên dead-letter sớm.

## 5. Real production scenario

Notification consumer nhận message schema cũ sau deployment. Deserialization luôn fail. Nếu chỉ retry, queue throughput bị tiêu tốn bởi message không thể thành công.

## 6. Failure scenario & troubleshooting

**Symptom** → DLQ tăng liên tục. **Evidence** → dead-letter reason tập trung ở một schema/version. **Diagnosis** → producer/consumer compatibility break. **Fix** → backward-compatible consumer hoặc migration/replay tool. **Verification** → replay sample, monitor active/DLQ counts và duplicate effects.

## 7. Common mistakes

Không alert DLQ; auto-replay toàn bộ; log payload chứa PII; dead-letter transient timeout ngay lần đầu; không lưu failure reason/correlation ID.

## 8. Alternatives

Retry queue/delayed retry hữu ích cho transient failures. Quarantine storage riêng phù hợp workflow cần manual approval phức tạp.

## 9. Trade-offs

### Advantages
Cô lập poison messages, giữ queue chính khỏe và hỗ trợ forensic recovery.

### Costs / Risks
Cần ownership, monitoring, retention và replay tooling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu DLQ chứa message cần xử lý tiếp.

### Middle
Phân loại transient/permanent failure và ghi reason hữu ích.

### Senior
Thiết kế retry budget, idempotent replay và dashboards.

### Technical Lead / Architect
Định nghĩa operational ownership: ai xử lý DLQ, SLA bao lâu, replay được kiểm soát thế nào.

## 11. Key takeaway

- DLQ không phải nơi “message chết rồi quên”.
- Retry phải có budget và failure classification.
- Replay phải idempotent và observable.

# 7. Kubernetes readiness vs liveness: tránh biến probe thành nguyên nhân outage

## 1. What is it?

Readiness quyết định Pod có nên nhận traffic; liveness quyết định container có cần restart. Hai probe trả lời hai câu hỏi khác nhau.

## 2. Why does it exist?

Process running không đồng nghĩa service sẵn sàng. Ngược lại, dependency tạm thời lỗi không nhất thiết có nghĩa process phải restart.

## 3. How does it work?

```text
readiness fail -> remove Pod from Service endpoints
liveness fail  -> kubelet restarts container
```

Nếu liveness phụ thuộc database, DB outage có thể làm toàn bộ pods restart đồng loạt và tạo recovery storm.

## 4. Practical implementation

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<StartupReadyCheck>("ready");

app.MapHealthChecks("/health/live", new() { Predicate = _ => false });
app.MapHealthChecks("/health/ready");
```

Liveness thường chỉ cần chứng minh process/event loop còn sống; readiness có thể kiểm tra điều kiện bắt buộc để serve traffic.

## 5. Real production scenario

SQL outage 90 giây. Liveness endpoint query SQL nên tất cả pods bị restart. Khi SQL hồi phục, pods đồng loạt cold-start và mở connection, kéo dài incident.

## 6. Failure scenario & troubleshooting

**Symptom** → `RESTARTS` tăng mạnh khi dependency lỗi. **Evidence** → probe failures trước mỗi restart. **Diagnosis** → dependency check nằm trong liveness. **Fix** → tách probe semantics, tune thresholds/timeouts. **Verification** → chaos test dependency outage và xác nhận pods không restart vô ích.

## 7. Common mistakes

Cùng endpoint cho readiness/liveness; probe gọi nhiều external services; timeout quá ngắn; readiness luôn 200 dù startup chưa hoàn tất; coi restart là universal recovery.

## 8. Alternatives

App Service health checks có model đơn giản hơn. Với app không orchestrated, reverse proxy + application health vẫn cần semantic tương tự.

## 9. Trade-offs

### Advantages
Traffic routing và self-healing tốt khi probe phản ánh đúng state.

### Costs / Risks
Probe sai có thể trở thành outage amplifier.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Biết readiness khác liveness.

### Middle
Tạo endpoint nhẹ, timeout hợp lý.

### Senior
Thiết kế dependency semantics và test degraded mode.

### Technical Lead / Architect
Quyết định service có thể serve partial functionality hay phải rời traffic hoàn toàn.

## 11. Key takeaway

- Readiness quản lý traffic; liveness quản lý restart.
- Dependency outage không mặc định đồng nghĩa process chết.
- Probe phải được chaos-test như production logic khác.

# 8. Application Insights dependency telemetry: điều tra p95 latency theo critical path

## 1. What is it?

Dependency telemetry ghi thời gian và kết quả của outbound calls như SQL, HTTP hoặc Azure services. Nó cho phép tách request latency thành các đoạn của critical path.

## 2. Why does it exist?

Một request 2 giây không cho biết 2 giây nằm ở application CPU, SQL, Redis hay external API. Không có dependency timing, team dễ tối ưu sai tầng.

## 3. How does it work?

```text
Request 1200 ms
 |-- app work 80 ms
 |-- SQL 120 ms
 |-- Pricing API 950 ms
 `-- serialization 50 ms
```

Distributed tracing liên kết request span với dependency spans bằng trace context.

## 4. Practical implementation

```csharp
builder.Services.AddApplicationInsightsTelemetry();
```

Khi dùng `HttpClient`/supported SQL instrumentation, dependency telemetry thường được capture tự động; custom protocol cần custom `Activity`/OpenTelemetry instrumentation.

## 5. Real production scenario

Checkout p95 tăng từ 500 ms lên 1.8 s. CPU và SQL bình thường. Trace cho thấy Review API không nằm critical path nhưng Pricing API tăng p95 lên 1.4 s; investigation chuyển đúng ownership team.

## 6. Failure scenario & troubleshooting

**Symptom** → request latency tăng nhưng dependency dashboard không chỉ ra nguyên nhân. **Evidence** → trace có missing spans. **Hypothesis** → custom client không instrument hoặc context propagation bị mất. **Diagnosis** → kiểm tra `Activity`, sampling và trace IDs. **Fix** → OpenTelemetry/custom instrumentation. **Verification** → một synthetic request có end-to-end trace đầy đủ.

## 7. Common mistakes

Chỉ nhìn average; log duration thủ công nhưng không correlation; sampling làm mất critical traces mà không hiểu policy; tạo high-cardinality dimensions vô hạn.

## 8. Alternatives

OpenTelemetry cho vendor-neutral instrumentation; logs hữu ích cho detail nhưng không thay thế latency topology; metrics tốt cho aggregate trends.

## 9. Trade-offs

### Advantages

### Costs / Risks

Phân tích p95/p99, sampling và missing spans.

# 9. Optimizely CMS content modeling: page/block boundary, editor experience và coupling

## 1. What is it?

Content modeling định nghĩa cấu trúc nội dung mà editor quản lý: page types, blocks, properties và composition rules. Đây vừa là data model vừa là editorial contract.

## 2. Why does it exist?

Nếu CMS model bám trực tiếp UI component hiện tại, redesign sẽ kéo theo content migration. Nếu model quá generic, editor phải hiểu implementation details và dễ tạo invalid composition.

## 3. How does it work?

```text
Editor intent
   |
   v
Content model -> delivery/rendering layer -> CDN/browser
```

Reusable block nên đại diện reusable editorial concept, không chỉ một `<div>` tái sử dụng.

## 4. Practical implementation

```csharp
[ContentType(DisplayName = "Hero Block", GUID = "11111111-1111-1111-1111-111111111111")]
public class HeroBlock : BlockData
{
    [Display(Name = "Heading")]
    public virtual string Heading { get; set; } = string.Empty;

    [UIHint(UIHint.Image)]
    public virtual ContentReference? Image { get; set; }
}
```

Validation và allowed types nên phản ánh editor workflow, không chỉ compiler constraints.

## 5. Real production scenario

Marketing site có Hero dùng trên landing pages. Nếu block lưu `DesktopWidth=7` và CSS class cụ thể, frontend redesign phá content model. Nếu lưu semantic intent như heading/image/CTA, rendering layer có thể tiến hóa độc lập hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → editors tạo page hợp lệ trong CMS nhưng frontend vỡ layout. **Evidence** → content area cho phép block combinations không được UI support. **Diagnosis** → modeling/validation boundary thiếu. **Fix** → allowed types, validation, semantic model và preview tests. **Verification** → editor acceptance + rendering regression tests.

## 7. Common mistakes

Page type cho mọi visual variation; giant universal block; property names chứa CSS implementation; migration không có backward compatibility; cache invalidation không gắn publish lifecycle.

## 8. Alternatives

Headless CMS tách delivery mạnh hơn nhưng không tự giải quyết content-model quality. Hard-coded pages đơn giản hơn khi nội dung hiếm khi do editor thay đổi.

## 9. Trade-offs

### Advantages
Semantic model tốt tăng reuse và editor autonomy.

### Costs / Risks
Model quá abstract làm editor khó dùng; model quá UI-specific làm redesign đắt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu page/block/content property khác UI DOM.

### Middle
Implement content types, validation và rendering rõ ràng.

### Senior
Thiết kế model bền với redesign, caching và migrations.

### Technical Lead / Architect
Cân bằng editorial flexibility, governance, delivery architecture và long-term compatibility.

## 11. Key takeaway

- Content model nên mô tả editorial intent hơn là CSS hiện tại.
- Reuse phải có semantic meaning.
- Editor experience là một phần của architecture quality.

# 10. AI coding agent trong PR review: repository grounding, verification và deterministic quality gates

## 1. What is it?

AI coding agent có thể đọc repository, diff, tests và documentation để hỗ trợ PR review. Mental model: agent là probabilistic reviewer có khả năng tìm pattern nhanh, không phải authority quyết định code đúng.

## 2. Why does it exist?

PR lớn chứa nhiều cross-file effects; con người dễ bỏ sót repetitive issues. Agent có thể mở rộng search surface, nhưng output chỉ có giá trị khi grounded vào source và được verify.

## 3. How does it work?

```text
Requirements + main branch docs
          |
          v
PR diff + repository context
          |
          v
AI hypotheses/findings
          |
          v
build/tests/static analysis
          |
          v
human engineering decision
```

LLM reasoning là probabilistic; compiler, tests, schema validation và security policy phải giữ deterministic.

## 4. Practical implementation

Một review workflow tốt yêu cầu agent dẫn chính xác file/symbol, phân biệt requirement source với changed docs, rồi chạy deterministic gates:

```bash
dotnet build --no-restore
dotnet test --no-build
```

Frontend có thể thêm unit tests và Playwright; static analysis có thể thêm SonarQube/linter.

## 5. Real production scenario

Agent thấy PR thêm generic repository và kết luận “Clean Architecture best practice”. Repository context cho thấy `DbContext` đã là intended persistence boundary và requirement không yêu cầu abstraction mới. Grounding ngăn architecture advice generic trở thành unnecessary complexity.

## 6. Failure scenario & troubleshooting

**Symptom** → review báo method/package không tồn tại hoặc claim test coverage sai. **Evidence** → source search/build không xác nhận finding. **Hypothesis** → hallucination hoặc context thiếu. **Diagnosis** → kiểm tra exact branch, file, package version và executable tests. **Fix** → source-grounded prompts + deterministic verification. **Verification** → mỗi blocking finding phải có reproducible evidence.

## 7. Common mistakes

Tin confidence language; review diff mà không đọc authoritative requirements; để agent tự merge; coi generated tests là bằng chứng nếu tests chỉ mirror implementation; không kiểm tra branch/ref.

## 8. Alternatives

Human-only review có judgment mạnh nhưng search bandwidth thấp hơn. Static analysis deterministic nhưng không hiểu business intent. Kết hợp cả ba thường hiệu quả nhất.

## 9. Trade-offs

### Advantages
Mở rộng coverage, phát hiện cross-file patterns, hỗ trợ test/document analysis nhanh.

### Costs / Risks
Hallucination, context cost, false positives và automation bias.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Dùng AI để giải thích diff nhưng luôn kiểm tra source.

### Middle
Yêu cầu evidence và chạy build/tests trước khi chấp nhận finding.

### Senior
Phân biệt correctness, maintainability, architecture và speculative advice.

### Technical Lead / Architect
Thiết kế review policy: AI tăng search/reasoning bandwidth nhưng merge authority và deterministic gates vẫn thuộc engineering process.

## 11. Key takeaway

- AI review phải grounded vào đúng repository/ref/requirements.
- Compiler, tests và policy gates không được thay bằng model confidence.
- Giá trị lớn nhất của agent là tăng investigation surface, không phải thay engineering judgment.
