# 1. C# `IAsyncDisposable`: async cleanup, resource lifetime và shutdown correctness

## 1. What is it?

`IAsyncDisposable` biểu diễn một resource cần cleanup bằng asynchronous I/O. Mental model: `IDisposable` phù hợp khi cleanup hoàn thành đồng bộ; `IAsyncDisposable` phù hợp khi cleanup phải flush, close hoặc release một resource qua network/storage mà không nên block thread.

## 2. Why does it exist?

Một connection, stream hoặc writer có thể cần gửi dữ liệu cuối, flush buffer hoặc đóng protocol asynchronously. Nếu ép việc đó thành synchronous cleanup, server có thể block ThreadPool đúng lúc tải cao hoặc shutdown.

## 3. How does it work?

`await using` được compiler hạ thành `try/finally`; trong `finally`, runtime gọi `DisposeAsync()` và await `ValueTask` trả về. Lifetime vì vậy vẫn deterministic, nhưng cleanup không cần sync-over-async.

## 4. Practical implementation

```csharp
public async Task ExportAsync(Stream destination, CancellationToken ct)
{
    await using var writer = new StreamWriter(destination, leaveOpen: true);
    await writer.WriteLineAsync("id,name".AsMemory(), ct);
    await writer.FlushAsync(ct);
}
```

Với type tự viết, chỉ implement async disposal khi thực sự sở hữu resource cần async cleanup; đừng thêm interface chỉ vì “modern .NET”.

## 5. Real production scenario

Worker xuất file lớn lên remote stream. Handler hoàn tất business logic nhưng buffer cuối chưa flush. `await using` giữ resource sống đến khi cleanup hoàn tất trước khi job được đánh dấu thành công.

## 6. Failure scenario & troubleshooting

**Symptom** → shutdown lâu, file bị truncate hoặc ThreadPool tăng queue.  
**Evidence** → trace cho thấy synchronous wait quanh cleanup hoặc resource chưa flush.  
**Hypothesis** → async resource bị dispose đồng bộ hoặc không dispose.  
**Diagnosis** → kiểm tra ownership và disposal path.  
**Fix** → propagate async disposal đến boundary sở hữu resource.  
**Verification** → graceful shutdown hoàn tất và output integrity test pass.

## 7. Common mistakes

Gọi `.DisposeAsync().AsTask().Wait()`; dispose resource không thuộc ownership của method; vừa `using` vừa `await using` sai semantics; bỏ qua cleanup khi exception xảy ra.

## 8. Alternatives

`IDisposable` đơn giản hơn cho resource thuần synchronous. Explicit `try/finally` hữu ích khi cleanup có nhiều bước nghiệp vụ, nhưng `await using` giảm khả năng quên cleanup.

## 9. Trade-offs

### Advantages

Không block thread khi cleanup I/O; lifetime rõ; hỗ trợ graceful shutdown tốt hơn.

### Costs / Risks

Async lan lên call chain; ownership phức tạp vẫn không được interface giải quyết; cleanup chậm vẫn làm request/job chậm kết thúc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `using` quản lý lifetime và `await using` dành cho async cleanup.

### Middle

Biết implement, test exception path và phân biệt ai sở hữu resource.

### Senior

Nhận ra sync-over-async, shutdown leak và cleanup latency trong production.

### Technical Lead / Architect

Quyết định boundary sở hữu resource và liệu resource lifecycle nên gắn request, job hay application lifetime.

## 11. Key takeaway

- Async cleanup vẫn là correctness, không chỉ performance.
- Ownership quan trọng hơn việc “có gọi Dispose hay không”.
- Không biến async disposal thành synchronous wait.

# 2. ASP.NET Core rate limiting: bảo vệ capacity thay vì chỉ “chặn request”

## 1. What is it?

Rate limiting giới hạn lượng công việc được chấp nhận theo một dimension như client, user, API key hoặc endpoint. Mental model đúng là admission control: giữ workload trong capacity mà hệ thống có thể phục vụ.

## 2. Why does it exist?

Không giới hạn, burst traffic có thể làm cạn connection pool, ThreadPool, downstream quota hoặc CPU. Autoscaling không phản ứng tức thời và cũng không chữa được một dependency có hard limit.

## 3. How does it work?

Request đi qua middleware; partition key được xác định; limiter như fixed window, sliding window, token bucket hoặc concurrency limiter quyết định permit. Request vượt ngưỡng nhận `429 Too Many Requests` thay vì tiếp tục tạo áp lực phía sau.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddFixedWindowLimiter("write-api", o =>
    {
        o.PermitLimit = 100;
        o.Window = TimeSpan.FromSeconds(10);
        o.QueueLimit = 0;
    });
});

app.UseRateLimiter();
app.MapPost("/orders", CreateOrder)
   .RequireRateLimiting("write-api");
```

Partition theo authenticated identity khi cần fairness; IP không phải identity đáng tin trong mọi topology.

## 5. Real production scenario

Promotion làm `POST /orders` tăng 20x. API vẫn có thể nhận socket nhưng database chỉ xử lý an toàn 500 writes/s. Rate limiter reject sớm một phần traffic để database không collapse cho tất cả người dùng.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều 429 dù CPU thấp.  
**Evidence** → limiter metrics cao nhưng downstream còn capacity.  
**Hypothesis** → policy quá chặt hoặc partition key gom nhiều user.  
**Diagnosis** → đối chiếu permit/reject với dependency saturation.  
**Fix** → điều chỉnh algorithm/key/capacity bằng load test.  
**Verification** → p95 ổn định và downstream utilization nằm trong budget.

## 7. Common mistakes

Dùng một global limit cho endpoint có cost khác nhau; tin `X-Forwarded-For` khi proxy chưa cấu hình an toàn; retry 429 ngay lập tức; coi rate limiting là DDoS protection hoàn chỉnh.

## 8. Alternatives

Queue-based load leveling phù hợp công việc có thể async. Concurrency limiting phù hợp khi cost phụ thuộc số operation đồng thời. API gateway có thể enforce policy ở edge nhưng application vẫn cần hiểu capacity thật.

## 9. Trade-offs

### Advantages

Fail fast, bảo vệ dependency, tạo fairness và latency predictable hơn.

### Costs / Risks

Reject legitimate burst; distributed limits khó hơn; policy sai có thể trở thành bottleneck nhân tạo.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 429 nghĩa là server chủ động từ chối workload.

### Middle

Cấu hình policy, key và response đúng.

### Senior

Liên hệ limit với capacity, retry behavior và downstream saturation.

### Technical Lead / Architect

Quyết định admission control nằm ở edge, service hay cả hai và capacity budget được sở hữu bởi team nào.

## 11. Key takeaway

- Rate limit phải xuất phát từ capacity, không phải con số tùy ý.
- Reject sớm thường tốt hơn để toàn hệ thống timeout.
- Client retry policy là một phần của thiết kế.

# 3. EF Core split queries: tránh cartesian explosion mà không che giấu round trips

## 1. What is it?

`AsSplitQuery()` cho phép EF Core tải một object graph bằng nhiều SQL query thay vì một JOIN query lớn. Nó giải quyết duplication/cross-product khi nhiều collection navigation được `Include`.

## 2. Why does it exist?

JOIN nhiều one-to-many collection có thể nhân số row truyền qua network. Một Order có 100 Lines và 20 Events có thể tạo lượng row lớn hơn nhiều so với dữ liệu logic cần trả.

## 3. How does it work?

Single query JOIN dữ liệu rồi materializer de-duplicate entity. Split query lấy root trước và các collection bằng query riêng, sau đó EF ghép graph theo key. Ta đổi payload duplication lấy thêm round trips và consistency considerations.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .Where(x => x.Status == OrderStatus.Open)
    .Include(x => x.Lines)
    .Include(x => x.Events)
    .AsSplitQuery()
    .AsNoTracking()
    .ToListAsync(ct);
```

Trước khi chọn split query, đo generated SQL, row count và payload.

## 5. Real production scenario

Admin screen tải 50 orders cùng lines và audit events. Sau release thêm `Include`, p95 tăng mạnh dù SQL “chỉ có một query”. Network bytes và database reads cho thấy cartesian explosion.

## 6. Failure scenario & troubleshooting

**Symptom** → API chậm sau khi thêm navigation.  
**Evidence** → query trả hàng chục nghìn rows cho vài chục root entities.  
**Hypothesis** → JOIN multiplication.  
**Diagnosis** → inspect SQL/execution plan và actual row count.  
**Fix** → projection hoặc split query.  
**Verification** → giảm bytes/rows và đo lại p95.

## 7. Common mistakes

Mặc định `Include` mọi navigation; chuyển toàn hệ thống sang split query; quên rằng nhiều query có thể thấy dữ liệu ở các thời điểm khác nhau; không cân nhắc projection.

## 8. Alternatives

Projection DTO thường tốt nhất cho read API. Explicit separate queries cho phép kiểm soát tối đa. Single query vẫn tốt khi graph nhỏ và round-trip latency cao.

## 9. Trade-offs

### Advantages

Giảm duplicated payload và memory materialization cho graph phức tạp.

### Costs / Risks

Nhiều round trips; consistency window; query count tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` ảnh hưởng SQL thật.

### Middle

Biết inspect generated SQL và chọn projection/split query.

### Senior

Đánh giá I/O, round trips, consistency và allocation.

### Technical Lead / Architect

Đặt read-model boundary để API không phụ thuộc object graph persistence quá mức.

## 11. Key takeaway

- “Một SQL query” không đồng nghĩa rẻ.
- Split query là trade-off, không phải default optimization.
- Projection thường là baseline tốt cho read API.

# 4. SQL covering index: giảm I/O nhưng không biến mọi query thành index khổng lồ

## 1. What is it?

Covering index là index chứa đủ columns để database trả kết quả mà không cần lookup về base table/clustered index. Key columns phục vụ seek/order; included columns có thể phục vụ output.

## 2. Why does it exist?

Một non-clustered seek có thể tìm đúng rows nhưng phải thực hiện hàng nghìn key lookups để lấy columns còn thiếu. Khi lookup cost lớn, latency và logical reads tăng mạnh.

## 3. How does it work?

Query → optimizer chọn plan → index seek lọc rows → nếu index cover SELECT thì engine trả dữ liệu trực tiếp. Nếu không cover, plan có thể thêm Key Lookup. Selectivity, statistics và row estimate vẫn quyết định plan.

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_CustomerId_CreatedAt
ON dbo.Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, TotalAmount);

SELECT CreatedAt, Status, TotalAmount
FROM dbo.Orders
WHERE CustomerId = @customerId
ORDER BY CreatedAt DESC;
```

Đo `STATISTICS IO` và actual execution plan trước/sau.

## 5. Real production scenario

Order history API đọc vài trăm rows theo customer. Index cũ chỉ có `CustomerId`; plan tạo hàng trăm lookups. Include ba output columns làm logical reads giảm rõ rệt.

## 6. Failure scenario & troubleshooting

**Symptom** → SELECT nhanh hơn nhưng write latency và storage tăng.  
**Evidence** → index size lớn, update cost tăng.  
**Hypothesis** → over-indexing.  
**Diagnosis** → usage stats + workload write/read.  
**Fix** → thu hẹp INCLUDE hoặc bỏ index ít giá trị.  
**Verification** → benchmark cả read và write.

## 7. Common mistakes

INCLUDE mọi column; nhầm key order với INCLUDE; tạo index từ một execution plan duy nhất; bỏ qua write amplification và statistics.

## 8. Alternatives

Projection nhỏ hơn có thể loại nhu cầu cover. Clustered/index redesign hữu ích nếu access pattern cốt lõi khác. Columnstore phù hợp workload analytical chứ không thay thế tùy tiện.

## 9. Trade-offs

### Advantages

Ít I/O và lookup, latency read tốt hơn.

### Costs / Risks

Tốn storage/memory, tăng write amplification, maintenance và deployment time.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index là cấu trúc dữ liệu có chi phí.

### Middle

Đọc seek/scan/lookup trong execution plan.

### Senior

Đánh giá selectivity, logical reads và write cost.

### Technical Lead / Architect

Quyết định indexing theo workload tổng thể và ownership của schema/performance.

## 11. Key takeaway

- Cover query để giảm lookup, không phải để “index mọi thứ”.
- Luôn đo I/O và plan.
- Mỗi index read optimization đều có write cost.

# 5. Redis cache stampede: kiểm soát concurrent misses trên hot key

## 1. What is it?

Cache stampede xảy ra khi một hot key hết hạn và nhiều request đồng thời cùng miss, rồi tất cả đánh xuống database/API nguồn.

## 2. Why does it exist?

Cache thường làm giảm load rất mạnh. Khi key biến mất, traffic vốn được hấp thụ bởi Redis đột ngột chuyển toàn bộ sang origin; dependency có thể quá tải chỉ trong vài giây.

## 3. How does it work?

Client → Redis miss → origin. Nếu 1.000 requests cùng miss, có thể có 1.000 origin calls. Mitigation phổ biến: single-flight/locking, TTL jitter, stale-while-revalidate hoặc proactive refresh.

## 4. Practical implementation

```csharp
var value = await cache.GetStringAsync(key, ct);
if (value is not null) return Deserialize(value);

await gate.WaitAsync(ct);
try
{
    value = await cache.GetStringAsync(key, ct);
    if (value is not null) return Deserialize(value);

    var data = await repository.LoadAsync(id, ct);
    await cache.SetStringAsync(
        key, Serialize(data),
        new DistributedCacheEntryOptions {
            AbsoluteExpirationRelativeToNow =
                TimeSpan.FromMinutes(5) + TimeSpan.FromSeconds(Random.Shared.Next(0, 30))
        }, ct);
    return data;
}
finally { gate.Release(); }
```

Local semaphore chỉ single-flight trong một process; multi-instance cần strategy khác.

## 5. Real production scenario

Homepage product configuration là hot key. TTL đồng loạt hết sau deployment; 20 instances cùng rebuild cache và SQL CPU spike.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL QPS spike theo chu kỳ TTL.  
**Evidence** → Redis misses tăng cùng lúc với DB latency.  
**Hypothesis** → synchronized expiry.  
**Diagnosis** → correlate key TTL/miss metrics.  
**Fix** → jitter + single-flight/stale strategy.  
**Verification** → origin QPS không còn spike khi key refresh.

## 7. Common mistakes

Dùng distributed lock không timeout; lock mọi key qua một mutex; cache null vô hạn; Redis fail thì retry liên tục; không xác định stale tolerance.

## 8. Alternatives

Không cache nếu origin đủ nhanh. Local cache giảm network nhưng consistency khó hơn. CDN phù hợp public HTTP content. Precomputation phù hợp dữ liệu đắt và predictable.

## 9. Trade-offs

### Advantages

Giữ origin ổn định và giảm tail latency khi expiry.

### Costs / Risks

Locking thêm complexity; stale serving giảm freshness; refresh logic cần observability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss tạo work ở origin.

### Middle

Implement cache-aside, TTL và fallback.

### Senior

Thiết kế stampede protection, outage behavior và metrics.

### Technical Lead / Architect

Quyết định dữ liệu nào đáng cache, freshness SLA và Redis có được phép trở thành critical dependency hay không.

## 11. Key takeaway

- TTL là một event vận hành, không chỉ một con số.
- Hot key expiry có thể tạo outage ở database.
- Cache design phải bao gồm miss và failure path.

# 6. Azure Blob Storage large-file upload: streaming, SAS và failure recovery

## 1. What is it?

Azure Blob Storage là object storage; với file lớn, thiết kế tốt thường stream hoặc upload theo blocks thay vì buffer toàn bộ file trong application memory.

## 2. Why does it exist?

Đưa file lớn qua web server rồi giữ toàn bộ trong RAM làm memory footprint tăng theo concurrent uploads. Object storage tách binary payload khỏi application compute và scale độc lập.

## 3. How does it work?

Một flow phổ biến: API authenticate/authorize → cấp short-lived SAS có scope hẹp → browser upload trực tiếp Blob Storage → application lưu metadata hoặc xử lý event sau upload. Block blobs hỗ trợ upload từng block và commit block list.

## 4. Practical implementation

```csharp
var blob = container.GetBlobClient(blobName);

await blob.UploadAsync(
    stream,
    new BlobUploadOptions
    {
        HttpHeaders = new BlobHttpHeaders
        {
            ContentType = contentType
        }
    },
    ct);
```

Ở quy mô lớn, ưu tiên SDK transfer options hoặc direct-to-Blob SAS; SAS phải ngắn hạn, giới hạn permission/container/blob phù hợp.

## 5. Real production scenario

CMS cho editor upload video 2 GB. Direct upload giúp App Service không giữ connection/data path cho toàn bộ payload; backend chỉ cấp quyền và quản lý metadata.

## 6. Failure scenario & troubleshooting

**Symptom** → blob tồn tại nhưng DB chưa có metadata, hoặc upload dở dang.  
**Evidence** → storage log có object/block nhưng application transaction fail.  
**Hypothesis** → cross-resource workflow không atomic.  
**Diagnosis** → correlate upload ID/blob name.  
**Fix** → trạng thái Pending/Completed, cleanup orphan và idempotent finalize.  
**Verification** → chaos test ngắt client/API giữa flow.

## 7. Common mistakes

SAS quá rộng hoặc sống quá lâu; buffer `IFormFile` lớn không giới hạn; tin Content-Type từ client; không scan file nguy hiểm; không cleanup orphan.

## 8. Alternatives

Proxy upload qua API đơn giản hơn cho file nhỏ và policy tập trung. SFTP phù hợp một số enterprise integrations. Database binary storage thường không phải lựa chọn tốt cho object lớn.

## 9. Trade-offs

### Advantages

Scale storage độc lập, giảm app memory/bandwidth, hỗ trợ large objects tốt.

### Costs / Risks

Workflow consistency phức tạp hơn; SAS/security lifecycle; orphan cleanup và malware scanning cần thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Blob là object storage, không phải filesystem local.

### Middle

Upload stream, metadata, cancellation và SAS an toàn.

### Senior

Thiết kế resumability, orphan handling, validation và telemetry.

### Technical Lead / Architect

Chọn data path, trust boundary, retention/lifecycle và cost model.

## 11. Key takeaway

- File lớn không nên mặc định đi qua application memory.
- Direct upload đổi performance tốt hơn lấy workflow/security complexity.
- Metadata và blob không atomic: phải thiết kế failure recovery.

# 7. Saga Pattern: consistency qua nhiều service mà không dùng distributed transaction

## 1. What is it?

Saga là chuỗi local transactions qua nhiều service, với compensating actions khi bước sau thất bại. Nó không tạo ACID transaction toàn hệ thống; nó quản lý eventual consistency có chủ đích.

## 2. Why does it exist?

Một order có thể liên quan Payment, Inventory và Shipping, mỗi service sở hữu database riêng. Giữ distributed lock/2PC xuyên network thường làm coupling và availability tệ.

## 3. How does it work?

Ví dụ orchestration:

```text
Order: Create Pending
  -> Inventory: Reserve
  -> Payment: Authorize
  -> Order: Confirm

Payment fails
  -> Inventory: Release
  -> Order: Cancel
```

Mỗi message có thể duplicate; handlers cần idempotent. Compensation là business action, không phải “rollback database từ xa”.

## 4. Practical implementation

```csharp
public async Task Handle(PaymentFailed message, CancellationToken ct)
{
    if (await inbox.AlreadyProcessed(message.Id, ct)) return;

    await inventory.ReleaseAsync(message.OrderId, ct);
    await orders.MarkCancelledAsync(message.OrderId, ct);
    await inbox.MarkProcessed(message.Id, ct);
}
```

Trong production, transaction boundary giữa inbox/state/outbox phải được thiết kế cẩn thận.

## 5. Real production scenario

E-commerce checkout reserve stock thành công nhưng payment provider timeout. Order giữ trạng thái `PaymentPending`; reconciliation xác định kết quả payment trước khi compensate để tránh vừa charge vừa release sai.

## 6. Failure scenario & troubleshooting

**Symptom** → order stuck giữa states.  
**Evidence** → trace cho thấy message B chưa đến hoặc compensation fail.  
**Hypothesis** → partial failure.  
**Diagnosis** → inspect saga state, outbox/inbox, DLQ.  
**Fix** → retry idempotently hoặc operator-assisted recovery.  
**Verification** → invariant cuối cùng đúng và không duplicate side effects.

## 7. Common mistakes

Gọi Saga là rollback; compensation không idempotent; không có explicit state machine; retry payment mù quáng; không có timeout/reconciliation; log không có correlation ID.

## 8. Alternatives

Single database transaction đơn giản hơn nếu boundary cho phép. Modular Monolith có thể tránh distributed consistency. 2PC chỉ phù hợp môi trường rất cụ thể và tăng coupling.

## 9. Trade-offs

### Advantages

Service autonomy, tránh global lock, chịu partial failure tốt hơn.

### Costs / Risks

Eventual consistency, nhiều intermediate states, compensation và observability phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu network call không nằm trong một ACID transaction chung.

### Middle

Implement idempotent handler và explicit states.

### Senior

Thiết kế compensation, timeout, deduplication và recovery.

### Technical Lead / Architect

Quyết định có thực sự cần service boundary gây distributed transaction hay một deployment/data boundary đơn giản hơn tốt hơn.

## 11. Key takeaway

- Saga quản lý inconsistency tạm thời; không xóa nó.
- Compensation là nghiệp vụ.
- Nếu có thể giữ transaction trong một boundary, đó thường là lựa chọn đơn giản hơn.

# 8. Docker container memory limits và .NET GC: khi app “đủ RAM” nhưng vẫn bị OOMKilled

## 1. What is it?

Container memory limit là hard resource boundary do runtime/orchestrator áp đặt. .NET GC nhận biết container environment, nhưng managed heap chỉ là một phần memory process sử dụng.

## 2. Why does it exist?

Không có limit, một process lỗi có thể chiếm memory của node. Có limit, scheduler có thể cô lập workload; đổi lại application phải sống trong budget thực tế chứ không phải RAM toàn máy.

## 3. How does it work?

Process dùng managed heap + native memory + stacks + buffers + runtime/JIT. Khi usage vượt cgroup/container limit, OS có thể kill process; GC không thể reclaim native/leaked/live managed objects tùy ý.

## 4. Practical implementation

```yaml
services:
  api:
    image: my-api:latest
    mem_limit: 768m
```

Trong Kubernetes, đặt `resources.requests.memory` theo baseline và `limits.memory` có headroom dựa trên load test. Theo dõi working set, GC heap size, allocation rate và Gen2 collections cùng nhau.

## 5. Real production scenario

API xử lý image upload chạy ổn local 16 GB nhưng container limit 512 MB. Concurrent requests buffer file thành byte arrays, LOH tăng nhanh và container bị kill trước khi health endpoint báo lỗi hữu ích.

## 6. Failure scenario & troubleshooting

**Symptom** → pod/container restart, application log không có `OutOfMemoryException`.  
**Evidence** → orchestrator ghi OOMKilled; memory working set chạm limit.  
**Hypothesis** → external kill.  
**Diagnosis** → correlate GC metrics, native memory, request concurrency.  
**Fix** → stream dữ liệu, bound concurrency, giảm allocation hoặc tăng limit có căn cứ.  
**Verification** → load test giữ peak dưới budget với headroom.

## 7. Common mistakes

Chỉ nhìn managed heap; tăng limit mà không tìm growth source; đặt request=limit cực thấp; buffer file lớn; cache không bound; nhầm memory leak với high legitimate live set.

## 8. Alternatives

Scale out giảm per-instance concurrency nhưng không chữa leak. Process memory dump/profiling giúp localize. Streaming và bounded queues thường giảm memory structurally.

## 9. Trade-offs

### Advantages

Limits tạo isolation và scheduling predictability.

### Costs / Risks

Limit quá thấp gây restart; quá cao giảm packing efficiency và che giấu inefficiency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu container có resource boundary riêng.

### Middle

Đọc memory metrics và OOM status.

### Senior

Phân biệt managed/native/live set, LOH và concurrency-driven growth.

### Technical Lead / Architect

Định nghĩa resource budget, load-test envelope và scaling policy theo workload.

## 11. Key takeaway

- OOMKilled không nhất thiết tạo `OutOfMemoryException`.
- GC heap không phải toàn bộ process memory.
- Resource limits phải dựa trên đo đạc dưới tải.

# 9. Vue.js async state race: response cũ ghi đè state mới

## 1. What is it?

Async state race xảy ra khi nhiều request được khởi tạo theo thứ tự A rồi B nhưng hoàn tất B rồi A; response A cũ ghi đè state mà B vừa cập nhật.

## 2. Why does it exist?

Browser/network không đảm bảo completion order. Reactive framework cập nhật UI đúng theo assignment cuối cùng, nhưng không biết response nào còn hợp lệ về business intent.

## 3. How does it work?

User chọn customer A → request A. Ngay sau đó chọn B → request B. B trả trước và UI hiển thị B; A trả sau và component gán A vào cùng state. Đây là logical race dù JavaScript chạy event loop một thread.

## 4. Practical implementation

```ts
let controller: AbortController | undefined;

async function loadCustomer(id: string) {
  controller?.abort();
  controller = new AbortController();

  try {
    const response = await fetch(`/api/customers/${id}`, {
      signal: controller.signal
    });
    customer.value = await response.json();
  } catch (e) {
    if ((e as DOMException).name !== "AbortError") throw e;
  }
}
```

Một request sequence/token cũng hữu ích khi operation không abort được.

## 5. Real production scenario

Admin search typeahead gọi API mỗi lần filter đổi. Network jitter khiến kết quả query cũ xuất hiện sau query mới, tạo cảm giác backend trả sai dữ liệu.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị dữ liệu không khớp input hiện tại.  
**Evidence** → DevTools cho thấy response completion order đảo.  
**Hypothesis** → stale async response.  
**Diagnosis** → log request sequence/input snapshot.  
**Fix** → abort hoặc ignore stale response.  
**Verification** → throttle network và rapid interaction test.

## 7. Common mistakes

Debounce rồi nghĩ race đã biến mất; catch `AbortError` như lỗi production; dùng global loading boolean cho nhiều requests; không snapshot parameter.

## 8. Alternatives

Sequence number đơn giản và framework-agnostic. Data-fetching libraries có request identity/cancellation. Server-side rendering không loại race ở client interactions.

## 9. Trade-offs

### Advantages

Cancellation giảm wasted work và bảo vệ UI correctness.

### Costs / Risks

Không phải mọi operation abort được; cancellation propagation cần thiết kế; optimistic UI có semantics khác.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async completion order không đảm bảo.

### Middle

Implement cancellation/loading/error state đúng.

### Senior

Phân biệt UI race, backend race và idempotency; test dưới network jitter.

### Technical Lead / Architect

Chuẩn hóa data-fetching pattern để component không tự phát minh lifecycle handling.

## 11. Key takeaway

- Single-threaded JavaScript vẫn có logical races.
- UI phải biết response nào còn current.
- Network throttling là công cụ debugging hữu ích.

# 10. Feature flags trong CI/CD: tách deployment khỏi release nhưng không tạo “configuration debt”

## 1. What is it?

Feature flag cho phép code đã deploy nhưng behavior được bật/tắt theo configuration, user cohort hoặc rule. Deployment đưa artifact vào production; release cho user tiếp cận capability.

## 2. Why does it exist?

Một change lớn khó deploy atomically cho toàn bộ user. Flags cho phép progressive exposure, kill switch và phối hợp backend/frontend mà không cần tạo build riêng.

## 3. How does it work?

Pipeline vẫn là commit → build → test → artifact → deploy → health validation. Runtime đọc flag để chọn path. Flag service/config trở thành control plane; telemetry phải phân biệt traffic theo variant.

## 4. Practical implementation

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
{
    return await newCheckout.ExecuteAsync(request, ct);
}

return await legacyCheckout.ExecuteAsync(request, ct);
```

Flag không được dùng để bypass authorization. Với critical behavior, định nghĩa default khi flag provider unavailable.

## 5. Real production scenario

Checkout mới deploy cho toàn bộ App Service instances nhưng chỉ bật 5% users. Metrics cho variant mới cho thấy payment failure tăng; team disable flag mà không rollback artifact.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng version nhưng user thấy behavior khác khó tái hiện.  
**Evidence** → logs thiếu flag evaluation context.  
**Hypothesis** → flag/cohort khác nhau.  
**Diagnosis** → trace user/request với flag snapshot.  
**Fix** → structured telemetry và deterministic targeting.  
**Verification** → reproduce đúng cohort và so sánh metrics.

## 7. Common mistakes

Flag tồn tại vĩnh viễn; nested flags tạo state explosion; dùng flag thay schema compatibility; không test cả on/off; đổi behavior critical mà không audit; provider outage làm app fail.

## 8. Alternatives

Blue-Green chuyển toàn environment. Canary route theo deployment instances. Branch dài hạn trì hoãn integration và thường tăng merge risk. Configuration setting đơn giản đủ cho static operational toggle.

## 9. Trade-offs

### Advantages

Giảm release blast radius, rollback behavior nhanh, hỗ trợ progressive delivery.

### Costs / Risks

Hai code paths, test matrix lớn, runtime dependency và flag debt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy khác release.

### Middle

Implement flag với test on/off và safe default.

### Senior

Thiết kế telemetry, cleanup lifecycle và interaction giữa flags.

### Technical Lead / Architect

Quy định loại flag, owner, expiry date, security boundary và khi nào Canary/Blue-Green phù hợp hơn.

## 11. Key takeaway

- Feature flag là release-control mechanism, không phải authorization.
- Mọi flag cần owner và kế hoạch xóa.
- Progressive delivery chỉ an toàn khi metrics phân biệt được variant.
