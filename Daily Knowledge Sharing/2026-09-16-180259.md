# 1. .NET `ArrayPool<T>`: giảm allocation mà không làm sai buffer ownership

## 1. What is it?

`ArrayPool<T>` là pool các arrays có thể thuê (`Rent`) và trả lại (`Return`) để tái sử dụng memory. Mental model không phải “array cache”, mà là **temporary buffer ownership**: trong khoảng từ `Rent` đến `Return`, caller được quyền sử dụng buffer; sau `Return`, caller phải coi buffer đó không còn thuộc về mình.

## 2. Why does it exist?

Các workload parsing, compression, serialization hoặc file/network processing có thể tạo hàng nghìn temporary arrays. Allocation rate cao làm Gen0/Gen1 GC chạy thường xuyên; buffers lớn còn có thể đi vào LOH. Pooling giảm allocation pressure khi profiling chứng minh temporary buffers là bottleneck.

## 3. How does it work?

`ArrayPool<T>.Shared.Rent(minimumLength)` trả array có độ dài **ít nhất** bằng yêu cầu, không đảm bảo đúng kích thước. `Return` đưa array về pool để request khác tái sử dụng. Pool không đảm bảo buffer được zero hóa.

```text
Rent -> exclusive temporary use -> Return
                               |
                               +-> after Return: reference is invalid logically
```

## 4. Practical implementation

```csharp
var pool = ArrayPool<byte>.Shared;
byte[] buffer = pool.Rent(64 * 1024);

try
{
    int read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
    await ProcessAsync(buffer.AsMemory(0, read), ct);
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

Chỉ truyền slice chứa dữ liệu hợp lệ; không dùng `buffer.Length` như số byte thực tế.

## 5. Real production scenario

File-processing API nhận nhiều uploads đồng thời và mỗi request allocate nhiều buffers 64–256 KB. Allocation profile cho thấy GC time tăng mạnh. Pooling buffers ở hot path giảm allocation rate, nhưng chỉ có ý nghĩa sau khi đo bằng `dotnet-counters`, profiler hoặc benchmark.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu thỉnh thoảng bị corrupt dù tests đơn luồng pass.  
**Evidence** → async operation giữ reference tới rented array sau khi caller đã `Return`.  
**Hypothesis** → use-after-return.  
**Diagnosis** → trace ownership lifetime quanh asynchronous consumers.  
**Fix** → chỉ return sau khi mọi consumer hoàn tất; copy khi ownership phải vượt scope.  
**Verification** → concurrency stress test và allocation profile.

## 7. Common mistakes

Return buffer trước khi async consumer xong; giả định rented length đúng bằng requested length; giữ pooled buffer trong object dài hạn; dùng pool khi allocation không phải bottleneck; không cân nhắc dữ liệu nhạy cảm còn tồn tại trong buffer.

## 8. Alternatives

Array allocation đơn giản và an toàn hơn cho non-hot paths. `MemoryPool<T>` phù hợp khi cần owner abstraction. `Span<T>` giảm copy nhưng không tự cung cấp storage. Stack allocation phù hợp buffers nhỏ, bounded và synchronous.

## 9. Trade-offs

### Advantages

Giảm allocations và GC pressure ở hot path; tái sử dụng buffers lớn.

### Costs / Risks

Ownership phức tạp hơn; có nguy cơ data leakage/corruption; pooling có thể tối ưu nhầm bottleneck.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Rent`/`Return` và buffer có thể lớn hơn yêu cầu.

### Middle

Dùng `try/finally`, slices và test async lifetime.

### Senior

Đọc allocation/GC evidence, phát hiện use-after-return và security implications.

### Technical Lead / Architect

Quyết định hot path nào đáng đánh đổi simplicity lấy pooling; chuẩn hóa ownership contract.

## 11. Key takeaway

- Pooling là optimization dựa trên measurement.
- `Return` kết thúc ownership; không được dùng buffer sau đó.
- Giảm allocation nhưng tăng complexity và correctness risk.

# 2. ASP.NET Core request timeout budget: deadline propagation qua dependency chain

## 1. What is it?

Timeout budget là tổng thời gian một request được phép tiêu thụ và cách budget đó được phân bổ xuống SQL, HTTP, Redis hoặc messaging dependencies. Một timeout riêng lẻ không tạo ra reliability nếu mỗi layer tự retry và dùng timeout dài hơn deadline của caller.

## 2. Why does it exist?

Nếu reverse proxy timeout ở 5 giây nhưng API gọi dependency với timeout 30 giây, backend có thể tiếp tục làm việc sau khi client đã bỏ đi. Nếu ba dependencies tuần tự mỗi cái timeout 4 giây, request không thể đáp ứng SLO 3 giây.

## 3. How does it work?

```text
Client deadline 3s
  -> API overhead 200ms
  -> SQL budget 700ms
  -> remote API budget 1.5s
  -> response reserve 600ms
```

Deadline nên giảm dần theo elapsed time. `CancellationToken` truyền cancellation intent; timeout policy tạo cancellation khi operation vượt budget.

## 4. Practical implementation

```csharp
using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(requestAborted);
timeoutCts.CancelAfter(TimeSpan.FromSeconds(2));

using var response = await httpClient.GetAsync(
    "/inventory/42",
    timeoutCts.Token);
```

Không nên hard-code timeout khác nhau rải rác; policy cần gắn với dependency và SLO.

## 5. Real production scenario

Checkout API có SLO p95 dưới 2 giây. Inventory API đôi lúc treo 10 giây. Không có budget, ASP.NET Core workers không nhất thiết bị block nhưng sockets, pending requests và downstream capacity vẫn tích tụ.

## 6. Failure scenario & troubleshooting

**Symptom** → client thấy timeout 5 giây nhưng server traces kéo dài 20 giây.  
**Evidence** → dependency spans tiếp tục sau request abort.  
**Hypothesis** → deadline không propagate hoặc retry policy vượt budget.  
**Diagnosis** → so proxy timeout, ASP.NET Core timeout, `HttpClient` policy và DB command timeout.  
**Fix** → thiết kế hierarchical budget và linked cancellation.  
**Verification** → fault injection dependency chậm và kiểm tra resource release.

## 7. Common mistakes

Đặt mọi timeout thành 30 giây; retry sau timeout mà không còn budget; nhầm timeout với cancellation; dùng timeout quá ngắn không dựa latency distribution; không reserve thời gian để trả error response.

## 8. Alternatives

Circuit Breaker giảm calls tới dependency đang lỗi; Bulkhead giới hạn concurrency; asynchronous workflow phù hợp work không cần hoàn tất trong HTTP request. Chúng không thay thế deadline.

## 9. Trade-offs

### Advantages

Giới hạn resource retention, giảm failure propagation và làm latency predictable hơn.

### Costs / Risks

Timeout quá aggressive tạo false failures; cần SLO và telemetry để tuning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout giới hạn thời gian operation.

### Middle

Propagate token và cấu hình dependency timeout.

### Senior

Reason về retries, tail latency và ambiguous outcomes.

### Technical Lead / Architect

Thiết kế end-to-end deadline dựa trên SLO và critical path.

## 11. Key takeaway

- Timeout phải phù hợp deadline của caller.
- Retry tiêu thụ budget, không tạo thêm thời gian.
- Deadline, cancellation, Circuit Breaker và Bulkhead giải quyết các lớp khác nhau.

# 3. EF Core `AsSplitQuery`: tránh Cartesian explosion nhưng không miễn phí

## 1. What is it?

Khi `Include` nhiều collection relationships, single SQL query có thể tạo Cartesian multiplication. `AsSplitQuery()` yêu cầu EF Core tải related collections bằng nhiều SQL queries thay vì một join khổng lồ.

## 2. Why does it exist?

Một `Order` có 20 `Items` và 10 `Notes`; join hai collections có thể tạo 200 rows cho cùng order. Network payload, materialization và duplicated columns tăng dù số entities thật nhỏ hơn nhiều.

## 3. How does it work?

Single query:

```text
Orders JOIN Items JOIN Notes -> multiplied result rows
```

Split query:

```text
Query Orders
Query Items for selected Orders
Query Notes for selected Orders
EF correlates results
```

Đổi duplication lấy additional round trips và consistency considerations.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .Where(x => x.CustomerId == customerId)
    .ToListAsync(ct);
```

Nếu API chỉ cần DTO summary, projection thường tốt hơn cả hai.

## 5. Real production scenario

Order detail endpoint thêm `Items`, `Discounts`, `Shipments`. Sau release, SQL trả hàng chục nghìn rows cho một order lớn. `AsSplitQuery` giảm payload, nhưng team sau đó nhận ra projection chính xác còn hiệu quả hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → memory và query duration tăng sau khi thêm `Include`.  
**Evidence** → generated SQL và row count lớn bất thường.  
**Hypothesis** → Cartesian explosion.  
**Diagnosis** → đo SQL rows, payload và materialization.  
**Fix** → projection hoặc split query tùy use case.  
**Verification** → so round trips, bytes, DB duration và API p95.

## 7. Common mistakes

Dùng `AsSplitQuery` như universal fix; load full graph cho read API; bỏ qua consistency giữa nhiều queries; không paginate parent set; đánh giá performance chỉ bằng SQL duration.

## 8. Alternatives

Projection (`Select`) thường tốt nhất cho read models. Explicit loading hữu ích khi conditional. Single query phù hợp graph nhỏ. Raw SQL có thể cần khi query shape đặc biệt.

## 9. Trade-offs

### Advantages

Giảm row multiplication và duplicated payload.

### Costs / Risks

Nhiều round trips; dữ liệu có thể thay đổi giữa queries tùy isolation; latency tăng khi network xa.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` biến thành relational query work.

### Middle

Nhận diện Cartesian explosion và dùng split query có chủ đích.

### Senior

So projection/split/single query bằng evidence.

### Technical Lead / Architect

Định nghĩa read-model strategy thay vì expose domain graph tùy tiện.

## 11. Key takeaway

- `Include` không miễn phí.
- Split query đổi duplication lấy round trips.
- Với API reads, projection thường là baseline cần xem xét đầu tiên.

# 4. PostgreSQL transaction isolation: `READ COMMITTED`, repeatable reads và business invariants

## 1. What is it?

Isolation level quyết định transaction nhìn thấy thay đổi concurrent như thế nào. PostgreSQL mặc định `READ COMMITTED`: mỗi statement thấy snapshot mới tại lúc statement bắt đầu. Isolation không chỉ là database setting; nó ảnh hưởng trực tiếp business invariants.

## 2. Why does it exist?

Concurrency tạo race mà code tuần tự không thấy. Hai requests có thể cùng đọc “còn 1 slot”, rồi cả hai insert booking. Transaction có tồn tại nhưng invariant vẫn có thể bị phá nếu isolation/constraint không đủ.

## 3. How does it work?

MVCC cho readers thấy snapshot phù hợp mà không cần block mọi writer. `REPEATABLE READ` giữ transaction snapshot ổn định hơn; `SERIALIZABLE` phát hiện patterns không thể tương đương serial execution và có thể abort transaction.

## 4. Practical implementation

Invariant nên được bảo vệ gần data nhất khi có thể:

```sql
CREATE UNIQUE INDEX ux_booking_slot
ON bookings(event_id, slot_number);
```

Trong .NET/Npgsql, transaction isolation có thể chọn explicit, nhưng constraint thường đáng tin hơn pattern “check rồi insert”.

## 5. Real production scenario

Event system kiểm tra seat còn trống bằng `SELECT`, sau đó `INSERT`. Hai requests chạy đồng thời đều pass check. Unique constraint biến race thành một success và một deterministic conflict.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate business state xuất hiện hiếm khi load cao.  
**Evidence** → concurrent timeline cho thấy check-before-write race.  
**Hypothesis** → invariant chỉ tồn tại trong application logic.  
**Diagnosis** → kiểm tra constraints, transaction boundary và isolation.  
**Fix** → constraint/atomic statement hoặc isolation mạnh hơn khi thực sự cần.  
**Verification** → concurrency test hàng trăm parallel attempts.

## 7. Common mistakes

Nghĩ “có transaction” nghĩa là không race; nâng lên `SERIALIZABLE` mà không xử lý serialization failure; giữ transaction mở qua remote API; không dùng database constraints cho invariant có thể biểu diễn được.

## 8. Alternatives

Optimistic concurrency phù hợp row updates; pessimistic locking phù hợp contention cụ thể; atomic SQL/constraints thường đơn giản hơn distributed locking.

## 9. Trade-offs

### Advantages

Isolation mạnh tăng consistency guarantees.

### Costs / Risks

Có thể tăng abort/retry hoặc contention; transaction dài giữ resources/version history lâu hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu concurrent transactions có thể interleave.

### Middle

Dùng constraints và transaction boundaries đúng.

### Senior

Reason về anomalies, MVCC và retry semantics.

### Technical Lead / Architect

Chọn consistency mechanism theo invariant thay vì blanket isolation policy.

## 11. Key takeaway

- Transaction không tự bảo vệ mọi business invariant.
- Constraint/atomic write thường mạnh hơn check-before-write.
- Isolation mạnh hơn có operational cost và failure mode riêng.

# 5. Cosmos DB partition key: scalability boundary quyết định cost và correctness

## 1. What is it?

Partition key quyết định cách Cosmos DB phân phối logical items lên physical partitions. Nó đồng thời ảnh hưởng query fan-out, throughput distribution, transaction scope và khả năng scale.

## 2. Why does it exist?

Một distributed database không thể giữ mọi dữ liệu trên một node. Để scale horizontally, hệ thống cần key phân phối data/workload. Chọn key sai có thể tạo hot partition dù tổng RU còn dư.

## 3. How does it work?

Items cùng logical partition key được colocate logic và transactional batch bị giới hạn trong logical partition. Query không có partition key có thể fan out qua partitions, tăng RU và latency.

## 4. Practical implementation

Với multi-tenant SaaS:

```json
{
  "id": "order-9182",
  "tenantId": "tenant-42",
  "status": "Pending"
}
```

Nếu access pattern chủ yếu `tenantId + order`, `/tenantId` có thể phù hợp, nhưng phải đánh giá tenant lớn có tạo hotspot hay vượt logical partition constraints không.

## 5. Real production scenario

Telemetry system dùng `/deviceType` làm partition key. 70% traffic là `mobile`, nên một key nhận phần lớn writes. Scale RU toàn container không giải quyết hiệu quả hotspot vật lý.

## 6. Failure scenario & troubleshooting

**Symptom** → throttling `429` dù aggregate RU chưa cao.  
**Evidence** → metrics theo partition key range cho thấy skew.  
**Hypothesis** → hot partition.  
**Diagnosis** → phân tích cardinality, traffic distribution và access patterns.  
**Fix** → redesign key/hierarchical strategy hoặc shard key domain; migration dữ liệu có thể cần container mới.  
**Verification** → RU và throttling phân bố đều hơn.

## 7. Common mistakes

Chọn key chỉ vì unique; chọn low-cardinality field; query không truyền partition key; nghĩ partition key chỉ ảnh hưởng performance; bỏ qua transaction boundary.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp relational consistency và joins. MongoDB có shard-key concerns tương tự. Cosmos DB phù hợp khi distribution/access patterns justify distributed document store.

## 9. Trade-offs

### Advantages

Partitioning tốt cho horizontal scale, predictable routing và colocated operations.

### Costs / Risks

Key là architectural commitment khó đổi; query fan-out và hotspot có cost lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định nơi dữ liệu được nhóm.

### Middle

Luôn truyền key khi point-read/query có thể route trực tiếp.

### Senior

Đánh giá RU, cardinality, skew và transaction scope.

### Technical Lead / Architect

Chọn database/key từ access patterns và growth model; dự liệu migration strategy.

## 11. Key takeaway

- Partition key là scalability và ownership boundary.
- High cardinality chưa đủ; traffic cũng phải phân bố hợp lý.
- Sai partition key thường không sửa được bằng tăng RU đơn thuần.

# 6. Modular Monolith: module boundary, data ownership và khi chưa cần Microservices

## 1. What is it?

Modular Monolith là một deployable application nhưng chia business capabilities thành modules có boundaries rõ. Module không chỉ là folder: nó sở hữu behavior/data contract và hạn chế dependency trực tiếp sang internals của module khác.

## 2. Why does it exist?

Layered monolith lớn dễ thành shared-model/shared-database coupling. Microservices giải deployment/ownership isolation nhưng thêm network failure, observability, messaging và operational cost. Modular Monolith giữ process đơn giản trong khi xây boundaries có chủ đích.

## 3. How does it work?

```text
Single deployment
+-----------------------------+
| Orders | Catalog | Billing  |
|   | public contracts |      |
+-----------------------------+
      one process
```

Module giao tiếp qua explicit interfaces/events; data ownership có thể dùng schema/table boundaries dù cùng physical DB.

## 4. Practical implementation

```csharp
public interface ICatalogQueries
{
    Task<ProductSnapshot?> GetProductAsync(Guid id, CancellationToken ct);
}
```

Orders phụ thuộc contract này thay vì query thẳng `CatalogDbContext` hoặc tables của Catalog.

## 5. Real production scenario

E-commerce team có Orders, Catalog và Promotions nhưng chỉ 6 developers. Microservices sẽ yêu cầu nhiều pipelines, telemetry và failure handling. Modular Monolith cho phép một deployment trong khi giữ module seams để tách sau nếu scale/team ownership yêu cầu.

## 6. Failure scenario & troubleshooting

**Symptom** → mọi feature sửa nhiều modules và migrations chạm shared tables.  
**Evidence** → cross-module entity references và direct SQL.  
**Hypothesis** → boundaries chỉ tồn tại trong namespace.  
**Diagnosis** → dependency graph/data ownership review.  
**Fix** → public contracts, ownership rules và integration tests.  
**Verification** → thay internals module không buộc consumers đổi.

## 7. Common mistakes

Gọi bất kỳ monolith nào là modular; share domain entities giữa modules; dùng event bus nội bộ cho mọi method call; tạo abstraction ceremony không có business boundary.

## 8. Alternatives

Simple layered architecture tốt cho domain nhỏ. Microservices phù hợp khi independent deployment/scale/team ownership mang giá trị đủ lớn. Modular Monolith là lựa chọn trung gian, không phải bước bắt buộc tới Microservices.

## 9. Trade-offs

### Advantages

Deployment đơn giản, transactions dễ hơn, latency thấp, boundaries tốt hơn monolith tự do.

### Costs / Risks

Process/resource isolation thấp hơn Microservices; discipline cần được enforce bằng tests/architecture rules.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module đại diện business capability.

### Middle

Tôn trọng public contracts và ownership.

### Senior

Thiết kế boundaries, integration và transaction semantics.

### Technical Lead / Architect

Quyết định khi nào independent deployment đáng operational complexity của Microservices.

## 11. Key takeaway

- Architecture boundary không phải folder boundary.
- Một process vẫn có thể có ownership rõ.
- Microservices chỉ đáng dùng khi lợi ích độc lập vượt chi phí phân tán.

# 7. Azure Service Bus dead-letter queue: DLQ là recovery workflow, không phải thùng rác

## 1. What is it?

Dead-letter queue (DLQ) chứa messages không thể tiếp tục xử lý bình thường, ví dụ vượt `MaxDeliveryCount`, bị dead-letter explicit hoặc vi phạm một số broker rules. Message ở DLQ không tự biến mất nhờ consumer chính sửa code.

## 2. Why does it exist?

Poison message retry vô hạn có thể giữ queue nóng, tốn compute và che traffic tốt. DLQ cô lập failure để main flow tiếp tục, đồng thời giữ evidence cho diagnosis/recovery.

## 3. How does it work?

```text
Queue -> Consumer -> fail -> abandon/retry
                    -> MaxDeliveryCount
                    -> DLQ -> inspect -> repair/replay/manual decision
```

At-least-once delivery vẫn áp dụng; replay phải idempotent.

## 4. Practical implementation

```csharp
await receiver.DeadLetterMessageAsync(
    message,
    deadLetterReason: "UnsupportedSchemaVersion",
    deadLetterErrorDescription: "Expected v3 or lower",
    cancellationToken: ct);
```

Operational tooling cần hiển thị reason, age, message type, correlation ID và replay outcome.

## 5. Real production scenario

Notification consumer deploy version mới nhưng một producer cũ gửi schema không tương thích. Messages vào DLQ. Sau khi consumer hỗ trợ schema cũ, operator replay theo batch thay vì purge.

## 6. Failure scenario & troubleshooting

**Symptom** → main queue ổn nhưng DLQ tăng liên tục.  
**Evidence** → group dead-letter reasons và deployment timestamps.  
**Hypothesis** → deterministic contract bug, không phải transient outage.  
**Diagnosis** → inspect representative payload, producer version và consumer logs.  
**Fix** → sửa contract/consumer, test idempotency rồi replay có kiểm soát.  
**Verification** → DLQ drain, main processing success và không duplicate side effects.

## 7. Common mistakes

Không monitor DLQ; auto-replay vô hạn; log payload chứa PII; purge trước root-cause; retry validation error như transient error; replay không idempotent.

## 8. Alternatives

Parking-lot queue có thể hữu ích cho workflow recovery riêng. Retry queue/delayed retry phù hợp transient failures. DLQ phù hợp failures cần intervention/analysis.

## 9. Trade-offs

### Advantages

Failure isolation, evidence retention và controlled recovery.

### Costs / Risks

Tạo operational workflow bắt buộc; backlog DLQ có thể trở thành data-loss-by-neglect.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu message thất bại nhiều lần có thể vào DLQ.

### Middle

Ghi reason/correlation và xử lý replay.

### Senior

Phân loại transient/permanent failure và đảm bảo idempotency.

### Technical Lead / Architect

Định nghĩa DLQ ownership, alert thresholds, retention và recovery runbook.

## 11. Key takeaway

- DLQ là một phần của production workflow.
- Replay phải idempotent và có kiểm soát.
- DLQ tăng liên tục là reliability signal cần owner rõ.

# 8. Blue-Green deployment: traffic switch, database compatibility và rollback thật sự

## 1. What is it?

Blue-Green duy trì hai application environments: environment hiện tại và candidate. Candidate được deploy/test trước, sau đó traffic được chuyển. Rollback application có thể nhanh bằng traffic switch ngược lại.

## 2. Why does it exist?

In-place deployment có khoảng thời gian mixed binaries/files và rollback chậm. Blue-Green tách preparation khỏi traffic cutover, giảm release risk cho application layer.

## 3. How does it work?

```text
Users -> Router -> Blue (current)
                  Green (candidate, warm + validate)

Cutover: Router -> Green
Rollback: Router -> Blue
```

Database thường vẫn shared, vì vậy schema phải tương thích cả hai versions trong rollback window.

## 4. Practical implementation

Azure App Service deployment slots là một implementation thực tế: deploy staging slot, warm-up, health validation, rồi swap. Config nào là slot-specific phải được kiểm soát rõ; migration destructive không nên chạy trước compatibility window.

## 5. Real production scenario

API vNext deploy vào staging slot, chạy smoke/integration checks rồi swap. Sau cutover error rate tăng. Team swap back trong phút, nhưng rollback chỉ thành công vì database migration trước đó là additive.

## 6. Failure scenario & troubleshooting

**Symptom** → swap back nhưng Blue vẫn lỗi SQL.  
**Evidence** → Green migration đã drop/rename column Blue cần.  
**Hypothesis** → application rollback path tồn tại nhưng schema rollback path không tồn tại.  
**Diagnosis** → compare binary/schema compatibility.  
**Fix** → expand/contract migrations.  
**Verification** → pre-production test cả N và N-1 against target schema.

## 7. Common mistakes

Gọi deployment slot là zero-risk; không warm caches/JIT; session state phụ thuộc instance; destructive migration cùng release; health check chỉ kiểm tra process alive.

## 8. Alternatives

Rolling deployment dùng ít duplicate capacity hơn. Canary giảm blast radius bằng traffic percentage. Feature flags tách code deployment khỏi feature exposure.

## 9. Trade-offs

### Advantages

Fast cutover/rollback, candidate validation trước traffic.

### Costs / Risks

Duplicate environment cost; state/database compatibility vẫn phức tạp; cache/warm-up khác production traffic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hai environments và traffic switch.

### Middle

Thiết kế health checks và slot configuration.

### Senior

Reason về DB compatibility, warm-up và rollback verification.

### Technical Lead / Architect

Chọn Blue-Green/Canary/Rolling theo risk, cost và state model.

## 11. Key takeaway

- Blue-Green rollback nhanh cho application, không tự rollback database.
- Health validation phải kiểm tra dependencies quan trọng.
- Schema compatibility quyết định rollback có thật hay chỉ tồn tại trên slide.

# 9. SLI/SLO và error budget: biến reliability thành quyết định engineering đo được

## 1. What is it?

SLI là chỉ số đo service behavior; SLO là target cho SLI trong window; error budget là phần unreliability được phép trước khi vi phạm SLO. SLA là cam kết bên ngoài và không nên bị đồng nhất với SLO nội bộ.

## 2. Why does it exist?

“Service phải ổn định” không đủ để quyết định có nên dừng feature work, tăng redundancy hay chấp nhận risk. SLO biến reliability thành target có thể đo và trade-off.

## 3. How does it work?

Ví dụ SLO: 99.9% successful requests trong 30 ngày. Error budget ≈ 0.1% requests. Burn rate cho biết budget đang bị tiêu nhanh đến mức nào.

```text
Telemetry -> SLI -> compare SLO -> error-budget burn -> engineering action
```

## 4. Practical implementation

Một availability SLI tốt nên dựa trên user-visible outcomes, ví dụ:

```text
good requests / eligible requests
```

Không nhất thiết coi mọi `4xx` là service failure; contract phải định nghĩa rõ eligible/good events.

## 5. Real production scenario

Checkout có SLO 99.95%. Một release tạo intermittent 5xx và burn 40% monthly budget trong hai giờ. Đây là signal mạnh để rollback và ưu tiên remediation hơn tiếp tục release feature.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard “green” nhưng users phàn nàn.  
**Evidence** → SLI đo process uptime thay vì successful checkout.  
**Hypothesis** → indicator không phản ánh user journey.  
**Diagnosis** → map critical user outcome tới telemetry.  
**Fix** → định nghĩa request-based hoặc journey-based SLI đúng hơn.  
**Verification** → historical incidents phải xuất hiện rõ trong SLI.

## 7. Common mistakes

Đặt SLO 100%; dùng average latency; alert trên mọi metric; nhầm SLA và SLO; chọn SLI vì dễ query thay vì vì phản ánh user experience.

## 8. Alternatives

Traditional threshold alerts vẫn hữu ích cho component diagnostics. SLO không thay CPU/memory alerts; nó giúp ưu tiên và đánh giá service-level reliability.

## 9. Trade-offs

### Advantages

Tạo reliability language chung, giảm alert noise và hỗ trợ risk decisions.

### Costs / Risks

SLI sai tạo false confidence; telemetry/storage và governance có chi phí.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt metric và user-visible success.

### Middle

Query SLI và hiểu percentile/error rate.

### Senior

Thiết kế burn-rate alerts và correlate incidents.

### Technical Lead / Architect

Đặt SLO theo business criticality và dùng error budget cho release/risk policy.

## 11. Key takeaway

- SLO chỉ tốt khi SLI phản ánh user outcome.
- 100% reliability thường là mục tiêu kinh tế không hợp lý.
- Error budget kết nối reliability với engineering decisions.

# 10. Vue.js async state: race condition giữa browser requests và stale UI

## 1. What is it?

Frontend race condition xảy ra khi nhiều async requests cùng cập nhật state nhưng completion order khác initiation order. Request mới nhất về intent chưa chắc hoàn thành cuối cùng.

## 2. Why does it exist?

Search-as-you-type, filters và route changes phát requests liên tục. Network latency không deterministic. Nếu response cũ ghi state sau response mới, UI hiển thị stale data dù backend hoàn toàn đúng.

## 3. How does it work?

```text
User types "ca"  -> Request A ---------> response late
User types "car" -> Request B -> response early
                              UI=car
A returns later                 UI=ca  (wrong)
```

State ownership cần gắn với current intent hoặc cancellation/version token.

## 4. Practical implementation

```ts
import { ref, watch } from 'vue'

const query = ref('')
const results = ref<any[]>([])
let controller: AbortController | undefined

watch(query, async q => {
  controller?.abort()
  controller = new AbortController()

  try {
    const r = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
      signal: controller.signal
    })
    results.value = await r.json()
  } catch (e: any) {
    if (e.name !== 'AbortError') throw e
  }
})
```

Backend vẫn nên nhận cancellation và bảo vệ capacity.

## 5. Real production scenario

Automotive marketplace có make/model filters. User đổi model nhanh; request cũ trả sau request mới và danh sách xe “nhảy ngược”. Bug bị hiểu nhầm là cache/backend consistency issue.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị kết quả không khớp filter hiện tại.  
**Evidence** → DevTools Network cho thấy response order đảo.  
**Hypothesis** → stale async completion overwrites state.  
**Diagnosis** → correlate request params với state update timestamp.  
**Fix** → abort stale request hoặc sequence/version responses.  
**Verification** → throttle network và thay filters nhanh trong automated test.

## 7. Common mistakes

Chỉ debounce nhưng không xử lý in-flight request; show mọi abort như error; mutate shared state từ nhiều components; assume Promise completion order bằng invocation order.

## 8. Alternatives

Sequence counter bỏ qua stale responses mà không cần abort. Query libraries có thể quản lý caching/cancellation/deduplication. Server-side rendering giải quyết initial render, không loại bỏ client races sau hydration.

## 9. Trade-offs

### Advantages

Cancellation giảm wasted work và stale UI; versioning đơn giản cho correctness.

### Costs / Risks

Abort không đảm bảo backend side effects chưa xảy ra; state management phức tạp hơn với shared caches.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async responses có thể về khác thứ tự.

### Middle

Dùng `AbortController`, loading/error states và DevTools.

### Senior

Thiết kế request identity, cache semantics và stale-data policy.

### Technical Lead / Architect

Xác định frontend state ownership và API semantics để cancellation/idempotency nhất quán end-to-end.

## 11. Key takeaway

- Async invocation order không đảm bảo completion order.
- Debounce và cancellation giải quyết vấn đề khác nhau.
- Browser cancellation nên nối với backend cancellation nhưng không được coi là rollback side effect.
