# 1. C# SemaphoreSlim: giới hạn concurrency để bảo vệ downstream

## 1. What is it?

`SemaphoreSlim` giới hạn số operation được chạy đồng thời. Khác `lock` (mutual exclusion), semaphore cho phép N concurrent callers; `WaitAsync` không block worker thread.

## 2. Why does it exist?

HTTP API có thể nhận nhiều requests hơn capacity của vendor hoặc database. Không giới hạn, burst load biến thành timeout và retry storm.

## 3. How does it work?

Permit được lấy trước I/O và trả trong `finally`. Khi hết permit, callers chờ; thời gian chờ phải bounded. Limiter theo từng process không phải quota toàn cluster.

## 4. Practical implementation

~~~csharp
if (!await gate.WaitAsync(TimeSpan.FromSeconds(2), ct))
    throw new TimeoutException("Downstream saturated");
try { await vendor.SendAsync(payload, ct); }
finally { gate.Release(); }
~~~
`gate` phải shared giữa requests, ví dụ singleton service; không khởi tạo trong endpoint.

## 5. Real production scenario

Payroll integration có quota 12 concurrent calls. Một import 5.000 nhân viên được xử lý với concurrency 12, tránh vendor 429.

## 6. Failure scenario & troubleshooting

**Symptom:** p99 tăng. **Evidence:** semaphore wait time và vendor 429 tăng. **Hypothesis:** downstream saturated. **Diagnosis:** đo active/waiting calls và latency. **Fix:** bounded queue, giảm fan-out. **Verification:** load test cùng arrival rate.

## 7. Common mistakes

Quên `Release`; tạo semaphore per request; queue vô hạn; cho rằng 12 permits/pod bằng 12 permits/cluster; tăng limit mà không đo vendor.

## 8. Alternatives

`ConcurrencyLimiter` có lease/queue policy; `Channel<T>` phù hợp pipeline; durable queue phù hợp work không được mất khi process restart.

## 9. Trade-offs

### Advantages

 bounded load, giảm failure amplification. 
### Costs / Risks

 tăng waiting latency, có thể reject requests; global quota cần coordination.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

 phân biệt concurrency và rate. 
### Middle

 viết `WaitAsync`/`finally`. 
### Senior

 đo saturation, timeout budget. 
### Technical Lead / Architect

 quyết định limit ở API, worker hay gateway và global quota owner.

## 11. Key takeaway

- Limit theo capacity thực, không theo số CPU cores.
- Chờ cũng phải có timeout.
- Local limiter không bảo vệ global quota.

# 2. ASP.NET Core Forwarded Headers: reverse proxy là trust boundary

## 1. What is it?

Behind ingress, ASP.NET Core thường nhìn thấy IP của proxy và HTTP nội bộ. `ForwardedHeadersMiddleware` có thể khôi phục scheme/IP gốc từ trusted proxy.

## 2. Why does it exist?

OIDC redirects, audit và HTTPS redirection cần scheme/IP chính xác. Tin headers do client tự đặt lại tạo nguy cơ spoofing.

## 3. How does it work?

Client HTTPS → proxy terminates TLS → proxy thêm `X-Forwarded-Proto` → middleware kiểm tra trusted hop → `Request.Scheme`. Không phải mọi forwarded header đều đáng tin.

## 4. Practical implementation

~~~csharp
builder.Services.Configure<ForwardedHeadersOptions>(o => {
  o.ForwardedHeaders = ForwardedHeaders.XForwardedFor |
      ForwardedHeaders.XForwardedProto;
  o.KnownProxies.Add(IPAddress.Parse("10.0.2.10"));
  o.ForwardLimit = 1;
});
app.UseForwardedHeaders(); // before redirects/auth
~~~
Thay IP bằng trusted ingress thật; proxy phải sanitize client-supplied headers.

## 5. Real production scenario

App sau Application Gateway tạo OIDC redirect URI `http://...` thay vì `https://...`; identity provider từ chối callback.

## 6. Failure scenario & troubleshooting

**Symptom:** redirect loop/401. **Evidence:** `Request.Scheme` khác browser scheme. **Hypothesis:** middleware order hoặc proxy trust sai. **Diagnosis:** trace ingress headers và proxy chain. **Fix:** trusted-hop config. **Verification:** forged forwarded headers từ client không được tin.

## 7. Common mistakes

Clear mọi `KnownProxies` để hết lỗi; dùng raw forwarded IP làm authorization; middleware chạy sau auth; không kiểm tra multi-proxy chain.

## 8. Alternatives

TLS end-to-end hoặc platform integration có thể đơn giản hơn, nhưng trust boundary vẫn cần rõ.

## 9. Trade-offs

### Advantages

 correct URLs và client metadata. 
### Costs / Risks

 coupling với network topology; trust cấu hình rộng có thể gây security incident.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

 hiểu reverse proxy. 
### Middle

 cấu hình middleware. 
### Senior

 threat-model header spoofing. 
### Technical Lead / Architect

 sở hữu ingress contract và test khi topology thay đổi.

## 11. Key takeaway

- Forwarded headers là untrusted input nếu proxy chưa được xác thực.
- Middleware order quan trọng.
- Test cả legitimate request và forged headers.

# 3. EF Core DbContext pooling: mutable tenant state có thể rò dữ liệu

## 1. What is it?

`AddDbContextPool` tái sử dụng physical `DbContext` instance qua nhiều request scopes; không giống database connection pooling.

## 2. Why does it exist?

Pooling giảm allocation/setup overhead, nhưng application-defined fields không được EF Core tự reset. Multi-tenant query filter dùng field còn sót có thể đọc sai tenant.

## 3. How does it work?

Request A lease context → set TenantId=A → dispose về pool → request B lease cùng instance. Nếu B không set TenantId, query có thể dùng A.

## 4. Practical implementation

~~~csharp
public string TenantId { get; set; } = "";
protected override void OnModelCreating(ModelBuilder b) =>
  b.Entity<Invoice>().HasQueryFilter(x => x.TenantId == TenantId);
~~~
Với pooled context, scoped factory phải gán authenticated tenant trên **mỗi lease**; hoặc dùng `AddDbContext` thường để giảm risk.

## 5. Real production scenario

SaaS invoicing thỉnh thoảng trả invoice tenant A cho tenant B khi một background endpoint quên khởi tạo tenant field.

## 6. Failure scenario & troubleshooting

**Symptom:** cross-tenant result chỉ dưới load. **Evidence:** pooled instance reuse, tenant mismatch. **Hypothesis:** stale custom state. **Diagnosis:** concurrency tests với overlapping IDs. **Fix:** centralized initialization hoặc bỏ pooling. **Verification:** không có cross-tenant reads/writes.

## 7. Common mistakes

Inject scoped tenant service vào pooled context và nghĩ constructor chạy mỗi request; chỉ dựa vào query filter thay authorization; dùng `IgnoreQueryFilters` tùy tiện.

## 8. Alternatives

`AddDbContext` không pool đơn giản hơn; separate database/schema per tenant tăng isolation nhưng tăng operations.

## 9. Trade-offs

### Advantages

 giảm setup cost ở hot path. 
### Costs / Risks

 state leakage, lifetime complexity; benefit thường nhỏ so với database latency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

 DbContext không phải singleton. 
### Middle

 hiểu tracking và disposal. 
### Senior

 kiểm chứng pooled mutable state. 
### Technical Lead / Architect

 ưu tiên tenant isolation hay micro-optimization, xác định defense-in-depth.

## 11. Key takeaway

- EF reset internal state, không tự reset mọi custom field.
- Tenant phải lấy từ authenticated context.
- Không bật pooling chỉ vì nghe nói nhanh.

# 4. SQL Server memory grants: Sort/Hash spills xuống tempdb

## 1. What is it?

Operators như `Sort`, `Hash Match` cần working memory. SQL Server cấp memory grant theo estimated cardinality; grant thấp gây spill xuống `tempdb`, grant quá lớn gây memory waits.

## 2. Why does it exist?

Query có index vẫn chậm nếu sort/aggregate phải xử lý tập rows lớn. Memory grant là resource-sharing decision của optimizer.

## 3. How does it work?

Predicate → cardinality estimate → plan/memory grant → actual rows. Estimate sai làm operator spill hoặc chiếm RAM thừa, ảnh hưởng concurrent queries.

## 4. Practical implementation

~~~sql
SET STATISTICS IO, TIME ON;
SELECT CustomerId, SUM(Amount) AS Total
FROM dbo.Orders
WHERE CreatedAt >= @From AND CreatedAt < @To
GROUP BY CustomerId
ORDER BY Total DESC;
~~~
Đọc actual execution plan: spill warnings, granted/used memory, actual vs estimated rows và `tempdb` I/O.

## 5. Real production scenario

CRM quarterly report từ 400 ms lên 14 s vì hash aggregate spill; index seek vẫn có nhưng estimate quá thấp.

## 6. Failure scenario & troubleshooting

**Symptom:** p95 tăng, `tempdb` I/O spike. **Evidence:** plan spill warning. **Hypothesis:** cardinality mismatch. **Diagnosis:** statistics, parameters, Query Store. **Fix:** improve estimates/plan hoặc pre-aggregate. **Verification:** logical reads, spills, latency dưới concurrency.

## 7. Common mistakes

Chỉ xem estimated plan; thêm index theo phản xạ; tăng server memory trước khi đo; dùng `OPTION(RECOMPILE)` cho mọi query.

## 8. Alternatives

Summary table/reporting store phù hợp analytics nặng; query rewrite hoặc index có thể loại bớt sort tùy plan.

## 9. Trade-offs

### Advantages

 fix đúng nguyên nhân tail latency. 
### Costs / Risks

 index thêm write cost, recompilation tăng CPU, plan tốt cho range này có thể tệ cho range khác.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

 query có operators cần RAM. 
### Middle

 đọc actual plan. 
### Senior

 phân tích grant/spill/estimate. 
### Technical Lead / Architect

 cân nhắc tách analytics khỏi OLTP.

## 11. Key takeaway

- Index tốt không đồng nghĩa không spill.
- So estimated vs actual rows.
- Benchmark dưới concurrent workload.

# 5. Redis cache keys: tenant isolation, versioning và invalidation

## 1. What is it?

Cache key là identity contract của cached representation. Key cần chứa mọi dimension làm response khác nhau: tenant, resource, locale, version hoặc authorization scope khi phù hợp.

## 2. Why does it exist?

Key `product:42` có thể collision giữa hai tenants; schema serialization thay đổi giữa app versions cũng gây lỗi. TTL không sửa correctness của key sai.

## 3. How does it work?

Authenticated tenant + resource ID + representation version → key → cache-aside lookup → DB miss → write với TTL. Invalidation phải gắn với owner của dữ liệu.

## 4. Practical implementation

~~~csharp
var key = $"tenant:{tenantId}:product:{id}:v3";
var json = await cache.GetStringAsync(key, ct);
// On miss: query DB with WHERE TenantId == tenantId;
// Set with bounded TTL; invalidate after successful write.
~~~
`tenantId` phải đến từ validated claims, không tin query string.

## 5. Real production scenario

Marketplace deploy canary thay đổi `ProductDto`; key version v3 ngăn new code đọc JSON v2, nhưng cần cleanup old keys.

## 6. Failure scenario & troubleshooting

**Symptom:** tenant B thấy dữ liệu tenant A. **Evidence:** Redis key không chứa tenant. **Hypothesis:** collision. **Diagnosis:** correlate claims, generated keys, DB predicates. **Fix:** key redesign + purge. **Verification:** integration tests cùng ID khác tenants.

## 7. Common mistakes

Cache PII dưới shared key; TTL quá dài; invalidate trước DB commit; để Redis outage gây full API outage; log raw sensitive keys.

## 8. Alternatives

`IMemoryCache` phù hợp single-instance; không cache nếu dữ liệu thay đổi liên tục; materialized read model khi aggregate phức tạp.

## 9. Trade-offs

### Advantages

 giảm DB load, cải thiện latency. 
### Costs / Risks

 stale data, key/schema evolution, invalidation races, security risk.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

 key xác định representation. 
### Middle

 TTL/cache-aside. 
### Senior

 isolation và invalidation race. 
### Technical Lead / Architect

 xác định cache ownership, freshness SLO, fallback khi Redis down.

## 11. Key takeaway

- Cache key sai là data correctness bug.
- Tenant isolation phải có cả trong query và key.
- TTL không thay invalidation.

# 6. Azure Blob User Delegation SAS: direct upload với least privilege

## 1. What is it?

User Delegation SAS là capability URL ngắn hạn, ký bằng delegation key từ Microsoft Entra credentials, cho phép client thao tác với một Blob cụ thể mà không nhận account key.

## 2. Why does it exist?

Upload file lớn qua ASP.NET Core API tốn bandwidth và giữ connection lâu. SAS giúp browser upload trực tiếp; API vẫn giữ authorization.

## 3. How does it work?

Browser xin quyền → API xác thực, cấp unique blob name và SAS create-only → browser PUT Blob → API xác minh metadata/scan trước khi publish.

## 4. Practical implementation

~~~csharp
var sas = new BlobSasBuilder {
  BlobContainerName = "incoming", BlobName = blobName,
  Resource = "b", ExpiresOn = DateTimeOffset.UtcNow.AddMinutes(10),
  Protocol = SasProtocol.Https
};
sas.SetPermissions(BlobSasPermissions.Create);
// Sign with a user delegation key obtained using Managed Identity.
~~~
SAS không tự giới hạn kích thước hay scan malware; server phải kiểm tra hậu upload.

## 5. Real production scenario

HR portal upload CV 100 MB trực tiếp vào quarantine container; background scanner chuyển file sang trạng thái `Ready`.

## 6. Failure scenario & troubleshooting

**Symptom:** 403 khi PUT. **Evidence:** SAS expiry/permission, storage request ID, firewall hoặc CORS. **Hypothesis:** scope/network mismatch. **Diagnosis:** browser network trace và storage logs. **Fix:** correct RBAC, SAS, CORS. **Verification:** expired/wrong-blob URL bị reject.

## 7. Common mistakes

Đưa account key vào frontend; SAS cho cả container với delete permission; TTL nhiều ngày; tin content-type do client gửi; log full SAS URL.

## 8. Alternatives

API-proxied upload đơn giản cho file nhỏ; server-to-server Blob SDK phù hợp trusted services.

## 9. Trade-offs

### Advantages

 giảm API bandwidth và scale upload. 
### Costs / Risks

 orphan blobs, scanning workflow, SAS leakage, storage/network configuration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

 SAS là scoped capability. 
### Middle

 issuance/upload flow. 
### Senior

 RBAC, quarantine, expiry và abuse controls. 
### Technical Lead / Architect

 chọn security boundary và owner của file lifecycle.

## 11. Key takeaway

- Quyền SAS phải hẹp theo resource, operation và thời gian.
- Upload success chưa có nghĩa file an toàn.
- Không lộ account key hoặc SAS trong logs.

# 7. Webhook HMAC + Inbox: authenticity không đồng nghĩa exactly-once

## 1. What is it?

Webhook receiver cần xác minh chữ ký HMAC trên raw request bytes, kiểm tra timestamp chống replay và deduplicate event bằng durable Inbox. Đây là ba lớp bảo vệ khác nhau.

## 2. Why does it exist?

Provider retry khi timeout; attacker có thể replay request đã ký. Không có idempotency, cùng payment event có thể tạo hai ledger entries.

## 3. How does it work?

Verify provider-specific signed payload → reject stale timestamp → INSERT Inbox với UNIQUE `(Provider,EventId)` → process transactionally → acknowledge. HMAC phải dùng constant-time comparison.

## 4. Practical implementation

~~~csharp
var expected = HMACSHA256.HashData(secret, signedRawBytes);
if (provided.Length != expected.Length ||
    !CryptographicOperations.FixedTimeEquals(provided, expected))
    return Results.Unauthorized();
~~~
`signedRawBytes` phải được dựng đúng spec của provider, gồm timestamp nếu provider yêu cầu. Dedupe: `CREATE UNIQUE INDEX UX_Inbox ON dbo.Inbox(Provider,EventId);`

## 5. Real production scenario

Payment provider gửi `payment.succeeded` hai lần do response đầu timeout; Inbox bỏ qua duplicate trong khi business posting cũng dùng idempotency key.

## 6. Failure scenario & troubleshooting

**Symptom:** duplicate invoice. **Evidence:** cùng event ID trong delivery logs. **Hypothesis:** dedupe chỉ trong memory. **Diagnosis:** audit transaction boundary. **Fix:** durable unique constraint + retry-safe handler. **Verification:** replay và concurrent duplicate tests.

## 7. Common mistakes

Verify trên JSON đã reserialize; so sánh signature bằng string equality; bỏ timestamp window; trả 200 trước khi persist; nghĩ valid HMAC đồng nghĩa authorized tenant.

## 8. Alternatives

Polling đơn giản hơn nếu provider không có reliable webhooks; message gateway hữu ích với nhiều providers nhưng vẫn cần Inbox.

## 9. Trade-offs

### Advantages

 near-real-time integration, authenticity, duplicate tolerance. 
### Costs / Risks

 secret rotation, provider-specific contracts, Inbox storage/reconciliation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

 callback có thể đến nhiều lần. 
### Middle

 implement HMAC và unique key. 
### Senior

 xử lý replay/crash consistency. 
### Technical Lead / Architect

 ownership của reconciliation và retention policy.

## 11. Key takeaway

- Signature, replay window, idempotency là ba controls riêng.
- Verify raw bytes theo provider contract.
- Database uniqueness mạnh hơn in-memory dedupe.

# 8. Kubernetes HPA: CPU metric có thể bỏ lỡ queue backlog

## 1. What is it?

HPA scale Pods theo metrics. CPU-based HPA chỉ phù hợp nếu CPU tương quan với demand; queue consumers chờ I/O có thể backlog rất lớn dù CPU thấp.

## 2. Why does it exist?

Fixed replicas không xử lý burst, nhưng autoscale sai metric cũng vô ích. Scaling phải xét downstream capacity và queue age.

## 3. How does it work?

Producer → durable queue → workers; external metric như queue depth/age → KEDA/HPA → desired replicas. Scale-out làm tăng concurrent calls tới dependencies.

## 4. Practical implementation

~~~yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: document-worker }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: document-worker }
  minReplicas: 2
  maxReplicas: 12
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
~~~
Đây là baseline CPU HPA; với Azure Service Bus, cân nhắc KEDA queue trigger/external metrics và cap concurrency per Pod.

## 5. Real production scenario

OCR worker CPU 15% nhưng queue tăng 20.000 items vì chờ external OCR API. CPU HPA không scale; queue-based scaling hữu ích khi quota còn headroom.

## 6. Failure scenario & troubleshooting

**Symptom:** queue age tăng, replicas đứng yên. **Evidence:** CPU thấp, arrivals > completions. **Hypothesis:** metric sai. **Diagnosis:** HPA events, queue age, vendor 429. **Fix:** external metric + bounded concurrency. **Verification:** burst load test, backlog drain mà không tạo retry storm.

## 7. Common mistakes

Scale chỉ theo queue count; bỏ qua poison messages/DLQ; không set resource requests; scale pods vượt database connection limit; scale-down quá nhanh.

## 8. Alternatives

Azure Functions queue trigger giảm Kubernetes operational burden; fixed workers đủ cho predictable workload.

## 9. Trade-offs

### Advantages

 elastic capacity. 
### Costs / Risks

 metric lag, oscillation, cold starts, cloud bill và dependency overload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

 replicas khác per-Pod concurrency. 
### Middle

 đọc HPA status. 
### Senior

 chọn metric và cooldown. 
### Technical Lead / Architect

 có cần KEDA/Kubernetes hay managed compute đơn giản hơn?

## 11. Key takeaway

- Autoscaling phụ thuộc quality của signal.
- Queue age thường quan trọng hơn CPU với I/O workers.
- Scale-out không được vượt downstream quota.

# 9. OpenTelemetry metric cardinality: observability cũng có capacity

## 1. What is it?

Cardinality là số combinations của metric tag values. Route template/method/status thường bounded; `userId`, raw URL chứa GUID hoặc `orderId` có thể tạo hàng triệu time series.

## 2. Why does it exist?

Tags giúp phân tích nhưng mỗi series tốn memory, ingestion và query cost. Telemetry backend cũng có thể quá tải.

## 3. How does it work?

20 routes × 5 methods × 8 statuses ≈ tối đa 800 combinations; thêm 100.000 users làm upper bound tăng lên 80 triệu. Observed series tùy traffic thực tế.

## 4. Practical implementation

~~~csharp
using var meter = new Meter("Orders.Api");
var completed = meter.CreateCounter<long>("orders.completed");
completed.Add(1,
    new KeyValuePair<string, object?>("outcome", "success"),
    new KeyValuePair<string, object?>("region", regionCode));
~~~
`regionCode` phải thuộc allowlist; không tag email/order ID. Dùng `http.route` thay raw dynamic path.

## 5. Real production scenario

Sau deploy, metrics thêm `customerId`; exporter drop datapoints, dashboard chậm và telemetry bill tăng, dù business API vẫn chạy.

## 6. Failure scenario & troubleshooting

**Symptom:** series count và ingestion cost spike. **Evidence:** new unbounded tag. **Hypothesis:** cardinality explosion. **Diagnosis:** inspect metric dimensions/exporter diagnostics. **Fix:** bounded allowlist, drop dynamic tags. **Verification:** series count và dashboard latency giảm.

## 7. Common mistakes

Nhầm trace attributes với metric labels; thêm raw exception message; dùng trace sampling để chữa metric cardinality; thiếu telemetry budget.

## 8. Alternatives

Traces/logs (có privacy controls) cho per-request investigation; metrics cho bounded aggregates; exemplars liên kết hai tầng khi hỗ trợ.

## 9. Trade-offs

### Advantages

 low-cardinality metrics ổn định, rẻ và alertable. 
### Costs / Risks

 giảm drill-down trực tiếp, cần correlation sang traces/logs.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

 tags không miễn phí. 
### Middle

 chọn bounded dimensions. 
### Senior

 debug exporter drops. 
### Technical Lead / Architect

 định nghĩa metric schema, cardinality budget và retention.

## 11. Key takeaway

- Metrics cần bounded labels.
- High-cardinality identifiers thuộc traces/logs có kiểm soát.
- Monitoring infrastructure cũng cần capacity planning.

# 10. Git cherry-pick hotfix: patch replay không phải branch sync

## 1. What is it?

`git cherry-pick` áp dụng changes của một commit sang branch khác, tạo commit SHA mới. Nó không tự đồng bộ histories.

## 2. Why does it exist?

Production chạy `release/1.8` nhưng `main` chứa features chưa deploy; cần đưa một bugfix nhỏ vào production mà không merge toàn bộ main.

## 3. How does it work?

Fix commit F trên main → cherry-pick lên release thành F' → test target branch → deploy → bảo đảm main và release đều có logical fix. Patch có thể conflict do code context khác.

## 4. Practical implementation

~~~bash
git fetch origin
git switch -c hotfix/tax origin/release/1.8
git cherry-pick -x <fix-commit-sha>
dotnet test
git push -u origin hotfix/tax
~~~
Mở PR vào release, chạy CI và smoke test; nếu fix làm trên release trước thì forward-port vào main.

## 5. Real production scenario

Checkout v1.8 sai rounding tax; main đã refactor payments. Cherry-pick isolated fix giúp giảm release scope.

## 6. Failure scenario & troubleshooting

**Symptom:** lỗi quay lại ở release kế tiếp. **Evidence:** hotfix chỉ ở release branch. **Hypothesis:** thiếu forward-port. **Diagnosis:** compare commits và regression tests. **Fix:** apply equivalent change vào main. **Verification:** CI trên cả branches.

## 7. Common mistakes

Cherry-pick commit có hidden dependencies; bỏ tests trên target branch; dùng force push; không forward-port; không audit config/database migration đi kèm.

## 8. Alternatives

Merge hotfix branch khi strategy phù hợp; trunk-based development + feature flags giảm long-lived divergence.

## 9. Trade-offs

### Advantages

 surgical production fix, audit patch origin với `-x`. 
### Costs / Risks

 conflicts, duplicate logical commits, divergence.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

 hiểu commit SHA mới. 
### Middle

 conflict resolution/PR. 
### Senior

 review dependencies và rollback. 
### Technical Lead / Architect

 chọn branching/release policy và forward-port ownership.

## 11. Key takeaway

- Cherry-pick không thay thế branch synchronization.
- Test trên target release.
- Fix phải đi tới future release.
