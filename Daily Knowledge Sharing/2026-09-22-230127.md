# 1. ASP.NET Core graceful shutdown và `CancellationToken`: dừng instance mà không bỏ dở request/work

## 1. What is it?

Graceful shutdown là quá trình instance ngừng nhận workload mới, báo cancellation cho workload đang chạy và cho chúng một khoảng thời gian để hoàn tất hoặc dừng ở trạng thái an toàn trước khi process bị terminate. `CancellationToken` là cooperative cancellation: nó truyền tín hiệu dừng, không cưỡng chế kill code.

## 2. Why does it exist?

Production thường restart vì deployment, autoscaling, node maintenance hoặc App Service recycle. Nếu code coi process là bất tử, request, file processing hoặc queue handler có thể bị cắt giữa chừng, tạo partial side effect.

## 3. How does it work?

```text
Platform sends termination
        |
HostApplicationLifetime signals stopping
        |
stop accepting new work
        |
CancellationToken propagated
        |
work completes / checkpoints / abandons safely
        |
process exits
```

ASP.NET Core host quản lý lifetime; application phải truyền cancellation xuống EF Core, HttpClient và background operations.

## 4. Practical implementation

```csharp
public sealed class Worker(ChannelReader<Job> jobs) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in jobs.ReadAllAsync(stoppingToken))
        {
            await ProcessAsync(job, stoppingToken);
        }
    }
}
```

Với HTTP endpoint, truyền `HttpContext.RequestAborted` hoặc parameter `CancellationToken` xuống dependency thay vì tạo token mới và làm mất cancellation chain.

## 5. Real production scenario

Một instance đang upload report sang Blob Storage thì deployment bắt đầu. Readiness bị rút khỏi load balancer; worker nhận cancellation. Nếu upload có thể retry/idempotent, handler checkpoint trạng thái và dừng thay vì đánh dấu job `Completed` trước khi upload thực sự hoàn tất.

## 6. Failure scenario & troubleshooting

**Symptom** → sau deployment xuất hiện job ở trạng thái `Processing` vĩnh viễn.

**Evidence** → log kết thúc đúng thời điểm instance shutdown; operation không nhận cancellation và không có lease timeout.

**Hypothesis** → lifecycle/process failure không được đưa vào job-state design.

**Diagnosis** → correlate deployment events, shutdown logs và job timestamps.

**Fix** → propagate token, thiết kế retry/lease/idempotency, tăng shutdown grace period chỉ khi cần.

**Verification** → terminate instance trong integration test và xác nhận job được recover.

## 7. Common mistakes

Nuốt `OperationCanceledException` rồi log Error; dùng `CancellationToken.None`; đánh dấu business state hoàn tất quá sớm; kỳ vọng finally luôn chạy khi process bị kill cứng; shutdown timeout cực dài để che non-resumable work.

## 8. Alternatives

Work ngắn có thể hoàn tất trong request. Work dài và quan trọng thường phù hợp hơn với durable queue + worker/Azure Functions để process restart không làm mất ownership.

## 9. Trade-offs

### Advantages

Giảm partial work và deployment disruption; shutdown có semantics rõ.

### Costs / Risks

Cần cooperative code, idempotency và state recovery; grace period dài làm rollout chậm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu cancellation là tín hiệu hợp tác, không phải thread abort.

### Middle
Truyền token end-to-end và xử lý cancellation đúng log level.

### Senior
Thiết kế resumable/idempotent background work và kiểm thử termination.

### Technical Lead / Architect
Quyết định workload nào được phép sống trong web process và recovery SLA khi instance mất đột ngột.

## 11. Key takeaway

- Process restart là hành vi bình thường của Production.
- Cancellation phải được propagate tới dependency thực sự đang chờ.
- Graceful shutdown không thay thế durable state và idempotency.

# 2. EF Core optimistic concurrency: bảo vệ lost update bằng concurrency token

## 1. What is it?

Optimistic concurrency cho phép nhiều request đọc cùng record nhưng phát hiện conflict khi ghi. EF Core đưa concurrency token vào `WHERE` của `UPDATE`; nếu database báo 0 rows affected, EF Core ném `DbUpdateConcurrencyException`.

## 2. Why does it exist?

Không có concurrency control, hai user đọc version 1, cùng sửa, rồi người ghi sau âm thầm ghi đè người trước: lost update. Giữ database lock từ lúc user mở form đến lúc submit lại không thực tế.

## 3. How does it work?

```text
A reads rowversion=10
B reads rowversion=10
A UPDATE ... WHERE Id=1 AND rowversion=10 -> success, version=11
B UPDATE ... WHERE Id=1 AND rowversion=10 -> 0 rows -> conflict
```

## 4. Practical implementation

```csharp
public class Employee
{
    public int Id { get; set; }
    public string Name { get; set; } = "";

    [Timestamp]
    public byte[] Version { get; set; } = [];
}
```

API nên đưa version vào DTO/ETag và yêu cầu client gửi lại khi update. Khi conflict, application quyết định reload, merge hoặc trả `409 Conflict`/`412 Precondition Failed` theo contract.

## 5. Real production scenario

Manager A sửa title, HR B sửa salary của cùng employee. Generic “last write wins” có thể làm mất một thay đổi. Concurrency token phát hiện record đã thay đổi và buộc workflow xử lý conflict rõ ràng.

## 6. Failure scenario & troubleshooting

**Symptom** → Production thỉnh thoảng trả conflict dù code update đúng.

**Evidence** → rowversion client gửi khác database.

**Hypothesis** → record đã được update bởi request/background process khác.

**Diagnosis** → xem audit trail và SQL generated; không mặc định coi exception là transient database error.

**Fix** → implement conflict policy; chỉ retry tự động nếu merge semantics thật sự an toàn.

**Verification** → integration test hai DbContext cùng đọc rồi ghi xen kẽ.

## 7. Common mistakes

Catch exception rồi retry `SaveChanges` với entity cũ; không expose token tới client; dùng timestamp business field có precision không phù hợp; áp concurrency toàn entity nhưng UX không giải thích conflict.

## 8. Alternatives

Pessimistic locking phù hợp critical short transaction nhưng giảm concurrency. Domain-specific compare-and-swap có thể dùng version integer. Last-write-wins đơn giản nếu mất update thực sự chấp nhận được.

## 9. Trade-offs

### Advantages

Không giữ lock dài, phát hiện lost update rõ ràng.

### Costs / Risks

Conflict resolution chuyển sang application/UX; retry mù có thể ghi đè dữ liệu hợp lệ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu hai request có thể sửa cùng row.

### Middle
Cấu hình token và xử lý `DbUpdateConcurrencyException`.

### Senior
Thiết kế merge/retry semantics theo business invariant.

### Technical Lead / Architect
Quyết định aggregate nào cần optimistic concurrency và conflict được biểu diễn ra API/UX thế nào.

## 11. Key takeaway

- Optimistic concurrency phát hiện conflict; nó không tự quyết định cách giải quyết.
- Retry chỉ đúng khi business semantics cho phép.
- Concurrency policy là phần của domain/API contract, không chỉ EF Core configuration.

# 3. SQL keyset pagination: ổn định latency khi dữ liệu lớn hơn `OFFSET`

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên sort key cuối cùng đã thấy thay vì yêu cầu database bỏ qua N rows. Ví dụ `WHERE (CreatedAt, Id) < (@lastCreatedAt, @lastId)` theo ordering tương ứng.

## 2. Why does it exist?

`OFFSET 500000 FETCH NEXT 50` vẫn buộc database tìm/sắp xếp/scan qua lượng lớn rows trước khi bỏ chúng. Deep pages ngày càng đắt và dễ thay đổi kết quả khi rows mới được chèn.

## 3. How does it work?

```text
Page 1: ORDER BY CreatedAt DESC, Id DESC LIMIT 50
cursor = last(CreatedAt, Id)
Page 2: WHERE key < cursor ORDER BY ... LIMIT 50
```

Composite ordering phải deterministic; `Id` thường là tie-breaker.

## 4. Practical implementation

```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE CreatedAt < @CreatedAt
   OR (CreatedAt = @CreatedAt AND Id < @Id)
ORDER BY CreatedAt DESC, Id DESC;
```

Index phù hợp có thể là `(CreatedAt DESC, Id DESC)` với included columns tùy workload, nhưng phải xác nhận execution plan/I/O.

## 5. Real production scenario

Order history có 20 triệu rows. UI chỉ cần Next/Previous, không cần “đến trang 87,421”. Keyset giữ latency gần với page đầu thay vì tăng theo offset depth.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate/missing item giữa hai pages.

**Evidence** → ordering chỉ dùng `CreatedAt`, nhiều rows có cùng timestamp.

**Hypothesis** → cursor không xác định total order.

**Diagnosis** → kiểm tra sort keys và concurrent inserts.

**Fix** → thêm unique tie-breaker và encode toàn bộ cursor state.

**Verification** → test nhiều rows cùng timestamp và insert xen giữa requests.

## 7. Common mistakes

Dùng non-unique sort key; expose cursor có thể bị sửa mà không validate; cố dùng keyset khi requirement bắt buộc random page number; thêm index mà không đo reads/write cost.

## 8. Alternatives

Offset pagination đơn giản và tốt cho dataset nhỏ/shallow navigation. Snapshot/export job phù hợp khi cần duyệt toàn bộ tập dữ liệu ổn định.

## 9. Trade-offs

### Advantages

Deep-page performance tốt, ít scan bỏ dữ liệu, ổn định hơn dưới inserts.

### Costs / Risks

Không nhảy page tùy ý dễ dàng; cursor/API phức tạp hơn; sort/index phải được thiết kế cùng nhau.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu OFFSET phải bỏ qua rows.

### Middle
Implement deterministic cursor pagination.

### Senior
Đọc execution plan, logical reads và thiết kế composite index.

### Technical Lead / Architect
Chọn pagination semantics dựa trên UX, scale và consistency requirement.

## 11. Key takeaway

- Pagination là database access pattern, không chỉ API parameter.
- Keyset đặc biệt mạnh cho sequential navigation trên bảng lớn.
- Cursor phải đại diện deterministic ordering.

# 4. Cosmos DB partition key: quyết định locality, throughput và khả năng scale

## 1. What is it?

Partition key quyết định cách documents được phân phối vào logical partitions; Cosmos DB dùng giá trị này để route requests và phân phối storage/throughput trên physical partitions. Đây là quyết định data-modeling cốt lõi, không phải metadata phụ.

## 2. Why does it exist?

Một node không thể chứa và phục vụ dữ liệu vô hạn. Distributed database phải chia dữ liệu để scale. Key tốt phân bố workload nhưng vẫn giữ các access patterns quan trọng có thể route hiệu quả.

## 3. How does it work?

```text
Container
  |-- tenant A ----> partition range
  |-- tenant B ----> partition range
  |-- tenant C ----> partition range
```

Point read có `id + partition key` rất hiệu quả. Query không có partition key có thể fan-out qua nhiều partitions và tiêu thụ RU cao hơn.

## 4. Practical implementation

```csharp
var response = await container.ReadItemAsync<Order>(
    id: orderId,
    partitionKey: new PartitionKey(tenantId),
    cancellationToken: cancellationToken);
```

Nếu SaaS access chủ yếu theo tenant, `/tenantId` thường là candidate nhưng phải đánh giá tenant size/skew; một “mega tenant” có thể thành hot partition.

## 5. Real production scenario

Event platform partition theo `/country`. 70% traffic đến một country nên writes dồn vào một logical key. Tổng RU còn dư nhưng request vẫn bị throttled tại hotspot.

## 6. Failure scenario & troubleshooting

**Symptom** → 429 tăng trong khi aggregate RU utilization không cao.

**Evidence** → metrics theo partition key range cho thấy skew.

**Hypothesis** → hot partition.

**Diagnosis** → phân tích request distribution, item size, query fan-out và key cardinality.

**Fix** → thay access pattern/model hoặc synthetic/hierarchical partition strategy khi phù hợp; migration thường không rẻ.

**Verification** → load test với realistic key distribution, không chỉ uniform synthetic data.

## 7. Common mistakes

Chọn key cardinality thấp; chọn random GUID để phân bố đẹp nhưng phá query locality; nghĩ tăng RU luôn sửa hotspot; thiết kế schema trước rồi chọn partition key sau.

## 8. Alternatives

SQL/PostgreSQL phù hợp nếu relational transactions/joins là trung tâm. MongoDB có sharding với trade-offs tương tự. Không nên chọn Cosmos DB chỉ vì “NoSQL scale”.

## 9. Trade-offs

### Advantages

Horizontal scale, predictable routing, point reads hiệu quả khi model đúng.

### Costs / Risks

Partition-key mistake khó sửa; cross-partition query tốn RU; distribution thực tế có thể skew.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu partition key quyết định dữ liệu nằm đâu.

### Middle
Thực hiện point read/query với key và đo RU.

### Senior
Phân tích cardinality, skew, hot partition và consistency/access patterns.

### Technical Lead / Architect
Chọn data model dựa trên workload dự kiến và kế hoạch migration nếu partition strategy không còn phù hợp.

## 11. Key takeaway

- Partition key là architectural decision.
- Distribution tốt nhưng query locality tệ vẫn là thiết kế xấu.
- Đo RU theo access pattern và skew thật.

# 5. Outbox Pattern: nối database transaction với message delivery mà không cần distributed transaction

## 1. What is it?

Outbox Pattern ghi business state và message-to-be-published vào cùng local database transaction. Một publisher riêng đọc outbox và gửi message ra broker. Nó tránh “DB commit nhưng publish fail” mà không yêu cầu atomic transaction xuyên database + broker.

## 2. Why does it exist?

Code kiểu `SaveChanges(); Publish();` có failure window. Nếu process chết sau DB commit trước publish, downstream không bao giờ biết thay đổi. Đảo thứ tự lại tạo trường hợp message được publish nhưng DB rollback.

## 3. How does it work?

```text
Request
  |
  +-- DB transaction ----------------+
  |   update Order                    |
  |   insert OutboxMessage            |
  +-----------------------------------+
                  |
             Outbox Publisher
                  |
                  v
            Service Bus
                  |
          idempotent consumer
```

Outbox bảo đảm durable intent-to-publish; delivery vẫn thường at-least-once nên consumer phải xử lý duplicate.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

order.MarkPaid();
db.OutboxMessages.Add(new OutboxMessage(
    Guid.NewGuid(), "OrderPaid", JsonSerializer.Serialize(payload)));

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Publisher chỉ đánh dấu sent sau broker acknowledgement; cần retry và cleanup policy.

## 5. Real production scenario

Payment API cập nhật `Order=Paid` rồi phát `OrderPaid`. Notification và fulfillment subscribe event. Broker outage 3 phút không làm mất event: outbox rows tích lại và publisher gửi sau khi broker hồi phục.

## 6. Failure scenario & troubleshooting

**Symptom** → downstream nhận cùng event hai lần.

**Evidence** → publisher gửi thành công nhưng crash trước khi đánh dấu outbox sent.

**Hypothesis** → duplicate delivery hợp lệ của protocol.

**Diagnosis** → correlate MessageId/outbox id.

**Fix** → consumer Inbox/unique processed-message key và idempotent side effect.

**Verification** → inject crash sau publish trước state update.

## 7. Common mistakes

Tuyên bố exactly-once; outbox table tăng vô hạn; publisher không có backpressure; serialize domain object nội bộ thành public event contract; transaction chứa remote broker call.

## 8. Alternatives

Distributed transaction có thể tồn tại trong một số stack nhưng tăng coupling/operational constraints. CDC có thể publish DB changes nhưng cần mapping business semantics. Với hệ thống đơn giản không có messaging, đừng thêm Outbox chỉ vì pattern phổ biến.

## 9. Trade-offs

### Advantages

Loại bỏ critical dual-write window, không cần cross-system transaction.

### Costs / Risks

Eventual consistency, duplicate handling, publisher/cleanup/monitoring mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu vấn đề DB + broker không commit atomically.

### Middle
Implement transactional outbox và publisher retry.

### Senior
Thiết kế idempotency, ordering, cleanup, backlog monitoring.

### Technical Lead / Architect
Quyết định nơi eventual consistency chấp nhận được và contract ownership giữa bounded contexts.

## 11. Key takeaway

- Outbox biến publish intent thành durable database state.
- Nó không tạo exactly-once delivery.
- Consumer idempotency và outbox observability là phần bắt buộc của thiết kế.

# 6. Azure Blob Storage large-file upload: streaming, SAS và failure recovery

## 1. What is it?

Large-file upload nên truyền dữ liệu theo stream/chunks thay vì đọc toàn bộ file vào application memory. Azure Blob Storage hỗ trợ block blobs, parallel transfer và SAS để client có thể upload trực tiếp với quyền giới hạn.

## 2. Why does it exist?

Nếu API nhận file 2 GB rồi `ReadAllBytes`, vài concurrent uploads có thể làm memory pressure/LOH/GC hoặc OOM. Proxy timeout cũng làm request dài dễ thất bại.

## 3. How does it work?

```text
Option A: Client -> API stream -> Blob
Option B: Client -> API gets short-lived SAS
                  Client ----------> Blob
                  API records metadata
```

Direct-to-Blob giảm data-plane load trên API nhưng cần upload authorization/finalization workflow.

## 4. Practical implementation

```csharp
await blobClient.UploadAsync(
    request.Body,
    new BlobUploadOptions
    {
        HttpHeaders = new BlobHttpHeaders
        {
            ContentType = request.ContentType
        }
    },
    cancellationToken);
```

Không tin `ContentType`/filename từ client cho security decisions; validate size/type theo policy.

## 5. Real production scenario

CMS cho editor upload video. API cấp write-only SAS cho một blob path scoped theo tenant và expiry 10 phút. Client upload trực tiếp; sau đó gọi finalize endpoint để application kiểm tra metadata/scanning state trước khi publish content.

## 6. Failure scenario & troubleshooting

**Symptom** → blob tồn tại nhưng database không có asset record.

**Evidence** → client upload thành công nhưng finalize request fail.

**Hypothesis** → direct upload tạo orphan blob.

**Diagnosis** → so sánh storage inventory với upload-session table.

**Fix** → staging prefix/container + lifecycle cleanup + explicit finalize state machine.

**Verification** → simulate disconnect giữa upload và finalize.

## 7. Common mistakes

SAS quá rộng/quá lâu; buffer file toàn bộ; public container ngoài ý muốn; tin extension; không cleanup orphan blocks/blobs; đồng nhất “upload xong” với “file an toàn để phục vụ”.

## 8. Alternatives

API proxy upload đơn giản hơn cho file nhỏ và central validation. Direct SAS tốt cho file lớn. Background ingestion phù hợp khi cần virus scanning/transcoding trước publish.

## 9. Trade-offs

### Advantages

Giảm memory/network pressure trên app, tận dụng storage scalability.

### Costs / Risks

Workflow nhiều trạng thái, SAS security, orphan cleanup, scanning/finalization complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu stream khác load toàn file vào memory.

### Middle
Implement upload với cancellation, limits và scoped SAS.

### Senior
Thiết kế staging/finalization, security scanning và retry.

### Technical Lead / Architect
Chọn data path dựa trên file size, trust boundary, cost và operational ownership.

## 11. Key takeaway

- Large files là streaming/workflow problem, không chỉ storage API.
- SAS phải least-privilege và short-lived.
- Direct upload cần trạng thái finalize và orphan cleanup.

# 7. Application Insights dependency telemetry: điều tra p95 latency theo dependency

## 1. What is it?

Dependency telemetry ghi lại outbound calls như SQL, HTTP, Redis với duration, success và correlation tới request/trace. Nó giúp phân biệt “API chậm” với “dependency mà API đang chờ bị chậm”.

## 2. Why does it exist?

Average latency có thể ổn trong khi 5% request cực chậm. Nếu chỉ nhìn request duration tổng, team dễ tối ưu code sai tầng.

## 3. How does it work?

```text
Request 1.2s
  |-- application CPU 40ms
  |-- SQL 80ms
  |-- Pricing API 1.05s
```

Correlation/trace context nối request với dependency spans. Metrics/queries sau đó group theo target, operation và percentile.

## 4. Practical implementation

Ví dụ KQL:

```kusto
dependencies
| where timestamp > ago(1h)
| summarize p95=percentile(duration, 95), failures=countif(success == false)
  by target, type
| order by p95 desc
```

Dùng cùng deployment marker để kiểm tra regression trước/sau release.

## 5. Real production scenario

Checkout p95 tăng từ 450 ms lên 1.8 s sau 14:00. CPU/API instance bình thường. Dependency telemetry cho thấy external tax API p95 tăng 4x; SQL không đổi. Điều tra chuyển sang timeout/fallback/vendor thay vì scale App Service mù.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard nói HTTP dependency nhanh nhưng user vẫn chậm.

**Evidence** → trace thiếu queue wait/client retry hoặc sampling bỏ spans liên quan.

**Hypothesis** → telemetry model không bao phủ toàn critical path.

**Diagnosis** → so sánh end-to-end request span với child spans và unaccounted duration.

**Fix** → bổ sung custom spans/metrics có semantic value và kiểm tra sampling.

**Verification** → trace duration được giải thích bởi các phase chính.

## 7. Common mistakes

Chỉ xem average; high-cardinality dimensions không kiểm soát; log PII; alert trên từng transient failure; không gắn deployment version.

## 8. Alternatives

OpenTelemetry + backend khác cho portability. Structured logs có correlation đủ cho hệ thống nhỏ nhưng khó percentile/dependency analysis hơn.

## 9. Trade-offs

### Advantages

Nhanh localize bottleneck, hỗ trợ incident triage dựa trên evidence.

### Costs / Risks

Telemetry ingestion cost, sampling, privacy/cardinality management.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu request duration gồm thời gian chờ dependencies.

### Middle
Dùng trace/KQL để tìm dependency chậm.

### Senior
Phân tích p95/p99, sampling và regression theo release.

### Technical Lead / Architect
Định nghĩa SLI, telemetry standard, retention và cost budget.

## 11. Key takeaway

- p95/p99 cho thấy tail latency mà average che mất.
- Dependency telemetry giúp tìm đúng ownership của bottleneck.
- Observability phải giải thích critical path, không chỉ thu nhiều logs.

# 8. Blue-Green deployment và database compatibility: deploy application không đồng nghĩa schema có thể đổi tùy ý

## 1. What is it?

Blue-Green giữ hai application environments: version hiện tại và version mới. Traffic được chuyển khi Green đã health-validated. Nhưng nếu cả hai versions dùng cùng database, schema phải tương thích trong giai đoạn coexist/rollback.

## 2. Why does it exist?

Application rollback nhanh vô nghĩa nếu migration đã drop/rename column mà old version cần. Deployment safety phải bao gồm database evolution, không chỉ binary switching.

## 3. How does it work?

```text
Blue v1 ----+
             +--> Shared DB schema compatible with v1 + v2
Green v2 ---+

1. Expand schema
2. Deploy compatible v2
3. migrate/backfill data
4. switch traffic
5. observe
6. contract old schema later
```

Đây thường gọi là expand-and-contract migration.

## 4. Practical implementation

Thay vì rename `Name -> DisplayName` trực tiếp:

```sql
ALTER TABLE Customers ADD DisplayName nvarchar(200) NULL;
```

v2 tạm thời đọc fallback từ `Name`, ghi theo migration strategy; backfill; chỉ drop `Name` ở release sau khi không còn code phụ thuộc.

## 5. Real production scenario

Green chạy tốt 10 phút rồi error rate tăng. Team switch traffic về Blue. Nếu migration đã drop column Blue cần, rollback application vẫn fail. Compatible schema giữ rollback path thực sự tồn tại.

## 6. Failure scenario & troubleshooting

**Symptom** → rollback deployment thành công nhưng Blue trả SQL “invalid column”.

**Evidence** → migration contract chạy cùng release.

**Hypothesis** → application rollback và database rollback không tương thích.

**Diagnosis** → compare schema requirement của cả hai versions.

**Fix** → expand-contract, tách destructive migration khỏi initial rollout.

**Verification** → pre-production test chạy v1 và v2 đồng thời trên migrated schema.

## 7. Common mistakes

Blue-Green nhưng dùng irreversible migration; migration dài khóa bảng trong deploy; health check chỉ `/health` không test critical path; switch 100% traffic ngay mà không quan sát.

## 8. Alternatives

Rolling deployment đơn giản hơn nhưng versions coexist vẫn cần compatibility. Canary giảm blast radius. Feature flags tách code deployment khỏi feature exposure nhưng không tự giải quyết schema migration.

## 9. Trade-offs

### Advantages

Cutover/rollback nhanh, environment validation tốt.

### Costs / Risks

Tốn environment capacity; database vẫn là shared coupling; schema evolution chậm hơn vì cần compatibility window.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu deploy mới và DB migration là hai lifecycle liên quan.

### Middle
Viết backward-compatible migrations.

### Senior
Thiết kế expand/backfill/contract và rollback validation.

### Technical Lead / Architect
Quyết định release strategy, compatibility window và ownership của destructive migrations.

## 11. Key takeaway

- Blue-Green chỉ an toàn khi shared dependencies cũng hỗ trợ coexistence.
- Database rollback thường khó hơn application rollback.
- Destructive schema change nên tách khỏi release đầu tiên.

# 9. React stale closure: khi async callback đọc state cũ

## 1. What is it?

JavaScript closure giữ references/values theo lexical scope của render đã tạo callback. Trong React functional components, mỗi render có snapshot state riêng. Async callback/timer có thể chạy sau và quan sát state từ render cũ: stale closure.

## 2. Why does it exist?

React render model ưu tiên predictable immutable snapshots. Nhưng async operations sống lâu hơn một render, nên developer phải hiểu callback đang capture snapshot nào.

## 3. How does it work?

```text
Render #1: count=0 -> callback captures count=0
setCount(1)
Render #2: count=1
...later callback from Render #1 executes -> sees 0
```

## 4. Practical implementation

Sai trong nhiều concurrent updates:

```tsx
setCount(count + 1);
```

Khi update phụ thuộc previous state, dùng functional update:

```tsx
setCount(current => current + 1);
```

Với effect, dependencies phải phản ánh values được sử dụng; đừng tắt lint rule chỉ để hết warning.

## 5. Real production scenario

Search component gửi request cho query A rồi query B. Response A về sau B và overwrite UI bằng dữ liệu cũ. Đây là async race liên quan lifecycle, không chỉ “React render chậm”.

## 6. Failure scenario & troubleshooting

**Symptom** → kết quả search đôi lúc quay về query trước.

**Evidence** → network waterfall cho thấy responses về ngược thứ tự.

**Hypothesis** → stale async result được commit.

**Diagnosis** → log request id/query tại dispatch và completion.

**Fix** → abort request cũ bằng `AbortController` hoặc chỉ accept result của request hiện hành.

**Verification** → throttle network và gõ nhanh để force out-of-order completion.

## 7. Common mistakes

Thiếu effect dependencies; mutate state; dùng `useRef` để né mọi rerender; không cancel fetch; cho rằng response order luôn bằng request order.

## 8. Alternatives

Data-fetching libraries có thể quản lý cancellation/cache/request identity. Với component đơn giản, native effect + AbortController đủ tốt; không cần thêm state framework chỉ vì một race.

## 9. Trade-offs

### Advantages

Snapshot model giúp render reasoning rõ.

### Costs / Risks

Async lifecycle cần explicit cancellation/request identity; hooks dễ bị dùng sai nếu không hiểu closure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu mỗi render có state snapshot.

### Middle
Dùng functional update, dependencies và cancellation đúng.

### Senior
Debug race qua DevTools/network timeline và thiết kế API/UI resilient với out-of-order response.

### Technical Lead / Architect
Chuẩn hóa data-fetching strategy ở frontend mà không overengineer state management.

## 11. Key takeaway

- Async callback có thể thuộc render cũ.
- Out-of-order responses là failure mode thực tế.
- Cancellation/request identity thường quan trọng hơn thêm state library.

# 10. AI RAG: retrieval grounding không đồng nghĩa câu trả lời luôn đúng

## 1. What is it?

Retrieval-Augmented Generation (RAG) lấy các chunks liên quan từ knowledge source rồi đưa chúng vào model context để model tạo câu trả lời dựa trên evidence. Retrieval giảm phụ thuộc vào model parametric knowledge nhưng không biến output thành deterministic truth.

## 2. Why does it exist?

Enterprise knowledge thay đổi liên tục, private và quá lớn để nhét toàn bộ vào prompt. RAG cho phép chọn context liên quan tại runtime mà không fine-tune model cho mỗi document update.

## 3. How does it work?

```text
Question
   |
embedding / query rewrite
   |
retrieve candidates
   |
filter/rerank
   |
context + instructions
   |
LLM
   |
answer + citations
```

Failure có thể xảy ra ở retrieval, chunking, ranking hoặc generation.

## 4. Practical implementation

Application nên giữ authorization deterministic trước retrieval:

```csharp
var allowedDocumentIds = await authorization.GetReadableDocumentsAsync(userId, ct);
var hits = await search.SearchAsync(query, allowedDocumentIds, ct);
var response = await llm.AnswerAsync(query, hits, ct);
```

Không retrieve toàn tenant rồi yêu cầu model “đừng tiết lộ tài liệu user không được xem”.

## 5. Real production scenario

Internal support assistant trả lời policy từ SharePoint/knowledge base. Document mới được index nhưng chunk có exception clause nằm xa main rule. Retrieval chỉ lấy main rule, model trả lời tự tin nhưng thiếu exception.

## 6. Failure scenario & troubleshooting

**Symptom** → answer sai dù source document chứa câu đúng.

**Evidence** → trace cho thấy correct chunk không nằm trong top-k.

**Hypothesis** → retrieval failure, không phải generation failure.

**Diagnosis** → lưu evaluation trace gồm query, retrieved IDs/scores, reranked context và final answer.

**Fix** → cải thiện chunking, hybrid search/reranking/query rewrite; thêm abstention khi evidence yếu.

**Verification** → regression evaluation trên curated question set, đo retrieval recall riêng với answer quality.

## 7. Common mistakes

Chỉ đo “câu trả lời nghe hay”; vector search không filter ACL; chunks quá lớn/nhỏ; không version index; đưa retrieved text như trusted instruction và mở prompt-injection path; không có citations/evaluation.

## 8. Alternatives

Deterministic database/query API tốt hơn cho số dư, authorization, financial state. Full-text/hybrid search đủ nếu user cần tài liệu chứ không cần synthesized answer. Fine-tuning không phải thay thế trực tiếp cho fresh private knowledge retrieval.

## 9. Trade-offs

### Advantages

Grounding vào private/fresh knowledge, cập nhật corpus không cần retrain model.

### Costs / Risks

Retrieval latency/cost, index synchronization, ACL complexity, hallucination vẫn tồn tại, evaluation khó.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu RAG = retrieve evidence rồi generate.

### Middle
Build ingestion, chunking, retrieval và citations cơ bản.

### Senior
Đo retrieval recall, generation quality, latency, cost và prompt-injection risks.

### Technical Lead / Architect
Quyết định phần nào dùng probabilistic AI, phần nào phải deterministic; thiết kế authorization, evaluation và observability boundary.

## 11. Key takeaway

- RAG có ít nhất hai hệ thống cần debug: retrieval và generation.
- Authorization phải được enforce trước/ở retrieval layer, không giao cho model.
- Grounded output vẫn cần evaluation, citations và khả năng abstain.
