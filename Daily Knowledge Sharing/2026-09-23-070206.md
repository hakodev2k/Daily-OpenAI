# 1. `CancellationToken` propagation: cancellation là cooperative contract, không phải force-kill

## 1. What is it?

`CancellationToken` là tín hiệu cooperative cancellation. Nó không cưỡng bức kill thread hay rollback mọi side effect đã xảy ra. Code nhận token phải chủ động quan sát token hoặc truyền token xuống operation hỗ trợ cancellation.

Trong ASP.NET Core, `HttpContext.RequestAborted` phản ánh client/request bị hủy. Khi endpoint truyền token xuống EF Core, `HttpClient`, queue/client API hoặc internal services, toàn bộ call chain có cơ hội dừng công việc không còn giá trị.

## 2. Why does it exist?

Nếu client timeout sau 3 giây nhưng server tiếp tục query database 30 giây, gọi external API và serialize response mà không ai nhận, tài nguyên Production vẫn bị tiêu thụ. Khi traffic cao, “orphaned work” có thể làm pool/thread/connection bị chiếm và khuếch đại overload.

Cancellation tồn tại để lifetime của công việc bám sát lifetime của operation business/request.

## 3. How does it work?

```text
Client disconnect
      |
      v
RequestAborted cancelled
      |
      +--> Application service
      |       |
      |       +--> EF Core
      |       +--> HttpClient
      |       +--> other async work
      |
      v
OperationCanceledException / early exit
```

Token chỉ là signal. Nếu một synchronous CPU loop không kiểm tra token, nó vẫn chạy.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    OrdersDbContext db,
    HttpClient client,
    CancellationToken cancellationToken) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    if (order is null)
        return Results.NotFound();

    var risk = await client.GetFromJsonAsync<RiskResult>(
        $"risk/{id}", cancellationToken);

    return Results.Ok(new { order.Id, order.Total, risk });
});
```

Internal methods cũng phải nhận và truyền token thay vì tạo `CancellationToken.None` tùy tiện.

## 5. Real production scenario

Search API có timeout phía gateway 5 giây. Elasticsearch query đôi lúc mất 20 giây. Nếu request cancellation không propagate, gateway đã trả timeout nhưng backend vẫn giữ connection và compute. Dưới spike, các query “vô chủ” làm cluster càng chậm.

## 6. Failure scenario & troubleshooting

**Symptom** → gateway timeout tăng, nhưng database/external dependency vẫn có lượng work cao nhiều giây sau khi request kết thúc.

**Evidence** → traces cho thấy parent request đã kết thúc nhưng dependency spans tiếp tục; code không truyền token.

**Hypothesis** → cancellation bị cắt tại application boundary.

**Diagnosis** → trace call chain và kiểm tra method signatures.

**Fix** → propagate token; đặt explicit timeout cho dependency nếu business timeout khác request timeout.

**Verification** → cancel load test request và xác nhận dependency operation dừng sớm.

## 7. Common mistakes

Nuốt `OperationCanceledException` rồi log Error; dùng một token toàn application cho request work; cancel sau khi irreversible side effect đã commit rồi giả định transaction được hoàn tác; truyền token nhưng library operation không hỗ trợ cancellation.

## 8. Alternatives

Timeout giới hạn thời gian; cancellation truyền intent dừng. Hai cơ chế bổ sung nhau. Với durable background work, client disconnect không nên cancel business process đã được accepted; nên persist/enqueue rồi trả `202 Accepted`.

## 9. Trade-offs

### Advantages

Giảm wasted work, cải thiện overload behavior, giải phóng dependency resources sớm.

### Costs / Risks

Cần propagate xuyên nhiều layer; cancellation ở sai boundary có thể bỏ dở workflow; phải hiểu side effect nào đã commit.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cancellation là cooperative signal.

### Middle

Truyền token end-to-end qua async APIs và xử lý cancellation khác failure.

### Senior

Xác định cancellation boundary quanh transactions, external calls và background work.

### Technical Lead / Architect

Định nghĩa timeout/cancellation budget xuyên service chain và quyết định workflow nào phải durable dù request biến mất.

## 11. Key takeaway

- Token không kill thread; code phải cooperate.
- Cancellation phải propagate tới dependency thật sự đang tiêu thụ tài nguyên.
- Không cancel durable business work chỉ vì HTTP client disconnect nếu operation đã được accepted.

# 2. EF Core optimistic concurrency: bảo vệ lost update bằng concurrency token

## 1. What is it?

Optimistic concurrency giả định conflict hiếm, nên không giữ lock business record trong suốt thời gian user đọc/chỉnh sửa. Khi update, application kiểm tra record có còn ở version đã đọc hay không.

EF Core hỗ trợ concurrency token như SQL Server `rowversion` hoặc application-managed version. Nếu `UPDATE ... WHERE Id = @id AND Version = @oldVersion` ảnh hưởng 0 rows, EF Core ném `DbUpdateConcurrencyException`.

## 2. Why does it exist?

Hai user có thể mở cùng order. A sửa status, B sửa shipping address từ snapshot cũ. Nếu mỗi update ghi toàn bộ entity mà không phát hiện version thay đổi, B có thể vô tình ghi đè thay đổi của A: lost update.

## 3. How does it work?

```text
Read: Id=42, Version=7
        |
User edits
        |
UPDATE ... WHERE Id=42 AND Version=7
        |
   +----+----+
   |         |
1 row      0 rows
success    conflict
```

## 4. Practical implementation

```csharp
public class Order
{
    public Guid Id { get; set; }
    public string Status { get; set; } = null!;

    [Timestamp]
    public byte[] Version { get; set; } = null!;
}
```

API nên round-trip version, ví dụ qua DTO/ETag. Khi conflict, application có thể trả `409 Conflict` hoặc `412 Precondition Failed` tùy HTTP contract.

## 5. Real production scenario

Approval workflow có manager và finance cùng chỉnh request. Không có concurrency control, update sau cùng thắng dù dựa trên state cũ. Với token, conflict được phát hiện và user phải reload/merge theo business rule.

## 6. Failure scenario & troubleshooting

**Symptom** → thay đổi của user “biến mất” không có exception.

**Evidence** → generated SQL chỉ có `WHERE Id = ...`, không có concurrency predicate.

**Hypothesis** → entity chưa cấu hình concurrency token hoặc DTO không mang original version.

**Diagnosis** → inspect EF model metadata/generated SQL.

**Fix** → cấu hình token, preserve original version và xử lý `DbUpdateConcurrencyException` rõ ràng.

**Verification** → integration test hai DbContext đọc cùng version rồi update cạnh tranh.

## 7. Common mistakes

Retry concurrency exception tự động bằng state cũ; dùng timestamp thời gian với precision không đảm bảo; bắt exception rồi overwrite database; expose conflict như generic 500; giả định transaction isolation tự giải quyết long-lived user editing.

## 8. Alternatives

Pessimistic locking phù hợp critical short transaction nhưng không nên giữ DB lock qua user think-time. Domain-specific merge phù hợp khi fields độc lập có thể hòa giải. Event sourcing lưu history nhưng complexity lớn hơn nhiều.

## 9. Trade-offs

### Advantages

Không giữ long lock, phát hiện lost update, scale tốt khi conflict hiếm.

### Costs / Risks

Application phải có conflict UX/business policy; retry không luôn an toàn; version phải đi qua API contract đúng cách.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu last-write-wins có thể làm mất dữ liệu.

### Middle

Cấu hình concurrency token và viết integration test conflict.

### Senior

Thiết kế merge/retry/conflict semantics theo aggregate invariant.

### Technical Lead / Architect

Quyết định entity nào cần optimistic concurrency và contract HTTP nào biểu diễn conflict ổn định.

## 11. Key takeaway

- Optimistic concurrency phát hiện snapshot cũ tại thời điểm write.
- `DbUpdateConcurrencyException` là business concurrency signal, không đơn thuần infrastructure failure.
- Không auto-retry nếu chưa biết merge semantics.

# 3. PostgreSQL composite index: thứ tự cột quyết định access path, không chỉ “có index hay không”

## 1. What is it?

Composite index chứa nhiều columns theo một thứ tự xác định, ví dụ `(tenant_id, status, created_at)`. Thứ tự này ảnh hưởng mạnh đến predicates và ordering mà PostgreSQL có thể tận dụng hiệu quả.

Index phải được thiết kế theo access pattern, selectivity và sort/range behavior, không theo thứ tự fields trong entity.

## 2. Why does it exist?

Production query thường lọc theo nhiều dimensions: tenant, trạng thái, thời gian. Nhiều single-column indexes không luôn tương đương một composite index phù hợp; planner có thể bitmap-combine nhưng cost khác và ordering không tự có.

## 3. How does it work?

Với B-tree `(tenant_id, status, created_at)`, dữ liệu index được ordered lexicographically. Query:

```sql
WHERE tenant_id = $1
  AND status = 'Open'
ORDER BY created_at DESC
LIMIT 50
```

có thể tận dụng prefix equality rồi scan theo `created_at` hiệu quả. Query chỉ theo `created_at` thường không hưởng cùng lợi ích từ leading columns.

## 4. Practical implementation

```sql
CREATE INDEX CONCURRENTLY ix_orders_tenant_status_created
ON orders (tenant_id, status, created_at DESC)
INCLUDE (total, customer_id);
```

Đánh giá bằng:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total, customer_id, created_at
FROM orders
WHERE tenant_id = 42
  AND status = 'Open'
ORDER BY created_at DESC
LIMIT 50;
```

## 5. Real production scenario

Multi-tenant SaaS có 80 triệu orders. Endpoint dashboard luôn scope theo tenant rồi status và lấy newest 50. Index chỉ trên `created_at` buộc database scan/filter nhiều rows; composite index aligned với access pattern giảm I/O đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → đã thêm index nhưng planner vẫn dùng sequential scan.

**Evidence** → `EXPLAIN ANALYZE` cho thấy predicate không match useful prefix hoặc query trả tỷ lệ lớn table; statistics cho thấy low selectivity.

**Hypothesis** → index design không phù hợp access pattern.

**Diagnosis** → xem actual rows, buffers, estimates và predicates.

**Fix** → redesign index dựa trên real query; update statistics nếu estimates sai; không ép index mù quáng.

**Verification** → so sánh execution time, buffer reads và write overhead.

## 7. Common mistakes

Tạo index cho mọi filter combination; đặt range column trước equality columns mà không lý do; bỏ qua write amplification; benchmark trên dataset nhỏ; chỉ nhìn estimated cost mà không chạy `ANALYZE` ở môi trường an toàn.

## 8. Alternatives

Single-column indexes đủ cho simple access patterns. Partial index tốt khi query tập trung subset như `WHERE status='Open'`. BRIN hữu ích cho very large naturally ordered data nhưng semantics khác B-tree.

## 9. Trade-offs

### Advantages

Giảm I/O, có thể hỗ trợ filter + order, covering query qua `INCLUDE`.

### Costs / Risks

Tăng storage, write cost, vacuum/index maintenance và migration complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index là ordered access structure, không phải magic speed flag.

### Middle

Đọc `EXPLAIN ANALYZE` và thiết kế index cho query cụ thể.

### Senior

Cân bằng selectivity, ordering, range predicates, write amplification và cardinality.

### Technical Lead / Architect

Thiết kế indexing strategy theo workload/SLO thay vì từng ticket performance riêng lẻ.

## 11. Key takeaway

- Composite index order là một phần của query design.
- Đo execution plan + I/O trước và sau thay đổi.
- Read nhanh hơn luôn đổi lấy storage/write/maintenance cost.

# 4. Redis hot key: cache có thể giảm tải database nhưng tạo bottleneck tập trung mới

## 1. What is it?

Hot key là key nhận tỷ lệ traffic rất lớn so với phần còn lại. Dù Redis nhanh, một key hoặc shard chứa key đó có thể trở thành bottleneck về CPU/network trong clustered deployment.

Cache phân tán không đảm bảo load tự động phân tán nếu access distribution cực lệch.

## 2. Why does it exist?

Một homepage config, viral product hoặc global feature configuration có thể được hàng nghìn instances/users đọc cùng key. Database được bảo vệ nhưng traffic tập trung sang Redis node.

## 3. How does it work?

```text
10k clients
   \ | /
    \|/
  key:product:viral
        |
        v
   Redis shard #3  <-- concentrated load
```

Cluster partitions theo key hash; một key không tự chia across shards.

## 4. Practical implementation

Với dữ liệu chấp nhận freshness ngắn, có thể dùng two-level cache:

```csharp
if (memoryCache.TryGetValue(key, out ProductDto? local))
    return local!;

var json = await redis.StringGetAsync(key);
var product = JsonSerializer.Deserialize<ProductDto>(json!)!;

memoryCache.Set(key, product, TimeSpan.FromSeconds(10));
return product;
```

Local cache 10 giây hấp thụ repeated reads trên từng instance; phải cân nhắc stale data/invalidation.

## 5. Real production scenario

Flash sale làm một SKU nhận 40% traffic toàn site. Redis CPU trên một shard tăng cao trong khi shards khác nhàn. Team tưởng cache cluster còn capacity vì average CPU thấp.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis latency tăng nhưng cluster average utilization bình thường.

**Evidence** → per-node metrics và key access sampling cho thấy một shard/key vượt trội.

**Hypothesis** → hot key concentration.

**Diagnosis** → correlate command rate, network, shard CPU và top keys.

**Fix** → local caching nếu freshness cho phép; redesign key/data; request coalescing; scale appropriate tier. Key replication/sharding thủ công chỉ dùng khi hiểu consistency cost.

**Verification** → per-shard load cân bằng hơn và p95 cache latency giảm.

## 7. Common mistakes

Chỉ scale cluster nodes; đặt TTL giống nhau khiến mass expiration; cache giant object hot key; dùng distributed lock quanh mọi read; không đo per-shard metrics.

## 8. Alternatives

`IMemoryCache` phù hợp data nhỏ chấp nhận per-instance copies. CDN phù hợp public HTTP data. Database/read replica đôi khi đủ nếu workload không cần Redis.

## 9. Trade-offs

### Advantages

Redis giảm database round trips và latency.

### Costs / Risks

Hot keys, stale data, extra dependency, serialization/network overhead và operational cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache không loại bỏ bottleneck; nó có thể di chuyển bottleneck.

### Middle

Thiết kế key/TTL và đo hit rate/latency.

### Senior

Phân tích per-shard load, hot-key mitigation và consistency impact.

### Technical Lead / Architect

Quyết định liệu Redis có thực sự cần thiết và failure/freshness contract của cache layer.

## 11. Key takeaway

- Distributed cache không đồng nghĩa distributed load cho một key.
- Đo per-key/per-shard, không chỉ cluster average.
- Local cache/CDN đôi khi là lớp hấp thụ hot-read đơn giản hơn.

# 5. Saga Pattern: consistency xuyên services bằng local transaction và compensation

## 1. What is it?

Saga là chuỗi local transactions trong nhiều services. Mỗi bước commit state riêng; nếu bước sau thất bại, workflow thực hiện compensating actions thay vì rollback một ACID transaction toàn hệ thống.

Compensation là business action mới, không phải time-travel rollback.

## 2. Why does it exist?

Trong Microservices, giữ distributed transaction qua Order, Payment, Inventory thường khó vận hành, coupling cao hoặc không được hạ tầng hỗ trợ. Nhưng business workflow vẫn cần consistency ở mức nghiệp vụ.

## 3. How does it work?

```text
Create Order
    |
Reserve Inventory
    |
Charge Payment ----X---- failure
    |
    +--> Release Inventory
    +--> Cancel Order
```

Saga có thể orchestration bởi coordinator hoặc choreography bằng events. Mỗi message/action phải chịu được duplicate delivery.

## 4. Practical implementation

State machine đơn giản:

```csharp
public enum CheckoutState
{
    Pending,
    InventoryReserved,
    Paid,
    Completed,
    Compensating,
    Failed
}
```

Persist state trước/đồng thời với reliable message publication bằng Outbox. Consumer dùng Inbox/idempotency key để tránh compensation chạy hai lần gây side effect mới.

## 5. Real production scenario

Order service tạo order, Inventory reserve stock, Payment charge card. Shipping creation fail không nhất thiết refund ngay nếu business cho phép retry shipping. Saga policy phải phân biệt technical transient failure với business failure cần compensation.

## 6. Failure scenario & troubleshooting

**Symptom** → customer bị refund nhưng inventory vẫn reserved.

**Evidence** → trace/event history cho thấy compensation message bị dead-letter.

**Hypothesis** → compensation itself failed.

**Diagnosis** → inspect saga state, outbox/inbox, DLQ và correlation ID.

**Fix** → retry bounded, operator recovery workflow và idempotent compensation.

**Verification** → reconcile final business invariants across services.

## 7. Common mistakes

Gọi mọi multi-service workflow là Saga; không persist saga state; compensation giả định luôn thành công; choreography quá nhiều events khiến ownership mơ hồ; dùng Saga khi một local transaction trong Modular Monolith đã đủ.

## 8. Alternatives

Local ACID transaction đơn giản hơn nếu boundary cho phép. Transactional Outbox giải quyết reliable publication nhưng không tự giải quyết multi-step business compensation. Distributed transaction có thể phù hợp trong controlled homogeneous environment nhưng operational coupling cao.

## 9. Trade-offs

### Advantages

Không cần global lock/transaction coordinator; services giữ local autonomy; phù hợp long-running workflow.

### Costs / Risks

Eventual consistency, compensation complexity, debugging khó, cần durable state/observability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu đã commit local transaction thì không thể “rollback từ xa” như cùng DB.

### Middle

Implement idempotent step/compensation và correlation.

### Senior

Thiết kế state machine, retries, failure classification và recovery.

### Technical Lead / Architect

Quyết định có thực sự cần distributed workflow hay boundary hiện tại đang bị chia quá sớm.

## 11. Key takeaway

- Saga quản lý business consistency, không cung cấp global ACID.
- Compensation cũng có thể fail và phải được vận hành như first-class workflow.
- Nếu một local transaction đủ, đừng thêm Saga.

# 6. Azure App Service deployment slots: zero/low-downtime release không đồng nghĩa database migration an toàn

## 1. What is it?

Deployment slot là live App Service environment riêng như `staging` có thể deploy/warm-up trước khi swap vào production. Swap giảm application deployment downtime nhưng database thường vẫn là shared external state.

## 2. Why does it exist?

Deploy trực tiếp lên production instance có thể tạo cold start, partially updated files hoặc rollback chậm. Slot cho phép validate artifact/config trước cutover.

## 3. How does it work?

```text
Production slot -> v1
Staging slot    -> v2 (warm + health check)
        |
      swap
        v
Production slot -> v2
Staging slot    -> v1
```

Database không tự rollback khi swap ngược.

## 4. Practical implementation

Release flow:

```text
build immutable artifact
-> deploy staging
-> run health/smoke tests
-> apply backward-compatible DB migration
-> swap
-> monitor
-> rollback app if needed
```

Ví dụ schema change nên dùng expand/contract: thêm nullable/new column trước, deploy code tương thích cả old/new, backfill, rồi mới remove old column ở release sau.

## 5. Real production scenario

v2 rename database column và migration drop column cũ. Sau swap, lỗi tăng và team swap lại v1. v1 không chạy được vì schema cũ đã bị phá. Slot rollback application thành công nhưng system rollback thất bại.

## 6. Failure scenario & troubleshooting

**Symptom** → rollback slot xong vẫn 500.

**Evidence** → old binary query column đã bị migration xóa.

**Hypothesis** → destructive migration không backward-compatible.

**Diagnosis** → compare app version/schema migration history.

**Fix** → restore compatible schema hoặc forward-fix; áp dụng expand/contract cho future releases.

**Verification** → automated compatibility test chạy old + new app version với transitional schema.

## 7. Common mistakes

Coi slot là full environment isolation dù dùng chung DB; để slot settings sai; swap trước warm-up; migration destructive cùng release; không test background jobs chạy đồng thời ở staging/production.

## 8. Alternatives

Blue-Green trên Container Apps/Kubernetes có control khác nhưng shared database problem vẫn tồn tại. Rolling deployment đơn giản hơn nhưng chạy mixed versions lâu hơn.

## 9. Trade-offs

### Advantages

Warm-up, smoke test trước cutover, app rollback nhanh.

### Costs / Risks

Extra compute/config complexity; database và external side effects không rollback cùng slot; mixed-version compatibility vẫn quan trọng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slot swap đổi application traffic, không undo database.

### Middle

Deploy staging, health validate và quản lý slot settings.

### Senior

Thiết kế backward-compatible migration và mixed-version behavior.

### Technical Lead / Architect

Định nghĩa release protocol, rollback boundary và schema evolution policy.

## 11. Key takeaway

- Deployment slot giải quyết application cutover, không giải quyết data rollback.
- Database migration phải tương thích với rollback window.
- Expand/contract thường an toàn hơn rename/drop trong một release.

# 7. Application Insights dependency telemetry: tìm dependency làm p95 API tăng thay vì đoán

## 1. What is it?

Dependency telemetry ghi nhận outbound calls như SQL, HTTP, Redis và thời lượng/kết quả của chúng. Khi correlated với request telemetry và traces, nó cho biết request chậm vì application code hay dependency nào.

## 2. Why does it exist?

Một endpoint 1.5 giây không nói bottleneck nằm ở đâu. CPU profiling không giúp nhiều nếu 1.3 giây là chờ remote HTTP. Production diagnosis cần evidence theo dependency.

## 3. How does it work?

```text
Request GET /checkout 1500 ms
   |
   +-- SQL      80 ms
   +-- Redis     5 ms
   +-- Reviews 120 ms
   +-- Payment 1250 ms  <-- dominant
```

Correlation context nối request với dependency operations.

## 4. Practical implementation

ASP.NET Core/Application Insights auto-collection thường instrument common dependencies. Với custom dependency:

```csharp
using var activity = MyActivitySource.StartActivity("Pricing.Calculate");
activity?.SetTag("pricing.mode", "contract");

var result = await pricingClient.CalculateAsync(
    request,
    cancellationToken);
```

Không đưa customer PII/high-cardinality payload tùy tiện vào tags.

## 5. Real production scenario

Sau release, `/product` p95 tăng từ 300 ms lên 900 ms. Team nghi EF query mới. Dependency breakdown cho thấy SQL không đổi, nhưng review provider tăng từ 100 lên 650 ms. Fix đúng là timeout/cache/degradation cho reviews, không phải index database.

## 6. Failure scenario & troubleshooting

**Symptom** → request telemetry có latency nhưng dependencies trống.

**Evidence** → custom SDK không dùng instrumented `HttpClient`, hoặc context bị mất.

**Hypothesis** → instrumentation gap.

**Diagnosis** → compare traces với network logs và Activity propagation.

**Fix** → dùng standard instrumentation/OpenTelemetry hoặc tạo custom Activity đúng semantic.

**Verification** → synthetic request tạo complete dependency waterfall.

## 7. Common mistakes

Chỉ xem average; không filter theo operation/version; high-cardinality dimensions làm cost tăng; log full SQL parameters chứa PII; alert từng dependency call thay vì SLO symptom.

## 8. Alternatives

OpenTelemetry cung cấp vendor-neutral instrumentation. Structured logs + correlation đủ cho hệ thống nhỏ nhưng query latency distribution khó hơn. Network monitoring không có application semantic context.

## 9. Trade-offs

### Advantages

Nhanh localize bottleneck, correlation tốt, hỗ trợ regression analysis.

### Costs / Risks

Telemetry cost, sampling, privacy và instrumentation gaps.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết request latency gồm application + dependencies.

### Middle

Dùng dependency telemetry để tìm slow call.

### Senior

Correlate p95/p99, release version, failures và dependency saturation.

### Technical Lead / Architect

Định nghĩa telemetry standard, sampling/cost budget và SLO-driven alerting.

## 11. Key takeaway

- Đừng tối ưu component chưa được chứng minh là bottleneck.
- Dependency telemetry biến latency thành waterfall có evidence.
- Correlation, percentiles và release dimensions quan trọng hơn một average chart.

# 8. Playwright E2E: test critical user journey mà không biến suite thành flaky bottleneck

## 1. What is it?

Playwright E2E test chạy browser thật để kiểm tra user journey xuyên frontend, API, authentication và backend dependencies trong test environment. Giá trị lớn nhất là bảo vệ integration seams mà unit test không thấy.

E2E không nên test mọi permutation business logic.

## 2. Why does it exist?

Component/unit tests có thể đều xanh nhưng login redirect sai, API route mismatch, CORS/configuration lỗi hoặc button không wired đúng. E2E kiểm tra system assembled thực tế.

## 3. How does it work?

```text
Browser
  -> UI
  -> API
  -> test DB / dependencies
  -> UI assertion
```

Playwright auto-wait dựa trên actionability tốt hơn arbitrary sleep, nhưng test vẫn flaky nếu data/environment không deterministic.

## 4. Practical implementation

```ts
test('manager approves a timesheet', async ({ page }) => {
  await page.goto('/timesheets/pending');

  const row = page.getByTestId('timesheet-TS-1001');
  await row.getByRole('button', { name: 'Approve' }).click();

  await expect(row.getByText('Approved')).toBeVisible();
});
```

Seed `TS-1001` bằng fixture/API trước test thay vì phụ thuộc data còn lại từ test trước.

## 5. Real production scenario

Backend đổi `401` handling, frontend interceptor redirect loop về login. Unit tests của API và component đều pass vì mock responses. Một critical-login E2E phát hiện regression trước release.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail 1/20 runs.

**Evidence** → screenshot/trace cho thấy element chưa load; test dùng `waitForTimeout(2000)` và shared test data.

**Hypothesis** → timing/data coupling.

**Diagnosis** → bật Playwright trace, inspect network/action timeline.

**Fix** → locator semantic, deterministic fixture, wait theo observable state, isolate parallel data.

**Verification** → repeat test nhiều lần/parallel trong CI.

## 7. Common mistakes

Test mọi field combination bằng E2E; CSS selectors brittle; fixed sleeps; tests phụ thuộc thứ tự; mock toàn backend khiến “E2E” không còn end-to-end; bỏ trace artifacts khi fail.

## 8. Alternatives

Unit tests nhanh cho business rules. Integration/API tests tốt cho DB/HTTP contract. Contract tests bảo vệ service boundaries. E2E chỉ nên cover critical cross-system journeys và high-risk integration behavior.

## 9. Trade-offs

### Advantages

Bắt configuration/wiring/browser regressions, confidence cao cho critical journeys.

### Costs / Risks

Chậm, environment-sensitive, debug phức tạp, maintenance cost cao hơn lower-level tests.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu E2E test hành vi user nhìn thấy, không phải implementation details.

### Middle

Viết deterministic Playwright tests và dùng traces/screenshots để debug.

### Senior

Chọn đúng test layer và loại bỏ flakiness/root cause thay vì retry vô hạn.

### Technical Lead / Architect

Thiết kế test strategy theo risk, CI duration và release confidence.

## 11. Key takeaway

- E2E có giá trị nhất ở critical integration journeys.
- Flakiness thường là test/environment design problem, không phải lý do chấp nhận retry vô hạn.
- Đẩy business permutations xuống unit/integration tests rẻ hơn.

# 9. Akamai/CDN `Cache-Control`: ai thực sự quyết định freshness giữa browser, edge và origin

## 1. What is it?

`Cache-Control` là HTTP caching contract giữa origin, shared caches như Akamai và browser. Một response có thể tồn tại ở nhiều cache layers với freshness policy khác nhau tùy directives và CDN configuration.

`max-age` thường áp dụng freshness cho caches nói chung; `s-maxage` có thể đặt freshness riêng cho shared cache; `private` ngăn shared cache lưu response; `no-store` yêu cầu không lưu.

## 2. Why does it exist?

Không có explicit caching contract, teams dễ gặp hai cực: mọi request về origin hoặc content stale khó kiểm soát. CDN chỉ hiệu quả khi application hiểu dữ liệu nào public/shareable và freshness requirement.

## 3. How does it work?

```text
Browser cache
    |
    v
Akamai edge cache
    |
    v
Origin / ASP.NET Core
```

Ví dụ:

```http
Cache-Control: public, max-age=60, s-maxage=300
```

Browser có thể coi response fresh 60 giây; shared cache có thể dùng 300 giây nếu policy tôn trọng header.

## 4. Practical implementation

ASP.NET Core:

```csharp
app.MapGet("/catalog/{slug}", async (string slug, CatalogService service) =>
{
    var page = await service.GetPublicCatalogAsync(slug);
    return Results.Ok(page);
})
.WithMetadata(new ResponseCacheAttribute
{
    Duration = 60,
    Location = ResponseCacheLocation.Any
});
```

Trong Production phải xác minh actual headers và Akamai property rules; framework metadata không đảm bảo edge behavior nếu CDN override policy.

## 5. Real production scenario

Product description public cache 5 phút, nhưng price cần 30 giây. Nếu API trả cả hai trong một response cache 5 phút, user thấy price stale. Boundary response/cache phải phản ánh freshness domain thay vì “cache cả page cho nhanh”.

## 6. Failure scenario & troubleshooting

**Symptom** → deploy/publish xong origin trả content mới nhưng user vẫn thấy cũ.

**Evidence** → direct-origin response mới; edge response có `Age` lớn/cache hit.

**Hypothesis** → stale CDN object hoặc purge/key mismatch.

**Diagnosis** → inspect response headers, cache key dimensions, Akamai rules và purge status.

**Fix** → purge/version asset hoặc điều chỉnh TTL/cache key.

**Verification** → kiểm tra nhiều edge requests và browser cache riêng biệt.

## 7. Common mistakes

Cache authenticated/personalized response dưới shared key; dùng query string nhưng cache key bỏ qua parameter quan trọng; TTL quá dài rồi dựa hoàn toàn vào purge; nhầm browser cache với CDN cache; dùng `no-cache` như đồng nghĩa `no-store`.

## 8. Alternatives

Application/Redis cache giảm origin computation nhưng vẫn nhận request. Browser cache giảm cả edge request. Versioned immutable assets phù hợp static content hơn purge liên tục.

## 9. Trade-offs

### Advantages

Giảm latency toàn cầu, origin load và bandwidth phía backend.

### Costs / Risks

Staleness, cache-key/security bugs, purge operational complexity và khó debug multi-layer caching.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser, CDN và origin là các cache layers khác nhau.

### Middle

Đọc `Cache-Control`, `Age` và xác định cache hit/miss.

### Senior

Thiết kế key/freshness/purge và tránh personalization leakage.

### Technical Lead / Architect

Định nghĩa caching contract theo data ownership/freshness SLA và quyết định layer nào chịu trách nhiệm.

## 11. Key takeaway

- CDN caching là HTTP/data-consistency decision, không chỉ infrastructure switch.
- Freshness của price, content và static asset có thể cần policy khác nhau.
- Debug stale response phải xác định layer nào đang phục vụ bản sao.

# 10. .NET Framework → modern .NET incremental migration: Strangler approach thay vì big-bang rewrite

## 1. What is it?

Incremental modernization di chuyển capability từ legacy .NET Framework sang modern .NET theo từng boundary, trong khi hệ thống cũ vẫn phục vụ phần chưa migrate. Strangler approach đặt routing/integration seam để traffic dần chuyển sang implementation mới.

Mục tiêu là giảm migration risk, không phải tạo hai hệ thống tồn tại vĩnh viễn.

## 2. Why does it exist?

Enterprise .NET Framework app thường chứa hàng năm business rules, third-party dependencies, IIS assumptions và database coupling. Rewrite toàn bộ tạo thời gian dài không tạo business value và risk “unknown behavior” lớn.

## 3. How does it work?

```text
Clients
   |
Gateway / routing seam
   |--------------------|
   v                    v
Legacy .NET Framework   Modern .NET
   |                    |
   +------ shared/integration data boundary
```

Chọn capability có boundary rõ, thêm characterization tests, tách contract, migrate rồi chuyển traffic có kiểm soát.

## 4. Practical implementation

Ví dụ legacy app có `/reports`. Đầu tiên xác định HTTP/data contract và tests. New ASP.NET Core service implement endpoint tương thích. Reverse proxy route `/reports/*` sang service mới; các route khác vẫn về legacy.

```text
/orders/*  -> legacy IIS app
/reports/* -> ASP.NET Core app
```

Không nên để cả hai applications cùng ghi tùy ý vào cùng tables mà không có ownership plan.

## 5. Real production scenario

Legacy commerce backoffice chạy .NET Framework 4.8 với Web Forms/MVC và nhiều integrations. Reporting ít transaction coupling nên được tách trước. Checkout phụ thuộc session, payment và shared DB sâu nên migrate sau khi boundaries được cải thiện.

## 6. Failure scenario & troubleshooting

**Symptom** → feature mới trả dữ liệu khác legacy dù cùng input.

**Evidence** → characterization tests phát hiện hidden legacy normalization/timezone rule.

**Hypothesis** → rewrite dựa trên documented requirement nhưng bỏ behavior thực tế.

**Diagnosis** → compare production-like fixtures/output và legacy code path.

**Fix** → quyết định behavior cũ là requirement hay bug; encode decision vào contract/test.

**Verification** → shadow/parallel comparison hoặc controlled traffic before full cutover.

## 7. Common mistakes

Rewrite toàn bộ vì code “xấu”; migrate framework nhưng giữ nguyên coupling nên không đạt lợi ích; share database vô thời hạn; không có rollback; nâng tất cả packages cùng lúc làm scope bùng nổ; không inventory Windows-only dependencies.

## 8. Alternatives

In-place upgrade phù hợp app nhỏ/dependencies compatible. Big-bang rewrite chỉ hợp khi scope nhỏ hoặc legacy không thể evolve và business chấp nhận risk. Giữ nguyên hệ thống cũng là lựa chọn hợp lệ nếu cost/risk migration lớn hơn value.

## 9. Trade-offs

### Advantages

Giảm blast radius, tạo value từng phần, rollback/cutover dễ hơn, học dần unknowns.

### Costs / Risks

Temporary dual-system complexity, routing/integration seams, data ownership transition và migration kéo dài nếu không có end-state.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu modernization không đồng nghĩa rewrite.

### Middle

Viết characterization/integration tests và migrate isolated component.

### Senior

Phân tích compatibility, data boundary, deployment/rollback và hidden behavior.

### Technical Lead / Architect

Chọn migration sequence theo business value/coupling/risk, định nghĩa target architecture và tiêu chí retire legacy.

## 11. Key takeaway

- Legacy migration là risk-management problem trước khi là framework problem.
- Characterization tests bảo vệ behavior mà documentation có thể không ghi.
- Incremental migration cần boundary và end-state rõ để không tạo distributed legacy mới.
