# Daily Knowledge Sharing — `HttpClient` vẫn gọi nhầm IP sau khi service đã đổi endpoint

> **Chủ đề:** DNS freshness, connection pooling và lifetime của `HttpClient` trong .NET  
> **Ngày:** 2026-09-15 20:57:29 (Asia/Saigon)  
> **Mức độ:** Middle → Senior Backend .NET

---

## 1. Tình huống thực tế

Bạn có một ASP.NET Core service gọi sang `payment-api`:

```text
checkout-api
    |
    | HTTPS https://payment.internal
    v
payment-api
```

Deployment mới của `payment-api` diễn ra bình thường. DNS của `payment.internal` đã đổi từ IP cũ sang IP mới. Các máy khác resolve đúng IP mới, nhưng một instance của `checkout-api` vẫn tiếp tục gửi request đến IP cũ trong một khoảng thời gian dài.

Triệu chứng thường gây nhầm lẫn:

- `nslookup payment.internal` trên host/container trả về IP mới.
- Restart `checkout-api` thì lỗi biến mất ngay.
- Không có lỗi DNS rõ ràng trong application log.
- Request có thể timeout, `Connection refused`, hoặc vẫn thành công nhưng đi vào deployment cũ.
- Team kết luận ban đầu: "DNS cache của OS bị stale".

Điểm quan trọng: **DNS có thể đã đúng, nhưng application vẫn đang tái sử dụng một TCP connection được tạo khi hostname còn resolve sang IP cũ.**

## 2. Mental model cần nhớ

`HttpClient` không thực hiện DNS lookup cho mọi HTTP request.

Một cách đơn giản hóa:

```text
HTTP request
    |
    v
HttpClient
    |
    v
SocketsHttpHandler
    |
    v
Connection Pool
    |
    +---- existing TCP/TLS connection? ---- YES ---> reuse connection ---> old IP
    |
    NO
    |
    v
DNS lookup ---> new IP ---> TCP connect ---> TLS ---> HTTP request
```

Nếu connection trong pool vẫn usable, request tiếp theo có thể reuse connection đó mà không cần DNS lookup mới.

Vì vậy cần phân biệt ba lifetime khác nhau:

```text
HttpClient lifetime
        !=
HttpMessageHandler lifetime
        !=
pooled TCP connection lifetime
```

Đây là chỗ rất nhiều bug production bắt đầu.

---

## 3. Vì sao DNS TTL không tự giải quyết vấn đề?

DNS record có thể có TTL, ví dụ:

```text
payment.internal -> 10.20.1.15
TTL = 60 seconds
```

Sau deployment:

```text
payment.internal -> 10.20.2.42
```

TTL nói về lifetime của DNS answer trong DNS caching layer. Nó **không có nghĩa rằng một TCP connection đang mở phải bị đóng sau 60 giây**.

Theo hướng dẫn hiện hành của Microsoft, `HttpClient` resolve DNS khi một connection được tạo và không tự theo dõi DNS TTL để ép connection hiện tại được thay thế.

Do đó:

```text
DNS record changed
        |
        v
existing pooled connection still alive
        |
        v
no new connection required
        |
        v
no new DNS lookup required
        |
        v
requests may continue reaching old endpoint
```

Đây là lý do restart process thường "fix" lỗi: restart phá connection pool, buộc application tạo connection mới và resolve DNS lại.

Restart chỉ là bằng chứng chẩn đoán hữu ích, không phải thiết kế lifetime đúng.

## 4. Sai lầm đối nghịch: tạo `HttpClient` cho từng request

Khi gặp stale connection, phản xạ nguy hiểm là:

```csharp
public async Task<string> GetPaymentAsync()
{
    using var client = new HttpClient();
    return await client.GetStringAsync("https://payment.internal/health");
}
```

Cách này buộc tạo/dispose client liên tục và phá lợi ích của connection pooling.

Ở tải cao, việc tạo connection quá nhiều có thể dẫn tới:

- nhiều TCP handshakes;
- nhiều TLS handshakes;
- tăng latency;
- nhiều socket ở trạng thái `TIME_WAIT`;
- nguy cơ ephemeral port exhaustion.

Vậy bài toán không phải:

> reuse hay không reuse `HttpClient`?

Mà là:

> **reuse connection đủ lâu để hiệu quả, nhưng không lâu đến mức topology/DNS thay đổi mà process không thích nghi được.**

## 5. `PooledConnectionLifetime` giải quyết điều gì?

Với long-lived `HttpClient`, có thể cấu hình `SocketsHttpHandler.PooledConnectionLifetime`:

```csharp
var handler = new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(5)
};

var client = new HttpClient(handler);
```

Ý nghĩa không phải là request đang chạy bị cắt đúng phút thứ 5.

Mental model tốt hơn:

```text
connection created at T0
        |
        | reused for requests
        v
age >= PooledConnectionLifetime
        |
        | current request completes
        v
connection becomes replaceable / closed
        |
        v
next required connection
        |
        v
DNS lookup again
```

Microsoft cũng nhấn mạnh rằng các giá trị ví dụ như 2 hoặc 15 phút chỉ là minh họa. Lifetime thực tế phải dựa trên tần suất DNS/network topology có thể thay đổi.

### Một cấu hình ASP.NET Core rõ ràng

```csharp
builder.Services
    .AddHttpClient<PaymentClient>(client =>
    {
        client.BaseAddress = new Uri("https://payment.internal");
        client.Timeout = TimeSpan.FromSeconds(10);
    })
    .UseSocketsHttpHandler((handler, _) =>
    {
        handler.PooledConnectionLifetime = TimeSpan.FromMinutes(5);
        handler.PooledConnectionIdleTimeout = TimeSpan.FromMinutes(2);
        handler.ConnectTimeout = TimeSpan.FromSeconds(3);
    })
    .SetHandlerLifetime(Timeout.InfiniteTimeSpan);
```

Ở đây connection rotation được giao cho `SocketsHttpHandler`, nên handler rotation ở `IHttpClientFactory` được tắt để lifetime model dễ hiểu hơn.

Không nên copy nguyên `5 minutes` vào mọi hệ thống. Hãy xác định nó từ topology thật.

## 6. `HandlerLifetime` và `PooledConnectionLifetime` không phải một thứ

Đây là distinction quan trọng.

### `HandlerLifetime`

`IHttpClientFactory` cache `HttpMessageHandler` để tái sử dụng connection pool. `HandlerLifetime` kiểm soát khoảng thời gian handler được giữ trước khi factory có thể rotate handler.

Ví dụ:

```csharp
services
    .AddHttpClient("payment")
    .SetHandlerLifetime(TimeSpan.FromMinutes(5));
```

Factory-created `HttpClient` được thiết kế để short-lived. Khi code thường xuyên lấy client mới từ factory, handler rotation giúp application thích nghi với DNS changes.

### `PooledConnectionLifetime`

Thuộc `SocketsHttpHandler` và tác động trực tiếp tới lifetime của từng pooled connection.

```csharp
services
    .AddHttpClient("payment")
    .UseSocketsHttpHandler((handler, _) =>
    {
        handler.PooledConnectionLifetime = TimeSpan.FromMinutes(5);
    });
```

Nó giải quyết vấn đề ở tầng thấp hơn: connection đủ tuổi sẽ được thay thế, dẫn tới DNS lookup mới khi cần connection mới.

### Bảng mental model

| Setting | Scope | Mục tiêu chính |
|---|---|---|
| `HttpClient` lifetime | client object | configuration + request API |
| `HandlerLifetime` | handler / pool owner | rotation do `IHttpClientFactory` quản lý |
| `PooledConnectionLifetime` | individual pooled connection | định kỳ tạo connection mới, qua đó refresh DNS |
| `PooledConnectionIdleTimeout` | idle pooled connection | loại connection không được dùng trong một khoảng thời gian |
| `ConnectTimeout` | connection establishment | giới hạn thời gian chờ tạo connection |

## 7. Một bug tinh vi: typed client bị capture bởi singleton

Code nhìn rất hợp lý:

```csharp
builder.Services.AddHttpClient<PaymentClient>();
builder.Services.AddSingleton<OrderCoordinator>();
```

```csharp
public sealed class OrderCoordinator
{
    private readonly PaymentClient _paymentClient;

    public OrderCoordinator(PaymentClient paymentClient)
    {
        _paymentClient = paymentClient;
    }
}
```

Nếu `PaymentClient` là typed client chứa `HttpClient`, singleton `OrderCoordinator` giữ typed client đó rất lâu.

Vấn đề là factory không thể magically thay `HttpClient` object đã bị singleton giữ lại bằng một client mới. Microsoft troubleshooting guidance cảnh báo không nên capture factory-created `HttpClient` lâu dài và không nên inject typed client vào singleton theo cách làm mất lifetime semantics của factory.

Cách thiết kế phải làm lifetime rõ ràng.

Ví dụ nếu coordinator bắt buộc singleton, có thể inject `IHttpClientFactory` và lấy client khi thực hiện operation:

```csharp
public sealed class OrderCoordinator
{
    private readonly IHttpClientFactory _httpClientFactory;

    public OrderCoordinator(IHttpClientFactory httpClientFactory)
    {
        _httpClientFactory = httpClientFactory;
    }

    public async Task<HttpResponseMessage> CheckPaymentAsync(
        CancellationToken cancellationToken)
    {
        using var client = _httpClientFactory.CreateClient("payment");

        return await client.GetAsync(
            "/health",
            cancellationToken);
    }
}
```

Điểm dễ hiểu sai: dispose factory-created client ở đây không tương đương pattern `new HttpClient()` per request, vì factory quản lý và cache underlying handlers/pools.

## 8. .NET 9 thay đổi một assumption đáng chú ý

Từ .NET 9, trên các platform hỗ trợ, `IHttpClientFactory` mặc định dùng `SocketsHttpHandler` làm primary handler thay vì luôn mặc định là `HttpClientHandler`. `PooledConnectionLifetime` của handler cũng được đặt tương ứng với `HandlerLifetime`.

Vì vậy code kiểu này dựa vào implementation detail có thể hỏng:

```csharp
services.AddHttpClient("payment")
    .ConfigurePrimaryHttpMessageHandler((handler, _) =>
    {
        var httpHandler = (HttpClientHandler)handler;
        httpHandler.UseCookies = false;
    });
```

Cast có thể ném:

```text
InvalidCastException
```

Bài học rộng hơn:

> Đừng thiết kế configuration dựa trên concrete handler type mặc định nếu contract không đảm bảo type đó.

Nếu cần concrete handler, hãy cấu hình nó một cách explicit.

## 9. Production debugging: chứng minh stale connection thay vì đoán

Khi service "không chịu nhận DNS mới", đừng dừng ở `nslookup`.

### Bước 1 — kiểm tra DNS hiện tại

Trong cùng network namespace/container với application:

```bash
nslookup payment.internal
```

hoặc:

```bash
dig payment.internal
```

Xác nhận DNS hiện tại trả IP nào.

### Bước 2 — kiểm tra process đang kết nối tới IP nào

Linux:

```bash
ss -tnp
```

hoặc lọc port:

```bash
ss -tnp | grep ':443'
```

Nếu DNS trả IP mới nhưng process vẫn giữ established connection tới IP cũ, hypothesis về pooled connection trở nên mạnh hơn nhiều.

### Bước 3 — correlation với deployment timeline

So sánh:

```text
T0  connection established to old IP
T1  DNS changed
T2  requests still use old established connection
T3  process restarted / connection recycled
T4  new connection established to new IP
```

Timeline này có giá trị hơn việc chỉ nhìn một exception.

### Bước 4 — quan sát connection creation

Trong môi trường điều tra sâu hơn, dùng .NET networking diagnostics/EventSource, distributed tracing và network telemetry để phân biệt:

- request reuse existing connection;
- request tạo connection mới;
- DNS lookup;
- connect timeout;
- TLS handshake;
- upstream latency.

### Bước 5 — kiểm tra DI lifetime

Tìm:

```text
Singleton
  -> Typed Client
      -> HttpClient
```

hoặc code cache client vào static field trong khi client vốn được tạo bởi factory với expectation short-lived.

## 10. Chọn lifetime theo topology, không theo con số "best practice"

Không tồn tại một `PooledConnectionLifetime = 2 minutes` đúng cho mọi hệ thống.

Hãy hỏi:

1. Endpoint có đổi IP khi rolling deployment không?
2. DNS/service discovery có TTL bao nhiêu?
3. Load balancer có stable virtual IP không?
4. Connection có thể sống hàng giờ không?
5. HTTP/2 có giữ một connection multiplexed rất lâu không?
6. Failover RTO mong muốn là bao lâu?
7. Rotation connection có tạo thêm TLS/CPU cost đáng kể không?

Ví dụ, nếu service discovery có thể chuyển endpoint trong khoảng 60 giây và business muốn failover trong vòng vài phút, connection lifetime 30 phút rõ ràng không phù hợp dù application chạy hoàn toàn ổn trong steady state.

Ngược lại, ép lifetime vài giây có thể làm tăng connection churn và TLS overhead không cần thiết.

Đây là một optimization problem:

```text
freshness ↑  <---- shorter lifetime ---->  connection reuse ↓
```

Mục tiêu là đặt lifetime phù hợp với failure/reconfiguration model của hệ thống.

## 11. Mini review exercise

Hãy review configuration sau:

```csharp
builder.Services.AddHttpClient<InventoryClient>(client =>
{
    client.BaseAddress = new Uri("https://inventory.internal");
});

builder.Services.AddSingleton<CheckoutOrchestrator>();
```

```csharp
public sealed class CheckoutOrchestrator
{
    private readonly InventoryClient _inventory;

    public CheckoutOrchestrator(InventoryClient inventory)
    {
        _inventory = inventory;
    }
}
```

Production symptom:

```text
inventory.internal DNS changed at 10:00
one checkout instance continued talking to the old backend until 14:20
restart fixed it immediately
```

### Trước khi xem đáp án, tự trả lời

- DNS server có nhất thiết bị lỗi không?
- `AddHttpClient` có tự đảm bảo rằng mọi cách sử dụng typed client đều refresh DNS đúng không?
- Lifetime mismatch nằm ở đâu?
- Bạn sẽ sửa DI design hay connection lifetime, hay cả hai?
- Bạn sẽ thu thập evidence nào trước khi deploy fix?

### Hướng phân tích

`CheckoutOrchestrator` là singleton nên typed `InventoryClient` được capture theo lifetime của singleton. Đây là pattern cần xem xét đầu tiên. Nếu dựa vào factory handler rotation nhưng không tạo client mới, assumption đó không còn đúng.

Một fix tốt không chỉ "restart thường xuyên hơn". Hãy làm ownership/lifetime rõ ràng và cấu hình connection recycling phù hợp với topology. Với long-lived client, `SocketsHttpHandler.PooledConnectionLifetime` là primitive quan trọng; với factory-created clients, giữ chúng short-lived và không capture typed client vào singleton lâu dài.

```text

[ ] Có typed client bị inject vào singleton không?
```

## 13. Takeaway

Một `HttpClient` "gọi nhầm IP" sau DNS change không nhất thiết là DNS cache bug.

Root mental model là:

```text
DNS is consulted when a connection is created.
Connection pooling can avoid creating a new connection.
Therefore DNS freshness depends partly on connection lifetime.
```

Ba điều nên nhớ:

1. **Đừng tạo/dispose `new HttpClient()` cho từng request chỉ để lấy DNS mới.** Connection reuse là thiết yếu cho hiệu năng và socket health.
2. **Đừng giả định DNS TTL tự động giới hạn lifetime của pooled TCP connection.** Với long-lived clients, cân nhắc `PooledConnectionLifetime` theo topology thực tế.
3. **Đừng capture factory-created/typed clients vào singleton một cách vô thức.** DI lifetime có thể vô hiệu hóa handler-rotation model mà bạn tưởng mình đang sử dụng.

Khi debug production, hãy chứng minh cả hai phía: **DNS hiện resolve tới đâu** và **process thực sự đang giữ connection tới đâu**.
