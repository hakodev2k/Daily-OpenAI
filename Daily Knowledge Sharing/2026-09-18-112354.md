# 1. .NET Dependency Injection: captive dependency và lifetime boundary

## 1. What is it?

Captive dependency xuất hiện khi service có lifetime dài giữ dependency có lifetime ngắn hơn, điển hình `Singleton -> Scoped`. Mental model quan trọng: DI lifetime không chỉ quyết định lúc object được tạo; nó định nghĩa ownership và khoảng thời gian state được phép tồn tại.

## 2. Why does it exist?

ASP.NET Core tạo scope theo request để các object như `DbContext` có lifecycle hữu hạn. Nếu singleton giữ scoped object, request boundary bị phá: tracked state, connection-related resources hoặc dữ liệu request có thể tồn tại lâu hơn thiết kế.

## 3. How does it work?

```text
Application root
└── Singleton A
    └── Scoped DbContext  ← bị giữ qua nhiều request
```

Scope validation có thể bắt một số dependency graph sai, nhưng factory hoặc service-locator usage có thể che vấn đề.

## 4. Practical implementation

Sai:

```csharp
builder.Services.AddSingleton<ReportCache>();
builder.Services.AddScoped<AppDbContext>();

public sealed class ReportCache(AppDbContext db)
{
    public Task<int> CountAsync(CancellationToken ct) =>
        db.Orders.CountAsync(ct);
}
```

Với singleton worker, tạo scope theo operation:

```csharp
public sealed class ReportWorker(IServiceScopeFactory scopes)
{
    public async Task RunAsync(CancellationToken ct)
    {
        await using var scope = scopes.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        await db.Orders.CountAsync(ct);
    }
}
```

## 5. Real production scenario

Một `BackgroundService` inject repository scoped trực tiếp. Worker chạy nhiều giờ và `DbContext` giữ tracked entities tăng dần. Memory tăng không phải chỉ là “EF leak”; lifetime boundary đã sai.

## 6. Failure scenario & troubleshooting

**Symptom** → disposed-object errors, stale state hoặc memory tăng.  
**Evidence** → dependency graph có singleton giữ scoped service.  
**Hypothesis** → captive dependency.  
**Diagnosis** → bật scope validation và inspect registrations/constructors.  
**Fix** → align lifetimes hoặc tạo explicit scope theo unit of work.  
**Verification** → mỗi operation có scoped instance mới và disposal đúng lúc.

## 7. Common mistakes

Biến mọi service thành singleton để “nhanh hơn”; inject `IServiceProvider` khắp nơi; giữ scoped object trong static field; nhầm thread-safe với lifetime-safe.

## 8. Alternatives

Transient phù hợp stateless lightweight services. Scoped phù hợp request/message unit of work. Singleton phù hợp immutable hoặc thread-safe state có ownership toàn process.

## 9. Trade-offs

### Advantages

Lifetime đúng làm ownership, state isolation và disposal predictable.

### Costs / Risks

Explicit scopes trong workers thêm ceremony; singleton yêu cầu thread-safety nghiêm ngặt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Transient`, `Scoped`, `Singleton`.

### Middle

Debug dependency graph và disposal.

### Senior

Nhận diện lifetime leakage qua workers, factories và caches.

### Technical Lead / Architect

Định nghĩa lifecycle boundary theo request, message, job và process thay vì chọn lifetime theo thói quen.

## 11. Key takeaway

- Lifetime là ownership contract.
- Singleton không được vô tình kéo scoped state ra ngoài scope.
- Background work cần explicit unit-of-work scope.

# 2. REST API Idempotency-Key: chống duplicate side effect khi client retry

## 1. What is it?

`Idempotency-Key` là identifier do client tạo để server nhận ra nhiều attempts thuộc cùng một logical operation. Nó đặc biệt hữu ích cho `POST` tạo side effect như payment hoặc order creation.

## 2. Why does it exist?

Network timeout tạo ambiguity: client không biết server chưa xử lý hay đã commit nhưng response bị mất. Retry mù có thể tạo hai orders hoặc charge hai lần.

## 3. How does it work?

```text
POST + key K
   ├─ first attempt ─► execute ─► persist result for K
   └─ retry K ───────► return same logical result
```

Cùng key nhưng payload khác phải bị reject; nếu không key có thể che một request mới thực sự.

## 4. Practical implementation

```csharp
var record = await db.IdempotencyRecords
    .SingleOrDefaultAsync(x => x.Key == key, ct);

if (record is not null)
    return Results.Ok(record.OrderId);

var order = Order.Create(request);
db.Orders.Add(order);
db.IdempotencyRecords.Add(new IdempotencyRecord(key, requestHash, order.Id));
await db.SaveChangesAsync(ct);
return Results.Ok(order.Id);
```

Database cần unique constraint trên key; application-level check một mình có race.

## 5. Real production scenario

Mobile checkout mất mạng sau khi server đã tạo order. App retry cùng key. API trả order cũ thay vì tạo order thứ hai.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate records dù có key.  
**Evidence** → hai concurrent requests đều thấy “key chưa tồn tại”.  
**Hypothesis** → check-then-insert race.  
**Diagnosis** → inspect transaction và unique constraint.  
**Fix** → durable uniqueness và conflict handling như replay.  
**Verification** → concurrent load với cùng key chỉ tạo một business effect.

## 7. Common mistakes

Lưu key chỉ trong memory; không validate payload; TTL quá ngắn; client tạo key mới khi retry; downstream payment call không idempotent.

## 8. Alternatives

`PUT` với client-chosen resource ID có idempotency tự nhiên khi semantics phù hợp. Natural business key đôi khi đủ. Broker deduplication giải quyết messaging, không thay HTTP contract.

## 9. Trade-offs

### Advantages

Retry an toàn hơn và xử lý network ambiguity rõ ràng.

### Costs / Risks

Cần storage, retention, payload consistency và atomicity design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không chứng minh operation thất bại.

### Middle

Implement key storage và unique constraint.

### Senior

Thiết kế atomicity với downstream side effects và replay response.

### Technical Lead / Architect

Xác định operation nào cần idempotency contract xuyên service boundaries.

## 11. Key takeaway

- Retry và duplicate prevention phải được thiết kế cùng nhau.
- Unique constraint là correctness guard.
- Idempotency phải end-to-end nếu downstream cũng tạo side effect.

# 3. SQL Server deadlock: wait-for cycle, victim selection và diagnostic reasoning

## 1. What is it?

Deadlock là cycle trong đó các transactions giữ resources và chờ resources của nhau nên không transaction nào tự tiến tiếp. SQL Server phát hiện cycle và chọn một victim để rollback.

## 2. Why does it exist?

Concurrency tăng throughput nhưng transactions có thể acquire locks theo thứ tự khác nhau. Không có deadlock detection, cycle có thể chờ vô hạn.

## 3. How does it work?

```text
Tx A: holds Row 1 ── waits ──► Row 2
  ▲                            │
  └──────── waits ── holds ─── Tx B
```

Deadlock khác blocking: blocking có thể tự giải phóng khi blocker commit; deadlock cần engine phá cycle.

## 4. Practical implementation

```sql
-- Tx A
UPDATE Accounts SET Balance = Balance - 10 WHERE Id = 1;
UPDATE Accounts SET Balance = Balance + 10 WHERE Id = 2;

-- Tx B
UPDATE Accounts SET Balance = Balance - 20 WHERE Id = 2;
UPDATE Accounts SET Balance = Balance + 20 WHERE Id = 1;
```

Mitigation quan trọng là access resources theo deterministic order và giữ transaction ngắn.

## 5. Real production scenario

Approval workflow update `Request` rồi `EmployeeSummary`, trong khi reconciliation update theo thứ tự ngược lại. Mỗi query riêng lẻ nhanh nhưng concurrency tạo cycle.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL error 1205 ngẫu nhiên dưới tải.  
**Evidence** → deadlock graph từ Extended Events.  
**Hypothesis** → inconsistent resource order hoặc transaction quá rộng.  
**Diagnosis** → đọc victim/process/resource nodes, statements, indexes và lock modes.  
**Fix** → consistent ordering, transaction nhỏ hơn, access path phù hợp; retry bounded.  
**Verification** → replay concurrent workload và theo dõi deadlock rate.

## 7. Common mistakes

Chỉ tăng timeout; retry vô hạn; dùng `NOLOCK` như thuốc chữa; không lưu deadlock graph; chỉ tối ưu một statement mà bỏ transaction boundary.

## 8. Alternatives

Snapshot-based isolation giảm một số reader/writer blocking nhưng không loại mọi writer conflict. Optimistic concurrency giải quyết loại conflict khác.

## 9. Trade-offs

### Advantages

Locking bảo vệ consistency và deadlock detector giúp hệ thống recover.

### Costs / Risks

Rollback work, latency spike và retry amplification.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt blocking và deadlock.

### Middle

Đọc deadlock graph cơ bản.

### Senior

Reason về lock order, indexes và transaction boundaries.

### Technical Lead / Architect

Thiết kế write workflows giảm cross-boundary transaction và có retry policy an toàn.

## 11. Key takeaway

- Deadlock là cycle, không phải mọi blocking.
- Deadlock graph là evidence chính.
- Retry là safety net, không phải root-cause fix.

# 4. Redis cache stampede: request coalescing, TTL jitter và stale-while-revalidate

## 1. What is it?

Cache stampede xảy ra khi nhiều requests cùng miss một hot key và đồng thời đánh xuống database/dependency. Cache bình thường giảm load; tại expiration boundary nó có thể khuếch đại load.

## 2. Why does it exist?

Một key nhận hàng nghìn requests/phút hết hạn. Nếu mỗi request tự rebuild, origin nhận burst mà bình thường không bao giờ thấy.

## 3. How does it work?

```text
Hot key expires
   ├─ Request 1 ─┐
   ├─ Request 2 ─┼─► DB/API rebuild x N
   └─ Request N ─┘
```

Các chiến lược gồm single-flight/request coalescing, TTL jitter, pre-refresh và stale-while-revalidate.

## 4. Practical implementation

```csharp
var value = await cache.GetStringAsync(key, ct);
if (value is not null) return value;

await gate.WaitAsync(ct);
try
{
    value = await cache.GetStringAsync(key, ct);
    if (value is not null) return value;

    value = await LoadFromOrigin(ct);
    await cache.SetStringAsync(key, value,
        new DistributedCacheEntryOptions {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
        }, ct);
    return value;
}
finally { gate.Release(); }
```

Local gate chỉ bảo vệ một process; multi-instance deployment cần hiểu boundary này.

## 5. Real production scenario

Homepage configuration hết TTL sau deployment. Hàng chục App Service instances cùng rebuild key, SQL CPU nhảy lên 95%.

## 6. Failure scenario & troubleshooting

**Symptom** → DB spike theo chu kỳ TTL.  
**Evidence** → cache misses và origin QPS tăng đồng thời.  
**Hypothesis** → synchronized expiration.  
**Diagnosis** → correlate miss rate, TTL, key popularity và dependency latency.  
**Fix** → jitter, coalescing, pre-refresh hoặc bounded stale serving.  
**Verification** → expiration không còn tạo origin burst.

## 7. Common mistakes

Distributed lock cho mọi miss; lock không timeout; mọi key cùng TTL; không định nghĩa stale tolerance; cache failure làm application failure.

## 8. Alternatives

`IMemoryCache` phù hợp per-instance data. CDN phù hợp public HTTP content. Không cache là lựa chọn đúng nếu origin đủ nhanh.

## 9. Trade-offs

### Advantages

Giảm burst load và tail latency khi hot key refresh.

### Costs / Risks

Synchronization thêm complexity; stale serving đổi freshness lấy availability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu concurrent misses tạo burst.

### Middle

Implement double-check + coalescing.

### Senior

Chọn TTL jitter, stale policy và metrics.

### Technical Lead / Architect

Quyết định cache có cần tồn tại và ai sở hữu invalidation/freshness contract.

## 11. Key takeaway

- Cache expiration là một load event.
- Hot keys cần refresh strategy.
- Freshness và availability phải dựa trên business semantics.

# 5. Saga Pattern: compensation không phải database rollback phân tán

## 1. What is it?

Saga là chuỗi local transactions giữa nhiều services với compensating actions khi workflow không thể hoàn tất. Mental model: business recovery workflow, không phải ACID transaction kéo dài qua network.

## 2. Why does it exist?

Checkout có Order, Payment và Inventory thuộc các ownership boundaries khác nhau. Distributed transaction xuyên tất cả services làm coupling, availability và operations phức tạp.

## 3. How does it work?

```text
Create Order → Reserve Inventory → Capture Payment
     │                │                 │ fail
     │                │                 ▼
     │                └──── Release Inventory
     └───────────────────── Cancel Order
```

Compensation là operation mới và bản thân nó cũng có thể fail.

## 4. Practical implementation

```csharp
public async Task Handle(PaymentFailed e, CancellationToken ct)
{
    await inventory.ReleaseAsync(e.OrderId, ct); // idempotent
    await orders.CancelAsync(e.OrderId, "Payment failed", ct);
}
```

Saga production cần durable state, correlation, retries và terminal/manual-intervention states.

## 5. Real production scenario

Travel booking reserve hotel thành công nhưng flight thất bại. Cancel hotel là business compensation; có thể phát sinh cancellation fee nên state không quay lại lịch sử như chưa từng xảy ra.

## 6. Failure scenario & troubleshooting

**Symptom** → order cancelled nhưng inventory vẫn reserved.  
**Evidence** → compensation message retry nhiều lần.  
**Hypothesis** → compensation dependency unavailable.  
**Diagnosis** → inspect saga state, delivery và idempotency.  
**Fix** → bounded retry, DLQ/manual recovery, reconciliation.  
**Verification** → invariant cuối cùng hội tụ và stuck saga có alert.

## 7. Common mistakes

Gọi compensation là rollback; không persist saga state; compensation không idempotent; không có timeout hoặc manual recovery.

## 8. Alternatives

Single database transaction đơn giản hơn nếu ownership cho phép. Modular Monolith có thể giữ transaction local. Đừng tạo distributed workflow nếu boundary chưa cần phân tán.

## 9. Trade-offs

### Advantages

Giữ service autonomy và tránh long distributed transaction.

### Costs / Risks

Eventual consistency, nhiều failure states, reconciliation và observability phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu local transaction + compensation.

### Middle

Implement idempotent saga step.

### Senior

Thiết kế timeout, retries và recovery states.

### Technical Lead / Architect

Quyết định có cần distributed workflow hay system đang bị chia service quá nhỏ.

## 11. Key takeaway

- Compensation là business action, không phải time travel.
- Saga cần durable state và recovery path.
- Nếu local transaction đủ, giữ giải pháp đơn giản.

# 6. Azure Key Vault + Managed Identity: secretless application access và rotation

## 1. What is it?

Managed Identity cấp identity cho Azure resource; Key Vault lưu secrets, keys và certificates. Kết hợp hai thứ giúp application authenticate tới vault mà không cần static client secret.

## 2. Why does it exist?

Nếu App Service cần database password nhưng credential để đọc vault lại nằm trong config, ta chỉ chuyển secret problem sang vị trí khác.

## 3. How does it work?

```text
App Service Managed Identity
      │ Azure token
      ▼
Key Vault authorization
      │
      ▼
Secret / certificate
```

Authentication và authorization là hai bước riêng. Có identity không đồng nghĩa có quyền đọc vault.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(configuration["KeyVaultUri"]!),
    new DefaultAzureCredential());

var secret = await client.GetSecretAsync(
    "SqlPassword",
    cancellationToken: ct);
```

Production cần least-privilege RBAC, network policy và secret caching/refresh hợp lý.

## 5. Real production scenario

App Service truy cập third-party API key trong Key Vault. Khi rotate key, deployment pipeline không cần ghi secret mới vào source-controlled configuration.

## 6. Failure scenario & troubleshooting

**Symptom** → local chạy được, Azure trả 403.  
**Evidence** → token acquisition thành công nhưng vault authorization denied.  
**Hypothesis** → principal/role/scope sai hoặc network boundary chặn.  
**Diagnosis** → kiểm tra principal ID, RBAC, vault firewall/Private Endpoint và DNS.  
**Fix** → cấp đúng quyền tối thiểu và sửa network path.  
**Verification** → app đọc đúng secret nhưng không có quyền ngoài scope.

## 7. Common mistakes

Cấp `Key Vault Administrator`; log secret; cache secret mãi mãi; nhầm system-assigned/user-assigned identity; bỏ qua Private DNS.

## 8. Alternatives

Environment variables đơn giản hơn nhưng distribution/rotation khó hơn. Kubernetes workloads có thể dùng workload identity. Không phải mọi config đều cần Key Vault.

## 9. Trade-offs

### Advantages

Giảm static credentials, centralize secret governance và rotation.

### Costs / Risks

Thêm runtime dependency, RBAC/network complexity và operational monitoring.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt identity, secret và authorization.

### Middle

Configure Managed Identity + least privilege.

### Senior

Thiết kế rotation, caching, networking và failure behavior.

### Technical Lead / Architect

Định nghĩa secret-management standard và migration khỏi long-lived credentials.

## 11. Key takeaway

- Managed Identity loại static credential dùng để authenticate Azure workload.
- Key Vault access vẫn cần least privilege.
- Rotation chỉ hữu ích nếu application thực sự consume version mới.

# 7. Playwright test isolation: browser context, deterministic data và flaky E2E

## 1. What is it?

Test isolation nghĩa là mỗi test chạy với state đủ độc lập để kết quả không phụ thuộc test trước. Playwright dùng isolated `BrowserContext` để tách cookies/storage, nhưng backend data vẫn cần isolation riêng.

## 2. Why does it exist?

E2E tests chia sẻ cookies, users hoặc mutable records dễ tạo failures phụ thuộc execution order và parallelism.

## 3. How does it work?

```text
Browser process
 ├── Context Test A → cookies/storage A
 ├── Context Test B → cookies/storage B
 └── Context Test C → cookies/storage C
```

Browser isolation không tự cô lập database.

## 4. Practical implementation

```ts
test('user can create approval request', async ({ page }) => {
  const name = `request-${crypto.randomUUID()}`;
  await page.goto('/requests/new');
  await page.getByLabel('Name').fill(name);
  await page.getByRole('button', { name: 'Create' }).click();
  await expect(page.getByText(name)).toBeVisible();
});
```

Dùng semantic locators và deterministic setup thay vì arbitrary sleeps.

## 5. Real production scenario

CI chạy 8 workers. Tests dùng cùng employee account và draft record nên xóa/sửa data của nhau. Local sequential run luôn xanh.

## 6. Failure scenario & troubleshooting

**Symptom** → flaky chỉ khi CI parallel.  
**Evidence** → cùng data IDs xuất hiện ở nhiều workers.  
**Hypothesis** → shared mutable backend state.  
**Diagnosis** → repeat/parallel run, log worker/test IDs và data ownership.  
**Fix** → unique data, isolated tenant/schema hoặc deterministic reset.  
**Verification** → repeated parallel runs ổn định.

## 7. Common mistakes

`waitForTimeout`; selector theo layout; retry để che flake; tests phụ thuộc thứ tự; reuse shared account có mutable state.

## 8. Alternatives

Integration tests nhanh hơn cho backend rules. Unit tests bảo vệ pure logic. E2E nên tập trung critical user journeys và integration seams.

## 9. Trade-offs

### Advantages

Confidence cao ở browser-to-backend flow thực.

### Costs / Risks

Chậm, expensive và nhạy với environment/data nếu isolation kém.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Viết locator và assertion ổn định.

### Middle

Thiết kế setup/cleanup và parallel-safe data.

### Senior

Phân loại flake theo UI, network, data và environment.

### Technical Lead / Architect

Xây test portfolio theo risk thay vì đẩy mọi behavior vào E2E.

## 11. Key takeaway

- Browser isolation không đồng nghĩa database isolation.
- Flaky test là defect của test system.
- E2E nên bảo vệ critical journeys.

# 8. CDN Cache-Control: browser cache, shared cache và invalidation contract

## 1. What is it?

`Cache-Control` mô tả caching policy cho HTTP response. Mental model: origin phát hành freshness/reuse contract cho browser và shared caches như CDN.

## 2. Why does it exist?

Không có explicit policy, caches phải dùng heuristic hoặc không reuse response hiệu quả. Điều này ảnh hưởng latency, origin load và freshness correctness.

## 3. How does it work?

```text
Browser → CDN → Origin
           ├─ fresh hit → serve edge
           └─ stale/miss → revalidate/fetch
```

`max-age` và `s-maxage` có thể định nghĩa freshness khác nhau cho browser và shared cache. `no-cache` không đồng nghĩa `no-store`.

## 4. Practical implementation

Fingerprint asset:

```http
Cache-Control: public, max-age=31536000, immutable
```

Dynamic HTML thường cần TTL ngắn hoặc revalidation thay vì cache một năm.

## 5. Real production scenario

E-commerce deploy `app.abc123.js`. URL đổi khi content đổi nên TTL dài an toàn. Product price endpoint lại cần policy khác vì freshness là business requirement.

## 6. Failure scenario & troubleshooting

**Symptom** → deploy xong users vẫn thấy asset cũ.  
**Evidence** → mutable URL có TTL dài và CDN hit với `Age` lớn.  
**Hypothesis** → version/cache-key strategy sai.  
**Diagnosis** → inspect headers, cache status và waterfall.  
**Fix** → content hashing/versioned URLs; purge chỉ dùng khi cần.  
**Verification** → HTML mới tham chiếu asset URL mới.

## 7. Common mistakes

`no-store` cho mọi thứ; TTL dài trên mutable URL; nhầm browser cache với CDN cache; cache personalized response public.

## 8. Alternatives

Redis/application cache giảm backend compute nhưng không giảm network distance như CDN. Browser cache chỉ phục vụ một client.

## 9. Trade-offs

### Advantages

Latency thấp, giảm origin traffic và tăng resilience cho cacheable content.

### Costs / Risks

Stale content, invalidation complexity và privacy risk nếu policy sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu fresh, stale và revalidation.

### Middle

Đọc headers và DevTools.

### Senior

Thiết kế immutable assets và shared-cache safety.

### Technical Lead / Architect

Định nghĩa caching contract xuyên Browser → CDN → Application theo data class.

## 11. Key takeaway

- Cache policy là correctness contract.
- Immutable content nên đi với versioned URL.
- Personalized data cần shared-cache boundary nghiêm ngặt.

# 9. OpenTelemetry sampling: giữ trace hữu ích mà kiểm soát telemetry cost

## 1. What is it?

Sampling quyết định traces/spans nào được record/export. Mental model: observability có budget; không phải hệ thống production nào cũng cần hoặc có thể lưu 100% traces.

## 2. Why does it exist?

Traffic lớn tạo volume spans rất cao, tăng network, storage và query cost. Sampling sai lại có thể loại đúng rare failures cần điều tra.

## 3. How does it work?

```text
Incoming request
      │
      ▼
Sampling decision
  ├─ sampled ─► export trace
  └─ dropped ─► giảm telemetry volume
```

Head sampling quyết định sớm; tail sampling quyết định sau khi collector thấy nhiều hơn về trace và có thể ưu tiên errors/slow traces.

## 4. Practical implementation

```csharp
services.AddOpenTelemetry()
    .WithTracing(b => b
        .SetSampler(new ParentBasedSampler(
            new TraceIdRatioBasedSampler(0.1)))
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation());
```

Parent-based strategy giúp sampling decision nhất quán hơn xuyên services.

## 5. Real production scenario

API 5.000 RPS tạo telemetry bill lớn với 100% tracing. Team giữ representative baseline và ưu tiên error/slow traces ở collector.

## 6. Failure scenario & troubleshooting

**Symptom** → metrics báo error nhưng không có trace tương ứng.  
**Evidence** → head sampling rate thấp.  
**Hypothesis** → rare failure bị drop trước khi biết outcome.  
**Diagnosis** → review sampler/collector policies và correlation với logs/metrics.  
**Fix** → tail/error-preserving policy phù hợp.  
**Verification** → synthetic failures giữ trace đủ context.

## 7. Common mistakes

Dùng traces thay metrics; sampling từng service độc lập; giữ 100% vô hạn; không monitor collector saturation; export high-cardinality data thiếu kiểm soát.

## 8. Alternatives

Metrics phù hợp aggregate SLI; structured logs phù hợp discrete events; traces mạnh cho causal path qua distributed dependencies.

## 9. Trade-offs

### Advantages

Kiểm soát volume/cost trong khi vẫn giữ distributed context.

### Costs / Risks

Mất evidence nếu policy kém; tail sampling tăng collector state và complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu trace/span và sampling.

### Middle

Configure parent-based sampling.

### Senior

Thiết kế policy theo error/latency và validate coverage.

### Technical Lead / Architect

Cân bằng observability fidelity, incident needs, privacy và platform cost.

## 11. Key takeaway

- Sampling là observability design, không chỉ cost switch.
- Metrics và traces có vai trò khác nhau.
- Rare failures cần evidence-preserving policy có chủ đích.

# 10. LLM Structured Outputs: schema contract, validation và deterministic boundary

## 1. What is it?

Structured Outputs yêu cầu model trả dữ liệu theo schema thay vì free-form text. Mental model: schema làm interface contract cho model output nhưng không biến nội dung probabilistic thành business truth.

## 2. Why does it exist?

Parsing prose hoặc chỉ prompt “hãy trả JSON” dễ hỏng vì missing fields, sai type hoặc extra text. Machine workflow cần output shape ổn định hơn.

## 3. How does it work?

```text
Application
   │ prompt + schema
   ▼
LLM
   │ structured result
   ▼
Schema-valid object
   ├─ deterministic validation
   └─ side effect only after authorization/rules
```

Schema validity trả lời “shape có đúng không?”, không trả lời “fact có đúng không?”.

## 4. Practical implementation

```csharp
public sealed record TicketClassification(
    string Category,
    string Priority,
    string[] Reasons);

static bool IsAllowedPriority(string value) =>
    value is "low" or "medium" or "high";
```

Application vẫn validate domain rules, permissions và high-risk decisions sau model output.

## 5. Real production scenario

Support system dùng LLM phân loại ticket. Model trả object đúng schema, nhưng SLA-critical escalation vẫn áp deterministic rules cho security incident hoặc contractual priority.

## 6. Failure scenario & troubleshooting

**Symptom** → JSON luôn parse được nhưng ticket route sai.  
**Evidence** → schema valid, semantic classification sai.  
**Hypothesis** → structural reliability bị nhầm với semantic accuracy.  
**Diagnosis** → versioned evaluation dataset và failure slices.  
**Fix** → improve context/examples, deterministic overrides, human review cho high-risk cases.  
**Verification** → rerun eval và đo precision/recall theo class.

## 7. Common mistakes

Coi schema-valid là correct; cho model tự quyết authorization; không version schema; không có evals; retry vô hạn khi output không phù hợp business rule.

## 8. Alternatives

Tool Calling phù hợp khi model chọn action. Deterministic rules tốt hơn khi logic rõ. Free-form output phù hợp nội dung cho người đọc.

## 9. Trade-offs

### Advantages

Integration ổn định hơn, giảm parsing glue code và dễ test contract.

### Costs / Risks

Semantic hallucination vẫn tồn tại; schema evolution và model behavior cần quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt free text và structured contract.

### Middle

Implement schema parsing + domain validation.

### Senior

Xây evals, fallback và deterministic safety checks.

### Technical Lead / Architect

Quyết định boundary nào cho phép probabilistic output và boundary nào bắt buộc deterministic correctness.

## 11. Key takeaway

- Schema correctness không đồng nghĩa business correctness.
- Side effects quan trọng cần deterministic validation và authorization.
- AI integration cần evals, versioning và observable failure modes.
