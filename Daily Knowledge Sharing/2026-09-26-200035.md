# 1. C# CancellationToken propagation: cancellation là protocol, không phải exception handling

## 1. What is it?

Mental model: `CancellationToken` là tín hiệu hợp tác truyền từ caller xuống toàn bộ call chain. Nó không “kill thread”; code nhận token quyết định điểm nào an toàn để dừng.

## 2. Why does it exist?

Khi HTTP client disconnect hoặc timeout, tiếp tục query database, gọi HTTP và serialize response chỉ tiêu tốn capacity cho kết quả không còn người nhận. Cancellation cho phép giải phóng tài nguyên sớm.

## 3. How does it work?

```text
RequestAborted
  -> Application Service
     -> EF Core
     -> HttpClient
     -> background operation
```

Token mang trạng thái cancellation; API hỗ trợ token đăng ký callback hoặc ném `OperationCanceledException` tại cancellation point.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:int}", async (
    int id, AppDbContext db, HttpClient http, CancellationToken ct) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    if (order is null) return Results.NotFound();

    using var response = await http.GetAsync(
        $"risk/{order.CustomerId}", ct);

    return Results.Ok(order);
});
```

## 5. Real production scenario

Một mobile request bị user đóng màn hình sau 500 ms. Nếu token được propagate, SQL command và outbound HTTP có thể bị cancel; nếu không, server vẫn giữ connection, thread continuation và dependency capacity.

## 6. Failure scenario & troubleshooting

**Symptom** → request đã timeout ở gateway nhưng SQL workload vẫn tăng.  
**Evidence** → trace cho thấy dependency span tiếp tục sau request span.  
**Hypothesis** → token bị mất ở service boundary.  
**Diagnosis** → tìm method async không nhận hoặc không truyền token.  
**Fix** → propagate token tới I/O boundary.  
**Verification** → cancel request và xác nhận dependency kết thúc sớm.

## 7. Common mistakes

Dùng `CancellationToken.None` giữa call chain; catch `Exception` rồi log cancellation như lỗi; cancel sau khi side effect không thể rollback mà không xác định semantics.

## 8. Alternatives

Timeout giới hạn thời lượng; cancellation phản ánh caller không còn cần kết quả. Hai cơ chế bổ sung nhau, không thay thế nhau.

## 9. Trade-offs

### Advantages
Giảm wasted work, cải thiện shutdown và capacity.

### Costs / Risks
Phải xác định cancellation boundary; dừng giữa workflow có side effect có thể để trạng thái dở dang.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu token là cooperative signal.

### Middle
Propagate token qua EF Core, HttpClient và service methods.

### Senior
Phân biệt operation có thể cancel an toàn với side effect cần hoàn tất/idempotency.

### Technical Lead / Architect
Quy định cancellation semantics xuyên API, messaging và shutdown; không biến mọi method thành cancellation point tùy tiện.

## 11. Key takeaway

- Cancellation phải được propagate tới I/O boundary.
- Timeout và cancellation giải quyết hai vấn đề khác nhau.
- Sau irreversible side effect, cancellation cần engineering judgment.

# 2. ASP.NET Core streaming: giảm memory footprint nhưng phải hiểu backpressure và disconnect

## 1. What is it?

Streaming gửi dữ liệu dần thay vì materialize toàn bộ payload trong memory. Mental model: producer tạo chunk theo tốc độ mà transport có thể tiêu thụ.

## 2. Why does it exist?

Export 500 MB bằng `byte[]` có thể đẩy process vào memory pressure/LOH. Streaming giữ working set gần với buffer size thay vì file size.

## 3. How does it work?

```text
Database/File -> producer -> response buffer -> Kestrel -> proxy -> client
                    <------ backpressure ------
```

Async write cho phép producer chờ khi downstream chậm.

## 4. Practical implementation

```csharp
app.MapGet("/exports/{name}", async (
    string name, HttpResponse response, CancellationToken ct) =>
{
    response.ContentType = "text/csv";
    await using var writer = new StreamWriter(response.Body, leaveOpen: true);

    await foreach (var row in LoadRowsAsync(name, ct))
    {
        await writer.WriteLineAsync($"{row.Id},{row.Name}");
        if (ct.IsCancellationRequested) break;
    }
    await writer.FlushAsync(ct);
});
```

## 5. Real production scenario

Một reporting API phục vụ nhiều export đồng thời. Streaming tránh giữ hàng chục file lớn trong RAM và bắt đầu trả byte đầu tiên sớm hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → memory thấp nhưng request treo rất lâu.  
**Evidence** → client/network chậm, active requests tăng.  
**Diagnosis** → downstream backpressure giữ connection lâu.  
**Fix** → cancellation, timeout hợp lý, giới hạn concurrency và cân nhắc Blob Storage + SAS cho file lớn.  
**Verification** → load test với slow clients.

## 7. Common mistakes

Gọi `ToListAsync()` trước khi stream; buffer toàn bộ file; bỏ qua disconnect; assume reverse proxy không buffering.

## 8. Alternatives

Blob Storage + SAS phù hợp artifact lớn/tái sử dụng; buffered response đơn giản hơn cho payload nhỏ.

## 9. Trade-offs

### Advantages
Working set thấp, time-to-first-byte tốt.

### Costs / Risks
Connection sống lâu, retry khó hơn, lỗi sau khi headers đã gửi không thể đổi status code dễ dàng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu stream khác materialization.

### Middle
Implement async streaming và cancellation.

### Senior
Đo backpressure, proxy buffering, concurrency và partial-response semantics.

### Technical Lead / Architect
Quyết định khi nào API stream trực tiếp, khi nào tạo artifact rồi phân phối qua object storage/CDN.

## 11. Key takeaway

- Streaming tối ưu memory, không tự động tối ưu throughput.
- Slow consumer trở thành capacity concern.
- File rất lớn thường nên tách generation khỏi delivery.

# 3. EF Core ExecuteUpdate/ExecuteDelete: set-based mutation và cái giá của việc bypass Change Tracker

## 1. What is it?

`ExecuteUpdateAsync` và `ExecuteDeleteAsync` biến LINQ predicate thành SQL `UPDATE`/`DELETE` trực tiếp. Chúng không load từng entity và không đồng bộ Change Tracker.

## 2. Why does it exist?

Load 100.000 rows chỉ để đổi một cột tạo round trips, allocations và tracking overhead không cần thiết. Database vốn có set-based operations.

## 3. How does it work?

```text
LINQ predicate -> SQL translation -> one set-based statement -> database
                              X-> no tracked entity synchronization
```

## 4. Practical implementation

```csharp
var affected = await db.Orders
    .Where(x => x.Status == OrderStatus.Pending &&
                x.CreatedAt < cutoff)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired), ct);
```

## 5. Real production scenario

Job hết hạn pending orders chạy mỗi giờ. Set-based update giảm hàng nghìn entity materializations thành một command.

## 6. Failure scenario & troubleshooting

**Symptom** → sau update, code đọc tracked entity vẫn thấy status cũ.  
**Evidence** → SQL đã update đúng nhưng Change Tracker chứa snapshot cũ.  
**Diagnosis** → bulk mutation bypass tracker.  
**Fix** → không trộn tracked entities với set-based mutation trong cùng unit of work, hoặc reload/clear có chủ đích.  
**Verification** → integration test kiểm tra cả DB và context behavior.

## 7. Common mistakes

Mong `SaveChanges` quản lý mutation này; quên concurrency/business invariant; update predicate quá rộng; không kiểm tra affected row count.

## 8. Alternatives

Tracked update tốt khi cần domain logic từng entity. Raw SQL linh hoạt hơn nhưng giảm type safety. Bulk library hữu ích cho import phức tạp.

## 9. Trade-offs

### Advantages
Ít memory, ít round trip, tận dụng database engine.

### Costs / Risks
Bypass tracking và domain hooks; transaction/invariant phải thiết kế rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu tracked update và set-based update khác nhau.

### Middle
Dùng đúng predicate và transaction.

### Senior
Nhận ra stale tracker, concurrency và invariant risks.

### Technical Lead / Architect
Quyết định mutation nào thuộc domain workflow, mutation nào là data operation thuần.

## 11. Key takeaway

- Set-based mutation mạnh vì không materialize entities.
- “Nhanh hơn” đi kèm việc bỏ qua Change Tracker semantics.
- Affected-row count là signal correctness quan trọng.

# 4. SQL Server deadlock: đọc wait graph thay vì chữa bằng retry mù quáng

## 1. What is it?

Deadlock xảy ra khi các transaction giữ resource mà transaction khác cần và tạo vòng chờ. SQL Server chọn một victim để phá vòng.

## 2. Why does it exist?

Concurrency cho throughput, nhưng nhiều lock acquisition order có thể tạo cycle. Database không thể chờ vô hạn nên phải abort một transaction.

## 3. How does it work?

```text
T1 holds Order  -> waits Customer
T2 holds Customer -> waits Order
             cycle -> deadlock victim
```

## 4. Practical implementation

Giữ lock order nhất quán:

```sql
BEGIN TRAN;

UPDATE dbo.Customers
SET UpdatedAt = SYSUTCDATETIME()
WHERE Id = @CustomerId;

UPDATE dbo.Orders
SET Status = @Status
WHERE Id = @OrderId;

COMMIT;
```

Mọi workflow liên quan nên acquire cùng thứ tự khi khả thi.

## 5. Real production scenario

Checkout và fraud-review cùng update Customer/Order nhưng thứ tự ngược nhau. Bình thường chạy tốt; peak traffic mới xuất hiện deadlock.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi 1205 rải rác.  
**Evidence** → Extended Events deadlock graph.  
**Hypothesis** → lock order hoặc scan giữ lock quá rộng.  
**Diagnosis** → đọc victim/process/resource nodes; xem execution plan và index.  
**Fix** → thống nhất access order, rút ngắn transaction, cải thiện access path. Retry chỉ là safety net.  
**Verification** → replay concurrent workload và theo dõi deadlock rate.

## 7. Common mistakes

Tăng timeout; retry vô hạn; thêm index không đọc plan; giữ transaction trong lúc gọi external API.

## 8. Alternatives

Optimistic concurrency xử lý lost update, không loại bỏ mọi deadlock. Snapshot isolation giảm một số reader/writer blocking nhưng không chữa mọi writer/writer cycle.

## 9. Trade-offs

### Advantages
Transaction locking bảo vệ consistency.

### Costs / Risks
Concurrency cao làm contention và deadlock trở thành runtime behavior cần quan sát.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu deadlock là cycle, không chỉ “query chậm”.

### Middle
Biết lấy deadlock graph.

### Senior
Liên hệ plan, index, lock scope, transaction duration.

### Technical Lead / Architect
Thiết kế transaction boundary và access ordering giữa workflows.

## 11. Key takeaway

- Deadlock graph là evidence chính.
- Retry không thay thế root-cause fix.
- Transaction càng dài, contention surface càng lớn.

# 5. Redis outage strategy: cache phải degrade được thay vì biến thành dependency bắt buộc

## 1. What is it?

Cache outage strategy định nghĩa application làm gì khi Redis timeout/unavailable: fallback DB, serve stale, fail fast, hay từ chối một phần traffic.

## 2. Why does it exist?

Một cache được thêm để tăng reliability/performance nhưng nếu mọi request bắt buộc Redis thành công, cache vô tình trở thành critical dependency.

## 3. How does it work?

```text
Request -> Redis
          | hit -> response
          | miss/failure
          v
        Database -> optional repopulate
```

Fallback phải có capacity guard để không biến Redis outage thành database outage.

## 4. Practical implementation

```csharp
Product? cached = null;
try
{
    cached = await cache.GetAsync<Product>(key, ct);
}
catch (RedisException ex)
{
    logger.LogWarning(ex, "Redis unavailable for {Key}", key);
}

if (cached is not null) return cached;

await dbFallbackGate.WaitAsync(ct);
try
{
    return await db.Products.AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);
}
finally { dbFallbackGate.Release(); }
```

## 5. Real production scenario

Product catalog cache mất kết nối. Nếu toàn bộ 5.000 RPS đổ ngay vào SQL, fallback “thành công” có thể làm SQL sập sau vài giây.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis errors tăng, sau đó SQL CPU/connection pool tăng mạnh.  
**Evidence** → trace cho thấy cache failure và DB traffic tương quan.  
**Diagnosis** → unbounded fallback.  
**Fix** → timeout ngắn, bulkhead, stale strategy, load shedding.  
**Verification** → chaos test Redis outage.

## 7. Common mistakes

Retry Redis nhiều lần trong request; fallback không giới hạn; cache authorization data quá lâu; không có metric hit/miss/error.

## 8. Alternatives

`IMemoryCache` tránh network nhưng không shared; CDN phù hợp HTTP content; không cache là lựa chọn tốt nếu DB đã đáp ứng SLO.

## 9. Trade-offs

### Advantages
Giảm latency và DB load.

### Costs / Risks
Freshness, invalidation, serialization và một failure mode mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu cache là optimization layer.

### Middle
Implement cache-aside với timeout.

### Senior
Thiết kế fallback có capacity protection.

### Technical Lead / Architect
Quyết định dữ liệu nào có thể stale và liệu Redis có đáng với operational burden.

## 11. Key takeaway

- Cache outage phải được thiết kế trước.
- Fallback không giới hạn có thể gây cascading failure.
- Có trường hợp đúng nhất là không cache.

# 6. Azure App Service deployment slots: zero-downtime release, warm-up và configuration boundaries

## 1. What is it?

Deployment slot là environment chạy song song trong cùng App Service để deploy/validate trước khi swap vào Production.

## 2. Why does it exist?

Deploy trực tiếp có thể expose cold start, bad config hoặc binary lỗi ngay cho user. Slot tạo pre-production runtime gần Production và hỗ trợ traffic switch nhanh.

## 3. How does it work?

```text
Build artifact -> Staging slot -> warm-up/health
                              -> swap -> Production
Old Production <------------- becomes Staging
```

Slot settings có thể “stick” theo slot thay vì swap.

## 4. Practical implementation

Application nên có readiness endpoint kiểm tra khả năng phục vụ mà không biến mọi dependency optional thành hard gate:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, name: "sql");

app.MapHealthChecks("/health/ready");
```

## 5. Real production scenario

Release API mới lên staging, warm JIT/cache, chạy smoke tests rồi swap. User không chịu cold-start của deployment trực tiếp.

## 6. Failure scenario & troubleshooting

**Symptom** → staging khỏe nhưng sau swap Production lỗi DB authentication.  
**Evidence** → configuration diff cho thấy connection/identity setting là slot-specific sai.  
**Diagnosis** → hiểu sai slot setting semantics.  
**Fix** → classify config rõ: artifact-invariant, environment-specific, slot-sticky.  
**Verification** → pre-swap validation bằng chính identity/network path dự kiến.

## 7. Common mistakes

Dùng slot như full isolation; chạy destructive migration khi app versions chưa backward compatible; health check quá nông; quên outbound/network differences.

## 8. Alternatives

Blue-Green ở Container Apps/Kubernetes cho nhiều control hơn; direct deployment đơn giản hơn với low-risk internal service.

## 9. Trade-offs

### Advantages
Rollback/swap nhanh, warm-up trước release.

### Costs / Risks
Config complexity, extra compute, database vẫn thường shared.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu deploy và release có thể tách nhau.

### Middle
Deploy staging, health validate, swap.

### Senior
Thiết kế backward-compatible migration và rollback.

### Technical Lead / Architect
Quyết định release topology dựa trên blast radius, SLO và cost.

## 11. Key takeaway

- Slot giảm application deployment risk, không tự giải quyết database migration.
- Configuration classification là phần của release design.
- Health validation phải phản ánh khả năng phục vụ thực.

# 7. DDD Aggregate: bảo vệ invariant và transaction boundary thay vì gom object theo quan hệ

## 1. What is it?

Aggregate là consistency boundary trong domain; Aggregate Root là entry point để thay đổi state bên trong boundary. Không phải mọi object có foreign key đều thuộc cùng aggregate.

## 2. Why does it exist?

Nếu business invariant cần đúng ngay sau mỗi transaction, ta cần boundary xác định dữ liệu nào phải thay đổi atomically. Aggregate giúp tránh transaction lan qua toàn graph.

## 3. How does it work?

```text
Application Service
      |
      v
Aggregate Root -> Entity / Value Object
      |
 enforce invariant
      |
 transaction
```

Cross-aggregate consistency thường được xử lý qua ID reference và eventual workflow nếu không cần atomicity.

## 4. Practical implementation

```csharp
public sealed class PurchaseOrder
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyCollection<OrderLine> Lines => _lines;
    public decimal Limit { get; private set; }

    public void AddLine(ProductId productId, decimal price)
    {
        if (_lines.Sum(x => x.Price) + price > Limit)
            throw new DomainException("Order limit exceeded");

        _lines.Add(new OrderLine(productId, price));
    }
}
```

## 5. Real production scenario

Approval workflow yêu cầu “approved order không được sửa line”. Rule nên được bảo vệ tại aggregate boundary thay vì dựa vào UI disable button.

## 6. Failure scenario & troubleshooting

**Symptom** → SaveChanges chậm, nhiều concurrency conflict.  
**Evidence** → aggregate load hàng nghìn child rows cho thay đổi nhỏ.  
**Diagnosis** → boundary được chọn theo object graph thay vì invariant.  
**Fix** → tách boundary theo consistency requirement.  
**Verification** → domain tests + concurrency integration tests.

## 7. Common mistakes

Một aggregate cho cả bounded context; repository cho từng child entity; public setters bypass invariant; dùng DDD vocabulary cho CRUD model.

## 8. Alternatives

Transaction Script phù hợp domain đơn giản. Anemic CRUD model có thể đủ khi business rules ít. DDD có giá trị khi complexity nằm trong domain.

## 9. Trade-offs

### Advantages
Invariant rõ, mutation có entry point, transaction boundary có ý nghĩa.

### Costs / Risks
Modeling khó, aggregate quá lớn gây contention; quá nhỏ gây orchestration complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu invariant phải được bảo vệ ở code server-side.

### Middle
Implement behavior qua Aggregate Root.

### Senior
Phân biệt strong consistency và eventual consistency.

### Technical Lead / Architect
Định boundary theo business capability, transaction và contention; biết khi DDD là overkill.

## 11. Key takeaway

- Aggregate là consistency boundary, không phải folder.
- Boundary xuất phát từ invariant.
- DDD không cần thiết cho mọi CRUD system.

# 8. Azure Service Bus lock duration và message settlement: tránh duplicate processing khi handler chạy lâu

## 1. What is it?

Ở Peek-Lock mode, consumer nhận message nhưng broker chỉ khóa tạm thời. Sau xử lý, consumer `Complete`; nếu lock hết hạn trước settlement, message có thể được giao lại.

## 2. Why does it exist?

Broker cần phục hồi message nếu consumer crash. Permanent ownership sẽ làm message mắc kẹt; lease/lock tạo cơ chế recovery.

## 3. How does it work?

```text
Receive -> lock lease -> process -> Complete
                    |
                    +-> lease expires -> redelivery
```

At-least-once delivery nghĩa duplicate là behavior hợp lệ.

## 4. Practical implementation

```csharp
var processor = client.CreateProcessor("billing", new ServiceBusProcessorOptions
{
    MaxConcurrentCalls = 8,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(10)
});

processor.ProcessMessageAsync += async args =>
{
    await handler.HandleAsync(args.Message, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message, args.CancellationToken);
};
```

Side effect vẫn phải idempotent; lock renewal không biến delivery thành exactly-once.

## 5. Real production scenario

PDF generation mất 4 phút trong khi lock ngắn hơn. Handler hoàn thành side effect nhưng settlement thất bại; broker giao message lại và tạo PDF lần hai.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate business action dù queue không có “duplicate message” rõ ràng.  
**Evidence** → lock-lost exception, delivery count tăng.  
**Diagnosis** → processing time vượt lock/renewal hoặc process pause.  
**Fix** → idempotency, chia nhỏ work, điều chỉnh renewal có giới hạn.  
**Verification** → inject delay vượt lock và kiểm tra side effect chỉ xảy ra một lần.

## 7. Common mistakes

Complete trước side effect; assume lock = exactly once; handler quá dài; retry poison message vô hạn thay vì DLQ.

## 8. Alternatives

Queue work thành nhiều stage; Durable Functions cho orchestration dài; database job table cho workflow đơn giản nhưng phải tự xây leasing/retry.

## 9. Trade-offs

### Advantages
Crash recovery tốt, competing consumers tự nhiên.

### Costs / Risks
Duplicate processing, lock management, DLQ operations và idempotency storage.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu receive chưa đồng nghĩa message biến mất.

### Middle
Biết Complete/Abandon/DeadLetter và cancellation.

### Senior
Thiết kế idempotency và xử lý lock loss.

### Technical Lead / Architect
Quyết định workload nào phù hợp queue, workload nào cần orchestration khác; đặt ownership cho DLQ.

## 11. Key takeaway

- Message lock là lease, không phải ownership vĩnh viễn.
- Duplicate delivery là expected behavior.
- Long-running handler cần cả lock strategy và idempotency.

# 9. Akamai/CDN Cache-Control: điều khiển freshness xuyên Browser → Edge → Origin

## 1. What is it?

CDN cache giữ response gần user. `Cache-Control` mô tả freshness/revalidation semantics cho browser và shared caches; Akamai có thể bổ sung policy ở edge.

## 2. Why does it exist?

Static/content-heavy site không nên đưa mọi request về origin. Edge cache giảm latency, bandwidth và origin load.

## 3. How does it work?

```text
Browser -> Akamai Edge -> Origin/App -> CMS
   cache       cache
```

`max-age` ảnh hưởng client cache; `s-maxage` có thể đặt lifetime riêng cho shared cache.

## 4. Practical implementation

```csharp
app.MapGet("/catalog/{slug}", async (string slug, CatalogService svc, HttpContext ctx) =>
{
    var page = await svc.GetAsync(slug);
    ctx.Response.Headers.CacheControl = "public, max-age=60, s-maxage=300";
    return Results.Ok(page);
});
```

Chỉ cache response không chứa dữ liệu user-specific nếu cache key/policy chưa phân tách an toàn.

## 5. Real production scenario

CMS marketing page có traffic toàn cầu. Edge TTL 5 phút giảm origin requests mạnh; publish flow cần purge/revalidation để editor không thấy nội dung cũ quá lâu.

## 6. Failure scenario & troubleshooting

**Symptom** → origin đã deploy nội dung mới nhưng user vẫn thấy bản cũ.  
**Evidence** → response headers/edge diagnostics cho thấy cache hit và age cao.  
**Diagnosis** → TTL/purge/cache-key policy.  
**Fix** → sửa freshness policy hoặc purge đúng object; tránh “disable cache toàn site”.  
**Verification** → kiểm tra Browser, Edge và Origin riêng biệt.

## 7. Common mistakes

Cache personalized response; dùng query string không nhất quán; purge mọi thứ; nhầm browser cache với edge cache; thiếu versioned static assets.

## 8. Alternatives

Browser cache chỉ giảm request từ cùng client; reverse-proxy cache gần origin; Redis cache dữ liệu/application object chứ không thay CDN.

## 9. Trade-offs

### Advantages
Latency thấp, giảm origin load, tăng resilience trước traffic spike.

### Costs / Risks
Stale content, invalidation complexity, cache-key/security mistakes.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu có nhiều cache layer.

### Middle
Đọc `Cache-Control`, `Age`, request waterfall.

### Senior
Debug cache key, freshness và personalized-content risk.

### Technical Lead / Architect
Chọn freshness SLA, purge strategy và ownership giữa app/CMS/CDN team.

## 11. Key takeaway

- Debug CDN phải xác định response đến từ layer nào.
- Freshness là business/engineering contract.
- Không cache user-specific response nếu key isolation chưa chắc chắn.

# 10. Contract testing cho API: bảo vệ compatibility mà không biến test suite thành E2E khổng lồ

## 1. What is it?

Contract test xác minh producer và consumer đồng ý về shape/semantics của interface: endpoint, fields, status, event schema hoặc protocol expectations.

## 2. Why does it exist?

Unit test có thể xanh ở cả hai service nhưng integration vẫn vỡ khi producer rename field hoặc đổi enum. Full E2E phát hiện được nhưng thường chậm, flaky và khó bao phủ mọi consumer expectation.

## 3. How does it work?

```text
Consumer expectation -> contract
                         |
                    verification
                         v
                      Producer
```

Contract không thay thế integration test; nó tập trung compatibility boundary.

## 4. Practical implementation

Một API integration test có thể khóa contract quan trọng:

```csharp
[Fact]
public async Task GetOrder_returns_backward_compatible_contract()
{
    var response = await _client.GetAsync("/api/orders/42");
    response.EnsureSuccessStatusCode();

    var json = await response.Content.ReadFromJsonAsync<JsonElement>();
    Assert.True(json.TryGetProperty("id", out _));
    Assert.True(json.TryGetProperty("status", out _));
    Assert.True(json.TryGetProperty("total", out _));
}
```

Với nhiều team/consumer, consumer-driven contract tooling có thể formalize expectations tốt hơn.

## 5. Real production scenario

Mobile app version cũ còn ngoài thị trường nhiều tháng. Backend release đổi `status` từ string sang object; server tests vẫn pass nhưng client cũ crash. Contract compatibility phải được xem như release constraint.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment producer làm một consumer lỗi ngay sau release.  
**Evidence** → trace/400/deserialization errors tại boundary.  
**Hypothesis** → breaking contract change.  
**Diagnosis** → diff OpenAPI/schema và consumer expectations.  
**Fix** → additive change, versioning hoặc compatibility adapter.  
**Verification** → chạy producer verification với contracts của active consumers.

## 7. Common mistakes

Snapshot toàn JSON khiến test brittle; contract test business internals; coi OpenAPI generation là đủ; xóa field “không còn dùng” mà không biết consumer ownership.

## 8. Alternatives

Integration test dùng real dependencies kiểm tra behavior rộng hơn. E2E bảo vệ user journey. Schema validation bảo vệ structure nhưng có thể không nắm semantic expectation.

## 9. Trade-offs

### Advantages
Feedback nhanh về breaking change, giảm nhu cầu E2E combinatorial.

### Costs / Risks
Contract lifecycle, versioning, stale consumer expectations và tooling overhead.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu API contract là cam kết với consumer.

### Middle
Viết integration/contract assertions cho fields và status quan trọng.

### Senior
Thiết kế additive evolution, deprecation và compatibility window.

### Technical Lead / Architect
Thiết lập ownership, version policy và chọn contract testing khi số consumer/independent deployment thực sự biện minh complexity.

## 11. Key takeaway

- Contract test bảo vệ boundary, không test lại toàn business logic.
- Backward compatibility là release concern, không chỉ coding concern.
- E2E, integration và contract tests bảo vệ các loại rủi ro khác nhau.
