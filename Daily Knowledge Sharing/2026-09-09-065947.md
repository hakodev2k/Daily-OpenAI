# 1. C# `ValueTask`: khi nào giảm allocation, khi nào làm async code nguy hiểm hơn

## 1. What is it?

`ValueTask` / `ValueTask<T>` là awaitable value type dùng để biểu diễn một operation có thể hoàn thành đồng bộ mà không cần luôn tạo một `Task` object mới.

Mental model:

```text
Task<T>
  └─ thường là một heap object đại diện completion

ValueTask<T>
  ├─ có thể chứa kết quả trực tiếp
  ├─ có thể wrap Task<T>
  └─ có thể dùng IValueTaskSource<T>
```

Điểm quan trọng: `ValueTask` không phải “Task nhưng nhanh hơn”. Nó đổi allocation profile bằng cách tăng complexity của usage contract.

## 2. Why does it exist?

Ở hot path mà phần lớn operations hoàn thành đồng bộ, tạo `Task<T>` cho mỗi call có thể sinh allocation không cần thiết.

Ví dụ một parser, pool hoặc cache layer có 95% cache hits. Nếu mỗi hit vẫn tạo `Task<T>`, hàng triệu calls mỗi phút có thể tạo allocation pressure đáng kể.

`ValueTask<T>` tồn tại để tối ưu trường hợp này khi profiling chứng minh allocation thực sự đáng quan tâm.

## 3. How does it work?

Một `ValueTask<T>` có thể chứa trực tiếp result hoặc reference tới asynchronous operation.

```csharp
public ValueTask<Product?> GetAsync(Guid id)
{
    if (_memory.TryGetValue(id, out var product))
        return ValueTask.FromResult<Product?>(product);

    return new ValueTask<Product?>(LoadFromDatabaseAsync(id));
}
```

Nếu cache hit, không cần tạo `Task<Product?>` mới. Nếu cache miss, nó wrap `Task` từ database path.

Nhưng unlike `Task`, một `ValueTask` không nên được await nhiều lần tùy ý, lưu lâu dài hoặc dùng với nhiều combinators mà không hiểu backing implementation.

## 4. Practical implementation

Dùng `ValueTask` ở internal hot path khi có bằng chứng rõ:

```csharp
public sealed class ProductLookup
{
    private readonly Dictionary<Guid, Product> _cache = new();

    public ValueTask<Product?> TryGetAsync(Guid id)
    {
        if (_cache.TryGetValue(id, out var product))
            return ValueTask.FromResult<Product?>(product);

        return LoadAsync(id);
    }

    private async ValueTask<Product?> LoadAsync(Guid id)
    {
        await Task.Delay(10);
        return null;
    }
}
```

Caller dùng bình thường:

```csharp
var product = await lookup.TryGetAsync(id);
```

Nếu cần cache awaitable, truyền qua API generic hoặc await nhiều lần, thường nên chuyển sang `Task`:

```csharp
Task<Product?> task = lookup.TryGetAsync(id).AsTask();
```

## 5. Real production scenario

Một high-throughput in-memory metadata resolver được gọi hàng chục triệu lần/ngày. 98% calls hoàn thành từ local cache. Allocation profiling cho thấy `Task<T>` chiếm tỷ lệ đáng kể Gen 0 allocation.

Chuyển đúng hot path sang `ValueTask<T>` giúp giảm allocation. Nhưng nếu dùng rộng khắp service layer chỉ vì “nhanh hơn”, code review và correctness cost có thể lớn hơn lợi ích.

## 6. Failure scenario & troubleshooting

**Symptom** → code async thỉnh thoảng throw hoặc behavior khó đoán khi cùng `ValueTask` bị await nhiều lần.

**Evidence** → call site giữ `ValueTask` trong field hoặc await lại sau khi operation hoàn tất.

**Hypothesis** → backing implementation dùng `IValueTaskSource<T>` chỉ hỗ trợ single consumption.

**Diagnosis** → kiểm tra ownership và lifetime của returned `ValueTask`.

**Fix** → await ngay một lần hoặc convert sang `Task` nếu cần reuse.

**Verification** → concurrency tests + allocation benchmark.

## 7. Common mistakes

* Thay mọi `Task<T>` bằng `ValueTask<T>` mà không benchmark.
* Await cùng instance nhiều lần.
* Dùng `ValueTask` trong public API chỉ để “tối ưu”.
* Quên rằng struct lớn hơn reference có thể tăng copy cost.
* Đánh giá performance chỉ bằng microbenchmark không representative.

## 8. Alternatives

`Task<T>` vẫn là lựa chọn mặc định vì semantics đơn giản, tooling tốt và dễ compose với `Task.WhenAll` / `Task.WhenAny`.

Nếu optimization target là pooling sâu hơn, `IValueTaskSource<T>` tồn tại nhưng chỉ nên dùng ở library/runtime-level code hoặc very hot infrastructure path.

## 9. Trade-offs

### Advantages

* Có thể giảm allocation cho frequently synchronous completion.
* Hữu ích trong high-throughput library/internal infrastructure.

### Costs / Risks

* Usage contract phức tạp hơn.
* Dễ misuse ở call site.
* Ít composable hơn `Task`.
* Lợi ích thường không đáng kể ở normal business code.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task` là default abstraction cho async work; `ValueTask` là optimization-specific tool.

### Middle

Biết khi nào `ValueTask` có synchronous fast path và biết chỉ await một lần.

### Senior

Đo allocation, hiểu `IValueTaskSource`, API compatibility và composition cost.

### Technical Lead / Architect

Quyết định nơi nào optimization này thực sự đáng complexity và ngăn team biến micro-optimization thành coding convention toàn hệ thống.

## 11. Key takeaway

* `ValueTask` không phải phiên bản tốt hơn của `Task`.
* Chỉ dùng khi profiling cho thấy allocation của `Task` là bottleneck thực.
* Simplicity của `Task` thường có giá trị lớn hơn vài allocation tiết kiệm được.

# 2. ASP.NET Core Rate Limiting: partitioning, queueing và bảo vệ downstream thay vì chỉ “chặn request”

## 1. What is it?

Rate limiting là cơ chế giới hạn lượng work một client, tenant hoặc route có thể đưa vào hệ thống trong một khoảng thời gian.

Mental model:

```text
Incoming requests
       ↓
partition key: user / API key / tenant / IP
       ↓
rate limiter
   ├─ permit
   ├─ queue
   └─ reject 429
```

Mục tiêu không chỉ là chống abuse. Rate limiting còn là capacity protection cho database, third-party API và shared infrastructure.

## 2. Why does it exist?

Nếu một tenant hoặc integration bug gửi 20.000 requests/second, autoscaling không phải lúc nào cũng cứu được hệ thống. Database connection pool, external quota hoặc shared CPU có thể cạn trước khi compute scale xong.

Rate limiting biến capacity thành policy explicit thay vì để overload tự quyết định failure mode.

## 3. How does it work?

ASP.NET Core hỗ trợ các limiter như fixed window, sliding window, token bucket và concurrency limiter.

Partitioning đặc biệt quan trọng:

```text
wrong: one global bucket
→ one noisy tenant can consume all permits

better: bucket per tenant/API key
→ blast radius nhỏ hơn
```

Token bucket phù hợp workload có burst ngắn nhưng cần average rate kiểm soát. Concurrency limiter phù hợp resource mà số requests đồng thời quan trọng hơn requests/second.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(
        httpContext =>
        {
            var key = httpContext.User.FindFirst("tenant_id")?.Value
                      ?? httpContext.Connection.RemoteIpAddress?.ToString()
                      ?? "anonymous";

            return RateLimitPartition.GetTokenBucketLimiter(
                key,
                _ => new TokenBucketRateLimiterOptions
                {
                    TokenLimit = 100,
                    TokensPerPeriod = 50,
                    ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                    AutoReplenishment = true,
                    QueueLimit = 20,
                    QueueProcessingOrder = QueueProcessingOrder.OldestFirst
                });
        });
});

app.UseRateLimiter();
```

Client nên nhận `429` và retry có backoff, không phải retry loop tức thì.

## 5. Real production scenario

Một B2B API có vài enterprise tenants. Một customer rollout lỗi polling every 50 ms thay vì every 5 seconds. Traffic tăng 100× nhưng chỉ từ một tenant.

Global limiter có thể làm mọi tenant bị ảnh hưởng. Partitioned limiter theo tenant giữ blast radius cục bộ và bảo vệ SQL Server + external dependencies.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều `429` xuất hiện sau deploy nhưng server CPU vẫn thấp.

**Evidence** → rate-limit rejection tăng trên một partition cụ thể.

**Hypothesis** → policy quá thấp hoặc client traffic pattern thay đổi.

**Diagnosis** → xem permits, queue depth, tenant distribution, downstream capacity và endpoint latency.

**Fix** → tune policy theo resource budget; có thể tách read/write hoặc premium/default tenant classes.

**Verification** → load test burst + steady-state, quan sát `429`, queue delay, p95/p99 và downstream health.

## 7. Common mistakes

* Rate limit theo IP trong hệ thống sau NAT/proxy mà không hiểu forwarded headers.
* Một global bucket cho multi-tenant SaaS.
* Queue quá dài làm request timeout thay vì reject sớm.
* Client retry `429` ngay lập tức.
* Dùng rate limit thay authorization/quota/business entitlement.

## 8. Alternatives

API Gateway, Azure API Management, CDN/WAF hoặc reverse proxy có thể enforce rate limits sớm hơn edge. Application-level limiter vẫn hữu ích khi policy phụ thuộc authenticated tenant, subscription tier hoặc business context.

## 9. Trade-offs

### Advantages

* Bảo vệ capacity và dependencies.
* Giảm noisy-neighbor effect.
* Cho phép policy theo tenant/route.

### Costs / Risks

* Sai partition key có thể gây unfairness.
* Queueing tăng latency.
* Distributed enforcement giữa nhiều instances có thể cần gateway/shared coordination.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `429 Too Many Requests` là capacity/policy signal.

### Middle

Cấu hình limiter, partition key và test burst behavior.

### Senior

Thiết kế policy dựa trên downstream limits, fairness và retry behavior.

### Technical Lead / Architect

Quyết định enforce ở edge, gateway hay app; xác định capacity budget và tenant isolation strategy.

## 11. Key takeaway

* Rate limiting là overload control, không chỉ anti-abuse.
* Partitioning quyết định blast radius.
* Queue quá nhiều có thể tệ hơn reject sớm.

# 3. EF Core transaction boundaries + execution strategy: retry đúng chỗ mà không nhân đôi side effect

## 1. What is it?

EF Core transaction boundary xác định nhóm database changes nào phải commit hoặc rollback cùng nhau. Execution strategy là retry mechanism cho transient database failures.

Mental model:

```text
Business operation
   ↓
DB transaction
   ├─ SaveChanges
   ├─ SaveChanges
   └─ Commit

Transient failure?
   ↓
retry WHOLE safe unit
```

Retry một câu lệnh và retry toàn business operation không phải lúc nào cũng tương đương.

## 2. Why does it exist?

Cloud databases có transient failures: connection reset, failover, temporary throttling. Retry là hợp lý. Nhưng nếu operation vừa update DB vừa gọi payment API, retry toàn block có thể charge hai lần.

Vì vậy transaction boundary và retry boundary phải được thiết kế cùng nhau.

## 3. How does it work?

`SaveChanges` mặc định dùng transaction khi cần. Khi developer tạo transaction thủ công và execution strategy có retry, EF Core yêu cầu callback bao bọc toàn transaction unit để retry nhất quán.

Một failure nguy hiểm là commit ambiguity:

```text
client sends COMMIT
network breaks
client không biết commit succeeded hay failed
```

Blind retry có thể tạo duplicate business outcome nếu operation không idempotent.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var transaction =
        await db.Database.BeginTransactionAsync(cancellationToken);

    order.MarkPaid();
    await db.SaveChangesAsync(cancellationToken);

    db.OutboxMessages.Add(
        OutboxMessage.From(new OrderPaid(order.Id)));

    await db.SaveChangesAsync(cancellationToken);
    await transaction.CommitAsync(cancellationToken);
});
```

External publication được tách khỏi DB transaction qua Outbox thay vì gọi Service Bus trực tiếp bên trong retry block.

## 5. Real production scenario

Checkout service update Order + write audit row + publish event. Team gọi Service Bus trực tiếp giữa hai `SaveChanges`. SQL transient failure sau publish làm retry operation và event được publish hai lần.

Thiết kế đúng là giữ database mutation + Outbox record trong một transaction rồi publish bất đồng bộ sau commit.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate message xuất hiện sau SQL failover.

**Evidence** → retry telemetry trùng thời điểm duplicate publish.

**Hypothesis** → external side effect nằm trong retryable database unit.

**Diagnosis** → map transaction boundary và retry callback; tìm HTTP/message calls bên trong.

**Fix** → dùng Outbox hoặc idempotency cho external side effect.

**Verification** → fault-injection network failure quanh commit và xác nhận business outcome không bị nhân đôi.

## 7. Common mistakes

* Retry mọi exception.
* Gọi third-party API bên trong execution-strategy callback.
* Giữ transaction mở trong lúc chờ network lâu.
* Tưởng DB transaction có thể rollback external API.
* Không phân biệt transient failure với validation/deadlock/design problem.

## 8. Alternatives

Stored procedure có thể giữ logic database-centric trong một round trip. Saga phù hợp multi-service workflow. Outbox phù hợp coupling database commit với asynchronous message publication.

## 9. Trade-offs

### Advantages

* Retry giúp resilience trước transient DB faults.
* Explicit transaction bảo vệ multi-step DB invariant.

### Costs / Risks

* Transaction dài tăng lock duration.
* Retry có thể duplicate side effects.
* Outbox thêm worker/monitoring complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction bảo vệ database state, không bảo vệ external systems.

### Middle

Dùng transaction/execution strategy đúng scope.

### Senior

Phân tích commit ambiguity, retry safety và idempotency.

### Technical Lead / Architect

Thiết kế transaction boundary theo aggregate/service boundary và chọn Outbox/Saga khi crossing distributed boundary.

## 11. Key takeaway

* Retry boundary phải khớp với side-effect semantics.
* Database transaction không bao phủ external API/message broker.
* Outbox thường là bridge an toàn giữa DB commit và message publish.

# 4. Azure Cosmos DB partition key: RU, hot partition và vì sao data modeling phải đi từ access pattern

## 1. What is it?

Partition key là giá trị Cosmos DB dùng để phân phối documents thành logical partitions và ultimately physical partitions.

Mental model:

```text
Document
  ↓ partition key value
Logical partition
  ↓ distributed across
Physical partitions
```

Partition key quyết định scalability, query routing, transaction scope và khả năng xuất hiện hot partition.

## 2. Why does it exist?

Một single machine không thể giữ/write vô hạn data. Cosmos DB scale bằng cách chia dữ liệu và request load qua nhiều partitions.

Nếu application chọn key kém, toàn bộ traffic có thể dồn vào một partition dù account đã provision nhiều RU/s.

## 3. How does it work?

Point read biết cả `id` và partition key có thể route trực tiếp. Query không có partition key thường fan-out nhiều partitions và tốn RU hơn.

Ví dụ tốt cho multi-tenant workload có access chủ yếu theo tenant:

```json
{
  "id": "order-123",
  "tenantId": "tenant-42",
  "status": "Paid"
}
```

Partition key `/tenantId` giữ tenant-local operations cùng logical partition, nhưng một tenant cực lớn có thể trở thành hot key.

## 4. Practical implementation

```csharp
var container = cosmosClient.GetContainer("commerce", "orders");

var response = await container.ReadItemAsync<Order>(
    id: "order-123",
    partitionKey: new PartitionKey("tenant-42"),
    cancellationToken: cancellationToken);

Console.WriteLine(response.RequestCharge);
```

Production code nên record `RequestCharge`, latency và throttling (`429`) để hiểu query cost thật.

## 5. Real production scenario

SaaS platform chọn `/country` làm partition key vì “dữ liệu có country”. 70% customers ở US nên phần lớn writes dồn vào một key. Account tăng RU nhưng hot partition vẫn throttled.

Root cause là data distribution không khớp traffic distribution.

## 6. Failure scenario & troubleshooting

**Symptom** → `429 Too Many Requests` dù tổng RU usage toàn account chưa max.

**Evidence** → throttling tập trung vào một partition key range.

**Hypothesis** → hot partition.

**Diagnosis** → analyze key cardinality, request distribution, top tenants/users và access patterns.

**Fix** → redesign partition key, hierarchical partition keys hoặc workload sharding strategy.

**Verification** → replay representative load và theo dõi RU + throttling distribution.

## 7. Common mistakes

* Chọn partition key chỉ vì field có high cardinality.
* Không quan tâm traffic skew.
* Query cross-partition mọi nơi.
* Dùng Cosmos DB như relational DB rồi join bằng application loops.
* Không đo `RequestCharge`.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp relational transactions/query patterns mạnh. MongoDB có sharding model khác. Cosmos DB đáng cân nhắc khi global distribution, elastic scale và predictable partitioned access có giá trị rõ.

## 9. Trade-offs

### Advantages

* Horizontal scaling mạnh.
* Point reads theo partition key hiệu quả.
* Global distribution built-in.

### Costs / Risks

* Partition-key mistake khó sửa sau này.
* Cross-partition queries tốn RU.
* Data modeling bị ràng buộc bởi access patterns.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định nơi data được phân phối.

### Middle

Thực hiện point read/query đúng key và đo RU.

### Senior

Phân tích hot partition, data skew và query fan-out.

### Technical Lead / Architect

Quyết định partition strategy từ workload, tenant growth, transaction boundary và migration cost.

## 11. Key takeaway

* Partition key là architecture decision, không phải annotation nhỏ.
* High cardinality chưa đủ; phải xét traffic distribution.
* Access pattern nên dẫn dắt document model.

# 5. DDD Domain Event vs Integration Event: cùng là “event” nhưng khác boundary, consistency và ownership

## 1. What is it?

Domain Event mô tả một điều có ý nghĩa đã xảy ra bên trong domain model/bounded context. Integration Event là contract dùng để thông báo cho hệ thống hoặc bounded context khác.

```text
Inside bounded context:
Order aggregate
   ↓ Domain Event
Application handlers
   ↓
Integration mapping
   ↓ Integration Event
Service Bus / external consumers
```

Hai loại event có thể liên quan nhưng không nên mặc định là cùng một class.

## 2. Why does it exist?

Domain model cần express business consequences mà không coupling aggregate trực tiếp tới infrastructure. External consumers lại cần stable contract có lifecycle/versioning riêng.

Nếu publish domain object nội bộ trực tiếp ra broker, internal refactor có thể vô tình trở thành breaking integration change.

## 3. How does it work?

Aggregate phát domain event:

```csharp
public void MarkPaid()
{
    if (Status == OrderStatus.Paid)
        return;

    Status = OrderStatus.Paid;
    AddDomainEvent(new OrderPaidDomainEvent(Id));
}
```

Application handler có thể tạo integration event:

```csharp
public sealed record OrderPaidIntegrationEvent(
    Guid OrderId,
    DateTimeOffset PaidAt,
    int SchemaVersion);
```

Integration event thường được lưu Outbox để đảm bảo publish sau database commit.

## 4. Practical implementation

```csharp
public sealed class OrderPaidHandler
{
    public Task Handle(
        OrderPaidDomainEvent domainEvent,
        CancellationToken ct)
    {
        _outbox.Add(new OrderPaidIntegrationEvent(
            domainEvent.OrderId,
            _clock.UtcNow,
            SchemaVersion: 1));

        return Task.CompletedTask;
    }
}
```

Domain event có thể đổi theo internal model; integration event cần compatibility discipline.

## 5. Real production scenario

Commerce service có aggregate `Order`. Sau payment, domain cần update loyalty state nội bộ và analytics system ngoài service cũng cần biết order paid.

Một domain event có thể trigger internal handler. Integration event riêng được publish cho analytics. Khi aggregate refactor, analytics contract không bị thay đổi vô tình.

## 6. Failure scenario & troubleshooting

**Symptom** → một refactor rename property domain làm external consumer deserialization fail.

**Evidence** → broker payload dùng trực tiếp domain event type.

**Hypothesis** → internal model và public integration contract bị coupling.

**Diagnosis** → inspect event class ownership và versioning policy.

**Fix** → map domain event sang integration contract riêng.

**Verification** → consumer contract test + schema compatibility check.

## 7. Common mistakes

* Gọi mọi message là “Domain Event”.
* Publish entity/aggregate serialization ra broker.
* Dùng MediatR notification như durable integration delivery.
* Không version integration contract.
* Tưởng event-driven nghĩa là mọi action phải publish event.

## 8. Alternatives

Direct application service call đơn giản hơn cho logic cùng process. Synchronous API phù hợp khi caller cần immediate response. Integration event phù hợp asynchronous decoupling khi consistency delay chấp nhận được.

## 9. Trade-offs

### Advantages

* Tách internal business model khỏi external contracts.
* Giảm accidental coupling.
* Cho phép evolve bounded context độc lập hơn.

### Costs / Risks

* Mapping và duplicate models tăng.
* Eventual consistency phức tạp hơn.
* Cần ownership/versioning governance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event là “điều đã xảy ra”, không phải command disguised.

### Middle

Biết phát domain event và tạo integration DTO riêng.

### Senior

Thiết kế delivery, outbox, retries và compatibility.

### Technical Lead / Architect

Định nghĩa bounded-context contracts, event ownership và khi nào messaging thực sự đáng complexity.

## 11. Key takeaway

* Domain Event thuộc domain boundary; Integration Event thuộc integration boundary.
* Không publish internal model trực tiếp chỉ vì tiện.
* Stable external contract đáng giá hơn việc reuse một class.

# 6. HTTP Idempotency Key: làm POST retry-safe cho payment/order command mà không giả vờ mọi POST đều idempotent

## 1. What is it?

Idempotency Key là client-generated identifier gắn với một logical command để server nhận biết duplicate retry và trả lại outcome cũ thay vì thực hiện side effect lần nữa.

Mental model:

```text
POST /payments
Idempotency-Key: abc123
       ↓
server checks key
  ├─ unseen → execute + store result
  └─ seen   → return stored outcome
```

## 2. Why does it exist?

Network failure tạo ambiguity: client gửi request, server xử lý xong nhưng response bị mất. Client không biết payment đã xảy ra chưa.

Nếu retry POST bình thường, server có thể charge hai lần. Nếu không retry, user có thể thấy false failure.

Idempotency Key giải quyết duplicate command do retry/replay.

## 3. How does it work?

Server lưu mapping:

```text
(idempotency key, operation scope, request hash)
→ status/result
```

Nếu cùng key nhưng payload khác, server nên reject thay vì coi là cùng command.

Key scope cần rõ theo tenant/user/endpoint để tránh collision giữa contexts.

## 4. Practical implementation

Simplified persistence:

```sql
CREATE TABLE IdempotencyRequests
(
    TenantId UNIQUEIDENTIFIER NOT NULL,
    IdempotencyKey NVARCHAR(100) NOT NULL,
    RequestHash VARBINARY(32) NOT NULL,
    ResponseJson NVARCHAR(MAX) NULL,
    StatusCode INT NULL,
    CreatedAt DATETIME2 NOT NULL,
    CONSTRAINT PK_Idempotency PRIMARY KEY (TenantId, IdempotencyKey)
);
```

ASP.NET Core flow:

```csharp
var key = request.Headers["Idempotency-Key"].SingleOrDefault();
if (string.IsNullOrWhiteSpace(key))
    return Results.BadRequest();

var existing = await store.FindAsync(tenantId, key, ct);
if (existing is not null)
    return existing.ToHttpResult();

// claim key atomically, execute command, persist result
```

Production implementation phải xử lý concurrent duplicate requests atomically.

## 5. Real production scenario

Mobile client gọi `POST /orders`. Server create order thành công nhưng mobile network drop trước response. App retry cùng key.

Không idempotency → hai orders. Có key → server trả lại original order result.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate orders dù clients gửi same idempotency key.

**Evidence** → hai app instances cùng kiểm tra “key chưa tồn tại” rồi cùng execute.

**Hypothesis** → check-then-insert race.

**Diagnosis** → inspect DB uniqueness/transaction around key claim.

**Fix** → atomic insert/unique constraint hoặc transactional claim trước side effect.

**Verification** → concurrency test 50 identical requests cùng lúc.

## 7. Common mistakes

* Trust key uniqueness mà không có database constraint.
* Same key cho payload khác nhau.
* Không scope key theo tenant/operation.
* Cache-only idempotency khiến restart mất history.
* Retain keys mãi mãi không có policy.

## 8. Alternatives

PUT với resource ID client-chosen có natural idempotency trong nhiều cases. Unique business constraint đôi khi đủ. Message consumers dùng deduplication/inbox thay HTTP idempotency key.

## 9. Trade-offs

### Advantages

* Retry-safe cho critical POST commands.
* Giảm duplicate side effects từ network ambiguity.

### Costs / Risks

* Cần persistent state và cleanup.
* Concurrent claim phức tạp.
* Không tự giải quyết downstream duplicate side effect nếu boundary khác.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry có thể tạo duplicate side effect.

### Middle

Implement key validation và persistent uniqueness.

### Senior

Thiết kế race handling, request hash, retention và downstream idempotency.

### Technical Lead / Architect

Quyết định commands nào bắt buộc idempotency contract và standardize behavior across APIs.

## 11. Key takeaway

* Network timeout không cho biết server đã thực hiện command hay chưa.
* Idempotency Key biến retry thành explicit protocol.
* Atomic claim quan trọng hơn việc chỉ “lưu key”.

# 7. Azure Service Bus Dead-Letter Queue: poison message, retry budget và operational recovery workflow

## 1. What is it?

Dead-Letter Queue (DLQ) là nơi giữ messages không thể xử lý thành công theo normal flow.

Mental model:

```text
Queue
  ↓ delivery
Consumer
  ├─ complete → done
  ├─ transient failure → abandon/retry
  └─ permanent/retry exhausted → DLQ
```

DLQ không phải thùng rác. Nó là operational state cần ownership, telemetry và recovery process.

## 2. Why does it exist?

Một poison message có thể fail mãi vì schema invalid, business entity không tồn tại hoặc bug deterministic. Nếu queue retry vô hạn, message đó tiêu tốn throughput và gây retry storm.

DLQ tách messages không tiến triển được khỏi healthy flow.

## 3. How does it work?

Service Bus tăng delivery count khi message được redeliver. Khi vượt `MaxDeliveryCount`, message thường được dead-letter tự động.

Consumer cũng có thể chủ động dead-letter:

```csharp
await args.DeadLetterMessageAsync(
    args.Message,
    deadLetterReason: "UnsupportedSchema",
    deadLetterErrorDescription: "schemaVersion=7 is not supported");
```

Reason/description nên hỗ trợ diagnosis nhưng không leak secrets/PII.

## 4. Practical implementation

```csharp
processor.ProcessMessageAsync += async args =>
{
    try
    {
        var command = Deserialize(args.Message.Body);
        await handler.HandleAsync(command, args.CancellationToken);
        await args.CompleteMessageAsync(args.Message);
    }
    catch (UnsupportedSchemaException ex)
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            "UnsupportedSchema",
            ex.Message);
    }
    catch (TransientDependencyException)
    {
        await args.AbandonMessageAsync(args.Message);
    }
};
```

DLQ cần dashboard theo message count, age of oldest message và reason distribution.

## 5. Real production scenario

Order consumer nhận event schema mới mà version cũ không hiểu. Nếu throw generic exception, message retry nhiều lần rồi DLQ mà không reason hữu ích.

Team có alert `DLQ count > 0`, inspect reason, deploy compatibility fix rồi replay messages có kiểm soát.

## 6. Failure scenario & troubleshooting

**Symptom** → DLQ tăng liên tục sau release.

**Evidence** → reason chủ yếu `DeserializationFailed` và message schema version mới.

**Hypothesis** → backward compatibility break.

**Diagnosis** → compare producer payload schema và consumer deployed version.

**Fix** → support additive schema/version mapping; deploy fix trước replay.

**Verification** → replay sample messages, confirm DLQ stops growing and side effects remain idempotent.

## 7. Common mistakes

* Không monitor DLQ.
* Auto-replay toàn bộ DLQ mà chưa fix root cause.
* Retry permanent validation errors.
* Dead-letter mọi transient timeout ngay lần đầu.
* Replay message mà consumer không idempotent.

## 8. Alternatives

Separate quarantine storage có thể phù hợp với custom broker/workflow. Scheduled retry queue hữu ích cho long-delay retry. Nhưng Service Bus DLQ là built-in primitive cho failed delivery lifecycle.

## 9. Trade-offs

### Advantages

* Cô lập poison messages.
* Giữ evidence để điều tra/replay.
* Ngăn endless retry.

### Costs / Risks

* Cần runbook và ownership.
* Message retention không vô hạn.
* Replay có thể tạo duplicate side effects.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DLQ là failed-message holding area, không phải success path.

### Middle

Phân biệt transient vs permanent failure và set reason rõ.

### Senior

Thiết kế retry budget, idempotent replay và monitoring.

### Technical Lead / Architect

Định nghĩa operational ownership, alerting threshold và recovery workflow cho messaging platform.

## 11. Key takeaway

* DLQ là production workflow, không phải folder để quên.
* Fix root cause trước replay.
* Retry budget và idempotency phải được thiết kế cùng DLQ.

# 8. Optimizely CMS content modeling: Page Type vs Block Type và cách tránh content model coupling

## 1. What is it?

Trong Optimizely CMS, Page Type thường đại diện một content node có URL/hierarchy riêng; Block Type đại diện reusable content component có thể được compose vào pages hoặc content areas.

Mental model:

```text
Site tree
  └─ Page
      ├─ page-specific properties
      └─ ContentArea
          ├─ Hero Block
          ├─ Promo Block
          └─ CTA Block
```

Content model là editor-facing domain model, không chỉ class structure.

## 2. Why does it exist?

Nếu mọi nội dung được hard-code thành properties trên HomePage, developer phải deploy code cho mỗi thay đổi layout/content variation. Nếu mọi thứ lại thành generic block, editor experience trở nên khó hiểu và validation yếu.

Page/Block separation tồn tại để cân bằng navigation semantics, reuse và editorial flexibility.

## 3. How does it work?

Một page type định nghĩa page-level intent:

```csharp
[ContentType(
    DisplayName = "Landing Page",
    GUID = "11111111-1111-1111-1111-111111111111")]
public class LandingPage : PageData
{
    public virtual string Heading { get; set; } = string.Empty;
    public virtual ContentArea MainContent { get; set; } = null!;
}
```

Reusable block:

```csharp
[ContentType(
    DisplayName = "Hero Block",
    GUID = "22222222-2222-2222-2222-222222222222")]
public class HeroBlock : BlockData
{
    public virtual string Title { get; set; } = string.Empty;
    public virtual ContentReference Image { get; set; } = null!;
}
```

Rendering layer map content type tới component/view tương ứng.

## 4. Practical implementation

Good content modeling hỏi trước:

* Editor có cần reuse component này ở nhiều pages không?
* Nó có URL/SEO lifecycle riêng không?
* Validation/invariants thuộc page hay component?
* Một thay đổi design có làm content migration lớn không?

Ví dụ CTA nên là block nếu được reuse và independent config. Page title, canonical metadata hoặc page-level navigation semantics nên ở page.

## 5. Real production scenario

Marketing website bắt đầu với HomePage có 25 hard-coded properties: hero, cards, promotions, testimonial, CTA. Sau vài tháng, team muốn reuse testimonial trên product pages.

Model cũ buộc duplicate properties/rendering. Chuyển reusable sections sang blocks giúp editors compose mà không duplicate code/content.

## 6. Failure scenario & troubleshooting

**Symptom** → editors có hàng chục block types gần giống nhau và không biết chọn cái nào.

**Evidence** → mỗi campaign tạo một block type mới chỉ khác vài style options.

**Hypothesis** → content model đang mirror design variations quá chi tiết.

**Diagnosis** → review business semantics vs presentation-only differences.

**Fix** → consolidate blocks theo content intent, dùng controlled variants thay duplicate types.

**Verification** → editor usability test + content migration rehearsal.

## 7. Common mistakes

* Dùng page type cho reusable fragments.
* Tạo generic “everything block” với quá nhiều optional fields.
* Coupling content model trực tiếp tới CSS layout hiện tại.
* Đổi GUID/content type identity tùy tiện trong upgrade.
* Chỉ hỏi developer, không validate editorial workflow.

## 8. Alternatives

Headless CMS tách delivery/rendering mạnh hơn nhưng content modeling principles vẫn giống. Traditional MVC-rendered Optimizely đơn giản hơn nếu frontend cùng .NET stack và không cần đa-channel delivery.

## 9. Trade-offs

### Advantages

* Blocks tăng reuse và editorial composition.
* Pages giữ navigation/SEO semantics rõ.

### Costs / Risks

* Quá nhiều blocks làm editor UX phức tạp.
* Quá generic làm validation yếu.
* Content model change có migration cost lâu dài.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Page là navigable content, Block là reusable component.

### Middle

Implement content types, rendering và validation hợp lý.

### Senior

Thiết kế content model theo editorial workflow, reuse và upgrade impact.

### Technical Lead / Architect

Quyết định traditional/headless/composable boundary và governance cho content schema evolution.

## 11. Key takeaway

* Content model là long-lived contract với editors và stored content.
* Page vs Block nên dựa trên semantics/reuse, không chỉ UI layout.
* Tránh cả hai cực: page quá cứng và block quá generic.

# 9. Database migration compatibility testing: expand/contract để deploy database mà không khóa release train

## 1. What is it?

Expand/contract là deployment technique cho schema changes theo nhiều bước backward-compatible thay vì đổi schema và application contract cùng lúc.

Mental model:

```text
1. Expand schema
2. Deploy code compatible old + new
3. Backfill/migrate data
4. Switch reads/writes
5. Contract old schema later
```

Mục tiêu là cho old và new application versions coexist trong rolling/blue-green deployment.

## 2. Why does it exist?

Trong production, deploy không xảy ra atomically. Có thể vài instances chạy version cũ trong khi vài instances chạy version mới.

Nếu migration rename/drop column trước khi old instances dừng, chúng có thể crash ngay giữa rollout.

## 3. How does it work?

Ví dụ muốn rename `Customer.Name` → `DisplayName`.

Bad migration:

```sql
EXEC sp_rename 'Customers.Name', 'DisplayName', 'COLUMN';
```

Safer progression:

```text
Release A: add nullable DisplayName
Release B: dual-write Name + DisplayName
Backfill historical rows
Release C: read DisplayName, fallback Name
Release D: stop using Name
Release E: drop Name
```

Mỗi step có rollback story riêng.

## 4. Practical implementation

Migration:

```csharp
migrationBuilder.AddColumn<string>(
    name: "DisplayName",
    table: "Customers",
    type: "nvarchar(200)",
    nullable: true);
```

Compatibility integration test nên chạy:

```text
old app ↔ new schema
new app ↔ expanded schema
```

Không chỉ test “new app + new schema”.

## 5. Real production scenario

App Service deployment slot swap có vài phút old/new instances coexist. Team drop column trong migration trước app deploy. Old instances tiếp tục query column cũ và tạo 500s trong rollout.

Expand/contract tách destructive change sang release sau khi old code đã biến mất.

## 6. Failure scenario & troubleshooting

**Symptom** → 500 chỉ trong thời gian deployment, sau đó tự hết.

**Evidence** → old app version logs SQL “invalid column name”.

**Hypothesis** → schema change không backward-compatible với rolling deployment.

**Diagnosis** → map deployment order, instance versions và migration timing.

**Fix** → expand-first migration + compatibility window.

**Verification** → deploy rehearsal với mixed versions và smoke tests.

## 7. Common mistakes

* Rename/drop column trong cùng release với code change.
* Migration chạy tự động từ every app instance startup.
* Long blocking migration trong peak traffic.
* Không test rollback.
* Backfill hàng triệu rows trong one transaction.

## 8. Alternatives

Maintenance window + synchronized downtime có thể đơn giản và hợp lý với low-availability internal systems. Feature flags hoặc database views đôi khi bridge compatibility. Không phải hệ thống nào cũng cần zero-downtime migration complexity.

## 9. Trade-offs

### Advantages

* Hỗ trợ rolling/blue-green deploy.
* Giảm coupling giữa schema và app release.
* Rollback an toàn hơn.

### Costs / Risks

* Nhiều release steps.
* Temporary duplicate columns/logic.
* Backfill cần monitoring.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu app và DB versions có thể coexist trong deploy.

### Middle

Viết non-destructive migrations và compatibility tests.

### Senior

Thiết kế backfill, rollback, lock impact và migration sequencing.

### Technical Lead / Architect

Chọn deployment compatibility policy dựa trên availability requirement và release topology.

## 11. Key takeaway

* Database migration là release-engineering problem, không chỉ EF command.
* Expand trước, contract sau giúp mixed versions coexist.
* Zero-downtime có complexity cost; chỉ dùng mức cần thiết.

# 10. TypeScript discriminated unions cho API state: loại bỏ “boolean soup” và làm UI failure states explicit

## 1. What is it?

Discriminated union là TypeScript type pattern dùng một field literal làm discriminator để biểu diễn các trạng thái loại trừ lẫn nhau.

Bad state model:

```ts
{
  loading: boolean;
  hasError: boolean;
  data?: Product;
  error?: string;
}
```

Nó cho phép trạng thái vô nghĩa như `loading=true`, `hasError=true`, `data` cũng tồn tại.

Discriminated union:

```ts
type ProductState =
  | { kind: "idle" }
  | { kind: "loading" }
  | { kind: "loaded"; data: Product }
  | { kind: "error"; error: ApiProblem };
```

## 2. Why does it exist?

UI async state là state machine. Nếu biểu diễn bằng nhiều booleans độc lập, combinations hợp lệ/không hợp lệ tăng nhanh và runtime bugs xuất hiện.

Type system có thể encode invariant: loaded state bắt buộc có data; error state bắt buộc có error.

## 3. How does it work?

TypeScript narrow type dựa trên discriminator:

```ts
function render(state: ProductState) {
  switch (state.kind) {
    case "loading":
      return "Loading...";
    case "loaded":
      return state.data.name;
    case "error":
      return state.error.title;
    default:
      return "";
  }
}
```

Compiler giúp ngăn truy cập `data` khi state không phải `loaded`.

## 4. Practical implementation

API error contract từ ASP.NET Core có thể map trực tiếp:

```ts
type ApiProblem = {
  type: string;
  title: string;
  status: number;
  traceId?: string;
};

type SaveState =
  | { kind: "idle" }
  | { kind: "saving" }
  | { kind: "saved"; id: string }
  | { kind: "validation-error"; problem: ApiProblem }
  | { kind: "conflict"; problem: ApiProblem }
  | { kind: "failed"; problem: ApiProblem };
```

Frontend behavior trở nên explicit cho 400/409/500 thay vì một generic boolean `hasError`.

## 5. Real production scenario

Order-edit UI có optimistic concurrency. Backend trả 409 khi record stale. UI cũ chỉ có `isLoading` + `errorMessage`, nên 409 bị hiển thị như generic failure.

Với discriminated union, `conflict` là state riêng; UI có thể đưa action “Reload latest version” thay vì “Try again”.

## 6. Failure scenario & troubleshooting

**Symptom** → spinner không biến mất sau một error path.

**Evidence** → code set `hasError=true` nhưng quên `loading=false`.

**Hypothesis** → state model cho phép inconsistent boolean combination.

**Diagnosis** → inspect transitions thay vì chỉ component rendering.

**Fix** → dùng single discriminated state và explicit transitions.

**Verification** → unit test state reducer cho success/error/conflict/cancel paths.

## 7. Common mistakes

* Dùng quá nhiều booleans cho mutually exclusive states.
* Union có discriminator nhưng vẫn thêm optional fields khắp nơi.
* Cast `as` để bypass compiler khi state design sai.
* Không map backend error semantics rõ ràng.
* Dùng one generic `error` state cho mọi recoverable condition.

## 8. Alternatives

State machine libraries như XState hữu ích cho flow phức tạp nhiều transitions. Vue/React local state + discriminated union đủ cho phần lớn API request states. Redux reducer cũng có thể encode cùng pattern.

## 9. Trade-offs

### Advantages

* Invalid states khó biểu diễn.
* Compiler hỗ trợ exhaustive handling.
* UI behavior rõ hơn.

### Costs / Risks

* Nhiều state variants hơn.
* Flow đơn giản có thể không cần formal modeling.
* Over-modeling làm component verbose.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async UI có các trạng thái khác nhau, không chỉ loading true/false.

### Middle

Dùng discriminated unions và exhaustive switches.

### Senior

Map backend semantics như validation/conflict/retryable failure vào UI state đúng.

### Technical Lead / Architect

Chuẩn hóa frontend state/error contracts giữa API và UI mà không introduce state-management framework nặng khi chưa cần.

## 11. Key takeaway

* Async UI là state machine dù code có gọi tên như vậy hay không.
* Discriminated unions giúp type system loại invalid state combinations.
* Frontend error state nên phản ánh semantics từ API, không chỉ một chuỗi lỗi generic.
