# 1. C# `IAsyncDisposable` và `await using`: giải phóng asynchronous resources mà không kéo sync-over-async vào cleanup path

## 1. What is it?

`IAsyncDisposable` là contract cho resource có cleanup cần asynchronous I/O. Thay vì chỉ có `Dispose()`, object cung cấp `DisposeAsync()` và caller dùng `await using`.

```csharp
await using var session = await OpenSessionAsync(ct);
await session.ProcessAsync(ct);
```

Mental model:

```text
Acquire async resource
      ↓
use resource
      ↓
DisposeAsync()
      ↓
flush / close / send / commit async cleanup
```

Nó phù hợp khi cleanup có thể phải flush network stream, complete asynchronous writer, hoặc release resource qua async protocol.

## 2. Why does it exist?

Một synchronous `Dispose()` không thể `await`. Nếu cleanup thực sự cần I/O, implementation dễ rơi vào `.GetAwaiter().GetResult()` hoặc `.Result`, kéo blocking vào path vốn đang async. Dưới tải cao, cleanup blocking có thể góp phần vào ThreadPool starvation hoặc kéo dài request latency.

## 3. How does it work?

Interface tối thiểu:

```csharp
public interface IAsyncDisposable
{
    ValueTask DisposeAsync();
}
```

Compiler biến `await using` thành `try/finally` và `await` cleanup trong `finally`.

```csharp
await using (var resource = await factory.CreateAsync(ct))
{
    await resource.RunAsync(ct);
}
```

Điểm quan trọng: disposal vẫn chạy khi body ném exception. Vì vậy cleanup phải được thiết kế sao cho không che mất root exception một cách vô tình.

## 4. Practical implementation

Một resource vừa sở hữu managed async resource vừa có state riêng:

```csharp
public sealed class ExportSession : IAsyncDisposable
{
    private readonly Stream _stream;
    private bool _disposed;

    public ExportSession(Stream stream) => _stream = stream;

    public async ValueTask DisposeAsync()
    {
        if (_disposed) return;
        _disposed = true;

        await _stream.FlushAsync();
        await _stream.DisposeAsync();
    }
}
```

Nếu class hỗ trợ cả `IDisposable` và `IAsyncDisposable`, phải định nghĩa rõ semantics của hai paths thay vì để synchronous dispose gọi async code bằng blocking tùy tiện.

## 5. Real production scenario

Một service generate file lớn lên cloud-backed stream. Version đầu gọi synchronous `Dispose()` sau khi write. Underlying wrapper phải flush dữ liệu ra network và block thread cho tới khi hoàn tất. Khi nhiều exports kết thúc cùng lúc, request completion time tăng mạnh dù CPU thấp. Chuyển resource lifetime sang `await using` giữ cleanup trên asynchronous path và giảm blocked worker threads.

## 6. Failure scenario & troubleshooting

**Symptom** → request đã xử lý xong business logic nhưng latency vẫn treo ở cuối request.

**Evidence** → trace/profiler cho thấy nhiều thread nằm ở synchronous `Dispose()` hoặc `.GetResult()` trong cleanup.

**Hypothesis** → async-capable resource bị dispose synchronously.

**Diagnosis** → inspect ownership chain, wrappers và nơi resource được tạo/dispose; kiểm tra resource có implement `IAsyncDisposable` không.

**Fix** → propagate asynchronous lifetime tới owner phù hợp, dùng `await using`, tránh sync-over-async.

**Verification** → load test concurrent cleanup, theo dõi blocked threads, p95/p99 latency và resource leak counters.

## 7. Common mistakes

* Dùng `await using` nhưng resource thực tế không cần async cleanup, tăng complexity không cần thiết.
* Dispose cùng resource từ nhiều owners.
* Ném exception mới trong `DisposeAsync()` làm mất exception gốc.
* Quên disposal khi factory trả resource sau nhiều branches.
* Cho object sống lâu hơn scope cần thiết chỉ vì cleanup là async.

## 8. Alternatives

`IDisposable` vẫn đúng cho memory-only/unmanaged-handle cleanup nhanh và synchronous. Explicit lifecycle method như `CompleteAsync()` phù hợp khi “complete operation” là business action chứ không phải resource cleanup. Dependency injection container có thể quản lý lifetime cho service-owned resources, nhưng ownership vẫn cần rõ.

## 9. Trade-offs

### Advantages

* Không block thread cho async cleanup.
* Lifetime rõ ràng bằng language construct.
* Cleanup vẫn chạy qua exception path.

### Costs / Risks

* API surface phức tạp hơn.
* Caller phải async all the way tới lifetime owner.
* Cleanup exception semantics cần policy rõ ràng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `using` và resource ownership trước khi dùng `await using`.

### Middle

Biết khi nào resource cần `IAsyncDisposable` và propagate async cleanup.

### Senior

Phân tích disposal latency, exception precedence và mixed sync/async lifetime.

### Technical Lead / Architect

Định nghĩa resource-lifetime conventions để libraries không ép application vào sync-over-async cleanup.

## 11. Key takeaway

* `IAsyncDisposable` giải quyết asynchronous cleanup, không thay thế `IDisposable` một cách máy móc.
* Resource owner phải chịu trách nhiệm dispose đúng path.
* Cleanup cũng là một phần của latency và reliability budget.

# 2. ASP.NET Core Forwarded Headers: scheme, host, client IP và trust boundary khi chạy sau reverse proxy

## 1. What is it?

Khi ASP.NET Core chạy sau IIS, Nginx, ingress, load balancer hoặc CDN, application thường không trực tiếp thấy request gốc từ browser. Proxy có thể chuyển thông tin gốc qua các headers như `X-Forwarded-For` và `X-Forwarded-Proto`.

```text
Browser HTTPS
   ↓
Load balancer
   ↓ HTTP nội bộ
ASP.NET Core
```

Không xử lý forwarded headers đúng có thể khiến app tưởng request là HTTP, thấy sai client IP hoặc generate redirect/callback URL sai.

## 2. Why does it exist?

Proxy termination thay đổi connection-level facts. App cần biết scheme/client address bên ngoài để:

* redirect HTTPS đúng;
* tạo absolute URL;
* OAuth/OIDC callback đúng scheme;
* audit/rate-limit theo client hợp lý;
* không ghi log toàn bộ users như cùng IP của proxy.

Nhưng tin headers từ bất kỳ client nào lại tạo spoofing risk.

## 3. How does it work?

Forwarded Headers Middleware đọc headers từ proxy được tin cậy rồi cập nhật `HttpContext.Request.Scheme`, `RemoteIpAddress` và các giá trị liên quan.

```csharp
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders =
        ForwardedHeaders.XForwardedFor |
        ForwardedHeaders.XForwardedProto;
});
```

Trong production, `KnownProxies`/`KnownNetworks` và proxy chain phải phản ánh topology thật. Trust boundary quan trọng hơn việc “bật middleware”.

## 4. Practical implementation

Middleware phải nằm đủ sớm trước logic phụ thuộc scheme/IP:

```csharp
app.UseForwardedHeaders();
app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
```

Nếu có nhiều proxy hops, cần hiểu proxy nào append/overwrite header và `ForwardLimit` phù hợp. Không mở trust vô hạn chỉ để sửa nhanh redirect loop.

## 5. Real production scenario

Một API sau Azure/Application Gateway terminate TLS ở edge rồi forward HTTP nội bộ. App không dùng forwarded headers nên OIDC redirect URI được generate thành `http://...`. Identity provider từ chối callback hoặc browser rơi vào HTTPS redirect loop. Local dev không tái hiện vì Kestrel chạy HTTPS trực tiếp.

## 6. Failure scenario & troubleshooting

**Symptom** → infinite redirect HTTPS, callback URI sai scheme hoặc logs ghi client IP là load balancer.

**Evidence** → raw inbound headers có forwarded values đúng nhưng `Request.Scheme`/`RemoteIpAddress` trong app sai.

**Hypothesis** → middleware thiếu, sai thứ tự hoặc proxy không được trust.

**Diagnosis** → trace request qua từng hop, ghi sanitized scheme/host/remote IP trước và sau middleware, kiểm tra network topology.

**Fix** → cấu hình đúng known proxy/network, forwarded header set và middleware order.

**Verification** → test qua chính reverse-proxy path production-like, không chỉ gọi Kestrel trực tiếp.

## 7. Common mistakes

* Trust `X-Forwarded-For` từ Internet trực tiếp.
* Clear toàn bộ known networks để “cho chạy được” mà không đánh giá spoofing.
* Đặt middleware sau HTTPS redirection/authentication.
* Giả định chỉ có một proxy hop.
* Dùng client IP làm identity hoặc authorization factor.

## 8. Alternatives

Standard `Forwarded` header có thể được infrastructure hỗ trợ. Một số hosting integration tự cấu hình proxy semantics. Với security enforcement, identity/token claims tốt hơn IP; IP chỉ nên là tín hiệu phụ cho logging/rate limiting khi phù hợp.

## 9. Trade-offs

### Advantages

* App hiểu đúng external request context.
* Fix absolute URL, redirect và audit semantics.

### Costs / Risks

* Sai trust boundary tạo header spoofing.
* Multi-proxy topology khó debug.
* Infrastructure change có thể làm assumptions cũ sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu reverse proxy làm thay đổi request context.

### Middle

Biết middleware ordering và forwarded header configuration.

### Senior

Thiết kế trusted proxy chain, audit client IP semantics và test deployment topology.

### Technical Lead / Architect

Chuẩn hóa edge/proxy contract để app teams không tự cấu hình header trust theo cảm tính.

## 11. Key takeaway

* Forwarded headers là vấn đề trust boundary, không chỉ configuration.
* Scheme/IP chỉ đáng tin khi đến từ proxy chain được xác định rõ.
* Phải test qua đường đi thật của traffic.

# 3. EF Core `SaveChangesInterceptor`: audit, cross-cutting persistence behavior và ranh giới với domain logic

## 1. What is it?

EF Core interceptors cho phép quan sát hoặc can thiệp vào lifecycle của database operations. `SaveChangesInterceptor` hữu ích cho persistence-level cross-cutting concerns như audit metadata, diagnostics hoặc outbox preparation.

Nó không phải nơi phù hợp để nhét mọi business rule vì interceptor chạy ở persistence boundary, xa intent của use case.

## 2. Why does it exist?

Nhiều entities cần cùng behavior:

```text
CreatedAt
UpdatedAt
ChangedBy
correlation metadata
```

Nếu mỗi command handler tự set các fields này, logic lặp lại và dễ quên. Interceptor có thể centralize behavior gắn trực tiếp với persistence lifecycle.

## 3. How does it work?

Interceptor nhận callbacks trước/sau `SaveChanges`:

```csharp
public sealed class AuditInterceptor : SaveChangesInterceptor
{
    public override InterceptionResult<int> SavingChanges(
        DbContextEventData eventData,
        InterceptionResult<int> result)
    {
        ApplyAudit(eventData.Context);
        return result;
    }
}
```

Async applications nên override async path khi cần async dependency. Tuy nhiên external I/O trong `SavingChanges` thường là smell vì kéo remote dependency vào transaction-sensitive path.

## 4. Practical implementation

Ví dụ set timestamps cho tracked auditable entities:

```csharp
private static void ApplyAudit(DbContext? db)
{
    if (db is null) return;

    var now = DateTimeOffset.UtcNow;

    foreach (var entry in db.ChangeTracker.Entries<IAuditable>())
    {
        if (entry.State == EntityState.Added)
            entry.Entity.CreatedAt = now;

        if (entry.State is EntityState.Added or EntityState.Modified)
            entry.Entity.UpdatedAt = now;
    }
}
```

User identity nên đi qua scoped abstraction rõ ràng, không để persistence layer đọc trực tiếp global/static request context.

## 5. Real production scenario

Một hệ thống có hàng chục command handlers. Một số developer quên update `UpdatedAt`, khiến incremental sync dựa vào timestamp bỏ sót records. Centralizing mechanical audit stamping trong interceptor loại bỏ class bug này, trong khi business events vẫn được tạo ở aggregate/application layer.

## 6. Failure scenario & troubleshooting

**Symptom** → một update chạy đúng nhưng audit fields hoặc outbox rows không xuất hiện.

**Evidence** → operation dùng `ExecuteUpdate`, raw SQL hoặc bulk library nên không đi qua normal tracked `SaveChanges` pipeline.

**Hypothesis** → team giả định interceptor bao phủ mọi database mutation.

**Diagnosis** → inventory write paths và xác định path nào bypass Change Tracker/interceptors.

**Fix** → policy rõ cho bulk/raw writes, audit ở database/application layer thích hợp, hoặc cấm bypass với use case cần invariant đó.

**Verification** → integration tests cho từng mutation path, không chỉ repository chuẩn.

## 7. Common mistakes

* Đặt pricing/authorization/business validation trong interceptor.
* Gọi external API trong `SavingChanges`.
* Giả định bulk updates đi qua interceptor giống tracked entities.
* Swallow exception ở post-save callback.
* Interceptor phụ thuộc ambient state khó test.

## 8. Alternatives

Override `DbContext.SaveChanges` đơn giản hơn với codebase nhỏ. Domain events phù hợp business-significant changes. Database triggers phù hợp invariant/audit phải áp dụng cho mọi writers, nhưng làm behavior xa application code và khó test hơn.

## 9. Trade-offs

### Advantages

* Centralize persistence cross-cutting behavior.
* Giảm duplication và omission bugs.
* Reusable giữa nhiều DbContext configurations.

### Costs / Risks

* Behavior trở nên implicit.
* Bypass paths tạo inconsistency.
* Interceptor quá mạnh dễ thành “hidden business layer”.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Change Tracker và `SaveChanges` lifecycle.

### Middle

Dùng interceptor cho mechanical persistence concerns.

### Senior

Phân biệt persistence concern với domain invariant và kiểm soát bypass paths.

### Technical Lead / Architect

Định nghĩa write-path governance, audit guarantees và nơi business behavior được phép tồn tại.

## 11. Key takeaway

* Interceptor phù hợp cross-cutting persistence behavior, không phải business-rule dumping ground.
* Hãy liệt kê mọi path bypass `SaveChanges`.
* Behavior càng implicit càng cần integration tests và conventions rõ.

# 4. SQL Server Query Store: bắt plan regression và sửa performance bằng evidence thay vì đoán index

## 1. What is it?

Query Store lưu lịch sử query text, execution plans và runtime statistics theo thời gian. Nó cho phép trả lời câu hỏi quan trọng:

```text
Query nào chậm hơn?
Từ lúc nào?
Plan nào thay đổi?
Plan cũ có tốt hơn không?
```

Đây là công cụ đặc biệt hữu ích cho performance regression sau deploy, statistics change hoặc data distribution shift.

## 2. Why does it exist?

Execution plan cache là trạng thái hiện tại và có thể bị evict/recompile. Khi incident xảy ra lúc 2 giờ sáng nhưng đến sáng plan đã khác, chỉ nhìn current plan có thể mất evidence. Query Store giữ timeline để so sánh trước/sau.

## 3. How does it work?

Query Store capture query/plan/runtime metrics và aggregate theo intervals. Một query có thể có nhiều plan IDs với duration/CPU/reads khác nhau.

Mental model:

```text
Query A
 ├─ Plan 17 → p50 20 ms
 └─ Plan 42 → p50 1.8 s  ← regression
```

DBA có thể investigate, và trong tình huống phù hợp có thể force known-good plan như mitigation trong khi tìm root cause.

## 4. Practical implementation

Workflow troubleshooting:

1. Xác định time window incident.
2. Tìm top regressed queries theo duration/CPU/logical reads.
3. So sánh plans trước/sau.
4. Kiểm tra estimated vs actual rows, index access, joins, memory grant.
5. Xác định trigger: statistics, parameter/data skew, schema/index change.
6. Mitigate rồi verify bằng runtime metrics.

Không tạo index chỉ vì missing-index suggestion xuất hiện; suggestion không hiểu toàn bộ write/storage/index portfolio.

## 5. Real production scenario

Một report query vốn chạy 200 ms đột ngột lên 8 giây sau đợt data load lớn. Query Store cho thấy plan đổi từ seek + hash aggregate sang nested loops với cardinality estimate thấp. Team force plan cũ tạm thời để phục hồi SLO, sau đó sửa statistics/index/query shape và bỏ force sau validation.

## 6. Failure scenario & troubleshooting

**Symptom** → API database latency tăng sau deploy nhưng code diff không chạm query đó.

**Evidence** → Query Store ghi plan mới xuất hiện cùng thời điểm regression.

**Hypothesis** → plan regression do compile context/data distribution chứ không phải application logic.

**Diagnosis** → compare plans và runtime stats, xem waits, row estimates, parameters khi có evidence phù hợp.

**Fix** → sửa root cause; plan forcing chỉ nên là controlled mitigation nếu plan cũ vẫn semantically/performance-safe.

**Verification** → theo dõi nhiều workload intervals và parameter patterns, không chỉ chạy một query bằng SSMS.

## 7. Common mistakes

* Clear plan cache như phản xạ đầu tiên và xóa evidence.
* Force plan vĩnh viễn rồi quên data/schema thay đổi.
* Chỉ nhìn average duration, bỏ p95/workload distribution.
* Thêm mọi index recommendation.
* Test query với parameter khác production rồi kết luận plan tốt.

## 8. Alternatives

Extended Events phù hợp event-level diagnostics. DMVs hữu ích current/recent runtime state nhưng không thay lịch sử Query Store. Application tracing giúp map SQL latency về user request; tốt nhất là correlate cả application và database evidence.

## 9. Trade-offs

### Advantages

* Có lịch sử plan/runtime.
* Điều tra regression nhanh hơn.
* Có controlled mitigation bằng plan forcing khi phù hợp.

### Costs / Risks

* Có storage/collection overhead.
* Retention/capture policy cần quản lý.
* Force plan có thể trở thành technical debt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết slow query phải có plan/evidence trước khi sửa.

### Middle

Đọc Query Store regression và compare plans.

### Senior

Liên kết plan change với cardinality, waits, parameters và data evolution.

### Technical Lead / Architect

Thiết lập performance regression workflow, baselines và ownership giữa app/DB teams.

## 11. Key takeaway

* Query Store biến “database tự nhiên chậm” thành một timeline có evidence.
* Plan forcing là mitigation, không mặc định là root fix.
* Tối ưu production query phải dựa trên workload thật.

# 5. MongoDB read concern + write concern: consistency, durability và replica lag trong production

## 1. What is it?

MongoDB `writeConcern` quy định mức acknowledgment/durability mà write yêu cầu. `readConcern` quy định loại consistency/isolation mà read mong muốn.

Hai knobs này giúp trả lời:

```text
Write được xem là thành công khi nào?
Read được phép thấy loại dữ liệu nào?
```

Chúng không phải “set càng mạnh càng tốt”; mức mạnh hơn có latency/availability cost.

## 2. Why does it exist?

Replica set có primary và secondaries. Replication không tức thời. Một write được primary nhận chưa đồng nghĩa mọi replica đã có dữ liệu. Nếu application đọc từ secondary ngay sau write, có thể gặp stale read tùy read preference/concern và replication lag.

## 3. How does it work?

Ví dụ majority write:

```text
Client → Primary writes
           ↓ replicate
        Secondary A
        Secondary B
           ↓
majority acknowledgment
```

`writeConcern: "majority"` tăng confidence write đã được replicated đủ để chịu một số failover cases. `readConcern: "majority"` giúp tránh đọc dữ liệu chưa majority-committed trong semantics tương ứng.

## 4. Practical implementation

Configuration phải dựa trên business semantics:

* shopping catalog có thể chịu stale read ngắn;
* balance/permission/security state thường cần consistency mạnh hơn;
* analytics có thể chọn eventual behavior để giảm latency.

Đừng thay đổi concern per query tùy hứng. Define defaults theo workload class và đo replication lag.

## 5. Real production scenario

User cập nhật profile rồi request tiếp theo đọc từ nearest secondary. UI thỉnh thoảng hiển thị value cũ trong vài giây. Team tưởng cache stale, nhưng trace cho thấy request thứ hai đi vào secondary đang lag. Root cause là read preference/consistency contract không phù hợp read-after-write expectation.

## 6. Failure scenario & troubleshooting

**Symptom** → API trả dữ liệu cũ ngay sau successful update.

**Evidence** → write đi primary, read đi secondary; replication lag spike trong cùng window.

**Hypothesis** → read-your-writes expectation không được consistency configuration bảo đảm.

**Diagnosis** → log operation timestamp/correlation, server selection, read preference và replica lag metrics.

**Fix** → route critical read về primary hoặc chọn consistency/read concern phù hợp; giảm lag root cause nếu bất thường.

**Verification** → failover + lag tests với exact read-after-write workflow.

## 7. Common mistakes

* Nghĩ `acknowledged` đồng nghĩa durable trên majority replicas.
* Dùng secondary reads cho mọi endpoint để “scale read”.
* Không định nghĩa stale-data tolerance.
* Tăng consistency mà không đo latency/availability cost.
* Confuse transaction isolation với replica freshness.

## 8. Alternatives

Relational primary-replica systems có trade-offs tương tự. Application-level version tokens có thể phát hiện stale state. Cache-aside cần consistency contract riêng và không chữa replica lag semantics.

## 9. Trade-offs

### Advantages của stronger guarantees

* Giảm ambiguous states sau failover.
* Phù hợp workflows nhạy cảm consistency.

### Costs / Risks

* Tăng latency.
* Có thể giảm availability khi đủ replicas không reachable.
* Secondary scaling benefits bị giới hạn nếu reads phải về primary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu replication có lag.

### Middle

Biết read/write concern và read preference là các concepts khác nhau.

### Senior

Map consistency level về business workflow, failover và latency budget.

### Technical Lead / Architect

Định nghĩa consistency classes cho platform thay vì để từng repository tự chọn.

## 11. Key takeaway

* Consistency là product/business contract trước khi là database option.
* Secondary read không mặc định có read-after-write guarantee.
* Test cả failover và replication lag, không chỉ happy path.

# 6. API idempotency keys: làm POST retry-safe mà không biến duplicate request thành duplicate side effect

## 1. What is it?

Idempotency key là client-generated unique key đại diện cho một logical operation. Server nhớ kết quả của key đó để request retry không tạo side effect lần hai.

```text
POST /payments
Idempotency-Key: abc-123

attempt 1 → payment created
network timeout
attempt 2 → return same logical result
```

Đây là pattern quan trọng cho payment, order creation, provisioning và bất kỳ operation nào client có lý do hợp lệ để retry sau timeout không rõ kết quả.

## 2. Why does it exist?

Timeout tạo ambiguity:

```text
Client không nhận response
     ≠
Server chưa thực hiện operation
```

Nếu client retry POST bình thường, server có thể tạo order/payment thứ hai. “Không retry POST” cũng không giải quyết UX/reliability khi network fail.

## 3. How does it work?

Server lưu record theo `(scope, idempotencyKey)` gồm request fingerprint/status/result reference. First request atomically claim key. Duplicate cùng payload nhận lại kết quả hoặc trạng thái đang xử lý. Cùng key nhưng payload khác phải bị reject.

```text
key K + payload hash H1 → accepted
key K + payload hash H1 → replay result
key K + payload hash H2 → conflict/error
```

## 4. Practical implementation

Table đơn giản:

```sql
CREATE TABLE IdempotencyRequests (
    IdempotencyKey nvarchar(100) NOT NULL,
    Scope nvarchar(100) NOT NULL,
    RequestHash varbinary(32) NOT NULL,
    ResourceId uniqueidentifier NULL,
    Status varchar(20) NOT NULL,
    CreatedAt datetime2 NOT NULL,
    CONSTRAINT PK_Idempotency PRIMARY KEY (Scope, IdempotencyKey)
);
```

Unique constraint là phần correctness quan trọng; check-then-insert không atomic có race condition.

## 5. Real production scenario

Mobile client submit order khi mạng chập chờn. Server tạo order thành công nhưng response mất. App retry sau 2 giây. Trước idempotency, customer có hai orders. Sau idempotency key scoped theo account + create-order operation, retry trả lại cùng `OrderId`.

## 6. Failure scenario & troubleshooting

**Symptom** → vẫn xuất hiện duplicate resources dù client gửi cùng key.

**Evidence** → hai app instances cùng thấy “key chưa tồn tại” rồi cùng execute side effect.

**Hypothesis** → idempotency implementation dùng non-atomic cache/check.

**Diagnosis** → inspect uniqueness constraint/transaction, timing và side-effect boundary.

**Fix** → atomic claim key, persist state cùng transaction khi có thể, hoặc workflow/outbox cho external side effects.

**Verification** → concurrency test hàng chục identical requests cùng millisecond và network-failure injection sau commit trước response.

## 7. Common mistakes

* Chỉ lưu key trong per-instance memory cache.
* Không bind key với request fingerprint.
* Expire key quá sớm so với retry window.
* Dùng idempotency key như authentication token.
* Retry external payment/provider mà provider-side idempotency chưa được thiết kế.

## 8. Alternatives

PUT với client-known resource ID tự nhiên idempotent cho một số resource creation flows. Unique business constraint như external order number cũng có thể chống duplicate. Messaging consumers thường dùng inbox/deduplication pattern tương tự.

## 9. Trade-offs

### Advantages

* Retry-safe user operations.
* Giảm duplicate side effects.
* Làm timeout recovery deterministic hơn.

### Costs / Risks

* Cần storage/retention policy.
* Concurrent in-progress requests cần semantics rõ.
* External side effects làm atomicity phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không chứng minh operation thất bại.

### Middle

Implement key + unique constraint + replay semantics.

### Senior

Thiết kế fingerprint, concurrent request state và external-side-effect recovery.

### Technical Lead / Architect

Chuẩn hóa idempotency contract cho critical commands toàn hệ thống.

## 11. Key takeaway

* Retry safety phải được thiết kế từ server, không giao cho client đoán.
* Atomic key claim quan trọng hơn một cache lookup đơn giản.
* Idempotency scope và retention phải phản ánh business operation.

# 7. Azure SQL connection resiliency: transient faults, retry strategy và transaction boundary trong EF Core

## 1. What is it?

Cloud database connections có thể gặp transient failures do failover, network blip, throttling hoặc maintenance. EF Core có execution strategy hỗ trợ retry các failures được nhận diện là transient.

```csharp
options.UseSqlServer(connectionString,
    sql => sql.EnableRetryOnFailure());
```

Mục tiêu là làm operation ngắn, retry-safe tự phục hồi khỏi lỗi tạm thời — không phải che mọi database exception.

## 2. Why does it exist?

On-prem single-node assumptions thường là connection ổn định lâu dài. Cloud database được thiết kế để failover/patch/scale. Một vài connection attempts có thể fail dù service tổng thể healthy. Nếu mọi transient blip trở thành HTTP 500, application availability thấp hơn database platform khả dụng thực tế.

## 3. How does it work?

Execution strategy wrap database operation và retry theo policy khi lỗi thuộc transient class. Nhưng user-created transaction tạo complication: toàn unit phải được replay như một block.

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);
    // database work
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
});
```

Operation bên trong phải có replay semantics phù hợp.

## 4. Practical implementation

Retry budget phải nằm trong end-to-end latency budget. Nếu API timeout là 2 giây, database retry policy tổng cộng 30 giây là vô nghĩa.

Phân biệt:

* transient connectivity/failover → có thể retry;
* constraint violation → không retry;
* deadlock → có thể retry bounded nhưng vẫn investigate root cause;
* timeout do overloaded query → retry mù có thể khuếch đại tải.

## 5. Real production scenario

Azure SQL failover làm một nhóm connections reset. API không có retry strategy nên error rate spike vài chục giây. Sau khi enable bounded retry và đảm bảo commands replay-safe, phần lớn requests tự phục hồi. Team vẫn giữ telemetry để failover không biến mất khỏi operational visibility.

## 6. Failure scenario & troubleshooting

**Symptom** → bật retry xong p99 latency tăng mạnh khi database overloaded.

**Evidence** → mỗi request phát nhiều query attempts, database CPU/worker pressure tăng thêm.

**Hypothesis** → retry đang khuếch đại non-transient overload.

**Diagnosis** → correlate retries với error codes, DB waits, query duration và request deadlines.

**Fix** → giới hạn retries/backoff, sửa slow query/capacity, circuit/load shedding nếu cần.

**Verification** → chaos failover test và overload test riêng; policy phải giúp transient case nhưng không phá overload case.

## 7. Common mistakes

* Retry mọi `SqlException`.
* Nested retry ở HTTP + service + EF khiến attempts nhân lên.
* External API call bên trong database execution strategy replay block.
* Không tính request cancellation/deadline.
* Dùng retry để che permanent configuration/auth errors.

## 8. Alternatives

Application-level command retry phù hợp khi cần replay toàn workflow với idempotency. Queue-based processing tốt cho work không cần synchronous response. Circuit breaker/load shedding phù hợp persistent dependency failure, không thay transient retry.

## 9. Trade-offs

### Advantages

* Tăng resilience trước failover/network blips.
* Giảm user-visible transient errors.

### Costs / Risks

* Tăng tail latency.
* Retry storm nếu policy sai.
* Transaction replay semantics phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt transient với permanent failure.

### Middle

Cấu hình execution strategy và cancellation hợp lý.

### Senior

Thiết kế retry budget, transaction replay và telemetry.

### Technical Lead / Architect

Chuẩn hóa retry layers để tránh retry multiplication toàn distributed call graph.

## 11. Key takeaway

* Cloud SQL resiliency cần bounded, evidence-based retry.
* Retry phải nằm trong latency budget và operation phải replay-safe.
* Overload không phải transient fault để retry vô hạn.

# 8. Docker hardening cho .NET: multi-stage build, non-root user và read-only filesystem

## 1. What is it?

Container image là production artifact chứa application và runtime dependencies. Hardening giảm attack surface và quyền của process khi compromise xảy ra.

Ba controls nền tảng:

```text
multi-stage build → image nhỏ, không mang build tools
non-root process   → giảm privilege
read-only rootfs   → giảm khả năng ghi/persist trong container
```

## 2. Why does it exist?

Một container không phải security boundary tuyệt đối. Nếu app bị RCE và chạy root với writable filesystem, attacker có nhiều khả năng sửa files/process environment hoặc tận dụng misconfiguration. Principle of least privilege vẫn áp dụng trong container.

## 3. How does it work?

Multi-stage Dockerfile chỉ copy publish output sang runtime image:

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
USER app
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

Exact user/image conventions phải khớp runtime version được organization hỗ trợ.

## 4. Practical implementation

Ngoài non-root:

* không copy source/secrets vào runtime image;
* pin/track base image updates;
* mount writable volume chỉ cho path thật sự cần;
* đưa logs ra stdout/stderr;
* temp files dùng explicit temp path;
* drop Linux capabilities nếu platform cho phép;
* scan SBOM/image nhưng không coi scanner là defense duy nhất.

Read-only root filesystem cần test vì một số library mặc định ghi temp/cache files.

## 5. Real production scenario

Một legacy .NET service ghi generated PDF vào `/app/files`. Khi Kubernetes bật read-only rootfs theo security baseline, service fail production. Root problem là app dựa vào ephemeral container filesystem như persistent storage. Team chuyển output sang object storage/temp volume rõ ràng và giữ rootfs read-only.

## 6. Failure scenario & troubleshooting

**Symptom** → container chạy local nhưng production non-root báo permission denied.

**Evidence** → stack trace cho thấy app ghi vào application directory hoặc bind privileged port/path.

**Hypothesis** → image/app assumptions phụ thuộc root privileges.

**Diagnosis** → chạy image local với cùng UID/read-only settings và inspect write paths.

**Fix** → đổi ownership ở build time nếu thật sự cần, tốt hơn là chuyển writable data sang mounted/temp/external storage phù hợp.

**Verification** → security-context integration test trong CI/staging.

## 7. Common mistakes

* Cài SDK/build tools trong runtime image.
* Chạy root vì “container đã isolate rồi”.
* Bake secrets vào `ENV` hoặc image layer.
* `chmod -R 777` để chữa permission.
* Dùng container local disk cho durable user data.

## 8. Alternatives

Platform buildpacks/container tooling có thể tạo hardened images theo convention. Distroless/minimal images giảm attack surface thêm nhưng debugging/compatibility trade-offs tăng. VM/App Service vẫn cần least privilege dù packaging khác.

## 9. Trade-offs

### Advantages

* Giảm image size/attack surface.
* Hạn chế blast radius của RCE.
* Deployment artifact sạch và reproducible hơn.

### Costs / Risks

* Legacy assumptions về filesystem/permissions lộ ra.
* Debug production image tối giản khó hơn.
* Base-image lifecycle cần automation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết build image nhiều stage và không đưa secrets vào image.

### Middle

Chạy non-root, externalize state/logs.

### Senior

Thiết kế filesystem/capability/security context và supply-chain controls.

### Technical Lead / Architect

Đưa hardened runtime baseline vào platform template/policy thay vì review thủ công từng Dockerfile.

## 11. Key takeaway

* Containerization không xóa principle of least privilege.
* Non-root + minimal runtime + explicit writable paths là baseline tốt.
* Security controls phải được test như functional behavior.

# 9. SLO + error-budget burn-rate alerts: cảnh báo theo user impact thay vì CPU threshold tùy ý

## 1. What is it?

SLO định nghĩa target reliability cho một service indicator có ý nghĩa với user, ví dụ 99,9% requests thành công dưới một latency threshold trong 30 ngày. Error budget là phần failure được phép trong target đó.

Burn rate đo tốc độ tiêu thụ error budget:

```text
burn rate = tốc độ error budget đang bị tiêu thụ
            so với tốc độ cho phép
```

Alert theo burn rate giúp phân biệt incident thực sự đe dọa SLO với metric spike vô hại.

## 2. Why does it exist?

CPU 90% không nhất thiết là incident nếu users vẫn được phục vụ tốt. CPU 20% cũng không chứng minh service healthy nếu dependency timeout làm 30% requests fail. Infrastructure metrics là diagnostic signals; SLO nên bắt đầu từ user-visible outcome.

## 3. How does it work?

Ví dụ availability SLO 99,9% cho 30 ngày nghĩa error budget khoảng 0,1%. Nếu current bad-event ratio cao gấp nhiều lần mức budget cho phép, burn rate lớn và cần action.

Multi-window alert thường kết hợp:

```text
fast window  → bắt outage nghiêm trọng nhanh
slow window  → xác nhận impact đủ bền, giảm noise
```

## 4. Practical implementation

Đầu tiên định nghĩa SLI rõ:

```text
good events = HTTP requests hợp lệ trả success theo product semantics
valid events = requests thuộc scope SLO
SLI = good / valid
```

Không nên tính health probes, bot traffic hoặc client errors vào cùng mẫu số nếu chúng không phản ánh reliability contract tương tự.

Dashboard gồm SLO remaining budget, burn rate, request volume và diagnostic breakdown.

## 5. Real production scenario

Một API có CPU alert 80%. Batch job mỗi đêm đẩy CPU 90% nhưng latency không đổi, pager đánh thức on-call vô ích. Trong incident thật, dependency trả 503 nhưng CPU app giảm xuống 30%, nên old alert im lặng. Chuyển primary paging sang SLO burn alerts bắt đúng user-impact incident và để CPU thành diagnostic alert/dashboard.

## 6. Failure scenario & troubleshooting

**Symptom** → burn alert fire liên tục khi traffic rất thấp.

**Evidence** → 2 failures trên 5 requests tạo error ratio 40% nhưng absolute user impact nhỏ.

**Hypothesis** → low-volume service cần minimum-event guard hoặc different SLO window strategy.

**Diagnosis** → inspect numerator/denominator, traffic seasonality và event classification.

**Fix** → multi-window/multi-burn policy, minimum request volume hoặc synthetic checks nếu phù hợp.

**Verification** → replay historical incidents và noisy periods để xem alert precision/recall.

## 7. Common mistakes

* SLO = uptime của VM thay vì user journey.
* Dùng average latency làm SLI duy nhất.
* Đặt 100% target không có engineering trade-off.
* Alert mọi metric thay vì dùng metrics để diagnosis.
* Không review SLO khi product traffic/criticality thay đổi.

## 8. Alternatives

Static threshold alerts vẫn hữu ích cho imminent resource exhaustion như disk nearly full. Anomaly detection có thể bắt pattern bất thường nhưng khó giải thích và không thay reliability objective. Synthetic monitoring bổ sung external perspective.

## 9. Trade-offs

### Advantages

* Pager gắn với user impact.
* Reliability trở thành measurable product trade-off.
* Giảm alert fatigue nếu thiết kế tốt.

### Costs / Risks

* SLI classification sai dẫn đến false confidence.
* Low-traffic services cần policy riêng.
* Cần telemetry pipeline đáng tin cậy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt infrastructure metric và user-facing reliability.

### Middle

Tính SLI/SLO/error budget và đọc burn rate.

### Senior

Thiết kế multi-window alert, traffic guards và incident correlation.

### Technical Lead / Architect

Đồng thuận SLO với product/business và dùng error budget để cân bằng reliability với release velocity.

## 11. Key takeaway

* Pager nên phản ánh nguy cơ vi phạm reliability objective, không phải mọi metric spike.
* Error budget biến reliability thành một budget có thể đo.
* Infrastructure metrics vẫn cần, nhưng chủ yếu để chẩn đoán sau khi biết user đang bị ảnh hưởng.

# 10. AI/RAG retrieval quality: chunking, metadata filtering và evaluation trước khi blame model

## 1. What is it?

Retrieval-Augmented Generation (RAG) đưa relevant context từ nguồn dữ liệu vào model trước khi generate answer. Chất lượng output phụ thuộc không chỉ model mà còn ingestion, chunking, embeddings/retrieval, filters, ranking và context assembly.

```text
Documents
  ↓ chunk/index
Retriever
  ↓ candidates
Rerank/filter
  ↓ context
LLM
  ↓ answer
```

Nếu relevant evidence không vào context, model mạnh hơn cũng không thể reliably “biết” tài liệu private đó.

## 2. Why does it exist?

Enterprise knowledge thay đổi liên tục và thường không nằm trong model training. RAG cho phép answers dựa trên current/private corpus mà không fine-tune model cho từng document update.

Nhưng naive vector search dễ trả chunk gần về từ vựng nhưng sai product/version/tenant.

## 3. How does it work?

Chunking quyết định unit được index. Chunk quá lớn chứa nhiều chủ đề, embedding trở nên mơ hồ và tốn context. Chunk quá nhỏ mất surrounding meaning.

Metadata giúp constrain search:

```text
tenant = A
product = Payments
version = v3
status = Published
language = vi
```

Hybrid retrieval có thể kết hợp lexical search với semantic vectors; reranker sắp lại candidates trước khi đưa vào model.

## 4. Practical implementation

Build evaluation set trước khi tuning:

```text
Question
Expected source document/chunk
Must-have facts
Forbidden/unsupported claim
```

Đo ít nhất hai tầng:

* **retrieval metrics**: relevant chunk có vào top-k không?
* **answer metrics**: answer có grounded/correct theo context không?

Nếu retrieval recall thấp, đổi prompt model thường chỉ che symptom.

## 5. Real production scenario

Support assistant trả hướng dẫn API v2 cho customer dùng v3. Vector similarity cao vì hai docs gần giống nhau. Root cause không phải hallucination thuần túy mà index thiếu version metadata filtering. Sau khi filter `productVersion=v3` và ưu tiên published/current docs, answer accuracy tăng mà không đổi model.

## 6. Failure scenario & troubleshooting

**Symptom** → answer tự tin nhưng trích sai policy cũ.

**Evidence** → retrieved context chứa archived document và không có current policy.

**Hypothesis** → ingestion/filter/ranking lỗi hơn là generation lỗi.

**Diagnosis** → log sanitized retrieval IDs/scores/metadata, inspect top-k và compare expected source trong eval set.

**Fix** → metadata lifecycle, chunking/ranking/filter policy; chỉ tune generation sau khi retrieval evidence đúng.

**Verification** → rerun fixed evaluation set và regression suite trước/ sau thay đổi.

## 7. Common mistakes

* Chọn chunk size theo một con số internet mà không eval corpus thật.
* Index Draft/Archived và Published như nhau.
* Không enforce tenant/security filter trước retrieval.
* Chỉ chấm answer “nghe có vẻ hay”.
* Tăng top-k vô hạn, làm context đầy noise và tăng token cost.

## 8. Alternatives

Full-text search đủ tốt cho exact identifiers/technical terms. SQL/query tools tốt hơn RAG khi câu hỏi cần deterministic structured aggregation. Fine-tuning phù hợp behavior/style/patterns nhất định nhưng không phải replacement cho frequently changing factual corpus.

## 9. Trade-offs

### Advantages

* Ground model bằng current/private knowledge.
* Update knowledge nhanh hơn retraining.
* Có thể cung cấp source traceability.

### Costs / Risks

* Retrieval pipeline trở thành distributed information system cần observability.
* Security filtering sai có thể leak cross-tenant data.
* More context không đồng nghĩa more accuracy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG gồm retrieval + generation, không chỉ prompt.

### Middle

Thiết kế chunking, metadata và inspect top-k results.

### Senior

Xây evaluation set, hybrid/rerank strategy và security filters.

### Technical Lead / Architect

Đặt quality gates, data governance, observability và cost/latency SLO cho toàn AI knowledge pipeline.

## 11. Key takeaway

* Khi RAG trả lời sai, hãy kiểm tra context được retrieve trước khi blame model.
* Metadata/version/security filters là correctness boundary.
* Evaluation phải đo retrieval và generation riêng để biết cần sửa layer nào.
