# 1. C# `ValueTask<T>`: giảm allocation ở hot path nhưng chỉ khi xác suất hoàn thành synchronous đủ cao và contract được hiểu đúng

## 1. What is it?

`ValueTask<T>` là một awaitable value type trong .NET có thể đại diện cho một kết quả đã có sẵn ngay lập tức hoặc cho một asynchronous operation sẽ hoàn thành sau.

Mental model quan trọng không phải là:

```text
ValueTask = Task nhưng nhanh hơn
```

mà là:

```text
ValueTask = cơ chế tối ưu allocation cho một số async API có khả năng hoàn thành synchronously rất thường xuyên
```

`Task<T>` là reference type. Nếu một API được gọi cực nhiều và đa số lần đã có kết quả ngay, việc tạo `Task<T>` hoàn chỉnh cho mỗi call có thể tạo allocation không cần thiết. `ValueTask<T>` cho phép trả kết quả trực tiếp bên trong struct trong trường hợp đó.

## 2. Why does it exist?

Một cache hoặc buffer reader có thể có data sẵn phần lớn thời gian:

```text
ReadAsync()
  ├─ 95%: data đã có trong buffer
  └─ 5%: phải thật sự chờ I/O
```

Nếu luôn trả `Task<T>`, 95% fast path vẫn có thể tạo object cho một kết quả đã biết.

Trong hot path có hàng trăm nghìn operations/second, allocation nhỏ nhưng lặp lại liên tục có thể tăng GC pressure.

`ValueTask<T>` tồn tại để biểu diễn cả synchronous completion và asynchronous completion mà không bắt buộc tạo `Task<T>` mới cho fast path.

## 3. How does it work?

Một `ValueTask<T>` có thể wrap:

* giá trị `T` trực tiếp
* một `Task<T>`
* một `IValueTaskSource<T>` tối ưu hơn cho reusable async machinery

Ví dụ:

```csharp
public ValueTask<string> GetNameAsync(int id)
{
    if (_cache.TryGetValue(id, out var name))
        return ValueTask.FromResult(name);

    return new ValueTask<string>(LoadFromDatabaseAsync(id));
}
```

Fast path trả giá trị mà không cần allocation `Task<string>` riêng. Slow path vẫn có thể dựa trên `Task<string>`.

Tuy nhiên, vì một số `ValueTask` được backing bởi reusable source, contract usage thường là **await một lần**. Không nên mặc định cache `ValueTask`, await nhiều lần hoặc dùng đồng thời như một `Task` bình thường.

## 4. Practical implementation

Một API phù hợp hơn là read-through cache cực nóng:

```csharp
public sealed class CountryNameResolver
{
    private readonly ConcurrentDictionary<int, string> _cache = new();
    private readonly CountryRepository _repository;

    public CountryNameResolver(CountryRepository repository)
    {
        _repository = repository;
    }

    public ValueTask<string?> ResolveAsync(
        int countryId,
        CancellationToken cancellationToken)
    {
        if (_cache.TryGetValue(countryId, out var cached))
            return ValueTask.FromResult<string?>(cached);

        return new ValueTask<string?>(LoadAsync(countryId, cancellationToken));
    }

    private async Task<string?> LoadAsync(
        int countryId,
        CancellationToken cancellationToken)
    {
        var value = await _repository.GetNameAsync(countryId, cancellationToken);

        if (value is not null)
            _cache.TryAdd(countryId, value);

        return value;
    }
}
```

Caller vẫn dùng tự nhiên:

```csharp
var name = await resolver.ResolveAsync(countryId, cancellationToken);
```

Không nên đổi mọi `Task<T>` trong application sang `ValueTask<T>` chỉ vì nghe rằng struct “không allocation”.

## 5. Real production scenario

Một pricing service gọi local resolver hàng triệu lần mỗi phút để map internal IDs sang metadata. Sau profiling, team thấy resolver hit in-memory cache trên 99% requests và riêng allocation từ completed `Task<T>` đóng góp đáng kể vào Gen 0 collections.

Ở đây `ValueTask<T>` có thể đáng cân nhắc vì:

* call frequency cực cao
* synchronous completion rate cực cao
* API usage đơn giản: await một lần
* profiling đã chứng minh allocation là bottleneck đáng quan tâm

Ngược lại, một repository EF Core hầu như luôn phải chờ database không phải ứng viên tự nhiên để đổi sang `ValueTask<T>`.

## 6. Failure scenario & troubleshooting

**Symptom** → sau “optimization”, code khó debug hơn, có intermittent exception khi cùng `ValueTask` bị consume nhiều lần.

**Evidence** → call site lưu `ValueTask` vào field hoặc await lại cùng instance; benchmark không cho thấy throughput tăng đáng kể.

**Hypothesis** → API đã áp dụng `ValueTask` sai workload hoặc sai consumption contract.

**Diagnosis** → kiểm tra synchronous completion rate, allocations bằng profiler/BenchmarkDotNet, và usage sites.

**Fix** → quay lại `Task<T>` nếu lợi ích không đo được; chỉ giữ `ValueTask<T>` ở API có fast path rõ ràng.

**Verification** → benchmark trước/sau với workload đại diện, không chỉ microbenchmark synthetic.

## 7. Common mistakes

* Thay toàn bộ `Task<T>` bằng `ValueTask<T>` như coding standard.
* Gọi `.AsTask()` ngay lập tức ở hầu hết call sites, làm mất phần lớn lợi ích.
* Await cùng `ValueTask` nhiều lần mà không hiểu backing source.
* Chỉ nhìn allocation mà bỏ qua code complexity và API semantics.
* Tối ưu trước khi profiler chứng minh đây là bottleneck.

## 8. Alternatives

`Task<T>` vẫn là mặc định tốt nhất cho phần lớn asynchronous APIs vì semantics đơn giản, composability tốt và tooling quen thuộc.

Nếu vấn đề là cache, có thể tối ưu access pattern, batching hoặc giảm số calls trước khi đụng tới awaitable representation.

## 9. Trade-offs

### Advantages

* Có thể giảm allocation ở fast path hoàn thành synchronously.
* Hữu ích cho runtime/library-level APIs hoặc cực nóng, cực thường xuyên.

### Costs / Risks

* Struct lớn hơn reference pointer và có thể tăng copying cost.
* Contract consumption phức tạp hơn.
* Lợi ích thường bằng 0 nếu operation gần như luôn asynchronous.
* Làm public API khó hiểu hơn nếu team không quen semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task<T>` là mặc định cho async và `ValueTask<T>` không phải phiên bản “tốt hơn”.

### Middle

Biết consume `ValueTask<T>` đúng bằng `await`, tránh lưu/await lặp khi không có contract cho phép.

### Senior

Dùng profiler và completion-rate evidence để quyết định có đáng đổi API hay không.

### Technical Lead / Architect

Giữ complexity budget: chỉ đưa `ValueTask<T>` vào shared contracts khi performance evidence đủ mạnh và ownership rõ ràng.

## 11. Key takeaway

* `ValueTask<T>` là optimization tool, không phải default async return type.
* Nó có giá trị nhất khi synchronous completion xảy ra rất thường xuyên.
* Measure allocation và throughput trước khi đổi contract.

# 2. ASP.NET Core partitioned rate limiting: bảo vệ dependency theo tenant/user/API key thay vì dùng một global limit thô

## 1. What is it?

Rate limiting kiểm soát lượng request được phép đi qua trong một khoảng thời gian hoặc theo mức concurrency. Partitioned rate limiting chia budget theo một key như tenant, user, API key, client application hoặc endpoint.

Mental model:

```text
Tenant A ──> limiter[A]
Tenant B ──> limiter[B]
Tenant C ──> limiter[C]
                  ↓
             protected API
```

Điểm cốt lõi: một noisy tenant không nên dùng hết capacity budget của tất cả tenant khác.

## 2. Why does it exist?

Một global limit kiểu “1000 requests/second cho toàn API” đơn giản nhưng có thể gây unfairness:

```text
Tenant A: 950 req/s
Tenant B: 30 req/s
Tenant C: 20 req/s
```

Khi A burst lên, B/C có thể bị reject dù workload của họ hoàn toàn bình thường.

Rate limiting theo partition giúp kết nối technical capacity với ownership hoặc commercial/business boundary.

## 3. How does it work?

ASP.NET Core Rate Limiting middleware có thể chọn limiter dựa trên request context.

Flow:

```text
Request
  ↓
resolve partition key
  ↓
obtain limiter for partition
  ↓
acquire permit
  ├─ granted → endpoint
  └─ rejected → 429 Too Many Requests
```

Các algorithm phổ biến gồm fixed window, sliding window, token bucket và concurrency limiter. Chúng giải quyết workload pattern khác nhau.

## 4. Practical implementation

Ví dụ partition theo authenticated tenant claim:

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(
        context =>
        {
            var tenantId = context.User.FindFirst("tenant_id")?.Value
                           ?? "anonymous";

            return RateLimitPartition.GetTokenBucketLimiter(
                tenantId,
                _ => new TokenBucketRateLimiterOptions
                {
                    TokenLimit = 100,
                    TokensPerPeriod = 50,
                    ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                    QueueLimit = 20,
                    AutoReplenishment = true
                });
        });

    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});

app.UseRateLimiter();
```

Production API nên trả contract rõ ràng và, khi phù hợp, `Retry-After` để client biết retry behavior.

## 5. Real production scenario

Một SaaS reporting endpoint gọi downstream analytics database có capacity giới hạn. Một tenant import dashboard và vô tình poll endpoint 30 lần/second từ nhiều browser tabs.

Không partition: toàn service chậm cho mọi tenant.

Partition theo tenant: tenant gây burst bị 429 hoặc queue trong budget riêng, trong khi tenant khác vẫn hoạt động bình thường.

## 6. Failure scenario & troubleshooting

**Symptom** → sau deploy rate limiter, legitimate batch client nhận nhiều 429 dù total traffic thấp.

**Evidence** → metrics cho thấy reject tập trung vào một partition; traffic có short bursts thay vì steady rate.

**Hypothesis** → algorithm/window không khớp traffic pattern.

**Diagnosis** → xem per-partition throughput, burst size, queue wait và downstream capacity.

**Fix** → điều chỉnh token bucket/window/concurrency limit; không chỉ tăng con số tùy tiện.

**Verification** → replay representative burst và kiểm tra cả reject rate lẫn downstream p95.

## 7. Common mistakes

* Rate limit theo client IP trong hệ thống sau reverse proxy nhưng đọc sai forwarded IP.
* Dùng global limit cho multi-tenant workload rồi gọi đó là fairness.
* Queue quá dài khiến request không bị reject nhưng latency tăng đến mức vô dụng.
* Retry 429 ngay lập tức không jitter, tạo retry storm.
* Xem rate limiting như security thay thế authorization.

## 8. Alternatives

API gateway/Azure API Management có thể enforce quota/rate policy trước application. Điều này tốt khi policy mang tính platform/API product.

Application-level limiter phù hợp khi partition key hoặc business capacity chỉ application hiểu rõ.

## 9. Trade-offs

### Advantages

* Isolation tốt hơn giữa tenants/clients.
* Bảo vệ downstream khỏi overload.
* Có thể encode fairness và service tiers.

### Costs / Risks

* State per partition tăng memory/complexity.
* Multi-instance application cần hiểu limiter state có local hay distributed semantics.
* Sai key có thể tạo bypass hoặc unfair throttling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 429 là server từ chối do capacity/policy, không phải generic 500.

### Middle

Biết configure limiter, partition key và response behavior.

### Senior

Chọn algorithm dựa trên burst/concurrency/downstream characteristics và đo impact bằng metrics.

### Technical Lead / Architect

Quyết định rate limit đặt ở app, gateway hay cả hai; xác định fairness boundary và capacity ownership.

## 11. Key takeaway

* Rate limiting tốt phải phản ánh resource boundary thực tế.
* Partitioning ngăn một client tiêu hết shared capacity.
* 429 không giải quyết overload nếu client retry sai cách.

# 3. EF Core `AsSplitQuery`: xử lý cartesian explosion khi `Include` nhiều collection mà không đánh đổi consistency một cách vô thức

## 1. What is it?

Khi EF Core load nhiều collection navigation bằng `Include` trong một single SQL query, các `JOIN` có thể tạo cartesian multiplication: cùng parent row bị lặp rất nhiều lần vì mỗi combination của child collections tạo một result row.

`AsSplitQuery()` yêu cầu EF Core tách graph load thành nhiều SQL queries thay vì một query JOIN khổng lồ.

## 2. Why does it exist?

Giả sử một Order có:

* 20 OrderLines
* 10 Notes
* 5 Discounts

Một joined shape không nhất thiết chỉ trả 35 child rows. Nếu collections được join cùng cấp, intermediate row count có thể tăng theo tích số lượng combinations.

Kết quả:

* nhiều bytes truyền qua network
* duplicate parent columns
* tăng DB CPU/I/O
* tăng materialization cost

## 3. How does it work?

Single query:

```text
Orders
  JOIN OrderLines
  JOIN Notes
  JOIN Discounts
```

Split query:

```text
Query 1: Orders
Query 2: OrderLines cho Orders đã chọn
Query 3: Notes cho Orders đã chọn
Query 4: Discounts cho Orders đã chọn
```

EF Core materializer ghép kết quả về object graph ở client side.

## 4. Practical implementation

```csharp
var order = await db.Orders
    .Where(x => x.Id == orderId)
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .Include(x => x.Discounts)
    .AsSplitQuery()
    .SingleAsync(cancellationToken);
```

Tuy nhiên nếu endpoint chỉ cần read model, projection thường tốt hơn:

```csharp
var dto = await db.Orders
    .Where(x => x.Id == orderId)
    .Select(x => new OrderDetailsDto
    {
        Id = x.Id,
        LineCount = x.Lines.Count,
        TotalDiscount = x.Discounts.Sum(d => d.Amount)
    })
    .SingleAsync(cancellationToken);
```

`AsSplitQuery` không phải giấy phép để `Include` mọi thứ.

## 5. Real production scenario

Admin endpoint load Product cùng Images, Variants, Categories và Reviews. Query hoạt động nhanh với test data nhỏ nhưng Production products có hàng trăm variants/reviews.

APM cho thấy SQL trả hàng chục nghìn rows để dựng một product object. Network payload DB→app lớn hơn dữ liệu logic rất nhiều.

Sau khi đo, team chuyển read endpoint sang projection cho phần summary và dùng split query ở nơi thực sự cần full graph.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint chậm, application CPU/materialization cao, SQL row count lớn bất thường.

**Evidence** → generated SQL có nhiều collection JOIN; actual rows lớn hơn số entities đáng kể.

**Hypothesis** → cartesian explosion.

**Diagnosis** → log generated SQL, execution plan, row count và payload size.

**Fix** → projection hoặc `AsSplitQuery`; kiểm tra transaction/isolation nếu consistency giữa split queries quan trọng.

**Verification** → so sánh logical entities, SQL reads, bytes transferred và p95.

## 7. Common mistakes

* Thấy query chậm là thêm `AsSplitQuery` mà không xem graph có thực sự cần thiết.
* Quên rằng split query tạo nhiều database round trips.
* Assume mọi split query nhìn cùng một snapshot trong điều kiện concurrent writes.
* `Include` graph lớn để map xuống DTO cuối cùng chỉ dùng vài fields.

## 8. Alternatives

Projection là lựa chọn tốt nhất cho nhiều read endpoints.

Explicit loading phù hợp khi child data chỉ cần trong một số branch, nhưng dễ tạo N+1 nếu dùng trong loop.

Single query vẫn tốt khi graph nhỏ và round-trip minimization quan trọng.

## 9. Trade-offs

### Advantages

* Giảm result-set duplication và cartesian explosion.
* Có thể giảm memory/materialization cost đáng kể.

### Costs / Risks

* Tăng round trips.
* Có potential consistency differences giữa queries nếu data thay đổi giữa lúc đọc.
* Không sửa được vấn đề “load quá nhiều data” về mặt business requirement.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` không miễn phí và SQL phía dưới quyết định cost.

### Middle

Biết inspect generated SQL và dùng projection/`AsSplitQuery` đúng chỗ.

### Senior

Đo row multiplication, consistency implications và round-trip trade-offs.

### Technical Lead / Architect

Thiết kế read model/API contract để không buộc persistence layer hydrate object graph khổng lồ một cách mặc định.

## 11. Key takeaway

* Nhiều collection `Include` có thể nhân số rows thay vì cộng đơn giản.
* `AsSplitQuery` đổi duplication lấy round trips.
* Projection thường là câu trả lời sạch hơn cho read-only API.

# 4. SQL Server parameter sniffing và plan regression: khi cùng một query text nhưng parameter distribution khác nhau cần execution plan khác nhau

## 1. What is it?

SQL Server thường compile execution plan dựa trên parameter values nhìn thấy tại thời điểm compilation rồi cache plan để tái sử dụng. Parameter sniffing tự nó không phải bug; nó thường giúp optimizer chọn plan tốt dựa trên real parameter.

Vấn đề xuất hiện khi data distribution skew lớn: plan tốt cho parameter phổ biến có thể rất tệ cho parameter hiếm, hoặc ngược lại.

## 2. Why does it exist?

Compile query plan mỗi execution rất tốn CPU. Plan cache cho phép reuse.

Nhưng một plan duy nhất không phải lúc nào phù hợp với mọi cardinality:

```text
Tenant 1: 10 rows
Tenant 999: 30,000,000 rows
```

Cùng predicate `WHERE TenantId = @tenantId` có thể cần access strategy khác nhau.

## 3. How does it work?

Ví dụ:

```sql
SELECT Id, CreatedUtc, Total
FROM Orders
WHERE TenantId = @TenantId
  AND CreatedUtc >= @FromUtc;
```

Nếu compile lần đầu cho tenant cực nhỏ, optimizer có thể chọn nested loops + seeks. Plan đó được cached. Tenant khổng lồ chạy sau có thể tạo hàng triệu lookups và latency tăng mạnh.

Ngược lại, plan scan/hash phù hợp tenant lớn có thể quá đắt cho tenant nhỏ.

## 4. Practical implementation

Đầu tiên đo chứ không sửa bằng hint ngay:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

So sánh actual execution plan giữa representative parameters. Kiểm tra estimated rows vs actual rows.

Có nhiều remediation tùy workload:

```sql
OPTION (RECOMPILE);
```

hoặc query/store plan features, statistics/index improvements, query redesign, hoặc tách code path cho cardinality classes rõ ràng.

`RECOMPILE` đổi plan adaptability lấy compile CPU, vì vậy không nên dùng mặc định.

## 5. Real production scenario

Multi-tenant SaaS có 5,000 tenants. 99% tenants dưới 100k orders, nhưng ba enterprise tenants có hàng chục triệu orders.

Sau deployment/restart, tenant nhỏ chạy report đầu tiên và plan được compile theo distribution nhỏ. Sau đó enterprise report tăng từ 2 giây lên 90 giây dù code/app không thay đổi.

Đây là ví dụ điển hình cho câu hỏi: “Tại sao hôm qua query nhanh, hôm nay cùng SQL lại chậm?”

## 6. Failure scenario & troubleshooting

**Symptom** → latency query biến động mạnh theo parameter hoặc sau plan cache reset/deploy.

**Evidence** → cùng query hash có execution durations khác nhau; estimated vs actual rows lệch lớn.

**Hypothesis** → cached plan không phù hợp parameter distribution.

**Diagnosis** → Query Store/actual plans, parameter samples, statistics và cardinality distribution.

**Fix** → chọn remediation nhỏ nhất có evidence: stats/index/query shape/recompile/plan control hoặc split path.

**Verification** → benchmark cả small và large parameter cohorts, không chỉ case đang lỗi.

## 7. Common mistakes

* Gọi mọi plan regression là parameter sniffing mà chưa xem execution plan.
* `OPTION (RECOMPILE)` lên mọi query chậm.
* Clear toàn plan cache trong Production để “fix” tạm thời, gây compile storm và che root cause.
* Test query bằng đúng một tenant rồi kết luận đã tối ưu.

## 8. Alternatives

Nếu access pattern khác nhau về bản chất, hai query shapes riêng có thể rõ ràng hơn một query “universal”.

Partitioning hoặc data architecture khác có thể cần nếu một vài tenants lớn đến mức shared-table strategy không còn phù hợp, nhưng đó là quyết định lớn hơn nhiều.

## 9. Trade-offs

### Advantages

Plan reuse giảm compile CPU và thường tăng throughput.

### Costs / Risks

Một cached plan có thể không đại diện tốt cho skewed distributions. Adaptive remediation thêm complexity và cần monitoring.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SQL execution không chỉ phụ thuộc query text mà còn statistics/data distribution.

### Middle

Biết đọc estimated/actual rows và dùng Query Store/execution plan evidence.

### Senior

Phân biệt bad index, stale stats, sniffing và general cardinality-estimation problems.

### Technical Lead / Architect

Nhận ra khi data skew là implementation concern và khi nó đã trở thành tenancy/data-partition architecture concern.

## 11. Key takeaway

* Parameter sniffing là cơ chế tối ưu hữu ích, không phải lỗi tự thân.
* Data skew có thể khiến một cached plan không phù hợp mọi parameter.
* Tối ưu phải kiểm chứng trên nhiều cardinality cohorts.

# 5. Redis negative caching và cache penetration: chặn traffic “không tồn tại” khỏi liên tục xuyên xuống database

## 1. What is it?

Cache penetration xảy ra khi requests liên tục hỏi những keys không tồn tại trong cache **và cũng không tồn tại ở source of truth**, khiến mỗi request đều xuyên xuống database.

Negative caching lưu tạm kết quả “không tồn tại” để các request giống nhau không lặp database lookup trong một khoảng thời gian ngắn.

## 2. Why does it exist?

Cache-aside thường làm:

```text
cache miss
  ↓
query DB
  ↓
found? cache value
```

Nếu DB trả “not found” nhưng ta không cache điều đó:

```text
GET /products/invalid-id
→ Redis miss
→ SQL miss
→ repeat forever
```

Bot traffic, broken client hoặc hot invalid identifier có thể tạo load đáng kể lên DB dù Redis hit rate nhìn tổng thể vẫn khá cao.

## 3. How does it work?

Ta lưu sentinel có TTL ngắn:

```text
product:123 = <NOT_FOUND> TTL 30s
```

Request tiếp theo thấy sentinel và trả 404 mà không query DB.

TTL negative thường ngắn hơn positive cache vì entity có thể được tạo sau đó và stale “not found” có impact trực tiếp lên correctness/freshness.

## 4. Practical implementation

```csharp
private const string NotFoundMarker = "__NOT_FOUND__";

public async Task<ProductDto?> GetAsync(Guid id, CancellationToken ct)
{
    var key = $"product:{id:N}";
    var cached = await _redis.StringGetAsync(key);

    if (cached.HasValue)
    {
        if (cached == NotFoundMarker)
            return null;

        return JsonSerializer.Deserialize<ProductDto>(cached!);
    }

    var product = await _db.Products
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new ProductDto(x.Id, x.Name))
        .SingleOrDefaultAsync(ct);

    if (product is null)
    {
        await _redis.StringSetAsync(key, NotFoundMarker, TimeSpan.FromSeconds(30));
        return null;
    }

    await _redis.StringSetAsync(
        key,
        JsonSerializer.Serialize(product),
        TimeSpan.FromMinutes(5));

    return product;
}
```

## 5. Real production scenario

Public product API nhận hàng triệu requests/ngày. Một crawler sinh URL product IDs sai do bug. Những IDs này không tồn tại nhưng mỗi URL được crawl lặp lại.

Database CPU tăng dù business traffic không đổi. Negative caching trong 30–60 giây giảm hàng nghìn repeated misses xuống một lookup mỗi key/window.

## 6. Failure scenario & troubleshooting

**Symptom** → DB query volume tăng mạnh nhưng cache hit rate của valid entities vẫn cao.

**Evidence** → query logs cho thấy cùng missing IDs lặp lại; API 404 volume tăng.

**Hypothesis** → cache penetration từ invalid/nonexistent keys.

**Diagnosis** → metric riêng positive hit / negative hit / miss; top missing keys và client source.

**Fix** → negative cache + input validation/rate limiting nếu traffic abusive.

**Verification** → DB miss queries giảm mà valid-new-entity visibility vẫn đáp ứng freshness requirement.

## 7. Common mistakes

* Cache `null` với TTL bằng positive value rồi làm newly-created record “biến mất” quá lâu.
* Không phân biệt “not found” với dependency timeout. Timeout không nên bị cache như business 404.
* Cho attacker tạo hàng triệu unique invalid keys, khiến negative cache tự trở thành memory pressure.
* Dùng negative caching thay vì sửa broken client tạo invalid traffic.

## 8. Alternatives

Bloom filter có thể chặn nhiều definitely-not-present keys với memory hiệu quả, nhưng có false positives và cần lifecycle/rebuild strategy.

Validation/rate limiting hữu ích nếu invalid key pattern có thể phát hiện trước DB.

## 9. Trade-offs

### Advantages

* Giảm repeated misses xuống database.
* Đơn giản, hiệu quả cho hot nonexistent keys.

### Costs / Risks

* Stale negative result.
* Cache key cardinality tăng.
* Phải phân loại chính xác “not found” với transient failure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss không đồng nghĩa DB có dữ liệu để cache.

### Middle

Biết lưu sentinel với TTL hợp lý.

### Senior

Thiết kế metrics, cardinality guard và phân biệt business absence với infrastructure failure.

### Technical Lead / Architect

Quyết định cache có thật sự cần hay upstream validation/rate policy giải quyết vấn đề sạch hơn.

## 11. Key takeaway

* Missing data cũng có thể là hot access pattern.
* Negative cache TTL thường phải ngắn và có business rationale.
* Không cache transient failure như “not found”.

# 6. Modular Monolith boundaries: chia module theo business capability, ownership và transaction boundary thay vì chỉ chia folder

## 1. What is it?

Modular Monolith là một deployable application duy nhất nhưng bên trong có các module với boundaries rõ ràng về responsibility, dependencies, data ownership và public contracts.

Nó không đơn giản là:

```text
/Modules/Orders
/Modules/Payments
/Modules/Users
```

Nếu mọi module vẫn query trực tiếp tables của nhau và gọi implementation classes tùy ý, hệ thống chỉ là monolith có folder đẹp.

## 2. Why does it exist?

Microservices giải quyết một số isolation/deployment/ownership problems nhưng mang theo network, distributed consistency, observability và operational overhead.

Nhiều sản phẩm chưa cần independent deployment nhưng vẫn cần change isolation và business boundaries. Modular Monolith cho phép giữ local transaction/simpler operations trong khi tránh “big ball of mud”.

## 3. How does it work?

Ví dụ:

```text
Web/API Host
 ├─ Orders Module
 │   ├─ application contract
 │   ├─ domain
 │   └─ persistence
 ├─ Billing Module
 │   ├─ application contract
 │   ├─ domain
 │   └─ persistence
 └─ Identity Module
```

Orders không nên `db.BillingInvoices.Where(...)` trực tiếp. Nó giao tiếp qua public module contract hoặc integration event nội bộ tùy consistency need.

Dependency direction và database ownership phải enforce được bằng code/review/tests, không chỉ docs.

## 4. Practical implementation

Public contract:

```csharp
public interface IBillingModule
{
    Task<BillingStatus> GetStatusAsync(
        Guid customerId,
        CancellationToken cancellationToken);
}
```

Internal implementation không được public hóa toàn bộ:

```csharp
internal sealed class BillingModule : IBillingModule
{
    private readonly BillingDbContext _db;

    public async Task<BillingStatus> GetStatusAsync(
        Guid customerId,
        CancellationToken ct)
    {
        return await _db.Accounts
            .Where(x => x.CustomerId == customerId)
            .Select(x => x.Status)
            .SingleAsync(ct);
    }
}
```

Có thể dùng separate schema/DbContext per module để làm ownership rõ hơn dù vẫn cùng physical SQL Server.

## 5. Real production scenario

Một SaaS ban đầu chỉ có 8 engineers. Nếu tách 15 microservices ngay, team phải vận hành broker, tracing, deployment pipelines, retries và eventual consistency trước khi business complexity cần đến.

Modular Monolith cho phép Orders, Notifications, Billing, Documents có boundaries nhưng deploy cùng nhau. Sau này nếu Notifications cần scale/deploy độc lập, module boundary tốt làm extraction dễ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → thay schema Billing làm Orders build/runtime fail dù không đổi Billing public contract.

**Evidence** → Orders repository query trực tiếp Billing tables hoặc reference Billing EF entities.

**Hypothesis** → data ownership boundary đã bị bypass.

**Diagnosis** → dependency graph/static architecture tests/search cross-module table access.

**Fix** → đưa interaction về module API/read contract; xác định transaction semantics rõ ràng.

**Verification** → internal Billing refactor không buộc Orders sửa nếu contract không đổi.

## 7. Common mistakes

* Gọi Modular Monolith chỉ vì có folder `Modules`.
* Shared `DbContext` với mọi entity public cho toàn application.
* Dùng MediatR global bus rồi module nào cũng gọi handler internals của module khác.
* Tạo abstraction quá nhiều dù boundaries chưa có business meaning.
* Thiết kế module như future microservice giả định thay vì nhu cầu hiện tại.

## 8. Alternatives

Layered Monolith đơn giản hơn và hoàn toàn hợp lý cho domain nhỏ.

Microservices phù hợp khi có independent scaling/deployment/team ownership/failure isolation requirement đủ mạnh để trả distributed-system cost.

## 9. Trade-offs

### Advantages

* Một deployment, local debugging và local transactions đơn giản hơn microservices.
* Vẫn tạo change isolation và ownership boundaries tốt.
* Có đường evolution sang services nếu thật sự cần.

### Costs / Risks

* Boundary enforcement cần kỷ luật/tooling.
* Process failure vẫn có thể ảnh hưởng toàn application.
* Independent scaling/deployment không có sẵn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module đại diện business responsibility chứ không phải folder grouping.

### Middle

Biết giữ dependency qua public contracts và không truy cập internals tùy tiện.

### Senior

Thiết kế data ownership, transaction boundary và interaction pattern giữa modules.

### Technical Lead / Architect

Quyết định khi nào Modular Monolith đủ tốt và chỉ extract service khi operational/business pressure thực sự tồn tại.

## 11. Key takeaway

* Boundary quan trọng hơn folder structure.
* Data ownership là phép thử thực tế của modularity.
* Microservices không phải bước trưởng thành bắt buộc sau monolith.

# 7. Azure Blob Storage large-file streaming + SAS / Managed Identity: truyền file lớn mà không biến Web API thành memory bottleneck hoặc secret distributor

## 1. What is it?

Azure Blob Storage là object storage phù hợp cho file lớn, media, exports và documents. Với large-file flow, kiến trúc quan trọng là quyết định bytes đi qua Web API hay client upload/download trực tiếp với Blob Storage.

Managed Identity cho server-side application authenticate tới Storage mà không giữ account key. SAS cung cấp delegated, time-limited permission cho client khi cần direct access.

## 2. Why does it exist?

Naive upload:

```text
Browser → Web API → memory buffer → Blob
```

Với file 2 GB và nhiều concurrent users, API có thể trở thành unnecessary bandwidth/memory bottleneck.

Better flow trong nhiều use case:

```text
Browser → API: xin upload authorization
API → generate constrained SAS
Browser → Blob Storage trực tiếp
API ← completion metadata/event
```

## 3. How does it work?

Server authenticate bằng Managed Identity để quản lý blob/container. Khi user được authorization business-level để upload, server cấp SAS scoped vào đúng blob/container, permissions và expiration.

SAS không thay authorization business logic. Nó chỉ là storage capability token sau khi application đã quyết định user được phép gì.

## 4. Practical implementation

Server-side streaming nếu file phải đi qua app:

```csharp
await blobClient.UploadAsync(
    request.Body,
    overwrite: false,
    cancellationToken);
```

Tránh `MemoryStream` toàn file khi không cần.

Managed Identity setup trong .NET thường dùng `DefaultAzureCredential`:

```csharp
var serviceClient = new BlobServiceClient(
    new Uri(storageEndpoint),
    new DefaultAzureCredential());
```

Nếu cấp user-delegation SAS, scope phải minimum privilege, short-lived và gắn đúng resource.

## 5. Real production scenario

CMS cho editor upload video 800 MB. Phiên bản đầu đọc `IFormFile` vào byte array rồi upload Blob. App Service memory tăng đột biến, GC/LOH pressure và request timeout khi nhiều editors upload đồng thời.

Team chuyển sang direct-to-Blob upload bằng short-lived SAS; API chỉ quản lý authorization và metadata. Application bandwidth/memory giảm mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → upload lớn fail ở 30–60 giây hoặc app memory tăng theo file size.

**Evidence** → request body buffering, process working set tăng, gateway timeout; Blob service vẫn healthy.

**Hypothesis** → API đang buffer/proxy bytes không cần thiết.

**Diagnosis** → trace request path, inspect ASP.NET body handling, upload code và reverse-proxy limits.

**Fix** → streaming hoặc direct upload; chunk/block upload nếu cần; SAS short-lived.

**Verification** → concurrent large-file load test; app memory không scale tuyến tính theo tổng bytes in-flight.

## 7. Common mistakes

* Lưu Storage account key trong appsettings/secret pipeline dù Managed Identity dùng được.
* Cấp SAS cả container với write/delete permissions khi user chỉ cần upload một blob.
* SAS expiration quá dài và log full SAS URL.
* Tin file upload thành công đồng nghĩa file an toàn; malware/content validation vẫn là concern riêng.
* Không có lifecycle policy cho orphaned uploads.

## 8. Alternatives

Proxy qua API vẫn hợp lý khi server bắt buộc transform/encrypt/inspect stream inline hoặc client không thể access Blob trực tiếp.

Azure Front Door/CDN có thể phục vụ public/static download paths khi cacheability phù hợp.

## 9. Trade-offs

### Advantages

* Direct Blob transfer giảm app CPU/memory/bandwidth.
* Managed Identity giảm secret-management burden.
* SAS cho least-privilege delegation có expiry.

### Costs / Risks

* Client flow phức tạp hơn.
* CORS, multipart/chunk retry và orphan cleanup cần thiết kế.
* SAS là bearer capability; leak token có thể tạo unauthorized storage action trong thời gian hiệu lực.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu object storage nên giữ file, database thường chỉ giữ metadata/reference.

### Middle

Biết stream upload/download và dùng Blob SDK với `CancellationToken`.

### Senior

Thiết kế direct upload, constrained SAS, retry/chunking và lifecycle cleanup.

### Technical Lead / Architect

Chọn data path dựa trên security, cost, bandwidth và compliance; xác định application hay storage chịu responsibility nào.

## 11. Key takeaway

* File lớn không nên mặc định buffer qua Web API.
* Managed Identity dành cho service identity; SAS dành cho delegated limited access.
* Direct upload vẫn cần business authorization và validation lifecycle.

# 8. Azure App Service deployment slots: warm-up, swap và rollback release mà vẫn phải thiết kế database compatibility đúng

## 1. What is it?

Deployment slot là một live App Service environment riêng trong cùng app, ví dụ `production` và `staging`. Ta deploy version mới vào staging, warm-up/test nó, rồi swap routing/configuration để version mới nhận Production traffic.

Mental model:

```text
Build v2
  ↓
Staging slot
  ↓ warm-up + smoke test
Swap
  ↓
Production traffic → v2
```

## 2. Why does it exist?

Deploy trực tiếp vào Production có thể gây cold start, partial file replacement hoặc khó rollback. Slot tạo một release boundary để version mới chạy sẵn trước khi nhận user traffic.

Nhưng slot không tự giải quyết database migration compatibility hoặc external side effects.

## 3. How does it work?

Application code/content của slots được swap. Một số settings có thể được đánh dấu slot-sticky để không swap, ví dụ staging-only endpoints hoặc secrets/config khác môi trường.

Warm-up cho phép application process khởi động, JIT/load dependencies và health-check trước cutover.

Sau swap, old production version thường nằm ở staging, tạo rollback path bằng swap lại nếu contract vẫn compatible.

## 4. Practical implementation

Health endpoint nên kiểm tra readiness vừa đủ:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, name: "sql");

app.MapHealthChecks("/health/ready");
```

Deployment pipeline conceptual flow:

```text
build
→ automated tests
→ deploy staging
→ warm-up
→ smoke tests
→ migrate schema using Expand step
→ swap
→ monitor
→ rollback if needed
```

Database migration không nên assume chỉ v2 chạy tại thời điểm swap.

## 5. Real production scenario

v2 đổi column `Customer.FullName` thành `FirstName` + `LastName`. Nếu migration drop `FullName` trước swap, production v1 đang chạy có thể fail ngay cả khi v2 staging hoàn toàn healthy.

Safe release dùng Expand-Contract:

1. thêm new columns compatible với v1
2. deploy code có thể làm việc với transition schema
3. backfill
4. swap/monitor
5. chỉ remove old column trong later release khi không version cũ nào cần nữa

## 6. Failure scenario & troubleshooting

**Symptom** → staging smoke test pass, nhưng ngay sau swap Production trả 500.

**Evidence** → exceptions liên quan config hoặc schema; staging và production có different slot settings.

**Hypothesis** → slot-specific configuration hoặc database compatibility mismatch.

**Diagnosis** → compare effective config, health dependencies, migration state và logs trước/sau swap.

**Fix** → swap back nếu safe; sửa compatibility/config; không tiếp tục forward blindly.

**Verification** → run smoke tests trên target slot và monitor error/p95 after cutover.

## 7. Common mistakes

* Nghĩ slot swap = zero-risk deployment.
* Database destructive migration cùng release với code mới.
* Không đánh dấu settings nào phải sticky.
* Health check chỉ trả 200 hard-coded nên warm-up “pass” dù dependency/config sai.
* Rollback code nhưng schema đã irreversibly drop dữ liệu cũ.

## 8. Alternatives

Blue-Green ở Kubernetes/Container Apps cho control tương tự ở platform khác.

Canary rollout giảm blast radius bằng traffic percentage nhưng phức tạp hơn, đặc biệt với state/session/schema.

## 9. Trade-offs

### Advantages

* Warm deployment trước cutover.
* Rollback nhanh hơn direct deployment.
* Smoke test version thật trên platform thật.

### Costs / Risks

* Slot/config management thêm complexity.
* Database/external contract vẫn phải backward compatible.
* Cost/runtime resources có thể tăng tùy plan và architecture.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu staging slot là running deployment target riêng, không phải chỉ folder.

### Middle

Biết pipeline deploy/warm/smoke/swap và inspect slot settings.

### Senior

Thiết kế schema/config backward compatibility và rollback verification.

### Technical Lead / Architect

Chọn deployment strategy dựa trên release risk/SLO và bảo đảm application, database, messaging contracts cùng có rollback story.

## 11. Key takeaway

* Slot giúp code cutover an toàn hơn nhưng không thay thế migration design.
* Rollback chỉ thật sự tồn tại khi schema/contracts còn compatible.
* Health validation phải phản ánh readiness thực tế.

# 9. Contract testing cho third-party API integration: phát hiện breaking contract trước Production mà không mock mất những rủi ro quan trọng

## 1. What is it?

Contract testing kiểm tra assumptions tại boundary giữa consumer và provider: endpoint, fields, types, required/optional semantics, status codes và đôi khi headers/protocol behavior.

Với third-party APIs, mục tiêu không phải chứng minh provider “đúng”, mà là chứng minh integration assumptions của ta vẫn khớp provider contract mà application phụ thuộc.

## 2. Why does it exist?

Unit test kiểu này rất dễ pass mãi mãi:

```csharp
mock.Setup(x => x.GetCustomerAsync(...))
    .ReturnsAsync(expectedCustomer);
```

Mock do chính team viết sẽ trả đúng shape mà code mong đợi, kể cả khi real provider đã đổi field từ nullable sang missing, status code từ 404 sang 200-empty, hoặc date format thay đổi.

Contract testing đặt evidence gần external boundary hơn.

## 3. How does it work?

Có nhiều mức:

```text
Consumer unit tests
      ↓
Recorded/schema contract tests
      ↓
Provider sandbox integration tests
      ↓
Production synthetic/telemetry
```

Không có một loại test nào thay thế toàn bộ loại khác.

Consumer-driven contract mạnh nhất khi provider do team khác trong cùng organization hỗ trợ contract broker/workflow. Với public third-party provider, schema/sample/sandbox tests thường thực tế hơn.

## 4. Practical implementation

Ví dụ DTO intentionally tolerant:

```csharp
public sealed record ProviderCustomerResponse(
    string Id,
    string? DisplayName,
    string Status);
```

Integration test gọi sandbox/test server real contract nếu provider cho phép:

```csharp
[Fact]
public async Task Customer_response_matches_supported_contract()
{
    var response = await _client.GetAsync("/v1/customers/test-customer");

    response.EnsureSuccessStatusCode();

    var json = await response.Content.ReadAsStringAsync();
    var model = JsonSerializer.Deserialize<ProviderCustomerResponse>(json);

    Assert.NotNull(model);
    Assert.False(string.IsNullOrWhiteSpace(model.Id));
    Assert.Contains(model.Status, new[] { "active", "inactive" });
}
```

Test phải validate assumptions meaningful, không snapshot toàn JSON một cách brittle.

## 5. Real production scenario

Payment provider thêm enum value `pending_review`. Application deserialize vào strict enum rồi throw vì chỉ biết `approved/rejected`.

Unit tests vẫn xanh vì mocks chỉ trả hai values cũ. Contract/sandbox test chạy hàng ngày phát hiện value mới trước khi traffic Production chạm path đó.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment không đổi nhưng external integration 5xx tăng.

**Evidence** → raw sanitized response chứa field/value mới; provider status page không có outage.

**Hypothesis** → contract drift.

**Diagnosis** → compare response với supported schema/test fixture; correlate provider API version/changelog nếu có.

**Fix** → tolerant parsing/version pinning/adapter update; thêm regression contract test.

**Verification** → sandbox/recorded contract + targeted Production synthetic pass.

## 7. Common mistakes

* Mock toàn provider client và coi đó là integration coverage.
* Snapshot exact JSON khiến harmless field addition làm build fail.
* Contract test dùng Production real customer/payment data.
* Test sandbox nhưng assume sandbox behavior giống Production 100%.
* Không log provider correlation/request ID nên support investigation khó khăn.

## 8. Alternatives

Schema validation từ OpenAPI/JSON Schema có thể phát hiện structural drift nhưng không cover behavioral semantics.

End-to-end tests cover nhiều hơn nhưng chậm, flaky và khó cô lập root cause.

## 9. Trade-offs

### Advantages

* Phát hiện boundary assumptions sai sớm.
* Giảm false confidence từ self-authored mocks.
* Giúp adapter layer có explicit supported contract.

### Costs / Risks

* Sandbox/test dependency có thể flaky/rate-limited.
* Contract maintenance cần ownership.
* Quá strict tạo noise; quá loose không bảo vệ gì.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mock không chứng minh external API thật vẫn có cùng behavior.

### Middle

Biết viết integration/contract tests cho fields/status/semantics mà code phụ thuộc.

### Senior

Thiết kế tolerant adapter, test pyramid và failure evidence cho external dependency.

### Technical Lead / Architect

Xác định provider risk tier, compatibility strategy, version pinning, fallback và contract-monitoring ownership.

## 11. Key takeaway

* Mock chỉ phản ánh assumption của ta; contract test kiểm tra boundary thực hơn.
* Test contract nên bảo vệ assumptions quan trọng, không freeze toàn payload.
* Third-party dependency cần observability và compatibility strategy, không chỉ SDK wrapper.

# 10. OpenAI Structured Outputs: dùng schema để giảm parsing uncertainty nhưng vẫn giữ validation và authorization trong deterministic application logic

## 1. What is it?

Structured Outputs cho phép yêu cầu model trả dữ liệu theo một schema có cấu trúc thay vì free-form text mà application phải tự regex/parse một cách mong manh.

Mental model:

```text
Unstructured LLM text
    ↓ hard to parse reliably

Schema-constrained output
    ↓
Typed application object
    ↓
Deterministic validation/business logic
```

Schema constraint cải thiện interface reliability, nhưng không biến nội dung model sinh ra thành fact hoặc authorized decision.

## 2. Why does it exist?

Application integration cần machine-readable data. Prompt kiểu “hãy trả JSON và đừng thêm markdown” không phải protocol guarantee đủ mạnh cho production workflows.

Structured output giảm class lỗi như:

* missing field
* wrong data type
* extra prose quanh JSON
* inconsistent enum shape

Nhưng semantic correctness vẫn cần evaluation/validation.

## 3. How does it work?

Application định nghĩa schema, model generation bị constrained để output conform shape. Sau đó application deserialize và thực hiện deterministic checks.

```text
User input
  ↓
LLM + schema
  ↓
{ action, documentId, confidence }
  ↓
validate values
  ↓
authorization policy
  ↓
optional tool execution
```

Quan trọng: schema nói `documentId` là string không có nghĩa document đó tồn tại hoặc user được quyền truy cập.

## 4. Practical implementation

Ví dụ conceptual C# model:

```csharp
public sealed record TicketClassification(
    string Category,
    string Priority,
    string Summary);
```

Sau khi nhận structured response:

```csharp
var result = await classifier.ClassifyAsync(ticketText, cancellationToken);

if (!AllowedCategories.Contains(result.Category))
    throw new InvalidOperationException("Unsupported category");

if (!AllowedPriorities.Contains(result.Priority))
    throw new InvalidOperationException("Unsupported priority");

await ticketService.ApplyClassificationAsync(
    ticketId,
    result.Category,
    result.Priority,
    cancellationToken);
```

Nếu action có security impact:

```csharp
if (!await authorization.CanModifyTicketAsync(user, ticketId, cancellationToken))
    return Results.Forbid();
```

Authorization không được delegate cho model output.

## 5. Real production scenario

Support platform dùng LLM để phân loại ticket và đề xuất routing. Free-form JSON trước đây thỉnh thoảng có markdown fence hoặc priority value ngoài supported set, làm parser fail và queue backlog.

Structured Outputs loại phần lớn shape failures. Tuy nhiên team vẫn giữ deterministic allowlist và business validation để model không thể route ticket vào internal restricted queue chỉ vì prompt/input manipulation.

## 6. Failure scenario & troubleshooting

**Symptom** → JSON luôn parse được nhưng business routing vẫn sai ở một số categories.

**Evidence** → schema-valid outputs có semantic misclassification; evaluation dataset cho thấy precision thấp trên multilingual tickets.

**Hypothesis** → team đã giải quyết serialization reliability nhưng chưa giải quyết model quality.

**Diagnosis** → offline eval theo category, prompt/context inspection, representative failure examples.

**Fix** → cải thiện instructions/context/examples/model selection; thêm deterministic fallback/threshold/human review khi risk cao.

**Verification** → rerun eval và Production shadow metrics trước full rollout.

## 7. Common mistakes

* Nghĩ schema-valid = factually correct.
* Cho model trả `isAuthorized: true` rồi dùng trực tiếp.
* Dùng structured output nhưng không version schema/application contract.
* Không có eval dataset; chỉ test vài prompts thủ công.
* Retry mọi bad semantic result như network error, làm tăng token cost mà không cải thiện chất lượng.

## 8. Alternatives

Function/Tool Calling phù hợp khi model cần chọn operation để application thực thi, nhưng tool arguments vẫn phải validate/authorize.

Nếu bài toán là deterministic classification theo rules rõ ràng, code/rule engine có thể đơn giản, rẻ và predictable hơn LLM.

## 9. Trade-offs

### Advantages

* Machine-readable contract ổn định hơn free-form prompting.
* Giảm parser branching và malformed-response handling.
* Dễ gắn typed validation/evaluation pipeline.

### Costs / Risks

* Không giải quyết hallucination/semantic error.
* Schema evolution cần compatibility planning.
* Token/latency/cost và model availability vẫn là distributed dependency concerns.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu structured output làm response shape predictable hơn, không làm model deterministic hoàn toàn.

### Middle

Biết deserialize, validate enums/ranges và handle API timeout/rate-limit errors.

### Senior

Thiết kế evals, fallback, observability, prompt-injection boundary và schema versioning.

### Technical Lead / Architect

Quyết định phần nào nên do LLM đề xuất và phần nào bắt buộc deterministic; cân bằng quality, latency, cost, security và operational dependency.

## 11. Key takeaway

* Structured Outputs giải quyết contract shape tốt hơn free-form JSON prompting.
* Schema conformance không đồng nghĩa semantic correctness.
* Authorization, financial correctness và security-critical checks phải nằm trong deterministic code.
