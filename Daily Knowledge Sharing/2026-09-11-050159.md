# 1. C# `ValueTask`: giảm allocation có điều kiện nhưng dễ tạo API khó dùng và bug subtle nếu áp dụng sai

## 1. What is it?

`ValueTask<T>` là một awaitable value type có thể đại diện cho kết quả đã có sẵn hoặc cho một asynchronous operation chưa hoàn tất. Mental model quan trọng là: `Task<T>` luôn là một object đại diện cho operation; `ValueTask<T>` là một wrapper có thể tránh tạo `Task` mới trong một số hot path mà phần lớn lời gọi hoàn thành synchronously.

Nó không phải “Task nhanh hơn”. Nó là một optimization tool với contract sử dụng phức tạp hơn.

## 2. Why does it exist?

Một số API như parser, buffer reader, pipeline hoặc cache có xác suất rất cao trả kết quả ngay. Nếu mỗi call vẫn tạo một `Task<T>`, hàng triệu calls có thể tạo allocation và GC pressure không cần thiết.

`ValueTask<T>` tồn tại để giảm allocation đó khi synchronous completion là common path.

## 3. How does it work?

Một `ValueTask<T>` có thể chứa trực tiếp `T`, wrap một `Task<T>`, hoặc wrap một `IValueTaskSource<T>` reusable source.

```text
Call
 ├─ result đã có      → ValueTask<T>(T)
 └─ phải async        → ValueTask<T>(Task<T>)
```

Do nó có thể đại diện cho reusable source, consumer không được tùy ý await nhiều lần, gọi `.Result` rồi await lại, hoặc convert lặp lại mà không hiểu contract.

## 4. Practical implementation

Một cache reader có synchronous hit path:

```csharp
public ValueTask<UserProfile?> GetAsync(
    Guid userId,
    CancellationToken cancellationToken)
{
    if (_memoryCache.TryGetValue(userId, out UserProfile? profile))
        return ValueTask.FromResult(profile);

    return new ValueTask<UserProfile?>(
        LoadFromDatabaseAsync(userId, cancellationToken));
}
```

Consumer vẫn dùng bình thường:

```csharp
var profile = await profileStore.GetAsync(userId, ct);
```

Đừng dùng `ValueTask` chỉ vì method có chữ `Async`.

## 5. Real production scenario

Một high-throughput ASP.NET Core gateway gọi local metadata cache hàng chục nghìn lần/giây. 97% requests là cache hit trong memory. Profiling cho thấy số lượng short-lived `Task<T>` đáng kể.

Sau khi đo được allocation là bottleneck thực sự, team đổi riêng hot API sang `ValueTask<T>`. Allocation giảm mà không thay architecture.

## 6. Failure scenario & troubleshooting

**Symptom** → code hoạt động ở môi trường này nhưng lỗi hoặc hành vi lạ khi await cùng `ValueTask` nhiều lần.

**Evidence** → consumer lưu `ValueTask` rồi await ở nhiều nơi hoặc dùng `.AsTask()` nhiều lần.

**Hypothesis** → caller vi phạm single-consumption semantics của underlying source.

**Diagnosis** → kiểm tra call sites, đặc biệt nơi cache awaitable thay vì kết quả.

**Fix** → await một lần; nếu thật sự cần multi-await semantics, convert một lần sang `Task<T>` và giữ task đó.

**Verification** → concurrency tests và allocation benchmark.

## 7. Common mistakes

* Thay toàn bộ `Task<T>` bằng `ValueTask<T>` mà không benchmark.
* Trả `ValueTask<T>` cho API public rộng, tăng cognitive cost cho consumer.
* Await cùng instance nhiều lần.
* Dùng `ValueTask` cho operation gần như luôn asynchronous; khi đó complexity tăng nhưng allocation benefit gần như không có.

## 8. Alternatives

`Task<T>` vẫn là default tốt nhất cho hầu hết business/application code vì semantics đơn giản, dễ compose và dễ cache.

Object pooling hoặc `ArrayPool<T>` giải quyết loại allocation khác; chúng không thay thế `ValueTask`.

## 9. Trade-offs

### Advantages

Giảm allocation trong hot path có tỷ lệ synchronous completion cao.

### Costs / Risks

API semantics phức tạp hơn, struct lớn hơn reference, misuse dễ xảy ra, profiling/debugging khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task<T>` là lựa chọn mặc định; `ValueTask<T>` không phải bản nâng cấp tự động.

### Middle

Biết dùng/await đúng và không reuse tùy tiện.

### Senior

Chỉ áp dụng sau profiling, hiểu synchronous completion ratio và allocation impact.

### Technical Lead / Architect

Giữ `ValueTask` ở performance-critical boundary thay vì lan toàn codebase vì micro-optimization.

## 11. Key takeaway

* `ValueTask` là optimization, không phải coding style.
* Chỉ đáng dùng khi synchronous completion thường xuyên và allocation đã được đo.
* Simplicity của `Task` thường có giá trị hơn vài allocation chưa chứng minh là bottleneck.

# 2. ASP.NET Core rate limiting: bảo vệ dependency và fairness thay vì chỉ “chặn bot”

## 1. What is it?

Rate limiting giới hạn số lượng hoặc tốc độ request một caller được phép gửi trong một khoảng thời gian hoặc theo capacity model. Nó có thể áp dụng theo IP, user, tenant, API key, route hoặc business dimension.

Mental model:

```text
Client
  ↓
Rate limiter
  ├─ permit → endpoint
  └─ reject → 429 Too Many Requests
```

## 2. Why does it exist?

Backend không có capacity vô hạn. Một caller có thể vô tình hoặc cố ý chiếm toàn bộ connection pool, downstream quota hay CPU.

Rate limiting tạo một admission-control boundary trước khi expensive work xảy ra. Nó bảo vệ fairness, availability và downstream systems.

## 3. How does it work?

Các algorithm phổ biến gồm fixed window, sliding window, token bucket và concurrency limiter.

Token bucket cho phép burst nhỏ nhưng kiểm soát average rate:

```text
bucket capacity = 100
refill = 20 tokens/s
mỗi request = 1 token
```

Nếu hết token, request bị từ chối hoặc queue tùy policy.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("per-user", httpContext =>
    {
        var userId = httpContext.User.FindFirst("sub")?.Value ?? "anonymous";

        return RateLimitPartition.GetTokenBucketLimiter(
            userId,
            _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 20,
                ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                AutoReplenishment = true,
                QueueLimit = 0
            });
    });

    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});
```

Endpoint:

```csharp
app.MapPost("/api/search", HandleSearch)
   .RequireRateLimiting("per-user");
```

## 5. Real production scenario

Search API gọi Elasticsearch. Một tenant import dữ liệu rồi chạy polling 200 requests/second, trong khi các tenant khác chỉ 5–10 requests/second.

Không có limiter, hot tenant làm saturate search cluster và p99 toàn hệ thống tăng. Per-tenant token bucket giữ burst hợp lý nhưng bảo vệ shared capacity.

## 6. Failure scenario & troubleshooting

**Symptom** → downstream latency tăng và 5xx xuất hiện dù tổng traffic không quá lớn.

**Evidence** → một tenant chiếm phần lớn requests; Elasticsearch thread pool queue tăng.

**Hypothesis** → thiếu fairness/admission control.

**Diagnosis** → breakdown traffic theo tenant/API key, correlate với dependency saturation.

**Fix** → rate-limit ở boundary phù hợp, trả 429 cùng retry guidance, có quota riêng cho privileged flows nếu cần.

**Verification** → load test mixed tenants; noisy tenant bị giới hạn nhưng normal tenants giữ SLO.

## 7. Common mistakes

* Chỉ limit theo IP trong SaaS phía sau NAT/proxy, vô tình gom nhiều users thành một identity.
* Queue quá nhiều requests thay vì reject sớm, biến limiter thành nơi tích latency.
* Retry 429 ngay lập tức, tạo retry storm.
* Chỉ đặt limiter ở edge nhưng downstream internal API vẫn có thể bị một service khác flood.

## 8. Alternatives

Concurrency limiter hữu ích khi bottleneck là số in-flight operations hơn là requests/second.

Queue-based load leveling phù hợp cho work không cần synchronous response.

API gateway rate limiting có thể centralize policy nhưng application vẫn cần hiểu business identity và downstream capacity.

## 9. Trade-offs

### Advantages

Bảo vệ shared resources, cải thiện fairness, giảm blast radius của abusive hoặc buggy clients.

### Costs / Risks

Policy sai có thể reject legitimate traffic; distributed limiter cần shared state hoặc approximation; quota design trở thành product concern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu 429 nghĩa là server chủ động giới hạn request rate.

### Middle

Biết cấu hình limiter và key theo caller phù hợp.

### Senior

Phân biệt throughput limit với concurrency limit, thiết kế retry semantics và observability.

### Technical Lead / Architect

Định nghĩa capacity budget theo tenant/service và quyết định layer nào phải enforce để bảo vệ dependency thực sự.

## 11. Key takeaway

* Rate limiting là reliability mechanism, không chỉ anti-abuse.
* Key partition phải phản ánh identity/business boundary thật.
* Reject sớm thường tốt hơn queue vô hạn.

# 3. EF Core split queries: tránh cartesian explosion khi `Include` nhiều collection nhưng hiểu rõ consistency trade-off

## 1. What is it?

Split query cho phép EF Core tải object graph bằng nhiều SQL statements thay vì một JOIN lớn khi query có nhiều collection navigations.

```text
Single query:
Orders JOIN Items JOIN Payments

Split query:
SELECT Orders
SELECT Items WHERE OrderId IN (...)
SELECT Payments WHERE OrderId IN (...)
```

## 2. Why does it exist?

Khi JOIN nhiều one-to-many collections cùng cấp, số row có thể nhân chéo. Một order có 20 items và 10 payments có thể tạo 200 joined rows cho chỉ một order.

Điều này tăng network payload, materialization work và memory usage.

## 3. How does it work?

`AsSplitQuery()` yêu cầu EF Core phát nhiều query và sau đó fix-up relationships trong memory.

```csharp
var orders = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .ToListAsync(ct);
```

Nó giảm duplicated rows nhưng tăng database round trips và mở một consistency window giữa các statements.

## 4. Practical implementation

Nếu API chỉ cần summary, projection thường tốt hơn cả `Include`:

```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Select(x => new OrderSummary(
        x.Id,
        x.Items.Count,
        x.Payments.Sum(p => p.Amount)))
    .ToListAsync(ct);
```

Nếu thật sự cần aggregate graph để business processing:

```csharp
var order = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .SingleAsync(x => x.Id == id, ct);
```

## 5. Real production scenario

Admin endpoint tải 100 orders, mỗi order có trung bình 30 items và 8 audit events. Single query tạo lượng rows rất lớn, p95 tăng và app allocation spike.

Split query giảm payload đáng kể. Sau đó team còn tối ưu thêm bằng projection cho read-only screen.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint chậm, SQL duration vừa phải nhưng response materialization/network lớn.

**Evidence** → resultset row count cao bất thường, duplicated parent columns, memory allocation tăng.

**Hypothesis** → cartesian explosion từ multiple collection includes.

**Diagnosis** → inspect generated SQL và actual returned row count.

**Fix** → projection hoặc `AsSplitQuery()` tùy use case.

**Verification** → đo SQL rows, bytes transferred, allocations và endpoint p95 trước/sau.

## 7. Common mistakes

* Mặc định mọi query phức tạp đều dùng `AsSplitQuery()` mà không đo.
* Dùng `Include` cho API DTO dù chỉ cần vài fields.
* Quên rằng nhiều statements có thể thấy các committed states khác nhau nếu data đổi giữa chúng.
* Không xem số round trips khi database ở network xa.

## 8. Alternatives

Projection-first là lựa chọn tốt nhất cho read models.

Explicit loading hữu ích khi quyết định load relation phụ thuộc runtime logic nhưng dễ tạo N+1 nếu dùng trong loop.

Single query phù hợp khi graph nhỏ hoặc cần một SQL snapshot đơn giản hơn.

## 9. Trade-offs

### Advantages

Giảm cartesian duplication, memory và bandwidth cho graph nhiều collections.

### Costs / Risks

Tăng round trips và có consistency window giữa queries; vẫn có thể load quá nhiều dữ liệu nếu graph lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` có thể làm SQL JOIN và nhân số rows.

### Middle

Biết đọc generated SQL và thử `AsSplitQuery()` đúng chỗ.

### Senior

Đo materialization/network cost, ưu tiên projection và hiểu consistency trade-off.

### Technical Lead / Architect

Định nghĩa read model boundary; không để domain graph trở thành API data-access contract mặc định.

## 11. Key takeaway

* `Include` nhiều collection có thể tạo cartesian explosion.
* Split query giải quyết duplication nhưng đổi lấy round trips và consistency window.
* Read API thường nên bắt đầu từ projection, không phải entity graph.

# 4. PostgreSQL MVCC và vacuum: vì sao reader ít block writer nhưng dead tuples vẫn có giá phải trả

## 1. What is it?

PostgreSQL dùng MVCC (Multi-Version Concurrency Control) để nhiều transaction có thể thấy các version dữ liệu khác nhau theo snapshot. `UPDATE` thường tạo tuple version mới thay vì sửa in-place theo cách đơn giản.

Version cũ không biến mất ngay; khi không transaction nào cần chúng nữa, vacuum có thể reclaim chúng cho reuse.

## 2. Why does it exist?

Nếu reader và writer luôn phải khóa lẫn nhau, concurrency của OLTP system sẽ giảm mạnh. MVCC cho phép reader thường đọc snapshot ổn định trong khi writer tạo version mới.

Cái giá là storage phải quản lý old versions.

## 3. How does it work?

Simplified flow:

```text
Row v1 visible to old snapshot
UPDATE
Row v2 visible to newer snapshot
v1 trở thành dead tuple khi không còn snapshot cần
VACUUM → đánh dấu space reusable
```

Autovacuum chạy dựa trên thresholds và statistics. Vacuum không phải lúc nào cũng trả disk ngay cho OS; nó chủ yếu làm page space reusable.

## 4. Practical implementation

Theo dõi tables có dead tuples:

```sql
SELECT relname,
       n_live_tup,
       n_dead_tup,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Một high-update table có thể cần tuning autovacuum theo table thay vì global config.

## 5. Real production scenario

Job queue table được update status hàng triệu lần/ngày. Query bắt đầu chậm dù index vẫn tồn tại. Table/index bloat tăng và autovacuum không theo kịp churn.

Root cause không phải “PostgreSQL lock kém” mà là MVCC version churn + vacuum lag.

## 6. Failure scenario & troubleshooting

**Symptom** → table size tăng, index scans đọc nhiều pages hơn, latency tăng dần.

**Evidence** → `n_dead_tup` cao, autovacuum chạy ít hoặc không hoàn tất, long-running transaction tồn tại.

**Hypothesis** → dead tuple accumulation/bloat.

**Diagnosis** → kiểm tra autovacuum activity, transaction age, update pattern và index/table sizes.

**Fix** → kết thúc long transactions, tune autovacuum, giảm churn; cân nhắc maintenance operation khi cần.

**Verification** → dead tuples ổn định hơn, vacuum cadence phù hợp và query I/O giảm.

## 7. Common mistakes

* Cho rằng MVCC nghĩa là “không có lock”. Writers vẫn có thể conflict.
* Disable autovacuum để giảm I/O mà không hiểu hậu quả.
* Giữ transaction mở rất lâu; snapshot cũ có thể ngăn reclaim versions.
* Chỉ nhìn row count mà bỏ qua table/index bloat.

## 8. Alternatives

SQL Server có row-versioning modes nhưng implementation/storage khác. Pessimistic locking engines có behavior khác và có thể phù hợp workload khác.

Không có “database concurrency model tốt nhất” độc lập với workload.

## 9. Trade-offs

### Advantages

Reader/writer concurrency tốt và snapshot semantics mạnh.

### Costs / Risks

Dead tuples, vacuum overhead, bloat và transaction-age management trở thành operational concerns.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu update có thể tạo row version mới.

### Middle

Biết xem `pg_stat_user_tables`, autovacuum và long transactions.

### Senior

Liên hệ MVCC với bloat, I/O, transaction lifetime và latency.

### Technical Lead / Architect

Thiết kế retention/update pattern và operational monitoring phù hợp với workload, không chỉ chọn PostgreSQL vì feature checklist.

## 11. Key takeaway

* MVCC giảm nhiều reader-writer conflicts nhưng không miễn phí.
* Dead tuples và vacuum là một phần của normal PostgreSQL operation.
* Long-running transaction có thể gây hậu quả storage/performance ngoài phạm vi transaction đó.

# 5. Redis cache penetration: bảo vệ database trước các request cho key không tồn tại mà không cache dữ liệu sai

## 1. What is it?

Cache penetration xảy ra khi requests liên tục hỏi dữ liệu không tồn tại. Vì cache miss, mọi request đi xuống database; database cũng trả “not found”, nhưng nếu kết quả âm không được cache thì lần sau lại lặp lại.

```text
GET user:999999
Redis miss
DB miss
repeat × 10000
```

## 2. Why does it exist?

Cache-aside thường chỉ cache object tồn tại. Điều này tốt cho correctness đơn giản, nhưng tạo đường tắt để invalid IDs bypass cache hoàn toàn.

Nguồn traffic có thể là bot, client bug hoặc random probing.

## 3. How does it work?

Một kỹ thuật là negative caching: cache marker “not found” với TTL ngắn.

```text
Redis key: user:999999
value: __NULL__
TTL: 30s
```

Subsequent requests không hit database trong khoảng TTL.

## 4. Practical implementation

```csharp
public async Task<UserDto?> GetUserAsync(Guid id, CancellationToken ct)
{
    var key = $"user:{id}";
    var cached = await redis.StringGetAsync(key);

    if (cached == "__NULL__")
        return null;

    if (cached.HasValue)
        return JsonSerializer.Deserialize<UserDto>(cached!);

    var user = await db.Users
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new UserDto(x.Id, x.Name))
        .SingleOrDefaultAsync(ct);

    if (user is null)
    {
        await redis.StringSetAsync(key, "__NULL__", TimeSpan.FromSeconds(30));
        return null;
    }

    await redis.StringSetAsync(
        key,
        JsonSerializer.Serialize(user),
        TimeSpan.FromMinutes(5));

    return user;
}
```

## 5. Real production scenario

Public product endpoint nhận hàng triệu requests với IDs được crawl tự động. 40% IDs không tồn tại. Redis hit ratio trông thấp và SQL CPU tăng.

Negative caching giảm repeated misses đáng kể mà không cần tăng database tier.

## 6. Failure scenario & troubleshooting

**Symptom** → database QPS cao nhưng phần lớn queries trả 0 rows.

**Evidence** → top keys/URLs cho thấy cùng invalid IDs lặp lại; Redis miss rate cao.

**Hypothesis** → cache penetration.

**Diagnosis** → correlate not-found response rate với DB query pattern.

**Fix** → short-lived negative caching, validation/rate limiting và monitoring.

**Verification** → DB queries cho repeated invalid IDs giảm mạnh.

## 7. Common mistakes

* Cache “not found” quá lâu; object được tạo ngay sau đó nhưng user vẫn thấy 404 stale.
* Dùng cùng marker với real serialized value, gây ambiguity.
* Negative-cache mọi transient DB error như “not found”.
* Bỏ qua rate limiting cho attacker tạo random unique IDs, khiến mỗi key chỉ miss một lần nhưng vẫn flood DB/cache.

## 8. Alternatives

Bloom filter có thể chặn nhiều impossible keys trước cache/database, hữu ích ở scale rất lớn nhưng có false positives và lifecycle complexity.

Rate limiting/validation giải quyết abusive traffic; không thay thế negative caching cho legitimate repeated misses.

## 9. Trade-offs

### Advantages

Giảm DB load từ repeated misses và cải thiện latency cho not-found responses.

### Costs / Risks

Introduces stale-negative window và thêm key volume trong Redis.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss cho object không tồn tại vẫn có cost.

### Middle

Biết negative cache với TTL ngắn và phân biệt not-found với error.

### Senior

Kết hợp metrics, TTL, invalidation và abuse protection.

### Technical Lead / Architect

Quyết định liệu vấn đề cần negative caching, rate limiting, Bloom filter hay đơn giản là database đủ nhanh.

## 11. Key takeaway

* “Không có dữ liệu” cũng là một kết quả có thể cache có kiểm soát.
* Negative TTL phải ngắn và phù hợp business freshness.
* Random-key attacks cần admission control; negative cache không phải shield tuyệt đối.

# 6. DDD Aggregate boundary: đặt invariant và transaction boundary đúng thay vì gom entity theo quan hệ database

## 1. What is it?

Aggregate là một consistency boundary trong domain model. Aggregate Root là entry point duy nhất để thay đổi state bên trong aggregate và giữ business invariants.

Nó không đồng nghĩa với “một parent table và tất cả child tables có foreign key”.

## 2. Why does it exist?

Business rules thường cần một nhóm state thay đổi atomically. Nếu mọi entity đều được sửa trực tiếp từ bất kỳ nơi nào, invariants dễ bị phá.

Ví dụ Order cần đảm bảo:

```text
Total = sum(OrderLines)
Cannot add line after Order is Submitted
```

Để enforce chắc chắn, những state liên quan nên thuộc cùng consistency boundary.

## 3. How does it work?

Application load Aggregate Root, gọi behavior method, rồi persist transaction.

```text
API
 ↓
Application Service
 ↓
Order Aggregate Root
 ├─ OrderLine
 └─ invariant checks
 ↓
Repository/DbContext
 ↓
transaction commit
```

External aggregate khác nên được tham chiếu bằng ID thay vì object graph nếu không cùng invariant boundary.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = new();

    public Guid Id { get; private set; }
    public OrderStatus Status { get; private set; }
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void AddLine(Guid productId, int quantity, decimal unitPrice)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Submitted order cannot be modified.");

        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(nameof(quantity));

        _lines.Add(new OrderLine(productId, quantity, unitPrice));
    }
}
```

Application service không sửa `_lines` trực tiếp.

## 5. Real production scenario

Team modeling PurchaseOrder aggregate chứa supplier, approvals, invoices, receipts, documents và audit history chỉ vì tất cả liên quan PO.

Mỗi command phải load graph khổng lồ, conflicts tăng và transaction dài. Sau review, team tách consistency boundaries: PurchaseOrder, Invoice, Receipt thành aggregates riêng, liên kết bằng IDs và events/workflow.

## 6. Failure scenario & troubleshooting

**Symptom** → update nhỏ cần load hàng nghìn rows; concurrency conflicts thường xuyên.

**Evidence** → aggregate graph lớn, nhiều unrelated collections cùng được tracked.

**Hypothesis** → aggregate boundary được chọn theo relational relationship thay vì invariant.

**Diagnosis** → hỏi “state nào thật sự phải atomic cùng nhau?”

**Fix** → thu nhỏ aggregate, chuyển cross-boundary coordination sang application workflow/eventual consistency nơi business cho phép.

**Verification** → transaction size giảm, conflicts giảm, invariants vẫn được test và giữ đúng.

## 7. Common mistakes

* Một aggregate cho cả bounded context.
* Một table = một aggregate như rule cứng.
* Dùng public setters rồi kỳ vọng application layer nhớ mọi invariant.
* Dùng domain event để né một invariant thật sự cần atomic transaction.

## 8. Alternatives

Anemic model + application services có thể đủ cho CRUD-centric domain ít business rules.

Database constraints vẫn cần cho invariants dữ liệu cơ bản và race conditions; domain model không thay thế database integrity.

## 9. Trade-offs

### Advantages

Invariants rõ, transaction boundary rõ, giảm coupling giữa domain changes.

### Costs / Risks

Boundary sai có thể tạo aggregate quá lớn hoặc eventual consistency không cần thiết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Aggregate Root kiểm soát thay đổi trong một consistency boundary.

### Middle

Biết đặt behavior và invariants vào domain model thay vì rải ở controller.

### Senior

Phân biệt relational association với transactional consistency requirement.

### Technical Lead / Architect

Thiết kế aggregates dựa trên invariants, contention, transaction size và business tolerance cho eventual consistency.

## 11. Key takeaway

* Aggregate là consistency boundary, không phải object graph tiện tay.
* Giữ aggregate nhỏ nhất có thể nhưng đủ bảo vệ invariant.
* Cross-aggregate workflow chỉ nên eventual-consistent khi business cho phép.

# 7. Azure Functions cold start và concurrency: serverless scale không miễn phí về latency, downstream pressure và idempotency

## 1. What is it?

Azure Functions cung cấp event-driven/serverless compute. Platform có thể scale instances theo workload. Cold start là latency khi một instance mới cần khởi tạo runtime, app dependencies và code trước khi xử lý invocation.

Concurrency là số invocations có thể chạy đồng thời trên một instance; scale-out tăng tổng concurrency bằng nhiều instances.

## 2. Why does it exist?

Serverless tối ưu cho workload biến động và event-driven processing: trả tiền/scale gần với demand thay vì luôn giữ servers cố định.

Nhưng “auto scale” không có nghĩa downstream cũng auto scale hoặc latency luôn bằng 0.

## 3. How does it work?

Simplified queue-trigger flow:

```text
Service Bus backlog tăng
  ↓
Functions scale controller
  ↓
new instances
  ↓
cold initialization
  ↓
more concurrent consumers
  ↓
SQL / external API chịu tải lớn hơn
```

Nếu mỗi function instance mở nhiều concurrent DB operations, scale-out nhanh có thể làm connection pool/database quá tải.

## 4. Practical implementation

Function cần idempotent handler và tránh heavy startup work không cần thiết.

```csharp
public sealed class ProcessInvoice
{
    private readonly InvoiceProcessor _processor;

    public ProcessInvoice(InvoiceProcessor processor)
        => _processor = processor;

    [Function("ProcessInvoice")]
    public async Task Run(
        [ServiceBusTrigger("invoices", Connection = "ServiceBus")]
        ServiceBusReceivedMessage message,
        CancellationToken ct)
    {
        await _processor.ProcessAsync(message.MessageId, message.Body, ct);
    }
}
```

Idempotency key có thể là `MessageId` kết hợp business identity.

## 5. Real production scenario

Một promotion tạo 200,000 order events trong vài phút. Functions scale nhanh từ vài instances lên nhiều instances. Service Bus backlog giảm, nhưng SQL connections tăng đột biến và database latency tăng gấp 5.

Bottleneck đã di chuyển từ consumer capacity sang database capacity.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog lúc đầu giảm rồi tăng lại; SQL timeout tăng khi Functions scale-out.

**Evidence** → instance count và DB concurrent connections tăng cùng thời điểm.

**Hypothesis** → uncontrolled downstream pressure.

**Diagnosis** → correlate Function concurrency, scale events, DB pool/DTU/vCore metrics.

**Fix** → tune concurrency, batch hợp lý, queue load leveling, backoff và database capacity.

**Verification** → peak replay test; backlog drain ổn định mà dependency không vượt SLO.

## 7. Common mistakes

* Giả định scale-out luôn cải thiện throughput.
* Không implement idempotency dù trigger có thể redeliver.
* Để startup load secrets/schema/cache quá nặng làm cold start tệ hơn.
* Đưa long-running stateful workflow vào Function đơn giản mà không có orchestration/state strategy.

## 8. Alternatives

Worker Service/Container Apps phù hợp khi cần stable warm capacity, custom concurrency hoặc long-running process.

App Service background worker có thể đơn giản hơn nếu workload gắn chặt một application và scale profile ổn định.

## 9. Trade-offs

### Advantages

Operational simplicity cho event-driven workloads, elastic scale và integration tốt với Azure services.

### Costs / Risks

Cold start, scale unpredictability, downstream pressure, execution/runtime constraints và cost có thể tăng bất ngờ ở high volume.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Function chạy theo trigger và có thể có nhiều instances.

### Middle

Biết viết idempotent handler, cancellation và telemetry.

### Senior

Phân tích scale/concurrency cùng downstream limits và cold-start latency.

### Technical Lead / Architect

Chọn Functions, Worker Service hay Container Apps dựa trên workload shape, latency SLO, control needs và cost model.

## 11. Key takeaway

* Serverless scale chỉ hữu ích nếu downstream chịu được load.
* Cold start là latency characteristic cần đo, không phải lý thuyết.
* Queue-trigger consumer vẫn cần idempotency.

# 8. Blue-Green deployment với backward-compatible database changes: deploy application an toàn khi hai version cùng tồn tại

## 1. What is it?

Blue-Green deployment duy trì hai application environments: version hiện tại và version mới. Traffic được chuyển từ Blue sang Green khi Green vượt health validation.

Database thường là shared state nên không thể coi deployment chỉ là đổi binary. Schema phải tương thích khi Blue và Green cùng sống trong transition window.

## 2. Why does it exist?

Rolling/in-place deployment có thể tạo thời gian hệ thống chạy mixed versions. Nếu migration đổi schema breaking ngay, old app có thể fail trước khi traffic chuyển xong hoặc rollback trở nên bất khả thi.

Blue-Green giảm application rollback time nhưng chỉ an toàn nếu database evolution cũng được thiết kế.

## 3. How does it work?

Expand-Contract flow:

```text
1. Expand schema: add nullable/new columns, new table
2. Deploy Green tương thích cả old/new schema
3. Switch traffic
4. Observe
5. Migrate/backfill data
6. Sau khi Blue không còn cần → Contract old schema
```

Không drop/rename critical column trong cùng release mà old version vẫn có thể chạy.

## 4. Practical implementation

Migration an toàn:

```sql
ALTER TABLE Customers
ADD DisplayName nvarchar(200) NULL;
```

Green code hỗ trợ fallback:

```csharp
var displayName = customer.DisplayName ?? customer.LegacyName;
```

Release sau, sau backfill và xác nhận không còn Blue/old consumers, mới remove legacy field.

## 5. Real production scenario

E-commerce API rename `Customer.FullName` thành `DisplayName`. Nếu migration drop `FullName` trước khi traffic switch hoàn tất, Blue instances bắt đầu throw SQL errors.

Expand-Contract cho phép cả hai versions đọc/ghi trong transition.

## 6. Failure scenario & troubleshooting

**Symptom** → Green healthy nhưng khi switch một phần traffic thì Blue bắt đầu 500 hoặc rollback Green cũng fail.

**Evidence** → SQL “invalid column” sau migration.

**Hypothesis** → schema migration breaking old binary.

**Diagnosis** → map application versions với DB contract expected.

**Fix** → restore compatibility hoặc deploy bridge version; tránh emergency rollback chỉ ở app layer.

**Verification** → run both versions against expanded schema trước production switch.

## 7. Common mistakes

* Gọi Blue-Green là zero-downtime nhưng migration vẫn destructive.
* Chạy backfill lớn trong blocking migration transaction.
* Contract schema ngay sau traffic switch, không để rollback window.
* Không version external contracts/events cùng release.

## 8. Alternatives

Canary deployment giảm blast radius bằng traffic nhỏ trước. Rolling deployment dùng ít duplicate infrastructure hơn nhưng mixed-version window rõ hơn.

Feature flags có thể tách code deployment khỏi feature activation nhưng không thay thế schema compatibility.

## 9. Trade-offs

### Advantages

Fast traffic rollback, production validation trước full cutover và reduced deployment downtime.

### Costs / Risks

Double-environment cost, deployment orchestration và database compatibility discipline cao hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Blue và Green là hai app versions cùng tồn tại trong deployment.

### Middle

Biết viết additive migrations và backward-compatible code.

### Senior

Thiết kế backfill, rollback window, dual-read/write transition khi cần.

### Technical Lead / Architect

Xây release strategy bao gồm app, schema, message contract, caches và external consumers — không chỉ CI/CD pipeline.

## 11. Key takeaway

* Blue-Green không tự giải quyết database compatibility.
* Expand trước, Contract sau khi old version hết lifetime.
* Rollback phải được thiết kế ở data-contract level.

# 9. Playwright integration/E2E testing: kiểm tra user flow thật nhưng tránh biến test suite thành hệ thống flaky đắt đỏ

## 1. What is it?

Playwright điều khiển browser thật để test user flow qua frontend, network và backend integration. Nó đặc biệt hữu ích để bảo vệ critical journeys như login, checkout, approval hoặc document publishing.

E2E test kiểm tra nhiều boundaries cùng lúc, vì vậy confidence cao nhưng diagnosis cost cũng cao hơn unit/integration tests.

## 2. Why does it exist?

Unit tests có thể chứng minh component/service đúng riêng lẻ nhưng không đảm bảo wiring tổng thể đúng: route sai, auth cookie thiếu, API contract lệch hoặc frontend selector không tồn tại.

E2E test bảo vệ behavior mà user thật trải nghiệm.

## 3. How does it work?

```text
Test runner
  ↓
Browser
  ↓
Frontend
  ↓
API
  ↓
Database / dependencies
```

Playwright có auto-waiting cho nhiều actions nên giảm nhu cầu `Thread.Sleep`/fixed delay.

## 4. Practical implementation

```csharp
[Fact]
public async Task User_can_create_project()
{
    using var playwright = await Playwright.CreateAsync();
    await using var browser = await playwright.Chromium.LaunchAsync();
    var page = await browser.NewPageAsync();

    await page.GotoAsync("http://localhost:3000");
    await page.GetByRole(AriaRole.Button, new() { Name = "New project" }).ClickAsync();
    await page.GetByLabel("Title").FillAsync("Migration");
    await page.GetByRole(AriaRole.Button, new() { Name = "Save" }).ClickAsync();

    await Expect(page.GetByText("Migration")).ToBeVisibleAsync();
}
```

Dùng stable semantic locators tốt hơn CSS selector phụ thuộc layout.

## 5. Real production scenario

Backend tests đều pass sau auth refactor, nhưng production login loop xảy ra vì cookie `SameSite`/redirect flow tương tác sai với frontend host.

Một browser-level E2E login test có thể bắt lỗi này trước release vì nó chạy qua real browser behavior.

## 6. Failure scenario & troubleshooting

**Symptom** → E2E suite fail ngẫu nhiên 5–10% dù app đúng.

**Evidence** → failures tập trung ở fixed waits, shared test account hoặc reused database state.

**Hypothesis** → nondeterministic test setup, timing assumption hoặc shared state.

**Diagnosis** → inspect trace/video/network logs, rerun isolated test, xem parallel interference.

**Fix** → deterministic fixture, unique data per test, semantic waits/locators, mock chỉ external unstable dependency khi appropriate.

**Verification** → repeated runs không còn flaky pattern.

## 7. Common mistakes

* Dùng E2E cho mọi branch condition thay vì unit/integration tests.
* `WaitForTimeout(5000)` để “fix flaky”.
* Shared mutable test account/data.
* Assert implementation detail thay vì user-observable behavior.
* Chạy toàn bộ suite serial rồi chấp nhận 40 phút feedback time.

## 8. Alternatives

Integration tests dùng `WebApplicationFactory` nhanh và deterministic hơn cho API/database boundaries.

Unit tests tốt cho business rules và edge cases.

Contract tests phù hợp khi service boundaries thay đổi độc lập.

## 9. Trade-offs

### Advantages

Confidence cao cho critical user journeys và bắt wiring/browser/configuration bugs.

### Costs / Risks

Chậm hơn, setup phức tạp, failure diagnosis khó, dễ flaky nếu test data/timing không deterministic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu E2E test mô phỏng user flow thật.

### Middle

Biết dùng stable locators, fixtures và trace artifacts.

### Senior

Biết chọn đúng test layer cho từng risk và triage flaky tests có bằng chứng.

### Technical Lead / Architect

Thiết kế test portfolio: ít critical E2E, nhiều integration/unit tests, clear ownership và execution budget trong CI.

## 11. Key takeaway

* E2E test nên bảo vệ critical journeys, không thay mọi test layer khác.
* Fixed sleep là dấu hiệu thiết kế test kém.
* Deterministic data và observability của test quan trọng ngang assertion.

# 10. Structured Outputs cho LLM API: ép schema ở transport boundary nhưng không nhầm schema-valid với business-correct

## 1. What is it?

Structured Outputs là cách yêu cầu model trả dữ liệu tuân theo một schema đã định thay vì free-form text. Nó giúp application nhận JSON có shape predictable để parse và validate ở transport boundary.

Mental model:

```text
Prompt + schema
   ↓
LLM
   ↓
Schema-constrained response
   ↓
Application validation
   ↓
Deterministic business logic
```

## 2. Why does it exist?

Free-form model output khó parse ổn định. Prompt kiểu “hãy trả JSON” vẫn có thể sinh sai field, extra text hoặc wrong type.

Structured output giảm lỗi shape nhưng không bảo đảm factual correctness hoặc business validity.

## 3. How does it work?

Application gửi schema mô tả object mong muốn. Model generation bị constrain để tạo response phù hợp schema hỗ trợ.

Ví dụ schema concept:

```json
{
  "type": "object",
  "properties": {
    "priority": { "type": "string", "enum": ["low", "medium", "high"] },
    "reason": { "type": "string" }
  },
  "required": ["priority", "reason"],
  "additionalProperties": false
}
```

Model có thể trả `priority = high` đúng schema nhưng reasoning vẫn sai. Do đó business/security decisions vẫn cần deterministic checks.

## 4. Practical implementation

Application boundary có typed contract:

```csharp
public sealed record TicketClassification(
    string Priority,
    string Reason);
```

Sau parse:

```csharp
var result = await llm.ClassifyAsync(ticket, ct);

if (!allowedPriorities.Contains(result.Priority))
    throw new InvalidOperationException("Unexpected priority.");

if (ticket.IsSecurityIncident)
{
    // Deterministic override; do not delegate critical routing solely to model.
    return Priority.High;
}
```

Schema-valid output vẫn đi qua business policy.

## 5. Real production scenario

Support system dùng LLM để classify ticket và đề xuất queue. Trước Structured Outputs, parser thỉnh thoảng fail vì model thêm markdown fence hoặc field đổi tên.

Structured schema loại phần lớn transport-shape failures. Nhưng một lần model phân loại security incident thành `medium`; deterministic rule vẫn route `high` dựa trên trusted signal.

## 6. Failure scenario & troubleshooting

**Symptom** → JSON parse không lỗi nhưng downstream workflow chạy sai.

**Evidence** → response hoàn toàn schema-valid nhưng semantic classification không đúng business rule.

**Hypothesis** → team nhầm structural guarantee với correctness guarantee.

**Diagnosis** → replay input qua eval set, inspect confusion cases và deterministic policy coverage.

**Fix** → thêm validation/rules cho critical conditions, evaluation dataset và confidence/fallback design.

**Verification** → regression eval + application tests cho protected business invariants.

## 7. Common mistakes

* Coi schema enforcement là factual guarantee.
* Cho model tự quyết định authorization/payment/financial correctness chỉ vì output typed.
* Schema quá phức tạp, biến model response contract thành domain model khổng lồ.
* Không version schema khi consumers evolve.
* Không log model/version/prompt/evaluation metadata phù hợp cho incident analysis.

## 8. Alternatives

Function/Tool Calling phù hợp khi output nhằm đề xuất một action/tool invocation; vẫn cần deterministic authorization trước khi execute.

Free-form text tốt khi output chủ yếu để human đọc và không cần machine parsing.

Rule engine phù hợp cho logic deterministic rõ ràng, không nên thay bằng LLM.

## 9. Trade-offs

### Advantages

Parsing ổn định hơn, type-safe integration dễ hơn và giảm defensive text parsing.

### Costs / Risks

Schema governance, token/context overhead và nguy cơ false confidence rằng typed output = correct output.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Structured Outputs giúp response có shape ổn định.

### Middle

Biết map schema sang DTO và validate response.

### Senior

Tách structural validation, semantic validation, evaluation và fallback.

### Technical Lead / Architect

Quyết định boundary giữa probabilistic model output và deterministic application logic; xác định use case nào không được phép giao final authority cho model.

## 11. Key takeaway

* Schema-valid không đồng nghĩa business-correct.
* Structured Outputs giải quyết integration contract, không thay evaluation.
* Security-critical và financial-critical decisions vẫn cần deterministic enforcement.
