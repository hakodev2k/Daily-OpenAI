# 1. C# `readonly struct`, defensive copy và boxing: value type nhỏ có thể nhanh nhưng copy semantics sai chỗ vẫn tạo chi phí và bug khó thấy

## 1. What is it?

`struct` là value type: assignment và truyền tham số thường copy giá trị thay vì copy reference. `readonly struct` nói với compiler rằng instance state không được mutate sau khi khởi tạo.

Mental model:

```text
class  -> biến giữ reference tới object
struct -> biến thường chứa chính value và có thể bị copy
```

Điểm quan trọng không phải “struct nằm trên stack, class nằm trên heap” — đó là simplification dễ gây hiểu sai. Điều đáng quan tâm là **value semantics, copy cost, boxing và mutability**.

`readonly struct` giúp compiler tránh một số defensive copies khi member thực sự bất biến và làm contract rõ hơn.

## 2. Why does it exist?

Value type phù hợp cho dữ liệu nhỏ, có identity không quan trọng: coordinate, range, money-like value, IDs wrapper hoặc runtime primitives.

Nếu mutable struct được đọc qua readonly context, compiler có thể phải tạo defensive copy để đảm bảo method không mutate original value. Khi hot path lặp hàng triệu lần, những copy này có thể thành cost thực tế.

## 3. How does it work?

Ví dụ:

```csharp
public readonly struct Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        Amount = amount;
        Currency = currency;
    }
}
```

Khi assign:

```csharp
var a = new Money(100, "USD");
var b = a;
```

`b` nhận một copy value. Với struct lớn, copy liên tục qua method calls có thể đắt hơn việc truyền reference.

Boxing xảy ra khi value type phải được đóng gói thành object/interface representation phù hợp:

```csharp
object boxed = a;
```

Việc này có thể tạo allocation.

## 4. Practical implementation

Với value object nhỏ, bất biến:

```csharp
public readonly record struct CustomerId(Guid Value)
{
    public override string ToString() => Value.ToString();
}
```

Khi dùng API hot path, cân nhắc `in` cho large readonly struct nếu profiling chứng minh copy đáng kể:

```csharp
static decimal CalculateTax(in PriceBreakdown value)
    => value.Net + value.Vat;
```

Không áp `in` đại trà; call-site complexity và JIT behavior phải được đo.

## 5. Real production scenario

Pricing engine xử lý hàng triệu price calculations. Team tạo một mutable struct 128 bytes và truyền by value qua nhiều layers. Profiling cho thấy thời gian tăng ở copy-related generated code và allocations do boxing qua non-generic interfaces.

Fix không phải “đổi toàn bộ thành class”. Team thu nhỏ model, làm immutable, bỏ boxing path và chỉ dùng by-ref semantics ở hot path đã đo.

## 6. Failure scenario & troubleshooting

**Symptom:** CPU tăng sau refactor dù allocation dashboard không tăng nhiều.

**Evidence:** profiler cho thấy method hot path copy large structs hoặc boxing ở interface/object boundary.

**Hypothesis:** value semantics tạo copy cost lớn hơn dự kiến.

**Diagnosis:** BenchmarkDotNet/microbenchmark cho isolated path, production profiler cho real traffic.

**Fix:** giảm struct size, dùng immutable representation, generic API hoặc đổi sang class khi reference semantics phù hợp hơn.

**Verification:** so throughput, CPU và allocation trước/sau với cùng workload.

## 7. Common mistakes

- Tin rằng mọi struct đều “không allocation”.
- Dùng mutable struct làm domain entity.
- Tạo struct rất lớn rồi truyền by value khắp nơi.
- Boxing qua `object`, non-generic collection hoặc interface mà không nhận ra.
- Dùng `in`/`ref` để micro-optimize trước khi profiling.

## 8. Alternatives

- `class`: phù hợp identity, shared mutable state hoặc object lớn.
- `record class`: reference semantics + value-style equality.
- `record struct`: value semantics với syntax gọn.
- primitive/tuple: phù hợp data cực nhỏ và local scope.

## 9. Trade-offs

### Advantages

- Value semantics rõ cho small immutable values.
- Có thể giảm heap allocation trong một số workload.
- `readonly` giúp contract và optimization rõ hơn.

### Costs / Risks

- Copy cost tăng theo size.
- Boxing vẫn tạo allocation.
- Mutable struct rất dễ gây semantic bug.
- By-ref optimization làm API khó hiểu hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu value semantics khác reference semantics.

### Middle

Nhận biết boxing, mutable struct pitfalls và chọn record/class/struct đúng use case.

### Senior

Đo copy/boxing cost bằng profiler thay vì dựa trên folklore về stack/heap.

### Technical Lead / Architect

Đặt modeling guideline: struct cho small immutable value, class cho identity/reference semantics; chỉ tối ưu by-ref khi workload chứng minh cần.

## 11. Key takeaway

- `struct` là lựa chọn semantics trước khi là lựa chọn performance.
- `readonly struct` giảm mutability risk nhưng không làm copy cost biến mất.
- Boxing và large-value copying chỉ nên tối ưu sau profiling.

# 2. ASP.NET Core `HttpResponse.HasStarted`: exception handling sau khi response bắt đầu và vì sao middleware không thể “đổi thành 500” ở mọi thời điểm

## 1. What is it?

`HttpResponse.HasStarted` cho biết headers của response đã được gửi tới client hay chưa.

Trước khi response bắt đầu, middleware có thể thay status code, headers hoặc body strategy. Sau khi headers đã được flush, HTTP response contract đã bắt đầu được commit trên wire.

Mental model:

```text
Request
 -> endpoint
 -> set headers/status
 -> response starts  <--- boundary
 -> stream body
 -> exception xảy ra ở đây
```

Sau boundary đó, global exception middleware không thể luôn biến response thành một sạch sẽ `500 ProblemDetails`.

## 2. Why does it exist?

Streaming, file download, Server-Sent Events hoặc large response thường cần gửi dữ liệu trước khi toàn bộ operation hoàn tất. HTTP không có cơ chế “undo” bytes đã gửi.

Nếu application giả định exception handler luôn có thể rewrite response, production sẽ xuất hiện truncated payload, status `200` nhưng connection reset, hoặc client parse lỗi.

## 3. How does it work?

Typical middleware:

```text
Exception middleware
    -> endpoint
        -> WriteAsync / FlushAsync
             -> headers committed
        -> later exception
    <- exception bubbles
```

Exception middleware bắt được exception nhưng nếu `HasStarted == true`, options thường chỉ còn log và terminate/abort flow phù hợp.

## 4. Practical implementation

```csharp
app.UseExceptionHandler(errorApp =>
{
    errorApp.Run(async context =>
    {
        if (context.Response.HasStarted)
            return;

        context.Response.StatusCode = StatusCodes.Status500InternalServerError;
        await context.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Status = 500,
            Title = "Unexpected server error"
        });
    });
});
```

Với streaming endpoint, validate càng nhiều điều kiện có thể **trước first write**.

```csharp
app.MapGet("/export", async (HttpContext ctx, ExportService service, CancellationToken ct) =>
{
    var metadata = await service.ValidateAndPrepareAsync(ct);
    ctx.Response.ContentType = "text/csv";

    await foreach (var row in service.StreamRowsAsync(metadata, ct))
        await ctx.Response.WriteAsync(row + "\n", ct);
});
```

## 5. Real production scenario

Export API trả CSV vài GB. Endpoint gửi header `200 OK` rồi stream rows. Sau 30 giây, database connection timeout.

Client đã nhận `200`, nhưng file bị cắt giữa chừng. Exception middleware log lỗi nhưng không thể đổi response thành `500` chuẩn nữa.

Engineering response có thể là resumable export, background generation + Blob download, checksum hoặc trailer/protocol riêng tùy requirement.

## 6. Failure scenario & troubleshooting

**Symptom:** client báo file corrupt nhưng server access log vẫn có `200`.

**Evidence:** application trace có exception sau first response write; bytes sent nhỏ hơn expected.

**Hypothesis:** failure xảy ra sau response started.

**Diagnosis:** log `HasStarted`, bytes written, dependency timing và cancellation reason.

**Fix:** move validation trước streaming; chọn async export architecture nếu operation failure risk cao.

**Verification:** fault-injection dependency giữa stream và xác nhận client nhận behavior được thiết kế rõ.

## 7. Common mistakes

- Giả định global exception handler luôn rewrite được response.
- Flush sớm không cần thiết.
- Set headers sau first write.
- Stream transaction-sensitive data mà không có protocol phát hiện partial output.
- Log full exception nhưng không log response-started state.

## 8. Alternatives

- Buffer toàn bộ response trước khi gửi: đơn giản hơn nhưng tốn memory/latency.
- Background export + Blob: tốt cho file lớn hoặc long-running generation.
- Streaming: tốt khi latency-to-first-byte và memory quan trọng.

## 9. Trade-offs

### Advantages

- Streaming giảm peak memory và bắt đầu trả dữ liệu sớm.

### Costs / Risks

- Error contract phức tạp sau first byte.
- Retry toàn request có thể tốn kém.
- Partial result cần client semantics rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status/header không thể thay đổi tùy ý sau khi response bắt đầu.

### Middle

Biết kiểm tra `HasStarted`, organize validation và streaming correctly.

### Senior

Thiết kế protocol/failure semantics cho large streaming response.

### Technical Lead / Architect

Quyết định workload nào stream trực tiếp, workload nào phải background + durable artifact dựa trên failure tolerance và UX.

## 11. Key takeaway

- `HasStarted` là protocol boundary thực tế, không chỉ property của ASP.NET Core.
- Sau first byte, nhiều lỗi không còn có thể biến thành clean JSON error.
- Streaming architecture phải thiết kế partial-failure semantics từ đầu.

# 3. EF Core savepoint và transaction recovery: xử lý partial failure trong một transaction mà không nhầm lẫn với distributed transaction

## 1. What is it?

Savepoint là checkpoint bên trong một database transaction. Application có thể rollback về checkpoint thay vì rollback toàn bộ transaction.

Mental model:

```text
BEGIN TRANSACTION
  step A
  SAVEPOINT S1
  step B
  step C fails
  ROLLBACK TO S1
  alternative step
COMMIT
```

Savepoint chỉ nằm trong **một database transaction**; nó không làm remote API, queue hoặc filesystem trở thành transactional.

## 2. Why does it exist?

Một business operation đôi khi có nhiều database steps và cần recovery cục bộ. Rollback toàn bộ transaction có thể không cần thiết, nhưng commit partial data cũng không được phép.

EF Core có thể dùng savepoint khi `SaveChanges` chạy bên trong transaction hiện có, tùy provider/capabilities.

## 3. How does it work?

Database transaction giữ locks/version state như bình thường. Savepoint chỉ đánh dấu position logic để rollback changes sau đó.

Không có atomicity xuyên resource:

```text
SQL transaction + HTTP payment call != one ACID transaction
```

Nếu payment thành công nhưng SQL rollback, savepoint không thể “rollback payment”.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

try
{
    order.MarkValidated();
    await db.SaveChangesAsync(ct);

    await tx.CreateSavepointAsync("BeforeReservation", ct);

    try
    {
        await inventoryWriter.ReserveInDatabaseAsync(order, ct);
        await db.SaveChangesAsync(ct);
    }
    catch (DbUpdateException)
    {
        await tx.RollbackToSavepointAsync("BeforeReservation", ct);
        order.MarkManualReview();
        await db.SaveChangesAsync(ct);
    }

    await tx.CommitAsync(ct);
}
catch
{
    await tx.RollbackAsync(ct);
    throw;
}
```

Ví dụ chỉ hợp lý nếu `inventoryWriter` vẫn dùng cùng transactional database boundary.

## 5. Real production scenario

Order import xử lý validation rồi optional reservation record. Một reservation conflict không nên hủy audit/import metadata đã tạo trong cùng workflow, nhưng business cho phép chuyển order sang `ManualReview`.

Savepoint cho phép rollback phần reservation trong cùng DB transaction và tiếp tục alternative branch.

## 6. Failure scenario & troubleshooting

**Symptom:** transaction giữ lock rất lâu và deadlock tăng.

**Evidence:** transaction duration lớn, nhiều savepoints, business flow chờ remote dependencies trong transaction.

**Hypothesis:** savepoint bị dùng để kéo dài transaction qua quá nhiều steps.

**Diagnosis:** trace SQL transaction lifetime và external calls.

**Fix:** thu nhỏ transaction boundary; dùng Outbox/Saga khi workflow vượt database boundary.

**Verification:** lock duration, deadlock rate và transaction latency giảm.

## 7. Common mistakes

- Coi savepoint như nested distributed transaction.
- Gọi remote API khi DB transaction đang giữ locks.
- Tạo quá nhiều savepoint thay vì đơn giản hóa workflow.
- Retry `SaveChanges` mà không hiểu transaction state.
- Rollback đến savepoint nhưng in-memory tracked state vẫn cần được reasoning cẩn thận.

## 8. Alternatives

- Rollback toàn transaction: đơn giản nhất nếu partial recovery không có business value.
- Separate transactions: phù hợp nếu eventual consistency chấp nhận được.
- Saga/compensation: cho multi-service workflow.
- Outbox: cho database + message publication boundary.

## 9. Trade-offs

### Advantages

- Recovery cục bộ trong một DB transaction.
- Có thể giữ business invariant mà không restart toàn workflow.

### Costs / Risks

- Transaction dài hơn nếu lạm dụng.
- Locking/concurrency vẫn tồn tại.
- Không giải quyết side effect ngoài database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction và savepoint khác nhau.

### Middle

Dùng savepoint với explicit failure handling trong cùng DB.

### Senior

Đánh giá transaction duration, locking và tracked state khi rollback partial.

### Technical Lead / Architect

Quyết định khi nào transaction-local recovery đủ và khi nào phải chuyển sang Saga/Outbox/eventual consistency.

## 11. Key takeaway

- Savepoint là recovery primitive bên trong một transaction, không phải distributed consistency solution.
- Transaction boundary càng dài, lock/latency risk càng lớn.
- External side effects cần pattern khác.

# 4. SQL Server SARGability: vì sao function trên indexed column biến index seek thành scan dù đã “có index đúng”

## 1. What is it?

SARGable predicate là điều kiện mà query optimizer có thể dùng để tìm phạm vi index hiệu quả.

Ví dụ tốt:

```sql
WHERE CreatedAt >= @From
  AND CreatedAt <  @To
```

Ví dụ dễ phá index seek:

```sql
WHERE CAST(CreatedAt AS date) = @Date
```

Index có thể tồn tại nhưng predicate khiến engine phải transform/evaluate giá trị trên nhiều rows trước khi biết row nào match.

## 2. Why does it exist?

B-tree index hiệu quả khi optimizer có thể map predicate thành range trên key order. Nếu column bị bọc trong function, implicit conversion hoặc expression không tương thích index, khả năng seek giảm.

“Có index” không đảm bảo “query dùng index đúng cách”.

## 3. How does it work?

Giả sử index:

```sql
CREATE INDEX IX_Orders_CreatedAt
ON dbo.Orders(CreatedAt);
```

Predicate range:

```text
seek start: 2026-09-13 00:00
seek end:   2026-09-14 00:00
```

Engine có thể nhảy thẳng tới range.

Với `CAST(CreatedAt AS date)`, engine có thể phải xử lý nhiều entries hơn, tùy optimizer transformation và statistics.

## 4. Practical implementation

Thay:

```sql
SELECT Id, Total
FROM dbo.Orders
WHERE CONVERT(date, CreatedAt) = @Date;
```

Bằng:

```sql
DECLARE @From datetime2 = @Date;
DECLARE @To datetime2 = DATEADD(day, 1, @From);

SELECT Id, Total
FROM dbo.Orders
WHERE CreatedAt >= @From
  AND CreatedAt < @To;
```

Một case khác là implicit conversion: nếu column là `varchar` nhưng parameter gửi `nvarchar`, plan có thể xuất hiện `CONVERT_IMPLICIT` trên column side.

## 5. Real production scenario

Dashboard query bảng 200 triệu transactions theo ngày. Index trên `CreatedAt` tồn tại, nhưng developer dùng `WHERE YEAR(CreatedAt)=2026 AND MONTH(CreatedAt)=9`.

Execution plan scan hàng triệu rows, logical reads tăng mạnh và p95 API tăng theo data growth.

## 6. Failure scenario & troubleshooting

**Symptom:** query từng nhanh nhưng chậm dần khi bảng lớn lên.

**Evidence:** actual execution plan có scan, residual predicate hoặc implicit conversion; logical reads cao.

**Hypothesis:** predicate không SARGable.

**Diagnosis:** xem actual plan, `SET STATISTICS IO, TIME ON`, data distribution và parameter types.

**Fix:** rewrite predicate thành range/searchable form hoặc dùng computed persisted column/index nếu business query bắt buộc expression.

**Verification:** logical reads, elapsed time và plan operator cải thiện dưới representative parameters.

## 7. Common mistakes

- Chỉ nhìn query duration mà không xem reads/plan.
- Thêm index thứ hai thay vì sửa predicate.
- Dùng function trên column trong hot filter.
- Bỏ qua implicit conversion giữa parameter và column type.
- Ép index hint để che query-shape problem.

## 8. Alternatives

- Computed persisted column + index: hữu ích cho expression được query thường xuyên.
- Materialized/reporting table: phù hợp analytics pattern khác OLTP.
- Columnstore: cho analytical workload lớn, không phải universal replacement.

## 9. Trade-offs

### Advantages

- SARGable queries tận dụng B-tree hiệu quả và giảm I/O.

### Costs / Risks

- Rewrite predicate đôi khi làm code ít “đẹp” hơn.
- Computed/indexed columns tăng write/storage cost.
- Index phù hợp một access pattern có thể không giúp pattern khác.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không tự động làm mọi filter nhanh.

### Middle

Biết đọc seek/scan và tránh function/implicit conversion phổ biến.

### Senior

Reason từ predicate → plan → reads → latency, không chỉ “thêm index”.

### Technical Lead / Architect

Thiết kế schema/access pattern dựa trên workload thực; tách OLTP/reporting nếu query shape xung đột sâu.

## 11. Key takeaway

- Predicate shape quyết định index usability nhiều như bản thân index.
- Actual plan + logical reads là evidence quan trọng.
- SARGability nên được xem cùng parameter types, statistics và data distribution.

# 5. Redis eviction và memory pressure: cache có giới hạn memory sẽ loại key như thế nào và khi nào eviction biến thành production incident

## 1. What is it?

Redis chạy trong memory nên memory là finite resource. Khi đạt configured memory limit, Redis phải áp eviction policy hoặc từ chối writes tùy cấu hình.

Mental model:

```text
Memory < maxmemory -> normal
Memory ~= maxmemory -> eviction / write failure tùy policy
```

Eviction khác expiration: expiration xảy ra theo TTL; eviction xảy ra vì memory pressure.

## 2. Why does it exist?

Cache không thể tăng memory vô hạn theo số keys. Một production cache cần policy rõ: ưu tiên loại keys nào, có cho key không TTL tồn tại mãi không, và behavior khi không thể giải phóng đủ memory.

## 3. How does it work?

Các policy thường dựa trên LRU/LFU approximation, TTL hoặc nhóm keys đủ điều kiện eviction. Ý nghĩa vận hành quan trọng hơn tên policy:

- Có thể eviction mọi key hay chỉ key có TTL?
- Application có chịu được miss không?
- Một số keys có thực chất là durable/session-critical data không?

Nếu Redis đang giữ thứ “không được phép mất”, gọi nó là cache đã sai boundary.

## 4. Practical implementation

Application nên coi Redis miss là bình thường:

```csharp
var cached = await cache.GetStringAsync(key, ct);
if (cached is not null)
    return JsonSerializer.Deserialize<Product>(cached)!;

var product = await repository.GetAsync(id, ct);

await cache.SetStringAsync(
    key,
    JsonSerializer.Serialize(product),
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
    },
    ct);

return product;
```

Quan trọng hơn code là metrics: used memory, evicted keys, hit rate, miss rate và downstream QPS.

## 5. Real production scenario

E-commerce cache chứa product pages và session-like temporary data. Marketing campaign tăng cardinality keys gấp 5 lần. Redis chạm maxmemory và eviction tăng nhanh.

Hit rate giảm từ 95% xuống 55%, SQL traffic tăng mạnh và database trở thành bottleneck dù Redis bản thân vẫn “up”.

## 6. Failure scenario & troubleshooting

**Symptom:** API latency tăng, Redis health check xanh, database QPS tăng đột ngột.

**Evidence:** `evicted_keys` tăng, memory sát limit, cache hit ratio giảm.

**Hypothesis:** Redis memory pressure tạo miss storm.

**Diagnosis:** phân tích keyspace/cardinality, TTL distribution, value size và traffic source.

**Fix:** loại cache không cần thiết, sửa TTL, split workloads, tăng memory khi justified hoặc sửa key explosion.

**Verification:** eviction ổn định, hit ratio phục hồi và DB QPS giảm.

## 7. Common mistakes

- Chỉ monitor Redis availability, không monitor eviction.
- Lưu session/business-critical state nhưng vẫn chọn eviction policy có thể loại key.
- Key chứa unbounded user input làm cardinality explosion.
- Cache object quá lớn.
- Tăng memory ngay mà không tìm leak/key growth pattern.

## 8. Alternatives

- `IMemoryCache`: per-instance, đơn giản nhưng không shared.
- Database/read replica: có thể đủ nếu query đã nhanh.
- CDN: tốt cho cacheable HTTP content.
- Không cache: đúng nếu complexity lớn hơn lợi ích.

## 9. Trade-offs

### Advantages

- Eviction giữ Redis trong memory budget.
- Cache giảm load nguồn dữ liệu khi hit ratio tốt.

### Costs / Risks

- Miss rate có thể tăng đột ngột dưới pressure.
- Chính sách sai có thể làm mất state quan trọng.
- Redis trở thành hidden critical dependency nếu fallback không được capacity-plan.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu expiration và eviction là hai cơ chế khác nhau.

### Middle

Theo dõi hit/miss, TTL, key size và memory.

### Senior

Liên hệ eviction với downstream capacity và thiết kế fallback bounded.

### Technical Lead / Architect

Quyết định dữ liệu nào thực sự là cache, workload nào cần cluster/split, và capacity plan khi Redis degraded.

## 11. Key takeaway

- Redis “up” không có nghĩa cache khỏe.
- Eviction rate và hit ratio là production signals quan trọng.
- Nếu dữ liệu không được phép mất, đừng dựa vào eviction-prone cache làm source of truth.

# 6. Domain Event vs Integration Event: tách transaction nội bộ khỏi communication giữa bounded contexts để tránh coupling và inconsistency

## 1. What is it?

**Domain Event** mô tả điều có ý nghĩa vừa xảy ra trong domain boundary, ví dụ `OrderConfirmed`.

**Integration Event** là contract được publish ra ngoài boundary để service/bounded context khác phản ứng.

Hai event có thể có tên giống nhau nhưng không nên mặc định là cùng một object/contract.

## 2. Why does it exist?

Domain model cần biểu diễn business consequence nội bộ. Distributed system lại cần contract ổn định, versionable và chịu được asynchronous delivery.

Nếu publish domain object trực tiếp ra broker, internal model evolution bị coupling vào consumers bên ngoài.

## 3. How does it work?

Flow lành mạnh:

```text
Aggregate
 -> Domain Event
 -> application handler
 -> persist state + Outbox Integration Event
 -> commit
 -> publisher
 -> broker
 -> external consumers
```

Domain event có thể được xử lý synchronously trong application transaction. Integration event thường được deliver asynchronously và phải chịu duplicate/eventual consistency.

## 4. Practical implementation

```csharp
public sealed record OrderConfirmedDomainEvent(Guid OrderId);

public sealed record OrderConfirmedIntegrationEvent(
    Guid OrderId,
    DateTimeOffset ConfirmedAt,
    int ContractVersion);
```

Application handler map domain event thành outbox message:

```csharp
outbox.Add(new OutboxMessage(
    type: "order.confirmed.v1",
    payload: JsonSerializer.Serialize(
        new OrderConfirmedIntegrationEvent(order.Id, clock.UtcNow, 1))));
```

## 5. Real production scenario

Order domain thay đổi internal aggregate và thêm fields phục vụ pricing. Nếu consumers ngoài service deserialize domain object trực tiếp, một refactor nội bộ dễ thành breaking integration change.

Integration event riêng giúp chỉ expose dữ liệu consumers thực sự cần.

## 6. Failure scenario & troubleshooting

**Symptom:** deploy Order service làm Inventory consumer fail deserialize.

**Evidence:** broker payload dùng serialized domain model; schema thay đổi theo refactor nội bộ.

**Hypothesis:** internal model và external contract bị trộn.

**Diagnosis:** trace event ownership/version và consumer dependencies.

**Fix:** tách integration DTO/contract, version rõ, dùng outbox và compatibility policy.

**Verification:** old consumer vẫn đọc version được hỗ trợ sau internal refactor.

## 7. Common mistakes

- Coi mọi domain event phải publish ra broker.
- Serialize entity/aggregate trực tiếp thành integration event.
- Publish message trước database commit.
- Giả định broker exactly-once nên consumer không cần idempotency.
- Event schema chứa quá nhiều internal fields.

## 8. Alternatives

- Synchronous REST: tốt khi caller cần immediate response và coupling chấp nhận được.
- Database polling/read model: phù hợp một số reporting flow.
- Shared database: đơn giản ban đầu nhưng ownership coupling cao.

## 9. Trade-offs

### Advantages

- Tách internal model evolution khỏi public event contract.
- Hỗ trợ bounded context ownership rõ.
- Outbox giúp nhất quán DB + publication intent.

### Costs / Risks

- Thêm mapping, schema governance và observability.
- Eventual consistency tăng complexity.
- Quá nhiều events có thể tạo khó hiểu nếu business boundary không rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu domain event không đồng nghĩa message broker event.

### Middle

Tạo integration contract riêng và xử lý async/idempotency.

### Senior

Thiết kế versioning, outbox và failure semantics.

### Technical Lead / Architect

Định nghĩa event ownership, bounded-context contracts và khi nào REST đơn giản hơn messaging.

## 11. Key takeaway

- Domain Event tối ưu cho business model; Integration Event tối ưu cho external contract.
- Đừng để internal aggregate trở thành public schema.
- Publish sau durable commit và giả định duplicate delivery có thể xảy ra.

# 7. Azure Blob Storage lifecycle management: tự động tier/delete dữ liệu nhưng không biến retention policy thành mất dữ liệu ngoài ý muốn

## 1. What is it?

Lifecycle management cho Blob Storage cho phép rule tự động chuyển blob sang access tier khác hoặc delete dựa trên age/path/metadata-like conditions được hỗ trợ.

Mental model:

```text
Hot data
 -> ít truy cập dần
 -> cooler tier
 -> retention hết hạn
 -> delete
```

Đây là data-retention automation, không chỉ cost optimization.

## 2. Why does it exist?

Logs, exports, media và archives thường có access pattern giảm theo thời gian. Giữ mọi thứ ở tier đắt nhất hoặc giữ vô hạn gây cost và compliance risk.

Manual cleanup không đáng tin khi data scale lớn.

## 3. How does it work?

Lifecycle engine đánh giá blob theo rule và thực hiện transition/delete asynchronously. Application không nên giả định change xảy ra ngay đúng giây threshold.

Kiến trúc cần tách:

```text
Business retention requirement
       |
       v
Storage lifecycle policy
       |
       v
Tiering / deletion execution
```

Policy phải khớp backup, legal hold, versioning và restore expectations.

## 4. Practical implementation

Một naming convention giúp rule rõ:

```text
exports/{tenantId}/{yyyy}/{MM}/{file}.csv
logs/{service}/{yyyy}/{MM}/{dd}/...
```

Application nên lưu metadata nghiệp vụ trong database nếu cần query/authorization; không scan blob container như một database nghiệp vụ.

Ví dụ policy concept:

```text
exports/*
- sau 30 ngày: cool tier
- sau 180 ngày: delete nếu business retention cho phép
```

Trước khi áp rule, chạy inventory và dry-review bằng report/script riêng để biết blob nào sẽ bị ảnh hưởng.

## 5. Real production scenario

SaaS tạo PDF export cho khách hàng. 95% file chỉ được tải trong 7 ngày đầu. Team giữ Hot tier 3 năm nên storage bill tăng đều.

Lifecycle policy giảm cost, nhưng legal/compliance yêu cầu một số tenants giữ 7 năm. Một global delete rule sẽ là data-loss incident nếu không phân loại retention scope.

## 6. Failure scenario & troubleshooting

**Symptom:** customer không tải được archive cũ sau policy rollout.

**Evidence:** lifecycle rule match prefix rộng hơn dự kiến; blob đã bị deleted/tiered.

**Hypothesis:** retention policy và storage rule không cùng business classification.

**Diagnosis:** kiểm tra policy version, prefix, tags/metadata strategy, soft delete/versioning và audit logs.

**Fix:** thu hẹp rule, dùng retention class rõ, enable protection mechanisms phù hợp.

**Verification:** test representative containers/tenants trước rollout rộng.

## 7. Common mistakes

- Dùng prefix naming không ổn định rồi lifecycle theo prefix.
- Xóa data trước khi xác nhận compliance/legal retention.
- Coi archive tier như instant-access tier.
- Không tính retrieval/rehydration operational impact.
- Không có inventory trước khi bật delete rule.

## 8. Alternatives

- Application-managed cleanup job: linh hoạt business logic hơn nhưng tăng operational code.
- Separate storage accounts/containers theo retention class: boundary rõ hơn nhưng nhiều resources hơn.
- Giữ Hot tier: đơn giản nhất khi data nhỏ hoặc access unpredictable.

## 9. Trade-offs

### Advantages

- Tự động cost/retention management ở storage layer.
- Giảm custom cleanup jobs.

### Costs / Risks

- Rule sai có thể ảnh hưởng data diện rộng.
- Cold tiers đổi restore latency/cost.
- Compliance exceptions làm policy phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Blob tiering và retention là lifecycle của data.

### Middle

Thiết kế naming/metadata để rule match đúng scope.

### Senior

Đánh giá restore path, audit, legal retention và rollout safety.

### Technical Lead / Architect

Quyết định data classes, account/container boundaries và policy ownership giữa product, compliance và platform team.

## 11. Key takeaway

- Lifecycle policy là data-governance mechanism, không chỉ cách giảm bill.
- Delete automation cần protection, inventory và business retention rõ.
- Tier choice phải xét cả retrieval latency và operational recovery.

# 8. Structured logging trong .NET: message template, scopes và correlation để log trở thành evidence thay vì chuỗi text khó truy vấn

## 1. What is it?

Structured logging ghi event với fields có cấu trúc thay vì chỉ nối string.

Không tốt:

```csharp
_logger.LogInformation("Order " + orderId + " processed for " + customerId);
```

Tốt hơn:

```csharp
_logger.LogInformation(
    "Order {OrderId} processed for customer {CustomerId}",
    orderId,
    customerId);
```

Backend observability có thể index/search `OrderId` như field thay vì parse text.

Production incident hiếm khi được giải bằng đọc tuần tự hàng triệu log lines. Team cần query theo request, tenant, dependency, operation hoặc error category.

Structured fields biến log thành evidence có thể aggregate và correlate.

## 3. How does it work?

Logging pipeline thường là:

```text
Application event
 -> ILogger message template + properties
 -> provider/exporter
 -> Application Insights / Elasticsearch / other backend
 -> query/dashboard/alert
```

`BeginScope` có thể thêm contextual properties cho toàn bộ log trong một operation.

## 4. Practical implementation

```csharp
using (_logger.BeginScope(new Dictionary<string, object>
{
    ["OrderId"] = order.Id,
    ["TenantId"] = tenant.Id
}))
{
    _logger.LogInformation("Starting order confirmation");

    await paymentClient.AuthorizeAsync(order, ct);

    _logger.LogInformation("Order confirmation completed");
}
```

Correlation nên ưu tiên trace/request context chuẩn thay vì tự tạo random ID ở mọi layer.

Không log token, password, connection string, full payment data hoặc sensitive payload.

## 5. Real production scenario

Checkout p99 tăng. Với structured logs + traces, team query tất cả failures theo `OrderId`, thấy payment dependency timeout chỉ trên một region và đối chiếu deployment/version.

**Symptom:** log volume rất lớn nhưng không trả lời được “request nào bị ảnh hưởng và dependency nào fail”.

**Evidence:** messages thiếu stable fields/correlation, field names inconsistent giữa services.

**Hypothesis:** logging được dùng như printf thay vì observability schema.

**Diagnosis:** review representative incident queries và required dimensions.

**Fix:** chuẩn hóa field names/scopes, dùng trace context, giảm noisy logs.

**Verification:** chạy incident drill và đo thời gian tìm root cause.

## 7. Common mistakes

- String interpolation mọi nơi làm mất template semantics tùy provider.
- Log object nhạy cảm nguyên khối.
- Mỗi team dùng tên field khác nhau: `user_id`, `UserId`, `uid`.
- Log Information trong tight loop.
- Dùng logs thay metrics cho high-volume counters.

## 8. Alternatives

- Metrics: tốt cho aggregate trends/alerts.
- Traces: tốt cho request dependency path.
- Audit log: security/business evidence với retention/access khác operational logs.

## 9. Trade-offs

### Advantages

- Query/filter/correlation tốt hơn.
- Incident response nhanh hơn.

### Costs / Risks

- Storage/query cost tăng nếu log quá nhiều.
- Sensitive fields có thể tạo data exposure.
- High-cardinality fields cần đặt đúng loại telemetry.

# 10. File upload security trong ASP.NET Core: extension, MIME, path traversal, malware và quarantine boundary trước khi file trở thành trusted asset

## 1. What is it?

File upload là security boundary vì client đang gửi bytes mà server không kiểm soát. Filename, extension và `Content-Type` đều là untrusted input.

Mental model an toàn:

```text
Client upload
 -> size/type policy
 -> generated server-side name
 -> quarantine storage
 -> scan/validation
 -> trusted storage/publish
```

Không nên upload thẳng vào public web root rồi “kiểm tra sau”.

## 2. Why does it exist?

File có thể chứa malware, active content, path traversal filename, decompression bomb hoặc payload ngụy trang extension. Nếu application phục vụ lại file với content type sai hoặc từ cùng origin, risk XSS/content-sniffing cũng tăng.

## 3. How does it work?

Defense cần nhiều lớp:

- limit request/file size;
- không tin client filename;
- allowlist loại file theo business need;
- kiểm tra magic/header/signature khi phù hợp;
- lưu ngoài executable path;
- malware scan/quarantine khi risk yêu cầu;
- authorization khi download;
- safe response headers/content disposition.

## 4. Practical implementation

```csharp
app.MapPost("/documents", async (
    IFormFile file,
    IFileStore store,
    CancellationToken ct) =>
{
    if (file.Length == 0 || file.Length > 10 * 1024 * 1024)
        return Results.BadRequest("Invalid file size");

    var extension = Path.GetExtension(file.FileName).ToLowerInvariant();
    var allowed = new HashSet<string> { ".pdf", ".png", ".jpg" };

    if (!allowed.Contains(extension))
        return Results.BadRequest("File type not allowed");

    var storageName = $"{Guid.NewGuid():N}{extension}";

    await using var stream = file.OpenReadStream();
    await store.SaveToQuarantineAsync(storageName, stream, ct);

    return Results.Accepted($"/documents/{storageName}/status");
});
```

Extension check chỉ là lớp đầu; với risk cao cần content inspection/scanning.

## 5. Real production scenario

CMS cho editor upload “image”. Attacker đổi tên HTML/SVG/script-like payload thành `.jpg` hoặc upload SVG có active content. Nếu hệ thống serve file inline cùng origin với wrong content type, browser có thể tạo security impact.

Một workflow quarantine + verified media processing giảm blast radius.

## 6. Failure scenario & troubleshooting

**Symptom:** security scanner phát hiện uploaded file có script/malware hoặc path bất thường.

**Evidence:** file được lưu bằng original filename trong public directory; validation chỉ kiểm tra extension.

**Hypothesis:** upload flow coi metadata client là trusted.

**Diagnosis:** trace upload→storage→scan→serve pipeline, content headers và ACL.

**Fix:** generated names, private/quarantine storage, strict allowlist, scanner/media re-encode, safe download headers.

**Verification:** test malicious filenames, oversized files, polyglot files và unauthorized download.

## 7. Common mistakes

- `Path.Combine(uploadRoot, file.FileName)` trực tiếp.
- Chỉ tin `Content-Type` từ client.
- Cho phép mọi extension rồi blacklist vài loại nguy hiểm.
- Lưu file executable dưới web root.
- Virus scan synchronous trong request nếu scanner chậm, không có timeout/circuit policy.
- Public URL không kiểm tra authorization khi file nhạy cảm.

## 8. Alternatives

- Direct-to-Blob upload với short-lived SAS + backend finalize flow.
- Background scanning pipeline cho file lớn.
- Re-encode image/PDF preprocessing để loại active content trong use case phù hợp.
- Không hỗ trợ upload loại file không có business value.

## 9. Trade-offs

### Advantages

- Quarantine giảm khả năng untrusted bytes trở thành public asset ngay.
- Layered validation giảm phụ thuộc vào một check duy nhất.

### Costs / Risks

- Malware scanning tăng latency/cost.
- Content inspection không hoàn hảo.
- Direct upload giảm API load nhưng authorization/finalization phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu filename, extension và MIME từ client đều không đáng tin.

### Middle

Implement size/type validation, safe naming, private storage và authorization.

### Senior

Thiết kế quarantine/scanning/serving headers và failure behavior khi scanner unavailable.

### Technical Lead / Architect

Quyết định file types được hỗ trợ, retention, scanning SLA, storage boundary và incident response cho malicious content.

## 11. Key takeaway

- File upload là untrusted-content pipeline, không phải chỉ API nhận `IFormFile`.
- Không bao giờ dùng original filename làm trusted storage path.
- Quarantine, validation, authorization và safe serving phải được thiết kế như một chuỗi control.
