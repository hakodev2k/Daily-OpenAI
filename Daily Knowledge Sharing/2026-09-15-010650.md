# 1. C# covariance và contravariance trong generics: type safety cho producer/consumer abstraction thay vì ép cast ở runtime

## 1. What is it?

Variance mô tả quan hệ giữa generic types khi type argument có quan hệ kế thừa. Với C#, `out` biểu thị covariance cho producer, còn `in` biểu thị contravariance cho consumer.

Mental model:

```text
Producer<Dog>  -> có thể dùng như Producer<Animal>
Consumer<Animal> -> có thể dùng như Consumer<Dog>
```

Ví dụ trong BCL:

```csharp
IEnumerable<out T>
IComparer<in T>
Func<in T, out TResult>
```

Covariance an toàn khi generic abstraction chỉ “đưa T ra ngoài”. Contravariance an toàn khi abstraction chỉ “nhận T vào”.

## 2. Why does it exist?

Không có variance, code dùng generic interfaces thường phải tạo adapter hoặc cast dù quan hệ type về mặt logic hoàn toàn an toàn.

Ví dụ một service trả `IEnumerable<Dog>` có thể phục vụ caller chỉ cần đọc `Animal`. Nếu generic type bất biến tuyệt đối, abstraction trở nên cứng hơn cần thiết.

Variance cho phép API reuse tốt hơn mà vẫn giữ compile-time type safety.

## 3. How does it work?

Giả sử:

```csharp
public class Animal { }
public sealed class Dog : Animal { }

IEnumerable<Dog> dogs = new List<Dog>();
IEnumerable<Animal> animals = dogs;
```

Điều này hợp lệ vì `IEnumerable<T>` chỉ expose `T` theo hướng output.

Ngược lại:

```csharp
IComparer<Animal> animalComparer = ...;
IComparer<Dog> dogComparer = animalComparer;
```

Hợp lệ vì comparer biết so sánh mọi `Animal`, nên đương nhiên so sánh được `Dog`.

Một generic interface vừa consume vừa produce cùng `T` thường không thể khai báo variance:

```csharp
public interface IRepository<T>
{
    T Get(Guid id);
    void Save(T entity);
}
```

`T` xuất hiện ở cả input và output nên abstraction này invariant.

## 4. Practical implementation

Một event handler abstraction có thể khai báo contravariance:

```csharp
public interface IEventHandler<in TEvent>
{
    Task HandleAsync(TEvent @event, CancellationToken cancellationToken);
}

public sealed class AuditAllDomainEventsHandler
    : IEventHandler<DomainEvent>
{
    public Task HandleAsync(
        DomainEvent @event,
        CancellationToken cancellationToken)
    {
        // structured audit
        return Task.CompletedTask;
    }
}
```

Nếu `OrderPlaced : DomainEvent`, handler nhận `DomainEvent` có thể được dùng ở nơi cần `IEventHandler<OrderPlaced>`.

Điều này giúp composition linh hoạt mà không cần reflection/cast thủ công.

## 5. Real production scenario

Một enterprise platform có pipeline xử lý domain events. Team muốn một audit handler chung cho mọi event, đồng thời có handler chuyên biệt cho từng event.

Nếu generic handler abstraction thiết kế đúng variance, DI registration và decorator pipeline có thể reuse handler chung. Nếu thiết kế sai, team dễ tạo nhiều adapter boilerplate hoặc dùng cast runtime.

## 6. Failure scenario & troubleshooting

**Symptom** → compiler từ chối assignment giữa hai generic types dù `Dog : Animal`.

**Evidence** → generic interface vừa nhận vừa trả `T`, hoặc type parameter chưa khai báo `in`/`out`.

**Hypothesis** → abstraction không variance-safe.

**Diagnosis** → kiểm tra mọi vị trí sử dụng `T`: parameter, return type, nested generic.

**Fix** → tách producer và consumer interface nếu trách nhiệm thực sự khác nhau.

**Verification** → compile-time tests/samples xác nhận assignment hợp lệ mà không có runtime cast.

## 7. Common mistakes

* Nghĩ mọi `Generic<Dog>` đều có thể cast thành `Generic<Animal>`.
* Dùng covariance cho type có method nhận `T`.
* Dùng contravariance cho type trả `T`.
* Thêm variance chỉ để “compiler hết lỗi” mà không hiểu contract direction.
* Thiết kế interface vừa đọc vừa ghi rồi kỳ vọng variance hoạt động.

## 8. Alternatives

* Adapter explicit khi semantics khác nhau.
* Non-generic base interface nếu type relationship không quan trọng.
* Tách `IReader<out T>` và `IWriter<in T>` thay vì một abstraction hai chiều.
* Pattern matching/runtime dispatch khi behavior thực sự phụ thuộc concrete type.

## 9. Trade-offs

### Advantages

* Reuse abstraction tốt hơn.
* Giữ compile-time type safety.
* Giảm cast và adapter không cần thiết.

### Costs / Risks

* Generic API khó đọc hơn với developer chưa quen variance.
* Tách interface có thể tăng số type.
* Variance không áp dụng được cho mọi design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `out` = produce, `in` = consume.

### Middle

Nhận diện khi generic interface invariant và biết tách read/write responsibilities.

### Senior

Đánh giá variance dựa trên type-safety direction, DI composition và API ergonomics.

### Technical Lead / Architect

Quyết định abstraction boundary nào cần generic flexibility và khi nào adapter explicit dễ bảo trì hơn.

## 11. Key takeaway

* Covariance dành cho producer; contravariance dành cho consumer.
* Variance là compile-time type-safety feature, không phải runtime casting trick.
* Interface vừa consume vừa produce cùng `T` thường phải invariant.

# 2. ASP.NET Core API Versioning và backward compatibility: thay đổi contract mà không biến mỗi release thành coordinated deployment

## 1. What is it?

API versioning là chiến lược quản lý nhiều contract versions khi server cần thay đổi behavior hoặc schema nhưng client cũ chưa thể nâng cấp đồng thời.

Mental model:

```text
Client A -> v1 contract
Client B -> v2 contract
              |
              v
         Same backend capability
```

Versioning không chỉ là thêm `/v2`. Vấn đề chính là ownership của compatibility window.

## 2. Why does it exist?

Mobile app, partner integration hoặc frontend được deploy độc lập với backend. Nếu backend rename field, thay semantics hoặc đổi required input ngay lập tức, client cũ có thể hỏng.

Coordinated deployment giữa mọi consumer thường không thực tế.

## 3. How does it work?

Version có thể được truyền qua:

* URL segment: `/api/v1/orders`
* query string
* header
* media type

Quan trọng hơn transport là policy:

```text
Introduce v2
  -> keep v1 supported
  -> observe usage
  -> notify consumers
  -> deprecate
  -> remove after agreed window
```

Backward-compatible change thường không cần version mới, ví dụ thêm optional response field mà client tolerant.

## 4. Practical implementation

Endpoint groups có thể tách contract rõ ràng:

```csharp
var v1 = app.MapGroup("/api/v1/orders");
var v2 = app.MapGroup("/api/v2/orders");

v1.MapGet("/{id:guid}", async (Guid id, OrderService service, CancellationToken ct) =>
{
    var order = await service.GetAsync(id, ct);
    return Results.Ok(new OrderV1Response(order.Id, order.Total));
});

v2.MapGet("/{id:guid}", async (Guid id, OrderService service, CancellationToken ct) =>
{
    var order = await service.GetAsync(id, ct);
    return Results.Ok(new OrderV2Response(
        order.Id,
        order.Total.Amount,
        order.Total.Currency));
});
```

Domain/application logic không nhất thiết duplicate; mapping contract mới là nơi thường thay đổi.

## 5. Real production scenario

Một e-commerce API ban đầu trả `total: 120.5`. Sau đó business mở đa currency và cần `{ amount, currency }`.

Đổi trực tiếp field thành object sẽ break client. V2 có thể expose money model mới trong khi v1 tiếp tục map về legacy representation trong thời gian migration.

## 6. Failure scenario & troubleshooting

**Symptom** → mobile app cũ bắt đầu lỗi parse JSON sau backend deployment.

**Evidence** → response field đổi type nhưng endpoint version vẫn giữ nguyên.

**Hypothesis** → breaking contract change được release như non-breaking change.

**Diagnosis** → compare OpenAPI/schema giữa release, kiểm tra client telemetry theo app version.

**Fix** → restore v1 shape, introduce version mới hoặc compatibility adapter.

**Verification** → contract tests cho v1/v2 và replay payload từ client cũ.

## 7. Common mistakes

* Version mọi thay đổi, kể cả change hoàn toàn backward-compatible.
* Giữ version cũ vô thời hạn mà không đo usage.
* Copy toàn bộ business logic giữa v1/v2.
* Chỉ version route nhưng không quản lý semantics.
* Xóa field vì “frontend mới không dùng nữa” mà bỏ quên external consumer.

## 8. Alternatives

* Additive evolution với tolerant readers.
* Capability negotiation.
* GraphQL schema evolution/deprecation.
* Consumer-driven contract testing để phát hiện breaking change sớm.

## 9. Trade-offs

### Advantages

* Consumer nâng cấp độc lập.
* Giảm coordinated deployment.
* Cho phép migration có kiểm soát.

### Costs / Risks

* Nhiều contract cần test và vận hành.
* Compatibility code tích tụ.
* Documentation và support phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu API contract là cam kết với consumer, không chỉ là controller code.

### Middle

Phân biệt breaking/non-breaking change và implement versioned DTO mapping.

### Senior

Thiết kế deprecation, observability theo version và contract tests.

### Technical Lead / Architect

Đặt compatibility policy, support window và ownership giữa provider/consumers.

## 11. Key takeaway

* Versioning giải quyết independent deployment, không phải chỉ thay URL.
* Không phải mọi schema change đều cần version mới.
* Version cũ phải có lifecycle và telemetry, nếu không technical debt tăng vô hạn.

# 3. EF Core compiled queries: giảm query-compilation overhead nhưng chỉ đáng dùng sau khi đo đúng bottleneck

## 1. What is it?

EF Core phải phân tích LINQ expression, translate sang database query và cache metadata cần thiết trước khi execute. Compiled query cho phép ứng dụng tạo delegate đã compile trước cho một query shape ổn định.

Ví dụ:

```csharp
private static readonly Func<AppDbContext, Guid, Task<Order?>>
    GetOrderById = EF.CompileAsyncQuery(
        (AppDbContext db, Guid id) =>
            db.Orders.AsNoTracking().FirstOrDefault(x => x.Id == id));
```

## 2. Why does it exist?

Trong hot path có query cực thường xuyên và đơn giản, query-processing overhead phía EF có thể trở thành phần đáng kể so với database execution.

Nhưng với query mất 50 ms ở database, tiết kiệm vài micro/milliseconds ở query compilation thường không đáng kể.

## 3. How does it work?

Normal flow:

```text
LINQ expression
   -> expression analysis
   -> translation/cache lookup
   -> SQL
   -> database
```

Compiled query giữ sẵn delegate cho query shape:

```text
Compiled delegate
   -> bind parameters
   -> database
```

Database vẫn phải parse/plan/execute theo cơ chế của database/provider. Compiled query không biến slow SQL thành fast SQL.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, string, IAsyncEnumerable<Product>>
    ProductsByCategory =
        EF.CompileAsyncQuery(
            (AppDbContext db, string category) =>
                db.Products
                  .AsNoTracking()
                  .Where(x => x.Category == category)
                  .OrderBy(x => x.Id)
                  .Take(100));

public async Task<List<Product>> GetProductsAsync(
    string category,
    CancellationToken cancellationToken)
{
    var result = new List<Product>();

    await foreach (var item in ProductsByCategory(_db, category)
        .WithCancellation(cancellationToken))
    {
        result.Add(item);
    }

    return result;
}
```

Chỉ nên áp dụng sau benchmark với realistic provider/data.

## 5. Real production scenario

Một pricing service gọi cùng lookup query hàng chục nghìn lần/giây. Database query đã có index tốt và thường hoàn tất rất nhanh. Profiling cho thấy EF query pipeline chiếm tỷ lệ CPU đáng kể.

Compiled query có thể hợp lý ở đây. Nhưng với admin report phức tạp chạy vài lần/phút, lợi ích gần như không đáng complexity.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries nhưng p95 API gần như không đổi.

**Evidence** → distributed trace cho thấy 95% latency nằm ở network/database I/O.

**Hypothesis** → optimization nhắm sai bottleneck.

**Diagnosis** → benchmark query pipeline và database time riêng.

**Fix** → xử lý execution plan, round trips hoặc data volume trước.

**Verification** → measure lại CPU, throughput, p95/p99.

## 7. Common mistakes

* Compile query trước khi profiling.
* Nghĩ compiled query là compiled SQL stored procedure.
* Dùng cho query shape thay đổi động liên tục.
* Bỏ qua index/query plan vì tập trung vào EF overhead.
* Tạo abstraction khó đọc chỉ để tiết kiệm negligible CPU.

## 8. Alternatives

* Dựa vào EF Core query cache mặc định.
* Projection để giảm dữ liệu.
* Raw SQL cho trường hợp thật sự cần control.
* Stored procedure khi phù hợp governance/database logic.
* Giảm round trips thường đem lại lợi ích lớn hơn.

## 9. Trade-offs

### Advantages

* Giảm một phần CPU/query-processing overhead.
* Có ích với hot query ổn định, chạy cực thường xuyên.

### Costs / Risks

* Code ít linh hoạt hơn.
* Khó compose dynamic query.
* Tăng complexity mà có thể không cải thiện latency đáng kể.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ không tự động là SQL; EF phải translate query.

### Middle

Biết viết compiled query và parameterize đúng.

### Senior

Benchmark để xác nhận query compilation thực sự là bottleneck.

### Technical Lead / Architect

Chặn premature optimization và yêu cầu evidence trước khi đưa specialized optimization vào shared codebase.

## 11. Key takeaway

* Compiled query tối ưu EF query pipeline, không tối ưu database execution plan thay bạn.
* Chỉ đáng dùng ở hot path đã được đo.
* Round trip, I/O và bad SQL thường quan trọng hơn.

# 4. PostgreSQL covering index và index-only scan: giảm heap access nhưng phải hiểu visibility map, write cost và index bloat

## 1. What is it?

Covering index chứa đủ dữ liệu để PostgreSQL có thể trả query từ index mà không cần đọc thêm columns từ heap. `INCLUDE` cho phép thêm non-key columns vào index.

```sql
CREATE INDEX ix_orders_customer_created
ON orders (customer_id, created_at DESC)
INCLUDE (status, total_amount);
```

Một query phù hợp có thể dùng index-only scan.

## 2. Why does it exist?

Index lookup thường tìm row location rồi vẫn phải truy cập heap để lấy các column còn thiếu. Với query đọc nhiều rows, heap access ngẫu nhiên có thể tăng I/O đáng kể.

Covering index đổi storage/write cost để giảm read I/O.

## 3. How does it work?

```text
Query
  -> B-tree index
  -> matching entries
  -> visibility check
  -> possibly return from index
  -> otherwise visit heap
```

PostgreSQL MVCC yêu cầu biết tuple có visible với transaction hiện tại không. Visibility map giúp database biết heap page nào “all-visible” để thực hiện index-only scan thực sự.

Vì vậy có covering index chưa chắc query luôn tránh heap fetch.

## 4. Practical implementation

Query:

```sql
SELECT created_at, status, total_amount
FROM orders
WHERE customer_id = $1
ORDER BY created_at DESC
LIMIT 50;
```

Index:

```sql
CREATE INDEX CONCURRENTLY ix_orders_customer_created
ON orders (customer_id, created_at DESC)
INCLUDE (status, total_amount);
```

Kiểm tra:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT created_at, status, total_amount
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 50;
```

Quan sát `Index Only Scan`, `Heap Fetches` và buffer reads.

## 5. Real production scenario

Order-history endpoint đọc 50 orders gần nhất cho customer. Query chạy hàng triệu lần/ngày. Index hiện tại chỉ có `(customer_id, created_at)` nên database phải fetch heap để lấy `status` và `total_amount`.

Sau khi đo I/O, `INCLUDE` có thể giảm heap access đáng kể cho workload read-heavy.

## 6. Failure scenario & troubleshooting

**Symptom** → execution plan ghi `Index Only Scan` nhưng I/O vẫn cao.

**Evidence** → `Heap Fetches` lớn.

**Hypothesis** → pages chưa all-visible do update churn/VACUUM lag.

**Diagnosis** → kiểm tra `EXPLAIN (ANALYZE, BUFFERS)`, autovacuum health và table churn.

**Fix** → xử lý vacuum tuning/churn hoặc chấp nhận index-only scan không phải lúc nào cũng heap-free.

**Verification** → so sánh heap fetches và latency sau thay đổi.

## 7. Common mistakes

* Thêm mọi selected column vào index.
* Bỏ qua write amplification.
* Không kiểm tra actual plan.
* Nghĩ `INCLUDE` columns giúp filter/order như key columns.
* Tạo index lớn cho table update-heavy mà không đo bloat.

## 8. Alternatives

* Narrow index + heap lookup nếu workload không đủ nóng.
* Materialized/read model cho query đặc biệt.
* Denormalization có kiểm soát.
* Cache nếu freshness semantics cho phép.

## 9. Trade-offs

### Advantages

* Có thể giảm random heap I/O.
* Tốt cho read-heavy query shape ổn định.

### Costs / Risks

* Index lớn hơn, write chậm hơn.
* Vacuum/bloat cost tăng.
* Hiệu quả phụ thuộc MVCC visibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không chứa mặc định mọi column của row.

### Middle

Biết dùng `EXPLAIN ANALYZE` và `INCLUDE`.

### Senior

Đánh giá visibility map, heap fetches, write amplification và bloat.

### Technical Lead / Architect

Quyết định read optimization có đáng đổi lấy storage/write/operations cost hay không.

## 11. Key takeaway

* Covering index nhằm giảm heap access, không phải “index càng nhiều column càng tốt”.
* `Index Only Scan` vẫn chịu ảnh hưởng MVCC visibility.
* Luôn đo plan, buffers và write cost.

# 5. Cosmos DB partition key và hot partition: scale-out chỉ hiệu quả khi workload phân bố đúng theo access pattern

## 1. What is it?

Cosmos DB phân phối dữ liệu theo logical partition key. Partition key quyết định dữ liệu nào nằm cùng logical partition và cách request được route.

Một key tốt phải cân bằng hai mục tiêu:

* query/transaction thường xuyên nằm cùng partition khi có thể,
* traffic/storage phân bố đủ rộng để tránh một partition trở thành hotspot.

## 2. Why does it exist?

Distributed database cần cách chia dữ liệu qua nhiều physical resources. Nếu không có partitioning strategy, scale-out không thể route và phân bổ workload hiệu quả.

Partition key là một phần của domain/access-pattern design, không phải config có thể sửa tùy ý sau cùng.

## 3. How does it work?

Ví dụ chọn `/tenantId`:

```text
Tenant A -> logical partition A
Tenant B -> logical partition B
Tenant C -> logical partition C
```

Query có partition key cụ thể được route hiệu quả hơn cross-partition query.

Nhưng nếu một tenant chiếm 80% traffic, `/tenantId` có thể tạo hot partition dù cardinality nhìn có vẻ tốt.

## 4. Practical implementation

C# SDK:

```csharp
var item = new OrderDocument
{
    Id = order.Id.ToString(),
    TenantId = order.TenantId,
    Status = order.Status
};

await container.CreateItemAsync(
    item,
    new PartitionKey(item.TenantId),
    cancellationToken: cancellationToken);
```

Point read:

```csharp
var response = await container.ReadItemAsync<OrderDocument>(
    id: orderId,
    partitionKey: new PartitionKey(tenantId),
    cancellationToken: cancellationToken);
```

Request nên mang đủ partition-key context khi possible.

## 5. Real production scenario

SaaS platform dùng `/tenantId`. Phần lớn tenant nhỏ, nhưng một enterprise tenant tạo traffic gấp hàng trăm lần tenant khác. Toàn bộ workload tenant lớn dồn vào một logical partition.

Thiết kế có thể cần hierarchical/synthetic partition strategy tùy access pattern, ví dụ kết hợp tenant với bucket/business dimension.

## 6. Failure scenario & troubleshooting

**Symptom** → throttling 429 tăng dù tổng RU/s còn vẻ “đủ”.

**Evidence** → request charge/throttling tập trung ở một partition-key range.

**Hypothesis** → hot partition.

**Diagnosis** → phân tích RU distribution theo partition key, top tenants và query pattern.

**Fix** → redesign key/bucketing cho future data hoặc isolate heavy tenant; tăng RU chỉ là giải pháp tạm nếu skew vẫn tồn tại.

**Verification** → load test với production-like key distribution.

## 7. Common mistakes

* Chọn key chỉ vì high cardinality.
* Dùng timestamp làm key gây write concentration theo thời gian.
* Query cross-partition cho mọi request.
* Không lưu partition key cùng identifier ở application boundary.
* Giả định tăng RU giải quyết mọi hotspot.

## 8. Alternatives

* SQL/PostgreSQL nếu relational transactions/query phù hợp hơn.
* MongoDB với shard-key strategy khác.
* Separate containers cho workload có isolation requirement.
* Synthetic partition key.

## 9. Trade-offs

### Advantages

* Scale-out và routing hiệu quả khi key phù hợp.
* Point reads rất predictable.
* Locality tốt cho operations cùng key.

### Costs / Risks

* Key sai rất khó sửa cho dữ liệu hiện hữu.
* Cross-partition query tốn RU hơn.
* Workload skew có thể tạo hotspot.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định data locality.

### Middle

Biết truyền partition key cho writes/point reads.

### Senior

Chọn key từ access pattern, tenancy model và growth projection; lên migration strategy nếu key sai.

## 11. Key takeaway

* Partition key là architecture decision.
* Cardinality cao chưa đủ; traffic distribution cũng phải cân bằng.
* Thiết kế phải dựa trên access pattern thật và skew thực tế.

# 6. CQRS với một database: tách command/query để giảm coupling mà không nhảy ngay sang hai data stores và Event Sourcing

## 1. What is it?

CQRS tách intent ghi (Command) khỏi intent đọc (Query). Nó không bắt buộc phải có hai databases, message broker hoặc Event Sourcing.

Mental model đơn giản:

```text
HTTP
 ├-> Command -> business mutation -> same SQL DB
 └-> Query   -> optimized projection -> same SQL DB
```

Giá trị ban đầu thường nằm ở separation of intent và model, không phải infrastructure.

## 2. Why does it exist?

Một model duy nhất vừa cố bảo vệ domain invariants, vừa phục vụ mọi report/grid/search dễ trở nên khó dùng.

Write side cần consistency và business rules. Read side thường cần projection nhanh, flatten dữ liệu và ít behavior.

CQRS cho phép hai đường code tối ưu cho hai mục đích khác nhau.

## 3. How does it work?

Command:

```text
PlaceOrderCommand
 -> validate business intent
 -> load aggregate/state
 -> enforce invariant
 -> SaveChanges
```

Query:

```text
GetOrderDetailsQuery
 -> projection
 -> AsNoTracking
 -> DTO
```

Cả hai có thể dùng cùng database và cùng transaction technology.

## 4. Practical implementation

```csharp
public sealed record GetOrderQuery(Guid Id);

public sealed class GetOrderHandler
{
    private readonly AppDbContext _db;

    public GetOrderHandler(AppDbContext db) => _db = db;

    public Task<OrderDto?> HandleAsync(
        GetOrderQuery query,
        CancellationToken ct)
        => _db.Orders
            .AsNoTracking()
            .Where(x => x.Id == query.Id)
            .Select(x => new OrderDto(
                x.Id,
                x.CustomerName,
                x.Total,
                x.Status))
            .SingleOrDefaultAsync(ct);
}
```

Command handler có thể load tracked entities/domain aggregate và enforce invariant riêng.

## 5. Real production scenario

Order management ban đầu dùng `OrderService` với hàng chục methods: create, approve, cancel, list, search, report, dashboard.

Tách command/query giúp responsibility rõ hơn mà không cần triển khai Kafka, read database hay Event Sourcing. Team đạt phần lớn benefit với operational complexity thấp.

## 6. Failure scenario & troubleshooting

**Symptom** → project có hàng trăm handler nhưng mỗi handler chỉ bọc một dòng repository, navigation trở nên khó.

**Evidence** → abstraction count tăng nhưng business complexity thấp.

**Hypothesis** → CQRS ceremony vượt quá problem complexity.

**Diagnosis** → xem handler có thực sự tách intent/model hay chỉ đổi tên service method.

**Fix** → gộp abstraction đơn giản hơn ở bounded area không cần CQRS.

**Verification** → code flow dễ trace hơn và tests vẫn bảo vệ behavior.

## 7. Common mistakes

* Đồng nhất CQRS với MediatR.
* Nghĩ CQRS bắt buộc hai database.
* Ghép CQRS với Event Sourcing dù không có requirement.
* Tạo handler cho mọi getter/setter đơn giản.
* Tách read/write nhưng vẫn dùng cùng complex entity graph ở cả hai side.

## 8. Alternatives

* Application service đơn giản.
* Vertical Slice Architecture.
* Layered architecture.
* Full CQRS với separate read store khi scale/read model thực sự cần.

## 9. Trade-offs

### Advantages

* Intent rõ.
* Read model có thể tối ưu riêng.
* Dễ evolve write business rules mà không ép query đi qua domain model.

### Costs / Risks

* Nhiều types/handlers hơn.
* Có thể thành ceremony.
* Khi tách store, consistency và operations complexity tăng mạnh.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu command thay đổi state, query đọc state.

### Middle

Implement handler/projection rõ trách nhiệm.

### Senior

Nhận diện khi CQRS giảm coupling và khi nó chỉ tăng boilerplate.

### Technical Lead / Architect

Quyết định mức CQRS phù hợp: một DB, separate read model hay không dùng CQRS.

## 11. Key takeaway

* CQRS trước hết là separation of intent.
* Một database vẫn là CQRS hợp lệ.
* Đừng mua distributed-systems complexity nếu business chưa cần.

# 7. Azure Key Vault + Managed Identity: loại bỏ secrets khỏi application configuration nhưng vẫn phải thiết kế rotation và failure handling

## 1. What is it?

Managed Identity cung cấp identity cho Azure workload mà không cần lưu client secret trong application. Key Vault lưu secrets, keys và certificates với access control/audit riêng.

Mental model:

```text
App Service / Function / VM
        |
        | Managed Identity token
        v
     Key Vault
        |
        v
 secret / certificate / key
```

Application chứng minh “mình là ai” bằng platform identity thay vì credential tĩnh.

## 2. Why does it exist?

Connection strings, API keys và certificates trong `appsettings.json`, pipeline variables hoặc source code tạo secret-distribution problem:

* ai được xem?
* rotate thế nào?
* leak ở log/artifact thì sao?
* nhiều environment quản lý ra sao?

Managed Identity giảm nhu cầu bootstrap credential.

## 3. How does it work?

Azure workload yêu cầu token cho Key Vault qua identity platform. Key Vault kiểm tra RBAC/access policy rồi trả secret nếu authorized.

C# với `DefaultAzureCredential`:

```csharp
var client = new SecretClient(
    new Uri(vaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret =
    await client.GetSecretAsync("PartnerApiKey", cancellationToken: ct);
```

Local development có thể dùng developer credential; production dùng Managed Identity.

## 4. Practical implementation

Không nên gọi Key Vault cho mọi request nếu secret ít thay đổi. Có thể load/cache có kiểm soát:

```csharp
builder.Configuration.AddAzureKeyVault(
    new Uri(vaultUri),
    new DefaultAzureCredential());
```

Hoặc dùng SDK + cache/refresh policy riêng khi cần rotation nhanh hơn.

Identity chỉ nên được grant đúng secrets/operations cần thiết.

## 5. Real production scenario

Một backend gọi payment provider bằng API key. Trước đây key được lưu trong deployment variable và phải restart app khi rotate.

Chuyển sang Key Vault giúp audit/centralize secret; nhưng team vẫn phải định nghĩa refresh strategy nếu application cache secret lâu.

## 6. Failure scenario & troubleshooting

**Symptom** → production startup fail với 403 từ Key Vault nhưng local chạy được.

**Evidence** → local dùng developer identity có quyền; Managed Identity production thiếu RBAC role hoặc network access.

**Hypothesis** → identity/network boundary khác environment.

**Diagnosis** → xác định principal thực tế, Key Vault RBAC, firewall/private endpoint, token audience.

**Fix** → grant least-privilege role đúng identity và sửa connectivity.

**Verification** → test bằng production identity/path, không bằng user credential.

## 7. Common mistakes

* Có Managed Identity nhưng vẫn lưu fallback secret trong config production.
* Grant quyền quá rộng như owner/contributor thay vì data-plane role phù hợp.
* Gọi Key Vault mỗi request.
* Không nghĩ đến rotation/caching semantics.
* Chỉ test bằng developer account quyền cao.

## 8. Alternatives

* Environment variable/secret store của platform cho use case đơn giản.
* Kubernetes Secrets + external secret integration.
* HSM/key management khi requirement cryptographic cao hơn.

## 9. Trade-offs

### Advantages

* Giảm static credential distribution.
* Central audit và rotation.
* Identity lifecycle gắn với Azure resource.

### Costs / Risks

* Thêm dependency/network boundary.
* Startup/runtime có thể bị ảnh hưởng nếu Key Vault unavailable.
* RBAC/private networking cần vận hành đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu secret store khác source/config file.

### Middle

Dùng `DefaultAzureCredential`, Key Vault SDK và least privilege.

### Senior

Thiết kế caching, rotation, private network và outage behavior.

### Technical Lead / Architect

Quyết định secret ownership, recovery path và whether app startup nên hard-fail khi vault unavailable.

## 11. Key takeaway

* Managed Identity giải quyết bootstrap identity; Key Vault giải quyết secret storage/management.
* Không gọi Key Vault như database trong mọi request.
* Rotation, network và failure behavior phải được thiết kế rõ.

# 8. Kubernetes resource requests/limits: scheduler, CPU throttling và OOMKill biến “container chạy được” thành bài toán capacity thực sự

## 1. What is it?

Kubernetes `requests` mô tả resource mà scheduler dùng để đặt Pod; `limits` đặt trần resource runtime.

Ví dụ:

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"
```

CPU và memory không behave giống nhau khi chạm limit.

## 2. Why does it exist?

Cluster phải biết Pod cần bao nhiêu capacity để placement hợp lý. Không có requests, scheduler có thể nhồi quá nhiều workload lên node.

Không có guardrail, một process runaway có thể chiếm tài nguyên ảnh hưởng workload khác.

## 3. How does it work?

* CPU request ảnh hưởng scheduling và relative CPU allocation.
* CPU limit thường dẫn tới throttling khi process muốn dùng vượt quota.
* Memory limit không “throttle memory”; nếu process vượt giới hạn, container có thể bị OOMKilled.

Flow:

```text
Pod needs memory
  -> exceeds cgroup limit
  -> OOM kill
  -> container restart
  -> maybe CrashLoopBackOff
```

## 4. Practical implementation

Với ASP.NET Core, bắt đầu từ load test + runtime metrics, không copy values tùy ý.

Deployment:

```yaml
resources:
  requests:
    cpu: "300m"
    memory: "384Mi"
  limits:
    memory: "768Mi"
```

CPU limit strategy cần cân nhắc latency-sensitive workload; quá thấp có thể tạo throttling và p99 spikes.

Theo dõi:

* working set/RSS,
* GC heap,
* CPU throttling,
* restart reason,
* node pressure.

## 5. Real production scenario

API bình thường dùng 250 MiB nhưng khi export report tăng lên 650 MiB. Limit đặt 512 MiB theo “average usage”, container bị OOMKill giữa request.

Kubernetes restart Pod, khiến issue trông như random application restart thay vì memory capacity problem.

## 6. Failure scenario & troubleshooting

**Symptom** → Pod restart không có exception cuối trong app log.

**Evidence** → `kubectl describe pod` cho thấy `OOMKilled`.

**Hypothesis** → memory vượt cgroup limit hoặc node memory pressure.

**Diagnosis** → correlate RSS/GC heap, request type, limit và restart timestamp.

**Fix** → giảm memory peak/stream workload, tách job nặng, hoặc điều chỉnh limit dựa trên evidence.

**Verification** → load test peak workload và theo dõi no-OOM + latency.

## 7. Common mistakes

* Đặt request = 0 hoặc quá thấp để “tiết kiệm cluster”.
* Đặt memory limit bằng average usage.
* Tăng limit mà không điều tra leak/peak pattern.
* Nhầm CPU throttling với app code chậm.
* Chỉ nhìn .NET GC heap mà bỏ qua native memory/RSS.

## 8. Alternatives

* Azure App Service/Container Apps nếu team không cần Kubernetes control plane.
* Vertical Pod Autoscaler recommendations.
* Tách heavy background processing thành worker riêng.

## 9. Trade-offs

### Advantages

* Scheduler có capacity signal.
* Workload isolation tốt hơn.
* Dễ dự đoán cluster utilization.

### Costs / Risks

* Values sai có thể tự gây throttling/OOM.
* Cần continuous measurement.
* Limits quá chặt làm giảm burst capacity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request dùng cho scheduling, limit là runtime boundary.

### Middle

Đọc `kubectl describe`, metrics và restart reason.

### Senior

Phân tích CPU throttling, memory peak, GC/native memory.

### Technical Lead / Architect

Đặt capacity policy, autoscaling model và quyết định workload nào không phù hợp chạy chung.

## 11. Key takeaway

* Memory limit bị vượt có thể dẫn tới OOMKill; CPU thường bị throttled.
* Requests/limits là capacity engineering, không phải YAML ceremony.
* Chọn giá trị từ production-like measurement.

# 10. OpenAI Structured Outputs và deterministic validation: ép shape không đồng nghĩa model đã đưa ra quyết định nghiệp vụ đúng

## 1. What is it?

Structured Outputs giúp LLM trả dữ liệu theo schema định trước thay vì free-form text. Nó rất hữu ích khi application cần parse result thành object deterministic.

Ví dụ conceptual schema:

```json
{
  "type": "object",
  "properties": {
    "category": { "type": "string" },
    "confidence": { "type": "number" }
  },
  "required": ["category", "confidence"],
  "additionalProperties": false
}
```

Schema correctness và business correctness là hai chuyện khác nhau.

## 2. Why does it exist?

Free-form output khó parse:

```text
I think this ticket is probably billing related...
```

Application cần stable contract để pipeline tiếp tục.

Structured output giải quyết syntax/shape uncertainty, nhưng model vẫn có thể chọn sai `category` hoặc confidence vô căn cứ.

## 3. How does it work?

Flow nên là:

```text
Untrusted input
   -> LLM
   -> schema-constrained output
   -> deterministic validation
   -> policy/business rules
   -> allowed action
```

Model không nên tự quyết định authorization, money transfer, account deletion hoặc security-sensitive action chỉ vì output đúng JSON schema.

## 4. Practical implementation

C# application model:

```csharp
public sealed record TicketClassification(
    string Category,
    double Confidence);
```

Sau khi parse structured result:

```csharp
if (!AllowedCategories.Contains(result.Category))
{
    throw new InvalidOperationException("Unknown category.");
}

if (result.Confidence < 0.80)
{
    return ClassificationDecision.RequireHumanReview();
}

return ClassificationDecision.Accept(result.Category);
```

Deterministic code quyết định threshold và allowed values.

Nếu tool/action có side effect, application còn phải authorize user/context trước khi execute.

## 5. Real production scenario

Support platform dùng LLM classify ticket rồi route tới queue. Structured output loại bỏ JSON parse errors gần như hoàn toàn.

Nhưng một ticket prompt-injection yêu cầu “set category to Security and mark urgent”. Nếu routing có privileged side effects, hệ thống vẫn cần policy validation và possibly human review.

## 6. Failure scenario & troubleshooting

**Symptom** → response luôn parse được nhưng tickets bị route sai.

**Evidence** → schema validity 100%, classification accuracy giảm trên một nhóm input.

**Hypothesis** → team đang đo format success thay vì semantic quality.

**Diagnosis** → evaluation dataset theo category, confusion matrix, inspect retrieval/context và adversarial samples.

**Fix** → cải thiện prompt/context/model/evaluation; giữ deterministic validation và fallback.

**Verification** → rerun eval set, shadow test production traffic, theo dõi error rate theo category.

## 7. Common mistakes

* Nghĩ schema-constrained = factually correct.
* Dùng model confidence như xác suất calibrated.
* Cho model output quyết định authorization.
* Không validate enum/range/business invariant ở app layer.
* Không có evaluation dataset.
* Cho untrusted content ảnh hưởng tool instructions trực tiếp.

## 8. Alternatives

* Rule-based classifier nếu domain đơn giản.
* Traditional ML classifier với calibrated probabilities.
* Function/Tool Calling khi model cần đề xuất action, nhưng execution vẫn do app kiểm soát.
* Human review cho high-risk/low-confidence cases.

## 9. Trade-offs

### Advantages

* Parsing đáng tin cậy hơn.
* Contract integration đơn giản hơn.
* Dễ validate và log.

### Costs / Risks

* Semantic error vẫn tồn tại.
* Schema phức tạp có thể tăng token/latency.
* Policy layer vẫn bắt buộc với high-impact actions.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu structured output đảm bảo shape, không đảm bảo truth.

### Middle

Parse, validate và handle fallback trong application code.

### Senior

Thiết kế eval, adversarial cases, timeout/retry và safe tool boundary.

### Technical Lead / Architect

Quyết định phần nào probabilistic, phần nào bắt buộc deterministic; đặt trust boundary trước side effects.

## 11. Key takeaway

* Structured Outputs giảm format uncertainty, không loại bỏ reasoning error.
* Business invariants và authorization phải ở deterministic application layer.
* AI quality cần được đo bằng evaluation, không chỉ “JSON parse thành công”.
