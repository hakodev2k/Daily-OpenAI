# 1. C# `ValueTask<T>`: giảm allocation trong hot path nhưng chỉ khi hiểu synchronous completion và consumption semantics

## 1. What is it?

`ValueTask<T>` là một awaitable có thể đại diện cho kết quả đã có sẵn **hoặc** một asynchronous operation chưa hoàn thành mà không bắt buộc mỗi lần phải tạo một `Task<T>` object mới.

Mental model:

```text
Task<T>
  -> thường có một object Task đại diện operation

ValueTask<T>
  -> có thể chứa trực tiếp T
  -> hoặc wrap Task<T>
  -> hoặc dùng IValueTaskSource<T>
```

Điểm quan trọng: `ValueTask<T>` là công cụ tối ưu allocation cho một số hot path, không phải “phiên bản tốt hơn của Task”.

## 2. Why does it exist?

Một API thường hoàn thành synchronously từ cache có thể trả kết quả ngay phần lớn thời gian:

```text
95% cache hit  -> result có sẵn
5% cache miss  -> phải await I/O
```

Nếu mỗi call đều tạo `Task<T>` dù 95% đã có kết quả, allocation có thể trở thành cost đáng kể ở throughput rất cao.

`ValueTask<T>` cho phép synchronous completion không nhất thiết tạo `Task<T>` mới.

## 3. How does it work?

Ví dụ:

```csharp
public ValueTask<User?> GetAsync(Guid id, CancellationToken ct)
{
    if (_cache.TryGetValue(id, out var user))
        return ValueTask.FromResult<User?>(user);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id, ct));
}
```

Caller vẫn dùng:

```csharp
var user = await service.GetAsync(id, ct);
```

Nhưng semantics phức tạp hơn `Task<T>`. Một `ValueTask<T>` không nên mặc định được await nhiều lần, lưu lâu dài hoặc dùng với các combinators như `Task.WhenAll` mà không chuyển sang `Task` khi cần.

## 4. Practical implementation

Một use case hợp lý là component cache-heavy:

```csharp
public sealed class CountryLookup
{
    private readonly Dictionary<string, Country> _cache;
    private readonly ICountryRepository _repository;

    public ValueTask<Country?> FindAsync(
        string code,
        CancellationToken ct)
    {
        if (_cache.TryGetValue(code, out var country))
            return ValueTask.FromResult<Country?>(country);

        return new ValueTask<Country?>(
            _repository.FindAsync(code, ct));
    }
}
```

Nếu caller cần retain hoặc await nhiều lần:

```csharp
Task<Country?> task = lookup.FindAsync(code, ct).AsTask();
```

Nhưng khi phải gọi `AsTask()` thường xuyên, lợi ích ban đầu có thể biến mất.

## 5. Real production scenario

Một metadata service được gọi hàng triệu lần mỗi phút và gần như luôn trả dữ liệu từ in-memory cache. Allocation profile cho thấy lượng lớn short-lived `Task<T>` objects dù dependency I/O rất hiếm.

Sau benchmark thực tế, chuyển riêng hot API đó sang `ValueTask<T>` giảm allocation và GC pressure. Team không đổi tất cả service methods sang `ValueTask<T>` vì phần lớn methods luôn thực hiện database/network I/O và không có synchronous fast path.

## 6. Failure scenario & troubleshooting

**Symptom** → code hoạt động trong test đơn giản nhưng xuất hiện undefined/invalid behavior khi một `ValueTask` được consume nhiều lần hoặc được convert/combine sai cách.

**Evidence** → cùng instance `ValueTask<T>` bị await nhiều lần; underlying implementation dùng `IValueTaskSource<T>`.

**Hypothesis** → caller đang áp semantics của reusable `Task<T>` cho `ValueTask<T>`.

**Diagnosis** → kiểm tra lifetime và số lần consume của awaitable; review API contract.

**Fix** → await một lần; nếu operation phải được lưu/reuse/combine, chuyển sang `Task<T>` bằng `AsTask()` hoặc giữ API là `Task<T>` từ đầu.

**Verification** → concurrency tests + allocation benchmark xác nhận correctness và lợi ích performance.

## 7. Common mistakes

- Đổi mọi `Task<T>` sang `ValueTask<T>` vì nghĩ nhanh hơn.
- Benchmark không có realistic synchronous-completion ratio.
- Await cùng `ValueTask<T>` nhiều lần.
- Lưu `ValueTask<T>` trong field/cache.
- Dùng nó ở API public chỉ để tiết kiệm allocation không đáng kể.
- Bỏ qua việc struct lớn hơn cũng có copy cost.

## 8. Alternatives

- `Task<T>`: default tốt, semantics đơn giản, reusable/composable tốt.
- Synchronous method: đúng hơn nếu operation luôn synchronous.
- Cache + `Task.FromResult`: đơn giản nhưng vẫn có allocation/caching semantics riêng.

## 9. Trade-offs

### Advantages

- Có thể giảm allocation khi synchronous completion xảy ra thường xuyên.
- Hữu ích cho high-throughput libraries/hot paths.

### Costs / Risks

- Consumption rules phức tạp hơn.
- API ergonomics kém hơn `Task<T>`.
- Lợi ích bằng 0 hoặc âm nếu operation hầu như luôn asynchronous.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task<T>` vẫn là lựa chọn mặc định; `ValueTask<T>` không phải syntax async mới.

### Middle

Biết synchronous completion và quy tắc await một lần.

### Senior

Chỉ áp dụng sau profiler/benchmark và hiểu allocation-vs-complexity trade-off.

### Technical Lead / Architect

Quyết định API surface nào được phép dùng performance-oriented abstraction, tránh để micro-optimization lan thành convention toàn codebase.

## 11. Key takeaway

- `ValueTask<T>` tối ưu một pattern rất cụ thể: frequent synchronous completion.
- `Task<T>` vẫn là default khi simplicity/composability quan trọng hơn micro-allocation.
- Đo allocation trước và sau; không tối ưu theo cảm giác.

# 2. ASP.NET Core file upload streaming & security: nhận file lớn mà không làm OOM và không biến upload endpoint thành attack surface

## 1. What is it?

File upload endpoint nhận untrusted binary data từ client. Hai vấn đề phải giải quyết đồng thời:

1. **resource handling** — không buffer file lớn vô hạn trong RAM/disk;
2. **security boundary** — không tin filename, MIME type hoặc content do client khai báo.

Mental model:

```text
Client
  -> reverse proxy limits
  -> ASP.NET Core request limits
  -> stream/temporary storage
  -> validation/scanning
  -> durable storage
  -> metadata persistence
```

## 2. Why does it exist?

Naive implementation thường đọc toàn bộ file vào `byte[]` hoặc `MemoryStream`. Với 100 concurrent uploads × 200 MB, memory pressure có thể phá process trước khi business logic chạy xong.

Mặt khác, file upload là attack surface phổ biến: path traversal, executable content, zip bomb, oversized payload, fake MIME type, malware hoặc file parser vulnerabilities.

## 3. How does it work?

ASP.NET Core có thể bind `IFormFile`, nhưng multipart form processing có buffering thresholds/temporary-file behavior. Với file rất lớn hoặc throughput cao, explicit streaming giúp kiểm soát memory tốt hơn.

Resource controls nên tồn tại ở nhiều lớp:

```text
Edge/reverse proxy request limit
        |
ASP.NET Core body/form limit
        |
application business size limit
        |
stream processing + cancellation
```

Security validation phải dựa trên server-generated storage name và content policy, không phải original filename.

## 4. Practical implementation

Một implementation đơn giản cho upload stream:

```csharp
app.MapPost("/uploads", async (
    HttpRequest request,
    IBlobStore blobStore,
    CancellationToken ct) =>
{
    if (request.ContentLength is > 50 * 1024 * 1024)
        return Results.Problem(statusCode: 413, title: "File too large");

    var contentType = request.ContentType;
    if (contentType is not "application/pdf")
        return Results.BadRequest(new { error = "unsupported_type" });

    var storageKey = $"uploads/{Guid.NewGuid():N}";

    await blobStore.WriteAsync(storageKey, request.Body, ct);

    return Results.Accepted(value: new { id = storageKey });
});
```

Production code cần kiểm tra magic bytes/signature khi format cho phép, virus/malware scanning nếu threat model yêu cầu, checksum, business ownership và quarantine trước khi public-serving.

Không dùng trực tiếp:

```csharp
Path.Combine(root, uploadedFile.FileName)
```

vì original filename là untrusted metadata.

## 5. Real production scenario

Một CMS cho editor upload PDF/images. Ban đầu server nhận `IFormFile`, copy vào `MemoryStream`, rồi mới upload Azure Blob Storage. Khi marketing upload nhiều video/image assets đồng thời, pod/App Service memory tăng đột biến và GC pressure kéo theo latency toàn website.

Chuyển sang streaming trực tiếp tới quarantine blob container giúp memory ổn định. Sau đó background scanner validate content rồi mới promote sang public asset container.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng mạnh hoặc process restart khi nhiều uploads đồng thời.

**Evidence** → allocation trace cho thấy `byte[]`/`MemoryStream` rất lớn; upload handler materialize toàn file.

**Hypothesis** → request path đang buffering toàn payload.

**Diagnosis** → inspect proxy limits, form options, temporary-file behavior, application code và concurrent upload count.

**Fix** → stream, đặt size/concurrency limits, dùng external object storage và quarantine workflow.

**Verification** → load test bằng file sát size limit; theo dõi working set, temp disk, request duration và rejected oversized requests.

## 7. Common mistakes

- Tin `Content-Type` do client gửi.
- Dùng extension để quyết định file an toàn.
- Lưu file bằng original filename.
- Cho upload vào web root rồi serve trực tiếp.
- Không giới hạn decompression/archive expansion.
- Đọc toàn bộ file vào RAM.
- Không propagate cancellation khi client disconnect.
- Log raw file content hoặc sensitive filenames.

## 8. Alternatives

- **Direct-to-Blob upload bằng SAS/presigned URL:** application không proxy toàn bytes; tốt cho file lớn.
- **API-mediated streaming:** hợp lý khi server cần kiểm soát upload path trực tiếp.
- **Background ingestion:** tốt khi validation/scanning/transcoding lâu.

## 9. Trade-offs

### Advantages

- Streaming giảm memory pressure.
- Quarantine tách untrusted content khỏi public serving.
- Direct-to-object-storage giảm application bandwidth.

### Costs / Risks

- Workflow phức tạp hơn synchronous save.
- Cần cleanup orphaned/quarantined objects.
- Malware/content validation có latency và operational cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu file từ client là untrusted data; filename/MIME không đáng tin.

### Middle

Implement size limit, streaming, generated storage key và cancellation.

### Senior

Thiết kế quarantine, scanning, concurrency budget, object storage và abuse protection.

### Technical Lead / Architect

Quyết định bytes đi qua app hay direct-to-storage, retention/scan policy, public-serving boundary và ownership khi validation fail.

## 11. Key takeaway

- Upload endpoint vừa là performance boundary vừa là security boundary.
- Không materialize file lớn nếu không cần.
- Untrusted upload nên được giới hạn, quarantine và validate trước khi sử dụng/public-serving.

# 3. EF Core `ExecuteUpdate` / `ExecuteDelete`: bulk mutation hiệu quả nhưng có thể làm Change Tracker lệch khỏi database

## 1. What is it?

`ExecuteUpdateAsync` và `ExecuteDeleteAsync` cho phép EF Core gửi `UPDATE`/`DELETE` trực tiếp xuống database từ LINQ query mà không phải load từng entity vào memory rồi gọi `SaveChanges`.

Mental model:

```text
Traditional tracked update
SELECT rows -> materialize -> track -> modify -> SaveChanges -> UPDATE(s)

ExecuteUpdate
LINQ predicate -> single UPDATE statement
```

## 2. Why does it exist?

Nếu cần mark 100,000 expired sessions thành inactive, load 100,000 entities chỉ để đổi một field tạo network, allocation và Change Tracker overhead rất lớn.

Set-based SQL là abstraction tự nhiên hơn cho bulk mutation.

## 3. How does it work?

Ví dụ:

```csharp
await db.Sessions
    .Where(x => x.ExpiresAtUtc < now && x.IsActive)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.IsActive, false)
        .SetProperty(x => x.UpdatedAtUtc, now), ct);
```

EF Core tạo SQL gần với:

```sql
UPDATE Sessions
SET IsActive = 0,
    UpdatedAtUtc = @now
WHERE ExpiresAtUtc < @now
  AND IsActive = 1;
```

Không có entity instances được tracked cho rows đó.

## 4. Practical implementation

Delete expired ephemeral records:

```csharp
var deleted = await db.ApiTokens
    .Where(x => x.RevokedAtUtc != null && x.RevokedAtUtc < cutoff)
    .ExecuteDeleteAsync(ct);
```

Nếu cùng `DbContext` đã track entity liên quan, cần cẩn thận:

```csharp
var session = await db.Sessions.FindAsync([id], ct);

await db.Sessions
    .Where(x => x.Id == id)
    .ExecuteUpdateAsync(s => s
        .SetProperty(x => x.IsActive, false), ct);

// session.IsActive có thể vẫn là true trong memory.
```

## 5. Real production scenario

Nightly cleanup job phải expire hàng triệu soft-state rows. Phiên bản cũ load entities theo batch và `SaveChanges`, khiến memory và DB round trips tăng cao.

Set-based `ExecuteUpdate` giảm round trips đáng kể. Nhưng job được tách khỏi request `DbContext` để tránh tracked-state confusion.

## 6. Failure scenario & troubleshooting

**Symptom** → database đã đổi nhưng code tiếp tục dùng entity cũ và sau đó `SaveChanges` ghi ngược giá trị.

**Evidence** → cùng context vừa track entity, vừa chạy `ExecuteUpdate`; Change Tracker không được đồng bộ tự động.

**Hypothesis** → direct database mutation bypass tracked state.

**Diagnosis** → inspect `ChangeTracker.Entries()` và command order.

**Fix** → tránh mix tracked mutation với bulk direct mutation trong cùng unit of work; reload/clear tracker khi boundary thực sự cần.

**Verification** → integration test trên provider thật với entity tracked trước/sau bulk operation.

## 7. Common mistakes

- Nghĩ `ExecuteUpdate` tương đương sửa entity rồi `SaveChanges`.
- Mong domain events/interceptors trên entity mutation tự chạy như trước.
- Bulk update business-critical rows mà bỏ optimistic concurrency predicate.
- Chạy query quá rộng không có index/predicate kiểm chứng.
- Không xem locks/log growth cho mass update.

## 8. Alternatives

- Tracked updates: tốt khi business invariant/domain behavior cần chạy trên từng aggregate.
- Raw SQL: linh hoạt hơn nhưng ít type-safe hơn.
- Bulk libraries: hữu ích khi cần insert/upsert/batch capabilities ngoài built-in APIs.

## 9. Trade-offs

### Advantages

- Ít round trips và allocations.
- Dùng set-based database operation hiệu quả.
- Code vẫn dựa trên LINQ predicate.

### Costs / Risks

- Bypass Change Tracker.
- Có thể bypass domain behavior/interceptors dựa trên tracked entities.
- Mass mutation có lock/log impact lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu direct bulk update không load entities.

### Middle

Biết dùng `ExecuteUpdate/Delete` với predicate chính xác và test SQL behavior.

### Senior

Reasoning về tracker divergence, concurrency, locking và domain invariant bypass.

### Technical Lead / Architect

Đặt boundary: operational/bulk maintenance dùng set-based mutation; aggregate business behavior không bị biến thành raw data mutation chỉ để nhanh hơn.

## 11. Key takeaway

- Set-based mutation rất mạnh khi không cần per-entity behavior.
- `ExecuteUpdate/Delete` bypass Change Tracker.
- Performance optimization không được phá business invariant boundary.

# 4. PostgreSQL partial index: index đúng tập dữ liệu thực sự cần truy vấn thay vì trả write/storage cost cho toàn bảng

## 1. What is it?

Partial index là index chỉ chứa rows thỏa một predicate.

Ví dụ hệ thống có 50 triệu jobs nhưng chỉ vài nghìn jobs ở trạng thái `Pending`:

```sql
CREATE INDEX ix_jobs_pending_created_at
ON jobs (created_at)
WHERE status = 'Pending';
```

Index này không chứa `Completed`, `Cancelled`, `Failed` rows.

## 2. Why does it exist?

Một full index trên `(status, created_at)` có thể rất lớn và phải được maintain cho mọi write dù application chủ yếu cần tìm active/pending subset rất nhỏ.

Partial index giảm:

- index size;
- write maintenance;
- cache footprint;

khi access pattern tập trung vào một subset ổn định.

## 3. How does it work?

Planner chỉ dùng partial index khi có thể chứng minh query predicate phù hợp với index predicate.

Index:

```sql
WHERE deleted_at IS NULL
```

Query:

```sql
SELECT id, created_at
FROM documents
WHERE deleted_at IS NULL
ORDER BY created_at DESC
LIMIT 50;
```

có thể tận dụng index phù hợp.

Nhưng một query có semantics khác không tự động được index hỗ trợ chỉ vì nhìn “gần giống”.

## 4. Practical implementation

Soft-delete table:

```sql
CREATE INDEX ix_customers_active_email
ON customers (email)
WHERE deleted_at IS NULL;
```

Kiểm tra bằng:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, email
FROM customers
WHERE deleted_at IS NULL
  AND email = 'a@example.com';
```

Đừng chỉ nhìn `Execution Time`; xem actual rows, buffers và scan type.

## 5. Real production scenario

Workflow table giữ 3 năm lịch sử, nhưng worker chỉ poll `Pending` records. Full index ngày càng lớn trong khi pending rows luôn dưới 0.1% tổng dữ liệu.

Partial index trên pending state giúp poll query nhỏ và cache-friendly hơn, đồng thời giảm index maintenance cho completed history.

## 6. Failure scenario & troubleshooting

**Symptom** → partial index tồn tại nhưng query vẫn sequential scan/full index scan.

**Evidence** → predicate query dùng expression/parameter semantics mà planner không chứng minh tương thích, hoặc selectivity không còn tốt.

**Hypothesis** → query predicate không match index predicate hoặc statistics/cost cho thấy index không có lợi.

**Diagnosis** → `EXPLAIN (ANALYZE, BUFFERS)`, inspect exact predicate và data distribution.

**Fix** → align query/index semantics, cập nhật statistics khi cần, hoặc bỏ partial index nếu workload đã thay đổi.

**Verification** → benchmark representative values và write workload.

## 7. Common mistakes

- Tạo partial index cho predicate thay đổi liên tục theo business rule.
- Tưởng index nhỏ nghĩa write cost bằng 0.
- Không kiểm tra query planner thực sự sử dụng index.
- Duplicate full + partial indexes không cần thiết.
- Dùng `WHERE created_at > now() - interval ...` như một dynamic assumption mà không hiểu index predicate constraints/lifecycle.

## 8. Alternatives

- Composite full index: phù hợp khi nhiều states đều được query thường xuyên.
- Partitioning: phù hợp khi data lifecycle/volume yêu cầu physical partition boundaries.
- Archiving/history table: giảm active table size nếu business lifecycle cho phép.

## 9. Trade-offs

### Advantages

- Index nhỏ hơn.
- Tốt cho sparse active subset.
- Giảm cache/write cost so với full index tương đương.

### Costs / Risks

- Query phải match predicate semantics.
- Access pattern thay đổi có thể làm index mất giá trị.
- Tăng schema-specific knowledge cho team.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không nhất thiết chứa mọi row.

### Middle

Biết tạo partial index và đọc `EXPLAIN ANALYZE`.

### Senior

Đánh giá selectivity, write cost, planner behavior và data lifecycle.

### Technical Lead / Architect

Quyết định khi partial index là tối ưu bền vững hay chỉ vá access pattern đang cần redesign/partition/archive.

## 11. Key takeaway

- Partial index mạnh khi hot subset nhỏ và predicate ổn định.
- Query planner evidence quan trọng hơn assumption.
- Index design phải xét cả reads, writes và data lifecycle.

# 5. Azure Cosmos DB consistency levels & session tokens: consistency là product behavior chứ không chỉ database setting

## 1. What is it?

Cosmos DB cung cấp nhiều consistency levels như Strong, Bounded Staleness, Session, Consistent Prefix và Eventual. Chúng mô tả client được đảm bảo nhìn thấy writes mới đến mức nào trong hệ thống phân tán.

Session consistency đặc biệt phổ biến vì cho phép một logical client/session đọc lại chính writes của mình thông qua session token trong khi vẫn giữ scalability tốt hơn Strong ở nhiều topology.

## 2. Why does it exist?

Distributed replicas tạo trade-off:

```text
write ở replica/region A
   -> replication cần thời gian
   -> read ở nơi khác có thể xảy ra trước khi update lan tới
```

Không phải mọi use case cần cùng consistency.

- Bank balance confirmation có requirement khác product catalog.
- User vừa đổi profile thường kỳ vọng refresh thấy dữ liệu mới.
- Analytics feed có thể chấp nhận vài giây stale.

## 3. How does it work?

Với Session consistency:

```text
Client writes item
   -> Cosmos returns session token
Client sends token on later reads
   -> read observes session progress guarantee
```

SDK thường quản lý session tokens cho cùng client instance. Nhưng nếu application tách request qua nhiều independent clients/services, assumption “read-your-writes luôn tự nhiên” có thể không còn đúng theo flow mong muốn.

## 4. Practical implementation

Trong .NET, giữ `CosmosClient` long-lived thay vì tạo mỗi request:

```csharp
builder.Services.AddSingleton(_ =>
    new CosmosClient(
        connectionString,
        new CosmosClientOptions
        {
            ConsistencyLevel = ConsistencyLevel.Session
        }));
```

Application không nên nâng toàn database lên Strong chỉ để xử lý một màn hình cần immediate feedback. Có thể thiết kế request flow, session token propagation hoặc response echo phù hợp hơn tùy requirement.

## 5. Real production scenario

User cập nhật shipping address rồi ngay lập tức GET profile qua một khác service instance. Thỉnh thoảng UI thấy address cũ.

Team ban đầu gọi đó là “Cosmos bug”, nhưng root cause là read path không giữ expected session context và architecture không định nghĩa read-your-write requirement xuyên services.

## 6. Failure scenario & troubleshooting

**Symptom** → user vừa write thành công nhưng read kế tiếp đôi lúc trả version cũ.

**Evidence** → write/read qua different service/client context; configured consistency là Session/Eventual; telemetry cho thấy replicas/regions khác nhau.

**Hypothesis** → consistency expectation của product cao hơn guarantee thực tế của request flow.

**Diagnosis** → map write/read path, client lifetime, region routing và consistency/session token behavior.

**Fix** → giữ session semantics đúng, propagate required context hoặc chọn stronger consistency chỉ tại nơi business thực sự cần và platform hỗ trợ.

**Verification** → integration tests thực hiện immediate write→read qua topology production-like.

## 7. Common mistakes

- Nghĩ eventual consistency nghĩa dữ liệu “có thể sai mãi mãi”.
- Chọn Strong mặc định vì nghe an toàn hơn.
- Tạo `CosmosClient` mỗi request.
- Không định nghĩa product expectation về stale reads.
- Nhầm session/user login session với exact internal session-token semantics.

## 8. Alternatives

- SQL database với transaction/replica semantics phù hợp.
- Application response dùng write result trực tiếp thay vì read lại ngay.
- Event-driven projection khi stale read là explicit part của architecture.

## 9. Trade-offs

### Advantages

- Có spectrum consistency để phù hợp latency/availability requirement.
- Session thường cân bằng tốt cho user-centric workloads.

### Costs / Risks

- Weaker consistency yêu cầu product/UI hiểu staleness.
- Stronger guarantees có latency/availability/topology cost.
- Cross-service flow làm session assumptions khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu replicas có thể chưa đồng bộ tức thì.

### Middle

Biết consistency level ảnh hưởng read behavior và giữ client lifecycle đúng.

### Senior

Map consistency guarantee vào user-visible scenarios và multi-region failure modes.

### Technical Lead / Architect

Chọn consistency theo business invariant/SLO, không theo cảm giác; quyết định nơi stale data được chấp nhận và nơi không.

## 11. Key takeaway

- Consistency là business-visible behavior.
- Session consistency hữu ích cho read-your-writes nhưng request topology vẫn quan trọng.
- Đừng mua stronger consistency nếu requirement không cần nó.

# 6. DDD Aggregate boundaries: bảo vệ invariant trong đúng transaction boundary thay vì gom entity theo quan hệ database

## 1. What is it?

Aggregate là một cluster domain objects có một **Aggregate Root** chịu trách nhiệm bảo vệ invariant trong một consistency boundary.

Nó không đơn giản là “object có nhiều child objects” và không được xác định chỉ vì database có foreign key.

Mental model:

```text
Order (Aggregate Root)
  |- OrderLine
  |- ShippingDecision

External code
  -> thay đổi aggregate thông qua Order
  -> invariant được bảo vệ trong boundary
```

## 2. Why does it exist?

Nếu mọi entity có thể bị sửa trực tiếp từ mọi nơi, business rules dễ bị phân tán:

```text
Controller cập nhật Status
Repository cập nhật Total
Job sửa LineItem
SQL script sửa Inventory
```

Không còn chỗ nào đảm bảo invariant như:

> Confirmed order phải có ít nhất một line và total phải bằng tổng hợp lệ của lines.

Aggregate tạo một consistency boundary có ownership rõ.

## 3. How does it work?

Một transaction thường load/change một aggregate root và commit invariant của nó.

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public OrderStatus Status { get; private set; }
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void Confirm()
    {
        if (_lines.Count == 0)
            throw new DomainException("Cannot confirm an empty order.");

        if (Status != OrderStatus.Draft)
            throw new DomainException("Only draft orders can be confirmed.");

        Status = OrderStatus.Confirmed;
    }
}
```

Aggregate references khác thường nên qua ID nếu chúng không cần cùng transaction/invariant.

## 4. Practical implementation

Application service:

```csharp
public async Task ConfirmOrderAsync(Guid orderId, CancellationToken ct)
{
    var order = await repository.GetAsync(orderId, ct)
        ?? throw new OrderNotFoundException(orderId);

    order.Confirm();

    await unitOfWork.SaveChangesAsync(ct);
}
```

Không cần tạo generic repository cho mọi entity. Domain-specific repository hữu ích khi aggregate load/save semantics đáng được che khỏi caller.

## 5. Real production scenario

E-commerce model ban đầu tạo một `Customer` aggregate chứa Orders, Addresses, Payments và Preferences vì tất cả “thuộc customer”. Mỗi update profile phải load/lock graph lớn và concurrent order operations conflict không cần thiết.

Tách consistency boundaries thành Customer Profile, Order, Payment giúp transactions nhỏ hơn và ownership rõ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều optimistic concurrency conflict trên unrelated operations hoặc aggregate load rất lớn.

**Evidence** → root chứa collections khổng lồ và business operations chỉ chạm một phần nhỏ graph.

**Hypothesis** → aggregate boundary quá lớn so với invariant thực tế.

**Diagnosis** → liệt kê invariants cần atomicity, transaction paths và contention points.

**Fix** → tách aggregates theo invariant/transaction boundary; dùng domain events/eventual consistency giữa boundaries khi phù hợp.

**Verification** → concurrency tests và transaction scope cho thấy unrelated updates không còn tranh chấp cùng root.

## 7. Common mistakes

- Aggregate = database table group.
- Aggregate = toàn bounded context.
- Expose setters public rồi mong service layer “nhớ rule”.
- Aggregate quá lớn vì object graph tự nhiên nhìn đẹp.
- Aggregate quá nhỏ khiến một invariant luôn cần distributed transaction.
- Đưa HTTP/EF/Azure concerns vào domain model.

## 8. Alternatives

- Transaction script/application service: đủ tốt cho domain CRUD đơn giản.
- Anemic model: không tự động sai nếu business rules rất ít và team giữ logic rõ.
- Rich domain aggregate: đáng giá khi invariants/lifecycle có complexity thực sự.

## 9. Trade-offs

### Advantages

- Business invariant có owner rõ.
- Transaction boundary dễ reasoning.
- Giảm accidental mutation.

### Costs / Risks

- Modeling khó hơn CRUD.
- Boundary sai gây contention hoặc eventual-consistency complexity.
- Rich domain model không đáng nếu business logic quá đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Aggregate Root là entry point bảo vệ business state, không chỉ parent entity.

### Middle

Implement methods giữ invariant và persistence boundary rõ.

### Senior

Thiết kế aggregate size theo transaction/concurrency/invariant evidence.

### Technical Lead / Architect

Quyết định domain có đủ complexity để cần DDD tactical patterns và consistency nào được giữ trong aggregate vs eventual giữa aggregates.

## 11. Key takeaway

- Aggregate boundary được quyết định bởi invariant và transaction, không phải ER diagram.
- Aggregate càng lớn càng tăng contention/lifecycle coupling.
- Đừng dùng rich DDD model nếu simple transaction script đã đủ.

# 7. Inbox Pattern & deduplication: xử lý message at-least-once mà không tạo duplicate business side effects

## 1. What is it?

Inbox Pattern ghi lại message ID đã được consumer xử lý để duplicate delivery có thể được nhận diện và bỏ qua an toàn.

Mental model:

```text
Broker delivers Message M42
    |
Consumer transaction
    |- check Inbox M42
    |- apply business change
    |- insert Inbox M42
    `- commit

Broker redelivers M42
    |
Inbox already exists -> no-op/complete
```

## 2. Why does it exist?

At-least-once messaging có thể redeliver khi:

1. consumer commit DB thành công;
2. process crash trước khi broker nhận `Complete/Ack`;
3. broker gửi lại cùng message.

Nếu handler thực hiện charge, email, points credit hoặc state transition lần nữa, duplicate delivery trở thành duplicate business effect.

## 3. How does it work?

Inbox cần stable message identifier và uniqueness constraint:

```sql
CREATE TABLE InboxMessages (
    Consumer varchar(100) NOT NULL,
    MessageId uuid NOT NULL,
    ProcessedAtUtc timestamptz NOT NULL,
    PRIMARY KEY (Consumer, MessageId)
);
```

Business update + inbox insert nên nằm trong cùng local transaction khi cùng database.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

var alreadyProcessed = await db.InboxMessages
    .AnyAsync(x => x.Consumer == "Billing" &&
                   x.MessageId == message.Id, ct);

if (!alreadyProcessed)
{
    await billing.ApplyPaymentAsync(message.OrderId, message.Amount, ct);

    db.InboxMessages.Add(new InboxMessage
    {
        Consumer = "Billing",
        MessageId = message.Id,
        ProcessedAtUtc = DateTime.UtcNow
    });

    await db.SaveChangesAsync(ct);
}

await tx.CommitAsync(ct);
```

Ở concurrency cao, unique constraint vẫn là final correctness guard; check-then-insert một mình có race.

## 5. Real production scenario

Order service nhận `PaymentCaptured`. Broker redeliver message sau receiver lock timeout. Handler cũ tạo fulfillment request hai lần.

Inbox keyed theo event ID làm second delivery thành no-op. Downstream side effects ngoài database vẫn phải có idempotency key hoặc own dedupe boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng event tạo hai invoices dù consumer “đã check duplicate”.

**Evidence** → hai instances cùng check `AnyAsync=false` trước khi một instance insert inbox row; không có unique constraint hoặc side effect xảy ra ngoài transaction.

**Hypothesis** → dedupe logic không atomic hoặc side effect nằm ngoài protected boundary.

**Diagnosis** → trace message ID xuyên broker/DB/downstream và kiểm tra unique index/transaction.

**Fix** → unique constraint, atomic local transaction, downstream idempotency key cho external side effect.

**Verification** → fault-injection test crash sau DB commit nhưng trước message acknowledgement; replay same message nhiều lần.

## 7. Common mistakes

- Dùng payload hash không ổn định thay message ID.
- Lưu inbox sau side effect nhưng ngoài transaction.
- Giữ inbox vô hạn không có retention strategy.
- Tưởng dedupe transport đồng nghĩa exactly-once business semantics.
- Không namespace message ID theo consumer/context khi cần.

## 8. Alternatives

- Idempotent state transition: ví dụ `UPDATE ... WHERE Status='Pending'` có thể tự nhiên chống duplicate.
- Broker duplicate detection: hữu ích nhưng không bảo vệ mọi application failure window.
- Exactly-once platform semantics: vẫn cần hiểu boundary nào thực sự được guarantee.

## 9. Trade-offs

### Advantages

- Chống duplicate delivery có bằng chứng rõ.
- Dùng local transaction quen thuộc.
- Dễ audit/replay hơn handler chỉ “hy vọng message đến một lần”.

### Costs / Risks

- Thêm write/storage cho mỗi message.
- Retention/cleanup cần quản lý.
- External side effects vẫn cần idempotency riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu broker có thể giao cùng message nhiều lần.

### Middle

Implement message ID, inbox table và unique constraint.

### Senior

Reasoning về crash windows, transaction boundaries và external side effects.

### Technical Lead / Architect

Chọn nơi dedupe thật sự cần, retention policy và idempotency contract xuyên service boundaries.

## 11. Key takeaway

- At-least-once delivery phải giả định duplicate.
- Inbox + local transaction bảo vệ database side effect tốt hơn check memory.
- Exactly-once business outcome thường đến từ idempotency, không từ niềm tin vào transport.

# 8. Azure Front Door vs Application Gateway: phân biệt global edge routing và regional Layer-7 ingress trước khi ghép thêm hạ tầng

## 1. What is it?

Azure Front Door và Application Gateway đều xử lý HTTP(S), routing và có security capabilities, nhưng chúng nằm ở các vị trí kiến trúc khác nhau.

Mental model đơn giản:

```text
Internet users globally
        |
 Azure Front Door
   global edge
        |
  region / origin
        |
Application Gateway
 regional VNet ingress
        |
 App Service / AKS / VM
```

Không phải hệ thống nào cũng cần cả hai.

## 2. Why does it exist?

Front Door giải quyết global entry point, edge routing/failover/acceleration và edge WAF scenarios.

Application Gateway giải quyết regional Layer-7 load balancing và ingress gần/private với VNet-hosted backends.

Nếu chỉ hỏi “cái nào là load balancer tốt hơn” sẽ bỏ qua network boundary thật.

## 3. How does it work?

**Front Door** hoạt động qua globally distributed edge POPs. Client kết nối edge gần, rule chọn origin/origin group dựa routing/health.

**Application Gateway** được deploy vào Azure region/VNet, route HTTP traffic đến backend pools trong regional network topology.

```text
DNS -> Front Door edge
        -> health-based origin selection
        -> regional gateway/private origin
        -> backend
```

Origin protection phải đảm bảo client không bypass Front Door để gọi backend public trực tiếp nếu security model yêu cầu edge enforcement.

## 4. Practical implementation

Một architecture có thể là:

```text
Users
  |
Front Door Premium + WAF
  |
Private Link / protected origin
  |
App Service
```

Nếu AKS cần regional ingress/private routing phức tạp:

```text
Users
  |
Front Door
  |
Application Gateway / ingress layer
  |
AKS services
```

Nhưng nếu một regional App Service public đơn giản đã đáp ứng requirement, thêm Application Gateway chỉ để “enterprise hơn” tạo thêm cost/operations.

## 5. Real production scenario

E-commerce chạy West Europe + Southeast Asia. Front Door định tuyến users tới healthy/nearby origin và fail over khi một region unhealthy.

Trong mỗi region, private AKS workloads cần Layer-7 routing nội bộ từ regional ingress. Application Gateway có thể phù hợp ở boundary đó.

## 6. Failure scenario & troubleshooting

**Symptom** → Front Door health báo origin unhealthy nhưng gọi backend trực tiếp vẫn 200.

**Evidence** → health probe path/host header/TLS/SNI khác request thật hoặc NSG/private endpoint route chặn edge/gateway path.

**Hypothesis** → network path của probe khác assumption application team.

**Diagnosis** → trace DNS → edge → origin → gateway → backend; kiểm tra health probe config, certificate, host header và private connectivity.

**Fix** → align probe với actual serving path, secure origin access, kiểm tra routing/firewall rules.

**Verification** → controlled origin failure và failover test từ external client.

## 7. Common mistakes

- Dùng cả Front Door và Application Gateway mà không có requirement riêng cho từng layer.
- Để backend public và bypass được WAF edge.
- Health endpoint luôn 200 dù critical dependency/startup chưa ready.
- Nhầm global failover với regional load balancing.
- Không tính TLS certificate/DNS/private connectivity ownership.

## 8. Alternatives

- App Service built-in ingress/custom domain: đơn giản hơn cho single-region/simple apps.
- Azure Load Balancer: Layer-4 use cases.
- AKS ingress/controller/gateway options: phù hợp Kubernetes-specific routing.
- CDN-only service: khi chủ yếu cần static edge caching chứ không application routing.

## 9. Trade-offs

### Advantages

- Front Door: global edge, failover, WAF/acceleration.
- Application Gateway: regional VNet-aware L7 ingress.

### Costs / Risks

- Mỗi layer thêm cost, latency, certificates, rules, logs và incident surface.
- Double proxying làm troubleshooting phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu edge/global khác regional/VNet ingress.

### Middle

Biết routing, probes, TLS và backend pool/origin concepts.

### Senior

Debug end-to-end path, failover, private connectivity và origin protection.

### Technical Lead / Architect

Chọn số lớp tối thiểu đáp ứng global availability/security/network requirements; tránh hạ tầng trùng chức năng.

## 11. Key takeaway

- Front Door và Application Gateway giải quyết boundaries khác nhau.
- Chỉ ghép cả hai khi architecture thực sự cần global edge + regional ingress.
- Health probe và origin protection là production correctness, không phải config phụ.

# 9. CI/CD immutable artifact promotion: build một lần, promote cùng artifact qua environments thay vì rebuild production từ source

## 1. What is it?

Immutable artifact promotion nghĩa là pipeline build/test một artifact cụ thể một lần, sau đó deploy **chính artifact đó** qua Dev/Test/Staging/Production.

```text
commit
  -> build
  -> test
  -> artifact A (immutable)
  -> deploy Dev
  -> validate
  -> promote A to Staging
  -> validate
  -> promote A to Production
```

Production không rebuild artifact mới từ cùng commit nếu có thể tránh.

## 2. Why does it exist?

Nếu mỗi environment tự chạy `dotnet publish`, `npm install` hoặc Docker build riêng:

```text
same source commit
!= necessarily same binary/container
```

Dependency resolution, base image, timestamps, tooling hoặc external feeds có thể thay đổi. “Đã test commit này” không còn đồng nghĩa “đã test binary đang chạy Production”.

## 3. How does it work?

Build stage tạo versioned artifact:

- `.zip`/package;
- Docker image digest;
- NuGet/package;
- deployment bundle.

Artifact được lưu vào repository/registry và được tham chiếu bằng immutable version/digest.

Environment-specific configuration được inject/runtime-bound riêng, không bake secret/environment URL vào artifact khác nhau.

## 4. Practical implementation

Container flow:

```text
Git commit abc123
  -> docker build
  -> image: nexora:1.8.4
  -> digest sha256:XYZ
  -> tests/security scan
  -> Dev deploy sha256:XYZ
  -> Staging deploy sha256:XYZ
  -> Prod deploy sha256:XYZ
```

Trong Octopus/Azure DevOps/TeamCity/Jenkins, release object nên tham chiếu package version đã build, không trigger build mới khi promote.

## 5. Real production scenario

Staging pass với image build sáng thứ Hai. Production pipeline tối thứ Ba rebuild `latest` base image và restore dependency mới patch-level. Production crash do native dependency thay đổi dù git SHA giống Staging.

Immutable promotion loại class drift đó: Production chạy đúng digest đã qua staging validation.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng commit SHA nhưng staging và production có behavior khác nhau ngay startup.

**Evidence** → image/package hashes khác; production pipeline rebuild; package restore/base image version khác.

**Hypothesis** → source identity bị nhầm với artifact identity.

**Diagnosis** → so sánh artifact digest, SBOM, build metadata và pipeline stages.

**Fix** → build once, store immutable artifact, promote by version/digest; config tách khỏi binary.

**Verification** → deployment telemetry ghi exact artifact digest và rollback deploy lại digest trước đó.

## 7. Common mistakes

- Tag Docker chỉ bằng `latest`.
- Rebuild ở mỗi environment.
- Bake environment secrets vào image.
- Không lưu artifact/SBOM đủ lâu để rollback/audit.
- Deploy thành công nhưng không health validate.
- Rollback bằng “rebuild commit cũ” thay vì deploy artifact cũ đã biết.

## 8. Alternatives

- Reproducible builds có thể giảm drift nhưng vẫn không thay lợi ích của exact artifact promotion.
- Source-based deployment có thể đủ cho low-risk internal tooling, nhưng traceability kém hơn.

## 9. Trade-offs

### Advantages

- Traceability mạnh: biết chính xác binary nào đang chạy.
- Rollback nhanh hơn.
- Staging validation có giá trị trực tiếp cho production artifact.

### Costs / Risks

- Cần artifact repository/registry và retention policy.
- Configuration separation phải thiết kế rõ.
- Artifact promotion không cứu được environment-specific infrastructure/config lỗi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu commit và deployable artifact là hai identity khác nhau.

### Middle

Biết version package/image và deploy theo immutable version.

### Senior

Thiết kế build metadata, SBOM, config separation, health gates và rollback.

### Technical Lead / Architect

Đặt release governance: artifact provenance, retention, promotion gates và environment parity theo risk thực tế.

## 11. Key takeaway

- Test artifact nào thì promote đúng artifact đó.
- Git SHA giống nhau không đảm bảo binary giống nhau nếu rebuild.
- Artifact identity/digest là nền tảng của rollback và release audit đáng tin cậy.

# 10. Vue `computed` vs `watch`: derived state nên deterministic, side effect mới cần watcher

## 1. What is it?

Trong Vue, `computed` biểu diễn **derived state** được tính từ reactive dependencies. `watch` quan sát thay đổi và chạy một effect/imperative reaction.

Mental model:

```text
state A + state B
      |
   computed
      |
 derived value

state change
      |
    watch
      |
 side effect: HTTP, storage, analytics, imperative integration
```

## 2. Why does it exist?

Nếu mọi derived value được đồng bộ bằng watchers:

```text
firstName changes -> update fullName
lastName changes  -> update fullName
```

application tạo duplicate mutable state và synchronization bugs.

`computed` giữ một source of truth. `watch` chỉ cần khi thay đổi phải gây side effect ngoài pure derivation.

## 3. How does it work?

```ts
const firstName = ref('Ha')
const lastName = ref('Dinh')

const fullName = computed(() =>
  `${firstName.value} ${lastName.value}`
)
```

Vue track dependencies được đọc trong computed getter và invalidate cache khi dependency thay đổi.

Watcher:

```ts
watch(searchText, async (value, _, onCleanup) => {
  const controller = new AbortController()
  onCleanup(() => controller.abort())

  await searchApi(value, controller.signal)
})
```

Watcher lifecycle/cleanup quan trọng khi effect asynchronous.

## 4. Practical implementation

Bad — duplicate state:

```ts
const items = ref<Item[]>([])
const total = ref(0)

watch(items, value => {
  total.value = value.reduce((sum, x) => sum + x.price, 0)
}, { deep: true })
```

Better:

```ts
const total = computed(() =>
  items.value.reduce((sum, x) => sum + x.price, 0)
)
```

Watcher hợp lý hơn cho persistence:

```ts
watch(theme, value => {
  localStorage.setItem('theme', value)
})
```

## 5. Real production scenario

Filter page có `selectedFilters`, `queryString`, `resultCount` và URL state. Team dùng nhiều watchers cập nhật lẫn nhau, tạo loop/race và state khó debug.

Refactor để query model là computed từ canonical filters; chỉ một watcher đồng bộ URL/trigger external effect. Data flow trở nên một chiều và dễ test hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → API bị gọi nhiều lần, UI flicker hoặc watcher loop sau một user action.

**Evidence** → watcher A mutate state B; watcher B lại mutate state A; async watcher cũ hoàn thành sau watcher mới.

**Hypothesis** → derived state bị model thành imperative synchronization hoặc effect thiếu cleanup.

**Diagnosis** → map reactive sources → computed values → watchers; dùng Vue Devtools và network timeline.

**Fix** → chuyển pure derivation sang `computed`, giảm mutable copies, cleanup/abort stale async effect.

**Verification** → một user action tạo expected number of state transitions/API calls; tests cover rapid changes.

## 7. Common mistakes

- Dùng `watch` để tính value có thể là `computed`.
- Deep-watch object lớn gây expensive traversal.
- Mutate dependency bên trong computed getter.
- Async watcher không cleanup request cũ.
- Hai chiều sync nhiều sources of truth.
- Watch cả store lớn thay vì specific dependency.

## 8. Alternatives

- `computed`: pure derived value.
- `watchEffect`: effect tự track dependencies, tiện nhưng dependency implicit hơn.
- Explicit event/action: tốt khi business transition nên rõ thay vì implicit reactive effect.
- State-management store: phù hợp shared state, nhưng vẫn cần giữ derived state deterministic.

## 9. Trade-offs

### Advantages

- `computed` giữ data flow dễ reasoning và cache derived work.
- `watch` hữu ích cho integration side effects.

### Costs / Risks

- Watcher chain dễ tạo hidden control flow.
- Deep/eager watches có performance cost.
- Async side effects cần cancellation/ordering discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu computed dùng cho giá trị suy ra; watch dùng để phản ứng bằng effect.

### Middle

Biết cleanup async watcher và tránh duplicate mutable state.

### Senior

Thiết kế reactive graph một chiều, giảm hidden coupling và debug race/performance issues.

### Technical Lead / Architect

Đặt frontend state conventions: canonical state ở đâu, derived data ở đâu, side effect boundary ở đâu, khi nào cần store/action thay watcher tự phát.

## 11. Key takeaway

- Pure derived state nên là `computed`.
- `watch` phù hợp side effects, không phải state synchronization mặc định.
- Reactive code dễ maintain nhất khi source of truth ít và data flow một chiều.
