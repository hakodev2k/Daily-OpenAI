# 1. C# `System.Threading.Channels` và bounded backpressure: tách producer khỏi consumer mà không biến queue trong memory thành nguyên nhân OOM

## 1. What is it?

`System.Threading.Channels` cung cấp asynchronous producer-consumer queue trong .NET. Producer ghi items vào `ChannelWriter<T>`, consumer đọc từ `ChannelReader<T>`.

Mental model:

```text
Producers
   |   |   |
   v   v   v
+-------------+
|   Channel   |
| bounded N   |
+-------------+
      |
      v
 Consumers
```

Điểm quan trọng không phải chỉ là “queue trong memory”. Giá trị chính là **coordination + backpressure** giữa tốc độ producer và consumer.

## 2. Why does it exist?

Nếu HTTP requests tạo work nhanh hơn background worker xử lý, một `ConcurrentQueue<T>` unbounded có thể tăng mãi:

```text
incoming = 5,000 items/s
processing = 2,000 items/s
backlog += 3,000 items/s
```

Application vẫn trả 202 rất nhanh nên nhìn bề ngoài khỏe, nhưng memory tăng liên tục cho tới khi process bị OOM hoặc restart.

Bounded channel buộc hệ thống biểu diễn capacity hữu hạn thay vì giả vờ queue là vô hạn.

## 3. How does it work?

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(1000)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true,
    SingleWriter = false
});
```

Với `FullMode = Wait`, khi buffer đầy, `WriteAsync` chờ tới khi consumer tạo chỗ trống.

Flow:

```text
Producer writes
   |
   +-- buffer has capacity --> enqueue
   |
   +-- buffer full ---------> await
                                  |
Consumer reads ------------------+
```

Các mode khác như drop newest/oldest/write có semantics khác và chỉ đúng khi mất work là chấp nhận được.

## 4. Practical implementation

```csharp
public sealed record EmailJob(Guid UserId, string Template);

public sealed class EmailQueue
{
    private readonly Channel<EmailJob> _channel =
        Channel.CreateBounded<EmailJob>(new BoundedChannelOptions(500)
        {
            FullMode = BoundedChannelFullMode.Wait,
            SingleReader = true,
            SingleWriter = false
        });

    public ValueTask EnqueueAsync(EmailJob job, CancellationToken ct) =>
        _channel.Writer.WriteAsync(job, ct);

    public IAsyncEnumerable<EmailJob> ReadAllAsync(CancellationToken ct) =>
        _channel.Reader.ReadAllAsync(ct);
}

public sealed class EmailWorker(
    EmailQueue queue,
    ILogger<EmailWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in queue.ReadAllAsync(stoppingToken))
        {
            try
            {
                await SendEmailAsync(job, stoppingToken);
            }
            catch (Exception ex)
            {
                logger.LogError(ex, "Failed email job {UserId}", job.UserId);
            }
        }
    }
}
```

Nếu work phải survive process restart, Channel không đủ; cần durable broker/database queue.

## 5. Real production scenario

Một ASP.NET Core API nhận webhook, parse payload rồi enqueue notification work. Traffic spike 10x trong campaign. Unbounded queue trước đây giữ hàng trăm nghìn objects và process memory vượt limit.

Bounded Channel giúp team nhìn thấy capacity mismatch sớm: enqueue latency tăng, từ đó API có thể trả 429/503 hoặc chuyển sang durable queue thay vì tiếp tục nhận work không thể xử lý.

## 6. Failure scenario & troubleshooting

**Symptom** → request latency tăng mạnh nhưng CPU không cao; queue depth luôn gần maximum.

**Evidence** → producer đang chờ `WriteAsync`; consumer throughput thấp hơn arrival rate; downstream email API chậm.

**Hypothesis** → downstream throughput là bottleneck, Channel chỉ đang biểu diễn backpressure đúng.

**Diagnosis** → đo queue depth, enqueue wait duration, processing rate và dependency latency.

**Fix** → tăng consumer concurrency có kiểm soát, giảm incoming rate, batch work hoặc dùng durable broker nếu backlog cần tồn tại lâu.

**Verification** → dưới load test, queue depth ổn định và processing rate >= sustainable arrival rate.

## 7. Common mistakes

- Dùng unbounded channel cho work không giới hạn.
- Tăng consumer concurrency vô hạn rồi làm downstream overload.
- Dùng Channel cho critical jobs nhưng không chấp nhận mất queue khi process crash.
- Swallow exception khiến job mất im lặng.
- Không propagate shutdown `CancellationToken`.
- Dùng drop mode mà business không cho phép mất work.

## 8. Alternatives

- `ConcurrentQueue<T>`: primitive đơn giản, không có async backpressure tích hợp.
- Azure Service Bus/RabbitMQ/Kafka: durable, cross-process và phù hợp work cần survive restart.
- TPL Dataflow: mạnh hơn cho multi-stage processing graph nhưng thêm abstraction.
- Direct synchronous processing: đơn giản hơn nếu workload nhỏ và request có thể chờ.

## 9. Trade-offs

### Advantages

- Backpressure rõ ràng.
- API async tốt cho producer-consumer trong một process.
- Allocation/locking behavior tối ưu hơn nhiều custom queue implementations.

### Costs / Risks

- Không durable.
- Queue capacity trở thành tuning parameter cần telemetry.
- Multi-instance application có một queue riêng trên mỗi process.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu producer và consumer có thể chạy khác tốc độ và queue không nên được coi là vô hạn.

### Middle

Biết tạo bounded channel, cancellation, graceful shutdown và worker consumption.

### Senior

Thiết kế concurrency budget, failure handling, backpressure metrics và phân biệt in-memory vs durable work.

### Technical Lead / Architect

Quyết định work nào đủ an toàn với Channel và work nào cần broker; xác định capacity/failure contract toàn hệ thống.

## 11. Key takeaway

- Bounded queue làm capacity hữu hạn trở nên explicit.
- Backpressure là tín hiệu bảo vệ hệ thống, không phải lỗi cần “né”.
- Critical work cần durability thì dùng broker, không dùng Channel như message bus giả.

# 2. ASP.NET Core `ProblemDetails` và exception mapping: biến lỗi thành HTTP contract ổn định mà không làm lộ implementation details

## 1. What is it?

`ProblemDetails` là standardized HTTP error representation theo RFC 7807/9457 style, thường chứa `type`, `title`, `status`, `detail`, `instance` và extensions.

Mental model:

```text
Exception / validation / conflict
           |
           v
Error mapping boundary
           |
           v
Stable HTTP ProblemDetails
```

Mục tiêu là tách internal exception model khỏi public API contract.

## 2. Why does it exist?

Nếu mỗi controller trả một format lỗi khác nhau:

```json
{ "error": "bad request" }
```

```json
{ "message": "invalid", "code": 12 }
```

clients phải viết logic đặc thù cho từng endpoint. Tệ hơn, nếu serialize exception trực tiếp, stack trace, SQL hoặc implementation details có thể bị leak.

Error contract cần ổn định giống success contract.

## 3. How does it work?

Application classify errors ở boundary:

```text
Validation failure    -> 400/422
Resource not found    -> 404
Business conflict     -> 409
Unauthorized          -> 401
Forbidden             -> 403
Unexpected exception  -> 500
```

Không phải exception nào cũng nên map chỉ dựa trên class name. HTTP status phải phản ánh semantics của request/resource.

ASP.NET Core có `AddProblemDetails()` và exception handling middleware để centralize mapping.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails(options =>
{
    options.CustomizeProblemDetails = context =>
    {
        context.ProblemDetails.Extensions["traceId"] =
            context.HttpContext.TraceIdentifier;
    };
});

var app = builder.Build();

app.UseExceptionHandler(exceptionHandlerApp =>
{
    exceptionHandlerApp.Run(async context =>
    {
        var feature = context.Features.Get<IExceptionHandlerFeature>();
        var exception = feature?.Error;

        var (status, title, code) = exception switch
        {
            OrderNotFoundException =>
                (StatusCodes.Status404NotFound, "Order not found", "order_not_found"),

            OrderAlreadyApprovedException =>
                (StatusCodes.Status409Conflict, "Order state conflict", "order_conflict"),

            _ =>
                (StatusCodes.Status500InternalServerError, "Unexpected server error", "internal_error")
        };

        context.Response.StatusCode = status;

        await Results.Problem(
            statusCode: status,
            title: title,
            extensions: new Dictionary<string, object?>
            {
                ["code"] = code,
                ["traceId"] = context.TraceIdentifier
            }).ExecuteAsync(context);
    });
});
```

Production nên log full exception server-side, nhưng trả client chỉ thông tin cần thiết.

## 5. Real production scenario

Một mobile app dựa vào message text “Order already approved” để quyết định hiển thị UI. Sau khi backend đổi wording, app behavior vỡ.

Đúng hơn là dùng machine-readable code ổn định:

```json
{
  "status": 409,
  "title": "Order state conflict",
  "code": "order_already_approved",
  "traceId": "..."
}
```

UI có thể localize message độc lập.

## 6. Failure scenario & troubleshooting

**Symptom** → production API trả 500 cho expected business conflict, hoặc client nhận stack trace/database message.

**Evidence** → exception mapping thiếu case; exception middleware trả `exception.Message` trực tiếp.

**Hypothesis** → internal failure model đang leak qua HTTP boundary hoặc classification sai.

**Diagnosis** → inspect status distribution, response samples, trace ID và server logs.

**Fix** → centralize mapping, define stable error codes, sanitize unexpected failures.

**Verification** → integration tests cho 400/401/403/404/409/500 và assertion rằng 500 không chứa sensitive details.

## 7. Common mistakes

- Trả HTTP 200 kèm `{ success:false }` cho mọi lỗi.
- Map mọi domain exception thành 400.
- Dùng exception cho normal validation flow ở mọi layer.
- Trả stack trace ở production.
- Dùng human-readable message như machine contract.
- Không gắn correlation/trace identifier.

## 8. Alternatives

- Result/Union types ở application layer rồi map sang HTTP tại API boundary.
- Exception mapping phù hợp exceptional/error flow khi codebase convention rõ.
- gRPC status model cho gRPC APIs thay vì ép HTTP ProblemDetails vào protocol khác.

## 9. Trade-offs

### Advantages

- Error contract nhất quán.
- Giảm coupling với implementation.
- Dễ correlation với logs/traces.

### Costs / Risks

- Cần governance cho error codes.
- Mapping layer có thể trở thành giant switch nếu domain boundaries không rõ.
- Quá nhiều generic 500 làm mất actionable semantics; quá nhiều chi tiết lại leak internals.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP status và response body là public contract, không phải nơi dump exception.

### Middle

Biết centralize error handling, validation response và trace IDs.

### Senior

Thiết kế taxonomy của business/system errors, compatibility và observability.

### Technical Lead / Architect

Đặt platform-wide error contract, ownership của error codes và policy về sensitive information.

## 11. Key takeaway

- Internal exception không phải public API contract.
- Status code + stable machine-readable code quan trọng hơn exception message.
- Full diagnostics ở server telemetry; client chỉ nhận dữ liệu an toàn và actionable.

# 3. EF Core compiled queries và query-shape caching: tối ưu query pipeline đúng chỗ thay vì compile cùng một expression shape lặp đi lặp lại

## 1. What is it?

EF Core phải chuyển LINQ expression tree thành database command. EF đã cache translation theo query shape, nhưng với cực kỳ hot query, compiled query có thể giảm thêm overhead của query compilation/cache lookup.

Mental model:

```text
LINQ expression
   -> normalize/query shape
   -> translate
   -> SQL command
   -> execute DB
```

Compiled query tối ưu phần trước execution; nó **không làm database query itself nhanh hơn** nếu bottleneck nằm ở scan, lock hoặc network.

## 2. Why does it exist?

Một endpoint gọi cùng query shape hàng trăm nghìn lần:

```csharp
ctx.Products.SingleAsync(x => x.Id == id)
```

EF Core đã parameterize và cache phần lớn work, nhưng ở micro-hot paths, overhead expression processing có thể vẫn đáng đo.

Compiled query tồn tại cho workload nơi application-side query pipeline thực sự là measurable cost.

## 3. How does it work?

```csharp
private static readonly Func<AppDbContext, Guid, Product?> FindProduct =
    EF.CompileQuery((AppDbContext db, Guid id) =>
        db.Products.AsNoTracking().SingleOrDefault(x => x.Id == id));
```

Query shape được compile một lần thành delegate. Parameter `id` thay đổi nhưng shape giữ nguyên.

Một anti-pattern làm cache kém hiệu quả là dynamic expression chứa constants embedded vào tree thay vì parameters, tạo nhiều shapes khác nhau.

## 4. Practical implementation

Async variant:

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<ProductDto>>
    ProductById = EF.CompileAsyncQuery(
        (AppDbContext db, Guid id) =>
            db.Products
                .AsNoTracking()
                .Where(x => x.Id == id)
                .Select(x => new ProductDto(x.Id, x.Name, x.Price)));
```

Usage:

```csharp
await foreach (var product in ProductById(db, id).WithCancellation(ct))
{
    return product;
}

return null;
```

Trước khi áp dụng, benchmark end-to-end và nhìn query duration; nếu SQL mất 80 ms thì tiết kiệm vài microseconds compilation thường không đáng complexity.

## 5. Real production scenario

Một high-throughput authorization service thực hiện query lookup nhỏ, indexed tốt, DB latency dưới 1 ms trong local network. Profiling cho thấy application-side EF query overhead chiếm phần đáng kể ở hàng trăm nghìn calls/second.

Compiled query có thể đáng dùng ở đúng path đó, nhưng không cần áp vào mọi repository method.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries khắp code nhưng p95 gần như không đổi.

**Evidence** → traces cho thấy 95% latency nằm ở database I/O; compilation chỉ fraction rất nhỏ.

**Hypothesis** → optimization target sai layer.

**Diagnosis** → benchmark query pipeline riêng và measure actual DB execution/network latency.

**Fix** → tối ưu index/query shape/database trước; giữ compiled query chỉ ở path profiler chứng minh có lợi.

**Verification** → benchmark trước/sau dưới representative concurrency.

## 7. Common mistakes

- Nghĩ compiled query = compiled SQL stored procedure.
- Dùng nó để che N+1 hoặc missing index.
- Tạo delegate cho mỗi dynamic combination khiến maintainability giảm.
- Benchmark in-memory/local DB rồi suy ra production benefit.
- Micro-optimize EF trước khi xem SQL execution plan.

## 8. Alternatives

- Standard EF query: default tốt vì EF đã cache query shapes.
- Raw SQL/Dapper: phù hợp nếu workload query-centric và cần control thấp hơn abstraction.
- Database-side optimization: index, projection, query rewrite thường tạo lợi ích lớn hơn.

## 9. Trade-offs

### Advantages

- Giảm overhead query pipeline ở hot path.
- Delegate reusable, parameterized.

### Costs / Risks

- Tăng code ceremony.
- Benefit nhỏ trong phần lớn I/O-bound business APIs.
- Dynamic query scenarios khó phù hợp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu EF phải translate LINQ trước khi database chạy SQL.

### Middle

Biết parameterize query, projection và benchmark query performance.

### Senior

Dùng profiler để phân biệt EF pipeline overhead với DB execution cost.

### Technical Lead / Architect

Chỉ cho phép compiled query ở measured hotspots; tránh biến micro-optimization thành repository convention.

## 11. Key takeaway

- Compiled queries tối ưu application-side query compilation, không sửa slow SQL.
- EF đã cache query shape; benefit bổ sung thường nhỏ.
- Chỉ dùng khi profiling chứng minh đây là bottleneck thật.

# 4. SQL Server statistics và cardinality estimation: execution plan sai thường bắt đầu từ việc optimizer ước lượng sai số rows

## 1. What is it?

SQL Server statistics mô tả distribution của values trong columns/index keys. Query optimizer dùng statistics để ước lượng **cardinality** — có bao nhiêu rows sẽ đi qua từng operator.

Mental model:

```text
SQL query
   + statistics
   |
   v
estimated rows
   |
   v
join type / index access / memory grant / parallelism
```

Optimizer không chạy thử mọi plan; nó ra quyết định từ estimates.

## 2. Why does it exist?

Một join có 10 rows phù hợp Nested Loops. Một join có 10 triệu rows có thể phù hợp Hash Join hơn. Nếu optimizer nghĩ có 10 nhưng thực tế là 10 triệu, plan có thể catastrophic dù indexes tồn tại.

Statistics giúp optimizer dự đoán workload mà không scan toàn table trước mỗi query.

## 3. How does it work?

Statistics thường có histogram trên leading column và density information. Khi data thay đổi, auto-update statistics có thể refresh, nhưng threshold/timing không phải lúc nào cũng phù hợp workload skewed hoặc bulk load lớn.

Ví dụ kiểm tra plan:

```sql
SELECT o.Id, o.Total
FROM dbo.Orders AS o
WHERE o.Status = @status
  AND o.CreatedAt >= @from;
```

Trong actual execution plan, so sánh:

```text
Estimated Number of Rows: 1,000
Actual Number of Rows:    450,000
```

Gap lớn là signal để điều tra statistics, parameter distribution, predicate correlation hoặc query shape.

## 4. Practical implementation

Inspect statistics:

```sql
DBCC SHOW_STATISTICS ('dbo.Orders', 'IX_Orders_Status_CreatedAt');
```

Update có chủ đích sau large data load nếu cần:

```sql
UPDATE STATISTICS dbo.Orders IX_Orders_Status_CreatedAt WITH FULLSCAN;
```

Không chạy `FULLSCAN` mọi table theo cron một cách mù quáng; cost có thể lớn và auto stats thường đã đủ.

## 5. Real production scenario

E-commerce import 20 triệu archived orders qua batch. Sau import, `Status='Open'` chỉ chiếm 0.1% nhưng old statistics phản ánh distribution trước load. Query optimizer chọn scan + oversized memory grant cho endpoint open orders.

Actual plan cho thấy estimate lệch hàng trăm lần. Refresh statistics giúp optimizer chọn access path tốt hơn mà không đổi application code.

## 6. Failure scenario & troubleshooting

**Symptom** → query từng nhanh bỗng chậm sau bulk load/release dù SQL text không đổi.

**Evidence** → actual vs estimated rows lệch lớn; plan đổi; stats modification counter cao hoặc histogram không phản ánh dữ liệu mới.

**Hypothesis** → cardinality estimate sai do stale/skewed statistics hoặc parameter sensitivity.

**Diagnosis** → actual execution plan, Query Store, statistics metadata/histogram, compare parameter values.

**Fix** → refresh stats, cải thiện index/statistics strategy, rewrite predicate hoặc xử lý parameter-sensitive workload đúng cách.

**Verification** → estimates gần actual hơn và latency/logical reads ổn định qua representative parameters.

## 7. Common mistakes

- Rebuild mọi index chỉ để “refresh stats” mà không biết root cause.
- Update all statistics FULLSCAN thường xuyên gây maintenance cost lớn.
- Chỉ nhìn estimated plan, không capture actual rows.
- Thấy estimate sai rồi lập tức thêm index.
- Bỏ qua data skew và correlated predicates.

## 8. Alternatives

- Query Store giúp phát hiện plan regression và historical comparison.
- Filtered statistics/index có thể hữu ích cho skewed subset.
- Query rewrite hoặc schema redesign nếu data model tạo estimation problem thường xuyên.

## 9. Trade-offs

### Advantages

- Statistics tốt giúp optimizer chọn plan hợp lý tự động.
- Không cần hard-code execution strategy cho phần lớn queries.

### Costs / Risks

- Refresh statistics có CPU/I/O cost.
- Sampled statistics có thể bỏ lỡ distribution hiếm.
- Data skew khiến một plan không tốt cho mọi parameter.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu optimizer phải ước lượng rows trước khi chọn plan.

### Middle

Biết so estimated vs actual rows và inspect statistics cơ bản.

### Senior

Liên hệ cardinality error với join choice, memory grant, parameter sensitivity và data skew.

### Technical Lead / Architect

Thiết kế database maintenance/Query Store observability dựa workload thay vì blanket scripts.

## 11. Key takeaway

- Plan quality phụ thuộc mạnh vào cardinality estimate.
- Estimated-vs-actual row gap là một diagnostic signal quan trọng.
- Đừng thêm index trước khi hiểu optimizer đang ước lượng sai ở đâu và vì sao.

# 5. MongoDB Change Streams và resume tokens: phản ứng với thay đổi dữ liệu mà không polling liên tục nhưng vẫn phải thiết kế cho reconnect và duplicate processing

## 1. What is it?

Change Streams cho phép application subscribe các changes từ MongoDB collections/database/deployment dựa trên replication oplog.

Mental model:

```text
MongoDB write
   |
   v
replication oplog
   |
   v
Change Stream
   |
   v
consumer reacts
```

Consumer nhận events như insert, update, replace, delete cùng metadata và resume token.

## 2. Why does it exist?

Polling kiểu:

```text
every 5 seconds -> query UpdatedAt > lastSeen
```

waste database reads, tăng latency và dễ có edge cases khi timestamps trùng hoặc clock assumptions sai.

Change Streams cung cấp event-like feed gần database change source, phù hợp search indexing, cache invalidation hoặc sync workflows.

## 3. How does it work?

Consumer mở cursor/watch. Mỗi change event có `_id` dùng làm resume token. Khi connection bị mất, client có thể resume từ token gần nhất.

```text
Event A -> process -> persist token A
Event B -> process -> persist token B
network fails
reconnect with token B
Event C -> ...
```

Resume không đồng nghĩa exactly-once. Failure giữa side effect và persist token có thể khiến event được xử lý lại.

## 4. Practical implementation

```csharp
var pipeline = new EmptyPipelineDefinition<ChangeStreamDocument<Order>>()
    .Match(x => x.OperationType == ChangeStreamOperationType.Insert ||
                x.OperationType == ChangeStreamOperationType.Update ||
                x.OperationType == ChangeStreamOperationType.Replace);

using var cursor = await orders.WatchAsync(pipeline, cancellationToken: ct);

await foreach (var change in cursor.ToAsyncEnumerable(ct))
{
    await indexer.UpsertAsync(change.DocumentKey["_id"].AsObjectId, ct);

    var resumeToken = change.ResumeToken;
    await checkpointStore.SaveAsync(resumeToken, ct);
}
```

Checkpoint store phải durable nếu consumer cần resume qua process restart.

## 5. Real production scenario

Product catalog lưu primary state trong MongoDB và search read model trong Elasticsearch. Change Stream consumer nhận product updates và cập nhật search index.

Nếu Elasticsearch outage 20 phút, consumer phải retry/buffer/checkpoint hợp lý thay vì advance token trước khi indexing thành công rồi mất changes.

## 6. Failure scenario & troubleshooting

**Symptom** → search index thiếu một số products sau consumer restart.

**Evidence** → code persist resume token trước side effect hoặc token chỉ giữ in-memory.

**Hypothesis** → checkpoint boundary không khớp processing guarantee.

**Diagnosis** → correlate MongoDB change event IDs, checkpoint, Elasticsearch document versions và consumer logs.

**Fix** → side effect idempotent, checkpoint sau successful processing, durable checkpoint; có reconciliation job cho drift.

**Verification** → fault-injection kill consumer giữa processing và checkpoint, sau restart data vẫn converge đúng.

## 7. Common mistakes

- Coi Change Stream là exactly-once event bus.
- Không persist resume token.
- Persist token trước side effect.
- Không có strategy khi resume token quá cũ/oplog history không còn.
- Put long synchronous work trực tiếp trong cursor loop mà không quản lý throughput.
- Không có reconciliation cho derived system quan trọng.

## 8. Alternatives

- Polling với durable watermark: đơn giản hơn cho low-frequency sync.
- Application outbox/event broker: tốt khi business event semantics quan trọng hơn raw database change.
- CDC platform/connectors: phù hợp data integration rộng hơn.

## 9. Trade-offs

### Advantages

- Latency thấp hơn polling.
- Giảm repeated read queries.
- Resume support tốt cho transient disconnects.

### Costs / Risks

- Coupling với database change shape.
- Duplicate/replay vẫn phải xử lý.
- Oplog retention và checkpoint lifecycle trở thành operational concern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Change Stream là feed của database changes, không phải business event tự động.

### Middle

Biết watch, filter, checkpoint và reconnect.

### Senior

Thiết kế idempotency, resume semantics, reconciliation và downstream outage handling.

### Technical Lead / Architect

Quyết định dùng Change Stream hay explicit domain/integration events tùy coupling và audit semantics mong muốn.

## 11. Key takeaway

- Resume token giúp reconnect, không tạo exactly-once processing.
- Checkpoint phải gắn với side-effect completion.
- Derived stores quan trọng cần reconciliation ngoài streaming path.

# 6. Redis cache stampede và request coalescing: cache hết hạn đồng loạt có thể làm database sập dù cache hit rate trước đó rất đẹp

## 1. What is it?

Cache stampede xảy ra khi nhiều requests cùng miss một hot key và đồng thời gọi origin/database để rebuild cùng dữ liệu.

Mental model:

```text
Before TTL expiry:
10,000 requests -> Redis hit

After expiry:
10,000 requests -> miss -> 10,000 DB queries
```

Cache giảm load bình thường nhưng expiry boundary có thể tạo load spike lớn hơn hệ thống chưa từng chịu.

## 2. Why does it exist?

TTL-based cache thường coi từng request độc lập. Khi key biến mất, mọi request đều thấy “tôi phải load data”. Với hot keys, chỉ vài milliseconds race cũng đủ tạo hàng trăm concurrent origin calls.

Request coalescing/single-flight đảm bảo một actor rebuild, các request khác chờ hoặc dùng stale value tùy policy.

## 3. How does it work?

Một strategy:

```text
cache hit -> return
cache miss
  -> acquire per-key rebuild lease
       -> winner loads DB + sets cache
       -> others wait/retry/read stale
```

Thêm TTL jitter để nhiều keys không expire cùng giây:

```text
base TTL = 5 min
actual TTL = 5 min + random(0..60 sec)
```

Stale-while-revalidate có thể trả stale data trong short window trong khi background refresh.

## 4. Practical implementation

Một single-instance coalescing pattern đơn giản:

```csharp
private readonly ConcurrentDictionary<string, SemaphoreSlim> _locks = new();

public async Task<ProductDto?> GetProductAsync(Guid id, CancellationToken ct)
{
    var key = $"product:{id}";
    var cached = await cache.GetStringAsync(key, ct);
    if (cached is not null)
        return JsonSerializer.Deserialize<ProductDto>(cached);

    var gate = _locks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
    await gate.WaitAsync(ct);
    try
    {
        cached = await cache.GetStringAsync(key, ct);
        if (cached is not null)
            return JsonSerializer.Deserialize<ProductDto>(cached);

        var product = await LoadProductFromDbAsync(id, ct);
        if (product is null) return null;

        await cache.SetStringAsync(
            key,
            JsonSerializer.Serialize(product),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
            },
            ct);

        return product;
    }
    finally
    {
        gate.Release();
    }
}
```

Đây chỉ coalesce trong một process. Multi-instance cần distributed coordination hoặc cache library/pattern phù hợp; không nên tự viết distributed locking tùy tiện.

## 5. Real production scenario

Homepage có “top 100 products” cache 10 phút. 20 application instances cùng cache miss khi TTL hết. Mỗi instance nhận hàng trăm requests và cùng query expensive aggregation. SQL CPU từ 25% lên 100%, p99 vượt timeout.

TTL jitter + single-flight + stale fallback làm refresh load bounded hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → cứ đúng chu kỳ 10 phút DB CPU spike và API latency tăng.

**Evidence** → Redis hit rate tụt ngắn hạn đúng TTL boundary; DB query count tăng hàng trăm lần; cùng cache key miss đồng thời.

**Hypothesis** → synchronized expiration/stampede.

**Diagnosis** → correlate cache misses, key TTL, DB QPS và instance count.

**Fix** → coalescing, jitter, stale-while-revalidate, prewarm nếu cần; tối ưu origin query vẫn quan trọng.

**Verification** → qua nhiều expiration cycles, origin QPS giữ bounded và p99 không spike lớn.

## 7. Common mistakes

- Chỉ tăng TTL để che stampede.
- Dùng one global lock khiến unrelated keys block nhau.
- Không double-check cache sau khi acquire gate.
- Redis down thì mọi request thẳng DB không có load shedding.
- Cache null/error responses vô thời hạn.
- Không đo hot-key distribution.

## 8. Alternatives

- Proactive refresh trước TTL.
- CDN/output cache nếu data public HTTP-level.
- Materialized read model nếu origin computation vốn quá đắt.
- Không cache nếu workload nhỏ và DB đủ capacity.

## 9. Trade-offs

### Advantages

- Giảm origin spikes.
- Ổn định tail latency quanh expiry.
- Bảo vệ database tốt hơn simple cache-aside.

### Costs / Risks

- Thêm coordination logic.
- Stale fallback đánh đổi freshness.
- Distributed coalescing phức tạp hơn single process.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache miss trên hot key có thể nhân load lên rất lớn.

### Middle

Biết double-check locking/coalescing, TTL jitter và cache metrics.

### Senior

Thiết kế failure behavior khi Redis/origin chậm, freshness budget và multi-instance coordination.

### Technical Lead / Architect

Quyết định layer nào cache, stale policy nào business chấp nhận và liệu cache có đang che một read model cần redesign hay không.

## 11. Key takeaway

- Cache hit rate đẹp không đảm bảo expiry behavior an toàn.
- Hot-key refresh cần bounded concurrency.
- Jitter, coalescing và stale policy phải được thiết kế cùng origin capacity.

# 7. Elasticsearch near-real-time refresh và optimistic concurrency: document đã index không có nghĩa search sẽ thấy ngay, và concurrent writes vẫn cần version semantics

## 1. What is it?

Elasticsearch search là **near real-time (NRT)**. Index/write operation có thể acknowledged trước khi document trở nên visible với search. Visibility thường xảy ra sau refresh tạo search segments mới.

Ngoài ra, Elasticsearch dùng sequence number (`_seq_no`) và primary term (`_primary_term`) để hỗ trợ optimistic concurrency control.

## 2. Why does it exist?

Nếu mỗi write buộc Lucene refresh/segment publication ngay lập tức, indexing throughput sẽ giảm mạnh. Elasticsearch batch refresh để cân bằng write throughput và search freshness.

Concurrent writes cũng cần protection: service A đọc document version cũ rồi update sau service B có thể overwrite state nếu không có concurrency condition.

## 3. How does it work?

Write path đơn giản hóa:

```text
index request
  -> primary shard accepts write
  -> replicas
  -> acknowledged
  -> later refresh
  -> searchable
```

Vì vậy:

```text
POST index document
immediately SEARCH
```

có thể chưa thấy document.

Optimistic write có thể truyền `if_seq_no` và `if_primary_term`; nếu document đã thay đổi, Elasticsearch trả conflict thay vì silent overwrite.

## 4. Practical implementation

Index rồi yêu cầu wait-for refresh khi use case thật sự cần read-after-write qua search:

```http
PUT /products/_doc/123?refresh=wait_for
{
  "name": "Keyboard",
  "price": 120
}
```

Nhưng không nên dùng `refresh=true` cho mọi write vì nó gây refresh pressure.

Concurrency-safe update:

```http
PUT /products/_doc/123?if_seq_no=17&if_primary_term=3
{
  "name": "Keyboard",
  "price": 125
}
```

Conflict cần được application xử lý theo business semantics, không blindly retry overwrite.

## 5. Real production scenario

CMS editor publish article rồi redirect ngay tới search page. Editor không thấy article trong vài trăm milliseconds và báo “publish bị mất”. Primary database đã đúng; search chỉ chưa refresh.

Solution có thể là UI đọc trực tiếp authoritative content sau publish, hoặc `refresh=wait_for` cho low-frequency publishing path — không cần làm toàn cluster refresh mỗi write.

## 6. Failure scenario & troubleshooting

**Symptom** → index API 200 nhưng immediate search không thấy document; hoặc concurrent editors overwrite nhau.

**Evidence** → GET by ID có state mới nhưng search chưa visible; hoặc sequence numbers cho thấy document đổi sau lần đọc.

**Hypothesis** → NRT refresh semantics hoặc lost-update race.

**Diagnosis** → inspect refresh interval, shard/index metrics, seq_no/primary_term và request timeline.

**Fix** → chọn read path đúng, `refresh=wait_for` chỉ nơi cần, optimistic concurrency cho updates.

**Verification** → integration tests mô phỏng immediate search + concurrent writers và assert expected conflict/freshness behavior.

## 7. Common mistakes

- Gọi manual refresh sau mỗi document.
- Coi Elasticsearch là authoritative transactional database chỉ vì GET nhanh.
- Blind retry 409 rồi overwrite latest document.
- Không định nghĩa freshness SLA cho search.
- Tăng refresh frequency mà không đo indexing/search resource cost.

## 8. Alternatives

- Read authoritative database cho read-after-write critical flow.
- Eventual search visibility cho user-facing search bình thường.
- Database full-text search nếu scale/features chưa cần Elasticsearch operational complexity.

## 9. Trade-offs

### Advantages

- NRT architecture cho indexing/search throughput tốt.
- Optimistic concurrency tránh coarse lock.

### Costs / Risks

- Freshness không instantaneous.
- Conflict resolution thuộc application/business semantics.
- Tuning refresh ảnh hưởng indexing CPU/I/O và segment churn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu indexed/acknowledged không đồng nghĩa searchable ngay lập tức.

### Middle

Biết `refresh=wait_for`, seq_no/primary_term và 409 handling.

### Senior

Thiết kế freshness SLA, authoritative source và concurrency behavior dựa workload.

### Technical Lead / Architect

Quyết định use case nào thực sự cần Elasticsearch và operational cost của freshness/consistency có đáng hay không.

## 11. Key takeaway

- Elasticsearch là near real-time search system.
- Đừng force refresh toàn bộ workload chỉ để giải quyết một read-after-write UX path.
- Concurrent writes cần explicit version semantics, không blind retry.

# 8. Expand–Contract database migration trong CI/CD: thay đổi schema mà old code và new code có thể cùng chạy trong zero-downtime deployment

## 1. What is it?

Expand–Contract là migration strategy chia breaking schema change thành nhiều compatible phases.

Ví dụ đổi `FullName` thành `FirstName` + `LastName` không làm trong một deployment duy nhất:

```text
Expand  -> add new schema, old code still works
Migrate -> backfill / dual-read-write as needed
Switch  -> new code uses new schema
Contract-> remove old schema later
```

## 2. Why does it exist?

Trong rolling/blue-green deployment, old và new application versions có thể cùng chạy vài phút hoặc lâu hơn.

Nếu migration xóa/rename column trước khi old pods dừng:

```text
old app -> SELECT FullName -> column missing -> production errors
```

Zero-downtime deployment yêu cầu compatibility giữa versions chồng lấn.

## 3. How does it work?

Phase 1 — Expand:

```sql
ALTER TABLE Users ADD FirstName nvarchar(100) NULL;
ALTER TABLE Users ADD LastName  nvarchar(100) NULL;
```

Phase 2 — deploy code hiểu cả old/new shape, backfill data theo batches.

Phase 3 — switch reads/writes hoàn toàn sang new columns sau khi telemetry xác nhận.

Phase 4 — Contract trong release sau:

```sql
ALTER TABLE Users DROP COLUMN FullName;
```

Contract chỉ xảy ra khi chắc chắn không còn binary/job/report nào phụ thuộc old schema.

## 4. Practical implementation

Một application transition có thể tạm dual-write:

```csharp
user.FullName = request.FullName; // compatibility path
(user.FirstName, user.LastName) = NameParser.Parse(request.FullName);
```

Sau backfill và version cutover, remove old write. Dual-write phải có thời hạn; nếu để lâu, nó trở thành permanent inconsistency risk.

CI/CD pipeline nên tách migration artifact/step và health validation:

```text
commit
 -> build
 -> test
 -> artifact
 -> expand migration
 -> deploy application
 -> health validation
 -> monitor
 -> later contract migration
```

## 5. Real production scenario

Một API chạy 20 Kubernetes pods. Deployment rolling thay 2 pods mỗi lần. Team rename column trực tiếp trong migration startup của new pod. Migration hoàn tất ngay, 18 old pods bắt đầu throw SQL errors.

Expand–Contract cho phép cả hai versions chạy trên cùng schema trong transition.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment mới healthy nhưng old instances bắt đầu 500 ngay sau DB migration.

**Evidence** → SQL invalid-column errors chỉ trên old build version; migration vừa drop/rename field.

**Hypothesis** → schema migration không backward compatible với overlapping deployment versions.

**Diagnosis** → map deployment timeline, app versions, migration version và query errors.

**Fix** → restore compatible schema/hotfix, sau đó chia migration thành expand/backfill/switch/contract.

**Verification** → pre-production test chạy old+new binaries đồng thời trên expanded schema.

## 7. Common mistakes

- Rename/drop column trong cùng release với code switch.
- Add `NOT NULL` column không default/backfill strategy trên table lớn.
- Chạy huge backfill trong one transaction.
- Assume chỉ web app dùng schema; quên jobs/reports/integrations.
- Giữ dual-write vĩnh viễn.
- Auto-run destructive migration khi mỗi pod startup.

## 8. Alternatives

- Maintenance window: đơn giản nếu downtime được chấp nhận.
- Feature flag staged rollout kết hợp compatible schema.
- New table/versioned schema khi migration quá lớn/phức tạp để alter in place.

## 9. Trade-offs

### Advantages

- Hỗ trợ rolling/blue-green deployment an toàn hơn.
- Rollback application dễ hơn vì schema cũ vẫn còn trong transition.

### Costs / Risks

- Cần nhiều releases/phases.
- Temporary duplicate fields/logic tăng complexity.
- Backfill và cleanup cần ownership rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DB schema là shared contract giữa nhiều application versions.

### Middle

Biết viết additive migrations và backfill có kiểm soát.

### Senior

Thiết kế compatibility window, batch backfill, rollback và telemetry.

### Technical Lead / Architect

Đặt migration policy cho CI/CD: ai chạy migration, destructive change gate nào tồn tại, khi nào contract phase được phép chạy.

## 11. Key takeaway

- Zero downtime yêu cầu schema tương thích với old + new code trong overlap window.
- Breaking migration nên tách expand và contract qua nhiều releases.
- Database migration là deployment architecture, không chỉ một file SQL.

# 9. OpenID Connect Authorization Code + PKCE: bảo vệ browser/mobile login flow mà không biến access token thành session state tùy tiện

## 1. What is it?

OpenID Connect (OIDC) xây trên OAuth 2.0 để thêm identity/authentication. Authorization Code flow trả một short-lived authorization code cho client, rồi code được đổi lấy tokens qua token endpoint.

PKCE thêm `code_verifier`/`code_challenge` để kẻ đánh cắp authorization code không thể đổi code thành token nếu không có verifier gốc.

## 2. Why does it exist?

Browser/mobile clients không thể giữ client secret đáng tin cậy như backend server. Redirect URL cũng đi qua user agent và có risk code interception.

PKCE làm authorization code bị bind với client instance đã khởi tạo login flow.

OIDC còn phân biệt:

- **ID token**: thông tin authentication về user/client session.
- **Access token**: credential để gọi protected resource/API.

Không nên dùng ID token như API access token.

## 3. How does it work?

```text
Client generates verifier
  -> hash/verifier => code_challenge

Client -> Authorization Server
         /authorize + challenge

Authorization Server -> Client
         redirect + authorization code

Client -> Token Endpoint
         code + verifier

Server validates verifier matches challenge
  -> tokens
```

`state` chống request correlation/CSRF style attacks; `nonce` liên quan OIDC ID token replay/correlation. PKCE không thay thế hai khái niệm đó.

## 4. Practical implementation

Trong ASP.NET Core server-side web app, OIDC handler quản lý flow:

```csharp
builder.Services
    .AddAuthentication(options =>
    {
        options.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;
        options.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;
    })
    .AddCookie()
    .AddOpenIdConnect(options =>
    {
        options.Authority = configuration["Auth:Authority"];
        options.ClientId = configuration["Auth:ClientId"];
        options.ResponseType = "code";
        options.UsePkce = true;
        options.SaveTokens = false;
    });
```

Đối với SPA, architecture BFF có thể giữ tokens server-side và chỉ đưa secure session cookie tới browser, giảm exposure của bearer token trong JavaScript. Nhưng BFF thêm backend state/operational complexity; không phải mọi SPA đều bắt buộc dùng.

## 5. Real production scenario

Một mobile app dùng custom URI redirect. Attacker app cố claim cùng URI scheme và intercept authorization code. PKCE khiến intercepted code vô dụng nếu attacker không có `code_verifier` của legitimate app.

Một web SPA khác lưu long-lived access token trong `localStorage`; XSS lấy token và gọi API từ máy attacker. PKCE bảo vệ code exchange nhưng **không bảo vệ token sau khi browser đã lưu nó** — token storage là threat khác.

## 6. Failure scenario & troubleshooting

**Symptom** → login thành công ở local nhưng production callback lỗi `invalid_grant`, state mismatch hoặc redirect URI mismatch.

**Evidence** → IdP logs, callback URL, proxy scheme/host, correlation cookie, PKCE/token exchange response.

**Hypothesis** → reverse proxy làm application suy ra callback scheme sai; cookie SameSite/Secure hoặc registered redirect URI không khớp.

**Diagnosis** → trace authorize request → redirect → callback → token exchange; kiểm tra forwarded headers và exact redirect URI.

**Fix** → cấu hình trusted forwarded headers, HTTPS/cookie settings và IdP redirect URI chính xác; không disable validation để “cho chạy”.

**Verification** → end-to-end login test trên production-like proxy/domain và multiple browser scenarios.

## 7. Common mistakes

- Dùng ID token để authorize API.
- Lưu long-lived bearer token tùy tiện trong browser storage.
- Nghĩ PKCE thay `state`/`nonce`.
- Disable issuer/audience/signature validation để sửa 401.
- Hard-code client secret vào public SPA/mobile app.
- Dùng access token claims như permanent user profile database.

## 8. Alternatives

- BFF + secure cookie session: giảm browser token exposure nhưng thêm backend component.
- Client credentials: machine-to-machine, không đại diện end-user login.
- Device Authorization Grant: phù hợp device input hạn chế, không thay login web chuẩn.

## 9. Trade-offs

### Advantages

- Authorization Code + PKCE phù hợp public clients.
- Tách authentication identity khỏi API authorization token.
- Standard protocol, interoperable IdPs.

### Costs / Risks

- Redirect/cookie/proxy configuration phức tạp.
- Token lifecycle, logout và refresh vẫn cần thiết kế.
- Protocol đúng không cứu được XSS hoặc authorization logic sai trong API.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ID token và access token có mục đích khác nhau.

### Middle

Biết flow code + PKCE, state/nonce và cấu hình OIDC middleware.

### Senior

Threat-model redirect, token storage, reverse proxy, refresh/logout và API authorization.

### Technical Lead / Architect

Chọn SPA token model vs BFF, IdP boundaries và browser security posture dựa risk/operational cost.

## 11. Key takeaway

- PKCE bind authorization code với client instance tạo login flow.
- PKCE không giải quyết XSS/token theft sau login.
- Identity flow chuẩn vẫn cần đúng token storage, validation và authorization boundaries.

# 10. RAG retrieval evaluation và embedding/index versioning: model tốt không cứu được retrieval kém, và thay embedding model là một data migration thực sự

## 1. What is it?

Retrieval-Augmented Generation (RAG) lấy relevant documents/chunks từ knowledge store rồi đưa chúng vào model context để trả lời dựa trên external data.

Mental model:

```text
User query
   -> query transform/embedding
   -> retrieve candidates
   -> rank/filter
   -> context assembly
   -> LLM generation
```

Một RAG system có ít nhất hai correctness boundaries: **retrieval quality** và **generation behavior**.

## 2. Why does it exist?

LLM không tự biết private/current enterprise data. Nhét toàn bộ corpus vào prompt vừa quá token budget vừa đắt và nhiễu.

Retrieval chọn subset relevant. Nhưng nếu retriever không lấy đúng evidence, model phía sau không thể “suy luận ra” tài liệu đã không được đưa vào context.

Vì vậy evaluation phải đo retrieval riêng, không chỉ hỏi “answer nghe có hay không?”.

## 3. How does it work?

Một evaluation set nên chứa:

```text
question
expected relevant document/chunk IDs
expected answer facts
```

Retrieval metrics có thể gồm:

- Recall@K: relevant evidence có xuất hiện trong top K không?
- Precision@K: top K chứa bao nhiêu evidence thực sự relevant?
- MRR/NDCG khi ranking order quan trọng.

Sau retrieval mới đo answer groundedness/correctness.

Embedding/index version cần được explicit:

```text
chunk_schema_version = 3
embedding_model = model-X
embedding_dimension = 1536
index_version = products-v7
```

Không trộn vectors từ incompatible embedding spaces trong cùng similarity semantics.

## 4. Practical implementation

Metadata example:

```json
{
  "documentId": "policy-42",
  "chunkId": "policy-42#7",
  "contentHash": "sha256:...",
  "chunkSchemaVersion": 3,
  "embeddingModel": "embedding-model-v2",
  "embeddingVersion": "2026-09",
  "indexedAtUtc": "2026-09-13T12:00:00Z"
}
```

Deployment flow khi đổi embedding model:

```text
existing index v1 serves traffic
  |
  +-> build index v2 offline
      -> embed corpus
      -> run retrieval eval
      -> shadow/canary queries
      -> switch alias/routing
      -> monitor
      -> retire v1 later
```

Đừng overwrite vectors in-place từng phần nếu query embeddings đã chuyển model nhưng corpus vectors chưa đồng bộ.

## 5. Real production scenario

Internal HR assistant trước đây đạt answer accuracy tốt. Team đổi embedding model “mới hơn” rồi re-embed chỉ documents được cập nhật gần đây. Query vectors dùng model mới nhưng phần lớn corpus vẫn vector cũ.

Search không crash; nó chỉ âm thầm retrieve kém. LLM bắt đầu hallucinate vì evidence relevant biến mất khỏi top K.

Versioned index + offline eval sẽ phát hiện regression trước traffic cutover.

## 6. Failure scenario & troubleshooting

**Symptom** → model response quality giảm sau index/model update dù LLM version không đổi.

**Evidence** → expected evidence không còn trong top K; retrieval Recall@K giảm; latency/token usage có thể vẫn bình thường.

**Hypothesis** → embedding/index/chunking regression, không phải generation model.

**Diagnosis** → replay fixed evaluation corpus, compare top-K IDs/scores giữa old/new index, inspect metadata versions và chunk boundaries.

**Fix** → rebuild consistent index, rollback alias, tune chunking/reranking; chỉ sau đó xem prompt/model nếu retrieval đã đúng.

**Verification** → retrieval metrics phục hồi và answer groundedness pass trên held-out eval set.

## 7. Common mistakes

- Chỉ đánh giá final answer bằng subjective spot checks.
- Đổi embedding model mà không version/rebuild index.
- Không lưu source/chunk IDs nên không trace evidence.
- Chunk theo arbitrary character count mà bỏ document semantics.
- Increase top K vô hạn rồi làm context nhiễu/tốn token.
- Cho model tự quyết side effect dựa trên untrusted retrieved text.
- Đưa secrets/PII vào vector store mà không có access-control filtering.

## 8. Alternatives

- Keyword/BM25 search: rất mạnh với identifiers, exact terms và có thể kết hợp vector thành hybrid retrieval.
- Database lookup/tool calling: tốt hơn RAG khi answer cần deterministic structured facts.
- Fine-tuning: thay đổi model behavior/style, không phải giải pháp tốt để cập nhật frequently changing factual corpus.

## 9. Trade-offs

### Advantages

- Dùng current/private knowledge mà không retrain model.
- Có thể trace evidence nếu metadata tốt.
- Hybrid retrieval/reranking linh hoạt.

### Costs / Risks

- Indexing pipeline trở thành data system cần versioning/monitoring.
- Retrieval failure thường silent.
- Token, embedding, reranking và storage đều có cost.
- Retrieved content có thể chứa prompt injection; deterministic authorization/tool execution phải nằm ngoài model.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG gồm retrieval trước generation; LLM chỉ thấy context được đưa vào.

### Middle

Biết chunk/embed/index, giữ source metadata và debug top-K results.

### Senior

Thiết kế retrieval eval, hybrid search, reranking, versioned reindex và prompt-injection/data-access controls.

### Technical Lead / Architect

Quyết định khi nào RAG phù hợp, deterministic lookup/tool nào nên dùng thay thế, và đặt release gate/cost/observability cho knowledge pipeline.

## 11. Key takeaway

- Đánh giá retrieval độc lập với generation.
- Đổi embedding/chunking là data migration cần versioned rollout và rollback.
- Deterministic authorization và side effects không được giao cho retrieved prompt text hay LLM quyết định tự do.
