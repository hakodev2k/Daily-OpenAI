# 1. ASP.NET Core DI lifetimes: captive dependency và request state leak

## 1. What is it?

ASP.NET Core DI có ba lifetime phổ biến: `Transient`, `Scoped` và `Singleton`. Mental model quan trọng không phải “bao lâu tạo object một lần”, mà là **object nào được phép giữ reference tới object nào**. Captive dependency xuất hiện khi component sống lâu, điển hình `Singleton`, giữ một dependency có lifetime ngắn hơn như `Scoped`.

## 2. Why does it exist?

Lifetime cho phép runtime quản lý ownership và disposal. `DbContext` thường scoped theo request vì change tracker và transaction state không nên chia sẻ giữa requests. Singleton phù hợp component stateless/thread-safe dùng toàn process. Nếu lifetime graph sai, state của request có thể sống lâu hơn dự kiến hoặc dependency đã dispose vẫn bị dùng.

## 3. How does it work?

```text
Root container
 ├─ Singleton ─────────────────────── process lifetime
 └─ Request scope
      ├─ Scoped DbContext
      └─ Scoped application service
```

Singleton được resolve từ root. Nếu nó capture scoped service, scoped object về mặt thực tế bị kéo lên lifetime dài hơn hoặc container phát hiện cấu hình sai khi scope validation bật.

## 4. Practical implementation

Sai:

```csharp
builder.Services.AddDbContext<AppDbContext>();
builder.Services.AddSingleton<ReportCache>();

public sealed class ReportCache(AppDbContext db)
{
    public Task<int> CountAsync(CancellationToken ct) =>
        db.Reports.CountAsync(ct);
}
```

Nếu singleton thực sự cần tạo scope cho một operation nền, tạo scope có chủ đích:

```csharp
public sealed class ReportRefreshWorker(
    IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = scopeFactory.CreateAsyncScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            await RefreshAsync(db, stoppingToken);
            await Task.Delay(TimeSpan.FromMinutes(1), stoppingToken);
        }
    }
}
```

## 5. Real production scenario

Một singleton cache service vô tình inject repository chứa `DbContext`. Dưới concurrent traffic, nhiều requests cùng chạm một context. Hệ thống bắt đầu có lỗi concurrent operation, tracking state bất thường hoặc memory tăng vì tracked entities sống quá lâu.

## 6. Failure scenario & troubleshooting

**Symptom** → lỗi `A second operation was started on this context...` chỉ xuất hiện dưới load. **Evidence** → dependency graph cho thấy singleton giữ scoped repository. **Hypothesis** → `DbContext` bị chia sẻ cross-request. **Diagnosis** → kiểm tra registrations và constructor chain; bật scope validation ở môi trường phù hợp. **Fix** → sửa lifetime hoặc tạo scope per unit-of-work. **Verification** → concurrency test và xác nhận mỗi request/job iteration có context riêng.

## 7. Common mistakes

Đổi mọi service thành singleton để “nhanh hơn”; inject `HttpContext` state vào singleton; giữ scoped service trong field của background worker; tạo service locator tùy tiện để né lifetime rules; cho rằng singleton tự động thread-safe.

## 8. Alternatives

Stateless singleton có thể nhận `IDbContextFactory<T>` để tạo context theo operation. Với request service thông thường, scoped lifetime đơn giản hơn và rõ ownership hơn.

## 9. Trade-offs

### Advantages

Lifetime đúng giúp disposal, state isolation và ownership rõ ràng.

### Costs / Risks

Tạo scope/factory thủ công làm lifecycle phức tạp hơn; singleton đòi hỏi thread-safety và tránh request-specific state.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Transient/Scoped/Singleton và `DbContext` không nên chia sẻ giữa requests.

### Middle

Đọc dependency graph, chọn lifetime và xử lý background scope đúng.

### Senior

Nhận diện captive dependency, thread-safety, disposal và hidden state dưới load.

### Technical Lead / Architect

Đặt guideline lifetime theo ownership và concurrency model, không theo micro-optimization.

## 11. Key takeaway

- Lifetime là ownership boundary, không chỉ là tần suất `new` object.
- Dependency sống lâu không nên capture dependency sống ngắn hơn.
- Singleton phải được thiết kế thread-safe và không chứa request state.

# 2. REST idempotency keys: chống duplicate side effect khi client retry

## 1. What is it?

Idempotency key là identifier do client gửi cùng một logical mutation để server nhận biết nhiều HTTP requests thực chất là cùng một operation. Nó đặc biệt quan trọng với `POST` tạo payment, order hoặc booking khi retry có thể xảy ra sau timeout.

## 2. Why does it exist?

Client timeout không cho biết server đã thực hiện operation hay chưa. Nếu client gửi lại `POST /payments`, request thứ hai có thể tạo payment thứ hai. “Không retry” lại làm giảm reliability khi request thực sự chưa tới server.

## 3. How does it work?

```text
Client POST key=abc
   │
   ├─ Server commits order #42
   └─ Response lost

Client retries key=abc
   │
   └─ Server finds completed key=abc → returns prior result
```

Server lưu key, request fingerprint, trạng thái và kết quả đủ lâu cho retry window. Check và business mutation cần transaction boundary phù hợp để tránh hai concurrent requests cùng thắng.

## 4. Practical implementation

Một schema đơn giản:

```sql
CREATE TABLE IdempotencyKeys (
    [Key] nvarchar(100) NOT NULL PRIMARY KEY,
    RequestHash varbinary(32) NOT NULL,
    ResourceId uniqueidentifier NULL,
    Status varchar(20) NOT NULL,
    CreatedAt datetime2 NOT NULL
);
```

ASP.NET Core handler nên reject cùng key nhưng payload khác, và trả lại canonical result nếu key đã completed.

## 5. Real production scenario

Mobile checkout gửi order creation qua mạng yếu. Server commit order nhưng response bị mất. App retry sau 2 giây. Idempotency key giúp retry trả lại cùng `OrderId` thay vì tạo order mới.

## 6. Failure scenario & troubleshooting

**Symptom** → vẫn có duplicate orders dù đã có idempotency key. **Evidence** → hai requests cùng key insert/check gần đồng thời. **Hypothesis** → check-then-insert không atomic. **Diagnosis** → trace transaction và unique constraint. **Fix** → dùng unique constraint + transaction/atomic claim của key. **Verification** → gửi hàng chục concurrent requests cùng key và xác nhận chỉ một side effect.

## 7. Common mistakes

Dùng idempotency key nhưng không có unique constraint; cho phép cùng key với payload khác; giữ key quá ngắn so với retry window; lưu key sau business commit bằng transaction khác; coi `POST` tự nhiên idempotent.

## 8. Alternatives

PUT tới client-generated resource ID có idempotency tự nhiên hơn trong một số API. Message consumer có thể dùng Inbox/deduplication thay vì HTTP idempotency store.

## 9. Trade-offs

### Advantages

Cho phép retry an toàn hơn và giảm duplicate side effects.

### Costs / Risks

Cần storage, expiration, concurrency control và semantics rõ cho in-progress/failed operations.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không đồng nghĩa operation thất bại.

### Middle

Implement key storage, unique constraint và response reuse.

### Senior

Thiết kế atomicity, payload fingerprint, TTL và crash recovery.

### Technical Lead / Architect

Xác định mutation nào bắt buộc idempotent và chuẩn hóa contract xuyên API/gateway/client.

## 11. Key takeaway

- Retry an toàn cần operation identity, không chỉ retry policy.
- Idempotency check phải chống concurrent duplicate.
- Cùng key nhưng payload khác phải được xử lý như contract violation.

# 3. SQL Server deadlock: wait-for graph, victim selection và cách sửa đúng access pattern

## 1. What is it?

Deadlock xảy ra khi các transactions giữ resources mà transaction khác cần và tạo vòng chờ không thể tự giải phóng. SQL Server phát hiện cycle và chọn một victim để rollback, cho phép phần còn lại tiếp tục.

## 2. Why does it exist?

Locking bảo vệ isolation và consistency. Khi nhiều transaction truy cập resources theo thứ tự khác nhau, việc chờ là hợp lệ cho đến khi wait graph tạo cycle. Database phải phá cycle; nếu không, tất cả participants có thể chờ vô hạn.

## 3. How does it work?

```text
Tx A: holds Order 1 → waits Order 2
                       ▲           │
                       │           ▼
Tx B: waits Order 1 ← holds Order 2
```

Deadlock khác blocking: blocking có thể tự kết thúc khi holder commit; deadlock có cycle.

## 4. Practical implementation

Hai code paths nên cập nhật cùng resource order:

```sql
BEGIN TRAN;
UPDATE Orders SET Status = @status WHERE Id = @orderId;
UPDATE Inventory SET Reserved = Reserved + 1 WHERE ProductId = @productId;
COMMIT;
```

Nếu path khác làm Inventory trước rồi Orders sau, hãy chuẩn hóa thứ tự nếu business transaction cho phép. Thu thập deadlock graph qua Extended Events để biết objects, indexes và statements thật sự tham gia.

## 5. Real production scenario

Checkout cập nhật `Orders` rồi `Inventory`; stock reconciliation cập nhật `Inventory` rồi `Orders`. Traffic bình thường không thấy lỗi, nhưng flash sale tăng concurrency làm deadlock rate tăng mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL error 1205 tăng theo load. **Evidence** → deadlock graph cho thấy hai statements và lock resources tạo cycle. **Hypothesis** → inconsistent access order hoặc transaction giữ lock quá lâu. **Diagnosis** → đọc graph thay vì chỉ nhìn query chậm. **Fix** → thống nhất access order, rút ngắn transaction, cải thiện access path/index nếu scan khóa quá nhiều rows. **Verification** → replay concurrent workload và theo dõi deadlock count.

## 7. Common mistakes

Retry vô hạn; thêm `NOLOCK` để “fix”; tăng timeout; xóa transaction; thêm index không đọc execution plan; nhầm mọi lock wait với deadlock.

## 8. Alternatives

Optimistic concurrency giảm một số lock contention nhưng không thay transaction isolation. Snapshot-based isolation có thể giảm reader/writer blocking nhưng vẫn cần hiểu write conflicts và tempdb/version store cost.

## 9. Trade-offs

### Advantages

Locking giữ consistency mạnh và deadlock detector cho phép recovery.

### Costs / Risks

High contention làm latency/retry tăng; mitigation sai có thể hy sinh correctness.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt blocking và deadlock.

### Middle

Đọc transaction scope và retry transient victim có giới hạn.

### Senior

Đọc deadlock graph, execution plan, lock footprint và access order.

### Technical Lead / Architect

Thiết kế transaction boundaries và contention model cho hot workflows.

## 11. Key takeaway

- Deadlock là cycle, không phải đơn thuần query chậm.
- Deadlock graph là bằng chứng chính.
- Sửa access order/transaction scope trước khi dùng workaround làm yếu consistency.

# 4. Cosmos DB RU throttling: partition-aware capacity và xử lý 429 đúng cách

## 1. What is it?

Request Unit (RU) là abstraction chi phí cho CPU, I/O và memory mà Cosmos DB dùng để thực hiện operation. HTTP 429 không nhất thiết nghĩa database “hỏng”; nó thường nghĩa workload đã vượt provisioned capacity tại thời điểm/partition liên quan.

## 2. Why does it exist?

Distributed database cần cơ chế chia sẻ và kiểm soát capacity. RU tạo budget đo được để provision/autoscale. Nhưng tổng RU cao không cứu được một logical partition nóng nếu traffic tập trung bất cân đối.

## 3. How does it work?

Request được route theo partition key. Query point-read theo `id + partitionKey` rẻ và định tuyến chính xác hơn cross-partition query. Khi capacity tạm thời không đủ, SDK nhận 429 cùng retry-after và thường retry theo policy.

## 4. Practical implementation

Với .NET SDK, luôn truyền partition key khi biết:

```csharp
var response = await container.ReadItemAsync<Order>(
    id,
    new PartitionKey(tenantId),
    cancellationToken: ct);

logger.LogInformation(
    "Order read consumed {Ru} RU",
    response.RequestCharge);
```

Theo dõi RU charge, throttled requests và distribution theo partition/access pattern.

## 5. Real production scenario

SaaS partition theo `TenantId`. Một enterprise tenant tạo 70% traffic, trở thành hot partition. Tổng account RU nhìn vẫn hợp lý nhưng tenant đó nhận 429 và p99 tăng.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng kèm 429. **Evidence** → metrics cho thấy throttling tập trung một partition key; SDK retries làm request cuối cùng vẫn 200 nhưng duration tăng. **Hypothesis** → hot partition. **Diagnosis** → kiểm tra key distribution và RU/request. **Fix** → tối ưu query/data model, tăng capacity hoặc redesign partition key nếu scale model sai. **Verification** → load test representative key skew và theo dõi 429/p99.

## 7. Common mistakes

Chỉ nhìn average RU; cross-partition query không cần thiết; retry 429 bằng custom tight loop; chọn partition key cardinality thấp; đổi partition design quá muộn sau khi data volume lớn.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp hơn nếu relational transactions/query flexibility là trung tâm. MongoDB có distribution model khác nhưng vẫn cần shard-key reasoning.

## 9. Trade-offs

### Advantages

RU làm capacity/cost tương đối observable; partitioning hỗ trợ horizontal scale.

### Costs / Risks

Data model bị ảnh hưởng mạnh bởi access pattern; hot partition và cross-partition query có thể phá latency/cost assumptions.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định data placement và request routing.

### Middle

Đo RequestCharge, xử lý 429 và dùng point read.

### Senior

Phân tích skew, retry amplification và query cost.

### Technical Lead / Architect

Chọn partition strategy dựa growth/access pattern, không dựa field “trông có vẻ unique”.

## 11. Key takeaway

- RU là capacity budget, không phải chỉ billing unit.
- Partition distribution quan trọng hơn tổng capacity khi traffic skewed.
- 429 cần được đo cả khi SDK retry thành công.

# 5. Modular Monolith: boundary thật sự nằm ở ownership và dependency, không phải folder

## 1. What is it?

Modular Monolith là một deployable application nhưng chia thành modules có business boundary, ownership và dependency rules rõ. Nó không phải monolith với nhiều folders; module phải hạn chế cách code/data bên ngoài truy cập internals.

## 2. Why does it exist?

Một codebase lớn có thể cần isolation để nhiều team phát triển mà chưa cần operational cost của microservices. Nếu mọi module gọi trực tiếp table/service nội bộ của nhau, hệ thống vẫn là tightly coupled monolith dù folder đẹp.

## 3. How does it work?

```text
[Orders Module] ── public contract ──> [Payments Module]
      │                                  │
   Orders DB objects                  Payments DB objects
      │                                  │
      └──── no direct table mutation ────┘
```

Modules có thể cùng database server nhưng ownership schema/table rõ. Communication có thể là in-process contract hoặc domain/integration event tùy consistency need.

## 4. Practical implementation

Trong .NET solution, expose interface nhỏ:

```csharp
public interface IInventoryAvailability
{
    Task<Availability> CheckAsync(
        ProductId productId,
        Quantity quantity,
        CancellationToken ct);
}
```

Orders tham chiếu contract, không tham chiếu EF entity/repository nội bộ của Inventory. Architecture tests có thể enforce forbidden project references.

## 5. Real production scenario

E-commerce có Catalog, Orders, Inventory, Payments. Team muốn tách microservices vì solution khó thay đổi. Phân tích cho thấy vấn đề chính là cross-module database access. Modularization trước có thể giảm coupling mà chưa thêm network, distributed tracing và message operations.

## 6. Failure scenario & troubleshooting

**Symptom** → thay schema Inventory làm build hoặc runtime Orders hỏng. **Evidence** → Orders query trực tiếp Inventory tables. **Hypothesis** → data ownership boundary không tồn tại. **Diagnosis** → dependency map và SQL access review. **Fix** → tạo module contract/read model, migrate call sites dần. **Verification** → architecture tests và module-level integration tests.

## 7. Common mistakes

Mỗi folder gọi là module; shared project chứa toàn bộ domain models; generic repository xuyên modules; event hóa mọi call; tách database ngay cả khi transaction consistency cần mạnh; coi Modular Monolith là bước bắt buộc tới microservices.

## 8. Alternatives

Layered monolith đơn giản hơn cho domain nhỏ/team nhỏ. Microservices hợp khi cần independent deployment/scaling/ownership và tổ chức chịu được distributed-systems cost.

## 9. Trade-offs

### Advantages

Boundary tốt với deployment đơn giản; refactor/transaction thường dễ hơn microservices.

### Costs / Risks

Boundary cần discipline và enforcement; cùng process/database khiến developer dễ “đi đường tắt”.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business capability, không chỉ namespace.

### Middle

Giữ dependencies qua public contract và test module behavior.

### Senior

Thiết kế data ownership, transaction boundary và migration path.

### Technical Lead / Architect

Quyết định liệu operational independence có thật sự đáng giá hơn modular monolith hay không.

## 11. Key takeaway

- Module boundary phải kiểm soát dependency và data ownership.
- Một deployment không đồng nghĩa kiến trúc phải tightly coupled.
- Đừng dùng microservices để sửa coupling mà bạn chưa sửa trong codebase.

# 6. Azure Key Vault + Managed Identity: secret retrieval, rotation và failure boundary

## 1. What is it?

Azure Key Vault lưu secrets/keys/certificates; Managed Identity cho Azure workload một identity trong Microsoft Entra ID mà không cần nhúng client secret vào application. Mental model: Managed Identity giải quyết **application authenticates to Azure**, còn Key Vault giải quyết **controlled storage/access của secret material**.

## 2. Why does it exist?

Connection string/API key trong source hoặc environment được copy rộng, khó rotate và dễ leak. Central secret store + workload identity giảm static credentials và cho phép audit/least privilege.

## 3. How does it work?

```text
App Service
   │ Managed Identity token
   ▼
Microsoft Entra ID
   │ access token
   ▼
Key Vault ── authorization ──> secret
```

App vẫn cần network path và permission phù hợp. Private Endpoint có thể làm DNS/network trở thành một phần failure boundary.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(vaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync(
    "PartnerApiKey",
    cancellationToken: ct);
```

Production nên cân nhắc caching secret hợp lý thay vì gọi Key Vault mỗi request; rotation semantics phải xác định app refresh secret khi nào.

## 5. Real production scenario

App Service gọi legacy partner bắt buộc API key. Managed Identity truy cập Key Vault, app lấy partner key. Partner rotate key hàng quý; deployment không cần chứa key mới trong artifact.

## 6. Failure scenario & troubleshooting

**Symptom** → deploy production xong app startup fail nhưng local chạy tốt. **Evidence** → `403` từ Key Vault hoặc DNS timeout tới private endpoint. **Hypothesis** → identity permission hoặc network path khác local. **Diagnosis** → kiểm tra identity đang dùng, RBAC/access policy, DNS và private connectivity. **Fix** → cấp least privilege đúng identity hoặc sửa networking. **Verification** → health/startup test bằng production identity, không dùng developer credential.

## 7. Common mistakes

Dùng `DefaultAzureCredential` nhưng không biết credential nào thắng; cấp quyền quá rộng; fetch secret mỗi request; log secret; assume rotation tự động refresh mọi client; dùng Key Vault nhưng vẫn giữ bootstrap client secret trong config dù Managed Identity khả dụng.

## 8. Alternatives

App configuration/environment secret có thể đủ cho hệ thống nhỏ nhưng rotation/audit yếu hơn. Workload identity/federation phù hợp CI/CD và Kubernetes scenarios.

## 9. Trade-offs

### Advantages

Giảm static credential, centralize access control/audit và hỗ trợ rotation tốt hơn.

### Costs / Risks

Thêm runtime dependency, IAM/network complexity và startup/fetch failure mode.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt identity với secret.

### Middle

Cấu hình Managed Identity, Key Vault access và client code.

### Senior

Thiết kế caching, rotation, private networking và incident diagnostics.

### Technical Lead / Architect

Xác định secret ownership, rotation SLA, break-glass và dependency strategy.

## 11. Key takeaway

- Managed Identity loại bỏ nhiều static Azure credentials, không loại bỏ mọi secret.
- Key Vault access phụ thuộc cả identity lẫn network.
- Rotation chỉ hoàn chỉnh khi consumer refresh credential đúng cách.

# 7. OpenTelemetry trace sampling: giữ signal mà không trả giá cho 100% telemetry

## 1. What is it?

Trace sampling quyết định request nào được ghi/export đầy đủ spans. Mục tiêu không phải giảm telemetry tùy tiện mà là giữ đủ signal cho diagnosis/SLO trong khi kiểm soát CPU, network, storage và observability bill.

## 2. Why does it exist?

Ở 20.000 requests/s, 100% tracing với nhiều spans có thể tạo khối lượng dữ liệu khổng lồ. Nhưng random 1% sampling có thể bỏ mất rare error hoặc slow trace quan trọng.

## 3. How does it work?

Head sampling quyết định sớm khi trace bắt đầu, rẻ nhưng chưa biết kết quả cuối. Tail sampling quyết định sau khi thu thập spans, có thể giữ error/slow traces nhưng cần Collector buffer/state và nhiều resource hơn.

## 4. Practical implementation

Một head sampler trong .NET:

```csharp
services.AddOpenTelemetry()
    .WithTracing(builder => builder
        .SetSampler(new ParentBasedSampler(
            new TraceIdRatioBasedSampler(0.10)))
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation());
```

Nếu cần giữ 100% errors/slow traces, tail sampling tại Collector thường phù hợp hơn ratio-only head sampling.

## 5. Real production scenario

Checkout API có 10k RPS, error rate 0.05%. 5% random sampling tiết kiệm cost nhưng có thể chỉ giữ vài error traces. Tail policy giữ tất cả failed/slow traces và sample nhỏ success traffic.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard báo errors nhưng không tìm thấy trace tương ứng. **Evidence** → sampling policy drop phần lớn error traces trước khi biết status. **Hypothesis** → head sampling quá aggressive. **Diagnosis** → kiểm tra sampler/collector policy và propagated sampling flags. **Fix** → tail sampling hoặc policy phù hợp signal. **Verification** → inject known failures và xác nhận trace retention rate.

## 7. Common mistakes

Sampling logs/metrics giống traces; bỏ propagation; sample theo user ID gây bias; tail sampling không budget memory; giữ 100% spans nhưng vẫn thêm high-cardinality attributes không kiểm soát.

## 8. Alternatives

100% tracing phù hợp traffic thấp hoặc incident window. Dynamic/adaptive sampling có thể phù hợp backend cụ thể. Logs + metrics vẫn cần vì traces không thay thế aggregate signal.

## 9. Trade-offs

### Advantages

Giảm ingestion/storage cost và collector load.

### Costs / Risks

Có thể mất rare evidence; tail sampling tăng complexity và buffering.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu một trace gồm spans xuyên dependencies.

### Middle

Cấu hình instrumentation, propagation và basic sampler.

### Senior

Thiết kế sampling theo errors/latency/traffic và kiểm tra bias.

### Technical Lead / Architect

Đặt observability budget và retention policy dựa SLO/incident needs.

## 11. Key takeaway

- Sampling là signal-design decision, không chỉ cost switch.
- Head sampling rẻ; tail sampling thông minh hơn nhưng vận hành phức tạp hơn.
- Metrics phát hiện vấn đề; traces giúp giải thích một request path cụ thể.

# 8. Playwright E2E: deterministic synchronization thay vì sleep và retry che lỗi

## 1. What is it?

Playwright E2E test chạy user journey qua browser thật. Test ổn định dựa trên observable state và auto-waiting, không dựa vào thời gian ước lượng như `Task.Delay`/`waitForTimeout(5000)`.

## 2. Why does it exist?

Browser, API và rendering đều asynchronous. Fixed sleep có hai failure mode: quá ngắn thì flaky; quá dài thì suite chậm. Retry toàn test có thể biến bug race condition thật thành “green eventually”.

## 3. How does it work?

Playwright locators auto-wait cho actionability. Assertions có polling semantics. Test nên chờ trạng thái business/UI cụ thể, ví dụ row xuất hiện hoặc API response hoàn tất, thay vì chờ clock.

## 4. Practical implementation

```ts
await page.getByRole('button', { name: 'Approve' }).click();

await expect(page.getByTestId('status'))
  .toHaveText('Approved');

await expect(page.getByRole('alert'))
  .toContainText('Approval completed');
```

Seed data bằng API/fixture có kiểm soát thay vì phụ thuộc dữ liệu còn lại từ test trước.

## 5. Real production scenario

Approval workflow test đôi lúc fail CI vì API mất 1.2 giây thay vì 800 ms. Team thêm sleep 3 giây ở nhiều chỗ, suite tăng lên 40 phút. Chuyển sang state-based assertions giảm cả flakiness lẫn runtime.

## 6. Failure scenario & troubleshooting

**Symptom** → test pass khi retry. **Evidence** → trace/video cho thấy click xảy ra trước component ready hoặc data dùng chung bị test khác sửa. **Hypothesis** → synchronization/test isolation. **Diagnosis** → dùng Playwright trace, network logs và unique test data. **Fix** → locator/assertion theo state, isolate data. **Verification** → chạy test lặp nhiều lần và parallel CI.

## 7. Common mistakes

Sleep cố định; selector dựa CSS implementation; E2E test mọi edge case; share account/data mutable; retry cao để đạt green build; mock toàn backend rồi gọi đó là E2E.

## 8. Alternatives

Unit/component tests nhanh hơn cho logic/UI states. API integration tests tốt cho backend contracts. E2E nên bảo vệ số ít critical journeys xuyên hệ thống.

## 9. Trade-offs

### Advantages

Bắt lỗi integration/browser/deployment mà unit test không thấy.

### Costs / Risks

Chậm, khó isolate và nhạy với environment nếu scope quá rộng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Viết locator theo user-visible semantics.

### Middle

Dùng fixtures, traces, deterministic waits và isolated data.

### Senior

Phân loại flake vs product race, tối ưu test pyramid và CI parallelism.

### Technical Lead / Architect

Chọn journeys đáng E2E dựa business risk, không dựa coverage vanity.

## 11. Key takeaway

- Chờ state, không chờ clock.
- Retry không được dùng để che nondeterminism chưa hiểu.
- E2E có giá trị nhất ở critical cross-system journeys.

# 9. Akamai/CDN cache-control: freshness, invalidation và stale content ở edge

## 1. What is it?

CDN cache response gần user tại edge. `Cache-Control`, TTL và cache key quyết định response nào được reuse và trong bao lâu. Mental model: sau khi response được cache, origin không còn tham gia mọi request, nên deploy origin không đồng nghĩa edge content lập tức đổi.

## 2. Why does it exist?

Static assets và public content phục vụ từ origin cho mọi user làm tăng latency, bandwidth và origin load. CDN hấp thụ phần lớn read traffic và giảm distance tới client.

## 3. How does it work?

```text
Browser → Akamai Edge ── HIT ──> response
              │
             MISS
              ▼
           Origin
```

Freshness có thể đến từ `max-age`, `s-maxage` hoặc edge configuration. Cache key thường gồm host/path/query và có thể vary theo headers; key quá rộng gây sai content, quá chi tiết làm hit ratio thấp.

## 4. Practical implementation

ASP.NET Core public versioned asset:

```csharp
context.Response.Headers.CacheControl =
    "public,max-age=31536000,immutable";
```

Chỉ dùng TTL dài khi URL content-addressed/versioned như `app.a1b2c3.js`. HTML entry point thường cần policy ngắn hơn để trỏ tới asset version mới.

## 5. Real production scenario

Deploy frontend mới tạo bundle hash mới nhưng HTML cũ vẫn cached 30 phút ở edge. User nhận HTML trỏ tới asset đã bị cleanup, gây blank page. Root cause không nằm ở JavaScript logic mà ở release + cache lifecycle.

## 6. Failure scenario & troubleshooting

**Symptom** → một số regions vẫn thấy version cũ sau deploy. **Evidence** → response headers/edge diagnostics cho thấy cache HIT và Age cao. **Hypothesis** → edge object chưa expire/purge. **Diagnosis** → so sánh origin response với edge response và cache key. **Fix** → purge đúng object hoặc dùng versioned URL + release retention. **Verification** → kiểm tra nhiều POP/regions và headers sau purge.

## 7. Common mistakes

Cache personalized HTML; dùng TTL dài cho URL không versioned; purge toàn site mỗi deploy; bỏ query/header khỏi key dù response phụ thuộc chúng; assume browser cache và CDN cache là một tầng.

## 8. Alternatives

Browser cache giảm repeat load của cùng user nhưng không giảm origin cho first visit. Reverse-proxy cache gần origin hữu ích nhưng không có global edge proximity như CDN.

## 9. Trade-offs

### Advantages

Giảm latency, bandwidth và origin load; tăng resilience cho cacheable content.

### Costs / Risks

Stale content, invalidation complexity và cache-key security/correctness issues.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HIT/MISS, TTL và browser vs edge cache.

### Middle

Đọc cache headers, version assets và troubleshoot stale response.

### Senior

Thiết kế cache key, purge strategy, stale policy và deployment compatibility.

### Technical Lead / Architect

Xem CDN là một runtime data-delivery layer cần ownership, observability và release design.

## 11. Key takeaway

- Deploy origin không tự động invalidate edge.
- Versioned immutable assets đơn giản hóa cache correctness.
- Cache policy là một phần release architecture, không chỉ performance tuning.

# 10. AI Structured Outputs: schema validation không biến LLM thành deterministic business logic

## 1. What is it?

Structured Outputs yêu cầu model trả dữ liệu theo schema/shape xác định để application parse ổn định hơn. Nó giải quyết **output structure**, không đảm bảo mọi field mang ý nghĩa đúng, factual hay business-valid.

## 2. Why does it exist?

Parse prose bằng regex hoặc kỳ vọng JSON “gần đúng” làm integration brittle. Application cần contract machine-readable để gọi tool, tạo workflow hoặc lưu intermediate result.

## 3. How does it work?

```text
Prompt + schema
      │
      ▼
     LLM
      │ structured candidate
      ▼
Schema-valid output
      │
      ▼
Deterministic business validation
      │
      ├─ accept
      └─ reject / request correction
```

Schema có thể buộc `amount` là number nhưng không biết amount đó có vượt credit limit hay model đã suy luận đúng invoice hay không.

## 4. Practical implementation

Trong .NET, map response vào DTO rồi chạy deterministic validation:

```csharp
public sealed record RefundProposal(
    string OrderId,
    decimal Amount,
    string Reason);

public static Result Validate(
    RefundProposal proposal,
    Order order)
{
    if (proposal.OrderId != order.Id.ToString())
        return Result.Fail("order_mismatch");

    if (proposal.Amount < 0 || proposal.Amount > order.PaidAmount)
        return Result.Fail("invalid_amount");

    return Result.Success();
}
```

Model có thể đề xuất; application quyết định invariant tài chính.

## 5. Real production scenario

Support agent đọc ticket và đề xuất refund category/amount. Structured output giúp workflow parse proposal, nhưng backend vẫn kiểm tra order ownership, paid amount, policy limit và authorization trước khi tạo refund.

## 6. Failure scenario & troubleshooting

**Symptom** → JSON luôn parse được nhưng đôi lúc refund proposal sai business rule. **Evidence** → schema pass, domain validation fail. **Hypothesis** → team nhầm syntactic validity với semantic correctness. **Diagnosis** → phân loại failures theo schema, factual grounding và business invariant. **Fix** → deterministic validation + source grounding + evaluation dataset. **Verification** → chạy eval cases adversarial/edge và đo invalid proposal rate.

## 7. Common mistakes

Cho model tự quyết authorization; tin enum hợp lệ nghĩa decision đúng; không version schema; retry vô hạn khi model không thể biết missing data; đưa secret/tool capability không cần thiết vào context; test vài happy prompts rồi gọi production-ready.

## 8. Alternatives

Nếu logic có thể viết bằng rule/SQL/code rõ ràng, deterministic implementation thường rẻ và đáng tin hơn. LLM phù hợp extraction/classification/reasoning trên dữ liệu mơ hồ, với validation boundary rõ.

## 9. Trade-offs

### Advantages

Giảm parsing fragility, làm tool/workflow integration rõ contract hơn.

### Costs / Risks

Model vẫn probabilistic; schema evolution, token cost, latency, prompt injection và semantic error vẫn tồn tại.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt valid JSON với correct answer.

### Middle

Implement schema parsing, validation, timeout/retry và error handling.

### Senior

Thiết kế evals, grounding, security boundary và failure taxonomy.

### Technical Lead / Architect

Quyết định phần nào được giao cho model và phần nào bắt buộc deterministic, auditable và testable.

## 11. Key takeaway

- Structured output đảm bảo shape tốt hơn, không đảm bảo business truth.
- Authorization, financial invariants và security decisions phải ở deterministic boundary.
- Production AI cần validation + evaluation + observability, không chỉ prompt tốt.
