# 1. .NET `ArrayPool<T>` + `Span<T>`: giảm allocation trong hot path nhưng tránh biến optimization thành lifetime bug

## 1. What is it?

`ArrayPool<T>` cho phép thuê và trả lại array buffers để tái sử dụng thay vì allocate array mới liên tục. `Span<T>` là view type trên một vùng memory liên tục, cho phép slice và xử lý dữ liệu mà không cần tạo thêm array/sub-string ở nhiều trường hợp.

Mental model:

```text
Request 1 ─┐
Request 2 ─┼─> shared pool of reusable buffers
Request 3 ─┘
```

Đây là performance tool, không phải coding style mặc định. Nó hữu ích khi profiling đã chỉ ra allocation/GC pressure đáng kể ở hot path.

## 2. Why does it exist?

Nếu một API xử lý hàng nghìn payload/second và mỗi payload tạo nhiều temporary arrays, allocation rate có thể tăng mạnh. GC phải thu gom nhiều object ngắn hạn dù business logic rất đơn giản.

Pooling giảm số lần cấp phát và `Span<T>` giúp thao tác trên buffer hiện có mà không tạo copy không cần thiết.

## 3. How does it work?

`ArrayPool<T>.Shared.Rent(size)` trả một array có độ dài **ít nhất** bằng `size`, không đảm bảo đúng bằng `size`. Buffer được dùng xong phải `Return` để pool có thể tái sử dụng.

`Span<T>` chỉ là view:

```text
byte[] rented buffer
┌──────────────────────────────┐
│ header │ payload │ unused    │
└──────────────────────────────┘
          ↑
       Span<byte>
```

`Span<T>` là `ref struct`, không thể sống tùy ý trên heap và không được giữ qua các async suspension points như một object thông thường.

## 4. Practical implementation

```csharp
public static int CountAsciiDigits(ReadOnlySpan<byte> input)
{
    var count = 0;

    foreach (var b in input)
    {
        if (b is >= (byte)'0' and <= (byte)'9')
            count++;
    }

    return count;
}
```

Pooling buffer:

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(64 * 1024);

try
{
    var read = await stream.ReadAsync(
        buffer.AsMemory(0, 64 * 1024),
        cancellationToken);

    Process(buffer.AsSpan(0, read));
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

Nếu buffer chứa secret hoặc dữ liệu nhạy cảm, cân nhắc `clearArray: true` hoặc chủ động zero vùng đã sử dụng trước khi trả pool.

## 5. Real production scenario

Một service import CSV xử lý 5 GB dữ liệu theo stream. Phiên bản đầu dùng `ReadToEndAsync()` và nhiều `string.Split`, tạo lượng lớn object và temporary arrays.

Sau khi profiling xác nhận allocation là bottleneck, team chuyển parser sang chunked reads với pooled buffers và `Span<char>`. Throughput tăng, GC time giảm và memory peak ổn định hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu thỉnh thoảng bị corruption hoặc request A thấy dữ liệu request B.

**Evidence** → bug chỉ xuất hiện dưới concurrency cao, buffer content thay đổi sau khi method đã “trả kết quả”.

**Hypothesis** → code giữ reference tới rented buffer sau khi buffer đã `Return` về pool.

**Diagnosis** → kiểm tra ownership/lifetime, tìm nơi buffer được capture hoặc lưu trong object lâu sống.

**Fix** → copy dữ liệu cần tồn tại lâu sang owned memory hoặc trì hoãn `Return` tới khi consumer hoàn tất.

**Verification** → stress test concurrent workload và thêm ownership-focused tests.

## 7. Common mistakes

* Giả định array thuê có length đúng bằng requested size.
* `Return` buffer rồi vẫn sử dụng reference.
* Pool mọi array dù allocation rate không phải bottleneck.
* Không clear sensitive data trước khi trả pool.
* Cố giữ `Span<T>` qua `await` thay vì dùng `Memory<T>` khi cần async lifetime.

## 8. Alternatives

`Memory<T>` phù hợp khi buffer cần đi qua asynchronous boundaries.

Array allocation bình thường thường đơn giản hơn và hoàn toàn đủ nếu workload nhỏ hoặc GC không phải bottleneck.

`System.IO.Pipelines` phù hợp hơn khi xây high-throughput streaming parser/network pipeline phức tạp.

## 9. Trade-offs

### Advantages

Giảm allocation rate, giảm GC pressure và giảm copy trong hot path.

### Costs / Risks

Ownership phức tạp hơn, dễ tạo lifetime bug hoặc data leakage. Pooling cũng có thể giữ memory lớn lâu hơn dự kiến.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu allocation tạo áp lực cho GC và pooled buffer phải có owner rõ ràng.

### Middle

Biết dùng `Rent`/`Return`, `Span<T>`/`Memory<T>` đúng lifetime.

### Senior

Chỉ áp dụng sau profiling, đánh giá security, contention và end-to-end allocation reduction.

### Technical Lead / Architect

Quyết định hot path nào đáng complexity và đặt coding conventions để tránh pooling lan rộng không kiểm soát.

## 11. Key takeaway

* Pooling là optimization có ownership cost.
* `Span<T>` giúp xử lý view trên memory mà không copy.
* Đừng tối ưu allocation khi chưa đo allocation.

# 2. ASP.NET Core graceful shutdown: ngừng nhận traffic, hoàn tất request đang chạy và dừng background work đúng cách

## 1. What is it?

Graceful shutdown là quá trình application nhận tín hiệu dừng rồi chuyển từ “đang phục vụ bình thường” sang “không nhận work mới, cố hoàn tất work đang chạy, giải phóng resource và thoát”.

Nó quan trọng trong App Service recycle, Kubernetes rollout, container stop, VM shutdown và deployment.

## 2. Why does it exist?

Nếu process bị kill ngay lập tức:

* request đang xử lý có thể bị cắt giữa chừng
* queue message có thể bị mất lock hoặc xử lý duplicate
* buffered telemetry chưa flush
* temporary files/resources chưa cleanup
* database transaction có thể rollback ngoài ý muốn

Graceful shutdown làm deployment/restart trở thành behavior có kiểm soát thay vì random failure.

## 3. How does it work?

Typical flow:

```text
SIGTERM / stop signal
        ↓
readiness = unhealthy
        ↓
load balancer ngừng gửi request mới
        ↓
in-flight requests + BackgroundService nhận cancellation
        ↓
cleanup
        ↓
process exit
```

ASP.NET Core host truyền cancellation token tới hosted services. Host cũng có shutdown timeout; nếu code không dừng kịp, process vẫn có thể bị terminate.

## 4. Practical implementation

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var message = await ReceiveAsync(stoppingToken);
            await ProcessAsync(message, stoppingToken);
        }
    }
}
```

Đừng bỏ qua token:

```csharp
await httpClient.SendAsync(request, stoppingToken);
await db.SaveChangesAsync(stoppingToken);
```

Health endpoints nên phân biệt liveness và readiness để orchestration có thể ngừng routing trước khi kill process.

## 5. Real production scenario

Một service xử lý payment webhook mất 10–20 giây/request. Deployment rolling restart pod mỗi vài phút trong release window.

Nếu pod bị remove khỏi traffic và terminate đúng trình tự, requests đang xử lý có cơ hội hoàn tất. Nếu health/readiness không phối hợp, ingress vẫn gửi request mới vào pod sắp chết và tỷ lệ 502/499 tăng trong mỗi deployment.

## 6. Failure scenario & troubleshooting

**Symptom** → error rate chỉ tăng lúc deploy/restart.

**Evidence** → logs có `OperationCanceledException`, connection reset hoặc request bị cắt sát thời điểm pod/process termination.

**Hypothesis** → shutdown grace period ngắn hoặc app không dừng nhận work mới.

**Diagnosis** → correlate deployment timeline, readiness state, termination grace period và request duration.

**Fix** → readiness-first draining, propagate cancellation, điều chỉnh shutdown timeout hợp lý.

**Verification** → repeated rolling deployments dưới synthetic traffic không tạo spike đáng kể ở failed requests.

## 7. Common mistakes

* Catch `OperationCanceledException` rồi log Error như production defect.
* Hosted service dùng `CancellationToken.None` cho mọi I/O.
* Shutdown hook khởi động thêm work mới.
* Grace period 30 giây nhưng job thường chạy 10 phút và không có checkpoint/requeue strategy.

## 8. Alternatives

Long-running work có thể chuyển sang durable queue/worker architecture thay vì cố hoàn tất mọi thứ trong process shutdown window.

Một số stateless short-request APIs có thể dùng shutdown đơn giản hơn, nhưng vẫn cần traffic draining đúng.

## 9. Trade-offs

### Advantages

Giảm deployment-induced failures, giảm duplicate/lost work và tăng tính dự đoán khi restart.

### Costs / Risks

Shutdown lâu làm deployment chậm. Cố giữ process quá lâu có thể chặn orchestration nếu work không bounded.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process có thể bị dừng bất kỳ lúc nào và cancellation là control signal.

### Middle

Biết propagate `CancellationToken` và viết hosted service dừng đúng.

### Senior

Thiết kế draining, timeout và idempotent recovery cho interrupted work.

### Technical Lead / Architect

Xác định workload nào cần durable execution thay vì phụ thuộc process lifetime.

## 11. Key takeaway

* Restart là normal production event, không phải exception hiếm gặp.
* Graceful shutdown cần phối hợp app + load balancer/orchestrator.
* Long-running work phải có recovery strategy nếu vượt shutdown window.

# 3. EF Core transaction savepoints: phục hồi một phần transaction mà không rollback toàn bộ unit of work

## 1. What is it?

Savepoint là mốc bên trong database transaction cho phép rollback về một điểm trước đó thay vì rollback toàn transaction.

EF Core có thể tạo savepoint khi `SaveChanges` chạy trong transaction hiện có, tùy provider/cấu hình.

## 2. Why does it exist?

Một business operation đôi khi có nhiều bước persistence nhưng vẫn muốn giữ outer transaction.

Nếu bước sau fail vì concurrency hoặc validation database-level, team có thể muốn sửa/retry bước đó mà vẫn giữ transaction context thay vì bỏ toàn bộ work đã chuẩn bị.

## 3. How does it work?

```text
BEGIN TRANSACTION
  ↓
Step A
  ↓
SAVEPOINT before_step_b
  ↓
Step B fails
  ↓
ROLLBACK TO SAVEPOINT
  ↓
retry/alternative B
  ↓
COMMIT
```

Savepoint không commit dữ liệu sớm. Tất cả vẫn nằm trong cùng outer transaction cho tới `COMMIT`.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

try
{
    await UpdateOrderAsync(db, ct);
    await db.SaveChangesAsync(ct);

    await tx.CreateSavepointAsync("BeforeInventory", ct);

    try
    {
        await ReserveInventoryAsync(db, ct);
        await db.SaveChangesAsync(ct);
    }
    catch
    {
        await tx.RollbackToSavepointAsync("BeforeInventory", ct);
        throw;
    }

    await tx.CommitAsync(ct);
}
catch
{
    await tx.RollbackAsync(ct);
    throw;
}
```

Trong code thật, rollback-to-savepoint chỉ có ý nghĩa nếu application có recovery path rõ ràng; không nên thêm vì “framework hỗ trợ”.

## 5. Real production scenario

Một batch approval cập nhật header, sau đó xử lý nhiều child rows. Một child gặp concurrency conflict. Nếu business cho phép reload child rồi retry trong cùng transaction, savepoint giúp không cần restart toàn batch.

## 6. Failure scenario & troubleshooting

**Symptom** → transaction bị rollback toàn bộ dù developer nghĩ `SaveChanges` chỉ ảnh hưởng phần mới nhất.

**Evidence** → provider logs cho thấy transaction abort hoặc savepoint không được tạo.

**Hypothesis** → provider/transaction configuration không hỗ trợ behavior mà code giả định.

**Diagnosis** → kiểm tra generated transaction commands, provider docs và transaction state.

**Fix** → dùng explicit savepoint nếu thực sự cần và test integration với database thật.

**Verification** → deliberately fail bước sau và xác nhận state trước savepoint vẫn còn trong transaction trước commit.

## 7. Common mistakes

* Dùng savepoint để che thiết kế transaction quá lớn.
* Retry lỗi không-transient trong cùng transaction mà không thay đổi input/state.
* Chỉ test bằng mock thay vì provider thật.
* Giữ transaction mở trong khi gọi external API.

## 8. Alternatives

Tách transaction thành nhiều local transactions nếu business không cần atomicity xuyên các bước.

Saga/compensation phù hợp hơn nếu workflow đi qua nhiều services hoặc external systems.

## 9. Trade-offs

### Advantages

Cho phép recovery tinh hơn trong một local transaction.

### Costs / Risks

Tăng complexity, transaction vẫn giữ locks/resources lâu và có thể làm code khó reasoning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction chỉ commit khi outer transaction hoàn tất.

### Middle

Biết tạo/rollback savepoint và test với database thật.

### Senior

Phân biệt concurrency retry, transient retry và design smell do transaction quá dài.

### Technical Lead / Architect

Quyết định transaction boundary trước; chỉ dùng savepoint khi business recovery semantics thật sự cần.

## 11. Key takeaway

* Savepoint là partial rollback point, không phải partial commit.
* Transaction càng dài càng tăng lock/resource cost.
* Thiết kế transaction boundary quan trọng hơn API savepoint.

# 4. Cosmos DB partition key + hot partition: throughput phân tán chỉ tốt khi data distribution và access pattern khớp nhau

## 1. What is it?

Cosmos DB phân phối dữ liệu theo partition key. Các items có cùng logical partition key được nhóm vào cùng logical partition và được map lên physical partitions.

Partition key quyết định cả data locality lẫn cách request load được phân tán.

## 2. Why does it exist?

Một distributed database cần biết cách chia dữ liệu qua nhiều nodes để scale storage và throughput. Nếu mọi request đều đập vào cùng partition key, scale-out của toàn account không giúp nhiều cho hot key đó.

## 3. How does it work?

```text
Tenant A ─┐
Tenant B ─┼─ hash(partition key) → physical partitions
Tenant C ─┘
```

Một query có exact partition key thường rẻ hơn cross-partition query vì hệ thống biết nơi cần đọc.

Hot partition xuất hiện khi một key nhận disproportionate traffic, ví dụ `/country = "VN"` trong system mà 80% users ở Việt Nam.

## 4. Practical implementation

Model multi-tenant phổ biến:

```json
{
  "id": "order-123",
  "tenantId": "tenant-42",
  "customerId": "customer-7",
  "status": "Paid"
}
```

Container partition key:

```text
/tenantId
```

Query scoped theo tenant:

```csharp
var query = container.GetItemLinqQueryable<Order>(
        requestOptions: new QueryRequestOptions
        {
            PartitionKey = new PartitionKey(tenantId)
        })
    .Where(x => x.Status == "Paid");
```

Partition key nên xuất phát từ dominant access pattern, cardinality và expected distribution, không chỉ từ field “trông hợp lý”.

## 5. Real production scenario

Telemetry platform partition theo `/deviceType`. 70% devices là cùng một type. Khi campaign bắt đầu, write load dồn vào một partition range và nhận 429 dù account vẫn còn tổng RU/s chưa dùng hết ở các partition khác.

## 6. Failure scenario & troubleshooting

**Symptom** → 429 tập trung ở một subset requests; overall throughput nhìn vẫn chưa đầy.

**Evidence** → metrics cho thấy normalized RU consumption cao ở một physical partition và key distribution lệch.

**Hypothesis** → hot partition.

**Diagnosis** → phân tích top partition-key values và request distribution.

**Fix** → redesign key cho write distribution tốt hơn hoặc introduce synthetic partition key nếu access pattern cho phép.

**Verification** → load test với realistic key skew, theo dõi normalized RU trên từng partition.

## 7. Common mistakes

* Chọn partition key có cardinality thấp.
* Chỉ nghĩ về storage size mà không nghĩ request rate.
* Dùng random key để phân tán writes nhưng sau đó mọi read trở thành fan-out.
* Giả định tăng tổng RU/s sẽ tự chữa mọi hot partition.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp hơn nếu transaction relational và query flexibility quan trọng hơn global distribution.

MongoDB sharding có bài toán shard key tương tự: key distribution và access pattern vẫn là trung tâm.

## 9. Trade-offs

### Advantages

Partitioning đúng giúp throughput và storage scale horizontally hiệu quả.

### Costs / Risks

Key khó thay đổi sau khi hệ thống lớn; sai key tạo cross-partition queries hoặc hotspot dài hạn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định nơi data sống.

### Middle

Biết scope query theo key và đọc RU/429 metrics.

### Senior

Đánh giá skew, cardinality, fan-out và synthetic keys.

### Technical Lead / Architect

Chọn partition strategy từ business access patterns và growth model, không từ entity schema đơn thuần.

## 11. Key takeaway

* Partition key là scalability contract.
* High cardinality chưa đủ; distribution phải phù hợp traffic.
* Read locality và write distribution thường phải trade-off.

# 5. Modular Monolith module boundaries: tách ownership và dependency mà chưa trả giá vận hành của Microservices

## 1. What is it?

Modular Monolith là một deployable application duy nhất nhưng được chia thành các modules có boundary rõ về code, dependency và data ownership.

```text
Single deployment
├─ Orders module
├─ Billing module
├─ Identity module
└─ Notifications module
```

Điểm cốt lõi là module boundary, không phải folder naming.

## 2. Why does it exist?

Layered monolith thường trượt dần thành hệ thống nơi mọi feature gọi trực tiếp repository/service của feature khác. Coupling tăng nhanh và thay đổi nhỏ kéo theo regression rộng.

Microservices có thể tạo boundary mạnh nhưng thêm network, deployment, observability và consistency complexity. Modular Monolith nằm giữa hai thái cực.

## 3. How does it work?

Mỗi module sở hữu API/application/domain logic của nó. Module khác chỉ tương tác qua public contract hoặc integration mechanism được cho phép.

Dependency rule:

```text
Orders ──public contract──> Billing
Orders -X-> Billing internal repository
```

Data có thể cùng database vật lý nhưng ownership logical phải rõ. Cross-module table access cần được hạn chế nếu muốn boundary có giá trị.

## 4. Practical implementation

```csharp
public interface IBillingModule
{
    Task<PaymentStatus> GetPaymentStatusAsync(
        OrderId orderId,
        CancellationToken cancellationToken);
}
```

`Orders` phụ thuộc contract thay vì `BillingDbContext`.

Với integration event nội bộ:

```csharp
public sealed record OrderPlaced(Guid OrderId, Guid CustomerId);
```

Có thể dispatch in-process lúc đầu và chuyển sang broker sau nếu deployment boundary thay đổi.

## 5. Real production scenario

Một SaaS có Projects, Billing, Documents và Notifications. Team ban đầu cùng một application. Billing release cadence chưa cần độc lập và traffic chưa đủ để justify separate service.

Modular Monolith giúp team cô lập Billing schema/code và public contract mà không cần vận hành bốn services, bốn pipelines và distributed tracing ngay lập tức.

## 6. Failure scenario & troubleshooting

**Symptom** → module A thay đổi table/module B và build vẫn pass nhưng production regression xuất hiện ở B.

**Evidence** → direct database references, shared entities và circular project references.

**Hypothesis** → module boundary chỉ tồn tại trên sơ đồ.

**Diagnosis** → dependency analysis và search cross-module data access.

**Fix** → public contracts, ownership rules, architecture tests và migration strategy cho shared types.

**Verification** → module internals có thể thay đổi mà consumer chỉ bị ảnh hưởng khi public contract đổi.

## 7. Common mistakes

* Gọi Modular Monolith chỉ vì có nhiều class-library projects.
* Shared “Common” project chứa toàn bộ domain entities.
* Mọi module cùng truy cập mọi table.
* Introduce internal event bus phức tạp dù direct contract call đã đủ.

## 8. Alternatives

Simple layered monolith phù hợp với product nhỏ và business complexity thấp.

Microservices phù hợp khi cần independent deployment/scaling/ownership và tổ chức đủ năng lực vận hành distributed system.

## 9. Trade-offs

### Advantages

Boundary tốt hơn monolith tự do nhưng deployment, debugging và transaction đơn giản hơn Microservices.

### Costs / Risks

Boundary có thể bị phá dễ dàng vì process/database vẫn chung. Cần discipline và automated architecture checks.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module có public surface và internal implementation.

### Middle

Biết tránh direct cross-module repository/entity usage.

### Senior

Thiết kế ownership, transaction boundary và integration contracts.

### Technical Lead / Architect

Quyết định khi nào module cần tách thành service thật dựa trên scale, team ownership và operational requirement.

## 11. Key takeaway

* Modular Monolith là boundary strategy, không phải folder strategy.
* Microservices không phải bước nâng cấp mặc định.
* Data ownership phải rõ ngay cả khi dùng chung database server.

# 6. Azure Blob Storage large-file streaming + SAS: upload/download file lớn mà không giữ toàn bộ file trong application memory

## 1. What is it?

Azure Blob Storage lưu object/file độc lập với application process. Với file lớn, application nên stream dữ liệu hoặc cho client upload trực tiếp bằng scoped SAS thay vì buffer toàn bộ file trong web server memory.

## 2. Why does it exist?

Pattern ngây thơ:

```text
Client → API memory → Blob Storage
```

Nếu API gọi `CopyToAsync(MemoryStream)` cho file 1 GB, vài concurrent uploads có thể đẩy process vào memory pressure/OOM.

Direct-to-blob upload giảm data path qua application server.

## 3. How does it work?

Option 1 — server streaming:

```text
Client → ASP.NET Core stream → Blob Storage
```

Option 2 — SAS upload:

```text
Client → API xin short-lived SAS
Client → Blob Storage upload trực tiếp
Client → API finalize metadata
```

SAS phải scope tối thiểu quyền, resource và thời gian.

## 4. Practical implementation

Server streaming:

```csharp
await blobClient.UploadAsync(
    request.Body,
    overwrite: false,
    cancellationToken);
```

Không cần đọc toàn bộ request vào byte array trước.

Với SAS, backend tạo URI chỉ có quyền cần thiết cho một blob cụ thể, ví dụ create/write trong vài phút. Nếu môi trường hỗ trợ, ưu tiên User Delegation SAS dùng Microsoft Entra credentials thay vì account key dài hạn.

## 5. Real production scenario

CMS cho editor upload video 2–5 GB. Khi upload đi qua App Service, memory và outbound bandwidth tăng mạnh, deployment scale-out đắt hơn.

Team đổi sang direct Blob upload bằng short-lived SAS; application chỉ quản metadata, authorization và post-processing events.

## 6. Failure scenario & troubleshooting

**Symptom** → API memory tăng theo số upload đồng thời, request timeout và process restart.

**Evidence** → traces cho thấy endpoint giữ request lâu; heap có large byte arrays/MemoryStream.

**Hypothesis** → full buffering.

**Diagnosis** → inspect upload path và request limits.

**Fix** → streaming hoặc direct-to-blob; bounded post-processing.

**Verification** → upload nhiều file lớn đồng thời, process memory không tăng tỷ lệ trực tiếp với file size.

## 7. Common mistakes

* SAS có expiry quá dài hoặc quyền container-wide không cần thiết.
* Tin filename/content-type từ client mà không validate.
* Cho upload xong là “trusted”; không malware scanning/content validation khi domain yêu cầu.
* Lưu account key trong config thay vì Managed Identity/User Delegation khi có thể.

## 8. Alternatives

API proxy streaming phù hợp khi server phải inspect/transform bytes inline.

Azure Files phù hợp hơn khi workload cần filesystem semantics thay vì object storage.

## 9. Trade-offs

### Advantages

Giảm application memory/bandwidth pressure và tận dụng storage service scale.

### Costs / Risks

Direct upload làm workflow nhiều bước hơn và cần finalize/cleanup orphan blobs, security policy và CORS phù hợp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu stream khác với load toàn bộ file vào memory.

### Middle

Biết implement upload streaming và scoped SAS.

### Senior

Thiết kế orphan cleanup, resumable/block uploads, validation và telemetry.

### Technical Lead / Architect

Chọn data path dựa trên file size, compliance, cost và trust boundary.

## 11. Key takeaway

* File lớn không nên tự động đi qua application memory.
* SAS là delegated capability và phải least-privilege, short-lived.
* Upload architecture phải bao gồm validation và cleanup lifecycle.

# 7. Third-party API resilience với timeout, retry, jitter và Circuit Breaker: chống failure propagation mà không tạo retry storm

## 1. What is it?

Resilience policy kiểm soát cách service phản ứng khi remote dependency chậm hoặc lỗi. Các primitive thường gồm timeout, retry, exponential backoff, jitter và Circuit Breaker.

Chúng giải quyết các failure modes khác nhau và không nên ghép máy móc.

## 2. Why does it exist?

Remote dependency sẽ có latency spike, connection reset, throttling hoặc outage. Không có timeout, request có thể treo quá lâu. Retry có thể cứu transient failure, nhưng retry quá mức làm dependency đang yếu càng yếu hơn.

## 3. How does it work?

```text
Request
  ↓
per-attempt timeout
  ↓ fail transient
retry after backoff + jitter
  ↓ repeated failures
Circuit opens
  ↓
fail fast trong cooling window
```

Jitter làm nhiều clients không retry cùng một millisecond sau outage.

## 4. Practical implementation

Với modern .NET resilience stack, policy nên gắn vào `HttpClient` đã được quản lý bởi `IHttpClientFactory`.

Pseudo-config gần production:

```csharp
services.AddHttpClient("reviews", client =>
{
    client.BaseAddress = new Uri(config.ReviewsBaseUrl);
})
.AddStandardResilienceHandler();
```

Business rule phải quyết định status nào retry được. `400 Bad Request` thường không transient; `429`, timeout hoặc một số `5xx` có thể retry nếu operation an toàn.

## 5. Real production scenario

Product page gọi Review API. Dependency chậm 8 giây trong outage. Nếu web request chờ đủ 8 giây, toàn page latency bị kéo theo.

Team đặt short timeout, fallback sang “reviews temporarily unavailable”, và circuit breaker để không tiếp tục bắn hàng nghìn calls vào dependency đang down.

## 6. Failure scenario & troubleshooting

**Symptom** → external provider outage nhỏ nhưng outbound request volume tăng gấp 4.

**Evidence** → mỗi inbound request tạo nhiều retries, provider trả 429 ngày càng nhiều.

**Hypothesis** → retry amplification.

**Diagnosis** → inspect retry count, backoff và end-to-end deadline.

**Fix** → retry budget nhỏ, exponential backoff + jitter, circuit breaker và fallback khi business cho phép.

**Verification** → chaos test dependency failure; outbound QPS phải bounded.

## 7. Common mistakes

* Retry `POST` side-effecting mà không có idempotency.
* Timeout mỗi attempt 5s × 4 retries trong request budget 3s.
* Retry tất cả exceptions/status codes.
* Circuit breaker toàn service nhưng không phân biệt dependency/endpoint quan trọng.

## 8. Alternatives

Queue-based asynchronous integration tốt hơn nếu request không cần synchronous response từ dependency.

Cached/stale data có thể phù hợp cho read-only third-party data khi freshness cho phép.

## 9. Trade-offs

### Advantages

Giảm failure propagation và cải thiện recovery từ transient faults.

### Costs / Risks

Policy sai dễ tăng load, latency và complexity. Circuit breaker có thể fail-fast cả lúc dependency vừa hồi phục nếu tuning quá bảo thủ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout, retry và circuit breaker giải quyết vấn đề khác nhau.

### Middle

Biết cấu hình policy cơ bản và log attempt/final outcome.

### Senior

Thiết kế retry budget, idempotency và end-to-end deadline.

### Technical Lead / Architect

Quyết định synchronous dependency nào nên tồn tại và failure nào cần degrade gracefully thay vì retry.

## 11. Key takeaway

* Retry không phải reliability nếu nó khuếch đại outage.
* Timeout phải nằm trong end-to-end latency budget.
* Remote dependency cần explicit degradation strategy.

# 8. SLI/SLO + burn-rate alerting: cảnh báo theo user impact thay vì chỉ theo CPU hoặc error spike tức thời

## 1. What is it?

SLI là chỉ số đo trải nghiệm/reliability thực tế, ví dụ tỷ lệ successful requests hoặc tỷ lệ requests dưới latency threshold.

SLO là mục tiêu cho SLI trong một cửa sổ thời gian, ví dụ 99.9% successful requests trong 30 ngày.

Error budget là phần failure cho phép: với SLO 99.9%, budget là 0.1%.

## 2. Why does it exist?

Alert kiểu “CPU > 80%” có thể ồn nhưng không nói user có bị ảnh hưởng không. Ngược lại, API trả 20% lỗi do dependency failure trong khi CPU chỉ 30% vẫn là incident nghiêm trọng.

SLO chuyển monitoring sang outcome mà product/users quan tâm.

## 3. How does it work?

Ví dụ availability SLI:

```text
successful eligible requests
----------------------------
total eligible requests
```

Burn rate đo tốc độ tiêu error budget. Nếu hệ thống tiêu budget nhanh gấp 14 lần bình thường, outage ngắn cũng đáng page ngay.

Multi-window alerts thường kết hợp cửa sổ ngắn để phát hiện nhanh và cửa sổ dài để tránh noise.

## 4. Practical implementation

Giả sử API có SLO 99.9%. Metrics cần ít nhất:

```text
requests_total
requests_good
```

PromQL-like concept:

```text
error_ratio = 1 - good_requests / total_requests
burn_rate = error_ratio / 0.001
```

Trong Application Insights/Azure Monitor, có thể xây metric-based alert tương đương dựa trên success rate và latency percentile.

## 5. Real production scenario

Checkout API có CPU 55%, memory ổn nhưng payment provider trả timeout. Error rate 8% trong 10 phút.

Infra alerts gần như im lặng. SLO alert page ngay vì error budget burn cao và user không checkout được.

## 6. Failure scenario & troubleshooting

**Symptom** → on-call bị hàng trăm alerts nhưng phần lớn không cần hành động.

**Evidence** → alerts dựa vào low-level metrics không correlate với failed user requests.

**Hypothesis** → monitoring không gắn với service objective.

**Diagnosis** → map alerts hiện tại tới user impact và incident history.

**Fix** → định nghĩa SLI/SLO, giữ resource alerts như diagnostic/supporting signals thay vì primary paging trigger.

**Verification** → retrospective: pages mới có precision tốt hơn và bắt được incidents có user impact.

## 7. Common mistakes

* SLO = SLA pháp lý; thực tế chúng phục vụ mục đích khác nhau.
* Chọn 100% SLO và vô tình cấm mọi thay đổi/risk.
* Dùng average latency làm SLI thay vì percentile/threshold phù hợp.
* Tính cả requests không thuộc service responsibility làm denominator sai.

## 8. Alternatives

Static threshold alerts vẫn hữu ích cho hard capacity limits, certificate expiry hoặc queue disk pressure.

Không phải service nào cũng cần formal SLO phức tạp; internal low-risk tool có thể dùng simpler targets.

## 9. Trade-offs

### Advantages

Alerts sát user impact hơn, hỗ trợ release-risk decisions và giảm noise.

### Costs / Risks

Cần thống nhất definition, telemetry chất lượng và stakeholder alignment.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SLI đo reliability; SLO là mục tiêu.

### Middle

Biết instrument good/total requests và latency.

### Senior

Thiết kế burn-rate alerts và phân tích denominator/exclusions.

### Technical Lead / Architect

Chọn SLO phản ánh business criticality và dùng error budget để cân bằng reliability với delivery speed.

## 11. Key takeaway

* Page nên phản ánh user impact, không chỉ machine activity.
* Error budget biến reliability thành quantity có thể reasoning.
* SLO tốt phụ thuộc SLI definition tốt.

# 9. HTTP caching với `Cache-Control`, ETag và CDN revalidation: giảm origin load mà vẫn kiểm soát freshness

## 1. What is it?

HTTP caching cho phép browser/CDN giữ response và reuse hoặc revalidate nó dựa trên standard headers.

`Cache-Control` mô tả freshness/cacheability. ETag là validator đại diện cho version của representation.

## 2. Why does it exist?

Nếu static hoặc semi-static content luôn về origin, hệ thống tốn latency, bandwidth và application/database capacity không cần thiết.

Nhưng cache mà không có freshness contract rõ ràng dễ trả stale hoặc private data sai đối tượng.

## 3. How does it work?

Fresh cache hit:

```text
Browser → CDN → cached response
```

Revalidation:

```text
Client → If-None-Match: "v42"
Origin → 304 Not Modified
```

`304` tránh gửi lại response body nếu representation chưa đổi.

## 4. Practical implementation

```csharp
app.MapGet("/catalog/{id}", async (int id, CatalogService service) =>
{
    var item = await service.GetAsync(id);
    var etag = $"\"{item.Version}\"";

    return Results.Ok(item);
});
```

Trong thực tế, middleware/filter có thể set:

```http
Cache-Control: public, max-age=60, s-maxage=300
ETag: "catalog-42"
```

Dynamic personalized endpoint thường cần `private` hoặc `no-store` tùy sensitivity.

## 5. Real production scenario

Marketing/CMS page có 95% anonymous traffic và thay đổi vài lần/ngày. CDN cache 5 phút giảm origin QPS mạnh.

Khi editor publish update, team có thể purge targeted URL hoặc dựa vào short TTL/revalidation tùy freshness requirement.

## 6. Failure scenario & troubleshooting

**Symptom** → user A thấy response có dữ liệu user B.

**Evidence** → response personalized bị header `public` và CDN cache key không vary theo identity/input phù hợp.

**Hypothesis** → cache boundary sai.

**Diagnosis** → inspect response headers, CDN cache status và cache key configuration.

**Fix** → private/no-store cho personalized content hoặc redesign cache key nếu use case thật sự cho phép shared caching.

**Verification** → cross-user tests qua CDN và browser cache disabled/enabled.

## 7. Common mistakes

* Set `public` cho authenticated response chỉ vì endpoint GET.
* TTL dài nhưng không có purge strategy.
* Dùng ETag dựa trên timestamp không ổn định làm mọi request miss validation.
* Quên `Vary`/cache-key dimensions khi response phụ thuộc headers/query parameters.

## 8. Alternatives

Application/Redis caching giảm backend computation nhưng request vẫn phải đến origin.

CDN caching hiệu quả hơn khi muốn tránh cả network hop tới application.

## 9. Trade-offs

### Advantages

Giảm latency, origin load và bandwidth; tận dụng standard browser/CDN behavior.

### Costs / Risks

Freshness và cache-key correctness phức tạp; sai boundary có thể thành security incident.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu freshness và revalidation khác nhau.

### Middle

Biết dùng `Cache-Control`, ETag và kiểm tra browser/CDN headers.

### Senior

Thiết kế cache key, purge strategy và privacy rules.

### Technical Lead / Architect

Quyết định layer cache nào nên tồn tại: browser, CDN, reverse proxy, Redis hay application.

## 11. Key takeaway

* HTTP cache là protocol-level architecture, không chỉ browser optimization.
* Shared caching và personalized data là boundary nguy hiểm.
* ETag giúp revalidate mà không phải tải lại body.

# 10. JWT validation + signing-key rotation: xác thực token đúng issuer/audience/signature khi identity provider thay key

## 1. What is it?

JWT validation không phải chỉ decode payload. API phải xác minh signature và các claims/constraints quan trọng như issuer, audience, lifetime và token type phù hợp.

Identity provider có thể rotate signing keys. API thường lấy metadata/JWKS để biết public keys hợp lệ.

## 2. Why does it exist?

JWT payload là Base64URL-encoded và ai cũng có thể đọc/tạo chuỗi tương tự. Security đến từ cryptographic signature và validation policy, không đến từ format JWT.

Key rotation cho phép IdP thay signing key mà không phải dừng toàn ecosystem.

## 3. How does it work?

```text
Client nhận access token từ IdP
        ↓
API đọc kid trong JWT header
        ↓
API tìm matching public key từ JWKS
        ↓
verify signature
        ↓
validate iss + aud + exp + policy
        ↓
authorize request
```

Nếu `kid` mới xuất hiện sau rotation và API metadata cache chưa refresh, valid token có thể bị reject tạm thời.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services
    .AddAuthentication("Bearer")
    .AddJwtBearer("Bearer", options =>
    {
        options.Authority = config["Identity:Authority"];
        options.Audience = config["Identity:Audience"];
        options.RequireHttpsMetadata = true;
    });
```

Không nên tự parse JWT rồi tin claims:

```csharp
// Sai mental model nếu dùng để authorize:
var jwt = new JwtSecurityTokenHandler().ReadJwtToken(token);
var role = jwt.Claims.First(x => x.Type == "role").Value;
```

Parsing không chứng minh token hợp lệ.

## 5. Real production scenario

Production dùng Microsoft Entra ID. IdP rotate key; một instance API cache metadata cũ lâu hơn expected. Một subset requests bắt đầu 401 với signature-key-not-found trong vài phút.

Incident ban đầu bị nhầm thành “user session expired”, nhưng telemetry cho thấy failures correlate theo `kid` mới.

## 6. Failure scenario & troubleshooting

**Symptom** → token hoạt động ở instance/environment này nhưng 401 ở instance khác.

**Evidence** → authentication logs có key-not-found, issuer/audience mismatch hoặc clock/lifetime validation failure.

**Hypothesis** → stale metadata/JWKS hoặc config khác nhau giữa instances.

**Diagnosis** → so `iss`, `aud`, `kid`, metadata endpoint, cache refresh behavior và clock skew.

**Fix** → dùng standards-based middleware metadata refresh; đồng bộ config; không hard-code single signing key nếu IdP hỗ trợ rotation.

**Verification** → test token ký bằng current key và simulated next key/refresh path.

## 7. Common mistakes

* Decode JWT rồi coi đó là validation.
* Disable audience/issuer validation để “fix 401”.
* Log full access token vào logs.
* Hard-code signing key lâu dài.
* Dùng ID token để gọi API thay vì access token phù hợp.

## 8. Alternatives

Opaque/reference tokens với introspection phù hợp khi muốn server-side revocation/control mạnh hơn, nhưng tăng dependency vào authorization server.

Cookie authentication phù hợp cho server-rendered web apps ở một số architectures.

## 9. Trade-offs

### Advantages

JWT validation local giảm round trip tới IdP cho mỗi request và scale tốt.

### Costs / Risks

Revocation khó tức thời hơn, key/metadata cache phải đúng và validation misconfiguration có thể trở thành security bug nghiêm trọng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu decode khác validate.

### Middle

Biết cấu hình Authority/Audience và đọc authentication logs.

### Senior

Hiểu JWKS, `kid`, key rotation, token lifetime và clock skew.

### Technical Lead / Architect

Xác định trust boundary, token type, issuer strategy và cách xử lý revocation/rotation toàn hệ thống.

## 11. Key takeaway

* JWT chỉ đáng tin sau signature + claim validation đúng.
* Key rotation phải là expected operational behavior.
* Không “fix” authentication bằng cách tắt validation quan trọng.
