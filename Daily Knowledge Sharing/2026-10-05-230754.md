# 1. .NET GC latency modes và allocation rate: đọc GC pressure thay vì chỉ nhìn memory usage

## 1. What is it?

Mental model: Garbage Collector không chỉ quan tâm application đang giữ bao nhiêu memory; nó phải xử lý **tốc độ tạo object**, tuổi thọ object và kích thước heap. Hai service cùng dùng 1 GB RAM có thể có GC behavior hoàn toàn khác nhau nếu một service allocate 5 MB/s còn service kia allocate 500 MB/s.

.NET GC chia managed heap thành generations và có nhiều latency/concurrency behaviors để cân bằng throughput với pause time.

## 2. Why does it exist?

Automatic memory management loại bỏ phần lớn manual allocation/free errors, nhưng GC phải tìm object còn sống, compact hoặc reclaim heap. Nếu request path tạo quá nhiều temporary objects, application có thể tốn CPU cho collection và xuất hiện tail-latency spikes dù memory graph nhìn “ổn”.

## 3. How does it work?

Object mới thường vào Gen 0. Object sống qua collection được promote. Object lớn thường đi vào LOH.

```text
request
  -> allocations
  -> Gen 0 fills
  -> GC
  -> survivors promoted
  -> more allocations
  -> Gen 1 / Gen 2 pressure
```

Điểm cần quan sát là allocation rate, collection count, pause duration, promoted bytes và LOH—not only process working set.

## 4. Practical implementation

Dùng runtime counters trước khi sửa code:

```bash
dotnet-counters monitor -p <PID> System.Runtime
```

Sau đó profile allocation hot path. Ví dụ serialization loop tạo string trung gian không cần thiết:

```csharp
// Avoid repeated temporary strings in a hot loop when direct serialization is possible.
await JsonSerializer.SerializeAsync(
    response.Body,
    payload,
    cancellationToken: ct);
```

Optimization chỉ hợp lý khi profiler chứng minh allocation nằm trên hot path.

## 5. Real production scenario

Product API có p50 40 ms nhưng p99 thỉnh thoảng vượt 900 ms. CPU tăng theo traffic, memory không leak. Runtime counters cho thấy allocation rate tăng mạnh sau release và Gen 2 collections xuất hiện thường xuyên hơn. Root cause là middleware mới materialize request/response bodies thành nhiều large strings để logging.

## 6. Failure scenario & troubleshooting

**Symptom** → tail latency tăng theo traffic. **Evidence** → allocation rate và GC pause tăng. **Hypothesis** → temporary allocations gây GC pressure. **Diagnosis** → counters → allocation profiler → hot call stacks. **Fix** → giảm materialization/copying, bounded logging, pooling khi thực sự đáng giá. **Verification** → chạy cùng load và so allocation/sec, GC pause, p95/p99.

## 7. Common mistakes

Chỉ nhìn RAM; gọi `GC.Collect()`; dùng object pooling cho mọi object; chuyển sang `Span<T>` trước khi profile; nhầm memory leak với high allocation churn.

## 8. Alternatives

Đôi khi scale-out rẻ và an toàn hơn micro-optimization. Pooling phù hợp với expensive reusable buffers; code thông thường nên ưu tiên readability nếu GC không phải bottleneck.

## 9. Trade-offs

### Advantages

Giảm allocation có thể giảm CPU và tail latency.

### Costs / Risks

Pooling, spans và manual buffer management tăng complexity, lifetime bugs và maintenance cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu managed memory vẫn có runtime cost.

### Middle

Biết đọc basic GC counters và tránh obvious allocation waste.

### Senior

Phân biệt leak, high allocation rate, LOH pressure và genuine GC bottleneck bằng profiling.

### Technical Lead / Architect

Quyết định optimization nào đáng complexity và đặt performance budget theo workload/SLO.

## 11. Key takeaway

- Memory usage và allocation rate là hai tín hiệu khác nhau.
- Đo GC behavior trước khi tối ưu.
- Tail latency thường quan trọng hơn average latency.

# 2. ASP.NET Core streaming responses: backpressure, cancellation và tránh buffer toàn bộ payload

## 1. What is it?

Streaming response gửi dữ liệu dần cho client thay vì materialize toàn bộ response trong memory trước khi bắt đầu truyền. Mental model: producer tạo dữ liệu theo dòng/chunk và network consumer quyết định tốc độ thực tế.

## 2. Why does it exist?

Export 2 GB CSV hoặc proxy file lớn không thể scale tốt nếu mỗi request giữ toàn bộ payload trong RAM. Buffering làm tăng memory pressure và time-to-first-byte.

## 3. How does it work?

```text
Database / Blob
      |
      v
application reads chunk
      |
      v
response stream
      |
      v
client/network
```

Nếu client đọc chậm, writes có thể chậm theo. Đây là backpressure tự nhiên; application không nên tiếp tục tạo unbounded data phía trước consumer.

## 4. Practical implementation

```csharp
app.MapGet("/export", async (
    HttpResponse response,
    ReportService reports,
    CancellationToken ct) =>
{
    response.ContentType = "text/csv";

    await foreach (var row in reports.StreamRowsAsync(ct))
    {
        await response.WriteAsync(
            $"{row.Id},{row.Total}\n",
            ct);
    }
});
```

Production code cần CSV escaping, batching writes và cancellation propagation.

## 5. Real production scenario

Admin export vài triệu transactions. Version cũ gọi `ToListAsync()`, build một giant string rồi trả file. Ba exports đồng thời gây memory spike. Streaming giảm peak memory và client nhận bytes sớm hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → requests sống rất lâu và connection count tăng. **Evidence** → clients tải chậm hoặc disconnect nhưng backend work vẫn chạy. **Hypothesis** → cancellation không propagate / producer chạy trước consumer. **Diagnosis** → traces + active request duration + cancellation logs. **Fix** → propagate request cancellation, bounded buffering, batch writes. **Verification** → throttle/disconnect client trong load test.

## 7. Common mistakes

Streaming nhưng vẫn `ToListAsync()` trước; giữ DbContext/transaction hàng giờ; bỏ cancellation; flush từng byte; giả định response có thể đổi status code sau khi headers đã gửi.

## 8. Alternatives

Background export job + Blob Storage/SAS tốt hơn cho exports rất lớn hoặc cần retry/resume. Buffered response đơn giản hơn cho payload nhỏ.

## 9. Trade-offs

### Advantages

Peak memory thấp, time-to-first-byte tốt.

### Costs / Risks

Connection sống lâu, error handling khó hơn sau khi response bắt đầu, database resources có thể bị giữ lâu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu buffering vs streaming.

### Middle

Implement stream với cancellation.

### Senior

Thiết kế backpressure, resource lifetime và failure after headers.

### Technical Lead / Architect

Chọn synchronous streaming hay asynchronous export workflow dựa trên size, SLO và operational cost.

## 11. Key takeaway

- Streaming không đồng nghĩa “free scalability”.
- Backpressure và cancellation là phần của design.
- Export cực lớn thường phù hợp background job hơn request dài.

# 3. EF Core execution strategy + transaction: retry transient failure mà không phá transaction boundary

## 1. What is it?

EF Core execution strategy có thể retry database operations khi gặp transient failures. Mental model: retry chỉ an toàn khi **toàn bộ unit of work có thể được replay đúng cách**.

## 2. Why does it exist?

Cloud database connections có thể transiently fail do networking, failover hoặc throttling. Retry từng command tùy tiện trong transaction có thể tạo state không xác định.

## 3. How does it work?

Execution strategy gọi một delegate. Nếu transient exception xảy ra, delegate được chạy lại. Khi application tự mở transaction, transaction phải nằm **bên trong** retriable delegate.

## 4. Practical implementation

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    order.MarkApproved();
    db.AuditEntries.Add(new AuditEntry(order.Id, "Approved"));

    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
});
```

External side effects như gửi email không nên nằm tùy tiện trong replayable block; Outbox thường phù hợp hơn.

## 5. Real production scenario

Azure SQL failover tạo transient connection error giữa approval workflow. Retry strategy replay database unit of work. Notification intent được ghi bằng Outbox trong cùng transaction thay vì gửi email trực tiếp trong retry block.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate external action hoặc lỗi “execution strategy does not support user-initiated transactions”. **Evidence** → transaction mở ngoài strategy hoặc HTTP/message send trong delegate. **Hypothesis** → retry boundary sai. **Diagnosis** → trace transaction + side effects. **Fix** → đưa transaction vào strategy; tách side effects bằng Outbox/idempotency. **Verification** → fault injection giữa commands.

## 7. Common mistakes

Retry mọi exception; nested retry ở EF + Polly + application; gửi message/email trong retriable delegate; nghĩ commit timeout chắc chắn nghĩa là rollback.

## 8. Alternatives

Database-native resiliency, application-level retry hoặc không retry nếu operation không replay-safe.

## 9. Trade-offs

### Advantages

Tăng resilience trước transient faults.

### Costs / Risks

Replay làm transaction dài hơn và có thể duplicate non-transactional side effects.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt transient và permanent failure.

### Middle

Configure execution strategy đúng.

### Senior

Reason về ambiguous commit và replay-safe side effects.

### Technical Lead / Architect

Đặt retry boundary xuyên application, database và messaging để tránh retry amplification.

## 11. Key takeaway

- Retry là correctness problem, không chỉ reliability feature.
- Transaction và retry boundary phải được thiết kế cùng nhau.
- External side effects cần idempotency hoặc Outbox.

# 4. PostgreSQL MVCC và vacuum: long-running transaction có thể làm database phình

## 1. What is it?

MVCC cho phép readers/writers làm việc với các row versions thay vì luôn block nhau. Khi `UPDATE`, PostgreSQL tạo row version mới; version cũ chỉ được reclaim khi không transaction nào còn cần nhìn thấy nó.

## 2. Why does it exist?

Nếu mọi reader giữ shared lock chặn writer, concurrency sẽ thấp. MVCC cho phép snapshot-based reads nhưng đổi lại database phải quản lý dead tuples.

## 3. How does it work?

```text
T1 snapshot starts
T2 updates row -> new version
old version cannot be removed while T1 may still need it
T1 stays open...
dead tuples accumulate
VACUUM cannot reclaim all old versions
```

## 4. Practical implementation

Theo dõi long transactions và table statistics:

```sql
SELECT pid, xact_start, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Không giữ transaction mở trong lúc gọi external API hoặc chờ user interaction.

## 5. Real production scenario

Batch service mở transaction, đọc records rồi gọi third-party API cho từng record trong 40 phút. Table update liên tục. Autovacuum chạy nhưng không reclaim được nhiều dead tuples; storage và query I/O tăng.

## 6. Failure scenario & troubleshooting

**Symptom** → table/index size tăng, query chậm dần. **Evidence** → old transaction + dead tuples. **Hypothesis** → MVCC cleanup bị giữ lại. **Diagnosis** → `pg_stat_activity`, table stats, vacuum logs. **Fix** → rút ngắn transaction; tune vacuum sau khi sửa root cause. **Verification** → transaction age giảm và dead tuple trend phục hồi.

## 7. Common mistakes

Chạy `VACUUM FULL` như phản xạ đầu tiên; transaction bao quanh network calls; hiểu MVCC là “không có lock”; bỏ qua connection ở trạng thái idle in transaction.

## 8. Alternatives

Pessimistic locking vẫn cần cho một số invariants. SQL Server cũng có row-versioning mechanisms nhưng implementation/cleanup semantics khác.

## 9. Trade-offs

### Advantages

Read/write concurrency tốt.

### Costs / Risks

Version storage, vacuum overhead và operational sensitivity với long transactions.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu update không đơn giản ghi đè bytes tại chỗ.

### Middle

Biết transaction scope ảnh hưởng database.

### Senior

Điều tra bloat/vacuum bằng evidence.

### Technical Lead / Architect

Thiết kế workflow không giữ transaction qua slow external boundaries.

## 11. Key takeaway

- MVCC đổi blocking lấy version-management cost.
- Long transaction là operational risk.
- Sửa transaction boundary trước khi chỉ tune vacuum.

# 5. Elasticsearch alias + reindex: thay mapping không downtime nhưng consistency vẫn là bài toán

## 1. What is it?

Index alias là tên logic trỏ tới một hoặc nhiều Elasticsearch indexes. Reindex strategy tạo index mới với mapping/settings mới, copy dữ liệu rồi atomically chuyển alias.

## 2. Why does it exist?

Nhiều mapping changes không thể áp dụng trực tiếp an toàn lên index hiện tại. Nếu Search API hard-code physical index name, migration buộc application downtime hoặc coupling deployment.

## 3. How does it work?

```text
Search API -> products-read -> products-v1

create products-v2
reindex v1 -> v2
sync changes during migration
switch alias:
products-read -> products-v2
```

Alias switch nhanh, nhưng dữ liệu thay đổi trong lúc reindex phải được xử lý.

## 4. Practical implementation

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v1", "alias": "products-read" }},
    { "add":    { "index": "products-v2", "alias": "products-read" }}
  ]
}
```

Migration runbook phải bao gồm catch-up strategy, validation và rollback alias.

## 5. Real production scenario

E-commerce cần analyzer mới cho product names. Team build `products-v2`, backfill từ source of truth, replay changes phát sinh trong migration, compare document counts/sample queries rồi switch alias.

## 6. Failure scenario & troubleshooting

**Symptom** → một số products mới biến mất sau alias switch. **Evidence** → chúng được tạo sau khi backfill bắt đầu nhưng trước cutover. **Hypothesis** → migration không capture delta. **Diagnosis** → compare primary DB change stream/outbox với index versions. **Fix** → dual-write/catch-up/replay có checkpoint. **Verification** → consistency reconciliation trước và sau switch.

## 7. Common mistakes

Coi reindex là chỉ copy dữ liệu; không có rollback; Search API gọi physical index; Elasticsearch trở thành source of truth; không version mappings.

## 8. Alternatives

In-place compatible changes khi Elasticsearch cho phép; recreate từ primary DB; blue/green search cluster cho migration lớn hơn.

## 9. Trade-offs

### Advantages

Mapping evolution với downtime thấp và rollback nhanh.

### Costs / Risks

Temporary storage gấp đôi, synchronization complexity và migration duration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu alias tách logical name khỏi physical index.

### Middle

Thực hiện reindex + alias switch.

### Senior

Thiết kế delta synchronization và validation.

### Technical Lead / Architect

Quyết định source of truth, recovery path và migration ownership.

## 11. Key takeaway

- Alias giải cutover, không tự giải consistency.
- Reindex cần delta/catch-up strategy.
- Primary database thường vẫn là source of truth.

# 6. Azure Service Bus lock renewal: message dài, duplicate delivery và idempotent consumer

## 1. What is it?

Ở Peek-Lock mode, consumer nhận message nhưng broker chưa xóa message. Consumer có lock trong một khoảng thời gian; sau khi xử lý thành công mới `Complete`.

## 2. Why does it exist?

Nếu broker xóa message ngay khi delivery rồi process crash, work bị mất. Lock cho phép message quay lại khi consumer không hoàn thành.

## 3. How does it work?

```text
receive -> lock acquired
process
  -> complete before lock expires -> removed
  -> crash/lock expires -> message available again
```

Long-running handler có thể cần auto lock renewal, nhưng renewal không tạo exactly-once semantics.

## 4. Practical implementation

```csharp
var processor = client.CreateProcessor(queueName, new ServiceBusProcessorOptions
{
    MaxConcurrentCalls = 8,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(10)
});

processor.ProcessMessageAsync += async args =>
{
    await handler.HandleAsync(args.Message, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message);
};
```

Handler vẫn phải idempotent theo business operation/message ID.

## 5. Real production scenario

Document conversion mất 4–8 phút. Default lock hết giữa processing, message được consumer khác nhận. Hai workers cùng tạo output. Auto-renew giảm premature redelivery; idempotency bảo vệ duplicate vẫn có thể xảy ra.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate processing và `MessageLockLostException`. **Evidence** → handler duration vượt lock/renewal hoặc CPU starvation làm renewal trễ. **Hypothesis** → processing vượt lock assumptions. **Diagnosis** → duration metrics + delivery count + lock-lost logs. **Fix** → renewal, giảm handler duration, checkpoint workflow hoặc tách job. **Verification** → slow/failure injection.

## 7. Common mistakes

Tin lock = exactly once; complete trước side effect; concurrency quá cao; retry poison message vô hạn; không monitor DLQ/delivery count.

## 8. Alternatives

Queue chỉ chứa job pointer và durable worker workflow; Azure Functions trigger phù hợp workload đơn giản; orchestration engine phù hợp long-running stateful process.

## 9. Trade-offs

### Advantages

At-least-once delivery bảo vệ work khỏi consumer crash.

### Costs / Risks

Duplicate handling, lock lifecycle, retry/DLQ complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu receive khác complete.

### Middle

Configure processor, concurrency, DLQ.

### Senior

Thiết kế idempotency và lock-failure behavior.

### Technical Lead / Architect

Quyết định khi message handler đã quá dài để còn là một queue operation đơn giản.

## 11. Key takeaway

- Lock renewal không tạo exactly-once.
- Handler phải chịu được redelivery.
- Long-running work cần explicit workflow design.

# 7. OAuth 2.0 / OIDC token validation: issuer, audience, signing key và clock skew

## 1. What is it?

API không nên chỉ decode JWT; nó phải **validate** token theo trust contract: signature, issuer, audience, lifetime và các policy-specific claims.

## 2. Why does it exist?

JWT là format, không phải bằng chứng tự thân. Token có signature hợp lệ từ đúng identity provider nhưng dành cho API khác vẫn không nên được chấp nhận.

## 3. How does it work?

```text
Bearer token
 -> parse header/claims
 -> obtain trusted signing keys
 -> validate signature
 -> validate iss
 -> validate aud
 -> validate exp/nbf
 -> authorization policies
```

OIDC discovery/JWKS giúp key rotation mà application không hard-code một signing key vĩnh viễn.

## 4. Practical implementation

```csharp
builder.Services.AddAuthentication("Bearer")
    .AddJwtBearer("Bearer", options =>
    {
        options.Authority = configuration["Auth:Authority"];
        options.Audience = "orders-api";
        options.TokenValidationParameters.ClockSkew =
            TimeSpan.FromMinutes(1);
    });
```

Authorization vẫn phải kiểm tra scopes/roles/policies phù hợp endpoint.

## 5. Real production scenario

Token login thành công ở frontend nhưng Production API trả 401. Signature đúng; `aud` lại là Graph/API khác do frontend request sai scope/resource. Local environment vô tình tắt audience validation nên bug chỉ lộ ở Production.

## 6. Failure scenario & troubleshooting

**Symptom** → 401 sau identity-provider key rotation. **Evidence** → unknown `kid`, discovery/JWKS fetch errors. **Hypothesis** → stale metadata/network restriction. **Diagnosis** → inspect token header, authority metadata, outbound connectivity. **Fix** → restore discovery/key refresh path; không bypass signature validation. **Verification** → token signed bằng active key validate thành công.

## 7. Common mistakes

Decode token rồi tin claims; tắt issuer/audience validation; log raw access token; dùng ID token để gọi API; clock skew quá lớn; authorization chỉ kiểm tra “authenticated”.

## 8. Alternatives

Opaque/reference tokens + introspection phù hợp một số architectures. Cookie auth phù hợp server-rendered web apps.

## 9. Trade-offs

### Advantages

Self-contained JWT validation giảm per-request dependency vào identity provider.

### Costs / Risks

Key rotation, revocation semantics, claim design và token leakage risk.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt authentication và authorization.

### Middle

Configure issuer/audience/scope đúng.

### Senior

Debug key rotation, clock, multi-tenant issuer và token-type confusion.

### Technical Lead / Architect

Thiết kế trust boundaries và token audiences thay vì dùng một token cho mọi service.

## 11. Key takeaway

- Decode không phải validate.
- Signature đúng chưa đủ; issuer/audience/lifetime cũng phải đúng.
- Authorization là bước riêng sau authentication.

# 8. Canary deployment + database compatibility: nhiều application versions phải cùng sống với một schema

## 1. What is it?

Canary deployment đưa version mới tới một phần nhỏ traffic trước khi rollout toàn bộ. Với database dùng chung, mental model quan trọng là **old app và new app có thể chạy đồng thời**.

## 2. Why does it exist?

Canary giảm blast radius của code regression. Nhưng migration phá backward compatibility có thể làm old instances fail ngay cả khi chỉ 5% traffic đi tới new version.

## 3. How does it work?

Dùng expand-and-contract:

```text
1. Expand schema: additive, compatible
2. Deploy app version that understands old + new
3. Backfill/migrate data
4. Move traffic / complete rollout
5. Contract old schema only after old app is gone
```

## 4. Practical implementation

Thay vì rename column trực tiếp:

```sql
ALTER TABLE Customer ADD DisplayName nvarchar(200) NULL;
```

Deploy code đọc fallback từ old field, backfill, chuyển writes, rồi ở release sau mới remove old column.

## 5. Real production scenario

Checkout v2 canary 10% traffic. Migration đổi tên `Total` thành `GrandTotal` bằng destructive rename. 90% pods v1 vẫn query `Total` và fail. Canary code healthy nhưng shared schema đã phá fleet.

## 6. Failure scenario & troubleshooting

**Symptom** → old pods bắt đầu 500 ngay khi migration chạy. **Evidence** → SQL invalid-column errors trước khi traffic shift hoàn tất. **Hypothesis** → schema migration không backward compatible. **Diagnosis** → compare app versions và migration timeline. **Fix** → rollback/compatibility layer; áp dụng expand-contract. **Verification** → chạy integration tests của N và N-1 trên migrated schema.

## 7. Common mistakes

Migration destructive cùng release; rollback application nhưng database không rollback được; feature flag chỉ ở code trong khi schema đã thay; không test mixed-version fleet.

## 8. Alternatives

Blue-green với database riêng tăng isolation nhưng data synchronization/cutover phức tạp. Maintenance window đơn giản hơn nếu business chấp nhận downtime.

## 9. Trade-offs

### Advantages

Canary giảm deployment risk và cung cấp production evidence sớm.

### Costs / Risks

Mixed-version compatibility, telemetry segmentation và migration choreography phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deployment không phải instant switch.

### Middle

Viết additive migration.

### Senior

Thiết kế N/N-1 compatibility và rollback path.

### Technical Lead / Architect

Quyết định release strategy dựa trên SLO, data migration risk và team operational maturity.

## 11. Key takeaway

- Canary application nhưng shared database vẫn là shared blast radius.
- Expand-contract là kỹ thuật compatibility, không chỉ migration style.
- Rollback phải được thiết kế trước deployment.

# 9. IIS Application Pool recycling: process lifecycle, in-memory state và graceful shutdown

## 1. What is it?

IIS Application Pool quản lý worker process `w3wp.exe` cho hosted application. Recycling thay worker process theo configuration/health/lifecycle conditions.

## 2. Why does it exist?

Process cần isolation và lifecycle management. Recycling có thể giúp operational maintenance, nhưng application không được giả định worker sống vĩnh viễn.

## 3. How does it work?

```text
IIS
 -> App Pool
    -> w3wp old
       -> shutdown/drain
    -> w3wp new
       -> application startup
```

Overlapped recycle có thể có old/new workers cùng tồn tại ngắn hạn.

## 4. Practical implementation

Background work trong ASP.NET application phải lắng nghe shutdown:

```csharp
public sealed class CleanupWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await RunBatchAsync(stoppingToken);
            await Task.Delay(TimeSpan.FromMinutes(1), stoppingToken);
        }
    }
}
```

Critical durable work không nên chỉ tồn tại trong process memory.

## 5. Real production scenario

Legacy ASP.NET/.NET application giữ session/job queue trong memory. Nightly recycle làm queue biến mất hoặc job chạy lại trên process mới. Root cause không phải “IIS random restart” mà là state ownership sai.

## 6. Failure scenario & troubleshooting

**Symptom** → application “restart” định kỳ, cache cold, background job duplicate. **Evidence** → IIS recycle events/process IDs đổi. **Hypothesis** → configured recycle hoặc health action. **Diagnosis** → Event Viewer, IIS/App Pool settings, application startup logs. **Fix** → hiểu trigger, externalize durable state, graceful cancellation. **Verification** → controlled recycle dưới traffic.

## 7. Common mistakes

Lưu durable state trong static dictionary; scheduled job chạy trong mỗi worker; disable recycle để che memory leak; không log startup/shutdown; assume single process.

## 8. Alternatives

Windows Service/Worker Service cho durable background processing; containers/App Service có lifecycle khác nhưng cùng nguyên tắc: process có thể bị thay thế.

## 9. Trade-offs

### Advantages

Process isolation và lifecycle control phù hợp enterprise hosting.

### Costs / Risks

Legacy configuration complexity và hidden assumptions về process lifetime.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu web app process có thể restart.

### Middle

Đọc IIS logs/events và viết shutdown-aware code.

### Senior

Tách durable state/work khỏi web process.

### Technical Lead / Architect

Quyết định modernization/hosting boundary và loại workload nào không nên sống trong IIS web worker.

## 11. Key takeaway

- Process lifetime không phải application data lifetime.
- Recycling phải là expected lifecycle event.
- Durable work/state cần external ownership.

# 10. RAG retrieval quality: chunking, embeddings, reranking và evaluation trước khi đổi model

## 1. What is it?

Retrieval-Augmented Generation (RAG) đưa external knowledge vào model context bằng retrieval. Mental model: answer quality bị giới hạn bởi **khả năng tìm đúng evidence**, không chỉ bởi model generation.

## 2. Why does it exist?

LLM không tự biết private/current enterprise data. Nhét toàn bộ corpus vào prompt quá đắt hoặc vượt context. Retrieval chọn một tập nhỏ relevant documents/chunks.

## 3. How does it work?

```text
User question
 -> query normalization
 -> embedding / lexical retrieval
 -> candidate chunks
 -> optional reranking
 -> selected context
 -> LLM
 -> answer + citations
```

Chunking quyết định retrieval unit; embedding quyết định semantic similarity; reranker có thể cải thiện ordering của candidate set.

## 4. Practical implementation

Một service nên giữ deterministic boundaries rõ:

```csharp
var candidates = await search.RetrieveAsync(query, topK: 30, ct);
var ranked = await reranker.RankAsync(query, candidates, ct);
var context = ranked.Take(6).ToArray();

var answer = await llm.AnswerAsync(
    query,
    context,
    ct);
```

Authorization filtering phải xảy ra trước khi context nhạy cảm được gửi tới model.

## 5. Real production scenario

Internal engineering assistant trả lời sai policy dù dùng model mạnh. Evaluation cho thấy relevant policy document chỉ xuất hiện rank 18; generator chưa bao giờ nhìn thấy evidence đúng. Tăng model size không sửa retrieval recall. Hybrid retrieval + reranking cải thiện grounded-answer rate.

## 6. Failure scenario & troubleshooting

**Symptom** → fluent answer nhưng sai tài liệu. **Evidence** → retrieved chunks không chứa supporting fact. **Hypothesis** → retrieval failure, không phải generation failure. **Diagnosis** → tách metrics: retrieval recall@K, reranker quality, groundedness, answer correctness. **Fix** → chunking/metadata/hybrid search/reranking. **Verification** → chạy fixed evaluation set trước/sau.

## 7. Common mistakes

Đổi prompt/model trước khi inspect retrieved context; chunks quá lớn hoặc mất semantic boundary; vector search cho exact identifiers; không filter authorization; không version corpus/index; không có evaluation dataset.

## 8. Alternatives

Full-text/BM25 đủ tốt cho exact search. Fine-tuning phù hợp behavior/style hoặc learned task patterns, không phải cách mặc định để cập nhật factual corpus. Tool/API lookup tốt hơn RAG cho deterministic live data.

## 9. Trade-offs

### Advantages

Knowledge cập nhật độc lập model, có thể cung cấp evidence/citations.

### Costs / Risks

Retrieval infrastructure, indexing freshness, latency, token cost, security filtering và evaluation complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu model chỉ trả lời từ context mà pipeline cung cấp.

### Middle

Build chunk/index/retrieve/prompt pipeline và log retrieval evidence.

### Senior

Đo retrieval vs generation failures, tune hybrid retrieval/reranking và security boundaries.

### Technical Lead / Architect

Quyết định phần nào dùng RAG, phần nào phải là deterministic API/tool call, ai sở hữu corpus freshness và evaluation SLO.

## 11. Key takeaway

- RAG quality bắt đầu từ retrieval quality.
- Đánh giá retrieval và generation riêng.
- Live/critical deterministic data thường nên đi qua API/tool thay vì semantic retrieval.
