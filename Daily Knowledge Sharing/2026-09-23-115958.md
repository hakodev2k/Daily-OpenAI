# 1. C# `Channel<T>`: bounded producer-consumer pipelines và backpressure

## 1. What is it?

`System.Threading.Channels` cung cấp asynchronous queue cho producer-consumer workloads trong cùng process. Mental model quan trọng không phải “queue nhanh”, mà là **boundary giữa tốc độ sản xuất và tốc độ tiêu thụ**. Với bounded channel, hệ thống có thể tạo backpressure thay vì cho memory tăng vô hạn.

## 2. Why does it exist?

Nếu HTTP request tạo work nhanh hơn background worker xử lý, `ConcurrentQueue<T>` không tự đặt capacity. Traffic burst có thể biến thành hàng trăm nghìn objects nằm trong RAM. `Channel<T>` cho phép writer chờ khi buffer đầy, drop theo policy hoặc reject work có chủ đích.

## 3. How does it work?

```text
Producer(s) -> Channel buffer [bounded N] -> Consumer(s)
                    |
                    +-- full -> Wait / Drop / Reject policy
```

Writer và reader dùng async APIs nên không cần block thread trong lúc chờ capacity/data.

## 4. Practical implementation

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = false
});

await channel.Writer.WriteAsync(job, cancellationToken);

await foreach (var item in channel.Reader.ReadAllAsync(stoppingToken))
{
    await processor.ProcessAsync(item, stoppingToken);
}
```

Capacity phải dựa trên memory budget, processing rate và acceptable queueing delay.

## 5. Real production scenario

API nhận webhook nhanh hơn worker ghi xuống downstream. Unbounded queue chạy ổn ở traffic bình thường nhưng memory tăng mạnh khi downstream chậm 10 phút. Bounded channel biến overload thành explicit waiting/rejection thay vì OOM ngẫu nhiên.

## 6. Failure scenario & troubleshooting

**Symptom** → request latency tăng khi queue đầy. **Evidence** → queue depth chạm capacity, consumer throughput giảm. **Hypothesis** → downstream bottleneck chứ không phải Channel chậm. **Diagnosis** → đo enqueue wait time, depth, dequeue rate và processing duration. **Fix** → tăng consumer capacity nếu dependency chịu được, giảm producer rate hoặc chuyển durable work sang broker. **Verification** → overload test dài hơn burst window.

## 7. Common mistakes

Dùng unbounded channel cho unbounded traffic; tăng consumer count đến mức database pool cạn; không complete writer khi shutdown; nhầm in-memory queue với durable messaging; bỏ cancellation.

## 8. Alternatives

`BlockingCollection<T>` phù hợp synchronous pipeline cũ. Azure Service Bus/RabbitMQ/Kafka phù hợp khi cần durability, cross-process delivery hoặc replay.

## 9. Trade-offs

Channel có overhead thấp và async-native nhưng mất dữ liệu khi process chết nếu work chưa được persist.

## 10. Junior → Middle → Senior → Technical Lead

Junior hiểu producer/consumer; Middle dùng bounded channel; Senior thiết kế backpressure/shutdown; Lead quyết định khi nào workload phải rời process sang durable broker.

## 11. Key takeaway

- Queue capacity là một phần của reliability design.
- Backpressure tốt hơn memory growth vô hạn.
- In-memory queue không thay durable broker.

# 2. ASP.NET Core request timeout: thiết kế timeout budget xuyên call chain

## 1. What is it?

Request timeout là giới hạn thời gian một request được phép tiêu thụ trước khi hệ thống hủy work hoặc trả timeout. Nó khác với `HttpClient.Timeout`: request budget là end-to-end; dependency timeout chỉ áp dụng cho một outbound operation.

## 2. Why does it exist?

Nếu ingress cho phép 5 giây nhưng service gọi ba dependencies mỗi cái timeout 10 giây, request có thể tiếp tục tiêu tốn connection/thread/database work sau khi caller đã bỏ cuộc. Timeout budget cần truyền xuống dưới qua cancellation.

## 3. How does it work?

```text
Client budget 5s
 API processing 0.2s
 DB budget <= remaining
 HTTP dependency <= remaining
 cleanup <= remaining policy
```

Cancellation là signal hợp tác; nó không tự động dừng code nếu dependency không observe token.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:long}", async (
    long id,
    OrderService service,
    CancellationToken requestAborted) =>
{
    var order = await service.GetAsync(id, requestAborted);
    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

Service/repository/outbound SDK tiếp tục nhận cùng token hoặc linked token có deadline ngắn hơn theo dependency budget.

## 5. Real production scenario

Mobile gateway timeout ở 8 giây nhưng backend SQL command timeout 30 giây. Khi database degrade, clients retry sau 8 giây trong khi query cũ vẫn chạy, làm load nhân lên. Propagated cancellation + bounded retry giảm wasted work.

## 6. Failure scenario & troubleshooting

**Symptom** → client thấy timeout nhưng server CPU/DB sessions tiếp tục tăng. **Evidence** → traces kéo dài sau client disconnect. **Hypothesis** → cancellation không propagate. **Diagnosis** → inspect request-aborted token xuyên call graph. **Fix** → truyền token, đặt dependency timeout nhỏ hơn remaining budget, giới hạn retry. **Verification** → intentionally disconnect/timeout và quan sát downstream work kết thúc.

## 7. Common mistakes

Catch `OperationCanceledException` rồi retry; mọi dependency cùng timeout bằng request timeout; retry 3 lần mỗi lần full timeout; coi cancellation là lỗi 500; dùng `CancellationToken.None` trong repository.

## 8. Alternatives

Long-running work nên chuyển sang asynchronous job + polling/callback thay vì kéo HTTP request vô hạn.

## 9. Trade-offs

Timeout ngắn bảo vệ capacity nhưng có thể cắt legitimate slow operations; timeout dài tăng completion chance nhưng làm overload recovery khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

Junior truyền token; Middle phân biệt timeout/cancellation; Senior thiết kế deadline + retry budget; Lead đặt SLO và latency budget xuyên services.

## 11. Key takeaway

- Timeout phải được budget end-to-end.
- Cancellation chỉ hiệu quả khi propagate.
- Retry phải nằm bên trong tổng latency budget.

# 3. EF Core compiled queries: tối ưu đúng bottleneck

## 1. What is it?

EF Core phải xử lý LINQ expression thành executable query pipeline trước khi database thực thi. EF đã cache query compilation theo shape; compiled query cho phép application tạo delegate đã compile trước để giảm một phần overhead ở hot paths.

## 2. Why does it exist?

Với query cực kỳ thường xuyên và database operation rất nhanh, client-side query preparation có thể trở thành phần đáng kể của latency/CPU. Nhưng nếu SQL mất 100 ms, tiết kiệm microseconds ở compilation thường không đáng kể.

## 3. How does it work?

```text
normal LINQ -> expression processing/cache lookup -> SQL -> DB
compiled delegate -------------------------------> SQL -> DB
```

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, long, Task<Order?>> GetOrder =
    EF.CompileAsyncQuery((AppDbContext db, long id) =>
        db.Orders.AsNoTracking().FirstOrDefault(x => x.Id == id));

var order = await GetOrder(db, orderId);
```

Chỉ áp dụng sau benchmark representative workload.

## 5. Real production scenario

Lookup endpoint chạy hàng chục nghìn lần/giây, query PK rất nhanh và CPU application đáng kể. Profiling cho thấy query pipeline overhead measurable. Compiled query có ích. Với reporting query 800 ms, nó gần như không thay đổi outcome.

## 6. Failure scenario & troubleshooting

**Symptom** → thêm compiled queries nhưng p95 không đổi. **Evidence** → database duration chiếm gần toàn latency. **Hypothesis** → tối ưu sai layer. **Diagnosis** → split app CPU, network và DB duration. **Fix** → tập trung execution plan/index/data shape. **Verification** → benchmark trước/sau.

## 7. Common mistakes

Compile mọi query; tạo dynamic shape khó reuse; bỏ qua allocations/materialization; dùng compiled query để che N+1 hoặc thiếu index.

## 8. Alternatives

Projection, `AsNoTracking`, index tuning, raw SQL/Dapper cho specialized path thường có impact lớn hơn tùy bottleneck.

## 9. Trade-offs

Giảm overhead nhưng tăng static code/maintenance và giảm flexibility cho dynamic query composition.

## 10. Junior → Middle → Senior → Technical Lead

Junior hiểu LINQ-to-SQL; Middle benchmark query; Senior profile client vs DB cost; Lead tránh micro-optimization không có production evidence.

## 11. Key takeaway

- EF đã cache query shape; compiled query là optimization chuyên biệt.
- Chỉ dùng khi compilation overhead thực sự measurable.
- Tối ưu layer chiếm latency lớn nhất trước.

# 4. SQL Server covering index: giảm lookup có chủ đích

## 1. What is it?

Covering index là index chứa đủ columns để query được phục vụ mà không cần quay lại clustered index/heap lấy thêm dữ liệu. Key columns hỗ trợ seek/order; `INCLUDE` columns có thể cung cấp payload ở leaf level.

## 2. Why does it exist?

Một nonclustered index có thể tìm đúng 100.000 rows rất nhanh nhưng sau đó thực hiện 100.000 key lookups để lấy columns còn thiếu. Với cardinality lớn, lookup cost có thể thống trị query.

## 3. How does it work?

```sql
CREATE INDEX IX_Orders_Customer_CreatedAt
ON dbo.Orders(CustomerId, CreatedAt DESC)
INCLUDE (Status, Total);
```

Query filter/order theo key và select `Status, Total` có thể được cover.

## 4. Practical implementation

Đọc actual execution plan và logical reads. Chỉ thêm columns query thực sự cần; kiểm tra write workload vì mỗi INSERT/UPDATE phải maintain index.

## 5. Real production scenario

Order history query seek đúng customer nhưng 20k key lookups làm logical reads tăng mạnh. Thêm hai projected columns vào `INCLUDE` loại lookup và giảm I/O. Thêm toàn bộ entity vào index sẽ lại làm index quá rộng.

## 6. Failure scenario & troubleshooting

**Symptom** → reads giảm cho SELECT nhưng write latency tăng. **Evidence** → index size và maintenance/write cost tăng. **Hypothesis** → over-indexing. **Diagnosis** → usage stats + write workload. **Fix** → thu hẹp/drop redundant indexes. **Verification** → benchmark read và write, không chỉ query mục tiêu.

## 7. Common mistakes

Copy mọi SELECT column vào INCLUDE; duplicate gần-identical indexes; bỏ qua filtered index; tin missing-index suggestion tuyệt đối; không xét update frequency.

## 8. Alternatives

Projection nhỏ hơn, filtered index, clustered-key redesign hoặc materialized/read model tùy access pattern.

## 9. Trade-offs

Đổi storage + write amplification lấy read efficiency.

## 10. Junior → Middle → Senior → Technical Lead

Junior hiểu seek/scan; Middle đọc lookup; Senior cân read/write cost; Lead quản trị index portfolio theo workload.

## 11. Key takeaway

- Cover query, đừng cover table.
- `INCLUDE` vẫn có storage/write cost.
- Đo logical reads và write impact.

# 5. MongoDB compound index: Equality → Sort → Range

## 1. What is it?

Compound index chứa nhiều fields theo thứ tự xác định. Thứ tự fields quyết định query shapes nào có thể dùng index hiệu quả. Heuristic ESR — Equality, Sort, Range — là điểm khởi đầu hữu ích, không phải luật tuyệt đối.

## 2. Why does it exist?

Index `{ tenantId: 1, createdAt: -1, total: 1 }` có behavior khác `{ createdAt: -1, tenantId: 1, total: 1 }`. Query multi-tenant thường cần thu hẹp tenant trước khi sort/range.

## 3. How does it work?

```javascript
db.orders.createIndex({ tenantId: 1, createdAt: -1, _id: -1 })
```

Query equality `tenantId`, sort `createdAt/_id` có thể traverse contiguous index range mà không in-memory sort.

## 4. Practical implementation

```javascript
db.orders.find({ tenantId: tenant, createdAt: { $lt: cursor } })
  .sort({ createdAt: -1, _id: -1 })
  .limit(50)
  .explain("executionStats")
```

Quan sát `totalKeysExamined`, `totalDocsExamined`, returned count và stage tree.

## 5. Real production scenario

Audit collection hàng trăm triệu documents. Index chỉ trên `createdAt` khiến query tenant phải scan lượng lớn keys rồi filter. Compound index bắt đầu bằng tenant giảm search space đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → query dùng index nhưng vẫn chậm. **Evidence** → keys examined lớn hơn returned rows nhiều lần. **Hypothesis** → index order không phù hợp selectivity/query shape. **Diagnosis** → `explain("executionStats")`. **Fix** → redesign index theo workload. **Verification** → test nhiều tenant cardinalities.

## 7. Common mistakes

Một index cho mọi query; thêm index cho từng field; bỏ qua sort direction/compound sort semantics; không xét write amplification; dùng ESR máy móc khi range cực selective.

## 8. Alternatives

Partial indexes, specialized collections/read models, Atlas Search cho full-text/search workload.

## 9. Trade-offs

Compound indexes tăng read efficiency nhưng tiêu storage/RAM và làm writes đắt hơn.

## 10. Junior → Middle → Senior → Technical Lead

Junior hiểu index; Middle đọc explain; Senior thiết kế theo cardinality; Lead quản lý query/index contract theo workload growth.

## 11. Key takeaway

- Index field order là access-path design.
- ESR là heuristic, execution stats mới là evidence.
- Test data distribution thực tế.

# 6. Distributed lock: lease và fencing token

## 1. What is it?

Distributed lock cố tạo mutual exclusion giữa nhiều processes/nodes. Nhưng trong distributed systems, “tôi đang giữ lock” có thể trở nên sai nếu process pause, network partition hoặc lease hết hạn. Fencing token là monotonically increasing token giúp resource từ chối stale owner.

## 2. Why does it exist?

Worker A lấy lease 10s rồi GC pause 15s. Lease hết hạn, B lấy lock và ghi. A tỉnh lại, nếu downstream không phân biệt stale owner, A vẫn có thể ghi đè B.

## 3. How does it work?

```text
A gets token 41 -> pauses
lease expires
B gets token 42 -> resource accepts 42
A resumes token 41 -> resource rejects 41 (<42)
```

Mutual exclusion ở lock service chưa đủ nếu protected resource không enforce ownership freshness.

## 4. Practical implementation

Với correctness-critical work, thiết kế version/fencing ở database/resource boundary. Lock cần unique owner value, bounded lease, safe release chỉ bởi owner và failure semantics rõ.

## 5. Real production scenario

Hai schedulers cùng generate invoice batch. Simple Redis `SET NX EX` giảm collision nhưng process pause làm lease expire giữa operation. Database-level unique constraint/idempotency + fencing/version mới bảo vệ invariant cuối cùng.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate side effects dù logs cho thấy lock. **Evidence** → operation kéo dài hơn lease hoặc connectivity pause. **Hypothesis** → stale owner tiếp tục work. **Diagnosis** → correlate lease/token/resource writes. **Fix** → fencing/idempotency/DB invariant. **Verification** → inject pauses dài hơn lease.

## 7. Common mistakes

Release lock bằng `DEL` không check owner; lease không có renewal policy; lock là protection duy nhất cho money/inventory invariant; giả định clock/network hoàn hảo.

## 8. Alternatives

Database uniqueness/transaction, single-writer partition, queue serialization, optimistic concurrency thường đơn giản và mạnh hơn tùy problem.

## 9. Trade-offs

Distributed lock thêm coordination latency và failure modes; fencing tăng correctness nhưng protected resource phải hỗ trợ ordering/version check.

## 10. Junior → Middle → Senior → Technical Lead

Junior hiểu race condition; Middle implement owner-safe lease; Senior reason về pause/partition/fencing; Lead ưu tiên invariant ở authoritative store trước lock convenience.

## 11. Key takeaway

- Lease có thể hết khi owner vẫn chạy.
- Stale owner là failure mode cốt lõi.
- Critical correctness cần protection tại resource/invariant boundary.

# 7. Azure Key Vault secret rotation: secret lifecycle độc lập deployment

## 1. What is it?

Key Vault quản lý secret/key/certificate versions tách khỏi application binaries. Rotation là quá trình tạo version mới, chuyển consumers sang version đó và retire version cũ có kiểm soát.

## 2. Why does it exist?

Secret hard-code trong config/image buộc rotation đi cùng deployment và tăng blast radius khi credential lộ. Managed identity + vault giảm nhu cầu phân phối long-lived credentials.

## 3. How does it work?

```text
App identity -> Entra auth -> Key Vault authorization -> secret version
                                       |
                                audit/access policy
```

Ứng dụng có thể reference current version hoặc pinned version tùy rollout requirement.

## 4. Practical implementation

Ưu tiên `DefaultAzureCredential`/managed identity trên Azure. Cache secret hợp lý thay vì gọi vault mỗi request. Thiết kế refresh khi version thay đổi và giữ overlap window nếu downstream credential hỗ trợ dual keys.

## 5. Real production scenario

Database password phải rotate khẩn cấp. Nếu mọi pod giữ secret từ startup và chỉ refresh khi redeploy, rollout kéo dài tạo mixed credentials. Dual credential window + controlled refresh cho phép chuyển dần và rollback.

## 6. Failure scenario & troubleshooting

**Symptom** → một số replicas auth fail sau rotation. **Evidence** → pods dùng secret versions khác nhau. **Hypothesis** → stale cache/startup-only loading. **Diagnosis** → correlate secret version với instance. **Fix** → rotation-aware refresh/overlap. **Verification** → rehearsal rotation không downtime.

## 7. Common mistakes

Vault lookup mỗi request; log secret value; cấp app quyền quá rộng; xóa old version ngay; không có break-glass/rotation runbook.

## 8. Alternatives

Managed identity loại bỏ secret cho nhiều Azure services; workload identity/certificate auth phù hợp các trust models khác.

## 9. Trade-offs

Central vault cải thiện governance nhưng tạo dependency cần caching, retry và access design.

## 10. Junior → Middle → Senior → Technical Lead

Junior không hard-code secret; Middle dùng managed identity; Senior thiết kế rotation/cache; Lead định nghĩa credential lifecycle và least privilege.

## 11. Key takeaway

- Secret storage và secret rotation là hai bài toán khác nhau.
- Rotation phải được rehearsal.
- Loại bỏ secret bằng workload identity tốt hơn chỉ quản lý secret tốt hơn khi khả thi.

# 8. Kubernetes resource requests/limits: scheduling, throttling và OOMKill

## 1. What is it?

`requests` mô tả resource scheduler dùng để đặt Pod và ảnh hưởng QoS; `limits` đặt upper boundary cho resource usage theo cơ chế runtime/cgroup. CPU và memory phản ứng khác nhau khi chạm limit.

## 2. Why does it exist?

Không khai báo resource làm scheduling/capacity planning mù. Nhưng đặt limit sai cũng gây throttling hoặc OOMKill dù node còn tài nguyên ở một số tình huống.

## 3. How does it work?

```text
CPU request -> scheduler capacity accounting
CPU limit   -> throttling khi vượt quota
Memory request -> scheduling
Memory limit   -> vượt giới hạn có thể OOMKill container
```

## 4. Practical implementation

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
```

Giá trị phải dựa trên production percentiles, startup behavior và workload class.

## 5. Real production scenario

.NET API có CPU limit quá thấp. CPU node chỉ 50% nhưng container bị throttled ở peak, p99 tăng. Team scale replicas nhưng mỗi pod vẫn bị quota. Metrics `container_cpu_cfs_throttled_*` chỉ ra vấn đề.

## 6. Failure scenario & troubleshooting

**Symptom** → pod restart với `OOMKilled`. **Evidence** → working set chạm memory limit. **Hypothesis** → leak, burst hoặc limit quá thấp. **Diagnosis** → heap/runtime/container memory metrics. **Fix** → sửa allocation/leak hoặc right-size memory. **Verification** → sustained load + restart count.

## 7. Common mistakes

Request=limit cho mọi workload mà không hiểu QoS; CPU limit quá thấp cho latency-sensitive service; nhìn node CPU thay container throttling; tăng memory limit thay vì điều tra leak.

## 8. Alternatives

VPA recommendations, HPA theo suitable metrics và workload isolation hỗ trợ right-sizing nhưng không thay measurement.

## 9. Trade-offs

Requests cao tăng reserved capacity/cost; requests thấp tăng contention risk; limits bảo vệ neighbors nhưng có thể bóp workload.

## 10. Junior → Middle → Senior → Technical Lead

Junior hiểu CPU/memory units; Middle đọc pod metrics; Senior phân tích throttling/OOM; Lead xây capacity/right-sizing policy theo SLO.

## 11. Key takeaway

- Requests và limits giải quyết khác nhau.
- CPU throttling khác memory OOM.
- Right-sizing cần production evidence.

# 9. OpenTelemetry sampling: giữ tín hiệu, giảm cost

## 1. What is it?

Sampling quyết định trace/span nào được record/export để kiểm soát telemetry volume. Head sampling quyết định sớm khi trace bắt đầu; tail sampling có thể quyết định sau khi đã thấy nhiều thông tin của trace.

## 2. Why does it exist?

100% tracing ở traffic lớn có thể tốn storage/network đáng kể. Nhưng random 1% sampling có thể bỏ mất rare 500s hoặc high-latency traces mà ta cần nhất.

## 3. How does it work?

```text
Head sampling: request start -> decide keep/drop
Tail sampling: collect trace -> evaluate error/latency/attributes -> keep/drop
```

Tail sampling cần collector buffering/state và đủ capacity.

## 4. Practical implementation

Giữ sampling policy đơn giản: baseline probabilistic sample + ưu tiên errors/high latency ở collector nếu architecture hỗ trợ. Propagate sampling decision nhất quán xuyên trace.

## 5. Real production scenario

Service 20k RPS export 100% traces làm observability bill tăng mạnh. Giảm random xuống 1% tiết kiệm cost nhưng incident rare timeout không có trace. Tail policy giữ errors và >2s traces, sample phần healthy traffic.

## 6. Failure scenario & troubleshooting

**Symptom** → metrics báo 500 nhưng trace search không thấy failures. **Evidence** → sampling policy drop trước khi biết response status. **Hypothesis** → head sample quá aggressive. **Diagnosis** → inspect sampler/export pipeline. **Fix** → tail/error-aware policy hoặc tăng baseline theo budget. **Verification** → synthetic failures và confirm trace retention.

## 7. Common mistakes

Sampling metrics như traces; inconsistent decisions giữa services; tail sampler thiếu memory; high-cardinality rules; coi sampled trace volume là traffic volume tuyệt đối.

## 8. Alternatives

Exemplars nối metrics với sampled traces; structured logs giữ selected events; adaptive sampling tùy platform.

## 9. Trade-offs

Ít telemetry giảm cost nhưng giảm forensic detail; tail sampling giữ valuable traces nhưng tăng collector complexity.

## 10. Junior → Middle → Senior → Technical Lead

Junior hiểu sampling; Middle cấu hình probabilistic; Senior thiết kế error/latency retention; Lead đặt telemetry budget và evidence requirements.

## 11. Key takeaway

- Sampling là information-budget decision.
- Rare failures cần policy khác healthy traffic.
- Metrics và traces bổ sung nhau.

# 10. API idempotency key: retry an toàn cho side-effecting request

## 1. What is it?

Idempotency key là client-generated identifier cho một logical operation. Server lưu kết quả/trạng thái theo key để request retry không tạo side effect lần hai.

## 2. Why does it exist?

Client gửi `POST /payments`; server charge thành công nhưng response mất do network. Client không biết operation thành công hay chưa và retry. Nếu server coi retry là request mới, customer có thể bị charge hai lần.

## 3. How does it work?

```text
POST key=abc
 -> atomically claim abc
 -> execute operation
 -> store outcome
retry key=abc
 -> return/reconcile stored outcome
```

Key phải gắn với request fingerprint/operation scope để cùng key nhưng payload khác bị reject.

## 4. Practical implementation

Persistence cần atomic uniqueness:

```sql
CREATE UNIQUE INDEX UX_Idempotency_Tenant_Key
ON ApiIdempotency(TenantId, IdempotencyKey);
```

Record nên có status, request hash, result reference và expiry policy. Business write + idempotency record cần transaction strategy phù hợp.

## 5. Real production scenario

Order creation API timeout sau khi commit. Mobile app retry ba lần. Idempotency key làm cả bốn attempts quy về cùng OrderId thay vì tạo bốn orders.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate operation vẫn xảy ra. **Evidence** → check-then-insert idempotency record không atomic, hai requests concurrent cùng thấy key absent. **Hypothesis** → race ở claim. **Diagnosis** → concurrent test + DB constraints. **Fix** → unique constraint/transactional claim. **Verification** → fire nhiều identical requests đồng thời và kiểm tra đúng một side effect.

## 7. Common mistakes

Chỉ cache response in-memory; không bind key với tenant/payload; TTL ngắn hơn retry window; lưu success nhưng không xử lý in-progress/failed ambiguity; tin HTTP retry library tự tạo idempotency.

## 8. Alternatives

Natural idempotency bằng business identifier/unique constraint; PUT semantics khi resource ID do client xác định; message deduplication ở broker cho asynchronous flows.

## 9. Trade-offs

Tăng persistence/state cleanup nhưng đổi network ambiguity thành deterministic API behavior.

## 10. Junior → Middle → Senior → Technical Lead

Junior hiểu duplicate retry; Middle implement unique key; Senior xử lý atomicity/in-progress/recovery; Lead định nghĩa idempotency contract xuyên API, DB và messaging.

## 11. Key takeaway

- Retry side effect cần identity của logical operation.
- Atomic claim quan trọng hơn cache response.
- Idempotency phải được bảo vệ ở authoritative persistence boundary.
