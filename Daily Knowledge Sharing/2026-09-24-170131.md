# 1. .NET Large Object Heap: allocation lớn, fragmentation và GC pressure

## 1. What is it?

Mental model: .NET GC không xem mọi managed allocation giống nhau. Object đủ lớn được cấp phát trên Large Object Heap (LOH). Những allocation này thường sống và được thu gom theo cơ chế gắn với full GC, nên workload liên tục tạo buffer lớn có thể gây memory pressure và pause khác hẳn nhiều object nhỏ ngắn hạn.

Điểm quan trọng không phải học thuộc một threshold rồi tối ưu theo con số đó; điều cần hiểu là allocation size, lifetime và reuse pattern quyết định GC behavior.

## 2. Why does it exist?

Di chuyển object lớn trong compacting GC rất đắt. Runtime vì vậy xử lý large objects khác với object nhỏ. Cách này hợp lý cho những object lớn sống tương đối lâu, nhưng trở thành vấn đề khi application liên tục tạo rồi bỏ các `byte[]`, `char[]` hoặc serialized payload lớn.

Nếu không hiểu LOH, team dễ thấy process memory tăng rồi kết luận “memory leak”, trong khi root cause thực tế có thể là allocation churn, fragmentation hoặc retained buffers.

## 3. How does it work?

```text
Request
  -> allocate large byte[]
  -> LOH allocation
  -> request completes
  -> object becomes unreachable
  -> memory is reclaimed on an appropriate GC

High request rate
  -> repeated large allocations
  -> allocation pressure / fragmentation
  -> more expensive GC cycles
  -> latency spikes
```

GC metric phải được đọc cùng allocation rate, heap size, pause duration và retained-object evidence.

## 4. Practical implementation

Thay vì tạo buffer lớn cho mỗi request, cân nhắc streaming hoặc pooling khi profiling chứng minh allocation là bottleneck:

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(128 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(), cancellationToken);
    await destination.WriteAsync(buffer.AsMemory(0, read), cancellationToken);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);
}
```

Pooling cũng có cost và correctness risk; không áp dụng máy móc.

## 5. Real production scenario

API export report tạo một `MemoryStream` rồi serialize toàn bộ file 20 MB trước khi trả response. Khi 100 users export đồng thời, process memory tăng mạnh, full GC thường xuyên hơn và p99 của các endpoint không liên quan cũng tăng. Chuyển sang streaming làm giảm peak live memory và allocation rate đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → latency spike theo chu kỳ, memory cao và GC pause tăng. **Evidence** → allocation profile cho thấy large arrays/streams chiếm phần lớn bytes allocated. **Hypothesis** → large-object churn. **Diagnosis** → dùng `dotnet-counters`, `dotnet-gcdump`, profiler hoặc dump để phân biệt live retention với allocation churn. **Fix** → stream, reuse/pool có kiểm soát hoặc giảm materialization. **Verification** → chạy cùng load và so sánh allocation rate, GC pause, p95/p99 và working set.

## 7. Common mistakes

Gọi `GC.Collect()` để “sửa memory”; pool mọi buffer mà không clear sensitive data; giữ pooled buffer quá lâu; chỉ nhìn working set; load toàn file vào memory khi có thể stream; nhầm high allocation với leak.

## 8. Alternatives

Streaming thường đơn giản và an toàn hơn pooling. `RecyclableMemoryStream`-style approaches có thể phù hợp với workload cụ thể. Nếu object thực sự cần sống lâu, tối ưu allocation không thay đổi business requirement.

## 9. Trade-offs

### Advantages

Giảm allocation churn có thể giảm GC CPU, memory peaks và tail latency.

### Costs / Risks

Pooling thêm lifetime complexity, contention và nguy cơ data leakage; streaming có thể làm API implementation phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu managed memory vẫn có cost và GC không đồng nghĩa “không cần quan tâm memory”.

### Middle

Biết đo allocation và tránh materialize payload lớn không cần thiết.

### Senior

Phân biệt leak, retention, fragmentation và allocation pressure bằng evidence.

### Technical Lead / Architect

Thiết kế payload/file-processing boundary sao cho memory consumption bounded theo concurrency.

## 11. Key takeaway

- Large allocation phải được đánh giá cùng lifetime và concurrency.
- Streaming thường là giải pháp đầu tiên cho payload lớn.
- Đo GC/allocation trước khi đưa pooling complexity vào hệ thống.

# 2. ASP.NET Core ProblemDetails: error response là API contract

## 1. What is it?

`ProblemDetails` là structured HTTP error representation. Mental model: client không nên phải parse exception message hoặc đoán lỗi từ một chuỗi tùy ý; API cần một error contract có semantics ổn định.

## 2. Why does it exist?

Nếu mỗi endpoint trả lỗi theo format khác nhau, frontend và integrations phải viết branching logic theo từng API. Exception text còn có thể lộ implementation details và thay đổi sau refactor.

## 3. How does it work?

Request đi qua exception/validation handling, lỗi domain/application được map sang HTTP status và machine-readable fields.

```text
Domain conflict
 -> application error
 -> HTTP mapping
 -> 409 + ProblemDetails
```

HTTP boundary chịu trách nhiệm chuyển internal failure semantics thành public contract.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler();

return Results.Problem(
    statusCode: StatusCodes.Status409Conflict,
    title: "Timesheet conflict",
    detail: "The timesheet was modified by another request.",
    extensions: new Dictionary<string, object?>
    {
        ["code"] = "TIMESHEET_VERSION_CONFLICT"
    });
```

`code` ổn định hữu ích hơn việc client phụ thuộc vào `detail` dành cho con người.

## 5. Real production scenario

Mobile app submit timesheet với version cũ. Backend phát hiện optimistic concurrency conflict và trả `409` cùng code ổn định. App hiển thị UX refresh/merge thay vì generic “Something went wrong”.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend xử lý lỗi sai sau backend release. **Evidence** → frontend match exact `detail` string. **Hypothesis** → human-readable text bị dùng như machine contract. **Diagnosis** → inspect API response/client branching. **Fix** → status + stable error code/schema. **Verification** → contract tests giữa API và client.

## 7. Common mistakes

Trả stack trace; mọi lỗi đều 500; validation, authorization và conflict cùng một code; dùng 200 với `{ success:false }`; thay đổi machine code tùy tiện; expose database exception.

## 8. Alternatives

Custom error envelope có thể dùng nếu ecosystem đã chuẩn hóa, nhưng phải có semantics rõ và consistent. GraphQL có error model riêng; không nên ép HTTP pattern một cách máy móc.

## 9. Trade-offs

### Advantages

Client integration rõ, observability tốt hơn và giảm leakage.

### Costs / Risks

Cần governance/versioning cho error taxonomy; mapping quá chi tiết có thể coupling client vào internals.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code và structured error khác exception message.

### Middle

Implement centralized mapping và validation errors.

### Senior

Thiết kế stable error codes, security boundaries và backward compatibility.

### Technical Lead / Architect

Chuẩn hóa error contract xuyên services mà không tạo taxonomy khổng lồ khó quản lý.

## 11. Key takeaway

- Error response là public contract.
- Machine-readable code phải ổn định hơn human-readable text.
- Internal exception không nên trở thành external API model.

# 3. SQL Server covering index: giảm lookup nhưng phải trả write cost

## 1. What is it?

Covering index là index chứa đủ columns để SQL Server phục vụ query mà không phải quay lại clustered index/heap lấy thêm dữ liệu. Key columns phục vụ seek/sort; `INCLUDE` columns có thể cung cấp output mà không làm chúng thành key ordering columns.

## 2. Why does it exist?

Một nonclustered index có thể tìm đúng rows nhanh nhưng query vẫn cần thêm columns. Nếu result set lớn, hàng nghìn Key Lookup có thể biến một seek tưởng nhanh thành nhiều random I/O.

## 3. How does it work?

```text
Nonclustered seek
  -> matching row references
  -> Key Lookup for each row
  -> requested columns
```

Covering index có thể loại lookup:

```text
Nonclustered seek
  -> all required columns already present
```

## 4. Practical implementation

Query:

```sql
SELECT OrderId, CreatedAt, TotalAmount
FROM dbo.Orders
WHERE CustomerId = @CustomerId
  AND Status = @Status
ORDER BY CreatedAt DESC;
```

Candidate:

```sql
CREATE INDEX IX_Orders_Customer_Status_CreatedAt
ON dbo.Orders(CustomerId, Status, CreatedAt DESC)
INCLUDE (OrderId, TotalAmount);
```

Phải kiểm tra actual execution plan, logical reads và write workload trước/sau.

## 5. Real production scenario

Customer order-history endpoint trả 50 rows. Existing index seek được theo customer nhưng mỗi row phải lookup `TotalAmount`. Với high traffic, lookup I/O chiếm đáng kể. Một covering index đúng access pattern giảm reads mà không cần cache.

## 6. Failure scenario & troubleshooting

**Symptom** → read query nhanh hơn nhưng write latency/storage tăng. **Evidence** → nhiều wide indexes cùng columns, page writes và index size tăng. **Hypothesis** → over-indexing. **Diagnosis** → index usage stats, query plans, storage và write metrics. **Fix** → consolidate/drop low-value indexes hoặc thu hẹp INCLUDE. **Verification** → đo cả read và write workload.

## 7. Common mistakes

INCLUDE mọi column; tạo index theo từng query mà không nhìn portfolio; bỏ qua selectivity; tin estimated plan mà không xem actual rows; không cân nhắc update frequency.

## 8. Alternatives

Projection nhỏ hơn, query redesign, filtered index, precomputed read model hoặc caching tùy workload.

## 9. Trade-offs

### Advantages

Giảm lookup và logical I/O cho read path.

### Costs / Risks

Tăng storage, write amplification, maintenance và memory footprint.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không chỉ quyết định row nào được tìm mà còn dữ liệu nào đã có sẵn.

### Middle

Đọc Key Lookup trong execution plan và đo logical reads.

### Senior

Cân read benefit với write/storage/index portfolio.

### Technical Lead / Architect

Quản lý indexes theo workload tổng thể thay vì tối ưu từng query cô lập.

## 11. Key takeaway

- Key Lookup chỉ là vấn đề khi cost/frequency thực sự đáng kể.
- `INCLUDE` là công cụ covering, không phải nơi copy toàn table.
- Index optimization phải đo cả read và write cost.

# 4. Elasticsearch alias-based reindex: thay index mà Search API không downtime

## 1. What is it?

Alias là tên logic trỏ tới một hoặc nhiều Elasticsearch indexes. Mental model: application phụ thuộc vào stable logical name, còn physical index có thể được version hóa và thay thế.

## 2. Why does it exist?

Nhiều mapping/analyzer changes không thể áp dụng an toàn trực tiếp lên index hiện tại. Reindex sang index mới cần thời gian; nếu application gọi physical index name, cutover trở nên coupling và dễ downtime.

## 3. How does it work?

```text
Search API -> products-read alias -> products-v1

Build products-v2
 -> copy/reindex data
 -> validate
 -> atomically switch alias

Search API -> products-read alias -> products-v2
```

Primary database vẫn là transactional source of truth; indexing pipeline phải xử lý changes xảy ra trong lúc reindex.

## 4. Practical implementation

Tạo versioned index, bulk-load dữ liệu, replay incremental changes, validate document counts/search behavior rồi switch alias bằng một aliases operation.

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v1", "alias": "products-read" } },
    { "add":    { "index": "products-v2", "alias": "products-read" } }
  ]
}
```

## 5. Real production scenario

E-commerce thay analyzer để hỗ trợ synonyms và normalization mới. Reindex 20 triệu products mất hàng giờ. Search traffic vẫn chạy trên v1; sau validation alias chuyển sang v2 mà API configuration không đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → sau cutover, một số sản phẩm mới biến mất. **Evidence** → bulk snapshot hoàn tất nhưng changes phát sinh trong reindex window chưa replay. **Hypothesis** → synchronization gap. **Diagnosis** → compare primary DB change sequence với indexed watermark. **Fix** → replay CDC/outbox events đến known watermark trước cutover. **Verification** → count/sample/invariant checks và search acceptance tests.

## 7. Common mistakes

Reindex từ stale snapshot rồi switch ngay; application hard-code physical index; không có rollback alias; bỏ qua mapping compatibility; dùng Elasticsearch làm transactional truth.

## 8. Alternatives

In-place update phù hợp với changes hỗ trợ được. Blue/green index strategy thực chất thường dùng alias để triển khai cleanly.

## 9. Trade-offs

### Advantages

Cutover nhanh, rollback rõ và application decoupled khỏi physical index lifecycle.

### Costs / Risks

Cần temporary duplicate storage, synchronization discipline và validation pipeline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu alias là indirection layer.

### Middle

Tạo versioned index và switch alias.

### Senior

Giải quyết concurrent writes, watermark, rollback và validation.

### Technical Lead / Architect

Thiết kế ownership giữa primary DB, indexing pipeline và search service cùng recovery strategy.

## 11. Key takeaway

- Reindex là data migration, không chỉ Elasticsearch command.
- Alias làm cutover/rollback rẻ hơn.
- Concurrent data changes phải được xử lý có watermark hoặc event replay.

# 5. DDD Aggregate boundary: consistency boundary, không phải object graph

## 1. What is it?

Aggregate là nhóm domain objects được thay đổi thông qua một Aggregate Root để bảo vệ invariants trong một consistency boundary. Mental model: aggregate trả lời “những gì bắt buộc phải đúng cùng một transaction?” chứ không trả lời “những objects nào có quan hệ với nhau?”.

## 2. Why does it exist?

Nếu mọi related entity nằm trong một aggregate lớn, mỗi command phải load/lock/change một graph lớn và concurrency giảm. Nếu boundary quá nhỏ, invariant cần atomicity có thể bị phá.

## 3. How does it work?

Ví dụ Order có invariant tổng quantity không vượt business limit. `Order` root kiểm soát `OrderLine`. Nhưng Customer profile không nhất thiết nằm trong cùng aggregate chỉ vì Order có CustomerId.

```text
Order Aggregate
 ├─ Order (root)
 └─ OrderLine[]

Customer Aggregate
 └─ Customer (root)

Cross-boundary reference: CustomerId
```

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public void AddLine(ProductId productId, int quantity)
    {
        if (quantity <= 0) throw new DomainException("Quantity must be positive");
        if (_lines.Sum(x => x.Quantity) + quantity > 100)
            throw new DomainException("Order quantity limit exceeded");

        _lines.Add(new OrderLine(productId, quantity));
    }
}
```

Invariant nằm gần state mà nó bảo vệ.

## 5. Real production scenario

Approval workflow ban đầu model Employee → Timesheets → Approvals thành một giant aggregate. Khi nhiều managers approve song song, optimistic concurrency conflicts tăng. Tách boundaries theo transaction invariants giảm contention và cho phép workflow coordination bằng events/application logic.

## 6. Failure scenario & troubleshooting

**Symptom** → unrelated updates conflict thường xuyên hoặc command load hàng nghìn child rows. **Evidence** → aggregate graph lớn và version token thay đổi cho mọi operation. **Hypothesis** → boundary quá rộng. **Diagnosis** → liệt kê invariants thực sự cần atomicity. **Fix** → tách aggregate và dùng eventual consistency cho cross-boundary process nếu business cho phép. **Verification** → concurrency tests + invariant tests.

## 7. Common mistakes

Aggregate = EF navigation graph; mọi foreign key = same aggregate; expose mutable child collections; dùng repository cho mọi entity; domain event để né invariant đáng lẽ phải atomic.

## 8. Alternatives

CRUD/anemic model có thể đủ cho domain đơn giản. Application service + database constraints đôi khi đơn giản hơn rich domain model.

## 9. Trade-offs

### Advantages

Invariant ownership rõ, transaction boundary có chủ đích và giảm coupling.

### Costs / Risks

Cross-aggregate workflow cần eventual consistency/coordination; DDD modeling có learning/maintenance cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt Entity, Value Object, Aggregate và Aggregate Root.

### Middle

Implement invariants qua root và transaction boundary rõ.

### Senior

Thiết kế aggregate theo contention, invariants và lifecycle thay vì ER diagram.

### Technical Lead / Architect

Quyết định domain nào đủ phức tạp để DDD đem lại giá trị và consistency nào business thực sự yêu cầu.

## 11. Key takeaway

- Aggregate là consistency boundary.
- Relationship không tự động có nghĩa same aggregate.
- Aggregate càng lớn, concurrency/transaction cost thường càng lớn.

# 6. Azure Managed Identity + Key Vault: identity thay secret trong application configuration

## 1. What is it?

Managed Identity cung cấp Azure-hosted workload một identity do platform quản lý. Application có thể dùng identity đó để xin token truy cập Key Vault hoặc Azure resources mà không lưu client secret trong configuration.

## 2. Why does it exist?

Client secrets phải được tạo, phân phối, lưu và rotate. Mỗi bước tạo leakage risk. Nếu workload đã chạy trong Azure, platform identity loại bỏ một lớp secret-management burden.

## 3. How does it work?

```text
App Service / Function / VM
 -> Managed Identity
 -> Microsoft Entra token
 -> Key Vault authorization
 -> secret/certificate/key access
```

Key Vault vẫn chứa secrets cần tồn tại; Managed Identity giải bài toán application xác thực tới vault/resource.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(configuration["KeyVaultUri"]!),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("ThirdPartyApiKey");
```

Production dùng Managed Identity; local development có thể dùng developer credential chain phù hợp. Quyền Key Vault phải least privilege.

## 5. Real production scenario

App Service cần third-party API key. Thay vì đặt key trong deployment variable, app identity chỉ có quyền đọc đúng secret cần thiết. Rotation trong Key Vault không yêu cầu phân phối credential của chính vault.

## 6. Failure scenario & troubleshooting

**Symptom** → local chạy nhưng production trả 403 từ Key Vault. **Evidence** → token acquisition thành công nhưng authorization denied. **Hypothesis** → identity có token nhưng thiếu vault role/access. **Diagnosis** → xác định principal thực tế, RBAC assignment, vault/network restrictions. **Fix** → cấp quyền tối thiểu đúng identity. **Verification** → read allowed secret và chứng minh secret khác vẫn denied.

## 7. Common mistakes

Nhầm authentication với authorization; cấp Contributor quá rộng; vẫn giữ fallback client secret trong production; log secret value; quên Private Endpoint/firewall có thể chặn dù RBAC đúng.

## 8. Alternatives

Workload identity/federated credentials phù hợp các hosting contexts khác. Client certificate/secret vẫn cần cho external systems không hỗ trợ managed identity.

## 9. Trade-offs

### Advantages

Giảm stored credentials, rotation burden và blast radius.

### Costs / Risks

Azure coupling, RBAC/network troubleshooting và local-dev parity cần thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu identity khác secret được application tự giữ.

### Middle

Dùng `DefaultAzureCredential` và cấu hình RBAC.

### Senior

Troubleshoot token/RBAC/network separately và thiết kế least privilege.

### Technical Lead / Architect

Chuẩn hóa workload identity strategy xuyên App Service, Functions, AKS và CI/CD.

## 11. Key takeaway

- Managed Identity giảm nhu cầu lưu application credentials.
- Có identity không đồng nghĩa có authorization.
- Key Vault security gồm identity, RBAC và network boundary.

# 7. Database migration theo Expand/Contract: deploy không cần lockstep

## 1. What is it?

Expand/Contract là migration strategy thay schema qua nhiều compatible phases. Expand thêm cấu trúc mới mà version cũ vẫn chạy; application chuyển dần; Contract chỉ xóa cấu trúc cũ sau khi không còn consumer.

## 2. Why does it exist?

Trong rolling/blue-green deployment, version cũ và mới có thể chạy đồng thời. Migration kiểu rename/drop trực tiếp khiến một version lập tức hỏng và rollback application không còn an toàn.

## 3. How does it work?

```text
Phase 1 Expand: add NewColumn, keep OldColumn
Phase 2 Migrate: new app reads/writes compatible representation
Phase 3 Backfill/verify
Phase 4 Contract: remove OldColumn after all old app versions are gone
```

Database compatibility window trở thành một phần release design.

## 4. Practical implementation

Thay vì rename `FullName` → `DisplayName` trong một deploy, thêm `DisplayName` nullable, deploy code có fallback, backfill, chuyển reads, rồi drop `FullName` ở release sau.

```sql
ALTER TABLE dbo.Users ADD DisplayName nvarchar(200) NULL;
```

## 5. Real production scenario

Kubernetes rolling update giữ old pods vài phút. New release cần schema mới. Expand-first cho phép cả hai versions chạy trong rollout và rollback mà không khôi phục database ngay lập tức.

## 6. Failure scenario & troubleshooting

**Symptom** → rollback app sau incident nhưng old binary crash vì column đã drop. **Evidence** → destructive migration chạy trước khi old version retired. **Hypothesis** → schema/app compatibility bị lockstep. **Diagnosis** → reconstruct deployment timeline. **Fix** → restore compatibility hoặc forward-fix; sau incident chuyển sang phased migration. **Verification** → test N và N-1 application versions trên expanded schema.

## 7. Common mistakes

Drop/rename cùng release; long blocking migration trong startup; dual-write vô thời hạn; backfill không throttle; không đo remaining old readers/writers.

## 8. Alternatives

Maintenance-window migration có thể đơn giản hơn cho internal low-availability systems. Lockstep deploy chấp nhận được nếu topology thực sự single-instance và downtime được business cho phép.

## 9. Trade-offs

### Advantages

Rollback/deployment an toàn hơn và giảm downtime coupling.

### Costs / Risks

Temporary schema duplication, multi-release coordination và cleanup discipline.

### Middle

Viết additive migration/backfill an toàn.

### Senior

Thiết kế compatibility window, rollout và rollback.

## 11. Key takeaway

- Database schema là shared runtime contract.
- Expand trước, contract sau giúp rolling deployment/rollback an toàn.

# 8. IIS Application Pool recycling: process lifecycle là một failure boundary

## 1. What is it?

IIS Application Pool chạy web application trong worker process. Recycling thay worker process theo policy/configuration hoặc operational event. Mental model: web process là disposable runtime instance; in-memory state không phải durable state.

## 2. Why does it exist?

Process cần lifecycle management cho configuration, health, deployment và resource recovery. Enterprise IIS environments còn có scheduled recycle hoặc idle behavior.

## 3. How does it work?

```text
IIS
 -> App Pool
    -> w3wp old process
       recycle
    -> w3wp new process
```

Overlap/recycle behavior có thể giữ traffic phục vụ, nhưng background/in-memory work trong old process vẫn cần shutdown semantics đúng.

## 4. Practical implementation

ASP.NET Core hosted trên IIS không nên lưu session/business state chỉ trong static dictionary. Background work cần cancellation/graceful shutdown và durable queue nếu không được phép mất.

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        await ProcessNextAsync(stoppingToken);
    }
}
```

## 5. Real production scenario

Legacy CMS giữ generated-report jobs trong in-memory queue. Nightly app-pool recycle làm jobs đang chạy biến mất. Chuyển work items sang durable queue/worker khiến recycle chỉ thay compute instance, không làm mất business work.

## 6. Failure scenario & troubleshooting

**Symptom** → user reports session/job “biến mất” gần cùng thời điểm mỗi ngày. **Evidence** → IIS recycle events/process IDs thay đổi. **Hypothesis** → state gắn với process lifetime. **Diagnosis** → correlate IIS event logs, app startup/shutdown logs và job state. **Fix** → externalize durable state, graceful cancellation/requeue. **Verification** → trigger controlled recycle trong test environment.

## 7. Common mistakes

Static cache được coi là durable; scheduled job chạy trong every web instance; ignore shutdown token; recycle để chữa memory leak thay vì tìm root cause; không log process start/stop identity.

## 8. Alternatives

Azure App Service/containers cũng có disposable instance lifecycle; thay hosting platform không loại nguyên tắc này. Dedicated Worker Service phù hợp work dài hạn hơn web request process trong nhiều trường hợp.

## 9. Trade-offs

### Advantages

Recycling giúp operational lifecycle và process recovery.

### Costs / Risks

Stateful application design sẽ lộ lỗi; startup warm-up và in-flight work cần quản lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process có thể restart bất cứ lúc nào.

### Middle

Log lifecycle và không giữ durable state chỉ trong memory.

### Senior

Thiết kế graceful shutdown, background-work durability và recycle investigation.

### Technical Lead / Architect

Đảm bảo hosting lifecycle không quyết định business correctness.

## 11. Key takeaway

- Web process phải được coi là disposable.
- Durable work/state không nên phụ thuộc một `w3wp` instance.
- Restart/recycle là scenario phải test, không phải edge case.

# 9. Vue/TypeScript stale-request race: response cũ có thể thắng response mới

## 1. What is it?

Stale-request race xảy ra khi UI gửi nhiều async requests theo state thay đổi nhanh và response của request cũ đến sau request mới, rồi ghi đè state mới hơn.

## 2. Why does it exist?

Network completion order không đảm bảo giống request order. Search-as-you-type, filters và route changes đặc biệt dễ gặp lỗi này.

## 3. How does it work?

```text
User types "car"   -> request A (slow)
User types "cargo" -> request B (fast)
B returns -> UI shows cargo
A returns -> UI incorrectly shows car
```

Promise correctness không tự giải semantic ordering.

## 4. Practical implementation

Dùng `AbortController` để cancel request trước:

```typescript
let controller: AbortController | undefined;

async function search(query: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(`/api/search?q=${encodeURIComponent(query)}`, {
    signal: controller.signal
  });

  return await response.json();
}
```

Component lifecycle cũng phải abort work khi unmount/navigation nếu result không còn relevant.

## 5. Real production scenario

Automotive marketplace có filters make/model/price. User đổi filter nhanh; API query cũ chậm do cache miss. Không cancellation/version guard, result cũ ghi đè result mới và URL filter không khớp danh sách hiển thị.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị data không khớp filter hiện tại. **Evidence** → DevTools cho thấy request cũ hoàn tất sau request mới. **Hypothesis** → stale-response race. **Diagnosis** → log request sequence/filter state. **Fix** → abort hoặc sequence/version guard. **Verification** → throttle network và thay filter nhanh liên tục.

## 7. Common mistakes

Debounce rồi tưởng race biến mất; swallow mọi `AbortError` cùng real network errors; update loading state từ stale request; không cleanup khi component unmount.

## 8. Alternatives

Sequence token/latest-request-wins guard hữu ích khi transport không cancel được. Data libraries có thể quản lý cancellation/cache nhưng vẫn cần đúng query key semantics.

## 9. Trade-offs

### Advantages

UI state deterministic hơn và giảm unnecessary backend work.

### Costs / Risks

Cancellation/state management thêm complexity; backend có thể đã bắt đầu work dù client abort.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu async completion order không cố định.

### Middle

Implement abort/cleanup và loading/error state đúng.

### Senior

Thiết kế request identity, caching và stale-data semantics.

### Technical Lead / Architect

Chuẩn hóa frontend data-fetching pattern để tránh mỗi component tự phát minh concurrency model.

## 11. Key takeaway

- Request order không đảm bảo response order.
- Debounce và cancellation giải hai vấn đề khác nhau.
- Test race bằng network throttling, không chỉ happy-path local network.

# 10. RAG evaluation: tách retrieval failure khỏi generation failure

## 1. What is it?

RAG evaluation đo riêng các bước retrieval và answer generation. Mental model: nếu model nhận sai context, prompt hay hơn không thể đáng tin cậy sửa knowledge retrieval; nếu context đúng nhưng answer sai, retriever không phải root cause.

## 2. Why does it exist?

RAG có nhiều failure boundaries: chunking, embedding, query transformation, ranking, context selection và generation. Chỉ chấm final answer khiến team không biết nên sửa layer nào.

## 3. How does it work?

```text
Question
 -> retrieval
 -> ranked chunks
 -> context
 -> LLM generation
 -> answer

Evaluate retrieval relevance/coverage separately
Evaluate answer faithfulness/correctness separately
```

Authorization, tenant filtering và security-critical decisions vẫn phải deterministic ở application layer.

## 4. Practical implementation

Tạo evaluation dataset có question, expected source documents và expected answer criteria. Với mỗi run, lưu retrieved document IDs/scores, prompt version, model/version và final output. So sánh changes theo fixed dataset trước khi rollout.

Ví dụ record:

```json
{
  "caseId": "refund-policy-17",
  "expectedDocs": ["policy-2026-04"],
  "retrievedDocs": ["policy-2025-11", "faq-22"],
  "answerGrounded": false
}
```

## 5. Real production scenario

Internal support assistant trả refund policy cũ. Team ban đầu sửa system prompt. Evaluation cho thấy correct 2026 policy không lọt top-k vì old policy chunk có lexical overlap cao hơn. Root cause nằm ở retrieval/index lifecycle, không phải generation.

## 6. Failure scenario & troubleshooting

**Symptom** → answer confidently sai dù prompt yêu cầu “chỉ dùng context”. **Evidence** → retrieved chunks không chứa fact cần thiết. **Hypothesis** → retrieval miss. **Diagnosis** → inspect ranked chunks, metadata filters, chunking và corpus freshness. **Fix** → retrieval/index strategy rồi rerun fixed eval set. **Verification** → retrieval metric và final grounded-answer metric cùng cải thiện.

## 7. Common mistakes

Chỉ eyeball vài prompts; đổi model, prompt và retriever cùng lúc; dùng LLM judge mà không calibration; không version corpus; để model quyết định authorization filter; không lưu retrieved evidence.

## 8. Alternatives

Fine-tuning phù hợp một số behavior/style tasks nhưng không thay retrieval cho frequently changing private knowledge. Plain deterministic search có thể tốt hơn khi user cần exact document lookup.

## 9. Trade-offs

### Advantages

Localize failure, regression-test changes và giảm tuning theo cảm giác.

### Costs / Risks

Eval dataset cần maintenance; automatic judges có bias; production distribution có thể drift khỏi offline cases.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG gồm retrieval + generation, không phải một model call.

### Middle

Log sources/chunks và xây fixed regression cases.

### Senior

Phân loại retrieval, grounding, freshness và generation failures; thiết kế metrics phù hợp.

### Technical Lead / Architect

Quyết định phần nào probabilistic, phần nào deterministic, acceptance threshold và rollout/rollback strategy cho AI feature.

## 11. Key takeaway

- Final-answer score một mình không chỉ ra root cause.
- Retrieval quality và generation quality phải được đo riêng.
- Security/authorization không được giao cho probabilistic model output.
