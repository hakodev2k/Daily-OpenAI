# 1. C# async state machine + continuation cost: hiểu `await` được compiler biến đổi thế nào và vì sao “async everywhere” vẫn cần đo allocation

## 1. What is it?

`async`/`await` trong C# là syntax được compiler chuyển thành một state machine. Method async không đơn giản là “chạy trên thread khác”. Nó được chia thành các đoạn trước và sau từng `await`; khi operation chưa hoàn tất, state hiện tại được lưu lại để continuation chạy sau.

Mental model:

```text
call async method
   -> chạy đồng bộ đến await đầu tiên chưa complete
   -> lưu state
   -> return Task
   -> I/O hoàn tất
   -> continuation được schedule
   -> state machine chạy tiếp
```

## 2. Why does it exist?

Trước `async`/`await`, asynchronous code dùng callback hoặc explicit continuation, rất khó đọc và xử lý exception. State machine cho phép viết control flow gần giống synchronous code nhưng không giữ thread trong lúc chờ I/O.

Tuy nhiên abstraction này không miễn phí tuyệt đối. `Task`, closure, captured state và continuation có thể tạo allocation, đặc biệt trên hot path.

## 3. How does it work?

Ví dụ:

```csharp
public async Task<Order?> GetOrderAsync(Guid id)
{
    var order = await _repository.GetAsync(id);
    return order;
}
```

Compiler tạo state machine có state integer, builder, awaiter và field cho local variable cần sống qua `await`.

Nếu awaited `Task` đã complete, continuation có thể chạy inline. Nếu chưa, method trả control cho caller và continuation được đăng ký để resume sau.

Trong ASP.NET Core hiện đại, không có request `SynchronizationContext` kiểu ASP.NET cũ, nên continuation không cần quay về request thread cụ thể. Vì vậy `ConfigureAwait(false)` thường không mang lợi ích giống legacy ASP.NET/UI code.

## 4. Practical implementation

Tránh tạo async wrapper không cần thiết:

```csharp
public Task<Order?> GetOrderAsync(Guid id, CancellationToken ct)
    => _repository.GetAsync(id, ct);
```

Thay vì:

```csharp
public async Task<Order?> GetOrderAsync(Guid id, CancellationToken ct)
{
    return await _repository.GetAsync(id, ct);
}
```

Wrapper thứ hai tạo state machine dù không thêm logic, exception handling hay resource scope.

Nếu cần `try/finally`, logging sau `await`, `using`, hoặc transform result, async state machine là hợp lý.

## 5. Real production scenario

Một high-throughput API có utility layer gồm nhiều method chỉ `return await` sang layer kế tiếp. Mỗi request đi qua hàng chục wrapper. Individually cost nhỏ, nhưng ở hàng chục nghìn request/second, allocation rate tăng và Gen 0 GC chạy thường xuyên hơn.

Tối ưu đúng không phải xóa toàn bộ `async`, mà đo hot path rồi loại state machine dư thừa nơi có ý nghĩa.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU và allocation rate tăng dù dependency latency không đổi.

**Evidence** → profiler cho thấy nhiều `AsyncStateMachineBox`/Task-related allocations trên hot path.

**Hypothesis** → async wrappers hoặc unnecessary task creation.

**Diagnosis** → dùng BenchmarkDotNet cho micro-path và profiler/runtime counters cho Production-like workload.

**Fix** → return Task trực tiếp khi semantics cho phép; tránh closure không cần thiết; không đổi sang sync I/O để “giảm allocation”.

**Verification** → so throughput, allocation/op và GC frequency trước/sau.

## 7. Common mistakes

- Nghĩ `async` luôn tạo thread mới.
- Xóa `async` bằng cách gọi `.Result` để “nhanh hơn”.
- Dùng `ConfigureAwait(false)` máy móc trong ASP.NET Core mà không hiểu context.
- Tối ưu state machine trước khi đo bottleneck thực.
- Dùng `ValueTask` cho mọi method chỉ để tránh allocation dù contract phức tạp hơn.

## 8. Alternatives

`Task` là mặc định tốt cho asynchronous API. `ValueTask` phù hợp khi operation thường complete synchronously và measurement chứng minh Task allocation đáng kể. Synchronous API chỉ nên dùng khi underlying work thực sự synchronous hoặc blocking là chấp nhận được.

## 9. Trade-offs

### Advantages

`async`/`await` làm asynchronous control flow dễ đọc, exception propagation rõ và giải phóng thread khi chờ I/O.

### Costs / Risks

Có state-machine complexity, allocation và debugging stack trace phức tạp hơn. Tối ưu quá mức có thể làm API khó dùng hơn lợi ích performance đạt được.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` tạm dừng method chứ không block thread trong I/O async.

### Middle

Biết propagate async/cancellation end-to-end và tránh `.Result`/`.Wait()`.

### Senior

Đọc profiler, hiểu state-machine allocation, sync-completion path và khi nào `ValueTask` thực sự có lợi.

### Technical Lead / Architect

Đặt guideline dựa trên correctness trước, measurement sau; tránh team biến micro-optimization thành coding ritual.

## 11. Key takeaway

- `async`/`await` là compiler-generated state machine, không phải thread creation.
- Async wrapper có cost nhưng thường nhỏ; chỉ tối ưu khi có evidence.
- Không đổi non-blocking design thành blocking chỉ để giảm allocation.

# 2. ASP.NET Core API versioning + backward compatibility: thay đổi contract mà không buộc mọi client nâng cấp cùng lúc

## 1. What is it?

API versioning là chiến lược cho phép nhiều contract version cùng tồn tại trong một khoảng thời gian. Mục tiêu không phải tạo `/v2` mỗi khi code thay đổi, mà quản lý breaking change giữa provider và client độc lập lifecycle.

Backward compatibility nghĩa là client cũ vẫn tiếp tục hoạt động khi server được nâng cấp.

## 2. Why does it exist?

Trong distributed system, provider không kiểm soát thời điểm mọi mobile app, partner integration hay frontend deploy version mới. Một field rename tưởng nhỏ có thể làm deserialization hoặc business logic phía client hỏng.

Không version hoặc không compatibility strategy sẽ biến deployment server thành coordinated deployment toàn hệ thống.

## 3. How does it work?

Common version transport:

```text
URL:        /api/v1/orders
Header:     Api-Version: 1.0
Media type: application/vnd.company.orders.v1+json
```

Quan trọng hơn transport là lifecycle:

```text
introduce compatible change
   -> announce/deprecate old contract
   -> support overlap window
   -> observe usage
   -> migrate clients
   -> retire old version
```

## 4. Practical implementation

Ví dụ giữ field cũ và thêm field mới trước khi breaking removal:

```csharp
public sealed record OrderResponse(
    Guid Id,
    decimal Total,
    string Status,
    string? StatusDisplayName);
```

Thay vì rename `Status` ngay, có thể thêm `StatusDisplayName`, migrate client, rồi mới lên major version nếu cần xóa field cũ.

Với ASP.NET Core, versioning package hoặc endpoint-group strategy đều được; điều quan trọng là contract test và retirement policy.

## 5. Real production scenario

Mobile app version cũ còn tồn tại nhiều tháng trong app store ecosystem. Backend đổi `customerName` thành nested `customer.name`. Web frontend nâng cấp ngay nhưng mobile cũ crash khi parse response.

Một compatibility-first rollout sẽ thêm nested structure mà vẫn giữ field cũ trong overlap window, theo dõi usage rồi mới retire.

## 6. Failure scenario & troubleshooting

**Symptom** → 4xx/deserialization error tăng chỉ ở một nhóm client sau backend deployment.

**Evidence** → logs theo client version cho thấy failure tập trung ở contract cũ.

**Hypothesis** → breaking response/request change.

**Diagnosis** → compare OpenAPI/schema trước-sau, replay request từ client cũ, kiểm tra status code/error contract.

**Fix** → restore compatibility hoặc route client cũ vào version cũ; sau đó thêm contract test.

**Verification** → synthetic test cho supported client versions và telemetry usage theo API version.

## 7. Common mistakes

- Version mọi internal refactor dù contract không đổi.
- Chỉ version URL nhưng cùng DTO được mutate cho tất cả version.
- Xóa enum value hoặc thay semantics mà nghĩ là “không breaking vì JSON shape không đổi”.
- Không có deprecation telemetry nên không biết version cũ còn client nào dùng.
- Dùng versioning để giữ contract lỗi vĩnh viễn thay vì có retirement plan.

## 8. Alternatives

Nếu API chỉ có một frontend deploy cùng pipeline, compatible additive changes có thể đủ mà không cần formal versioning. GraphQL có schema evolution khác nhưng vẫn cần deprecation discipline. Event contracts cần schema/version strategy riêng vì message có thể nằm lâu trong broker.

## 9. Trade-offs

### Advantages

Giảm coupling về deployment time, cho phép migration có kiểm soát và giảm incident từ breaking contract.

### Costs / Risks

Nhiều version làm tăng code path, test matrix và support burden. Versioning không thay thế good compatibility design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu additive change thường an toàn hơn rename/remove.

### Middle

Implement version routing, DTO riêng và contract test.

### Senior

Nhận diện semantic breaking change, deprecation telemetry và backward-compatible migration sequence.

### Technical Lead / Architect

Quyết định khi nào thật sự cần major version, support window bao lâu và client ownership nào quyết định retirement risk.

## 11. Key takeaway

- API versioning quản lý lifecycle của breaking contract, không phải decoration trên URL.
- Compatibility thường rẻ hơn coordinated deployment.
- Version cũ phải có telemetry và retirement plan.

# 3. EF Core Change Tracker + identity resolution: hiểu chi phí tracking trước khi dùng `AsNoTracking` như một câu thần chú performance

## 1. What is it?

EF Core Change Tracker giữ state của entity được materialize bởi `DbContext`: `Added`, `Modified`, `Deleted`, `Unchanged`, cùng original/current values cần cho `SaveChanges`.

Identity resolution đảm bảo trong một tracking query, cùng primary key thường map về cùng entity instance.

## 2. Why does it exist?

ORM cần biết object nào thay đổi để generate `INSERT/UPDATE/DELETE`. Nếu mỗi row join tạo một object riêng cho cùng entity, object graph dễ inconsistency.

Tracking giải quyết unit-of-work semantics nhưng dùng CPU/memory để tạo entries, snapshot và relationship fix-up.

## 3. How does it work?

```text
SQL row
  -> materializer
  -> lookup primary key trong StateManager
  -> existing entity? reuse instance
  -> new entity? create + track
  -> navigation relationship fix-up
```

`AsNoTracking()` bỏ phần lớn tracking overhead. `AsNoTrackingWithIdentityResolution()` không track cho update nhưng vẫn deduplicate entity instance trong query result.

## 4. Practical implementation

Read-only projection thường tốt hơn materialize toàn entity:

```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummaryDto(
        x.Id,
        x.Total,
        x.Status))
    .ToListAsync(ct);
```

Update workflow có thể dùng tracking tự nhiên:

```csharp
var order = await db.Orders.SingleAsync(x => x.Id == id, ct);
order.Approve(userId);
await db.SaveChangesAsync(ct);
```

## 5. Real production scenario

Một reporting endpoint load 50.000 entities với nhiều relationships chỉ để serialize read-only response. Change Tracker giữ hàng chục nghìn entries dù không có update. Memory và CPU tăng, request p95 xấu hơn.

Chuyển sang projection + `AsNoTracking` giảm materialization và state-management cost đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → query SQL chạy nhanh trong database nhưng API vẫn tốn CPU/memory sau khi query hoàn tất.

**Evidence** → trace cho thấy database dependency ngắn nhưng request processing dài; profiler có materialization/change-tracker activity.

**Hypothesis** → quá nhiều tracked entity/object graph.

**Diagnosis** → kiểm tra `ChangeTracker.Entries().Count()`, payload size, projection và Include graph.

**Fix** → projection, no-tracking cho read-only path, split workload thành batch nếu cần.

**Verification** → đo allocation, request latency và tracked entry count.

## 7. Common mistakes

- Gắn `AsNoTracking` vào mọi query rồi attach entity thủ công để update.
- Load full entity chỉ để lấy 3 column.
- Giữ `DbContext` sống quá lâu khiến tracker phình dần.
- Dùng no-tracking rồi kỳ vọng thay đổi object tự được persist.
- Không hiểu duplicate object instance khi no-tracking join phức tạp.

## 8. Alternatives

Raw SQL/Dapper phù hợp read-heavy path cần kiểm soát materialization cao, nhưng mất một phần EF convenience. EF projection thường đủ và giữ LINQ/composability.

## 9. Trade-offs

### Advantages

Tracking giúp update workflow rất tự nhiên, relationship fix-up và optimistic concurrency thuận tiện.

### Costs / Risks

Memory/CPU tăng theo graph size; long-lived context dễ giữ stale state. No-tracking nhanh hơn cho read-only path nhưng không phải universal rule.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu entity được query có thể được `DbContext` theo dõi để save sau.

### Middle

Biết chọn tracking/no-tracking và dùng projection cho read endpoint.

### Senior

Hiểu identity resolution, relationship fix-up, context lifetime và materialization cost.

### Technical Lead / Architect

Đặt persistence boundary rõ: transactional command path có thể tracking; high-volume query path nên ưu tiên read model/projection đơn giản.

## 11. Key takeaway

- Change Tracker mang lại update semantics nhưng có runtime cost.
- `AsNoTracking` phù hợp read-only, không phải coding ritual.
- Projection thường mang lại lợi ích lớn hơn chỉ bật no-tracking.

# 4. SQL composite index order: vì sao cùng các column nhưng thứ tự index khác nhau có thể tạo execution plan hoàn toàn khác

## 1. What is it?

Composite index chứa nhiều key column theo thứ tự xác định. Index `(TenantId, Status, CreatedAt)` không tương đương `(CreatedAt, TenantId, Status)`.

Thứ tự key quyết định database có thể seek hiệu quả theo predicate và ordering nào.

## 2. Why does it exist?

B-tree được sắp xếp lexicographically theo key. Database có thể nhanh chóng tìm range khi query constrain left-most prefix. Nếu query bỏ qua leading key, index có thể phải scan nhiều hơn.

Vì vậy “index có đủ column” chưa nói lên index phù hợp.

## 3. How does it work?

Index:

```sql
CREATE INDEX IX_Orders_Tenant_Status_CreatedAt
ON Orders (TenantId, Status, CreatedAt DESC);
```

Query phù hợp:

```sql
SELECT TOP (50) Id, Total, CreatedAt
FROM Orders
WHERE TenantId = @tenantId
  AND Status = @status
ORDER BY CreatedAt DESC;
```

Database có thể seek vào `(TenantId, Status)` rồi đọc range đã sắp theo `CreatedAt`.

Query chỉ filter `CreatedAt` có thể không hưởng lợi tương tự vì `TenantId` là leading key.

## 4. Practical implementation

Bắt đầu từ access pattern, không từ danh sách column:

```sql
SET STATISTICS IO, TIME ON;
```

Sau đó xem actual execution plan: seek predicates, residual predicates, sort operator, key lookup và estimated/actual rows.

Có thể thêm `INCLUDE` cho output columns nếu giúp giảm lookup, nhưng phải cân write amplification.

## 5. Real production scenario

SaaS multi-tenant có dashboard query `TenantId + Status + newest first`. Developer tạo index `(CreatedAt, Status, TenantId)` vì nghĩ sort column quan trọng nhất. Query vẫn đọc lượng page lớn.

Đổi index để equality predicates đứng trước và range/order column sau làm logical reads giảm mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → index tồn tại nhưng query vẫn scan hoặc sort lớn.

**Evidence** → plan cho thấy Index Scan, residual predicate hoặc explicit Sort.

**Hypothesis** → key order không khớp access pattern hoặc selectivity/cardinality estimate không tốt.

**Diagnosis** → đọc seek predicate, IO statistics và data distribution.

**Fix** → thiết kế key order theo equality/range/order requirement; có thể cần filtered index hoặc index khác cho workload khác.

**Verification** → compare logical reads, CPU, duration và write cost.

## 7. Common mistakes

- Nghĩ composite index chỉ là tập hợp unordered columns.
- Tạo index riêng cho mọi query mà không tính write/storage cost.
- Đưa mọi output column vào key thay vì `INCLUDE`.
- Chỉ nhìn estimated plan mà không xem actual row mismatch.
- Bỏ qua multi-tenant skew và parameter sensitivity.

## 8. Alternatives

Single-column indexes có thể đủ cho query đơn giản. Filtered index hữu ích cho subset nhỏ như active rows. Columnstore phù hợp analytic workload hơn OLTP seek pattern.

## 9. Trade-offs

### Advantages

Composite index đúng access pattern có thể giảm I/O, tránh sort và giữ latency ổn định.

### Costs / Risks

Mỗi index làm insert/update/delete đắt hơn, tăng storage và maintenance. Một index không thể tối ưu mọi query shape.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index được sắp theo thứ tự key cụ thể.

### Middle

Biết đọc seek/scan và thiết kế index cho equality + range query.

### Senior

Đánh giá selectivity, cardinality, lookup, sort, write amplification và competing workloads.

### Technical Lead / Architect

Cân bằng read SLA với write throughput/storage; yêu cầu evidence từ execution plan thay vì “thêm index cho chắc”.

## 11. Key takeaway

- `(A,B,C)` không tương đương `(C,B,A)`.
- Thiết kế index bắt đầu từ query access pattern và data distribution.
- Tối ưu read luôn có write/storage cost.

# 5. Redis cache stampede + single-flight: ngăn hàng nghìn request đồng thời xuyên cache xuống database khi hot key hết hạn

## 1. What is it?

Cache stampede xảy ra khi một hot key hết hạn hoặc bị evict và nhiều request đồng thời thấy cache miss. Tất cả cùng query origin/database, biến cache miss thành traffic spike.

Single-flight là cơ chế cho phép chỉ một caller refresh dữ liệu, caller khác chờ hoặc dùng stale value.

## 2. Why does it exist?

Cache giúp giảm load trong steady state nhưng đồng bộ expiration có thể tạo load burst lớn hơn mức origin từng thấy. Nếu một product catalog key nhận 10.000 request/second, một lần expiry có thể đưa gần toàn bộ traffic xuống SQL.

## 3. How does it work?

```text
10,000 requests
      |
      v
Redis key expired
      |
      +--> request #1 refresh DB
      +--> others wait / stale-read
      |
      v
cache repopulated
```

Mitigation thường kết hợp:

- TTL jitter để key không cùng hết hạn.
- local/distributed single-flight.
- stale-while-revalidate khi business cho phép.
- bounded concurrency ở origin.

## 4. Practical implementation

Một process-local single-flight đơn giản:

```csharp
private readonly ConcurrentDictionary<string, SemaphoreSlim> _locks = new();

public async Task<T> GetOrCreateAsync<T>(
    string key,
    Func<CancellationToken, Task<T>> factory,
    CancellationToken ct)
{
    var cached = await _cache.GetStringAsync(key, ct);
    if (cached is not null)
        return JsonSerializer.Deserialize<T>(cached)!;

    var gate = _locks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
    await gate.WaitAsync(ct);
    try
    {
        cached = await _cache.GetStringAsync(key, ct);
        if (cached is not null)
            return JsonSerializer.Deserialize<T>(cached)!;

        var value = await factory(ct);
        await _cache.SetStringAsync(
            key,
            JsonSerializer.Serialize(value),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
            }, ct);

        return value;
    }
    finally
    {
        gate.Release();
    }
}
```

Multi-instance system cần nghĩ thêm về distributed coordination hoặc chấp nhận mỗi instance có một refresher.

## 5. Real production scenario

Homepage lấy “top products” từ Redis. Key TTL 5 phút, tất cả web instances dùng cùng key. Mỗi expiry tạo spike database CPU, connection pool chạm giới hạn và API p99 tăng mạnh đúng chu kỳ 5 phút.

TTL jitter + stale refresh + bounded regeneration loại bỏ periodic spike.

## 6. Failure scenario & troubleshooting

**Symptom** → latency/DB CPU spike theo chu kỳ trùng TTL.

**Evidence** → Redis miss rate tăng đột ngột trước DB dependency count.

**Hypothesis** → cache stampede.

**Diagnosis** → correlate cache misses, key TTL, DB calls và request rate.

**Fix** → single-flight, TTL jitter, stale-while-revalidate, giới hạn refresh concurrency.

**Verification** → force key expiry dưới load và quan sát origin request count.

## 7. Common mistakes

- Thêm distributed lock phức tạp trước khi chứng minh cần coordination cross-instance.
- Lock không timeout hoặc không xử lý owner crash.
- Cache mọi thứ với cùng TTL.
- Khi Redis down, toàn bộ traffic fail thẳng thay vì degrade có kiểm soát.
- Cache stale data cho domain không cho phép stale.

## 8. Alternatives

`IMemoryCache` với single-flight phù hợp single instance hoặc per-instance hot data. Precompute/background refresh phù hợp dữ liệu predictable. Không cache cũng có thể đúng nếu origin đủ nhanh và load thấp.

## 9. Trade-offs

### Advantages

Giảm burst load, giữ database ổn định và làm cache behavior predictable hơn.

### Costs / Risks

Coordination thêm latency/complexity; stale data có thể không chấp nhận được. Distributed lock sai còn nguy hiểm hơn stampede nhỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu nhiều concurrent cache miss có thể cùng gọi database.

### Middle

Implement double-check + bounded refresh và TTL jitter.

### Senior

Đánh giá cross-instance coordination, stale policy, Redis outage behavior và origin capacity.

### Technical Lead / Architect

Quyết định dữ liệu nào đáng cache, freshness SLA là gì và có cần distributed lock hay chỉ local single-flight là đủ.

## 11. Key takeaway

- Cache miss trên hot key là concurrency problem, không chỉ lookup problem.
- TTL jitter + single-flight thường hiệu quả hơn tăng TTL mù quáng.
- Cache design phải bao gồm cả failure behavior khi Redis không available.

# 6. Anti-Corruption Layer: cô lập model và semantics của third-party system khỏi domain nội bộ

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary chuyển đổi model, terminology và protocol của external/legacy system sang model mà bounded context nội bộ hiểu.

ACL không đơn giản là một HTTP wrapper. Nó bảo vệ domain khỏi semantics bên ngoài.

## 2. Why does it exist?

Third-party API thường có naming, status code, lifecycle và data model không khớp domain của ta. Nếu DTO bên ngoài đi thẳng vào domain, thay đổi provider lan khắp codebase và business logic bắt đầu nói ngôn ngữ của provider.

## 3. How does it work?

```text
Domain/Application
       |
       v
Port: IShippingService
       |
       v
Anti-Corruption Adapter
       |
       +--> map domain -> provider request
       +--> map provider response -> domain result
       +--> translate provider errors
       v
Third-party API
```

Dependency direction giữ domain phụ thuộc abstraction do application/domain sở hữu, không phụ thuộc SDK provider.

## 4. Practical implementation

```csharp
public interface IShippingQuoteService
{
    Task<ShippingQuote> GetQuoteAsync(
        Shipment shipment,
        CancellationToken ct);
}

public sealed class CarrierXShippingAdapter : IShippingQuoteService
{
    private readonly CarrierXClient _client;

    public async Task<ShippingQuote> GetQuoteAsync(
        Shipment shipment,
        CancellationToken ct)
    {
        var response = await _client.GetRateAsync(new CarrierXRateRequest
        {
            Postal = shipment.Destination.PostalCode,
            WeightGrams = shipment.Weight.Grams
        }, ct);

        return new ShippingQuote(
            Money.FromMinorUnits(response.PriceCents, response.Currency),
            MapServiceLevel(response.ServiceCode));
    }
}
```

Domain không biết `CarrierXRateRequest` hoặc provider-specific status code.

## 5. Real production scenario

E-commerce tích hợp review provider trả rating theo thang 0–100, còn domain dùng 1–5 stars. Nếu provider DTO được dùng trực tiếp xuyên application, UI, persistence và analytics đều phụ thuộc provider semantics.

ACL map sang domain concept ngay tại boundary, giúp thay provider hoặc version API mà blast radius nhỏ hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → provider đổi enum/string và nhiều layer cùng lỗi compile/runtime.

**Evidence** → external DTO xuất hiện trong domain, controller, database model và frontend contract.

**Hypothesis** → thiếu boundary translation.

**Diagnosis** → trace dependency graph và search provider SDK type usage.

**Fix** → introduce adapter + internal model; migrate call sites dần.

**Verification** → contract tests cho provider adapter; domain tests không cần provider SDK.

## 7. Common mistakes

- Tạo interface 1:1 mirror SDK nhưng không translate semantics.
- Biến ACL thành giant shared “integration layer” cho mọi bounded context.
- Swallow provider error và trả generic null.
- Leak provider rate-limit/retry detail vào domain.
- Overengineering ACL cho dependency rất nhỏ, ổn định và non-critical.

## 8. Alternatives

Direct SDK usage có thể hợp lý ở application nhỏ hoặc low-volatility integration. API gateway có thể normalize transport-level concern nhưng không thay thế domain semantic translation.

## 9. Trade-offs

### Advantages

Giảm coupling, cô lập vendor change và giữ domain language sạch.

### Costs / Risks

Thêm mapping code, test và abstraction. Nếu model nội bộ chỉ copy y nguyên provider, ACL trở thành ceremony không tạo giá trị.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain model.

### Middle

Implement adapter, mapping và provider error translation.

### Senior

Thiết kế boundary theo volatility, retry/timeout semantics và contract testing.

### Technical Lead / Architect

Quyết định integration nào cần ACL, ownership thuộc bounded context nào và chi phí abstraction có xứng với dependency risk không.

## 11. Key takeaway

- ACL bảo vệ semantics, không chỉ che HTTP client.
- External model nên dừng ở integration boundary.
- Không cần ACL nặng nếu integration đơn giản và ít volatility.

# 7. Azure Container Apps autoscaling: scale theo HTTP/queue signal nhưng không đẩy overload sang database hoặc downstream

## 1. What is it?

Azure Container Apps có thể scale replica dựa trên HTTP concurrency hoặc event-driven metrics qua KEDA, ví dụ Azure Service Bus queue length.

Autoscaling tăng số compute replica; nó không tự tăng capacity của SQL, Redis, external API hoặc quota khác.

## 2. Why does it exist?

Workload biến động cần capacity co giãn mà không vận hành Kubernetes cluster đầy đủ. Event-driven worker có thể scale xuống thấp khi idle và tăng replica khi backlog tăng.

Nhưng nếu downstream là bottleneck, scale-out application quá nhanh chỉ chuyển queue từ application sang database connection pool.

## 3. How does it work?

```text
Service Bus backlog grows
        |
        v
KEDA scaler observes metric
        |
        v
Container Apps replicas increase
        |
        v
more consumers
        |
        v
SQL / external API load increases
```

Scaling rule phải đi cùng per-replica concurrency và downstream capacity budget.

## 4. Practical implementation

Worker nên giới hạn xử lý đồng thời thay vì mỗi replica mở concurrency vô hạn:

```csharp
var options = new ParallelOptions
{
    MaxDegreeOfParallelism = 8,
    CancellationToken = stoppingToken
};

await Parallel.ForEachAsync(messages, options, async (message, ct) =>
{
    await ProcessAsync(message, ct);
});
```

Nếu scale tối đa 20 replicas, theoretical concurrent processing là khoảng 160 operations; phải so với SQL pool, provider quota và Service Bus lock semantics.

## 5. Real production scenario

Queue backlog tăng sau marketing campaign. Autoscaler tăng từ 2 lên 30 replicas. Mỗi replica xử lý 50 messages song song. SQL connection pool và external CRM rate limit bị overload, retry tăng và backlog còn lớn hơn.

Giải pháp là giới hạn max replicas/concurrency theo downstream budget, retry có jitter và autoscale signal phản ánh throughput thực.

## 6. Failure scenario & troubleshooting

**Symptom** → replicas tăng nhưng queue drain rate không tăng, timeout/429/DB waits tăng.

**Evidence** → scaling telemetry đi lên cùng dependency failure rate.

**Hypothesis** → bottleneck nằm downstream, không phải compute.

**Diagnosis** → compare messages/sec per replica, dependency latency, connection pool, quota và CPU.

**Fix** → cap concurrency, tune scale rule, batch hợp lý hoặc tăng downstream capacity nếu justified.

**Verification** → load test backlog và quan sát throughput đạt plateau ở đâu.

## 7. Common mistakes

- Nghĩ autoscale luôn cải thiện throughput.
- Không đặt max replicas.
- Scale trên queue length nhưng bỏ qua message processing time.
- Retry ngay lập tức khi 429, tạo retry storm.
- Không phân biệt CPU-bound và dependency-bound workload.

## 8. Alternatives

Azure Functions phù hợp event-driven workload đơn giản; Worker Service trên App Service/VM phù hợp khi capacity ổn định. AKS phù hợp khi cần control sâu hơn nhưng operational cost lớn hơn.

## 9. Trade-offs

### Advantages

Operational surface nhỏ hơn Kubernetes, event-driven scaling tiện và cost tốt cho workload biến động.

### Costs / Risks

Scale decisions có delay, cold start, quota và downstream pressure. Cloud autoscaling không thay capacity planning.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu replica tăng nghĩa là nhiều process cùng xử lý work.

### Middle

Cấu hình scaling rule và bounded concurrency.

### Senior

Model throughput theo replica, queue age, dependency budget và retry behavior.

### Technical Lead / Architect

Chọn compute model và max scale dựa trên end-to-end bottleneck/cost, không chỉ application CPU.

## 11. Key takeaway

- Autoscaling compute không tự autoscale toàn bộ dependency chain.
- Concurrency × replicas phải nằm trong downstream capacity budget.
- Queue drain rate quan trọng hơn chỉ nhìn replica count.

# 8. Feature flags + deployment separation: deploy code không đồng nghĩa release behavior cho người dùng

## 1. What is it?

Feature flag tách **deployment** khỏi **release**. Code mới có thể được deploy vào Production nhưng behavior chỉ bật cho nhóm user, tenant hoặc percentage cụ thể.

Flag là runtime decision point, không phải replacement cho source control branch.

## 2. Why does it exist?

Big-bang release khiến rollback thường đồng nghĩa rollback binary. Với schema migration, multi-service rollout hoặc risky UX, việc bật behavior độc lập giúp giảm blast radius và kiểm chứng telemetry trước khi mở rộng.

## 3. How does it work?

```text
Deploy code with old + new path
          |
          v
Feature flag evaluation
   | false      | true
   v            v
old behavior   new behavior
```

Release có thể theo tenant hoặc percentage. Nếu metric xấu, disable flag nhanh mà không rebuild artifact.

## 4. Practical implementation

```csharp
if (await _featureManager.IsEnabledAsync("NewCheckout"))
{
    return await _newCheckout.ExecuteAsync(request, ct);
}

return await _legacyCheckout.ExecuteAsync(request, ct);
```

Critical rule: cả hai path phải tương thích với database/schema trong overlap period.

## 5. Real production scenario

Checkout service deploy thuật toán promotion mới. Team bật 5% traffic, thấy payment authorization failure tăng 2%. Tắt flag trong vài phút, giữ binary deployment nguyên vẹn để điều tra.

Nếu không có flag, rollback application có thể va vào database migration vừa chạy.

## 6. Failure scenario & troubleshooting

**Symptom** → behavior khác nhau khó reproduce giữa user/tenant.

**Evidence** → logs thiếu flag evaluation context.

**Hypothesis** → rollout targeting hoặc stale flag config.

**Diagnosis** → log flag name/version/variant dưới structured field; kiểm tra config propagation.

**Fix** → add observability, deterministic targeting và fallback behavior.

**Verification** → synthetic user cho từng variant và dashboard segmented by flag state.

## 7. Common mistakes

- Giữ flag vĩnh viễn, codebase đầy dead branches.
- Dùng flag để che incomplete migration không có compatibility strategy.
- Flag security-sensitive feature nhưng client có thể tự override.
- Không log variant nên incident khó phân tích.
- Tạo nested flags quá nhiều làm state space bùng nổ.

## 8. Alternatives

Blue-Green hoặc Canary deployment route traffic theo deployment unit thay vì code-level behavior. Deployment slots phù hợp release infrastructure level. Đôi khi simple deployment + rollback là đủ nếu risk thấp.

## 9. Trade-offs

### Advantages

Giảm blast radius, rollback behavior nhanh và hỗ trợ progressive delivery.

### Costs / Risks

Tăng code path, test matrix và flag lifecycle management. Flag sai có thể trở thành hidden configuration dependency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy và release là hai khái niệm khác nhau.

### Middle

Implement flag evaluation và test cả on/off path.

### Senior

Thiết kế telemetry, schema compatibility, cleanup và failure fallback.

### Technical Lead / Architect

Quyết định feature nào đáng progressive rollout và governance để flag không biến thành permanent complexity.

## 11. Key takeaway

- Feature flag giảm release risk nhưng tăng runtime state.
- Flag cần observability và expiry/cleanup owner.
- Database/API compatibility vẫn phải được thiết kế độc lập.

# 9. Load testing với p95/p99 và coordinated omission: benchmark có thể “đẹp giả” nếu tool không đo thời gian user thực sự chờ

## 1. What is it?

Load testing đo hệ thống dưới traffic mô phỏng. p95/p99 cho biết tail latency thay vì chỉ average.

Coordinated omission là lỗi measurement khi load generator chờ response trước rồi mới gửi request kế tiếp. Khi server stall, generator cũng gửi ít request hơn, vô tình bỏ qua chính khoảng latency xấu nhất.

## 2. Why does it exist?

User traffic thường đến theo arrival rate tương đối độc lập với server latency. Nếu server chậm 5 giây, người dùng khác vẫn tiếp tục tới. Closed-loop benchmark có thể giảm load đúng lúc server yếu nhất và báo kết quả quá lạc quan.

## 3. How does it work?

Closed-loop:

```text
send request -> wait response -> send next
```

Nếu response chậm, request rate tự giảm.

Open-model gần production hơn cho nhiều workload:

```text
arrival schedule -> request
arrival schedule -> request
arrival schedule -> request
```

Server stall không làm generator “ngừng user đến”.

## 4. Practical implementation

Thiết kế test với target arrival rate và ghi p50/p95/p99 theo endpoint. Đồng thời monitor server-side metrics:

```text
RPS
CPU
GC
ThreadPool queue
DB connections
dependency latency
error rate
queue depth
```

Không kết luận chỉ từ client latency chart.

## 5. Real production scenario

Load test checkout dùng 100 virtual users, mỗi user chờ request hoàn tất. Khi database pause, request rate từ 1000 RPS tụt xuống 150 RPS; average latency vẫn trông chấp nhận được sau khi stall qua.

Production thật vẫn nhận gần 1000 RPS, queue phình và timeout cascade. Test model đã che bottleneck.

## 6. Failure scenario & troubleshooting

**Symptom** → load test pass nhưng Production p99 collapse dưới cùng nominal traffic.

**Evidence** → test RPS giảm đúng lúc latency tăng.

**Hypothesis** → coordinated omission hoặc workload model không giống production.

**Diagnosis** → plot arrival rate vs achieved RPS và latency timeline.

**Fix** → dùng open workload model, record intended start time và thêm overload/failure scenarios.

**Verification** → test phải giữ target arrival rate cho tới configured overload limit và capture queueing delay.

## 7. Common mistakes

- Chỉ báo average latency.
- Test với warm cache hoàn hảo và không có realistic data distribution.
- Tăng client concurrency đến vô hạn mà không mô phỏng arrival behavior.
- Không monitor dependency/DB trong test.
- Dùng load test để “chứng minh hệ thống nhanh” thay vì tìm saturation point.

## 8. Alternatives

Closed-loop test vẫn hữu ích cho user journey nơi mỗi user thật sự chờ bước trước. Microbenchmark phù hợp function-level cost nhưng không thay system load test. Production canary telemetry cung cấp behavior thật nhưng blast radius phải nhỏ.

## 9. Trade-offs

### Advantages

Tail latency + realistic arrival model giúp thấy saturation, queueing và failure propagation.

### Costs / Risks

Test environment/data càng giống Production càng tốn chi phí. Poorly designed test có thể cho confidence sai nguy hiểm hơn không test.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu p95 nghĩa là 95% request nhanh hơn threshold đó, không phải average.

### Middle

Chạy load test và correlate với server metrics.

### Senior

Thiết kế workload model, saturation experiment, failure injection và đọc tail latency.

### Technical Lead / Architect

Đặt performance SLO/test gate dựa trên user traffic model và capacity headroom, không dựa một con số benchmark đơn lẻ.

## 11. Key takeaway

- Average latency dễ che tail behavior.
- Load generator có thể tự giảm load và tạo kết quả “đẹp giả”.
- Performance test phải đo cả arrival, queueing, dependency và saturation point.

# 10. OAuth refresh token rotation + reuse detection: giới hạn blast radius khi refresh token bị đánh cắp

## 1. What is it?

Refresh token rotation nghĩa là mỗi lần client đổi refresh token lấy access token mới, authorization server phát refresh token mới và làm token cũ không còn hợp lệ.

Reuse detection phát hiện token cũ đã bị dùng lại; đây có thể là tín hiệu token bị copy/đánh cắp.

## 2. Why does it exist?

Access token thường sống ngắn để giới hạn exposure. Refresh token sống lâu hơn nên nếu bị đánh cắp, attacker có thể liên tục lấy access token mới.

Rotation biến refresh token thành credential one-time hoặc one-generation, giảm cửa sổ lạm dụng và cho phép phát hiện reuse.

## 3. How does it work?

```text
Client has RT1
   -> refresh
Server invalidates RT1, issues AT2 + RT2

Attacker later uses stolen RT1
   -> reuse detected
   -> revoke token family/session
```

Một số provider quản lý “token family” để revoke toàn chuỗi khi reuse xảy ra.

## 4. Practical implementation

Nếu tự xây authorization server, refresh token record không nên lưu raw token plaintext; lưu hash và metadata:

```csharp
public sealed class RefreshTokenRecord
{
    public Guid Id { get; init; }
    public required byte[] TokenHash { get; init; }
    public required string UserId { get; init; }
    public Guid FamilyId { get; init; }
    public DateTimeOffset ExpiresAtUtc { get; init; }
    public DateTimeOffset? ConsumedAtUtc { get; set; }
    public Guid? ReplacedById { get; set; }
}
```

Trong enterprise system, ưu tiên dùng mature identity provider thay vì tự implement OAuth protocol nếu không có yêu cầu đặc biệt.

## 5. Real production scenario

SPA/mobile app lưu refresh token bằng cơ chế platform phù hợp. Malware lấy được RT1. User tiếp tục dùng app và đã rotate sang RT2. Khi attacker dùng RT1, server nhận biết token đã consumed và revoke session family, buộc re-authentication.

Không rotation, RT1 có thể dùng đến hết expiry mà khó phân biệt attacker với client hợp lệ.

## 6. Failure scenario & troubleshooting

**Symptom** → user bị logout ngẫu nhiên hoặc token family bị revoke dù không có attacker.

**Evidence** → hai refresh request gần đồng thời dùng cùng token.

**Hypothesis** → client race condition gửi parallel refresh.

**Diagnosis** → correlate token family, device/session và request timestamps; không log raw token.

**Fix** → serialize refresh operation phía client, thiết kế grace/retry behavior phù hợp provider semantics.

**Verification** → concurrency test cho multiple API calls khi access token hết hạn.

## 7. Common mistakes

- Lưu refresh token plaintext trong database/log.
- Để access token sống rất lâu rồi coi refresh rotation là đủ.
- Cho nhiều tab/thread refresh đồng thời không có client coordination.
- Tự implement OAuth/OIDC đầy đủ khi identity provider hiện có đã hỗ trợ.
- Chỉ revoke một token mà không xem xét token family/session sau reuse.

## 8. Alternatives

Cookie session với server-side session store phù hợp traditional web app. BFF pattern có thể giữ OAuth token khỏi browser JavaScript. Long-lived access token đơn giản hơn nhưng blast radius lớn và thường không nên dùng cho sensitive system.

## 9. Trade-offs

### Advantages

Giảm giá trị của refresh token bị copy và cung cấp tín hiệu compromise rõ hơn.

### Costs / Risks

State management phức tạp hơn, concurrent refresh cần xử lý đúng và user có thể bị forced re-login khi reuse detection kích hoạt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt access token ngắn hạn và refresh token dài hạn.

### Middle

Implement client refresh flow đúng, tránh logging token và xử lý expiry.

### Senior

Hiểu rotation, token family, concurrent refresh race và secure storage.

### Technical Lead / Architect

Chọn authentication architecture, identity provider, token lifetime và compromise response dựa trên threat model thay vì tự xây protocol cho tiện.

## 11. Key takeaway

- Refresh token là long-lived credential và cần bảo vệ nghiêm ngặt.
- Rotation + reuse detection giảm blast radius khi token bị copy.
- Với OAuth/OIDC, dùng mature identity provider thường an toàn hơn tự triển khai protocol.
