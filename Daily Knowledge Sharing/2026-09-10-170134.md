# 1. .NET Large Object Heap + pinned objects: khi allocation lớn và pinning làm GC compaction kém hiệu quả

## 1. What is it?

Trong .NET, các object lớn được cấp phát trên **Large Object Heap (LOH)**. Mental model quan trọng là LOH không chỉ là “heap cho object lớn”, mà là vùng memory có behavior GC khác Small Object Heap.

Một object vượt ngưỡng kích thước LOH sẽ thường được allocate trực tiếp vào LOH. Những object này thường có lifetime tương đối dài hơn, chi phí allocation/collection đáng kể hơn, và historically việc compaction không diễn ra giống SOH trong mọi collection.

Pinned object là object mà GC không được phép di chuyển vì unmanaged/native code đang giữ địa chỉ memory cố định.

```text
Managed heap

[ movable ][ movable ][ pinned ][ movable ][ large object ........ ]
                        ↑
                  cannot move
```

Khi large allocations và pinning xuất hiện cùng lúc, heap fragmentation có thể trở thành production concern.

## 2. Why does it exist?

GC đạt hiệu quả cao vì có thể compact memory và di chuyển object để tạo vùng trống liên tục. Nhưng native interop, sockets, file I/O hoặc APIs dùng buffer pointer có lúc cần địa chỉ memory ổn định.

LOH tồn tại vì việc copy/compact object rất lớn thường tốn chi phí đáng kể. Pinned memory tồn tại vì unmanaged code không thể theo dõi việc GC di chuyển object.

Nếu không có những cơ chế này, managed runtime sẽ khó tương tác hiệu quả với OS/native APIs. Nhưng đổi lại developer phải hiểu rằng allocation pattern có thể ảnh hưởng heap layout.

## 3. How does it work?

Một pattern nguy hiểm:

```csharp
for (var i = 0; i < requests.Count; i++)
{
    var buffer = new byte[200_000];
    await ProcessAsync(buffer);
}
```

Nếu traffic cao, application tạo liên tục nhiều arrays lớn. Khi các object chết ở thời điểm khác nhau, LOH có thể xuất hiện các holes khó reuse hiệu quả cho object có kích thước khác.

Pinning làm vấn đề phức tạp thêm:

```csharp
var handle = GCHandle.Alloc(buffer, GCHandleType.Pinned);
try
{
    // native call uses fixed address
}
finally
{
    handle.Free();
}
```

Trong thời gian pin, GC không thể relocate buffer đó.

## 4. Practical implementation

Thay vì allocate buffer lớn liên tục, dùng pool khi ownership rõ ràng:

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(256 * 1024);

try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, buffer.Length), ct);
    await ProcessAsync(buffer.AsMemory(0, read), ct);
}
finally
{
    pool.Return(buffer, clearArray: false);
}
```

Nếu buffer chứa secret hoặc PII, cân nhắc `clearArray: true` hoặc clear phần đã dùng trước khi return.

Không nên áp dụng pooling máy móc cho mọi allocation; pooling chỉ hợp lý khi allocation profile cho thấy buffer churn thực sự là bottleneck.

## 5. Real production scenario

Một ASP.NET Core API cho phép upload file rồi parse nội dung vào `byte[]`. Mỗi request đọc toàn bộ file 10–20 MB vào memory. Khi 100 uploads chạy đồng thời, process memory tăng nhanh, GC pause tăng và container gần chạm memory limit.

Database và CPU application vẫn chưa cao, nhưng latency tăng vì GC pressure và memory contention.

Thiết kế đúng hơn thường là streaming hoặc bounded buffering, không phải tăng container memory vô hạn.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng theo traffic burst, p99 latency xấu đi, GC CPU tăng.

**Evidence** → profiler / `dotnet-counters` cho thấy LOH size và allocation rate tăng mạnh.

**Hypothesis** → large short-lived buffers đang tạo LOH churn.

**Diagnosis** → allocation profiler chỉ ra `byte[]`, image buffers hoặc serialization buffers có kích thước lớn.

**Fix** → streaming, pooling, chunking hoặc giảm materialization.

**Verification** → chạy cùng load test; allocation rate, Gen 2/LOH collections và peak memory phải giảm.

## 7. Common mistakes

* Nghĩ GC sẽ tự tối ưu mọi allocation pattern.
* Đọc toàn bộ file lớn vào memory vì code đơn giản hơn.
* Pool buffer nhưng giữ reference quá lâu.
* Pin managed buffer lâu hơn cần thiết.
* Clear toàn bộ rented buffer rất lớn mà không cân nhắc chi phí khi dữ liệu không nhạy cảm.

## 8. Alternatives

* Streaming: tốt nhất khi consumer có thể xử lý dữ liệu tuần tự.
* `ArrayPool<T>`: tốt khi cần temporary reusable buffer.
* `MemoryPool<T>`: hữu ích cho memory ownership abstractions trong pipelines/networking.
* Allocate trực tiếp: vẫn là lựa chọn đúng nếu object nhỏ, ít và profiling không cho thấy vấn đề.

## 9. Trade-offs

### Advantages

Hiểu LOH và pinning giúp giảm memory spikes, GC pressure và OOM risk.

### Costs / Risks

Pooling và ownership logic làm code phức tạp hơn, dễ data leakage hoặc use-after-return nếu lifecycle sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu large allocation khác small allocation và GC không phải “free memory management”.

### Middle

Biết dùng streaming/pooling và đo allocation thay vì đoán.

### Senior

Hiểu fragmentation, pinning, Gen 2 pressure và production impact.

### Technical Lead / Architect

Quyết định data-flow boundary: file/binary payload nào được materialize, payload nào phải stream, và memory budget mỗi request là bao nhiêu.

## 11. Key takeaway

* LOH pressure thường là access-pattern problem hơn là GC bug.
* Streaming tốt hơn buffering toàn bộ khi payload lớn.
* Pooling chỉ đáng dùng khi ownership rõ và measurement chứng minh lợi ích.

# 2. ASP.NET Core Output Caching: cache response đúng boundary mà không trả nhầm dữ liệu theo user, query hoặc header

## 1. What is it?

Output Caching lưu lại HTTP response đã tạo để request tương đương sau đó có thể trả từ cache mà không chạy toàn bộ application pipeline phía sau.

Mental model:

```text
Client
  ↓
ASP.NET Core Output Cache
  ├─ hit  → cached response
  └─ miss → endpoint → DB/API → response → cache
```

Điểm khó không phải bật cache; điểm khó là xác định **request nào thực sự tương đương** và **response nào an toàn để share**.

## 2. Why does it exist?

Một endpoint public như product detail có thể bị gọi hàng nghìn lần với cùng input. Nếu mỗi request đều query DB, compose CMS blocks và serialize JSON, hệ thống lặp lại cùng work.

Output Cache giúp giảm:

* database calls
* serialization work
* dependency latency
* CPU

Nhưng nếu cache key thiếu dimension như language, tenant hoặc query parameter, cache có thể trả response sai.

## 3. How does it work?

Cache key thường phải phản ánh những inputs ảnh hưởng output:

```text
Path
+ Query
+ selected Headers
+ custom variation key
```

Ví dụ `/products/42?currency=USD` và `/products/42?currency=EUR` không phải cùng response.

User-specific response càng nguy hiểm:

```text
GET /me
Authorization: Bearer user-A
```

Nếu cache public mà không vary đúng, user B có thể nhận dữ liệu user A.

## 4. Practical implementation

```csharp
builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("catalog", policy =>
        policy
            .Expire(TimeSpan.FromSeconds(30))
            .SetVaryByQuery("currency")
            .SetVaryByHeader("Accept-Language"));
});

app.UseOutputCache();

app.MapGet("/products/{id:int}", GetProduct)
   .CacheOutput("catalog");
```

Với invalidation theo tag:

```csharp
app.MapGet("/products/{id:int}", async (int id) =>
{
    // ...
})
.CacheOutput(policy => policy.Tag("catalog"));
```

Khi catalog thay đổi, application có thể evict entries theo policy phù hợp thay vì chờ TTL quá lâu.

## 5. Real production scenario

E-commerce product page gọi Product API, Review API và CMS. Product data chỉ thay đổi vài phút một lần nhưng traffic rất cao.

Output caching 20–30 giây giảm dependency load đáng kể. Tuy nhiên price theo market/currency và content theo locale phải nằm trong cache variation strategy.

## 6. Failure scenario & troubleshooting

**Symptom** → user ở `vi-VN` đôi lúc nhận content tiếng Anh hoặc price currency sai.

**Evidence** → cache-hit requests có cùng key dù `Accept-Language` hoặc `currency` khác nhau.

**Hypothesis** → cache key thiếu variation dimension.

**Diagnosis** → kiểm tra policy, request headers/query và response differences.

**Fix** → thêm vary dimension hoặc không cache endpoint đó.

**Verification** → test matrix theo locale/currency/auth state, kiểm tra cache hit vẫn trả đúng output.

## 7. Common mistakes

* Cache endpoint authenticated mà chưa phân tích data isolation.
* Vary theo quá nhiều high-cardinality values làm hit ratio gần 0.
* TTL dài để “tăng performance” nhưng bỏ qua freshness requirement.
* Không có invalidation owner.
* Cache error response ngoài ý muốn.

## 8. Alternatives

* `IMemoryCache`: cache object/application result, linh hoạt nhưng phải tự quản lý key và serialization semantics.
* Redis: shared distributed cache giữa instances.
* CDN: cache gần client, phù hợp public HTTP content.
* Không cache: đúng khi dữ liệu rất dynamic hoặc correctness quan trọng hơn latency.

## 9. Trade-offs

### Advantages

* Giảm repeated work rất hiệu quả.
* Có thể cải thiện p95/p99 đáng kể.

### Costs / Risks

* Staleness.
* Cache-key complexity.
* Security/correctness bug nếu cache boundary sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache hit bỏ qua phần work phía sau.

### Middle

Biết cấu hình TTL và variation theo query/header.

### Senior

Đánh giá freshness, privacy, hit ratio và invalidation strategy.

### Technical Lead / Architect

Quyết định layer cache đúng: browser, CDN, Output Cache, Redis hay database optimization; tránh nhiều cache layers không có ownership.

## 11. Key takeaway

* Cache key là correctness contract.
* Không cache authenticated/user-specific response nếu chưa chứng minh isolation an toàn.
* Cache layer càng gần client càng hiệu quả, nhưng invalidation/freshness càng cần thiết kế rõ.

# 3. EF Core `SaveChangesInterceptor`: cross-cutting persistence concern, auditing và Outbox mà không làm domain model phụ thuộc Infrastructure

## 1. What is it?

`SaveChangesInterceptor` cho phép hook vào lifecycle `SaveChanges` / `SaveChangesAsync` của EF Core.

Nó phù hợp cho một số **cross-cutting persistence concerns** như audit metadata, diagnostics hoặc tạo Outbox records từ domain events.

Mental model:

```text
Application
   ↓
DbContext.SaveChangesAsync()
   ↓
Interceptor
   ↓
SQL transaction
```

Interceptor không phải nơi để nhét business logic tùy ý.

## 2. Why does it exist?

Nếu mỗi application service tự set `UpdatedAt`, ghi audit record hoặc extract domain events, logic bị lặp và dễ bỏ sót.

Ngược lại, đặt trực tiếp EF-specific code trong domain entity sẽ làm domain phụ thuộc persistence technology.

Interceptor tạo một boundary nơi Infrastructure có thể phản ứng với persistence lifecycle mà domain vẫn độc lập.

## 3. How does it work?

Interceptor nhận callback trước/sau SaveChanges. Nó có thể inspect `ChangeTracker`:

```text
Tracked entities
   ↓
detect Added / Modified / Deleted
   ↓
create audit/outbox entries
   ↓
SaveChanges transaction
```

Nếu Outbox records được add vào cùng DbContext trước commit, business state và Outbox message có thể được ghi atomically trong cùng database transaction.

## 4. Practical implementation

```csharp
public sealed class AuditingInterceptor : SaveChangesInterceptor
{
    private readonly IClock _clock;

    public AuditingInterceptor(IClock clock) => _clock = clock;

    public override InterceptionResult<int> SavingChanges(
        DbContextEventData eventData,
        InterceptionResult<int> result)
    {
        var db = eventData.Context!;

        foreach (var entry in db.ChangeTracker.Entries<IAuditable>())
        {
            if (entry.State == EntityState.Modified)
                entry.Entity.UpdatedAtUtc = _clock.UtcNow;
        }

        return result;
    }
}
```

Registration:

```csharp
builder.Services.AddDbContext<AppDbContext>((sp, options) =>
{
    options.UseSqlServer(connectionString);
    options.AddInterceptors(sp.GetRequiredService<AuditingInterceptor>());
});
```

## 5. Real production scenario

Một approval platform cần audit timestamp và publish domain events sau khi transaction commit. Team ban đầu đặt code audit ở từng command handler.

Sau vài tháng, một handler mới quên set `UpdatedAt`, khiến reporting sai.

Interceptor giúp enforce infrastructure-level consistency, trong khi business invariant vẫn nằm trong aggregate/domain service.

## 6. Failure scenario & troubleshooting

**Symptom** → SaveChanges chậm hơn nhiều sau khi thêm audit interceptor.

**Evidence** → profiler cho thấy interceptor serialize toàn bộ entity graph cho mỗi update.

**Hypothesis** → cross-cutting hook đang làm quá nhiều work synchronous.

**Diagnosis** → đo duration trước/sau interceptor và số tracked entities.

**Fix** → chỉ capture changed properties cần thiết; tránh external I/O trong interceptor.

**Verification** → persistence latency trở lại baseline và audit correctness vẫn đạt yêu cầu.

## 7. Common mistakes

* Gọi external API trong `SavingChanges`.
* Đặt business validation vào interceptor vì “mọi save đều đi qua đây”.
* Serialize navigation graph lớn.
* Giả định interceptor luôn chạy nếu code dùng raw SQL ngoài DbContext.
* Publish event ra broker trước khi DB transaction commit.

## 8. Alternatives

* Override `SaveChanges`: đơn giản cho một DbContext nhưng coupling cao hơn.
* Application service explicit logic: rõ ràng, phù hợp business-specific flow.
* Database trigger: enforce ở DB nhưng khó đưa domain context và testing vào application.

## 9. Trade-offs

### Advantages

* Centralize persistence concern.
* Giữ domain ít phụ thuộc Infrastructure.
* Hữu ích cho Outbox/auditing consistency.

### Costs / Risks

* Hidden behavior.
* Debug khó hơn nếu interceptor chain lớn.
* Dễ biến thành “god hook”.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu interceptor chạy quanh SaveChanges, không thay thế business service.

### Middle

Biết inspect ChangeTracker và register interceptor.

### Senior

Phân biệt persistence concern với domain rule và tránh external I/O trong transaction hook.

### Technical Lead / Architect

Quyết định concern nào đáng centralize, transaction boundary ở đâu, và Outbox/publish workflow vận hành thế nào sau commit.

## 11. Key takeaway

* Interceptor phù hợp cross-cutting persistence concern, không phải business orchestration.
* External side effect không nên chạy trước transaction commit.
* Hidden behavior cần telemetry và conventions rõ để maintainable.

# 4. ADO.NET / EF Core connection pooling: vì sao pool exhaustion làm API timeout dù database CPU vẫn thấp

## 1. What is it?

ADO.NET connection pooling tái sử dụng database connections vật lý thay vì tạo TCP/TLS/login session mới cho mỗi query.

Mental model:

```text
Request
  ↓ Open()
Connection Pool
  ├─ free connection → reuse
  └─ no free connection → wait
```

`DbConnection.Close()` hoặc dispose thường **trả connection về pool**, không nhất thiết đóng physical connection.

## 2. Why does it exist?

Mở database connection thật có chi phí network, authentication và server session setup. Pool giúp giảm latency và tăng throughput.

Nhưng pool có giới hạn. Nếu application giữ connections quá lâu, requests mới phải chờ dù SQL Server CPU chỉ 20%.

## 3. How does it work?

Pool thường được partition theo connection string/config identity. Khi code gọi `OpenAsync`, provider lấy idle connection nếu có.

Pool exhaustion xảy ra khi:

```text
Request concurrency ↑
      ↓
connections held too long
      ↓
active connections == pool max
      ↓
new request waits
      ↓
command/request timeout
```

Nguyên nhân có thể là slow query, long transaction, streaming reader, connection leak hoặc downstream request giữ DbContext trong scope quá lâu.

## 4. Practical implementation

EF Core thường quản lý open/close quanh operation. Code application nên để lifetime ngắn:

```csharp
public async Task<OrderDto?> GetAsync(Guid id, CancellationToken ct)
{
    return await db.Orders
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new OrderDto(x.Id, x.Number))
        .SingleOrDefaultAsync(ct);
}
```

Tránh:

```csharp
await db.Database.OpenConnectionAsync(ct);
await SomeExternalApiCallAsync(ct); // connection vẫn bị giữ
```

Nếu cần explicit connection, dispose trong scope nhỏ nhất.

## 5. Real production scenario

API có pool max 100. Một release mới thêm transaction quanh workflow gồm SQL query + HTTP call 5 giây.

Chỉ cần ~100 concurrent requests là toàn bộ pool bị giữ. Database CPU thấp nhưng request queue tăng và API trả timeout hàng loạt.

## 6. Failure scenario & troubleshooting

**Symptom** → API timeout, SQL CPU thấp, connection-open latency tăng.

**Evidence** → application metrics cho thấy active pooled connections gần max; traces cho thấy long dependency spans/transactions.

**Hypothesis** → pool exhaustion chứ không phải DB compute saturation.

**Diagnosis** → inspect connection duration, transaction duration, slow queries và external calls nằm trong DB scope.

**Fix** → rút ngắn transaction/connection lifetime, tối ưu query, tránh external I/O khi giữ connection.

**Verification** → dưới cùng load, pool utilization có headroom và acquire latency thấp.

## 7. Common mistakes

* Tăng `Max Pool Size` ngay lập tức mà không tìm lý do connections bị giữ lâu.
* Giữ transaction xuyên external API call.
* Dùng DbContext singleton.
* Mở nhiều connection strings chỉ khác nhỏ config, vô tình tạo nhiều pools.
* Không propagate cancellation cho long query.

## 8. Alternatives

Không có lựa chọn “không pool” hợp lý cho phần lớn web workloads. Tuy nhiên có thể giảm pressure bằng batching, caching, queueing hoặc thay đổi data access pattern.

## 9. Trade-offs

### Advantages

* Reuse connection hiệu quả.
* Giảm latency mở connection.

### Costs / Risks

* Pool trở thành bounded shared resource.
* Leak/long transaction khuếch đại thành system-wide outage.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Open` không đồng nghĩa luôn tạo connection vật lý mới.

### Middle

Biết dispose DbContext/connection đúng scope và tránh long transaction.

### Senior

Phân biệt DB saturation với pool saturation bằng telemetry.

### Technical Lead / Architect

Đặt connection budget theo instance/concurrency/database capacity và thiết kế workflows không giữ DB resource qua remote calls.

## 11. Key takeaway

* Connection pool là bounded resource.
* Database CPU thấp không chứng minh database path khỏe.
* Rút ngắn connection/transaction lifetime thường quan trọng hơn tăng pool size.

# 5. MongoDB embedding vs referencing: thiết kế document theo access pattern, consistency boundary và document growth

## 1. What is it?

MongoDB document modeling thường có hai lựa chọn chính:

* **Embedding**: dữ liệu con nằm trong cùng document.
* **Referencing**: document lưu ID và dữ liệu liên quan nằm ở collection khác.

```text
Embedding
Order
 └─ Items[]

Referencing
Order ── productId ──> Product
```

Đây không phải quyết định “normalization vs denormalization” đơn giản; nó là quyết định về access pattern, update frequency, atomicity và document growth.

## 2. Why does it exist?

Document database tối ưu khi dữ liệu thường được đọc/ghi theo aggregate-like boundary.

Nếu luôn split mọi entity giống relational model, application có thể phải thực hiện nhiều queries hoặc `$lookup` không cần thiết.

Ngược lại, embed mọi thứ có thể tạo document rất lớn, duplicate dữ liệu và update fan-out.

## 3. How does it work?

Embedding phù hợp khi child data:

* bounded về size
* thường đọc cùng parent
* lifecycle gắn với parent
* cần atomic update trong một document

Referencing phù hợp khi data:

* được share giữa nhiều parents
* update độc lập thường xuyên
* có cardinality lớn/unbounded
* cần query riêng

Ví dụ order line nên thường snapshot product name/price tại thời điểm mua thay vì reference live product price cho historical invoice.

## 4. Practical implementation

```json
{
  "_id": "order-123",
  "customerId": "cust-10",
  "items": [
    {
      "productId": "p-42",
      "name": "Keyboard X",
      "unitPrice": 120.00,
      "quantity": 2
    }
  ],
  "total": 240.00
}
```

Ở đây product fields là snapshot business data. Không cần join sang Product collection để reconstruct historical order.

## 5. Real production scenario

Automotive marketplace lưu Listing với hàng nghìn view events. Nếu embed mọi view vào Listing document, document tăng không giới hạn và trở thành write hotspot.

Thiết kế tốt hơn là embed bounded listing attributes, còn analytics events nằm collection/time-series riêng.

## 6. Failure scenario & troubleshooting

**Symptom** → update Listing ngày càng chậm, document size tăng mạnh.

**Evidence** → document chứa array events hàng trăm nghìn phần tử.

**Hypothesis** → unbounded child collection bị embed sai boundary.

**Diagnosis** → kiểm tra document growth, update pattern và working-set size.

**Fix** → chuyển unbounded events sang collection riêng; giữ aggregate document bounded.

**Verification** → document size ổn định và write latency giảm.

## 7. Common mistakes

* Copy relational schema sang MongoDB 1:1.
* Embed unbounded arrays.
* Reference mọi thứ rồi cần nhiều round trips.
* Duplicate mutable data nhưng không có synchronization strategy.
* Chọn schema trước khi hiểu query/update patterns.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp hơn khi quan hệ phức tạp, constraints và joins là trung tâm của workload.

MongoDB phù hợp khi aggregate/document access patterns rõ và schema flexibility có giá trị thực.

## 9. Trade-offs

### Advantages

Embedding giảm round trips và có atomicity tự nhiên trong document.

### Costs / Risks

Duplication, document growth và synchronization complexity có thể tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu embed là “store together because used together”, không phải “NoSQL không có relation”.

### Middle

Biết thiết kế bounded document theo read/write flow.

### Senior

Đánh giá duplication, update frequency, working set và growth risk.

### Technical Lead / Architect

Chọn persistence model dựa trên consistency/access patterns, không dựa trên buzzword “schema-less”.

## 11. Key takeaway

* Model document theo access pattern.
* Unbounded arrays là warning sign lớn.
* Duplicate dữ liệu chỉ an toàn khi ownership và synchronization semantics rõ.

# 6. Anti-Corruption Layer trong Hexagonal Architecture: cô lập third-party model để external contract không xâm nhập domain

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary chuyển đổi model/protocol của external system sang language/model nội bộ.

Trong Hexagonal Architecture, external provider là adapter phía ngoài; domain/application phụ thuộc vào port nội bộ.

```text
Domain/Application
      ↓ port
PaymentGateway
      ↑ adapter
Stripe/Legacy ERP/Partner API
```

ACL bảo vệ domain khỏi external naming, error codes và data shapes.

## 2. Why does it exist?

External API thay đổi theo roadmap của bên khác. Nếu controller/service/domain object dùng trực tiếp SDK types hoặc provider statuses, external contract trở thành internal architecture.

Ví dụ provider có status `CAPTURED`, `SETTLED`, `AUTHORIZED`. Domain của bạn có thể chỉ cần `Paid` và `Pending` theo business rules riêng.

## 3. How does it work?

Port nội bộ:

```csharp
public interface IPaymentGateway
{
    Task<PaymentResult> ChargeAsync(
        PaymentRequest request,
        CancellationToken ct);
}
```

Adapter map sang provider:

```text
Internal PaymentRequest
      ↓ mapping
Provider DTO / SDK
      ↓ remote call
Provider response
      ↓ mapping
Internal PaymentResult
```

Provider exceptions cũng nên được translate thành internal failure categories có ý nghĩa.

## 4. Practical implementation

```csharp
public sealed class PartnerPaymentGateway : IPaymentGateway
{
    private readonly PartnerClient _client;

    public async Task<PaymentResult> ChargeAsync(
        PaymentRequest request,
        CancellationToken ct)
    {
        var response = await _client.CreateChargeAsync(new PartnerCharge
        {
            AmountInMinorUnits = request.AmountInMinorUnits,
            Reference = request.OrderId.ToString()
        }, ct);

        return response.Status switch
        {
            "APPROVED" => PaymentResult.Paid(response.Id),
            "DECLINED" => PaymentResult.Declined(response.Code),
            _ => PaymentResult.Pending(response.Id)
        };
    }
}
```

Domain không cần biết `PartnerCharge` hay raw provider status.

## 5. Real production scenario

E-commerce đổi review provider từ vendor A sang vendor B. Nếu UI/business service dùng vendor-A DTO trực tiếp, migration lan khắp codebase.

Nếu có internal `ReviewSummary` contract và adapter, thay provider chủ yếu giới hạn trong Infrastructure/integration module.

## 6. Failure scenario & troubleshooting

**Symptom** → provider thêm status mới, application silently map thành success.

**Evidence** → logs có unknown external status nhưng business order chuyển sai state.

**Hypothesis** → mapping có unsafe default.

**Diagnosis** → inspect ACL translation logic.

**Fix** → fail-safe mapping, explicit unknown state, telemetry/alert cho contract drift.

**Verification** → contract tests với known/unknown provider responses.

## 7. Common mistakes

* Wrap SDK bằng interface nhưng trả nguyên SDK DTO ra ngoài.
* Copy mọi field từ provider vào domain “để phòng sau này dùng”.
* Swallow provider error details cần cho diagnosis.
* ACL quá lớn vì cố unify nhiều providers có semantics khác nhau.

## 8. Alternatives

Direct SDK usage đủ tốt cho prototype hoặc integration rất nhỏ, ít business coupling.

ACL đáng giá khi provider contract có volatility, domain semantics quan trọng hoặc khả năng thay provider là realistic concern.

## 9. Trade-offs

### Advantages

* Change isolation.
* Domain language sạch hơn.
* Testability tốt hơn.

### Costs / Risks

* Mapping code tăng.
* Có thể over-abstract nếu external API đơn giản và ổn định.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain model.

### Middle

Biết tạo port/adapter và mapping explicit.

### Senior

Thiết kế error semantics, contract drift handling và observability.

### Technical Lead / Architect

Quyết định boundary nào cần ACL và boundary nào direct integration là đủ đơn giản.

## 11. Key takeaway

* Interface wrapper không tự động tạo abstraction tốt.
* ACL phải translate semantics, không chỉ đổi tên class.
* Chỉ thêm boundary khi volatility/business isolation thực sự đáng giá.

# 7. Azure Container Apps revisions: deploy version mới, split traffic và rollback mà không biến revision thành stateful deployment

## 1. What is it?

Azure Container Apps revision là immutable snapshot của application configuration/container deployment tại một thời điểm.

Một app có thể có nhiều active revisions và phân chia traffic giữa chúng.

```text
Users
  ↓
Container App ingress
  ├─ 90% → revision v10
  └─ 10% → revision v11
```

Revision phù hợp cho rollout/canary, nhưng application vẫn nên được thiết kế stateless hoặc externalize state.

## 2. Why does it exist?

Deploy “replace all at once” làm blast radius lớn. Nếu build mới có regression, 100% traffic bị ảnh hưởng ngay.

Revision cho phép chạy version cũ và mới song song để validate behavior trước khi chuyển toàn traffic.

## 3. How does it work?

Một revision mới được tạo khi revision-scope configuration thay đổi. Traffic routing có thể chuyển theo percentage hoặc label.

Important dependency flow:

```text
Revision v10 ─┐
              ├─> shared DB / Redis / Service Bus
Revision v11 ─┘
```

Vì hai versions có thể sống đồng thời, DB schema/API contracts phải backward compatible trong rollout window.

## 4. Practical implementation

Application nên expose readiness endpoint:

```csharp
builder.Services.AddHealthChecks()
    .AddDbContextCheck<AppDbContext>();

app.MapHealthChecks("/health/ready");
```

Deployment strategy có thể là:

```text
Deploy v11 with 0% traffic
→ verify startup/health
→ 5%
→ observe error rate + p95
→ 25%
→ 100%
```

Rollback traffic về v10 nhanh hơn rebuild/redeploy nếu v10 vẫn active và compatible.

## 5. Real production scenario

Một API release thay serialization logic. Canary 5% cho thấy 500 rate tăng chỉ ở v11. Team route traffic về v10 trước khi phần lớn users bị ảnh hưởng.

Database migration vẫn là điểm cần chú ý: nếu migration của v11 phá schema mà v10 cần, traffic rollback không cứu được hệ thống.

## 6. Failure scenario & troubleshooting

**Symptom** → rollback traffic về old revision nhưng old revision vẫn lỗi.

**Evidence** → DB schema đã drop/rename column cũ.

**Hypothesis** → application rollback bị phá bởi incompatible database migration.

**Diagnosis** → compare deployment/migration timeline và SQL errors của old revision.

**Fix** → dùng Expand-Contract migrations, không destructive change trong cùng rollout.

**Verification** → old/new revisions đều chạy được trong migration window.

## 7. Common mistakes

* Nghĩ revision rollback = full system rollback.
* Store session/local state trong container filesystem.
* Chuyển 100% traffic trước khi có telemetry đủ.
* Health probe chỉ kiểm tra process sống, không kiểm tra readiness thực tế.

## 8. Alternatives

* Azure App Service deployment slots: phù hợp App Service workloads.
* Kubernetes rolling/canary: linh hoạt hơn nhưng operational overhead cao hơn.
* Simple replace deployment: đủ cho low-risk internal app.

## 9. Trade-offs

### Advantages

* Canary/traffic splitting built-in.
* Rollback application version nhanh.
* Ít Kubernetes operational burden hơn.

### Costs / Risks

* Multi-revision compatibility requirement.
* Shared state/schema vẫn là common failure domain.
* Cost tăng khi nhiều revisions active.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu revision là immutable deployment version.

### Middle

Biết health checks và gradual traffic shift.

### Senior

Hiểu compatibility, rollback limits và telemetry gating.

### Technical Lead / Architect

Thiết kế release strategy kết hợp app revision, database migration, message contract và rollback policy.

## 11. Key takeaway

* Revision giúp rollback code, không rollback database/state tự động.
* Canary chỉ có giá trị khi có telemetry và success criteria.
* Multi-version compatibility là điều kiện của safe rollout.

# 8. Zero-downtime database migration với Expand-Contract: schema evolution khi application cũ và mới phải cùng tồn tại

## 1. What is it?

Expand-Contract là migration strategy tách breaking schema change thành nhiều bước backward-compatible.

Ví dụ rename column `Name` → `DisplayName` không nên làm một bước trực tiếp trong Production khi old/new app versions cùng chạy.

```text
Expand: add DisplayName
   ↓
Dual-compatible application
   ↓
Backfill
   ↓
Switch reads/writes
   ↓
Contract: remove Name later
```

## 2. Why does it exist?

Trong rolling/canary deployment, old version và new version có thể cùng chạy vài phút hoặc vài giờ.

Nếu migration drop column mà old version vẫn query, deployment tạo immediate outage.

Database schema có lifecycle chậm hơn application process và cần compatibility window.

## 3. How does it work?

Bước điển hình:

1. Add schema mới không breaking.
2. Deploy code có thể làm việc với old + new schema.
3. Backfill dữ liệu.
4. Switch reads/writes sang schema mới.
5. Quan sát đủ lâu.
6. Remove old schema trong release sau.

Transaction boundary và backfill volume phải được thiết kế để tránh long locks.

## 4. Practical implementation

Migration đầu:

```sql
ALTER TABLE Customers
ADD DisplayName nvarchar(200) NULL;
```

Backfill theo batch thay vì một transaction khổng lồ:

```sql
UPDATE TOP (1000) Customers
SET DisplayName = Name
WHERE DisplayName IS NULL;
```

Application transition có thể temporarily read fallback:

```csharp
var displayName = customer.DisplayName ?? customer.Name;
```

Sau khi tất cả code và data đã chuyển, release khác mới drop old column.

## 5. Real production scenario

SaaS deploy 10 instances. Rolling deployment mất 15 phút. Nếu migration rename/drop column ngay trước rollout, 9 old instances có thể crash query trong khi instance đầu tiên đang chạy code mới.

Expand-Contract cho phép cả hai versions coexist.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment mới healthy trên một node nhưng phần còn lại trả SQL invalid-column errors.

**Evidence** → old app logs reference column vừa bị drop.

**Hypothesis** → migration không backward compatible.

**Diagnosis** → compare schema change với app versions đang active.

**Fix** → restore compatibility hoặc rollback schema có kiểm soát; về dài hạn áp dụng Expand-Contract.

**Verification** → test old + new binaries cùng chạy trên transitional schema.

## 7. Common mistakes

* Drop/rename column trong cùng release dùng code mới.
* Backfill toàn bộ bảng lớn trong một transaction.
* Thêm `NOT NULL` ngay khi dữ liệu cũ chưa có giá trị.
* Giả định rollback app sẽ rollback schema.
* Không test migration trên production-scale data.

## 8. Alternatives

Maintenance window có thể đơn giản hơn cho hệ thống chấp nhận downtime.

Expand-Contract đáng dùng khi availability requirement cao hoặc deployment có multiple concurrent versions.

## 9. Trade-offs

### Advantages

* Giảm deployment blast radius.
* Hỗ trợ rolling/canary/rollback.

### Costs / Risks

* Migration kéo dài qua nhiều releases.
* Transitional code/schema tạm thời phức tạp.
* Cần cleanup discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu app và DB không update atomically như một file duy nhất.

### Middle

Biết tạo additive migration và backfill an toàn.

### Senior

Thiết kế multi-version compatibility và đo lock/backfill impact.

### Technical Lead / Architect

Định nghĩa migration policy, rollback contract và release sequencing giữa app, DB và async consumers.

## 11. Key takeaway

* Safe deployment đòi hỏi schema tương thích với nhiều app versions.
* Destructive change nên đến sau compatibility window.
* Rollback code không đủ nếu schema đã breaking.

# 9. Structured logging + trace correlation: biến log thành evidence điều tra thay vì chuỗi text khó truy vấn

## 1. What is it?

Structured logging ghi event dưới dạng message template + named properties thay vì nối chuỗi text.

```csharp
logger.LogInformation(
    "Order {OrderId} submitted by {UserId}",
    order.Id,
    userId);
```

Backend có thể index `OrderId`, `UserId`, `TraceId`, `Environment` thành fields để query.

Trace correlation nối logs của cùng distributed operation qua `TraceId`/`SpanId`.

## 2. Why does it exist?

Text log kiểu:

```text
Order 42 failed for user 7
```

khó query đáng tin cậy khi format thay đổi. Trong microservice/integration flow, một request có thể tạo logs ở nhiều services.

Structured properties + trace context biến logs thành searchable evidence.

## 3. How does it work?

ASP.NET Core/OpenTelemetry có thể propagate W3C trace context:

```text
Client request
  ↓ traceparent
API span
  ↓ HTTP/message propagation
Worker span
```

Mỗi log trong active `Activity` có thể được enriched bằng TraceId/SpanId.

Correlation không thay thế logs, metrics hay traces; chúng bổ sung nhau:

```text
Metric → phát hiện anomaly
Trace  → localize slow/failing path
Logs   → inspect detailed event/context
```

## 4. Practical implementation

```csharp
using (logger.BeginScope(new Dictionary<string, object>
{
    ["OrderId"] = orderId,
    ["TenantId"] = tenantId
}))
{
    logger.LogInformation("Submitting order");
    await service.SubmitAsync(orderId, ct);
}
```

Không log toàn request body/token chỉ để “có context”. Chỉ capture fields cần cho operation và không vi phạm privacy/security.

## 5. Real production scenario

Checkout API p95 tăng từ 300 ms lên 1.5 s. Metric báo latency regression. Trace cho thấy Payment API span chiếm 1.1 s. Structured logs theo `TraceId` chỉ ra provider response status và retry attempt.

Investigation đi từ signal rộng tới evidence cụ thể thay vì grep hàng triệu lines.

## 6. Failure scenario & troubleshooting

**Symptom** → logs có rất nhiều dữ liệu nhưng không nối được request giữa API và Worker.

**Evidence** → producer logs có TraceId A, consumer có TraceId mới nhưng không có parent/link/correlation property.

**Hypothesis** → propagation bị mất qua message metadata.

**Diagnosis** → inspect publish/consume instrumentation.

**Fix** → propagate trace context chuẩn và giữ business correlation ID khi cần long-lived workflow.

**Verification** → truy từ request sang downstream operation được trong telemetry backend.

## 7. Common mistakes

* String interpolation mọi log làm mất structured properties.
* Log PII, JWT hoặc secrets.
* Dùng `UserId`, URL đầy đủ hoặc arbitrary input làm high-cardinality metric label.
* Log exception message mà bỏ stack trace.
* Tạo custom correlation ID nhưng không dùng OpenTelemetry trace context.

## 8. Alternatives

Plain text logs có thể đủ cho tool nhỏ/local script. Production distributed system thường hưởng lợi mạnh từ structured logging + traces.

## 9. Trade-offs

### Advantages

* Query/debug nhanh hơn.
* Correlation giữa services tốt hơn.
* Hỗ trợ alert/investigation automation.

### Costs / Risks

* Storage/ingestion cost.
* Schema/property discipline cần governance.
* Sensitive-data leakage nếu logging không kiểm soát.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu log event nên có properties có nghĩa.

### Middle

Biết dùng message templates, scopes và trace context.

### Senior

Thiết kế telemetry hỗ trợ hypothesis-driven investigation và kiểm soát cost/privacy.

### Technical Lead / Architect

Định nghĩa logging conventions, retention, sampling, correlation strategy và ownership của observability data.

## 11. Key takeaway

* Log nhiều không đồng nghĩa observable.
* Structured properties phải phục vụ query/investigation thực tế.
* Metrics, traces và logs nên nối thành một reasoning loop.

# 10. SSRF trong server-side integration: khi một URL “do user nhập” trở thành đường vào metadata service và private network

## 1. What is it?

SSRF — Server-Side Request Forgery — xảy ra khi attacker kiểm soát hoặc ảnh hưởng URL mà server sẽ request.

Ví dụ API nhận:

```json
{
  "imageUrl": "https://example.com/image.png"
}
```

và backend gọi URL đó bằng `HttpClient` mà không hạn chế destination.

Attacker có thể thử URL trỏ tới localhost, private network hoặc cloud metadata endpoints.

## 2. Why does it exist?

Server thường có network access mà client internet không có:

* internal APIs
* localhost admin ports
* private endpoints
* metadata services

Khi server trở thành HTTP proxy theo input user, trust boundary bị xuyên thủng.

## 3. How does it work?

Attack flow:

```text
Attacker
   ↓ malicious URL
Public API
   ↓ server-side fetch
Internal / metadata endpoint
   ↓ response
Public API
   ↓
Attacker
```

Chặn chỉ hostname string chưa đủ vì DNS resolution, redirects, IPv6/IPv4 forms và alternate encodings có thể bypass naive checks.

## 4. Practical implementation

Thiết kế an toàn nhất thường là **allowlist destinations** thay vì blacklist.

```csharp
private static readonly HashSet<string> AllowedHosts =
    new(StringComparer.OrdinalIgnoreCase)
    {
        "cdn.partner.example",
        "images.partner.example"
    };

static Uri ValidateExternalUri(string value)
{
    if (!Uri.TryCreate(value, UriKind.Absolute, out var uri))
        throw new ValidationException("Invalid URL");

    if (uri.Scheme != Uri.UriSchemeHttps)
        throw new ValidationException("HTTPS required");

    if (!AllowedHosts.Contains(uri.Host))
        throw new ValidationException("Host not allowed");

    return uri;
}
```

Ngoài application validation, network egress policy nên giới hạn những destinations server được phép gọi.

## 5. Real production scenario

CMS có feature “import image from URL”. Backend tải ảnh rồi lưu vào Blob Storage.

Nếu URL không được giới hạn, attacker có account editor thấp quyền có thể thử gọi internal admin endpoint hoặc metadata service qua server network identity.

SSRF vì vậy không chỉ là input-validation bug; nó là network architecture issue.

## 6. Failure scenario & troubleshooting

**Symptom** → logs cho thấy image-import endpoint gọi IP private/localhost bất thường.

**Evidence** → request URL đến `127.0.0.1`, RFC1918 range hoặc cloud metadata destination.

**Hypothesis** → SSRF attempt.

**Diagnosis** → kiểm tra URL validation, redirect behavior, DNS resolution và outbound network rules.

**Fix** → strict allowlist, disable/validate redirects, egress restrictions, least-privilege identity.

**Verification** → security tests với localhost, private IP, encoded IP, redirect-to-private và DNS edge cases đều bị block.

## 7. Common mistakes

* Blacklist chuỗi `localhost` nhưng cho phép `127.0.0.1`.
* Validate URL ban đầu nhưng auto-follow redirect sang private destination.
* Chỉ dựa vào application validation, không có network egress control.
* Cho phép arbitrary schemes.
* Log response chứa sensitive internal data.

## 8. Alternatives

Nếu use case chỉ cần fetch từ vài providers, integration-specific API/allowlist tốt hơn generic “fetch any URL”.

Nếu generic fetch là business requirement thật, cần sandbox/egress proxy chuyên biệt và network isolation mạnh hơn.

## 9. Trade-offs

### Advantages

Allowlist + egress control giảm attack surface rõ rệt.

### Costs / Risks

Giảm flexibility; onboarding provider mới cần config/deployment/governance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu server có network privilege khác browser/client.

### Middle

Biết validate scheme/host và không trust arbitrary URL.

### Senior

Hiểu redirects, DNS tricks, private ranges, metadata service và egress policy.

### Technical Lead / Architect

Quyết định có nên tồn tại generic fetch capability hay phải cô lập nó thành component với restricted network identity.

## 11. Key takeaway

* SSRF là trust-boundary + network problem, không chỉ regex validation.
* Allowlist tốt hơn blacklist cho server-side fetch.
* Application validation nên được hỗ trợ bởi egress restriction và least privilege.
