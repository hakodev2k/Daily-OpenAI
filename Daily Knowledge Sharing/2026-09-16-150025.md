# 1. `Task.WhenAll` và bounded fan-out: concurrency không đồng nghĩa tạo vô hạn Tasks

## 1. What is it?

`Task.WhenAll` chờ một tập asynchronous operations hoàn tất. Nó không tự giới hạn concurrency. Nếu tạo 50.000 HTTP/database operations rồi đưa tất cả vào `WhenAll`, application có thể tạo áp lực lên sockets, connection pools, remote quotas và memory dù code hoàn toàn `async`.

## 2. Why does it exist?

Các I/O độc lập có thể chạy đồng thời để giảm wall-clock latency. Nhưng concurrency hữu ích chỉ tới capacity của dependency. Sau điểm đó, thêm concurrency tạo queueing, timeout và retry amplification.

## 3. How does it work?

Mỗi async operation chạy tới điểm await và giữ state machine thay vì giữ thread. `WhenAll` tạo task tổng hợp hoàn tất khi mọi task con hoàn tất. Resource bên dưới vẫn hữu hạn: SQL pool, HTTP connection limit, API quota và CPU xử lý continuation.

## 4. Practical implementation

```csharp
await Parallel.ForEachAsync(
    orderIds,
    new ParallelOptions { MaxDegreeOfParallelism = 16, CancellationToken = ct },
    async (id, token) =>
    {
        await processor.ProcessAsync(id, token);
    });
```

Hoặc dùng `SemaphoreSlim`/`Channel<T>` khi cần explicit queue/backpressure.

## 5. Real production scenario

Worker import 20.000 products gọi pricing API cho từng item. Phiên bản đầu dùng `Task.WhenAll` trên toàn bộ collection. Pricing API chỉ cho 100 concurrent requests nên 429 tăng mạnh, retry làm backlog lớn hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 tăng, 429/timeout tăng dù CPU thấp. **Evidence** → dependency concurrent calls và socket/connection pool queue tăng. **Hypothesis** → fan-out vượt capacity. **Diagnosis** → so throughput theo concurrency level. **Fix** → bounded concurrency phù hợp quota/capacity. **Verification** → throughput ổn định, tail latency và retry giảm.

## 7. Common mistakes

Cho rằng async luôn scalable; tạo task cho toàn bộ dataset; dùng `WhenAll` với EF Core trên cùng `DbContext`; retry từng task không có budget; không propagate cancellation.

## 8. Alternatives

Sequential processing đơn giản và đúng khi volume thấp. `Parallel.ForEachAsync` phù hợp bounded fan-out đơn giản. `Channel<T>` tốt khi cần producer/consumer backpressure. Queue/message broker phù hợp khi work cần durable distribution.

## 9. Trade-offs

### Advantages

Giảm latency và tăng throughput khi dependency còn capacity.

### Costs / Risks

Concurrency cao làm tăng resource pressure, ordering complexity và failure amplification.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu concurrency khác parallelism và `WhenAll` không giới hạn số operations.

### Middle

Implement bounded concurrency và cancellation.

### Senior

Đo capacity, quota, connection pool và tail latency trước khi chọn degree.

### Technical Lead / Architect

Quyết định in-process concurrency hay durable queue dựa trên reliability, load và ownership boundary.

## 11. Key takeaway

- Async loại bỏ blocked thread, không tạo resource vô hạn.
- Concurrency phải bị giới hạn theo dependency capacity.
- Đo throughput và p95/p99 thay vì chọn degree theo cảm giác.

# 2. ASP.NET Core Request Timeout: deadline propagation thay vì timeout rời rạc ở từng layer

## 1. What is it?

Request timeout là budget thời gian cho một request. Deadline propagation nghĩa là downstream operations nhận phần budget còn lại thay vì mỗi dependency tự bắt đầu một timeout mới.

## 2. Why does it exist?

Nếu API có SLA 2 giây nhưng SQL timeout 30 giây và external API timeout 100 giây, client có thể bỏ cuộc từ lâu trong khi backend tiếp tục tiêu thụ resource.

## 3. How does it work?

Ingress xác định deadline. Cancellation token/deadline được truyền qua application và dependencies. Mỗi dependency phải kết thúc trước deadline tổng, có thể với budget nhỏ hơn để còn thời gian xử lý response/fallback.

## 4. Practical implementation

```csharp
builder.Services.AddRequestTimeouts(o =>
{
    o.AddPolicy("api", TimeSpan.FromSeconds(2));
});

app.UseRequestTimeouts();
app.MapGet("/quote", HandleQuote).WithRequestTimeout("api");
```

Handler tiếp tục truyền `CancellationToken` xuống EF Core và `HttpClient`.

## 5. Real production scenario

Checkout API gọi inventory và payment. Nếu inventory đã mất 1.7 giây trong budget 2 giây, payment không nên bắt đầu với timeout độc lập 10 giây nếu response không còn cơ hội hoàn thành đúng contract.

## 6. Failure scenario & troubleshooting

**Symptom** → client timeout nhưng active SQL/HTTP calls vẫn kéo dài. **Evidence** → traces có child spans sống sau request deadline. **Diagnosis** → timeout/cancellation không propagate. **Fix** → central budget + token propagation. **Verification** → dependency spans kết thúc trong deadline và resource usage giảm.

## 7. Common mistakes

Nhầm timeout với retry; mỗi layer reset timeout; catch cancellation rồi tiếp tục work; đặt timeout quá ngắn mà không dựa trên latency distribution.

## 8. Alternatives

Dependency-specific timeout vẫn cần cho remote calls nhưng phải nằm trong request budget. Background asynchronous workflow phù hợp nếu business operation hợp lệ nhưng không thể hoàn thành trong HTTP deadline.

## 9. Trade-offs

### Advantages

Giới hạn resource retention và failure propagation; làm latency contract rõ.

### Costs / Risks

Deadline quá chặt tạo false failures; cần thiết kế partial work và idempotency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout giới hạn thời gian chờ.

### Middle

Cấu hình timeout và propagate cancellation.

### Senior

Thiết kế budget giữa dependencies dựa trên telemetry.

### Technical Lead / Architect

Quyết định operation nào phải synchronous và operation nào nên chuyển sang asynchronous workflow.

## 11. Key takeaway

- Timeout nên là budget end-to-end, không phải các đồng hồ độc lập.
- Cancellation phải đi cùng deadline.
- Operation dài có thể cần đổi interaction model thay vì chỉ tăng timeout.

# 3. EF Core `AsNoTrackingWithIdentityResolution`: cân bằng read performance và object identity

## 1. What is it?

`AsNoTrackingWithIdentityResolution` thực hiện no-tracking query nhưng vẫn đảm bảo cùng database entity xuất hiện nhiều lần trong result graph được materialize thành cùng object instance trong phạm vi query.

## 2. Why does it exist?

`AsNoTracking` giảm Change Tracker overhead cho read-only queries, nhưng join/include có thể materialize duplicate object instances. Identity resolution hữu ích khi graph cần reference consistency nhưng không cần update tracking.

## 3. How does it work?

EF Core dùng temporary identity map trong quá trình materialization rồi bỏ nó sau query. Entity không được attach vào `DbContext` Change Tracker.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .AsNoTrackingWithIdentityResolution()
    .Include(x => x.Customer)
    .Include(x => x.Lines)
    .Where(x => x.CreatedAt >= from)
    .ToListAsync(ct);
```

Nếu chỉ cần DTO, projection thường tốt hơn.

## 5. Real production scenario

Reporting endpoint tải graph Orders/Customer/Lines để serialize. Nhiều orders cùng customer. Identity resolution giảm duplicate Customer objects trong graph nhưng vẫn tránh long-lived tracking.

## 6. Failure scenario & troubleshooting

**Symptom** → memory allocation vẫn cao sau khi đổi từ tracking query. **Evidence** → query materialize graph lớn dù API chỉ dùng vài fields. **Diagnosis** → vấn đề là over-fetching, không chỉ tracking. **Fix** → projection và pagination. **Verification** → allocations, SQL columns và payload giảm.

## 7. Common mistakes

Dùng nó như mặc định cho mọi read; materialize entity graph khi DTO đủ; kỳ vọng entity được tracked để `SaveChanges`; che N+1/over-fetching bằng tracking option.

## 8. Alternatives

`AsNoTracking` nhẹ hơn nếu identity không quan trọng. Projection thường tối ưu nhất cho API read model. Tracking query đúng khi entity sẽ được thay đổi trong cùng unit of work.

## 9. Trade-offs

### Advantages

Giảm tracking overhead nhưng giữ identity consistency trong result.

### Costs / Risks

Temporary identity map vẫn tốn CPU/memory; không thay thế query-shape optimization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu tracking dùng cho update state.

### Middle

Chọn tracking/no-tracking theo use case.

### Senior

Đo materialization, allocation và SQL shape; ưu tiên projection khi phù hợp.

### Technical Lead / Architect

Chuẩn hóa read-model patterns mà không biến EF configuration thành abstraction cứng nhắc.

## 11. Key takeaway

- No-tracking không tự làm query hiệu quả nếu vẫn over-fetch.
- Identity resolution giải quyết object identity, không giải quyết SQL complexity.
- API read path thường nên cân nhắc projection trước entity graph.

# 4. PostgreSQL JSONB + GIN index: linh hoạt schema nhưng vẫn phải thiết kế access pattern

## 1. What is it?

`jsonb` lưu JSON ở binary representation hỗ trợ operators và indexing. GIN index có thể index các keys/values để tăng tốc containment/existence queries.

## 2. Why does it exist?

Một số attributes thay đổi theo product/category hoặc integration payload và không đáng tạo hàng chục nullable columns. Nhưng flexibility không loại bỏ nhu cầu schema governance và query design.

## 3. How does it work?

```sql
CREATE INDEX ix_products_attributes
ON products USING GIN (attributes jsonb_path_ops);

SELECT id
FROM products
WHERE attributes @> '{"color":"black"}';
```

Planner chỉ dùng index khi predicate/operator và selectivity phù hợp. Index cũng tăng write amplification và storage.

## 4. Practical implementation

Giữ fields quan trọng cho joins, constraints, sorting và frequent filtering ở typed columns; dùng JSONB cho sparse/extensible attributes. Đo bằng `EXPLAIN (ANALYZE, BUFFERS)`.

## 5. Real production scenario

Marketplace có attributes khác nhau cho car, motorcycle và accessory. JSONB chứa category-specific metadata, nhưng `seller_id`, `price`, `created_at`, status vẫn là columns vì chúng có invariants và query thường xuyên.

## 6. Failure scenario & troubleshooting

**Symptom** → write latency tăng và index size phình lớn. **Evidence** → GIN index lớn, update JSON thường xuyên. **Hypothesis** → index toàn document cho workload chỉ query vài keys. **Fix** → expression/targeted indexes hoặc promote hot attributes thành columns. **Verification** → compare write I/O và query plans.

## 7. Common mistakes

Dùng JSONB để né schema design; lưu money/date dưới string; index toàn bộ document vô điều kiện; không validate payload; dùng JSONB cho relational relationships.

## 8. Alternatives

Typed columns cho stable schema/invariants. Child tables phù hợp repeated relational data. Document DB phù hợp nếu aggregate/access pattern thực sự document-oriented.

## 9. Trade-offs

### Advantages

Schema evolution linh hoạt, phù hợp sparse attributes.

### Costs / Risks

Constraint yếu hơn, index/write cost cao và query có thể khó tối ưu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết JSONB không chỉ là text JSON.

### Middle

Viết containment query và GIN index.

### Senior

Đọc plan, chọn operator class và cân bằng read/write cost.

### Technical Lead / Architect

Quyết định boundary giữa relational schema, JSONB và document store dựa trên access patterns/invariants.

## 11. Key takeaway

- JSONB là công cụ schema flexibility, không phải lý do bỏ schema design.
- Index phải theo query pattern thực tế.
- Stable business invariants nên có typed representation khi có thể.

# 5. DDD Domain Event vs Integration Event: tách transaction boundary khỏi public contract

## 1. What is it?

Domain Event biểu diễn sự kiện có ý nghĩa bên trong domain/bounded context. Integration Event là contract dùng để thông báo cho hệ thống/bounded context khác. Chúng có thể liên quan nhưng không nên mặc định là cùng một object.

## 2. Why does it exist?

Nếu internal domain model bị publish trực tiếp, thay đổi domain refactoring có thể trở thành breaking external contract. Đồng thời external delivery có failure semantics khác transaction nội bộ.

## 3. How does it work?

```text
API -> Application -> Aggregate
                    -> Domain Event
                         |
                         v
                  Application handler
                         |
                  DB transaction + Outbox
                         |
                         v
                  Integration Event -> Bus
```

Aggregate sở hữu invariants; application layer chuyển internal outcome thành durable external message khi cần.

## 4. Practical implementation

```csharp
public sealed record OrderConfirmedDomainEvent(Guid OrderId);
public sealed record OrderConfirmedV1(Guid OrderId, DateTimeOffset ConfirmedAt);
```

Mapping sang integration contract nên xảy ra ở boundary, không bắt Domain phụ thuộc messaging SDK.

## 5. Real production scenario

Order bounded context confirm order. Domain handlers cập nhật internal audit. Notification và fulfillment contexts nhận `OrderConfirmedV1` qua bus sau khi Outbox publish.

## 6. Failure scenario & troubleshooting

**Symptom** → đổi tên property trong domain làm consumer khác deserialize lỗi. **Evidence** → cùng class được dùng cho domain và bus contract. **Diagnosis** → boundary bị coupling. **Fix** → versioned integration contract + mapping. **Verification** → consumer contract tests chạy với old/new producers.

## 7. Common mistakes

Publish entity trực tiếp; coi Domain Event luôn asynchronous; đưa Service Bus dependency vào Domain; không version public event; phát integration event trước DB commit.

## 8. Alternatives

Không cần Domain Events nếu workflow đơn giản và direct application service rõ hơn. Integration events vẫn có thể được tạo trực tiếp từ application transaction khi domain event abstraction không đem lại giá trị.

## 9. Trade-offs

### Advantages

Giảm coupling, bảo vệ domain model, rõ transaction và communication boundaries.

### Costs / Risks

Thêm mapping/contracts/handlers; dễ overengineer CRUD system đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt event nội bộ và message public.

### Middle

Implement domain event handler và integration mapping.

### Senior

Reason về transaction, Outbox, versioning và failure propagation.

### Technical Lead / Architect

Xác định bounded contexts, data ownership, public contracts và nơi event architecture thực sự cần thiết.

## 11. Key takeaway

- Domain Event và Integration Event có lifecycle khác nhau.
- Public event là compatibility contract, không phải serialization của entity.
- Hệ thống đơn giản không cần event abstraction chỉ vì dùng DDD.

# 6. Idempotency Key cho POST: chống duplicate side effect trong distributed systems

## 1. What is it?

Idempotency key là client-generated identifier gắn với một logical command. Server lưu kết quả/trạng thái theo key để retry cùng command không tạo side effect lần hai.

## 2. Why does it exist?

Network timeout tạo ambiguity: client không biết server chưa nhận request hay đã commit nhưng response bị mất. Retry POST mù có thể tạo hai payments/orders.

## 3. How does it work?

Server atomically claim key với operation. Duplicate request cùng key và cùng payload nhận lại kết quả trước hoặc trạng thái đang xử lý. Key khác đại diện command khác.

## 4. Practical implementation

```sql
CREATE TABLE idempotency_requests (
  key uuid PRIMARY KEY,
  request_hash text NOT NULL,
  status text NOT NULL,
  response jsonb,
  created_at timestamptz NOT NULL
);
```

Claim key và business mutation cần transaction boundary phù hợp. So sánh request hash để ngăn reuse key cho payload khác.

## 5. Real production scenario

Mobile checkout gửi `POST /orders`; mạng rớt sau commit. App retry cùng key. Server trả order đã tạo thay vì insert order thứ hai.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate orders dù client có retry policy. **Evidence** → hai requests cùng business intent nhưng khác/no idempotency key. **Diagnosis** → retry không có deduplication contract. **Fix** → idempotency key + durable atomic claim. **Verification** → fault injection làm mất response sau commit và retry vẫn chỉ có một side effect.

## 7. Common mistakes

Lưu key chỉ trong memory; key không gắn payload; TTL quá ngắn; check-then-insert không atomic; coi database unique constraint trên unrelated field là idempotency hoàn chỉnh.

## 8. Alternatives

Natural business key/unique constraint đủ nếu domain đã có identifier duy nhất. PUT thường naturally idempotent theo resource URI. Messaging consumers dùng message ID/inbox pattern cho vấn đề tương tự.

## 9. Trade-offs

### Advantages

Cho phép safe retry và xử lý ambiguous network outcomes.

### Costs / Risks

Cần storage, cleanup, payload validation và concurrency control.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu duplicate request có thể xảy ra dù client chỉ “bấm một lần”.

### Middle

Implement key storage và unique constraint.

### Senior

Thiết kế atomicity, TTL, response replay và conflict semantics.

### Technical Lead / Architect

Chuẩn hóa idempotency contract cho payment/order/command APIs theo business risk.

## 11. Key takeaway

- Timeout không chứng minh server chưa commit.
- Retry side-effecting POST cần deduplication strategy.
- Idempotency phải durable và atomic ở correctness boundary.

# 7. Azure Event Grid delivery semantics: event notification, retry và dead-letter design

## 1. What is it?

Azure Event Grid là event routing service cho notifications theo pub/sub. Nó phù hợp thông báo rằng một sự kiện đã xảy ra; subscriber phải thiết kế cho retry, duplicate delivery và temporary unavailability.

## 2. Why does it exist?

Producer không nên biết trực tiếp mọi consumer. Event Grid decouple routing và fan-out, đặc biệt cho Azure resource events và lightweight integration notifications.

## 3. How does it work?

Publisher gửi event tới topic/system topic; Event Grid match subscriptions rồi push tới handlers. Delivery failure được retry theo policy; dead-letter destination có thể giữ undeliverable events.

## 4. Practical implementation

Handler ASP.NET Core nên validate event, nhanh chóng persist/enqueue work rồi trả success thay vì giữ HTTP request cho long-running processing. Dùng event ID làm deduplication key khi side effect cần exactly-once business behavior.

## 5. Real production scenario

Blob upload phát event; subscriber tạo thumbnail và metadata job. Event Grid notification không phải nơi chứa toàn bộ file; Blob Storage vẫn là source của payload lớn.

## 6. Failure scenario & troubleshooting

**Symptom** → thumbnail tạo hai lần hoặc event biến mất sau nhiều retries. **Evidence** → delivery logs/dead-letter storage và duplicate event IDs. **Diagnosis** → consumer không idempotent hoặc dead-letter không được monitor. **Fix** → dedupe + DLQ processing/alerts. **Verification** → replay event không tạo duplicate side effect.

## 7. Common mistakes

Giả định exactly-once; chạy long work trực tiếp trong webhook; không dead-letter; nhầm Event Grid với durable work queue; đưa sensitive payload không cần thiết vào event.

## 8. Alternatives

Azure Service Bus phù hợp commands/work queues, ordering/sessions và richer broker semantics. Event Hubs phù hợp high-throughput event streams. Direct HTTP đơn giản khi chỉ có một synchronous consumer.

## 9. Trade-offs

### Advantages

Managed fan-out, loose coupling, tích hợp Azure tốt.

### Costs / Risks

Eventual delivery, duplicates, operational need cho retries/dead-letter; cost tăng theo event volume.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu publisher/subscriber và event notification.

### Middle

Implement subscription handler và validation.

### Senior

Thiết kế idempotency, retry, DLQ, identity/networking và monitoring.

### Technical Lead / Architect

Chọn Event Grid vs Service Bus vs Event Hubs dựa trên semantics, không chỉ vì đều “gửi message”.

## 11. Key takeaway

- Event Grid là event routing, không phải universal queue.
- Consumer phải chịu được duplicate/retry.
- Dead-letter chỉ hữu ích nếu có ownership, alert và replay procedure.

# 8. CI/CD database migration orchestration: deploy code và schema theo compatibility window

## 1. What is it?

Migration orchestration là cách pipeline kiểm soát khi nào schema change chạy so với build, test, deploy, health validation và rollback. Mục tiêu là tránh mỗi application instance tự cạnh tranh chạy migration và tránh schema breaking mixed versions.

## 2. Why does it exist?

Trong rolling deployment, nhiều versions có thể cùng chạy. Nếu startup tự chạy destructive migration, instance đầu tiên có thể phá schema mà instances cũ vẫn cần.

## 3. How does it work?

```text
commit -> build -> test -> artifact
       -> compatibility migration
       -> deploy
       -> health validation
       -> monitor
       -> later cleanup migration
```

Migration là release step có audit/lock/failure policy riêng.

## 4. Practical implementation

Pipeline tạo migration bundle/script từ cùng commit với application artifact, chạy một lần bằng deployment identity giới hạn quyền. Application runtime identity không nhất thiết cần DDL permissions.

## 5. Real production scenario

TeamCity build artifact; Octopus deploy App Service slots. Pre-deploy step thêm nullable column/index online-compatible. App vNext deploy và health check. Drop old column chỉ ở release sau khi rollback window kết thúc.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment mới chưa chạy nhưng database đã breaking; old pods trả 500. **Evidence** → migration log cho thấy drop/rename chạy trước rollout. **Diagnosis** → schema compatibility không được orchestration. **Fix** → expand/contract và explicit migration stage. **Verification** → test N/N-1 compatibility trong staging.

## 7. Common mistakes

`Database.Migrate()` trên mọi startup production; DDL quyền cho app runtime; migration không timeout/monitor; rollback binary nhưng không có database strategy; backfill lớn trong một transaction.

## 8. Alternatives

Startup migration có thể đủ cho single-instance internal app nhỏ. Manual DBA migration phù hợp môi trường governance cao nhưng chậm và dễ drift nếu không automation. Dedicated migration job cân bằng control và repeatability.

## 9. Trade-offs

### Advantages

Release deterministic, audit rõ, giảm race và blast radius.

### Costs / Risks

Pipeline phức tạp hơn; cần ownership giữa developers/DBA/platform team.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu schema là dependency của nhiều app versions.

### Middle

Tạo migration scripts/bundles và test staging.

### Senior

Thiết kế compatibility, backfill, failure/rollback và permissions.

### Technical Lead / Architect

Định nghĩa release contract: ai sở hữu migration, khi nào chạy, health gate và cleanup window.

## 11. Key takeaway

- Database migration là release engineering, không chỉ ORM feature.
- Runtime app không nên mặc định sở hữu DDL production.
- Compatibility window giúp rolling deploy và rollback an toàn hơn.

# 9. CPU profiling .NET bằng flame graph: tìm hot path thay vì tối ưu theo cảm giác

## 1. What is it?

CPU profiler sampling ghi lại call stacks theo thời gian; flame graph aggregate samples để cho thấy code path nào tiêu thụ CPU nhiều nhất. Chiều rộng biểu diễn tỷ lệ samples, không phải thời gian của một invocation đơn lẻ.

## 2. Why does it exist?

CPU 90% chỉ là symptom. Tối ưu serializer, LINQ hoặc regex theo trực giác có thể không tác động critical path. Profiling cung cấp evidence về nơi CPU thực sự được dùng.

## 3. How does it work?

Profiler lấy stack samples định kỳ. Stack giống nhau được aggregate. Hot frame rộng cho biết function xuất hiện nhiều trong sampled execution path; cần phân biệt self cost và inclusive cost.

## 4. Practical implementation

Capture trace trong representative load bằng `dotnet-trace`/profiling tool, sau đó mở trong PerfView/Speedscope-compatible viewer. So sánh cùng workload trước/sau change, không profile idle process rồi kết luận.

## 5. Real production scenario

API p99 tăng cùng CPU sau release. Flame graph cho thấy phần lớn samples nằm trong JSON serialization của graph quá lớn, không phải SQL. Root cause là endpoint mới trả entity graph dư fields.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU cao, throughput giảm. **Measure** → CPU + request rate + p95/p99. **Localize** → profiler cho hot serialization path. **Hypothesis** → over-serialization. **Test** → projection DTO nhỏ hơn. **Change** → giảm graph. **Measure again** → CPU/request và p99 giảm.

## 7. Common mistakes

Tối ưu method nhỏ không nằm hot path; đọc flame graph như timeline; profile debug build; bỏ qua allocation/GC khi CPU nằm trong GC; so hai traces với workload khác nhau.

## 8. Alternatives

`dotnet-counters` tốt để triage runtime counters; allocation profiler cho memory/GC; tracing cho latency/dependency. CPU profiler dùng khi evidence chỉ về compute hotspot.

## 9. Trade-offs

### Advantages

Evidence-driven, xác định hot path nhanh hơn code inspection.

### Costs / Risks

Profiling có overhead; sampling có thể bỏ lỡ rare events; cần representative workload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CPU cao cần đo trước khi sửa.

### Middle

Capture profile và đọc hot frames.

### Senior

Phân biệt CPU, GC, lock contention và I/O symptoms; benchmark fix.

### Technical Lead / Architect

Thiết lập performance regression workflow và capacity baselines thay vì incident-only profiling.

## 11. Key takeaway

- Hot path phải được đo, không được đoán.
- Flame graph width phản ánh sampled CPU presence.
- Luôn measure again với workload tương đương sau optimization.

# 10. ADR: ghi lại architectural decision, constraints và trade-offs để giảm knowledge loss

## 1. What is it?

Architecture Decision Record (ADR) là tài liệu ngắn ghi một quyết định kỹ thuật quan trọng: context, constraints, options, decision, trade-offs và consequences. ADR không phải full architecture specification.

## 2. Why does it exist?

Sau vài tháng, team thường nhớ “chúng ta dùng Service Bus” nhưng quên vì sao không dùng direct HTTP hoặc Event Grid, assumptions nào tồn tại và khi nào quyết định cần xem lại.

## 3. How does it work?

Một ADR có lifecycle: Proposed → Accepted → Superseded/Deprecated. Nó liên kết decision với evidence tại thời điểm ra quyết định, không cố chứng minh lựa chọn là vĩnh viễn đúng.

## 4. Practical implementation

```markdown
# ADR-014: Use Service Bus for order fulfillment commands
Status: Accepted
Context: fulfillment may be unavailable for 30 minutes...
Options: synchronous HTTP, Event Grid, Service Bus
Decision: Service Bus queue
Consequences: at-least-once delivery; consumer idempotency required
Review trigger: throughput > X or ordering requirement changes
```

## 5. Real production scenario

Năm sau team muốn thay messaging stack. ADR cho thấy lựa chọn ban đầu dựa trên durable buffering và outage tolerance, giúp đánh giá liệu constraints còn tồn tại thay vì tranh luận từ đầu.

## 6. Failure scenario & troubleshooting

**Symptom** → ADR repository đầy tài liệu nhưng team không dùng. **Evidence** → records chỉ ghi “chọn X” không có context/consequences hoặc không supersede decisions cũ. **Diagnosis** → ADR trở thành bureaucracy. **Fix** → chỉ record consequential decisions, thêm review triggers và links. **Verification** → architecture review dùng ADR để giải thích trade-offs thực.

## 7. Common mistakes

Viết ADR sau quyết định chỉ để hợp thức hóa; ghi implementation detail nhỏ; không liệt kê alternatives; không cập nhật status khi superseded; biến ADR thành meeting transcript dài.

## 8. Alternatives

README/design doc đủ cho quyết định nhỏ hoặc feature-local. RFC phù hợp proposal lớn cần discussion trước. ADR phù hợp lưu durable decision history sau khi chốt.

## 9. Trade-offs

### Advantages

Giữ reasoning, onboarding nhanh hơn, giảm lặp lại tranh luận và làm technical debt có context.

### Costs / Risks

Tốn maintenance; quá nhiều ADR tạo noise; outdated status gây hiểu nhầm.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết đọc decision context thay vì chỉ copy architecture hiện tại.

### Middle

Ghi options và consequences rõ cho quyết định phạm vi feature.

### Senior

Đưa evidence, operational cost, migration path và review triggers vào decision.

### Technical Lead / Architect

Quyết định điều gì đáng record, ai sở hữu review và khi nào supersede architecture.

## 11. Key takeaway

- ADR lưu reasoning và constraints, không chỉ kết quả.
- Decision tốt phải nêu alternatives và consequences.
- ADR chỉ có giá trị khi status và review triggers còn đáng tin cậy.
