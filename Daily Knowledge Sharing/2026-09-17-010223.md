# 1. .NET ThreadPool starvation: khi `async` vẫn có thể làm server nghẹt

## 1. What is it?

ThreadPool starvation xảy ra khi application có work cần ThreadPool thread nhưng số thread khả dụng không theo kịp lượng work đang chờ. Mental model: CPU có thể chưa 100%, nhưng request vẫn xếp hàng vì worker thread đang bị giữ bởi blocking work.

## 2. Why does it exist?

.NET dùng ThreadPool để tái sử dụng thread thay vì tạo OS thread cho từng request. Điều này hiệu quả nếu I/O được await và thread được trả lại pool. Khi code dùng `.Result`, `.Wait()`, synchronous I/O hoặc lock dài, thread bị giữ trong lúc không tạo ra useful CPU work.

## 3. How does it work?

```text
HTTP requests
     │
     ▼
ThreadPool queue ──► worker threads
                       │
              blocking DB/HTTP call
                       │
                       └── thread không quay lại pool
```

ThreadPool có cơ chế tăng worker count nhưng ramp-up không phải tức thời. Vì vậy burst traffic cộng sync-over-async có thể làm p95/p99 tăng mạnh trước khi CPU chạm trần.

## 4. Practical implementation

Sai:

```csharp
public IActionResult Get()
{
    var data = _client.GetStringAsync("/catalog").Result;
    return Ok(data);
}
```

Đúng hơn:

```csharp
public async Task<IActionResult> Get(CancellationToken ct)
{
    var data = await _client.GetStringAsync("/catalog", ct);
    return Ok(data);
}
```

Với CPU-bound work, đừng mặc định bọc mọi thứ bằng `Task.Run` trong ASP.NET Core; nó vẫn tiêu thụ ThreadPool capacity.

## 5. Real production scenario

Một e-commerce API bình thường chạy 300 req/s. Sau release, một library wrapper gọi external pricing API bằng `.GetAwaiter().GetResult()`. Traffic tăng vào giờ cao điểm; request queue tăng, latency từ 150 ms lên 8 s nhưng CPU chỉ 45%. Đây là dấu hiệu điển hình cần kiểm tra ThreadPool chứ không chỉ scale CPU.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 tăng, timeout tăng, CPU chưa bão hòa.  
**Evidence** → `dotnet-counters` cho thấy ThreadPool queue length và thread count tăng; trace có nhiều thread blocked.  
**Hypothesis** → sync-over-async hoặc blocking dependency.  
**Diagnosis** → profiler/trace tìm `.Wait()`, `.Result`, synchronous DB/file/network calls.  
**Fix** → async xuyên call chain, giới hạn concurrency cho work bắt buộc blocking.  
**Verification** → load test lại và so queue length, p95/p99, throughput.

## 7. Common mistakes

Chỉ tăng `MinThreads`; dùng `Task.Run` để che synchronous I/O; nhìn CPU thấp rồi kết luận server còn khỏe; convert controller thành `async` nhưng tầng repository vẫn blocking.

## 8. Alternatives

Nếu dependency chỉ có synchronous API, có thể cô lập bằng bounded worker/concurrency limit. Với CPU-heavy jobs, đẩy sang Worker Service/queue thường an toàn hơn giữ request thread lâu.

## 9. Trade-offs

### Advantages

Async I/O tăng khả năng phục vụ concurrent requests mà không cần tương ứng một thread cho mỗi request.

### Costs / Risks

Async propagation làm API surface rộng hơn; concurrency quá cao vẫn có thể phá database/external dependency. Không blocking thread không đồng nghĩa downstream có infinite capacity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `await` giải phóng thread trong thời gian chờ I/O; nó không làm code “chạy nhanh hơn” một cách tự động.

### Middle

Viết async end-to-end, truyền `CancellationToken`, tránh `.Result`/`.Wait()`.

### Senior

Nhận diện starvation bằng metrics/traces và phân biệt với CPU saturation, connection-pool exhaustion hoặc downstream latency.

### Technical Lead / Architect

Thiết kế concurrency budget: request path nào được phép chạy CPU-heavy, dependency nào cần bulkhead, workload nào nên tách khỏi web process.

## 11. Key takeaway

- `async` chỉ hữu ích khi call chain thực sự non-blocking.
- CPU thấp không loại trừ ThreadPool starvation.
- Chẩn đoán bằng queue/thread/trace evidence, không bằng cảm giác.

# 2. ASP.NET Core `ProblemDetails`: biến error contract thành API boundary ổn định

## 1. What is it?

`ProblemDetails` là representation chuẩn cho HTTP API errors, dựa trên problem details format. Mental model: exception là implementation detail; error response là public contract với client.

## 2. Why does it exist?

Nếu mỗi endpoint trả `{ message }`, `{ error }`, string hoặc stack trace khác nhau, frontend và integration client phải viết branching logic theo từng API. Một error envelope ổn định giúp client xử lý status, error type và correlation metadata nhất quán.

## 3. How does it work?

```text
Exception / validation failure
          │
          ▼
Exception handler / status-code mapping
          │
          ▼
ProblemDetails
(type, title, status, detail, instance, extensions)
          │
          ▼
Client
```

Không phải mọi exception đều là `500`; mapping phải dựa trên semantic boundary: not found, conflict, validation, unauthorized, dependency failure.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();
app.UseExceptionHandler();

app.MapGet("/orders/{id:int}", async (int id, AppDbContext db) =>
{
    var order = await db.Orders.FindAsync(id);
    return order is null
        ? Results.Problem(statusCode: 404, title: "Order not found")
        : Results.Ok(order);
});
```

Production response không nên chứa stack trace hoặc SQL text.

## 5. Real production scenario

Vue.js frontend và mobile app cùng gọi Order API. Khi API chuẩn hóa `409` cho optimistic concurrency conflict và `400` cho validation, cả hai client có thể dùng shared error-handling policy thay vì parse message text.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend hiển thị generic error sau release.  
**Evidence** → response shape thay đổi hoặc middleware trả HTML error page.  
**Diagnosis** → exception handler ordering sai hoặc reverse proxy/application environment trả response khác nhau.  
**Fix** → central mapping, contract test, không expose raw exception.  
**Verification** → integration tests assert status + media type + stable fields.

## 7. Common mistakes

Luôn trả `200` kèm `success=false`; trả exception message cho client; dùng `500` cho business conflict; nhét domain-specific fields tùy tiện mà không version/contract-test.

## 8. Alternatives

Custom error envelope có thể hợp lý nếu organization đã có contract mạnh. Nhưng nếu không có yêu cầu đặc biệt, chuẩn hóa trên `ProblemDetails` giảm custom protocol surface.

## 9. Trade-offs

### Advantages

Consistent contract, dễ observability và client integration.

### Costs / Risks

Central mapper có thể trở thành “god switch” nếu domain errors không được model rõ; quá nhiều extension fields tạo coupling mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt exception nội bộ với HTTP response public.

### Middle

Map validation/not-found/conflict đúng status code và viết integration tests.

### Senior

Thiết kế error taxonomy, correlation ID và security boundary cho error details.

### Technical Lead / Architect

Quyết định contract dùng chung giữa services, backward compatibility và ownership khi error semantics thay đổi.

## 11. Key takeaway

- Error response là API contract, không phải dump exception.
- Status code và machine-readable type quan trọng hơn message text.
- Contract tests bảo vệ client khỏi accidental breaking change.

# 3. SQL Server deadlock: đọc wait-for graph thay vì chữa bằng retry mù

## 1. What is it?

Deadlock là chu trình chờ tài nguyên: transaction A giữ resource X và chờ Y, transaction B giữ Y và chờ X. SQL Server phải chọn một deadlock victim để phá vòng chờ.

## 2. Why does it exist?

Transactions cần locks để bảo vệ consistency. Khi nhiều transaction acquire locks theo thứ tự khác nhau, concurrency tạo ra circular wait. Đây không đơn giản là “query chậm”.

## 3. How does it work?

```text
Tx A: holds Order(1) ───── waits Customer(9)
          ▲                       │
          │                       ▼
Tx B: waits Order(1) ◄──── holds Customer(9)
```

Deadlock khác blocking: blocking có thể tự giải phóng khi blocker commit; deadlock là cycle và database phải can thiệp.

## 4. Practical implementation

Một cách giảm risk là thống nhất lock order:

```sql
BEGIN TRAN;

UPDATE dbo.Customers
SET UpdatedAt = SYSUTCDATETIME()
WHERE Id = @CustomerId;

UPDATE dbo.Orders
SET Status = @Status
WHERE Id = @OrderId;

COMMIT;
```

Mọi workflow liên quan cùng hai resource nên cố gắng access theo cùng thứ tự.

## 5. Real production scenario

Approval workflow cập nhật `Timesheet` rồi `EmployeeBalance`, trong khi payroll job cập nhật `EmployeeBalance` rồi `Timesheet`. Từng query nhanh nhưng khi chạy đồng thời, lock order đảo ngược tạo deadlock burst.

## 6. Failure scenario & troubleshooting

**Symptom** → SQL error 1205 ngẫu nhiên dưới load.  
**Evidence** → Extended Events deadlock graph.  
**Hypothesis** → transaction overlap + inconsistent lock order.  
**Diagnosis** → đọc victim/process/resource nodes; xác định statements và lock modes.  
**Fix** → consistent access order, transaction ngắn hơn, query/index/access pattern phù hợp.  
**Verification** → replay/load test và theo dõi deadlock events.

## 7. Common mistakes

Chỉ tăng timeout; retry vô hạn; thêm `NOLOCK`; mở transaction trước khi gọi external API; nhìn hai query riêng lẻ mà không nhìn transaction boundary.

## 8. Alternatives

Optimistic concurrency giải quyết lost update nhưng không thay thế toàn bộ lock behavior. Row-versioning isolation có thể giảm read/write blocking nhưng write/write conflict vẫn tồn tại.

## 9. Trade-offs

### Advantages

Transactions và locking giữ correctness mạnh.

### Costs / Risks

Transaction dài và access pattern phức tạp tăng contention. Retry có thể hữu ích cho transient deadlock nhưng phải bounded và idempotent.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deadlock là circular wait, không phải synonym của slow query.

### Middle

Giữ transaction ngắn, access resources theo thứ tự nhất quán.

### Senior

Đọc deadlock graph và liên hệ query plan, indexes, lock footprint, transaction scope.

### Technical Lead / Architect

Thiết kế transaction boundary và workload scheduling để correctness không phụ thuộc vào retry storm.

## 11. Key takeaway

- Deadlock phải được phân tích ở transaction/resource graph.
- Retry là safety net, không phải root-cause fix.
- Lock order và transaction duration là hai đòn bẩy quan trọng.

# 4. Cosmos DB partition key: data distribution, hot partition và RU economics

## 1. What is it?

Partition key quyết định cách Cosmos DB phân phối items vào logical partitions và từ đó lên physical partitions. Mental model: partition key là quyết định về **data locality + scalability boundary**, không chỉ là một indexed column.

## 2. Why does it exist?

Một node không thể scale storage và throughput vô hạn. Distributed database cần chia data/workload. Key tốt phân tán traffic nhưng vẫn giữ các query/transaction cần thiết trong boundary hợp lý.

## 3. How does it work?

```text
Requests
   │
   ├── tenant-A ─► logical partition A ─┐
   ├── tenant-B ─► logical partition B ─┼─► physical partitions
   └── tenant-C ─► logical partition C ─┘
```

Query có partition key thường được route hẹp. Cross-partition query phải fan out, tăng RU và latency.

## 4. Practical implementation

```csharp
var container = database.GetContainer("orders");

await container.CreateItemAsync(
    order,
    new PartitionKey(order.TenantId),
    cancellationToken: ct);

var response = await container.ReadItemAsync<Order>(
    order.Id,
    new PartitionKey(order.TenantId),
    cancellationToken: ct);
```

Access pattern phải được thiết kế trước schema, không phải chọn `/id` theo thói quen.

## 5. Real production scenario

Multi-tenant SaaS dùng `/tenantId`. Phần lớn tenant nhỏ, một enterprise tenant tạo 45% traffic. Logical distribution nhìn có vẻ tốt theo số tenant nhưng traffic skew tạo hot partition.

## 6. Failure scenario & troubleshooting

**Symptom** → 429 tăng ở một nhóm tenant dù tổng provisioned RU còn dư.  
**Evidence** → metrics theo partition key range cho thấy skew.  
**Diagnosis** → hot key, cross-partition query hoặc request burst.  
**Fix** → reconsider key/hierarchical partitioning, spread write pattern, autoscale phù hợp, tối ưu query.  
**Verification** → theo dõi normalized RU consumption và 429 distribution.

## 7. Common mistakes

Chọn key cardinality thấp; chọn key không xuất hiện trong query; coi autoscale là thuốc chữa hot partition; migrate production rồi mới kiểm tra access pattern.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp hơn nếu workload cần joins/relational transactions mạnh. MongoDB có sharding model khác nhưng vẫn buộc giải bài toán shard-key distribution.

## 9. Trade-offs

### Advantages

Partitioning cho horizontal scale và predictable routing khi access pattern phù hợp.

### Costs / Risks

Key sai rất khó sửa; denormalization và cross-partition operations tăng complexity/cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định data nằm và được route như thế nào.

### Middle

Thực hiện point reads/writes với key đúng và đo RU.

### Senior

Phân tích cardinality, skew, query fan-out, hot partitions và consistency needs.

### Technical Lead / Architect

Quyết định Cosmos DB có thực sự phù hợp và partition strategy có sống được với growth 10x hay không.

## 11. Key takeaway

- Partition key là architectural decision.
- Tổng RU đủ không đảm bảo không có hot partition.
- Thiết kế từ access pattern, distribution và transaction boundary.

# 5. Modular Monolith: module boundary trước khi trả operational tax của Microservices

## 1. What is it?

Modular Monolith là một deployable application nhưng chia business capability thành modules có boundary rõ. Nó không phải “monolith có nhiều folders”; giá trị nằm ở dependency rules, ownership và data/transaction boundaries.

## 2. Why does it exist?

Một monolith không có boundary dễ trở thành tightly coupled codebase. Microservices có thể tạo isolation nhưng thêm network failure, deployment orchestration, distributed tracing, eventual consistency và infrastructure cost. Modular Monolith giữ local-call simplicity trong khi ép hệ thống có module seams.

## 3. How does it work?

```text
Single deployment
┌──────────────────────────────────────┐
│ Orders       Billing       Identity  │
│   │             │              │     │
│ public API   public API     public API│
│   └──── controlled module calls ────┘│
└──────────────────────────────────────┘
```

Module không được tùy tiện query table hoặc gọi internal class của module khác.

## 4. Practical implementation

```csharp
public interface IInventoryModule
{
    Task<ReservationResult> ReserveAsync(
        ProductId productId,
        int quantity,
        CancellationToken ct);
}
```

`Orders` phụ thuộc vào contract của `Inventory`, không phụ thuộc trực tiếp `InventoryDbContext` hoặc internal entity.

## 5. Real production scenario

E-commerce team có Orders, Catalog, Inventory và Reviews. Traffic chưa đủ để justify independent scaling. Modular Monolith cho phép release một artifact, transaction local khi cần, nhưng vẫn cô lập business model để sau này extraction có seam rõ.

## 6. Failure scenario & troubleshooting

**Symptom** → thay đổi Inventory làm vỡ Orders dù “đã chia module”.  
**Evidence** → cross-module DB queries và project references vòng.  
**Diagnosis** → boundary chỉ tồn tại trong folder naming.  
**Fix** → explicit contracts, architecture tests, ownership rules, cấm direct table/entity sharing.  
**Verification** → dependency graph và tests đảm bảo forbidden references không quay lại.

## 7. Common mistakes

Một shared `Common` project chứa mọi domain type; module dùng chung DbContext rồi query tables tùy ý; đưa MediatR vào rồi gọi đó là modular architecture; tách service quá sớm vì “future scale”.

## 8. Alternatives

Layered Monolith đơn giản hơn khi domain nhỏ. Microservices hợp lý khi cần independent deployment/scaling/ownership thực sự. Modular Monolith thường là bước giữa có chi phí vận hành thấp hơn.

## 9. Trade-offs

### Advantages

Local calls, đơn giản deployment, transaction dễ hơn, boundary tốt hơn monolith tự do.

### Costs / Risks

Boundary cần discipline và automated enforcement; vẫn scale/deploy cùng process nếu chưa extract.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module đại diện business capability, không chỉ technical layer.

### Middle

Tôn trọng public contract và không bypass module boundary.

### Senior

Thiết kế module API, data ownership, transaction crossing và dependency direction.

### Technical Lead / Architect

Quyết định khi nào giữ monolith, khi nào modularize và bằng chứng nào thực sự justify service extraction.

## 11. Key takeaway

- Boundary quan trọng hơn số process.
- Microservices không phải mặc định “senior hơn”.
- Modular Monolith tạo extraction seam mà chưa trả distributed-systems tax.

# 6. Azure App Service deployment slots: zero/low-downtime release và hidden state khi swap

## 1. What is it?

Deployment slot là live environment riêng trong cùng App Service cho phép deploy candidate version vào staging rồi swap với production. Mental model: swap là chuyển routing/configuration semantics giữa hai running slots, không đơn giản là copy files.

## 2. Why does it exist?

Deploy trực tiếp lên production có thể gây cold start, partial file replacement hoặc không có điểm validation trước khi traffic thật đến. Slot cho phép warm-up và smoke test trước cutover.

## 3. How does it work?

```text
Build artifact
     │
     ▼
Staging slot ── warm-up / smoke test
     │
     ▼ swap
Production slot ◄── user traffic
```

Một số settings có thể được đánh dấu slot-specific. Nếu hiểu sai sticky settings, staging có thể kết nối production dependency hoặc ngược lại.

## 4. Practical implementation

Pipeline nên theo flow:

```text
Deploy staging
→ wait for readiness
→ run smoke tests
→ swap
→ validate production telemetry
→ rollback/swap back if needed
```

Application phải đọc secrets/config từ environment/Key Vault thay vì hard-code theo slot name.

## 5. Real production scenario

ASP.NET Core API deploy version mới có JIT/startup cost 20 giây. Staging slot được warm trước; sau smoke test, swap giảm user-visible cold-start. Nhưng database migration vẫn phải backward-compatible vì old/new app có thể tồn tại trong transition.

## 6. Failure scenario & troubleshooting

**Symptom** → swap thành công nhưng production trả 500.  
**Evidence** → Application Insights cho thấy connection string hoặc Key Vault access sai.  
**Diagnosis** → slot setting classification sai hoặc Managed Identity/secret configuration khác staging expectation.  
**Fix** → explicit slot settings, pre-swap validation, backward-compatible config/schema.  
**Verification** → synthetic health test và dependency telemetry sau swap.

## 7. Common mistakes

Coi slot là full isolated environment; chạy destructive migration trước swap; không warm application; smoke test chỉ `/health` nhưng không kiểm tra critical dependency; không có rollback criterion.

## 8. Alternatives

Blue-Green trên Container Apps/Kubernetes cho control rộng hơn nhưng operational complexity cao hơn. Direct deployment đơn giản hơn cho low-risk internal app.

## 9. Trade-offs

### Advantages

Pre-production validation trên runtime gần production, nhanh rollback, giảm downtime.

### Costs / Risks

Config/state complexity; schema compatibility vẫn là trách nhiệm application; slot có cost và giới hạn theo App Service plan.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu staging slot là running deployment target riêng.

### Middle

Deploy, smoke test, swap và biết slot settings.

### Senior

Thiết kế backward-compatible release, telemetry gate và rollback.

### Technical Lead / Architect

Quyết định deployment strategy dựa trên blast radius, RTO, database changes và team operational maturity.

## 11. Key takeaway

- Slot swap không giải quyết schema incompatibility.
- Release success phải được xác nhận bằng health + telemetry.
- Configuration ownership là phần của deployment architecture.

# 7. IIS Application Pool recycle: process lifetime, warm-up và production outage khó thấy

## 1. What is it?

IIS Application Pool cô lập web applications trong worker process (`w3wp.exe`). Recycle thay worker process theo policy hoặc event. Mental model: web app process không sống mãi; application phải chịu được restart.

## 2. Why does it exist?

Process isolation giúp security, fault containment và lifecycle management. Recycling có thể giải phóng process state hoặc áp dụng configuration, nhưng cũng làm mất in-memory state và gây warm-up.

## 3. How does it work?

```text
IIS
 └─ App Pool
     ├─ old w3wp.exe ── draining
     └─ new w3wp.exe ── startup / warm-up
```

Overlap recycling có thể giữ old process trong lúc new process khởi động, nhưng startup failure vẫn gây outage.

## 4. Practical implementation

ASP.NET Core app sau IIS nên giữ session/cache quan trọng ngoài process khi cần multi-instance/restart tolerance. Startup không nên phụ thuộc vào long-running migration hoặc remote call không bounded timeout.

```csharp
app.MapHealthChecks("/health/ready");
```

Readiness nên phản ánh dependency bắt buộc cho traffic, nhưng không biến mọi optional dependency thành lý do làm app unavailable.

## 5. Real production scenario

Legacy enterprise site lưu user workflow trong `IMemoryCache`. Nightly recycle làm hàng loạt users mất state lúc 02:00. Bug bị hiểu nhầm là “random logout” vì không ai correlate IIS recycle events với application logs.

## 6. Failure scenario & troubleshooting

**Symptom** → 502/503 ngắn theo chu kỳ.  
**Evidence** → Windows Event Viewer/IIS logs trùng thời điểm worker recycle; app startup logs chậm.  
**Hypothesis** → recycle + cold startup.  
**Diagnosis** → kiểm tra recycle settings, idle timeout, memory limits, startup dependencies.  
**Fix** → đúng lifecycle policy, preload/warm-up, externalize critical state.  
**Verification** → controlled recycle trong staging và quan sát traffic continuity.

## 7. Common mistakes

Dùng recycle định kỳ để “fix memory leak”; lưu critical state trong process; không log startup/shutdown; process restart làm mất background job nhưng không có recovery.

## 8. Alternatives

Azure App Service quản lý hosting lifecycle cao hơn nhưng process restart vẫn tồn tại. Containers thay packaging model, không xóa requirement về stateless/restart-safe application.

## 9. Trade-offs

### Advantages

Isolation và lifecycle control đơn giản cho Windows-hosted enterprise apps.

### Costs / Risks

Warm-up, hidden process state và Windows-specific operations cần được hiểu rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết IIS worker process có thể restart độc lập với server.

### Middle

Đọc IIS logs/Event Viewer và cấu hình app pool cơ bản.

### Senior

Thiết kế app restart-safe, correlate recycle với telemetry, không chữa leak bằng restart mù.

### Technical Lead / Architect

Đánh giá modernization/hosting strategy và loại bỏ assumptions rằng process lifetime = business state lifetime.

## 11. Key takeaway

- Production process luôn có thể restart.
- Critical state không nên phụ thuộc vào lifetime của `w3wp.exe`.
- Recycle là lifecycle event cần observability, không phải memory-leak strategy.

# 8. Akamai/CDN `Cache-Control`: freshness contract giữa browser, edge và origin

## 1. What is it?

`Cache-Control` mô tả caching policy cho response qua browser/shared caches như CDN. Mental model: CDN không “tự biết” dữ liệu nào được phép stale; origin phải phát tín hiệu freshness đúng.

## 2. Why does it exist?

Không cache làm mọi request về origin, tăng latency và load. Cache quá lâu làm user thấy stale content. HTTP caching tạo contract cân bằng latency, origin cost và freshness.

## 3. How does it work?

```text
Browser
   │ cache lookup
   ▼
Akamai Edge
   │ miss / revalidate
   ▼
Origin / ASP.NET Core
   │
   ▼
CMS / API / DB
```

`max-age` thường điều khiển freshness cho client cache; shared-cache policy có thể dùng `s-maxage`. `ETag`/`Last-Modified` hỗ trợ revalidation.

## 4. Practical implementation

```csharp
app.MapGet("/catalog/{slug}", async (string slug, CatalogService service) =>
{
    var page = await service.GetAsync(slug);
    return Results.Ok(page);
})
.WithMetadata(new ResponseCacheAttribute
{
    Duration = 60,
    Location = ResponseCacheLocation.Any
});
```

Trong thực tế cần kiểm tra headers thực tế tại edge; middleware metadata không đảm bảo CDN policy nếu Akamai property rules override chúng.

## 5. Real production scenario

CMS marketing page thay banner. Origin trả nội dung mới ngay nhưng Akamai vẫn giữ object cũ 30 phút. Editor nghĩ CMS publish lỗi, trong khi vấn đề nằm ở edge freshness/invalidation.

## 6. Failure scenario & troubleshooting

**Symptom** → một số users thấy nội dung cũ.  
**Evidence** → origin response mới nhưng edge response có `Age` lớn/cache hit.  
**Hypothesis** → TTL/purge/key mismatch.  
**Diagnosis** → so headers browser → edge → origin, kiểm tra cache key và Akamai rules.  
**Fix** → policy đúng, purge targeted hoặc versioned URL cho static assets.  
**Verification** → request từ edge locations và kiểm tra `Age`/fresh content.

## 7. Common mistakes

Cache personalized response ở shared cache; dùng purge như normal application flow; TTL quá ngắn làm CDN gần như vô nghĩa; query-string cache key không nhất quán; chỉ clear browser cache khi stale nằm ở edge.

## 8. Alternatives

Browser cache chỉ giảm repeat request của một client. Reverse-proxy cache gần origin giảm app load nhưng không giảm global network distance như CDN.

## 9. Trade-offs

### Advantages

Latency thấp hơn, origin load thấp hơn, resilience tốt hơn cho cacheable content.

### Costs / Risks

Freshness/invalidation complexity và security risk nếu cache private data sai boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser cache và CDN cache là hai tầng khác nhau.

### Middle

Đọc `Cache-Control`, `Age`, `ETag` và dùng DevTools/curl để kiểm tra.

### Senior

Thiết kế cache key, TTL, purge strategy và personalized-content boundaries.

### Technical Lead / Architect

Quyết định freshness SLA nào chấp nhận được và cache policy nào giảm cost mà không phá correctness.

## 11. Key takeaway

- Caching là freshness contract, không chỉ performance switch.
- Debug stale content phải xác định chính xác cache layer.
- Shared cache tuyệt đối cần boundary rõ với personalized data.

# 9. Third-party webhook integration: authenticity, idempotency và eventual processing

## 1. What is it?

Webhook là callback HTTP từ external provider khi event xảy ra. Mental model: đây là **untrusted, retryable external message delivery qua HTTP**, không phải một request nội bộ đáng tin cậy.

## 2. Why does it exist?

Polling liên tục lãng phí requests và tăng latency phát hiện thay đổi. Webhook cho provider push event gần real-time, nhưng đổi lại consumer phải xử lý duplicate, out-of-order, signature verification và provider outage/retry behavior.

## 3. How does it work?

```text
Provider
   │ signed webhook
   ▼
Webhook endpoint
   │ verify + persist/deduplicate
   ▼
Queue / durable inbox
   │
   ▼
Business processor
```

Endpoint nên acknowledge nhanh sau khi đã durable-capture event; business processing dài không nên giữ provider request mở.

## 4. Practical implementation

```csharp
app.MapPost("/webhooks/payments", async (
    HttpRequest request,
    IWebhookVerifier verifier,
    IInboxStore inbox,
    CancellationToken ct) =>
{
    using var reader = new StreamReader(request.Body);
    var payload = await reader.ReadToEndAsync(ct);

    if (!verifier.IsValid(payload, request.Headers))
        return Results.Unauthorized();

    var eventId = verifier.GetEventId(payload);
    await inbox.TryStoreAsync(eventId, payload, ct); // unique eventId

    return Results.Ok();
});
```

Signature verification phải dùng raw payload theo provider specification; parse/re-serialize trước verification có thể làm signature mismatch.

## 5. Real production scenario

Review provider gửi `review.updated`. Consumer timeout sau khi đã lưu event nên provider retry. Nếu handler không idempotent, cùng review bị apply hai lần hoặc tạo duplicate notification.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate business actions.  
**Evidence** → cùng provider event ID xuất hiện nhiều request.  
**Hypothesis** → at-least-once retry.  
**Diagnosis** → endpoint side effect xảy ra trước deduplication hoặc dedupe chỉ in-memory.  
**Fix** → durable unique event ID/inbox, idempotent processing, fast acknowledgement.  
**Verification** → replay cùng payload nhiều lần và assert một business effect.

## 7. Common mistakes

Tin IP address thay signature; log secrets/raw PII; xử lý business logic 30 giây trong HTTP callback; dedupe bằng cache TTL quá ngắn; assume ordering; trả `200` trước khi event được lưu durable.

## 8. Alternatives

Polling đơn giản hơn khi provider không có reliable webhook hoặc freshness không quan trọng. Managed messaging tốt hơn khi cả hai phía thuộc cùng architecture, nhưng third-party thường chỉ expose HTTP.

## 9. Trade-offs

### Advantages

Near-real-time, ít polling traffic, decoupled trigger.

### Costs / Risks

Security verification, retries, duplicates, schema evolution và observability trở thành trách nhiệm consumer.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu webhook có thể đến nhiều lần và không mặc định trusted.

### Middle

Verify signature, persist event, xử lý idempotently.

### Senior

Thiết kế replay, deduplication, ordering tolerance, metrics và dead-letter/recovery flow.

### Technical Lead / Architect

Đặt ownership boundary: provider contract, failure SLA, data retention, security secret rotation và fallback khi webhook ngừng đến.

## 11. Key takeaway

- Webhook phải được coi như external at-least-once message.
- Verify trước, durable-capture sớm, process async khi phù hợp.
- Idempotency là correctness requirement, không phải optimization.

# 10. Git `bisect`: biến regression hunting từ đoán commit thành binary search có bằng chứng

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên làm behavior chuyển từ good sang bad. Mental model: thay vì đọc tuần tự 200 commits, ta liên tục chia đôi search space bằng một test có kết quả pass/fail.

## 2. Why does it exist?

Regression thường xuất hiện trong khoảng giữa một release tốt và release lỗi. Manual guessing dựa vào commit message dễ bias và tốn thời gian. Binary search giảm số lần kiểm tra từ tuyến tính xuống logarithmic nếu history/test đủ rõ.

## 3. How does it work?

```text
Good ------------------------------ Bad
                  test midpoint
        Good ------|--------------- Bad
                         test midpoint
                         ...
```

Với 256 commits, lý tưởng chỉ cần khoảng 8 bước phân loại.

## 4. Practical implementation

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0

# chạy test ở commit Git checkout
git bisect good   # hoặc: git bisect bad

# kết thúc
git bisect reset
```

Nếu có deterministic test:

```bash
git bisect run dotnet test tests/Regression.Tests/Regression.Tests.csproj
```

Exit code `0` được xem là good; non-zero thường là bad theo `bisect run` semantics.

## 5. Real production scenario

Sau 3 tuần development, API export Excel tăng memory gấp 4 lần. Release trước không lỗi. Team viết regression test đo behavior đủ ổn định rồi bisect giữa release tag và HEAD, tìm ra commit thay streaming bằng buffering toàn file.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ tới commit không build được hoặc test flaky.  
**Evidence** → midpoint không thể phân loại good/bad.  
**Diagnosis** → history có intermediate broken states hoặc test không deterministic.  
**Fix** → `git bisect skip` cho commit không test được; cải thiện regression test; chọn narrower known-good range.  
**Verification** → checkout culprit parent/commit và reproduce behavior transition.

## 7. Common mistakes

Dùng “app có vẻ ổn” thay deterministic criterion; chọn known-good sai; quên dependency/database state khác giữa commits; kết luận culprit mà không verify parent vs commit.

## 8. Alternatives

`git log`, `git blame` hữu ích khi đã biết file/line nghi vấn. Profiler/traces tìm runtime bottleneck. `bisect` mạnh nhất khi có clear good/bad predicate nhưng chưa biết code area.

## 9. Trade-offs

### Advantages

Nhanh, evidence-driven, có thể automation bằng test command.

### Costs / Risks

History phải build/test được tương đối; database migrations/external dependencies có thể làm old commits khó reproduce.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết good/bad commit và cách reset bisect.

### Middle

Dùng `bisect` với repeatable test để tìm regression.

### Senior

Xây regression harness, kiểm soát environment và phân biệt culprit commit với root architectural cause.

### Technical Lead / Architect

Tạo engineering practice để release tags, reproducible builds và automated tests làm incident investigation nhanh hơn về lâu dài.

## 11. Key takeaway

- `git bisect` biến regression search thành binary search.
- Chất lượng kết quả phụ thuộc vào deterministic good/bad test.
- Sau khi tìm commit, vẫn phải phân tích root cause và thêm regression protection.
