# 1. .NET `Channel<T>`: bounded backpressure cho producer/consumer

## 1. What is it?

`Channel<T>` là async producer/consumer primitive trong .NET. Mental model quan trọng không phải “queue nhanh”, mà là **ranh giới điều tiết tốc độ** giữa producer và consumer. Với bounded channel, producer phải chậm lại khi downstream không theo kịp.

## 2. Why does it exist?

Một API có thể nhận 5.000 work items/s trong khi worker chỉ xử lý 1.000/s. Nếu dùng unbounded in-memory queue, backlog trở thành memory growth. Nếu xử lý trực tiếp, request latency bị kéo theo worker. Backpressure giúp hệ thống biểu diễn capacity hữu hạn.

## 3. How does it work?

```text
Producer ──WriteAsync──► [ bounded Channel ] ──ReadAllAsync──► Consumer
                              full
                               │
                               └── producer waits / rejects / drops theo policy
```

`BoundedChannelFullMode` quyết định khi đầy: `Wait`, `DropNewest`, `DropOldest`, `DropWrite`. Đây là business/reliability decision, không chỉ tuning.

## 4. Practical implementation

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true
});

await channel.Writer.WriteAsync(job, ct);

await foreach (var item in channel.Reader.ReadAllAsync(stoppingToken))
{
    await processor.ProcessAsync(item, stoppingToken);
}
```

Nếu work phải survive process restart, `Channel<T>` không phải durable queue; dùng Service Bus/RabbitMQ/Kafka phù hợp hơn.

## 5. Real production scenario

File-processing API nhận burst upload metadata. Một bounded channel giới hạn concurrent downstream parsing. Khi worker chậm, ingress bị backpressure thay vì process ăn hết RAM.

## 6. Failure scenario & troubleshooting

**Symptom** → request latency tăng mạnh nhưng CPU thấp.  
**Evidence** → channel luôn gần capacity, `WriteAsync` wait dài.  
**Hypothesis** → consumer throughput thấp hơn arrival rate.  
**Diagnosis** → đo queue depth, enqueue wait, processing duration và dependency latency.  
**Fix** → tăng consumer capacity có kiểm soát, giảm producer rate hoặc chuyển durable async workflow.  
**Verification** → backlog hội tụ sau burst và memory ổn định.

## 7. Common mistakes

Dùng unbounded channel mặc định; fire-and-forget `WriteAsync`; không complete writer khi shutdown; tăng consumer count mà bỏ qua DB connection pool; dùng channel cho work cần durability.

## 8. Alternatives

`ConcurrentQueue<T>` không có async backpressure. `BlockingCollection<T>` phù hợp synchronous/blocking model cũ hơn. Azure Service Bus phù hợp cross-process durable messaging.

## 9. Trade-offs

### Advantages

Allocation/coordination hiệu quả, async-native, backpressure rõ ràng.

### Costs / Risks

In-memory, mất dữ liệu khi process chết; capacity và full-mode phải được thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu producer/consumer và bounded queue.

### Middle
Implement cancellation, completion và worker loop.

### Senior
Đo arrival/service rate, queue depth và downstream capacity.

### Technical Lead / Architect
Quyết định khi nào in-process buffering đủ và khi nào cần durable broker.

## 11. Key takeaway

- Queue không có bound có thể chỉ chuyển overload thành memory failure.
- Backpressure là reliability mechanism.
- `Channel<T>` không thay durable messaging.

# 2. ASP.NET Core `ProblemDetails`: error contract ổn định thay vì exception-shaped API

## 1. What is it?

`ProblemDetails` là HTTP error representation theo RFC 7807/9457 family. Mental model: exception là implementation detail; API error là **public contract** dành cho client.

## 2. Why does it exist?

Nếu controller trả raw exception message hoặc mỗi endpoint tự invent JSON lỗi, client phải parse nhiều shapes và server có nguy cơ leak stack trace/internal data.

## 3. How does it work?

```text
Exception / validation failure
        ↓
central error mapping
        ↓
HTTP status + ProblemDetails
        ↓
client handles stable error type/code
```

Transport status (`404`, `409`, `422`, `500`) và machine-readable business code nên có semantics rõ.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();
app.UseExceptionHandler();

app.MapPost("/orders", async (...) =>
{
    if (duplicate)
        return Results.Problem(
            statusCode: 409,
            title: "Order conflict",
            extensions: new Dictionary<string, object?>
            {
                ["code"] = "order.already_exists"
            });

    // ...
});
```

Không đưa SQL text, stack trace, tokens hoặc PII vào production response.

## 5. Real production scenario

Web và mobile client cùng consume approval API. Stable `code` cho phép cả hai hiển thị đúng UX dù backend refactor exception hierarchy.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend coi mọi lỗi là “Something went wrong”.  
**Evidence** → backend trả 500 cho validation, conflict và dependency timeout.  
**Hypothesis** → error taxonomy không tồn tại.  
**Diagnosis** → inventory status/code theo endpoint.  
**Fix** → central mapping và documented error contract.  
**Verification** → contract tests cho representative failures.

## 7. Common mistakes

Trả 200 với `{ success:false }`; expose exception message; dùng 500 cho lỗi business; thay error code tùy tiện; duplicate mapping trong controllers.

## 8. Alternatives

Custom envelope có thể hợp legacy API nhưng phải duy trì semantics. gRPC dùng status/details khác. Dù format nào, principle vẫn là implementation error ≠ public contract.

## 9. Trade-offs

### Advantages

Client integration ổn định, observability và security tốt hơn.

### Costs / Risks

Cần taxonomy, backward compatibility và mapping discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt HTTP status và exception.

### Middle
Implement centralized mapping.

### Senior
Thiết kế retryable/non-retryable semantics và tránh information leakage.

### Technical Lead / Architect
Định nghĩa organization-wide error contract/versioning policy.

## 11. Key takeaway

- Exception không phải API contract.
- Status code + stable machine code phải có semantics.
- Error response cũng cần compatibility discipline.

# 3. EF Core optimistic concurrency: `rowversion`, lost update và retry đúng nghĩa

## 1. What is it?

Optimistic concurrency giả định conflict hiếm, không lock row suốt thời gian user chỉnh sửa. Khi save, persistence layer xác minh row vẫn ở version đã đọc.

## 2. Why does it exist?

Hai users đọc cùng employee record. A sửa salary, B sửa title. Nếu B save snapshot cũ bằng unconditional update, thay đổi của A có thể bị ghi đè.

## 3. How does it work?

```text
Read Id=42, Version=7
        ↓
UPDATE ... WHERE Id=42 AND Version=7
        ↓
0 rows → conflict
1 row  → success, new version
```

EF Core chuyển zero affected rows của concurrency-token update thành `DbUpdateConcurrencyException`.

## 4. Practical implementation

```csharp
public sealed class Employee
{
    public int Id { get; set; }
    public string Title { get; set; } = "";
    [Timestamp]
    public byte[] Version { get; set; } = [];
}

try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new { code = "employee.concurrent_update" });
}
```

Không tự động retry business update với stale input; thường phải reload/merge hoặc yêu cầu client quyết định.

## 5. Real production scenario

HR portal có nhiều operators sửa employee profile. Concurrency token biến silent lost update thành explicit conflict.

## 6. Failure scenario & troubleshooting

**Symptom** → retry policy chạy lại `SaveChanges` ba lần nhưng vẫn conflict.  
**Evidence** → original version vẫn cũ.  
**Hypothesis** → team nhầm concurrency conflict với transient DB error.  
**Diagnosis** → inspect original/current/database values.  
**Fix** → define merge/reload policy.  
**Verification** → concurrent integration test chứng minh không lost update.

## 7. Common mistakes

Retry blind; dùng timestamp client làm token; catch rồi ignore; token chỉ check ở API nhưng SQL update unconditional; giữ DbContext quá lâu.

## 8. Alternatives

Pessimistic locking phù hợp short critical DB workflows nhưng không phù hợp user edit kéo dài. Application-managed version hữu ích khi provider không có native rowversion.

## 9. Trade-offs

### Advantages

Không giữ long lock, conflict explicit.

### Costs / Risks

Application phải định nghĩa conflict UX và merge semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu lost update.

### Middle
Configure token và handle exception.

### Senior
Phân biệt transient retry với semantic conflict.

### Technical Lead / Architect
Định nghĩa concurrency contract xuyên UI/API/database.

## 11. Key takeaway

- Concurrency conflict là business state, không nhất thiết là transient failure.
- Retry mù có thể ghi đè intent mới hơn.
- Atomic version check phải nằm trong write.

# 4. PostgreSQL keyset pagination: latency ổn định khi dataset lớn

## 1. What is it?

Keyset pagination lấy page tiếp theo dựa trên giá trị sort cuối cùng thay vì bỏ qua N rows bằng `OFFSET`. Mental model: **seek từ cursor**, không đếm rồi discard toàn bộ prefix.

## 2. Why does it exist?

`OFFSET 500000 LIMIT 50` vẫn buộc database đi qua lượng lớn rows/index entries trước khi trả 50 rows. Latency thường tăng theo page depth.

## 3. How does it work?

```sql
SELECT id, created_at, total
FROM orders
WHERE (created_at, id) < (@created_at, @id)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Composite cursor cần deterministic ordering; `id` làm tie-breaker khi nhiều rows có cùng timestamp.

## 4. Practical implementation

Index phải hỗ trợ access pattern:

```sql
CREATE INDEX ix_orders_created_id
ON orders (created_at DESC, id DESC);
```

Cursor API nên encode values opaque cho client thay vì expose implementation quá chặt.

## 5. Real production scenario

Audit log có 80 triệu rows. Page 1 nhanh nhưng page 10.000 bằng offset chậm hàng giây. Keyset giữ work gần page size.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate/missing items khi user paging.  
**Evidence** → sort chỉ theo non-unique `created_at`.  
**Hypothesis** → cursor order không deterministic.  
**Diagnosis** → tìm equal sort values quanh page boundary.  
**Fix** → thêm stable unique tie-breaker.  
**Verification** → paging toàn test dataset không duplicate/missing trong defined consistency model.

## 7. Common mistakes

Cursor chỉ chứa timestamp; index order không match query; cho phép arbitrary jump-to-page nhưng vẫn chọn keyset; không định nghĩa behavior khi rows được insert giữa pages.

## 8. Alternatives

Offset pagination đơn giản và tốt cho small datasets/jump-to-page UX. Snapshot/export workflow phù hợp khi cần consistent traversal rất lớn.

## 9. Trade-offs

### Advantages

Latency ổn định hơn và ít wasted I/O.

### Costs / Risks

Không tự nhiên cho random page number; cursor contract phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `LIMIT/OFFSET`.

### Middle
Implement deterministic cursor.

### Senior
Đọc execution plan và index access.

### Technical Lead / Architect
Chọn pagination theo UX + scale, không theo convention.

## 11. Key takeaway

- Deep offset có cost dù chỉ trả ít rows.
- Keyset cần deterministic ordering.
- Pagination design là API + database decision.

# 5. Elasticsearch mapping evolution: vì sao đổi field type thường cần reindex

## 1. What is it?

Elasticsearch mapping định nghĩa cách fields được index. Một field đã index dưới representation nhất định thường không thể đổi type/analyzer in-place theo cách làm dữ liệu cũ tự biến đổi.

## 2. Why does it exist?

Inverted index và doc values được xây lúc indexing. Đổi `keyword` thành `text` không thể retroactively tokenize dữ liệu đã index.

## 3. How does it work?

```text
Primary DB → index-v1(mapping A)
                ↓ reindex
             index-v2(mapping B)
                ↓
             alias switch
```

Alias giúp consumer dùng logical name trong khi physical index thay đổi.

## 4. Practical implementation

```json
PUT products-v2
{
  "mappings": {
    "properties": {
      "name": { "type": "text", "fields": { "raw": { "type": "keyword" } } }
    }
  }
}
```

Sau backfill và validation, atomically switch alias tới `products-v2`.

## 5. Real production scenario

Product search cần sorting exact name nhưng field cũ chỉ có analyzed text. Team tạo multi-field mapping mới, reindex rồi đổi alias.

## 6. Failure scenario & troubleshooting

**Symptom** → v2 index thiếu products mới phát sinh trong lúc backfill.  
**Evidence** → sync pipeline chỉ ghi v1.  
**Hypothesis** → migration không xử lý concurrent writes.  
**Diagnosis** → compare DB watermark/index counts/events.  
**Fix** → dual-write/change capture hoặc replay delta trước cutover.  
**Verification** → consistency checks trước alias switch.

## 7. Common mistakes

Sửa mapping rồi kỳ vọng old docs đổi; reindex production không capacity plan; switch alias trước validation; coi Elasticsearch là transactional truth.

## 8. Alternatives

Runtime fields giải quyết một số derived use cases nhưng có query cost. SQL full-text có thể đủ cho search đơn giản và giảm operational component.

## 9. Trade-offs

### Advantages

Versioned indices cho migration/rollback rõ.

### Costs / Risks

Double storage, reindex load và synchronization complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu mapping ảnh hưởng indexing.

### Middle
Tạo versioned index và alias.

### Senior
Thiết kế delta synchronization và capacity-safe migration.

### Technical Lead / Architect
Quyết định search engine có đáng operational burden và ai sở hữu source of truth.

## 11. Key takeaway

- Mapping là storage/indexing contract.
- Reindex migration phải xử lý writes trong lúc backfill.
- Alias switch chỉ là cutover, không tự giải consistency.

# 6. Modular Monolith: module boundary, data ownership và transaction boundary

## 1. What is it?

Modular Monolith là một deployable application nhưng được chia thành modules có business ownership và dependency boundaries rõ. Nó không phải chỉ là nhiều folders trong cùng solution.

## 2. Why does it exist?

Một monolith không boundary dễ trở thành shared-everything codebase. Microservices lại thêm network, deployment, observability và eventual consistency trước khi business cần.

## 3. How does it work?

```text
Single deployment
├── Orders module ── owns Orders data/model
├── Billing module ─ owns Billing data/model
└── Catalog module ─ owns Catalog data/model

Cross-module access → explicit contract, không query repository nội bộ tùy tiện
```

Modules có thể dùng cùng physical database nhưng ownership vẫn logical; cross-module joins làm migration sang independent services khó hơn.

## 4. Practical implementation

```csharp
public interface IInventoryAvailability
{
    Task<bool> CanReserveAsync(ProductId productId, int quantity, CancellationToken ct);
}
```

Orders phụ thuộc contract public của Inventory, không phụ thuộc `InventoryDbContext` hoặc internal entity.

## 5. Real production scenario

SaaS 8 developers có Orders, Billing, Notifications. Một deployable artifact giữ operations đơn giản nhưng module contracts giúp teams thay đổi independently hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → “modular” solution nhưng sửa Billing làm compile errors khắp Orders.  
**Evidence** → modules reference internal entities/repositories trực tiếp.  
**Hypothesis** → boundary chỉ tồn tại ở folder.  
**Diagnosis** → dependency graph và database ownership review.  
**Fix** → public contracts, internal visibility, architecture tests.  
**Verification** → module internals refactor mà consumers không đổi.

## 7. Common mistakes

Một generic repository dùng chung toàn hệ thống; shared domain entities; event bus in-process nhưng giả vờ network semantics; tách module quá nhỏ.

## 8. Alternatives

Layered Monolith đủ cho domain đơn giản. Microservices phù hợp khi independent scaling/deployment/ownership thực sự cần và team chịu được operations.

## 9. Trade-offs

### Advantages

Boundary tốt với deployment/transaction simplicity.

### Costs / Risks

Boundary enforcement cần discipline; shared process/database vẫn có coupling opportunities.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu module theo business responsibility.

### Middle
Giữ dependency qua public contract.

### Senior
Reason về data/transaction ownership.

### Technical Lead / Architect
Quyết định module nào đáng tách service dựa trên operational/business pressure.

## 11. Key takeaway

- Modular Monolith không phải folder convention.
- Data ownership quyết định boundary mạnh hơn project layout.
- Microservices nên là response cho pressure thật, không phải maturity badge.

# 7. Azure Service Bus lock settlement: duplicate delivery, lock loss và idempotent consumer

## 1. What is it?

Ở `PeekLock`, receiver khóa message tạm thời, xử lý rồi `Complete`. Nếu lock hết hạn hoặc process chết trước settlement, message có thể được delivery lại. Mental model: **at-least-once processing**, không phải exactly-once side effect.

## 2. Why does it exist?

Broker không thể biết chắc business transaction của consumer đã commit nếu connection mất đúng thời điểm. Redelivery ưu tiên không mất message, đổi lại consumer phải chịu duplicate.

## 3. How does it work?

```text
Receive + lock
   ↓
business work
   ↓
Complete ──► remove

crash / lock expiry
   ↓
message visible again
```

## 4. Practical implementation

```csharp
processor.ProcessMessageAsync += async args =>
{
    var id = args.Message.MessageId;
    if (await inbox.AlreadyProcessedAsync(id, args.CancellationToken))
    {
        await args.CompleteMessageAsync(args.Message);
        return;
    }

    await handler.HandleAsync(args.Message, args.CancellationToken);
    await inbox.MarkProcessedAsync(id, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message);
};
```

Inbox marker và business write nên có atomic design khi cùng datastore cho phép.

## 5. Real production scenario

Payment-confirmed consumer cập nhật order thành Paid. DB commit thành công nhưng process chết trước `Complete`; message quay lại. Idempotency ngăn gửi confirmation email/transition lần hai.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate side effects dù broker không có duplicate send.  
**Evidence** → same `MessageId`, delivery count > 1.  
**Hypothesis** → redelivery sau lock loss/crash.  
**Diagnosis** → correlate processing duration, lock renewal, settlement errors.  
**Fix** → idempotent handler, bounded processing, lock configuration và DLQ policy.  
**Verification** → kill consumer sau DB commit trước settlement và confirm no duplicate effect.

## 7. Common mistakes

Complete trước business commit; assume duplicate detection giải consumer duplicates; handler dài hơn lock; retry poison message vô hạn.

## 8. Alternatives

Receive-and-delete giảm duplicate nhưng tăng message-loss risk. Kafka có semantics khác nhưng application side effects vẫn cần careful processing.

## 9. Trade-offs

### Advantages

Reliable redelivery khi consumer fail.

### Costs / Risks

Duplicate handling, lock management và reconciliation complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu receive/complete/abandon.

### Middle
Handle settlement và DLQ.

### Senior
Thiết kế idempotency và crash-window tests.

### Technical Lead / Architect
Định nghĩa delivery semantics xuyên broker → DB → external side effects.

## 11. Key takeaway

- `Complete` là broker settlement, không phải business transaction.
- Duplicate delivery là expected failure mode.
- Idempotency phải được kiểm thử tại crash boundaries.

# 8. Kubernetes resource requests/limits: scheduling, throttling và OOMKilled

## 1. What is it?

`requests` biểu diễn resource Kubernetes scheduler dùng để đặt Pod; `limits` đặt ceiling runtime cho container. CPU và memory limit có failure behavior khác nhau.

## 2. Why does it exist?

Không khai báo resource, scheduler không có capacity signal tốt và một workload có thể cạnh tranh tài nguyên với workloads khác trên node.

## 3. How does it work?

```text
requests → scheduling / reserved capacity model
limits   → runtime enforcement

CPU over limit    → throttling
Memory over limit → possible OOM kill
```

## 4. Practical implementation

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
```

Values phải dựa trên measured workload, startup spikes, GC behavior và SLO—not copied defaults.

## 5. Real production scenario

.NET API có normal RSS 300 MiB nhưng memory limit 256 MiB. Pod restart dưới traffic burst, readiness oscillates và deployment tưởng application bug.

## 6. Failure scenario & troubleshooting

**Symptom** → latency p99 tăng nhưng CPU dashboard chỉ quanh configured ceiling.  
**Evidence** → container CPU throttling tăng.  
**Hypothesis** → CPU limit thấp hơn burst requirement.  
**Diagnosis** → inspect throttling, node capacity, request latency và GC.  
**Fix** → right-size resources hoặc scaling policy.  
**Verification** → load test không còn throttling-induced tail latency.

## 7. Common mistakes

Requests=limits copy-paste; memory limit dưới realistic working set; chỉ tăng replicas khi dependency là bottleneck; không xem OOMKilled reason.

## 8. Alternatives

VM/App Service abstract một phần scheduling nhưng vẫn có finite compute/memory. VPA/HPA hỗ trợ sizing/scaling nhưng không thay capacity reasoning.

## 9. Trade-offs

### Advantages

Predictable scheduling, isolation và capacity planning.

### Costs / Risks

Over-request waste capacity; under-limit gây throttling/restarts.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu requests vs limits.

### Middle
Đọc Pod status và metrics.

### Senior
Correlate throttling/OOM với .NET runtime behavior.

### Technical Lead / Architect
Định nghĩa resource policy theo SLO, cost và cluster capacity.

## 11. Key takeaway

- CPU limit và memory limit không fail giống nhau.
- Resource values phải đo được.
- Autoscaling không sửa downstream bottleneck.

# 9. Contract Testing: bảo vệ integration contract mà không biến E2E thành bottleneck

## 1. What is it?

Contract test xác minh producer và consumer đồng ý về request/response/message contract. Nó nằm giữa unit/integration tests và full E2E: mục tiêu là phát hiện **integration incompatibility** sớm.

## 2. Why does it exist?

Hai services deploy độc lập. Producer đổi `customerId` thành `customer_id`; unit tests hai bên vẫn xanh, E2E có thể chỉ phát hiện sau khi environments được tích hợp.

## 3. How does it work?

```text
Consumer expectation
      ↓
versioned contract
      ↓
Provider verification
      ↓
compatible? → safe promotion signal
```

Contract test không chứng minh business workflow end-to-end hoàn chỉnh.

## 4. Practical implementation

Ví dụ provider verification tối thiểu bằng integration test:

```csharp
var response = await client.GetAsync("/api/customers/42");
response.EnsureSuccessStatusCode();
var json = await response.Content.ReadFromJsonAsync<CustomerContract>();
json!.Id.Should().Be(42);
json.Name.Should().NotBeNull();
```

Consumer-driven tooling như Pact hữu ích khi nhiều independent consumers cần publish expectations.

## 5. Real production scenario

Frontend BFF và Customer API release riêng. Contract verification chặn provider release xóa field mà production consumer vẫn dùng.

## 6. Failure scenario & troubleshooting

**Symptom** → contract tests xanh nhưng workflow production fail.  
**Evidence** → test chỉ verify schema, không auth/rate-limit/business state.  
**Hypothesis** → team kỳ vọng contract test thay E2E/integration testing.  
**Diagnosis** → map risk tới test layer.  
**Fix** → giữ ít critical E2E và integration tests cho runtime behavior.  
**Verification** → mỗi failure class có test layer phù hợp.

## 7. Common mistakes

Snapshot toàn response quá brittle; contract chứa implementation details; không version consumer expectations; dùng mocks tự invent thay provider reality.

## 8. Alternatives

OpenAPI schema checks đơn giản hơn cho HTTP shape. Full E2E có confidence rộng hơn nhưng chậm/flaky hơn. Integration tests kiểm tra service + real dependencies sâu hơn.

## 9. Trade-offs

### Advantages

Fast compatibility feedback, hỗ trợ independent deployment.

### Costs / Risks

Contract lifecycle/tooling và false confidence nếu scope hiểu sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu contract khác implementation.

### Middle
Viết provider/consumer compatibility tests.

### Senior
Chọn đúng test layer cho failure class.

### Technical Lead / Architect
Thiết kế release gate mà không tạo test-suite bottleneck.

## 11. Key takeaway

- Contract tests bảo vệ compatibility, không bảo vệ mọi behavior.
- Mock phải grounded vào real contract.
- Test strategy cần nhiều layers theo risk.

# 10. AI Tool Calling: model chọn action nhưng application giữ quyền kiểm soát

## 1. What is it?

Tool Calling cho phép LLM đề xuất gọi một function/tool với structured arguments. Mental model: model là **planner/proposer probabilistic**; application là executor deterministic chịu trách nhiệm validation, authorization và side effects.

## 2. Why does it exist?

LLM không thể chỉ bằng text tự đọc database private, gửi email hay tạo ticket. Tools tạo controlled bridge từ reasoning layer tới capabilities thật.

## 3. How does it work?

```text
User → LLM
        ↓ proposes tool + args
Application policy boundary
        ↓ validate/authz
Tool/API executes
        ↓ result
LLM → final response
```

Tool schema giảm structural ambiguity nhưng không đảm bảo action đúng intent hoặc an toàn.

## 4. Practical implementation

```csharp
public sealed record RefundArgs(Guid OrderId, decimal Amount);

static async Task<RefundResult> ExecuteRefundAsync(
    RefundArgs args, ClaimsPrincipal user, CancellationToken ct)
{
    if (!user.IsInRole("RefundOperator"))
        throw new UnauthorizedAccessException();

    if (args.Amount <= 0 || args.Amount > 500m)
        throw new ValidationException("Manual approval required");

    return await payments.RefundAsync(args.OrderId, args.Amount, ct);
}
```

Authorization và financial limits nằm trong deterministic code, không nằm trong prompt.

## 5. Real production scenario

Support agent cho phép AI tra order, tạo draft response và đề xuất refund. Read-only lookup có thể tự động; refund lớn yêu cầu policy + human approval.

## 6. Failure scenario & troubleshooting

**Symptom** → model gọi tool đúng schema nhưng sai customer/order.  
**Evidence** → arguments structurally valid nhưng entity resolution sai.  
**Hypothesis** → schema validation bị nhầm với semantic validation.  
**Diagnosis** → trace prompt/tool call/result và authorization context.  
**Fix** → server-side ownership checks, confirmation boundary và idempotency key.  
**Verification** → adversarial evals không thể cross-tenant action.

## 7. Common mistakes

Cho model quyết định authorization; expose quá nhiều generic tools; tool descriptions mơ hồ; không timeout/retry policy; không audit side effects; prompt injection có thể route tới privileged tool.

## 8. Alternatives

Structured Outputs phù hợp khi chỉ cần machine-readable result. Deterministic workflow tốt hơn nếu action sequence cố định. Human-in-the-loop phù hợp high-impact operations.

## 9. Trade-offs

### Advantages

Natural-language orchestration, reuse existing APIs, mở rộng capability có kiểm soát.

### Costs / Risks

Probabilistic planning, security surface, latency/token/tool cost và evaluation burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu model không trực tiếp “thực thi” business authority.

### Middle
Implement schemas, validation, timeout và error handling.

### Senior
Threat-model prompt injection, cross-tenant access, retries và duplicate side effects.

### Technical Lead / Architect
Phân loại tools theo risk, approval level và deterministic guardrails; quyết định action nào không nên giao cho agent.

## 11. Key takeaway

- Tool schema bảo vệ shape, không bảo vệ intent.
- Authorization và correctness-critical rules phải ở application.
- High-impact tools cần audit, idempotency và approval boundary.
