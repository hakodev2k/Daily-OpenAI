# 1. .NET `CancellationToken`: cancellation propagation và cooperative cancellation

## 1. What is it?

Mental model: cancellation không phải “giết thread”. `CancellationToken` là tín hiệu hợp tác: caller thông báo “kết quả này không còn cần thiết”, còn code ở downstream phải chủ động quan sát token và dừng ở điểm an toàn.

Trong .NET, token thường đi xuyên từ HTTP request, application service, EF Core đến HTTP client hoặc queue operation. Giá trị lớn nhất không nằm ở API `ThrowIfCancellationRequested()`, mà ở việc giải phóng capacity sớm.

## 2. Why does it exist?

Nếu client disconnect nhưng server vẫn query database 20 giây, gọi external API và serialize response, hệ thống tiêu CPU, connection và ThreadPool cho kết quả không ai nhận. Khi load cao, “orphan work” khuếch đại thành latency và exhaustion.

## 3. How does it work?

`CancellationTokenSource` phát tín hiệu; token được truyền xuống call chain. API hỗ trợ cancellation đăng ký callback hoặc kiểm tra trạng thái. `OperationCanceledException`/ `TaskCanceledException` biểu diễn luồng bị hủy, không nên mặc định xem như lỗi ứng dụng.

```text
HTTP aborted
  -> RequestAborted
  -> Application service
  -> EF Core / HttpClient
  -> operation stops cooperatively
```

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:int}", async (
    int id,
    AppDbContext db,
    HttpContext http) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, http.RequestAborted);

    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

Application methods nên nhận token ở boundary:

```csharp
public Task<Order?> GetAsync(int id, CancellationToken ct) =>
    _db.Orders.AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);
```

## 5. Real production scenario

Search API gọi SQL và review provider. User đổi filter liên tục; request cũ bị browser hủy. Nếu token propagate đầy đủ, SQL command và outbound HTTP cũ có cơ hội dừng, giữ capacity cho request mới.

## 6. Failure scenario & troubleshooting

**Symptom** → request đã disconnect nhưng DB CPU và outbound calls vẫn cao.  
**Evidence** → trace cho thấy dependency span tiếp tục sau khi request span kết thúc.  
**Hypothesis** → token bị “rơi” tại service boundary.  
**Diagnosis** → tìm method async không nhận/truyền token.  
**Fix** → propagate token đến API hỗ trợ cancellation.  
**Verification** → abort load test; dependency duration và active connections giảm.

## 7. Common mistakes

Tạo `new CancellationTokenSource()` ở mỗi layer làm mất ownership; dùng `CancellationToken.None`; catch `Exception` rồi log cancellation như error; hủy giữa một chuỗi side effects mà không suy nghĩ consistency.

## 8. Alternatives

Timeout giới hạn thời gian tối đa; cancellation phản ánh caller không còn cần kết quả. Production thường cần cả hai. Timeout không thay thế propagation.

## 9. Trade-offs

### Advantages

Giảm wasted work, cải thiện capacity và shutdown behavior.

### Costs / Risks

Phải thiết kế cancellation boundary; operation có side effect cần xác định điểm nào có thể hủy an toàn. Cancellation sau khi đã charge payment không thể đơn giản “undo”.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu token là cooperative signal, không phải thread termination.

### Middle
Truyền token xuyên async call chain và phân biệt cancellation với failure.

### Senior
Xác định safe cancellation points, quan sát orphan work và kết hợp timeout.

### Technical Lead / Architect
Quy định cancellation contract tại API/application/integration boundaries và quyết định operation nào phải hoàn tất dù caller đã rời đi.

## 11. Key takeaway

- Cancellation phải propagate mới có giá trị.
- Timeout và cancellation giải quyết hai vấn đề khác nhau.
- Side effect quyết định nơi cancellation còn an toàn.

# 2. ASP.NET Core graceful shutdown: drain request và dừng service đúng cách

## 1. What is it?

Graceful shutdown là quá trình instance ngừng nhận work mới, cho work đang chạy thời gian hoàn tất, báo cancellation cho background work rồi mới terminate process.

## 2. Why does it exist?

Container, App Service hay Kubernetes đều có thể recycle instance. Nếu process chết ngay, request đang ghi DB, upload file hoặc xử lý message có thể bị cắt giữa chừng, tạo retry, duplicate hoặc partial side effect.

## 3. How does it work?

Host nhận SIGTERM/process shutdown → application lifetime phát tín hiệu → server ngừng nhận request mới → hosted services nhận cancellation → host chờ trong shutdown timeout → process kết thúc.

Readiness nên chuyển sang unavailable trước khi process chết để load balancer drain traffic.

## 4. Practical implementation

```csharp
builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(30));

public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await ProcessNextAsync(stoppingToken);
        }
    }
}
```

Không dùng `Task.Delay(...)` thiếu token trong loop.

## 5. Real production scenario

Một App Service deployment thay instance trong lúc API có request export 15 giây. Graceful drain cho request hoàn tất thay vì client nhận 502 và retry toàn bộ export.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment có spike 499/502 và duplicate message.  
**Evidence** → lỗi tập trung đúng thời điểm instance restart.  
**Hypothesis** → shutdown timeout ngắn hoặc worker bỏ qua token.  
**Diagnosis** → correlate deployment event, process stop và trace chưa hoàn tất.  
**Fix** → readiness/drain đúng, token propagation, bounded operation duration.  
**Verification** → rolling deployment dưới synthetic load không tăng error rate.

## 7. Common mistakes

Coi shutdown như exceptional event; background loop không nhận token; shutdown timeout vô hạn; bắt đầu work dài ngay sau khi shutdown signal đã đến; ack message trước khi side effect hoàn tất.

## 8. Alternatives

Work dài và retryable thường phù hợp queue + Worker Service/Azure Functions hơn giữ HTTP request. Kubernetes có termination grace period; App Service có lifecycle riêng, nhưng application vẫn phải cooperative.

## 9. Trade-offs

### Advantages
Giảm lỗi deployment/restart và partial work.

### Costs / Risks
Drain lâu làm rollout chậm; timeout quá lớn che giấu operation không bounded.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu process restart là bình thường trong production.

### Middle
Viết HostedService tôn trọng stopping token.

### Senior
Thiết kế idempotency và quan sát lỗi quanh deployment.

### Technical Lead / Architect
Chọn workload placement và shutdown budget dựa trên SLA, retry semantics và orchestration platform.

## 11. Key takeaway

- Restart là lifecycle bình thường, không phải edge case.
- Graceful shutdown cần cả traffic draining và cooperative cancellation.
- Work dài nên có retry/idempotency thay vì phụ thuộc process sống mãi.

# 3. EF Core optimistic concurrency: chống lost update bằng concurrency token

## 1. What is it?

Optimistic concurrency giả định conflict hiếm, cho nhiều actor đọc song song nhưng kiểm tra dữ liệu chưa đổi khi UPDATE. EF Core dùng concurrency token như SQL Server `rowversion` để phát hiện conflict.

## 2. Why does it exist?

Hai user cùng đọc Order version 10. A đổi address; B đổi status dựa trên snapshot cũ. Nếu UPDATE chỉ theo `Id`, B có thể ghi đè thay đổi của A mà không biết: lost update.

## 3. How does it work?

EF Core giữ original concurrency value. UPDATE sinh điều kiện:

```sql
UPDATE Orders
SET Status = @status
WHERE Id = @id AND RowVersion = @originalRowVersion;
```

Affected rows = 0 → EF Core ném `DbUpdateConcurrencyException`.

## 4. Practical implementation

```csharp
public class Order
{
    public int Id { get; set; }
    public string Status { get; set; } = "";
    [Timestamp]
    public byte[] RowVersion { get; set; } = [];
}
```

```csharp
try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict(new
    {
        code = "order_changed",
        message = "Order was modified. Reload and retry."
    });
}
```

## 5. Real production scenario

Approval workflow: manager A approve trong khi HR sửa dữ liệu. API không nên silently overwrite. Conflict 409 cho client reload snapshot và quyết định lại.

## 6. Failure scenario & troubleshooting

**Symptom** → user nói dữ liệu “tự quay lại” sau save.  
**Evidence** → audit log có hai UPDATE sát nhau.  
**Hypothesis** → last-write-wins ngoài ý muốn.  
**Diagnosis** → UPDATE predicate không có version.  
**Fix** → concurrency token + explicit conflict policy.  
**Verification** → integration test hai DbContext đọc cùng row, save lần hai phải conflict.

## 7. Common mistakes

Retry `SaveChanges` mù quáng; trả 500 cho conflict business; dùng timestamp thời gian có precision không phù hợp; thêm token nhưng DTO không round-trip version; hiểu concurrency token như database lock.

## 8. Alternatives

Pessimistic locking phù hợp khi conflict rất đắt và transaction ngắn; application-level version integer dùng được đa DB; ETag/`If-Match` đưa cùng semantic ra HTTP boundary.

## 9. Trade-offs

### Advantages
Không giữ lock suốt thời gian user suy nghĩ; scale tốt cho conflict hiếm.

### Costs / Risks
Application phải có merge/reload/reject policy; conflict không tự được “giải quyết” bởi EF.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu lost update và version check.

### Middle
Cấu hình token, catch exception, viết integration test.

### Senior
Thiết kế conflict semantics theo business invariant.

### Technical Lead / Architect
Quyết định optimistic/pessimistic/last-write-wins theo contention, UX và consistency requirement.

## 11. Key takeaway

- Concurrency detection không đồng nghĩa conflict resolution.
- `rowversion` biến silent overwrite thành explicit decision.
- Retry chỉ đúng khi business operation vẫn hợp lệ trên state mới.

# 4. SQL Server keyset pagination: ổn định latency khi dữ liệu lớn

## 1. What is it?

Keyset pagination lấy “trang tiếp theo sau khóa cuối cùng” thay vì `OFFSET N`. Cursor thường gồm sort key + unique tie-breaker.

## 2. Why does it exist?

`OFFSET 500000 FETCH 50` vẫn buộc database đi qua lượng lớn rows trước khi bỏ chúng. Deep page làm I/O và latency tăng theo offset; concurrent insert còn gây duplicate/missing rows giữa các page.

## 3. How does it work?

Với sort `CreatedAt DESC, Id DESC`, page tiếp theo dùng predicate lexicographic:

```sql
WHERE CreatedAt < @lastCreatedAt
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC
```

Index nên hỗ trợ cùng access pattern.

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON Orders (CreatedAt DESC, Id DESC)
INCLUDE (Status, CustomerId);
```

```csharp
var query = db.Orders.AsNoTracking();

if (cursor is not null)
{
    query = query.Where(x =>
        x.CreatedAt < cursor.CreatedAt ||
        (x.CreatedAt == cursor.CreatedAt && x.Id < cursor.Id));
}

var page = await query
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id)
    .Take(51)
    .ToListAsync(ct);
```

## 5. Real production scenario

Activity feed có hàng chục triệu records. User chủ yếu “load more”, không cần nhảy đến page 12,431. Keyset giữ query gần như seek + bounded read.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 tăng mạnh khi page number lớn.  
**Evidence** → execution plan và logical reads tăng theo OFFSET.  
**Hypothesis** → deep pagination scan.  
**Diagnosis** → benchmark offset 0, 100k, 1m.  
**Fix** → keyset + matching composite index.  
**Verification** → logical reads/latency ổn định theo depth.

## 7. Common mistakes

Cursor chỉ chứa non-unique `CreatedAt`; sort UI tùy ý nhưng không có index strategy; encode cursor nhưng không validate; vẫn chạy `COUNT(*)` đắt cho mọi request.

## 8. Alternatives

OFFSET phù hợp admin grid nhỏ và cần nhảy page. Keyset phù hợp feed/infinite scroll. Search engine `search_after` là ý tưởng tương tự cho search workloads.

## 9. Trade-offs

### Advantages
Latency ổn định, ít I/O, tốt hơn khi dữ liệu thay đổi.

### Costs / Risks
Không tự nhiên cho random page jump; cursor contract phức tạp hơn; mỗi sort mode cần access pattern/index cân nhắc riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu OFFSET phải bỏ qua rows.

### Middle
Implement cursor có deterministic ordering.

### Senior
Đọc execution plan, logical reads và thiết kế composite index.

### Technical Lead / Architect
Chọn pagination contract theo UX và scale thay vì mặc định page number.

## 11. Key takeaway

- Deep OFFSET là access-pattern problem, không chỉ syntax problem.
- Cursor phải có unique tie-breaker.
- Query, ordering và index phải được thiết kế cùng nhau.

# 5. Azure Service Bus idempotent consumer: sống chung với at-least-once delivery

## 1. What is it?

Idempotent consumer đảm bảo xử lý cùng logical message nhiều lần nhưng business effect chỉ xảy ra một lần. Đây là defense bắt buộc khi broker có at-least-once delivery.

## 2. Why does it exist?

Consumer có thể commit DB thành công rồi crash trước khi `CompleteMessageAsync`. Broker không biết DB đã commit nên redeliver. “Exactly once” end-to-end không tự xuất hiện chỉ vì broker có duplicate detection.

## 3. How does it work?

Consumer dùng stable MessageId/idempotency key. Trong cùng transaction với business update, ghi Inbox/ProcessedMessages có unique constraint. Duplicate insert thất bại hoặc được phát hiện trước side effect.

```text
Service Bus -> Consumer -> DB transaction
                         |- ProcessedMessages(MessageId UNIQUE)
                         |- Business changes
             <- Complete message only after commit
```

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

if (await db.ProcessedMessages.AnyAsync(x => x.Id == message.MessageId, ct))
{
    await tx.RollbackAsync(ct);
    await receiver.CompleteMessageAsync(message, ct);
    return;
}

db.ProcessedMessages.Add(new(message.MessageId));
order.MarkPaid();
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);

await receiver.CompleteMessageAsync(message, ct);
```

Trong production, unique constraint vẫn là guard cuối chống race.

## 5. Real production scenario

PaymentConfirmed cập nhật order và tạo fulfillment. Consumer restart đúng sau DB commit. Message chạy lại nhưng Inbox ngăn tạo shipment thứ hai.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng order có hai shipment.  
**Evidence** → Service Bus delivery count > 1, hai trace cùng MessageId.  
**Hypothesis** → side effect không idempotent.  
**Diagnosis** → ack xảy ra sau DB commit nhưng không có dedup state.  
**Fix** → stable ID + transactional Inbox/unique business constraint.  
**Verification** → fault-injection crash sau commit trước ack; chỉ một effect tồn tại.

## 7. Common mistakes

Dùng in-memory HashSet; dedup theo timestamp; complete trước commit; retry non-idempotent external API không có idempotency key; tin rằng broker duplicate detection bảo vệ toàn bộ workflow.

## 8. Alternatives

Natural idempotency qua unique business key có thể đơn giản hơn Inbox. Outbox giải quyết reliable publishing phía producer; Inbox giải quyết duplicate consumption phía consumer. Chúng bổ sung nhau.

## 9. Trade-offs

### Advantages
Cho phép retry an toàn và recovery sau crash.

### Costs / Risks
Thêm storage, cleanup policy, transaction reasoning và key design.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu message có thể tới nhiều lần.

### Middle
Implement dedup và settlement đúng thứ tự.

### Senior
Thiết kế atomicity giữa dedup record và business effect.

### Technical Lead / Architect
Xác định delivery semantics toàn workflow, retention của Inbox và external side-effect strategy.

## 11. Key takeaway

- At-least-once nghĩa là duplicate là bình thường.
- Ack chỉ sau durable business commit.
- Idempotency phải bao phủ business effect, không chỉ handler code.

# 6. Elasticsearch alias + reindex: thay mapping không downtime

## 1. What is it?

Index alias là tên logic trỏ tới physical index. Khi mapping/analyzer cần thay đổi, tạo index mới, reindex dữ liệu rồi atomically chuyển alias thay vì sửa index đang phục vụ traffic.

## 2. Why does it exist?

Nhiều mapping changes không thể áp dụng an toàn in-place. Nếu Search API hard-code `products-v1`, migration buộc deployment đồng bộ hoặc downtime.

## 3. How does it work?

```text
Search API -> products-read -> products-v1
                         reindex
                             -> products-v2
alias switch: products-read -> products-v2
```

Write synchronization trong migration phải được xử lý: dual write, replay change feed hoặc pause/catch-up có kiểm soát.

## 4. Practical implementation

```http
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v1", "alias": "products-read" } },
    { "add":    { "index": "products-v2", "alias": "products-read" } }
  ]
}
```

Trước switch, compare document count, sample queries và lag watermark.

## 5. Real production scenario

E-commerce đổi analyzer để autocomplete tốt hơn. Index v2 được build song song; API vẫn đọc v1. Sau validation, alias switch trong một operation và rollback chỉ là trỏ lại nếu write model cho phép.

## 6. Failure scenario & troubleshooting

**Symptom** → sau switch thiếu sản phẩm mới trong vài phút reindex cuối.  
**Evidence** → DB updated_at lớn hơn watermark của v2.  
**Hypothesis** → writes trong reindex window bị mất.  
**Diagnosis** → kiểm tra synchronization pipeline/change sequence.  
**Fix** → catch-up delta trước switch hoặc replay event stream.  
**Verification** → count + watermark + representative search parity.

## 7. Common mistakes

Chỉ so document count; bỏ qua analyzer behavior; delete v1 ngay sau switch; coi Elasticsearch là source of truth; không có strategy cho concurrent writes.

## 8. Alternatives

In-place compatible mapping update cho thay đổi nhỏ; versioned alias phù hợp breaking mapping; managed search services vẫn cần migration semantics tương tự.

## 9. Trade-offs

### Advantages
Near-zero downtime, rollback nhanh, migration tách khỏi app release.

### Costs / Risks
Tốn gấp đôi storage tạm thời, reindex load và synchronization complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu alias tách logical name khỏi physical index.

### Middle
Tạo index version, reindex và switch alias.

### Senior
Giải quyết concurrent writes, validation và rollback.

### Technical Lead / Architect
Thiết kế search synchronization, ownership và migration SLO; quyết định khi nào search complexity thực sự đáng giá.

## 11. Key takeaway

- Reindex là data migration, không chỉ Elasticsearch command.
- Alias giúp decouple consumer khỏi physical index.
- Watermark/parity quan trọng hơn document count đơn thuần.

# 7. Managed Identity + Key Vault: bỏ secrets khỏi application configuration

## 1. What is it?

Managed Identity cho Azure workload một identity do platform quản lý. Application dùng identity đó lấy token từ Microsoft Entra ID để truy cập Key Vault hoặc Azure resources mà không lưu client secret.

## 2. Why does it exist?

Secret trong appsettings, pipeline variable hay Kubernetes Secret vẫn phải được tạo, phân phối, rotate và tránh leak. Managed Identity loại bỏ credential dài hạn khỏi application cho Azure-to-Azure authentication.

## 3. How does it work?

```text
App Service/Container
  -> Managed Identity
  -> Entra ID token
  -> Key Vault / Storage / SQL
  -> RBAC authorizes operation
```

Identity chứng minh “workload này là ai”; RBAC quyết định “được làm gì”.

## 4. Practical implementation

```csharp
var client = new SecretClient(
    new Uri(configuration["KeyVaultUri"]!),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("ExternalApiKey");
```

Local development có thể dùng developer credential; production chain chọn Managed Identity. Không hard-code fallback secret.

## 5. Real production scenario

App Service cần đọc third-party API key từ Key Vault và truy cập Blob Storage. Identity được cấp `Key Vault Secrets User` và role storage tối thiểu, không cần client secret trong deployment pipeline.

## 6. Failure scenario & troubleshooting

**Symptom** → local chạy, production nhận 403 từ Key Vault.  
**Evidence** → authentication thành công nhưng authorization denied.  
**Hypothesis** → identity đúng nhưng thiếu role/scope.  
**Diagnosis** → xác định principal ID thực tế, RBAC assignment và vault/network access.  
**Fix** → least-privilege role đúng scope; kiểm tra Private Endpoint/DNS nếu dùng private network.  
**Verification** → token-based access thành công và audit log ghi đúng principal.

## 7. Common mistakes

Nhầm authentication với authorization; cấp Contributor quá rộng; dùng user-assigned identity nhưng app thực tế chọn system-assigned khác; cache secret vô hạn nên rotation không có tác dụng; log secret value.

## 8. Alternatives

Client secret/certificate cần cho một số non-Azure hoặc cross-boundary scenarios. Workload identity federation tránh long-lived secrets trong CI/CD/Kubernetes. Managed Identity là lựa chọn tự nhiên khi workload chạy trên Azure hỗ trợ nó.

## 9. Trade-offs

### Advantages
Giảm secret distribution/rotation burden, audit tốt, RBAC rõ.

### Costs / Risks
Phụ thuộc Azure identity plane; local/prod credential behavior khác nhau; networking và RBAC vẫn cần vận hành đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt identity, credential và permission.

### Middle
Dùng `DefaultAzureCredential`, cấu hình role và Key Vault.

### Senior
Debug token/RBAC/network boundary và thiết kế rotation/caching.

### Technical Lead / Architect
Xây identity strategy theo workload, environment, least privilege và blast radius.

## 11. Key takeaway

- Mục tiêu không phải “giấu secret tốt hơn” mà là loại bỏ secret khi có thể.
- Authentication thành công vẫn có thể authorization thất bại.
- Managed Identity + RBAC cần được thiết kế cùng network boundary.

# 8. Modular Monolith: boundary mạnh mà chưa trả operational tax của microservices

## 1. What is it?

Modular Monolith là một deployable application nhưng chia thành modules có ownership, domain model, dependency và data boundary rõ. Nó không phải “monolith với nhiều folders”.

## 2. Why does it exist?

Microservices cho deployment autonomy và failure isolation nhưng thêm network failure, observability, distributed consistency, CI/CD và platform cost. Nhiều hệ thống chưa cần trả chi phí đó nhưng vẫn cần ngăn codebase thành tightly coupled big ball of mud.

## 3. How does it work?

Ví dụ modules `Orders`, `Catalog`, `Identity`. Module expose contract hẹp; module khác không truy cập trực tiếp internal entity/repository. Có thể cùng database server nhưng schema/ownership được tách.

```text
Host
 ├─ Orders     -> Orders schema
 ├─ Catalog    -> Catalog schema
 └─ Identity   -> Identity schema

Orders --contract/event--> Catalog
(no direct Catalog table access)
```

## 4. Practical implementation

```csharp
public interface ICatalogQueries
{
    Task<ProductSnapshot?> GetProductAsync(
        Guid productId, CancellationToken ct);
}

// Orders depends on the contract, not CatalogDbContext.
```

Architecture tests có thể cấm assembly reference sai direction.

## 5. Real production scenario

SaaS ban đầu có 8 engineers. Orders và Catalog thay đổi nhanh nhưng chưa có nhu cầu scale/deploy độc lập. Modular Monolith giữ transaction/local calls đơn giản và tạo extraction seam nếu sau này Catalog cần tách.

## 6. Failure scenario & troubleshooting

**Symptom** → thay Catalog entity làm hàng chục Orders tests vỡ.  
**Evidence** → Orders reference trực tiếp Catalog persistence types.  
**Hypothesis** → module boundary chỉ tồn tại trên folder.  
**Diagnosis** → dependency graph và cross-schema queries.  
**Fix** → explicit contract, ownership và architecture tests.  
**Verification** → internal Catalog refactor không yêu cầu sửa Orders.

## 7. Common mistakes

Mỗi module thành mini Clean Architecture 12 projects dù domain đơn giản; shared-kernel khổng lồ; cross-module FK/query tùy tiện; dùng in-process MediatR rồi gọi đó là loose coupling; thiết kế module theo technical layer thay vì business capability.

## 8. Alternatives

Layered monolith đơn giản hơn cho domain nhỏ. Microservices hợp lý khi có independent deployment/scale/ownership requirement thật. Modular Monolith thường là điểm giữa tốt, không phải bước bắt buộc trước microservices.

## 9. Trade-offs

### Advantages
Local transaction, debug/deploy đơn giản, boundary tốt, operational cost thấp hơn microservices.

### Costs / Risks
Failure vẫn có thể ảnh hưởng toàn process; deployment vẫn coupled; discipline cần tooling/review vì network không cưỡng chế boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu module là business boundary, không phải folder.

### Middle
Giữ dependency qua public contract.

### Senior
Thiết kế data ownership, transaction và integration giữa modules.

### Technical Lead / Architect
Quyết định liệu independent deployment có đủ giá trị để đổi lấy distributed-systems complexity hay chưa.

## 11. Key takeaway

- Boundary tốt không yêu cầu network boundary.
- Microservices giải quyết organizational/operational constraints cụ thể, không phải maturity badge.
- Modular Monolith chỉ hiệu quả khi data và dependency ownership thực sự được enforce.

# 9. React/TypeScript request cancellation: tránh stale UI và wasted work

## 1. What is it?

Request cancellation ở browser dùng `AbortController` để hủy fetch không còn cần thiết khi component unmount hoặc input mới supersede request cũ.

## 2. Why does it exist?

User gõ “iphone”, rồi nhanh chóng đổi thành “ipad”. Request đầu có thể trả sau request thứ hai và ghi đè state bằng dữ liệu cũ. Ngoài stale UI, backend còn xử lý work không cần thiết.

## 3. How does it work?

Mỗi effect/request sở hữu `AbortController`. Cleanup gọi `abort()`. `fetch` reject với `AbortError`; browser có thể đóng request, và backend ASP.NET Core có thể nhận `RequestAborted`.

## 4. Practical implementation

```tsx
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    try {
      const r = await fetch(
        `/api/search?q=${encodeURIComponent(query)}`,
        { signal: controller.signal }
      );
      if (!r.ok) throw new Error(`HTTP ${r.status}`);
      setItems(await r.json());
    } catch (e) {
      if ((e as DOMException).name !== "AbortError") {
        setError("Search failed");
      }
    }
  }

  void load();
  return () => controller.abort();
}, [query]);
```

## 5. Real production scenario

Product search autocomplete phát request theo input. Debounce giảm số request; abort loại request đã phát nhưng không còn relevant. Backend tiếp tục propagate cancellation xuống SQL/search engine.

## 6. Failure scenario & troubleshooting

**Symptom** → kết quả nhảy ngược về query cũ.  
**Evidence** → DevTools Network cho thấy request cũ hoàn thành sau request mới.  
**Hypothesis** → race giữa responses.  
**Diagnosis** → log query + request sequence khi set state.  
**Fix** → abort superseded request hoặc sequence guard.  
**Verification** → network throttling test không còn stale render.

## 7. Common mistakes

Chỉ debounce nhưng không xử lý in-flight race; hiện error toast cho `AbortError`; abort frontend nhưng backend bỏ qua cancellation; dùng boolean `isMounted` để ngăn setState nhưng vẫn lãng phí network/server work.

## 8. Alternatives

Sequence/request ID guard bảo vệ state ngay cả khi transport không abort được. Data libraries như TanStack Query quản lý lifecycle/caching tốt hơn khi nhu cầu phức tạp. Debounce giải quyết frequency, không hoàn toàn thay cancellation.

## 9. Trade-offs

### Advantages
UI correctness tốt hơn và giảm wasted work.

### Costs / Risks
Lifecycle logic phức tạp; cancellation không đảm bảo server side effect chưa xảy ra.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu async response không đảm bảo về đúng thứ tự.

### Middle
Implement cleanup, abort và error handling.

### Senior
Kết nối browser cancellation với API cancellation, caching và race semantics.

### Technical Lead / Architect
Chọn client data strategy và xác định operation nào được phép supersede/cancel.

## 11. Key takeaway

- Debounce và cancellation giải quyết hai lớp vấn đề khác nhau.
- UI phải chống out-of-order responses.
- Cancellation hiệu quả nhất khi propagate end-to-end.

# 10. AI Tool Calling: giữ business rules deterministic quanh LLM

## 1. What is it?

Tool Calling cho model chọn một capability có schema, ví dụ `get_order` hay `create_refund_request`. Model đề xuất tool + arguments; application mới là thành phần validate, authorize và thực thi.

## 2. Why does it exist?

LLM mạnh ở natural-language interpretation nhưng không nên là authority cho permission, tiền, inventory hay invariant. Tool boundary cho phép dùng model để hiểu intent mà giữ critical logic trong deterministic code.

## 3. How does it work?

```text
User
 -> LLM: intent + available tool schemas
 <- tool call proposal
 -> Application: validate + authorize + execute
 -> Tool result
 -> LLM: formulate response
 -> User
```

Model output là untrusted input giống request từ client.

## 4. Practical implementation

```csharp
public sealed record RefundArgs(Guid OrderId, decimal Amount);

public async Task<RefundResult> CreateRefundAsync(
    ClaimsPrincipal user,
    RefundArgs args,
    CancellationToken ct)
{
    if (!await _authorization.CanRefundAsync(user, args.OrderId, ct))
        throw new ForbiddenException();

    var order = await _orders.GetAsync(args.OrderId, ct);

    if (args.Amount <= 0 || args.Amount > order.RefundableAmount)
        throw new ValidationException("Invalid refund amount.");

    return await _refunds.CreateIdempotentAsync(order, args.Amount, ct);
}
```

Schema giúp cấu trúc arguments nhưng business validation vẫn ở server.

## 5. Real production scenario

Support assistant nhận câu “hoàn lại 500k cho đơn X”. Model map sang refund tool. Application kiểm tra user permission, order ownership, currency, refundable amount và idempotency key trước khi gọi payment provider.

## 6. Failure scenario & troubleshooting

**Symptom** → assistant cố gọi tool với order không thuộc tenant.  
**Evidence** → tool trace có arguments hợp schema nhưng authorization fail.  
**Hypothesis** → model suy diễn identifier từ context hoặc prompt injection.  
**Diagnosis** → inspect tool-call trace, retrieved context và auth decision.  
**Fix** → server-side tenant scoping, allowlist tools theo principal, không đưa secret vào model context.  
**Verification** → adversarial evaluation phải bị deny ở deterministic layer.

## 7. Common mistakes

Tin Structured Outputs đồng nghĩa dữ liệu đúng; để model quyết định authorization; tool quá rộng kiểu `execute_sql`; tự động retry tool có side effect; đưa raw secrets vào prompt; log sensitive model/tool payload; không giới hạn tool chain.

## 8. Alternatives

Deterministic UI/workflow tốt hơn khi intent đã rõ. RAG cung cấp knowledge nhưng không thay action boundary. Rule engine phù hợp decision logic ổn định. Agentic loop chỉ đáng dùng khi task thật sự cần dynamic planning.

## 9. Trade-offs

### Advantages
Natural interaction, extensible capabilities, separation giữa language reasoning và execution.

### Costs / Risks
Latency, token cost, nondeterminism, prompt injection, evaluation burden và operational tracing mới.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu model đề xuất action; application mới thực thi.

### Middle
Định nghĩa schema, validate arguments, handle timeout/error.

### Senior
Thiết kế idempotency, authorization, observability, evals và prompt-injection defenses.

### Technical Lead / Architect
Quyết định phần nào đáng dùng LLM và phần nào bắt buộc deterministic; giới hạn blast radius, cost và data exposure.

## 11. Key takeaway

- Tool schema không phải security boundary.
- Authorization và business invariants phải nằm ngoài LLM.
- Agent complexity chỉ đáng trả khi dynamic reasoning tạo giá trị thật.
