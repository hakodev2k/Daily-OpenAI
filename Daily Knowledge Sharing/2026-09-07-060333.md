# 1. `ValueTask` vs `Task`: allocation, completion path và khi tối ưu trở thành phản tác dụng

## 1. What is it?

`Task` là reference type đại diện cho một asynchronous operation. Với một method `async Task<T>`, runtime thường cần một object `Task<T>` để biểu diễn kết quả chưa hoàn tất hoặc đã hoàn tất.

`ValueTask<T>` là một value type có thể biểu diễn một kết quả đã có sẵn mà không nhất thiết phải allocate một `Task<T>`. Mental model đúng không phải là “ValueTask nhanh hơn Task”, mà là: **ValueTask tối ưu cho hot path nơi operation thường hoàn tất synchronously và allocation của Task đã được chứng minh là đáng kể**.

## 2. Why does it exist?

Một số API như pooled I/O, parsers, caches hoặc pipelines có tỷ lệ cache hit rất cao. Nếu 99% lời gọi có kết quả ngay nhưng mỗi lần vẫn tạo một `Task<T>`, allocation rate có thể lớn trong workload hàng trăm nghìn operations/second.

`ValueTask<T>` cho phép trả trực tiếp kết quả trong struct ở synchronous-completion path. Nhưng đổi lại API có semantics phức tạp hơn.

## 3. How does it work?

`ValueTask<T>` có thể chứa:

* một giá trị `T` đã hoàn tất,
* một `Task<T>`,
* hoặc implementation dựa trên `IValueTaskSource<T>` để tái sử dụng backing object.

Flow thường là:

```text
Call operation
   |
   +-- result available now --> ValueTask<T>(value)
   |
   +-- operation pending ----> ValueTask<T>(Task<T>/IValueTaskSource<T>)
```

Vì có thể dựa trên reusable source, một `ValueTask` không được mặc định xem như một `Task` có thể await nhiều lần an toàn.

## 4. Practical implementation

Ví dụ cache có synchronous hit path:

```csharp
public ValueTask<Product?> GetAsync(
    string key,
    CancellationToken cancellationToken)
{
    if (_memoryCache.TryGetValue<Product>(key, out var product))
    {
        return ValueTask.FromResult<Product?>(product);
    }

    return new ValueTask<Product?>(LoadFromDatabaseAsync(key, cancellationToken));
}

private async Task<Product?> LoadFromDatabaseAsync(
    string key,
    CancellationToken cancellationToken)
{
    return await _db.Products
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.CacheKey == key, cancellationToken);
}
```

Không nên đổi toàn bộ public APIs từ `Task` sang `ValueTask` nếu chưa đo allocation pressure.

## 5. Real production scenario

Một in-memory metadata service phục vụ hàng trăm nghìn lookup mỗi phút; 99.8% lookup hit cache. Profiling cho thấy `Task<T>` allocations đáng kể trong hot path dù business logic gần như không làm gì.

Sau khi đo bằng profiler và benchmark, đổi riêng hot method sang `ValueTask<T>` có thể giảm allocation rate. Nhưng database path vẫn dùng `Task<T>` vì đó là naturally asynchronous path.

## 6. Failure scenario & troubleshooting

**Symptom** → code thỉnh thoảng throw hoặc behavior lạ khi consumer await cùng `ValueTask` nhiều lần.

**Evidence** → consumer lưu `ValueTask` vào field hoặc gọi `await` hai lần trên value đến từ pooled `IValueTaskSource`.

**Hypothesis** → caller đang áp semantics của `Task` cho `ValueTask`.

**Diagnosis** → inspect call sites; nếu cần multiple awaits, convert một lần bằng `.AsTask()`.

**Fix** → await `ValueTask` đúng một lần hoặc expose `Task` nếu API contract cần reuse/composition.

**Verification** → concurrency tests và benchmark allocation trước/sau.

## 7. Common mistakes

* Dùng `ValueTask` vì nghĩ nó luôn nhanh hơn.
* Return `ValueTask` trên mọi async method.
* Await cùng instance nhiều lần.
* Dùng `.Result` hoặc sync blocking vì operation “thường complete ngay”.
* Tối ưu allocation khi bottleneck thực tế nằm ở SQL hoặc network.

## 8. Alternatives

`Task<T>` vẫn là default tốt nhất cho phần lớn application code. Nếu workload synchronous hoàn toàn, return `T`. Nếu cần low-level reusable async primitives, `IValueTaskSource<T>` tồn tại nhưng chỉ nên xuất hiện trong infrastructure/library code có profiling rõ ràng.

## 9. Trade-offs

### Advantages

* Có thể giảm allocations ở high-frequency synchronous-completion path.
* Hữu ích cho low-level libraries và caching layers.

### Costs / Risks

* API semantics khó hơn.
* Composition với `Task.WhenAll` kém trực tiếp hơn.
* Dễ tạo correctness bug nếu consumer không hiểu constraints.
* Optimization benefit có thể bằng 0 với application thông thường.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task` là đại diện asynchronous operation, không phải thread.

### Middle

Biết dùng `Task` làm default và đọc đúng semantics của `ValueTask`.

### Senior

Biết đo allocations, synchronous completion rate và quyết định khi nào `ValueTask` tạo lợi ích thực.

### Technical Lead / Architect

Đặt guideline: không đưa `ValueTask` vào public contracts nếu chưa có measured hot path và không muốn đẩy complexity sang mọi caller.

## 11. Key takeaway

* `Task` là default; `ValueTask` là optimization tool.
* Chỉ tối ưu khi profiler cho thấy allocation thực sự đáng kể.
* API simplicity thường có giá trị lớn hơn vài allocation chưa được chứng minh.

# 2. ASP.NET Core `ProblemDetails`: thiết kế error contract ổn định thay vì trả exception tùy tiện

## 1. What is it?

`ProblemDetails` là representation chuẩn hóa cho HTTP API errors, dựa trên RFC problem details semantics. Nó tách **internal exception** khỏi **external API contract**.

Mental model: exception phục vụ control flow/error handling bên trong application; error contract phục vụ client và phải ổn định, versionable, machine-readable.

## 2. Why does it exist?

Nếu mỗi endpoint trả error khác nhau — string, anonymous object, stack trace hoặc status code không nhất quán — frontend và external consumers phải viết logic đặc biệt cho từng endpoint.

Tệ hơn, serialize exception trực tiếp có thể leak stack trace, SQL details, file paths hoặc secrets.

## 3. How does it work?

Pipeline điển hình:

```text
Endpoint/Application throws known exception
             |
             v
Exception handler middleware
             |
             v
Map exception category
             |
             v
status + type + title + detail + extensions
             |
             v
ProblemDetails response
```

Ví dụ domain validation có thể map 400/422; resource missing map 404; concurrency conflict map 409; unknown exception map 500 nhưng không leak details.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();

app.UseExceptionHandler(exceptionHandlerApp =>
{
    exceptionHandlerApp.Run(async context =>
    {
        var exception = context.Features
            .Get<IExceptionHandlerFeature>()?.Error;

        var (status, title) = exception switch
        {
            EntityNotFoundException => (404, "Resource not found"),
            ConcurrencyException => (409, "Concurrency conflict"),
            ValidationException => (422, "Validation failed"),
            _ => (500, "Unexpected server error")
        };

        await Results.Problem(
            statusCode: status,
            title: title,
            extensions: new Dictionary<string, object?>
            {
                ["traceId"] = context.TraceIdentifier
            })
            .ExecuteAsync(context);
    });
});
```

Production logging giữ exception đầy đủ ở server; response chỉ trả information cần thiết.

## 5. Real production scenario

Một Vue frontend gọi 30 APIs. Nếu mỗi API có error schema riêng, UI khó hiển thị validation messages và support team khó correlate user report với logs.

Một `traceId`, stable `type` và predictable status mapping giúp frontend xử lý thống nhất và support tìm đúng trace trong Application Insights.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend nhận 500 cho cả validation lỗi và concurrency conflict.

**Evidence** → logs cho thấy exception categories khác nhau nhưng middleware catch-all map tất cả thành 500.

**Hypothesis** → error taxonomy chưa được thiết kế.

**Diagnosis** → inventory exceptions và HTTP semantics theo use case.

**Fix** → map lỗi deterministic, dùng stable error codes/extensions; giữ unknown error là 500.

**Verification** → contract tests cho 400/401/403/404/409/422/500 và đảm bảo không leak stack trace.

## 7. Common mistakes

* Return `ex.Message` trực tiếp.
* Dùng 200 OK với `{ success:false }` cho mọi lỗi.
* Nhầm 401 và 403.
* Dùng 500 cho business validation.
* Thay đổi error code mà không xem đó là API contract.
* Không gắn correlation/trace identifier.

## 8. Alternatives

Custom error envelope vẫn có thể hợp lý nếu organization đã có mature standard, nhưng nên giữ HTTP semantics đúng. `ProblemDetails` thường giảm việc tự phát minh schema và tích hợp tốt với ASP.NET Core.

## 9. Trade-offs

### Advantages

* Error response thống nhất.
* Dễ document, test và observe.
* Giảm leakage của implementation details.

### Costs / Risks

* Cần error taxonomy rõ ràng.
* Nếu tạo quá nhiều custom codes, contract trở nên khó quản lý.
* Mapping exception-to-HTTP sai có thể che domain semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP status code và response body là API contract.

### Middle

Implement global exception handling và `ProblemDetails` nhất quán.

### Senior

Thiết kế error taxonomy, traceability, backward compatibility và security boundaries.

### Technical Lead / Architect

Định nghĩa organization-wide error contract: status semantics, stable codes, observability fields và versioning policy.

## 11. Key takeaway

* Exception nội bộ không phải public API error model.
* Error contract cần predictable, secure và observable.
* `traceId` hữu ích hơn việc leak stack trace cho client.

# 3. EF Core compiled queries và query hot path: khi compilation cost thực sự đáng quan tâm

## 1. What is it?

EF Core phải biến LINQ expression thành query representation và SQL trước khi database thực thi. EF Core đã cache query compilation theo query shape, nên phần lớn application không cần compiled query thủ công.

`EF.CompileQuery` / `EF.CompileAsyncQuery` cho phép compile query delegate trước, giảm một phần overhead ở repeated hot path.

## 2. Why does it exist?

Trong endpoint cực kỳ hot, query đơn giản chạy hàng trăm nghìn lần, database latency thấp và result nhỏ, client-side query compilation/lookup overhead có thể trở thành measurable fraction của total latency.

Nhưng nếu SQL mất 80 ms, tiết kiệm microseconds ở query compilation gần như không quan trọng.

## 3. How does it work?

Normal path:

```text
LINQ expression
 -> inspect query shape
 -> lookup/compile query
 -> generate command
 -> database
```

Compiled path:

```text
precompiled delegate
 -> bind parameters
 -> database
```

Lợi ích chỉ đáng kể khi query shape ổn định và được gọi rất thường xuyên.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<OrderDto>>
    GetOrder = EF.CompileAsyncQuery(
        (AppDbContext db, Guid id) =>
            db.Orders
                .AsNoTracking()
                .Where(x => x.Id == id)
                .Select(x => new OrderDto(x.Id, x.Status, x.Total)));

public async Task<OrderDto?> FindAsync(Guid id, CancellationToken ct)
{
    await foreach (var item in GetOrder(_db, id).WithCancellation(ct))
    {
        return item;
    }

    return null;
}
```

Trước khi làm vậy, benchmark normal query trong realistic environment.

## 5. Real production scenario

Pricing service đọc một record theo key hàng chục nghìn lần/second từ database colocated với app, query đã được index tốt và latency rất thấp. Profiling chỉ ra EF query overhead đáng kể so với DB execution.

Compiled query có thể hợp lý. Ngược lại, admin reporting query chạy 400 ms vì scan hàng triệu rows sẽ không được cứu bởi compiled query.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries khắp nơi nhưng p95 không thay đổi.

**Evidence** → trace cho thấy 95% thời gian vẫn ở SQL dependency.

**Hypothesis** → optimization nhắm sai bottleneck.

**Diagnosis** → tách application CPU time, EF overhead và database duration.

**Fix** → tập trung access pattern, index, projection hoặc round trips trước.

**Verification** → benchmark end-to-end và allocation/CPU, không chỉ microbenchmark delegate.

## 7. Common mistakes

* Compile mọi query theo cargo-cult.
* Bỏ qua generated SQL.
* Tối ưu EF overhead trước database I/O.
* Dùng dynamic query shape khiến compiled delegate không phù hợp.
* Hy sinh readability mà không có benchmark.

## 8. Alternatives

* Normal EF Core queries với built-in caching.
* Dapper/raw SQL cho read hot path cần control sâu.
* Caching nếu data semantics cho phép.
* Database-level optimization khi execution plan mới là bottleneck.

## 9. Trade-offs

### Advantages

* Có thể giảm EF overhead trong extreme hot path.
* Predictable query shape.

### Costs / Risks

* Boilerplate tăng.
* Flexibility giảm.
* Benefit thường nhỏ so với database/network latency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ phải được dịch sang SQL trước khi chạy.

### Middle

Biết inspect generated SQL và projection trước khi tối ưu nâng cao.

### Senior

Benchmark query pipeline, phân biệt EF overhead với DB execution.

### Technical Lead / Architect

Chỉ cho phép compiled query khi có performance evidence và hot-path ownership rõ ràng.

## 11. Key takeaway

* EF Core đã cache query compilation theo query shape.
* Compiled query là optimization chuyên biệt, không phải default.
* Đo database time trước khi tối ưu ORM overhead.

# 4. SQL Server parameter sniffing, statistics và execution plan regression

## 1. What is it?

SQL Server optimizer chọn execution plan dựa trên query, schema, indexes, statistics và parameter values tại compile time. “Parameter sniffing” mô tả việc optimizer sử dụng parameter value ban đầu để ước lượng cardinality và chọn plan.

Điều này thường tốt — nhưng plan tối ưu cho một parameter có thể rất tệ cho parameter khác khi data distribution lệch mạnh.

## 2. Why does it exist?

Compiling execution plan cho mọi request rất đắt. SQL Server reuse plan để tiết kiệm CPU. Reuse là trade-off: plan phải đủ tốt cho nhiều parameter distributions.

## 3. How does it work?

Ví dụ bảng Orders có 99.9% `Status='Completed'`, nhưng `Status='Failed'` chỉ 0.1%.

Plan compile lần đầu với `Failed` có thể chọn index seek + lookup. Nếu reuse cho `Completed`, hàng triệu lookups có thể tệ hơn scan.

Flow:

```text
parameter
 -> cardinality estimate from statistics
 -> optimizer compares candidate plans
 -> chosen plan cached
 -> reused for later executions
```

## 4. Practical implementation

Bắt đầu bằng measurement:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

EXEC dbo.GetOrdersByStatus @Status = 'Failed';
EXEC dbo.GetOrdersByStatus @Status = 'Completed';
```

Inspect actual execution plan, estimated vs actual rows, logical reads và Query Store history.

Không nên nhảy ngay vào `OPTION (RECOMPILE)`; đó là trade-off CPU-for-plan-quality.

## 5. Real production scenario

Sau data growth, API listing Orders đột nhiên p99 tăng từ 300 ms lên 7 s. Code không đổi. Query Store cho thấy execution plan mới xuất hiện sau statistics update/deployment và logical reads tăng hàng chục lần.

Đây là execution plan regression, không phải “EF Core chậm”.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng query, có parameter chạy 20 ms và parameter khác chạy 5 s.

**Evidence** → estimated rows khác xa actual rows; Query Store có multiple plans.

**Hypothesis** → skewed data + reused plan không phù hợp.

**Diagnosis** → compare plans, statistics histogram và parameter distributions.

**Fix** → tùy case: better index, query rewrite, updated statistics, Query Store plan forcing, `OPTIMIZE FOR`, hoặc recompile có chủ đích.

**Verification** → test representative parameter sets và production-like data.

## 7. Common mistakes

* “Add index” mà không xem plan.
* Clear plan cache toàn server như permanent fix.
* Dùng `OPTION(RECOMPILE)` mọi nơi.
* Test chỉ với một parameter.
* Không dùng Query Store để so regression theo thời gian.

## 8. Alternatives

Plan forcing có thể ổn định nhanh nhưng cần monitoring. Query rewrite hoặc index redesign giải quyết root cause tốt hơn nếu access pattern rõ. Recompile hợp với query ít chạy nhưng distribution cực lệch.

## 9. Trade-offs

### Advantages

* Plan reuse giảm compilation CPU.
* Optimizer thường tạo plan tốt khi statistics đại diện đúng data.

### Costs / Risks

* Skewed distribution làm một plan không phù hợp mọi parameter.
* Statistics stale tạo cardinality errors.
* Mitigation sai có thể chuyển bottleneck sang CPU compilation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu query được optimizer chọn execution plan, không “chạy SQL text trực tiếp” theo nghĩa đơn giản.

### Middle

Đọc actual plan, logical reads, estimated/actual rows.

### Senior

Phân tích parameter distribution, Query Store và plan regression.

### Technical Lead / Architect

Thiết lập production process để monitor slow queries và plan regressions thay vì chữa bằng index ngẫu nhiên.

## 11. Key takeaway

* Query performance phụ thuộc execution plan và data distribution.
* Một plan tốt cho parameter A có thể rất tệ cho B.
* Query Store + representative data quan trọng cho investigation.

# 5. Elasticsearch `text` vs `keyword`, analyzers và mapping decisions ảnh hưởng search quality

## 1. What is it?

Elasticsearch không chỉ lưu string rồi `LIKE`. Mapping quyết định field được index như thế nào.

* `text`: đi qua analyzer để tạo tokens cho full-text search.
* `keyword`: giữ giá trị gần như nguyên khối để exact match, filtering, sorting, aggregation.

Analyzer thường gồm character filters, tokenizer và token filters.

## 2. Why does it exist?

Search “Senior .NET Developer” cần match theo tokens, normalization và relevance. Nhưng filter `status = Published` hoặc sort theo SKU cần exact value semantics.

Nếu mapping sai, query có thể technically chạy nhưng kết quả relevance rất kém hoặc aggregations không hoạt động đúng.

## 3. How does it work?

```text
"Senior .NET Developer"
      |
      v
Analyzer
      |
      +--> tokenizer
      +--> lowercase/normalization
      v
[senior, net, developer]
      |
      v
Inverted Index
```

Một field có thể dùng multi-fields:

```json
"title": {
  "type": "text",
  "fields": {
    "raw": { "type": "keyword" }
  }
}
```

`title` dùng search; `title.raw` dùng sort/exact aggregation.

## 4. Practical implementation

Mapping đơn giản:

```json
PUT products-v1
{
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "analyzer": "standard",
        "fields": {
          "raw": { "type": "keyword" }
        }
      },
      "brand": { "type": "keyword" },
      "description": { "type": "text" }
    }
  }
}
```

Trước khi chọn analyzer custom, dùng `_analyze` để xem tokens thực tế.

## 5. Real production scenario

E-commerce search cần “iphone 15 pro” match product title, nhưng brand filter phải exact. Nếu `brand` được map thành `text`, aggregation/filter behavior có thể gây bất ngờ; nếu `name` chỉ là `keyword`, full-text relevance gần như không có.

## 6. Failure scenario & troubleshooting

**Symptom** → search trả quá ít/không đúng kết quả dù data có tồn tại.

**Evidence** → `_analyze` cho thấy tokenizer tạo tokens khác kỳ vọng hoặc query đang dùng `.raw` field nhầm.

**Hypothesis** → mapping/analyzer không phù hợp language/domain.

**Diagnosis** → inspect mapping, analyze sample text, compare query DSL và tokens.

**Fix** → tạo mapping mới, reindex qua alias; mapping analyzer thường không sửa in-place an toàn cho existing indexed terms.

**Verification** → relevance test set với representative queries.

## 7. Common mistakes

* Dùng `text` cho IDs/status/enums.
* Dùng `keyword` cho full-text paragraphs.
* Tạo analyzer quá phức tạp trước khi có search test set.
* Thay mapping production mà không plan reindex.
* Dùng Elasticsearch như transactional source of truth.

## 8. Alternatives

SQL full-text search có thể đủ với yêu cầu đơn giản và giảm operational complexity. Dedicated search engine hợp lý khi relevance, analyzers, autocomplete, facets hoặc scale search yêu cầu nhiều hơn.

## 9. Trade-offs

### Advantages

* Full-text relevance mạnh.
* Flexible analyzers và multi-fields.
* Aggregations/filtering nhanh trên đúng mapping.

### Costs / Risks

* Mapping decisions khó đổi sau khi index data.
* Reindexing cần operational process.
* Eventual consistency với primary database phải được chấp nhận và monitor.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt exact match với full-text search.

### Middle

Biết chọn `text`, `keyword`, multi-fields và test analyzer.

### Senior

Thiết kế relevance test, reindex strategy, aliases và failure recovery.

### Technical Lead / Architect

Quyết định khi nào Elasticsearch thực sự cần thiết và ai sở hữu consistency/search quality.

## 11. Key takeaway

* Mapping là part of search architecture, không phải schema decoration.
* `text` phục vụ analyzed full-text; `keyword` phục vụ exact semantics.
* Search quality cần test set, không thể đánh giá chỉ bằng “query trả kết quả”.

# 6. Hexagonal Architecture và Anti-Corruption Layer cho third-party integration

## 1. What is it?

Hexagonal Architecture mô hình hóa application core qua **ports** và **adapters**. Core định nghĩa capability cần thiết; infrastructure adapters kết nối SQL, HTTP, queue, CMS hoặc third-party systems.

Anti-Corruption Layer (ACL) là boundary dịch model/protocol của external system sang model nội bộ, ngăn external vocabulary và quirks lan vào domain.

## 2. Why does it exist?

Một vendor API thường có naming, status values, retry semantics và data model riêng. Nếu business code dùng trực tiếp vendor DTO ở khắp nơi, đổi vendor hoặc API version sẽ lan thay đổi toàn hệ thống.

ACL cô lập dependency volatility.

## 3. How does it work?

```text
Application Core
      |
      | Port: IShippingGateway
      v
Shipping Adapter / ACL
      |
      | translate domain <-> vendor DTO
      v
Third-party Shipping API
```

Dependency compile-time hướng vào application-owned interface; adapter phụ thuộc external SDK.

## 4. Practical implementation

Port:

```csharp
public interface IShippingGateway
{
    Task<ShipmentQuote> GetQuoteAsync(
        ShipmentRequest request,
        CancellationToken ct);
}
```

Adapter:

```csharp
public sealed class VendorShippingGateway(HttpClient httpClient)
    : IShippingGateway
{
    public async Task<ShipmentQuote> GetQuoteAsync(
        ShipmentRequest request,
        CancellationToken ct)
    {
        var vendorRequest = new VendorQuoteRequest
        {
            PostalCode = request.DestinationPostalCode,
            WeightGrams = request.Weight.Grams
        };

        var response = await httpClient.PostAsJsonAsync(
            "/v2/quotes", vendorRequest, ct);

        response.EnsureSuccessStatusCode();
        var vendor = await response.Content
            .ReadFromJsonAsync<VendorQuoteResponse>(cancellationToken: ct);

        return new ShipmentQuote(vendor!.Price, vendor.Currency);
    }
}
```

Domain không cần biết `VendorQuoteResponse` tồn tại.

## 5. Real production scenario

Automotive marketplace tích hợp review provider. Vendor gọi rating là `score`, dùng 0–100; domain dùng `Rating` 1–5. ACL chuyển semantics, xử lý missing fields và normalize error conditions.

Khi vendor API đổi field names, chỉ adapter thay đổi thay vì hàng chục services.

## 6. Failure scenario & troubleshooting

**Symptom** → domain logic đầy `if (vendorStatus == "X7")`.

**Evidence** → external DTO xuất hiện trong application/domain projects.

**Hypothesis** → boundary bị leak.

**Diagnosis** → dependency analysis và search vendor namespace references.

**Fix** → đưa translation về adapter/ACL; domain dùng stable internal concepts.

**Verification** → external SDK chỉ được referenced trong infrastructure boundary.

## 7. Common mistakes

* Tạo interface chỉ để mock nhưng DTO vẫn leak.
* ACL trở thành giant generic mapping layer không chứa semantic translation.
* Retry mọi vendor error.
* Hide observability ở adapter khiến incident khó trace.
* Overengineer ports cho internal code không có volatility.

## 8. Alternatives

Simple service wrapper đủ khi integration nhỏ và model gần giống. ACL đáng giá khi external system phức tạp, vendor-specific hoặc có lifecycle độc lập. Microservice riêng chỉ cần khi ownership/deployment/failure isolation thực sự yêu cầu.

## 9. Trade-offs

### Advantages

* Isolate vendor churn.
* Domain vocabulary sạch hơn.
* Testing và migration dễ hơn.

### Costs / Risks

* Mapping code tăng.
* Có thể che mất useful vendor capabilities nếu abstraction quá thấp chung.
* Boundary cần ownership rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain model.

### Middle

Implement adapter và mapping có test.

### Senior

Thiết kế timeout, retries, fallback, telemetry và semantic translation.

### Technical Lead / Architect

Quyết định boundary nào đáng tạo, tránh cả vendor lock-in quá mức lẫn abstraction vô nghĩa.

## 11. Key takeaway

* ACL bảo vệ domain khỏi external vocabulary và quirks.
* Architecture value nằm ở change isolation.
* Không cần port/adapter cho mọi class; chỉ tạo boundary nơi volatility đáng kể.

# 7. Azure Private Endpoint, VNet và DNS: private connectivity thường hỏng ở đâu

## 1. What is it?

Azure Private Endpoint cung cấp private IP trong Virtual Network để truy cập một PaaS resource như Storage, SQL hoặc Key Vault qua private connectivity thay vì public endpoint path.

Điểm thường bị hiểu thiếu là: **private networking không chỉ là IP routing; DNS resolution là một phần thiết yếu của architecture**.

## 2. Why does it exist?

Enterprise systems thường cần hạn chế public network exposure, áp network segmentation và kiểm soát egress/ingress. Private Endpoint cho phép service address vẫn dùng hostname quen thuộc nhưng resolve về private IP trong network context phù hợp.

## 3. How does it work?

Ví dụ Key Vault:

```text
App in VNet
   |
   | DNS query: myvault.vault.azure.net
   v
Private DNS zone
   |
   v
10.x.x.x private endpoint IP
   |
   v
Azure Key Vault
```

Nếu DNS không được link đúng VNet hoặc on-prem resolver không forward đúng zone, app có thể resolve public IP hoặc không resolve được.

## 4. Practical implementation

Application code thường không đổi:

```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://myvault.vault.azure.net"),
    credential);
```

Networking layer chịu trách nhiệm hostname resolve tới private endpoint.

Troubleshooting từ host/container:

```bash
nslookup myvault.vault.azure.net
```

Sau đó kiểm tra route/connectivity tới private IP và authentication riêng biệt.

## 5. Real production scenario

App Service dùng VNet Integration để gọi Azure SQL qua Private Endpoint. Deployment thành công nhưng app timeout khi mở DB connection. Managed Identity đúng, firewall đúng — nhưng DNS vẫn resolve SQL hostname về public endpoint do Private DNS Zone chưa link với VNet.

## 6. Failure scenario & troubleshooting

**Symptom** → connection timeout chỉ ở Production.

**Evidence** → `nslookup` ở production instance trả public IP; dev environment trả private IP.

**Hypothesis** → DNS path sai, không phải credential.

**Diagnosis** → kiểm tra Private DNS Zone link, custom DNS forwarders, VNet integration và effective route.

**Fix** → sửa DNS zone/forwarding; không “fix” bằng mở public network access rộng hơn.

**Verification** → DNS trả private IP và connection telemetry xác nhận private path.

## 7. Common mistakes

* Tạo Private Endpoint nhưng quên DNS.
* Nhầm VNet Integration với inbound private endpoint.
* Mở public access lại để chữa timeout mà không tìm root cause.
* Debug authentication trước khi xác minh basic network resolution.
* Không test từ chính runtime environment.

## 8. Alternatives

Service Endpoints đơn giản hơn ở một số scenarios nhưng security/network semantics khác. Public endpoint + firewall có thể đủ cho lower-risk systems. Private Endpoint tăng isolation nhưng cũng tăng networking operations burden.

## 9. Trade-offs

### Advantages

* Giảm public exposure.
* Private IP-based connectivity.
* Hợp với enterprise network segmentation.

### Costs / Risks

* DNS complexity tăng mạnh.
* Cross-VNet/on-prem resolution cần thiết kế cẩn thận.
* Troubleshooting đòi hỏi network observability và ownership.
* Chi phí resource/networking cao hơn simple public endpoint.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hostname phải resolve đúng IP trước khi application có thể connect.

### Middle

Biết kiểm tra DNS, port connectivity và identity như ba lớp riêng.

### Senior

Debug VNet, Private DNS, App Service integration và hybrid resolution.

### Technical Lead / Architect

Quyết định resource nào cần private connectivity dựa trên threat model, compliance và operational capability của team.

## 11. Key takeaway

* Private Endpoint không hoàn chỉnh nếu DNS chưa đúng.
* Network, DNS và identity là ba failure domains khác nhau.
* Đừng mở public access chỉ để che một lỗi DNS.

# 8. SLI / SLO / SLA với OpenTelemetry và Application Insights: biến telemetry thành reliability decision

## 1. What is it?

* **SLI** là measurement thực tế của service behavior: availability, latency, correctness, freshness...
* **SLO** là target nội bộ cho SLI, ví dụ 99.9% successful requests trong 30 ngày.
* **SLA** là cam kết business/contract, thường kèm consequence nếu vi phạm.

Mental model: telemetry không có giá trị chỉ vì dashboard đẹp; nó phải giúp team quyết định service đang khỏe đến mức nào và khi nào reliability cần ưu tiên hơn feature delivery.

## 2. Why does it exist?

“CPU dưới 70%” không nói users có thành công không. Một service có CPU 20% nhưng trả 500 cho 10% requests vẫn là outage.

SLI/SLO kéo monitoring về user-visible outcomes.

## 3. How does it work?

Availability SLI ví dụ:

```text
successful eligible requests
----------------------------
all eligible requests
```

Latency SLI có thể là percentage requests dưới 500 ms thay vì average latency.

OpenTelemetry thu metrics/traces; Application Insights/Azure Monitor lưu, query và alert.

## 4. Practical implementation

Một ASP.NET Core service có thể tạo custom metric cho business success:

```csharp
private static readonly Meter Meter = new("Checkout.Api");
private static readonly Counter<long> CheckoutSuccess =
    Meter.CreateCounter<long>("checkout.success");
private static readonly Counter<long> CheckoutFailure =
    Meter.CreateCounter<long>("checkout.failure");
```

Nhưng càng tốt nếu tận dụng HTTP request telemetry chuẩn rồi filter đúng eligible traffic: loại health checks, synthetic tests nếu không thuộc user SLI, và phân loại expected 4xx cẩn thận.

## 5. Real production scenario

Checkout có SLO 99.95% successful attempts. Error budget cho phép một lượng nhỏ failure. Sau release, error rate tăng từ 0.02% lên 0.3%; CPU và memory vẫn bình thường.

SLO burn alert phát hiện issue nhanh vì nhìn user outcome, trace sau đó chỉ ra payment dependency regression.

## 6. Failure scenario & troubleshooting

**Symptom** → alerts rất nhiều nhưng không phản ánh customer impact.

**Evidence** → alerts dựa trên CPU, memory, instance count mà không map tới service objective.

**Hypothesis** → monitoring signal-centric thay vì outcome-centric.

**Diagnosis** → map critical user journeys → measurable SLIs → SLOs.

**Fix** → tạo burn-rate alerts và dependency telemetry hỗ trợ RCA.

**Verification** → replay historical incidents xem alerts có phát đúng và ít noise hơn không.

## 7. Common mistakes

* Đặt SLO = 100% mà không xem cost.
* Dùng SLA và SLO như cùng một khái niệm.
* Tính tất cả 4xx là server failure.
* Cardinality quá cao trong metric labels.
* Alert mọi metric thay vì alert service objectives.
* Có traces nhưng không propagate correlation context qua messaging.

## 8. Alternatives

Simple availability/latency dashboards đủ cho small systems. Mature SLO practice đáng giá khi service quan trọng, nhiều teams phụ thuộc hoặc incident cost cao.

## 9. Trade-offs

### Advantages

* Reliability target gắn với user experience.
* Alert quality tốt hơn threshold tùy ý.
* Hỗ trợ prioritization giữa feature và reliability work.

### Costs / Risks

* SLI definition sai sẽ dẫn tới quyết định sai.
* Telemetry storage/cardinality có cost.
* SLO governance cần ownership liên tục.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu metrics, logs, traces phục vụ các câu hỏi khác nhau.

### Middle

Biết query latency/error telemetry và correlate traces.

### Senior

Thiết kế useful SLI, burn-rate alerts và incident evidence loop.

### Technical Lead / Architect

Đặt SLO theo business criticality, dependency model và cost of reliability; không chọn số chỉ vì “five nines nghe tốt”.

## 11. Key takeaway

* SLI đo behavior; SLO đặt target; SLA là business commitment.
* User outcome quan trọng hơn infrastructure metric đơn lẻ.
* Alert nên dẫn đến action, không chỉ tạo noise.

# 9. Contract Testing: bảo vệ API compatibility mà không biến test suite thành E2E khổng lồ

## 1. What is it?

Contract Testing xác minh interface giữa producer và consumer: request shape, response shape, required fields, status semantics hoặc message schema.

Nó nằm giữa unit tests và full E2E: mục tiêu không phải test toàn hệ thống, mà là bắt compatibility break tại integration boundary.

## 2. Why does it exist?

Trong distributed systems, service A có thể deploy độc lập service B. Producer đổi field, enum hoặc endpoint semantics mà unit tests của cả hai vẫn pass vì mỗi repo test riêng.

Chỉ dựa vào E2E thường chậm, flaky và khó cover mọi consumer expectation.

## 3. How does it work?

Consumer-driven flow đơn giản:

```text
Consumer expectation
      |
      v
Contract artifact
      |
      v
Producer verification
      |
      v
Can producer safely deploy?
```

Schema-based testing cũng có giá trị với OpenAPI/AsyncAPI nếu organization quản lý backward compatibility rõ.

## 4. Practical implementation

Ví dụ producer response:

```json
{
  "id": "ord-123",
  "status": "Paid",
  "total": 120.50
}
```

Contract nên bảo vệ fields consumer thực sự cần, không snapshot toàn response một cách brittle.

Ở CI, producer verification chạy trước deployment và fail nếu thay đổi làm contract hiện tại không còn thỏa mãn.

## 5. Real production scenario

Orders API đổi `status` từ string sang nested object để “cleaner”. Producer unit tests pass; frontend compile cũng có thể pass nếu types generated chưa refresh. Contract test sẽ phát hiện response shape break trước production.

## 6. Failure scenario & troubleshooting

**Symptom** → contract suite fail liên tục vì fields consumer không dùng cũng bị snapshot.

**Evidence** → test assert toàn JSON payload.

**Hypothesis** → contract quá chặt và phản ánh implementation thay vì consumer need.

**Diagnosis** → xác định fields/status semantics thực sự required.

**Fix** → narrow contract; dùng compatibility rules thay exact snapshot khi phù hợp.

**Verification** → intentional additive change phải pass, breaking change phải fail.

## 7. Common mistakes

* Dùng contract tests thay toàn bộ integration tests.
* Snapshot mọi field.
* Không version contract artifacts.
* Producer deploy mà không verify active consumer contracts.
* Cho rằng OpenAPI schema tồn tại đồng nghĩa compatibility được kiểm soát.

## 8. Alternatives

Integration tests với real infrastructure phù hợp kiểm tra DB/HTTP behavior nội bộ. E2E bảo vệ critical journeys. Contract tests tập trung boundary compatibility; ba loại không thay thế hoàn toàn nhau.

## 9. Trade-offs

### Advantages

* Feedback nhanh hơn E2E.
* Bắt breaking integration changes sớm.
* Hỗ trợ independent deployment tốt hơn.

### Costs / Risks

* Contract lifecycle cần governance.
* Stale consumer contracts gây false confidence.
* Over-specified contracts tạo brittle tests.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu test cần bảo vệ behavior/risk, không chỉ code coverage.

### Middle

Viết contract cho fields và status semantics consumer cần.

### Senior

Thiết kế compatibility policy, test pyramid và CI verification flow.

### Technical Lead / Architect

Quyết định boundary nào cần contract testing dựa trên independent deployments, ownership và blast radius.

## 11. Key takeaway

* Contract tests bảo vệ integration boundary, không phải toàn system behavior.
* Contract càng sát consumer need càng ít brittle.
* Kết hợp unit, integration, contract và E2E theo risk.

# 10. Modernize `.NET Framework` sang modern .NET theo chiến lược incremental migration

## 1. What is it?

Modernization không đồng nghĩa rewrite. Với hệ thống `.NET Framework` lớn, mục tiêu thường là giảm platform constraint, nâng runtime/supportability và mở đường cho modern hosting/deployment trong khi giữ business continuity.

Incremental migration chia modernization thành boundaries có thể deploy và rollback thay vì “big bang rewrite”.

## 2. Why does it exist?

Legacy application thường chứa hàng năm business rules, integrations và undocumented behavior. Rewrite toàn bộ có rủi ro chức năng cao dù code mới đẹp hơn.

Ngoài source code, migration còn liên quan packages, configuration, authentication, hosting, Windows dependencies, EF version, build pipeline và deployment model.

## 3. How does it work?

Một progression thực tế có thể là:

```text
Inventory dependencies
      |
      v
Separate portable business/application components
      |
      v
Introduce compatibility boundary / strangler endpoints
      |
      v
Move workloads incrementally to modern .NET
      |
      v
Observe + compare behavior
      |
      v
Retire legacy slice
```

Không nhất thiết đi tuần tự `.NET Core -> .NET 6 -> .NET 8`; target runtime nên dựa trên supported destination và package compatibility hiện tại.

## 4. Practical implementation

Bước đầu tiên nên là inventory:

```text
- .NET Framework target version
- System.Web dependencies
- WCF/remoting usage
- Windows-only APIs
- Entity Framework 6 usage
- NuGet packages and unsupported versions
- authentication middleware
- IIS-specific configuration
- scheduled Windows tasks/services
- COM/native dependencies
```

Một strategy phổ biến là tách use case mới sang ASP.NET Core service hoặc module, rồi route một phần traffic sang implementation mới thay vì rewrite toàn monolith.

## 5. Real production scenario

Enterprise CMS/e-commerce app chạy `.NET Framework` trên IIS, có 200+ projects và nhiều third-party integrations. Team muốn containerize và dùng modern observability.

Thay vì rewrite, họ migrate shared libraries tương thích trước, tạo modern API boundary cho một domain ít coupling, deploy song song và dùng feature flag/router để chuyển traffic từng phần.

## 6. Failure scenario & troubleshooting

**Symptom** → migration project kéo dài nhiều tháng mà chưa deploy được business value nào.

**Evidence** → branch khổng lồ, mọi team chờ toàn bộ system “xong” mới release.

**Hypothesis** → big-bang migration không có deployable slices.

**Diagnosis** → dependency graph và architecture boundaries chưa được phân tích.

**Fix** → chọn vertical slice nhỏ, define compatibility contract, deploy incrementally, giữ rollback path.

**Verification** → compare functional tests, telemetry, error rate và performance giữa legacy/new path.

## 7. Common mistakes

* Rewrite vì “legacy code xấu”.
* Upgrade runtime mà không inventory packages.
* Quên Windows/IIS-specific behavior.
* Thay database + architecture + frontend + runtime cùng lúc.
* Không có parity tests hoặc production telemetry comparison.
* Không plan rollback.

## 8. Alternatives

Nếu application ổn định, ít thay đổi và migration cost cao hơn business value, giữ nguyên có thể là quyết định hợp lý trong ngắn hạn. Lift-and-shift hosting không giải quyết technical debt nhưng đôi khi giảm immediate infrastructure risk. Full rewrite chỉ phù hợp khi domain/requirements cũng thay đổi mạnh và organization chấp nhận risk.

## 9. Trade-offs

### Advantages

* Incremental migration giảm blast radius.
* Cho phép học từ production từng slice.
* Tránh “rewrite parity trap”.

### Costs / Risks

* Một thời gian phải vận hành hai stacks.
* Compatibility adapters và duplicate infrastructure tăng complexity tạm thời.
* Migration kéo dài nếu không có clear retirement milestones.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu runtime upgrade không chỉ là đổi target framework.

### Middle

Biết inventory packages, configuration, hosting và tests.

### Senior

Thiết kế vertical migration slice, parity verification và rollback.

### Technical Lead / Architect

Quyết định migrate, rewrite hay retain dựa trên business change rate, support risk, team capacity và dependency graph; chịu trách nhiệm roadmap retire legacy components.

## 11. Key takeaway

* Modernization là risk-management exercise, không phải code-style project.
* Incremental migration thường an toàn hơn big-bang rewrite.
* Package, hosting, identity, data và deployment compatibility quan trọng ngang source code.
