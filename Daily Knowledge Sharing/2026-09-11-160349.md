# 1. .NET `Channel<T>` và backpressure

## 1. What is it?
`Channel<T>` là producer/consumer primitive bất đồng bộ trong .NET. Điểm quan trọng là bounded channel có thể tạo backpressure khi producer nhanh hơn consumer.

## 2. Why does it exist?
Nếu producer tạo work nhanh hơn downstream xử lý, queue không giới hạn sẽ làm memory và số task pending tăng liên tục. Backpressure buộc upstream chậm lại theo capacity thực tế.

## 3. How does it work?
```text
Producer -> bounded Channel<T> -> Consumer
              full => producer waits
```
`WriteAsync` chờ khi buffer đầy thay vì tiếp tục allocation vô hạn.

## 4. Practical implementation
```csharp
var channel = Channel.CreateBounded<Job>(100);

async Task ProduceAsync(IEnumerable<Job> jobs, CancellationToken ct)
{
    foreach (var job in jobs)
        await channel.Writer.WriteAsync(job, ct);
    channel.Writer.Complete();
}

async Task ConsumeAsync(CancellationToken ct)
{
    await foreach (var job in channel.Reader.ReadAllAsync(ct))
        await ProcessAsync(job, ct);
}
```

## 5. Real production scenario
Worker enrich hàng trăm nghìn product qua third-party API. Bounded channel giữ backlog hữu hạn thay vì tạo hàng trăm nghìn `Task` cùng lúc.

## 6. Failure scenario & troubleshooting
**Symptom** → memory tăng, GC dày, throughput không tăng. **Evidence** → backlog tăng nhanh. **Diagnosis** → producer outruns consumer. **Fix** → bounded channel + giới hạn concurrency. **Verification** → queue depth và memory ổn định dưới load test dài.

## 7. Common mistakes
Dùng unbounded channel cho input vô hạn; tăng consumer vượt quota downstream; không `Complete`; không propagate cancellation.

## 8. Alternatives
`TPL Dataflow` cho pipeline phức tạp hơn; Azure Service Bus khi cần durability và scale-out.

## 9. Trade-offs
### Advantages
Backpressure đơn giản, async-friendly, ít allocation hơn cách tạo task đại trà.
### Costs / Risks
Không durable; capacity sai có thể giảm throughput hoặc tăng memory.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu producer và consumer có tốc độ khác nhau.
### Middle
Biết tạo bounded channel và shutdown đúng.
### Senior
Đo throughput, backlog, downstream saturation.
### Technical Lead / Architect
Quyết định khi nào in-process queue đủ và khi nào phải dùng durable broker.

## 11. Key takeaway
- Backpressure là reliability mechanism.
- Queue depth cần hữu hạn.
- `Channel<T>` không thay thế message broker.

# 2. ASP.NET Core DI lifetime trong `BackgroundService`

## 1. What is it?
`BackgroundService` là singleton, trong khi `DbContext` thường scoped. Singleton không nên giữ scoped dependency xuyên suốt process lifetime.

## 2. Why does it exist?
Background worker không có HTTP request tự nhiên để tạo DI scope. Nếu giữ `DbContext` quá lâu, change tracker phình ra và concurrent usage dễ xảy ra.

## 3. How does it work?
Worker inject `IServiceScopeFactory`, tạo scope cho từng batch/unit of work, rồi dispose scope sau khi xử lý xong.

## 4. Practical implementation
```csharp
public sealed class Worker(IServiceScopeFactory scopes) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await using var scope = scopes.CreateAsyncScope();
            var processor = scope.ServiceProvider.GetRequiredService<IProcessor>();
            await processor.ProcessAsync(ct);
            await Task.Delay(1000, ct);
        }
    }
}
```

## 5. Real production scenario
Invoice worker dùng EF Core. Scope theo batch giúp mỗi batch có `DbContext` mới và transaction boundary rõ.

## 6. Failure scenario & troubleshooting
**Symptom** → memory tăng, tracking state lạ, `DbContext` concurrency exception. **Evidence** → cùng context sống xuyên nhiều vòng lặp. **Fix** → resolve scoped dependency trong scope ngắn hạn.

## 7. Common mistakes
Inject `DbContext` trực tiếp; giữ một scope duy nhất; dùng chung scoped service cho parallel work; bỏ `stoppingToken`.

## 8. Alternatives
`IDbContextFactory<TContext>` phù hợp nếu chủ yếu cần tạo context theo work item.

## 9. Trade-offs
### Advantages
Lifetime rõ, cleanup tốt, giảm state leakage.
### Costs / Risks
Scope quá nhỏ tạo overhead; quá lớn lại giữ resource lâu.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Phân biệt singleton và scoped.
### Middle
Biết dùng `IServiceScopeFactory`.
### Senior
Thiết kế scope theo unit of work và shutdown đúng.
### Technical Lead / Architect
Quyết định worker nằm cùng web host hay tách service riêng.

## 11. Key takeaway
- Hosted service là singleton.
- Scoped dependency phải được resolve trong scope phù hợp.
- Scope nên bám theo unit of work.

# 3. EF Core compiled query

## 1. What is it?
Compiled query cho phép EF Core chuẩn bị trước một query shape và tái sử dụng delegate thay vì lặp lại một phần query-compilation work ở hot path.

## 2. Why does it exist?
Một số query rất đơn giản nhưng được gọi cực nhiều lần; lúc đó application CPU cho query pipeline có thể trở thành measurable overhead.

## 3. How does it work?
```csharp
private static readonly Func<AppDbContext, Guid, Task<User?>> Query =
    EF.CompileAsyncQuery((AppDbContext db, Guid id) =>
        db.Users.AsNoTracking().FirstOrDefault(x => x.Id == id));
```
Parameter vẫn truyền runtime; query shape được tái sử dụng.

## 4. Practical implementation
Chỉ áp dụng sau profiling/benchmark. Nếu SQL mất 200 ms thì giảm vài micro/milliseconds ở query compilation không giải quyết bottleneck chính.

## 5. Real production scenario
Permission lookup rất đơn giản chạy hàng chục nghìn lần/giây; profiling cho thấy EF query pipeline tiêu tốn CPU đáng kể.

## 6. Failure scenario & troubleshooting
**Symptom** → thêm compiled query nhưng latency gần như không đổi. **Evidence** → trace cho thấy thời gian vẫn nằm ở SQL. **Fix** → tối ưu execution plan, projection, index hoặc round-trip count.

## 7. Common mistakes
Compile mọi query; bỏ qua N+1; tăng ceremony mà không đo trước/sau.

## 8. Alternatives
Query cache mặc định của EF Core thường đủ; Dapper/raw SQL khi cần kiểm soát thấp hơn nhưng tăng maintenance.

## 9. Trade-offs
### Advantages
Giảm application CPU ở hot query lặp lại nhiều.
### Costs / Risks
Thêm code ceremony và dễ tối ưu sai layer.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu LINQ phải được translate sang SQL.
### Middle
Biết dùng compiled query đúng API.
### Senior
Phân biệt EF overhead với database latency.
### Technical Lead / Architect
Không biến micro-optimization thành coding standard nếu chưa có evidence.

## 11. Key takeaway
- Compiled query là optimization có điều kiện.
- Measure trước.
- SQL/round-trip thường quan trọng hơn.

# 4. SQL Server isolation levels

## 1. What is it?
Isolation level quyết định transaction nhìn thấy thay đổi của transaction khác như thế nào và SQL Server phải dùng lock hoặc row versioning ra sao.

## 2. Why does it exist?
Concurrent read/write có thể tạo anomaly. Consistency mạnh hơn thường đổi lấy blocking, deadlock hoặc version-store cost.

## 3. How does it work?
`READ COMMITTED` thường dùng locking; `READ_COMMITTED_SNAPSHOT` dùng row versions cho reader; `SERIALIZABLE` có thể giữ range locks để ngăn phantom.

## 4. Practical implementation
```csharp
await using var tx = await db.Database.BeginTransactionAsync(
    IsolationLevel.Serializable, ct);
// critical invariant work
await tx.CommitAsync(ct);
```
Không dùng `Serializable` mặc định; chỉ chọn khi invariant thực sự cần.

## 5. Real production scenario
Checkout đồng thời trên SKU tồn kho thấp. Isolation phải bảo vệ inventory invariant mà không làm toàn hệ thống chịu blocking quá mức.

## 6. Failure scenario & troubleshooting
**Symptom** → latency tăng khi traffic cao. **Evidence** → blocking chain/lock waits. **Diagnosis** → transaction dài hoặc isolation quá mạnh. **Fix** → thu hẹp transaction, dùng row-versioning/optimistic concurrency khi phù hợp.

## 7. Common mistakes
Dùng `NOLOCK` như thuốc chữa blocking; giữ transaction qua HTTP call; chọn mức mạnh nhất cho mọi request.

## 8. Alternatives
Optimistic concurrency cho user edits; application-level coordination cho một số business workflows.

## 9. Trade-offs
### Advantages
Isolation đúng giúp bảo vệ invariant.
### Costs / Risks
Mức mạnh hơn có thể giảm throughput và tăng contention.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu transaction có thể chạy đồng thời.
### Middle
Biết transaction scope và isolation cơ bản.
### Senior
Đọc lock waits và versioning behavior.
### Technical Lead / Architect
Xác định nơi cần strong consistency và nơi optimistic/eventual là đủ.

## 11. Key takeaway
- Isolation là trade-off.
- Transaction scope rất quan trọng.
- Business invariant phải dẫn dắt lựa chọn.

# 5. Redis distributed lock và lease expiry

## 1. What is it?
Distributed lock cho nhiều process phối hợp quyền thực hiện một critical section. Trong Redis, lock thường là key có unique token và TTL.

## 2. Why does it exist?
`lock`/`SemaphoreSlim` chỉ bảo vệ trong một process. Multi-instance scheduled job có thể cần coordination ngoài process.

## 3. How does it work?
```text
SET job:lock <token> NX PX 30000
```
Owner có lease 30 giây. Nếu TTL hết trước khi work hoàn tất, instance khác có thể acquire lock mới trong khi owner cũ vẫn chạy.

## 4. Practical implementation
Release phải atomically kiểm tra token trước khi xóa key, thường bằng Lua. Work quan trọng còn cần idempotency hoặc fencing token ở downstream.

## 5. Real production scenario
Job chạy 4 phút nhưng lock TTL 60 giây. Sau phút đầu, instance thứ hai acquire lock và xử lý trùng.

## 6. Failure scenario & troubleshooting
**Symptom** → duplicate execution hiếm gặp. **Evidence** → job duration vượt TTL. **Fix** → renewal, fencing, idempotency hoặc redesign bằng queue/leader mechanism.

## 7. Common mistakes
`DEL` lock không kiểm tra owner; TTL quá ngắn; nghĩ lock đảm bảo exactly-once; dùng lock thay cho unique constraint.

## 8. Alternatives
Database advisory lock, leader election, queue competing consumers, hoặc làm operation idempotent.

## 9. Trade-offs
### Advantages
Coordination nhanh và đơn giản cho một số singleton work.
### Costs / Risks
Lease expiry, Redis outage và split-brain tạo correctness risk.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu in-process lock không bảo vệ nhiều instances.
### Middle
Biết token + TTL.
### Senior
Hiểu renewal, fencing và idempotency.
### Technical Lead / Architect
Đánh giá có thật sự cần distributed lock hay có design đơn giản hơn.

## 11. Key takeaway
- Distributed lock là lease.
- TTL expiry có thể tạo nhiều owner.
- Downstream vẫn cần bảo vệ invariant.

# 6. CQRS với một database vs separate read/write stores

## 1. What is it?
CQRS tách command thay đổi state khỏi query chỉ đọc state. CQRS không bắt buộc phải có hai database hay Event Sourcing.

## 2. Why does it exist?
Write model tập trung invariant; read model có thể tối ưu projection cho UI. CRUD model duy nhất đôi khi làm hai nhu cầu này kéo nhau theo hướng khó maintain.

## 3. How does it work?
```text
Command -> handler -> write model -> SQL
Query   -> handler -> projection  -> SQL
```
Khi tách read store:
```text
Write DB -> event/change feed -> Read Store
```
Từ đó xuất hiện eventual consistency.

## 4. Practical implementation
Command handler load aggregate và `SaveChanges`; query handler dùng `AsNoTracking()` + projection DTO trực tiếp.

## 5. Real production scenario
Expense workflow có approval rule phức tạp nhưng dashboard chỉ cần dữ liệu phẳng. CQRS một database đã đủ tách responsibilities mà chưa cần thêm broker/read store.

## 6. Failure scenario & troubleshooting
Với read store riêng, **symptom** là command thành công nhưng UI chưa thấy thay đổi. Kiểm tra sync lag, outbox/change feed và failed projection.

## 7. Common mistakes
Đồng nhất CQRS với MediatR; mặc định phải tách DB; mặc định phải dùng Event Sourcing; không định nghĩa consistency expectation.

## 8. Alternatives
Layered CRUD service phù hợp với domain đơn giản.

## 9. Trade-offs
### Advantages
Intent rõ và read/write có thể tối ưu riêng.
### Costs / Risks
Separate stores thêm messaging, rebuild, lag và operational complexity.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Phân biệt command và query.
### Middle
Implement handler/projection rõ ràng.
### Senior
Xử lý read-model lag và rebuild.
### Technical Lead / Architect
Chọn mức CQRS tối thiểu đủ đáp ứng business/scale.

## 11. Key takeaway
- CQRS bắt đầu từ separation of intent.
- Hai database là tùy chọn nâng cao.
- Eventual consistency phải được thiết kế khi tách store.

# 7. Azure Service Bus dead-letter queue

## 1. What is it?
DLQ chứa message không thể xử lý thành công hoặc vượt delivery rules để main queue không bị poison message giữ chân.

## 2. Why does it exist?
Permanent failure không nên retry vô hạn. DLQ tạo quarantine boundary để hệ thống tiếp tục xử lý message hợp lệ.

## 3. How does it work?
```text
Queue -> Consumer
        -> success: Complete
        -> transient: retry
        -> permanent: DeadLetter
DLQ -> investigate -> fix -> controlled replay
```

## 4. Practical implementation
```csharp
catch (ValidationException ex)
{
    await args.DeadLetterMessageAsync(
        args.Message,
        "InvalidPayload",
        ex.Message,
        args.CancellationToken);
}
```

## 5. Real production scenario
Producer đổi schema nhưng consumer cũ chưa compatible. Message mới không deserialize được; DLQ giữ message để main queue tiếp tục.

## 6. Failure scenario & troubleshooting
**Symptom** → DLQ depth tăng. **Evidence** → dead-letter reason tập trung ở một schema/version. **Fix** → sửa consumer/contract rồi replay có kiểm soát.

## 7. Common mistakes
Không alert DLQ; auto-replay mù quáng; log PII trong reason; không version event contract.

## 8. Alternatives
Delayed retry cho transient failure; parking-lot queue riêng cho workflow xử lý đặc biệt.

## 9. Trade-offs
### Advantages
Cô lập poison message và giữ evidence.
### Costs / Risks
Cần ownership, alerting, runbook và replay tooling.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Phân biệt retry và dead-letter.
### Middle
Phân loại transient/permanent failure.
### Senior
Thiết kế replay idempotent và monitoring.
### Technical Lead / Architect
Định nghĩa SLO/ownership cho DLQ và contract evolution.

## 11. Key takeaway
- DLQ là quarantine, không phải thùng rác.
- Replay phải có kiểm soát.
- DLQ depth là production signal.

# 8. OpenTelemetry context propagation

## 1. What is it?
Context propagation mang trace/span identity qua HTTP, messaging và async boundaries để telemetry từ nhiều service nối thành cùng một distributed trace.

## 2. Why does it exist?
Không có shared trace context, điều tra một request xuyên API, worker, SQL và external HTTP phải ghép log bằng timestamp thủ công.

## 3. How does it work?
W3C Trace Context dùng `traceparent`; instrumentation tạo child spans cho dependency calls và downstream service tiếp tục cùng trace.

## 4. Practical implementation
```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation()
        .AddOtlpExporter());
```

## 5. Real production scenario
Checkout chậm. Trace cho thấy API chỉ dùng 40 ms nhưng pricing dependency mất 1.8 s, trong đó SQL của pricing mất 1.6 s.

## 6. Failure scenario & troubleshooting
**Symptom** → trace đứt giữa producer/consumer. **Evidence** → consumer có trace ID mới. **Fix** → inject/extract context trong message properties và kiểm tra instrumentation.

## 7. Common mistakes
Chỉ instrument incoming HTTP; gắn PII vào tags; tạo quá nhiều spans; sampling quá mạnh mà không hiểu hậu quả.

## 8. Alternatives
Application Insights proprietary instrumentation có thể đủ trong Azure-centric system; structured logs vẫn cần thiết.

## 9. Trade-offs
### Advantages
Giảm thời gian localize failure xuyên service.
### Costs / Risks
Telemetry volume, sampling, cardinality và storage cost.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu trace gồm nhiều spans.
### Middle
Instrument ASP.NET Core/HttpClient/EF Core.
### Senior
Thiết kế propagation qua messaging và sampling.
### Technical Lead / Architect
Đặt observability standard và telemetry budget toàn hệ thống.

## 11. Key takeaway
- Context phải đi qua mọi boundary quan trọng.
- Traces không thay logs/metrics.
- Observability cũng có cost và privacy boundary.

# 9. IIS Application Pool recycling

## 1. What is it?
IIS Application Pool quản lý worker process `w3wp.exe`; recycling tạo process mới theo policy hoặc condition.

## 2. Why does it exist?
Recycle giúp áp config mới hoặc phục hồi process, nhưng với application nó vẫn là một dạng restart và làm mất in-memory state.

## 3. How does it work?
```text
App Pool -> old w3wp -> recycle -> new w3wp -> old process drains/exits
```
Startup, cache warm-up và connection initialization xảy ra lại.

## 4. Practical implementation
Application cần restart-safe: không coi process memory là durable storage; background work phải shutdown đúng; health/warm-up phải phản ánh readiness.

## 5. Real production scenario
Commerce site dùng in-memory session. Scheduled recycle làm user mất session và first requests chậm vì cache cold.

## 6. Failure scenario & troubleshooting
**Symptom** → latency/error spike theo chu kỳ. **Evidence** → IIS/Windows logs cho thấy recycle cùng thời điểm. **Fix** → externalize critical state, warm-up và điều chỉnh policy nếu thực sự cần.

## 7. Common mistakes
Dùng recycle để che memory leak; không biết recycle schedule; giữ critical session trong process.

## 8. Alternatives
Azure App Service/container có lifecycle khác nhưng process restart vẫn là failure mode bình thường.

## 9. Trade-offs
### Advantages
Process renewal và operational recovery.
### Costs / Risks
Cold start, cache loss, interrupted background work.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu worker process không chạy vĩnh viễn.
### Middle
Biết xem recycle settings/logs.
### Senior
Phân tích warm-up và restart safety.
### Technical Lead / Architect
Thiết kế application stateless/restart-safe theo availability target.

## 11. Key takeaway
- Recycle là restart có kiểm soát.
- Critical state không nên chỉ sống trong process.
- Test restart như production failure mode bình thường.

# 10. Vue.js / TypeScript stale request cancellation

## 1. What is it?
Stale request race xảy ra khi response của request cũ về sau request mới và ghi đè state hiện tại.

## 2. Why does it exist?
Network không đảm bảo response order. Search-as-you-type là ví dụ điển hình.

## 3. How does it work?
```text
q=car  ----800ms----> old response
q=cars --150ms--> new response
```
Nếu old response update state cuối cùng, UI hiển thị dữ liệu stale.

## 4. Practical implementation
```ts
let controller: AbortController | null = null;

async function search(q: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(
    `/api/products?q=${encodeURIComponent(q)}`,
    { signal: controller.signal });

  return response.json();
}
```
Phân biệt `AbortError` với lỗi thật để không hiện error toast sai.

## 5. Real production scenario
User gõ `audi`; request cho `a` về cuối và dropdown nhảy về kết quả broad của `a`.

## 6. Failure scenario & troubleshooting
**Symptom** → UI thỉnh thoảng “nhảy ngược”. **Evidence** → DevTools cho thấy response order khác request order. **Fix** → abort request cũ hoặc dùng sequence number và chỉ apply response mới nhất.

## 7. Common mistakes
Nghĩ debounce tự loại bỏ race; không cancel khi component unmount; coi abort là user-facing error; backend không propagate cancellation.

## 8. Alternatives
Sequence/version token; TanStack Query cho state/cache phức tạp hơn.

## 9. Trade-offs
### Advantages
UI nhất quán hơn và giảm wasted work.
### Costs / Risks
Async state/cancellation logic phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu request gửi trước không chắc response về trước.
### Middle
Dùng `AbortController` và lifecycle cleanup.
### Senior
Thiết kế client state chống race và phối hợp backend cancellation.
### Technical Lead / Architect
Chuẩn hóa data-fetching pattern cho retry/cache/stale behavior.

## 11. Key takeaway
- Async UI có race condition.
- Debounce và cancellation giải quyết hai vấn đề khác nhau.
- Chỉ response còn hợp lệ với state hiện tại mới được update UI.
