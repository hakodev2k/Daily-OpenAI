# 1. .NET `Channel<T>` và backpressure trong producer/consumer pipelines

## 1. What is it?

Mental model: `Channel<T>` là một asynchronous queue trong process, tách producer khỏi consumer. Điểm quan trọng không phải chỉ là “queue dữ liệu”, mà là **backpressure**: khi consumer chậm hơn producer, hệ thống phải có chính sách rõ ràng thay vì để memory tăng vô hạn.

## 2. Why does it exist?

Một producer có thể nhận 5.000 events/s trong khi consumer chỉ xử lý 1.000 events/s. Nếu dùng `ConcurrentQueue<T>` rồi liên tục enqueue, queue có thể tăng cho tới khi process gặp memory pressure. Bounded channel biến capacity thành một phần của design.

## 3. How does it work?

```text
Producer -> bounded Channel<T> -> Consumer
              |
              +-- full -> wait / drop according to policy
```

`ChannelWriter<T>.WriteAsync` có thể asynchronous wait khi channel đầy. Consumer dùng `ReadAllAsync` để đọc tới khi writer complete.

## 4. Practical implementation

```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = false
});

await channel.Writer.WriteAsync(job, cancellationToken);

await foreach (var item in channel.Reader.ReadAllAsync(stoppingToken))
{
    await ProcessAsync(item, stoppingToken);
}
```

Capacity phải dựa trên throughput, acceptable buffering và memory footprint, không chọn tùy ý.

## 5. Real production scenario

API nhận requests tạo thumbnail. Request chỉ validate và enqueue work vào channel; một `BackgroundService` xử lý tối đa N jobs đồng thời. Khi image processor chậm, bounded channel làm producer chờ hoặc reject có kiểm soát thay vì ăn hết RAM.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng liên tục, GC frequency tăng, latency cuối cùng spike. **Evidence** → producer throughput lớn hơn consumer throughput và queue depth tăng. **Hypothesis** → unbounded buffering. **Diagnosis** → đo arrival rate, processing rate, queue depth và item size. **Fix** → bounded channel + concurrency limit + admission control. **Verification** → load test khi downstream cố tình chậm.

## 7. Common mistakes

Dùng unbounded channel cho workload không bounded; spawn `Task.Run` cho mỗi item; không complete writer khi shutdown; bỏ qua cancellation; coi in-memory channel là durable queue.

## 8. Alternatives

`SemaphoreSlim` phù hợp giới hạn concurrency nhưng không phải queue. Azure Service Bus phù hợp khi cần durability, cross-process delivery và retry. `BlockingCollection<T>` phù hợp hơn với synchronous producer/consumer legacy code.

## 9. Trade-offs

### Advantages

API rõ cho asynchronous producer/consumer, bounded capacity, ít coordination code.

### Costs / Risks

Không durable; process crash làm mất buffered work. Capacity và full-mode sai có thể tăng latency hoặc drop work.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu producer và consumer có tốc độ khác nhau.

### Middle
Implement bounded channel, cancellation và graceful completion.

### Senior
Thiết kế backpressure từ throughput/memory evidence và xử lý overload.

### Technical Lead / Architect
Quyết định khi nào in-process queue đủ và khi nào workload phải chuyển sang durable broker.

## 11. Key takeaway

- Queue không bounded là deferred failure.
- Backpressure là behavior phải thiết kế, không phải implementation detail.
- `Channel<T>` không thay thế durable messaging.

# 2. ASP.NET Core `ProblemDetails`: error contract ổn định thay vì exception-shaped API

## 1. What is it?

`ProblemDetails` là representation chuẩn hóa cho HTTP API errors. Mental model: exception là implementation detail; API error là **public contract** dành cho caller.

## 2. Why does it exist?

Nếu mỗi endpoint trả `{ error: ... }`, `{ message: ... }` hoặc raw exception khác nhau, client phải viết branching logic theo từng endpoint. Tệ hơn, expose exception có thể leak stack trace, SQL hoặc internal identifiers.

## 3. How does it work?

Request failure được map từ domain/application/infrastructure condition sang HTTP semantics:

```text
Domain conflict -> 409 ProblemDetails
Validation      -> 400/422 ProblemDetails
Missing entity  -> 404 ProblemDetails
Unexpected bug  -> 500 generic ProblemDetails + correlation id
```

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();
app.UseExceptionHandler();
app.UseStatusCodePages();
```

Custom mapping nên giữ `type`, `title`, `status`, `detail`, `instance` ổn định và có machine-readable error code nếu clients cần branching.

## 5. Real production scenario

Mobile app và web app cùng gọi approval API. Business rule “timesheet already approved” được trả `409` với code `timesheet_already_approved`; cả hai clients xử lý ổn định dù backend refactor exception hierarchy.

## 6. Failure scenario & troubleshooting

**Symptom** → client production bắt đầu fail parse sau backend deployment. **Evidence** → error payload shape thay đổi theo exception mới. **Hypothesis** → API contract phụ thuộc implementation exception. **Diagnosis** → compare responses trước/sau. **Fix** → central mapping và contract tests. **Verification** → regression tests cho known failure classes.

## 7. Common mistakes

Trả 200 với `success=false`; expose stack trace; dùng 500 cho validation; đưa localized text làm machine identifier; tạo hàng trăm error shapes.

## 8. Alternatives

Custom error envelope vẫn có thể tốt nếu organization đã có mature contract, nhưng cần cùng discipline. gRPC dùng status/details semantics khác HTTP REST.

## 9. Trade-offs

### Advantages

Consistency, client interoperability, observability và security tốt hơn.

### Costs / Risks

Cần governance cho status/code mapping và backward compatibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Phân biệt HTTP status với exception type.

### Middle
Map validation/not-found/conflict đúng semantics.

### Senior
Thiết kế stable error codes, correlation và information disclosure policy.

### Technical Lead / Architect
Chuẩn hóa error contract xuyên services mà không coupling clients vào internal implementation.

## 11. Key takeaway

- Error response là API contract.
- Exception không nên tự động trở thành wire format.
- Stable machine codes quan trọng hơn message text cho client logic.

# 3. SQL keyset pagination: scale pagination mà không trả giá tuyến tính cho `OFFSET`

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên giá trị sort key cuối cùng đã thấy, thay vì yêu cầu database bỏ qua N rows.

## 2. Why does it exist?

`OFFSET 500000 ROWS FETCH NEXT 50 ROWS` vẫn buộc engine tìm/đi qua một lượng lớn rows trước khi trả 50 rows. Với feed lớn, latency tăng theo page depth.

## 3. How does it work?

Nếu sort bằng `(CreatedAt DESC, Id DESC)`, cursor chứa cặp cuối trang trước:

```sql
WHERE CreatedAt < @LastCreatedAt
   OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC
```

Index phù hợp cho phép seek gần vị trí cần đọc.

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON dbo.Orders (CreatedAt DESC, Id DESC)
INCLUDE (CustomerId, Status);
```

Query phải có deterministic ordering; `Id` thường đóng vai trò tie-breaker.

## 5. Real production scenario

Audit log có 80 triệu rows. UI chủ yếu “next page”. Offset pagination page sâu mất vài giây; keyset pagination giữ latency gần ổn định vì seek theo cursor.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate hoặc missing rows giữa pages. **Evidence** → sort chỉ theo non-unique `CreatedAt`. **Hypothesis** → cursor không định nghĩa total ordering. **Diagnosis** → tìm timestamp trùng nhau. **Fix** → thêm stable unique tie-breaker vào ORDER BY/cursor/index. **Verification** → pagination test với nhiều rows cùng timestamp và concurrent inserts.

## 7. Common mistakes

Cursor chỉ chứa một non-unique field; encode cursor nhưng không validate; index order không khớp query; dùng keyset khi UX cần nhảy trực tiếp tới page 937.

## 8. Alternatives

Offset pagination đơn giản và hợp lý cho dataset nhỏ hoặc shallow pages. Search engine `search_after` dùng ý tưởng tương tự cho deep pagination.

## 9. Trade-offs

### Advantages

Deep-page performance ổn định hơn và ít scan bỏ phí.

### Costs / Risks

Không thuận tiện cho random page numbers; cursor contract phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu `OFFSET` không làm database “teleport” tới row N.

### Middle
Implement deterministic cursor và index.

### Senior
Đọc execution plan/I/O và xử lý concurrent data changes.

### Technical Lead / Architect
Chọn pagination semantics dựa trên UX, scale và consistency expectations.

## 11. Key takeaway

- Deep offset có cost thật.
- Keyset cần deterministic total ordering.
- Cursor và index phải được thiết kế cùng nhau.

# 4. Modular Monolith: module boundary, data ownership và transaction boundary

## 1. What is it?

Modular Monolith là một deployable application nhưng bên trong có các modules với ownership và dependency boundaries rõ ràng. Nó không phải chỉ là nhiều folders trong cùng solution.

## 2. Why does it exist?

Một monolith không boundary dễ trở thành shared-everything codebase; microservices lại thêm network, deployment, observability và consistency complexity. Modular Monolith giữ operational simplicity trong khi cô lập business complexity.

## 3. How does it work?

```text
HTTP Host
 ├─ Orders Module  -> owns Orders data/model
 ├─ Billing Module -> owns Billing data/model
 └─ Catalog Module -> owns Catalog data/model

Cross-module interaction -> explicit contract
```

Module không nên query trực tiếp tables/internal classes của module khác chỉ vì cùng database/process.

## 4. Practical implementation

C# project boundaries có thể enforce references:

```text
Host
Orders.Api -> Orders.Application -> Orders.Domain
Billing.Api -> Billing.Application -> Billing.Domain
```

Cross-module command/event contract nằm ở explicit contracts assembly hoặc interface boundary, không phải shared domain model khổng lồ.

## 5. Real production scenario

E-commerce platform có Catalog, Orders và Payments. Team chưa cần independent deployment. Module ownership cho phép Orders thay đổi workflow mà không kéo Catalog internals vào transaction logic.

## 6. Failure scenario & troubleshooting

**Symptom** → sửa field trong Catalog làm hàng chục Orders handlers compile fail. **Evidence** → modules reference shared entities/repositories trực tiếp. **Hypothesis** → boundary chỉ tồn tại trên folder tree. **Diagnosis** → dependency graph và database access map. **Fix** → explicit contracts/data ownership. **Verification** → architecture tests + module-level integration tests.

## 7. Common mistakes

Mỗi module có folder nhưng dùng chung DbContext/entities; event bus in-process bị dùng để che coupling; generic repository xuyên modules; tạo abstraction layers không có business boundary.

## 8. Alternatives

Simple layered monolith phù hợp domain nhỏ. Microservices phù hợp khi independent deployment/scaling/ownership đủ giá trị để trả distributed-system cost.

## 9. Trade-offs

### Advantages

Deployment đơn giản, local transactions dễ, boundaries có thể chuẩn bị cho future extraction.

### Costs / Risks

Boundary cần discipline/tooling; process/database vẫn là shared failure domain nếu không thiết kế thêm isolation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu module là responsibility boundary.

### Middle
Giữ dependency direction và API contract rõ.

### Senior
Thiết kế data ownership, transaction boundary và cross-module communication.

### Technical Lead / Architect
Quyết định khi module nên ở monolith và khi operational/business pressure thực sự justify service extraction.

## 11. Key takeaway

- Modular Monolith là boundary design, không phải folder convention.
- Data ownership quan trọng như code ownership.
- Đừng trả microservices tax trước khi cần independent service properties.

# 5. Azure Service Bus Sessions: ordering theo business stream thay vì global ordering

## 1. What is it?

Service Bus Sessions nhóm messages có cùng `SessionId` thành một ordered stream được một session receiver xử lý độc quyền tại một thời điểm.

## 2. Why does it exist?

Competing consumers tăng throughput nhưng phá global processing order. Nhiều domain chỉ cần order **per aggregate/customer/workflow**, không cần serialize toàn queue.

## 3. How does it work?

```text
Order-42: Created -> Paid -> Shipped   (SessionId=42)
Order-99: Created -> Cancelled         (SessionId=99)

Consumer A locks session 42
Consumer B locks session 99
```

Ordering được giữ trong từng session trong khi sessions khác xử lý song song.

## 4. Practical implementation

```csharp
var options = new ServiceBusSessionProcessorOptions
{
    MaxConcurrentSessions = 16,
    MaxConcurrentCallsPerSession = 1
};

var processor = client.CreateSessionProcessor(queueName, options);
```

Producer phải chọn stable business key làm `SessionId`.

## 5. Real production scenario

Order workflow cần `PaymentCaptured` không chạy trước `OrderCreated` cho cùng order, nhưng hàng nghìn orders có thể xử lý parallel. Session per OrderId đáp ứng đúng requirement.

## 6. Failure scenario & troubleshooting

**Symptom** → một subset messages backlog trong khi consumers vẫn hoạt động. **Evidence** → một hot session có rất nhiều messages hoặc handler giữ session lock lâu. **Hypothesis** → partition key/session design tạo serialization hotspot. **Diagnosis** → queue/session metrics và processing duration. **Fix** → xem lại granularity hoặc handler latency. **Verification** → load test skewed session distribution.

## 7. Common mistakes

Dùng một `SessionId` cho toàn queue; nghĩ sessions tạo exactly-once; không xử lý duplicate; handler dài hơn lock assumptions; session state phình lớn.

## 8. Alternatives

Không cần ordering thì normal competing consumers đơn giản hơn. Partitioning theo aggregate ở broker khác có semantics tương tự. Nếu workflow cần orchestration phức tạp, durable workflow/state machine có thể phù hợp hơn.

## 9. Trade-offs

### Advantages

Per-key ordering và parallelism giữa keys.

### Costs / Risks

Hot sessions, lock/session lifecycle complexity và throughput bị giới hạn trong mỗi stream.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu queue order khác processing order khi có nhiều consumers.

### Middle
Configure session processor và stable SessionId.

### Senior
Thiết kế idempotency, lock recovery và hotspot analysis.

### Technical Lead / Architect
Xác định ordering requirement thật sự nằm ở business invariant nào, tránh global ordering không cần thiết.

## 11. Key takeaway

- Ordering thường nên scoped theo business stream.
- Sessions không loại bỏ duplicate delivery.
- Session key quyết định concurrency architecture.

# 6. Azure App Service Deployment Slots: low-downtime release và hidden state khi swap

## 1. What is it?

Deployment Slot là một live App Service environment cùng app, cho phép deploy phiên bản mới vào staging rồi swap routing/configuration với production.

## 2. Why does it exist?

Deploy trực tiếp production có startup/warm-up risk và rollback chậm. Slot cho phép validate artifact trong Azure hosting environment trước khi nhận production traffic.

## 3. How does it work?

```text
v1 -> Production slot -> traffic
v2 -> Staging slot    -> warm/validate
          |
          +--- swap ---> Production receives v2
```

Một số settings có thể được đánh dấu slot-sticky; không phải mọi configuration đều swap giống code.

## 4. Practical implementation

Pipeline:

```text
build once -> artifact
-> deploy staging
-> health/smoke test
-> swap
-> monitor
-> swap back if application regression permits
```

Database migrations phải backward-compatible với cả v1 và v2 trong transition window.

## 5. Real production scenario

ASP.NET Core release thêm endpoint mới. Staging slot được warm, health check và smoke test. Swap diễn ra nhanh hơn direct redeploy; old version vẫn có thể dùng cho rollback.

## 6. Failure scenario & troubleshooting

**Symptom** → app chạy đúng staging nhưng fail ngay sau swap. **Evidence** → production-only secret/connection/config khác hoặc migration incompatible. **Hypothesis** → slot settings/state assumptions. **Diagnosis** → compare slot-sticky settings, identity, networking, DB schema. **Fix** → configuration governance + expand/contract migrations. **Verification** → pre-swap production-equivalent checks và post-swap telemetry.

## 7. Common mistakes

Build artifact riêng cho staging/prod; migration destructive trước swap; assume swap rollback luôn sửa DB changes; secrets sai slot; không warm dependencies.

## 8. Alternatives

Blue-Green ở separate apps/clusters cho isolation mạnh hơn. Canary/feature flags giảm blast radius theo traffic/user cohort. Rolling deployment phù hợp orchestrators như Kubernetes.

## 9. Trade-offs

### Advantages

Release nhanh, warm-up trước traffic, rollback application version thuận tiện.

### Costs / Risks

Slot cost/config complexity; database/external side effects không rollback theo code swap.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu artifact và environment configuration là hai thứ khác nhau.

### Middle
Deploy/smoke/swap đúng pipeline.

### Senior
Thiết kế backward-compatible migrations và post-swap validation.

### Technical Lead / Architect
Chọn slots, canary hay Blue-Green dựa trên blast radius, state và rollback requirements.

## 11. Key takeaway

- Slot swap không phải transaction cho toàn hệ thống.
- Database compatibility quyết định rollback thực tế.
- Build once, promote artifact; đừng rebuild theo environment.

# 7. Akamai/CDN stale content: `Cache-Control`, cache key và invalidation reasoning

## 1. What is it?

CDN edge cache giữ response gần user. Stale content thường không phải “CDN lỗi” mà là kết quả của TTL, cache key, revalidation và purge policy không khớp freshness requirement.

## 2. Why does it exist?

Caching giảm origin latency/load. Nhưng cache tạo một bản sao state. Mọi bản sao đều đặt câu hỏi: nó hợp lệ bao lâu và điều gì làm nó invalid?

## 3. How does it work?

```text
Browser -> Akamai edge -> Origin
             |
             +-- HIT: serve cached representation
             +-- MISS/expired: fetch/revalidate origin
```

`Cache-Control`, `Vary`, query-string rules, cookies và Akamai property configuration cùng quyết định cacheability/key.

## 4. Practical implementation

Static hashed asset:

```http
Cache-Control: public, max-age=31536000, immutable
```

HTML/content thay đổi thường xuyên cần TTL ngắn hơn hoặc revalidation/purge strategy. Filename content hashing giúp tránh purge static assets.

## 5. Real production scenario

CMS editor publish banner mới nhưng một số regions vẫn thấy banner cũ. Origin đúng; edge object còn TTL vì publish workflow không trigger purge đúng cache key.

## 6. Failure scenario & troubleshooting

**Symptom** → user A thấy mới, user B thấy cũ. **Evidence** → origin response mới nhưng edge HIT trả object cũ. **Hypothesis** → stale edge variant/cache-key mismatch. **Diagnosis** → inspect response headers, cache key inputs, TTL và purge status. **Fix** → sửa invalidation/key policy. **Verification** → test multiple edges/variants sau publish.

## 7. Common mistakes

Purge toàn site cho mỗi content change; cache personalized response thiếu `Vary`/key isolation; query-string policy không rõ; cache HTML lâu như hashed JS; blame browser khi edge vẫn HIT stale object.

## 8. Alternatives

Browser-only caching không giảm origin network distance. Reverse-proxy cache gần origin hữu ích nhưng không có global edge benefit. No-cache đơn giản nhưng mất performance/capacity advantages.

## 9. Trade-offs

### Advantages

Latency thấp, origin offload, resilience cho cacheable content.

### Costs / Risks

Freshness complexity, purge propagation, privacy risk nếu cache key sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu browser cache và CDN cache là hai layers.

### Middle
Đọc cache headers/HIT-MISS và thiết kế static asset caching.

### Senior
Debug variants, purge, stale behavior và origin shielding.

### Technical Lead / Architect
Định nghĩa freshness SLA và ownership giữa CMS, application và CDN configuration.

## 11. Key takeaway

- Cache key là một phần của correctness.
- Immutable hashed assets và mutable HTML cần policy khác nhau.
- Stale incident phải trace Browser → CDN → Origin.

# 8. SSRF trong backend integrations: outbound HTTP cũng là security boundary

## 1. What is it?

Server-Side Request Forgery xảy ra khi attacker ảnh hưởng destination của request do server gửi, khiến server truy cập tài nguyên mà attacker trực tiếp không truy cập được.

## 2. Why does it exist?

Backend thường có network privilege lớn hơn browser: private endpoints, metadata services, internal APIs. Feature “fetch URL”, webhook tester hoặc image importer có thể vô tình biến backend thành network proxy.

## 3. How does it work?

```text
Attacker input URL
      -> Backend HTTP client
      -> internal/private destination
      -> response/data side effect
```

Validation chỉ kiểm tra string hostname có thể không đủ do redirects, DNS behavior và alternate IP representations.

## 4. Practical implementation

Ưu tiên allowlist destinations cho integration cố định. Không nhận arbitrary scheme/host nếu business requirement không cần. Disable hoặc validate redirects, enforce HTTP/HTTPS, network egress policy và timeout/response-size limits.

```csharp
if (!AllowedHosts.Contains(uri.Host))
    return Results.BadRequest();
```

Application validation nên kết hợp network-level egress controls; snippet trên một mình chưa đủ cho hostile arbitrary-URL fetcher.

## 5. Real production scenario

Marketing tool cho nhập URL để tạo preview. Attacker nhập internal admin endpoint. Production server có private network access nên fetch thành công dù endpoint không public.

## 6. Failure scenario & troubleshooting

**Symptom** → outbound logs có requests tới private ranges/unknown hosts. **Evidence** → user-controlled URL preceding request. **Hypothesis** → SSRF path. **Diagnosis** → trace input, redirects, DNS resolution và egress logs. **Fix** → allowlist + redirect/network restrictions. **Verification** → security tests với localhost/private/link-local/redirect chains.

## 7. Common mistakes

Block string `127.0.0.1` rồi coi xong; validate initial URL nhưng follow redirect tùy ý; log secrets trong fetched URLs; không giới hạn response size; để server access internal network rộng không cần thiết.

## 8. Alternatives

Dedicated isolated fetch service với restricted egress giảm blast radius. Predefined integration endpoints loại arbitrary URL capability hoàn toàn.

## 9. Trade-offs

### Advantages

Strict egress/allowlist giảm attack surface đáng kể.

### Costs / Risks

Dynamic integrations khó hơn; DNS/network policy cần operational ownership.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu outbound request có thể nguy hiểm như inbound input.

### Middle
Validate URI/scheme/host và configure safe HTTP client behavior.

### Senior
Threat-model DNS, redirects, private ranges, cloud metadata và egress.

### Technical Lead / Architect
Quyết định có cần arbitrary fetch hay không và đặt isolation boundary phù hợp.

## 11. Key takeaway

- User-controlled URL là security-sensitive input.
- App validation và network egress controls nên bổ trợ nhau.
- Tính năng không cần arbitrary destinations thì đừng hỗ trợ chúng.

# 9. Production SLO với p95/p99: biến telemetry thành reliability decision

## 1. What is it?

SLI là measurement, ví dụ tỷ lệ successful requests hoặc latency distribution. SLO là target reliability cho SLI trong một window. p95/p99 mô tả tail latency: 95%/99% observations nằm dưới threshold đó.

## 2. Why does it exist?

Average latency có thể che tail rất xấu. 99 requests 100 ms và một request 10 giây vẫn có average trông “không quá tệ”, nhưng user ở tail gặp experience khác hẳn.

## 3. How does it work?

Ví dụ SLO:

```text
99.9% checkout requests successful over 30 days
95% checkout requests < 500 ms over 30 days
```

Error budget = phần unreliability được phép. Burn rate cho biết budget đang bị tiêu nhanh đến đâu.

## 4. Practical implementation

Instrument request duration/status bằng OpenTelemetry/Application Insights. Dùng route template thay raw URL để tránh cardinality. Dashboard phải phân tách dependency latency, server latency và error classes.

## 5. Real production scenario

Average checkout latency 220 ms vẫn ổn nhưng p99 tăng từ 800 ms lên 6 giây sau deploy. Trace sampling ở tail chỉ ra 1% requests gặp SQL lock waits; average metric gần như che mất regression.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard “green” nhưng users complain. **Evidence** → average ổn, p99/error segment xấu. **Hypothesis** → tail/segment-specific failure. **Diagnosis** → slice theo route, dependency, region, version; drill vào traces. **Fix** → root cause. **Verification** → SLI distribution và error-budget burn trở lại baseline.

## 7. Common mistakes

Một SLO cho mọi endpoints; dùng client-controlled high-cardinality labels; alert mỗi p99 spike một phút; đặt 100% SLO; metric không phản ánh user journey.

## 8. Alternatives

Apdex có thể hữu ích cho experience summary nhưng ít trực tiếp hơn explicit SLIs. Synthetic monitoring bổ sung end-to-end signal; không thay server telemetry.

## 9. Trade-offs

### Advantages

Reliability trở thành measurable engineering objective thay vì cảm giác.

### Costs / Risks

SLO sai tạo incentive sai; telemetry/storage/alert design có operational cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu average, percentile và error rate khác nhau.

### Middle
Build dashboards và correlate logs/metrics/traces.

### Senior
Thiết kế meaningful SLIs và investigate tail latency.

### Technical Lead / Architect
Dùng SLO/error budget để cân release velocity, reliability work và architectural investment.

## 11. Key takeaway

- Average không đại diện tail experience.
- SLO phải gắn với user-visible behavior.
- Telemetry chỉ có giá trị khi dẫn tới decision và diagnosis.

# 10. LLM Structured Outputs: schema compliance không đồng nghĩa business correctness

## 1. What is it?

Structured Outputs ép model trả dữ liệu theo schema đã định nghĩa, ví dụ object có fields/types/enums cụ thể. Mental model: nó làm **shape deterministic hơn**, không biến nội dung model thành deterministic business truth.

## 2. Why does it exist?

Parse free-form text bằng regex hoặc “hãy trả JSON” rất dễ hỏng. Application cần contract machine-readable để nối model vào workflow/tooling.

## 3. How does it work?

```text
Application -> prompt + schema -> LLM
LLM -> schema-conforming object
Application -> deterministic validation/business rules
```

Schema có thể đảm bảo `amount` là number và `currency` thuộc enum, nhưng không đảm bảo amount được suy luận đúng từ invoice.

## 4. Practical implementation

Sau model response vẫn cần deterministic validation:

```csharp
if (result.Amount <= 0)
    return ValidationFailure("amount_invalid");

if (!authorizedAccounts.Contains(result.AccountId))
    return AuthorizationFailure();
```

Authorization, payment correctness và irreversible actions không nên dựa trực tiếp vào unconstrained model judgment.

## 5. Real production scenario

AI đọc support ticket và trả `{ category, priority, suggestedAction }`. Schema giúp workflow parse ổn định. Nhưng `suggestedAction=Refund` chỉ là đề xuất; deterministic policy kiểm tra order, amount, user authorization trước khi tool refund được gọi.

## 6. Failure scenario & troubleshooting

**Symptom** → JSON luôn parse được nhưng workflow vẫn thực hiện action sai. **Evidence** → object đúng schema nhưng field value semantically incorrect. **Hypothesis** → team nhầm syntactic validity với factual/business validity. **Diagnosis** → replay eval dataset và inspect decision boundary. **Fix** → deterministic validators, retrieval grounding, confidence/escalation policy. **Verification** → evals cho both schema validity và business outcome accuracy.

## 7. Common mistakes

Tin enum output là authorization; không version schema; prompt chứa secrets không cần thiết; retry vô hạn khi model/service lỗi; không log model/version/schema/eval signals; generated tests chỉ kiểm tra parse success.

## 8. Alternatives

Function/Tool Calling phù hợp khi model chọn operation; application vẫn phải validate arguments. Plain text phù hợp human-facing generation không cần machine contract. Deterministic parser/rules tốt hơn LLM khi problem vốn deterministic.

## 9. Trade-offs

### Advantages

Integration ổn định hơn, giảm parsing failures, dễ validate/version.

### Costs / Risks

Semantic errors vẫn tồn tại; schema evolution, token/cost, model latency và provider failure phải được vận hành.

## 10. Junior → Middle → Senior → Technical Lead

### Junior
Hiểu schema-valid khác factually-correct.

### Middle
Implement schema + deterministic validation + retries/timeouts.

### Senior
Thiết kế evals, grounding, observability và safe failure paths.

### Technical Lead / Architect
Quyết định phần nào được giao cho probabilistic reasoning và phần nào bắt buộc deterministic/authorized execution.

## 11. Key takeaway

- Structured output giải contract shape, không giải truth.
- Security/business invariants phải deterministic.
- Evals phải đo outcome correctness, không chỉ JSON parse rate.
