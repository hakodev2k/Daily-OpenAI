# 1. .NET `ArrayPool<T>`: giảm allocation mà không biến pooling thành memory leak

## 1. What is it?

Mental model: `ArrayPool<T>` cho phép thuê một array tạm thời rồi trả lại để lần xử lý sau tái sử dụng. Nó không làm allocation “miễn phí”; nó đổi nhiều allocation ngắn hạn lấy một tập buffer sống lâu hơn.

## 2. Why does it exist?

Hot path xử lý serialization, compression, file hoặc network thường tạo buffer liên tục. Allocation rate cao làm GC chạy thường xuyên; buffer lớn còn có thể đi vào LOH. Pooling hữu ích khi profiling chứng minh buffer allocation là bottleneck.

## 3. How does it work?

`Rent(n)` trả array có độ dài **ít nhất** `n`, không đảm bảo đúng `n`. `Return` đưa buffer về pool. Buffer có thể chứa dữ liệu từ lần dùng trước và có thể được cấp lại cho code khác.

`Rent → use bounded slice → optionally clear → Return in finally`.

## 4. Practical implementation

```csharp
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(64 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024), ct);
    await destination.WriteAsync(buffer.AsMemory(0, read), ct);
}
finally
{
    pool.Return(buffer, clearArray: true);
}
```

`clearArray: true` có cost nhưng phù hợp nếu buffer từng chứa dữ liệu nhạy cảm.

## 5. Real production scenario

API import file xử lý hàng nghìn chunks mỗi phút. Profiling cho thấy allocation rate và Gen 2 GC tăng mạnh. Reuse buffer ở pipeline streaming giảm allocation mà không cần cache toàn bộ file.

## 6. Failure scenario & troubleshooting

**Symptom** → memory giữ cao hoặc dữ liệu “lạ” xuất hiện trong output.  
**Evidence** → allocation profile giảm nhưng retained memory tăng; code dùng toàn bộ `buffer.Length`.  
**Hypothesis** → buffer không được trả hoặc đọc vùng chưa ghi.  
**Diagnosis** → audit mọi `Rent`, `Return`, slice length.  
**Fix** → `finally`, chỉ xử lý logical length, clear khi cần.  
**Verification** → load test và so sánh allocation/GC/working set.

## 7. Common mistakes

Giữ rented array trong object sống lâu; quên `Return`; giả định kích thước chính xác; return buffer trong khi async operation vẫn dùng; pool mọi thứ trước khi đo.

## 8. Alternatives

Array thường đơn giản nhất. `MemoryPool<T>` phù hợp ownership model khác. `stackalloc` hữu ích cho buffer nhỏ, bounded và synchronous scope.

## 9. Trade-offs

### Advantages

Giảm allocation rate, GC pressure và chi phí cấp phát buffer lặp lại.

### Costs / Risks

Ownership phức tạp hơn, dữ liệu cũ có thể tồn tại, retained memory tăng và bug use-after-return rất khó debug.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Rent` là mượn, không phải tạo array mới thuộc sở hữu vĩnh viễn.

### Middle

Dùng `try/finally`, logical length và cancellation đúng.

### Senior

Chỉ pooling sau profiling; đánh giá LOH, security clearing và lifetime.

### Technical Lead / Architect

Quyết định hot path nào xứng đáng nhận complexity; không biến pooling thành coding convention toàn hệ thống.

## 11. Key takeaway

- Pooling tối ưu **allocation rate**, không tự động tối ưu mọi latency.
- Ownership và logical length phải rõ.
- Đo trước và sau khi áp dụng.

# 2. ASP.NET Core rate limiting: bảo vệ capacity thay vì chỉ “chặn spam”

## 1. What is it?

Rate limiting là admission control: giới hạn lượng work một caller có thể đưa vào hệ thống trong một khoảng thời gian hoặc theo capacity.

## 2. Why does it exist?

Một request hợp lệ vẫn tiêu thụ thread scheduling, connection pool, database I/O và downstream quota. Nếu nhận work nhanh hơn khả năng xử lý, latency tăng rồi toàn hệ thống có thể collapse.

## 3. How does it work?

ASP.NET Core có fixed window, sliding window, token bucket và concurrency limiter. Partition key có thể là user, API key, tenant hoặc endpoint. Rejected request thường trả `429 Too Many Requests`.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(o =>
{
    o.AddFixedWindowLimiter("writes", x =>
    {
        x.PermitLimit = 50;
        x.Window = TimeSpan.FromSeconds(10);
        x.QueueLimit = 0;
    });
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});

app.UseRateLimiter();
app.MapPost("/orders", CreateOrder).RequireRateLimiting("writes");
```

## 5. Real production scenario

Checkout API phụ thuộc payment provider có quota. Limiter theo tenant ngăn một integration lỗi retry liên tục chiếm toàn bộ capacity của các tenant khác.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều 429 dù CPU thấp.  
**Evidence** → rejection tăng chỉ ở một instance hoặc partition.  
**Hypothesis** → limit cấu hình sai hoặc per-instance limiter không phản ánh global quota.  
**Diagnosis** → so sánh traffic distribution, partition key, downstream quota.  
**Fix** → chỉnh policy hoặc đưa global coordination tới gateway/distributed layer khi thật sự cần.  
**Verification** → load test theo tenant và theo số instance.

## 7. Common mistakes

Rate limit theo IP sau proxy mà không xử lý forwarded headers; một limit cho mọi endpoint; queue quá lớn; retry 429 ngay lập tức; coi limiter là DDoS protection hoàn chỉnh.

## 8. Alternatives

API gateway/CDN/WAF có thể limit trước origin. Concurrency limiter phù hợp khi vấn đề là số work đồng thời. Queue phù hợp workload có thể xử lý bất đồng bộ.

## 9. Trade-offs

### Advantages

Bảo vệ capacity và fairness, failure sớm và rẻ.

### Costs / Risks

Có thể reject traffic hợp lệ; distributed quota phức tạp; policy sai gây self-inflicted outage.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt 429 với 401/403 và 503.

### Middle

Implement policy, partition và test rejection.

### Senior

Thiết kế retry/backoff, fairness và capacity dựa trên telemetry.

### Technical Lead / Architect

Chọn enforcement boundary: CDN, gateway, application hay downstream-specific bulkhead.

## 11. Key takeaway

- Rate limiting là capacity protection.
- Partition key quan trọng ngang con số limit.
- Global quota không tự nhiên xuất hiện từ per-instance limiter.

# 3. EF Core split queries: tránh cartesian explosion nhưng phải trả giá bằng round trips và consistency

## 1. What is it?

`AsSplitQuery()` yêu cầu EF Core tải các collection liên quan bằng nhiều SQL query thay vì một JOIN lớn.

## 2. Why does it exist?

Khi include nhiều collection siblings, JOIN có thể nhân số row. Một order có 20 lines và 10 notes có thể tạo 200 rows trước khi EF materialize lại object graph.

## 3. How does it work?

Single query: một SQL statement, nhiều JOIN, duplication lớn. Split query: query root trước rồi query collection liên quan và correlate kết quả trong client.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .AsNoTracking()
    .ToListAsync(ct);
```

Nếu endpoint chỉ cần DTO, projection thường tốt hơn cả hai.

## 5. Real production scenario

Admin order screen chậm sau khi thêm audit notes. SQL duration không quá cao nhưng result set tăng hàng chục lần. Split query giảm payload; sau đó projection tiếp tục giảm columns không cần thiết.

## 6. Failure scenario & troubleshooting

**Symptom** → latency giảm ở local nhưng tăng production.  
**Evidence** → nhiều database round trips trên network latency cao.  
**Hypothesis** → split query chữa row explosion nhưng tạo quá nhiều round trips.  
**Diagnosis** → trace SQL count, rows, bytes và duration.  
**Fix** → projection hoặc reshape query.  
**Verification** → đo p95 với dữ liệu production-like.

## 7. Common mistakes

Dùng `Include` như default; bật split query toàn hệ thống; không xét dữ liệu thay đổi giữa các query; benchmark database local rồi kết luận production.

## 8. Alternatives

Projection DTO; explicit query riêng có chủ đích; single query khi cardinality nhỏ; endpoint tách dữ liệu nếu UI không cần tất cả ngay.

## 9. Trade-offs

### Advantages

Giảm cartesian explosion và duplicated payload.

### Costs / Risks

Nhiều round trips; consistency giữa các statement cần được cân nhắc; query plan/latency tổng thể vẫn có thể xấu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Include` ảnh hưởng SQL thật.

### Middle

Đọc generated SQL và dùng projection/split query có lý do.

### Senior

Đo cardinality, bytes, round trips và consistency.

### Technical Lead / Architect

Đặt API shape theo use case thay vì expose entity graph rồi cố tối ưu sau.

## 11. Key takeaway

- `AsSplitQuery` giải một loại query-shape problem.
- Projection thường là lựa chọn tốt nhất cho read API.
- Tối ưu dựa trên rows, bytes, round trips và latency.

# 4. SQL Server isolation levels: chọn consistency contract thay vì chữa blocking bằng `NOLOCK`

## 1. What is it?

Isolation level định nghĩa transaction được phép quan sát thay đổi đồng thời như thế nào. Đây là consistency contract, không chỉ là performance switch.

## 2. Why does it exist?

Concurrent transactions cần cân bằng correctness và concurrency. Nếu không có rule, read có thể thấy trạng thái trung gian hoặc các lần đọc trong cùng transaction mâu thuẫn với nhau.

## 3. How does it work?

`READ COMMITTED` mặc định ngăn dirty read. `SNAPSHOT`/RCSI dùng row versions để giảm read/write blocking. Isolation mạnh hơn giữ consistency lớn hơn nhưng có thể tăng locking/versioning cost.

## 4. Practical implementation

```sql
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

SELECT Status, Total
FROM Orders
WHERE Id = @OrderId;

-- business work

COMMIT;
```

Không bật database option chỉ vì một query bị block; phải đánh giá workload và temp/version store.

## 5. Real production scenario

Reporting query đọc bảng Orders trong khi checkout update liên tục. Team thêm `NOLOCK`, report nhanh hơn nhưng đôi lúc tổng doanh thu sai. Vấn đề được xử lý bằng read model/RCSI phù hợp contract thay vì dirty reads.

## 6. Failure scenario & troubleshooting

**Symptom** → request timeout và blocked sessions.  
**Evidence** → wait stats/blocked process cho thấy lock waits.  
**Hypothesis** → transaction giữ lock quá lâu hoặc access order xấu.  
**Diagnosis** → inspect transaction duration, execution plan, indexes.  
**Fix** → rút ngắn transaction, tối ưu query; cân nhắc row-versioning isolation.  
**Verification** → đo blocking và kiểm tra correctness.

## 7. Common mistakes

Dùng `NOLOCK` như performance hint; transaction bao quanh external HTTP call; nhầm deadlock với blocking; tăng timeout thay vì tìm lock owner.

## 8. Alternatives

RCSI/SNAPSHOT; read replica/read model; optimistic concurrency ở application; transaction ngắn hơn.

## 9. Trade-offs

### Advantages

Isolation phù hợp bảo vệ business invariant và có thể cải thiện concurrency.

### Costs / Risks

Locking, version-store overhead, update conflicts hoặc semantics phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết transaction không đồng nghĩa mọi concurrent behavior đều an toàn.

### Middle

Nhận diện blocking và giữ transaction scope nhỏ.

### Senior

Đọc waits, locks và chọn isolation theo invariant.

### Technical Lead / Architect

Định nghĩa consistency requirement theo workflow, không theo “setting nhanh nhất”.

## 11. Key takeaway

- Isolation là correctness decision.
- `NOLOCK` có thể trả dữ liệu sai.
- Chữa root cause trước khi đổi isolation.

# 5. Azure Blob Storage SAS: delegated access, expiry và blast radius

## 1. What is it?

Shared Access Signature (SAS) là capability token cho phép client truy cập Azure Blob Storage với quyền, resource và thời hạn giới hạn mà không nhận storage account key.

## 2. Why does it exist?

Nếu file upload/download phải đi xuyên API, application chịu bandwidth và scaling không cần thiết. SAS cho phép data plane đi trực tiếp client ↔ Blob trong khi backend vẫn kiểm soát authorization.

## 3. How does it work?

Backend authenticate user, authorize resource, phát SAS ngắn hạn; client dùng SAS truy cập Blob. User delegation SAS kết hợp Microsoft Entra credentials thường giảm phụ thuộc account key.

## 4. Practical implementation

```csharp
var sas = new BlobSasBuilder
{
    BlobContainerName = container,
    BlobName = blobName,
    Resource = "b",
    ExpiresOn = DateTimeOffset.UtcNow.AddMinutes(10)
};
sas.SetPermissions(BlobSasPermissions.Write | BlobSasPermissions.Create);
```

Production nên ưu tiên identity-based generation khi kiến trúc hỗ trợ.

## 5. Real production scenario

CMS cho editor upload video 500 MB. API cấp upload permission cho đúng blob path trong 10 phút; browser upload trực tiếp tới storage.

## 6. Failure scenario & troubleshooting

**Symptom** → 403 chỉ ở production.  
**Evidence** → Storage logs cho thấy signature/permission/time mismatch.  
**Hypothesis** → clock, permission, resource scope hoặc network policy.  
**Diagnosis** → kiểm tra SAS fields, expiry, container/blob path, firewall/private endpoint.  
**Fix** → scope đúng và TTL hợp lý.  
**Verification** → test upload từ đúng network/client.

## 7. Common mistakes

SAS sống nhiều ngày; quyền `rwld` khi chỉ cần read; log full SAS URL; dùng account key khắp nơi; blob name do client tự chọn dẫn tới overwrite resource khác.

## 8. Alternatives

Backend proxy upload; Managed Identity cho service-to-service; public blob chỉ cho nội dung thật sự public.

## 9. Trade-offs

### Advantages

Offload bandwidth, delegated least privilege, scale tốt cho large files.

### Costs / Risks

Token bị lộ có thể dùng đến khi hết hạn; revoke khó hơn central session; CORS/networking cần cấu hình đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SAS là credential tạm thời.

### Middle

Scope permissions/resource/expiry tối thiểu.

### Senior

Threat-model leakage, overwrite, logging và network boundary.

### Technical Lead / Architect

Chọn direct-to-storage hay proxy dựa trên security, transformation, audit và cost.

## 11. Key takeaway

- SAS phải ngắn hạn và least privilege.
- Không log token.
- Authorization business vẫn thuộc backend.

# 6. CQRS với một database: tách intent trước khi tách hạ tầng

## 1. What is it?

CQRS tách command (thay đổi state) khỏi query (đọc state). CQRS **không bắt buộc** hai database, Event Sourcing hay message bus.

## 2. Why does it exist?

Read và write thường có shape, validation và optimization khác nhau. Một generic service/repository API có thể làm intent mờ và khiến business rule trộn với query composition.

## 3. How does it work?

```text
HTTP POST -> Command -> Handler -> Domain/DbContext -> SQL
HTTP GET  -> Query   -> Handler -> Projection       -> SQL
```

Cả hai vẫn có thể dùng cùng database và cùng deployment.

## 4. Practical implementation

```csharp
public sealed record ApproveTimesheet(Guid Id);

public sealed class ApproveTimesheetHandler(AppDbContext db)
{
    public async Task Handle(ApproveTimesheet cmd, CancellationToken ct)
    {
        var item = await db.Timesheets.SingleAsync(x => x.Id == cmd.Id, ct);
        item.Approve();
        await db.SaveChangesAsync(ct);
    }
}
```

Query handler có thể projection trực tiếp DTO và `AsNoTracking`.

## 5. Real production scenario

Timesheet system có workflow approve phức tạp nhưng dashboard cần nhiều projections. Tách command/query làm code rõ hơn mà chưa cần vận hành read store riêng.

## 6. Failure scenario & troubleshooting

**Symptom** → hàng trăm handler một dòng, khó trace flow.  
**Evidence** → mọi CRUD được bọc command/query dù không có behavior khác biệt.  
**Hypothesis** → pattern trở thành ceremony.  
**Diagnosis** → xem complexity có thực sự được cô lập không.  
**Fix** → gom use case đơn giản hoặc bỏ CQRS ở bounded context đơn giản.  
**Verification** → code path và test trở nên rõ hơn.

## 7. Common mistakes

Đồng nhất CQRS với MediatR; tách database quá sớm; handler gọi handler dây chuyền; generic repository che mất EF capabilities.

## 8. Alternatives

Application service đơn giản; vertical slice không formal CQRS; CRUD service cho domain ít business logic.

## 9. Trade-offs

### Advantages

Intent rõ, read/write tối ưu độc lập, boundary use case tốt.

### Costs / Risks

Nhiều types/files; navigation khó hơn; tách store tạo eventual consistency và operations burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt read và state-changing operation.

### Middle

Implement handler với validation, transaction và test rõ.

### Senior

Nhận ra khi CQRS chỉ tạo ceremony.

### Technical Lead / Architect

Quyết định mức separation theo business complexity; chỉ tách store khi có pressure thật.

## 11. Key takeaway

- CQRS trước hết là separation of intent.
- Một database vẫn là CQRS hợp lệ.
- Không mua eventual consistency nếu chưa cần.

# 7. Docker container shutdown: PID 1, signals và graceful termination của ASP.NET Core

## 1. What is it?

Container shutdown là protocol giữa orchestrator, process và application: gửi termination signal, cho grace period, sau đó force kill nếu process chưa thoát.

## 2. Why does it exist?

Pod/container có thể bị restart vì deployment, scale-in hoặc node maintenance. Nếu process chết ngay, request và message đang xử lý có thể bị cắt giữa chừng.

## 3. How does it work?

Docker/Kubernetes gửi signal tới container process. ASP.NET Core host chuyển thành cancellation/shutdown, ngừng nhận work mới và chờ graceful completion trong giới hạn.

## 4. Practical implementation

```csharp
public sealed class Consumer(ILogger<Consumer> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
            await ProcessNextAsync(stoppingToken);
    }
}
```

Dockerfile nên dùng exec form để application nhận signal trực tiếp:

```dockerfile
ENTRYPOINT ["dotnet", "Api.dll"]
```

## 5. Real production scenario

Kubernetes rolling update thay pod consumer. Pod cũ phải ngừng nhận message mới, hoàn thành/abandon message đang giữ rồi thoát trước termination deadline.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate messages tăng mỗi deployment.  
**Evidence** → logs kết thúc đột ngột; message lock hết hạn.  
**Hypothesis** → process không nhận signal hoặc shutdown dài hơn grace period.  
**Diagnosis** → inspect entrypoint, cancellation propagation và termination events.  
**Fix** → exec form, propagate token, bounded shutdown.  
**Verification** → rolling deployment dưới load.

## 7. Common mistakes

Shell wrapper nuốt signal; bỏ qua `CancellationToken`; bắt đầu work dài ngay khi shutdown; grace period cực dài thay vì thiết kế resumable/idempotent work.

## 8. Alternatives

External queue + short handlers; checkpointed worker; serverless consumer khi execution model phù hợp.

## 9. Trade-offs

### Advantages

Giảm dropped work và deployment disruption.

### Costs / Risks

Grace period làm rollout chậm; không thể đảm bảo hoàn thành mọi work; vẫn cần idempotency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu container restart là bình thường.

### Middle

Propagate cancellation và cleanup resource.

### Senior

Thiết kế in-flight work, message settlement và timeout.

### Technical Lead / Architect

Đặt shutdown contract phù hợp orchestrator và delivery semantics.

## 11. Key takeaway

- Graceful shutdown là protocol, không phải `finally` đơn thuần.
- Cancellation phải đi xuyên call chain.
- Idempotency vẫn cần khi process có thể bị kill.

# 8. Vue 3 reactivity: identity, `ref`, `reactive` và những bug state khó thấy

## 1. What is it?

Vue reactivity theo dõi dependency khi reactive value được đọc và trigger effect/render khi value liên quan thay đổi.

## 2. Why does it exist?

Imperative DOM synchronization nhanh chóng trở nên khó duy trì. Reactive model cho phép developer mô tả UI từ state, framework chịu trách nhiệm cập nhật phần cần thiết.

## 3. How does it work?

`ref` bọc value qua `.value`; `reactive` dùng Proxy cho object. Dependency tracking phụ thuộc việc truy cập qua reactive wrapper/proxy; phá identity hoặc destructure sai có thể làm mất tracking mong đợi.

## 4. Practical implementation

```ts
const state = reactive({ query: "", results: [] as Product[] })
const loading = ref(false)

async function search() {
  loading.value = true
  try {
    state.results = await api.search(state.query)
  } finally {
    loading.value = false
  }
}
```

## 5. Real production scenario

Product search component giữ query, result và loading state. Backend engineer debug thấy API trả đúng nhưng UI không update vì code copy/destructure state ra primitive không reactive.

## 6. Failure scenario & troubleshooting

**Symptom** → network response đúng nhưng component hiển thị state cũ.  
**Evidence** → Vue DevTools thấy source reactive thay đổi khác biến template đang đọc.  
**Hypothesis** → mất reactive connection hoặc stale async response.  
**Diagnosis** → inspect refs/proxy và request ordering.  
**Fix** → giữ reactive source đúng; thêm cancellation/request identity khi cần.  
**Verification** → test rapid input và navigation.

## 7. Common mistakes

Destructure `reactive` tùy tiện; trộn server state và UI state; deep watcher khắp nơi; mutate state từ nhiều nơi không ownership.

## 8. Alternatives

Plain local state cho dữ liệu không cần reactive; composables; dedicated server-state library khi caching/refetch complexity tăng.

## 9. Trade-offs

### Advantages

UI synchronization ngắn gọn và composable.

### Costs / Risks

Implicit dependency tracking có thể khó debug; deep reactive graphs và watchers tạo complexity/performance cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu UI render từ state.

### Middle

Dùng `ref`, `reactive`, computed và lifecycle đúng.

### Senior

Debug async ordering, dependency tracking và performance.

### Technical Lead / Architect

Đặt state ownership boundary; không đưa mọi server data vào global store.

## 11. Key takeaway

- Reactivity phụ thuộc cách value được truy cập.
- State ownership rõ quan trọng hơn chọn `ref` hay `reactive`.
- Debug UI phải kiểm tra cả network lẫn reactive dependency.

# 9. Git bisect: biến regression investigation thành binary search có bằng chứng

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên làm behavior chuyển từ good sang bad.

## 2. Why does it exist?

Khi regression nằm trong hàng trăm commits, đọc diff tuần tự hoặc đoán theo tác giả rất chậm và dễ bias. Nếu có test tái hiện deterministic, history trở thành search space.

## 3. How does it work?

Đánh dấu một commit bad và một commit good. Git checkout commit giữa; ta test rồi đánh dấu good/bad. Lặp lại đến culprit.

## 4. Practical implementation

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
git bisect run dotnet test tests/Regression.Tests
git bisect reset
```

Script phải trả exit code ổn định.

## 5. Real production scenario

API p95 tăng sau hai tuần releases. Team tạo benchmark/regression test phản ánh query count vượt threshold rồi bisect để tìm commit thêm accidental N+1.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit không liên quan.  
**Evidence** → cùng commit lúc pass lúc fail.  
**Hypothesis** → test flaky hoặc phụ thuộc external environment.  
**Diagnosis** → chạy lặp lại culprit và neighboring commits.  
**Fix** → deterministic fixture, pin dependency/data.  
**Verification** → revert/fix culprit làm test pass ổn định.

## 7. Common mistakes

Bisect bằng manual intuition; dùng test flaky; history không build được mà đánh dấu bad; quên `git bisect reset`.

## 8. Alternatives

PR/change review; deployment correlation; feature flags; profiler. Bisect mạnh nhất khi regression có reproducible predicate.

## 9. Trade-offs

### Advantages

Giảm search space logarithmically, evidence-driven và có thể automation.

### Costs / Risks

Cần buildable history và deterministic test; migration/external dependencies có thể làm old commits khó chạy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết good/bad là behavior, không phải “commit đẹp/xấu”.

### Middle

Tạo reproduction và chạy bisect.

### Senior

Biến production symptom thành deterministic predicate.

### Technical Lead / Architect

Đầu tư testability/build reproducibility để incident investigation nhanh hơn.

## 11. Key takeaway

- Reproduction tốt biến debugging history thành binary search.
- Flaky predicate làm kết quả vô nghĩa.
- Culprit commit là bằng chứng khởi đầu cho root-cause analysis.

# 10. .NET Framework → modern .NET: incremental modernization thay vì big-bang rewrite

## 1. What is it?

Modernization là chuyển runtime, hosting, libraries và architecture của hệ thống legacy sang modern .NET trong các bước có thể kiểm chứng, không đồng nghĩa viết lại toàn bộ.

## 2. Why does it exist?

Legacy .NET Framework có dependency, IIS assumptions, old configuration và packages không tương thích. Big-bang rewrite thường kéo dài đến mức business tiếp tục thay đổi trong khi replacement chưa tạo giá trị.

## 3. How does it work?

Một lộ trình thực dụng:

```text
Inventory dependencies
  -> characterize behavior with tests
  -> isolate Framework-only boundaries
  -> move shared code toward compatible targets
  -> extract/migrate vertical slices
  -> run old + new side by side
  -> shift traffic
  -> retire legacy
```

Boundary thường quan trọng hơn việc đổi syntax.

## 4. Practical implementation

Một bước nhỏ có thể là chuyển business library thuần logic khỏi `System.Web`, inject clock/filesystem/external clients, rồi test library độc lập trước khi host mới xuất hiện.

```csharp
public interface IClock
{
    DateTimeOffset UtcNow { get; }
}

public sealed class SystemClock : IClock
{
    public DateTimeOffset UtcNow => DateTimeOffset.UtcNow;
}
```

## 5. Real production scenario

ASP.NET MVC 5 commerce application phụ thuộc IIS, old authentication và vendor SDK. Team migrate product-read API trước sang ASP.NET Core, giữ checkout legacy cho tới khi auth/payment boundaries được kiểm chứng.

## 6. Failure scenario & troubleshooting

**Symptom** → project compile trên modern .NET nhưng production behavior khác.  
**Evidence** → cookie/auth/configuration/serialization semantics lệch.  
**Hypothesis** → migration được coi là compile exercise.  
**Diagnosis** → contract tests, traffic comparison, logs và response diff.  
**Fix** → compatibility adapter hoặc explicit contract migration.  
**Verification** → shadow/canary traffic và rollback path.

## 7. Common mistakes

Rewrite toàn bộ vì code “xấu”; upgrade framework cùng lúc redesign domain; không inventory vendor dependencies; migration database không backward compatible; không có rollback.

## 8. Alternatives

Giữ .NET Framework và giảm risk; in-place dependency upgrades; strangler migration; full rewrite chỉ khi economics và business boundary thật sự biện minh.

## 9. Trade-offs

### Advantages

Modern runtime/support, deployment options, performance và ecosystem tốt hơn.

### Costs / Risks

Dual-running systems, compatibility work, temporary duplication và migration kéo dài.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt runtime migration với feature rewrite.

### Middle

Port library, tests, configuration và API compatibility.

### Senior

Tìm hidden dependencies, behavioral differences và deployment risks.

### Technical Lead / Architect

Chọn migration seam, sequence, coexistence period và stop criteria; có thể kết luận chưa nên migrate một phần nếu risk/cost cao hơn value.

## 11. Key takeaway

- Modernization thành công nhờ boundaries và verification.
- Compile được không có nghĩa behavior tương thích.
- Incremental migration giữ rollback và business delivery khả thi.
