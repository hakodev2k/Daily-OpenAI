# 1. C# `IAsyncDisposable`: async cleanup, resource ownership và vì sao `DisposeAsync` không phải “Dispose nhưng thêm await”

## 1. What is it?

`IAsyncDisposable` là contract cho resource cleanup cần asynchronous I/O. Mental model quan trọng là:

```text
Acquire resource
    ↓
Use resource
    ↓
Release resource
    ↓
Release itself may need async I/O
```

Ví dụ: flush network buffer, close protocol session, commit/abort stream asynchronously, dispose async database/network wrapper.

`DisposeAsync()` không tồn tại để thay toàn bộ `IDisposable`. Nó chỉ phù hợp khi quá trình cleanup thực sự có asynchronous work.

## 2. Why does it exist?

`IDisposable.Dispose()` là synchronous. Nếu cleanup cần gọi I/O mà developer buộc phải block bằng `.GetAwaiter().GetResult()` hoặc `.Wait()`, code có thể:

* block ThreadPool thread;
* tăng shutdown latency;
* tạo sync-over-async;
* deadlock trong môi trường có `SynchronizationContext` đặc biệt;
* làm request latency tăng ở boundary cleanup.

Trong server workload lớn, cleanup cũng là một phần của resource lifecycle; nó không miễn phí chỉ vì business method đã return.

## 3. How does it work?

C# hỗ trợ `await using`:

```csharp
await using var resource = await CreateResourceAsync();
```

Compiler bảo đảm `DisposeAsync()` được gọi khi scope kết thúc, kể cả khi exception xảy ra.

Mental flow:

```text
Create
  ↓
try
  ↓
work
  ↓
finally
  ↓
await DisposeAsync()
```

Nếu một type hỗ trợ cả sync và async cleanup, cần xác định ownership rõ: caller synchronous dùng `Dispose`, caller async dùng `DisposeAsync`.

## 4. Practical implementation

Ví dụ custom async resource:

```csharp
public sealed class BatchWriter : IAsyncDisposable
{
    private readonly Stream _stream;
    private bool _disposed;

    public BatchWriter(Stream stream)
    {
        _stream = stream;
    }

    public async Task WriteAsync(
        ReadOnlyMemory<byte> payload,
        CancellationToken cancellationToken)
    {
        ObjectDisposedException.ThrowIf(_disposed, this);
        await _stream.WriteAsync(payload, cancellationToken);
    }

    public async ValueTask DisposeAsync()
    {
        if (_disposed)
            return;

        _disposed = true;
        await _stream.FlushAsync();
        await _stream.DisposeAsync();
    }
}
```

Caller:

```csharp
await using var writer = new BatchWriter(stream);
await writer.WriteAsync(payload, cancellationToken);
```

## 5. Real production scenario

Một file-processing worker ghi dữ liệu lớn vào remote object stream. Version đầu dispose đồng bộ sau mỗi file. Under load, worker threads bị block trong network flush, throughput giảm và shutdown mất nhiều thời gian.

Chuyển cleanup path sang async giúp worker không giữ thread trong lúc network stack flush dữ liệu.

## 6. Failure scenario & troubleshooting

**Symptom** → shutdown chậm, worker threads tăng nhưng CPU thấp.

**Evidence** → stack traces có synchronous blocking trong cleanup path.

**Hypothesis** → async-capable resource đang bị dispose synchronously.

**Diagnosis** → kiểm tra `Dispose`, `.Wait()`, `.Result`, `GetAwaiter().GetResult()` trong cleanup code.

**Fix** → propagate async lifecycle tới caller và dùng `await using`.

**Verification** → graceful-shutdown test với active workload; đo shutdown duration và blocked thread count.

## 7. Common mistakes

* Implement `IAsyncDisposable` dù cleanup chỉ thay field và free managed memory.
* Gọi cả `Dispose()` và `DisposeAsync()` cho cùng instance mà không có idempotent guard.
* Quên dispose nested async resource.
* Giữ resource sau khi scope đã dispose.
* Dùng async dispose để che ownership không rõ ràng.

## 8. Alternatives

Nếu cleanup thuần synchronous, `IDisposable` đơn giản hơn. Nếu resource được DI container quản lý, lifetime nên giao cho container thay vì dispose thủ công. Nếu resource là pooled object, return-to-pool semantics có thể phù hợp hơn dispose.

## 9. Trade-offs

### Advantages

* Không block thread khi cleanup cần I/O.
* Phù hợp graceful shutdown và streaming workloads.
* Lifecycle rõ hơn cho async resources.

### Costs / Risks

* Async lifecycle lan lên caller.
* Testing cleanup path phức tạp hơn.
* Dễ overuse và tạo API complexity không cần thiết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dispose là ownership/lifecycle, không chỉ “dọn memory”.

### Middle

Dùng `await using`, implement idempotent `DisposeAsync` và tránh sync-over-async.

### Senior

Đánh giá cleanup latency, nested ownership và graceful shutdown behavior.

### Technical Lead / Architect

Quyết định resource ownership boundary nào thuộc application, DI container, pool hoặc infrastructure client; tránh lan async-disposal complexity vô cớ.

## 11. Key takeaway

* `IAsyncDisposable` dành cho cleanup có async I/O thật sự.
* Cleanup path cũng có thể gây ThreadPool pressure và latency.
* Ownership rõ quan trọng hơn việc type hỗ trợ bao nhiêu dispose APIs.

# 2. ASP.NET Core Response Compression: CPU, payload size, reverse proxy và cache correctness

## 1. What is it?

Response compression giảm kích thước HTTP response bằng gzip/Brotli trước khi truyền qua network.

Mental model:

```text
Application payload
      ↓ serialize
large response bytes
      ↓ compress
smaller response bytes
      ↓ network
client decompresses
```

Compression tối ưu network cost nhưng đổi lại CPU cost và ảnh hưởng cache variants thông qua `Accept-Encoding` / `Content-Encoding`.

## 2. Why does it exist?

JSON, HTML, CSS và JavaScript thường compress tốt. Nếu API trả 500 KB JSON cho hàng nghìn requests mỗi giây, bandwidth và transfer latency có thể trở thành bottleneck.

Nhưng “compress mọi response” cũng sai: file ảnh/video đã compressed, payload nhỏ không đủ lợi ích, CPU-bound service có thể tệ hơn nếu thêm compression.

## 3. How does it work?

Client gửi:

```http
Accept-Encoding: br, gzip
```

Server/proxy chọn encoding phù hợp và trả:

```http
Content-Encoding: br
Vary: Accept-Encoding
```

`Vary` rất quan trọng với shared caches. Nếu cache bỏ qua representation variant, client không support Brotli có thể nhận body Brotli đã cache.

## 4. Practical implementation

```csharp
builder.Services.AddResponseCompression(options =>
{
    options.EnableForHttps = true;
});

var app = builder.Build();
app.UseResponseCompression();
```

Trong production cần xác định compression thực hiện ở đâu: Kestrel, reverse proxy, CDN hay edge. Tránh compress cùng payload nhiều lần qua nhiều hop.

Kiểm tra response bằng:

```bash
curl -H "Accept-Encoding: br,gzip" -I https://example.com/api/catalog
```

## 5. Real production scenario

Một e-commerce API trả product-search response 350 KB. Sau khi bật Brotli ở edge, transfer size giảm đáng kể và p95 latency ở mobile network tốt hơn.

Nhưng application CPU không tăng vì compression nằm ở CDN/reverse proxy thay vì app process.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU application tăng mạnh sau khi enable compression.

**Evidence** → profiler cho thấy compression stream chiếm CPU; network bandwidth giảm nhưng request throughput lại giảm.

**Hypothesis** → compression level/work placement không phù hợp.

**Diagnosis** → đo payload sizes, content types, CPU profile và edge capabilities.

**Fix** → offload compression ra reverse proxy/CDN hoặc chỉ compress content type/size phù hợp.

**Verification** → so sánh p95/p99, CPU, egress bytes và throughput trước/sau.

## 7. Common mistakes

* Compress JPEG/PNG/video lại.
* Không có `Vary: Accept-Encoding` ở cache boundary.
* Bật compression level cao nhất mà không benchmark CPU.
* Compress tiny responses vài trăm bytes.
* Không biết CDN đã compression nên app vẫn làm lại.

## 8. Alternatives

Giảm payload bằng projection/pagination thường tốt hơn compression nếu response vốn quá lớn. HTTP caching/CDN giúp tránh gửi lại payload. Streaming phù hợp khi dữ liệu lớn cần tiêu thụ dần nhưng không thay compression.

## 9. Trade-offs

### Advantages

* Giảm network transfer.
* Tốt cho text-based payload.
* Có thể cải thiện mobile/web latency.

### Costs / Risks

* Tăng CPU.
* Cache representation phức tạp hơn.
* Có thể vô ích với already-compressed media.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu compression đổi CPU lấy bandwidth.

### Middle

Cấu hình ASP.NET Core, kiểm tra headers và content types.

### Senior

Benchmark CPU/network, hiểu cache variants và proxy/CDN behavior.

### Technical Lead / Architect

Quyết định compression boundary nào phù hợp: application, ingress, reverse proxy hay CDN, dựa trên topology và cost.

## 11. Key takeaway

* Compression không miễn phí: bandwidth giảm nhưng CPU tăng.
* `Vary: Accept-Encoding` là cache correctness concern.
* Nếu edge đã làm tốt, application thường không cần tự compress mọi thứ.

# 3. MongoDB embedding vs referencing: thiết kế document theo access pattern thay vì mô phỏng relational schema

## 1. What is it?

Trong MongoDB, hai cách modeling chính là:

* **embedding**: đặt related data trong cùng document;
* **referencing**: lưu ID/reference sang document khác.

Mental model:

```text
Embedding:
Order
 ├─ customer snapshot
 └─ items[]

Referencing:
Order → CustomerId
Order → ProductIds
```

Quyết định này liên quan trực tiếp tới access pattern, update frequency, document growth và consistency.

## 2. Why does it exist?

Relational design ưu tiên normalization và joins. Document database tối ưu cho aggregate data được đọc cùng nhau.

Nếu copy relational schema 1:1 sang MongoDB rồi tạo collection cho mọi bảng, application có thể phải thực hiện nhiều round trips và manual joins, bỏ mất lợi thế document locality.

Ngược lại, embed tất cả cũng nguy hiểm vì document có thể phình lớn và duplicate mutable data quá nhiều.

## 3. How does it work?

Embedding phù hợp khi:

* dữ liệu thường đọc cùng nhau;
* child thuộc lifecycle của parent;
* cardinality bounded;
* update riêng lẻ không quá thường xuyên.

Referencing phù hợp khi:

* entity được share rộng;
* child cardinality lớn/unbounded;
* dữ liệu thay đổi độc lập;
* cần query entity riêng thường xuyên.

## 4. Practical implementation

Order document:

```json
{
  "_id": "order-123",
  "customerId": "customer-42",
  "customerNameSnapshot": "Alice Nguyen",
  "items": [
    {
      "productId": "p-1",
      "nameSnapshot": "Keyboard",
      "quantity": 2,
      "unitPrice": 49.9
    }
  ]
}
```

Ở đây `customerId` là reference nhưng `customerNameSnapshot` và product information được embed như historical snapshot để order không thay đổi khi master data đổi.

## 5. Real production scenario

E-commerce system cần hiển thị order history đúng tại thời điểm mua. Nếu order chỉ reference Product collection, khi product đổi tên/giá, historical order có thể hiển thị dữ liệu hiện tại thay vì dữ liệu lúc checkout.

Embedding snapshot giải quyết đúng business semantics hơn normalization thuần túy.

## 6. Failure scenario & troubleshooting

**Symptom** → một customer document tăng tới hàng chục MB và update ngày càng chậm.

**Evidence** → team embed toàn bộ order history vào `Customer.orders[]`.

**Hypothesis** → unbounded child collection bị embed sai boundary.

**Diagnosis** → đo document size, update frequency, query patterns và growth rate.

**Fix** → tách orders thành collection riêng, giữ summary/bounded recent items nếu thực sự cần.

**Verification** → load test write/read, kiểm tra document growth và query count.

## 7. Common mistakes

* Mô phỏng foreign key schema của SQL 1:1.
* Embed unbounded arrays.
* Duplicate mutable master data mà không có consistency strategy.
* Reference mọi thứ rồi tạo N+1 queries ở application.
* Chọn model trước khi biết access pattern.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp khi relational joins, constraints và multi-row transactions là core requirement. Cosmos DB cũng dùng denormalized modeling nhưng partition key và RU model tạo constraints khác MongoDB.

## 9. Trade-offs

### Advantages

Embedding giảm round trips và tăng locality. Referencing giảm duplication và document growth.

### Costs / Risks

Embedding tăng duplication/update complexity. Referencing tăng query/lookup complexity và có thể tăng latency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu document không phải table được đổi tên.

### Middle

Model theo read/write access pattern và lifecycle.

### Senior

Đánh giá cardinality, growth, update amplification và consistency.

### Technical Lead / Architect

Quyết định aggregate/data boundary dựa trên workload, scale, ownership và operational constraints; chọn SQL nếu relational semantics phù hợp hơn.

## 11. Key takeaway

* MongoDB modeling bắt đầu từ access pattern.
* Embed khi dữ liệu thuộc cùng lifecycle và cardinality bounded.
* Historical snapshot đôi khi đúng nghiệp vụ hơn strict normalization.

# 4. Elasticsearch near-real-time indexing: refresh, stale search result và consistency với transactional database

## 1. What is it?

Elasticsearch search là near-real-time, không phải transactionally immediate. Một document index thành công chưa nhất thiết xuất hiện ngay trong search result cho tới khi refresh làm segment mới searchable.

Mental model:

```text
Primary DB commit
      ↓
index request
      ↓
in-memory/indexing buffer
      ↓ refresh
searchable segment
      ↓
Search API sees document
```

## 2. Why does it exist?

Nếu mọi write phải đồng bộ fsync + publish searchable structure ngay lập tức, indexing throughput sẽ thấp hơn nhiều. Elasticsearch batch-style refresh để cân bằng write throughput và search freshness.

Điều này tạo eventual-consistency window mà application phải hiểu.

## 3. How does it work?

Một document có thể:

* đã được accepted/indexed;
* có thể GET trực tiếp theo ID trong một số flow;
* nhưng chưa xuất hiện trong `_search` cho tới refresh.

Application thường có primary transactional DB làm source of truth, Elasticsearch làm search projection.

```text
SQL commit
   ↓
CDC / event / sync worker
   ↓
Elasticsearch
   ↓
search becomes eventually consistent
```

## 4. Practical implementation

Không nên gọi refresh thủ công sau mọi write chỉ để test pass. Thay vào đó, integration workflow nên chấp nhận eventual consistency hoặc dùng `refresh=wait_for` có chọn lọc ở operation thực sự cần read-your-write search behavior.

Ví dụ request:

```http
POST /products/_doc/123?refresh=wait_for
Content-Type: application/json

{
  "name": "Mechanical Keyboard",
  "status": "Published"
}
```

Dùng có chủ đích vì latency write sẽ tăng.

## 5. Real production scenario

CMS editor publish article rồi ngay lập tức search trong backoffice nhưng không thấy article trong 1–2 giây. Database đã commit; search index sync thành công nhưng refresh chưa làm document searchable.

Nếu UI hiểu search là eventually consistent, có thể hiển thị “Publishing to search…” hoặc đọc chi tiết từ primary store sau publish.

## 6. Failure scenario & troubleshooting

**Symptom** → document có trong SQL nhưng search không thấy trong nhiều phút.

**Evidence** → synchronization worker có backlog hoặc indexing failures.

**Hypothesis** → đây không còn là refresh delay bình thường mà là projection lag.

**Diagnosis** → kiểm tra queue lag, failed indexing requests, index mapping errors, refresh health.

**Fix** → xử lý failed messages, replay projection hoặc repair/reindex.

**Verification** → so sánh source-of-truth count/version với search projection và theo dõi lag metric.

## 7. Common mistakes

* Dùng Elasticsearch làm transactional source of truth.
* Force refresh sau mọi write.
* Không có retry/replay cho failed indexing.
* Không đo indexing lag.
* Test giả định write xong search thấy ngay.

## 8. Alternatives

SQL full-text search có thể đủ cho simple requirements và strong consistency gần hơn. Azure AI Search hoặc OpenSearch cung cấp search platform khác nhưng vẫn có indexing-consistency concerns tương tự.

## 9. Trade-offs

### Advantages

* Full-text search mạnh và scalable.
* Tách search workload khỏi transactional DB.

### Costs / Risks

* Eventual consistency.
* Projection sync cần vận hành.
* Mapping/reindex lifecycle phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu “index request success” không đồng nghĩa search thấy ngay.

### Middle

Implement sync worker và retry/replay logic.

### Senior

Phân biệt refresh delay với synchronization lag/failure.

### Technical Lead / Architect

Quyết định freshness SLA, source-of-truth ownership và repair/reindex strategy; đánh giá search platform có thực sự cần thiết không.

## 11. Key takeaway

* Elasticsearch search là near-real-time.
* Search projection cần lag monitoring và repair path.
* Đừng hy sinh indexing throughput bằng force-refresh mọi write chỉ để giả strong consistency.

# 5. Strangler Fig Pattern cho .NET Framework modernization: migrate từng capability mà không cần big-bang rewrite

## 1. What is it?

Strangler Fig Pattern là modernization strategy trong đó hệ thống mới dần “bao quanh” hệ thống cũ, migrate từng capability cho tới khi legacy phần lớn hoặc hoàn toàn được thay thế.

Mental model:

```text
Client
  ↓
Routing boundary
  ├── legacy .NET Framework
  └── modern .NET service/module
```

Mục tiêu là giảm migration risk bằng incremental replacement thay vì rewrite toàn bộ rồi cut-over một lần.

## 2. Why does it exist?

Big-bang rewrite thường gặp ba vấn đề:

* business vẫn thay đổi trong khi rewrite kéo dài;
* behavior ẩn trong legacy code không được document đầy đủ;
* cut-over cuối dự án có blast radius rất lớn.

Incremental modernization cho phép deliver value sớm và học từ production từng phần.

## 3. How does it work?

Chọn seam/boundary rõ:

```text
/legacy-orders/* → old app
/api/catalog/*   → new .NET 8 app
```

Hoặc dùng module/business capability boundary. Mỗi capability cần:

* ownership rõ;
* data access strategy;
* compatibility contract;
* routing;
* observability;
* rollback.

Data migration thường khó hơn code migration. Không nên để cả legacy và new system cùng ghi một table vô điều kiện nếu ownership không rõ.

## 4. Practical implementation

Reverse proxy bằng YARP có thể route traffic:

```json
{
  "ReverseProxy": {
    "Routes": {
      "catalog": {
        "ClusterId": "modern",
        "Match": { "Path": "/api/catalog/{**catch-all}" }
      },
      "legacy": {
        "ClusterId": "legacy",
        "Match": { "Path": "/{**catch-all}" }
      }
    }
  }
}
```

Routing chỉ là kỹ thuật; boundary và data ownership mới là phần kiến trúc quan trọng.

## 5. Real production scenario

Một enterprise portal chạy .NET Framework + IIS với hàng trăm screens. Team cần .NET 8 nhưng không thể dừng roadmap hai năm để rewrite.

Họ tách notification capability trước: API mới, DB ownership mới, route mới. Sau đó migrate document/search flows. Legacy app vẫn chạy cho phần chưa chuyển.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng business object bị update từ cả legacy và modern service, dữ liệu diverge.

**Evidence** → hai code paths cùng ghi shared tables với validation khác nhau.

**Hypothesis** → strangler chỉ tách HTTP routing nhưng chưa tách ownership.

**Diagnosis** → map writers/readers theo table/domain capability.

**Fix** → xác định single writer, anti-corruption boundary hoặc migration bridge.

**Verification** → contract/data-consistency tests và production reconciliation metrics.

## 7. Common mistakes

* Chuyển controller sang .NET mới nhưng vẫn chia sẻ mọi coupling cũ.
* Rewrite technology layer mà không tách business capability.
* Không có rollback per slice.
* Cho hai systems cùng write dữ liệu mà không governance.
* Dùng microservices như mục tiêu mặc định của modernization.

## 8. Alternatives

In-place upgrade phù hợp codebase nhỏ/compatible. Modular Monolith mới có thể đơn giản hơn nhiều microservices. Big-bang rewrite chỉ hợp khi system nhỏ, requirement ổn định và migration window kiểm soát được.

## 9. Trade-offs

### Advantages

* Giảm migration blast radius.
* Deliver incremental value.
* Cho phép rollback từng capability.

### Costs / Risks

* Tồn tại dual architecture trong thời gian dài.
* Routing/data synchronization phức tạp.
* Operational footprint tăng tạm thời.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu modernization không đồng nghĩa rewrite toàn bộ.

### Middle

Implement routing seam, compatibility adapter và tests.

### Senior

Đánh giá data ownership, rollback và hidden legacy behavior.

### Technical Lead / Architect

Chọn migration slices, target architecture và sequencing sao cho business vẫn ship features trong suốt modernization.

## 11. Key takeaway

* Strangler là migration strategy, không phải proxy trick.
* Data ownership quyết định thành bại nhiều hơn route ownership.
* Modernization tốt giảm risk theo từng slice thay vì dồn risk vào cut-over cuối.

# 6. Retry budget + exponential backoff + jitter: khi retry cứu hệ thống và khi retry tạo retry storm

## 1. What is it?

Retry là cơ chế thử lại transient failure. Nhưng retry an toàn cần ba yếu tố:

* bounded attempts / retry budget;
* exponential backoff;
* jitter.

Mental model:

```text
Failure
  ↓
wait 100ms + jitter
  ↓ retry
wait 200ms + jitter
  ↓ retry
wait 400ms + jitter
  ↓ stop
```

Retry không phải “cứ thất bại thì thử lại”.

## 2. Why does it exist?

Network và distributed services có transient failures: connection reset, leader failover, throttling, short overload.

Immediate retry có thể thành synchronized flood. 10.000 clients cùng retry sau 100 ms có thể biến transient incident thành outage kéo dài.

## 3. How does it work?

Exponential backoff tăng delay qua mỗi attempt. Jitter thêm randomness để clients không đồng bộ.

Retry budget giới hạn tổng attempts/time để request không vượt latency SLA hoặc khuếch đại load vô hạn.

Quan trọng hơn: chỉ retry operation có semantics an toàn. POST charge payment không idempotent thì retry mù có thể charge hai lần.

## 4. Practical implementation

Với resilience pipeline trong .NET:

```csharp
var pipeline = new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddRetry(new RetryStrategyOptions<HttpResponseMessage>
    {
        MaxRetryAttempts = 3,
        Delay = TimeSpan.FromMilliseconds(200),
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,
        ShouldHandle = new PredicateBuilder<HttpResponseMessage>()
            .Handle<HttpRequestException>()
    })
    .Build();
```

Retry policy phải phối hợp timeout/circuit breaker và business idempotency.

## 5. Real production scenario

Inventory service có 2 giây overload. 100 instances của API mỗi instance retry 5 lần ngay lập tức. Dependency nhận tải gấp nhiều lần traffic gốc và không thể phục hồi.

Giảm attempts, thêm jitter, timeout budget và circuit breaker giúp dependency có recovery window.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency request rate tăng mạnh đúng lúc error rate tăng.

**Evidence** → telemetry cho thấy một inbound request tạo nhiều outbound retries.

**Hypothesis** → retry amplification/retry storm.

**Diagnosis** → đo attempts per request, backoff timing, downstream status codes và latency budget.

**Fix** → giảm budget, thêm jitter, honor `Retry-After`, circuit breaker hoặc fail fast.

**Verification** → fault-injection test dependency outage và quan sát downstream QPS không tăng mất kiểm soát.

## 7. Common mistakes

* Retry mọi 4xx.
* Retry non-idempotent operation không có idempotency key.
* Retry ở nhiều layers cùng lúc.
* Không có total timeout.
* Ignore `Retry-After`.
* Log mỗi retry như independent critical incident gây alert noise.

## 8. Alternatives

Queueing phù hợp operation không cần synchronous response. Circuit Breaker dừng calls khi dependency unhealthy. Bulkhead giới hạn concurrent pressure. Cache/fallback chỉ phù hợp khi stale/degraded response chấp nhận được.

## 9. Trade-offs

### Advantages

* Che transient failures.
* Tăng success rate trong failure ngắn.

### Costs / Risks

* Tăng latency.
* Tăng downstream load.
* Có thể duplicate side effects.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry chỉ dành cho transient failures.

### Middle

Implement bounded backoff/jitter và idempotency-aware retry.

### Senior

Phân tích retry amplification, timeout budgets và layered retries.

### Technical Lead / Architect

Đặt resilience policy theo dependency class và SLA; quyết định khi nào queue/fail-fast tốt hơn retry.

## 11. Key takeaway

* Retry có thể cứu request hoặc giết dependency.
* Backoff + jitter + budget phải đi cùng nhau.
* Không retry side effect nếu correctness/idempotency chưa rõ.

# 7. Azure App Service deployment slots: warm-up, swap semantics, sticky settings và zero-downtime deployment

## 1. What is it?

Deployment slot là một live App Service environment riêng như `staging` và `production`, cùng App Service app nhưng có hostname/configuration riêng.

Mental model:

```text
Build artifact
    ↓
Deploy to staging slot
    ↓
warm + validate
    ↓
swap
    ↓
production receives warmed app
```

Slot swap giúp tách deployment khỏi production traffic cut-over.

## 2. Why does it exist?

Deploy trực tiếp vào production có thể gây:

* cold start;
* startup failure;
* config mismatch;
* broken artifact ngay lập tức nhận traffic.

Slot cho phép artifact chạy thật trước khi production traffic chuyển sang.

## 3. How does it work?

Swap trao đổi slot content/config theo App Service semantics. Một số settings có thể marked as deployment-slot settings (“sticky”), nghĩa là chúng không đi theo swap.

Điều quan trọng: database/external dependencies thường không swap. Vì vậy app version mới phải compatible với shared production dependencies tại thời điểm cut-over.

## 4. Practical implementation

Release flow:

```text
CI build once
→ deploy artifact to staging
→ health check
→ smoke test
→ warm key endpoints
→ swap staging → production
→ monitor
→ swap back if necessary
```

Config như staging-only diagnostic flag nên sticky. Connection string production cần thiết kế cẩn thận theo intended slot behavior.

## 5. Real production scenario

ASP.NET Core app mất 40 giây để load configuration, JIT hot paths và initialize caches. Direct deployment tạo 5xx trong warm-up.

Với staging slot, app warm trước. Swap chỉ chuyển production traffic khi health validation đạt yêu cầu.

## 6. Failure scenario & troubleshooting

**Symptom** → swap thành công nhưng production app kết nối staging dependency.

**Evidence** → App Settings/connection strings được đánh dấu sticky sai hoặc config ownership không rõ.

**Hypothesis** → slot-setting semantics bị hiểu sai.

**Diagnosis** → diff slot configuration trước swap, kiểm tra deployment-slot flags.

**Fix** → classify settings: artifact config, environment config, secrets và sticky settings.

**Verification** → automated post-swap probes kiểm tra dependency identities/environment markers.

## 7. Common mistakes

* Nghĩ swap cũng rollback database migration.
* Build lại artifact cho staging và production thay vì promote same artifact.
* Không warm endpoint quan trọng.
* Không test sticky settings.
* Swap xong không monitor p95/error rate.

## 8. Alternatives

Blue-Green trên separate apps/infra cho isolation mạnh hơn. Canary cho gradual exposure. Rolling deployment phù hợp container/Kubernetes. Direct deploy đơn giản hơn với low-risk internal apps.

## 9. Trade-offs

### Advantages

* Warm-up trước production.
* Rollback nhanh bằng swap back.
* Giảm deployment downtime.

### Costs / Risks

* Config semantics phức tạp.
* Database vẫn là shared migration problem.
* Slot resource/cost và operational discipline tăng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slot là live environment, không chỉ folder backup.

### Middle

Deploy, health-check và swap đúng flow.

### Senior

Thiết kế config/sticky settings, backward-compatible DB migrations và rollback.

### Technical Lead / Architect

Chọn slots, Blue-Green, Canary hay rolling dựa trên risk, traffic và infrastructure topology.

## 11. Key takeaway

* Slot swap giảm application cut-over risk nhưng không rollback database.
* Promote cùng artifact đáng tin hơn rebuild mỗi environment.
* Zero-downtime deployment cần compatibility ở cả app, config và schema.

# 8. OAuth 2.0 Authorization Code + PKCE cho SPA: bảo vệ authorization code mà không nhét client secret vào browser

## 1. What is it?

Authorization Code + PKCE là flow trong đó SPA redirect user tới Authorization Server, nhận authorization code, rồi đổi code lấy token bằng `code_verifier` đã tạo trước.

Mental model:

```text
SPA generates verifier
    ↓ hash
code_challenge
    ↓
Authorization request
    ↓
authorization code
    ↓
Token request + original verifier
    ↓
Authorization Server verifies match
```

Browser là public client: không thể giữ client secret an toàn.

## 2. Why does it exist?

Nếu attacker chặn authorization code, họ có thể cố đổi code lấy token. PKCE ràng buộc code với client instance đã khởi tạo flow bằng secret tạm thời `code_verifier` không gửi trong authorization request ban đầu.

Nó giải quyết code interception, không thay thế redirect URI validation, state/nonce hoặc XSS protection.

## 3. How does it work?

Client tạo random verifier:

```text
code_verifier = high-entropy random value
```

Challenge:

```text
BASE64URL(SHA256(code_verifier))
```

Authorization request gửi challenge. Token endpoint chỉ cấp token nếu verifier khớp challenge đã lưu với code.

## 4. Practical implementation

Trong SPA thực tế nên dùng OIDC/OAuth library mature thay vì tự implement cryptography/redirect handling.

Config conceptual:

```ts
const auth = {
  authority: "https://login.example.com",
  client_id: "spa-client",
  redirect_uri: "https://app.example.com/callback",
  response_type: "code",
  scope: "openid profile api.read"
};
```

Library thực hiện PKCE internally. Application tập trung vào secure token handling và authorization trên API.

## 5. Real production scenario

Vue/React SPA gọi ASP.NET Core API qua Microsoft Entra ID. Team cũ muốn thêm client secret vào JavaScript bundle vì “OAuth cần secret”. Đây là sai trust model: bất kỳ browser user nào cũng đọc được secret.

Public SPA dùng Authorization Code + PKCE; confidential backend mới giữ secret/certificate nếu flow cần.

## 6. Failure scenario & troubleshooting

**Symptom** → login thành công ở local nhưng production callback fail `invalid_grant`.

**Evidence** → redirect URI hoặc verifier flow không khớp; multiple tabs/storage handling có thể overwrite transaction state.

**Hypothesis** → authorization transaction state bị mismatch.

**Diagnosis** → kiểm tra redirect URI exact match, PKCE transaction storage, clock và auth library logs.

**Fix** → cấu hình redirect URIs đúng, dùng library-supported transaction storage và không tự sửa verifier.

**Verification** → test multi-tab, refresh callback, expired code và replayed code.

## 7. Common mistakes

* Đặt client secret trong SPA.
* Tự viết OAuth flow bằng vài fetch calls.
* Nghĩ PKCE là authorization.
* Lưu token dài hạn trong browser storage mà không đánh giá XSS risk.
* API tin role/permission từ frontend thay vì validate token/claims server-side.

## 8. Alternatives

BFF pattern giữ tokens ở server-side session/cookie và giảm token exposure trong browser. Traditional server-rendered app có thể dùng confidential-client flow. Lựa chọn phụ thuộc threat model và architecture.

## 9. Trade-offs

### Advantages

* Phù hợp public clients.
* Giảm authorization-code interception risk.
* Không cần fake “secret” trong browser.

### Costs / Risks

* Browser vẫn là hostile environment.
* XSS vẫn có thể đánh cắp session/token.
* Redirect/state handling phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser không giữ được client secret.

### Middle

Cấu hình OIDC library, redirect URI, scopes và API validation.

### Senior

Đánh giá token storage, XSS, BFF alternatives và multi-tab/session behavior.

### Technical Lead / Architect

Chọn SPA direct-token hay BFF dựa trên threat model, user experience và operational complexity.

## 11. Key takeaway

* PKCE bảo vệ authorization code, không thay authorization.
* Client secret trong SPA không còn là secret.
* Dùng mature OIDC/OAuth library thay vì tự implement protocol.

# 9. .NET memory-growth investigation: GC roots, retained objects, `dotnet-counters` và dump analysis

## 1. What is it?

Memory leak trong managed .NET thường không phải memory “quên free” theo kiểu unmanaged. Phổ biến hơn là object vẫn reachable từ GC root nên GC đúng luật không thể collect nó.

Mental model:

```text
GC Root
  ↓
static / singleton / event / cache / running Task
  ↓
object graph
  ↓
large retained memory
```

Investigation phải phân biệt allocation rate cao với retained-memory growth.

## 2. Why does it exist?

GC tự quản lý memory nhưng không biết business object nào “không còn cần”. Nếu một static dictionary giữ reference mãi, object vẫn hợp lệ về mặt runtime.

Vì vậy “dùng managed memory thì không leak” là misconception.

## 3. How does it work?

Bước đầu theo dõi process:

```bash
dotnet-counters monitor -p <PID> System.Runtime
```

Quan sát:

* GC Heap Size;
* allocation rate;
* Gen 2 collections;
* LOH size;
* working set.

Nếu heap tăng bền vững qua nhiều full collections, capture dump:

```bash
dotnet-dump collect -p <PID>
dotnet-dump analyze <dump-file>
```

Sau đó inspect dominant types và GC roots.

## 4. Practical implementation

Một leak kinh điển:

```csharp
public sealed class EventBus
{
    public event EventHandler<OrderChangedEventArgs>? OrderChanged;

    public void Publish(OrderChangedEventArgs args) =>
        OrderChanged?.Invoke(this, args);
}
```

Nếu long-lived singleton `EventBus` giữ event handler của short-lived objects và subscribers không unsubscribe, singleton trở thành root giữ cả object graph.

Fix có thể là explicit unsubscribe, weak subscription khi phù hợp hoặc redesign ownership.

## 5. Real production scenario

ASP.NET Core worker process memory tăng từ 500 MB lên 8 GB sau vài ngày. GC vẫn chạy, CPU bình thường. Team restart process mỗi đêm để “fix”.

Dump cho thấy singleton cache giữ mỗi request's transformed payload mà không eviction. Restart chỉ che root cause.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng liên tục, cuối cùng container OOMKill.

**Evidence** → Gen 2 heap tăng sau full GCs; dump cho thấy millions objects cùng root.

**Hypothesis** → retention leak thay vì temporary allocation burst.

**Diagnosis** → compare two dumps theo thời gian, dominant types, root paths, cache/event/static ownership.

**Fix** → bounded cache, unsubscribe, shorten lifetime hoặc break references.

**Verification** → soak test dài, heap plateau sau warm-up và repeated GC cycles.

## 7. Common mistakes

* Nhìn working set rồi kết luận leak ngay.
* Restart process thay vì root-cause.
* Tối ưu allocation khi vấn đề là retention.
* Dump production nhưng không bảo vệ sensitive data trong dump.
* Chụp một snapshot duy nhất rồi suy luận trend.

## 8. Alternatives

`dotnet-gcdump` nhẹ hơn full dump cho GC heap analysis. Application Insights/containers metrics tốt cho trend. Profilers như PerfView/Visual Studio/dotMemory hữu ích khi reproduction local/staging khả thi.

## 9. Trade-offs

### Advantages

* GC-root analysis cho evidence trực tiếp về retention.
* Managed diagnostics tooling khá mạnh.

### Costs / Risks

* Dump lớn và chứa sensitive memory.
* Production capture có operational overhead.
* Cần hiểu warm-up/cache behavior để tránh false positive.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu object reachable thì GC không collect.

### Middle

Dùng counters, reproduce leak và inspect dominant types.

### Senior

Phân biệt allocation pressure, LOH growth và retained object graph; đọc root path.

### Technical Lead / Architect

Thiết kế bounded caches, lifetime/ownership conventions và production diagnostics policy an toàn.

## 11. Key takeaway

* Managed memory vẫn leak khi references sống quá lâu.
* Phân biệt allocation rate và retained growth trước khi sửa.
* Root path quan trọng hơn chỉ nhìn type count.

# 10. Akamai/CDN `Cache-Control`: browser cache, edge cache, stale content và purge/invalidation ownership

## 1. What is it?

CDN caching có ít nhất hai cache layers khác nhau:

```text
Browser cache
      ↓
CDN edge cache
      ↓
Origin application
```

`Cache-Control` quyết định representation được cache ở đâu, trong bao lâu và khi nào phải revalidate.

## 2. Why does it exist?

Nếu mọi user request đều về origin để lấy CSS, image hoặc public content giống nhau, origin chịu network/CPU load không cần thiết và global latency cao.

CDN đưa content gần user hơn. Nhưng caching sai có thể serve stale hoặc private data cho sai user, nên caching là correctness concern chứ không chỉ performance.

## 3. How does it work?

Ví dụ static asset versioned:

```http
Cache-Control: public, max-age=31536000, immutable
```

HTML/content cần freshness hơn:

```http
Cache-Control: public, max-age=60, s-maxage=300
```

`max-age` thường áp dụng downstream/private caches; `s-maxage` có thể hướng shared cache. Exact CDN behavior còn phụ thuộc property configuration ở Akamai.

Cache key cũng quan trọng: path, query string, headers, cookies có thể ảnh hưởng object variant.

## 4. Practical implementation

ASP.NET Core static files có fingerprinted filenames:

```text
app.7f3a91.js
styles.a82b1c.css
```

Khi content hash thay đổi, URL mới xuất hiện, nên asset cũ có thể cache rất lâu mà không cần purge.

Dynamic CMS page nên có explicit cache policy và surrogate invalidation strategy thay vì TTL 1 năm.

## 5. Real production scenario

Marketing website qua Akamai publish hero banner mới. Origin đã đúng nhưng một số regions vẫn thấy banner cũ vì edge object TTL còn 30 phút.

Team panic purge toàn site, làm origin traffic spike. Vấn đề là invalidation ownership và TTL strategy chưa rõ.

## 6. Failure scenario & troubleshooting

**Symptom** → user A thấy stale page còn user B thấy mới.

**Evidence** → response headers cho thấy different edge cache status/age.

**Hypothesis** → edge cache variant/region chưa revalidate hoặc purge chưa propagate.

**Diagnosis** → inspect `Age`, cache headers, cache key inputs, Akamai debug headers/tooling và origin version.

**Fix** → targeted purge/invalidation, TTL hợp lý hoặc versioned URL.

**Verification** → kiểm tra nhiều regions/edge nodes và confirm origin traffic không spike bất thường.

## 7. Common mistakes

* Cache personalized response như public content.
* Dùng cookie/request header trong cache key mà không chủ đích, làm hit ratio sụp.
* Purge toàn site cho mọi content update.
* TTL rất ngắn khiến CDN gần như vô dụng.
* Không version static assets.

## 8. Alternatives

Browser-only caching đơn giản hơn nhưng không giảm origin traffic giữa users. Reverse-proxy cache gần origin giảm app load nhưng không giảm geographic latency như global CDN. No-cache phù hợp security-sensitive/private data.

## 9. Trade-offs

### Advantages

* Giảm latency toàn cầu.
* Giảm origin load và egress path.
* Tăng resilience cho cacheable content.

### Costs / Risks

* Staleness và invalidation complexity.
* Cache-key sai gây leakage hoặc low hit ratio.
* Purge operations có blast radius.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser cache và CDN edge cache là hai layer khác nhau.

### Middle

Đọc `Cache-Control`, `Age`, cache status và version static assets.

### Senior

Debug stale variants, cache keys, purge propagation và origin load impact.

### Technical Lead / Architect

Định nghĩa cache ownership theo content type, freshness SLA, invalidation mechanism và security boundary; quyết định content nào không nên cache.

## 11. Key takeaway

* CDN caching là correctness + performance, không chỉ speed.
* Versioned immutable assets giảm nhu cầu purge đáng kể.
* Invalidation phải targeted và có owner; purge toàn site là emergency tool, không phải normal workflow.
