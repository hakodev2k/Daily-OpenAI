# 1. .NET `Task.WhenAll`: bounded fan-out, exception semantics và dependency pressure

## 1. What is it?

`Task.WhenAll` tạo một task hoàn tất khi toàn bộ tập tasks đầu vào đã hoàn tất. Mental model quan trọng không phải “chạy song song cho nhanh”, mà là **fan-out asynchronous work rồi join kết quả**. Nó không tự giới hạn concurrency, không tạo capacity cho downstream và không biến I/O-bound work thành CPU parallelism.

## 2. Why does it exist?

Khi các I/O operations độc lập, chạy tuần tự làm tổng latency gần bằng tổng latency từng call. Fan-out cho phép overlap thời gian chờ. Nhưng nếu fan-out không bounded, một request có thể tạo hàng trăm database/HTTP calls và chuyển bottleneck sang dependency.

## 3. How does it work?

```text
Request
  ├── Task A ─► dependency
  ├── Task B ─► dependency
  ├── Task C ─► dependency
  └── Task N ─► dependency
          │
          ▼
      Task.WhenAll
```

Các async methods bắt đầu work khi được gọi. `WhenAll` chủ yếu aggregate completion. Nếu nhiều tasks fault, task tổng hợp fault; khi `await`, cần hiểu rằng diagnostic đầy đủ có thể nằm trong các tasks/aggregate exception information chứ không nên chỉ log một message rồi mất context.

## 4. Practical implementation

Với danh sách lớn, giới hạn fan-out:

```csharp
var gate = new SemaphoreSlim(8);

var tasks = ids.Select(async id =>
{
    await gate.WaitAsync(ct);
    try
    {
        return await client.GetOrderAsync(id, ct);
    }
    finally
    {
        gate.Release();
    }
});

var orders = await Task.WhenAll(tasks);
```

Nếu workload là stream lớn, `Parallel.ForEachAsync` với `MaxDegreeOfParallelism` có thể diễn đạt bounded concurrency rõ hơn.

## 5. Real production scenario

Một product page cần enrich 80 SKUs từ pricing API. Chuyển loop tuần tự sang `Task.WhenAll` làm latency giảm mạnh ở staging, nhưng production pricing API bị 429 vì mỗi web request tạo 80 concurrent calls. Tối ưu local latency đã phá capacity downstream.

## 6. Failure scenario & troubleshooting

**Symptom** → p95 giảm lúc tải thấp nhưng 429/timeouts tăng khi traffic cao.  
**Evidence** → dependency concurrent requests tăng theo `incoming RPS × fan-out`.  
**Hypothesis** → unbounded fan-out gây saturation.  
**Diagnosis** → xem dependency traces, active requests, connection pool và rate-limit telemetry.  
**Fix** → bounded concurrency, batching, caching hoặc redesign API.  
**Verification** → load test lại và đo cả endpoint latency lẫn dependency saturation.

## 7. Common mistakes

Dùng `Task.WhenAll` cho hàng nghìn items không giới hạn; dùng `Task.Run` quanh async I/O; quên cancellation; chỉ log exception đầu tiên; tạo fan-out qua EF Core bằng cùng một `DbContext` dù `DbContext` không hỗ trợ concurrent operations.

## 8. Alternatives

Sequential execution đúng khi dependency yêu cầu ordering hoặc volume nhỏ. `Parallel.ForEachAsync` phù hợp bounded asynchronous iteration. Batching tốt hơn nếu downstream hỗ trợ. Queue-based processing phù hợp khi không cần synchronous completion.

## 9. Trade-offs

### Advantages

Giảm wall-clock latency cho independent I/O và tận dụng thời gian chờ hiệu quả.

### Costs / Risks

Tăng concurrency, connection usage, rate-limit pressure và failure amplification.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu concurrency khác parallelism và `WhenAll` không tự tạo thread cho I/O.

### Middle

Biết propagate cancellation, xử lý failures và giới hạn concurrency.

### Senior

Tính fan-out amplification và quan sát downstream capacity.

### Technical Lead / Architect

Quyết định khi nào nên fan-out, batch, cache hoặc chuyển workflow sang asynchronous messaging.

## 11. Key takeaway

- `Task.WhenAll` là join primitive, không phải capacity-control primitive.
- Tối ưu latency phải tính pressure lên downstream.
- Bounded concurrency thường quan trọng hơn “chạy tất cả cùng lúc”.

# 2. ASP.NET Core Endpoint Filters: cross-cutting behavior ở endpoint boundary

## 1. What is it?

Endpoint Filters cho phép chèn logic trước/sau Minimal API handler. Mental model: một **endpoint-scoped interception pipeline** cho concerns gắn với endpoint contract, không phải middleware thay thế cho toàn bộ HTTP pipeline.

## 2. Why does it exist?

Middleware phù hợp concerns toàn request pipeline, nhưng đôi khi validation, endpoint-specific authorization checks hoặc response transformation cần metadata/arguments của handler. Đẩy logic này vào từng handler tạo duplication.

## 3. How does it work?

```text
HTTP middleware
   │
   ▼
Endpoint selected
   │
Filter A → Filter B → Handler → Filter B → Filter A
```

Filter chạy sau routing/endpoint selection và có thể inspect invocation arguments. Boundary này hẹp hơn middleware.

## 4. Practical implementation

```csharp
public sealed class ValidationFilter<T> : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var request = context.Arguments.OfType<T>().FirstOrDefault();
        if (request is null)
            return Results.BadRequest();

        return await next(context);
    }
}

app.MapPost("/orders", CreateOrder)
   .AddEndpointFilter<ValidationFilter<CreateOrderRequest>>();
```

Filter nên giữ concern rõ ràng; business policy vẫn thuộc application/domain layer.

## 5. Real production scenario

Một nhóm Minimal APIs có cùng request validation và tenant-context checks. Filter giúp giữ handler tập trung vào use case mà không biến global middleware thành nơi biết mọi DTO.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint trả response khác nhau tùy thứ tự filters.  
**Evidence** → một filter short-circuit trước filter logging/validation khác.  
**Hypothesis** → filter ordering mang semantic dependency không được document.  
**Diagnosis** → trace execution order và short-circuit paths.  
**Fix** → giảm coupling giữa filters, đặt ordering rõ và integration test pipeline.  
**Verification** → success/failure paths đều tạo contract và telemetry mong đợi.

## 7. Common mistakes

Đưa domain logic vào filters; dùng filter cho concern global đáng ra là middleware; tạo hidden dependency theo order; swallow exception; duplicate authorization framework bằng custom code.

## 8. Alternatives

Middleware cho cross-cutting concern toàn pipeline. Authorization policies cho access control. Application pipeline behaviors phù hợp use-case boundary độc lập HTTP.

## 9. Trade-offs

### Advantages

Giảm endpoint duplication và truy cập được endpoint arguments/context.

### Costs / Risks

Pipeline khó nhìn thấy hơn nếu quá nhiều filters; ordering và short-circuit tăng cognitive load.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu middleware và endpoint filter ở hai boundary khác nhau.

### Middle

Implement reusable validation/endpoint concern và test ordering.

### Senior

Giữ business logic khỏi HTTP interception infrastructure.

### Technical Lead / Architect

Định nghĩa concern nào thuộc global pipeline, endpoint boundary hay application layer.

## 11. Key takeaway

- Endpoint Filter phù hợp concern biết endpoint/arguments.
- Không dùng filter như nơi giấu business logic.
- Boundary và ordering quan trọng hơn giảm vài dòng code.

# 3. EF Core Temporal Tables: audit/history queries mà không biến application thành event store

## 1. What is it?

SQL Server temporal table tự duy trì history của row theo system time; EF Core hỗ trợ mapping/query temporal data. Mental model: **database-managed row-version history**, không phải Event Sourcing và không tự lưu business intent.

## 2. Why does it exist?

Nhiều enterprise systems cần trả lời “record trông như thế nào lúc 10:00 hôm qua?” mà không muốn tự viết audit-copy logic cho mọi update/delete.

## 3. How does it work?

```text
Current table
  UPDATE/DELETE
      │
      ├── current version changes
      └── previous row ─► history table + validity period
```

Database lưu row states theo thời gian hệ thống. Nó biết dữ liệu thay đổi từ A sang B, nhưng không biết business reason như “Manager approved timesheet”.

## 4. Practical implementation

```csharp
modelBuilder.Entity<Employee>()
    .ToTable("Employees", b => b.IsTemporal());

var snapshot = await db.Employees
    .TemporalAsOf(asOfUtc)
    .AsNoTracking()
    .SingleAsync(x => x.Id == employeeId, ct);
```

Migration cần được review vì enabling temporal behavior thay đổi schema/history storage.

## 5. Real production scenario

HR support cần điều tra employee profile đã có manager nào tại thời điểm approval. Temporal query cung cấp row snapshot mà không phải restore backup hoặc đọc ad-hoc audit logs.

## 6. Failure scenario & troubleshooting

**Symptom** → history table tăng rất nhanh và migration/maintenance chậm.  
**Evidence** → high-update table giữ mọi row version lâu dài.  
**Hypothesis** → retention/storage chưa được thiết kế.  
**Diagnosis** → đo history growth, update frequency, indexes và query patterns.  
**Fix** → retention/archival strategy và index phù hợp.  
**Verification** → history queries đáp ứng SLA trong khi storage growth bounded.

## 7. Common mistakes

Gọi temporal table là Event Sourcing; dùng history như business audit đầy đủ; không tính storage; dùng local time không nhất quán; query history với tracking khi không cần.

## 8. Alternatives

Explicit audit table lưu actor/reason tốt hơn cho compliance semantics. Domain Events lưu business facts nhưng lifecycle khác. Event Sourcing phù hợp khi event log là source of truth, với complexity lớn hơn nhiều.

## 9. Trade-offs

### Advantages

History tự động ở database layer, query point-in-time thuận tiện, ít application plumbing.

### Costs / Risks

Storage tăng, retention/indexing cần vận hành và không capture business intent đầy đủ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu current row và historical row versions.

### Middle

Map/query temporal data bằng EF Core.

### Senior

Thiết kế retention, indexing và audit semantics.

### Technical Lead / Architect

Quyết định temporal history có đáp ứng requirement hay cần explicit audit/event model.

## 11. Key takeaway

- Temporal table lưu state history, không tự lưu business intent.
- History storage cần lifecycle như dữ liệu production khác.
- Không nâng requirement audit đơn giản thành Event Sourcing nếu không cần.

# 4. SQL Server SARGability: vì sao cùng một predicate có thể biến Index Seek thành Scan

## 1. What is it?

SARGable predicate là predicate mà optimizer có thể dùng search argument hiệu quả với index access path. Mental model: index chỉ hữu ích khi predicate cho engine một phạm vi/key có thể tìm trực tiếp; bọc indexed column trong function thường làm việc đó khó hơn.

## 2. Why does it exist?

Một query nhìn “đúng logic” có thể buộc SQL Server evaluate expression cho rất nhiều rows. Khi bảng lớn, CPU/I/O tăng dù index tồn tại.

## 3. How does it work?

Không tốt:

```sql
WHERE YEAR(CreatedAt) = 2026
```

Tốt hơn:

```sql
WHERE CreatedAt >= '20260101'
  AND CreatedAt <  '20270101'
```

Predicate thứ hai biểu diễn range trực tiếp trên `CreatedAt`, tạo cơ hội cho Index Seek nếu statistics/index/selectivity phù hợp.

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_CreatedAt
ON dbo.Orders(CreatedAt)
INCLUDE (CustomerId, Total);

SELECT CustomerId, Total
FROM dbo.Orders
WHERE CreatedAt >= @From
  AND CreatedAt < @To;
```

Đừng kết luận từ operator name một mình; xem actual rows, logical reads, CPU và elapsed time.

## 5. Real production scenario

Dashboard filter orders theo ngày chạy 40 ms ở dev nhưng 6 giây trên bảng 200 triệu rows. Index đã có, nhưng query dùng `CONVERT(date, CreatedAt)` trong predicate và đọc lượng pages rất lớn.

## 6. Failure scenario & troubleshooting

**Symptom** → query scan nhiều pages dù có index.  
**Evidence** → execution plan + `STATISTICS IO` cho logical reads cao.  
**Hypothesis** → non-SARGable predicate hoặc access path không selective.  
**Diagnosis** → inspect predicate, implicit conversions, statistics và plan estimates.  
**Fix** → rewrite predicate/range, sửa type mismatch; chỉ thay index khi evidence cần.  
**Verification** → logical reads và p95 giảm trên representative data.

## 7. Common mistakes

Thêm index mới mà không sửa predicate; function trên indexed column; implicit conversion do parameter type sai; chỉ nhìn estimated plan; dùng wildcard `%term` rồi kỳ vọng normal B-tree seek.

## 8. Alternatives

Persisted computed column + index hữu ích khi expression là requirement lặp lại. Full-text search phù hợp text search. Scan có thể đúng nếu query thực sự cần phần lớn bảng.

## 9. Trade-offs

### Advantages

Predicate tốt có thể tận dụng index hiện hữu và giảm I/O mạnh.

### Costs / Risks

Rewrite phải giữ semantics; thêm computed/index structures tăng write/storage cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Index Seek và Scan không chỉ phụ thuộc “có index hay không”.

### Middle

Đọc plan và `STATISTICS IO`.

### Senior

Reason từ query → estimates → access path → I/O → locks → latency.

### Technical Lead / Architect

Đặt query-review/performance practice dựa trên production-shaped data thay vì rule “mọi filter phải có index”.

## 11. Key takeaway

- Index không cứu được mọi predicate.
- Logical reads là evidence quan trọng hơn cảm giác query “đơn giản”.
- Scan đôi khi đúng; mục tiêu là access path phù hợp workload.

# 5. Elasticsearch refresh interval: near-real-time search, indexing throughput và freshness contract

## 1. What is it?

Elasticsearch refresh làm các thay đổi đã index trở nên searchable bằng cách mở search-visible segments mới. Mental model: **acknowledged indexing không đồng nghĩa ngay lập tức searchable**; Elasticsearch là near-real-time search engine.

## 2. Why does it exist?

Nếu mọi document write buộc synchronous search visibility, indexing throughput và I/O cost sẽ tăng. Refresh tách durability/indexing progress khỏi search visibility timing.

## 3. How does it work?

```text
Primary DB → sync worker → Elasticsearch index buffer
                              │
                           refresh
                              ▼
                       searchable segment
```

Freshness chịu ảnh hưởng bởi cả upstream synchronization lag và Elasticsearch refresh; chỉ chỉnh refresh interval không sửa worker backlog.

## 4. Practical implementation

Bulk import có thể tạm điều chỉnh refresh behavior, sau đó restore policy và refresh có chủ đích. Application không nên gọi refresh sau từng document chỉ để test “read-after-write”.

```http
PUT products/_settings
{
  "index": {
    "refresh_interval": "5s"
  }
}
```

Giá trị thực tế phải dựa workload/freshness SLO, không copy cố định.

## 5. Real production scenario

Merchandiser publish product rồi search page chưa thấy trong vài giây. Nếu requirement cho phép 10-second search freshness thì đây có thể là expected eventual consistency; admin UI cần thể hiện trạng thái thay vì giả vờ strong consistency.

## 6. Failure scenario & troubleshooting

**Symptom** → search lag 10 phút.  
**Evidence** → refresh bình thường nhưng sync queue backlog lớn.  
**Hypothesis** → ingestion pipeline, không phải refresh.  
**Diagnosis** → đo DB-change timestamp → queue → indexing ack → searchable timestamp.  
**Fix** → xử lý bottleneck đúng stage.  
**Verification** → end-to-end freshness percentile về trong SLO.

## 7. Common mistakes

Refresh sau mỗi write; coi Elasticsearch là transactional source of truth; chỉ đo indexing API latency; không có replay/reindex path; giảm refresh interval mà không đo indexing throughput.

## 8. Alternatives

SQL search đủ cho filtering/simple search nhỏ. Dedicated search engine đáng giá khi relevance, analyzers, full-text và search scale thực sự cần.

## 9. Trade-offs

### Advantages

Tách write throughput khỏi immediate search visibility và cho phép tune freshness.

### Costs / Risks

Eventual consistency trở thành product/operational concern; refresh quá thường xuyên tăng segment/I/O overhead.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu indexed không đồng nghĩa searchable ngay.

### Middle

Đo refresh và ingestion lag.

### Senior

Tách sync backlog khỏi Elasticsearch refresh behavior.

### Technical Lead / Architect

Định nghĩa search freshness SLO và recovery/reindex architecture từ source of truth.

## 11. Key takeaway

- Search freshness là end-to-end property.
- Refresh interval là trade-off, không phải “càng thấp càng tốt”.
- Primary database vẫn nên sở hữu transactional truth.

# 6. Anti-Corruption Layer: bảo vệ domain model khỏi contract của hệ thống bên ngoài

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary chuyển đổi model/protocol của external hoặc legacy system thành model phù hợp bounded context nội bộ. Mental model: **translation boundary chống semantic coupling**, không phải generic wrapper quanh mọi HTTP client.

## 2. Why does it exist?

External ERP có thể gọi `Customer` là `Account`, status codes có semantics lịch sử và field names không phù hợp domain mới. Nếu application lan trực tiếp external DTO khắp domain, model nội bộ bị external contract điều khiển.

## 3. How does it work?

```text
Our Domain
   │ internal concepts
   ▼
Application Port
   │
   ▼
Anti-Corruption Adapter
   │ translate semantics/protocol
   ▼
Legacy ERP / External API
```

Data ownership vẫn ở hệ thống tương ứng; ACL không tạo distributed transaction. External failure được map thành failure semantics nội bộ có chủ đích.

## 4. Practical implementation

```csharp
public interface ICustomerCreditGateway
{
    Task<CreditDecision> CheckAsync(CustomerId id, Money amount, CancellationToken ct);
}

internal sealed class ErpCreditGateway(ErpClient client) : ICustomerCreditGateway
{
    public async Task<CreditDecision> CheckAsync(CustomerId id, Money amount, CancellationToken ct)
    {
        var dto = await client.CheckAsync(id.Value, amount.Value, ct);
        return dto.Code switch
        {
            "A" => CreditDecision.Approved,
            "R" => CreditDecision.Rejected,
            _ => CreditDecision.Unavailable
        };
    }
}
```

## 5. Real production scenario

E-commerce platform tích hợp legacy inventory service có `-1` nghĩa “unknown”, không phải zero stock. ACL giữ semantic này khỏi contaminating product domain.

## 6. Failure scenario & troubleshooting

**Symptom** → external provider đổi enum và domain bắt đầu xử lý sai.  
**Evidence** → mapping default coi unknown code là valid business state.  
**Hypothesis** → contract drift tại integration boundary.  
**Diagnosis** → contract tests, payload telemetry và provider changelog.  
**Fix** → fail/translate explicit unknown states, version adapter.  
**Verification** → contract tests cover old/new payloads và domain invariant giữ nguyên.

## 7. Common mistakes

Chỉ rename DTO fields rồi gọi đó là ACL; external DTO đi thẳng vào domain; ACL chứa business rules thuộc domain; tạo ACL cho stable internal library không có semantic mismatch.

## 8. Alternatives

Direct integration đơn giản hơn khi semantics gần nhau và coupling chấp nhận được. Adapter đơn thuần đủ nếu chỉ protocol mismatch. ACL đáng giá khi semantic translation/change isolation là vấn đề thật.

## 9. Trade-offs

### Advantages

Giữ domain language sạch, cô lập contract drift và giảm blast radius của legacy/external semantics.

### Costs / Risks

Thêm mapping code, tests và ownership boundary cần duy trì.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu external DTO không nhất thiết là domain model.

### Middle

Implement explicit translation và contract tests.

### Senior

Thiết kế failure mapping, retries và semantic version drift.

### Technical Lead / Architect

Quyết định integration boundary nào cần ACL và ai sở hữu mapping khi hai systems thay đổi độc lập.

## 11. Key takeaway

- ACL bảo vệ semantics, không chỉ đổi tên fields.
- External contract không nên trở thành domain language mặc định.
- Chỉ thêm boundary khi change isolation thực sự có giá trị.

# 7. Azure Private Endpoint + Private DNS: private connectivity và lỗi “works locally, fails in Azure”

## 1. What is it?

Azure Private Endpoint đưa một PaaS resource như Storage/Key Vault vào private network path bằng private IP trong VNet. Private DNS giúp hostname chuẩn resolve về private IP từ network phù hợp. Mental model: **identity của service vẫn qua hostname, nhưng network route được private hóa**.

## 2. Why does it exist?

Enterprise workloads thường không muốn data-plane endpoint reachable qua public network. Chỉ firewall IP public có thể không đáp ứng segmentation/private-connectivity requirement.

## 3. How does it work?

```text
App Service / VNet-integrated workload
        │ DNS lookup service hostname
        ▼
Private DNS zone
        │ private IP
        ▼
Private Endpoint NIC ─► Azure PaaS service
```

Private Endpoint, DNS, VNet integration và service firewall là các phần riêng; tạo một Private Endpoint không tự sửa DNS cho mọi network.

## 4. Practical implementation

Application code thường không đổi endpoint:

```csharp
var client = new BlobServiceClient(
    new Uri("https://myaccount.blob.core.windows.net"),
    new DefaultAzureCredential());
```

Điều cần verify là DNS từ runtime environment:

```bash
nslookup myaccount.blob.core.windows.net
```

Kết quả phải đi tới private address theo topology mong đợi.

## 5. Real production scenario

Storage public access bị disable. Developer laptop qua public path thất bại, App Service production qua VNet phải resolve private endpoint. Một staging slot chưa gắn VNet integration nên deployment health check fail.

## 6. Failure scenario & troubleshooting

**Symptom** → authentication đúng nhưng connection timeout.  
**Evidence** → DNS resolve public IP hoặc private IP không route được.  
**Hypothesis** → DNS/network path sai, không phải credential.  
**Diagnosis** → DNS resolution, effective routes, NSG/firewall, VNet integration và Private Endpoint approval.  
**Fix** → link đúng Private DNS zone và sửa network path.  
**Verification** → DNS + TCP connectivity + application dependency trace đều đúng.

## 7. Common mistakes

Debug 403/timeout chỉ bằng RBAC; hard-code private IP; quên DNS cho on-prem/VPN; assume deployment slot dùng cùng network settings; mở public access lại để “fix” production.

## 8. Alternatives

Public endpoint + firewall có operational model đơn giản hơn và có thể đủ cho risk profile thấp hơn. Service Endpoint là cơ chế khác với Private Endpoint và không tạo private IP cho service theo cùng cách.

## 9. Trade-offs

### Advantages

Private data-plane connectivity, giảm public exposure và phù hợp network segmentation.

### Costs / Risks

DNS/topology phức tạp hơn, thêm resource/cost và troubleshooting khó hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt DNS, route, authentication và authorization.

### Middle

Debug hostname resolution và connectivity từ workload.

### Senior

Reason về VNet integration, Private DNS, firewall và hybrid DNS.

### Technical Lead / Architect

Quyết định service nào cần private connectivity dựa threat model, compliance, cost và supportability.

## 11. Key takeaway

- Private Endpoint là network boundary; Managed Identity/RBAC là identity boundary.
- DNS là phần cốt lõi của private connectivity.
- Đừng mở lại public access trước khi chứng minh root cause.

# 8. TeamCity Build Chain: artifact promotion thay vì rebuild mỗi environment

## 1. What is it?

TeamCity Build Chain nối các build configurations bằng snapshot/artifact dependencies. Mental model cho release engineering: **build một immutable artifact, sau đó promote chính artifact đó qua environments**, thay vì compile lại source cho từng environment.

## 2. Why does it exist?

Nếu Production rebuild từ cùng Git commit nhưng dependency resolution/toolchain thay đổi, artifact production có thể khác artifact đã test ở staging. Điều đó phá evidence “thứ đã test chính là thứ đang deploy”.

## 3. How does it work?

```text
Commit
  ▼
Build → Unit/Integration Tests → Artifact v123
                               │
                 ┌─────────────┴─────────────┐
                 ▼                           ▼
              Staging                    Production
                 │ health                    │ health
                 └──────── monitor/rollback ─┘
```

Configuration khác nhau nên được inject lúc deploy/runtime; binary artifact không nên được rebuild chỉ để thay environment settings.

## 4. Practical implementation

Build configuration xuất artifact:

```text
artifacts/
  Nexora.Api.zip
  migrations/
  manifest.json
```

Deployment configuration nhận artifact dependency từ build đã pass tests. Version/commit SHA được ghi vào manifest để trace production binary về source.

## 5. Real production scenario

TeamCity build staging sáng thứ Hai, Production rebuild cùng commit thứ Ba. NuGet floating dependency thay đổi khiến production binary khác staging. Artifact promotion loại class drift này.

## 6. Failure scenario & troubleshooting

**Symptom** → “same commit” nhưng behavior staging/prod khác.  
**Evidence** → artifact hashes khác nhau.  
**Hypothesis** → rebuild-per-environment.  
**Diagnosis** → trace build IDs, package lockfiles, artifact hashes và deployment logs.  
**Fix** → immutable artifact promotion, pinned dependencies, environment config separation.  
**Verification** → hash deployed binary giống artifact đã test.

## 7. Common mistakes

Rebuild cho Production; bake secrets vào artifact; không version artifact; deploy “latest”; database migration chạy không có backward-compatibility plan; health check chỉ xác nhận process chạy.

## 8. Alternatives

Jenkins/Azure Pipelines/GitHub Actions đều có thể implement cùng principle. Tool không quan trọng bằng artifact immutability và promotion model.

## 9. Trade-offs

### Advantages

Reproducibility, traceability và rollback confidence tốt hơn.

### Costs / Risks

Cần artifact repository, retention, versioning và config separation discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu build artifact khác source checkout.

### Middle

Thiết lập build → test → artifact → deploy dependency.

### Senior

Đảm bảo reproducibility, migrations, health validation và rollback.

### Technical Lead / Architect

Định nghĩa release contract độc lập CI/CD vendor: immutable artifact, provenance, promotion và verification.

## 11. Key takeaway

- Build once, promote many.
- Same commit không đảm bảo same binary nếu rebuild.
- Release evidence phải nối source → artifact → deployment → health.

# 9. Alert fatigue: thiết kế alert từ SLO và actionable symptom thay vì mọi metric spike

## 1. What is it?

Alert fatigue xảy ra khi hệ thống phát quá nhiều notifications ít actionable khiến engineers dần bỏ qua chúng. Mental model: alert không phải dashboard threshold; alert là **yêu cầu con người hành động vì user-impacting risk đủ cao**.

## 2. Why does it exist?

Production có vô số metric dao động bình thường. Alert trên CPU > 70% trong một phút, từng exception hoặc từng pod restart tạo noise và làm on-call mất khả năng phân biệt incident thật.

## 3. How does it work?

```text
Logs ─┐
Metrics ─┼─► telemetry → SLI/SLO reasoning → actionable alert → human
Traces ─┘                         │
                                 └─ dashboard only nếu chưa cần action
```

Một service có 99.9% availability SLO nên ưu tiên alert dựa error-budget burn/user symptoms hơn infrastructure fluctuation không gây impact.

## 4. Practical implementation

Ví dụ alert logic khái niệm:

```text
Fast burn:  error budget burn > 14x trong 5m và 1h
Slow burn:  error budget burn > 2x trong 6h và 24h
```

Con số phải dựa SLO thực tế. Alert payload nên có service, symptom, scope, dashboard/runbook và recent deployment context.

## 5. Real production scenario

API CPU lên 85% mỗi ngày lúc batch chạy nhưng latency/error rate vẫn trong SLO. CPU alert đánh thức on-call vô ích. Một tuần sau, real checkout failure bị bỏ qua giữa hàng trăm noisy alerts.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều alerts nhưng incident detection vẫn chậm.  
**Evidence** → high alert volume, low action rate, repeated acknowledgements không remediation.  
**Hypothesis** → thresholds không gắn user impact/action.  
**Diagnosis** → review 30 ngày alerts: actionable, duplicate, false-positive, symptom vs cause.  
**Fix** → deduplicate, route severity, dùng SLO/burn-rate và chuyển diagnostic metrics về dashboard.  
**Verification** → alert volume giảm nhưng detection time/user-impact coverage tốt hơn.

## 7. Common mistakes

Alert mọi exception; alert cause thay vì symptom; không có owner/runbook; threshold giống nhau mọi service; mute noisy alert mà không sửa; chỉ có logs mà thiếu metrics/traces để điều tra.

## 8. Alternatives

Dashboard phù hợp exploration. Ticket phù hợp non-urgent degradation. Alert/page dành cho condition cần phản ứng nhanh. Không phải telemetry nào cũng cần notification.

## 9. Trade-offs

### Advantages

Ít noise, phản ứng incident nhanh hơn và on-call signal đáng tin hơn.

### Costs / Risks

Threshold quá bảo thủ có thể bỏ early warning; SLO design và telemetry quality cần đầu tư.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt log, metric, trace và alert.

### Middle

Tạo alert có context và runbook.

### Senior

Tune theo SLI/SLO, burn rate và incident evidence.

### Technical Lead / Architect

Định nghĩa observability ownership, severity policy và review alert quality như production code.

## 11. Key takeaway

- Alert phải yêu cầu action, không chỉ báo metric thay đổi.
- Logs + Metrics + Traces hỗ trợ diagnosis; alert quyết định khi nào con người cần vào cuộc.
- Noise cao làm giảm reliability thay vì tăng nó.

# 10. React stale closure: async UI, state snapshot và race condition với backend API

## 1. What is it?

Trong React, function render tạo closures nhìn thấy state/props của render đó. Async callback có thể tiếp tục giữ snapshot cũ sau khi UI đã render state mới. Mental model: **mỗi render có một state snapshot**, không phải mọi callback luôn đọc “giá trị mới nhất”.

## 2. Why does it exist?

JavaScript closures giữ lexical bindings; React render model dựa trên immutable snapshots. Điều này làm reasoning deterministic nhưng async effects/timers/network callbacks dễ dùng stale values nếu dependency/lifecycle không đúng.

## 3. How does it work?

```text
Render A: query = "car"
  └─ request A --------------------┐
Render B: query = "car parts"      │
  └─ request B ----► result B       │
                                     └─► result A arrives late
```

Nếu callback A vẫn commit result, UI có thể hiển thị data cho query cũ dù input đã đổi.

## 4. Practical implementation

Hủy request cũ trong effect cleanup:

```tsx
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    const response = await fetch(`/api/search?q=${encodeURIComponent(query)}`, {
      signal: controller.signal
    });
    const data = await response.json();
    setResults(data);
  }

  load().catch(err => {
    if (err.name !== 'AbortError') throw err;
  });

  return () => controller.abort();
}, [query]);
```

Backend vẫn nên support cancellation/timeouts và không giả định client abort rollback side effects.

## 5. Real production scenario

Automotive search page gửi request khi filter thay đổi. User click nhanh nhiều filters; request cũ chậm hơn request mới và overwrite results, tạo bug “filter đúng nhưng danh sách sai”.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị response cũ.  
**Evidence** → network waterfall cho request A hoàn tất sau B.  
**Hypothesis** → stale async result/race.  
**Diagnosis** → log request IDs, render state và response completion order.  
**Fix** → abort stale request hoặc guard bằng request/version identity.  
**Verification** → rapid-interaction test không commit stale response.

## 7. Common mistakes

Thiếu dependencies trong `useEffect`; dùng stale state trong timer; debounce nhưng không xử lý out-of-order response; coi client abort là transactional rollback; thêm arbitrary delay để “ổn định”.

## 8. Alternatives

Query libraries có thể quản lý request keys, caching và stale results. Reducer/state machine phù hợp flow phức tạp. Server-side rendering không loại bỏ client race sau hydration.

## 9. Trade-offs

### Advantages

Hiểu snapshot model giúp code predictable và xử lý async correctness rõ ràng.

### Costs / Risks

Cancellation/version guards thêm lifecycle complexity; frontend và backend cần thống nhất semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu closure giữ state của render tương ứng.

### Middle

Implement effect dependencies, cleanup và cancellation.

### Senior

Phân biệt stale closure, stale response, cache staleness và backend consistency.

### Technical Lead / Architect

Định nghĩa client data-access pattern để race/cancellation/error handling nhất quán toàn frontend.

## 11. Key takeaway

- React async callback không tự nhìn thấy “state mới nhất”.
- Network responses có thể hoàn tất khác thứ tự gửi.
- UI cancellation và backend transactional semantics là hai boundary khác nhau.
