# 1. C# `CancellationTokenSource.CreateLinkedTokenSource`: phân biệt client disconnect, timeout và application shutdown thay vì dùng một token cho mọi failure

## 1. What is it?

`CancellationToken` trong .NET là cơ chế **cooperative cancellation**: một caller phát tín hiệu “hãy dừng nếu có thể”, còn code phía dưới chủ động quan sát token và kết thúc công việc ở boundary an toàn.

Trong application thực tế, một operation thường có nhiều lý do để bị hủy:

- client đóng HTTP connection;
- application đang shutdown;
- business operation vượt timeout;
- caller phía trên hủy workflow.

`CancellationTokenSource.CreateLinkedTokenSource` tạo một token bị cancel khi **bất kỳ** token nguồn nào bị cancel.

Mental model:

```text
RequestAborted ----\
ShutdownToken ------+--> Linked Token --> DB / HTTP / file / queue
TimeoutToken -------/
```

## 2. Why does it exist?

Nếu chỉ propagate `HttpContext.RequestAborted`, request có thể chạy vô thời hạn khi downstream bị treo nhưng client vẫn kết nối.

Nếu chỉ dùng timeout token, application có thể tiếp tục làm việc trong lúc host đang shutdown.

Nếu tạo token riêng ở mỗi layer mà không liên kết, cancellation semantics bị phân mảnh: database dừng nhưng HTTP call vẫn chạy, hoặc ngược lại.

Linked token tồn tại để tạo **một cancellation boundary cho operation**, nhưng vẫn giữ được nhiều nguồn tín hiệu.

## 3. How does it work?

`CancellationTokenSource` đăng ký callback lên các source token. Khi bất kỳ source nào cancel, linked source chuyển sang canceled state.

```csharp
using var timeoutCts = new CancellationTokenSource(
    TimeSpan.FromSeconds(3));

using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(
    requestAborted,
    timeoutCts.Token,
    appStopping);

await ExecuteAsync(linkedCts.Token);
```

Cancellation không cưỡng bức kill thread. Nếu `ExecuteAsync` không truyền token xuống dependency hoặc code CPU loop không kiểm tra token, work vẫn chạy.

## 4. Practical implementation

Một ASP.NET Core endpoint có explicit timeout:

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    OrderService service,
    HttpContext http,
    IHostApplicationLifetime lifetime) =>
{
    using var timeoutCts = new CancellationTokenSource(
        TimeSpan.FromSeconds(5));

    using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(
        http.RequestAborted,
        lifetime.ApplicationStopping,
        timeoutCts.Token);

    try
    {
        var order = await service.GetAsync(id, linkedCts.Token);
        return order is null ? Results.NotFound() : Results.Ok(order);
    }
    catch (OperationCanceledException)
        when (timeoutCts.IsCancellationRequested &&
              !http.RequestAborted.IsCancellationRequested)
    {
        return Results.StatusCode(StatusCodes.Status504GatewayTimeout);
    }
});
```

Service tiếp tục propagate token:

```csharp
public Task<Order?> GetAsync(Guid id, CancellationToken ct)
    => _db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);
```

## 5. Real production scenario

Một API gọi SQL rồi gọi pricing service. Pricing service đôi lúc mất 30 giây mới timeout ở TCP layer. Client mobile đã bỏ request sau 2 giây nhưng backend vẫn giữ connection và continuation thêm hàng chục giây.

Khi traffic tăng, hàng nghìn “orphan operations” tích tụ, chiếm connection pool và memory.

Propagate linked cancellation giúp work kết thúc gần với lifecycle thật của request và application.

## 6. Failure scenario & troubleshooting

**Symptom** → request đã timeout ở gateway nhưng database/external API vẫn tiếp tục chạy.

**Evidence** → trace cho thấy client span kết thúc nhưng downstream span còn sống; SQL active requests tồn tại sau HTTP disconnect.

**Hypothesis** → token bị mất ở một layer hoặc dependency call dùng `CancellationToken.None`.

**Diagnosis** → theo call chain và kiểm tra từng async API có nhận đúng token không; phân biệt `TaskCanceledException` do timeout với client cancellation bằng source state.

**Fix** → propagate token end-to-end; đặt timeout tại đúng boundary; không catch rồi nuốt `OperationCanceledException` như generic error.

**Verification** → disconnect client/load test và xác nhận downstream work giảm ngay sau cancellation.

## 7. Common mistakes

- Dùng một global timeout cho mọi operation dù latency budget khác nhau.
- Catch `Exception` rồi log cancellation như lỗi Production.
- Tạo `CancellationTokenSource` nhưng quên dispose.
- Propagate token tới operation đã commit side effect rồi giả định cancellation rollback được side effect.
- Dùng cancellation thay cho idempotency.

## 8. Alternatives

`HttpClient.Timeout` có thể giới hạn HTTP call cụ thể nhưng không biểu diễn toàn bộ operation budget. Polly/resilience timeout phù hợp khi timeout là policy của dependency. Database command timeout giải quyết SQL command duration nhưng không thay request cancellation.

## 9. Trade-offs

### Advantages

- Giảm orphan work và resource waste.
- Shutdown/redeploy predictable hơn.
- Một operation có latency budget rõ.

### Costs / Risks

- Cancellation path phải được test.
- Side effect giữa chừng cần idempotency/recovery.
- Quá nhiều nested timeout gây khó phân biệt root cause.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cancellation là tín hiệu hợp tác, không phải kill thread.

### Middle

Propagate token xuyên EF Core, HTTP, file I/O và background work.

### Senior

Phân biệt client abort, timeout, shutdown và partial side effect; thiết kế latency budget theo dependency chain.

### Technical Lead / Architect

Xác định timeout budget ở từng boundary và quy ước telemetry để biết operation bị hủy vì nguyên nhân nào.

## 11. Key takeaway

- Cancellation reason khác nhau cần semantics khác nhau.
- Linked token giúp gom lifecycle nhưng không thay idempotency.
- Token chỉ có tác dụng khi được propagate và observed end-to-end.

# 2. ASP.NET Core `IHttpClientFactory`: handler pooling, DNS refresh và socket exhaustion trong long-running services

## 1. What is it?

`IHttpClientFactory` quản lý việc tạo `HttpClient` trong khi tái sử dụng underlying `HttpMessageHandler` theo lifecycle có kiểm soát.

Điểm quan trọng: vấn đề không phải “`HttpClient` có `IDisposable` nên phải `new`/dispose mỗi request”. `HttpClient` đại diện client abstraction; connection pooling nằm sâu hơn trong `SocketsHttpHandler`.

Mental model:

```text
HttpClient instance
      |
      v
pooled HttpMessageHandler
      |
      v
connection pool -> sockets -> DNS-resolved endpoints
```

## 2. Why does it exist?

Hai anti-pattern phổ biến:

1. Tạo/dispose `HttpClient` liên tục → nhiều TCP connections rơi vào `TIME_WAIT`, socket churn.
2. Giữ một handler sống vô hạn → DNS thay đổi nhưng connection pool tiếp tục dùng endpoint cũ quá lâu.

Factory tồn tại để cân bằng connection reuse với handler/DNS lifecycle, đồng thời centralize configuration, logging và resilience.

## 3. How does it work?

Factory tạo `HttpClient` mới nhẹ, nhưng handler có thể được pool/reuse. Sau handler lifetime, handler cũ được retire; connection mới có cơ hội resolve DNS lại.

```text
Client A --\
Client B ----> Handler #1 -> connection pool
Client C --/

lifetime expires
new clients -> Handler #2 -> fresh DNS/connection pool
```

DNS behavior còn phụ thuộc `PooledConnectionLifetime` và platform networking. Không nên xem handler lifetime như magic fix cho mọi service-discovery issue.

## 4. Practical implementation

Typed client:

```csharp
builder.Services.AddHttpClient<ProductApiClient>(client =>
{
    client.BaseAddress = new Uri(configuration["ProductApi:BaseUrl"]!);
    client.Timeout = TimeSpan.FromSeconds(10);
})
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(5),
    MaxConnectionsPerServer = 100
});
```

Consumer:

```csharp
public sealed class ProductApiClient(HttpClient httpClient)
{
    public async Task<ProductDto?> GetAsync(
        Guid id,
        CancellationToken ct)
    {
        using var response = await httpClient.GetAsync(
            $"/products/{id}", ct);

        if (response.StatusCode == HttpStatusCode.NotFound)
            return null;

        response.EnsureSuccessStatusCode();
        return await response.Content
            .ReadFromJsonAsync<ProductDto>(cancellationToken: ct);
    }
}
```

## 5. Real production scenario

Một ASP.NET Core service gọi Kubernetes service/traffic manager. Backend IP thay đổi sau deployment. Application giữ connection pool cực lâu và một phần traffic tiếp tục đi tới endpoint cũ đang drain.

Ở hệ thống khác, developer tạo `new HttpClient()` cho từng request; dưới load test xuất hiện socket errors dù CPU/DB vẫn khỏe.

Cả hai đều là lifecycle problem nhưng nguyên nhân đối nghịch.

## 6. Failure scenario & troubleshooting

**Symptom** → intermittent connection refused sau downstream deploy, hoặc outbound socket exhaustion dưới load.

**Evidence** → nhiều `TIME_WAIT`, handler/client creation per request, DNS resolves khác với active remote connections.

**Hypothesis** → handler/connection lifecycle sai.

**Diagnosis** → inspect DI registration, `netstat`/platform network metrics, outbound dependency traces, DNS records và connection age.

**Fix** → dùng factory/long-lived handler strategy, configure connection lifetime theo infrastructure, giới hạn concurrency nếu downstream có capacity limit.

**Verification** → rolling downstream deployment + sustained load test.

## 7. Common mistakes

- Dispose `HttpClient` mỗi request vì thấy `IDisposable`.
- Dùng singleton typed client nhưng capture scoped dependency sai cách.
- Retry mọi `POST` mà không có idempotency.
- Set timeout 100 giây mặc định cho dependency có SLO 2 giây.
- Nghĩ `IHttpClientFactory` tự tạo Circuit Breaker/Retry đúng cho business semantics.

## 8. Alternatives

Một static/long-lived `HttpClient` với `SocketsHttpHandler.PooledConnectionLifetime` có thể hoàn toàn tốt trong library/service đơn giản. Factory hữu ích khi cần nhiều named/typed clients, central configuration và DI integration.

## 9. Trade-offs

### Advantages

- Quản lý handler lifecycle tốt hơn.
- Centralized telemetry/configuration.
- Typed clients làm dependency contract rõ.

### Costs / Risks

- Misconfiguration vẫn gây stale DNS hoặc overload.
- Resilience policy chồng chéo có thể tạo retry storm.
- Nhiều named clients làm config khó quản lý nếu không có ownership.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `HttpClient` reuse liên quan connection pooling.

### Middle

Dùng typed clients, cancellation, timeout và status handling đúng.

### Senior

Chẩn đoán DNS/connection pool/socket behavior và retry amplification.

### Technical Lead / Architect

Định nghĩa dependency-specific budgets, connection policy và ownership thay vì một global HTTP policy cho mọi service.

## 11. Key takeaway

- `HttpClient` lifecycle và socket lifecycle không phải một thứ.
- Reuse connection là tốt, nhưng connection sống quá lâu cũng có operational cost.
- Factory giúp quản lý lifecycle; correctness vẫn phụ thuộc timeout/retry/idempotency design.

# 3. EF Core Global Query Filters cho multi-tenant data: tiện lợi nhưng có thể biến thành data-leak boundary nếu tenant context sai

## 1. What is it?

Global Query Filter là predicate EF Core tự động áp vào query của một entity type. Với multi-tenant application, filter thường thêm `TenantId == currentTenantId` để developer không phải nhớ điều kiện ở từng query.

```text
DbSet<Order>.Where(...)
        |
        v
implicit TenantId filter
        |
        v
SQL WHERE TenantId = @tenant
```

## 2. Why does it exist?

Nếu mọi repository/service phải nhớ `.Where(x => x.TenantId == tenantId)`, chỉ một query quên filter có thể leak dữ liệu tenant khác.

Global filter giảm repeated boilerplate và tạo default isolation ở ORM layer.

Nhưng đây **không phải authorization boundary tuyệt đối**. Raw SQL, `IgnoreQueryFilters`, admin query, background work hoặc tenant-context bug vẫn có thể bypass.

## 3. How does it work?

Configuration:

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Order>()
        .HasQueryFilter(x => x.TenantId == _tenantId);
}
```

Mỗi query được EF compose với predicate này. Context lifetime vì thế rất quan trọng: `_tenantId` phải đúng cho scope hiện tại.

Nếu `DbContext` pooling được dùng, mutable tenant state phải được reset/managed cực kỳ cẩn thận; nếu không tenant A context state có thể bị reuse cho tenant B.

## 4. Practical implementation

Tenant provider scoped:

```csharp
public interface ITenantContext
{
    Guid TenantId { get; }
}

public sealed class AppDbContext(
    DbContextOptions<AppDbContext> options,
    ITenantContext tenant) : DbContext(options)
{
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Order>()
            .HasQueryFilter(x => x.TenantId == tenant.TenantId);
    }
}
```

Write path vẫn phải set/validate tenant explicitly:

```csharp
var order = new Order
{
    Id = Guid.NewGuid(),
    TenantId = tenant.TenantId,
    Status = OrderStatus.Pending
};
```

Database constraint/RLS có thể bổ sung defense in depth.

## 5. Real production scenario

SaaS CRM có hàng trăm tenants. Một admin export job chạy ngoài HTTP request, `TenantContext` không được khởi tạo đúng và mặc định `Guid.Empty`. Developer thêm `IgnoreQueryFilters()` để “fix export”, rồi query vô tình lấy toàn bộ customers và gửi file cho một tenant.

Vấn đề không phải EF filter “không tốt”; vấn đề là tenant ownership và privileged bypass không được thiết kế rõ.

## 6. Failure scenario & troubleshooting

**Symptom** → user thấy record tenant khác hoặc background job trả zero/all rows bất thường.

**Evidence** → generated SQL thiếu/sai `TenantId`, code path dùng `IgnoreQueryFilters`, tenant context không có correlation với request/job.

**Hypothesis** → tenant scope bị mất hoặc bypass filter quá rộng.

**Diagnosis** → log tenant ID như structured context (không high-cardinality metric label), inspect generated SQL, audit privileged query paths.

**Fix** → explicit tenant requirement, privileged repository riêng, integration tests nhiều tenants, DB-level guard khi risk cao.

**Verification** → negative tests chứng minh tenant A không thể đọc/write tenant B qua mọi endpoint/job.

## 7. Common mistakes

- Coi global filter là authorization duy nhất.
- Default tenant về `Guid.Empty` thay vì fail fast.
- Dùng `IgnoreQueryFilters()` trong generic repository.
- Quên write isolation: client gửi `TenantId` tùy ý.
- Kết hợp `DbContext` pooling với mutable tenant state không kiểm soát.

## 8. Alternatives

Database Row-Level Security có boundary gần data hơn nhưng tăng operational/schema complexity. Separate database per tenant cho isolation mạnh hơn nhưng migration/cost lớn hơn. Separate schema là lựa chọn trung gian tùy platform.

## 9. Trade-offs

### Advantages

- Default query isolation dễ duy trì.
- Giảm boilerplate và lỗi quên predicate.
- Tích hợp tự nhiên với LINQ.

### Costs / Risks

- Filter implicit làm query behavior khó thấy.
- Bypass có thể nguy hiểm.
- Tenant context/lifetime trở thành critical security state.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu tenant isolation không chỉ là thêm một cột `TenantId`.

### Middle

Implement query filter và test multi-tenant read/write.

### Senior

Đánh giá bypass, context lifetime, background jobs, raw SQL và DB defense-in-depth.

### Technical Lead / Architect

Chọn isolation model theo regulatory/risk/cost requirement và xác định privileged cross-tenant access boundary rõ ràng.

## 11. Key takeaway

- Global filter là safe default, không phải security silver bullet.
- Tenant context phải fail closed và có lifecycle rõ.
- Multi-tenant correctness cần negative tests, không chỉ happy-path tests.

# 4. SQL window functions (`ROW_NUMBER`, `LAG`, `SUM OVER`): giải quyết ranking và running totals theo set-based processing thay vì loop trong C#

## 1. What is it?

Window function tính toán trên một “window” của rows nhưng vẫn giữ từng row trong result, khác `GROUP BY` vốn collapse nhiều rows thành một row tổng hợp.

Ví dụ:

```sql
ROW_NUMBER() OVER (
    PARTITION BY CustomerId
    ORDER BY CreatedAt DESC)
```

cho phép đánh số orders trong từng customer mà không mất row detail.

## 2. Why does it exist?

Nhiều bài toán reporting/query cần:

- top N per group;
- running total;
- previous/next value;
- rank;
- rolling average.

Cách naive thường query toàn bộ rows rồi group/sort/loop trong C#, gây network payload lớn và mất lợi thế set-based engine.

## 3. How does it work?

Window có ba ý chính:

```text
PARTITION BY -> chia logical groups
ORDER BY     -> thứ tự trong group
frame        -> phạm vi rows tham gia phép tính
```

Ví dụ running total:

```sql
SELECT
    AccountId,
    TransactionDate,
    Amount,
    SUM(Amount) OVER (
        PARTITION BY AccountId
        ORDER BY TransactionDate, Id
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS RunningBalance
FROM Transactions;
```

## 4. Practical implementation

Lấy order mới nhất mỗi customer:

```sql
WITH RankedOrders AS
(
    SELECT
        Id,
        CustomerId,
        CreatedAt,
        Total,
        ROW_NUMBER() OVER (
            PARTITION BY CustomerId
            ORDER BY CreatedAt DESC, Id DESC) AS rn
    FROM Orders
)
SELECT Id, CustomerId, CreatedAt, Total
FROM RankedOrders
WHERE rn = 1;
```

Dùng `LAG` phát hiện status transition time:

```sql
SELECT
    OrderId,
    ChangedAt,
    Status,
    LAG(Status) OVER (
        PARTITION BY OrderId
        ORDER BY ChangedAt) AS PreviousStatus
FROM OrderHistory;
```

## 5. Real production scenario

Dashboard cần “latest approval per employee” cho 200.000 employees. Implementation cũ load approvals rồi group trong application, tạo hàng trăm MB payload.

Window function đẩy ranking vào database và chỉ trả row cần thiết, giảm round-trip bytes và application allocation.

## 6. Failure scenario & troubleshooting

**Symptom** → query window function vẫn chậm và spill tempdb/disk.

**Evidence** → execution plan có large sort, memory grant/spill, logical reads cao.

**Hypothesis** → partition/order chưa được index hỗ trợ hoặc dataset quá lớn.

**Diagnosis** → actual plan, sort operator, cardinality, index order.

**Fix** → index theo filter + partition/order pattern khi justified; giảm input rows trước window; tránh chọn columns không cần.

**Verification** → compare logical reads, sort spill, elapsed time và returned bytes.

## 7. Common mistakes

- Quên deterministic tie-breaker trong `ORDER BY`.
- Dùng `RANK`, `DENSE_RANK`, `ROW_NUMBER` như nhau.
- Window trên toàn dataset rồi mới filter dù filter có thể push sớm.
- Chuyển mọi reporting logic vào một query khổng lồ khó vận hành.
- Thêm index chỉ vì có sort mà không đo write/storage cost.

## 8. Alternatives

`GROUP BY` tốt khi chỉ cần aggregate collapsed result. Application-side aggregation hợp lý với dataset nhỏ hoặc business algorithm khó biểu diễn trong SQL. Materialized view/reporting store phù hợp cho expensive analytics lặp lại.

## 9. Trade-offs

### Advantages

- Set-based, giảm data transfer.
- Biểu diễn ranking/running calculations rõ.
- Tránh N+1/application loops.

### Costs / Risks

- Sort/memory cost có thể lớn.
- Query phức tạp hơn cho team ít SQL experience.
- Heavy analytics có thể ảnh hưởng OLTP database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt window function với `GROUP BY`.

### Middle

Dùng `ROW_NUMBER`, `LAG`, `SUM OVER` đúng partition/order.

### Senior

Đọc execution plan, memory grants/spills và index trade-offs.

### Technical Lead / Architect

Quyết định reporting chạy trên OLTP, replica hay dedicated analytical store dựa trên workload và SLO.

## 11. Key takeaway

- Window functions giữ row detail trong khi tính theo group/window.
- Deterministic ordering là correctness requirement.
- SQL mạnh hơn C# loop khi bài toán thực chất là set-based data processing.

# 5. Elasticsearch Index Lifecycle Management: rollover, retention và shard growth trước khi cluster search chậm vì index phình vô hạn

## 1. What is it?

Index Lifecycle Management (ILM) quản lý vòng đời time-oriented Elasticsearch indices theo policy: rollover index mới, chuyển phase, giảm cost hoặc delete dữ liệu cũ.

Mental model:

```text
write alias
   -> hot index-000001
      size/age threshold
   -> rollover index-000002
   -> old index warm/cold/delete theo policy
```

## 2. Why does it exist?

Log/audit/search event data thường tăng liên tục. Một index duy nhất phình mãi dẫn đến:

- shard rất lớn;
- recovery/rebalancing lâu;
- segment merge cost tăng;
- backup/snapshot và maintenance khó;
- retention thủ công dễ sai.

Ngược lại, tạo index quá nhỏ mỗi giờ/ngày cũng tạo shard explosion.

## 3. How does it work?

Rollover dựa trên condition như age, primary shard size hoặc document count. Alias/data stream giữ write target ổn định trong khi physical index thay đổi.

Lifecycle có thể gồm:

```text
hot -> warm -> cold/frozen -> delete
```

Tùy deployment/version/license, tier capabilities khác nhau; engineering principle là data temperature và retention phải map vào business/search requirement.

## 4. Practical implementation

Conceptual ILM policy:

```json
PUT _ilm/policy/audit-policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": {
            "max_primary_shard_size": "40gb",
            "max_age": "7d"
          }
        }
      },
      "delete": {
        "min_age": "90d",
        "actions": { "delete": {} }
      }
    }
  }
}
```

Application nên write qua stable alias/data stream, không hardcode physical index suffix.

## 5. Real production scenario

Audit platform ingest 100 GB/day. Team tạo một index mỗi tháng. Đến cuối tháng shard đạt hàng trăm GB, node restart khiến shard recovery mất nhiều giờ và search latency spike.

Rollover theo shard size giúp physical units predictable hơn thay vì calendar-driven growth bất thường.

## 6. Failure scenario & troubleshooting

**Symptom** → search p95 tăng, cluster recovery lâu, unassigned shards sau node failure.

**Evidence** → shard size distribution lệch mạnh, shard count quá cao/thấp, ILM explain cho thấy step failed.

**Hypothesis** → lifecycle/shard strategy không phù hợp ingest volume.

**Diagnosis** → inspect `_cat/indices`, shard sizes, ILM status, node disk/watermarks, retention policy.

**Fix** → tune rollover threshold, shard count/template, repair alias/policy, reindex oversized historical data khi cần.

**Verification** → theo dõi shard size, recovery time, indexing/search latency qua nhiều rollover cycles.

## 7. Common mistakes

- Rollover chỉ theo ngày dù ingest volume biến động 100×.
- Tạo quá nhiều primary shards “để scale”.
- Hardcode index name trong application.
- Delete documents hàng loạt thay vì drop old time index khi retention cho phép.
- Dùng Elasticsearch làm source of truth duy nhất cho transactional data.

## 8. Alternatives

Simple fixed indices đủ cho dataset nhỏ. Data streams phù hợp time-series/log use case và tích hợp lifecycle tốt. Primary database + archive storage có thể tốt hơn nếu historical search hiếm.

## 9. Trade-offs

### Advantages

- Predictable shard size và retention.
- Recovery/operations dễ hơn.
- Có thể hạ storage cost theo data age.

### Costs / Risks

- Policy/template/alias complexity.
- Sai lifecycle có thể delete data sớm.
- Tiering tăng dependency vào cluster topology.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index/shard là physical operational unit, không chỉ logical search collection.

### Middle

Biết alias/data stream, rollover và retention basics.

### Senior

Capacity-plan shard size/count, recovery và segment behavior.

### Technical Lead / Architect

Định nghĩa retention/SLA/data-temperature policy và xác định dữ liệu nào thực sự cần nằm trong Elasticsearch.

## 11. Key takeaway

- Index không nên tăng vô hạn.
- Rollover theo size/age phải phản ánh ingest thực tế.
- Shard strategy là reliability/cost decision, không chỉ search configuration.

# 6. Strangler Fig modernization: di chuyển `.NET Framework` sang modern .NET từng lát thay vì rewrite toàn hệ thống

## 1. What is it?

Strangler Fig là modernization strategy: đặt boundary trước hệ thống legacy, rồi dần chuyển từng capability sang implementation mới trong khi phần cũ vẫn chạy.

```text
Client
  |
  v
Routing / Facade
  |-----------------> Legacy .NET Framework
  |-----------------> Modern .NET module/service
```

Mục tiêu là giảm “big-bang rewrite” risk bằng incremental replacement.

## 2. Why does it exist?

Rewrite toàn bộ enterprise system thường thất bại vì:

- business rules ẩn trong legacy code;
- integrations/document formats đặc biệt;
- migration kéo dài nhưng business vẫn thay đổi;
- test coverage không đủ để chứng minh parity;
- rollout/rollback khó.

Incremental modernization cho phép học từ production và tạo value từng phần.

## 3. How does it work?

Chọn seam/capability có boundary rõ:

```text
Legacy UI/API
 -> façade/router
 -> old implementation
```

Sau đó:

1. Characterize behavior bằng tests/telemetry.
2. Tạo contract ổn định.
3. Implement capability mới.
4. Route subset traffic/workflow sang mới.
5. Compare/monitor.
6. Remove legacy path khi đủ confidence.

Data ownership thường là phần khó nhất. Nếu code mới vẫn trực tiếp mutate legacy DB tables tùy ý, architectural strangling chưa thật sự xảy ra.

## 4. Practical implementation

ASP.NET Core gateway/facade có thể route capability:

```csharp
app.Map("/api/customers", customerApp);

app.MapFallback(async context =>
{
    await legacyProxy.ForwardAsync(context);
});
```

Ở mức process, có thể dùng reverse proxy. Ở mức module, có thể extract library/domain trước khi extract deployment.

Contract test giữa old/new giúp kiểm tra compatibility:

```csharp
[Theory]
[MemberData(nameof(CustomerCases))]
public async Task New_endpoint_matches_required_legacy_behavior(CustomerCase test)
{
    var oldResult = await _legacy.ExecuteAsync(test);
    var newResult = await _modern.ExecuteAsync(test);

    AssertEquivalentBusinessResult(oldResult, newResult);
}
```

## 5. Real production scenario

Một .NET Framework MVC application quản lý employee, timesheet, approval và payroll integration. Team muốn lên .NET 8/10.

Thay vì rewrite 18 tháng, họ bắt đầu với read-only employee profile API, sau đó approval workflow, cuối cùng mới xử lý phần có transaction/integration phức tạp.

Legacy vẫn deploy được trong quá trình migration và rollback theo capability.

## 6. Failure scenario & troubleshooting

**Symptom** → modernization kéo dài nhưng cả old/new đều phải sửa cho mọi feature; coupling không giảm.

**Evidence** → shared database writes, shared models, feature logic duplicated hai bên.

**Hypothesis** → team đang “copy code” chứ chưa tạo boundary.

**Diagnosis** → dependency/data ownership map, change-impact analysis cho một feature.

**Fix** → chọn vertical capability, anti-corruption layer, explicit ownership và retirement criteria.

**Verification** → capability mới có thể evolve/deploy mà ít sửa legacy path; telemetry chứng minh traffic đã chuyển.

## 7. Common mistakes

- Rewrite UI trước nhưng backend/domain coupling giữ nguyên.
- Chia theo technical layer thay vì business capability.
- Giữ shared DB write forever.
- Không có decommission milestone nên hai hệ thống sống song song vĩnh viễn.
- Coi modern .NET migration là đổi target framework đơn thuần.

## 8. Alternatives

In-place upgrade phù hợp application nhỏ, dependency tương thích tốt. Big-bang rewrite chỉ hợp khi scope nhỏ hoặc old system thật sự disposable. Modularize monolith trước khi service extraction có thể giảm risk đáng kể.

## 9. Trade-offs

### Advantages

- Incremental risk và rollback tốt hơn.
- Business tiếp tục giao feature.
- Boundary được kiểm chứng dần.

### Costs / Risks

- Temporary duplicate infrastructure/code.
- Routing/data sync phức tạp.
- Migration có thể kéo dài nếu không có ownership/decommission discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu modernization không đồng nghĩa rewrite.

### Middle

Viết characterization tests, adapters và compatibility code.

### Senior

Xác định seams, data coupling, rollout/rollback và hidden behavior.

### Technical Lead / Architect

Chọn migration sequence theo business risk/value, đặt retirement criteria và ngăn temporary bridge trở thành permanent architecture.

## 11. Key takeaway

- Modernization tốt thường là migration program, không phải rewrite project.
- Business/data boundary quyết định khả năng strangling.
- Mỗi bước phải có rollback và decommission path.

# 7. Azure Service Bus Sessions: giữ ordering theo business key mà không serialize toàn bộ queue

## 1. What is it?

Service Bus Sessions nhóm messages có cùng `SessionId` thành một ordered stream. Một session receiver giữ exclusive lock cho một session tại một thời điểm, giúp processing tuần tự **trong session**, trong khi nhiều sessions vẫn có thể xử lý song song.

Mental model:

```text
Order A: A1 -> A2 -> A3   (ordered)
Order B: B1 -> B2         (ordered)
Order C: C1 -> C2 -> C3   (ordered)

A/B/C có thể chạy concurrently.
```

## 2. Why does it exist?

Queue bình thường không đảm bảo business-level ordering trong mọi failure/retry/concurrent consumer situation.

Nếu chỉ cần order events của cùng aggregate/customer/workflow, serializing **toàn bộ queue** làm throughput giảm không cần thiết.

Sessions cung cấp ordering partition theo business key.

## 3. How does it work?

Producer set:

```csharp
new ServiceBusMessage(body)
{
    SessionId = orderId.ToString(),
    MessageId = eventId.ToString()
};
```

Consumer nhận lock cho session. Messages trong session được nhận theo sequence. Khi consumer crash/lock expire, session có thể được consumer khác nhận tiếp.

Ordering không loại bỏ duplicate delivery. At-least-once semantics và idempotency vẫn cần.

## 4. Practical implementation

Producer:

```csharp
var message = new ServiceBusMessage(
    BinaryData.FromObjectAsJson(evt))
{
    SessionId = evt.OrderId.ToString(),
    MessageId = evt.EventId.ToString()
};

await sender.SendMessageAsync(message, ct);
```

Consumer logic nên kiểm tra expected aggregate version:

```csharp
if (message.Version <= state.LastProcessedVersion)
{
    // duplicate/old message
    return;
}

if (message.Version != state.LastProcessedVersion + 1)
{
    throw new OutOfOrderMessageException();
}
```

Session ordering là transport property; business version vẫn hữu ích để detect gap/duplicate.

## 5. Real production scenario

Order workflow phát `OrderCreated`, `PaymentConfirmed`, `OrderCancelled`. Nếu các message của cùng order được xử lý concurrent, `OrderCancelled` có thể chạy trước `PaymentConfirmed` do retry/network timing.

Đặt `SessionId = OrderId` giữ sequence per order nhưng vẫn cho hàng nghìn orders xử lý parallel.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog tăng dù tổng CPU thấp; một số sessions xử lý rất lâu.

**Evidence** → hot session có hàng nghìn messages, session lock renewals, uneven processing distribution.

**Hypothesis** → session key quá coarse hoặc một business entity tạo workload cực lớn.

**Diagnosis** → metrics theo session workload (không export session ID thành unbounded metric label), processing duration, dead-letter reason.

**Fix** → chọn partition key hợp lý, giảm work per message, tách aggregate/workflow nếu business cho phép.

**Verification** → load test skewed sessions và đo throughput/fairness.

## 7. Common mistakes

- Dùng một `SessionId` cho toàn queue.
- Nghĩ sessions cho exactly-once processing.
- Không idempotent vì “đã ordered”.
- Session handler gọi external API chậm làm block mọi message sau trong cùng session.
- Chọn customer ID khi một enterprise customer có 80% traffic, tạo hot session.

## 8. Alternatives

Không dùng sessions nếu events độc lập và ordering không phải invariant. Partitioned/event-stream platforms phù hợp workload throughput rất lớn và ordering by partition. Database workflow/row lock có thể đơn giản hơn nếu tất cả state vẫn trong một service.

## 9. Trade-offs

### Advantages

- Ordering theo business key.
- Parallelism giữa sessions.
- Session state có thể hỗ trợ workflow scenarios.

### Costs / Risks

- Hot session giới hạn throughput.
- Consumer model phức tạp hơn.
- Ordering làm head-of-line blocking trong session.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ordering toàn queue khác ordering per business key.

### Middle

Set `SessionId`, configure session consumer và xử lý duplicate.

### Senior

Thiết kế partition key, lock/retry behavior và detect message gaps.

### Technical Lead / Architect

Quyết định ordering có thật sự là business invariant hay có thể thiết kế events commutative/idempotent để giảm coupling.

## 11. Key takeaway

- Sessions serialize theo key, không serialize toàn hệ thống.
- Ordered delivery không có nghĩa exactly-once.
- Chọn session key là capacity + business consistency decision.

# 8. High-cardinality telemetry: vì sao `userId`/`requestId` trong metrics label có thể làm observability platform đắt và chậm

## 1. What is it?

Cardinality là số lượng combinations riêng biệt của dimensions/labels trong metrics hoặc indexed telemetry.

Metric tưởng đơn giản:

```text
http_requests_total{endpoint, status, userId}
```

Nếu có 1.000 endpoints/status combinations và 2 triệu users, số time series tiềm năng có thể bùng nổ.

Metrics mạnh khi dimensions có cardinality bounded; trace/log phù hợp hơn cho identifiers gần như unique.

## 2. Why does it exist?

Observability backend phải index/store/query mỗi unique time series/dimension combination. High cardinality làm:

- memory/index tăng;
- ingestion cost tăng;
- dashboard query chậm;
- retention đắt;
- alerting unstable.

Developer thường thêm `requestId`, `email`, `orderId` vì “càng nhiều context càng tốt” nhưng không phân biệt telemetry type.

## 3. How does it work?

Một design tốt phân vai:

```text
Metrics: endpoint, status class, region, dependency
Traces: traceId + span attributes + sampled request context
Logs: structured event with identifiers when needed
```

Correlation dùng trace ID để drill-down từ aggregate metric sang representative traces/logs.

Không cần biến mọi identifier thành metric label.

## 4. Practical implementation

OpenTelemetry metric:

```csharp
_requests.Add(
    1,
    new KeyValuePair<string, object?>("route", routePattern),
    new KeyValuePair<string, object?>("status_code", statusCode));
```

Không:

```csharp
_requests.Add(
    1,
    new("user_id", userId),
    new("request_id", requestId));
```

Identifier có thể đặt ở trace:

```csharp
Activity.Current?.SetTag("order.id", orderId);
```

Nhưng vẫn phải cân nhắc PII/security và exporter/index cost.

## 5. Real production scenario

Team thêm `customerId` label vào latency histogram để “xem latency từng customer”. Sau vài tuần observability bill tăng nhiều lần, query dashboard timeout vì hàng triệu series.

Nhu cầu thật sự chỉ là phát hiện top enterprise customers bị chậm. Giải pháp có thể dùng bounded customer tier metric + trace/log query theo customer ID khi incident.

## 6. Failure scenario & troubleshooting

**Symptom** → telemetry ingestion cost tăng, metrics backend memory/query latency tăng mạnh sau release.

**Evidence** → active series count/dimension cardinality tăng; top label values gần unique.

**Hypothesis** → high-cardinality attribute mới.

**Diagnosis** → cardinality report, schema diff telemetry trước/sau deploy.

**Fix** → remove/bucket dimension, use route template thay raw URL, đưa unique IDs sang traces/logs có sampling/retention phù hợp.

**Verification** → active series giảm và dashboards/alerts vẫn trả đúng signal.

## 7. Common mistakes

- Label metric bằng `requestId`, `userId`, raw URL.
- Dùng exception message làm dimension.
- URL `/orders/123` thay route `/orders/{id}`.
- Tin rằng sampling traces sẽ tự giảm metrics cardinality.
- Ghi PII vào telemetry vì thuận tiện debug.

## 8. Alternatives

Logs/traces cho point investigation. Exemplars có thể link metric histogram với trace representative. Pre-aggregated business dimensions phù hợp khi thực sự cần segment analysis.

## 9. Trade-offs

### Advantages

Low-cardinality metrics rất rẻ và mạnh cho alert/SLO aggregation.

### Costs / Risks

Ít dimensions hơn nghĩa là phải drill-down qua traces/logs để tìm entity cụ thể. Quá ít context cũng làm investigation khó, nên cần telemetry architecture cân bằng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu metrics khác logs/traces về data model.

### Middle

Dùng bounded labels và route templates.

### Senior

Theo dõi series cardinality, cost và correlation strategy.

### Technical Lead / Architect

Thiết kế telemetry schema/budget toàn platform, including PII policy và retention theo signal value.

## 11. Key takeaway

- Unique identifier gần như không nên là metric label.
- Metrics để aggregate; traces/logs để drill down.
- Telemetry schema là production architecture, không phải debug detail tùy ý.

# 9. React stale closures và asynchronous state: callback chạy đúng JavaScript nhưng đọc state cũ sau render

## 1. What is it?

Trong React function component, mỗi render tạo một lexical scope mới. Callback async/timer/event handler có thể capture state của **render lúc callback được tạo**, không tự động đọc state mới nhất ở tương lai.

Mental model:

```text
Render #1: count = 0 -> callback captures 0
Render #2: count = 5
callback from #1 fires later -> still sees 0
```

Đây là JavaScript closure semantics kết hợp React render model, không phải “React randomly lost state”.

## 2. Why does it exist?

Function component là function execution snapshot. Closure cho phép callback giữ variables từ scope đó. Điều này làm code predictable, nhưng async timing có thể khiến snapshot trở nên stale.

Senior full-stack engineer cần hiểu vì frontend bug kiểu này thường bị nhầm với API race condition hoặc backend inconsistency.

## 3. How does it work?

Ví dụ lỗi:

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  const incrementLater = () => {
    setTimeout(() => {
      setCount(count + 1);
    }, 1000);
  };

  // ...
}
```

Nếu user thay đổi `count` nhiều lần trước timer chạy, callback vẫn dùng `count` tại render cũ.

Functional update đọc previous state theo update queue:

```tsx
setCount(current => current + 1);
```

## 4. Practical implementation

Với async search, stale closure/race còn liên quan request lifecycle:

```tsx
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(query)}`,
      { signal: controller.signal }
    );

    const data = await response.json();
    setResults(data);
  }

  load().catch(error => {
    if (error.name !== "AbortError") {
      setError(error);
    }
  });

  return () => controller.abort();
}, [query]);
```

Effect cleanup đảm bảo request của render cũ bị hủy khi dependency thay đổi.

## 5. Real production scenario

Search box gọi API sau mỗi query change. User gõ `car`, rồi nhanh chóng `cargo`.

Request `cargo` trả trước và UI hiển thị đúng. Sau đó request `car` chậm hơn trả về và ghi đè state, khiến UI hiển thị kết quả cũ.

Backend hoàn toàn đúng; bug là frontend request/state lifecycle.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng quay về dữ liệu cũ hoặc click nhiều lần tăng counter sai.

**Evidence** → browser Network cho thấy response order khác request order; React DevTools/render logs cho thấy callback thuộc render cũ.

**Hypothesis** → stale closure hoặc async race.

**Diagnosis** → xác định callback capture biến nào, dependency array, request cancellation/versioning.

**Fix** → functional state updates, correct dependencies, cleanup/AbortController, request sequence guard khi cần.

**Verification** → throttle network trong DevTools và reproduce rapid input/navigation.

## 7. Common mistakes

- Bỏ dependency khỏi `useEffect` để “ngăn chạy nhiều lần”.
- Thêm mọi object/function vào dependency rồi tạo render loop.
- Dùng mutable global variable để né closure.
- Backend retry/caching để sửa frontend race.
- Không abort request khi component unmount/query đổi.

## 8. Alternatives

React Query/TanStack Query hoặc data-fetching framework có thể quản lý cache, stale state và request lifecycle tốt hơn, nhưng vẫn phải hiểu query keys và cancellation semantics. Simple local `useEffect` đủ cho use case nhỏ.

## 9. Trade-offs

### Advantages

Closure/render snapshot làm component reasoning deterministic khi hiểu đúng model.

### Costs / Risks

Async callback dễ giữ stale state. Abstraction data-fetching thêm dependency nhưng giảm repetitive race/cache handling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mỗi render có snapshot state riêng.

### Middle

Dùng functional update, dependency array và cleanup đúng.

### Senior

Phân biệt stale closure, response race, server stale cache và optimistic UI conflict.

### Technical Lead / Architect

Chuẩn hóa frontend data-fetching/state strategy để tránh mỗi component tự phát minh request lifecycle.

## 11. Key takeaway

- Closure capture state của render cụ thể.
- Async response order không đảm bảo giống request order.
- Cancellation/state ownership phải được thiết kế cả ở frontend, không chỉ backend.

# 10. SSRF trong third-party URL integration: server-side HTTP client không được phép trở thành proxy tới internal network

## 1. What is it?

SSRF (Server-Side Request Forgery) xảy ra khi attacker kiểm soát hoặc ảnh hưởng URL mà server sẽ request, từ đó lợi dụng network privilege của server để truy cập destination mà attacker trực tiếp không tới được.

Ví dụ feature nguy hiểm:

```text
POST /preview
{ "url": "https://..." }

Server -> fetch arbitrary URL
```

Nếu không có guard, attacker có thể thử localhost, private IP, cloud metadata endpoint hoặc internal admin services.

## 2. Why does it exist?

Server thường có network trust cao hơn browser/user:

- private VNet routes;
- internal DNS;
- Managed Identity environment;
- access tới metadata/control endpoints;
- firewall allowlist theo source network.

Một generic “fetch URL” endpoint vô tình chuyển trust này cho user.

## 3. How does it work?

Attack path:

```text
Attacker
 -> public API accepts URL
 -> server resolves hostname
 -> server connects from trusted network
 -> internal service responds
 -> response/status/timing leaks back
```

Chỉ check string `StartsWith("https://")` không đủ. DNS rebinding, redirects, IPv6, alternative IP encodings và hostname resolution đều ảnh hưởng security.

## 4. Practical implementation

Tốt nhất dùng allowlist theo known integrations thay vì arbitrary URL:

```csharp
private static readonly HashSet<string> AllowedHosts =
    new(StringComparer.OrdinalIgnoreCase)
    {
        "api.partner-a.com",
        "images.partner-b.com"
    };

public static bool IsAllowed(Uri uri)
{
    if (uri.Scheme != Uri.UriSchemeHttps)
        return false;

    return AllowedHosts.Contains(uri.Host);
}
```

Nhưng với arbitrary user URL business requirement, cần defense sâu hơn:

- resolve DNS và reject loopback/private/link-local ranges;
- validate every redirect destination;
- restrict ports/schemes;
- network egress firewall/proxy;
- response size/time limits;
- không forward credentials/headers;
- isolate fetcher workload.

Security-critical validation không nên chỉ dựa vào một regex.

## 5. Real production scenario

CMS có “import image from URL”. Attacker/editor compromised account nhập URL trỏ tới internal admin endpoint. App Service có private network access và fetch thành công.

Ngay cả khi response body không trả trực tiếp, timing/status differences có thể giúp map internal network. Nếu endpoint là cloud metadata/identity-sensitive service, blast radius còn lớn hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → outbound logs có requests tới `127.0.0.1`, RFC1918/private ranges hoặc hostname nội bộ từ public feature.

**Evidence** → user-controlled URL correlation, DNS resolution, redirect chain, egress logs.

**Hypothesis** → SSRF guard thiếu hoặc redirect bypass.

**Diagnosis** → trace original input → normalized URI → DNS → redirects → final remote IP; review network policy.

**Fix** → allowlist nếu có thể, reject private/metadata ranges, revalidate redirects, enforce egress proxy/firewall, rotate exposed credentials nếu compromise suspected.

**Verification** → security tests với localhost, private IPv4/IPv6, redirects, DNS-changing hosts và oversized responses.

## 7. Common mistakes

- Chỉ cho phép `https` rồi nghĩ an toàn.
- Validate hostname trước nhưng tự động follow redirect tới private IP.
- Block `127.0.0.1` nhưng quên IPv6 loopback/link-local/private ranges.
- Gửi service auth headers tới URL do user chọn.
- Cho model/AI agent gọi generic URL-fetch tool với unrestricted egress.

## 8. Alternatives

Predefined partner connectors có fixed base URLs là đơn giản và an toàn hơn. Browser-side fetch giảm server network privilege nhưng bị CORS và vẫn có data/security concerns. Dedicated isolated fetch service/proxy phù hợp nếu arbitrary URL retrieval là core feature.

## 9. Trade-offs

### Advantages

Cho phép server fetch remote content có thể đơn giản hóa integrations, previews và imports.

### Costs / Risks

Server network privilege biến feature thành security-sensitive proxy. Strict allowlist giảm flexibility; isolated egress tăng infrastructure complexity nhưng giảm blast radius.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu URL từ user là untrusted input dù server chỉ thực hiện `GET`.

### Middle

Validate scheme/host, timeout, size và redirect behavior.

### Senior

Threat-model DNS resolution, redirects, private ranges, cloud metadata và credential propagation.

### Technical Lead / Architect

Quyết định có thật sự cần arbitrary outbound access; nếu cần, thiết kế network egress boundary và least privilege thay vì chỉ application validation.

## 11. Key takeaway

- SSRF là network-authorization problem, không chỉ URL-validation problem.
- Allowlist destination tốt hơn blacklist khi integration set hữu hạn.
- Application validation + egress controls + least privilege mới tạo defense in depth.
