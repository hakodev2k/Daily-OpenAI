# 1. Modular Monolith và ranh giới module

## 1. What is it?

Modular Monolith là kiến trúc một ứng dụng deploy như một unit nhưng được chia thành các module độc lập về business.

## 2. Why does it exist?

Nó giải quyết vấn đề monolith truyền thống bị coupling cao nhưng tránh được complexity ban đầu của microservices.

## 3. How does it work?

```text
API
 |
 +-- Order Module
 |      Domain
 |      Application
 |
 +-- Payment Module
 |      Domain
 |      Application
 |
 Database
```

Mỗi module sở hữu business rule và interface riêng.

## 4. Practical example

ASP.NET Core có các module Employee, Timesheet, Notification thay vì một service chứa toàn bộ logic.

## 5. Real production scenario

Hệ thống SaaS có thể tách Billing khỏi User Management để sau này dễ extract thành service riêng.

## 6. Common mistakes

- Chỉ chia folder nhưng vẫn truy cập database lẫn nhau.
- Không định nghĩa ownership của dữ liệu.

## 7. Trade-offs

Ưu điểm: đơn giản hơn microservices, dễ deploy.

Rủi ro: cần kỷ luật để giữ boundary.

## 8. Junior → Middle → Senior

Junior hiểu module boundary.
Middle thiết kế dependency.
Senior quyết định khi nào tách service.

## 9. Key takeaway

Boundary tốt quan trọng hơn số lượng service.

# 2. Domain-Driven Design (DDD) và Bounded Context

## 1. What is it?

DDD tập trung mô hình phần mềm theo domain thực tế.

## 2. Why does it exist?

Business complexity thường lớn hơn technical complexity.

## 3. How does it work?

```text
Business Domain
      |
Bounded Context
      |
Entities + Rules + Events
```

## 4. Practical example

Order có trạng thái riêng trong Sales Context, không dùng chung với Shipping Context.

## 5. Real production scenario

E-commerce tránh dùng một Order model cho tất cả phòng ban.

## 6. Common mistakes

Tạo entity chỉ phản ánh database table.

## 7. Trade-offs

Tăng chất lượng model nhưng cần đầu tư phân tích domain.

## 8. Junior → Middle → Senior

Junior hiểu entity.
Middle thiết kế aggregate.
Senior xác định bounded context.

## 9. Key takeaway

Model nên phản ánh business, không chỉ schema.

# 3. API Versioning trong REST API

API Versioning giúp thay đổi contract mà không phá client cũ.

Ví dụ:

```http
GET /api/v1/orders
GET /api/v2/orders
```

Production cần strategy rõ ràng cho deprecation, backward compatibility và migration.

# 4. Optimistic Concurrency với EF Core

Dùng khi nhiều user có thể cập nhật cùng một dữ liệu.

Ví dụ:

```csharp
public byte[] RowVersion { get; set; }
```

EF Core kiểm tra version trước khi update để tránh ghi đè dữ liệu mới.

Cần xử lý DbUpdateConcurrencyException.

# 5. Azure Functions và Background Processing

Azure Functions phù hợp cho workload event-driven, scheduled job hoặc xử lý ngắn hạn.

Flow:

```text
Event
 |
Azure Function
 |
Process
 |
Storage/API
```

Cần cân nhắc App Service Worker, Container Apps khi cần chạy lâu hoặc kiểm soát nhiều hơn.

# 6. Azure Key Vault và Secret Management

Azure Key Vault lưu connection string, certificate, API key an toàn.

Ứng dụng nên dùng Managed Identity thay vì hard-code secret.

Production cần rotation, access policy và audit log.

# 7. Distributed Cache với Redis

Redis giảm tải database bằng cách lưu dữ liệu truy cập thường xuyên.

Flow:

```text
Request -> Redis -> Hit
              |
              Miss -> Database -> Redis
```

Cần thiết kế TTL, invalidation và fallback khi Redis unavailable.

---

# 8. Production Troubleshooting với Structured Logging

Structured Logging lưu log dạng có cấu trúc thay vì text thuần.

Ví dụ:

```csharp
logger.LogError("Payment failed {OrderId}", orderId);
```

Kết hợp trace id, metrics và logs giúp điều tra incident nhanh hơn.

# 9. AI Function Calling và kiểm soát workflow

Function Calling cho phép LLM gọi tool nhưng business logic vẫn do code kiểm soát.

```text
User
 |
LLM
 |
Tool Call
 |
Application Service
 |
Database/API
```

Không nên để AI tự quyết định hành động nhạy cảm như thanh toán.

# 10. CI/CD với Blue-Green Deployment

Blue-Green tạo hai môi trường production song song.

```text
Blue (Current)
       |
       Switch
       |
Green (New)
```

Giúp rollback nhanh nhưng cần quản lý database migration và cost hạ tầng.

# Final Takeaways

- Kiến trúc tốt bắt đầu từ boundary rõ ràng.
- Production engineering cần quan tâm failure mode, observability và rollback.
- Công nghệ chỉ giải quyết vấn đề khi được đặt đúng context.
