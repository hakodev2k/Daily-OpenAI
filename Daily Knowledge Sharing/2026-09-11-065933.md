# 1. .NET `IAsyncDisposable`: giải phóng resource có asynchronous cleanup mà không biến shutdown thành fire-and-forget

## 1. What is it?

`IAsyncDisposable` là contract cho resource cần cleanup có thao tác asynchronous, thông qua `ValueTask DisposeAsync()`.

Mental model:

```text
Acquire resource
    ↓
use resource
    ↓
cleanup cần I/O
    ↓
await DisposeAsync()
```

Khác với `IDisposable`, cleanup không bị ép chạy synchronous. Điều này quan trọng khi teardown cần flush network buffer, complete stream, close protocol session hoặc release resource qua asynchronous API.

## 2. Why does it exist?

`Dispose()` phù hợp khi cleanup chỉ là thao tác local, nhanh và deterministic. Nhưng một số resource phải chờ I/O.

Nếu synchronous cleanup gọi `.Wait()` hoặc `.GetAwaiter().GetResult()` trên operation async, application có thể block ThreadPool hoặc kéo dài shutdown. Nếu fire-and-forget cleanup, process có thể kết thúc trước khi dữ liệu được flush.

`IAsyncDisposable` cho phép lifecycle phản ánh đúng bản chất của resource.

## 3. How does it work?

C# hỗ trợ `await using`:

```csharp
await using var resource = await CreateResourceAsync(ct);
```

Compiler về bản chất đảm bảo `DisposeAsync()` được `await` khi scope kết thúc, kể cả khi có exception.

```text
try
  └─ use resource
finally
  └─ await DisposeAsync()
```

`DisposeAsync()` thường trả `ValueTask` vì cleanup có thể hoàn tất synchronously trong một số trường hợp và framework muốn tránh allocation `Task` không cần thiết.

## 4. Practical implementation

```csharp
public sealed class ExportWriter : IAsyncDisposable
{
    private readonly StreamWriter _writer;

    public ExportWriter(Stream stream)
    {
        _writer = new StreamWriter(stream, leaveOpen: false);
    }

    public Task WriteAsync(string line) => _writer.WriteLineAsync(line);

    public async ValueTask DisposeAsync()
    {
        await _writer.FlushAsync();
        await _writer.DisposeAsync();
    }
}
```

Usage:

```csharp
await using var writer = new ExportWriter(response.Body);
await writer.WriteAsync("id,name");
```

Nếu class vừa có sync vừa async cleanup, implementation cần rõ ownership và tránh dispose cùng resource hai lần.

## 5. Real production scenario

Một background export job ghi hàng trăm MB dữ liệu ra remote stream. Khi job bị cancel, code cũ gọi `Dispose()` trên wrapper nhưng buffer chưa flush hoàn toàn. Một số files xuất hiện trong storage với kích thước nhỏ hơn expected dù job log “completed cleanup”.

Chuyển lifecycle sang `await using` giúp shutdown chờ đúng asynchronous flush trước khi resource bị đóng.

## 6. Failure scenario & troubleshooting

**Symptom** → file đôi khi truncated, connection đóng muộn, shutdown vượt timeout.

**Evidence** → trace cho thấy process stop trong lúc flush/close vẫn đang chạy; exception từ cleanup bị mất vì fire-and-forget.

**Hypothesis** → resource có async cleanup nhưng lifecycle đang dùng sync disposal hoặc không `await`.

**Diagnosis** → kiểm tra ownership chain và các loại implement `IAsyncDisposable`.

**Fix** → propagate async disposal đến boundary phù hợp; tránh blocking wrapper.

**Verification** → cancel job dưới load, kiểm tra file integrity và shutdown duration.

## 7. Common mistakes

* Gọi `DisposeAsync()` nhưng không `await`.
* Tạo wrapper `Dispose()` rồi block trên `DisposeAsync()` trong hot path.
* Dispose resource do DI container sở hữu bằng tay.
* Dùng `IAsyncDisposable` cho object không có asynchronous cleanup thực sự, làm API phức tạp vô ích.

## 8. Alternatives

Nếu cleanup hoàn toàn synchronous, `IDisposable` đơn giản hơn.

Nếu resource lifetime do DI container quản lý, để container dispose đúng scope thường tốt hơn tự viết lifecycle thủ công.

## 9. Trade-offs

### Advantages

Cleanup đúng semantics, tránh fire-and-forget và giảm nhu cầu sync-over-async.

### Costs / Risks

Async disposal lan truyền lên caller; ownership trở nên quan trọng hơn và shutdown path cần timeout/cancellation policy rõ ràng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Dispose` là quản lý lifecycle, không phải “GC sẽ lo hết”.

### Middle

Biết dùng `await using`, phân biệt `IDisposable` và `IAsyncDisposable`.

### Senior

Biết điều tra resource leak, shutdown latency, ownership và cleanup exception.

### Technical Lead / Architect

Định nghĩa lifecycle boundary: resource nào thuộc request, job, singleton service hay host; cleanup có nằm trong shutdown budget hay không.

## 11. Key takeaway

* Async cleanup phải được `await` nếu correctness phụ thuộc vào nó.
* GC không thay thế deterministic resource cleanup.
* Chỉ dùng `IAsyncDisposable` khi lifecycle thực sự có asynchronous work.

# 2. ASP.NET Core request body streaming + file-upload security: xử lý payload lớn mà không giữ toàn bộ file trong memory và không tin client metadata

## 1. What is it?

Request body streaming là xử lý dữ liệu khi bytes đi qua stream thay vì đọc toàn bộ payload vào `byte[]` hoặc memory buffer trước.

Với upload, performance và security liên quan trực tiếp: file lớn có thể gây memory pressure, còn filename/content-type từ client không phải dữ liệu đáng tin cậy.

## 2. Why does it exist?

Naive implementation:

```csharp
using var ms = new MemoryStream();
await file.CopyToAsync(ms);
var bytes = ms.ToArray();
```

Với 100 concurrent uploads, mỗi file 200 MB, application có thể cố giữ hàng chục GB logical buffers. Hệ thống chết trước khi business logic thực sự bắt đầu.

Ngoài ra, `Content-Type: image/png` không chứng minh payload là PNG và filename có thể chứa path tricks hoặc characters không mong muốn.

## 3. How does it work?

Streaming flow:

```text
Client
  ↓ chunks
ASP.NET Core request stream
  ↓ bounded buffer
validation / hashing / scanner
  ↓
Blob/file destination
```

Điểm chính là memory usage gần với buffer size và concurrency, không tỷ lệ trực tiếp với tổng file size.

Security boundary nên xác thực kích thước, loại file dựa trên actual content nếu cần, destination name do server tạo, authorization và malware scanning theo risk model.

## 4. Practical implementation

Ví dụ copy trực tiếp với size limit:

```csharp
app.MapPost("/uploads", async (
    HttpRequest request,
    IBlobStore store,
    CancellationToken ct) =>
{
    if (request.ContentLength is > 100 * 1024 * 1024)
        return Results.BadRequest("File too large");

    var objectName = $"{Guid.NewGuid():N}.bin";

    await store.WriteAsync(
        objectName,
        request.Body,
        ct);

    return Results.Ok(new { objectName });
});
```

Trong hệ thống thực, có thể stream qua hashing/validation layer hoặc upload trực tiếp từ client lên Blob Storage bằng short-lived SAS nếu application không cần proxy bytes.

## 5. Real production scenario

CMS cho editor upload video 500 MB. Khi traffic bình thường, upload ổn. Trong một campaign, 20 editors upload cùng lúc và web instances tăng memory nhanh, GC pressure cao, cuối cùng restart.

Root cause không phải Azure Blob Storage mà là web app buffer toàn bộ `IFormFile` vào memory trước khi upload downstream.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng theo số upload concurrent, request timeout, pod/process restart.

**Evidence** → allocation profile có large byte arrays/MemoryStream; request sizes tương quan với working set.

**Hypothesis** → application buffering full payload.

**Diagnosis** → trace upload path, Kestrel/form limits, middleware và storage SDK usage.

**Fix** → streaming hoặc direct-to-storage; bounded concurrency; explicit size limits.

**Verification** → load test nhiều large uploads, memory phải giữ tương đối ổn định theo configured buffers.

## 7. Common mistakes

* Tin `Content-Type` và extension do client gửi.
* Lưu nguyên `FileName` làm server path.
* Không giới hạn payload size.
* Virus-scan sau khi file đã public-accessible.
* Dùng synchronous file I/O trong request path.

## 8. Alternatives

Direct-to-Blob bằng SAS giảm bandwidth qua application, phù hợp file lớn. Proxy qua application hữu ích khi cần kiểm soát stream hoặc transform bắt buộc.

Chunked/resumable upload phù hợp file rất lớn hoặc network không ổn định nhưng protocol phức tạp hơn.

## 9. Trade-offs

### Advantages

Streaming giảm memory pressure và cải thiện scalability.

### Costs / Risks

Validation phức tạp hơn vì không phải rule nào cũng quyết định được từ vài bytes đầu; cleanup partial uploads và retry semantics cần thiết kế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu file upload là stream bytes, không nhất thiết là một `byte[]` lớn.

### Middle

Biết giới hạn size, stream dữ liệu và sanitize/server-generate object name.

### Senior

Threat-model malformed files, partial upload, concurrency, scanning và storage failure.

### Technical Lead / Architect

Chọn proxy upload hay direct-to-storage, xác định trust boundary, retention và scanning workflow.

## 11. Key takeaway

* Payload lớn nên được stream thay vì buffer toàn bộ.
* Client metadata không phải security evidence.
* Upload architecture phải xét memory, authorization và lifecycle của partial files cùng lúc.

# 3. EF Core `IQueryable` + deferred execution: hiểu boundary giữa expression tree, SQL translation và in-memory execution

## 1. What is it?

`IQueryable<T>` đại diện cho một query expression chưa nhất thiết chạy. EF Core xây expression tree, translate phần hỗ trợ sang SQL và chỉ thực thi khi có terminal operation như `ToListAsync`, `SingleAsync`, `CountAsync`.

Mental model:

```text
LINQ expression
   ↓
IQueryable
   ↓ translation
SQL
   ↓ execution
rows
   ↓ materialization
objects/DTOs
```

## 2. Why does it exist?

Nếu mỗi LINQ operator chạy ngay, application không thể compose filters, sort và projection thành một SQL query tối ưu ở database.

Deferred execution cho phép nhiều layer thêm điều kiện trước execution. Nhưng nó cũng tạo hidden boundary: developer có thể vô tình chuyển sang in-memory quá sớm hoặc execute query nhiều lần.

## 3. How does it work?

Đoạn sau chưa query database:

```csharp
var query = db.Orders
    .Where(x => x.Status == OrderStatus.Open);
```

Sau đó compose:

```csharp
query = query.Where(x => x.CreatedUtc >= from);
```

Database chỉ bị gọi tại:

```csharp
var rows = await query
    .Select(x => new OrderDto(x.Id, x.Total))
    .ToListAsync(ct);
```

`AsEnumerable()` hoặc `ToList()` đổi execution boundary. Sau boundary đó, LINQ có thể chạy trong process thay vì SQL Server.

## 4. Practical implementation

Tốt:

```csharp
IQueryable<Order> query = db.Orders.AsNoTracking();

if (status is not null)
    query = query.Where(x => x.Status == status);

return await query
    .OrderByDescending(x => x.CreatedUtc)
    .Select(x => new OrderListItem(x.Id, x.Total, x.Status))
    .Take(100)
    .ToListAsync(ct);
```

Nguy hiểm:

```csharp
var orders = await db.Orders.ToListAsync(ct);
return orders.Where(x => ExpensiveFilter(x));
```

Nếu table có 5 triệu rows, filter đã chuyển từ database xuống application.

## 5. Real production scenario

Một reporting endpoint thêm helper extension trả `IEnumerable<Order>` thay vì `IQueryable<Order>`. Code review nhìn gần như giống nhau, nhưng filter theo ngày diễn ra sau khi toàn bộ rows đã materialize.

Production CPU/memory của API tăng mạnh và database network traffic cũng tăng.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint chậm, memory cao, số rows đọc từ DB lớn hơn nhiều rows trả về.

**Evidence** → generated SQL thiếu filter/projection expected.

**Hypothesis** → execution boundary xảy ra quá sớm.

**Diagnosis** → tìm `ToList`, `AsEnumerable`, helper methods và debugger/query logs.

**Fix** → giữ query compose trên `IQueryable` tới projection/terminal operation.

**Verification** → kiểm tra generated SQL, row count, logical reads và allocation.

## 7. Common mistakes

* Expose `IQueryable` xuyên mọi architectural boundary, làm persistence details rò ra ngoài.
* Gọi `ToListAsync()` rồi filter tiếp.
* Enumerate cùng query nhiều lần và tạo nhiều round trips.
* Dùng custom .NET method trong expression mà provider không translate được.

## 8. Alternatives

Repository/domain query method có thể đóng gói query shape và không expose `IQueryable` ra application boundary.

Raw SQL phù hợp query đặc thù cần kiểm soát execution plan hoặc dùng feature SQL khó biểu diễn qua LINQ.

## 9. Trade-offs

### Advantages

Composable query, push filtering/projection xuống database, expressive code.

### Costs / Risks

Execution timing ẩn, translation limitations và abstraction leak nếu `IQueryable` được lan truyền không kiểm soát.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu viết LINQ chưa đồng nghĩa query đã chạy.

### Middle

Biết terminal operators, projection và generated SQL.

### Senior

Nhận diện hidden execution boundary, multiple enumeration và provider translation issues.

### Technical Lead / Architect

Quyết định nơi query composition được phép tồn tại để cân bằng flexibility với boundary clarity.

## 11. Key takeaway

* `IQueryable` là query plan đang được compose, không phải collection đã có sẵn.
* Materialize quá sớm có thể biến database filtering thành in-memory processing.
* Luôn xem generated SQL khi performance/correctness phụ thuộc query shape.

# 4. SQL Server statistics + parameter-sensitive plans: vì sao cùng một query có lúc chạy 20 ms, có lúc chạy 20 giây

## 1. What is it?

SQL Server statistics mô tả distribution của dữ liệu để optimizer ước lượng cardinality. Cardinality estimate ảnh hưởng quyết định index seek/scan, join algorithm, memory grant và join order.

Parameter-sensitive plan xảy ra khi một execution plan tốt cho parameter này lại tệ cho parameter khác vì data distribution lệch mạnh.

## 2. Why does it exist?

Optimizer không chạy thử mọi chiến lược. Nó dùng statistics để dự đoán số rows rồi chọn plan có estimated cost thấp.

Ví dụ `TenantId=1` có 10 triệu rows nhưng `TenantId=99` chỉ có 100 rows. Một plan tối ưu cho tenant nhỏ có thể trở thành thảm họa cho tenant lớn.

## 3. How does it work?

Query:

```sql
SELECT Id, CreatedUtc, Total
FROM Orders
WHERE TenantId = @TenantId
  AND Status = @Status;
```

Optimizer dùng histogram/statistics để estimate selectivity. Cached plan có thể được reuse cho lần gọi sau.

Nếu plan ban đầu được tạo từ parameter rất selective, optimizer có thể chọn nested loops + seeks. Với parameter trả millions rows, hash join/scan hoặc plan khác có thể phù hợp hơn.

## 4. Practical implementation

Bắt đầu từ evidence:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

So sánh Actual Execution Plan giữa parameter nhỏ và lớn. Quan sát:

```text
Estimated Rows vs Actual Rows
Index Seek/Scan
Join type
Memory Grant
Spill warnings
```

Đừng nhảy ngay tới `OPTION (RECOMPILE)`. Có thể cần cập nhật statistics, sửa index/access pattern hoặc dùng khả năng Parameter Sensitive Plan của SQL Server phiên bản phù hợp.

## 5. Real production scenario

Multi-tenant SaaS có một enterprise tenant chiếm 65% bảng `Events`. Query dashboard chạy nhanh cho hầu hết tenants nhưng tenant lớn mất 15–25 giây.

Application metrics chỉ cho thấy cùng endpoint có bimodal latency. Execution plans theo tenant mới lộ ra cardinality mismatch.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng query text nhưng latency thay đổi rất lớn theo parameter hoặc sau restart/deploy.

**Evidence** → Query Store có nhiều runtime distributions; estimated rows lệch xa actual rows.

**Hypothesis** → stale statistics hoặc parameter-sensitive plan.

**Diagnosis** → Query Store, actual plan, histogram, row distribution và index usage.

**Fix** → chọn biện pháp dựa trên cause: statistics maintenance, index/query redesign, plan strategy hoặc data partitioning.

**Verification** → test representative parameter sets, không chỉ một happy-path value.

## 7. Common mistakes

* “Add index” mà không nhìn cardinality.
* Test query bằng parameter không đại diện Production.
* Clear plan cache như permanent fix.
* Force một plan mà không quan sát workload drift.

## 8. Alternatives

Query branching cho các data shapes cực khác nhau có thể rõ ràng hơn một universal query.

Partitioning/data architecture có thể phù hợp khi skew phản ánh boundary business lớn, nhưng operational cost cao hơn.

## 9. Trade-offs

### Advantages

Hiểu statistics giúp sửa root cause thay vì tuning theo cảm giác.

### Costs / Risks

Plan behavior phụ thuộc data distribution theo thời gian; forced-plan/recompile approaches có maintenance hoặc CPU cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu optimizer chọn plan dựa trên ước lượng, không “biết chắc” dữ liệu sẽ ra bao nhiêu rows.

### Middle

Biết đọc estimated vs actual rows và basic plan operators.

### Senior

Phân tích skew, Query Store, memory grants và plan regressions.

### Technical Lead / Architect

Quyết định query/index fix đã đủ hay data model/tenant isolation cần thay đổi.

## 11. Key takeaway

* Execution plan tốt phụ thuộc cardinality estimate tốt.
* Cùng query text không đảm bảo cùng performance cho mọi parameter.
* Tuning phải dùng representative Production data shapes.

# 5. Redis eviction + memory pressure: cache hit cao vẫn có thể trở thành outage khi eviction policy và workload không khớp

## 1. What is it?

Eviction là cơ chế Redis loại keys khi memory đạt giới hạn cấu hình. Policy quyết định key nào bị loại, ví dụ ưu tiên keys có TTL hoặc chọn theo LRU/LFU approximation tùy cấu hình.

Mental model:

```text
writes vào cache
   ↓
memory đạt max
   ↓
eviction policy
   ↓
remove keys hoặc reject writes
```

## 2. Why does it exist?

Cache không thể tăng memory vô hạn. Khi dataset nóng lớn hơn capacity, Redis phải có hành vi rõ ràng.

Nếu policy không khớp workload, cache có thể liên tục đẩy ra keys vừa cần, làm hit ratio giảm và database nhận load đột ngột.

## 3. How does it work?

Ví dụ cache-aside:

```text
API → Redis hit → nhanh
API → Redis miss → SQL → SET Redis
```

Khi memory pressure tăng, nhiều keys bị evict. Misses tăng, SQL load tăng, response chậm. Slower responses giữ concurrency lâu hơn, có thể tạo positive feedback loop.

Eviction khác expiration: expiration xảy ra vì TTL; eviction xảy ra vì capacity pressure.

## 4. Practical implementation

Application nên đo ít nhất:

```text
used_memory
maxmemory
keyspace_hits
keyspace_misses
evicted_keys
expired_keys
```

Cache key design nên có TTL có chủ đích:

```csharp
await cache.StringSetAsync(
    key,
    payload,
    expiry: TimeSpan.FromMinutes(10));
```

Không nên đưa mọi object vào cache chỉ vì “Redis còn RAM”.

## 5. Real production scenario

Product API cache catalog và session-like temporary data trong cùng Redis. Campaign tạo hàng triệu temporary keys, memory chạm max và Redis bắt đầu evict product hot keys.

Hit ratio tụt từ 95% xuống 50%; SQL CPU tăng mạnh dù Redis vẫn “UP”.

## 6. Failure scenario & troubleshooting

**Symptom** → database latency tăng, Redis không outage, cache hit ratio giảm.

**Evidence** → `evicted_keys` tăng nhanh và used memory sát max.

**Hypothesis** → eviction pressure đang chuyển load xuống database.

**Diagnosis** → phân tích key cardinality, sizes, TTL distribution và workload theo namespace.

**Fix** → bỏ keys giá trị thấp, điều chỉnh TTL/capacity/policy, tách workloads nếu ownership khác nhau.

**Verification** → eviction rate giảm, hit ratio ổn định và DB load về baseline.

## 7. Common mistakes

* Chỉ alert khi Redis unreachable, không alert eviction.
* Dùng Redis như database thứ hai nhưng không có memory budget.
* Key không TTL cho dữ liệu cache thực sự disposable.
* Tăng memory mà không hiểu key growth.

## 8. Alternatives

`IMemoryCache` phù hợp local instance data không cần shared consistency.

Không cache cũng là lựa chọn tốt nếu database query đã đủ nhanh và cache invalidation/operations tạo complexity lớn hơn lợi ích.

## 9. Trade-offs

### Advantages

Redis giảm latency và offload backend khi working set phù hợp capacity.

### Costs / Risks

Thêm failure mode, memory sizing, serialization, invalidation và eviction behavior.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache có capacity hữu hạn và key có thể biến mất.

### Middle

Biết đặt TTL, đọc hit/miss/eviction metrics.

### Senior

Phân tích memory pressure, hot-key behavior và downstream amplification.

### Technical Lead / Architect

Quyết định cache ownership, capacity budget, workload isolation và degraded mode khi hit ratio sụp.

## 11. Key takeaway

* Redis “healthy” không có nghĩa cache đang hoạt động hiệu quả.
* Eviction có thể biến thành database incident.
* Cache cần capacity model và observability như một production dependency thực sự.

# 6. Domain Event vs Integration Event: tách business fact trong bounded context khỏi contract phát ra ngoài hệ thống

## 1. What is it?

Domain Event biểu diễn một business fact quan trọng bên trong domain model, ví dụ `OrderConfirmed`. Integration Event là contract phát ra ngoài bounded context để hệ thống khác phản ứng.

Hai khái niệm có thể cùng nói về một sự kiện business nhưng không nhất thiết cùng type, schema hoặc lifecycle.

## 2. Why does it exist?

Nếu domain object publish trực tiếp external contract, internal model bị khóa vào integration concerns: broker metadata, versioning, privacy và consumer expectations.

Tách hai lớp giúp bounded context giữ autonomy:

```text
Domain invariant
  ↓
Domain Event
  ↓ Application/Integration mapping
Integration Event
  ↓
Broker
```

## 3. How does it work?

Domain entity tạo event khi state transition hợp lệ:

```text
Order.Confirm()
  ├─ validate invariant
  ├─ state = Confirmed
  └─ raise OrderConfirmedDomainEvent
```

Application layer xử lý event và quyết định external consequence. Nếu cần reliable publication, Integration Event được lưu qua Outbox trong cùng transaction.

Không phải mọi Domain Event đều phải rời service.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<IDomainEvent> _events = [];

    public void Confirm()
    {
        if (Status != OrderStatus.Pending)
            throw new InvalidOperationException();

        Status = OrderStatus.Confirmed;
        _events.Add(new OrderConfirmedDomainEvent(Id));
    }
}
```

Mapping:

```csharp
public Task Handle(OrderConfirmedDomainEvent e, CancellationToken ct)
{
    var integrationEvent = new OrderConfirmedV1(
        e.OrderId,
        DateTimeOffset.UtcNow);

    return _outbox.AddAsync(integrationEvent, ct);
}
```

## 5. Real production scenario

E-commerce domain thêm internal detail về fraud review. Nếu external consumers dùng trực tiếp domain event object, thay đổi internal model có thể phá Notification và Analytics.

Với explicit integration contract, domain có thể evolve độc lập và chỉ phát fields external consumers thực sự cần.

## 6. Failure scenario & troubleshooting

**Symptom** → một refactor domain gây breaking change cho multiple downstream services.

**Evidence** → shared event package chứa domain entities hoặc internal enums.

**Hypothesis** → domain contract và integration contract bị trộn.

**Diagnosis** → map dependency graph từ producer assembly/package đến consumers.

**Fix** → tách integration schema, version contract và dùng translation boundary.

**Verification** → domain refactor không buộc consumer rebuild nếu external behavior không đổi.

## 7. Common mistakes

* Publish mọi Domain Event ra broker “vì event-driven”.
* Shared library chứa cả domain entities giữa services.
* Đổi integration event schema in-place mà không xét consumers cũ.
* Gửi sensitive fields chỉ vì chúng có sẵn trong domain object.

## 8. Alternatives

Trong monolith đơn giản, application service gọi trực tiếp collaborator có thể rõ hơn event dispatch.

Nếu chỉ có một external consumer và flow cần synchronous correctness, REST/internal call có thể đơn giản hơn messaging.

## 9. Trade-offs

### Advantages

Giữ domain độc lập, integration contracts explicit và dễ version hơn.

### Costs / Risks

Thêm mapping, event lifecycle, eventual consistency và debugging complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu event là một fact đã xảy ra, không phải command yêu cầu làm gì.

### Middle

Biết raise domain event và map sang integration event.

### Senior

Hiểu transaction boundary, outbox, schema versioning và duplicate delivery.

### Technical Lead / Architect

Quyết định fact nào là internal, fact nào thuộc public service contract và ownership lâu dài của schema.

## 11. Key takeaway

* Domain Event phục vụ domain boundary; Integration Event phục vụ system boundary.
* Không phải mọi internal fact đều nên trở thành public event.
* Explicit translation giảm coupling giữa model nội bộ và consumers bên ngoài.

# 7. Azure App Service deployment slots: warm-up, slot swap và configuration boundaries để release không biến thành cold-start incident

## 1. What is it?

Deployment slot là một running environment riêng trong cùng App Service app, thường dùng `staging` và `production`. Version mới được deploy vào staging, warm/validate trước rồi swap traffic/configuration theo slot semantics.

```text
Build v42
  ↓
Staging slot
  ↓ warm + health validate
Swap
  ↓
Production receives v42
```

## 2. Why does it exist?

Deploy trực tiếp lên Production có thể kết hợp nhiều rủi ro cùng lúc: process restart, startup migration, JIT, cache warm-up, config error và bad artifact.

Slot cho phép version mới chạy trước khi nhận production traffic và tạo rollback path nhanh hơn bằng swap-back trong trường hợp phù hợp.

## 3. How does it work?

Hai slot có code/config state riêng. Một số settings có thể đánh dấu “deployment slot setting” để không swap, thường là environment-specific secrets/endpoints.

Warm-up request giúp application startup trước cutover. Sau swap, old production version vẫn tồn tại ở slot kia, hữu ích cho rollback nhưng database changes vẫn phải backward compatible.

## 4. Practical implementation

Application nên có health endpoint tách readiness khỏi superficial “process alive”:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString);

app.MapHealthChecks("/health/ready");
```

Release pipeline:

```text
artifact
→ deploy staging
→ startup/warm-up
→ smoke test
→ readiness validation
→ swap
→ monitor p95/error rate
→ swap back nếu cần
```

Database migration không nên mặc định chạy nguy hiểm trên startup của mọi slot.

## 5. Real production scenario

ASP.NET Core app load nhiều configuration và compile templates khi startup. Direct deploy trước đây tạo 60–90 giây elevated latency.

Staging slot warm-up hấp thụ cold startup trước khi traffic switch, giảm release impact đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → app staging healthy nhưng sau swap Production gọi nhầm dependency hoặc login fail.

**Evidence** → environment-specific setting bị swap cùng code.

**Hypothesis** → slot-sticky configuration chưa được đánh dấu đúng.

**Diagnosis** → compare slot settings, managed identity permissions, network access và connection strings.

**Fix** → phân loại setting nào theo deployment artifact, setting nào theo environment/slot.

**Verification** → rehearsed swap và smoke tests trên dependencies thực của target slot.

## 7. Common mistakes

* Nghĩ slot swap rollback được destructive database migration.
* Staging dùng hoàn toàn fake dependencies nên validation không đại diện Production.
* Không warm application trước swap.
* Chạy migration từ cả staging và production instances song song.

## 8. Alternatives

Blue-Green bằng hai App Services cho isolation mạnh hơn nhưng chi phí/quản lý lớn hơn.

Container Apps/Kubernetes có revision/rolling deployment semantics khác, phù hợp containerized platform.

## 9. Trade-offs

### Advantages

Giảm downtime/cold-start impact, cho phép pre-production validation và rollback nhanh ở application layer.

### Costs / Risks

Configuration semantics, slot capacity, DB compatibility và networking vẫn cần quản lý; slot không thay thế release engineering.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slot là running environment khác, không chỉ folder deploy khác.

### Middle

Biết deploy staging, health-check và swap.

### Senior

Thiết kế sticky settings, warm-up, migration compatibility và rollback validation.

### Technical Lead / Architect

Chọn release strategy dựa trên downtime tolerance, DB evolution, cost và operational maturity.

## 11. Key takeaway

* Slot giảm application cutover risk nhưng không tự giải quyết database compatibility.
* Configuration phải phân biệt rõ environment-specific và swappable.
* Health validation phải phản ánh khả năng phục vụ traffic thực tế.

# 8. Docker multi-stage builds + image layers: giảm attack surface, image size và drift giữa build/runtime

## 1. What is it?

Docker image được tạo từ các immutable layers. Multi-stage build dùng một stage có SDK/build tools để compile, rồi copy artifact cần thiết sang runtime image nhỏ hơn.

```text
SDK image
  ↓ build/publish
artifact
  ↓ copy
ASP.NET runtime image
```

## 2. Why does it exist?

Nếu Production image chứa full SDK, source code, package caches và build tooling, image lớn hơn, pull chậm hơn và attack surface tăng.

Multi-stage build giữ build environment và runtime environment tách biệt nhưng reproducible từ cùng Dockerfile.

## 3. How does it work?

Mỗi Dockerfile instruction tạo/có thể reuse layer. Cache hiệu quả phụ thuộc ordering. Nếu copy toàn source trước `dotnet restore`, thay đổi một file code có thể invalidate restore layer không cần thiết.

Multi-stage cho phép final image chỉ chứa published output và runtime dependencies.

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

COPY MyApp.csproj ./
RUN dotnet restore MyApp.csproj

COPY . .
RUN dotnet publish MyApp.csproj \
    -c Release \
    -o /app/publish \
    --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApp.dll"]
```

Pin base images theo policy phù hợp và scan dependencies/images trong CI.

## 5. Real production scenario

Team ban đầu dùng SDK image 1+ GB cho runtime. Kubernetes rolling deployment chậm vì nodes thường xuyên pull image lớn. Security scanner cũng báo nhiều CVEs nằm trong build tooling không dùng lúc runtime.

Multi-stage build giảm đáng kể bytes và loại build-only packages khỏi Production image.

## 6. Failure scenario & troubleshooting

**Symptom** → build local chạy nhưng container Production fail vì native dependency thiếu.

**Evidence** → runtime image khác distro/base assumptions so với build environment.

**Hypothesis** → artifact phụ thuộc native library không tồn tại trong final stage.

**Diagnosis** → inspect runtime logs, `ldd`/native dependencies và base image variants.

**Fix** → thêm runtime dependency thật sự cần hoặc chọn compatible runtime base; không quay lại full SDK chỉ để “cho chạy”.

**Verification** → integration test image final, không chỉ `dotnet test` ngoài container.

## 7. Common mistakes

* Copy secrets vào image layer rồi xóa ở layer sau; secret vẫn có thể tồn tại trong history/layer.
* Dùng `latest` không kiểm soát và nhận base-image drift.
* Chạy container bằng root khi không cần.
* Không có `.dockerignore`, gửi cả repository/build artifacts vào context.

## 8. Alternatives

Self-contained/native deployment không cần container trong một số IIS/VM environments.

Buildpacks hoặc platform build services giảm Dockerfile maintenance nhưng đánh đổi một phần transparency/control.

## 9. Trade-offs

### Advantages

Image nhỏ hơn, build/runtime boundary rõ hơn, giảm attack surface và cải thiện deployment speed.

### Costs / Risks

Cần hiểu base image compatibility, caching và supply-chain lifecycle; image nhỏ không tự động đồng nghĩa secure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu image gồm layers và container chạy từ image immutable.

### Middle

Biết viết multi-stage Dockerfile và tận dụng build cache.

### Senior

Xử lý native dependency, non-root execution, scanning và reproducibility.

### Technical Lead / Architect

Đặt base-image policy, patch cadence, provenance/SBOM strategy và CI controls cho toàn tổ chức.

## 11. Key takeaway

* Build tools không cần nằm trong runtime image.
* Layer ordering ảnh hưởng cả cache lẫn khả năng vô tình lưu secret.
* Test chính final image sẽ deploy, không chỉ source project.

# 9. Contract testing cho third-party API: phát hiện schema drift trước khi Production thay vì mock một thế giới không tồn tại

## 1. What is it?

Contract testing kiểm tra assumptions giữa consumer và provider: endpoint, fields, types, status codes, compatibility và semantics quan trọng.

Với third-party API, ta thường không kiểm soát provider code, nên mục tiêu là xác minh integration assumptions bằng sandbox/schema/recorded fixtures hoặc scheduled verification có kiểm soát.

## 2. Why does it exist?

Unit test với mock kiểu:

```csharp
clientMock.Setup(x => x.GetCustomerAsync(...))
          .ReturnsAsync(expectedCustomer);
```

chỉ chứng minh code tương tác đúng với mock do chính ta viết. Nếu provider đổi `phoneNumber` thành nullable, status code hoặc JSON shape, mock vẫn xanh.

Contract testing bảo vệ boundary thực tế hơn.

## 3. How does it work?

Boundary test nên xác minh raw transport contract trước mapping:

```text
Third-party response
  ↓ deserialize
transport DTO
  ↓ validate assumptions
anti-corruption mapping
  ↓
domain/application model
```

Test có thể chạy against provider sandbox hoặc fixture được capture có version/provenance rõ ràng.

## 4. Practical implementation

```csharp
[Fact]
public async Task Customer_response_matches_supported_contract()
{
    var response = await _client.GetAsync("/customers/contract-fixture");

    response.EnsureSuccessStatusCode();

    var json = await response.Content.ReadAsStringAsync();
    var dto = JsonSerializer.Deserialize<CustomerResponse>(json);

    Assert.NotNull(dto);
    Assert.False(string.IsNullOrWhiteSpace(dto.Id));
}
```

Transport DTO nên tolerant với additive fields nhưng strict với invariants application thực sự cần.

## 5. Real production scenario

Review provider đổi enum `Approved|Rejected` thành thêm `PendingReview`. Application dùng switch exhaustive cũ và throw exception. Unit tests vẫn pass vì fixtures chỉ có hai giá trị cũ.

Contract verification với sandbox/sample mới phát hiện unknown enum trước rollout Production.

## 6. Failure scenario & troubleshooting

**Symptom** → deserialize errors tăng ngay sau provider release dù app không deploy.

**Evidence** → raw response chứa field/type/enum mới.

**Hypothesis** → external contract drift.

**Diagnosis** → compare payload với stored schema/fixture và provider changelog nếu có.

**Fix** → tolerant reader ở nơi hợp lý, explicit unknown handling hoặc compatibility adapter.

**Verification** → replay representative payloads và integration test provider boundary.

## 7. Common mistakes

* Mock provider hoàn toàn và gọi đó là integration test.
* Deserialize trực tiếp external DTO vào domain entity.
* Throw với mọi unknown additive field dù JSON serializer có thể ignore an toàn.
* Contract test gọi Production destructive endpoint.

## 8. Alternatives

Consumer-driven contracts rất mạnh khi bạn kiểm soát cả provider. Với SaaS third-party, sandbox/schema monitoring hoặc synthetic read-only probes thường thực tế hơn.

Recorded fixtures hữu ích nhưng có thể stale nếu không refresh có quy trình.

## 9. Trade-offs

### Advantages

Phát hiện boundary drift sớm và giảm false confidence từ mocks.

### Costs / Risks

Sandbox có thể khác Production; tests external dễ flaky và phụ thuộc quota/network. Cần tách chúng khỏi deterministic unit-test gate phù hợp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu mock chỉ mô phỏng assumption của team.

### Middle

Biết test serialization/status/error contract với representative responses.

### Senior

Thiết kế tolerant mapping, fallback và telemetry cho schema drift.

### Technical Lead / Architect

Quyết định contract verification cadence, provider isolation boundary và degraded-mode strategy khi dependency thay đổi.

## 11. Key takeaway

* Mock xanh không chứng minh external API còn tương thích.
* External DTO nên dừng ở integration boundary.
* Contract tests cần đại diện provider thực nhưng không trở thành flaky blocker vô kiểm soát.

# 10. Optimizely CMS content modeling + cache invalidation: thiết kế content boundary để editor linh hoạt nhưng website vẫn ổn định và nhanh

## 1. What is it?

Content modeling trong CMS xác định Page Types, Blocks, properties và quan hệ nội dung. Trong Optimizely CMS, model code không chỉ là data class; nó trở thành contract giữa editor experience, rendering code, cache và content lifecycle.

Caching giúp giảm chi phí đọc/render nội dung, nhưng invalidation phải đi cùng publish/update semantics.

## 2. Why does it exist?

Nếu mọi page là một blob tự do, editors linh hoạt nhưng code khó enforce cấu trúc, reuse và accessibility. Nếu model quá rigid, mỗi thay đổi marketing lại cần developer deploy.

Mục tiêu là chọn content boundary phản ánh reuse và ownership thật, không biến mỗi đoạn text thành block riêng.

## 3. How does it work?

Typical flow:

```text
Editor changes content
  ↓
CMS version created
  ↓ publish
content repository updated
  ↓
cache invalidation/event
  ↓
next request loads fresh content
  ↓
rendered response/CDN cache
```

Có nhiều cache layers: application/content cache, rendered fragment/output cache và CDN/browser cache. Invalidation ở CMS không tự động có nghĩa edge cache đã fresh.

## 4. Practical implementation

Ví dụ content type đơn giản:

```csharp
[ContentType(
    DisplayName = "Campaign Page",
    GUID = "A9D91052-9CD4-40C0-BD72-AD5D70D7056E")]
public class CampaignPage : PageData
{
    [CultureSpecific]
    public virtual string Heading { get; set; } = string.Empty;

    public virtual ContentArea MainContent { get; set; } = null!;
}
```

Một reusable `ProductPromoBlock` nên tồn tại nếu nó có semantics/reuse riêng, không chỉ vì developer muốn tách component frontend.

Ở HTTP layer, cache headers phải phản ánh freshness requirement; publish workflow cần purge/revalidation strategy nếu CDN giữ HTML.

## 5. Real production scenario

Marketing sửa legal text trên campaign page và publish. CMS backoffice hiển thị version mới nhưng public site ở một số regions vẫn trả content cũ 20 phút.

Application cache đã invalidated đúng; culprit là CDN TTL không có purge/revalidation integration với publish flow.

## 6. Failure scenario & troubleshooting

**Symptom** → editor thấy Published version mới, một số users vẫn thấy old content.

**Evidence** → origin response mới nhưng CDN response có `Age` cao/cache hit.

**Hypothesis** → stale edge cache, không phải CMS persistence failure.

**Diagnosis** → so sánh CMS version, origin request bypass cache, response headers và CDN cache key.

**Fix** → purge/revalidation đúng scope hoặc thiết kế TTL/cache-control phù hợp content volatility.

**Verification** → publish test content và trace từ CMS → origin → CDN → browser.

## 7. Common mistakes

* Thiết kế CMS type theo component tree hiện tại thay vì editorial/business semantics.
* Tạo quá nhiều micro-blocks làm editor workflow khó dùng.
* Clear toàn bộ cache sau mỗi publish và tạo load spike.
* Quên multilingual/culture-specific behavior.
* Nghĩ publish trong CMS đồng nghĩa mọi cache layer ngoài CMS đã invalidated.

## 8. Alternatives

Headless CMS tách content API khỏi rendering frontend, phù hợp multi-channel nhưng tăng integration/caching concerns.

Traditional server-rendered CMS đơn giản hơn cho website tập trung một channel và editorial workflow mạnh.

## 9. Trade-offs

### Advantages

Content types rõ giúp reuse, validation và editor experience ổn định; caching cải thiện latency và origin load.

### Costs / Risks

Model migration, backward compatibility, cache invalidation và editor complexity tăng khi schema phát triển.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Page/Block là content model có lifecycle, không chỉ ViewModel.

### Middle

Biết tạo content type, render và xử lý culture/basic caching.

### Senior

Thiết kế reusable boundaries, migration, publish/cache behavior và troubleshoot stale content xuyên layers.

### Technical Lead / Architect

Quyết định traditional vs headless/composable boundary, content ownership, caching strategy và upgrade path của CMS platform.

## 11. Key takeaway

* Content model nên phản ánh editorial semantics, không sao chép máy móc frontend component tree.
* CMS publish và CDN freshness là hai lifecycle khác nhau.
* Cache invalidation cần được thiết kế xuyên CMS → application → CDN → browser.
