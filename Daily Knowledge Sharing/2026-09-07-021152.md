# 1. async / await internals và ThreadPool starvation trong .NET

## 1. What is it?

`async / await` trong C# không có nghĩa là “tạo thêm thread”. Mental model đúng hơn là: compiler biến method thành một state machine; khi gặp một asynchronous operation chưa hoàn tất, method trả quyền điều khiển cho caller và đăng ký continuation để chạy tiếp khi operation hoàn tất.

Điều này đặc biệt hiệu quả với I/O-bound work như HTTP, database, file hoặc queue. Trong thời gian chờ I/O, request không cần giữ một worker thread.

## 2. Why does it exist?

Nếu một ASP.NET Core request dùng blocking I/O, worker thread bị giữ trong lúc chờ network hoặc database. Khi traffic tăng, số thread bị giữ tăng theo, ThreadPool phải tạo thêm thread chậm dần và toàn hệ thống có thể rơi vào ThreadPool starvation.

Asynchronous I/O cho phép một số lượng thread nhỏ hơn phục vụ nhiều request đang chờ I/O.

## 3. How does it work?

Luồng đơn giản:

```text
HTTP Request
   |
   v
Controller
   |
   v
await db.ExecuteAsync()
   |
   +--> I/O đang chờ -> thread được trả về ThreadPool
   |
I/O hoàn tất
   |
   v
continuation được schedule
   |
   v
response
```

Khi compiler gặp `await`, nó lưu state hiện tại vào state machine. Nếu `Task` đã complete thì chạy tiếp đồng bộ; nếu chưa thì method trả về một incomplete `Task` và continuation được đăng ký.

## 4. Practical implementation

```csharp
public async Task<IResult> GetOrderAsync(
    Guid id,
    OrderDbContext db,
    CancellationToken cancellationToken)
{
    var order = await db.Orders
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new
        {
            x.Id,
            x.Status,
            x.Total
        })
        .SingleOrDefaultAsync(cancellationToken);

    return order is null
        ? Results.NotFound()
        : Results.Ok(order);
}
```

Điểm quan trọng không phải chỉ thêm `async`, mà là toàn bộ call chain phải thực sự asynchronous.

## 5. Real production scenario

Một API e-commerce gọi SQL Server và hai external APIs. Nếu mỗi request dùng `.Result` hoặc `.Wait()`, 500 request đồng thời có thể giữ hàng trăm worker threads trong lúc chờ network.

Khi đổi sang `await` xuyên suốt call chain, thread được giải phóng trong thời gian chờ I/O, throughput tăng và tail latency ổn định hơn.

## 6. Failure scenario & troubleshooting

**Symptom**  
API p95 tăng mạnh, CPU chưa cao nhưng request queue dài.

**Evidence**  
ThreadPool queue length tăng, số active threads tăng liên tục, traces cho thấy nhiều request chờ external dependency.

**Hypothesis**  
Có sync-over-async hoặc blocking I/O.

**Diagnosis**  
Tìm `.Result`, `.Wait()`, `Task.Run` không cần thiết, synchronous database/network APIs.

**Fix**  
Chuyển call chain sang async end-to-end và truyền `CancellationToken`.

**Verification**  
So sánh throughput, ThreadPool queue length và p95/p99 sau thay đổi.

## 7. Common mistakes

* Dùng `.Result` hoặc `.Wait()` trong request path.
* Dùng `Task.Run` để “biến I/O thành async”.
* Không truyền `CancellationToken`.
* Giả định async luôn nhanh hơn cho CPU-bound work.
* Tạo quá nhiều tasks song song rồi overload database hoặc external API.

## 8. Alternatives

* CPU-bound work: cân nhắc bounded parallelism hoặc background worker.
* I/O-bound work: ưu tiên native async APIs.
* Long-running work: queue + Worker Service hoặc Azure Functions thường phù hợp hơn request thread.

## 9. Trade-offs

### Advantages

* Tăng scalability cho I/O-heavy systems.
* Giảm worker thread bị block.
* Hỗ trợ cancellation và graceful shutdown tốt hơn.

### Costs / Risks

* Call chain phức tạp hơn nếu cancellation, retries và exceptions không được quản lý tốt.
* Parallel async quá mức có thể phá downstream.
* Debugging concurrency khó hơn synchronous code.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu rằng `await` không đồng nghĩa với “new thread”.

### Middle

Biết triển khai async end-to-end, dùng `CancellationToken`, tránh sync-over-async.

### Senior

Biết nhận diện ThreadPool starvation, bounded concurrency và downstream saturation.

### Technical Lead / Architect

Quyết định workload nào nên chạy trong request path, background worker hay queue; đánh giá throughput, timeout và backpressure toàn hệ thống.

## 11. Key takeaway

* Async chủ yếu giải phóng thread khi chờ I/O.
* `async` sai cách vẫn có thể gây ThreadPool starvation.
* Đo ThreadPool, dependency latency và request queue trước khi kết luận.

# 2. ASP.NET Core DI lifetimes: Singleton, Scoped, Transient và captive dependency

## 1. What is it?

ASP.NET Core DI lifetime quy định một service instance sống bao lâu:

* `Singleton`: một instance cho toàn application.
* `Scoped`: thường một instance cho mỗi HTTP request.
* `Transient`: tạo instance mới mỗi lần resolve.

Vấn đề quan trọng không phải nhớ định nghĩa, mà là lifetime ảnh hưởng trực tiếp tới thread safety, state sharing và resource ownership.

## 2. Why does it exist?

Các dependency có vòng đời khác nhau. `DbContext` nên gắn với transaction/request boundary; stateless metadata cache có thể là Singleton; lightweight stateless services có thể là Transient.

Nếu lifetime sai, bug thường chỉ xuất hiện dưới concurrency hoặc production load.

## 3. How does it work?

ASP.NET Core tạo root service provider khi application start. Mỗi request tạo một scope riêng.

```text
Root Provider
  |
  +-- Singleton
  |
  +-- Request Scope A
  |     +-- Scoped DbContext A
  |
  +-- Request Scope B
        +-- Scoped DbContext B
```

Một Singleton giữ reference tới Scoped service là captive dependency: scoped object bị kéo dài lifetime ngoài boundary dự kiến.

## 4. Practical implementation

```csharp
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddScoped<OrderDbContext>();
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddTransient<IEmailFormatter, EmailFormatter>();
```

Background service cần Scoped dependency phải tạo scope:

```csharp
public sealed class InvoiceWorker(
    IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = scopeFactory.CreateScope();
            var processor = scope.ServiceProvider
                .GetRequiredService<IInvoiceProcessor>();

            await processor.RunOnceAsync(stoppingToken);
        }
    }
}
```

## 5. Real production scenario

Một `Singleton` service vô tình inject `DbContext`. Khi nhiều request chạy đồng thời, cùng một context bị dùng cross-thread, gây tracking state corruption, concurrency exceptions hoặc memory tăng vì tracked entities không được giải phóng đúng scope.

## 6. Failure scenario & troubleshooting

**Symptom**  
Lỗi ngẫu nhiên: “A second operation was started on this context...” hoặc dữ liệu tracking bất thường.

**Evidence**  
DI graph cho thấy Singleton phụ thuộc Scoped.

**Diagnosis**  
Captive dependency.

**Fix**  
Điều chỉnh lifetime hoặc dùng `IServiceScopeFactory` tại boundary phù hợp.

**Verification**  
Load test đồng thời và theo dõi exceptions, allocations, DbContext count.

## 7. Common mistakes

* Đăng ký business service thành Singleton chỉ để “tối ưu”.
* Singleton chứa mutable state không thread-safe.
* Inject Scoped service vào Singleton.
* Tạo scope thủ công trong controller mà không cần.
* Dùng Service Locator thay cho constructor injection.

## 8. Alternatives

Nếu dependency cần state theo request, dùng Scoped. Nếu stateless và rẻ, Transient thường đủ. Singleton chỉ phù hợp khi object thực sự thread-safe và intended to be shared.

## 9. Trade-offs

### Advantages

* Lifetime đúng giúp resource ownership rõ ràng.
* Giảm accidental state sharing.
* Dễ align transaction boundary với request scope.

### Costs / Risks

* Scope creation có overhead nhỏ.
* Singleton yêu cầu thread safety.
* Lifetime graph sai tạo bug rất khó tái hiện.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu sự khác nhau giữa Singleton, Scoped và Transient.

### Middle

Biết chọn lifetime theo state/resource ownership.

### Senior

Biết phát hiện captive dependency và concurrency bugs.

### Technical Lead / Architect

Đặt lifetime conventions và boundary cho web request, background worker, messaging consumer và domain services.

## 11. Key takeaway

* Lifetime là vấn đề correctness, không chỉ performance.
* `DbContext` thường phù hợp Scoped.
* Singleton phải thread-safe và không giữ Scoped dependency.

# 3. EF Core IQueryable, query translation và projection để tránh over-fetching

## 1. What is it?

`IQueryable<T>` biểu diễn một query expression có thể được provider, như EF Core, dịch sang SQL. Query chưa chạy cho tới terminal operation như `ToListAsync`, `SingleAsync`, `CountAsync`.

Projection là việc chỉ chọn fields thực sự cần thay vì materialize toàn entity graph.

## 2. Why does it exist?

Nếu application load toàn entity rồi filter hoặc map trong memory, database trả nhiều rows/columns hơn cần thiết, tăng network, allocations và GC pressure.

Query provider cho phép đẩy computation xuống database.

## 3. How does it work?

```text
LINQ expression
   |
   v
Expression Tree
   |
   v
EF Core query translator
   |
   v
SQL
   |
   v
Database execution plan
   |
   v
Result materialization
```

Không phải mọi .NET method đều dịch được sang SQL. Translation boundary rất quan trọng.

## 4. Practical implementation

Không tốt:

```csharp
var orders = await db.Orders
    .Include(x => x.Items)
    .ToListAsync(ct);

var result = orders
    .Where(x => x.Status == OrderStatus.Open)
    .Select(x => new OrderDto(x.Id, x.Items.Count));
```

Tốt hơn:

```csharp
var result = await db.Orders
    .AsNoTracking()
    .Where(x => x.Status == OrderStatus.Open)
    .Select(x => new OrderDto(
        x.Id,
        x.Items.Count))
    .ToListAsync(ct);
```

## 5. Real production scenario

Admin screen chỉ cần 20 orders với `Id`, `CustomerName`, `Total`, nhưng code dùng `Include` cho Items, Payments, Shipments. SQL result phình lớn và có cartesian explosion.

Projection giảm dữ liệu truyền và tránh materialize graph không cần thiết.

## 6. Failure scenario & troubleshooting

**Symptom**  
Endpoint chậm và memory allocation cao.

**Evidence**  
SQL log có SELECT nhiều columns, nhiều JOINs; response chỉ dùng vài fields.

**Hypothesis**  
Over-fetching.

**Diagnosis**  
Kiểm tra generated SQL bằng `ToQueryString()` và execution plan.

**Fix**  
Projection, pagination, split query khi cần.

**Verification**  
Đo query duration, bytes transferred, allocations và p95.

## 7. Common mistakes

* Gọi `ToList()` quá sớm.
* Chuyển sang `IEnumerable` rồi filter trong memory.
* Dùng `Include` theo thói quen.
* Query entity chỉ để map sang DTO sau đó.
* Bỏ qua N+1 khi lazy loading.

## 8. Alternatives

* Raw SQL/Dapper khi query phức tạp hoặc cần tối ưu sâu.
* EF Core compiled queries trong hot path rất ổn định.
* Projection vẫn thường là lựa chọn đầu tiên với EF Core.

## 9. Trade-offs

### Advantages

* Giảm I/O và allocations.
* SQL gần use case hơn.
* Thường đơn giản hơn generic repository abstraction.

### Costs / Risks

* Projection phức tạp có thể khó đọc.
* Translation limitations phụ thuộc EF Core/provider.
* Query logic có thể leak vào application layer nếu boundary không tốt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deferred execution và terminal operations.

### Middle

Biết dùng `AsNoTracking`, projection, pagination.

### Senior

Đọc generated SQL, execution plan và phân biệt client/server evaluation.

### Technical Lead / Architect

Quyết định khi nào direct DbContext là đủ và khi nào cần domain-specific repository hoặc read-model abstraction.

## 11. Key takeaway

* Query chưa chạy cho tới terminal operation.
* Projection thường quan trọng hơn `Include`.
* Luôn kiểm tra generated SQL khi performance quan trọng.

# 4. SQL Keyset Pagination và composite index cho dữ liệu lớn

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên giá trị cuối cùng của trang trước thay vì dùng `OFFSET`.

Ví dụ với sort theo `CreatedAt DESC, Id DESC`, cursor chứa `CreatedAt` và `Id` của row cuối cùng.

## 2. Why does it exist?

`OFFSET 500000 ROWS` vẫn buộc database tìm và bỏ qua lượng lớn rows. Khi page number sâu, latency tăng.

Keyset pagination cho phép database seek gần vị trí cần đọc nếu index phù hợp.

## 3. How does it work?

```sql
SELECT TOP (50)
    Id,
    CreatedAt,
    Status
FROM Orders
WHERE
    CreatedAt < @LastCreatedAt
    OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index:

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON Orders (CreatedAt DESC, Id DESC)
INCLUDE (Status);
```

## 4. Practical implementation

Cursor DTO:

```csharp
public sealed record OrderCursor(DateTimeOffset CreatedAt, Guid Id);
```

EF Core:

```csharp
var query = db.Orders.AsNoTracking();

if (cursor is not null)
{
    query = query.Where(x =>
        x.CreatedAt < cursor.CreatedAt ||
        (x.CreatedAt == cursor.CreatedAt && x.Id.CompareTo(cursor.Id) < 0));
}

var page = await query
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id)
    .Take(50)
    .Select(x => new OrderListItem(x.Id, x.CreatedAt, x.Status))
    .ToListAsync(ct);
```

## 5. Real production scenario

Audit log có hàng chục triệu rows. UI chỉ cần “Load more”. Offset pagination chậm rõ rệt từ page vài nghìn; keyset giữ latency ổn định hơn.

## 6. Failure scenario & troubleshooting

**Symptom**  
Page sâu mất vài giây.

**Evidence**  
Execution plan cho thấy scan và nhiều rows read dù chỉ trả 50 rows.

**Hypothesis**  
Offset pagination gây work tăng tuyến tính theo page depth.

**Diagnosis**  
So sánh logical reads giữa OFFSET và keyset.

**Fix**  
Dùng stable sort key + cursor + composite index.

**Verification**  
Đo logical reads và p95 theo nhiều page depths.

## 7. Common mistakes

* Cursor chỉ dùng `CreatedAt` khi giá trị có thể trùng.
* Sort không deterministic.
* Index column order không khớp ORDER BY.
* Encode cursor nhưng client vẫn truyền page number.
* Dùng keyset khi user cần jump trực tiếp tới page 1250.

## 8. Alternatives

Offset pagination phù hợp cho dataset nhỏ hoặc UX cần page number. Keyset phù hợp “next/previous”, feeds, logs, timelines.

## 9. Trade-offs

### Advantages

* Latency ổn định hơn khi dữ liệu lớn.
* Ít I/O hơn.
* Tốt cho continuously changing datasets.

### Costs / Risks

* Không thuận tiện cho arbitrary page jump.
* Cursor contract phức tạp hơn.
* Sort key phải ổn định và unique enough.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu OFFSET và cursor khác nhau thế nào.

### Middle

Implement keyset với tie-breaker key.

### Senior

Đọc execution plan, logical reads và thiết kế composite index.

### Technical Lead / Architect

Chọn pagination contract dựa trên UX, dataset growth và consistency requirement.

## 11. Key takeaway

* Page càng sâu, OFFSET càng dễ đắt.
* Keyset cần deterministic ordering.
* Index phải phục vụ đúng access pattern.

# 5. Cosmos DB Partition Key, hot partition và Request Units

## 1. What is it?

Cosmos DB scale dữ liệu bằng partitioning. Partition key quyết định dữ liệu được phân bố và query nào có thể route hiệu quả.

Request Units (RU) là abstraction cho cost của CPU, I/O và memory cho mỗi operation.

## 2. Why does it exist?

Một distributed database không thể scale vô hạn trên một node. Partitioning chia dữ liệu ra nhiều physical partitions.

Nhưng nếu partition key không cân bằng, một partition có thể nhận phần lớn traffic và trở thành hot partition.

## 3. How does it work?

Ví dụ SaaS multi-tenant:

```json
{
  "id": "order-123",
  "tenantId": "tenant-a",
  "status": "Paid"
}
```

Nếu `/tenantId` là partition key, query có tenantId cụ thể có thể route tới partition liên quan. Query không có partition key có thể fan-out nhiều partitions và tốn RU hơn.

## 4. Practical implementation

```csharp
var response = await container.ReadItemAsync<Order>(
    id: orderId,
    partitionKey: new PartitionKey(tenantId),
    cancellationToken: ct);

Console.WriteLine(response.RequestCharge);
```

Với query:

```csharp
var definition = new QueryDefinition(
    "SELECT * FROM c WHERE c.tenantId = @tenantId AND c.status = @status")
    .WithParameter("@tenantId", tenantId)
    .WithParameter("@status", "Paid");
```

## 5. Real production scenario

Hệ thống event ingestion chọn `eventType` làm partition key. 80% events là `PageViewed`, khiến một logical partition nhận phần lớn write throughput.

Dù tổng RU provisioned cao, partition nóng vẫn bị 429.

## 6. Failure scenario & troubleshooting

**Symptom**  
429 Too Many Requests tập trung vào một workload.

**Evidence**  
RU consumption cao bất thường ở một partition key range.

**Hypothesis**  
Hot partition.

**Diagnosis**  
Phân tích cardinality, traffic distribution và top partition keys.

**Fix**  
Redesign partition key hoặc dùng synthetic key phù hợp access pattern.

**Verification**  
Theo dõi 429 rate, RU distribution và latency.

## 7. Common mistakes

* Chọn partition key có cardinality thấp.
* Chỉ nhìn data distribution mà bỏ qua traffic distribution.
* Query cross-partition thường xuyên.
* Dùng Cosmos DB giống relational database.
* Không đo `RequestCharge`.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp khi transaction relational và joins là trung tâm. MongoDB có partitioning model khác. Cosmos DB mạnh khi global distribution, predictable access pattern và horizontal scale quan trọng.

## 9. Trade-offs

### Advantages

* Horizontal scaling và global distribution mạnh.
* Low-latency access khi partition key phù hợp.
* Flexible consistency models.

### Costs / Risks

* Data model bị chi phối bởi access pattern.
* Query sai partition có thể tốn RU.
* Partition redesign về sau có thể đắt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key dùng để phân bố dữ liệu.

### Middle

Biết query kèm partition key và theo dõi RU.

### Senior

Phân tích hot partition, consistency và cross-partition cost.

### Technical Lead / Architect

Chọn data model và partition strategy dựa trên growth, traffic skew, tenant isolation và cost.

## 11. Key takeaway

* Partition key là quyết định kiến trúc, không phải field chọn ngẫu nhiên.
* Traffic skew quan trọng không kém data skew.
* Theo dõi RU và 429 bằng telemetry thực tế.

# 6. Clean Architecture: dependency direction, boundary và khi nào không nên dùng

## 1. What is it?

Clean Architecture là cách tổ chức dependency để business rules không phụ thuộc trực tiếp vào delivery mechanism, database hay framework.

Điểm cốt lõi là dependency direction và boundary, không phải số lượng project hay folder.

## 2. Why does it exist?

Nếu domain logic phụ thuộc chặt EF Core, HTTP, Azure SDK và UI, thay đổi infrastructure dễ lan vào business code, testing khó và coupling cao.

Clean Architecture cố gắng cô lập phần có tốc độ thay đổi khác nhau.

## 3. How does it work?

```text
API
 |
 v
Application
 |
 v
Domain
 ^
 |
Infrastructure
```

Infrastructure implement interfaces mà Application/Domain sở hữu. Dependency compile-time hướng vào trong; runtime vẫn có thể đi ra database/API qua inversion.

## 4. Practical implementation

Application contract:

```csharp
public interface IEmailSender
{
    Task SendAsync(string to, string subject, string body, CancellationToken ct);
}
```

Infrastructure:

```csharp
public sealed class SendGridEmailSender : IEmailSender
{
    public Task SendAsync(
        string to,
        string subject,
        string body,
        CancellationToken ct)
    {
        // external SDK call
        return Task.CompletedTask;
    }
}
```

Không cần tạo abstraction cho mọi class. Boundary nên xuất hiện khi có lý do thay đổi, testability hoặc ownership rõ ràng.

## 5. Real production scenario

Một employee platform có business rule approval phức tạp. Nếu rule nằm trong controllers và EF entities, thay đổi workflow dễ tác động API và persistence. Đưa rule vào domain/application boundary giúp isolate thay đổi.

## 6. Failure scenario & troubleshooting

**Symptom**  
Feature đơn giản cần sửa 8 projects và thêm nhiều interfaces không có giá trị.

**Evidence**  
Nhiều pass-through layers, handlers chỉ gọi repository rồi return.

**Hypothesis**  
Architecture ceremony vượt business complexity.

**Diagnosis**  
Đếm abstraction không có independent reason to change.

**Fix**  
Collapse layers không cần thiết; giữ boundary quan trọng.

**Verification**  
Feature mới có ít boilerplate hơn nhưng dependency rules vẫn rõ.

## 7. Common mistakes

* Biến architecture thành folder template.
* Interface cho mọi class.
* Generic Repository trên EF Core chỉ để “đúng pattern”.
* Domain layer không có domain logic.
* MediatR được dùng như mục tiêu thay vì implementation choice.

## 8. Alternatives

Layered Architecture đơn giản thường đủ cho CRUD-heavy systems. Modular Monolith hữu ích khi business boundaries lớn hơn. Hexagonal/Onion có cùng tư tưởng dependency inversion với cách diễn đạt khác.

## 9. Trade-offs

### Advantages

* Change isolation tốt hơn.
* Business logic dễ test.
* Framework/infrastructure coupling giảm.

### Costs / Risks

* Boilerplate và abstraction cost.
* Team phải hiểu boundary.
* Có thể overengineer hệ thống đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu business logic không nên bị trộn ngẫu nhiên với infrastructure.

### Middle

Biết đặt dependency direction và implement interfaces ở đúng layer.

### Senior

Biết loại bỏ abstraction vô ích và giữ transaction boundary rõ.

### Technical Lead / Architect

Quyết định hệ thống có đủ business complexity để cần kiến trúc này hay Layered Architecture đơn giản hơn là phù hợp.

## 11. Key takeaway

* Architecture là boundary và dependency direction.
* Không phải mọi project cần Clean Architecture đầy đủ.
* Abstraction phải trả lời được: nó đang cô lập thay đổi nào?

# 7. Azure Blob Storage: large-file streaming, SAS và failure handling

## 1. What is it?

Azure Blob Storage là object storage cho file, media, backup và large binary content. Với file lớn, application nên stream thay vì load toàn bộ file vào memory.

SAS cho phép cấp quyền giới hạn theo resource, action và thời gian mà không lộ storage account key.

## 2. Why does it exist?

Database không phải nơi lý tưởng cho large binary objects trong nhiều workload. Blob Storage tách binary storage khỏi transactional data store và scale độc lập.

Streaming giúp tránh memory spike khi nhiều uploads/downloads đồng thời.

## 3. How does it work?

```text
Client
  |
  | upload stream
  v
ASP.NET Core
  |
  | Stream
  v
Azure Blob Storage
```

Hoặc client upload trực tiếp bằng SAS để giảm bandwidth đi qua application.

## 4. Practical implementation

Server-side streaming:

```csharp
public async Task UploadAsync(
    Stream input,
    string blobName,
    CancellationToken ct)
{
    var blob = containerClient.GetBlobClient(blobName);

    await blob.UploadAsync(
        input,
        overwrite: false,
        cancellationToken: ct);
}
```

Tuyệt đối tránh:

```csharp
using var ms = new MemoryStream();
await file.CopyToAsync(ms);
await blob.UploadAsync(new BinaryData(ms.ToArray()));
```

với file lớn.

## 5. Real production scenario

CMS cho phép upload video 500 MB. Nếu mỗi request copy file vào `byte[]`, chỉ vài upload đồng thời có thể tạo memory pressure và LOH allocations lớn.

Streaming giữ memory footprint thấp hơn nhiều.

## 6. Failure scenario & troubleshooting

**Symptom**  
Process memory tăng mạnh khi nhiều uploads.

**Evidence**  
GC heap/LOH tăng, allocation profile chứa large byte arrays.

**Hypothesis**  
Application buffering toàn file.

**Diagnosis**  
Review upload path và profiling allocations.

**Fix**  
Streaming, chunked upload hoặc direct-to-Blob bằng SAS.

**Verification**  
Load test nhiều upload đồng thời và theo dõi working set/GC.

## 7. Common mistakes

* Đưa storage account key vào config/source.
* SAS lifetime quá dài.
* SAS cho quyền rộng hơn cần thiết.
* Buffer toàn file vào memory.
* Không validate content type/size và filename metadata.

## 8. Alternatives

* Direct upload bằng SAS: giảm load app nhưng client flow phức tạp hơn.
* App-mediated upload: kiểm soát tốt hơn nhưng tốn bandwidth/compute.
* Database BLOB chỉ hợp lý cho một số consistency requirements đặc biệt.

## 9. Trade-offs

### Advantages

* Scale storage độc lập.
* Chi phí object storage thường hợp lý.
* Hỗ trợ lifecycle management.

### Costs / Risks

* Cần xử lý orphaned blobs và metadata consistency.
* SAS misconfiguration là security risk.
* Network failures yêu cầu retry/resume strategy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Blob Storage dùng cho object/binary content.

### Middle

Biết stream upload/download và dùng SAS hạn chế.

### Senior

Thiết kế retry, chunking, idempotency, cleanup orphan blobs.

### Technical Lead / Architect

Quyết định direct upload hay app-mediated upload, ownership metadata, retention và security model.

## 11. Key takeaway

* File lớn nên stream, không buffer toàn bộ.
* SAS phải least privilege và short-lived.
* Blob metadata và transactional metadata cần consistency strategy riêng.

# 8. Kubernetes readiness/liveness probes và deployment troubleshooting

## 1. What is it?

`readinessProbe` trả lời: “Pod có sẵn sàng nhận traffic không?”

`livenessProbe` trả lời: “Process có còn sống theo nghĩa cần restart không?”

Hai probe giải quyết hai failure modes khác nhau.

## 2. Why does it exist?

Process có thể chạy nhưng chưa sẵn sàng vì đang warm-up, migration, load cache hoặc dependency tạm thời unavailable.

Nếu readiness fail, Pod nên bị loại khỏi Service endpoints. Nếu liveness fail, kubelet có thể restart container.

## 3. How does it work?

```text
Deployment
  |
  v
Pod starts
  |
  +--> readiness fail -> không nhận traffic
  |
  +--> readiness pass -> nhận traffic
  |
  +--> liveness fail -> container restart
```

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, name: "sql");

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = _ => true
});
```

Kubernetes:

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10

livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  initialDelaySeconds: 20
  periodSeconds: 20
```

## 5. Real production scenario

Sau deployment, app cần 20 giây để load configuration và initialize caches. Nếu traffic đến ngay, users nhận 500. Readiness giữ Pod ngoài traffic cho tới khi app thực sự ready.

## 6. Failure scenario & troubleshooting

**Symptom**  
Pod rơi vào restart loop dù app chỉ bị database outage tạm thời.

**Evidence**  
Liveness endpoint kiểm tra database và fail theo database.

**Hypothesis**  
Liveness phụ thuộc external dependency.

**Diagnosis**  
Inspect probe config và container events.

**Fix**  
Liveness chỉ kiểm tra process health; dependency readiness đưa sang readiness probe.

**Verification**  
Mô phỏng database outage; Pod không restart storm nhưng được rút khỏi traffic khi cần.

## 7. Common mistakes

* Liveness gọi database/external API.
* Readiness luôn trả 200.
* Timeout quá ngắn.
* Probe endpoint thực hiện expensive work.
* Không xem `kubectl describe pod` và events khi CrashLoopBackOff.

## 8. Alternatives

Trên Azure App Service có health checks khác về operational model. Containers không dùng Kubernetes vẫn cần equivalent readiness/startup strategy ở load balancer/reverse proxy.

## 9. Trade-offs

### Advantages

* Giảm traffic vào instance chưa ready.
* Tự recovery process bị treo.
* Hỗ trợ rolling deployment an toàn hơn.

### Costs / Risks

* Probe sai có thể tạo restart storm.
* Dependency health semantics phải được thiết kế cẩn thận.
* Tăng operational configuration.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt readiness và liveness.

### Middle

Implement health endpoints và probe config.

### Senior

Debug CrashLoopBackOff, restart storms và dependency-induced failures.

### Technical Lead / Architect

Định nghĩa health semantics, rollout policy và dependency degradation strategy.

## 11. Key takeaway

* Readiness quyết định nhận traffic.
* Liveness quyết định restart.
* Đừng để dependency outage biến thành restart storm.

# 9. OAuth 2.0 / OpenID Connect: token validation đúng trong ASP.NET Core

## 1. What is it?

OAuth 2.0 là authorization framework; OpenID Connect bổ sung identity layer. Trong API, access token thường là bearer credential đại diện quyền truy cập đã được cấp.

API không chỉ “decode JWT”; nó phải validate cryptographically và kiểm tra issuer, audience, lifetime cùng authorization policy.

## 2. Why does it exist?

Nếu mỗi application tự xử lý username/password và token riêng, attack surface và credential management tăng mạnh.

Identity Provider tập trung authentication; APIs dựa trên trusted tokens nhưng vẫn phải validate và authorize đúng.

## 3. How does it work?

```text
User
  |
  v
Identity Provider
  |
  | access token
  v
Client
  |
  | Authorization: Bearer ...
  v
API
  |
  +--> signature
  +--> issuer
  +--> audience
  +--> expiry
  +--> claims/policies
```

## 4. Practical implementation

```csharp
builder.Services
    .AddAuthentication("Bearer")
    .AddJwtBearer("Bearer", options =>
    {
        options.Authority = configuration["Auth:Authority"];
        options.Audience = configuration["Auth:Audience"];
        options.RequireHttpsMetadata = true;
    });

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("orders.read", policy =>
        policy.RequireClaim("scope", "orders.read"));
});
```

Endpoint:

```csharp
app.MapGet("/orders", GetOrders)
   .RequireAuthorization("orders.read");
```

## 5. Real production scenario

API chạy local tốt nhưng Production trả 401. Local token được phát cho audience `api-dev`, Production API kỳ vọng `api-prod`.

Token signature đúng nhưng audience mismatch, nên rejection là chính xác.

## 6. Failure scenario & troubleshooting

**Symptom**  
401 sau deployment.

**Evidence**  
Authentication logs cho thấy invalid audience hoặc issuer.

**Hypothesis**  
Environment-specific identity config sai.

**Diagnosis**  
So sánh `iss`, `aud`, expiry và metadata endpoint.

**Fix**  
Sửa authority/audience/configuration, không tắt validation.

**Verification**  
Test token đúng/sai audience và đảm bảo negative tests fail.

## 7. Common mistakes

* Chỉ base64-decode JWT rồi tin claims.
* Disable audience validation để “fix” 401.
* Nhầm Authentication với Authorization.
* Dùng role khi permission/scope phù hợp hơn.
* Log raw access token vào telemetry.
* Access token lifetime quá dài.

## 8. Alternatives

Cookie authentication phù hợp server-rendered web apps. Managed Identity phù hợp service-to-service Azure resources. API key đơn giản hơn nhưng yếu hơn về delegated authorization và lifecycle.

## 9. Trade-offs

### Advantages

* Centralized identity.
* Standards-based interoperability.
* Fine-grained scopes/claims.

### Costs / Risks

* Configuration phức tạp.
* Token leakage là serious security incident.
* Clock skew, issuer/audience và key rotation phải được xử lý đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt authentication và authorization.

### Middle

Configure JwtBearer và policies.

### Senior

Debug issuer/audience/key rotation, token lifetime và least privilege.

### Technical Lead / Architect

Chọn identity flow, token boundaries, service-to-service model và permission taxonomy.

## 11. Key takeaway

* JWT decode không phải JWT validation.
* API phải kiểm tra signature, issuer, audience và lifetime.
* Authorization policy phải tách khỏi authentication.

# 10. Performance Engineering với p50 / p95 / p99 và bottleneck localization

## 1. What is it?

Latency percentile mô tả phân bố thời gian phản hồi.

* p50: median.
* p95: 95% requests nhanh hơn giá trị này.
* p99: 99% requests nhanh hơn giá trị này.

Average latency có thể che tail latency rất xấu.

## 2. Why does it exist?

Một API có average 120 ms vẫn có thể có 1% requests mất 5 giây. Với traffic lớn, 1% là rất nhiều users.

Percentiles giúp nhìn experience của phần chậm trong distribution.

## 3. How does it work?

Giả sử 1000 requests:

* p50 = 80 ms
* p95 = 220 ms
* p99 = 1800 ms

Pattern này gợi ý một subset requests gặp dependency timeout, GC pause, lock contention hoặc cold path.

Investigation loop:

```text
Symptom
  -> measure
  -> localize bottleneck
  -> hypothesis
  -> test
  -> change
  -> measure again
```

## 4. Practical implementation

OpenTelemetry metrics có thể ghi histogram:

```csharp
private static readonly Meter Meter = new("Orders.Api");
private static readonly Histogram<double> Duration =
    Meter.CreateHistogram<double>("orders.request.duration", "ms");

var sw = Stopwatch.StartNew();
try
{
    await handler(ct);
}
finally
{
    Duration.Record(sw.Elapsed.TotalMilliseconds);
}
```

Ở Application Insights / metrics backend, phân tích percentile theo endpoint, dependency, status code hoặc tenant.

## 5. Real production scenario

Sau release, average latency tăng nhẹ từ 110 lên 130 ms nhưng p99 tăng từ 700 ms lên 4.5 s. Trace analysis cho thấy một new enrichment call tới third-party API đôi lúc timeout 4 giây.

Nếu chỉ nhìn average, regression có thể bị bỏ qua.

## 6. Failure scenario & troubleshooting

**Symptom**  
Users báo “thỉnh thoảng rất chậm”.

**Evidence**  
p50 ổn, p99 tăng mạnh.

**Hypothesis**  
Tail dependency latency.

**Diagnosis**  
Trace slowest requests, group theo dependency span.

**Fix**  
Timeout hợp lý, fallback hoặc bỏ dependency khỏi critical path.

**Verification**  
So sánh p95/p99 trước và sau; không chỉ average.

## 7. Common mistakes

* Chỉ xem average.
* Optimize CPU khi bottleneck là database I/O.
* Thêm cache trước khi đo access pattern.
* Load test không giống production.
* Không segment metrics theo endpoint/tenant/dependency.
* Đo latency nhưng không đo error rate và throughput.

## 8. Alternatives

Profiling phù hợp CPU/allocation bottleneck. Execution plan phù hợp SQL. Distributed tracing phù hợp cross-service latency. Metrics cho biết “có vấn đề”, profiling/tracing/logs giúp trả lời “vì sao”.

## 9. Trade-offs

### Advantages

* Percentiles phản ánh tail behavior.
* Dễ đặt SLO thực tế hơn average.
* Hỗ trợ regression detection.

### Costs / Risks

* High-cardinality labels có thể đắt.
* Percentile aggregation phải hiểu backend semantics.
* Metrics không thay thế traces và profiling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu average và percentile khác nhau.

### Middle

Biết đọc p50/p95/p99 và correlate với errors/dependencies.

### Senior

Localize bottleneck bằng metrics, traces, profiler, SQL plan.

### Technical Lead / Architect

Đặt performance budget/SLO và quyết định optimization dựa trên business impact thay vì cảm giác.

## 11. Key takeaway

* Average latency có thể che tail latency.
* p95/p99 rất quan trọng cho production.
* Tối ưu đúng bắt đầu bằng measurement và bottleneck localization.
