# 1. C# `System.Text.Json` source generation: giảm reflection/runtime metadata cost mà không đánh đổi contract correctness

## 1. What is it?

`System.Text.Json` source generation cho phép serializer metadata được tạo ở compile time thay vì phải khám phá type structure chủ yếu ở runtime bằng reflection.

Mental model:

```text
Reflection-based serialization
runtime -> inspect type -> build metadata -> serialize

Source-generated serialization
compile time -> generate metadata/code
runtime -> use generated contract -> serialize
```

Mục tiêu không chỉ là “serialize nhanh hơn”. Nó còn giúp giảm runtime metadata discovery, phù hợp hơn với trimming/Native AOT và làm serialization contract explicit hơn.

## 2. Why does it exist?

Serializer cần biết property nào tồn tại, tên JSON là gì, converter nào áp dụng và constructor nào dùng. Reflection giải quyết linh hoạt nhưng có cost runtime và khó hơn khi linker trimming code không được tham chiếu tĩnh.

Với API throughput cao hoặc application Native AOT, generated metadata có thể giảm startup/CPU/allocation và tránh một số reflection compatibility problem.

## 3. How does it work?

Khai báo context:

```csharp
[JsonSerializable(typeof(OrderResponse))]
[JsonSerializable(typeof(List<OrderResponse>))]
public partial class ApiJsonContext : JsonSerializerContext
{
}
```

Source generator tạo implementation cho `ApiJsonContext`. Runtime sau đó dùng metadata đã biết:

```csharp
var json = JsonSerializer.Serialize(
    order,
    ApiJsonContext.Default.OrderResponse);
```

Trong ASP.NET Core, context có thể được thêm vào JSON options để framework dùng generated metadata cho endpoint serialization.

## 4. Practical implementation

```csharp
builder.Services.ConfigureHttpJsonOptions(options =>
{
    options.SerializerOptions.TypeInfoResolverChain.Insert(
        0,
        ApiJsonContext.Default);
});

public sealed record OrderResponse(
    Guid Id,
    decimal Total,
    string Status);

[JsonSerializable(typeof(OrderResponse))]
[JsonSerializable(typeof(OrderResponse[]))]
internal partial class ApiJsonContext : JsonSerializerContext;
```

Không nên coi source generation là lý do để serialize domain entity trực tiếp. Public DTO contract vẫn cần tách khỏi persistence/domain model khi compatibility yêu cầu.

## 5. Real production scenario

Một high-throughput catalog API trả hàng nghìn JSON responses/giây. Profiling cho thấy serialization chiếm CPU đáng kể sau khi database query đã được tối ưu. Team chuyển hot DTOs sang source-generated metadata và đo được giảm CPU/allocation.

Lợi ích này có ý nghĩa vì bottleneck đã được đo. Với CRUD API vài chục RPS, complexity thêm vào có thể không đáng kể.

## 6. Failure scenario & troubleshooting

**Symptom** → một DTO mới serialize fail hoặc field biến mất sau khi chuyển sang AOT/trimming.

**Evidence** → generated context không chứa type/converter cần thiết; runtime fallback bị vô hiệu hoặc reflection metadata đã bị trim.

**Hypothesis** → serialization contract chưa được khai báo đầy đủ trong source-generation graph.

**Diagnosis** → kiểm tra generated context, serializer options, custom converters và integration tests trên publish mode giống Production.

**Fix** → đăng ký đúng root types/converters; tránh dựa vào runtime-discovered polymorphism nếu deployment mode không support an toàn.

**Verification** → contract tests cho request/response JSON, đặc biệt enum, nullable, polymorphism và backward compatibility.

## 7. Common mistakes

- Chuyển toàn bộ codebase sang source generation mà không benchmark.
- Serialize EF entities trực tiếp chỉ vì serializer nhanh hơn.
- Không test publish trimmed/AOT artifact.
- Quên custom converter hoặc polymorphic subtype.
- Đánh đồng performance optimization với API contract design.

## 8. Alternatives

Reflection-based `System.Text.Json` là default tốt cho đa số application. Newtonsoft.Json vẫn hữu ích nếu project phụ thuộc feature/legacy behavior đặc thù, nhưng cần cân nhắc migration và performance.

## 9. Trade-offs

### Advantages

- Giảm runtime metadata discovery.
- Tốt hơn cho trimming/Native AOT.
- Có thể giảm CPU/allocation trên serialization hot path.

### Costs / Risks

- Cần maintain serialization context.
- Dynamic/polymorphic scenarios phức tạp hơn.
- Lợi ích nhỏ nếu serialization không phải bottleneck.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu serializer phải có metadata về type; JSON không tự “xuất hiện” từ object.

### Middle

Biết cấu hình source-generated context và viết contract tests.

### Senior

Đo serialization CPU/allocation, hiểu trimming/AOT và converter/polymorphism implications.

### Technical Lead / Architect

Quyết định deployment/performance requirement có thật sự cần generated serialization hay reflection default đơn giản hơn đã đủ.

## 11. Key takeaway

- Source generation là optimization + deployment compatibility tool, không phải API design pattern.
- DTO contract vẫn quan trọng hơn serializer mechanism.
- Chỉ tối ưu serialization sau khi measurement chứng minh nó có ý nghĩa.

# 2. ASP.NET Core `IOptionsMonitor<T>` và runtime configuration reload: dynamic config không đồng nghĩa mọi setting đều nên thay đổi live

## 1. What is it?

Options Pattern map configuration thành strongly typed object. `IOptionsMonitor<T>` cung cấp current value và notification khi configuration provider hỗ trợ reload.

Mental model:

```text
configuration source
 -> change token
 -> options rebind
 -> IOptionsMonitor.CurrentValue
 -> optional OnChange callback
```

Nó khác `IOptions<T>` thường biểu diễn một value ổn định cho application lifetime và `IOptionsSnapshot<T>` tạo snapshot theo scope/request.

## 2. Why does it exist?

Một số setting cần thay đổi mà không restart application: feature tuning, timeout, threshold, display behavior. Nhưng restart mọi instance chỉ để đổi một threshold nhỏ có thể không cần thiết.

Ngược lại, runtime reload cho database schema, identity authority hoặc invariant-critical config có thể tạo mixed behavior giữa requests và rất khó rollback/debug.

## 3. How does it work?

```csharp
public sealed class CheckoutOptions
{
    public int MaxItems { get; init; } = 100;
    public TimeSpan Timeout { get; init; } = TimeSpan.FromSeconds(5);
}

builder.Services
    .AddOptions<CheckoutOptions>()
    .BindConfiguration("Checkout")
    .ValidateDataAnnotations()
    .ValidateOnStart();
```

Consumer:

```csharp
public sealed class CheckoutService(
    IOptionsMonitor<CheckoutOptions> options)
{
    public bool CanAccept(int itemCount)
        => itemCount <= options.CurrentValue.MaxItems;
}
```

`OnChange` callback nên nhẹ và thread-safe; nó không phải nơi chạy migration hoặc network workflow phức tạp.

## 4. Practical implementation

```csharp
public sealed class TimeoutPolicy : IDisposable
{
    private readonly IDisposable _subscription;
    private volatile TimeSpan _timeout;

    public TimeoutPolicy(IOptionsMonitor<CheckoutOptions> monitor)
    {
        _timeout = monitor.CurrentValue.Timeout;
        _subscription = monitor.OnChange(x => _timeout = x.Timeout);
    }

    public TimeSpan CurrentTimeout => _timeout;

    public void Dispose() => _subscription.Dispose();
}
```

Cần quyết định một operation dài dùng config tại lúc bắt đầu hay đọc lại giữa chừng. Thường snapshot tại operation boundary dễ reasoning hơn.

## 5. Real production scenario

Một third-party API bắt đầu chậm. Ops đổi timeout từ 2 lên 5 giây qua configuration. Một số requests mới dùng timeout mới, requests đang chạy giữ policy cũ.

Nếu business không định nghĩa semantics này, support có thể thấy behavior “lúc 2 giây, lúc 5 giây” và tưởng deployment không đồng nhất.

## 6. Failure scenario & troubleshooting

**Symptom** → config file/secret đã thay nhưng application behavior không đổi, hoặc thay đổi giữa requests không nhất quán.

**Evidence** → provider không support reload, `reloadOnChange` không bật, instance/container không nhận file update, hoặc service cache option value trong constructor.

**Hypothesis** → misunderstanding về lifetime/provider semantics.

**Diagnosis** → log safe config version, kiểm tra provider/change token và cách options được inject.

**Fix** → chọn đúng `IOptions`, `IOptionsSnapshot`, `IOptionsMonitor`; restart nếu config bản chất cần immutable startup semantics.

**Verification** → integration test thay config và quan sát behavior mới trên operation boundary xác định.

## 7. Common mistakes

- Dùng `IOptionsMonitor` cho mọi setting chỉ vì “linh hoạt”.
- Đọc secret/config trong hot loop liên tục.
- `OnChange` chạy side effect lớn.
- Không validate value mới.
- Không định nghĩa config version trong incident/debugging.

## 8. Alternatives

Feature flag service phù hợp hơn cho controlled rollout/targeting. Restart-based immutable config đơn giản và dễ reasoning hơn cho nhiều infrastructure settings.

## 9. Trade-offs

### Advantages

- Thay đổi selected settings không cần redeploy/restart.
- Strong typing và validation.

### Costs / Risks

- Runtime state thay đổi làm reproducibility khó hơn.
- Multi-instance propagation có thể lệch thời gian.
- Callback/lifetime semantics cần thread safety.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu configuration cũng có lifetime giống dependency khác.

### Middle

Biết chọn `IOptions`/`Snapshot`/`Monitor` và validate config.

### Senior

Thiết kế operation-boundary semantics, multi-instance propagation và telemetry config version.

### Technical Lead / Architect

Quy định setting nào được phép live reload và setting nào phải immutable/restart để giữ system predictability.

## 11. Key takeaway

- Dynamic config là capability, không phải default requirement.
- Chọn options lifetime theo semantics của setting.
- Config thay đổi phải observable, validated và có ownership rõ ràng.

# 3. EF Core savepoints trong transaction: rollback một phần unit of work mà không phá toàn bộ transaction

## 1. What is it?

Savepoint là checkpoint bên trong database transaction. Có thể rollback tới savepoint thay vì rollback toàn bộ transaction.

Mental model:

```text
BEGIN TRANSACTION
  Step A
  SAVEPOINT before_B
  Step B
  failure
  ROLLBACK TO before_B
  alternative B
COMMIT
```

EF Core có thể sử dụng savepoints khi `SaveChanges` chạy trong transaction đã tồn tại, tùy provider/capability.

## 2. Why does it exist?

Có workflow cần giữ các thay đổi trước đó trong transaction nhưng thử một phần operation có thể thất bại recoverably. Rollback toàn bộ sẽ làm mất work đã hợp lệ; commit một phần tùy tiện lại phá atomicity mong muốn.

Savepoint cung cấp rollback scope nhỏ hơn mà vẫn nằm trong một transaction database.

## 3. How does it work?

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

await PersistHeaderAsync(db, ct);
await tx.CreateSavepointAsync("BeforeLines", ct);

try
{
    await PersistLinesAsync(db, ct);
}
catch (DbUpdateException)
{
    await tx.RollbackToSavepointAsync("BeforeLines", ct);
    // choose recoverable alternative
}

await tx.CommitAsync(ct);
```

Savepoint không giải quyết external side effects. Nếu trước savepoint đã gửi email/payment HTTP call, rollback DB không thể “undo” side effect đó.

## 4. Practical implementation

Một import batch có thể xử lý record optional trong cùng transaction:

```csharp
await using var transaction = await db.Database.BeginTransactionAsync(ct);

order.MarkImported();
await db.SaveChangesAsync(ct);

await transaction.CreateSavepointAsync("BeforeOptionalMetadata", ct);

try
{
    db.Metadata.AddRange(metadata);
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateException ex) when (CanIgnoreMetadata(ex))
{
    await transaction.RollbackToSavepointAsync(
        "BeforeOptionalMetadata",
        ct);
}

await transaction.CommitAsync(ct);
```

Business phải thực sự cho phép metadata failure không invalidate order import.

## 5. Real production scenario

Migration/import service ghi core employee record và optional legacy metadata. Một malformed metadata row vi phạm constraint. Nếu toàn bộ transaction rollback, hàng nghìn valid core records phải xử lý lại.

Savepoint có thể phù hợp nếu business xác nhận metadata optional và recovery/audit rõ ràng.

## 6. Failure scenario & troubleshooting

**Symptom** → sau một `SaveChanges` failure, transaction không còn usable hoặc state tracker không khớp DB state.

**Evidence** → provider behavior/savepoint support, tracked entities vẫn ở state modified/added dù DB đã rollback một phần.

**Hypothesis** → rollback database state nhưng application state chưa được reconcile.

**Diagnosis** → inspect transaction logs, EF ChangeTracker states và provider limitations.

**Fix** → reload/detach/reconcile affected entities; giữ savepoint scope nhỏ; không tiếp tục transaction nếu failure không recoverable.

**Verification** → integration test trên database provider thật, không chỉ InMemory provider.

## 7. Common mistakes

- Dùng savepoint để che transaction quá lớn.
- Rollback DB nhưng quên tracked state.
- Giả định mọi provider support giống nhau.
- External side effect nằm trong “rollback-able” reasoning.
- Catch mọi DB error rồi tiếp tục transaction.

## 8. Alternatives

Transaction ngắn riêng biệt thường đơn giản hơn nếu atomicity xuyên steps không bắt buộc. Saga/compensation phù hợp khi workflow vượt qua nhiều services/resources.

## 9. Trade-offs

### Advantages

- Fine-grained rollback trong một transaction.
- Có thể recovery một phần operation.

### Costs / Risks

- Transaction sống lâu hơn, giữ locks/resources.
- Application state reconciliation phức tạp.
- Không áp dụng cho remote side effects.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transaction có thể có checkpoint nhưng commit cuối vẫn là boundary durability chính.

### Middle

Biết tạo/rollback savepoint và test provider thật.

### Senior

Reason về locks, tracked state, recoverable vs unrecoverable error.

### Technical Lead / Architect

Quyết định workflow có thật sự cần savepoint hay nên chia transaction/workflow đơn giản hơn.

## 11. Key takeaway

- Savepoint thu nhỏ rollback scope, không thu nhỏ mọi side effect.
- Database state và EF tracked state phải được reconcile sau rollback.
- Chỉ dùng khi partial recovery có business semantics rõ ràng.

# 4. SQL Server statistics và cardinality estimation: execution plan có thể xấu đi dù index không thay đổi

## 1. What is it?

Statistics mô tả distribution của data trên column/index key để SQL Server ước lượng số rows sẽ đi qua từng operator. Cardinality estimate ảnh hưởng join type, index access, memory grant và operator order.

Mental model:

```text
query predicate
 -> statistics
 -> estimated rows
 -> optimizer cost model
 -> execution plan
 -> actual I/O/CPU/latency
```

## 2. Why does it exist?

Optimizer không thể chạy mọi possible plan để biết plan nào tốt nhất. Nó dựa vào metadata/statistics để estimate cost.

Nếu estimate 100 rows nhưng thực tế 5 triệu rows, nested loops + key lookups từng rất hợp lý ở 100 rows có thể trở thành disaster ở 5 triệu.

## 3. How does it work?

Statistics thường chứa histogram/density information. Data thay đổi theo thời gian; auto-update statistics cố duy trì đủ freshness nhưng không bảo đảm mọi distribution change được phản ánh ngay theo workload đặc thù.

Ví dụ:

```sql
SELECT Id, CustomerId, Total
FROM Orders
WHERE Status = @Status;
```

Nếu `Pending` trước đây chiếm 1% nhưng sau business change chiếm 60%, plan dựa trên estimate cũ có thể không còn phù hợp.

## 4. Practical implementation

Điều tra bằng Actual Execution Plan, Query Store và statistics metadata.

```sql
DBCC SHOW_STATISTICS ('dbo.Orders', 'IX_Orders_Status');
```

Không update statistics mù quáng như ritual. Trước hết xem:

- estimated vs actual rows;
- logical reads;
- operator choice;
- histogram phù hợp predicate không;
- data skew và parameter pattern.

## 5. Real production scenario

Sau campaign, bảng Orders tăng từ 5 lên 40 triệu rows trong vài ngày. Không có deployment code/database index nào, nhưng p95 endpoint tăng từ 150 ms lên 4 giây.

Actual plan cho thấy estimate thấp hơn actual hàng trăm lần. Root cause là data distribution thay đổi, khiến cached plan và statistics không còn đại diện workload mới.

## 6. Failure scenario & troubleshooting

**Symptom** → query đột nhiên chậm sau data growth, không có code release.

**Evidence** → estimated/actual rows lệch lớn; Query Store cho thấy plan regression; statistics age/modification lớn.

**Hypothesis** → cardinality estimate sai do stale/skewed statistics hoặc parameter-sensitive workload.

**Diagnosis** → compare plan versions, histogram, representative parameter values.

**Fix** → update statistics khi evidence support; cải thiện index/query shape; cân nhắc strategy cho skewed parameters.

**Verification** → benchmark representative distributions, theo dõi logical reads và plan stability.

## 7. Common mistakes

- “Có index thì query phải nhanh”.
- Rebuild mọi index để vô tình update statistics rồi nghĩ fragmentation là root cause.
- Clear plan cache toàn server.
- Chỉ test với development data ít rows.
- Bỏ qua data skew giữa tenants/status values.

## 8. Alternatives

Query rewrite, filtered index, partitioning hoặc workload separation có thể tốt hơn update statistics liên tục nếu data distribution bản chất cực skewed.

## 9. Trade-offs

### Advantages

Statistics giúp optimizer chọn plan tốt mà không cần developer hard-code execution strategy.

### Costs / Risks

Estimate luôn là approximation. Update/compile quá thường xuyên cũng có CPU/operational cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index chỉ là một input; optimizer cần ước lượng bao nhiêu rows sẽ được đọc.

### Middle

Đọc estimated vs actual rows và logical reads.

### Senior

Phân tích histogram, skew, Query Store và plan regression.

### Technical Lead / Architect

Thiết kế production performance process dựa trên representative data, không chỉ schema/code review.

## 11. Key takeaway

- Execution plan phụ thuộc data distribution, không chỉ SQL text/index.
- Estimate sai có thể đổi toàn bộ physical strategy.
- Production performance phải quan sát plan + data evolution.

# 5. Elasticsearch synchronization từ primary database: xử lý indexing failure mà không biến search index thành source of truth

## 1. What is it?

Trong kiến trúc search phổ biến, SQL/database chính sở hữu transactional state; Elasticsearch giữ read/search projection được tối ưu cho full-text, filtering và relevance.

```text
Primary DB
   -> change capture/event/outbox
   -> indexing worker
   -> Elasticsearch
   -> Search API
```

Elasticsearch projection có thể lag hoặc rebuild; business truth không nên phụ thuộc duy nhất vào nó.

## 2. Why does it exist?

SQL rất tốt cho transactions/constraints nhưng không tối ưu cho analyzer, inverted index và relevance scoring. Elasticsearch giải quyết search workload nhưng đổi lấy eventual consistency và một synchronization pipeline mới.

## 3. How does it work?

Khi Product được update:

1. DB transaction commit Product.
2. Durable change intent được ghi/publish.
3. Indexer transform data thành search document.
4. Elasticsearch index document.
5. Search API thấy version mới sau một khoảng lag.

Nếu bước 4 fail, DB vẫn đúng; pipeline phải retry/recover mà không yêu cầu user sửa lại product chỉ để trigger indexing.

## 4. Practical implementation

Document nên mang version/update timestamp:

```csharp
public sealed record ProductSearchDocument(
    Guid Id,
    long Version,
    string Name,
    string Description,
    string Category);
```

Indexer idempotent theo document ID/version. Bulk indexing cần inspect per-item failures, vì HTTP bulk request có thể trả thành công transport nhưng một số items fail.

## 5. Real production scenario

CMS publish product title mới. SQL commit thành công nhưng Elasticsearch cluster reject indexing tạm thời vì disk watermark. Website detail page đọc DB thấy title mới, search results vẫn title cũ.

Đây là expected eventual-consistency failure mode, nhưng phải có lag metric/retry/rebuild path.

## 6. Failure scenario & troubleshooting

**Symptom** → product tồn tại nhưng search không tìm thấy hoặc data cũ nhiều giờ.

**Evidence** → DB version mới hơn index document; indexing backlog/retry tăng; bulk item errors.

**Hypothesis** → synchronization pipeline stalled hoặc poison document mapping failure.

**Diagnosis** → correlate entity ID từ DB → outbox/message → worker trace → Elasticsearch response.

**Fix** → retry transient failure, DLQ permanent mapping/data failure, reindex affected entity/range, sửa mapping pipeline.

**Verification** → measure indexing lag distribution và compare sampled DB/index versions.

## 7. Common mistakes

- Dual-write DB + Elasticsearch trực tiếp trong request và hy vọng cả hai luôn thành công.
- Dùng Elasticsearch làm transactional source of truth.
- Không có replay/rebuild mechanism.
- Bulk API nhưng không inspect item-level error.
- Search freshness requirement không được định nghĩa.

## 8. Alternatives

Database full-text search đủ cho workload nhỏ/đơn giản và giảm operational component. Managed search service có thể giảm ops burden nhưng eventual consistency/sync ownership vẫn tồn tại.

## 9. Trade-offs

### Advantages

- Search capability và scale tốt hơn cho text/relevance workload.
- Read model độc lập với transactional schema.

### Costs / Risks

- Eventual consistency.
- Indexing pipeline, replay, monitoring và mapping migrations.
- Thêm một distributed system phải vận hành.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DB và search index có thể tạm thời khác nhau.

### Middle

Implement idempotent indexing và inspect bulk failures.

### Senior

Thiết kế replay, lag telemetry, mapping/version migration và recovery.

### Technical Lead / Architect

Quyết định search requirement có đủ lớn để justify Elasticsearch và định nghĩa freshness/recovery SLO.

## 11. Key takeaway

- Search index nên là rebuildable projection.
- Sync failure phải recover được mà không sửa lại business data.
- Indexing lag là production metric, không phải implementation detail.

# 6. Outbox Pattern với EF Core + Azure Service Bus: commit business data và message intent trong cùng transaction

## 1. What is it?

Outbox Pattern ghi business state và message-to-be-published vào cùng database transaction. Một worker riêng đọc Outbox rồi publish lên broker.

```text
HTTP request
 -> DB transaction
    -> Orders
    -> OutboxMessages
 -> COMMIT

Publisher worker
 -> read Outbox
 -> Service Bus
 -> mark published
```

## 2. Why does it exist?

Naive dual-write:

```text
Save order to SQL
Publish OrderCreated to Service Bus
```

có failure window:

- DB commit thành công, publish fail → downstream không biết order tồn tại.
- Publish thành công, DB rollback → downstream xử lý event cho state không tồn tại.

Một local ACID transaction không thể atomically commit cả SQL và remote broker theo cách đơn giản.

## 3. How does it work?

Trong cùng `SaveChanges` transaction, application insert domain data + outbox row. Sau commit, publisher gửi message.

Publisher có thể crash sau khi broker nhận message nhưng trước khi mark published. Vì vậy duplicate delivery vẫn có thể xảy ra; consumer phải idempotent.

## 4. Practical implementation

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

var order = Order.Create(request.CustomerId);
db.Orders.Add(order);

db.OutboxMessages.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    Type = "OrderCreated",
    AggregateId = order.Id,
    Payload = JsonSerializer.Serialize(
        new { order.Id, order.CustomerId }),
    OccurredAtUtc = DateTime.UtcNow
});

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Publisher nên batch, claim rows an toàn giữa nhiều instances và có retry/backoff.

## 5. Real production scenario

Checkout tạo order thành công nhưng Service Bus gặp transient outage 30 giây. Không có Outbox, API đã trả 201 nhưng inventory workflow không bao giờ nhận event.

Với Outbox, event intent vẫn nằm durable trong SQL và publisher gửi sau khi broker phục hồi.

## 6. Failure scenario & troubleshooting

**Symptom** → Outbox table tăng liên tục, downstream không nhận events.

**Evidence** → oldest unpublished age tăng; publisher errors; Service Bus telemetry.

**Hypothesis** → publisher stalled, poison payload hoặc auth/network failure.

**Diagnosis** → metric backlog/age, inspect representative row + broker response.

**Fix** → restore publisher, quarantine permanent failures, replay idempotently.

**Verification** → fault injection broker outage và xác nhận backlog tăng rồi drain sau recovery.

## 7. Common mistakes

- Gọi broker bên trong DB transaction và giữ transaction mở chờ network.
- Nghĩ Outbox tạo exactly-once delivery.
- Không cleanup/archive published rows.
- Nhiều publisher instances cùng publish row mà không claim strategy.
- Consumer không idempotent.

## 8. Alternatives

Nếu application không cần asynchronous integration, direct synchronous call có thể đơn giản hơn. Change Data Capture có thể phát hiện DB changes nhưng semantics business event khác raw row changes.

## 9. Trade-offs

### Advantages

- Loại bỏ atomicity gap giữa business commit và message intent.
- Survive broker outage.
- Replay/audit tốt hơn.

### Costs / Risks

- Thêm table + publisher + cleanup + monitoring.
- Eventual delivery, không immediate guarantee.
- Duplicate vẫn tồn tại.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu “save DB rồi publish” có khoảng failure giữa hai bước.

### Middle

Implement outbox row cùng transaction và publisher retry.

### Senior

Thiết kế claim/concurrency, deduplication, cleanup, poison message và observability.

### Technical Lead / Architect

Chỉ đưa Outbox vào nơi cross-boundary event reliability thực sự cần; không dùng messaging complexity cho mọi CRUD operation.

## 11. Key takeaway

- Outbox giải quyết atomic message intent, không tạo exactly-once processing.
- Publisher backlog phải được monitor như production queue.
- Consumer idempotency vẫn bắt buộc.

# 7. Azure Service Bus Sessions: giữ ordering theo business key mà không serialize toàn bộ queue

## 1. What is it?

Service Bus Session gom messages có cùng `SessionId` thành một ordered stream logic. Một consumer giữ session lock và xử lý messages của session đó tuần tự.

Ví dụ:

```text
SessionId = Order-123
  Event 1: Created
  Event 2: Paid
  Event 3: Shipped
```

Các order khác nhau có session khác và vẫn có thể xử lý song song.

## 2. Why does it exist?

Global FIFO làm throughput thấp vì mọi message phải serialize. Nhưng nhiều business workflow chỉ cần ordering **trong cùng aggregate/customer/workflow**, không cần ordering toàn hệ thống.

Sessions tạo scoped ordering + stateful conversation semantics theo business key.

## 3. How does it work?

```text
Queue
 ├─ Session A -> consumer 1 -> ordered
 ├─ Session B -> consumer 2 -> ordered
 └─ Session C -> consumer 3 -> ordered
```

Broker cấp session lock. Nếu consumer chết hoặc lock expire, session có thể được consumer khác nhận lại. At-least-once semantics vẫn còn, nên ordered không đồng nghĩa duplicate-free.

## 4. Practical implementation

Producer:

```csharp
var message = new ServiceBusMessage(payload)
{
    MessageId = eventId.ToString(),
    SessionId = orderId.ToString()
};

await sender.SendMessageAsync(message, ct);
```

Consumer cần xử lý nhanh hơn lock/session policy hoặc renew lock phù hợp; external calls dài vẫn cần timeout/idempotency.

## 5. Real production scenario

Order workflow nhận `PaymentConfirmed` và `OrderCancelled` gần nhau. Nếu xử lý concurrent không có version/order guard, final state phụ thuộc race.

Session theo `OrderId` giúp serialize events của một order trong khi hàng nghìn orders khác vẫn parallel.

## 6. Failure scenario & troubleshooting

**Symptom** → một vài sessions backlog rất sâu trong khi queue tổng thể vẫn có consumer rảnh.

**Evidence** → hot SessionId có processing time lớn; session lock lost; repeated delivery.

**Hypothesis** → hot session hoặc poison message đang block ordered stream.

**Diagnosis** → metric backlog theo business key nếu available/application telemetry; inspect delivery count và processing duration.

**Fix** → xử lý poison message/DLQ, giảm work trong handler, chọn session key granular hợp lý.

**Verification** → load test một hot customer/order family cùng nhiều normal sessions.

## 7. Common mistakes

- Dùng một `SessionId` cho toàn tenant/system → mất parallelism.
- Nghĩ session loại duplicate.
- Handler chờ external API hàng phút.
- Không thiết kế poison message trong ordered stream.
- Chọn key thay đổi giữa events của cùng workflow.

## 8. Alternatives

Optimistic concurrency/version check trong database có thể đủ nếu strict broker ordering không cần. Partitioned Kafka-style stream phù hợp throughput/event-log workloads khác. Plain Service Bus queue đơn giản hơn nếu operations độc lập.

## 9. Trade-offs

### Advantages

- Ordering theo business scope.
- Parallelism giữa scopes.
- Hữu ích cho stateful workflow.

### Costs / Risks

- Hot sessions giới hạn throughput.
- Session-aware consumer/config phức tạp hơn.
- Lock/retry/idempotency vẫn phải xử lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ordering requirement thường thuộc một entity/workflow, không phải toàn queue.

### Middle

Set stable `SessionId` và xử lý session consumer đúng.

### Senior

Phân tích hot session, lock, duplicate và poison-message interaction.

### Technical Lead / Architect

Quyết định ordering có thật sự là requirement hay invariant/versioning ở consumer đơn giản hơn và scale tốt hơn.

## 11. Key takeaway

- Sessions cung cấp scoped ordering, không exactly-once.
- Session key quyết định cả correctness lẫn parallelism.
- Ordered stream cần poison-message recovery rõ ràng.

# 8. `.NET Framework` → modern .NET incremental modernization: giảm migration risk thay vì rewrite toàn hệ thống

## 1. What is it?

Incremental modernization là di chuyển một hệ thống legacy theo từng boundary/capability thay vì rewrite “big bang”. Mục tiêu là giảm risk, tạo feedback sớm và giữ business chạy trong quá trình chuyển đổi.

```text
Legacy .NET Framework
 -> isolate dependencies
 -> modernize shared libraries/contracts
 -> extract/replace selected edge
 -> migrate hosting/data incrementally
 -> retire legacy pieces
```

## 2. Why does it exist?

Rewrite toàn bộ thường đánh giá thấp behavior ẩn trong production: edge cases, batch jobs, integrations, auth rules và operational knowledge.

Một system 8 năm có thể có hàng nghìn “requirements” chỉ tồn tại trong code và user behavior. Rewrite làm mất hidden knowledge cùng lúc.

## 3. How does it work?

Bắt đầu inventory:

- .NET Framework-only libraries;
- System.Web dependencies;
- WCF/legacy auth;
- EF6/data access;
- IIS-specific behavior;
- Windows-only APIs;
- third-party packages;
- deployment/configuration.

Sau đó chọn seam có business value và dependency thấp để migrate trước.

## 4. Practical implementation

Shared business library có thể multi-target tạm thời nếu hợp lý:

```xml
<TargetFrameworks>net48;net8.0</TargetFrameworks>
```

Nhưng multi-target không phải mục tiêu vĩnh viễn. Nó là migration bridge.

HTTP boundary có thể dùng strangler-style routing:

```text
Reverse Proxy
  /legacy/* -> old ASP.NET app
  /api/new/* -> ASP.NET Core .NET 8
```

Contract tests bảo vệ behavior giữa old/new implementations.

## 5. Real production scenario

Enterprise portal .NET Framework 4.8 có 120 projects. Team estimate rewrite 18 tháng. Sau 9 tháng chưa có production value và requirements tiếp tục thay đổi.

Incremental plan thay vào đó đưa authentication adapter, reporting API và background processing sang modern .NET từng phần, giảm risk và tạo production learning sớm.

## 6. Failure scenario & troubleshooting

**Symptom** → migration branch sống nhiều tháng, merge conflict tăng, không feature nào production.

**Evidence** → scope “migrate everything” không có independently deployable milestones.

**Hypothesis** → migration strategy theo technical completeness thay vì business slices.

**Diagnosis** → map dependency graph, production traffic và change frequency.

**Fix** → tạo migration seams nhỏ, contract tests, compatibility layer tạm thời, release từng slice.

**Verification** → mỗi milestone có traffic/feature thật chạy modern stack và rollback path.

## 7. Common mistakes

- Rewrite vì code “xấu” mà không định lượng business risk/value.
- Upgrade framework + architecture + database + UX cùng lúc.
- Mang nguyên legacy abstractions sang modern .NET dù constraint cũ đã mất.
- Không test deployment/IIS/auth/config differences.
- Compatibility bridge trở thành permanent architecture mà không retirement plan.

## 8. Alternatives

In-place framework upgrade đủ nếu system ổn định và không cần architectural change lớn. Big-bang rewrite chỉ hợp lý khi system nhỏ, boundaries rõ và replacement risk thấp.

## 9. Trade-offs

### Advantages

- Risk nhỏ hơn, feedback production sớm.
- Có rollback và business continuity.
- Học dependency thực tế từng bước.

### Costs / Risks

- Tạm thời vận hành hai stacks.
- Adapter/bridge code tăng complexity.
- Migration kéo dài cần governance để không dừng giữa đường.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu framework migration không chỉ là đổi target framework.

### Middle

Port library/API và viết compatibility tests.

### Senior

Phân tích runtime/hosting/package/data differences và migration seam.

### Technical Lead / Architect

Chọn sequence dựa trên business value, dependency graph, rollback và retirement strategy; không mặc định rewrite là sạch hơn về tổng chi phí.

## 11. Key takeaway

- Modernization là risk-management program, không phải syntax upgrade.
- Migrate theo deployable business slices khi có thể.
- Compatibility layer phải có ngày nghỉ hưu.

# 9. Webhook signature verification + replay protection: authenticated payload vẫn chưa đủ nếu request cũ có thể phát lại

## 1. What is it?

Webhook verification xác nhận request thực sự được tạo bởi provider có shared secret/public key và payload không bị sửa. Replay protection ngăn attacker lấy một webhook hợp lệ cũ rồi gửi lại để trigger side effect lần nữa.

```text
HTTP body + timestamp + signature
 -> verify cryptographically
 -> verify freshness
 -> deduplicate event ID
 -> process idempotently
```

## 2. Why does it exist?

Webhook endpoint thường public Internet. Chỉ “khó đoán URL” hoặc check API key header là không đủ.

Ngay cả HMAC signature hợp lệ cũng không chứng minh request **mới**. Nếu captured request có thể replay, payment/order state có thể bị apply nhiều lần.

## 3. How does it work?

Provider thường ký raw body cùng timestamp:

```text
signature = HMAC(secret, timestamp + "." + rawBody)
```

Consumer:

1. đọc raw body;
2. parse timestamp;
3. reject quá cũ;
4. compute signature;
5. constant-time compare;
6. check provider event ID đã xử lý chưa;
7. process idempotently.

## 4. Practical implementation

```csharp
var payload = await new StreamReader(request.Body)
    .ReadToEndAsync(ct);

var expected = ComputeHmac(secret, timestamp, payload);
var supplied = Convert.FromHexString(signatureHeader);

if (!CryptographicOperations.FixedTimeEquals(expected, supplied))
    return Results.Unauthorized();

if (Math.Abs((DateTimeOffset.UtcNow - eventTime).TotalMinutes) > 5)
    return Results.Unauthorized();

if (await inbox.ExistsAsync(eventId, ct))
    return Results.Ok();
```

Phải verify đúng raw bytes theo provider spec; deserialize rồi serialize lại có thể thay whitespace/order và làm signature sai.

## 5. Real production scenario

Payment provider gửi `payment.succeeded`. Attacker lấy request log bị leak chứa body + signature và replay 20 lần.

Nếu endpoint chỉ verify signature, mọi replay đều cryptographically valid. Idempotency theo provider event ID/business payment ID mới ngăn duplicate fulfillment.

## 6. Failure scenario & troubleshooting

**Symptom** → signature fail chỉ Production hoặc duplicate fulfillment xảy ra dù signature verify đúng.

**Evidence** → reverse proxy/body transformation, clock skew, raw body mismatch, cùng event ID nhiều requests.

**Hypothesis** → verify sai byte representation hoặc thiếu replay/dedup layer.

**Diagnosis** → log hash/event ID/timestamp an toàn, không log secret/full sensitive payload; compare provider docs/examples.

**Fix** → verify raw body, clock tolerance hợp lý, event dedup + idempotent state transition.

**Verification** → test modified body, wrong secret, expired timestamp và replay same valid event.

## 7. Common mistakes

- Secret đặt trong source code.
- Dùng normal string equality cho MAC.
- Verify object đã deserialize/re-serialize.
- Không có timestamp tolerance.
- Chỉ dedup trong memory, mất khi restart/multi-instance.

## 8. Alternatives

mTLS/private networking có thể tăng trust boundary nhưng không thay message-level authenticity/idempotency hoàn toàn. Polling provider API tránh public webhook nhưng tăng latency/quota/load.

## 9. Trade-offs

### Advantages

- Xác thực source/integrity.
- Replay protection giảm duplicate side effect.

### Costs / Risks

- Key rotation và clock handling.
- Cần durable dedup storage.
- Provider signature schemes khác nhau.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTPS bảo vệ transport nhưng webhook vẫn cần xác thực sender/message.

### Middle

Implement HMAC verification, timestamp validation và event dedup.

### Senior

Thiết kế key rotation, raw-body handling, multi-instance idempotency và incident telemetry.

### Technical Lead / Architect

Chuẩn hóa webhook security library/policy và quyết định retention window của dedup state theo business impact.

## 11. Key takeaway

- Valid signature không tự ngăn replay.
- Verify raw payload đúng provider specification.
- Side-effect endpoint phải idempotent và dedup durable.

# 10. TypeScript discriminated unions cho API state: loại bỏ impossible UI states thay vì quản lý nhiều boolean rời rạc

## 1. What is it?

Discriminated union biểu diễn một tập states hữu hạn bằng property phân biệt (`kind`, `status`, ...). TypeScript compiler sau đó narrow type theo state.

Thay vì:

```ts
let loading = false;
let error: string | null = null;
let data: Order[] | null = null;
```

có thể dùng:

```ts
type OrdersState =
  | { kind: 'idle' }
  | { kind: 'loading' }
  | { kind: 'loaded'; data: Order[] }
  | { kind: 'error'; message: string };
```

## 2. Why does it exist?

Nhiều booleans cho phép impossible states:

```text
loading = true
error != null
data != null
```

UI phải đoán precedence. Đây là state-modeling problem, không phải rendering problem.

Union encode invariant ngay trong type system: `loaded` bắt buộc có data; `error` bắt buộc có message; `loading` không có stale error trừ khi model chủ đích cho phép.

## 3. How does it work?

```ts
function render(state: OrdersState) {
  switch (state.kind) {
    case 'idle':
      return 'Ready';
    case 'loading':
      return 'Loading...';
    case 'loaded':
      return `${state.data.length} orders`;
    case 'error':
      return state.message;
  }
}
```

Compiler narrow `state` trong từng branch. Có thể thêm exhaustive check để compile fail khi state mới chưa được handle.

## 4. Practical implementation

Vue composable:

```ts
const state = ref<OrdersState>({ kind: 'idle' });

async function loadOrders(signal?: AbortSignal) {
  state.value = { kind: 'loading' };

  try {
    const response = await fetch('/api/orders', { signal });
    if (!response.ok) throw new Error(`HTTP ${response.status}`);

    const data: Order[] = await response.json();
    state.value = { kind: 'loaded', data };
  } catch (error) {
    if (error instanceof DOMException && error.name === 'AbortError')
      return;

    state.value = {
      kind: 'error',
      message: error instanceof Error ? error.message : 'Unknown error'
    };
  }
}
```

## 5. Real production scenario

Order dashboard có loading spinner, stale data và error banner. Với ba independent refs, race condition khiến spinner biến mất nhưng old error vẫn còn dù request mới success.

State machine explicit làm transition rõ:

```text
idle -> loading -> loaded
              -> error
```

Nếu cần stale-while-refresh, tạo state riêng thay vì “ngầm” kết hợp booleans.

## 6. Failure scenario & troubleshooting

**Symptom** → UI hiển thị spinner + error + data cùng lúc hoặc button enable ở state không hợp lệ.

**Evidence** → nhiều independent flags được update ở các async callbacks khác nhau.

**Hypothesis** → state space không được model explicit.

**Diagnosis** → liệt kê valid business/UI states và transitions; tìm combinations không nên tồn tại.

**Fix** → union/state machine; centralize transition; cancel/ignore stale async responses.

**Verification** → component tests cho từng state và race/abort scenario.

## 7. Common mistakes

- Union nhưng lại thêm optional fields cho mọi state, mất type safety.
- `as any` để bỏ compiler warning.
- Không exhaustive-check switch.
- Nhét toàn app vào một giant state union.
- Dùng state machine phức tạp cho component chỉ có hai trivial states.

## 8. Alternatives

Simple refs/booleans đủ cho UI nhỏ. Dedicated state-machine library phù hợp workflow nhiều transitions/concurrent states. Server-state libraries có cache/loading/error model riêng cho data fetching.

## 9. Trade-offs

### Advantages

- Impossible states bị loại ở compile time.
- Rendering và tests rõ hơn.
- Refactor state transition an toàn hơn.

### Costs / Risks

- Thêm type/transition ceremony.
- Union lớn có thể khó maintain nếu boundary sai.
- Không tự giải quyết network race nếu transition logic vẫn sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu UI state nên biểu diễn những tình huống thực sự có thể tồn tại.

### Middle

Dùng discriminated union + exhaustive switch cho async views.

### Senior

Model stale/refresh/cancel/error transitions và race conditions rõ ràng.

### Technical Lead / Architect

Chọn mức state-machine complexity phù hợp; giữ server state, form state và workflow state ở boundary dễ ownership/test.

## 11. Key takeaway

- Nhiều booleans dễ tạo state không hợp lệ.
- Type system có thể encode UI invariants hữu ích.
- Modeling state tốt giảm cả runtime bug lẫn test complexity.
