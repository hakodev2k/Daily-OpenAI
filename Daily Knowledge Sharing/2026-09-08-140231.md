# 1. `Span<T>` và `Memory<T>` trong .NET: tối ưu buffer mà không phá lifetime safety

## 1. What is it?

`Span<T>` là một `ref struct` biểu diễn một vùng nhớ liên tục mà không nhất thiết phải tạo array mới. Nó có thể trỏ tới array, stack-allocated memory, unmanaged memory hoặc slice của một buffer hiện có. `Memory<T>` có mental model tương tự nhưng có lifetime linh hoạt hơn và có thể đi qua async boundary.

Mental model quan trọng:

```text
Existing buffer
┌──────────────────────────────┐
│ A │ B │ C │ D │ E │ F │ G │ H │
└──────────────────────────────┘
        └──── Span slice ────┘
```

Thay vì copy dữ liệu sang array/string mới, ta tạo một view lên vùng nhớ đã tồn tại.

`Span<T>` ưu tiên synchronous, stack-confined processing. `Memory<T>` phù hợp khi buffer cần sống qua `await`, được giữ bởi object hoặc truyền giữa async components.

## 2. Why does it exist?

Nhiều thao tác parsing, serialization, protocol handling và text processing trước đây tạo rất nhiều allocation chỉ để lấy substring hoặc sub-array.

Ví dụ:

```csharp
var prefix = bytes.Skip(0).Take(16).ToArray();
```

Operation này tạo collection machinery và allocation mới. Với hot path chạy hàng triệu lần, allocation nhỏ tích lũy thành GC pressure đáng kể.

`Span<T>` tồn tại để cho phép xử lý dữ liệu theo slice mà không copy. Nhưng nó không phải API cần dùng ở mọi business service; lợi ích chỉ rõ khi workload thực sự allocation-sensitive.

## 3. How does it work?

`Span<T>` chứa reference tới vùng nhớ cùng length. Vì nó là `ref struct`, CLR/C# áp các restriction để tránh span sống lâu hơn memory mà nó tham chiếu.

Một consequence quan trọng: `Span<T>` không thể được lưu trong field của class thông thường và không thể sống qua `await`.

Flow điển hình:

```text
byte[] input
   ↓
AsSpan()
   ↓
Slice without copy
   ↓
Parse synchronously
```

Nếu cần async:

```text
Memory<byte>
   ↓
await stream.ReadAsync(memory)
   ↓
memory.Span
   ↓
synchronous parse
```

## 4. Practical implementation

Ví dụ parse một protocol header cố định:

```csharp
public readonly record struct MessageHeader(int Version, int PayloadLength);

public static MessageHeader ParseHeader(ReadOnlySpan<byte> buffer)
{
    if (buffer.Length < 8)
        throw new ArgumentException("Header requires 8 bytes.", nameof(buffer));

    var version = BinaryPrimitives.ReadInt32LittleEndian(buffer[..4]);
    var payloadLength = BinaryPrimitives.ReadInt32LittleEndian(buffer.Slice(4, 4));

    return new MessageHeader(version, payloadLength);
}
```

Async buffer reading nên dùng `Memory<byte>`:

```csharp
public static async Task<int> ReadChunkAsync(
    Stream stream,
    Memory<byte> buffer,
    CancellationToken cancellationToken)
{
    return await stream.ReadAsync(buffer, cancellationToken);
}
```

Sau `await`, synchronous processing có thể dùng:

```csharp
var span = buffer.Span[..bytesRead];
```

## 5. Real production scenario

Một ingestion service đọc hàng nghìn message/second từ binary feed. Mỗi message có header 32 bytes và payload vài KB.

Version cũ dùng `ToArray()`, `Substring()` và temporary buffers ở nhiều bước. Allocation profiler cho thấy hàng GB allocation/hour dù live memory không lớn.

Thay selective hot paths bằng `ReadOnlySpan<byte>` giảm temporary allocation và Gen0 GC frequency. Business code còn lại vẫn dùng collection/string bình thường để giữ maintainability.

## 6. Failure scenario & troubleshooting

**Symptom** → team refactor rộng sang `Span<T>` nhưng latency hầu như không giảm, code phức tạp hơn.

**Evidence** → profiler cho thấy bottleneck là network và database; allocation từ parsing chỉ chiếm phần rất nhỏ.

**Hypothesis** → tối ưu micro-allocation ở layer không phải bottleneck.

**Diagnosis** → so sánh allocation profile, GC pause, CPU samples trước và sau.

**Fix** → giữ span chỉ ở parsing/serialization hot path đã có evidence; revert abstraction không mang lại value.

**Verification** → benchmark production-like workload với allocations/op, throughput và p99.

## 7. Common mistakes

* Dùng `Span<T>` vì nghĩ mọi allocation đều xấu.
* Cố giữ `Span<T>` qua `await` thay vì dùng `Memory<T>`.
* Trả span trỏ vào memory có lifetime không còn hợp lệ.
* Tối ưu buffer trước khi đo GC pressure.
* Đưa low-level memory API vào business layer khiến code khó đọc.

## 8. Alternatives

* Array/string thông thường: đơn giản nhất, phù hợp phần lớn business code.
* `ArrayPool<T>`: hữu ích khi cần buffer lớn tái sử dụng.
* `Memory<T>`: dùng khi cần async/heap-friendly ownership.
* Pipelines (`System.IO.Pipelines`): phù hợp high-throughput streaming protocol phức tạp.

## 9. Trade-offs

### Advantages

* Giảm copy và temporary allocation.
* Tốt cho parser/serializer hot path.
* Có thể giảm GC pressure và tăng throughput.

### Costs / Risks

* API lifetime phức tạp hơn.
* Debugging khó hơn với slicing/ownership.
* Dễ over-optimize nơi không cần thiết.
* Có thể làm abstraction leak vào business code.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Span<T>` là view trên memory, không phải container mới.

### Middle

Biết dùng `ReadOnlySpan<T>`, `Slice`, `Memory<T>` và tránh copy không cần thiết.

### Senior

Biết đọc allocation profile, đánh giá lifetime, async boundary, GC impact và benchmark.

### Technical Lead / Architect

Quyết định hot path nào xứng đáng dùng low-level memory abstraction và giữ phần còn lại của codebase đơn giản.

## 11. Key takeaway

* `Span<T>` tối ưu copy/allocation, không phải universal performance switch.
* `Memory<T>` phù hợp hơn khi buffer phải qua async boundary.
* Chỉ đưa low-level memory API vào hot path đã có measurement.

# 2. ASP.NET Core middleware ordering: authentication, authorization, exception handling và routing phải đứng đúng vị trí

## 1. What is it?

ASP.NET Core middleware pipeline là chuỗi component xử lý request theo thứ tự đăng ký. Mỗi middleware có thể xử lý request trước khi gọi `next`, rồi xử lý response khi control flow quay ngược lại.

Mental model:

```text
Request
  ↓
Exception Handler
  ↓
Routing
  ↓
Authentication
  ↓
Authorization
  ↓
Endpoint
  ↑
Response flows back through pipeline
```

Ordering là behavior, không chỉ style. Cùng các middleware nhưng đặt sai vị trí có thể làm authentication không chạy đúng, exception không được capture hoặc static response bị policy xử lý không cần thiết.

## 2. Why does it exist?

Cross-cutting concerns như logging, security, compression, error handling và routing cần áp dụng quanh endpoint mà không duplicate code ở từng controller.

Middleware giải quyết điều đó bằng pipeline composition. Nhưng vì mỗi component phụ thuộc context do component trước tạo ra, thứ tự trở thành contract.

Ví dụ authorization cần biết endpoint metadata. Routing phải chạy trước authorization. Authentication thường phải thiết lập `HttpContext.User` trước authorization.

## 3. How does it work?

Middleware hoạt động theo nested call stack:

```text
A before
  B before
    Endpoint
  B after
A after
```

Một exception handler ở đầu pipeline có thể catch exception từ downstream. Nếu đặt nó sau endpoint dispatch, exception đã vượt khỏi khả năng của handler.

Một cấu hình phổ biến:

```csharp
app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
```

Trong modern ASP.NET Core, endpoint routing được framework tích hợp linh hoạt hơn trước, nhưng nguyên tắc dependency ordering vẫn giữ nguyên.

## 4. Practical implementation

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddAuthentication()
    .AddJwtBearer();

builder.Services.AddAuthorization();
builder.Services.AddProblemDetails();

var app = builder.Build();

app.UseExceptionHandler();
app.UseHttpsRedirection();

app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();

app.Run();
```

Custom correlation middleware nên được đặt đủ sớm để mọi downstream log có correlation ID:

```csharp
app.Use(async (context, next) =>
{
    var correlationId = context.Request.Headers["X-Correlation-ID"].FirstOrDefault()
        ?? Guid.NewGuid().ToString("N");

    context.Response.Headers["X-Correlation-ID"] = correlationId;

    using (logger.BeginScope(new Dictionary<string, object>
    {
        ["CorrelationId"] = correlationId
    }))
    {
        await next();
    }
});
```

## 5. Real production scenario

Một enterprise API deploy version mới và bắt đầu trả 403 cho endpoint vốn hoạt động bình thường. Local tests qua anonymous routes vẫn pass.

Root cause: custom middleware chạy authorization logic trước khi authentication middleware populate claims. Security configuration tồn tại đầy đủ nhưng ordering sai khiến request bị evaluate với anonymous principal.

## 6. Failure scenario & troubleshooting

**Symptom** → user có JWT hợp lệ nhưng API trả 401/403.

**Evidence** → token validation event không xuất hiện trước authorization logs; `HttpContext.User.Identity.IsAuthenticated` là false trong policy.

**Hypothesis** → middleware ordering sai hoặc endpoint bypass pipeline mong đợi.

**Diagnosis** → inspect `Program.cs`, endpoint mapping và middleware placement; thêm trace log ở từng stage.

**Fix** → đặt authentication trước authorization, đảm bảo routing/endpoint metadata sẵn sàng trước policy evaluation.

**Verification** → integration test request pipeline với authenticated và unauthenticated cases.

## 7. Common mistakes

* Đặt `UseAuthorization()` trước `UseAuthentication()`.
* Đặt exception handler quá muộn.
* Viết custom middleware giữ scoped service trong singleton field sai cách.
* Middleware luôn đọc/rewind request body gây overhead trên mọi request.
* Logging full body chứa secrets/PII.
* Không test pipeline thực mà chỉ unit-test controller.

## 8. Alternatives

* Filters: phù hợp MVC/action-specific behavior.
* Endpoint filters: phù hợp Minimal APIs/endpoint-level cross-cutting logic.
* DelegatingHandler: phù hợp outbound `HttpClient` pipeline, không phải inbound HTTP.
* Domain/application decorator: phù hợp business cross-cutting concern không nên phụ thuộc HTTP.

## 9. Trade-offs

### Advantages

* Composition rõ cho cross-cutting concern.
* Áp dụng nhất quán toàn application.
* Có thể quan sát request lifecycle end-to-end.

### Costs / Risks

* Order dependency dễ bị bỏ sót.
* Custom middleware quá nhiều làm pipeline khó reason.
* Một middleware đắt có thể ảnh hưởng toàn bộ traffic.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request đi qua middleware tuần tự và response quay ngược lại.

### Middle

Biết đặt routing/authentication/authorization/error handler đúng thứ tự và viết middleware đơn giản.

### Senior

Phân tích ordering dependency, body buffering, scoped lifetime, security và performance impact.

### Technical Lead / Architect

Quyết định concern nào thuộc HTTP middleware, concern nào thuộc application/domain layer để tránh pipeline trở thành “god layer”.

## 11. Key takeaway

* Middleware ordering là runtime behavior.
* Authentication và authorization không interchangeable.
* Cross-cutting concern phải được đặt ở đúng architectural boundary.

# 3. EF Core compiled queries: giảm query compilation overhead nhưng chỉ đáng dùng ở hot path đã đo được

## 1. What is it?

EF Core phải biến LINQ expression tree thành query model rồi translate thành SQL. EF có internal query caching, nhưng trong một số hot path rất lặp lại, compiled query có thể giảm thêm overhead của bước query processing bằng cách compile delegate trước.

Mental model:

```text
Normal repeated query
LINQ expression → cache lookup / compile path → SQL → DB

Compiled query
precompiled delegate → parameters → SQL → DB
```

Compiled query tối ưu client-side EF query overhead, không làm database query tự nhiên nhanh hơn.

## 2. Why does it exist?

Nếu endpoint thực thi cùng query shape cực nhiều lần và query DB bản thân rất nhanh, EF query compilation/cache lookup có thể trở thành phần đáng kể của total latency.

Ngược lại, nếu SQL mất 200 ms thì tiết kiệm vài microseconds ở client-side compilation gần như vô nghĩa.

## 3. How does it work?

EF Core cung cấp `EF.CompileQuery` và `EF.CompileAsyncQuery`. Expression được compile thành delegate tái sử dụng.

Ví dụ:

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<ProductDto>>
    ProductByCategoryQuery =
        EF.CompileAsyncQuery(
            (AppDbContext db, Guid categoryId) =>
                db.Products
                    .AsNoTracking()
                    .Where(x => x.CategoryId == categoryId)
                    .OrderBy(x => x.Name)
                    .Select(x => new ProductDto(x.Id, x.Name, x.Price)));
```

Call site chỉ truyền context và parameter.

## 4. Practical implementation

```csharp
public async Task<List<ProductDto>> GetByCategoryAsync(
    Guid categoryId,
    CancellationToken cancellationToken)
{
    var result = new List<ProductDto>();

    await foreach (var item in ProductByCategoryQuery(_db, categoryId)
        .WithCancellation(cancellationToken))
    {
        result.Add(item);
    }

    return result;
}
```

Trước khi dùng compiled query, benchmark nên đo:

* query execution latency;
* EF CPU overhead;
* requests/sec;
* database duration;
* allocation.

## 5. Real production scenario

Một pricing lookup API gọi cùng một simple indexed query hàng chục nghìn lần/second. SQL Server trả row trong khoảng 1–2 ms. CPU profile cho thấy EF query pipeline chiếm tỷ lệ đáng kể ở app tier.

Compiled query có thể hợp lý ở path này. Nhưng với order report query mất 300 ms, effort đó không giải quyết bottleneck chính.

## 6. Failure scenario & troubleshooting

**Symptom** → thêm compiled query nhưng throughput không đổi.

**Evidence** → database duration chiếm 98% total latency.

**Hypothesis** → optimization target sai.

**Diagnosis** → compare app CPU, DB time và end-to-end trace.

**Fix** → quay lại query plan, access pattern, index hoặc round-trip reduction.

**Verification** → đo lại toàn pipeline; chỉ giữ compiled query nếu benefit thực và code complexity chấp nhận được.

## 7. Common mistakes

* Dùng compiled query cho mọi repository method.
* Nghĩ compiled query cache result dữ liệu.
* Dùng compiled query để “sửa” slow SQL.
* Dynamic query shape quá phức tạp nhưng cố ép vào compiled form.
* Không benchmark với production-like latency.

## 8. Alternatives

* EF Core normal query cache: đủ cho phần lớn use case.
* Projection + `AsNoTracking()`: thường tạo benefit lớn hơn.
* Raw SQL/Dapper: có thể giảm abstraction overhead nhưng tăng maintenance/SQL ownership.
* Database optimization: cần thiết nếu bottleneck nằm ở execution plan/I/O.

## 9. Trade-offs

### Advantages

* Giảm repeated query processing overhead.
* Hữu ích cho cực hot, stable query shapes.

### Costs / Risks

* Code khó đọc hơn.
* Flexibility với dynamic query thấp hơn.
* Benefit thường nhỏ nếu DB latency dominate.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ phải được translate thành SQL, không chạy “trực tiếp”.

### Middle

Biết xem generated SQL, dùng projection và `AsNoTracking()` trước.

### Senior

Biết profile client-side EF overhead và xác định compiled query có đáng hay không.

### Technical Lead / Architect

Đặt performance discipline: tối ưu từ bottleneck đã đo, không áp micro-optimization thành convention toàn codebase.

## 11. Key takeaway

* Compiled query tối ưu EF query-processing overhead, không tối ưu database execution.
* Chỉ đáng dùng ở hot path stable và được đo rõ.
* Projection, round-trip và query plan thường quan trọng hơn.

# 4. PostgreSQL MVCC và vacuum: concurrency không blocking nhiều nhưng tạo ra dead tuples và maintenance debt

## 1. What is it?

PostgreSQL dùng MVCC (Multi-Version Concurrency Control) để cho reader và writer hoạt động đồng thời bằng cách giữ nhiều version của row.

Thay vì update row “tại chỗ” theo nghĩa logic đơn giản, PostgreSQL tạo row version mới. Transaction khác nhìn version phù hợp với snapshot của nó.

Mental model:

```text
Row v1  ← visible to older snapshot
Row v2  ← visible to newer snapshot
Row v1 eventually becomes dead tuple
                 ↓
              VACUUM
```

## 2. Why does it exist?

Nếu mọi read phải block write hoặc mọi write phải block read, concurrency của OLTP workload sẽ giảm mạnh.

MVCC cho phép snapshot-based visibility, giảm lock contention cho read/write phổ biến. Nhưng consequence là obsolete row versions không tự biến mất ngay; database cần vacuum để reclaim/reuse space và duy trì transaction ID safety.

## 3. How does it work?

Mỗi row version có transaction metadata. Query quyết định row nào visible dựa trên transaction snapshot.

`UPDATE` tạo version mới và old version trở thành dead khi không transaction nào còn cần thấy nó. `VACUUM` đánh dấu/reclaim dead tuples cho reuse. Autovacuum tự động chạy theo threshold/configuration.

Long-running transaction có thể giữ snapshot cũ rất lâu, khiến vacuum không thể dọn row versions mà transaction đó vẫn có thể nhìn thấy.

## 4. Practical implementation

Điều tra table bloat/dead tuples:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Tìm long-running transactions:

```sql
SELECT
    pid,
    usename,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Application nên giữ transaction ngắn:

```csharp
await using var transaction = await db.Database.BeginTransactionAsync(cancellationToken);

await service.ApplyBusinessChangesAsync(cancellationToken);
await db.SaveChangesAsync(cancellationToken);

await transaction.CommitAsync(cancellationToken);
```

Không nên mở transaction rồi chờ user interaction hoặc remote API trong nhiều phút.

## 5. Real production scenario

Một reporting job mở transaction rồi stream dữ liệu trong 45 phút. Trong thời gian đó, bảng `Orders` nhận nhiều update.

Autovacuum vẫn chạy nhưng không thể reclaim nhiều tuple cũ vì snapshot dài còn cần visibility. Dead tuples tăng, table/index bloat tăng, cache efficiency giảm và query latency xấu dần.

## 6. Failure scenario & troubleshooting

**Symptom** → query ngày càng chậm, storage tăng dù row count gần như không đổi.

**Evidence** → `n_dead_tup` cao, old transactions tồn tại lâu, autovacuum chạy nhưng không reclaim hiệu quả.

**Hypothesis** → long-running transaction giữ xmin horizon.

**Diagnosis** → correlate `pg_stat_activity`, vacuum stats, table size và workload timeline.

**Fix** → rút ngắn transaction; điều chỉnh batch/report strategy; tune autovacuum nếu workload cần; xử lý connection bị `idle in transaction`.

**Verification** → dead tuple ratio giảm, vacuum progress bình thường, storage/query latency ổn định.

## 7. Common mistakes

* Nghĩ MVCC nghĩa là “không có locking”.
* Để connection ở `idle in transaction` lâu.
* Tắt autovacuum vì thấy nó dùng I/O.
* Chỉ tăng disk mà không tìm dead tuple source.
* Chạy `VACUUM FULL` như routine fix dù nó có operational impact lớn.

## 8. Alternatives

Không có “alternative” trực tiếp nếu vẫn dùng PostgreSQL, nhưng concurrency model khác ở các database có implementation khác. SQL Server có lock-based và row-versioning isolation choices. Điều quan trọng là hiểu engine behavior thay vì áp mental model của database này sang database khác.

## 9. Trade-offs

### Advantages

* Reader/writer concurrency tốt.
* Snapshot semantics rõ.
* Giảm nhiều loại read/write blocking.

### Costs / Risks

* Dead tuples và bloat.
* Vacuum là operational concern thực sự.
* Long-running transaction có hidden system-wide cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu row có thể có nhiều version và snapshot quyết định visibility.

### Middle

Biết giữ transaction ngắn và đọc basic PostgreSQL activity stats.

### Senior

Phân tích bloat, long transaction, vacuum behavior và transaction isolation.

### Technical Lead / Architect

Thiết kế batch/reporting/access pattern để không phá MVCC maintenance, đồng thời xác định monitoring cho transaction age và table health.

## 11. Key takeaway

* MVCC đổi blocking pressure thành version-management pressure.
* Long-running transaction có thể gây hậu quả xa hơn scope của chính nó.
* Autovacuum không phải optional housekeeping; nó là phần của runtime architecture PostgreSQL.

# 5. SQL connection pooling exhaustion: khi database chưa quá tải nhưng application vẫn timeout hàng loạt

## 1. What is it?

ADO.NET connection pooling giữ các physical database connections để tái sử dụng giữa request. `SqlConnection.OpenAsync()` thường lấy connection từ pool thay vì tạo TCP/TLS/login mới mỗi lần.

Mental model:

```text
Application requests
      ↓
Connection Pool
  ├─ free connection → immediate checkout
  └─ no free connection → wait
                         ↓
                       timeout
```

Pool exhaustion xảy ra khi mọi pooled connection đang bị giữ hoặc pool growth chạm giới hạn và request mới phải chờ.

## 2. Why does it exist?

Tạo physical SQL connection rất đắt: network handshake, TLS, authentication, session setup. Pooling tăng throughput đáng kể.

Nhưng pooling tạo shared finite resource. Nếu application giữ connection lâu hơn cần thiết, một downstream slow query có thể chuyển thành queue tại connection pool và cuối cùng làm cả endpoint khác timeout.

## 3. How does it work?

Pool thường được phân tách theo connection string/identity. Khi `SqlConnection.Dispose()` chạy, connection được trả về pool thay vì đóng physical socket ngay.

EF Core thường mở connection khi cần query và đóng/trả lại sau operation. Nhưng explicit transaction, streaming query hoặc leaked connection có thể giữ checkout lâu hơn.

Một request timeline xấu:

```text
Request
  ↓ acquire DB connection
  ↓ start transaction
  ↓ call slow external API 8s
  ↓ commit
  ↓ return connection
```

Trong 8 giây external call, connection bị chiếm vô ích.

## 4. Practical implementation

Không giữ DB transaction qua remote call:

```csharp
var order = await db.Orders
    .AsNoTracking()
    .SingleAsync(x => x.Id == orderId, cancellationToken);

var quote = await pricingClient.GetQuoteAsync(orderId, cancellationToken);

await using var transaction = await db.Database.BeginTransactionAsync(cancellationToken);

order.ApplyQuote(quote);
await db.SaveChangesAsync(cancellationToken);
await transaction.CommitAsync(cancellationToken);
```

Nếu consistency yêu cầu khác, cần redesign workflow; không mặc định mở transaction từ đầu request.

ADO.NET luôn dispose connection:

```csharp
await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(cancellationToken);

await using var command = connection.CreateCommand();
command.CommandText = "SELECT ...";
```

## 5. Real production scenario

API có pool max 100 connections. Bình thường mỗi query 50 ms. Sau deployment, một endpoint mới mở transaction rồi gọi third-party API 5–10 giây.

Chỉ cần khoảng 100 concurrent requests endpoint này là pool gần như bị giữ hết. Các endpoint khác có query rất nhanh vẫn timeout ở bước acquire connection.

Database CPU có thể chỉ 30%, khiến team ban đầu hiểu nhầm là “SQL khỏe nên không phải database issue”.

## 6. Failure scenario & troubleshooting

**Symptom** → API timeout hàng loạt, SQL CPU bình thường.

**Evidence** → traces cho thấy latency trước SQL command execution; connection pool counters/checkouts cao; request chờ `OpenAsync`.

**Hypothesis** → pool exhaustion hoặc connection leak.

**Diagnosis** → inspect long transactions, active sessions, connection checkout duration, slow dependency call bên trong transaction.

**Fix** → rút ngắn connection lifetime; dispose đúng; giảm transaction scope; tối ưu query; dùng backpressure nếu workload vượt capacity.

**Verification** → dưới load test, connection wait time gần zero và pool utilization có headroom.

## 7. Common mistakes

* Tăng `Max Pool Size` như fix đầu tiên.
* Giữ transaction qua HTTP call.
* Không dispose connection/reader.
* Nghĩ `DbContext` pooling đồng nghĩa database connection pooling.
* Tạo nhiều connection strings khác nhau vô tình chia pool thành nhiều nhóm nhỏ.

## 8. Alternatives

* Tăng pool size: chỉ hữu ích nếu DB thực sự chịu được concurrency cao hơn.
* Queue/background processing: phù hợp bursty write workloads không cần sync response.
* Read replica: giúp read scalability nhưng không sửa leaked/long-held connections.

## 9. Trade-offs

### Advantages

* Pooling giảm connection setup cost rất lớn.
* Cho phép high-throughput application với số physical connection hữu hạn.

### Costs / Risks

* Pool là hidden finite resource.
* Long checkout gây failure propagation.
* Tăng pool quá mức có thể đẩy bottleneck sang database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu dispose connection nghĩa là trả về pool.

### Middle

Biết giữ query/transaction scope ngắn và trace database timing.

### Senior

Phân biệt query latency, connection-acquire latency và database capacity; điều tra pool exhaustion.

### Technical Lead / Architect

Đặt concurrency budget giữa app instances và database, tránh scale app vô hạn mà không tính tổng connection pressure.

## 11. Key takeaway

* Database có thể khỏe trong khi pool ở app đã cạn.
* Connection lifetime và transaction scope là production capacity concern.
* Tăng pool size không thay thế việc sửa access pattern.

# 6. CQRS với một database: tách intent trước khi tách storage và complexity vận hành

## 1. What is it?

CQRS (Command Query Responsibility Segregation) tách operation thay đổi state (Command) khỏi operation đọc dữ liệu (Query).

Điểm quan trọng: CQRS không bắt buộc hai database, Event Sourcing hoặc Microservices.

Một implementation đơn giản:

```text
HTTP API
  ├─ Command Handler → Domain/Application → same SQL database
  └─ Query Handler   → projection/read SQL → same SQL database
```

Tách intent có thể mang lại clarity mà chưa cần distributed consistency.

## 2. Why does it exist?

Read và write thường có nhu cầu khác nhau.

Write cần:

* validation;
* invariants;
* transaction boundaries;
* authorization;
* side-effect control.

Read cần:

* projection;
* filtering;
* pagination;
* performance;
* shape phù hợp UI.

Nếu ép cả hai qua cùng một generic repository/entity graph, code có thể trở nên khó tối ưu và business intent mờ đi.

## 3. How does it work?

Command biểu diễn intent như `ApproveTimesheet`. Query biểu diễn request dữ liệu như `GetTimesheetSummary`.

Cả hai vẫn có thể dùng một database:

```text
Command
  ↓
Load Aggregate
  ↓ validate invariant
SaveChanges

Query
  ↓
AsNoTracking projection
  ↓
DTO
```

Sau này nếu read scalability thực sự cần, read model có thể được tách storage. Nhưng đó là bước tiến hóa, không phải requirement ban đầu.

## 4. Practical implementation

Command:

```csharp
public sealed record ApproveTimesheetCommand(Guid TimesheetId, Guid ApproverId);

public sealed class ApproveTimesheetHandler
{
    private readonly AppDbContext _db;

    public ApproveTimesheetHandler(AppDbContext db) => _db = db;

    public async Task Handle(
        ApproveTimesheetCommand command,
        CancellationToken cancellationToken)
    {
        var timesheet = await _db.Timesheets
            .SingleAsync(x => x.Id == command.TimesheetId, cancellationToken);

        timesheet.Approve(command.ApproverId);

        await _db.SaveChangesAsync(cancellationToken);
    }
}
```

Query:

```csharp
public Task<TimesheetSummaryDto?> GetSummaryAsync(
    Guid id,
    CancellationToken cancellationToken) =>
    _db.Timesheets
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new TimesheetSummaryDto(
            x.Id,
            x.Employee.Name,
            x.TotalHours,
            x.Status))
        .SingleOrDefaultAsync(cancellationToken);
```

Không nhất thiết phải thêm MediatR nếu team không cần abstraction đó.

## 5. Real production scenario

Một approval platform ban đầu có service method `SaveTimesheet(TimesheetDto dto)` vừa create, edit, submit, approve tùy field trong DTO.

Business rules ngày càng nhiều và authorization khó reason.

Team tách command thành `Create`, `Update`, `Submit`, `Approve`, trong khi read dùng projection riêng. Vẫn giữ một SQL database. Clarity và testability tăng mà chưa thêm messaging/read replica/eventual consistency.

## 6. Failure scenario & troubleshooting

**Symptom** → team “áp CQRS” nhưng codebase có hàng trăm handler một dòng, mỗi handler chỉ gọi generic repository; complexity tăng nhưng business intent không rõ hơn.

**Evidence** → command/query boundaries không mang behavior riêng; mapping và boilerplate chiếm phần lớn code.

**Hypothesis** → pattern được áp theo template chứ không giải quyết complexity thật.

**Diagnosis** → xem handler có encapsulate intent, invariant, read optimization hay chỉ đổi tên service method.

**Fix** → giữ CQRS ở nơi domain/read-write asymmetry có giá trị; use case đơn giản có thể dùng application service trực tiếp.

**Verification** → code review tập trung khả năng reason về intent, transaction và read shape thay vì số layer.

## 7. Common mistakes

* Đồng nhất CQRS với Event Sourcing.
* Tách read/write database ngay từ đầu.
* Bắt mọi request đi qua mediator dù không có lợi ích.
* Command trả về giant read model làm boundary mờ.
* Duplicate business rules giữa nhiều handlers.

## 8. Alternatives

* Traditional application service: đơn giản hơn cho CRUD-dominant domain.
* Vertical Slice Architecture: tổ chức theo use case, có thể kết hợp hoặc không với CQRS.
* Full CQRS separate stores: chỉ đáng dùng khi read/write scalability hoặc model khác biệt đủ lớn.

## 9. Trade-offs

### Advantages

* Intent rõ.
* Write model tập trung invariants.
* Read model tối ưu theo consumer.
* Có đường tiến hóa về separate stores nếu cần.

### Costs / Risks

* Nhiều types/handlers hơn.
* Boilerplate nếu domain đơn giản.
* Separate stores sau này kéo theo eventual consistency và operational burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu command thay đổi state, query đọc state.

### Middle

Biết viết handler/use case rõ transaction và projection.

### Senior

Đánh giá boundary, duplicate logic, read optimization và khi nào separate model có value.

### Technical Lead / Architect

Quyết định mức CQRS phù hợp: intent separation đơn giản, separate read model, hay distributed read/write architecture; không nhảy complexity trước nhu cầu.

## 11. Key takeaway

* CQRS bắt đầu từ tách intent, không bắt đầu từ hai database.
* Một database thường là điểm khởi đầu hợp lý.
* Architecture pattern chỉ có giá trị nếu làm system dễ reason hơn.

# 7. Azure Service Bus message lock, settlement và duplicate delivery: thiết kế consumer đúng cho at-least-once processing

## 1. What is it?

Trong Azure Service Bus Peek-Lock mode, consumer nhận message nhưng broker chưa xóa message ngay. Message được lock tạm thời cho consumer đó.

Sau processing:

* `Complete` → broker xóa message;
* `Abandon` → message có thể được giao lại;
* `DeadLetter` → chuyển DLQ;
* lock hết hạn trước `Complete` → message có thể xuất hiện lại.

Mental model:

```text
Receive + lock
   ↓
Process
   ├─ success → Complete
   ├─ retryable fail → Abandon / lock expires
   └─ non-retryable → DeadLetter
```

Đây là foundation của at-least-once processing.

## 2. Why does it exist?

Nếu broker xóa message ngay khi gửi cho consumer và process crash giữa chừng, message mất.

Peek-Lock giữ message cho tới khi consumer xác nhận completion. Đổi lại, duplicate delivery trở thành behavior bình thường cần được thiết kế cho, không phải anomaly hiếm.

## 3. How does it work?

Message có lock duration hữu hạn. SDK có thể auto-renew lock trong một khoảng cấu hình, nhưng long-running processing vẫn cần được thiết kế cẩn thận.

Failure example:

```text
Consumer updates DB successfully
       ↓
process crashes before Complete
       ↓
lock expires
       ↓
message delivered again
       ↓
DB update executes twice unless idempotent
```

Do đó settlement và business side effect là hai operations riêng biệt; không có atomic transaction tự nhiên giữa database và broker trong mọi architecture.

## 4. Practical implementation

```csharp
var processor = client.CreateProcessor(queueName, new ServiceBusProcessorOptions
{
    AutoCompleteMessages = false,
    MaxConcurrentCalls = 8,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(5)
});

processor.ProcessMessageAsync += async args =>
{
    var messageId = args.Message.MessageId;

    if (await inboxStore.HasProcessedAsync(messageId, args.CancellationToken))
    {
        await args.CompleteMessageAsync(args.Message, args.CancellationToken);
        return;
    }

    await orderService.ApplyAsync(args.Message.Body, args.CancellationToken);
    await inboxStore.MarkProcessedAsync(messageId, args.CancellationToken);

    await args.CompleteMessageAsync(args.Message, args.CancellationToken);
};
```

Trong production, `ApplyAsync` và `MarkProcessedAsync` nên nằm cùng database transaction nếu inbox/idempotency state dùng cùng database.

## 5. Real production scenario

Order consumer nhận `PaymentCaptured`. Nó cập nhật order thành Paid và gửi email receipt.

DB update thành công nhưng app restart trước `Complete`. Message được giao lại. Nếu handler không idempotent, order audit log và email có thể bị tạo hai lần.

Senior design dùng inbox/deduplication key cho state transition và tách notification side effect theo event riêng nếu cần reliability tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng `MessageId` xuất hiện nhiều lần, một số business action chạy lặp.

**Evidence** → Service Bus delivery count > 1; logs cho thấy lock lost/restart/timeout trước settlement.

**Hypothesis** → duplicate delivery bình thường nhưng consumer không idempotent.

**Diagnosis** → xem handler transaction boundary, idempotency store, lock duration và processing time.

**Fix** → thêm deduplication/inbox; rút processing; chia long-running work; điều chỉnh auto-lock renewal có kiểm soát.

**Verification** → fault injection crash sau DB commit nhưng trước `Complete` và xác nhận side effect không lặp sai.

## 7. Common mistakes

* Giả định queue giao exactly once.
* `Complete` trước khi business transaction commit.
* Retry mọi exception vô hạn.
* Long-running processing vượt lock duration mà không renew/chia nhỏ.
* Dùng `MessageId` không ổn định nên deduplication vô nghĩa.
* Gửi email/payment side effect trực tiếp mà không xét duplicate.

## 8. Alternatives

* Receive-and-delete: đơn giản nhưng có nguy cơ mất message khi crash; chỉ hợp work chấp nhận loss.
* Event Grid/Event Hubs: giải quyết use case khác, không thay Service Bus queue semantics trực tiếp.
* Database work queue: giảm distributed components nhưng có scalability/operational trade-offs riêng.

## 9. Trade-offs

### Advantages

* Không mất message chỉ vì consumer crash trước completion.
* Backpressure và competing consumers rõ.
* DLQ hỗ trợ failure isolation.

### Costs / Risks

* Duplicate delivery là expected behavior.
* Idempotency tăng design complexity.
* Lock renewal và long-running work cần monitoring.
* Throughput phụ thuộc concurrency, processing time và downstream capacity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu receive không đồng nghĩa message đã bị xóa.

### Middle

Biết `Complete`, `Abandon`, `DeadLetter`, delivery count và lock duration.

### Senior

Thiết kế idempotent consumer, inbox pattern, transaction boundary và poison-message strategy.

### Technical Lead / Architect

Xác định delivery semantics toàn hệ thống, ownership của deduplication và cách downstream side effects chịu duplicate/retry.

## 11. Key takeaway

* Azure Service Bus consumer phải giả định at-least-once delivery.
* `Complete` chỉ nên xảy ra sau khi business processing an toàn.
* Idempotency là correctness requirement, không phải optional optimization.

# 8. Azure Front Door vs Application Gateway: global edge routing khác regional application ingress như thế nào

## 1. What is it?

Azure Front Door và Application Gateway đều có thể đứng trước web application nhưng giải quyết boundary khác nhau.

Mental model:

```text
Global users
    ↓
Azure Front Door
    ↓ global edge routing / WAF / CDN-like acceleration
Region A                 Region B
   ↓                        ↓
Application Gateway      Application Gateway
   ↓ regional L7 ingress    ↓
App/AKS                  App/AKS
```

Front Door là global edge service. Application Gateway là regional Layer 7 load balancer/reverse proxy trong Azure region/VNet context.

## 2. Why does it exist?

Một global SaaS cần route user tới healthy/near region, terminate edge traffic và bảo vệ public surface. Một regional AKS/App Service topology lại cần ingress routing, TLS, WAF hoặc private backend integration trong region.

Nếu coi hai service là interchangeable chỉ vì cả hai “route HTTP”, architecture dễ sai boundary.

## 3. How does it work?

Front Door nhận traffic tại Microsoft edge, evaluate route/origin health rồi forward tới origin phù hợp. Nó phù hợp multi-region failover/global routing.

Application Gateway hoạt động trong một Azure region và VNet, route request tới backend pools dựa trên host/path rules.

Một architecture có thể dùng cả hai, nhưng không nên mặc định stack chúng nếu requirement không cần.

## 4. Practical implementation

Application nên chuẩn hóa forwarded headers khi reverse proxy ở trước:

```csharp
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders =
        ForwardedHeaders.XForwardedFor |
        ForwardedHeaders.XForwardedProto;
});

var app = builder.Build();
app.UseForwardedHeaders();
```

Health endpoint dành cho routing nên nhẹ và phản ánh khả năng nhận traffic:

```csharp
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

Không nên để edge health probe gọi một dependency đắt và vô tình tạo traffic lớn.

## 5. Real production scenario

E-commerce chạy active-active tại West Europe và Southeast Asia. Front Door route user và failover giữa hai origins. Mỗi region có Application Gateway trước AKS để route path `/api`, `/cms`, `/search` tới services nội vùng.

Nếu workload chỉ có một App Service public trong một region, chỉ Front Door hoặc thậm chí App Service built-in endpoint có thể đã đủ; không cần stack mọi networking service.

## 6. Failure scenario & troubleshooting

**Symptom** → user bị redirect loop từ HTTP sang HTTPS hoặc application log sai client IP.

**Evidence** → app thấy scheme `http` vì TLS terminate ở proxy, hoặc forwarded headers không được trust/process đúng.

**Hypothesis** → reverse proxy boundary không được application hiểu đúng.

**Diagnosis** → inspect `X-Forwarded-Proto`, `X-Forwarded-For`, backend health, Front Door origin configuration và Application Gateway listener/rules.

**Fix** → cấu hình forwarded headers đúng trust boundary, chuẩn hóa TLS termination và health probes.

**Verification** → test end-to-end qua public edge, không chỉ gọi backend trực tiếp.

## 7. Common mistakes

* Dùng Front Door và Application Gateway chỉ vì “best practice” mà không có requirement.
* Health probe quá sâu, khiến transient dependency issue remove toàn region khỏi traffic.
* App không xử lý forwarded headers.
* Public expose backend bypass WAF/edge policy.
* Không tính egress/processing cost và latency của extra hops.

## 8. Alternatives

* Azure Load Balancer: Layer 4, phù hợp TCP/UDP hơn L7 HTTP routing.
* App Service built-in ingress: đơn giản hơn cho workload nhỏ.
* NGINX/Ingress Controller trong AKS: regional ingress alternative nhưng operational model khác.
* Traffic Manager: DNS-based global routing, behavior khác proxy-based Front Door.

## 9. Trade-offs

### Advantages

* Front Door: global routing, edge presence, multi-region failover.
* Application Gateway: regional L7 routing, VNet integration, backend control.

### Costs / Risks

* Thêm hop và cost.
* WAF/routing configuration phức tạp.
* Health signal sai có thể gây self-inflicted outage.
* Debugging cần correlate nhiều proxy layers.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu edge/global khác regional ingress.

### Middle

Biết host/path routing, health probes, TLS và forwarded headers.

### Senior

Debug routing chain, failover behavior, private connectivity và WAF impacts.

### Technical Lead / Architect

Chọn số lớp ingress tối thiểu đáp ứng global routing, security, private networking và availability requirement.

## 11. Key takeaway

* Front Door và Application Gateway có scope khác nhau.
* Thêm proxy layer chỉ khi requirement xứng đáng với cost/complexity.
* Health probe và forwarded-header design là phần của correctness.

# 9. Playwright E2E testing: kiểm thử user journey mà không biến test suite thành nguồn flaky build

## 1. What is it?

Playwright là browser automation framework dùng để chạy end-to-end test qua browser thật hoặc browser engine gần thực tế.

E2E test kiểm chứng system behavior xuyên nhiều layer:

```text
Browser
  ↓
Frontend
  ↓
API
  ↓
Authentication
  ↓
Database / external integration substitutes
```

Nó bảo vệ user journey, không phải thay thế unit/integration tests.

## 2. Why does it exist?

Unit test có thể chứng minh từng service method đúng nhưng vẫn bỏ sót lỗi wiring:

* route sai;
* JS bundle lỗi;
* authentication redirect loop;
* API contract mismatch;
* button bị disabled sai;
* deployment config thiếu.

E2E test tồn tại để kiểm chứng critical path như user thực sự trải nghiệm.

## 3. How does it work?

Playwright điều khiển browser, tìm element theo semantic locator, tương tác và assert UI/network behavior.

Test tốt nên phụ thuộc user-visible contract:

```text
role / label / accessible name
```

thay vì fragile selector như:

```text
div:nth-child(3) > span:nth-child(2)
```

Auto-waiting giúp giảm explicit sleeps, nhưng test vẫn flaky nếu environment/data không deterministic.

## 4. Practical implementation

```typescript
import { test, expect } from '@playwright/test';

test('manager can approve a submitted timesheet', async ({ page }) => {
  await page.goto('/timesheets/123');

  await expect(page.getByRole('heading', { name: 'Timesheet' }))
    .toBeVisible();

  await page.getByRole('button', { name: 'Approve' }).click();

  await expect(page.getByText('Approved'))
    .toBeVisible();
});
```

Không dùng:

```typescript
await page.waitForTimeout(5000);
```

nếu có thể chờ condition thực:

```typescript
await expect(page.getByText('Approved')).toBeVisible();
```

## 5. Real production scenario

CI có hàng trăm unit tests pass nhưng deployment bị lỗi vì callback URL của Entra ID sai hostname. Login flow production-like fail hoàn toàn.

Một E2E smoke test chạy sau deploy qua public endpoint có thể bắt lỗi wiring này trước khi promote release.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng test pass 9 lần, fail 1 lần trong CI.

**Evidence** → screenshot/video cho thấy element chưa xuất hiện khi click; network response chậm ngẫu nhiên.

**Hypothesis** → test phụ thuộc fixed delay/timing hoặc shared data.

**Diagnosis** → inspect trace, network, browser console, test data isolation và environment contention.

**Fix** → dùng semantic waits, deterministic fixtures, isolated data, retry chỉ như diagnostic safety net chứ không che lỗi.

**Verification** → chạy test lặp nhiều lần và parallel để chứng minh stability.

## 7. Common mistakes

* Dùng `waitForTimeout` khắp nơi.
* Selector dựa vào DOM structure/styling class.
* E2E test mọi validation branch nhỏ.
* Shared account/data làm tests ảnh hưởng nhau.
* Retry nhiều lần rồi coi flaky test là “pass”.
* Không giữ trace/screenshot/video khi CI fail.

## 8. Alternatives

* Unit test: nhanh, tốt cho pure logic.
* Integration test: tốt cho API/database boundary.
* Contract test: tốt cho independent service contracts.
* E2E: nên tập trung critical journeys và deployment wiring.

## 9. Trade-offs

### Advantages

* Bắt lỗi cross-layer thực tế.
* Validate browser behavior và deployment config.
* Tốt cho critical business journey.

### Costs / Risks

* Chậm hơn.
* Environment-sensitive.
* Test data management khó.
* Flakiness có thể làm giảm niềm tin CI.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu E2E test mô phỏng user journey qua nhiều layer.

### Middle

Biết viết semantic locator, deterministic waits và fixtures.

### Senior

Phân loại failure do product vs environment vs test, thiết kế test isolation và observability.

### Technical Lead / Architect

Xây test strategy theo risk: phần nào unit, integration, contract, E2E; giới hạn E2E ở nơi nó cung cấp signal cao nhất.

## 11. Key takeaway

* E2E test bảo vệ integration của cả system, không thay unit/integration test.
* Flaky test là engineering defect cần xử lý.
* Critical journey + deterministic environment tốt hơn hàng nghìn UI tests yếu.

# 10. Incremental .NET Framework modernization: Strangler migration thay vì rewrite toàn bộ hệ thống một lần

## 1. What is it?

Incremental modernization là chuyển hệ thống legacy từ .NET Framework sang modern .NET theo từng boundary/use case thay vì rewrite toàn bộ application rồi cut over một lần.

Strangler-style mental model:

```text
Users
  ↓
Routing / facade
  ├─ legacy feature → .NET Framework app
  └─ migrated feature → modern .NET service/module
```

Theo thời gian, traffic/functionality dịch dần sang system mới.

## 2. Why does it exist?

Full rewrite hấp dẫn về mặt kỹ thuật vì cho cảm giác “làm sạch tất cả”. Nhưng rewrite lớn mang nhiều risk:

* behavior legacy không được document đầy đủ;
* business rules ẩn trong code/database;
* migration kéo dài nhiều tháng/năm;
* production bug vẫn phải fix song song ở system cũ;
* ngày cutover có blast radius rất lớn.

Incremental migration giảm risk bằng cách chia transformation thành các bước có thể deploy, quan sát và rollback.

## 3. How does it work?

Một modernization flow thực tế:

```text
1. Inventory dependencies
2. Identify seams / bounded capabilities
3. Add characterization tests
4. Extract shared contracts carefully
5. Route one capability to modern .NET
6. Observe production
7. Migrate data/integration boundary if needed
8. Repeat
```

Boundary có thể là endpoint group, background job, report, authentication façade hoặc domain module.

Không nên tạo distributed monolith bằng cách tách process nhưng vẫn shared database tables/transaction assumptions hỗn loạn.

## 4. Practical implementation

Một reverse-proxy façade có thể route legacy và modern endpoints. Với YARP:

```csharp
builder.Services
    .AddReverseProxy()
    .LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"));

var app = builder.Build();
app.MapReverseProxy();
app.Run();
```

Config concept:

```json
{
  "ReverseProxy": {
    "Routes": {
      "modern-orders": {
        "ClusterId": "modern",
        "Match": { "Path": "/api/orders/{**catch-all}" }
      },
      "legacy": {
        "ClusterId": "legacy",
        "Match": { "Path": "/{**catch-all}" }
      }
    }
  }
}
```

Trong migration, contract tests và observability quan trọng hơn proxy syntax.

## 5. Real production scenario

Một enterprise portal .NET Framework 4.8 chứa MVC, background jobs, EF6 và nhiều third-party libraries cũ.

Team chọn migrate notification/reporting trước vì boundary rõ, ít transaction coupling. Sau đó migrate REST APIs có nhiều traffic. Authentication và core legacy workflow giữ lại tới khi dependency compatibility rõ.

Mỗi bước có production telemetry và rollback route.

## 6. Failure scenario & troubleshooting

**Symptom** → feature migrated nhưng dữ liệu giữa legacy và modern module không nhất quán.

**Evidence** → cả hai cùng update chung tables theo assumptions khác nhau; cache invalidation và transaction boundary không đồng bộ.

**Hypothesis** → process boundary được tách trước data ownership boundary.

**Diagnosis** → map writers/readers của từng table, transaction flow và integration calls.

**Fix** → xác định ownership rõ; dùng API/event contract; tránh dual-write không kiểm soát; migrate theo capability có data boundary hợp lý.

**Verification** → compare business outcomes, audit data consistency và rollback path qua production-like migration test.

## 7. Common mistakes

* Rewrite toàn bộ chỉ vì code cũ “xấu”.
* Migrate framework version nhưng không characterization test behavior.
* Tách service nhưng vẫn dùng chung domain/database như cũ.
* Upgrade quá nhiều dependencies trong cùng release.
* Không có rollback hoặc parallel validation.
* Dùng migration để đồng thời redesign toàn business domain mà không kiểm soát scope.

## 8. Alternatives

* In-place upgrade: phù hợp khi application nhỏ và dependencies đã compatible.
* Full rewrite: đôi khi hợp lý với system nhỏ, behavior đơn giản, replaceable và migration window ngắn.
* Replatform hosting trước rồi refactor sau: giảm một loại risk nhưng không giải quyết code architecture trực tiếp.

## 9. Trade-offs

### Advantages

* Giảm blast radius.
* Có giá trị production sớm.
* Cho phép học từ từng bước.
* Rollback thực tế hơn.

### Costs / Risks

* Tạm thời phải vận hành hai technology stacks.
* Routing/integration complexity tăng trong transition.
* Migration có thể kéo dài nếu không có end-state governance.
* Duplicate capability tạm thời tạo maintenance cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu modernization không đồng nghĩa rewrite.

### Middle

Biết inventory dependencies, add tests và migrate isolated feature.

### Senior

Đánh giá compatibility, data ownership, rollback, deployment và cross-system observability.

### Technical Lead / Architect

Thiết kế migration roadmap theo business capability, dependency risk và operational seams; quyết định khi nào incremental migration tốt hơn in-place upgrade hoặc rewrite.

## 11. Key takeaway

* Modernization là risk-management problem trước khi là framework-upgrade problem.
* Data ownership và contract boundary quan trọng hơn việc tách process.
* Incremental migration cho phép production feedback và rollback sau từng bước.
