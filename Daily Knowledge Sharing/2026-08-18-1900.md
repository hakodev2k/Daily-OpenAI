# 1. Clean Architecture và ranh giới phụ thuộc

### 1. What is it?
Clean Architecture là cách tổ chức hệ thống dựa trên nguyên tắc dependency chỉ hướng vào business rules. Domain không phụ thuộc framework, database hay API.

### 2. Why does it exist?
Mục tiêu là tránh business logic bị khóa vào công nghệ. Khi database, UI hoặc framework thay đổi, phần lõi vẫn ổn định.

### 3. How does it work?

```text
API
 ↓
Application
 ↓
Domain
 ↑
Infrastructure
```

Domain chứa nghiệp vụ. Application điều phối use case. Infrastructure cung cấp triển khai kỹ thuật.

### 4. Practical example
ASP.NET Core API gọi Application service, service xử lý command và dùng interface repository được implement bởi EF Core.

### 5. Real production scenario
Hệ thống quản lý nhân sự có thể thay SQL Server bằng PostgreSQL mà không thay đổi business rules.

### 6. Common mistakes
Tạo quá nhiều layer nhưng không có boundary rõ ràng. Đưa EF Core entity logic vào API controller.

### 7. Trade-offs
Ưu điểm: dễ test, dễ mở rộng. Chi phí: nhiều abstraction và code ban đầu.

### 8. Junior → Middle → Senior
Junior hiểu dependency direction. Middle biết thiết kế use case. Senior quyết định boundary phù hợp.

### 9. Key takeaway
Architecture tốt bảo vệ business logic khỏi thay đổi bên ngoài.

# 2. CQRS trong backend

CQRS tách thao tác đọc và ghi thành hai mô hình riêng.

Lý do tồn tại: hệ thống có nhu cầu đọc lớn nhưng ghi phức tạp.

Luồng:

```text
Command -> Handler -> Database
Query -> Read Model
```

Ví dụ .NET dùng MediatR để dispatch command handler.

Sai lầm phổ biến là áp dụng CQRS cho mọi CRUD nhỏ.

Trade-off: linh hoạt hơn nhưng tăng complexity.

Junior hiểu command/query. Middle triển khai handler. Senior đánh giá khi nào cần tách read model.

Key takeaway: CQRS là công cụ giải quyết complexity, không phải mặc định.

# 3. Idempotency trong REST API

Idempotency đảm bảo gửi cùng một request nhiều lần vẫn tạo một kết quả nhất quán.

Ví dụ payment API lưu Idempotency-Key.

Production scenario: retry khi mạng lỗi không tạo hai giao dịch.

Sai lầm: retry POST mà không có protection.

Trade-off: thêm storage và logic kiểm tra.

Key takeaway: retry an toàn cần idempotency.

# 4. Optimistic Concurrency với EF Core

Dùng version token để phát hiện dữ liệu bị thay đổi bởi process khác.

Ví dụ:

```csharp
public byte[] RowVersion { get; set; }
```

EF Core kiểm tra row version khi update.

Production scenario: nhiều user sửa cùng employee profile.

Trade-off: ít lock nhưng cần xử lý conflict.

Key takeaway: concurrency phải được thiết kế rõ ràng.

# 5. Azure Service Bus

Azure Service Bus là message broker giúp tách producer và consumer.

```text
API -> Queue -> Worker
```

Dùng cho background processing, integration và retry.

Sai lầm: xử lý message không idempotent.

Trade-off: tăng reliability nhưng cần quản lý eventual consistency.

Key takeaway: message-driven system cần failure handling.

# 6. Managed Identity trong Azure

Managed Identity cho phép service Azure xác thực mà không lưu secret.

Ví dụ App Service truy cập Azure Key Vault.

Lợi ích: giảm rủi ro credential leak.

Sai lầm: cấp quyền quá rộng.

Key takeaway: ưu tiên identity-based security.

# 7. Redis Cache Aside Pattern

Application kiểm tra cache trước database.

```text
Request -> Redis -> Database -> Redis update
```

Dùng cho dữ liệu đọc nhiều.

Sai lầm lớn nhất là cache invalidation sai.

Trade-off: tăng performance nhưng giảm consistency tức thời.

Key takeaway: cache là bài toán dữ liệu, không chỉ tốc độ.

# 8. OpenTelemetry và Distributed Tracing

OpenTelemetry chuẩn hóa thu thập logs, metrics và traces.

Giúp tìm request đi qua nhiều service.

Production scenario: API gọi payment service rồi notification service.

Sai lầm: chỉ log message mà không có correlation id.

Key takeaway: production cần nhìn thấy toàn bộ request lifecycle.

# 9. RAG Architecture cho AI Application

RAG kết hợp LLM với dữ liệu riêng thông qua retrieval.

Luồng:

```text
Question -> Embedding -> Vector Search -> Context -> LLM
```

Dùng cho chatbot nội bộ, document assistant.

Sai lầm: đưa toàn bộ dữ liệu vào prompt.

Trade-off: chính xác hơn nhưng cần quản lý indexing và cost.

Key takeaway: AI production cần data pipeline.

# 10. Feature Flags trong Continuous Delivery

Feature flag cho phép bật/tắt tính năng mà không cần deploy lại.

Dùng trong canary release và testing production.

Sai lầm: để flag cũ tồn tại mãi mãi.

Trade-off: release nhanh hơn nhưng tăng complexity.

Key takeaway: feature flag là công cụ quản trị rủi ro khi release.
