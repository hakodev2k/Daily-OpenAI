# 1. .NET ThreadPool starvation và sync-over-async

## 1. What is it?
ThreadPool starvation xảy ra khi application còn work nhưng thiếu worker thread khả dụng vì nhiều thread đang bị block. Nó khác CPU saturation: CPU có thể chỉ 40–50% nhưng request vẫn xếp hàng.

## 2. Why does it exist?
ASP.NET Core dùng ThreadPool để chạy request continuations. .Result, .Wait(), synchronous I/O hoặc lock dài giữ thread trong lúc không tạo giá trị, làm capacity suy giảm dây chuyền.

## 3. How does it work?
~~~text
Request -> worker -> blocking I/O
New requests -> ThreadPool queue -> chờ worker -> p95/p99 tăng
~~~
ThreadPool có thể bổ sung thread nhưng ramp-up không tức thời; thêm quá nhiều thread còn tăng context switching.

## 4. Practical implementation
Thay vì gọi GetStringAsync(...).Result, dùng await httpClient.GetStringAsync(url, cancellationToken). Quan sát thread_pool.queue.length, thread count, CPU và request duration bằng dotnet-counters.

## 5. Real production scenario
Một API gọi SDK legacy synchronous. Downstream tăng latency từ 100 ms lên 5 giây; hàng trăm worker bị giữ, CPU chưa bão hòa nhưng p99 vượt 20 giây.

## 6. Failure scenario & troubleshooting
Symptom → timeout tăng. Evidence → ThreadPool queue/thread count tăng nhưng CPU thấp. Hypothesis → blocking work. Diagnosis → trace/thread dump chỉ ra .Result/.Wait(). Fix → async end-to-end, timeout, cancellation và bounded concurrency. Verification → queue gần 0 dưới cùng workload.

## 7. Common mistakes
Tăng MinThreads ngay; bọc I/O bằng Task.Run; chỉ nhìn CPU; bỏ CancellationToken; để downstream timeout quá dài.

## 8. Alternatives
CPU-bound work có thể cần bounded worker/queue riêng. I/O-bound work nên asynchronous thay vì thêm thread.

## 9. Trade-offs
### Advantages
Async I/O giải phóng worker khi chờ.
### Costs / Risks
Async không làm CPU work nhanh hơn; concurrency không giới hạn vẫn làm cạn connection/downstream capacity.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu await không có nghĩa tạo thread mới cho I/O.
### Middle
Loại sync-over-async và propagate cancellation.
### Senior
Phân biệt starvation, CPU saturation, lock contention và dependency latency bằng telemetry.
### Technical Lead / Architect
Thiết kế concurrency budget và isolation boundary.

## 11. Key takeaway
- CPU thấp không loại trừ ThreadPool starvation.
- Đo queue, threads và dependency latency cùng nhau.
- Async end-to-end quan trọng hơn “thêm thread”.

# 2. ASP.NET Core HttpClientFactory và resilience boundary

## 1. What is it?
IHttpClientFactory quản lý HttpMessageHandler lifecycle để tái sử dụng connection pool nhưng vẫn refresh handler. HttpClient là façade; connection thật nằm dưới SocketsHttpHandler.

## 2. Why does it exist?
Tạo/dispose HttpClient per request gây socket churn/port exhaustion. Giữ handler vô hạn có thể bám DNS cũ trong môi trường endpoint thay đổi.

## 3. How does it work?
Factory tạo logical clients, pool handlers và cho phép typed/named configuration. Connection reuse giảm handshake; lifetime hợp lý cho phép endpoint rotation.

## 4. Practical implementation
~~~csharp
builder.Services.AddHttpClient<ProductClient>(client =>
{
    client.BaseAddress = new Uri(config["ProductApi:BaseUrl"]!);
    client.Timeout = TimeSpan.FromSeconds(3);
});
~~~
Typed client gom contract, timeout và dependency-specific behavior tại một boundary.

## 5. Real production scenario
Product API đổi IP sau deployment. Client cần reuse connections để hiệu quả nhưng không được giữ endpoint cũ vô hạn.

## 6. Failure scenario & troubleshooting
Symptom → timeout sau downstream deployment. Evidence → DNS trả IP mới nhưng process kết nối IP cũ. Diagnosis → handler/connection lifetime sai. Fix → factory hoặc PooledConnectionLifetime hợp lý. Verification → trace cho thấy connection tới endpoint mới.

## 7. Common mistakes
new HttpClient() mỗi call; retry mọi status; retry POST không idempotent; timeout quá dài; một policy cho mọi dependency.

## 8. Alternatives
Singleton HttpClient với SocketsHttpHandler cấu hình đúng cũng hợp lệ. Factory hữu ích khi có nhiều dependency/policy.

## 9. Trade-offs
### Advantages
Centralized configuration, pooling, typed boundaries.
### Costs / Risks
Retry sai có thể tạo retry storm; abstraction không thay thế hiểu biết HTTP.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu vì sao không tạo client per request.
### Middle
Dùng typed client, timeout và cancellation.
### Senior
Thiết kế retry cho transient + idempotent operation.
### Technical Lead / Architect
Đặt resilience/concurrency policy theo semantics từng dependency.

## 11. Key takeaway
- Handler lifecycle quan trọng hơn lifecycle bề mặt HttpClient.
- Timeout, retry và idempotency phải thiết kế cùng nhau.
- Resilience policy phải dependency-specific.

# 3. EF Core transaction boundary + Outbox Pattern

## 1. What is it?
Outbox ghi business change và message cần publish trong cùng relational transaction. Sau commit, worker đọc Outbox và gửi Azure Service Bus.

## 2. Why does it exist?
SaveChanges thành công nhưng publish fail làm mất event; publish trước nhưng DB fail tạo phantom event. Hai hệ thống không có atomic commit tự nhiên.

## 3. How does it work?
~~~mermaid
flowchart LR
 API --> DB[(Business + Outbox)]
 DB --> Worker
 Worker --> SB[Azure Service Bus]
 SB --> Consumer
~~~
Atomicity nằm trong DB; delivery ra broker vẫn thường at-least-once.

## 4. Practical implementation
~~~csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);
db.Orders.Add(order);
db.OutboxMessages.Add(new OutboxMessage(Guid.NewGuid(), "OrderCreated", payload));
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
~~~

## 5. Real production scenario
Order API commit đơn hàng trong lúc Service Bus outage 10 phút. Event vẫn nằm trong Outbox để publisher gửi lại sau.

## 6. Failure scenario & troubleshooting
Symptom → Outbox backlog tăng. Evidence → unprocessed rows + broker failures. Diagnosis → publisher outage/poison payload. Fix → bounded retry, backoff, quarantine/DLQ. Verification → backlog drain mà consumer không tạo duplicate side effect.

## 7. Common mistakes
Nghĩ Outbox tạo exactly-once; không index ProcessedAt; transaction chứa network call; consumer không idempotent; xóa message khi publish outcome còn ambiguous.

## 8. Alternatives
Direct publish đơn giản hơn nếu mất event chấp nhận được. CDC giảm application publisher logic nhưng tăng infrastructure.

## 9. Trade-offs
### Advantages
Không mất publish intent sau DB commit.
### Costs / Risks
Eventual consistency, duplicate delivery, backlog monitoring và cleanup.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu DB commit và broker publish không atomic.
### Middle
Implement Outbox + worker.
### Senior
Xử lý ambiguous publish, idempotency và ordering.
### Technical Lead / Architect
Chỉ dùng pattern nơi consistency requirement biện minh operational cost.

## 11. Key takeaway
- Outbox bảo vệ intent, không tạo exactly-once.
- Consumer idempotency vẫn bắt buộc.
- Backlog phải là monitored production signal.

# 4. SQL Server deadlock và wait-for cycle

## 1. What is it?
Deadlock là chu trình chờ: transaction A giữ resource B cần, còn B giữ resource A cần. SQL Server chọn một victim để rollback.

## 2. Why does it exist?
Concurrency cần locking để bảo vệ consistency; access order khác nhau giữa transaction có thể tạo cycle dù từng query riêng lẻ hợp lệ.

## 3. How does it work?
~~~text
Tx A: lock Order -> waits Customer
Tx B: lock Customer -> waits Order
~~~
Deadlock detector phát hiện cycle và phá nó bằng rollback victim.

## 4. Practical implementation
Giữ access order nhất quán, transaction ngắn và query có access path tốt. Dùng Extended Events deadlock graph để xem statements, resources và lock modes thực tế.

## 5. Real production scenario
Payment callback và admin approval cùng update Orders/Customers theo thứ tự ngược nhau. Peak traffic làm error 1205 tăng.

## 6. Failure scenario & troubleshooting
Symptom → error 1205. Evidence → deadlock graph. Diagnosis → lock-order inversion. Fix → thống nhất order, rút ngắn transaction, cải thiện access path; retry victim nếu operation an toàn. Verification → workload test không tái tạo cycle.

## 7. Common mistakes
Tăng timeout; thêm NOLOCK; retry vô hạn; transaction chứa HTTP call; chỉ tối ưu victim query thay vì cả cycle.

## 8. Alternatives
Snapshot-based isolation giảm một số reader/writer blocking nhưng không loại mọi deadlock. Optimistic concurrency giải quyết vấn đề khác: lost update.

## 9. Trade-offs
### Advantages
Locking bảo vệ consistency.
### Costs / Risks
Transaction dài và isolation mạnh tăng contention.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Phân biệt blocking và deadlock.
### Middle
Biết error 1205 và transaction boundary.
### Senior
Đọc deadlock graph/index/access order.
### Technical Lead / Architect
Thiết kế transaction + retry semantics không tạo duplicate side effect.

## 11. Key takeaway
- Deadlock là cycle, không đơn giản là query chậm.
- Deadlock graph là evidence chính.
- Retry là safety net, không thay root-cause fix.

# 5. Redis outage strategy và controlled fallback

## 1. What is it?
Redis có thể là distributed cache, nhưng kiến trúc phải xác định nó chỉ tăng performance hay correctness/availability của application phụ thuộc vào nó.

## 2. Why does it exist?
Cache giảm latency và DB load. Nhưng nếu Redis down làm mọi request fail hoặc fallback flood DB, optimization đã trở thành hidden critical dependency.

## 3. How does it work?
Cache-aside: API → Redis GET; hit trả ngay; miss → DB → Redis SET. Khi Redis unavailable cần fail-open, fail-closed hoặc degraded mode có chủ đích.

## 4. Practical implementation
Catch Redis timeout ngắn và fallback DB chỉ với bounded concurrency/rate limit. Không retry cache nhiều lần trước khi query source of truth.

## 5. Real production scenario
Catalog có 90% hit ratio. Redis outage chuyển 500 QPS DB traffic thành 5,000 QPS; SQL cũng sập vì uncontrolled fallback.

## 6. Failure scenario & troubleshooting
Symptom → Redis errors rồi DB CPU tăng. Evidence → hit ratio 0, DB QPS 10x. Diagnosis → fallback không bounded. Fix → short timeout, load shedding, stale-if-acceptable, concurrency limit. Verification → chaos test Redis-off vẫn giữ critical API trong SLO.

## 7. Common mistakes
Redis timeout dài; retry storm; cache mọi thứ; không đo hit ratio; distributed lock không có failure semantics.

## 8. Alternatives
IMemoryCache cho per-instance data; CDN cho HTTP content; DB/materialized view nếu query đủ rẻ.

## 9. Trade-offs
### Advantages
Latency thấp và giảm origin load.
### Costs / Risks
Staleness, invalidation, infrastructure và cascading failure.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Cache không phải source of truth.
### Middle
Cache-aside, TTL, fallback.
### Senior
Stampede protection, outage capacity, timeout.
### Technical Lead / Architect
Quyết định Redis có thật sự cần tồn tại và availability dependency là gì.

## 11. Key takeaway
- “Có fallback” chưa đủ; fallback phải chịu production load.
- Cache outage cần load-test.
- Cache chỉ là optimization khi correctness không phụ thuộc vào nó.

# 6. Azure App Service deployment slots và database compatibility

## 1. What is it?
Deployment slot chạy version mới song song production để warm, validate rồi swap traffic/configuration.

## 2. Why does it exist?
Direct deployment có cold start, transient 5xx và rollback chậm. Slot giảm release blast radius nhưng không tự giải quyết database schema.

## 3. How does it work?
~~~text
artifact -> staging -> warm/health -> swap -> production
                         |
                       rollback
~~~

## 4. Practical implementation
Dùng readiness health check và migration theo expand/contract: thêm schema compatible trước, deploy code mới, cleanup destructive change ở release sau.

## 5. Real production scenario
Version N đọc cột cũ; N+1 muốn đổi schema. Trong swap hai version có thể cùng tồn tại. Drop cột trước swap làm version N lỗi.

## 6. Failure scenario & troubleshooting
Symptom → swap thành công nhưng 5xx tăng. Evidence → missing-column logs. Diagnosis → schema không backward-compatible. Fix → rollback slot và transitional schema. Verification → smoke test old/new binaries với cùng schema.

## 7. Common mistakes
Xem swap như transaction; destructive migration cùng release; health check quá nông; không phân biệt slot settings; không test rollback.

## 8. Alternatives
Blue-Green/Canary trên Container Apps/Kubernetes; rolling deployment. Slot đơn giản hơn cho App Service.

## 9. Trade-offs
### Advantages
Warm release, quick swap/rollback.
### Costs / Risks
Capacity/config complexity; DB compatibility vẫn là trách nhiệm team.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu staging/production chạy song song.
### Middle
Deploy, smoke test, swap.
### Senior
Backward-compatible migration và telemetry gate.
### Technical Lead / Architect
Chọn release strategy theo blast radius, data migration và SLO.

## 11. Key takeaway
- Slot không giải quyết schema compatibility.
- Migration quyết định rollback safety.
- Release cần health + telemetry validation.

# 7. OpenTelemetry distributed tracing

## 1. What is it?
Distributed trace biểu diễn một request xuyên nhiều component bằng trace/span hierarchy. OpenTelemetry chuẩn hóa instrumentation/export.

## 2. Why does it exist?
Logs riêng từng service khó trả lời “thời gian đi đâu?”. Correlation ID giúp tìm log; trace còn thể hiện timing và parent-child dependency.

## 3. How does it work?
~~~text
Trace
 |- ASP.NET Core request 420ms
 |- SQL 35ms
 +- Product API 330ms
     +- downstream SQL 280ms
~~~
W3C Trace Context truyền traceparent qua HTTP.

## 4. Practical implementation
~~~csharp
builder.Services.AddOpenTelemetry()
 .WithTracing(t => t
   .AddAspNetCoreInstrumentation()
   .AddHttpClientInstrumentation()
   .AddEntityFrameworkCoreInstrumentation());
~~~

## 5. Real production scenario
Checkout p95 từ 600 ms lên 1.8 s. Trace chỉ ra 70% duration nằm ở Reviews API downstream, không phải SQL local.

## 6. Failure scenario & troubleshooting
Symptom → trace đứt giữa services. Evidence → trace ID đổi sau proxy/custom client. Diagnosis → context propagation bị strip. Fix → chuẩn hóa inject/extract. Verification → một trace xuyên ingress đến dependency.

## 7. Common mistakes
Sample 100% traffic lớn; high-cardinality attributes; log token/PII; instrument quá chi tiết; chỉ có traces mà thiếu metrics.

## 8. Alternatives
Application Insights auto-instrumentation có thể đủ cho Azure-centric system; correlation logs đơn giản hơn nhưng kém topology/timing.

## 9. Trade-offs
### Advantages
Localize latency/failure nhanh, vendor-neutral.
### Costs / Risks
Telemetry volume, storage cost, sampling và privacy.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu trace/span/correlation.
### Middle
Instrument HTTP/DB.
### Senior
Sampling, attributes và Logs + Metrics + Traces workflow.
### Technical Lead / Architect
Đặt observability standard và cost/privacy guardrails.

## 11. Key takeaway
- Trace trả lời “thời gian đi đâu?”.
- Context propagation quyết định trace continuity.
- Observability không chỉ là logging.

# 8. Kubernetes resource requests/limits với .NET

## 1. What is it?
requests giúp scheduler đặt Pod; limits đặt trần runtime. CPU vượt limit thường bị throttling; memory vượt limit có thể OOMKilled.

## 2. Why does it exist?
Không có governance, noisy neighbor chiếm node. Nhưng sizing sai lại tự tạo latency hoặc restart.

## 3. How does it work?
~~~yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
~~~
Scheduler dùng requests; cgroup enforcement áp limits.

## 4. Practical implementation
Load-test .NET API, đo CPU p95, working set, GC heap và allocation rồi đặt headroom. Không copy values từ service khác.

## 5. Real production scenario
Batch JSON lớn đẩy process vượt 512 MiB. Pod bị OOMKilled và restart dù node còn memory tổng thể.

## 6. Failure scenario & troubleshooting
Symptom → CrashLoopBackOff. Evidence → kubectl describe pod: OOMKilled. Diagnosis → correlate workload với GC/working set. Fix → sửa allocation/leak hoặc resize sau measurement. Verification → soak test không restart.

## 7. Common mistakes
Chỉ tăng memory; CPU limit quá thấp; request=limit theo thói quen; dùng liveness probe che resource issue.

## 8. Alternatives
App Service/Container Apps đơn giản hóa orchestration nếu Kubernetes complexity chưa cần thiết.

## 9. Trade-offs
### Advantages
Isolation và predictable scheduling.
### Costs / Risks
Sai sizing gây throttling, pending hoặc OOM.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Phân biệt requests/limits.
### Middle
Đọc Pod events/metrics.
### Senior
Liên hệ .NET GC với container constraints.
### Technical Lead / Architect
Capacity/autoscaling theo SLO và measured workload.

## 11. Key takeaway
- CPU và memory limits fail khác nhau.
- Sizing phải dựa trên measurement.
- OOMKilled là evidence, chưa phải root cause cuối.

# 9. Optimizely CMS content modeling

## 1. What is it?
Content modeling định nghĩa content types và composition editor quản lý. Trong Optimizely CMS, Page thường là routable content; Block là reusable/composable content.

## 2. Why does it exist?
Blob HTML linh hoạt nhưng khó reuse/search/evolve; model quá cứng khiến mọi editorial change cần deployment.

## 3. How does it work?
~~~text
ProductLandingPage
 |- HeroBlock
 |- PromoGridBlock
 +- FAQBlock

Product price/inventory -> Product API
Editorial copy/layout -> CMS
~~~

## 4. Practical implementation
Model field theo semantic intent như Heading, Image, CTA Link thay vì CSS-oriented LeftText/BlueButton. Content type cần defaults/validation để content cũ vẫn render.

## 5. Real production scenario
Marketing reuse Hero trên nhiều campaign. Giá sản phẩm thay đổi từ commerce API; đưa price vào CMS tạo stale data và ownership conflict.

## 6. Failure scenario & troubleshooting
Symptom → content cũ lỗi sau deployment. Evidence → field mới null/renamed. Diagnosis → model evolution breaking. Fix → tolerant rendering, defaults, migration. Verification → staging render cả old/new content.

## 7. Common mistakes
Block mirror UI component; duplicate business data vào CMS; breaking field removal; cache không invalidate khi publish.

## 8. Alternatives
Headless CMS tách frontend mạnh hơn; coupled CMS đơn giản hơn cho server-rendered site; static config đủ cho content không cần editorial workflow.

## 9. Trade-offs
### Advantages
Editor autonomy, reuse, structured content.
### Costs / Risks
Migration, caching, preview/publish và coupling nếu model bám UI.

# 10. RAG security: prompt injection và data authorization

## 1. What is it?
RAG đưa retrieved documents vào LLM context. Security boundary nằm ở authentication, authorization, retrieval filters, tool permissions và deterministic application logic—not ở prompt.

## 2. Why does it exist?
Model có thể bị prompt injection từ user hoặc document. Nếu retriever đưa dữ liệu unauthorized vào context, system prompt “không tiết lộ” không phải access control.

## 3. How does it work?
~~~mermaid
flowchart LR
 U[User] --> A[API/AuthZ]
 A --> R[Retriever + ACL]
 R --> V[(Search/Vector Index)]
 R --> L[LLM]
 L --> P[Policy validation]
 P --> U
~~~
Authorization phải xảy ra trước khi sensitive context được đưa vào model.

## 4. Practical implementation
Lấy tenant/security principal từ verified identity claims rồi áp ACL filter trực tiếp trong search query. Không nhận tenant ID tùy ý từ request body. Tool calls có side effect phải re-authorize server-side.

## 5. Real production scenario
Internal assistant search tài liệu nhiều khách hàng. Một PDF chứa “ignore previous instructions”. Text retrieved phải được xem là untrusted data, không phải privileged instruction.

## 6. Failure scenario & troubleshooting
Symptom → user thấy citation tenant khác. Evidence → retrieval trace có ACL mismatch. Diagnosis → authorization chỉ chạy sau generation. Fix → enforce ACL tại retrieval/partition layer. Verification → adversarial cross-tenant tests không retrieve unauthorized docs.

## 7. Common mistakes
Dùng prompt như authorization; agent tool quyền quá rộng; index secrets; log full prompt chứa PII; để model quyết định payment/approval authorization.

## 8. Alternatives
Search UI không LLM đơn giản hơn nếu chỉ cần retrieval. Deterministic workflow phù hợp operation yêu cầu correctness cao. Fine-tuning không thay authorization.

## 9. Trade-offs
### Advantages
Private/fresh knowledge mà không retrain; có thể cung cấp citations.
### Costs / Risks
Retrieval leakage, injection, latency, token cost và evaluation complexity.

## 10. Junior → Middle → Senior → Technical Lead
### Junior
Hiểu retrieved text là untrusted data.
### Middle
ACL-filtered retrieval, safe logging, timeout.
### Senior
Threat-model injection, cross-tenant leakage và tool abuse.
### Technical Lead / Architect
Giữ authorization và destructive actions trong deterministic control plane.

## 11. Key takeaway
- Prompt không phải security boundary.
- Authorization phải xảy ra trước context exposure.
- High-impact logic phải được deterministic enforcement.
