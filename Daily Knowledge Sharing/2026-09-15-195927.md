# 1. C# `Span<T>` và `Memory<T>`: zero-copy slices, lifetime rules và khi optimization làm API khó dùng hơn

## 1. What is it?

`Span<T>` là view liên tục trên một vùng memory mà không cần copy dữ liệu. Nó có thể trỏ vào array, stack memory hoặc unmanaged memory. `Memory<T>` có mental model tương tự nhưng có thể sống qua asynchronous boundaries và được lưu trên heap.

```text
byte[] buffer
┌──────────────────────────────┐
│ header │ payload │ checksum  │
└──────────────────────────────┘
          ↑
       Span<byte>
       chỉ là view
```

`Span<T>` là `ref struct`, nên compiler áp lifetime restrictions để reference không sống lâu hơn memory mà nó trỏ tới.

## 2. Why does it exist?

Parser hoặc protocol code thường chỉ cần đọc một đoạn của buffer. Nếu mỗi slice tạo array/string mới, allocation rate và copy cost có thể trở thành bottleneck trên hot path.

`Span<T>` cho phép slicing gần như chỉ bằng offset + length. Nhưng mục tiêu không phải loại bỏ mọi allocation; nó hữu ích nhất khi profiling cho thấy copying/allocation thực sự đáng kể.

## 3. How does it work?

```csharp
ReadOnlySpan<byte> packet = buffer;
ReadOnlySpan<byte> header = packet[..8];
ReadOnlySpan<byte> payload = packet[8..^4];
```

Các slices cùng nhìn vào backing memory. Không có payload array mới được tạo.

`Span<T>` không được capture bởi lambda, boxed, stored như field của class hoặc sống qua `await`. Khi cần asynchronous lifetime, dùng `Memory<T>`:

```csharp
await stream.WriteAsync(memory, cancellationToken);
```

## 4. Practical implementation

Một parser đơn giản:

```csharp
public static bool TryReadLength(
    ReadOnlySpan<byte> input,
    out int length)
{
    if (input.Length < 4)
    {
        length = 0;
        return false;
    }

    length = BinaryPrimitives.ReadInt32BigEndian(input[..4]);
    return true;
}
```

Không cần `input.Take(4).ToArray()` chỉ để parse integer.

## 5. Real production scenario

Một API import CSV lớn. Profiling cho thấy parser tạo hàng triệu substring và temporary arrays. Team chuyển hot parsing path sang `ReadOnlySpan<char>` và giảm allocation đáng kể. Họ không đổi toàn application sang Span-based APIs vì business-layer readability không được lợi.

## 6. Failure scenario & troubleshooting

**Symptom** → optimization refactor làm code không compile khi `Span<T>` được dùng qua `await`.

**Evidence** → compiler báo ref-struct lifetime violation.

**Hypothesis** → view stack-scoped đang được giữ qua asynchronous suspension.

**Diagnosis** → xác định dữ liệu cần sống tới sau `await` hay chỉ parsing trước đó.

**Fix** → hoàn tất Span processing trước `await`, hoặc chuyển boundary sang `Memory<T>`/owned array.

**Verification** → benchmark allocation và test correctness với buffer boundaries.

## 7. Common mistakes

* Dùng `Span<T>` vì thấy “performance” mà không benchmark.
* Convert span trở lại array/string ngay lập tức, mất lợi ích zero-copy.
* Nhầm `Memory<T>` là owner của memory; nó vẫn chỉ là view.
* Expose low-level Span API lên business layer không có nhu cầu.

## 8. Alternatives

Array/string slicing đơn giản hơn khi workload nhỏ. `ArrayPool<T>` giải quyết buffer reuse, không cùng bài toán với Span slicing. `MemoryPool<T>` hữu ích khi cần explicit memory ownership.

## 9. Trade-offs

### Advantages

* Giảm copy và allocation trên hot paths.
* API parsing có thể rất hiệu quả.

### Costs / Risks

* Lifetime rules phức tạp hơn.
* API khó compose qua async boundaries.
* Optimization có thể làm code khó đọc mà không tạo measurable benefit.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Span là view, không phải copy.

### Middle

Biết slicing, `ReadOnlySpan<T>` và async boundary.

### Senior

Dùng profiler/BenchmarkDotNet để chứng minh lợi ích và quản lý ownership/lifetime.

### Technical Lead / Architect

Giới hạn zero-copy complexity ở infrastructure/hot path thay vì lan ra toàn domain API.

## 11. Key takeaway

* `Span<T>` tối ưu access/copy, không phải business abstraction.
* Lifetime restrictions là safety feature.
* Chỉ đổi simplicity lấy zero-copy khi measurement chứng minh cần thiết.

# 2. ASP.NET Core graceful shutdown: `CancellationToken`, request draining và background work khi App Service/container bị terminate

## 1. What is it?

Graceful shutdown là quá trình application ngừng nhận work mới, cho work đang chạy cơ hội hoàn tất trong một khoảng thời gian hữu hạn, rồi đóng resources sạch sẽ trước khi process bị terminate.

## 2. Why does it exist?

Production process thường bị dừng vì deployment, autoscaling, node maintenance hoặc crash recovery. Nếu application coi shutdown là sự kiện hiếm, in-flight request, message hoặc file processing có thể bị cắt giữa chừng.

Graceful shutdown không đảm bảo mọi work hoàn tất; nó tạo protocol rõ ràng để dừng có kiểm soát.

## 3. How does it work?

```text
Platform sends termination
        ↓
Host stopping token cancelled
        ↓
Stop accepting new work
        ↓
Drain requests / stop consumers
        ↓
Finish or checkpoint in-flight work
        ↓
Dispose resources
        ↓
Process exits before hard timeout
```

ASP.NET Core host cung cấp cancellation tokens cho lifecycle và request cancellation.

## 4. Practical implementation

Background worker phải tôn trọng stopping token:

```csharp
public sealed class QueueWorker : BackgroundService
{
    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var item = await queue.ReceiveAsync(stoppingToken);
            await ProcessAsync(item, stoppingToken);
        }
    }
}
```

Không swallow `OperationCanceledException` rồi tiếp tục loop vô hạn khi host đang stop.

## 5. Real production scenario

Một App Service deployment recycle instance trong lúc worker đang tạo PDF 40 giây. Worker bỏ qua cancellation và platform hard-kill process sau shutdown window. Job bị xử lý lại nhưng code không idempotent, tạo hai documents.

Thiết kế tốt hơn là checkpoint hoặc dùng queue message settlement để uncompleted work quay lại queue an toàn.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate jobs tăng đúng lúc deployments.

**Evidence** → logs kết thúc đột ngột, message chưa complete nhưng side effect đã tạo một phần.

**Hypothesis** → shutdown interrupt non-idempotent operation.

**Diagnosis** → correlate deployment/restart telemetry với processing IDs.

**Fix** → propagate cancellation, shorten atomic units, settle message sau durable side effect và thêm idempotency.

**Verification** → terminate instance trong integration/load test giữa processing.

## 7. Common mistakes

* Bắt cancellation như error và retry ngay trong same stopping process.
* Bắt đầu work mới sau shutdown signal.
* Assume `finally` luôn có vô hạn thời gian chạy.
* Giữ job dài hàng phút trong web process mà không có recovery semantics.

## 8. Alternatives

Queue-triggered Worker Service/Azure Functions có thể phù hợp hơn web-hosted background work. Durable workflow phù hợp long-running stateful orchestration.

## 9. Trade-offs

### Advantages

Giảm partial work và deployment-related failures.

### Costs / Risks

Cần idempotency/checkpointing; platform hard timeout vẫn tồn tại; shutdown logic tăng lifecycle complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu process có thể bị stop bất kỳ lúc nào.

### Middle

Propagate `CancellationToken` và cleanup đúng.

### Senior

Thiết kế recoverable/idempotent background work.

### Technical Lead / Architect

Chọn hosting boundary và shutdown budget theo workload, không nhét mọi job vào web app.

## 11. Key takeaway

* Graceful shutdown là bounded opportunity, không phải guarantee.
* Cancellation phải propagate tới I/O và worker loops.
* Durable work cần recovery/idempotency ngay cả khi shutdown được xử lý tốt.

# 3. EF Core split queries: tránh Cartesian explosion nhưng không biến nhiều round trips thành mặc định

## 1. What is it?

Khi query một root entity cùng nhiều collection navigations bằng `Include`, single SQL query có thể tạo Cartesian multiplication. EF Core split query tách việc load collections thành nhiều SQL queries rồi fix-up object graph ở client.

## 2. Why does it exist?

Ví dụ một `Order` có 50 `Lines` và 20 `Notes`. Join cả hai collections có thể tạo 1.000 result rows cho một order dù dữ liệu logic chỉ 71 records.

Duplicated root columns làm tăng network transfer, database work và materialization cost.

## 3. How does it work?

Single query:

```text
Orders
 JOIN Lines
 JOIN Notes
     ↓
rows multiplied
```

Split query:

```text
Query Orders
Query Lines for Orders
Query Notes for Orders
       ↓
EF correlates results
```

EF Core dùng identity/correlation information để ghép navigations về đúng entities.

## 4. Practical implementation

```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Include(x => x.Lines)
    .Include(x => x.Notes)
    .AsSplitQuery()
    .Where(x => x.CustomerId == customerId)
    .Take(50)
    .ToListAsync(cancellationToken);
```

Tốt hơn nữa, nếu API chỉ cần summary, projection thường thắng cả Include và split query:

```csharp
var result = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Select(x => new
    {
        x.Id,
        LineCount = x.Lines.Count,
        NoteCount = x.Notes.Count
    })
    .ToListAsync(cancellationToken);
```

## 5. Real production scenario

Order details API Include Lines, Discounts và AuditEntries. SQL trả hàng chục nghìn rows cho vài chục logical entities. Application Insights cho thấy dependency payload/time tăng mạnh sau khi thêm Include mới.

`AsSplitQuery()` giảm multiplication; sau đó team còn projection để tránh load fields không dùng.

## 6. Failure scenario & troubleshooting

**Symptom** → sau chuyển split query, latency tăng ở network có RTT cao.

**Evidence** → row count giảm nhưng database round trips tăng từ 1 lên 4.

**Hypothesis** → Cartesian cost đã nhỏ hơn round-trip cost.

**Diagnosis** → đo SQL duration, transferred rows và round trips.

**Fix** → projection, single query có kiểm soát hoặc reshape endpoint.

**Verification** → benchmark với production-like cardinality/latency.

## 7. Common mistakes

* Bật split queries globally để “fix performance”.
* Include toàn graph thay vì projection.
* Không hiểu consistency implications khi nhiều queries đọc dữ liệu thay đổi giữa các statements.
* Tối ưu theo số SQL statements thay vì total cost.

## 8. Alternatives

Projection là lựa chọn tốt cho read API. Explicit separate queries cho phép control rõ hơn. Single query phù hợp khi cardinality nhỏ.

## 9. Trade-offs

### Advantages

Giảm Cartesian explosion và duplicated payload.

### Costs / Risks

Tăng round trips và có thể quan sát snapshots khác nhau nếu data thay đổi giữa queries tùy isolation semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Include có thể nhân rows.

### Middle

Biết dùng `AsSplitQuery()` và projection.

### Senior

Đo cardinality, network RTT, materialization và consistency.

### Technical Lead / Architect

Định hình read contracts để API không yêu cầu load aggregate graph khổng lồ chỉ vì ORM cho phép.

## 11. Key takeaway

* Split query đổi row multiplication lấy round trips.
* Projection thường là optimization quan trọng hơn.
* Chọn dựa trên measured access pattern.

# 4. SQL Server deadlock: wait-for cycle, victim selection và điều tra bằng execution plan thay vì chỉ retry

## 1. What is it?

Deadlock xảy ra khi hai hoặc nhiều transactions giữ resources mà transaction khác cần và tạo vòng chờ không thể tự tiến triển.

```text
Tx A holds Row 1 → waits Row 2
Tx B holds Row 2 → waits Row 1
```

SQL Server phát hiện cycle và chọn một victim để rollback, giải phóng vòng chờ.

## 2. Why does it exist?

Locks bảo vệ transaction consistency. Khi transactions acquire locks theo thứ tự khác nhau hoặc giữ locks quá lâu, concurrency có thể tạo cycle.

Deadlock không đồng nghĩa database “hỏng”; nó là emergent behavior của concurrent access patterns.

## 3. How does it work?

Deadlock monitor phân tích wait graph. Một transaction bị terminate với error 1205. Victim selection cân nhắc deadlock priority và rollback cost.

Root cause thường nằm ở access order, missing/inefficient index khiến lock footprint lớn, hoặc transaction boundary quá rộng.

## 4. Practical implementation

Giữ access order nhất quán:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

var first = await db.Accounts.SingleAsync(x => x.Id == smallerId, ct);
var second = await db.Accounts.SingleAsync(x => x.Id == largerId, ct);

// update in deterministic order
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Retry transient deadlock có thể hợp lý nếu operation idempotent/replay-safe, nhưng retry không thay thế root-cause fix.

## 5. Real production scenario

Transfer workflow A update Account rồi Ledger; reconciliation job update Ledger rồi Account. Dưới tải, hai transactions giao nhau và deadlock frequency tăng.

Team trước đây chỉ retry 3 lần. Hệ thống “chạy được” nhưng latency tail tăng. Chuẩn hóa access order và thu hẹp transaction giảm deadlocks tận gốc.

## 6. Failure scenario & troubleshooting

**Symptom** → sporadic SQL error 1205 và p99 tăng.

**Evidence** → deadlock graph cho thấy two statements/locks tạo cycle.

**Hypothesis** → inconsistent access order hoặc scan lock footprint lớn.

**Diagnosis** → đọc deadlock graph cùng actual execution plans/index usage.

**Fix** → consistent order, better access path, shorter transaction hoặc giảm contention.

**Verification** → replay concurrent workload và theo dõi deadlock count.

## 7. Common mistakes

* Retry vô hạn.
* Dùng `NOLOCK` như deadlock cure.
* Chỉ nhìn victim statement mà không nhìn statement đang giữ lock.
* Giữ transaction mở qua HTTP call/user interaction.

## 8. Alternatives

Optimistic concurrency giải quyết lost updates nhưng không loại mọi DB locking. Snapshot-based isolation có thể giảm reader/writer blocking, nhưng write/write contention vẫn tồn tại.

## 9. Trade-offs

### Advantages

Locks cung cấp correctness mạnh cho transactional updates.

### Costs / Risks

Contention và deadlocks tăng khi transaction footprint/lifetime lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt blocking và deadlock.

### Middle

Đọc error 1205 và viết replay-safe retry khi phù hợp.

### Senior

Đọc deadlock graph, plans, locks và transaction ordering.

### Technical Lead / Architect

Thiết kế write workflows/data ownership để giảm hot shared resources thay vì chỉ tuning retry count.

## 11. Key takeaway

* Deadlock là cycle, không chỉ slow lock wait.
* Retry xử lý symptom; access pattern mới quyết định root cause.
* Transaction ngắn và deterministic ordering thường rất giá trị.

# 5. Elasticsearch alias + reindex: thay đổi mapping production mà không khóa Search API vào một index vật lý

## 1. What is it?

Elasticsearch alias là logical name trỏ tới một hoặc nhiều indices. Search API có thể query alias `products-read` thay vì hard-code `products-v17`.

Mapping changes không phải lúc nào cũng sửa in-place được. Reindex tạo index mới, copy/rebuild documents rồi atomically chuyển alias.

## 2. Why does it exist?

Search schema tiến hóa: analyzer, tokenizer, field type hoặc index settings thay đổi. Nếu clients biết physical index name, migration buộc coordinated deployment và downtime/risk cao hơn.

Alias tạo indirection ở đúng infrastructure boundary.

## 3. How does it work?

```text
Search API → products-read → products-v17

Create products-v18
       ↓
Reindex / backfill
       ↓
Validate
       ↓
Atomic alias switch
       ↓
Search API → products-read → products-v18
```

Primary database vẫn là source of truth; reindex có thể rebuild từ authoritative source hoặc existing index tùy change.

## 4. Practical implementation

Alias switch request:

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v17", "alias": "products-read" } },
    { "add":    { "index": "products-v18", "alias": "products-read" } }
  ]
}
```

Application config chỉ dùng `products-read`.

## 5. Real production scenario

E-commerce search cần đổi analyzer cho product names. Reindex 40 triệu documents mất hàng giờ. Team build `v18` song song, validate search relevance và document counts rồi switch alias trong một metadata operation.

## 6. Failure scenario & troubleshooting

**Symptom** → sau alias switch, một số recent products biến mất.

**Evidence** → backfill snapshot kết thúc trước khi concurrent changes được replay sang new index.

**Hypothesis** → migration thiếu catch-up synchronization.

**Diagnosis** → compare primary DB change sequence/outbox offsets với new index.

**Fix** → dual-write/change-stream catch-up hoặc replay events từ known checkpoint trước switch.

**Verification** → compare counts/checksums/sample queries và synchronization lag.

## 7. Common mistakes

* Reindex rồi switch mà không xử lý writes phát sinh trong migration window.
* Xóa old index ngay, mất rollback option.
* Hard-code physical index names trong application.
* Validate chỉ document count mà không validate search semantics.

## 8. Alternatives

In-place compatible mapping additions có thể đủ. Blue/green index pattern bằng application config cũng làm được nhưng alias switch tập trung hơn.

## 9. Trade-offs

### Advantages

* Near-zero-downtime schema evolution.
* Rollback nhanh khi giữ old index.
* Application tách khỏi physical index lifecycle.

### Costs / Risks

* Tạm dùng gấp đôi storage/compute.
* Catch-up synchronization phức tạp.
* Relevance validation không thể chỉ tự động bằng count.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu alias là logical pointer.

### Middle

Tạo versioned index, reindex và switch alias.

### Senior

Thiết kế catch-up, rollback và relevance verification.

### Technical Lead / Architect

Định nghĩa search indexing pipeline, source of truth và migration ownership.

## 11. Key takeaway

* Alias tách application contract khỏi index lifecycle.
* Reindex migration phải xử lý concurrent writes.
* Search correctness gồm relevance, không chỉ document count.

# 6. Hexagonal Architecture và Anti-Corruption Layer: cô lập third-party contracts khỏi domain mà không xây abstraction cho mọi class

## 1. What is it?

Hexagonal Architecture tổ chức system quanh application/domain core và các ports mô tả capability cần thiết. Adapters kết nối ports với database, HTTP, messaging hoặc third-party systems.

Anti-Corruption Layer (ACL) là translation boundary ngăn external model lan vào domain model.

## 2. Why does it exist?

Nếu domain dùng trực tiếp DTO, enum và error semantics của vendor, vendor contract trở thành implicit domain model. Một breaking change bên ngoài kéo theo thay đổi khắp application.

Boundary có giá trị khi external model khác business language hoặc thay đổi độc lập.

## 3. How does it work?

```text
Domain/Application
      ↓ port
IReviewProvider
      ↑
VendorReviewAdapter
      ↓
Third-party API
```

Adapter map external DTO thành internal concepts và translate failures sang semantics application hiểu.

## 4. Practical implementation

```csharp
public interface IReviewProvider
{
    Task<ProductRating?> GetRatingAsync(
        string productId,
        CancellationToken cancellationToken);
}

public sealed class VendorReviewAdapter(HttpClient client)
    : IReviewProvider
{
    public async Task<ProductRating?> GetRatingAsync(
        string productId,
        CancellationToken cancellationToken)
    {
        var dto = await client.GetFromJsonAsync<VendorRatingDto>(
            $"ratings/{productId}", cancellationToken);

        return dto is null
            ? null
            : new ProductRating(dto.Score, dto.ReviewCount);
    }
}
```

Domain không cần biết `VendorRatingDto`.

## 5. Real production scenario

Commerce platform đổi review provider. Vì vendor DTO từng bị dùng trực tiếp trong controllers, cache và domain services, migration chạm hàng chục modules.

Sau khi đưa integration qua ACL, lần thay vendor tiếp theo chủ yếu thay adapter/mapping và contract tests.

## 6. Failure scenario & troubleshooting

**Symptom** → vendor thêm enum value mới làm deserialization hoặc business switch fail.

**Evidence** → external enum leak trực tiếp vào domain.

**Hypothesis** → ACL không thực sự translate semantics.

**Diagnosis** → trace external types xuyên dependency graph.

**Fix** → tolerant external parsing + explicit mapping sang internal representation.

**Verification** → contract test unknown/new vendor values.

## 7. Common mistakes

* Tạo interface cho mọi class dù không có boundary/change pressure.
* ACL chỉ rename DTO nhưng vẫn giữ nguyên vendor semantics.
* Domain project reference vendor SDK.
* Che giấu useful failure details tới mức troubleshooting khó.

## 8. Alternatives

Simple layered architecture đủ cho CRUD app nhỏ. Direct SDK usage hợp lý nếu integration rất nhỏ và switching/semantic isolation không có giá trị.

## 9. Trade-offs

### Advantages

Change isolation, testability và domain language sạch hơn.

### Costs / Risks

Mapping code, abstraction overhead và nguy cơ overengineering.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu adapter chuyển external contract sang internal model.

### Middle

Implement port/adapter và mapping tests.

### Senior

Chọn boundary theo volatility/semantic mismatch, không theo pattern purity.

### Technical Lead / Architect

Quyết định integrations nào đáng ACL và ownership/dependency direction của chúng.

## 11. Key takeaway

* Architecture boundary có giá trị khi nó cô lập change/semantics thật.
* ACL phải translate model, không chỉ wrap SDK.
* Không cần interface cho mọi class để gọi là Hexagonal Architecture.

# 7. Azure Blob Storage SAS: delegated access, least privilege và lifecycle của upload/download URL

## 1. What is it?

Shared Access Signature (SAS) là signed token cấp quyền giới hạn lên Azure Storage resource trong phạm vi và thời gian xác định, ví dụ chỉ upload một blob trong 10 phút.

## 2. Why does it exist?

Nếu client upload file qua API server, application phải proxy toàn bộ bytes, tăng bandwidth, memory/connection pressure và latency.

Không thể đưa Storage account key cho browser/mobile. SAS cho phép backend cấp delegated access có giới hạn.

## 3. How does it work?

```text
Client → API: request upload permission
API authenticates/authorizes
API → Client: short-lived SAS
Client → Blob Storage: upload directly
Client → API: confirm metadata
```

SAS có scope, permissions, start/expiry và signature. User Delegation SAS dùng Microsoft Entra credentials thay vì account key và thường phù hợp security posture tốt hơn.

## 4. Practical implementation

Backend nên authorize business object trước khi phát SAS và tạo blob name server-side, ví dụ:

```text
tenant/{tenantId}/documents/{documentId}/{generatedFileName}
```

Permissions chỉ cần `Create`/`Write`, expiry ngắn. Download SAS chỉ cấp `Read` nếu object không public.

## 5. Real production scenario

CMS cho editor upload video 500 MB. Proxy qua ASP.NET Core khiến App Service bandwidth/connection usage tăng. Direct-to-Blob SAS chuyển data path ra khỏi web app, còn API giữ control plane: identity, metadata và authorization.

## 6. Failure scenario & troubleshooting

**Symptom** → SAS URL bị leak trong logs và vẫn dùng được hàng giờ.

**Evidence** → expiry 24 giờ và query string được logging đầy đủ.

**Hypothesis** → delegated credential lifetime/sensitive logging quá rộng.

**Diagnosis** → inspect SAS generation và HTTP logging policies.

**Fix** → expiry ngắn, redact query strings, scope xuống blob cụ thể và permission tối thiểu.

**Verification** → security test expired/wrong-blob/wrong-operation requests.

## 7. Common mistakes

* SAS cấp container-wide write khi chỉ cần một blob.
* Expiry quá dài.
* Cho client tự quyết blob path chứa tenant ID.
* Log full SAS URL.
* Nghĩ SAS thay thế application authorization.

## 8. Alternatives

Backend proxy upload phù hợp file nhỏ hoặc cần inline inspection. Managed Identity phù hợp service-to-storage, không trực tiếp cấp browser credential. Public blob chỉ phù hợp genuinely public content.

## 9. Trade-offs

### Advantages

Giảm application data-plane load, scale file transfer tốt và giữ quyền giới hạn.

### Costs / Risks

SAS là bearer credential trong lifetime của nó; revocation và leakage cần cân nhắc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SAS là temporary delegated permission.

### Middle

Cấp scope/permission/expiry đúng và direct upload.

### Senior

Thiết kế naming, malware scanning workflow, logging redaction và revocation strategy.

### Technical Lead / Architect

Tách control plane khỏi data plane và chọn trust boundary phù hợp cho file lifecycle.

## 11. Key takeaway

* SAS không phải account key thu nhỏ; nó vẫn là credential cần bảo vệ.
* Least privilege gồm cả scope, operation và lifetime.
* Direct Blob transfer thường tốt cho large files nhưng authorization vẫn thuộc application.

# 8. Kubernetes readiness vs liveness probes: tránh restart application chỉ vì dependency tạm thời chậm

## 1. What is it?

Readiness probe trả lời: **Pod hiện có nên nhận traffic không?**

Liveness probe trả lời: **Process có bị kẹt đến mức cần restart không?**

Hai câu hỏi khác nhau và không nên dùng cùng dependency checks một cách máy móc.

## 2. Why does it exist?

Một process có thể sống nhưng chưa ready sau startup. Ngược lại, database outage có thể làm app không phục vụ request hữu ích nhưng restart process không sửa được database.

Nếu liveness phụ thuộc SQL/Redis, outage dependency có thể làm Kubernetes restart toàn bộ pods, khuếch đại incident.

## 3. How does it work?

```text
Readiness fails → Pod removed from Service endpoints
Liveness fails  → kubelet restarts container
```

Startup probe có thể bảo vệ slow-starting application khỏi bị liveness kill trước khi initialization hoàn tất.

## 4. Practical implementation

ASP.NET Core tách health checks:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, tags: ["ready"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

Liveness ở đây chủ yếu xác nhận process/pipeline trả response; readiness kiểm tra critical dependency.

## 5. Real production scenario

SQL outage 3 phút. Tất cả pods dùng SQL check cho liveness. Kubernetes restart liên tục, làm startup traffic và connection attempts tăng đúng lúc DB đang phục hồi.

Tách readiness/liveness giúp pods ngừng nhận traffic mà không tạo restart storm.

## 6. Failure scenario & troubleshooting

**Symptom** → `CrashLoopBackOff` đồng thời với external DB outage.

**Evidence** → liveness endpoint fail vì SQL health check.

**Hypothesis** → probe semantics sai.

**Diagnosis** → inspect pod events, probe endpoint và dependency telemetry.

**Fix** → liveness chỉ kiểm tra process-level fatal state; readiness chứa dependency readiness phù hợp.

**Verification** → fault-inject DB outage và xác nhận pods không restart hàng loạt.

## 7. Common mistakes

* Cùng endpoint cho readiness/liveness.
* Probe quá aggressive, timeout ngắn hơn normal GC/startup behavior.
* Health check thực hiện expensive query.
* Readiness yêu cầu mọi optional dependency healthy.

## 8. Alternatives

App Service health checks có semantics platform khác nhưng cùng nguyên tắc: health signal phải dẫn tới remediation phù hợp.

## 9. Trade-offs

### Advantages

Traffic routing và self-healing chính xác hơn.

### Costs / Risks

Probe design sai có thể tự gây outage; dependency graph càng lớn càng khó định nghĩa “ready”.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Nhớ readiness ≠ liveness.

### Middle

Tạo endpoints/tags và cấu hình probes.

### Senior

Fault-test probe behavior và tránh cascading restart.

### Technical Lead / Architect

Định nghĩa health semantics theo remediation: remove traffic, restart hay alert—không theo checklist.

## 11. Key takeaway

* Một health check chỉ hữu ích nếu failure dẫn tới action đúng.
* Dependency outage thường không phải lý do restart process.
* Probe configuration là reliability code.

# 9. Playwright E2E test isolation: deterministic test data, browser state và lý do UI tests dễ flaky

## 1. What is it?

E2E test kiểm tra user flow qua browser, frontend, API và thường cả database/integrations. Test isolation nghĩa là mỗi test có state đủ độc lập để kết quả không phụ thuộc thứ tự, test khác hoặc dữ liệu tồn tại từ run trước.

## 2. Why does it exist?

UI test có nhiều moving parts: browser timing, network, async rendering, shared accounts, backend data và environment. Nếu test dùng chung state, parallel execution làm failures trở nên nondeterministic.

Flaky test làm CI mất credibility: team bắt đầu rerun thay vì điều tra.

## 3. How does it work?

Isolation thường gồm:

```text
unique test identity/data
        +
fresh browser context
        +
deterministic setup via API/fixture
        +
wait on observable UI state
        +
cleanup or disposable environment
```

Playwright browser contexts cung cấp isolated cookies/local storage tương đối rẻ.

## 4. Practical implementation

```typescript
test('manager approves timesheet', async ({ page, request }) => {
  const employee = await createEmployee(request);
  const timesheet = await createSubmittedTimesheet(request, employee.id);

  await loginAsManager(page);
  await page.goto(`/timesheets/${timesheet.id}`);

  await page.getByRole('button', { name: 'Approve' }).click();
  await expect(page.getByText('Approved')).toBeVisible();
});
```

Setup qua API thường nhanh và deterministic hơn click qua UI để tạo mọi prerequisite, trừ khi chính creation flow là behavior cần test.

## 5. Real production scenario

CI chạy 20 workers. Hai tests cùng dùng `test.manager@example.com` và cùng sửa cart/profile. Chạy riêng từng test đều pass; chạy suite parallel thì random fail.

Tạo unique user/data per test và fresh context loại dependency ẩn giữa tests.

## 6. Failure scenario & troubleshooting

**Symptom** → test fail 1/20 runs ở `waitForTimeout(2000)`.

**Evidence** → UI event hoàn tất từ 500 ms đến 4 s tùy CI load.

**Hypothesis** → fixed sleep thay cho condition synchronization.

**Diagnosis** → inspect trace/video/network timeline.

**Fix** → wait/assert observable state, response hoặc locator condition.

**Verification** → repeat test hàng trăm lần dưới parallel load.

## 7. Common mistakes

* `waitForTimeout` để chữa race.
* Shared mutable accounts/data.
* Test implementation details/CSS selectors dễ đổi.
* Mock toàn backend rồi gọi đó là E2E.
* Không giữ trace/screenshots cho failure investigation.

## 8. Alternatives

Unit/component tests nhanh hơn cho logic cục bộ. API integration tests bảo vệ backend contracts. E2E chỉ nên tập trung critical cross-system journeys.

## 9. Trade-offs

### Advantages

Bảo vệ integration/user journeys mà lower-level tests không thấy.

### Costs / Risks

Chậm, expensive và dễ flaky nếu state/timing không được kiểm soát.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu E2E kiểm tra journey, không phải mọi permutation.

### Middle

Viết stable locators, deterministic setup và artifacts.

### Senior

Thiết kế test data/environment isolation và debug flakes bằng traces.

### Technical Lead / Architect

Xây test strategy theo risk: unit + integration + một lớp E2E nhỏ nhưng đáng tin.

## 11. Key takeaway

* Flakiness thường là state/timing design problem.
* Fixed sleeps che race thay vì giải quyết nó.
* E2E suite nhỏ, isolated và đáng tin có giá trị hơn suite lớn thường xuyên rerun.

# 10. AI Tool Calling: model chọn intent nhưng deterministic application phải validate authorization, arguments và side effects

## 1. What is it?

Tool Calling cho phép LLM trả về structured request để application gọi function/API bên ngoài. Model không trực tiếp sở hữu database hoặc payment system; application là execution boundary.

```text
User → LLM
        ↓ proposes tool + args
Application policy/validation
        ↓
Authorized tool execution
        ↓
Result → LLM → User
```

## 2. Why does it exist?

LLM giỏi hiểu natural-language intent nhưng không phải deterministic transaction engine. Tool Calling kết hợp probabilistic reasoning với deterministic systems.

Giá trị nằm ở orchestration, nhưng security boundary phải ở application.

## 3. How does it work?

Application khai báo tool schema. Model có thể chọn tool và arguments. Runtime parse structured output, validate schema/business rules/identity rồi mới thực thi.

Model output là **proposal**, không phải authorization decision.

## 4. Practical implementation

C# boundary nên giống:

```csharp
public async Task<ToolResult> ExecuteAsync(
    ToolCall call,
    ClaimsPrincipal user,
    CancellationToken cancellationToken)
{
    var args = ParseAndValidate(call.Arguments);

    authorization.EnsureCanAccessTenant(user, args.TenantId);

    return call.Name switch
    {
        "get_order" => await orders.GetAsync(args.OrderId, cancellationToken),
        _ => throw new InvalidOperationException("Unsupported tool")
    };
}
```

Không tin `TenantId`, price, role hoặc approval decision chỉ vì model output đúng JSON schema.

## 5. Real production scenario

AI assistant cho support staff tra order. User prompt injection trong ticket text yêu cầu model gọi `refund_order`. Nếu tool executor chỉ kiểm tra tool name/JSON shape, untrusted content có thể dẫn tới privileged side effect.

Thiết kế đúng tách read tools khỏi write tools, kiểm tra staff permissions và yêu cầu deterministic approval/confirmation policy cho refund.

## 6. Failure scenario & troubleshooting

**Symptom** → model gọi tool với order ID thuộc tenant khác.

**Evidence** → argument hợp schema nhưng không hợp authorization scope.

**Hypothesis** → application coi model-generated arguments là trusted.

**Diagnosis** → audit tool calls với user identity, arguments và policy decision.

**Fix** → server-side authorization dựa trên authenticated principal; derive tenant context server-side khi có thể.

**Verification** → adversarial tests prompt injection/cross-tenant IDs và xác nhận executor từ chối.

## 7. Common mistakes

* JSON schema validation = business validation.
* Cho model quyết định role/permission.
* Expose destructive tools quá rộng.
* Tool retries tạo duplicate side effects mà không có idempotency key.
* Log sensitive prompts/tool results không kiểm soát.

## 8. Alternatives

Deterministic UI/workflow tốt hơn nếu intent cố định và high-risk. RAG chỉ cung cấp knowledge, không cần side-effect tools. Human approval phù hợp high-impact actions.

## 9. Trade-offs

### Advantages

Natural-language orchestration linh hoạt và kết nối được hệ thống hiện hữu.

### Costs / Risks

Prompt injection, probabilistic tool selection, latency/cost và audit complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu model đề xuất call; application thực thi.

### Middle

Implement schemas, validation, timeout và error handling.

### Senior

Thiết kế authorization, idempotency, prompt-injection defenses và observability.

### Technical Lead / Architect

Quyết định tool nào được expose, side effects nào cần deterministic/human gate và trust boundaries giữa model/context/systems.

## 11. Key takeaway

* Structured Output không biến LLM thành trusted authority.
* Authorization và financial/security correctness phải deterministic.
* Tool surface càng nhỏ và capability-scoped, blast radius càng thấp.
