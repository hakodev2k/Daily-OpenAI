# 1. C# `SemaphoreSlim` cho bounded concurrency: giới hạn số operation chạy đồng thời mà không block ThreadPool

## 1. What is it?

`SemaphoreSlim` là synchronization primitive cho phép tối đa một số lượng operation nhất định đi vào critical/concurrent section cùng lúc.

Mental model:

```text
1000 requests cần gọi downstream API
        |
        v
SemaphoreSlim(20)
        |
        +--> tối đa 20 operation chạy
        +--> phần còn lại await permit
```

Khác với `lock`, mục tiêu không nhất thiết là mutual exclusion một-một. Với `SemaphoreSlim(20)`, hệ thống vẫn có concurrency nhưng được bounded.

## 2. Why does it exist?

`async` giúp không block thread trong khi chờ I/O, nhưng không tự bảo vệ downstream capacity.

Nếu code tạo 5.000 tasks đồng thời để gọi database, HTTP API hoặc xử lý file, ThreadPool có thể không phải bottleneck nhưng dependency vẫn bị overload:

- connection pool cạn;
- remote API trả `429`;
- socket usage tăng;
- memory tăng do hàng nghìn operation đang giữ state;
- p95/p99 xấu đi do queueing ngoài tầm kiểm soát.

Bounded concurrency tồn tại để biến “bao nhiêu work được phép cùng chạy” thành explicit resource policy.

## 3. How does it work?

`WaitAsync` giảm available permit. `Release` trả permit lại.

```text
permits = 3

A -> acquire -> 2
B -> acquire -> 1
C -> acquire -> 0
D -> await
E -> await

B completes -> release -> 1
D resumes   -> acquire -> 0
```

Điểm correctness quan trọng nhất: mỗi successful acquire phải có đúng một `Release`, kể cả khi exception hoặc cancellation xảy ra sau đó.

## 4. Practical implementation

```csharp
public sealed class ThumbnailProcessor
{
    private readonly SemaphoreSlim _gate = new(initialCount: 8);

    public async Task ProcessAsync(
        IReadOnlyCollection<ImageJob> jobs,
        CancellationToken ct)
    {
        var tasks = jobs.Select(job => ProcessOneAsync(job, ct));
        await Task.WhenAll(tasks);
    }

    private async Task ProcessOneAsync(ImageJob job, CancellationToken ct)
    {
        await _gate.WaitAsync(ct);

        try
        {
            await _renderer.RenderAsync(job, ct);
        }
        finally
        {
            _gate.Release();
        }
    }
}
```

Nếu mỗi request tạo riêng một `SemaphoreSlim`, nó không giới hạn concurrency toàn process. Lifetime của limiter phải phù hợp với resource mà nó đang bảo vệ.

## 5. Real production scenario

Một Worker đọc 2.000 message từ queue và với mỗi message gọi external document-rendering API. Sau khi tăng prefetch, throughput không tăng mà error rate tăng vì renderer chỉ chịu khoảng 30 concurrent requests.

Không có bound:

```text
queue burst -> 500 concurrent HTTP calls -> 429/timeout -> retry -> retry storm
```

Có bound 25–30:

```text
queue burst -> local wait -> stable downstream concurrency -> predictable throughput
```

## 6. Failure scenario & troubleshooting

**Symptom** → application dần dần treo, `WaitAsync` chờ vô hạn dù workload đã giảm.

**Evidence** → semaphore current count không phục hồi; một code path acquire nhưng exception trước `Release`.

**Hypothesis** → leaked permit.

**Diagnosis** → trace acquire/release count; review mọi early-return/exception path; kiểm tra `Release` có nằm trong `finally` không.

**Fix** → luôn `try/finally`; không release nếu acquire chưa thành công; propagate cancellation hợp lý.

**Verification** → fault-injection trong critical section và load test dài để current permit count ổn định.

## 7. Common mistakes

- Tạo semaphore per method call nên thực tế không giới hạn gì.
- Quên `finally`.
- Set concurrency theo cảm giác thay vì dependency capacity.
- Dùng `Task.WhenAll` với hàng trăm nghìn tasks rồi nghĩ semaphore đã giải quyết memory hoàn toàn.
- Dùng `SemaphoreSlim` như distributed lock giữa nhiều instances.

## 8. Alternatives

`Channel<T>` phù hợp hơn khi cần producer/consumer queue có bounded capacity.

`Parallel.ForEachAsync` có `MaxDegreeOfParallelism` phù hợp cho batch processing.

Rate limiter phù hợp khi limit theo request/time hoặc tenant.

Distributed coordination cần Redis/database/lease mechanism, không phải `SemaphoreSlim`.

## 9. Trade-offs

### Advantages

- Bảo vệ downstream resource.
- Giữ concurrency nhưng tránh overload.
- Dễ implement trong-process.

### Costs / Risks

- Thêm local queueing và latency.
- Chọn limit sai có thể underutilize hoặc overload.
- Không coordinate giữa nhiều app instances.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `async` không có nghĩa “unlimited concurrency là an toàn”.

### Middle

Biết dùng `WaitAsync` + `finally` và propagate `CancellationToken`.

### Senior

Đo capacity của dependency, queueing, p95/p99 và failure amplification khi retry.

### Technical Lead / Architect

Quyết định concurrency budget nằm ở client, queue consumer, gateway hay downstream service; đánh giá có cần distributed throttling hay local bound là đủ.

## 11. Key takeaway

- Bounded concurrency là capacity control, không chỉ synchronization.
- Permit phải luôn được trả trong `finally`.
- Limit phải dựa trên throughput/dependency evidence, không dựa trên số CPU core một cách máy móc.

# 2. ASP.NET Core ETag + conditional requests: giảm bandwidth và ngăn lost update bằng HTTP semantics thay vì custom version header tùy ý

## 1. What is it?

ETag là opaque validator đại diện cho một version của HTTP representation.

Server có thể trả:

```http
ETag: "order-42-v7"
```

Client dùng:

- `If-None-Match` cho conditional GET;
- `If-Match` cho conditional update/delete.

Hai use case khác nhau nhưng cùng dựa trên một ý tưởng: client nói “chỉ thực hiện request nếu resource version còn thỏa điều kiện”.

## 2. Why does it exist?

Không có validator:

- client download lại response dù data không đổi;
- hai user update cùng resource và request sau silently ghi đè request trước.

ETag đưa versioning vào HTTP contract thay vì tạo endpoint-specific convention như `X-Row-Version` mà proxy/client library không hiểu semantics.

## 3. How does it work?

Conditional GET:

```text
GET /products/42
<- 200 + ETag "v9"

GET /products/42
If-None-Match: "v9"

resource unchanged
<- 304 Not Modified
```

Conditional update:

```text
PUT /orders/42
If-Match: "v7"

DB is now v8
<- 412 Precondition Failed
```

`304` không chứa full response body. `412` cho biết precondition không còn đúng.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    AppDbContext db,
    HttpContext http,
    CancellationToken ct) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .Where(x => x.Id == id)
        .Select(x => new
        {
            x.Id,
            x.Status,
            x.Total,
            x.RowVersion
        })
        .SingleOrDefaultAsync(ct);

    if (order is null)
        return Results.NotFound();

    var etag = $"\"{Convert.ToBase64String(order.RowVersion)}\"";

    if (http.Request.Headers.IfNoneMatch == etag)
        return Results.StatusCode(StatusCodes.Status304NotModified);

    http.Response.Headers.ETag = etag;
    return Results.Ok(order);
});
```

Với update, map `If-Match` về concurrency token và trả `412` khi version stale.

## 5. Real production scenario

CRM frontend mở customer profile. Hai agent A/B cùng load version 14.

A update email → version 15.

B update phone từ form cũ. Nếu PUT cả object mà không concurrency check, email mới của A có thể bị overwritten bằng email cũ B đang giữ.

`If-Match: "v14"` khiến request B fail rõ ràng thay vì silently mất dữ liệu.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận `412` liên tục dù user vừa reload.

**Evidence** → ETag thay đổi mỗi request dù resource business data không đổi.

**Hypothesis** → validator được tạo từ unstable data như timestamp “now”, serialization order hoặc field thay đổi không liên quan.

**Diagnosis** → compare ETag inputs giữa requests; xác định representation/version boundary.

**Fix** → dùng stable concurrency/version token; không hash dữ liệu volatile không cần thiết.

**Verification** → cùng resource unchanged phải giữ validator; update thực sự phải đổi validator.

## 7. Common mistakes

- Dùng weak ETag cho write concurrency mà không hiểu semantics.
- Trả ETag nhưng client không gửi conditional header.
- Hash toàn response rất đắt khi đã có rowversion/version field.
- Dùng `304` nhưng vẫn chạy toàn bộ expensive query/render path nên chỉ tiết kiệm bandwidth.
- Trả `409` cho mọi concurrency case mà bỏ qua `412` khi failure đúng là precondition HTTP.

## 8. Alternatives

Custom version field trong JSON dễ hiểu và đôi khi phù hợp hơn cho internal APIs.

Last-Modified / `If-Modified-Since` đơn giản hơn nhưng timestamp resolution và semantics có thể yếu hơn.

Database optimistic concurrency vẫn cần ở persistence layer; ETag là cách expose version contract qua HTTP.

## 9. Trade-offs

### Advantages

- Chuẩn HTTP, client/proxy hiểu được.
- Giảm transfer khi representation không đổi.
- Hỗ trợ optimistic concurrency rõ ràng.

### Costs / Risks

- Client complexity tăng.
- Validator design sai làm cache/concurrency behavior khó đoán.
- Không loại bỏ database race nếu server implementation không enforce token atomically.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu ETag là version của representation, không phải arbitrary cache string.

### Middle

Implement `If-None-Match`/`If-Match` và status `304`/`412` đúng semantics.

### Senior

Kết nối HTTP precondition với database optimistic concurrency và caching layer.

### Technical Lead / Architect

Quyết định public API có dùng HTTP-native concurrency hay explicit domain version, và đảm bảo contract nhất quán giữa gateway, CDN, client và persistence.

## 11. Key takeaway

- ETag có thể phục vụ cả caching validation và concurrency preconditions.
- `If-Match` phải được enforce atomically với write.
- Validator phải stable khi resource chưa đổi và đổi khi version thật sự đổi.

# 3. EF Core `ExecuteUpdate` / `ExecuteDelete`: bulk mutation không qua Change Tracker và những consistency trap cần hiểu

## 1. What is it?

`ExecuteUpdateAsync` và `ExecuteDeleteAsync` cho phép EF Core phát trực tiếp một `UPDATE` hoặc `DELETE` SQL từ LINQ predicate mà không materialize entities vào memory và không đi qua normal Change Tracker mutation flow.

Ví dụ:

```csharp
await db.Sessions
    .Where(x => x.ExpiresAt < now)
    .ExecuteDeleteAsync(ct);
```

## 2. Why does it exist?

Cách naive để expire 100.000 records:

```text
SELECT 100k rows
-> materialize entities
-> track entities
-> mark modified/deleted
-> SaveChanges
```

Đây là rất nhiều network payload, memory và Change Tracker work chỉ để tạo một set-based SQL operation mà database đã làm rất tốt.

## 3. How does it work?

`ExecuteUpdate` dịch expression thành một SQL statement trực tiếp:

```csharp
await db.Jobs
    .Where(x => x.Status == JobStatus.Pending && x.CreatedAt < cutoff)
    .ExecuteUpdateAsync(
        setters => setters
            .SetProperty(x => x.Status, JobStatus.Expired)
            .SetProperty(x => x.UpdatedAt, now),
        ct);
```

Conceptual SQL:

```sql
UPDATE Jobs
SET Status = @Expired,
    UpdatedAt = @Now
WHERE Status = @Pending
  AND CreatedAt < @Cutoff;
```

Không có entity instance nào được synchronize tự động trong Change Tracker.

## 4. Practical implementation

Nếu context đã track entity trước bulk update:

```csharp
var job = await db.Jobs.SingleAsync(x => x.Id == id, ct);

await db.Jobs
    .Where(x => x.Id == id)
    .ExecuteUpdateAsync(
        s => s.SetProperty(x => x.Status, JobStatus.Expired),
        ct);

// job.Status trong memory vẫn có thể là giá trị cũ.
```

Sau đó `SaveChanges` trên tracked entity stale có thể ghi đè bulk update tùy field/state.

Safe approach thường là tránh mixing hoặc reload/clear tracking state có chủ đích.

## 5. Real production scenario

Scheduler hàng giờ expire 2 triệu temporary tokens. Implementation cũ load từng entity rồi `RemoveRange`, làm memory spike và transaction kéo dài.

`ExecuteDeleteAsync` biến workload thành một set-based command, giảm round trips và allocation đáng kể.

Nhưng nếu audit/domain events dựa trên entity lifecycle hook/interceptor, direct delete có thể bypass expectation đó.

## 6. Failure scenario & troubleshooting

**Symptom** → database đã update đúng nhưng API tiếp tục trả state cũ trong cùng request, hoặc `SaveChanges` sau đó “undo” một phần bulk mutation.

**Evidence** → tracked entity values khác database values; direct SQL xảy ra trước normal SaveChanges.

**Hypothesis** → Change Tracker stale state.

**Diagnosis** → inspect `ChangeTracker.Entries()`, generated SQL và transaction boundary.

**Fix** → không mix bulk mutation với tracked aggregate trong cùng unit-of-work; reload entity hoặc `ChangeTracker.Clear()` khi semantics cho phép.

**Verification** → integration test cùng transaction/context với before/after values.

## 7. Common mistakes

- Nghĩ `ExecuteUpdate` trigger domain method/event.
- Bulk update rồi tiếp tục dùng tracked entities như thể synchronized.
- Bỏ qua concurrency token/business invariant.
- Update hàng triệu rows một transaction mà không xem lock/log impact.
- Dùng bulk mutation để né domain rule chỉ vì nhanh hơn.

## 8. Alternatives

Normal tracked update phù hợp khi cần aggregate invariant, domain behavior hoặc per-entity logic.

Raw SQL/stored procedure phù hợp khi SQL rất đặc thù.

Batch processing nhiều transaction phù hợp khi một giant set-based mutation gây lock/log pressure quá lớn.

## 9. Trade-offs

### Advantages

- Ít round trips và allocation.
- Tận dụng set-based database execution.
- Rất tốt cho maintenance/bulk state transition đơn giản.

### Costs / Risks

- Bypass Change Tracker semantics.
- Có thể bypass application/domain hooks.
- Lock/log impact vẫn có thể lớn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu bulk direct mutation khác với load entity rồi `SaveChanges`.

### Middle

Biết khi nào tracker stale và viết integration test cho bulk operation.

### Senior

Đánh giá lock, transaction log, concurrency và domain-event implications.

### Technical Lead / Architect

Quyết định boundary nào cho phép set-based infrastructure operation và boundary nào bắt buộc đi qua aggregate/domain behavior.

## 11. Key takeaway

- `ExecuteUpdate/Delete` tối ưu vì bỏ materialization và Change Tracker.
- Performance gain đi cùng semantic difference.
- Không mix direct bulk mutation và tracked state mà không có kế hoạch synchronization rõ ràng.

# 4. PostgreSQL MVCC + `VACUUM`: long-running transaction có thể tạo table bloat dù query không hề “chậm” lúc bắt đầu

## 1. What is it?

PostgreSQL dùng MVCC (Multi-Version Concurrency Control): update thường tạo row version mới thay vì overwrite trực tiếp version cũ theo cách làm reader phải block writer.

Old row versions (dead tuples) cần được reclaim dần bởi `VACUUM` khi không còn transaction nào có thể nhìn thấy chúng.

Mental model:

```text
UPDATE row
 -> old tuple remains
 -> new tuple created
 -> readers see version phù hợp snapshot
 -> VACUUM later reclaims old tuple
```

## 2. Why does it exist?

MVCC giảm reader/writer blocking và cho transaction có snapshot semantics mạnh.

Nhưng “không block” không có nghĩa old versions miễn phí. Nếu một transaction rất cũ vẫn mở, PostgreSQL phải giữ nhiều tuple cũ vì transaction đó về lý thuyết vẫn có thể cần thấy chúng.

## 3. How does it work?

Transaction giữ snapshot với visibility horizon.

Một session chạy:

```sql
BEGIN;
SELECT ...;
-- rồi để transaction mở 45 phút
```

Trong lúc đó bảng bị update liên tục. Autovacuum không thể reclaim tuple vẫn potentially visible với snapshot cũ.

Kết quả:

```text
long transaction
 -> dead tuples accumulate
 -> table/index bloat
 -> more pages read
 -> cache efficiency giảm
 -> latency tăng dần
```

## 4. Practical implementation

Tìm long-running transaction:

```sql
SELECT
    pid,
    usename,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Xem dead tuples:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Application nên giữ transaction boundary ngắn và không mở transaction trong lúc chờ user/network không liên quan.

## 5. Real production scenario

Admin reporting endpoint mở transaction `Repeatable Read`, stream kết quả rất lâu về client chậm. Trong cùng giờ, order table nhận hàng triệu updates.

Report vẫn chạy “đúng”, nhưng vacuum bị giữ lại, table bloat tăng và transactional API bắt đầu tăng I/O.

Incident xuất hiện ở workload khác với nơi gây ra root cause.

## 6. Failure scenario & troubleshooting

**Symptom** → table size tăng nhanh, query reads tăng dù row count không tăng tương ứng.

**Evidence** → `n_dead_tup` cao, transaction age dài, autovacuum chạy nhưng không reclaim hiệu quả.

**Hypothesis** → long-running transaction giữ visibility horizon.

**Diagnosis** → correlate old transactions, vacuum progress, table churn và index/table size.

**Fix** → đóng transaction sớm, batch report, dùng replica phù hợp, tune autovacuum sau khi sửa root cause.

**Verification** → transaction age giảm; dead tuple count và bloat trend ổn định theo thời gian.

## 7. Common mistakes

- Chỉ tăng autovacuum frequency trong khi transaction cũ vẫn giữ tuples.
- Giữ transaction xuyên external HTTP call.
- Nghĩ read-only transaction không thể gây operational impact.
- Dùng `VACUUM FULL` như routine fix mà không hiểu lock/downtime implications.
- Chỉ monitor row count, không monitor dead tuples/transaction age.

## 8. Alternatives

Read replica có thể tách analytical/reporting workload nhưng replica cũng có MVCC/replay trade-offs.

Snapshot export/data warehouse phù hợp cho report dài.

SQL Server dùng implementation concurrency/versioning khác; đừng chuyển tuning rule giữa engines một cách máy móc.

## 9. Trade-offs

### Advantages

- Reader/writer concurrency tốt.
- Strong snapshot semantics.
- Update không bắt buộc reader phải block.

### Costs / Risks

- Dead tuples cần maintenance.
- Long transactions gây bloat gián tiếp.
- Vacuum/tuning trở thành operational concern.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu update có thể tạo row version cũ thay vì “ghi đè tại chỗ”.

### Middle

Biết kiểm tra `pg_stat_activity`, dead tuples và giữ transaction ngắn.

### Senior

Phân tích snapshot horizon, autovacuum, bloat và workload churn.

### Technical Lead / Architect

Quyết định transactional/reporting workload có nên chung primary database không và đặt guardrail cho transaction duration.

## 11. Key takeaway

- MVCC giảm blocking nhưng tạo lifecycle cho old row versions.
- Long-running read transaction cũng có thể gây production impact.
- Tuning vacuum không thay thế việc sửa transaction boundary sai.

# 5. Retry + Timeout + Circuit Breaker: resilience policy chỉ đúng khi hiểu thứ tự composition và loại failure nào được phép retry

## 1. What is it?

Ba resilience mechanism giải quyết ba vấn đề khác nhau:

- **Timeout:** giới hạn thời gian chờ một attempt/operation.
- **Retry:** thử lại failure có khả năng transient.
- **Circuit Breaker:** ngừng gửi request tạm thời khi dependency đang fail nhiều, tránh tiếp tục gây load vô ích.

Chúng không phải ba checkbox độc lập. Thứ tự và scope quyết định behavior thật sự.

## 2. Why does it exist?

Remote dependency sẽ có partial failure: packet loss, overload, deployment, throttling.

Không timeout → request treo quá lâu.

Không retry → transient failure nhỏ trở thành user-visible error.

Retry vô hạn → retry storm.

Không circuit breaker → unhealthy dependency tiếp tục nhận traffic dù gần như chắc chắn fail.

## 3. How does it work?

Một composition concept:

```text
Overall timeout 5s
  -> Retry max 2
       -> Per-attempt timeout 1.5s
       -> HTTP call

Circuit breaker quan sát outcomes
```

Nếu đặt retry ngoài timeout hoặc timeout ngoài retry khác nhau, tổng thời gian có thể khác hoàn toàn.

Ví dụ 3 attempts × 2s timeout có thể khiến request mất gần 6s cộng backoff.

## 4. Practical implementation

Với modern .NET resilience stack, intent phải explicit. Conceptual example:

```csharp
builder.Services
    .AddHttpClient<InventoryClient>()
    .AddStandardResilienceHandler(options =>
    {
        options.AttemptTimeout.Timeout = TimeSpan.FromSeconds(1);
        options.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(4);
        options.Retry.MaxRetryAttempts = 2;
        options.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(30);
    });
```

Quan trọng hơn config là retry eligibility. `GET` thường retry-safe hơn `POST payment` nếu downstream không hỗ trợ idempotency key.

## 5. Real production scenario

Checkout gọi payment provider. Provider timeout sau khi thực tế đã charge thành công nhưng response bị mất.

Naive retry:

```text
POST charge
 -> timeout
 -> retry POST charge
 -> customer charged twice
```

Safe design cần idempotency key hoặc query operation status trước retry.

## 6. Failure scenario & troubleshooting

**Symptom** → dependency incident làm outbound RPS tăng gấp 3 thay vì giảm.

**Evidence** → traces có cùng logical request gọi downstream nhiều lần; latency tổng tăng mạnh; `429/503` nhiều.

**Hypothesis** → retry amplification và policy ordering sai.

**Diagnosis** → inspect attempt count, backoff, timeout scope, status codes được retry và breaker state.

**Fix** → giảm retries, thêm jitter/backoff, honor `Retry-After`, circuit-break đúng threshold, không retry non-idempotent operation tùy tiện.

**Verification** → fault injection dependency 500/timeout/429 và đo outbound attempt rate.

## 7. Common mistakes

- Retry mọi `5xx`/exception giống nhau.
- Retry `429` mà bỏ `Retry-After`.
- Retry ở nhiều layers cùng lúc: SDK + service + gateway.
- Circuit breaker threshold quá nhạy nên mở circuit vì vài lỗi ngẫu nhiên.
- Timeout dài hơn upstream request budget.

## 8. Alternatives

Queue-based asynchronous workflow phù hợp khi operation không cần synchronous response và cần durability.

Fallback/cache chỉ hợp lý nếu stale data chấp nhận được.

Bulkhead/bounded concurrency giúp cô lập capacity nhưng không thay timeout/retry.

## 9. Trade-offs

### Advantages

- Hấp thụ transient faults.
- Giới hạn latency và failure propagation.
- Circuit breaker bảo vệ dependency và caller.

### Costs / Risks

- Retry tăng load và latency.
- Circuit breaker tạo trạng thái mới cần observability.
- Policy sai có thể gây incident lớn hơn failure gốc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry không đồng nghĩa “thử lại cho đến khi thành công”.

### Middle

Configure timeout/retry và biết operation nào idempotent.

### Senior

Phân tích total latency budget, amplification, jitter, breaker metrics và duplicate side effects.

### Technical Lead / Architect

Đặt resilience ownership theo boundary để tránh nested retries; quyết định operation nào cần synchronous resilience và operation nào nên chuyển sang async workflow.

## 11. Key takeaway

- Timeout, Retry và Circuit Breaker giải quyết các failure mode khác nhau.
- Composition/order quyết định total behavior.
- Retry chỉ an toàn khi failure có khả năng transient và side effect có idempotency semantics phù hợp.

# 6. Azure Front Door origin health + failover: high availability ở edge không tự đảm bảo application state và dependency state an toàn

## 1. What is it?

Azure Front Door định tuyến HTTP traffic ở edge tới một hoặc nhiều origins. Health probe được dùng để đánh giá origin có đủ healthy để nhận traffic không; routing policy có thể fail over sang origin/region khác.

Mental model:

```text
Client
  -> Azure Front Door
      -> Region A origin (healthy)
      -> Region B origin (standby/secondary)
```

## 2. Why does it exist?

Một region, App Service hoặc origin endpoint có thể fail. DNS-level failover thường chậm và coarse-grained hơn. Edge routing cho phép traffic chuyển origin nhanh hơn và có TLS/WAF/CDN integration.

Nhưng routing traffic chỉ giải quyết network/application endpoint availability. Nó không tự replicate database state, session, files hoặc queue state.

## 3. How does it work?

Front Door gửi probe tới origin path. Nếu probe fail theo configured threshold, origin bị loại khỏi healthy pool.

Nếu `/health` chỉ trả `200` miễn process còn chạy, Front Door có thể tiếp tục gửi traffic vào app không access được critical dependency.

Ngược lại, nếu probe phụ thuộc mọi optional dependency, một dependency phụ chập chờn có thể làm cả origin bị eject không cần thiết.

## 4. Practical implementation

ASP.NET Core có thể tách liveness/readiness:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, tags: new[] { "ready" });

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

Front Door nên probe endpoint phản ánh “origin có thể phục vụ critical traffic không”, nhưng endpoint cũng phải nhẹ và ổn định.

## 5. Real production scenario

System active-active hai regions nhưng session state nằm trong region-local memory. Front Door fail over user từ A sang B.

HTTP endpoint B healthy, nhưng user mất cart/session.

HA network path hoạt động đúng; application architecture không support cross-region state semantics.

## 6. Failure scenario & troubleshooting

**Symptom** → traffic fail over thành công nhưng error rate vẫn cao hoặc user state mất.

**Evidence** → Front Door metrics cho thấy origin B healthy; app traces B lỗi database/session dependency.

**Hypothesis** → health definition không đại diện end-to-end readiness hoặc state không replicated.

**Diagnosis** → trace request qua edge/origin, inspect probe status, dependency topology và region ownership.

**Fix** → thiết kế data/session replication hoặc stateless app; cải thiện readiness; xác định dependency nào phải region-resilient.

**Verification** → game day: disable origin A và test full user journey, không chỉ `/health`.

## 7. Common mistakes

- Health probe luôn `200 OK` nếu process sống.
- Dùng liveness probe nặng gọi hàng loạt dependencies.
- Nghĩ Front Door replicate database/session.
- Active-active compute nhưng single-region database.
- Không test failback behavior sau khi region phục hồi.

## 8. Alternatives

Application Gateway phù hợp regional L7 routing.

Traffic Manager là DNS-based routing.

Nếu business không cần multi-region HA, single-region App Service + zone redundancy/backups có thể đơn giản và rẻ hơn.

## 9. Trade-offs

### Advantages

- Global entry point và fast origin failover.
- Edge security/routing/CDN integration.
- Giảm dependence vào client DNS refresh behavior.

### Costs / Risks

- Multi-region architecture tăng data consistency và operational complexity.
- Probe design sai gây false failover hoặc false healthy.
- Cost tăng ở network, duplicated infrastructure và observability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Front Door route traffic; nó không tự đồng bộ application state.

### Middle

Biết health endpoints và origin configuration cơ bản.

### Senior

Debug probe, routing, state/dependency failure và failover behavior.

### Technical Lead / Architect

Quyết định RTO/RPO có thật sự yêu cầu multi-region; nếu có phải thiết kế compute, data, messaging và session như một tổng thể.

## 11. Key takeaway

- Edge HA không bằng end-to-end HA.
- Health probe phải phản ánh khả năng phục vụ traffic critical, không chỉ process existence.
- Multi-region chỉ đáng làm khi business requirement biện minh được complexity/cost.

# 7. JWT signing-key rotation + JWKS caching: token validation có thể fail theo chu kỳ dù code authentication không đổi

## 1. What is it?

Identity Provider ký JWT bằng private key. API validate signature bằng public key tương ứng.

JWKS (JSON Web Key Set) publish tập public keys, thường tại metadata endpoint của OpenID Connect provider.

Token header có `kid` để validator chọn đúng key.

## 2. Why does it exist?

Signing key không thể tồn tại mãi. Provider cần rotate key vì:

- security policy;
- certificate expiration;
- incident response;
- routine key management.

Nếu API hardcode một public key/certificate, lần rotation kế tiếp có thể làm authentication fail toàn hệ thống.

## 3. How does it work?

```text
Token header: kid = K2

API token validator
 -> local key cache có K2?
      yes -> validate
      no  -> refresh OIDC/JWKS metadata
            -> get K2
            -> validate
```

Provider thường overlap old/new keys để tokens đã phát trước rotation vẫn validate đến khi expiry.

Metadata/JWKS cache và refresh behavior vì vậy là một phần của auth reliability.

## 4. Practical implementation

ASP.NET Core nên dùng authority/metadata thay vì hardcode key:

```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = "https://login.example.com/tenant/v2.0";
        options.Audience = "api://orders";

        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true
        };
    });
```

TLS, issuer và audience validation vẫn bắt buộc; auto metadata không có nghĩa “trust mọi key từ internet”.

## 5. Real production scenario

API chạy ổn nhiều tháng. Identity Provider rotate signing certificate lúc 02:00. Một số app instances refresh metadata và chạy bình thường; một số instances giữ stale key cache/network không tới metadata endpoint nên bắt đầu trả `401`.

Load balancer khiến user thấy request lúc thành công lúc thất bại.

## 6. Failure scenario & troubleshooting

**Symptom** → `401` tăng đột ngột; log có lỗi “signature key not found” / unknown `kid`.

**Evidence** → token `kid` mới không có trong cached JWKS; metadata endpoint có key mới.

**Hypothesis** → key rotation + stale metadata/cache/network issue.

**Diagnosis** → decode JWT header an toàn, compare `kid`, inspect OIDC discovery/JWKS, kiểm tra outbound connectivity/DNS/time sync.

**Fix** → dùng standards-based metadata refresh, đảm bảo instances truy cập IdP, không pin stale certificate tùy tiện.

**Verification** → test token ký bằng current/new key và rollover scenario ở staging.

## 7. Common mistakes

- Hardcode signing certificate trong app config.
- Disable signature validation để “fix 401”.
- Chỉ validate signature nhưng bỏ issuer/audience/lifetime.
- Log full access token vào telemetry.
- Không đồng bộ system clock, gây false expiry/not-before errors.

## 8. Alternatives

Opaque token + introspection phù hợp một số architectures nhưng tăng runtime dependency vào authorization server.

mTLS hoặc Managed Identity phù hợp cho service-to-service trong Azure ở những use case khác; không phải drop-in replacement cho end-user OIDC JWT.

## 9. Trade-offs

### Advantages

- JWT validation local, latency thấp.
- JWKS cho phép rotation không cần redeploy API.
- Standards-based interoperability.

### Costs / Risks

- Metadata cache/refresh tạo hidden dependency.
- Token revocation tức thời khó hơn opaque token/introspection.
- Configuration sai dễ thành security incident.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu JWT signature validate bằng public key và `kid` chọn key.

### Middle

Configure Authority/Audience/Issuer và đọc auth logs.

### Senior

Debug rotation, metadata refresh, clock skew và partial-instance failures.

### Technical Lead / Architect

Thiết kế identity trust boundary, token lifetime, rotation/runbook và telemetry mà không làm lộ token/secrets.

## 11. Key takeaway

- Signing-key rotation là expected lifecycle event.
- Đừng hardcode key nếu provider support OIDC/JWKS discovery.
- `401` theo chu kỳ có thể là metadata/key-refresh problem, không chỉ “token sai”.

# 8. SLO + error budget + burn-rate alerting: biến observability từ dashboard trang trí thành quyết định vận hành có ngưỡng rõ ràng

## 1. What is it?

SLI là chỉ số đo behavior user quan tâm, ví dụ successful request ratio hoặc latency.

SLO là target cho SLI trong một window:

```text
99.9% requests thành công trong 30 ngày
```

Error budget là phần failure được phép:

```text
100% - 99.9% = 0.1%
```

Burn rate mô tả budget đang bị tiêu nhanh gấp bao nhiêu so với tốc độ “được phép”.

## 2. Why does it exist?

Alert kiểu:

```text
CPU > 80%
```

không trực tiếp nói user có bị ảnh hưởng không. CPU cao có thể hoàn toàn bình thường; CPU thấp vẫn có thể 100% error vì dependency auth fail.

SLO buộc team nối telemetry với reliability outcome thay vì monitor infrastructure metric rời rạc.

## 3. How does it work?

Giả sử SLO availability 99.9%/30 ngày.

Error budget ≈ 43 phút downtime tương đương nếu tính đơn giản theo time, hoặc 0.1% bad events nếu event-based.

Burn rate 10x nghĩa là nếu giữ tốc độ hiện tại, budget sẽ bị tiêu nhanh gấp 10 lần mức bền vững.

Multi-window alerting giúp bắt cả incident nhanh/lớn và degradation chậm.

## 4. Practical implementation

Một SLI event-based:

```text
Good events:
HTTP requests trả 2xx/3xx, trừ endpoints không nằm trong user journey

Total events:
all eligible user requests

SLI = good / total
```

Prometheus-like expression concept:

```text
error_ratio = 5xx_requests / eligible_requests
```

Trong Application Insights/Azure Monitor, dashboard nên có:

- success ratio;
- p95/p99 latency;
- error-budget remaining;
- burn-rate alerts;
- dependency correlations.

## 5. Real production scenario

Checkout service CPU chỉ 45%, memory bình thường nhưng payment dependency fail 8% requests trong 20 phút.

Infra dashboards “xanh”. SLO burn rate lại báo incident nghiêm trọng ngay vì user-visible failure đang tiêu budget rất nhanh.

## 6. Failure scenario & troubleshooting

**Symptom** → pager kêu liên tục cho issue không ảnh hưởng user hoặc không kêu khi customer đang lỗi.

**Evidence** → alerts dựa trên raw CPU/log count, không map vào SLI.

**Hypothesis** → alerting không gắn với service objective.

**Diagnosis** → review alert history, false positive/negative, user impact và SLO coverage.

**Fix** → định nghĩa eligible traffic, good/bad event rõ; dùng burn-rate windows; giữ infra alerts cho resource exhaustion thực sự action-able.

**Verification** → replay historical incidents và xem rule mới có detect đúng severity/time không.

## 7. Common mistakes

- Chọn 99.99% vì “nghe chuyên nghiệp” mà không tính cost.
- SLO = SLA contract pháp lý.
- Dùng average latency làm SLI duy nhất.
- Alert trên mọi exception log.
- Tính success ratio bao gồm health checks/background noise không liên quan user.

## 8. Alternatives

Threshold alerts vẫn cần cho hard resource constraints như disk nearly full hoặc certificate sắp expire.

Business KPI monitoring bổ sung góc nhìn conversion/payment success nhưng không thay service reliability metrics.

## 9. Trade-offs

### Advantages

- Alert tập trung user impact.
- Có ngôn ngữ chung giữa reliability và delivery speed.
- Giảm noisy paging nếu thiết kế tốt.

### Costs / Risks

- SLI definition sai dẫn tới falsa confidence.
- Cần instrumentation/query discipline.
- High SLO target có thể làm architecture/cost tăng đáng kể.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SLO là reliability target, không phải dashboard chart tùy ý.

### Middle

Biết instrument success/latency và phân biệt logs/metrics/traces.

### Senior

Thiết kế SLI, burn-rate alert và investigate user-impact path.

### Technical Lead / Architect

Chọn SLO dựa trên business criticality, dependency reality và cost; dùng error budget để cân bằng reliability work với feature delivery.

## 11. Key takeaway

- SLO phải đo outcome user thực sự quan tâm.
- Error budget biến reliability thành quantity có thể quản lý.
- Alerting tốt ưu tiên burn rate/user impact thay vì mọi metric vượt threshold.

# 9. Git `rebase`, `merge` và `--force-with-lease`: giữ lịch sử sạch mà không vô tình ghi đè công việc của người khác

## 1. What is it?

`merge` tạo commit kết hợp histories mà không rewrite commit cũ.

`rebase` replay commits của branch lên một base mới, tạo commit IDs mới.

`git push --force-with-lease` cho phép push rewritten history nhưng chỉ khi remote vẫn ở commit mà local kỳ vọng, giảm nguy cơ overwrite thay đổi mới của người khác.

## 2. Why does it exist?

Feature branch thường tụt sau `main`.

Hai mục tiêu có thể mâu thuẫn:

- giữ history thật như đã diễn ra;
- giữ feature history tuyến tính/dễ review.

Rebase phục vụ mục tiêu thứ hai nhưng rewrite history. Vì vậy nó cần safety discipline khi branch đã được share.

## 3. How does it work?

Ban đầu:

```text
A---B---C main
     \
      D---E feature
```

Main tiến tới F:

```text
A---B---C---F main
     \
      D---E feature
```

Rebase:

```text
A---B---C---F main
             \
              D'---E' feature
```

`D'` và `E'` có SHA mới dù content có thể tương tự.

## 4. Practical implementation

```bash
git fetch origin
git checkout feature/my-work
git rebase origin/main
```

Resolve conflicts:

```bash
git add <resolved-files>
git rebase --continue
```

Sau successful rebase của branch đã push:

```bash
git push --force-with-lease origin feature/my-work
```

Tránh:

```bash
git push --force
```

trên shared branch trừ khi team workflow thật sự kiểm soát được hậu quả.

## 5. Real production scenario

Developer A rebase PR branch rồi force push. Trong lúc đó Developer B vừa push một hotfix commit vào cùng branch.

`--force` có thể xóa commit B khỏi branch remote.

`--force-with-lease` fail vì remote SHA đã khác expectation, buộc A fetch/reconcile trước.

## 6. Failure scenario & troubleshooting

**Symptom** → commit “biến mất” sau force push hoặc PR history thay đổi bất ngờ.

**Evidence** → reflog/local clone còn commit cũ; remote branch head bị rewritten.

**Hypothesis** → unsafe force push sau rebase.

**Diagnosis** → inspect reflog, PR events và remote refs.

**Fix** → recover commit từ reflog/other clone, cherry-pick/reapply, dùng `--force-with-lease` về sau.

**Verification** → branch chứa cả intended rewritten history và commits mới nhất từ collaborators.

## 7. Common mistakes

- Rebase public/shared `main`.
- Force push sau rebase mà không fetch.
- Resolve conflict bằng cách chọn “ours/theirs” máy móc.
- Merge main vào feature nhiều lần chỉ để “fix CI”, tạo noisy history không cần thiết.
- Squash mọi commit dù intermediate commits có giá trị review/debug.

## 8. Alternatives

Merge commit an toàn và phản ánh integration history rõ hơn.

Squash merge phù hợp khi muốn main có một commit per PR.

Rebase merge phù hợp khi team muốn linear history và PR commits đã được curate.

Không có một strategy luôn tốt nhất; consistency trong team quan trọng hơn sở thích cá nhân.

## 9. Trade-offs

### Advantages

Rebase tạo history tuyến tính, dễ đọc và dễ bisect trong nhiều trường hợp.

Merge không rewrite history, an toàn hơn cho shared work.

### Costs / Risks

Rebase thay SHA và có thể làm collaboration khó nếu branch shared.

Merge history có thể noisy nếu sync quá thường xuyên.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu rebase rewrite commits, merge thì không.

### Middle

Biết resolve conflicts và dùng `--force-with-lease`.

### Senior

Phục hồi bằng reflog, chọn integration strategy theo workflow và review needs.

### Technical Lead / Architect

Đặt branch policy rõ: khi nào rebase, khi nào squash, ai được force push và CI/protection nào bảo vệ shared branches.

## 11. Key takeaway

- Rebase là history rewrite, không chỉ “update branch”.
- `--force-with-lease` an toàn hơn `--force` vì kiểm tra remote expectation.
- Git strategy nên phục vụ collaboration/review/debugging, không phục vụ aesthetic history đơn thuần.

# 10. Semantic HTML + accessibility: component chạy đúng bằng chuột vẫn có thể hỏng hoàn toàn với keyboard và screen reader

## 1. What is it?

Semantic HTML dùng đúng element theo meaning/interaction: `button`, `a`, `label`, `nav`, `main`, headings, form controls… thay vì dùng `div` cho mọi thứ rồi tự gắn click handler.

Accessibility engineering đảm bảo UI có thể được dùng bằng keyboard, assistive technology và trong nhiều capability constraints khác nhau.

Mental model:

```text
visual appearance != interaction semantics
```

Một `div` trông giống button không tự có keyboard focus, Enter/Space behavior hoặc accessible role/name như `<button>`.

## 2. Why does it exist?

Browser và assistive technologies dựa vào semantic tree/accessibility tree để hiểu UI.

Nếu frontend chỉ tối ưu cho mouse + pixels, application có thể unusable với:

- keyboard-only user;
- screen reader;
- voice control;
- low vision/high zoom;
- automated accessibility tooling.

## 3. How does it work?

Native element cung cấp behavior built-in:

```html
<button type="button">Save</button>
```

Browser tự cung cấp:

- focusability;
- keyboard activation;
- button role;
- accessible name từ text;
- disabled semantics nếu dùng `disabled`.

Custom `div` phải tái implement những behavior này và rất dễ thiếu.

## 4. Practical implementation

Không nên:

```html
<div class="button" onclick="save()">Save</div>
```

Nên:

```html
<button type="button" @click="save">
  Save
</button>
```

Form label:

```html
<label for="email">Email</label>
<input id="email" name="email" type="email" autocomplete="email" />
```

Icon-only button cần accessible name:

```html
<button type="button" aria-label="Close dialog">
  <svg aria-hidden="true">...</svg>
</button>
```

ARIA bổ sung semantics khi native HTML chưa đủ; ARIA không nên thay native element một cách tùy tiện.

## 5. Real production scenario

E-commerce checkout có custom dropdown/cart controls xây hoàn toàn bằng `div`. Mouse users không thấy vấn đề. Keyboard users không thể focus/remove item; screen reader chỉ đọc “group” không biết đây là button.

Bug không nằm ở CSS mà ở interaction contract.

## 6. Failure scenario & troubleshooting

**Symptom** → Lighthouse/axe báo issue hoặc QA keyboard không thể hoàn thành workflow.

**Evidence** → tab order thiếu control; accessibility tree không có role/name/state; focus bị mất khi modal mở.

**Hypothesis** → visual component không có native semantics/focus management.

**Diagnosis** → dùng browser Accessibility tree, keyboard-only test, screen-reader spot checks và automated scanner.

**Fix** → ưu tiên native elements, label/control association, focus management, visible focus indicator; dùng ARIA đúng specification khi cần.

**Verification** → hoàn thành critical journey bằng keyboard, rerun automated checks và manual assistive-tech test cho high-risk components.

## 7. Common mistakes

- `div role="button"` nhưng quên keyboard handler/tabindex.
- `aria-label` ghi đè accessible name hữu ích bằng text sai.
- Xóa focus outline để “đẹp”.
- Heading levels chọn theo font size thay vì document hierarchy.
- Tin Lighthouse 100 điểm đồng nghĩa accessibility hoàn hảo.

## 8. Alternatives

Native HTML luôn nên là lựa chọn đầu tiên khi có element phù hợp.

Mature component libraries có thể giúp implement complex widgets như dialog/combobox nhưng vẫn cần verify integration và styling không phá semantics.

## 9. Trade-offs

### Advantages

- Ít custom code hơn.
- Keyboard/screen-reader behavior tốt hơn mặc định.
- SEO/testability thường cũng được cải thiện nhờ structure rõ.

### Costs / Risks

- Complex custom interaction vẫn cần focus/state engineering.
- Manual testing tốn công.
- Accessibility requirement có thể ảnh hưởng component API/design system.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTML element có semantics, không chỉ style mặc định.

### Middle

Build form/control bằng native elements, test keyboard và accessible names.

### Senior

Debug accessibility tree, focus lifecycle, ARIA state và SPA dynamic content.

### Technical Lead / Architect

Đưa accessibility vào design system, component contracts và CI/testing strategy thay vì kiểm tra muộn ở cuối dự án.

## 11. Key takeaway

- Dùng native semantic HTML trước khi tự tạo custom widget.
- Accessibility phải test interaction, không chỉ scan static markup.
- UI đúng bằng chuột chưa đủ để kết luận component đúng.
