# 1. C# `ValueTask`: khi giảm allocation có ích và khi reuse/await sai làm code trở nên nguy hiểm

## 1. What is it?

`ValueTask` và `ValueTask<T>` là awaitable value types có thể biểu diễn một operation hoàn tất synchronously mà không nhất thiết phải cấp phát một `Task` object mới.

Mental model:

```text
Operation
 ├─ hoàn tất ngay      -> ValueTask chứa kết quả trực tiếp
 └─ chưa hoàn tất      -> ValueTask bọc Task / IValueTaskSource
```

Điểm quan trọng: `ValueTask` là công cụ tối ưu allocation trong hot path, không phải phiên bản “nhanh hơn” mặc định của `Task`.

## 2. Why does it exist?

Một số APIs được gọi cực nhiều lần và phần lớn hoàn tất synchronously, ví dụ đọc từ buffer/cache nội bộ. Nếu mỗi lần đều tạo `Task<T>` mới, allocation nhỏ nhưng lặp hàng triệu lần có thể tạo GC pressure đáng kể.

`ValueTask<T>` cho phép trả trực tiếp kết quả đã có sẵn mà không luôn cần heap allocation.

## 3. How does it work?

Một `ValueTask<T>` có thể chứa:

* `T` trực tiếp khi đã hoàn tất
* một `Task<T>`
* một `IValueTaskSource<T>` cùng token nội bộ

Vì representation có thể dựa trên reusable source, consumer không được giả định `ValueTask` có semantics giống hệt `Task`.

Đặc biệt, một `ValueTask` thường chỉ nên được await **một lần** trừ khi API documentation đảm bảo khác.

## 4. Practical implementation

Ví dụ cache lookup:

```csharp
public ValueTask<User?> GetUserAsync(Guid id, CancellationToken ct)
{
    if (_cache.TryGetValue(id, out User? cached))
        return ValueTask.FromResult(cached);

    return new ValueTask<User?>(LoadFromDatabaseAsync(id, ct));
}

private async Task<User?> LoadFromDatabaseAsync(
    Guid id,
    CancellationToken ct)
{
    return await _db.Users
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);
}
```

Consumer:

```csharp
var user = await service.GetUserAsync(id, ct);
```

Không nên giữ `ValueTask` lại rồi await nhiều lần:

```csharp
var pending = service.GetUserAsync(id, ct);
var a = await pending;
var b = await pending; // semantics có thể không an toàn
```

## 5. Real production scenario

Một protocol parser hoặc high-throughput queue consumer thực hiện hàng triệu reads. 95% reads lấy được dữ liệu ngay từ in-memory buffer. `Task<T>` allocation cho từng read có thể trở thành measurable GC overhead.

Trong một CRUD API bình thường với database round-trip vài milliseconds, tiết kiệm một `Task` allocation gần như không phải bottleneck chính.

## 6. Failure scenario & troubleshooting

**Symptom** → sau tối ưu `Task<T>` thành `ValueTask<T>`, code thỉnh thoảng throw hoặc behavior không ổn định.

**Evidence** → cùng một `ValueTask` bị await hai lần hoặc bị convert/consume ở nhiều nơi.

**Hypothesis** → consumer đang dùng `ValueTask` như reusable `Task`.

**Diagnosis** → tìm chỗ lưu `ValueTask` vào field, enumerate nhiều lần hoặc await lặp.

**Fix** → await ngay; nếu cần reuse, chuyển thành `Task` bằng `AsTask()` một lần hoặc giữ API là `Task<T>`.

**Verification** → benchmark lại allocation và chạy concurrency tests.

## 7. Common mistakes

* Đổi toàn bộ `Task<T>` thành `ValueTask<T>` vì nghĩ luôn nhanh hơn.
* Await cùng một `ValueTask` nhiều lần.
* Lưu `ValueTask` dài hạn.
* Dùng `ValueTask` trong code không có profiling evidence.
* Tối ưu allocation nhỏ trong khi bottleneck thật là SQL hoặc network.

## 8. Alternatives

`Task<T>` vẫn là default tốt nhất cho phần lớn asynchronous APIs vì semantics đơn giản, dễ compose và dễ cache/reuse.

`ValueTask<T>` phù hợp hơn cho hot path có tỷ lệ synchronous completion cao và profiling cho thấy allocation đáng kể.

## 9. Trade-offs

### Advantages

* Có thể giảm heap allocation.
* Hữu ích trong runtime/library/hot-path code.

### Costs / Risks

* Consumer rules phức tạp hơn.
* Struct lớn hơn reference của `Task` trong một số call paths.
* Có thể làm code khó compose/debug hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task` là default; không xem `ValueTask` như “Task nhanh hơn”.

### Middle

Biết await `ValueTask` đúng cách và tránh reuse sai.

### Senior

Chỉ dùng khi profiling cho thấy allocation pressure và hiểu synchronous-completion ratio.

### Technical Lead / Architect

Đặt guideline: application code ưu tiên clarity; `ValueTask` chỉ vào hot path có benchmark/evidence.

## 11. Key takeaway

* `ValueTask` là optimization contract, không phải default async abstraction.
* Tối ưu đúng khi synchronous completion phổ biến và allocation thực sự đáng kể.
* API semantics đơn giản thường đáng giá hơn micro-optimization chưa đo đạc.

# 2. ASP.NET Core health checks: phân biệt liveness, readiness và dependency health để tránh tự khuếch đại outage

## 1. What is it?

Health check là endpoint hoặc signal cho platform biết application có đang chạy và có sẵn sàng nhận traffic hay không.

Hai khái niệm quan trọng:

```text
Liveness  = process có còn sống hợp lý không?
Readiness = instance có sẵn sàng phục vụ request mới không?
```

Không nên gộp mọi dependency check vào một endpoint duy nhất rồi để orchestrator xử lý tất cả như nhau.

## 2. Why does it exist?

Load balancer và orchestrator không thể suy luận health chỉ từ “process còn tồn tại”. Application có thể đang deadlock, chưa warm-up xong hoặc mất dependency quan trọng.

Ngược lại, restart process chỉ vì một dependency tạm thời lỗi có thể làm outage nặng hơn.

## 3. How does it work?

ASP.NET Core Health Checks cho phép đăng ký probes và map endpoints khác nhau.

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<StartupHealthCheck>("startup", tags: ["ready"])
    .AddSqlServer(connectionString, tags: ["dependency"]);
```

Map riêng:

```csharp
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

Liveness thường nên cực nhẹ và không phụ thuộc external services.

## 4. Practical implementation

Một readiness check có thể phản ánh warm-up nội bộ:

```csharp
public sealed class StartupHealthCheck : IHealthCheck
{
    private volatile bool _ready;

    public void MarkReady() => _ready = true;

    public Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context,
        CancellationToken cancellationToken = default)
    {
        return Task.FromResult(
            _ready
                ? HealthCheckResult.Healthy()
                : HealthCheckResult.Unhealthy("Application is warming up"));
    }
}
```

## 5. Real production scenario

Một API trên Kubernetes phụ thuộc SQL Server. SQL mất kết nối 20 giây.

Nếu liveness probe gọi SQL và fail, Kubernetes restart toàn bộ pods. Mỗi pod restart lại mở connection, warm caches và tạo thêm pressure đúng lúc database đang phục hồi.

Nếu liveness chỉ kiểm tra process health còn readiness tạm remove pod khỏi traffic khi cần, failure được cô lập tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → một dependency outage ngắn biến thành pod restart storm.

**Evidence** → liveness probe failures trùng với SQL timeout; restart count tăng nhanh.

**Hypothesis** → external dependency bị đưa vào liveness.

**Diagnosis** → inspect probe endpoint và registered checks.

**Fix** → tách liveness/readiness; dependency checks phải có semantics phù hợp.

**Verification** → simulate database outage; pods không restart vô ích và traffic routing hoạt động theo policy.

## 7. Common mistakes

* Liveness gọi database, Redis, third-party API.
* Health endpoint chạy query nặng.
* Readiness luôn trả 200 dù startup chưa hoàn tất.
* Dùng health check làm monitoring duy nhất.
* Không đặt timeout cho dependency health checks.

## 8. Alternatives

Application metrics và synthetic tests bổ sung health checks nhưng không thay thế probe semantics của platform.

## 9. Trade-offs

### Advantages

* Routing và restart decisions tốt hơn.
* Hỗ trợ graceful deployment/warm-up.

### Costs / Risks

* Probe thiết kế sai có thể gây self-inflicted outage.
* Dependency checks thêm traffic.
* “Healthy” không có nghĩa business flow chắc chắn đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu liveness khác readiness.

### Middle

Biết cấu hình ASP.NET Core health checks và probe endpoints.

### Senior

Thiết kế probes theo failure semantics thay vì check càng nhiều càng tốt.

### Technical Lead / Architect

Quyết định dependency nào ảnh hưởng traffic admission, dependency nào chỉ cần alert, và restart policy nào tránh cascading failure.

## 11. Key takeaway

* Liveness trả lời “có nên restart process?”, readiness trả lời “có nên nhận traffic?”.
* External dependency failure không mặc định là lý do restart application.
* Probe là control-plane signal, nên thiết kế rất thận trọng.

# 3. EF Core compiled queries: giảm query-compilation overhead mà không tối ưu nhầm bottleneck

## 1. What is it?

EF Core phải xử lý LINQ expression tree, xác định query shape, translate sang SQL và cache compilation metadata. Compiled query cho phép application chuẩn bị query delegate để giảm một phần overhead trên hot query path.

Mental model:

```text
LINQ shape
  ↓ compile/translate metadata
cached delegate
  ↓ repeated parameters
SQL execution
```

## 2. Why does it exist?

Với query rất đơn giản nhưng chạy hàng chục nghìn lần mỗi giây, client-side query processing overhead có thể trở nên measurable.

Nhưng với query mất 100 ms ở database, tiết kiệm microseconds phía EF gần như không giải quyết bottleneck chính.

## 3. How does it work?

EF Core bình thường đã cache query theo expression shape. Explicit compiled query giảm thêm lookup/processing overhead bằng delegate đã compile.

```csharp
private static readonly Func<AppDbContext, Guid, User?> GetUser =
    EF.CompileQuery((AppDbContext db, Guid id) =>
        db.Users
            .AsNoTracking()
            .SingleOrDefault(x => x.Id == id));
```

Async:

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<User>> UsersByTenant =
    EF.CompileAsyncQuery((AppDbContext db, Guid tenantId) =>
        db.Users
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId));
```

## 4. Practical implementation

Dùng compiled query cho stable hot path:

```csharp
public async Task<User?> GetAsync(Guid id, CancellationToken ct)
{
    await foreach (var user in UsersById(_db, id).WithCancellation(ct))
        return user;

    return null;
}
```

Trước khi áp dụng, đo bằng BenchmarkDotNet hoặc production profiling thay vì giả định.

## 5. Real production scenario

Authorization service kiểm tra tenant/user metadata cực thường xuyên. Query chỉ trả một row theo indexed key và database latency rất thấp. EF query overhead trở thành phần đáng kể trong total local execution.

Đây là trường hợp compiled query có thể có giá trị hơn một reporting query phức tạp mất 300 ms trong SQL Server.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries nhưng p95 gần như không đổi.

**Evidence** → tracing cho thấy 95% latency nằm ở SQL I/O.

**Hypothesis** → tối ưu sai layer.

**Diagnosis** → compare EF client-side duration, database duration, query plan và round trips.

**Fix** → xử lý database access pattern/index/query shape trước.

**Verification** → benchmark từng layer và production latency sau thay đổi.

## 7. Common mistakes

* Compile mọi query.
* Dùng compiled query cho dynamic query shape phức tạp.
* Bỏ qua SQL execution plan.
* Cho rằng compiled query thay thế indexing/projection.
* Tăng abstraction complexity mà không có benchmark.

## 8. Alternatives

* EF query cache mặc định thường đã đủ.
* Projection và `AsNoTracking` thường tạo impact lớn hơn.
* Raw SQL/Dapper chỉ nên cân nhắc khi có evidence rõ về translation/materialization overhead.

## 9. Trade-offs

### Advantages

* Giảm client-side overhead trên hot stable queries.
* Predictable query delegate.

### Costs / Risks

* Tăng code ceremony.
* Ít linh hoạt với dynamic queries.
* Dễ che khuất bottleneck thật.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ không trực tiếp là SQL; EF cần translate query shape.

### Middle

Biết query cache mặc định tồn tại và compiled query không phải requirement.

### Senior

Dùng profiling để xác định EF overhead có thực sự đáng kể.

### Technical Lead / Architect

Đặt performance optimization theo evidence hierarchy: round trips/query plan/materialization trước micro-optimization.

## 11. Key takeaway

* Compiled query là optimization cho hot stable query path.
* EF đã có query caching; explicit compilation chỉ tối ưu thêm một phần nhỏ.
* Nếu database là bottleneck, hãy sửa database path trước.

# 4. SQL Server covering index với `INCLUDE`: giảm key lookup nhưng không biến mọi query thành index-only access miễn phí

## 1. What is it?

Covering index là index chứa đủ columns để SQL Server phục vụ query mà không cần quay lại clustered index/heap để lấy thêm dữ liệu.

Ví dụ:

```sql
CREATE INDEX IX_Orders_CustomerId_OrderDate
ON dbo.Orders(CustomerId, OrderDate DESC)
INCLUDE (Status, TotalAmount);
```

Key columns phục vụ seek/sort; `INCLUDE` columns chủ yếu giúp cover output.

## 2. Why does it exist?

Query có thể seek nhanh bằng nonclustered index nhưng vẫn phải thực hiện hàng nghìn key lookups để lấy columns không nằm trong index.

Khi số rows lớn, random I/O từ lookup có thể chiếm phần lớn cost.

## 3. How does it work?

Flow không cover:

```text
Nonclustered Index Seek
      ↓ row locator
Key Lookup vào clustered index
      ↓
output columns
```

Flow được cover:

```text
Nonclustered Index Seek
      ↓
required columns đã nằm trong index leaf
      ↓
output
```

`INCLUDE` không quyết định seek predicate order như key columns.

## 4. Practical implementation

Query:

```sql
SELECT OrderDate, Status, TotalAmount
FROM dbo.Orders
WHERE CustomerId = @CustomerId
ORDER BY OrderDate DESC;
```

Index phù hợp:

```sql
CREATE INDEX IX_Orders_CustomerId_OrderDate
ON dbo.Orders(CustomerId, OrderDate DESC)
INCLUDE (Status, TotalAmount);
```

Sau đó kiểm tra actual execution plan, logical reads và write overhead.

## 5. Real production scenario

Customer order history API trả 50 records gần nhất. Query ban đầu có seek nhưng plan cho thấy hàng nghìn lookups khi filter rộng hơn trong reporting scenario.

Thêm `INCLUDE` giảm reads rõ rệt. Tuy nhiên index lớn hơn và mọi insert/update liên quan columns phải maintain thêm structure.

## 6. Failure scenario & troubleshooting

**Symptom** → read query nhanh hơn nhưng write throughput giảm và index storage tăng mạnh.

**Evidence** → nhiều overlapping indexes cùng include rất nhiều columns.

**Hypothesis** → over-indexing để “cover everything”.

**Diagnosis** → xem index usage stats, write frequency, page count và duplicate index definitions.

**Fix** → consolidate indexes, giữ columns thực sự cần, drop indexes ít giá trị.

**Verification** → benchmark cả read và write workload.

## 7. Common mistakes

* Đưa mọi SELECT column vào key thay vì `INCLUDE`.
* Cover query ít chạy nhưng làm write-heavy table nặng hơn.
* Không kiểm tra selectivity và key order.
* Chỉ nhìn estimated plan.
* Giả định index càng nhiều càng tốt.

## 8. Alternatives

* Projection nhỏ hơn có thể loại nhu cầu include.
* Clustered-index redesign chỉ nên làm khi access patterns rộng hơn chứng minh cần thiết.
* Columnstore phù hợp analytic workload hơn một số wide covering indexes.

## 9. Trade-offs

### Advantages

* Giảm key lookups và logical I/O.
* Có thể hỗ trợ ORDER BY cùng key order.

### Costs / Risks

* Tăng storage.
* Tăng write amplification.
* Tăng maintenance/rebuild cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index leaf có thể chứa thêm columns.

### Middle

Đọc execution plan để thấy seek + key lookup.

### Senior

Đánh đổi read gain với write/storage cost dựa trên workload.

### Technical Lead / Architect

Định nghĩa indexing strategy theo dominant access patterns thay vì tuning từng query cô lập.

## 11. Key takeaway

* `INCLUDE` hữu ích khi lookup cost thực sự đáng kể.
* Covering index vẫn có write và storage cost.
* Tuning index luôn cần execution plan + workload evidence.

# 5. Azure Cosmos DB partition key + hot partition: scalability phụ thuộc data distribution chứ không chỉ tăng RU/s

## 1. What is it?

Cosmos DB phân phối dữ liệu theo logical partition key. Partition key quyết định items nào cùng nằm trong một logical partition và ảnh hưởng routing, throughput distribution và transaction scope.

Mental model:

```text
Partition key values
 Tenant-A ──> physical partition 1
 Tenant-B ──> physical partition 2
 Tenant-C ──> physical partition 3
```

Hot partition xảy ra khi một phần nhỏ key space nhận phần lớn traffic hoặc data.

## 2. Why does it exist?

Distributed database cần cách xác định dữ liệu nằm ở đâu để route request và scale ngang.

Nếu mọi request đều phải broadcast toàn cluster, latency và cost tăng mạnh. Partition key cho phép targeted routing.

## 3. How does it work?

Cosmos DB hash partition-key values để phân phối logical partitions vào physical partitions. Throughput/capacity vật lý không thể được khai thác hiệu quả nếu traffic tập trung quá mạnh vào một key.

Ví dụ chọn `/country` cho global SaaS nhưng 80% users ở một quốc gia có thể tạo skew.

## 4. Practical implementation

Entity:

```csharp
public sealed record OrderDocument(
    string Id,
    string TenantId,
    string CustomerId,
    decimal Total);
```

Container partitioned by `/tenantId`:

```csharp
var response = await container.ReadItemAsync<OrderDocument>(
    id,
    new PartitionKey(tenantId),
    cancellationToken: ct);
```

Point read với id + partition key thường hiệu quả hơn cross-partition query.

## 5. Real production scenario

Multi-tenant SaaS chọn `TenantId` làm partition key. Phần lớn tenants nhỏ nhưng một enterprise tenant tạo 60% traffic toàn hệ thống.

Tổng RU/s còn dư nhưng riêng logical partition đó throttle. Tăng RU toàn container có thể tốn tiền mà không giải quyết architecture skew đủ tốt.

## 6. Failure scenario & troubleshooting

**Symptom** → HTTP 429 tập trung vào một tenant dù overall utilization không cao.

**Evidence** → metrics theo partition-key range cho thấy skew lớn.

**Hypothesis** → hot logical partition.

**Diagnosis** → phân tích request distribution, item growth và access pattern theo key.

**Fix** → redesign key cho workload mới, ví dụ synthetic key như `TenantId + Bucket`, nếu business access pattern cho phép.

**Verification** → traffic/RU được phân phối đều hơn và cross-partition query cost không tăng quá mức.

## 7. Common mistakes

* Chọn partition key chỉ vì field “unique-ish”.
* Dùng timestamp đơn thuần tạo hotspot theo thời gian.
* Bỏ qua tenant size skew.
* Query không cung cấp partition key dù application biết nó.
* Nghĩ autoscale tự sửa data-distribution problem.

## 8. Alternatives

SQL Server/PostgreSQL có thể đơn giản hơn khi workload chưa cần distributed partitioning. MongoDB sharding có bài toán shard-key tương tự về distribution và routing.

## 9. Trade-offs

### Advantages

* Horizontal scalability.
* Efficient targeted reads khi key phù hợp.

### Costs / Risks

* Partition-key decision khó thay đổi về sau.
* Cross-partition queries tăng cost.
* Hot keys có thể giới hạn scalability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định dữ liệu và request được route thế nào.

### Middle

Biết truyền partition key cho point reads và đọc 429 metrics.

### Senior

Đánh giá cardinality, skew, growth và access patterns trước khi chọn key.

### Technical Lead / Architect

Thiết kế partition strategy dựa trên business growth model, không chỉ schema hiện tại.

## 11. Key takeaway

* Distributed scale bắt đầu từ data distribution.
* RU/s không cứu được partition key lệch tải nghiêm trọng.
* Partition key là quyết định kiến trúc, không phải annotation kỹ thuật nhỏ.

# 6. Bulkhead Pattern + retry budget: cô lập dependency failure thay vì để retry chiếm toàn bộ capacity

## 1. What is it?

Bulkhead Pattern giới hạn số lượng concurrent operations cho một dependency hoặc workload để failure ở một vùng không chiếm hết shared resources.

Tên gọi đến từ vách ngăn tàu:

```text
Dependency A pool | Dependency B pool | Critical path pool
     fail                 ok                 ok
```

Retry budget giới hạn tổng lượng retry thay vì cho từng request retry độc lập vô hạn.

## 2. Why does it exist?

Nếu downstream API chậm từ 100 ms lên 10 giây, requests tích tụ. Nếu mỗi request retry ba lần, application có thể nhân tải lên dependency đang yếu và đồng thời giữ socket/thread/concurrency slots lâu hơn.

Một dependency phụ có thể kéo sập toàn bộ API.

## 3. How does it work?

Bulkhead dùng semaphore/concurrency limiter/isolated queue để giới hạn in-flight work.

Retry budget kiểm soát amplification:

```text
100 original requests
+ tối đa 10 retry requests
không phải
100 x 3 retries
```

Timeout, retry, circuit breaker và bulkhead phải phối hợp; từng policy riêng lẻ không đủ.

## 4. Practical implementation

Ví dụ đơn giản:

```csharp
private readonly SemaphoreSlim _slots = new(20, 20);

public async Task<Price?> GetPriceAsync(string sku, CancellationToken ct)
{
    if (!await _slots.WaitAsync(TimeSpan.FromMilliseconds(50), ct))
        throw new DependencyOverloadedException();

    try
    {
        return await _client.GetFromJsonAsync<Price>(
            $"/prices/{sku}", ct);
    }
    finally
    {
        _slots.Release();
    }
}
```

Production code có thể dùng resilience libraries, nhưng phải hiểu semantics thay vì chồng policies máy móc.

## 5. Real production scenario

Product page gọi Reviews API, Inventory API và Pricing API. Reviews bắt đầu timeout.

Nếu tất cả calls dùng chung unlimited concurrency, Reviews có thể chiếm socket/concurrency capacity và làm cả Pricing chậm theo.

Bulkhead cho Reviews giữ blast radius ở dependency không critical; page có thể degrade bằng cách ẩn reviews.

## 6. Failure scenario & troubleshooting

**Symptom** → một dependency outage khiến toàn bộ API p99 tăng và retry traffic tăng gấp nhiều lần.

**Evidence** → dependency call count vượt original request count đáng kể; concurrent requests tăng tới limit.

**Hypothesis** → retry amplification + không có isolation.

**Diagnosis** → trace retry count, queue depth, active requests và dependency timeout.

**Fix** → giảm retries, thêm jitter/budget, bulkhead và fallback phù hợp.

**Verification** → chaos test dependency failure; critical paths vẫn giữ SLO.

## 7. Common mistakes

* Retry mọi exception.
* Retry non-idempotent operation.
* Không có timeout nhưng vẫn có retry.
* Bulkhead limit quá nhỏ mà không đo throughput.
* Circuit breaker dùng như load balancer.

## 8. Alternatives

* Queue-based async isolation phù hợp background workloads.
* Separate service/process isolation mạnh hơn nhưng tăng operational complexity.
* Không cần bulkhead riêng nếu dependency traffic rất nhỏ và resource pool đã tách tự nhiên.

## 9. Trade-offs

### Advantages

* Giới hạn blast radius.
* Tạo predictable resource usage.
* Cho phép graceful degradation.

### Costs / Risks

* Có thể reject requests sớm.
* Cần capacity tuning.
* Nhiều policy làm behavior khó reasoning nếu thiếu observability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry tạo thêm traffic chứ không miễn phí.

### Middle

Biết giới hạn concurrency và timeout downstream calls.

### Senior

Thiết kế retry theo idempotency, budget và dependency failure mode.

### Technical Lead / Architect

Xác định critical/non-critical dependencies, degradation strategy và resource isolation boundaries.

## 11. Key takeaway

* Resilience không phải “retry nhiều hơn”.
* Bulkhead bảo vệ capacity của phần còn khỏe mạnh.
* Retry phải có budget, timeout và idempotency semantics.

# 7. Azure Key Vault + Managed Identity + secret rotation: bỏ credential khỏi application config nhưng vẫn phải thiết kế lifecycle

## 1. What is it?

Managed Identity cho Azure resource một workload identity mà không cần nhúng client secret vào application. Azure Key Vault lưu secrets/keys/certificates và kiểm soát access qua identity/authorization.

Flow:

```text
App Service
   ↓ Managed Identity token
Microsoft Entra ID
   ↓
Key Vault authorization
   ↓
Secret / key
```

## 2. Why does it exist?

Static credentials trong `appsettings.json`, pipeline variables hoặc container environment dễ bị leak, copy sai môi trường hoặc quên rotate.

Managed Identity loại bỏ một lớp bootstrap secret: application không cần secret để lấy secret khác.

## 3. How does it work?

Azure resource nhận identity. SDK dùng `DefaultAzureCredential` để lấy token trong environment phù hợp.

```csharp
var client = new SecretClient(
    new Uri(vaultUri),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync(
    "PaymentApiKey",
    cancellationToken: ct);
```

Authorization nên theo least privilege. Network access vẫn là một boundary riêng: identity đúng không có nghĩa network path chắc chắn mở.

## 4. Practical implementation

Local Development có thể dùng developer credential; Production dùng Managed Identity thông qua cùng `DefaultAzureCredential` chain.

Không nên log secret value:

```csharp
logger.LogInformation("Loaded payment credential version {Version}",
    secret.Properties.Version);
```

Nếu secret rotate, application phải quyết định refresh strategy: restart, periodic reload, cache TTL hoặc version-aware retrieval.

## 5. Real production scenario

Payment provider yêu cầu rotate API key mỗi 90 ngày. Team update secret version trong Key Vault.

Nếu application đọc secret một lần lúc startup và pods không restart, traffic vẫn dùng version cũ. “Secret đã rotate trong Vault” chưa đồng nghĩa workload đã dùng secret mới.

## 6. Failure scenario & troubleshooting

**Symptom** → secret tồn tại nhưng Production trả 403 khi đọc Vault.

**Evidence** → token acquisition thành công; Key Vault access denied.

**Hypothesis** → RBAC/access policy hoặc scope sai.

**Diagnosis** → kiểm tra identity object, role assignment, vault/network settings và version URI.

**Fix** → cấp đúng least-privilege role và network access.

**Verification** → test từ workload identity thật; không dùng developer admin account để xác nhận Production path.

## 7. Common mistakes

* Cho app quyền quá rộng toàn Vault.
* Nghĩ Managed Identity giải quyết luôn network isolation.
* Fetch secret mỗi request gây latency/throttling.
* Cache secret vô hạn nên rotation không hiệu lực.
* Log exception chứa sensitive payload.

## 8. Alternatives

* Environment variables: đơn giản nhưng secret lifecycle phụ thuộc deployment system.
* Kubernetes Secrets: phù hợp cluster-local secret distribution nhưng cần bảo vệ etcd/access.
* External secret managers khác có cùng core problem: identity, authorization, caching và rotation.

## 9. Trade-offs

### Advantages

* Giảm static credential exposure.
* Centralized audit/rotation.
* Stronger least-privilege model.

### Costs / Risks

* Runtime dependency vào identity/Vault/network.
* Rotation semantics phải thiết kế.
* Có latency và service limits nếu access pattern sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu secret không nên nằm trong source code.

### Middle

Biết dùng `DefaultAzureCredential` và Key Vault SDK.

### Senior

Thiết kế caching, rotation, fallback và observability mà không leak secrets.

### Technical Lead / Architect

Định nghĩa secret ownership, rotation SLA, network boundary và break-glass procedure.

## 11. Key takeaway

* Managed Identity loại bỏ bootstrap secret nhưng không loại bỏ secret lifecycle.
* Rotation chỉ hoàn tất khi workloads thực sự chuyển sang version mới.
* Identity, authorization và networking là ba boundary riêng.

# 8. Git bisect: tìm commit gây regression bằng binary search thay vì đọc lịch sử theo cảm tính

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên gây regression khi có thể phân loại một commit là `good` hoặc `bad`.

```text
Good ------------------------------ Bad
                 ↓ test midpoint
          loại bỏ nửa history
```

Với 1024 commits, lý thuyết chỉ cần khoảng 10 lần phân loại thay vì kiểm tra tuần tự hàng trăm commits.

## 2. Why does it exist?

Khi bug xuất hiện “đâu đó trong hai tuần gần đây”, đọc diff thủ công dễ bị bias và tốn thời gian.

Nếu có reproducible test, commit history trở thành search space có thể thu hẹp có hệ thống.

## 3. How does it work?

Bắt đầu:

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0
```

Git checkout midpoint. Sau khi test:

```bash
git bisect good
# hoặc
git bisect bad
```

Lặp lại tới khi Git xác định first bad commit.

Kết thúc:

```bash
git bisect reset
```

## 4. Practical implementation

Có thể tự động hóa nếu có deterministic test script:

```bash
git bisect start HEAD v1.8.0
git bisect run dotnet test tests/Regression.Tests \
  --filter FullyQualifiedName~PriceCalculationRegression
```

Exit code 0 = good; non-zero phù hợp semantics của bisect run.

## 5. Real production scenario

Sau nhiều merges, checkout API bắt đầu tạo rounding sai trong một edge case. Không ai nhớ commit nào gây ra.

Team viết regression test tái hiện bug và chạy `git bisect run`. Trong vài vòng, commit refactor decimal conversion được xác định.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit không liên quan hoặc kết quả thay đổi mỗi lần.

**Evidence** → test flaky hoặc commits giữa history không build được.

**Hypothesis** → predicate good/bad không deterministic.

**Diagnosis** → chạy test lặp lại cùng commit; kiểm tra environment dependency.

**Fix** → làm test deterministic; dùng `git bisect skip` cho commit không test được.

**Verification** → rerun bisect và confirm candidate bằng parent/child commits.

## 7. Common mistakes

* Chọn `good` commit chưa thực sự xác nhận.
* Bisect bằng manual observation không ổn định.
* Quên reset sau khi xong.
* Tin candidate commit tuyệt đối mà không inspect diff/context.
* Dùng bisect cho bug phụ thuộc external data không reproducible.

## 8. Alternatives

* `git log` / PR history khi suspect range rất nhỏ.
* `git blame` khi đã biết dòng code liên quan.
* Observability/deployment comparison khi regression gắn với environment hơn source commit.

## 9. Trade-offs

### Advantages

* Thu hẹp history rất nhanh.
* Tận dụng regression test để có evidence.

### Costs / Risks

* Cần reproducible predicate.
* Historical commits có thể không build với environment hiện tại.
* Merge topology phức tạp có thể cần interpretation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết checkout/history cơ bản và khái niệm good/bad commit.

### Middle

Dùng bisect thủ công cho regression reproducible.

### Senior

Tự động hóa bisect bằng focused test và xử lý flaky/history issues.

### Technical Lead / Architect

Xây release/test discipline để regressions có thể được cô lập bằng evidence nhanh chóng.

## 11. Key takeaway

* `git bisect` biến regression search thành binary-search problem.
* Giá trị cao nhất xuất hiện khi có deterministic regression test.
* Candidate commit vẫn cần code review và causal verification.

# 9. Akamai/CDN `stale-while-revalidate`: giảm origin latency nhưng phải quản lý freshness và invalidation rõ ràng

## 1. What is it?

`stale-while-revalidate` cho phép cache phục vụ response hơi cũ trong một khoảng thời gian trong khi cache refresh nội dung từ origin ở background.

Ví dụ:

```http
Cache-Control: public, max-age=60, stale-while-revalidate=300
```

Mental model:

```text
0-60s: fresh cache
60-360s: có thể serve stale + revalidate
sau đó: phải refresh theo policy
```

## 2. Why does it exist?

Nếu hàng nghìn requests cùng đến ngay khi TTL hết, tất cả có thể đập vào origin. Đây là thundering-herd behavior ở CDN boundary.

Serving stale tạm thời giúp giữ latency thấp và giảm origin spike trong lúc một refresh xảy ra.

## 3. How does it work?

Browser/CDN semantics phụ thuộc cache implementation và headers. Khi object vừa hết freshness lifetime nhưng còn trong stale window, cache có thể trả object cũ ngay rồi revalidate với origin.

Trong multi-layer setup:

```text
Browser cache
   ↓
Akamai edge
   ↓
Origin/reverse proxy
   ↓
ASP.NET Core
```

mỗi layer có cache policy riêng nên cần hiểu response thực sự đến từ đâu.

## 4. Practical implementation

Cho marketing content chấp nhận stale vài phút:

```csharp
context.Response.Headers.CacheControl =
    "public, max-age=60, stale-while-revalidate=300";
```

Không nên dùng cho response chứa account balance, authorization-sensitive data hoặc dữ liệu phải fresh tuyệt đối.

## 5. Real production scenario

Homepage campaign traffic tăng mạnh đúng lúc cache TTL hết. Không có stale strategy, hàng nghìn edge misses cùng quay về origin và làm CPU spike.

`stale-while-revalidate` giúp edge tiếp tục phục vụ content cũ ngắn hạn trong khi refresh, giảm latency và origin load.

## 6. Failure scenario & troubleshooting

**Symptom** → editor publish banner mới nhưng một số users vẫn thấy banner cũ vài phút.

**Evidence** → response `Age`/cache headers cho thấy stale serving vẫn nằm trong policy.

**Hypothesis** → behavior đúng theo freshness contract nhưng không đúng business expectation.

**Diagnosis** → so sánh TTL/stale window với editorial freshness requirement.

**Fix** → purge targeted object hoặc giảm stale window cho content class đó.

**Verification** → kiểm tra nhiều edge locations và origin bypass.

## 7. Common mistakes

* Dùng stale policy cho personalized content.
* Không document business freshness SLA.
* Purge toàn site thay vì targeted invalidation.
* Chỉ nhìn application logs khi response đến từ edge.
* Đặt TTL quá ngắn rồi tạo origin pressure liên tục.

## 8. Alternatives

* Hard TTL + synchronous refresh: fresh hơn nhưng latency spike khi miss.
* Pre-warming: hữu ích trước known campaigns nhưng không giải quyết mọi expiry.
* Origin shielding/request collapsing: bổ sung để giảm duplicate origin fetches.

## 9. Trade-offs

### Advantages

* Low latency trong expiry window.
* Giảm thundering herd lên origin.
* Tăng availability khi origin chậm ngắn hạn.

### Costs / Risks

* Dữ liệu có thể stale có chủ đích.
* Debug multi-layer cache khó hơn.
* Invalidation semantics cần rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu TTL hết không nhất thiết nghĩa cache phải bỏ object ngay.

### Middle

Biết đọc `Cache-Control`, `Age` và cache-hit headers.

### Senior

Thiết kế stale policy theo freshness/capacity trade-off.

### Technical Lead / Architect

Định nghĩa content classes: cái gì cache được, stale bao lâu, ai sở hữu purge và origin protection strategy.

## 11. Key takeaway

* `stale-while-revalidate` đổi một ít freshness lấy latency và resilience.
* Cache policy là business contract, không chỉ performance config.
* Multi-layer caching cần observability ở từng layer.

# 10. RAG retrieval evaluation: đo chất lượng retrieval riêng khỏi chất lượng model để không sửa prompt cho lỗi dữ liệu

## 1. What is it?

RAG gồm ít nhất hai hệ thống có thể fail độc lập:

```text
User question
   ↓
Retrieval
   ↓ relevant context
LLM generation
   ↓
Answer
```

Retrieval evaluation đo xem retriever có đưa đúng evidence vào context hay không trước khi đánh giá model có tạo câu trả lời tốt hay không.

## 2. Why does it exist?

Nếu answer sai, nguyên nhân có thể là:

* document đúng không được retrieve
* chunk bị cắt sai
* ranking đặt evidence ở quá thấp
* metadata filter loại nhầm dữ liệu
* model bỏ qua context đúng
* prompt cho phép hallucination

Nếu không tách các layers, team dễ “prompt engineer” một retrieval bug.

## 3. How does it work?

Tạo evaluation set gồm:

* query
* expected relevant documents/chunks
* optional expected answer/evidence

Metrics retrieval có thể bao gồm Recall@K, Precision@K, MRR hoặc domain-specific hit rate.

Ví dụ:

```text
Query: "Refund window for enterprise plan?"
Expected chunk: Policy-2026 section 4.2
Top-5 retrieved contains expected? -> Recall@5 hit
Rank of expected chunk -> ranking quality
```

## 4. Practical implementation

Pseudo-near-production C# model:

```csharp
public sealed record RetrievalCase(
    string Query,
    IReadOnlySet<string> ExpectedDocumentIds);

public static double RecallAtK(
    RetrievalCase test,
    IReadOnlyList<string> retrievedIds,
    int k)
{
    var top = retrievedIds.Take(k).ToHashSet();
    var hit = test.ExpectedDocumentIds.Count(top.Contains);

    return test.ExpectedDocumentIds.Count == 0
        ? 1
        : (double)hit / test.ExpectedDocumentIds.Count;
}
```

Sau retrieval eval mới đánh giá answer faithfulness/correctness.

## 5. Real production scenario

Support assistant trả policy refund cũ. Model được blame vì hallucination.

Investigation cho thấy vector search thường retrieve version 2025 do chunk cũ có lexical similarity cao hơn, còn metadata filter không ưu tiên active policy version.

Sửa prompt không giải quyết được root cause. Cần version-aware retrieval/indexing.

## 6. Failure scenario & troubleshooting

**Symptom** → model trả lời sai dù “RAG đã bật”.

**Evidence** → trace cho thấy context không chứa document đúng.

**Hypothesis** → retrieval failure.

**Diagnosis** → chạy evaluation query, inspect top-K, similarity/reranker scores và metadata filters.

**Fix** → cải thiện chunking, metadata, hybrid search, reranking hoặc index freshness.

**Verification** → Recall@K tăng trên fixed eval set và answer quality tăng mà không chỉ test một anecdotal query.

## 7. Common mistakes

* Chỉ đánh giá final answer.
* Thay prompt liên tục mà không lưu retrieval trace.
* Dùng một vài demo questions làm benchmark.
* Không version documents.
* Nhét top-K quá lớn làm context đầy noise.
* Cho model tự quyết authorization dựa trên retrieved text.

## 8. Alternatives

* Fine-tuning không thay thế retrieval khi knowledge thay đổi thường xuyên.
* Direct SQL/tool lookup tốt hơn vector search cho deterministic structured facts.
* Hybrid lexical + vector + reranking thường phù hợp khi domain có cả exact identifiers và semantic language.

## 9. Trade-offs

### Advantages

* Xác định lỗi nằm ở retrieval hay generation.
* Cho phép regression testing khi đổi embedding/chunking/reranker.
* Tạo evidence cho tuning decisions.

### Costs / Risks

* Cần curated evaluation dataset.
* Ground truth có thể tốn công duy trì.
* Metrics retrieval tốt chưa đảm bảo answer cuối cùng tốt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu RAG không phải “LLM biết tài liệu”; context phải được retrieve trước.

### Middle

Biết log top-K chunks, metadata và scores để debug.

### Senior

Tách retrieval metrics khỏi answer metrics và xây regression eval.

### Technical Lead / Architect

Quyết định dữ liệu nào dùng vector retrieval, dữ liệu nào phải deterministic lookup; thiết kế observability, versioning và evaluation lifecycle cho toàn AI system.

## 11. Key takeaway

* RAG có ít nhất hai failure domains: retrieval và generation.
* Đừng sửa prompt khi evidence đúng chưa vào context.
* Evaluation set và retrieval telemetry biến RAG tuning từ cảm tính thành engineering process.
