# 1. `CancellationToken` và graceful cancellation trong ASP.NET Core

## 1. What is it?

`CancellationToken` là cơ chế cooperative cancellation trong .NET. Nó không force-stop thread; caller phát tín hiệu hủy và operation phía dưới chủ động quan sát để dừng đúng lúc. Trong ASP.NET Core, request bị client hủy, timeout budget hết hoặc application shutdown đều là những nguồn cancellation quan trọng.

## 2. Why does it exist?

Nếu request đã mất consumer nhưng backend vẫn query database, gọi external API hoặc xử lý file, hệ thống tiếp tục tiêu tốn capacity cho kết quả không còn giá trị. Dưới load cao, các orphaned operations này làm connection pool, ThreadPool và downstream chậm cho request còn hợp lệ.

## 3. How does it work?

```text
Client disconnects
      |
      v
RequestAborted cancelled
      |
      v
Endpoint -> Application -> EF Core / HttpClient / Stream
```

Cancellation chỉ hiệu quả khi token được propagate xuyên toàn call chain.

## 4. Practical implementation

```csharp
app.MapGet("/orders/{id:guid}", async (
    Guid id,
    OrderDbContext db,
    CancellationToken ct) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

Background worker cũng phải honor shutdown token:

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        await ProcessBatchAsync(stoppingToken);
        await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
    }
}
```

## 5. Real production scenario

Một API export báo cáo mất 20 giây. User đóng tab sau 2 giây nhưng backend vẫn chạy query lớn và upload Blob. Propagate `RequestAborted` giúp dừng work sớm, giảm database I/O và memory pressure.

## 6. Failure scenario & troubleshooting

**Symptom** → traffic giảm nhưng database active queries vẫn cao.  
**Evidence** → request span đã kết thúc nhưng dependency spans vẫn tiếp tục.  
**Hypothesis** → cancellation không được propagate.  
**Diagnosis** → tìm method thiếu `CancellationToken` hoặc dependency call dùng token mặc định.  
**Fix** → propagate token end-to-end.  
**Verification** → hủy request trong load test và xác nhận dependency dừng sớm.

## 7. Common mistakes

* Nhận token ở controller nhưng không truyền xuống dưới.
* Dùng `.Result`/`.Wait()` khiến cancellation semantics khó kiểm soát.
* Log `OperationCanceledException` như server error.
* Nghĩ cancellation tự động rollback mọi side effect.

## 8. Alternatives

Timeout giới hạn thời gian; cancellation truyền tín hiệu. Long-running work cần sống lâu hơn HTTP request nên chuyển sang queue + Worker Service hoặc Azure Functions.

## 9. Trade-offs

### Advantages

* Giảm wasted work.
* Hỗ trợ graceful shutdown.
* Cải thiện capacity under load.

### Costs / Risks

* Tăng complexity trong call chain.
* Cancellation giữa multi-step workflow có thể để lại partial state nếu boundary sai.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cancellation là cooperative, không phải kill thread.

### Middle

Biết truyền token vào EF Core, `HttpClient`, streams và background loops.

### Senior

Hiểu interaction giữa cancellation, timeout, retry và transaction boundary.

### Technical Lead / Architect

Quyết định workload nào gắn với request lifetime và workload nào cần background boundary riêng.

## 11. Key takeaway

* Cancellation phải propagate end-to-end.
* Cancellation đúng giúp reliability chứ không chỉ UX.
* Side effect và transaction boundary phải được thiết kế cùng cancellation.

# 2. `ProblemDetails` và error contract ổn định cho REST API

## 1. What is it?

`ProblemDetails` là format chuẩn hóa cho lỗi HTTP. Giá trị lớn nhất không nằm ở JSON shape mà ở việc tạo một error contract có semantics ổn định cho client: lỗi validation, conflict, unauthorized hay server failure phải phân biệt rõ.

## 2. Why does it exist?

Nếu mỗi endpoint trả một kiểu lỗi khác nhau, frontend và external consumers phải viết logic đặc biệt cho từng API. Contract không ổn định tạo coupling và làm backward compatibility khó kiểm soát.

## 3. How does it work?

```text
Endpoint failure
   |
Exception middleware
   |
Map domain/application error
   |
HTTP status + ProblemDetails
```

`404`, `409`, `400`, `401/403`, `500` phải phản ánh semantics thay vì dùng thay thế tùy tiện.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();
var app = builder.Build();
app.UseExceptionHandler();

app.MapPost("/orders", async (
    CreateOrderRequest request,
    IOrderService service,
    CancellationToken ct) =>
{
    var result = await service.CreateAsync(request, ct);

    return result switch
    {
        CreateOrderResult.Success s => Results.Created($"/orders/{s.OrderId}", s),
        CreateOrderResult.Duplicate => Results.Problem(
            statusCode: 409,
            title: "Order already exists",
            type: "https://example.com/problems/order-duplicate"),
        _ => Results.Problem(statusCode: 500)
    };
});
```

## 5. Real production scenario

Checkout hết inventory. Nếu backend trả `500`, client có thể retry vô ích. Nếu trả `409` với stable problem type, client biết đây là business conflict và refresh trạng thái inventory.

## 6. Failure scenario & troubleshooting

**Symptom** → client show “Unknown error”.  
**Evidence** → cùng business case trả response shape khác giữa endpoints.  
**Hypothesis** → không có centralized error mapping.  
**Diagnosis** → kiểm tra exception middleware và error taxonomy.  
**Fix** → chuẩn hóa status, problem type và validation contract.  
**Verification** → contract tests cho success và error responses.

## 7. Common mistakes

* Trả `200 OK` với `{ success:false }` cho mọi lỗi.
* Expose stack trace/internal exception message.
* Dùng `500` cho validation hoặc conflict.
* Thay đổi error code tùy ý giữa releases.

## 8. Alternatives

Custom error envelope có thể phù hợp với hệ thống legacy, miễn có stable machine-readable code và HTTP semantics rõ ràng.

## 9. Trade-offs

### Advantages

* Client integration rõ hơn.
* Debugging và observability tốt hơn.
* Backward compatibility dễ quản lý.

### Costs / Risks

* Cần maintain error taxonomy.
* Quá nhiều error codes cũng tạo complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP status mang semantics.

### Middle

Implement centralized exception handling và validation response.

### Senior

Thiết kế stable error contract và retry semantics.

### Technical Lead / Architect

Định nghĩa organization-wide API error conventions và versioning rules.

## 11. Key takeaway

* Error response cũng là API contract.
* Stable error type quan trọng cho machine clients.
* Không leak internal exceptions ra ngoài boundary.

# 3. EF Core `N+1`, `Include`, projection và split query

## 1. What is it?

`N+1` xảy ra khi application lấy N parent rows rồi chạy thêm một query cho từng row để lấy dữ liệu liên quan. EF Core có nhiều chiến lược load data: projection, `Include`, explicit loading và split query.

## 2. Why does it exist?

Object graph và relational database có model khác nhau. Một navigation property trông đơn giản trong C# nhưng có thể gây hàng trăm round trips hoặc một JOIN khổng lồ nếu load không đúng cách.

## 3. How does it work?

```text
Query Orders -> 100 rows
for each order:
    Query Items -> 100 more queries
```

Một single query với nhiều collections tránh N+1 nhưng có thể tạo row multiplication. Split query đổi một giant JOIN thành vài queries có kiểm soát.

## 4. Practical implementation

Projection cho read API:

```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.Status == OrderStatus.Open)
    .Select(x => new OrderSummaryDto(
        x.Id,
        x.Customer.Name,
        x.Items.Count,
        x.Items.Sum(i => i.Quantity * i.UnitPrice)))
    .ToListAsync(ct);
```

Entity graph khi cần:

```csharp
var order = await db.Orders
    .Include(x => x.Items)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .SingleAsync(x => x.Id == id, ct);
```

## 5. Real production scenario

CMS list 100 pages; mỗi page lazy-load author và tags. Local DB nhanh nhưng production có network latency nên vài trăm round trips làm p95 tăng mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng gần tuyến tính với số rows.  
**Evidence** → SQL logs lặp cùng query pattern hàng trăm lần.  
**Hypothesis** → N+1.  
**Diagnosis** → correlate request trace với database spans.  
**Fix** → projection, eager loading hoặc split query phù hợp.  
**Verification** → số round trips giảm rõ và p95 ổn định hơn.

## 7. Common mistakes

* Bật lazy loading theo mặc định.
* `Include` mọi navigation “cho chắc”.
* Không kiểm tra Cartesian explosion.
* Load entity rồi map DTO trong memory khi SQL có thể project.

## 8. Alternatives

Dapper/raw SQL phù hợp với complex hot read queries. CQRS read model hữu ích khi read shape khác transactional model đáng kể, nhưng không nên introduce chỉ để tránh viết projection.

## 9. Trade-offs

### Advantages

Projection giảm I/O và allocations. Split query giảm row multiplication.

### Costs / Risks

Split query tăng round trips và có consistency implications giữa queries. `Include` đơn giản nhưng dễ over-fetch.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu navigation property không miễn phí về database.

### Middle

Biết dùng projection, `Include`, `AsSplitQuery`, `AsNoTracking`.

### Senior

Phân tích generated SQL, round trips và execution plan.

### Technical Lead / Architect

Quyết định khi nào direct EF Core read model đủ và khi nào cần read boundary riêng.

## 11. Key takeaway

* N+1 là vấn đề round trip.
* Projection thường là lựa chọn tốt cho read APIs.
* `Include` và split query đều phải được đo.

# 4. Elasticsearch analyzer, mapping và reindex strategy

## 1. What is it?

Elasticsearch full-text search dựa trên inverted index. Analyzer quyết định text được tokenize và normalize ra sao; mapping định nghĩa field types như `text`, `keyword`, date hoặc numeric.

## 2. Why does it exist?

SQL query thông thường không tối ưu cho relevance ranking, linguistic tokenization và search-specific aggregations ở quy mô lớn. Elasticsearch pre-processes dữ liệu để phục vụ search workload.

## 3. How does it work?

```text
"Running Shoes"
      |
   Analyzer
      |
 running, shoes
      |
 Inverted Index
```

`text` phù hợp full-text; `keyword` phù hợp exact match, sort và aggregation. Mapping thay đổi lớn thường cần index mới + reindex.

## 4. Practical implementation

```json
{
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "fields": {
          "keyword": { "type": "keyword" }
        }
      },
      "status": { "type": "keyword" },
      "createdAt": { "type": "date" }
    }
  }
}
```

Safe rollout:

```text
products-v1 <- alias products-read
create products-v2
reindex
switch alias
```

## 5. Real production scenario

E-commerce search cần full-text product name nhưng exact filter theo brand/status. Mapping sai làm relevance kém hoặc aggregation không đúng.

## 6. Failure scenario & troubleshooting

**Symptom** → query không match như kỳ vọng.  
**Evidence** → analyzer tokens hoặc mapping khác assumptions.  
**Hypothesis** → analyzer/mapping mismatch.  
**Diagnosis** → kiểm tra `_analyze`, mapping và query DSL.  
**Fix** → version index, reindex, switch alias.  
**Verification** → relevance test set + latency + document count consistency.

## 7. Common mistakes

* Dùng Elasticsearch làm transactional source of truth.
* Dynamic mapping không kiểm soát.
* Không version index schema.
* API phụ thuộc exact index name thay vì alias.

## 8. Alternatives

SQL Server/PostgreSQL full-text có thể đủ cho scope nhỏ. Dedicated search engine chỉ nên xuất hiện khi search requirements justify operational cost.

## 9. Trade-offs

### Advantages

* Full-text và relevance mạnh.
* Scale search độc lập.

### Costs / Risks

* Eventual consistency.
* Reindex có operational cost.
* Mapping decisions khó sửa trực tiếp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu inverted index, `text`, `keyword`.

### Middle

Biết thiết kế mapping và test analyzer.

### Senior

Biết alias migration, reindex và failure recovery.

### Technical Lead / Architect

Quyết định Elasticsearch có cần tồn tại không và ai sở hữu synchronization pipeline.

## 11. Key takeaway

* Analyzer quyết định search semantics.
* Mapping là schema dù Elasticsearch linh hoạt.
* Reindex + alias là pattern quan trọng cho schema evolution.

# 5. Saga Pattern và compensating transaction trong distributed systems

## 1. What is it?

Saga là cách phối hợp business workflow trải qua nhiều service/data stores mà không dùng một ACID transaction xuyên toàn hệ thống. Mỗi step commit local transaction; khi step sau thất bại, system thực hiện compensating action để đưa business state về trạng thái chấp nhận được.

## 2. Why does it exist?

Order, Payment, Inventory thường sở hữu database riêng trong distributed architecture. Distributed ACID transaction tạo coupling và operational complexity lớn. Saga chấp nhận intermediate state và eventual consistency để đổi lấy autonomy.

## 3. How does it work?

```text
Create Order
   |
Reserve Inventory
   |
Charge Payment
   |
Confirm Order
```

Nếu payment fail:

```text
Payment failed
   |
Release Inventory
   |
Cancel Order
```

Compensation là business action ngược, không phải byte-level rollback.

## 4. Practical implementation

```csharp
public enum OrderSagaState
{
    Created,
    InventoryReserved,
    PaymentCaptured,
    Completed,
    Compensating,
    Failed
}
```

Message handlers cần idempotent và saga state phải durable để retry/recovery an toàn.

## 5. Real production scenario

Checkout reserve inventory thành công nhưng payment provider timeout. Hệ thống không thể biết chắc payment failed hay response bị mất. Saga cần trạng thái pending/reconciliation thay vì blind retry.

## 6. Failure scenario & troubleshooting

**Symptom** → inventory bị giữ nhưng order không hoàn tất.  
**Evidence** → saga dừng ở `InventoryReserved`.  
**Hypothesis** → message publication/consumer failure.  
**Diagnosis** → inspect Outbox, broker, DLQ và correlation trace.  
**Fix** → replay idempotently hoặc compensate theo business rule.  
**Verification** → saga đạt terminal state và invariant được khôi phục.

## 7. Common mistakes

* Nghĩ compensation giống SQL rollback.
* Không thiết kế idempotency.
* Không lưu saga state.
* Không có timeout/reconciliation cho stuck workflow.

## 8. Alternatives

Nếu workflow nằm trong một database, local ACID transaction đơn giản hơn. Modular Monolith có thể giữ shared transaction boundary khi business chưa cần distributed ownership.

## 9. Trade-offs

### Advantages

* Service autonomy.
* Không cần cross-service ACID transaction.

### Costs / Risks

* Eventual consistency.
* Intermediate states nhiều hơn.
* Debugging và compensation phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu distributed workflow không rollback giống một SQL transaction.

### Middle

Implement idempotent handlers và compensation cơ bản.

### Senior

Thiết kế saga state, timeout, retry, reconciliation và DLQ handling.

### Technical Lead / Architect

Quyết định workflow có thực sự cần cross-service Saga hay nên giữ cùng transaction boundary.

## 11. Key takeaway

* Saga là business consistency pattern.
* Compensation phải được thiết kế có chủ đích.
* Nếu một database đủ, đừng thêm Saga chỉ vì kiến trúc trông hiện đại.

# 6. Azure App Service Deployment Slots và database migration an toàn

## 1. What is it?

Deployment Slot cho phép deploy version mới vào slot phụ như `staging`, warm up và validate trước khi swap sang production. Nó giảm risk của application rollout nhưng không tự giải quyết database compatibility.

## 2. Why does it exist?

Deploy trực tiếp dễ gây cold start hoặc downtime. Slot cho phép chuẩn bị instance mới trước khi chuyển traffic. Tuy nhiên nếu staging code thực hiện destructive migration trên shared database, production version cũ có thể bị phá ngay trước swap.

## 3. How does it work?

```text
Production -> v1
Staging    -> v2
Deploy v2
Warm up + health validation
Swap
Production -> v2
```

Database nên evolve theo sequence:

```text
Expand schema -> compatible code -> backfill -> switch behavior -> contract later
```

## 4. Practical implementation

Ví dụ rename column: add `NewColumn` trước; deploy code đọc được old/new; backfill; chuyển write; chỉ drop old column sau khi old application version không còn chạy.

## 5. Real production scenario

Release v2 drop column cũ khi deploy staging. Production v1 vẫn đang dùng column đó nên fail trước cả khi slot swap. Deployment mechanism đúng nhưng schema strategy sai.

## 6. Failure scenario & troubleshooting

**Symptom** → production lỗi ngay khi staging deploy.  
**Evidence** → logs báo missing column.  
**Hypothesis** → migration không backward-compatible.  
**Diagnosis** → compare migration với code version đang live.  
**Fix** → restore compatibility hoặc rollback migration khi safe.  
**Verification** → chạy v1/v2 song song trên schema mới trong pre-production.

## 7. Common mistakes

* Nghĩ slot swap đồng nghĩa zero-risk deployment.
* Chạy destructive migration trước khi old app rời production.
* Không warm up/health validate staging.
* Rollback binary nhưng database đã incompatible.

## 8. Alternatives

Blue-Green, Canary và rolling deployment có operational model khác nhưng cùng yêu cầu backward-compatible data evolution.

## 9. Trade-offs

### Advantages

* Giảm cold start và downtime.
* Swap nhanh.

### Costs / Risks

* Slot configuration phức tạp hơn.
* Database vẫn là shared state khó rollback.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu slot là version app khác chạy trước production.

### Middle

Biết deploy, warm-up, health check và slot settings.

### Senior

Thiết kế backward-compatible migration và rollback path.

### Technical Lead / Architect

Định nghĩa release strategy kết hợp app rollout, schema evolution, feature flags và observability.

## 11. Key takeaway

* Deployment Slot không giải quyết database migration.
* Schema phải hỗ trợ old/new coexistence.
* Rollback chỉ thực tế khi data/schema còn tương thích.

# 7. Docker multi-stage build, image layers và runtime hardening

## 1. What is it?

Docker image gồm immutable layers. Multi-stage build tách build environment khỏi runtime image: SDK/compiler ở build stage; runtime stage chỉ chứa artifacts cần chạy.

## 2. Why does it exist?

Ship cả .NET SDK, source, package cache và build tools làm image lớn, deploy chậm và tăng vulnerability surface.

## 3. How does it work?

```text
Build Stage: SDK -> restore -> publish
                    |
                    v
Runtime Stage: ASP.NET runtime + published output
```

Layer cache tăng build speed nhưng secret từng copy vào layer có thể vẫn tồn tại trong image history.

## 4. Practical implementation

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet restore
RUN dotnet publish -c Release -o /app/publish --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
USER app
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

## 5. Real production scenario

Single-stage SDK image hơn 1 GB, pull chậm và scanner phát hiện nhiều packages không cần runtime. Multi-stage build giảm image size và attack surface.

## 6. Failure scenario & troubleshooting

**Symptom** → container chạy local nhưng fail production với `permission denied`.  
**Evidence** → app chạy non-root và ghi vào path không writable.  
**Hypothesis** → hidden filesystem assumption.  
**Diagnosis** → inspect write paths và volume ownership.  
**Fix** → tạo writable directory/volume rõ ràng.  
**Verification** → integration test bằng đúng non-root runtime user.

## 7. Common mistakes

* Chạy root không cần thiết.
* Copy `.env`/credentials vào image.
* Không có `.dockerignore`.
* Dùng build tools trong runtime image.

## 8. Alternatives

Self-contained deployment hoặc traditional hosting vẫn hợp lý nếu containerization không giảm deployment complexity.

## 9. Trade-offs

### Advantages

* Reproducible artifact.
* Runtime image nhỏ hơn.
* Hardening dễ hơn.

### Costs / Risks

* Thêm registry/image lifecycle.
* Team cần hiểu networking, volumes và resource limits.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu image, container và layer khác nhau.

### Middle

Viết multi-stage Dockerfile và chạy non-root.

### Senior

Tối ưu cache, secret handling và startup behavior.

### Technical Lead / Architect

Quyết định container có mang business/operational value hay chỉ chuyển complexity sang platform khác.

## 11. Key takeaway

* Tách build và runtime image.
* Không đưa secrets vào layers.
* Test production image với đúng runtime permissions.

# 8. Contract testing cho API và integration boundaries

## 1. What is it?

Contract testing kiểm tra rằng producer và consumer đồng ý về interface: endpoint, payload shape, required fields, status semantics hoặc message schema.

## 2. Why does it exist?

API có thể pass unit tests nhưng vẫn phá consumer nếu đổi field type, nullable behavior hoặc status code. Full E2E test phát hiện được nhưng thường chậm và brittle.

## 3. How does it work?

Consumer expectation được biểu diễn thành contract; producer verification chạy contract đó trên version mới. OpenAPI/schema diff cũng có thể chặn breaking changes trong CI.

## 4. Practical implementation

```csharp
[Fact]
public async Task GetOrder_returns_stable_contract()
{
    var response = await client.GetAsync("/orders/123");
    response.StatusCode.Should().Be(HttpStatusCode.OK);

    var json = await response.Content.ReadFromJsonAsync<JsonElement>();
    json.GetProperty("id").GetString().Should().Be("123");
    json.GetProperty("status").GetString().Should().NotBeNull();
}
```

## 5. Real production scenario

Backend đổi `customerId` từ string thành object. Backend tests pass nhưng mobile app cũ crash. Contract test hoặc schema compatibility check có thể chặn release.

## 6. Failure scenario & troubleshooting

**Symptom** → consumer fail sau backend release dù health endpoint vẫn green.  
**Evidence** → payload field/type/status thay đổi.  
**Hypothesis** → breaking contract change.  
**Diagnosis** → compare old/new schema và consumer expectation.  
**Fix** → restore compatibility hoặc version contract.  
**Verification** → producer verification pass cho active consumers.

## 7. Common mistakes

* Mock producer hoàn toàn trong consumer tests.
* Test implementation detail thay vì contract.
* Không version event/message schema.
* Nghĩ `100% coverage` bảo vệ integration compatibility.

## 8. Alternatives

Integration tests kiểm tra behavior rộng hơn; E2E bảo vệ critical user journeys. Contract testing bổ sung compatibility coverage giữa boundaries.

## 9. Trade-offs

### Advantages

* Feedback nhanh về breaking changes.
* Ít brittle hơn full E2E.

### Costs / Risks

* Contract lifecycle management.
* Có thể giữ producer tương thích với outdated consumer quá lâu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu public API shape là contract.

### Middle

Viết integration/contract tests cho success và error responses.

### Senior

Thiết kế compatibility rules và schema evolution.

### Technical Lead / Architect

Quyết định boundary nào cần contract testing và deprecation policy thế nào.

## 11. Key takeaway

* Unit test không bảo vệ integration contract.
* Contract testing tập trung vào compatibility.
* Test strategy nên dựa trên risk, không phải coverage percentage.

# 9. `Git bisect` và chiến lược cô lập deployment regression

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên gây regression. Thay vì kiểm tra tuần tự hàng chục commit, nó giảm số lần test xuống gần `log2(N)`.

## 2. Why does it exist?

Production regression thường xuất hiện sau một khoảng nhiều commits: build cuối tuần trước tốt, build hôm nay xấu. Đọc diff thủ công dễ bị bias và bỏ sót thay đổi gián tiếp.

## 3. How does it work?

```text
Known good commit ---------------- Known bad commit
             \      midpoint      /
              test good/bad
                  |
            halve search space
```

Git lặp lại cho tới khi tìm first bad commit.

## 4. Practical implementation

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0

# test current midpoint
git bisect good   # hoặc git bisect bad

# khi hoàn tất
git bisect reset
```

Nếu có deterministic regression test:

```bash
git bisect run ./scripts/regression-test.sh
```

## 5. Real production scenario

API p95 tăng gấp đôi sau 40 commits. Regression test tái hiện bằng một benchmark/query scenario. `git bisect run` xác định commit thay đổi serialization option gây allocation tăng mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → `git bisect` đưa kết quả không ổn định.  
**Evidence** → cùng commit lúc pass lúc fail.  
**Hypothesis** → test flaky hoặc phụ thuộc external state.  
**Diagnosis** → chạy lại midpoint nhiều lần, kiểm tra fixture/environment.  
**Fix** → tạo deterministic reproduction trước khi bisect.  
**Verification** → commit trước consistently good, commit sau consistently bad.

## 7. Common mistakes

* Bắt đầu bisect khi chưa có reproducible test.
* Chọn “good” commit nhưng thực tế chưa verify.
* Test phụ thuộc shared database/environment.
* Stop ở commit nghi ngờ nhưng không đọc causal diff.

## 8. Alternatives

Manual diff review phù hợp khi chỉ có vài commits. Feature flags, deployment telemetry và canary analysis có thể localize theo release trước khi cần bisect.

## 9. Trade-offs

### Advantages

* Giảm search space nhanh.
* Dựa trên evidence hơn phỏng đoán.
* Có thể automate.

### Costs / Risks

* Cần reproducible test.
* Intermediate commits có thể không build hoặc cần migration đặc biệt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu concept good/bad commit.

### Middle

Biết chạy bisect thủ công và đọc diff kết quả.

### Senior

Tạo deterministic regression harness và automate `bisect run`.

### Technical Lead / Architect

Thiết kế release/build retention và observability đủ tốt để regression localization nhanh, thay vì phụ thuộc cá nhân nhớ commit nào thay đổi gì.

## 11. Key takeaway

* Bisect hiệu quả nhất khi regression tái hiện được.
* Binary search giảm mạnh số commits cần kiểm tra.
* Commit được tìm thấy là điểm bắt đầu causal analysis, không phải kết luận cuối cùng.

# 10. SLI, SLO và error budget trong Production Engineering

## 1. What is it?

SLI là chỉ số reliability thực tế, ví dụ tỷ lệ request thành công hoặc latency dưới threshold. SLO là target cho SLI. Error budget là phần failure được phép tương ứng với SLO. SLA là cam kết contractual/business và không nên nhầm với engineering SLO.

## 2. Why does it exist?

“Zero downtime” là mục tiêu không thực tế cho đa số hệ thống. SLO biến reliability thành một target đo được để cân bằng feature velocity và reliability investment.

## 3. How does it work?

Ví dụ SLO availability 99.9% trong 30 ngày:

```text
Error budget = 0.1%
```

Nếu có 10 triệu eligible requests, khoảng 10.000 requests có thể fail theo định nghĩa SLI trước khi budget bị tiêu hết.

## 4. Practical implementation

Một SLI đơn giản:

```text
good requests / eligible requests
```

Ví dụ `good` = success response và latency < 500 ms; `eligible` loại health checks và một số client-abort cases. Azure Monitor, Application Insights hoặc OpenTelemetry có thể feed dashboard và burn-rate alert.

## 5. Real production scenario

Team deploy hàng ngày. Sau vài regressions, error budget burn quá nhanh. Thay vì freeze release vĩnh viễn, team tạm ưu tiên reliability fixes cho tới khi burn rate trở lại kiểm soát.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard báo availability rất cao nhưng users vẫn phàn nàn.  
**Evidence** → metric chỉ đo process up/down, không đo checkout failure hoặc tail latency.  
**Hypothesis** → SLI không đại diện user experience.  
**Diagnosis** → map critical journey sang measurable indicator.  
**Fix** → thiết kế SLI gần user outcome hơn.  
**Verification** → incident thực phải phản ánh rõ trên SLI.

## 7. Common mistakes

* Chỉ dùng infrastructure uptime làm SLI.
* Đặt SLO không dựa trên business need.
* Nhầm SLA và SLO.
* Alert mọi error thay vì impact/burn rate.

## 8. Alternatives

Simple uptime/latency thresholds có thể đủ cho hệ thống nhỏ. Error budget có giá trị nhất khi team có đủ traffic, release frequency và operational maturity để hành động theo metric.

## 9. Trade-offs

### Advantages

* Reliability decision dựa trên dữ liệu.
* Cân bằng release velocity và stability.

### Costs / Risks

* SLI definition khó.
* Metric sai tạo false confidence.
* Observability backend có operational cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu metric, target và contractual commitment khác nhau.

### Middle

Biết đọc availability/latency SLI và dashboard.

### Senior

Thiết kế SLI theo user impact và burn-rate alert.

### Technical Lead / Architect

Đặt SLO theo business criticality và dùng error budget để cân bằng release risk với reliability investment.

## 11. Key takeaway

* SLI phải phản ánh user experience, không chỉ server uptime.
* SLO là engineering target; SLA là business commitment.
* Error budget biến reliability thành trade-off có thể quản lý.
