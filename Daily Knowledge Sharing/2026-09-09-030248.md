# 1. C# GC pinning và Pinned Object Heap: khi interop làm managed memory khó compact

## 1. What is it?

Garbage Collector của .NET không chỉ thu hồi object không còn dùng; với nhiều generations nó còn **compact** memory để giảm fragmentation. Một object bị **pinned** là object mà GC không được phép di chuyển vì native code, pointer hoặc interop đang phụ thuộc địa chỉ memory hiện tại của nó.

Mental model:

```text
Managed heap bình thường
[A][B][dead][C][D]
        ↓ GC compact
[A][B][C][D]

Có pinned object
[A][PIN][dead][C][D]
       ↓
GC không thể dời PIN
→ khoảng trống có thể còn lại
→ fragmentation tăng
```

Pinned Object Heap (POH) được đưa vào modern .NET để gom những object được thiết kế để pin lâu dài sang một heap riêng, giảm ảnh hưởng fragmentation lên các heap compacting thông thường.

## 2. Why does it exist?

Interop với native API, socket buffers, P/Invoke, unsafe code hoặc một số high-performance APIs có lúc cần địa chỉ memory ổn định.

Nếu runtime cứ di chuyển object trong GC compaction, native pointer có thể trỏ vào địa chỉ cũ và gây memory corruption. Vì vậy pinning tồn tại để đổi lấy địa chỉ ổn định.

Vấn đề là nếu pin quá nhiều object hoặc giữ pin quá lâu, GC mất tự do sắp xếp heap và fragmentation tăng.

## 3. How does it work?

Một object có thể bị pin bằng `GCHandle`, `fixed`, hoặc các API interop khác.

Ví dụ:

```csharp
var buffer = new byte[4096];

var handle = GCHandle.Alloc(
    buffer,
    GCHandleType.Pinned);

try
{
    IntPtr address = handle.AddrOfPinnedObject();
    NativeApi.Process(address, buffer.Length);
}
finally
{
    handle.Free();
}
```

Trong thời gian handle tồn tại, GC không được relocate `buffer`.

POH hỗ trợ allocation pinned có chủ đích:

```csharp
byte[] buffer = GC.AllocateArray<byte>(
    length: 4096,
    pinned: true);
```

Object đó được tạo trong heap dành cho pinned allocations thay vì làm chướng ngại vật trong heap compacting thông thường.

## 4. Practical implementation

Nếu pin chỉ để gọi native API ngắn hạn, hãy giữ lifetime cực ngắn:

```csharp
public static unsafe void ProcessBuffer(byte[] buffer)
{
    fixed (byte* ptr = buffer)
    {
        NativeApi.Process((IntPtr)ptr, buffer.Length);
    }
}
```

Không giữ pointer hoặc pinned handle ra ngoài boundary của operation nếu không thật sự cần.

Nếu có reusable long-lived buffers cho native I/O, cân nhắc POH hoặc native/unmanaged allocation thay vì pin hàng loạt short-lived arrays ở Gen 0/Gen 1.

## 5. Real production scenario

Một image-processing service gọi native codec. Mỗi request tạo nhiều `byte[]` rồi pin chúng suốt toàn pipeline. Dưới load cao, memory footprint tăng dần và GC pause dài hơn dù tổng live objects không tăng tương ứng.

Profiler cho thấy nhiều pinned handles và fragmented heap. Vấn đề không phải memory leak truyền thống; object được giải phóng, nhưng heap bị chia vụn vì các pinned regions.

## 6. Failure scenario & troubleshooting

**Symptom** → process memory tăng, allocation rate bình thường nhưng GC duration và fragmentation tăng.

**Evidence** → memory profiler cho thấy nhiều pinned objects hoặc pinned handles sống lâu.

**Hypothesis** → long-lived pinning đang cản compaction.

**Diagnosis** → dùng `dotnet-gcdump`, PerfView, Visual Studio profiler hoặc `dotnet-counters` để xem heap/GC behavior và pinned object count.

**Fix** → rút ngắn pin lifetime, reuse buffers có kiểm soát, dùng POH/native memory cho long-lived interop buffers.

**Verification** → load test lại, so fragmentation, Gen 2 collections, pause time và working set.

## 7. Common mistakes

* Pin object “cho chắc” dù native API chỉ cần copy dữ liệu.
* Quên `GCHandle.Free()`.
* Giữ pinned buffer trong singleton lâu dài mà không đo fragmentation.
* Dùng unsafe pointer sau khi object đã unpin.
* Nhầm memory fragmentation với managed memory leak.

## 8. Alternatives

* Copy sang unmanaged buffer cho operation ngắn nếu lifetime ownership rõ hơn.
* Dùng `Memory<T>` / `Span<T>` khi chỉ cần zero-copy trong managed code, không cần pin.
* Sử dụng POH cho long-lived pinned buffers.
* Dùng native memory khi component chủ yếu giao tiếp với unmanaged library.

## 9. Trade-offs

### Advantages

* Địa chỉ memory ổn định cho interop.
* Tránh copy trong một số hot path.
* Có thể giảm latency khi data path lớn.

### Costs / Risks

* Tăng fragmentation.
* Ownership và lifetime phức tạp.
* Unsafe misuse có thể gây crash/corruption.
* Optimization khó đáng giá nếu không có profiling evidence.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu GC có thể di chuyển object và pinning ngăn điều đó.

### Middle

Biết dùng `fixed` / `GCHandle` đúng lifetime và luôn release.

### Senior

Phân tích fragmentation, GC pressure và quyết định POH vs unmanaged memory.

### Technical Lead / Architect

Đánh giá interop boundary có thật sự cần zero-copy/pinning hay không và chuẩn hóa memory ownership cho native integrations.

## 11. Key takeaway

* Pinning là correctness requirement cho một số interop cases nhưng có chi phí GC.
* Pin càng ngắn càng tốt.
* Với long-lived pinned buffers, POH hoặc unmanaged memory thường rõ ràng hơn.

# 2. ASP.NET Core model binding + validation boundary: đừng để transport model âm thầm trở thành domain model

## 1. What is it?

Model binding biến HTTP input thành .NET objects. Validation kiểm tra request có thỏa contract transport hay không.

Mental model đúng:

```text
HTTP request
   ↓
Model binding
   ↓
Transport validation
   ↓
Application command
   ↓
Domain invariants
```

DTO nhận JSON không nên tự động trở thành domain entity chỉ vì các field trông giống nhau.

## 2. Why does it exist?

HTTP input đến từ boundary không đáng tin cậy. Request có thể thiếu field, sai format, chứa data ngoài range hoặc chứa field mà client không được quyền điều khiển.

Nếu bind thẳng vào entity persistence/domain, transport concerns bắt đầu chi phối domain model và tạo mass-assignment bugs.

## 3. How does it work?

ASP.NET Core bind dữ liệu từ route, query, header, form hoặc body. Validation attributes hoặc custom validators kiểm tra shape/format.

Ví dụ:

```csharp
public sealed record CreateOrderRequest(
    [property: Required] string CustomerId,
    [property: Range(1, 1000)] int Quantity);
```

Nhưng business invariant không nên phụ thuộc hoàn toàn vào DataAnnotations:

```csharp
var result = Order.Create(
    customer,
    product,
    request.Quantity);
```

Domain có thể kiểm tra stock policy, customer status, product state và các invariant không thể hiện chỉ bằng attribute.

## 4. Practical implementation

Endpoint:

```csharp
app.MapPost("/orders", async (
    CreateOrderRequest request,
    OrderService service,
    CancellationToken ct) =>
{
    var result = await service.CreateAsync(
        new CreateOrderCommand(
            request.CustomerId,
            request.Quantity),
        ct);

    return result switch
    {
        CreateOrderResult.Success x =>
            Results.Created($"/orders/{x.Id}", x),

        CreateOrderResult.Invalid x =>
            Results.ValidationProblem(x.Errors),

        _ => Results.Problem(statusCode: 500)
    };
});
```

Request DTO không chứa server-controlled fields như `Status`, `CreatedBy`, `TenantId`, `ApprovedAt` nếu client không được phép set chúng.

## 5. Real production scenario

Một employee management API dùng EF entity làm request model. Entity có `IsAdmin`, `TenantId`, `SalaryApproved` và các fields persistence khác.

Frontend bình thường không gửi chúng, nhưng attacker gửi JSON thủ công với `IsAdmin=true`. Binder populate entity rồi repository save trực tiếp.

Đây là classic over-posting/mass assignment issue.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu server-controlled thay đổi dù UI không có field tương ứng.

**Evidence** → request payload chứa property dư nhưng API vẫn bind/save.

**Hypothesis** → transport model quá rộng hoặc entity được bind trực tiếp.

**Diagnosis** → inspect DTO/entity mapping, binder behavior và update methods.

**Fix** → request-specific DTO, explicit mapping và authorization/domain validation.

**Verification** → negative tests với hidden/unauthorized fields.

## 7. Common mistakes

* Bind EF entity trực tiếp từ request body.
* Dùng validation attribute để thay business rules.
* Tin frontend đã ẩn field thì client không thể gửi field đó.
* Dùng generic PATCH/update reflection không whitelist fields.
* Trả raw model-state structure không thống nhất API error contract.

## 8. Alternatives

FluentValidation có thể hữu ích cho transport/application validation phức tạp. Manual validation phù hợp endpoint nhỏ. Domain object vẫn phải bảo vệ invariant quan trọng dù validation framework nào được dùng.

## 9. Trade-offs

### Advantages

* DTO boundary rõ.
* Giảm mass-assignment risk.
* API contract có thể evolve độc lập domain/persistence model.

### Costs / Risks

* Tăng mapping code.
* Có thể tạo DTO explosion nếu chia quá nhỏ.
* Validation duplicated nếu boundary responsibility không rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu HTTP DTO và domain entity là hai mục đích khác nhau.

### Middle

Thiết kế request model nhỏ, validate input và map explicit.

### Senior

Phân biệt transport validation, authorization và domain invariants; phát hiện over-posting risks.

### Technical Lead / Architect

Đặt conventions cho DTO boundaries, error contracts và server-controlled fields xuyên API surface.

## 11. Key takeaway

* Model binding là transport concern, không phải domain modeling.
* DTO càng explicit càng giảm accidental privilege/data mutation.
* Validation ở transport không thay thế domain invariant và authorization.

# 3. SQL Server keyset pagination: tránh OFFSET càng sâu càng chậm và giữ thứ tự ổn định

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên giá trị cuối cùng đã thấy thay vì “bỏ qua N rows”.

OFFSET pagination:

```sql
ORDER BY CreatedAt DESC
OFFSET 500000 ROWS FETCH NEXT 50 ROWS ONLY;
```

Keyset pagination:

```sql
WHERE (CreatedAt < @LastCreatedAt)
   OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC
OFFSET 0 ROWS FETCH NEXT 50 ROWS ONLY;
```

## 2. Why does it exist?

OFFSET dễ hiểu nhưng page càng sâu, database càng phải scan/sort/skip nhiều rows trước khi trả 50 rows cần thiết.

Ngoài performance, concurrent insert/delete còn khiến item bị duplicate hoặc skip giữa các pages nếu client dựa vào page number.

## 3. How does it work?

Keyset dùng sort key ổn định làm cursor. Query seek vào vị trí sau record cuối của page trước.

Composite ordering thường cần unique tie-breaker:

```text
ORDER BY CreatedAt DESC, Id DESC
```

Cursor phải chứa cả `CreatedAt` và `Id`; chỉ dùng `CreatedAt` có thể bỏ sót rows có cùng timestamp.

## 4. Practical implementation

SQL Server index:

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON Orders(CreatedAt DESC, Id DESC)
INCLUDE (CustomerId, Status, Total);
```

Query:

```sql
SELECT TOP (@Take)
    Id,
    CreatedAt,
    CustomerId,
    Status,
    Total
FROM Orders
WHERE
    @LastCreatedAt IS NULL
    OR CreatedAt < @LastCreatedAt
    OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

API có thể encode cursor thành opaque token thay vì expose raw keys.

## 5. Real production scenario

Admin portal duyệt hàng chục triệu audit records. Page 1 nhanh 30 ms nhưng page 8.000 mất vài giây vì OFFSET phải skip hàng trăm nghìn rows.

Chuyển sang keyset giúp latency page sâu gần với page đầu vì engine seek theo index boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → pagination càng sâu càng chậm, CPU/logical reads tăng.

**Evidence** → Actual Plan cho thấy scan nhiều rows rồi discard.

**Hypothesis** → OFFSET cost tăng theo depth.

**Diagnosis** → so logical reads page 1 vs page 5.000.

**Fix** → keyset cursor + stable composite index.

**Verification** → benchmark nhiều depths và concurrent inserts.

## 7. Common mistakes

* Cursor dùng field không unique.
* Ordering khác index order.
* Cho phép user jump trực tiếp đến page 10.000 nhưng dùng keyset mà không thiết kế navigation semantics.
* Encode cursor nhưng không validate/filter compatibility.
* Dùng keyset khi product thật sự cần random page access chính xác.

## 8. Alternatives

OFFSET phù hợp dataset nhỏ hoặc back-office cần page number đơn giản. Search engine `search_after` là concept tương tự keyset. Snapshot/materialized result phù hợp exports/reporting cần deterministic full traversal.

## 9. Trade-offs

### Advantages

* Performance ổn định hơn ở deep pagination.
* Ít duplicate/skip do concurrent inserts nếu ordering đúng.
* Tận dụng index seek tốt.

### Costs / Risks

* Không dễ jump page N.
* Cursor contract phức tạp hơn.
* Filter/sort thay đổi làm cursor cũ có thể mất nghĩa.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu OFFSET phải bỏ qua rows trước đó.

### Middle

Implement stable cursor với unique tie-breaker.

### Senior

Thiết kế index, cursor compatibility và concurrency semantics.

### Technical Lead / Architect

Quyết định UX/API có thật sự cần page number hay nên chuyển sang cursor-based navigation theo scale thực tế.

## 11. Key takeaway

* OFFSET cost thường tăng theo page depth.
* Keyset cần stable unique ordering.
* Pagination strategy là API + database design decision, không chỉ UI concern.

# 4. Cosmos DB partition key: thiết kế theo access pattern để tránh hot partition và RU waste

## 1. What is it?

Partition key quyết định cách Cosmos DB phân phối items vào logical/physical partitions.

Mental model:

```text
Container
  ├─ partition key A
  ├─ partition key B
  └─ partition key C
        ↓
physical partitions phân phối storage + RU throughput
```

Partition key không chỉ là field “bắt buộc phải chọn”. Nó quyết định scalability, query cost và hotspot behavior.

## 2. Why does it exist?

Cosmos DB cần phân tán dữ liệu và request load qua nhiều physical partitions. Nếu mọi request tập trung vào một key, total account RU lớn vẫn không cứu được partition nóng đó.

Ngược lại, partition key phân phối tốt nhưng không khớp query pattern có thể khiến query fan-out qua nhiều partitions và tốn RU.

## 3. How does it work?

Một request point-read biết cả `id` và partition key có thể route trực tiếp tới partition liên quan.

```csharp
await container.ReadItemAsync<Order>(
    id,
    new PartitionKey(customerId),
    cancellationToken: ct);
```

Nếu query không constrain partition key, Cosmos có thể phải query nhiều partitions.

Partition key tốt thường cần:

* high cardinality;
* phân phối traffic tương đối đều;
* đi cùng access pattern chính;
* tránh single tenant/device quá nóng nếu workload skewed.

## 4. Practical implementation

E-commerce orders theo customer:

```json
{
  "id": "order-123",
  "customerId": "customer-42",
  "status": "Paid",
  "createdAt": "2026-09-09T02:00:00Z"
}
```

Nếu phần lớn requests là “orders của một customer”, `/customerId` là candidate hợp lý.

Nhưng nếu có một marketplace seller với hàng triệu writes/second, seller ID có thể trở thành hot key. Khi đó cần xem hierarchical partition keys hoặc thiết kế key có thêm dimension phù hợp access patterns.

## 5. Real production scenario

Telemetry system chọn `/deviceType` làm partition key vì “chỉ có vài loại device và query theo type”. Kết quả: vài key như `mobile`, `sensor`, `gateway` nhận toàn bộ writes.

Container scale RU rất lớn nhưng một logical partition vẫn nóng, xuất hiện 429 throttling.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều 429 nhưng tổng RU provisioned vẫn có vẻ đủ.

**Evidence** → normalized RU consumption phân bố lệch giữa partition key ranges.

**Hypothesis** → hot partition.

**Diagnosis** → xem top partition keys, request distribution và query fan-out.

**Fix** → redesign partitioning/access pattern; không chỉ tăng RU vô hạn.

**Verification** → load test theo real key distribution, không dùng uniform synthetic IDs nếu production skewed.

## 7. Common mistakes

* Chọn low-cardinality key như `country`, `status`, `type`.
* Chọn random GUID để phân tán đẹp nhưng query luôn cross-partition.
* Chỉ benchmark uniform traffic.
* Dùng relational thinking rồi query join/filter tùy ý.
* Bỏ qua migration cost khi partition key đã sai.

## 8. Alternatives

SQL Server/PostgreSQL phù hợp khi relational joins và transactional consistency quan trọng hơn global distributed scale. MongoDB có sharding trade-offs tương tự. Cosmos DB container riêng theo workload có thể đơn giản hơn một mega-container dùng chung.

## 9. Trade-offs

### Advantages

* Scale-out throughput/storage.
* Point reads rất hiệu quả khi biết partition key.
* Phù hợp distributed workloads.

### Costs / Risks

* Sai partition key rất khó sửa sau này.
* Cross-partition query tốn RU.
* Hot key làm throughput thực thấp hơn kỳ vọng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định data distribution.

### Middle

Biết query point-read, đo RU và tránh low-cardinality key.

### Senior

Phân tích workload skew, hot partitions, consistency và migration options.

### Technical Lead / Architect

Chọn storage model dựa trên access pattern dài hạn; quyết định khi nào Cosmos DB không phải lựa chọn phù hợp.

## 11. Key takeaway

* Partition key là architecture decision, không phải schema detail.
* Distribution tốt nhưng query pattern tệ vẫn tốn RU.
* Benchmark phải dùng traffic distribution giống production.

# 5. DDD Aggregate boundary: transaction consistency, invariant và lý do aggregate không nên quá lớn

## 1. What is it?

Aggregate là consistency boundary trong Domain-Driven Design. Aggregate Root là entry point bảo vệ invariant bên trong aggregate.

Mental model:

```text
Command
   ↓
Aggregate Root
   ↓
validate invariant
   ↓
change internal state
   ↓
one transaction boundary
```

Aggregate không phải “một object graph lớn chứa mọi entity liên quan”.

## 2. Why does it exist?

Business rules thường cần một nhóm state phải nhất quán ngay tại transaction commit. Ví dụ Order không được có total âm hoặc transition từ `Cancelled` sang `Paid` tùy tiện.

Nếu boundary quá nhỏ, invariant bị phân tán. Nếu quá lớn, mọi operation phải load/lock/update một graph khổng lồ và concurrency giảm mạnh.

## 3. How does it work?

Một aggregate nên bảo vệ những invariant cần **strong transactional consistency** cùng lúc.

Ví dụ:

```text
Order aggregate
 ├─ OrderLine
 └─ ShippingAddress value object
```

Nhưng Customer, Inventory và Payment thường không nên nằm chung một aggregate chỉ vì business process có liên quan.

Cross-aggregate consistency thường được xử lý bằng application workflow, domain events, messaging hoặc eventual consistency.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = new();

    public Guid Id { get; private set; }
    public OrderStatus Status { get; private set; }
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void AddLine(ProductId productId, int quantity, Money price)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException(
                "Only draft orders can be changed.");

        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(nameof(quantity));

        _lines.Add(new OrderLine(productId, quantity, price));
    }
}
```

Application service có thể load một aggregate, invoke behavior rồi `SaveChanges` trong một transaction.

## 5. Real production scenario

Một e-commerce design cho `Customer` aggregate chứa toàn bộ Orders, Addresses, PaymentMethods và Preferences. Mỗi update customer phải load hàng nghìn orders hoặc làm tracking graph phức tạp.

Kết quả: memory tăng, EF Core change tracking nặng, transaction scope không rõ và concurrent updates conflict nhiều.

Root cause: aggregate boundary được thiết kế theo object ownership thay vì consistency boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → command đơn giản load quá nhiều data, concurrency conflict tăng.

**Evidence** → aggregate graph rất lớn, transaction chạm nhiều tables/entities không cần thiết.

**Hypothesis** → aggregate boundary quá rộng.

**Diagnosis** → hỏi invariant nào thật sự phải atomically consistent.

**Fix** → tách aggregates, liên kết bằng IDs, xử lý cross-boundary workflow qua application/event mechanisms.

**Verification** → measure query count, transaction duration và concurrency conflict sau refactor.

## 7. Common mistakes

* Mỗi database table = aggregate.
* Mọi relation trong domain = navigation inside aggregate.
* Aggregate root chỉ là class có `Id`, không có invariant.
* Domain event dùng để né mọi transaction thay vì vì boundary thực sự khác.
* Thiết kế aggregate theo UI screen.

## 8. Alternatives

Anemic CRUD model hoàn toàn hợp lý cho domain đơn giản. Transaction Script có thể tốt hơn full DDD nếu business rules ít. DDD aggregate chỉ đáng dùng khi invariant/business behavior thật sự đủ phức tạp.

## 9. Trade-offs

### Advantages

* Boundary invariant rõ.
* Transaction scope có chủ đích.
* Giảm coupling giữa business concepts.

### Costs / Risks

* Yêu cầu domain analysis sâu.
* Cross-aggregate workflow phức tạp hơn.
* Eventual consistency có thể xuất hiện.
* Over-DDD làm code khó hiểu nếu domain chỉ CRUD.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu aggregate là consistency boundary, không chỉ object tree.

### Middle

Implement behavior qua Aggregate Root và không expose mutable internals tùy tiện.

### Senior

Phân tích invariant, transaction scope, concurrency và cross-aggregate workflow.

### Technical Lead / Architect

Quyết định domain nào đủ phức tạp để cần aggregates và boundary nào cân bằng correctness với operational simplicity.

## 11. Key takeaway

* Aggregate boundary nên theo invariant cần transaction consistency.
* Aggregate quá lớn làm concurrency và persistence nặng.
* Không phải hệ thống CRUD nào cũng cần DDD aggregates.

# 6. Azure Service Bus Dead-Letter Queue: poison message, retry policy và operational ownership

## 1. What is it?

Dead-Letter Queue (DLQ) là nơi giữ messages không thể được xử lý thành công hoặc bị hệ thống dead-letter theo policy.

Mental model:

```text
Queue/Subscription
      ↓ delivery
Consumer fails
      ↓ retry / redelivery
Max delivery reached
      ↓
Dead-Letter Queue
```

DLQ không phải “thùng rác tự động”. Nó là operational backlog cần owner, telemetry và remediation workflow.

## 2. Why does it exist?

Một poison message có thể fail deterministic mãi mãi: schema không hợp lệ, referenced entity không tồn tại, business invariant vi phạm hoặc code bug.

Nếu queue chỉ retry vô hạn, message đó gây retry storm, tốn compute và có thể chặn throughput/order processing.

## 3. How does it work?

Azure Service Bus dùng at-least-once delivery. Consumer có thể complete, abandon, dead-letter hoặc để lock expire.

Sau số delivery attempts nhất định, message có thể vào DLQ.

Application cũng có thể chủ động dead-letter:

```csharp
await receiver.DeadLetterMessageAsync(
    message,
    deadLetterReason: "InvalidSchema",
    deadLetterErrorDescription: "Missing customerId",
    cancellationToken: ct);
```

Transient error nên retry; deterministic invalid message thường nên dead-letter sớm.

## 4. Practical implementation

Consumer skeleton:

```csharp
try
{
    var command = Deserialize(message.Body);

    await handler.HandleAsync(command, ct);
    await receiver.CompleteMessageAsync(message, ct);
}
catch (SchemaValidationException ex)
{
    await receiver.DeadLetterMessageAsync(
        message,
        "InvalidSchema",
        ex.Message,
        ct);
}
catch (TransientDependencyException)
{
    await receiver.AbandonMessageAsync(message, cancellationToken: ct);
}
```

DLQ processor nên classify, alert, inspect và replay có kiểm soát; không auto-replay mọi message liên tục.

## 5. Real production scenario

Order consumer deploy schema mới nhưng producer cũ vẫn gửi payload thiếu field bắt buộc. Messages fail liên tục tới `MaxDeliveryCount` rồi vào DLQ.

Nếu team chỉ monitor active queue length, production nhìn “ổn” trong khi hàng nghìn orders đang nằm chết ở DLQ.

## 6. Failure scenario & troubleshooting

**Symptom** → active queue ổn nhưng business records không được tạo.

**Evidence** → DLQ count tăng, `DeadLetterReason` lặp lại.

**Hypothesis** → deterministic contract/data failure.

**Diagnosis** → inspect representative messages, producer version và consumer exception telemetry.

**Fix** → sửa contract/consumer, viết replay tool idempotent.

**Verification** → replay sample, xác nhận processing thành công và DLQ trend giảm.

## 7. Common mistakes

* Retry mọi exception giống nhau.
* Không alert DLQ growth.
* Xóa DLQ để “dọn queue” mà không root-cause.
* Replay hàng loạt message không idempotent.
* Put PII/secrets vào dead-letter description.
* Không có runbook/owner cho DLQ.

## 8. Alternatives

Poison-message quarantine riêng có thể dùng khi cần workflow remediation đặc thù. Event streaming platforms có failure handling khác; đôi khi lỗi nên được ghi vào database work queue thay vì broker DLQ nếu business cần manual review sâu.

## 9. Trade-offs

### Advantages

* Cô lập poison messages.
* Giữ queue chính tiếp tục chạy.
* Hỗ trợ forensic investigation/replay.

### Costs / Risks

* Tạo backlog cần operational ownership.
* Replay có thể gây duplicate side effects.
* Message retention/cost và PII governance cần chú ý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu DLQ là queue riêng cho messages không xử lý được.

### Middle

Phân biệt transient vs deterministic failure và settlement đúng.

### Senior

Thiết kế retry budget, idempotent replay, alerting và poison-message classification.

### Technical Lead / Architect

Đặt organization-wide message failure policy, ownership và recovery tooling.

## 11. Key takeaway

* DLQ là operational workflow, không phải nơi message “biến mất”.
* Retry chỉ dành cho failure có khả năng tự hồi phục.
* Replay bắt buộc cân nhắc idempotency và duplicate delivery.

# 7. Zero-downtime database migration với Expand–Migrate–Contract: deploy app và schema mà không cần coordinated outage

## 1. What is it?

Expand–Migrate–Contract là migration strategy chia breaking schema change thành nhiều deployment backward-compatible.

Mental model:

```text
1. Expand   → thêm schema mới, vẫn giữ schema cũ
2. Migrate  → backfill/dual-read/dual-write nếu cần
3. Contract → xóa schema cũ khi không còn consumer
```

Mục tiêu là application version cũ và mới có thể overlap trong rolling/blue-green deployment.

## 2. Why does it exist?

Production deployment hiếm khi atomically thay toàn bộ app instances cùng lúc. Trong vài phút hoặc vài giờ, old và new versions có thể chạy song song.

Nếu migration rename/drop column ngay lập tức, old version có thể crash dù migration “chạy thành công”.

## 3. How does it work?

Ví dụ muốn rename `FullName` thành `DisplayName`.

**Expand:**

```sql
ALTER TABLE Customers
ADD DisplayName nvarchar(200) NULL;
```

App mới đọc `DisplayName ?? FullName` và có thể ghi cả hai trong transition.

**Migrate:** backfill dữ liệu:

```sql
UPDATE Customers
SET DisplayName = FullName
WHERE DisplayName IS NULL;
```

Thực tế dataset lớn nên batch thay vì một transaction khổng lồ.

**Contract:** sau khi old app không còn và data verified, drop `FullName` ở release sau.

## 4. Practical implementation

EF Core migration không nên mặc định chứa destructive operation cùng release với code switch.

Backfill lớn:

```sql
WHILE 1 = 1
BEGIN
    UPDATE TOP (5000) Customers
    SET DisplayName = FullName
    WHERE DisplayName IS NULL;

    IF @@ROWCOUNT = 0 BREAK;
END
```

Monitor locks, transaction log và latency trong quá trình backfill.

## 5. Real production scenario

App Service chạy 8 instances rolling deployment. Migration rename column `Status` trước khi rollout app mới hoàn tất.

4 old instances vẫn query old column và bắt đầu trả 500. Deployment pipeline báo “migration success” nhưng production error rate tăng mạnh.

## 6. Failure scenario & troubleshooting

**Symptom** → 5xx chỉ xuất hiện trên một subset instances ngay sau migration.

**Evidence** → old version logs SQL “invalid column name”.

**Hypothesis** → schema change không backward-compatible với overlapping versions.

**Diagnosis** → correlate app version, migration version và query errors.

**Fix** → restore compatible schema hoặc rollback app; sau đó chuyển sang expand-contract sequence.

**Verification** → deployment test có old/new versions chạy đồng thời trên cùng schema.

## 7. Common mistakes

* Rename/drop column trong một release duy nhất.
* Backfill hàng trăm triệu rows trong một transaction.
* Assume deploy “nhanh nên overlap không đáng kể”.
* Không xem background jobs/reporting/ETL là schema consumers.
* Contract quá sớm khi chưa xác nhận old consumers biến mất.

## 8. Alternatives

Maintenance window phù hợp hệ thống nhỏ chấp nhận downtime. Blue-green vẫn cần schema compatibility nếu cả environments dùng chung DB. Database-per-version rất hiếm khi đáng complexity.

## 9. Trade-offs

### Advantages

* Hỗ trợ rolling/canary deployment an toàn.
* Giảm coordinated outage.
* Rollback application dễ hơn.

### Costs / Risks

* Migration kéo dài nhiều releases.
* Có temporary duplicate fields/logic.
* Cần telemetry để biết khi nào contract an toàn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu app và DB versions có thể overlap.

### Middle

Viết additive migrations và backfill an toàn.

### Senior

Thiết kế rollback, compatibility window và batch migration.

### Technical Lead / Architect

Đặt release policy cho schema evolution xuyên app, jobs, integrations và analytics consumers.

## 11. Key takeaway

* Production schema migration là compatibility problem, không chỉ SQL problem.
* Destructive change nên tách khỏi release introduce schema mới.
* Test old/new application versions cùng chạy trên transitional schema.

# 8. p50 / p95 / p99 latency: vì sao average latency che mất trải nghiệm tệ nhất trong production

## 1. What is it?

Percentile latency mô tả phân phối thay vì chỉ trung bình.

* p50: 50% requests nhanh hơn giá trị này.
* p95: 95% requests nhanh hơn.
* p99: 99% requests nhanh hơn.

Nếu p50 = 80 ms nhưng p99 = 4 giây, average 120 ms có thể khiến dashboard trông ổn dù 1% requests rất tệ.

## 2. Why does it exist?

Latency thường không phân phối đều. GC pause, lock contention, cache miss, cold path, dependency retry hoặc noisy neighbor tạo long tail.

Average làm loãng tail latency nên không đủ để đánh giá user experience hoặc SLO.

## 3. How does it work?

Giả sử 99 requests mất 100 ms và 1 request mất 10 giây.

Average khoảng 199 ms, nghe vẫn “dưới 200 ms”, nhưng user trúng request cuối chờ 10 giây.

Percentile giúp thấy tail trực tiếp.

Histogram metrics thường được dùng để tính percentiles gần đúng trong telemetry systems.

## 4. Practical implementation

Khi điều tra API latency:

```text
1. So p50/p95/p99 theo endpoint
2. Split theo dependency / region / app version
3. Inspect traces ở slow percentile
4. Identify recurring slow component
5. Reproduce under representative load
```

Application Insights/OpenTelemetry traces có thể cho thấy p99 requests đều gặp SQL query 3 giây trong khi p50 hit Redis.

## 5. Real production scenario

Product API average latency 180 ms nên team không ưu tiên. Tuy nhiên p99 là 5.2 giây ở enterprise tenants do một query plan khác.

Chỉ sau khi segment percentile theo tenant size, team mới thấy issue thực sự.

## 6. Failure scenario & troubleshooting

**Symptom** → users complain “thỉnh thoảng rất chậm” nhưng average dashboard ổn.

**Evidence** → p99 spike, p50 không đổi.

**Hypothesis** → tail-path issue như cache miss, lock hoặc dependency retry.

**Diagnosis** → sample traces từ high-latency bucket, compare fast vs slow requests.

**Fix** → sửa root cause, không chỉ tăng timeout.

**Verification** → p99 cải thiện mà error rate/throughput không xấu đi.

## 7. Common mistakes

* Chỉ monitor average.
* So percentile từ dataset quá nhỏ.
* Aggregate mọi endpoints thành một metric.
* Tối ưu p99 nhưng không xem error rate hoặc throughput.
* Dùng client timeout dài hơn để “cải thiện success rate”.

## 8. Alternatives

Max latency quá nhạy với outlier đơn lẻ. Average vẫn hữu ích cho capacity/trend nhưng không đủ cho UX. SLO thường nên dựa trên threshold success hoặc percentile tùy service semantics.

## 9. Trade-offs

### Advantages

* Thấy tail behavior.
* Phù hợp reliability/performance monitoring.
* Giúp ưu tiên incidents ảnh hưởng subset users.

### Costs / Risks

* Percentile aggregation across services/time windows dễ sai nếu telemetry system xử lý không đúng.
* High percentile cần đủ sample volume.
* Một con số p99 không chỉ ra root cause.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu average có thể che outliers.

### Middle

Đọc p50/p95/p99 và correlate với traces.

### Senior

Segment percentile theo endpoint, tenant, region, version và phân tích tail-path.

### Technical Lead / Architect

Đặt SLI/SLO phù hợp business experience thay vì chọn metric đẹp trên dashboard.

## 11. Key takeaway

* Average latency không đại diện cho tail experience.
* p95/p99 là signal; trace/evidence mới tìm ra root cause.
* Luôn segment latency theo dimensions có ý nghĩa.

# 9. Webhook integration: signature verification, idempotency và replay protection cho third-party callbacks

## 1. What is it?

Webhook là HTTP callback từ external provider tới application khi một event xảy ra.

Mental model:

```text
Provider
   ↓ signed HTTP POST
Webhook endpoint
   ↓ verify authenticity
Persist / enqueue
   ↓
Idempotent processing
```

Webhook không nên được tin chỉ vì request đến đúng URL bí mật.

## 2. Why does it exist?

Polling liên tục lãng phí request quota và tăng latency. Webhook cho phép provider push event ngay khi có thay đổi.

Nhưng internet delivery có retry, duplicate, out-of-order và malicious requests. Vì vậy webhook handler phải thiết kế như distributed messaging boundary.

## 3. How does it work?

Provider thường ký raw payload bằng shared secret hoặc asymmetric signature.

Ví dụ HMAC concept:

```csharp
var expected = HMACSHA256.HashData(
    secretBytes,
    rawBodyBytes);

var valid = CryptographicOperations.FixedTimeEquals(
    expected,
    providedSignatureBytes);
```

Phải verify **raw body bytes** theo provider spec; deserialize rồi serialize lại có thể thay whitespace/property order và làm signature sai.

Sau authentication, event ID dùng cho deduplication.

## 4. Practical implementation

Endpoint nên làm nhanh:

```text
receive
→ verify signature + timestamp
→ check event ID
→ persist/enqueue durably
→ return 2xx
```

Không nên giữ provider connection trong khi chạy workflow 30 giây.

Deduplication table:

```sql
CREATE TABLE ProcessedWebhook (
    Provider nvarchar(50) NOT NULL,
    EventId nvarchar(200) NOT NULL,
    ProcessedAt datetime2 NOT NULL,
    CONSTRAINT PK_ProcessedWebhook
        PRIMARY KEY (Provider, EventId)
);
```

Unique constraint biến duplicate delivery thành deterministic outcome.

## 5. Real production scenario

Payment provider gửi `payment.succeeded`. Endpoint xử lý trực tiếp rồi response chậm hơn provider timeout. Provider retry event; application tạo invoice/payment record lần hai.

Webhook delivery đúng theo contract at-least-once, nhưng consumer không idempotent.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate business side effects dù provider chỉ có một logical payment.

**Evidence** → cùng event ID xuất hiện nhiều lần trong access logs.

**Hypothesis** → provider retry + non-idempotent handler.

**Diagnosis** → inspect response latency/status và event identifiers.

**Fix** → durable enqueue nhanh + unique deduplication key + idempotent processor.

**Verification** → replay cùng webhook nhiều lần, side effect chỉ xảy ra một lần.

## 7. Common mistakes

* Chỉ whitelist IP và bỏ signature validation.
* So signature bằng normal string comparison.
* Không validate timestamp, cho phép replay cũ.
* Parse body trước khi verify signature nếu provider ký raw bytes.
* Trả 500 cho duplicate event hợp lệ.
* Làm long-running processing inline.

## 8. Alternatives

Polling phù hợp provider không hỗ trợ webhook hoặc cần reconciliation. Message broker tốt hơn nếu cả hai systems cùng kiểm soát integration. Nhiều hệ thống dùng cả webhook realtime + periodic reconciliation để phát hiện event bị mất.

## 9. Trade-offs

### Advantages

* Near-real-time.
* Giảm polling cost.
* Decouple provider event timing khỏi scheduled fetch.

### Costs / Risks

* Duplicate/out-of-order delivery.
* Security verification phức tạp.
* Public ingress endpoint cần protection/observability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu webhook là external HTTP callback có thể retry.

### Middle

Verify signature, return nhanh và deduplicate event IDs.

### Senior

Thiết kế replay protection, ordering semantics, reconciliation và idempotent side effects.

### Technical Lead / Architect

Định nghĩa trust boundary, operational ownership và recovery strategy cho external event integrations.

## 11. Key takeaway

* Webhook là untrusted distributed message delivered over HTTP.
* Signature verification và idempotency là baseline, không phải optional hardening.
* Realtime webhook thường vẫn cần reconciliation cho critical financial/business data.

# 10. Frontend JavaScript event loop: microtask, rendering và lý do UI vẫn lag dù code dùng `async/await`

## 1. What is it?

JavaScript trong browser thường chạy main-thread event loop cho script execution, event handlers và phần lớn UI coordination.

`async/await` không làm CPU-heavy JavaScript chạy trên thread khác.

Mental model:

```text
Task queue
   ↓
run JavaScript task
   ↓
flush microtasks (Promise continuations)
   ↓
render opportunity
   ↓
next task
```

Nếu một task hoặc chuỗi microtasks chạy quá lâu, browser không có cơ hội render/input response kịp thời.

## 2. Why does it exist?

Browser phải phối hợp network events, timers, promises, DOM updates và user input mà vẫn giữ execution model dễ reasoning.

Event loop giúp tránh nhiều shared-memory concurrency bugs, nhưng đổi lại main thread có thể bị block bởi CPU work.

## 3. How does it work?

Promise callbacks và continuation sau `await` thường được đưa vào microtask queue.

```javascript
console.log('A');

setTimeout(() => console.log('B'), 0);

Promise.resolve().then(() => console.log('C'));

console.log('D');
```

Thứ tự thường là:

```text
A
D
C
B
```

Vì microtask được flush trước task tiếp theo.

Nhưng nếu code tạo chain microtasks liên tục, rendering vẫn có thể bị starve.

## 4. Practical implementation

CPU-heavy transform không nên chỉ bọc trong `async`:

```typescript
async function processLargeDataset(items: Item[]) {
  return items
    .map(expensiveTransform)
    .filter(expensivePredicate);
}
```

Method vẫn chạy CPU work trên main thread.

Nếu workload thực sự nặng, cân nhắc Web Worker:

```typescript
const worker = new Worker(
  new URL('./processor.worker.ts', import.meta.url),
  { type: 'module' }
);

worker.postMessage(data);
worker.onmessage = event => {
  renderResult(event.data);
};
```

## 5. Real production scenario

Vue/React admin page tải 50.000 records rồi chạy sorting + grouping phức tạp client-side. API trả trong 300 ms nhưng UI freeze 2–3 giây.

Backend team nhìn network timing và kết luận API nhanh. Browser Performance profiler lại cho thấy long task trên main thread sau response.

## 6. Failure scenario & troubleshooting

**Symptom** → click/input lag, spinner không animate dù API response nhanh.

**Evidence** → Chrome DevTools Performance có long tasks >50 ms, scripting time cao.

**Hypothesis** → CPU-heavy JS hoặc excessive render/microtask chain.

**Diagnosis** → record performance trace, inspect call tree, React/Vue profiler và network waterfall.

**Fix** → giảm data xử lý, virtualize list, memoize hợp lý, chunk work hoặc chuyển CPU-heavy work sang Worker/server.

**Verification** → Interaction to Next Paint/long-task duration cải thiện mà output vẫn đúng.

## 7. Common mistakes

* Nghĩ `await` tự chuyển work sang background thread.
* Fetch ít thời gian nhưng render hàng nghìn DOM nodes.
* Tối ưu backend khi bottleneck ở browser main thread.
* Tạo Promise chain không bounded.
* Dùng Web Worker cho mọi việc dù serialization/copy overhead lớn hơn lợi ích.

## 8. Alternatives

Server-side aggregation giảm client CPU và payload. Virtualization giải quyết rendering lists lớn. Web Worker phù hợp CPU-bound browser work cần giữ UI responsive. `requestIdleCallback`/chunking phù hợp non-urgent work nhưng không bảo đảm hard realtime.

## 9. Trade-offs

### Advantages

* Hiểu event loop giúp debug UI responsiveness đúng layer.
* Web Workers cô lập CPU-heavy work khỏi main thread.

### Costs / Risks

* Worker communication/serialization có overhead.
* State synchronization phức tạp hơn.
* Moving work client-side có thể tăng device variability.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `async/await` không đồng nghĩa multithreading.

### Middle

Dùng DevTools để phân biệt network, scripting và rendering bottlenecks.

### Senior

Phân tích long tasks, microtasks, rendering cost và chọn server/worker/virtualization phù hợp.

### Technical Lead / Architect

Quyết định boundary xử lý dữ liệu giữa frontend và backend dựa trên payload, device capability, UX latency và maintainability.

## 11. Key takeaway

* `async/await` giúp cấu trúc asynchronous control flow, không tự giải phóng main thread khỏi CPU work.
* UI lag cần đo scripting/rendering chứ không chỉ API latency.
* Chọn server processing, virtualization hoặc Web Worker dựa trên bottleneck thực tế.
