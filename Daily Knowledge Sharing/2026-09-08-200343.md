# 1. C# nullable reference types: biến nullability thành compile-time contract thay vì runtime surprise

## 1. What is it?

Nullable reference types là hệ thống annotation + static flow analysis của C# giúp compiler phân biệt reference được kỳ vọng là non-null với reference có thể null.

Mental model:

```text
string   -> contract: caller nên nhận giá trị non-null
string?  -> contract: null là trạng thái hợp lệ và phải được xử lý
```

Nó không thay CLR representation của reference type. Một `string` vẫn có thể bị null ở runtime nếu dữ liệu đi vào từ boundary không an toàn, reflection, serialization hoặc code suppress warning. Giá trị chính của feature nằm ở **contract + compiler analysis**.

## 2. Why does it exist?

Trước nullable reference types, chữ ký:

```csharp
string GetName(int id)
```

không nói rõ method có thể trả null hay không. Caller phải đọc implementation, tài liệu hoặc chờ `NullReferenceException` xảy ra.

Trong codebase lớn, đây là ambiguity lan truyền qua hàng nghìn call sites. Nullable annotations đưa một phần domain contract vào type system để compiler cảnh báo sớm.

## 3. How does it work?

Compiler theo dõi null-state qua control flow:

```csharp
string? name = repository.FindName(id);

if (name is null)
{
    return NotFound();
}

Console.WriteLine(name.Length); // compiler biết name non-null tại đây
```

Các annotation trong `System.Diagnostics.CodeAnalysis` như `NotNullWhen`, `MemberNotNull`, `MaybeNull` giúp mô tả contract phức tạp hơn khi flow analysis mặc định chưa đủ.

Ví dụ:

```csharp
public static bool HasValue(
    [NotNullWhen(true)] string? value)
    => !string.IsNullOrWhiteSpace(value);
```

Sau `if (HasValue(input))`, compiler hiểu `input` là non-null.

## 4. Practical implementation

DTO nhận dữ liệu từ API nên thể hiện nullability theo contract thật:

```csharp
public sealed record CreateCustomerRequest(
    string Name,
    string Email,
    string? PhoneNumber);
```

Entity/domain object nên bảo vệ invariant thay vì dùng null-forgiving operator để “làm compiler im lặng”:

```csharp
public sealed class Customer
{
    public Guid Id { get; private set; }
    public string Name { get; private set; }
    public string Email { get; private set; }
    public string? PhoneNumber { get; private set; }

    private Customer() { }

    public Customer(string name, string email, string? phoneNumber)
    {
        Name = string.IsNullOrWhiteSpace(name)
            ? throw new ArgumentException("Name is required", nameof(name))
            : name;

        Email = string.IsNullOrWhiteSpace(email)
            ? throw new ArgumentException("Email is required", nameof(email))
            : email;

        PhoneNumber = phoneNumber;
    }
}
```

Nếu EF Core cần parameterless constructor, không nên phản xạ bằng hàng loạt `= null!;` nếu có thể thiết kế constructor/private setter rõ ràng hơn.

## 5. Real production scenario

Một CRM có `Customer.MiddleName` optional nhưng `Customer.Email` bắt buộc. Nếu cả hai đều dùng `string`, developer mới khó biết field nào được phép null. Nếu cả hai đều dùng `string?`, domain contract lại bị làm yếu.

Nullable annotations giúp API, application và persistence layer thống nhất expectation. Khi schema thay đổi một field từ optional thành required, compiler có thể làm lộ ra nhiều call site cần sửa trước khi deploy.

## 6. Failure scenario & troubleshooting

**Symptom** → build không warning nhưng Production vẫn có `NullReferenceException` từ dữ liệu deserialize.

**Evidence** → incoming JSON thiếu property non-nullable; serializer tạo object với field null hoặc binding validation không chặn đúng boundary.

**Hypothesis** → team nhầm nullable reference types là runtime validation.

**Diagnosis** → kiểm tra model binding/serializer behavior, validation pipeline và dữ liệu persistence cũ.

**Fix** → validation tại boundary, database constraint tương ứng, migration dữ liệu cũ và nullability annotation đúng.

**Verification** → integration tests với payload thiếu/null, schema constraint test và static analysis sạch warning thực sự.

## 7. Common mistakes

* Dùng `!` để suppress warning thay vì sửa contract.
* Đánh dấu gần như mọi property là `string?` để “đỡ warning”.
* Nghĩ non-nullable reference tự động chặn null ở runtime.
* Không đồng bộ nullability giữa API contract, domain model và database schema.
* Disable nullable toàn project vì migration ban đầu tạo nhiều warning.

## 8. Alternatives

Trước nullable reference types, có thể dựa vào runtime guards, annotations riêng, documentation hoặc Option/Maybe abstractions. Những cách này vẫn hữu ích cho domain phức tạp, nhưng compiler-native nullability có lợi thế vì tích hợp trực tiếp với C# tooling và flow analysis.

## 9. Trade-offs

### Advantages

* Contract rõ hơn ngay trong type signature.
* Bắt lỗi sớm lúc compile.
* Refactoring an toàn hơn trong codebase lớn.
* IDE support tốt.

### Costs / Risks

* Migration legacy code tốn công.
* Annotation sai tạo false confidence.
* External/serialization boundary vẫn cần runtime validation.
* Suppression quá mức làm mất giá trị của feature.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `T` và `T?` thể hiện expectation khác nhau.

### Middle

Biết xử lý compiler warnings đúng, tránh `!`, viết DTO và domain model phản ánh nullability thực tế.

### Senior

Hiểu interaction giữa nullable flow analysis, serialization, EF Core, legacy data và database constraints.

### Technical Lead / Architect

Đặt migration strategy cho legacy solution, coding convention về nullability và yêu cầu boundary validation để compile-time contract khớp runtime reality.

## 11. Key takeaway

* Nullable reference types là compile-time contract, không phải runtime validation.
* `null!` chỉ nên là ngoại lệ có chủ đích, không phải công cụ dọn warning.
* Nullability nên nhất quán từ API → domain → database.

# 2. ASP.NET Core request body limits và streaming upload: bảo vệ memory, disk và reverse proxy boundary

## 1. What is it?

Request body limit là giới hạn kích thước payload mà reverse proxy/server/application chấp nhận. Streaming upload là cách xử lý payload lớn theo dòng dữ liệu thay vì buffer toàn bộ request vào memory.

Mental model:

```text
Client
  ↓ upload
CDN / reverse proxy
  ↓ size/time limits
Kestrel / IIS
  ↓ request body
ASP.NET Core endpoint
  ↓ stream
Blob Storage / file processor
```

Upload lớn là cross-layer concern. Chỉ tăng limit trong ASP.NET Core thường không đủ.

## 2. Why does it exist?

Nếu endpoint cho phép request body vô hạn:

* attacker có thể giữ connection lâu hoặc gửi payload cực lớn;
* app có thể hết memory/disk nếu buffering;
* reverse proxy timeout trước khi app xử lý xong;
* concurrent uploads có thể chiếm toàn bộ network bandwidth.

Vì vậy upload path cần capacity policy rõ ràng, không chỉ “cho phép file 2 GB”.

## 3. How does it work?

ASP.NET Core có nhiều lớp limit tùy hosting. Kestrel có request body size setting; IIS có request filtering; proxy/CDN có limit riêng.

Nếu dùng `IFormFile`, framework có thể buffer multipart content theo threshold. Với file rất lớn, raw streaming thường predictable hơn.

Flow nên là:

```text
validate headers/metadata
→ enforce maximum allowed size
→ read stream chunk-by-chunk
→ optionally hash/scan
→ write destination stream
→ cancel on client disconnect
```

## 4. Practical implementation

Ví dụ endpoint stream trực tiếp sang Blob Storage:

```csharp
app.MapPost("/files/{name}", async (
    string name,
    HttpRequest request,
    BlobContainerClient container,
    CancellationToken cancellationToken) =>
{
    const long maxBytes = 500L * 1024 * 1024;

    if (request.ContentLength is > maxBytes)
    {
        return Results.StatusCode(StatusCodes.Status413PayloadTooLarge);
    }

    var blob = container.GetBlobClient(name);

    await blob.UploadAsync(
        request.Body,
        overwrite: false,
        cancellationToken);

    return Results.Created($"/files/{name}", null);
});
```

Trong production cần thêm authentication, content-type validation, malware scanning strategy, checksum và safe filename handling.

## 5. Real production scenario

Một enterprise CMS cho editor upload video 1 GB. Local development chạy Kestrel trực tiếp nên upload thành công. Production đi qua Application Gateway + IIS + ASP.NET Core và fail ở 30 MB.

Root cause không nằm ở controller mà ở lower limit tại hosting/proxy layer. Team cần document end-to-end upload budget và cấu hình nhất quán từng hop.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận 413 trước khi application log endpoint invocation.

**Evidence** → reverse proxy/IIS access log có 413 nhưng application trace không có request span.

**Hypothesis** → request bị reject trước application.

**Diagnosis** → kiểm tra CDN/proxy/IIS/Kestrel limits theo đúng request path.

**Fix** → align limits, nhưng chỉ tăng tới business requirement thực tế; dùng direct-to-Blob upload/SAS nếu application không cần nằm giữa data path.

**Verification** → test file ở boundary kích thước: dưới limit, đúng limit, vượt limit; quan sát memory và throughput khi concurrent uploads.

## 7. Common mistakes

* Tăng `MaxRequestBodySize` toàn hệ thống vô hạn.
* Dùng `ReadToEndAsync()` hoặc `byte[]` cho file lớn.
* Không propagate request cancellation.
* Tin `Content-Length` hoàn toàn mà không enforce actual bytes read.
* Cho app server proxy hàng GB dữ liệu dù Blob Storage có thể nhận trực tiếp.
* Không phân biệt upload limit với execution timeout.

## 8. Alternatives

* Direct-to-Blob upload bằng SAS: giảm load application, phù hợp file lớn.
* Chunked/multipart upload protocol: hỗ trợ resume và retry từng phần.
* Background ingestion từ object storage: phù hợp antivirus/transcoding workflow.

## 9. Trade-offs

### Advantages

* Streaming giữ memory ổn định.
* Explicit limits bảo vệ capacity.
* Direct storage upload giảm app bandwidth.

### Costs / Risks

* Cross-layer config phức tạp.
* Large upload giữ connection lâu.
* Security scanning và partial upload cleanup cần thiết kế riêng.
* SAS/direct upload làm authorization flow phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu upload file lớn không nên đọc hết vào memory.

### Middle

Biết stream request, kiểm tra size và handle cancellation.

### Senior

Debug 413/timeout qua proxy → server → app, thiết kế checksum, partial failure và abuse protection.

### Technical Lead / Architect

Quyết định upload path: app-proxied hay direct-to-object-storage, cùng với limit, security, observability và retention policy.

## 11. Key takeaway

* Upload limit là end-to-end concern qua nhiều hop.
* File lớn nên stream, không buffer toàn bộ.
* Direct-to-Blob thường tốt hơn để app server đứng giữa đường truyền lớn.

# 3. EF Core raw SQL + parameterization: khi ORM abstraction không đủ nhưng vẫn phải giữ query safety

## 1. What is it?

Raw SQL trong EF Core cho phép chạy SQL trực tiếp khi LINQ khó biểu diễn, query planner cần shape cụ thể, dùng database feature riêng hoặc cần migration từ legacy query.

Raw SQL không có nghĩa “bỏ ORM”. EF Core vẫn có thể materialize result, quản lý connection/transaction và parameter binding.

## 2. Why does it exist?

LINQ ưu tiên composability và abstraction, nhưng có những trường hợp:

* window function/query hint/vendor-specific feature;
* stored procedure legacy;
* hand-tuned reporting query;
* query expression quá phức tạp hoặc translation không phù hợp.

Senior engineering không nên ép mọi query vào LINQ chỉ để giữ “purity”. Nhưng raw SQL mở lại rủi ro injection và maintainability nếu dùng sai.

## 3. How does it work?

EF Core phân biệt API có parameterization tự động với API nhận raw string.

Ví dụ interpolated SQL an toàn:

```csharp
var minTotal = 1000m;

var orders = await db.Orders
    .FromSqlInterpolated($"""
        SELECT *
        FROM Orders
        WHERE Total >= {minTotal}
        """)
    .AsNoTracking()
    .ToListAsync(cancellationToken);
```

`minTotal` được biến thành database parameter, không concatenate vào SQL text.

Nguy hiểm:

```csharp
var sql = $"SELECT * FROM Orders WHERE Number = '{input}'";
await db.Orders.FromSqlRaw(sql).ToListAsync();
```

Ở đây untrusted input đã được ghép vào câu SQL trước khi EF thấy nó.

## 4. Practical implementation

Có thể dùng ​`ExecuteSqlInterpolatedAsync` cho command:

```csharp
var cutoff = DateTimeOffset.UtcNow.AddYears(-2);

var affected = await db.Database.ExecuteSqlInterpolatedAsync($"""
    UPDATE Orders
    SET Archived = 1
    WHERE CompletedAt < {cutoff}
      AND Archived = 0
    """, cancellationToken);
```

Nếu operation nằm trong transaction nghiệp vụ chung:

```csharp
await using var tx = await db.Database
    .BeginTransactionAsync(cancellationToken);

await db.Database.ExecuteSqlInterpolatedAsync(
    $"UPDATE Inventory SET Reserved = Reserved + {quantity} WHERE Id = {id}",
    cancellationToken);

await db.SaveChangesAsync(cancellationToken);
await tx.CommitAsync(cancellationToken);
```

## 5. Real production scenario

Một reporting endpoint cần `ROW_NUMBER()`, partition aggregation và SQL Server-specific optimization. LINQ translation tạo SQL khó đọc và plan không ổn định.

Team chuyển riêng query read-only đó sang raw SQL có integration tests, giữ command-side entities bằng EF Core bình thường. Đây là localized optimization thay vì đổi toàn data-access stack.

## 6. Failure scenario & troubleshooting

**Symptom** → security scan phát hiện SQL injection ở endpoint search.

**Evidence** → code dùng `FromSqlRaw($"...{userInput}...")`.

**Hypothesis** → developer tưởng interpolation trong C# sẽ được parameterized dù đã tạo raw string trước.

**Diagnosis** → inspect generated command text + parameters.

**Fix** → dùng `FromSqlInterpolated`, explicit `DbParameter`, hoặc parameterized stored procedure.

**Verification** → penetration test với quote/comment payload và log command metadata không chứa sensitive raw input.

## 7. Common mistakes

* Ghép user input trực tiếp vào raw SQL.
* Đưa table/column name từ user vào query mà không whitelist.
* Dùng raw SQL để né hiểu biết về LINQ translation thay vì đo bottleneck.
* Query entity bằng raw SQL nhưng quên tracking side effects.
* Duplicate business rules giữa SQL và domain/application layer.

## 8. Alternatives

* LINQ/EF Core: default tốt cho phần lớn CRUD/query.
* Dapper: nhẹ và explicit cho SQL-heavy read models.
* Stored procedures: hữu ích với database-owned logic/legacy governance nhưng coupling và deployment riêng.
* Database view: ổn cho reusable complex reads.

## 9. Trade-offs

### Advantages

* Kiểm soát SQL shape rõ ràng.
* Dùng được database-specific feature.
* Tối ưu localized hotspot.

### Costs / Risks

* Coupling vào database dialect.
* Dễ injection nếu parameterization sai.
* Refactoring schema ít được compiler hỗ trợ.
* Test burden cao hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu raw SQL không đồng nghĩa string concatenation.

### Middle

Biết dùng parameterized APIs và integration test query.

### Senior

Đánh giá execution plan, transaction participation, tracking và portability.

### Technical Lead / Architect

Đặt rule rõ ràng khi nào raw SQL/Dapper/stored procedure được phép và cách review security + maintainability.

## 11. Key takeaway

* Raw SQL là escape hatch hợp lệ, không phải anti-pattern tự động.
* Parameterization là bắt buộc với untrusted values.
* Chỉ tối ưu ra khỏi LINQ khi có evidence và boundary rõ ràng.

# 4. SQL Server deadlock graph: đọc wait cycle để sửa transaction design thay vì chỉ retry

## 1. What is it?

Deadlock xảy ra khi hai hoặc nhiều transaction giữ resource mà transaction kia cần, tạo vòng chờ không thể tự giải phóng.

Ví dụ:

```text
T1 giữ Row A → chờ Row B
T2 giữ Row B → chờ Row A
```

SQL Server phát hiện cycle và chọn một transaction làm deadlock victim để rollback.

## 2. Why does it exist?

Locking bảo vệ consistency. Khi concurrent transactions khóa resource theo thứ tự khác nhau, hệ thống có thể tạo circular wait.

Deadlock không nhất thiết nghĩa database “quá tải”. Nó thường là vấn đề **access order + transaction scope + indexing + isolation**.

## 3. How does it work?

Deadlock graph cho biết:

* process/session nào tham gia;
* resource/key/page/object nào bị lock;
* lock mode;
* statement đang chạy;
* victim nào bị chọn.

Mental model investigation:

```text
Deadlock error 1205
   ↓
collect deadlock graph
   ↓
identify cycle
   ↓
map SQL statements + lock order
   ↓
reduce scope / align order / improve access path
```

Extended Events `xml_deadlock_report` là nguồn bằng chứng quan trọng.

## 4. Practical implementation

Hai transaction khóa theo thứ tự ngược nhau:

```sql
-- Transaction A
BEGIN TRAN;
UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1;
UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 2;
COMMIT;
```

```sql
-- Transaction B
BEGIN TRAN;
UPDATE Accounts SET Balance = Balance - 50 WHERE Id = 2;
UPDATE Accounts SET Balance = Balance + 50 WHERE Id = 1;
COMMIT;
```

Một fix đơn giản là normalize lock order, ví dụ luôn update account có Id nhỏ trước.

Trong application, retry có thể là lớp resilience bổ sung:

```csharp
for (var attempt = 1; attempt <= 3; attempt++)
{
    try
    {
        await ExecuteTransferAsync(cancellationToken);
        break;
    }
    catch (SqlException ex) when (ex.Number == 1205 && attempt < 3)
    {
        await Task.Delay(TimeSpan.FromMilliseconds(100 * attempt), cancellationToken);
    }
}
```

Nhưng retry không thay cho root-cause fix.

## 5. Real production scenario

Approval workflow update `Request` rồi `Employee`; background sync update `Employee` rồi `Request`. Cả hai transaction ngắn nhưng access order trái nhau. Dưới traffic thấp gần như không thấy lỗi; cuối tháng concurrency tăng thì deadlock tăng mạnh.

Deadlock graph cho thấy chính xác hai statement và keys tham gia, giúp team sửa order thay vì tăng command timeout.

## 6. Failure scenario & troubleshooting

**Symptom** → API thỉnh thoảng 500 với SQL error 1205.

**Evidence** → deadlock XML cho thấy transaction A giữ key lock trên table X, chờ Y; transaction B ngược lại.

**Hypothesis** → inconsistent resource ordering.

**Diagnosis** → map statements về application use cases, xem transaction duration và execution plan.

**Fix** → thống nhất access order, rút ngắn transaction, thêm/chỉnh index nếu scan đang khóa quá nhiều rows, cân nhắc isolation strategy.

**Verification** → concurrency load test + monitor deadlock event rate sau release.

## 7. Common mistakes

* Chỉ retry vô hạn.
* Tăng timeout để “fix” deadlock.
* Dùng `NOLOCK` bừa bãi.
* Bỏ qua missing/bad index làm statement scan phạm vi lớn.
* Giữ transaction mở trong lúc gọi HTTP/external service.

## 8. Alternatives

* Optimistic concurrency phù hợp conflict logic khác, nhưng không loại mọi database lock.
* Snapshot-based isolation có thể giảm read/write blocking, nhưng có tempdb/versioning cost.
* Queue serialization theo business key đôi khi đơn giản hơn nếu domain chấp nhận throughput thấp hơn.

## 9. Trade-offs

### Advantages của disciplined transaction design

* Giảm deadlock tận gốc.
* Predictable concurrency behavior.
* Ít retry waste.

### Costs / Risks

* Có thể cần thay đổi application workflow.
* Snapshot isolation tăng version-store cost.
* Strict ordering đôi khi giảm parallelism.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deadlock là circular wait, khác timeout bình thường.

### Middle

Biết đọc error 1205 và thu deadlock graph.

### Senior

Phân tích lock order, transaction scope, execution plan và isolation level.

### Technical Lead / Architect

Thiết kế consistency boundary, concurrency strategy và retry policy để domain operations chịu được production concurrency.

## 11. Key takeaway

* Deadlock cần bằng chứng từ deadlock graph.
* Retry là safety net, không phải root-cause fix.
* Lock ordering và transaction scope thường quan trọng hơn tăng timeout.

# 5. Redis hot key: một key có thể phá scalability dù cluster còn rất nhiều capacity

## 1. What is it?

Hot key là cache key nhận tỷ lệ request cực lớn so với các key khác. Dù Redis cluster có nhiều node, một key cụ thể thường nằm ở một shard/primary cụ thể, khiến workload bị tập trung.

Mental model:

```text
1,000,000 keys spread across cluster
but
"homepage:global" = 40% all reads
                ↓
one shard becomes hotspot
```

## 2. Why does it exist?

Horizontal scaling chỉ hiệu quả khi traffic phân bố. Một global config, top products list, session index hoặc rate-limit counter có thể trở thành hotspot nếu mọi request cùng chạm một key.

Hot key là data-access problem, không đơn giản là “Redis chưa đủ lớn”.

## 3. How does it work?

Trong Redis Cluster, key được map vào hash slot. Tất cả request cho key đó đi tới owner của slot. Replicas có thể hỗ trợ read scaling trong một số architecture, nhưng consistency và client behavior phải phù hợp.

Symptoms thường là:

* một node CPU/network cao;
* cluster tổng thể còn dư;
* latency tập trung command/key pattern cụ thể;
* cache hit ratio vẫn rất tốt nhưng API p99 xấu.

## 4. Practical implementation

Một strategy cho data chịu stale nhẹ là local two-level cache:

```csharp
public async Task<HomeConfig> GetHomeConfigAsync(
    CancellationToken cancellationToken)
{
    if (_memoryCache.TryGetValue("home-config", out HomeConfig? cached))
    {
        return cached!;
    }

    var json = await _redis.StringGetAsync("home-config");
    var config = JsonSerializer.Deserialize<HomeConfig>(json!)!;

    _memoryCache.Set(
        "home-config",
        config,
        TimeSpan.FromSeconds(15));

    return config;
}
```

Local cache giảm số read tới Redis đổi lại freshness window.

## 5. Real production scenario

Một marketplace có key `navigation:global` được đọc mọi page request. Khi traffic 100k RPS, riêng key này chiếm phần lớn Redis traffic. Cluster có 6 shards nhưng một shard đạt network saturation.

Giải pháp không phải thêm 6 shards nữa nếu key vẫn chỉ nằm trên một shard. Team thêm local in-process cache 10–30 giây + event-driven invalidation cho config thay đổi hiếm.

## 6. Failure scenario & troubleshooting

**Symptom** → Redis overall memory bình thường nhưng một node latency và network cao.

**Evidence** → command stats/key sampling cho thấy một key chiếm disproportionate request volume.

**Hypothesis** → hot key.

**Diagnosis** → phân tích per-node throughput và top key pattern; kiểm tra global key có thực sự cần fresh mỗi request không.

**Fix** → local cache, replicate immutable data, partition logical key nếu semantics cho phép, giảm access frequency.

**Verification** → traffic phân bố đều hơn, Redis node p99 giảm, application correctness vẫn đúng với freshness policy.

## 7. Common mistakes

* Chỉ nhìn cluster average.
* Thêm shard mà không thay access pattern.
* Random-suffix key để “phân tán” nhưng làm consistency/invalidation khó kiểm soát.
* Cache mutable critical data local mà không xác định stale tolerance.
* Dùng Redis distributed lock trên một global lock key dưới contention cực cao.

## 8. Alternatives

* `IMemoryCache`: cực nhanh, per-instance, phù hợp dữ liệu có thể stale ngắn.
* CDN/edge cache: tốt cho public HTTP response.
* Database/read replica: nếu cache không cần thiết và source query đủ rẻ.
* Precomputed distributed data với shard-aware key design.

## 9. Trade-offs

### Advantages của mitigation

* Giảm pressure hotspot.
* Tăng khả năng scale-out thực tế.
* Tail latency tốt hơn.

### Costs / Risks

* Multi-level cache làm invalidation phức tạp.
* Stale data window tăng.
* Replication/sharding logical data tăng implementation burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu nhiều node không đảm bảo mọi key được load-balanced.

### Middle

Biết tìm hot key và đo per-node metrics.

### Senior

Đánh giá freshness, local cache, replication và consistency.

### Technical Lead / Architect

Quyết định liệu Redis có đúng boundary không, key ownership thuộc team nào và operational safeguards cho hotspot là gì.

## 11. Key takeaway

* Cluster scale không cứu được một key quá nóng nếu access pattern không đổi.
* Đo per-node và per-key pattern, không chỉ cluster average.
* Local cache có thể là fix tốt nếu stale window được chấp nhận rõ ràng.

# 6. Microservices boundary bằng business capability: tránh distributed monolith và shared-database coupling

## 1. What is it?

Microservice boundary nên đại diện một business capability hoặc bounded context có ownership dữ liệu và lifecycle đủ độc lập, thay vì tách service theo technical layer hoặc table.

Bad decomposition:

```text
CustomerService → AddressService → EmailService → ValidationService
```

cho một request đơn giản có thể biến local method calls thành distributed calls.

Better decomposition có thể là:

```text
Customer Management
Order Management
Billing
Search
Notifications
```

mỗi capability có responsibility và data ownership rõ hơn.

## 2. Why does it exist?

Microservices hứa hẹn independent deployment, scaling và team autonomy. Những lợi ích đó chỉ xuất hiện nếu boundary giảm coupling thực sự.

Nếu services vẫn:

* share database tables;
* deploy cùng lúc;
* gọi sync chain dày đặc;
* dùng chung domain model package;

thì hệ thống chỉ trở thành distributed monolith với network failure thêm vào.

## 3. How does it work?

Một healthy service boundary thường có:

* business responsibility rõ;
* own data schema/storage;
* explicit API/event contract;
* transaction boundary nội bộ;
* eventual consistency qua integration events khi cần;
* ownership vận hành rõ ràng.

```text
Orders DB           Billing DB
   ↑                    ↑
Orders Service → event → Billing Service
```

Không nên cho Billing đọc trực tiếp table Orders chỉ để “đỡ gọi API”.

## 4. Practical implementation

Ví dụ command tạo order commit local transaction và Outbox event:

```csharp
await using var tx = await db.Database
    .BeginTransactionAsync(cancellationToken);

var order = Order.Create(customerId, items);
db.Orders.Add(order);

db.OutboxMessages.Add(new OutboxMessage(
    Guid.NewGuid(),
    "OrderCreated",
    JsonSerializer.Serialize(new
    {
        order.Id,
        order.CustomerId,
        order.Total
    })));

await db.SaveChangesAsync(cancellationToken);
await tx.CommitAsync(cancellationToken);
```

Billing nhận event qua messaging thay vì join trực tiếp Orders DB.

## 5. Real production scenario

Một SaaS ban đầu tách `UserService`, `ProfileService`, `PermissionService`, `SettingsService`. Hầu hết request login/profile phải gọi 4 services sync. Deployment permission schema thay đổi buộc 3 services release cùng ngày.

Team nhận ra boundary quá nhỏ và regroup theo Identity/Account capability. Số network hops giảm, ownership rõ hơn và release độc lập thực tế hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → một endpoint lỗi hàng loạt khi một “tiny service” downstream chậm.

**Evidence** → distributed trace có chain 7 synchronous calls; nhiều services cùng cần deploy khi contract đổi.

**Hypothesis** → boundary kỹ thuật, coupling cao.

**Diagnosis** → map business use case → service calls → data ownership → deployment dependencies.

**Fix** → merge service khi boundary không tạo autonomy, hoặc redesign contract/event flow để giảm sync coupling.

**Verification** → fewer required cross-service calls, independent deployment test, failure isolation tốt hơn.

## 7. Common mistakes

* Một table = một microservice.
* Shared database giữa services nhưng vẫn gọi nó “microservices”.
* Shared domain entities package giữa nhiều services.
* Synchronous call chain dài cho một user request.
* Tách microservices trước khi domain boundaries đủ hiểu.

## 8. Alternatives

* Modular Monolith: thường tốt hơn khi team nhỏ, domain chưa ổn định hoặc operational maturity chưa đủ.
* Layered Monolith: đủ cho business đơn giản.
* Macroservices/coarse-grained services: compromise khi cần independent deployment một số capability lớn.

## 9. Trade-offs

### Advantages

* Independent scaling/deployment khi boundary đúng.
* Fault isolation tốt hơn.
* Ownership rõ.

### Costs / Risks

* Network/partial failure.
* Eventual consistency.
* Observability, deployment và data migration phức tạp.
* Duplicate infrastructure và operational burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu microservice không chỉ là project nhỏ chạy HTTP riêng.

### Middle

Biết explicit contracts, data ownership và integration patterns cơ bản.

### Senior

Nhìn ra distributed monolith qua sync chains, shared DB và lockstep deployment.

### Technical Lead / Architect

Quyết định boundary theo business capability, team topology, scale và operational cost; có quyền kết luận “chưa cần microservices”.

## 11. Key takeaway

* Boundary quan trọng hơn số lượng services.
* Shared DB và lockstep deployment là dấu hiệu autonomy giả.
* Modular Monolith thường là bước an toàn hơn trước microservices.

# 7. Azure Functions concurrency và scale-out: throughput không chỉ là “tăng instance”

## 1. What is it?

Azure Functions scale-out tăng số host instances; concurrency quyết định mỗi instance xử lý bao nhiêu invocation cùng lúc.

Mental model:

```text
Total throughput ≈ instances × useful concurrency per instance
```

Nhưng “useful concurrency” bị giới hạn bởi CPU, memory, connection pools, downstream services và trigger semantics.

## 2. Why does it exist?

Serverless giúp scale tự động, nhưng nếu mỗi instance xử lý quá nhiều message đồng thời:

* SQL connection pool có thể cạn;
* external API rate limit bị vượt;
* memory tăng mạnh;
* lock renewal/message visibility timeout gặp vấn đề.

Ngược lại concurrency quá thấp làm queue backlog tăng dù CPU còn rảnh.

## 3. How does it work?

Trigger có behavior khác nhau. Service Bus trigger có prefetch/concurrency controls; HTTP Functions scale theo request pressure; dynamic concurrency có thể điều chỉnh theo runtime signals tùy extension/runtime.

Flow:

```text
Queue backlog grows
   ↓
Function host pulls messages
   ↓
N concurrent handlers per instance
   ↓
scale controller may add instances
   ↓
downstream capacity becomes real bottleneck
```

## 4. Practical implementation

Handler phải idempotent và propagate cancellation:

```csharp
public sealed class ProcessInvoiceFunction
{
    private readonly InvoiceProcessor _processor;

    public ProcessInvoiceFunction(InvoiceProcessor processor)
        => _processor = processor;

    [Function("ProcessInvoice")]
    public async Task Run(
        [ServiceBusTrigger("invoice-jobs", Connection = "ServiceBus")]
        string message,
        CancellationToken cancellationToken)
    {
        var job = JsonSerializer.Deserialize<InvoiceJob>(message)
            ?? throw new InvalidOperationException("Invalid message");

        await _processor.ProcessIdempotentlyAsync(job, cancellationToken);
    }
}
```

Nếu downstream SQL chỉ chịu 100 concurrent writes, function concurrency strategy phải respect giới hạn đó thay vì scale vô hạn.

## 5. Real production scenario

Queue có 1 triệu jobs sau import lớn. Azure Functions scale từ 5 lên 50 instances. SQL Database CPU đạt 100%, latency tăng, messages timeout/retry và backlog còn tệ hơn.

Scale-out đã khuếch đại pressure lên bottleneck downstream. Team giảm per-instance concurrency, đặt backpressure qua queue và scale SQL hoặc batch workload hợp lý.

## 6. Failure scenario & troubleshooting

**Symptom** → số instances tăng nhưng queue age vẫn tăng, SQL timeout cũng tăng.

**Evidence** → Functions host CPU không max, nhưng dependency telemetry cho thấy SQL saturation và retry spike.

**Hypothesis** → downstream bottleneck, không phải compute shortage.

**Diagnosis** → correlate queue length/age, active instances, invocation concurrency, SQL DTU/vCore/connection pool và retry counts.

**Fix** → cap concurrency, optimize/batch DB operations, scale downstream nếu business value justify.

**Verification** → queue age giảm bền vững mà dependency error rate không tăng.

## 7. Common mistakes

* Tăng scale limit trước khi xem downstream capacity.
* Không idempotent nên retry tạo duplicate side effect.
* Prefetch quá lớn làm message lock hết hạn khi xử lý chậm.
* Dùng static in-memory state giả định một instance.
* Không monitor queue age, chỉ nhìn queue length.

## 8. Alternatives

* Worker Service/Container Apps: kiểm soát concurrency và lifecycle rõ hơn cho long-running processors.
* App Service background worker: đơn giản nếu đã có hosting fixed.
* Durable Functions: phù hợp orchestration/stateful workflow, nhưng operational model phức tạp hơn.

## 9. Trade-offs

### Advantages

* Elastic throughput.
* Operational overhead thấp hơn tự quản VM.
* Trigger integration tiện.

### Costs / Risks

* Scale-out behavior gián tiếp.
* Downstream dễ bị overwhelm.
* Cold start/cost/concurrency tuning cần hiểu workload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu instance count và concurrency là hai trục khác nhau.

### Middle

Biết viết idempotent handler và monitor queue backlog.

### Senior

Tuning concurrency theo dependency capacity, retries và lock semantics.

### Technical Lead / Architect

Thiết kế throughput budget end-to-end và quyết định Functions có đúng compute model cho workload hay không.

## 11. Key takeaway

* Auto-scale không thể vượt bottleneck downstream một cách thần kỳ.
* Concurrency phải được budget theo dependency capacity.
* Queue age + dependency telemetry quan trọng hơn chỉ nhìn instance count.

# 8. Feature flags trong CI/CD: decouple deployment khỏi release nhưng không được biến thành permanent branching system

## 1. What is it?

Feature flag là runtime decision cho phép code đã deploy nhưng feature chưa mở cho toàn bộ users.

Mental model:

```text
Deploy code ≠ Release feature
```

Deployment đưa artifact vào production. Release quyết định ai được sử dụng behavior mới.

## 2. Why does it exist?

Nếu deployment và release luôn là một hành động:

* feature lớn phải chờ hoàn thiện 100% mới merge;
* rollback code có thể cần deploy lại;
* Canary theo user/tenant khó làm;
* QA production validation bị hạn chế.

Feature flags giúp trunk-based development và progressive rollout dễ hơn.

## 3. How does it work?

Application evaluate flag theo context:

```text
request
  ↓
user / tenant / percentage / environment
  ↓
feature flag provider
  ↓
old path OR new path
```

Flag nên có owner, purpose, expiry date và observability.

## 4. Practical implementation

Ví dụ đơn giản với feature management:

```csharp
public sealed class CheckoutService
{
    private readonly IFeatureManager _features;

    public CheckoutService(IFeatureManager features)
        => _features = features;

    public async Task<CheckoutResult> CheckoutAsync(
        Cart cart,
        CancellationToken cancellationToken)
    {
        if (await _features.IsEnabledAsync("NewCheckout"))
        {
            return await CheckoutV2Async(cart, cancellationToken);
        }

        return await CheckoutV1Async(cart, cancellationToken);
    }
}
```

Critical rule: nếu old/new path mutate data khác schema, deployment và DB migration phải vẫn backward-compatible.

## 5. Real production scenario

Team release checkout mới cho 5% internal users, sau đó 10% customers, rồi 50%. Metrics cho thấy payment failure rate tăng ở v2 nên flag được tắt trong vài giây mà không rollback deployment.

Đây là lợi ích thật: reduce release blast radius.

## 6. Failure scenario & troubleshooting

**Symptom** → codebase có 120 flags, developer không biết combinations nào hợp lệ.

**Evidence** → nhiều nested `if feature A && !feature B`, flags tồn tại hơn một năm.

**Hypothesis** → flags không có lifecycle governance.

**Diagnosis** → inventory owner, creation date, rollout status, dead branches.

**Fix** → expiry policy, cleanup ticket ngay khi tạo flag, automated stale-flag report.

**Verification** → flag count/trend giảm, removed old code paths sau full rollout.

## 7. Common mistakes

* Dùng flag như permanent config/business rule.
* Không test cả enabled/disabled paths.
* Flag evaluation remote trên critical path không cache/fallback.
* New path phụ thuộc incompatible DB migration nên disable flag cũng không rollback được behavior.
* Không xóa old path sau rollout.

## 8. Alternatives

* Deployment slots/Blue-Green: switch artifact/environment level.
* Canary deployment: route percentage traffic theo infrastructure.
* Branching: source-code isolation nhưng không giúp runtime rollout.

Feature flags và Canary có thể kết hợp nhưng giải quyết boundary khác nhau.

## 9. Trade-offs

### Advantages

* Decouple deployment/release.
* Progressive rollout.
* Kill switch nhanh.

### Costs / Risks

* Tăng code paths và test matrix.
* Stale flags tạo technical debt.
* Flag platform trở thành production dependency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu feature deploy rồi chưa chắc đã release.

### Middle

Biết implement/test both paths.

### Senior

Thiết kế migration/backward compatibility để flag thật sự reversible.

### Technical Lead / Architect

Đặt governance về naming, ownership, expiry, rollout metrics và quyết định khi nào dùng feature flag versus deployment strategy.

## 11. Key takeaway

* Feature flags giảm blast radius nếu có cleanup lifecycle.
* Reversible runtime flag không cứu được irreversible database change.
* Flag phải có owner và expiry từ ngày tạo.

# 9. IIS Application Pool recycling: process lifecycle, cold start và hidden state trong legacy enterprise hosting

## 1. What is it?

IIS Application Pool là isolation boundary cho một hoặc nhiều web applications, chạy qua worker process `w3wp.exe`. Recycling là việc worker process được thay mới theo configuration hoặc health condition.

Mental model:

```text
IIS
 └─ App Pool
     └─ w3wp.exe
         └─ ASP.NET / ASP.NET Core hosted app
```

Recycling không phải “restart máy”; nó là process lifecycle event.

## 2. Why does it exist?

Long-running process có thể gặp:

* memory growth;
* config/deployment changes;
* health degradation;
* scheduled recycle policy.

IIS cho phép process được thay mới để isolation và recoverability tốt hơn. Nhưng application phải chịu được process restart.

## 3. How does it work?

Tùy hosting model, IIS/ASP.NET Core Module quản lý process. Khi recycle:

1. process mới có thể được khởi tạo;
2. process cũ ngừng nhận request mới;
3. in-flight requests có grace period;
4. old process kết thúc.

Nếu app giữ session/cache/job state chỉ trong memory, state đó biến mất cùng process.

## 4. Practical implementation

ASP.NET Core app nên coi local memory là ephemeral. Session quan trọng có thể dùng distributed store:

```csharp
builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = builder.Configuration
        .GetConnectionString("Redis");
});

builder.Services.AddSession(options =>
{
    options.IdleTimeout = TimeSpan.FromMinutes(20);
    options.Cookie.HttpOnly = true;
});
```

Background work quan trọng không nên phụ thuộc timer trong web process nếu cần exactly-once/reliable execution.

## 5. Real production scenario

Legacy HR portal chạy IIS, có in-memory dictionary chứa temporary approval state. Mỗi đêm App Pool recycle theo schedule. Sáng hôm sau users báo approval đang làm dở “biến mất”.

Vấn đề không phải IIS bug; architecture đã lưu durable business state vào process memory.

## 6. Failure scenario & troubleshooting

**Symptom** → app thỉnh thoảng cold start, users mất session hoặc background task dừng giữa chừng.

**Evidence** → IIS event log/App Pool recycle history trùng thời điểm; process ID thay đổi.

**Hypothesis** → hidden single-process assumption.

**Diagnosis** → inventory in-memory state, timers, static caches, startup duration và external session store.

**Fix** → externalize durable state, dùng resilient job processor, tối ưu startup/warm-up.

**Verification** → chủ động recycle App Pool trong staging và xác minh request/session/job behavior.

## 7. Common mistakes

* Disable recycling để che memory leak.
* Lưu durable workflow state trong static variables.
* Chạy critical scheduler trong web process mà không có distributed coordination.
* Không monitor process restarts.
* Confuse App Pool identity với application user identity.

## 8. Alternatives

* Azure App Service: abstraction managed hơn nhưng process restart vẫn tồn tại.
* Windows Service/Worker Service: phù hợp background processing riêng.
* Containers/Kubernetes: lifecycle khác nhưng pod restart vẫn yêu cầu statelessness tương tự.

## 9. Trade-offs

### Advantages

* Isolation process rõ.
* Recovery đơn giản.
* Phù hợp enterprise Windows hosting legacy.

### Costs / Risks

* Cold start.
* Local state mất khi recycle.
* Config/identity/certificate troubleshooting có thể phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu App Pool chứa worker process và process có thể restart.

### Middle

Biết đọc IIS logs/event logs, bindings và recycle settings.

### Senior

Nhận diện hidden process state, cold start và background job risk.

### Technical Lead / Architect

Thiết kế app restart-safe, xác định workload nào nên tách khỏi IIS web process và có migration plan sang hosting hiện đại khi hợp lý.

## 11. Key takeaway

* Process restart là expected operational event.
* Durable state không nên sống chỉ trong `w3wp.exe` memory.
* Đừng disable recycle để che architectural hoặc memory problem.

# 10. Technical SEO với canonical URL + redirects: correctness của routing ảnh hưởng trực tiếp crawlability và indexing

## 1. What is it?

Canonical URL cho search engine biết URL đại diện ưu tiên cho một nội dung khi nhiều URL có thể trả nội dung tương tự. Redirect là HTTP mechanism chuyển client/crawler từ URL cũ sang URL mới.

Ví dụ duplicate URLs:

```text
/products/widget
/products/widget?utm_source=email
/products/widget/
```

Canonical có thể chỉ về URL chính:

```html
<link rel="canonical" href="https://example.com/products/widget" />
```

## 2. Why does it exist?

Web application thực tế sinh nhiều URL do query params, route aliases, pagination, tracking và CMS history. Nếu routing không có canonical strategy:

* crawler thấy duplicate content;
* ranking signals bị phân tán;
* crawl budget lãng phí;
* old URLs sau migration có thể 404 hàng loạt.

Đây là engineering concern vì behavior nằm ở HTTP routing, status code, HTML rendering và deployment migration.

## 3. How does it work?

Redirect status có semantic khác nhau:

* `301`/`308`: permanent move signal;
* `302`/`307`: temporary behavior.

Canonical không bắt buộc crawler tuyệt đối, nhưng là strong hint. Redirect thường mạnh hơn khi URL cũ thực sự không còn nên tồn tại.

Flow migration:

```text
Old URL
  ↓ 301/308
New URL
  ↓ 200
<link rel="canonical" href="New URL">
```

## 4. Practical implementation

ASP.NET Core middleware cho legacy route:

```csharp
app.MapGet("/old-products/{slug}", (string slug) =>
{
    return Results.Redirect(
        $"/products/{Uri.EscapeDataString(slug)}",
        permanent: true,
        preserveMethod: true);
});
```

Trong Razor/layout, canonical nên được tạo từ normalized route chứ không copy toàn bộ tracking query string:

```html
<link rel="canonical" href="@Model.CanonicalUrl" />
```

## 5. Real production scenario

Một Optimizely CMS redesign đổi cấu trúc:

```text
/insights/article-title
→ /knowledge/article-title
```

Nếu chỉ publish pages mới và để URL cũ 404, external backlinks và indexed URLs mất giá trị. Migration map + permanent redirects giữ continuity tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → Google Search Console báo nhiều duplicate URLs hoặc “alternate page with proper canonical” bất thường; organic traffic giảm sau redesign.

**Evidence** → nhiều pages tự canonical về sai domain/path hoặc redirect chain dài.

**Hypothesis** → canonical generation/routing migration bug.

**Diagnosis** → crawl site, inspect status code chain, canonical tag, sitemap và internal links.

**Fix** → normalize URL strategy, one-hop permanent redirects, canonical đúng final URL, update sitemap/internal links.

**Verification** → crawl lại, giảm redirect chains/duplicate sets, theo dõi indexing sau re-crawl.

## 7. Common mistakes

* Canonical mọi page về homepage.
* Dùng canonical thay cho redirect khi URL cũ thực sự đã obsolete.
* Redirect chain A→B→C thay vì A→C.
* Giữ tracking params trong canonical URL.
* Dùng 200 page “not found” thay vì 404/410 phù hợp.
* Không cập nhật sitemap và internal links sau route migration.

## 8. Alternatives

* `robots.txt` dùng để điều khiển crawling phạm vi, không thay canonical.
* `noindex` yêu cầu page không được index, khác duplicate consolidation.
* 404/410 phù hợp khi content thật sự biến mất và không có replacement.

## 9. Trade-offs

### Advantages

* Consolidate duplicate signals.
* Migration URL an toàn hơn.
* Crawl behavior predictable hơn.

### Costs / Risks

* Sai canonical có thể de-index page đúng.
* Redirect rules legacy dễ tích tụ và conflict.
* Multi-domain/CDN setup làm URL generation phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code và canonical tag có semantic khác nhau.

### Middle

Biết implement redirects, canonical URL và kiểm tra bằng browser/devtools/crawler.

### Senior

Đánh giá route migration, query normalization, CDN/proxy host headers và soft-404 behavior.

### Technical Lead / Architect

Thiết kế URL governance lâu dài cho CMS/e-commerce, bao gồm redirect ownership, migration testing, sitemap và observability sau release.

## 11. Key takeaway

* URL correctness là application architecture concern, không chỉ marketing concern.
* Redirect dùng cho move thật; canonical dùng để chỉ preferred representation.
* Route migration phải được test như một production compatibility change.
