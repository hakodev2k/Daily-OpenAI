# 1. C# `IAsyncEnumerable<T>`: stream dữ liệu theo từng phần mà vẫn giữ cancellation và resource lifetime đúng

## 1. What is it?

`IAsyncEnumerable<T>` là abstraction cho một sequence mà từng phần tử được tạo hoặc đọc bất đồng bộ theo thời gian. Mental model quan trọng là **pull-based async streaming**: consumer yêu cầu phần tử tiếp theo, producer có thể chờ I/O rồi trả dữ liệu mà không cần materialize toàn bộ collection trước.

```text
Consumer asks next
      ↓
Producer awaits I/O
      ↓
Returns one item
      ↓
Consumer processes
      ↓
Repeat
```

Nó đặc biệt phù hợp với database cursor, paged API, event stream hoặc file parsing lớn.

## 2. Why does it exist?

Nếu method trả `Task<List<T>>`, producer phải hoàn tất toàn bộ công việc trước khi consumer nhận phần tử đầu tiên. Với dataset lớn, điều này tăng:

* memory footprint,
* time-to-first-result,
* latency khi downstream xử lý từng item,
* nguy cơ giữ database/network resource lâu mà không tạo giá trị sớm.

Streaming cho phép xử lý incremental, nhưng đổi lại resource lifetime và cancellation phải được quản lý cẩn thận.

## 3. How does it work?

Compiler biến async iterator thành state machine. Mỗi lần consumer gọi `MoveNextAsync`, iterator tiếp tục từ vị trí trước đó cho tới khi `yield return`, `yield break` hoặc exception.

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken cancellationToken = default)
{
    await foreach (var order in LoadOrdersAsync(cancellationToken))
    {
        yield return Map(order);
    }
}
```

`[EnumeratorCancellation]` giúp cancellation token truyền từ consumer vào iterator đúng semantics.

## 4. Practical implementation

Streaming từ EF Core:

```csharp
public async IAsyncEnumerable<OrderSummary> StreamRecentOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct)
{
    var query = _db.Orders
        .AsNoTracking()
        .Where(x => x.CreatedAt >= DateTimeOffset.UtcNow.AddDays(-1))
        .OrderBy(x => x.Id)
        .Select(x => new OrderSummary(x.Id, x.Total));

    await foreach (var row in query.AsAsyncEnumerable().WithCancellation(ct))
    {
        yield return row;
    }
}
```

Consumer:

```csharp
await foreach (var order in service.StreamRecentOrdersAsync(ct))
{
    await writer.WriteLineAsync(JsonSerializer.Serialize(order));
}
```

Không nên giữ `DbContext` sống lâu hơn stream một cách vô tình nếu consumer có thể xử lý rất chậm.

## 5. Real production scenario

Một export endpoint cần xuất 500.000 records. Phiên bản cũ dùng `ToListAsync()` rồi serialize toàn bộ, khiến process memory tăng mạnh và time-to-first-byte cao.

Chuyển sang async streaming giúp:

* nhận dữ liệu theo batch/cursor,
* serialize từng phần,
* giảm peak memory,
* phản hồi sớm hơn.

Nhưng nếu client tải rất chậm, database reader có thể bị giữ lâu. Lúc này có thể cần tách producer/consumer bằng bounded buffer hoặc xuất file background thay vì giữ HTTP request mở hàng chục phút.

## 6. Failure scenario & troubleshooting

**Symptom** → connection pool cạn khi nhiều client cùng stream report lớn.

**Evidence** → active DB connections tồn tại lâu tương ứng duration của HTTP response.

**Hypothesis** → async iterator giữ `DbDataReader` và connection suốt lifecycle stream.

**Diagnosis** → correlate request duration, DB connection duration và client transfer rate.

**Fix** → giới hạn report size, dùng batching có cursor, buffer tạm rồi đóng DB sớm hơn, hoặc chuyển export lớn sang background job.

**Verification** → load test với slow client và theo dõi pool usage.

## 7. Common mistakes

* Tưởng streaming tự động giảm mọi loại memory usage.
* Quên cancellation khi client disconnect.
* Giữ transaction hoặc DbContext quá lâu.
* Dùng `ToListAsync()` trước rồi mới trả `IAsyncEnumerable<T>` — lúc đó không còn streaming thật.
* Producer nhanh hơn consumer nhưng không có backpressure strategy.

## 8. Alternatives

* `Task<List<T>>`: đơn giản và phù hợp dataset nhỏ.
* Pagination/keyset pagination: tốt khi client muốn request từng page độc lập.
* `Channel<T>`: phù hợp producer/consumer concurrent và cần bounded buffering.
* Background export + Blob Storage: tốt cho dataset rất lớn.

## 9. Trade-offs

### Advantages

* Giảm peak memory.
* Time-to-first-item tốt hơn.
* Phù hợp pipeline dài và incremental processing.

### Costs / Risks

* Resource lifetime dài hơn nếu consumer chậm.
* Cancellation và disposal phức tạp hơn.
* Exception có thể xảy ra giữa stream sau khi response đã bắt đầu.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác biệt giữa “trả cả list sau khi hoàn tất” và “yield từng item theo thời gian”.

### Middle

Biết viết async iterator, propagate `CancellationToken` và consume bằng `await foreach`.

### Senior

Nhận diện connection/resource lifetime, slow consumer, partial failure và backpressure.

### Technical Lead / Architect

Quyết định khi nào streaming HTTP là đủ, khi nào cần paging, queue hoặc background export để cô lập long-running workload.

## 11. Key takeaway

* `IAsyncEnumerable<T>` tối ưu flow dữ liệu, không chỉ syntax.
* Streaming giảm materialization nhưng có thể kéo dài resource lifetime.
* Cancellation và backpressure phải được xem là một phần của thiết kế.

# 2. ASP.NET Core Endpoint Filters: đặt validation và cross-cutting logic đúng boundary thay vì nhét mọi thứ vào middleware hoặc endpoint

## 1. What is it?

Endpoint Filter trong ASP.NET Core là logic chạy quanh một Minimal API endpoint trước và/hoặc sau endpoint handler. Mental model của nó gần với một lightweight interception boundary ở **endpoint level**.

```text
Request
  ↓
Middleware
  ↓
Endpoint Filter
  ↓
Endpoint Handler
  ↓
Endpoint Filter post-processing
  ↓
Response
```

Nó phù hợp khi concern phụ thuộc endpoint arguments hoặc metadata, nhưng không nên áp dụng toàn application như middleware.

## 2. Why does it exist?

Middleware rất tốt cho concern cấp request pipeline như correlation, authentication hoặc global exception handling. Nhưng middleware không tự nhiên truy cập typed endpoint arguments.

Ngược lại, nếu validation/idempotency logic được viết trực tiếp trong từng endpoint, code bị lặp và business handler bị nhiễm transport concern.

Endpoint Filters lấp khoảng trống đó.

## 3. How does it work?

Filter nhận `EndpointFilterInvocationContext` và delegate tới filter tiếp theo hoặc endpoint cuối cùng.

```csharp
public async ValueTask<object?> InvokeAsync(
    EndpointFilterInvocationContext context,
    EndpointFilterDelegate next)
{
    // before
    var result = await next(context);
    // after
    return result;
}
```

Filter có thể short-circuit bằng cách trả response ngay mà không gọi `next`.

## 4. Practical implementation

Validation filter:

```csharp
public sealed class ValidateCreateOrderFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var request = context.GetArgument<CreateOrderRequest>(0);

        if (request.Items.Count == 0)
        {
            return Results.ValidationProblem(new Dictionary<string, string[]>
            {
                ["items"] = ["At least one item is required."]
            });
        }

        return await next(context);
    }
}
```

Registration:

```csharp
app.MapPost("/orders", CreateOrder)
   .AddEndpointFilter<ValidateCreateOrderFilter>();
```

Business invariant vẫn nên nằm ở domain/application layer; filter chỉ bảo vệ transport-level contract.

## 5. Real production scenario

Một API có 20 Minimal API endpoints cần verify `Idempotency-Key`. Nếu mỗi handler tự đọc header, validate format và lookup cache, behavior dễ drift.

Endpoint Filter có thể chuẩn hóa transport behavior trong một group:

```csharp
var payments = app.MapGroup("/payments")
    .AddEndpointFilter<IdempotencyFilter>();
```

## 6. Failure scenario & troubleshooting

**Symptom** → một số endpoint bypass validation dù cùng route group.

**Evidence** → filter chỉ gắn trên một endpoint cụ thể, không phải group.

**Hypothesis** → filter registration boundary sai.

**Diagnosis** → inspect endpoint metadata và registration hierarchy.

**Fix** → đăng ký filter tại `MapGroup` phù hợp hoặc dùng shared convention.

**Verification** → integration test mọi endpoint thuộc group.

## 7. Common mistakes

* Dùng Endpoint Filter cho concern cần áp dụng toàn pipeline như global exception handling.
* Đưa business rule sâu vào filter khiến logic không reusable ngoài HTTP.
* Filter phụ thuộc thứ tự nhưng không document order.
* Short-circuit nhưng không trả error contract nhất quán.
* Duplicate cùng validation ở filter và application layer mà không phân biệt trách nhiệm.

## 8. Alternatives

* Middleware: concern global/pipeline-level.
* MVC Action Filters: phù hợp MVC/controller stack.
* FluentValidation/application validation: cho object/domain validation rộng hơn.
* Explicit handler logic: tốt nếu concern chỉ tồn tại ở một endpoint.

## 9. Trade-offs

### Advantages

* Gần endpoint contract hơn middleware.
* Reuse cross-cutting logic theo route group.
* Giữ handler gọn hơn.

### Costs / Risks

* Dễ tạo nhiều interception layer khó trace.
* Order của filters có thể ảnh hưởng behavior.
* Có nguy cơ đẩy business logic sai boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu middleware và endpoint filter chạy ở hai scope khác nhau.

### Middle

Triển khai filter cho validation/idempotency transport concern.

### Senior

Phân biệt HTTP-level rule với business invariant và thiết kế ordering/test coverage.

### Technical Lead / Architect

Quy định concern nào thuộc middleware, endpoint filter, application pipeline hoặc domain để tránh architecture drift.

## 11. Key takeaway

* Endpoint Filter phù hợp concern gắn với endpoint arguments/metadata.
* Business invariant không nên bị khóa trong HTTP filter.
* Ít interception layer hơn thường dễ debug hơn.

# 3. EF Core Temporal Tables: truy vấn lịch sử dữ liệu mà không tự xây audit table thủ công cho mọi thay đổi

## 1. What is it?

Temporal Table là khả năng của SQL Server giữ lịch sử row tự động theo system time. EF Core hỗ trợ mapping và query temporal data.

Mental model:

```text
Current table
   │ UPDATE / DELETE
   ▼
Database preserves old row
   ▼
History table
```

Ứng dụng có thể hỏi: “record này trông như thế nào tại thời điểm X?”

## 2. Why does it exist?

Audit lịch sử thường được implement thủ công bằng trigger hoặc application code. Cách đó dễ bỏ sót update path, migration hoặc bulk operation.

Temporal Tables đưa historical versioning xuống database engine, giúp nhất quán hơn cho row history.

## 3. How does it work?

SQL Server thêm period columns như `ValidFrom` và `ValidTo`. Khi row update/delete, phiên bản cũ được chuyển vào history table.

EF Core mapping:

```csharp
modelBuilder.Entity<Employee>()
    .ToTable("Employees", b => b.IsTemporal());
```

Query thời điểm cụ thể:

```csharp
var snapshot = await db.Employees
    .TemporalAsOf(asOfUtc)
    .Where(x => x.Id == employeeId)
    .SingleAsync(ct);
```

## 4. Practical implementation

Một mapping rõ hơn:

```csharp
modelBuilder.Entity<Order>()
    .ToTable("Orders", tb => tb.IsTemporal(ttb =>
    {
        ttb.HasPeriodStart("ValidFrom");
        ttb.HasPeriodEnd("ValidTo");
        ttb.UseHistoryTable("OrderHistory");
    }));
```

Query full history:

```csharp
var history = await db.Orders
    .TemporalAll()
    .Where(x => x.Id == orderId)
    .OrderBy(x => EF.Property<DateTime>(x, "ValidFrom"))
    .AsNoTracking()
    .ToListAsync(ct);
```

## 5. Real production scenario

HR system cần support câu hỏi: “salary band của employee trước khi thay đổi tuần trước là gì?”

Nếu chỉ log text như “salary updated”, không đủ để reconstruct state. Temporal table lưu full row versions giúp investigation và support dễ hơn.

Nhưng temporal history không tự trả lời “ai thay đổi” hoặc “business reason là gì”; đó vẫn cần audit metadata ở application layer.

## 6. Failure scenario & troubleshooting

**Symptom** → history table tăng nhanh và backup/storage cost tăng mạnh.

**Evidence** → entity có high-frequency updates, mỗi update tạo historical row.

**Hypothesis** → retention không được quản lý.

**Diagnosis** → đo growth rate, row count, index size và query pattern.

**Fix** → thiết kế retention/archive policy, index phù hợp, không bật temporal cho mọi table theo mặc định.

**Verification** → theo dõi storage growth sau retention policy.

## 7. Common mistakes

* Nghĩ temporal table thay thế business audit log hoàn toàn.
* Không tính retention và storage growth.
* Bật temporal cho volatile table không có use case lịch sử.
* Query `TemporalAll()` rồi materialize lượng dữ liệu khổng lồ.
* Không dùng UTC/consistent time semantics khi phân tích historical state.

## 8. Alternatives

* Application audit table.
* Database trigger audit.
* Event Sourcing nếu lịch sử event chính là source of truth.
* CDC cho integration/change capture, không giống historical row querying.

## 9. Trade-offs

### Advantages

* Versioning tự động ở database boundary.
* Dễ truy vấn point-in-time state.
* Ít phụ thuộc mọi application write path phải nhớ audit.

### Costs / Risks

* Storage tăng theo write volume.
* Không chứa business intent mặc định.
* Schema/index/retention cần vận hành như production data thật.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu current row và historical versions là hai lớp dữ liệu khác nhau.

### Middle

Map temporal table và dùng `TemporalAsOf`, `TemporalAll` đúng cách.

### Senior

Thiết kế retention, indexing và phân biệt historical state với audit event.

### Technical Lead / Architect

Quyết định table nào cần temporal capability và chi phí lưu trữ dài hạn có hợp lý không.

## 11. Key takeaway

* Temporal Table giải quyết row history, không tự giải quyết business audit semantics.
* History growth phải được budget và quản lý.
* Chỉ bật khi historical reconstruction thực sự có giá trị.

# 4. PostgreSQL `jsonb` và GIN index: dùng document-like fields trong relational database mà không biến query thành full scan

## 1. What is it?

`jsonb` cho phép PostgreSQL lưu JSON ở dạng binary normalized để có thể query và index hiệu quả hơn raw JSON text.

Mental model đúng không phải “PostgreSQL trở thành MongoDB”, mà là:

> relational core + semi-structured extension cho phần dữ liệu có shape linh hoạt.

## 2. Why does it exist?

Một số domain có metadata thay đổi thường xuyên: product attributes, integration payloads, feature configuration. Tạo column cho mọi field có thể quá cứng, nhưng tách toàn bộ sang document database cũng có thể không đáng operational complexity.

`jsonb` tạo middle ground.

## 3. How does it work?

Query containment:

```sql
SELECT id, name
FROM products
WHERE attributes @> '{"color":"black"}';
```

Không có index, database có thể phải scan nhiều rows và inspect JSON.

GIN index:

```sql
CREATE INDEX ix_products_attributes_gin
ON products
USING GIN (attributes);
```

GIN index phù hợp containment/existence style queries nhưng có write/storage cost.

## 4. Practical implementation

Nếu workload chủ yếu query một property cụ thể, expression index có thể tốt hơn generic GIN:

```sql
CREATE INDEX ix_products_brand
ON products ((attributes->>'brand'));
```

Query:

```sql
SELECT id, name
FROM products
WHERE attributes->>'brand' = 'Acme';
```

Senior engineer phải chọn index theo access pattern thay vì “jsonb => GIN”.

## 5. Real production scenario

E-commerce catalog có 50 loại sản phẩm, mỗi loại có attributes khác nhau. Core fields như `sku`, `price`, `category_id` vẫn là relational columns; category-specific metadata nằm trong `jsonb`.

Search filters phổ biến như brand/color được index có chủ đích.

## 6. Failure scenario & troubleshooting

**Symptom** → query filter JSON tăng từ 30 ms lên 2 giây khi dataset lớn.

**Evidence** → `EXPLAIN ANALYZE` cho thấy sequential scan và high buffer reads.

**Hypothesis** → predicate không được index hỗ trợ hoặc index operator class không phù hợp.

**Diagnosis** → đọc execution plan, rows estimated/actual, buffers, index condition.

**Fix** → expression/GIN index đúng query shape; nếu field trở thành core business property, cân nhắc promote thành real column.

**Verification** → compare execution plan và I/O trước/sau.

## 7. Common mistakes

* Nhét toàn bộ entity vào một `jsonb` column rồi mất relational constraints.
* Tạo GIN index khổng lồ cho dữ liệu hiếm khi query.
* Không enforce schema ở application boundary.
* Query bằng expression khác với expression index.
* Dùng `jsonb` để né schema design thay vì vì access pattern phù hợp.

## 8. Alternatives

* Normal relational columns.
* EAV model — linh hoạt nhưng query/constraint phức tạp.
* MongoDB/document DB nếu toàn domain thiên về document access.
* Separate attribute tables cho controlled extensibility.

## 9. Trade-offs

### Advantages

* Schema linh hoạt cho phần dữ liệu biến động.
* Vẫn giữ transaction/join với relational data.
* Có indexing mạnh khi query pattern rõ.

### Costs / Risks

* Constraint/type safety yếu hơn real columns.
* GIN index có write/storage overhead.
* Query/ORM mapping phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `jsonb` là một data type trong PostgreSQL, không phải database khác.

### Middle

Viết containment/expression queries và tạo index cơ bản.

### Senior

Đọc `EXPLAIN ANALYZE`, chọn index/operator phù hợp và nhận diện khi field nên được promote thành column.

### Technical Lead / Architect

Quyết định boundary giữa structured schema và semi-structured metadata dựa trên invariants, query patterns và operational cost.

## 11. Key takeaway

* `jsonb` hữu ích khi chỉ một phần model cần linh hoạt.
* Index phải theo query shape thực tế.
* Field càng quan trọng cho invariant/query, càng có lý do trở thành first-class column.

# 5. Elasticsearch refresh interval và near-real-time consistency: document đã index chưa chắc lập tức search thấy

## 1. What is it?

Elasticsearch là near-real-time search engine. Sau khi index document, write có thể acknowledged trước khi document trở nên visible cho search.

Refresh tạo searchable segment mới từ recent in-memory/index buffers.

Mental model:

```text
Index request acknowledged
        ↓
Document durable/accepted
        ↓
Refresh happens
        ↓
Document becomes searchable
```

## 2. Why does it exist?

Nếu mỗi write buộc tạo searchable segment ngay lập tức, indexing throughput sẽ giảm mạnh. Elasticsearch batch work để cân bằng write throughput và search freshness.

Đây là trade-off có chủ đích giữa latency của indexing và freshness của search.

## 3. How does it work?

Index có `refresh_interval`. Refresh định kỳ làm dữ liệu mới visible cho search.

Application có thể dùng `refresh=wait_for` trong một số operation cần read-after-write search semantics, nhưng lạm dụng sẽ làm giảm throughput.

## 4. Practical implementation

Nếu workflow admin tạo product rồi ngay lập tức redirect sang trang search, có thể:

* đọc authoritative record từ primary DB,
* chấp nhận search lag ngắn,
* hoặc dùng `refresh=wait_for` cho flow hiếm nhưng cần UX cụ thể.

Không nên gọi explicit refresh sau mỗi write trong bulk indexing.

Bulk ingestion thường có thể tăng refresh interval tạm thời để tăng throughput, sau đó restore.

## 5. Real production scenario

CMS publish article, database commit thành công nhưng user tìm kiếm trong vài trăm milliseconds đầu chưa thấy bài.

Nếu product expectation không hiểu NRT semantics, team có thể coi đây là data loss dù indexing pipeline hoàn toàn bình thường.

## 6. Failure scenario & troubleshooting

**Symptom** → entity tồn tại trong DB nhưng search không trả về sau nhiều phút.

**Evidence** → lag vượt xa expected refresh interval.

**Hypothesis** → vấn đề không còn là refresh bình thường mà là indexing pipeline failure/backlog.

**Diagnosis** → kiểm tra indexing errors, queue lag, rejected writes, shard health và document version.

**Fix** → xử lý pipeline failure; refresh không sửa được event chưa bao giờ index thành công.

**Verification** → measure DB-change-to-search-visible latency end-to-end.

## 7. Common mistakes

* Gọi `_refresh` sau mỗi write.
* Giả định acknowledged write đồng nghĩa search-visible ngay.
* Dùng Elasticsearch làm transactional source of truth.
* Không monitor indexing lag.
* Không phân biệt refresh delay với failed synchronization.

## 8. Alternatives

* Primary DB query cho read-after-write critical flow.
* `refresh=wait_for` cho operation chọn lọc.
* Database full-text search nếu search requirements đơn giản.
* Eventual consistency với UX rõ ràng nếu freshness không cần tức thì.

## 9. Trade-offs

### Advantages

* Batching refresh giúp indexing throughput tốt hơn.
* NRT model phù hợp đa số search workloads.

### Costs / Risks

* User có thể thấy stale search results ngắn hạn.
* Stronger freshness yêu cầu thêm cost.
* Debugging cần phân biệt refresh, queue lag và indexing failure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu “indexed” và “search-visible” không luôn cùng thời điểm.

### Middle

Biết refresh interval và `refresh=wait_for` dùng khi nào.

### Senior

Theo dõi indexing lag, shard health và throughput/freshness trade-off.

### Technical Lead / Architect

Định nghĩa consistency expectation giữa primary DB và search subsystem theo UX/business requirement.

## 11. Key takeaway

* Elasticsearch là near-real-time, không phải read-after-write transactional store.
* Explicit refresh là công cụ đắt và không nên dùng mặc định.
* Phải monitor end-to-end indexing lag, không chỉ cluster health.

# 6. Bulkhead Pattern và bounded concurrency: cô lập dependency chậm để một lỗi cục bộ không chiếm hết tài nguyên toàn service

## 1. What is it?

Bulkhead Pattern lấy ý tưởng từ khoang kín trên tàu: failure ở một khu vực không được phép làm ngập toàn bộ hệ thống.

Trong service, bulkhead thường là giới hạn concurrency/resource pool riêng cho một dependency hoặc workload.

```text
API
 ├─ Payment dependency: max 20 concurrent
 ├─ Search dependency: max 50 concurrent
 └─ Reporting work: max 5 concurrent
```

## 2. Why does it exist?

Một dependency chậm có thể làm request chờ lâu. Nếu không giới hạn, hàng nghìn requests cùng chờ sẽ chiếm:

* sockets,
* memory,
* request slots,
* downstream connections,
* thread/continuation scheduling capacity.

Lỗi cục bộ có thể trở thành service-wide resource exhaustion.

## 3. How does it work?

Bulkhead đặt capacity limit. Khi capacity đầy, request mới:

* chờ trong bounded queue,
* fail fast,
* fallback,
* hoặc bị reject tùy policy.

Điểm quan trọng là queue cũng phải bounded. “Chỉ chờ thêm” có thể biến memory thành queue vô hạn.

## 4. Practical implementation

Ví dụ đơn giản:

```csharp
public sealed class PaymentGate
{
    private readonly SemaphoreSlim _gate = new(20, 20);

    public async Task<T> ExecuteAsync<T>(
        Func<CancellationToken, Task<T>> action,
        CancellationToken ct)
    {
        if (!await _gate.WaitAsync(TimeSpan.FromMilliseconds(100), ct))
            throw new InvalidOperationException("Payment capacity exhausted.");

        try
        {
            return await action(ct);
        }
        finally
        {
            _gate.Release();
        }
    }
}
```

Production implementation có thể dùng resilience library/pipeline nhưng mental model không đổi: capacity phải hữu hạn.

## 5. Real production scenario

Review provider bên thứ ba tăng latency từ 200 ms lên 10 giây. Product page cần reviews nhưng cũng cần CMS, pricing và inventory.

Nếu mọi request đồng thời giữ open call tới review provider, toàn web app có thể nghẽn. Bulkhead + timeout + fallback “reviews unavailable” giữ core product page hoạt động.

## 6. Failure scenario & troubleshooting

**Symptom** → bulkhead rejection tăng dù dependency latency bình thường.

**Evidence** → concurrency limit quá thấp so với normal throughput.

**Hypothesis** → policy đang trở thành bottleneck nhân tạo.

**Diagnosis** → đo arrival rate, service time, queue wait và saturation.

**Fix** → size capacity theo measured workload và downstream limits, không copy magic number.

**Verification** → load test normal + degraded dependency scenarios.

## 7. Common mistakes

* Dùng một semaphore global cho mọi dependency.
* Queue vô hạn phía trước bulkhead.
* Không có metrics cho saturation/rejection.
* Tăng limit chỉ để “hết lỗi” mà bỏ qua downstream capacity.
* Dùng retry bên trong saturated bulkhead gây thêm load.

## 8. Alternatives

* Timeout: giới hạn thời gian nhưng không giới hạn concurrency.
* Circuit Breaker: ngừng gọi dependency khi failure rate cao.
* Rate limiting: giới hạn arrival rate.
* Queue-based async processing: tách request path hoàn toàn.

Các pattern thường kết hợp, không thay thế tuyệt đối nhau.

## 9. Trade-offs

### Advantages

* Ngăn failure lan toàn service.
* Capacity predictable hơn.
* Tạo điểm đo saturation rõ ràng.

### Costs / Risks

* Request có thể bị reject sớm.
* Sizing sai tạo under-utilization hoặc overload.
* Nhiều pools/policies tăng operational complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu concurrency không thể tăng vô hạn chỉ vì code dùng async.

### Middle

Implement bounded concurrency và cancellation đúng cách.

### Senior

Đọc saturation metrics và kết hợp timeout/retry/circuit breaker hợp lý.

### Technical Lead / Architect

Phân bổ capacity theo dependency criticality và thiết kế degraded mode khi dependency không ổn định.

## 11. Key takeaway

* Async không loại bỏ resource limits.
* Bulkhead bảo vệ toàn service bằng cách giới hạn blast radius.
* Capacity và queue phải được đo, không chọn bằng cảm tính.

# 7. Azure Container Apps revisions và traffic splitting: deploy phiên bản mới có kiểm soát mà không buộc toàn bộ traffic chuyển ngay lập tức

## 1. What is it?

Azure Container Apps revision là immutable snapshot của application configuration/container version. Nhiều revisions có thể tồn tại cùng lúc và nhận phần trăm traffic khác nhau.

Mental model:

```text
Ingress
  ├─ 95% → revision A
  └─  5% → revision B
```

Điều này cho phép canary/blue-green-like rollout ở application platform level.

## 2. Why does it exist?

Deploy “replace toàn bộ instance ngay lập tức” khiến một regression ảnh hưởng 100% users ngay khi release.

Revision-based traffic splitting cho phép exposure nhỏ, quan sát metrics rồi tăng dần.

## 3. How does it work?

Mỗi revision có container image, environment/config snapshot và replica lifecycle riêng. Ingress router phân traffic theo configured weights.

Scaling vẫn xảy ra theo rules của từng active revision. Vì vậy chạy song song hai revisions có thể tăng resource/cost tạm thời.

## 4. Practical implementation

Release flow:

```text
commit
→ build
→ test
→ immutable image
→ deploy new revision
→ route 5%
→ health validation
→ monitor error/latency/business metrics
→ 25%
→ 100%
→ deactivate old revision later
```

Application phải backward-compatible với database/schema và shared messages trong khoảng thời gian hai versions chạy song song.

## 5. Real production scenario

API checkout deploy v2 với new discount calculation. Team route 5% traffic sang revision mới.

Technical metrics không xấu nhưng business metric “checkout completion” giảm. Vì rollout nhỏ, team rollback traffic về v1 nhanh mà không redeploy image.

## 6. Failure scenario & troubleshooting

**Symptom** → v2 hoạt động riêng lẻ nhưng lỗi khi chạy song song với v1.

**Evidence** → cả hai revisions consume cùng Service Bus schema nhưng v2 phát message mới không backward-compatible.

**Hypothesis** → deployment compatibility boundary bị bỏ qua.

**Diagnosis** → inspect shared database/message contracts giữa versions.

**Fix** → Expand–Migrate–Contract, versioned messages hoặc tolerant readers.

**Verification** → staging chạy mixed-version test trước production traffic split.

## 7. Common mistakes

* Canary chỉ nhìn HTTP 5xx, không nhìn business metric.
* Database migration phá old revision ngay lập tức.
* Dùng mutable image tag như `latest` khiến revision identity mơ hồ.
* Giữ old revisions active vô thời hạn tăng cost.
* Không xác định rollback condition trước release.

## 8. Alternatives

* Azure App Service deployment slots.
* Kubernetes rolling/canary rollout.
* Front Door weighted routing giữa backends.
* Simple rolling deploy nếu risk thấp và rollback nhanh.

## 9. Trade-offs

### Advantages

* Rollout từng phần.
* Rollback traffic nhanh.
* Revision identity rõ ràng với immutable image.

### Costs / Risks

* Mixed-version compatibility phức tạp.
* Tạm thời chạy duplicate capacity.
* Observability phải tách metrics theo revision.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu revision là một version deployment có thể chạy song song.

### Middle

Triển khai traffic split và kiểm tra health/metrics.

### Senior

Thiết kế schema/message compatibility và rollback criteria.

### Technical Lead / Architect

Chọn rollout strategy theo blast radius, state compatibility và operational maturity của team.

## 11. Key takeaway

* Traffic splitting chỉ an toàn khi versions có thể coexist.
* Canary cần business telemetry, không chỉ technical telemetry.
* Immutable artifact + rollback condition là nền tảng release đáng tin cậy.

# 8. Điều tra memory leak trong .NET bằng `dotnet-counters`, `dotnet-gcdump` và `dotnet-dump`: từ symptom đến retained-object evidence

## 1. What is it?

Memory leak trong managed .NET thường không có nghĩa GC “quên free memory”. Thường object vẫn còn reachable từ một GC root, nên runtime buộc phải giữ nó.

Mental model:

```text
GC Root
  ↓
Long-lived reference
  ↓
Object graph
  ↓
Memory remains retained
```

Mục tiêu investigation là tìm **ai đang giữ object sống**.

## 2. Why does it exist?

Production memory growth có nhiều nguyên nhân:

* legitimate cache growth,
* LOH pressure,
* fragmentation,
* request spike,
* native memory,
* object retention bug.

Chỉ nhìn Task Manager không đủ để kết luận leak.

## 3. How does it work?

Điều tra nên đi theo tầng:

1. `dotnet-counters`: xác nhận GC heap, allocation rate, Gen 2 collections.
2. `dotnet-gcdump`: snapshot managed heap nhẹ hơn full dump.
3. `dotnet-dump`: deep inspection khi cần roots/stacks.

Ví dụ:

```bash
dotnet-counters monitor --process-id 1234 System.Runtime
```

Sau đó:

```bash
dotnet-gcdump collect --process-id 1234
```

Nếu cần full dump:

```bash
dotnet-dump collect --process-id 1234
```

## 4. Practical implementation

Trong `dotnet-dump analyze`:

```text
> dumpheap -stat
> dumpheap -type MyLargeObject
> gcroot <address>
```

Workflow:

* tìm type tăng nhiều,
* chọn instance,
* dùng `gcroot` tìm reference path,
* quay lại source code để xác định owner/lifetime sai.

Ví dụ thường gặp: singleton cache giữ dictionary không giới hạn hoặc event subscription giữ object đáng lẽ đã chết.

## 5. Real production scenario

API memory tăng đều 100 MB mỗi giờ. GC chạy bình thường nhưng heap sau Gen 2 không giảm.

`dumpheap -stat` cho thấy hàng triệu `SessionSnapshot`. `gcroot` cho thấy chúng nằm trong static dictionary không có eviction.

Root cause không phải GC tuning; đó là ownership bug.

## 6. Failure scenario & troubleshooting

**Symptom** → process memory cao nhưng managed heap không cao tương ứng.

**Evidence** → `dotnet-counters` cho thấy GC heap ổn định.

**Hypothesis** → native memory, memory-mapped file, unmanaged library hoặc container reporting nuance.

**Diagnosis** → không tiếp tục ép giả thuyết managed leak; dùng OS/container/native diagnostics phù hợp.

**Fix** → dựa trên evidence của đúng memory domain.

**Verification** → memory curve ổn định sau representative load/soak test.

## 7. Common mistakes

* Restart process rồi coi incident đã được giải quyết.
* Tăng container memory limit mà không tìm retention path.
* Kết luận leak chỉ vì RSS không giảm ngay sau GC.
* Chụp dump ở production mà không cân nhắc size/pause/storage/security.
* Tối ưu allocation khi vấn đề là retained references.

## 8. Alternatives

* Visual Studio profiler cho local reproduction.
* PerfView cho allocation/GC deep analysis.
* `dotnet-trace` cho runtime events.
* Application Insights/custom metrics để correlate workload với growth.

## 9. Trade-offs

### Advantages

* Evidence-based thay vì đoán.
* Có thể đi từ type statistics tới exact GC root.
* Phân biệt allocation pressure và retention leak.

### Costs / Risks

* Dump có thể lớn và chứa sensitive data.
* Collection/analysis cần operational permission.
* Full dump có overhead và cần storage bảo mật.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu GC chỉ thu object không còn reachable.

### Middle

Dùng counters/gcdump để nhận diện growth pattern.

### Senior

Phân tích `gcroot`, retained graph và correlate với code ownership.

### Technical Lead / Architect

Thiết kế diagnostic runbook, safe dump handling và memory SLO/capacity cho production.

## 11. Key takeaway

* Managed leak thường là reference lifetime bug, không phải GC bug.
* Bắt đầu bằng metrics, sau đó mới snapshot/dump.
* Tìm GC root quan trọng hơn chỉ biết type nào chiếm nhiều memory.

# 9. CSRF, SameSite cookies và anti-forgery boundary: cookie authentication cần chống request giả mạo ngay cả khi attacker không đọc được cookie

## 1. What is it?

CSRF xảy ra khi browser tự động gửi credentials, thường là authentication cookie, tới target site trong một request được attacker kích hoạt từ origin khác.

Attacker không cần đọc cookie; browser tự attach cookie nếu policy cho phép.

```text
Victim logged in to bank.example
        ↓
Visits attacker.example
        ↓
Attacker causes POST to bank.example
        ↓
Browser may attach auth cookie
```

## 2. Why does it exist?

Cookie authentication dựa vào browser-managed credential. Điều này tiện nhưng tạo ambient authority: request có thể mang credential mà JavaScript của attacker không hề biết giá trị cookie.

Vì vậy server cần biết request có thực sự xuất phát từ trusted interaction hay không.

## 3. How does it work?

Defense thường kết hợp:

* `SameSite` cookie policy,
* anti-forgery token,
* correct HTTP method semantics,
* origin/referrer validation trong một số architecture.

Anti-forgery token là value attacker không thể tự tạo từ cross-site context, được gửi ngoài ambient cookie channel.

## 4. Practical implementation

Với browser app dùng cookie auth, state-changing requests nên có anti-forgery protection.

ASP.NET Core services:

```csharp
builder.Services.AddAntiforgery(options =>
{
    options.HeaderName = "X-CSRF-TOKEN";
});
```

Frontend lấy token theo flow được server thiết kế và gửi trong custom header cho `POST`, `PUT`, `PATCH`, `DELETE`.

`SameSite=Lax/Strict` giảm attack surface nhưng không nên được xem là thay thế universal cho anti-forgery trong mọi flow.

## 5. Real production scenario

Admin portal dùng cookie authentication. Endpoint `/users/{id}/disable` nhận POST nhưng không có anti-forgery validation.

Attacker gửi link tới admin chứa auto-submit form. Nếu browser gửi auth cookie, action có thể chạy dưới quyền admin dù attacker không biết cookie.

## 6. Failure scenario & troubleshooting

**Symptom** → anti-forgery hoạt động local nhưng fail sau khi deploy SPA/frontend trên domain khác.

**Evidence** → browser không gửi cookie/token như mong đợi do `SameSite`, `Secure`, domain hoặc CORS/credentials settings.

**Hypothesis** → deployment topology khác local origin assumptions.

**Diagnosis** → dùng browser DevTools kiểm tra cookie attributes, request origin, credentials mode và response headers.

**Fix** → thiết kế cookie/CSRF policy theo topology thực tế; nếu cần cross-site cookie, dùng `SameSite=None; Secure` và giữ anti-forgery boundary mạnh.

**Verification** → security test cả same-site và malicious cross-site request.

## 7. Common mistakes

* Nghĩ CORS tự động chống CSRF.
* Nghĩ HttpOnly cookie chống CSRF — HttpOnly chủ yếu giảm JavaScript access/XSS credential theft.
* Dùng GET cho state-changing action.
* Tắt anti-forgery vì “SPA gọi API”.
* Dùng `SameSite=None` mà không hiểu cross-site consequence.

## 8. Alternatives

* Bearer token trong `Authorization` header do application chủ động gửi thường không có ambient-cookie CSRF problem tương tự, nhưng có threat model khác như token theft/XSS.
* SameSite-only defense có thể đủ trong một số constrained flows nhưng cần threat review.
* BFF pattern có thể giữ browser token exposure thấp hơn nhưng vẫn phải xử lý cookie CSRF.

## 9. Trade-offs

### Advantages

* Anti-forgery bảo vệ state-changing cookie-authenticated requests.
* SameSite giảm nhiều cross-site credential scenarios.

### Costs / Risks

* Cross-domain SPA/SSO flows phức tạp hơn.
* Configuration sai dễ gây production-only auth bugs.
* Không thay thế XSS protection hay authorization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu browser tự gửi cookie và attacker không cần đọc cookie để gây CSRF.

### Middle

Cấu hình anti-forgery token và SameSite đúng cho app thông thường.

### Senior

Phân tích CORS, cookie attributes, XSS, CSRF và cross-origin topology như các boundary khác nhau.

### Technical Lead / Architect

Chọn browser authentication architecture theo threat model và deployment domains, không theo snippet mặc định.

## 11. Key takeaway

* HttpOnly không chống CSRF.
* CORS và CSRF giải quyết hai vấn đề khác nhau.
* Cookie auth cho state-changing requests cần explicit anti-forgery reasoning.

# 10. Architecture Decision Record (ADR): lưu lại “vì sao chọn” để kiến trúc không biến thành tribal knowledge

## 1. What is it?

ADR là một tài liệu ngắn ghi lại một quyết định kiến trúc đáng kể, context, alternatives và trade-offs tại thời điểm quyết định.

Một ADR tốt trả lời:

* Vấn đề gì cần quyết định?
* Constraints nào đang tồn tại?
* Chọn phương án nào?
* Vì sao?
* Hệ quả là gì?
* Khi nào nên revisit?

## 2. Why does it exist?

Sau vài tháng, code chỉ cho biết “hệ thống đang dùng Kafka/Service Bus/Redis”, nhưng không cho biết vì sao team chọn nó.

Khi người ra quyết định rời team, thiếu context dẫn tới:

* lặp lại tranh luận cũ,
* xóa workaround thực ra bảo vệ constraint quan trọng,
* cargo-cult architecture,
* khó biết điều kiện nào đã thay đổi đủ để revisiting decision.

## 3. How does it work?

ADR thường immutable theo lịch sử. Nếu decision đổi, tạo ADR mới supersede ADR cũ thay vì sửa lịch sử như chưa từng có quyết định trước đó.

```text
ADR-001: Use Modular Monolith
Status: Accepted

Context
Decision
Alternatives
Consequences
Revisit triggers
```

Decision record nên gần code repository để review cùng source changes.

## 4. Practical implementation

Ví dụ ngắn:

```markdown
# ADR-012: Use Azure Service Bus for order integration

## Status
Accepted

## Context
Order processing must tolerate temporary downstream outages and duplicate delivery.

## Decision
Use Azure Service Bus queue with idempotent consumers.

## Alternatives
- Direct synchronous HTTP
- Kafka

## Consequences
- Eventual consistency
- DLQ and retry runbook required
- Message schema becomes a versioned contract

## Revisit when
Throughput/order requirements exceed current queue model.
```

ADR không nên trở thành 20-page design document.

## 5. Real production scenario

Team mới muốn bỏ Redis vì “cache gây complexity”. ADR cũ cho thấy Redis được thêm sau incident khi external pricing API có rate limit nghiêm ngặt và p99 3 giây.

Context đó không có nghĩa Redis phải tồn tại mãi, nhưng giúp team đánh giá liệu constraint đã thay đổi hay chưa thay vì xóa theo sở thích cá nhân.

## 6. Failure scenario & troubleshooting

**Symptom** → repository có hàng trăm ADR nhưng không ai tin hoặc đọc.

**Evidence** → docs stale, không link tới code/decision, status không cập nhật.

**Hypothesis** → ADR bị biến thành compliance paperwork.

**Diagnosis** → kiểm tra liệu significant decisions gần đây có ADR và ADR cũ có supersede state rõ ràng không.

**Fix** → chỉ record decisions có architectural consequence; giữ template ngắn; review ADR trong PR nơi decision được thực hiện.

**Verification** → trong architecture review, team có thể truy ngược quyết định và trade-offs mà không cần hỏi người cũ.

## 7. Common mistakes

* Ghi mọi implementation detail thành ADR.
* Chỉ ghi “Decision” mà không ghi alternatives/trade-offs.
* Sửa ADR cũ để xóa lịch sử.
* Dùng ADR thay cho code documentation/runbook/API contract.
* Decision đã implement nhưng ADR chỉ được viết nhiều tháng sau theo trí nhớ.

## 8. Alternatives

* Design document: tốt cho thiết kế lớn, chi tiết hơn ADR.
* README/wiki: phù hợp overview nhưng dễ mất historical decision chain.
* PR description: có context tốt nhưng khó discover lâu dài.
* RFC process: phù hợp decision lớn cần broader review.

## 9. Trade-offs

### Advantages

* Giữ reasoning cùng lịch sử hệ thống.
* Giúp onboarding và architecture review.
* Làm rõ trade-off thay vì chỉ ghi technology choice.

### Costs / Risks

* Docs có thể stale nếu process quá nặng.
* Quá nhiều ADR tạo noise.
* Không thay thế communication trực tiếp khi decision đang được hình thành.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu architecture decision có context, không chỉ có “best practice”.

### Middle

Đọc ADR để hiểu constraints trước khi refactor component.

### Senior

Viết ADR ngắn, rõ alternatives và consequences cho decision đáng kể.

### Technical Lead / Architect

Dùng ADR để duy trì decision history, revisit assumptions và quản lý evolutionary architecture mà không biến documentation thành bureaucracy.

## 11. Key takeaway

* ADR lưu reasoning, không chỉ lưu kết quả.
* Decision tốt luôn gắn với context và trade-offs cụ thể.
* ADR nên ngắn, gần code và có cơ chế supersede rõ ràng.
