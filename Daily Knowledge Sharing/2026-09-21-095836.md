# 1. .NET Large Object Heap: allocation lớn, Gen 2 pressure và pooling có kỷ luật

## 1. What is it?

Large Object Heap (LOH) là vùng managed heap mà .NET thường dùng cho object lớn, điển hình allocation từ khoảng 85 KB trở lên. Mental model quan trọng: object lớn không chỉ “tốn nhiều RAM”; lifetime và collection behavior của nó có thể kéo chi phí GC lên đáng kể vì LOH được thu gom cùng Gen 2.

## 2. Why does it exist?

Di chuyển object rất lớn trong quá trình compact GC có chi phí cao. CLR tách chúng khỏi Small Object Heap để quản lý khác đi. Điều này tối ưu một số workload nhưng tạo áp lực nếu application liên tục tạo rồi bỏ các buffer lớn.

## 3. How does it work?

```text
Request
  -> allocate byte[200 KB]
  -> LOH
  -> object becomes unreachable
  -> memory chỉ được reclaim khi Gen 2/LOH collection xảy ra
  -> allocation churn cao => GC pause + memory pressure
```

LOH có thể bị fragmentation; runtime có cơ chế compaction nhưng compaction không phải lý do để bỏ qua allocation design.

## 4. Practical implementation

Khi xử lý buffer tạm thời có kích thước lớn và tần suất cao, `ArrayPool<T>` có thể giảm allocation churn:

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(128 * 1024);
try
{
    var read = await stream.ReadAsync(buffer.AsMemory(), cancellationToken);
    await ProcessAsync(buffer.AsMemory(0, read), cancellationToken);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}
```

Không giữ pooled buffer sau khi `Return`.

## 5. Real production scenario

API import file tạo nhiều `byte[]` 1–5 MB cho mỗi chunk. Khi concurrency tăng, memory tăng theo saw-tooth, Gen 2 GC xuất hiện thường xuyên và p99 latency nhảy cao dù CPU business logic thấp.

## 6. Failure scenario & troubleshooting

**Symptom** → memory cao và latency spike. **Evidence** → allocation profile cho thấy large arrays; GC metrics có Gen 2 collections tăng. **Hypothesis** → LOH churn. **Diagnosis** → dùng `dotnet-counters`, `dotnet-gcdump` hoặc profiler để xác định allocation source. **Fix** → streaming, bounded buffer, pooling khi hợp lý. **Verification** → load test lại, so allocation rate, Gen 2 frequency và p99.

## 7. Common mistakes

Đọc toàn bộ file vào memory; pooling mọi allocation nhỏ; quên trả buffer; giữ reference tới pooled array; tăng memory limit thay vì tìm allocation source; ép GC thủ công trong request path.

## 8. Alternatives

Streaming thường đơn giản và an toàn hơn pooling nếu dữ liệu có thể xử lý tuần tự. `Memory<T>`/`Span<T>` giúp thao tác slice mà không copy nhưng không tự loại bỏ allocation nguồn.

## 9. Trade-offs

### Advantages

Pooling có thể giảm allocation và GC pressure đáng kể trên hot path.

### Costs / Risks

Ownership phức tạp, buffer có thể chứa dữ liệu cũ, pool giữ memory và misuse có thể gây data corruption.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu allocation lớn ảnh hưởng GC khác allocation nhỏ.

### Middle

Biết dùng streaming và `ArrayPool<T>` đúng ownership.

### Senior

Đo allocation rate, Gen 2, LOH size và p99 trước khi tối ưu.

### Technical Lead / Architect

Thiết kế memory budget và concurrency limit cho workload file/serialization thay vì chỉ tăng instance size.

## 11. Key takeaway

- LOH problem thường là allocation pattern, không chỉ dung lượng RAM.
- Streaming nên được cân nhắc trước pooling.
- Tối ưu memory phải dựa trên telemetry và load test.

# 2. ASP.NET Core `ProblemDetails`: error contract ổn định thay vì exception leakage

## 1. What is it?

`ProblemDetails` là representation chuẩn hóa cho HTTP API errors theo RFC 7807/RFC 9457 family: `type`, `title`, `status`, `detail`, `instance` và extensions. Nó tạo contract giữa backend và clients thay vì trả exception text tùy ý.

## 2. Why does it exist?

Nếu mỗi endpoint trả error shape khác nhau, frontend phải viết parsing riêng. Nếu trả stack trace trực tiếp, API vừa leak implementation vừa tạo contract không ổn định. Error contract cần tách public failure semantics khỏi internal exception details.

## 3. How does it work?

```text
Exception / validation failure
        -> exception handler
        -> classify failure
        -> HTTP status + ProblemDetails
        -> client

Internal stack trace -> logs/traces, không phải public response
```

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();
app.UseExceptionHandler();

app.MapGet("/orders/{id:int}", async (int id, AppDbContext db, CancellationToken ct) =>
{
    var order = await db.Orders.FindAsync([id], ct);
    return order is null
        ? Results.Problem(statusCode: 404, title: "Order not found")
        : Results.Ok(order);
});
```

Domain/application exceptions nên được map có chủ đích, không map tất cả thành `500` hoặc `400`.

## 5. Real production scenario

Vue frontend gọi Orders API. Validation errors, not-found và conflict đều có shape thống nhất; UI có thể dựa trên status/error code ổn định, trong khi correlation ID giúp support tìm trace nội bộ.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận `500` nhưng không thể correlate với logs. **Evidence** → response không có request/trace identifier. **Diagnosis** → error contract thiếu operational correlation. **Fix** → thêm safe trace identifier extension và structured logging. **Verification** → từ một failed response có thể tìm đúng trace mà không expose stack trace.

## 7. Common mistakes

Trả `ex.Message`; dùng `200 OK` kèm `{ success:false }`; biến mọi domain error thành `400`; thay đổi error code tùy message; trả PII trong `detail`; để middleware order khiến exception không được handler bắt.

## 8. Alternatives

Custom error envelope có thể dùng nhưng phải duy trì contract riêng. gRPC có status/trailers khác HTTP REST. `ProblemDetails` hợp với HTTP APIs vì ecosystem hiểu semantics chuẩn.

## 9. Trade-offs

### Advantages

Consistent contract, client đơn giản hơn, giảm leakage và cải thiện observability.

### Costs / Risks

Vẫn cần taxonomy lỗi, mapping policy và backward compatibility; chuẩn format không tự thiết kế business error semantics.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt public error với exception nội bộ.

### Middle

Map validation/not-found/conflict đúng status và test contract.

### Senior

Thiết kế error taxonomy, correlation và safe diagnostics.

### Technical Lead / Architect

Chuẩn hóa error contract xuyên services và quyết định versioning/backward compatibility cho machine-readable error codes.

## 11. Key takeaway

- Error response là API contract.
- Stack trace thuộc telemetry, không thuộc client response.
- HTTP status và machine-readable error semantics phải ổn định.

# 3. SQL Server Snapshot Isolation: giảm blocking nhưng phải trả giá bằng versioning

## 1. What is it?

Snapshot-based isolation cho phép reader thấy version dữ liệu phù hợp thay vì chờ writer lock trong nhiều trường hợp. SQL Server hỗ trợ `READ_COMMITTED_SNAPSHOT` và `SNAPSHOT` với semantics khác nhau. Mental model: giảm read/write blocking bằng row versions, không phải “không còn concurrency problem”.

## 2. Why does it exist?

Pessimistic locking có thể khiến read traffic bị block bởi transactions ghi dài. Với workload nhiều reads, versioning giúp throughput và latency tốt hơn, nhưng cần storage và vẫn phải xử lý write conflicts/consistency semantics.

## 3. How does it work?

```text
T1 updates Row A
  -> current version changes
  -> old version retained in version store
T2 reads
  -> obtains version appropriate to its isolation semantics
  -> không nhất thiết chờ T1 commit
```

## 4. Practical implementation

```sql
ALTER DATABASE Sales
SET READ_COMMITTED_SNAPSHOT ON;
```

Trước khi bật production phải đánh giá transaction behavior, tempdb/version store pressure và application assumptions. Đây là database-level behavior change, không phải tuning switch vô hại.

## 5. Real production scenario

Reporting/API reads thường bị block bởi batch update inventory. RCSI giảm reader blocking, nhưng batch transaction vẫn cần ngắn và indexes vẫn cần tốt; snapshot không chữa query scan hàng triệu rows.

## 6. Failure scenario & troubleshooting

**Symptom** → blocking giảm nhưng tempdb/version store tăng mạnh. **Evidence** → long-running transactions giữ old versions lâu. **Hypothesis** → transaction lifetime kéo dài version retention. **Diagnosis** → correlate active transactions với version store usage. **Fix** → rút ngắn transaction, batch work hợp lý. **Verification** → đo blocking, tempdb và transaction duration dưới load.

## 7. Common mistakes

Cho rằng snapshot loại bỏ lost update; bật mà không test semantics; giữ transaction qua user/network interaction; dùng isolation level để che query/index problem; bỏ qua write/write conflicts.

## 8. Alternatives

Default locking phù hợp nhiều systems và đơn giản hơn về storage. Optimistic concurrency token ở application giải quyết lost update theo business semantics. `SERIALIZABLE` mạnh hơn nhưng tăng blocking/range locks.

## 9. Trade-offs

### Advantages

Giảm reader/writer blocking, cải thiện concurrency cho read-heavy workload.

### Costs / Risks

Version store overhead, semantics khác, long transaction cost và vẫn cần concurrency strategy cho writes.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu isolation quyết định dữ liệu transaction được phép thấy.

### Middle

Biết phân biệt blocking với deadlock và kiểm tra transaction boundary.

### Senior

Đánh giá version store, write conflicts và workload trước/sau thay đổi.

### Technical Lead / Architect

Chọn consistency/concurrency model dựa trên business invariants, không chỉ benchmark throughput.

## 11. Key takeaway

- Snapshot đổi blocking thành versioning cost.
- Isolation level không thay thế application concurrency design.
- Long-running transactions vẫn là kẻ thù.

# 4. Elasticsearch alias + reindex: thay index schema mà không buộc Search API downtime

## 1. What is it?

Index alias là tên logic trỏ tới physical index. Khi mapping/analyzer cần thay đổi không thể sửa in-place an toàn, có thể tạo index mới, reindex dữ liệu rồi atomically chuyển alias.

## 2. Why does it exist?

Search schema tiến hóa: analyzer mới, field type mới, shard strategy mới. Nếu API hard-code physical index, migration buộc deploy đồng bộ hoặc downtime. Alias tạo indirection boundary.

## 3. How does it work?

```text
Search API -> products-read -> products-v1

Build products-v2
DB/events -> sync
Reindex/backfill
Validate
Alias switch:
products-read -> products-v2
```

Alias switch nhanh, nhưng consistency trong giai đoạn backfill/catch-up vẫn phải được thiết kế.

## 4. Practical implementation

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v1", "alias": "products-read" }},
    { "add":    { "index": "products-v2", "alias": "products-read" }}
  ]
}
```

Application chỉ query `products-read`.

## 5. Real production scenario

E-commerce cần analyzer mới cho Vietnamese product search. Team tạo `products-v2`, backfill từ source of truth, replay changes phát sinh trong thời gian backfill, chạy relevance checks rồi switch alias.

## 6. Failure scenario & troubleshooting

**Symptom** → sau switch thiếu products vừa cập nhật. **Evidence** → backfill snapshot cũ và event consumer chưa catch up. **Hypothesis** → migration không có synchronization watermark. **Diagnosis** → so source DB version/event offset với index. **Fix** → dual-write/event replay hoặc checkpointed catch-up trước switch. **Verification** → document counts, sampled business queries và lag metric đạt threshold.

## 7. Common mistakes

Coi `_reindex` là toàn bộ migration plan; dùng Elasticsearch làm source of truth; không giữ rollback alias; không test analyzer/relevance; xóa old index ngay sau switch; không monitor indexing failures.

## 8. Alternatives

In-place mapping addition phù hợp compatible changes. New index + alias phù hợp breaking mapping/analyzer changes. Database full-text search có thể đơn giản hơn nếu search requirements chưa đủ phức tạp.

## 9. Trade-offs

### Advantages

Near-zero-downtime schema migration, rollback dễ hơn, decouple API khỏi physical index.

### Costs / Risks

Tạm thời cần double storage, synchronization logic và validation/cutover discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu alias là logical name, không phải duplicate index.

### Middle

Tạo/reindex/switch và test queries.

### Senior

Thiết kế catch-up, rollback, lag monitoring và relevance validation.

### Technical Lead / Architect

Quyết định khi Elasticsearch complexity được business search requirements biện minh.

## 11. Key takeaway

- Alias giải quyết cutover, không tự giải quyết data consistency.
- Primary database vẫn là transactional source of truth.
- Reindex cần checkpoint, validation và rollback plan.

# 5. Modular Monolith: module boundary và data ownership trước khi nghĩ tới Microservices

## 1. What is it?

Modular Monolith là một deployable application nhưng được chia thành business modules có boundary rõ: API/contracts, domain logic và data ownership. Nó không đơn thuần là nhiều folders trong cùng solution.

## 2. Why does it exist?

Monolith không modular dễ thành tightly coupled codebase. Microservices giải một số deployment/ownership/scale problems nhưng thêm network, messaging, observability và consistency complexity. Modular Monolith giữ operational simplicity trong khi ép boundary tốt hơn.

## 3. How does it work?

```text
Single deployment
├─ Orders
│  ├─ Application
│  ├─ Domain
│  └─ Persistence
├─ Inventory
└─ Billing

Orders --contract/event--> Inventory
Orders -X-> Inventory internal tables/classes
```

Module communication có thể in-process nhưng vẫn qua explicit contracts.

## 4. Practical implementation

```csharp
public interface IInventoryModule
{
    Task<ReservationResult> ReserveAsync(
        ReserveInventory command,
        CancellationToken ct);
}
```

Không inject `InventoryDbContext` trực tiếp vào Orders. Boundary quan trọng hơn việc interface nằm folder nào.

## 5. Real production scenario

SaaS có Orders, Billing và Notifications do một team vận hành. Traffic chưa cần independent scaling. Modular Monolith cho transaction/deployment đơn giản nhưng giữ Billing internals không bị Orders sử dụng trực tiếp.

## 6. Failure scenario & troubleshooting

**Symptom** → “modules” tồn tại nhưng thay Billing schema làm Orders compile fail hàng loạt. **Evidence** → cross-module entity references và direct table access. **Diagnosis** → boundary chỉ là folder. **Fix** → contracts, ownership rules, architecture tests và migration từng dependency. **Verification** → module internals có thể đổi mà consumers chỉ phụ thuộc public contract.

## 7. Common mistakes

Một shared project chứa mọi domain model; cross-module joins tùy tiện; event bus nội bộ cho mọi method call; copy Microservices ceremony mà không có distributed need; chia module theo technical layer thay vì business capability.

## 8. Alternatives

Layered Monolith đơn giản hơn cho domain nhỏ. Microservices phù hợp khi cần independent deployment/scale/ownership thật sự. Không có lý do biến modularity thành distributed systems sớm.

## 9. Trade-offs

### Advantages

Deployment đơn giản, debugging dễ, transaction local, boundary tốt tạo đường migration sau này.

### Costs / Risks

Process/database vẫn shared ở mức vận hành; team phải enforce boundary bằng convention/tests; không có independent scaling.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business responsibility, không phải folder.

### Middle

Tôn trọng public contracts và không bypass persistence ownership.

### Senior

Thiết kế dependency direction, transaction boundaries và integration contracts.

### Technical Lead / Architect

Chỉ tách service khi operational/business pressure đủ lớn; modularity trước distribution.

## 11. Key takeaway

- Boundary tốt không yêu cầu network boundary.
- Data ownership là phần cốt lõi của modularity.
- Modular Monolith thường là điểm khởi đầu an toàn hơn Microservices.

# 6. Azure Container Apps autoscaling: scale theo workload nhưng không xóa downstream bottleneck

## 1. What is it?

Azure Container Apps chạy containerized workloads với managed orchestration và autoscaling, thường dựa trên HTTP concurrency hoặc event-driven metrics qua KEDA. Scale-out thêm replicas của application; nó không tự tăng capacity của SQL, Redis hay external API.

## 2. Why does it exist?

Teams muốn container deployment và elastic scaling mà không vận hành toàn bộ Kubernetes control plane. Tuy nhiên autoscaling chỉ hiệu quả khi workload có thể phân phối và downstream chịu được concurrency tăng.

## 3. How does it work?

```text
Traffic / Queue
      -> scaling metric
      -> Container Apps replicas ↑
      -> each replica
      -> SQL / Redis / APIs
```

Nếu 20 replicas cùng mở nhiều DB connections, bottleneck có thể chuyển từ compute sang database.

## 4. Practical implementation

Một HTTP API nên stateless, đọc configuration/secrets ngoài image, expose health endpoint và propagate cancellation. Với queue consumer, concurrency per replica và max replicas phải khớp downstream capacity thay vì đặt càng cao càng tốt.

## 5. Real production scenario

Image-processing API tăng từ 2 lên 20 replicas khi traffic spike. CPU ổn nhưng metadata SQL bắt đầu timeout vì tổng connection concurrency tăng 10 lần. Autoscaling đã scale đúng application nhưng sai system capacity budget.

## 6. Failure scenario & troubleshooting

**Symptom** → replicas tăng nhưng p95 xấu hơn. **Evidence** → app CPU thấp, DB pool waits và dependency latency tăng. **Hypothesis** → downstream saturation. **Diagnosis** → distributed traces + metrics theo replica/dependency. **Fix** → cap scale/concurrency, batch/queue, tối ưu downstream hoặc scale data tier có chủ đích. **Verification** → load test toàn system, không chỉ container CPU.

## 7. Common mistakes

Scale theo CPU cho I/O-bound workload mà không hiểu signal; không set max replicas; giữ session in-memory; bỏ qua cold start; không có resource limits; cho autoscaler tạo retry storm tới dependency.

## 8. Alternatives

App Service đơn giản hơn cho web app truyền thống. Azure Functions phù hợp event-driven/serverless workload. AKS phù hợp khi cần Kubernetes control/flexibility sâu nhưng operational cost cao hơn.

## 9. Trade-offs

### Advantages

Managed container runtime, elastic scale, ít cluster operations hơn AKS.

### Costs / Risks

Cold starts, scaling lag, platform constraints và downstream capacity vẫn là trách nhiệm architecture.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu replica là thêm application capacity, không phải toàn system capacity.

### Middle

Containerize stateless app, health checks và configuration đúng.

### Senior

Thiết kế scaling metric, concurrency và dependency budgets.

### Technical Lead / Architect

Chọn App Service/Functions/Container Apps/AKS dựa trên workload và operational capability, không theo độ “cloud-native”.

## 11. Key takeaway

- Autoscaling có thể khuếch đại áp lực downstream.
- Scale signal phải phản ánh workload thực.
- Capacity planning là end-to-end.

# 7. Feature flags trong deployment: tách deploy khỏi release nhưng tránh permanent branching

## 1. What is it?

Feature flag cho phép code được deploy nhưng behavior được bật/tắt theo configuration, cohort hoặc environment. Nó tách **deployment** (đưa code vào production) khỏi **release** (cho users sử dụng feature).

## 2. Why does it exist?

Big-bang releases tăng blast radius. Flag hỗ trợ gradual rollout, kill switch và phối hợp frontend/backend. Nhưng mỗi flag là một branch runtime cần test và cuối cùng phải được xóa.

## 3. How does it work?

```text
Deploy artifact containing old + new path
                |
          evaluate flag
           /         \
       old path     new path
```

Flag service/configuration phải có failure semantics rõ: nếu provider unavailable thì default nào an toàn?

## 4. Practical implementation

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
    return await newCheckout.ExecuteAsync(command, ct);

return await legacyCheckout.ExecuteAsync(command, ct);
```

Không đặt security authorization chỉ sau một feature flag; authorization vẫn phải enforce độc lập.

## 5. Real production scenario

Checkout mới deploy cho 5% traffic. Metrics error/latency tăng nên team disable flag mà không rollback artifact. Sau khi fix, rollout 5% → 25% → 100%.

## 6. Failure scenario & troubleshooting

**Symptom** → bug chỉ xuất hiện với một cohort. **Evidence** → logs không ghi evaluated flag/version. **Diagnosis** → thiếu release-context telemetry. **Fix** → enrich traces/metrics với low-cardinality flag state cần thiết. **Verification** → dashboard so old/new path và rollback flag được diễn tập.

## 7. Common mistakes

Flags tồn tại nhiều năm; nested flags tạo combinatorial states; dùng flag thay authorization; thay database schema theo flag không backward-compatible; không có owner/expiry; test chỉ một branch.

## 8. Alternatives

Blue-Green/Canary điều khiển traffic giữa deployments thay vì code paths. Deployment slots phù hợp environment cutover. Flag mạnh khi cần user/cohort-level release nhưng không thay thế deployment safety.

## 9. Trade-offs

### Advantages

Giảm release blast radius, kill switch nhanh, gradual experimentation.

### Costs / Risks

Runtime complexity, test matrix, stale code và configuration dependency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt deploy và release.

### Middle

Implement default behavior, tests cho cả hai paths.

### Senior

Thiết kế telemetry, rollback và database compatibility.

### Technical Lead / Architect

Đặt lifecycle policy: owner, expiry, cleanup và giới hạn số active flags.

## 11. Key takeaway

- Feature flag là temporary operational control.
- Flag không phải security boundary.
- Mỗi flag cần owner và deletion plan.

# 8. Application Insights sampling: giảm telemetry cost mà không phá incident investigation

## 1. What is it?

Sampling giữ một phần telemetry thay vì ingest mọi event. Mục tiêu là kiểm soát volume/cost trong khi vẫn giữ statistical signal và trace usefulness. Sampling không nên ngẫu nhiên phá từng span của cùng distributed trace.

## 2. Why does it exist?

High-throughput service có thể tạo hàng triệu requests, dependencies và logs. Ingest 100% có thể đắt và làm query noisy. Nhưng sampling sai có thể loại mất rare errors cần điều tra.

## 3. How does it work?

```text
Request trace
  ├─ API span
  ├─ SQL span
  └─ HTTP span
       |
  sampling decision
       |
 keep coherent trace OR drop according to policy
```

Metrics quan trọng thường cần semantics khác traces; errors/audit/security events cũng không nên xử lý như debug traces.

## 4. Practical implementation

Với OpenTelemetry/.NET, sampling policy nên được cấu hình ở tracing pipeline và propagated nhất quán. Application code vẫn tạo spans có meaningful attributes nhưng tránh high-cardinality data như raw user IDs trong metric dimensions.

## 5. Real production scenario

API 20k requests/second chỉ giữ một tỷ lệ normal traces nhưng giữ đủ error/slow traces theo pipeline strategy. Dashboard dùng metrics cho detection; trace dùng cho diagnosis.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard báo 500 errors nhưng không tìm được trace tương ứng. **Evidence** → sampling loại error traces hoặc correlation bị mất. **Hypothesis** → policy không giữ diagnostic exceptions. **Diagnosis** → kiểm tra SDK/collector sampling và trace propagation. **Fix** → điều chỉnh policy, tail-based strategy khi hạ tầng hỗ trợ hoặc preserve critical telemetry. **Verification** → inject controlled failures và xác nhận end-to-end trace có thể truy tìm.

## 7. Common mistakes

Dùng logs thay metrics; sample audit records; thêm unbounded dimensions; giữ 100% “cho chắc”; sampling độc lập ở mỗi service làm trace bị đứt; không hiểu billing/retention.

## 8. Alternatives

Giảm noisy instrumentation, aggregate metrics, thay log level hoặc retention. Sampling là một công cụ trong telemetry budget, không phải giải pháp duy nhất.

## 9. Trade-offs

### Advantages

Giảm ingestion/storage cost và noise.

### Costs / Risks

Có thể bỏ rare evidence; weighted counts và statistical interpretation cần đúng; policy phức tạp hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu logs, metrics và traces có mục đích khác nhau.

### Middle

Instrument correlation và structured attributes.

### Senior

Thiết kế sampling để vẫn điều tra p99/errors và kiểm soát cardinality.

### Technical Lead / Architect

Đặt telemetry budget/SLO và quyết định evidence nào bắt buộc giữ vì reliability/compliance.

## 11. Key takeaway

- Metrics phát hiện; traces giải thích; logs bổ sung evidence.
- Sampling phải bảo vệ trace coherence và critical failures.
- Observability cũng có cost budget.

# 9. Optimizely CMS content modeling: thiết kế cho editor workflow thay vì map database tables

## 1. What is it?

Content modeling xác định Page Types, Blocks, properties và relationships mà editors dùng để tạo trải nghiệm. Trong Optimizely CMS, model tốt phản ánh reusable content semantics và editorial workflow, không phản ánh schema database của application.

## 2. Why does it exist?

Nếu content type quá technical, editor phải hiểu implementation. Nếu một giant page model chứa mọi field, reuse và governance kém. Nếu chia block quá nhỏ, editing trở nên fragmentary và khó preview.

## 3. How does it work?

```text
Product Landing Page
 ├─ Hero Block
 ├─ Rich Content Block
 ├─ Product Listing Block -> Product API
 └─ FAQ Block

CMS owns editorial content
Commerce API owns price/inventory
```

Boundary content vs transactional/product data phải rõ.

## 4. Practical implementation

```csharp
[ContentType(DisplayName = "Hero Block", GUID = "11111111-1111-1111-1111-111111111111")]
public class HeroBlock : BlockData
{
    [CultureSpecific]
    public virtual string? Heading { get; set; }

    public virtual ContentReference? Image { get; set; }

    public virtual Url? CallToActionUrl { get; set; }
}
```

Property names, validation và editor hints nên mô tả business/editor intent.

## 5. Real production scenario

Marketing cần hero dùng lại trên landing pages. Product price không được copy vào CMS vì sẽ stale; block giữ editorial text/product reference, runtime lấy price từ commerce source.

## 6. Failure scenario & troubleshooting

**Symptom** → editors publish content nhưng page hiển thị stale data. **Evidence** → CMS/CDN cache chưa invalidated hoặc dynamic product data bị cache cùng editorial TTL. **Hypothesis** → cache boundary không khớp ownership. **Diagnosis** → trace Browser → CDN → app → CMS/Product API. **Fix** → tách cache policies và invalidation owner. **Verification** → publish/update scenario phản ánh đúng SLA freshness.

## 7. Common mistakes

Map domain entity thành content type; copy inventory/price vào CMS; tạo block quá generic với hàng chục optional fields; hard-code presentation vào model; bỏ migration/backward compatibility khi đổi property.

## 8. Alternatives

Headless CMS tách delivery khỏi rendering nhưng tăng integration responsibility. Traditional Optimizely rendering đơn giản hơn khi web application và CMS lifecycle gắn chặt. Không phải site nào cũng cần composable architecture.

## 9. Trade-offs

### Advantages

Editor autonomy, reusable content, governance và localization tốt.

### Costs / Risks

Content model migration, cache complexity, preview/editor UX và integration boundaries cần duy trì.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Page/Block là editorial concepts.

### Middle

Tạo reusable models, validation và rendering/API mapping.

### Senior

Thiết kế caching, upgrades, localization và ownership giữa CMS với commerce/search.

### Technical Lead / Architect

Quyết định content nào thuộc CMS, data nào thuộc systems of record và khi nào headless/composable đáng complexity.

## 11. Key takeaway

- Model content theo editor intent và ownership.
- CMS không nên trở thành database cho transactional data.
- Cache/invalidation phải theo từng source of truth.

# 10. Webhook verification: remote callback là untrusted input và phải chống replay

## 1. What is it?

Webhook là HTTP callback từ external provider tới application. Verification xác minh request thực sự đến từ provider và payload không bị sửa, thường bằng HMAC signature hoặc asymmetric signature. Nhưng authenticity chưa đủ: cần chống replay và xử lý duplicate delivery.

## 2. Why does it exist?

Webhook endpoint thường public Internet. Nếu chỉ tin JSON body, attacker có thể giả payment event. Nếu signature hợp lệ nhưng request cũ bị replay, side effect vẫn có thể xảy ra lần nữa.

## 3. How does it work?

```text
Provider
  -> timestamp + raw payload
  -> signature(secret/key)
  -> HTTPS webhook
API
  -> verify timestamp window
  -> verify signature constant-time
  -> deduplicate event ID
  -> persist/queue
  -> return promptly
```

Signature thường phải tính trên raw body chính xác, không phải object đã deserialize rồi serialize lại.

## 4. Practical implementation

```csharp
static bool IsValidSignature(
    ReadOnlySpan<byte> body,
    ReadOnlySpan<byte> expected,
    byte[] secret)
{
    using var hmac = new HMACSHA256(secret);
    var actual = hmac.ComputeHash(body.ToArray());
    return CryptographicOperations.FixedTimeEquals(actual, expected);
}
```

Production implementation phải theo đúng canonicalization/signature specification của provider, validate timestamp và rotate secrets an toàn.

## 5. Real production scenario

Payment provider gửi `payment.succeeded`. API verify signature, kiểm tra event ID chưa xử lý, ghi Inbox/queue rồi trả `2xx`. Worker cập nhật order idempotently. Provider retry không tạo shipment lần hai.

## 6. Failure scenario & troubleshooting

**Symptom** → valid webhook bị reject sau deploy. **Evidence** → signature mismatch nhưng provider logs cho thấy payload hợp lệ. **Hypothesis** → middleware đã parse/normalize body trước verification hoặc secret version sai. **Diagnosis** → compare raw bytes, headers, timestamp và key version. **Fix** → preserve raw body, follow provider canonicalization, support rotation overlap. **Verification** → official signed fixtures + replay/duplicate tests.

## 7. Common mistakes

Tin source IP duy nhất; compare signature bằng string thường; bỏ timestamp; log secret/raw sensitive payload; thực hiện heavy business logic trước `2xx`; không deduplicate event ID; retry downstream không idempotent.

## 8. Alternatives

Polling tránh public callback nhưng tăng latency/quota/cost. Queue integration tốt hơn khi provider hỗ trợ native messaging. Webhook vẫn phù hợp cho near-real-time third-party integration nếu security và delivery semantics được thiết kế đúng.

## 9. Trade-offs

### Advantages

Near-real-time, ít polling, integration đơn giản ở protocol level.

### Costs / Risks

Public attack surface, duplicate/out-of-order delivery, secret rotation và observability complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Không tin webhook chỉ vì endpoint “bí mật”.

### Middle

Verify signature/timestamp và xử lý duplicate event.

### Senior

Thiết kế Inbox/idempotency, ordering assumptions, retries, secret rotation và audit.

### Technical Lead / Architect

Xác định trust boundary, failure policy và business reconciliation khi provider hoặc webhook delivery bị gián đoạn.

## 11. Key takeaway

- Webhook payload là untrusted input cho tới khi verification hoàn tất.
- Valid signature không tự chống replay/duplicate.
- Acknowledge nhanh; xử lý business idempotently phía sau durable boundary.
