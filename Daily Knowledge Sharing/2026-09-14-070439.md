# 1. C# `Span<T>` và `Memory<T>`: xử lý slices/buffers hiệu quả mà không đánh đổi safety chỉ để giảm allocation

## 1. What is it?

Mental model:

```text
byte[] / string / unmanaged buffer
          |
          v
       Span<T>
  view trên vùng nhớ liên tục
  không sở hữu dữ liệu
```

`Span<T>` là một `ref struct` đại diện cho một vùng nhớ liên tục mà không cần copy dữ liệu. Nó có thể trỏ vào array, stack memory hoặc unmanaged memory nhưng bị giới hạn lifetime để CLR/compiler ngăn reference thoát khỏi vùng an toàn.

`Memory<T>` phục vụ use case tương tự nhưng có thể sống trên heap, lưu trong field và đi qua async boundary. Khi cần truy cập dữ liệu synchronously, thường lấy `.Span` từ `Memory<T>`.

## 2. Why does it exist?

Nhiều parser, serializer và protocol handler trước đây tạo rất nhiều string/array trung gian:

```csharp
var parts = input.Split(':');
var prefix = parts[0];
```

Với hot path có hàng triệu requests, các allocation ngắn hạn làm tăng Gen0 GC và CPU dù business logic rất đơn giản.

`Span<T>` cho phép slicing trực tiếp trên buffer gốc:

```text
original buffer
[HEADER|PAYLOAD|CRC]
   |       |
 slice    slice
```

Không cần tạo array mới chỉ để nhìn một đoạn dữ liệu.

## 3. How does it work?

`Span<T>` giữ reference + length. `Slice` tạo view mới chứ không copy:

```csharp
ReadOnlySpan<char> input = "ORDER:12345";
var separator = input.IndexOf(':');

ReadOnlySpan<char> kind = input[..separator];
ReadOnlySpan<char> id = input[(separator + 1)..];
```

Vì `Span<T>` là `ref struct`, compiler không cho:

- box nó;
- lưu trong normal class field;
- capture vào lambda thông thường;
- đi xuyên `await` boundary khi lifetime không đảm bảo.

Đây là safety mechanism, không phải hạn chế tùy ý.

`Memory<T>` giải quyết scenario cần giữ buffer qua async operation:

```csharp
public async Task SendAsync(ReadOnlyMemory<byte> payload, CancellationToken ct)
{
    await _stream.WriteAsync(payload, ct);
}
```

## 4. Practical implementation

Ví dụ parse header đơn giản mà không tạo substring:

```csharp
public static bool TryParseHeader(
    ReadOnlySpan<char> input,
    out int version,
    out ReadOnlySpan<char> command)
{
    version = default;
    command = default;

    var first = input.IndexOf('|');
    if (first <= 0)
        return false;

    if (!int.TryParse(input[..first], out version))
        return false;

    command = input[(first + 1)..];
    return true;
}
```

Đây phù hợp khi profiling cho thấy parser/string allocation thực sự là bottleneck. Với CRUD API vài trăm requests/second, việc đổi code rõ ràng sang low-level span logic có thể không đáng.

## 5. Real production scenario

Một ingestion service đọc hàng chục nghìn telemetry lines mỗi giây. Mỗi line được `Split`, `Substring`, rồi parse nhiều fields. CPU không cao vì business logic mà cao vì allocation và GC.

Sau khi chuyển parsing hot path sang `ReadOnlySpan<char>` và giữ buffer ownership rõ ràng, allocation rate giảm đáng kể. Nhưng team chỉ tối ưu parser, không áp dụng `Span<T>` vào toàn codebase.

## 6. Failure scenario & troubleshooting

**Symptom** → tối ưu bằng `Span<T>` nhưng code trở nên khó maintain, performance không cải thiện hoặc xuất hiện bug do buffer bị reuse.

**Evidence** → profiler cho thấy allocation bottleneck vốn nằm ở JSON serialization/database I/O; hoặc `Memory<T>` tham chiếu pooled buffer đã trả lại pool.

**Hypothesis** → zero-copy abstraction được dùng sai ownership/lifetime boundary.

**Diagnosis** → xác định ai sở hữu buffer, buffer sống đến khi nào, caller có giữ reference sau khi pool trả buffer hay không.

**Fix** → dùng copy ở boundary cần ownership độc lập; chỉ dùng pooling/span trong measured hot path.

**Verification** → benchmark allocation + correctness tests với concurrent/reused buffers.

## 7. Common mistakes

- Dùng `Span<T>` chỉ vì “nhanh hơn”.
- Tối ưu trước khi đo allocation.
- Trả `Memory<T>` trỏ vào pooled buffer đã `Return`.
- Cố ép `Span<T>` qua async boundary.
- Làm public API quá low-level khiến caller khó dùng.
- Nhầm zero-copy với zero-cost; bounds checks, parsing và cache locality vẫn quan trọng.

## 8. Alternatives

- `string`/array thông thường: tốt nhất khi simplicity quan trọng hơn micro-allocation.
- `ArrayPool<T>`: giảm allocation cho buffers lớn/repeated nhưng tăng ownership complexity.
- `System.IO.Pipelines`: phù hợp streaming parser phức tạp và high-throughput I/O.

## 9. Trade-offs

### Advantages

- Giảm copy và allocation trong hot paths.
- Slicing rẻ.
- Compiler enforce nhiều lifetime constraints.

### Costs / Risks

- Code khó đọc hơn.
- Buffer ownership trở nên critical.
- Lợi ích nhỏ nếu bottleneck nằm ở network/database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Span<T>` là view, không sở hữu data.

### Middle

Biết slicing/parsing và phân biệt `Span<T>` với `Memory<T>`.

### Senior

Dùng profiler để xác định allocation hot path và hiểu pooled-buffer lifetime.

### Technical Lead / Architect

Đặt performance abstraction đúng boundary; không biến low-level optimization thành coding convention toàn hệ thống.

## 11. Key takeaway

- `Span<T>` giúp tránh copy/allocation, nhưng chỉ đáng dùng trong measured hot path.
- `Memory<T>` phù hợp hơn khi cần giữ data qua async/lifetime dài hơn.
- Buffer ownership quan trọng hơn việc “không copy bằng mọi giá”.

# 2. ASP.NET Core middleware ordering: vì sao đúng middleware nhưng sai thứ tự vẫn tạo security bug và behavior khó đoán

## 1. What is it?

ASP.NET Core request pipeline là chuỗi middleware chạy theo thứ tự đăng ký.

Mental model:

```text
Request
  |
Exception handling
  |
Routing
  |
Authentication
  |
Authorization
  |
Endpoint
  |
Response đi ngược pipeline
```

Mỗi middleware có thể chạy code trước và sau `next()`. Vì vậy ordering quyết định middleware nào nhìn thấy route metadata, user identity, exception và response cuối cùng.

## 2. Why does it exist?

Cross-cutting concerns như security, logging, CORS, exception handling, compression và routing không thể hoạt động đúng nếu chúng không được đặt tại đúng lifecycle point.

Ví dụ Authorization cần endpoint metadata do routing xác định và principal do Authentication tạo. Nếu chạy sai thứ tự, policy có thể không có context đúng.

## 3. How does it work?

Simplified pipeline:

```csharp
app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseRouting();
app.UseCors();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
```

Request đi xuống theo thứ tự. Response/exception có thể unwind ngược lên.

Một outer middleware có thể đo toàn request duration:

```csharp
app.Use(async (ctx, next) =>
{
    var sw = Stopwatch.StartNew();
    try
    {
        await next();
    }
    finally
    {
        logger.LogInformation("Request took {Elapsed}ms", sw.ElapsedMilliseconds);
    }
});
```

## 4. Practical implementation

Đừng memorize một thứ tự duy nhất; hãy hỏi middleware cần context nào.

Ví dụ custom tenant authorization cần authenticated user + endpoint metadata:

```csharp
app.UseRouting();
app.UseAuthentication();
app.UseMiddleware<TenantContextMiddleware>();
app.UseAuthorization();
```

Nếu `TenantContextMiddleware` cần claims, nó phải chạy sau authentication. Nếu nó set data để authorization policy đọc, nó phải chạy trước authorization.

## 5. Real production scenario

Một API thêm custom middleware kiểm tra claim `tenant_id` nhưng middleware được đặt trước `UseAuthentication()`. Local tests dùng mocked `HttpContext.User`, nên pass. Production bearer authentication chạy sau đó, middleware luôn thấy anonymous user và trả 403.

Bug nhìn giống token validation lỗi nhưng root cause là pipeline order.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint có `[Authorize]` nhưng principal/metadata không như expected, hoặc exception handler không bắt được lỗi từ một middleware.

**Evidence** → log trace cho thấy component chạy trước dependency context mà nó cần.

**Hypothesis** → ordering mismatch.

**Diagnosis** → vẽ pipeline thực tế; xác định mỗi middleware đọc/ghi gì trước và sau `next()`.

**Fix** → reorder theo data dependency thay vì copy boilerplate từ project khác.

**Verification** → integration tests qua full pipeline, không chỉ unit-test middleware riêng.

## 7. Common mistakes

- Đặt custom authorization trước authentication.
- Cho exception handler quá sâu nên không bắt exception ở middleware bên ngoài.
- Đặt response-modifying middleware sau endpoint khiến nó không chạy như kỳ vọng.
- Không hiểu `Map`, `UseWhen`, branch pipelines.
- Copy pipeline từ template cũ mà không xem middleware mới cần gì.

## 8. Alternatives

- Endpoint filters/filters khi concern chỉ áp dụng endpoint/controller layer.
- Authorization policies thay custom security middleware khi bài toán là permission.
- Delegating handlers cho outbound HTTP, không nên nhét vào inbound middleware.

## 9. Trade-offs

### Advantages

- Middleware là composition model mạnh cho cross-cutting request concerns.
- Central behavior dễ nhất quán.

### Costs / Risks

- Ordering tạo implicit dependency khó nhìn.
- Một middleware global có thể tác động mọi endpoint.
- Custom middleware quá nhiều biến pipeline thành hidden architecture.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu request đi xuống, response đi ngược pipeline.

### Middle

Biết đặt authentication/authorization/routing đúng dependency order.

### Senior

Debug branch pipelines, exception boundaries và metadata/user availability.

### Technical Lead / Architect

Quy định concern nào thuộc middleware, filter, endpoint hay application layer để pipeline không trở thành nơi chứa business logic.

## 11. Key takeaway

- Middleware đúng nhưng sai thứ tự vẫn là implementation sai.
- Hãy xác định context dependency của middleware, không học thuộc ordering vô điều kiện.
- Security behavior phải được test qua real pipeline.

# 3. EF Core transactions + execution strategy: retry transient failure chỉ an toàn khi transaction boundary được thiết kế đúng

## 1. What is it?

EF Core execution strategy có thể retry database operations khi gặp transient failures. Nhưng user-managed transaction tạo một nhóm operations phải được retry như một unit.

Mental model:

```text
Operation A
Operation B
Commit
   |
transient error ở giữa
   |
retry phải replay toàn transactional unit
```

Retry từng statement riêng lẻ có thể làm transaction semantics sai.

## 2. Why does it exist?

Cloud database connections có transient disconnect, failover hoặc throttling. Retry giúp application phục hồi mà không fail request ngay lập tức.

Nhưng transaction có state. Nếu bạn bắt đầu transaction ngoài execution strategy rồi retry statement thứ hai, execution strategy không thể giả định transaction đầu còn hợp lệ.

## 3. How does it work?

Pattern chuẩn khi dùng manual transaction cùng retry strategy:

```csharp
var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    // nhiều DB operations

    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
});
```

Strategy có thể replay delegate khi transient failure xảy ra.

Nhưng replay an toàn chỉ khi side effects trong delegate cũng replay-safe. Nếu bạn gọi external payment API trong cùng delegate, retry có thể charge hai lần.

## 4. Practical implementation

Ví dụ chỉ giữ database side effects trong retriable transaction:

```csharp
await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    order.MarkConfirmed();
    db.OutboxMessages.Add(OutboxMessage.For(order));

    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
});
```

External publish xử lý từ Outbox sau commit, không nằm trong retryable DB transaction.

## 5. Real production scenario

Checkout service tạo order rồi gọi payment provider trước `Commit`. Database commit gặp connection error không rõ outcome. Request retry toàn endpoint và payment provider charge lại.

Đây là ambiguous outcome: application không biết commit/payment bước nào đã thành công.

Thiết kế tốt cần idempotency ở external side effect và durable state transition/outbox.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate external side effects sau transient SQL errors hoặc exception “execution strategy does not support user-initiated transactions”.

**Evidence** → transaction được tạo ngoài execution strategy hoặc external call nằm trong retry delegate.

**Hypothesis** → retry boundary và transaction boundary không trùng nhau.

**Diagnosis** → trace từng side effect trong retry block; phân loại database-local vs external/irreversible.

**Fix** → execute whole DB transaction trong strategy; tách external side effects qua Outbox/idempotency.

**Verification** → fault-injection tại save/commit và xác nhận không duplicate business effect.

## 7. Common mistakes

- Bật retry rồi nghĩ mọi transaction tự động an toàn.
- Retry `SaveChanges` sau một external API call không idempotent.
- Transaction quá dài bao gồm network calls.
- Catch transient error rồi tạo transaction mới mà không biết outcome cũ.
- Không test connection drop/failover.

## 8. Alternatives

- Không dùng explicit transaction khi một `SaveChanges` đã đủ atomicity.
- Outbox Pattern cho database + messaging.
- Saga khi workflow đi qua nhiều services.

## 9. Trade-offs

### Advantages

- Execution strategy tăng resilience với transient database failures.
- Correct transaction scoping giữ invariants trong replay.

### Costs / Risks

- Retry tăng latency và load khi dependency đang degraded.
- Ambiguous commit vẫn là vấn đề cần reasoning.
- External side effects cần idempotency/durable workflow riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `SaveChanges` thường đã có transaction cho một batch thay đổi.

### Middle

Biết explicit transaction và execution strategy phải phối hợp đúng.

### Senior

Phân tích ambiguous outcome, retry safety và external side effects.

### Technical Lead / Architect

Định nghĩa transaction boundary, Outbox/idempotency và failure model cho workflows quan trọng.

## 11. Key takeaway

- Retry và transaction là hai mechanisms phải thiết kế cùng nhau.
- Không đưa non-idempotent external side effect vào retryable DB transaction.
- Fault-injection quan trọng hơn chỉ test happy path.

# 4. PostgreSQL MVCC và VACUUM: đọc/ghi concurrent không có nghĩa database không tích lũy dead tuples và bloat

## 1. What is it?

PostgreSQL dùng MVCC — Multi-Version Concurrency Control — để cho readers nhìn thấy snapshot phù hợp trong khi writers tạo version mới của row.

Mental model:

```text
UPDATE row
old tuple  -> vẫn tồn tại tạm thời
new tuple  -> version mới

active transactions quyết định version nào còn visible
VACUUM dọn version không còn cần thiết
```

UPDATE thường không “ghi đè tại chỗ” theo mental model đơn giản; row version cũ có thể trở thành dead tuple.

## 2. Why does it exist?

Nếu readers và writers phải khóa nhau cho mọi operation, concurrency giảm mạnh. MVCC cho phép nhiều reads diễn ra mà không block writes theo cùng cách lock-based model truyền thống.

Đổi lại, hệ thống cần cleanup versions cũ.

## 3. How does it work?

Mỗi transaction nhìn database theo visibility rules. Khi row update/delete, old tuple không lập tức biến mất vì transaction cũ có thể vẫn cần nó.

Autovacuum dọn dead tuples khi không còn snapshot nào cần chúng và cập nhật housekeeping metadata.

Long-running transactions có thể giữ old snapshots quá lâu và ngăn cleanup hiệu quả.

## 4. Practical implementation

Theo dõi tables có dead tuples lớn:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Theo dõi long-running transactions:

```sql
SELECT pid, now() - xact_start AS age, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Không nên phản xạ bằng cách `VACUUM FULL` ngay production vì nó có locking/space implications mạnh hơn normal vacuum.

## 5. Real production scenario

Một SaaS có bảng jobs update status liên tục. Một reporting connection mở transaction nhiều giờ. Autovacuum chạy nhưng không reclaim được nhiều tuples cũ vì snapshot vẫn cần visibility history.

Table/index bloat tăng, query I/O tăng và disk usage phình ra dù row count business gần như không đổi.

## 6. Failure scenario & troubleshooting

**Symptom** → disk tăng, query chậm dần, table size lớn bất thường so với live rows.

**Evidence** → `n_dead_tup` cao, long-running transaction tồn tại, autovacuum lag.

**Hypothesis** → churn cao + vacuum bị cản hoặc settings không phù hợp workload.

**Diagnosis** → xem transaction age, vacuum history, tuple churn và table/index sizes.

**Fix** → xử lý long transaction, tune autovacuum có mục tiêu, redesign churn-heavy patterns nếu cần.

**Verification** → dead tuples giảm, table growth ổn định, I/O/query latency cải thiện.

## 7. Common mistakes

- Nghĩ PostgreSQL “không lock” vì có MVCC.
- Giữ transaction mở trong interactive/reporting flow quá lâu.
- Tắt autovacuum để giảm CPU.
- Chạy `VACUUM FULL` như routine maintenance.
- Chỉ nhìn row count mà không nhìn dead tuples/index bloat.

## 8. Alternatives

Không có “alternative” trực tiếp nếu đang dùng PostgreSQL; đây là storage/concurrency model cần vận hành đúng. Ở mức architecture, append-only/event models hoặc partitioning có thể phù hợp workload churn rất cao nhưng đổi complexity lớn.

## 9. Trade-offs

### Advantages

- Reader/writer concurrency tốt.
- Snapshot semantics mạnh.

### Costs / Risks

- Dead tuples cần vacuum.
- Long transactions có tác động operational lớn.
- High-update tables cần tuning/monitoring.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu UPDATE tạo row version mới về mặt MVCC.

### Middle

Biết theo dõi dead tuples và tránh transaction dài vô lý.

### Senior

Chẩn đoán bloat/autovacuum lag dựa trên workload và transaction age.

### Technical Lead / Architect

Thiết kế workload, reporting boundaries và operational SLO để database không bị transaction usage pattern phá dần theo thời gian.

## 11. Key takeaway

- MVCC giảm reader-writer blocking bằng versioning, không phải miễn phí.
- Long-running transaction có thể ngăn cleanup và gây bloat.
- Vacuum là phần của correctness/operations model, không chỉ housekeeping tùy chọn.

# 5. Saga Pattern và compensating transactions: phối hợp business workflow nhiều services mà không giả vờ có distributed ACID transaction

## 1. What is it?

Saga là cách chia một business transaction lớn thành nhiều local transactions. Nếu bước sau thất bại, hệ thống chạy compensating action cho các bước trước khi business semantics cho phép.

Mental model:

```text
Create Order
   |
Reserve Inventory
   |
Charge Payment
   |
Book Shipment

nếu Charge fail:
Release Inventory
Cancel Order
```

Compensation không phải database rollback. Nó là business action mới để đưa hệ thống tới trạng thái chấp nhận được.

## 2. Why does it exist?

Trong microservices, mỗi service sở hữu database riêng. Giữ một distributed transaction xuyên SQL, payment provider, warehouse và shipping thường không khả thi hoặc quá đắt về coupling/availability.

Saga chấp nhận eventual consistency và explicit failure handling.

## 3. How does it work?

Hai phong cách phổ biến:

- orchestration: một coordinator quyết định bước tiếp theo;
- choreography: services phản ứng với events.

Orchestration dễ nhìn workflow hơn:

```text
Saga Orchestrator
  -> Inventory: Reserve
  -> Payment: Charge
  -> Shipping: Create
```

Choreography giảm central coordinator nhưng flow có thể khó trace khi event graph lớn.

## 4. Practical implementation

State machine nên lưu durable state:

```csharp
public enum CheckoutState
{
    Started,
    InventoryReserved,
    PaymentCaptured,
    Completed,
    Compensating,
    Failed
}
```

Mỗi command/event cần correlation ID và idempotency key. Compensation cũng phải idempotent vì message có thể giao nhiều lần.

Ví dụ `ReleaseInventory(orderId)` chạy hai lần không được cộng stock gấp đôi.

## 5. Real production scenario

Checkout reserve hàng thành công nhưng payment provider timeout. Hệ thống không biết provider đã charge hay chưa.

Nếu lập tức release stock và retry charge mù, có thể tạo inconsistent outcome. Saga cần trạng thái `PaymentUnknown`, reconciliation hoặc idempotency key với provider để xác định kết quả trước khi compensate.

## 6. Failure scenario & troubleshooting

**Symptom** → order stuck ở trạng thái trung gian, stock reserved mãi hoặc compensation chạy lặp.

**Evidence** → trace cho thấy missing event, duplicate delivery hoặc compensation failure.

**Hypothesis** → saga state không durable/idempotent hoặc không có recovery path.

**Diagnosis** → inspect state transitions, message IDs, retries, DLQ và external side-effect records.

**Fix** → durable saga state, idempotent handlers, timeout/reconciliation workflow và observable terminal states.

**Verification** → chaos/fault tests tại từng transition và compensation.

## 7. Common mistakes

- Gọi compensation là rollback.
- Không thiết kế compensation trước khi phát hành workflow.
- Choreography quá nhiều events không có ownership rõ.
- Không lưu saga state durable.
- Assume message exactly-once.
- Compensation không idempotent.

## 8. Alternatives

- Single database transaction nếu workflow nằm trong một bounded context và một DB.
- Modular Monolith nếu phân service chưa đem lại lợi ích đủ lớn.
- Manual operational recovery cho workflow hiếm/low-volume thay vì xây full saga platform.

## 9. Trade-offs

### Advantages

- Không cần distributed lock/2PC xuyên services.
- Cho phép service autonomy và partial recovery.

### Costs / Risks

- Eventual consistency và intermediate states.
- Compensation logic phức tạp.
- Observability/reconciliation trở thành requirement.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu local transaction không thể tự rollback service khác.

### Middle

Implement idempotent steps và explicit state transitions.

### Senior

Thiết kế timeout, compensation, reconciliation và duplicate-message handling.

### Technical Lead / Architect

Quyết định workflow có thật sự cần phân tán hay một transaction boundary đơn giản hơn vẫn tốt hơn.

## 11. Key takeaway

- Saga quản lý business consistency, không giả lập distributed ACID transaction.
- Compensation là action mới và phải idempotent.
- Nếu một database transaction đủ giải quyết, đừng đưa Saga vào chỉ vì architecture “hiện đại”.

# 6. Azure Blob Storage SAS: cấp quyền giới hạn theo thời gian mà không biến storage account key thành credential dùng chung

## 1. What is it?

Shared Access Signature (SAS) là token cấp quyền hạn chế lên Azure Storage resource trong thời gian xác định.

Mental model:

```text
Client
  |
SAS URL
  |
  v
Blob Storage

permissions: read/write/list?
resource: blob/container?
time: start-expiry
```

Client có thể upload/download trực tiếp mà application không cần proxy toàn payload.

## 2. Why does it exist?

Nếu browser/mobile upload file lớn qua API server, application phải chịu bandwidth, connection duration và scaling cost. Nhưng đưa storage account key cho client là hoàn toàn không chấp nhận được.

SAS cho phép delegated, scoped access.

## 3. How does it work?

SAS chứa signed constraints như resource, permissions và expiry. Với Azure-hosted backend, user delegation SAS thường tốt hơn account-key SAS vì signature dựa trên Microsoft Entra credentials thay vì long-lived account key.

Flow:

```text
Client -> API: request upload authorization
API -> validate user/business rules
API -> Blob: generate scoped authorization context
API -> Client: short-lived SAS
Client -> Blob: upload directly
```

## 4. Practical implementation

Backend chỉ phát SAS sau authorization:

```csharp
var sas = new BlobSasBuilder
{
    BlobContainerName = container,
    BlobName = blobName,
    Resource = "b",
    ExpiresOn = DateTimeOffset.UtcNow.AddMinutes(10)
};

sas.SetPermissions(BlobSasPermissions.Create | BlobSasPermissions.Write);
```

Production nên dùng generated blob name, short expiry, least privilege và validate upload sau khi hoàn tất.

Không nên cấp `List` hoặc container-wide `Write` nếu client chỉ cần upload một blob cụ thể.

## 5. Real production scenario

CMS cho editor upload video 2 GB. Qua App Service, request giữ connection lâu, tăng bandwidth cost và memory/temp-disk pressure.

Chuyển sang direct-to-Blob bằng short-lived SAS giúp App Service chỉ xử lý authorization + metadata. Upload bytes đi thẳng từ browser tới Storage.

## 6. Failure scenario & troubleshooting

**Symptom** → client nhận 403 từ Blob dù SAS vừa được cấp.

**Evidence** → SAS scope/permission/time window sai; clock skew; blob path không khớp; network restrictions chặn client.

**Hypothesis** → delegated permission không khớp actual operation.

**Diagnosis** → kiểm tra resource path, `sp`, `st`, `se`, network rules và request method.

**Fix** → cấp minimal correct permission/time scope; không mở rộng quyền vô điều kiện để “cho chạy”.

**Verification** → positive + negative tests: blob đúng upload được, blob khác/container listing phải bị deny.

## 7. Common mistakes

- SAS expiry vài ngày/tháng cho browser upload.
- Cấp container-wide permissions không cần thiết.
- Log full SAS URL.
- Dùng account key ở frontend.
- Nghĩ upload thành công nghĩa file an toàn; vẫn cần content validation/scanning.
- Không cleanup abandoned uploads.

## 8. Alternatives

- API-mediated streaming khi server bắt buộc inspect bytes inline.
- Private service-to-service access bằng Managed Identity, không cần SAS cho trusted backend.
- CDN signed URLs/tokens cho distribution scenarios khác.

## 9. Trade-offs

### Advantages

- Offload bandwidth khỏi application.
- Least-privilege access có thời hạn.
- Scale upload/download tốt hơn.

### Costs / Risks

- Client thấy direct storage endpoint.
- SAS leakage có hiệu lực đến khi expiry/policy bị revoke theo mechanism phù hợp.
- Workflow cần finalize/scan/cleanup riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu SAS là delegated temporary access, không phải account credential.

### Middle

Tạo short-lived blob-scoped permissions.

### Senior

Thiết kế direct upload, validation, cleanup và network/security controls.

### Technical Lead / Architect

Chọn data path: app-proxy hay direct storage, dựa trên threat model, cost, file size và compliance.

## 11. Key takeaway

- SAS nên ngắn hạn, scope hẹp và least privilege.
- Direct-to-Blob giảm app bandwidth nhưng không bỏ bước validation/business authorization.
- Ưu tiên identity-based delegation thay vì chia sẻ long-lived account keys.

# 7. Kubernetes resource requests/limits: scheduler, throttling và OOMKilled bắt đầu từ hai con số tưởng như chỉ là cấu hình deployment

## 1. What is it?

`requests` mô tả lượng CPU/memory pod cần để scheduler placement. `limits` đặt trần resource runtime theo cơ chế container/cgroup tương ứng.

Mental model:

```text
requests -> scheduler capacity planning
limits   -> runtime enforcement

CPU limit exceeded    -> throttling
Memory limit exceeded -> OOMKilled
```

## 2. Why does it exist?

Không có resource contracts, một workload có thể chiếm node và ảnh hưởng workloads khác. Nhưng đặt limits quá thấp cũng tự gây incident.

Resource configuration là capacity model, không phải YAML decoration.

## 3. How does it work?

Ví dụ:

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
```

Scheduler dùng requests để xem node còn đủ capacity không. Memory vượt limit có thể bị kernel/container runtime kill. CPU thường bị throttled thay vì kill.

Vì vậy `CPU throttling` và `OOMKilled` có failure semantics khác nhau.

## 4. Practical implementation

Đặt giá trị dựa trên measurement:

- baseline idle;
- typical p50/p95 memory;
- peak request load;
- GC behavior;
- startup spikes;
- concurrency.

.NET container cần quan sát heap + native memory, không chỉ managed heap.

Đừng set memory limit sát mức steady-state 350 MiB ở 384 MiB nếu workload có temporary allocations 100 MiB khi serialize/export.

## 5. Real production scenario

API chạy ổn ở staging với ít data. Production export endpoint tạo large buffers; container memory vượt 512 MiB và bị OOMKilled. Kubernetes restart pod, khiến symptom bên ngoài là intermittent 502.

Team tăng replicas nhưng mỗi replica vẫn có cùng memory ceiling, nên lỗi không biến mất.

## 6. Failure scenario & troubleshooting

**Symptom** → pod restart, exit code 137/OOMKilled hoặc latency tăng dù CPU node còn rảnh.

**Evidence** → pod status/events, container memory working set, CPU throttling metrics.

**Hypothesis** → resource limit mismatch hoặc memory leak/allocation spike.

**Diagnosis** → correlate workload with resource metrics; phân biệt node pressure, container limit, GC heap và native memory.

**Fix** → sửa code/allocation hoặc điều chỉnh resource contract dựa trên evidence; không chỉ tăng limit vô hạn.

**Verification** → load test cùng data shape và quan sát throttling/OOM/restart count.

## 7. Common mistakes

- Copy requests/limits từ service khác.
- Requests = limits mọi workload mà không hiểu consequence.
- Chỉ nhìn average CPU.
- Tăng replicas để chữa per-pod memory leak.
- Set memory limit quá sát baseline.
- Không xem startup/migration spikes.

## 8. Alternatives

- Azure App Service/Container Apps khi team không cần trực tiếp quản lý Kubernetes scheduling semantics.
- Vertical scaling cho workload đơn giản.
- HPA/VPA có thể hỗ trợ nhưng không thay measurement/capacity reasoning.

## 9. Trade-offs

### Advantages

- Scheduler placement có cơ sở.
- Giảm noisy-neighbor risk.
- Giúp autoscaling/capacity planning rõ hơn.

### Costs / Risks

- Values sai gây throttling hoặc OOM.
- Requests quá cao lãng phí cluster capacity.
- Limits quá thấp biến burst hợp lệ thành failure.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu requests và limits không cùng mục đích.

### Middle

Debug `OOMKilled`, CPU throttling và pod events.

### Senior

Đặt capacity dựa trên profiling/load tests và .NET memory behavior.

### Technical Lead / Architect

Quyết định liệu Kubernetes complexity có đáng giá và thiết lập resource governance/SLO ở platform level.

## 11. Key takeaway

- Requests ảnh hưởng scheduling; limits ảnh hưởng runtime enforcement.
- Memory limit sai thường biểu hiện thành restart, CPU limit sai thường biểu hiện thành latency/throttling.
- Resource values phải đến từ measurement, không phải copy-paste YAML.

# 8. JavaScript event loop + microtasks: frontend race condition thường đến từ thứ tự completion chứ không chỉ từ “async chậm”

## 1. What is it?

JavaScript trên browser thường chạy application code trên một main thread với event loop. Async operations hoàn tất sẽ schedule callbacks/tasks; Promise continuations thường đi vào microtask queue.

Mental model:

```text
Call Stack
   |
Task queue ------>
Microtask queue -> chạy trước task tiếp theo sau stack hiện tại
   |
Render opportunity
```

Điểm quan trọng: async operations có thể hoàn tất theo thứ tự khác với thứ tự chúng được bắt đầu.

## 2. Why does it exist?

Browser cần xử lý UI events, timers, network callbacks và rendering mà không block toàn giao diện. Event loop cho phép concurrency về I/O mà không yêu cầu application code chạy multi-thread mặc định.

Nhưng UI state có thể bị stale request overwrite.

## 3. How does it work?

Ví dụ user search:

```text
t=0 request "a"
t=1 request "ab"
t=2 response "ab"
t=3 response "a"
```

Nếu mỗi response đều set state, kết quả cuối cùng lại là data cũ của "a".

Đây là race condition logic dù JavaScript code không chạy song song trên hai threads.

## 4. Practical implementation

Dùng `AbortController` hoặc request version:

```ts
let controller: AbortController | undefined;

async function search(query: string) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(`/api/search?q=${encodeURIComponent(query)}`, {
    signal: controller.signal
  });

  const data = await response.json();
  render(data);
}
```

Hoặc giữ monotonically increasing request ID và chỉ apply latest response.

## 5. Real production scenario

Vue autocomplete gọi API mỗi keystroke. Network mobile không ổn định làm request cũ trả về sau request mới. UI hiển thị suggestions không khớp input hiện tại.

Backend không sai; contract cũng không sai. Frontend thiếu stale-result control.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng quay lại dữ liệu cũ hoặc loading indicator sai trạng thái.

**Evidence** → DevTools Network cho thấy responses về out-of-order.

**Hypothesis** → multiple async operations cùng mutate state mà không có ownership/version rule.

**Diagnosis** → trace request start/end và state writes; không chỉ đặt breakpoint theo source order.

**Fix** → cancellation, request versioning hoặc state machine rõ ràng.

**Verification** → throttle network và tạo out-of-order responses có chủ đích.

## 7. Common mistakes

- Nghĩ single-threaded JavaScript không có race condition.
- Chỉ debounce nhưng không cancel/ignore in-flight request cũ.
- Một `finally` của request cũ set `loading=false` trong khi request mới vẫn chạy.
- Catch `AbortError` như application error.
- Không cleanup async work khi component unmount/route change.

## 8. Alternatives

- Debounce giảm số requests nhưng không tự xử lý race.
- Server-side pagination/search vẫn cần frontend stale-response control.
- State management libraries giúp tổ chức state nhưng không tự tạo cancellation semantics.

## 9. Trade-offs

### Advantages

- Cancellation giảm wasted network/backend work.
- Request versioning đơn giản và deterministic.

### Costs / Risks

- State lifecycle phức tạp hơn happy-path fetch.
- Không phải mọi operation nên cancel nếu side effect phải hoàn tất.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Promise/`await` không đảm bảo completion order.

### Middle

Implement cancellation/versioning cho search/filter/navigation.

### Senior

Thiết kế UI state để stale effects không overwrite current intent.

### Technical Lead / Architect

Định nghĩa frontend async conventions, observability và API semantics để cancellation/idempotency tương thích end-to-end.

## 11. Key takeaway

- Single-threaded không đồng nghĩa không có race condition.
- Race thường nằm ở thứ tự completion và state ownership.
- Throttle network là cách tốt để tái hiện bug async frontend.

# 10. API idempotency keys: biến retry từ nguồn double-charge thành behavior có kiểm soát ở write endpoints

## 1. What is it?

Idempotency key là client-generated/request-scoped identifier giúp server nhận biết nhiều lần gửi cùng một logical write operation và trả cùng outcome thay vì thực hiện side effect lại.

Mental model:

```text
POST /payments
Idempotency-Key: abc-123
        |
first request -> execute -> persist result
        |
retry same key -> return stored result
                  không charge lần hai
```

HTTP method `POST` tự nó không idempotent. Idempotency key thêm application-level semantics.

## 2. Why does it exist?

Distributed systems có ambiguous failure:

```text
Client -> Server: create payment
Server -> Provider: success
Server -> Client: connection lost
```

Client thấy timeout và không biết operation đã thành công hay chưa. Retry có thể duplicate side effect.

“No retry” cũng không giải quyết vì user có thể submit lại hoặc intermediary retry.

## 3. How does it work?

Server lưu record theo `(scope, idempotencyKey)` gồm:

- request fingerprint/hash;
- processing state;
- response/result reference;
- expiry policy.

Flow:

```text
receive key
  |
lookup
  |-- completed -> return previous result
  |-- processing -> reject/wait according policy
  |-- missing -> reserve key atomically -> execute
```

Nếu cùng key nhưng payload khác, server nên reject vì client đang reuse key sai semantic.

## 4. Practical implementation

Simplified data model:

```sql
CREATE TABLE IdempotencyRequests (
    Scope nvarchar(100) NOT NULL,
    IdempotencyKey nvarchar(100) NOT NULL,
    RequestHash char(64) NOT NULL,
    Status varchar(20) NOT NULL,
    ResultId uniqueidentifier NULL,
    CreatedAtUtc datetime2 NOT NULL,
    CONSTRAINT PK_IdempotencyRequests
        PRIMARY KEY (Scope, IdempotencyKey)
);
```

Unique constraint là critical để hai concurrent requests không cùng “thắng”.

Application nên persist idempotency state và business mutation trong transaction khi có thể.

## 5. Real production scenario

Mobile app gọi `POST /orders`. User đi qua mạng yếu; API tạo order nhưng response mất. App retry sau 3 giây.

Không có idempotency, hệ thống tạo hai orders. Với key ổn định cho một checkout attempt, retry trả lại order đã tạo.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate orders/payments dù client “chỉ bấm một lần”.

**Evidence** → access logs có repeated POSTs sau timeout; business records được tạo nhiều lần.

**Hypothesis** → retry path không có deduplication hoặc reservation không atomic.

**Diagnosis** → correlate request IDs, idempotency keys, database writes và provider transaction IDs.

**Fix** → atomic key reservation, payload fingerprint, durable result mapping và provider idempotency nếu available.

**Verification** → gửi concurrent duplicate requests + inject lost response và xác nhận chỉ một side effect.

## 7. Common mistakes

- Idempotency key chỉ lưu trong memory của một instance.
- Check-then-insert không có unique constraint nên race vẫn tạo duplicate.
- Reuse cùng key cho payload khác.
- Chỉ dedupe ở API nhưng external provider call vẫn không idempotent.
- Giữ keys vô thời hạn không có retention policy.
- Nhầm request ID/correlation ID với idempotency key.

## 8. Alternatives

- Natural business key/unique constraint nếu domain có identifier đủ mạnh.
- PUT với client-chosen resource ID trong resource-oriented APIs.
- At-most-once UI disabling không đủ tin cậy trong distributed systems.

## 9. Trade-offs

### Advantages

- Retry-safe cho critical writes.
- Giảm duplicate business side effects.
- Cho phép client phục hồi từ ambiguous network failures.

### Costs / Risks

- Cần persistent deduplication state.
- Request fingerprint/result retention tăng storage/complexity.
- Endpoint semantics phải rõ về scope và expiry.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không đồng nghĩa server chưa thực hiện operation.

### Middle

Implement idempotency key + unique constraint + repeated-response behavior.

### Senior

Thiết kế atomic reservation, concurrent duplicates, payload mismatch và external provider idempotency.

### Technical Lead / Architect

Xác định endpoints nào thật sự cần idempotency contract và chuẩn hóa semantics xuyên clients, APIs, messaging và external integrations.

## 11. Key takeaway

- Retry của write operation cần idempotency, không chỉ exponential backoff.
- Unique constraint/durable reservation quan trọng để chống concurrent duplicate.
- Idempotency phải đi xuyên tới side effect thực sự, không chỉ dừng ở HTTP layer.
