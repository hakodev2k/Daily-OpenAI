# 1. C# source-generated logging với `LoggerMessage`: giảm allocation ở hot path mà vẫn giữ structured logs

## 1. What is it?

`LoggerMessage` source generation là cơ chế của .NET giúp tạo code logging strongly-typed từ các partial methods được annotate bằng `LoggerMessageAttribute`.

Thay vì mỗi lần gọi log phải parse message template, tạo `object[]`, box value types hoặc format string không cần thiết, compiler/source generator sinh sẵn implementation tối ưu.

Mental model:

```text
Traditional logging call
    ↓
parse template / build arguments / possible boxing
    ↓
ILogger pipeline

Source-generated logging
    ↓
pre-generated strongly-typed logging method
    ↓
ILogger pipeline
```

Đây là optimization ở logging hot path, nhưng lợi ích lớn hơn chỉ performance: event ID, template và parameter names trở thành contract rõ hơn trong code.

## 2. Why does it exist?

Logging trong server application thường nằm trên mọi request path. Một log call riêng lẻ rẻ, nhưng vài chục log events trên hàng chục nghìn requests/second có thể tạo allocation đáng kể.

Đặc biệt, code kiểu:

```csharp
_logger.LogInformation(
    "Processed order {OrderId} in {ElapsedMs} ms",
    orderId,
    elapsedMs);
```

có thể phải xử lý params array và boxing tùy overload/runtime path. Nếu log level bị disable, ta vẫn muốn overhead gần tối thiểu.

Source generation đưa phần lớn template preparation sang build time.

## 3. How does it work?

Khai báo partial method:

```csharp
public static partial class OrderLogs
{
    [LoggerMessage(
        EventId = 1201,
        Level = LogLevel.Information,
        Message = "Processed order {OrderId} in {ElapsedMs} ms")]
    public static partial void OrderProcessed(
        ILogger logger,
        Guid orderId,
        double elapsedMs);
}
```

Generator tạo implementation tương ứng khi build.

Structured property names `OrderId` và `ElapsedMs` được giữ nguyên để sink như Application Insights, Seq hoặc Elasticsearch có thể index/filter chúng.

## 4. Practical implementation

Trong service:

```csharp
public sealed class OrderProcessor(
    ILogger<OrderProcessor> logger,
    IOrderRepository repository)
{
    public async Task ProcessAsync(
        Guid orderId,
        CancellationToken cancellationToken)
    {
        var started = Stopwatch.GetTimestamp();

        var order = await repository.GetAsync(
            orderId,
            cancellationToken);

        if (order is null)
        {
            OrderLogs.OrderNotFound(logger, orderId);
            return;
        }

        await order.ProcessAsync(cancellationToken);

        var elapsed = Stopwatch.GetElapsedTime(started);
        OrderLogs.OrderProcessed(
            logger,
            orderId,
            elapsed.TotalMilliseconds);
    }
}

public static partial class OrderLogs
{
    [LoggerMessage(
        EventId = 1200,
        Level = LogLevel.Warning,
        Message = "Order {OrderId} was not found")]
    public static partial void OrderNotFound(
        ILogger logger,
        Guid orderId);

    [LoggerMessage(
        EventId = 1201,
        Level = LogLevel.Information,
        Message = "Processed order {OrderId} in {ElapsedMs} ms")]
    public static partial void OrderProcessed(
        ILogger logger,
        Guid orderId,
        double elapsedMs);
}
```

Production code nên giữ template names ổn định vì dashboard/query có thể phụ thuộc chúng.

## 5. Real production scenario

Một high-throughput API có 20.000 requests/second và nhiều debug/information logs ở request pipeline. Allocation profiling cho thấy logging chiếm tỷ lệ đáng kể Gen 0 allocations dù phần lớn debug logs bị filter.

Team chuyển các hot-path events quan trọng sang source-generated logging. Allocation rate giảm và event taxonomy trở nên nhất quán hơn nhờ event IDs cố định.

Điểm quan trọng: team không rewrite toàn bộ logging chỉ để “modernize”; họ bắt đầu từ paths profiler chứng minh có cost.

## 6. Failure scenario & troubleshooting

**Symptom** → telemetry backend có rất nhiều fields gần giống nhau: `OrderID`, `orderId`, `OrderId`, khiến queries khó thống nhất.

**Evidence** → message templates không có naming convention; cùng business identifier dùng nhiều property names.

**Hypothesis** → logging implementation được tối ưu nhưng telemetry contract không được govern.

**Diagnosis** → inventory event IDs/templates/properties trên critical services.

**Fix** → chuẩn hóa semantic property names và event ranges; source-generated methods trở thành reusable logging contract.

**Verification** → query telemetry theo một property name duy nhất và kiểm tra dashboards/alerts còn hoạt động sau deploy.

## 7. Common mistakes

* Dùng string interpolation: `_logger.LogInformation($"Order {id}")`, làm mất structured property.
* Source-generate mọi log call dù workload không cần optimization.
* Đưa PII/secrets vào structured fields vì “dễ search”.
* Thay đổi property names tùy ý giữa releases.
* Log exception message nhưng bỏ exception object, làm mất stack trace.
* Dùng logging để thay metrics cho high-volume counters.

## 8. Alternatives

Normal `ILogger` extension methods hoàn toàn đủ cho phần lớn business code. `LoggerMessage.Define` cung cấp cached delegates nhưng verbose hơn. Với metrics/SLO, dùng `Meter`/OpenTelemetry metrics thay vì log mỗi request rồi aggregate lại.

## 9. Trade-offs

### Advantages

* Giảm parsing/allocation trên hot logging path.
* Strongly-typed parameters.
* Event ID/template được centralize.
* Structured telemetry nhất quán hơn.

### Costs / Risks

* Tăng số partial methods và boilerplate.
* Có thể over-optimize code không nóng.
* Event taxonomy cần governance.
* Structured logs vẫn có storage/cardinality cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu structured logging khác string formatting và biết giữ property names có nghĩa.

### Middle

Dùng `LoggerMessage` cho hot/repeated events và truyền exception đúng cách.

### Senior

Profile allocation, thiết kế event IDs, privacy/cardinality boundaries và correlation với traces.

### Technical Lead / Architect

Đặt logging conventions organization-wide: semantic fields, PII policy, event ownership và khi nào log/metric/trace là signal phù hợp.

## 11. Key takeaway

* Source-generated logging là optimization có mục tiêu, không phải default bắt buộc cho mọi line.
* Structured property names là telemetry contract.
* Tối ưu logging không có ý nghĩa nếu log volume/cardinality vẫn không được kiểm soát.

# 2. ASP.NET Core Output Caching: cache response đúng key, đúng user và đúng invalidation boundary

## 1. What is it?

Output Caching lưu kết quả HTTP response đã tạo để request tương đương sau đó có thể nhận response từ cache mà không chạy lại toàn bộ endpoint/business/data path.

Mental model:

```text
Request
  ↓
cache key calculation
  ├─ HIT  → cached HTTP response
  └─ MISS → endpoint → DB/API → response
                         ↓
                       cache
```

Khác cache object trong service, output cache nằm gần HTTP boundary và cache representation cuối cùng của endpoint.

## 2. Why does it exist?

Một catalog endpoint có thể tạo cùng JSON cho hàng nghìn anonymous users. Nếu mỗi request lại query database, map DTO và serialize, application đang lặp lại work không cần thiết.

Output cache có thể giảm:

* database reads;
* serialization CPU;
* downstream calls;
* response latency.

Nhưng cache ở HTTP boundary rất dễ sai nếu response phụ thuộc user, tenant, locale, query string hoặc authorization context mà cache key không phản ánh đầy đủ.

## 3. How does it work?

ASP.NET Core Output Caching áp policy để xác định:

* request nào được cache;
* key vary theo route/query/header nào;
* TTL;
* tags dùng cho invalidation;
* response nào không được cache.

Ví dụ hai request:

```text
GET /products?category=keyboard&lang=en
GET /products?category=keyboard&lang=vi
```

Nếu `lang` ảnh hưởng payload nhưng không nằm trong cache key, user có thể nhận representation sai.

## 4. Practical implementation

```csharp
builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("catalog", builder =>
    {
        builder
            .Expire(TimeSpan.FromMinutes(2))
            .SetVaryByQuery("category", "page")
            .SetVaryByHeader("Accept-Language")
            .Tag("catalog");
    });
});

var app = builder.Build();
app.UseOutputCache();

app.MapGet("/products", GetProducts)
   .CacheOutput("catalog");
```

Khi catalog mutation xảy ra, application có thể evict theo tag thay vì chờ TTL nếu freshness requirement cần như vậy.

User-specific endpoints thường không nên cache shared representation trừ khi partition/key policy chứng minh isolation an toàn.

## 5. Real production scenario

Một public product-list endpoint được gọi 5.000 RPS nhưng underlying catalog chỉ thay đổi vài lần mỗi phút. Trước caching, SQL Server đọc cùng dữ liệu lặp lại và JSON serialization chiếm CPU đáng kể.

Sau khi output cache 30–120 giây với đúng vary keys, DB load giảm mạnh.

Tuy nhiên `/me/recommendations` không được đưa vào cùng policy vì response phụ thuộc authenticated user. Team chọn service-level cache partitioned theo user cho use case đó thay vì shared HTTP output cache.

## 6. Failure scenario & troubleshooting

**Symptom** → user A thỉnh thoảng thấy dữ liệu của user B.

**Evidence** → endpoint authenticated được output-cache nhưng cache key không vary theo identity/tenant.

**Hypothesis** → cache isolation boundary sai.

**Diagnosis** → capture request headers/claims và cache policy; reproduce hai identities cùng URL.

**Fix** → không shared-cache personalized response hoặc partition cache key bằng server-trusted identity dimension.

**Verification** → integration test cross-user/cross-tenant requests và negative caching cases.

## 7. Common mistakes

* Cache authenticated response mà không hiểu identity isolation.
* Bỏ query/header ảnh hưởng representation khỏi key.
* TTL rất dài nhưng không có invalidation ownership.
* Cache error response hoặc transient failure ngoài ý muốn.
* Dùng cache để che query chậm thay vì sửa query khi data không cacheable.
* Cache quá nhiều unique keys làm memory/backend cache phình lớn.

## 8. Alternatives

CDN/edge caching phù hợp public content có HTTP cache semantics rõ. Distributed/object cache ở service layer phù hợp dữ liệu reuse giữa nhiều endpoints. Database optimization phù hợp khi query vẫn phải authoritative mỗi request.

## 9. Trade-offs

### Advantages

* Giảm application/DB work đáng kể.
* Cache ngay serialized representation.
* Latency thấp cho repeated requests.

### Costs / Risks

* Stale data.
* Cache key correctness là security/correctness concern.
* Invalidation complexity.
* High-cardinality keys có thể triệt tiêu hit rate.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu cache hit bỏ qua phần lớn endpoint execution và có thể trả dữ liệu cũ.

### Middle

Cấu hình TTL, vary keys và cache only safe endpoints.

### Senior

Thiết kế invalidation, tenant/user isolation, hit-rate metrics và stale-data policy.

### Technical Lead / Architect

Quyết định layer cache: browser/CDN/output/service/database-derived cache, cùng ownership và freshness SLA cho từng data class.

## 11. Key takeaway

* Cache key là một phần của correctness và security.
* Shared output cache phù hợp nhất với representation dùng chung và bounded variation.
* TTL không thay thế invalidation strategy khi business yêu cầu freshness nhanh.

# 3. EF Core Change Tracker + identity resolution: khi tracking giúp correctness và khi nó trở thành memory/performance cost

## 1. What is it?

EF Core Change Tracker theo dõi entity instances đã materialize để phát hiện thay đổi và tạo `INSERT`/`UPDATE`/`DELETE` khi `SaveChanges` chạy.

Nó cũng cung cấp identity resolution: trong một tracked query/context, cùng database row thường được biểu diễn bởi cùng một entity instance.

Mental model:

```text
Database row Id=42
      ↓ materialize
Change Tracker identity map
      ↓
Customer instance #42
      ↓
mutate properties
      ↓
SaveChanges → SQL UPDATE
```

## 2. Why does it exist?

ORM cần biết original/current values và relationship state để biến object graph mutation thành database changes.

Identity resolution cũng tránh scenario một order graph chứa nhiều object instances khác nhau đại diện cùng customer, làm relationship fix-up/conflict khó kiểm soát.

Nhưng với read-only queries trả hàng chục nghìn rows, tracking every entity tạo memory và CPU cost không cần thiết.

## 3. How does it work?

Default tracking query:

```csharp
var order = await db.Orders
    .Include(x => x.Customer)
    .SingleAsync(x => x.Id == id, ct);
```

Entity được đăng ký trong tracker. Nếu query lại cùng order trong context, EF có thể reuse tracked instance.

Read-only:

```csharp
var rows = await db.Orders
    .AsNoTracking()
    .Select(x => new OrderListItem(...))
    .ToListAsync(ct);
```

`AsNoTrackingWithIdentityResolution()` là lựa chọn trung gian: không giữ entities trong context sau query, nhưng trong quá trình materialization vẫn deduplicate identity khi graph cần.

## 4. Practical implementation

Command path:

```csharp
public async Task RenameCustomerAsync(
    Guid customerId,
    string name,
    CancellationToken ct)
{
    var customer = await db.Customers
        .SingleAsync(x => x.Id == customerId, ct);

    customer.Rename(name);
    await db.SaveChangesAsync(ct);
}
```

Query path:

```csharp
public Task<List<CustomerSummary>> SearchAsync(
    string term,
    CancellationToken ct) =>
    db.Customers
      .AsNoTracking()
      .Where(x => x.Name.Contains(term))
      .Select(x => new CustomerSummary(x.Id, x.Name))
      .ToListAsync(ct);
```

`DbContext` nên ngắn hạn theo unit-of-work/request; không giữ tracker sống hàng giờ như application cache.

## 5. Real production scenario

Background import xử lý 500.000 records bằng một `DbContext` duy nhất. Mỗi batch query/add entities nhưng không clear tracker. Process memory tăng liên tục và `DetectChanges` ngày càng chậm.

Root cause không phải memory leak theo nghĩa object “không thể release”; context vẫn giữ references theo design.

Giải pháp là context/batch lifetime ngắn, set-based operations khi phù hợp và không track read-only data.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng query càng chạy lâu càng chậm trong long-running worker.

**Evidence** → `ChangeTracker.Entries().Count()` tăng theo mỗi batch; heap dump cho thấy entities retained bởi `DbContext`.

**Hypothesis** → oversized unit of work.

**Diagnosis** → đo tracked entity count, context lifetime, `DetectChanges` duration và allocation.

**Fix** → new context per bounded batch hoặc `ChangeTracker.Clear()` khi semantics cho phép; dùng no-tracking queries cho read paths.

**Verification** → soak test, memory plateau và stable batch latency.

## 7. Common mistakes

* `AsNoTracking()` ở command path rồi attach graph mù quáng để update.
* Một singleton `DbContext` cho toàn application.
* Dùng tracking cho report/export read-only khổng lồ.
* Gọi `Update(entityFromClient)` trên detached graph và mark mọi field modified.
* Nhầm identity resolution với database uniqueness/concurrency protection.

## 8. Alternatives

Dapper/raw SQL phù hợp read path cần mapping nhẹ. `ExecuteUpdate`/`ExecuteDelete` phù hợp set-based mutation. Explicit SQL/stored procedure phù hợp batch operations phức tạp.

## 9. Trade-offs

### Advantages

* Unit-of-work ergonomics tốt.
* Relationship fix-up và identity resolution.
* Automatic change detection.

### Costs / Risks

* Memory tăng theo số tracked entities.
* `DetectChanges`/graph management có CPU cost.
* Long-lived context tạo stale state và concurrency issues.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu tracked entity khác DTO/read-only projection.

### Middle

Chọn tracking/no-tracking theo use case và giữ `DbContext` lifetime ngắn.

### Senior

Phân tích tracker memory, detached graph update và batch-unit boundaries.

### Technical Lead / Architect

Đặt conventions cho command/query paths, bulk operations và context ownership để codebase không dựa vào tracking một cách vô thức.

## 11. Key takeaway

* Change Tracker là correctness/ergonomics feature có measurable cost.
* Track khi cần mutate aggregate; project/no-track khi chỉ đọc.
* `DbContext` là unit-of-work, không phải application cache.

# 4. SQL Server memory grant + tempdb spill: vì sao query có thể chậm dù CPU và index trông vẫn “ổn”

## 1. What is it?

Một số SQL operators như Sort, Hash Join và Hash Aggregate cần working memory. SQL Server optimizer ước lượng lượng memory query cần và cấp **memory grant** trước execution.

Nếu grant quá nhỏ, operator có thể spill intermediate data xuống `tempdb`. Nếu grant quá lớn, query giữ memory dư và làm các queries khác phải chờ.

Mental model:

```text
estimated rows + row width
        ↓
memory grant
        ↓
Sort / Hash operation
   ├─ đủ memory → in-memory
   └─ thiếu      → spill to tempdb
```

## 2. Why does it exist?

Database không thể cho mỗi query dùng RAM vô hạn. Nó phải phân bổ memory giữa concurrent requests.

Optimizer dựa trên cardinality estimates. Vì vậy statistics sai, parameter skew hoặc expression khó estimate có thể khiến grant khác xa nhu cầu thật.

## 3. How does it work?

Ví dụ report:

```sql
SELECT CustomerId, SUM(Total) AS Revenue
FROM Orders
WHERE CreatedAt >= @From
GROUP BY CustomerId
ORDER BY Revenue DESC;
```

Hash aggregate và sort có thể cần memory lớn. Nếu estimated 10.000 rows nhưng actual 10 triệu rows, granted memory có thể thiếu và operator ghi partitions/runs xuống `tempdb`.

Actual Execution Plan thường hiển thị spill warnings và memory grant information.

## 4. Practical implementation

Bắt đầu bằng evidence:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

Kiểm tra Actual Plan:

* estimated vs actual rows;
* requested/granted/used memory;
* spill warnings;
* sort/hash operators;
* tempdb I/O;
* waits như memory grant waits khi concurrency cao.

Query Store giúp xác định plan regression theo thời gian.

Fix có thể là:

* statistics/index/access path tốt hơn;
* projection hẹp hơn;
* giảm rows trước sort/hash;
* rewrite query;
* xử lý parameter-sensitive workload;
* resource governance khi reporting tranh memory với OLTP.

## 5. Real production scenario

Một dashboard query chạy 300 ms buổi sáng nhưng 20 giây cuối tháng. CPU SQL không max, index scans không quá đáng ngờ.

Actual Plan cuối tháng cho thấy sort spill hàng GB xuống `tempdb` vì cardinality estimate thấp. Khi nhiều users chạy cùng report, `tempdb` I/O và memory contention làm p99 tăng mạnh.

Team sửa predicate/statistics và tách reporting workload khỏi transactional peak thay vì chỉ tăng timeout.

## 6. Failure scenario & troubleshooting

**Symptom** → query latency cao, `tempdb` I/O tăng, CPU không tương xứng.

**Evidence** → spill warning trong actual plan; actual rows lớn hơn estimate nhiều lần.

**Hypothesis** → insufficient memory grant do cardinality mismatch.

**Diagnosis** → so estimated/actual rows, memory grant, sort/hash spill level, data distribution.

**Fix** → sửa estimate/access pattern trước; tránh dùng query hint như giải pháp đầu tiên.

**Verification** → chạy representative parameters và concurrency test; spill phải giảm và p95/p99 cải thiện.

## 7. Common mistakes

* Thấy `tempdb` cao rồi tăng disk mà không tìm query spill.
* Chỉ xem estimated plan, không xem actual runtime evidence.
* Tăng server memory nhưng query vẫn estimate sai.
* Dùng `MAX_GRANT_PERCENT`/hints đại trà.
* Không test dữ liệu cuối tháng/enterprise tenant.
* Nhầm spill là nguyên nhân duy nhất; đôi khi spill chỉ là symptom của cardinality/index problem.

## 8. Alternatives

Pre-aggregation/materialized reporting tables, columnstore, read replica/warehouse hoặc asynchronous report generation phù hợp workload analytical lớn hơn việc ép OLTP query xử lý mọi thứ trực tiếp.

## 9. Trade-offs

### Advantages

Memory grants cho phép database điều phối RAM giữa concurrent queries và chạy sort/hash hiệu quả khi estimate tốt.

### Costs / Risks

Estimate sai gây spill hoặc over-grant. Large grants cũng có thể làm concurrency giảm dù từng query chạy nhanh riêng lẻ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu query performance không chỉ phụ thuộc index; sort/hash cũng cần memory.

### Middle

Đọc actual plan, spill warning, statistics I/O/time và estimated-vs-actual rows.

### Senior

Liên kết cardinality, memory grants, tempdb I/O và workload concurrency.

### Technical Lead / Architect

Quyết định workload nào còn phù hợp OLTP SQL và workload nào cần reporting/read architecture riêng để tránh tranh tài nguyên.

## 11. Key takeaway

* Spill là disk fallback khi working memory không đủ.
* Root cause thường nằm ở estimate/data shape, không phải chỉ ở `tempdb`.
* Performance diagnosis phải đo actual plan + workload concurrency, không chỉ single-query duration.

# 5. Materialized Read Model: tách read workload khỏi transactional model mà không biến CQRS thành distributed over-engineering

## 1. What is it?

Materialized Read Model là dữ liệu được chuẩn bị sẵn theo shape mà read use case cần, thay vì mỗi request join/aggregate từ transactional schema.

Nó có thể nằm cùng database, table riêng, view indexed/materialized, cache, search index hoặc data store riêng.

Mental model:

```text
Transactional model
Orders + Customers + Payments
          ↓ projection
OrderDashboardReadModel
          ↓
fast query shaped for UI/API
```

Đây là một kỹ thuật read optimization. Nó không bắt buộc phải kéo theo microservices, event sourcing hoặc hai database ngay từ đầu.

## 2. Why does it exist?

Write model thường tối ưu correctness, normalization và transaction boundaries. UI/report thường cần shape khác: nhiều aggregates, counts, summaries, search fields.

Nếu mỗi page load chạy 12 joins, multiple aggregates và external lookups, read path có thể vừa chậm vừa coupling mạnh vào transactional schema.

Read model cho phép trả đúng dữ liệu cần với query đơn giản hơn.

## 3. How does it work?

Có hai consistency models chính:

**Synchronous projection**

```text
transaction writes business state + read table
→ strong/near-strong consistency
→ transaction rộng hơn
```

**Asynchronous projection**

```text
business transaction commits
→ event/outbox
→ projector updates read model
→ eventual consistency
```

Điểm kiến trúc quan trọng là xác định source of truth. Read model thường là derived state và phải rebuild được hoặc reconcile được.

## 4. Practical implementation

Trong modular monolith, có thể bắt đầu bằng table read model cùng SQL Server:

```sql
CREATE TABLE ProjectDashboardReadModel
(
    ProjectId uniqueidentifier PRIMARY KEY,
    Title nvarchar(200) NOT NULL,
    OpenTaskCount int NOT NULL,
    OverdueTaskCount int NOT NULL,
    LastActivityAt datetime2 NOT NULL,
    ProjectionVersion bigint NOT NULL
);
```

Projector xử lý domain/integration event idempotently:

```csharp
public async Task HandleAsync(
    TaskCompleted message,
    CancellationToken ct)
{
    await db.ProjectDashboard
        .Where(x => x.ProjectId == message.ProjectId &&
                    x.ProjectionVersion < message.Sequence)
        .ExecuteUpdateAsync(setters => setters
            .SetProperty(x => x.OpenTaskCount, x => x.OpenTaskCount - 1)
            .SetProperty(x => x.LastActivityAt, message.OccurredAt)
            .SetProperty(x => x.ProjectionVersion, message.Sequence), ct);
}
```

Production implementation cần strategy cho missing/out-of-order events hoặc rebuild.

## 5. Real production scenario

Project dashboard cần project metadata, task counts, overdue counts, last activity và owner summary. Query normalized transactional schema mất 1–2 giây ở customers lớn.

Team tạo một read table cập nhật async từ Outbox events. Dashboard query còn một indexed lookup.

UI chấp nhận lag vài giây vì đây là summary; khi user mở task detail, system đọc authoritative transactional data.

## 6. Failure scenario & troubleshooting

**Symptom** → dashboard nói 12 open tasks nhưng task list authoritative chỉ có 11.

**Evidence** → projector checkpoint đã tiến qua event sequence nhưng một update failed hoặc duplicate/out-of-order event xử lý sai.

**Hypothesis** → projection consistency/replay semantics lỗi.

**Diagnosis** → compare source event stream/outbox sequence với projection version; inspect failed messages and retries.

**Fix** → idempotent projection, deterministic rebuild/reconciliation job, explicit checkpoint semantics.

**Verification** → replay events từ clean read model và compare result với source of truth.

## 7. Common mistakes

* Biến read model thành source of truth rồi update trực tiếp từ nhiều nơi.
* Tạo separate database/service trước khi read complexity thực sự cần.
* Không có rebuild/reconciliation story.
* Event handlers không idempotent.
* UI đòi strong consistency nhưng architecture lại async mà không nói rõ.
* Duplicate mọi field “đề phòng sau này”.

## 8. Alternatives

Projection LINQ/SQL trực tiếp phù hợp read đơn giản. Database view/stored query đủ cho nhiều use cases. Cache thích hợp repeated data nhưng khác read model vì cache lifecycle/freshness semantics thường khác. Search index phù hợp full-text/faceted retrieval.

## 9. Trade-offs

### Advantages

* Read query đơn giản và nhanh.
* Model theo UI/API need.
* Giảm coupling read path với complex transactional joins.
* Có thể scale read workload độc lập nếu sau này cần.

### Costs / Risks

* Duplicate derived data.
* Eventual consistency nếu async.
* Rebuild/monitoring/projector complexity.
* Schema evolution phải quản lý cả projection.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu read model là derived representation, không phải copy database vô mục đích.

### Middle

Tạo projection theo query need và giữ source of truth rõ ràng.

### Senior

Thiết kế idempotency, checkpoints, rebuild và consistency SLA.

### Technical Lead / Architect

Quyết định khi nào read complexity đủ lớn để justify materialization và khi nào query trực tiếp vẫn đơn giản hơn, tránh premature CQRS infrastructure.

## 11. Key takeaway

* Tách read shape khỏi write model là công cụ, không phải lý do để lập tức tách service/database.
* Derived state phải có rebuild/reconciliation strategy.
* Consistency lag phải là product/engineering decision explicit.

# 6. Azure Blob Storage data protection: soft delete, versioning, lifecycle và immutability cho dữ liệu production

## 1. What is it?

Blob data protection là tập các cơ chế giúp giảm rủi ro mất hoặc ghi đè dữ liệu: soft delete, blob versioning, snapshots, lifecycle management, redundancy và immutable storage policies.

Mental model:

```text
Application write/delete
        ↓
Blob Storage account
  ├─ current blob
  ├─ previous versions
  ├─ soft-deleted state
  └─ lifecycle/retention policy
```

Backup/data protection không phải một checkbox; mỗi mechanism bảo vệ một failure mode khác nhau.

## 2. Why does it exist?

Production data có thể mất do:

* application bug gọi delete sai;
* user xóa nhầm;
* overwrite file với content lỗi;
* credential compromise;
* retention job sai;
* compliance yêu cầu dữ liệu không được sửa/xóa trong thời gian nhất định.

Replication giữa datacenters không bảo vệ khỏi logical delete: delete cũng có thể được replicate rất chính xác.

## 3. How does it work?

**Soft delete** giữ deleted blob trong retention window để restore.

**Versioning** tạo version cũ khi blob bị overwrite/update.

**Lifecycle management** tự chuyển tier hoặc xóa versions/objects theo age/rules.

**Immutability/WORM** ngăn modify/delete trong retention scope, phù hợp audit/compliance records nhưng phải dùng cẩn thận vì operation có thể cố ý không reversible.

Các features này nên được thiết kế cùng business retention policy.

## 4. Practical implementation

Application nên lưu blob identity/version/ETag trong metadata database khi version correctness quan trọng:

```csharp
var response = await blob.UploadAsync(
    stream,
    overwrite: false,
    cancellationToken);

var properties = await blob.GetPropertiesAsync(
    cancellationToken: cancellationToken);

await metadataRepository.SaveAsync(new FileRecord(
    blobName,
    properties.Value.ETag.ToString(),
    properties.Value.VersionId),
    cancellationToken);
```

Restore workflow phải được test, không chỉ enable feature trên portal.

Lifecycle rule cần tránh xóa version đang nằm trong legal/business retention window.

## 5. Real production scenario

Document management system cho users upload contracts. Một deployment bug chạy cleanup với predicate sai và delete hàng nghìn blobs.

Geo-redundancy không giúp vì logical delete replicate sang secondary. Soft delete 14 ngày cho phép restore.

Với audit exports bắt buộc giữ 7 năm, immutable policy phù hợp hơn soft delete vì requirement là chống cả intentional modification trong retention period.

## 6. Failure scenario & troubleshooting

**Symptom** → storage cost tăng đều dù active file count ổn định.

**Evidence** → hàng triệu old versions và soft-deleted blobs chưa lifecycle cleanup.

**Hypothesis** → protection được bật nhưng retention lifecycle không được budget/govern.

**Diagnosis** → inventory current versions, previous versions, snapshots, deleted state và tier distribution.

**Fix** → lifecycle rules phù hợp recovery SLA/compliance; không xóa blindly dữ liệu có legal hold.

**Verification** → restore drill + cost trend monitoring + policy test trên non-production account.

## 7. Common mistakes

* Nghĩ replication = backup.
* Enable versioning nhưng không lifecycle old versions.
* Retention quá ngắn so với thời gian phát hiện incident.
* Immutability trên container sai scope rồi không thể cleanup theo nhu cầu vận hành.
* Không test restore permissions/workflow.
* App database delete metadata trước khi blob recovery workflow có thể định vị object.

## 8. Alternatives

Backup/export sang account/subscription khác tăng isolation cho high-value data. Azure Files/database backup có semantics khác. Application-level recycle bin phù hợp user workflow nhưng không thay storage-level protection.

## 9. Trade-offs

### Advantages

* Recovery từ accidental delete/overwrite.
* Version history hỗ trợ forensic/rollback.
* Immutability hỗ trợ compliance/tamper resistance.

### Costs / Risks

* Storage cost tăng.
* Lifecycle policy phức tạp.
* Restore operation cần tooling/permissions.
* Immutability có thể hạn chế legitimate deletion.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu redundancy không bảo vệ khỏi logical corruption/delete.

### Middle

Biết soft delete/versioning/lifecycle khác nhau và test restore.

### Senior

Thiết kế retention, recovery drills, identity boundaries và cost controls.

### Technical Lead / Architect

Map business RPO/RTO/compliance vào layered protection strategy thay vì bật features rời rạc.

## 11. Key takeaway

* Data protection phải map tới failure modes cụ thể.
* Versioning/soft delete không miễn phí; lifecycle và restore drills là bắt buộc.
* Replication bảo vệ infrastructure failure, không tự bảo vệ logical mistake.

# 7. Docker multi-stage build + non-root runtime: giảm image size, attack surface và deployment drift

## 1. What is it?

Multi-stage build dùng nhiều stages trong Dockerfile: build/test/publish ở image có SDK/toolchain, sau đó copy artifact cần thiết sang runtime image nhỏ hơn.

Non-root runtime chạy process bằng user không có root privileges trong container.

Mental model:

```text
SDK/build image
  ├─ compiler
  ├─ source
  ├─ NuGet cache
  └─ publish output
         ↓ copy only output
runtime image
  ├─ app binaries
  └─ minimal runtime
```

## 2. Why does it exist?

Nếu production image chứa SDK, source code, build tools và package manager không cần thiết:

* image lớn hơn;
* pull/start chậm hơn;
* nhiều packages tăng vulnerability surface;
* attacker có thêm tools nếu compromise container.

Chạy root làm tăng blast radius khi process exploit có thể truy cập filesystem/capabilities nhiều hơn cần thiết.

## 3. How does it work?

Build stage:

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app/publish
```

Runtime stage:

```dockerfile
FROM mcr.microsoft.com/dotnet/aspnet AS runtime
WORKDIR /app
COPY --from=build /app/publish .
USER app
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

Exact base image/tag cần được pin/govern theo project policy để build reproducible và patch cadence rõ.

## 4. Practical implementation

Tối ưu build cache bằng cách copy project files/restore trước source code thay đổi thường xuyên:

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk AS build
WORKDIR /src

COPY MyApi.csproj ./
RUN dotnet restore MyApi.csproj

COPY . ./
RUN dotnet publish MyApi.csproj \
    -c Release \
    -o /out \
    --no-restore

FROM mcr.microsoft.com/dotnet/aspnet AS runtime
WORKDIR /app
COPY --from=build /out ./
USER app
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

`.dockerignore` phải loại `.git`, local secrets, test artifacts, node_modules/bin/obj không cần trong context.

## 5. Real production scenario

Một .NET service image 1.8 GB vì team dùng SDK image làm production image và copy toàn repository. CI push/pull chậm, vulnerability scanner báo hàng trăm CVEs từ build tools không chạy ở runtime.

Multi-stage publish giảm image đáng kể và số packages cần patch. Chuyển non-root phát hiện thêm một bug: app ghi file vào `/app` nhưng user runtime không có quyền. Team sửa ownership và chuyển temporary data sang writable volume/path đúng thiết kế.

## 6. Failure scenario & troubleshooting

**Symptom** → container chạy local bằng root nhưng crash production sau chuyển non-root với `Permission denied`.

**Evidence** → app ghi logs/uploads/temp vào path chỉ root writable.

**Hypothesis** → filesystem ownership/runtime write assumptions chưa explicit.

**Diagnosis** → inspect `USER`, file permissions, mounted volumes và paths app ghi.

**Fix** → tạo/chown đúng runtime directories hoặc dùng external storage/volume; không quay lại root chỉ để “fix nhanh”.

**Verification** → run container locally/CI với cùng user/security constraints production.

## 7. Common mistakes

* Dùng `latest` tag không kiểm soát.
* Copy secrets vào build context/image layer.
* `apt install` nhiều debug tools vào runtime image “để phòng khi cần”.
* Chạy root vì permission setup khó.
* Dockerfile build khác CI release artifact, tạo hai supply chains.
* Không scan base image/dependencies.

## 8. Alternatives

Framework-dependent deployment trên VM/App Service có thể phù hợp nếu containerization không tạo giá trị. Distroless/chiseled images giảm surface hơn nữa nhưng debugging/compatibility cần đánh giá. Buildpacks tự động hóa image creation nhưng vẫn cần hiểu security/runtime ownership.

## 9. Trade-offs

### Advantages

* Image nhỏ hơn và pull nhanh hơn.
* Attack surface giảm.
* Build/runtime responsibilities rõ.
* Non-root giảm privilege.

### Costs / Risks

* Dockerfile/build cache cần maintain.
* Minimal images khó debug trực tiếp.
* Native dependencies/timezone/certificates phải kiểm tra.
* Non-root yêu cầu filesystem discipline.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu build image và runtime image có trách nhiệm khác nhau.

### Middle

Viết multi-stage Dockerfile, `.dockerignore` và chạy non-root.

### Senior

Tối ưu cache, supply-chain scanning, filesystem ownership và reproducibility.

### Technical Lead / Architect

Chuẩn hóa base images, patch cadence, provenance/signing và runtime security policy cho toàn engineering organization.

## 11. Key takeaway

* Production image chỉ nên chứa thứ cần để chạy application.
* Non-root phải là runtime assumption được test, không phải hardening thêm sau cùng.
* Container image là software supply-chain artifact, không chỉ packaging format.

# 8. Git `revert`, `reset`, `cherry-pick`: chọn đúng cơ chế khi sửa release hoặc backport production fix

## 1. What is it?

Ba lệnh đều thay đổi lịch sử/working state theo cách rất khác:

* `git revert` tạo commit mới đảo ngược effect của commit cũ;
* `git reset` di chuyển branch reference/HEAD và có thể thay index/working tree;
* `git cherry-pick` áp effect của một commit lên branch hiện tại dưới commit mới.

Mental model:

```text
revert      = preserve history + add inverse commit
reset       = move branch pointer
cherry-pick = copy selected change onto another history
```

## 2. Why does it exist?

Production Git workflows cần các operations khác nhau:

* rollback commit đã merge vào shared branch;
* sửa local commits chưa push;
* backport hotfix từ `main` sang release branch.

Dùng sai lệnh có thể rewrite shared history hoặc mang theo thay đổi ngoài ý muốn.

## 3. How does it work?

Shared branch rollback:

```bash
git revert <bad-commit>
```

Local cleanup chưa push:

```bash
git reset --soft HEAD~1
```

Backport fix:

```bash
git switch release/1.4
git cherry-pick <fix-commit>
```

Mỗi action tạo conflict theo context branch hiện tại; conflict resolution phải được test như code change bình thường.

## 4. Practical implementation

Incident flow an toàn cho commit đã deploy:

```bash
git switch main
git pull --ff-only

git revert <bad-commit-sha>

dotnet test

git push origin main
```

Nếu fix đã tồn tại trên main nhưng customer release branch cần patch:

```bash
git switch release/1.4
git pull --ff-only

git cherry-pick <hotfix-sha>

dotnet test
```

Không cherry-pick merge lớn nếu chỉ cần một nhỏ bugfix commit; chọn smallest safe change.

## 5. Real production scenario

Release mới làm checkout lỗi. Commit đã merge và nhiều developers đã pull `main`.

Một developer dùng `git reset --hard` rồi force-push shared branch để “xóa commit”. Những người khác giờ có divergent history và CI references khó truy vết.

`git revert` tốt hơn vì tạo một commit rollback explicit, audit trail vẫn giữ nguyên và shared history không bị rewrite.

## 6. Failure scenario & troubleshooting

**Symptom** → backport compile được nhưng behavior sai vì hotfix phụ thuộc commit khác chưa có trên release branch.

**Evidence** → cherry-picked diff reference API/schema introduced later.

**Hypothesis** → commit không độc lập về dependency.

**Diagnosis** → inspect parent commits, diff, tests và runtime dependencies.

**Fix** → backport minimal dependency chain hoặc implement equivalent fix phù hợp release architecture.

**Verification** → build/test trên exact release branch + integration regression test cho bug.

## 7. Common mistakes

* Force-push `main` để rollback production.
* `reset --hard` khi chưa hiểu mất local changes.
* Cherry-pick nhiều commits theo SHA mà không hiểu ordering/dependencies.
* Revert merge commit mà không hiểu mainline parent semantics.
* Xử lý conflict bằng chọn “theirs/ours” đại trà rồi không test.
* Backport code nhưng quên DB/config/API compatibility.

## 8. Alternatives

Feature flag có thể disable behavior nhanh hơn code rollback nếu design hỗ trợ. Redeploy previous artifact là operational rollback nhưng source branch vẫn cần reconciled. Release branch merge có thể phù hợp khi muốn mang toàn bộ tested patch set thay vì single commit.

## 9. Trade-offs

### Advantages

* `revert`: audit-safe trên shared history.
* `reset`: mạnh và tiện cho local history cleanup.
* `cherry-pick`: precise backport.

### Costs / Risks

* Revert có thể conflict với later changes.
* Reset có thể mất data/rewrite history.
* Cherry-pick tạo duplicate logical commits và dependency drift giữa branches.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt working-tree cleanup với shared-history rollback.

### Middle

Dùng revert/reset/cherry-pick đúng context và resolve conflict có kiểm chứng.

### Senior

Đánh giá dependency của backport, release compatibility và rollback strategy.

### Technical Lead / Architect

Thiết kế branch/release policy sao cho rollback/backport có audit trail, automated tests và ít history surgery nhất.

## 11. Key takeaway

* Shared production history thường rollback bằng `revert`, không force-reset.
* Cherry-pick chỉ an toàn khi hiểu dependency của commit.
* Git operation kết thúc bằng verification, không kết thúc khi command exit code = 0.

# 9. SonarQube Quality Gate: biến static analysis thành engineering signal thay vì một dashboard đầy noise

## 1. What is it?

SonarQube phân tích source code để phát hiện bugs, vulnerabilities/security hotspots, code smells, duplication và coverage-related signals. Quality Gate là tập conditions quyết định một analysis có đạt tiêu chuẩn merge/release hay không.

Mental model:

```text
Code change
   ↓
static analysis + coverage/imported test data
   ↓
quality profile rules
   ↓
quality gate
   ├─ pass
   └─ fail CI/PR policy
```

Static analysis là heuristic/semantic analysis; nó không chứng minh code correct và không thay runtime tests.

## 2. Why does it exist?

Code review bằng người khó giữ hàng trăm rules nhất quán: nullability risks, duplicated code, injection patterns, resource misuse, complexity thresholds.

Automation giúp bắt classes of issues sớm.

Nhưng legacy codebase có thể có hàng nghìn findings. Nếu CI fail vì toàn bộ historical debt, team thường chọn tắt Quality Gate thay vì sửa mọi thứ.

## 3. How does it work?

Một strategy thực dụng là tập trung **New Code**:

```text
existing legacy debt
    ↓ baseline / track separately
new or changed code
    ↓
must meet stricter gate
```

Gate có thể kiểm tra:

* new critical/blocker issues;
* security findings;
* coverage on new code;
* duplication on new code;
* maintainability/reliability ratings.

Rule profile phải phù hợp language/framework và organization risk model.

## 4. Practical implementation

CI sequence conceptual:

```text
restore
build
unit/integration tests + coverage
Sonar begin/analyze/end
Quality Gate check
merge allowed only if gate passes
```

Khi finding là false positive hoặc accepted risk, resolution nên có reason/documentation thay vì suppress bằng comment hàng loạt.

Security Hotspot khác confirmed vulnerability: hotspot thường yêu cầu human review theo context.

## 5. Real production scenario

Legacy .NET Framework solution có 8.000 code smells. Team bật gate “total issues = 0”; mọi PR fail và developers bắt đầu mark findings `Won't Fix` đại trà.

Team chuyển sang Clean-as-You-Code: historical debt được backlog riêng, còn code mới không được làm quality xấu hơn. Critical security rules vẫn áp toàn codebase theo risk.

Kết quả là gate trở thành enforceable contract thay vì ceremony bị bypass.

## 6. Failure scenario & troubleshooting

**Symptom** → developers coi Sonar findings là noise và ignore gate.

**Evidence** → nhiều suppressed issues, false-positive disputes, rule churn.

**Hypothesis** → quality profile/gate không reflect codebase risk và ownership.

**Diagnosis** → review top failing rules, true-positive rate, remediation effort và incidents mà rule class từng gây.

**Fix** → tune profile có governance, giữ security/correctness rules mạnh, tránh style rules biến CI thành formatting war.

**Verification** → theo dõi gate failure reasons và sampling resolved findings qua vài sprints.

## 7. Common mistakes

* Dùng coverage % như proof test quality.
* Fail legacy project vì mọi historical smell ngay ngày đầu.
* Tắt rule mỗi khi một PR bị fail.
* Treat Security Hotspot = confirmed vulnerability hoặc ngược lại.
* Đặt complexity threshold giống nhau cho generated code, test code và business code mà không phân loại.
* Sonar pass rồi bỏ code review/threat modeling.

## 8. Alternatives

Compiler analyzers/Roslyn rules cho feedback rất nhanh trong IDE/build. SAST chuyên sâu tập trung security. ESLint/StyleCop/formatters giải quyết style. Code review, tests và runtime observability vẫn cần vì static analysis không nhìn thấy mọi integration/failure behavior.

## 9. Trade-offs

### Advantages

* Automated consistency.
* Bắt nhiều defect patterns trước runtime.
* New-code gate giúp ngăn debt tăng.
* Security findings có workflow tập trung.

### Costs / Risks

* False positives/noise.
* Scan time/CI complexity.
* Metric gaming nếu gate thiết kế sai.
* Rule/profile maintenance cần ownership.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu finding là signal cần review, không phải compiler truth tuyệt đối.

### Middle

Fix root cause, hiểu suppress/false-positive workflow và coverage semantics.

### Senior

Phân loại risk, tune analyzers với evidence và kết hợp static analysis với tests/security review.

### Technical Lead / Architect

Đặt Quality Gate policy cho new code, legacy debt, security severity và exception governance để tooling hỗ trợ engineering judgment thay vì thay thế nó.

## 11. Key takeaway

* Quality Gate tốt phải enforce được trong thực tế.
* Clean-as-You-Code thường hiệu quả hơn yêu cầu legacy debt về 0 ngay lập tức.
* Static analysis là một lớp phòng thủ, không phải proof of correctness.

# 10. AI coding agent trong repository thật: deterministic verification, least privilege và boundary cho thay đổi do LLM đề xuất

## 1. What is it?

AI coding agent là hệ thống dùng LLM để đọc repository, lập kế hoạch, sửa file, chạy tools/tests và đôi khi tạo commit/PR.

Phần LLM là probabilistic: cùng task có thể sinh phương án khác nhau. Vì vậy workflow an toàn phải đặt các deterministic controls xung quanh model.

Mental model:

```text
Task + repository context
        ↓
LLM proposes/edits
        ↓
diff boundary
        ↓
deterministic checks
build + tests + analyzers + policy
        ↓
human/review gate where needed
        ↓
merge/deploy
```

## 2. Why does it exist?

Agent giúp giảm work cơ học: tìm call sites, update boilerplate, generate tests, migrate APIs, inspect errors. Nhưng repository thật chứa secrets boundaries, deployment manifests, database migrations và security-sensitive logic.

“Model hiểu task” không phải security guarantee. Một edit syntactically valid vẫn có thể phá authorization, compatibility hoặc data integrity.

## 3. How does it work?

Safe workflow tách **proposal authority** khỏi **execution authority**.

Agent có thể được quyền:

* đọc repository;
* sửa files trong scope;
* chạy build/test/linter;
* tạo branch/PR.

Nhưng production deploy, secret access, destructive DB operation hoặc permission change thường cần deterministic policy/human approval.

Tool arguments cũng phải validate như untrusted input, tương tự mọi external input.

## 4. Practical implementation

Repository nên có machine-readable rules gần code:

```text
/AGENTS.md or engineering rules
/architecture decisions
/test commands
/security constraints
/migration policy
```

Agent workflow:

```bash
dotnet restore
dotnet build --no-restore
dotnet test --no-build
```

Sau edit, verify diff scope:

```bash
git diff --stat
git diff --check
git status --short
```

CI tiếp tục chạy canonical tests/analyzers từ trusted pipeline, không tin kết quả agent tự báo trong prose.

## 5. Real production scenario

Task yêu cầu “thêm endpoint admin export users”. Agent implement endpoint đúng DTO và compile xanh nhưng quên authorization policy vì nearby endpoint legacy cũng thiếu attribute.

Nếu verification chỉ là build + unit test happy path, PR có thể pass.

Defense tốt hơn:

* repository rule bắt admin endpoints phải map policy;
* integration security test gọi endpoint anonymous/non-admin;
* static review/diff gate phát hiện route mới;
* human approval cho permission-sensitive changes.

## 6. Failure scenario & troubleshooting

**Symptom** → agent PR thay 40 files dù task chỉ yêu cầu bugfix 2 files.

**Evidence** → diff có formatting/refactor/unrelated dependency updates.

**Hypothesis** → scope constraint quá lỏng hoặc agent tối ưu “clean up nearby code”.

**Diagnosis** → compare requested files/use case với changed-file graph và dependency justification.

**Fix** → smallest-change rule, explicit forbidden paths, limit tool permissions và require justification cho schema/dependency/config changes.

**Verification** → canonical CI + focused regression test + diff review; reject unrelated changes dù tests xanh.

## 7. Common mistakes

* Tin model explanation thay vì inspect diff.
* Cho agent broad cloud/production credentials.
* Agent tự sửa tests để “làm test pass” mà không preserve intent.
* Không distinguish generated output với authoritative source files.
* Cho phép destructive migration tự chạy production.
* Prompt chứa security rule nhưng CI không enforce rule đó.
* Dùng LLM để quyết định authorization/financial correctness mà không deterministic checks.

## 8. Alternatives

IDE autocomplete/chat phù hợp tasks nhỏ cần human-in-loop liên tục. Deterministic codemod/Roslyn analyzer tốt hơn LLM cho mechanical refactor có rule chính xác. Traditional developer workflow phù hợp high-risk changes mà agent autonomy không tạo đủ benefit.

## 9. Trade-offs

### Advantages

* Tăng tốc repository exploration và repetitive changes.
* Có thể generate broad test cases/diffs nhanh.
* Hữu ích cho migrations có nhiều call sites.

### Costs / Risks

* Probabilistic mistakes và hallucinated assumptions.
* Context có thể thiếu hidden operational constraints.
* Tool permission mở rộng blast radius.
* Review burden tăng nếu diff quá lớn/noisy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Dùng agent như collaborator nhưng luôn đọc diff và chạy tests.

### Middle

Đưa acceptance criteria rõ, tạo focused tests và giữ change scope nhỏ.

### Senior

Thiết kế deterministic verification cho security, compatibility, migrations và concurrency behavior.

### Technical Lead / Architect

Xây agent governance: repository rules, least-privilege connectors, protected paths, CI policy, audit trail và human approval cho high-impact actions.

## 11. Key takeaway

* LLM đề xuất code; deterministic system quyết định code có đủ điều kiện merge/deploy hay không.
* Agent permissions phải nhỏ hơn hoặc bằng blast radius mà organization chấp nhận.
* Một agent workflow tốt được đánh giá bằng verified outcomes, không bằng chất lượng lời giải thích của model.
