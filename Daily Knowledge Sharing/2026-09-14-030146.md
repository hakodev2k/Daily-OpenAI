# 1. C# `System.IO.Pipelines`: xử lý stream tốc độ cao mà không tự quản lý buffer phức tạp và allocation liên tục

## 1. What is it?

Mental model của `System.IO.Pipelines` là tách producer và consumer của byte stream bằng một vùng buffer được quản lý hiệu quả:

```text
Socket/File/Stream
      |
      v
 PipeWriter
      |
 managed buffers
      |
 PipeReader
      |
 parser/consumer
```

Thay vì mỗi lần đọc network lại tạo một `byte[]`, copy dữ liệu sang buffer khác rồi parse thủ công, `PipeReader` cho consumer đọc `ReadOnlySequence<byte>` có thể gồm nhiều segments mà không bắt buộc copy thành một block liên tục.

Nó đặc biệt hữu ích cho protocol parsers, gateways, streaming servers hoặc hot paths có lượng byte lớn và cần kiểm soát allocation.

## 2. Why does it exist?

Code stream kiểu truyền thống thường rơi vào một trong hai cực:

- đơn giản nhưng tạo nhiều allocation/copy;
- tối ưu nhưng tự quản lý buffer rất khó, dễ bug khi dữ liệu bị chia thành nhiều packet/chunk.

Network không đảm bảo một `ReadAsync` tương ứng đúng một message. Header 20 bytes có thể đến thành 8 bytes + 12 bytes. Nếu parser giả định boundary của transport là boundary của protocol, bug sẽ xuất hiện ngẫu nhiên dưới tải.

`Pipelines` giải quyết cả buffering lẫn producer-consumer coordination.

## 3. How does it work?

Consumer gọi:

```csharp
ReadResult result = await reader.ReadAsync(ct);
ReadOnlySequence<byte> buffer = result.Buffer;
```

Sau khi parse được một phần dữ liệu, consumer phải báo cho pipe biết:

- bytes nào đã consume;
- bytes nào đã examine.

```csharp
reader.AdvanceTo(consumed, examined);
```

Hai vị trí này khác nhau. `consumed` cho phép buffer giải phóng phần đã xử lý; `examined` nói consumer đã nhìn đến đâu. Advance sai có thể giữ memory quá lâu hoặc gây loop đọc không tiến triển.

## 4. Practical implementation

Ví dụ đọc line-delimited protocol:

```csharp
static async Task ProcessAsync(PipeReader reader, CancellationToken ct)
{
    while (true)
    {
        var result = await reader.ReadAsync(ct);
        var buffer = result.Buffer;

        while (TryReadLine(ref buffer, out var line))
        {
            ProcessLine(line);
        }

        reader.AdvanceTo(buffer.Start, buffer.End);

        if (result.IsCompleted)
            break;
    }

    await reader.CompleteAsync();
}

static bool TryReadLine(
    ref ReadOnlySequence<byte> buffer,
    out ReadOnlySequence<byte> line)
{
    var position = buffer.PositionOf((byte)'\n');
    if (position is null)
    {
        line = default;
        return false;
    }

    line = buffer.Slice(0, position.Value);
    buffer = buffer.Slice(buffer.GetPosition(1, position.Value));
    return true;
}
```

Điểm quan trọng là parser không yêu cầu line nằm trong một segment duy nhất.

## 5. Real production scenario

Một ingestion service nhận hàng chục nghìn telemetry messages/second qua TCP. Version đầu dùng `NetworkStream.ReadAsync`, tạo `byte[]` cho từng message rồi concat khi packet bị split.

Under load, profiler cho thấy:

- allocation rate rất cao;
- nhiều short-lived arrays;
- GC Gen 0 chạy liên tục;
- CPU dành đáng kể cho copying.

Sau khi chuyển parsing hot path sang `PipeReader`, service giảm allocation và xử lý packet fragmentation rõ ràng hơn. Team chỉ dùng `Pipelines` ở ingestion path thay vì thay mọi stream usage trong hệ thống.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng theo throughput dù consumer vẫn xử lý message.

**Evidence** → memory profile cho thấy buffers không được reclaim; pipeline loop vẫn active.

**Hypothesis** → `AdvanceTo` dùng sai `consumed`/`examined`, khiến pipe phải giữ lại quá nhiều bytes.

**Diagnosis** → trace parser progress; xác nhận mỗi iteration thực sự consume data hoặc chờ thêm data có lý do.

**Fix** → advance đúng vị trí; đặt maximum message size; reject malformed frame không có delimiter/header hợp lệ.

**Verification** → stress test với fragmented packets, oversized frames và incomplete messages; memory phải plateau thay vì tăng tuyến tính.

## 7. Common mistakes

- Giả định mỗi read chứa một message hoàn chỉnh.
- Convert `ReadOnlySequence<byte>` sang array/string ở mọi bước, làm mất lợi ích zero/minimal-copy.
- Không giới hạn message size, tạo DoS bằng frame vô hạn.
- `AdvanceTo` sai khiến buffer không được giải phóng.
- Dùng `Pipelines` cho code CRUD bình thường nơi `Stream` đã đủ đơn giản.
- Tối ưu trước khi profiler chứng minh allocation/copy là bottleneck.

## 8. Alternatives

- `Stream` + `ReadAsync`: lựa chọn mặc định khi throughput vừa phải và parser đơn giản.
- `SequenceReader<T>`: hữu ích cùng `ReadOnlySequence<T>` cho parser chi tiết.
- gRPC/HTTP framework abstractions: tốt hơn nếu không cần tự xây protocol layer.

## 9. Trade-offs

### Advantages

- Giảm allocation/copy trong high-throughput byte processing.
- Xử lý fragmented data tự nhiên hơn.
- Tách producer/consumer và backpressure tốt hơn code buffer tự chế.

### Costs / Risks

- API phức tạp hơn `Stream`.
- Sai buffer lifecycle gây memory retention khó thấy.
- Debugging segmented buffers khó hơn contiguous arrays.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu transport read boundary không phải message boundary.

### Middle

Biết đọc `ReadOnlySequence<byte>`, parse incremental và advance buffer đúng.

### Senior

Đo allocation/copy cost, đặt framing limits và kiểm thử malformed/fragmented input.

### Technical Lead / Architect

Quyết định hot path nào thực sự cần `Pipelines`, tránh biến performance abstraction thành complexity mặc định toàn codebase.

## 11. Key takeaway

- `Pipelines` hữu ích khi byte throughput và buffer management thực sự là bottleneck.
- Parser phải đúng với fragmented input, không dựa vào network packet boundaries.
- Buffer lifecycle sai có thể đổi GC pressure thành memory-retention problem khác.

# 2. ASP.NET Core Health Checks: phân biệt liveness, readiness và dependency health để tránh restart đúng lúc hệ thống chỉ đang degraded

## 1. What is it?

Health check là tín hiệu machine-readable cho platform biết application đang ở trạng thái nào.

Mental model nên tách ít nhất hai câu hỏi:

```text
Liveness:  Process này còn có khả năng tiếp tục chạy không?
Readiness: Instance này hiện có nên nhận traffic không?
```

Một dependency check như database, Redis hay external API không tự động nên trở thành liveness condition.

## 2. Why does it exist?

Trong distributed hosting, orchestrator/load balancer cần quyết định:

- có gửi request vào instance không;
- có nên restart process không;
- deployment đã warm-up đủ để nhận traffic chưa.

Nếu mọi dependency outage đều làm liveness fail, Redis outage 2 phút có thể khiến tất cả pods restart liên tục, tạo thêm load và làm recovery tệ hơn.

## 3. How does it work?

ASP.NET Core Health Checks cho phép đăng ký checks và filter theo tags.

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<DatabaseHealthCheck>(
        "database",
        tags: ["ready"]);
```

Map endpoints riêng:

```csharp
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

`/health/live` ở đây chỉ xác nhận process pipeline phản hồi. `/health/ready` có thể kiểm tra dependency thật sự cần để phục vụ request chính.

## 4. Practical implementation

Một database readiness check nên:

- timeout ngắn;
- query nhẹ;
- không chạy expensive business query;
- không mutate state.

```csharp
public sealed class DatabaseHealthCheck(AppDbContext db)
    : IHealthCheck
{
    public async Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context,
        CancellationToken ct = default)
    {
        try
        {
            var canConnect = await db.Database.CanConnectAsync(ct);
            return canConnect
                ? HealthCheckResult.Healthy()
                : HealthCheckResult.Unhealthy("Database unavailable");
        }
        catch (Exception ex)
        {
            return HealthCheckResult.Unhealthy("Database check failed", ex);
        }
    }
}
```

Production setup phải cân nhắc tần suất probe để health check không tự tạo workload lớn.

## 5. Real production scenario

Một Kubernetes-hosted API đánh dấu Redis outage là liveness failure. Khi Redis cluster maintenance bắt đầu, mọi pods fail liveness và bị restart.

Sau restart:

- application cold start;
- connections đồng loạt mở lại;
- cache vẫn chưa available;
- probes tiếp tục fail;
- cluster rơi vào restart loop.

Thực ra API có thể phục vụ degraded mode bằng database fallback. Redis nên ảnh hưởng readiness/degraded telemetry theo policy, không nhất thiết liveness.

## 6. Failure scenario & troubleshooting

**Symptom** → deployment/pods restart hàng loạt khi một dependency tạm thời lỗi.

**Evidence** → platform events cho thấy liveness probe failure; app logs cho thấy root cause là external dependency.

**Hypothesis** → health semantics bị trộn: dependency health đang quyết định process death.

**Diagnosis** → map từng probe với platform action tương ứng; xác định dependency nào thực sự làm instance không thể phục vụ traffic.

**Fix** → tách liveness/readiness; cho timeout; thiết kế degraded behavior; tránh probe quá sâu.

**Verification** → chaos test dependency outage: instance không restart vô ích, traffic routing phản ánh readiness policy.

## 7. Common mistakes

- Một endpoint `/health` dùng cho mọi platform action.
- Gọi tất cả dependencies trong liveness.
- Health check chạy query nặng.
- Không timeout check khiến probe treo.
- Trả 200 dù check nội bộ failed chỉ vì muốn dashboard “xanh”.
- Dùng health check thay observability/alerts.

## 8. Alternatives

- Synthetic monitoring từ bên ngoài cho end-user journey.
- Application metrics/SLIs cho chất lượng dịch vụ dài hạn.
- Startup probe trong Kubernetes cho workload khởi động chậm.

Health checks và observability bổ sung nhau, không thay thế nhau.

## 9. Trade-offs

### Advantages

- Platform có tín hiệu rõ để route/restart.
- Deployment automation kiểm tra readiness trước khi shift traffic.

### Costs / Risks

- Probe design sai có thể gây restart storm hoặc remove capacity quá mức.
- Dependency checks tự tạo load.
- Health endpoint exposed sai có thể leak topology/details.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu health endpoint không chỉ là URL trả 200.

### Middle

Biết đăng ký checks, timeout và map readiness/liveness riêng.

### Senior

Thiết kế degraded mode, dependency classification và probe behavior dưới outage.

### Technical Lead / Architect

Định nghĩa platform action cho từng health signal và đảm bảo health policy không khuếch đại failure.

## 11. Key takeaway

- Liveness trả lời “restart có giúp không?”, readiness trả lời “có nên nhận traffic không?”.
- Dependency outage không mặc định là liveness failure.
- Health checks phải đơn giản, bounded và gắn với platform behavior rõ ràng.

# 3. EF Core Interceptors: chèn cross-cutting behavior vào database pipeline mà không trộn concern vào business code

## 1. What is it?

EF Core interceptor là hook vào các operation của EF như command execution, connection, transaction hoặc `SaveChanges`.

Mental model:

```text
Application code
      |
   EF Core
      |
 interceptor(s)
      |
 DbCommand / Transaction / Connection
      |
   Database
```

Nó phù hợp cho cross-cutting concerns ở persistence boundary: audit metadata, command diagnostics, guardrails hoặc instrumentation.

## 2. Why does it exist?

Nếu mọi repository/service đều tự thêm logging, tenant guards, audit timestamp hoặc SQL instrumentation, logic bị lặp và dễ bỏ sót.

Interceptor cho phép áp concern ở một boundary chung mà không làm domain/application code biết quá nhiều về persistence mechanics.

Nhưng vì interceptor nằm sâu trong pipeline, dùng sai có thể tạo hidden behavior khó debug.

## 3. How does it work?

EF Core cung cấp nhiều base classes/interfaces như:

- `SaveChangesInterceptor`;
- `DbCommandInterceptor`;
- `DbConnectionInterceptor`;
- transaction interceptors.

Ví dụ `SaveChangesInterceptor` có thể inspect `ChangeTracker` trước commit.

## 4. Practical implementation

Audit timestamps:

```csharp
public sealed class AuditSaveChangesInterceptor(TimeProvider timeProvider)
    : SaveChangesInterceptor
{
    public override InterceptionResult<int> SavingChanges(
        DbContextEventData eventData,
        InterceptionResult<int> result)
    {
        ApplyAudit(eventData.Context);
        return base.SavingChanges(eventData, result);
    }

    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData,
        InterceptionResult<int> result,
        CancellationToken cancellationToken = default)
    {
        ApplyAudit(eventData.Context);
        return base.SavingChangesAsync(
            eventData, result, cancellationToken);
    }

    private void ApplyAudit(DbContext? context)
    {
        if (context is null) return;

        var now = timeProvider.GetUtcNow();

        foreach (var entry in context.ChangeTracker
                     .Entries<IAuditableEntity>())
        {
            if (entry.State == EntityState.Added)
                entry.Entity.CreatedAtUtc = now;

            if (entry.State is EntityState.Added or EntityState.Modified)
                entry.Entity.UpdatedAtUtc = now;
        }
    }
}
```

Registration:

```csharp
options.AddInterceptors(auditInterceptor);
```

## 5. Real production scenario

Một SaaS platform cần audit `CreatedAtUtc`, `UpdatedAtUtc` cho hàng trăm entities. Ban đầu mỗi service tự set timestamps; một số import/background flows quên update metadata.

Chuyển concern này vào interceptor giúp consistency tốt hơn. Tuy nhiên authorization và business approval rules vẫn ở application/domain layer, không bị “giấu” trong interceptor.

## 6. Failure scenario & troubleshooting

**Symptom** → mọi query production chậm hơn sau khi thêm instrumentation interceptor.

**Evidence** → interceptor làm synchronous logging/network call cho từng command.

**Hypothesis** → cross-cutting hook đang thêm I/O vào hot persistence path.

**Diagnosis** → profile command duration trước/sau; inspect interceptor code và call frequency.

**Fix** → giữ interceptor lightweight; emit structured telemetry không-blocking; không gọi remote service trên mỗi DB command.

**Verification** → load test query-heavy workload và so sánh latency/allocation.

## 7. Common mistakes

- Đưa business rules vào interceptor vì “chạy tự động”.
- Thay đổi query semantics âm thầm ở command interceptor.
- Log full SQL parameters có sensitive data.
- Làm network I/O trong `SavingChanges` mà không nghĩ transaction latency.
- Tạo interceptor stateful không thread-safe rồi reuse qua nhiều contexts.
- Dùng interceptor khi application service rõ ràng hơn.

## 8. Alternatives

- Override `DbContext.SaveChanges` cho concern đơn giản, local với một context.
- Domain events cho business-side effects sau domain state change.
- Database trigger cho rules/audit bắt buộc ở database boundary.
- Middleware không phù hợp vì chỉ bao HTTP, không bao worker/background DB operations.

## 9. Trade-offs

### Advantages

- Centralize persistence cross-cutting logic.
- Bao phủ cả HTTP và background flows dùng cùng DbContext configuration.
- Hữu ích cho diagnostics/audit/guardrails.

### Costs / Risks

- Hidden behavior làm execution path khó nhìn.
- Hot-path overhead áp lên nhiều queries/commands.
- Interceptor quá thông minh làm persistence layer khó kiểm soát.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu interceptor là hook của EF pipeline, không phải business event.

### Middle

Biết implement audit/diagnostic concern đơn giản và test lifecycle.

### Senior

Đánh giá overhead, sensitive logging và interaction với transaction/async paths.

### Technical Lead / Architect

Quyết định concern nào nên centralize ở persistence boundary và concern nào phải visible ở domain/application layer.

## 11. Key takeaway

- Interceptors tốt cho cross-cutting persistence concerns, không phải nơi giấu business logic.
- Mọi interceptor chạy trên hot path cần cực kỳ nhẹ và observable.
- Centralization hữu ích chỉ khi behavior vẫn predictable và testable.

# 4. SQL Server sargability: vì sao cùng một điều kiện logic nhưng query shape khác nhau có thể biến index seek thành scan

## 1. What is it?

SARGable nghĩa là predicate có thể dùng index access hiệu quả để giới hạn phạm vi dữ liệu cần đọc.

Mental model:

```text
SARGable:
IndexedColumn >= @from AND IndexedColumn < @to
        -> seek/range scan

Non-SARGable:
FUNCTION(IndexedColumn) = @value
        -> thường phải evaluate nhiều rows
```

Sargability là đặc tính của query shape so với index, không chỉ việc “có index hay chưa”.

## 2. Why does it exist?

Optimizer dùng index statistics và key ordering để tìm vùng dữ liệu cần đọc. Nếu predicate bọc indexed column trong function/transformation, engine có thể không trực tiếp map điều kiện sang index range.

Khi table nhỏ, khác biệt ít thấy. Khi table lên hàng trăm triệu rows, non-sargable predicate có thể biến milliseconds thành seconds và tăng I/O mạnh.

## 3. How does it work?

Ví dụ kém:

```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE CAST(CreatedAt AS date) = @Date;
```

Tốt hơn:

```sql
SELECT Id, CreatedAt, Total
FROM Orders
WHERE CreatedAt >= @Date
  AND CreatedAt < DATEADD(day, 1, @Date);
```

Nếu `CreatedAt` là key đầu trong index phù hợp, query thứ hai cho optimizer range boundary rõ hơn.

## 4. Practical implementation

Trong EF Core, tránh tạo expression dẫn tới function trên column khi có thể express range trực tiếp:

```csharp
var from = date.ToDateTime(TimeOnly.MinValue, DateTimeKind.Utc);
var to = from.AddDays(1);

var orders = await db.Orders
    .Where(x => x.CreatedAtUtc >= from && x.CreatedAtUtc < to)
    .Select(x => new { x.Id, x.Total })
    .ToListAsync(ct);
```

Luôn inspect generated SQL và actual execution plan khi performance matter.

## 5. Real production scenario

Dashboard filter orders theo ngày. Query dùng `CONVERT(date, CreatedAt)` và chạy tốt khi database có 500k rows. Sau vài năm, table có 250 triệu rows; API p95 tăng mạnh vào giờ cao điểm.

Actual plan cho thấy scan với millions logical reads. Rewrite thành half-open range + index phù hợp giảm I/O đáng kể mà không thêm cache hay scale database.

## 6. Failure scenario & troubleshooting

**Symptom** → query lọc rất chọn lọc nhưng vẫn đọc phần lớn table/index.

**Evidence** → actual execution plan có scan; logical reads cao; estimated predicate selectivity không chuyển thành seek range.

**Hypothesis** → predicate non-sargable hoặc index key order không hỗ trợ filter.

**Diagnosis** → kiểm tra SQL text, plan, `SET STATISTICS IO`, parameter types và implicit conversions.

**Fix** → rewrite predicate; xử lý type mismatch; cân nhắc computed persisted column + index khi transformation là business requirement thường xuyên.

**Verification** → compare logical reads, CPU, duration và plan shape trước/sau trên production-like data distribution.

## 7. Common mistakes

- Chỉ thêm index nhưng giữ non-sargable predicate.
- Dùng `LOWER(Column)` cho case-insensitive search mà không hiểu collation/index design.
- Implicit conversion vì parameter type khác column type.
- Đo duration một lần mà không nhìn logical reads.
- Dùng `%term%` với B-tree index rồi kỳ vọng seek.
- Rewrite SQL nhưng không kiểm tra semantics timezone/date boundary.

## 8. Alternatives

- Persisted computed column + index khi transformed value là access pattern chính.
- Full-text search cho linguistic search.
- Elasticsearch khi search requirement vượt relational indexing phù hợp.

## 9. Trade-offs

### Advantages

- Sargable query thường giảm I/O mà không thêm infrastructure.
- Giữ database query path đơn giản và predictable hơn.

### Costs / Risks

- Computed/indexed columns tăng storage và write cost.
- Query rewrite có thể phức tạp hơn về timezone/collation.
- Không mọi scan đều xấu; small table/full-range query có thể scan hợp lý.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index chỉ hữu ích khi query có thể tận dụng nó.

### Middle

Biết đọc seek vs scan và tránh function trên indexed column trong hot filters.

### Senior

Dùng plan + logical I/O + cardinality để xác định sargability issue thực sự.

### Technical Lead / Architect

Đặt performance review dựa trên access patterns/data scale, không tạo culture “thêm index cho mọi slow query”.

## 11. Key takeaway

- Query shape quyết định index có thực sự usable hay không.
- Đo execution plan và logical I/O trước khi tối ưu.
- Sargability thường là cách giảm I/O rẻ hơn scale-up hoặc cache thêm tầng.

# 5. DDD Value Objects: gom invariant và semantics vào domain type thay vì để primitive values lan khắp codebase

## 1. What is it?

Value Object là domain object được xác định bởi **giá trị và invariant**, không phải identity riêng.

Mental model:

```text
Primitive approach:
string email
string currency
string countryCode

domain types:
EmailAddress
Money
CountryCode
```

Hai `Money(100, "USD")` có cùng value semantics dù được tạo ở hai nơi khác nhau.

## 2. Why does it exist?

Primitive obsession làm domain rules bị phân tán:

```text
Controller validates email
Service trims email
Repository lowercases email
Another service forgets validation
```

Value Object gom construction rules và semantics vào một type, giảm trạng thái invalid tồn tại lâu trong system.

## 3. How does it work?

Một Value Object thường:

- immutable hoặc effectively immutable;
- equality theo constituent values;
- validate invariant khi tạo;
- không có lifecycle/identity riêng.

Ví dụ `Money` không chỉ là `decimal`; currency là một phần semantics.

## 4. Practical implementation

```csharp
public sealed record EmailAddress
{
    public string Value { get; }

    private EmailAddress(string value) => Value = value;

    public static EmailAddress Create(string value)
    {
        if (string.IsNullOrWhiteSpace(value))
            throw new ArgumentException("Email is required.");

        var normalized = value.Trim().ToLowerInvariant();

        if (!normalized.Contains('@'))
            throw new ArgumentException("Invalid email.");

        return new EmailAddress(normalized);
    }

    public override string ToString() => Value;
}
```

Production email validation có thể tinh vi hơn, nhưng point chính là invariant nằm cùng domain type.

Trong EF Core, Value Object có thể map bằng owned/complex type hoặc value converter tùy shape/version.

## 5. Real production scenario

Một billing system truyền `decimal amount` + `string currency` qua nhiều methods. Một code path convert amount nhưng quên đổi currency metadata, tạo invoice sai.

Refactor sang `Money` buộc amount và currency di chuyển cùng nhau; operation `Add` có thể reject khác currency tại domain boundary thay vì chờ bug xuất hiện trong persistence/reporting.

## 6. Failure scenario & troubleshooting

**Symptom** → domain type xuất hiện nhưng code vẫn có thể tạo instance invalid qua serializer/ORM/reflection path.

**Evidence** → production data chứa value mà factory không cho phép.

**Hypothesis** → persistence/serialization bypass invariant hoặc constructor quá permissive.

**Diagnosis** → kiểm tra ORM mapping, deserialization constructors và migration path từ legacy data.

**Fix** → đảm bảo invariants ở construction boundary; validate existing data trước migration; không giả định type alone sửa được legacy invalid rows.

**Verification** → property/unit tests cho equality và invariants; integration tests persistence round-trip.

## 7. Common mistakes

- Tạo Value Object cho mọi `string`/`int`, làm code ceremony quá mức.
- Value Object mutable nhưng dùng như immutable key.
- Dùng Value Object như Entity có repository riêng không cần thiết.
- Throw exception cho input validation expected ở high-volume edge mà không có strategy rõ.
- Nhét infrastructure concerns vào domain type.
- Không plan migration cho existing primitive columns/data.

## 8. Alternatives

- Primitive + validation ở boundary: đủ cho domain đơn giản.
- Strongly typed IDs: hữu ích để tránh trộn `CustomerId` và `OrderId`, nhưng khác Value Object giàu behavior.
- Entity khi concept có identity/lifecycle riêng.

## 9. Trade-offs

### Advantages

- Invariants và semantics tập trung.
- Equality rõ ràng.
- Giảm parameter mix-up và primitive obsession.

### Costs / Risks

- Tăng số types và mapping complexity.
- Serialization/ORM/tooling cần cấu hình.
- Over-modeling domain đơn giản làm maintainability tệ hơn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Value Object được nhận diện bằng value, không phải ID.

### Middle

Biết implement immutable value semantics và validation.

### Senior

Chọn đúng domain concepts cần type riêng và xử lý persistence/serialization boundaries.

### Technical Lead / Architect

Dùng Value Objects để làm rõ ubiquitous language nhưng giữ complexity proportional với business rules.

## 11. Key takeaway

- Value Object hữu ích khi primitive đang che business semantics/invariant thực sự.
- Immutability và value equality là mental model cốt lõi.
- Đừng biến DDD thành cuộc thi tạo nhiều class nhất.

# 6. Eventual consistency và read-your-writes: khi write thành công nhưng user vẫn thấy dữ liệu cũ, hệ thống cần consistency strategy rõ ràng

## 1. What is it?

Eventual consistency nghĩa là sau một write, các replicas/read models/downstream projections có thể chưa phản ánh thay đổi ngay lập tức nhưng sẽ hội tụ sau một khoảng thời gian.

Read-your-writes là một user-visible consistency property:

> Sau khi chính user vừa cập nhật thành công, lần đọc tiếp theo của user có thấy thay đổi đó không?

Hai khái niệm này rất quan trọng trong CQRS, search indexes, caches và geo-replicated systems.

## 2. Why does it exist?

Hệ thống thường tách write path khỏi read path để scale hoặc decouple:

```text
Write API -> Primary DB -> Event -> Read Model/Search/Cache
```

Nếu UI redirect ngay sang page đọc từ read model, projection lag 500 ms có thể khiến user thấy dữ liệu cũ và nghĩ save thất bại.

Backend technically correct nhưng product behavior kém.

## 3. How does it work?

Có nhiều consistency strategies:

- đọc primary ngay sau write;
- sticky/session routing;
- version token;
- optimistic UI;
- poll/read model đến version mong muốn;
- explicit “processing” state;
- invalidate/update cache synchronously nếu safe.

Không có một solution universal; phải dựa vào latency, availability và correctness requirement.

## 4. Practical implementation

Một pattern là trả `version` sau command:

```json
POST /orders/123/status

{
  "status": "Approved"
}

202 Accepted
{
  "orderId": "123",
  "version": 42
}
```

Read API có thể trả current projection version. Client chỉ coi state đã hội tụ khi `readVersion >= 42`.

Với operation cần immediate confirmation, có thể đọc write store cho request kế tiếp thay vì ép mọi read toàn hệ thống trở thành strongly consistent.

## 5. Real production scenario

E-commerce admin cập nhật product title trong CMS/product service. Search index được update async. UI save thành công rồi redirect về search results; item vẫn hiện title cũ trong 2 giây.

Nếu không có consistency design, support tickets xuất hiện: “Save lúc được lúc không”.

Giải pháp có thể là hiển thị saved state từ command response ngay trên detail page và chấp nhận search results hội tụ sau, kèm indexing status nếu business cần.

## 6. Failure scenario & troubleshooting

**Symptom** → write API 200/202 nhưng read API ngay sau đó trả state cũ.

**Evidence** → primary DB đúng; projection/event consumer lag; trace cho thấy read đi vào replica/search index.

**Hypothesis** → expected consistency property chưa được xác định.

**Diagnosis** → map write store, event path, read store, cache và lag metrics.

**Fix** → chọn explicit read-your-writes strategy; thêm projection version/lag telemetry.

**Verification** → integration test write→immediate read dưới injected consumer delay.

## 7. Common mistakes

- Gọi mọi behavior là “eventual consistency” rồi bắt user tự chịu stale data.
- Retry write chỉ vì read model chưa update, gây duplicate side effect.
- Không đo consumer/projection lag.
- Cache read model lâu hơn business freshness budget.
- Biến toàn hệ thống thành strongly consistent chỉ để giải quyết một UI flow.
- Không phân biệt command acceptance với downstream completion.

## 8. Alternatives

- Single relational database + synchronous transaction khi scale/business chưa cần distributed model.
- Strong-consistency read từ primary cho critical flows.
- Async projection cho scale/search/reporting nơi short lag chấp nhận được.

## 9. Trade-offs

### Advantages

- Async read models giảm coupling và có thể scale độc lập.
- Eventual consistency hỗ trợ failure isolation tốt hơn trong nhiều workflows.

### Costs / Risks

- User-visible stale state.
- Cần versioning/lag telemetry/reconciliation.
- Mental model và testing phức tạp hơn single-database transaction.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu write success không đảm bảo mọi read store cập nhật ngay.

### Middle

Biết trace command→event→projection và tránh retry write do stale read.

### Senior

Thiết kế read-your-writes behavior và lag observability theo UX/correctness requirement.

### Technical Lead / Architect

Quyết định nơi eventual consistency đáng complexity và nơi synchronous consistency vẫn là lựa chọn tốt hơn.

## 11. Key takeaway

- Eventual consistency là product behavior, không chỉ backend implementation detail.
- Read-your-writes cần được thiết kế nếu user mong thấy thay đổi ngay.
- Đo projection lag và dùng version semantics thay vì retry mù.

# 7. Azure Container Apps autoscaling với KEDA: scale theo workload mà không biến mọi ứng dụng thành Kubernetes platform project

## 1. What is it?

Azure Container Apps là managed container platform cho HTTP services, background workers và event-driven workloads. Autoscaling của nó dựa trên KEDA concepts, cho phép scale theo HTTP concurrency hoặc event sources như queue length.

Mental model:

```text
Image
  |
Container App revision
  |
replicas 1..N
  ^
  |
scale rule
  |
HTTP / Queue / Event metric
```

Platform quản lý phần lớn Kubernetes control-plane complexity phía sau.

## 2. Why does it exist?

App Service đơn giản cho web apps; AKS linh hoạt nhưng có operational cost lớn. Nhiều teams chỉ cần:

- deploy container;
- scale theo traffic/workload;
- revision-based rollout;
- managed ingress;
- secrets/identity/network integration.

Container Apps lấp khoảng giữa đó.

## 3. How does it work?

Scale rule quan sát metric/event source. Với queue consumer:

```text
queue depth grows
    |
KEDA scaler
    |
increase replicas
    |
competing consumers drain queue
```

Scale-out không tự đảm bảo correctness. Nếu messages at-least-once, mỗi replica vẫn cần idempotency, lock/settlement và poison-message strategy.

## 4. Practical implementation

Ví dụ conceptual Azure CLI/config thường đặt:

- minimum replicas;
- maximum replicas;
- queue scaler threshold;
- Managed Identity để đọc Service Bus/Storage metric hoặc consume messages.

Application worker vẫn cần graceful shutdown:

```csharp
public sealed class QueueWorker(...) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await ProcessNextAsync(stoppingToken);
        }
    }
}
```

Không assume scale-in sẽ đợi vô hạn; operation dài phải có cancellation/idempotency semantics.

## 5. Real production scenario

Image-processing system nhận 100 jobs/phút bình thường nhưng marketing campaign tạo 20,000 jobs trong vài phút.

Fixed two-worker App Service làm backlog kéo dài hàng giờ. Container Apps scale theo queue depth giúp tăng consumers tạm thời rồi scale down khi backlog hết.

Team đặt max replicas dựa trên downstream database/API capacity, không để autoscaler tạo 500 consumers làm dependency sập.

## 6. Failure scenario & troubleshooting

**Symptom** → queue depth tăng nhưng replicas không tăng, hoặc replicas tăng mạnh nhưng throughput không cải thiện.

**Evidence** → scaler metric/identity lỗi; hoặc downstream throttling tăng khi replicas tăng.

**Hypothesis** → scale signal sai hoặc bottleneck nằm ở dependency chứ không phải worker count.

**Diagnosis** → kiểm tra queue depth, replica count, processing duration, failures, dependency saturation và scaler auth/configuration.

**Fix** → sửa scale rule/identity; đặt max concurrency; tune batch/prefetch; bảo vệ downstream.

**Verification** → controlled load test backlog growth và quan sát scale-out→drain→scale-in.

## 7. Common mistakes

- Nghĩ autoscaling thay thế capacity planning.
- Scale theo queue length nhưng không xét average processing time.
- Max replicas quá lớn so với database connection budget.
- Không idempotent khi nhiều replicas compete.
- Scale-to-zero cho workload cần ultra-low latency nhưng không chấp nhận cold start.
- Chọn Container Apps chỉ vì “containers hiện đại hơn”.

## 8. Alternatives

- Azure App Service: đơn giản cho web/API truyền thống.
- Azure Functions: tốt cho event-driven functions và bursty execution với programming model phù hợp.
- Worker Service trên App Service/VM: đơn giản nếu scale cố định.
- AKS: khi cần Kubernetes-level control/ecosystem và team có platform capability.

## 9. Trade-offs

### Advantages

- Managed container runtime với autoscaling/event-driven support.
- Ít operational burden hơn AKS cho nhiều application teams.
- Revision model hỗ trợ deployment traffic management.

### Costs / Risks

- Cold start/scale latency cho scale-to-zero.
- Platform abstraction có giới hạn so với AKS.
- Scale rule sai có thể tạo cost spike hoặc downstream overload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu replica count là capacity, không phải correctness guarantee.

### Middle

Biết containerize worker/API và cấu hình basic scale limits.

### Senior

Thiết kế scaler metric, graceful shutdown, idempotency và downstream capacity budget.

### Technical Lead / Architect

Chọn Container Apps vs App Service/Functions/AKS dựa trên workload và operational maturity, không dựa trên trend.

## 11. Key takeaway

- Autoscaling phải dựa trên bottleneck và downstream capacity, không chỉ traffic tăng.
- Queue-driven scale cần idempotent consumers và failure handling như mọi distributed worker.
- Container Apps có giá trị khi cần container flexibility mà chưa cần toàn bộ AKS complexity.

# 8. High-cardinality metrics: observability có thể tự trở thành bottleneck khi labels/tags tăng theo user, request hoặc entity ID

## 1. What is it?

Cardinality là số combination distinct của metric dimensions/labels.

Ví dụ an toàn tương đối:

```text
http_requests_total{
  method="GET",
  route="/orders/{id}",
  status="200"
}
```

Ví dụ nguy hiểm:

```text
http_requests_total{
  user_id="8f...",
  order_id="123456789",
  request_id="..."
}
```

Mỗi distinct combination tạo time series mới trong nhiều metrics backends.

## 2. Why does it exist?

Metrics được thiết kế để aggregate trends nhanh. Logs/traces phù hợp hơn cho high-cardinality identifiers.

Nếu gắn `userId` hoặc `requestId` vào metrics, số series có thể tăng theo traffic thay vì theo bounded system dimensions, làm storage/memory/query cost bùng nổ.

## 3. How does it work?

Giả sử labels có:

```text
20 routes
5 status classes
3 regions
100,000 users
```

Nếu thêm `user_id`, theoretical combinations tăng từ khoảng hàng trăm lên hàng chục triệu.

Backend phải ingest, index và retain mỗi series. Alert queries cũng chậm hơn.

## 4. Practical implementation

Metric dimensions nên bounded:

```csharp
meter.CreateCounter<long>("orders.processed")
    .Add(1,
        new KeyValuePair<string, object?>("result", "success"),
        new KeyValuePair<string, object?>("region", region));
```

Không thêm `orderId`.

Để điều tra order cụ thể, dùng structured logs/traces:

```csharp
logger.LogInformation(
    "Processed order {OrderId} with trace {TraceId}",
    orderId,
    Activity.Current?.TraceId);
```

## 5. Real production scenario

Team thêm `customer_id` vào HTTP latency metric để “debug khách hàng cụ thể”. Sau vài tuần, telemetry bill tăng mạnh, dashboard queries timeout và metrics backend bắt đầu drop series.

Thay đổi đúng là giữ metrics bounded theo route/status/region, còn customer-specific investigation đi qua logs/traces có trace correlation.

## 6. Failure scenario & troubleshooting

**Symptom** → observability cost/storage tăng nhanh, metrics queries chậm hoặc backend báo series limit.

**Evidence** → top label cardinality cho thấy user/request/entity IDs tạo hàng triệu values.

**Hypothesis** → high-cardinality tags đang được dùng sai cho metrics.

**Diagnosis** → inventory dimensions, unique values và series growth theo thời gian.

**Fix** → remove/unset unbounded labels; route identifiers sang logs/traces; pre-aggregate dimensions cần thiết.

**Verification** → theo dõi active time series và ingestion cost giảm sau retention window.

## 7. Common mistakes

- Gắn correlation ID vào metric.
- Dùng raw URL `/orders/123` thay normalized route `/orders/{id}`.
- Tag exception message làm dimension.
- Cho tenant ID vào mọi metric dù hàng trăm nghìn tenants.
- Tưởng sampling trace sẽ tự giảm metric cardinality.
- Không review custom metrics trước production.

## 8. Alternatives

- Logs cho event details/high-cardinality fields.
- Traces cho request/dependency path và identifiers.
- Exemplars nếu telemetry stack hỗ trợ liên kết metric point với trace mà không biến trace ID thành metric label.

## 9. Trade-offs

### Advantages

- Bounded metrics nhanh, rẻ hơn và phù hợp alerts/SLIs.
- Logs/traces giữ khả năng drill-down chi tiết.

### Costs / Risks

- Quá ít dimensions làm metric không đủ actionable.
- Logs/traces có cost riêng và cần sampling/retention.
- Phải thiết kế telemetry schema, không thể tag tùy tiện.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu metrics dùng cho aggregation, không phải lưu mọi identifier.

### Middle

Biết chọn bounded labels và normalize routes.

### Senior

Đánh giá series growth, telemetry cost và correlation giữa metrics/traces/logs.

### Technical Lead / Architect

Đặt observability conventions và cardinality budgets trước khi mỗi team tự định nghĩa tags.

## 11. Key takeaway

- High-cardinality labels có thể làm metrics system đắt và chậm hơn application cần quan sát.
- User/request/entity IDs thường thuộc logs/traces, không thuộc metric dimensions.
- Observability schema cũng cần architecture và cost discipline.

# 9. Content Security Policy: giảm XSS blast radius bằng browser-enforced policy thay vì chỉ trông chờ output encoding

## 1. What is it?

Content Security Policy (CSP) là HTTP response policy yêu cầu browser chỉ load/execute content từ các nguồn và kiểu được phép.

Ví dụ:

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m';
  object-src 'none';
  base-uri 'self';
```

Mental model:

```text
Server response
   |
CSP header
   |
Browser enforcement
   |
script/style/frame/resource allowed or blocked
```

CSP là defense-in-depth, không thay output encoding/sanitization.

## 2. Why does it exist?

XSS xảy ra khi attacker-controlled data được browser diễn giải như executable content. Output encoding và framework auto-escaping giảm risk nhưng bugs vẫn có thể lọt qua unsafe HTML APIs, legacy scripts hoặc third-party content.

CSP giới hạn những gì injected markup có thể thực thi.

## 3. How does it work?

Policy có directives như:

- `default-src`;
- `script-src`;
- `style-src`;
- `img-src`;
- `connect-src`;
- `frame-ancestors`.

Nonce-based policy cho phép server đánh dấu scripts hợp lệ mà không bật `'unsafe-inline'` toàn bộ.

```html
<script nonce="r4nd0m" src="/app.js"></script>
```

Browser chỉ chạy script có nonce đúng policy.

## 4. Practical implementation

ASP.NET Core middleware có thể tạo nonce mỗi response:

```csharp
app.Use(async (context, next) =>
{
    var nonce = Convert.ToBase64String(
        RandomNumberGenerator.GetBytes(16));

    context.Items["CspNonce"] = nonce;

    context.Response.Headers.ContentSecurityPolicy =
        $"default-src 'self'; " +
        $"script-src 'self' 'nonce-{nonce}'; " +
        "object-src 'none'; base-uri 'self';";

    await next();
});
```

SSR/template layer phải apply cùng nonce cho approved inline bootstrapping scripts nếu thật sự cần.

## 5. Real production scenario

Legacy commerce page dùng CMS rich text và một số third-party scripts. Team không thể refactor toàn bộ frontend ngay. CSP được rollout trước ở `Content-Security-Policy-Report-Only` để quan sát violations, sau đó tighten sources và loại inline scripts dần.

Điều này giảm blast radius trong quá trình modernization thay vì chờ frontend “hoàn hảo” mới có protection.

## 6. Failure scenario & troubleshooting

**Symptom** → sau khi bật CSP, payment widget/analytics hoặc app bundle ngừng hoạt động.

**Evidence** → browser console/CSP violation reports chỉ rõ blocked source/directive.

**Hypothesis** → policy quá chặt hoặc third-party integration dựa vào inline/eval behavior.

**Diagnosis** → dùng report-only; inventory script/connect/frame domains; xác định source thực sự cần.

**Fix** → thêm directive tối thiểu, nonce/hash approved inline code hoặc thay integration không tương thích.

**Verification** → automated E2E trên critical flows + CSP violation monitoring.

## 7. Common mistakes

- Thêm `'unsafe-inline'` và `'unsafe-eval'` rộng để “fix nhanh”, làm policy yếu đi đáng kể.
- Allowlist wildcard domains quá rộng.
- Nghĩ CSP thay sanitization/output encoding.
- Bật enforcement production ngay không chạy report-only trên app legacy.
- Quên `frame-ancestors`/clickjacking concerns.
- Không inventory third-party scripts.

## 8. Alternatives

- Strict output encoding/sanitization vẫn bắt buộc.
- Trusted Types có thể bổ sung cho DOM XSS trong browser ecosystems phù hợp.
- Subresource Integrity hữu ích cho fixed external resources nhưng giải quyết problem khác.

## 9. Trade-offs

### Advantages

- Browser-enforced layer giảm khả năng injected content execute.
- Report mode cung cấp visibility về resource behavior.
- Ép team hiểu third-party script surface.

### Costs / Risks

- Legacy inline scripts làm rollout khó.
- Third-party integrations có thể cần policy mở rộng.
- CSP configuration phức tạp và dễ bị weaken bằng exceptions.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CSP là browser security policy, không phải backend authentication.

### Middle

Biết đọc CSP violations và cấu hình source directives cơ bản.

### Senior

Thiết kế nonce/report-only rollout và tránh unsafe exceptions lan rộng.

### Technical Lead / Architect

Quản trị third-party script trust boundary và CSP baseline toàn platform/web properties.

## 11. Key takeaway

- CSP là defense-in-depth cho XSS, không thay encoding/sanitization.
- Nonce/hash-based policies mạnh hơn blanket `'unsafe-inline'`.
- Rollout report-only giúp tighten policy dựa trên evidence thay vì đoán.

# 10. Core Web Vitals với LCP, INP, CLS: đo trải nghiệm thật của browser thay vì chỉ nhìn backend response time

## 1. What is it?

Core Web Vitals là nhóm user-experience metrics tập trung vào loading, responsiveness và visual stability.

Ba metrics chính:

```text
LCP -> nội dung lớn chính hiển thị nhanh đến đâu
INP -> trang phản hồi interaction nhanh đến đâu
CLS -> layout có nhảy bất ngờ hay không
```

Backend latency chỉ là một phần trong full page lifecycle.

## 2. Why does it exist?

Một API trả 100 ms không đảm bảo page nhanh. Browser còn phải:

- download HTML/CSS/JS/images;
- parse;
- execute JavaScript;
- render;
- load fonts;
- hydrate frontend;
- respond event handlers.

Nếu JS main thread bị block 800 ms, user thấy app chậm dù backend rất khỏe.

## 3. How does it work?

LCP thường bị ảnh hưởng bởi:

- TTFB;
- render-blocking resources;
- hero image/font loading;
- client-side rendering delay.

INP bị ảnh hưởng bởi long tasks, heavy JS và expensive render/update.

CLS tăng khi elements thay đổi vị trí do images/ads/fonts không reserve space.

## 4. Practical implementation

Một investigation flow:

```text
Field metric poor
   |
segment by page/device/network
   |
DevTools/Lighthouse trace
   |
network + main-thread + layout evidence
   |
fix bottleneck
   |
measure field data again
```

Ví dụ cải thiện LCP image:

```html
<img
  src="/hero.avif"
  width="1600"
  height="900"
  fetchpriority="high"
  alt="Product hero">
```

Kích thước giúp reserve layout; `fetchpriority` chỉ nên dùng có chủ đích cho critical resource.

## 5. Real production scenario

Marketing site dùng CDN và backend TTFB ~120 ms nhưng LCP trên mobile >4 s. Waterfall cho thấy hero image 3 MB được discovered muộn sau client-side JavaScript và CSS background processing.

Tối ưu backend thêm 20 ms gần như không ảnh hưởng UX. Fix thực sự là resource prioritization, image sizing/compression và render path.

## 6. Failure scenario & troubleshooting

**Symptom** → synthetic desktop test xanh nhưng real-user mobile INP/LCP xấu.

**Evidence** → field telemetry cho thấy low-end devices/mobile network tệ hơn lab; browser trace có long tasks hoặc late LCP discovery.

**Hypothesis** → lab environment không đại diện real users hoặc bottleneck nằm client-side.

**Diagnosis** → kết hợp RUM/field data, Lighthouse/DevTools và backend traces.

**Fix** → tối ưu critical rendering path, JS execution, image/font delivery hoặc API waterfall đúng bottleneck.

**Verification** → theo dõi percentile field metrics sau rollout, không chỉ rerun một Lighthouse test.

## 7. Common mistakes

- Chỉ tối ưu server response time.
- Dùng Lighthouse score như single source of truth.
- Lazy-load LCP image vô điều kiện.
- Không set dimensions cho images/components async.
- Ship quá nhiều third-party JavaScript.
- Fix average metric nhưng bỏ mobile percentile/users chậm.
- Dùng CDN nhưng cache headers sai nên assets vẫn về origin thường xuyên.

## 8. Alternatives

Không có metric duy nhất thay thế Core Web Vitals. Nên kết hợp:

- backend APM;
- CDN telemetry;
- browser RUM;
- Lighthouse/DevTools;
- business conversion/error metrics.

## 9. Trade-offs

### Advantages

- Đo gần user experience hơn backend-only latency.
- Chỉ ra frontend/network/render bottlenecks.
- Hữu ích cho SEO engineering và product quality.

### Costs / Risks

- Field metrics bị ảnh hưởng device/network diversity.
- Tối ưu một metric cực đoan có thể làm code/UX phức tạp hơn.
- Third-party scripts/assets giới hạn khả năng kiểm soát.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu page speed là browser pipeline, không chỉ API speed.

### Middle

Biết dùng DevTools waterfall/performance và giải thích LCP/INP/CLS basics.

### Senior

Kết hợp field telemetry với backend traces/CDN metrics để localize bottleneck.

### Technical Lead / Architect

Đặt performance budgets và ownership xuyên frontend, backend, CDN, CMS và third-party integrations.

## 11. Key takeaway

- Backend nhanh không đồng nghĩa user thấy page nhanh.
- Dùng field data + browser evidence để tối ưu đúng bottleneck.
- LCP, INP và CLS phản ánh ba failure modes khác nhau: loading, interaction và layout stability.
