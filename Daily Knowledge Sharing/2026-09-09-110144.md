# 1. C# `IAsyncEnumerable<T>`: stream dữ liệu từng phần mà không biến async pipeline thành unbounded buffering

## 1. What is it?

`IAsyncEnumerable<T>` là abstraction của C# cho một chuỗi dữ liệu được tạo ra bất đồng bộ từng phần. Thay vì chờ toàn bộ dataset hoàn tất rồi trả về `List<T>`, consumer có thể nhận item ngay khi producer tạo xong item đó.

Mental model:

```text
Producer fetches item 1 ──> consumer handles item 1
Producer fetches item 2 ──> consumer handles item 2
Producer fetches item 3 ──> consumer handles item 3
...
```

Điểm quan trọng là **streaming semantics**. `IAsyncEnumerable<T>` không tự động bảo đảm backpressure, bounded memory hoặc network streaming; những đặc tính đó còn phụ thuộc producer, serializer và consumer.

## 2. Why does it exist?

Một endpoint export 500.000 records không nên luôn làm:

```csharp
var rows = await repository.GetEverythingAsync();
return Results.Ok(rows);
```

Cách này buộc application giữ toàn bộ result trong memory trước khi response hoàn tất. Với nhiều concurrent requests, memory pressure và GC cost tăng mạnh.

Streaming cho phép xử lý dataset lớn theo từng item hoặc batch, giảm peak memory và time-to-first-byte.

## 3. How does it work?

Compiler biến async iterator thành state machine tương tự `async` method. `yield return` phát item mà không kết thúc iterator:

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken cancellationToken)
{
    await foreach (var order in QueryOrdersAsync(cancellationToken))
    {
        yield return Map(order);
    }
}
```

Consumer dùng:

```csharp
await foreach (var order in source.WithCancellation(cancellationToken))
{
    await ProcessAsync(order, cancellationToken);
}
```

Nếu consumer xử lý chậm, producer thường chỉ tiến khi consumer gọi `MoveNextAsync()`. Nhưng nếu producer tự tạo background queue không bounded, lợi ích này có thể bị mất.

## 4. Practical implementation

Một data-export pipeline có thể stream EF Core query:

```csharp
public IAsyncEnumerable<OrderExportRow> StreamAsync(
    DateTime from,
    CancellationToken cancellationToken)
{
    return _db.Orders
        .AsNoTracking()
        .Where(x => x.CreatedAt >= from)
        .OrderBy(x => x.Id)
        .Select(x => new OrderExportRow(
            x.Id,
            x.Number,
            x.Total,
            x.CreatedAt))
        .AsAsyncEnumerable();
}
```

Consumer ghi CSV từng dòng:

```csharp
await foreach (var row in service.StreamAsync(from, ct)
    .WithCancellation(ct))
{
    await writer.WriteLineAsync(
        $"{row.Id},{row.Number},{row.Total},{row.CreatedAt:O}");
}
```

Với ASP.NET Core, cần xác minh serializer/response path thực sự flush theo stream mong muốn; không giả định rằng chỉ cần return `IAsyncEnumerable<T>` là mọi reverse proxy đều truyền từng item ngay lập tức.

## 5. Real production scenario

Một reporting API trả 300.000 invoices. Version đầu materialize bằng `ToListAsync()`, khiến mỗi request dùng hàng trăm MB memory. Khi ba enterprise users export đồng thời, pod/container bắt đầu GC liên tục và cuối cùng OOM.

Chuyển sang async streaming + projection nhỏ + response compression phù hợp giúp peak memory gần như không phụ thuộc toàn bộ dataset size.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint “streaming” vẫn dùng rất nhiều memory.

**Evidence** → profiler cho thấy một `List<T>` lớn hoặc buffering middleware/serializer vẫn giữ toàn response.

**Hypothesis** → pipeline đã materialize hoặc buffer ở giữa.

**Diagnosis** → kiểm tra `ToListAsync`, `ToArrayAsync`, custom mapping, response compression/proxy buffering và producer queue.

**Fix** → giữ dữ liệu lazy xuyên pipeline, projection nhỏ, batch hợp lý và bỏ unbounded intermediate buffers.

**Verification** → load test với dataset tăng từ 10k → 100k → 1M rows; peak memory phải tăng chậm hơn nhiều so với dataset size.

## 7. Common mistakes

* Gọi `ToListAsync()` trước khi `yield return`.
* Không propagate `CancellationToken` khi client disconnect.
* Giữ `DbContext` sống quá lâu mà không hiểu connection lifetime.
* Dùng async stream cho dataset nhỏ khiến code phức tạp vô ích.
* Tạo producer background task đẩy vô hạn vào `Channel<T>` unbounded.

## 8. Alternatives

Pagination phù hợp API interactive. Batch processing phù hợp background jobs. `Channel<T>` phù hợp producer/consumer cần decoupling rõ ràng. File export sang Blob Storage rồi trả download link thường tốt hơn nếu job kéo dài nhiều phút.

## 9. Trade-offs

### Advantages

* Giảm peak memory.
* Time-to-first-item thấp hơn.
* Natural fit cho large sequential datasets.

### Costs / Risks

* Error có thể xảy ra sau khi response đã bắt đầu.
* Transaction/connection có thể tồn tại lâu hơn.
* Proxy/client buffering có thể làm mất lợi ích streaming.
* Retry toàn stream phức tạp hơn retry request ngắn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác biệt giữa materialize toàn bộ và consume từng item.

### Middle

Biết dùng async iterator, cancellation và EF Core projection.

### Senior

Phân tích buffering, connection lifetime, backpressure và partial-failure semantics.

### Technical Lead / Architect

Quyết định khi nào stream trực tiếp, khi nào pagination, khi nào chuyển export sang asynchronous job/object storage.

## 11. Key takeaway

* `IAsyncEnumerable<T>` là streaming abstraction, không phải magic low-memory switch.
* Phải tránh materialization/buffering ở mọi layer giữa producer và consumer.
* Long-lived streams cần cancellation, timeout và resource-lifetime policy rõ ràng.

# 2. ASP.NET Core `HttpClientFactory`: handler lifetime, DNS rotation và socket exhaustion trong outbound HTTP

## 1. What is it?

`IHttpClientFactory` là cơ chế quản lý `HttpClient` và underlying handlers trong .NET. Mục tiêu chính không phải “factory pattern cho đẹp”, mà là quản lý connection pooling, DNS changes, handler lifetime và centralized outbound HTTP configuration.

Mental model:

```text
HttpClient instance
      ↓
HttpMessageHandler
      ↓
connection pool
      ↓
DNS/IP endpoints
```

Một `HttpClient` mới không nhất thiết đồng nghĩa một TCP connection mới, nhưng tạo/dispose handler sai cách có thể phá connection reuse.

## 2. Why does it exist?

Anti-pattern kinh điển:

```csharp
using var client = new HttpClient();
await client.GetAsync(url);
```

Nếu làm liên tục với handler mới, connection đi vào `TIME_WAIT`, socket reuse kém và dưới tải cao có thể cạn ephemeral ports.

Ngược lại, giữ một handler mãi mãi có thể giữ DNS resolution cũ quá lâu trong môi trường service discovery hoặc load balancing động.

## 3. How does it work?

`IHttpClientFactory` tạo `HttpClient` objects ngắn hạn nhưng pool/reuse handlers theo configured lifetime. Handler chứa connection pools; khi handler được rotate, DNS và connections được làm mới theo lifecycle mới.

```csharp
builder.Services.AddHttpClient<PricingClient>(client =>
{
    client.BaseAddress = new Uri("https://pricing.internal/");
    client.Timeout = TimeSpan.FromSeconds(3);
});
```

Typed client nhận `HttpClient` qua DI nhưng không sở hữu raw socket lifecycle trực tiếp.

## 4. Practical implementation

```csharp
builder.Services.AddHttpClient<InventoryClient>(client =>
{
    client.BaseAddress = new Uri(config["Inventory:BaseUrl"]!);
    client.DefaultRequestHeaders.UserAgent.ParseAdd("OrdersApi/1.0");
})
.SetHandlerLifetime(TimeSpan.FromMinutes(5));
```

Client:

```csharp
public sealed class InventoryClient(HttpClient httpClient)
{
    public async Task<InventoryDto?> GetAsync(
        Guid productId,
        CancellationToken cancellationToken)
    {
        using var response = await httpClient.GetAsync(
            $"inventory/{productId}",
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        response.EnsureSuccessStatusCode();

        return await response.Content.ReadFromJsonAsync<InventoryDto>(
            cancellationToken: cancellationToken);
    }
}
```

Resilience policy phải phù hợp semantics; không retry POST/payment tùy tiện nếu chưa có idempotency.

## 5. Real production scenario

Một API gọi 6 downstream services mỗi request. Team tạo `new HttpClient()` trong từng method. Staging traffic thấp nên ổn. Production bắt đầu có intermittent `SocketException`, connect timeout và số connections tăng bất thường dù downstream healthy.

Sau khi chuyển sang managed clients + handler pooling + bounded timeouts, socket usage ổn định hơn và telemetry theo dependency rõ ràng hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → outbound HTTP thỉnh thoảng connect timeout sau deploy infrastructure/DNS change.

**Evidence** → service DNS đã trỏ IP mới nhưng process vẫn giữ connections tới IP cũ.

**Hypothesis** → handler/connection lifetime quá dài hoặc DNS refresh behavior không phù hợp.

**Diagnosis** → kiểm tra handler lifetime, connection pool metrics, DNS TTL, Service Discovery behavior và destination IP trong traces/network diagnostics.

**Fix** → cấu hình handler/connection lifetime phù hợp, không dispose handler per call, và để infrastructure load-balancing model quyết định refresh cadence.

**Verification** → rotate backend IP trong controlled test và xác nhận clients migrate sang endpoint mới mà không outage kéo dài.

## 7. Common mistakes

* `new HttpClient()` cho mỗi request.
* Retry mọi HTTP method giống nhau.
* Timeout 100 giây mặc định cho dependency có latency budget 500 ms.
* Đăng ký typed client rồi capture nó trong Singleton không hiểu lifetime.
* Log full request/response có secrets hoặc PII.

## 8. Alternatives

Một static `HttpClient` cấu hình đúng `SocketsHttpHandler.PooledConnectionLifetime` cũng có thể tốt. `IHttpClientFactory` đặc biệt hữu ích khi có nhiều named/typed clients, policies và centralized instrumentation.

## 9. Trade-offs

### Advantages

* Connection reuse tốt hơn.
* Centralized config và observability.
* Dễ quản lý DNS/handler rotation.

### Costs / Risks

* Policy layering có thể phức tạp.
* Handler lifetime sai vẫn gây vấn đề.
* Retry/circuit breaker dùng máy móc có thể khuếch đại tải.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Không tạo/dispose `HttpClient` tùy tiện trên mỗi call.

### Middle

Dùng typed/named clients, timeout và cancellation đúng.

### Senior

Hiểu handler pools, DNS rotation, connection lifetime và retry semantics.

### Technical Lead / Architect

Chuẩn hóa outbound HTTP policies, latency budgets, telemetry và idempotency requirements toàn platform.

## 11. Key takeaway

* `HttpClientFactory` chủ yếu giải quyết lifecycle của handlers/connections, không chỉ object creation.
* DNS và socket behavior là production concern thực sự.
* Resilience policy phải dựa trên operation semantics, không dựa trên “retry luôn cho chắc”.

# 3. SQL Server statistics + cardinality estimation: plan xấu bắt đầu từ việc optimizer đoán sai số lượng rows như thế nào

## 1. What is it?

SQL Server statistics mô tả distribution của dữ liệu để Query Optimizer ước lượng số rows sẽ đi qua từng operator. Cardinality estimation là quá trình dùng statistics + assumptions để dự đoán row count trước khi query chạy.

Execution plan tốt phụ thuộc rất lớn vào câu hỏi:

```text
Optimizer nghĩ sẽ có bao nhiêu rows?
```

Nếu câu trả lời sai hàng nghìn lần, join strategy, memory grant, parallelism và index access path đều có thể sai.

## 2. Why does it exist?

Optimizer không chạy thử mọi plan. Nó cần metadata để ước lượng chi phí. Statistics cung cấp histogram, density và row counts để so sánh các plan candidates.

Ví dụ optimizer đoán 10 rows nhưng thực tế 2 triệu rows; Nested Loops có thể được chọn trong khi Hash Join hoặc scan khác hợp lý hơn.

## 3. How does it work?

Statistics có thể được tạo tự động trên indexed columns hoặc columns được query. SQL Server update statistics theo thresholds/changes, nhưng workload lớn hoặc skewed data vẫn có thể khiến metadata không phản ánh distribution hiện tại đủ tốt.

Query:

```sql
SELECT o.Id, o.Total
FROM Orders o
WHERE o.Status = @Status
  AND o.CreatedAt >= @From;
```

Nếu `Status='Pending'` chỉ có 0.1% rows nhưng `Status='Completed'` có 95%, cùng predicate shape có distribution rất khác.

## 4. Practical implementation

Kiểm tra statistics metadata:

```sql
DBCC SHOW_STATISTICS ('dbo.Orders', 'IX_Orders_Status_CreatedAt');
```

Trong Actual Execution Plan, so sánh:

* Estimated Number of Rows;
* Actual Number of Rows;
* join type;
* memory grant;
* spills;
* logical reads.

Có thể update có chủ đích:

```sql
UPDATE STATISTICS dbo.Orders IX_Orders_Status_CreatedAt WITH FULLSCAN;
```

Nhưng `FULLSCAN` không phải default fix cho mọi table lớn; maintenance cost phải được đo.

## 5. Real production scenario

Một ingestion job thêm 40 triệu rows mới trong vài giờ. Dashboard query vốn chạy 100 ms tăng lên 12 giây. Index vẫn tồn tại và CPU không quá cao.

Actual plan cho thấy optimizer ước lượng vài nghìn rows nhưng thực tế vài triệu. Memory grant quá nhỏ dẫn tới spill và join strategy kém. Statistics refresh + index/query review phục hồi plan phù hợp hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → query đột nhiên chậm sau bulk load nhưng SQL text không đổi.

**Evidence** → Estimated Rows lệch rất xa Actual Rows.

**Hypothesis** → statistics stale hoặc distribution skew không được mô hình hóa tốt.

**Diagnosis** → xem statistics last updated, histogram, data distribution, parameter values và Query Store plan history.

**Fix** → refresh statistics có mục tiêu, cải thiện index/query shape hoặc xử lý parameter-sensitive workload đúng cách.

**Verification** → test nhiều representative parameter classes và so estimated/actual rows sau fix.

## 7. Common mistakes

* Rebuild mọi index khi chỉ cần statistics review.
* Clear plan cache toàn server như giải pháp dài hạn.
* Chỉ nhìn duration mà không nhìn estimated-vs-actual rows.
* `FULLSCAN` mọi table nightly dù chi phí rất cao.
* Test query chỉ với một parameter “đẹp”.

## 8. Alternatives

Filtered statistics/indexes giúp distribution subset đặc thù. Query Store hỗ trợ plan analysis. Với extreme skew, đôi khi cần query path riêng, partitioning hoặc data-model change.

## 9. Trade-offs

### Advantages

* Statistics tốt giúp optimizer ra quyết định gần reality hơn.
* Có thể sửa plan regression mà không đổi business logic.

### Costs / Risks

* Statistics maintenance tiêu tốn I/O/CPU.
* Histogram không mô tả hoàn hảo mọi correlation giữa columns.
* Refresh statistics có thể tạo plan mới tốt hoặc xấu tùy workload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết optimizer dựa trên estimated row counts.

### Middle

Đọc estimated vs actual rows và `DBCC SHOW_STATISTICS`.

### Senior

Phân tích skew, stale stats, memory grant và plan regressions.

### Technical Lead / Architect

Thiết kế statistics/index maintenance theo data-change pattern thay vì cron job cố định thiếu căn cứ.

## 11. Key takeaway

* Cardinality estimate sai thường là nguồn gốc của plan sai.
* Đừng chỉ hỏi “có index chưa”; hãy hỏi optimizer hiểu data distribution đúng chưa.
* Statistics maintenance phải dựa trên workload và data volatility.

# 4. MongoDB compound index theo ESR rule: Equality → Sort → Range và lý do thứ tự field trong index quyết định hiệu năng

## 1. What is it?

Compound index trong MongoDB chứa nhiều fields theo một thứ tự xác định. ESR là heuristic phổ biến:

```text
Equality → Sort → Range
```

Tức là các field equality thường đứng trước, tiếp theo là fields phục vụ sort, rồi range predicates.

Đây không phải luật tuyệt đối, nhưng là mental model tốt để thiết kế index theo query shape.

## 2. Why does it exist?

Index B-tree có prefix order. Một index:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

không tương đương:

```javascript
{ createdAt: -1, tenantId: 1, status: 1 }
```

Với query multi-tenant equality + status equality + sort theo thời gian, thứ tự đầu thường cho phép engine thu hẹp prefix sớm và trả kết quả đã đúng sort order.

## 3. How does it work?

Query:

```javascript
db.orders.find({
  tenantId: "T1",
  status: "Pending",
  total: { $gte: 100 }
}).sort({ createdAt: -1 })
```

Một candidate index:

```javascript
{ tenantId: 1, status: 1, createdAt: -1, total: 1 }
```

Equality fields thu hẹp index range trước. Sort field tiếp theo giữ ordering hữu ích. Range field thường nằm sau vì range có thể làm giảm khả năng sử dụng phần suffix cho ordered traversal.

## 4. Practical implementation

Tạo index:

```javascript
db.orders.createIndex({
  tenantId: 1,
  status: 1,
  createdAt: -1,
  total: 1
})
```

Đo plan:

```javascript
db.orders.find({
  tenantId: "T1",
  status: "Pending"
})
.sort({ createdAt: -1 })
.limit(100)
.explain("executionStats")
```

Quan sát:

* `IXSCAN` hay `COLLSCAN`;
* `totalKeysExamined`;
* `totalDocsExamined`;
* số documents returned;
* có blocking sort hay không.

## 5. Real production scenario

Activity feed cho mỗi tenant query 50 events mới nhất. Collection có 200 triệu documents. Index chỉ trên `createdAt` giúp sort nhưng phải scan rất nhiều tenants khác trước khi filter.

Đổi sang compound index bắt đầu bằng `tenantId`, sau đó event type/status và `createdAt` giúp scan nhỏ hơn nhiều và latency ổn định theo tenant.

## 6. Failure scenario & troubleshooting

**Symptom** → query có index nhưng `totalKeysExamined` lớn gấp hàng nghìn lần `nReturned`.

**Evidence** → index prefix không khớp equality filters chính.

**Hypothesis** → field order không phù hợp query shape.

**Diagnosis** → `explain("executionStats")`, so sánh candidate indexes và real parameter distributions.

**Fix** → thiết kế compound index theo dominant access pattern; xóa duplicate/redundant indexes sau khi đo.

**Verification** → benchmark representative tenants, bao gồm tenant lớn nhất và nhỏ nhất.

## 7. Common mistakes

* Tạo một index cho từng field rồi mong MongoDB luôn kết hợp tối ưu.
* Đặt range field trước equality field quan trọng.
* Tạo quá nhiều indexes làm write amplification tăng.
* Không đo `keysExamined/docsExamined`.
* Thiết kế index theo schema thay vì query patterns.

## 8. Alternatives

Index intersection đôi khi hữu ích nhưng không thay thế compound index cho hot path. Partial indexes, sparse indexes hoặc data partition/sharding có thể phù hợp hơn tùy workload.

## 9. Trade-offs

### Advantages

* Query latency ổn định hơn.
* Có thể phục vụ cả filter và sort.
* Giảm documents examined.

### Costs / Risks

* Mỗi compound index tăng storage và write cost.
* Index tốt cho query A có thể không tốt cho query B.
* Thứ tự fields gắn chặt với access patterns.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu compound index có thứ tự, không chỉ tập fields.

### Middle

Dùng `explain` và ESR heuristic.

### Senior

Đánh giá selectivity, sort, range, index coverage và write amplification.

### Technical Lead / Architect

Thiết kế indexing portfolio theo workload classes và data growth, không theo từng ticket chậm riêng lẻ.

## 11. Key takeaway

* Compound-index field order là phần của query design.
* ESR là heuristic hữu ích nhưng phải xác minh bằng `explain` và dữ liệu thật.
* Index nhiều hơn không đồng nghĩa tốt hơn.

# 5. DDD Aggregate boundaries: invariant, transaction boundary và cách tránh “mega aggregate” khóa cả domain

## 1. What is it?

Trong Domain-Driven Design, Aggregate là một cluster của domain objects được thay đổi như một consistency boundary. Aggregate Root là entry point duy nhất cho mutations từ bên ngoài.

Mental model:

```text
Command
  ↓
Aggregate Root
  ↓
enforce invariants
  ↓
commit one consistency boundary
```

Aggregate không phải đơn giản là “entity có child collection”. Boundary nên phản ánh những invariants nào phải đúng **ngay trong cùng transaction**.

## 2. Why does it exist?

Nếu mọi entity liên quan đều nằm trong một giant aggregate, mỗi update phải load/lock quá nhiều state, transaction dài và contention tăng.

Ngược lại, nếu tách quá nhỏ, invariant cần atomicity có thể bị phá.

Câu hỏi trung tâm:

> Những dữ liệu nào bắt buộc phải nhất quán ngay tại thời điểm commit?

## 3. How does it work?

Ví dụ Order có thể là aggregate gồm `Order` + `OrderLine` vì invariant tổng tiền và line quantity phải nhất quán cùng mutation.

Nhưng Customer credit profile có thể là aggregate khác. Order chỉ giữ `CustomerId` thay vì object graph Customer đầy đủ.

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public IReadOnlyCollection<OrderLine> Lines => _lines;
    public Money Total => _lines.Aggregate(
        Money.Zero,
        (sum, line) => sum + line.Subtotal);

    public void AddLine(ProductId productId, int quantity, Money price)
    {
        if (quantity <= 0)
            throw new DomainException("Quantity must be positive.");

        _lines.Add(new OrderLine(productId, quantity, price));
    }
}
```

## 4. Practical implementation

Application service nên load aggregate root, gọi domain behavior rồi commit:

```csharp
var order = await repository.GetAsync(orderId, ct)
    ?? throw new NotFoundException();

order.AddLine(productId, quantity, price);

await unitOfWork.SaveChangesAsync(ct);
```

Không nên để controller update trực tiếp child entities bằng setters nếu invariant thuộc aggregate.

Cross-aggregate consistency thường xử lý bằng process/eventual consistency nếu business cho phép.

## 5. Real production scenario

Một ecommerce system model `Customer` aggregate chứa addresses, orders, payments, loyalty history và support cases. Chỉ đổi shipping address cũng load graph lớn và gây optimistic concurrency conflict với payment process.

Tách boundaries theo invariants giúp address/profile, order và payment evolve độc lập hơn, giảm contention và transaction scope.

## 6. Failure scenario & troubleshooting

**Symptom** → nhiều concurrency conflicts giữa operations không liên quan business-wise.

**Evidence** → mọi mutation đều update cùng aggregate/version row.

**Hypothesis** → aggregate boundary quá lớn.

**Diagnosis** → liệt kê invariants và transactions; tìm objects chỉ “có liên quan” nhưng không cần atomic consistency.

**Fix** → split aggregate, reference bằng IDs, dùng domain events/process manager cho cross-boundary workflow.

**Verification** → concurrency tests cho independent commands và invariant tests cho từng aggregate.

## 7. Common mistakes

* Một database table = một aggregate.
* Một object graph UI = một aggregate.
* Aggregate chứa hàng nghìn children không bounded.
* Cross-aggregate transaction chỉ để giữ “mọi thứ strong consistent”.
* Expose setters khiến invariant bị bypass.

## 8. Alternatives

CRUD/anemic model có thể đủ cho domain đơn giản. Transaction Script phù hợp use case ít business rules. Aggregate modeling đáng giá khi invariants và concurrent changes đủ phức tạp.

## 9. Trade-offs

### Advantages

* Invariants rõ ràng.
* Transaction boundary nhỏ hơn.
* Domain behavior tập trung.

### Costs / Risks

* Eventual consistency xuất hiện giữa aggregates.
* Boundary sai gây coupling hoặc consistency bugs.
* Repository/event workflows phức tạp hơn CRUD đơn giản.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu aggregate không đồng nghĩa toàn bộ object graph liên quan.

### Middle

Đặt invariant logic trong aggregate root.

### Senior

Thiết kế boundary dựa trên transactional consistency và concurrency.

### Technical Lead / Architect

Cân bằng domain purity, scalability, eventual consistency và operational simplicity toàn hệ thống.

## 11. Key takeaway

* Aggregate boundary là consistency/transaction boundary.
* Chỉ gom những state thật sự cần atomic invariant.
* Mega aggregate thường tạo contention và coupling không cần thiết.

# 6. Event schema evolution: thay đổi message contract mà không phá consumer cũ hoặc khả năng replay

## 1. What is it?

Event schema evolution là cách thay đổi contract của event/message theo thời gian trong khi producers, consumers và historical events có thể đang ở nhiều versions khác nhau.

Khác HTTP request ngắn hạn, event thường tồn tại lâu trong queue, archive hoặc event store. Một consumer deploy hôm nay có thể đọc message được tạo nhiều tháng trước.

## 2. Why does it exist?

Breaking change đơn giản như đổi:

```json
{ "total": 100 }
```

thành:

```json
{ "total": { "amount": 100, "currency": "USD" } }
```

có thể làm consumer cũ deserialize fail hoặc replay lịch sử thất bại.

Distributed deployment nghĩa là producer và consumers hiếm khi nâng version đồng thời tuyệt đối.

## 3. How does it work?

Một strategy phổ biến là ưu tiên additive changes:

```json
{
  "eventType": "OrderPlaced",
  "schemaVersion": 2,
  "orderId": "...",
  "total": 100,
  "currency": "USD"
}
```

Consumer nên tolerant với fields mới mà nó không dùng. Breaking semantic changes có thể yêu cầu event type/version mới hoặc upcaster khi replay.

Mental model:

```text
Old events v1 ─┐
New events v2 ─┼─> compatibility/upcast layer ─> current domain handler
Future v3    ──┘
```

## 4. Practical implementation

C# envelope:

```csharp
public sealed record EventEnvelope<T>(
    string EventType,
    int SchemaVersion,
    Guid EventId,
    DateTimeOffset OccurredAt,
    T Data);
```

Deserializer có thể route theo version:

```csharp
return envelope.SchemaVersion switch
{
    1 => UpcastV1ToCurrent(envelope),
    2 => DeserializeCurrent(envelope),
    _ => throw new UnsupportedEventVersionException()
};
```

Schema registry hoặc contract tests giúp enforce compatibility trước deploy.

## 5. Real production scenario

Billing consumer dùng `OrderPlaced` để generate invoice. Producer thêm currency support. Nếu rename `total` trực tiếp, billing version cũ fail hàng loạt messages và DLQ tăng.

Additive field + migration window cho phép consumers nâng cấp dần. Khi semantics thật sự thay đổi, một new event type hoặc explicit version giúp tránh ambiguity.

## 6. Failure scenario & troubleshooting

**Symptom** → consumer deploy mới chạy bình thường với current traffic nhưng replay archive fail ở events cũ.

**Evidence** → deserializer chỉ hiểu schema hiện tại.

**Hypothesis** → backward replay compatibility bị bỏ qua.

**Diagnosis** → replay representative historical event versions trong CI/staging.

**Fix** → upcaster/version routing hoặc migration historical data nếu architecture cho phép.

**Verification** → test producer-current → consumer-old, producer-current → consumer-current và replay-old → consumer-current.

## 7. Common mistakes

* Rename/remove field vì “consumer đã deploy rồi”.
* Reuse cùng event name nhưng đổi semantics hoàn toàn.
* Không lưu schema version hoặc event type rõ.
* Consumer reject unknown optional fields.
* Chỉ test current messages, không test replay.

## 8. Alternatives

New event type cho semantic break lớn. Schema Registry với Avro/Protobuf hỗ trợ compatibility rules mạnh hơn. Snapshot/migration có thể giảm replay depth trong event-sourced systems.

## 9. Trade-offs

### Advantages

* Independent deployment an toàn hơn.
* Replay đáng tin cậy hơn.
* Consumer migration có kiểm soát.

### Costs / Risks

* Phải maintain old contracts/upcasters.
* Test matrix tăng.
* Semantic compatibility khó hơn structural compatibility.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu message là contract giữa processes.

### Middle

Ưu tiên additive changes và tolerant deserialization.

### Senior

Thiết kế versioning, replay compatibility và schema tests.

### Technical Lead / Architect

Đặt event-contract governance, retention/replay policy và compatibility guarantees cho toàn platform.

## 11. Key takeaway

* Event contract sống lâu hơn một deployment.
* Additive evolution thường an toàn nhất.
* Replay compatibility phải được test như first-class requirement.

# 7. Azure Container Apps revisions + traffic splitting: rollout an toàn, rollback nhanh và tránh config drift giữa revisions

## 1. What is it?

Azure Container Apps revision là immutable snapshot của một app version/configuration có thể chạy song song với revisions khác. Traffic splitting cho phép phân phối phần trăm traffic giữa các revisions.

Mental model:

```text
Revision A (stable) 90%
Revision B (new)    10%
          ↓
observe metrics/errors
          ↓
B 100% or rollback to A
```

Đây là primitive hữu ích cho canary rollout và zero/low-downtime deployment.

## 2. Why does it exist?

Nếu deploy luôn thay 100% instances ngay lập tức, một bug chỉ xuất hiện với production traffic sẽ ảnh hưởng toàn bộ users trước khi team phản ứng.

Parallel revisions tạo migration window và rollback path nhanh hơn redeploy image cũ.

## 3. How does it work?

Một thay đổi revision-scope như container image/config có thể tạo revision mới. Multiple revision mode cho phép nhiều revisions active cùng lúc và gán traffic weights.

Nhưng database/schema vẫn là shared dependency; traffic splitting không tự giải quyết backward-incompatible migration.

## 4. Practical implementation

Deployment discipline:

```text
1. Build immutable image tag/digest
2. Deploy new revision with backward-compatible config
3. Route 5–10% traffic
4. Compare error rate, latency, dependency failures
5. Increase 25% → 50% → 100%
6. Keep previous revision ready for rollback window
```

Application nên expose revision/build metadata trong telemetry để metrics có thể split theo version.

Ví dụ log scope:

```csharp
logger.LogInformation(
    "Application started. Revision={Revision} Commit={Commit}",
    revisionName,
    commitSha);
```

## 5. Real production scenario

Checkout API version mới có serialization regression chỉ xảy ra với một legacy mobile payload. Canary 10% traffic cho thấy 400 rate tăng ở revision mới trong vài phút. Team route traffic về stable revision mà không cần build lại image.

Nếu deploy 100% ngay, toàn bộ mobile clients bị ảnh hưởng.

## 6. Failure scenario & troubleshooting

**Symptom** → canary revision healthy ở infrastructure level nhưng error rate business tăng.

**Evidence** → CPU/memory bình thường, nhưng `checkout_failed` và HTTP 4xx/5xx tăng riêng revision B.

**Hypothesis** → application contract regression, không phải container health.

**Diagnosis** → segment telemetry theo revision, client version, endpoint và dependency.

**Fix** → shift traffic về stable revision, sửa code, tạo revision mới; không mutate historical revision để “vá”.

**Verification** → canary lại với same problematic traffic segment.

## 7. Common mistakes

* Dùng `latest` image tag thay immutable digest/version.
* Canary app nhưng chạy destructive DB migration trước đó.
* Không tag telemetry theo revision.
* Secret/config drift khiến rollback revision cũ không còn chạy đúng.
* Health check xanh được coi là đủ để promote 100%.

## 8. Alternatives

AKS có Deployment/Service Mesh patterns sâu hơn. App Service deployment slots phù hợp web apps. Blue-green ở load balancer layer cũng khả thi. Container Apps phù hợp khi muốn managed container platform với operational surface nhỏ hơn Kubernetes đầy đủ.

## 9. Trade-offs

### Advantages

* Canary/blue-green đơn giản hơn.
* Rollback traffic nhanh.
* Immutable revision giúp audit release rõ.

### Costs / Risks

* Multiple revisions tăng temporary capacity cost.
* Shared DB migrations vẫn là hard problem.
* Config/secret lifecycle phải tương thích rollback.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu revision là deployable snapshot, không chỉ replica.

### Middle

Biết traffic splitting, health checks và immutable images.

### Senior

Thiết kế canary metrics, rollback và backward-compatible migrations.

### Technical Lead / Architect

Định nghĩa progressive-delivery policy và promotion gates cho platform.

## 11. Key takeaway

* Traffic splitting giảm blast radius nhưng không sửa incompatible database changes.
* Canary phải dựa trên business + technical telemetry.
* Immutable artifacts và rollback compatibility là nền tảng của safe deployment.

# 8. Elasticsearch refresh interval: near-real-time search, read-after-write mismatch và chi phí của refresh quá thường xuyên

## 1. What is it?

Elasticsearch là near-real-time search engine. Document được index thành công không nhất thiết lập tức xuất hiện trong search result. Refresh tạo searchable segments từ dữ liệu mới trong indexing buffers.

Mental model:

```text
index request acknowledged
        ↓
not necessarily searchable yet
        ↓
refresh
        ↓
document visible to search
```

Đây là consistency characteristic cần được hiểu ở application layer.

## 2. Why does it exist?

Nếu mỗi document write bắt buộc sync flush/refresh ngay, indexing throughput sẽ giảm mạnh vì Lucene phải tạo nhiều small segments và tăng merge overhead.

Near-real-time model đánh đổi một khoảng visibility delay nhỏ để đạt indexing/search throughput tốt hơn.

## 3. How does it work?

Index có `refresh_interval`. Elasticsearch định kỳ refresh active shards. Request có thể dùng refresh behavior đặc biệt như chờ refresh khi business thật sự cần read-after-write search visibility.

Nhưng ép refresh trên mọi write biến throughput workload thành latency-sensitive sync workflow.

## 4. Practical implementation

Với user action cần search thấy document ngay, có thể dùng chiến lược có mục tiêu thay vì global refresh cực ngắn.

Ví dụ concept:

```http
POST /products/_doc/123?refresh=wait_for
{
  "name": "Keyboard",
  "price": 100
}
```

Bulk ingestion thì ưu tiên throughput:

```text
Bulk index many documents
→ allow normal refresh cadence
→ query only after ingestion checkpoint if required
```

Theo dõi refresh/merge/indexing metrics thay vì chỉ API latency.

## 5. Real production scenario

Admin tạo product rồi lập tức search product name để edit tiếp. Index API trả 201 nhưng search chưa thấy product trong vài trăm ms/giây, UI báo “not found”.

Fix đúng có thể là UI dùng primary datastore cho immediate confirmation hoặc selective `refresh=wait_for`, thay vì giảm global refresh interval xuống 100 ms cho toàn cluster.

## 6. Failure scenario & troubleshooting

**Symptom** → indexing throughput giảm mạnh sau khi team “fix consistency” bằng refresh rất thường xuyên.

**Evidence** → refresh/segment/merge activity tăng, shard CPU và I/O cao.

**Hypothesis** → refresh cadence quá aggressive.

**Diagnosis** → kiểm tra `refresh_interval`, segment count, merge time và write pattern.

**Fix** → restore reasonable interval, batch writes và chỉ chờ refresh trên critical flows.

**Verification** → benchmark indexing throughput + search freshness SLA cùng lúc.

## 7. Common mistakes

* Giả định index ACK = search visible ngay.
* `refresh=true` trên mọi write.
* Giảm refresh interval toàn cluster để sửa một UI flow.
* Dùng Elasticsearch làm system of record cho transaction cần strong consistency mà không đánh giá semantics.
* Không theo dõi segment/merge pressure.

## 8. Alternatives

Primary DB có thể phục vụ immediate read-after-write. Cache/DB + asynchronous search indexing là common pattern. OpenSearch có semantics tương tự ở mức Lucene-based near-real-time model.

## 9. Trade-offs

### Advantages

* Near-real-time model hỗ trợ high indexing throughput.
* Refresh cadence có thể tune theo workload.

### Costs / Risks

* Search visibility có delay.
* Forced refresh tăng segment/merge overhead.
* Application phải hiểu consistency boundary.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu search visibility không nhất thiết immediate sau index.

### Middle

Biết refresh interval và selective wait-for-refresh.

### Senior

Phân tích segment/merge/indexing throughput và UX consistency needs.

### Technical Lead / Architect

Quyết định system-of-record vs search-index responsibilities và freshness SLA.

## 11. Key takeaway

* Elasticsearch là near-real-time, không phải immediate-consistency database.
* Forced refresh là performance trade-off, không phải free correctness switch.
* Freshness SLA nên được thiết kế theo business flow.

# 9. RED + USE methods trong observability: từ dashboard metrics tới chẩn đoán bottleneck có hệ thống

## 1. What is it?

RED và USE là hai mental models để chọn metrics theo góc nhìn khác nhau.

**RED** cho request-driven services:

```text
Rate      – bao nhiêu requests/events mỗi giây?
Errors    – bao nhiêu request thất bại?
Duration  – latency distribution ra sao?
```

**USE** cho resources:

```text
Utilization – resource bận bao nhiêu?
Saturation  – có queue/wait vì thiếu capacity không?
Errors      – resource có lỗi không?
```

Kết hợp hai model giúp đi từ symptom của service tới bottleneck tài nguyên.

## 2. Why does it exist?

Dashboard có 200 charts không đồng nghĩa observable. Khi incident xảy ra, team cần một navigation path có cấu trúc.

Ví dụ p99 latency tăng. RED cho biết endpoint nào bị ảnh hưởng; USE giúp kiểm tra CPU, ThreadPool, DB connections, disk, queue hoặc downstream saturation.

## 3. How does it work?

Một investigation có thể đi:

```text
RED:
/orders p99 ↑, errors stable, rate ↑
        ↓
USE:
CPU 40%, DB pool utilization 100%, wait queue ↑
        ↓
Hypothesis:
connection pool saturation
```

Điểm quan trọng là **saturation**. CPU chỉ 40% không có nghĩa system còn capacity nếu DB pool, thread pool hoặc queue đã đầy.

## 4. Practical implementation

ASP.NET Core/OpenTelemetry metrics nên có bounded dimensions:

```text
http.server.request.duration{route,status}
http.server.active_requests{route}
db.client.operation.duration{operation}
```

Resource metrics có thể gồm:

```text
process.cpu.utilization
process.runtime.dotnet.gc.heap.size
thread_pool.queue.length
sql.connection_pool.active
sql.connection_pool.pending
queue.message.count
```

Alert nên dựa trên user impact + saturation, không chỉ raw CPU threshold.

## 5. Real production scenario

API p95 tăng từ 150 ms lên 2 giây. CPU 35%, memory 50%, nên initial conclusion là “application không quá tải”.

USE analysis cho thấy SQL connection pool full và pending requests tăng. Root cause là một query mới giữ connections lâu, không phải CPU.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng nhưng dashboard infrastructure “xanh”.

**Evidence** → chỉ có CPU/memory charts, không có queue/saturation metrics.

**Hypothesis** → observability thiếu resource bottleneck signals.

**Diagnosis** → inventory bounded resources: threads, connections, queues, disk I/O, sockets, worker concurrency.

**Fix** → instrument utilization + saturation + errors cho critical resources và RED cho service boundaries.

**Verification** → load test tới saturation và xác nhận dashboard chỉ ra bottleneck trước khi system collapse.

## 7. Common mistakes

* Chỉ alert CPU > 80%.
* Dùng average latency thay p95/p99.
* Không đo queue length/wait time.
* Label metrics bằng user IDs gây cardinality explosion.
* Có dashboard nhưng không có incident navigation logic.

## 8. Alternatives

Golden Signals của SRE gồm latency, traffic, errors, saturation và rất gần RED/USE. Domain-specific business metrics vẫn cần bên cạnh technical metrics.

## 9. Trade-offs

### Advantages

* Investigation path có cấu trúc.
* Dễ phát hiện hidden saturation.
* Giảm dashboard noise.

### Costs / Risks

* Cần xác định đúng bounded resources.
* Metrics không thay traces/logs khi cần drill-down.
* Sai aggregation vẫn có thể che tail latency.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết rate/error/latency khác CPU/memory.

### Middle

Dùng RED cho services và USE cho resources.

### Senior

Correlate service symptom với resource saturation và dependency traces.

### Technical Lead / Architect

Chuẩn hóa observability scorecards, SLO signals và capacity metrics toàn hệ thống.

## 11. Key takeaway

* RED cho biết user-facing symptom; USE giúp tìm resource bottleneck.
* Saturation thường quan trọng hơn raw utilization.
* Dashboard tốt phải hỗ trợ một diagnostic path, không chỉ hiển thị nhiều charts.

# 10. Software supply-chain security với NuGet lock files + SBOM: kiểm soát dependency drift và artifact provenance

## 1. What is it?

Software supply-chain security bảo vệ đường đi từ source code → dependencies → build → artifact → deployment. Hai building blocks hữu ích là:

* dependency lock files để build resolve cùng dependency graph đã được review;
* SBOM (Software Bill of Materials) để biết artifact chứa những components nào.

Mental model:

```text
Source
  + locked dependencies
       ↓
reproducible-ish build
       ↓
artifact + SBOM
       ↓
scan / provenance / deployment policy
```

## 2. Why does it exist?

Một project reference package range hoặc transitive dependency có thể thay đổi giữa hai builds dù source commit giống nhau. Khi CVE xuất hiện, team cũng cần trả lời nhanh:

> Production artifact nào đang chứa package/version bị ảnh hưởng?

Nếu chỉ search `*.csproj`, transitive dependencies và actual deployed artifact có thể bị bỏ sót.

## 3. How does it work?

NuGet `packages.lock.json` ghi resolved dependency graph. Locked mode có thể khiến restore fail nếu graph khác lock file thay vì silently chọn versions mới.

SBOM mô tả components, versions, hashes/relationships tùy format như SPDX/CycloneDX.

Lock file trả lời “build đã resolve gì”; SBOM trả lời “artifact này gồm gì”.

## 4. Practical implementation

Enable lock file trong project/central props:

```xml
<PropertyGroup>
  <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
</PropertyGroup>
```

CI release có thể dùng locked mode:

```bash
dotnet restore --locked-mode
dotnet build --no-restore -c Release
dotnet test --no-build -c Release
```

Pipeline sau đó generate/store SBOM cùng artifact/container image và scan dependency vulnerabilities theo policy.

## 5. Real production scenario

Security team nhận advisory cho transitive NuGet package `X.Y` version vulnerable. Không service nào reference trực tiếp package đó trong `.csproj`, nhưng 12 services kéo nó transitively.

SBOM inventory cho deployed artifacts giúp xác định chính xác services ảnh hưởng thay vì grep source repositories thủ công.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng commit build hôm qua xanh, hôm nay dependency restore tạo behavior khác.

**Evidence** → package graph thay đổi do floating/range/transitive resolution; lock file không được enforce.

**Hypothesis** → dependency drift.

**Diagnosis** → compare assets/lock graph, package feeds và resolved versions giữa builds.

**Fix** → commit lock files theo policy, dùng locked restore cho release, update dependencies qua explicit PR.

**Verification** → rebuild same commit trong clean environment và compare dependency graph/artifact metadata.

## 7. Common mistakes

* Nghĩ lock file bảo đảm binary reproducibility tuyệt đối.
* Generate SBOM nhưng không lưu/link với artifact digest.
* Chỉ scan direct dependencies.
* Auto-update packages thẳng production không review.
* Treat vulnerability severity score như quyết định duy nhất, không xét exploitability/context.

## 8. Alternatives

Central Package Management giúp version governance. Container image digest/signing/provenance frameworks bổ sung artifact identity. Renovate/Dependabot hỗ trợ controlled dependency-update workflow nhưng không thay lock/SBOM inventory.

## 9. Trade-offs

### Advantages

* Dependency drift rõ ràng hơn.
* Incident response cho CVE nhanh hơn.
* Audit artifact composition tốt hơn.

### Costs / Risks

* Lock files cần update discipline.
* SBOM storage/scanning pipeline tăng operational work.
* Scanner có false positives/negatives.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu direct và transitive dependencies đều ảnh hưởng artifact.

### Middle

Dùng lock file, locked restore và dependency-update PRs.

### Senior
