# 1. C# `TimeProvider`, `DateTimeOffset` và testable time: tách business clock khỏi system clock để tránh flaky test và timezone bug

## 1. What is it?

Trong application code, thời gian thường bị lấy trực tiếp bằng `DateTime.UtcNow`, `DateTime.Now` hoặc `DateTimeOffset.UtcNow`. Cách này đơn giản nhưng tạo hidden dependency vào system clock.

`TimeProvider` cung cấp abstraction cho thời gian hiện tại và timer. Mental model quan trọng là:

```text
Business logic
    ↓
TimeProvider
    ↓
System clock / fake clock trong test
```

`DateTimeOffset` biểu diễn một thời điểm cùng offset, phù hợp hơn `DateTime` khi dữ liệu đi qua API, database hoặc nhiều timezone.

## 2. Why does it exist?

Logic kiểu “token hết hạn sau 15 phút”, “đơn hàng chỉ sửa được trong 24 giờ”, “job chạy lại sau 30 giây” đều phụ thuộc thời gian.

Nếu code gọi system clock trực tiếp:

* unit test khó kiểm soát thời gian,
* test dễ phải `Task.Delay`,
* DST và timezone gây bug khó tái hiện,
* boundary gần midnight dễ flaky,
* logic time-based bị trộn với infrastructure concern.

## 3. How does it work?

Application nhận `TimeProvider` qua DI rồi gọi:

```csharp
var now = _timeProvider.GetUtcNow();
```

Trong production dùng `TimeProvider.System`. Trong test có thể dùng fake provider và chủ động advance time.

Time nên được phân biệt thành hai loại:

* **instant**: một điểm tuyệt đối trên timeline, thường dùng UTC/`DateTimeOffset`;
* **local calendar time**: khái niệm như 09:00 giờ Việt Nam, cần timezone rule để convert.

Không nên lưu “local time nhưng không timezone” rồi mong hệ thống tự hiểu.

## 4. Practical implementation

Đăng ký:

```csharp
builder.Services.AddSingleton(TimeProvider.System);
```

Service:

```csharp
public sealed class PasswordResetPolicy
{
    private readonly TimeProvider _clock;

    public PasswordResetPolicy(TimeProvider clock) => _clock = clock;

    public bool IsExpired(DateTimeOffset issuedAt, TimeSpan lifetime)
        => _clock.GetUtcNow() >= issuedAt + lifetime;
}
```

Test có fake clock:

```csharp
var fake = new FakeTimeProvider(
    new DateTimeOffset(2026, 9, 14, 8, 0, 0, TimeSpan.Zero));

var policy = new PasswordResetPolicy(fake);
var issuedAt = fake.GetUtcNow();

fake.Advance(TimeSpan.FromMinutes(31));

Assert.True(policy.IsExpired(issuedAt, TimeSpan.FromMinutes(30)));
```

## 5. Real production scenario

Một approval workflow cho phép manager approve trong vòng 48 giờ. Code cũ dùng `DateTime.Now`; server ở UTC nhưng QA chạy laptop ở UTC+7. Một số test pass local nhưng fail CI.

Sau khi chuyển storage sang UTC `DateTimeOffset` và inject `TimeProvider`, logic expiration trở nên deterministic. Conversion sang timezone chỉ xảy ra ở UI/report boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → record “hết hạn sớm 7 giờ” chỉ ở production.

**Evidence** → database chứa local time nhưng server deserialize như UTC.

**Hypothesis** → semantic của timestamp không nhất quán.

**Diagnosis** → trace input, storage type, timezone conversion và `Kind`/offset ở từng boundary.

**Fix** → dùng UTC instant cho persistence/integration, convert sang timezone khi hiển thị hoặc business rule thật sự phụ thuộc local calendar.

**Verification** → test quanh midnight, DST của timezone có DST và cross-region serialization.

## 7. Common mistakes

* Trộn `DateTime.Now` và `DateTime.UtcNow` trong cùng workflow.
* Dùng `DateTime` không rõ `Kind` làm API contract.
* Test time-based logic bằng `Thread.Sleep` hoặc `Task.Delay`.
* Convert timezone ở nhiều tầng khác nhau.
* Cho rằng offset `+07:00` là timezone rule hoàn chỉnh trong mọi quốc gia.

## 8. Alternatives

* Custom `IClock`: đơn giản và vẫn hợp lệ nếu codebase nhỏ.
* Noda Time: mạnh khi domain có nhiều calendar/timezone semantics phức tạp.
* Direct system clock: đủ nếu timestamp chỉ dùng telemetry và không cần deterministic test.

## 9. Trade-offs

### Advantages

* Test deterministic và nhanh.
* Time dependency trở nên explicit.
* Giảm timezone bug ở API/database boundary.

### Costs / Risks

* Thêm abstraction vào code.
* Team phải thống nhất semantic của timestamp.
* Domain calendar phức tạp vẫn cần timezone library/rule rõ ràng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu UTC instant khác local display time và biết `DateTimeOffset` giữ offset.

### Middle

Inject clock, viết test time-based không dùng delay, giữ conversion ở boundary rõ ràng.

### Senior

Thiết kế timestamp contract giữa API, database, queue và frontend; nhận diện DST, clock skew và expiration race.

### Technical Lead / Architect

Đặt policy chung cho toàn hệ thống: storage timezone, API serialization, business calendar ownership và test clock abstraction.

## 11. Key takeaway

* Thời gian là dependency, không chỉ là giá trị global.
* Lưu instant bằng UTC/`DateTimeOffset`, convert local tại boundary phù hợp.
* `TimeProvider` giúp test business-time logic mà không chờ thời gian thật.

# 2. ASP.NET Core Forwarded Headers và proxy trust: hiểu request gốc khi application chạy sau reverse proxy mà không mở spoofing boundary

## 1. What is it?

Khi ASP.NET Core chạy sau reverse proxy, application thường không trực tiếp thấy client IP, scheme hoặc host ban đầu. Proxy gửi thông tin này qua các header như `X-Forwarded-For` và `X-Forwarded-Proto`.

Forwarded Headers Middleware đọc các header đó và cập nhật `HttpContext`.

Mental model:

```text
Client HTTPS
   ↓
Reverse proxy / ingress
   ↓ HTTP nội bộ
ASP.NET Core
```

Nếu không xử lý forwarded headers, app có thể tưởng request là HTTP từ IP của proxy.

## 2. Why does it exist?

Các feature phụ thuộc request origin gồm:

* generate redirect HTTPS,
* absolute callback URL,
* OAuth/OpenID Connect redirect URI,
* rate limiting theo client IP,
* security audit,
* geo/risk checks.

Không hiểu proxy boundary có thể tạo redirect loop, callback sai scheme hoặc log sai IP.

## 3. How does it work?

Proxy thêm hoặc nối forwarded header. ASP.NET Core chỉ nên tin header từ proxy/network đã biết.

```csharp
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders =
        ForwardedHeaders.XForwardedFor |
        ForwardedHeaders.XForwardedProto;

    options.KnownProxies.Add(IPAddress.Parse("10.0.0.10"));
});
```

Sau đó middleware phải nằm đủ sớm:

```csharp
app.UseForwardedHeaders();
app.UseHttpsRedirection();
```

## 4. Practical implementation

Một diagnostic endpoint nội bộ có thể log:

```csharp
app.MapGet("/_diag/request", (HttpContext ctx) => new
{
    Scheme = ctx.Request.Scheme,
    Host = ctx.Request.Host.Value,
    RemoteIp = ctx.Connection.RemoteIpAddress?.ToString()
});
```

Trong production không nên public endpoint này nếu chứa thông tin nhạy cảm.

Khi dùng Azure Front Door, Application Gateway, nginx hay ingress controller, cần biết topology và chain proxy thực tế để cấu hình `ForwardLimit`, `KnownNetworks`, `KnownProxies` phù hợp.

## 5. Real production scenario

Một app dùng OpenID Connect chạy sau ingress. Client truy cập HTTPS nhưng backend nhận HTTP. Middleware tạo callback `http://.../signin-oidc`, identity provider từ chối do redirect URI mismatch.

Root cause không nằm ở identity provider mà ở việc application không reconstruct scheme gốc.

## 6. Failure scenario & troubleshooting

**Symptom** → redirect loop giữa HTTP và HTTPS.

**Evidence** → proxy terminate TLS nhưng `Request.Scheme` vẫn là `http`.

**Hypothesis** → forwarded headers chưa được apply trước HTTPS redirection.

**Diagnosis** → kiểm tra raw proxy headers, middleware order, proxy trust config.

**Fix** → đặt `UseForwardedHeaders` trước các middleware phụ thuộc scheme/host và giới hạn proxy được trust.

**Verification** → test qua đường đi thật từ edge tới application, không chỉ localhost.

## 7. Common mistakes

* Tin mọi `X-Forwarded-*` từ Internet.
* Đặt middleware sau authentication/redirect logic.
* Dùng `RemoteIpAddress` cho rate limiting mà không hiểu proxy chain.
* Hard-code HTTPS URL để che lỗi topology.
* Không kiểm tra multi-proxy chain.

## 8. Alternatives

* Platform integration tự chuẩn hóa headers: giảm config application nhưng vẫn phải hiểu trust model.
* PROXY protocol ở Layer 4: phù hợp một số load balancer/network stack.
* Không dùng forwarded headers nếu app trực tiếp terminate connection từ client.

## 9. Trade-offs

### Advantages

* Application thấy request metadata gần với client-facing request.
* Redirect, auth callback và audit chính xác hơn.

### Costs / Risks

* Trust sai proxy có thể cho attacker spoof client IP/scheme.
* Multi-hop proxy làm configuration phức tạp.
* Behavior khác nhau giữa local và production nếu không integration test.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu reverse proxy có thể thay đổi connection mà backend trực tiếp nhìn thấy.

### Middle

Cấu hình middleware order và kiểm tra `Request.Scheme`/remote IP.

### Senior

Thiết kế trust boundary, multi-proxy chain và security impact của spoofed headers.

### Technical Lead / Architect

Chuẩn hóa ingress topology, ownership của TLS, trusted proxy ranges và observability xuyên edge-to-app.

## 11. Key takeaway

* Forwarded header là trust boundary, không chỉ là plumbing.
* Middleware order quyết định scheme/IP application nhìn thấy.
* Chỉ tin forwarded metadata từ proxy/network đã được xác định.

# 3. EF Core compiled queries và query shape: tối ưu hot path khi query compilation thực sự đáng kể mà không che mất bottleneck database

## 1. What is it?

EF Core phải phân tích LINQ expression tree, translate sang SQL và cache query plan phía client theo query shape. Compiled query cho phép application compile explicit một query delegate để giảm overhead ở các hot paths có cùng shape được gọi rất nhiều lần.

Ví dụ:

```csharp
private static readonly Func<AppDbContext, int, Task<Product?>> GetProduct =
    EF.CompileAsyncQuery((AppDbContext db, int id) =>
        db.Products.AsNoTracking().FirstOrDefault(x => x.Id == id));
```

## 2. Why does it exist?

Trong đa số enterprise API, network/database latency lớn hơn query compilation overhead nhiều lần. Tuy nhiên ở query rất nhỏ, được gọi với tần suất cực cao, client-side overhead có thể đáng kể.

Compiled query tồn tại cho trường hợp tối ưu có evidence, không phải default pattern cho mọi repository method.

## 3. How does it work?

EF cache query dựa trên expression shape. Hai query khác shape có thể cần translation riêng.

Bad pattern:

```csharp
if (includeInactive)
    query = query.Where(x => x.IsActive || includeInactive);
else
    query = query.Where(x => x.IsActive);
```

Dynamic composition tạo nhiều shape hơn. Compiled query cố định expression và truyền parameter vào delegate.

Database vẫn phải parse/optimize/execute SQL theo cơ chế của DB engine; compiled EF query không “compile database query forever”.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, string, int, IAsyncEnumerable<Order>>
    OrdersByCustomer = EF.CompileAsyncQuery(
        (AppDbContext db, string customerId, int take) =>
            db.Orders
              .AsNoTracking()
              .Where(x => x.CustomerId == customerId)
              .OrderByDescending(x => x.CreatedAt)
              .Take(take));
```

Call:

```csharp
await foreach (var order in OrdersByCustomer(db, customerId, 20)
    .WithCancellation(ct))
{
    // map response
}
```

Trước khi dùng, benchmark cả end-to-end và isolated EF overhead.

## 5. Real production scenario

Một pricing service gọi query lookup đơn giản hàng chục nghìn lần/giây với DB nằm cùng region và index seek rất nhanh. Profiling cho thấy translation/cache lookup + allocation phía application chiếm tỷ lệ đáng kể.

Compiled query có thể giúp. Nhưng nếu SQL mất 150 ms vì scan, compiled query tiết kiệm vài micro/millisecond không giải quyết vấn đề chính.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries nhưng p95 API gần như không đổi.

**Evidence** → trace cho thấy 95% thời gian ở database I/O.

**Hypothesis** → tối ưu nhầm layer.

**Diagnosis** → tách timing: request → EF translation → network → DB execution → materialization.

**Fix** → xử lý query plan/index/access pattern trước; compiled query chỉ khi client overhead measurable.

**Verification** → benchmark sau mỗi thay đổi và so allocation/CPU/latency.

## 7. Common mistakes

* Compile mọi query vì nghĩ luôn nhanh hơn đáng kể.
* Che dynamic business filters vào một compiled query cực lớn.
* Quên `AsNoTracking` ở read-only hot path.
* Chỉ benchmark in-memory compilation mà bỏ qua end-to-end latency.
* Nhầm EF query caching với SQL Server plan cache.

## 8. Alternatives

* EF Core automatic query cache: đủ cho phần lớn workload.
* Raw SQL/Dapper: hữu ích khi cần control mapping/SQL rõ hơn.
* Stored procedure: phù hợp một số boundary/organization nhưng tăng coupling DB.
* Cache dữ liệu nếu access pattern thực sự cacheable.

## 9. Trade-offs

### Advantages

* Giảm một phần CPU/allocation của repeated query execution.
* Query delegate explicit và reusable cho hot path.

### Costs / Risks

* Code khó đọc hơn query LINQ bình thường.
* Ít linh hoạt với dynamic shape.
* Dễ tối ưu nhầm tầng và bỏ qua DB bottleneck.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ được translate thành SQL chứ không execute trực tiếp như in-memory collection.

### Middle

Biết xem generated SQL, tracking mode và query shape.

### Senior

Benchmark translation/materialization/database time trước khi compiled query.

### Technical Lead / Architect

Đặt performance practice dựa trên profiling; tránh biến micro-optimization thành code convention toàn hệ thống.

## 11. Key takeaway

* EF đã cache query shape; compiled query là optimization chuyên biệt.
* Đo database time và application CPU riêng biệt.
* Query plan/access pattern thường quan trọng hơn vài micro-optimization ở LINQ layer.

# 4. SQL Server sargability và composite index order: viết predicate để optimizer có thể seek thay vì scan dữ liệu không cần thiết

## 1. What is it?

Sargable predicate là điều kiện mà optimizer có thể dùng hiệu quả để tìm range trong index thay vì phải tính expression trên nhiều rows trước khi filter.

Ví dụ kém:

```sql
WHERE CAST(CreatedAt AS date) = @date
```

Thường tốt hơn:

```sql
WHERE CreatedAt >= @start
  AND CreatedAt <  @end
```

## 2. Why does it exist?

Index được sắp xếp theo key. Muốn seek, database cần predicate map được thành range trên key đó.

Nếu bọc indexed column trong function, implicit conversion hoặc expression khó suy luận, engine có thể phải scan nhiều pages hơn.

Composite index order cũng quan trọng vì index `(TenantId, CreatedAt)` có behavior khác `(CreatedAt, TenantId)`.

## 3. How does it work?

Giả sử query:

```sql
SELECT Id, Status, CreatedAt
FROM Orders
WHERE TenantId = @tenantId
  AND CreatedAt >= @from
ORDER BY CreatedAt DESC;
```

Index:

```sql
CREATE INDEX IX_Orders_Tenant_CreatedAt
ON Orders(TenantId, CreatedAt DESC)
INCLUDE(Status);
```

Equality trên leading key `TenantId` giúp engine locate tenant range, sau đó range/order theo `CreatedAt`.

Flow reasoning:

```text
query
→ predicate shape
→ execution plan
→ seek/scan
→ logical reads
→ locks/latches
→ latency
```

## 4. Practical implementation

Tránh implicit conversion:

```sql
-- Column là nvarchar nhưng parameter truyền varchar có thể tạo conversion issue tùy case.
WHERE Email = @email;
```

Đảm bảo parameter type khớp schema.

Đo bằng execution plan và `SET STATISTICS IO, TIME ON` trong môi trường phù hợp:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

Không chỉ nhìn estimated cost percentage.

## 5. Real production scenario

Search endpoint filter order theo ngày dùng:

```sql
WHERE CONVERT(date, CreatedAt) = @selectedDate
```

Bảng vài chục triệu rows. Query scan nhiều pages, CPU và I/O tăng. Rewrite thành half-open range `[start, nextDay)` cho phép index seek và giảm logical reads rất lớn.

## 6. Failure scenario & troubleshooting

**Symptom** → query chậm dần khi bảng lớn dù “đã có index CreatedAt”.

**Evidence** → actual execution plan cho thấy Index Scan với residual predicate; logical reads cao.

**Hypothesis** → predicate không sargable hoặc leading index key không phù hợp.

**Diagnosis** → xem seek predicates, residual predicates, implicit conversions, cardinality estimate.

**Fix** → rewrite predicate hoặc thiết kế composite index theo access pattern.

**Verification** → so actual plan, reads, CPU, duration trên representative data.

## 7. Common mistakes

* Bọc indexed column bằng `LOWER`, `CAST`, `DATEDIFF` rồi mong seek như cũ.
* Tạo index theo thứ tự column trong `WHERE` thay vì selectivity/access pattern/order needs.
* Thêm nhiều indexes mà không tính write cost.
* Chỉ xem duration một lần, không xem logical reads.
* Dùng function-based workaround mà không hiểu persisted computed column/index alternative.

## 8. Alternatives

* Persisted computed column + index khi expression là requirement thật.
* Full-text search cho text search phức tạp.
* Filtered index cho subset ổn định.
* Columnstore cho analytical scans, không thay thế OLTP seek pattern.

## 9. Trade-offs

### Advantages

* Sargable queries tận dụng index tốt hơn.
* Composite index đúng có thể giảm I/O và sort.

### Costs / Risks

* Index thêm làm write/update tốn hơn.
* Index order tối ưu query này có thể không tối ưu query khác.
* Over-indexing tăng storage và maintenance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không đảm bảo query sẽ tự động seek.

### Middle

Đọc basic execution plan và nhận diện scan/seek, implicit conversion.

### Senior

Thiết kế predicate/index từ access pattern và đo I/O/locks/latency.

### Technical Lead / Architect

Quản lý indexing strategy theo workload tổng thể, cân bằng read performance với write/storage/operational cost.

## 11. Key takeaway

* Predicate shape quyết định optimizer có thể dùng index hiệu quả tới đâu.
* Composite index order phải phản ánh access pattern, không phải thứ tự ngẫu nhiên.
* Đo actual plan và logical reads trước khi kết luận “thiếu index”.

# 5. Azure Cosmos DB RU throttling và hot partition: scale throughput không chỉ bằng tăng RU/s mà phải sửa access pattern và partition key

## 1. What is it?

Azure Cosmos DB tính chi phí operation bằng Request Units (RU). Khi workload vượt throughput khả dụng tại partition, request có thể nhận HTTP `429 Too Many Requests` cùng retry-after.

Hot partition xảy ra khi traffic/data distribution tập trung vào một logical/physical partition dù tổng RU toàn container nhìn có vẻ còn khả năng.

## 2. Why does it exist?

Cosmos DB phân phối data và throughput theo partition. Partition key quyết định data locality và khả năng scale.

Nếu mọi request dùng cùng key như `TenantId = "global"`, hệ thống không thể phân tán load tốt chỉ bằng việc có nhiều partitions.

## 3. How does it work?

Request cost phụ thuộc:

* point read hay query,
* document size,
* index work,
* cross-partition fan-out,
* consistency level.

SDK thường tự retry 429 trong một giới hạn. Nhưng retry che symptoms chứ không sửa hot key.

```text
Client
  ↓
Partition routing
  ├─ P1: 90% load  ← hot
  ├─ P2: 5%
  └─ P3: 5%
```

## 4. Practical implementation

Point read hiệu quả khi biết `id` + partition key:

```csharp
var response = await container.ReadItemAsync<Order>(
    id,
    new PartitionKey(tenantId),
    cancellationToken: ct);
```

Query cross-partition:

```csharp
var query = new QueryDefinition(
    "SELECT * FROM c WHERE c.status = @status")
    .WithParameter("@status", "Pending");
```

có thể fan-out nếu `status` không định vị partition.

Monitor `RequestCharge`, 429 rate và normalized RU consumption theo partition key range.

## 5. Real production scenario

Multi-tenant SaaS chọn `TenantId` làm partition key. Phần lớn tenant nhỏ, nhưng một enterprise tenant tạo 60% traffic. Container liên tục 429 dù tổng throughput đã tăng nhiều lần.

Cần đánh giá hierarchical partition key hoặc composite distribution strategy phù hợp workload, không chỉ nâng RU/s.

## 6. Failure scenario & troubleshooting

**Symptom** → latency p99 tăng và SDK retry nhiều nhưng average throughput chưa chạm limit rõ ràng.

**Evidence** → một partition key range có normalized RU gần 100%, các range khác thấp.

**Hypothesis** → hot partition.

**Diagnosis** → phân tích request charge theo operation + key distribution + query fan-out.

**Fix** → sửa partition strategy, giảm query cost, cache/read model phù hợp hoặc tách workload.

**Verification** → kiểm tra 429 rate, RU/key distribution và latency sau migration.

## 7. Common mistakes

* Chọn partition key chỉ vì field “luôn có”.
* Dùng low-cardinality key như `Country`, `Status` cho workload lớn.
* Cho SDK retry 429 vô hạn mà không alert.
* Dùng query khi point read đủ.
* Đánh giá RU trung bình mà bỏ qua partition-level saturation.

## 8. Alternatives

* Azure SQL/PostgreSQL khi relational consistency/querying quan trọng hơn global distribution.
* MongoDB với sharding model riêng.
* Separate containers cho workload có access pattern khác nhau.
* Cache layer nếu read workload lặp lại và consistency cho phép.

## 9. Trade-offs

### Advantages

* Cosmos DB scale horizontal và có managed global distribution.
* RU model giúp định lượng phần nào resource consumption.

### Costs / Risks

* Partition key khó thay đổi về sau.
* Hot partition phá giả định “scale tự động”.
* Cross-partition query có thể tốn RU cao.
* Provisioned throughput tăng trực tiếp cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu partition key quyết định nơi data được phân phối.

### Middle

Biết point read, RequestCharge, 429 và retry-after.

### Senior

Phân tích hot partition, RU distribution và access pattern thực tế.

### Technical Lead / Architect

Chọn data model/partition strategy theo growth và tenant skew, đồng thời lập migration plan vì partition key là quyết định dài hạn.

## 11. Key takeaway

* 429 trong Cosmos DB thường là capacity/distribution signal, không chỉ là transient error.
* Partition key là architecture decision quan trọng hơn tăng RU đơn thuần.
* Theo dõi partition-level saturation và request charge, không chỉ average throughput.

# 6. Modular Monolith boundaries: giữ deployment đơn giản nhưng enforce ownership, dependency direction và transaction boundary như nhiều module độc lập

## 1. What is it?

Modular Monolith là một application được deploy như một unit nhưng chia thành các module business có boundary rõ ràng.

Ví dụ:

```text
Host
 ├─ Ordering
 ├─ Catalog
 ├─ Identity
 └─ Billing
```

Điểm cốt lõi không phải folder. Mỗi module cần ownership của model/data/API nội bộ và dependency rule rõ ràng.

## 2. Why does it exist?

Một monolith không boundary thường tiến hóa thành “big ball of mud”: bất kỳ layer nào cũng truy cập entity/table/service của phần khác.

Microservices có thể tạo isolation mạnh hơn nhưng mang thêm network, deployment, observability, consistency và operational cost.

Modular Monolith là lựa chọn khi business complexity cần boundaries nhưng scale/organization chưa cần independent deployment.

## 3. How does it work?

Một module nên expose contract qua application/API boundary, không cho module khác truy cập persistence internals trực tiếp.

```text
Ordering ──contract/event──> Catalog
   │                         │
 owns orders                 owns products
```

Data có thể cùng physical database nhưng ownership logic vẫn tách. Cross-module transaction nên được coi là design decision explicit, không phải “join table nào cũng được”.

Dependency direction cần enforce bằng project references, architecture tests hoặc internal visibility.

## 4. Practical implementation

Solution:

```text
src/
  Host/
  Modules/
    Ordering/
      Ordering.Application/
      Ordering.Domain/
      Ordering.Infrastructure/
      Ordering.Contracts/
    Catalog/
      ...
```

Ordering chỉ reference `Catalog.Contracts`, không reference `Catalog.Infrastructure`.

Một architecture test có thể kiểm tra namespace/project dependency để boundary không bị phá dần theo thời gian.

## 5. Real production scenario

E-commerce platform ban đầu có một `AppDbContext` với toàn bộ tables và service gọi chéo lẫn nhau. Mỗi thay đổi product pricing dễ phá checkout.

Team chưa có nhu cầu deploy Catalog độc lập. Tách thành module với contract + ownership rõ giảm coupling mà không phải vận hành Service Bus, service discovery, distributed tracing giữa hàng chục services.

## 6. Failure scenario & troubleshooting

**Symptom** → “modular monolith” nhưng thay đổi một module yêu cầu sửa code ở 6 module khác.

**Evidence** → module reference domain entity/repository của nhau trực tiếp.

**Hypothesis** → boundary chỉ tồn tại trong folder naming.

**Diagnosis** → build dependency graph, tìm shared model/database access.

**Fix** → tạo explicit contracts, chuyển ownership về module, dùng event/query boundary khi cần.

**Verification** → architecture tests và review dependency direction trong CI.

## 7. Common mistakes

* Một shared project chứa tất cả domain models.
* Module khác truy cập table trực tiếp vì “cùng database cho nhanh”.
* Tạo interface nhưng implementation vẫn coupling internals.
* Dùng MediatR như bằng chứng đã có module boundary.
* Tách module quá nhỏ theo technical concern thay vì business capability.

## 8. Alternatives

* Simple Layered Monolith: phù hợp domain nhỏ, team nhỏ.
* Microservices: phù hợp khi cần independent deployment/scale/ownership đủ mạnh.
* Vertical Slice Architecture: tổ chức theo feature; có thể kết hợp modular monolith.

## 9. Trade-offs

### Advantages

* Deployment đơn giản hơn microservices.
* Transaction local dễ hơn.
* Boundary tốt giúp thay đổi cô lập và mở đường tách service sau này nếu cần.

### Costs / Risks

* Boundary cần discipline/enforcement.
* Shared process vẫn có shared failure domain.
* Independent scaling/deployment hạn chế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business boundary, không chỉ thư mục.

### Middle

Không xuyên qua contract để gọi repository/entity nội bộ module khác.

### Senior

Thiết kế data ownership, cross-module communication và transaction boundary.

### Technical Lead / Architect

Quyết định khi modular monolith đủ tốt và tiêu chí nào thật sự biện minh cho việc tách microservice.

## 11. Key takeaway

* Modular Monolith tối ưu boundary trước khi tối ưu independent deployment.
* Data ownership và dependency direction quan trọng hơn folder structure.
* Không cần microservices để có architecture boundary tốt.

# 7. Azure Functions cold start, concurrency và scale-out: serverless scale tự động không có nghĩa mọi workload đều có latency và throughput ổn định

## 1. What is it?

Azure Functions chạy code theo trigger và có thể scale instances theo workload. Cold start là latency khi platform cần tạo/warm worker trước khi function xử lý request/event.

Concurrency là số invocations một instance xử lý đồng thời; scale-out là tăng số instances.

Ba khái niệm này tương tác trực tiếp tới latency, downstream pressure và cost.

## 2. Why does it exist?

Serverless giảm operational burden và phù hợp bursty/event-driven workload. Nhưng tài nguyên không luôn resident như app server truyền thống.

Khi traffic đột ngột tăng:

```text
Queue grows
  ↓
Functions scale out
  ↓
More consumers
  ↓
Database/API load also grows
```

Scale nhanh ở compute layer có thể làm dependency phía dưới quá tải.

## 3. How does it work?

Trigger-specific scaling theo queue depth/event rate/HTTP demand. Worker host có startup, dependency injection, package load, JIT và connection initialization.

Nếu startup path nặng, cold start lâu hơn.

Concurrency cao giúp throughput per instance nhưng cũng tăng simultaneous DB connections/HTTP calls.

## 4. Practical implementation

Function nên giữ startup lightweight và reuse expensive clients:

```csharp
builder.Services.AddHttpClient<PartnerClient>();
builder.Services.AddSingleton<CosmosClient>(sp =>
    new CosmosClient(configuration["Cosmos:Connection"]));
```

Không tạo `HttpClient`/DB client mới mỗi invocation nếu SDK khuyến nghị reuse.

Đặt timeout, retry và idempotency theo trigger semantics. Với queue trigger, poison handling phải rõ.

## 5. Real production scenario

Một queue worker xử lý image metadata. Marketing import 500k records. Functions scale out nhanh, mỗi invocation gọi SQL và external image API. SQL connection pool và third-party quota bị saturation.

Giải pháp không chỉ “thêm RU/DB size”; cần giới hạn concurrency, batch hợp lý, backpressure và rate-limit awareness.

## 6. Failure scenario & troubleshooting

**Symptom** → queue backlog giảm chậm dù instance count tăng; dependency timeout/429 tăng.

**Evidence** → Functions concurrency tăng cùng SQL connection failures và partner rate-limit responses.

**Hypothesis** → compute scale-out đang vượt downstream capacity.

**Diagnosis** → correlate instance count, trigger concurrency, queue age, dependency latency/error.

**Fix** → tune concurrency/batch, thêm backoff, partition workload hoặc tăng downstream capacity có chủ đích.

**Verification** → replay production-like burst và theo dõi backlog drain rate + dependency saturation.

## 7. Common mistakes

* Cho rằng autoscale giải quyết mọi bottleneck.
* Startup load nhiều configuration/network calls.
* Tạo client/socket mỗi invocation.
* Retry 429 ngay lập tức làm rate-limit nặng hơn.
* Không monitor queue age, chỉ monitor queue length.

## 8. Alternatives

* Worker Service/App Service: phù hợp long-running steady workload và cần control process lifecycle.
* Azure Container Apps jobs: hữu ích containerized event/batch scenarios.
* Kubernetes worker: nhiều control hơn nhưng operational burden cao hơn.
* Logic Apps: phù hợp orchestration integration low-code hơn custom compute.

## 9. Trade-offs

### Advantages

* Elastic scaling và event-driven programming model.
* Ít infrastructure management.
* Cost tốt cho bursty/low-duty workload trong nhiều trường hợp.

### Costs / Risks

* Cold start có thể ảnh hưởng latency.
* Scale-out làm downstream pressure tăng nhanh.
* Trigger semantics/concurrency tuning cần hiểu rõ.
* Observability phân tán qua nhiều ephemeral instances.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu function invocation có thể chạy trên nhiều instances khác nhau.

### Middle

Biết reuse clients, cancellation, retry và poison message handling.

### Senior

Tune concurrency/scale theo downstream capacity và observability evidence.

### Technical Lead / Architect

Chọn Functions chỉ khi execution model phù hợp; đánh giá cold-start SLO, dependency limits, cost và migration alternative.

## 11. Key takeaway

* Serverless autoscale chỉ scale compute layer, không scale dependency thay bạn.
* Cold start và concurrency là production design concern.
* Queue age + dependency saturation thường quan trọng hơn instance count đơn lẻ.

# 8. `dotnet-counters` và EventCounters: chẩn đoán CPU, GC, ThreadPool và connection pressure trước khi tối ưu theo cảm tính

## 1. What is it?

`dotnet-counters` là diagnostic tool của .NET để quan sát runtime/application counters theo thời gian thực mà không cần full profiler ngay lập tức.

Các signal thường hữu ích:

* CPU usage,
* GC heap size,
* allocation rate,
* Gen 0/1/2 GC,
* ThreadPool queue length,
* exception rate,
* ASP.NET Core request metrics,
* networking/runtime counters tùy provider.

## 2. Why does it exist?

Production incident thường bắt đầu bằng symptom mơ hồ: “API chậm”, “CPU cao”, “memory tăng”. Nếu đoán nguyên nhân từ code review, team dễ sửa sai layer.

Counters cung cấp first-pass evidence với overhead thấp hơn full trace/profiler.

## 3. How does it work?

Runtime và libraries publish counters/events. Tool subscribe vào process diagnostic channel.

Ví dụ:

```bash
dotnet-counters monitor --process-id 1234 System.Runtime Microsoft.AspNetCore.Hosting
```

Mental model:

```text
Symptom
  ↓
Counters
  ↓
Narrow hypothesis
  ↓
Trace / dump / profiler / DB evidence
```

Counter thường giúp localize, không phải luôn đủ để xác định root cause cuối cùng.

## 4. Practical implementation

Một flow điều tra:

```bash
dotnet-counters ps

dotnet-counters monitor \
  --process-id 1234 \
  System.Runtime
```

Nếu thấy ThreadPool queue tăng, CPU không max và request latency tăng, có thể nghi sync-over-async/blocking.

Nếu allocation rate tăng mạnh và Gen 2 GC dày, tiếp theo dùng `dotnet-trace`, profiler hoặc dump để tìm allocation source.

## 5. Real production scenario

Sau deploy, p99 API tăng từ 300 ms lên 2 s. CPU chỉ 45%. `dotnet-counters` cho thấy ThreadPool queue length tăng liên tục và thread count tăng dần.

Code diff cho thấy mới thêm `.Result` trên HTTP async call. Fix async path làm queue giảm và latency trở lại bình thường.

## 6. Failure scenario & troubleshooting

**Symptom** → memory process tăng nhưng GC heap không tăng tương ứng.

**Evidence** → managed heap counters ổn định.

**Hypothesis** → native memory, socket buffer, mapped file hoặc external library allocation.

**Diagnosis** → counters loại trừ managed heap rồi chuyển sang process/native tooling.

**Fix** → phụ thuộc root cause, không ép `GC.Collect()`.

**Verification** → repeat workload và so working set + managed/native evidence.

## 7. Common mistakes

* Nhìn một counter đơn lẻ rồi kết luận.
* Dùng average CPU mà bỏ qua saturation dependency.
* Thấy memory cao rồi gọi `GC.Collect()`.
* Không lấy baseline lúc hệ thống khỏe.
* Không correlate counters với logs/traces/deploy timeline.

## 8. Alternatives

* `dotnet-trace`: event trace sâu hơn.
* `dotnet-dump`: memory/crash investigation.
* PerfView/Visual Studio Profiler: analysis chi tiết.
* Application Insights/OpenTelemetry metrics: historical distributed observability.

## 9. Trade-offs

### Advantages

* Nhanh, lightweight, tốt cho triage.
* Runtime signals trực tiếp giúp loại bỏ nhiều giả thuyết.

### Costs / Risks

* Không luôn cho call stack/root cause.
* Short sample dễ gây kết luận sai.
* Container/production access có thể bị hạn chế.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết đọc CPU, GC heap, allocation và ThreadPool ở mức cơ bản.

### Middle

Dùng counters để tạo evidence trước khi đổi code.

### Senior

Correlate counters với traces, dumps, DB/network telemetry và deploy change.

### Technical Lead / Architect

Xây incident workflow có baseline, telemetry ownership và escalation path từ metric → trace → profiler/dump.

## 11. Key takeaway

* Đo runtime signal trước khi tối ưu.
* Counter giúp thu hẹp hypothesis, không thay thế root-cause analysis.
* Baseline lúc hệ thống khỏe làm incident evidence có ý nghĩa hơn.

# 9. Testcontainers cho integration testing: dùng infrastructure thật có lifecycle cô lập thay vì mock mất hành vi quan trọng

## 1. What is it?

Testcontainers khởi động dependency thật như PostgreSQL, SQL Server, Redis hoặc message broker trong container cho test lifecycle.

Mental model:

```text
Test process
  ├─ start ephemeral DB/container
  ├─ apply schema
  ├─ run real integration
  └─ destroy container
```

Mục tiêu là test behavior mà mock không mô phỏng chính xác: SQL translation, transaction, constraint, serialization, network protocol.

## 2. Why does it exist?

Mock repository dễ tạo false confidence. Một LINQ expression pass với mocked `IQueryable` có thể fail khi EF translate sang SQL. Transaction/unique constraint/index/DB collation cũng không được mock đúng.

Shared integration DB lại gây flaky tests do state leakage và parallel execution.

## 3. How does it work?

Test suite tạo container từ image version cố định, đợi readiness, lấy connection string động rồi cấu hình application-under-test.

Ví dụ C#:

```csharp
private readonly PostgreSqlContainer _postgres =
    new PostgreSqlBuilder()
        .WithImage("postgres:16")
        .Build();

public async Task InitializeAsync()
{
    await _postgres.StartAsync();
}
```

Sau đó override DbContext connection cho `WebApplicationFactory`.

## 4. Practical implementation

Integration test có thể:

1. start DB,
2. apply EF migrations,
3. seed minimal data,
4. gọi real HTTP endpoint,
5. assert DB side effect.

```csharp
var response = await client.PostAsJsonAsync("/orders", request);
response.EnsureSuccessStatusCode();

await using var db = CreateDbContext();
Assert.Single(await db.Orders.ToListAsync());
```

Nên cố định image version thay vì `latest` để CI reproducible.

## 5. Real production scenario

Một query dùng PostgreSQL-specific `ILIKE`. Unit test mock repository pass. Production query lại fail do extension/type mismatch ở migration.

Testcontainers chạy PostgreSQL thật phát hiện lỗi trước deploy mà không cần shared QA database.

## 6. Failure scenario & troubleshooting

**Symptom** → integration test flaky chỉ trên CI.

**Evidence** → test bắt đầu trước khi database thật sự ready hoặc port/resource contention.

**Hypothesis** → lifecycle/readiness không deterministic.

**Diagnosis** → xem container logs, wait strategy và parallelism.

**Fix** → readiness check đúng protocol, isolation schema/container hợp lý, giới hạn parallelism nếu resource nhỏ.

**Verification** → chạy test suite lặp nhiều lần trên CI worker tương tự production pipeline.

## 7. Common mistakes

* Dùng image `latest`.
* Seed khối dữ liệu lớn cho mọi test.
* Chạy mỗi test một heavy container dù fixture reuse đủ an toàn.
* Gọi test là integration nhưng vẫn mock database.
* Không cleanup external side effect.

## 8. Alternatives

* SQLite in-memory: nhanh nhưng behavior khác SQL Server/PostgreSQL ở nhiều chi tiết.
* Shared test DB: dễ setup nhưng state leakage và coordination cao.
* Pure unit test: tốt cho domain logic không cần infrastructure.
* Docker Compose test environment: phù hợp multi-service suite nhưng lifecycle coarse-grained hơn.

## 9. Trade-offs

### Advantages

* Fidelity cao với real infrastructure behavior.
* Test isolation tốt hơn shared environment.
* CI reproducible nếu version/lifecycle rõ ràng.

### Costs / Risks

* Test chậm hơn unit test.
* CI cần Docker/container runtime và đủ resource.
* Không nên dùng cho mọi logic nhỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu unit test và integration test bảo vệ loại risk khác nhau.

### Middle

Tạo container fixture, migration và deterministic test data.

### Senior

Thiết kế test boundary theo risk, tối ưu reuse/isolation và xử lý flaky infrastructure test.

### Technical Lead / Architect

Định nghĩa test portfolio: logic nào unit, boundary nào integration, flow nào E2E; không chase coverage percentage máy móc.

## 11. Key takeaway

* Mock không thể đại diện đầy đủ behavior của database/broker thật.
* Testcontainers tăng fidelity nhưng nên dùng đúng boundary có rủi ro infrastructure.
* Reproducibility phụ thuộc version pinning, readiness và data isolation.

# 10. CORS trong browser security: cấu hình cross-origin đúng boundary thay vì coi `AllowAnyOrigin` là cách “fix frontend”

## 1. What is it?

CORS là browser-enforced policy cho phép server khai báo origin nào được browser frontend đọc response cross-origin.

Ví dụ frontend:

```text
https://app.example.com
```

gọi API:

```text
https://api.example.com
```

là cross-origin vì host khác.

CORS không phải authentication và không ngăn server-to-server/client non-browser gửi request.

## 2. Why does it exist?

Browser áp dụng Same-Origin Policy để hạn chế trang độc hại đọc dữ liệu từ origin khác bằng credentials của user.

Một số legitimate architecture cần frontend và API ở origin khác nhau, nên CORS cung cấp controlled relaxation.

## 3. How does it work?

Với request “non-simple”, browser gửi preflight `OPTIONS`:

```text
Browser
  ├─ OPTIONS + Origin + requested method/headers
  ↓
API
  ├─ Access-Control-Allow-Origin
  ├─ Access-Control-Allow-Methods
  └─ Access-Control-Allow-Headers
  ↓
Browser decides whether JS may continue/read response
```

Server vẫn phải authentication/authorization bình thường.

## 4. Practical implementation

ASP.NET Core:

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("Frontend", policy =>
    {
        policy.WithOrigins("https://app.example.com")
              .WithMethods("GET", "POST", "PUT", "DELETE")
              .WithHeaders("Content-Type", "Authorization");
    });
});
```

Middleware:

```csharp
app.UseCors("Frontend");
```

Nếu dùng cookies/credentials, origin phải explicit; không kết hợp wildcard origin với credentials.

## 5. Real production scenario

Frontend deploy sang domain mới. API chưa thêm origin, browser báo CORS error. Team tạm đổi sang `AllowAnyOrigin`, rồi để nguyên production.

Cách đúng là xác định allowed origins theo environment/config, không hạ toàn bộ boundary chỉ để unblock deploy.

## 6. Failure scenario & troubleshooting

**Symptom** → Postman gọi API thành công nhưng browser fail.

**Evidence** → DevTools cho thấy preflight `OPTIONS` bị 401/404 hoặc thiếu `Access-Control-Allow-Origin`.

**Hypothesis** → CORS/preflight pipeline sai, không phải API business logic.

**Diagnosis** → inspect Network tab: origin, method, custom headers, preflight response, middleware order.

**Fix** → policy explicit và đảm bảo OPTIONS đi qua đúng CORS handling.

**Verification** → test từ browser origin thật, cả request có credentials và custom headers.

## 7. Common mistakes

* Nghĩ CORS bảo vệ API khỏi curl/Postman.
* Dùng `AllowAnyOrigin` cho API có sensitive browser data mà không cân nhắc threat model.
* Chỉ cho phép GET nhưng frontend gửi custom header làm preflight fail.
* Nhầm CORS error với authentication error.
* Dynamically reflect mọi `Origin` mà không validate allowlist.

## 8. Alternatives

* Same-origin deployment qua reverse proxy/BFF để tránh cross-origin trong browser.
* Backend-for-Frontend pattern khi cần kiểm soát browser session/API composition.
* Server-to-server integration không cần CORS vì browser không tham gia.

## 9. Trade-offs

### Advantages

* Cho phép frontend architecture đa-origin có kiểm soát.
* Browser cung cấp enforcement layer cho response visibility.

### Costs / Risks

* Policy sai dễ gây outage frontend hoặc mở origin quá rộng.
* Preflight thêm request/latency cho một số calls.
* Không thay thế CSRF/authentication/authorization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CORS là browser policy và Same-Origin Policy là nguyên nhân nền.

### Middle

Cấu hình allowed origins/methods/headers và debug preflight trong DevTools.

### Senior

Phân biệt CORS, CSRF, cookies, bearer token và security boundary thực tế.

### Technical Lead / Architect

Chọn topology same-origin/BFF/cross-origin theo auth model, environment governance và operational simplicity.

## 11. Key takeaway
