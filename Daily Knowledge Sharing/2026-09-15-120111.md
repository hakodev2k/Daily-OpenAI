# 1. .NET `TimeProvider`: biến thời gian từ hidden global dependency thành dependency có thể test và kiểm soát

## 1. What is it?

`TimeProvider` là abstraction của .NET cho việc đọc thời gian và tạo timer. Mental model: thay vì business logic gọi trực tiếp `DateTime.UtcNow`, code nhận một nguồn thời gian qua dependency.

```text
Business logic → TimeProvider → system clock/test clock
```

## 2. Why does it exist?

Thời gian là external state. Code gọi clock trực tiếp rất khó test deterministic: test expiry, timeout, grace period hoặc scheduled behavior phải chờ thời gian thật hoặc dùng workaround dễ flaky.

## 3. How does it work?

Production dùng `TimeProvider.System`. Test có thể cung cấp fake provider và chủ động advance clock. Business logic không cần biết nguồn thời gian là thật hay giả.

## 4. Practical implementation

```csharp
public sealed class TokenPolicy(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt) =>
        timeProvider.GetUtcNow() >= expiresAt;
}

builder.Services.AddSingleton(TimeProvider.System);
```

Test inject fake clock rồi advance thay vì `Task.Delay`.

## 5. Real production scenario

Một approval link hết hạn sau 24 giờ. Test cũ dùng `DateTime.UtcNow` ở nhiều lớp và đôi lúc fail tại boundary. Đưa clock thành dependency giúp toàn flow dùng cùng một notion of time.

## 6. Failure scenario & troubleshooting

**Symptom** → expiry tests flaky quanh second/minute boundary. **Evidence** → nhiều lần đọc system clock trong cùng operation. **Diagnosis** → hidden temporal dependency. **Fix** → inject `TimeProvider`, capture `now` một lần khi consistency trong operation quan trọng. **Verification** → advance fake time chính xác qua boundary.

## 7. Common mistakes

* Wrap `DateTime.UtcNow` bằng interface riêng dù framework đã có abstraction phù hợp.
* Trộn local time và UTC trong persistence.
* Đọc clock nhiều lần trong một invariant cần cùng timestamp.

## 8. Alternatives

Interface clock tự viết vẫn hợp lý ở legacy code. `DateTimeOffset.UtcNow` đủ cho code nhỏ không cần deterministic temporal tests.

## 9. Trade-offs

### Advantages

Deterministic tests, explicit dependency, hỗ trợ timer abstraction.

### Costs / Risks

Thêm dependency vào code; abstraction không tự giải quyết timezone/domain calendar rules.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu clock là external dependency.

### Middle

Inject `TimeProvider` và test expiry không dùng sleep.

### Senior

Phân biệt instant, timezone, business calendar và monotonic duration.

### Technical Lead / Architect

Chuẩn hóa temporal semantics toàn hệ thống, đặc biệt persistence và distributed workflows.

## 11. Key takeaway

* Thời gian nên explicit khi ảnh hưởng correctness.
* Test thời gian bằng controllable clock, không bằng chờ thật.
* UTC instant và business timezone là hai khái niệm khác nhau.

# 2. ASP.NET Core Endpoint Filters: cross-cutting behavior sát endpoint mà không biến middleware pipeline thành nơi chứa mọi policy

## 1. What is it?

Endpoint Filter bao quanh Minimal API handler và có thể chạy logic trước/sau endpoint. Nó phù hợp behavior gắn với nhóm endpoint hơn là toàn request pipeline.

## 2. Why does it exist?

Middleware rất mạnh nhưng quá rộng cho validation hoặc policy chỉ áp dụng một endpoint family. Nhét mọi concern vào middleware làm pipeline khó reasoning và phụ thuộc routing metadata phức tạp.

## 3. How does it work?

Filter nhận `EndpointFilterInvocationContext`, có thể inspect arguments, short-circuit hoặc gọi `next(context)`.

```text
Middleware → Endpoint filter A → Filter B → Handler
```

## 4. Practical implementation

```csharp
public sealed class ValidateIdFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var id = context.GetArgument<Guid>(0);
        if (id == Guid.Empty)
            return Results.BadRequest(new { error = "Invalid id" });

        return await next(context);
    }
}

app.MapGet("/orders/{id:guid}", GetOrder)
   .AddEndpointFilter<ValidateIdFilter>();
```

## 5. Real production scenario

Một API group cần tenant validation trước mọi handler. Filter áp dụng ở route group giữ policy gần endpoints mà không ảnh hưởng health checks hoặc public endpoints.

## 6. Failure scenario & troubleshooting

**Symptom** → endpoint trả 400 trước authorization hoặc telemetry mong đợi. **Evidence** → filter order và middleware order không đúng mental model. **Fix** → xác định concern thuộc middleware, authorization hay filter; test pipeline order. **Verification** → integration tests cho authenticated/invalid cases.

## 7. Common mistakes

* Dùng filter thay authorization policy.
* Nhét business logic vào filter.
* Tạo filter chain dài khó quan sát.

## 8. Alternatives

Middleware cho global HTTP concerns; authorization handlers cho access control; application pipeline behaviors cho use-case concerns.

## 9. Trade-offs

### Advantages

Scope hẹp, composable, gần endpoint metadata.

### Costs / Risks

Thêm execution layer; dễ duplicate logic nếu route groups không được quản lý rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu filter bao quanh handler.

### Middle

Biết short-circuit và đăng ký theo endpoint/group.

### Senior

Chọn đúng boundary giữa middleware/filter/application behavior.

### Technical Lead / Architect

Giữ cross-cutting architecture nhất quán thay vì nhiều mechanism chồng chéo.

## 11. Key takeaway

* Endpoint Filter phù hợp concern có endpoint scope.
* Security/business invariants vẫn cần đúng abstraction riêng.
* Ít layers rõ ràng tốt hơn nhiều layers “reusable”.

# 3. EF Core Interceptors: quan sát và can thiệp database operations đúng boundary thay vì rải logging/retry thủ công

## 1. What is it?

EF Core Interceptor là hook vào lifecycle như command execution, connection, transaction hoặc `SaveChanges`. Nó cho phép cross-cutting behavior tại persistence boundary.

## 2. Why does it exist?

Một số concern cần áp dụng nhất quán cho mọi database operation: diagnostics, auditing metadata hoặc command inspection. Copy logic vào repository/service dễ thiếu và khó maintain.

## 3. How does it work?

Interceptor được EF gọi trước/sau operation. Nó có thể observe, modify hoặc trong một số hook suppress operation. Vì nằm sâu trong persistence path, code phải rất nhẹ và predictable.

## 4. Practical implementation

```csharp
public sealed class SlowCommandInterceptor(ILogger<SlowCommandInterceptor> logger)
    : DbCommandInterceptor
{
    public override async ValueTask<DbDataReader> ReaderExecutedAsync(
        DbCommand command,
        CommandExecutedEventData eventData,
        DbDataReader result,
        CancellationToken cancellationToken = default)
    {
        if (eventData.Duration > TimeSpan.FromMilliseconds(500))
            logger.LogWarning("Slow SQL {Duration} {Command}",
                eventData.Duration, command.CommandText);

        return await base.ReaderExecutedAsync(
            command, eventData, result, cancellationToken);
    }
}
```

## 5. Real production scenario

Team cần phát hiện query regression sau release. Command interceptor bổ sung structured telemetry thống nhất thay vì từng repository tự đo duration.

## 6. Failure scenario & troubleshooting

**Symptom** → latency tăng sau khi thêm auditing interceptor. **Evidence** → interceptor thực hiện network call synchronous cho mỗi command. **Diagnosis** → observability path nằm trên hot path. **Fix** → logging non-blocking phù hợp, sampling/batching; không gọi remote service trực tiếp. **Verification** → benchmark và load test trước/sau.

## 7. Common mistakes

* Implement business rule trong interceptor.
* Tự retry command mà không hiểu transaction semantics.
* Log SQL parameters chứa secrets/PII.

## 8. Alternatives

EF logging/OpenTelemetry đủ cho pure observability; domain/application code phù hợp business auditing; database auditing phù hợp compliance ở DB boundary.

## 9. Trade-offs

### Advantages

Centralized, consistent, gần persistence mechanism.

### Costs / Risks

Hidden behavior, hot-path overhead, debugging khó nếu interceptor mutate commands.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu interceptor là persistence hook.

### Middle

Dùng cho diagnostics/audit đơn giản.

### Senior

Đánh giá transaction, security và performance implications.

### Technical Lead / Architect

Quyết định concern nào thực sự thuộc persistence boundary.

## 11. Key takeaway

* Interceptor tốt cho cross-cutting persistence concerns.
* Không biến interceptor thành hidden business layer.
* Đo overhead vì nó nằm trên đường chạy database nóng.

# 4. SQL SARGability: viết predicate để optimizer có thể seek thay vì ép database scan vì function trên indexed column

## 1. What is it?

SARGable predicate là điều kiện mà optimizer có thể dùng hiệu quả search argument với index. Một index tồn tại không đảm bảo query sử dụng được nó.

## 2. Why does it exist?

Khi function được áp lên indexed column, engine có thể phải tính function cho nhiều rows trước khi biết row nào match, dẫn tới scan và I/O lớn.

## 3. How does it work?

Không tốt:

```sql
WHERE CAST(CreatedAt AS date) = @date
```

Tốt hơn:

```sql
WHERE CreatedAt >= @start
  AND CreatedAt < @end
```

Với index trên `CreatedAt`, range predicate cho phép seek vào đúng key range.

## 4. Practical implementation

```sql
CREATE INDEX IX_Orders_CreatedAt
ON Orders(CreatedAt)
INCLUDE (Id, Status, Total);

SELECT Id, Status, Total
FROM Orders
WHERE CreatedAt >= @startUtc
  AND CreatedAt < @endUtc;
```

Kiểm tra actual execution plan và logical reads, không chỉ duration một lần.

## 5. Real production scenario

Report endpoint chạy nhanh với 100k rows nhưng chậm ở production 50 triệu rows. Plan cho thấy index scan vì query dùng `YEAR(CreatedAt) = 2026`.

## 6. Failure scenario & troubleshooting

**Symptom** → CPU/I/O tăng dù “đã có index”. **Evidence** → execution plan scan, logical reads rất cao. **Hypothesis** → predicate không SARGable. **Fix** → rewrite range predicate hoặc computed indexed column nếu domain cần. **Verification** → compare plan, reads, p95.

## 7. Common mistakes

* Function trên indexed column.
* Implicit type conversion giữa parameter và column.
* Leading wildcard `LIKE '%term'` rồi kỳ vọng B-tree seek.

## 8. Alternatives

Computed persisted column/index cho derived search; full-text search cho linguistic search; scan có thể đúng với low-selectivity query.

## 9. Trade-offs

### Advantages

Giảm I/O, tận dụng index, latency ổn định hơn khi data tăng.

### Costs / Risks

Rewrite có thể phức tạp; thêm computed/index structures tăng write/storage cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index chỉ hữu ích nếu predicate cho phép engine dùng nó.

### Middle

Đọc seek/scan và logical reads.

### Senior

Reason từ query → plan → I/O → index → locks → latency.

### Technical Lead / Architect

Thiết kế access patterns và schema thay vì chữa từng slow query riêng lẻ.

## 11. Key takeaway

* “Có index” không đồng nghĩa “query seek được”.
* Execution plan và I/O là evidence chính.
* Scan đôi khi đúng; mục tiêu là đúng access path, không phải seek bằng mọi giá.

# 5. MongoDB Change Streams: phản ứng với data changes mà không polling liên tục, nhưng phải thiết kế resume và recovery

## 1. What is it?

Change Streams cho application subscribe các thay đổi trong MongoDB collection/database dựa trên replication oplog thay vì polling table theo interval.

## 2. Why does it exist?

Polling tạo query load, latency theo interval và bookkeeping watermark. Change Streams cung cấp event-like feed gần data source cho projection, cache invalidation hoặc integration workflow.

## 3. How does it work?

Consumer mở change stream, nhận insert/update/delete events và có resume token. Nếu process restart, token có thể dùng để tiếp tục từ vị trí trước đó miễn history còn khả dụng.

## 4. Practical implementation

```csharp
var pipeline = new EmptyPipelineDefinition<ChangeStreamDocument<Product>>()
    .Match(x => x.OperationType == ChangeStreamOperationType.Update);

using var cursor = await collection.WatchAsync(pipeline, cancellationToken: ct);

await cursor.ForEachAsync(change =>
{
    Console.WriteLine(change.ResumeToken);
}, ct);
```

Production cần persist checkpoint/resume token sau khi side effect được xử lý theo semantics rõ ràng.

## 5. Real production scenario

Product catalog thay đổi cần cập nhật search projection. Change Stream worker đọc updates rồi index sang Elasticsearch mà không query MongoDB mỗi 5 giây.

## 6. Failure scenario & troubleshooting

**Symptom** → sau downtime dài consumer không resume được. **Evidence** → resume token nằm ngoài oplog history. **Diagnosis** → recovery assumption vượt retention window. **Fix** → full reconciliation/rebuild projection rồi lấy checkpoint mới. **Verification** → so sánh source-of-truth với projection.

## 7. Common mistakes

* Coi Change Stream là durable message broker vô hạn retention.
* Không persist resume token.
* Side effect không idempotent.
* Không có reconciliation path.

## 8. Alternatives

Polling đơn giản hơn cho low-frequency workload; dedicated broker tốt hơn cho explicit integration events; CDC platform phù hợp broader data pipelines.

## 9. Trade-offs

### Advantages

Latency thấp hơn polling, giảm repetitive reads, data-change integration thuận tiện.

### Costs / Risks

Phụ thuộc replication history, recovery phức tạp, event schema gắn với data model.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu stream phản ánh database changes.

### Middle

Consume và persist resume token.

### Senior

Thiết kế idempotency, checkpoint và reconciliation.

### Technical Lead / Architect

Quyết định data-change feed có nên là integration contract hay domain events rõ nghĩa tốt hơn.

## 11. Key takeaway

* Change Stream giảm polling nhưng không thay message broker trong mọi case.
* Resume token cần durable ownership.
* Projection luôn cần recovery/reconciliation strategy.

# 6. Bulkhead Pattern: cô lập concurrency/resource pool để một dependency chậm không chiếm hết capacity của application

## 1. What is it?

Bulkhead chia capacity thành các vùng độc lập, giống khoang kín trên tàu. Một dependency hoặc workload bị kẹt không được phép tiêu thụ toàn bộ thread, connection hoặc concurrency budget.

## 2. Why does it exist?

Partial failure dễ lan truyền. Nếu external review API chậm và mọi request được phép gọi đồng thời không giới hạn, nó có thể giữ hàng nghìn operations, làm chính API hết resource dù các endpoint khác không phụ thuộc review service.

## 3. How does it work?

```text
Product traffic → pool A (100)
Review traffic  → pool B (20)
Admin traffic   → pool C (10)
```

Khi pool B đầy, review work bị reject/queued theo policy thay vì lấy capacity của A/C.

## 4. Practical implementation

```csharp
private readonly SemaphoreSlim _reviewSlots = new(20);

public async Task<Review?> GetReviewAsync(Guid id, CancellationToken ct)
{
    if (!await _reviewSlots.WaitAsync(TimeSpan.FromMilliseconds(50), ct))
        return null; // graceful degradation if business allows

    try
    {
        return await client.GetFromJsonAsync<Review>($"reviews/{id}", ct);
    }
    finally
    {
        _reviewSlots.Release();
    }
}
```

Production thường kết hợp timeout, circuit breaker và metrics.

## 5. Real production scenario

Product page phụ thuộc optional reviews provider. Provider latency tăng 20 giây. Bulkhead giới hạn concurrent review calls; page vẫn trả product data với review section degraded.

## 6. Failure scenario & troubleshooting

**Symptom** → bulkhead luôn full dù dependency đã hồi phục. **Evidence** → operations không release permit khi exception/cancellation. **Fix** → `finally`, bounded timeout và cancellation. **Verification** → fault injection và gauge active/waiting slots.

## 7. Common mistakes

* Queue vô hạn phía trước bulkhead.
* Một global pool cho mọi dependencies.
* Retry bên trong saturated bulkhead làm giữ slot lâu hơn.

## 8. Alternatives

Queue load-leveling cho asynchronous work; separate service/process cho stronger isolation; concurrency limiter tại HTTP boundary.

## 9. Trade-offs

### Advantages

Failure isolation, predictable resource use, graceful degradation.

### Costs / Risks

Capacity tuning khó; reject sớm có thể giảm success rate dù downstream còn capacity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu không cho một dependency dùng hết resource.

### Middle

Implement bounded concurrency và cancellation.

### Senior

Kết hợp timeout/retry/circuit breaker đúng thứ tự.

### Technical Lead / Architect

Phân bổ concurrency budgets theo criticality và SLO.

## 11. Key takeaway

* Bulkhead ngăn partial failure trở thành system-wide failure.
* Queue vô hạn phá isolation.
* Capacity phải đo và tune theo workload thực.

# 7. Azure Blob Storage lifecycle tiers: tối ưu storage cost bằng access pattern mà không biến archival thành latency surprise

## 1. What is it?

Blob lifecycle management áp rule chuyển/xóa objects dựa trên tuổi hoặc access pattern. Storage tiers đổi trade-off giữa storage price, access price và retrieval latency.

## 2. Why does it exist?

File audit, export và media có thể tích lũy nhiều TB. Giữ tất cả ở hot tier đơn giản nhưng tốn chi phí; xóa sớm lại vi phạm retention/business need.

## 3. How does it work?

Rule định kỳ đánh giá blobs rồi chuyển tier hoặc delete. Application architecture phải hiểu rằng archived object có thể không phục vụ request realtime ngay lập tức.

## 4. Practical implementation

Ví dụ policy conceptual:

```json
{
  "rules": [{
    "name": "archive-old-exports",
    "enabled": true,
    "type": "Lifecycle",
    "definition": {
      "actions": {
        "baseBlob": {
          "tierToCool": { "daysAfterModificationGreaterThan": 30 },
          "delete": { "daysAfterModificationGreaterThan": 365 }
        }
      }
    }
  }]
}
```

Managed Identity nên được dùng cho application access thay vì embedded storage keys khi phù hợp.

## 5. Real production scenario

SaaS lưu monthly exports. 95% downloads xảy ra trong 14 ngày đầu; sau 90 ngày gần như chỉ compliance team truy cập. Lifecycle policy giảm hot-storage footprint mà không cần custom cleanup worker.

## 6. Failure scenario & troubleshooting

**Symptom** → user tải file cũ và latency/cost bất ngờ. **Evidence** → blob đã ở archival tier. **Diagnosis** → product SLA không khớp storage lifecycle. **Fix** → expose restore workflow hoặc giữ tier phù hợp cho files cần interactive access. **Verification** → test retrieval path và cost model.

## 7. Common mistakes

* Chọn tier chỉ theo storage price.
* Không tính early deletion/access charges.
* Lifecycle delete không align legal retention.
* Dùng public blob access không cần thiết.

## 8. Alternatives

Custom retention worker cho complex domain rules; separate containers theo lifecycle; database chỉ nên giữ metadata chứ không phải large binary payload trong nhiều cases.

## 9. Trade-offs

### Advantages

Tự động hóa retention/tiering, giảm storage cost, ít custom code.

### Costs / Risks

Retrieval latency/charges, policy delay, governance mistakes có thể xóa dữ liệu không thể phục hồi.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hot/cool/archive là cost-access trade-off.

### Middle

Cấu hình policy và secure access.

### Senior

Model access frequency, restore behavior, monitoring và retention.

### Technical Lead / Architect

Align storage lifecycle với product SLA, compliance và cost ownership.

## 11. Key takeaway

* Cheapest storage tier không luôn là cheapest system behavior.
* Lifecycle policy phải xuất phát từ access pattern và retention requirement.
* Security, restore path và monitoring là một phần của storage design.

# 8. RED và USE metrics: chọn telemetry theo service/resource để điều tra incident bằng evidence thay vì dashboard noise

## 1. What is it?

RED tập trung service/request: **Rate, Errors, Duration**. USE tập trung resource: **Utilization, Saturation, Errors**.

Hai mental models giúp chọn metrics có mục đích thay vì thu mọi counter có thể thu.

## 2. Why does it exist?

Dashboard có 200 charts không đồng nghĩa observability tốt. Incident cần nhanh chóng trả lời: user đang bị ảnh hưởng thế nào, bottleneck nằm ở service hay resource nào.

## 3. How does it work?

RED cho biết symptom ở request boundary. USE giúp drill down capacity constraint.

```text
RED: API duration p99 ↑
        ↓
USE: DB pool saturation ↑
        ↓
Trace: dependency wait ↑
        ↓
Logs: timeout evidence
```

## 4. Practical implementation

ASP.NET Core/OpenTelemetry thu request duration/error rate; custom metrics chỉ thêm khi business/system semantics không có sẵn.

Ví dụ metric hữu ích:

```csharp
var meter = new Meter("Orders");
var backlog = meter.CreateObservableGauge(
    "orders.queue.backlog",
    () => queueMetrics.PendingCount);
```

Alert nên gắn SLO/user impact hơn arbitrary CPU threshold đơn lẻ.

## 5. Real production scenario

API p99 tăng nhưng CPU 35%. RED xác nhận duration tăng và error chưa tăng. USE cho thấy SQL connection pool saturation cao. Trace cho thấy request chờ connection trước query execution.

## 6. Failure scenario & troubleshooting

**Symptom** → alert storm nhưng user không bị ảnh hưởng. **Evidence** → alert dựa từng host CPU spike ngắn. **Diagnosis** → telemetry không gắn service objective. **Fix** → alert theo sustained saturation/burn rate và correlate request impact. **Verification** → replay incident/fault test.

## 7. Common mistakes

* Chỉ nhìn averages.
* Alert mọi metric.
* High-cardinality labels như user ID.
* Metrics không có owner/runbook.

## 8. Alternatives

Golden Signals tương tự cho latency, traffic, errors, saturation. SLI/SLO framework dùng để quyết định mức nào thực sự quan trọng với user.

## 9. Trade-offs

### Advantages

Giảm dashboard noise, incident triage có cấu trúc, nối symptom với capacity.

### Costs / Risks

# 9. Optimizely CMS caching: content freshness, invalidation và multi-instance behavior quan trọng hơn việc “cache càng nhiều càng tốt”

## 1. What is it?

CMS caching giữ content/rendered data gần application để giảm repeated content-store access. Trong Optimizely, content APIs và platform caching đã có semantics riêng; custom caching phải tôn trọng publish/invalidation lifecycle.

## 2. Why does it exist?

Marketing pages có read-heavy workload. Query content store và compose blocks lại cho mỗi request gây latency/CPU không cần thiết. Nhưng CMS khác static data vì editors kỳ vọng publish được phản ánh đúng lúc.

## 3. How does it work?

```text
Editor publishes
   ↓
Content version changes
   ↓
Cache invalidation event
   ↓
App instances refresh/read new content
   ↓
CDN may still have separate TTL
```

Có nhiều cache layers: browser/CDN, output cache, application/content cache. Mỗi layer có owner và invalidation semantics khác nhau.

## 4. Practical implementation

Khi cần custom derived cache, key nên chứa stable content identity/version hoặc được invalidate theo content events thay vì TTL tùy ý.

```csharp
var cacheKey = $"product-page:{contentLink.ID}:{language.Name}:{version}";
```

Không cache editor-sensitive/personalized response bằng shared key thiếu variation dimensions.

## 5. Real production scenario

Editor publish campaign banner mới. Origin đã thấy content mới nhưng Akamai/CDN vẫn giữ HTML cũ 10 phút. Team tưởng Optimizely cache lỗi, thực tế stale layer nằm ở edge.

## 6. Failure scenario & troubleshooting

**Symptom** → instance A thấy content mới, instance B thấy cũ. **Evidence** → cache invalidation event không tới một node hoặc custom local cache không participate platform invalidation. **Diagnosis** → multi-instance cache ownership sai. **Fix** → dùng platform-supported cache/invalidation hoặc distributed strategy phù hợp. **Verification** → publish và request qua nhiều instances/edge paths.

## 7. Common mistakes

* Cache personalized content bằng global key.
* TTL rất dài nhưng không có invalidation.
* Clear toàn cache mỗi publish.
* Không phân biệt CMS cache với CDN cache.

## 8. Alternatives

Output caching cho response-level data; CDN cho public edge-cacheable pages; no custom cache khi built-in content cache đã đủ.

## 9. Trade-offs

### Advantages

Giảm content-store load, cải thiện latency, scale read-heavy traffic.

### Costs / Risks

Staleness, invalidation complexity, variation-key explosion, multi-layer debugging.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CMS publish và cache freshness liên quan nhau.

### Middle

Thiết kế cache key đủ language/version/variation.

### Senior

Debug stale content xuyên app/CDN/multi-instance layers.

### Technical Lead / Architect

Quyết định layer nào cache cái gì và ai sở hữu invalidation/SLA freshness.

## 11. Key takeaway

* Cache layer phải có owner và invalidation semantics.
* CMS freshness là product requirement, không chỉ TTL setting.
* Đừng thêm custom cache khi platform cache đã giải quyết vấn đề.

# 10. CSRF và SameSite cookies: browser tự gửi credential tạo ra attack surface khác hoàn toàn CORS

## 1. What is it?

CSRF xảy ra khi attacker khiến browser của user gửi request tới site mà user đã authenticated, và browser tự đính kèm credential như cookie.

SameSite cookie là một lớp giảm rủi ro bằng cách kiểm soát khi cookie được gửi trong cross-site context.

## 2. Why does it exist?

Cookie authentication tiện vì browser tự gửi cookie. Chính behavior đó tạo attack surface: malicious site không cần đọc cookie; nó chỉ cần khiến browser gửi state-changing request tới target.

## 3. How does it work?

```text
User logged into bank.example
      ↓
visits evil.example
      ↓
evil page submits POST to bank.example
      ↓
browser may attach auth cookie
```

Anti-forgery token chứng minh request đến từ page/app context được server phát token, không chỉ từ browser có cookie.

## 4. Practical implementation

Với ASP.NET Core app dùng cookie và form state changes, bật anti-forgery validation phù hợp. Cookie cần secure attributes:

```csharp
builder.Services.ConfigureApplicationCookie(options =>
{
    options.Cookie.HttpOnly = true;
    options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
    options.Cookie.SameSite = SameSiteMode.Lax;
});
```

SameSite choice phải phù hợp external login/payment flows; không copy setting máy móc.

## 5. Real production scenario

Admin portal dùng cookie auth. Endpoint `POST /users/{id}/disable` chỉ kiểm tra authentication và không anti-forgery. Attacker gửi admin một trang chứa auto-submit form. Nếu browser gửi cookie, action có thể chạy dưới identity của admin.

## 6. Failure scenario & troubleshooting

**Symptom** → OAuth/OIDC callback login fail sau khi đổi SameSite strict. **Evidence** → authentication correlation cookie không được gửi trong required cross-site flow. **Diagnosis** → security setting phá legitimate protocol flow. **Fix** → chọn SameSite policy theo exact flow và framework guidance, giữ anti-forgery cho state-changing app requests. **Verification** → test cross-site login và CSRF attack cases.

## 7. Common mistakes

* Nghĩ CORS chặn CSRF.
* Dùng GET cho state-changing operation.
* Tắt anti-forgery để fix frontend nhanh.
* Đặt SameSite mà không test external identity/payment redirects.

## 8. Alternatives

Bearer token trong explicit `Authorization` header thay đổi threat model vì browser không tự attach token như cookie, nhưng XSS/token storage risks lại khác. SameSite không thay hoàn toàn anti-forgery trong mọi architecture.

## 9. Trade-offs

### Advantages

Anti-forgery + cookie policy giảm cross-site request abuse mạnh.

### Costs / Risks

Protocol integrations phức tạp hơn; strict settings có thể phá legitimate cross-site flows.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CSRF dựa vào browser tự gửi credential.

### Middle

Cấu hình cookie/anti-forgery và dùng safe HTTP semantics.

### Senior

Phân biệt CSRF, CORS, XSS và OAuth redirect behavior.

### Technical Lead / Architect

Chọn browser authentication model và threat controls theo trust boundary toàn hệ thống.

## 11. Key takeaway

* CORS và CSRF giải quyết hai vấn đề khác nhau.
* Cookie tự động gửi là nguyên nhân cốt lõi của CSRF threat model.
* SameSite là defense layer, không phải excuse bỏ security design cho state-changing requests.
