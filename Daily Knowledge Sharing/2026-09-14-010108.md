# 1. C# `ArrayPool<T>`: giảm allocation trong hot path nhưng phải quản lý ownership, lifetime và dữ liệu cũ trong pooled buffers

## 1. What is it?

Mental model của `ArrayPool<T>` là **mượn một buffer dùng tạm rồi trả lại để người khác tái sử dụng**, thay vì tạo một array mới cho mỗi operation.

```text
Rent(minLength)
   |
   v
pooled array (có thể dài hơn yêu cầu)
   |
use within bounded lifetime
   |
Return(array)
   |
array quay lại pool
```

`ArrayPool<T>.Shared` đặc biệt hữu ích cho hot paths xử lý buffers tạm thời như serialization, parsing, compression hoặc network/file processing. Nó giảm số lượng arrays ngắn hạn phải đi qua GC.

Điểm khó là array được rent không còn thuộc riêng caller vĩnh viễn. Ownership chỉ tồn tại từ `Rent` đến `Return`.

## 2. Why does it exist?

Một API xử lý hàng chục nghìn requests mỗi giây có thể liên tục tạo `byte[]` 32–128 KB. Dù mỗi allocation nhỏ nhìn riêng lẻ, tổng allocation rate cao sẽ làm GC chạy thường xuyên. Array lớn hơn còn có thể đi vào Large Object Heap.

Straightforward code:

```csharp
var buffer = new byte[64 * 1024];
```

rất đúng cho phần lớn ứng dụng. Pooling chỉ đáng cân nhắc khi profiling cho thấy allocation của temporary arrays thật sự là bottleneck.

## 3. How does it work?

Pool giữ các arrays theo các bucket kích thước. Khi gọi:

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(4096);
```

caller có thể nhận array dài 4096, 8192 hoặc kích thước khác >= requested size.

Sau khi dùng:

```csharp
ArrayPool<byte>.Shared.Return(buffer);
```

buffer có thể được cấp lại cho operation khác.

Điều này kéo theo ba semantics quan trọng:

1. không dựa vào `Length == requestedLength`;
2. không dùng buffer sau khi đã return;
3. không giả định buffer mới được zero-initialize.

## 4. Practical implementation

Ví dụ đọc một stream với pooled buffer:

```csharp
using System.Buffers;

static async Task<long> DrainAsync(
    Stream input,
    CancellationToken ct)
{
    var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);

    try
    {
        long total = 0;

        while (true)
        {
            var read = await input.ReadAsync(
                buffer.AsMemory(0, 64 * 1024), ct);

            if (read == 0)
                return total;

            total += read;
        }
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer);
    }
}
```

Nếu buffer chứa secrets hoặc dữ liệu nhạy cảm và threat model yêu cầu, có thể:

```csharp
ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
```

nhưng clearing có CPU cost. Không nên bật theo thói quen cho mọi buffer.

## 5. Real production scenario

Một document-processing API nhận hàng nghìn files nhỏ, giải nén rồi hash nội dung. Profiler cho thấy phần lớn allocation rate đến từ các temporary `byte[]` 64 KB tạo trong mỗi stage.

Team thay riêng temporary buffers ở hot loop bằng `ArrayPool<byte>`. Allocation rate giảm rõ rệt, Gen 0 collections giảm và p99 ổn định hơn khi load cao. Team không đổi DTO arrays hoặc data cần sống lâu sang pooled arrays vì lifetime của chúng không phù hợp.

## 6. Failure scenario & troubleshooting

**Symptom** → dữ liệu thỉnh thoảng bị corrupt hoặc request A thấy bytes thuộc request B.

**Evidence** → code return array về pool trước khi asynchronous consumer hoàn thành; hoặc lưu pooled array trong object sống lâu.

**Hypothesis** → ownership/lifetime của buffer bị vi phạm.

**Diagnosis** → trace từ `Rent` đến `Return`, xác định mọi nơi buffer được capture, await hoặc truyền sang background operation.

**Fix** → giữ ownership đến khi consumer cuối cùng hoàn tất; copy dữ liệu nếu lifetime phải vượt pooled scope.

**Verification** → stress/concurrency tests với random payloads, checksum và race-heavy execution.

## 7. Common mistakes

- Dùng `ArrayPool<T>` trước khi đo allocation.
- Return buffer rồi vẫn giữ `Memory<T>`/`Span<T>` trỏ vào nó.
- Giả định rented array đã được clear.
- Xử lý toàn bộ `buffer.Length` thay vì số bytes thực sự valid.
- Quên `finally`, làm buffer không được return khi exception.
- Pool object có lifetime dài thay vì temporary workspace.
- Clear mọi buffer dù dữ liệu không nhạy cảm và throughput quan trọng.

## 8. Alternatives

- `new T[]`: mặc định đơn giản và đúng khi allocation rate không đáng kể.
- `stackalloc`: tốt cho buffer nhỏ, bounded và synchronous scope.
- `MemoryPool<T>`: phù hợp một số pipeline cần ownership abstraction qua `IMemoryOwner<T>`.
- `System.IO.Pipelines`: phù hợp high-performance streaming protocols hơn việc tự quản nhiều buffers.

## 9. Trade-offs

### Advantages

- Giảm temporary allocations và GC pressure.
- Hữu ích cho high-throughput I/O/parsing.
- Có thể tránh nhiều large-array allocations lặp lại.

### Costs / Risks

- Ownership semantics phức tạp hơn.
- Có rủi ro data leakage/corruption khi lifetime sai.
- Pooling có thể không cải thiện gì nếu allocation vốn không phải bottleneck.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu array thông thường thuộc caller, còn pooled array chỉ được mượn tạm.

### Middle

Biết `Rent`/`Return`, `try/finally`, valid length và không dùng buffer sau `Return`.

### Senior

Dùng profiler/benchmark để chứng minh pooling có ích; đánh giá LOH, allocation rate, security và async lifetime.

### Technical Lead / Architect

Quyết định hot-path libraries nào được phép dùng pooling và giữ API ownership đủ rõ để performance optimization không biến thành correctness risk.

## 11. Key takeaway

- `ArrayPool<T>` là optimization cho temporary buffers, không phải default collection strategy.
- Ownership từ `Rent` đến `Return` phải tuyệt đối rõ.
- Đo allocation/GC trước và sau; complexity chỉ đáng trả khi evidence chứng minh lợi ích.

# 2. ASP.NET Core idempotency keys cho `POST`: chống duplicate business side effects khi client retry sau timeout

## 1. What is it?

Idempotency key là client-generated identifier gắn với một logical operation. Nếu cùng operation được gửi lại với cùng key, server trả cùng outcome hoặc nhận diện nó đã được xử lý thay vì tạo side effect lần nữa.

```text
POST /payments
Idempotency-Key: abc-123

request 1 -> payment created
response lost

request 2, same key
        -> previous result
        -> không charge lần 2
```

Đây là business deduplication boundary, không chỉ HTTP middleware trick.

## 2. Why does it exist?

Distributed systems có ambiguous outcomes. Client timeout không có nghĩa server chưa xử lý request.

Ví dụ:

```text
Client -> API -> Payment Provider: charge success
                     |
                API response
                     X network lost
```

Client chỉ thấy timeout. Nếu retry một `POST` không idempotent, payment có thể bị charge lần hai.

Retry là cần thiết cho resilience, nhưng retry một side effect không có deduplication có thể phá correctness.

## 3. How does it work?

Server lưu association:

```text
(idempotency key, operation scope, request fingerprint)
       -> status/result
```

Khi request mới đến:

1. validate key;
2. xác định scope, ví dụ tenant + endpoint;
3. kiểm tra key đã tồn tại;
4. nếu đã completed, trả result trước;
5. nếu đang processing, trả trạng thái phù hợp hoặc chờ theo policy;
6. nếu mới, claim key và thực hiện operation;
7. persist outcome.

Request fingerprint giúp phát hiện client tái sử dụng cùng key cho payload khác.

## 4. Practical implementation

Schema tối giản:

```sql
CREATE TABLE IdempotencyRecords (
    TenantId uuid NOT NULL,
    IdempotencyKey text NOT NULL,
    RequestHash text NOT NULL,
    Status text NOT NULL,
    ResponseCode int NULL,
    ResponseBody jsonb NULL,
    CreatedAtUtc timestamptz NOT NULL,
    PRIMARY KEY (TenantId, IdempotencyKey)
);
```

Endpoint có thể yêu cầu header:

```csharp
app.MapPost("/orders", async (
    HttpRequest request,
    CreateOrder command,
    OrderService service,
    CancellationToken ct) =>
{
    if (!request.Headers.TryGetValue("Idempotency-Key", out var key))
        return Results.BadRequest(new { error = "idempotency_key_required" });

    return await service.CreateIdempotentlyAsync(
        key.ToString(), command, ct);
});
```

Phần quan trọng nằm trong transaction/coordination của `CreateIdempotentlyAsync`, không phải việc đọc header.

## 5. Real production scenario

Mobile app gọi `POST /checkout`. User đang ở mạng yếu. Backend đã tạo order và gọi payment thành công nhưng response không tới thiết bị.

Mobile SDK retry sau 3 giây. Không có idempotency, hệ thống tạo order thứ hai. Có idempotency key theo checkout attempt, request thứ hai resolve về order cũ.

## 6. Failure scenario & troubleshooting

**Symptom** → duplicate orders/payments xuất hiện đúng thời điểm latency hoặc network errors tăng.

**Evidence** → logs có cùng business intent từ cùng client trong vài giây nhưng request IDs khác nhau.

**Hypothesis** → retry đang tạo side effect mới vì hệ thống không có durable deduplication.

**Diagnosis** → trace client retry policy, API, DB transaction và downstream provider semantics.

**Fix** → introduce idempotency key ở operation boundary; dùng downstream idempotency feature nếu provider hỗ trợ.

**Verification** → integration test bằng cách làm mất response sau khi side effect thành công rồi retry cùng key.

## 7. Common mistakes

- Dùng request ID làm idempotency key dù mỗi retry sinh request ID mới.
- Chỉ cache response trong memory; restart instance là mất deduplication.
- Không scope key theo tenant/operation.
- Cho cùng key đi với payload khác mà không reject.
- Xóa record quá sớm trong khi client vẫn có thể retry.
- Lock toàn endpoint thay vì atomic claim theo key.
- Giả định database insert và external side effect tự nhiên atomic với nhau.

## 8. Alternatives

- HTTP `PUT` với client-defined resource ID nếu domain tự nhiên phù hợp.
- Unique business constraint, ví dụ unique `ExternalOrderId`.
- Downstream provider idempotency keys.
- Queue + idempotent consumer cho asynchronous workflows.

## 9. Trade-offs

### Advantages

- Cho phép safe retry sau timeout/network failure.
- Giảm duplicate business side effects.
- Làm ambiguous outcome dễ xử lý hơn.

### Costs / Risks

- Cần storage/retention/cleanup.
- Concurrent requests cùng key cần coordination.
- External side effects vẫn cần strategy riêng nếu không cùng transaction.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu retry `POST` có thể tạo duplicate side effect.

### Middle

Implement key validation, persistence và replay response.

### Senior

Giải quyết concurrency, request fingerprint, retention và external side-effect ambiguity.

### Technical Lead / Architect

Quyết định operation nào bắt buộc idempotency, key ownership ở client hay server, và consistency boundary xuyên API/database/provider.

## 11. Key takeaway

- Timeout không chứng minh operation thất bại.
- Safe retry cần durable idempotency ở business boundary.
- Idempotency key phải gắn với cùng intent, không chỉ cùng HTTP request.

# 3. EF Core compiled queries: giảm query-compilation overhead nhưng chỉ có giá trị khi query thật sự là hot path ổn định

## 1. What is it?

EF Core phải biến LINQ expression thành database command. EF đã cache query compilation theo query shape, nhưng compiled query cho phép application tạo delegate đã compile trước và gọi lại trực tiếp.

Mental model:

```text
normal query
LINQ expression
 -> identify query shape/cache
 -> translation pipeline
 -> command
 -> database

compiled query
precompiled delegate
 -> parameter values
 -> command
 -> database
```

Compiled query tối ưu CPU phía application; nó không làm SQL query hoặc database I/O tự nhiên nhanh hơn.

## 2. Why does it exist?

Ở high-throughput hot paths với query rất nhỏ và database cực nhanh, overhead của EF query pipeline có thể trở thành tỷ lệ đáng kể.

Nhưng với query mất 80 ms ở database, tiết kiệm vài microseconds ở client không giải quyết root cause. Trước khi compiled query, phải đo xem bottleneck nằm ở translation/client CPU hay SQL/I/O.

## 3. How does it work?

Ví dụ:

```csharp
private static readonly Func<AppDbContext, Guid, User?> GetUser =
    EF.CompileQuery(
        (AppDbContext db, Guid id) =>
            db.Users
              .AsNoTracking()
              .SingleOrDefault(x => x.Id == id));
```

Gọi:

```csharp
var user = GetUser(db, userId);
```

Async:

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<User>> ActiveUsers =
    EF.CompileAsyncQuery(
        (AppDbContext db, Guid tenantId) =>
            db.Users
              .AsNoTracking()
              .Where(x => x.TenantId == tenantId && x.IsActive));
```

Query shape phải ổn định và parameters nên được truyền rõ ràng.

## 4. Practical implementation

Trước khi introduce compiled query:

1. đo endpoint CPU và DB duration;
2. kiểm tra SQL/generated plan;
3. benchmark query execution với representative data;
4. chỉ compile query được gọi cực nhiều và shape ổn định.

Ví dụ hot lookup trong authorization layer có hàng chục nghìn calls/second có thể là candidate tốt hơn report query chạy vài lần/phút.

## 5. Real production scenario

Một authorization API đọc mapping tenant-user bằng indexed primary/unique lookup mất ~1 ms ở DB và chạy rất nhiều lần. CPU profile phía API cho thấy đáng kể thời gian ở query setup.

Compiled query giảm CPU/application overhead đủ để tăng throughput. Team không áp dụng compiled queries cho toàn repository vì maintenance cost tăng và database latency vẫn thống trị phần lớn queries.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries nhưng endpoint latency gần như không đổi.

**Evidence** → traces cho thấy 95% duration nằm ở DB network/I/O; SQL scan hàng triệu rows.

**Hypothesis** → optimization nhắm sai layer.

**Diagnosis** → tách application query-preparation duration khỏi database command duration và execution plan.

**Fix** → tune access pattern/index/query trước; bỏ compiled query nếu không còn value.

**Verification** → benchmark end-to-end chứ không chỉ microbenchmark delegate invocation.

## 7. Common mistakes

- Nghĩ compiled query tương đương SQL compiled plan.
- Dùng nó để chữa N+1 hoặc full scan.
- Tạo hàng trăm compiled delegates cho queries hiếm.
- Embed dynamic constants làm query variants khó kiểm soát.
- Bỏ qua database plan/I/O.
- Tối ưu trước khi đo.

## 8. Alternatives

- Dựa vào query cache mặc định của EF Core, đủ cho đa số applications.
- Raw SQL/Dapper cho một số hot read paths khi abstraction/performance justify.
- Database-side optimization như index, materialized/read model khi bottleneck ở DB.

## 9. Trade-offs

### Advantages

- Giảm một phần EF query-processing overhead.
- Có ích cho stable, frequently executed hot queries.

### Costs / Risks

- Code ít linh hoạt và khó đọc hơn LINQ thông thường.
- Lợi ích nhỏ nếu DB/network dominate.
- Có thêm benchmark/maintenance burden.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ phải được translate; query chưa chạy chỉ vì expression đã được tạo.

### Middle

Biết generated SQL, `AsNoTracking` và query shape quan trọng hơn micro-optimization.

### Senior

Đo client CPU vs database duration để biết compiled query có đáng dùng.

### Technical Lead / Architect

Cho phép specialized optimization ở measured hot paths nhưng tránh biến nó thành repository-wide convention.

## 11. Key takeaway

- Compiled query tối ưu EF-side overhead, không sửa SQL tệ.
- Chỉ dùng khi hot path đủ nóng để overhead đó đáng kể.
- Benchmark end-to-end và giữ giải pháp đơn giản nếu default query cache đã đủ.

# 4. PostgreSQL connection pool exhaustion: pool cạn thường là triệu chứng của transaction/I/O chậm chứ không chỉ “thiếu connection”

## 1. What is it?

Connection pool giữ một số physical database connections để application tái sử dụng thay vì mở TCP/TLS/authentication mới cho mỗi query.

Mental model:

```text
requests
   |
   v
Npgsql pool
 [conn][conn][conn] ... max
   |
 PostgreSQL
```

Pool exhaustion xảy ra khi mọi pooled connection đều đang bận và requests mới phải chờ hoặc timeout.

## 2. Why does it exist?

Database connection đắt hơn object C# thông thường. Pooling giảm connect overhead, nhưng đồng thời tạo capacity boundary.

Nếu pool size là 100 và 100 operations giữ connections trong 20 giây, request thứ 101 không thể “async” ra thêm capacity vô hạn. Nó phải chờ.

Tăng pool lên 500 có thể chỉ chuyển bottleneck sang PostgreSQL, làm nhiều active queries cạnh tranh CPU/I/O/locks mạnh hơn.

## 3. How does it work?

Với Npgsql, connection pooling thường bật mặc định theo connection string. `OpenAsync` có thể lấy connection đã tồn tại từ pool.

Một `DbContext`/command thường chỉ cần physical connection khi thực sự query/save. Nhưng transaction dài hoặc streaming reader có thể giữ connection lâu.

Little’s Law cho trực giác capacity:

```text
concurrency ≈ throughput × duration
```

Nếu query duration tăng 10x, số concurrent connections cần để giữ cùng throughput cũng tăng gần tương ứng.

## 4. Practical implementation

Dùng short-lived contexts/connections:

```csharp
await using var db = await dbFactory.CreateDbContextAsync(ct);

var order = await db.Orders
    .AsNoTracking()
    .SingleOrDefaultAsync(x => x.Id == id, ct);
```

Không giữ transaction trong khi chờ remote API:

```csharp
// Tránh:
// BEGIN TRANSACTION
// query
// await externalApi.CallAsync(...)
// update
// COMMIT
```

Thay vào đó, thu hẹp DB transaction và thiết kế external side effects bằng durable workflow/idempotency khi cần.

## 5. Real production scenario

Checkout service bình thường query PostgreSQL trong 30 ms. Một migration/index issue làm query inventory tăng lên 4 giây. Pool 100 connections nhanh chóng đầy. Sau đó mọi endpoints dùng cùng pool đều timeout, kể cả queries vốn nhanh.

Incident nhìn giống “database connection problem”, nhưng root cause là một query/access path giữ connection quá lâu.

## 6. Failure scenario & troubleshooting

**Symptom** → `Timeout while getting a connection from pool`, request latency tăng và DB connections chạm ngưỡng.

**Evidence** → active sessions/long-running queries tăng; pool wait time tăng; DB lock hoặc I/O metrics xấu.

**Hypothesis** → connections bị giữ lâu bởi query, transaction, reader hoặc leak.

**Diagnosis** → correlate application pool metrics/traces với `pg_stat_activity`, lock waits và slow-query evidence.

**Fix** → sửa long query/transaction/lifetime; sau đó mới cân nhắc pool size dựa trên measured concurrency và DB capacity.

**Verification** → load test ở traffic target, theo dõi pool wait, active DB sessions, query duration và DB saturation.

## 7. Common mistakes

- Tăng max pool size ngay khi thấy timeout.
- Giữ transaction khi gọi external API.
- Không dispose context/connection/reader đúng cách.
- Mỗi service instance có pool 100 nhưng quên nhân với 30 replicas.
- Set database max connections quá cao mà không tính memory/process cost.
- Không có timeout/cancellation hợp lý.
- Chỉ nhìn application logs, không nhìn `pg_stat_activity`.

## 8. Alternatives

- Connection proxy/pooler như PgBouncer trong topology phù hợp.
- Queue/background processing để giảm synchronous concurrency spikes.
- Read replicas/read models nếu workload đọc thật sự vượt capacity.
- Caching khi dữ liệu phù hợp, nhưng không dùng cache để che query path sai.

## 9. Trade-offs

### Advantages

- Pooling giảm connection setup cost.
- Giới hạn pool giúp tạo backpressure thay vì mở connections vô hạn.

### Costs / Risks

- Pool size sai có thể underutilize hoặc overload database.
- Scale-out application nhân tổng connections.
- Long transactions biến pool thành shared bottleneck.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbConnection` là tài nguyên hữu hạn và phải dispose đúng cách.

### Middle

Biết pool, transaction lifetime và async queries ảnh hưởng connection occupancy.

### Senior

Điều tra pool exhaustion bằng app telemetry + PostgreSQL sessions/locks/query plans.

### Technical Lead / Architect

Budget connections theo toàn fleet, database capacity và failure mode; tránh mỗi team tự tăng pool độc lập.

## 11. Key takeaway

- Pool exhaustion thường là downstream symptom của slow/blocked work.
- Pool size phải tính trên toàn số replicas, không trên một process.
- Thu hẹp transaction/connection occupancy trước khi tăng limits.

# 5. Anti-Corruption Layer: bảo vệ domain model khỏi contract và semantics của legacy/third-party systems

## 1. What is it?

Anti-Corruption Layer (ACL) là boundary dịch giữa model/semantics của hệ thống bên ngoài và domain model nội bộ.

```text
Our Domain
   |
Our Port / Interface
   |
Anti-Corruption Layer
   |  translate
External SDK/API/Legacy Model
```

Mục tiêu không phải chỉ map DTO fields. ACL ngăn vocabulary, failure semantics, identifiers và lifecycle của external system lan vào domain.

## 2. Why does it exist?

Giả sử provider gọi khách hàng là `Account`, dùng status `A`, `S`, `X`, trả lỗi bằng code số và có identifier format riêng.

Nếu toàn codebase bắt đầu dùng `ProviderAccountDto`, `StatusCode = "A"` và SDK exception, domain dần phụ thuộc vendor contract. Thay provider hoặc sửa business rule sẽ chạm khắp hệ thống.

ACL cô lập volatility đó.

## 3. How does it work?

Application/domain phụ thuộc abstraction nội bộ:

```csharp
public interface ICreditRiskService
{
    Task<RiskAssessment> AssessAsync(
        Customer customer,
        CancellationToken ct);
}
```

Infrastructure adapter gọi external API:

```csharp
public sealed class VendorRiskAdapter : ICreditRiskService
{
    private readonly VendorClient _client;

    public VendorRiskAdapter(VendorClient client) => _client = client;

    public async Task<RiskAssessment> AssessAsync(
        Customer customer,
        CancellationToken ct)
    {
        var response = await _client.ScoreAsync(
            new VendorRequest(customer.ExternalReference), ct);

        return response.Code switch
        {
            "G" => RiskAssessment.Low(),
            "R" => RiskAssessment.High(),
            _ => RiskAssessment.Unknown()
        };
    }
}
```

Translation boundary cũng map timeouts/errors thành semantics mà application hiểu.

## 4. Practical implementation

Một ACL tốt thường chịu trách nhiệm:

- request/response mapping;
- identifier translation;
- enum/status translation;
- error normalization;
- resilience policy phù hợp dependency;
- telemetry/correlation;
- compatibility với provider versions.

Không nên để adapter chứa toàn business workflow. Nó dịch boundary; domain vẫn quyết định business policy.

## 5. Real production scenario

E-commerce platform tích hợp legacy ERP có khái niệm “available stock” khác storefront. ERP coi hàng đang transfer giữa warehouses là available, còn storefront không muốn bán số đó.

Nếu map field `AvailableQty` trực tiếp vào domain, semantics sai. ACL chuyển ERP fields thành `SellableInventory` theo contract đã thống nhất và giữ ERP-specific rules tại boundary.

## 6. Failure scenario & troubleshooting

**Symptom** → provider đổi status code và hàng loạt business branches trong application lỗi.

**Evidence** → external DTOs/status strings xuất hiện trong domain/application layers.

**Hypothesis** → provider model đã xuyên qua integration boundary.

**Diagnosis** → search dependencies/types/constants của provider trong codebase và data model.

**Fix** → tạo internal contract + adapter translation; migrate call sites dần.

**Verification** → contract/integration tests với provider fixtures, đồng thời unit-test domain không reference provider packages/types.

## 7. Common mistakes

- Gọi mọi mapping class là ACL dù external semantics vẫn lan vào domain.
- Tạo abstraction giống hệt vendor API nên không giảm coupling.
- Đặt business rules cốt lõi trong adapter.
- Nuốt provider errors thành `null`.
- Không version/test mapping.
- Tạo ACL cho internal dependency ổn định đơn giản dù không có meaningful translation need.

## 8. Alternatives

- Gọi SDK/API trực tiếp khi integration nhỏ, ổn định và switching cost thấp.
- Generic gateway wrapper nếu chỉ cần transport/resilience, không có semantic translation.
- Separate integration service khi boundary đủ lớn và có ownership/deployment needs riêng.

## 9. Trade-offs

### Advantages

- Cô lập vendor/legacy volatility.
- Giữ domain vocabulary sạch.
- Làm migration/provider replacement dễ hơn.

### Costs / Risks

- Thêm mapping/code/tests.
- Có thể trở thành abstraction ceremony nếu external contract rất đơn giản.
- Translation semantics cần owner rõ ràng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu domain model không nhất thiết giống external DTO.

### Middle

Implement adapter mapping và error translation rõ ràng.

### Senior

Thiết kế boundary theo semantic differences, compatibility và failure behavior.

### Technical Lead / Architect

Quyết định integration nào đáng có ACL, ownership ở đâu và khi nào boundary nên thành service riêng thay vì library/module.

## 11. Key takeaway

- ACL bảo vệ semantics, không chỉ hide SDK.
- External vocabulary/status/errors không nên lan khắp domain.
- Chỉ thêm ACL khi integration volatility/coupling đủ để justify abstraction.

# 6. Scheduled work trên nhiều application instances: vì sao timer chạy một lần trong code có thể chạy N lần trong production

## 1. What is it?

Một `BackgroundService` hoặc timer nằm trong web application chạy **một lần trên mỗi process/instance**, không phải một lần cho toàn hệ thống.

```text
App instance A -> timer -> job
App instance B -> timer -> job
App instance C -> timer -> job

=> cùng logical schedule có thể chạy 3 lần
```

Đây là distributed execution problem.

## 2. Why does it exist?

Local developer thường chỉ chạy một process nên `PeriodicTimer` trông giống singleton scheduler.

Production autoscaling, deployment slots, rolling deployments hoặc Kubernetes replicas tạo nhiều processes. Mỗi process đều khởi tạo hosted service của riêng nó.

Nếu job gửi invoices, emails hoặc settlement, duplicate execution có business impact thật.

## 3. How does it work?

Có ba strategy chính:

1. **job idempotent** — nhiều executions không tạo duplicate effect;
2. **distributed coordination/lock** — chỉ một instance claim execution;
3. **external scheduler/queue** — schedule được tách khỏi web replicas.

Ngay cả khi có distributed lock, crash sau side effect nhưng trước release/mark-complete vẫn có thể tạo ambiguity. Vì vậy idempotency vẫn quan trọng.

## 4. Practical implementation

Với job đơn giản, tách trigger khỏi processor:

```text
Scheduler
  |
  v
Queue message { jobName, scheduledAt }
  |
competing consumers
  |
idempotent handler
```

Handler lưu execution key:

```text
DailyInvoice:2026-09-14
```

với unique constraint trước khi tạo side effects.

Nếu dùng distributed lock, lock phải có lease/expiry và fencing/ownership semantics phù hợp; không nên tự chế bằng một Redis `SET` không hiểu failure modes.

## 5. Real production scenario

Marketing site có `BackgroundService` gửi daily digest lúc 08:00. App Service scale từ 1 lên 4 instances. Một sáng users nhận bốn emails giống nhau.

Code timer không “chạy sai”; deployment topology đã thay đổi assumption từ singleton process thành replicated process.

## 6. Failure scenario & troubleshooting

**Symptom** → job chạy duplicate chỉ ở production hoặc trong lúc deploy/scale.

**Evidence** → logs có cùng scheduled timestamp nhưng khác instance IDs.

**Hypothesis** → schedule nằm trong replicated app mà không có system-wide coordination.

**Diagnosis** → kiểm tra hosting replicas, slot overlap, restart behavior và job execution records.

**Fix** → idempotent execution + external scheduler/queue hoặc proven distributed coordination.

**Verification** → chạy với nhiều replicas, kill leader/worker giữa execution và xác nhận không tạo duplicate business side effects.

## 7. Common mistakes

- Tin `BackgroundService` là singleton toàn cluster.
- Dùng in-memory flag `isRunning`.
- Distributed lock nhưng không có expiry.
- Có lock nhưng operation vẫn không idempotent.
- Job kéo dài hơn lock lease nhưng không renew.
- Scheduler và business processing gắn chặt trong web process.
- Không record execution identity/status.

## 8. Alternatives

- Azure Functions Timer Trigger cho scheduled trigger, nhưng vẫn cần hiểu retry/idempotency.
- Azure Service Bus queue để distribute work.
- Dedicated Worker Service với controlled replica count.
- Platform scheduler/Quartz/Hangfire với persistent coordination khi phù hợp.

## 9. Trade-offs

### Advantages

- External scheduling/queue làm execution topology rõ hơn.
- Idempotency giúp chịu retry/crash tốt hơn cả lock-only design.

### Costs / Risks

- Thêm queue/scheduler/storage làm operational footprint lớn hơn.
- Distributed locks có lease/network failure semantics phức tạp.
- Dedicated worker có deployment/monitoring riêng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu hosted service chạy trong mỗi process.

### Middle

Biết tạo idempotent job key và tránh in-memory coordination.

### Senior

Thiết kế retry, lease, crash recovery và execution history.

### Technical Lead / Architect

Chọn giữa in-process schedule, distributed lock, durable scheduler hoặc messaging dựa trên business criticality và operational cost.

## 11. Key takeaway

- Một timer trong replicated app không phải global singleton.
- Idempotency quan trọng hơn niềm tin rằng lock sẽ không bao giờ fail.
- Scheduled trigger và durable processing nên tách khi business impact lớn.

# 7. Azure App Configuration Feature Flags: tách deploy khỏi release nhưng phải kiểm soát targeting, stale configuration và cleanup

## 1. What is it?

Feature flag cho phép deploy code path mới nhưng quyết định runtime có bật cho ai/khi nào thông qua configuration.

Azure App Configuration cung cấp centralized configuration và feature-management integration cho .NET.

```text
deploy code
   |
flag OFF -> old behavior
   |
enable 5% / internal users / tenant
   |
observe
   |
expand rollout
```

Deploy và release trở thành hai hoạt động khác nhau.

## 2. Why does it exist?

Nếu mọi feature activation bắt buộc deploy binary mới, rollback behavior cũng cần redeploy. Điều đó làm release coupling cao.

Feature flags cho phép dark launch, progressive rollout và kill switch. Nhưng flag không thay thế testing; nó thêm runtime branch cần quản lý.

## 3. How does it work?

Application đọc flag từ configuration provider và evaluate theo filter.

Ví dụ .NET:

```csharp
builder.Configuration.AddAzureAppConfiguration(options =>
{
    options.Connect(new Uri(endpoint), new DefaultAzureCredential())
           .UseFeatureFlags();
});

builder.Services.AddFeatureManagement();
```

Usage:

```csharp
if (await featureManager.IsEnabledAsync("NewCheckout"))
{
    return await newCheckout.ExecuteAsync(ct);
}

return await oldCheckout.ExecuteAsync(ct);
```

Refresh/caching semantics quyết định bao lâu application thấy thay đổi mới.

## 4. Practical implementation

Flag nên có:

- owner;
- purpose;
- default;
- rollout rule;
- telemetry dimension;
- expiry/removal date.

Authorization/security-critical behavior không nên dựa vào client-side flag. Server-side deterministic policy vẫn phải enforce quyền.

Khi rollout, compare error rate, latency và business metrics giữa cohorts nếu design cho phép.

## 5. Real production scenario

Team deploy checkout engine mới nhưng chỉ bật cho employees trước. Sau đó bật 5% traffic. Metrics cho thấy payment latency tăng ở cohort mới nên team tắt flag ngay mà không rollback toàn deployment.

Sau khi sửa, rollout lại. Khi 100% ổn định, old path và flag được remove.

## 6. Failure scenario & troubleshooting

**Symptom** → portal đã tắt flag nhưng một số instances vẫn chạy feature mới.

**Evidence** → instances có config refresh timestamps khác nhau; network/private endpoint issue khiến một số nodes không refresh.

**Hypothesis** → stale cached configuration.

**Diagnosis** → kiểm tra provider refresh policy, App Configuration availability/network và per-instance telemetry của evaluated flag version.

**Fix** → thiết kế refresh/fallback phù hợp; với kill switch critical, chọn bounded staleness có chủ đích.

**Verification** → controlled flag flip dưới multi-instance environment và đo propagation delay.

## 7. Common mistakes

- Giữ flag vĩnh viễn sau rollout.
- Lồng quá nhiều flags làm state space không test nổi.
- Dùng flag như authorization.
- Không biết default behavior khi App Configuration unavailable.
- Không log/metric cohort hoặc evaluated flag.
- Client quyết định sensitive server behavior.
- Flag name kỹ thuật nhưng không có owner/expiry.

## 8. Alternatives

- Environment configuration cho behavior ổn định theo environment.
- Deployment slots/blue-green cho whole-release switching.
- Canary deployment ở infrastructure layer cho traffic-based binary rollout.
- Simple database/config setting nếu scale/targeting requirements rất nhỏ.

## 9. Trade-offs

### Advantages

- Giảm coupling giữa deployment và user exposure.
- Hỗ trợ gradual rollout/kill switch.
- Giảm blast radius của feature release.

### Costs / Risks

- Tăng runtime complexity và test combinations.
- Stale config là failure mode mới.
- Flags không cleanup tạo permanent technical debt.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu flag điều khiển runtime behavior, không phải preprocessor compile switch.

### Middle

Implement server-side evaluation và fallback/default rõ ràng.

### Senior

Thiết kế refresh, rollout telemetry, cohort correctness và cleanup lifecycle.

### Technical Lead / Architect

Quy định loại flags, ownership, expiry, security boundaries và khi nào dùng app flag vs deployment-level canary.

## 11. Key takeaway

- Feature flags tách deploy khỏi release nhưng tạo runtime state cần governance.
- Quan sát propagation/staleness và cohort metrics, không chỉ trạng thái portal.
- Flag tạm thời phải được xóa sau khi rollout hoàn tất.

# 8. Elasticsearch refresh interval & bulk indexing: search gần real-time không đồng nghĩa document vừa ghi sẽ lập tức tìm thấy

## 1. What is it?

Elasticsearch là near-real-time search engine. Document index thành công không nhất thiết lập tức visible với search. Search visibility thường phụ thuộc refresh tạo searchable segments.

```text
index request accepted
      |
translog / in-memory indexing
      |
refresh
      |
new segment searchable
      |
search sees document
```

`refresh_interval` cân bằng search freshness với indexing throughput.

## 2. Why does it exist?

Nếu mỗi indexed document buộc phải tạo/searchable segment ngay lập tức, indexing cost sẽ cao. Elasticsearch batch nhiều changes rồi refresh theo interval.

Điều này phù hợp search systems vì vài trăm milliseconds hoặc vài giây delay thường chấp nhận được, nhưng không phù hợp assumption “write succeeded => immediate search read”.

## 3. How does it work?

Bulk indexing giảm per-request overhead:

```http
POST _bulk
{"index":{"_index":"products","_id":"p1"}}
{"name":"Keyboard","price":120}
{"index":{"_index":"products","_id":"p2"}}
{"name":"Mouse","price":40}
```

Sau bulk response, documents đã được accepted/indexed theo semantics của operation, nhưng search visibility phụ thuộc refresh.

`refresh=wait_for` có thể chờ refresh khi workflow thực sự cần read-after-write search visibility, nhưng dùng đại trà làm giảm throughput/raise latency.

## 4. Practical implementation

Search projection pipeline:

```text
SQL transaction
   |
Outbox/change event
   |
Indexer consumer
   |
Bulk API
   |
Elasticsearch
   |
Search API
```

UI sau product update có thể đọc source-of-truth SQL cho confirmation screen thay vì yêu cầu Elasticsearch phản ánh ngay lập tức.

Indexer nên metric:

- batch size;
- bulk duration;
- item-level failures;
- indexing lag;
- refresh/search freshness where relevant.

## 5. Real production scenario

Editor publish sản phẩm và lập tức search trong admin UI nhưng chưa thấy trong 1–2 giây. Team ban đầu coi đây là bug “lost document” và force refresh sau mọi write.

Indexing throughput giảm mạnh trong campaign import. Correct design là phân biệt transactional confirmation với eventual search projection, chỉ dùng stronger freshness ở workflow thật sự cần.

## 6. Failure scenario & troubleshooting

**Symptom** → DB có record mới nhưng search chưa thấy; hoặc bulk indexing throughput tụt sau khi giảm refresh interval.

**Evidence** → event/indexing lag nhỏ nhưng search visibility trễ đến refresh; cluster segment/merge activity tăng.

**Hypothesis** → freshness configuration đang đánh đổi quá nhiều indexing efficiency.

**Diagnosis** → đo end-to-end lag: DB commit → event → bulk success → searchable; xem refresh/merge/indexing metrics.

**Fix** → restore sensible refresh interval, batch writes, dùng `wait_for` có chọn lọc hoặc thiết kế UI chấp nhận eventual consistency.

**Verification** → load test ingest + search đồng thời, đo indexing throughput, p95 search latency và freshness lag.

## 7. Common mistakes

- `refresh=true` sau mọi document.
- Nghĩ bulk response success nghĩa search phải thấy ngay.
- Không inspect item-level errors trong bulk response.
- Dùng Elasticsearch làm transactional source of truth.
- Không có metric indexing lag.
- Reindex/import khối lượng lớn với refresh policy giống interactive workload.

## 8. Alternatives

- SQL/PostgreSQL full-text search cho workload đơn giản và strong consistency gần source data.
- Dedicated read model khác nếu search features không cần inverted-index capabilities.
- Explicit source-of-truth lookup cho post-write confirmation.

## 9. Trade-offs

### Advantages

- Relaxed refresh giúp indexing throughput tốt hơn.
- Bulk API giảm request overhead và phù hợp projection pipelines.

### Costs / Risks

- Search có eventual-consistency window.
- Tuning freshness/throughput sai có thể tăng segment/merge cost.
- Pipeline thêm observability/replay requirements.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Elasticsearch search không nhất thiết read-after-write ngay lập tức.

### Middle

Biết Bulk API, refresh interval và item-level error handling.

### Senior

Đo indexing lag, segment/merge behavior và chọn freshness theo use case.

### Technical Lead / Architect

Định nghĩa source of truth, user-facing consistency expectation và nơi nào đáng trả cost cho stronger search freshness.

## 11. Key takeaway

- Elasticsearch là near-real-time; successful write và searchable visibility là hai thời điểm khác nhau.
- Force refresh trên mọi write thường đổi correctness cảm nhận lấy throughput rất đắt.
- Đo end-to-end indexing lag và thiết kế UX/API theo consistency thực tế.

# 9. .NET memory growth investigation: phân biệt high allocation, GC pressure và true memory leak bằng evidence

## 1. What is it?

Memory tăng không đồng nghĩa memory leak.

Ba mental models cần tách:

```text
High allocation rate
 -> rất nhiều object được tạo
 -> GC thu hồi được

High live set
 -> nhiều object hợp lệ vẫn đang được giữ

Leak / unintended retention
 -> object đáng lẽ chết nhưng còn reference path giữ sống
```

Process working set còn khác managed heap vì có native memory, JIT, stacks, mapped files và runtime overhead.

## 2. Why does it exist?

Nếu thấy container memory từ 500 MB lên 1.5 GB rồi lập tức tăng pod limit, team có thể chỉ trì hoãn OOM.

Nếu memory tăng do burst + GC behavior hợp lệ, “fix leak” bằng random disposal lại tốn thời gian.

Production debugging cần evidence về allocation rate, GC collections, heap size, live object types và reference roots.

## 3. How does it work?

Investigation loop:

```text
Symptom: memory grows
  |
runtime counters
  |
managed heap or native?
  |
gcdump/dump/profile
  |
top object types + roots
  |
code ownership/lifetime
  |
fix
  |
repeat load and compare
```

Tools có thể gồm:

```bash
dotnet-counters monitor --process-id <pid> System.Runtime
dotnet-gcdump collect --process-id <pid>
dotnet-dump collect --process-id <pid>
```

Environment/container permissions có thể ảnh hưởng khả năng capture diagnostics.

## 4. Practical implementation

Theo dõi ít nhất:

- GC heap size;
- allocation rate;
- Gen 0/1/2 counts;
- LOH size;
- working set;
- request/concurrency level.

Nếu heap snapshot cho thấy hàng triệu entries trong singleton dictionary/cache, tìm ownership và eviction policy.

Nếu managed heap ổn nhưng working set tiếp tục tăng, investigate native allocations, unmanaged libraries, sockets, image processing hoặc fragmentation.

## 5. Real production scenario

Một multi-tenant API cache metadata trong `ConcurrentDictionary<string, TenantConfig>` không có eviction. Mỗi tenant mới để lại object graph sống vĩnh viễn.

Allocation rate không quá cao nhưng Gen 2/live heap tăng theo thời gian. Dump comparison cho thấy dictionary dominator giữ phần lớn retained bytes.

Fix là bounded cache/eviction + ownership policy, không phải gọi `GC.Collect()`.

## 6. Failure scenario & troubleshooting

**Symptom** → memory tăng vài trăm MB mỗi ngày và chỉ reset khi restart.

**Evidence** → managed heap snapshots qua thời gian cho thấy cùng object type tăng monotonically và được root bởi singleton/static collection.

**Hypothesis** → unintended retention.

**Diagnosis** → inspect dominators/reference paths, map root về code/lifetime.

**Fix** → bounded cache, unsubscribe event, dispose resource hoặc sửa reference ownership tùy root cause.

**Verification** → replay representative workload lâu đủ, compare live heap after steady-state GC, không chỉ nhìn immediate working set.

## 7. Common mistakes

- Gọi `GC.Collect()` để chữa leak.
- Chỉ nhìn Task Manager/container RSS.
- Chụp một dump duy nhất rồi kết luận.
- Nghĩ `IDisposable` giải quyết mọi managed retention.
- Dùng unbounded dictionary/cache trong Singleton.
- Event subscription giữ subscriber sống ngoài ý muốn.
- Tăng memory limit trước khi hiểu growth curve.

## 8. Alternatives

- Allocation profiler khi vấn đề là churn/GC pressure.
- Heap dump/gcdump khi vấn đề là retention.
- Native memory tools khi managed heap không giải thích working set.
- Load test soak testing để tái tạo gradual growth.

## 9. Trade-offs

### Advantages

- Evidence-driven diagnostics tránh random fixes.
- Heap/root analysis chỉ ra ownership bug cụ thể.

### Costs / Risks

- Dumps có thể lớn và chứa sensitive data.
- Capture diagnostics có overhead/operational permissions.
- Production traffic patterns khó tái tạo hoàn toàn.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Phân biệt allocation với object còn sống.

### Middle

Biết đọc runtime counters và nhận ra unbounded caches/static state.

### Senior

Phân tích heap snapshots, roots, managed-vs-native memory và reproduce bằng soak load.

### Technical Lead / Architect

Thiết kế observability, diagnostics access, cache bounds và memory budgets trước incident; cân nhắc dữ liệu nhạy cảm trong dumps.

## 11. Key takeaway

- Memory tăng cần phân loại: allocation churn, live set, managed leak hay native growth.
- So sánh evidence theo thời gian và reference roots, không đoán từ RSS.
- `GC.Collect()` không sửa ownership/lifetime bug.

# 10. Git `bisect`: tìm commit gây production regression bằng binary search thay vì đọc hàng trăm commits thủ công

## 1. What is it?

`git bisect` dùng binary search trên commit history để tìm commit đầu tiên gây lỗi, miễn là ta có thể phân loại một commit là `good` hoặc `bad`.

```text
known good ---------------- known bad
             |
          midpoint
        good/bad?
             |
       bỏ nửa history
```

Với 1024 commits, lý thuyết chỉ cần khoảng 10 lần phân loại thay vì xem tuần tự 1024 commits.

## 2. Why does it exist?

Production regression thường được phát hiện sau nhiều commits đã merge. Đọc diff hàng tuần bằng mắt dễ bias và chậm.

Nếu bug có deterministic reproduction/test, commit history trở thành searchable state space.

## 3. How does it work?

Bắt đầu:

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
```

Git checkout midpoint. Chạy test/reproduction rồi đánh dấu:

```bash
git bisect good
```

hoặc:

```bash
git bisect bad
```

Lặp đến khi Git xác định first bad commit.

Kết thúc:

```bash
git bisect reset
```

## 4. Practical implementation

Tốt nhất automate:

```bash
git bisect start HEAD v2.4.0
git bisect run dotnet test tests/Regression.Tests \
  --filter FullyQualifiedName~CheckoutLatencyRegression
```

Exit code 0 nghĩa good; non-zero nghĩa bad theo script/test được thiết kế.

Nếu một commit không build vì unrelated reason:

```bash
git bisect skip
```

nhưng quá nhiều skipped commits làm kết quả kém xác định.

## 5. Real production scenario

Sau release, API xuất hiện bug timezone chỉ với DST edge case. Release chứa ~300 commits. Team viết regression test tái hiện input cụ thể rồi dùng `git bisect run`.

Sau vài iterations, commit đầu tiên đổi parsing từ `DateTimeOffset` sang `DateTime` được xác định. Root cause được tìm dựa trên executable evidence thay vì đoán owner/feature.

## 6. Failure scenario & troubleshooting

**Symptom** → bisect chỉ ra commit “không liên quan” hoặc kết quả thay đổi giữa các lần chạy.

**Evidence** → reproduction test flaky, phụ thuộc clock/network/database state.

**Hypothesis** → predicate `good/bad` không deterministic.

**Diagnosis** → chạy test nhiều lần trên cùng commit; cô lập external dependencies/time/randomness.

**Fix** → tạo deterministic regression harness trước khi tiếp tục bisect.

**Verification** → first bad commit fail ổn định, parent commit pass ổn định; inspect diff để xác nhận causal mechanism.

## 7. Common mistakes

- Bisect với flaky E2E test.
- Chọn `good` commit thực ra chưa được verify.
- Tin first bad commit là root cause cuối cùng mà không đọc diff.
- Bisect trên history bị environment/schema incompatibility mà không script setup.
- Dùng nó khi bug phụ thuộc production data nhưng không có reproduction predicate.
- Quên `git bisect reset`.

## 8. Alternatives

- `git log`/PR history khi range rất nhỏ.
- Feature flags/telemetry để correlate regression với rollout.
- `git blame` khi đã biết chính xác line gây behavior.
- Profiling/tracing khi symptom không map được thành deterministic pass/fail.

## 9. Trade-offs

### Advantages

- Giảm search space theo logarithmic fashion.
- Rất mạnh khi có automated regression test.
- Ít phụ thuộc phỏng đoán con người.

### Costs / Risks

- Cần build/test được historical commits.
- Flaky predicate làm kết quả vô nghĩa.
- Schema/external service evolution có thể khiến old commits khó chạy.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết dùng history/diff thay vì sửa trực tiếp mà không tìm root cause.

### Middle

Dùng `git bisect` thủ công với known-good/known-bad commits.

### Senior

Tạo deterministic regression test và automate bằng `git bisect run`.

### Technical Lead / Architect

Khuyến khích release tagging, reproducible builds/tests và observability để incident investigation có thể thu hẹp regression nhanh, thay vì phụ thuộc tribal knowledge.

## 11. Key takeaway

- `git bisect` biến regression hunting thành binary search khi có good/bad predicate đáng tin.
- Chất lượng reproduction test quyết định chất lượng kết quả.
- First bad commit là điểm bắt đầu root-cause analysis, không phải bằng chứng tự động rằng tác giả commit “gây lỗi”.
