# 1. `IAsyncEnumerable<T>`: streaming dữ liệu với cancellation và backpressure

## 1. What is it?

`IAsyncEnumerable<T>` biểu diễn một chuỗi phần tử được tạo bất đồng bộ theo thời gian. Mental model quan trọng là **pull-based asynchronous stream**: consumer yêu cầu phần tử tiếp theo bằng `MoveNextAsync()`, thay vì producer phải materialize toàn bộ collection trước khi trả về.

Nó hữu ích khi dữ liệu lớn, đến theo từng batch, hoặc cần trả kết quả sớm. Tuy nhiên streaming không tự động tạo backpressure hoàn hảo cho mọi tầng; database provider, serializer, proxy và client đều có buffering riêng.

## 2. Why does it exist?

Nếu query 500.000 records rồi `ToListAsync()`, ứng dụng phải chờ toàn bộ query hoàn tất và giữ toàn bộ object graph trong memory. Với streaming, time-to-first-byte và peak memory có thể giảm đáng kể.

Nhưng nếu downstream chậm, connection database có thể bị giữ lâu. Vì vậy lợi ích memory phải được cân bằng với connection occupancy và cancellation.

## 3. How does it work?

Compiler biến `async iterator` thành state machine. Mỗi lần consumer yêu cầu phần tử kế tiếp, producer tiếp tục thực thi đến `yield return` tiếp theo.

```text
Consumer -> MoveNextAsync -> Producer -> await I/O -> yield item
Consumer <- item
```

Cancellation phải được truyền tới iterator và xuống I/O thực tế; nếu không, client disconnect nhưng database query vẫn chạy.

## 4. Practical implementation

```csharp
public async IAsyncEnumerable<OrderDto> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken cancellationToken)
{
    await foreach (var order in _db.Orders
        .AsNoTracking()
        .OrderBy(x => x.Id)
        .Select(x => new OrderDto(x.Id, x.Total))
        .AsAsyncEnumerable()
        .WithCancellation(cancellationToken))
    {
        yield return order;
    }
}
```

Trong ASP.NET Core, hãy liên kết với `HttpContext.RequestAborted` hoặc token của endpoint.

## 5. Real production scenario

Một export API cần stream hàng trăm nghìn order sang NDJSON. Streaming cho phép client bắt đầu nhận dữ liệu sớm và tránh một `List<OrderDto>` khổng lồ. Tuy nhiên transaction/connection database sống trong suốt quá trình enumeration, nên client chậm có thể giữ resource lâu hơn dự kiến.

## 6. Failure scenario & troubleshooting

**Symptom:** memory thấp hơn nhưng connection pool bắt đầu cạn. **Evidence:** số active DB connections tăng, request duration dài, client throughput thấp. **Hypothesis:** streaming giữ reader/connection trong toàn bộ response. **Diagnosis:** trace thời gian query enumeration và response write. **Fix:** phân trang/batching, giới hạn export concurrency, propagate cancellation. **Verification:** đo lại pool utilization, p95 duration và memory.

## 7. Common mistakes

Gọi `ToListAsync()` trước khi `yield` làm mất streaming; bỏ `CancellationToken`; dùng lazy loading trong iterator tạo N+1; giả định mọi proxy đều flush từng item; stream trong transaction dài.

## 8. Alternatives

Pagination phù hợp UI và retry từng page. Background export + Blob Storage phù hợp file rất lớn. `Channel<T>` phù hợp producer/consumer trong process và có bounded capacity rõ ràng hơn.

## 9. Trade-offs

### Advantages

Giảm peak memory, trả dữ liệu sớm, composable với async I/O.

### Costs / Risks

Giữ dependency lâu hơn, cancellation phức tạp hơn, partial response khó retry, buffering ngoài application có thể triệt tiêu lợi ích.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu khác biệt giữa materialization và asynchronous enumeration.

### Middle

Implement iterator, cancellation và projection đúng.

### Senior

Đo memory, connection lifetime, client speed và failure giữa stream.

### Technical Lead / Architect

Quyết định khi nào streaming hợp lý hơn pagination hoặc asynchronous export dựa trên resource ownership và retry semantics.

## 11. Key takeaway

- Streaming giảm memory nhưng có thể kéo dài lifetime của connection.
- Cancellation phải đi tới I/O thực tế.
- Với export lớn, background job + object storage thường đơn giản hơn HTTP stream dài.

# 2. ASP.NET Core Request Timeouts: deadline phải đi xuyên suốt dependency chain

## 1. What is it?

Request timeout là giới hạn thời gian một HTTP operation được phép chiếm tài nguyên. Timeout ở edge chỉ có giá trị nếu deadline/cancellation được truyền xuống database, HTTP dependency và background operation liên quan.

## 2. Why does it exist?

Không có timeout, một dependency treo có thể giữ request, socket, memory và concurrency slot vô thời hạn. Khi tải tăng, các request treo tích lũy thành cascading failure.

## 3. How does it work?

ASP.NET Core có Request Timeout middleware/policies. Khi deadline hết, cancellation token được signal. Application code phải propagate token; timeout không thể cưỡng chế an toàn một arbitrary synchronous operation đang block.

```text
Client deadline
  -> API timeout
    -> HttpClient timeout/cancellation
    -> DB command cancellation
```

Budget downstream phải nhỏ hơn budget upstream để còn thời gian xử lý lỗi.

## 4. Practical implementation

```csharp
builder.Services.AddRequestTimeouts(options =>
{
    options.AddPolicy("interactive", TimeSpan.FromSeconds(8));
});

app.UseRequestTimeouts();

app.MapGet("/orders/{id:int}", async (
    int id, AppDbContext db, CancellationToken ct) =>
{
    return await db.Orders.AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, ct);
}).WithRequestTimeout("interactive");
```

Mọi `HttpClient.SendAsync`, EF Core query và delay phải nhận `ct`.

## 5. Real production scenario

Checkout API có SLO 2 giây nhưng payment dependency timeout 30 giây. Khi payment chậm, checkout request giữ resource quá lâu và retry từ client làm tải tăng. Thiết kế lại budget: edge 2s, application 1.8s, payment 1.2s, database 500ms tùy critical path.

## 6. Failure scenario & troubleshooting

**Symptom:** reverse proxy trả 504 nhưng backend vẫn chạy thêm 20 giây. **Evidence:** trace span backend kết thúc sau edge span; DB query vẫn active. **Hypothesis:** cancellation không propagate. **Diagnosis:** review call chain và token usage. **Fix:** truyền token, đặt dependency timeout phù hợp, loại sync blocking. **Verification:** sau client abort/deadline, dependency spans kết thúc nhanh.

## 7. Common mistakes

Chỉ đặt `HttpClient.Timeout`; dùng cùng timeout 30s cho mọi dependency; retry operation đã timeout mà không có remaining budget; catch `OperationCanceledException` rồi tiếp tục; không phân biệt timeout với caller cancellation.

## 8. Alternatives

Queue + asynchronous processing phù hợp operation dài. Circuit Breaker giảm gọi dependency đang lỗi nhưng không thay timeout. Bulkhead giới hạn blast radius nhưng cũng không thay deadline.

## 9. Trade-offs

### Advantages

Giới hạn resource occupancy, giảm cascading failure, làm latency contract rõ ràng.

### Costs / Risks

Timeout quá ngắn gây false failure; operation không idempotent có thể hoàn tất ở server dù caller đã bỏ cuộc.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu timeout không phải retry và cancellation là cooperative.

### Middle

Propagate token xuyên endpoint, EF Core và HTTP calls.

### Senior

Thiết kế timeout budget theo critical path và phân tích trace.

### Technical Lead / Architect

Đặt latency contract giữa services, retry policy và asynchronous boundary phù hợp SLO.

## 11. Key takeaway

- Timeout phải là end-to-end budget, không phải các con số độc lập.
- Cancellation chỉ hiệu quả khi downstream code tôn trọng token.
- Retry phải tiêu thụ remaining budget, không reset thời gian vô hạn.

# 3. EF Core `DbContext` pooling: giảm allocation nhưng tránh state leakage

## 1. What is it?

`AddDbContextPool` tái sử dụng instance `DbContext` sau khi EF reset internal state. Đây là object pooling, khác với database connection pooling do provider quản lý.

## 2. Why does it exist?

Tạo `DbContext` thường rẻ, nhưng ở throughput cao, pooling có thể giảm allocation và initialization overhead. Nó chỉ đáng dùng sau measurement; không phải default optimization bắt buộc.

## 3. How does it work?

Scope lấy context từ pool, sử dụng, rồi trả context về pool. Vì cùng instance có thể phục vụ request khác, state tùy request không được cấu hình một lần trong constructor rồi giả định thay đổi theo scope.

## 4. Practical implementation

```csharp
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Với multi-tenant, tránh lưu mutable `TenantId` tùy request như một field không được reset có chủ đích. Một factory/scoped abstraction nên gán state an toàn hoặc tốt hơn truyền tenant vào query boundary rõ ràng.

## 5. Real production scenario

SaaS API có hàng nghìn RPS và context creation xuất hiện đáng kể trong allocation profile. Pooling giảm allocation, nhưng một global query filter dùng tenant state sai khiến request tenant B có nguy cơ dùng state tenant A nếu thiết kế reset không đúng.

## 6. Failure scenario & troubleshooting

**Symptom:** dữ liệu tenant thỉnh thoảng sai và không tái hiện khi chạy đơn luồng. **Evidence:** context instance hash được reuse giữa requests; tenant state không đổi đúng. **Hypothesis:** pooled context chứa request-specific mutable state. **Diagnosis:** kiểm tra constructor, interceptors, query filters. **Fix:** loại state khỏi pooled context hoặc dùng scoped factory an toàn. **Verification:** concurrency integration test nhiều tenants và audit query parameters.

## 7. Common mistakes

Nhầm `DbContext` pool với connection pool; pool trước khi benchmark; giữ context ngoài scope; lưu user/tenant state trong context; mở connection thủ công rồi không reset trước khi trả pool.

## 8. Alternatives

`AddDbContext` thông thường đơn giản và đủ cho phần lớn API. `IDbContextFactory<T>` hữu ích khi cần tạo context theo operation. Tối ưu query thường đem lại lợi ích lớn hơn pooling context.

## 9. Trade-offs

### Advantages

Giảm allocation/initialization ở workload phù hợp.

### Costs / Risks

Lifetime semantics khó hơn, state leakage nguy hiểm, lợi ích nhỏ nếu bottleneck nằm ở database.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `DbContext` là Unit of Work ngắn hạn và không thread-safe.

### Middle

Phân biệt context pooling với connection pooling.

### Senior

Benchmark trước/sau và kiểm soát mutable state.

### Technical Lead / Architect

Chỉ đưa pooling vào khi profile chứng minh lợi ích và tenancy/security model chịu được complexity.

## 11. Key takeaway

- `DbContext` pooling là optimization, không phải correctness pattern.
- Pooled object không được mang state request trước sang request sau.
- Tối ưu database access pattern thường quan trọng hơn giảm chi phí tạo context.

# 4. SQL SARGability: vì sao một predicate nhỏ có thể biến Index Seek thành Scan

## 1. What is it?

SARGable predicate là điều kiện cho phép optimizer dùng index để xác định range/key cần đọc thay vì phải tính biểu thức trên nhiều rows trước khi lọc.

## 2. Why does it exist?

Một index tốt vẫn vô dụng nếu predicate che cột index bên trong function hoặc implicit conversion. Khi table tăng từ 100 nghìn lên 100 triệu rows, cùng query có thể chuyển từ milliseconds sang seconds.

## 3. How does it work?

Index B-tree được sắp theo key. Predicate `CreatedAt >= @from AND CreatedAt < @to` cho phép seek tới range. `CAST(CreatedAt AS date) = @date` có thể buộc engine xử lý biểu thức theo row hoặc tạo plan kém tối ưu tùy engine/version.

```text
predicate -> optimizer -> access path -> pages read -> locks/CPU -> latency
```

## 4. Practical implementation

Kém:

```sql
SELECT Id, Total
FROM Orders
WHERE CONVERT(date, CreatedAt) = @date;
```

Tốt hơn:

```sql
SELECT Id, Total
FROM Orders
WHERE CreatedAt >= @date
  AND CreatedAt < DATEADD(day, 1, @date);
```

Sau đó kiểm tra actual execution plan và `SET STATISTICS IO, TIME ON` thay vì chỉ tin syntax.

## 5. Real production scenario

Dashboard daily orders chạy tốt lúc dữ liệu nhỏ. Sau hai năm, logical reads tăng hàng trăm lần, CPU SQL spike mỗi sáng và các transaction khác bị chậm do I/O pressure.

## 6. Failure scenario & troubleshooting

**Symptom:** p95 query tăng mạnh nhưng index vẫn tồn tại. **Evidence:** actual plan có Scan, logical reads cao. **Hypothesis:** non-SARGable predicate hoặc implicit conversion. **Diagnosis:** xem predicate properties, data types, plan và statistics. **Fix:** rewrite range predicate, đồng nhất types; chỉ thêm computed/indexed column nếu access pattern thực sự cần. **Verification:** compare reads, CPU, elapsed time và plan.

## 7. Common mistakes

Bọc indexed column bằng function; so `nvarchar` với incompatible type; dùng leading wildcard `LIKE '%abc'`; thêm index mới trước khi đọc plan; benchmark trên dataset nhỏ.

## 8. Alternatives

Computed persisted column + index cho expression dùng thường xuyên; full-text search cho search semantics; pre-aggregation cho analytics. Không phải predicate nào cũng cần seek nếu query thực sự đọc phần lớn table.

## 9. Trade-offs

### Advantages

SARGable query thường giảm I/O và CPU mà không cần thêm index.

### Costs / Risks

Rewrite có thể phức tạp với timezone/collation; thêm computed index làm tăng write/storage cost.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Biết index không đảm bảo query sẽ dùng seek.

### Middle

Đọc actual plan và logical reads.

### Senior

Liên hệ predicate, statistics, selectivity, locks và workload.

### Technical Lead / Architect

Thiết kế query/index theo access pattern và cân bằng read performance với write amplification.

## 11. Key takeaway

- Tối ưu SQL bắt đầu từ evidence: plan + I/O + timing.
- Function/implicit conversion trên indexed column có thể phá access path.
- Index mới không sửa được mọi bad predicate.

# 5. Redis hot key: khi distributed cache tự trở thành bottleneck tập trung

## 1. What is it?

Hot key là một cache key nhận tỷ lệ request quá lớn so với phần còn lại. Dù Redis nhanh, một key/slot/node quá nóng có thể trở thành bottleneck về CPU, network hoặc single-threaded command processing.

## 2. Why does it exist?

Traffic thực tế thường skewed: homepage config, top product hoặc global feature state có thể chiếm phần lớn reads. Distributed cache không tự động phân tán một key duy nhất thành nhiều compute paths.

## 3. How does it work?

Trong Redis Cluster, key hash vào slot và slot thuộc một node. Nhiều clients đọc cùng key vẫn hội tụ về node đó. Replicas có thể hỗ trợ một số read architecture nhưng đổi consistency/complexity.

## 4. Practical implementation

Một giải pháp đơn giản cho immutable/short-lived configuration là two-level cache:

```csharp
var value = _memoryCache.Get<Config>(key);
if (value is not null) return value;

value = await _redis.GetAsync<Config>(key, ct);
_memoryCache.Set(key, value, TimeSpan.FromSeconds(10));
return value;
```

Local cache vài giây có thể giảm hàng nghìn remote reads nhưng phải chấp nhận bounded staleness.

## 5. Real production scenario

Product-detail traffic tăng đột biến cho một flash-sale SKU. Redis node CPU 95% trong khi các nodes khác thấp. API latency tăng dù database không tải cao.

## 6. Failure scenario & troubleshooting

**Symptom:** Redis latency tăng nhưng aggregate hit rate vẫn 99%. **Evidence:** command/key sampling cho thấy một key áp đảo, node/slot imbalance. **Hypothesis:** hot key. **Diagnosis:** correlate key access, node CPU/network và client latency. **Fix:** local cache, request coalescing, partition data nếu semantics cho phép. **Verification:** node utilization cân bằng hơn và p99 giảm.

## 7. Common mistakes

Chỉ theo dõi hit ratio; shard key bằng random suffix nhưng làm invalidation phức tạp; cache object quá lớn; coi Redis là dependency luôn available; không giới hạn stale window.

## 8. Alternatives

`IMemoryCache` cho data nhỏ và chấp nhận per-instance inconsistency. CDN/edge cache cho public HTTP data. Database read replica có thể phù hợp dữ liệu cần query hơn key-value cache.

## 9. Trade-offs

### Advantages

Local caching/coalescing giảm network và Redis pressure.

### Costs / Risks

Tăng stale data, invalidation complexity và memory trên mỗi instance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu distributed cache vẫn có physical nodes và finite throughput.

### Middle

Đo key access, TTL và cache hit/miss.

### Senior

Phân tích skew, slot/node utilization và fallback behavior.

### Technical Lead / Architect

Quyết định data nào nên ở Redis, local cache hay CDN dựa trên consistency và failure model.

## 11. Key takeaway

- Hit rate cao không đồng nghĩa cache khỏe.
- Một key có thể tập trung tải vào một node.
- Cache topology phải phản ánh traffic distribution và staleness tolerance.

# 6. Event schema evolution: thay đổi Integration Event mà không phá consumer cũ

## 1. What is it?

Event schema evolution là chiến lược thay đổi contract của Integration Event khi producer và consumers không deploy đồng thời. Event là public contract giữa bounded contexts, không phải DTO nội bộ có thể sửa tùy ý.

## 2. Why does it exist?

Trong distributed system, message cũ có thể còn trong queue, consumer cũ có thể vẫn chạy và replay có thể đọc event từ nhiều tháng trước. Breaking change trực tiếp tạo temporal coupling giữa deployments.

## 3. How does it work?

Producer sở hữu event contract nhưng phải duy trì compatibility window. Additive optional fields thường dễ hơn rename/remove/change meaning. Breaking semantic change nên tạo event version mới hoặc event type mới.

```text
Order BC -- OrderPlacedV1 --> Billing
         -- OrderPlacedV2 --> New consumer
```

Data ownership vẫn ở source bounded context; event chỉ truyền facts cần thiết. Transaction boundary thường là local DB + Outbox; consumer có transaction riêng và phải idempotent.

## 4. Practical implementation

```csharp
public sealed record OrderPlacedV2(
    Guid EventId,
    Guid OrderId,
    decimal Total,
    string Currency,
    DateTimeOffset OccurredAt,
    string? SalesChannel);
```

Không đổi `Total` từ gross sang net mà giữ cùng field name/version; đó là semantic breaking change khó phát hiện hơn compile error.

## 5. Real production scenario

Checkout phát `OrderPlaced`; Billing, CRM và Analytics consume độc lập. Team checkout cần thêm multi-currency. Nếu đổi `decimal Total` thành object mới ngay, consumer cũ deserialize thất bại và queue backlog tăng.

## 6. Failure scenario & troubleshooting

**Symptom:** sau producer deployment, một subscription dead-letter tăng. **Evidence:** deserialization errors ở consumer cũ. **Hypothesis:** incompatible schema. **Diagnosis:** so payload mới với contract consumer và messages trong DLQ. **Fix:** restore backward-compatible producer hoặc publish V2 song song; replay sau khi consumer hỗ trợ. **Verification:** DLQ dừng tăng và old/new payload đều được contract test.

## 7. Common mistakes

Dùng domain entity làm event; rename field tùy ý; xóa field ngay khi producer không dùng; không lưu event version; cho consumer phụ thuộc database producer; thay đổi meaning nhưng không version.

## 8. Alternatives

Synchronous REST dễ contract negotiation hơn nhưng tăng runtime coupling. Shared database đơn giản ban đầu nhưng phá ownership. Schema Registry hữu ích ở ecosystem lớn nhưng thêm operational component.

## 9. Trade-offs

### Advantages

Versioning giảm deployment coupling và hỗ trợ replay/migration.

### Costs / Risks

Phải duy trì nhiều versions, mapping code và compatibility tests.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Integration Event là contract giữa systems.

### Middle

Implement additive changes và tolerant deserialization.

### Senior

Thiết kế versioning, replay, idempotency và migration window.

### Technical Lead / Architect

Quyết định ownership, transaction boundary, compatibility policy, deprecation và khi messaging đơn giản hơn hay phức tạp hơn REST.

## 11. Key takeaway

- Event contract tồn tại lâu hơn một deployment.
- Semantic breaking change cũng nguy hiểm như schema breaking change.
- Versioning phải đi cùng replay, idempotency và contract testing.

# 7. Azure Functions cold start: hiểu latency, scale-out và lựa chọn hosting

## 1. What is it?

Cold start là latency phát sinh khi Azure Functions cần khởi tạo worker/host mới trước khi xử lý invocation. Nó phụ thuộc hosting plan, runtime, package/startup work và scale behavior.

## 2. Why does it exist?

Serverless tối ưu resource bằng cách scale theo demand; compute không phải lúc nào cũng warm. Đổi lại cost efficiency và elastic scale là startup latency trong một số plan/scenario.

## 3. How does it work?

Event đến -> platform quyết định scale -> instance khởi động -> runtime load -> DI/config initialization -> function chạy. Khi burst tạo nhiều instances, startup cost xuất hiện trên critical path của một phần requests.

## 4. Practical implementation

Giữ startup nhẹ, tránh network call trong service registration và reuse clients đúng lifetime:

```csharp
builder.Services.AddHttpClient<InventoryClient>();
builder.Services.AddSingleton<JsonSerializerOptions>(_ => new(JsonSerializerDefaults.Web));
```

Không tải toàn bộ reference dataset từ database trong startup nếu có thể lazy-load/cache có kiểm soát.

## 5. Real production scenario

Webhook HTTP Function ít traffic ban đêm nhưng yêu cầu phản hồi dưới 1 giây. Invocation đầu sau idle vượt SLO. Team phải đánh giá plan có warm instances/minimum instances phù hợp hay chuyển endpoint latency-sensitive sang App Service/Container Apps.

## 6. Failure scenario & troubleshooting

**Symptom:** p50 tốt nhưng p99 có spike sau idle/scale-out. **Evidence:** instance start telemetry trùng latency spike; dependency chưa được gọi. **Hypothesis:** cold start/startup initialization. **Diagnosis:** tách host startup time khỏi function execution. **Fix:** giảm startup work, chọn hosting option phù hợp, pre-warm/minimum instances khi available. **Verification:** đo distribution sau idle và burst, không chỉ steady-state benchmark.

## 7. Common mistakes

Gọi mọi latency spike là cold start; làm synchronous I/O trong startup; chọn Functions chỉ vì "serverless rẻ"; bỏ qua VNet/network initialization; benchmark chỉ trên warm instance.

## 8. Alternatives

App Service phù hợp HTTP API luôn-on. Worker Service/Container Apps phù hợp long-running consumer. Logic Apps phù hợp orchestration low-code. Lựa chọn dựa trên execution model, latency SLO và operational cost.

## 9. Trade-offs

### Advantages

Elastic scale, event integration, giảm quản lý server và có thể cost-efficient cho bursty workload.

### Costs / Risks

Cold-start variance, platform constraints, plan/network complexity và cost có thể tăng ở sustained load.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu function instance không nhất thiết luôn chạy.

### Middle

Giảm startup work và instrument execution.

### Senior

Phân biệt cold start với dependency latency và scale bottleneck.

### Technical Lead / Architect

Chọn Functions, App Service hay Container Apps dựa trên SLO, scale profile, identity/networking, monitoring và total cost.

## 11. Key takeaway

- Cold start là property của execution/hosting model, không phải một exception.
- Đo p95/p99 sau idle và scale-out.
- Latency-sensitive endpoint có thể cần always-warm compute dù serverless hấp dẫn về simplicity.

# 8. Canary deployment: giảm blast radius nhưng tăng yêu cầu observability

## 1. What is it?

Canary deployment đưa version mới tới một tỷ lệ traffic nhỏ trước, quan sát health rồi tăng dần. Mục tiêu là giới hạn blast radius của regression mà test trước production không bắt được.

## 2. Why does it exist?

Một deployment có thể build/test thành công nhưng lỗi chỉ xuất hiện với production traffic, data shape hoặc dependency behavior. Deploy 100% ngay biến lỗi nhỏ thành incident toàn hệ thống.

## 3. How does it work?

```text
commit -> build -> test -> immutable artifact
                         -> deploy canary 5%
                         -> health validation
                         -> monitor
                         -> 25% -> 50% -> 100%
                         -> rollback/roll-forward khi xấu
```

Database schema phải backward-compatible trong thời gian old/new versions cùng chạy. Đây là deployment implication quan trọng.

## 4. Practical implementation

Pipeline nên dùng cùng artifact cho mọi stage. Promotion gate dựa trên error rate, latency và business metric thay vì chỉ "pod is Ready".

Ví dụ policy: 5% traffic trong 15 phút; rollback nếu 5xx tăng >1 điểm %, p95 tăng >20%, hoặc payment success giảm vượt threshold đã định.

## 5. Real production scenario

Release checkout mới có bug chỉ với một payment method chiếm 8% traffic. Canary 5% làm business metric payment failure lệch sớm, giới hạn số user bị ảnh hưởng trước khi rollback.

## 6. Failure scenario & troubleshooting

**Symptom:** infrastructure metrics xanh nhưng conversion giảm. **Evidence:** canary cohort có business failure cao hơn control. **Hypothesis:** semantic regression không tạo 5xx. **Diagnosis:** compare version-tagged traces/logs/business metrics. **Fix:** rollback artifact hoặc disable feature flag. **Verification:** metrics trở lại baseline. Canary không hữu ích nếu telemetry không phân biệt version/cohort.

## 7. Common mistakes

Canary nhưng không có automated gates; migrate DB breaking trước; build artifact mới cho mỗi environment; không tag telemetry theo version; traffic sample quá nhỏ; rollback code nhưng schema không rollback được.

## 8. Alternatives

Blue-Green chuyển traffic nhanh giữa hai environments. Rolling deployment đơn giản hơn nhưng blast radius tăng dần theo replicas. Feature flags tách feature exposure khỏi deployment nhưng tạo lifecycle debt.

## 9. Trade-offs

### Advantages

Giảm blast radius, dùng production evidence, hỗ trợ progressive confidence.

### Costs / Risks

Routing, telemetry, schema compatibility và pipeline phức tạp hơn; cần đủ traffic để signal có ý nghĩa.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu deploy success không đồng nghĩa release health.

### Middle

Biết pipeline commit→test→artifact→deploy→health→monitor→rollback.

### Senior

Thiết kế gates, version telemetry và DB compatibility.

### Technical Lead / Architect

Quyết định strategy theo risk, traffic, rollback capability và operational maturity; hệ thống nhỏ có thể chỉ cần rolling deployment tốt.

## 11. Key takeaway

- Canary là risk-control mechanism, không chỉ routing technique.
- Không có observability và rollback thì canary gần như mất giá trị.
- Database changes phải tương thích khi nhiều app versions cùng tồn tại.

# 9. `dotnet-counters` và allocation profiling: điều tra CPU/GC trước khi tối ưu

## 1. What is it?

`dotnet-counters` cung cấp runtime metrics trực tiếp từ process .NET như CPU, GC heap, allocation rate, exception rate và ThreadPool behavior. Nó là công cụ triage nhẹ trước khi thu dump/trace nặng hơn.

## 2. Why does it exist?

CPU 90% không nói root cause. Có thể business computation thật sự nặng, allocation quá lớn kéo GC, exception storm, ThreadPool contention hoặc serialization. Tối ưu code khi chưa localize bottleneck dễ sửa sai nơi.

## 3. How does it work?

Runtime phát metrics qua diagnostics infrastructure. Workflow đúng:

```text
symptom -> counters -> hypothesis -> trace/profile -> code change -> counters again
```

Logs giải thích event, metrics cho trend, traces cho request path; counters bổ sung runtime evidence.

## 4. Practical implementation

```bash
dotnet-counters monitor --process-id 1234 System.Runtime
```

Quan sát CPU, allocation rate, GC heap size, Gen 0/1/2 collections, ThreadPool queue. Nếu allocation cao, chuyển sang `dotnet-trace`, profiler hoặc allocation flame graph để tìm call sites thay vì đoán.

## 5. Real production scenario

Sau release, API p99 tăng và CPU từ 40% lên 85%. Counters cho thấy allocation rate tăng gấp 4 và Gen 2 GC thường xuyên hơn. Trace xác định JSON mapping mới tạo nhiều temporary strings.

## 6. Failure scenario & troubleshooting

**Symptom:** latency và CPU tăng. **Evidence:** allocation/sec tăng ngay sau deployment; GC pause/collections tăng; traces chỉ ra endpoint cụ thể. **Hypothesis:** allocation regression. **Diagnosis:** allocation profile tìm type/call stack. **Fix:** giảm intermediate materialization/string conversion. **Verification:** cùng load test, allocation/sec, CPU và p99 đều giảm. Không chấp nhận benchmark chỉ nhanh hơn trên laptop mà production metric không đổi.

## 7. Common mistakes

Nhìn heap size một lần rồi kết luận leak; tối ưu allocations không đáng kể; thu dump liên tục trên production; không so baseline trước release; không correlate với traffic; đặt alert trực tiếp trên noisy runtime counter mà không hiểu workload.

## 8. Alternatives

Application Insights/OpenTelemetry tốt cho request/dependency view. `dotnet-trace` sâu hơn về runtime events. `dotnet-dump` phù hợp memory snapshot/leak investigation. Full profiler hữu ích khi cần call-tree CPU/allocation chi tiết.

## 9. Trade-offs

### Advantages

Triage nhanh, overhead tương đối thấp, evidence runtime trực tiếp.

### Costs / Risks

Counters không chỉ ra chính xác dòng code; cần công cụ sâu hơn và baseline workload để diễn giải đúng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu CPU, memory, allocation và GC là metrics khác nhau.

### Middle

Dùng counters để hình thành hypothesis.

### Senior

Correlate runtime metrics với traces, deployment và load profile.

### Technical Lead / Architect

Thiết lập performance regression workflow, SLO và profiling practice thay vì optimization theo cảm giác.

## 11. Key takeaway

- Measure trước khi optimize.
- Allocation rate thường hữu ích hơn chỉ nhìn heap size.
- Fix chỉ được chứng minh khi cùng workload cho metrics tốt hơn sau thay đổi.

# 10. CORS trust model: browser policy không phải cơ chế authorization của API

## 1. What is it?

CORS là browser security mechanism kiểm soát JavaScript từ một origin có được đọc/gửi một số cross-origin requests hay không. Server phát CORS response headers; browser enforce policy. Non-browser clients không bị CORS bảo vệ.

## 2. Why does it exist?

Same-Origin Policy hạn chế website độc hại đọc dữ liệu từ origin khác bằng credential của user. CORS cung cấp cách server chủ động cho phép cross-origin access có kiểm soát.

## 3. How does it work?

Với request cần preflight:

```text
Browser -> OPTIONS + Origin + requested method/headers
API -> Access-Control-Allow-*
Browser -> actual request nếu policy cho phép
```

CORS không xác minh user có quyền xem order 123. Authentication/authorization vẫn phải chạy ở API.

## 4. Practical implementation

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("web", policy =>
        policy.WithOrigins("https://app.example.com")
              .WithMethods("GET", "POST")
              .WithHeaders("content-type", "authorization"));
});

app.UseCors("web");
app.UseAuthentication();
app.UseAuthorization();
```

Nếu dùng credentials/cookies, không dùng wildcard origin; xem xét CSRF/SameSite riêng.

## 5. Real production scenario

Vue SPA ở `app.example.com` gọi API `api.example.com`. Production lỗi CORS sau khi thêm custom header. Backend team "fix" bằng `AllowAnyOrigin`, vô tình mở browser access rộng hơn yêu cầu dù authorization vẫn tồn tại.

## 6. Failure scenario & troubleshooting

**Symptom:** browser báo CORS nhưng Postman gọi thành công. **Evidence:** DevTools cho thấy preflight OPTIONS bị 401 hoặc thiếu allow header. **Hypothesis:** middleware/order/policy không xử lý preflight đúng. **Diagnosis:** inspect Network tab và response headers. **Fix:** allow đúng origin/method/header, đặt middleware đúng pipeline; không tắt auth cho actual resource. **Verification:** allowed origin hoạt động, disallowed origin bị browser chặn, API authorization tests vẫn độc lập.

## 7. Common mistakes

Coi CORS là authorization; `AllowAnyOrigin` để chữa lỗi; kết hợp wildcard với credentials; quên preflight; debug chỉ bằng Postman; cho rằng CORS ngăn attacker gọi API server-to-server.

## 8. Alternatives

Same-origin deployment/BFF giảm cross-origin complexity. Reverse proxy có thể đưa frontend/API dưới cùng origin. Nhưng dù topology nào, authentication và authorization vẫn là control riêng.

## 9. Trade-offs

### Advantages

Cho phép browser integration cross-origin có kiểm soát và explicit trust list.

### Costs / Risks

Configuration dễ sai, preflight thêm request, không cung cấp protection cho non-browser clients và không thay authorization.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu origin gồm scheme + host + port và browser enforce CORS.

### Middle

Cấu hình policy tối thiểu, debug preflight bằng DevTools.

### Senior

Phân biệt CORS, CSRF, authentication và authorization; review credential behavior.

### Technical Lead / Architect

Quyết định frontend/API topology, trusted origins và security boundaries; tránh biến CORS thành security theater.

## 11. Key takeaway

- CORS là browser policy, không phải API authorization.
- Postman thành công trong khi browser thất bại là tín hiệu điển hình của CORS/preflight.
- Chỉ allow origins/methods/headers thực sự cần và xử lý credential/CSRF riêng.
