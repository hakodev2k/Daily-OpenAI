# 1. .NET `Channel<T>`: bounded queues, backpressure và producer/consumer ownership

## 1. What is it?

`Channel<T>` là asynchronous producer/consumer primitive trong .NET. Mental model tốt nhất không phải “một `ConcurrentQueue<T>` có `await`”, mà là **một boundary điều tiết tốc độ giữa nơi tạo work và nơi tiêu thụ work**.

Channel có writer và reader độc lập. Với bounded channel, capacity trở thành một phần của reliability design: khi consumer chậm hơn producer, hệ thống phải quyết định chờ, drop hay fail thay vì âm thầm ăn hết memory.

## 2. Why does it exist?

Một API có thể nhận work nhanh hơn background worker xử lý. Nếu mỗi request tạo fire-and-forget `Task`, hoặc enqueue vào collection không giới hạn, burst traffic biến thành hàng nghìn objects đang chờ trong RAM. Latency tăng, GC pressure tăng và process có thể chết trước khi dependency phía sau hồi phục.

`Channel<T>` cung cấp asynchronous coordination, completion semantics và bounded capacity mà không cần tự ghép queue + semaphore + locking.

## 3. How does it work?

```text
Producer(s)
    │
    ▼
┌──────────────────────┐
│ bounded Channel<T>   │ capacity = 1000
└──────────────────────┘
    │
    ▼
Consumer(s)

Consumer chậm
→ queue đầy
→ writer phải chờ / drop theo configured FullMode
→ pressure quay ngược về producer
```

Đây chính là backpressure: overload không biến mất; nó được biểu diễn ở một boundary có kiểm soát.

## 4. Practical implementation

```csharp
var channel = Channel.CreateBounded<WorkItem>(
    new BoundedChannelOptions(500)
    {
        FullMode = BoundedChannelFullMode.Wait,
        SingleReader = true,
        SingleWriter = false
    });

public async Task EnqueueAsync(WorkItem item, CancellationToken ct)
{
    await channel.Writer.WriteAsync(item, ct);
}

public async Task ConsumeAsync(CancellationToken ct)
{
    await foreach (var item in channel.Reader.ReadAllAsync(ct))
    {
        await ProcessAsync(item, ct);
    }
}
```

`Wait` phù hợp khi producer có thể bị throttle. `DropOldest`, `DropNewest` hoặc `DropWrite` chỉ đúng khi business semantics cho phép mất work.

## 5. Real production scenario

Một document API nhận request upload và cần chạy lightweight metadata extraction trong process. Bình thường consumer xử lý 100 items/s; một burst tạo 5.000 items trong vài giây. Bounded channel giới hạn pending work, khiến producer chậm lại thay vì để process giữ hàng chục nghìn buffers và tasks.

Nếu work phải sống qua process restart, in-memory channel không đủ; durable broker mới là boundary đúng.

## 6. Failure scenario & troubleshooting

**Symptom** → API p99 tăng mạnh, memory tăng nhưng CPU consumer không cao.  
**Evidence** → channel depth luôn sát capacity; processing duration tăng.  
**Hypothesis** → downstream consumer trở thành bottleneck.  
**Diagnosis** → đo enqueue wait time, queue depth, processing latency và dependency latency.  
**Fix** → xử lý bottleneck, điều chỉnh concurrency có giới hạn hoặc chuyển durable work sang broker.  
**Verification** → burst test cho thấy memory bounded và backlog hồi phục sau burst.

## 7. Common mistakes

Dùng unbounded channel cho workload không giới hạn; tăng consumer count mà bỏ qua database connection pool; dùng drop mode cho business-critical work; không gọi `Complete`; coi in-memory channel như durable queue; bỏ qua shutdown và cancellation.

## 8. Alternatives

`ConcurrentQueue<T>` phù hợp khi coordination đơn giản và caller tự quản signaling. `BlockingCollection<T>` phù hợp legacy synchronous producer/consumer. Azure Service Bus hoặc broker khác đúng hơn khi cần durability, retry, multi-instance consumption và recovery sau process restart.

## 9. Trade-offs

### Advantages

Low-overhead async coordination, backpressure rõ ràng, API producer/consumer sạch.

### Costs / Risks

State chỉ nằm trong process; capacity và drop policy trở thành business decision; tăng consumers có thể đẩy bottleneck sang dependency khác.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu producer, consumer và queue capacity.

### Middle

Implement bounded channel, cancellation và graceful completion.

### Senior

Đo queue depth, throughput, dependency saturation và chọn backpressure policy.

### Technical Lead / Architect

Quyết định work nào được phép tồn tại trong memory và work nào bắt buộc phải đi qua durable messaging boundary.

## 11. Key takeaway

- Bounded queue biến overload thành trạng thái có thể kiểm soát.
- Backpressure tốt hơn unbounded memory growth.
- `Channel<T>` không thay thế durable broker khi work không được phép mất.

# 2. ASP.NET Core `ProblemDetails`: error contract, exception mapping và API compatibility

## 1. What is it?

`ProblemDetails` là representation chuẩn hóa cho HTTP API errors dựa trên RFC problem details. Mental model: **error response cũng là public API contract**, không phải nơi dump exception text.

Một API ổn định cần phân biệt machine-readable error semantics với diagnostic details dành cho logs/traces.

## 2. Why does it exist?

Nếu mỗi endpoint trả một shape khác nhau — `{ message }`, `{ error }`, plain text, stack trace — client phải viết parsing logic theo từng endpoint. Khi backend refactor exception type, frontend cũng có thể vỡ nếu nó phụ thuộc vào implementation detail.

## 3. How does it work?

```text
Domain/Application failure
        │
        ▼
Exception / Result mapping
        │
        ▼
HTTP status + ProblemDetails
        │
        ├── stable type/code for client
        └── correlation/trace id for support
```

Không phải mọi exception đều là `500`. Validation, not-found, concurrency conflict và authorization failure có semantics khác nhau.

## 4. Practical implementation

```csharp
builder.Services.AddProblemDetails(options =>
{
    options.CustomizeProblemDetails = context =>
    {
        context.ProblemDetails.Extensions["traceId"] =
            context.HttpContext.TraceIdentifier;
    };
});

app.UseExceptionHandler();

app.MapGet("/orders/{id:guid}", async (
    Guid id,
    AppDbContext db,
    CancellationToken ct) =>
{
    var order = await db.Orders.FindAsync([id], ct);
    return order is null
        ? Results.Problem(
            statusCode: 404,
            title: "Order not found",
            type: "https://example.com/problems/order-not-found")
        : Results.Ok(order);
});
```

Production API nên có stable application error codes nếu clients cần branching logic; `title`/human text không nên là discriminator.

## 5. Real production scenario

Mobile client gọi approval API. Backend thay database implementation và exception text đổi. Nếu client chỉ dựa trên `status=409` + stable `code=approval_already_processed`, client vẫn hoạt động mà không biết exception nội bộ.

## 6. Failure scenario & troubleshooting

**Symptom** → frontend hiển thị generic error dù backend biết nguyên nhân.  
**Evidence** → tất cả domain failures bị map thành `500`.  
**Hypothesis** → exception-to-contract mapping quá thô.  
**Diagnosis** → inspect error taxonomy, middleware mapping và client branching.  
**Fix** → định nghĩa stable problem types/codes theo client-relevant semantics.  
**Verification** → contract/integration tests xác nhận status, type và code cho từng failure class.

## 7. Common mistakes

Trả stack trace ra production; dùng exception message làm API contract; map mọi lỗi thành 200 + `{ success:false }`; expose SQL/provider details; tạo hàng trăm error types không có client value.

## 8. Alternatives

Custom error envelope vẫn có thể hợp lý nếu organization đã có contract trưởng thành. Result pattern giúp application layer biểu diễn expected failures mà không dùng exceptions cho control flow; HTTP boundary vẫn cần mapping rõ.

## 9. Trade-offs

### Advantages

Client handling nhất quán, API evolvability tốt hơn và support dễ correlate bằng trace ID.

### Costs / Risks

Cần error taxonomy, governance và backward compatibility; over-modeling errors làm contract nặng nề.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu status code và error body là hai phần của contract.

### Middle

Implement centralized mapping và validation errors.

### Senior

Phân biệt expected domain failures, infrastructure failures và security-safe diagnostics.

### Technical Lead / Architect

Định nghĩa error contract dùng được xuyên APIs nhưng không leak implementation details hoặc tạo coupling không cần thiết.

## 11. Key takeaway

- Error response là API contract.
- Client nên branch theo stable semantics, không theo exception message.
- Diagnostic detail thuộc telemetry; public response chỉ chứa thông tin an toàn và hữu ích.

# 3. SQL keyset pagination: stable ordering, index access path và deep-page performance

## 1. What is it?

Keyset pagination lấy trang tiếp theo dựa trên key của row cuối trang trước thay vì `OFFSET N`. Mental model: **tiếp tục scan từ vị trí đã biết**, thay vì yêu cầu database đếm/bỏ qua toàn bộ rows phía trước.

## 2. Why does it exist?

`OFFSET 100000 ROWS FETCH NEXT 50 ROWS` vẫn buộc engine xử lý một lượng lớn rows trước khi trả 50 rows cần thiết. Deep pagination làm I/O và CPU tăng theo page depth. Concurrent inserts/deletes còn có thể làm rows bị lặp hoặc bỏ qua giữa các requests.

## 3. How does it work?

Với ordering `(CreatedAt DESC, Id DESC)`, cursor giữ cặp key cuối cùng:

```text
Page 1: rows ... → last = (2026-09-18 10:00, 900)
Page 2: WHERE (CreatedAt, Id) < cursor
```

SQL Server không có row-value comparison giống một số DB khác, nên predicate thường được viết explicit.

## 4. Practical implementation

```sql
SELECT TOP (@PageSize)
    Id, CreatedAt, CustomerId, Total
FROM dbo.Orders
WHERE
    CreatedAt < @LastCreatedAt
    OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index phù hợp:

```sql
CREATE INDEX IX_Orders_CreatedAt_Id
ON dbo.Orders (CreatedAt DESC, Id DESC)
INCLUDE (CustomerId, Total);
```

`Id` đóng vai trò tie-breaker để ordering deterministic.

## 5. Real production scenario

Order-history API có hàng chục triệu records. Trang đầu bằng OFFSET nhanh, nhưng user/export process đi sâu hàng nghìn pages thì latency tăng dần. Cursor pagination giữ access path gần như ổn định vì database seek từ key gần nhất.

## 6. Failure scenario & troubleshooting

**Symptom** → API duplicate/missing rows giữa pages.  
**Evidence** → sort chỉ theo `CreatedAt`, nhiều rows có cùng timestamp.  
**Hypothesis** → ordering không unique/deterministic.  
**Diagnosis** → inspect ordering columns và concurrent data changes.  
**Fix** → thêm stable unique tie-breaker vào order + cursor + index.  
**Verification** → pagination test với duplicate timestamps và concurrent inserts không lặp/bỏ row trong expected snapshot semantics.

## 7. Common mistakes

Cursor chỉ chứa timestamp không unique; encode cursor nhưng không validate; index không match ordering; dùng keyset khi UI bắt buộc “jump to page 847”; expose raw internal IDs khi contract không muốn.

## 8. Alternatives

OFFSET pagination đơn giản và phù hợp shallow pages hoặc admin UI nhỏ. Snapshot/materialized export phù hợp khi cần traversal nhất quán trên dataset thay đổi liên tục. Search engines có riêng search-after/cursor mechanisms.

## 9. Trade-offs

### Advantages

Deep-page latency ổn định hơn, ít scan bỏ phí và tốt hơn trước concurrent inserts.

### Costs / Risks

Không thuận tiện random page jump; cursor contract phức tạp hơn; sort combinations cần index strategy tương ứng.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu OFFSET phải bỏ qua rows trước trang hiện tại.

### Middle

Implement deterministic cursor predicate.

### Senior

Đọc execution plan và thiết kế composite index theo sort/filter shape.

### Technical Lead / Architect

Chọn pagination semantics dựa trên UX, data volume, consistency expectation và operational cost.

## 11. Key takeaway

- Deep pagination là access-path problem, không chỉ API formatting.
- Keyset pagination cần deterministic unique ordering.
- Index phải phục vụ chính filter/order shape của cursor.

# 4. MongoDB compound indexes: ESR guideline, prefix reuse và query-shape reasoning

## 1. What is it?

Compound index chứa nhiều fields theo một thứ tự xác định. Mental model: **index order mô tả cách dữ liệu được sắp xếp để phục vụ một family of query shapes**, không phải danh sách các fields “hay được query”.

ESR thường được dùng như guideline: Equality → Sort → Range, nhưng nó là reasoning tool chứ không phải luật tuyệt đối.

## 2. Why does it exist?

Một index riêng cho `tenantId`, một index riêng cho `createdAt` không nhất thiết giúp query `tenantId = X ORDER BY createdAt DESC`. Database cần access path có thể thu hẹp equality scope rồi đọc theo sort order mong muốn.

## 3. How does it work?

Index:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

Có thể hỗ trợ prefix queries bắt đầu từ `tenantId`, và tốt cho query equality theo `tenantId/status` rồi sort theo `createdAt`.

```text
tenant A
 ├── pending → newest ... oldest
 ├── paid    → newest ... oldest
 └── shipped → newest ... oldest
```

Bỏ field prefix đầu thường làm index kém hữu ích hơn nhiều.

## 4. Practical implementation

```javascript
db.orders.createIndex({
  tenantId: 1,
  status: 1,
  createdAt: -1
})

// Query shape
db.orders.find({
  tenantId: "t-42",
  status: "paid"
}).sort({ createdAt: -1 }).limit(50)
```

Dùng `explain("executionStats")` để xem keys/docs examined thay vì đoán index từ tên fields.

## 5. Real production scenario

Multi-tenant activity feed filter theo tenant và status, luôn hiển thị newest first. Khi collection tăng từ vài trăm nghìn lên hàng chục triệu documents, một compound index đúng query shape giữ latency ổn định hơn collection scan + in-memory sort.

## 6. Failure scenario & troubleshooting

**Symptom** → query có index nhưng vẫn chậm và `docsExamined` rất cao.  
**Evidence** → index bắt đầu bằng field ít/không có trong predicate hoặc range field đặt trước sort.  
**Hypothesis** → compound index order không match query shape.  
**Diagnosis** → `explain`, query distribution và selectivity.  
**Fix** → redesign index dựa trên dominant query shape; loại redundant indexes nếu an toàn.  
**Verification** → giảm keys/docs examined và latency trên representative dataset.

## 7. Common mistakes

Tạo index cho mọi field; nghĩ compound index tự thay mọi single-field index; không tính write amplification; dùng ESR máy móc mà không đo selectivity; bỏ qua index size và working set.

## 8. Alternatives

Single-field index đủ cho simple queries. Partial index giảm index footprint cho subset phù hợp. Denormalized/materialized access pattern có thể tốt hơn khi query shape quá phức tạp.

## 9. Trade-offs

### Advantages

Giảm scan/sort, phục vụ query shape cụ thể rất hiệu quả.

### Costs / Risks

Mỗi index làm writes đắt hơn, tốn storage/memory và tăng operational maintenance.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu field order trong compound index có ý nghĩa.

### Middle

Dùng `explain` và match index với filter/sort.

### Senior

Cân bằng selectivity, prefixes, write cost và workload distribution.

### Technical Lead / Architect

Thiết kế data model/indexes theo access patterns thực tế thay vì mô phỏng relational schema trong document database.

## 11. Key takeaway

- Compound index là ordered access path.
- ESR là guideline để reasoning, không phải công thức tuyệt đối.
- Mỗi index mới phải trả lời cả read benefit lẫn write/storage cost.

# 5. DDD Aggregate: invariant boundary, transaction boundary và consistency scope

## 1. What is it?

Aggregate là một consistency boundary trong domain model. Một Aggregate Root kiểm soát các thay đổi cần giữ invariant cùng nhau. Mental model quan trọng: **Aggregate không phải object graph càng lớn càng tốt; nó là tập state cần consistency tức thời trong cùng transaction**.

## 2. Why does it exist?

Nếu bất kỳ code nào cũng sửa trực tiếp mọi entity, business invariant dễ bị phá. Ngược lại, gom toàn bộ domain vào một aggregate khổng lồ làm transaction contention, load quá nhiều data và coupling tăng.

## 3. How does it work?

```text
Order (Aggregate Root)
 ├── OrderLine
 └── ShippingAddress

Invariant:
Total = sum(lines)
Cannot add line after Order is Completed
```

External aggregate nên được reference bằng identity thay vì giữ một mutable graph khổng lồ. Cross-aggregate consistency thường cần workflow/eventual consistency thay vì một transaction vô hạn.

## 4. Practical implementation

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];
    public OrderStatus Status { get; private set; }
    public IReadOnlyCollection<OrderLine> Lines => _lines;

    public void AddLine(ProductId productId, int quantity, decimal unitPrice)
    {
        if (Status != OrderStatus.Draft)
            throw new DomainException("Completed order cannot be changed.");
        if (quantity <= 0)
            throw new DomainException("Quantity must be positive.");

        _lines.Add(new OrderLine(productId, quantity, unitPrice));
    }
}
```

Setter protection chỉ là kỹ thuật; giá trị thực nằm ở invariant được giữ tại boundary đúng.

## 5. Real production scenario

Approval system có `ApprovalRequest` và nhiều `ApprovalStep`. Việc “không được mark request Approved nếu còn mandatory step chưa Approved” có thể là invariant trong cùng aggregate. Nhưng `EmployeeProfile` không nhất thiết thuộc aggregate này chỉ vì request có EmployeeId.

## 6. Failure scenario & troubleshooting

**Symptom** → aggregate load chậm, concurrent updates conflict thường xuyên.  
**Evidence** → root chứa hàng nghìn child records và mọi thay đổi update cùng version token.  
**Hypothesis** → consistency boundary quá lớn.  
**Diagnosis** → liệt kê invariants nào thực sự cần atomic transaction.  
**Fix** → tách boundaries nếu invariants cho phép; chuyển cross-boundary rule sang workflow/eventual consistency có explicit semantics.  
**Verification** → invariants vẫn được bảo vệ nhưng contention/load giảm.

## 7. Common mistakes

DDD = Entities + Repository + MediatR; aggregate theo database foreign keys; aggregate chứa mọi related object; public setters phá invariant; cross-aggregate transaction trở thành mặc định.

## 8. Alternatives

Transaction Script phù hợp CRUD/business logic đơn giản. Anemic model có thể hoàn toàn đủ cho data-centric applications. Rich aggregate đáng giá khi domain invariants đủ phức tạp để cần behavior-centric model.

## 9. Trade-offs

### Advantages

Business rules có ownership rõ, transaction boundary dễ reasoning, domain model bảo vệ invariants.

### Costs / Risks

Modeling effort cao hơn; boundary sai tạo contention hoặc eventual-consistency complexity không cần thiết.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu entity không nên cho phép state invalid tùy ý.

### Middle

Implement behavior và invariants qua Aggregate Root.

### Senior

Phân biệt invariant cần strong consistency với workflow có thể eventual.

### Technical Lead / Architect

Chọn aggregate boundaries dựa trên business consistency, contention và ownership — không dựa trên table relationships.

## 11. Key takeaway

- Aggregate là consistency boundary trước khi là code structure.
- Boundary càng lớn, transaction/contension cost càng cao.
- DDD chỉ đáng dùng ở nơi business complexity thực sự cần nó.

# 6. Azure Service Bus message settlement: PeekLock, lock expiry và idempotent consumer

## 1. What is it?

Với `PeekLock`, consumer nhận message nhưng message chưa bị xóa. Service Bus lock message trong một khoảng thời gian; consumer phải `Complete`, `Abandon`, `DeadLetter` hoặc để lock hết hạn. Mental model: **delivery là một lease để xử lý, không phải ownership vĩnh viễn của message**.

## 2. Why does it exist?

Nếu broker xóa message ngay khi gửi cho consumer và process crash trước khi commit business work, message mất. PeekLock cho phép message xuất hiện lại khi processing không hoàn tất, đổi lại consumer phải chấp nhận duplicate delivery.

## 3. How does it work?

```text
Service Bus
   │ deliver + lock
   ▼
Consumer
   ├── success → Complete → remove
   ├── transient failure → Abandon / lock expires → redelivery
   └── unrecoverable → DeadLetter
```

At-least-once delivery nghĩa là cùng logical message có thể được xử lý nhiều lần. Lock renewal giảm risk cho long processing nhưng không tạo exactly-once side effects.

## 4. Practical implementation

```csharp
processor.ProcessMessageAsync += async args =>
{
    var messageId = args.Message.MessageId;

    if (await inbox.AlreadyProcessedAsync(messageId, args.CancellationToken))
    {
        await args.CompleteMessageAsync(args.Message, args.CancellationToken);
        return;
    }

    await handler.HandleAsync(args.Message.Body, args.CancellationToken);
    await inbox.MarkProcessedAsync(messageId, args.CancellationToken);
    await args.CompleteMessageAsync(args.Message, args.CancellationToken);
};
```

Production implementation cần atomicity reasoning giữa business write và inbox marker; sample trên chỉ minh họa settlement flow.

## 5. Real production scenario

Notification worker ghi notification record vào SQL rồi process bị restart trước `Complete`. Service Bus redeliver. Nếu handler idempotent theo `MessageId`/business key, notification không bị tạo hai lần.

## 6. Failure scenario & troubleshooting

**Symptom** → cùng order event được xử lý hai lần.  
**Evidence** → delivery count > 1; lock expired trong lúc dependency chậm.  
**Hypothesis** → processing vượt lock hoặc process crash trước settlement.  
**Diagnosis** → correlate processing duration, lock renewal, delivery count và handler commits.  
**Fix** → idempotent consumer; giảm processing duration hoặc configure renewal phù hợp; DLQ poison messages.  
**Verification** → fault-injection restart giữa commit và complete không tạo duplicate business effect.

## 7. Common mistakes

Giả định `Complete` tạo exactly-once; auto-complete trước business commit; lock duration cực dài để che slow handler; retry poison message vô hạn; không monitor DLQ và delivery count.

## 8. Alternatives

Receive-and-delete chỉ phù hợp khi message loss chấp nhận được. Durable workflow engines phù hợp orchestration dài. Database outbox/inbox hỗ trợ consistency giữa messaging và persistence nhưng thêm operational complexity.

## 9. Trade-offs

### Advantages

Recovery tốt hơn trước consumer crash và transient failure; broker quản lý redelivery.

### Costs / Risks

Duplicate delivery là bình thường; lock/renewal/settlement và idempotency tăng complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu receive không đồng nghĩa message đã bị xóa.

### Middle

Implement complete/abandon/dead-letter và cancellation.

### Senior

Thiết kế idempotency, lock renewal và poison-message handling.

### Technical Lead / Architect

Định nghĩa delivery semantics và transaction boundary giữa broker, database và external side effects.

## 11. Key takeaway

- PeekLock cung cấp recoverable delivery, không phải exactly-once.
- Consumer phải được thiết kế cho duplicate delivery.
- Settlement chỉ nên xảy ra khi business processing đạt trạng thái an toàn.

# 7. Azure App Service deployment slots: warm-up, swap và configuration boundary

## 1. What is it?

Deployment slot là một live deployment environment trong cùng App Service, ví dụ `staging` và `production`. Mental model: **chuẩn bị và validate release trên một runtime riêng rồi chuyển traffic/configuration theo swap semantics**, thay vì overwrite production process trực tiếp.

## 2. Why does it exist?

Deploy trực tiếp có thể gây cold start, startup failure hoặc configuration mismatch ngay trên production traffic. Slot cho phép application khởi động và health-check trước khi promotion.

## 3. How does it work?

```text
Build artifact
    │
    ▼
Staging slot ── warm-up / health validation
    │
    └──── swap ────► Production traffic
```

Một số settings có thể được đánh dấu slot-specific (“deployment slot setting”) để không swap. Đây là điểm critical với secrets, connection strings và environment-specific endpoints.

## 4. Practical implementation

Application nên có health endpoint phản ánh startup/readiness hợp lý:

```csharp
builder.Services.AddHealthChecks()
    .AddDbContextCheck<AppDbContext>();

app.MapHealthChecks("/health/ready");
```

Pipeline deploy cùng immutable artifact vào staging, chờ warm-up/health validation rồi mới swap. Database migration phải được thiết kế backward-compatible với cả old và new app trong transition window.

## 5. Real production scenario

E-commerce API có startup load cho configuration và JIT. Direct deployment từng tạo 20–30 giây 5xx. Staging slot warm trước khi swap giúp production traffic vào process đã sẵn sàng.

## 6. Failure scenario & troubleshooting

**Symptom** → staging xanh nhưng sau swap production gọi nhầm sandbox dependency.  
**Evidence** → endpoint configuration bị swap cùng application.  
**Hypothesis** → environment-specific setting không được đánh dấu slot-specific.  
**Diagnosis** → compare slot configuration trước/sau swap.  
**Fix** → classify settings: artifact-neutral, environment-specific, secret; cấu hình slot setting đúng.  
**Verification** → swap rehearsal và synthetic transaction xác nhận production dependency đúng.

## 7. Common mistakes

Coi slot như full isolated environment; chạy destructive migration trước swap; health check chỉ trả 200 hard-coded; config production/staging bị swap nhầm; không có rollback criteria.

## 8. Alternatives

Blue-Green ở infrastructure level cung cấp isolation rộng hơn. Container Apps/Kubernetes rolling/canary có traffic-control primitives khác. Direct deployment đơn giản hơn cho low-risk internal apps.

## 9. Trade-offs

### Advantages

Warm-up, pre-production validation và rollback/promotion nhanh hơn.

### Costs / Risks

Configuration semantics phức tạp; database vẫn thường shared; extra slot có resource/cost implications.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu staging slot và production slot là runtime endpoints khác nhau.

### Middle

Deploy, health-check và swap đúng configuration.

### Senior

Thiết kế backward-compatible migrations, warm-up và rollback validation.

### Technical Lead / Architect

Chọn release strategy dựa trên blast radius, database compatibility, traffic control và operational maturity.

## 11. Key takeaway

- Slot giảm deployment risk nhưng không tự giải quyết database compatibility.
- Slot-specific configuration phải được phân loại rõ.
- Promotion cần health evidence, không chỉ “deployment command succeeded”.

# 8. Optimizely CMS content modeling: Page, Block và editorial coupling

## 1. What is it?

Trong CMS, content model định nghĩa những khái niệm editor có thể tạo và kết hợp. Với Optimizely CMS, Page thường đại diện content có vị trí/URL trong site hierarchy; Block là reusable/composable content unit. Mental model: **content type là editorial/domain contract**, không phải mirror của component tree frontend.

## 2. Why does it exist?

Nếu content model bám sát HTML hiện tại — `TwoColumnBlueSection`, `HomepageRow3` — redesign UI sẽ buộc migration content. Nếu model quá generic — một giant JSON/free-form block — editor mất guardrails và validation.

## 3. How does it work?

```text
Editor intent
   │
   ▼
Content model
   ├── ProductLandingPage
   ├── HeroBlock
   └── PromotionBlock
        │
        ▼
Rendering / API delivery
        │
        ▼
Web experience
```

Model tốt tách semantic content khỏi presentation detail vừa đủ để UI có thể evolve.

## 4. Practical implementation

```csharp
[ContentType(
    DisplayName = "Promotion Block",
    GUID = "11111111-2222-3333-4444-555555555555")]
public class PromotionBlock : BlockData
{
    [Display(Name = "Heading", Order = 10)]
    public virtual string? Heading { get; set; }

    [Display(Name = "Body", Order = 20)]
    public virtual XhtmlString? Body { get; set; }

    [Display(Name = "Call to action", Order = 30)]
    public virtual Url? CallToAction { get; set; }
}
```

Property names nên mô tả editorial meaning, không mô tả CSS implementation.

## 5. Real production scenario

Marketing site cần promotion xuất hiện ở homepage, campaign page và category page. Reusable `PromotionBlock` cho phép editor quản lý semantic content; renderer quyết định presentation phù hợp context.

## 6. Failure scenario & troubleshooting

**Symptom** → redesign frontend cần sửa hàng nghìn content items.  
**Evidence** → content types chứa fields như `LeftColumnWidth`, `DesktopBlueBackground`, `RowNumber`.  
**Hypothesis** → presentation detail bị đóng cứng vào content schema.  
**Diagnosis** → map fields thành editorial intent vs rendering implementation.  
**Fix** → evolve model theo semantics, thêm migration/compatibility layer có kiểm soát.  
**Verification** → renderer mới dùng được content cũ hoặc migration được test trên production-like dataset.

## 7. Common mistakes

Một block cho mọi component nhỏ; content model mirror Figma frame; giant universal block; breaking rename/remove properties mà không migration; bỏ qua editor usability và preview.

## 8. Alternatives

Page-specific properties đơn giản hơn khi content không reusable. Headless CMS vẫn cần semantic modeling dù rendering tách riêng. Hard-coded application config phù hợp dữ liệu không thuộc editorial ownership.

## 9. Trade-offs

### Advantages

Reuse, editorial consistency, validation và UI evolution tốt hơn.

### Costs / Risks

Over-generalization làm editor khó dùng; schema evolution/migration cần governance; reusable content có thể tạo coupling ngoài dự kiến.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu Page vs reusable Block ở mức editorial purpose.

### Middle

Implement content types, validation và rendering.

### Senior

Thiết kế schema tránh presentation coupling và lên kế hoạch migration.

### Technical Lead / Architect

Đặt content ownership/boundary giữa CMS, product data, application configuration và frontend presentation.

## 11. Key takeaway

- Content model nên mô tả meaning trước presentation.
- Reuse có giá trị khi editorial concept thực sự reusable.
- CMS schema là long-lived contract; redesign UI không nên mặc định kéo theo content migration lớn.

# 9. TypeScript discriminated unions: biến API state thành compile-time contract

## 1. What is it?

Discriminated union là union type có một field literal chung dùng để phân biệt các variants. Mental model: **thay một object có nhiều nullable fields bằng tập các state hợp lệ được mô hình hóa explicit**.

## 2. Why does it exist?

Frontend thường có state như `loading`, `success`, `error`. Một object `{ loading:boolean, data?:T, error?:string }` cho phép trạng thái vô nghĩa: `loading=true` nhưng đồng thời có `data` và `error`. Type system không ngăn được.

## 3. How does it work?

```typescript
type LoadState<T> =
  | { kind: 'idle' }
  | { kind: 'loading' }
  | { kind: 'success'; data: T }
  | { kind: 'error'; problem: ApiProblem };
```

Khi code check `state.kind`, TypeScript narrow type và chỉ expose fields hợp lệ cho variant đó.

## 4. Practical implementation

```typescript
function OrderPanel({ state }: { state: LoadState<Order> }) {
  switch (state.kind) {
    case 'idle':
      return null;
    case 'loading':
      return <Spinner />;
    case 'success':
      return <OrderView order={state.data} />;
    case 'error':
      return <ErrorView problem={state.problem} />;
    default: {
      const neverState: never = state;
      return neverState;
    }
  }
}
```

Exhaustiveness check giúp compiler báo khi thêm state mới nhưng quên xử lý UI.

## 5. Real production scenario

Approval UI trước đây dùng ba booleans `isLoading`, `isSaving`, `hasError` và nhiều nullable objects. Race condition khiến success toast hiển thị đồng thời error banner. State machine nhỏ bằng discriminated union làm invalid combinations khó biểu diễn hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → UI không compile sau khi API workflow thêm `conflict` state.  
**Evidence** → exhaustive switch báo missing variant.  
**Hypothesis** → đây là intentional compile-time break giúp tìm consumer chưa cập nhật.  
**Diagnosis** → inspect all switches/selectors.  
**Fix** → thêm explicit conflict UX.  
**Verification** → typecheck + component tests cho từng state.

## 7. Common mistakes

Dùng `string` thay literal union; cast `as any` để bỏ compiler warning; tạo union quá chi tiết cho state không có behavioral difference; để backend enum thay đổi mà frontend contract generation không kiểm soát.

## 8. Alternatives

Simple boolean đủ cho truly binary state. State-machine library phù hợp workflow phức tạp với transitions/guards. Runtime schema validation vẫn cần ở network boundary vì TypeScript types biến mất lúc runtime.

## 9. Trade-offs

### Advantages

Invalid state khó biểu diễn, narrowing rõ và refactoring an toàn hơn.

### Costs / Risks

Nhiều variants tăng ceremony; compile-time safety không validate payload runtime.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu union và literal discriminator.

### Middle

Model UI/API state và exhaustive rendering.

### Senior

Phân biệt compile-time model với runtime validation và async race handling.

### Technical Lead / Architect

Định nghĩa frontend contract strategy để backend errors/states evolve có kiểm soát.

## 11. Key takeaway

- Type tốt nên loại bỏ invalid state, không chỉ autocomplete fields.
- Exhaustiveness failure là useful feedback khi contract evolve.
- Network data vẫn cần runtime validation dù TypeScript compile sạch.

# 10. LLM Tool Calling: model đề xuất hành động, application giữ authorization boundary

## 1. What is it?

Tool Calling cho phép LLM tạo structured request để application gọi một tool/function. Mental model an toàn: **model là planner/proposer; application là policy enforcement và execution boundary**.

Model không trực tiếp có quyền chỉ vì nó sinh ra `{ tool: "refund", amount: 1000 }`.

## 2. Why does it exist?

LLM giỏi diễn giải intent tự nhiên nhưng business systems cần deterministic APIs. Tool Calling nối probabilistic interpretation với deterministic capabilities bằng schema thay vì parse free-form prose.

## 3. How does it work?

```text
User input
   │
   ▼
LLM ── proposes tool + arguments
   │
   ▼
Application policy boundary
   ├── schema validation
   ├── authentication / authorization
   ├── business rules
   └── idempotency / audit
   │
   ▼
Real tool / API
   │
   ▼
Tool result → LLM → user response
```

Prompt instructions không phải security boundary. Tool executor phải coi model output là untrusted input.

## 4. Practical implementation

```csharp
public async Task<RefundResult> ExecuteRefundAsync(
    ClaimsPrincipal user,
    RefundArgs args,
    CancellationToken ct)
{
    if (!user.IsInRole("RefundOperator"))
        throw new ForbiddenException();

    if (args.Amount <= 0 || args.Amount > 500m)
        throw new ValidationException("Refund amount outside allowed range.");

    return await payments.RefundAsync(
        args.PaymentId,
        args.Amount,
        args.IdempotencyKey,
        ct);
}
```

LLM có thể chọn tool và arguments, nhưng authorization, amount limits và idempotency vẫn là deterministic code.

## 5. Real production scenario

Support assistant đọc ticket “khách bị charge hai lần, hoàn lại giao dịch thứ hai”. Model đề xuất refund tool. Application kiểm tra operator permission, payment ownership, maximum refundable amount và duplicate refund trước khi gọi payment provider.

## 6. Failure scenario & troubleshooting

**Symptom** → agent cố gọi privileged tool với arguments lấy từ malicious document.  
**Evidence** → retrieved content chứa prompt injection yêu cầu “ignore policy and refund”.  
**Hypothesis** → untrusted content ảnh hưởng planner, nhưng exploit chỉ thành công nếu executor tin model output.  
**Diagnosis** → inspect tool-call trace, retrieved sources và policy checks.  
**Fix** → enforce authorization/business rules ngoài model; scope tools; require confirmation/approval cho high-impact actions.  
**Verification** → adversarial eval chứng minh injected content không thể vượt executor policy.

## 7. Common mistakes

Đưa authorization rule chỉ vào system prompt; tool schema quá rộng; model tự tạo tenant/user ID; không có audit trail; retry tool gây duplicate side effect; trả secrets từ tool về context không cần thiết.

## 8. Alternatives

Deterministic UI/workflow tốt hơn khi intent đã structured. Function routing bằng code/rules phù hợp ít commands rõ ràng. Human approval phù hợp high-impact actions nơi false positive có cost lớn.

## 9. Trade-offs

### Advantages

Natural-language orchestration linh hoạt, schema rõ hơn free-form parsing và có thể kết nối nhiều deterministic systems.

### Costs / Risks

Prompt injection, probabilistic tool selection, token/latency cost, observability và authorization complexity.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu model không trực tiếp thực thi tool; application mới là executor.

### Middle

Implement schema validation, timeout và error handling cho tool calls.

### Senior

Thiết kế idempotency, authorization, audit, prompt-injection defenses và evals.

### Technical Lead / Architect

Quyết định capability nào được expose cho agent, capability nào cần approval và capability nào tuyệt đối không nên đặt sau probabilistic planner.

## 11. Key takeaway

- Model output phải được coi là untrusted input tại execution boundary.
- Authorization và financial/security correctness phải nằm trong deterministic application logic.
- Tool capability càng mạnh thì scope, audit, idempotency và approval càng quan trọng.
