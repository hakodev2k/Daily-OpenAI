# 1. CLR `ThreadPool` starvation: khi async code vẫn làm request queue tăng

## 1. What is it?

`ThreadPool` starvation xảy ra khi application cần worker threads nhanh hơn runtime có thể cung cấp chúng. Request chưa chắc tiêu thụ nhiều CPU; chúng có thể chỉ đang giữ threads bằng blocking operations. ASP.NET Core phụ thuộc mạnh vào `ThreadPool`, nên starvation có thể làm latency tăng toàn hệ thống dù CPU chưa đạt 100%.

Mental model:

```text
Incoming requests
      |
      v
ThreadPool queue grows
      |
      +--> worker blocks on .Result / Wait / sync I/O
      |
      +--> too few workers available
      v
new continuations wait longer
      |
      v
p95/p99 latency explodes
```

## 2. Why does it exist?

Threads là resource đắt: stack memory, scheduling và context switching. CLR không tạo vô hạn threads ngay lập tức; pool điều chỉnh số worker theo workload. Điều này hiệu quả với cooperative asynchronous I/O nhưng trở thành bottleneck khi code giữ worker trong lúc chỉ chờ I/O.

## 3. How does it work?

`await` trên operation thực sự asynchronous thường trả thread về pool. Khi I/O hoàn thành, continuation được queue để chạy tiếp. Ngược lại:

```csharp
var result = httpClient.GetStringAsync(url).Result;
```

worker bị giữ trong thời gian network wait. Dưới burst traffic, hàng trăm request có thể cùng giữ threads, trong khi continuations cần chính pool đó để tiến triển.

## 4. Practical implementation

Giữ call chain async end-to-end:

```csharp
public async Task<IResult> GetOrderAsync(
    Guid id,
    OrderService service,
    CancellationToken cancellationToken)
{
    var order = await service.GetAsync(id, cancellationToken);
    return order is null ? Results.NotFound() : Results.Ok(order);
}
```

Không chuyển async I/O thành blocking chỉ để giữ API synchronous.

## 5. Real production scenario

Sau deployment, API throughput giảm 60%, CPU chỉ 35%, database bình thường. Code mới gọi SDK async qua `.GetAwaiter().GetResult()`. Traffic tăng làm worker queue dài; health endpoint cũng chậm vì nó phải được schedule trên cùng runtime resources.

## 6. Failure scenario & troubleshooting

**Symptom:** p99 tăng, request queue tăng, CPU không tương xứng. **Hypothesis:** starvation thay vì CPU saturation. **Evidence:** `dotnet-counters` cho thấy `thread_pool.queue.length` cao và thread count tăng; traces cho thấy blocking stacks. **Root cause:** sync-over-async. **Remediation:** async end-to-end, bounded concurrency cho fan-out, tránh blocking I/O. **Verification:** load test lại và quan sát queue length, throughput, p95/p99.

## 7. Common mistakes

Tăng `ThreadPool.SetMinThreads` như permanent fix; chỉ nhìn CPU; dùng `Task.Run` để bọc database/network I/O; gọi `.Result` trong middleware; tạo fan-out không giới hạn rồi cho rằng `await` tự kiểm soát concurrency.

## 8. Alternatives

CPU-bound work dài có thể cần dedicated workers/queue. Workload đặc biệt có thể điều chỉnh minimum threads sau khi đo. Nhưng tuning pool không thay thế việc loại blocking path.

## 9. Trade-offs

Async giảm blocked workers nhưng tăng complexity về cancellation, exception flow và lifetime. Dedicated workers tạo isolation tốt hơn nhưng tăng operational components.

## 10. Junior → Middle → Senior → Technical Lead

**Junior:** hiểu `await` không có nghĩa là tạo thread mới. **Middle:** nhận diện sync-over-async. **Senior:** dùng runtime metrics và traces để phân biệt starvation với CPU saturation. **Technical Lead:** đặt concurrency budget và review blocking behavior ở architecture boundaries.

## 11. Senior / Architect Notes

Starvation là capacity failure. Một dependency chậm có thể biến thành local resource exhaustion nếu mỗi request giữ worker. Timeout, cancellation và concurrency limits phải được thiết kế cùng nhau.

## 12. Key Takeaways

- CPU thấp không loại trừ runtime saturation.
- Async I/O chỉ hữu ích nếu call chain không quay lại blocking.
- Điều tra bằng queue/thread/runtime telemetry, không đoán từ exception.

# 2. ASP.NET Core `RateLimiter`: bảo vệ capacity thay vì chỉ chống abuse

## 1. What is it?

Rate limiting kiểm soát lượng work application chấp nhận theo thời gian hoặc concurrency. Trong ASP.NET Core, `Microsoft.AspNetCore.RateLimiting` cung cấp middleware và các limiter như fixed window, sliding window, token bucket và concurrency limiter.

## 2. Why does it exist?

Backend có capacity hữu hạn: database connections, external API quota, CPU, memory và queue depth. Không giới hạn admission khiến overload tự khuếch đại: latency tăng → requests sống lâu hơn → resources bị giữ lâu hơn → latency tiếp tục tăng.

## 3. How does it work?

```text
Request
  |
  v
Partition key (user/API key/IP/tenant)
  |
  v
Limiter
  | allowed                 | rejected/queued
  v                         v
Endpoint                  429 / backpressure
```

Token bucket phù hợp khi muốn cho phép burst có kiểm soát; concurrency limiter phù hợp khi bottleneck là số operation đồng thời.

## 4. Practical implementation

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddConcurrencyLimiter("expensive-report", limiter =>
    {
        limiter.PermitLimit = 20;
        limiter.QueueLimit = 10;
        limiter.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
    });

    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});

app.UseRateLimiter();

app.MapPost("/reports", GenerateReport)
   .RequireRateLimiting("expensive-report");
```

Giới hạn phải liên hệ với capacity thật, không chọn số đẹp tùy ý.

## 5. Real production scenario

Report endpoint chạy query nặng. 100 concurrent requests làm connection pool cạn và ảnh hưởng cả checkout endpoints. Concurrency limiter tại report boundary giữ tối đa 20 operations, bảo vệ database capacity cho critical traffic.

## 6. Failure scenario & troubleshooting

**Symptom:** 429 tăng sau deployment. **Evidence:** limiter rejection metrics tăng nhưng DB latency ổn. **Diagnosis:** capacity policy quá thấp hoặc traffic pattern thay đổi. Ngược lại nếu limiter không reject nhưng DB pool vẫn exhausted, partition/boundary có thể sai. Verify bằng accepted/rejected rate, queue time, dependency saturation và end-to-end latency.

## 7. Common mistakes

Rate limit chỉ theo IP sau reverse proxy mà không xử lý forwarded headers; dùng một global limit làm noisy tenant ảnh hưởng tất cả; queue quá dài khiến request hết timeout trước khi được xử lý; retry 429 ngay lập tức; coi rate limiting là authorization.

## 8. Alternatives

API Gateway/Azure Front Door có thể limit ở edge; queue-based load leveling phù hợp với asynchronous work; autoscaling tăng capacity nhưng không thay admission control vì scaling có delay và dependency downstream vẫn hữu hạn.

## 9. Trade-offs

Reject sớm cải thiện system stability nhưng giảm acceptance rate. Queue hấp thụ burst nhỏ nhưng tăng latency và memory. Per-tenant partition công bằng hơn nhưng tăng state/cardinality.

## 10. Junior → Middle → Senior → Technical Lead

**Junior:** hiểu 429 và limiter. **Middle:** chọn algorithm theo workload. **Senior:** liên kết limit với downstream capacity. **Technical Lead:** thiết kế fairness, tiering và overload policy xuyên gateway/service/database.

## 11. Senior / Architect Notes

Rate limiter là một phần của load-shedding strategy. SLO quan trọng hơn việc “không reject request”: trong overload, reject 5% nhanh có thể tốt hơn làm 100% requests timeout.

## 12. Key Takeaways

- Rate limiting là capacity control.
- Chọn partition và queue policy quan trọng ngang con số limit.
- Đo rejection cùng dependency saturation và latency.

# 3. EF Core `ExecuteUpdate` / `ExecuteDelete`: set-based mutation và Change Tracker consistency

## 1. What is it?

`ExecuteUpdateAsync` và `ExecuteDeleteAsync` cho phép EF Core phát lệnh set-based trực tiếp xuống database mà không load entities và không đi qua normal `SaveChanges` change-tracking flow.

## 2. Why does it exist?

Pattern truyền thống:

```text
SELECT 50,000 rows
→ materialize entities
→ track them
→ mutate objects
→ generate UPDATEs
```

lãng phí memory, round trips và change-tracking cost khi business operation thực chất là một set operation.

## 3. How does it work?

```csharp
await db.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiresAt < now)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired), ct);
```

Database nhận một `UPDATE ... WHERE ...`. Tracked instances đang tồn tại trong `DbContext` không tự được đồng bộ với thay đổi này.

## 4. Practical implementation

Dùng context scope ngắn và tránh trộn tracked mutation với bulk set-based mutation trên cùng entities. Nếu bắt buộc, reload/clear tracker có chủ đích:

```csharp
await query.ExecuteUpdateAsync(..., ct);
db.ChangeTracker.Clear();
```

Không gọi `Clear()` mù quáng nếu context còn pending changes khác.

## 5. Real production scenario

Nightly job expire 200k carts. Load từng cart làm memory tăng mạnh và job chạy 20 phút. Set-based update giảm operation thành một SQL statement phù hợp với index và transaction strategy.

## 6. Failure scenario & troubleshooting

**Symptom:** database đã đổi `Status`, nhưng code sau đó đọc tracked entity vẫn thấy giá trị cũ và `SaveChanges` ghi ngược lại. **Evidence:** SQL trace xác nhận update thành công; debugger thấy entity state vẫn chứa old value. **Root cause:** tracker không biết direct database mutation. **Fix:** tách context/unit-of-work hoặc reload state. **Verification:** integration test trộn tracked + bulk operations.

## 7. Common mistakes

Giả định `SaveChanges` transaction bao luôn `ExecuteUpdate`; quên concurrency semantics; bỏ qua domain events/audit hooks nằm trong `SaveChanges`; bulk update bảng lớn không có selective predicate/index; giữ tracked entities stale.

## 8. Alternatives

Tracked updates phù hợp khi cần domain logic per entity. Raw SQL/stored procedures hữu ích cho database-specific logic. Dedicated bulk libraries có richer features nhưng thêm dependency và semantics riêng.

## 9. Trade-offs

Set-based mutation nhanh và ít allocation, nhưng bypass nhiều application-level behaviors. Càng nhiều invariants nằm trong entity lifecycle, càng phải cẩn thận.

## 10. Junior → Middle → Senior → Technical Lead

**Junior:** phân biệt entity update với SQL set update. **Middle:** dùng API đúng workload. **Senior:** quản lý transaction/tracker/concurrency. **Technical Lead:** quyết định invariant nào phải ở application, database constraint hay event pipeline.

## 11. Senior / Architect Notes

Performance optimization thay đổi semantic boundary. Nếu audit, outbox hoặc domain events dựa vào `SaveChanges`, direct mutation có thể tạo silent correctness gap.

## 12. Key Takeaways

- Set-based API tránh materialization không cần thiết.
- Change Tracker không tự đồng bộ.
- Review transaction, audit, concurrency và domain-event semantics trước khi dùng.

# 4. SQL Server deadlock: đọc deadlock graph thay vì tăng timeout

## 1. What is it?

Deadlock là chu kỳ dependency giữa transactions: mỗi transaction giữ resource mà transaction kia cần, khiến không bên nào tiến triển. SQL Server phát hiện chu kỳ và chọn một victim để rollback.

```text
Tx A holds Row X -> waits Row Y
      ^                 |
      |                 v
Tx B waits Row X <- holds Row Y
```

## 2. Why does it exist?

Locking bảo vệ isolation và consistency. Deadlock là hệ quả có thể xảy ra khi nhiều transactions lấy locks theo thứ tự khác nhau hoặc query plans chạm resource sets lớn.

## 3. How does it work?

SQL Server deadlock monitor phát hiện wait-for cycle và chọn victim dựa trên deadlock priority/cost. Application thường nhận error `1205`. Đây khác blocking: blocking có thể tự hết khi holder commit; deadlock cần một transaction bị rollback.

## 4. Practical implementation

Thu thập deadlock graph qua Extended Events (`system_health` thường chứa `xml_deadlock_report`). Đọc:

- processes và statements;
- resources;
- lock modes;
- owner/waiter relationships;
- victim;
- indexes/object names.

Sau đó sửa ordering/query/index/transaction scope dựa trên evidence.

## 5. Real production scenario

Checkout transaction update `Orders` rồi `Inventory`; replenishment job update `Inventory` rồi `Orders`. Dưới concurrency, hai flow tạo lock ordering đảo ngược.

## 6. Failure scenario & troubleshooting

**Symptom:** intermittent 1205 lúc peak. **Telemetry:** error rate tăng nhưng CPU/connection pool bình thường. **Evidence:** graph cho thấy two-key cycle. **Root cause:** inconsistent lock ordering. **Remediation:** chuẩn hóa order `Inventory → Orders` hoặc rút ngắn transaction; index để giảm scanned/locked rows. **Verification:** concurrency test và theo dõi deadlock events sau deploy.

## 7. Common mistakes

Tăng command timeout; bật `NOLOCK` khắp nơi; retry vô hạn; thêm index không đọc plan; giữ transaction mở trong lúc gọi HTTP; chỉ xem victim query mà bỏ qua transaction còn lại.

## 8. Alternatives

Optimistic concurrency giảm một số lock interactions nhưng không xóa mọi deadlock. Snapshot-based isolation thay đổi read/write blocking trade-off. Retry bounded với jitter là resilience layer sau khi transaction idempotent, không phải root-cause fix.

## 9. Trade-offs

Index có thể giảm lock footprint nhưng tăng write/storage cost. Isolation thấp hơn tăng concurrency nhưng có thể đổi consistency semantics. Transaction ngắn hơn tốt nhưng có thể yêu cầu redesign workflow.

## 10. Junior → Middle → Senior → Technical Lead

**Junior:** phân biệt deadlock và timeout. **Middle:** đọc graph cơ bản. **Senior:** liên kết graph với plan/index/transaction. **Technical Lead:** chuẩn hóa transaction ordering và observability cho critical workflows.

## 11. Senior / Architect Notes

Deadlock là concurrency design signal. Nếu transaction chứa remote call, user think-time hoặc quá nhiều aggregate boundaries, vấn đề có thể nằm ở architecture chứ không chỉ SQL.

## 12. Key Takeaways

- Error 1205 cần deadlock graph.
- Victim không nhất thiết là code “gây lỗi”.
- Fix ordering, lock footprint và transaction boundaries trước khi dựa vào retry.

# 5. MongoDB compound index: Equality → Sort → Range và access-pattern design

## 1. What is it?

Compound index lưu nhiều fields theo thứ tự xác định. Thứ tự fields ảnh hưởng trực tiếp khả năng database dùng index cho filtering và sorting.

Ví dụ access pattern:

```javascript
find({ tenantId: 42, status: "PAID", createdAt: { $gte: from } })
  .sort({ createdAt: -1 })
```

có thể dẫn tới index:

```javascript
{ tenantId: 1, status: 1, createdAt: -1 }
```

## 2. Why does it exist?

Một index riêng cho từng field không tương đương một compound index tối ưu cho query. Database cần traversal order hỗ trợ predicate và sort mà không scan/sort lượng dữ liệu lớn.

## 3. How does it work?

Guideline hữu ích là **Equality → Sort → Range (ESR)**: equality fields thu hẹp prefix; sort field cho phép trả dữ liệu theo index order; range thường đặt sau vì range làm giảm khả năng tận dụng các fields phía sau. Đây là heuristic, phải verify bằng explain plan và workload thật.

## 4. Practical implementation

```javascript
db.orders.createIndex({ tenantId: 1, status: 1, createdAt: -1 })
```

Sau đó:

```javascript
db.orders.find({...}).sort({createdAt:-1}).explain("executionStats")
```

Quan sát `totalKeysExamined`, `totalDocsExamined`, winning plan và returned count.

## 5. Real production scenario

Multi-tenant order history query nhanh cho tenant nhỏ nhưng timeout với tenant lớn. Index chỉ có `{ tenantId: 1 }`, nên hàng trăm nghìn documents của tenant vẫn phải filter/sort.

## 6. Failure scenario & troubleshooting

**Symptom:** query latency tăng theo tenant size. **Evidence:** explain cho thấy keys/docs examined cao và blocking sort. **Hypothesis:** index không match access pattern. **Fix:** compound index dựa trên filter/sort; verify trên representative cardinality. **Verification:** compare execution stats và p95 production.

## 7. Common mistakes

Tạo index cho mọi field; bỏ qua prefix rule; index low-selectivity field một mình; tin ESR như luật tuyệt đối; không tính write amplification; query không giới hạn tenant boundary; giữ unused indexes lâu dài.

## 8. Alternatives

Denormalize/materialized views cho read model đặc biệt; Atlas Search/Elasticsearch cho full-text/relevance; pagination bằng stable cursor thay vì large skip.

## 9. Trade-offs

Read nhanh hơn đổi lấy storage, RAM và write cost. Nhiều compound indexes làm insert/update đắt và operational tuning phức tạp.

## 10. Junior → Middle → Senior → Technical Lead

**Junior:** hiểu index field order. **Middle:** dùng explain. **Senior:** cân read/write/cardinality. **Technical Lead:** thiết kế index portfolio từ access patterns và SLO thay vì entity schema.

## 11. Senior / Architect Notes

Document modeling và indexing phải cùng xuất phát từ query patterns. “Schema flexible” không có nghĩa là performance model không cần thiết kế.

## 12. Key Takeaways

- Compound index order là semantic performance decision.
- ESR là starting heuristic, không thay explain plan.
- Đo examined/returned ratio và production latency.

# 6. `Circuit Breaker`: ngăn dependency failure lan thành resource exhaustion

## 1. What is it?

Circuit Breaker tạm thời chặn calls tới dependency đang có failure rate cao, thay vì tiếp tục gửi request mà khả năng lớn sẽ fail. States thường là closed, open và half-open.

```text
Closed -- failures exceed threshold --> Open
  ^                                     |
  |                                     | break duration
  +--------- successful probes <-- Half-Open
```

## 2. Why does it exist?

Remote failure thường chậm: timeout 10 giây nguy hiểm hơn fail-fast 10 ms vì mỗi request giữ memory, sockets và concurrency slots. Retry không kiểm soát còn nhân tải lên dependency đang yếu.

## 3. How does it work?

Breaker quan sát outcomes trong sampling window. Khi failure ratio/throughput đạt policy, circuit mở và reject nhanh. Sau break duration, limited probes kiểm tra recovery trước khi đóng lại.

## 4. Practical implementation

Với resilience pipeline của modern .NET, cấu hình timeout/retry/circuit breaker theo idempotency và dependency behavior. Conceptually:

```csharp
services.AddHttpClient<InventoryClient>()
    .AddStandardResilienceHandler();
```

Default policy chỉ là điểm bắt đầu; critical dependency cần review thresholds, timeout và retry semantics.

## 5. Real production scenario

Review API chậm 15 giây. Product page synchronous fan-out tới Reviews làm web threads/connections tích tụ. Breaker mở sau sustained failures và product page fallback sang “reviews unavailable”, giữ core commerce path hoạt động.

## 6. Failure scenario & troubleshooting

**Symptom:** breaker liên tục open/half-open. **Evidence:** dependency latency/error metrics và breaker events. **Diagnosis:** upstream chưa phục hồi hoặc policy quá nhạy. **Fix:** điều chỉnh threshold dựa trên baseline, giảm retry amplification, tạo fallback đúng business. **Verification:** chaos test dependency latency/error và quan sát resource usage.

## 7. Common mistakes

Breaker dùng thay timeout; breaker per request instance nên không tích lũy state; retry bên trong nhiều layers tạo multiplicative retries; fallback trả dữ liệu sai mà không đánh dấu degraded state; circuit chung cho unrelated endpoints.

## 8. Alternatives

Bulkhead/concurrency limiter cô lập capacity; queue tách temporal coupling; cache/stale reads cung cấp degraded experience; failover endpoint có thể hữu ích nếu thật sự độc lập failure domain.

## 9. Trade-offs

Fail-fast bảo vệ hệ thống nhưng chủ động từ chối một số requests có thể đã thành công. Shared breaker phản ứng nhanh hơn nhưng có thể over-isolate; granular breaker tăng state/complexity.

## 10. Junior → Middle → Senior → Technical Lead

**Junior:** hiểu three states. **Middle:** phối timeout/retry. **Senior:** thiết kế thresholds và fallback. **Technical Lead:** xác định dependency criticality, failure domains và degraded-mode product behavior.

## 11. Senior / Architect Notes

Resilience không phải “thêm Polly”. Cần budget: một user request được phép tạo bao nhiêu downstream attempts và giữ resources tối đa bao lâu?

## 12. Key Takeaways

- Breaker chủ yếu bảo vệ caller.
- Timeout, retry, breaker và concurrency limit phải phối hợp.
- Fallback là business decision, không chỉ technical callback.

# 7. Azure Blob Storage SAS: delegation, blast radius và upload architecture

## 1. What is it?

Shared Access Signature (SAS) cấp quyền giới hạn tới Azure Storage resource trong khoảng thời gian xác định mà không đưa account key cho client. User delegation SAS dùng Microsoft Entra credentials để ký delegation key và thường phù hợp hơn khi architecture hỗ trợ nó.

## 2. Why does it exist?

Nếu browser upload file qua application server:

```text
Browser -> API -> Blob Storage
```

API phải relay bytes, tốn bandwidth và compute. SAS cho phép:

```text
Browser -> API: request upload authorization
API -> Browser: short-lived scoped SAS
Browser --------------------> Blob Storage
```

## 3. How does it work?

SAS token encode resource scope, permissions và validity interval cùng signature. Storage service validate signature trước khi cho operation. Security nằm ở việc scope đúng resource/action/time, không phải vì URL “khó đoán”.

## 4. Practical implementation

Backend authenticate user, authorize business operation, generate SAS chỉ cho blob/container path cần thiết và permission tối thiểu (`Create`/`Write` thay vì broad read/delete). Blob name nên do server kiểm soát hoặc namespace theo tenant/user.

## 5. Real production scenario

CMS editors upload video 500 MB. Direct-to-Blob upload giảm App Service bandwidth, request timeout và memory pressure. Backend lưu metadata sau khi upload được xác nhận.

## 6. Failure scenario & troubleshooting

**Symptom:** attacker có leaked SAS vẫn upload được nhiều files. **Evidence:** SAS còn hạn dài và permission/container scope quá rộng. **Root cause:** delegation capability có blast radius lớn. **Fix:** short expiry, narrow path/permissions, revoke strategy, server-side validation pipeline. **Verification:** negative tests với expired/wrong-path/wrong-permission SAS.

## 7. Common mistakes

Log full SAS URL; SAS sống nhiều ngày; cấp container-wide delete; coi upload thành công là file an toàn; tin `Content-Type` từ browser; không xử lý orphan blobs khi metadata transaction fail.

## 8. Alternatives

Proxy upload qua API đơn giản hơn cho small files và centralized validation nhưng tốn capacity. Managed Identity phù hợp service-to-storage, không trực tiếp thay delegated browser access. Azure Front Door/CDN giải quyết delivery, không authorization upload.

## 9. Trade-offs

Direct upload scale tốt nhưng client workflow và lifecycle phức tạp hơn. Short expiry an toàn hơn nhưng upload lớn/chậm có thể cần carefully sized validity window.

## 10. Junior → Middle → Senior → Technical Lead

**Junior:** hiểu SAS là delegated capability. **Middle:** generate narrow permissions. **Senior:** xử lý malware scan, orphan cleanup và telemetry. **Technical Lead:** thiết kế trust boundary, retention và data-plane networking.

## 11. Senior / Architect Notes

File upload là security workflow: authorization, content validation, quarantine/scanning, metadata consistency và lifecycle management đều cần owner rõ ràng.

## 12. Key Takeaways

- SAS phải least-privilege và short-lived.
- Không log capability URL.
- Direct upload giảm backend load nhưng chuyển complexity sang workflow/security.

# 8. `BackgroundService`: graceful shutdown, scoped dependency và at-least-once work

## 1. What is it?

`BackgroundService` là base class cho long-running hosted work trong .NET Generic Host. `ExecuteAsync` nhận stopping token để cooperative shutdown khi host dừng.

## 2. Why does it exist?

Applications cần queue consumers, polling loops hoặc periodic maintenance chạy cùng host lifecycle. Primitive này tích hợp startup/shutdown và DI thay vì tự tạo unmanaged threads.

## 3. How does it work?

Hosted service thường được đăng ký singleton. Vì vậy scoped dependencies như `DbContext` không nên inject trực tiếp và giữ lâu dài; mỗi unit of work nên tạo scope riêng.

```text
Host starts
  -> ExecuteAsync loop
       -> create scope
       -> process one unit
       -> dispose scope
  -> stoppingToken signaled
  -> finish/abandon safely
Host stops
```

## 4. Practical implementation

```csharp
public sealed class OrderWorker(IServiceScopeFactory scopes) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = scopes.CreateAsyncScope();
            var processor = scope.ServiceProvider.GetRequiredService<OrderProcessor>();
            await processor.ProcessNextAsync(stoppingToken);
        }
    }
}
```

Processing method cần idempotent nếu source có redelivery.

## 5. Real production scenario

Azure Service Bus consumer nhận message, ghi database rồi process bị terminate trước settlement. Message được delivery lại. Worker đúng phải coi duplicate execution là normal distributed-systems behavior.

## 6. Failure scenario & troubleshooting

**Symptom:** deployment tạo duplicate side effect. **Evidence:** cùng MessageId được xử lý trước và sau restart. **Root cause:** work completed nhưng acknowledgement chưa hoàn tất. **Fix:** Inbox/idempotency key hoặc atomic business uniqueness constraint; propagate stopping token và stop receiving new work khi shutdown. **Verification:** kill process giữa commit và settlement trong integration test.

## 7. Common mistakes

Inject `DbContext` vào singleton worker; swallow cancellation; `Task.Delay` không truyền token; fire-and-forget tasks; assume shutdown luôn graceful; periodic timer trên nhiều replicas nhưng mong chỉ chạy một lần globally.

## 8. Alternatives

Azure Functions phù hợp event-triggered managed execution; Hangfire/Quartz cung cấp scheduling/persistence; Kubernetes CronJob phù hợp isolated scheduled process. Queue consumer riêng giúp scale/deploy độc lập web app.

## 9. Trade-offs

In-process worker đơn giản nhưng share failure/capacity với web host. Separate worker tăng operational footprint nhưng isolation và scaling tốt hơn.

## 10. Junior → Middle → Senior → Technical Lead

**Junior:** dùng stopping token. **Middle:** tạo DI scope đúng. **Senior:** thiết kế idempotency/shutdown. **Technical Lead:** chọn hosting model dựa trên delivery semantics, scaling và failure isolation.

## 11. Senior / Architect Notes

“Exactly once” hiếm khi đến từ worker loop. Business correctness thường đạt bằng at-least-once delivery + idempotent effects + durable state.

## 12. Key Takeaways

- Hosted service lifetime và scoped dependency phải tách đúng.
- Shutdown có thể xảy ra giữa bất kỳ hai side effects nào.
- Duplicate execution phải được thiết kế, không coi là edge case.

# 9. Playwright auto-waiting: loại bỏ flaky sleeps nhưng không che eventual consistency

## 1. What is it?

Playwright tự chờ actionability trước nhiều actions và assertions: element phải tồn tại/visible/stable/receivable tùy action. Điều này giảm nhu cầu dùng arbitrary sleeps.

## 2. Why does it exist?

UI hiện đại render asynchronous. Test kiểu:

```ts
await page.waitForTimeout(2000);
await page.click('#save');
```

vừa chậm vừa flaky: 2 giây có thể thừa ở local và thiếu trong CI.

## 3. How does it work?

Locator được resolve tại thời điểm action; Playwright retry trong timeout cho tới khi actionability/assertion condition đạt hoặc timeout. Web-first assertions cũng retry thay vì snapshot-check ngay lập tức.

## 4. Practical implementation

```ts
await page.getByRole('button', { name: 'Save' }).click();
await expect(page.getByText('Saved')).toBeVisible();
```

Ưu tiên role/label/test-id theo semantic contract thay vì brittle CSS tree selectors.

## 5. Real production scenario

Checkout UI gửi API, backend publish event, read model cập nhật sau vài trăm milliseconds. Button auto-waiting không giải quyết eventual consistency của business state. Test phải chờ observable business condition, ví dụ order status chuyển `Confirmed`.

## 6. Failure scenario & troubleshooting

**Symptom:** test pass local, fail CI vì “status still Pending”. **Evidence:** network trace cho thấy POST 200 nhưng projection update đến sau assertion. **Diagnosis:** test nhầm UI actionability với backend consistency. **Fix:** assertion polling trên user-visible state với bounded timeout; instrument API/event lag. **Verification:** chạy repeated/parallel CI và giữ traces/screenshots khi fail.

## 7. Common mistakes

`waitForTimeout` khắp nơi; selector theo CSS implementation; tăng global timeout để che bug; `force: true` bypass actionability; share mutable authentication/data state giữa parallel tests; assert implementation detail thay vì behavior.

## 8. Alternatives

Component tests nhanh hơn cho isolated UI logic. API integration tests xác minh backend contract. Contract tests giảm số E2E paths cần thiết. E2E vẫn cần cho critical user journeys xuyên boundaries.

## 9. Trade-offs

Auto-wait tăng reliability nhưng timeout failures có thể chậm. Semantic locators yêu cầu accessible UI tốt. Polling eventual state phản ánh production tốt hơn nhưng test duration dài hơn.

## 10. Junior → Middle → Senior → Technical Lead

**Junior:** bỏ fixed sleeps. **Middle:** dùng locators/assertions đúng. **Senior:** phân biệt UI synchronization với distributed consistency. **Technical Lead:** xây test pyramid, isolation và failure artifacts cho CI.

## 11. Senior / Architect Notes

Flaky test thường là observability problem thu nhỏ. Trace, network logs, console và server correlation IDs giúp biến “CI thỉnh thoảng đỏ” thành evidence-driven diagnosis.

## 12. Key Takeaways

- Auto-wait thay arbitrary timing assumptions cho UI actions.
- Nó không tự chờ business eventual consistency.
- E2E cần semantic locators, isolated state và diagnostic artifacts.

# 10. AI RAG: chunking, retrieval quality và grounding không đồng nghĩa correctness

## 1. What is it?

Retrieval-Augmented Generation (RAG) lấy context từ knowledge source rồi đưa context đó vào model để tạo answer. Nó tách phần knowledge retrieval khỏi model weights.

```text
Question
  -> query transformation / embedding
  -> retrieval
  -> ranking
  -> selected chunks
  -> LLM generation
  -> answer + citations
```

## 2. Why does it exist?

Enterprise knowledge thay đổi nhanh, private và quá lớn để nhét toàn bộ vào prompt. RAG cho phép model sử dụng documents hiện hành mà không fine-tune lại cho mỗi thay đổi dữ liệu.

## 3. How does it work?

Documents được chunk, indexed bằng lexical/vector/hybrid search. Query lấy candidates; optional reranker chọn context tốt hơn; model sinh answer dựa trên retrieved evidence. Chất lượng cuối phụ thuộc cả retrieval lẫn generation.

## 4. Practical implementation

Thiết kế metadata trước: tenant, document type, version, effective date, ACL. Retrieval phải filter authorization trước khi context đi vào model. Chunk theo semantic boundaries thay vì cắt mỗi N characters một cách mù quáng.

Pseudo-flow:

```csharp
var candidates = await search.HybridSearchAsync(
    query,
    filters: new { TenantId = tenantId, Status = "Current" },
    cancellationToken);

var context = reranker.Select(candidates);
var answer = await llm.AnswerAsync(query, context, cancellationToken);
```

## 5. Real production scenario

Internal support assistant có cả policy 2025 và policy 2026. Vector similarity trả chunk cũ vì wording gần hơn. Model trả lời rất tự tin nhưng policy đã superseded. Đây là retrieval/versioning failure, không chỉ hallucination.

## 6. Failure scenario & troubleshooting

**Symptom:** answer sai dù citation nhìn liên quan. **Evidence:** retrieved set chứa obsolete document; current policy không vào top-k. **Hypothesis:** metadata/version filters hoặc ranking yếu. **Root cause:** index không encode lifecycle/effective status. **Remediation:** current-version filtering, hybrid retrieval, reranking, chunk redesign. **Verification:** golden question set đo Recall@K, retrieval relevance và answer groundedness riêng biệt.

## 7. Common mistakes

Chỉ đánh giá final answer; tăng top-k vô hạn; chunk quá nhỏ mất context hoặc quá lớn loãng relevance; không enforce ACL trước retrieval; coi citation là bằng chứng answer đúng; index duplicate/obsolete docs; dùng vector search cho exact identifiers mà không hybrid lexical search.

## 8. Alternatives

Tool/API lookup phù hợp dữ liệu structured/current như account balance. SQL/search query deterministic tốt hơn cho exact facts. Fine-tuning phù hợp behavior/style/task patterns hơn là constantly changing private facts. Long-context prompting phù hợp corpus nhỏ có bounded size.

## 9. Trade-offs

Nhiều chunks tăng recall nhưng tăng token cost/noise. Aggressive filtering tăng precision nhưng có thể mất relevant evidence. Reranking tăng quality nhưng thêm latency/cost. Hybrid search tăng operational complexity nhưng thường robust hơn một retrieval mode.

## 10. Junior → Middle → Senior → Technical Lead

**Junior:** hiểu retrieve rồi generate. **Middle:** thiết kế chunks/metadata. **Senior:** tách retrieval metrics khỏi generation metrics và security filters. **Technical Lead:** quyết định RAG có thật sự là đúng architecture hay deterministic data access phù hợp hơn.

## 11. Senior / Architect Notes

Grounding giảm một class hallucination nhưng không tạo correctness guarantee. Với quyết định tài chính, authorization hoặc destructive action, model output phải đi qua deterministic validation/business rules.

## 12. Key Takeaways

- RAG quality bắt đầu từ document lifecycle và retrieval, không phải prompt cuối.
- Đo Recall@K/relevance riêng với answer quality.
- ACL, version và tenant filters là security/correctness boundaries.

# Cross-Topic Engineering Connections

Các chủ đề hôm nay cùng xoay quanh một nguyên tắc: **capacity, state và correctness phải được quản lý tại đúng boundary**.

- `ThreadPool` starvation và `RateLimiter` cho thấy asynchronous code không tự tạo capacity; admission control phải phản ánh resource budget.
- `ExecuteUpdate` và SQL deadlock cho thấy performance optimization không thể tách khỏi transaction semantics và state ownership.
- MongoDB compound indexes nhắc rằng storage design phải xuất phát từ access patterns, giống cách RAG index/chunking phải xuất phát từ retrieval patterns.
- `Circuit Breaker` và `BackgroundService` đều giả định failure/duplicate execution là bình thường trong distributed systems.
- SAS và RAG ACL đều là capability/security boundary: dữ liệu không được phép rời trust boundary chỉ vì implementation thuận tiện.
- Playwright và production observability dùng cùng reasoning loop: symptom → evidence → hypothesis → remediation → verification.

Một Technical Lead nên review hệ thống bằng câu hỏi xuyên suốt: **resource nào hữu hạn, state nào có thể stale/duplicate, failure nào có thể lan rộng, và telemetry nào chứng minh giả thuyết khi production khác với happy path?**
