# 1. C# `ValueTask<T>` và synchronous completion: giảm allocation đúng hot path mà không làm async API khó sử dụng hơn

## 1. What is it?

`ValueTask<T>` là một awaitable có thể đại diện cho kết quả đã có sẵn **hoặc** một asynchronous operation chưa hoàn thành. Mental model quan trọng nhất:

```text
Task<T>
-> luôn dùng một Task-like reference để biểu diễn operation

ValueTask<T>
-> có thể chứa trực tiếp T
-> hoặc wrap Task<T>/IValueTaskSource<T>
```

Lợi ích tiềm năng xuất hiện khi một API hoàn thành synchronously rất thường xuyên và việc tạo `Task<T>` mới trở thành allocation đáng kể.

`ValueTask<T>` không phải “Task nhanh hơn”. Nó đổi allocation profile lấy API/lifetime complexity cao hơn.

## 2. Why does it exist?

Một số hot path có cache hit rất cao:

```text
GetAsync(key)
  -> 95%: value đã nằm trong memory
  -> 5%: cần I/O tới database/network
```

Nếu mỗi cache hit vẫn tạo một `Task<T>` chỉ để trả kết quả đã có sẵn, application tạo nhiều short-lived allocations. Với hàng triệu calls, cost GC có thể đo được.

`ValueTask<T>` cho phép trả synchronous result mà không cần allocate `Task<T>` mới trong một số implementations.

Nếu operation gần như luôn asynchronous, lợi ích này thường biến mất và `Task<T>` đơn giản hơn.

## 3. How does it work?

Một method có thể trả:

```csharp
public ValueTask<Product?> GetAsync(string key, CancellationToken ct)
{
    if (_cache.TryGetValue(key, out Product? product))
        return ValueTask.FromResult(product);

    return new ValueTask<Product?>(LoadFromDatabaseAsync(key, ct));
}
```

Caller vẫn dùng:

```csharp
var product = await service.GetAsync(key, ct);
```

Nhưng `ValueTask<T>` có semantics khác `Task<T>`: không nên tùy tiện await nhiều lần, gọi `.Result`, hoặc convert qua lại nếu source sử dụng `IValueTaskSource<T>` có pooling/lifetime constraint.

## 4. Practical implementation

Default public API thường nên giữ `Task<T>`:

```csharp
public Task<Order?> GetOrderAsync(Guid id, CancellationToken ct)
    => _db.Orders.FindAsync([id], ct).AsTask();
```

Chỉ cân nhắc `ValueTask<T>` khi profiler cho thấy allocation từ completed async operations là bottleneck thật.

Ví dụ cache abstraction nội bộ:

```csharp
public ValueTask<byte[]?> TryGetAsync(string key, CancellationToken ct)
{
    if (_memory.TryGetValue(key, out byte[]? bytes))
        return ValueTask.FromResult(bytes);

    return new ValueTask<byte[]?>(_distributedCache.GetAsync(key, ct));
}
```

Sau đó benchmark cả cache-hit và cache-miss path.

## 5. Real production scenario

Một pricing service xử lý hàng chục nghìn requests/second. Phần lớn product metadata đã nằm trong process cache. Profiler cho thấy hàng triệu `Task<Product>` allocations từ cache hit, trong khi CPU business logic rất nhỏ.

Sau khi đổi một internal hot-path API sang `ValueTask<T>`, allocation/request giảm rõ ràng. Tuy nhiên team giữ các application/service APIs bình thường là `Task<T>` để tránh lan complexity ra toàn codebase.

Đây là optimization cục bộ, không phải coding standard mới.

## 6. Failure scenario & troubleshooting

**Symptom** → code async trở nên khó hiểu, có intermittent exception hoặc behavior bất thường sau khi pooling/custom awaitable được thêm vào.

**Evidence** → cùng một `ValueTask` bị await nhiều lần, được lưu vào field, hoặc được consume sau lifetime dự kiến.

**Hypothesis** → caller đang coi `ValueTask` như reusable `Task`.

**Diagnosis** → inspect ownership và consumption path; tìm `.AsTask()`, multiple-await, caching `ValueTask` instance.

**Fix** → await một lần; nếu cần chia sẻ operation/re-await, convert một lần thành `Task` ở boundary hoặc dùng `Task<T>` ngay từ API.

**Verification** → concurrency tests và allocation benchmark đều pass.

## 7. Common mistakes

- Đổi mọi `Task<T>` thành `ValueTask<T>` vì nghĩ nó luôn nhanh hơn.
- Dùng `ValueTask<T>` khi operation gần như luôn thực hiện I/O.
- Await cùng instance nhiều lần.
- Lưu `ValueTask<T>` lâu dài trong object state.
- Tối ưu allocation trước khi đo GC/allocation profile.
- Làm public API khó dùng chỉ để tiết kiệm allocation không đáng kể.

## 8. Alternatives

- **`Task<T>`:** default tốt nhất cho đa số async APIs; semantics đơn giản, composability tốt.
- **Synchronous method:** nếu operation thực sự không async.
- **`ValueTask<T>`:** phù hợp hot path có synchronous completion thường xuyên và đã có evidence về allocation.

## 9. Trade-offs

### Advantages

- Có thể tránh `Task` allocation khi hoàn thành synchronously.
- Hữu ích trong low-level/high-throughput libraries.

### Costs / Risks

- Consumption semantics phức tạp hơn.
- Dễ misuse khi operation được chia sẻ/reused.
- Có thể làm API khó maintain mà performance gain rất nhỏ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu `Task<T>` và `ValueTask<T>` đều là awaitable nhưng không có semantics giống hệt nhau.

### Middle

Biết consume `ValueTask<T>` an toàn và không re-await tùy tiện.

### Senior

Biết dùng profiler/benchmark để chứng minh synchronous-completion allocation là vấn đề thật trước khi tối ưu.

### Technical Lead / Architect

Quyết định complexity này chỉ nên tồn tại ở low-level hot path nào, và ngăn micro-optimization lan thành API convention không cần thiết.

## 11. Key takeaway

- `ValueTask<T>` là optimization tool, không phải replacement mặc định cho `Task<T>`.
- Giá trị lớn nhất xuất hiện khi synchronous completion xảy ra thường xuyên.
- Đo allocation trước và sau; giữ API đơn giản nếu gain không đáng kể.

# 2. ASP.NET Core Health Checks: phân biệt liveness, readiness và dependency health để deployment không tự tạo outage

## 1. What is it?

Health check trả lời trạng thái vận hành của application, nhưng “healthy” không chỉ có một nghĩa.

Mental model:

```text
Liveness  -> process có bị kẹt đến mức cần restart không?
Readiness -> instance hiện có nên nhận traffic không?
Dependency health -> downstream/database hiện trạng thế nào?
```

Gộp ba câu hỏi này vào một endpoint duy nhất có thể gây behavior deployment rất nguy hiểm.

## 2. Why does it exist?

Orchestrator/load balancer cần biết instance nào nên nhận traffic. Deployment pipeline cần biết version mới đã startup đúng chưa. Operations cần biết dependency nào đang degrade.

Nếu readiness check gọi 10 dependencies và chỉ một dịch vụ phụ fail, load balancer có thể loại toàn bộ instances khỏi rotation, biến partial outage thành full outage.

Health check tồn tại để automation ra quyết định, nên semantics phải rất rõ.

## 3. How does it work?

ASP.NET Core Health Checks chạy các registered checks và aggregate status:

```text
/health/live
  -> process self-check only

/health/ready
  -> checks cần thiết để serve core traffic

/health/details
  -> dependency diagnostics, thường internal-only
```

Tagging cho phép chọn check theo endpoint.

## 4. Practical implementation

```csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddSqlServer(
        builder.Configuration.GetConnectionString("MainDb")!,
        name: "sql",
        tags: ["ready"]);

var app = builder.Build();

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

Không đưa mọi external dependency vào readiness chỉ vì package có sẵn health-check extension.

## 5. Real production scenario

Một e-commerce API phụ thuộc SQL cho order flow và review provider cho phần reviews. Review provider outage không nên khiến toàn API bị remove khỏi load balancer nếu order/catalog core vẫn phục vụ được.

Readiness chỉ kiểm tra những dependencies thật sự required để instance xử lý traffic cốt lõi. Review dependency được monitor riêng và feature degrade gracefully.

## 6. Failure scenario & troubleshooting

**Symptom** → sau deploy, tất cả instances liên tục bị restart hoặc remove khỏi traffic dù process không crash.

**Evidence** → probe endpoint fail vì một external dependency chậm; liveness/readiness dùng cùng endpoint.

**Hypothesis** → health semantics sai: transient dependency failure đang được diễn giải thành process death.

**Diagnosis** → inspect probe config, timeout, dependency graph và failure policy.

**Fix** → tách liveness/readiness; giảm dependency set; dùng timeout ngắn; degraded feature thay vì fail toàn app khi phù hợp.

**Verification** → fault-inject optional dependency và xác nhận core traffic vẫn được route.

## 7. Common mistakes

- Liveness check gọi database/network.
- Health endpoint thực hiện expensive query.
- Không đặt timeout cho dependency check.
- Trả detailed internal exception công khai ra Internet.
- Coi health check là monitoring thay thế metrics/alerts.
- Dùng một probe cho startup, readiness và liveness mà không hiểu tác động.

## 8. Alternatives

- **Synthetic monitoring:** kiểm tra user journey từ bên ngoài.
- **Metrics/SLO alerts:** đánh giá health theo thời gian và tỷ lệ lỗi.
- **Startup validation:** fail fast với config/dependency bootstrap critical.

Health checks bổ sung các cơ chế này, không thay thế chúng.

## 9. Trade-offs

### Advantages

- Hỗ trợ traffic routing và automated deployment validation.
- Phát hiện instance không sẵn sàng nhanh.

### Costs / Risks

- Probe sai semantics có thể tự tạo outage.
- Dependency checks tạo thêm load.
- Trạng thái binary `healthy/unhealthy` đôi khi quá đơn giản cho degraded systems.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu health endpoint không chỉ là trả `200 OK` tùy ý.

### Middle

Biết đăng ký/tag checks và cấu hình probe endpoint.

### Senior

Phân biệt process failure, dependency degradation và traffic-readiness bằng failure semantics.

### Technical Lead / Architect

Quyết định dependency nào được phép quyết định traffic routing/restart và thiết kế graceful degradation cho phần còn lại.

## 11. Key takeaway

- Liveness và readiness trả lời hai câu hỏi khác nhau.
- Không để optional dependency failure khiến orchestrator giết healthy process.
- Probe là control-plane signal; semantics sai có blast radius lớn.

# 3. EF Core compiled queries: giảm query compilation overhead nhưng chỉ đáng dùng khi query shape thực sự là hot path

## 1. What is it?

EF Core phải xử lý LINQ expression tree để tạo query representation/SQL. EF có internal query cache, nhưng compiled query cho phép chuẩn bị delegate thực thi sẵn cho một query shape cố định.

Mental model:

```text
normal LINQ
expression -> lookup/compile query -> execute SQL

compiled query
prepared delegate -----------------> execute SQL
```

Đây là optimization cho query-processing overhead phía application, không làm database execution plan tự nhiên tốt hơn.

## 2. Why does it exist?

Với API thông thường, network + database latency thường lớn hơn EF query compilation overhead. Nhưng ở high-throughput service với query rất đơn giản và chạy cực nhiều lần, phần expression processing/cache lookup vẫn có thể đo được.

Compiled query tồn tại cho những hot path như vậy.

## 3. How does it work?

EF cung cấp `EF.CompileQuery` và `EF.CompileAsyncQuery`. Application tạo delegate một lần và tái sử dụng với parameters khác nhau.

Query shape phải ổn định. Nếu application tạo expression động phức tạp, compiled query ít phù hợp hơn.

## 4. Practical implementation

```csharp
private static readonly Func<AppDbContext, Guid, IAsyncEnumerable<OrderSummary>>
    GetOrdersByCustomer =
        EF.CompileAsyncQuery(
            (AppDbContext db, Guid customerId) =>
                db.Orders
                    .Where(x => x.CustomerId == customerId)
                    .OrderByDescending(x => x.CreatedAt)
                    .Select(x => new OrderSummary(
                        x.Id,
                        x.Number,
                        x.Status)));
```

Consumer:

```csharp
await foreach (var order in GetOrdersByCustomer(db, customerId).WithCancellation(ct))
{
    // consume
}
```

Benchmark với representative load trước khi thêm abstraction riêng chỉ để quản lý compiled queries.

## 5. Real production scenario

Một authorization service thực hiện query nhỏ theo tenant/user hàng chục nghìn lần/second. Query SQL chỉ mất sub-millisecond do index tốt, nên EF-side overhead bắt đầu chiếm tỷ lệ đáng kể trong profiler.

Compiled query giúp giảm CPU phía service. Nhưng với reporting query mất 150 ms ở database, compiled query gần như không giải quyết vấn đề chính.

## 6. Failure scenario & troubleshooting

**Symptom** → team thêm compiled queries nhưng latency không cải thiện đáng kể.

**Evidence** → trace cho thấy 98% thời gian nằm ở SQL I/O/locks; application CPU rất thấp.

**Hypothesis** → optimization nhắm sai bottleneck.

**Diagnosis** → tách EF client overhead khỏi database execution bằng profiler + DB telemetry.

**Fix** → tối ưu access pattern/index/query nếu bottleneck ở DB; bỏ compiled-query complexity nếu không có gain.

**Verification** → benchmark end-to-end và CPU/request, không chỉ microbenchmark delegate invocation.

## 7. Common mistakes

- Dùng compiled query để chữa slow SQL.
- Compile mọi query trong repository.
- Không benchmark normal EF query cache trước.
- Dùng với highly dynamic query shape rồi tạo hàng loạt variants.
- Tăng code complexity mà gain vài microseconds ở low-volume endpoint.

## 8. Alternatives

- Normal LINQ + EF query cache: default tốt cho đa số systems.
- Raw SQL/Dapper: khi cần kiểm soát query/result mapping chặt hơn.
- Database optimization: khi latency nằm ở execution plan/I/O/locks.

## 9. Trade-offs

### Advantages

- Giảm một phần application-side query preparation overhead.
- Hữu ích ở repeatable hot path throughput rất cao.

### Costs / Risks

- Thêm static/delegate boilerplate.
- Dynamic query flexibility giảm.
- Dễ tối ưu nhầm layer.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu LINQ không trực tiếp là SQL; EF phải translate/prepare query.

### Middle

Biết viết projection/index-friendly query trước khi nghĩ tới compiled query.

### Senior

Dùng profiling để xác định EF query compilation có thực sự nằm trong hot path.

### Technical Lead / Architect

Đặt performance rule: compiled queries chỉ được đưa vào nơi có benchmark/evidence và không làm codebase thành optimization maze.

## 11. Key takeaway

- Compiled query tối ưu EF-side overhead, không sửa bad SQL.
- Chỉ đáng dùng ở stable, high-frequency hot paths.
- End-to-end measurement quan trọng hơn microbenchmark đơn lẻ.

# 4. PostgreSQL partial index: index đúng subset dữ liệu thay vì bắt toàn bộ table trả write cost cho một truy vấn hiếm

## 1. What is it?

Partial index chỉ index những rows thỏa một predicate.

Ví dụ:

```sql
CREATE INDEX ix_orders_pending_created_at
ON orders (created_at)
WHERE status = 'Pending';
```

Nếu chỉ 2% orders đang `Pending`, index nhỏ hơn đáng kể so với index toàn bộ table.

## 2. Why does it exist?

Nhiều systems có access pattern tập trung vào subset nhỏ:

- unprocessed messages;
- active subscriptions;
- soft-deleted = false;
- failed jobs cần retry;
- pending approvals.

Full index bắt database maintain entries cho 100% rows dù query critical chỉ quan tâm vài phần trăm.

Partial index giảm storage/cache/write cost bằng cách index đúng active subset.

## 3. How does it work?

Planner chỉ dùng partial index khi có thể chứng minh query predicate tương thích với index predicate.

```sql
SELECT id, created_at
FROM orders
WHERE status = 'Pending'
ORDER BY created_at
LIMIT 100;
```

Query này phù hợp với index trên `WHERE status = 'Pending'`.

Nếu application viết predicate khác về semantics/planner reasoning, index có thể không được dùng.

## 4. Practical implementation

Trước:

```sql
CREATE INDEX ix_orders_status_created
ON orders(status, created_at);
```

Nếu `Completed` chiếm 98% table và hiếm khi query theo status, cân nhắc:

```sql
CREATE INDEX ix_orders_pending_created
ON orders(created_at)
WHERE status = 'Pending';
```

Kiểm tra bằng:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at
FROM orders
WHERE status = 'Pending'
ORDER BY created_at
LIMIT 100;
```

## 5. Real production scenario

Background worker lấy 100 jobs `Pending` cũ nhất từ table có 80 triệu rows lịch sử. Chỉ khoảng 50k rows còn pending.

Full status index rất lớn và write-heavy. Partial index trên pending subset vừa nhỏ vừa cache-friendly, giúp worker lookup nhanh mà không index toàn bộ historical rows không còn được xử lý nữa.

## 6. Failure scenario & troubleshooting

**Symptom** → partial index tồn tại nhưng planner vẫn seq scan/full index scan.

**Evidence** → `EXPLAIN ANALYZE` không dùng index; query predicate không match hoặc estimate cho rằng scan rẻ hơn.

**Hypothesis** → predicate mismatch, low selectivity, stale statistics hoặc query parameterization làm planner không chứng minh condition.

**Diagnosis** → inspect actual plan, row counts, statistics, exact WHERE clause.

**Fix** → align access pattern/predicate; `ANALYZE`; chỉ giữ index nếu workload chứng minh lợi ích.

**Verification** → compare buffers, rows, latency và write overhead.

## 7. Common mistakes

- Tạo partial index cho predicate thay đổi liên tục.
- Không đo tỷ lệ subset thực tế.
- Nghĩ planner luôn dùng index chỉ vì index nhỏ.
- Tạo nhiều partial indexes theo từng status dẫn đến index sprawl.
- Bỏ qua update cost khi row chuyển vào/ra indexed subset.

## 8. Alternatives

- Composite full index: tốt khi nhiều status đều được query thường xuyên.
- Partitioning: phù hợp data lifecycle/scale khác, không phải replacement đơn giản cho index.
- Archival table: tách hot/cold data nếu operational model cho phép.

## 9. Trade-offs

### Advantages

- Index nhỏ hơn.
- Ít write/storage cost hơn full index tương đương.
- Cache efficiency tốt cho hot subset.

### Costs / Risks

- Chỉ phục vụ query predicate phù hợp.
- Có thể tăng complexity schema/index governance.
- Access pattern thay đổi có thể làm index mất giá trị.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu index không nhất thiết chứa mọi row.

### Middle

Biết viết partial index và verify bằng `EXPLAIN ANALYZE`.

### Senior

Reasoning về selectivity, statistics, write cost và planner behavior.

### Technical Lead / Architect

Quyết định partial index, partitioning hay hot/cold data split dựa workload và lifecycle thay vì theo pattern cookbook.

## 11. Key takeaway

- Partial index rất mạnh khi critical workload chỉ dùng một subset nhỏ, ổn định.
- Planner evidence quyết định index có giá trị hay không.
- Index design phải cân bằng read gain với write/storage cost.

# 5. Elasticsearch bulk indexing, refresh và backpressure: throughput cao không đến từ việc gửi nhiều request song song vô hạn

## 1. What is it?

Bulk API gộp nhiều indexing operations vào ít HTTP requests hơn. `refresh` quyết định khi documents mới trở nên searchable trong Lucene segments.

Mental model:

```text
DB changes
  -> batch
  -> Bulk API
  -> indexing buffers
  -> refresh
  -> searchable segments
```

Bulk throughput phụ thuộc batch size, concurrency, shard capacity, refresh/merge pressure và downstream backpressure.

## 2. Why does it exist?

Gửi một HTTP request cho từng document tạo overhead connection/protocol rất lớn. Nhưng gửi 500 concurrent bulk requests cũng có thể overload Elasticsearch, làm rejection, heap pressure và merge backlog tăng.

Bulk indexing tồn tại để amortize overhead; backpressure tồn tại để producer không chạy nhanh hơn cluster có thể hấp thụ.

## 3. How does it work?

Bulk request chứa nhiều actions. Elasticsearch phân phối operations tới shards. Documents thường chưa searchable ngay lập tức cho tới refresh.

```text
producer rate > indexing capacity
-> queue/rejections
-> retries
-> retry storm
-> latency/heap/merge pressure tăng
```

Hệ thống cần bounded concurrency và retry với backoff cho transient rejection.

## 4. Practical implementation

Pseudo C# flow:

```csharp
const int batchSize = 500;
using var gate = new SemaphoreSlim(4);

foreach (var batch in documents.Chunk(batchSize))
{
    await gate.WaitAsync(ct);

    _ = Task.Run(async () =>
    {
        try
        {
            var response = await elastic.BulkAsync(b =>
                b.IndexMany(batch), ct);

            if (response.Errors)
                HandlePartialFailures(response);
        }
        finally
        {
            gate.Release();
        }
    }, ct);
}
```

Production implementation nên quản lý task lifetime đúng hơn ví dụ rút gọn trên; điểm chính là **bounded** concurrency và xử lý partial failure từng item.

## 5. Real production scenario

Catalog sync phải reindex 15 triệu products. Team tăng concurrency từ 4 lên 100 để “nhanh hơn”. Cluster bắt đầu trả 429/rejections, retries làm traffic tăng thêm và search latency của user production cũng xấu đi.

Giảm concurrency, tăng batch hợp lý, tạm điều chỉnh refresh strategy cho bulk rebuild và dùng alias swap giúp tổng thời gian reindex thực tế giảm.

## 6. Failure scenario & troubleshooting

**Symptom** → indexing lag tăng dù producer gửi nhanh hơn; search latency cũng tăng.

**Evidence** → 429/rejected executions, heap/CPU cao, merge pressure, bulk latency tăng.

**Hypothesis** → producer vượt cluster ingestion capacity.

**Diagnosis** → theo dõi indexing rate, queue/rejections, shard distribution, JVM/merge metrics.

**Fix** → bounded concurrency, exponential backoff + jitter, tune batch size, re-evaluate shard/index design và refresh requirement.

**Verification** → stable ingest rate cao hơn, rejections gần zero và search SLO phục hồi.

## 7. Common mistakes

- Retry toàn bulk request khi chỉ vài items fail.
- `refresh=true` trên mọi write.
- Tăng concurrency vô hạn.
- Không monitor indexing lag từ source-of-truth tới searchable state.
- Dùng Elasticsearch làm transactional source of truth.
- Reindex production index in-place khi alias-based migration đơn giản hơn.

## 8. Alternatives

- Single-document indexing: đủ cho low-volume/event-driven path.
- CDC/stream pipeline: tốt khi cần reliable continuous sync.
- Database search: đủ nếu search requirements đơn giản và scale nhỏ.

## 9. Trade-offs

### Advantages

- Bulk giảm per-request overhead.
- Có thể đạt throughput cao khi batch/concurrency phù hợp.

### Costs / Risks

- Search freshness có độ trễ.
- Partial failure/retry phức tạp.
- Aggressive ingestion có thể ảnh hưởng live search workload.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu bulk là nhiều indexing operations trong một request, không phải atomic transaction lớn.

### Middle

Biết xử lý item-level failure, batch size và retry.

### Senior

Phân tích refresh, merge, shard capacity, 429 và producer backpressure.

### Technical Lead / Architect

Thiết kế ingestion SLO/freshness contract và capacity isolation giữa reindex workload với user-facing search.

## 11. Key takeaway

- Bulk throughput cần bounded concurrency, không phải fan-out vô hạn.
- Refresh/freshness có cost.
- Rejections là backpressure signal, không phải lời mời retry ngay lập tức.

# 6. Modular Monolith: cô lập business modules bằng ownership và dependency boundary thay vì chỉ chia project/folder

## 1. What is it?

Modular Monolith là một deployable application nhưng bên trong được chia thành business modules có ownership và boundary rõ.

```text
Single deployment

Orders Module
  owns Orders data/rules

Billing Module
  owns Billing data/rules

Identity Module
  owns Identity data/rules
```

Điểm cốt lõi không phải số `.csproj`. Một solution có 20 projects nhưng mọi module đọc/chỉnh tables của nhau vẫn là tightly coupled monolith.

## 2. Why does it exist?

Microservices cho isolation mạnh nhưng thêm network failure, deployment coordination, messaging, observability và operational overhead.

Nhiều teams cần business boundaries rõ hơn layered monolith nhưng chưa cần distributed deployment.

Modular Monolith giữ simplicity của single deployment trong khi tạo change isolation đủ tốt để hệ thống lớn lên có kiểm soát.

## 3. How does it work?

Mỗi module sở hữu:

- domain model;
- application use cases;
- persistence/schema ownership;
- public contract/API nội bộ rõ ràng.

Dependency giữa modules đi qua explicit interfaces/messages/contracts, không đi thẳng vào internal repositories/tables.

```text
Orders -> Billing API/contract
Orders -X-> BillingDbContext internal entities
```

Transaction có thể vẫn local trong một database, nhưng ownership boundary phải rõ để tránh shared-data coupling.

## 4. Practical implementation

Một structure có thể là:

```text
Modules/
  Orders/
    Orders.Application
    Orders.Domain
    Orders.Infrastructure
  Billing/
    Billing.Application
    Billing.Domain
    Billing.Infrastructure
```

Quan trọng hơn structure là enforcement. Ví dụ Billing expose:

```csharp
public interface IBillingGateway
{
    Task<PaymentStatus> GetPaymentStatusAsync(
        Guid orderId,
        CancellationToken ct);
}
```

Orders không reference Billing EF entities hoặc query Billing tables trực tiếp.

## 5. Real production scenario

Một SaaS có Orders, Billing, Documents và Notifications. Team 8 người deploy cùng một application. Microservices sẽ tạo operational burden quá sớm.

Modular Monolith cho phép mỗi area có module owner, migrations và contracts riêng. Sau vài năm, Notifications có scaling/reliability requirement khác hẳn và có thể được extract dễ hơn vì dependency đã được kiểm soát.

## 6. Failure scenario & troubleshooting

**Symptom** → thay schema Billing làm Orders, Reports và Admin cùng vỡ dù “đã modularize”.

**Evidence** → nhiều modules reference cùng EF entities/tables; shared `Common` project chứa domain logic của mọi nơi.

**Hypothesis** → module boundary chỉ tồn tại ở folders, không tồn tại ở data/dependency ownership.

**Diagnosis** → map references, database access và cross-module write paths.

**Fix** → đặt ownership, internalize implementation, expose contract nhỏ và migrate cross-module access dần.

**Verification** → module test/build rules ngăn dependency cấm và schema change chỉ cần consumer-facing contract compatibility.

## 7. Common mistakes

- Gọi solution nhiều projects là Modular Monolith.
- Shared database = mọi module được query mọi table.
- `SharedKernel` trở thành nơi chứa mọi thứ.
- Thêm MediatR rồi nghĩ boundary đã được giải quyết.
- Thiết kế module quá nhỏ như microservice giả lập.
- Ép eventual consistency dù local transaction đơn giản là đủ.

## 8. Alternatives

- Layered Monolith: đơn giản hơn khi domain nhỏ.
- Microservices: hợp lý khi cần independent deployment/scaling/ownership thực sự.
- Hexagonal/Clean Architecture: giải quyết dependency structure khác; có thể dùng bên trong module nhưng không bắt buộc.

## 9. Trade-offs

### Advantages

- Một deployment, transaction và debug model đơn giản hơn distributed system.
- Boundary rõ giúp change isolation và future extraction.

### Costs / Risks

- Boundary cần discipline/enforcement.
- Shared process vẫn có resource/failure coupling.
- Không cung cấp independent scaling/deployment theo module.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu module là business boundary, không phải folder đẹp.

### Middle

Biết implement use case mà không bypass module public contract.

### Senior

Thiết kế data ownership, dependency direction và cross-module transaction hợp lý.

### Technical Lead / Architect

Quyết định khi nào monolith đủ tốt, module nào thật sự cần extraction, và không trả operational tax của microservices trước khi có requirement.

## 11. Key takeaway

- Modular Monolith là boundary/ownership discipline trong một deployable unit.
- Shared database không đồng nghĩa shared ownership.
- Microservices chỉ nên xuất hiện khi independent deployment/scaling/failure isolation tạo giá trị thật.

# 7. Azure Container Apps revisions và scaling: deploy an toàn khi hiểu revision traffic, cold start và statelessness

## 1. What is it?

Azure Container Apps chạy containerized workloads trên managed platform. Revision đại diện cho một immutable version của app configuration/container revision có thể nhận traffic độc lập.

Mental model:

```text
Revision A (v1) <- 90% traffic
Revision B (v2) <- 10% traffic
```

Điều này hỗ trợ gradual traffic shift/rollback mà không cần tự vận hành Kubernetes cluster.

## 2. Why does it exist?

Teams muốn container deployment, autoscaling và revision traffic management nhưng không muốn sở hữu full Kubernetes control plane/operations.

Revisions giúp giảm deployment risk. Autoscaling giúp match capacity theo load, nhưng yêu cầu application stateless hoặc externalize state đúng cách.

## 3. How does it work?

Một revision được tạo khi revision-scope properties thay đổi. Platform có thể route traffic theo weights. Scale rules quyết định replica count dựa HTTP/concurrency/events tùy workload.

```text
request spike
-> scale rule triggers
-> new replicas start
-> image pull + app startup
-> readiness
-> receive traffic
```

Nếu scale-to-zero được dùng, request đầu tiên sau idle có thể chịu cold-start latency.

## 4. Practical implementation

Application container nên:

- expose health/readiness endpoint;
- đọc configuration từ environment/secrets;
- không giữ session critical trong local memory/filesystem;
- handle SIGTERM/CancellationToken cho graceful shutdown;
- dùng external durable storage nếu cần state.

Deployment strategy:

```text
Deploy revision B
-> validate health
-> send 5–10% traffic
-> compare errors/latency
-> increase traffic
-> deactivate A after confidence
```

## 5. Real production scenario

Một notification API deploy version mới có bug serialization chỉ xảy ra với 3% payloads. Nếu switch 100% traffic ngay, error rate production tăng mạnh.

Revision split 10% giúp detect issue qua telemetry; traffic được đưa lại revision cũ trong vài phút mà không rebuild artifact.

## 6. Failure scenario & troubleshooting

**Symptom** → scale-out xảy ra nhưng user vẫn thấy latency spike đầu burst.

**Evidence** → replica startup time cao, image lớn, app startup chạy migrations/cache warming dài.

**Hypothesis** → cold-start/startup path chậm hơn traffic growth.

**Diagnosis** → measure image pull, container start, readiness duration và scale trigger delay.

**Fix** → giữ minimum replicas cho latency-sensitive workload, giảm image/startup cost, không chạy heavyweight migration mỗi replica startup.

**Verification** → burst test và compare p95/p99 trước/sau.

## 7. Common mistakes

- Lưu uploaded files trên local container filesystem.
- Dùng in-memory session làm correctness dependency khi scale-out.
- Scale-to-zero cho workload yêu cầu low-latency first request.
- Chạy DB migrations từ mọi replica startup.
- Roll forward 100% mà không có health/telemetry gate.
- Nghĩ managed platform nghĩa không cần capacity/cost reasoning.

## 8. Alternatives

- Azure App Service: đơn giản cho web apps không cần container-centric workflow mạnh.
- AKS: nhiều control hơn nhưng operational complexity cao hơn.
- Azure Functions: tốt cho event-driven/serverless execution pattern khác.
- VM/IIS: phù hợp một số legacy requirements nhưng ít managed scaling hơn.

## 9. Trade-offs

### Advantages

- Managed container runtime và autoscaling.
- Revision traffic split hỗ trợ safer rollout.
- Ít operational burden hơn AKS.

### Costs / Risks

- Cold start và scaling behavior cần hiểu.
- Platform abstraction giới hạn low-level control.
- Scale-out làm hidden local state bug lộ rõ.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu container instance có thể bị tạo/xóa và local state không bền.

### Middle

Biết deploy revision, configure health và externalize state.

### Senior

Reasoning về autoscale, cold start, rollout telemetry và rollback.

### Technical Lead / Architect

Chọn Container Apps vs App Service vs AKS dựa workload/control/operations, không dựa trend.

## 11. Key takeaway

- Revisions giúp rollout/rollback theo traffic có kiểm soát.
- Autoscaling chỉ an toàn khi app stateless đúng nghĩa.
- Startup time là một phần của production latency khi scale-out.

# 8. OpenTelemetry metrics cardinality: telemetry có thể làm observability đắt và chậm nếu label dimension mất kiểm soát

## 1. What is it?

Metric thường gồm tên + labels/attributes:

```text
http.server.duration{
  method="GET",
  route="/orders/{id}",
  status="200"
}
```

Mỗi tổ hợp label values tạo một time series. Cardinality là số lượng distinct combinations.

Nếu label chứa `userId`, `orderId`, raw URL hoặc trace ID, số series có thể tăng gần như không giới hạn.

## 2. Why does it exist?

Metrics được tối ưu cho aggregation: error rate theo endpoint, latency theo region, queue depth theo queue.

Chúng không phù hợp để lưu identity của từng request. High-cardinality data khiến backend telemetry tốn memory/storage/query cost và có thể throttle/drop data.

## 3. How does it work?

Ví dụ:

```text
route = 50 values
status = 5 values
region = 4 values
=> tối đa khoảng 1,000 combinations
```

Thêm `userId` có 2 triệu values:

```text
50 * 5 * 4 * 2,000,000
```

Series explosion trở thành operational problem.

Logs/traces phù hợp hơn cho per-request identifiers.

## 4. Practical implementation

Good metric dimensions:

```csharp
meter.CreateCounter<long>("orders.processed")
    .Add(1,
        new("result", result),
        new("region", region));
```

Bad:

```csharp
counter.Add(1,
    new("order.id", order.Id),
    new("user.id", user.Id));
```

Dùng route template `/orders/{id}` thay raw path `/orders/839127`.

## 5. Real production scenario

Team thêm `customer_id` vào every HTTP metric để “debug dễ hơn”. Application Insights/metrics backend ingest volume tăng đột biến, dashboard query chậm và bill telemetry tăng mạnh.

Sau khi bỏ high-cardinality labels, dùng trace/log correlation cho customer-specific investigation và giữ metrics cho aggregate health, chi phí giảm mà observability tốt hơn.

## 6. Failure scenario & troubleshooting

**Symptom** → metrics backend throttle, bill tăng, dashboards chậm hoặc missing series.

**Evidence** → distinct label value count tăng cực nhanh; raw URL/user IDs xuất hiện trong dimensions.

**Hypothesis** → cardinality explosion.

**Diagnosis** → inventory metric instruments/attributes và top unique values.

**Fix** → normalize route, whitelist dimensions, drop/rewrite attributes ở SDK/collector khi cần.

**Verification** → active series/ingest volume giảm trong khi SLI dashboards vẫn đủ thông tin.

## 7. Common mistakes

- Gắn request ID/trace ID vào metric.
- Dùng exception message làm label.
- Dùng raw URL chứa IDs.
- Thu thập mọi attribute vì “storage rẻ”.
- Dùng metrics thay logs/traces cho forensic debugging.
- Không đặt telemetry budget/attribute conventions.

## 8. Alternatives

- Logs: high-detail events/search.
- Traces: per-request causal path.
- Exemplars/correlation: nối aggregate metric tới representative trace khi platform hỗ trợ.

## 9. Trade-offs

### Advantages

- Metrics cardinality thấp cho query/alert rất hiệu quả.
- Aggregate SLI/SLO rõ ràng và cheap hơn request-level telemetry.

### Costs / Risks

- Ít detail hơn logs/traces.
- Dimension quá ít cũng làm metric khó phân tích theo failure domain.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu label combination tạo series riêng.

### Middle

Biết chọn route/status/region thay vì IDs ngẫu nhiên.

### Senior

Thiết kế metrics, logs và traces theo vai trò khác nhau; kiểm soát cardinality/cost.

### Technical Lead / Architect

Đặt telemetry schema, budget, retention và guardrails toàn platform để observability scale cùng traffic.

## 11. Key takeaway

- Metrics dùng cho aggregate dimensions hữu hạn, không dùng cho per-request identity.
- High cardinality là reliability/cost issue của telemetry platform.
- Dùng logs/traces để giữ chi tiết cần điều tra.

# 9. Secure file upload trong ASP.NET Core: validation, storage isolation và malware risk quan trọng hơn việc kiểm tra extension

## 1. What is it?

Secure file upload là một trust-boundary design. File từ client là untrusted bytes, bất kể filename, MIME type hoặc extension client gửi lên.

Mental model:

```text
Untrusted client bytes
-> size/content validation
-> generated safe identity
-> isolated storage
-> scanning/processing
-> controlled serving
```

`invoice.pdf` không chứng minh file là PDF an toàn.

## 2. Why does it exist?

Upload feature có thể dẫn tới:

- arbitrary executable/script storage;
- path traversal;
- oversized-file DoS;
- malware distribution;
- parser vulnerabilities;
- XSS nếu active content được serve cùng origin;
- sensitive file exposure.

Vì vậy validation không thể chỉ là `.EndsWith(".pdf")`.

## 3. How does it work?

Server kiểm soát:

1. maximum request/file size;
2. allowed content types/formats;
3. generated storage name;
4. storage outside executable web root;
5. authorization metadata;
6. malware/content scanning khi risk yêu cầu;
7. safe content-disposition/serving path.

Original filename chỉ nên là metadata đã sanitize cho display.

## 4. Practical implementation

Ví dụ streaming đơn giản hóa:

```csharp
app.MapPost("/documents", async (
    IFormFile file,
    IFileStore store,
    CancellationToken ct) =>
{
    if (file.Length is <= 0 or > 10 * 1024 * 1024)
        return Results.BadRequest("Invalid file size");

    var allowed = new HashSet<string>(StringComparer.OrdinalIgnoreCase)
    {
        "application/pdf"
    };

    if (!allowed.Contains(file.ContentType))
        return Results.BadRequest("Unsupported media type");

    var storageKey = Guid.NewGuid().ToString("N");

    await using var stream = file.OpenReadStream(10 * 1024 * 1024);
    await store.SaveAsync(storageKey, stream, ct);

    return Results.Accepted(value: new { id = storageKey });
});
```

Production cần content-signature validation/scanning phù hợp risk; MIME từ client không phải security proof.

## 5. Real production scenario

HR portal cho upload CV/PDF. Nếu file được lưu trực tiếp trong `wwwroot/uploads/{originalName}`, attacker có thể thử active content, filename collision/path tricks hoặc khiến app serve file dưới trusted origin.

Tốt hơn: private Blob Storage, generated key, metadata trong DB, malware scan pipeline, download endpoint kiểm tra authorization hoặc short-lived SAS phù hợp.

## 6. Failure scenario & troubleshooting

**Symptom** → application memory tăng mạnh và request workers bị giữ lâu khi nhiều users upload files lớn.

**Evidence** → buffering lớn, request body copied vào memory/temp disk, upload endpoint không có size/concurrency limit.

**Hypothesis** → upload path không streaming/bounded.

**Diagnosis** → inspect request size, buffering behavior, memory/temp storage metrics.

**Fix** → direct-to-Blob upload hoặc streaming, enforce limits, bounded concurrent processing, async scan pipeline.

**Verification** → load test large uploads; memory ổn định và malicious/oversized input bị reject đúng.

## 7. Common mistakes

- Tin extension hoặc `Content-Type` client gửi.
- Dùng original filename làm filesystem path.
- Lưu upload vào executable/public web root.
- Đọc toàn file vào `byte[]` không giới hạn.
- Quên authorization khi download.
- Log file content hoặc sensitive metadata.
- Scan file nhưng vẫn serve trước khi scan complete.

## 8. Alternatives

- Direct upload tới Azure Blob bằng short-lived scoped SAS.
- Application-proxied streaming khi cần kiểm soát synchronous validation.
- External secure file processing/scanning service nếu organization có platform chung.

## 9. Trade-offs

### Advantages

- Storage isolation giảm blast radius.
- Direct cloud upload giảm application bandwidth/memory pressure.

### Costs / Risks

- Scanning/quarantine pipeline tăng latency/complexity.
- SAS/lifecycle/access control cần thiết kế cẩn thận.
- Content validation hoàn hảo là khó; risk-based controls cần nhiều lớp.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu file upload là untrusted input, filename không đáng tin.

### Middle

Implement size/type limits, generated names và protected storage.

### Senior

Thiết kế streaming, quarantine, scanning, authorization và cloud upload boundary.

### Technical Lead / Architect

Chọn threat model và controls tương ứng business data/risk; tránh overengineering nhưng không để upload trở thành arbitrary-content execution path.

## 11. Key takeaway

- Extension/MIME chỉ là signal, không phải security proof.
- Tách untrusted content khỏi executable/public application surface.
- Bounded streaming + authorization + scanning theo risk là nền tảng production-safe upload.

# 10. Vue reactivity và async race conditions: UI đúng ở happy path vẫn có thể hiển thị stale data khi request hoàn thành sai thứ tự

## 1. What is it?

Vue reactivity tự động cập nhật UI khi reactive state thay đổi. Nhưng reactivity không tự giải quyết ordering của asynchronous requests.

Mental model:

```text
User chọn A -> Request A bắt đầu
User chọn B -> Request B bắt đầu
Request B hoàn thành -> UI = B
Request A hoàn thành sau -> UI = A   (stale/wrong)
```

UI framework phản ứng đúng với assignment cuối cùng; bug nằm ở async coordination.

## 2. Why does it exist?

Search-as-you-type, filters, route changes và dependent dropdowns tạo nhiều overlapping requests. Network latency không đảm bảo request bắt đầu trước sẽ hoàn thành trước.

Nếu component chỉ `await fetch()` rồi gán state, stale response có thể overwrite dữ liệu mới hơn.

## 3. How does it work?

`watch`/reactive effects chạy khi dependencies thay đổi. Mỗi run có thể launch async work.

Để giữ correctness, component cần một trong các strategy:

- cancel previous request;
- generation/request token;
- library quản lý query keys/cache/staleness;
- server/API idempotency nếu có write side effect.

## 4. Practical implementation

Vue example với `AbortController`:

```ts
const selectedCustomerId = ref<string | null>(null)
const orders = ref<Order[]>([])

watch(selectedCustomerId, async (id, _, onCleanup) => {
  if (!id) {
    orders.value = []
    return
  }

  const controller = new AbortController()
  onCleanup(() => controller.abort())

  try {
    const response = await fetch(`/api/customers/${id}/orders`, {
      signal: controller.signal
    })

    if (!response.ok) throw new Error(`HTTP ${response.status}`)
    orders.value = await response.json()
  } catch (error) {
    if ((error as DOMException).name !== 'AbortError')
      throw error
  }
})
```

Cleanup hủy request cũ khi dependency đổi.

## 5. Real production scenario

Admin screen có customer search. User click Customer A rồi nhanh chóng Customer B. A query ở DB chậm hơn nên response A về sau B và UI hiển thị orders của A dưới header Customer B.

Đây không chỉ là UX bug; nếu action tiếp theo dùng stale entity ID, nó có thể trở thành correctness/security concern.

## 6. Failure scenario & troubleshooting

**Symptom** → UI thỉnh thoảng hiển thị dữ liệu “nhảy ngược” khi user thao tác nhanh hoặc network chậm.

**Evidence** → DevTools Network cho thấy overlapping requests hoàn thành khác thứ tự; component không cancel/version responses.

**Hypothesis** → stale response overwrite latest state.

**Diagnosis** → log request key/generation và state assignment order.

**Fix** → AbortController, request sequence token hoặc query library có stale-key semantics.

**Verification** → throttle network trong DevTools, thao tác nhanh và xác nhận stale requests không update state.

## 7. Common mistakes

- Nghĩ `await` đảm bảo toàn component xử lý requests theo thứ tự.
- Dùng một global `loading` boolean cho nhiều concurrent requests.
- Không cleanup watcher/effect.
- Catch mọi error rồi hiển thị “server lỗi” kể cả AbortError.
- Client-side race protection cho GET nhưng bỏ qua write idempotency/concurrency phía server.

## 8. Alternatives

- Request generation counter: chỉ response mới nhất được commit.
- TanStack Query/Vue Query: quản lý query key, cache, cancellation/staleness tốt hơn cho data-heavy UI.
- Debounce: giảm request count nhưng không hoàn toàn thay cancellation/order handling.

## 9. Trade-offs

### Advantages

- Cancellation giảm unnecessary work và stale update risk.
- Query libraries chuẩn hóa caching/retry/loading/error state.

### Costs / Risks

- Thêm state/concurrency complexity.
- Debounce tăng input latency.
- Client cancellation không đảm bảo server đã dừng work nếu downstream không propagate cancellation.

## 10. Junior → Middle → Senior → Technical Lead

### Junior

Hiểu reactive state update không có nghĩa async operations được serialize.

### Middle

Biết dùng `watch`, cleanup và AbortController đúng lifecycle.

### Senior

Thiết kế UI request concurrency cùng API cancellation/idempotency semantics.

### Technical Lead / Architect

Chọn convention/query library và đảm bảo frontend/backend cùng có contract rõ về cancellation, stale data và write concurrency.

## 11. Key takeaway

- Network completion order không bằng request start order.
- Reactive framework không tự bảo vệ stale async responses.
- Test với network throttling và rapid user interactions, không chỉ happy-path local network.
