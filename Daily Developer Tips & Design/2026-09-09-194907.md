# Daily Developer Tips & Design — 2026-09-09

## 🛠 Developer Tips & Tricks

### Tip 1 — Validate `Options` ngay lúc startup thay vì đợi request đầu tiên mới lỗi

**Mẹo:**
Với ASP.NET Core/.NET application có configuration quan trọng như endpoint, timeout, feature settings hoặc external-service credentials, dùng Options validation và `ValidateOnStart()` để fail fast khi application khởi động.

**Tại sao hữu ích:**
Nếu configuration sai chỉ được đọc khi một request hiếm chạm vào code path đó, deployment có thể nhìn như thành công nhưng vài giờ sau mới phát sinh 500. Startup validation biến configuration error thành deployment signal rõ ràng hơn.

**Ví dụ:**
```csharp
builder.Services
    .AddOptions<PaymentOptions>()
    .BindConfiguration("Payment")
    .Validate(x => Uri.TryCreate(x.BaseUrl, UriKind.Absolute, out _),
        "Payment:BaseUrl must be an absolute URI")
    .Validate(x => x.TimeoutSeconds is > 0 and <= 30,
        "Payment:TimeoutSeconds must be between 1 and 30")
    .ValidateOnStart();
```

**Lưu ý:**
Không đưa validation cần gọi database hoặc external API vào startup validator theo phản xạ. Configuration validation nên nhanh và deterministic; dependency availability nên được phản ánh qua health/readiness checks phù hợp.

### Tip 2 — Với EF Core, projection thường tốt hơn `Include` khi API chỉ cần một read model nhỏ

**Mẹo:**
Nếu endpoint chỉ cần vài field để trả DTO, dùng `Select` projection trực tiếp từ query thay vì `Include` cả aggregate/entity graph rồi map trong memory.

**Tại sao hữu ích:**
Projection cho phép EF Core chỉ select những column cần thiết, giảm network payload, materialization và change-tracking cost. Nó cũng làm read contract rõ hơn và tránh vô tình tải collection lớn.

**Ví dụ:**
```csharp
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderListItem(
        x.Id,
        x.CreatedAt,
        x.Status,
        x.Lines.Sum(l => l.Quantity * l.UnitPrice)))
    .ToListAsync(ct);
```

**Lưu ý:**
Đừng projection quá phức tạp mà không kiểm tra SQL được generate. Một expression nhìn gọn trong C# vẫn có thể tạo SQL đắt; luôn xem query plan/SQL khi latency bất thường.

### Tip 3 — Với SQL Server filtered index, index theo tập dữ liệu “nóng” thay vì toàn bảng khi query pattern phù hợp

**Mẹo:**
Nếu phần lớn query production chỉ truy cập một subset nhỏ như `Status = 'Pending'`, cân nhắc filtered index thay vì index toàn bộ table.

**Tại sao hữu ích:**
Filtered index nhỏ hơn, ít tốn storage và write maintenance hơn full index, đồng thời optimizer có thể seek hiệu quả cho workload tập trung vào subset đó.

**Ví dụ:**
```sql
CREATE INDEX IX_Orders_Pending_CreatedAt
ON Orders (CreatedAt, Id)
INCLUDE (CustomerId, Total)
WHERE Status = 'Pending';
```

Một worker xử lý pending orders theo `CreatedAt` có thể hưởng lợi rõ rệt nếu pending chỉ chiếm tỷ lệ nhỏ của bảng.

**Lưu ý:**
Predicate của query phải tương thích với filter để optimizer dùng index tốt. Nếu distribution thay đổi và phần lớn rows trở thành `Pending`, lợi ích có thể giảm; kiểm tra statistics, execution plan và write cost định kỳ.

### Tip 4 — Dùng `git reflog` để cứu branch/commit tưởng đã mất sau reset hoặc rebase

**Mẹo:**
Khi lỡ `reset --hard`, rebase sai hoặc xóa branch local, kiểm tra `git reflog` trước khi kết luận commit đã mất.

**Tại sao hữu ích:**
Git reflog ghi lại lịch sử vị trí mà `HEAD` và refs local từng trỏ tới. Commit không còn reachable từ branch hiện tại vẫn thường có thể được khôi phục trong thời gian reflog/object chưa bị garbage-collected.

**Ví dụ:**
```bash
git reflog
# tìm commit trước thao tác sai

git branch rescue/old-state <commit-sha>
```

Sau đó có thể diff/cherry-pick hoặc tiếp tục từ branch rescue.

**Lưu ý:**
Reflog chủ yếu là local; nó không phải backup chiến lược. Không dùng nó thay cho push remote, branch protection hoặc backup repository quan trọng.

### Tip 5 — Với React/Vue search UI, debounce không thay thế cancellation và stale-response protection

**Mẹo:**
Debounce giúp giảm số request khi user gõ liên tục, nhưng vẫn cần hủy request cũ hoặc kiểm tra request identity nếu nhiều request đã được gửi.

**Tại sao hữu ích:**
Hai request có thể hoàn thành ngược thứ tự. Debounce chỉ giảm tần suất gửi, không đảm bảo response mới nhất về sau cùng. Nếu không bảo vệ, UI có thể hiển thị kết quả cho query cũ.

**Ví dụ:**
```text
User nhập: "redis"
request A: "red"   -> 450 ms
request B: "redis" -> 120 ms

B hoàn thành trước
A hoàn thành sau -> overwrite UI nếu không kiểm tra
```

Kết hợp debounce với `AbortController`, cancellation token tương đương hoặc sequence/request ID.

**Lưu ý:**
Cancellation phía client không đảm bảo backend rollback side effect. Pattern này phù hợp nhất cho read/search request; mutation cần idempotency/concurrency semantics riêng.

## 🧠 Software Design

### Design 1 — Không giữ database transaction mở trong lúc gọi external API

**Khái niệm:**
Database transaction nên bao quanh phần thay đổi state cần atomicity trong database, không nên mặc định kéo dài xuyên qua HTTP call hoặc dependency chậm bên ngoài.

**Vấn đề nó giải quyết:**
Một transaction đang giữ lock rồi chờ external API 5–10 giây làm tăng lock duration, connection usage và deadlock/blocking risk. Nếu dependency timeout, transaction dài còn làm giảm throughput toàn hệ thống.

**Ví dụ thực tế:**
Không tốt:
```text
BEGIN TRANSACTION
update Order
call Payment API 8s
update PaymentStatus
COMMIT
```

Một thiết kế khác có thể commit local intent trước, dùng state machine/Outbox và xử lý payment ở bước riêng với compensation/idempotency rõ ràng.

**Trade-off:**
Transaction ngắn cải thiện concurrency và reliability nhưng có thể chuyển bài toán sang eventual consistency, recovery và compensation. Với một số workflow đơn giản, synchronous call vẫn hợp lý nếu không giữ lock/database transaction trong lúc chờ.

**Middle → Senior insight:**
Middle developer cần nhận biết transaction scope và tránh đặt network I/O bên trong transaction một cách vô thức. Senior / Technical developer phải xác định invariant nào cần ACID local, state chuyển tiếp nào chấp nhận được và cơ chế recovery khi external step thất bại.

### Design 2 — RBAC vs ABAC cho authorization policy

**Khái niệm:**
RBAC cấp quyền dựa trên role như `Admin`, `Editor`; ABAC quyết định dựa trên attributes/context như tenant, resource owner, region, classification hoặc trạng thái resource.

**Vấn đề nó giải quyết:**
Khi policy chỉ là “Admin được làm X”, RBAC đơn giản và dễ vận hành. Nhưng nếu rule là “Editor chỉ sửa document thuộc tenant của mình, còn document Archived thì chỉ Owner được restore”, role đơn thuần nhanh chóng tạo role explosion.

**Ví dụ thực tế:**
```text
RBAC:
Role=SupportAgent -> được mở support console

ABAC/policy:
SupportAgent
AND userConsent=true
AND resource.Module in grantedModules
AND grant.ExpiresAt > now
```

Policy có thể kết hợp role với resource/context thay vì tạo `SupportAgentWithDocumentAccess24h` như một role riêng.

**Trade-off:**
RBAC dễ hiểu, audit và quản trị nhưng kém linh hoạt cho rule giàu context. ABAC diễn tả business policy tốt hơn nhưng khó debug, test và explain nếu rule phân tán hoặc quá động.

**Middle → Senior insight:**
Middle developer cần implement authorization ở server boundary và test cả allow/deny cases. Senior / Technical developer phải chọn policy model cân bằng giữa expressiveness, auditability, performance và khả năng quản trị—không biến mọi điều kiện thành role hoặc mọi permission thành một policy engine phức tạp.

### Design 3 — Materialized Read Model vs live aggregation cho dashboard

**Khái niệm:**
Live aggregation tính dữ liệu trực tiếp từ transactional tables mỗi request. Materialized read model/precomputed projection lưu sẵn shape tối ưu cho read path và cập nhật theo batch, event hoặc incremental processing.

**Vấn đề nó giải quyết:**
Dashboard lớn có thể cần join nhiều bảng, group hàng triệu rows và tính nhiều KPI. Nếu thực hiện mọi phép aggregate trên mỗi page load, latency và database load sẽ tăng nhanh theo data volume và concurrency.

**Ví dụ thực tế:**
```text
Transactional tables:
Orders, OrderLines, Payments

Projection:
DailyTenantRevenue
- TenantId
- Date
- Revenue
- OrderCount
- RefundTotal
```

Dashboard đọc projection thay vì scan lại toàn bộ transaction history.

**Trade-off:**
Live query luôn gần source-of-truth và đơn giản hơn về consistency, nhưng có thể đắt. Materialized model tăng read performance và isolation nhưng thêm synchronization, rebuild/backfill, stale-data semantics và monitoring cho projection pipeline.

**Middle → Senior insight:**
Middle developer cần đo query plan, latency và data volume trước khi precompute. Senior / Technical developer phải xác định freshness SLA, rebuild strategy, source-of-truth và failure recovery để read model không trở thành dữ liệu “nhanh nhưng không đáng tin”.
