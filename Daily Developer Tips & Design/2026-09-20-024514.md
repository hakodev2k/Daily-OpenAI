# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — Keyset pagination ổn định hơn `OFFSET` trên tập dữ liệu lớn

**Mẹo:**
Với API duyệt tuần tự qua dữ liệu lớn, cân nhắc keyset pagination dựa trên một sort key ổn định như `(CreatedAt, Id)` thay vì tăng `OFFSET` theo page number.

**Tại sao hữu ích:**
`OFFSET` lớn buộc database bỏ qua ngày càng nhiều rows trước khi trả page tiếp theo. Keyset dùng giá trị cuối của page trước làm boundary, cho phép optimizer seek vào vùng dữ liệu cần đọc nếu index phù hợp.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Composite index theo cùng thứ tự sort giúp query tránh scan phần lớn lịch sử.

**Lưu ý:**
Keyset không phù hợp nếu UX bắt buộc nhảy trực tiếp tới “page 317”. Sort key phải deterministic; chỉ dùng `CreatedAt` khi nhiều rows có cùng timestamp có thể làm mất hoặc lặp item.

### Tip 2 — Azure Service Bus lock expiry có thể tạo duplicate processing ngay khi handler vẫn đang chạy

**Mẹo:**
Với handler xử lý lâu, theo dõi message lock duration, auto lock renewal và processing time; đừng giả định một message đang chạy thì broker sẽ không giao lại cho consumer khác.

**Tại sao hữu ích:**
Trong Peek-Lock mode, consumer chỉ giữ quyền xử lý trong thời gian lock. Nếu lock hết hạn trước khi complete, message có thể được redeliver trong khi attempt đầu vẫn còn side effect đang chạy.

**Ví dụ:**
Một image-processing handler thường mất 8 phút nhưng lock/renewal chỉ bao phủ 5 phút. Telemetry cho thấy cùng `MessageId` xuất hiện trên hai instances. Giải pháp cần xem cả lock renewal, thời gian xử lý và idempotency của write cuối.

**Lưu ý:**
Tăng lock duration không biến delivery thành exactly-once. Process crash quanh thời điểm side effect/complete vẫn tạo duplicate window; consumer quan trọng phải idempotent.

### Tip 3 — File upload phải kiểm tra content, không tin extension hay `Content-Type`

**Mẹo:**
Với ASP.NET Core upload endpoint, coi filename, extension và client-supplied `Content-Type` là dữ liệu không đáng tin. Áp size limit, generated storage name, allowlist type và validation/scanning phù hợp trước khi file được phục vụ hoặc xử lý.

**Tại sao hữu ích:**
Attacker có thể đổi tên executable/script thành `.jpg` hoặc gửi MIME header giả. Nếu application lưu file dưới web root với tên do user kiểm soát, upload có thể trở thành đường dẫn tới XSS, overwrite hoặc malware distribution.

**Ví dụ:**
API nhận avatar, giới hạn kích thước, tạo blob name bằng server-generated ID, kiểm tra signature/decoder của định dạng ảnh và chỉ đánh dấu file usable sau validation pipeline.

**Lưu ý:**
Magic-byte checking cũng không phải antivirus. Với tài liệu từ nguồn không tin cậy, cần threat model cho malware scanning, archive bombs, image parser vulnerabilities và quyền truy cập storage.

### Tip 4 — Core Web Vitals regression cần trace về resource gây layout/render delay

**Mẹo:**
Khi Lighthouse hoặc real-user telemetry báo LCP/CLS xấu đi, dùng browser DevTools Performance/Network để tìm resource, render-blocking work hoặc layout shift cụ thể thay vì chỉ “minify thêm JavaScript”.

**Tại sao hữu ích:**
Core Web Vitals là symptom ở user experience. LCP có thể bị backend TTFB, image tải muộn hoặc main-thread work kéo dài; CLS có thể đến từ image/banner không reserve kích thước. Mỗi nguyên nhân cần fix khác nhau.

**Ví dụ:**
Product page có CLS tăng sau khi thêm recommendation banner. Performance trace cho thấy banner được inject sau render mà container không reserve space; đặt kích thước/layout contract đúng giải quyết nguyên nhân thay vì tối ưu bundle không liên quan.

**Lưu ý:**
Lighthouse lab score không thay thế field data. Device, network và traffic thực có distribution khác; ưu tiên percentile và segment có user impact rõ.

### Tip 5 — AI code review phải kiểm chứng claim bằng source và diff

**Mẹo:**
Khi dùng AI coding agent review PR, yêu cầu mỗi finding trỏ tới code path/diff cụ thể và tự kiểm chứng API/version/configuration trong repository trước khi coi finding là defect.

**Tại sao hữu ích:**
AI có thể suy luận từ pattern phổ biến nhưng repository dùng custom middleware, framework version hoặc invariant khác. Finding nghe hợp lý nhưng không grounded tạo review noise và làm team mất thời gian.

**Ví dụ:**
Agent cảnh báo endpoint thiếu authorization. Trước khi tạo blocker, kiểm tra route group, global fallback policy và integration tests; nếu authorization được áp ở boundary khác, finding phải bị loại thay vì lặp lại như “best practice”.

**Lưu ý:**
Test pass cũng không chứng minh finding sai hoặc code đúng. Security, concurrency và performance issue có thể thiếu coverage; verification cần kết hợp source, runtime behavior và requirement.

## 🧠 Software Design

### Design 1 — Consumer-driven contract testing cho services deploy độc lập

**Khái niệm:**
Consumer-driven contract test ghi lại những interaction mà consumer thực sự phụ thuộc và kiểm tra provider vẫn đáp ứng contract đó. Nó tập trung vào compatibility giữa các release độc lập thay vì chỉ test DTO nội bộ của từng service.

**Vấn đề nó giải quyết:**
Provider có thể pass unit/integration tests của chính nó nhưng vẫn phá consumer khi rename field, đổi status semantics hoặc bỏ response variant mà consumer đang dùng.

**Ví dụ thực tế:**
Mobile Backend phụ thuộc Pricing API trả `amount`, `currency` và `404` cho product không tồn tại. Contract từ consumer được verify trong provider CI trước khi Pricing release thay đổi behavior.

**Trade-off:**
Contract tests phát hiện integration breaking change sớm và giảm nhu cầu E2E khổng lồ, nhưng tạo contract lifecycle, versioning và ownership overhead. Nếu mọi component deploy cùng một artifact, lợi ích có thể không đủ lớn.

**Middle → Senior insight:**
Middle developer cần viết contract theo observable behavior, không theo implementation detail. Senior / Technical developer phải xác định provider/consumer ownership, compatibility policy, contract retirement và nơi contract testing bổ sung — chứ không thay thế — integration/E2E testing.

### Design 2 — Separate transaction boundary khỏi external network call

**Khái niệm:**
Database transaction nên bảo vệ state cần atomicity trong database; external HTTP/message side effect thường không nên bị giữ bên trong một transaction dài chỉ để tạo cảm giác “mọi thứ cùng commit”.

**Vấn đề nó giải quyết:**
Giữ transaction/locks trong lúc chờ payment API hoặc third-party service làm tăng blocking và connection occupancy, nhưng rollback database vẫn không thể rollback một external side effect đã thành công.

**Ví dụ thực tế:**
Order workflow ghi trạng thái `PendingPayment` rồi commit; payment được thực hiện qua workflow có idempotency. Kết quả cập nhật order bằng transaction ngắn tiếp theo. Nếu cần reliable async publication, có thể dùng Outbox thay vì giữ SQL transaction qua network call.

**Trade-off:**
Transaction ngắn tăng concurrency và làm failure boundary rõ hơn nhưng đưa hệ thống sang state machine/eventual consistency cần recovery. Với operation hoàn toàn trong cùng database, một ACID transaction đơn giản vẫn tốt hơn workflow phân tán.

**Middle → Senior insight:**
Middle developer cần tránh network I/O trong transaction khi không cần và hiểu rollback scope. Senior / Technical developer phải model intermediate states, retry/idempotency, compensation và user-visible semantics thay vì cố mô phỏng distributed transaction bằng transaction dài.

### Design 3 — SLO và error budget biến reliability thành quyết định kỹ thuật đo được

**Khái niệm:**
SLO mô tả mức reliability mục tiêu từ góc nhìn service/user, ví dụ tỷ lệ checkout thành công hoặc latency percentile. Error budget là phần failure/degradation được phép trong khoảng thời gian tương ứng.

**Vấn đề nó giải quyết:**
Nếu yêu cầu chỉ là “service phải luôn ổn định”, team khó quyết định khi nào ưu tiên feature, hardening hay rollback. SLO tạo boundary để đánh giá reliability bằng signal có ý nghĩa thay vì số exception tuyệt đối.

**Ví dụ thực tế:**
Checkout đặt SLO 99.9% successful requests trong 30 ngày, loại trừ request invalid theo contract. Nếu release mới tiêu thụ error budget nhanh vì dependency timeout, team có evidence để dừng rollout và ưu tiên reliability work.

**Trade-off:**
SLO giúp cân bằng delivery với reliability nhưng metric hoặc target chọn sai có thể tối ưu thứ user không quan tâm. Target quá cao cũng làm infrastructure/operational cost tăng mạnh mà business value không tương xứng.

**Middle → Senior insight:**
Middle developer cần hiểu metric, percentile và instrument user-visible outcomes đúng. Senior / Technical developer phải chọn SLI/SLO cùng business stakeholders, thiết kế alert theo burn rate và dùng budget để ra quyết định kiến trúc/release thay vì coi 100% availability là mặc định.
