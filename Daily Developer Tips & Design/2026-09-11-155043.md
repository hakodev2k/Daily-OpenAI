# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `AsSplitQuery` khi nhiều `Include` tạo cartesian explosion

**Mẹo:**
Trong EF Core, nếu một query load nhiều collection navigation bằng `Include`, kiểm tra SQL sinh ra và cân nhắc `AsSplitQuery()` khi single query tạo lượng row nhân chéo quá lớn.

**Tại sao hữu ích:**
Khi một entity cha có nhiều collection được join cùng lúc, số row trả về có thể tăng theo tích số phần tử. Database và network phải xử lý nhiều dữ liệu lặp lại dù application chỉ cần một object graph duy nhất.

**Ví dụ:**
```csharp
var order = await db.Orders
    .Include(x => x.Lines)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .SingleAsync(x => x.Id == orderId, ct);
```

Nếu Order có 40 Lines và 10 Payments, một single SQL query có thể trả hàng trăm row do join chéo. Split query tách collection loading thành nhiều SQL statement nhỏ hơn.

**Lưu ý:**
`AsSplitQuery` đổi một query lớn thành nhiều round trip, nên không mặc định luôn nhanh hơn. Với latency database cao hoặc dataset nhỏ, single query có thể tốt hơn. Hãy đo SQL, row count và total latency trước khi chọn.

### Tip 2 — Khi PostgreSQL chọn plan xấu sau khi dữ liệu lệch phân bố, kiểm tra statistics trước khi thêm index

**Mẹo:**
Nếu cùng một query trước đây nhanh nhưng đột nhiên dùng sequential scan hoặc join strategy không phù hợp, kiểm tra statistics và data skew trước khi kết luận thiếu index.

**Tại sao hữu ích:**
Planner dựa vào statistics để ước lượng cardinality. Nếu phân bố dữ liệu thay đổi mạnh hoặc statistics quá cũ, estimate sai có thể kéo theo plan sai dù index phù hợp vẫn tồn tại.

**Ví dụ:**
```sql
ANALYZE orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, status, created_at
FROM orders
WHERE tenant_id = 'tenant-42'
  AND status = 'Pending';
```

So sánh `rows` ước lượng với `actual rows`. Sai lệch lớn là tín hiệu cần xem lại statistics target, data skew hoặc cách viết predicate.

**Lưu ý:**
Không chạy `ANALYZE` thủ công như phản xạ cho mọi slow query. Nếu root cause là query shape, missing index, parameter sensitivity hoặc I/O pressure, refresh statistics chỉ tạm che triệu chứng.

### Tip 3 — Dùng Managed Identity để đọc Azure Key Vault thay vì nhét secret vào App Service settings

**Mẹo:**
Khi ứng dụng chạy trên Azure, ưu tiên cho workload xác thực bằng Managed Identity rồi đọc secret/certificate từ Azure Key Vault thay vì lưu credential dài hạn trong configuration.

**Tại sao hữu ích:**
Managed Identity loại bỏ nhu cầu phân phối và xoay vòng client secret cho chính ứng dụng. Quyền truy cập có thể quản lý bằng RBAC và thu hồi độc lập với deployment artifact.

**Ví dụ:**
```csharp
var client = new SecretClient(
    new Uri(keyVaultUri),
    new DefaultAzureCredential());

var secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);
```

Trong local development, `DefaultAzureCredential` có thể dùng developer identity; trên Azure, credential chain có thể dùng Managed Identity của workload.

**Lưu ý:**
Managed Identity không tự động tạo least privilege. Nếu identity có quyền đọc toàn bộ vault hoặc nhiều environment dùng chung một vault quá rộng, blast radius vẫn lớn. Tách quyền theo workload và environment.

### Tip 4 — Dùng Playwright Trace Viewer để điều tra flaky test thay vì chỉ tăng timeout

**Mẹo:**
Với E2E test chỉ fail trên CI, bật Playwright tracing cho retry hoặc failure rồi xem timeline, DOM snapshot, network và action sequence bằng Trace Viewer.

**Tại sao hữu ích:**
Một flaky test có thể do selector đổi, animation, race condition, request thất bại hoặc dữ liệu test không deterministic. Trace cung cấp evidence của đúng lần fail thay vì buộc bạn tái hiện bằng đoán mò.

**Ví dụ:**
```ts
use: {
  trace: 'on-first-retry'
}
```

Sau khi CI tạo trace artifact, mở bằng:

```bash
npx playwright show-trace trace.zip
```

Từ đó kiểm tra action nào bắt đầu chậm, network response nào lỗi và UI state thực tế tại thời điểm assertion fail.

**Lưu ý:**
Trace rất hữu ích nhưng có storage cost và có thể chứa dữ liệu nhạy cảm từ page/network. Không bật mức chi tiết tối đa cho mọi test production-like nếu chưa có retention và privacy policy phù hợp.

### Tip 5 — Dùng `PerformanceObserver` để đo Core Web Vitals từ người dùng thật, không chỉ dựa vào Lighthouse local

**Mẹo:**
Với website content-heavy hoặc CMS, thu thập performance metric từ browser thật thay vì chỉ tối ưu theo một lần chạy Lighthouse trên máy developer.

**Tại sao hữu ích:**
Lab test cho baseline ổn định nhưng không phản ánh đầy đủ device yếu, mạng chậm, cache state, geography và traffic thực tế. Real User Monitoring giúp biết LCP, INP hoặc layout instability xảy ra với nhóm user nào.

**Ví dụ:**
```js
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.name, entry.startTime)
  }
})

observer.observe({ type: 'largest-contentful-paint', buffered: true })
```

Trong production, metric nên được gửi kèm page type, release version và device/network category phù hợp để phân tích regression.

**Lưu ý:**
Không gắn URL chứa PII, user ID hoặc dimension cardinality cao vào telemetry. RUM bổ sung cho synthetic test chứ không thay thế hoàn toàn Lighthouse, profiling hoặc backend tracing.

## 🧠 Software Design

### Design 1 — Circuit Breaker không thay thế Retry; hai cơ chế giải quyết hai failure mode khác nhau

**Khái niệm:**
Retry xử lý failure tạm thời bằng cách thử lại có kiểm soát. Circuit Breaker ngừng gọi dependency trong một khoảng thời gian khi failure vượt ngưỡng, nhằm tránh tiếp tục dồn tải vào dependency đang hỏng.

**Vấn đề nó giải quyết:**
Nếu external API bắt đầu trả 503 và mỗi request của bạn retry ba lần, traffic tới dependency có thể tăng gấp nhiều lần đúng lúc nó yếu nhất. Retry tốt cho transient fault ngắn; circuit breaker cần thiết khi failure có xu hướng kéo dài.

**Ví dụ thực tế:**
```text
Payment API timeout tăng mạnh

Retry:
- tối đa 2 lần
- exponential backoff + jitter

Circuit Breaker:
- mở circuit sau ngưỡng failure
- fail fast trong 30 giây
- sau đó cho một số probe request thử lại
```

Flow thường còn cần timeout rõ ràng và fallback/degraded behavior nếu business cho phép.

**Trade-off:**
Kết hợp hai cơ chế giúp giảm retry storm và bảo vệ resource, nhưng policy sai có thể làm hệ thống fail fast quá sớm hoặc kéo dài recovery. Threshold, sampling window và retry count phải dựa trên SLO và đặc tính dependency, không lấy từ ví dụ mặc định.

**Middle → Senior insight:**
Middle developer cần phân biệt timeout, retry và circuit breaker và tránh retry vô hạn. Senior / Technical developer phải thiết kế resilience budget xuyên chuỗi dependency: số lần retry ở mỗi layer, tổng deadline, failure propagation, fallback semantics và cách tránh nhiều tầng cùng retry.

### Design 2 — Materialized Read Model phù hợp khi query shape ổn định và read path cần latency thấp

**Khái niệm:**
Materialized read model lưu sẵn dữ liệu đã được join/aggregate theo nhu cầu đọc thay vì tính lại từ transactional model ở mỗi request. Nó có thể nằm trong SQL table riêng, Redis, Elasticsearch hoặc datastore khác tùy use case.

**Vấn đề nó giải quyết:**
Dashboard hoặc search page có thể phải join nhiều bảng, tính aggregate và gọi nhiều service cho mỗi request. Nếu workload đọc lớn và shape tương đối ổn định, tính toán lặp lại sẽ tốn CPU, I/O và latency.

**Ví dụ thực tế:**
```text
Transactional model:
Projects + Tasks + Users + Documents

ProjectDashboardReadModel:
- ProjectId
- ProjectName
- OpenTaskCount
- OwnerName
- DocumentCount
- LastActivityAt
```

Projection có thể được cập nhật đồng bộ trong cùng database hoặc bất đồng bộ qua event tùy freshness requirement.

**Trade-off:**
Read model giúp query đơn giản và nhanh hơn, nhưng tạo duplicated data, projection logic, rebuild strategy và eventual-consistency concern. Nếu query gốc vẫn đáp ứng SLO bằng index và projection SQL đơn giản, thêm read model riêng có thể là over-engineering.

**Middle → Senior insight:**
Middle developer cần hiểu read model là dữ liệu dẫn xuất, không phải nguồn truth mặc định. Senior / Technical developer phải xác định freshness budget, rebuildability, ownership, failure recovery và cost vận hành trước khi chọn vật hóa dữ liệu thay vì tối ưu query hiện tại.

### Design 3 — Distributed Lock chỉ nên bảo vệ critical section nhỏ; long-running job cần ownership model rõ hơn

**Khái niệm:**
Distributed Lock giúp nhiều process thống nhất rằng tại một thời điểm chỉ một owner được thực hiện một critical section. Nó hữu ích cho coordination ngắn nhưng không tự biến một long-running workflow thành exactly-once execution.

**Vấn đề nó giải quyết:**
Trong môi trường multi-instance, cùng scheduled job hoặc maintenance task có thể được kích hoạt ở nhiều node. Nếu tất cả cùng xử lý, hệ thống có thể gửi email trùng, chạy settlement hai lần hoặc cập nhật resource đồng thời.

**Ví dụ thực tế:**
```text
3 App Service instances cùng kích hoạt DailySettlement

Option A:
- acquire lease 30 giây
- renew định kỳ
- chỉ owner tiếp tục

Nếu owner crash:
- lease hết hạn
- instance khác tiếp quản
```

Với Azure, có thể dùng lease/coordination mechanism phù hợp hoặc chuyển workload sang hệ thống job có ownership và retry semantics rõ ràng.

**Trade-off:**
Distributed lock đơn giản cho critical section nhỏ nhưng đưa vào vấn đề lease expiry, clock/timing, owner crash và stale owner. Lock giữ quá lâu làm recovery chậm; lock quá ngắn có thể khiến hai worker cùng tin rằng mình là owner.

**Middle → Senior insight:**
Middle developer cần hiểu process-local `lock` không bảo vệ nhiều instance và phải thiết kế operation idempotent khi có thể. Senior / Technical developer phải quyết định giữa distributed lock, broker competing consumers, leader election hoặc durable workflow dựa trên failure model, execution time và yêu cầu duplicate tolerance.
