# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Interlocked` cho counter/state đơn giản thay vì lock cả critical section

**Mẹo:**
Với các thao tác atomic đơn giản như tăng counter, swap reference hoặc compare-and-set, cân nhắc `Interlocked` thay vì tạo `lock` chỉ để bảo vệ một biến nhỏ.

**Tại sao hữu ích:**
Giảm contention và tránh overhead của monitor khi logic thực sự chỉ cần một primitive atomic operation.

**Ví dụ:**
```csharp
private long _processed;

public void MarkProcessed()
{
    Interlocked.Increment(ref _processed);
}
```

Với compare-and-set:

```csharp
if (Interlocked.CompareExchange(ref _state, 1, 0) == 0)
{
    StartOnce();
}
```

**Lưu ý:**
`Interlocked` không thay thế lock cho invariant nhiều biến hoặc sequence nhiều bước. Nếu correctness phụ thuộc nhiều state phải thay đổi cùng nhau, cần synchronization boundary lớn hơn.

### Tip 2 — Dùng database constraint để chặn invariant đơn giản ngay tại data layer

**Mẹo:**
Những rule dữ liệu đơn giản và bắt buộc với mọi code path nên được enforce thêm bằng constraint/index trong database, không chỉ bằng validation ở application.

**Tại sao hữu ích:**
Giúp bảo vệ dữ liệu trước race condition, script thủ công, background job hoặc code path mới vô tình bỏ qua validation.

**Ví dụ:**
SQL Server:

```sql
ALTER TABLE TimesheetEntries
ADD CONSTRAINT CK_TimesheetEntries_BillableHours
CHECK (BillableHours >= 0 AND BillableHours <= ActualHours);
```

**Lưu ý:**
Không nhét business workflow phức tạp vào constraint. Database constraint nên tập trung vào invariant cục bộ, deterministic và dễ hiểu.

### Tip 3 — Dùng `git show --remerge-diff` để xem merge conflict đã được resolve như thế nào

**Mẹo:**
Khi điều tra bug xuất hiện sau merge commit, dùng `git show --remerge-diff <merge-commit>` để xem khác biệt giữa auto-merge và kết quả conflict resolution cuối cùng.

**Tại sao hữu ích:**
Giúp phát hiện lỗi do resolve conflict sai mà diff merge thông thường có thể khó nhìn ra.

**Ví dụ:**
```bash
git show --remerge-diff <merge-commit-sha>
```

**Lưu ý:**
Tính năng hữu ích nhất với merge commit có conflict. Nếu lịch sử dùng squash/rebase-only, sẽ ít có giá trị hơn.

### Tip 4 — Dùng `docker stats` để kiểm tra nhanh container đang nghẽn CPU hay memory

**Mẹo:**
Khi container chậm hoặc bị restart bất thường, dùng `docker stats` để nhìn live CPU, memory và network trước khi vào profiler sâu hơn.

**Tại sao hữu ích:**
Giúp phân biệt nhanh application bottleneck với resource limit hoặc memory pressure của container.

**Ví dụ:**
```bash
docker stats myapp
```

Hoặc xem tất cả container:

```bash
docker stats
```

**Lưu ý:**
`docker stats` chỉ là snapshot/live telemetry mức container. Nó không cho biết method nào ăn CPU hoặc object nào giữ memory; cần kết hợp runtime metrics/profiler khi đào sâu.

### Tip 5 — Dùng constant-time comparison cho secret/token nhạy cảm

**Mẹo:**
Khi so sánh hash, MAC hoặc token secret có kích thước cố định, dùng API constant-time như `CryptographicOperations.FixedTimeEquals` thay vì `SequenceEqual` nếu timing side-channel là concern.

**Tại sao hữu ích:**
Giảm nguy cơ thời gian so sánh tiết lộ vị trí byte đầu tiên khác nhau cho attacker có khả năng đo latency đủ chính xác.

**Ví dụ:**
```csharp
using System.Security.Cryptography;

bool valid = CryptographicOperations.FixedTimeEquals(
    expectedMac,
    actualMac);
```

**Lưu ý:**
Constant-time comparison chỉ giải quyết một phần nhỏ của security design. Vẫn cần key management, secure transport, replay protection và validation đúng context.

## 🧠 Software Design

### Design 1 — Database constraint và application rule nên bổ sung cho nhau

**Khái niệm:**
Application layer phù hợp để diễn đạt business rule giàu ngữ nghĩa, trong khi database constraint bảo vệ invariant đơn giản ở boundary cuối cùng của dữ liệu.

**Vấn đề nó giải quyết:**
Nếu chỉ tin application validation, race condition hoặc code path khác có thể ghi dữ liệu bất hợp lệ. Nếu nhét toàn bộ business logic vào database, logic lại khó test, version và evolve.

**Ví dụ thực tế:**
Rule `BillableHours <= ActualHours` có thể được validate ở command handler để trả message thân thiện, đồng thời database `CHECK` constraint bảo vệ dữ liệu khỏi concurrent update hoặc script ngoài application.

**Trade-off:**
Dual protection tăng safety nhưng rule phải được giữ nhất quán ở hai nơi. Constraint quá phức tạp sẽ làm migration/debug khó; application-only thì dễ để lọt dữ liệu sai khi concurrency xảy ra.

**Middle → Senior insight:**
Middle developer nên biết validation ở UI/API không phải enforcement tuyệt đối. Senior developer phải phân loại rule nào thuộc domain workflow, rule nào đủ local để database enforce và cách tránh duplicated logic trở thành divergence.

### Design 2 — Semantic Lock khi không thể giữ database transaction xuyên workflow dài

**Khái niệm:**
Semantic Lock dùng trạng thái nghiệp vụ như `Processing`, `PendingApproval` hoặc `Reserved` để ngăn operation xung đột, thay vì giữ physical database lock trong nhiều phút hoặc nhiều service call.

**Vấn đề nó giải quyết:**
Long-running workflow không thể giữ SQL transaction mở xuyên network call, human approval hoặc background processing mà không gây contention và failure recovery phức tạp.

**Ví dụ thực tế:**
Khi bắt đầu refund, Order chuyển từ `Paid` sang `RefundPending`. Các command khác kiểm tra state này và không cho phép shipment mới cho đến khi refund hoàn tất hoặc fail.

**Trade-off:**
Semantic lock phù hợp với workflow dài và dễ recovery hơn physical lock, nhưng thêm state transition, timeout/reconciliation và UX cho trạng thái trung gian.

**Middle → Senior insight:**
Middle developer nên hiểu lock không nhất thiết là mutex/database row lock. Senior developer phải thiết kế state machine, ownership, timeout, compensation và rule khi lock nghiệp vụ bị bỏ dở.

### Design 3 — Push hay Pull model cho background processing phụ thuộc ai kiểm soát nhịp độ

**Khái niệm:**
Push model để producer chủ động đẩy work tới consumer; Pull model để consumer tự lấy work khi còn capacity. Cả hai đều hợp lệ tùy load pattern và control cần thiết.

**Vấn đề nó giải quyết:**
Nếu producer đẩy quá nhanh, consumer dễ bị overload. Nếu consumer pull quá chậm, latency tăng và queue backlog kéo dài.

**Ví dụ thực tế:**
Webhook là push: external system gọi ngay khi event xảy ra. Database job queue thường là pull: worker lấy 20 job khi còn slot xử lý. Một hệ thống có thể nhận event bằng push rồi đưa vào internal queue để consumer pull theo capacity.

**Trade-off:**
Push giảm latency nhưng cần rate limiting/backpressure mạnh. Pull kiểm soát capacity tốt hơn nhưng cần polling, lease và xử lý latency giữa các lần fetch.

**Middle → Senior insight:**
Middle developer nên phân biệt delivery mechanism với processing semantics. Senior developer cần chọn push/pull dựa trên latency SLA, backpressure, retry, ownership, cost polling và khả năng hấp thụ burst của downstream.
