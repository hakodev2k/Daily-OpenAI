# Daily Developer Tips & Design — 2026-09-19

## 🛠 Developer Tips & Tricks

### Tip 1 — `ConfigureAwait(false)` không phải tối ưu mặc định cho ASP.NET Core

**Mẹo:**
Trong application code ASP.NET Core hiện đại, đừng thêm `ConfigureAwait(false)` máy móc vào mọi `await`. ASP.NET Core không cài đặt request `SynchronizationContext` kiểu ASP.NET cũ, nên continuation thông thường không cần quay lại một request thread/context đặc biệt.

**Tại sao hữu ích:**
Hiểu cơ chế này giúp tránh cargo-cult optimization và phân biệt behavior giữa legacy ASP.NET/.NET Framework với ASP.NET Core. Giá trị của `ConfigureAwait(false)` rõ hơn trong reusable library code có thể chạy dưới nhiều loại `SynchronizationContext`.

**Ví dụ:**
Một service ASP.NET Core gọi `await repository.LoadAsync(ct)` có thể giữ code đơn giản. Nếu cùng code là thư viện dùng bởi WPF/WinForms hoặc môi trường có custom context, quyết định capture context cần được đánh giá ở boundary thư viện.

**Lưu ý:**
Không suy rộng thành “`ConfigureAwait(false)` vô dụng”. Context phụ thuộc host/library; khi migrate legacy .NET Framework cần hiểu runtime model thực tế trước khi thay đổi hàng loạt.

### Tip 2 — Đọc actual execution plan cùng memory grant khi query sort/hash chậm

**Mẹo:**
Khi SQL query có `SORT`, hash join hoặc aggregation chậm bất thường, kiểm tra actual execution plan, estimated/actual rows và memory grant/spill evidence thay vì chỉ tìm missing index.

**Tại sao hữu ích:**
Cardinality estimate sai có thể khiến engine cấp quá ít memory, làm sort/hash spill xuống temp storage; cấp quá nhiều lại giữ memory không cần thiết và giảm concurrency. Symptom có thể là latency tăng mạnh khi tải cao dù query logic không đổi.

**Ví dụ:**
Một reporting query nhanh với 10 nghìn rows nhưng chậm sau data growth. Plan cho thấy actual rows lớn hơn estimate nhiều lần và sort spill. Diagnosis cần đi từ spill/evidence → estimate/data distribution → statistics/query shape, không phải thêm index theo phản xạ.

**Lưu ý:**
Memory grant chỉ là một phần của plan. Blocking, I/O, parameter sensitivity và concurrent workload có thể tạo triệu chứng tương tự; luôn correlate với runtime evidence.

### Tip 3 — Azure Service Bus DLQ phải có quy trình xử lý, không chỉ dashboard

**Mẹo:**
Thiết kế dead-letter queue như một operational workflow: ghi reason/context đủ dùng, alert theo threshold, có cách inspect, repair/replay hoặc discard có kiểm soát.

**Tại sao hữu ích:**
Đưa message vào DLQ chỉ ngăn poison message chặn luồng chính. Nếu không có ownership và remediation path, DLQ trở thành nơi tích lũy business operations thất bại âm thầm.

**Ví dụ:**
Consumer gặp payload hợp lệ nhưng reference data chưa tồn tại sau nhiều retry. Message vào DLQ với `MessageId`, sanitized business key và failure category. Runbook cho phép operator xác nhận dependency đã được sửa rồi replay có kiểm soát.

**Lưu ý:**
Không replay toàn bộ DLQ hàng loạt mà không hiểu root cause. Consumer vẫn phải idempotent vì replay có thể gặp message đã tạo một phần side effect trước khi thất bại.

### Tip 4 — Browser cache cần phân biệt hashed asset với HTML

**Mẹo:**
Với frontend build có content-hashed filenames, có thể cache static assets rất lâu; HTML/entry document thường cần policy khác để client nhanh chóng nhận references tới bundle mới.

**Tại sao hữu ích:**
Nếu cả HTML và bundle đều cache dài không đúng cách, deployment mới có thể bị client giữ entry document cũ hoặc gặp mismatch giữa assets đã purge và HTML còn stale. Cache policy phải đi theo khả năng immutable của resource.

**Ví dụ:**
`app.a1b2c3.js` thay tên khi content đổi nên phù hợp với long-lived immutable caching. `index.html` có thể cần revalidation/TTL ngắn hơn để deployment mới được phát hiện mà vẫn tận dụng CDN/browser cache hợp lý.

**Lưu ý:**
Không dùng một `Cache-Control` cho mọi resource. CDN, reverse proxy và browser có thể có cache layers khác nhau; kiểm tra response headers thực tế và purge strategy.

### Tip 5 — Integration test database nên kiểm tra behavior mà mock không mô phỏng được

**Mẹo:**
Dùng database thật/containerized test cho behavior phụ thuộc query translation, constraint, transaction, isolation hoặc provider-specific semantics thay vì cố mock `DbSet`/repository đến mức giả lập database.

**Tại sao hữu ích:**
Mock có thể làm LINQ chạy in-memory và bỏ qua SQL translation, collation, unique constraint hay transaction behavior. Test xanh nhưng production vẫn fail ở chính integration boundary cần bảo vệ.

**Ví dụ:**
Một bug do PostgreSQL case sensitivity hoặc unique constraint nên được tái hiện bằng integration test trên cùng engine/version gần production, với schema migration thực, thay vì mock trả exception được lập trình sẵn.

**Lưu ý:**
Không biến mọi test thành database integration test. Pure domain rules vẫn nên test nhanh ở unit level; chọn layer nhỏ nhất còn giữ đúng failure semantics.

## 🧠 Software Design

### Design 1 — Idempotent Consumer cho at-least-once delivery

**Khái niệm:**
Trong hệ thống message at-least-once, consumer phải chấp nhận cùng logical message có thể được giao nhiều lần và đảm bảo duplicate không tạo side effect nghiệp vụ lặp ngoài ý muốn.

**Vấn đề nó giải quyết:**
Consumer có thể commit database rồi crash trước khi broker nhận acknowledgement. Broker redeliver message dù business update lần đầu đã thành công.

**Ví dụ thực tế:**
Payment notification mang `MessageId`/business operation ID. Consumer ghi processed ID cùng business update trong transaction phù hợp; lần delivery sau phát hiện operation đã xử lý và không tạo invoice hoặc email thứ hai.

**Trade-off:**
Deduplication tăng reliability nhưng cần storage, retention và transaction strategy. Giữ mọi message ID mãi mãi không thực tế; dùng business idempotency sai granularity cũng có thể bỏ qua operation hợp lệ.

**Middle → Senior insight:**
Middle developer cần hiểu duplicate delivery và implement idempotency tại side-effect boundary. Senior / Technical developer phải chọn dedup key, atomicity, retention window và semantics khi message được replay có chủ đích.

### Design 2 — Anti-Corruption Layer khi tích hợp legacy domain

**Khái niệm:**
Anti-Corruption Layer (ACL) đặt translation boundary giữa domain của hệ thống và model/protocol của external hoặc legacy system, tránh để khái niệm bên ngoài lan trực tiếp vào core model.

**Vấn đề nó giải quyết:**
Legacy ERP có field names, status codes và workflow semantics khác domain mới. Nếu toàn bộ application dùng trực tiếp DTO/status của ERP, thay đổi integration sẽ kéo coupling xuyên nhiều layers.

**Ví dụ thực tế:**
ERP trả `CUST_TYPE=03` và nhiều trạng thái kỹ thuật. Adapter chuyển chúng thành `CustomerCategory` và business states của application; domain không cần biết transport schema hoặc magic codes của ERP.

**Trade-off:**
ACL cô lập coupling và làm domain rõ hơn nhưng thêm mapping, code và nơi cần test. Với integration nhỏ, ổn định và model gần như giống nhau, một abstraction lớn có thể là over-engineering.

**Middle → Senior insight:**
Middle developer cần giữ mapping/integration concerns ngoài domain logic. Senior / Technical developer phải đánh giá volatility, semantic mismatch và migration roadmap để quyết định boundary mỏng hay ACL đầy đủ.

### Design 3 — SLO-driven observability thay vì thu thập mọi metric

**Khái niệm:**
Observability design nên bắt đầu từ behavior người dùng/hệ thống cần bảo vệ và Service Level Objective (SLO), sau đó chọn metrics, traces và logs hỗ trợ phát hiện/diagnose violation thay vì thu thập mọi thứ có thể.

**Vấn đề nó giải quyết:**
Hệ thống có hàng nghìn metrics nhưng incident vẫn khó xử lý nếu không biết signal nào phản ánh availability, latency hoặc correctness thực sự. Telemetry dư thừa còn tăng chi phí và noise.

**Ví dụ thực tế:**
Checkout có SLO về successful request rate và p95 latency. Dashboard ưu tiên request outcome/latency, dependency failures và saturation; traces/logs được dùng để drill down khi SLO burn tăng thay vì alert từng exception đơn lẻ.

**Trade-off:**
SLO-driven telemetry giảm noise và tập trung vào user impact nhưng cần thống nhất business-critical journeys. Chỉ theo SLO mà bỏ component diagnostics lại làm root-cause analysis thiếu evidence.

**Middle → Senior insight:**
Middle developer cần emit structured telemetry có correlation và hiểu golden signals. Senior / Technical developer phải chọn SLI/SLO, alert theo impact/burn rate và cân bằng diagnostic depth với cardinality, storage cost và operational complexity.
