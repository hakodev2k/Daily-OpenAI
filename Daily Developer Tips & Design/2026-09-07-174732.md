# Daily Developer Tips & Design — 2026-09-07

## 🛠 Developer Tips & Tricks

### Tip 1 — Truyền `CancellationToken` xuyên suốt call chain, không chỉ ở controller

**Mẹo:**
Khi một ASP.NET Core request bị client hủy hoặc timeout, hãy truyền `CancellationToken` từ endpoint xuống EF Core, outbound HTTP call và các operation bất đồng bộ có hỗ trợ cancellation thay vì dừng ở layer trên cùng.

**Tại sao hữu ích:**
Nếu controller biết request đã bị hủy nhưng database query và HTTP call phía dưới vẫn tiếp tục chạy, hệ thống vẫn tiêu CPU, connection pool và network cho công việc mà không còn consumer. Dưới tải cao, các “zombie operation” này có thể làm resource exhaustion nặng hơn.

**Ví dụ:**
```csharp
app.MapGet("/orders/{id:int}", async (
    int id,
    AppDbContext db,
    InventoryClient inventory,
    CancellationToken cancellationToken) =>
{
    var order = await db.Orders
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    if (order is null)
        return Results.NotFound();

    var stock = await inventory.GetStockAsync(
        order.ProductId,
        cancellationToken);

    return Results.Ok(new { order.Id, stock });
});
```

**Lưu ý:**
Cancellation không đồng nghĩa rollback business operation đã commit. Nếu payment đã được ghi xuống database rồi client disconnect, không được coi cancellation như cơ chế undo. Transaction boundary và side effect phải được thiết kế riêng.

### Tip 2 — Điều tra deadlock bằng deadlock graph trước khi thêm retry

**Mẹo:**
Khi SQL Server báo deadlock, thu thập deadlock graph hoặc Extended Events để xác định transaction nào giữ lock, transaction nào chờ và thứ tự truy cập resource trước khi chỉ thêm retry policy.

**Tại sao hữu ích:**
Retry có thể làm giảm lỗi nhìn thấy ở application nhưng không loại bỏ nguyên nhân. Deadlock thường xuất hiện khi hai transaction khóa cùng resource theo thứ tự khác nhau, giữ transaction quá lâu hoặc dùng index/query plan làm phạm vi lock lớn hơn cần thiết.

**Ví dụ:**
Một flow cập nhật `Orders` rồi `Inventory`, trong khi flow khác cập nhật `Inventory` rồi `Orders`. Hai transaction có thể tạo vòng chờ:

```text
Transaction A: lock Orders -> wait Inventory
Transaction B: lock Inventory -> wait Orders
```

Giải pháp bền vững có thể là chuẩn hóa thứ tự truy cập, rút ngắn transaction hoặc điều chỉnh query/index để giảm lock footprint.

**Lưu ý:**
Retry vẫn hữu ích vì deadlock là lỗi transient mà database chủ động chọn một victim. Nhưng retry phải có giới hạn, backoff và chỉ áp dụng cho operation có semantics an toàn; không dùng retry để che transaction design kém.

### Tip 3 — Với Azure Service Bus, handler dài hơn lock duration có thể tạo duplicate processing

**Mẹo:**
Khi consumer dùng PeekLock, hãy hiểu rõ `LockDuration`, automatic lock renewal và thời gian xử lý thực tế. Nếu message xử lý lâu hơn lock mà không renew thành công, message có thể được giao lại cho consumer khác trong khi handler đầu vẫn đang chạy.

**Tại sao hữu ích:**
Azure Service Bus cung cấp at-least-once delivery, không phải exactly-once processing. Lock hết hạn làm tăng khả năng hai execution cùng xử lý một business operation, đặc biệt ở workload có call external API, file processing hoặc batch dài.

**Ví dụ:**
Một message `GenerateMonthlyReport` mất 4 phút nhưng queue lock chỉ 1 phút. Nếu client không renew lock đủ lâu, execution thứ hai có thể bắt đầu trước khi execution đầu kết thúc.

Consumer nên:

- đặt processing time hợp lý,
- cấu hình lock renewal phù hợp,
- giữ handler idempotent,
- cân nhắc chia work lớn thành các step nhỏ hơn.

**Lưu ý:**
Đừng chỉ tăng lock duration hoặc renewal window vô hạn. Handler quá dài làm recovery chậm khi process chết và giữ work unit quá lớn. Với job hàng chục phút, một workflow/job system hoặc decomposition khác có thể phù hợp hơn.

### Tip 4 — Dùng `git bisect` để tìm commit gây regression thay vì đọc hàng trăm commit thủ công

**Mẹo:**
Khi biết một phiên bản cũ hoạt động và phiên bản mới bị lỗi, dùng `git bisect` để binary-search commit gây regression. Với test có thể chạy tự động, kết hợp `git bisect run` để giảm đáng kể thời gian điều tra.

**Tại sao hữu ích:**
Nếu khoảng thay đổi có 256 commit, binary search chỉ cần khoảng 8 lần phân loại good/bad thay vì kiểm tra tuần tự toàn bộ lịch sử. Đây là công cụ rất hiệu quả với regression về performance, config, serialization hoặc behavior khó thấy trong code review.

**Ví dụ:**
```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0

# Git checkout một commit trung gian.
# Chạy test rồi đánh dấu:
git bisect good
# hoặc
git bisect bad
```

Nếu có script trả exit code 0 khi pass và khác 0 khi fail:

```bash
git bisect run ./scripts/regression-test.sh
```

**Lưu ý:**
`git bisect` hoạt động tốt nhất khi mỗi commit build/test được độc lập. Nếu lịch sử chứa commit không build được hoặc bug phụ thuộc external state không deterministic, cần dùng `git bisect skip` hoặc cải thiện reproduction trước.

### Tip 5 — Với AI coding agent, ground vào source và version thực tế trước khi chấp nhận API được đề xuất

**Mẹo:**
Khi dùng AI coding agent để sửa hoặc mở rộng repository, yêu cầu agent kiểm tra project file, package version, interface hiện có và test trước khi tạo code. Đừng chấp nhận API chỉ vì code “trông đúng”.

**Tại sao hữu ích:**
AI có thể sinh method tồn tại ở version mới hơn, nhầm overload, giả định architecture không có thật hoặc tạo abstraction lệch convention của repository. Grounding vào source giúp giảm hallucinated API và tránh patch đúng về cú pháp nhưng sai với hệ thống hiện tại.

**Ví dụ:**
Trước khi yêu cầu agent thêm resilience cho outbound HTTP, nên để agent kiểm tra:

```text
- TargetFramework trong *.csproj
- Microsoft.Extensions.Http.Resilience version
- cách đăng ký HttpClient hiện tại
- integration tests liên quan
```

Sau đó mới đề xuất patch và chạy build/test.

**Lưu ý:**
Build pass không chứng minh thay đổi đúng semantics. Code generated vẫn cần review về security, concurrency, failure behavior và maintainability; test do chính agent sinh cũng có thể chỉ xác nhận implementation mà bỏ sót requirement thật.

## 🧠 Software Design

### Design 1 — Outbox Pattern cho database commit và message publish

**Khái niệm:**
Outbox Pattern lưu business change và event/message cần publish trong cùng local database transaction. Một background publisher đọc outbox sau đó gửi message ra broker, thay vì cố commit database và publish message như hai operation độc lập.

**Vấn đề nó giải quyết:**
Giả sử Order đã commit nhưng process crash trước khi publish `OrderCompleted`. Database nói order thành công nhưng downstream Billing hoặc Analytics không bao giờ nhận event. Trường hợp ngược lại cũng nguy hiểm: message publish thành công nhưng database rollback.

**Ví dụ thực tế:**
Trong transaction tạo Order:

```text
1. INSERT Orders
2. INSERT OutboxMessages(OrderCompleted, payload)
3. COMMIT
```

Worker sau đó đọc `OutboxMessages`, publish lên Azure Service Bus và đánh dấu message đã gửi. Nếu publish thất bại, worker retry mà business transaction không cần chạy lại.

**Trade-off:**
Outbox loại bỏ khoảng hở giữa database commit và message intent, đồng thời phù hợp at-least-once messaging. Chi phí là thêm bảng outbox, publisher, cleanup, duplicate publish possibility, monitoring và yêu cầu consumer idempotent.

**Middle → Senior insight:**
Middle developer cần đảm bảo business record và outbox entry nằm trong cùng transaction, publish có retry và consumer xử lý duplicate an toàn. Senior / Technical developer phải quyết định polling hay CDC, ordering requirement, retention, partition strategy, operational visibility và liệu hệ thống hiện tại có thật sự cần asynchronous integration đủ để biện minh cho complexity này.

### Design 2 — Modular Monolith chỉ có giá trị khi module boundary được enforce

**Khái niệm:**
Modular Monolith giữ deployment unit chung nhưng chia code theo capability/domain boundary rõ ràng. Điểm quan trọng không phải folder structure mà là dependency direction, ownership và cách module giao tiếp với nhau.

**Vấn đề nó giải quyết:**
Một monolith lớn thường xuống cấp khi mọi feature truy cập trực tiếp mọi table, service và internal class. Khi coupling lan rộng, thay đổi nhỏ tạo blast radius lớn và việc tách service sau này trở nên rất đắt.

**Ví dụ thực tế:**
Một e-commerce application có các module `Catalog`, `Ordering`, `Payments`. `Ordering` không đọc trực tiếp table nội bộ của `Catalog`; nó dùng public contract của module hoặc integration event nội bộ đã định nghĩa. Build-time architecture test có thể chặn reference trái phép giữa module.

**Trade-off:**
Modular Monolith giữ deployment, local transaction và debugging đơn giản hơn Microservices, nhưng boundary vẫn cần kỷ luật. Nếu tất cả module cùng dùng shared entity và query chéo database tùy ý, hệ thống chỉ là layered monolith đổi tên. Enforce boundary cũng tạo thêm contract, mapping và design effort.

**Middle → Senior insight:**
Middle developer cần tôn trọng public/internal API của module và tránh shortcut truy cập xuyên boundary. Senior / Technical developer phải xác định bounded context hợp lý, policy cho cross-module data access, transaction boundary, ownership và tiêu chí khi nào một module thực sự cần tách thành service thay vì tách chỉ vì kích thước codebase.

### Design 3 — Feature Flag tách deployment khỏi release nhưng tạo state cần quản lý

**Khái niệm:**
Feature Flag cho phép deploy code trước nhưng chỉ bật behavior mới cho một nhóm user, environment hoặc tỷ lệ traffic nhất định. Nó giảm coupling giữa thời điểm software được triển khai và thời điểm business feature được phát hành.

**Vấn đề nó giải quyết:**
Một thay đổi lớn có thể cần deploy sớm để giảm release risk, thử với internal user hoặc canary cohort trước khi bật toàn bộ. Nếu không có flag, rollback thường đồng nghĩa redeploy toàn bộ artifact.

**Ví dụ thực tế:**
Một checkout flow mới được deploy cùng version hiện tại nhưng flag chỉ bật cho 5% traffic. Team theo dõi error rate, conversion và latency; nếu có regression, flag được tắt mà không cần rollback binary ngay lập tức.

**Trade-off:**
Feature Flag hỗ trợ progressive delivery và giảm blast radius, nhưng tạo nhiều execution path, test matrix và configuration state. Flag tồn tại lâu trở thành technical debt; permission/config sai có thể vô tình bật feature chưa sẵn sàng.

**Middle → Senior insight:**
Middle developer cần viết code để cả on/off path hoạt động đúng và test boundary của flag. Senior / Technical developer phải phân loại release flag, experiment flag và operational kill switch; xác định owner, expiry, cleanup policy, observability và tránh biến hệ thống thành mê cung condition mà không ai biết production đang chạy path nào.
