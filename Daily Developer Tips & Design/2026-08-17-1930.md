# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CollectionsMarshal.AsSpan()` khi cần sửa `List<T>` tại chỗ trên hot path

**Mẹo:**
Khi performance profiling cho thấy việc index `List<T>` hoặc copy sang array/span gây overhead đáng kể, `CollectionsMarshal.AsSpan()` cho phép truy cập trực tiếp vùng nhớ backing của `List<T>` dưới dạng `Span<T>`.

**Tại sao hữu ích:**
Có thể giảm boundary-check/copy trong các loop xử lý dữ liệu lớn và cho phép mutate phần tử tại chỗ mà không tạo collection trung gian.

**Ví dụ:**
```csharp
using System.Runtime.InteropServices;

var values = new List<int> { 10, 20, 30 };
var span = CollectionsMarshal.AsSpan(values);

for (var i = 0; i < span.Length; i++)
{
    span[i] *= 2;
}
```

**Lưu ý:**
Đây là API low-level. Không thêm/xóa phần tử khỏi `List<T>` trong lúc đang giữ span vì backing storage có thể thay đổi. Chỉ dùng khi profiling chứng minh lợi ích thực tế.

### Tip 2 — Dùng EF Core compiled model khi startup/model-building thật sự là bottleneck

**Mẹo:**
Với model EF Core rất lớn và application startup thường xuyên, có thể dùng compiled model để chuyển phần model-building sang build time.

**Tại sao hữu ích:**
Giảm thời gian khởi tạo metadata của EF Core, hữu ích với serverless, CLI tool, test suite lớn hoặc service có hàng trăm entity và startup latency nhạy cảm.

**Ví dụ:**
Generate compiled model:

```bash
dotnet ef dbcontext optimize
```

Sau đó cấu hình context sử dụng generated model theo code mà EF Core tạo ra.

**Lưu ý:**
Compiled model làm build artifact và migration workflow phức tạp hơn. Với application startup ít lần hoặc model nhỏ, lợi ích thường không đáng kể.

### Tip 3 — Dùng `pg_blocking_pids()` để tìm process đang block query PostgreSQL

**Mẹo:**
Khi query PostgreSQL đứng chờ lock, dùng `pg_blocking_pids(pid)` để xác định session nào đang chặn nó thay vì chỉ tăng timeout.

**Tại sao hữu ích:**
Giúp phân biệt query chậm do execution plan với query chậm vì lock contention và nhanh chóng lần ra transaction gây blocking chain.

**Ví dụ:**
```sql
SELECT
    pid,
    query,
    pg_blocking_pids(pid) AS blocking_pids
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

**Lưu ý:**
Đừng terminate blocking session ngay chỉ vì nó giữ lock. Cần hiểu transaction/business operation đang chạy để tránh làm hỏng dữ liệu hoặc tạo retry storm.

### Tip 4 — Dùng `git sparse-checkout` cho monorepo quá lớn

**Mẹo:**
Nếu repository chứa nhiều project nhưng bạn chỉ làm việc với một phần nhỏ, dùng sparse checkout để working tree chỉ materialize các folder cần thiết.

**Tại sao hữu ích:**
Giảm số file IDE phải index, giảm filesystem overhead và giúp workflow nhẹ hơn khi monorepo có hàng trăm nghìn file.

**Ví dụ:**
```bash
git sparse-checkout init --cone
git sparse-checkout set src/backend tests/backend
```

Muốn thêm folder:

```bash
git sparse-checkout add tools
```

**Lưu ý:**
Git history vẫn tồn tại; sparse checkout chủ yếu giảm working-tree footprint. Một số script/build tool giả định toàn repo có mặt có thể cần điều chỉnh.

### Tip 5 — Dùng `dotnet-gcdump` khi nghi memory pressure nhưng chưa cần full dump

**Mẹo:**
Khi process .NET dùng nhiều memory và bạn muốn biết object nào đang chiếm heap, `dotnet-gcdump` có thể thu GC heap snapshot nhẹ hơn full process dump.

**Tại sao hữu ích:**
Nhanh chóng cho thấy loại object nào chiếm nhiều instance/bytes và hữu ích để phát hiện cache phình, collection bị giữ lâu hoặc allocation bất thường.

**Ví dụ:**
```bash
dotnet-gcdump collect -p <PID> -o app.gcdump
```

Sau đó mở file bằng Visual Studio hoặc công cụ hỗ trợ GC dump.

**Lưu ý:**
GC dump không chứa đầy đủ native memory, thread stack hoặc mọi runtime state. Nếu leak nằm ngoài managed heap, cần dùng full dump hoặc profiler khác.

## 🧠 Software Design

### Design 1 — Chỉ áp dụng CQRS khi read/write thật sự có pressure khác nhau

**Khái niệm:**
CQRS tách command model và query model khi hai phía có requirement, data shape hoặc scaling pattern khác nhau đáng kể. Nó không yêu cầu Event Sourcing và cũng không nhất thiết phải thành hai service riêng.

**Vấn đề nó giải quyết:**
Một model duy nhất đôi khi bị kéo theo hai hướng: write path cần invariant/domain behavior, trong khi read path cần join, denormalization và projection tối ưu cho UI/reporting.

**Ví dụ thực tế:**
Write side của Timesheet enforce rule về ngày làm việc, trạng thái approval và billable hours. Dashboard lại cần tổng hợp theo employee/project/month từ read model đã materialize. Hai model có thể khác nhau nhưng vẫn nằm trong cùng Modular Monolith.

**Trade-off:**
CQRS giúp mỗi side tối ưu độc lập và giảm model compromise, nhưng tăng mapping, synchronization, eventual consistency và số artifact phải maintain. Với CRUD đơn giản, một model thường dễ vận hành hơn.

**Middle → Senior insight:**
Middle developer nên hiểu CQRS là tách responsibility chứ không phải “dùng MediatR là CQRS”. Senior developer phải chứng minh read/write pressure đủ khác biệt để complexity mới mang lại giá trị.

### Design 2 — Partition message queue theo ordering key nhỏ nhất cần thiết

**Khái niệm:**
Nếu message cần giữ thứ tự, partition theo key đại diện cho phạm vi ordering thực sự cần, thay vì ép toàn queue chạy tuần tự.

**Vấn đề nó giải quyết:**
Global ordering làm throughput thấp và tạo head-of-line blocking. Không ordering lại có thể khiến update cùng entity được xử lý sai thứ tự.

**Ví dụ thực tế:**
Event của Order có thể partition theo `OrderId`. Mọi event của cùng một order đi cùng partition để giữ thứ tự, nhưng các order khác vẫn được xử lý song song.

**Trade-off:**
Partitioning giữ cân bằng giữa ordering và throughput, nhưng hot key có thể làm một partition quá tải. Repartitioning và consumer rebalancing cũng làm operational behavior phức tạp hơn.

**Middle → Senior insight:**
Middle developer nên hỏi “thứ tự cần giữ theo toàn hệ thống hay chỉ theo entity/tenant?”. Senior developer cần thiết kế partition key dựa trên ordering scope, traffic skew, retry semantics và khả năng scale consumer.

### Design 3 — Dependency Inversion chỉ có giá trị khi abstraction che một volatility thật

**Khái niệm:**
Dependency Inversion yêu cầu high-level policy không phụ thuộc trực tiếp low-level detail. Nhưng abstraction nên đại diện cho capability hoặc volatility thật, không phải tạo interface cho mọi class theo thói quen.

**Vấn đề nó giải quyết:**
Business logic phụ thuộc trực tiếp SDK, database hoặc vendor API làm test và thay implementation khó. Ngược lại, interface 1:1 cho mọi class chỉ tạo thêm indirection mà không giảm coupling đáng kể.

**Ví dụ thực tế:**
`EmployeeOffboardingService` phụ thuộc `IMailboxAdministration` hợp lý vì Exchange Online là external dependency có thể thay đổi và cần test double. Nhưng tạo `IEmployeeNameFormatter` chỉ vì class có một implementation đơn giản có thể không đem lại giá trị.

**Trade-off:**
Abstraction đúng giúp bảo vệ business core và giảm vendor coupling; abstraction quá mức làm codebase nhiều interface, mapping và navigation cost hơn.

**Middle → Senior insight:**
Middle developer nên biết interface không tự động tạo loose coupling. Senior developer cần nhận diện volatility, ownership boundary và test seam trước khi quyết định nơi nào cần dependency inversion.
