# Daily Developer Tips & Design — 2026-09-29

## 🛠 Developer Tips & Tricks

### Tip 1 — Nhận diện LOH trước khi đổ lỗi cho Garbage Collector

**Mẹo:**
Khi .NET service có memory tăng mạnh hoặc GC pause bất thường, hãy đo allocation profile và kiểm tra object lớn trước khi tăng heap limit. Array/string khoảng 85 KB trở lên thường được cấp phát trên Large Object Heap (LOH), nên các buffer lớn lặp lại có thể tạo GC pressure đáng kể.

**Tại sao hữu ích:**
Tối ưu GC mà không biết allocation source dễ chữa sai tầng. Payload JSON lớn, byte[] khi upload/download hoặc serialize toàn bộ response vào memory có thể tạo nhiều large allocations; giảm allocation hoặc chuyển sang streaming thường giải quyết nguyên nhân tốt hơn tuning GC.

**Ví dụ:**
Một API export tạo MemoryStream, serialize toàn bộ file 40 MB rồi mới trả response. Profiling cho thấy nhiều byte[] lớn và Gen 2 collections tăng. Chuyển sang streaming trực tiếp ra response giúp peak memory giảm mà không cần thay GC mode.

**Lưu ý:**
Không dùng ArrayPool<T> theo phản xạ cho mọi array. Buffer thuê phải được trả đúng cách, dữ liệu nhạy cảm có thể cần clear, và giữ buffer thuê quá lâu có thể làm pool mất hiệu quả. Hãy profile trước khi tối ưu.

### Tip 2 — Khi SQL query bỗng chậm, kiểm tra statistics và cardinality estimate

**Mẹo:**
Nếu cùng một query từng nhanh nhưng đột nhiên dùng execution plan tệ, so sánh estimated rows với actual rows và kiểm tra statistics trước khi kết luận rằng “thiếu index”.

**Tại sao hữu ích:**
Optimizer chọn join type, memory grant và access path dựa trên cardinality estimate. Statistics cũ hoặc data distribution lệch có thể khiến estimate sai hàng trăm lần, từ đó một index vốn phù hợp vẫn bị sử dụng theo plan kém.

**Ví dụ:**
Một query Orders WHERE TenantId = @TenantId AND Status = 'Pending' estimate 50 rows nhưng thực tế trả 300.000 rows cho một tenant lớn. Nested Loops và lookup từng phù hợp với tenant nhỏ trở thành bottleneck. Actual execution plan, statistics và data skew cung cấp evidence trước khi quyết định update statistics, đổi index hoặc thay query strategy.

**Lưu ý:**
Đừng chạy UPDATE STATISTICS hay ép query hint như một “fix chuẩn” cho mọi incident. Parameter sensitivity, data skew, schema/index design và workload thay đổi cũng có thể là nguyên nhân; hint có thể khóa hệ thống vào một plan tệ khác.

### Tip 3 — Dùng Managed Identity thay vì đưa secret Azure vào configuration

**Mẹo:**
Với workload chạy trên Azure, ưu tiên Managed Identity để truy cập Key Vault, Blob Storage hoặc các Azure resources hỗ trợ Microsoft Entra authentication thay vì lưu client secret trong appsettings, pipeline variable hoặc container secret nếu không cần thiết.

**Tại sao hữu ích:**
Managed Identity loại bỏ vòng đời phân phối và rotation của credential tĩnh. Application nhận token qua Azure identity platform, còn quyền được kiểm soát bằng RBAC/access policy, giảm nguy cơ secret bị copy vào log, repository hoặc deployment artifact.

**Ví dụ:**
    var client = new SecretClient(
        new Uri("https://my-vault.vault.azure.net/"),
        new DefaultAzureCredential());

    var secret = await client.GetSecretAsync("PaymentApiKey", cancellationToken: ct);

Local development có thể dùng developer credential; trên Azure, DefaultAzureCredential có thể sử dụng Managed Identity của workload.

**Lưu ý:**
Managed Identity không tự tạo least privilege. Cấp role quá rộng vẫn là security risk. Đồng thời phải hiểu credential chain ở từng environment để tránh application vô tình dùng identity khác với identity bạn nghĩ đang được sử dụng.

### Tip 4 — MongoDB: thiết kế index từ query shape, không từ danh sách field

**Mẹo:**
Trước khi thêm compound index cho MongoDB, ghi rõ query shape gồm equality filters, sort và range; sau đó dùng explain() để xác minh số document/key được scan.

**Tại sao hữu ích:**
Index { tenantId: 1, status: 1, createdAt: -1 } có giá trị khi workload thực sự filter theo tenant/status rồi sort theo thời gian. Tạo index riêng cho từng field có thể vẫn khiến database scan nhiều dữ liệu hoặc cần in-memory sort.

**Ví dụ:**
    db.orders.find({
      tenantId: 42,
      status: "Pending"
    }).sort({ createdAt: -1 }).limit(50).explain("executionStats")

So sánh totalKeysExamined, totalDocsExamined và số kết quả trả về để đánh giá index thay vì chỉ thấy query “có dùng IXSCAN”.

**Lưu ý:**
Compound index tăng write cost và storage. Thứ tự field không có một công thức áp dụng tuyệt đối; cardinality, sort, range predicate và query variants thực tế phải được cân nhắc cùng nhau.

### Tip 5 — Chặn XSS bằng output encoding, đừng chỉ “lọc chuỗi nguy hiểm”

**Mẹo:**
Trong Vue.js/React.js, mặc định render dữ liệu người dùng như text và tránh v-html/dangerouslySetInnerHTML với content không tin cậy. Nếu business bắt buộc render HTML, dùng sanitizer được duy trì và policy allowlist rõ ràng.

**Tại sao hữu ích:**
Blacklist script tag không đủ: XSS có thể đi qua event handlers, malformed markup, URL schemes hoặc nhiều browser parsing contexts. Context-aware encoding và tránh raw HTML làm giảm attack surface ngay tại rendering boundary.

**Ví dụ:**
Một CMS cho editor nhập rich text. API lưu content, frontend cần render HTML. Thay vì tự xóa chuỗi script, hệ thống sanitize theo allowlist các tag/attribute được phép và kiểm soát URL schemes trước khi đưa content vào raw-HTML rendering path.

**Lưu ý:**
Sanitization không thay thế Content Security Policy, validation và secure cookie/token design. Cũng không sanitize bằng regex HTML tự viết; parser/browser semantics phức tạp hơn các pattern chuỗi đơn giản.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency cho cập nhật dữ liệu cạnh tranh

**Khái niệm:**
Optimistic Concurrency cho phép nhiều request đọc cùng dữ liệu nhưng phát hiện conflict tại lúc ghi bằng version/token như SQL Server rowversion hoặc application-managed concurrency token, thay vì khóa record trong toàn bộ thời gian người dùng thao tác.

**Vấn đề nó giải quyết:**
Trong CRM, hai nhân viên cùng mở Customer version 7. Người A cập nhật địa chỉ, người B cập nhật số điện thoại từ snapshot cũ. Nếu update cuối cùng ghi đè toàn row mà không kiểm tra version, thay đổi của A có thể bị mất âm thầm.

**Ví dụ thực tế:**
EF Core cấu hình rowversion làm concurrency token. UPDATE chứa điều kiện cả Id và version cũ; nếu affected rows bằng 0, EF Core phát DbUpdateConcurrencyException. Application có thể trả 409 Conflict, tải state mới và yêu cầu merge/retry theo rule nghiệp vụ.

**Trade-off:**
Optimistic Concurrency tránh giữ lock dài và phù hợp khi conflict hiếm, nhưng đẩy complexity sang conflict detection/resolution. Với contention rất cao hoặc invariant yêu cầu serialization chặt, database locking hay một coordination strategy khác có thể phù hợp hơn.

**Middle → Senior insight:**
Middle developer cần không nuốt DbUpdateConcurrencyException và phải bảo toàn concurrency token qua API contract. Senior / Technical developer phải quyết định conflict được reject, merge hay retry ở đâu; phân biệt technical retry với business conflict và chọn consistency mechanism dựa trên contention/invariant thực tế.

### Design 2 — Service Bus Queue vs Topic theo ownership của message

**Khái niệm:**
Queue phù hợp khi một logical work item cần được một consumer trong nhóm xử lý; Topic + subscriptions phù hợp khi một event cần được nhiều consumer độc lập nhận theo nhu cầu riêng. Đây là quyết định về delivery semantics và ownership, không chỉ về topology broker.

**Vấn đề nó giải quyết:**
Nếu OrderCreated được đưa vào một queue chung cho Billing, Analytics và Notification, các competing consumers sẽ chia nhau message thay vì mỗi capability nhận một bản. Ngược lại, dùng topic cho command chỉ có một owner có thể tạo ambiguity về ai chịu trách nhiệm thực thi.

**Ví dụ thực tế:**
GenerateInvoice là command có một processing owner nên có thể đi vào queue của Billing. OrderCreated là integration event; Billing, Analytics và Notification có subscription riêng, filter và dead-letter behavior riêng.

**Trade-off:**
Topic tăng khả năng fan-out và decouple consumers nhưng thêm subscription management, duplicate delivery, monitoring và cost. Queue đơn giản hơn cho work distribution nhưng không phù hợp để giả lập broadcast bằng cách để nhiều business consumers tranh cùng message.

**Middle → Senior insight:**
Middle developer cần hiểu at-least-once delivery, idempotent consumer và DLQ ở cả hai mô hình. Senior / Technical developer phải xác định message là command hay event, ownership, ordering, replay/evolution và failure isolation trước khi chọn topology; broker structure nên phản ánh domain responsibility.

### Design 3 — Anti-Corruption Layer khi tích hợp legacy hoặc third-party model

**Khái niệm:**
Anti-Corruption Layer (ACL) đặt translation boundary giữa domain của hệ thống và model/protocol bên ngoài. Thay vì để DTO, status code hoặc naming của vendor lan xuyên application, boundary chuyển chúng sang khái niệm nội bộ có ý nghĩa với domain.

**Vấn đề nó giải quyết:**
Một legacy ERP có thể dùng CustomerType = "A7" và field semantics khác hệ thống mới. Nếu mọi service hiểu trực tiếp "A7", dependency vào model của ERP lan rộng, khiến migration hoặc đổi provider trở nên tốn kém và business code khó hiểu.

**Ví dụ thực tế:**
Integration adapter map ERP response thành CustomerEligibility của domain, đồng thời cô lập retry, authentication và vendor error mapping. Application layer chỉ phụ thuộc contract nội bộ; khi ERP API đổi version, phần lớn thay đổi nằm ở adapter.

**Trade-off:**
ACL giảm coupling và bảo vệ domain language nhưng thêm mapping code, test và một abstraction cần duy trì. Với integration nhỏ, stable và chỉ dùng ở một nơi, một client adapter đơn giản có thể đủ; xây cả framework translation sẽ là over-engineering.

**Middle → Senior insight:**
Middle developer cần giữ external DTO ở integration boundary và viết mapping/test rõ ràng. Senior / Technical developer phải xác định boundary nào đáng bảo vệ, semantic mismatch nào cần translation và khi nào chi phí ACL vượt lợi ích; mục tiêu là cô lập volatility, không phải thêm layer theo pattern catalog.
