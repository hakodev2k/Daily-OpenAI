# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng dùng `ValueTask` thay `Task` theo mặc định

**Mẹo:**
Chỉ cân nhắc `ValueTask` khi method rất thường xuyên hoàn thành đồng bộ và allocation của `Task` thực sự là bottleneck đã được đo bằng profiling.

**Tại sao hữu ích:**
`ValueTask` có thể giảm allocation trên hot path, nhưng đổi lại API phức tạp hơn và dễ bị dùng sai. Trong phần lớn application code, `Task` vẫn là lựa chọn đơn giản và an toàn hơn.

**Ví dụ:**
```csharp
public ValueTask<User?> GetCachedUserAsync(Guid id)
{
    if (_cache.TryGetValue(id, out User? user))
    {
        return ValueTask.FromResult(user);
    }

    return new ValueTask<User?>(LoadFromDatabaseAsync(id));
}
```

**Lưu ý:**
Một `ValueTask` không nên bị `await` nhiều lần hoặc được lưu giữ tùy tiện. Nếu không có dữ liệu profiling chứng minh lợi ích, dùng `Task` để giảm complexity.

### Tip 2 — Dùng `AsSplitQuery()` khi `Include` tạo Cartesian explosion

**Mẹo:**
Trong EF Core, nếu một query `Include` nhiều collection khiến SQL join nhân số dòng rất lớn, cân nhắc `AsSplitQuery()` để tách thành nhiều query nhỏ hơn.

**Tại sao hữu ích:**
Giảm duplicated row data và lượng dữ liệu truyền từ database khi một aggregate có nhiều collection con.

**Ví dụ:**
```csharp
var orders = await dbContext.Orders
    .Include(x => x.Items)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .Where(x => x.CustomerId == customerId)
    .ToListAsync();
```

**Lưu ý:**
Split query tạo nhiều round trips và có thể quan sát dữ liệu ở các thời điểm hơi khác nhau nếu không nằm trong transaction phù hợp. Đừng bật chỉ vì query có `Include`; hãy xem execution plan và lượng dữ liệu thực tế.

### Tip 3 — Viết predicate SQL theo kiểu SARGable để index có cơ hội được dùng

**Mẹo:**
Tránh bọc indexed column trong function ở `WHERE` nếu có thể rewrite predicate thành range comparison.

**Tại sao hữu ích:**
Predicate SARGable giúp database có thể dùng index seek thay vì scan toàn bộ tập dữ liệu.

**Ví dụ:**
Tránh:

```sql
WHERE CAST(CreatedAt AS DATE) = @Date
```

Ưu tiên:

```sql
WHERE CreatedAt >= @Date
  AND CreatedAt < DATEADD(day, 1, @Date)
```

**Lưu ý:**
Không phải query nào rewrite cũng tự động nhanh hơn. Cardinality, index design và statistics vẫn quyết định execution plan cuối cùng.

### Tip 4 — Dùng `git worktree` để làm hai branch song song mà không stash liên tục

**Mẹo:**
Khi đang làm feature nhưng cần sửa gấp production bug trên branch khác, dùng `git worktree` để có thêm working directory cho cùng repository.

**Tại sao hữu ích:**
Không cần commit tạm, stash hoặc đổi branch liên tục. Mỗi worktree giữ working state riêng.

**Ví dụ:**
```bash
git worktree add ../app-hotfix origin/main
cd ../app-hotfix
git switch -c hotfix/payment-timeout
```

Kiểm tra các worktree:

```bash
git worktree list
```

**Lưu ý:**
Một branch không thể được checkout đồng thời ở hai worktree. Khi xóa directory thủ công, nên chạy `git worktree prune` để dọn metadata cũ.

### Tip 5 — Dùng `dotnet-trace` khi CPU spike nhưng logs không nói được nguyên nhân

**Mẹo:**
Khi một .NET process dùng CPU cao, thu runtime trace trong khoảng ngắn rồi phân tích call stacks thay vì thêm log ngẫu nhiên vào code.

**Tại sao hữu ích:**
Trace giúp thấy method nào tiêu tốn CPU, GC activity, contention và execution path thực tế mà không cần đoán bottleneck.

**Ví dụ:**
```bash
dotnet-trace collect --process-id <PID>
```

Hoặc giới hạn thời gian:

```bash
dotnet-trace collect --process-id <PID> --duration 00:00:30
```

Sau đó mở file trace bằng công cụ hỗ trợ như PerfView hoặc Visual Studio Profiler.

**Lưu ý:**
Tracing có overhead. Trên production nên thu trong khoảng ngắn, đúng process và đúng thời điểm sự cố thay vì bật kéo dài không kiểm soát.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency thay vì khóa record lâu

**Khái niệm:**
Optimistic Concurrency cho phép nhiều request đọc cùng dữ liệu nhưng kiểm tra version khi update. Nếu dữ liệu đã bị thay đổi từ lúc đọc, update bị từ chối thay vì âm thầm overwrite.

**Vấn đề nó giải quyết:**
Hai người cùng sửa một entity có thể tạo lost update. Pessimistic lock tránh được nhưng giữ lock lâu và giảm concurrency trong hệ thống có nhiều request.

**Ví dụ thực tế:**
Một màn hình chỉnh sửa employee đọc record có `RowVersion`. User A và User B cùng mở dữ liệu. A lưu trước, làm version thay đổi. Khi B lưu bằng version cũ, EF Core ném `DbUpdateConcurrencyException`, application yêu cầu reload hoặc merge thay đổi.

```csharp
public byte[] RowVersion { get; set; } = default!;
```

```csharp
builder.Property(x => x.RowVersion)
    .IsRowVersion();
```

**Trade-off:**
Lợi ích là throughput cao hơn và không giữ database lock trong thời gian user thao tác. Chi phí là application phải xử lý conflict rõ ràng; với dữ liệu bị tranh chấp thường xuyên, retry hoặc merge có thể trở nên phức tạp.

**Middle → Senior insight:**
Middle developer cần hiểu `DbUpdateConcurrencyException` không chỉ là lỗi kỹ thuật mà biểu diễn business conflict. Senior developer phải quyết định conflict nào retry tự động, conflict nào merge và conflict nào phải trả về cho người dùng xử lý.

### Design 2 — Rate Limiting và Backpressure phải được thiết kế cùng nhau

**Khái niệm:**
Rate Limiting giới hạn lượng request được nhận trong một khoảng thời gian. Backpressure kiểm soát điều gì xảy ra khi tốc độ producer lớn hơn khả năng xử lý của consumer.

**Vấn đề nó giải quyết:**
Nếu hệ thống tiếp tục nhận vô hạn request hoặc message khi downstream đang chậm, queue, memory, connection pool và latency có thể tăng cho đến khi toàn hệ thống sụp đổ.

**Ví dụ thực tế:**
Một API export chỉ xử lý ổn định 20 jobs đồng thời. Thay vì nhận mọi request rồi tạo hàng nghìn background tasks, API giới hạn request, đưa phần hợp lệ vào bounded queue và trả `429 Too Many Requests` hoặc yêu cầu client retry khi capacity đã đầy.

**Trade-off:**
Lợi ích là bảo vệ hệ thống và giữ latency có kiểm soát. Chi phí là một số workload bị reject hoặc trì hoãn, đồng thời cần định nghĩa fairness, queue capacity, retry policy và priority.

**Middle → Senior insight:**
Middle developer nên hiểu `429`, bounded queue và concurrency limit. Senior developer cần thiết kế admission control dựa trên thực tế capacity, xác định nơi reject sớm nhất và tránh retry storm giữa nhiều service.

### Design 3 — Composition over Inheritance cho behavior thay đổi độc lập

**Khái niệm:**
Composition over Inheritance ưu tiên kết hợp các behavior nhỏ qua interface hoặc object composition thay vì tạo một hierarchy kế thừa sâu chỉ để thay đổi vài hành vi.

**Vấn đề nó giải quyết:**
Inheritance hierarchy thường trở nên cứng khi các dimension thay đổi độc lập. Một class con phải kế thừa cả behavior cần và không cần, khiến sửa base class dễ tạo regression cho nhiều nhánh.

**Ví dụ thực tế:**
Một hệ thống notification có nhiều channel và retry strategy. Thay vì tạo `EmailRetryNotification`, `SmsRetryNotification`, `EmailNoRetryNotification`..., tách behavior:

```csharp
public interface INotificationSender
{
    Task SendAsync(Message message, CancellationToken cancellationToken);
}

public interface IRetryPolicy
{
    Task ExecuteAsync(Func<Task> action);
}
```

Sau đó compose `EmailSender` với `ExponentialBackoffRetryPolicy` theo configuration.

**Trade-off:**
Composition linh hoạt, test dễ hơn và giảm coupling vào base class. Đổi lại số lượng abstraction/object có thể tăng; nếu behavior rất đơn giản và ổn định, inheritance nhỏ vẫn có thể dễ đọc hơn.

**Middle → Senior insight:**
Middle developer nên nhận ra khi hierarchy bắt đầu chứa nhiều override và condition đặc biệt. Senior developer phải biết đâu là behavior thực sự thay đổi độc lập để tách thành composition, thay vì biến mọi class thành một tập interface quá nhỏ và khó theo dõi.
