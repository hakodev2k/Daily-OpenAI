# Daily Developer Tips & Design — 2026-09-12

## 🛠 Developer Tips & Tricks

### Tip 1 — Partition ASP.NET Core Rate Limiting theo tenant hoặc user, không chỉ theo IP

**Mẹo:**
Khi bật Rate Limiting cho API có authentication hoặc multi-tenant, cân nhắc partition limiter theo `UserId`, `TenantId` hoặc API key thay vì chỉ dùng remote IP.

**Tại sao hữu ích:**
IP không phải lúc nào cũng đại diện cho một caller. Nhiều user có thể đi qua cùng NAT/proxy và một attacker cũng có thể phân tán request qua nhiều IP. Partition theo identity làm quota bám sát consumer thực tế hơn.

**Ví dụ:**
```csharp
options.AddPolicy("per-user", context =>
    RateLimitPartition.GetFixedWindowLimiter(
        context.User.Identity?.Name ?? context.Connection.RemoteIpAddress?.ToString() ?? "anonymous",
        _ => new FixedWindowRateLimiterOptions
        {
            PermitLimit = 100,
            Window = TimeSpan.FromMinutes(1)
        }));
```

Nếu API phục vụ SaaS B2B, `TenantId` thường còn phù hợp hơn `UserId` cho shared quota.

**Lưu ý:**
Đừng tin `X-Forwarded-For` nếu proxy chain chưa được cấu hình `ForwardedHeaders` an toàn. Rate limit cũng không thay thế authorization, abuse detection hoặc quota nghiệp vụ.

### Tip 2 — Dùng `FOR UPDATE SKIP LOCKED` để nhiều worker lấy job mà không chặn nhau

**Mẹo:**
Nếu PostgreSQL được dùng như một job table nhỏ và nhiều worker cùng polling, có thể dùng `FOR UPDATE SKIP LOCKED` để mỗi worker lấy các row chưa bị worker khác khóa.

**Tại sao hữu ích:**
Nếu các worker cùng `SELECT` row `Pending`, chúng có thể tranh cùng job hoặc block nhau. `SKIP LOCKED` cho phép worker bỏ qua row đang được xử lý và tiếp tục lấy work khác.

**Ví dụ:**
```sql
BEGIN;

SELECT id
FROM jobs
WHERE status = 'Pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 20;

-- mark selected jobs as Processing
COMMIT;
```

Cách này phù hợp với workload vừa phải khi chưa cần message broker riêng.

**Lưu ý:**
Job table vẫn cần retry, timeout, recovery cho row mắc kẹt ở `Processing` và index phù hợp. Khi throughput, fan-out hoặc retention tăng mạnh, broker chuyên dụng thường vận hành tốt hơn database polling.

### Tip 3 — Phân biệt Kubernetes `readinessProbe` và `livenessProbe` để tránh restart sai nguyên nhân

**Mẹo:**
Dùng `readinessProbe` để quyết định pod có nên nhận traffic và `livenessProbe` để phát hiện process thật sự không thể tự phục hồi. Không dùng cùng một dependency check cho cả hai theo thói quen.

**Tại sao hữu ích:**
Nếu database tạm thời unavailable mà liveness probe cũng fail, Kubernetes có thể restart toàn bộ pod dù restart không sửa được database. Điều này làm outage nặng hơn và tạo restart storm.

**Ví dụ:**
```text
readiness:
- application startup xong
- dependency bắt buộc hiện có thể phục vụ request

liveness:
- process/event loop còn sống
- internal deadlock hoặc unrecoverable state không xảy ra
```

Một API mất Redis cache có thể vẫn live và thậm chí vẫn ready nếu có fallback phù hợp.

**Lưu ý:**
Probe quá nhạy gây flapping; probe quá chậm kéo dài time-to-recovery. Cấu hình threshold dựa trên startup time và failure mode thực tế, không copy mặc định giữa các service.

### Tip 4 — Dùng mutation testing để phát hiện test chỉ “chạy qua code” nhưng không bắt lỗi

**Mẹo:**
Với business logic quan trọng, thỉnh thoảng dùng mutation testing để kiểm tra test suite có thực sự phát hiện thay đổi sai logic hay chỉ đạt coverage cao.

**Tại sao hữu ích:**
Code coverage chỉ cho biết dòng code đã được execute. Một test có thể chạy qua điều kiện quan trọng nhưng không assert kết quả đủ mạnh. Mutation testing cố tình đổi toán tử/condition rồi kiểm tra test có fail hay không.

**Ví dụ:**
```text
Original:
if (total >= 1_000_000) ApplyDiscount();

Mutation:
if (total > 1_000_000) ApplyDiscount();
```

Nếu toàn bộ test vẫn pass, boundary case `1_000_000` đang thiếu assertion hữu ích.

**Lưu ý:**
Mutation testing tốn CPU và có thể chậm trên solution lớn. Nên tập trung vào domain-critical project hoặc chạy định kỳ thay vì bắt mọi PR nhỏ phải mutation-test toàn repository.

### Tip 5 — Kiểm tra package vulnerability từ CLI thay vì chờ production scanner phát hiện

**Mẹo:**
Trong .NET repository, thêm bước kiểm tra dependency vulnerability trong local workflow hoặc CI để thấy package có advisory trước khi release.

**Tại sao hữu ích:**
Một application có thể không thay code nhưng vẫn mang dependency version có CVE. Phát hiện sớm giúp team đánh giá upgrade impact trước khi security issue trở thành hotfix production.

**Ví dụ:**
```bash
dotnet list package --vulnerable --include-transitive
```

Với monorepo, có thể chạy theo solution/project và lưu kết quả vào pipeline artifact để review.

**Lưu ý:**
Không nâng package major version tự động chỉ vì scanner báo advisory. Cần xác nhận affected path, fixed version, breaking changes và test regression; một package transitively vulnerable nhưng feature không reachable vẫn cần đánh giá rủi ro có evidence.

## 🧠 Software Design

### Design 1 — Azure Service Bus Queue vs Topic theo delivery topology

**Khái niệm:**
Queue phù hợp khi một message cần được xử lý bởi một consumer group theo competing-consumer model. Topic + Subscription phù hợp khi cùng một event cần fan-out tới nhiều consumer độc lập.

**Vấn đề nó giải quyết:**
Nếu `OrderPaid` phải đồng thời kích hoạt Shipping, Email và Analytics, một queue duy nhất khiến các consumer cạnh tranh lấy cùng message thay vì mỗi capability nhận một bản sao logic của event.

**Ví dụ thực tế:**
```text
Queue: GenerateInvoice
-> nhiều worker cùng loại
-> mỗi message chỉ một worker xử lý thành công

Topic: OrderPaid
-> Shipping subscription
-> Email subscription
-> Analytics subscription
```

Mỗi subscription có thể có filter, retry và dead-letter behavior riêng.

**Trade-off:**
Queue đơn giản hơn cho work distribution và backpressure. Topic tăng decoupling/fan-out nhưng thêm subscription lifecycle, duplicate delivery, schema evolution và observability trên nhiều consumer.

**Middle → Senior insight:**
Middle developer cần hiểu competing consumers, subscriptions và idempotent processing. Senior / Technical developer phải chọn topology dựa trên business ownership, fan-out requirement, replay/failure isolation và cách event contract sẽ tiến hóa theo thời gian.

### Design 2 — Clean Architecture vs Layered Architecture: chọn boundary theo change pressure

**Khái niệm:**
Clean Architecture nhấn mạnh dependency hướng vào business core và cô lập infrastructure qua boundary rõ. Layered Architecture đơn giản hơn, thường tổ chức Presentation → Business → Data. Cả hai đều có thể đúng tùy độ phức tạp hệ thống.

**Vấn đề nó giải quyết:**
Một hệ thống có nhiều integration, domain rule và thay đổi infrastructure thường hưởng lợi từ boundary mạnh. Nhưng CRUD application nhỏ có thể bị chôn trong interface, mapper và project ceremony nếu áp Clean Architecture đầy đủ.

**Ví dụ thực tế:**
```text
Internal admin CRUD:
- 20 màn hình
- business rule ít
- một database
=> Layered Architecture có thể đủ

Pricing engine:
- domain rule phức tạp
- nhiều datasource/provider
- test domain độc lập cần thiết
=> boundary kiểu Clean Architecture đáng giá hơn
```

**Trade-off:**
Clean Architecture tăng testability và giảm infrastructure coupling nhưng thêm abstraction và mapping cost. Layered Architecture ít ceremony hơn nhưng dễ để data/infrastructure concern lan vào business logic nếu không giữ discipline.

**Middle → Senior insight:**
Middle developer cần hiểu dependency direction và tránh leak concern giữa layer. Senior / Technical developer phải chọn mức abstraction tối thiểu đủ cho change pressure, team size và system lifetime thay vì coi số project nhiều hơn là kiến trúc tốt hơn.

### Design 3 — Shared Database vs Database-per-Service theo ownership và consistency requirement

**Khái niệm:**
Shared Database cho nhiều service/module cùng dùng một database/schema hoặc cùng datastore. Database-per-Service trao ownership dữ liệu cho từng service và buộc integration đi qua contract/event thay vì query trực tiếp dữ liệu của nhau.

**Vấn đề nó giải quyết:**
Khi các service release độc lập nhưng cùng sửa/query một schema, coupling qua database làm migration, ownership và backward compatibility khó kiểm soát. Ngược lại, tách database quá sớm làm các join/transaction đơn giản biến thành distributed workflow.

**Ví dụ thực tế:**
```text
Team nhỏ + Modular Monolith:
Orders và Billing cùng SQL Server nhưng schema/boundary rõ
=> shared physical database có thể hợp lý

Hai service độc lập:
Orders service owns Orders DB
Billing service owns Billing DB
=> trao đổi qua API/event
=> không query bảng của nhau
```

**Trade-off:**
Shared Database đơn giản cho transaction, reporting và operations nhưng tăng schema coupling. Database-per-Service tăng autonomy và fault isolation nhưng thêm eventual consistency, duplicated data, integration và operational cost.

**Middle → Senior insight:**
Middle developer cần tôn trọng data ownership và không bypass service contract bằng query trực tiếp. Senior / Technical developer phải cân bằng autonomy, transaction requirement, reporting needs, team ownership và operational maturity trước khi tách datastore.
