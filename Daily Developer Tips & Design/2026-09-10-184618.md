# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng bounded `Channel<T>` để tạo backpressure trong `BackgroundService`

**Mẹo:**
Nếu producer có thể tạo work nhanh hơn consumer xử lý, ưu tiên bounded `Channel<T>` thay vì queue tăng không giới hạn trong memory.

**Tại sao hữu ích:**
Queue không giới hạn thường chỉ chuyển bottleneck thành memory growth. Bounded channel buộc hệ thống thể hiện pressure rõ ràng: producer phải chờ, drop theo policy hoặc từ chối work thay vì âm thầm tích lũy hàng trăm nghìn item.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = false
});

await channel.Writer.WriteAsync(job, ct);
```

Consumer trong `BackgroundService` đọc từ `channel.Reader.ReadAllAsync(stoppingToken)` và xử lý theo concurrency phù hợp.

**Lưu ý:**
Backpressure chỉ hiệu quả khi upstream biết xử lý trạng thái chờ hoặc từ chối. Nếu HTTP request bị block quá lâu để chờ queue trống, bạn có thể cần trả `429/503`, persist work vào broker hoặc thay đổi admission-control strategy.

### Tip 2 — Chuẩn hóa lỗi API bằng `ProblemDetails` thay vì tự chế response ở từng endpoint

**Mẹo:**
Trong ASP.NET Core, dùng `ProblemDetails` và exception handling tập trung để error contract nhất quán giữa validation, domain error và unexpected failure.

**Tại sao hữu ích:**
Khi mỗi controller trả một shape lỗi khác nhau, frontend/mobile client phải viết branching logic riêng và production logs khó correlate. Một contract chuẩn giúp client xử lý predictable hơn và giảm duplication.

**Ví dụ:**
```csharp
builder.Services.AddProblemDetails();

app.UseExceptionHandler();
app.UseStatusCodePages();
```

Có thể map domain exception thành status code và extension field ổn định như `errorCode`, đồng thời giữ stack trace khỏi response production.

**Lưu ý:**
Đừng trả toàn bộ exception message hoặc internal object vào `ProblemDetails`. Error contract nên hữu ích cho client nhưng không làm lộ SQL, secret, file path hay implementation detail.

### Tip 3 — Chặn SSRF bằng outbound allowlist và validation ở tầng network, không chỉ regex URL

**Mẹo:**
Nếu application nhận URL từ user rồi gọi outbound HTTP, giới hạn destination được phép và kiểm soát redirect/DNS behavior thay vì chỉ kiểm tra chuỗi URL ban đầu.

**Tại sao hữu ích:**
Một URL nhìn hợp lệ có thể resolve tới loopback, private IP, metadata endpoint hoặc redirect sang destination nội bộ. Regex đơn giản không bảo vệ được DNS rebinding và redirect chain.

**Ví dụ:**
```text
Cho phép:
- https
- host thuộc allowlist đối tác
- port được kiểm soát

Từ chối:
- localhost / loopback
- private/link-local ranges
- metadata endpoints
- redirect ra ngoài allowlist
```

Với integration cố định, tốt hơn là lưu base URL phía server và chỉ cho user truyền identifier/path hợp lệ thay vì arbitrary URL.

**Lưu ý:**
Validation application-level không thay thế egress firewall/network policy. Defense-in-depth quan trọng vì hostname có thể thay đổi resolution theo thời gian.

### Tip 4 — Thay đổi Elasticsearch mapping lớn nên dùng index mới + alias swap

**Mẹo:**
Khi cần đổi analyzer, field type hoặc mapping không tương thích, tạo index mới, reindex dữ liệu rồi atomically chuyển alias thay vì cố mutate index hiện tại.

**Tại sao hữu ích:**
Nhiều thay đổi mapping không thể áp dụng ngược lên field đã index. Alias giúp application tiếp tục query tên logic ổn định trong khi migration diễn ra phía sau.

**Ví dụ:**
```text
products-v12  <- alias: products

1. create products-v13 với mapping mới
2. reindex v12 -> v13
3. verify document count + query behavior
4. switch alias products -> products-v13
5. giữ v12 trong rollback window
```

**Lưu ý:**
Reindex không tự đảm bảo consistency nếu source vẫn đang nhận write. Cần dual-write, change capture hoặc sync delta trước alias swap tùy yêu cầu downtime và freshness.

### Tip 5 — Dùng `git reflog` để cứu commit tưởng đã mất sau `reset` hoặc rebase

**Mẹo:**
Nếu vừa `reset --hard`, rebase hoặc move branch sai và commit biến mất khỏi `git log`, kiểm tra `git reflog` trước khi kết luận code đã mất.

**Tại sao hữu ích:**
Git thường vẫn giữ object một thời gian dù branch pointer không còn trỏ tới commit. Reflog ghi lịch sử thay đổi của `HEAD` và refs local, rất hữu ích khi thao tác lịch sử nhầm.

**Ví dụ:**
```bash
git reflog
# tìm SHA trước khi reset/rebase

git switch -c rescue-work <sha>
```

Tạo branch mới ngay khi tìm được commit cần cứu để tránh phụ thuộc vào thời gian retention của unreachable objects.

**Lưu ý:**
Reflog chủ yếu là local và không phải backup lâu dài. Nếu repository đã garbage-collect object hoặc bạn đang ở máy khác, commit có thể không còn phục hồi được theo cách này.

## 🧠 Software Design

### Design 1 — Azure Functions vs Worker Service theo execution model, không theo độ “cloud-native”

**Khái niệm:**
Azure Functions phù hợp với event-triggered workload có lifecycle ngắn hoặc scale theo trigger; Worker Service phù hợp hơn khi process cần chạy liên tục, kiểm soát concurrency/lifecycle sâu hoặc giữ long-lived connection/state trong process.

**Vấn đề nó giải quyết:**
Team dễ chọn Functions cho mọi background job vì deployment đơn giản, hoặc chọn Worker cho mọi thứ vì quen .NET. Hai execution model có failure mode, scaling và operational behavior khác nhau.

**Ví dụ thực tế:**
```text
Resize ảnh khi Blob xuất hiện
-> Azure Function có thể phù hợp

Consumer xử lý stream liên tục,
giữ connection lâu và cần custom throttling
-> Worker Service có thể rõ ràng hơn
```

**Trade-off:**
Functions giảm infrastructure management và scale thuận tiện nhưng có cold start, execution/runtime constraint và platform-specific behavior. Worker Service cho control tốt hơn nhưng bạn phải tự vận hành hosting, scaling, health checks và deployment.

**Middle → Senior insight:**
Middle developer cần hiểu trigger, retry và cancellation lifecycle của từng model. Senior / Technical developer phải chọn dựa trên workload shape, latency, execution duration, cost, observability, scaling behavior và operational ownership — không dựa trên nhãn serverless.

### Design 2 — Optimistic vs Pessimistic Concurrency theo contention và business invariant

**Khái niệm:**
Optimistic concurrency giả định conflict hiếm và phát hiện xung đột lúc update; pessimistic concurrency giữ lock để ngăn actor khác sửa dữ liệu trong critical section.

**Vấn đề nó giải quyết:**
Hai user cùng sửa một resource có thể tạo lost update hoặc vi phạm invariant. Cách xử lý phù hợp phụ thuộc xác suất conflict, thời gian giữ transaction và khả năng retry của business flow.

**Ví dụ thực tế:**
```text
Chỉnh profile người dùng
-> optimistic concurrency với version/rowversion thường hợp lý

Phân bổ một resource cực khan hiếm trong transaction ngắn
-> pessimistic locking có thể đáng cân nhắc
```

Với EF Core, concurrency token cho phép phát hiện khi `UPDATE` không còn match version đã đọc.

**Trade-off:**
Optimistic concurrency giảm lock contention nhưng caller phải xử lý conflict/retry/merge. Pessimistic locking đơn giản hóa một số critical section nhưng tăng blocking, deadlock risk và giảm throughput nếu lock giữ lâu.

**Middle → Senior insight:**
Middle developer cần tránh silent overwrite và biết xử lý concurrency exception. Senior / Technical developer phải đánh giá contention rate, transaction duration, retry semantics, user experience và invariant trước khi chọn cơ chế khóa.

### Design 3 — Contract Testing để giảm phụ thuộc vào E2E test giữa service

**Khái niệm:**
Contract testing kiểm tra provider và consumer cùng tuân thủ một interface đã thỏa thuận mà không cần dựng toàn bộ hệ thống end-to-end cho mọi test case.

**Vấn đề nó giải quyết:**
E2E test xuyên nhiều service thường chậm, brittle và khó xác định root cause. Unit test lại không phát hiện provider đã đổi field, status code hoặc semantics mà consumer đang phụ thuộc.

**Ví dụ thực tế:**
```text
Orders API consumer kỳ vọng:
GET /customers/{id}
-> 200
-> id, displayName, status

Contract test xác nhận Customer service
vẫn cung cấp đúng behavior đó ở build pipeline.
```

Contract không nên chỉ snapshot toàn bộ JSON; nó nên mô tả những behavior consumer thực sự phụ thuộc.

**Trade-off:**
Contract testing phát hiện incompatibility sớm và giảm số lượng E2E test cần thiết, nhưng thêm artifact/versioning và coordination giữa teams. Nó cũng không thay thế test cho network failure, authentication flow hoặc production topology thật.

**Middle → Senior insight:**
Middle developer cần biết consumer phụ thuộc vào phần nào của API contract. Senior / Technical developer phải thiết kế ownership, versioning, provider verification và migration policy để contract test hỗ trợ evolution thay vì khóa chặt implementation.
