# Daily Developer Tips & Design — 2026-09-29

## 🛠 Developer Tips & Tricks

### Tip 1 — Bắt EF Core optimistic concurrency bằng concurrency token

**Mẹo:**
Với dữ liệu có nhiều người cùng sửa, dùng concurrency token như SQL Server `rowversion` để phát hiện bản ghi đã thay đổi kể từ lúc đọc thay vì để “last write wins” âm thầm ghi đè.

**Tại sao hữu ích:**
EF Core đưa concurrency token vào `WHERE` của `UPDATE`. Nếu database trả về 0 affected rows, `DbUpdateConcurrencyException` cho biết state đã bị thay đổi bởi transaction khác. Đây là cơ chế phát hiện conflict, không phải database lock.

**Ví dụ:**
```csharp
public class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }

    [Timestamp]
    public byte[] Version { get; set; } = [];
}

try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    // reload, merge hoặc trả 409 Conflict tùy business rule
}
```
Hai nhân viên sửa cùng giá sản phẩm: request thứ hai phải xử lý conflict có chủ đích thay vì ghi đè thay đổi đầu tiên.

**Lưu ý:**
Đừng tự động retry rồi overwrite dữ liệu mới; conflict resolution là quyết định nghiệp vụ. Với aggregate phức tạp, cần xác định field nào có thể merge và field nào phải yêu cầu user xác nhận.

### Tip 2 — Chẩn đoán connection-pool exhaustion từ thời gian giữ connection

**Mẹo:**
Khi API bắt đầu timeout chờ database connection, đo số connection đang dùng và thời gian chúng bị giữ; đừng lập tức tăng `Max Pool Size`.

**Tại sao hữu ích:**
Pool exhaustion thường là hậu quả của slow query, transaction dài, streaming giữ reader, hoặc code không dispose resource đúng lúc. Tăng pool có thể chỉ chuyển bottleneck sang SQL Server và làm database nhận nhiều concurrent work hơn.

**Ví dụ:**
Một endpoint tăng từ 300 ms lên 8 giây. SQL CPU vẫn vừa phải nhưng telemetry cho thấy request mất phần lớn thời gian trước khi query bắt đầu. Trace tiếp theo phát hiện transaction giữ connection trong lúc gọi external API. Rút HTTP call khỏi transaction làm pool phục hồi mà không cần tăng kích thước.

**Lưu ý:**
Pool size vẫn là tuning parameter hợp lệ khi concurrency thực sự cần thiết, nhưng phải đối chiếu với database capacity, query latency và số application instances.

### Tip 3 — Dùng Managed Identity thay cho secret khi App Service truy cập Key Vault

**Mẹo:**
Khi Azure workload hỗ trợ identity-based authentication, ưu tiên Managed Identity và RBAC thay vì lưu client secret trong configuration hoặc pipeline variable.

**Tại sao hữu ích:**
Managed Identity loại bỏ vòng đời phân phối/rotate credential khỏi application. Token được Azure cấp cho workload identity và quyền có thể giới hạn theo least privilege.

**Ví dụ:**
ASP.NET Core chạy trên Azure App Service dùng `DefaultAzureCredential` để đọc secret cần thiết từ Azure Key Vault. Production dùng Managed Identity; local development có thể dùng developer credential phù hợp mà không nhúng secret production vào `appsettings.json`.

**Lưu ý:**
Managed Identity không tự động bảo đảm least privilege. Quyền Key Vault quá rộng vẫn là rủi ro; đồng thời cần phân biệt lỗi identity, RBAC và network/firewall khi troubleshooting.

### Tip 4 — Dùng Playwright locator theo semantics thay vì DOM structure

**Mẹo:**
Trong E2E tests, ưu tiên locator theo role, accessible name hoặc stable test contract thay vì selector phụ thuộc sâu vào CSS/DOM.

**Tại sao hữu ích:**
Selector như `.card > div:nth-child(2) button` khiến refactor UI không đổi behavior vẫn phá test. Semantic locator kiểm tra gần với cách user tương tác và đồng thời khuyến khích accessibility tốt hơn.

**Ví dụ:**
```ts
await page.getByRole('button', { name: 'Save' }).click();
await expect(page.getByRole('status')).toHaveText('Saved');
```
Test vẫn sống khi team thay layout từ flex sang grid nếu contract người dùng không đổi.

**Lưu ý:**
Không biến `data-testid` thành mặc định cho mọi element. Nó hữu ích khi không có semantic hook ổn định, nhưng test vẫn phải tập trung vào observable behavior thay vì implementation detail.

### Tip 5 — Kiểm tra cache headers ở CDN và browser như hai lớp riêng

**Mẹo:**
Khi web/CMS trả nội dung stale, inspect `Cache-Control`, `Age`, CDN headers và browser cache riêng biệt trước khi purge mọi thứ.

**Tại sao hữu ích:**
Một response có thể được cache tại browser, CDN hoặc origin application với TTL khác nhau. Xác định layer đang phục vụ stale object giúp sửa đúng policy thay vì dùng purge như giải pháp thường trực.

**Ví dụ:**
Trang product đã publish giá mới nhưng một nhóm user vẫn thấy giá cũ. Request trực tiếp origin đúng, CDN response có `Age` cao và cache key không phân biệt locale. Root cause nằm ở delivery policy, không phải CMS database.

**Lưu ý:**
Không cache response chứa dữ liệu cá nhân/public-private không đúng semantics. Cache key thiếu header/query dimension quan trọng có thể gây lỗi correctness hoặc rò rỉ dữ liệu nghiêm trọng.

## 🧠 Software Design

### Design 1 — Queue hay Topic trong Azure Service Bus

**Khái niệm:**
Queue phù hợp khi một logical consumer xử lý mỗi message; Topic + subscriptions phù hợp khi cùng một event cần được nhiều consumer độc lập nhận theo fan-out/filtering.

**Vấn đề nó giải quyết:**
Hệ thống cần tách producer khỏi consumer nhưng topology phải phản ánh ownership: “một công việc cần được xử lý” khác với “một sự kiện nhiều bên quan tâm”.

**Ví dụ thực tế:**
`GenerateInvoice` là command được một billing worker xử lý nên queue hợp lý. `OrderCompleted` cần inventory, analytics và notification phản ứng độc lập nên topic với ba subscriptions phù hợp hơn.

**Trade-off:**
Queue đơn giản hơn về vận hành và semantics. Topic tăng extensibility nhưng thêm subscriptions, retry/DLQ, monitoring và khả năng các consumer tiến triển không đồng bộ.

**Middle → Senior insight:**
Middle cần hiểu delivery, retry và consumer idempotency. Senior cần chọn topology từ business semantics, ownership, failure isolation và nhu cầu evolution; không dùng pub/sub chỉ vì “event-driven” nghe hiện đại.

### Design 2 — SQL hay NoSQL dựa trên access pattern và consistency

**Khái niệm:**
Chọn datastore từ invariant, query pattern, consistency, scale và operational constraints thay vì từ hình dạng JSON của object.

**Vấn đề nó giải quyết:**
Relational model mạnh ở transaction, constraints và flexible joins; document/partitioned stores có thể phù hợp hơn khi aggregate tự chứa, access pattern rõ và cần phân phối dữ liệu ở quy mô lớn.

**Ví dụ thực tế:**
Order/payment cần transaction và relational integrity có thể ở SQL Server. Một catalog cực lớn đọc chủ yếu theo product/partition với schema linh hoạt có thể phù hợp Cosmos DB, nếu partition key và RU economics được thiết kế đúng.

**Trade-off:**
NoSQL có thể giảm impedance cho một số access pattern nhưng chuyển complexity sang denormalization, partitioning và consistency. SQL mạnh về integrity/query flexibility nhưng cũng cần scale/tuning có chủ đích.

**Middle → Senior insight:**
Middle phải model/query đúng datastore đã chọn. Senior phải chứng minh lựa chọn bằng workload, invariant, growth model, failure behavior, cost và khả năng vận hành của team—kể cả quyết định giữ SQL vì nó đơn giản hơn.

### Design 3 — Feature flag tách deployment khỏi release

**Khái niệm:**
Feature flag cho phép deploy code trước nhưng kiểm soát lúc và đối tượng được kích hoạt behavior mới, thay vì coi deployment đồng nghĩa release.

**Vấn đề nó giải quyết:**
Một thay đổi lớn cần rollout dần, canary theo user/tenant hoặc khả năng tắt nhanh khi production metrics xấu mà không nhất thiết rollback toàn artifact.

**Ví dụ thực tế:**
Checkout engine mới được deploy cùng phiên bản cũ. Team bật cho internal users, sau đó 5%, 25%, 100% traffic trong khi theo dõi conversion, error rate và latency; nếu failure tăng, flag quay về implementation cũ.

**Trade-off:**
Flag giảm release risk nhưng tạo thêm branch logic, test matrix và technical debt. Flag tồn tại lâu có thể khiến code khó reasoning và tạo những tổ hợp state chưa được test.

**Middle → Senior insight:**
Middle cần implement flag an toàn và test cả on/off paths. Senior cần thiết kế lifecycle, owner, cleanup date, observability và quyết định khi nào flag không đủ—ví dụ schema migration không backward-compatible vẫn cần chiến lược expand/contract.
