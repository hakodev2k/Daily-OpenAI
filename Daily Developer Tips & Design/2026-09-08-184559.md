# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt `Task.WhenAll` với parallelism thật sự trong .NET

**Mẹo:**
Dùng `Task.WhenAll` khi bạn có nhiều I/O-bound operation độc lập cần chạy đồng thời, nhưng đừng mặc định rằng nó tạo thêm thread hoặc phù hợp với CPU-bound workload.

**Tại sao hữu ích:**
Với HTTP, database hoặc storage call bất đồng bộ, `Task.WhenAll` giúp chồng thời gian chờ I/O và giảm tổng latency. Nhưng với CPU-bound work, việc tạo nhiều `Task` không tự động tạo parallelism hiệu quả; bạn có thể gây ThreadPool pressure nếu ép quá nhiều work đồng thời.

**Ví dụ:**
```csharp
var customerTask = customerApi.GetAsync(id, cancellationToken);
var ordersTask = orderApi.GetRecentAsync(id, cancellationToken);
var profileTask = profileApi.GetAsync(id, cancellationToken);

await Task.WhenAll(customerTask, ordersTask, profileTask);
```

Nếu mỗi call mất khoảng 300 ms và độc lập, tổng thời gian có thể gần 300–400 ms thay vì khoảng 900 ms khi await tuần tự.

**Lưu ý:**
Concurrency phải có giới hạn. Gọi 5,000 downstream requests cùng lúc có thể làm cạn socket, connection pool hoặc đánh sập dependency. Với workload lớn, dùng throttling như `SemaphoreSlim`, `Channel<T>` hoặc bounded concurrency.

### Tip 2 — Với Cosmos DB, partition key tệ có thể làm tăng RU và tạo hot partition dù query đúng

**Mẹo:**
Khi thiết kế Cosmos DB, chọn partition key theo access pattern và khả năng phân phối traffic/data, không chỉ theo field “trông có vẻ unique”.

**Tại sao hữu ích:**
Cosmos DB scale theo physical partition. Nếu phần lớn request rơi vào một logical partition, throughput tổng của database có thể còn dư nhưng partition nóng vẫn throttle. Query cross-partition cũng tốn RU hơn vì phải fan-out.

**Ví dụ:**
Một hệ thống event logging dùng:
```text
partition key = /tenantId
```

Nếu một tenant chiếm 70% traffic, đây có thể trở thành hot partition. Một chiến lược khác có thể là composite logical key ở application level như:
```text
tenantId + yyyyMM
```

nếu query chủ yếu theo tenant và khoảng thời gian.

**Lưu ý:**
Không đổi partition key chỉ để “chia đều” nếu query sau đó luôn phải quét toàn bộ partition. Partition design phải cân bằng write distribution, point-read khả năng, query pattern và lifecycle dữ liệu.

### Tip 3 — Với Kubernetes, phân biệt readiness failure và liveness failure trước khi chỉnh probe

**Mẹo:**
Khi Pod restart hoặc bị loại khỏi traffic, xem probe nào fail và symptom cụ thể trước khi tăng timeout hoặc delay một cách cảm tính.

**Tại sao hữu ích:**
`readinessProbe` quyết định Pod có nhận traffic hay không; `livenessProbe` có thể khiến container bị restart. Nếu database tạm chậm nhưng process vẫn khỏe, liveness phụ thuộc database có thể gây restart loop và làm incident nặng hơn.

**Ví dụ:**
Thiết kế thường hợp lý hơn:
```text
/liveness  -> process đang sống, event loop/runtime không bị kẹt
/readiness -> app đã khởi động và dependency tối thiểu để serve traffic đang sẵn sàng
```

Nếu external payment API down, app có thể vẫn nên `live` dù một capability đang degraded.

**Lưu ý:**
Probe không phải nơi kiểm tra mọi dependency. Health check quá sâu tạo coupling với hệ thống ngoài và dễ gây cascading restart. Hãy tách startup, readiness và liveness semantics rõ ràng.

### Tip 4 — Dùng browser Network waterfall để tìm frontend chậm trước khi tối ưu bundle theo cảm tính

**Mẹo:**
Khi Vue.js hoặc React.js page tải chậm, mở Network waterfall và xác định thứ tự request, TTFB, blocking, duplicate calls và resource chain trước khi bắt đầu tree-shaking hoặc code splitting.

**Tại sao hữu ích:**
Frontend chậm có thể do API chain tuần tự, DNS/TLS, ảnh lớn, cache miss hoặc JavaScript bundle. Nếu bottleneck thật là ba API call phụ thuộc nhau, giảm 50 KB JavaScript gần như không thay đổi trải nghiệm.

**Ví dụ:**
Waterfall:
```text
HTML          180 ms
main.js       220 ms
/api/user     350 ms
/api/config   starts after /api/user
/api/orders   starts after /api/config
```

Nếu các API không thực sự phụ thuộc, có thể parallelize fetch và rút ngắn critical path đáng kể.

**Lưu ý:**
Lab trace và production behavior có thể khác nhau do cache, CDN, mobile network và device CPU. Khi có thể, đối chiếu với real-user metrics thay vì chỉ đo trên máy dev mạnh.

### Tip 5 — Khi dùng AI coding agent, yêu cầu nó chứng minh thay đổi bằng test và source reference

**Mẹo:**
Đừng chỉ yêu cầu agent “fix bug”. Hãy buộc workflow gồm: xác định source liên quan, nêu giả thuyết, sửa tối thiểu, chạy test phù hợp và chỉ ra evidence cho behavior sau sửa.

**Tại sao hữu ích:**
AI có thể tạo API không tồn tại, hiểu sai architecture hoặc sửa symptom thay vì root cause. Grounding vào repository và verification bằng test làm giảm rủi ro code “trông hợp lý nhưng sai”.

**Ví dụ:**
Một instruction tốt hơn:
```text
Find the request path causing duplicate order creation.
Trace controller -> application service -> persistence.
Identify the exact race condition.
Apply the smallest fix.
Add a regression test that fails before the fix and passes after it.
Do not introduce a new abstraction unless required.
```

**Lưu ý:**
Test do AI sinh cũng có thể sai hoặc chỉ verify implementation detail. Review assertion, edge case và failure mode như với code production bình thường.

## 🧠 Software Design

### Design 1 — CQRS chỉ đáng giá khi read/write pressure thực sự khác nhau

**Khái niệm:**
CQRS tách model hoặc flow xử lý command khỏi query. Mục tiêu không phải “mọi request đều qua MediatR”, mà là cho phép read và write evolve theo constraint khác nhau khi domain hoặc scale yêu cầu.

**Vấn đề nó giải quyết:**
Một model duy nhất có thể trở nên khó tối ưu khi write side cần bảo vệ invariant phức tạp nhưng read side cần projection phẳng, search nhanh hoặc dữ liệu tổng hợp từ nhiều nguồn.

**Ví dụ thực tế:**
Order write model có thể giữ aggregate và transaction rule chặt, trong khi dashboard dùng read model riêng:
```text
Write: Order aggregate -> SQL transactional tables
Read:  OrderSummary projection -> denormalized table/cache/search index
```

**Trade-off:**
CQRS tăng khả năng tối ưu độc lập và làm domain intent rõ hơn, nhưng thêm mapping, eventual consistency, synchronization và operational complexity. CRUD system đơn giản thường không cần tách model sâu.

**Middle → Senior insight:**
Middle developer cần phân biệt command thay đổi state với query đọc dữ liệu và giữ handler đơn giản. Senior / Technical developer phải chứng minh lợi ích của việc tách read/write bằng workload, domain complexity hoặc scaling need; nếu không có pressure thật, kiến trúc đơn giản hơn thường tốt hơn.

### Design 2 — Bulkhead Pattern giới hạn blast radius khi dependency bị nghẽn

**Khái niệm:**
Bulkhead cô lập resource theo workload hoặc dependency để một nhánh bị nghẽn không chiếm hết thread, connection hoặc concurrency của toàn application.

**Vấn đề nó giải quyết:**
Nếu Product API chậm và mọi inbound request đều mở thêm outbound call tới đó, toàn bộ service có thể bị cạn connection/thread dù các endpoint không dùng Product API vốn vẫn có thể hoạt động.

**Ví dụ thực tế:**
Có thể giới hạn concurrency riêng:
```text
Product API pool: max 40 concurrent calls
Search API pool:  max 80 concurrent calls
Background sync:  max 10 concurrent calls
```

Khi Product API đạt giới hạn, request liên quan fail fast hoặc degrade thay vì nuốt toàn bộ resource của process.

**Trade-off:**
Bulkhead cải thiện failure isolation nhưng có thể làm một workload bị reject sớm dù hệ thống tổng thể còn capacity. Nó cũng thêm cấu hình và tuning theo traffic thực tế.

**Middle → Senior insight:**
Middle developer cần hiểu bounded concurrency và không mở parallelism vô hạn. Senior / Technical developer phải xác định resource nào cần isolation, chọn queue/rejection policy và đo saturation để tránh biến bulkhead thành bottleneck nhân tạo.

### Design 3 — Contract Testing bảo vệ integration tốt hơn việc mock theo implementation

**Khái niệm:**
Contract Testing kiểm tra producer và consumer có còn đồng thuận về API/message contract hay không, tập trung vào behavior observable thay vì internal implementation của service khác.

**Vấn đề nó giải quyết:**
Unit test của Consumer có thể mock response cũ và vẫn xanh trong khi Producer đã đổi field, enum hoặc validation rule. Integration chỉ vỡ khi deploy chung hoặc chạy production.

**Ví dụ thực tế:**
Mobile API consumer kỳ vọng:
```json
{
  "id": "123",
  "status": "Pending"
}
```

Producer đổi `status` thành object hoặc bỏ field sẽ được phát hiện sớm nếu contract được verify trong CI, thay vì chờ frontend/mobile lỗi sau release.

**Trade-off:**
Contract tests giảm integration regression và cho phép service release độc lập hơn, nhưng thêm contract lifecycle, test infrastructure và governance. Chúng không thay thế end-to-end test cho business flow quan trọng.

**Middle → Senior insight:**
Middle developer cần giữ contract test tập trung vào public behavior và backward compatibility. Senior / Technical developer phải quyết định contract ownership, versioning, deprecation policy và mức test nào thuộc unit, contract, integration hay end-to-end để tránh test pyramid bị phình không kiểm soát.
