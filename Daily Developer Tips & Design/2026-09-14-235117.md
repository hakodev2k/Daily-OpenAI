# Daily Developer Tips & Design — 2026-09-14

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Task.WhenAll` để parallelize I/O độc lập, nhưng giữ bounded concurrency

**Mẹo:**
Khi nhiều I/O operation hoàn toàn độc lập, như gọi ba API downstream hoặc đọc ba nguồn dữ liệu không phụ thuộc nhau, có thể khởi động chúng trước rồi `await Task.WhenAll(...)` thay vì `await` tuần tự. Tuy nhiên, với collection lớn hãy giới hạn concurrency thay vì tạo hàng nghìn task cùng lúc.

**Tại sao hữu ích:**
`await` tuần tự cộng dồn latency của từng operation. Nếu ba call lần lượt mất 120 ms, 180 ms và 100 ms, tổng thời gian có thể gần 400 ms; chạy đồng thời có thể tiến gần operation chậm nhất. Nhưng concurrency không giới hạn lại gây socket pressure, connection-pool exhaustion hoặc làm downstream bị overload.

**Ví dụ:**
```csharp
var profileTask = profileClient.GetAsync(userId, ct);
var ordersTask = orderClient.GetRecentAsync(userId, ct);
var pointsTask = loyaltyClient.GetPointsAsync(userId, ct);

await Task.WhenAll(profileTask, ordersTask, pointsTask);

return new DashboardDto(
    await profileTask,
    await ordersTask,
    await pointsTask);
```

Với hàng nghìn item, dùng `Parallel.ForEachAsync`, `SemaphoreSlim` hoặc worker/channel để đặt concurrency limit phù hợp với downstream capacity.

**Lưu ý:**
Chỉ parallelize khi operation thật sự độc lập. Đừng tăng concurrency nếu cùng tranh một database connection pool hoặc dependency có rate limit thấp. Khi một task lỗi, vẫn phải hiểu exception/cancellation semantics của cả nhóm thay vì giả định `WhenAll` tự rollback các side effect đã hoàn tất.

### Tip 2 — Với PostgreSQL query chậm, xem `EXPLAIN (ANALYZE, BUFFERS)` thay vì đo mỗi thời gian tổng

**Mẹo:**
Khi PostgreSQL query chậm, dùng `EXPLAIN (ANALYZE, BUFFERS)` trên môi trường an toàn để so sánh estimated rows, actual rows, execution nodes và buffer activity. Điều này giúp phân biệt vấn đề cardinality estimate, I/O, scan strategy và join choice.

**Tại sao hữu ích:**
Một query chậm không đồng nghĩa “thiếu index”. Nếu optimizer ước lượng 100 row nhưng thực tế trả 2 triệu row, nó có thể chọn Nested Loop rất tệ. Nếu plan hợp lý nhưng `shared read` cao, bottleneck có thể nằm ở disk/cache. Evidence từ plan giúp sửa root cause thay vì thêm index theo cảm tính.

**Ví dụ:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.total
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE c.region = 'APAC'
  AND o.created_at >= now() - interval '30 days';
```

Đặc biệt chú ý chênh lệch `rows=` giữa estimate và `actual rows`, số loop, scan type và buffer hit/read.

**Lưu ý:**
`ANALYZE` thực sự chạy query; với `UPDATE`, `DELETE` hoặc query rất nặng có thể gây side effect hoặc tải lớn. Dùng transaction rollback khi phù hợp, hoặc chỉ `EXPLAIN` trước. Statistics cũ, data skew và parameterization đều có thể làm plan khác giữa test và production.

### Tip 3 — Phân biệt CPU throttling và `OOMKilled` khi Kubernetes pod chậm hoặc restart

**Mẹo:**
Khi pod chậm hoặc restart, kiểm tra `requests`, `limits`, container state và metrics trước khi tăng replica. CPU limit quá thấp thường gây throttling; memory vượt limit thường dẫn tới `OOMKilled`.

**Tại sao hữu ích:**
Hai triệu chứng đều có thể biểu hiện thành latency tăng hoặc pod không ổn định nhưng nguyên nhân khác nhau. CPU throttling làm process vẫn sống nhưng bị cắt thời gian CPU. Memory limit là hard boundary: container có thể bị kernel terminate, làm request/job đang chạy mất giữa chừng.

**Ví dụ:**
```bash
kubectl describe pod api-7d9f6
kubectl top pod api-7d9f6
```

Nếu `Last State` cho thấy `Reason: OOMKilled`, hãy profile allocation/working set và xem memory limit. Nếu CPU usage thường xuyên chạm limit trong khi latency tăng, kiểm tra throttling metrics và sizing trước khi chỉ tăng replica.

**Lưu ý:**
Không nên bỏ toàn bộ limits như một “fix”. Requests ảnh hưởng scheduling; limits ảnh hưởng isolation và capacity planning. Tăng limit mà không tìm memory leak, unbounded cache hoặc allocation spike chỉ trì hoãn incident. Với .NET, container memory limit còn ảnh hưởng cách GC tự điều chỉnh heap budget.

### Tip 4 — Dùng trace/correlation để nối request với dependency thay vì tìm log bằng timestamp

**Mẹo:**
Trong distributed application, propagate trace context qua HTTP/message boundary và ghi `TraceId`/correlation metadata vào structured logs. Khi điều tra một request chậm, bắt đầu từ trace rồi drill-down dependency thay vì grep log quanh cùng timestamp.

**Tại sao hữu ích:**
Nhiều request chạy đồng thời nên timestamp gần nhau không chứng minh cùng execution flow. Distributed tracing cho thấy request nào gọi SQL, Redis, Service Bus hoặc third-party API nào, mỗi dependency mất bao lâu và failure xuất hiện ở span nào.

**Ví dụ:**
```text
GET /checkout   1.82s  TraceId=9f2...
 ├─ SQL          42ms
 ├─ Redis         8ms
 └─ Payment API 1.71s  timeout/retry
```

Với ASP.NET Core và Application Insights/OpenTelemetry, giữ context propagation mặc định và bổ sung business dimensions như `tenantId` hoặc `orderId` dưới dạng field có kiểm soát.

**Lưu ý:**
Không log secret, access token hoặc PII chỉ để “dễ trace”. Cardinality quá cao trên metrics/tags cũng làm telemetry đắt và khó query. Correlation ID tự chế không nên phá chuẩn W3C Trace Context nếu stack đã hỗ trợ distributed tracing.

### Tip 5 — Trong CMS, tách content cache key khỏi URL khi nội dung còn phụ thuộc language hoặc personalization

**Mẹo:**
Khi cache output hoặc fragment trong CMS/e-commerce site, cache key phải phản ánh những dimension thực sự thay đổi nội dung, ví dụ culture, site, authentication segment hoặc personalization variant; chỉ dùng URL thường chưa đủ.

**Tại sao hữu ích:**
Hai request cùng `/products/123` có thể trả nội dung khác nhau cho `vi-VN` và `en-US`, hoặc cho visitor thường và member. Nếu cache key không chứa dimension đó, hệ thống có thể phục vụ nhầm content — lỗi correctness khó nhận ra vì cache hit vẫn rất cao.

**Ví dụ:**
```text
Sai:
cache-key = /products/123

Tốt hơn khi business cần:
cache-key = site:main|culture:vi-VN|segment:member|path:/products/123
```

Với Optimizely CMS hoặc headless delivery, xác định rõ dữ liệu nào được cache ở application, CDN và browser để mỗi layer có đúng variation policy.

**Lưu ý:**
Thêm quá nhiều dimension có thể làm cache fragmentation và hit ratio giảm mạnh. Không đưa user ID vào key nếu chỉ cần vài segment chung. Với personalized/private response, đôi khi quyết định đúng là không cache ở shared CDN thay vì cố tạo key cực chi tiết.

## 🧠 Software Design

### Design 1 — Anti-Corruption Layer bảo vệ domain khỏi model của hệ thống bên ngoài

**Khái niệm:**
Anti-Corruption Layer (ACL) là boundary dịch contract, terminology và behavior của hệ thống ngoài thành model mà application của bạn hiểu. Nó không chỉ là một mapper DTO; nó ngăn vendor model hoặc legacy semantics lan trực tiếp vào domain.

**Vấn đề nó giải quyết:**
Một CRM bên ngoài gọi khách hàng là `Account`, dùng status code `A`, `S`, `X` và có quy tắc lifecycle khác hệ thống nội bộ. Nếu application dùng trực tiếp DTO của CRM khắp codebase, mọi service bắt đầu phụ thuộc vào naming, enum và quirks của vendor. Khi đổi CRM hoặc API version, blast radius rất lớn.

**Ví dụ thực tế:**
```text
CRM API
  CustomerResponse(status="A", tier="03")
        |
        v
CustomerCrmAdapter / ACL
        |
        v
Domain
  CustomerStatus.Active
  MembershipTier.Premium
```

ACL có thể đồng thời normalize error, retry classification và identifier mapping nếu đó là khác biệt semantics của integration.

**Trade-off:**
ACL giảm coupling và giữ ubiquitous language sạch, nhưng thêm mapping code, test và maintenance. Nếu integration rất nhỏ, stable và chỉ tồn tại ở một boundary, abstraction lớn có thể là overengineering. Giá trị tăng mạnh khi external model khác domain đáng kể hoặc vendor có khả năng thay đổi.

**Middle → Senior insight:**
Middle developer cần tránh để SDK/DTO bên ngoài tràn qua application layers và phải test mapping rõ ràng. Senior / Technical developer phải quyết định boundary nào đáng bảo vệ, semantics nào cần translate, error nào là transient/permanent và mức abstraction nào đủ mà không xây một framework integration chung quá sớm.

### Design 2 — API evolution nên ưu tiên additive compatibility trước khi tạo version mới

**Khái niệm:**
API evolution là quá trình thay đổi contract mà không làm consumer hiện tại ngừng hoạt động. Với nhiều thay đổi, cách an toàn nhất là mở rộng contract theo hướng additive — thêm optional field, endpoint hoặc capability — trước khi nghĩ tới `/v2`.

**Vấn đề nó giải quyết:**
Mobile app, partner integration hoặc frontend cũ không phải lúc nào cũng deploy đồng thời với backend. Rename field, đổi meaning của status code hoặc biến optional field thành required có thể phá consumer dù server build/deploy hoàn toàn thành công.

**Ví dụ thực tế:**
```text
Hiện tại:
GET /orders/42
{ "status": "paid" }

Nhu cầu mới:
Thêm payment timestamp

Additive:
{ "status": "paid", "paidAt": "2026-09-14T10:15:00Z" }
```

Nếu semantics của `status` phải thay đổi căn bản và không thể giữ backward compatibility, khi đó version mới hoặc endpoint mới có thể hợp lý hơn.

**Trade-off:**
Additive change giảm migration pressure nhưng contract có thể tích lũy field cũ và compatibility code. Versioning cho phép clean break nhưng tăng số contract phải support, test và document. Mỗi version còn kéo theo monitoring, deprecation policy và migration communication.

**Middle → Senior insight:**
Middle developer cần nhận diện breaking change ở request/response schema, validation và semantics, không chỉ ở URL. Senior / Solution-oriented engineer phải quản lý compatibility window, consumer inventory, telemetry usage, deprecation timeline và quyết định khi nào chi phí giữ compatibility lớn hơn chi phí versioning.

### Design 3 — Feature Flag tách thời điểm deploy code khỏi thời điểm release behavior

**Khái niệm:**
Feature Flag cho phép deploy code đã hoàn thành nhưng chỉ bật behavior cho một nhóm user, tenant hoặc tỷ lệ traffic nhất định. Điều này tách deployment — đưa binary/code vào production — khỏi release — cho user thực sự sử dụng capability mới.

**Vấn đề nó giải quyết:**
Một thay đổi lớn cần đi cùng release train nhưng Product muốn rollout dần, QA cần validate production-like environment hoặc team muốn có kill switch khi dependency mới gặp sự cố. Nếu mọi deploy đồng nghĩa bật feature ngay lập tức, rollback thường phải redeploy toàn application.

**Ví dụ thực tế:**
```text
Deploy version 5.4
Feature: NewCheckout = off

Internal users -> on
5% customers   -> on
25% customers  -> on
100% customers -> on
```

Telemetry nên phân tách cohort để biết error rate/latency thay đổi có liên quan tới flag hay không.

**Trade-off:**
Feature flag giảm release risk và hỗ trợ progressive delivery, nhưng mỗi flag tạo thêm execution path cần test. Flag sống quá lâu tạo dead code và combinatorial complexity. Flag hệ thống cũng trở thành runtime dependency nếu quyết định quan trọng phải được resolve trong hot path.

**Middle → Senior insight:**
Middle developer cần triển khai cả đường on/off an toàn và không để flag che mất invariant. Senior / Technical developer phải định nghĩa owner, expiry date, default khi flag service lỗi, rollout/rollback criteria và cleanup plan; đồng thời phân biệt release flag ngắn hạn với permission/configuration dài hạn.
