# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — Tránh ThreadPool starvation khi biến async thành blocking

**Mẹo:**
Trong ASP.NET Core, giữ call chain bất đồng bộ end-to-end và tránh `.Result`, `.Wait()` hoặc `Task.Run` để bọc I/O async. Khi dependency đã có async API, hãy `await` trực tiếp.

**Tại sao hữu ích:**
Blocking một ThreadPool thread trong lúc chờ I/O làm giảm worker khả dụng. Khi traffic tăng, request mới phải chờ ThreadPool bổ sung thread; latency có thể tăng mạnh dù CPU chưa đạt 100%. Đây là failure mode khác với deadlock kiểu UI synchronization context.

**Ví dụ:**
```csharp
// Không nên
var customer = httpClient.GetFromJsonAsync<Customer>(url).Result;

// Nên
var customer = await httpClient.GetFromJsonAsync<Customer>(url, ct);
```
Nếu production có request queue tăng, latency tăng nhưng CPU tương đối thấp, kiểm tra ThreadPool counters và stack trace để tìm synchronous blocking trước khi scale instance.

**Lưu ý:**
`async` không làm CPU-bound work nhanh hơn. Với CPU-heavy workload, cần giới hạn concurrency hoặc tách workload phù hợp; chuyển mọi đoạn CPU sang `Task.Run` trong web request có thể chỉ chuyển áp lực sang cùng ThreadPool.

### Tip 2 — `IHttpClientFactory` không chỉ để tránh socket exhaustion

**Mẹo:**
Dùng `IHttpClientFactory` hoặc typed client để quản lý outbound HTTP client, handler lifetime, configuration và resilience policy thay vì tạo `new HttpClient()` cho từng request.

**Tại sao hữu ích:**
Mỗi request tạo/dispose handler riêng có thể gây churn connection và socket. Ngược lại, giữ một handler vô hạn có thể khiến DNS change không được phản ánh đúng thời điểm. Factory quản lý handler pooling/lifetime và tạo boundary rõ cho từng external dependency.

**Ví dụ:**
```csharp
builder.Services.AddHttpClient<PaymentClient>(client =>
{
    client.BaseAddress = new Uri(paymentBaseUrl);
    client.Timeout = TimeSpan.FromSeconds(3);
});
```
Telemetry, timeout và resilience của Payment API có thể cấu hình riêng thay vì dùng một global client cho mọi dependency.

**Lưu ý:**
Factory không sửa retry policy sai. Không retry mọi `POST` chỉ vì gặp timeout; operation có thể đã được xử lý phía server. Retry write cần idempotency semantics và retry budget rõ ràng.

### Tip 3 — Composite index phải theo query shape, không theo thứ tự cột trong model

**Mẹo:**
Thiết kế composite index dựa trên predicate, sort và selectivity thực tế của workload. Đừng giả định index `(A, B, C)` tương đương `(B, A, C)` chỉ vì chứa cùng các cột.

**Tại sao hữu ích:**
B-tree được sắp xếp theo key từ trái sang phải. Khả năng seek phụ thuộc prefix và loại predicate. Một index có đủ cột nhưng key order không phù hợp vẫn có thể khiến database scan nhiều dữ liệu hoặc cần sort bổ sung.

**Ví dụ:**
Query thường dùng:
```sql
SELECT Id, Total
FROM Orders
WHERE TenantId = @tenantId
  AND CreatedAt >= @from
ORDER BY CreatedAt DESC;
```
Index bắt đầu bằng `TenantId, CreatedAt` thường phù hợp hơn index bắt đầu bằng `Status` chỉ vì `Status` cũng xuất hiện ở một số query khác. Kiểm tra execution plan và workload trước khi kết luận.

**Lưu ý:**
Thêm index làm tăng storage và chi phí `INSERT`/`UPDATE`/maintenance. Một covering index rất rộng có thể cải thiện một read query nhưng làm write path tệ hơn; tối ưu theo workload tổng thể, không theo một query cô lập.

### Tip 4 — Dùng `git reflog` khi commit “biến mất” sau rebase/reset

**Mẹo:**
Khi vừa `rebase`, `reset --hard` hoặc đổi branch và không còn thấy commit local, kiểm tra `git reflog` trước khi kết luận code đã mất.

**Tại sao hữu ích:**
Branch ref có thể bị di chuyển nhưng Git vẫn ghi lịch sử thay đổi của `HEAD`/refs trong reflog một thời gian. SHA cũ thường còn reachable để tạo branch cứu hộ hoặc cherry-pick lại commit.

**Ví dụ:**
```bash
git reflog
git branch rescue-work <old-sha>
```
Sau đó review diff của `rescue-work` trước khi đưa commit trở lại branch chính.

**Lưu ý:**
Reflog chủ yếu là local và không phải backup vĩnh viễn; object unreachable cuối cùng có thể bị garbage collection. Với work quan trọng, vẫn cần commit/push hợp lý thay vì dựa vào reflog như chiến lược lưu trữ.

### Tip 5 — Elasticsearch mapping sai thường đắt hơn việc viết query dài hơn

**Mẹo:**
Thiết kế mapping theo cách field được search, filter, sort và aggregate. Với chuỗi vừa cần full-text vừa cần exact match, thường dùng `text` cho analyzed search và `keyword` subfield cho filter/sort/aggregation.

**Tại sao hữu ích:**
Analyzer biến text thành token để phục vụ full-text relevance; exact filtering lại cần giá trị không bị phân tích. Nếu mapping không phản ánh access pattern, query có thể cho kết quả sai nghĩa hoặc buộc reindex khi hệ thống đã có nhiều dữ liệu.

**Ví dụ:**
Tên sản phẩm `"ASP.NET Core Handbook"` có thể search qua analyzed `name`, nhưng faceting/sort dùng `name.keyword`. Filter tenant/category nên dùng field phù hợp với exact matching thay vì full-text query.

**Lưu ý:**
Mapping change không phải lúc nào cũng sửa in-place được cho dữ liệu hiện hữu. Production cần kế hoạch index versioning, reindex và alias switch; đồng thời database transactional vẫn nên là source of truth nếu search index chỉ là projection.

## 🧠 Software Design

### Design 1 — Timeout, Retry và Circuit Breaker phải được thiết kế như một resilience budget

**Khái niệm:**
Timeout giới hạn thời gian chờ một attempt; Retry tạo attempt mới cho failure có khả năng transient; Circuit Breaker tạm ngừng gọi dependency đang lỗi để tránh tiếp tục tiêu tốn capacity. Ba cơ chế này giải quyết các pressure khác nhau và cần phối hợp theo latency budget tổng.

**Vấn đề nó giải quyết:**
Nếu một API có SLO 2 giây nhưng mỗi dependency attempt timeout 2 giây và retry ba lần, riêng một dependency đã có thể vượt xa latency budget. Retry đồng loạt khi downstream đang overload còn có thể khuếch đại sự cố thành retry storm.

**Ví dụ thực tế:**
Checkout có 1.5 giây budget cho fraud provider. Team đặt timeout từng attempt ngắn hơn budget tổng, chỉ retry lỗi transient/idempotent với jittered backoff, và mở circuit khi tỷ lệ failure vượt ngưỡng. Khi circuit mở, application fail fast hoặc dùng degradation path đã định nghĩa.

**Trade-off:**
Timeout quá ngắn tạo false failure; retry tăng xác suất thành công nhưng tăng load và tail latency; circuit breaker giảm pressure nhưng có thể từ chối request trong lúc dependency đã bắt đầu hồi phục. Policy cần telemetry và tuning theo dependency cụ thể.

**Middle → Senior insight:**
Middle developer cần phân biệt failure nào retry được và propagate cancellation đúng. Senior / Technical developer phải tính end-to-end latency/retry budget, xem xét idempotency, retry amplification, fallback semantics và phối hợp policy giữa nhiều service để resilience không biến thành nguồn overload mới.

### Design 2 — Database constraint nên giữ invariant mà application không được phép phá

**Khái niệm:**
Business rule có thể được kiểm tra ở application layer, nhưng invariant quan trọng có biểu diễn tự nhiên bằng database constraint — unique key, foreign key, check constraint hoặc atomic conditional update — nên được bảo vệ ở nơi concurrency cuối cùng hội tụ.

**Vấn đề nó giải quyết:**
Pattern `SELECT để kiểm tra -> INSERT` có race khi hai request chạy đồng thời. Cả hai có thể cùng thấy “chưa tồn tại” rồi cùng insert nếu database không enforce uniqueness.

**Ví dụ thực tế:**
Một user chỉ được có một active subscription cho cùng product. Application kiểm tra để trả lỗi thân thiện, nhưng database vẫn có unique strategy phù hợp để chặn duplicate trong race. Application bắt constraint violation và map sang business response thay vì dựa hoàn toàn vào pre-check.

**Trade-off:**
Không phải mọi domain rule đều biểu diễn tốt bằng constraint; rule phụ thuộc nhiều aggregate/external state có thể làm schema phức tạp hoặc không khả thi. Constraint cũng cần migration cẩn thận khi dữ liệu legacy đã vi phạm invariant.

**Middle → Senior insight:**
Middle developer cần hiểu validation không thay thế concurrency protection. Senior / Technical developer phải quyết định invariant nào thuộc database, aggregate transaction hay distributed workflow, đồng thời thiết kế error mapping và migration để enforcement không chỉ đúng về kỹ thuật mà còn đúng semantics.

### Design 3 — Observability phải được thiết kế theo câu hỏi vận hành, không theo số lượng log

**Khái niệm:**
Observability design chọn logs, metrics và traces để suy luận trạng thái hệ thống từ production evidence. Mục tiêu không phải ghi càng nhiều càng tốt mà là trả lời nhanh các câu hỏi về failure, latency, saturation và business flow.

**Vấn đề nó giải quyết:**
Một service có hàng triệu log lines vẫn khó debug nếu thiếu correlation, duration, dependency outcome hoặc business identifiers an toàn. Ngược lại, high-cardinality metric tùy tiện có thể làm telemetry cực đắt mà không hỗ trợ diagnosis.

**Ví dụ thực tế:**
Order API phát request trace có correlation tới SQL và Service Bus; metrics theo request rate/error/latency và queue lag; structured logs chỉ bổ sung context cho failure quan trọng. Khi order bị kẹt, engineer đi từ symptom metric -> trace cụ thể -> structured event thay vì grep text ngẫu nhiên.

**Trade-off:**
Telemetry tăng storage, network và ingestion cost; sampling có thể mất rare event; log quá nhiều dữ liệu business có nguy cơ lộ PII. Instrumentation cũng là code cần governance và schema ổn định.

**Middle → Senior insight:**
Middle developer cần structured logging, correlation và biết dùng trace/metric khi troubleshoot. Senior / Technical developer phải định nghĩa telemetry theo SLO/failure mode, kiểm soát cardinality/cost, đặt sampling strategy và bảo đảm mỗi critical workflow có đủ evidence để đi từ symptom → hypothesis → diagnosis mà không cần deploy thêm log trong lúc incident.
