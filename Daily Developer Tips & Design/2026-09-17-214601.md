# Daily Developer Tips & Design — 2026-09-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng retry `HttpClient` nếu request không có retry budget

**Mẹo:**
Khi gọi third-party API từ ASP.NET Core, đặt timeout theo từng attempt và giới hạn tổng thời gian retry bằng một retry budget. Retry chỉ các lỗi transient phù hợp và thêm jitter vào backoff.

**Tại sao hữu ích:**
Ba lần retry với timeout 30 giây có thể biến dependency chậm thành request kéo dài hơn một phút, giữ connection và tài nguyên lâu hơn, rồi khuếch đại sự cố khi traffic tăng. Budget buộc resilience policy tôn trọng latency contract của request phía trên.

**Ví dụ:**
```csharp
using var cts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
cts.CancelAfter(TimeSpan.FromSeconds(3));

using var response = await httpClient.GetAsync("/inventory/42", cts.Token);
response.EnsureSuccessStatusCode();
```

Nếu endpoint có SLO 2 giây, retry policy phải được thiết kế trong giới hạn đó thay vì cộng các timeout độc lập một cách vô hạn.

**Lưu ý:**
Không retry mù `POST` hoặc operation có side effect nếu API không hỗ trợ idempotency. Retry storm có thể làm dependency đang quá tải tệ hơn; circuit breaker, concurrency limit hoặc fail-fast đôi khi phù hợp hơn.

### Tip 2 — Dùng keyset pagination khi `OFFSET` bắt đầu trả giá đắt

**Mẹo:**
Với bảng lớn và endpoint đọc tuần tự theo thời gian, cân nhắc keyset pagination dựa trên cột sort ổn định thay vì `OFFSET ... FETCH` ở các trang sâu.

**Tại sao hữu ích:**
`OFFSET` vẫn buộc database tìm và bỏ qua nhiều rows trước khi trả page hiện tại. Keyset cho phép engine seek từ vị trí cuối cùng nếu index phù hợp, đồng thời giảm hiện tượng item bị nhảy hoặc lặp khi dữ liệu mới được insert giữa hai lần đọc.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index nên phục vụ cùng ordering, ví dụ `(CreatedAt DESC, Id DESC)` với các included columns cần thiết tùy workload.

**Lưu ý:**
Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới “page 317”. Sort key phải deterministic; chỉ dùng `CreatedAt` khi có nhiều giá trị trùng nhau sẽ làm pagination sai.

### Tip 3 — Phân biệt Kubernetes readiness với liveness để tránh restart sai bệnh

**Mẹo:**
Dùng readiness probe để quyết định Pod có nhận traffic hay không; dùng liveness probe chỉ khi process thực sự cần restart để hồi phục. Đừng biến mọi dependency check thành liveness check.

**Tại sao hữu ích:**
Nếu database tạm thời unavailable và liveness endpoint cũng fail theo, Kubernetes có thể restart hàng loạt Pod đang hoàn toàn khỏe về process. Restart không sửa database nhưng làm cold start, connection churn và recovery khó hơn.

**Ví dụ:**
```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
```

`/health/ready` có thể phản ánh khả năng phục vụ traffic; `/health/live` nên kiểm tra process có còn tiến triển hợp lý hay không.

**Lưu ý:**
Probe quá nhạy cũng gây flapping. Cần tune `timeoutSeconds`, `failureThreshold`, startup behavior và hiểu semantics của từng health check thay vì copy cấu hình giữa các service.

### Tip 4 — Vue/React frontend nên hủy request khi state đã đổi ngữ cảnh

**Mẹo:**
Với autocomplete, filter hoặc route change, dùng `AbortController` để hủy fetch cũ thay vì để response cũ quay về sau và ghi đè state mới.

**Tại sao hữu ích:**
Đây là race condition phổ biến: user gõ `camera`, request A chạy; user đổi thành `camera lens`, request B chạy; B trả trước rồi A trả sau và UI hiển thị kết quả sai. Cancellation giảm cả stale update lẫn network work không còn giá trị.

**Ví dụ:**
```typescript
let controller: AbortController | undefined;

async function search(q: string) {
  controller?.abort();
  controller = new AbortController();
  const r = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
    signal: controller.signal
  });
  return r.json();
}
```

**Lưu ý:**
Abort ở browser không bảo đảm backend đã rollback mọi work; server vẫn cần propagate cancellation hợp lý. Đồng thời phân biệt `AbortError` với lỗi mạng thật để không hiển thị cảnh báo giả cho user.

### Tip 5 — Log correlation phải đi xuyên qua background message, không chỉ HTTP request

**Mẹo:**
Khi một HTTP request tạo message cho Azure Service Bus, đưa correlation identifier vào message metadata và khôi phục tracing context ở consumer để nối request → publish → consume trong observability.

**Tại sao hữu ích:**
Nếu chỉ log `CorrelationId` trong controller, incident điều tra sẽ bị đứt khi workflow chuyển sang asynchronous processing. Trace context xuyên boundary giúp xác định latency nằm ở API, broker wait time hay consumer dependency.

**Ví dụ:**
```csharp
message.ApplicationProperties["CorrelationId"] = correlationId;
logger.LogInformation("Processing order {OrderId} correlation {CorrelationId}",
    orderId, correlationId);
```

Tốt hơn nữa, ưu tiên chuẩn distributed tracing/W3C trace context của telemetry stack thay vì tự phát minh toàn bộ propagation protocol.

**Lưu ý:**
Không đưa token, PII hoặc secret vào correlation metadata/log. Correlation ID không thay thế business idempotency key; hai giá trị giải quyết hai vấn đề khác nhau.

## 🧠 Software Design

### Design 1 — Retry budget và Circuit Breaker là hai cơ chế khác nhau

**Khái niệm:**
Retry budget giới hạn lượng thời gian/số lần thử dành cho transient failure; Circuit Breaker tạm ngừng gọi dependency khi failure pattern cho thấy tiếp tục gọi có khả năng vô ích. Chúng bổ sung nhau nhưng không thể thay thế nhau.

**Vấn đề nó giải quyết:**
Một service phụ thuộc payment API đang timeout. Retry vô hạn làm tăng traffic lên dependency và kéo dài request; fail ngay mọi lỗi lại làm mất khả năng phục hồi từ lỗi transient ngắn. Hệ thống cần cân bằng recovery với load amplification.

**Ví dụ thực tế:**
Checkout có latency budget 2 giây. Client có thể thử lại một lần với jitter nếu còn budget; nếu tỷ lệ failure vượt ngưỡng trong rolling window, breaker mở và request mới fail fast hoặc chuyển sang business fallback phù hợp.

**Trade-off:**
Retry tăng xác suất thành công với lỗi transient nhưng tăng load và tail latency. Circuit Breaker bảo vệ dependency và caller nhưng có thể từ chối request trong lúc dependency vừa hồi phục; threshold và half-open behavior cần telemetry để tune.

**Middle → Senior insight:**
Middle developer cần phân loại lỗi retryable và tránh retry operation không idempotent. Senior / Technical developer phải thiết kế end-to-end latency budget, tránh retry ở nhiều layer gây multiplicative attempts, xác định fallback semantics và dùng production telemetry để điều chỉnh policy.

### Design 2 — SQL hay Cosmos DB phải bắt đầu từ access pattern và consistency requirement

**Khái niệm:**
Chọn relational hay document database không nên dựa trên “schema linh hoạt” hoặc “NoSQL scale tốt hơn” như khẩu hiệu. Quyết định phải xuất phát từ transaction/invariant, query pattern, partitioning, consistency, data growth và operational model.

**Vấn đề nó giải quyết:**
Một catalog toàn cầu có read pattern theo tenant/product có thể phù hợp document model; nhưng order/payment cần invariant xuyên nhiều records và reporting ad-hoc có thể phù hợp relational model hơn. Chọn sai persistence model sẽ chuyển complexity từ database sang application.

**Ví dụ thực tế:**
Product configuration được đọc chủ yếu theo `tenantId + productId`, ít join và có natural partition key có thể là ứng viên cho Cosmos DB. Billing ledger cần transaction chặt, constraint và reconciliation SQL phong phú có thể giữ ở SQL Server/PostgreSQL.

**Trade-off:**
Document model có thể giảm join và scale theo partition tốt, nhưng partition-key mistake tạo hot partition và cross-partition query cost. Relational database cung cấp constraint, join và transaction mạnh nhưng scale/write topology cũng có giới hạn và operational trade-off riêng.

**Middle → Senior insight:**
Middle developer cần model dữ liệu theo query thật thay vì ánh xạ object máy móc. Senior / Technical developer phải lượng hóa partition cardinality, consistency, transaction boundary, migration/recovery, cost model và khả năng vận hành của team trước khi chọn hoặc polyglot persistence.

### Design 3 — Contract Testing ở boundary quan trọng hơn việc mock mọi dependency

**Khái niệm:**
Contract Testing xác minh producer và consumer còn đồng ý về API/message contract mà không cần chạy toàn bộ hệ thống end-to-end. Nó tập trung vào boundary behavior thay vì implementation nội bộ.

**Vấn đề nó giải quyết:**
Unit test của service A mock response từ service B có thể luôn xanh dù B đã đổi field, status code hoặc schema. E2E test bắt được lỗi nhưng thường chậm, brittle và khó chạy đủ mọi combination trước deployment độc lập.

**Ví dụ thực tế:**
Mobile backend phụ thuộc Product API. Consumer contract xác định `GET /products/{id}` cần `id`, `name`, `price` và semantics của `404`; CI của producer kiểm tra implementation mới vẫn thỏa contract trước khi release.

**Trade-off:**
Contract tests phát hiện breaking change sớm và rẻ hơn full E2E, nhưng thêm contract lifecycle/versioning và không chứng minh network, auth, deployment hay data integration thực tế đều hoạt động. Integration/E2E tests vẫn cần cho các rủi ro khác.

**Middle → Senior insight:**
Middle developer cần test observable behavior và tránh mock theo implementation detail. Senior / Technical developer phải quyết định boundary nào đáng contract-test, ownership contract thuộc ai, cách xử lý backward compatibility/versioning và phối hợp contract tests với integration/E2E strategy thay vì biến chúng thành một tầng test dư thừa.
