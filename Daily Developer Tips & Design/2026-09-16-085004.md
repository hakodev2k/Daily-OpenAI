## Developer Tips & Tricks

### 1. Đừng dùng `ConcurrentDictionary.GetOrAdd` như thể value factory chỉ chạy đúng một lần

**Vấn đề thực tế:** Bạn cache một resource đắt tiền bằng `GetOrAdd(key, _ => BuildExpensiveResource())` và giả định `BuildExpensiveResource` chỉ được gọi một lần. Khi nhiều request tranh chấp cùng key, factory có thể được thực thi nhiều lần dù cuối cùng chỉ một value được lưu.

**Cơ chế bên dưới:** `ConcurrentDictionary` đảm bảo thao tác cập nhật dictionary thread-safe, nhưng delegate của `GetOrAdd` được gọi ngoài internal lock để tránh chạy arbitrary user code trong critical section. Vì vậy nhiều thread có thể cùng tạo candidate value.

**Cách làm tốt hơn:** Nếu initialization phải thực sự single-execution, lưu `Lazy<T>` hoặc `Lazy<Task<T>>` thay vì lưu resource trực tiếp.

```csharp
private readonly ConcurrentDictionary<string, Lazy<Task<Client>>>
    _clients = new();

public Task<Client> GetClientAsync(string tenantId)
{
    var lazy = _clients.GetOrAdd(
        tenantId,
        id => new Lazy<Task<Client>>(
            () => BuildClientAsync(id),
            LazyThreadSafetyMode.ExecutionAndPublication));

    return lazy.Value;
}
```

**Khi nên dùng:** Per-tenant clients, expensive metadata loading, schema discovery hoặc initialization có side effect. Nếu factory rẻ và idempotent, việc factory chạy thừa có thể chấp nhận được và không cần thêm `Lazy<T>`.

### 2. Đừng để `IQueryable` thoát khỏi data-access boundary nếu caller không sở hữu query semantics

**Vấn đề thực tế:** Repository trả `IQueryable<Order>` để service tự nối thêm `Where`, `Include`, `OrderBy`. Ban đầu rất linh hoạt, nhưng application layer dần phụ thuộc vào EF Core translation behavior; một thay đổi LINQ nhỏ có thể tạo SQL cực đắt hoặc runtime translation failure.

**Cơ chế bên dưới:** `IQueryable` không phải collection đã tải; nó là expression tree sẽ được provider dịch sau. Vì execution bị deferred, layer trả `IQueryable` không còn kiểm soát SQL cuối cùng, tracking mode, projection, pagination hay thời điểm `DbContext` còn sống.

**Cách làm tốt hơn:** Đặt query semantics ở nơi hiểu persistence và expose use-case-oriented methods/read models.

```csharp
public Task<IReadOnlyList<OrderSummary>> GetPendingOrdersAsync(
    DateTimeOffset olderThan,
    int limit,
    CancellationToken ct)
{
    return _db.Orders
        .AsNoTracking()
        .Where(x => x.Status == OrderStatus.Pending &&
                    x.CreatedAt < olderThan)
        .OrderBy(x => x.CreatedAt)
        .Select(x => new OrderSummary(x.Id, x.CreatedAt, x.Total))
        .Take(limit)
        .ToListAsync(ct)
        .ContinueWith<IReadOnlyList<OrderSummary>>(
            t => t.Result,
            ct,
            TaskContinuationOptions.ExecuteSynchronously,
            TaskScheduler.Default);
}
```

Trong production code, có thể trả trực tiếp `Task<List<OrderSummary>>` để tránh adapter không cần thiết; điểm quan trọng là materialize tại boundary.

**Khi nên dùng:** Application có layering rõ, query phức tạp hoặc cần kiểm soát performance. Với internal query composition trong cùng persistence layer, `IQueryable` vẫn là abstraction hữu ích.

### 3. Phân biệt `DbCommandTimeout` với request timeout: chúng bảo vệ hai failure domain khác nhau

**Vấn đề thực tế:** API có request timeout 5 giây nhưng SQL command vẫn chạy lâu trong database sau khi client đã bỏ request, hoặc ngược lại SQL timeout quá ngắn khiến query hợp lệ bị hủy dù request budget còn nhiều.

**Cơ chế bên dưới:** HTTP/request cancellation biểu diễn lifetime của operation phía application. Database command timeout là giới hạn provider dành riêng cho command execution. Chúng không thay thế nhau. `CancellationToken` cần được propagate xuống EF Core để request cancellation có cơ hội cancel command; command timeout vẫn là guardrail độc lập khi database/query bất thường.

**Cách làm tốt hơn:** Xác định end-to-end latency budget, propagate token và cấu hình database timeout nhỏ hơn hoặc phù hợp với budget của operation.

```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
{
    options.UseSqlServer(connectionString, sql =>
    {
        sql.CommandTimeout(3);
    });
});

var rows = await db.Orders
    .AsNoTracking()
    .Where(x => x.CustomerId == customerId)
    .ToListAsync(cancellationToken);
```

**Khi nên dùng:** APIs có SLO/latency budget rõ ràng, background jobs hoặc hệ thống chịu database contention. Không chọn timeout chỉ bằng cảm tính; đo p95/p99 latency và phân biệt normal slow query với pathological query.

### 4. Dùng `dotnet-counters` để xác định ThreadPool starvation trước khi lao vào đọc code

**Vấn đề thực tế:** Service có CPU chưa đầy nhưng latency tăng mạnh, request queue dài và throughput giảm. Nhìn CPU dashboard dễ kết luận sai rằng database hoặc network đang chậm.

**Cơ chế bên dưới:** Sync blocking, `.Result`, `.Wait()`, lock contention hoặc quá nhiều blocking I/O có thể giữ ThreadPool workers. Runtime phải inject thread mới dần dần, khiến work queue tăng dù CPU còn dư. Runtime counters giúp phân biệt starvation với CPU saturation hoặc GC pressure.

**Cách làm tốt hơn:** Quan sát runtime counters trên process đang gặp vấn đề trước, sau đó mới thu trace sâu hơn.

```bash
dotnet-counters monitor \
  --process-id 12345 \
  --counters System.Runtime
```

Tập trung vào `dotnet.thread_pool.thread.count`, `dotnet.thread_pool.queue.length`, CPU usage và GC metrics. Nếu thread count tăng đều, queue tồn tại lâu nhưng CPU chưa saturated, hãy tìm blocking path bằng trace/profiler.

**Khi nên dùng:** Production-like load test, incident latency hoặc performance regression khó tái hiện bằng debugger. Counters là bước triage; chúng chỉ ra symptom/resource pressure chứ không tự xác định dòng code gây lỗi.

### 5. Đừng dùng `DateTime.Now` cho business rule cần tính đúng qua timezone và DST

**Vấn đề thực tế:** Rule “subscription hết hạn lúc 09:00 theo giờ địa phương của khách hàng” được lưu bằng `DateTime` và so với `DateTime.Now`. Khi deployment đổi timezone hoặc khu vực bước qua DST transition, rule có thể chạy sai một giờ hoặc gặp local time không tồn tại/không duy nhất.

**Cơ chế bên dưới:** `DateTime` có `Kind` nhưng không chứa timezone rule. UTC timestamp và civil/local business time là hai khái niệm khác nhau. `DateTimeOffset` giữ instant cùng offset, còn timezone identifier cho phép chuyển đổi theo rule của vùng.

**Cách làm tốt hơn:** Lưu instant bằng UTC/`DateTimeOffset`; lưu timezone ID riêng nếu business semantics phụ thuộc local time. Inject `TimeProvider` để test deterministic.

```csharp
public sealed class SubscriptionService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAtUtc)
        => timeProvider.GetUtcNow() >= expiresAtUtc;
}
```

**Khi nên dùng:** Expiration, scheduling, billing, reminders, multi-region systems và tests phụ thuộc thời gian. Với timestamp thuần túy như `CreatedAt`, UTC instant thường là representation đúng nhất.

## Software Design

### 6. Idempotent Consumer: `at-least-once delivery` nghĩa là duplicate phải được coi là trạng thái bình thường

**Vấn đề thực tế:** Consumer nhận `PaymentCaptured` rồi cộng balance. Broker redeliver message vì ACK bị mất sau khi transaction đã commit. Nếu handler chạy lại nguyên logic, balance bị cộng hai lần.

**Trade-off thiết kế:** Với at-least-once messaging, duplicate delivery không phải edge case hiếm; nó là semantics cần thiết kế. Consumer có thể ghi `MessageId` đã xử lý cùng business transaction và bỏ qua duplicate. Đổi lại, bạn phải lưu deduplication state, thiết kế retention và đảm bảo unique constraint thực sự nằm ở database.

```text
Message Broker
      |
      v
 Consumer
      |
      +---- DB Transaction ----------------------+
      |  INSERT ProcessedMessages(MessageId)     |
      |        UNIQUE(MessageId)                 |
      |  UPDATE AccountBalance                   |
      +---------------- COMMIT ------------------+
      |
      v
     ACK

ACK bị mất -> broker redeliver
              -> UNIQUE(MessageId) phát hiện duplicate
              -> không apply business effect lần hai
```

**Khi phù hợp:** Payment, inventory, notification workflow hoặc bất kỳ consumer nào có side effect không được phép lặp. Nếu operation vốn idempotent tự nhiên, ví dụ `SET status = 'Active'`, có thể không cần dedup store riêng.

### 7. Strangler Fig pattern: thay legacy system theo vertical slice thay vì big-bang rewrite

**Vấn đề thực tế:** Một monolith cũ khó bảo trì nhưng vẫn phục vụ production. Rewrite toàn bộ mất 12–18 tháng, trong thời gian đó business vẫn thay đổi và team phải duy trì cả hệ cũ lẫn code rewrite chưa tạo giá trị.

**Trade-off thiết kế:** Strangler Fig đặt routing/facade ở boundary và chuyển từng capability sang implementation mới. Traffic cho phần đã migrate đi vào hệ mới; phần còn lại vẫn vào legacy. Cách này giảm migration risk và tạo incremental value, nhưng tạm thời tăng operational complexity, data synchronization và observability requirements.

```text
Clients
   |
   v
Routing / API Facade
   |
   +---- /customers ----> New Customer Service
   |
   +---- /orders --------> Legacy Monolith
   |
   +---- /billing -------> Legacy Monolith

Sau mỗi migration slice:
Legacy surface area giảm dần -> cuối cùng retire monolith
```

**Khi phù hợp:** Legacy modernization lớn, hệ thống không thể dừng để rewrite và domain có boundary đủ rõ để bóc dần. Không nên áp dụng máy móc cho codebase nhỏ nơi incremental coexistence còn phức tạp hơn rewrite trực tiếp.

### 8. CQRS không có nghĩa là phải có hai database hay event sourcing

**Vấn đề thực tế:** Team muốn tối ưu read model nên áp dụng CQRS, rồi lập tức thêm message broker, event store, read database riêng và eventual consistency cho mọi feature. Complexity tăng mạnh trước khi có nhu cầu thực tế.

**Trade-off thiết kế:** Cốt lõi của CQRS là tách model/flow xử lý command khỏi query khi chúng có nhu cầu khác nhau. Mức đơn giản nhất có thể vẫn dùng cùng một database: command load aggregate có tracking, query project thẳng DTO bằng `AsNoTracking`. Chỉ tách storage hoặc thêm asynchronous projection khi scale, availability hoặc model mismatch chứng minh cần thiết.

```text
                    Application
                   /           \
                  /             \
            Commands           Queries
               |                  |
        Domain/Aggregates      Read Models
               |                  |
               +------ SQL -------+

Level tiếp theo, chỉ khi cần:
Commands -> Write DB -> Events -> Projection -> Read DB
```

**Khi phù hợp:** Domain write-side có invariants phức tạp nhưng read-side cần projection/search khác biệt, hoặc read/write scale khác nhau. Với CRUD đơn giản, một model thống nhất thường dễ vận hành và bảo trì hơn.
