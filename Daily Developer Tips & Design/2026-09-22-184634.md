# Daily Developer Tips & Design — 2026-09-22

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng chẩn đoán memory leak chỉ từ việc process memory không giảm

**Mẹo:**
Khi .NET process tăng memory, phân biệt managed heap growth, Large Object Heap, native memory và memory mà GC đã giữ lại để tái sử dụng trước khi kết luận có leak.

**Tại sao hữu ích:**
GC không có nghĩa vụ trả ngay mọi committed memory về OS sau collection. Process RSS/working set cao có thể tồn tại dù nhiều managed objects đã chết. Chẩn đoán đúng cần nhìn allocation rate, heap size sau GC, generation, object retention và native allocations thay vì chỉ nhìn Task Manager.

**Ví dụ:**
Một API xử lý file lớn tăng từ 500 MB lên 2 GB rồi giữ quanh 1.5 GB. Trước khi sửa code, thu thập `dotnet-counters`/dump và kiểm tra GC heap sau Gen 2 collection. Nếu heap ổn định nhưng process memory vẫn cao, investigation khác hoàn toàn trường hợp số lượng `byte[]` được retained liên tục tăng.

**Lưu ý:**
Không gọi `GC.Collect()` định kỳ để ép memory giảm trong production. Forced full collections có thể làm latency xấu hơn và che root cause về object lifetime hoặc allocation pattern.

### Tip 2 — Cosmos DB partition key phải đi theo access pattern, không chỉ theo domain field đẹp

**Mẹo:**
Chọn partition key dựa trên cardinality, phân phối traffic và query patterns thực tế. Một field hợp lý về business nhưng tập trung phần lớn request vào vài values có thể tạo hot partition.

**Tại sao hữu ích:**
Cosmos DB phân phối data và throughput theo partitioning. Nếu phần lớn reads/writes dồn vào một logical partition, tăng tổng RU không nhất thiết loại bỏ bottleneck tại partition nóng; cross-partition query cũng tăng request cost và fan-out.

**Ví dụ:**
Hệ thống multi-tenant dùng `TenantId` có thể phù hợp nếu tenants tương đối cân bằng. Nhưng nếu một enterprise tenant tạo 70% traffic, cần đánh giá partition strategy khác hoặc synthetic key thay vì mặc định `TenantId` luôn tốt.

**Lưu ý:**
Partition key là quyết định khó thay đổi sau khi hệ thống có nhiều dữ liệu. Đừng tối ưu chỉ cho storage distribution mà bỏ qua transaction scope và queries cần chạy thường xuyên.

### Tip 3 — Managed Identity loại bỏ secret nhưng không loại bỏ authorization design

**Mẹo:**
Trên Azure, ưu tiên Managed Identity khi App Service, Function hoặc workload cần truy cập Key Vault/Storage/Service Bus, nhưng cấp quyền tối thiểu cho đúng identity và đúng resource scope.

**Tại sao hữu ích:**
Managed Identity loại bỏ việc application phải lưu và rotate client secret. Tuy nhiên authentication thành công chỉ chứng minh workload là ai; RBAC/access policy vẫn quyết định workload được phép làm gì. Quyền quá rộng biến identity không-secret thành một principal có blast radius lớn.

**Ví dụ:**
Order API đọc một nhóm secrets trong Key Vault và gửi message vào một Service Bus queue. Identity của API chỉ nhận quyền cần thiết cho các operations đó thay vì Contributor trên subscription hoặc namespace rộng hơn nhu cầu.

**Lưu ý:**
Đừng fallback sang connection string hard-code chỉ vì local development khác Azure. Tách local credential flow và production Managed Identity rõ ràng, đồng thời kiểm tra permissions như một phần của deployment.

### Tip 4 — Dùng browser Network waterfall để tìm frontend chậm trước khi tối ưu component

**Mẹo:**
Khi trang Vue/React load chậm, mở DevTools Network và xác định request nào nằm trên critical path, request nào bị serialize không cần thiết và payload nào quá lớn trước khi refactor rendering code.

**Tại sao hữu ích:**
Frontend latency thường là tổng của DNS/TLS, API latency, dependency chains, bundle tải xuống và rendering. Nếu component chờ API A rồi mới biết để gọi API B dù hai request độc lập, micro-optimize JavaScript không giải quyết bottleneck chính.

**Ví dụ:**
Trang dashboard mất 3 giây. Waterfall cho thấy profile API 700 ms hoàn tất rồi mới bắt đầu permissions API 900 ms dù cả hai chỉ cần access token. Chạy song song hai calls có thể giảm critical path đáng kể mà không thay đổi framework.

**Lưu ý:**
Không parallelize mọi request. Calls có dependency dữ liệu hoặc backend capacity hạn chế vẫn cần sequencing/batching phù hợp; đo cả server impact thay vì chỉ nhìn browser nhanh hơn.

### Tip 5 — Với AI code review, bắt agent chứng minh claim bằng source và test

**Mẹo:**
Khi dùng AI coding agent để review repository, yêu cầu mọi finding quan trọng trỏ tới file/function cụ thể, mô tả execution path và đề xuất cách tái hiện hoặc test thất bại.

**Tại sao hữu ích:**
AI có thể suy diễn từ tên class, pattern phổ biến hoặc documentation mà không kiểm tra implementation thực. Evidence-based review biến một nhận xét “có vẻ lỗi” thành hypothesis có thể xác minh và giảm thời gian developer xử lý false positive.

**Ví dụ:**
Thay vì chấp nhận “endpoint có race condition”, yêu cầu agent chỉ ra hai concurrent paths cùng mutate state nào, synchronization hiện tại ở đâu và viết integration test chạy concurrent requests để chứng minh invariant bị phá.

**Lưu ý:**
Test do AI sinh cũng có thể xác nhận assumption sai hoặc mock mất behavior quan trọng. Review assertion, test boundary và production semantics trước khi coi finding đã được chứng minh.

## 🧠 Software Design

### Design 1 — REST hay messaging phải bắt đầu từ coupling và failure semantics

**Khái niệm:**
REST phù hợp khi caller cần response trong cùng interaction và chấp nhận temporal coupling. Messaging phù hợp khi workflow có thể xử lý bất đồng bộ, cần buffering hoặc muốn producer không phụ thuộc consumer đang online tại thời điểm gửi.

**Vấn đề nó giải quyết:**
Dùng synchronous call cho mọi integration tạo chuỗi dependency dễ lan truyền timeout. Ngược lại, biến mọi command thành message làm workflow khó quan sát và tăng eventual-consistency complexity dù business thực sự cần response ngay.

**Ví dụ thực tế:**
Checkout cần pricing tức thời trước khi xác nhận giá nên synchronous API có thể hợp lý. Sau khi order đã được chấp nhận, gửi email và analytics có thể đi qua messaging vì chúng không cần nằm trên latency path của customer.

**Trade-off:**
REST đơn giản về request/response và consistency tức thời nhưng tăng runtime coupling. Messaging tăng resilience và decoupling theo thời gian nhưng thêm broker, retries, duplicates, ordering, tracing và eventual consistency.

**Middle → Senior insight:**
Middle developer cần implement timeout/retry hoặc consumer idempotency đúng theo communication style. Senior / Technical developer phải chọn boundary dựa trên business latency, consistency, failure isolation và operational capability thay vì mặc định Microservices phải dùng event everywhere.

### Design 2 — Cache invalidation là consistency policy, không chỉ là thao tác `Remove`

**Khái niệm:**
Thiết kế cache cần xác định source of truth, thời điểm dữ liệu được coi là stale, TTL, invalidation mechanism và behavior khi cache unavailable. `Remove(key)` chỉ là một implementation detail trong policy đó.

**Vấn đề nó giải quyết:**
Cache tăng tốc reads nhưng tạo thêm một bản sao dữ liệu. Khi database thay đổi mà cache chưa thay đổi, hệ thống phải có semantics rõ về việc stale data được chấp nhận bao lâu và ai chịu trách nhiệm đồng bộ.

**Ví dụ thực tế:**
Product catalog cho phép giá trị description stale 5 phút nhưng inventory không được stale theo cùng policy. Hai loại data vì thế không nên dùng một cache strategy chỉ vì cùng nằm trong `ProductDto`.

**Trade-off:**
TTL đơn giản và resilient nhưng có stale window. Event-driven invalidation giảm stale time nhưng thêm message reliability và race conditions. Write-through có consistency path rõ hơn nhưng tăng write latency và coupling với cache availability.

**Middle → Senior insight:**
Middle developer cần key/TTL/invalidation đúng và xử lý cache miss an toàn. Senior / Technical developer phải phân loại consistency requirement theo dữ liệu, thiết kế failure mode khi Redis down và quyết định complexity nào thực sự đáng trả cho freshness cần thiết.

### Design 3 — Anti-Corruption Layer bảo vệ domain khi tích hợp legacy hoặc third-party model

**Khái niệm:**
Anti-Corruption Layer (ACL) dịch model/protocol bên ngoài sang model mà application sở hữu, thay vì để DTO, status code hoặc terminology của external system lan xuyên qua domain.

**Vấn đề nó giải quyết:**
Third-party API và legacy system thay đổi theo lifecycle riêng. Nếu business logic phụ thuộc trực tiếp vào external schema, một thay đổi vendor hoặc migration sẽ lan rộng qua nhiều layers và làm domain mang semantics không thuộc về nó.

**Ví dụ thực tế:**
Legacy ERP biểu diễn order status bằng numeric codes và nullable flags. Integration adapter chuyển chúng thành các concepts rõ ràng trong Ordering domain; application code không cần biết `Status=17` của ERP nghĩa là gì.

**Trade-off:**
ACL giảm coupling và cô lập migration nhưng thêm mapping code, tests và nguy cơ translation mất thông tin. Với integration rất nhỏ, ổn định và chỉ dùng ở một boundary, abstraction quá dày có thể không đáng chi phí.

**Middle → Senior insight:**
Middle developer cần giữ external contracts ở integration boundary và test mapping edge cases. Senior / Technical developer phải quyết định mức isolation cần thiết, ownership của canonical model và tránh biến ACL thành một generic abstraction layer khổng lồ không phản ánh business semantics.
