# Daily Developer Tips & Design — 2026-09-12

## 🛠 Developer Tips & Tricks

### Tip 1 — Đừng giữ `HttpClient` handler quá lâu nếu DNS của downstream có thể thay đổi

**Mẹo:**
Khi gọi external API từ ASP.NET Core, dùng `IHttpClientFactory` và cấu hình handler lifetime phù hợp thay vì tự tạo một `HttpClient` singleton với connection pool sống vô thời hạn.

**Tại sao hữu ích:**
`HttpClient` tái sử dụng connection là đúng, nhưng connection pool có thể tiếp tục nói chuyện với IP cũ sau khi DNS của downstream thay đổi. `IHttpClientFactory` quản lý handler lifecycle để cân bằng connection reuse với DNS refresh.

**Ví dụ:**
```csharp
builder.Services
    .AddHttpClient<PaymentClient>(client =>
    {
        client.BaseAddress = new Uri("https://payments.example.com");
        client.Timeout = TimeSpan.FromSeconds(3);
    })
    .SetHandlerLifetime(TimeSpan.FromMinutes(5));
```

Nếu downstream chạy sau load balancer, container platform hoặc failover DNS, behavior này đáng kiểm tra trong production troubleshooting.

**Lưu ý:**
Không tạo `new HttpClient()` cho từng request; cách đó dễ gây socket exhaustion. Ngược lại, handler lifetime quá ngắn làm mất lợi ích connection pooling và tăng TLS/DNS overhead.

### Tip 2 — Với SQL Server, dùng `INCLUDE` để cover query thay vì nhét mọi cột vào key của index

**Mẹo:**
Nếu query filter/sort bằng vài cột nhưng chỉ cần thêm một số cột để trả kết quả, cân nhắc nonclustered index với `INCLUDE` cho các cột chỉ dùng để đọc.

**Tại sao hữu ích:**
Một covering index có thể giúp SQL Server trả kết quả trực tiếp từ index mà không cần key lookup về clustered index/table. Giữ các cột không tham gia search/sort ở phần `INCLUDE` cũng tránh làm key của index rộng hơn cần thiết.

**Ví dụ:**
```sql
CREATE INDEX IX_Orders_Status_CreatedAt
ON Orders (Status, CreatedAt DESC)
INCLUDE (CustomerId, Total);
```

Query sau có thể được cover tốt hơn:
```sql
SELECT CustomerId, Total, CreatedAt
FROM Orders
WHERE Status = @Status
ORDER BY CreatedAt DESC;
```

**Lưu ý:**
Covering index không miễn phí. Mỗi cột thêm vào làm index lớn hơn, tốn storage, cache và write I/O. Xác nhận bằng actual execution plan và workload thực tế thay vì cố cover mọi query.

### Tip 3 — Propagate trace context qua message broker nếu muốn thấy một distributed trace hoàn chỉnh

**Mẹo:**
Khi publish message từ HTTP request sang Azure Service Bus hoặc broker khác, propagate trace context trong message properties để consumer tiếp tục cùng distributed trace thay vì tạo một trace hoàn toàn mới.

**Tại sao hữu ích:**
Nếu HTTP request kết thúc ở producer và consumer sinh trace độc lập, Application Insights/OpenTelemetry khó nối được user request với background processing. Trace propagation giúp điều tra latency và failure xuyên asynchronous boundary.

**Ví dụ:**
```text
HTTP POST /orders
trace-id = abc123

Producer
-> publish OrderCreated
-> message carries trace context

Consumer
-> creates child activity from propagated context
-> DB call + external call cùng nằm trong trace abc123
```

Dùng instrumentation chuẩn của OpenTelemetry/Azure SDK trước khi tự định nghĩa header riêng.

**Lưu ý:**
Trace context không thay thế business correlation ID. Một business workflow có thể kéo dài hơn thời gian trace hợp lý hoặc tạo nhiều message; khi đó nên có cả `OrderId`/`CorrelationId` phục vụ nghiệp vụ.

### Tip 4 — Dùng `git rerere` khi phải resolve cùng kiểu conflict nhiều lần

**Mẹo:**
Trong branch dài hoặc rebase nhiều lần, có thể bật `rerere` để Git ghi nhớ cách bạn đã resolve một conflict và thử tái áp dụng resolution khi cùng conflict xuất hiện lại.

**Tại sao hữu ích:**
Khi branch liên tục rebase lên main, cùng một vùng code có thể conflict lặp đi lặp lại. `rerere` giảm thao tác thủ công và giúp workflow rebase/cherry-pick hiệu quả hơn.

**Ví dụ:**
```bash
git config --global rerere.enabled true
```

Sau khi bạn resolve conflict và commit/rebase thành công, Git lưu resolution tương ứng để tái sử dụng nếu conflict tương tự xuất hiện.

**Lưu ý:**
Luôn review resolution Git tự áp dụng. Context có thể đã thay đổi dù conflict text giống nhau; không được coi reused resolution là tự động đúng về semantics.

### Tip 5 — Khi Core Web Vitals xấu, đọc network waterfall trước khi tối ưu JavaScript ngẫu nhiên

**Mẹo:**
Nếu LCP hoặc INP của website xấu, dùng browser DevTools/Lighthouse để xác định resource nào chặn rendering, request nào nối chuỗi và script nào chiếm main thread trước khi tối ưu theo cảm tính.

**Tại sao hữu ích:**
Một hero image tải muộn do CSS discovery, font blocking hoặc backend TTFB cao có thể ảnh hưởng LCP nhiều hơn việc giảm vài kilobyte JavaScript. Network waterfall cho evidence về critical path thực tế.

**Ví dụ:**
```text
Document TTFB: 900 ms
-> CSS discovered
-> hero image chỉ được discover sau CSS
-> image tải 1.2 s

Kết luận:
LCP không chỉ là vấn đề "ảnh lớn";
backend latency + discovery order cũng nằm trên critical path.
```

**Lưu ý:**
Lighthouse local chỉ là một sample. Kết hợp lab data với Real User Monitoring nếu có; production device/network distribution có thể khác mạnh máy developer.

## 🧠 Software Design

### Design 1 — Transaction boundary nên theo business operation, không theo từng Repository call

**Khái niệm:**
Một transaction nên bao quanh tập thay đổi cần thành công hoặc thất bại cùng nhau theo invariant nghiệp vụ. Việc mỗi Repository tự `SaveChanges` hoặc tự mở transaction thường làm boundary bị chia nhỏ sai chỗ.

**Vấn đề nó giải quyết:**
Nếu `CreateOrder`, `ReserveStock` và `RecordPaymentIntent` là các thay đổi trong cùng database cần atomic, commit từng Repository riêng lẻ có thể để hệ thống ở trạng thái nửa hoàn tất khi bước sau thất bại.

**Ví dụ thực tế:**
```text
PlaceOrder use case:
1. tạo Order
2. giảm AvailableStock
3. ghi PaymentIntent
4. SaveChanges/COMMIT một lần
```

Application service/use case boundary thường là nơi tự nhiên để quyết định transaction, thay vì để mỗi data-access class tự commit.

**Trade-off:**
Transaction rộng hơn giúp bảo vệ invariant nhưng giữ lock lâu hơn và tăng contention nếu chứa network call hoặc work chậm. Transaction quá nhỏ giảm lock time nhưng có thể phá atomicity nghiệp vụ.

**Middle → Senior insight:**
Middle developer cần biết `SaveChanges` và transaction boundary không nên rải tùy tiện qua Repository. Senior / Technical developer phải xác định invariant nào thật sự cần atomic, loại work nào phải đưa ra ngoài transaction và khi nào cần eventual consistency thay vì kéo transaction quá rộng.

### Design 2 — Circuit Breaker nên đặt theo dependency failure domain, không theo mọi method call

**Khái niệm:**
Circuit Breaker ngăn application tiếp tục gọi một dependency đang thất bại trong một khoảng thời gian, cho hệ thống cơ hội phục hồi và tránh lãng phí resource. Boundary breaker nên phản ánh dependency/failure domain thực tế.

**Vấn đề nó giải quyết:**
Nếu payment provider đang timeout, hàng nghìn request tiếp tục chờ timeout sẽ giữ socket/thread/resource và có thể kéo application vào cascading failure. Nhưng đặt breaker cho từng method nhỏ có thể tạo quá nhiều state và behavior khó dự đoán.

**Ví dụ thực tế:**
```text
PaymentProviderClient
- Authorize
- Capture
- Refund

Nếu cả ba dùng cùng downstream endpoint/failure domain,
có thể chia sẻ policy phù hợp theo provider thay vì mỗi method có breaker độc lập không liên quan.
```

Nếu provider có endpoint độc lập với SLA khác nhau, tách policy có thể hợp lý hơn.

**Trade-off:**
Circuit Breaker giảm load khi dependency hỏng và fail fast, nhưng có thể từ chối request trong thời gian downstream đã bắt đầu phục hồi. Threshold quá nhạy gây false-open; quá chậm lại không bảo vệ được hệ thống.

**Middle → Senior insight:**
Middle developer cần hiểu timeout, retry và circuit breaker phối hợp ra sao. Senior / Technical developer phải thiết kế policy theo dependency topology, traffic volume, SLO, fallback capability và blast radius thay vì áp cùng một Polly policy cho mọi HTTP call.

### Design 3 — Feature Flag tách deployment khỏi release, nhưng phải có lifecycle và owner

**Khái niệm:**
Feature Flag cho phép deploy code vào production nhưng kiểm soát thời điểm hoặc nhóm user được bật behavior mới. Nó giúp giảm coupling giữa kỹ thuật deploy và quyết định release.

**Vấn đề nó giải quyết:**
Một feature lớn có thể cần merge sớm, test production với nhóm nhỏ hoặc rollback nhanh mà không redeploy. Flag cũng hữu ích cho gradual rollout và giảm rủi ro release đồng loạt.

**Ví dụ thực tế:**
```text
CheckoutV2 deployed = yes
CheckoutV2 enabled:
- internal users: 100%
- 5% production traffic
- sau đó 25% -> 50% -> 100%

Nếu error rate tăng:
-> disable flag
-> không cần rollback toàn deployment
```

**Trade-off:**
Feature Flag tăng release flexibility nhưng tạo nhiều execution path, test matrix và dead code. Flag tồn tại quá lâu trở thành technical debt và có thể làm behavior production khó hiểu.

**Middle → Senior insight:**
Middle developer cần viết code flag rõ ràng và test cả enabled/disabled path. Senior / Technical developer phải định nghĩa owner, expiry date, rollout metrics, kill-switch semantics và cleanup process để flag không trở thành kiến trúc vĩnh viễn.
