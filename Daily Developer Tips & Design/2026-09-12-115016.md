# Daily Developer Tips & Design — 2026-09-12

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `TimeProvider` để test logic phụ thuộc thời gian mà không cần `DateTime.UtcNow`

**Mẹo:**
Trong .NET 8+, inject `TimeProvider` vào service có logic về expiration, retry window, schedule hoặc timeout thay vì gọi trực tiếp `DateTime.UtcNow` ở nhiều nơi.

**Tại sao hữu ích:**
Khi code đọc system clock trực tiếp, test phải chờ thời gian thật hoặc dùng workaround khó kiểm soát. `TimeProvider` tách clock khỏi business logic, giúp test deterministic và làm rõ dependency về thời gian.

**Ví dụ:**
```csharp
public sealed class TokenService(TimeProvider timeProvider)
{
    public bool IsExpired(DateTimeOffset expiresAt)
        => timeProvider.GetUtcNow() >= expiresAt;
}
```

Trong test có thể dùng fake time provider để tiến clock mà không `Task.Delay`.

**Lưu ý:**
Không cần inject clock abstraction vào mọi class. Chỉ dùng khi thời gian thực sự ảnh hưởng behavior; abstraction quá rộng cho code thuần CRUD sẽ làm thiết kế nặng hơn cần thiết.

### Tip 2 — Với Azure Service Bus, `PrefetchCount` quá cao có thể làm message hết lock trước khi được xử lý

**Mẹo:**
Khi tăng throughput consumer bằng prefetch, kiểm tra thời gian xử lý thực tế, lock duration và concurrency thay vì chỉ tăng `PrefetchCount` thật lớn.

**Tại sao hữu ích:**
Message được prefetch đã bị lock tại broker. Nếu chúng nằm trong local buffer quá lâu, lock có thể hết trước khi handler bắt đầu hoặc hoàn tất, dẫn tới redelivery và duplicate processing dù consumer không crash.

**Ví dụ:**
```text
Lock duration: 60s
Average processing: 5s
MaxConcurrentCalls: 4
PrefetchCount: 500

=> nhiều message có thể chờ trong memory lâu hơn lock window
=> DeliveryCount tăng, duplicate xuất hiện
```

Theo dõi `DeliveryCount`, lock-lost exception, processing latency và backlog trước khi tune.

**Lưu ý:**
Auto lock renewal không phải lý do để prefetch vô hạn. Prefetch lớn còn tăng memory usage và làm phân phối message giữa nhiều consumer kém cân bằng hơn.

### Tip 3 — Với keyset pagination, luôn có unique tiebreaker trong `ORDER BY`

**Mẹo:**
Nếu dùng keyset pagination theo `CreatedAt`, thêm một field unique như `Id` vào cả `ORDER BY` và điều kiện seek.

**Tại sao hữu ích:**
Nhiều row có thể cùng timestamp. Nếu chỉ seek theo `CreatedAt`, một số row có thể bị bỏ qua hoặc xuất hiện lại giữa các page. Composite ordering tạo thứ tự total order ổn định.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE CreatedAt < @LastCreatedAt
   OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index phù hợp thường bắt đầu theo cùng ordering pattern để tránh scan/sort không cần thiết.

**Lưu ý:**
Keyset pagination phù hợp với next/previous navigation nhưng không thuận tiện cho “nhảy tới page 237”. Nếu product requirement cần random page access, offset pagination hoặc chiến lược hybrid có thể hợp lý hơn.

### Tip 4 — Trong CMS, đừng giữ `IContent` mutable lâu hơn request nếu platform có cache/version semantics riêng

**Mẹo:**
Khi làm việc với Optimizely CMS hoặc CMS tương tự, tránh lấy content một lần rồi giữ reference lâu dài trong singleton/service cache tùy ý. Hãy tôn trọng content cache và version lifecycle của platform.

**Tại sao hữu ích:**
Content có thể được publish, expire, language fallback hoặc invalidate giữa các request. Một object được giữ ngoài lifecycle chuẩn có thể trở thành stale state và khiến production hiển thị nội dung không đồng nhất giữa instance.

**Ví dụ:**
```text
Không nên:
Singleton ProductContentService
-> load page lúc startup
-> giữ object trong field nhiều giờ

Nên:
request/job
-> resolve content qua CMS API/cache chuẩn
-> map sang immutable DTO nếu cần truyền sâu hơn
```

**Lưu ý:**
Không phải mọi cache custom đều sai. Nếu cần cache projection đắt đỏ, cache DTO với key/version/invalidation rõ ràng thay vì cache trực tiếp domain object của CMS không kiểm soát lifecycle.

### Tip 5 — Khi log authentication failure, giữ evidence nhưng không log token hoặc secret

**Mẹo:**
Với lỗi JWT/OAuth, log metadata phục vụ diagnosis như issuer, audience mismatch, token expiration category, correlation ID và authentication scheme; không log raw access token, refresh token hoặc Authorization header.

**Tại sao hữu ích:**
Raw token thường là credential có thể replay. Log đủ metadata giúp phân biệt cấu hình sai, clock skew, expired token hay wrong audience mà không biến log system thành kho chứa secret.

**Ví dụ:**
```csharp
logger.LogWarning(
    "Authentication failed. Scheme={Scheme} Reason={Reason} TraceId={TraceId}",
    scheme,
    reason,
    Activity.Current?.TraceId);
```

Có thể log token expiry timestamp đã parse nếu policy cho phép, nhưng không log toàn bộ token.

**Lưu ý:**
PII masking phải nhất quán giữa application logs, reverse proxy, Application Insights và API gateway. Xóa token khỏi application log chưa đủ nếu upstream vẫn ghi Authorization header.

## 🧠 Software Design

### Design 1 — Retry phải nằm trong end-to-end latency budget

**Khái niệm:**
Retry không phải reliability feature độc lập. Nó phải được thiết kế cùng timeout, backoff, circuit breaker và tổng latency budget mà caller có thể chấp nhận.

**Vấn đề nó giải quyết:**
Nếu mỗi tầng tự retry 3 lần, một request đi qua nhiều dependency có thể nhân số lần gọi và kéo latency vượt xa timeout phía client. Khi downstream đang quá tải, retry còn có thể làm outage nặng hơn.

**Ví dụ thực tế:**
```text
Client budget: 2 giây
API -> Payment provider

Không hợp lý:
3 retries x timeout 2 giây
=> riêng dependency đã có thể tốn >6 giây

Hợp lý hơn:
- timeout từng attempt ngắn
- exponential backoff + jitter
- chỉ retry transient failure
- dừng khi không còn đủ latency budget
```

**Trade-off:**
Retry cải thiện success rate với transient fault nhưng tăng traffic, latency và duplicate risk. Retry ít hơn giảm amplification nhưng có thể bỏ lỡ lỗi tạm thời ngắn.

**Middle → Senior insight:**
Middle developer cần phân biệt transient với permanent failure và dùng timeout/backoff đúng. Senior / Technical developer phải thiết kế retry budget theo SLO, idempotency, dependency capacity và cascading-failure risk của toàn call chain.

### Design 2 — CQRS nên áp dụng theo pressure của read/write model, không theo template kiến trúc

**Khái niệm:**
CQRS tách command model và query model khi hai phía có nhu cầu khác biệt đáng kể về validation, consistency, schema hoặc scaling. Nó không yêu cầu mọi application phải có hai database hay event sourcing.

**Vấn đề nó giải quyết:**
Một model duy nhất đôi khi bị kéo theo hai hướng: write model cần invariant rõ và normalized state, trong khi read model cần projection tối ưu cho dashboard/search. Nhưng với CRUD đơn giản, tách hai model chỉ tăng ceremony.

**Ví dụ thực tế:**
```text
Order write path:
- validate inventory
- enforce state transition
- transaction rõ ràng

Order dashboard:
- cần CustomerName, ItemCount, PaymentStatus, ShipmentStatus
- đọc rất nhiều, update ít

Có thể dùng read projection riêng mà vẫn giữ cùng database ban đầu.
```

**Trade-off:**
CQRS cho phép tối ưu read/write độc lập và làm business command rõ hơn, nhưng thêm mapping, synchronization và eventual consistency nếu read model tách riêng. Complexity này chỉ đáng giá khi workload thực sự có pressure tương ứng.

**Middle → Senior insight:**
Middle developer cần tránh nhầm CQRS với “mỗi request phải qua MediatR”. Senior / Technical developer phải xác định chính xác pressure nào cần separation và chọn mức tách nhỏ nhất đủ giải quyết vấn đề.

### Design 3 — Chọn Cosmos DB partition key theo access pattern và transaction boundary

**Khái niệm:**
Partition key quyết định cách dữ liệu được phân phối, query được route và transactional batch có thể hoạt động trong Cosmos DB. Đây là quyết định kiến trúc dữ liệu, không chỉ là field để “chia đều”.

**Vấn đề nó giải quyết:**
Partition key sai có thể tạo hot partition, cross-partition query đắt hoặc làm các entity cần cập nhật atomically nằm ở nhiều logical partition khác nhau.

**Ví dụ thực tế:**
```text
SaaS system:
TenantId có thể là partition key tốt khi:
- hầu hết query scoped theo tenant
- business transaction nằm trong một tenant
- tenant size tương đối kiểm soát được

Nhưng nếu một tenant chiếm phần lớn traffic:
TenantId đơn lẻ có thể tạo hot partition
=> cần xem lại data model hoặc synthetic partition strategy
```

**Trade-off:**
Partition key bám access pattern giúp query rẻ và transaction đơn giản hơn, nhưng khó thay đổi sau khi hệ thống lớn. Synthetic key có thể phân phối tốt hơn nhưng làm query và transaction phức tạp hơn.

**Middle → Senior insight:**
Middle developer cần hiểu partition key ảnh hưởng query cost và transaction scope. Senior / Technical developer phải cân nhắc cardinality, traffic skew, growth model, RU distribution, transactional requirements và migration cost trước khi chốt schema.
