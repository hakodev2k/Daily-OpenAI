# Daily Developer Tips & Design — 2026-09-10

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Channel<T>` bounded để tạo backpressure thay vì để producer đẩy vô hạn

**Mẹo:**
Khi một background pipeline trong .NET có producer tạo work nhanh hơn consumer xử lý, dùng bounded `Channel<T>` để giới hạn số item đang chờ thay vì dùng queue tăng kích thước không kiểm soát.

**Tại sao hữu ích:**
Unbounded queue có thể che giấu overload trong thời gian ngắn nhưng đổi latency thành memory pressure. Khi producer tiếp tục enqueue nhanh hơn consumer, process có thể tăng RAM, GC pressure và cuối cùng fail. Bounded channel biến overload thành backpressure có chủ đích.

**Ví dụ:**
```csharp
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(500)
{
    FullMode = BoundedChannelFullMode.Wait
});

await channel.Writer.WriteAsync(job, ct);
```

Khi buffer đầy, producer phải chờ consumer giải phóng capacity thay vì tiếp tục tích lũy work.

**Lưu ý:**
Backpressure không tự giải quyết throughput thiếu. Nếu consumer luôn chậm hơn producer trong dài hạn, cần giảm input rate, tăng processing capacity hoặc thay đổi architecture. Chọn `DropOldest`/`DropWrite` chỉ khi business semantics cho phép mất dữ liệu.

### Tip 2 — Khi SQL query chậm, so sánh `Estimated Rows` và `Actual Rows` trước khi ép index hint

**Mẹo:**
Trong SQL Server execution plan, nếu query bất ngờ chọn join strategy hoặc scan tệ, kiểm tra chênh lệch giữa estimated row count và actual row count trước khi thêm `FORCESEEK`, index hint hoặc rewrite ngẫu nhiên.

**Tại sao hữu ích:**
Optimizer ra quyết định dựa trên cardinality estimate. Nếu statistics cũ, predicate khó ước lượng hoặc data distribution skewed, plan có thể hợp lý theo estimate nhưng rất tệ với dữ liệu thực tế.

**Ví dụ:**
```text
Estimated Rows: 120
Actual Rows:    850,000
```

Sai lệch lớn như vậy có thể khiến optimizer chọn Nested Loops trong khi Hash Join hoặc plan khác phù hợp hơn với volume thực.

**Lưu ý:**
Index hint có thể sửa symptom cho dataset hiện tại nhưng khóa optimizer vào lựa chọn có thể tệ sau khi data thay đổi. Ưu tiên tìm nguyên nhân như statistics, parameter sensitivity, predicate hoặc schema/index design trước.

### Tip 3 — Trong Vue/React, hủy request cũ khi user đổi search/filter liên tục để tránh stale response ghi đè state mới

**Mẹo:**
Với autocomplete hoặc filter gọi API theo input, dùng `AbortController` để cancel request trước khi gửi request mới.

**Tại sao hữu ích:**
HTTP response không đảm bảo trả về theo thứ tự request. Request cho keyword cũ có thể chậm hơn rồi về sau cùng, ghi đè UI bằng kết quả stale dù user đã nhập giá trị mới.

**Ví dụ:**
```javascript
let controller;

async function search(term) {
  controller?.abort();
  controller = new AbortController();

  const response = await fetch(`/api/search?q=${encodeURIComponent(term)}`, {
    signal: controller.signal
  });

  return response.json();
}
```

**Lưu ý:**
Cancellation phía browser không đảm bảo backend đã dừng xử lý. Nếu backend operation tốn tài nguyên, API cũng cần propagate cancellation từ request xuống database hoặc outbound dependency khi framework hỗ trợ.

### Tip 4 — Ưu tiên `Managed Identity` khi Azure workload truy cập `Key Vault` thay vì lưu client secret trong config

**Mẹo:**
Trên Azure App Service, Function hoặc workload hỗ trợ identity, dùng `Managed Identity` + RBAC để truy cập `Azure Key Vault` thay vì lưu `ClientSecret` trong environment variable hoặc deployment pipeline.

**Tại sao hữu ích:**
Client secret có lifecycle riêng: phải tạo, phân phối, rotate và tránh leak. Managed Identity cho Azure quản lý credential nền, application chỉ yêu cầu token cho resource cần thiết.

**Ví dụ:**
```csharp
var credential = new DefaultAzureCredential();
var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);
```

Local development có thể dùng developer credential; production dùng Managed Identity mà không thay application code.

**Lưu ý:**
Managed Identity không thay thế authorization design. Identity vẫn phải được cấp quyền tối thiểu cần thiết. Không cấp quyền rộng toàn vault hoặc subscription chỉ để “cho chạy được”.

### Tip 5 — Dùng `dotnet-counters` để xác nhận ThreadPool starvation trước khi tăng timeout

**Mẹo:**
Nếu ASP.NET Core API đột nhiên tăng latency dưới load nhưng CPU chưa chắc đạt 100%, theo dõi ThreadPool counters như queue length và thread count trước khi kết luận database hoặc network chậm.

**Tại sao hữu ích:**
Sync-over-async, blocking I/O hoặc `.Result`/`.Wait()` có thể giữ worker threads. Khi request mới phải chờ ThreadPool tạo thêm thread, latency tăng dù dependency vẫn bình thường.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234 System.Runtime
```

Quan sát cùng lúc các signal như ThreadPool queue, thread count, allocation và CPU để xác nhận hypothesis.

**Lưu ý:**
ThreadPool thread tăng không tự động nghĩa là starvation. Cần correlate với request latency, blocking stack trace và dependency telemetry. Tăng timeout thường chỉ làm queue dài hơn nếu root cause là blocking.

## 🧠 Software Design

### Design 1 — Azure Service Bus Queue vs Topic theo consumption semantics, không theo tên feature

**Khái niệm:**
Queue phù hợp khi một logical work item cần được một consumer trong nhóm xử lý. Topic + Subscription phù hợp khi cùng một event cần được nhiều consumer độc lập nhận và xử lý theo nhu cầu riêng.

**Vấn đề nó giải quyết:**
Nếu dùng một Queue cho event mà Billing, Analytics và Notification đều cần nhận, các consumer sẽ cạnh tranh nhau và chỉ một bên nhận message. Ngược lại, dùng Topic cho command chỉ cần một worker xử lý có thể tạo duplication semantics không cần thiết.

**Ví dụ thực tế:**
```text
Command:
GenerateInvoice
-> Queue
-> một worker xử lý

Event:
OrderCompleted
-> Topic
   -> Billing subscription
   -> Loyalty subscription
   -> Analytics subscription
```

**Trade-off:**
Queue đơn giản hơn cho competing consumers và load distribution. Topic tăng fan-out flexibility nhưng thêm subscription management, retry/DLQ riêng và operational visibility cho từng consumer.

**Middle → Senior insight:**
Middle developer cần phân biệt command và event semantics cơ bản. Senior / Technical developer phải xét ownership, delivery guarantees, filtering, replay/recovery, ordering và blast radius trước khi chọn topology; không chọn Topic chỉ vì “có nhiều service”.

### Design 2 — Optimistic concurrency cho collaborative update thay vì khóa record từ lúc user mở form

**Khái niệm:**
Optimistic concurrency cho phép nhiều user đọc cùng dữ liệu, nhưng khi update sẽ kiểm tra version đã đọc có còn hiện hành hay không. Nếu version đã đổi, application phát hiện conflict thay vì âm thầm ghi đè.

**Vấn đề nó giải quyết:**
Giữ database lock trong suốt thời gian user mở form là không khả thi: user có thể để màn hình hàng phút. Nếu không có concurrency check, người save sau sẽ ghi đè thay đổi của người save trước.

**Ví dụ thực tế:**
```text
User A đọc Order version 12
User B đọc Order version 12
User A save -> version 13
User B save với expected version 12 -> conflict
```

Trong EF Core có thể dùng `rowversion`/concurrency token và bắt `DbUpdateConcurrencyException`.

**Trade-off:**
Optimistic concurrency không giữ lock lâu và phù hợp khi conflict hiếm, nhưng application phải thiết kế UX merge/retry/reload. Pessimistic locking có thể hợp lý cho critical short-lived operation với contention cao, nhưng tăng blocking và deadlock risk.

**Middle → Senior insight:**
Middle developer cần không nuốt concurrency exception và tránh last-write-wins ngoài ý muốn. Senior / Technical developer phải quyết định conflict policy theo business invariant: reject, merge field-level, retry tự động hay serialize operation.

### Design 3 — Hexagonal Architecture hữu ích khi cần bảo vệ core khỏi nhiều adapter, nhưng không phải monolith nào cũng cần nó

**Khái niệm:**
Hexagonal Architecture đặt business capability ở core và tương tác với database, HTTP, message broker hoặc external provider qua ports/adapters. Giá trị chính là kiểm soát dependency direction và thay đổi infrastructure mà không làm domain phụ thuộc trực tiếp vào framework.

**Vấn đề nó giải quyết:**
Một application có thể dần để business logic gọi trực tiếp EF Core, SDK vendor, HTTP client và framework type ở mọi nơi. Khi integration đổi hoặc cần test logic độc lập, coupling này làm thay đổi lan rộng.

**Ví dụ thực tế:**
```text
Core use case
  -> PaymentGateway port
       -> Stripe adapter
       -> Fake adapter for tests

Core use case
  -> OrderRepository port
       -> EF Core adapter
```

Không phải mọi class đều cần interface; port nên đại diện cho boundary có ý nghĩa.

**Trade-off:**
Hexagonal Architecture tăng testability và isolation của core nhưng thêm abstraction, mapping và navigation cost. Với CRUD application nhỏ, Layered Architecture đơn giản có thể dễ hiểu và rẻ hơn đáng kể.

**Middle → Senior insight:**
Middle developer cần giữ business rule khỏi bị rải khắp controller/infrastructure. Senior / Technical developer phải xác định boundary nào thực sự có volatility hoặc ownership riêng để tạo port; không tạo interface cho mọi repository/service chỉ để “đúng pattern”.
