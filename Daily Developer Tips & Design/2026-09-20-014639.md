# Daily Developer Tips & Design — 2026-09-20

## 🛠 Developer Tips & Tricks

### Tip 1 — `Task.WhenAll` không biến nhiều I/O thành “an toàn khi chạy song song”

**Mẹo:**
Dùng `Task.WhenAll` khi các operation độc lập và dependency bên dưới chịu được concurrency đó. Đừng chuyển một vòng lặp tuần tự thành hàng trăm request/query đồng thời chỉ vì tất cả API đều là `async`.

**Tại sao hữu ích:**
`async` giải phóng thread trong lúc chờ I/O nhưng không loại bỏ giới hạn connection pool, downstream rate limit hay database capacity. Fan-out không giới hạn có thể giảm tổng latency ở tải nhỏ nhưng gây saturation khi production traffic tăng.

**Ví dụ:**
Một job enrich 2.000 products từ external API không nên tạo 2.000 tasks cùng lúc. Dùng bounded concurrency, đo latency/error/throttling và chọn mức song song dựa trên capacity của dependency.

**Lưu ý:**
Khi nhiều tasks fail, phải hiểu cách aggregate/observe exceptions và cancellation. Bounded concurrency cũng không thay thế timeout, retry classification hoặc idempotency.

### Tip 2 — EF Core `Include` không phải mặc định cho mọi màn hình cần dữ liệu liên quan

**Mẹo:**
Với read endpoint, bắt đầu từ response shape rồi `Select` projection đúng fields cần thiết; chỉ dùng `Include` khi thực sự cần materialize entity graph cho workflow đó.

**Tại sao hữu ích:**
`Include` dễ kéo nhiều columns/rows hơn response cần, đặc biệt với nhiều collections. Projection cho phép database trả đúng shape và thường giảm network, allocation và change-tracking overhead.

**Ví dụ:**
Order list chỉ cần `Id`, `CustomerName`, `Total` và số lines thì project trực tiếp DTO, thay vì `Include(o => o.Lines)` rồi tính/count trong memory. Kiểm tra SQL sinh ra và execution plan khi query quan trọng.

**Lưu ý:**
Projection phức tạp cũng có thể tạo SQL khó tối ưu. Đừng tối ưu theo cảm giác; đo query duration, rows, payload và plan. Với aggregate cần update, entity loading có thể phù hợp hơn.

### Tip 3 — Azure App Service slot swap phải phân biệt code với environment-specific settings

**Mẹo:**
Khi dùng deployment slots, đánh dấu các configuration/secrets phải giữ theo slot là slot settings và kiểm tra behavior của application sau swap, không chỉ trạng thái deployment thành công.

**Tại sao hữu ích:**
Swap chuyển application content/configuration theo semantics của App Service. Nếu production/staging dùng endpoint, secret hoặc feature configuration khác nhau mà sticky settings sai, code đúng vẫn có thể gọi nhầm dependency sau release.

**Ví dụ:**
Staging dùng sandbox payment endpoint còn production dùng live endpoint. Trước swap, verify slot-specific settings, warm-up/health endpoint và dependency connectivity; sau swap correlate release marker với error/latency telemetry.

**Lưu ý:**
Slot swap không tự làm database migration backward-compatible. Nếu old/new instances cùng tồn tại trong rollout, schema change vẫn cần deployment sequence an toàn.

### Tip 4 — Frontend search phải chống stale response, không chỉ debounce

**Mẹo:**
Với Vue/React live search, ngoài debounce hãy cancel request cũ bằng `AbortController` hoặc bỏ qua response không còn tương ứng với query hiện tại.

**Tại sao hữu ích:**
Network response có thể về sai thứ tự. User gõ `camera`, request mới trả trước request cũ `cam`; nếu UI nhận mọi response, kết quả cũ có thể ghi đè state mới dù backend hoàn toàn đúng.

**Ví dụ:**
Mỗi lần query thay đổi, abort fetch trước rồi tạo request mới với `signal`. Nếu client/library không hỗ trợ cancellation đầy đủ, giữ request sequence/token và chỉ commit response của request mới nhất.

**Lưu ý:**
Debounce chỉ giảm số request, không đảm bảo ordering. Cancellation phía browser cũng không đảm bảo server đã dừng work; backend vẫn cần cancellation/capacity strategy phù hợp.

### Tip 5 — AI-generated database migration phải review generated SQL và rollback assumptions

**Mẹo:**
Khi AI coding agent tạo EF Core migration hoặc SQL migration, review generated SQL, lock/scan risk, data-loss behavior và compatibility với version application đang chạy trước khi merge.

**Tại sao hữu ích:**
Migration có thể compile và pass unit tests nhưng vẫn lock bảng lớn, drop dữ liệu, tạo index tốn thời gian hoặc phá rolling deployment. AI thường thiếu production cardinality, traffic và deployment topology nếu context không được cung cấp.

**Ví dụ:**
Agent đề xuất rename column bằng drop/add. Trên production, cách đó có thể mất dữ liệu hoặc tạo breaking window. Kiểm tra migration SQL, schema hiện tại, row count và chọn expand/backfill/contract nếu rollout yêu cầu zero downtime.

**Lưu ý:**
Đừng chỉ hỏi AI “migration này có an toàn không?”. Ground review bằng source, database engine/version, execution plan khi phù hợp, production-like data volume và test migration/rollback path.

## 🧠 Software Design

### Design 1 — Concurrency budget thay vì retry/fan-out độc lập ở từng layer

**Khái niệm:**
Concurrency budget giới hạn lượng work đồng thời mà một request/workflow được phép đẩy xuống dependency. Nó nhìn fan-out, retry và background work như cùng tiêu thụ một capacity hữu hạn.

**Vấn đề nó giải quyết:**
Một API nhận 100 requests đồng thời, mỗi request fan-out 10 calls và mỗi call retry 3 lần có thể tạo hàng nghìn downstream attempts. Local optimization ở từng layer vô tình khuếch đại tải thành cascading failure.

**Ví dụ thực tế:**
Search aggregator gọi Catalog, Pricing và Reviews. Thay vì mỗi integration tự tăng concurrency/retry, hệ thống đặt giới hạn theo dependency, timeout budget và policy degrade khi Reviews chậm nhưng Catalog/Pricing vẫn đủ để trả kết quả hữu ích.

**Trade-off:**
Budget bảo vệ downstream và tail latency nhưng có thể giảm peak throughput hoặc từ chối work sớm. Tuning cần telemetry về saturation, queue time và business priority; một con số cố định cho mọi endpoint thường không hợp lý.

**Middle → Senior insight:**
Middle developer cần hiểu semaphore/concurrency limiter, timeout và cancellation. Senior / Technical developer phải model amplification xuyên layers, phân bổ capacity theo criticality và thiết kế overload behavior thay vì thêm retry ở nơi thấy lỗi.

### Design 2 — Hexagonal Architecture chỉ có giá trị khi ports phản ánh volatility thật

**Khái niệm:**
Hexagonal Architecture đặt business/application logic sau các ports và để database, HTTP client, messaging hoặc UI là adapters. Boundary hữu ích khi nó cô lập một dependency hoặc capability có lý do thay đổi khác core logic.

**Vấn đề nó giải quyết:**
Nếu domain logic phụ thuộc trực tiếp SDK, transport DTO hoặc persistence details, thay integration hoặc test business behavior có thể kéo theo thay đổi xuyên nhiều layers.

**Ví dụ thực tế:**
Pricing application cần lấy exchange rate từ external provider. Một port mang semantics `GetRateAsync(currencyPair)` giữ provider-specific authentication/DTO/retry trong adapter; domain không cần biết vendor API shape.

**Trade-off:**
Ports/adapters giảm coupling và tạo test seams nhưng mỗi abstraction thêm types, mapping và cognitive load. Với CRUD module nhỏ, stable dependency và ít domain logic, layered design trực tiếp có thể rõ hơn.

**Middle → Senior insight:**
Middle developer cần giữ dependency direction và tránh leak infrastructure types. Senior / Technical developer phải chọn boundary dựa trên volatility, ownership và testability; không tạo interface cho mọi class chỉ để “đúng Hexagonal”.

### Design 3 — Lease-based ownership cho scheduled job chạy trên nhiều instances

**Khái niệm:**
Khi cùng application được scale nhiều instances nhưng một scheduled operation chỉ nên có một active owner tại một thời điểm, lease có thời hạn cho phép instance giành quyền xử lý và tự giải phóng quyền khi owner chết/hết lease.

**Vấn đề nó giải quyết:**
Timer chạy trong mỗi App Service/Kubernetes instance có thể khiến cùng reconciliation hoặc billing job chạy nhiều lần. Một lock không có expiry lại có thể làm job ngừng vĩnh viễn nếu process chết khi đang giữ lock.

**Ví dụ thực tế:**
Mỗi worker cố acquire lease cho `nightly-reconciliation`, renew trong lúc chạy và dừng khi mất lease. Business writes vẫn dùng idempotency để bảo vệ trường hợp owner chết quanh ranh giới side effect rồi job được instance khác tiếp quản.

**Trade-off:**
Lease giảm concurrent ownership nhưng thêm clock/renewal/failure semantics và phụ thuộc shared coordination store. Với workload vốn có thể partition thành độc lập hoặc broker đã cung cấp competing-consumer semantics, global lease có thể là bottleneck không cần thiết.

**Middle → Senior insight:**
Middle developer cần implement acquire/renew/release và cancellation khi mất lease đúng. Senior / Technical developer phải xác định lease duration, fencing/idempotency, recovery semantics và cân nhắc scheduler/broker chuyên dụng thay vì tự xây distributed coordination.
