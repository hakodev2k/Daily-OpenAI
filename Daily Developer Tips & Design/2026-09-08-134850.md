# Daily Developer Tips & Design — 2026-09-08

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ExecuteUpdateAsync` cho bulk update khi không cần load entity

**Mẹo:**
Khi cần update nhiều row theo cùng một rule và không cần chạy domain logic trên từng entity, cân nhắc `ExecuteUpdateAsync()` của EF Core thay vì query toàn bộ entity, sửa từng object rồi `SaveChanges()`.

**Tại sao hữu ích:**
Cách load-then-update tạo materialization, change tracking và nhiều dữ liệu đi qua application không cần thiết. `ExecuteUpdateAsync()` dịch operation thành một câu `UPDATE` trực tiếp ở database, giảm memory, round trip và thời gian giữ `DbContext`.

**Ví dụ:**
```csharp
await dbContext.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.ExpiresAt < now)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired)
        .SetProperty(x => x.UpdatedAt, now),
        cancellationToken);
```

Thay vì load hàng nghìn `Order` rồi update từng entity trong memory.

**Lưu ý:**
`ExecuteUpdateAsync()` bypass change tracker. Entity đang được track trong cùng `DbContext` có thể giữ state cũ. Nó cũng không tự chạy domain method, interceptor hoặc logic dựa trên entity lifecycle như cách bạn có thể kỳ vọng với flow thông thường. Chỉ dùng khi semantics của set-based update phù hợp.

### Tip 2 — Với Cosmos DB, chọn partition key theo traffic distribution chứ không chỉ theo data model

**Mẹo:**
Khi thiết kế container, đánh giá partition key dựa trên cả query pattern và phân bố request. Một key nhìn hợp lý về domain nhưng dồn phần lớn read/write vào vài giá trị có thể tạo hot partition.

**Tại sao hữu ích:**
Cosmos DB scale theo physical partition. Nếu phần lớn RU/s tập trung vào một logical partition hoặc một nhóm nhỏ key, toàn container có thể còn capacity nhưng request vẫn bị throttling ở vùng nóng.

**Ví dụ:**
Một hệ thống multi-tenant dùng:
```text
partition key = /tenantId
```

có thể hoạt động tốt nếu tenant tương đối cân bằng. Nhưng nếu một tenant chiếm 70% traffic, cần xem lại distribution, query scope và khả năng dùng hierarchical/composite strategy phù hợp với workload.

Dấu hiệu cần điều tra:
```text
429 responses tăng
RU consumption lệch mạnh theo partition key range
một số tenant latency cao hơn rõ rệt
```

**Lưu ý:**
Đổi partition key sau khi hệ thống đã lớn thường là migration khó. Đừng chọn key chỉ vì “query tiện”; phải cân nhắc cardinality, growth, tenant skew, transaction boundary và khả năng fan-out query.

### Tip 3 — Phân biệt Kubernetes readiness, liveness và startup probe

**Mẹo:**
Dùng từng probe đúng mục đích: readiness quyết định Pod có nhận traffic hay không, liveness quyết định container có cần restart hay không, startup probe bảo vệ application khởi động chậm khỏi bị liveness giết quá sớm.

**Tại sao hữu ích:**
Cấu hình sai probe có thể biến dependency chậm thành restart loop hoặc route traffic vào Pod chưa sẵn sàng. Đây là failure mode phổ biến khi health endpoint gom mọi dependency vào một check duy nhất.

**Ví dụ:**
```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080

livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
```

`/health/ready` có thể kiểm tra application đã sẵn sàng phục vụ request quan trọng; `/health/live` nên chủ yếu trả lời process còn hoạt động hay đã rơi vào trạng thái không thể tự phục hồi.

**Lưu ý:**
Không nên để liveness phụ thuộc trực tiếp vào database hoặc external API nếu outage ngắn của dependency sẽ khiến hàng loạt Pod restart đồng thời. Restart chỉ hữu ích khi restart có khả năng sửa được lỗi.

### Tip 4 — Dùng `git reflog` để cứu branch hoặc commit vừa “biến mất”

**Mẹo:**
Nếu vừa `reset --hard`, rebase sai hoặc xóa branch local khiến commit không còn thấy trong history bình thường, kiểm tra `git reflog` trước khi kết luận code đã mất.

**Tại sao hữu ích:**
Git giữ lịch sử di chuyển của `HEAD` và branch ref trong reflog một thời gian. Nhiều lỗi Git tưởng như mất code thực ra chỉ làm commit không còn reachable từ branch hiện tại.

**Ví dụ:**
```bash
git reflog
```

Có thể thấy:
```text
91ab123 HEAD@{0}: reset: moving to HEAD~3
4df8210 HEAD@{1}: commit: Fix checkout race condition
```

Khôi phục bằng:
```bash
git branch recovery/checkout-fix 4df8210
```

**Lưu ý:**
Reflog chủ yếu là local và không phải backup vĩnh viễn. Nếu object đã bị garbage-collected hoặc commit chỉ tồn tại ở máy khác, khả năng khôi phục thay đổi. Đừng dùng reflog thay cho remote backup và branch protection.

### Tip 5 — Với AI coding agent, xác minh API và version từ repository trước khi chấp nhận code

**Mẹo:**
Khi dùng AI coding agent để sửa repository, buộc flow kiểm tra `csproj`, package lock, source hiện tại và test trước khi chấp nhận API hoặc pattern mà model đề xuất.

**Tại sao hữu ích:**
AI có thể nhớ đúng một API nhưng sai version, dùng extension method chưa được cài package hoặc áp pattern từ phiên bản framework mới hơn. Lỗi kiểu này thường nhìn “rất hợp lý” trong code review nhưng fail khi build hoặc tạo behavior khác với repository thực tế.

**Ví dụ:**
Một agent đề xuất API mới trong .NET package X. Trước khi merge:
```bash
dotnet list package
dotnet build
dotnet test
```

Sau đó kiểm tra signature thật trong source/package documentation phù hợp với version đang dùng, thay vì chỉ tin vào code generation.

**Lưu ý:**
Test pass chưa chứng minh implementation đúng hoàn toàn. Generated test cũng có thể lặp lại cùng giả định sai của generated code. Với thay đổi quan trọng, cần kiểm tra requirement, edge case, security và production behavior độc lập với output của agent.

## 🧠 Software Design

### Design 1 — CQRS chỉ đáng dùng khi read/write model thực sự có áp lực khác nhau

**Khái niệm:**
CQRS tách command model và query model khi hai phía có nhu cầu khác đáng kể về domain rule, data shape, scaling hoặc ownership. Nó không đồng nghĩa bắt buộc phải có hai database hay Event Sourcing.

**Vấn đề nó giải quyết:**
Một hệ thống có write model giàu invariant nhưng read side cần dashboard, search hoặc projection rất khác có thể trở nên khó tối ưu nếu bắt một model phục vụ cả hai mục tiêu.

**Ví dụ thực tế:**
Order domain có thể xử lý command qua aggregate và transaction rule chặt chẽ, trong khi dashboard cần read model phẳng:
```text
Command: PlaceOrder -> domain model -> SQL transaction
Query: OrderDashboard -> projection/read model -> optimized query
```

Nếu ứng dụng chỉ là CRUD với vài endpoint đơn giản, một model chung có thể tốt hơn.

**Trade-off:**
CQRS cho phép tối ưu read/write độc lập và boundary rõ hơn, nhưng thêm mapping, synchronization, eventual consistency và mental overhead. Nếu team phải vận hành projection pipeline chỉ để phục vụ vài query đơn giản, complexity có thể vượt lợi ích.

**Middle → Senior insight:**
Middle developer cần hiểu command không nên trả thành một “query framework” trá hình và query không nên chứa side effect. Senior / Technical developer phải đánh giá mức độ khác biệt của read/write pressure, consistency requirement, team ownership và chi phí vận hành trước khi quyết định tách model.

### Design 2 — Azure Service Bus Queue vs Topic: chọn theo số consumer độc lập

**Khái niệm:**
Queue phù hợp khi một message cần được xử lý bởi một logical consumer group. Topic + Subscription phù hợp khi cùng một event cần được nhiều consumer độc lập nhận theo nhu cầu riêng.

**Vấn đề nó giải quyết:**
Nếu Billing, Analytics và Notification đều cần phản ứng với `OrderPlaced`, dùng một queue chung khiến các consumer cạnh tranh cùng message thay vì mỗi hệ thống có bản sao riêng. Ngược lại, dùng topic cho một job chỉ cần một worker group có thể làm topology phức tạp không cần thiết.

**Ví dụ thực tế:**
```text
Queue: GenerateInvoice
  -> nhiều worker cùng cạnh tranh xử lý một job

Topic: OrderPlaced
  -> Billing subscription
  -> Analytics subscription
  -> Notification subscription
```

Mỗi subscription có retry, dead-letter và filter riêng.

**Trade-off:**
Topic tăng decoupling và cho phép fan-out, nhưng tăng số subscription, DLQ, monitoring và schema compatibility cần quản lý. Queue đơn giản hơn nhưng không phù hợp khi nhiều business capability cần tiêu thụ cùng event độc lập.

**Middle → Senior insight:**
Middle developer cần phân biệt competing consumers với pub/sub. Senior / Technical developer phải thiết kế event ownership, subscription lifecycle, retry isolation, message filtering, schema evolution và tránh biến topic thành broadcast bus không kiểm soát.

### Design 3 — Đặt rate limiting theo boundary cần bảo vệ, không mặc định chỉ ở API Gateway

**Khái niệm:**
Rate limiting có thể tồn tại ở edge/gateway, application hoặc từng downstream integration. Vị trí đúng phụ thuộc resource nào cần bảo vệ và identity nào có ý nghĩa tại boundary đó.

**Vấn đề nó giải quyết:**
Một gateway có thể chặn client gửi quá nhiều request, nhưng vẫn không ngăn một request hợp lệ fan-out thành hàng chục call xuống dependency yếu. Ngược lại, chỉ limit ở application có thể để traffic xấu tiêu tốn network, TLS và gateway resource trước khi bị chặn.

**Ví dụ thực tế:**
Một public API có thể áp:
```text
Edge: 100 req/min per API key
Application: 10 concurrent report generations per tenant
Outbound integration: 20 req/sec tới partner API
```

Ba limit bảo vệ ba resource khác nhau.

**Trade-off:**
Nhiều lớp rate limiting tăng resilience nhưng làm behavior khó hiểu hơn, đặc biệt khi client nhận `429` từ nhiều nguồn khác nhau. Cần contract rõ về retry-after, quota semantics, observability và distributed counter accuracy.

**Middle → Senior insight:**
Middle developer cần biết implement limiter đúng key, tránh global lock và trả response phù hợp. Senior / Technical developer phải xác định threat/resource model, placement của limiter, quota ownership, fairness giữa tenant và cách hệ thống degrade khi dependency giới hạn capacity.
