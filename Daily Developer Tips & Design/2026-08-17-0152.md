# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `ActivitySource` để trace custom operation trong .NET

**Mẹo:**
Khi OpenTelemetry đã được bật, dùng `ActivitySource` cho các operation quan trọng thay vì chỉ log start/end bằng text.

**Tại sao hữu ích:**
Trace cho thấy latency theo từng bước và liên kết operation với request hiện tại, giúp tìm bottleneck trong flow nhiều service hoặc nhiều dependency.

**Ví dụ:**
```csharp
private static readonly ActivitySource Source = new("Orders");

using var activity = Source.StartActivity("ReserveInventory");
activity?.SetTag("order.id", orderId);

await inventoryService.ReserveAsync(orderId, cancellationToken);
```

**Lưu ý:**
Không tạo span cho mọi method nhỏ. Quá nhiều spans làm tăng telemetry cost và khiến trace khó đọc.

### Tip 2 — Dùng `ExecuteUpdateAsync` khi không cần load entity trong EF Core

**Mẹo:**
Với bulk update đơn giản, dùng `ExecuteUpdateAsync` thay vì query entity vào memory rồi thay đổi từng record.

**Tại sao hữu ích:**
Giảm round-trip, memory usage và change-tracking overhead vì database thực hiện update trực tiếp.

**Ví dụ:**
```csharp
await dbContext.Orders
    .Where(x => x.Status == OrderStatus.Pending && x.CreatedAt < cutoff)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(x => x.Status, OrderStatus.Expired),
        cancellationToken);
```

**Lưu ý:**
`ExecuteUpdateAsync` không chạy logic đang nằm trong entity setter hoặc tracked entity state. Cần hiểu rõ business rules trước khi dùng.

### Tip 3 — Dùng `curl -v` để phân biệt lỗi HTTP với lỗi TLS/DNS/network

**Mẹo:**
Khi API gọi được từ máy này nhưng fail từ server khác, thử `curl -v` ngay trên chính host gặp lỗi.

**Tại sao hữu ích:**
Bạn thấy DNS resolution, TCP/TLS handshake, request headers và response headers, từ đó phân biệt lỗi application với network hoặc certificate.

**Ví dụ:**
```bash
curl -v https://api.example.com/health
```

Nếu cần kiểm tra timeout:

```bash
curl -v --connect-timeout 5 --max-time 10 https://api.example.com/health
```

**Lưu ý:**
Không dùng `-k` như một cách sửa lỗi certificate trong production. Nó chỉ nên dùng để chẩn đoán tạm thời vì bỏ qua TLS certificate validation.

### Tip 4 — Tránh `Task.WhenAll` không giới hạn với tập dữ liệu lớn

**Mẹo:**
Nếu có hàng nghìn công việc I/O, đừng tạo hàng nghìn task cùng lúc. Giới hạn concurrency bằng `Parallel.ForEachAsync`, `SemaphoreSlim` hoặc worker queue.

**Tại sao hữu ích:**
Giảm nguy cơ làm cạn socket, database connection pool, rate limit hoặc memory khi tải tăng.

**Ví dụ:**
```csharp
await Parallel.ForEachAsync(
    items,
    new ParallelOptions
    {
        MaxDegreeOfParallelism = 10,
        CancellationToken = cancellationToken
    },
    async (item, ct) =>
    {
        await client.ProcessAsync(item, ct);
    });
```

**Lưu ý:**
Concurrency tối ưu phụ thuộc downstream capacity. Giá trị cao hơn không đồng nghĩa throughput cao hơn.

### Tip 5 — Dùng `git diff --word-diff` khi review thay đổi text lớn

**Mẹo:**
Khi review JSON, Markdown, config hoặc SQL dài, `git diff --word-diff` giúp thấy phần thay đổi nhỏ trong cùng một dòng dễ hơn diff line-based thông thường.

**Tại sao hữu ích:**
Giảm thời gian đọc các thay đổi có nhiều dòng gần giống nhau, đặc biệt với config hoặc generated-looking text.

**Ví dụ:**
```bash
git diff --word-diff
```

Hoặc chỉ một file:

```bash
git diff --word-diff -- appsettings.json
```

**Lưu ý:**
Với source code có formatting phức tạp, word diff đôi khi gây nhiễu. Khi đó diff theo line vẫn dễ review hơn.

## 🧠 Software Design

### Design 1 — Bounded Context thay vì dùng một domain model cho toàn hệ thống

**Khái niệm:**
Trong Domain-Driven Design, một khái niệm có thể mang nghĩa khác nhau ở các bounded context khác nhau. Không cần ép toàn hệ thống dùng chung một model duy nhất chỉ vì cùng tên business object.

**Vấn đề nó giải quyết:**
Shared model quá lớn thường tạo coupling: một thay đổi cho Billing có thể ảnh hưởng Orders, Reporting hoặc Identity dù các module cần dữ liệu khác nhau.

**Ví dụ thực tế:**
`Customer` trong Sales cần thông tin prospect và account owner; trong Billing cần invoice address và tax information; trong Support lại quan tâm ticket history. Ba context có thể dùng model riêng và chỉ chia sẻ identifier hoặc integration contract.

**Trade-off:**
Lợi ích là giảm coupling và tăng autonomy. Chi phí là duplicate data/model và cần mapping hoặc synchronization giữa contexts.

**Middle → Senior insight:**
Middle developer nên hiểu không phải mọi duplication đều xấu. Senior developer cần phân biệt duplication có chủ ý để bảo vệ boundary với duplication vô tổ chức, đồng thời thiết kế integration contract ổn định giữa contexts.

### Design 2 — Retry phải đi cùng timeout, backoff và stop condition

**Khái niệm:**
Retry là resilience pattern để thử lại transient failure, nhưng một retry policy tốt phải có timeout, backoff, giới hạn số lần thử và tiêu chí xác định lỗi nào được retry.

**Vấn đề nó giải quyết:**
Retry thiếu kiểm soát có thể biến một downstream đang chậm thành outage toàn hệ thống do retry storm, tăng load đúng lúc dependency yếu nhất.

**Ví dụ thực tế:**
Một service gọi external API. Thay vì retry mọi lỗi 10 lần ngay lập tức, hệ thống chỉ retry `429`, `503` hoặc network timeout với exponential backoff và jitter, ví dụ 200 ms → 500 ms → 1.2 s, rồi dừng.

**Trade-off:**
Retry cải thiện khả năng vượt qua lỗi tạm thời nhưng tăng latency và traffic. Retry quá mạnh có thể làm lỗi lan rộng; retry quá ít có thể làm mất cơ hội phục hồi tự động.

**Middle → Senior insight:**
Middle developer cần biết phân biệt transient và permanent failure. Senior developer phải thiết kế retry budget, timeout hierarchy, jitter, circuit breaker và đảm bảo operation được retry là idempotent hoặc có cơ chế chống duplicate.

### Design 3 — Read Model riêng khi query bắt đầu làm méo domain model

**Khái niệm:**
Không nhất thiết mọi query phải đi qua aggregate/domain model. Với màn hình hoặc report phức tạp, có thể xây read model hoặc projection riêng tối ưu cho nhu cầu đọc.

**Vấn đề nó giải quyết:**
Nếu cố dùng cùng domain model cho cả write behavior và mọi dạng query, code dễ sinh nhiều eager loading, navigation phức tạp và abstraction chỉ để phục vụ UI/reporting.

**Ví dụ thực tế:**
Trang dashboard cần tổng hợp order count, revenue, customer tier và last activity. Thay vì load nhiều aggregate rồi tính trong memory, có thể query trực tiếp sang `DashboardRowDto` bằng SQL/EF projection hoặc một read database riêng nếu scale yêu cầu.

**Trade-off:**
Read model giúp query đơn giản, nhanh và ít ảnh hưởng domain write model. Chi phí là thêm projection, mapping và có thể chấp nhận eventual consistency nếu read model được cập nhật bất đồng bộ.

**Middle → Senior insight:**
Middle developer nên biết projection DTO không phá Clean Architecture nếu dependency vẫn đúng. Senior developer cần nhận ra lúc nào query complexity đủ lớn để tách read model, nhưng cũng tránh áp dụng CQRS đầy đủ khi chỉ cần một projection SQL đơn giản.
