# Daily Developer Tips & Design — 2026-09-11

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Span<T>` cho parsing hot path, không phải để thay mọi `string`

**Mẹo:**
Khi code .NET phải parse nhiều substring trong hot path, cân nhắc `ReadOnlySpan<char>` để tránh tạo string tạm. Hãy dùng sau khi profiling cho thấy allocation từ slicing/parsing thực sự đáng kể.

**Tại sao hữu ích:**
Các thao tác như `Substring` tạo object mới trên heap. `Span<T>` cho phép thao tác trên một vùng memory hiện có mà không copy dữ liệu, nhờ đó có thể giảm allocation và GC pressure trong parser, serializer hoặc protocol handling.

**Ví dụ:**
```csharp
static bool TryParseHeader(ReadOnlySpan<char> input, out int id)
{
    var separator = input.IndexOf(':');
    if (separator < 0)
    {
        id = default;
        return false;
    }

    return int.TryParse(input[(separator + 1)..].Trim(), out id);
}
```

Nếu method được gọi hàng triệu lần, việc tránh substring tạm có thể tạo khác biệt đo được.

**Lưu ý:**
`Span<T>` có lifetime restriction và không thể được lưu tùy ý trên heap hoặc đi xuyên `await`. Với business code thông thường, readability quan trọng hơn micro-optimization chưa được đo.

### Tip 2 — Tách `liveness` và `readiness` để deployment không tự bắn vào chân

**Mẹo:**
Trong ASP.NET Core chạy trên Kubernetes hoặc orchestrator tương tự, dùng health check khác nhau cho `liveness` và `readiness`. `liveness` trả lời process còn sống không; `readiness` trả lời instance đã sẵn sàng nhận traffic chưa.

**Tại sao hữu ích:**
Nếu `liveness` phụ thuộc SQL, Redis hoặc external API, một dependency outage có thể khiến orchestrator restart toàn bộ pod liên tục dù process vẫn khỏe. Điều đó làm incident nặng hơn thay vì phục hồi.

**Ví dụ:**
```csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddSqlServer(connectionString, tags: ["ready"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready")
});
```

Khi database tạm thời down, pod có thể bị loại khỏi traffic qua readiness mà không bị restart vô ích.

**Lưu ý:**
Readiness cũng không nên kiểm tra mọi dependency một cách mù quáng. Chỉ đưa dependency vào nếu failure của nó thực sự khiến instance không thể phục vụ request có ý nghĩa.

### Tip 3 — Với pagination lớn, keyset thường ổn định hơn `OFFSET`

**Mẹo:**
Khi API phải paginate sâu trên bảng lớn, cân nhắc keyset pagination dựa trên sort key ổn định thay vì `OFFSET ... FETCH` ngày càng lớn.

**Tại sao hữu ích:**
`OFFSET 500000` vẫn buộc database tìm và bỏ qua một lượng lớn row trước khi trả page tiếp theo. Keyset bắt đầu từ giá trị cuối của page trước nên database có thể seek vào index phù hợp và đọc tiếp.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @LastCreatedAt)
   OR (CreatedAt = @LastCreatedAt AND Id < @LastId)
ORDER BY CreatedAt DESC, Id DESC;
```

Index phù hợp thường bắt đầu theo cùng thứ tự sort, ví dụ `(CreatedAt DESC, Id DESC)`.

**Lưu ý:**
Keyset pagination không phù hợp khi UI bắt buộc nhảy trực tiếp tới page 237 hoặc cần total-page semantics chính xác. Sort key phải deterministic; nếu chỉ sort theo timestamp có duplicate, thêm tie-breaker như `Id`.

### Tip 4 — Điều tra cache CDN bằng response header trước khi purge toàn bộ

**Mẹo:**
Khi website CMS trả content cũ qua CDN/Akamai, kiểm tra `Cache-Control`, `Age`, `ETag`, surrogate/cache-status header và request path trước khi purge toàn site.

**Tại sao hữu ích:**
Stale content có thể đến từ browser cache, CDN edge, reverse proxy hoặc application cache. Purge toàn bộ CDN thường che root cause và gây cache-miss storm khiến backend chịu spike traffic.

**Ví dụ:**
```bash
curl -I https://example.com/products/42
```

Từ response, kiểm tra TTL thực tế, `Age`, cache hit/miss và liệu URL có chứa query string hoặc variant header làm thay đổi cache key hay không.

**Lưu ý:**
Header naming khác nhau giữa CDN provider. Đừng giả định `Cache-Control: no-cache` nghĩa là “không lưu cache”; theo HTTP semantics, nó thường yêu cầu revalidation trước khi reuse.

### Tip 5 — Giảm flaky Playwright test bằng cách chờ state, không chờ thời gian

**Mẹo:**
Trong Playwright, ưu tiên locator assertions và condition-based waiting thay vì `WaitForTimeout` cố định.

**Tại sao hữu ích:**
Timing cố định khiến test vừa chậm vừa flaky: môi trường nhanh vẫn phải chờ đủ, còn CI chậm hơn lại có thể chưa kịp hoàn tất. Auto-wait của Playwright hoạt động tốt hơn khi test mô tả trạng thái người dùng thực sự cần thấy.

**Ví dụ:**
```ts
await page.getByRole('button', { name: 'Save' }).click()
await expect(page.getByText('Saved successfully')).toBeVisible()
await expect(page.getByRole('button', { name: 'Save' })).toBeEnabled()
```

Nếu cần chờ network-specific condition, chờ response hoặc URL state liên quan thay vì sleep vài giây.

**Lưu ý:**
Auto-wait không sửa được race condition trong application. Nếu test vẫn flaky, kiểm tra shared test data, eventual consistency, animation, background jobs và dependency bên ngoài thay vì chỉ tăng timeout.

## 🧠 Software Design

### Design 1 — Bulkhead để giới hạn blast radius của dependency chậm

**Khái niệm:**
Bulkhead tách capacity giữa các loại workload hoặc dependency để một phần hệ thống bị nghẽn không tiêu thụ hết thread, connection hoặc concurrency budget của phần còn lại.

**Vấn đề nó giải quyết:**
Một external API chậm có thể giữ hàng trăm request đang chờ, khiến connection pool, semaphore hoặc worker slots bị chiếm hết. Khi đó cả endpoint không liên quan cũng suy giảm dù dependency riêng của chúng vẫn khỏe.

**Ví dụ thực tế:**
```text
Checkout API
- Payment provider: tối đa 40 concurrent calls
- Recommendation provider: tối đa 10 concurrent calls
- Internal SQL work: capacity riêng
```

Nếu Recommendation provider treo, request liên quan có thể fail/degrade nhưng không chiếm toàn bộ capacity dành cho checkout chính.

**Trade-off:**
Bulkhead giảm cascading failure và làm capacity dễ kiểm soát hơn, nhưng đặt limit quá thấp sẽ tự tạo throttling; đặt quá nhiều pool riêng lại làm capacity bị phân mảnh và cấu hình khó vận hành.

**Middle → Senior insight:**
Middle developer cần hiểu timeout và concurrency limit phải được áp dụng có chủ đích. Senior / Technical developer phải xác định bulkhead boundary dựa trên dependency criticality, queueing behavior, latency SLO, traffic mix và khả năng degrade của từng feature.

### Design 2 — Modular Monolith cần boundary thật, không chỉ folder đẹp

**Khái niệm:**
Modular Monolith giữ deployment unit chung nhưng chia hệ thống thành module có ownership, dependency direction và data boundary rõ. Giá trị nằm ở runtime/code boundary chứ không phải cấu trúc thư mục tên `Modules`.

**Vấn đề nó giải quyết:**
Một monolith lớn thường trở nên khó thay đổi vì mọi feature đọc trực tiếp table, service và internal type của nhau. Chia module giúp giới hạn coupling mà chưa phải trả operational cost của Microservices.

**Ví dụ thực tế:**
```text
Modules:
- Projects
- Documents
- Notifications

Projects không truy cập trực tiếp DbSet nội bộ của Documents.
Nếu cần tích hợp:
- gọi application contract
- publish internal event
- dùng read model được công bố rõ
```

Có thể vẫn dùng một database vật lý nhưng ownership của schema/table phải minh bạch.

**Trade-off:**
Modular Monolith giữ deployment, transaction và debugging tương đối đơn giản, nhưng boundary chỉ tồn tại nếu team enforce dependency rules. Nếu module truy cập chéo tùy ý, nó sẽ nhanh chóng quay lại thành distributed spaghetti bên trong một process.

**Middle → Senior insight:**
Middle developer cần tuân thủ module contract và tránh bypass boundary để “làm nhanh”. Senior / Technical developer phải thiết kế cohesion, ownership, integration contract và quy tắc dependency sao cho module có thể tiến hóa độc lập mà không tạo ceremony không cần thiết.

### Design 3 — Queue vs Topic trong Azure Service Bus theo ownership của message

**Khái niệm:**
Queue thường biểu diễn work cần được một consumer group xử lý; Topic + Subscription phù hợp khi một event cần được nhiều consumer độc lập nhận và mỗi consumer có lifecycle riêng.

**Vấn đề nó giải quyết:**
Nếu nhiều hệ thống cùng đọc một queue với competing consumers, mỗi message chỉ được một consumer lấy, nên bạn không thể dùng nó để broadcast business event cho nhiều capability độc lập.

**Ví dụ thực tế:**
```text
Queue: GenerateInvoice
-> một worker bất kỳ xử lý command này

Topic: OrderCompleted
-> Billing subscription
-> Analytics subscription
-> Notification subscription
```

Mỗi subscription có retry, dead-letter và filtering riêng mà không tranh message với subscription khác.

**Trade-off:**
Queue đơn giản hơn cho work distribution và competing consumers. Topic tăng decoupling cho event fan-out nhưng thêm subscription management, duplicate delivery, observability và contract-evolution concerns.

**Middle → Senior insight:**
Middle developer cần phân biệt command “hãy làm việc này” với event “điều này đã xảy ra”. Senior / Technical developer phải chọn topology dựa trên ownership, fan-out, ordering, filtering, retry isolation và khả năng thêm consumer mới mà không làm thay đổi producer.
