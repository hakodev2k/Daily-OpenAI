# Daily Developer Tips & Design — 2026-09-18

## 🛠 Developer Tips & Tricks

### Tip 1 — `Span<T>` chỉ đáng dùng khi allocation thực sự nằm trên hot path

**Mẹo:**
Dùng `Span<T>`/`ReadOnlySpan<T>` khi profiling cho thấy việc slice/parse buffer đang tạo allocation đáng kể; đừng thay `string` và collection thông thường chỉ vì muốn code “performance-oriented”.

**Tại sao hữu ích:**
`Span<T>` cho phép thao tác trên vùng nhớ liên tục mà không cần tạo object/slice mới. Điều này hữu ích trong parser, serializer hoặc protocol handling chạy với tần suất cao, nhưng lợi ích phải được đặt cạnh complexity và giới hạn lifetime của ref struct.

**Ví dụ:**
```csharp
ReadOnlySpan<char> input = "ORD-2026-00142";
var prefix = input[..3];
var id = input[9..];
```
Nếu profiler cho thấy hàng triệu substring allocations trong parser, chuyển hot path sang span có thể giảm GC pressure rõ rệt.

**Lưu ý:**
Không thể giữ `Span<T>` tùy ý qua `await`, heap field hoặc nhiều abstraction boundary. Với business code ít chạy, readability thường quan trọng hơn vài allocation nhỏ.

### Tip 2 — SQL isolation level phải khớp anomaly cần ngăn chặn

**Mẹo:**
Khi gặp race condition dữ liệu, xác định anomaly cụ thể như dirty read, non-repeatable read, phantom hoặc lost-update trước khi tăng isolation level.

**Tại sao hữu ích:**
Isolation cao hơn có thể giảm một số concurrency anomaly nhưng đổi lại blocking, version-store pressure hoặc transaction retry. Chọn `SERIALIZABLE` theo phản xạ có thể chữa correctness bằng cách tạo throughput problem mới.

**Ví dụ:**
Một workflow kiểm tra “còn slot” rồi insert booking trong hai statement có thể race giữa hai transaction. Hãy xem invariant có thể được bảo vệ bằng unique/constraint, atomic statement hoặc locking thích hợp trước khi nâng isolation cho toàn transaction.

**Lưu ý:**
Behavior khác nhau giữa SQL Server và PostgreSQL, đặc biệt quanh MVCC/snapshot semantics. Đừng suy luận chỉ từ tên isolation level; kiểm chứng trên database engine thực tế.

### Tip 3 — Key Vault secret rotation cần kiểm tra lifecycle của client/config

**Mẹo:**
Nếu application đọc secret từ Azure Key Vault, xác định secret được resolve lúc startup, được cache bao lâu và khi rotation xảy ra process có nhận value mới hay không.

**Tại sao hữu ích:**
“Secret nằm trong Key Vault” không tự động đồng nghĩa rotation không cần restart hoặc refresh. Một secret được bind vào singleton/options lúc startup có thể tồn tại đến hết process lifetime dù vault đã có version mới.

**Ví dụ:**
Khi rotate credential của third-party API, ghi rõ flow: publish secret version mới → application refresh/restart theo cơ chế đã chọn → xác nhận outbound call dùng credential mới → revoke credential cũ sau compatibility window.

**Lưu ý:**
Nếu Azure service hỗ trợ Managed Identity/Entra authentication, ưu tiên loại bỏ long-lived secret thay vì xây rotation phức tạp. Không log secret value để “xác nhận” rotation.

### Tip 4 — OpenAPI diff trong CI giúp phát hiện breaking API change

**Mẹo:**
Với public/internal API có nhiều consumer, lưu hoặc generate OpenAPI contract trong CI và so sánh với baseline để flag breaking changes như xóa endpoint, đổi required field hoặc thu hẹp enum.

**Tại sao hữu ích:**
Code compile và unit test của provider không biết consumer bên ngoài đang phụ thuộc contract nào. Contract diff biến backward compatibility thành kiểm tra kỹ thuật thay vì chỉ dựa vào code review.

**Ví dụ:**
PR đổi `customerId` từ optional thành required có thể bị CI đánh dấu breaking. Team sau đó quyết định additive migration, version mới hoặc compatibility window thay vì phát hiện qua lỗi consumer sau deploy.

**Lưu ý:**
Không phải mọi schema diff đều thực sự breaking và semantic change có thể không xuất hiện trong schema. Automated diff cần policy/review, không thay thế consumer contract tests.

### Tip 5 — React/Vue: tránh memoization khi chưa có render bottleneck

**Mẹo:**
Dùng profiler để xác định expensive render/computation trước khi thêm `useMemo`, `useCallback`, custom memoization hoặc cache computed phức tạp.

**Tại sao hữu ích:**
Memoization có chi phí dependency tracking, memory và cognitive load. Nhiều component render rẻ hơn việc duy trì cache; tối ưu sai chỗ còn tạo stale dependency bug hoặc code khó đọc.

**Ví dụ:**
Nếu React Profiler cho thấy một bảng 5.000 rows rerender vì parent state thay đổi, hãy xử lý data shape/component boundary trước; memoization chỉ nên áp dụng nơi measurement cho thấy nó giảm work đáng kể.

**Lưu ý:**
Đừng nhầm network latency với render latency. Nếu UI chờ API 800 ms nhưng render 8 ms, memoization component không giải quyết trải nghiệm chính.

## 🧠 Software Design

### Design 1 — API Composition vs Materialized Read Model

**Khái niệm:**
API Composition lấy dữ liệu từ nhiều nguồn tại request time; Materialized Read Model chuẩn bị trước một view tối ưu cho query và cập nhật nó khi dữ liệu nguồn thay đổi.

**Vấn đề nó giải quyết:**
Một dashboard cần Order, Customer và Payment data từ nhiều bounded contexts. Gọi ba services cho mỗi request đơn giản lúc đầu nhưng latency/availability bị phụ thuộc vào toàn bộ fan-out chain.

**Ví dụ thực tế:**
Operations dashboard ít yêu cầu consistency tức thời có thể duy trì read model từ domain events. Trang quản trị hiếm dùng và cần dữ liệu mới nhất có thể composition trực tiếp nếu dependency count/latency còn chấp nhận được.

**Trade-off:**
Composition giảm duplication và đơn giản hóa write-side nhưng tăng runtime coupling. Materialized view cho read latency ổn định và giảm fan-out nhưng thêm eventual consistency, synchronization, replay/rebuild và storage.

**Middle → Senior insight:**
Middle developer cần tránh N+1 service calls và xử lý partial failure. Senior / Technical developer phải chọn dựa trên freshness requirement, query volume, failure tolerance và cost vận hành thay vì mặc định tạo read database riêng.

### Design 2 — Database constraint là lớp bảo vệ invariant cuối cùng

**Khái niệm:**
Business validation trong application cải thiện UX và express intent, nhưng invariant có thể biểu diễn chắc chắn bằng database constraint nên được cân nhắc bảo vệ tại persistence boundary.

**Vấn đề nó giải quyết:**
Nhiều application instances hoặc concurrent requests có thể cùng vượt qua check-before-write. Validation chỉ ở service layer không loại bỏ race condition giữa check và commit.

**Ví dụ thực tế:**
Hai request đồng thời tạo cùng external order reference. Cả hai đều thấy “chưa tồn tại”; unique constraint trên `(TenantId, ExternalOrderId)` bảo đảm chỉ một transaction commit, application map violation còn lại thành conflict phù hợp.

**Trade-off:**
Constraint cho correctness mạnh và gần dữ liệu nhưng error handling cần map database-specific failure và một số invariant phức tạp không thể biểu diễn dễ dàng. Đẩy toàn bộ business logic xuống database lại làm domain khó hiểu/test/evolve.

**Middle → Senior insight:**
Middle developer cần dùng PK/FK/unique/check constraints đúng và xử lý violation. Senior / Technical developer phải quyết định invariant nào cần defense-in-depth tại database, đặc biệt dưới concurrency, thay vì tin vào pre-check trong code.

### Design 3 — Ownership boundary quan trọng hơn số lượng microservices

**Khái niệm:**
Service boundary có giá trị khi nó tạo ownership rõ cho capability, data và lifecycle thay đổi. Chia process mà vẫn dùng chung schema, deploy đồng bộ và sửa chéo repository thường chỉ tạo distributed monolith.

**Vấn đề nó giải quyết:**
Team tách application thành nhiều services để “scale architecture”, nhưng mỗi feature vẫn cần coordinated change ở nhiều services và transaction xuyên shared database.

**Ví dụ thực tế:**
Catalog service sở hữu schema và contract của Catalog; Ordering chỉ dùng API/event được công bố. Nếu cả hai cùng update trực tiếp bảng `Products`, process separation không tạo isolation thực sự.

**Trade-off:**
Ownership rõ giảm coupling và cho phép evolution độc lập nhưng có thể tạo duplication, eventual consistency và governance overhead. Một Modular Monolith với module/data boundaries rõ đôi khi cung cấp phần lớn lợi ích với vận hành đơn giản hơn.

**Middle → Senior insight:**
Middle developer cần tôn trọng public boundary và tránh shortcut qua database/internal implementation. Senior / Technical developer phải đánh giá autonomy, team topology, change coupling và operational maturity trước khi biến module boundary thành network boundary.
