# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `EndpointFilter` cho cross-cutting logic cục bộ ở Minimal API

**Mẹo:**
Với ASP.NET Core Minimal API, khi validation, logging hoặc policy chỉ áp dụng cho một nhóm endpoint nhỏ, cân nhắc `IEndpointFilter` thay vì đẩy mọi thứ vào middleware global.

**Tại sao hữu ích:**
Giữ scope của behavior sát endpoint cần dùng, tránh middleware toàn cục phải chứa nhiều điều kiện theo route và giúp flow request dễ đọc hơn.

**Ví dụ:**
```csharp
public sealed class ValidateIdFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var id = context.GetArgument<int>(0);

        if (id <= 0)
        {
            return Results.BadRequest("id must be greater than 0");
        }

        return await next(context);
    }
}

app.MapGet("/orders/{id:int}", GetOrder)
   .AddEndpointFilter<ValidateIdFilter>();
```

**Lưu ý:**
Đừng biến filter thành nơi chứa business logic hoặc database access phức tạp. Middleware phù hợp hơn cho concern toàn application; domain/application layer vẫn nên giữ business rule thật sự.

### Tip 2 — Dùng SQL Server `SET DEADLOCK_PRIORITY` khi workload phụ nên nhường transaction quan trọng

**Mẹo:**
Với background task hoặc maintenance job ít quan trọng hơn transaction interactive, có thể đặt `DEADLOCK_PRIORITY LOW` để SQL Server ưu tiên chọn workload đó làm deadlock victim khi có chu kỳ lock.

**Tại sao hữu ích:**
Giảm khả năng batch/report phụ làm chết transaction quan trọng của user khi hai workload vô tình deadlock với nhau.

**Ví dụ:**
```sql
SET DEADLOCK_PRIORITY LOW;

BEGIN TRANSACTION;

UPDATE ArchivedOrders
SET Processed = 1
WHERE Id = @Id;

COMMIT;
```

**Lưu ý:**
Đây không phải cách sửa deadlock gốc. Vẫn cần phân tích deadlock graph, lock ordering, index và transaction scope; priority chỉ quyết định ai bị chọn làm victim khi deadlock đã xảy ra.

### Tip 3 — Dùng `git grep` để tìm code nhanh trong repository mà không phụ thuộc IDE

**Mẹo:**
Khi cần tìm symbol, config key hoặc error message ngay trong terminal, dùng `git grep` để search các file được Git quản lý.

**Tại sao hữu ích:**
Nhanh, scriptable và ít noise hơn search toàn filesystem vì mặc định bỏ qua file không tracked như build output hoặc dependency folder.

**Ví dụ:**
```bash
git grep -n "EmployeeProfileChanged"
```

Tìm không phân biệt hoa thường:

```bash
git grep -ni "timeout"
```

Giới hạn theo loại file:

```bash
git grep -n "CancellationToken" -- '*.cs'
```

**Lưu ý:**
`git grep` không tìm trong untracked file trừ khi dùng cách khác. Với generated file hoặc artifact ngoài repository, cần công cụ search filesystem như `rg`.

### Tip 4 — Dùng HTTP Range Request cho download lớn có khả năng resume

**Mẹo:**
Nếu API phục vụ file lớn, hỗ trợ `Range`/`Content-Range` để client tải một phần file và tiếp tục download sau khi bị gián đoạn thay vì bắt đầu lại từ byte đầu tiên.

**Tại sao hữu ích:**
Giảm bandwidth lãng phí và cải thiện trải nghiệm khi tải report, backup hoặc media lớn qua mạng không ổn định.

**Ví dụ:**
Client có thể gửi:

```http
GET /files/report.zip
Range: bytes=1048576-
```

Server trả:

```http
HTTP/1.1 206 Partial Content
Content-Range: bytes 1048576-5242879/5242880
```

**Lưu ý:**
Range support cần xử lý đúng validation, `ETag`/`If-Range`, giới hạn số range và authorization. Không nên tự implement parser Range sơ sài nếu framework/storage layer đã hỗ trợ.

### Tip 5 — Dùng mutation testing để phát hiện test chỉ “chạy qua” chứ không bảo vệ behavior

**Mẹo:**
Ngoài code coverage, dùng mutation testing như Stryker.NET để cố tình đổi toán tử, điều kiện hoặc constant rồi xem test có fail hay không.

**Tại sao hữu ích:**
Coverage 90% vẫn có thể vô nghĩa nếu assertion yếu. Mutation testing kiểm tra chất lượng của test bằng cách xác minh test có bắt được thay đổi behavior thực sự.

**Ví dụ:**
```bash
dotnet tool install -g dotnet-stryker

dotnet stryker
```

Nếu code:

```csharp
return amount > 0;
```

bị mutate thành:

```csharp
return amount >= 0;
```

mà test vẫn pass, test suite chưa bảo vệ boundary case `0`.

**Lưu ý:**
Mutation testing khá tốn thời gian. Nên chạy trên domain/core module hoặc PR quan trọng thay vì mặc định toàn solution ở mọi commit.

## 🧠 Software Design

### Design 1 — Published Language giúp các bounded context giao tiếp bằng contract ổn định

**Khái niệm:**
Published Language là một ngôn ngữ/contract chung được công bố rõ giữa các bounded context, thường thể hiện qua API schema, event schema hoặc canonical integration model.

**Vấn đề nó giải quyết:**
Nếu service A gửi trực tiếp entity nội bộ của mình sang service B, model nội bộ và integration contract bị trộn lẫn, khiến refactor domain trở thành breaking change ngoài ý muốn.

**Ví dụ thực tế:**
`Employee` có domain model phức tạp với nhiều field nội bộ, nhưng contract công bố sang `Payroll` chỉ gồm:

```text
EmployeeEmploymentChanged
- EmployeeId
- EmploymentStatus
- EffectiveDate
- Version
```

Consumer phụ thuộc vào contract này thay vì toàn bộ entity `Employee`.

**Trade-off:**
Published Language giảm coupling và giúp versioning rõ hơn, nhưng cần governance, schema ownership và mapping. Nếu thiết kế một canonical model khổng lồ cho toàn công ty, nó lại trở thành shared model khó tiến hóa.

**Middle → Senior insight:**
Middle developer nên hiểu public contract khác internal model. Senior developer phải quyết định contract tối thiểu, compatibility rule, ownership và khi nào nên translation riêng cho từng integration thay vì cố ép mọi context dùng chung một model.

### Design 2 — Batch và Streaming nên chọn theo latency requirement và cost model

**Khái niệm:**
Batch gom dữ liệu rồi xử lý theo đợt; Streaming xử lý dữ liệu liên tục khi event đến. Đây là lựa chọn về latency, throughput và operational complexity chứ không phải “streaming luôn hiện đại hơn”.

**Vấn đề nó giải quyết:**
Một số workload cần phản ứng trong vài giây, trong khi workload khác chỉ cần số liệu đúng vào cuối ngày. Dùng streaming cho mọi thứ có thể tăng complexity không cần thiết.

**Ví dụ thực tế:**
Fraud detection cho payment có thể cần stream gần real-time. Nhưng tổng hợp payroll report cuối tháng có thể chạy batch lúc ban đêm với SQL/data warehouse đơn giản hơn và rẻ hơn.

**Trade-off:**
Streaming giảm latency và cho xử lý liên tục nhưng tăng yêu cầu về ordering, replay, checkpoint, backpressure và observability. Batch đơn giản, dễ retry và tối ưu throughput nhưng dữ liệu luôn có độ trễ theo batch window.

**Middle → Senior insight:**
Middle developer nên chọn theo SLA thay vì theo trend. Senior developer cần đánh giá event volume, lateness, replay requirement, cost vận hành và business value của latency trước khi đưa streaming infrastructure vào hệ thống.

### Design 3 — ADR giúp lưu lại “vì sao” của quyết định kiến trúc

**Khái niệm:**
Architecture Decision Record (ADR) ghi ngắn gọn context, quyết định, alternatives và consequence của một quyết định kiến trúc tại thời điểm nó được đưa ra.

**Vấn đề nó giải quyết:**
Sau vài tháng, team thường chỉ thấy implementation hiện tại nhưng không còn biết vì sao đã chọn PostgreSQL, shared database, queue riêng hay eventual consistency. Khi đó quyết định cũ dễ bị đảo ngược mà không hiểu constraint ban đầu.

**Ví dụ thực tế:**
Một ADR có thể ghi:

```text
Decision: dùng Modular Monolith thay vì Microservices trong phase 1.
Context: team 4 người, bounded context còn thay đổi mạnh.
Consequence: deploy chung nhưng module ownership và DB schema boundary phải rõ.
Revisit when: release cadence hoặc scaling requirement giữa module bắt đầu khác biệt đáng kể.
```

**Trade-off:**
ADR tạo decision memory và hỗ trợ onboarding/review, nhưng nếu mọi thay đổi nhỏ đều viết ADR thì dễ thành bureaucracy. ADR cũng cần được đánh dấu superseded khi quyết định thay đổi.

**Middle → Senior insight:**
Middle developer nên đọc ADR để hiểu constraint trước khi refactor lớn. Senior developer cần ghi lại những quyết định khó đảo ngược hoặc có trade-off dài hạn, đồng thời nêu rõ trigger để revisit thay vì biến ADR thành tài liệu bất biến.
