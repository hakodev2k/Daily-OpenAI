# Daily Developer Tips & Design — 2026-09-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Span<T>` khi profiling chứng minh allocation là bottleneck

**Mẹo:**
Với hot path xử lý buffer hoặc parsing dữ liệu, cân nhắc `Span<T>`/`ReadOnlySpan<T>` để thao tác trên vùng nhớ hiện có thay vì tạo substring hoặc array trung gian.

**Tại sao hữu ích:**
Các allocation nhỏ nhưng lặp với tần suất rất cao làm tăng allocation rate và áp lực Garbage Collector. `Span<T>` cho phép tạo view trên memory mà không cần copy dữ liệu, nhưng lợi ích chỉ đáng kể khi workload thực sự allocation-sensitive.

**Ví dụ:**
```csharp
ReadOnlySpan<char> value = "order:92841";
var separator = value.IndexOf(':');
var id = value[(separator + 1)..];
```
Trong parser chạy hàng triệu lần, cách này có thể tránh tạo nhiều string tạm. Xác nhận bằng profiler hoặc allocation metrics trước và sau thay đổi.

**Lưu ý:**
Đừng đưa `Span<T>` vào business code thông thường chỉ để “tối ưu”. Đây là `ref struct` với lifetime restrictions; complexity tăng có thể không đáng nếu allocation rate không phải bottleneck.

### Tip 2 — Phân biệt blocking với deadlock khi SQL request bị treo

**Mẹo:**
Khi API chờ database lâu, kiểm tra blocking chain, active transactions và lock wait trước khi kết luận database deadlock.

**Tại sao hữu ích:**
Blocking là transaction phải chờ lock được giải phóng; deadlock là vòng phụ thuộc mà database engine phải chọn một victim để phá vòng. Hai triệu chứng có thể giống nhau ở application nhưng cách chẩn đoán và khắc phục khác nhau.

**Ví dụ:**
Một back-office transaction mở, update `Orders` rồi giữ transaction trong lúc gọi external API. Request khác update cùng row sẽ bị block. Evidence cần tìm là session giữ lock, transaction duration và wait type; không phải lập tức thêm retry policy.

**Lưu ý:**
Retry có thể hữu ích cho deadlock victim nhưng không sửa transaction boundary xấu. Với blocking kéo dài, hãy giảm thời gian transaction và tránh network I/O khi đang giữ database locks nếu business semantics cho phép.

### Tip 3 — Elasticsearch mapping phải được thiết kế trước khi dữ liệu lớn

**Mẹo:**
Xác định field nào cần full-text search, exact filtering, sorting và aggregation trước khi index lượng dữ liệu lớn; đừng để dynamic mapping quyết định toàn bộ schema production.

**Tại sao hữu ích:**
`text` và `keyword` phục vụ access pattern khác nhau. Mapping sai có thể làm query không đúng semantics, tăng index size hoặc buộc phải reindex khi muốn đổi analyzer/type. Reindex hàng trăm triệu documents là operational work thực sự.

**Ví dụ:**
`ProductName` có thể cần `text` với analyzer cho search và subfield `keyword` cho exact operations khi phù hợp. `ProductId` thường cần exact semantics thay vì tokenization.

**Lưu ý:**
Không tạo multi-field cho mọi property theo thói quen. Mỗi mapping/indexed field có storage và indexing cost; thiết kế theo query pattern thực tế.

### Tip 4 — Azure Blob upload lớn: tránh proxy toàn bộ bytes qua API nếu không cần

**Mẹo:**
Với file upload lớn từ browser/mobile, cân nhắc cho client upload trực tiếp tới Azure Blob Storage bằng quyền giới hạn thời gian/phạm vi thay vì luôn truyền toàn bộ file qua ASP.NET Core API.

**Tại sao hữu ích:**
Backend proxying tiêu tốn connection, bandwidth và compute của application tier cho dữ liệu mà Blob Storage có thể nhận trực tiếp. Direct upload giảm tải backend và thường scale tốt hơn.

**Ví dụ:**
API xác thực user, tạo upload authorization chỉ cho blob/path cần thiết với thời hạn ngắn; client upload trực tiếp rồi backend xác nhận metadata/process file bằng workflow riêng.

**Lưu ý:**
Đừng cấp SAS rộng hoặc sống quá lâu. Direct upload không loại bỏ validation: vẫn cần kiểm soát size/type, ownership, malware workflow và trạng thái file chưa được xác nhận.

### Tip 5 — Tái hiện production bug bằng regression test nhỏ nhất có thể

**Mẹo:**
Sau khi xác định root cause, viết test ở layer thấp nhất vẫn tái hiện đúng failure semantics thay vì luôn tạo E2E test lớn.

**Tại sao hữu ích:**
Regression test tốt vừa chứng minh fix vừa chạy nhanh và deterministic. Nếu bug nằm ở EF Core translation/database constraint, integration test với database thực có thể chính xác hơn unit mock; nếu bug nằm ở pure domain rule, unit test thường đủ.

**Ví dụ:**
Bug do unique constraint và concurrent insert không nên được “test” bằng mock repository trả exception giả. Một database integration test thực hiện competing writes có thể bắt đúng behavior cần bảo vệ.

**Lưu ý:**
Không chọn test layer chỉ vì dễ viết. Test quá thấp có thể bỏ mất integration failure; test quá cao làm suite chậm/flaky. Chọn boundary nhỏ nhất vẫn chứa nguyên nhân thật.

## 🧠 Software Design

### Design 1 — Cache-aside và consistency boundary

**Khái niệm:**
Cache-aside để application đọc cache trước, fallback về source of truth rồi populate cache. Vấn đề khó không phải `Get/Set`, mà là xác định dữ liệu được phép stale bao lâu và invalidation xảy ra khi write như thế nào.

**Vấn đề nó giải quyết:**
Read-heavy API có latency/database load cao nhưng dữ liệu không nhất thiết cần đọc mới tuyệt đối ở mọi request.

**Ví dụ thực tế:**
Product detail có thể cache vài phút, trong khi inventory khả dụng cho checkout cần consistency chặt hơn. Hai field cùng xuất hiện trên UI không có nghĩa chúng phải dùng cùng cache policy.

**Trade-off:**
Cache-aside giảm latency và source load nhưng tạo stale-data window, cold misses và failure mode khi cache unavailable. Invalidation chặt hơn tăng complexity; TTL ngắn hơn tăng source load.

**Middle → Senior insight:**
Middle developer cần implement key, TTL, serialization và cache-miss path đúng. Senior / Technical developer phải xác định consistency requirement theo business operation, degradation behavior khi Redis lỗi và dữ liệu nào không nên cache dù technically có thể.

### Design 2 — API backward compatibility bằng additive evolution

**Khái niệm:**
API contract nên tiến hóa theo cách consumer cũ tiếp tục hoạt động khi có thể: thêm optional field/endpoint thường an toàn hơn đổi meaning, xóa field hoặc thay kiểu dữ liệu hiện có.

**Vấn đề nó giải quyết:**
Mobile app, CMS frontend hoặc external partner không thể luôn deploy đồng thời với backend. Breaking change biến release độc lập thành coordinated deployment.

**Ví dụ thực tế:**
Thay vì đổi `status` từ string sang object ngay trên endpoint hiện tại, có thể thêm representation mới hoặc version contract khi semantics thực sự thay đổi. Theo dõi consumer adoption trước khi retire contract cũ.

**Trade-off:**
Backward compatibility giảm release coupling nhưng làm backend phải duy trì legacy contract và migration period. Versioning quá sớm lại nhân API surface và test burden.

**Middle → Senior insight:**
Middle developer cần nhận biết breaking changes trong OpenAPI/DTO và viết compatibility tests. Senior / Technical developer phải cân nhắc consumer ownership, deprecation policy, telemetry usage và migration cost để chọn additive change hay version mới.

### Design 3 — Modular Monolith trước khi Microservices có pressure rõ ràng

**Khái niệm:**
Modular Monolith giữ deployment/process đơn giản nhưng tạo module boundaries rõ trong code và data ownership. Nó cho phép separation of concerns mà chưa trả toàn bộ chi phí distributed systems.

**Vấn đề nó giải quyết:**
Một codebase lớn cần giảm coupling giữa business capabilities, nhưng team chưa có nhu cầu scale/deploy/own từng capability độc lập đủ mạnh để biện minh Microservices.

**Ví dụ thực tế:**
E-commerce có Catalog, Ordering và Customer modules trong một deployable. Module giao tiếp qua explicit contracts/events nội bộ và tránh truy cập trực tiếp internals của nhau. Sau này một module có pressure độc lập mới là candidate để extract.

**Trade-off:**
Modular Monolith đơn giản hơn về deployment, transactions và observability nhưng boundary có thể bị phá vì mọi thứ vẫn cùng process/database. Microservices enforce isolation mạnh hơn nhưng thêm network failure, eventual consistency, deployment và operational overhead.

**Middle → Senior insight:**
Middle developer cần giữ dependency direction và module API sạch. Senior / Technical developer phải đánh giá organizational ownership, scaling profile, release cadence và failure isolation trước khi tách service; khả năng vẽ nhiều services không phải bằng chứng hệ thống cần Microservices.
