# Daily Developer Tips & Design — 2026-09-21

## 🛠 Developer Tips & Tricks

### Tip 1 — `DbContext` pooling không giống database connection pooling

**Mẹo:**
Phân biệt `AddDbContextPool` với connection pooling của database driver. `DbContext` pooling tái sử dụng instance/context infrastructure; connection pooling tái sử dụng physical database connections. Chỉ bật context pooling khi profiling cho thấy context setup đáng kể và code không giữ state theo request trong context.

**Tại sao hữu ích:**
Nhầm hai cơ chế dễ dẫn tới tối ưu sai bottleneck. API có connection exhaustion sẽ không được chữa chỉ bằng `DbContext` pooling; ngược lại, pooled context có thể làm state từ request trước rò sang request sau nếu custom mutable state không được reset đúng.

**Ví dụ:**
Một multi-tenant API đặt `TenantId` mutable trực tiếp trên custom `DbContext`. Sau khi bật pooling, context được tái sử dụng và tenant state trở thành rủi ro. Team chuyển tenant-dependent state ra khỏi pooled context và đo riêng connection-pool metrics trước khi quyết định tối ưu tiếp.

**Lưu ý:**
Không giữ connection mở lâu chỉ vì driver có pool. `DbContext` vẫn nên có lifetime rõ ràng; pooling là performance optimization, không thay đổi transaction/lifetime semantics mà application phải quản lý.

### Tip 2 — `ProblemDetails` nên là contract lỗi ổn định, không phải wrapper của exception

**Mẹo:**
Chuẩn hóa lỗi HTTP bằng `ProblemDetails` với `type`, `status`, `title` và các extension fields ổn định như business error code hoặc trace identifier; map exception nội bộ sang contract thay vì serialize exception message/stack trace ra client.

**Tại sao hữu ích:**
Client cần xử lý lỗi theo semantics ổn định, trong khi exception type/message có thể đổi theo implementation và có thể lộ dữ liệu nhạy cảm. Một error contract tốt cũng giúp frontend, mobile và observability liên kết cùng một failure mà không coupling vào internals.

**Ví dụ:**
`OrderAlreadyPaidException` được map thành `409 Conflict` với code `order_already_paid` và `traceId`. Frontend dựa vào code để hiển thị hành vi phù hợp; stack trace chỉ nằm trong structured logs/traces phía server.

**Lưu ý:**
Đừng biến mọi exception thành `400`. Phân biệt validation, authentication, authorization, conflict, unavailable và unexpected server failure. Error code public đã phát hành cũng là API contract cần quản lý compatibility.

### Tip 3 — Redis hot key có thể làm cluster nghẽn dù tổng dung lượng còn rất nhiều

**Mẹo:**
Khi Redis latency tăng, kiểm tra request distribution theo key/slot thay vì chỉ nhìn tổng CPU và memory. Một key cực nóng có thể dồn phần lớn traffic vào một shard/node dù cluster còn capacity ở nơi khác.

**Tại sao hữu ích:**
Partitioning phân phối keys, không tự động chia tải của một key đơn lẻ. Cache cho một global object, counter hoặc popular query có thể trở thành serialization point và tạo network/CPU pressure cục bộ.

**Ví dụ:**
Trang chủ của e-commerce đọc cùng key `homepage:v1` hàng chục nghìn lần/giây. Một Redis node đạt latency cao trong khi nodes khác nhàn. Team cân nhắc local in-process cache ngắn hạn, request coalescing hoặc redesign dữ liệu thay vì chỉ tăng số shards.

**Lưu ý:**
Key replication/sharding thủ công làm invalidation và consistency khó hơn. Trước khi redesign, xác minh hot-key hypothesis bằng telemetry và phân biệt nó với slow commands, large values hoặc network bottleneck.

### Tip 4 — Structured logging phải giữ template, không build message bằng string interpolation

**Mẹo:**
Với logging framework hỗ trợ structured logs, dùng message template và named properties thay vì tạo chuỗi hoàn chỉnh trước khi logger nhận được dữ liệu.

**Tại sao hữu ích:**
Structured properties cho phép query/aggregate theo `OrderId`, `TenantId`, dependency hoặc operation mà không phải parse text. Logger cũng có thể tránh một phần formatting khi log level bị disable.

**Ví dụ:**
Dùng `logger.LogWarning("Payment timeout for {OrderId} after {ElapsedMs} ms", orderId, elapsedMs)` để Application Insights/Kibana nhận các fields riêng, thay vì `$"Payment timeout for {orderId} after {elapsedMs} ms"` chỉ còn một message string.

**Lưu ý:**
Không log password, token, cookie, connection string hoặc PII chỉ vì structured logging làm dữ liệu dễ query hơn. Cardinality và retention vẫn cần được kiểm soát; logging mọi object nguyên vẹn có thể vừa đắt vừa nguy hiểm.

### Tip 5 — Contract test nên bảo vệ consumer expectation, không clone toàn bộ integration test

**Mẹo:**
Dùng contract tests cho những assumptions giữa service/client boundaries như required fields, status semantics, schema và compatibility; giữ end-to-end tests cho workflow xuyên hệ thống thay vì kiểm tra mọi business path ở cả hai tầng.

**Tại sao hữu ích:**
Một provider có thể deploy độc lập và vô tình rename/remove field mà unit tests hai phía đều vẫn xanh. Contract test tạo feedback sớm cho compatibility mà không cần dựng toàn bộ distributed environment cho mỗi thay đổi.

**Ví dụ:**
Mobile BFF phụ thuộc `Catalog API` trả `productId`, `price.amount` và `currency`. Contract suite xác minh provider version mới vẫn đáp ứng expectation này; checkout E2E vẫn kiểm tra workflow thực thay vì contract suite giả lập toàn bộ checkout.

**Lưu ý:**
Contract test không chứng minh network, auth, deployment configuration hay dữ liệu production hoạt động end-to-end. Tránh snapshot khổng lồ khiến mọi additive field cũng làm test fail; contract nên tập trung vào behavior consumer thực sự phụ thuộc.

## 🧠 Software Design

### Design 1 — Saga orchestration vs choreography: chọn theo workflow visibility và coupling

**Khái niệm:**
Saga chia một business transaction dài thành nhiều local transactions kèm compensating actions. Orchestration dùng một coordinator quyết định bước tiếp theo; choreography để services phản ứng với events mà không có coordinator trung tâm.

**Vấn đề nó giải quyết:**
Một workflow như order → payment → inventory → shipping không thể dựa vào ACID transaction xuyên nhiều autonomous services. Khi một bước thất bại sau các bước trước đã commit, hệ thống cần state transition và compensation rõ ràng.

**Ví dụ thực tế:**
Checkout phức tạp có orchestrator lưu saga state, yêu cầu reserve inventory rồi authorize payment và phát lệnh compensation nếu bước sau thất bại. Một workflow analytics đơn giản chỉ fan-out events có thể dùng choreography mà không cần coordinator.

**Trade-off:**
Orchestration tập trung visibility, timeout và recovery nhưng coordinator có thể trở thành nơi chứa quá nhiều domain coupling. Choreography giảm central control nhưng workflow dễ trở nên khó nhìn, khó debug và tạo event chains ngầm giữa nhiều teams.

**Middle → Senior insight:**
Middle developer cần implement idempotent handlers, retries và compensation an toàn. Senior / Technical developer phải quyết định ownership của workflow, failure semantics, observability, coupling và cách evolution; không chọn choreography chỉ để tránh một coordinator trên diagram.

### Design 2 — Normalization vs denormalization: tối ưu theo invariant và read pressure

**Khái niệm:**
Normalization giảm duplication và giữ facts ở một nguồn nhất quán; denormalization chủ động sao chép/reshape dữ liệu để phục vụ read path hiệu quả hơn. Đây là trade-off giữa write consistency và read efficiency, không phải hai trường phái loại trừ nhau.

**Vấn đề nó giải quyết:**
Một normalized OLTP schema có thể yêu cầu nhiều joins/aggregations cho dashboard hoặc search; nhưng denormalize quá sớm khiến mỗi update phải đồng bộ nhiều copies và tăng nguy cơ stale data.

**Ví dụ thực tế:**
Order tables giữ normalized transactional state, trong khi reporting projection lưu `OrderSummary` đã tổng hợp cho dashboard. Projection có thể rebuild/reconcile từ source of truth thay vì biến mọi transactional table thành wide duplicated schema.

**Trade-off:**
Normalization giúp constraints và update semantics rõ nhưng có thể tăng query complexity. Denormalization giảm read cost nhưng thêm synchronization, storage và consistency model; nếu read volume nhỏ, duplication có thể không đáng giá.

**Middle → Senior insight:**
Middle developer cần hiểu keys, constraints, joins và source of truth. Senior / Technical developer phải định lượng read/write ratio, latency target, rebuild strategy và stale-data tolerance trước khi denormalize, thay vì dùng nó như shortcut cho query chưa được tối ưu.

### Design 3 — Security boundary phải theo trust boundary, không theo số layer trong solution

**Khái niệm:**
Security design xác định nơi dữ liệu hoặc caller chuyển từ vùng ít tin cậy sang vùng có quyền cao hơn, rồi enforce authentication, authorization, validation và least privilege tại boundary đó. Folder/layer architecture tự nó không tạo security boundary.

**Vấn đề nó giải quyết:**
Hệ thống có thể kiểm tra authorization ở UI/BFF nhưng backend domain API vẫn chấp nhận caller quá rộng; hoặc internal service được coi là “trusted” dù credential bị compromise có thể truy cập mọi tenant.

**Ví dụ thực tế:**
Multi-tenant API xác thực service/user identity ở ingress nhưng vẫn enforce tenant authorization tại application boundary trước data access. Managed Identity của background worker chỉ có quyền tới resources nó cần, không dùng chung identity toàn hệ thống.

**Trade-off:**
Enforcement ở nhiều meaningful boundaries tăng defense-in-depth nhưng cũng thêm policy management và test complexity. Lặp kiểm tra vô nghĩa ở mọi method gây ceremony; thiếu kiểm tra tại authoritative boundary lại tạo privilege-escalation risk.

**Middle → Senior insight:**
Middle developer cần phân biệt authentication với authorization và không tin input chỉ vì đến từ service nội bộ. Senior / Technical developer phải map trust boundaries, identities, data ownership và blast radius, rồi đặt controls ở nơi có thể enforce invariant bảo mật một cách nhất quán.
