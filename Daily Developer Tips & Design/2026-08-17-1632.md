# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `Activity` và trace context thay vì tự chế correlation ID xuyên service

**Mẹo:**
Khi cần correlate request xuyên nhiều service/background job, ưu tiên `System.Diagnostics.Activity` và chuẩn W3C trace context thay vì tự truyền một header custom rồi log thủ công ở mọi nơi.

**Tại sao hữu ích:**
`Activity` tích hợp tự nhiên với OpenTelemetry, `HttpClient`, ASP.NET Core và nhiều thư viện observability. Bạn có thể nối logs, traces và dependency calls bằng cùng trace/span context.

**Ví dụ:**
```csharp
using var activity = MyActivitySource.StartActivity("ProcessOrder");
activity?.SetTag("order.id", orderId);

_logger.LogInformation("Processing order {OrderId}", orderId);
```

Nếu outbound HTTP client đã được instrument, trace context sẽ được propagate tự động qua header chuẩn như `traceparent`.

**Lưu ý:**
Không đưa dữ liệu cardinality cực cao hoặc PII tùy tiện vào tags. Trace data có thể rất lớn; cần sampling và retention policy hợp lý.

### Tip 2 — Dùng `AsSplitQuery()` khi `Include` tạo Cartesian explosion

**Mẹo:**
Với EF Core, nếu một query `Include` nhiều collection làm số row join tăng theo cấp số nhân, cân nhắc `AsSplitQuery()` để tách thành nhiều SQL query nhỏ hơn.

**Tại sao hữu ích:**
Giảm dữ liệu lặp lại truyền từ database về application và tránh trường hợp một object graph nhỏ bị nhân thành hàng chục nghìn rows do nhiều collection join cùng lúc.

**Ví dụ:**
```csharp
var orders = await dbContext.Orders
    .Include(x => x.Items)
    .Include(x => x.Payments)
    .AsSplitQuery()
    .Where(x => x.CustomerId == customerId)
    .ToListAsync(cancellationToken);
```

**Lưu ý:**
Split query tăng số round trip và có thể quan sát dữ liệu ở các thời điểm hơi khác nhau nếu concurrent updates xảy ra giữa các query. Hãy đo cả network latency lẫn result size trước khi chọn.

### Tip 3 — Dùng `git range-diff` sau rebase để kiểm tra mình có làm mất thay đổi không

**Mẹo:**
Sau một rebase phức tạp, dùng `git range-diff` để so sánh chuỗi commit trước và sau rebase thay vì chỉ nhìn final diff.

**Tại sao hữu ích:**
Bạn có thể phát hiện commit bị rơi, patch bị thay đổi ngoài ý muốn hoặc conflict resolution làm mất một phần logic.

**Ví dụ:**
Giả sử branch cũ bắt đầu từ `old-base` và branch mới từ `new-base`:

```bash
git range-diff old-base..old-tip new-base..HEAD
```

Hoặc sau khi Git giữ lại ref trước rebase:

```bash
git range-diff main...ORIG_HEAD main...HEAD
```

**Lưu ý:**
`range-diff` so sánh patch series chứ không phải runtime behavior. Sau rebase vẫn cần chạy test và review final code.

### Tip 4 — Dùng `Any()` khi chỉ cần biết có phần tử, đừng `Count() > 0`

**Mẹo:**
Trong LINQ, khi logic chỉ cần kiểm tra tồn tại, dùng `Any()` thay vì `Count() > 0`.

**Tại sao hữu ích:**
`Any()` có thể dừng ngay khi thấy phần tử đầu tiên. Với `IQueryable`, provider thường dịch thành dạng `EXISTS`, tránh đếm toàn bộ tập dữ liệu.

**Ví dụ:**
```csharp
bool hasPending = await dbContext.Jobs
    .AnyAsync(x => x.Status == JobStatus.Pending, cancellationToken);
```

Thay vì:

```csharp
bool hasPending = await dbContext.Jobs
    .CountAsync(x => x.Status == JobStatus.Pending, cancellationToken) > 0;
```

**Lưu ý:**
Nếu collection là `ICollection<T>` trong memory, `Count` có thể là O(1). Nhưng intent vẫn nên rõ: dùng `Any()` cho existence check, `Count` khi thực sự cần số lượng.

### Tip 5 — Pin dependency version trong CI để tránh build “hôm qua chạy, hôm nay hỏng”

**Mẹo:**
Các tool quan trọng trong CI như SDK, Node.js, package manager, Docker action hoặc CLI nên được pin về version xác định thay vì dùng alias mơ hồ như `latest`.

**Tại sao hữu ích:**
Build trở nên reproducible hơn và giảm failure bất ngờ do toolchain tự đổi version ngoài control của repository.

**Ví dụ:**
Trong GitHub Actions:

```yaml
- uses: actions/setup-dotnet@v4
  with:
    dotnet-version: '10.0.x'

- uses: actions/setup-node@v4
  with:
    node-version: '24.5.0'
```

Với .NET có thể thêm `global.json` để cố định SDK family/version policy.

**Lưu ý:**
Pin quá cứng mà không có quy trình update sẽ khiến dependency/toolchain cũ lâu ngày. Nên kết hợp automated dependency update và CI validation định kỳ.

## 🧠 Software Design

### Design 1 — Transactional Outbox để nối database transaction với message publishing

**Khái niệm:**
Transactional Outbox ghi business change và một outbox record trong cùng database transaction. Một worker khác đọc outbox rồi publish message ra broker.

**Vấn đề nó giải quyết:**
Nếu application `COMMIT` database rồi mới publish event, process có thể crash giữa hai bước: dữ liệu đã lưu nhưng message chưa bao giờ được gửi. Làm ngược lại cũng có thể publish message rồi rollback database.

**Ví dụ thực tế:**
Khi tạo Order:

1. Insert `Orders`.
2. Insert `OutboxMessages` với event `OrderCreated`.
3. Commit cùng transaction.
4. Background publisher đọc outbox, gửi RabbitMQ rồi đánh dấu `ProcessedAt`.

**Trade-off:**
Lợi ích là tránh dual-write inconsistency mà không cần distributed transaction. Chi phí là thêm bảng outbox, publisher, cleanup, retry và yêu cầu consumer idempotent vì message có thể được publish hơn một lần.

**Middle → Senior insight:**
Middle developer cần hiểu Outbox giải quyết atomic persistence, không đảm bảo exactly-once delivery. Senior developer phải thiết kế polling/CDC strategy, ordering, deduplication, retry, retention và observability của backlog.

### Design 2 — Composition over Inheritance khi behavior thay đổi theo nhiều trục

**Khái niệm:**
Composition xây behavior bằng cách kết hợp các collaborator nhỏ thay vì tạo cây inheritance sâu để biểu diễn mọi biến thể.

**Vấn đề nó giải quyết:**
Inheritance dễ vỡ khi một class phải thay đổi theo nhiều dimension độc lập. Số subclass có thể bùng nổ và behavior bị khóa chặt vào hierarchy.

**Ví dụ thực tế:**
Thay vì tạo:

```text
EmailNotification
SmsNotification
RetryingEmailNotification
RetryingSmsNotification
AuditedRetryingEmailNotification
...
```

có thể compose:

```text
INotificationSender
IRetryPolicy
IAuditSink
```

`NotificationService` kết hợp các strategy cần thiết theo runtime/configuration.

**Trade-off:**
Composition giảm coupling với hierarchy và linh hoạt hơn, nhưng tăng số object/interface và wiring. Với behavior rất ổn định và quan hệ “is-a” thực sự mạnh, inheritance đơn giản vẫn có thể phù hợp.

**Middle → Senior insight:**
Middle developer nên nhận ra dấu hiệu inheritance hierarchy đang encode nhiều responsibility. Senior developer cần chọn composition khi variation axis thực sự độc lập, đồng thời tránh tạo quá nhiều strategy/interface chỉ để “pattern hóa” code đơn giản.

### Design 3 — Test Pyramid không phải tỷ lệ cố định mà là chiến lược feedback

**Khái niệm:**
Test Pyramid ưu tiên nhiều test nhanh, cô lập ở tầng thấp; ít integration test hơn; và chỉ một số end-to-end test cho critical flows. Ý chính là tối ưu feedback speed và confidence, không phải tuân thủ một tỷ lệ cứng.

**Vấn đề nó giải quyết:**
Nếu toàn bộ regression suite phụ thuộc browser, database, network và external services, test sẽ chậm, flaky và khó xác định root cause. Nhưng chỉ unit test lại bỏ sót wiring, serialization, transaction và infrastructure behavior.

**Ví dụ thực tế:**
Một API thanh toán có thể dùng:

- Unit test cho fee/rule calculation.
- Integration test cho repository, transaction, HTTP pipeline và broker contract.
- Một vài end-to-end test cho `Create order → Pay → Confirm`.

**Trade-off:**
Nhiều unit test cho feedback nhanh nhưng có thể mock quá xa reality. Integration/E2E cho confidence cao hơn ở boundary nhưng tốn thời gian, môi trường và công bảo trì.

**Middle → Senior insight:**
Middle developer nên chọn loại test theo failure cần bắt. Senior developer cần thiết kế test portfolio dựa trên risk, change frequency, blast radius và thời gian feedback của CI, thay vì tranh luận số lượng test ở từng tầng theo công thức cố định.
