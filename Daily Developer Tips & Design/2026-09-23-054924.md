# Daily Developer Tips & Design — 2026-09-23

## 🛠 Developer Tips & Tricks

### Tip 1 — Phân biệt timeout với cancellation khi gọi dependency

**Mẹo:**
Khi ASP.NET Core gọi database hoặc external API, truyền `CancellationToken` của request xuyên suốt, nhưng đặt timeout riêng cho dependency. Client disconnect và dependency quá chậm là hai nguyên nhân khác nhau và nên được quan sát khác nhau.

**Tại sao hữu ích:**
Nếu chỉ dùng một timeout chung, production telemetry khó phân biệt user đã bỏ request với downstream vượt latency budget. Cancellation propagation còn giúp giải phóng work không còn giá trị thay vì tiếp tục giữ connection và tài nguyên.

**Ví dụ:**
```csharp
using var timeout = new CancellationTokenSource(TimeSpan.FromSeconds(2));
using var linked = CancellationTokenSource.CreateLinkedTokenSource(
    httpContext.RequestAborted, timeout.Token);

await httpClient.GetAsync(uri, linked.Token);
```
Log/metric nên ghi nhận nguyên nhân cancellation thay vì gom mọi `OperationCanceledException` thành server error.

**Lưu ý:**
Không retry vô điều kiện sau timeout. Operation phía dependency có thể đã thành công dù response chưa về; write request cần idempotency hoặc cơ chế xác minh trạng thái trước khi retry.

### Tip 2 — Keyset pagination ổn định hơn `OFFSET` ở bảng lớn

**Mẹo:**
Với feed hoặc danh sách lớn được đọc tuần tự, cân nhắc keyset pagination dựa trên sort key ổn định thay vì `OFFSET ... FETCH` qua hàng trăm nghìn rows.

**Tại sao hữu ích:**
Offset lớn buộc database tìm/bỏ qua nhiều rows trước khi trả page. Keyset dùng điều kiện trên giá trị cuối của page trước để tiếp tục từ vị trí có thể seek qua index, đồng thời ít bị dịch page khi dữ liệu mới được insert.

**Ví dụ:**
```sql
SELECT TOP (50) Id, CreatedAt, Total
FROM Orders
WHERE (CreatedAt < @lastCreatedAt)
   OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```
Index phù hợp với `(CreatedAt DESC, Id DESC)` giúp truy vấn tiếp tục từ cursor thay vì skip N rows.

**Lưu ý:**
Keyset không phù hợp nếu UI bắt buộc nhảy trực tiếp tới page 537. Sort key phải deterministic; chỉ dùng `CreatedAt` khi có duplicate có thể làm mất/lặp row, vì vậy thường cần tie-breaker như `Id`.

### Tip 3 — Dùng trace để tìm dependency gây p95/p99 thay vì nhìn average

**Mẹo:**
Khi API “thỉnh thoảng chậm”, xem latency percentile và distributed trace trong Application Insights/Azure Monitor, rồi phân rã thời gian theo SQL, HTTP dependency, queue hoặc application span.

**Tại sao hữu ích:**
Average có thể đẹp dù một nhóm nhỏ request rất chậm. p95/p99 phản ánh tail latency; trace cho thấy request chậm đang chờ dependency nào thay vì suy đoán từ CPU hoặc tổng request duration.

**Ví dụ:**
Endpoint có average 180 ms nhưng p99 4.8 s. Trace của nhóm p99 cho thấy 4.2 s nằm ở một partner API, trong khi SQL chỉ 60 ms. Điều tra tiếp timeout, connection reuse và latency của partner thay vì tối ưu EF Core không liên quan.

**Lưu ý:**
Sampling có thể bỏ mất trace hiếm; correlation bị đứt nếu propagation không đúng. Đừng chỉ tăng sampling vô hạn trong production — cân bằng chi phí telemetry và khả năng điều tra.

### Tip 4 — File upload cần validate nội dung, không tin extension hay `Content-Type`

**Mẹo:**
Với API/CMS nhận file, coi filename, extension và client-provided `Content-Type` là dữ liệu không đáng tin. Áp giới hạn size, allowlist loại file, kiểm tra signature khi phù hợp, đổi tên phía server và lưu ngoài web root hoặc object storage.

**Tại sao hữu ích:**
Attacker có thể gửi executable/script với extension giả hoặc path nguy hiểm. Validation nhiều lớp giảm khả năng upload trở thành remote execution, stored XSS hoặc vector làm cạn disk/memory.

**Ví dụ:**
Ảnh profile chỉ cho JPEG/PNG, stream trực tiếp tới Blob Storage sau validation thay vì đọc toàn bộ file vào `byte[]`; generated object key không lấy trực tiếp từ filename người dùng.

**Lưu ý:**
Magic bytes cũng không chứng minh file an toàn tuyệt đối. Với tài liệu không tin cậy, cân nhắc malware scanning và content transformation. Không log token, raw file content hoặc metadata nhạy cảm chỉ để debug upload failure.

### Tip 5 — AI code review phải kiểm tra repository source trước khi tin API được đề xuất

**Mẹo:**
Khi dùng AI coding agent để sửa .NET solution, yêu cầu nó ground kết luận vào package version, source hiện tại, tests và official API surface của repository; sau đó build/test thay vì chấp nhận patch vì code “trông đúng”.

**Tại sao hữu ích:**
Model có thể nhớ API từ version khác, giả định architecture không tồn tại hoặc tạo test chỉ xác nhận implementation mới. Repository-grounded verification biến AI thành công cụ tăng tốc khám phá thay vì nguồn sự thật.

**Ví dụ:**
Agent đề xuất overload mới của một NuGet package. Trước khi merge, kiểm tra `.csproj`/lock file, compile solution và chạy test liên quan; nếu API không tồn tại ở version đang dùng, chọn implementation tương thích hoặc nâng package có chủ đích.

**Lưu ý:**
Test pass không chứng minh requirement đúng. Review cả behavioral contract, security, migration và failure path; đặc biệt cảnh giác khi agent tự sửa test để khớp code vừa sinh.

## 🧠 Software Design

### Design 1 — Optimistic Concurrency bảo vệ lost update mà không giữ lock dài

**Khái niệm:**
Optimistic Concurrency cho phép nhiều actor đọc cùng state nhưng khi update phải chứng minh state chưa thay đổi, thường bằng `rowversion`, version number hoặc concurrency token.

**Vấn đề nó giải quyết:**
Hai nhân viên cùng mở một order. A đổi địa chỉ, B đổi trạng thái dựa trên snapshot cũ. Nếu update cuối ghi đè toàn bộ row mà không kiểm tra version, thay đổi hợp lệ của A có thể biến mất âm thầm.

**Ví dụ thực tế:**
EF Core cấu hình `rowversion`; `UPDATE` bao gồm version cũ trong `WHERE`. Nếu affected rows = 0, application nhận concurrency conflict và có thể reload, merge theo business rule hoặc yêu cầu user xác nhận thay vì silently overwrite.

**Trade-off:**
Không giữ database lock dài nên phù hợp workload có conflict thấp, nhưng conflict phải được xử lý rõ ở UX/API. Với invariant cạnh tranh cao như cấp một tài nguyên duy nhất, database constraint, atomic statement hoặc pessimistic locking có thể phù hợp hơn.

**Middle → Senior insight:**
Middle developer cần hiểu concurrency token và xử lý `DbUpdateConcurrencyException`. Senior / Technical developer phải xác định conflict semantics theo từng aggregate/field, quyết định retry, merge hay reject và phân biệt lost-update protection với invariant cần atomic enforcement ở database.

### Design 2 — Queue và Topic giải quyết hai ownership model khác nhau

**Khái niệm:**
Queue phân phối mỗi message cho một consumer cạnh tranh trong cùng logical workload; Topic + Subscription fan-out cùng event tới nhiều consumer độc lập, mỗi subscription có delivery state riêng.

**Vấn đề nó giải quyết:**
Nếu một `OrderCreated` cần Billing, Analytics và Fulfillment đều phản ứng, đặt ba worker cạnh tranh trên cùng queue khiến chỉ một bên nhận message. Ngược lại, tạo topic cho work item chỉ cần một worker xử lý có thể tăng complexity không cần thiết.

**Ví dụ thực tế:**
`GenerateInvoice` command đi vào queue để một invoice worker xử lý. `OrderCreated` event publish lên Azure Service Bus topic; Billing, CRM và Analytics có subscription riêng, retry/DLQ độc lập.

**Trade-off:**
Topic tăng fan-out, số subscription, chi phí vận hành và schema evolution pressure. Queue đơn giản hơn nhưng không phù hợp broadcast. Cả hai vẫn có duplicate delivery và cần idempotent processing theo failure model.

**Middle → Senior insight:**
Middle developer cần phân biệt command/work distribution với event fan-out. Senior / Technical developer phải thiết kế ownership, subscription filtering, retry/DLQ, ordering và schema compatibility dựa trên coupling giữa producer-consumer chứ không chọn queue/topic chỉ theo thói quen.

### Design 3 — Modular Monolith có thể là bước trưởng thành trước Microservices

**Khái niệm:**
Modular Monolith giữ một deployable application nhưng chia domain thành module có boundary, ownership và dependency rule rõ. Mục tiêu là modularity trước khi trả chi phí distributed systems.

**Vấn đề nó giải quyết:**
Một monolith không boundary dễ thành “big ball of mud”, nhưng tách Microservices quá sớm tạo network failure, distributed tracing, deployment orchestration và consistency complexity khi domain/team chưa đủ ổn định.

**Ví dụ thực tế:**
E-commerce chia `Catalog`, `Ordering`, `Payments` thành module với application/domain boundary riêng. Module không truy cập bảng/internal class của nhau tùy ý; integration đi qua explicit contract hoặc internal event. Chỉ khi Payments có scaling, compliance hoặc ownership độc lập rõ ràng mới cân nhắc tách deployable service.

**Trade-off:**
Một process vẫn chia sẻ failure/deployment blast radius và scaling unit. Boundary chỉ tồn tại nếu được enforce; nếu mọi module cùng query schema của nhau thì tên folder không tạo modularity. Microservices cho autonomy mạnh hơn nhưng đổi lại operational và consistency cost lớn hơn.

**Middle → Senior insight:**
Middle developer cần giữ dependency direction và contract giữa module. Senior / Technical developer phải đánh giá team topology, deployment frequency, scaling profile, data ownership và failure isolation để quyết định boundary nào chỉ cần logical separation và boundary nào thực sự đáng tách thành service.
